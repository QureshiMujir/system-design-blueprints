Project Name: Reinforcement Learning Environment + Agent (PPO) from Scratch

Status: specification — locked

1. Goal & Scope

Build, from scratch, in Python 3.11 + PyTorch, a Gymnasium-compatible vectorized reinforcement-learning environment runtime and a Proximal Policy Optimization learner: an env/vector-env API conformance layer, rollout collection into a pre-allocated buffer, Generalized Advantage Estimation, a clipped-surrogate PPO update with entropy bonus and value-function clipping, observation/reward running-statistics normalization, and a deterministic evaluation + reproducibility harness — validated against CartPole-v1 and LunarLander-v2 / LunarLanderContinuous-v2 as named benchmarks.

Phase-0 deliverable (packages):

  1. rl_agent_ppo.envs.registry — EnvSpec + a single deterministic CartPole-v1 construction path.
  2. rl_agent_ppo.training.seeding — master-seed derivation for env / network / RNG.
  3. rl_agent_ppo.training.config — PPOConfig schema + load-time validation.
  4. rl_agent_ppo.training.logger — structured JSONL run log.
  5. CI workflow running lint + unit tests + the Phase-0 conformance fixture.

Boundaries:

  • Provides: env API contract + conformance harness, rollout buffer, GAE, PPO learner (discrete + Gaussian continuous), observation/reward normalization wrappers, synchronous vectorization, checkpoint/resume, eval harness.
  • Delegates: physical env dynamics to Gymnasium-registered envs; tensor kernels to PyTorch; RNG primitives to NumPy Generator / torch.Generator.
  • Does NOT provide: pixel-observation (Atari) wrappers, recurrent (LSTM) policies, multi-agent envs, a distributed/async actor-learner architecture, a Rust or C++ env runner, hyperparameter auto-tuning.

Non-goals: beating Stable-Baselines3 / CleanRL on wall-clock; supporting arbitrary third-party env engines out of the box; GPU-accelerated batched simulation (Isaac Gym / EnvPool-style).

Deployment model: single-process CLI training job (python -m rl_agent_ppo train --config <path>), CPU or single-GPU, no server component; the eval harness runs in-process post-training or standalone from a checkpoint.

Users / operators: ML engineers training or reproducing PPO baselines; researchers ablating implementation details; CI itself (nightly conformance run).

What later phases unlock: Phase 7 vectorization unlocks Atari-scale throughput headroom; Phase 9 continuous-action unlocks MuJoCo/PyBullet-class control; Phase 10 checkpoint/resume unlocks long-running/interruptible jobs; Phase 11's conformance suite unlocks differential testing against CleanRL/SB3.

Language: Python 3.11 (typing, structural pattern matching, tomllib) + PyTorch >= 2.1. Rationale: every cited reference implementation (CleanRL, SB3, Tianshou) is Python/PyTorch; NumPy interop for the buffer is first-class; Gymnasium is Python-native. Rejected: Julia (thin Gymnasium interop, small on-policy RL ecosystem outside ReinforcementLearning.jl); Rust (no mature autodiff ecosystem — reserved for the deferred env-runner seam only, never the learner); C++ (development velocity too low for an ablation-heavy research codebase).

Prerequisites: probability, multivariate calculus, the policy-gradient theorem (REINFORCE, actor-critic baseline), PyTorch autograd + nn.Module + torch.distributions, vectorized (N, T, ...) array reasoning.

Timeline: Phase 0 — 1 week. Full 12-phase system (Phase 0 through Phase 11) — 10 weeks full-time, ~4 months at 0.5 FTE.

Deferrals: PhaseDeferred("§31 Scalability Analysis") — recurrent (LSTM) policy trunks and async/subprocess vectorization beyond num_envs=64; PhaseDeferred("§36 Alternative Architectures") — Atari pixel wrappers + CNN encoder and the gRPC Rust env-runner bridge; PhaseDeferred("§27 Compatibility & Versioning") — multi-task / curriculum scheduling across an env pool.

2. Why Build This

  • On-policy default: PPO is the inner-loop algorithm of RLHF stacks, robotics-simulation benchmarks, and large-action-space game AI — Schulman et al. 2017.
  • The sample-inefficiency tradeoff is deliberate: on-policy avoids the deadly triad's worst instabilities that off-policy methods (DQN, SAC) manage only with target networks and replay buffers — Mnih et al. 2015 Nature DQN versus Schulman et al. 2017.
  • PPO approximates TRPO's trust region without a conjugate-gradient solve — Schulman et al. ICML 2015 TRPO motivates the KL constraint; Schulman et al. 2017 approximates it with a clipped ratio.
  • The measured PPO-over-TRPO win is mostly code-level optimizations, not the algorithm itself — Engstrom et al. ICLR 2020; Huang et al. 2022 (the 37 implementation details).
  • What matters empirically is task-dependent and in places counter to folklore (separate actor/critic nets, advantage normalization, orthogonal init) — Andrychowicz et al. ICLR 2021.
  • Reported RL results are fragile to seeds and implementation choices without disciplined evaluation — Henderson et al. AAAI 2018.
  • A correct vectorized rollout runner (env API + buffer) is reusable across the entire on-policy family (A2C, A3C, IMPALA, PPG) and underlies off-policy pipelines too.
  • RL bugs are silent: off-by-one errors in GAE, terminated/truncated bootstrap leaks, and advantage-normalization scope errors do not raise exceptions — they degrade the learning curve.

What Mastery Looks Like

  • Derive and hand-verify the GAE recursion over a 5-step trajectory without a reference implementation — Phase 4 (§16).
  • Explain why terminated and truncated require different bootstrap treatment, and reproduce the bug class that conflating them causes — Phase 1 (§13).
  • Implement the clipped surrogate objective and show, empirically, the clip-fraction / approx-KL telemetry that proves it is constraining updates — Phase 5 (§17).
  • Diagnose a stalled training curve using entropy, explained-variance, and approx-KL telemetry alone, without touching model code — Phase 8 (§20).
  • Add continuous-action (Gaussian policy) support without modifying the GAE or PPO-update core — Phase 9 (§21).
  • Reproduce a bitwise-identical training curve from a seed + config across two separate runs — Phase 10 (§22).
  • Run a differential test against CleanRL/SB3 on a fixed seed and explain any divergence in terms of a named implementation detail — Phase 11 (§23).

Env Core: the physical Gymnasium environment instances (N of them); untrusted with respect to the training process because env dynamics may come from third-party registered packages (T2, §24).

VecEnv Wrapper: the synchronous vectorization boundary; steps N env instances in lockstep inside the same process and returns batched (N, ...) arrays; this is the sole point of contact between the algorithm and the Gymnasium VectorEnv protocol (ADR-03, ADR-04).

Obs Normalizer: a RunningMeanStd applied per observation component; updates only during COLLECT, frozen during EVAL (I2); its state is part of the checkpoint (I10).

Reward Normalizer: a parallel RunningMeanStd over discounted return magnitude; scales reward before it enters the buffer so the value function is fit against a stationary-scale target (ADR-09).

Rollout Buffer: a single-writer, pre-allocated (T, N, ...) block; the decoupling boundary between data collection and policy update (I3, I5); never read across an update boundary.

GAE Computer: walks the buffer backward once, producing advantages and returns (I7); the most error-prone routine in the system, unit-tested against closed-form boundary cases.

Policy/Value Networks: pure forward functions from observation to an action distribution and a scalar value estimate; hold no rollout state themselves.

PPO Learner: consumes the flattened buffer, runs K epochs of shuffled-minibatch clipped-surrogate updates, optionally halting early on a KL budget (I14); the sole writer of network parameters.

Checkpoint Store: durable, versioned (ADR-17, §27) persistence of weights, optimizer state, RNG state, normalizer stats, and config (I10); the only component that crosses the process-restart boundary.

Telemetry/Logger: structured JSONL + TensorBoard scalars; the primary diagnostic surface (§7 debugging methodology); write-only from the training loop's perspective.

Eval Harness: reads the checkpoint's frozen normalizer state and current policy, runs disjoint-seed episodes, and writes a report; never mutates training-side state (I11).

6. Design Principles

P1 — env-API-compat. The runner consumes any object satisfying the Gymnasium VectorEnv protocol and depends on no Gymnasium internals. Tradeoff: forgoes convenience shortcuts (env.unwrapped, private attributes). Operational implication: a custom or third-party env works without runner code changes. Violating it means the runner silently binds to one env library version, e.g. reaching into env.spec.max_episode_steps breaks the moment a custom env omits spec.

P2 — vectorized-rollout-only. There is no single-env code path in training; all rollouts are (N, T) shaped, and N=1 runs through the identical path as N=64. Tradeoff: slightly more bookkeeping for the trivial case. Operational implication: eliminates "works on 1 env, breaks on N" bugs. Violating it produces the classic bug of collapsing a per-env (N,) array into a scalar mid-buffer and losing per-env return tracking permanently.

P3 — deterministic-rng-from-seed. A single integer seed determines all randomness: env reset seeds, network init, minibatch shuffling, eval episode seeds. Tradeoff: extra plumbing to avoid any global RNG. Operational implication: two runs with the same seed and code are bitwise identical on the same hardware. Violating it produces irreproducible regressions that cannot be bisected.

P4 — advantage-normalization-explicit. Advantages are normalized to zero mean, unit std across the full T*N rollout batch, never per-minibatch, and this is a config flag defaulting to on. Tradeoff: requires a full-batch reduction before any minibatch is formed. Operational implication: consistent gradient scale across minibatches. Violating it (normalizing per-minibatch) makes each minibatch's gradient direction depend on which 32-sample slice it happened to draw.

P5 — observation-normalization-per-env. Observation normalization uses per-env (or per-component) running statistics, updated only during collection, frozen during evaluation, and checkpointed alongside weights. Tradeoff: extra state to persist and restore. Operational implication: eval-time obs distribution matches train-time. Violating it causes a policy to silently degrade when a checkpoint loses its running stats and evaluation runs on unnormalized input.

P6 — action-space-pluggable. The actor head is constructed from the env's action space through exactly one dispatch point (make_distribution); Discrete maps to Categorical, Box to diagonal Gaussian, MultiDiscrete to factorized Categorical. Tradeoff: one extra layer of indirection at agent construction. Operational implication: adding a new space type touches one function. Violating it (ad hoc per-env-type branching scattered through the codebase) produces log-prob shape mismatches that train silently on the wrong gradient.

P7 — kl-budget-as-stop. Each PPO update runs up to K epochs but halts early if approximate KL between current and rollout-collection policy exceeds 1.5 * target_kl. Tradeoff: an extra forward pass's worth of bookkeeping per epoch. Operational implication: bounds policy drift within a single update. Violating it (no KL stop) lets a long inner-epoch loop drive the policy arbitrarily far from the data it was trained on, occasionally to a collapsed, near-deterministic policy.

P8 — value-clip-explicit. The value loss uses the pessimistic clipped form max((V - R)^2, (clip(V, V_old - eps, V_old + eps) - R)^2), a config flag defaulting to on. Tradeoff: requires storing V_old in the buffer even though it is reconstructible from a stale forward pass. Operational implication: bounds how far the value function can move per update, keeping in-rollout advantages approximately valid across epochs. Violating it lets the value function overfit within a single update and destabilize the next rollout's advantage estimates.

P9 — entropy-coefficient-anneal. The entropy bonus coefficient is a linear function of global_step / total_env_steps, never of iteration count. Tradeoff: requires threading global_step through the schedule instead of a simple counter. Operational implication: the schedule's real-world duration is invariant to num_envs/T changes. Violating it (annealing by iteration) silently changes the exploration schedule's wall-clock/step-count meaning whenever the rollout shape changes.

P10 — eval-disjoint-envs. Evaluation uses env instances seeded disjointly from training (seed + 1_000_000 + i), deterministic action selection, and never updates any running statistic. Tradeoff: a second env pool must be constructed and held read-only. Operational implication: eval numbers are uncontaminated by training-time-favorable seeds. Violating it lets a running normalizer statistic leak eval-observed states into the train-time policy's input distribution.

P11 — every-hyperparam-logged. Every hyperparameter, including derived quantities (rollout size, minibatch count, total updates), is written to a run manifest before the first training step. Tradeoff: a small startup-latency cost for the manifest write. Operational implication: any run's exact configuration is recoverable from its output directory alone. Violating it produces the un-reproducible-best-run failure: one good run whose hyperparameters were never recorded.

P12 — no-leaky-globals. No module-level mutable state, no global RNG, no global device, no global config; every function/class takes its dependencies as arguments or constructor parameters. Tradeoff: more explicit wiring at call sites. Operational implication: tests are order-independent; a fresh PpoAgent, RolloutBuffer, EnvRunner per test suffices. Violating it produces test-order-dependent failures where one test's mutation of a module-level singleton corrupts a later test's expectations.

Debugging methodology: when a run's return curve stalls, first read telemetry, never model code. Check entropy (collapsed early -> exploration-starved, violates the intent of P9); check explained variance (near zero -> the value function is not fitting, check I8's clip fraction); check approx-KL (near zero -> the policy is not moving, check I14's early-stop counter and the LR schedule); check gae_bootstrap_mismatch_count and rollout_age_updates (nonzero -> I4 or I1 has been violated by a code change). Only after telemetry is exhausted does the methodology move to reading ppo_update.py and gae.py directly.

8. Domain Model

MDP tuple

M = (S, A, P, R, gamma, rho0)
S: state space   A: action space   P(s'|s,a): transition kernel
R(s,a): reward function   gamma in [0,1): discount   rho0: initial-state distribution

Return

G_t = sum_{k=0}^{inf} gamma^k * r_{t+k+1}

Value / action-value / advantage

V_pi(s)   = E_pi[ G_t | s_t = s ]
Q_pi(s,a) = E_pi[ G_t | s_t = s, a_t = a ]
A_pi(s,a) = Q_pi(s,a) - V_pi(s)

TD residual

delta_t = r_t + gamma * V(s_{t+1}) * (1 - d_{t+1}) - V(s_t)

GAE recursion (Schulman et al. ICLR 2016; I7)

A_t^{GAE(gamma,lambda)} = sum_{l=0}^{inf} (gamma*lambda)^l * delta_{t+l}      [forward form]
A_t = delta_t + gamma * lambda * (1 - d_{t+1}) * A_{t+1}                      [backward recursion]

Advantage normalization (P4)

A_hat_t = ( A_t - mean(A) ) / ( std(A) + 1e-8 )     [computed once, over the full T*N batch]

PPO probability ratio and clipped surrogate (Schulman et al. 2017)

r_t(theta) = pi_theta(a_t|s_t) / pi_theta_old(a_t|s_t)
L_CLIP(theta) = E_t[ min( r_t(theta) * A_hat_t , clip(r_t(theta), 1-eps, 1+eps) * A_hat_t ) ]

Value loss, pessimistic clip (ADR-05/P8)

L_V(theta) = E_t[ max( (V_theta(s_t) - R_t)^2 ,
                       (clip(V_theta(s_t), V_old(s_t)-eps, V_old(s_t)+eps) - R_t)^2 ) ]

Entropy bonus and total objective

H_t = H[ pi_theta(.|s_t) ]
L(theta) = -L_CLIP(theta) + c1 * L_V(theta) - c2(step) * H_t      [c2 anneals per P9]

Terminated-vs-truncated bootstrap rule (I4)

bootstrap_mask_t = 1 - terminated_t          [never 1 - (terminated_t OR truncated_t)]
R_t = r_t                          if terminated_t
R_t = r_t + gamma * V(s_{t+1})     if truncated_t and not terminated_t

Malformed-Input Examples

  • Action outside Discrete(n) range (e.g. action=5 for Discrete(4)): VecEnv.step must raise ValueError at the step boundary, never silently wrap via modulo.
  • Reward NaN/Inf from a pathological custom env: RolloutBuffer.add rejects via shape_check, never silently poisoning the GAE backward pass.
  • Observation shape mismatch (env returns (5,) when the declared space is (4,)): caught by the Phase 1 conformance fixture, never by a downstream broadcasting error deep in the network forward pass.

Failure-Path Example

A sync-backend env raises mid-step() (e.g. a physics NaN). The exception propagates to env_runner; the in-progress rollout is aborted; the offending env is reset fresh; the event is logged to telemetry with the originating stack trace rooted in envs/, distinguishing an env-side fault from an agent-side one. No partial buffer write is retained (I1, I3).

16. Phase 4 — GAE + Advantage Normalization

16.1 Objectives

  • Implement compute_gae (§11) exactly per the §8 backward recursion, satisfying I4 and I7.
  • Wire RolloutBuffer.finalize() to call compute_gae and populate advantages/returns in place.
  • Implement per-rollout advantage normalization (P4, ADR-07) as a config-gated step applied once per finalized batch.

16.2 Detailed Implementation Steps

  1. Implement compute_gae(rewards, values, dones, bootstrap_value, bootstrap_done, gamma, gae_lambda) per §8's backward-recursion equations (Schulman et al. ICLR 2016 GAE; I7's single-backward-pass guarantee).
  2. Merge terminated/truncated into a single dones mask for the recursion's bootstrap-zeroing term, while preserving the raw terminated flag separately for the I4 bootstrap-source rule (§8's terminated-vs-truncated equations): truncated steps bootstrap through V(s_{t+1}), terminated steps do not.
  3. Wire RolloutBuffer.finalize(bootstrap_value, bootstrap_done) to call compute_gae and write advantages/returns (§11); this transitions the state machine's FINALIZE state (§8).
  4. Implement advantage normalization as a pure function over the full (T*N,) flattened advantage array, applied once, after finalize(), before as_flat_tensors() returns to the (not-yet-existent) PPO update (P4; normalize_advantages: bool config flag, default on, ADR-07).
  5. Write test_gae.py with three fixtures: (a) gae_lambda=0 reduces to 1-step TD; (b) gae_lambda=1 reduces to Monte-Carlo return minus value; (c) the §8 5-step hand-computed worked example, asserting each A_t/R_t to 1e-4 absolute tolerance.

16.3 Deliverable

A RolloutBuffer.finalize() that produces mathematically verified GAE advantages and returns, with advantage normalization as an explicit, tested, toggleable step.

16.4 Acceptance Criteria

  • test_gae.py's 5-step fixture matches the §8 worked example's A_t/R_t values to 1e-4 absolute tolerance for all t in {0..4}.
  • test_gae.py's lambda=0 fixture matches 1-step TD residuals exactly (1e-6 tolerance); lambda=1 fixture matches Monte-Carlo-return-minus-value exactly.
  • With normalize_advantages=True, the flattened advantage batch has abs(mean) < 1e-6 and abs(std - 1.0) < 1e-3 post-normalization.
  • gae_compute_ms for a (T=128, N=8) rollout is under the §4 rollout-collection latency budget's contribution (sub-millisecond; GAE itself is O(T*N), not the bottleneck).

16.5 Conformance Fixtures

  • tests/unit/test_gae.py::test_five_step_worked_example — the §8 table, encoded as exact expected floats.
  • tests/unit/test_gae.py::test_lambda_zero_boundary — property fixture: GAE reduces to 1-step TD (I7 regression target).
  • tests/unit/test_gae.py::test_lambda_one_boundary — property fixture: GAE reduces to Monte-Carlo return.
  • tests/unit/test_gae.py::test_malformed_shape_mismatch — malformed case: rewards.shape != values.shape raises BufferStateError, never a silent NumPy broadcast.
  • tests/unit/test_gae.py::test_terminated_vs_truncated — seeded-replay regression proving I4: a truncated episode's A_t differs from an otherwise-identical terminated episode's A_t by exactly the bootstrap term gamma * V(s_{t+1}).

16.6 Pitfalls

  • Using 1 - dones[t] instead of 1 - dones[t+1] as the bootstrap mask — an off-by-one that silently shifts every advantage by one timestep; caught only by the hand-computed fixture, never by a shape check.
  • Merging terminated and truncated into dones for the recursion's mask term but then also using the merged flag for the bootstrap-source decision — violates I4; the recursion's zeroing mask and the bootstrap-source rule are two different uses of two different flags.
  • Normalizing advantages before finalize() has fully populated the returns array — silently normalizes a zero-filled or partially-filled array on a code path that races finalize()'s two sub-steps.

16.7 Performance Concerns

  • compute_gae's Python-level for t in reversed(range(T)) loop is O(T) Python overhead independent of N (N is vectorized via NumPy broadcasting inside the loop body); at T=128 this is negligible against the §4 budget, but a T=8192 config (unusual for this project's target envs) would surface this loop as the first learner-side bottleneck ahead of the update step.

16.8 Edge Cases

  • A rollout with zero episode terminations at all (dones all-zero) — GAE must still produce finite, correctly bootstrapped advantages using only the final bootstrap value.
  • A rollout where every single step is a terminated episode boundary (very short episodes, e.g. a pathological 1-step MDP) — the recursion's last_gae must reset to the delta term alone at every step, never accumulate across episode boundaries.
  • gae_lambda exactly at the boundary values {0.0, 1.0} — must not require special-casing in the recursion; the general formula already reduces correctly (verified by 16.5's fixtures).

16.9 Failure Analysis

  • Symptom: value loss (once Phase 5 exists) never decreases below a large plateau. Root cause: advantage normalization applied per-minibatch instead of per-rollout (an ADR-07 violation smuggled in during a later refactor). Debug method: log advantages.std() immediately before minibatch splitting versus after; the two should be identical if normalization ran once at the rollout level. Signal: per-minibatch std values cluster near 1.0 individually but the full-rollout std does not. Recovery: move the normalization call to run exactly once, immediately after finalize(), before any minibatch split.

16.10 Operational Notes

  • gae_bootstrap_mismatch_count (I4's telemetry) must read exactly 0 across the entire Phase 4-11 test matrix; any nonzero reading blocks merge, per the §28 gating policy.

17.1 Objectives

  • Implement the clipped surrogate objective, pessimistic value loss, entropy bonus, and their combination into a single scalar loss (§8 equations).
  • Implement the K-epoch, M-minibatch update loop with the T-major-then-N flatten order and agent-owned shuffle RNG (I6).

17.2 Detailed Implementation Steps

  1. Implement losses.clipped_surrogate(ratio, advantages, clip_ratio) per §8's L_CLIP equation (Schulman et al. 2017); unit-test the clip boundary at ratio = 1 +/- clip_ratio exactly.
  2. Implement losses.value_loss(value, value_old, returns, clip_ratio, clip_value_loss) per §8's pessimistic clipped form (ADR-05/P8; openai/baselines ppo2 reference).
  3. Implement losses.entropy_bonus(distribution) and the annealed coefficient via schedules.linear_anneal driven by global_step / total_env_steps, never iteration count (P9, I12).
  4. Implement PpoUpdater.update(buffer): flatten (T,N) to (T*N,) in T-major-then-N order (matching CleanRL's convention, cited §5); shuffle indices using the updater's own Generator(seed) (I6); split into num_minibatches (ADR-16 minibatch count from config); run num_epochs_per_update epochs.
  5. Implement the approximate-KL early-stop check (Schulman 2020 blog, cited §5's papers list via the KL approximation formula (exp(log_ratio) - 1) - log_ratio) between epochs, not mid-epoch (I14); halt remaining epochs if mean(approx_kl) > 1.5 * target_kl.
  6. Implement global-norm gradient clipping at max_grad_norm=0.5 (ADR-13/Huang et al. 2022 detail #12) and the linear LR anneal to zero over total_env_steps (ADR-14).
  7. Write test_clipped_surrogate.py and test_value_loss.py against hand-computed boundary cases at ratio in {1-eps, 1, 1+eps, 1+2*eps}.

17.3 Deliverable

A complete PPO update step: given a finalized RolloutBuffer, produces UpdateStats (§11) and mutates network parameters exactly once per minibatch step, with KL-budget early stopping and LR annealing active.

17.4 Acceptance Criteria

  • CartPole-v1 mean episodic return reaches >= 475 (over 100 consecutive eval episodes) within 30,000 env steps, matching the §4 wall-clock target of <= 90 s on the 8-core reference CPU.
  • test_clipped_surrogate.py matches hand-computed L_CLIP values at the four boundary ratios to 1e-6.
  • kl_early_stop_epoch (I14 telemetry) is logged every update; across the CartPole acceptance run it fires on fewer than 5% of updates (a well-tuned run rarely needs it, per §5 citation 9's Huang et al. finding).
  • clip_fraction telemetry (ADR-21) is nonzero but below 0.3 by the final 10% of training (proof the clip is active but not dominating).

17.5 Conformance Fixtures

  • tests/unit/test_clipped_surrogate.py::test_clip_boundary — the four-ratio hand-computed fixture.
  • tests/unit/test_value_loss.py::test_pessimistic_clip — fixture with V_old, V_new, return chosen so the clipped and unclipped terms disagree, asserting the max() selects correctly.
  • tests/integration/test_cartpole_smoke.py::test_return_threshold — regression: 30,000-step run hits return >= 475; seeded-replay across two CI runs must match within +/- 5 return (float nondeterminism tolerance on GPU only; CPU must match exactly per I9).
  • tests/unit/test_clipped_surrogate.py::test_malformed_ratio — malformed case: a NaN ratio (from a degenerate log-prob) raises before entering the min()/clip() chain, never silently propagating NaN into the optimizer.

17.6 Pitfalls

  • Computing the surrogate loss to maximize rather than minimize by forgetting the sign flip in the total objective L(theta) = -L_CLIP + ... — trains a policy that anti-optimizes, producing a return curve that goes down instead of up, easily mistaken for "not learning" rather than "learning the opposite." cross-ref: §8 total-objective equation.
  • Flattening (T,N) in N-major-then-T order instead of T-major-then-N — every array remains internally consistent but silently mismatched against any external tool (e.g. a differential test against CleanRL, Phase 11) that assumes the canonical order.
  • Checking the KL early-stop condition inside the minibatch loop instead of between epochs — violates I14 and produces inconsistent behavior depending on minibatch count.
  • Using PyTorch's default Adam eps=1e-8 instead of 1e-5 — a one-character diff (ADR-13) that measurably slows convergence on the CartPole acceptance benchmark.

17.7 Performance Concerns

  • Learner update time budget is 180 ms CPU / 45 ms GPU for a 1,024-sample rollout at K=10, M=4 (§4); a minibatch loop that reconstructs the Categorical/Gaussian distribution object from scratch per minibatch rather than per forward pass adds measurable Python-level overhead at this scale.

17.8 Edge Cases

  • A minibatch whose advantages are all identical (degenerate rollout, e.g. all-zero reward) — advantage normalization's std() + 1e-8 denominator must not divide by exactly zero.
  • target_kl=None (KL early-stop disabled) — the K-epoch loop must run all num_epochs_per_update epochs unconditionally; kl_early_stop_epoch logs -1.
  • num_minibatches not evenly dividing T*N — must fail config validation (ADR-18) at load time, not silently drop or duplicate samples in the last minibatch.

17.9 Failure Analysis

  • Symptom: training return climbs briefly then collapses to a fixed low value and never recovers. Root cause: KL early-stop disabled or target_kl set too high, allowing a single bad update to drive the policy into a collapsed near-deterministic state (P7's named failure mode). Debug method: inspect approx_kl history around the collapse iteration; look for a spike immediately preceding it. Signal: kl_early_stop_epoch == -1 for the collapse iteration despite approx_kl far exceeding target_kl. Recovery: lower target_kl or re-enable the early stop; roll back to the last good checkpoint (§22).

17.10 Operational Notes

  • UpdateStats (§11) is the primary per-iteration telemetry payload; §7's debugging methodology assumes every field listed there is populated on every update, including when the KL early-stop fires.

18. Phase 6 — Observation/Reward Normalization

18.1 Objectives

  • Implement RunningMeanStd (§11) and wire it as observation_normalize.py and reward_scale.py wrappers (ADR-08, ADR-09).
  • Enforce I2 (frozen statistics at eval) and I5-adjacent checkpoint inclusion (I10) for normalizer state.
  • Validate empirically that normalization improves LunarLander-v2 convergence over the un-normalized Phase 5 baseline.

18.2 Detailed Implementation Steps

  1. Implement RunningMeanStd.update(batch) using Welford's parallel-variance algorithm (numerically stable accumulation, no code-body shown here — signature only per §11).
  2. Implement observation_normalize.py: a wrapper applying (obs - mean) / sqrt(var), clipped to +/- obs_clip (default 10.0, ADR-08), updating statistics only when training=True.
  3. Implement reward_scale.py: scale reward by the running std of the discounted return (ADR-09), never sign-clipping (that variant is reserved for the deferred Atari regime, §36).
  4. Wire both wrappers' RunningMeanStd instances into CheckpointRecord.normalizer_stats (§11, I10).
  5. Wire EvalHarness to construct wrapper instances with training=False, freezing statistics per I2/P10.
  6. Write test_running_stats.py: Welford accumulation matches a batch numpy.mean/numpy.var computation to 1e-6 after 10,000 samples; a frozen (training=False) instance's mean/var are provably unchanged across 1,000 normalize() calls.

18.3 Deliverable

Observation and reward normalization wrappers with checkpointed running statistics, frozen at evaluation, validated to improve LunarLander-v2 convergence over the Phase 5 unnormalized baseline.

18.4 Acceptance Criteria

  • LunarLander-v2 mean episodic return reaches >= 200 within 1,000,000 env steps with normalization enabled, matching the §4 wall-clock target (<= 35 min CPU / <= 12 min GPU).
  • The same config with normalize_observations=False either fails to reach return 200 within the same step budget or reaches it measurably later — recorded as an ablation data point feeding Phase 8 (§20).
  • test_running_stats.py Welford-vs-batch comparison passes at 1e-6 tolerance.
  • A checkpoint saved mid-training and reloaded produces identical RunningMeanStd.mean/var to the pre-save values (I10 regression).

18.5 Conformance Fixtures

  • tests/unit/test_running_stats.py::test_welford_matches_batch — numeric parity fixture.
  • tests/unit/test_running_stats.py::test_frozen_at_eval — I2 regression: 1,000 normalize() calls with training=False leave mean/var bit-identical.
  • tests/unit/test_running_stats.py::test_malformed_batch_shape — malformed case: a batch whose trailing dimension mismatches the normalizer's configured shape raises EnvContractError.
  • tests/integration/test_checkpoint_resume.py::test_normalizer_stats_roundtrip — seeded-replay: save, reload, re-run 100 steps, compare against a no-reload control run.

18.6 Pitfalls

  • Updating reward-normalizer statistics during the eval harness's episodes — a direct I2/I11 violation that inflates eval numbers by leaking eval-time reward distribution into future training-time scaling.
  • Clipping observations to +/- obs_clip before computing the running mean/var instead of after normalizing — silently biases the statistics toward the clip bounds rather than the true distribution.
  • Forgetting to include normalizer_stats in the checkpoint (I10) — produces the exact P5-named failure: a policy that trained well but evaluates poorly because the loaded checkpoint has no running stats and falls back to identity normalization.

18.7 Performance Concerns

  • Welford's algorithm is O(1) additional work per observation dimension per step; at CartPole/LunarLander scale this is immeasurable against the §4 rollout-collection budget, but the update must not allocate a new array per call (reuse in-place accumulation buffers).

18.8 Edge Cases

  • The very first observation ever seen (count == 0) — variance is undefined; the implementation must special-case count < 2 to avoid a divide-by-zero rather than silently returning NaN variance.
  • An observation dimension with genuinely zero variance across the whole run (a constant sensor reading) — normalization must not divide by zero; the + 1e-8-style epsilon floor applies here identically to the advantage-normalization case (P4).

18.9 Failure Analysis

  • Symptom: a checkpoint that trained to return 250 on LunarLander evaluates at return -100 after a process restart. Root cause: checkpoint saved before RunningMeanStd was added to CheckpointRecord (an I10 violation from an incomplete migration). Debug method: compare checkpoint_fields_present bitmap against the expected five-field set (I10). Signal: normalizer_stats bit is 0. Recovery: refuse to load (fail closed per I10), regenerate the checkpoint from a point after the normalizer was wired in.

18.10 Operational Notes

  • The LunarLander normalization ablation (18.4) is the first data point recorded into the Phase 8 (§20) implementation-details ablation matrix; record it in benchmarks/lunarlander_results.jsonl verbatim.

  3. Extend env_runner.collect_rollout to accept N > 1 with zero code-path branching versus the Phase 2 N=1 path (P2 verification point).
  4. Extend RolloutBuffer sizing and EnvSpec replication to build N per-index specs from one master seed (seed + idx derivation, P3, reused unmodified from §11).

  6. Run benchmarks/bench_vector_env.py at N in {1, 8, 64, 128} and record steps/second against the §4 table.

19.3 Deliverable

A SyncVectorEnv implementation meeting the §4 throughput targets at N=8, validated for parity against independent single-env runs, with the training loop unmodified from Phase 2 onward except for shape.

19.4 Acceptance Criteria

  • N=8 sync vectorized throughput measures 35,000 - 45,000 steps/s on the reference 8-core CPU (§4).
  • N=128 measures at or below the 120,000 steps/s ceiling (§4); a config requesting N > 128 logs a throughput-ceiling warning per ADR-04's ceiling note.
  • test_vector_env_parity.py shows byte-identical per-env-index observation trajectories between the vectorized run and 8 independent single-env runs sharing the same per-env seed.
  • CartPole-v1 wall clock to return >= 475 at N=8 matches or improves on the Phase 5 N=1 wall-clock baseline (§4's <= 90 s target).

19.5 Conformance Fixtures

  • benchmarks/cartpole_results.jsonl::vec_env_throughput_N8_N64_N128 — recorded steps/second at each N, regression-checked against the §4 table on every release (ADR-26).
  • tests/integration/test_vector_env_parity.py::test_per_env_seed_isolation — seeded-replay: env index 3 under N=8 produces the identical trajectory to a standalone N=1 run seeded seed+3.
  • tests/integration/test_vector_env_parity.py::test_malformed_action_batch — malformed case: an action batch of shape (N-1, ...) (one short) raises EnvContractError at SyncVectorEnv.step, never a silent NumPy broadcast that drops the last env.

19.6 Pitfalls

  • Autoreset that reuses the pre-reset observation in the batched output instead of the fresh post-reset observation — silently feeds the agent one stale observation per episode boundary, at every env, for the entire training run.
  • Deriving per-env seeds as seed * idx instead of seed + idx — collapses to identical seeds for idx=0 regardless of seed, silently reducing effective diversity across envs.
  • Assuming SyncVectorEnv's sequential inner loop preserves wall-clock determinism identically to AsyncVectorEnv — it does, but only because sync is the chosen default (ADR-04); do not generalize this assumption to the deferred async backend without re-deriving I9's guarantee.

19.7 Performance Concerns

  • Sync vectorization amortizes wrapper-stack Python overhead per rollout but not per env; each of the N inner step() calls still pays full interpreter cost — this is exactly the §4-documented N=128 ceiling, and the lever beyond it is the deferred async/subprocess backend (§31).

19.8 Edge Cases

  • All N envs terminating on the exact same step (synchronized episode length, e.g. a fixed-length custom MDP) — autoreset must handle a fully-simultaneous reset across all N slots without any ordering bug.
  • N=1 must remain a legal, tested configuration of SyncVectorEnv itself (not just of the pre-Phase-7 single-env path) — regression-tested by reusing the Phase 2 fixtures unchanged.

19.9 Failure Analysis

  • Symptom: test_vector_env_parity.py fails only for env indices >= 1, index 0 always matches. Root cause: the per-env seed derivation used seed unmodified for every index instead of seed + idx, so every env shares env index 0's seed. Debug method: log the derived seed per index at SyncVectorEnv construction and diff against the expected seed+idx sequence. Signal: all indices' derived seeds are identical. Recovery: fix the derivation call site; re-run the parity fixture.

19.10 Operational Notes

  • bench_vector_env.py's recorded throughput numbers are the primary input to §34's back-of-envelope capacity model and to §31's scalability analysis; re-run and re-record on every hardware change.

21. Phase 9 — Continuous-Action Support (Gaussian Policy)

21.1 Objectives

  • Extend make_distribution (P6) to Box action spaces via a diagonal Gaussian with state-independent log-std (ADR default per Andrychowicz et al. 2021's finding, cited §5).
  • Validate on LunarLanderContinuous-v2 without modifying compute_gae, PpoUpdater, or RolloutBuffer (proving P6's single-dispatch-point claim).
  • Extend the conformance harness (Phase 1) to cover the Box row of §8's space taxonomy table.

21.2 Detailed Implementation Steps

  1. Extend ActorCritic's policy head to emit (mu, log_sigma) for Box spaces; log_sigma is a state-independent learned parameter vector, not a function of the observation (ADR default, contrasted against the rejected state-dependent variant).
  2. Extend make_distribution(action_space, head_outputs) (P6's single dispatch point, unmodified since Phase 1 except for this new branch) to construct torch.distributions.Independent(Normal(mu, sigma), 1) for Box spaces.
  3. Extend action clamping: sampled actions are clamped to [low, high] before being sent to env.step, while log_prob is computed on the unclamped sample (a documented, tested convention — clamping after log-prob avoids a density-correction term this project does not implement).
  4. Extend RolloutBuffer's action field dtype/shape handling for continuous (N, action_dim) float32 actions — no structural change to RolloutBuffer itself (§11), only to the dtype passed at construction.
  5. Extend conformance/env_api_contract.py with a Box-space fixture run against LunarLanderContinuous-v2.
  6. Write test_distributions.py additions: Gaussian log_prob/entropy match closed-form values for a fixed (mu, sigma) pair to 1e-6.

21.3 Deliverable

Gaussian-policy continuous-action support validated end-to-end on LunarLanderContinuous-v2, with zero modifications to the GAE, PPO-update, or buffer core (only the single make_distribution dispatch point and the policy head extended).

21.4 Acceptance Criteria

  • LunarLanderContinuous-v2 mean episodic return reaches >= 200 within 1,000,000 env steps, matching the §4 wall-clock target adjusted for the continuous action head's marginally larger parameter count (<= 40 min CPU / <= 14 min GPU).
  • git diff between Phase 8's final state and this phase's buffer/, agent/ppo_update.py, and agent/ losses.py shows zero changes (P6 structural-isolation proof).
  • Gaussian closed-form log_prob/entropy test passes at 1e-6 tolerance.
  • The Box-space conformance fixture passes all six §8 Env API Contract rows.

21.5 Conformance Fixtures

  • conformance/fixtures/lunarlander_continuous_contract.json — golden expected shapes/dtypes for the Box space row.
  • tests/unit/test_distributions.py::test_gaussian_closed_form — closed-form Gaussian log_prob/entropy fixture.
  • tests/unit/test_distributions.py::test_malformed_box_bounds — malformed case: an action space with low > high on any dimension raises EnvContractError at agent construction, not at first step().
  • tests/integration/test_lunarlander_continuous_smoke.py::test_seeded_replay — 1,000,000-step seeded regression (CPU determinism, I9).

21.6 Pitfalls

  • Clamping the sampled action before computing log_prob, silently introducing a density mismatch between the action actually executed in the env and the log-probability the clipped surrogate assumes.
  • Making log_sigma state-dependent (a function of the observation) as a "more expressive" default without reading Andrychowicz et al. 2021 first — the paper's finding motivating the state-independent default is task-dependent, and state-dependent log-std has a documented tendency to collapse to near-zero variance early in training on low-dimensional control tasks.
  • Reusing the Discrete-space entropy formula's shape assumptions (entropy() returning a scalar per sample) without checking that Independent(Normal(...), 1)'s entropy correctly sums across action dimensions rather than returning a per-dimension vector.

21.7 Performance Concerns

  • The Gaussian policy head's parameter count is comparable to the Discrete head's (one extra log_sigma vector, dimension = action_dim); no measurable change to the §4 learner-update-time budget is expected.

21.8 Edge Cases

  • action_dim = 1 (a single continuous control dimension) — Independent(Normal(...), 1) must not degenerate incorrectly; verified by a dedicated 1-dimensional fixture.
  • A sampled action landing exactly on the low or high boundary — clamping must be a no-op in this case, not silently nudge the value.

21.9 Failure Analysis

  • Symptom: LunarLanderContinuous-v2 training plateaus early with entropy collapsing to a large negative number (Gaussian differential entropy can be negative, unlike Categorical entropy, so this signal must be read differently). Root cause: log_sigma initialized too small (a policy-head-init oversight distinct from ADR-11's Discrete-head gain, since the Gaussian head has an additional log_sigma parameter not covered by the original gain table). Debug method: log the mean sigma value (not just log_sigma) across early training; compare against the action space's (high - low) range. Signal: sigma orders of magnitude smaller than the action range from iteration 0. Recovery: initialize log_sigma to log(0.5 * (high - low))-scale, re-verify against the closed-form fixture.

21.10 Operational Notes

  • docs/hyperparameters.md (from Phase 8) gains a new section for continuous-control-specific settings (log_sigma init scale) distinct from the Discrete-action ablation entries.

Debug method: compare the very next post-resume reset()'s observation between resumed and control runs. Signal: first post-resume observation already differs. Recovery: extend RNG-state capture to include each vectorized env instance's np_random state, added as a sixth checkpoint field with a corresponding format_version bump (§27).

27. Compatibility & Versioning

Checkpoint format: versioned via CheckpointRecord.format_version (ADR-17); a major-version bump is required only for a genuinely breaking schema change (a field removed or reinterpreted), never for a purely additive optional field (FM-9's named pitfall).

Env API versioning: pinned to Gymnasium >= 0.29's 5-tuple step contract (ADR-03); a future Gymnasium major-version change that alters the step/reset signature requires a corresponding EnvSpec/ VecEnvProtocol review before adoption, gated through the conformance suite (§13, §23).

Config schema evolution: PPOConfig (§11) is additive-only within a minor version — new fields must carry defaults so old config YAML files continue to load; a field rename or removal requires a major version bump and a documented migration note in CHANGELOG.md.

Space-definition compatibility rule: a checkpoint trained against one (observation_space, action_space) pair may only be resumed or evaluated against an identical space definition (shape, dtype, bounds); a mismatch raises CheckpointCompatibilityError rather than attempting a best-effort reshape.

API stability: make_distribution, compute_gae, RolloutBuffer's public methods, and PPOConfig's existing fields are stable within a major version (P6's single-dispatch-point guarantee extends to this compatibility promise).

Migration: checkpoint format migrations ship as a tools/-housed one-off script per major-version bump, never as silent in-place mutation of load_checkpoint.

Deprecation: a deprecated config field remains loadable (with a logged warning) for one full minor-version cycle before removal.

SemVer: this project follows SemVer for the checkpoint format, the config schema, and the public Python API surface independently — each with its own version number (ADR-26); a release's CHANGELOG.md entry states which of the three changed.

Rolling-upgrade guarantees: an in-flight training run is never upgraded mid-run; a code/dependency upgrade takes effect only for a fresh train.py invocation, which may then resume from a prior-version checkpoint subject to the space-definition and format-version compatibility rules above.

31. Scalability Analysis

Constant regardless of scale: rollout buffer field count and dtype layout (§11); the GAE recursion's per-step work (O(1) per env per step, vectorized across N via NumPy); the checkpoint format's field schema (§27).

Grows with scale: rollout buffer bytes as O(T*N) (§34); learner FLOPs per update as O(minibatches * epochs * params) (§34); wall clock to a fixed step budget as O(1/num_envs) until the throughput ceiling (M12) is hit, then flat.

Named bottlenecks, in order: (1) env-step throughput (the sync-backend GIL ceiling at num_envs=128, M12) usually dominates before the learner does — this is the single most common misconception new PPO implementers carry, expecting the neural network to be the bottleneck when it rarely is at this scale; (2) Python-interpreter-per-step overhead inside SyncVectorEnv's sequential inner loop (§19.7); (3) the learner update (§4's 180 ms/45 ms budget), which only becomes the bottleneck once env throughput is no longer the constraint, e.g. on a very cheap synthetic env at very large num_envs.

Horizontal scaling: not supported within this blueprint's scope (§1's deployment model is single-process); the lever beyond the M12 ceiling is PhaseDeferred("§31 Scalability Analysis")'s own un-defer trigger — async/subprocess vectorization, which trades I9's cross-process bitwise-determinism guarantee for throughput (ADR-04's "when the rejected choice wins" column).

Vertical scaling: more CPU cores help only up to the GIL-bound ceiling (M12); more GPU memory helps the learner step (M6) but not env throughput (M1-M3), since env stepping in this blueprint's scope never runs on the GPU.

Coordination overhead: within sync vectorization there is none (single process, single thread, sequential inner loop); the deferred async backend introduces pipe-serialization coordination overhead proportional to num_envs * obs_bytes per step (§34).

Practical ceiling and the levers beyond it: the practical ceiling for this blueprint's scope is num_envs=128 at the M12 throughput plateau. Levers beyond it, each a deferred feature (§37): async/ subprocess vectorization (PhaseDeferred("§31 Scalability Analysis"), trades determinism for throughput); a recurrent policy trunk to reduce the effective rollout length needed for equivalent credit assignment on partially-observable tasks (PhaseDeferred("§31 Scalability Analysis")); a cross-language (Rust) env-runner to eliminate Python interpreter overhead per step (PhaseDeferred("§36 Alternative Architectures")); a batched-simulation backend (EnvPool/Isaac-Gym-style) that moves env stepping onto the GPU entirely, out of scope per §1's non-goals.

32. Mental Models & First Principles

MM1 — "PPO's clip is a trust region enforced by refusing to reward off-policy drift, not by measuring it." Predicts: KL can still drift unboundedly even while the clip term looks well-behaved. Bug class without it: policy collapse from an unbounded inner-epoch loop that trusts the clip alone. Resolves in §17.

MM2 — "The rollout buffer is a data contract, not a data structure." Predicts: any component that can be swapped (env-runner language, backend) needs only agree on buffer shape and dtype. Bug class without it: training logic coupled directly to env internals, breaking P1. Resolves in §11.

MM3 — "GAE is a recursion with a direction, not a formula." Predicts: any implementation computing deltas without walking backward first will silently mis-bootstrap. Bug class without it: a forward-computed "advantage" that is actually a disguised n-step return. Resolves in §16.

MM4 — "terminated and truncated answer two different questions: did the world end, or did we just stop watching." Predicts: bootstrapping through truncation is correct; through termination it is not. Bug class without it: FM-3's bootstrap leak. Resolves in §8 and §16.

MM5 — "Normalization statistics are part of the model, not preprocessing." Predicts: a checkpoint without them is a materially different function than the one that trained. Bug class without it: the eval-degradation failure named in P5 and FM-9. Resolves in §18 and §22.

MM6 — "Vectorization amortizes interpreter overhead; it does not parallelize computation." Predicts: throughput plateaus once GIL contention dominates, regardless of how many envs are added. Bug class without it: assuming linear scaling to num_envs=1024 on a single sync process. Resolves in §19 and §31.

MM7 — "Every implementation detail is a hypothesis until it's ablated on your own benchmark." Predicts: a cited paper's finding may not transfer to a different env/seed distribution. Bug class without it: cargo-culting a hyperparameter without re-verifying its direction locally. Resolves in §20.

MM8 — "Determinism is a property of the whole system, not of any one seed call." Predicts: one un-seeded RNG anywhere breaks the reproducibility guarantee for the entire run. Bug class without it: FM-10's dependency-induced nondeterminism. Resolves in §22.

34. Back-of-Envelope Capacity Model

1. Rollout buffer bytes, CartPole config. num_envs(8) * rollout_steps(128) * (obs_bytes(4*4=16) + action_bytes(4) + logprob_bytes(4) + value_bytes(4) + reward_bytes(4) + done_bytes(4)) = 8 * 128 * 36 = 36,864 B. Matches §4's stated figure exactly.

2. Rollout buffer bytes, LunarLander config. obs_dim=8 -> obs_bytes=32; per-transition bytes = 32+4+4+4+4+4=52; 8 * 128 * 52 = 53,248 B.

3. Learner FLOPs per update, MLP(64,64) separate actor+critic. Actor params: 4*64 + 64*64 + 64*2 = 256+4096+128 = 4,480. Critic params: 4*64 + 64*64 + 64*1 = 256+4096+64 = 4,416. Total params = 8,896. FLOPs per update = minibatches(4) * epochs(10) * params(8,896) * 6 = 2,135,040 (~2.1M FLOPs), using the standard 6 * params forward+backward heuristic.

4. Checkpoint bytes. Weights: 8,896 params * 4 B = 35,584 B. Adam optimizer state (2 extra buffers per param: m, v): 2 * 35,584 = 71,168 B. Weights + optimizer = 106,752 B (~104 KiB); normalizer stats and RNG-state blobs add a few KiB more. Total is comfortably under the 2 MiB budget (§4, M9).

5. Wall clock to CartPole-v1's 30,000-step benchmark, pure compute. Collection: 30,000 / 45,000 steps/s = 0.667 s. Iterations: 30,000 / (8*128) = 29.3 -> 29. Update time: 29 * 180 ms = 5.22 s. Pure compute total ~5.9 s; the documented <= 90 s target (§4, M7) includes eval cadence, checkpoint writes, and CI-variance margin on top of this figure.

6. Wall clock to LunarLander-v2's 1,000,000-step benchmark, pure compute. Collection: 1,000,000 / 40,000 steps/s = 25 s. Iterations: 1,000,000 / (8*128) = 976.6 -> 977. Update time: 977 * 180 ms = 175.9 s. Pure compute total ~201 s (~3.35 min); the documented <= 35 min target (§4, M8) leaves roughly 10x headroom for eval cadence, checkpoint I/O, and CI variance.

7. Env-throughput vs learner-throughput crossover setting the optimal num_envs. At num_envs=8: collection latency ~26 ms (p50, §4) versus learner update ~180 ms — learner-bound. At num_envs=64: throughput approaches the sync ceiling (~100,000+ steps/s), so collection for T=128, N=64=8,192 steps is ~82 ms, while update time grows with the larger minibatch (~350 ms estimated, roughly linear in sample count) — still learner-bound. The crossover toward env-bound sits near the num_envs=128 ceiling (M12), which is exactly why M12, not the learner, is named the dominant bottleneck in §31.

8. Subprocess IPC bandwidth, illustrative for the deferred async backend (§31/§36). At num_envs=64, LunarLander obs_bytes=32, and a per-env step rate of 100,000/64 ~= 1,562 steps/s: bandwidth = 64 * 32 * 1,562 ~= 3,198,976 B/s (~3.2 MB/s) — well within typical OS pipe bandwidth, showing IPC is not projected to be the bottleneck even in the deferred backend at this scale.

36. Alternative Architectures (Roads Not Taken)

Design 1 — Off-policy replay-based learning (SAC/DQN) instead of on-policy PPO.

+---------+  step   +--------+  (s,a,r,s') +----------------+
| Env     |<------->| Agent  |------------>| Replay Buffer  |
+---------+         +--------+             | (large, FIFO)  |
                          ^                +-------+--------+
                          |     sample minibatch (off-policy) |
                          +------------------------------------+

Winning regime: sample-efficiency-critical continuous control (MuJoCo/DeepMind Control Suite) or discrete control with cheap, replayable transitions (Atari at fixed compute budgets). Embodying system: Stable- Baselines3's SAC/DQN implementations (same repo, different algorithm family, §5 citation 4/13). Rejected because: this blueprint's non-goals (§1) explicitly target the on-policy family reusable across A2C/IMPALA/ PPG (§2); a replay buffer's data-freshness and target-network machinery is a fundamentally different set of invariants than I1/I3, not an incremental extension of them.

Design 2 — Distributed actor-learner with off-policy correction (IMPALA V-trace).

+--------+   +--------+   +--------+
| Actor 1|   | Actor 2|   | Actor N|   (many machines, slightly stale policy)
+---+----+   +---+----+   +---+----+
    |            |            |
    +------------+------------+
                 v
         +---------------+     V-trace off-policy
         | Central Learner|<--- correction for staleness
         +---------------+

Winning regime: massive-scale training where actor throughput must scale past a single process's ceiling (M12) across many machines. Embodying system: DeepMind's IMPALA / Acme framework (Espeholt et al. 2018, §5). Rejected because: this blueprint's deployment model (§1) is explicitly single-process; V-trace's importance-weighted correction is a different trust-region mechanism than PPO's clip (MM1), and adopting it would replace, not extend, the §17 learner core.

Design 3 — Evolution strategies / random search as a gradient-free alternative.

+------------------+    perturb theta    +------------------+
| Population of N   |-------------------->| Evaluate return  |
| perturbed policies|                     | per perturbation |
+------------------+<--------------------+------------------+
         weighted-average update toward higher-return perturbations

Winning regime: reward signals too sparse or non-differentiable for policy-gradient methods, or when massive embarrassingly-parallel compute is cheaper than careful gradient engineering. Embodying system: OpenAI's Evolution Strategies as a scalable alternative to RL (Salimans et al. 2017 lineage). Rejected because: this blueprint's mastery goal (§2) is specifically the policy-gradient/advantage-estimation skillset (GAE, clipped surrogate); ES requires no backward pass at all, which would eliminate rather than exercise the domain model of §8.

Design 4 — Model-based rollouts in a learned world model.

+--------+  real   +------------+  imagined rollouts  +-------------+
| Env    |-------->| World Model|-------------------->| Policy Update|
+--------+  data    +------------+   (cheap, no env)   +-------------+

Winning regime: environments where real interaction is expensive or dangerous (robotics, some sim-to-real pipelines), trading model-bias risk for sample efficiency. Embodying system: Dreamer-family world-model agents. Rejected because: this blueprint's Phase-0-through-11 arc (§12-§23) is scoped to model-free on-policy learning; a learned world model introduces an entirely separate component (with its own training loop, loss function, and failure modes) that would roughly double the invariant surface (§7) for a benefit this project's named benchmarks (CartPole/LunarLander) do not need.

38. Glossary

  • MDP — Markov Decision Process; the (S, A, P, R, gamma, rho0) tuple (§8).
  • Return — the discounted sum of future rewards, G_t.
  • Discount factor (gamma) — the per-step weight applied to future reward.
  • Advantage — Q(s,a) - V(s); how much better an action is than the state's average.
  • GAE — Generalized Advantage Estimation; the lambda-weighted advantage estimator (§16).
  • TD error (delta) — the one-step temporal-difference residual feeding the GAE recursion.
  • On-policy — learning only from data generated by the current (or very recently current) policy.
  • Off-policy — learning from data generated by a different (often older or replayed) policy.
  • Clip ratio (eps) — the PPO surrogate's bound on the probability ratio, default 0.2.
  • KL divergence — a distributional distance used here to bound policy drift per update (P7).
  • Entropy bonus — a reward for policy stochasticity, encouraging exploration (P9).
  • Value bootstrapping — estimating a return using a learned value function instead of a full rollout.
  • terminated — the episode ended because a true terminal state was reached (I4).
  • truncated — the episode was cut off by a time limit or external stop, not a true terminal (I4).
  • Rollout — one T-step, N-env batch of collected experience (§8).
  • Minibatch — a subset of a flattened rollout batch used for one gradient step.
  • Epoch (update) — one full pass over all minibatches of a rollout during a PPO update.
  • Vectorized env — an env wrapper exposing N parallel instances through one batched API (§13).
  • Autoreset — a vectorized env's automatic per-instance reset upon episode end (§8, §19).
  • Normalizer statistics — the running mean/variance used to normalize observations or rewards (P5).
  • Explained variance — the fraction of return variance the value function accounts for.
  • Clip fraction — the fraction of samples where the PPO clip was actually active.
  • Approx KL — the cheap, unbiased KL approximation used for the early-stop check (§5 citation, Schulman 2020 blog).
  • Orthogonal initialization — a weight-init scheme preserving vector norms; used with specific gains (ADR-11).
  • safetensors — a checkpoint serialization format that avoids arbitrary code execution on load (ADR-17).
  • Run manifest — the recorded config + derived values + seed + git SHA written at run start (P11).
  • Checkpoint — a persisted snapshot of weights, optimizer state, RNG state, normalizer stats, and config (I10).
  • RTO — Recovery Time Objective; the target time to resume training from a checkpoint (§4).
  • SBOM — Software Bill of Materials; a manifest of all dependencies in a release (§29).
  • SLSA — a supply-chain provenance/attestation framework referenced for release integrity (§29).
  • Conformance suite — the fixture-driven test harness validating the env/VecEnv API contract (§13).
  • Differential testing — comparing this codebase's behavior against a reference implementation on fixed seeds (§23, §28).
  • Fuzzing — feeding a parser or dispatch function large volumes of generated input to find unhandled crashes (§23, §28).
  • Chaos testing — deliberately injecting a fault (e.g. a hanging env) to verify recovery behavior (§28).
  • Soak test — a sustained-load test run over a long duration to surface slow leaks or drift (§28).
  • Seed — the integer from which all of a run's randomness is deterministically derived (P3).
  • RNG — Random Number Generator; this project uses per-component seeded Generator instances (I6).
  • Policy gradient — the family of methods that directly optimize a parameterized policy via the gradient of expected return.
  • Actor-critic — a policy-gradient method that uses a learned value function (critic) to reduce variance in the policy (actor) gradient.
  • REINFORCE — the foundational Monte-Carlo policy-gradient algorithm (Williams 1992, §5).
  • Baseline (variance reduction) — a state-dependent term subtracted from the return to reduce gradient variance without introducing bias.
  • Trust region — a bounded region of policy-parameter space within which an update is trusted to improve the policy (TRPO, §8).
  • Surrogate objective — a tractable proxy objective (here, the clipped surrogate) standing in for the true, expensive policy-improvement objective.
  • Value function (V) — the expected return from a state under the current policy.
  • Q-function (Q) — the expected return from a state-action pair under the current policy.
  • Categorical distribution — the discrete-action probability distribution produced by the policy head (§8 taxonomy).
  • Gaussian policy — the diagonal-Normal continuous-action distribution used in Phase 9 (§21).
  • Log-std — the log of the Gaussian policy's standard deviation parameter.
  • Bellman equation — the recursive relationship defining V/Q in terms of immediate reward plus discounted future value.
  • GIL — the CPython Global Interpreter Lock; the source of the sync-vectorization throughput ceiling (§19, §31).
  • IPC — Inter-Process Communication; relevant to the deferred async/subprocess vectorization backend.
  • Backpressure — a system's mechanism for slowing producers when consumers cannot keep up (ADR-05).
  • SemVer — Semantic Versioning; the MAJOR.MINOR.PATCH scheme governing this project's compatibility guarantees (§27).
  • Canary deployment — validating a change on a small scope before full promotion (§26).
  • Telemetry — the structured metrics/logging surface used for debugging and monitoring (§7, §26).
  • Span (tracing) — a named, timed unit of work within the training loop (ADR-20, §26).
  • Running mean/std — an incrementally updated estimate of a data stream's mean and variance (RunningMeanStd, §11).
  • Welford's algorithm — the numerically stable incremental variance-computation method used by RunningMeanStd (§18).
