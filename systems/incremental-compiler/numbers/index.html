32. Back-of-Envelope Capacity Model

All derived from the §4 System Constraints table (formulas shown).

  1. Source bytes at 50M LOC. 50M LOC × ~40 B/line (avg) = 2.0 GB source (matches §4 row 1). Formula: LOC × bytes_per_line.
  2. Memo entries. ~1 query per 5 LOC across ~8 pipeline stages → 50M/5 × (fraction materialized ≈ 0.3) ≈ 3M live derived entries at steady IDE working set (not all 50M cold). Formula: LOC/LOC_per_query × materialized_fraction.
  3. Working-set RAM (metadata + edges + trees). The three RAM consumers, each derived and summed: (a) memo metadata — 3M × 160 B/entry (§4 row 23: key 16 + fp 16 + revs 16 + dep header + value ptr) = 480 MB, formula entries × bytes_per_entry, under the 2.5 GB metadata ceiling (§4 row 3); (b) dependency edges — 3M × avg fan-in 6 = 18M edges × 8 B = 144 MB, formula entries × avg_fanin × bytes_per_edge (worst-case fan-in 100k, §4 row 16, is per-node, not average); (c) green trees — 2.0 GB source × ~3× node overhead with structural sharing ≈ 1.5 GB (largest single consumer), formula source_bytes × node_overhead_factor. Sum (a + b + c) ≈ 2.1 GB — within the 8 GB RSS ceiling (§4 row 2) with headroom for interner + scratch.
  4. Fingerprint bandwidth per full hash pass. 2.0 GB ÷ BLAKE3 ~3 GB/s = ~0.67 s to fingerprint the whole workspace once. Formula: source_bytes / hash_throughput. Confirms cold fingerprinting is not the M5 bottleneck.
  5. Warm edit recompute budget. M2 p50 25 ms ÷ M6 memo-lookup 5 µs = ~5,000 memo lookups affordable per warm edit before recompute dominates. Formula: recompute_budget / lookup_cost. Sets the fan-out ceiling before an edit misses M1.
  6. WAL write rate at steady edit. ~5,000 changed entries/edit (step 5) × 160 B = 800 KB/edit; at 10 edits/s = 8 MB/s WAL, group-committed. Formula: changed_entries × entry_bytes × edit_rate. Trivially within SSD + the M8 fsync budget.
  7. Disk footprint. 3M entries × avg 300 B value × 2.5 amplification (§4 row 15) = ~2.25 GB on disk. Formula: entries × avg_value_bytes × amplification.
  8. Crash recovery time. 1M WAL records ÷ ~50k records/s replay (crc + index insert) = ~20 s < the 30 s M9 target (§4 row 14). Formula: wal_records / replay_rate.
  9. FD budget. ~250k files (row 1) but only open segments + mmap'd index + active file handles ≈ hundreds concurrently → well under the 8,192 FD cap (§4 row 13). Formula: open_segments + index_maps + active_files.
  10. Parallel critical path. Cold M5 120 s × M13 speedup 12× ⇒ single-thread ≈ 1,440 s; critical path must be ≤ 120 s or speedup caps below 12×. Formula: single_thread_time / speedup ≥ critical_path.
  11. Interner size. 50M LOC at ~1 identifier per 8 tokens, ~4 tokens/line → 25M identifier occurrences, but with ~99% dedup (few unique names) → ~250k unique interned strings × ~24 B avg = 6 MB. Formula: occurrences × (1 − dedup_ratio) × avg_len. Negligible against the 8 GB ceiling (§4 row 2).
  12. Debounce & group-commit fsync rate. Two chained bounds on write churn: (a) at the 30 ms debounce window (§4 row 27) a keystroke burst collapses to ≤ 33 revisions/s regardless of typing speed, formula 1 / debounce_window, holding M1 under fast typing; (b) 33 rev/s × ~5,000 changed entries (step 5) = 165k naïve fsync/s (impossible), so group-commit at the ≤ 2 ms window (§4 row 28) collapses it to ≤ 500 fsync/s, formula edit_rate / commit_window — which is why M8 is reachable.
