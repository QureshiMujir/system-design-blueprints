242 — Incremental Compiler from Scratch

Project Number: 242

Project Name: Incremental Compiler from Scratch

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Build a query-based, demand-driven incremental compiler runtime from scratch: a memoized query engine that turns a source workspace into diagnostics, semantic facts, and lowered IR, recomputing only the queries whose transitive inputs changed. The core is not a language — it is the incremental substrate (revisions, red-green dependency tracking, fingerprint early-cutoff, durability firewalls, on-disk memo persistence, parallel query execution) plus a minimal statically-typed frontend (ecl, "example compiler language") that exercises every layer. The defining engineering fact: a keystroke that changes one function body must reconcile the whole workspace in p95 ≤ 80 ms warm (M1) while re-executing < 1% of derived queries, because early cutoff (I3) prunes recomputation at every fingerprint-stable edge.

Phase-0 deliverable — the numbered crate set (Rust workspace):

  1. query-engine — revisions, memo table, derived-query trait, execution loop, early cutoff.
  2. dependency-graph — dependency-edge recording, red-green color marking, cycle detection.
  3. syntax-green — immutable, structurally-shared green syntax trees + token interning.
  4. syntax-red — cursor overlay giving absolute offsets/parents over green trees.
  5. lexer — incremental, resumable UTF-8 tokenizer.
  6. parser — error-recovering incremental parser with subtree reuse.
  7. resolver — symbol interning, stable SymbolId, scope graph, span hygiene.
  8. hir — high-level IR lowering + semantic (type) queries.
  9. cache-store — content-addressed store (CAS), write-ahead log (WAL), on-disk memo serialization.
  10. scheduler — work-stealing parallel query executor with cancellation.
  11. replay — deterministic record/replay of a compile session.
  12. diagnostics — structured, span-anchored diagnostic model.
  13. telemetry — tracing spans, Prometheus metrics, OTLP export.
  14. compiler-driver — session lifecycle, batch + daemon entrypoints.
  15. lsp — JSON-RPC 2.0 Language Server adapter.
  16. interner — global deduplicating string/symbol interner.
  17. testing — fixture loader, differential + snapshot harness.
  18. fuzz-targets — libFuzzer entrypoints for lexer/parser/serializer.

System boundaries. Provides: incremental query evaluation, dependency tracking, persistence, diagnostics, LSP surface for the ecl frontend. Delegates: machine-code generation to LLVM/Cranelift (not built here — PhaseDeferred("§35")); on-disk block allocation to the host filesystem; TLS/auth for distributed cache to the transport layer. Does NOT provide: a runtime/VM, JIT, garbage-collected target language, optimizing backend, or distributed build farm in Phase 0.

Non-goals: LLVM replacement; register allocation / instruction selection; a production surface language (the ecl frontend is a test vehicle, not a product); speculative distributed scheduling; cross-machine cache sharing before §35 un-defer triggers fire.

Deployment model: (a) eclc batch CLI (one-shot compile), (b) ecld long-lived daemon holding a warm query database for a CI worker pool, (c) ecl-lsp per-editor language server over stdio. All three link the same compiler-driver and differ only in the front door.

Target users / operators: compiler engineers building the frontend; infra engineers running ecld on CI workers; IDE-tooling maintainers embedding ecl-lsp; SREs watching cache-hit and replay-divergence dashboards.

What later phases unlock: Phase 0 stands up the correctness kernel (memoize + revision bump + recompute); Phase 1 adds the incrementality that makes it fast; Phases 2–5 build the frontend that makes it a compiler; Phase 6 makes state survive restarts; Phase 7 makes it parallel; Phase 8 keeps memory bounded forever; Phase 9 makes it interactive and auditable.

Recommended language: Rust. Rationale: (a) affine ownership statically forbids the aliased-mutation bugs that corrupt a shared dependency graph — the single hardest class of incremental-compiler defect; (b) Arc/atomics give lock-free green-tree sharing with deterministic drop order; (c) no GC ⇒ memo memory is accounted precisely against the M12 8 GB ceiling; (d) rustc and salsa — the two reference incremental compilers — are Rust, so their techniques port directly; (e) cargo gives reproducible builds (ADR-20). Rejected: C++ (no borrow checker → graph aliasing UB, and reproducibility depends on hand discipline); OCaml (excellent for compilers but GC pauses fight the M1 tail-latency budget and FFI to blake3/zstd is friction); Go (GC + lack of sum types + no zero-cost generics make the memo table allocation-heavy); Zig (immature ecosystem for tracing/proptest, no stable ABI for the plugin surface).

Prerequisites (systems knowledge required): compiler construction (lexing→parsing→name resolution→lowering); incremental-computation theory (self-adjusting computation, function caching); graph algorithms (SCC, topological order, cycle detection); lock-free data structures and memory ordering; storage-engine design (WAL, CAS, compaction); deterministic-execution discipline; serialization/versioning.

Timeline: Phase 0 in 3 weeks; full ten-phase system in 9–12 months for a 3-engineer team (see Appendix B for the per-phase breakdown).

Deferred features (all registered in §35): distributed/remote query-cache sharing PhaseDeferred("§35"); cross-machine semantic-graph reuse PhaseDeferred("§35"); MIR-level profile-guided optimization PhaseDeferred("§35"); speculative/predictive query prefetch PhaseDeferred("§35"); native backend codegen PhaseDeferred("§35").

2. Why Build This

Unique systems knowledge. Incremental compilation is the sharpest real-world instance of incremental computation: a pure function (source → artifacts) that must be re-evaluated under small input deltas without recomputing the whole. Building it teaches the one idea most working engineers never internalize — that memoization plus a validated dependency graph plus early cutoff turns an O(program) batch computation into an O(change) incremental one, and that the hard part is not the cache but cache invalidation done exactly.

Architectural / historical significance. The query-based model is the through-line of the last decade of compiler engineering: rustc rebuilt its middle-end around a query system (2016→) with red-green marking; Microsoft's Roslyn made the C#/VB compiler an incremental, immutable-tree service; salsa extracted the pattern into a reusable framework; TypeScript and clangd ship incremental frontends that IDEs depend on. Underneath sits two decades of theory — Reps' incremental attribute evaluation (1982), Pugh & Teitelbaum's incremental evaluation via function caching (1989), Acar's self-adjusting computation (2006), Hammer et al.'s Adapton (2015), and Mokhov et al.'s unifying "Build Systems à la Carte" (2018). This project is where that theory meets a 50M-LOC production constraint.

Engineering muscles. Dependency-graph invalidation as a correctness problem; fingerprint design for early cutoff; durability/firewall layering to stop invalidation storms; deterministic parallelism (same result, any thread schedule); crash-safe persistence of a mutable graph; span/hygiene stability so identities survive edits; replay-based debugging of a nondeterminism bug.

Named cross-links to sibling systems. Databases (the memo table is a versioned MVCC store; revisions are transaction timestamps); build systems (Bazel/Buck2 Skyframe is the same demand-driven graph at file granularity); reactive UI runtimes (React/Salsa/Adapton share the "recompute the minimal dirty subgraph" core); LSM storage engines (the WAL + compaction design mirrors LevelDB); distributed schedulers (work-stealing query execution ≈ a task runtime).

Calibration value. After this build, "just cache it" stops being a phrase and becomes a design with a dependency graph, a fingerprint scheme, a durability policy, an eviction strategy, and a replay harness. You gain a permanent instinct for when incremental beats batch and the exact price you pay for it (graph memory, invalidation latency, determinism discipline).

What Mastery Looks Like

  • Explain and implement red-green dependency validation with early cutoff, and predict its recompute count on a given edit — cemented in Phase 1 (§13).
  • Design a fingerprint scheme that makes semantically-null edits (whitespace, comments) short-circuit at the earliest query — Phase 2 (§14) and Phase 1 (§13).
  • Build structurally-shared immutable syntax trees and reuse subtrees across reparses — Phase 2–3 (§14–§15).
  • Keep symbol identities and spans stable across unrelated edits so downstream memo entries survive — Phase 4 (§16).
  • Make a mutable dependency graph crash-safe with a WAL + content-addressed store and recover it in bounded time — Phase 6 (§18).
  • Achieve deterministic parallel query execution — identical outputs under any thread interleaving — Phase 7 (§19).
  • Garbage-collect a query cache without corrupting live dependency edges — Phase 8 (§20).
  • Diagnose a nondeterminism defect by deterministic replay of a recorded session — Phase 9 (§21).

compiler-driver / Session. Owns the single mutable Revision counter and the query database handle. Every external mutation (set_input) bumps the revision; every request demands a root query and returns when the engine has validated or recomputed it. It is the only writer of inputs — the trust boundary where untrusted source text enters.

query-engine. The memoized demand-driven core (per Salsa/rustc). Holds the MemoTable keyed by QueryKey, each entry carrying its output, its Fingerprint, the Revision it was verified_at and changed_at, its Durability, and its recorded dependency list. Executes a derived query only when validation proves a dependency's fingerprint changed (early cutoff, I3).

dependency-graph. Records the edges a query reads during execution and colors nodes green (validated-clean this revision) or red (must recompute) during backward validation. Detects cycles (SCC) and drives dirty propagation. Authoritative source of "what depends on what" (P12).

syntax + frontend queries. lexer→parser produce immutable, interned green trees; syntax-red overlays absolute offsets; resolver interns symbols to stable SymbolIds; hir lowers to semantic IR and answers type queries. Each stage is a derived query, so incrementality is free.

scheduler. Work-stealing thread pool that executes independent queries in parallel with cooperative cancellation; enforces the per-QueryId execution lock so a query runs at most once per revision (I8).

cache-store. Persistence boundary: WAL for durability, memory-mapped index for O(1) key lookup, content-addressed segment files (BLAKE3-named, zstd-compressed) for values. Guarantees no silent corruption (I6).

diagnostics + replay. Structured diagnostics anchored to stable spans; replay records inputs+revisions so a session can be re-executed bit-identically for debugging (I11).

telemetry. tracing spans per query, Prometheus pull metrics, OTLP export — observability is a first-class boundary, not an add-on (P9).

6. Design Principles

  • P1 — Purity of derived queries. A derived query is a deterministic function of the values it reads; it may read only through the database (never ambient globals, wallclock, or thread id). Tradeoff: forbids convenient side channels. Operational implication: replay (§21) is bit-exact. Violation: a query reading SystemTime makes cache keys non-reproducible → I11/replay mismatch and undebuggable heisenbugs.
  • P2 — Inputs are the only mutable state. Only the driver mutates inputs, and only between revisions. Tradeoff: no in-place graph edits. Implication: every recompute is triggered by a revision bump (I2). Violation: mid-revision mutation races validation → stale-read corruption.
  • P3 — Early cutoff at every edge. Compare a dependency's fingerprint, not its identity/timestamp; equal fingerprint ⇒ stop propagating. Tradeoff: fingerprint compute + storage cost. Implication: whitespace edits die at the lexer (M3). Violation: re-running downstream on unchanged values = O(program) not O(change).
  • P4 — Durability firewalls. Tag inputs with a Durability tier (LOW/MED/HIGH); a HIGH-durability input unchanged lets validation skip whole subgraphs by revision comparison. Tradeoff: mis-tagging a volatile input HIGH yields stale results. Implication: std-lib/config queries validate in O(1). Violation: every edit walks the entire std-lib subgraph → validation storm.
  • P5 — Structural sharing everywhere. Green nodes are immutable and interned; identical subtrees share one allocation. Tradeoff: interner contention. Implication: reparse allocates only changed nodes (M12). Violation: per-edit deep-copy of trees blows the memory ceiling.
  • P6 — Stable identities across edits. SymbolId/HirId/spans are content- and position-relative, not insertion-order; unrelated edits must not renumber them. Tradeoff: interning + hygiene bookkeeping. Implication: downstream memo entries survive edits (I9). Violation: every edit invalidates every symbol → zero reuse.
  • P7 — Crash safety by write-ahead logging. No metadata mutation reaches the index before its WAL record is fsynced. Tradeoff: fsync latency (M8). Implication: bounded recovery (M9, I6). Violation: torn write on crash → unrecoverable index.
  • P8 — Determinism over throughput. When a scheduling choice trades reproducibility for speed, reproducibility wins. Tradeoff: forbids order-dependent fast paths. Implication: parallel result == serial result (I8). Violation: nondeterministic output defeats replay and differential testing.
  • P9 — Observability is not optional. Every query execution emits a span; every invariant has a metric. Tradeoff: telemetry overhead (< 3%). Implication: production debugging from dashboards (§24). Violation: silent invalidation storms with no signal.
  • P10 — Bounded everything. Every queue, cache, and memory pool has an explicit ceiling and an eviction/backpressure policy. Tradeoff: rejects work under load. Implication: no OOM (M12). Violation: unbounded memo growth → daemon OOM-kill.
  • P11 — No hidden global state. All state lives in the Session/database; there are no static mut caches. Tradeoff: threading the database everywhere. Implication: multiple isolated sessions coexist. Violation: cross-session cache bleed → wrong diagnostics.
  • P12 — The dependency graph is authoritative. Invalidation is driven only by recorded edges, never by heuristics or timestamps. Tradeoff: must record every read. Implication: correctness is a graph property (I1). Violation: a missed edge = a stale result the user sees as a compiler bug.
  • P13 — Versioned, self-describing artifacts. Every serialized value carries a schema version; readers reject unknown-major versions. Tradeoff: version bookkeeping. Implication: safe rolling upgrades (§25). Violation: silently mis-decoding an old cache → corruption.
  • P14 — Cancellation is cooperative and safe. A cancelled query unwinds cleanly, leaving no half-written memo entry. Tradeoff: poll points. Implication: IDE edits cancel stale work instantly. Violation: torn memo entry poisons the cache.
  • P15 — Fail closed, quarantine, and recompute. On any detected corruption/divergence, drop the suspect entry and recompute from inputs rather than serve a possibly-wrong value. Tradeoff: a latency spike on the affected query. Implication: corruption never propagates (FM-4). Violation: serving corrupt cache silently ships wrong code.
  • P16 — Query granularity matches change granularity. A query's scope is chosen so that a typical edit dirties one query, not a coarse aggregate. Tradeoff: more query kinds, more edges to record. Implication: per-item, per-reference queries keep invalidation local (§4 row 16). Violation: file-level queries over-invalidate (the make failure, §34-A).
  • P17 — Separate the caller-visible contract from the private computation. Expose a stable "interface" query (signature, module symbol set) that changes only when the contract changes, and hide the volatile "implementation" query behind it. Tradeoff: two queries where one seemed to suffice. Implication: body edits don't touch callers (M1). Violation: every internal edit ripples to every consumer.

Debugging methodology. A deterministic single-thread simulator harness replays a scripted edit sequence with one assertion per invariant wired to the telemetry counter above; any counter leaving its allowed band (e.g. duplicate_exec_total > 0, early_cutoff_total below the M3 band) fails the run and dumps the minimal offending query subgraph. Combined with replay (§21) this turns "the compiler gave a wrong/stale answer once" into a reproducible, bisectable fixture.

8. Domain Model / Protocol / Data Model

8.1 The query universe

Two query kinds: inputs (set by the driver — file text, config, workspace layout) and derived queries (pure functions of other queries). Every query is identified by a QueryKey = (QueryId, KeyHash) where QueryId names the function and KeyHash is the stable hash of its argument.

The ecl surface grammar (EBNF; the parser in §15 implements it) — a deliberately small statically-typed language whose only job is to exercise every incremental layer (items, bodies, references, types):

program     = { item } ;
item        = fn_item | let_item | mod_item | use_item ;
fn_item     = "fn" ident "(" [ params ] ")" [ "->" type ] block ;
params      = param { "," param } ;
param       = ident ":" type ;
mod_item    = "mod" ident "{" { item } "}" ;
use_item    = "use" path ";" ;
let_item    = "let" ident [ ":" type ] "=" expr ";" ;
block       = "{" { stmt } [ expr ] "}" ;
stmt        = let_item | expr ";" ;
expr        = literal | path | call | binop | block | if_expr ;
call        = expr "(" [ args ] ")" ;
binop       = expr op expr ;                 (* Pratt precedence *)
if_expr     = "if" expr block [ "else" block ] ;
type        = "i32" | "i64" | "bool" | "unit" | path | fn_type ;
fn_type     = "fn" "(" [ type { "," type } ] ")" "->" type ;
path        = ident { "::" ident } ;
literal     = int_lit | bool_lit ;

The grammar is LL(k) with a Pratt expression sub-parser (bounded lookahead, §15.6) so reparse latency stays predictable. Signature (fn_item header + type) and body (block) are lexically separable, which §17 exploits to split type_of into a signature query and a body query.

Frontend derived-query pipeline (each is a memoized query):

file_text(FileId)            : input  -> Arc<str>
tokens(FileId)               : derived -> Arc<TokenStream>          reads file_text
green_tree(FileId)           : derived -> Arc<GreenNode>           reads tokens
symbols(ModuleId)            : derived -> Arc<SymbolTable>         reads green_tree(*)
resolve(RefId)               : derived -> SymbolId                 reads symbols(*)
hir(ItemId)                  : derived -> Arc<Hir>                 reads green_tree, resolve
type_of(ItemId)              : derived -> Ty                       reads hir, type_of(deps)
diagnostics(FileId)          : derived -> Arc<[Diagnostic]>        reads tokens, hir, type_of

8.2 Memo entry & fingerprint

Each memo entry records the revision it was last verified clean and the revision its value last changed. Early cutoff compares fingerprints; the changed_at of a dependency drives whether a dependent must re-run.

MemoEntry {
  key:          QueryKey,
  value:        Arc<dyn Any + Send + Sync>,   // typed by QueryId
  fingerprint:  Fingerprint,   // 128-bit BLAKE3 of the serialized value
  verified_at:  Revision,      // last revision proven clean
  changed_at:   Revision,      // last revision value actually changed
  durability:   Durability,    // LOW | MEDIUM | HIGH
  deps:         SmallVec<[QueryKey; 8]>,
}

8.3 Red-green validation (state transition table)

Validation of a derived query Q at revision R (goal: decide re-execute vs reuse):

Current state Condition checked Action Next color
unknown no memo entry execute Green (fresh)
memo present verified_at == R reuse (already validated this rev) Green
memo present all deps' changed_at ≤ entry.verified_at after validating each dep set verified_at=R, reuse Green
memo present some dep re-executed and its changed_at > entry.verified_at re-execute Q Red→(fingerprint compare)
re-executed new fingerprint == old fingerprint keep changed_at, bump verified_at (EARLY CUTOFF) Green
re-executed new fingerprint != old fingerprint changed_at=R, propagate to dependents Red
any dep validation detects back-edge to Q abort with cycle diagnostic (I4) —

Transport: newline-framed Content-Length headers over stdio (LSP), UDS for ecld. Requests carry id; $/cancelRequest maps to cooperative cancellation (P14). Example request/notification shapes (signatures, not code):

8.6 Worked example (incremental edit)

Workspace: a.ecl defines fn f()->i32; b.ecl calls f. Revision 7 baseline: all queries green. User edits a comment in a.ecl → set_input(a), revision 8. Validation: file_text(a).changed_at=8; tokens(a) re-executes but its fingerprint is unchanged (comments normalized out, I14) → early cutoff at tokens(a); green_tree(a), symbols, type_of(f), diagnostics(b) all reuse. Recompute count: 1 query (tokens), 0 downstream. Contrast: user changes f's return type to i64 → tokens(a) fingerprint changes → green_tree(a)→hir(f)→type_of(f)→type_of(caller in b)→diagnostics(b) re-execute; diagnostics(a), unrelated modules stay green.

8.7 Malformed-input & failure-path examples

Malformed input: b.ecl contains an unterminated string. Lexer emits an ERROR token with a span; parser inserts a recovery node; green_tree(b) still produces a well-formed tree (error nodes are first-class), so downstream queries run in degraded mode and diagnostics(b) reports the lex error. No query panics — malformed input is data, not an exception (I5 still holds: deps recorded).

Failure path: cache-store load of type_of(f) finds blake3(bytes) != IndexRecord.fingerprint (I7). The entry is dropped, checksum_fail_total incremented, and type_of(f) is recomputed from hir(f); the corrupt segment is scheduled for compaction-time reclaim. The user sees a one-query latency spike, never a wrong type.

12. Phase 0 — Repository Skeleton & Correctness Kernel

12.1 Objectives

Stand up the Cargo workspace (all 18 crates as stubs), CI, lint gates, and the correctness kernel: a memoized query engine with a global Revision, one input query (file_text), one derived query (char_count), and the execute/reuse loop — in-memory only, single-threaded. This proves the fundamental identity before any incrementality or persistence exists: recompute-on-change equals from-scratch, and unchanged inputs are reused.

12.2 Detailed Implementation Steps

  • Create workspace, rust-toolchain.toml, deny.toml (ADR-03), Makefile, CI ci.yml with clippy -D warnings + fmt --check (ADR-17).
  • Implement Runtime with AtomicU64 revision, sharded MemoTable, and a thread-local dependency stack (records reads — the mechanism behind I5), per Pugh & Teitelbaum function caching (paper 2, §5).
  • Implement DerivedQuery::execute dispatch and the reuse rule: if verified_at == current_revision reuse; else execute, store value + changed_at. (No fingerprints yet — every dep change re-executes; correctness first, incrementality in §13.) Grounded in P1 (purity) and P2 (inputs-only mutation).
  • Implement set_input on the driver that bumps Revision (I2) and marks the input's changed_at.
  • Wire telemetry skeleton: tracing subscriber, revision_current gauge (P9).
  • Install a panic hook that captures the offending QueryKey + revision into a structured log before unwinding, so a kernel bug is diagnosable (§12.9).
  • Split the compiler-driver into batch (eclc, one-shot: set inputs, demand roots, exit) and daemon (ecld, persistent Session) entrypoints sharing session.rs; only the driver holds &mut Runtime (P2).
  • Initialize the mimalloc global allocator (ADR-14) and a per-session bump arena for green-node scratch, measured against the M12 accounting from day one.
  • Add testing fixture loader and a determinism script check-determinism.sh (run twice, diff — I11 foundation).
  • Define the QueryId static registry (append-only, §25) and assert at startup that no two query kinds collide on an id.

12.3 Deliverable

cargo test green across the workspace; a kernel example that sets file_text, demands char_count, mutates the file, and re-demands — printing execution counts. eclc --version runs.

12.4 Acceptance Criteria

  • On an unchanged input, second demand of char_count executes 0 derived-query bodies (pure reuse), verified by duplicate_exec_total == 0 and an execution counter.
  • On a changed input, char_count re-executes exactly once and returns the from-scratch value (differential check against a batch recompute).
  • CI passes clippy -D warnings, fmt --check; determinism script shows 0 diff across two runs.
  • Fixture kernel_reuse.txt drives the reuse assertion.

12.6 Pitfalls

  • Hidden globals — a static mut cache breaks P11; symptom: cross-test bleed; fix: thread the Runtime; detect: run tests with --test-threads varied.
  • Recording deps too late — if the read barrier misses reads before first execute, deps is incomplete (I5); detect via audit recompute divergence.
  • Revision not bumped on set — silent staleness; guard with the I2 assertion.
  • Non-deterministic HashMap iteration leaking into output — use FxHashMap with sorted iteration where output-visible (ADR-20).
  • QueryId reuse — recycling a retired id aliases two caches (I16); the registry is append-only, ids are never reused (§25).
  • Value equality vs fingerprint equality — comparing values directly instead of fingerprints is slow and error-prone; the fingerprint is the canonical equality (P3).

12.7 Performance Concerns

  • Memo lookup is on the hot path from day one — target M6 p99 ≤ 5 µs even in this stub.
  • Shard the memo table so lookups don't serialize on a single lock (ADR-08).
  • Avoid a heap Vec per dep-record — inline with SmallVec (the common case is < 8 deps).
  • Keep tracing compile-time filterable so telemetry overhead stays < 3% (P9).

12.8 Edge Cases

  • Empty input file (valid — yields an empty tree, not an error).
  • Input set to byte-identical content (must reuse, not register a spurious change — compare bytes before bumping changed_at).
  • Re-entrant demand of the same query on one thread (self-cycle → I4 even in the kernel).
  • Revision counter overflow (u64 — document as unreachable at any realistic edit rate; assert).
  • Concurrent set_input and demand in the daemon (only the driver mutates, between revisions — P2).

12.9 Failure Analysis

If reuse is wrong (executes when it shouldn't or vice-versa), the whole incrementality premise is void. Detection: the audit harness recomputes a random query from scratch and compares (I1); blast radius = correctness of every result; containment = fail the build; postmortem: dump the dep stack and revision timeline for the offending key. Because this is the kernel, the failure is caught in CI, never in production: the differential harness (§26) runs every commit, and a mismatch blocks merge. The one production-relevant variant is a QueryId collision (I16) that aliases two caches — the startup registry assert makes that a refuse-to-start, not a silent wrong answer.

12.10 Operational Notes

Metrics: revision_current, memo_entries, duplicate_exec_total. Logging: one span per demand with query id + revision. No deployment yet (library + eclc --version); rollback = revert crate. Compatibility: manifest schema_version = 0.

13. Phase 1 — Red-Green Dependency Tracking & Early Cutoff

13.1 Objectives

Turn the correctness kernel into a fast incremental engine: record dependency edges, add fingerprints and early cutoff (I3, P3), add Durability firewalls (P4), and implement red-green backward validation exactly as rustc/Salsa do. After this phase, a semantically-null change to a dependency stops propagating at the first fingerprint-stable edge.

13.2 Detailed Implementation Steps

  • Implement DependencyEdge recording via the read barrier: executing Q pushes a frame; each db.query(dep) read appends dep to Q's frame; on return, the frame becomes Q's deps (I5, P12), per Adapton demand-driven memoization (Hammer 2015, paper 4).
  • Implement the red-green validation walk (§8.3 table): to serve Q at revision R, validate each dep; if all deps' changed_at ≤ Q.verified_at, reuse; else re-execute and compare fingerprints — equal ⇒ early cutoff (bump verified_at, keep changed_at), per the rustc dev-guide red-green algorithm (paper 7). Anchored in P3, I3.
  • Implement Durability tiers with a per-tier last_changed: Revision; a dep of HIGH durability whose tier hasn't changed since Q.verified_at skips its subtree walk (Salsa durability, paper 8; P4).
  • Add Fingerprint = BLAKE3-128 of the serialized value (ADR-12); values implement a stable fingerprint().
  • Add cycle detection: a back-edge during validation raises CycleError (I4), per SCC on the demand stack.
  • Implement the two-color validation as a backward walk from the demanded query: maybe_changed_since(key, rev) recursively validates deps, short-circuiting on the first dep proven changed, and memoizes the color per revision so a diamond-shaped graph validates each node once (I8).
  • Distinguish Value edges (read a dep's value) from Existence edges (only checked "is this input present?") so adding an unrelated file doesn't invalidate queries that merely enumerated a directory (EdgeKind, §11).
  • Telemetry: early_cutoff_total, cycle_detected_total, unrecorded_read_total, validation_visits.

13.3 Deliverable

Incremental engine where editing a dependency that produces the same fingerprint re-executes only that one query and stops. A depgraph-viz dump shows green/red coloring per revision.

13.4 Acceptance Criteria

  • On a fingerprint-stable dep change, dependents re-executed = 0 (early cutoff), measured by early_cutoff_total and exec counters on earlycutoff.fixture.
  • On a fingerprint-changing dep, exactly the transitive dependents re-execute — count matches the hand-computed set for propagation.fixture (differential vs batch).
  • HIGH-durability unchanged input ⇒ its subtree validated in O(1) (no per-node walk) on durability.fixture; validation node-visits ≤ 5 regardless of subtree size.
  • Cycle in cycle.fixture produces a CycleError diagnostic, not a stack overflow.

13.5 Conformance Fixtures

Fixture Purpose Expected output
earlycutoff.fixture fingerprint-stable edit 0 downstream re-exec
propagation.fixture real change re-exec set == hand-computed
durability.fixture HIGH-durability skip ≤5 validation visits
cycle.fixture recursive query CycleError with participants
missed_edge.regression regression for a once-missed read audit finds 0 divergence

13.6 Pitfalls

  • Missed dependency edge — the canonical incremental bug; a read not routed through the DB isn't recorded → stale result (I5, P12). Detect: audit recompute; debug: diff recorded deps vs a from-scratch trace.
  • Fingerprint instability — a value whose serialization includes iteration order flaps its fingerprint, killing cutoff (I14); symptom: early_cutoff_total far below M3 band.
  • Durability mis-tag — marking a volatile input HIGH serves stale results; guard: only the driver assigns durability, from a static policy.
  • changed_at vs verified_at confusion — swapping them either over-reuses (stale) or never cuts off; unit-test the §8.3 transition table directly.
  • Validating a dep more than once per revision — a diamond graph without per-revision color memoization does exponential work; memoize the color (I8 at validation level).
  • Durability tier not propagated to derived queries — a derived query's effective durability is the min of its deps'; compute it, don't default to LOW.

13.7 Performance Concerns

  • Validation must be cheaper than execution or incrementality loses its point.
  • Durability firewalls (P4) bound validation to changed subgraphs — the dominant lever.
  • Keep the dep list SmallVec-inline to avoid heap traffic on every validation walk.
  • Fingerprint compute is on the recompute path only — batch BLAKE3 over contiguous value bytes.
  • Target: warm single-query recompute p50 ≤ 25 ms (M2); memo validation, not execution, must dominate that budget.

13.8 Edge Cases

  • A query with 100k deps (§4 row 16 fan-in ceiling) — validation stays linear, iterative (no per-dep stack recursion).
  • A dep that oscillates fingerprint every revision (thrash) — bound the work, alert on the pattern.
  • First-ever run (cold, no memo entry) — execute and record; no validation path.
  • A dep removed between revisions — the edge must be dropped, not retained stale (re-recorded on each execute).
  • A diamond dependency (two paths to one dep) — validated once per revision, not twice (I8 at the validation level).

13.9 Failure Analysis

A missed edge ships a wrong answer — worst failure class (FM-1). Detection: continuous audit sampling (recompute k random queries/rev, compare — I1); blast radius = every dependent of the mis-tracked query; containment = quarantine + full recompute of the namespace; forensic artifact = the recorded vs actual dep-set diff; long-term mitigation = fuzz the read barrier (§26). A subtler failure is an extra edge (over-recording) — not a correctness bug but a performance one: it shows up as an early-cutoff-rate drop (FM-6), not an audit mismatch, so both counters must be watched. The read barrier is the single most-fuzzed component (§26) precisely because a missed edge is invisible until the audit catches it.

13.10 Operational Notes

Metrics: early_cutoff_total, cycle_detected_total, unrecorded_read_total, validation_visits. Runbook invalidation-storm.md triggers when early_cutoff_total drops (FM-6). Rollback: feature-flag early cutoff off (falls back to Phase-0 recompute-all — slow but correct). Compatibility: dep-list format is in-memory only this phase.

14. Phase 2 — Incremental Lexer & Green Syntax Trees

14.1 Objectives

Build the immutable, structurally-shared green tree (syntax-green) and an incremental UTF-8 lexer whose token stream fingerprint is stable under whitespace/comment edits (I14) so early cutoff fires at the earliest possible query (green_tree / tokens). Introduce token interning (P5).

14.2 Detailed Implementation Steps

  • Implement the lexer as a resumable scanner producing Token{kind,len,text:Interned}; trivia (whitespace/comments) attach as leading/trailing trivia to adjacent tokens, and the significant-token fingerprint excludes trivia text (I14, P3) — the mechanism that makes comment edits cut off.
  • Implement incremental relex: given an edit range, rescan only the affected token window and splice, per Cooper & Torczon Ch. 2 (book 1) and Roslyn's incremental lexer (ref-impl 3).
  • Implement GreenNode with Arc<[GreenChild]> children and a precomputed fp:Fingerprint (BLAKE3-128 over kind + children fps), enabling O(1) subtree fingerprint (ADR-12); intern identical green subtrees so structurally-equal trees share memory (P5).
  • Expose tokens(FileId) and green_tree(FileId) as derived queries (§8.1) so incrementality is inherited from §13.
  • Attach trivia (whitespace/comments) as leading trivia to the following significant token and trailing to the preceding one on the same line, matching the Roslyn trivia model (ref-impl 3), so trivia has a stable home across edits.
  • Store green-node child lengths (not absolute offsets) so a subtree's bytes are position-independent and reusable anywhere (§15 reuse depends on this).
  • Build the incremental relex boundary detector: an edit's affected window extends left/right to the nearest token whose lexer start-state is unaffected (handles the "delete a */" cross-token case, §14.6).
  • Diagnostics: lexer emits ERROR tokens with spans (§8.7) into diagnostics.

14.3 Deliverable

tokens and green_tree queries; editing a comment re-executes tokens but yields an identical fingerprint → 0 downstream. cargo fuzz run fuzz_lexer runs.

14.4 Acceptance Criteria

  • Whitespace/comment-only edit: ≥ 85% of dependent queries short-circuit (M3), measured on whitespace_edit.fixture.
  • Incremental relex touches ≤ (edited tokens + 2) tokens on single_token_edit.fixture (not a full rescan).
  • Lexer fuzz target: 0 panics / 0 hangs over a 1M-input CI corpus (fuzz_lexer).
  • Green-tree memory for a 10k-LOC file ≤ 12 MB (structural sharing check) on medium_file.ecl.

14.5 Conformance Fixtures

Fixture Purpose Expected output
whitespace_edit.fixture trivia edit fingerprint unchanged, ≥85% cutoff
single_token_edit.fixture localized relex ≤ edited+2 tokens rescanned
unicode_identifiers.ecl UTF-8 correctness tokens match golden snapshot
invalid_utf8.bin malformed bytes ERROR token + diagnostic, no panic

14.6 Pitfalls

  • Trivia in the fingerprint — the classic reason "just formatting" edits recompile the world (I14); detect via whitespace_edit.fixture cutoff rate.
  • Token offset drift — after an edit, absolute offsets recomputed wrong → spans point at wrong text; keep green nodes offset-free (relative lengths only), compute absolute positions in the red layer (§15).
  • Interner unbounded growth — never-evicted strings leak; bound + GC in §20 (I12).
  • Relex window too small — an edit inside a string/comment can change tokenization far away (e.g. deleting a */); expand the window to a lexer-state-stable boundary. (rust-analyzer, ref-impl 5.)

14.7 Performance Concerns

  • Green-node allocation churn dominates parse cost (M12) — intern subtrees and reuse Arcs.
  • Cache locality: lay a node's children contiguously so traversal is a linear scan.
  • The lexer is memory-bandwidth-bound — replace per-char branching with a table-driven classifier.
  • Target parse throughput ≥ 20 MB/s single-thread; relex touches only the edit window, feeding the early-cutoff win (M3).

14.8 Edge Cases

  • BOM handling (strip and record, don't let it shift offsets).
  • CRLF vs LF line endings (normalize consistently so offsets are stable).
  • A 128 MB single file (§4 row 26 — stream, don't slurp beyond the mmap).
  • An edit that deletes the whole file (empty tree, still valid — not an error).
  • Mixed/invalid encoding (reject with a diagnostic at the file boundary, invalid_utf8.bin).
  • An edit inside a comment/string that changes tokenization far away (relex window must expand to a stable lexer state).

14.9 Failure Analysis

A relex bug yields a subtly wrong tree → wrong diagnostics/types downstream. Detection: differential vs a full re-lex on every Nth edit in CI (I1 at the syntax layer); blast radius = one file's downstream; containment = fall back to full relex on mismatch; forensic = the edit + before/after token dumps. The highest-risk bug is a relex window that is too small — it produces a locally-plausible but globally-wrong token stream (e.g. a mis-scoped string), which the fingerprint hides because the wrong tree is internally consistent; the full-relex differential (I1) is the only reliable catch, so it runs unconditionally in CI even though it is skipped on the hot path.

14.10 Operational Notes

Metrics: relex_tokens, green_nodes_interned, fingerprint_flap_total (I14), parse latency histogram. Logging: span per green_tree build. Rollback: disable incremental relex (full relex fallback). Compatibility: green tree is in-memory; not yet serialized.

15. Phase 3 — Incremental Parser & Red Tree

15.1 Objectives

Build an error-recovering, incremental parser producing green trees with subtree reuse across edits, and the syntax-red overlay giving absolute offsets and parent links without mutating green nodes. Spans must be stable so diagnostics and later SymbolIds survive edits (P6).

15.2 Detailed Implementation Steps

  • Implement a hand-written recursive-descent + Pratt-expression parser over tokens (grammar in §8 EBNF style), per Dragon book Ch. 4 (book 2) and Cooper & Torczon Ch. 3 (book 1).
  • Implement error recovery: on unexpected token, insert an ERROR/MISSING node and resync to a follow-set token, so green_tree is always well-formed (§8.7); recovery must be deterministic (P8).
  • Implement subtree reuse: when reparsing after an edit, reuse an unedited green subtree if the edit range doesn't intersect it and its bounding trivia is stable (Roslyn/rust-analyzer technique, ref-impls 3, 5); this is what keeps reparse O(change) (P3, M2).
  • Implement RedNode overlay: absolute offset = parent offset + sum of preceding child lengths, computed lazily on cursor descent (Roslyn red/green, ref-impl 3).
  • Implement a bounded-lookahead marker/event API (open-node/close-node events collected into the green tree) so the parser body is allocation-light and the tree is built once at the end, per rust-analyzer's parser (ref-impl 5).
  • Cache each green subtree's byte length so the "does the edit range intersect this subtree?" test is O(1) — the check that makes reuse cheap (§15.7).
  • Guarantee resync progress: every error branch consumes ≥1 token or inserts exactly one MISSING node, so recovery provably terminates (recovery_loop.regression).
  • Feed parse errors to diagnostics with stable Spans.

15.3 Deliverable

green_tree/parse(FileId) derived query with subtree reuse; a red-tree cursor API used by resolver/hir. Editing one function body reuses all sibling functions' subtrees.

15.4 Acceptance Criteria

  • Editing one item reuses ≥ 95% of sibling green subtrees (by node count) on sibling_reuse.fixture.
  • Parser recovers from malformed_block.ecl producing a tree with exactly the expected ERROR node count (golden), no panic.
  • Reparse latency for a one-line edit in a 10k-LOC file p95 ≤ 15 ms (M2 sub-budget) on large_file_edit.fixture.
  • Parser fuzz (fuzz_parser): 0 panics / 0 infinite recovery loops over 1M inputs.

15.5 Conformance Fixtures

Fixture Purpose Expected output
sibling_reuse.fixture subtree reuse ≥95% siblings reused
malformed_block.ecl recovery golden ERROR-node count, valid tree
nested_generics.ecl grammar depth golden AST snapshot
large_file_edit.fixture reparse latency p95 ≤ 15 ms
recovery_loop.regression resync termination no infinite loop

15.6 Pitfalls

  • Recovery loops — resync that fails to consume a token loops forever; guarantee progress (always advance ≥1 token on error).
  • Reused subtree with drifted trivia — reusing a node whose leading trivia changed breaks offsets; include trivia in the reuse-eligibility check (§14.6).
  • Span instability — computing spans from parse order instead of byte offset renumbers on edits (breaks P6/I9); derive spans from red-tree absolute offsets only.
  • Ambiguous grammar backtracking — unbounded lookahead blows latency; keep the grammar LL(k)/Pratt with bounded lookahead.
  • Rebuilding the tree spine on a leaf edit — naïvely rebuilding all ancestors defeats reuse; reuse unaffected sibling subtrees at each level (Wagner & Graham, paper 11).

15.7 Performance Concerns

  • Reuse decisions are on the hot reparse path — make "edit intersects subtree?" O(1) via cached subtree byte-ranges.
  • Keep RedNode a lightweight borrow (no heap) so cursor traversal doesn't allocate.
  • Avoid rebuilding the whole tree spine on a leaf edit — reuse ancestors' unaffected siblings.
  • Bounded lookahead keeps reparse latency predictable (M2); no unbounded backtracking (§15.6).

15.8 Edge Cases

  • An edit spanning two items (both reparse; siblings still reused).
  • An edit inside a token (partial identifier) — relex first, then reparse the affected node.
  • Unbalanced delimiters at EOF — recover to a well-formed tree with MISSING nodes.
  • A file that is all comments (empty item list, valid).
  • Extremely wide trees (10k sibling items) — reuse and offset computation stay linear.
  • Pasting a whole new file's worth of text in one edit (single large reparse, not per-char).

15.9 Failure Analysis

Wrong reuse ⇒ a tree that doesn't match the source ⇒ wrong everything downstream. Detection: differential parse (incremental vs full) sampled in CI (I1); blast radius = one file; containment = full reparse fallback on mismatch + quarantine; forensic = edit script + tree diff. Recovery for a reproduced case: minimize the edit script with the fuzzer's delta-debugger into a recovery_loop.regression-style fixture, then bisect the reuse-eligibility predicate. A non-terminating recovery (infinite resync loop) is contained by the progress guarantee (§15.2) — every error branch advances ≥1 token — so the worst case is a slow parse, never a hang.

15.10 Operational Notes

Metrics: subtree_reuse_ratio, recovery_nodes_total, reparse latency histogram. Logging: span per parse with reuse ratio field. Rollback: disable subtree reuse (full reparse). Compatibility: red tree is a view; no serialization change.

16. Phase 4 — Name Resolution, Interning & Span Hygiene

16.1 Objectives

Resolve names to stable SymbolIds that survive unrelated edits (P6, I9), build the scope graph, and guarantee span hygiene so that inserting code above an item does not renumber its symbol or shift its logical identity. This is the phase that makes semantic memo entries reusable.

16.2 Detailed Implementation Steps

  • Implement the global interner (string → Interned(u32)), sharded and lock-free on read (P5, ADR-14 allocator), per Appel Ch. 5 symbol tables (book 3).
  • Compute SymbolId from content + scope path, not declaration order, so adding an unrelated item doesn't renumber siblings (I9, P6); this mirrors rust-analyzer's stable ids (ref-impl 5).
  • Build symbols(ModuleId) and resolve(RefId) derived queries over the green tree; a reference resolves through the Scope chain (§8.1). Purity (P1) means resolution reads only via the DB.
  • Implement span hygiene: spans are relative to their item's start where possible so intra-file offset shifts don't invalidate unrelated items' fingerprints (I14).
  • Split resolution into symbols(ModuleId) (defines the binding set of a module — changes only when a declaration changes) and resolve(RefId) (one reference's target); this firewall means editing one function's body invalidates no other module's symbols (P4, §16.7).
  • Represent the scope graph as immutable per-module Scope chains keyed by Interned names; a lookup walks parent scopes, and the walk is itself recorded as dependency edges so adding a shadowing binding invalidates exactly the affected lookups (I5).
  • Handle glob/use imports by recording an Existence edge on the imported module's symbols so a new export invalidates importers but an unrelated edit does not.
  • Emit name-resolution diagnostics (unresolved, duplicate, shadowing).

16.3 Deliverable

resolve and symbols queries; adding a comment or unrelated function leaves every other symbol's SymbolId byte-identical (snapshot). Cross-file references resolve.

16.4 Acceptance Criteria

  • Insert an unrelated item at top of file → 0 changed SymbolIds among pre-existing symbols (stable-ID snapshot diff = empty) on stable_ids.fixture.
  • A change to a name's definition invalidates exactly its references' resolve entries, not the whole module (differential) on localized_resolve.fixture.
  • Duplicate/shadow/unresolved cases produce golden diagnostics on resolution_errors.ecl.
  • unstable_id_total == 0 across the edit-sequence test.

16.5 Conformance Fixtures

Fixture Purpose Expected output

16.6 Pitfalls

  • Order-dependent SymbolId — deriving ids from a counter renumbers everything on any insert (breaks I9); derive from content+scope.
  • Interner never GC'd — leaks memory over a long daemon session (I12); tie interner GC to §20.
  • Hygiene leak — a span computed absolutely flaps on unrelated edits, killing downstream cutoff (I14); keep spans item-relative.
  • Import cycle mishandled — recursion in resolve must surface as CycleError, not hang (I4).

16.7 Performance Concerns

  • Symbol lookup is a hot path — scope maps use FxHashMap; the interner read path is lock-free (P5).
  • Resolution fan-in can be large (a widely-used symbol) — keep resolve per-reference.
  • Per-reference granularity means a definition change invalidates references individually, not the whole module (P16).
  • This bounds the §4 row 16 fan-in blast: a rename re-resolves N references but re-runs no unrelated query.

16.8 Edge Cases

  • Two symbols with identical names in different scopes (resolved by scope walk, not global lookup).
  • Forward references (a symbol referenced before its textual definition — resolution is order-independent).
  • A symbol referenced but never defined (unresolved diagnostic, Ty::Error downstream).
  • Deeply nested scopes (walk stays bounded; scope chain is immutable per module).
  • A rename touching thousands of references (blast radius test — per-reference resolve bounds re-work, §4 row 16).
  • A shadowing binding introduced mid-scope (invalidates exactly the shadowed lookups, I5).

16.9 Failure Analysis

Unstable ids ⇒ every edit invalidates all semantic memo entries ⇒ incrementality collapses to batch (FM-6). Detection: unstable_id_total metric + stable-ID snapshot in CI; blast radius = all downstream semantics; containment = alert + bisect the id-derivation change; forensic = id snapshot diff. This failure is silent on correctness (results are right, just slow) which makes it insidious — a SymbolId-derivation change that ships passes every correctness test and only shows up as a latency regression in production dashboards. The stable_ids.fixture snapshot gate (§16.4) exists to catch it at merge time; treat any diff there as a release blocker even when all functional tests pass.

16.10 Operational Notes

Metrics: unstable_id_total, interner_entries, resolve_fanin histogram. Logging: span per symbols/resolve. Rollback: none (correctness-critical); guard with the stable-ID gate in CI. Compatibility: SymbolId derivation is versioned (a change bumps schema_version, invalidating persisted semantic caches — §25).

17. Phase 5 — HIR Lowering & Semantic (Type) Queries

17.1 Objectives

Lower the resolved tree to hir and implement demand-driven type queries (type_of, diagnostics) as derived queries with correct dependency edges and durability firewalls, so a type change propagates exactly to affected items and no further. Introduce the poison (Ty::Error) propagation model.

17.2 Detailed Implementation Steps

  • Implement hir(ItemId) lowering from green tree + resolve (§8.1), producing Hir with stable HirId/ItemId (P6), per Appel Ch. 15 (book 3) and Muchnick IR framing (book 4).
  • Implement type_of(ItemId) as a derived query reading hir and type_of of referenced items; cyclic type dependencies raise CycleError (I4) unless broken by an explicit annotation.
  • Model dataflow-style demand: type_of pulls only the signatures it needs (demand-driven), per Muchnick Ch. 9 dataflow (book 4) and the query model (§13).
  • Implement poison propagation: an item that fails to type produces Ty::Error, which propagates but does not cascade duplicate diagnostics (P15 fail-closed at the value level).
  • Split typing into signature_of(ItemId) (parameter + return types — the caller-visible contract) and type_check_body(ItemId) (internal, no caller impact); callers depend only on signature_of, so a body edit whose signature fingerprint is stable stops at the body query (the core IDE win, §17.7, M1).
  • Implement bidirectional local type inference for expressions (check/synthesize) with Ty::Error as the unification bottom so one error doesn't abort the whole body.
  • Record inter-item type edges precisely: signature_of(caller) reads signature_of(callee), never the callee body — bounding the invalidation blast radius (P12, §4 row 16).
  • Set durability: std-lib/prelude items are HIGH durability (P4) so user edits don't re-validate them.

17.3 Deliverable

type_of and file diagnostics queries; editing one function's body re-types only it and its callers; std-lib stays green across user edits.

17.4 Acceptance Criteria

  • Edit a function body (not its signature) → callers' type_of not re-executed (signature fingerprint stable) on body_only_edit.fixture.
  • Edit a signature → exactly direct + transitive callers re-type; count matches hand-computed set on signature_change.fixture (differential vs batch).
  • Type errors produce golden diagnostics; a poisoned item yields exactly one root diagnostic, not N cascaded, on poison.ecl.
  • HIGH-durability std-lib subtree validated in O(1) after a user edit (≤ 5 visits) — reuses §13 durability.fixture pattern via stdlib_durability.fixture.

17.5 Conformance Fixtures

Fixture Purpose Expected output
body_only_edit.fixture signature-stable edit 0 caller re-type
signature_change.fixture sig change callers re-type == hand set
poison.ecl error propagation 1 root diagnostic

17.6 Pitfalls

  • Over-broad signature fingerprint — including body in the signature fingerprint re-types callers on any body edit (defeats P3); fingerprint the signature separately from the body.
  • Type cycle hang — mutual recursion without a cycle guard overflows the stack (I4); detect on the demand stack.
  • Poison cascade — propagating Ty::Error as new distinct errors spams diagnostics; suppress downstream diagnostics on already-poisoned inputs (P15).
  • Durability mis-tag of user code — tagging user items HIGH serves stale types; only prelude/std is HIGH (P4).
  • Reading a callee's body from a caller's signature query — collapses the M1 win by rippling body edits to callers (P17); signature_of(caller) must read only signature_of(callee).
  • Inference that mutates shared state — breaks purity (P1) and replay (I11); inference reads only through the DB and returns a value.

17.7 Performance Concerns

  • type_of is the deepest query chain — the signature/body split (P17) is the single biggest IDE win.
  • Body edits must not touch the signature memo, so callers stay green (M1).
  • Keep Hir bodies cache-local; never re-lower during validation, only on recompute.
  • Target warm re-type p95 ≤ 80 ms (M1); the tail is a deep caller chain, watched via span timing.

17.8 Edge Cases

  • Mutually recursive functions (require explicit return-type annotation to break the type cycle, else CycleError).
  • Generic instantiation blow-up (bound instantiation depth; deep monomorphization is out of scope for ecl).
  • A type referenced across many modules (fan-in §4 row 16 — signature_of split bounds the blast).
  • An edit that changes only a body local (no signature effect → 0 caller re-type, the M1 win).
  • A poisoned dependency (Ty::Error) feeding a valid item (propagates as Error, suppresses duplicate diagnostics, P15).
  • A type that depends on itself through a struct field (detected as CycleError, I4).

17.9 Failure Analysis

A wrong dependency edge in type_of ⇒ a stale type served to the user (looks like a compiler bug — FM-1). Detection: audit recompute of type_of (I1); blast radius = callers; containment = quarantine + recompute namespace; forensic = recorded vs actual dep set for the query. The classic instance is signature_of(caller) accidentally reading the callee's body instead of its signature_of (§17.2) — correct, but it makes body edits ripple to callers, collapsing the M1 win into a storm (FM-6). The differential harness catches wrongness; the early-cutoff-rate dashboard catches the over-edge; both gate the semantic core because it has no rollback path.

17.10 Operational Notes

Metrics: type_of_reexec_total, poison_items, re-type latency histogram, early_cutoff_total at the signature edge. Logging: span per type_of. Rollback: none (semantic core); guarded by differential CI. Compatibility: HIR + Ty layout versioned (I10); a change invalidates persisted semantic cache (§25).

18. Phase 6 — On-Disk Cache: WAL, CAS & Serialization

18.1 Objectives

Make the memo table survive process restart: a write-ahead log for durability (P7, I6), a content-addressed store for values (BLAKE3-named, zstd-compressed), a memory-mapped index for O(1) key lookup, versioned serialization (I10), and bounded crash recovery (M9). Zero silent corruption (I7).

18.2 Detailed Implementation Steps

  • Implement WalRecord append + fsync before index mutation (I6, P7), per Kleppmann Ch. 3 and Petrov Part I (books 5, 6). Record kinds: Put, Del, Checkpoint.
  • Implement CAS: value bytes → zstd (ADR-13) → BLAKE3-256 CasKey (ADR-12) → appended to a segment file; the IndexRecord stores (seg_id, seg_off, len, fingerprint). Content addressing deduplicates identical values.
  • Implement the mmap index keyed by QueryKey (§8.5); startup mmaps it for the ≤ 2 s warm start (§4 row 11).
  • Implement versioned serialization (ADR-05): every value prefixed with schema_version; decode rejects unknown-major (I10, P13).
  • Implement crash recovery: on startup, reconcile WAL tail against index, truncate torn records (crc-checked), replay committed puts (M9, I6).
  • Implement group-commit: batch WAL appends from concurrent writers into one fsync to amortize the M8 latency across many entries (Petrov, book 6).
  • Implement periodic Checkpoint records that snapshot the index root offset into the manifest, bounding WAL replay length on recovery (M9 — recovery replays only the tail since the last checkpoint).
  • Store the durability tier in the IndexRecord so GC (§20) can make eviction decisions from the index alone, without loading values.
  • Verify checksum on every read; mismatch ⇒ discard + recompute (I7, P15), per LSM design (O'Neil 1996, paper 10).

18.3 Deliverable

Persistent cache: ecld restarts and reuses the prior session's memo entries; a kill -9 mid-write recovers with no corruption. cache-inspect decodes segments/WAL.

18.4 Acceptance Criteria

  • Warm restart (1M-entry cache) startup ≤ 2 s (§4 row 11) on warm_restart.fixture.
  • Crash-injection (SIGKILL at 1000 random write points): 0 corrupt reads, recovery ≤ 30 s (M9, I7) on crash_matrix.fixture.
  • Storage amplification ≤ 2.5× live value bytes (M10) measured on amplification.fixture.
  • WAL fsync p99 ≤ 8 ms (M8); fuzz_serde round-trips 1M values with 0 mismatches.

18.6 Pitfalls

  • Index update before WAL fsync — a crash then loses the WAL's authority (I6 violated); enforce fsync-before-index in the write path and test with fault injection.
  • Torn record on replay — replaying a partial WAL tail corrupts state; crc-check each record and truncate at first bad crc.
  • Missing checksum on read path — silent corruption slips through (I7); make read-verify unconditional.
  • CAS segment fragmentation — dead values accumulate → amplification blows M10; compaction (§20) reclaims. Real incident anchor: LevelDB/RocksDB write-stall-under-compaction is the documented failure this design's bounded-compaction budget avoids (see FM-8).
  • Unversioned serialized values — decoding an old layout as a new one silently corrupts (I10); every value carries a schema_version and readers reject unknown-major (P13).

18.7 Performance Concerns

  • fsync is the latency bottleneck (M8) — batch WAL appends via group-commit (§32 step 12).
  • Keep the index mmap'd to avoid read syscalls on the lookup path and to hit the ≤ 2 s warm start (§4 row 11).
  • zstd dictionary training amortizes compression cost on the many small memo values (ADR-13).
  • Storage amplification (M10) is traded against compaction frequency — more compaction, less disk, more I/O.

18.8 Edge Cases

  • Disk full mid-write (fail the put, keep the index consistent, T12).
  • WAL larger than RAM (stream replay; never load the whole log).
  • Clock skew across machines (irrelevant — logical revisions, ADR-21).
  • Concurrent readers during recovery (block until reconciliation completes).
  • A value larger than one segment (chunk across segments, reassemble on read).
  • A crash between WAL fsync and index update (recovery replays the WAL put — that's exactly I6).

18.9 Failure Analysis

WAL corruption or a recovery bug ⇒ lost or wrong cache. Detection: startup reconciliation + checksum (I6, I7); blast radius = the whole persisted cache; containment = rebuild from WAL, or worst case discard cache and recompute cold (correct, slow); forensic = cache-inspect dump of WAL/segments; runbook recovery.md. This is FM-2. The design's safety net is that the cache is a pure derivative (MM10): even total cache loss degrades only to a cold rebuild, never to a wrong answer — so the recovery path is allowed to be conservative (discard on any doubt) rather than clever. The checkpoint cadence (§18.2) bounds the worst-case replay to the WAL tail since the last checkpoint, keeping recovery within M9 even for a multi-GB cache.

18.10 Operational Notes

Metrics: wal_fsync_latency, checksum_fail_total (I7), recovery_ok, storage_amplification, cas_dedup_ratio. Logging: span per checkpoint. Deployment: cache dir on fast local SSD. Rollback: run with --no-cache (in-memory only). Compatibility: manifest schema_version gates cross-version reuse (§25).

19. Phase 7 — Parallel Query Execution

19.1 Objectives

Execute independent queries across a work-stealing thread pool with deterministic results (I8, P8): identical outputs under any interleaving, single-flight per QueryId (I8), cooperative cancellation (P14, I13), and NUMA-aware pinning. This is where incrementality meets multicore (M13).

19.2 Detailed Implementation Steps

  • Implement the work-stealing pool (scheduler) with per-worker deques and a global injector, per Rust Atomics and Locks Ch. 2–4 (book 8); no async runtime (ADR-07).
  • Implement per-QueryId execution locks so a query runs at most once per revision; concurrent demanders of an in-flight query block on its result, not re-execute (I8, ADR-08).
  • Use MVCC-style revision-versioned memo reads so a reader sees a consistent snapshot without locking the whole table (Bernstein & Goodman, paper 9; lock-free reads ADR-08).
  • Implement cooperative cancellation via CancellationToken poll points; a cancelled query unwinds leaving no partial memo entry (P14, I13).
  • Handle cycles under parallelism: two workers demanding into a cycle must both observe CycleError deterministically (I4).
  • Publish memo entries via an atomic pointer swap so a lock-free reader either sees the old value or the fully-built new one, never a partial (I13); tie the swap to a completion flag guarded by the per-query lock.
  • Break lock-ordering deadlocks by acquiring per-query locks in QueryKey order, or, for the demand recursion, by detecting a re-entrant demand of a locked key as a cycle (I4) rather than blocking.
  • Isolate worker panics: a panicking query is caught at the worker boundary, converted to QueryError, and does not poison the pool or other queries (§19.8).
  • NUMA: pin worker threads and allocate arenas node-local (§4 row 17).

19.3 Deliverable

Parallel cold build; a --threads N flag; identical output to single-thread run (determinism harness). Cancellation of an in-flight LSP request stops work immediately.

19.4 Acceptance Criteria

  • Cold 1M-LOC build parallel speedup ≥ 12× on 16 cores (M13) on cold_build.rs.
  • Determinism: parallel output byte-identical to single-thread over 100 runs (I8, I11) on determinism_parallel.fixture; duplicate_exec_total == 0.
  • Cancellation: cancel_torn_total == 0 under a cancel-storm on cancel_storm.fixture.
  • Scheduler dispatch overhead ≤ 3 µs/task (M7) on scheduler_micro.bench.

19.6 Pitfalls

  • Duplicate execution race — two threads demand the same cold query; without the per-QueryId lock both run, wasting work and risking nondeterministic tie-break (I8); use single-flight.
  • Torn memo entry on cancel — writing the entry before completion then cancelling poisons the cache (I13); build the entry in scratch, publish atomically only on success (P14).
  • Deadlock via lock ordering — per-query locks acquired in inconsistent order deadlock; order by QueryKey or use try-lock + demand-stack detection. Real incident anchor: early Salsa's single global runtime lock serialized all queries (ref-impl 2) — this design's per-query locking is the documented fix.
  • Nondeterministic HashMap in parallel output — surfaces only under threads; enforce ADR-20 deterministic iteration.
  • Publishing a memo entry before completion — a lock-free reader could see a partial value; publish via atomic pointer swap only on success (I13).
  • Watchdog false-positive on a legitimately long query — tune the heartbeat above the longest expected type_of chain to avoid spurious restarts (FM-5).

19.7 Performance Concerns

  • Lock contention on hot queries (ADR-08); pad memo shards to a cache line to kill false sharing.
  • Work-stealing deque contention at high core count — per-worker deques + a global injector.
  • NUMA remote-memory penalty (§4 row 17) — pin workers and allocate arenas node-local.
  • Batch small queries to amortize the ≤ 3 µs dispatch (M7).
  • Tail latency from a single slow query blocking dependents — surface it via span timing, not averages.

19.8 Edge Cases

  • A query storm (100k ready tasks) — bounded admission queue sheds/queues (ADR-22).
  • A hung query (should never block on external I/O — queries are pure/CPU-bound, P1); a watchdog catches a runaway.
  • Cascading cancellations (a cancelled root cancels its in-flight children via the shared token).
  • A cycle discovered by two workers simultaneously (both observe the same deterministic CycleError, I4).
  • Thread-panic isolation (one worker panic → QueryError, pool survives, §19.2).
  • False sharing on adjacent memo shards under high core count (pad shards to a cache line).

19.9 Failure Analysis

Scheduler deadlock or a determinism break. Detection: watchdog heartbeat + queue-age metric for deadlock; the determinism harness for nondeterminism (I8); blast radius = the whole daemon (deadlock) or one wrong answer (nondeterminism); containment = watchdog restart + replay bisect; forensic = the recorded schedule + replay (§21). This is FM-5. Nondeterminism is the hardest to reproduce because it depends on a thread interleaving; the mitigation is that --threads 1 is always a correct fallback (§19.10), so an incident responder can pin a suspect session to single-thread, reproduce deterministically, and bisect the divergent QueryKey via replay. A deadlock, by contrast, is fail-loud: the watchdog fires within seconds and dumps the lock graph, turning a hang into a restart plus a forensic artifact.

19.10 Operational Notes

Metrics: duplicate_exec_total, cancel_torn_total, per-core utilization, deque steal rate, scheduler_queue_age. Logging: span tree mirrors query tree across threads. Deployment: --threads = physical cores; NUMA pinning on. Rollback: --threads 1 (deterministic, slow). Compatibility: no on-disk change.

20. Phase 8 — Garbage Collection & Cache Durability Management

20.1 Objectives

Keep memory bounded forever (I12, P10): LRU eviction of the in-memory memo table, generational reachability sweep of the persisted cache, durability-aware retention (never evict hot HIGH-durability entries first), and CAS segment compaction to hold storage amplification ≤ 2.5× (M10). A long-lived ecld must not grow unbounded.

20.2 Detailed Implementation Steps

  • Implement LRU tracking on MemoEntry access; evict coldest first when memo_bytes nears the ceiling (I12), per Salsa LRU (paper 8). Evicting a derived entry is always safe — it can be recomputed (P1).
  • Implement durability-aware eviction order: evict LOW durability before MEDIUM before HIGH, breaking ties by LRU (P4); HIGH entries (std-lib) are recompute-expensive and rarely change.
  • Implement generational reachability GC of the persisted CAS: mark values reachable from the current index, sweep unreachable segments during compaction (LSM compaction, O'Neil 1996, paper 10; ADR-24).
  • Implement bounded compaction: cap compaction I/O per interval to avoid write-stall (the FM-8 regime); compact when amplification exceeds threshold.
  • Pin entries during in-flight validation/read (a use-count on the shard) so eviction/GC never reclaims an entry a running query is reading (§20.8).
  • Reclaim CAS space by rewriting live values into fresh segments and dropping fully-dead segments, preserving CasKeys (content-addressed, so re-hashing is unnecessary); update the index atomically under a checkpoint (I6).
  • Track a per-durability-tier byte budget so a flood of LOW-durability entries can't evict the HIGH-durability std-lib working set (P4).
  • Interner GC: drop Interned strings unreferenced by any live green tree or symbol (ties off §14.6/§16.6 leaks).

20.3 Deliverable

An ecld that runs for days at bounded RSS; a compaction scheduler; metrics showing eviction and amplification steady-state.

20.4 Acceptance Criteria

  • Soak test (72 h, continuous edits): RSS stays ≤ 8 GB (M12), 0 OOM (I12) on soak_72h.fixture.
  • Post-compaction storage amplification ≤ 2.5× (M10) on compaction.fixture.
  • Evicting then re-demanding a derived query returns the identical value (recompute correctness, I1) on evict_recompute.fixture.
  • GC never reclaims a live-referenced value: dangling_ref_total == 0 on gc_liveness.fixture.

20.6 Pitfalls

  • Evicting a live input — inputs are not recomputable; GC must never touch input queries (P2); mark inputs pinned.
  • Reclaiming a referenced CAS value — a dangling IndexRecord → corruption (I7); mark-sweep must trace the full live set before reclaim.
  • Recompute-on-evict divergence — an evicted value that recomputes differently signals an impurity (I15, P1); treat evict_recompute_mismatch > 0 as a correctness bug, not a GC bug.
  • Compaction write-stall — unbounded compaction I/O starves foreground queries (FM-8); cap per-interval I/O.
  • LRU thrash — a working set larger than the ceiling evicts hot entries repeatedly; alert and recommend a larger ceiling rather than thrash silently (I12).
  • Evicting an input — inputs are not recomputable (P2); GC must pin inputs and only ever evict derived values (I15).
  • Interner entry freed while a persisted tree references it — trace persisted references, not just in-memory ones, before dropping an Interned string.

20.7 Performance Concerns

  • GC/compaction contends with foreground queries for CPU and disk — run compaction on a low-priority lane.
  • LRU bookkeeping must be O(1) per access (intrusive list, not a scan).
  • Reachability mark is O(live entries) — bound it by generational scoping so a full sweep is rare.
  • Cap compaction I/O at the §4 row 29 ceiling (50 MB/s) so it never starves interactive queries (FM-8).

20.8 Edge Cases

  • Ceiling set below the minimum live working set (refuse startup or warn — thrash is worse than a clear error).
  • Eviction during in-flight validation (pin-on-use prevents reclaiming an entry being read).
  • A burst filling the cache faster than compaction reclaims (backpressure, ADR-22).
  • An interner entry referenced by a persisted-but-not-in-memory tree (trace persisted references before GC).
  • Compaction interrupted by a crash (segments are append-only; the old segment stays valid until the checkpoint commits, I6).

20.9 Failure Analysis

A GC bug reclaims live state ⇒ corruption/crash; an eviction bug ⇒ OOM. Detection: dangling_ref_total, RSS watermark, evictions_total (I12); blast radius = daemon stability; containment = pin-on-use + full-sweep verification in CI; forensic = liveness snapshot at reclaim time. This is FM-9. The invariant that makes this recoverable is I15: any reclaimed derived value must recompute identically, so an over-aggressive eviction is a latency bug, not a correctness bug — the only truly dangerous reclaim is of a live-referenced value (I7 violation), which the pin-on-use use-count and the gc_liveness.fixture full-sweep test are designed to make impossible. Disabling GC (--no-gc) is always a safe stopgap bounded by process restart.

20.10 Operational Notes

Metrics: memo_bytes, evictions_total, storage_amplification, compaction_io_bytes, dangling_ref_total, interner_entries. Logging: span per compaction cycle. Deployment: tune ceiling to host RAM; compaction off-peak. Rollback: disable GC (bounded by restart). Compatibility: compaction rewrites segments but preserves CasKeys (content-addressed, stable).

21. Phase 9 — LSP Integration & Deterministic Replay

21.1 Objectives

Expose the engine to editors via LSP 3.17 (lsp), map edits to set_input + revision bumps and requests to demanded queries with cancellation, and ship deterministic record/replay (replay) so any production session can be re-executed bit-identically for debugging (I11, P8). This is the interactive, auditable capstone.

21.2 Detailed Implementation Steps

  • Implement the JSON-RPC 2.0 server (lsp) over stdio (LSP 3.17 / JSON-RPC RFCs, §5): didChange→set_input + revision bump (I2), hover/completion→resolve+type_of, publishDiagnostics←diagnostics (§8.4).
  • Map $/cancelRequest to the query CancellationToken (P14, I13) so stale requests stop immediately.
  • Implement replay record: log inputs, revisions, and per-query (QueryKey,Fingerprint) to a ReplayLog (§11); verify mode re-executes and diffs fingerprints (I11), overhead ≤ 15% (M11).
  • Implement debounced edit coalescing so rapid keystrokes bump one revision batch, not one per char (bounds validation churn).
  • Tag every published LSP result with the revision it was computed at; drop results whose revision is stale relative to the client's latest edit so the editor never shows diagnostics for text the user already changed (I2, §21.6).
  • Serve the visible file's diagnostics first (priority hint to the scheduler) so interactive latency (M1) is governed by the open buffer, not the whole workspace.
  • Implement incremental didChange range application: map an LSP range edit to a byte-range set_input delta that feeds the incremental relex/reparse (§14, §15) rather than re-reading the whole file.
  • Wire the differential harness (§26): incremental session vs from-scratch, compared via replay.

21.3 Deliverable

ecl-lsp usable in a real editor (VS Code) with hover, completion, live diagnostics; replay record/replay verify CLI; a recorded corpus in conformance/replay/.

21.4 Acceptance Criteria

  • Warm hover/diagnostics p95 ≤ 80 ms (M1), p99 ≤ 150 ms on lsp_latency.fixture.
  • Replay of any recorded session reproduces identical fingerprints: replay_mismatch_total == 0 (I11) on replay_corpus.fixture; replay overhead ≤ 15% (M11).
  • LSP conformance: all conformance/lsp/ message fixtures pass; malformed RPC yields a JSON-RPC error, not a crash, on malformed_rpc.fixture.
  • Cancellation of a stale request: 0 stale diagnostics published on rapid_edits.fixture.

21.6 Pitfalls

  • Stale diagnostics — publishing results from a cancelled/old revision confuses the editor; tag every result with its revision and drop stale ones (I2).
  • Cancellation leak — a cancelled request whose token isn't propagated keeps burning CPU (I13, P14); thread the token through every sub-query.
  • Replay nondeterminism — any impurity (P1) surfaces as a replay mismatch; treat replay_mismatch_total > 0 as a purity bug, bisect via the divergent QueryKey.
  • Edit storm without debounce — one revision per keystroke floods validation; coalesce (§4 row 27).
  • Publishing diagnostics for a superseded revision — tag every result with its revision and drop stale ones (I2), else the editor flickers.
  • Unbounded replay-log growth — a long daemon session's ReplayLog must be capped/rotated, not retained forever (P10).

21.7 Performance Concerns

  • LSP latency is the user-visible number (M1) — demand the visible file's queries first.
  • Replay recording adds ≤ 15% (M11) — make it append-only and off the critical path.
  • Debounce edits (§4 row 27) to bound the revision rate to ≤ 33/s (§32 step 12).
  • Range-based didChange feeds the incremental relex/reparse; never re-read the whole buffer on a keystroke.

21.8 Edge Cases

  • Client disconnect mid-request (cancel in-flight work + clean up the token, I13).
  • Overlapping edits to the same range (apply in order; each bumps the revision).
  • A request for a file not yet opened (open-on-demand as an input, or return an empty result).
  • A huge paste (single large set_input delta, not per-char — bounded by debounce).
  • Clock-independent replay across machines (logical revisions make the log portable, ADR-21).
  • A $/cancelRequest for an already-completed request (no-op; the result is dropped if stale).

21.9 Failure Analysis

A replay mismatch reveals a latent nondeterminism/impurity bug — exactly the class replay exists to catch (FM-3). Detection: replay_mismatch_total (I11); blast radius = trust in every incremental result; containment = fall back to batch recompute for the affected session, bisect the divergent query; forensic = the ReplayLog; this closes the debugging loop opened in §7. Because replay is fingerprint-exact, the mismatch report names the first divergent QueryKey in demand order, which is almost always the impure query itself (a SystemTime read, a HashMap-iteration leak, an uninitialized-memory read) rather than a downstream victim — turning "the compiler was flaky once" into a one-query fix. The LSP layer additionally drops stale-revision results (§21.6), so a revision race manifests as a caught replay mismatch in CI, not as flicker in the user's editor.

21.10 Operational Notes

Metrics: LSP request latency histogram, replay_mismatch_total (I11), cancelled_requests_total, revision rate. Logging: span per LSP request correlated to query spans. Deployment: ecl-lsp per editor over stdio; ecld shared daemon for CI. Rollback: eclc batch mode (no LSP). Compatibility: LSP capabilities negotiated at initialize; replay-log format versioned (I10).

Named runbooks. recovery.md (FM-2), invalidation-storm.md (FM-6), cache-corruption.md (FM-4). Incident response: page → consult runbook → contain (quarantine/restart) → replay-bisect → postmortem in docs/failure-analysis/. Runbook skeletons:

  • recovery.md (FM-2): (1) confirm recovery_ok == 0 and read the manifest via cache-inspect; (2) if the manifest magic/version is intact, let WAL replay run and watch recovery_seconds against M9; (3) if the WAL tail is torn, truncate at the first bad CRC and re-run; (4) if the manifest is unreadable, discard the cache dir and cold-rebuild (correct, slow) — the source is the truth (MM10).
  • invalidation-storm.md (FM-6): (1) confirm early_cutoff_total dropped or unstable_id_total > 0; (2) diff the recent deploy — a SymbolId/fingerprint-derivation change is the usual cause (I9, I14); (3) bisect with git bisect + the cutoff-rate fixture; (4) roll back the offending change; caches auto-recover as ids restabilize.
  • cache-corruption.md (FM-4): (1) confirm checksum_fail_total > 0; (2) cache-inspect the failing CasKey to classify bit-rot vs tampering (T3); (3) the engine has already discarded + recomputed (P15) — verify the recomputed value's fingerprint; (4) if widespread, suspect disk failure and fail over the host.

Backup/restore. The cache is a rebuildable derivative — "backup" = the source workspace; restore = cold rebuild. WAL + segments may be snapshotted for fast restore but are never authoritative over source.

Deployment topology. ecl-lsp per developer (stdio); ecld daemon pool on CI workers (UDS) behind a load balancer; Prometheus + OTEL collector sidecars.

Canary / rolling upgrade / rollback / migration. New daemon versions canary on a subset of CI workers; schema changes bump schema_version (I10) so old caches are ignored, not mis-read; rollback = redeploy prior binary (cache is version-gated, safe); migration is lazy (recompute on first demand under the new version).

25. Compatibility & Versioning

  • Wire (LSP/JSON-RPC). Capabilities negotiated at initialize; unknown methods return method-not-found, never crash (T7). LSP 3.17 baseline.
  • Storage/schema evolution. Every persisted record carries schema_version (I10, P13, ADR-05). Readers reject unknown-major and ignore old caches (recompute), accept known-minor additively. A SymbolId/Ty/HIR layout change bumps major → persisted semantic caches invalidated (§16.10, §17.10).
  • API stability. The DerivedQuery/Database traits are the internal contract; SemVer 2.0 governs the published crates. Query IDs are append-only (QueryId never reused).
  • Migration. Lazy: on version bump, entries are recomputed on first demand; no offline migration tool needed because derived state is rebuildable.
  • Deprecation policy. A query kind deprecated for ≥ 2 minor versions before removal; its QueryId is retired, not reused.
  • SemVer policy. Breaking on-disk format or wire change → major; additive query/metric → minor; fixes → patch.
  • Rolling-upgrade guarantees. Two adjacent minor versions of ecld interoperate on the same workspace: the newer ignores caches it can't read (version-gated), so mixed fleets degrade to recompute, never to corruption.

29. Scalability Analysis

Constant vs grows. Warm reconciliation cost is O(change) — proportional to dirtied queries, not workspace size — as long as early cutoff (I3) and durability firewalls (P4) hold; this is the defining property (§4). Cold build is O(program), parallelized to O(program / cores) up to the critical path (M13). Memo memory is O(live queries) ≈ O(workspace) (§32), bounded by GC (I12, §20). Validation traversal is O(dirty subgraph), not O(graph), via durability.

Named bottlenecks, in order. (1) Dependency fan-in — a widely-referenced symbol (§4 row 16, 100k edges) makes one change fan out; mitigated by per-reference resolve queries (§16.7). (2) Interner / memo lock contention at high core counts (ADR-08); sharding + lock-free reads. (3) WAL fsync serialization (M8); group-commit. (4) Compaction I/O vs foreground (FM-8); bounded lane. (5) Critical-path length limiting parallel speedup (M13).

Horizontal / vertical scaling. Vertical: more cores help cold build to the M13 ceiling; more RAM raises the memo ceiling (I12). Horizontal (deferred, §35): shard the query cache by module across ecld nodes with content-addressed cross-node reuse; coordination overhead = cache-key gossip + consistency of shared inputs.

Sharding/partitioning. Memo table sharded by QueryKey hash (in-process); persisted cache partitioned by segment; future cross-machine partition by module namespace.

Practical ceiling & levers. Single daemon: ~50M LOC at 8 GB (M12, §32). Beyond that: raise RAM (lever 1), shard across daemons (lever 2, deferred), coarsen durability tiers to cut validation (lever 3), or drop cold namespaces from the warm set (lever 4, LRU).

30. Mental Models & First Principles

  • MM1 — Incremental = memoize + validate + cut off. A derived query is a pure function; the cache holds its last value and its dependency fingerprints; you re-run only when a fingerprint changed. Predicts: recompute count ≈ size of the fingerprint-changing frontier, not the program. Bug without it: re-running downstream on unchanged values (batch-in-disguise). Applied: §13.
  • MM2 — Early cutoff is where the savings live. The graph's edges, not its nodes, are where you stop propagation: an unchanged fingerprint at an edge prunes an entire subtree. Predicts: trivia edits are nearly free (M3). Bug without it: a stable value that still forces dependents to recompute. Applied: §14, §13.
  • MM3 — Identity stability is a performance feature. If SymbolIds/spans renumber on unrelated edits, every downstream fingerprint flaps and incrementality collapses. Predicts: the biggest incremental wins come from not changing identities, not from faster recompute. Bug without it: "why does adding a comment recompile everything?" Applied: §16.
  • MM4 — Durability is a bet on change frequency. Tag rarely-changing inputs HIGH so validation skips their subgraphs by revision comparison alone. Predicts: std-lib validation is O(1) per edit. Bug without it: every keystroke walks the entire prelude. Applied: §13, §17.
  • MM5 — The dependency graph is the correctness boundary, not the cache. Cache invalidation is exactly graph reachability from changed inputs; a missed edge is a wrong answer, not a slow one. Predicts: correctness bugs are missed/extra edges. Bug without it: trusting timestamps/heuristics over recorded reads. Applied: §13 (P12, I5).
  • MM6 — WAL turns a crash into a bounded replay. Durability = "the log is the truth; the index is a cache of the log." Predicts: recovery time = replay of the WAL tail (M9), not a full rebuild. Bug without it: index-before-log ordering that loses data on crash. Applied: §18 (P7, I6).
  • MM7 — Determinism is what makes debugging possible. A pure, logical-revision system replays bit-exactly; a mismatch is a bug report. Predicts: nondeterminism surfaces as replay_mismatch_total, always. Bug without it: heisenbugs you can't reproduce. Applied: §21, §7 (P1, I11).
  • MM8 — Content addressing makes corruption self-detecting. If a value's name is the hash of its bytes, tampering/bit-rot is a name/content mismatch you catch on read. Predicts: zero silent corruption is achievable with one compare (I7). Bug without it: trusting bytes you can't verify. Applied: §18 (ADR-12, MM8→FM-4).
  • MM9 — Split a query along its firewall, not its function. Divide a computation where its consumers' interest changes (signature vs body, module-symbols vs one reference), so an edit invalidates the smallest consumer set. Predicts: the right query boundaries are where change frequency differs, not where the code is naturally factored. Bug without it: a coarse query that re-runs callers on irrelevant internal edits. Applied: §16 (symbols/resolve split), §17 (signature/body split).
  • MM10 — The cache is a derivative; the source is the truth. Every persisted byte is recomputable from source, so the cache is disposable and "backup" is meaningless for it. Predicts: the safe response to any cache doubt is discard-and-recompute, never repair-in-place. Bug without it: trying to salvage a corrupt cache and shipping a wrong answer (P15 violated). Applied: §24 (backup/restore), §18 (FM-4).

32. Back-of-Envelope Capacity Model

All derived from the §4 System Constraints table (formulas shown).

  1. Source bytes at 50M LOC. 50M LOC × ~40 B/line (avg) = 2.0 GB source (matches §4 row 1). Formula: LOC × bytes_per_line.
  2. Memo entries. ~1 query per 5 LOC across ~8 pipeline stages → 50M/5 × (fraction materialized ≈ 0.3) ≈ 3M live derived entries at steady IDE working set (not all 50M cold). Formula: LOC/LOC_per_query × materialized_fraction.
  3. Working-set RAM (metadata + edges + trees). The three RAM consumers, each derived and summed: (a) memo metadata — 3M × 160 B/entry (§4 row 23: key 16 + fp 16 + revs 16 + dep header + value ptr) = 480 MB, formula entries × bytes_per_entry, under the 2.5 GB metadata ceiling (§4 row 3); (b) dependency edges — 3M × avg fan-in 6 = 18M edges × 8 B = 144 MB, formula entries × avg_fanin × bytes_per_edge (worst-case fan-in 100k, §4 row 16, is per-node, not average); (c) green trees — 2.0 GB source × ~3× node overhead with structural sharing ≈ 1.5 GB (largest single consumer), formula source_bytes × node_overhead_factor. Sum (a + b + c) ≈ 2.1 GB — within the 8 GB RSS ceiling (§4 row 2) with headroom for interner + scratch.
  4. Fingerprint bandwidth per full hash pass. 2.0 GB ÷ BLAKE3 ~3 GB/s = ~0.67 s to fingerprint the whole workspace once. Formula: source_bytes / hash_throughput. Confirms cold fingerprinting is not the M5 bottleneck.
  5. Warm edit recompute budget. M2 p50 25 ms ÷ M6 memo-lookup 5 µs = ~5,000 memo lookups affordable per warm edit before recompute dominates. Formula: recompute_budget / lookup_cost. Sets the fan-out ceiling before an edit misses M1.
  6. WAL write rate at steady edit. ~5,000 changed entries/edit (step 5) × 160 B = 800 KB/edit; at 10 edits/s = 8 MB/s WAL, group-committed. Formula: changed_entries × entry_bytes × edit_rate. Trivially within SSD + the M8 fsync budget.
  7. Disk footprint. 3M entries × avg 300 B value × 2.5 amplification (§4 row 15) = ~2.25 GB on disk. Formula: entries × avg_value_bytes × amplification.
  8. Crash recovery time. 1M WAL records ÷ ~50k records/s replay (crc + index insert) = ~20 s < the 30 s M9 target (§4 row 14). Formula: wal_records / replay_rate.
  9. FD budget. ~250k files (row 1) but only open segments + mmap'd index + active file handles ≈ hundreds concurrently → well under the 8,192 FD cap (§4 row 13). Formula: open_segments + index_maps + active_files.
  10. Parallel critical path. Cold M5 120 s × M13 speedup 12× ⇒ single-thread ≈ 1,440 s; critical path must be ≤ 120 s or speedup caps below 12×. Formula: single_thread_time / speedup ≥ critical_path.
  11. Interner size. 50M LOC at ~1 identifier per 8 tokens, ~4 tokens/line → 25M identifier occurrences, but with ~99% dedup (few unique names) → ~250k unique interned strings × ~24 B avg = 6 MB. Formula: occurrences × (1 − dedup_ratio) × avg_len. Negligible against the 8 GB ceiling (§4 row 2).
  12. Debounce & group-commit fsync rate. Two chained bounds on write churn: (a) at the 30 ms debounce window (§4 row 27) a keystroke burst collapses to ≤ 33 revisions/s regardless of typing speed, formula 1 / debounce_window, holding M1 under fast typing; (b) 33 rev/s × ~5,000 changed entries (step 5) = 165k naïve fsync/s (impossible), so group-commit at the ≤ 2 ms window (§4 row 28) collapses it to ≤ 500 fsync/s, formula edit_rate / commit_window — which is why M8 is reachable.

34. Alternative Architectures (Roads Not Taken)

A. Timestamp/mtime file-granular rebuild (the make/coarse-build model).

files --mtime--> "dirty set" --> rebuild whole files --> outputs

Wins when: the unit of change really is a whole file and dependencies are coarse (C translation units, asset pipelines). Embodied by: make, early ccache, Ninja. Rejected because: file granularity over-invalidates (a comment edit rebuilds the file's every downstream); no early cutoff at sub-file granularity; mtimes are non-deterministic and clock-skew-fragile (violates P1/ADR-21). This design is query-granular (§29) precisely to avoid that blast radius.

B. Eager forward propagation (push/reactive dataflow).

input change --> push --> recompute every downstream immediately (spreadsheet-style)

Wins when: nearly everything is always needed and outputs must be continuously live (spreadsheets, streaming dataflow, some reactive UIs). Embodied by: Excel's recalc engine, differential dataflow. Rejected because: a compiler needs only the demanded outputs (the open file's diagnostics), so eager push wastes work on unviewed modules; demand-driven pull (Adapton/Salsa model, §13) computes only what's asked. Kept the pull model, borrowed nothing eager.

C. Global immutable snapshot per revision (pure persistent database).

revision N: whole-program snapshot --> revision N+1: new snapshot (structural share)

Wins when: you want trivial time-travel/undo and cheap consistency, in a GC'd runtime where snapshot sharing is nearly free. Embodied by: Roslyn's Compilation snapshots, Datomic. Rejected as the top-level model because: without GC, retaining every revision's snapshot blows the M12 memory ceiling, and validation still needs per-query fingerprints to avoid recomputing the snapshot. This design borrows immutable structural sharing at the tree level (§14–§15) but keeps a single mutable revision counter, not a retained snapshot per revision.

36. Glossary

  • Cold build — a build with an empty cache; O(program) (§29).
  • Compaction — reclaiming dead CAS segments to bound storage amplification (§20).
  • Cutoff (early cutoff) — stopping propagation when a re-executed query's fingerprint is unchanged (I3, P3).
  • DerivedQuery — a pure function of other queries; the memoized unit (§11).
  • Dependency edge — a recorded "query A read query B" relationship (P12, I5).
  • Durability — a tier (LOW/MED/HIGH) predicting an input's change frequency, letting validation skip stable subgraphs (P4).
  • ecl — the example compiler language, a test vehicle for the incremental substrate (§1).
  • ecld / eclc / ecl-lsp — the daemon, batch CLI, and language-server front doors (§1).
  • Fingerprint — 128-bit BLAKE3 of a query's serialized value; the early-cutoff comparison key.
  • Firewall — a durability boundary that halts invalidation propagation (P4).
  • Green tree — immutable, structurally-shared, offset-free syntax tree (§14, P5).
  • HIR — high-level intermediate representation, the semantic lowering target (§17).
  • Hygiene — the property that spans/identities stay stable across unrelated edits (I9, I14).
  • Input query — a query whose value is set by the driver, not computed (P2).
  • Interner — deduplicating string/symbol store producing Interned ids (§16, P5).
  • Invalidation storm — a pathological cascade where early cutoff fails and O(program) work results (FM-6).
  • Memo entry — a cached (value, fingerprint, revisions, deps) record for one query (§8.2, §11).
  • MVCC — multi-version concurrency control; revision-versioned reads under parallelism (§19, paper 9).
  • Poison (Ty::Error) — an error value that propagates without cascading duplicate diagnostics (P15, §17).
  • Query key — (QueryId, key_hash) uniquely identifying a query invocation (§11).
  • Red tree — a lightweight cursor overlay adding absolute offsets/parents over a green tree (§15).
  • Red-green marking — per-revision coloring (Green=validated-clean, Red=must recompute) (§8.3, §13).
  • Replay — recording inputs+revisions to re-execute a session bit-identically (I11, §21).
  • Revision — the global monotone logical clock; every input change bumps it (I2, ADR-21).
  • Single-flight — guarantee a query executes at most once per revision (I8).
  • Span — a (file, lo, hi) byte range anchoring diagnostics; hygiene-stable (I9).
  • Storage amplification — bytes on disk ÷ live value bytes; held ≤ 2.5× (M10).
  • Subtree reuse — reusing an unedited green subtree across a reparse (§15, P3).
  • SymbolId — content+scope-derived stable identity for a resolved name (P6, I9).
  • verified_at — the revision at which a memo entry was last proven clean (§8.2).
  • WAL (write-ahead log) — durable log fsynced before index mutation, enabling bounded recovery (P7, I6).
  • Work-stealing — the scheduler model where idle workers steal tasks from busy workers' deques (§19).
  • Workspace — the full set of source files/modules under one session (§4).
  • Arena — a bump-allocated region for short-lived scratch (e.g. parser events), freed as a unit (§12, ADR-14).
  • Backpressure — rejecting or queuing work when a bounded resource is full, rather than growing unbounded (P10, ADR-22).
  • Checkpoint — a WAL record snapshotting the index root, bounding replay length on recovery (§18, M9).
  • Debounce — coalescing rapid edits into one revision batch to bound validation churn (§21, §4 row 27).
  • Demand-driven (pull) — computing a value only when it is asked for, versus eager push (§13, §34-B).
  • Differential testing — comparing incremental output to a from-scratch recompute to catch reuse bugs (I1, §26).
  • EdgeKind — whether a dependency edge reads a value or only an input's existence (§11, §13).
  • Existence edge — a dependency on "is this input present?" rather than its value (§13).
  • Group-commit — batching many WAL appends into one fsync to amortize latency (§18, M8).
  • Injector queue — the global task queue a work-stealing pool pulls from when a worker's deque is empty (§19).
  • NUMA pinning — binding worker threads and their allocations to one memory node to avoid remote-access penalty (§19, §4 row 17).
  • Pratt parsing — precedence-climbing expression parsing used for ecl binops (§8 grammar, §15).
  • Quarantine — dropping a suspect cache entry and recomputing rather than serving it (P15, FM-4).
  • Trivia — whitespace and comments attached to tokens but excluded from the significant-token fingerprint (§14, I14).
  • Single-flight — see also I8; deduplicating concurrent demands of one query into a single execution (§19).
  • Compaction I/O ceiling — the cap (50 MB/s, §4 row 29) on background compaction throughput protecting foreground latency (FM-8).
  • Poison suppression — not emitting duplicate diagnostics for items whose inputs are already Ty::Error (§17, P15).
  • Work-stealing deque — a per-worker double-ended queue; the owner pushes/pops one end, thieves steal the other (§19).
  • Firewall query — the stable caller-visible query (signature, module symbol set) hiding a volatile implementation query (P17, MM9).
  • Read barrier — the instrumentation that routes every query read through the dependency recorder (I5, §13).
  • Verifying-trace rebuilder — the Build-Systems-à-la-Carte category this engine occupies: recompute a query iff a recorded dependency changed (Mokhov 2018, paper 5; §31).
  • Suspending scheduler — the scheduler category (pull, on-demand) paired with the verifying-trace rebuilder in the §31 taxonomy (Mokhov 2018).
