Project Name: Approximate Nearest Neighbor Index (HNSW/IVF-PQ)

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from scratch in Rust, an embeddable approximate-nearest-neighbor (ANN) vector index implementing the two dominant index families — HNSW (graph-based) and IVF-PQ (partition + compression-based) — plus a flat/brute-force index as the exact ground truth. The system's central engineering concern is making the recall-versus-latency- versus-memory tradeoff a measured, reportable quantity rather than a marketing adjective: every index configuration is a point on a three-dimensional surface (recall, latency, memory) and this blueprint requires that point to be stated, not implied. The index is a library and an on-disk artifact, not a service: it does not own payload storage, network protocol, authentication, or multi-tenancy. It provides distance computation, index construction, index search, incremental mutation, and evaluation; it delegates everything about "being a database" to a host process.

Phase-0 Deliverable — Crate List

  1. ann-core — shared types (VectorId, Dim, Metric), error taxonomy, no algorithm code.
  2. ann-simd — SIMD distance kernels (L2, inner product, cosine) with runtime CPU dispatch.
  3. ann-flat — flat/brute-force exact index; the recall oracle used by every other index.
  4. ann-quantize — k-means/k-means++ trainer, product-quantization codebooks, scalar quantization.
  5. ann-hnsw — HNSW graph builder and greedy-search traversal.
  6. ann-ivf — IVF coarse quantizer and inverted lists.
  7. ann-ivfpq — the combined IVF-PQ pipeline (coarse routing + asymmetric PQ distance).
  8. ann-mutate — incremental insert/delete, tombstones, compaction.
  9. ann-filter — filtered-search predicate evaluation (pre-filter and post-filter paths).
  10. ann-persist — on-disk serialization and memory-mapped index loading.
  11. ann-eval — recall@k / latency / memory evaluation harness, ANN-Benchmarks-compatible.
  12. ann-bench — CLI binaries: build, search, tune, evaluate.

Boundaries

Provides: distance kernels; flat/HNSW/IVF-PQ index construction and search; PQ and scalar quantization; incremental insert/delete with tombstones and compaction; filtered search combining metadata predicates with vector search; persistence and mmap loading; a recall/latency/memory evaluation harness.

Delegates to the host: storage of original vector payloads and any associated documents (the index stores only what it needs to compute distances and reconstruct approximations — VectorId plus the vector itself); the query API surface (REST/gRPC/ whatever the host exposes); authentication and multi-tenancy; distributed sharding and replication; embedding generation (the index consumes vectors, it does not produce them from raw text/images).

Does NOT provide: a full vector database (no network protocol, no persistence of arbitrary JSON payloads, no cluster coordination) — this is an index, one component a vector database would embed.

Non-Goals (Phase 0)

  • No GPU backend in Phase 0 — deferred, see PhaseDeferred("GPU-resident brute-force/IVF backend").
  • Not a distributed sharded index in Phase 0 — deferred, see PhaseDeferred("cross-node shard federation").
  • Not an embedding model — vectors arrive pre-computed from the host; the index never runs a neural network.
  • Not a full inverted-multi-index or anisotropic-quantization implementation in Phase 0 — deferred, see PhaseDeferred("anisotropic (ScaNN-style) quantization loss").

Deployment Model

Primary: embeddable library, linked into a host process, index resident either fully in heap memory or as a memory-mapped file backed by the page cache. Secondary (optional, not a Phase-0 deliverable): a thin evaluation/administration service wrapping ann-bench for offline tuning runs — this is a convenience binary, not a query-serving service.

Users / Operators

Users: ML-infrastructure engineers embedding the index into a retrieval or RAG service; search-infrastructure engineers who need a quantified recall/latency/memory point before choosing HNSW versus IVF-PQ; systems engineers profiling the SIMD distance kernels. Operators: whoever runs the host process — this blueprint's operational surface (§26) is written for that operator, not for a dedicated ANN-index SRE team, because there is no standalone service to operate in Phase 0.

What Later Phases Unlock

Phase 9 (insert/delete) unlocks online corpora that grow and shrink without a full rebuild. Phase 10 (filtered search + persistence) unlocks metadata-constrained queries and cold-start-safe mmap loading, which together are the two things a host vector database most needs from this library. Phase 11 (tuning + conformance) unlocks a defensible, benchmarked recall/latency/memory number for any given deployment target, which is the artifact every downstream integration decision depends on.

Language: Rust — Rationale and Rejected Alternatives

Rust is locked because the inner loop of every index family here is a tight distance-computation loop that must be branch-predictable, SIMD-vectorizable, and free of GC pauses that would otherwise appear as tail-latency spikes. Ownership lets the mmap-backed read path be zero-copy and Send + Sync without a garbage collector. Rejected: C++ (FAISS's own language — capable of identical SIMD throughput, rejected here because the teaching goal is a memory-safe from-scratch build without a class of use-after-free bugs that FAISS itself has had to harden against over a decade); Go (GC pauses are incompatible with a p99 latency floor measured in fractions of a millisecond, and its SIMD ecosystem is immature); Python (interpreter and GIL overhead make it structurally unable to run the inner distance loop at the required throughput — acceptable only as a bindings layer, never as the implementation language); Java (JIT warmup and GC pauses reproduce Go's problem with additional startup cost).

Prerequisites

Linear algebra (inner products, norms, orthogonal projections — needed for every distance metric and for PQ subspace splitting); probability (k-means convergence, variance reduction, the layer-assignment probability in HNSW); the geometry of high-dimensional spaces (concentration of measure, why volume concentrates near the surface of a high-dimensional ball, why this makes exact search intractable and approximate search necessary — foundational to Indyk & Motwani 1998 STOC and to every practical design decision from §8 onward).

2. Why Build This

  • graph-based ANN search internals (HNSW, navigable small worlds) — Phase 3, Phase 4.
  • quantization as lossy compression that preserves rank order, not values — Phase 5, Phase 6.
  • the curse of dimensionality made operational, not just theoretical — Phase 1, Phase 2.
  • recall as a measured quantity with a latency and a memory cost attached — Phase 2, Phase 11.
  • SIMD-vectorized numerical kernels and cache-aware data layout — Phase 0, Phase 2.
  • k-means and Lloyd's algorithm as the workhorse of every quantization scheme here — Phase 5.
  • asymmetric distance computation and why quantizing the query would be a mistake — Phase 6.
  • incremental mutation without full rebuilds, and the tombstone/compaction lifecycle — Phase 9.
  • filtered search as a decision (pre-filter vs. post-filter vs. in-graph) with no universal answer — Phase 10.
  • memory-mapped persistence and the difference between "loaded" and "resident" — Phase 10.

Historically, ANN indexes are the substrate underneath semantic search, retrieval- augmented generation, recommendation systems, deduplication, and image/audio similarity search. Every one of those systems is, underneath, a call to an index like this one.

  • Can state, unprompted, the recall@10, p50/p95/p99 latency, and memory-per-vector for a given HNSW or IVF-PQ configuration on a named dataset — Phase 11.
  • Can explain why the flat index is never replaced by "a better approximation" as the ground truth, only ever by exact math — Phase 1.
  • Can trace a greedy HNSW search by hand through its layers and explain why the upper layers are sparse — Phase 4.
  • Can derive product-quantization compression ratio and reconstruction error from the subspace count and bits-per-code, without running code — Phase 6.
  • Can explain why asymmetric distance computation exists and what compounding error it avoids — Phase 6.
  • Can diagnose a silent recall regression from telemetry alone, without re-running a benchmark — Phase 11, §26.

Vector Store: owns the canonical f32 (or quantized) representation of every inserted vector behind an Arc<[f32]>, immutable once written; every index family borrows from it rather than copying.

Distance Kernels: the single implementation of L2, inner-product, and cosine distance, SIMD-dispatched at runtime; every other box calls into this one and never reimplements arithmetic — a correctness bug here corrupts every index simultaneously.

Flat Index: brute-force exact k-NN over the vector store; read path takes a shared lock, write path (insert) takes none because appends to the underlying Vec are serialized through the mutation manager; this is the permanent ground truth (I1).

HNSW Graph: a layered proximity graph; each node's neighbor lists are individually lock-guarded so concurrent readers never block on unrelated nodes, while a single writer mutates neighbor lists during insertion under the mutation manager's serialization.

IVF Coarse Quantizer + Inverted Lists: partitions vector space into nlist Voronoi cells via k-means; each cell's inverted list is an append-mostly Vec<PqCode> guarded by a per-cell lock, so writes to different cells never contend.

Product Quantizer: trained offline (batch k-means per subspace) then frozen; read-only at query time; the sole owner of code-to-centroid semantics (I5).

Scalar Quantizer: optional heap-resident per-dimension linear quantization, used when PQ's memory win is not needed but a smaller-than-f32 footprint is; independent of PQ.

Filtered-Search Path: evaluates metadata predicates supplied by the host against a bitmap or callback, deciding pre-filter versus post-filter per §8's decision table; read-only with respect to the index.

Insert/Delete Manager: the only writer of mutating operations; delete marks a tombstone (I3) rather than removing data; compaction later reclaims tombstoned space in the background.

Persistence/Mmap Layer: serializes the graph, codebooks, and inverted lists to a versioned on-disk format; loading maps the file read-only and lets the OS page cache manage residency — the index reloaded from disk must return identical results to the in-memory index (I7).

Recall/Latency Evaluator: computes recall@k against the flat oracle and reports latency percentiles and memory; the only component permitted to declare a build "done."

6. Design Principles

P1 — Recall is measured, never adjectival. Rule: every index configuration reports recall@k, latency, and memory together; none is stated alone. Tradeoff: more reporting overhead in the eval harness. Operational implication: a configuration without a recall number is not deployable. Violating this breaks §28's differential-testing gate silently.

P2 — The flat index is the oracle. Rule: every approximate result is scored against exact k-NN from ann-flat, never against another approximation. Tradeoff: the oracle is slow and is never used at serve time, only at evaluation time. Violating this lets recall drift undetected because there is no longer a ground truth to drift from.

P3 — Quantized distance is a biased estimate, and asymmetric computation limits the bias. Rule: the query vector is never quantized before distance computation against quantized database vectors. Tradeoff: asymmetric distance tables cost more to build per query than symmetric lookup. Violating this compounds quantization error from both sides and silently lowers recall (Jégou et al. 2011).

P4 — A deleted vector is never returned once its tombstone commits. Rule: tombstone check happens before a candidate is added to any result set, not after. Tradeoff: every search path pays a tombstone-lookup cost. Violating this returns deleted data to callers, which for personal data is a compliance failure, not just a correctness bug.

P5 — Immutable graph publication, mutable graph construction. Rule: HNSW neighbor lists mutate only under the mutation manager's serialization; a searcher never observes a half-written neighbor list. Tradeoff: inserts are serialized, capping insert throughput. Violating this produces a graph a search can traverse into a dangling or inconsistent neighbor list.

P6 — Codebooks are frozen after training. Rule: a PQ codebook, once a segment uses it for encoding, never changes without a version bump and re-encoding. Tradeoff: adding data after a distribution shift may need a retrain, not an incremental update. Violating this reconstructs vectors from the wrong centroids, corrupting every stored code silently (I5).

P7 — Every distance metric normalizes cosine to inner product, not the reverse. Rule: cosine similarity is computed by normalizing vectors then taking the inner-product kernel — there is exactly one inner-product kernel, reused, not a separate cosine kernel. Tradeoff: normalization is an extra pass at insert time. Violating this duplicates SIMD kernels and risks the two silently disagreeing at the ULP level.

P8 — Parameters have ranges, not defaults treated as universal. Rule: M, ef, nlist, nprobe, and PQ subspace count are documented with the regime in which each value is correct (§9 ADR 6th column), never presented as one true default. Tradeoff: more documentation, more conformance fixtures per regime. Violating this produces silent under- or over-provisioning at a scale nobody tested.

P9 — Build-time cost is bounded and reported, not open-ended. Rule: HNSW efConstruction and IVF's k-means iteration count are finite and logged; there is no "train until convergence" without an iteration cap. Tradeoff: may stop short of the mathematical optimum. Violating this makes build time unpredictable and untestable.

P10 — The on-disk format is versioned before it is optimized. Rule: every persisted structure (graph, codebooks, inverted lists) carries a format version, checked at load. Tradeoff: version-check overhead on every load. Violating this makes a future format change silently corrupt old indexes instead of failing loudly (I6, §27).

P11 — mmap residency is observed, not assumed. Rule: the persistence layer reports page-fault counts and does not assume "mapped" means "in RAM." Tradeoff: instrumentation overhead on the hot path. Violating this hides the exact failure mode (mmap thrash) that causes the worst unexplained latency spikes in production ANN systems.

P12 — Filtered search picks a strategy by selectivity, not by convenience. Rule: pre-filter versus post-filter versus in-graph filtering is chosen from a measured or estimated predicate selectivity (§8 decision table), never hardcoded to one strategy. Tradeoff: requires selectivity estimation machinery. Violating this makes highly selective filters devolve into near-brute-force scans, or non-selective filters waste oversampling budget.

P13 — A rebuild is always available as an escape hatch, and always logged as one. Rule: any correction path that requires a full rebuild (codebook retrain, graph reconstruction after severe tombstone bloat) is explicit, scheduled, and telemetered — never a silent background fallback. Tradeoff: rebuilds are expensive and must be budgeted. Violating this means an operator discovers a rebuild happened only after noticing a CPU spike.

8. Domain Model

Distance Metrics

L2 (Euclidean) distance between vectors a, b ∈ ℝ^d:

d_L2(a, b) = sqrt( Σ_{i=1}^{d} (a_i − b_i)^2 )

Inner product:

d_IP(a, b) = − Σ_{i=1}^{d} a_i · b_i        (negated so smaller = closer, matching L2's convention)

Cosine similarity, and its identity via normalization (P7):

cos(a, b) = (a · b) / (||a|| · ||b||)
d_cos(a, b) = 1 − cos(a, b) = d_IP( a/||a||, b/||b|| ) + 1

Cosine is therefore never a separate kernel: normalize once at insert time, then reuse the inner-product kernel.

The Curse of Dimensionality, Quantitatively

For a uniform distribution in a d-dimensional unit ball, the fraction of volume within distance ε of the surface approaches 1 as d grows, because the ratio of the volume of a ball of radius (1−ε) to a ball of radius 1 is (1−ε)^d, which decays exponentially in d. Concretely, at d=128 and ε=0.05, (0.95)^128 ≈ 0.0014 — over 99.8% of the volume lies in a thin shell near the surface. The practical consequence: as d grows, the ratio between the nearest and farthest point's distance to a query tends toward 1 — everything is approximately equidistant — so exact search degenerates toward a near-linear scan with no useful pruning structure, and approximation (trading a small, bounded recall loss for large speed and memory wins) becomes necessary rather than optional (Indyk & Motwani 1998; Blum, Hopcroft, Kannan ch. 2).

HNSW Construction

Named steps (Malkov & Yashunin 2020):

  1. Layer assignment. On insertion, a random level l is drawn from an exponential distribution with parameter mL = 1 / ln(M): l = floor(−ln(U) × mL), U ~ Uniform(0,1). This produces exponentially fewer nodes at higher layers — the "express lane" structure.
  2. Entry-point descent. Starting from the current global entry point at the top layer, greedily descend layer by layer, at each layer performing a greedy walk toward the query vector using only that layer's edges, until reaching the target insertion layer.
  3. Neighbor search at each layer ≤ l. Run a beam search of width efConstruction at each layer from l down to 0, collecting candidate neighbors.
  4. Neighbor selection heuristic. From the candidate set, select up to M (or M0 at layer 0) neighbors using the heuristic that prefers diversity: a candidate is kept only if it is closer to the inserted point than to every already-selected neighbor, which prevents clustering of neighbor lists and preserves navigability.
  5. Bidirectional edge insertion and pruning. Add edges both directions; if a neighbor now exceeds its degree bound, prune its own list using the same heuristic.

HNSW Search — Worked Greedy-Search Trace

Given query q, entry point ep at top layer Ltop=3:

Layer Current node Action Result
3 ep greedy walk using layer-3 edges only converges to node A (local minimum at layer 3)
2 A greedy walk using layer-2 edges converges to node B
1 B greedy walk using layer-1 edges converges to node C
0 C beam search, width = efSearch returns top-efSearch candidates, truncate to k

Each layer narrows the search region; layer 0 (containing every node) does the fine- grained work, and the upper layers exist only to land the search near the right neighborhood cheaply — the "skip list generalized to a metric space" framing (§32 MM2).

Product Quantization

Subspace splitting: split a ∈ ℝ^d into m subvectors of dimension d/m:

a = (a^1, a^2, ..., a^m),   a^j ∈ ℝ^{d/m}

Per-subspace codebook training: for each subspace j, run k-means with k=2^b centroids (b bits per subquantizer) to produce codebook C^j = {c^j_1, ..., c^j_k}.

Code: the tuple of nearest-centroid indices,

code(a) = ( argmin_i ||a^1 − c^1_i||, ..., argmin_i ||a^m − c^m_i|| )

Reconstruction (lossy):

â = ( c^1_{code_1}, c^2_{code_2}, ..., c^m_{code_m} )

Symmetric distance (both query and database vector quantized — biased, cheaper):

d_sym(q, a) ≈ Σ_{j=1}^{m} ||ĉ^j_{code(q)_j} − c^j_{code(a)_j}||^2

Asymmetric distance computation (ADC, query left unquantized — P3, preferred):

d_asym(q, a) = Σ_{j=1}^{m} ||q^j − c^j_{code(a)_j}||^2

ADC is computed via a precomputed distance table: for each subspace j and each of the k centroids, precompute ||q^j − c^j_i||^2 once per query, then each database vector's distance is m table lookups plus additions — the dominant IVF-PQ inner loop.

Worked example. d=8, m=2 (two subspaces of dim 4), k=4 (2 bits/subquantizer). Query subspace-1 distances to the 4 centroids: [0.10, 0.85, 0.42, 0.90]. Database vector's subspace-1 code = 0 → contributes 0.10. Subspace-2 table: [0.30, 0.05, 0.77, 0.60]; database vector's subspace-2 code = 1 → contributes 0.05. d_asym = 0.10 + 0.05 = 0.15 — two table lookups and one add, no per-vector multiplication.

IVF Coarse Quantizer

nlist centroids trained via k-means over a sample of the corpus; each vector assigned to its nearest centroid's inverted list. At query time, nprobe closest cells (of nlist) are scanned instead of all of them.

nprobe (as fraction of nlist) Recall@10 (illustrative shape) Relative latency
1/nlist (single cell) lowest lowest
nlist/64 moderate low
nlist/8 high moderate
nlist (exhaustive) ≈ flat-equivalent recall ≈ flat-equivalent latency

Scalar Quantization

Per-dimension linear quantization: for dimension i with observed range [min_i, max_i], q_i = round( (a_i − min_i) / (max_i − min_i) × (2^b − 1) ), stored in b bits (typically 8). Reconstruction: â_i = min_i + q_i / (2^b − 1) × (max_i − min_i). Cheaper to train than PQ (no k-means), coarser compression (4× at 8-bit vs. PQ's ~40×+), and does not require subspace structure — useful when PQ's training cost is undesirable or the recall loss from cross-dimension centroid sharing is unacceptable.

Combined IVF-PQ Pipeline

Stage Input Operation Output
1. Coarse routing query q compute distance to all nlist centroids, pick nprobe closest list of cell IDs
2. Distance-table build query q, PQ codebooks precompute per-subspace, per-centroid distances m tables of size k
3. List scan selected cells' PqCodes ADC lookup + sum per code scored candidates
4. Top-k selection scored candidates partial sort / heap top-k approximate result
5. Optional exact rerank top-k candidate IDs recompute true distance from vector store reranked top-k

K-Means Training (Lloyd's Algorithm with k-means++ Seeding)

  1. Seed (Arthur & Vassilvitskii 2007): pick the first centroid uniformly at random; pick each subsequent centroid with probability proportional to its squared distance to the nearest already-chosen centroid.
  2. Assign (Lloyd 1982): assign every point to its nearest centroid.
  3. Update: recompute each centroid as the mean of its assigned points.
  4. Repeat steps 2–3 until assignment changes fall below a threshold or an iteration cap is reached (P9 — bounded, never "until convergence" unconditionally).
  5. Report inertia (sum of squared distances to assigned centroid) as the training quality signal, logged per Phase 5 telemetry.

Filtered-Search Strategy — Decision Table

Strategy When it wins Mechanism Risk
Pre-filter predicate selectivity low (< ~10% of corpus matches) build bitmap of matching IDs first, then restrict search to them if selectivity estimate is wrong, degenerates to near-brute-force
Post-filter with oversampling predicate selectivity high (most vectors match) run normal ANN search for k × oversample_factor, filter after may under-return if filter is stricter than estimated
In-graph filtering filter changes per query and predicate is cheap to evaluate per-node evaluate predicate during graph traversal, skip non-matching neighbors can break navigability if too many nodes are skipped — no clean solution in HNSW, an open problem this blueprint does not claim to solve generally

Insert / Delete Model

Insert: assign layer, run HNSW insertion algorithm (or IVF assignment + PQ encode), append to structures. Delete: mark a tombstone against the VectorId (I3); the vector remains in the graph/list for traversal purposes (removing it would break navigability) but is filtered from every result set. Compaction later rebuilds affected structures without tombstoned data, amortizing the cost.

Degenerate / Malformed Examples

  • Zero vector under cosine: ||a||=0 makes normalization undefined (division by zero) — the kernel must reject or special-case rather than emit NaN silently.
  • Duplicate vectors: two identical vectors at distance 0 — HNSW's neighbor-selection heuristic must still terminate (strict "closer than" comparisons need a tie-break).
  • Query against an empty index: must return an empty result set, not panic or block.
  • Filter matching nothing: pre-filter bitmap is empty — search must short-circuit rather than scan and find nothing after full cost is paid.
  • Dimensionality mismatch: query dimension ≠ index dimension — rejected at the ann-core boundary (I4), never silently truncated or padded.
  • Codebook that failed to converge: k-means hit the iteration cap with high residual inertia — flagged, not silently accepted as a normal codebook (Phase 5 N.9).

Failure-Path Example

A host inserts 10M vectors, then issues a search with efSearch=10 expecting the Phase-4 default recall. Measured recall@10 comes back at 0.60, far under the 0.95 target. Root-cause path: efSearch=10 is far below the tuned default of 100 for this corpus size — the fix is not a bug fix but a parameter correction, surfaced by I8's continuous recall probe rather than by a customer complaint.

  2. Implement Vector, Dim, Metric exactly per §11's signatures; Vector is Arc<[f32]>-backed for zero-copy sharing (P7, I4 validation hook stubbed here).
  3. Implement scalar reference kernels for L2, inner product, cosine-via-normalization (P7) as the correctness baseline every SIMD kernel is differential-tested against (I6).
  4. Implement AVX2 kernels for L2/inner product via core::arch::x86_64 intrinsics (ADR-02, citing the AVX2 reference from §5), AVX-512 behind a runtime feature check with AVX2 fallback, and an ARM NEON backend for parity.
  5. Add runtime CPU-feature detection and a kernel dispatch table selected once at process start and cached (avoids per-call dispatch overhead).
  6. Add memory-alignment wrappers (32-byte aligned allocation, ADR-04's SoA layout).
  7. Add cosine normalization at vector-construction time (P7): reused by the same inner-product kernel, never a separate cosine kernel.
  8. Wire cargo fmt, clippy deny-list, cargo audit, and SBOM generation into CI (ADR-27, §29); add Miri-based UB checking for every unsafe SIMD block.
  9. Add a Criterion benchmark skeleton measuring kernel throughput as the baseline for §30's targets table, plus structured logging bootstrap (tracing, ADR-24) with span-per-kernel-dispatch at debug level only.
  10. Add deterministic build flags (fixed timestamp, locked lockfile) per ADR-28's reproducibility requirement, extended to index construction later.

12.3 Deliverable

A compiling workspace exposing ann-core and ann-simd, with SIMD-accelerated L2, inner-product, and cosine distance kernels, CPU-dispatch selection, and a green CI pipeline enforcing lint, Miri, and audit gates.

12.4 Acceptance Criteria

  • AVX2 kernel throughput ≥ 4× the scalar reference kernel on 128-dimensional vectors (measured via the Criterion benchmark added in step 12).
  • Zero Miri-reported undefined behavior across all unsafe SIMD code paths.
  • CI wall-clock runtime < 15 minutes.
  • Zero clippy warnings under the deny-list configuration.
  • Scalar and SIMD kernels agree to within 1e-5 relative error on 10,000 random 128-dimensional vector pairs (fixture vectors/random-768.bin scaled down, plus a dedicated 128-d fixture).

12.5 Conformance Fixtures

  • vectors/random-128.bin — 10,000 random 128-d f32 vector pairs, purpose: SIMD-vs- scalar differential agreement, expected: ≤1e-5 relative error per pair.
  • vectors/aligned.bin — 32-byte aligned vectors, purpose: alignment-fastpath coverage.
  • vectors/misaligned.bin — deliberately misaligned vectors, purpose: verify the fallback path is taken and still correct, not that it is fast.
  • vectors/degenerate.bin — zero vectors, NaN, and Inf entries, purpose: exercise the degenerate-input handling required by §8's cosine-zero-vector case.

12.6 Pitfalls

  1. False sharing in batch kernels — writing per-lane partial sums into adjacent cache lines from different threads corrupts throughput measurements; manifests as inconsistent benchmark numbers across runs; detect via perf cache-miss counters; recover by padding per-thread accumulators to cache-line width.
  2. Alignment drift — a Vec<f32> reallocation silently loses 32-byte alignment; manifests as a silent fallback to the slow path with no error; detect via alignment assertions in debug builds; recover by using the aligned allocator wrapper everywhere, never a bare Vec::new() for vector storage.
  3. CPU-dispatch misdetection — cpuid-based feature detection reports AVX-512 support incorrectly in a virtualized environment; manifests as an illegal-instruction crash; detect via a startup self-test that executes one AVX-512 instruction and catches the trap; recover by falling back to AVX2 for the process lifetime.
  4. Denormal floating-point slowdown — near-zero difference vectors (e.g., nearly duplicate points) produce denormals that run 10–100× slower on some microarchitectures; manifests as unexplained p99 latency spikes; detect via denormal-count perf counters; recover by enabling flush-to-zero/denormals-are-zero mode at kernel entry.
  5. Cosine-via-normalization drift — normalizing at insert time versus at query time independently can accumulate different rounding; manifests as tiny but nonzero asymmetry in d(a,b) vs d(b,a); detect via a symmetry property test; recover by normalizing exactly once, at insert, and storing the normalized vector.

12.7 Performance Concerns

Branch prediction in the dispatch table (mispredicts are cheap if the dispatch happens once per process, expensive if per-call); prefetch distance tuning for batch kernels scanning large vector arrays; SIMD lane utilization (128-d vectors do not divide evenly into every lane width, requiring tail-handling code that must not become the common case); LLC (last-level cache) misses dominate once the vector store exceeds cache size, making memory bandwidth, not compute, the eventual ceiling (§30, §34).

12.8 Edge Cases

NaN in an input vector must produce a rejected insert (caught by validation, not propagated as a NaN distance); infinite values must be similarly rejected; a zero vector under L2/inner-product is well-defined (distance to origin) but under cosine is undefined (§8) and must return a typed error, not a silent NaN; a single-dimension (d=1) vector must still dispatch correctly, exercising the SIMD tail path exclusively.

12.9 Failure Analysis

An incorrect SIMD kernel is the single most dangerous defect class in this entire project: it manifests as silent ranking corruption — search still returns k results, still returns plausible-looking distances, but the ordering is subtly wrong, and no downstream consumer notices without a dedicated differential test against the scalar reference (I6). Debug method: run the differential fixture in 12.5 first, not a live recall benchmark, because a recall drop from a kernel bug looks identical to a recall drop from a parameter choice until isolated.

12.10 Operational Notes

Expose a kernel_dispatch_selected metric at process startup (which SIMD variant was chosen) so operators can confirm a fleet is not silently running the scalar fallback after a CPU-generation change. Startup logs must record the exact CPU features detected.

13. Phase 1 — The Flat Index as the Exact Recall Oracle

13.1 Objectives

Implement ann-flat: a brute-force exact k-NN index over the vector store, serving as the permanent recall oracle (I1, P2) that every approximate index in later phases is scored against.

13.2 Detailed Implementation Steps

  1. Implement FlatIndex per §11's signature: RwLock<Vec<(VectorId, Vector)>>.
  2. Implement insert: append under write lock; no reordering, no deduplication beyond what ann-core validation already rejects (I4).
  3. Implement exact k-NN search: compute distance from the query to every stored vector using the ann-simd batch kernel, then partial-sort (top-k selection, not full sort) to return the k closest.
  4. Implement tombstone-awareness (I3) even in the oracle: a deleted vector must never appear in flat results either, or it would no longer be a valid oracle for a mutated corpus (P4 applies uniformly).
  5. Add batch-query support reusing ann-simd::batch_distance for cache-friendly scanning.
  6. Add a full-scan cost model hook feeding §34's brute-force query-cost derivation.
  7. Add deterministic tie-breaking (by VectorId) when two vectors are exactly equidistant, required for I12's no-duplicate, deterministic-result-set guarantee.
  8. Add a "ground truth generation" mode: given a query set, emit the exact top-k neighbor IDs for every query, consumed by Phase 2's evaluation harness and every later phase's conformance fixtures.

13.3 Deliverable

A working exact k-NN index (ann-flat) capable of generating ground-truth neighbor sets for arbitrary query batches, usable both as a small-corpus production index and as the oracle for every approximate index.

13.4 Acceptance Criteria

  • Exact k-NN correctness verified by construction (full scan + partial sort — no approximation is possible to get wrong beyond an off-by-one or tie-break bug), confirmed via property test against an independent sort-based reference on 1,000 random queries against SIFT1M.
  • Full-scan p50 latency ≤ 4 ms on SIFT1M (1M × 128-d, AVX2, single core) — matches §4.
  • Ground-truth generation for a 10,000-query batch against SIFT1M completes in the CI time budget (< 5 minutes at the throughput derived in §34).

13.5 Conformance Fixtures

  • ground_truth/sift1m_top100.bin — exact top-100 neighbors for 10,000 SIFT1M queries, purpose: the canonical ground truth consumed by every later recall computation.
  • conformance/degenerate/empty_index_query.json — query against a zero-vector index, expected: empty SearchResult, no panic.
  • conformance/degenerate/tie_break.bin — vectors with exact duplicate distances, expected: deterministic ordering by VectorId.

13.6 Pitfalls

  1. Partial-sort bugs masquerading as approximation error — an off-by-one in top-k selection returns k−1 or k+1 results; manifests as a recall score that looks like a real approximation defect in later phases when it is actually an oracle bug; detect by asserting SearchResult.len() == k (I12) in the oracle's own test suite first.
  2. Tombstone check omitted in the "fast" oracle path — a developer bypasses the tombstone filter for oracle speed, silently making the oracle wrong for mutated corpora; manifests as recall appearing to regress after deletes when it is the oracle that drifted; detect via a dedicated post-delete oracle fixture.
  3. Non-deterministic tie-break — using unstable sort without an explicit secondary key produces different "ground truth" on different runs; manifests as flaky conformance tests; detect via repeated-run diffing in CI.
  4. Full-scan memory bandwidth saturation under concurrent queries — many concurrent oracle queries all scanning the same 512MB array evict each other's cache lines; manifests as latency degrading non-linearly with concurrency; detect via per-query latency under load testing.

13.7 Performance Concerns

Full scan is memory-bandwidth bound, not compute bound, once the vector store exceeds LLC size (§30, §34's derivation); sequential access pattern should saturate prefetchers; top-k selection should use a bounded heap (O(N log k)) rather than a full O(N log N) sort.

13.8 Edge Cases

k larger than the corpus size (must return all available vectors, not error or pad); k=0 (must return an empty result, not error); a query identical to a stored vector (distance 0, must appear as its own nearest neighbor unless tombstoned).

13.9 Failure Analysis

If the oracle itself is wrong, every downstream recall number in this entire project is meaningless — this is the single highest-blast-radius correctness defect possible. Debug method: the oracle has no approximation to blame, so any incorrect result here is either a distance-kernel bug (return to Phase 0's fixtures) or a selection/tie-break bug local to this phase; there is no third possibility.

13.10 Operational Notes

Any production deployment relying on the flat index directly (small corpora) must monitor full-scan latency growth as the corpus grows linearly — there is no configuration knob that changes this index's asymptotic behavior (§31).

14. Phase 2 — The Recall/Latency Evaluation Harness

14.1 Objectives

Implement ann-eval: an ANN-Benchmarks-compatible (Aumüller, Bernhardsson, Faithfull 2020) harness computing recall@k against the Phase-1 oracle, plus latency percentiles and memory accounting, for any index under test.

14.2 Detailed Implementation Steps

  1. Implement RecallReport per §11: dataset name, k, recall@k, p50/p95/p99 latency, memory bytes.
  2. Implement recall@k computation: for each query, compare the approximate index's top-k result set against the oracle's top-k ground truth (from Phase 1), recall@k = |intersection| / k, averaged across the query set (P1, P2).
  3. Implement latency measurement with warmup exclusion and coordinated-omission-aware sampling (fixed-rate issuance, not closed-loop, per §30's tail-latency methodology).
  4. Implement memory accounting: resident-set measurement for heap-resident indexes, mapped-but-not-necessarily-resident distinction for mmap indexes (P11).
  5. Implement dataset loaders for SIFT1M and GloVe in the ANN-Benchmarks format (§5 reading item 10), plus a Deep1B-subset loader for the §31/§34 billion-scale discussion.
  6. Implement the recall-vs-parameter sweep (recall/ef curve, recall/nprobe curve) that Phase 4's and Phase 7's acceptance criteria will consume.
  7. Implement a continuous "recall probe" mode: periodically re-run a fixed query sample against a live index and compare to a cached oracle answer, feeding I8's telemetry.
  8. Wire the harness into CI as a named gate (§28) comparing against previously recorded FAISS/hnswlib numbers on the same dataset as a regression baseline.
  9. Add report serialization (JSON) for the benchmark artifacts under benchmarks/.

14.3 Deliverable

A standalone ann-eval binary and library producing dataset-scoped RecallReport artifacts for any index implementing the search interface, plus a continuous recall- probe mode for production telemetry (I8).

14.4 Acceptance Criteria

  • Harness reproduces the Phase-1 oracle's own recall@k = 1.0 when evaluating the flat index against itself (a sanity fixture that must always pass).
  • Harness computes recall@10 for a fixed HNSW stub configuration on SIFT1M within ±0.005 of a hand-computed reference on a 1,000-query subsample.
  • p50/p95/p99 computed from ≥ 10,000 sampled queries, not fewer (statistical floor for percentile stability).
  • Recall-probe mode completes one probe cycle in < 1 second against a 1M-vector index.

14.5 Conformance Fixtures

  • recall_curves/flat_self_check.json — flat vs. flat, purpose: recall@k must equal 1.0 exactly, expected output: recall_at_k: 1.0 for every k.
  • recall_curves/sift1m_ef_sweep.json — recall@10 at efSearch ∈ {10, 50, 100, 200, 500}, purpose: monotonicity fixture consumed by Phase 4 and §28's property test.
  • degenerate/empty_query_set.json — zero queries supplied, expected: harness returns a typed error, not a divide-by-zero on the recall average.

14.6 Pitfalls

  1. Closed-loop latency measurement (coordinated omission) — issuing the next query only after the previous one returns understates tail latency under load; manifests as p99 numbers that look better than production reality; detect by comparing fixed-rate vs. closed-loop measurement on the same index; recover by defaulting to fixed-rate issuance.
  2. Recall computed against a stale oracle — ground truth generated before a corpus mutation no longer matches; manifests as recall appearing to drop after every insert batch; detect via ground-truth regeneration timestamp checks.
  3. Memory accounting conflating mapped and resident — reporting mmap'd file size as "memory used" overstates cost, reporting only RSS understates true footprint if pages are evicted; manifests as misleading memory comparisons across index types; detect by reporting both figures explicitly (P11).
  4. Percentile instability from too few samples — computing p99 from 100 queries gives a noisy, unstable number; manifests as benchmark flakiness across CI runs; detect via a minimum-sample-count assertion (10,000 floor per 14.4).

14.7 Performance Concerns

The harness itself must not become the bottleneck it is measuring — query issuance and ground-truth comparison must run on separate threads from the index under test to avoid skewing latency measurements with harness overhead.

14.8 Edge Cases

A dataset with fewer vectors than k requested; a query set with duplicate queries (recall must still average correctly, not double-count); an index that returns fewer than k results (must be handled in recall computation as a partial match, not an error).

14.9 Failure Analysis

A broken evaluation harness is nearly as dangerous as a broken oracle (Phase 1's 13.9): if recall is miscomputed, every acceptance criterion in every later phase is unverifiable. Debug method: always run the flat-vs-flat self-check fixture (14.5) first — if recall@k ≠ 1.0 there, the defect is in the harness, not in any approximate index.

14.10 Operational Notes

The continuous recall-probe mode (I8) is the single most important production signal this project defines (§26) — it must be wired into alerting before any index ships to a host that cannot tolerate silent recall drift.

15. Phase 3 — HNSW Graph Construction

15.1 Objectives

Implement ann-hnsw's construction path: layer assignment, entry-point descent, neighbor search per layer, the neighbor-selection heuristic, and bidirectional edge insertion with pruning, per Malkov & Yashunin 2020 and the precursor NSW paper (Malkov et al. 2014).

15.2 Detailed Implementation Steps

  1. Implement the layer-assignment probability (§8): l = floor(-ln(U) × mL), mL = 1/ln(M), citing Malkov & Yashunin 2020 (P8 — M is a documented range, not a fixed universal default). Implement HnswNode, NeighborList, EntryPoint per §11.
  2. Implement entry-point greedy descent from the top layer down to the target insertion layer (§8's worked trace, step 2), then the per-layer beam search (efConstruction-wide) collecting candidates at each layer down to 0.
  3. Implement the neighbor-selection heuristic (§8 step 4): prefer diversity, keep a candidate only if closer to the new point than to any already-selected neighbor — cite ADR-07's rejection of naive top-M.
  4. Implement bidirectional edge insertion respecting the per-layer degree bound M (M0 at layer 0, enforcing I9), and neighbor-list pruning when a neighbor's degree bound is exceeded, reusing the same selection heuristic.
  5. Implement entry-point update: if the newly inserted node's layer exceeds the current global entry point's layer, it becomes the new entry point (I2, atomically swapped).
  6. Implement single-writer serialization for graph mutation (P5, ADR-17): inserts pass through ann-mutate's op-log ordering (I13), while per-node RwLocks allow concurrent lock-free-for-readers traversal of unrelated nodes.
  7. Implement connectivity-sweep tooling verifying every node is reachable from the entry point at layer 0 (I2), used both in tests and as a background health check (§26).
  8. Implement graph serialization stubs (full persistence lands in Phase 10) and construction telemetry: neighbor-list saturation rate, average degree, per-layer node counts.

15.3 Deliverable

A buildable HNSW graph (ann-hnsw) over an arbitrary vector corpus, with verified navigability (I2) and bounded degree (I9), not yet wired to query-time search (Phase 4).

15.4 Acceptance Criteria

  • Graph connectivity sweep reports < 0.01% isolated nodes on SIFT1M at M=16, efConstruction=200.
  • Build throughput ≥ 5,000 vectors/second/core on SIFT1M (matches §4).
  • Average node degree at layer 0 within [M0 × 0.8, M0] (bounded, not collapsing toward a much sparser graph than configured).
  • Layer-count distribution matches the expected geometric decay within statistical tolerance (property test against the theoretical mL distribution).

15.5 Conformance Fixtures

  • hnsw/small_graph.bin — 10,000-vector build, purpose: fast CI-cycle correctness check, expected: connectivity sweep passes, degree bounds respected.
  • hnsw/disconnected_stress.bin — an adversarially clustered input designed to stress navigability, purpose: verify the diversity heuristic (ADR-07) prevents isolation, expected: < 0.01% isolated nodes even under clustering.
  • hnsw/high_degree_reject.bin — a fixture asserting neighbor lists never exceed M/M0, purpose: I9 enforcement check.
  • degenerate/duplicate_vectors.bin — many exactly-identical vectors, purpose: verify the selection heuristic terminates and does not infinite-loop on zero-distance ties.

15.6 Pitfalls

  1. Neighbor-list clustering from naive top-M selection — using nearest-M instead of the diversity heuristic causes neighbor lists to cluster around dense regions, collapsing navigability; manifests as high isolated-node counts or severe recall degradation at query time despite a "successful" build; detect via the connectivity sweep in 15.4; recover by confirming the heuristic implementation matches ADR-07.
  2. Entry-point race during concurrent insertion — two inserts both claiming a new max layer without atomic compare-and-swap corrupts the entry point; manifests as an unreachable subgraph; detect via I2's connectivity sweep; recover by serializing entry-point updates through the single-writer path (P5).
  3. Degree-bound violation from unpruned bidirectional edges — adding an edge without re-checking and pruning the neighbor's list lets degree grow unbounded; manifests as memory usage exceeding the §4 derivation; detect via I9's per-node degree assertion.
  4. Layer-assignment RNG non-determinism breaking reproducible builds — using a non-seeded RNG for layer assignment makes two builds from the same corpus produce different graphs; manifests as non-reproducible conformance fixtures; detect via ADR-28's fixed-seed replay requirement; recover by threading a deterministic seed through every layer-assignment call.
  5. Duplicate-vector infinite loop in the selection heuristic — a strict "closer than every selected neighbor" check with no tie-break can infinite-loop on exact duplicates; manifests as a build hang; detect via the degenerate duplicate-vectors fixture (15.5); recover by adding a deterministic tie-break identical to I12's.
  6. Insertion-order sensitivity — build quality depends on insertion order for adversarial inputs; manifests as different recall for the same corpus inserted in different orders; detect via an order-permutation stress fixture; document as an accepted, bounded limitation, not a bug (Malkov & Yashunin 2020 discuss this directly).

15.7 Performance Concerns

Random memory access dominates: neighbor-list traversal during beam search jumps across the heap unpredictably, defeating prefetchers — this is the primary reason HNSW build throughput is far below IVF-PQ's assignment throughput (§4, §34); lock contention on hot neighbor nodes (high-degree "hub" nodes) under concurrent insertion; allocation churn from per-insertion candidate heaps.

15.8 Edge Cases

Inserting into an empty graph (no entry point yet — first insert becomes the entry point trivially); inserting a vector identical to an existing one (§8's duplicate-vector case); efConstruction smaller than M (degenerate beam width, must still terminate correctly, just with worse quality); a single-node graph queried before any second insert.

15.9 Failure Analysis

Graph corruption (a violated I2 or I9) manifests at query time as either severe recall collapse (isolated regions never reached) or unbounded memory growth (unpruned degree), and both symptoms look identical to a tuning problem until the connectivity sweep is run — this is why 15.4's acceptance criteria mandate the sweep as a build-time gate, not an optional diagnostic.

15.10 Operational Notes

Expose hnsw_isolated_nodes_total and average-degree metrics continuously, not just at build time — tombstone accumulation in later phases can degrade effective connectivity even after a healthy initial build (§26 runbook: recall-regression triage).

16. Phase 4 — HNSW Greedy Search With ef Tuning

16.1 Objectives

Implement ann-hnsw's query-time search path: entry-point descent through upper layers, layer-0 beam search bounded by efSearch, and the recall/latency tradeoff that parameter induces, wired to Phase 2's evaluation harness.

16.2 Detailed Implementation Steps

  1. Implement query-time entry-point descent identical in structure to construction's descent (§8 worked trace, steps 1–3), reusing the same greedy-walk primitive.
  2. Implement the layer-0 beam search with a bounded candidate heap of width EfSearch (§11), returning the top-efSearch candidates before truncation to k.
  3. Implement visited-set tracking to avoid re-expanding nodes within one query (a per-query bitmap or hash set, not a persistent structure — I2 concerns construction connectivity, not query-time state).
  4. Implement early-termination: stop expanding once the candidate heap's worst member is closer than the closest unvisited candidate in the frontier (standard HNSW termination condition).
  5. Wire SearchParams.ef_search (§11) through to this beam width, defaulting per §4's range when unset.
  6. Run the recall/ef sweep from Phase 2 against this implementation to produce the recall_curves/sift1m_ef_sweep.json fixture referenced in 14.5.
  7. Add tombstone filtering (P4, I3) at candidate-collection time, before a candidate enters the result heap, not after.
  8. Add optional exact-rerank hook (§8 IVF-PQ pipeline step 5's counterpart) allowing a host to request true-distance recomputation on the top-k before returning.
  9. Add per-query tracing spans (efSearch used, nodes visited, distance computations performed) for §26's operational surface.

16.3 Deliverable

An end-to-end searchable HNSW index: ann-hnsw build (Phase 3) plus query (this phase), reporting recall@10, p50/p95/p99 latency, and memory via ann-eval.

16.4 Acceptance Criteria

  • Recall@10 ≥ 0.95 at efSearch=100 on SIFT1M (M=16, matches §4).
  • p50 ≤ 0.4 ms, p95 ≤ 0.9 ms, p99 ≤ 2.0 ms at that same configuration (§4).
  • QPS/core ≥ 2,500 at recall@10=0.95 (§4).
  • Recall increases monotonically with efSearch across {10, 50, 100, 200, 500} on the sweep fixture (property test tied to §28).
  • Recall@10 ≥ 0.90 on GloVe (cosine metric) at an equivalent efSearch, confirming the cosine-via-normalization path (P7) carries through search correctly.

16.5 Conformance Fixtures

  • recall_curves/sift1m_ef_sweep.json (from Phase 2, now populated) — expected: strictly non-decreasing recall@10 as efSearch increases.
  • hnsw/tombstone_filter.bin — a graph with pre-marked tombstones, purpose: verify deleted vectors never surface in results (I3), expected: zero tombstoned IDs in any result set across 1,000 queries.
  • degenerate/query_dimension_mismatch.json — query vector of wrong dimensionality, expected: AnnError::DimensionMismatch, no partial search performed.
  • degenerate/empty_graph_query.json — search against a freshly constructed empty graph, expected: empty SearchResult, no panic.

16.6 Pitfalls

  1. efSearch defaulting too low for the corpus size — a value tuned for a small corpus silently underperforms at scale; manifests as the exact failure-path example in §8 (recall@10 = 0.60 against an 0.95 target); detect via the continuous recall probe (I8); recover via Phase 11's tuning procedure.
  2. Visited-set reuse across queries — a pooled visited-set bitmap not fully cleared between queries causes false "already visited" skips; manifests as intermittently wrong (too-small) result sets; detect via a fixed-seed repeated-query determinism test.
  3. Tombstone check placed after result-heap insertion instead of before — violates P4/I3 even though the final truncation might appear to hide it in small tests; manifests as tombstoned vectors appearing when k is large enough to expose the gap; detect via the dedicated tombstone-filter fixture.
  4. Early termination too aggressive — cutting off beam expansion before the true frontier is exhausted trades unnecessary recall for marginal latency gain; manifests as a recall ceiling that does not improve even as efSearch increases; detect via the monotonicity property test.
  5. Cosine search silently reusing an un-normalized query vector — if the host passes a raw (non-normalized) query vector and the search path forgets to normalize it before the inner-product kernel, cosine results are subtly wrong; manifests as lower recall specifically on the GloVe/cosine fixture, not on SIFT1M/L2; detect via the per-metric acceptance criterion in 16.4.

16.7 Performance Concerns

Random memory access remains dominant at query time exactly as at build time (15.7); candidate-heap operations (insert, extract-min) are the second-order cost once distance computation is amortized by SIMD; visited-set implementation (bitmap vs. hash set) matters at scale — a hash set's allocation overhead can dominate for small efSearch.

16.8 Edge Cases

efSearch < k (must still return as many results as available, not error); a query landing exactly on a stored vector during descent (distance-0 tie handling, I12); concurrent search during an in-progress insert elsewhere in the graph (P5's per-node locking must not block unrelated readers).

16.9 Failure Analysis

A recall regression that appears only at query time (build-time connectivity sweep passed) points at either a parameter misconfiguration (16.6.1) or a query-path logic bug (tombstone ordering, visited-set reuse) — the debug method is to first re-run the sweep at a known-good efSearch to isolate parameter choice from implementation defect.

16.10 Operational Notes

efSearch in effect must be logged per query class (§26) — a fleet silently running a lower efSearch than intended after a config rollback is indistinguishable from a code regression without this telemetry.

17. Phase 5 — K-Means and Codebook Training

17.1 Objectives

Implement ann-quantize's KMeans trainer (Lloyd's algorithm with k-means++ seeding, Lloyd 1982, Arthur & Vassilvitskii 2007), the shared foundation both PQ codebook training (Phase 6) and IVF coarse-quantizer training (Phase 7) depend on.

17.2 Detailed Implementation Steps

  1. Implement k-means++ seeding (§8 step 1): first centroid uniform-random, subsequent centroids weighted by squared distance to the nearest already-chosen centroid.
  2. Implement the assignment step (§8 step 2, Lloyd 1982): nearest-centroid assignment for every point, using the ann-simd batch distance kernel.
  3. Implement the update step (§8 step 3): recompute each centroid as the mean of its assigned points.
  4. Implement the iteration loop with a bounded max_iters (P9) and a convergence threshold (fraction of points changing assignment below a configured epsilon).
  5. Implement inertia (sum of squared distances to assigned centroid) reporting as the training-quality telemetry signal.
  6. Implement deterministic seeding (ADR-28): a fixed RNG seed produces a bit-identical codebook across repeated runs on the same input.
  7. Implement empty-cluster handling: a centroid that ends an iteration with zero assigned points is re-seeded from the highest-inertia existing cluster's farthest point, rather than left degenerate.
  8. Implement a training-sample-size policy: k-means trains on a representative sample of the corpus (not necessarily the full corpus) when the corpus is large, per FAISS's documented convention (§5 reference implementations).
  9. Add training telemetry: iteration count at termination, final inertia, empty-cluster re-seed count.

17.3 Deliverable

A reusable KMeans trainer producing a Vec<Centroid> from an input vector set, deterministic given a seed, with bounded iteration count and convergence reporting.

17.4 Acceptance Criteria

  • Given a fixed seed, two independent training runs on the same 100,000-vector sample produce bit-identical centroids (ADR-28 reproducibility gate).
  • Training on a synthetic 8-cluster Gaussian-mixture fixture recovers centroids within a stated distance tolerance of the true cluster means in ≤ 25 iterations.
  • Empty-cluster re-seeding fixture: a deliberately skewed input never leaves a centroid with zero assigned points after termination.
  • k-means++ seeding measurably reduces final inertia versus random seeding on the same input (comparative fixture, ≥ 10% inertia reduction on the SIFT1M sample).

17.5 Conformance Fixtures

  • training/gaussian_mixture_8.bin — synthetic 8-cluster data with known ground-truth centroids, purpose: convergence correctness, expected: recovered centroids within tolerance.
  • training/skewed_clusters.bin — one dominant cluster and several sparse ones, purpose: empty-cluster re-seed path, expected: zero degenerate centroids at termination.
  • training/seed_determinism.json — same input, same seed, two runs, purpose: ADR-28 gate, expected: byte-identical centroid output.
  • degenerate/single_point_cluster.bin — fewer input points than requested k, purpose: verify a typed error (KMeansFailedToConverge-adjacent) rather than a panic.

17.6 Pitfalls

  1. Poor seeding causing bad local minima — random seeding (ADR-10's rejected alternative) occasionally collapses several centroids into one dense region; manifests as high final inertia and, downstream, poor PQ reconstruction or IVF cell imbalance; detect via the inertia-comparison fixture (17.5); recover via k-means++ (already the locked choice, verified by regression).
  2. Non-deterministic assignment iteration order — parallelizing the assignment step without a stable reduction order breaks bit-identical reproducibility; manifests as the seed-determinism fixture failing intermittently; detect via repeated CI runs; recover by using a deterministic reduction (e.g., sorted-by-index accumulation).
  3. Empty clusters silently left degenerate — without explicit handling, an empty centroid remains at its last (or initial) position forever, wasting a codebook slot; manifests as unexplained reconstruction-error plateaus in Phase 6; detect via the skewed-clusters fixture.
  4. Unbounded iteration on pathological input — without a hard max_iters cap (P9), oscillating assignments (rare but possible) can loop indefinitely; manifests as a training job that never returns; detect via a timeout in CI; recover by enforcing the bounded loop always, reporting KMeansFailedToConverge if the epsilon threshold is never met.
  5. Training on the full corpus when a sample would do — training k-means over 100M vectors instead of a representative sample multiplies training cost with no proportional quality gain; manifests as build-time budget overruns; detect via training-time telemetry versus the sample-size policy in step 8.

17.7 Performance Concerns

Assignment is the dominant cost (O(N × k × d) per iteration) and is embarrassingly parallel across points; update is a cheap reduction; memory bandwidth for reading the training sample repeatedly across iterations is the practical ceiling, motivating the sample-size policy (17.2 step 8) over training on the entire corpus.

17.8 Edge Cases

k larger than the number of training points (must error, not silently produce fewer centroids); all training points identical (every centroid should converge to that point without infinite empty-cluster re-seeding); max_iters = 1 (must still produce a valid, if poor, result rather than erroring).

17.9 Failure Analysis

A degraded codebook from bad k-means convergence does not fail loudly — it silently raises PQ reconstruction error (Phase 6) and IVF cell imbalance (Phase 7), both of which look like tuning problems in those later phases unless the training-quality telemetry (inertia, empty-cluster count) from this phase is checked first.

17.10 Operational Notes

Codebook (re)training is a scheduled, budgeted operation (P13), never a silent background fallback — expose training duration, final inertia, and iteration count as build-time metrics consumed by the runbook governing retraining decisions (§26).

18. Phase 6 — Product Quantization With Asymmetric Distance

18.1 Objectives

Implement ann-quantize's PQ path: subspace splitting, per-subspace codebook training (reusing Phase 5's KMeans), encoding, reconstruction, and both symmetric and asymmetric distance computation with precomputed distance tables (Jégou, Douze, Schmid 2011).

18.2 Detailed Implementation Steps

  1. Implement Subspace partitioning of Dim into m equal-width subspaces per ADR-08's default (d/16 subspaces), then per-subspace codebook training via Phase 5's KMeans independently on each subspace's projected data, producing m codebooks of k=2^b centroids each (ADR-09's 8-bit default).
  2. Implement the encoder (nearest centroid per subspace, emitted as one byte of the PqCode, §8's code-tuple definition) and reconstruction (centroid lookup + concat, §8's equation) — reconstruction backs optional exact-rerank and error measurement.
  3. Implement symmetric distance (both sides quantized, §8's equation) for stored-code- to-stored-code comparison.
  4. Implement asymmetric distance computation (ADC, P3, ADR-12): given an unquantized query, precompute a per-subspace, per-centroid distance table, then compute each candidate's distance as m table lookups plus additions (§8's worked example).
  5. Document OPQ (Ge, He, Ke, Sun 2013) as the mitigation for subspace-variance imbalance without building it in Phase 0 (ADR-11's scope note).
  6. Implement reconstruction-error telemetry (MSE between original and reconstructed vectors, tracked per codebook version) and codebook versioning (I5, I11, P6): a ProductQuantizer carries a version; encoding against a stale codebook is rejected.

18.3 Deliverable

A working PQ codec (ann-quantize): trainable codebooks, an encoder, symmetric and asymmetric distance computation, and reconstruction-error telemetry, ready to be combined with IVF routing in Phase 8.

18.4 Acceptance Criteria

  • Reconstruction error (mean squared error) decreases monotonically as bits-per-code increases across {4, 8, 16} bits on a fixed SIFT1M sample (property test tied to §28).
  • Asymmetric distance is a measurably better estimator of true distance than symmetric distance on a fixed codebook: mean absolute error of d_asym versus d_L2 ground truth is strictly lower than that of d_sym on the same 10,000-query sample (§28 property).
  • Compression ratio ≈ 42× versus flat storage at m=8, 8-bit codes, d=128 (matches §4, §34 derivation).
  • Codebook-version mismatch at load is rejected with AnnError::CodebookVersionMismatch, never silently decoded (I5).

18.5 Conformance Fixtures

  • pq/codebooks_m8_b8.bin — trained 8-subspace, 8-bit codebook on SIFT1M, purpose: the standard fixture for downstream IVF-PQ (Phase 8) tests.
  • pq/reconstruction_error_sweep.json — MSE at 4/8/16 bits, purpose: 18.4's monotonicity gate.
  • pq/asymmetric_vs_symmetric.json — paired distance estimates against ground truth, purpose: 18.4's ADC-superiority gate.
  • pq/invalid_codebook_version.bin — a code encoded under version N loaded against a version N+1 codebook, purpose: I5 rejection path, expected: CodebookVersionMismatch.
  • degenerate/undertrained_codebook.bin — a codebook whose k-means training hit max_iters without converging (Phase 5 §17.9), purpose: verify this is surfaced as a flagged, not silently accepted, codebook (§8's degenerate example).

18.6 Pitfalls

  1. Quantizing the query (violating P3/ADR-12) — computing symmetric distance at query time because it is simpler to implement; manifests as measurably worse recall than ADC at identical bit budget; detect via the asymmetric-vs-symmetric fixture.
  2. Subspace-variance imbalance — naive equal-width subspace splitting on a corpus whose variance is concentrated in a subset of dimensions produces some subspaces with far higher reconstruction error than others; manifests as reconstruction error that does not improve proportionally with more bits; detect via per-subspace MSE breakdown; mitigation documented (OPQ, Ge et al. 2013) but not built in Phase 0 (ADR-11 scope note) — recover by flagging high-imbalance corpora for a future OPQ phase rather than silently under-delivering.
  3. Distance-table recomputation per candidate instead of per query — rebuilding the m × k table for every candidate instead of once per query defeats the entire point of ADC's precomputation; manifests as IVF-PQ throughput far below the §4 target; detect via per-query profiling showing table-build cost scaling with candidate count.
  4. Codebook drift after a distribution shift left undetected — inserting vectors from a meaningfully different distribution than the training sample without retraining; manifests as slowly rising reconstruction error and falling recall over time; detect via the continuous MSE telemetry from step 8; recover via the scheduled retrain path (P13).
  5. Byte-alignment mismatch in PqCode storage — packing codes at non-byte boundaries to save a few bits breaks SIMD-friendly batch decode; manifests as decode throughput far below expectation; detect via the throughput target in §4; recover by keeping ADR-09's byte-per-subquantizer convention.

18.7 Performance Concerns

Distance-table construction is O(m × k × d/m) once per query — cheap relative to the scan that follows; the list/candidate scan itself is the dominant cost and is dominated by table-lookup memory access pattern (small table, likely L1-resident, so this is compute-bound on additions rather than bandwidth-bound, unlike flat scan); reconstruction (used only for optional rerank) is comparatively rare and not on the hot path.

18.8 Edge Cases

d not evenly divisible by m (must be rejected at configuration time, not silently truncate a subspace); a subspace with fewer training points than k centroids requested (inherits Phase 5's edge case 17.8); reconstructing a PqCode whose codebook version no longer exists (must error, not reconstruct from a wrong codebook).

18.9 Failure Analysis

PQ reconstruction error and recall degrade gracefully and continuously as codebooks drift — there is no hard failure threshold that fires automatically; this makes the continuous MSE and recall-probe telemetry (I8, step 8) the only reliable early-warning signal, and 18.6's pitfalls are all silent-degradation modes rather than crashes.

18.10 Operational Notes

Expose reconstruction-error-by-codebook-version as a standing dashboard metric (§26); an operator retraining a codebook must be able to compare old-versus-new MSE before cutting a segment over to the new version (P6, P13).

19. Phase 7 — The IVF Coarse Quantizer and Inverted Lists

19.1 Objectives

Implement ann-ivf: the coarse quantizer (k-means over nlist cells, reusing Phase 5's trainer) and the inverted-list structure that routes queries to nprobe cells at search time.

19.2 Detailed Implementation Steps

  1. Implement CoarseQuantizer training via Phase 5's KMeans with k = nlist, sized per §4's heuristic (nlist between √N and 4√N).
  2. Implement per-vector cell assignment: nearest coarse centroid, enforcing I10 (a vector's stored list membership must match its true nearest-centroid assignment at encode time).
  3. Implement InvertedList as a per-cell, lock-guarded, append-mostly Vec<(VectorId, PqCode)> (ADR-17: independent per-cell locks avoid cross-cell write contention).
  4. Implement the coarse-routing step (§8 combined-pipeline step 1): compute distance from the query to all nlist centroids, select the nprobe closest.
  5. Implement per-cell scan using Phase 6's asymmetric distance table (only cells among the selected nprobe are scanned — cells outside are never touched, bounding cost to nprobe × average_list_length).
  6. Implement cell-size imbalance telemetry: track list-length distribution to detect skewed coarse quantizers (a symptom of poor k-means convergence, Phase 5's 17.6).
  7. Implement the nprobe-vs-recall sweep, extending Phase 2's harness with an IVF- specific parameter dimension.
  8. Add tombstone filtering identical in placement (before result-heap insertion) to Phase 4's HNSW implementation, reusing the shared tombstone-check primitive from ann-mutate.
  9. Add rebalancing tooling: detect severely imbalanced cells and flag for coarse- quantizer retraining (P13), without silently rebalancing automatically.

19.3 Deliverable

A working IVF routing layer (ann-ivf) over PQ-encoded vectors: coarse quantizer, inverted lists, nprobe-bounded scanning, ready for the combined pipeline in Phase 8.

19.4 Acceptance Criteria

  • Cell-size distribution on SIFT1M with nlist=1024 has a coefficient of variation below a stated threshold (evidence of healthy, not degenerate, k-means convergence — ties back to Phase 5's inertia signal).
  • Recall@10 increases monotonically with nprobe across {1, 8, 16, 64, 1024} (i.e., fraction of nlist swept from near-zero to exhaustive) — property test tied to §28.
  • At nprobe=16 (nlist/64), recall@10 ≥ 0.85 on SIFT1M with the Phase-6 PQ codec at m=8, 8-bit (matches §4).
  • I10 enforcement: an assignment-consistency sweep over a built index finds zero misassigned codes.

19.5 Conformance Fixtures

  • ivf/coarse_quantizer_1024.bin — trained coarse quantizer on SIFT1M, purpose: the standard fixture consumed by Phase 8.
  • ivf/nprobe_sweep.json — recall@10 across the nprobe sweep in 19.4, purpose: monotonicity gate.
  • ivf/skewed_clusters_flag.json — an intentionally imbalanced coarse quantizer, purpose: verify the rebalancing-flag tooling fires (step 9), expected: a flagged retrain recommendation, not a silent no-op.
  • degenerate/misassigned_code_detection.bin — a deliberately corrupted list-membership fixture, purpose: I10's assignment-consistency sweep, expected: nonzero detection count and rejection of segment activation.

19.6 Pitfalls

  1. nlist too small for the corpus size — a coarse quantizer with too few cells makes every list too long, degrading nprobe's speed benefit; manifests as latency far above the §4 target at the recommended nprobe; detect via list-length telemetry against the §4 heuristic range.
  2. nlist too large — excessive cells make each list too short and coarse-routing overhead (distance to all nlist centroids) dominate; manifests as latency regression at low corpus sizes; detect via the coarse-routing-cost fraction of total query time.
  3. Cell-size imbalance from poor k-means seeding — inherited directly from Phase 5's 17.6.1 — manifests here as some lists being scanned far longer than others under a fixed nprobe, causing tail-latency variance across queries landing in different cells; detect via the coefficient-of-variation check (19.4).
  4. I10 violation from a race between assignment and list append — concurrent inserts into the same cell without the per-cell lock (ADR-17) can append a code to the wrong list under contention; manifests as the assignment-consistency sweep finding mismatches; detect via the misassigned-code fixture.
  5. Silent auto-rebalancing masking a training defect — automatically redistributing an imbalanced cell without flagging it hides a codebook-quality problem that will recur; manifests as recurring rebalancing operations with no root-cause fix; detect via rebalancing-frequency telemetry; recover by always flagging for a human-triggered retrain (P13), never auto-silent.

19.7 Performance Concerns

Coarse routing cost (O(nlist × d)) is fixed regardless of corpus size for a given nlist, and must remain small relative to the list-scan cost (O(nprobe × avg_list_len × m)) or it becomes the dominant term at small nprobe; per-cell lock overhead under high insert concurrency; cache locality of a single inverted list (contiguous storage per cell aids scan throughput, matching ADR-04's layout rationale extended to lists).

19.8 Edge Cases

nprobe > nlist (must clamp to nlist, i.e., exhaustive scan, not error); an empty cell (zero assigned vectors — must be skipped cleanly during scan, not treated as an error); nlist=1 (degenerates to a single list — must behave identically to a full scan over PQ-encoded data, a useful sanity check).

19.9 Failure Analysis

Cell imbalance is the IVF-specific analogue of HNSW's graph degeneration (15.9): it degrades tail latency and recall gradually rather than failing hard, and the only reliable detection is the list-length and coefficient-of-variation telemetry — a live recall-probe drop is a late, not early, signal for this failure mode.

19.10 Operational Notes

Expose per-cell list-length histograms and the coefficient-of-variation metric continuously (§26); a retrain recommendation (step 9) must reach an operator's runbook before any automatic action is taken.

20. Phase 8 — The Combined IVF-PQ Pipeline

20.1 Objectives

Wire Phase 6's PQ codec and Phase 7's IVF routing into ann-ivfpq, the end-to-end combined pipeline (§8's five-stage sequence table), and validate it against the Phase 2 harness on SIFT1M and GloVe.

20.2 Detailed Implementation Steps

  1. Implement IvfIndex + ProductQuantizer composition into a single ann-ivfpq entry point matching §8's pipeline: coarse routing → distance-table build → list scan → top-k selection → optional exact rerank.
  2. Implement segment-level parameter binding (I11): nlist, nprobe default, and PQ subspace/bit configuration are fixed together at segment-build time and validated as a set at load, not independently.
  3. Implement the optional exact-rerank stage (§8 step 5): given the approximate top-k from PQ-ADC, recompute true distance from the vector store (if retained) for a final reorder — documented as a recall/latency knob, not a mandatory stage.
  4. Implement end-to-end build orchestration: train coarse quantizer (Phase 7) → train PQ codebooks (Phase 6) → assign and encode every vector → populate inverted lists.
  5. Implement the combined-pipeline recall/latency/memory report via ann-eval, producing the central §8 framing-table row for IVF-PQ empirically, not just illustratively.
  6. Implement a differential test against Phase 3–4's HNSW pipeline on the same dataset, confirming both land in their respective §4 target bands.
  7. Add build-orchestration telemetry: time spent in each of the four build stages (coarse training, PQ training, encoding, list population), surfacing which stage dominates at a given corpus size.
  8. Add a rerank-effectiveness metric: recall@10 with vs. without the exact-rerank stage, quantifying its benefit for a given rerank-candidate-count choice.

20.3 Deliverable

A fully operational IVF-PQ index (ann-ivfpq) buildable end-to-end from raw vectors, searchable with tunable nprobe and optional exact rerank, reporting recall/latency/ memory via the shared evaluation harness.

20.4 Acceptance Criteria

  • Recall@10 ≥ 0.85 at nprobe=16 on SIFT1M (m=8, 8-bit PQ, nlist=1024) — matches §4 and 19.4.
  • p50 ≤ 0.15 ms, p95 ≤ 0.4 ms at that configuration (§4).
  • QPS/core ≥ 6,000 at recall@10=0.85 (§4).
  • Exact rerank over a 10×k candidate set raises recall@10 to within 0.02 of the flat oracle's recall (i.e., near-1.0), quantifying the rerank-effectiveness metric from step 8.
  • End-to-end build (coarse train + PQ train + encode + populate) on SIFT1M completes within a stated CI time budget, with per-stage timing broken out.

20.5 Conformance Fixtures

  • ivfpq/sift1m_full_build.bin — the complete built index, purpose: the canonical fixture for every subsequent phase's IVF-PQ tests.
  • ivfpq/recall_report_sift1m.json — the ann-eval output for this configuration, purpose: §4/§30 target verification.
  • ivfpq/rerank_effectiveness.json — recall with/without rerank, purpose: 20.4's rerank gate.
  • degenerate/param_set_mismatch.bin — a segment whose manifest nlist disagrees with its actual list count, purpose: I11 rejection path, expected: segment activation refused.

20.6 Pitfalls

  1. Parameter drift between coarse quantizer and PQ codebook versions — rebuilding one without the other (violating I11) produces a segment whose lists reference the wrong codebook; manifests as CodebookVersionMismatch at load, or worse, silent misdecoding if the version check is skipped; detect via the param-set-mismatch fixture.
  2. Build-stage ordering error — encoding vectors before the PQ codebook has finished training produces garbage codes; manifests as near-zero recall despite a "successful" build; detect via per-stage completion telemetry (step 7) showing encode starting before training's reported completion.
  3. Rerank stage silently disabled by a default candidate count of zero — a misconfigured rerank-candidate count effectively no-ops the stage while callers believe it is active; manifests as recall matching the no-rerank baseline exactly; detect via the rerank-effectiveness fixture (20.5) always being run in CI, not just ad hoc.
  4. Double-counting tombstone filtering across the IVF and PQ layers — filtering at both the list-scan stage and the top-k stage redundantly is harmless for correctness but can double the tombstone-check cost; manifests as unexplained latency overhead; detect via per-stage profiling.

20.7 Performance Concerns

The four build stages have very different cost profiles: coarse-quantizer training is O(N × nlist × d) per iteration, PQ training is O(N × k × d/m) per iteration per subspace, encoding is a single pass, and list population is append-dominated — profiling must attribute build time correctly (20.2 step 7) or an operator will mis-diagnose which stage to tune; query-time cost is dominated by the list scan exactly as in Phase 7, with rerank adding a bounded, k-proportional tail cost only when enabled.

20.8 Edge Cases

A corpus smaller than nlist (some cells will necessarily be empty, must not error); rerank requested but the original vector store was not retained (must error explicitly, not silently skip rerank); a query whose top PQ-ADC candidate ties exactly with the next candidate under rerank (I12's dedup/tie-break applies identically here).

20.9 Failure Analysis

Because this phase composes two already-validated components, a defect here is most likely a composition/ordering bug (parameter versioning, build-stage sequencing) rather than a numerical bug in either PQ or IVF individually — the debug method is to first confirm Phase 6's and Phase 7's own acceptance criteria still pass in isolation before suspecting the composition layer.

20.10 Operational Notes

The four-stage build telemetry (step 7) is the primary tool for capacity-planning a rebuild — an operator scheduling a retrain (P13) needs per-stage duration to estimate total downtime/CPU budget before triggering it.

21. Phase 9 — Incremental Insert, Delete, and Tombstones

21.1 Objectives

Implement ann-mutate: the single-writer op-log serializing insert and delete across every index family, the tombstone mechanism (I3, P4), and background compaction that reclaims tombstoned space without violating navigability (I2) or list consistency (I10).

21.2 Detailed Implementation Steps

  1. Implement the op-log (Tombstone, insert records) with strictly monotonic sequence numbers (I13), the single ordering authority across HNSW, IVF-PQ, and flat; route a validated (I4-checked) insert to every active index family under this serialization.
  2. Implement delete as a tombstone commit (P4): mark Tombstone { id, committed_seq } in a shared bitmap/set consulted by every search path (HNSW, IVF-PQ, flat) before any candidate enters a result set, plus tombstone-ratio telemetry as the compaction trigger metric.
  3. Implement compaction: rebuild affected structures (HNSW subgraph or IVF list) excluding tombstoned vectors, swapping the rebuilt structure in atomically (reusing the immutable-segment-swap pattern, P5's spirit extended to compaction), with backlog telemetry and a throttling policy bounding concurrent compaction work (P8).
  4. Implement crash-safety for the op-log: an incomplete insert/delete record at restart is discarded, not partially applied (replay is all-or-nothing per record).
  5. Implement re-insertion-after-delete semantics: inserting a VectorId that was previously tombstoned creates a new, distinct logical entry (never resurrects the tombstoned data), ordered by op-log sequence (I13); add insert/delete latency telemetry against the §4 targets (insert p99 ≤ 2 ms, delete p99 ≤ 10 µs).

21.3 Deliverable

A working mutation layer (ann-mutate) supporting online insert and delete across all three index families, tombstone-correct search (I3) at all times, and background compaction that reclaims space without violating navigability or list-membership invariants.

21.4 Acceptance Criteria

  • A deleted vector never appears in any search result across HNSW, IVF-PQ, or flat, verified across 10,000 delete-then-search sequences (property test tied to §28, I3).
  • Insert p99 ≤ 2 ms on HNSW at M=16, efConstruction=200 (§4).
  • Delete (tombstone mark) p99 ≤ 10 µs (§4).
  • Post-compaction, recall@10 on the compacted index is within 0.01 of a freshly built index over the same (post-deletion) live vector set — compaction must not itself degrade quality.
  • Connectivity sweep (I2) and assignment-consistency sweep (I10) both pass after compaction, not just after initial build.

21.5 Conformance Fixtures

  • mutate/delete_then_search.json — 10,000 delete/search pairs, purpose: I3 enforcement, expected: zero tombstoned IDs returned.
  • mutate/reinsert_after_delete.json — delete then re-insert the same VectorId, purpose: verify no resurrection of stale data, expected: search returns only the new entry's vector.
  • mutate/compaction_before_after.json — recall report pre- and post-compaction, purpose: 21.4's quality-preservation gate.
  • mutate/crash_mid_insert.plan — a simulated crash between op-log append and index structure update, purpose: crash-safety verification, expected: replay discards the incomplete record cleanly.

21.6 Pitfalls

  1. Tombstone check omitted in one index family but not another — HNSW search correctly filters tombstones but the flat oracle path (reused for rerank) does not; manifests as rerank occasionally surfacing deleted vectors even though primary search does not; detect via the delete-then-search fixture run against every index family, not just one.
  2. Compaction racing with an in-flight query — swapping a rebuilt HNSW subgraph while a query holds a reference into the old structure; manifests as a use-after- free-class bug or an inconsistent partial result; detect via a chaos fixture (concurrent insert/compaction during search, tied to §28's chaos testing); recover via the atomic-swap pattern (step 5), never in-place mutation during compaction.
  3. Op-log replay applying a partial record — a crash mid-write leaves a torn record that, if replayed naively, half-applies; manifests as an insert with a vector but no corresponding graph edges, or a tombstone with no matching original insert; detect via the crash-mid-insert fixture; recover by requiring a record checksum before replay applies it (full durable-log ownership beyond this checksum is delegated to the host per §1's boundaries).
  4. Unbounded tombstone accumulation degrading connectivity — if compaction never triggers (backlog telemetry ignored), enough tombstoned nodes in an HNSW graph can reduce effective navigability even though I2's raw connectivity still technically holds; manifests as slowly rising p99 latency and falling recall over the corpus's lifetime; detect via tombstone-ratio telemetry crossing a threshold; recover by scheduling compaction (P13), never leaving it purely reactive.
  5. Re-insertion resurrecting stale cached state — reusing an old in-memory struct for a re-inserted VectorId instead of treating it as wholly new; manifests as the reinsert-after-delete fixture returning stale vector values; detect via that fixture directly.

21.7 Performance Concerns

Insert throughput is bounded by the single-writer serialization (P5) — this is a deliberate tradeoff (correctness over raw mutation throughput per P5/ADR-17), and the practical mitigation is batching multiple inserts through one serialized op-log transaction rather than parallelizing writers; compaction competes for CPU with query serving and must be throttled (step 6) to avoid p99 latency regressions during maintenance windows.

21.8 Edge Cases

Deleting a VectorId that was never inserted (must be a no-op or a typed "not found" error, never a corrupted tombstone entry); deleting the same VectorId twice (idempotent, second delete is a no-op); inserting while a compaction of the same region is in progress (must serialize correctly through the op-log, not race).

21.9 Failure Analysis

Tombstone-related defects are compliance-critical, not just correctness bugs (P4) — a deleted vector resurfacing in results after a legally mandated deletion is a different severity class than a recall regression, and this phase's fixtures (21.5) and property tests (§28) must be treated as release-blocking, not advisory.

21.10 Operational Notes

Tombstone ratio and compaction backlog are named metrics in §26's operational surface; the tombstone-compaction runbook (docs/runbooks/tombstone-compaction.md) governs when an operator manually triggers compaction versus letting the scheduled policy handle it.

22. Phase 10 — Filtered Search and Persistence/Mmap

22.1 Objectives

Implement ann-filter's pre-filter/post-filter/in-graph decision (§8's decision table, P12) and ann-persist's versioned on-disk format with memory-mapped loading (I7, P10, P11), the two capabilities a host vector database most depends on (§1).

22.2 Detailed Implementation Steps

  1. Implement Predicate/Filter per §11, with a selectivity-estimation hook (host- supplied or sampled) driving the pre-filter/post-filter choice (P12) via the §4 threshold switch (pre-filter below ~10% selectivity, post-filter above).
  2. Implement the pre-filter path (build a bitmap of matching VectorIds first, restrict HNSW/IVF-PQ search to it) and the post-filter path (run normal search for k × oversample_factor candidates, apply the predicate afterward, return up to k).
  3. Document the in-graph filtering approach as an open problem (§8's decision table entry) rather than implementing it as a general solution in Phase 0.
  4. Implement the on-disk segment format: manifest (format version, checksum, vector count, index types — SegmentManifest per §11) plus the serialized graph, codebooks, and inverted lists.
  5. Implement the mmap loader (MmapRegion): read-only mapping, madvise(MADV_RANDOM) for HNSW graph pages, madvise(MADV_SEQUENTIAL) for flat/IVF-list full-scan regions (§4), plus checksum verification at load (I7) rejecting any segment whose checksum does not match its manifest before any query is served.
  6. Implement the reload-and-diff conformance tool (build, persist, reload, assert identical search results across a fixed query set, I7's direct test) and page-fault- rate telemetry for mmap'd regions, distinguishing "mapped" from "resident" (P11).

22.3 Deliverable

A filtered-search path (ann-filter) with a selectivity-driven strategy switch, and a persistence layer (ann-persist) producing a versioned, checksum-verified, memory- mappable on-disk index format that reloads to bit-identical search behavior.

22.4 Acceptance Criteria

  • Pre-filter path outperforms post-filter (lower latency) on a fixture with < 10% predicate selectivity; post-filter outperforms pre-filter above ~50% selectivity — both measured via ann-eval, confirming P12's switch is correctly directional.
  • A reloaded index returns identical SearchResult sets to the in-memory index that produced it, across 10,000 fixed queries (I7's direct acceptance test).
  • RTO ≤ 5 seconds to reload a 1M-vector index from disk (§4).
  • Checksum mismatch at load is rejected 100% of the time on a fixture set of corrupted segments (no false negatives).

22.5 Conformance Fixtures

  • filter/low_selectivity_prefilter.json — < 10% match predicate, purpose: 22.4's pre-filter-wins gate.
  • filter/high_selectivity_postfilter.json — > 50% match predicate, purpose: post- filter-wins gate.
  • filter/matches_nothing.json — a predicate matching zero vectors, purpose: §8's degenerate case, expected: an empty result set returned promptly, not a full scan followed by an empty result.
  • persist/reload_identity.json — build/persist/reload/query cycle, purpose: I7's direct gate.
  • persist/corrupt_checksum.seg — a segment with a deliberately corrupted checksum, purpose: load-rejection gate.
  • persist/version_mismatch.seg — a segment format version newer than the loader supports, purpose: I7/P10 rejection gate.

22.6 Pitfalls

  1. Wrong-side selectivity switch under a bad estimate — using a stale or wrong selectivity estimate picks the wrong strategy, degenerating to near-brute-force (pre-filter on a non-selective predicate) or wasted oversampling (post-filter on a highly selective one); manifests as latency far outside the §4 filtered-search expectations; detect via the two directional fixtures in 22.5 always run together.
  2. Full scan performed before discovering the filter matches nothing — evaluating the predicate lazily during traversal instead of checking bitmap emptiness upfront; manifests as full query latency paid for an empty result; detect via the matches-nothing fixture's latency assertion, not just its correctness assertion.
  3. mmap loader trusting an unchecksummed segment — skipping checksum verification for a "trusted" internal path; manifests as silently serving corrupted data, an especially dangerous defect given §24's T3 threat surface; detect via the corrupt- checksum fixture; recover by making checksum verification unconditional.
  4. Version-check treating "newer" and "older" identically — rejecting any version mismatch without distinguishing a safely-ignorable additive change from a breaking one; manifests as unnecessary rejection of forward-compatible segments; detect via §27's compatibility test matrix (addressed there, flagged here as the originating implementation concern).
  5. madvise policy mismatched to access pattern — applying MADV_RANDOM to a sequential IVF-list scan region (or vice versa) hurts OS readahead heuristics; manifests as page-fault telemetry (step 6) showing higher-than-expected faults for the access pattern in use; detect via that telemetry directly.

22.7 Performance Concerns

Pre-filter bitmap construction cost must be amortized against its benefit — building a bitmap over a billion-vector corpus for one query is nontrivial and must be weighed against the alternative; mmap cold-start page-fault behavior (§4) means the first queries after a reload are systematically slower until the working set is resident — reported as a distinct cold-start latency figure, not averaged into steady-state percentiles.

22.8 Edge Cases

A filter predicate referencing a field the host never populated (treated as non- matching, not an error, unless the host's contract specifies otherwise); reloading a segment built by an older but still-supported format version (§27's compatibility window); mmap loading on a filesystem lacking the OS's expected page-cache behavior (must degrade to a documented, not silently broken, behavior).

22.9 Failure Analysis

A filtered-search latency regression is diagnosed by first checking which strategy (pre/post-filter) was selected for the query in question (via tracing, 22.2 step 1's telemetry) before assuming an index-level defect — most filtered-search performance complaints trace to a selectivity-estimate mismatch, not a bug in either filter path itself.

22.10 Operational Notes

The mmap-thrash-diagnosis runbook (docs/runbooks/mmap-thrash-diagnosis.md) is the primary tool for an operator seeing elevated query latency after a reload or a memory- pressure event on the host — page-fault-rate telemetry (step 6) is the first thing checked.

23. Phase 11 — Parameter Tuning, Conformance on Standard Datasets, Perf Hardening

23.1 Objectives

Close out the v1 build: run the full ann-eval conformance suite against SIFT1M and GloVe for both HNSW and IVF-PQ, differentially compare against FAISS and hnswlib on the same datasets, and harden the tuning defaults (M, efSearch, nlist, nprobe, PQ bits) into documented, regime-scoped recommendations (P8).

23.2 Detailed Implementation Steps

  1. Run the complete recall/latency/memory sweep (efSearch, nprobe, M, PQ bits) across SIFT1M and GloVe, producing the definitive RecallReport set for this blueprint.
  2. Implement differential benchmarking against FAISS's IndexHNSWFlat and IndexIVFPQ, and against hnswlib, on identical datasets and identical recall targets, comparing latency and memory at matched recall (§28's differential-testing gate, citing Johnson, Douze, Jégou 2019 and the hnswlib reference implementation).
  3. Implement the parameter-recommendation table: for named corpus-size/dimensionality regimes, the recommended M/efSearch or nlist/nprobe/PQ-bits default, each tied to a measured recall/latency/memory point (feeds §9 ADR 6th-column regimes).
  4. Implement perf-hardening passes flagged by earlier phases' 30/34-adjacent profiling: cache-line padding where false sharing was found, prefetch-distance tuning for beam search, allocator-pressure reduction in candidate heaps.
  5. Implement the perf-regression CI gate: a recall floor and a latency ceiling enforced together, failing the build if either regresses beyond a stated tolerance versus the last known-good benchmark (§28, §30).
  6. Implement soak-test orchestration: multi-hour mixed insert/delete/search load, watching for memory growth (leak detection) and latency drift (compaction/tombstone interaction under sustained load).
  7. Finalize the conformance test suite tying every I# invariant to a concrete automated check, closing any gaps discovered during Phases 0–10.
  8. Produce the final docs/performance/ writeup documenting every §4/§30 target alongside its measured value at v1.

23.3 Deliverable

A tuned, benchmarked, conformant v1: documented parameter recommendations per regime, a passing differential-benchmark comparison against FAISS/hnswlib, a green perf- regression CI gate, and a completed soak test with no detected leaks or drift.

23.4 Acceptance Criteria

  • HNSW and IVF-PQ both meet every numeric target in §4 on SIFT1M and GloVe.
  • Differential benchmark shows this implementation within a stated tolerance band (e.g., within 2× latency at matched recall) of FAISS's and hnswlib's published/reproduced numbers on the same datasets — deviations beyond the band are documented with a root cause, not silently accepted.
  • 24-hour soak test shows zero unbounded memory growth and stable p99 latency (no upward drift beyond a stated bound) under continuous mixed insert/delete/search load.
  • Every invariant I1–I13 has at least one automated conformance check passing in CI.

  • conformance/faiss_differential.json, conformance/hnswlib_differential.json — side-by-side comparison reports, purpose: §28's differential gate.
  • conformance/soak_24h.log — soak-test telemetry export, purpose: leak/drift detection evidence.
  • conformance/invariant_coverage.json — a machine-checked map from every I# to its passing test(s), purpose: closing 23.4's invariant-coverage gate.

23.6 Pitfalls

  1. Tuning to one dataset's idiosyncrasies — parameter recommendations derived only from SIFT1M may not generalize to GloVe's different dimensionality and metric; manifests as the GloVe sweep underperforming despite SIFT1M looking excellent; detect via requiring both datasets' sweeps to independently meet §4 targets, not just one.
  2. Differential benchmark comparing mismatched configurations — comparing this implementation's HNSW at M=16 against FAISS's at a different M produces a misleading "we're slower/faster" conclusion; manifests as an unreproducible or contested benchmark result; detect by requiring matched-recall (not matched-parameter) comparison, since recall is the invariant quantity across implementations (P1).
  3. Soak test masking a slow leak behind a large initial heap — a leak too small to show up in a 1-hour run only becomes visible over many hours; manifests as a soak test "passing" that a longer run would have failed; detect via the mandated 24-hour minimum duration (23.4) rather than a shorter convenience run.
  4. Perf-regression gate tolerance set too loose — a generous tolerance band lets real regressions slip through incrementally, phase over phase; manifests as v1's final numbers being worse than early-phase measurements despite every individual CI run passing; detect by comparing v1's final sweep against Phase 4/8's original acceptance-criteria numbers directly, not just against the immediately prior commit.

23.7 Performance Concerns

This phase is where every earlier phase's deferred perf work (flagged in each phase's N.7) gets addressed or explicitly re-deferred with a documented reason; the differential benchmark against FAISS/hnswlib is itself expensive to run (building comparable reference indexes) and should be scheduled as a scheduled/nightly CI job, not on every commit.

23.8 Edge Cases

A parameter regime with no clean recommendation (e.g., a dimensionality far outside the tested range) must be explicitly flagged as "untested — proceed with an internal benchmark" rather than silently extrapolating a recommendation; a soak test that encounters a host-level resource limit (e.g., file descriptor exhaustion unrelated to this project) must be distinguished from a defect in this project.

23.9 Failure Analysis

A v1 that fails this phase's differential-benchmark gate is not necessarily "wrong" — it may be a legitimate, documented design tradeoff (e.g., a simpler coarse quantizer than FAISS's, ADR-11) — the exit criterion is that every deviation is explained, not that every number matches FAISS exactly.

27. Compatibility & Versioning

Persisted-index format versioning. The graph format, codebook format, and inverted- list format each carry an independent version field within the shared SegmentManifest (§11); a loader must check all three, since a future change might affect only one substructure (e.g., a new codebook encoding without a graph format change).

Metric and dimensionality as immutable index properties (I4, I11). Once a segment is built, its Metric and Dim never change; a host wanting a different metric or dimensionality builds a new index, it does not migrate one in place.

Codebook compatibility. A PQ or scalar-quantizer codebook version is tied to the segment that used it to encode (I5); loading a segment against a mismatched codebook version is rejected outright (P6) — there is no partial-compatibility mode.

Parameter-set evolution. Default recommendations (M, efSearch, nlist, nprobe, PQ bits) may change between minor versions of this project without breaking existing persisted segments, since those parameters are recorded per-segment (I11), not assumed from the library version.

API stability. The Rust crate API (types in §11) follows SemVer: breaking changes to VectorId, Metric, SearchParams, or any persisted type require a MAJOR bump.

Migration/reindex procedure. Any breaking format change ships with a documented reindex procedure (rebuild from the retained original vectors, if the host retained them — the index itself does not guarantee vector retention beyond what quantization requires); there is no in-place binary format migration in Phase 0.

Deprecation. A deprecated parameter or type is retained for at least one MAJOR version cycle with a compile-time warning before removal.

SemVer. MAJOR — persisted-format-breaking or API-breaking change. MINOR — new index family, new tunable, new capability, format-compatible. PATCH — bug fix, no format or API change.

Rolling-upgrade guarantees. Because the index is an embedded library, "rolling upgrade" means: a newer library version must be able to load segments written by any still-supported older MINOR version within the same MAJOR line (forward-readable within a major version), verified by §27's compatibility test matrix referenced from 22.6.4.

30. Performance Engineering

Methodology. Cache locality of neighbor lists (HNSW) and inverted lists (IVF-PQ) is the first-order concern because both are dominated by random or semi-random memory access (15.7, 19.7); SIMD utilization in the distance kernels is the dominant inner-loop cost for flat and for any per-candidate distance computation (Phase 0, §34); memory bandwidth is the practical ceiling for flat and IVF full-list scans once the working set exceeds cache size (13.7, §34); prefetching graph neighbors ahead of beam-search expansion mitigates HNSW's random-access penalty partially, not fully; allocation on the hot path (per-query candidate heaps, visited sets) is minimized by pooling (16.7); the precomputed-distance-table reuse in PQ (18.7) is the single largest IVF-PQ-specific optimization, amortizing table-build cost across an entire candidate list rather than per-candidate; tail latency is treated as the real latency (P design principle inherited from the domain, formalized in §30's targets below) — average latency is never reported without its p95/p99 companions.

31. Scalability Analysis

What stays constant vs. grows. Flat search cost is linear in N × d — it never improves structurally, it only benefits from more SIMD throughput or more cores (§34). HNSW search cost is roughly logarithmic in N, with a constant factor set by efSearch and M — this is the reason HNSW remains practical well past the corpus sizes where flat becomes untenable, though the constant factor (not the asymptotic class) is what actually gets tuned in practice. IVF search cost is linear in nprobe × average_list_ length, which itself grows roughly as N/nlist — increasing nlist alongside N keeps per-cell cost roughly constant, which is why §4's nlist ≈ √N heuristic exists. PQ trades memory for a small, bounded distance-estimation cost (the table-lookup overhead per subspace) that does not grow with N — it is a per-vector constant, not a scaling term.

Named bottlenecks, in order. (1) Memory bandwidth for flat and IVF full-cell scans once the working set exceeds cache (§34); (2) random memory access for HNSW graph traversal and IVF inverted-list pointer-chasing (15.7, 19.7); (3) k-means training cost at build time, which is the slowest single build stage at large nlist/k (17.7); (4) single-writer insert serialization (P5) capping mutation throughput independent of corpus size.

The memory wall. At billion-vector scale, flat's 512 B/vector (128-d f32) or even HNSW's ~608 B/vector becomes untenable on a single node — 1 billion × 608 B ≈ 566 GB, exceeding practical single-node RAM — this is precisely the regime PQ's ~12 B/vector (§34) exists to address, and it is the quantitative motivation for quantization at scale rather than a stylistic preference (Jégou, Douze, Schmid 2011; Johnson, Douze, Jégou 2019).

Build-time scaling. HNSW build time scales with N × efConstruction × average_ degree (23.2-adjacent); IVF-PQ build time is dominated by k-means training (O(N_sample × k × d) per iteration) rather than by N directly once a bounded training sample is used (17.2 step 8) — this decouples IVF-PQ build time from full corpus size more than HNSW's build time is decoupled.

Sharding and the path beyond RAM. This project does not implement sharding in Phase 0 (deferred, §37); the documented path beyond single-node RAM is DiskANN's on-disk graph approach (Subramanya et al. 2019, §36), which trades RAM for SSD-resident graph traversal rather than partitioning the corpus across nodes — a different axis of scaling than sharding, and the one this blueprint identifies as the more relevant "beyond RAM" answer for a single-node deployment before reaching for distribution.

Practical ceilings and the levers beyond them. Vector-count ceiling in Phase 0: ~100M single-node (§4), set by RAM for HNSW/flat and by RAM-for-codebooks-plus-lists for IVF-PQ; dimensionality ceiling: 4,096 (guard-railed, §4), set by per-vector memory and distance-kernel tail-handling cost, not by an algorithmic limit. Levers beyond these ceilings: quantization (already in Phase 0, gets to billions of vectors on one node per the memory-wall math above); on-disk graph residency (DiskANN-style, deferred, §36); sharding (deferred, §37); GPU-resident brute-force or IVF (deferred, §36, §37).

32. Mental Models & First Principles

MM1 — Approximate nearest neighbor is a deliberate trade of recall for speed and memory. Predicts: any ANN claim without a recall number and a named dataset is meaningless. Bug class without it: shipping a "fast" configuration that silently has unacceptable recall, because nobody asked the second question. Resolving §4, §8, §30.

MM2 — HNSW is a skip list generalized to a metric space. Predicts: the upper layers are express lanes, sparse by the geometric layer-assignment probability, existing only to land search near the right neighborhood cheaply; the real work happens at layer 0. Bug class without it: tuning M or efConstruction uniformly across layers instead of understanding layer 0 is where degree and beam width matter most. Resolving §8, Phase 3.

MM3 — Product quantization is lossy compression that preserves distances well enough to rank, which is all a nearest-neighbor query needs. Predicts: PQ reconstruction error is tolerable precisely because the deliverable is an ordering, not a value — a reconstructed vector need not resemble the original numerically as long as relative distances are preserved. Bug class without it: over-investing in reconstruction fidelity (more bits than needed) when the actual requirement is rank preservation at the target k. Resolving §8, Phase 6.

MM4 — In high dimensions everything is far from everything, so the interesting structure is entirely in the relative ordering, not the absolute distances. Predicts: absolute distance values become less informative as dimensionality grows, while rank order remains meaningful — this is why recall@k, not distance-value accuracy, is the correctness metric throughout this blueprint. Bug class without it: debugging a "distance looks wrong" complaint by chasing absolute-value precision instead of checking whether the ranking is correct. Resolving §8's curse-of-dimensionality section, P1.

MM5 — The flat index is not a slower version of the approximate ones, it is a different category of artifact: a proof, not a product. Predicts: nobody should ever try to "optimize" the flat index into an approximation — its entire value is being unambiguously exact. Bug class without it: someone adds an approximation shortcut to ann-flat "for speed" and silently destroys the oracle every other phase depends on. Resolving P2, I1, Phase 1.

MM6 — Asymmetric distance computation exists because compounding two approximations is worse than one. Predicts: quantizing the query would add a second, independent source of error on top of the database vector's quantization, so leaving the query exact is a strictly dominant choice, not a stylistic preference. Bug class without it: "simplifying" the search path to symmetric distance because it looks more elegant, silently paying a recall cost. Resolving P3, Phase 6.

MM7 — A tombstone is a promise, not an optimization. Predicts: the tombstone mechanism exists because immediate physical removal would break navigability/list consistency, not because it is a convenient shortcut — and the promise it makes (deleted data is never returned) is non-negotiable regardless of implementation convenience. Bug class without it: treating tombstone checks as optional or best-effort in a hot path, producing a compliance-severity defect. Resolving P4, I3, Phase 9.

MM8 — Every index configuration is a single point on a three-axis surface (recall, latency, memory), and choosing a configuration is choosing a point, not "tuning until it feels fast." Predicts: two engineers can both be "right" about a configuration while optimizing for different axes — the disagreement is about which point on the surface matters, not about a fact. Bug class without it: parameter arguments that never converge because the actual disagreement (which axis matters more) is never made explicit. Resolving P1, §8's framing table, §34.

FAISS's IVF-PQ heritage wins when a team needs the most battle-tested, broadest index-family coverage in one library and can absorb its C++ dependency and monolithic index-hierarchy coupling (ADR-01's rejected-alternative note) — it is the reference this blueprint benchmarks against precisely because it defines the practical state of the art for IVF-PQ (Johnson, Douze, Jégou 2019).

hnswlib's pure-HNSW simplicity wins when a team needs only graph-based search, full precision, and the smallest possible dependency surface — its header-only design is easy to embed but couples concurrency policy to the algorithm in a way this blueprint deliberately avoids (ADR-17, §5 reference-implementation pitfall).

ScaNN's anisotropic quantization wins when the deployment is already TensorFlow/ Google-ecosystem-native and the workload can tolerate a batch-oriented, less latency-sensitive query path in exchange for quantization loss specifically tuned to preserve top-k ranking rather than raw reconstruction fidelity (Guo et al. 2020) — this is exactly the capability this blueprint defers rather than rejects (§37).

DiskANN's on-disk billion-scale design wins when the corpus cannot fit in RAM on a single node and the deployment can tolerate SSD-latency graph traversal in exchange for avoiding both sharding and a RAM upgrade — the path this blueprint identifies (§31) as the relevant "beyond RAM" answer, deferred rather than built in Phase 0 (Subramanya et al. 2019, §36).

34. Back-of-Envelope Capacity Model

All derivations below use SIFT1M's N=1,000,000, d=128 baseline from §4 unless stated.

1. Flat-index memory. N × d × 4 bytes = 1,000,000 × 128 × 4 = 512,000,000 bytes ≈ 512 MB. This is the §4 "512 B/vector" figure times N.

2. HNSW memory. Flat's per-vector cost plus graph overhead: average node participates in ~1.33 layers (geometric decay from mL = 1/ln(16) ≈ 0.36, expected layer count ≈ 1/(1−e^{−1/mL})-derived, approximated here as ~1.33 for M=16) at M=16 neighbors/layer, 4 bytes/neighbor-id (u32): 128 × 4 + 16 × 1.33 × 4 ≈ 512 + 85 ≈ 597 B/vector, rounding to the §4 figure of ≈608 B/vector once bookkeeping (level field, pointers) is included. Total for N=1M: ≈ 608 MB, an ≈19% overhead over flat.

3. IVF-PQ memory. PQ code: m=8 subspaces × 1 byte (8-bit codes, ADR-09) = 8 bytes; plus a 4-byte coarse-list back-reference: 12 B/vector. Total for N=1M: 12 MB for codes, plus fixed codebook overhead (m × k × (d/m) × 4 bytes = 8 × 256 × 16 × 4 = 131,072 bytes ≈ 128 KB, independent of N) and coarse-quantizer centroids (nlist × d × 4 bytes = 1024 × 128 × 4 = 524,288 bytes ≈ 512 KB, also independent of N). Total ≈ 12.6 MB for N=1M — compression ratio versus flat: 512,000,000 / 12,600,000 ≈ 41×, matching §4's ≈42× figure. At 128-d, a 512-byte flat vector compresses to a 12-byte code (plus one-time fixed overhead under 1 MB regardless of corpus size).

4. Brute-force query cost. N × d multiply-adds = 1,000,000 × 128 = 128,000,000 per query. At an illustrative AVX2 SIMD throughput of ~32 GFLOP/s sustained for this access pattern, 128,000,000 × 2 FLOPs / 32×10^9 ≈ 8 µs of pure compute — but the measured p50 of 4 ms (§4) is two-plus orders of magnitude higher, confirming the scan is memory-bandwidth bound, not compute bound (§30): reading 512 MB sequentially at a practical single-core effective bandwidth of ~10–15 GB/s gives 512×10^6 / 12×10^9 ≈ 43 ms worst-case for a fully cold scan, with warm-cache/prefetched sequential access bringing realistic p50 down toward the millisecond range — this is why flat's QPS/core ceiling (~250, §4) is set by memory bandwidth divided by per-vector byte count, not by FLOP throughput.

5. HNSW query cost. Approximately efSearch × average_degree distance computations per query at layer 0, plus a small constant number of upper-layer hops: at efSearch=100, M=16, this is roughly 100 × 16 = 1,600 distance computations (upper bound; visited-set pruning typically reduces the realized count), each at the Phase-0 SIMD kernel's per-call cost — orders of magnitude fewer than flat's 1,000,000 comparisons, which is the entire structural reason HNSW's p50 (0.4 ms, §4) beats flat's (4 ms) by roughly 10× despite each comparison being similarly cheap.

6. IVF query cost. nprobe × average_list_length PQ-distance-table lookups: at nprobe=16, nlist=1024, N=1M, average list length ≈ 1,000,000 / 1024 ≈ 977, giving 16 × 977 ≈ 15,632 table-lookup-based distance evaluations — each cheaper per-operation than a full f32 distance (table lookup + add vs. multiply-accumulate over 128 floats), explaining IVF-PQ's further latency win (0.15 ms, §4) over HNSW despite evaluating more candidates than HNSW's ~1,600 estimate above — the per-candidate cost, not the candidate count, is what changed.

7. Build time (HNSW). N × efConstruction × average_degree distance computations, order-of-magnitude: 1,000,000 × 200 × 16 = 3.2×10^9 distance evaluations for the full build — at the Phase-0 SIMD kernel's throughput, this lands in the range consistent with the §4 target of ≥5,000 vectors/second/core (implying a full 1M-vector build completes in ≈200 seconds/core, before parallelization).

8. Recall/nprobe curve shape. From (6), query cost grows linearly with nprobe, while recall's marginal gain per additional probed cell shrinks as nprobe approaches nlist (each additional cell is, on average, farther from the query than the last, per the coarse quantizer's Voronoi-cell ordering) — this is why the recall/nprobe curve in §8's framing table is concave: linear cost, decelerating benefit, exactly the shape that motivates the default range in §4 (nlist/64 to nlist/8) as the practical knee of that curve rather than either extreme.

36. Alternative Architectures (Roads Not Taken)

A1 — Locality-Sensitive Hashing (LSH)

Query q --> [hash fn h1] --> bucket B1 --\
        --> [hash fn h2] --> bucket B2 ---+--> union of bucket members --> exact rerank
        --> [hash fn hL] --> bucket BL --/
(L independent hash tables, each mapping similar vectors to the same bucket
with provable probability; candidates are the union across tables)

Winning regime: theoretical guarantees matter more than empirical recall/latency — e.g., a setting requiring a provable bound on false-negative probability rather than an empirically measured recall number. Real embodying system: the original LSH family from Indyk & Motwani 1998 and Datar et al. 2004's Euclidean-distance LSH, still used in some approximate-duplicate-detection pipelines. Why rejected here: empirically, LSH's recall/latency/memory tradeoff is dominated by HNSW and IVF-PQ on the standard ANN-Benchmarks datasets this blueprint targets (§5 reading item 10) — the provable guarantee is real but not the load-bearing requirement for this project's stated users (§1).

A2 — Tree-Based Methods (k-d Trees, Random-Projection Forests)

        [split on dim i, value v]
        /                      \
  [dim j, v2]              [dim k, v3]
   /       \                 /      \
 leaf     leaf             leaf    leaf
(k-d tree: axis-aligned splits; Annoy's forest: random-hyperplane splits,
multiple trees voted/merged at query time)

Winning regime: low dimensionality (roughly d < 20, per Bentley 1975's original analysis and the well-known empirical falloff past that range) where axis-aligned or random-hyperplane partitioning still meaningfully prunes the search space. Real embodying system: Annoy (random-projection forests), FLANN (Muja & Lowe 2014, which auto-selects among several tree/graph strategies including k-d trees). Why rejected here: this blueprint's stated dimensionality range (up to 4,096, §4) is squarely in the regime where tree-based partitioning degrades toward linear scan (the curse of dimensionality, §8) — HNSW and IVF-PQ are structurally better suited to the target regime.

A3 — On-Disk Graph Index (DiskANN-Style)

+------------------+     +----------------------------+
| RAM: compressed   |     | SSD: full-precision        |
| PQ vectors +      | --> | vectors + Vamana graph      |
| graph skeleton     |    | (beam search reads pages    |
| (routing only)     |    | on demand, batched I/O)     |
+------------------+     +----------------------------+

Winning regime: corpus size exceeds single-node RAM by an order of magnitude or more, and SSD-latency (not RAM-latency) graph traversal is an acceptable tradeoff for avoiding both a RAM upgrade and horizontal sharding. Real embodying system: DiskANN (Subramanya et al. 2019). Why rejected here (for Phase 0): the on-disk beam-search graph layout and its I/O-batching strategy are a substantial independent design surface that this blueprint defers rather than folds into HNSW's Phase 3–4 scope — see PhaseDeferred("on-disk billion-scale graph index (DiskANN-style)"), §37.

A4 — GPU-Resident Brute-Force or IVF

Host RAM --DMA--> GPU device memory (vectors + coarse index)
                         |
                  massively parallel distance kernel
                  (thousands of threads, one/few per candidate)
                         |
                  top-k reduction on device --> results back to host

Winning regime: the entire dataset fits in GPU device memory and query throughput (not single-query latency) dominates the requirement — e.g., high-QPS batch similarity search. Real embodying system: FAISS-GPU (Johnson, Douze, Jégou 2019). Why rejected here (for Phase 0): GPU support adds a full additional build/dependency/ deployment dimension (a non-goal, §1) before the CPU algorithms themselves are validated and benchmarked — see PhaseDeferred("GPU-resident brute-force/IVF backend"), §37.

38. Glossary

Nearest neighbor — the point in a dataset minimizing distance to a query point under a chosen metric. Approximate nearest neighbor (ANN) — a nearest-neighbor result allowed to be wrong with bounded, measured probability in exchange for speed and/or memory savings (MM1). Recall@k — the fraction of a query's true top-k neighbors (per the flat oracle, I1) present in an approximate index's returned top-k. Ground truth — the exact top-k neighbor set produced by the flat index, used to compute recall. L2 / Euclidean distance — the square-root-of-sum-of-squared-differences metric (§8). Inner product — the dot-product-based metric, negated for consistency with "smaller is closer" (§8). Cosine similarity — the normalized inner product, computed via the cosine-via-normalization identity (P7, §8). Curse of dimensionality — the phenomenon where distances concentrate and pruning structure vanishes as dimensionality grows (§8). HNSW — Hierarchical Navigable Small World graph, a layered proximity-graph ANN index (Malkov & Yashunin 2020). Navigable small world — a graph structure enabling greedy routing to a target in a small number of hops (Malkov et al. 2014). Skip list — the classical probabilistic layered search structure HNSW generalizes to metric spaces (MM2). Layer — one level of an HNSW graph, with layer 0 containing every node (I2). Entry point — the node from which HNSW search begins its greedy descent, always the highest-layer node inserted so far. M — the HNSW neighbor-list degree bound per layer (§4, §9 ADR-07). efConstruction — the beam width used during HNSW graph construction. efSearch — the beam width used during HNSW query-time search (§16). Greedy search — the traversal strategy of always moving toward the closest known candidate. Neighbor-selection heuristic — the diversity-preferring rule choosing which candidates become graph edges (§8, ADR-07). Product quantization (PQ) — splitting a vector into subspaces and quantizing each independently via a trained codebook (Jégou, Douze, Schmid 2011). Subspace — one partition of a vector's dimensions under PQ. Codebook — the set of trained centroids for one PQ subspace. Centroid — the mean point of a k-means cluster, and one entry in a codebook. PQ code — the tuple of nearest-centroid indices representing a quantized vector. Symmetric distance — PQ distance computed with both sides quantized (§8). Asymmetric distance (ADC) — PQ distance computed with the query left unquantized (P3, §8). Distance table — the precomputed per-subspace, per-centroid distance values reused across an ADC scan. IVF — Inverted File index, partitioning vector space into cells via a coarse quantizer. Coarse quantizer — the k-means model producing IVF's cell centroids. nlist — the number of IVF cells. nprobe — the number of IVF cells scanned per query. Inverted list — the per-cell storage of member vectors' codes. Scalar quantization — per-dimension linear quantization to a reduced bit width (§8). K-means — the clustering algorithm underlying both PQ codebook and IVF coarse-quantizer training. K-means++ — the variance-weighted seeding strategy improving k-means convergence (Arthur & Vassilvitskii 2007). Lloyd's algorithm — the classical assign/update iteration at the core of k-means (Lloyd 1982). Tombstone — a deletion marker preventing a vector from appearing in results without physically removing it (I3, P4). Compaction — the background rebuild reclaiming tombstoned space (Phase 9). Filtered search — combining metadata predicate evaluation with vector search (§8, Phase 10). Pre-filter — evaluating the predicate before vector search, restricting the search space. Post-filter — evaluating the predicate after vector search, discarding non-matching results. In-graph filtering — evaluating the predicate during graph traversal itself (§8's open-problem note). Memory-mapped index — an on-disk index format loaded via mmap, with residency managed by the OS page cache (P11). Reconstruction error — the distance between an original vector and its quantized reconstruction, the PQ/scalar-quantization quality signal. Flat index — the brute-force exact index serving as the recall oracle (I1). Recall floor — the minimum acceptable recall@k, breach of which triggers an alert (I8). Op-log — the sequenced record of insert/delete operations serializing mutation (I13). Segment — a versioned, persisted unit of index data (graph, codebooks, lists) with its own manifest (§11). Manifest — the metadata record describing a segment's format version, checksum, and parameters (I7, I11). Cell imbalance — uneven distribution of vectors across IVF cells, a symptom of poor coarse-quantizer training (§19). Graph degeneration — loss of HNSW navigability from poor construction or excessive tombstone accumulation (§15, §21). Beam search — the bounded-width candidate expansion used in both HNSW traversal and PQ list scanning contexts. Selectivity — the fraction of a corpus matching a filter predicate, driving the pre/post-filter decision (P12). Rerank — recomputing exact distance on an approximate candidate set to improve final ordering (§8, §20). ANN-Benchmarks — the named evaluation methodology this project's harness is compatible with (Aumüller, Bernhardsson, Faithfull 2020).
