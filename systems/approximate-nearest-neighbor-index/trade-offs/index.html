Chosen

Rejected

When the rejected choice is right

ADR-05

Chosen

f32

Rejected

When the rejected choice is right

f16 wins at billion-scale where memory dominates and a further 2× recall loss is acceptable; f64 wins only for scientific-precision distance audits, never for serving

Why: f32 balances precision and SIMD lane width for this domain

Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

A1 — Locality-Sensitive Hashing (LSH)

Query q --> [hash fn h1] --> bucket B1 --\
        --> [hash fn h2] --> bucket B2 ---+--> union of bucket members --> exact rerank
        --> [hash fn hL] --> bucket BL --/
(L independent hash tables, each mapping similar vectors to the same bucket
with provable probability; candidates are the union across tables)

Winning regime: theoretical guarantees matter more than empirical recall/latency — e.g., a setting requiring a provable bound on false-negative probability rather than an empirically measured recall number. Real embodying system: the original LSH family from Indyk & Motwani 1998 and Datar et al. 2004's Euclidean-distance LSH, still used in some approximate-duplicate-detection pipelines. Why rejected here: empirically, LSH's recall/latency/memory tradeoff is dominated by HNSW and IVF-PQ on the standard ANN-Benchmarks datasets this blueprint targets (§5 reading item 10) — the provable guarantee is real but not the load-bearing requirement for this project's stated users (§1).

A2 — Tree-Based Methods (k-d Trees, Random-Projection Forests)

        [split on dim i, value v]
        /                      \
  [dim j, v2]              [dim k, v3]
   /       \                 /      \
 leaf     leaf             leaf    leaf
(k-d tree: axis-aligned splits; Annoy's forest: random-hyperplane splits,
multiple trees voted/merged at query time)

Winning regime: low dimensionality (roughly d < 20, per Bentley 1975's original analysis and the well-known empirical falloff past that range) where axis-aligned or random-hyperplane partitioning still meaningfully prunes the search space. Real embodying system: Annoy (random-projection forests), FLANN (Muja & Lowe 2014, which auto-selects among several tree/graph strategies including k-d trees). Why rejected here: this blueprint's stated dimensionality range (up to 4,096, §4) is squarely in the regime where tree-based partitioning degrades toward linear scan (the curse of dimensionality, §8) — HNSW and IVF-PQ are structurally better suited to the target regime.

A3 — On-Disk Graph Index (DiskANN-Style)

+------------------+     +----------------------------+
| RAM: compressed   |     | SSD: full-precision        |
| PQ vectors +      | --> | vectors + Vamana graph      |
| graph skeleton     |    | (beam search reads pages    |
| (routing only)     |    | on demand, batched I/O)     |
+------------------+     +----------------------------+

Winning regime: corpus size exceeds single-node RAM by an order of magnitude or more, and SSD-latency (not RAM-latency) graph traversal is an acceptable tradeoff for avoiding both a RAM upgrade and horizontal sharding. Real embodying system: DiskANN (Subramanya et al. 2019). Why rejected here (for Phase 0): the on-disk beam-search graph layout and its I/O-batching strategy are a substantial independent design surface that this blueprint defers rather than folds into HNSW's Phase 3–4 scope — see PhaseDeferred("on-disk billion-scale graph index (DiskANN-style)"), §37.

A4 — GPU-Resident Brute-Force or IVF

Host RAM --DMA--> GPU device memory (vectors + coarse index)
                         |
                  massively parallel distance kernel
                  (thousands of threads, one/few per candidate)
                         |
                  top-k reduction on device --> results back to host

Winning regime: the entire dataset fits in GPU device memory and query throughput (not single-query latency) dominates the requirement — e.g., high-QPS batch similarity search. Real embodying system: FAISS-GPU (Johnson, Douze, Jégou 2019). Why rejected here (for Phase 0): GPU support adds a full additional build/dependency/ deployment dimension (a non-goal, §1) before the CPU algorithms themselves are validated and benchmarked — see PhaseDeferred("GPU-resident brute-force/IVF backend"), §37.
