In one paragraph

This design is a Rust library and command-line tool, annopt, for the graph index behind vector search: each stored vector points to a few near neighbours, and a query walks that network instead of scanning every vector (§1.1, §2.1). Its focus is the layer the reference builders (hnswlib, DiskANN) bury inside construction code: which edges to keep, how to repair reachability, and how to tune search settings until a target recall is met at the fewest distance calculations (§2.1, §2.3). It is a single-node graph index and optimizer, not a full vector database (§1.2, §1.3). Its users are vector-database, retrieval and search-performance engineers (§1.4).

The problem, concretely

Finding the exact nearest neighbours means comparing the query to every stored vector, O(N) per query. A navigable graph answers in O(log N) expected hops instead (§2.2). Building that graph naively goes wrong in three ways the blueprint spells out.

First, linking each node to its M nearest points. The blueprint's six-point example has two clusters, {A,B,C} and {D,E,F}. For point B with M=2, nearest-M gives {A, C}, both in B's own cluster, so B can reach the far cluster only through A or C. The diversity rule gives {A, D}: it trades a redundant short edge for a long-range edge across clusters (§8.6). At scale the same mistake traps greedy search in a local basin and recall stalls near 0.7 whatever the search width (P7, MM1).

Second, losing reachability without noticing. If a deleted hub orphans a cluster, queries near it return only far neighbours; regional recall falls toward zero while global recall still looks fine (P6, MM3). Orphans are invisible in mean recall and catastrophic in tail recall (MM3).

Third, an "optimization" that quietly makes things worse. A pass that raises the navigability score can still drop recall@10 from 0.95 to 0.88 with no error raised (P1). The blueprint ranks this silent recall regression as the gravest failure class because the system looks healthy (Failure Modes, F2). Tuning on wall-clock time has its own trap: a configuration that is fast on one CPU family can regress on another, which is why cost is counted in distance computations (P2, MM5).

How it works, end to end

Follow one dataset through the boxes of §3.1's diagram. The seven crates are ann-core, ann-graph, ann-build, ann-optimize, ann-search, ann-store and ann-cli (§1.5, ADR-02):

    annopt CLI : build | optimize | search | diagnose | tune | bench
        |                  |                 |              |
        v                  v                 v              v
    ann-build         ann-optimize       ann-search     RecallHarness
    HnswBuilder       GraphDiagnostics   greedy_search  (recall@k vs
    VamanaBuilder ->  occlusion_prune    beam_search     exact KNN)
    select_neighbors  degree_rebalance   SearchContext
    robust_prune      connect_components VisitedSet/heaps
        |             reverse_edge_repair    |
        |  builds         CostModel/Autotuner|  reads
        v                 ^   |              v
    ann-graph : Graph / Layer / AdjacencyList / NeighborList / CsrGraph / EntryPoint
        |  vectors + distances                 |  persist / mmap / PQ
        v                                       v
    ann-core : VectorStore · Metric · SIMD DistanceKernel · DistanceCounter
                                               ann-store : on-disk graph · mmap · ProductQuantizer · DeleteSet
  1. Substrate. ann-core holds the VectorStore (row-major f32), the Metric (L2, InnerProduct, Cosine), and DistanceKernel. Every distance goes through it, so DistanceCounter is the single cost ground truth (§3.2). Inner product and cosine are stored negated or as 1-sim, so smaller always means closer (§3.2, ADR-08, INV-5).
  2. Build. ann-build takes a VectorStore plus BuildParams and returns a mutable Graph, using HnswBuilder or VamanaBuilder. A fixed seed makes builds deterministic (§3.2, P8).
  3. Optimize. ann-optimize runs GraphDiagnostics, the pruning and repair passes, then the CostModel and Autotuner. It calls search to measure what it changes (§3.2).
  4. Freeze. The mutable Graph becomes an immutable CsrGraph. This is the one-way gate between the writer side and the reader side (§3.1).
  5. Search. ann-search reads the CsrGraph through shared & references; each search thread reuses its own SearchContext with a visited set and heaps (§3.2, INV-7, P4).
  6. Score. RecallHarness compares results to exact brute-force k-NN at every stage (§3.2).
  7. Persist. ann-store writes a version-tagged, checksummed image; mmap_graph is the only way a file enters memory (§3.2, INV-9).

The annopt CLI only orchestrates and clamps adversarial arguments (§3.2). For an HNSW query, greedy_search descends through the sparse upper layers with width 1, then spends the full ef budget only on layer 0 (§8.4, §8.8). The blueprint draws three boundaries: untrusted input is validated at the CLI and ann-core/ann-build edges, a mutable graph has one writer while the CsrGraph has many readers, and ann-store owns the disk image (§3.1).

The core ideas

Best-first search on a graph (§8.4, §8.2)

A working list W of width ef is seeded with the entry point. Repeatedly take the closest unexpanded node, look at its neighbours, add unvisited ones that beat the worst item in W (or fit while it has room), and trim W back to ef. Stop when the closest unexpanded node is farther than the worst item in W. Return the top k (§3.2, §8.3). Over the flat CsrGraph this is beam search; over HNSW layers it is greedy_search (§8.4). A visited set marks nodes, and "reset" is just bumping an epoch counter, so clearing it costs O(1) per query (§8.4, INV-8, ADR-10).

The blueprint's trace uses q(0.5,0.5), entry point A, ef=2, k=1, with edges A to {B,C}, B to {A,D} and C to {A,F} (§8.6). Costs are in distance computations:

Step Expand Newly pushed Best-2 list W Distance comps so far
0 seed A none [A:0.5] 1
1 A B(0.5), C(0.5) [A:0.5, B:0.5] 3
2 B D(40.5) unchanged, D is worse 4
3 C F unchanged 5

The search stops because the closest unexpanded node, D at 40.5, is farther than the worst item kept, 0.5. The result is A, recall@1 is 1.0, at about 5 distance computations (§8.6). Note that search_layer pushes only nodes that beat the worst of a full W, yet the trace pushes C (a tie at 0.5) and D (§8.3, §8.6).

Choosing edges: diversity, not nearest-M (§8.3, ADR-06, ADR-07, P7)

The select-neighbours heuristic (HNSW's Algorithm 4) scans candidates nearest-first and keeps e only if it is closer to the query node q than to every neighbour already kept. A dropped candidate goes to a discard pile, and keep_pruned backfills from it only if the list is still short (§8.3). This is occlusion pruning: a kept neighbour "blocks" a candidate it already routes to (§8.5, MM4).

The six-point example from B shows it (§8.6). Candidates sorted by squared distance to B: A(1), C(2), D(41), E(50), F(52).

Rule Edges kept for B Why
nearest-M {A, C} both inside B's cluster
heuristic {A, D} A is nearest; C is dropped because its distance to B is 2 and it is not closer to B than to A; D is kept because d(D,B) < d(D,A)

Vamana's RobustPrune has the same spirit with a relaxation knob alpha (§8.3). Pop the closest remaining candidate p*, add the edge, then drop any v where alpha * d(p*,v) <= d(p,v), until the node has R edges or no candidates remain. alpha = 1 is exact RNG pruning, alpha > 1 keeps long-range edges, and at very high alpha nothing is pruned and you are back to nearest-M (MM4, Glossary). The build runs two passes, alpha = 1.0 and then a value in [1.2, 1.4]. The first seeds a connected structure and the second adds long-range edges while the degree cap R holds (§8.3, ADR-07, §2.7).

Layers: a skip list over space (§8.2, §2.2)

HNSW stacks layers. layers[0] holds every node and each higher layer is a subset of the one below (§8.2). A new node's top layer is L = floor(-ln(U) * ml) with U uniform in (0,1] and ml = 1/ln(M), so the chance of reaching level ℓ or higher is exp(-ℓ/ml), with layer-0 degree cap M_max0 = 2M (§8.2). Insertion descends greedily with ef=1 to the node's level, then on each layer it owns it searches with ef_construction, picks neighbours with the heuristic, links both ways and re-prunes any neighbour that now exceeds its cap (§8.3). Vamana is the single-layer alternative: one flat graph whose entry point is the medoid (the point with the smallest summed distance to the others), with a uniform cap R (§8.2).

The optimizer: measure, change, keep or roll back (§8.5, P3, INV-6)

GraphDiagnostics is the instrument panel: mean out-degree, a degree histogram, minimum in-degree, orphan_count, connected_components, unreachable_from_ep, a sampled navigability_score (expected hops, lower is better), and estimated_recall_at_10 against exact k-NN (§8.5). The passes are occlusion_prune, degree_rebalance, reverse_edge_repair (lifts nodes with no in-edges), connect_components (links stranded subgraphs to the entry point's component) and reselect_entry_point (§8.5).

The optimizer guarantee is the contract on every pass. It must not regress recall at fixed ef on the diagnostic sample, must keep every out-degree at most R, and must leave every node reachable from the entry point after connect_components. A violating pass is rejected and the graph rolled back (§8.5, P3, ADR-12). The OptimizerGuard takes a snapshot, applies the pass, re-measures, and rolls back if recall_after < recall_before - tol (§20). The Failure Modes section fixes that tolerance at epsilon = 0.005 (Failure Modes, F2). The blueprint is not uniform here: P3 says a pass "may only improve or preserve" recall, while INV-6 and F2 allow a drop up to epsilon (P3, §7.7, F2).

Frozen reads, tombstoned writes (§8.2, P4, P11)

Building needs cheap edge edits, so the build form is an AdjacencyList with one NeighborList per node. Searching wants contiguous memory, so it is frozen into CSR (compressed sparse row): two flat arrays, offsets and edges, with node v's neighbours at edges[offsets[v] .. offsets[v+1]] (§8.2, ADR-04). The blueprint's picture: node0 [3,7,1], node1 [0,4], node2 [5,2,6] becomes offsets: [0,3,5,8,...] and edges: [3,7,1, 0,4, ...] (§8.2).

Because &CsrGraph is Send + Sync and nothing mutates it, many threads search with no locks, and the compiler rejects a design that would break this (P4, MM6). The price is that deletes cannot edit it. A delete sets a bit in the DeleteSet; edges stay; search skips tombstoned ids in results but still walks through them; a later consolidation rewrites the CSR (P11, ADR-16). The blueprint contradicts itself here: INV-2 says every edge targets a live, non-tombstoned node, while its own entry says dangling edges accumulate until consolidation (§7.1, §7.3, P11).

The cost model and the autotuner (ADR-13, P2, P12, MM2, MM8)

Cost is counted in distance computations, not seconds. The cost model is mean_dist_comps ≈ ef * mean_out_degree * (1 + hop_factor) (P2, §2.2). The blueprint's worked case (Capacity Model, item 5): ef=64, mean_out_degree=28 and hop_factor≈0.3 give ≈2,330 computations, inside the 2,500 ceiling of §4.1.

ef is the search-time recall dial and R the memory dial; the two are nearly independent, so the Autotuner bisects ef first (recall is monotone in ef) and then sweeps a coarse grid over (alpha, R, L) (MM2, ADR-13). It reports the whole recall-versus-cost Pareto frontier (the set of points no other point beats on both axes), never one magic number (P12). Recall rises fast at low ef and flattens near 1.0, and the blueprint says recall@10 = 0.99 may cost 3 to 4 times the computations of 0.95 (MM8).

The trade-offs — where engineers disagree

Graph indexes only (ADR-03)

Chosen: HNSW plus Vamana/DiskANN with NSG-style repair. The project is the quality layer over graph indexes, and LSH and trees offer no edge-pruning surface to optimize (§9). Rejected: IVF/clustering-first, LSH, and tree (KD/ball) indexes (§9). When the rejected choice is right: IVF wins for very high-cardinality, low-recall workloads (top-100 with recall@100 ≥ 0.80 acceptable) where build time must be sub-minute and the corpus is static. LSH wins for streaming high-dimensional binary/Hamming data where graph construction is too slow (§9).

Diverse edges over nearest-M (ADR-06)

Chosen: the select-neighbours heuristic with keep_pruned backfill, for diverse, navigable neighbourhoods and no recall cliff (§9, P7). Rejected: naive nearest-M (§9). When the rejected choice is right: data where the diversity property is already present (the ADR's example is a synthetic uniform hypercube), or a build that must be twice as fast with a recall target of only ≥ 0.80. The diversity benefit is largest near recall ≥ 0.95 (§9).

Two-pass alpha for Vamana (ADR-07)

Chosen: robust_prune with alpha = 1.0 then a value in [1.2, 1.4] (§9). Rejected: a single pass, or alpha = 1 only (§9). When the rejected choice is right: low-dimensional data (≤ 32 dimensions) or near-uniform data, where the strict relative-neighbourhood rule alone gives a navigable graph (§9).

A hard safety gate on every pass (ADR-12)

Chosen: passes may only improve or preserve recall, with degree at most R and reachability kept. The gate runs RecallHarness and a reachability check before commit, else rolls back (§9). Rejected: best-effort pruning, or trusting the heuristic (§9). When the rejected choice is right: datasets so large (≥ 100M) that a harness run per pass is too expensive and the heuristic is known-good from offline validation. Offline A/B recall measurement then replaces the gate (§9).

Tombstones, not in-place deletes (ADR-16)

Chosen: a DeleteSet bitset plus lazy relink and periodic consolidation. In-place deletes fragment the CSR and break reachability mid-query (§9, P11). Rejected: in-place edge removal, or an immediate rebuild per delete (§9). When the rejected choice is right: an offline batch setting where deletes arrive in bulk at a known quiet time (say nightly) and hours of recall drift from stale tombstones is unacceptable (§9).

Roads not taken (Alternative Architectures, §1.7)

IVF / clustering-first wins on static corpora with sub-minute builds, recall targets of at most 0.90, very high N (≥ 100M) on limited RAM, or filtered search; FAISS IndexIVFPQ is the real system. It loses here because it has no edge topology to optimize (Alternative Architectures, Alt-1).

LSH with post-filtering wins on high-dimensional binary or Hamming data and on streaming data, at very high throughput with low precision needs (top-100 recall ≥ 0.70). It loses here because a hash table gives the optimizer nothing to prune or repair (Alternative Architectures, Alt-2).

Learned routing wins on a static corpus with a fixed query distribution where a learned router can shrink the search space. It loses here because it adds a training dependency outside the trust boundary and makes the optimizer's gains unattributable (Alternative Architectures, Alt-3, ADR-13).

Deferred features (§1.7) are GPU kernels, distributed or sharded indexes, disk-resident billion-scale beyond one node's mmap, and filtered search, each behind a PhaseDeferred gate. The gates point at §13, §14, §24 and §17, the Phase 1, 2, 12 and 5 sections; the first two (SIMD kernels, graph representation) are not about GPU or distributed indexes (§1.7, §13, §14).

What must never be false

Each invariant is a row in §7.1; GraphDiagnostics is the standing observability surface and annopt diagnose re-checks all of them (§7).

  • INV-1: a NeighborList is sorted nearest-first and no longer than R. Noticed by a degree-histogram bucket above R and a verify_sorted() scan; out_degree_hist (§7.2).
  • INV-2: every edge targets a live node. Noticed by diagnose counting edges into the DeleteSet; dangling_edge_count (§7.3).
  • INV-3: all live nodes are reachable from the entry point. Noticed by union-find and a reachability scan; unreachable_from_ep (§7.4).
  • INV-4: an HNSW node on level L is on every lower layer, and the entry point is on the top layer. Noticed by a per-layer subset check (§7.5).
  • INV-5: smaller distance always means closer, for every metric and heap. Noticed by the metric_monotone property test; there is no steady-state telemetry (§7.6).
  • INV-6: no pass reduces sampled recall@k at fixed ef. Noticed by a RecallHarness diff and a CI gate; estimated_recall_at_10 per pass (§7.7).
  • INV-7: search is a pure read of the CsrGraph and allocates nothing in steady state. Noticed by a dhat allocation-count test; alloc_count_per_query (§7.8).
  • INV-8: the visited set never leaks state between queries. Noticed by running query A then B on one context and comparing B with B on a fresh one; visited_full_reset_count (§7.9).
  • INV-9: save, mmap and search gives bit-identical results to in-memory search. Noticed by a round-trip differential test and the header checksum (§7.10).
  • INV-10: robust_prune and the heuristic always terminate and respect R. Noticed by fuzzing with a watchdog and an out_degree <= R post-condition (§7.11).
  • INV-11 and INV-12: DistanceCounter only rises within a query, and CSR offsets have length n+1, never decrease, and end at edges.len(). Noticed by a test hook against kernel calls and by a structural scan in diagnose and at load (§7.12).

What breaks in production

Severity: SEV1 is silent-wrong-or-data-loss, SEV2 unavailability, SEV3 degraded (Failure Modes). These sections name a library ann-index and a CLI annox, not the seven crates or annopt of §1.5 (Failure Modes, T13).

F2: silent recall regression (SEV1). Symptom: search returns k results with no error, but recall@10 has fallen below 0.95. Causes: over-aggressive pruning, alpha too low, an under-trained PQ codebook, a tombstone leak, stale tuner ground truth, a stale entry point. Detection is continuous: a PassReport per pass, a shadow evaluation of 1,000 held-out queries against brute_force_knn, PQ-rerank recall@10 ≥ 0.90. Recovery: the transactional pass framework reverts to the pre-pass CSR; the playbook first rules out stale ground truth, then bisects the pipeline stage by stage (Failure Modes, F2).

F8: connectivity loss (SEV1). Symptom: some live nodes are never returned for any query, so recall caps below 1.0 at any ef. Cause: an over-prune severs a last in-edge, the entry point or medoid is deleted without re-election, or an approximation wrongly skips a needed node. Detection: a reachability scan from the entry point. Recovery: ConnectivityRepair re-links orphans and the entry point is re-elected (Failure Modes, F8; INV-3).

F5: concurrency anomaly (SEV1). Symptom: a torn neighbour list, a missing recent insert, or a use-after-free risk, because a reader sees a half-updated list or consolidation frees a node under a live searcher. Detection: loom and ThreadSanitizer. Prevention: an immutable or epoch-protected graph for readers, per-node locks for writers, frees only after readers retire; a bug falls back to a coarse RwLock mode flag (Failure Modes, F5).

F4: crash mid-operation (SEV2). Symptom: partial index file after a build, consolidate or save. Cause: power loss or OOM-kill between mutation and fsync. Detection on open(): magic, version, CRC and a trailing commit record. Recovery: saves go to a temp file, fsync, then atomic rename, so a missing or bad commit record falls back to the last valid snapshot (Failure Modes, F4; Threat Model T8).

F7: performance cliff (SEV3). Symptom: p99 jumps from under 3 ms to tens of ms while recall stays steady, because ef_search drifted up, mmap pages are cold, or inserts and deletes fragmented the graph. Detection: latency histograms and a page-fault counter. Recovery: ef pinned to the Pareto point, a warm-up scan, LayoutReorder and Compact (Failure Modes, F7). The "under 3 ms" baseline conflicts with the p99 target of < 1 ms in §4.1.

Threats worth knowing (Threat Model):

  • T1, parameter blow-up (a huge ef_search, degree, dim or order), is stopped by rejecting values above the §4.2 caps before any allocation, returning a typed error with no partial state (T1, §4.2).
  • T7, untrusted index-file bytes, is met by header magic, version, per-section CRC32C and a bounds check on every CSR offset and neighbour id. A failing file is refused and the last good snapshot used (T7).
  • T10, an adversarial delete or prune sequence that orphans live nodes, is met by the reachability invariant. Alert on unreachable_live_total > 0 and watch a brute-force canary (T10, INV-3).
  • T11, stale or poisoned PQ codebooks and manipulated tuning data, is met by binding codebooks to the index generation, always re-ranking in full precision, and deriving ground truth from brute force (T11).

  • Timeline. §1.8 puts Phase 0 at 6 to 14 weeks; Appendix B's table gives it 1 week, while its closing note counts "Phase-0 done" as roughly Phases 0 to 7 (§1.8, Appendix B).

How it compares

  • hnswlib is HNSW only, in RAM, with no post-build optimizer and no first-class delete. Its recall/latency ratio in RAM is excellent, and it is this design's differential-test baseline (ADR-19, Comparative Architecture Table).
  • FAISS IndexHNSW is Meta's production library: HNSW embedded in a larger index factory with GPU and IVF-PQ paths, the graph fixed after build. This design borrows its PQ with asymmetric distance and uses it as a differential oracle (Comparative Architecture Table).
  • DiskANN is the SSD-resident billion-scale index: a flat Vamana graph on SSD, PQ codes in RAM and full-precision rerank. Its alpha, R and L are build-time choices with no post-build optimizer; Phases 6 and 12 implement this design (Comparative Architecture Table).
  • NGT builds a neighbour graph, then optimizes degrees and paths in a separate pass, the closest analogue to this optimizer. It lacks tombstone deletes and a Pareto tuner (Comparative Architecture Table).
  • ScaNN is not graph-based: tree partitioning plus anisotropic quantization. It is out of scope (ADR-03) and strong on some corpora because of quantization quality (Comparative Architecture Table).

Two conflicts inside the plan. If you only remember three things

A graph index lives or dies on which edges it keeps, so choose diverse neighbours, never the nearest M (P7, ADR-06). Every change to the graph is measured against exact k-NN and rolled back if recall drops, because the worst failure is the one that raises no error (P3, ADR-12, Failure Modes F2). Cost is counted in distance computations, and the tuner hands back a whole recall-versus-cost curve rather than one setting (P2, P12, ADR-13).

Words used here

  • Recall@k: the fraction of the true k nearest neighbours that a search returns, scored against an exact oracle (Glossary, ADR-17).
  • Graph index: vectors as nodes, each with a short list of neighbour edges, searched by walking edges (§1.1, §8.2).
  • Entry point: the node every search starts from; HNSW's top-layer node or the medoid (Glossary, §8.2).
  • ef: how wide the working list is during search; the main recall-versus-latency dial (Glossary, MM2).
  • HNSW: a stack of layers, sparse on top and dense on layer 0, searched top to bottom (Glossary, §8.2).
  • Occlusion pruning: dropping an edge because a kept neighbour already routes to the same place (Glossary, MM4).
  • alpha: the relaxation factor (≥ 1) that lets some long edges survive pruning (Glossary, §8.3).
  • CSR: the frozen two-array graph layout, offsets plus edges, that readers share without locks (Glossary, §8.2).
  • Tombstone: a logical delete marker; the physical removal waits for consolidation (Glossary, ADR-16).
  • Product quantization (PQ): compressing vectors into short codebook codes, with full-precision re-ranking at the end (Glossary, ADR-14).
  • Distance computation: one counted distance() call, the system's cost unit (Glossary, P2).
