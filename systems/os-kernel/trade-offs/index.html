Decisions (§9) · 32 ADRs

ADR-01

Implementation language

Chosen

Rust nightly, #![no_std]

Rejected

C, C++, Zig

When the rejected choice is right

a one-off research kernel with no safety budget at all — C avoids the toolchain tax

Why: memory safety in privileged code (P2)

ADR-02

Target architecture

Chosen

x86_64 first, aarch64 stretch

Rejected

i686, riscv64

When the rejected choice is right

riscv64 wins for an open-ISA teaching kernel with no legacy-mode baggage

Why: largest QEMU/tooling pool, cheapest verifiable hardware

ADR-03

Bootloader

Chosen

custom UEFI stub + multiboot2 fallback

Rejected

GRUB only, Limine only

When the rejected choice is right

GRUB wins when multi-OS chainloading is a hard requirement

Why: UEFI is the modern path; multiboot2 keeps QEMU iteration cheap

ADR-04

Build system

Chosen

cargo workspace + Makefile wrappers

Rejected

meson, bazel, raw rustc

When the rejected choice is right

bazel wins at a scale with 50+ interdependent build graphs across languages

Why: native to the language; CI is trivial

ADR-05

Custom target spec

Chosen

x86_64-allvest.json, no SSE in kernel

Rejected

x86_64-unknown-none

When the rejected choice is right

the stock target wins once kernel-mode SIMD (e.g. AES-NI crypto) is required

Why: avoids lazy FPU-state save cost in kernel mode

ADR-06

Address-space model

Chosen

higher-half kernel (0xFFFF_FFFF_8000_0000+)

Rejected

identity-mapped, lower-half, single-address-space (Theseus-shaped)

When the rejected choice is right

a single-address-space model wins for a language-safe, no-fork embedded target (Theseus)

Why: standard for x86_64; matches Linux/xv6 convention; supports per-process fork/COW

ADR-07

Physical frame allocator

Chosen

bitmap, then buddy

Rejected

freelist-only, slab-only

When the rejected choice is right

a freelist wins for a fixed-size-only embedded allocator with no fragmentation risk

Why: bitmap is simplest-correct; buddy is the natural follow-up for fragmentation

ADR-08

Kernel heap

Chosen

linked-list, then slab

Rejected

dlmalloc port, jemalloc port

When the rejected choice is right

jemalloc wins once multi-threaded allocation contention dominates (not our Phase-0 regime)

Why: linked-list is a correct Phase-0 fixture; slab is the canonical fixed-object follow-up (Bonwick 1994)

ADR-09

Page-table API

Chosen

per-arch Mapper trait

Rejected

macro-generated tables, recursive mapping trick

When the rejected choice is right

recursive mapping wins for a single-CPU, no-port-planned toy kernel

Why: trait keeps an aarch64 port honest; avoids SMP-unsafe recursive mapping

ADR-10

Interrupt controller

Chosen

xAPIC, x2APIC stretch

Rejected

legacy 8259 PIC

When the rejected choice is right

the 8259 PIC wins on pre-APIC hardware (irrelevant to our x86_64 target)

Why: PIC is masked at boot; xAPIC is the modern per-CPU path

ADR-11

Timer

Chosen

LAPIC timer + invariant TSC

Rejected

HPET, PIT

When the rejected choice is right

HPET wins when the TSC is non-invariant (pre-Nehalem or unexposed in a VM)

Why: LAPIC is per-CPU; TSC read is a single instruction

ADR-12

Scheduler

Chosen

per-CPU run-queue, MLFQ-lite

Rejected

global round-robin, CFS-clone

When the rejected choice is right

a global run-queue wins at ≤2 cores where balancing cost exceeds contention cost

Why: per-CPU avoids cache-line bouncing past 8 cores (Boyd-Wickizer 2010); MLFQ-lite suffices for Phase 0

ADR-13

Locking

Chosen

Spinlock/IRQ-safe variant; sleeping Mutex from Phase 5

Rejected

parking_lot, kernel RWLock everywhere

When the rejected choice is right

a sleeping lock wins whenever the critical section may block on I/O

Why: spinlocks are correct for short critical sections; sleeping locks need the scheduler online

37. Alternative Architectures (Roads Not Taken)

Alt-1 — Microkernel (seL4-shaped).

 user:  [ VFS server ] [ driver: virtio-blk ] [ driver: uart ]
              \              |                    /
               \             |                   /
                +--- capability-checked IPC ---+
                              |
                      [ microkernel: IPC,
                        scheduling, capabilities ]

Regime where it wins: security-critical or safety-critical deployments needing provable blast-radius bounds per component (avionics, medical, formally verified enclaves). Real system: seL4 (Klein et al., SOSP 2009). Rejected here because Phase 0–12's goal is teaching the full monolithic-kernel surface (§2) — pushing VFS/drivers to user-space would remove exactly the material (direct driver/VFS/scheduler interaction) this project exists to teach, and the IPC-marshaling engineering cost would roughly double the phase count for no scope gain at this project's size.

Alt-2 — Exokernel (Aegis-shaped).

 user: [ LibOS A: its own VM/scheduler ] [ LibOS B: its own VM/scheduler ]
              \                                    /
               +------ exokernel: hardware --------+
                     multiplexing only (no abstraction)

Regime where it wins: research systems needing per-application control over resource-management policy (custom pagers, custom schedulers) without kernel-imposed abstraction overhead. Real system: MIT Aegis/Exokernel (Engler, Kaashoek, O'Toole, SOSP 1995). Rejected here because a single opinionated VM/scheduler abstraction is exactly what lets Phase 0–12 ship one coherent syscall ABI and one conformance suite — an exokernel pushes that design work onto every LibOS, which this project's single user-space target does not need.

Alt-3 — Single-address-space / unikernel (Theseus-shaped).

 +-----------------------------------------------------+
 |  one address space: kernel code + all "process"      |
 |  logic as cooperatively-scheduled tasks, no fork/exec |
 +-----------------------------------------------------+

Regime where it wins: embedded or cloud-unikernel targets where a single trusted application is compiled directly against kernel internals for minimum overhead and maximum inlining/optimization opportunity. Real system: Theseus OS (Boos et al., OSDI 2020). Rejected here because it structurally cannot support the fork/COW model locked in ADR-06 — a single address space has no cross-process isolation boundary to speak of, which breaks I1/I2 and the entire process/thread teaching goal (§2).

Alt-4 — Multikernel (Barrelfish-shaped).

 CPU0: [ kernel replica | local state ]  <--messages-->
 CPU1: [ kernel replica | local state ]  <--messages-->
 CPU2: [ kernel replica | local state ]  <--messages-->
        (no shared kernel state; agreement via explicit messages)

Regime where it wins: very-high-core-count or heterogeneous-ISA systems where cache-coherent shared-memory coordination itself becomes the bottleneck (§32's named ceiling of ~32 CPUs before shootdown/load-balancing overhead dominates). Real system: Barrelfish / The Multikernel (Baumann et al., SOSP 2009). Rejected here because Phase 0–12 targets a single-socket, ≤128-logical-CPU reference rig (§4) where shared-memory SMP with per-CPU run-queues (ADR-12) is simpler to build and teach, and the message-passing agreement protocol a multikernel requires is exactly the kind of distributed-systems complexity this project defers to its distributed-systems siblings in the portfolio.
