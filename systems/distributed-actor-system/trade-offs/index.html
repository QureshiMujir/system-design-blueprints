Decisions (§9) · 30 ADRs

ADR-001

Language

Chosen

Rust 2021 ≥1.78

Rejected

Erlang, C/C++, Go

When the rejected choice is right

Go wins for rapid-prototype actor sketches where the runtime is a library, not the goal; C wins for embedded targets without a stable Rust target; Erlang wins if you want live upgrade + OTP behaviors out-of-the-box and can accept GC pauses

Why: static no-shared-state (I2) via ownership; no GC pauses; loom/Miri/fuzz; building the runtime so Erlang is out

ADR-002

Scheduler model

Chosen

M:N, thread-per-core, work-stealing, reduction-count preemption

Rejected

OS-thread-per-actor; pure Tokio

When the rejected choice is right

OS-thread-per-actor wins when actor count is ≤ 10k, each runs blocking I/O, and scheduling overhead matters more than raw scalability; pure Tokio wins if you piggyback on the Tokio ecosystem and never need custom preemption semantics

Why: millions of actors need M:N; explicit reductions give Erlang-style fairness Tokio doesn't expose (#54/#129/#131)

ADR-003

Async core

Chosen

hand-rolled minimal executor over Future/Waker (or thin Tokio for IO only)

Rejected

full Tokio scheduler

When the rejected choice is right

Full Tokio wins when the team size is small and the scheduler model doesn't need preemption customization — you get the entire async ecosystem for free with no scheduler maintenance burden

Why: need control of preemption + run-queues; reuse Tokio only for the TCP reactor

ADR-004

Mailbox

Chosen

lock-free bounded MPSC (crossbeam-style), per-actor

Rejected

global lock; unbounded channel

When the rejected choice is right

Unbounded channel wins when the producer-consumer rate mismatch is provably bounded by the application contract (e.g. a fixed-rate sensor feed); global lock wins if simplicity trumps throughput at small actor counts

Why: wait-free producer; bounded → backpressure (I8); no global contention

ADR-005

Payload serialization

Chosen

bincode-fixed for internal; tagged user payloads (CBOR/MessagePack option)

Rejected

JSON; language-native (serde-only)

When the rejected choice is right

JSON wins when human-readable debugging, interoperability with browser/HTTP endpoints, or schema-free exploratory development outweighs throughput; serde-only wins for pure single-language deployments where versioning is never a concern

Why: compact + fast internal frames; self-describing option for user msgs; type-tag → deserializer

ADR-006

Wire framing

Chosen

length-prefixed binary frames, magic+version header

Rejected

text protocol; gRPC/protobuf

When the rejected choice is right

gRPC/protobuf wins when you need language-agnostic clients, rich IDL, built-in flow control, and HTTP/2 multiplexing — i.e. the cluster is not homogeneous Rust; text protocol wins for pure debuggability in resource-constrained environments

Why: minimal overhead; versioned handshake; full control (contrast #155 gRPC)

ADR-007

Transport

Chosen

one TCP connection per peer, multiplexed

Rejected

UDP for data; QUIC; conn-per-message

When the rejected choice is right

QUIC wins when connections cross NAT, connection migration matters (mobile), or head-of-line blocking at the TCP level is a measured problem; UDP wins for detection-heartbeat-only traffic where loss tolerance is designed in

Why: TCP gives in-order reliable per-pair FIFO (I4); single conn amortizes handshake

ADR-008

Membership

Chosen

SWIM (ping + ping-req + gossip)

Rejected

full gossip-everything; central registry; Raft membership

When the rejected choice is right

Central registry wins for small clusters (≤ 20 nodes) where operational simplicity beats scalability; Raft membership wins when you need strongly-consistent membership (CP) and can accept the leader bottleneck

Why: scalable O(1) per-node per-period load, O(log N) convergence (Das 2002); AP

ADR-009

Failure detection

Chosen

phi-accrual (continuous φ)

Rejected

fixed binary timeout

When the rejected choice is right

Fixed binary timeout wins in very low-jitter networks (datacenter with HW timestamps) where the simplicity of a single threshold and the low implementation risk outweigh adaptivity

Why: adaptive to jitter; tunable false-positive rate (Hayashibara 2004)

ADR-010

Consistency posture

Chosen

AP (available under partition, surface split-brain)

Rejected

CP via Raft

When the rejected choice is right

CP wins when split-brain correctness is non-negotiable (e.g. a payment ledger, a distributed lock); tolerable data divergence is the wrong tradeoff there

Why: actor systems prioritize availability; consensus is #42's job (principle 8)

ADR-011

Delivery semantics

Chosen

at-most-once default; opt-in at-least-once + dedup

Rejected

exactly-once "guarantee"

When the rejected choice is right

ALO-everywhere wins when every message is a command with side effects and idempotency is cheap; at-most-once is wrong when loss would corrupt application state (use ALO + idempotent handler in that case)

Why: Erlang semantics; exactly-once is impossible without dedup+idempotency (principle 8)

ADR-012

Supervision

Chosen

tree + one-for-one/all/rest-for-one + intensity

Rejected

flat error returns; exceptions only

When the rejected choice is right

Flat error returns win in library code where the caller owns error handling and supervision overhead is undesirable; exception-based recovery wins in languages where exceptions are idiomatic and actor-model isolation is not available

Why: OTP fault model; isolates + bounds crashes (I9/I10)

ADR-013

Identity

Chosen

Pid{node,incarnation,local_id}

Rejected

UUID-only; name-only

When the rejected choice is right

UUID-only wins when global uniqueness without any coordination is required across an arbitrary number of independent namespaces; name-only wins in small static clusters where human-readable ids matter more than lifetime safety

Why: incarnation defeats stale-ref resurrection (I13); cheap + total order per node

ADR-014

Backpressure

Chosen

per-mailbox policy (Block/DropNewest/DropOldest/Fail)

Rejected

always-block; always-drop

When the rejected choice is right

Always-drop wins for pure telemetry/monitoring pipelines where data freshness matters more than completeness; always-block wins when all producers are co-located and thread-blocking is cheap

Why: configurable per actor class; bounded memory (I8)

ADR-015

Concurrency testing

Chosen

loom on mailbox + scheduler claim

Rejected

stress-test only

When the rejected choice is right

Stress-test-only wins when loom's state-space explosion makes exhaustive checking impractical for the model complexity; complement with property-based concurrency tests

Why: exhaustive interleaving model-check (I1/I4)

ADR-016

Fuzzing

Chosen

cargo fuzz on frame decoder + envelope parse

Rejected

none; property tests only

When the rejected choice is right

Property tests only win when the input space is well-constrained by the type system and arbitrary byte injection is provably impossible (e.g. internal-only codec behind a TLS + auth layer)

Why: never-panic on hostile bytes (I6)

ADR-017

Sanitizers

Chosen

Miri on lock-free unsafe paths

Rejected

none

When the rejected choice is right

Skipping Miri wins only when all unsafe code is eliminated entirely (a safe abstraction boundary hides it) and the performance cost of Miri in CI is prohibitive

Why: UB-free atomics/queue

ADR-018

Worker parking

Chosen

futex/condvar park when no ready cells

Rejected

busy-spin

When the rejected choice is right

Busy-spin wins for ultra-low-latency real-time systems (HPC, trading) where the 1–10 µs wake latency of a condvar is unacceptable and CPU waste is tolerable

Why: ≤1% idle CPU; latency on wake acceptable

ADR-019

Timers / heartbeats

Chosen

hashed-wheel timer per node

Rejected

per-actor OS timer

When the rejected choice is right

Per-actor OS timer wins at low actor counts (≤ 10k) where each actor has distinct, independently-managed timeouts and OS timer resolution is not a bottleneck

Why: scalable scheduling of heartbeats/timeouts at millions of actors

ADR-020

CLI / control

Chosen

actd daemon + act CLI over a local UDS control socket

Rejected

embed-only

When the rejected choice is right

Embed-only wins for tightly sandboxed deployments (e.g. WebAssembly, embedded firmware) where a daemon and UDS are not available

Why: ops inspection (members/ps/tree/send)

ADR-021

Config

Chosen

typed config (TOML) + env override; pinned defaults

Rejected

adhoc flags

When the rejected choice is right

Adhoc flags win for a tiny CLI tool with ≤5 knobs where TOML parsing overhead and a config file are unwarranted

Why: reproducible cluster config

ADR-022

Logging/metrics/tracing

Chosen

tracing spans + structured logs + metrics registry

Rejected

println

When the rejected choice is right

println wins for a throwaway prototype or a tiny embedded system where the tracing crate's dependency weight is prohibitive

Why: observability-first (principle 14)

ADR-023

Build / deps

Chosen

minimal, pinned, cargo deny, Cargo.lock

Rejected

many deps

When the rejected choice is right

Many-deps wins when ecosystem velocity and feature richness matter more than supply-chain auditability — early-stage products that iterate fast and audit later

Why: supply chain; reproducible

ADR-024

Versioning

Chosen

SemVer on wire (handshake-negotiated) + public API

Rejected

implicit

When the rejected choice is right

Implicit versioning wins for single-binary deployments where all nodes are upgraded atomically and the rolling-upgrade window is never required

Why: rolling-upgrade safety (principle 15)

ADR-025

Reproducibility

Chosen

pinned toolchain, deterministic per-actor execution

Rejected

floating

When the rejected choice is right

Floating toolchain wins for rapid prototyping when replay and bit-identical builds are not required; reproducibility is a production requirement, not a prototype one

Why: enables #344 replay (I1)

ADR-026

Fault model

Chosen

crash-fault (non-Byzantine), fail-stop assumed

Rejected

BFT

When the rejected choice is right

BFT wins when nodes are operated by mutually-untrusting parties (public blockchain, multi-organization consensus) and the 3f+1 cost is acceptable

Why: stated assumption; BFT (PBFT) out of scope (Threat Model)

ADR-027

Actor placement

Chosen

explicit spawn-on-node + optional consistent-hash ring

Rejected

virtual actors (Orleans)

When the rejected choice is right

Virtual actors win when the caller should not need to know or care which node an actor lives on (large-scale grain-style systems like Orleans or Cloudflare Durable Objects)

Why: explicit control; ring is additive (riak_core idea)

ADR-028

Hot code loading

Chosen

seams only (behavior swap point)

Rejected

implement now

When the rejected choice is right

Implement-now wins when the system must support zero-downtime upgrades of actor business logic without restarting the node — the primary Erlang/OTP use case

Why: live upgrade is #342 (PhaseDeferred("FD-1"))

ADR-029

Durability

Chosen

none in core; ALO buffers in-memory

Rejected

WAL/journal now

When the rejected choice is right

WAL/journal wins when at-least-once guarantees must survive a sender crash — durable execution (event sourcing, Temporal-style) requires persisted state

Why: durable execution is #163 (PhaseDeferred("FD-2"))

ADR-030

Bench harness

Chosen

criterion (msg latency, spawn, throughput)

Rejected

none

When the rejected choice is right

Skipping a bench harness wins only for a library that ships no perf SLOs and has no CI regression gates; this runtime has both

Why: §4 targets, perf regression gate

Alternative Architectures (Roads Not Taken)

Alt-1 — Shared-Memory Message Bus (Go-Style CSP Channels)

goroutines / green-threads
  │  send(ch, msg)
  ▼
  [channel buffer]   ← shared memory, GC-managed
  │  recv(ch)
  ▼
goroutine B (any goroutine can own B's "state" if not disciplined)

Regime where it wins: Co-located services on a single host where goroutine-level channels (Go chan) provide cheap and ergonomic CSP-style concurrency without the overhead of actor message serialization or mailbox allocation. Works well when the concurrency domain is bounded (100s–10ks of goroutines) and the performance ceiling of a global GC is acceptable.

Real system: Go's standard library and Kubernetes scheduler use goroutines + channels. The Go runtime does not enforce private state — the programmer must discipline themselves.

Why rejected: (a) Go's GC introduces unpredictable latency spikes incompatible with the latency targets (p99 ≤ 10 µs local). (b) Channels do not enforce ownership — shared mutable state is possible and common (the bug class the actor model eliminates). (c) No built-in supervision tree — fault handling is if err != nil everywhere. (d) Distribution requires bolting on gRPC or similar (no location transparency). This architecture trades safety and fault isolation for simplicity at small scale.

Alt-2 — Persistent Actor Model with WAL-Backed State (Event-Sourcing Style)

Actor A
  │  handle(msg) → emit(Event) → persist to WAL (disk)
  ▼              ← replay WAL on restart (no state loss)
  [durable state]     ← actor survives crashes AND node restarts

Regime where it wins: Financial and transactional systems where actor state must survive node restarts (not just within-session crashes). The durable execution model (Temporal, Akka Persistence, Durable Objects) gives effectively-once processing end-to-end because the actor's state and its message acknowledgements are co-committed to durable storage.

Real system: Akka Persistence (event sourcing, LevelDB/Cassandra backend), Microsoft Durable Task Framework, Cloudflare Durable Objects (V8 isolate + SQLite).

Why rejected: Durable persistence introduces a write-ahead log on every state transition, turning a sub-microsecond local message into a storage-bound operation. This fundamentally changes the latency model (p50 goes from 1 µs to 10s of µs or more) and makes the cell-overhead budget meaningless at millions of actors. The explicit non-goal is captured in ADR-029 and PhaseDeferred("FD-2") — this runtime is the non-durable layer; #163 (Durable Execution) adds the WAL layer on top.

Alt-3 — Virtual Actor Model (Orleans-Style, Automatic Placement)

Client call: grain_ref("account-42").deposit(100)
    │  (caller does not know or care which node activates it)
    ▼
Orleans runtime: is grain-42 active? → no → activate on node X
    │  route call to node X
    ▼
Grain-42 on node X  (single-activation guaranteed by runtime)

Regime where it wins: Large-scale cloud services where the actor count is huge (millions of unique entities), activation is dynamic and unpredictable, and the caller should not need to specify or know actor placement. Orleans' virtual-actor model provides "stateful serverless" ergonomics: callers just invoke a grain ID, the runtime handles activation, deactivation, and location.

Real system: Microsoft Orleans (.NET), Cloudflare Durable Objects, Halo's matchmaking service originally used Orleans at scale.

Why rejected: Single-activation guarantees require a coordination protocol at the placement layer (a consistent registry or a CP membership protocol) — this introduces the consensus overhead this runtime deliberately avoids (ADR-010). Explicit placement (ADR-027) is the right choice for telecom-style systems where the application architect knows and controls actor topology. The virtual-actor model is noted in the Comparative Architecture Table.

Alt-4 — Shared-Nothing Message Bus (Kafka-Style Partitioned Log)

Producer actors → write to Topic[partition=hash(key)]
    │  (durable, replicated, ordered per partition)
    ▼
Partition leader (broker) → replicates to followers (ISR)
    │  consumer groups pull at their own pace
    ▼
Consumer actors → process + commit offset

Regime where it wins: Systems where the primary requirement is durable, ordered, multi-consumer fan-out of messages — audit logs, event sourcing pipelines, CDC (change data capture), stream processing. Kafka is CP (ISR replication + controller epoch) on the durability axis, providing at-least-once delivery with exactly-once achievable via transactional producers + idempotent consumers.

Real system: Apache Kafka (LinkedIn, 2011), Confluent Platform, AWS MSK. Used in Uber (trip events), LinkedIn (activity streams), Netflix (operational data pipeline).

Why rejected: Kafka is a durable log broker, not an actor runtime. It does not provide: actor addressing (Pid/ActorRef), supervision trees, failure detection (phi-accrual), location transparency, or per-actor behavioral encapsulation. Sending a "message to actor X" requires knowing which partition X's messages land in. Cross-actor interactions (A sends to B which replies to C) become complex routing graphs in Kafka, not simple ActorRef sends. This runtime's use case — building a concurrent fault-tolerant application runtime with millions of in-memory actors — is orthogonal to Kafka's log-durability use case.
