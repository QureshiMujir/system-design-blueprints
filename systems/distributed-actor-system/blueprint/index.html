343 — Distributed Actor System (Erlang/Akka-like) from Scratch

Project Number: 343

Project Name: Distributed Actor System (Erlang/Akka-like) from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal

Build a distributed actor runtime in the Erlang/OTP and Akka tradition: lightweight actors (private mutable state + behavior + mailbox) that communicate only by asynchronous message passing, scheduled M:N over a thread-per-core pool, organized into supervision trees ("let it crash" + bounded restarts), addressed by location-transparent references (ActorRef/PID) that work identically local or remote, and clustered across nodes with SWIM membership + phi-accrual failure detection over a custom TCP wire protocol. Delivery is at-most-once by default (Erlang semantics), with documented at-least-once + dedup + ordering extensions. Output: act-runtime library + actd node daemon + act CLI that spawn millions of actors, supervise them, and pass messages within and across nodes.

In scope: actor trait + lifecycle (spawn/stop/restart); private-state, one-message-at-a-time processing (no concurrent handling per actor); lock-free bounded mailboxes + backpressure; M:N reduction-counting fair scheduler (Erlang-style preemption) over a thread-per-core executor; links + monitors + exit signals; supervision trees with one-for-one / one-for-all / rest-for-one strategies + restart-intensity limits; ActorRef/PID addressing with location transparency; binary wire protocol (framing + message serialization + handshake) over TCP; cluster membership (SWIM) + node join/leave; failure detection (phi-accrual) + remote-ref invalidation + split-brain awareness; delivery-semantics layer (at-most-once default; opt-in at-least-once with dedup + per-sender FIFO ordering).

Explicit non-goals (see Deferred Features Register; each anchored PhaseDeferred("FD-#")): hot code loading / live upgrade — that is #342 (PhaseDeferred("FD-1"), this runtime exposes the seams but does not implement code swap); durable execution / persistent actor journaling — that is #163 (PhaseDeferred("FD-2"), at-least-once here is in-memory + redelivery, not durable WAL); deterministic record/replay debugging — that is #344 (PhaseDeferred("FD-3"), we emit the event log it consumes); a full OTP behavior library (gen_server/gen_statem/gen_event, ETS, mnesia) beyond the actor + supervisor core (PhaseDeferred("FD-5")); consensus / strongly-consistent replicated state — cross-link #42 Raft (PhaseDeferred("FD-4")); cross-datacenter WAN federation + TLS/auth hardening beyond the threat-model baseline (PhaseDeferred("FD-7")/PhaseDeferred("FD-6")); a surface language / DSL — actors are plain Rust types implementing a trait.

Deployment model: act-runtime library crate embedded in an application; actd daemon = one OS process = one cluster node hosting many actors + the transport/membership/detector loops; act CLI for cluster inspection (act members, act ps, act tree, act send). A cluster = N actd processes on N hosts connected pairwise by TCP. No external broker, no shared database — the cluster is the system.

Target users: backend engineers building concurrent/fault-tolerant services (telecom-style "nine nines" lineage); distributed-systems learners building the membership→detection→delivery stack; runtime/scheduler engineers (cross-link #54/#129/#131); anyone who wants Erlang semantics with Rust safety + performance.

Phase 0 deliverable (crates/modules):

  1. act-types — Pid, ActorRef, Message, Envelope, ActorError, ExitReason, MailboxFull.
  2. act-mailbox — single-threaded bounded MPSC mailbox + enqueue/dequeue (lock-free path lands P2).
  3. act-actor — Actor trait (handle, lifecycle hooks) + Context (spawn/send/self).
  4. act-runtime — single-thread executor: spawn, mailbox run-loop, send, stop (M:N scheduler lands P1).
  5. act-cli (act) — spawn a demo actor tree, send messages, observe one-message-at-a-time ordering.

Later phases unlock: M:N reduction-fair scheduler (Phase 1), lock-free bounded mailbox + backpressure (Phase 2), links/monitors/exit signals (Phase 3), supervision trees + strategies (Phase 4), location-transparent addressing (Phase 5), wire protocol + serialization (Phase 6), TCP transport + remote send + handshake (Phase 7), SWIM membership (Phase 8), phi-accrual detection + remote-ref failure + split-brain (Phase 9), delivery semantics + dedup + ordering (Phase 10), hardening/fuzz/loom/chaos (Phase 11), soak + perf (millions of actors) + release (Phase 12).

Timeline: Phase 0 = 6–14 weeks (executor + mailbox + actor trait is the conceptual core); full = 8–13 months (distribution: wire protocol + SWIM + phi-accrual + delivery semantics are the long pole, each a subsystem with its own correctness story).

Recommended language: Rust (edition 2021, ≥1.78). Rationale (locked ADR-001): (a) fearless concurrency — Send/Sync + ownership statically enforce no shared mutable state across actors (invariant I2), the actor model's central safety property, with zero GC pauses (Erlang's BEAM has a GC; we get bounded latency by construction); (b) zero-cost async — Future/Waker express an actor's suspended run-loop without per-actor OS threads, enabling the M:N scheduler; (c) lock-free + atomics — crossbeam/std::sync::atomic build the MPSC mailbox without a global lock (perf at millions of actors); (d) exhaustive enum/match models ExitReason, Flow, SWIM message kinds, and wire frames precisely; (e) #[no_std]-friendly core + slices for zero-copy wire framing; (f) loom model-checks the mailbox/scheduler concurrency, cargo fuzz hardens the wire decoder, Miri checks the lock-free unsafe. BEAM-style preemption (reduction counting) is implemented cooperatively in async; the OS-thread-per-core executor gives NUMA locality. Rejected: Erlang itself (we are building the runtime), C/C++ (manual memory safety on a concurrent hostile surface), Go (GC + no compile-time data-race prevention + goroutines hide the scheduler we want to author).

Prerequisites: the actor model (Hewitt; Erlang's process model); M:N / green-thread scheduling + cooperative preemption (cross-link #54 Scheduler, #131 Fibers, #129 Async Runtime); lock-free MPSC queues + memory ordering (acquire/release, the C11/Rust memory model); supervision + "let it crash" (OTP design principles); SWIM membership + gossip (cross-link #197, #72); phi-accrual failure detection; distributed delivery semantics (at-most/at-least/exactly-once impossibility, idempotency, FIFO); binary framing + serialization; Rust async (Future, Waker, Pin), Send/Sync, atomics, unsafe discipline.

2. Why Build This

  • Unique knowledge: how a concurrency runtime and a distributed system fuse into one artifact. You implement the scheduler (how millions of logical processes share a handful of cores), the memory discipline (why no-shared-state makes concurrency tractable), the fault model (why "let it crash" + supervision beats defensive coding), and the distribution stack (membership, failure detection, the unavoidable delivery-semantics tradeoffs). This is the Erlang/BEAM and Akka architecture, rebuilt from first principles.
  • Historical/architectural: the actor model (Hewitt 1973) and Erlang (Ericsson, 1986, for telecom switches needing "nine nines") are the canonical answer to reliable concurrency. Akka brought it to the JVM; Orleans (virtual actors) and Pony (reference-capabilities) are descendants. Supervision trees + "let it crash" are a genuinely different fault philosophy from try/catch. SWIM + phi-accrual are the membership/detection primitives behind Cassandra, Consul, Akka Cluster, and HashiCorp Serf.
  • Engineering muscles: M:N scheduling + cooperative preemption; lock-free queue design + memory ordering; building a custom binary wire protocol + framing + serialization; SWIM membership + anti-entropy; phi-accrual statistical failure detection; reasoning about the at-most/at-least/exactly-once spectrum and why exactly-once needs dedup; split-brain handling; testing concurrent code with loom and distributed code with chaos/fault injection.
  • Production concepts exercised: backpressure (bounded mailboxes), crash-only software (restart > repair), location transparency (same API local/remote), failure detection vs. failure (a slow node looks dead), supply-chain + reproducibility, observability of an async runtime (per-actor mailbox depth, scheduler reductions, detector phi).
  • Cross-links: #54 Scheduler / #131 Fibers / #129 Async Runtime (the executor under the actors); #197 SWIM / #72 Gossip (membership + anti-entropy); #58 Pub/Sub (message routing patterns, topics over actors); #155 gRPC (an alternative wire/RPC model we contrast with our binary protocol); #163 Durable Execution (persistent at-least-once — our in-memory redelivery is the non-durable sibling); #342 Erlang Hot Code Loading (live upgrade atop this runtime); #344 Deterministic Replay (consumes our event log); #42 Raft (consensus — what we deliberately do not build, contrasting AP membership with CP consensus).
  • Calibration: after this you can reason about any concurrency runtime (Go, Erlang, Akka, Tokio), explain why distributed systems cannot have exactly-once without idempotency, debug "why did this actor's mailbox grow unbounded," and architect a fault-tolerant system around supervision rather than exceptions.

What Mastery Looks Like:

  • Design a correct lock-free bounded MPSC mailbox with the full backpressure policy matrix, explain every memory-ordering choice, and model-check it with loom — acquired in Phase 2.
  • Implement a reduction-counting M:N scheduler with work-stealing and NUMA-aware parking, and prove cell-run exclusivity without a global lock — acquired in Phase 1.
  • Build a supervision tree with all three strategies and exact intensity semantics, explain why restart to known state is preferable to in-place recovery, and trace a crash-loop escalation to root — acquired in Phase 4.
  • Implement the SWIM membership protocol and phi-accrual failure detector from their original papers, explain the false-positive / detection-latency tradeoff, and distinguish "slow" from "dead" in a running cluster — acquired in Phases 8–9.
  • Specify and fuzz-harden a versioned binary wire protocol, explain the frame-bound-before-alloc rule, and reason about the rolling-upgrade window and SemVer compatibility contract — acquired in Phases 6–7.
  • Articulate precisely why exactly-once delivery is not achievable without dedup + idempotency, implement the at-least-once + dedup window correctly, and select the right semantics for a given use case — acquired in Phase 10.
  • Operate a distributed actor cluster: read the phi heatmap dashboard, diagnose mailbox growth, identify a crash loop from restart metrics, and run the split-brain runbook — acquired in Phases 9 and 12.

Per-box:

Actor cell — the runtime's atom: a heap object holding an actor's private state, its behavior (the Actor trait object / typed handler), its mailbox, its links/monitors, and a handle to its supervisor. The cell is the only owner of the state; the scheduler grants it exclusive access for the duration of one message (invariant I1: a cell is never run on two workers at once → no concurrent handling → no data races without locks). Activation = "this cell has ≥1 message and is not currently running" → enqueued on a worker run-queue.

act-runtime (M:N scheduler) — a thread-per-core worker pool (one OS thread pinned per core for NUMA locality). Each worker owns a run-queue of ready actor cells; work-stealing balances load. A running cell processes messages until it hits a reduction budget (Erlang-style cooperative preemption: each message handled costs reductions; budget exhausted → yield, re-enqueue), guaranteeing fairness (I3: no actor starves the worker). Idle workers park (futex/condvar) to avoid busy-spin. This is the #54/#129/#131 cross-link made concrete.

act-mailbox — per-actor lock-free bounded MPSC queue (many senders, single consumer = the owning cell). Bounded → backpressure: when full, the configured policy (block sender / drop-newest / drop-oldest / fail-send) applies (I8). FIFO per sender pair (I4) — messages from sender A to actor X arrive in send order; no global ordering across senders. Enqueue transitions an idle cell to ready (notifies the scheduler).

act-supervise — supervision tree: every actor (except the root) has a parent supervisor; on child crash, the supervisor applies a strategy — one-for-one (restart only the crashed child), one-for-all (restart all children), rest-for-one (restart the crashed child + those started after it) — bounded by a restart-intensity limit (max R restarts in T seconds; exceeding it escalates the failure up the tree → "let it crash" all the way to a clean shutdown if unrecoverable). This is OTP's fault model (I9/I10).

act-addr — addressing: a Pid{ node, incarnation, local_id } uniquely names an actor across space and time (incarnation distinguishes a restarted node's reused ids). An ActorRef wraps a Pid + a resolution cache; send resolves to either a local cell (direct mailbox enqueue) or a remote target (hand the serialized Envelope to the transport). Location transparency (I11): the caller's API is identical either way — the only difference is at-most-once becomes more likely to silently drop on a partition (documented, not hidden).

act-transport — the wire protocol: one TCP connection per peer (multiplexing all actor traffic + heartbeats), length-prefixed frames, a versioned handshake (protocol version + node identity + incarnation), and message serialization (envelope header + opaque payload). Preserves per-sender FIFO over the connection (I4). Trust boundary: inbound bytes are hostile → the frame decoder must never panic (I6, fuzzed).

act-cluster (membership) — SWIM: nodes join via a seed, then maintain a member list through periodic ping + ping-req (indirect probe via k random members) + gossip of membership updates (alive/suspect/dead) piggybacked on probes. Incarnation numbers let a node refute a false suspicion. Detects and surfaces split-brain (a partition where each side thinks the other is dead) — this runtime is AP (availability + partition-tolerance), so it does not auto-resolve split-brain; it reports it (consensus/CP is #42's job).

act-detector (failure detection) — phi-accrual: instead of a binary timeout, it tracks the distribution of heartbeat inter-arrival times per peer and outputs a continuous suspicion level φ; when φ exceeds a threshold, the peer is suspected (feeds SWIM). Adaptive to network jitter (a momentary GC pause raises φ gradually, not a hard cutoff). Direct heartbeats + indirect ping-req confirm. On confirmed death, the peer's actors' remote ActorRefs are invalidated (I12: sends to them fail fast / dead-letter, monitors fire Down).

act-cli / observability — act talks to a local actd over a control socket: members (cluster view), ps (actors + mailbox depths), tree (supervision tree), send (inject a message). Metrics (mailbox depth, scheduler reductions, restarts, φ per peer, frame errors), tracing spans (send→enqueue→handle, probe→suspect→dead), structured logs.

4. System Constraints

Dimension Target
Actors per node ≥ 1,000,000 live actors (idle); spawn ≥ 1 M in ≤ 10 s; cell ≤ ~256 B fixed overhead + state
Local message send→handle p50 ≤ 1 µs, p99 ≤ 10 µs (warm, same-core); ≥ 10 M local msgs/s/node aggregate
Remote message (intra-DC) p50 ≤ 150 µs, p99 ≤ 2 ms (RTT-bound + serialize + frame); ≥ 200 k remote msgs/s/conn
Mailbox enqueue lock-free, wait-free for single producer; bounded; O(1); backpressure at capacity
Scheduler fairness no actor monopolizes a worker > 1 reduction budget (default ~2000 reductions ≈ 2000 msgs or cost units)
Worker pool 1 OS thread per core (configurable); ≤ 1% idle busy-spin (park when no ready cells)
Spawn latency p99 ≤ 5 µs local; remote-spawn (if enabled) RTT-bound
Supervision restart crash→detected→restart child p99 ≤ 100 µs (local); intensity limit enforced exactly
SWIM convergence membership change (join/leave/fail) propagates to all N nodes in O(log N) gossip rounds; ≤ ~5 s for N ≤ 1000
Failure detection phi-accrual: false-positive rate ≤ 1% at φ-threshold 8 under normal jitter; detect a truly dead node ≤ 3× heartbeat interval
Heartbeat interval default 1 s; tunable; ping-req fan-out k = 3
Frame size message payload ≤ 16 MiB default (configurable); header ≤ 256 B; reject oversize before alloc (I6)
Delivery (default) at-most-once; no redelivery; no ordering across senders; per-sender FIFO preserved (I4)
Delivery (at-least-once mode) redelivery until ack; dedup window per (sender, seq); bounded buffer; documented duplicate-on-failure
Determinism given a fixed message-arrival order, each actor's state evolution is deterministic (I1) — enables #344 replay
Startup (actd) ≤ 200 ms to listening + joined-to-seed for a fresh node
Shutdown graceful: stop accepting, drain mailboxes (bounded), notify supervisor + cluster (leave), flush → ≤ 5 s
Memory ceiling bounded: total mailbox bytes capped per node; reject/backpressure beyond → no OOM from a flood (I8)
Availability AP under partition: each side stays available; split-brain surfaced, not auto-merged
Concurrency scheduler + mailbox loom-verified; decoder Miri/fuzz clean; never a data race (I2 by construction)

Scaling: horizontal = add nodes (SWIM absorbs them; actor placement is explicit or hash-based); vertical = more cores → more workers (near-linear until mailbox/transport contention). No persistence in the core (stateless restart); at-least-once buffers are in-memory (durable = #163).

6. Design Principles

  1. No shared mutable state across actors (the prime directive). An actor owns its state exclusively; the only inter-actor communication is by value via messages. Enforced by Rust ownership + Send bounds on messages and the cell-runs-on-one-worker rule. Tradeoff: copying/serialization cost vs. data-race freedom. Violation: sharing a &mut across actors reintroduces locks, races, and the very bugs the model abolishes — I2 breaks and the safety story collapses.
  2. One message at a time, per actor. A cell handles exactly one message per activation; never two concurrently. Tradeoff: a single actor is a serialization point (not internally parallel — split work across actors). Violation: concurrent handling = data race on private state + non-determinism, breaking I1 and #344 replay.
  3. Let it crash; supervise, don't defend. Actors do not litter handlers with defensive error recovery; on an unexpected fault they crash, and a supervisor restarts them to a known-good state. Tradeoff: restart cost + transient unavailability vs. simpler, more correct code. Violation: in-actor try/catch everywhere recreates fragile error spaghetti and hides faults from the supervision tree (I9).
  4. Location transparency — but honest about partial failure. send is identical local or remote; however, remote sends can silently fail (at-most-once over a partition). We do not pretend remote == local (per Waldo's "Note on Distributed Computing"); monitors + dead-letters surface remote failure. Violation: assuming remote sends always arrive → lost-message bugs that only manifest under partition (I11/I12).
  5. Backpressure everywhere; bounded mailboxes. Every mailbox is bounded; a slow consumer applies backpressure (block/drop/fail) rather than growing unboundedly. Tradeoff: a fast producer is throttled vs. OOM. Violation: unbounded mailbox → one slow actor OOMs the node (I8), the classic actor-system outage.
  6. Crash-only / restart over repair. Components start and stop; there is no "repair in place." Restart returns to a known state (state is rebuilt, not patched). Violation: in-place mutation recovery leaves half-broken state — restart is the only trusted recovery (drives Phase 4 + #163 boundary).
  7. Failure detection is a hint, not a fact (◇P). A "dead" verdict can be wrong (a slow node looks dead). The detector is eventually accurate but may false-positive; the system must tolerate a live node being declared dead (and recover when it refutes via incarnation). Tradeoff: aggressive detection (fast, false positives) vs. conservative (slow, misses). Violation: treating detection as ground truth → killing healthy nodes (split-brain amplification, I12).
  8. AP, not CP — surface split-brain, don't fake consensus. Under partition we stay available on both sides and report the split; we never silently pick a winner or pretend consistency. Consensus (#42 Raft) is a deliberate non-goal. Violation: faking exactly-once / single-truth without consensus → silent data divergence (I-delivery, Phase 10).
  9. Determinism per actor. Given a fixed arrival order of messages, an actor's state trajectory is reproducible (no hidden nondeterminism in the handler path beyond the inputs). Tradeoff: must thread time/randomness as explicit messages/inputs. Violation: Instant::now()/RNG inside handlers breaks #344 deterministic replay (I1).
  10. The wire decoder never trusts its input. Every inbound frame is hostile: bounded sizes, no panic, no OOB, no unbounded allocation. Fuzzed + Miri-checked. Violation: a crafted frame crashes or OOMs a node = remote DoS across the cluster (I6, Threat Model).
  11. Fair scheduling via reduction counting. No actor monopolizes a worker; cooperative preemption (reduction budget) bounds per-activation work, then yields. Tradeoff: preemption overhead vs. fairness. Violation: a hot actor (tight message loop) starves all others on that worker (I3), latency cliff.
  12. Explicit ownership of every async resource. Each TCP connection, worker thread, timer, and mailbox has exactly one owner; shutdown is orderly (drain → close → join). Violation: leaked connections/threads on shutdown → fd exhaustion + zombie workers.
  13. Per-sender FIFO, no global order. Messages from one sender to one actor arrive in send order; there is no total order across senders. Tradeoff: cheap (no global sequencer) vs. callers must not assume cross-sender ordering. Violation: assuming global order → reordering bugs that pass locally and fail under load/distribution (I4).
  14. Observability is first-class. Mailbox depth, scheduler reductions/parks, restart counts, detector φ, frame errors, membership transitions are all metricized + traced from day one. Violation: an opaque async runtime is undebuggable in production (where the bugs are).
  15. Stable wire + API compatibility (SemVer). The wire protocol (handshake version negotiation) and the public Actor/ActorRef/Pid API are SemVer'd; nodes of adjacent versions interoperate. Violation: an unversioned wire change splits the cluster on rolling upgrade (Compatibility & Versioning).

8. Domain Model

8.1 The actor (three axioms, Hewitt 1973)

An actor, on receiving a message, may do exactly three things:

1. SEND   a finite number of messages to other actors (by ActorRef).
2. SPAWN  a finite number of new actors (it becomes their supervisor).
3. BECOME a new behavior for the *next* message (designate next state).

Everything else is built from these. An actor = { private state, current behavior, mailbox, identity (Pid), supervisor handle, links, monitors }. It is passive until a message activates it; the scheduler runs it; it processes one message; it goes idle (or is preempted).

8.2 Identity, addressing, and references

Pid        := { node: NodeId, incarnation: u32, local_id: u64 }     // unique across space + time
NodeId     := { name: String, addr: SocketAddr, uid: u64 }          // a cluster node
ActorRef   := { pid: Pid, hint: ResolveHint }                       // location-transparent handle
ResolveHint:= Local(CellPtr) | Remote(NodeId) | Unresolved          // cached resolution
DeadLetter := { from: Pid, to: Pid, payload: Bytes, reason: DeadReason }
  • local_id is unique within a node and incarnation; reuse after restart is disambiguated by incarnation (I13) — a stale ref to a pre-restart actor resolves to dead, never to a new actor that reused the id.
  • ActorRef::send resolves hint: Local → enqueue on the cell's mailbox directly; Remote → serialize Envelope, hand to transport for that NodeId; Unresolved → consult act-addr registry / cluster.

8.3 Message, Envelope, and the wire format

Logical message (application type) → wrapped in an Envelope for routing/wire.

Envelope := { to: Pid, from: Pid, kind: MsgKind, seq: u64, payload: Bytes }
MsgKind  := User | System(SystemMsg) | Monitor(MonitorMsg)
SystemMsg:= Link(Pid) | Unlink(Pid) | Exit{from:Pid, reason:ExitReason} | Stop | Restart
MonitorMsg := Down{ref:Pid, reason:ExitReason} | MonitorReq | DemonitorReq
ExitReason := Normal | Shutdown | Killed | Panic(String) | NodeDown(NodeId)

Wire frame (length-prefixed, big-endian on the TCP byte stream):

+--------+--------+----------------+-----------------+------------------+============+
| MAGIC  | VER    | FRAME_LEN(u32) | FRAME_TYPE(u8)  | HEADER (varint)  |  PAYLOAD   |
| 0xAC70 | u16    | bytes to follow| Msg|Ping|PingReq | to/from/kind/seq |  (opaque)  |
|        |        |                | Ack|Gossip|Hello | (serialized)     |            |
+--------+--------+----------------+-----------------+------------------+============+
FRAME_TYPE := Hello(0) Msg(1) Ping(2) PingReq(3) Ack(4) Gossip(5) Bye(6) ExitSig(7)
  • FRAME_LEN bounds the read (reject > 16 MiB before allocating — I6). Decoder reads header (fixed/varint), then exactly payload_len bytes; never trusts a length past the buffer.
  • Payload serialization is pluggable (ADR-005): bincode-style fixed for internal types; user payloads carry a type-tag the receiving node maps to a deserializer (or dead-letters on unknown type).
  • Handshake (Hello): { proto_ver, node_id, incarnation, capabilities } — both sides exchange before any Msg; version-mismatch → close (or negotiate down within a major, Compatibility & Versioning).

8.4 Mailbox semantics

Mailbox := bounded lock-free MPSC<Envelope>, capacity C, policy P
enqueue(env) -> Ok | Err(MailboxFull)   // many producers (any sender), wait-free fast path
dequeue()    -> Option<Envelope>        // single consumer (the owning cell), FIFO
policy P     := Block | DropNewest | DropOldest | Fail   // backpressure (I8)
  • FIFO per sender pair (I4): the queue is FIFO; combined with per-connection FIFO on the wire, A→X order is preserved. No cross-sender order guarantee.
  • System messages (Link/Exit/Stop) may use a priority lane (out-of-band) so a crash signal is not stuck behind a backlog of user messages — Erlang-style (documented in Phase 3).
  • Activation: the first enqueue onto an empty mailbox flips the cell idle→ready and notifies the scheduler (exactly once; subsequent enqueues while ready do not re-notify).

8.6 Supervision tree + strategies

Supervisor := { children: Vec<ChildSpec>, strategy: Strategy, intensity: (max_r:u32, within:Duration) }

Strategy   := OneForOne | OneForAll | RestForOne
Strategy On a child crash, restart…
OneForOne only the crashed child
OneForAll all children (siblings share fate)
RestForOne the crashed child + all children started after it (ordered dependency)
  • restart policy: Permanent (always restart), Transient (restart only on abnormal exit), Temporary (never restart).
  • Intensity (I9): if a child crashes > max_r times within within, the supervisor itself fails → its parent applies its strategy → escalation propagates toward the root. The root's failure = orderly node shutdown ("let it crash" to the top).

8.9 Worked example — remote send across a partition

NodeA actor P holds remoteRef R → actor Q on NodeB. Steady state: P.send(R,msg) → Envelope over TCP A→B → Q.mailbox.
Partition A|B:
  - NodeA's detector: B's heartbeats stop → φ rises → φ>θ → B Suspect → ping-req via C fails → B Dead (I12).
  - R is invalidated: P.send(R,msg) now → DeadLetter{NodeDown(B)} fast-fail (no hang). Monitors on Q fire Down{Q, NodeDown(B)}.
  - On NodeB (other side): A is likewise declared Dead. Both sides remain AVAILABLE (AP). This is split-brain — SURFACED, not merged (principle 8).
Heal:
  - Connectivity returns; Hello re-handshake; incarnations exchanged. If B restarted, its incarnation is higher → A adopts (I13);
    old refs to pre-restart B actors stay dead (I13). No automatic state reconciliation (deferred / CRDT note, Phase 9).

8.10 Malformed / failure-path examples

  • Oversize frame: FRAME_LEN = 4 GiB → reject before alloc, close connection, frame_error (I6); peer re-handshakes.
  • Unknown payload type-tag: receiver has no deserializer → dead-letter the message (do not crash the receiving actor) — graceful degradation.
  • Truncated frame (connection drops mid-frame): decoder returns FrameError::Truncated; connection torn down; per-sender FIFO means in-flight unacked messages (ALO mode) are redelivered on reconnect (I15); default mode drops them (I14).
  • Mailbox flood: a producer outpaces a consumer → mailbox hits capacity C → policy applies (Block throttles the producer; DropNewest sheds load; Fail returns MailboxFull to sender) — never OOM (I8).
  • Crash loop: a child crashes immediately on every restart → intensity limit (R-in-T) trips → supervisor escalates (I9) rather than spinning forever.
  • False-positive death: a node GC-pauses 4 s with a 1 s heartbeat → φ rises → Suspect; if it recovers and gossips Alive with a refute before the suspicion timeout, it is reinstated (I13) — no eviction. If it stays silent past timeout → Dead (acceptable false positive, ◇P, principle 7).
  • Duplicate under ALO: at-least-once redelivers an unacked message; the receiver's dedup window suppresses the duplicate by (from, seq) (I15); outside the window (very late duplicate) the application must be idempotent (documented limit — exactly-once = dedup + idempotency, never free).
  • Self-link / monitor-of-self: rejected or no-op (an actor crashing cannot meaningfully notify itself); validated at link time.

12. Phase 0 — Actor Trait, Single-Thread Runtime, Mailbox, Spawn/Send, CLI

0.1 Objectives

The actor core, single-threaded: an Actor trait (handle/init/terminate), a Context (spawn/send/self/stop), a bounded mailbox (FIFO, mutex-backed for now — lock-free lands P2), a single-thread executor that runs ready cells one message at a time (I1), and a CLI demoing a small actor tree. Establish from line one: one message at a time, no shared state, bounded mailbox.

0.2 Detailed Implementation Steps

  • act-types: Pid (single-node: node fixed, incarnation 0), ActorRef (Local hint only), Envelope, MsgKind::User, ExitReason, SendError::{MailboxFull,NoSuchActor}. Applies P1 (no shared mutable state — Send bound on Message), I2 (ownership enforces actor isolation at compile time), ADR-001 (Rust language choice).
  • act-mailbox: Mailbox over Mutex<VecDeque<Envelope>> + capacity + BackpressurePolicy::{Fail,Block}; enqueue/dequeue/len; first-enqueue returns became_ready. Applies I8 (bounded mailbox) and I4 (FIFO dequeue), ADR-004 (mailbox choice), Hewitt 1973 axiom 1 (send messages).
  • act-actor: Actor trait + typed Context; cell.rs = ActorCell{state, mailbox, run_state}; lifecycle.rs = Starting→Running→Terminating→Stopped. Applies P2 (one message at a time), I1 (single-runner), Hewitt 1973 axiom 2+3 (spawn + become), Armstrong thesis (process = unit of failure).
  • act-runtime (single-thread): a ready-queue of cells; loop: pop ready cell → dequeue one msg → handle → if more msgs, re-enqueue cell. spawn_root/spawn (child via Context). Panic in handle → catch (catch_unwind) → terminate(Panic) → Stopped. Applies P6 (crash-only restart), I1 (exactly one cell runs at a time), ADR-002 (scheduler model, single-thread precursor).
  • act-cli (act demo): build root → spawn child counter → send Inc×N → print final state + observe ordering. Validates P14 (observability first-class) and I1/I4 via the message log.

0.3 Deliverable

act demo runs an actor tree single-threaded: messages handled one-at-a-time in FIFO; cargo test shows deterministic state evolution; a panicking actor stops cleanly without taking down the runtime.

0.4 Acceptance Criteria

  • Counter actor receiving Inc×1000 ends at 1000, processed strictly in order (I1/I4).
  • Mailbox at capacity with Fail policy returns MailboxFull (I8); with Block, sender throttles.
  • Panic in handle → cell Stopped, runtime survives, other actors keep running (I7 precursor).
  • No unsafe; no shared mutable state (compiles only because state is owned, I2).

0.5 Conformance Fixtures

conformance/lifecycle/{spawn_handle_stop,panic_stops_cell}, mailbox/{fifo_order,backpressure_fail,backpressure_block}. Golden: ordered message log per actor.

0.6 Pitfalls

  • Re-entrant send during handle (an actor sends to itself) → must enqueue, not recurse (avoid stack blowup / re-entrant borrow of state).
  • became_ready race (two enqueues both think they made it ready) → exactly-once notify even single-threaded (sets the contract P2 must keep lock-free).
  • Catching panics but leaving the cell in a half-mutated state → on panic, the cell is terminated, not resumed (state is abandoned — crash-only, principle 6).
  • Borrow of state across an await (when async lands) → P0 is sync; keep handle non-async or carefully Pin later.

0.7 Performance Concerns

Single dispatch loop; VecDeque FIFO O(1) ends; no allocation per message beyond the envelope. Target (single-thread) ≥ 5 M msgs/s; sets the baseline P1/P2 must beat with M:N + lock-free.

0.8 Edge Cases

Empty mailbox (cell idle, not enqueued); send to a stopped actor (NoSuchActor/dead-letter); zero-capacity mailbox (degenerate; reject at config); self-send; spawn inside init.

0.9 Failure Analysis

A bug here (e.g., processing two messages "at once" via re-entrancy) violates I1 and poisons every later phase + #344 replay. Detection: the ordered-log fixture + a single-runner assert. Blast radius: the whole runtime model.

0.10 Operational Notes

Metrics: messages_handled, mailbox_depth, cell_panics, mailbox_full. act demo --trace prints per-message spans. Single-node, in-process; no network yet.

13. Phase 1 — M:N Scheduler: Thread-per-Core, Work-Stealing, Reduction-Count Preemption

1.1 Objectives

Replace the single-thread loop with a true M:N scheduler: W worker threads (one per core), each with a run-queue of ready cells; work-stealing balances load; reduction-count preemption (Erlang-style) bounds per-activation work for fairness (I3); idle workers park. Preserve I1 (a cell never runs on two workers) via a lock-free claim. This is the #54/#129/#131 cross-link.

1.2 Detailed Implementation Steps

  • act-runtime::worker: per-worker RunQueue (lock-free deque, crossbeam-style); steal from siblings when empty. Applies ADR-002 (M:N thread-per-core), BEAM scheduler ERTS paper (reduction-based fairness model), cross-link #54 Scheduler / #129 Async Runtime.
  • Cell claim: an atomic run_state (Idle/Ready/Running) with CAS so exactly one worker transitions Ready→Running (I1); on finish, Running→Idle or →Ready (if mailbox non-empty). Applies P2 (one message at a time), I1 (exclusive claim), ADR-015 (loom model-checks this claim), Bos Rust Atomics and Locks (acquire/release CAS discipline).
  • Reductions: reductions.rs — each message handled decrements a budget; budget hits 0 → yield: re-enqueue the cell at the tail (fairness, I3), pick the next ready cell. Applies P11 (fair scheduling via reduction counting), I3 (no starvation), ERTS internals paper (per-process reduction budget).
  • Parking: park.rs — when a worker's queue is empty and stealing fails, park on a futex/condvar; an enqueue that makes a cell ready wakes one parked worker. Applies ADR-018 (futex/condvar parking), I3 (≤1% idle CPU), P12 (explicit resource ownership for each worker thread).
  • timer_wheel.rs: hashed-wheel timer for heartbeats/timeouts/redelivery. Applies ADR-019 (hashed-wheel at scale vs. per-actor OS timer).

1.3 Deliverable

The same act demo now runs across all cores; a microbenchmark shows linear-ish scaling with worker count; a "hot" actor in a tight loop does not starve others (reduction preemption observable in traces).

1.4 Acceptance Criteria

  • Throughput scales with cores (e.g. 4× workers → ≥ 3× msgs/s) up to mailbox/contention limits.
  • A hot actor yields every reduction_budget messages; other actors on the same worker make progress (fairness fixture; reduction_overrun=0 beyond budget).
  • loom model-check (small config) proves the Ready→Running claim is exclusive (I1) under all interleavings.
  • Idle CPU ≤ 1% when no work (parking works); wake latency p99 bounded.

1.5 Conformance Fixtures

conformance/lifecycle/scheduler_fairness, loom/scheduler_claim.rs, benchmarks/{spawn,local_send} baselines per worker-count.

1.6 Pitfalls

  • Lost wakeup (cell becomes ready but the parking worker isn't woken) → actor stalls forever; pair the ready-flag store with the unpark via correct memory ordering (acquire/release) + re-check after parking.
  • Double-claim (two workers run the same cell) → data race on private state, I1 violation; the CAS must be the single source of truth (loom-verified).
  • Reduction accounting drift (counting differently across message types) → unfair scheduling; define reduction cost precisely (1/message default + optional cost hooks).
  • Work-stealing thrash (cells bouncing between workers, cache cold) → steal in batches; prefer local; back off.
  • Priority inversion (signal lane starved) → P3's signal lane must preempt user-msg processing.

1.7 Performance Concerns

Hot path = claim CAS + dequeue + handle. Cache: keep a cell's mailbox + state co-located; pin workers to cores (NUMA). Avoid per-message heap (reuse envelope buffers). Steal cost amortized. Target ≥ 10 M local msgs/s aggregate on 8 cores; p99 send→handle ≤ 10 µs warm.

1.8 Edge Cases

Single worker (degenerate M:N = P0 behavior); more workers than cores (oversubscription); a cell that re-enqueues itself instantly (would spin — reductions bound it); all workers parked then a burst arrives (wake exactly enough).

1.9 Failure Analysis

A scheduler bug = either starvation (fairness) or a data race (correctness). Detection: loom for races (pre-merge), fairness fixtures + reduction_overrun metric in CI. Blast radius: every actor on the runtime; a race is a memory-safety incident.

1.10 Operational Notes

Metrics: worker_busy_ratio, steals, parks, unparks, reduction_yields, runqueue_depth per worker. Tracing: scheduler spans (claim→handle→yield). Tuning: reduction_budget, workers in RuntimeCfg; runbook slow-node.md covers worker saturation.

14. Phase 2 — Lock-Free Bounded Mailbox + Backpressure Policies

2.1 Objectives

Replace the mutex mailbox with a lock-free bounded MPSC queue (many senders, single consumer), wait-free on the single-producer fast path, with the full backpressure policy set (Block/DropNewest/DropOldest/Fail, I8) and a priority signal lane so system messages (Link/Exit/Stop) bypass a user-message backlog. Memory-order-correct (Miri/loom).

2.2 Detailed Implementation Steps

  • act-mailbox::queue: lock-free MPSC ring (bounded) — atomic head/tail, slot states; producers CAS a slot; consumer reads in order (preserves FIFO per producer, I4). Applies ADR-004 (lock-free MPSC over global lock), Bos Rust Atomics and Locks (sequence-numbered Vyukov-style ring, acquire/release publishing), I2 (Send bound enforces move-only payloads), ADR-015 (loom model-checks this queue).
  • bounded.rs: capacity enforcement; on full, dispatch to policy.rs: Block, DropNewest, DropOldest, Fail. Applies P5 (backpressure everywhere), I8 (bounded mailbox, no OOM), ADR-014 (configurable per-mailbox policy), Vernon Reactive Messaging Patterns (backpressure patterns).
  • signal_lane.rs: a separate small high-priority queue checked before the user queue on each dequeue → exit/stop signals are never blocked. Applies P3 (let it crash — signal must reach supervisor), I7 (exit signal not lost), Armstrong Erlang Programming (system messages bypass user-message backlog).
  • Integrate with scheduler activation (first user-enqueue or any signal-enqueue → became_ready). Applies I1 (exactly-once ready notification), ADR-002 (M:N scheduler integration).

2.3 Deliverable

Mailbox is lock-free; under a multi-producer benchmark it sustains target enqueue rates with no global lock; backpressure policies demonstrably bound memory under a flood; system signals jump the queue.

2.4 Acceptance Criteria

  • loom/mailbox_mpsc.rs: FIFO-per-producer + no-lost-message + no-double-consume across all interleavings (I4); Miri-clean (no UB in the atomics).
  • Flood test: producer >> consumer → memory bounded at cap × envelope_size regardless of flood duration (I8); each policy behaves per spec (drop counts, block throttles, fail returns).
  • A Stop signal sent behind 10k queued user messages is processed before them (signal lane).

2.5 Conformance Fixtures

conformance/mailbox/{fifo_multiproducer,policy_block,policy_dropnewest,policy_dropoldest,policy_fail,signal_lane_priority}, loom/mailbox_mpsc.rs, fuzz n/a (internal), bench local_send multi-producer.

2.6 Pitfalls

  • ABA on the ring (slot reused while a producer holds a stale index) → use sequence-numbered slots (Vyukov-style MPMC/MPSC), not raw CAS on pointers.
  • Memory ordering too weak → consumer sees a half-written envelope; publish the payload with Release, consume with Acquire.
  • Backpressure deadlock (Block policy: actor A's handler sends to full mailbox of B which is waiting on A) → Block must be a yielding await (the worker keeps running other cells), never a thread-block that stalls the worker.
  • Signal-lane starvation of user messages (always draining signals first under a signal flood) → signals are rare/bounded by design; cap per-tick signal drain.
  • Drop accounting lost → every drop increments messages_dropped (observability).

2.7 Performance Concerns

Wait-free single-producer enqueue (the common case: one actor sends to another); MPSC contention only when many actors target the same hot actor (a design smell — shard hot actors). Cache: pad atomics to cache lines (avoid false sharing of head/tail). Target enqueue p99 ≤ 100 ns uncontended.

2.8 Edge Cases

Capacity 1 (every send may block/drop); simultaneous full + consumer drain (race the policy); signal lane full (rare — escalate); producer dies mid-enqueue (slot must not corrupt — sequence numbers guarantee).

2.9 Failure Analysis

A mailbox bug is the worst kind: silent message loss/dup or a data race. Detection: loom (pre-merge, exhaustive small-model), Miri (UB), flood test (memory). Blast radius: any actor; a lost-message bug surfaces as mysterious application stalls. Recovery: none at runtime (must be correct) — hence loom gating.

2.10 Operational Notes

Metrics: mailbox_depth (gauge), enqueue_latency, messages_dropped{policy}, backpressure_blocks, signal_lane_depth. act ps shows per-actor mailbox depth (the #1 production signal for a stuck/slow actor). Runbook mailbox-flood.md.

15. Phase 3 — Lifecycle, Links, Monitors, Exit Signals

3.1 Objectives

Implement the fault-propagation primitives beneath supervision: links (bidirectional fate-sharing — if A is linked to B and B crashes abnormally, A receives an exit signal and, by default, also terminates), monitors (unidirectional — A monitors B, gets a Down{B,reason} message but is not killed), and reliable exit-signal delivery to a crashed actor's supervisor (I7). Full lifecycle: graceful stop vs. crash, terminate hook, notify linked/monitored parties.

3.2 Detailed Implementation Steps

  • act-supervise::links: per-actor link set; on terminate, send SystemMsg::Exit{from,reason} to all links via the signal lane (P2) so it cannot be lost behind a backlog (I7). Linked normal exit = no propagation; abnormal = propagate (unless trapping). Applies P3 (let it crash), I7 (exit signal not lost), Armstrong Erlang Programming (link/trap-exit model), ADR-012 (tree supervision over flat errors).
  • monitors.rs: monitor registry; on target terminate, send MonitorMsg::Down{ref,reason} (a message, not a signal — monitor stays alive). Applies P4 (location transparency — monitors work across nodes in P9), I12 (remote-ref invalidation fires Down), Akka in Action (unidirectional Down notice pattern).
  • "Trap exits": actor flag — a supervisor traps exits, receiving them as normal messages. This is how supervisors are built (P4). Applies P3 (crash-only), I9 (supervisor handles crashes without dying), Armstrong thesis (fault isolation via trap_exit + supervisor boundary).
  • lifecycle.rs: finalize Starting/Running/Terminating/Stopped/Failed state machine (§8.5); terminate(reason, ctx) hook runs in Terminating; cell freed in Stopped. Applies P6 (crash-only), I10 (restart returns to known-good initial state), ADR-012 (supervision model).
  • Context::{link, monitor, stop} wired; ExitReason populated. Applies P1 (actor axiom 1: send), I5 (one supervisor per actor), ADR-013 (Pid incarnation to disambiguate stale refs).

3.3 Deliverable

Linked actors share fate; monitoring actors get Down notifications; a crashing actor reliably notifies its supervisor (trap-exits). Demo: a worker crash propagates to a linked sibling; a monitor logs the death without dying.

3.4 Acceptance Criteria

  • A crashes (Panic) → linked B (not trapping) also terminates with Exit{A,Panic}; linked S (trapping) receives Exit{A,Panic} as a message and survives (I7).
  • A monitor of A receives exactly one Down{A,Panic}; demonitor stops further notices.
  • Normal exit of A → linked non-trapping B is not killed (only abnormal propagates).
  • No exit signal is ever lost, even with A's killer message arriving amid a 10k user-message backlog (signal lane, I7).

3.5 Conformance Fixtures

conformance/supervision/{link_propagate_abnormal,link_no_propagate_normal,trap_exit_survives,monitor_down,demonitor}, golden signal/down traces.

3.6 Pitfalls

  • Lost exit signal behind user backlog → must use the signal lane (I7); a regression here silently breaks supervision.
  • Link cycle storm (A↔B↔C linked, one crash cascades) → propagation is correct but can cascade widely; trapping at supervisor boundaries contains it (this is the design, not a bug — but document the blast radius).
  • Double-notify (an actor linked and monitored) → both fire (by spec) — distinct mechanisms; don't dedup them.
  • Monitor of a dead actor → fire Down immediately (the target is already gone) rather than waiting forever.
  • Self-link → no-op/reject.
  • Reason fidelity — terminate reason must match the actual cause (Panic carries the message) for debuggability.

3.7 Performance Concerns

Links/monitors are sets touched only at link/terminate time (not on every message) → near-zero steady-state cost. Signal-lane enqueue is the priority path (P2). Terminate fan-out O(links+monitors).

3.8 Edge Cases

Linking to an already-dead actor (immediate exit signal); monitoring self; a supervisor (trapping) that itself crashes (escalates to its parent — P4); simultaneous crash of two linked actors (both notify; idempotent).

3.9 Failure Analysis

If exit signals are lost or misrouted, "let it crash" silently fails — crashes go unsupervised and the system degrades invisibly. Detection: the lost_exit_signal=0 invariant + supervision fixtures. Blast radius: the supervision subtree. This phase is the foundation P4 builds the tree on.

3.10 Operational Notes

Metrics: exit_signals, down_signals, links, monitors, trapped_exits. Tracing: crash→signal→supervisor span. act tree (P4) will visualize the link/supervision structure. Logs: every abnormal exit logged with reason + propagation path.

16. Phase 4 — Supervision Trees, Restart Strategies, Intensity Limits

4.1 Objectives

Build the supervision tree atop links/trap-exits (P3): a Supervisor actor with a strategy (one-for-one / one-for-all / rest-for-one), ChildSpecs (factory + restart policy), and a restart-intensity limit (≤ R restarts in T → escalate, I9). On a child crash, the supervisor restarts per strategy, returning the child to its initial state (I10, crash-only). This is the OTP fault model — the project's reliability core.

4.2 Detailed Implementation Steps

  • act-supervise::supervisor: a built-in actor that traps exits (P3); on Exit{child,reason}, consult strategy + restart policy. Applies P3 (let it crash — supervisor is the crash handler), I9 (intensity-bounded restarts), Armstrong thesis (supervision tree as primary reliability mechanism), ADR-012 (tree vs. flat errors).
  • strategy.rs: OneForOne, OneForAll, RestForOne — spawn-order tracked. Applies P3 (strategy encodes coupling contract), Cesarini & Thompson Erlang Programming (strategy taxonomy), Appendix F (strategy decision table), ADR-012.
  • childspec.rs: factory Fn()->Actor (re-run on restart for fresh state, I10); RestartPolicy::{Permanent, Transient, Temporary}. Applies P6 (crash-only/restart over repair), I10 (known-good initial state), Armstrong Erlang Programming (permanent/transient/temporary restart policies).
  • intensity.rs: sliding-window restart counter (R, T); exceeding → supervisor itself exits abnormally → parent supervises it (I9 escalation). Applies I9 (crash-loop containment), P3 (escalation is the designed recovery path), ADR-012, Armstrong thesis (intensity is the OTP crash-loop valve).
  • Wire Context::spawn to register with parent supervisor (I5). Applies P1 (Hewitt axiom 2: spawn), I5 (one supervisor per actor), ADR-027 (explicit placement — each spawn is assigned to a named parent).

4.3 Deliverable

act tree shows a supervision hierarchy; killing a child triggers the correct strategy; a crash-loop trips the intensity limit and escalates. Demo: a worker pool under a one-for-one supervisor self-heals; a poison-pill worker crash-loops and escalates.

4.4 Acceptance Criteria

  • OneForOne: crash child C → only C restarted, siblings untouched; C' has initial state (I10).
  • OneForAll: crash C → all children stopped + restarted.
  • RestForOne: crash the k-th child → children k..n restarted, 0..k-1 untouched.
  • Intensity: > R crashes in T → supervisor escalates (does not restart again) (I9); restart count metered exactly.
  • Transient: normal exit → no restart; abnormal → restart. Temporary: never restart. Permanent: always.
  • Every spawned actor has exactly one parent supervisor (I5; orphan audit = 0).

4.5 Conformance Fixtures

conformance/supervision/{one_for_one,one_for_all,rest_for_one,intensity_escalate,permanent,transient,temporary,initial_state_on_restart}, golden restart/escalation traces + act tree snapshots.

4.6 Pitfalls

  • Restart with stale state (reusing the old actor object) → must re-run the factory/init for a clean slate (I10); a regression resurrects corrupt state — the bug crash-only is meant to prevent.
  • Intensity window off-by-one (counting restarts vs. crashes, window edges) → either crash-loops forever (never escalates) or escalates too eagerly; define precisely (restarts within rolling T).
  • Escalation storm (one-for-all at a high level restarts a huge subtree) → correct but expensive; document blast radius; prefer fine-grained supervisors.
  • Ordering for rest-for-one (must track spawn order) → keep an ordered child list.
  • Restarting a child whose dependencies (siblings) are gone → strategy choice (one-for-all/rest-for-one) encodes dependency; wrong strategy = restarting into a broken environment.
  • Temporary child that crashes → must not restart; a bug here loops a should-die actor.

4.7 Performance Concerns

Supervision logic runs only on crashes (rare in steady state) → negligible hot-path cost. Restart latency = factory + init (target p99 ≤ 100 µs local). A wide one-for-all restart is O(children).

4.8 Edge Cases

Root supervisor crash (= node shutdown); a child that fails in init on restart (counts toward intensity → eventual escalation); simultaneous sibling crashes (one-for-one handles independently; one-for-all collapses them); deeply nested trees (escalation walks up).

4.9 Failure Analysis

The reliability story is this phase. If restarts don't return to known-good state, or intensity doesn't bound crash-loops, the system either accumulates corruption or spins on a poison input. Detection: supervision fixtures + restart_intensity_exceeded + initial-state checks. Blast radius: a subtree (contained by design) up to the whole node (intentional escalation to a clean stop).

4.10 Operational Notes

Metrics: restart_count{child}, restart_intensity_exceeded, escalations, supervisor_strategy. Tracing: crash→strategy→restart/escalate span. act tree visualizes the hierarchy + restart counts (the operator's map of system health). Runbook crash-loop.md (diagnose the poison input causing escalation).

17. Phase 5 — Location-Transparent Addressing (ActorRef / Pid Resolution)

5.1 Objectives

Make addressing location-transparent (I11): ActorRef::send works identically whether the target is local or remote — the caller never branches on locality. Build the Pid resolution machinery: a per-node registry (local_id → cell), ResolveHint caching, and the seam where a Remote ref will (in P6/P7) serialize + hand off to the transport. Still single-node (remote path stubbed/dead-lettered) — this phase locks the API so P6/P7 plug in without changing application code.

5.2 Detailed Implementation Steps

  • act-addr::registry: local_id → CellPtr map (sharded, lock-free read); register on spawn, deregister on stop (with incarnation, I13). Applies ADR-013 (Pid{node,incarnation,local_id}), I13 (incarnation defeats stale-ref resurrection), P1 (no shared mutable state — registry reads are lock-free by design).
  • resolve.rs: ActorRef::send → resolve hint: Local → direct mailbox enqueue (P2); Remote(node) → (P7) serialize + transport; Unresolved → registry/cluster lookup, then cache. Applies P4 (location transparency), I11 (identical send API for local/remote), Waldo 1994 (transparent API, honest about partial failure semantics), Akka in Action (ActorRef resolution pattern).
  • deadletter.rs: unresolvable/dead target → DeadLetter{from,to,payload,reason} routed to a dead-letter actor. Applies P4 (never panic on unresolvable ref), I14 (at-most-once: a dropped send is a dead-letter, not a panic), I11 (location transparency — the caller's API is identical, failure surfaces through Dead-letter + monitor Down).
  • Pid made cluster-ready (node field meaningful; incarnation participates). Applies ADR-013, I13, P15 (wire + API SemVer stability — Pid is a stable public type).

5.3 Deliverable

Application code uses ActorRef::send with no locality awareness; locally it enqueues directly, remotely (stub) it dead-letters with NodeDown/NoSuchActor. The dead-letter stream is observable.

5.4 Acceptance Criteria

  • send API is identical for a (future) remote ref and a local ref (I11) — verified by a conformance test that swaps a local ref for a remote-stub ref with zero call-site change.
  • A send to a stopped/unknown actor dead-letters (no panic, no hang) with the correct reason.
  • Stale ref (pre-restart incarnation) resolves to dead, never to a new actor reusing the id (I13).
  • Local fast path skips serialization (measurably faster than the remote path).

5.5 Conformance Fixtures

conformance/lifecycle/{deadletter_unknown,deadletter_stopped,stale_incarnation_deadletter}, addr/{local_resolve,remote_stub_deadletter,api_transparency}.

5.6 Pitfalls

  • Resolution cache staleness (cached Local after the actor moved/died) → validate against incarnation; invalidate on Down/membership change (P9).
  • Leaky transparency (callers depending on local-only timing/ordering) → document that remote adds latency + at-most-once failure (principle 4, Waldo's note); transparency is API-level, not semantics-level.
  • Dead-letter loop (dead-lettering a dead-letter) → the dead-letter actor must not re-dead-letter.
  • Registry contention (a global lock on spawn/lookup at millions of actors) → shard + lock-free reads.
  • Incarnation reuse (node restarts, reuses ids with a fresh incarnation) → resolution must compare incarnation (I13).

5.7 Performance Concerns

Local resolve = O(1) sharded lookup (or cached Local ptr = zero lookup). The local send path must stay ~P2 mailbox cost (no serialization). Registry reads lock-free; writes (spawn/stop) sharded.

5.8 Edge Cases

Self-send via ref; ref to root; ref outliving its actor (dead-letter); two refs to the same actor (both resolve identically); ref serialized for later use (owned variant).

5.9 Failure Analysis

If transparency leaks (callers assume local semantics), distribution (P7+) introduces lost-message bugs that only appear remotely/under partition. Detection: the api-transparency fixture + dead-letter metrics. Blast radius: application correctness across the local→remote boundary.

5.10 Operational Notes

Metrics: dead_letters{reason}, registry_size, resolve_local, resolve_remote, resolve_miss. act ps lists actors via the registry. Dead-letters are a key debugging signal (messages going nowhere). The dead-letter actor is itself supervised.

18. Phase 6 — Wire Protocol: Framing, Serialization, Handshake

6.1 Objectives

Define + implement the binary wire protocol (no network yet — codec in isolation): length-prefixed frames (magic + version + len + type + header + payload), Envelope serialization (to/from/kind/seq + opaque payload), a versioned handshake (Hello), and the never-panic decoder on hostile bytes (I6, fuzzed). This is the contract two nodes will speak in P7; getting framing + bounds right here is the security boundary.

6.2 Detailed Implementation Steps

  • act-transport::frame: Frame struct + FrameType (Hello/Msg/Ping/PingReq/Ack/Gossip/Bye/ExitSig); FRAME_LEN bound (≤ 16 MiB, reject before alloc — I6). Applies P10 (wire decoder never trusts input), I6 (bounded decoder), ADR-006 (length-prefixed binary frames), ADR-016 (cargo fuzz gate), Appendix D (normative wire spec).
  • codec.rs: Codec::encode/decode; header = varint-packed; payload length-checked. Applies P10 (I6), ADR-005 (bincode-fixed internal, typed user payloads), ADR-006 (wire framing choice), quinn/tokio-tungstenite framing reference (codec discipline study).
  • serialize.rs: internal bincode-fixed; user payloads carry a TypeTag → deserializer registry. Applies ADR-005, I6 (unknown tag → dead-letter, never crash), P10 (closed tag registry), ADR-024 (SemVer stable TypeTag registry — tags are append-only within a major).
  • handshake.rs: Hello{proto_ver,node_id,incarnation,caps} encode/decode; version compatibility rule. Applies P15 (stable wire + API compatibility), ADR-024 (SemVer versioning), I13 (peer incarnation recorded at handshake), ADR-006 (versioned handshake header).
  • Property + fuzz: round-trip + arbitrary bytes never panic/OOB/OOM. Applies ADR-016 (cargo fuzz gate), I6, P10 (decoder security property).

6.3 Deliverable

A codec that round-trips envelopes + handshakes deterministically and survives arbitrary byte fuzzing without panic/OOM; act wire-test <hex> decodes a frame for debugging.

6.4 Acceptance Criteria

  • Round-trip: decode(encode(env)) == env for all conformance envelopes + handshakes (golden).
  • cargo fuzz on frame_decode/envelope_parse: 0 panics/OOB/OOM across 1e8 execs (I6).
  • Oversize FRAME_LEN rejected before allocation; truncated frame → Truncated; unknown type → UnknownType; unknown payload tag → UnknownTag (no panic).
  • Encoding is deterministic + version-stamped; cross-version Hello mismatch → typed reject.

6.5 Conformance Fixtures

conformance/wire/{roundtrip_msg,roundtrip_hello,malformed_oversize,malformed_truncated,unknown_type,unknown_tag,version_mismatch}, fuzz/fuzz_targets/{frame_decode,envelope_parse,handshake}.rs.

6.6 Pitfalls

  • Trusting FRAME_LEN → Vec::with_capacity(attacker_len) = instant OOM; bound before alloc (I6) — the classic remote-DoS.
  • Partial reads (TCP delivers fewer bytes than FRAME_LEN) → the codec must be incremental/stateful or buffer until the full frame arrives (P7 wires this).
  • Endianness / alignment drift → fix big-endian framing; never reinterpret-cast a byte buffer to a struct (UB) — parse field-by-field.
  • Varint overflow in header decode → bounded varint, reject overlong.
  • Type-tag collision / spoofing → tags are a closed registry; unknown → dead-letter, never execute.
  • Serialization version skew (a field added) → versioned + #[non_exhaustive]; older nodes ignore unknown trailing fields (forward-compat) within a major.

6.7 Performance Concerns

Encode/decode is on the remote hot path → minimize copies (encode into a reused BytesMut; decode borrows the buffer, Frame<'a>). Varint header is compact. Serialization cost dominates remote latency vs. local — measure (§4 remote targets). Zero-copy payload pass-through where possible.

6.8 Edge Cases

Empty payload; max-size payload (exactly 16 MiB); frame split across two TCP reads (P7); back-to-back frames in one read (P7 framing must split); a Hello with a future major version; a tag the receiver lacks.

6.9 Failure Analysis

A decoder panic/OOM = a remote, unauthenticated node-kill = a cluster-wide DoS (one bad node poisons peers). Detection: fuzz (pre-release, 1e8+) + bounds asserts + frame_error metric. Blast radius: the receiving node (contained — drop frame + close conn, don't crash). This is the highest-severity attack surface (Threat Model).

6.10 Operational Notes

Metrics: frame_errors{kind}, frames_encoded, frames_decoded, payload_bytes, unknown_tags. The wire format is documented normatively in docs/protocol/wire.md + Appendix D. Version negotiation logged at handshake. Fuzzing is a release gate.

19. Phase 7 — TCP Transport: Connections, Remote Send, Handshakes

7.1 Objectives

Put the P6 codec on the network: one TCP connection per peer, multiplexing all actor traffic + heartbeats; a connection state machine (connect → Hello handshake → established → closed); the remote send path wired into ActorRef::send (P5) so remote refs serialize + transmit, preserving per-sender FIFO over the connection (I4). Two actd nodes now exchange messages — distribution begins.

7.2 Detailed Implementation Steps

  • act-transport::connection: read/write halves over a TCP socket; incremental framing (buffer partial frames, split concatenated frames — P6 codec applied to the byte stream); inbound Msg frames → deserialize → enqueue on the target local cell's mailbox. Applies ADR-007 (one TCP conn per peer, multiplexed), I4 (per-conn FIFO = per-sender FIFO over the wire), I6 (decode never panics on partial reads), P10 (decoder total safety).
  • connpool.rs: per-NodeId connection; lazily dial; dedupe simultaneous dials; reconnect with jittered backoff. Applies P12 (explicit ownership of each TCP connection), I16 (graceful shutdown drains then closes conns), ADR-007 (one-conn tie-break), Akka Cluster/Artery reference (connection pool model).
  • handshake.rs (P6) driven on connect: exchange Hello; reject on version mismatch; record peer incarnation. Applies P15 (SemVer wire versioning), I13 (incarnation recorded at handshake), ADR-006, ADR-024 (version negotiation rule).
  • Wire P5's Remote resolution: serialize Envelope → enqueue on peer write queue (per-conn FIFO, I4) → peer decodes + delivers. Applies P4 (location transparency), I11 (identical send API), I4 (FIFO over connection).
  • act-daemon: actd listens on a TCP port; two-node compose demo. Applies ADR-020 (daemon + CLI), P14 (observability: metrics/tracing from the first remote send).

7.3 Deliverable

Two actd nodes (compose) pass messages: a local actor on A sends to a remote actor on B with the same send API; ping-pong across nodes works; FIFO per sender preserved over the wire.

7.4 Acceptance Criteria

  • Remote send delivers (steady state, no partition): A→B message arrives at B's actor with correct content (round-trip via the live wire).
  • Per-sender FIFO over the connection (I4): A sends m1..m100 to B's actor X → X receives them in order.
  • One connection per peer (verified: concurrent sends to B reuse one conn); reconnect on drop with backoff.
  • Handshake rejects an incompatible peer (version mismatch) cleanly (no crash).
  • Location transparency holds (I11): the same code that worked locally (P5) now works remotely with no call-site change.

7.5 Conformance Fixtures

conformance/wire/{remote_roundtrip,fifo_over_conn,reconnect_backoff,handshake_reject} (integration, compose-driven), benchmarks/remote_send.

7.6 Pitfalls

  • Frame boundaries across TCP reads → a stateful reader that accumulates until a full frame, then splits multiple frames in one buffer (the #1 framing bug).
  • Head-of-line blocking (one huge message stalls all traffic on the single conn) → bound message size; consider a separate lane for heartbeats so detection isn't blocked by data (cross with P9).
  • Connection storms (both nodes dial each other simultaneously → two conns) → a tie-break (lower NodeId.uid wins / keep one) to converge to a single conn.
  • Reconnect thundering herd after a blip → jittered backoff.
  • Write-queue unbounded (remote backpressure) → bound the per-conn write queue; apply backpressure to senders (a slow/dead peer must not OOM the sender — ties to I8).
  • Partial write / slow peer → non-blocking writes + backpressure; don't block a worker on a socket.

7.7 Performance Concerns

Remote path = serialize + frame + TCP write + RTT + read + deserialize + enqueue. Batch small messages per write (Nagle-aware; coalesce frames) to amortize syscalls. Reuse buffers. Target remote p99 ≤ 2 ms intra-DC; ≥ 200 k msgs/s/conn. Heartbeat lane kept lightweight.

7.8 Edge Cases

Self-node send (loopback → local fast path, skip TCP); a message to a node not yet in the cluster (dial or dead-letter); connection drops mid-stream (in-flight messages: default drop / ALO redeliver — P10); a peer that handshakes then goes silent (P9 detects); IPv4/IPv6; max-size frame over the wire.

7.9 Failure Analysis

A transport bug = lost/misordered/duplicated remote messages or a head-of-line stall that also blocks failure detection (a node looks dead because its heartbeats are stuck behind data). Detection: FIFO fixture, integration round-trip, separate heartbeat lane. Blast radius: a node pair (or the whole cluster if detection is blocked). Recovery: reconnect + (P10) redelivery in ALO.

7.10 Operational Notes

Metrics: connections{peer}, bytes_tx/rx, reconnects, write_queue_depth, remote_send_latency, frame_errors (from P6). Tracing: send→serialize→tx→rx→deserialize→enqueue span across nodes (distributed trace). act members (P8) will show peer connections. Runbook slow-node.md (HoL + write-queue growth).

20. Phase 8 — Cluster Membership (SWIM): Join, Leave, Gossip, Incarnation

20.1 Objectives

Implement SWIM membership (Das 2002, #197/#72): nodes join via a seed, maintain a member list through periodic ping + indirect ping-req (probe via k random members when a direct ping fails), and gossip membership updates (Alive/Suspect/Dead + incarnation) piggybacked on probes — converging in O(log N) rounds. Incarnation numbers let a node refute a false suspicion (I13). Graceful leave announces departure. This makes the cluster self-organizing.

20.2 Detailed Implementation Steps

  • act-cluster::seed: join(seed_addr) → Hello (P7) → fetch seed's member list → merge. Applies ADR-008 (SWIM over central registry), Das et al. 2002 (join via seed), I13 (incarnation recorded on merge), ADR-010 (AP posture — membership is eventually consistent).
  • swim.rs: periodic protocol — pick random member, ping; on no Ack, PingReq to k random members; still no ack → Suspect. Applies Das et al. 2002 (ping + ping-req protocol), ADR-008 (SWIM), ADR-009 (hands off to phi-accrual for continuous suspicion in P9), P7 (failure detection is a hint — SWIM confirms, phi-accrual scores).
  • gossip.rs: piggyback bounded membership updates on every ping/ack/ping-req (anti-entropy, Demers et al. 1987). Applies Das 2002 (infection-style gossip), Demers 1987 (epidemic dissemination), ADR-008 (gossip piggybacking strategy), I13 (apply by incarnation precedence).
  • incarnation.rs: node bumps incarnation to refute Suspect/Dead rumors; higher wins (I13). Applies Das 2002 (incarnation refutation), I13 (stale-state resurrection prevention), Dadgar/Lifeguard 2018 (local health multiplier reduces unnecessary suspicion).
  • member.rs: member list + state machine (Alive/Suspect/Dead, §8.7); leave() gossips Dead(self). Applies ADR-008, I16 (graceful leave), ADR-010 (AP: membership is available, not consistent).
  • splitbrain.rs: detect partition, surface (don't merge). Applies P8 (AP — surface split-brain, not fake consensus), Fischer/Lynch/Paterson FLP 1985 (impossibility of auto-resolution without consensus), ADR-010.

20.3 Deliverable

A 3+ node cluster (compose) self-forms via a seed; act members shows the converged member list on every node; a joining node is discovered cluster-wide in O(log N) rounds; a graceful leave is propagated.

20.4 Acceptance Criteria

  • N nodes join via a seed → all N converge to the same member list (within ≤ ~5 s for N ≤ 1000); join propagates in O(log N) gossip rounds.
  • A node bumping its incarnation refutes a false Suspect rumor → reinstated Alive cluster-wide (I13).
  • Graceful leave → all nodes mark it Dead/Left promptly (no waiting for detection timeout).
  • Membership state machine transitions match §8.7 on fixtures (join/suspect/refute/dead).
  • Split-brain (injected partition) → each side's member list reflects the split; the condition is reported via a metric/log, not auto-resolved (principle 8).

20.5 Conformance Fixtures

conformance/swim/{join_converge,gossip_propagation,suspect_refute_incarnation,graceful_leave,splitbrain_surface,convergence_logN} (compose/simulated network).

20.6 Pitfalls

  • Incarnation comparison bugs → a healthy node permanently evicted (can't refute) or a dead node resurrected; strict "higher incarnation wins, equal: Dead>Suspect>Alive" precedence (I13).
  • Gossip amplification (re-gossiping the same update forever) → bound update lifetime (gossip each update a limited number of times / TTL).
  • Slow convergence from too-small fan-out → tune ping period + piggyback size; O(log N) needs adequate gossip per round.
  • Seed single point of failure at join → support multiple seeds; once joined, membership is decentralized.
  • Ping-req to dead helpers → k random currently-alive members; skip Suspect/Dead helpers.
  • Clock dependence → SWIM uses timeouts, not synchronized clocks; suspicion timeout is local-relative (avoid wall-clock assumptions, cross with P9 clock-skew).

20.7 Performance Concerns

SWIM is O(1) messages per node per period (one ping + bounded gossip), independent of N (its key property) → scales to thousands of nodes with constant per-node load. Gossip piggybacks (no extra packets). Member list O(N) memory per node. Convergence O(log N) rounds.

20.8 Edge Cases

Single-node cluster (no peers to ping); seed unreachable at join (retry other seeds); a node that rejoins after leaving (new incarnation); simultaneous joins; a flapping node (Alive↔Suspect — suspicion timeout + Lifeguard-style dampening, P9); the partition heals (members re-merge by incarnation).

20.9 Failure Analysis

A membership bug = the cluster's view of "who's alive" diverges → messages routed to dead nodes (or live nodes wrongly evicted). Detection: convergence fixtures + per-node member-list comparison + cluster_size/incarnation metrics. Blast radius: cluster-wide routing correctness. Recovery: gossip + incarnation eventually re-converge (eventual consistency of membership).

20.10 Operational Notes

Metrics: cluster_size, members{state}, gossip_msgs, pings, ping_reqs, incarnation, suspect_transitions, splitbrain_detected. act members shows the live view; tools/member-viz renders the cluster .dot. Tracing: probe→suspect→gossip span. Runbook split-brain.md.

21. Phase 9 — Failure Detection (phi-accrual) + Remote-Ref Invalidation + Split-Brain

9.1 Objectives

Replace SWIM's binary suspicion timeout with a phi-accrual detector (Hayashibara 2004): track the distribution of heartbeat inter-arrival times per peer and output a continuous suspicion level φ; φ > threshold ⇒ suspect (feeds SWIM Suspect). Adaptive to jitter (a GC pause raises φ gradually, not a hard cliff). On a confirmed-dead node, invalidate its remote ActorRefs (sends fail-fast, monitors fire Down, I12) and finalize split-brain handling (surface, AP). This closes the partial-failure-visibility loop.

9.2 Detailed Implementation Steps

  • act-detector::heartbeat: periodic heartbeats on a dedicated lane (not the data conn) so data traffic cannot block detection (cross P7 HoL mitigation). Record monotonic arrival timestamps. Applies P10 (decoder security on heartbeat path), ADR-007 (dedicated heartbeat lane), ADR-009 (phi-accrual input), Dean & Barroso The Tail at Scale (HoL blocking is a latency tail-risk).
  • window.rs: sliding window of inter-arrival samples per peer → mean + variance. Applies Hayashibara 2004 (arrival-time distribution model), ADR-009 (phi-accrual core), I12 (feeds suspicion → Dead).
  • phi.rs: phi(peer, now) = −log10(P(arrival > now − last)) under the fitted distribution; rises smoothly on silence. Applies Hayashibara 2004 (normative formula), ADR-009 (continuous φ vs. binary timeout), P7 (detection is a hint — φ is probabilistic, not a fact).
  • suspicion.rs: φ > θ ⇒ Suspect → SWIM confirms via ping-req → Dead. Applies Hayashibara 2004 (threshold θ semantics), Dadgar/Lifeguard 2018 (local health multiplier to reduce cascades), Chandra & Toueg 1996 (◇P: eventually accurate detection), I12, ADR-009.
  • Ref invalidation: on Dead, act-addr invalidates refs → NodeDown fast-fail; monitors fire Down. Applies I12 (fail-fast, not hang), P4 (location transparency is honest about failure), Waldo 1994 (partial failure must surface, not be hidden), I7 (Down signal is like an exit signal).
  • splitbrain.rs finalize: both sides stay available, emit splitbrain_detected. Applies P8 (AP), FLP 1985 (no auto-resolution without consensus), ADR-010.

9.3 Deliverable

A node that dies (kill -9 / partition) is detected via rising φ within a bounded time; its remote refs fail-fast; monitors fire Down; a recovering node (transient pause) is not falsely evicted (φ falls). Chaos demo: kill a node, observe detection + ref failure + monitor Down.

9.4 Acceptance Criteria

  • Truly dead node detected within ≤ 3× heartbeat interval (φ crosses θ); confirmed via ping-req → Dead (P8).
  • False-positive rate ≤ 1% at θ=8 under normal jitter (a brief pause does not cross θ; the node refutes via incarnation if it does, I13).
  • Dead node's remote refs → send returns NodeDown fast-fail (not a hang); monitors on its actors fire exactly one Down{NodeDown} (I12).
  • Split-brain (partition): both sides available; splitbrain_detected raised; no auto-merge (principle 8).
  • φ falls back below θ when heartbeats resume (adaptive recovery).

9.5 Conformance Fixtures

conformance/detector/{phi_rises_on_silence,phi_false_positive_under_jitter,detect_dead_node,ref_invalidation_on_dead,monitor_down_on_nodedown,splitbrain_both_available}, chaos/{kill-node,partition,packet-loss}.

9.6 Pitfalls

  • Heartbeats blocked behind data (HoL on the shared conn) → φ spikes falsely → false death; use a dedicated heartbeat lane / separate the detection path (cross P7).
  • Threshold mis-tuned (θ too low → false positives → split-brain amplification; too high → slow detection) → expose θ; document the latency/accuracy tradeoff (principle 7).
  • Distribution mis-fit (assuming normal when arrivals are bursty) → use a robust estimator; clamp φ; bound the window.
  • Cascading eviction (a transient blip evicts several nodes at once) → Lifeguard-style local-health multiplier (slow down our own suspicion if we might be the slow one).
  • Ref invalidation race (a message in flight when the node is declared dead) → in-flight: default drop / ALO redeliver (P10); new sends fail-fast.
  • Clock skew affecting timestamps → use monotonic local clocks for inter-arrival, never wall-clock differences across nodes (cross chaos/clock-skew).

9.7 Performance Concerns

Heartbeats are O(peers) lightweight frames per interval; φ computation is O(window) per check (small). The detection path must be low-latency + jitter-resistant (it gates correctness of "who's alive"). Window memory O(peers × samples).

9.8 Edge Cases

A node that pauses exactly at θ (boundary — refute window); all peers silent (network down — am I partitioned? local-health dampening); a node oscillating around θ (flapping — suspicion hysteresis); detection during a rolling upgrade (don't evict upgrading nodes — drain first, Operational Readiness).

9.9 Failure Analysis

The deepest distributed-systems hazard: confusing slow with dead. A false death evicts a healthy node (loses its actors, fires spurious Downs, can amplify into split-brain). A missed death routes messages into a black hole. Detection: false-positive-rate fixture + φ traces + chaos. Blast radius: cluster-wide (membership + routing). This phase encodes principle 7 (detection is a hint).

9.10 Operational Notes

Metrics: phi{peer} (gauge — the key dashboard signal), suspect_events, dead_events, false_positive_estimate, down_signals{NodeDown}, splitbrain_detected, heartbeat_rtt. tools/phi-plot graphs φ over time (operator's detection view). Runbooks false-positive-death.md, slow-node.md, split-brain.md. Tuning: heartbeat interval, θ, window size.

22. Phase 10 — Delivery Semantics: At-Most-Once, At-Least-Once, Dedup, Ordering

10.1 Objectives

Make the delivery-semantics spectrum explicit and correct. Default = at-most-once (Erlang: a message is delivered 0 or 1 times; on failure it's dropped, I14) — fast, no bookkeeping. Opt-in = at-least-once (redeliver until ack; a bounded dedup window by (sender, seq) suppresses duplicates; per-sender FIFO ordering preserved, I15). Document the impossibility of exactly-once without dedup + idempotency (principle 8). This phase makes the runtime's reliability guarantees precise + selectable.

10.2 Detailed Implementation Steps

  • act-delivery::atmostonce: default path — no acks, no buffering; on connection failure/dead node, in-flight messages are dropped (I14). FIFO still holds (P2/P7). Applies ADR-011 (AMO default = Erlang semantics), I14, P8 (AP — drops are the price of availability under partition), Tanenbaum & Van Steen (at-most-once impossibility of improvement without bookkeeping).
  • atleastonce.rs: sender buffers unacked outbound by seq; redelivery timer (P1 timer-wheel) re-sends until Ack; bounded buffer (backpressure when full, I8). Applies ADR-011 (ALO opt-in), I15, I8 (bounded buffer), Helland 2007 (at-least-once activity model), Vernon Reactive Messaging Patterns.
  • ack.rs: receiver acks by seq; cumulative acks where possible. Applies I15, ADR-011, P5 (backpressure — cumulative acks amortize traffic).
  • dedup.rs: bounded dedup window per sender (seen seqs); duplicate within window → suppress + re-ack (I15); outside window → app must be idempotent. Applies I15, Helland 2007 (idempotency + at-least-once), Kleppmann DDIA ch.9 (exactly-once = dedup + idempotency), ADR-011.
  • ordering.rs: per-sender FIFO maintained across redelivery (reorder buffer for out-of-order arrivals). Applies I4 (per-sender FIFO), I15 (ALO ordered mode).
  • Delivery mode selectable per ActorRef/message class. Applies ADR-011, P8 (we do not claim exactly-once), ADR-029 (durable ALO is #163).

10.3 Deliverable

Both modes work: at-most-once (default, no overhead, drops on failure); at-least-once (redelivers + dedups + orders) — demonstrated across a partition + reconnect (messages survive a transient partition in ALO; are dropped in at-most-once).

10.4 Acceptance Criteria

  • At-most-once: under a partition, in-flight messages dropped (0 duplicates, possible loss, I14); no redelivery overhead in steady state.
  • At-least-once: under a partition + reconnect, every message delivered ≥1 time (no loss, I15); the dedup window suppresses duplicates within the window (receiver sees each seq once); per-sender FIFO preserved.
  • Exactly-once is not claimed; the doc + tests show ALO + dedup-window + idempotency is the closest achievable (principle 8).
  • Dedup window bounded (memory I8); a duplicate outside the window is delivered (documented; app idempotency required).

10.5 Conformance Fixtures

conformance/delivery/{atmostonce_drop_on_partition,atleastonce_redeliver,dedup_within_window,dedup_outside_window_delivered,ordering_preserved_under_redelivery,ack_cumulative}, chaos/partition.

10.6 Pitfalls

  • Unbounded ack/redelivery buffer (a permanently dead peer) → bound + apply backpressure / give up after intensity (don't buffer forever → OOM, I8).
  • Dedup window too small → late duplicates slip through (acceptable but document; app idempotency); too large → memory. Tune by RTT × redelivery rate.
  • Reordering under redelivery (a redelivered seq n arrives after n+1) → the reorder buffer must hold n+1 until n is delivered (ordered ALO), or relax ordering explicitly.
  • Claiming exactly-once → the cardinal distributed-systems sin; we explicitly do not (principle 8); "effectively-once" = ALO + idempotent handler.
  • Ack amplification (acking every message) → cumulative/batched acks.
  • Duplicate side effects (a non-idempotent handler runs twice on redelivery before dedup) → dedup must be before handler invocation.

10.7 Performance Concerns

At-most-once = zero bookkeeping (the fast default). At-least-once adds: outbound buffer + redelivery timers + receiver dedup set → memory + CPU; reserve for the messages that need it. Cumulative acks amortize. Reorder buffer bounded.

10.8 Edge Cases

A message acked but the ack is lost → redelivered → dedup suppresses (correct); a duplicate exactly at the window edge; ALO to a node that never recovers (give-up policy → dead-letter); ordering across a sender restart (incarnation resets seq — dedup keyed by (sender_pid_with_incarnation, seq)); mixed-mode (some messages ALO, some at-most-once).

10.9 Failure Analysis

Delivery bugs are insidious: silent loss (at-most-once misused for critical data) or silent duplication (ALO without dedup → double side effects). Detection: the partition+reconnect fixtures + redelivery/dedup_hit/dropped_on_failure metrics. Blast radius: application correctness. This phase forces the operator to choose semantics consciously (not assume exactly-once).

10.10 Operational Notes

Metrics: delivery_mode, redeliveries, dedup_hits, dropped_on_failure, unacked_buffer_depth, reorder_buffer_depth. Tracing: send→(buffer)→tx→ack / redeliver span. Docs: docs/design/delivery.md (the semantics matrix, Appendix E). Durable ALO (survive a sender crash) is deferred to #163 (PhaseDeferred("FD-2")) — ours is in-memory.

23. Phase 11 — Hardening: loom, Miri, Fuzz, Chaos

11.1 Objectives

Prove the concurrency + distribution correctness story: loom model-checks the mailbox + scheduler claim (exhaustive interleavings, I1/I4); Miri verifies the lock-free unsafe; cargo fuzz hardens the wire decoder (I6); chaos (kill nodes, partitions, packet loss, clock skew) validates membership + detection + delivery under faults. This is the gate that says "trustworthy under concurrency + failure."

11.2 Detailed Implementation Steps

  • loom/: mailbox_mpsc.rs (FIFO-per-producer, no lost/double, I4), scheduler_claim.rs (exclusive Ready→Running, I1), signal_lane.rs (priority correctness). Small models, exhaustive. Applies ADR-015 (loom over stress-test), I1/I4, Bos Rust Atomics and Locks (the memory-ordering rules loom exercises), P2 (one-at-a-time invariant).
  • Miri: run the lock-free mailbox + atomics under Miri (UB detection). Applies ADR-017 (Miri gate on unsafe paths), I2 (no UB = no data race), ADR-001 (Rust + Miri as safety guarantee).
  • cargo fuzz: frame_decode, envelope_parse, gossip_parse, handshake — 0 panics/OOB/OOM (I6); seed from conformance corpus. Applies ADR-016, I6 (decoder total safety), P10 (wire decoder never trusts input).
  • chaos/: kill-node, partition, packet-loss, clock-skew. Assert: cluster re-converges, detection works, delivery semantics hold, no panics. Applies Das 2002 (SWIM convergence property), Hayashibara 2004 (false-positive rate under jitter), ADR-009 (monotonic clock requirement), P7 (detection is a hint — not a fact), P8 (AP — assert availability, not consistency).
  • Property tests: per-sender FIFO under concurrency; supervision invariants; membership convergence. Applies I4, I5, ADR-015, ADR-008 (gossip convergence under reordering).

11.3 Deliverable

Green loom (all interleavings), Miri-clean, 24 h fuzz (0 crashes), a chaos report (cluster survives kills/partitions/skew with correct membership + detection + delivery).

11.4 Acceptance Criteria

  • loom: 0 violations of I1 (no double-run), I4 (FIFO/no-loss), signal priority — across all interleavings of the small model.
  • Miri: no UB on the lock-free paths.
  • Fuzz: 0 panics/OOB/OOM across ≥ 1e9 execs on all decode targets (I6).
  • Chaos: kill a node → detected (P9), refs invalidated (I12), supervisors react (P4), cluster re-converges (P8); partition → both sides available + split-brain surfaced (principle 8); packet loss → ALO redelivers (I15), at-most-once drops (I14); clock skew → detection uses monotonic clocks (no false death). No panic in any scenario.

11.5 Conformance Fixtures

loom/*, fuzz/corpus/*, chaos/{kill-node,partition,packet-loss,clock-skew} scenarios + assertion scripts; conformance/** regression rerun under chaos.

11.6 Pitfalls

  • loom state-space explosion → keep models tiny (2 producers, 1 consumer, few messages); test the protocol, not throughput.
  • Fuzz finds a real OOM (oversize alloc) → the bound (I6) was wrong; fix + regress.
  • Chaos flakiness (timing-dependent assertions) → assert eventual properties (convergence within a bound), not instantaneous.
  • Clock-skew false death → confirms the monotonic-clock requirement (P9); a regression here re-breaks detection.
  • Partition assertion asserting consistency (we're AP) → assert availability + split-brain surfaced, not consistency.
  • Heisenbugs under Miri/loom that don't repro normally → these are real (memory-ordering) bugs; trust the model checker.

11.7 Performance Concerns

Hardening tools are off the production path (CI/nightly). Chaos measures degraded-mode behavior (latency under partition, recovery time). loom/Miri are slow (acceptable in CI). Fuzz runs nightly + smoke on PR.

11.8 Edge Cases

Simultaneous node kills (multiple failures); a partition that heals then re-splits (flapping); skew larger than the heartbeat interval; a fuzz input that is a valid-but-adversarial frame (huge but in-bounds → must process, not OOM); loom with the signal lane interleaved with user enqueues.

11.9 Failure Analysis

Any loom violation, Miri UB, or fuzz crash is a release blocker (a concurrency data race or a remote DoS). A chaos failure (cluster doesn't re-converge, false cascade) is a distributed-correctness bug. Detection is the purpose of this phase. Blast radius (if shipped): memory-safety incident (loom/Miri/fuzz) or cluster outage (chaos).

11.10 Operational Notes

Metrics during chaos: recovery time, false-positive deaths, dropped/redelivered counts, convergence time. CI gates: loom + Miri + fuzz-smoke on PR; 24 h fuzz + full chaos nightly. Runbooks updated from chaos findings. This phase certifies the invariants I1–I16 hold under adversity.

Compatibility & Versioning

Wire protocol: versioned in the Hello handshake (proto_ver). Rule: nodes of the same major interoperate; a minor difference negotiates to the lower minor (forward-compatible additive frame types/fields via #[non_exhaustive]); a major difference → handshake reject (no silent misinterpretation). New FrameType/MsgKind/SystemMsg variants are additive → minor. This makes rolling upgrades within a major safe (a cluster runs mixed minor versions during a rollout).

Public API: SemVer (ADR-024) on Pid, NodeId, ActorRef, Envelope, ExitReason, the Actor/Message traits, Context, Strategy/RestartPolicy, Delivery. Additive enum variants (#[non_exhaustive]) + new methods (default impls) → minor; field removal / trait-signature change / variant-semantics change → major.

Serialization: the envelope header format is versioned with the wire protocol; user payloads carry a TypeTag — adding a tag is additive (older nodes dead-letter unknown tags, I6); changing a tag's meaning is a breaking change requiring a major bump. Delivery semantics are a stable contract: at-most-once and at-least-once behaviors do not change within a major; exactly-once is never offered (principle 8). Membership/incarnation semantics (SWIM state machine, incarnation precedence) are stable within a major. Adjacent runtime versions in one cluster must agree on the SWIM + φ protocol majors.

  • Integration — multi-node docker-compose: remote send round-trip, FIFO over the wire, join/leave/converge, handshake reject.
  • Chaos / fault injection — kill-node, partition, packet-loss, clock-skew (Phase 11); assert convergence + detection + delivery + 0 panics under faults.
  • Conformance — conformance/** golden traces per subsystem (lifecycle, supervision, mailbox, wire, swim, detector, delivery).
  • Soak — ≥ 72 h multi-node under load: no leak, stable membership, deterministic per-actor, 0 panics (Phase 12).
  • Differential (where applicable) — supervision-strategy behavior vs. documented OTP semantics; SWIM convergence vs. the paper's expected rounds.
  • Performance regression (criterion) — latency/throughput/spawn/convergence vs. §4 thresholds in CI.

Weighting favors loom + fuzz + chaos: the failures that matter are silent concurrency bugs (data races on actor state), remote DoS (decoder), and distributed-correctness bugs (false death, lost/dup messages, non-convergence).

Scalability Analysis

Two scaling axes. Vertical (per node): more cores → more workers → near-linear message throughput until (a) the run-queue / work-steal becomes contended (mitigate: per-core queues, batched steals), (b) a hot actor (many senders → one mailbox) serializes (mitigate: shard the hot actor — it is a single-threaded point by design, principle 2), or (c) allocator/memory bandwidth saturates. Actors-per-node is bounded by cell_overhead × N + mailbox bytes → keep cells lean for millions. Horizontal (cluster): SWIM gives O(1) message load per node per period independent of N (its defining property) → membership scales to thousands of nodes; gossip converges in O(log N) rounds; member-list memory is O(N) per node. Bottlenecks at cluster scale: (1) cross-node fan-out (a broadcast to many actors on many nodes — mitigate with pub/sub overlay, #58, or hierarchical routing); (2) detector load O(peers) heartbeats (mitigate: heartbeat a random subset, SWIM-style, not all-to-all); (3) split-brain risk rises with partition probability (AP — surfaced, not solved). Coordination overhead: deliberately near-zero (no consensus — AP); the cost is no strong consistency (that's #42). No persistence → no storage-growth or compaction concern in the core (durable = #163). Linear scaling with cores + nodes is the design intent; the ceilings are hot-actor serialization (vertical) and broadcast fan-out (horizontal), both architectural (shard / route), not runtime limits.

Mental Models & First Principles

MM1 — An actor is a unit of failure, not a unit of computation. The compressed insight: the actor boundary exists for fault isolation, not for parallelism. A supervisor tree is not an optimization structure — it is a fault-containment boundary. Predicts: a crash in one actor cannot corrupt another's state; a crash in a subtree escalates cleanly up to a bounded recovery point. Bug class without it: writing try/catch inside handlers to avoid supervision (hiding faults from the tree, defeating the reliability model). Applying §: §6 P3/P6, Phase 4 (supervision tree), §7 I9/I10.

MM2 — The mailbox is the actor's event loop; one message at a time is not a restriction, it is the contract. An actor's handle method is not "called concurrently sometimes" — it is always called one at a time, with the actor owning its state exclusively for the full duration. Predicts: no lock needed inside a handler; the actor is a single-threaded sequential processor. Bug class without it: adding a Mutex around actor state "for safety," indicating the programmer has confused actor isolation with thread safety. Applying §: §6 P2, §7 I1, Phase 0/Phase 2 (cell claim), §11 Actor trait.

MM3 — Location transparency is an API contract, not a semantics contract. ActorRef::send looks identical whether the target is on the same core or across a continent. The API is transparent; the failure semantics are not — a remote send can silently drop (at-most-once under partition) in a way a local send never does. Predicts: a slow → dead detection pipeline (phi-accrual → SWIM) is mandatory to surface remote failure; dead-letters and monitors are not optional observability, they are the only way to detect dropped remote sends. Bug class without it: treating a remote ActorRef like a local one and assuming delivery, leading to silent message loss on partition. Applying §: §6 P4, §7 I11/I14, Phase 5 (ActorRef resolution), Phase 9 (ref invalidation), Waldo 1994 paper.

MM4 — A failure detector is a hint with a confidence level, never a fact. The phi-accrual detector outputs a continuous suspicion level φ, not a binary dead/alive verdict. A node declared dead may be alive (a false positive from a GC pause). The system must accommodate false positives gracefully (incarnation refutation) and tolerate them with designed-in recovery paths. Predicts: a node recovering from a false death refutes via a higher incarnation and rejoins; no irreversible damage. Bug class without it: treating a "dead" verdict as ground truth and immediately deleting all state associated with a node, losing actors and refs that could have been recovered. Applying §: §6 P7, §7 I12/I13, Phase 9 (phi.rs, suspicion.rs, incarnation refutation).

MM5 — Exactly-once delivery does not exist; it is an alias for at-least-once + idempotency. In an asynchronous unreliable network (FLP), a sender cannot distinguish "message lost" from "message delivered but ack lost." The minimum viable exactly-once approximation is: redeliver until ack (at-least-once) + deduplicate on the receiver side (dedup window) + ensure the handler is idempotent for out-of-window duplicates. Predicts: any system claiming "exactly-once" either has a dedup window (and an idempotency requirement for late duplicates) or is lying. Bug class without it: trusting a "guaranteed delivery" abstraction, building non-idempotent handlers, and then discovering duplicate side effects (double-charges, double-commits) on reconnect. Applying §: §6 P8, §7 I14/I15, Phase 10 (dedup.rs, ALO semantics), Appendix E, Helland 2007, FLP 1985.

MM6 — SWIM gives O(1) load per node, not O(N) — that is the entire point. Naive heartbeat-based membership requires each node to heartbeat every peer: O(N) messages per period per node, O(N²) cluster-wide. SWIM's insight: ping one random peer per period, piggyback gossip on probes. Each node sends O(1) probes/period; membership changes disseminate in O(log N) gossip rounds. Predicts: SWIM membership is practical at thousands of nodes; naive all-pairs heartbeating is not. Bug class without it: implementing an O(N)-per-node heartbeat loop thinking it is equivalent to SWIM, then observing the cluster saturate its own network at N=500. Applying §: §6 P7 (hint not fact — SWIM probe is the confirmation), Phase 8 (swim.rs, gossip.rs, gossip piggybacking), Scalability Analysis.

MM7 — The M:N scheduler is an implicit message queue with fairness guarantees; reduction counting is its preemption mechanism. A thread-per-actor model gives each actor its own OS thread — correct but wasteful at millions of actors. M:N maps M actors to N OS threads; the reduction budget is the preemption point that prevents a hot actor from monopolizing a worker. Predicts: without reduction counting, a message-tight actor loop starves all other actors on that worker. Bug class without it: building a "fiber" scheduler without a fairness bound, seeing latency spikes when one actor receives a burst. Applying §: §6 P11, §7 I3, Phase 1 (reductions.rs, worker.rs), BEAM scheduler ERTS paper.

MM8 — The wire decoder is a security boundary; frame length must be validated before allocation. Every inbound byte on the TCP socket is potentially hostile. The canonical remote DoS: a crafted frame with FRAME_LEN = 4 GiB causes the receiver to allocate 4 GiB before reading any payload. The fix is to validate FRAME_LEN against the configured maximum before any allocation. Predicts: a decoder that allocates first and checks second is a remote OOM vector. Bug class without it: a Vec::with_capacity(attacker_controlled_len) crash/OOM on a single malformed packet. Applying §: §6 P10, §7 I6, Phase 6 (codec.rs, Appendix D decoder safety rules), Threat Model.

Back-of-Envelope Capacity Model

All derivations from §4 System Constraints table. All numbers are for a representative 8-core node with 32 GiB RAM.

C1 — Actor count ceiling (memory):

  • From §4: cell overhead ≤ ~256 B fixed + state. Assume minimal stateless actor (state = 0 B extra): 256 B/actor.
  • Available actor-cell memory budget: 32 GiB × 0.5 (leaving 50% for mailboxes + transport buffers) = 16 GiB.
  • Maximum actors: 16 GiB / 256 B = 16 × 2³⁰ / 256 = 67 M actors. Safety target: ≤ 10 M active with state.
  • §4 target: ≥ 1 M live actors — we have ≥ 67× headroom with a 32 GiB node at 256 B/cell.

C2 — Mailbox memory ceiling (per node):

  • From §4: mailbox cap = 1024 envelopes/actor default; Envelope ≈ 128 B (header) + avg 256 B payload = 384 B.
  • 1 M actors × 1024 envelopes × 384 B = 384 GiB. This is why the memory ceiling is enforced per-node, not per-actor-class: a global cap of 4 GiB for mailboxes = max 10.4 M envelopes in-flight.
  • Practical limit: set mailbox_cap low (64–256) for most actors; reserve large caps for known-hot actors. At cap=64: 1 M actors × 64 × 384 B = 24 GiB — fits in 32 GiB alongside cells.

C3 — Local message throughput (M:N scheduler):

  • From §4: ≥ 10 M msgs/s/node on 8 cores = 1.25 M msgs/s/core.
  • Per-message cost estimate: claim CAS (~5 ns) + dequeue (~10 ns) + handle (application: assume 20 ns) + re-enqueue (~5 ns) = ~40 ns/msg → 25 M msgs/s/core theoretical upper bound.
  • With reduction-yield overhead (every 2000 msgs) and work-steal (amortized): ~60% efficiency = 15 M msgs/s/core → 8 cores = 120 M msgs/s. Target 10 M/s leaves ≥ 12× headroom for real application handler costs.

C4 — Remote message throughput + bandwidth:

  • From §4: ≥ 200 k msgs/s/connection.
  • Envelope size: 128 B header + 256 B avg payload = 384 B/msg.
  • 200 k msgs/s × 384 B = 76.8 MB/s = 614 Mbit/s per connection. A 10 Gbit link supports ~16 such connections at full throughput.
  • With batching (coalesce 10 msgs/write): syscall overhead amortized; effective encoding bandwidth ≈ 3.84 GB/s — well within a modern NIC.

C5 — TCP connection count (FD budget):

  • From §4: one TCP connection per peer. A 1000-node cluster → each node holds 999 peer connections.
  • Plus control UDS socket, heartbeat lanes, CLI socket: ~1005 FDs/node.
  • Default FD limit on Linux is 1 M (ulimit -n). 1000 peers well within limits; tune ulimit for >10k-node clusters.

C6 — SWIM gossip bandwidth:

  • From §4: ping interval 1 s; gossip piggybacked on ping/ack/ping-req.
  • Per probe: 1 Ping frame (~200 B) + k=3 PingReq if needed (~600 B) + ack (~200 B) + gossip payload (~50 B × bounded updates).
  • Per node/second: 1 probe out + 1 ack in ≈ 400 B/s gossip traffic per node. For 1000 nodes: 400 kB/s cluster-wide gossip. Negligible vs. application traffic.

C7 — Heartbeat bandwidth for phi-accrual:

  • From §4: heartbeat interval 1 s; one heartbeat frame per peer per interval.
  • Per node: (N−1) heartbeats/s × ~64 B/frame. For N=1000: 999 × 64 B/s = 63.9 kB/s → 0.5 Mbit/s. Dominated by application traffic even at 1000 nodes.

C8 — Dedup window memory (at-least-once mode):

  • From §4: dedup window per sender keyed by (sender_pid, seq). Assume 16 B/entry (8 B key + 8 B seq).
  • Window size = RTT × redelivery rate. Intra-DC RTT 1 ms; redelivery at seq ≈ 1k msgs/s/sender: window = 1 ms × 1 k = 1 entry. But bursty: practical window = 10k entries per sender pair.
  • 100 unique senders × 10k entries × 16 B = 16 MB per receiving actor in high-fan-in case. Bounded per §4 (I8).

C9 — Spawn storm latency:

  • From §4: spawn p99 ≤ 5 µs local; 1 M actors in ≤ 10 s.
  • 1 M actors / 10 s = 100 k spawns/s = 10 µs/spawn average. At 5 µs p99, the spawn path must be the cheapest path (cell allocation + registry insertion + first-enqueue). Memory allocation at 256 B/cell + 256 B/mailbox-ring: ~512 B/spawn → 512 MB total for 1 M actors (fits in RAM).

C10 — Phi-accrual window memory:

  • From §4: φ-accrual window samples per peer. Typical window: 1000 samples/peer × 8 B (f64 timestamp) = 8 kB/peer.
  • For 1000 peers: 8 kB × 1000 = 8 MB total for the phi detector. Negligible.

Alternative Architectures (Roads Not Taken)

Alt-1 — Shared-Memory Message Bus (Go-Style CSP Channels)

goroutines / green-threads
  │  send(ch, msg)
  ▼
  [channel buffer]   ← shared memory, GC-managed
  │  recv(ch)
  ▼
goroutine B (any goroutine can own B's "state" if not disciplined)

Regime where it wins: Co-located services on a single host where goroutine-level channels (Go chan) provide cheap and ergonomic CSP-style concurrency without the overhead of actor message serialization or mailbox allocation. Works well when the concurrency domain is bounded (100s–10ks of goroutines) and the performance ceiling of a global GC is acceptable.

Real system: Go's standard library and Kubernetes scheduler use goroutines + channels. The Go runtime does not enforce private state — the programmer must discipline themselves.

Why rejected: (a) Go's GC introduces unpredictable latency spikes incompatible with the latency targets (p99 ≤ 10 µs local). (b) Channels do not enforce ownership — shared mutable state is possible and common (the bug class the actor model eliminates). (c) No built-in supervision tree — fault handling is if err != nil everywhere. (d) Distribution requires bolting on gRPC or similar (no location transparency). This architecture trades safety and fault isolation for simplicity at small scale.

Alt-2 — Persistent Actor Model with WAL-Backed State (Event-Sourcing Style)

Actor A
  │  handle(msg) → emit(Event) → persist to WAL (disk)
  ▼              ← replay WAL on restart (no state loss)
  [durable state]     ← actor survives crashes AND node restarts

Regime where it wins: Financial and transactional systems where actor state must survive node restarts (not just within-session crashes). The durable execution model (Temporal, Akka Persistence, Durable Objects) gives effectively-once processing end-to-end because the actor's state and its message acknowledgements are co-committed to durable storage.

Real system: Akka Persistence (event sourcing, LevelDB/Cassandra backend), Microsoft Durable Task Framework, Cloudflare Durable Objects (V8 isolate + SQLite).

Why rejected: Durable persistence introduces a write-ahead log on every state transition, turning a sub-microsecond local message into a storage-bound operation. This fundamentally changes the latency model (p50 goes from 1 µs to 10s of µs or more) and makes the cell-overhead budget meaningless at millions of actors. The explicit non-goal is captured in ADR-029 and PhaseDeferred("FD-2") — this runtime is the non-durable layer; #163 (Durable Execution) adds the WAL layer on top.

Alt-3 — Virtual Actor Model (Orleans-Style, Automatic Placement)

Client call: grain_ref("account-42").deposit(100)
    │  (caller does not know or care which node activates it)
    ▼
Orleans runtime: is grain-42 active? → no → activate on node X
    │  route call to node X
    ▼
Grain-42 on node X  (single-activation guaranteed by runtime)

Regime where it wins: Large-scale cloud services where the actor count is huge (millions of unique entities), activation is dynamic and unpredictable, and the caller should not need to specify or know actor placement. Orleans' virtual-actor model provides "stateful serverless" ergonomics: callers just invoke a grain ID, the runtime handles activation, deactivation, and location.

Real system: Microsoft Orleans (.NET), Cloudflare Durable Objects, Halo's matchmaking service originally used Orleans at scale.

Why rejected: Single-activation guarantees require a coordination protocol at the placement layer (a consistent registry or a CP membership protocol) — this introduces the consensus overhead this runtime deliberately avoids (ADR-010). Explicit placement (ADR-027) is the right choice for telecom-style systems where the application architect knows and controls actor topology. The virtual-actor model is noted in the Comparative Architecture Table.

Alt-4 — Shared-Nothing Message Bus (Kafka-Style Partitioned Log)

Producer actors → write to Topic[partition=hash(key)]
    │  (durable, replicated, ordered per partition)
    ▼
Partition leader (broker) → replicates to followers (ISR)
    │  consumer groups pull at their own pace
    ▼
Consumer actors → process + commit offset

Regime where it wins: Systems where the primary requirement is durable, ordered, multi-consumer fan-out of messages — audit logs, event sourcing pipelines, CDC (change data capture), stream processing. Kafka is CP (ISR replication + controller epoch) on the durability axis, providing at-least-once delivery with exactly-once achievable via transactional producers + idempotent consumers.

Real system: Apache Kafka (LinkedIn, 2011), Confluent Platform, AWS MSK. Used in Uber (trip events), LinkedIn (activity streams), Netflix (operational data pipeline).

Why rejected: Kafka is a durable log broker, not an actor runtime. It does not provide: actor addressing (Pid/ActorRef), supervision trees, failure detection (phi-accrual), location transparency, or per-actor behavioral encapsulation. Sending a "message to actor X" requires knowing which partition X's messages land in. Cross-actor interactions (A sends to B which replies to C) become complex routing graphs in Kafka, not simple ActorRef sends. This runtime's use case — building a concurrent fault-tolerant application runtime with millions of in-memory actors — is orthogonal to Kafka's log-durability use case.

Appendix D — Wire-Protocol Reference

D.1 Frame header (on the TCP byte stream, big-endian)

offset  size  field        notes
0       2     MAGIC        0xAC70 (reject mismatch → BadMagic, close conn)
2       2     VERSION      proto_ver (u16); handshake-negotiated; major mismatch → reject
4       4     FRAME_LEN    u32, bytes following this field (bound ≤ 16 MiB BEFORE alloc, I6)
8       1     FRAME_TYPE   Hello0 Msg1 Ping2 PingReq3 Ack4 Gossip5 Bye6 ExitSig7
9       var   HEADER       per-type (Msg: to/from/kind/seq as varints + TypeTag)
...     ...   PAYLOAD      opaque (user) or typed (system); length implied by FRAME_LEN - header

D.2 Per-type header/payload

Type Header Payload
Hello(0) proto_ver, node_id(name,addr,uid), incarnation, caps —
Msg(1) to:Pid, from:Pid, kind:MsgKind, seq:u64 serialized message (TypeTag-led for User)
Ping(2) seq piggybacked gossip updates (bounded)
PingReq(3) target:NodeId, seq piggybacked gossip
Ack(4) seq (echo) piggybacked gossip
Gossip(5) count [(node, state, incarnation)] updates
Bye(6) reason — (graceful leave / shutdown, I16)
ExitSig(7) from:Pid, to:Pid, reason:ExitReason — (remote link/exit propagation, I7 across nodes)

D.3 Handshake sequence

A connects to B (TCP) → A sends Hello{ver,A_id,A_inc,caps} → B validates ver (same major?)
  ok  → B replies Hello{ver',B_id,B_inc,caps} → A validates → ESTABLISHED (record peer incarnation)
  bad → B sends Bye{VersionMismatch} + closes (handshake_reject++) — no Msg ever exchanged
both record each other in the member list (Alive) ; subsequent Msg/Ping/Gossip multiplexed on this conn

D.4 Decoder safety rules (I6)

1. Read 8 header bytes; verify MAGIC, VERSION.            (else BadMagic / version reject)
2. Read FRAME_LEN (u32). If FRAME_LEN > MAX (16 MiB) → OversizeLen, close. DO NOT allocate.
3. Buffer until FRAME_LEN bytes present (handle partial TCP reads); else wait (not error).
4. Parse HEADER field-by-field (varints bounded; no reinterpret-cast → no UB).
5. PAYLOAD length = FRAME_LEN - header_len ; bound-checked slice (never past buffer).
6. User payload: read TypeTag → registry lookup → deserializer | UnknownTag → dead-letter (not crash).
Any step's failure → typed FrameError → drop frame + close conn ; NEVER panic/OOB/OOM. Fuzz-verified.

D.5 Versioning + negotiation

  • VERSION major = wire incompatibility (reject); minor = additive (negotiate to min(minor)).
  • New FRAME_TYPE / MsgKind variant = additive (#[non_exhaustive]); an older node receiving an unknown type → ignore/drop that frame (forward-compat within a major), never misinterpret.
  • TypeTag registry is append-only within a major; meaning never changes (Compatibility & Versioning).

Property At-most-once (default, I14) At-least-once (opt-in, I15) Exactly-once
Delivery count 0 or 1 ≥ 1 (not offered)

Key impossibility (principle 8, Helland/Kleppmann): exactly-once delivery does not exist in an unreliable network; what is achievable is at-least-once + deduplication + idempotent processing = "effectively once." The dedup window makes this practical for the common case (duplicates arrive close together); truly late duplicates (outside the window) require an idempotent handler. We expose AMO and ALO honestly and never label anything "exactly-once."

            recovery is one well-tested path (restart), faults are visible (exit signals + metrics),
