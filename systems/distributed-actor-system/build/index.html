⬜ Phase 0 — Actor Trait, Single-Thread Runtime, Mailbox, Spawn/Send, CLI §12

Objectives

The actor core, single-threaded: an Actor trait (handle/init/terminate), a Context (spawn/send/self/stop), a bounded mailbox (FIFO, mutex-backed for now — lock-free lands P2), a single-thread executor that runs ready cells one message at a time (I1), and a CLI demoing a small actor tree. Establish from line one: one message at a time, no shared state, bounded mailbox.

Deliverable

act demo runs an actor tree single-threaded: messages handled one-at-a-time in FIFO; cargo test shows deterministic state evolution; a panicking actor stops cleanly without taking down the runtime.

Acceptance
  • Counter actor receiving Inc×1000 ends at 1000, processed strictly in order (I1/I4).
  • Mailbox at capacity with Fail policy returns MailboxFull (I8); with Block, sender throttles.
  • Panic in handle → cell Stopped, runtime survives, other actors keep running (I7 precursor).
  • No unsafe; no shared mutable state (compiles only because state is owned, I2).
Fixtures

conformance/lifecycle/{spawn_handle_stop,panic_stops_cell}, mailbox/{fifo_order,backpressure_fail,backpressure_block}. Golden: ordered message log per actor.

Pitfalls
  • Re-entrant send during handle (an actor sends to itself) → must enqueue, not recurse (avoid stack blowup / re-entrant borrow of state).
  • became_ready race (two enqueues both think they made it ready) → exactly-once notify even single-threaded (sets the contract P2 must keep lock-free).
  • Catching panics but leaving the cell in a half-mutated state → on panic, the cell is terminated, not resumed (state is abandoned — crash-only, principle 6).
  • Borrow of state across an await (when async lands) → P0 is sync; keep handle non-async or carefully Pin later.

⬜ Phase 1 — M:N Scheduler: Thread-per-Core, Work-Stealing, Reduction-Count Preemption §13

Objectives

Replace the single-thread loop with a true M:N scheduler: W worker threads (one per core), each with a run-queue of ready cells; work-stealing balances load; reduction-count preemption (Erlang-style) bounds per-activation work for fairness (I3); idle workers park. Preserve I1 (a cell never runs on two workers) via a lock-free claim. This is the #54/#129/#131 cross-link.

Deliverable

The same act demo now runs across all cores; a microbenchmark shows linear-ish scaling with worker count; a "hot" actor in a tight loop does not starve others (reduction preemption observable in traces).

Acceptance
  • Throughput scales with cores (e.g. 4× workers → ≥ 3× msgs/s) up to mailbox/contention limits.
  • A hot actor yields every reduction_budget messages; other actors on the same worker make progress (fairness fixture; reduction_overrun=0 beyond budget).
  • loom model-check (small config) proves the Ready→Running claim is exclusive (I1) under all interleavings.
  • Idle CPU ≤ 1% when no work (parking works); wake latency p99 bounded.
Fixtures

conformance/lifecycle/scheduler_fairness, loom/scheduler_claim.rs, benchmarks/{spawn,local_send} baselines per worker-count.

Pitfalls
  • Lost wakeup (cell becomes ready but the parking worker isn't woken) → actor stalls forever; pair the ready-flag store with the unpark via correct memory ordering (acquire/release) + re-check after parking.
  • Double-claim (two workers run the same cell) → data race on private state, I1 violation; the CAS must be the single source of truth (loom-verified).
  • Reduction accounting drift (counting differently across message types) → unfair scheduling; define reduction cost precisely (1/message default + optional cost hooks).
  • Work-stealing thrash (cells bouncing between workers, cache cold) → steal in batches; prefer local; back off.
  • Priority inversion (signal lane starved) → P3's signal lane must preempt user-msg processing.

⬜ Phase 2 — Lock-Free Bounded Mailbox + Backpressure Policies §14

Objectives

Replace the mutex mailbox with a lock-free bounded MPSC queue (many senders, single consumer), wait-free on the single-producer fast path, with the full backpressure policy set (Block/DropNewest/DropOldest/Fail, I8) and a priority signal lane so system messages (Link/Exit/Stop) bypass a user-message backlog. Memory-order-correct (Miri/loom).

Deliverable

Mailbox is lock-free; under a multi-producer benchmark it sustains target enqueue rates with no global lock; backpressure policies demonstrably bound memory under a flood; system signals jump the queue.

Acceptance
  • loom/mailbox_mpsc.rs: FIFO-per-producer + no-lost-message + no-double-consume across all interleavings (I4); Miri-clean (no UB in the atomics).
  • Flood test: producer >> consumer → memory bounded at cap × envelope_size regardless of flood duration (I8); each policy behaves per spec (drop counts, block throttles, fail returns).
  • A Stop signal sent behind 10k queued user messages is processed before them (signal lane).
Fixtures

conformance/mailbox/{fifo_multiproducer,policy_block,policy_dropnewest,policy_dropoldest,policy_fail,signal_lane_priority}, loom/mailbox_mpsc.rs, fuzz n/a (internal), bench local_send multi-producer.

Pitfalls
  • ABA on the ring (slot reused while a producer holds a stale index) → use sequence-numbered slots (Vyukov-style MPMC/MPSC), not raw CAS on pointers.
  • Memory ordering too weak → consumer sees a half-written envelope; publish the payload with Release, consume with Acquire.
  • Backpressure deadlock (Block policy: actor A's handler sends to full mailbox of B which is waiting on A) → Block must be a yielding await (the worker keeps running other cells), never a thread-block that stalls the worker.
  • Signal-lane starvation of user messages (always draining signals first under a signal flood) → signals are rare/bounded by design; cap per-tick signal drain.
  • Drop accounting lost → every drop increments messages_dropped (observability).

⬜ Phase 3 — Lifecycle, Links, Monitors, Exit Signals §15

Objectives

Implement the fault-propagation primitives beneath supervision: links (bidirectional fate-sharing — if A is linked to B and B crashes abnormally, A receives an exit signal and, by default, also terminates), monitors (unidirectional — A monitors B, gets a Down{B,reason} message but is not killed), and reliable exit-signal delivery to a crashed actor's supervisor (I7). Full lifecycle: graceful stop vs. crash, terminate hook, notify linked/monitored parties.

Deliverable

Linked actors share fate; monitoring actors get Down notifications; a crashing actor reliably notifies its supervisor (trap-exits). Demo: a worker crash propagates to a linked sibling; a monitor logs the death without dying.

Acceptance
  • A crashes (Panic) → linked B (not trapping) also terminates with Exit{A,Panic}; linked S (trapping) receives Exit{A,Panic} as a message and survives (I7).
  • A monitor of A receives exactly one Down{A,Panic}; demonitor stops further notices.
  • Normal exit of A → linked non-trapping B is not killed (only abnormal propagates).
  • No exit signal is ever lost, even with A's killer message arriving amid a 10k user-message backlog (signal lane, I7).
Fixtures

conformance/supervision/{link_propagate_abnormal,link_no_propagate_normal,trap_exit_survives,monitor_down,demonitor}, golden signal/down traces.

Pitfalls
  • Lost exit signal behind user backlog → must use the signal lane (I7); a regression here silently breaks supervision.
  • Link cycle storm (A↔B↔C linked, one crash cascades) → propagation is correct but can cascade widely; trapping at supervisor boundaries contains it (this is the design, not a bug — but document the blast radius).
  • Double-notify (an actor linked and monitored) → both fire (by spec) — distinct mechanisms; don't dedup them.
  • Monitor of a dead actor → fire Down immediately (the target is already gone) rather than waiting forever.
  • Self-link → no-op/reject.
  • Reason fidelity — terminate reason must match the actual cause (Panic carries the message) for debuggability.

⬜ Phase 4 — Supervision Trees, Restart Strategies, Intensity Limits §16

Objectives

Build the supervision tree atop links/trap-exits (P3): a Supervisor actor with a strategy (one-for-one / one-for-all / rest-for-one), ChildSpecs (factory + restart policy), and a restart-intensity limit (≤ R restarts in T → escalate, I9). On a child crash, the supervisor restarts per strategy, returning the child to its initial state (I10, crash-only). This is the OTP fault model — the project's reliability core.

Deliverable

act tree shows a supervision hierarchy; killing a child triggers the correct strategy; a crash-loop trips the intensity limit and escalates. Demo: a worker pool under a one-for-one supervisor self-heals; a poison-pill worker crash-loops and escalates.

Acceptance
  • OneForOne: crash child C → only C restarted, siblings untouched; C' has initial state (I10).
  • OneForAll: crash C → all children stopped + restarted.
  • RestForOne: crash the k-th child → children k..n restarted, 0..k-1 untouched.
  • Intensity: > R crashes in T → supervisor escalates (does not restart again) (I9); restart count metered exactly.
  • Transient: normal exit → no restart; abnormal → restart. Temporary: never restart. Permanent: always.
  • Every spawned actor has exactly one parent supervisor (I5; orphan audit = 0).
Fixtures

conformance/supervision/{one_for_one,one_for_all,rest_for_one,intensity_escalate,permanent,transient,temporary,initial_state_on_restart}, golden restart/escalation traces + act tree snapshots.

Pitfalls
  • Restart with stale state (reusing the old actor object) → must re-run the factory/init for a clean slate (I10); a regression resurrects corrupt state — the bug crash-only is meant to prevent.
  • Intensity window off-by-one (counting restarts vs. crashes, window edges) → either crash-loops forever (never escalates) or escalates too eagerly; define precisely (restarts within rolling T).
  • Escalation storm (one-for-all at a high level restarts a huge subtree) → correct but expensive; document blast radius; prefer fine-grained supervisors.
  • Ordering for rest-for-one (must track spawn order) → keep an ordered child list.
  • Restarting a child whose dependencies (siblings) are gone → strategy choice (one-for-all/rest-for-one) encodes dependency; wrong strategy = restarting into a broken environment.
  • Temporary child that crashes → must not restart; a bug here loops a should-die actor.

⬜ Phase 5 — Location-Transparent Addressing (ActorRef / Pid Resolution) §17

Objectives

Make addressing location-transparent (I11): ActorRef::send works identically whether the target is local or remote — the caller never branches on locality. Build the Pid resolution machinery: a per-node registry (local_id → cell), ResolveHint caching, and the seam where a Remote ref will (in P6/P7) serialize + hand off to the transport. Still single-node (remote path stubbed/dead-lettered) — this phase locks the API so P6/P7 plug in without changing application code.

Deliverable

Application code uses ActorRef::send with no locality awareness; locally it enqueues directly, remotely (stub) it dead-letters with NodeDown/NoSuchActor. The dead-letter stream is observable.

Acceptance
  • send API is identical for a (future) remote ref and a local ref (I11) — verified by a conformance test that swaps a local ref for a remote-stub ref with zero call-site change.
  • A send to a stopped/unknown actor dead-letters (no panic, no hang) with the correct reason.
  • Stale ref (pre-restart incarnation) resolves to dead, never to a new actor reusing the id (I13).
  • Local fast path skips serialization (measurably faster than the remote path).
Fixtures

conformance/lifecycle/{deadletter_unknown,deadletter_stopped,stale_incarnation_deadletter}, addr/{local_resolve,remote_stub_deadletter,api_transparency}.

Pitfalls
  • Resolution cache staleness (cached Local after the actor moved/died) → validate against incarnation; invalidate on Down/membership change (P9).
  • Leaky transparency (callers depending on local-only timing/ordering) → document that remote adds latency + at-most-once failure (principle 4, Waldo's note); transparency is API-level, not semantics-level.
  • Dead-letter loop (dead-lettering a dead-letter) → the dead-letter actor must not re-dead-letter.
  • Registry contention (a global lock on spawn/lookup at millions of actors) → shard + lock-free reads.
  • Incarnation reuse (node restarts, reuses ids with a fresh incarnation) → resolution must compare incarnation (I13).

⬜ Phase 6 — Wire Protocol: Framing, Serialization, Handshake §18

Objectives

Define + implement the binary wire protocol (no network yet — codec in isolation): length-prefixed frames (magic + version + len + type + header + payload), Envelope serialization (to/from/kind/seq + opaque payload), a versioned handshake (Hello), and the never-panic decoder on hostile bytes (I6, fuzzed). This is the contract two nodes will speak in P7; getting framing + bounds right here is the security boundary.

Deliverable

A codec that round-trips envelopes + handshakes deterministically and survives arbitrary byte fuzzing without panic/OOM; act wire-test <hex> decodes a frame for debugging.

Acceptance
  • Round-trip: decode(encode(env)) == env for all conformance envelopes + handshakes (golden).
  • cargo fuzz on frame_decode/envelope_parse: 0 panics/OOB/OOM across 1e8 execs (I6).
  • Oversize FRAME_LEN rejected before allocation; truncated frame → Truncated; unknown type → UnknownType; unknown payload tag → UnknownTag (no panic).
  • Encoding is deterministic + version-stamped; cross-version Hello mismatch → typed reject.
Fixtures

conformance/wire/{roundtrip_msg,roundtrip_hello,malformed_oversize,malformed_truncated,unknown_type,unknown_tag,version_mismatch}, fuzz/fuzz_targets/{frame_decode,envelope_parse,handshake}.rs.

Pitfalls
  • Trusting FRAME_LEN → Vec::with_capacity(attacker_len) = instant OOM; bound before alloc (I6) — the classic remote-DoS.
  • Partial reads (TCP delivers fewer bytes than FRAME_LEN) → the codec must be incremental/stateful or buffer until the full frame arrives (P7 wires this).
  • Endianness / alignment drift → fix big-endian framing; never reinterpret-cast a byte buffer to a struct (UB) — parse field-by-field.
  • Varint overflow in header decode → bounded varint, reject overlong.
  • Type-tag collision / spoofing → tags are a closed registry; unknown → dead-letter, never execute.
  • Serialization version skew (a field added) → versioned + #[non_exhaustive]; older nodes ignore unknown trailing fields (forward-compat) within a major.

⬜ Phase 7 — TCP Transport: Connections, Remote Send, Handshakes §19

Objectives

Put the P6 codec on the network: one TCP connection per peer, multiplexing all actor traffic + heartbeats; a connection state machine (connect → Hello handshake → established → closed); the remote send path wired into ActorRef::send (P5) so remote refs serialize + transmit, preserving per-sender FIFO over the connection (I4). Two actd nodes now exchange messages — distribution begins.

Deliverable

Two actd nodes (compose) pass messages: a local actor on A sends to a remote actor on B with the same send API; ping-pong across nodes works; FIFO per sender preserved over the wire.

Acceptance
  • Remote send delivers (steady state, no partition): A→B message arrives at B's actor with correct content (round-trip via the live wire).
  • Per-sender FIFO over the connection (I4): A sends m1..m100 to B's actor X → X receives them in order.
  • One connection per peer (verified: concurrent sends to B reuse one conn); reconnect on drop with backoff.
  • Handshake rejects an incompatible peer (version mismatch) cleanly (no crash).
  • Location transparency holds (I11): the same code that worked locally (P5) now works remotely with no call-site change.
Fixtures

conformance/wire/{remote_roundtrip,fifo_over_conn,reconnect_backoff,handshake_reject} (integration, compose-driven), benchmarks/remote_send.

Pitfalls
  • Frame boundaries across TCP reads → a stateful reader that accumulates until a full frame, then splits multiple frames in one buffer (the #1 framing bug).
  • Head-of-line blocking (one huge message stalls all traffic on the single conn) → bound message size; consider a separate lane for heartbeats so detection isn't blocked by data (cross with P9).
  • Connection storms (both nodes dial each other simultaneously → two conns) → a tie-break (lower NodeId.uid wins / keep one) to converge to a single conn.
  • Reconnect thundering herd after a blip → jittered backoff.
  • Write-queue unbounded (remote backpressure) → bound the per-conn write queue; apply backpressure to senders (a slow/dead peer must not OOM the sender — ties to I8).
  • Partial write / slow peer → non-blocking writes + backpressure; don't block a worker on a socket.

⬜ Phase 8 — Cluster Membership (SWIM): Join, Leave, Gossip, Incarnation §20

Objectives

Implement SWIM membership (Das 2002, #197/#72): nodes join via a seed, maintain a member list through periodic ping + indirect ping-req (probe via k random members when a direct ping fails), and gossip membership updates (Alive/Suspect/Dead + incarnation) piggybacked on probes — converging in O(log N) rounds. Incarnation numbers let a node refute a false suspicion (I13). Graceful leave announces departure. This makes the cluster self-organizing.

Deliverable

A 3+ node cluster (compose) self-forms via a seed; act members shows the converged member list on every node; a joining node is discovered cluster-wide in O(log N) rounds; a graceful leave is propagated.

Acceptance
  • N nodes join via a seed → all N converge to the same member list (within ≤ ~5 s for N ≤ 1000); join propagates in O(log N) gossip rounds.
  • A node bumping its incarnation refutes a false Suspect rumor → reinstated Alive cluster-wide (I13).
  • Graceful leave → all nodes mark it Dead/Left promptly (no waiting for detection timeout).
  • Membership state machine transitions match §8.7 on fixtures (join/suspect/refute/dead).
  • Split-brain (injected partition) → each side's member list reflects the split; the condition is reported via a metric/log, not auto-resolved (principle 8).
Fixtures

conformance/swim/{join_converge,gossip_propagation,suspect_refute_incarnation,graceful_leave,splitbrain_surface,convergence_logN} (compose/simulated network).

Pitfalls
  • Incarnation comparison bugs → a healthy node permanently evicted (can't refute) or a dead node resurrected; strict "higher incarnation wins, equal: Dead>Suspect>Alive" precedence (I13).
  • Gossip amplification (re-gossiping the same update forever) → bound update lifetime (gossip each update a limited number of times / TTL).
  • Slow convergence from too-small fan-out → tune ping period + piggyback size; O(log N) needs adequate gossip per round.
  • Seed single point of failure at join → support multiple seeds; once joined, membership is decentralized.
  • Ping-req to dead helpers → k random currently-alive members; skip Suspect/Dead helpers.
  • Clock dependence → SWIM uses timeouts, not synchronized clocks; suspicion timeout is local-relative (avoid wall-clock assumptions, cross with P9 clock-skew).

⬜ Phase 9 — Failure Detection (phi-accrual) + Remote-Ref Invalidation + Split-Brain §21

Objectives

Replace SWIM's binary suspicion timeout with a phi-accrual detector (Hayashibara 2004): track the distribution of heartbeat inter-arrival times per peer and output a continuous suspicion level φ; φ > threshold ⇒ suspect (feeds SWIM Suspect). Adaptive to jitter (a GC pause raises φ gradually, not a hard cliff). On a confirmed-dead node, invalidate its remote ActorRefs (sends fail-fast, monitors fire Down, I12) and finalize split-brain handling (surface, AP). This closes the partial-failure-visibility loop.

Deliverable

A node that dies (kill -9 / partition) is detected via rising φ within a bounded time; its remote refs fail-fast; monitors fire Down; a recovering node (transient pause) is not falsely evicted (φ falls). Chaos demo: kill a node, observe detection + ref failure + monitor Down.

Acceptance
  • Truly dead node detected within ≤ 3× heartbeat interval (φ crosses θ); confirmed via ping-req → Dead (P8).
  • False-positive rate ≤ 1% at θ=8 under normal jitter (a brief pause does not cross θ; the node refutes via incarnation if it does, I13).
  • Dead node's remote refs → send returns NodeDown fast-fail (not a hang); monitors on its actors fire exactly one Down{NodeDown} (I12).
  • Split-brain (partition): both sides available; splitbrain_detected raised; no auto-merge (principle 8).
  • φ falls back below θ when heartbeats resume (adaptive recovery).
Fixtures

conformance/detector/{phi_rises_on_silence,phi_false_positive_under_jitter,detect_dead_node,ref_invalidation_on_dead,monitor_down_on_nodedown,splitbrain_both_available}, chaos/{kill-node,partition,packet-loss}.

Pitfalls
  • Heartbeats blocked behind data (HoL on the shared conn) → φ spikes falsely → false death; use a dedicated heartbeat lane / separate the detection path (cross P7).
  • Threshold mis-tuned (θ too low → false positives → split-brain amplification; too high → slow detection) → expose θ; document the latency/accuracy tradeoff (principle 7).
  • Distribution mis-fit (assuming normal when arrivals are bursty) → use a robust estimator; clamp φ; bound the window.
  • Cascading eviction (a transient blip evicts several nodes at once) → Lifeguard-style local-health multiplier (slow down our own suspicion if we might be the slow one).
  • Ref invalidation race (a message in flight when the node is declared dead) → in-flight: default drop / ALO redeliver (P10); new sends fail-fast.
  • Clock skew affecting timestamps → use monotonic local clocks for inter-arrival, never wall-clock differences across nodes (cross chaos/clock-skew).

⬜ Phase 10 — Delivery Semantics: At-Most-Once, At-Least-Once, Dedup, Ordering §22

Objectives

Make the delivery-semantics spectrum explicit and correct. Default = at-most-once (Erlang: a message is delivered 0 or 1 times; on failure it's dropped, I14) — fast, no bookkeeping. Opt-in = at-least-once (redeliver until ack; a bounded dedup window by (sender, seq) suppresses duplicates; per-sender FIFO ordering preserved, I15). Document the impossibility of exactly-once without dedup + idempotency (principle 8). This phase makes the runtime's reliability guarantees precise + selectable.

Deliverable

Both modes work: at-most-once (default, no overhead, drops on failure); at-least-once (redelivers + dedups + orders) — demonstrated across a partition + reconnect (messages survive a transient partition in ALO; are dropped in at-most-once).

Acceptance
  • At-most-once: under a partition, in-flight messages dropped (0 duplicates, possible loss, I14); no redelivery overhead in steady state.
  • At-least-once: under a partition + reconnect, every message delivered ≥1 time (no loss, I15); the dedup window suppresses duplicates within the window (receiver sees each seq once); per-sender FIFO preserved.
  • Exactly-once is not claimed; the doc + tests show ALO + dedup-window + idempotency is the closest achievable (principle 8).
  • Dedup window bounded (memory I8); a duplicate outside the window is delivered (documented; app idempotency required).
Fixtures

conformance/delivery/{atmostonce_drop_on_partition,atleastonce_redeliver,dedup_within_window,dedup_outside_window_delivered,ordering_preserved_under_redelivery,ack_cumulative}, chaos/partition.

Pitfalls
  • Unbounded ack/redelivery buffer (a permanently dead peer) → bound + apply backpressure / give up after intensity (don't buffer forever → OOM, I8).
  • Dedup window too small → late duplicates slip through (acceptable but document; app idempotency); too large → memory. Tune by RTT × redelivery rate.
  • Reordering under redelivery (a redelivered seq n arrives after n+1) → the reorder buffer must hold n+1 until n is delivered (ordered ALO), or relax ordering explicitly.
  • Claiming exactly-once → the cardinal distributed-systems sin; we explicitly do not (principle 8); "effectively-once" = ALO + idempotent handler.
  • Ack amplification (acking every message) → cumulative/batched acks.
  • Duplicate side effects (a non-idempotent handler runs twice on redelivery before dedup) → dedup must be before handler invocation.

⬜ Phase 11 — Hardening: loom, Miri, Fuzz, Chaos §23

Objectives

Prove the concurrency + distribution correctness story: loom model-checks the mailbox + scheduler claim (exhaustive interleavings, I1/I4); Miri verifies the lock-free unsafe; cargo fuzz hardens the wire decoder (I6); chaos (kill nodes, partitions, packet loss, clock skew) validates membership + detection + delivery under faults. This is the gate that says "trustworthy under concurrency + failure."

Deliverable

Green loom (all interleavings), Miri-clean, 24 h fuzz (0 crashes), a chaos report (cluster survives kills/partitions/skew with correct membership + detection + delivery).

Acceptance
  • loom: 0 violations of I1 (no double-run), I4 (FIFO/no-loss), signal priority — across all interleavings of the small model.
  • Miri: no UB on the lock-free paths.
  • Fuzz: 0 panics/OOB/OOM across ≥ 1e9 execs on all decode targets (I6).
  • Chaos: kill a node → detected (P9), refs invalidated (I12), supervisors react (P4), cluster re-converges (P8); partition → both sides available + split-brain surfaced (principle 8); packet loss → ALO redelivers (I15), at-most-once drops (I14); clock skew → detection uses monotonic clocks (no false death). No panic in any scenario.
Fixtures

loom/*, fuzz/corpus/*, chaos/{kill-node,partition,packet-loss,clock-skew} scenarios + assertion scripts; conformance/** regression rerun under chaos.

Pitfalls
  • loom state-space explosion → keep models tiny (2 producers, 1 consumer, few messages); test the protocol, not throughput.
  • Fuzz finds a real OOM (oversize alloc) → the bound (I6) was wrong; fix + regress.
  • Chaos flakiness (timing-dependent assertions) → assert eventual properties (convergence within a bound), not instantaneous.
  • Clock-skew false death → confirms the monotonic-clock requirement (P9); a regression here re-breaks detection.
  • Partition assertion asserting consistency (we're AP) → assert availability + split-brain surfaced, not consistency.
  • Heisenbugs under Miri/loom that don't repro normally → these are real (memory-ordering) bugs; trust the model checker.

⬜ Phase 12 — Soak, Performance (Millions of Actors), Release §24

Objectives

Validate scale + lock performance: spawn millions of actors, sustain target message rates, soak a multi-node cluster for days (no leak, bounded memory, stable membership), profile + tune the scheduler/mailbox/transport against §4, and ship a reproducible, signed release with an SBOM. This is the production-readiness gate.

Deliverable

A benchmarked, soak-tested, signed release: millions of actors, target throughput/latency met, days-long stability, reproducible build + SBOM.

Acceptance
  • ≥ 1 M live actors/node; spawn ≥ 1 M in ≤ 10 s; cell overhead ≤ ~256 B (§4).
  • Local send p50 ≤ 1 µs, p99 ≤ 10 µs; ≥ 10 M local msgs/s/node; remote p99 ≤ 2 ms intra-DC.
  • SWIM converges O(log N); φ false-positive ≤ 1% at θ=8.
  • 72 h soak: flat memory (no leak), stable membership, 0 panics, deterministic per-actor evolution (I1).
  • Reproducible build (bit-identical), SBOM generated, artifacts signed.
Fixtures

benchmarks/{local_send,spawn,remote_send,swim_convergence,phi_accuracy} with thresholds; scripts/soak.sh; release reproducibility check; full conformance/** green.

Pitfalls
  • Per-actor overhead too high (fat cell) → millions of actors OOM; keep the cell lean (state + small fixed metadata); box rarely-used fields.
  • Scheduler contention at scale (run-queue / steal hot) → shard, batch steals, per-core locality (NUMA).
  • Mailbox false sharing (head/tail on the same cache line) → pad atomics (P2 — verify under profiling).
  • Memory leak over days (unbounded buffers: dedup windows, ack buffers, gossip history) → bound everything; soak catches it.
  • GC-free but allocator-bound (per-message alloc) → reuse buffers; arena/pool envelopes.
  • Tail latency (a preemption/park/steal spike) → measure p99/p999 (The Tail at Scale); tune reduction budget + parking.
