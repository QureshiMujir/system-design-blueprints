Back-of-Envelope Capacity Model

All derivations from §4 System Constraints table. All numbers are for a representative 8-core node with 32 GiB RAM.

C1 — Actor count ceiling (memory):

  • From §4: cell overhead ≤ ~256 B fixed + state. Assume minimal stateless actor (state = 0 B extra): 256 B/actor.
  • Available actor-cell memory budget: 32 GiB × 0.5 (leaving 50% for mailboxes + transport buffers) = 16 GiB.
  • Maximum actors: 16 GiB / 256 B = 16 × 2³⁰ / 256 = 67 M actors. Safety target: ≤ 10 M active with state.
  • §4 target: ≥ 1 M live actors — we have ≥ 67× headroom with a 32 GiB node at 256 B/cell.

C2 — Mailbox memory ceiling (per node):

  • From §4: mailbox cap = 1024 envelopes/actor default; Envelope ≈ 128 B (header) + avg 256 B payload = 384 B.
  • 1 M actors × 1024 envelopes × 384 B = 384 GiB. This is why the memory ceiling is enforced per-node, not per-actor-class: a global cap of 4 GiB for mailboxes = max 10.4 M envelopes in-flight.
  • Practical limit: set mailbox_cap low (64–256) for most actors; reserve large caps for known-hot actors. At cap=64: 1 M actors × 64 × 384 B = 24 GiB — fits in 32 GiB alongside cells.

C3 — Local message throughput (M:N scheduler):

  • From §4: ≥ 10 M msgs/s/node on 8 cores = 1.25 M msgs/s/core.
  • Per-message cost estimate: claim CAS (~5 ns) + dequeue (~10 ns) + handle (application: assume 20 ns) + re-enqueue (~5 ns) = ~40 ns/msg → 25 M msgs/s/core theoretical upper bound.
  • With reduction-yield overhead (every 2000 msgs) and work-steal (amortized): ~60% efficiency = 15 M msgs/s/core → 8 cores = 120 M msgs/s. Target 10 M/s leaves ≥ 12× headroom for real application handler costs.

C4 — Remote message throughput + bandwidth:

  • From §4: ≥ 200 k msgs/s/connection.
  • Envelope size: 128 B header + 256 B avg payload = 384 B/msg.
  • 200 k msgs/s × 384 B = 76.8 MB/s = 614 Mbit/s per connection. A 10 Gbit link supports ~16 such connections at full throughput.
  • With batching (coalesce 10 msgs/write): syscall overhead amortized; effective encoding bandwidth ≈ 3.84 GB/s — well within a modern NIC.

C5 — TCP connection count (FD budget):

  • From §4: one TCP connection per peer. A 1000-node cluster → each node holds 999 peer connections.
  • Plus control UDS socket, heartbeat lanes, CLI socket: ~1005 FDs/node.
  • Default FD limit on Linux is 1 M (ulimit -n). 1000 peers well within limits; tune ulimit for >10k-node clusters.

C6 — SWIM gossip bandwidth:

  • From §4: ping interval 1 s; gossip piggybacked on ping/ack/ping-req.
  • Per probe: 1 Ping frame (~200 B) + k=3 PingReq if needed (~600 B) + ack (~200 B) + gossip payload (~50 B × bounded updates).
  • Per node/second: 1 probe out + 1 ack in ≈ 400 B/s gossip traffic per node. For 1000 nodes: 400 kB/s cluster-wide gossip. Negligible vs. application traffic.

C7 — Heartbeat bandwidth for phi-accrual:

  • From §4: heartbeat interval 1 s; one heartbeat frame per peer per interval.
  • Per node: (N−1) heartbeats/s × ~64 B/frame. For N=1000: 999 × 64 B/s = 63.9 kB/s → 0.5 Mbit/s. Dominated by application traffic even at 1000 nodes.

C8 — Dedup window memory (at-least-once mode):

  • From §4: dedup window per sender keyed by (sender_pid, seq). Assume 16 B/entry (8 B key + 8 B seq).
  • Window size = RTT × redelivery rate. Intra-DC RTT 1 ms; redelivery at seq ≈ 1k msgs/s/sender: window = 1 ms × 1 k = 1 entry. But bursty: practical window = 10k entries per sender pair.
  • 100 unique senders × 10k entries × 16 B = 16 MB per receiving actor in high-fan-in case. Bounded per §4 (I8).

C9 — Spawn storm latency:

  • From §4: spawn p99 ≤ 5 µs local; 1 M actors in ≤ 10 s.
  • 1 M actors / 10 s = 100 k spawns/s = 10 µs/spawn average. At 5 µs p99, the spawn path must be the cheapest path (cell allocation + registry insertion + first-enqueue). Memory allocation at 256 B/cell + 256 B/mailbox-ring: ~512 B/spawn → 512 MB total for 1 M actors (fits in RAM).

C10 — Phi-accrual window memory:

  • From §4: φ-accrual window samples per peer. Typical window: 1000 samples/peer × 8 B (f64 timestamp) = 8 kB/peer.
  • For 1000 peers: 8 kB × 1000 = 8 MB total for the phi detector. Negligible.
