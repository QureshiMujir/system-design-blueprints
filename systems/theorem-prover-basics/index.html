In one paragraph

prove is an interactive theorem prover. You state a mathematical claim in a small higher-order logic (HOL-lite) and the tool helps you build a proof that a tiny trusted module, tp-kernel, checks (§1, §3). Its defining idea is the LCF discipline: a theorem is a value of an abstract type that only ten primitive inference rules can construct, so soundness reduces to auditing one crate (§1, P3). The parser, tactics and automation may be buggy; at worst a proof attempt fails (§3, P4). It is a Rust workspace of seven crates, run as a single-threaded REPL and script checker (§1.1, §1.2, §1.5).

The problem, concretely

A theorem prover is only worth using if "proved" means proved. If any reachable path produces a theorem that is not derivable, a derived |- F makes every goal provable through eq_mp and inst (§6 P1). The blueprint names how such a path appears: automation allowed to return a bare yes/no verdict (§6 P12, P4); a swallowed TypeMismatch in eq_mp letting a mismatched theorem through (§6 P14); named bound variables, where one missed rename forges a theorem (§6 P7); a public theorem constructor, so any crate could write Thm(Sequent{..}) (§6 P3); and unsafe code in a calling crate (§26 T1).

Hostile input adds two more pressures: a term with 10^6 nested parentheses can overflow the stack (§26 T2), and a substitution loop can blow terms up exponentially (§26 T3). The blueprint's answer is one idea: shrink the part you must trust until a person can audit it, make everything else unable to forge a result, and bound every resource so that hitting a limit means "failed", never "wrong" (§4, §6 P2, P10). It will not do dependent types, SAT, SMT, model checking or an industrial math library (§1.2, §1.3).

How it works, end to end

Follow one proof through the boxes of §3's diagram. The blueprint draws it like this:

    proof script (.thm) / REPL  ──  prove CLI (prove · check · repl · bench)
                         |  parse
                         v
    tp-parse : Parser -> Term/Type/script · notation/fixity · PrettyPrinter · ParseError
                         |  parsed Terms + tactic scripts
                         v
    tp-tactic : Goal · GoalState · Tactic + Justification
        tacticals THEN/ORELSE/REPEAT/TRY · intro · apply · assumption · exact
                         |  uses derived rules          | builds Thm via Justification(Vec<Thm>)
                         v                              v
    tp-logic : HOL-lite constants = ==> /\ \/ ~ T F ! ? choice + derived intro/elim
        ^  defined via primitives (conservative)        |
        |                                               v
    tp-auto : Unify (unify_fo + unify_pattern/Miller) · ResolutionProver · CongruenceClosure · LinearArith
        |  every result = a sequence of primitive-rule calls -> a Thm
        v
    ====================== TRUST BOUNDARY — everything below is the TCB ======================
    tp-kernel : Term (de Bruijn) · Type · Thm (ABSTRACT, private field) · Sequent · type_of
        primitive rules:  refl · trans · mk_comb · abs · beta · assume · eq_mp · deduct_antisym
                          · inst · inst_type · new_basic_definition · new_basic_type_definition
    Trust:   ONLY tp-kernel trusted. Untrusted code obtains Thm solely via primitive rules.
    Input:   proof script (.thm) — may crash/loop; cannot derive a false Thm.
    Concurrency: single-threaded REPL/checker.  Persistence: none at runtime; Proofs serializable.
  1. tp-cli is the entry point: prove, check, repl, bench (§1.1 item 7, §3). The proof script (.thm) is the only untrusted input; it may crash or loop but cannot derive a false theorem (§1.2, §3).
  2. tp-parse turns text into Term/Type values and tactic scripts with a hand-written lexer and Pratt parser driven by a fixity table, and reports a precise ParseError (§3.1, ADR-17). Parsed terms are re-typechecked by the kernel, so the parser is not trusted (§3.1).
  3. tp-tactic holds the proof state. A Tactic maps a Goal to a list of subgoals plus a Justification, and THEN/ORELSE/REPEAT/TRY combine tactics (§1.1 item 5, ADR-10, ADR-11).
  4. tp-logic defines the logic's constants (T, /\, ==>, !, ?, F, ~, \/, choice) from the primitives and derives intro/elim rules such as DISCH, MP, GEN (§8.4). tp-term adds untrusted substitution, alpha/beta/eta, free-variable and matching utilities (§1.1 item 2).
  5. tp-auto is the search layer: Unify (unify_fo and the Miller-pattern unify_pattern), ResolutionProver, CongruenceClosure, LinearArith. Every result must be a sequence of primitive-rule calls that ends in a Thm (§3, P12).
  6. tp-kernel is the trust boundary. It owns Type, Term, the abstract Thm, Sequent, type_of, the ten rules and the two definition principles (§3, §8.3, §8.6).
  7. At the end, prove(goal, tac) checks that the resulting theorem's conclusion equals the goal up to alpha-equivalence; a mismatch is a TacticError (§6 P4, §7 I8). Optionally, recheck_proof replays a recorded proof term in an isolated context (§6 P8, §7 I10, §25).

The blueprint's first worked proof, p ==> p (§8.7 Proof 1): the tactic engine works backwards from the goal, then the justification runs forwards through kernel rules:

Goal       :  ⊢ p ==> p
intro()    :  subgoal  {p} ⊢ p
assumption :  close via assume(p) : p ⊢ p
justify    :  j1 = |th| DISCH(p, th); j2 = |_| assume(p)
prove()    :  j1(j2(∅)) → ⊢ p ==> p

Where recheck_proof lives is stated two ways: in tp-cli (file tp-cli/src/check.rs, §25, §3.1, §11.7) and in tp-kernel (§40, §37 Q6, §26 T4). This page does not settle it.

The core ideas

1. An abstract Thm: the LCF trick (§3, §11.2, ADR-04, P3, I1)

In plain words: a theorem is a value you cannot write by hand. Thm is a struct wrapping a Sequent (hypotheses plus conclusion) whose field is private to tp-kernel; the only way to get one is to call a primitive rule or a definition principle (§11.2, P3). Untrusted crates read it through accessors such as concl() and hyps() (§11.2, P3). The blueprint adds anti-forgery properties: no unsafe, no Deserialize, no Default, Clone only (§11.2).

The payoff is the "central claim": any value of type Thm is a sequent derivable in HOL-lite, so a bug in tp-tactic, tp-auto or tp-parse hurts completeness (a proof attempt fails), never soundness (§3). Rust enforces this with module privacy at compile time, not by convention (§1.5, ADR-04). A tiny check: Phase 0 has a trybuild compile-fail test that building Thm(seq) from outside the crate is error E0603 (§12 AC0.3).

2. de Bruijn terms: bound variables as numbers (§8.1, §8.5, P7, ADR-05)

Instead of naming bound variables, the kernel numbers them by how many binders away they are (de Bruijn indices). Abs(ty, body) binds index 0 in body, and each enclosing Abs shifts the reference up by one (§8.1). Free variables keep names (locally nameless, §6 P7). The five term forms are Var, Bound, Const, Comb (application) and Abs (§8.1).

The payoff: two terms are alpha-equivalent exactly when they are structurally equal, and substitution avoids capture by shifting indices (§6 P7, §7 I4, I5). The cost is fiddly index arithmetic, which the blueprint localises to tp-kernel and tp-term and tests exhaustively (§6 P7). Three operations carry the idea (§8.5): shift adds d to every Bound(k) with k >= c, where the cutoff c grows under each Abs; subst replaces Bound(j) by a term shifted to the current depth; beta substitutes the argument for Bound(0) and then shifts the remaining free indices down by one. A Bound(k) with k at least the number of enclosing binders is dangling, and is rejected (§8.1). The blueprint's worked example, copied from §8.5:

Comb( Abs(α, Abs(β, Bound(1))), Var("a",α) )
beta: substitute arg for Bound(0) in Abs(β, Bound(1)):
  - enter inner Abs → cutoff c=1; Bound(1) refers to x (depth 0 outside)
  - replace with arg shifted by 1 → Var("a",α)
  - drop consumed binder, shift remaining free indices down 1
result : Abs(β, Var("a",α))    i.e.  \y. a
thm    : ⊢ (\x. \y. x) a = (\y. a)

3. A typing check and ten rules (§8.2, §8.3, §8.8, ADR-07)

Every rule re-runs a total, deterministic type_of on its inputs, so an ill-typed term never enters a theorem (§2.1, §7 I2, I11). type_of has five cases, each a one-line rule (§8.2): a free Var has its stated type; Bound(k) has the k-th type in the context or fails with IllTyped; Const must be a type-instance of its declared type; Comb(f,x) needs f : fun[a,b] and x : a and gives b, else TypeMismatch; Abs(t,b) gives fun[t, type of b].

The ten primitive rules are refl, trans, mk_comb, abs, beta, assume, eq_mp, deduct_antisym, inst, inst_type; with the two definition principles they are the whole basis (§8.3, ADR-07). In words: refl gives |- t = t; trans chains s = t and t' = u when t and t' are identical; assume(p) gives p |- p for a boolean p; eq_mp turns p = q and p into q (§8.3). Bad inputs give typed KernelError values, never silent ones: abs over a variable free in a hypothesis is FreeVarEscape, assume on a non-boolean is IllTyped (§8.8, §6 P14).

4. Definitions and the logic bootstrap (§8.4, §8.6, P5, ADR-08, ADR-09)

You may name a new constant only under three conditions: the name is fresh, the right-hand side is closed (no free variables), and its type variables all appear in the constant's type; violations give BadDefinition (§8.6). That makes a definition a conservative extension: it cannot introduce inconsistency (§6 P5, ADR-08). A new type needs a proven-nonempty subset, witnessed by a theorem (§8.6, §6 P5).

With only = and these rules, tp-logic defines the rest in order (§8.4). Three of the nine rows:

Constant Defining equation (from §8.4) Derived rules
T T = ((\p:bool. p) = (\p:bool. p)) TRUTH
/\ /\ = \p q. (\f. f p q) = (\f. f T T) CONJ, CONJUNCT1/2
==> ==> = \p q. (p /\ q) = p DISCH, MP

Rows 1 to 8 are conservative definitions; row 9, the choice constant, adds one extralogical axiom, SELECT_AX, which gives classical HOL (§8.4). That sits awkwardly with §3.1, which describes tp-logic as "Conservative definitions only; no new primitives", and with ADR-08, which rejects "asserting axioms directly; new_axiom for everything" (§3.1, §8.4, §9 ADR-08). Appendix B, in turn, names the Phase 5 deliverable "HOL-lite axioms" (§42). The statements stand side by side in the blueprint.

5. Tactics: work backwards, prove forwards (§8.7, ADR-10, ADR-11, P4, I7, I8)

A tactic takes a goal and returns smaller subgoals plus a justification: a function that, given theorems for the subgoals, builds a theorem for the goal out of primitive-rule calls (ADR-10, §8.7). A buggy tactic cannot produce a wrong theorem; it fails to produce one (§2.1, P4). The blueprint's second worked proof, |- !x. P x ==> ?y. P y, takes four steps: intro() (via GEN, fresh a), intro() (via DISCH), exists(a) (via EXISTS), then assumption closes {P a} |- P a with assume(P a) (§8.7 Proof 2). The justification then runs bottom-up: assume(P a), EXISTS, DISCH, GEN (§8.7). The tacticals are ordinary Rust functions, so there is no separate tactic language to trust (ADR-11). Two Phase-7 tests show their meaning: try_tac(tac) equals orelse(tac, id_tac), and repeat(tac) stops when tac fails (§19 AC7.3, AC7.4). Invariant I7 is the contract: a justification applied to valid subgoal theorems yields a theorem proving the goal (§7).

6. Search is untrusted, checking is trusted (§3, §4, ADR-12 to ADR-16, P8, P12, I9, I10)

Automation is allowed to be clever because the kernel re-checks it (§2.1). Resolution (refutation-complete for first-order logic) negates the goal, converts to clauses, and saturates; the refutation is then replayed as kernel rule calls (§2.1, ADR-13). It returns Option<Proof>, never a bare boolean (§6 P12), and has a default budget of max_inferences = 10^6 and a 30 s timeout; exhausting it gives None, never an unsound result (§4, P10). Unification finds substitutions making two terms equal: unify_fo is linear using union-find, and unify_pattern handles the decidable, unitary Miller patterns; full higher-order unification is undecidable and infinitary, hence rejected (§4, ADR-12). CongruenceClosure and LinearArith emit certificates the kernel re-derives (ADR-14). Phase tests show the intent: {f(a)=f(b), a=b} is congruent, and {x > 0, y > 0, x+y <= 0} is unsatisfiable, each with a certificate that must re-check (§24 AC12.1, AC12.3).

The last layer is the de Bruijn criterion: record the proof as a term and have a small independent checker (recheck_proof) re-run it, so trust reduces to the checker rather than the producer (§6 P8, ADR-16). Recording is optional and off by default because it costs memory (§6 P8).

The trade-offs — where engineers disagree

Foundational logic (ADR-03)

Chosen: HOL-lite (classical higher-order logic): simple types plus rank-1 polymorphism give expressive logic, decidable typing and a tiny kernel (§9 ADR-03). Rejected: first-order natural deduction (too weak) and CIC / dependent types (the kernel is huge). When the rejected choice is right: CIC when the project needs dependent types, proof-relevant programming, or extraction to certified compilers (§9 ADR-03).

Kernel discipline: an abstract Thm (ADR-04)

Chosen: Thm with a private constructor, obtained only through rules, so trust reduces to the kernel audit and Rust's privacy gives the guarantee statically (§9 ADR-04). Rejected: a public Thm struct plus a runtime checker; capability tokens. When the rejected choice is right: a runtime checker for a prover running in a dynamic language (Lisp/Python), or a distributed verifier where Thms cross process boundaries (§9 ADR-04).

Term representation (ADR-05)

Chosen: de Bruijn indices for bound variables, named free Var, typed binders: alpha-equivalence becomes syntactic and capture-avoidance falls out of index shifting (§9 ADR-05). Rejected: named bound variables; locally-nameless with both named. When the rejected choice is right: named variables when readability while debugging is critical and alpha-renaming bugs are tolerable, as in small research provers and teaching tools (§9 ADR-05).

Proof terms (ADR-16)

Chosen: record a proof term and recheck_proof it independently; terms are serialisable for offline third-party checking (§9 ADR-16). Rejected: no proof terms, LCF-only. When the rejected choice is right: a pure interactive session tool where memory is severely constrained and all checking happens in-session (§9 ADR-16).

Kernel size budget (ADR-19)

Chosen: tp-kernel at most about 1500 lines (target about 800), tracked, with CI failing on regression, because audit cost scales with size (§9 ADR-19). Rejected: no budget, "keep it small" informally. When the rejected choice is right: a larger budget when the logic is inherently more complex (CIC, linear types) and auditability relies on formal verification of the kernel itself (§9 ADR-19).

Roads not taken

Sequent-calculus core (§38 Alt-1). Wins for automated first-order and proof-search-oriented systems, where cut-elimination gives completeness. Rejected because HOL Light, the differential-testing oracle, uses natural deduction, and multi-conclusion sequents complicate the kernel (§38).

Hash-consing table instead of an arena (§38 Alt-2). Wins with massive term duplication: less memory, pointer-comparison alpha-equality (Lean 4, HOL4). Rejected because a global mutable table puts shared state in the kernel; the arena is adequate at 10^7 nodes or fewer (§38).

Proof-carrying code with an external verifier (§38 Alt-3). Wins when the search engine is large and the checker can be minimal and formally verified (Metamath, Candle). Rejected because it adds a second trusted artifact and a process boundary that recheck_proof avoids (§38, §25).

A dependent type theory kernel (§38 Alt-4). Wins when proofs and programs must be unified, or for certified extraction (Coq/Rocq, Lean 4, Agda). Rejected because the kernel is an order of magnitude larger; HOL is sufficient and auditable within 1500 lines (§38).

Deferred, not rejected (§39): full CIC, full Huet HOU, parallel proof search, an SMT oracle, an LSP server, universe polymorphism, proof minification and an HOL Light FFI, each with an un-defer trigger, such as profiling showing over 50% of wall time in sequential search (§39).

What must never be false

Invariants I1 to I7, I11 and I12 are classed TCB (violation means a false theorem could exist); I8 to I10 are classed UX (a tactic or checker bug, not a soundness hole) (§7). The master rule is that I1 holds even if every untrusted invariant fails (§7). Note that the master rule names "I7 to I10" as the untrusted ones, while the table classes I7 as TCB (§7).

  • I1: no Thm exists that was not built by a primitive rule. Noticed at compile time via module privacy and by the kernel_no_forge fuzz target; the rule_calls[rule_id] counter records use (§7).
  • I2: every Term in any Sequent is well-typed under type_of. A debug_assert! at each rule exit catches it; the rule returns Err (§7).
  • I3: every Bound(k) is in range. A lc(t, depth) check in debug_assert! plus property tests; constructors return IllTyped (§7).
  • I4: substitution is capture-avoiding. A differential test against a named-representation oracle and property tests (§7).
  • I5: alpha-equivalent terms are structurally equal. Property test alpha_rename(t) == t (§7).
  • I6: new_basic_definition admits only a fresh constant, closed right side and no new type variables. Unit tests per rejection class; Err(BadDefinition) leaves the signature unchanged (§7).
  • I7: a Justification applied to valid subgoal theorems proves the goal. Per-tactic property tests and the lemma library; a failing justification gives TacticError (§7).
  • I8: prove(goal, _) returns a theorem whose conclusion is exactly goal up to alpha. Noticed by the prove() assert and a regression suite; mismatch gives TacticError::ConclMismatch (§7).
  • I9: a prove_fol refutation re-checks through the kernel. Every success is fed to recheck_proof in tests; a failed replay discards the proof (§7).
  • I10: recheck_proof re-derives the identical Thm independently. Round-trip property and a conformance hash; a mismatch gives Err(KernelError) (§7).
  • I11: type_of is total and deterministic. Property tests, a totality fuzz, and a call-twice determinism check (§7).
  • I12: every Thm carries the set of axiom/oracle tags used to derive it, and a tag outside the declared basis is rejected with UntrackedAxiom. Noticed because recheck_proof re-accumulates tags and CI asserts the basis covers them (§7). Yet §11.2 defines Thm as a wrapper around a Sequent alone, with no tags field (§11.2), and I12 fixes the basis "at new_axiom", a mechanism ADR-08 lists among the rejected alternatives (§7, §9 ADR-08).

What breaks in production

  • Kernel unsoundness (§27 F1). Symptom: a Thm can be derived for False ⊢ True with an empty assumption set. Cause: a logic error in one of the ten rules, or a type-equality bypass. Detected by the differential test against HOL Light or a conformance failure. Recovery: none at runtime; halt, re-audit the kernel against §15 and revert to the last known-sound commit.
  • Parser stack overflow (§27 F2). Symptom: SIGSEGV or a stack-overflow message while parsing. Cause: recursive descent without a depth guard on adversarial nesting. Detected by the fuzz_parse target. Recovery: input is rejected at the depth limit with no state corrupted; raise the stack size or lower the limit.
  • Term size explosion (§27 F3). Symptom: a proof takes over 5 s and memory climbs. Cause: a rewrite loop with no size guard, or exponential substitution blowup. Detected by the proof-step budget or wall-clock timeout. Recovery: Err(Budget) is returned automatically; restructure the proof.
  • Tactic nontermination (§27 F6). Symptom: prove hangs. Cause: a combinator loop, such as REPEAT without a progress check. Detected by the wall-clock timeout, which exits with code 3. Recovery: add a progress metric to the tactic.
  • Unification cycle (§27 F7). Symptom: unify loops on a higher-order flex-flex pair. Cause: a missing occurs-check in the higher-order path. Detected by a step counter exceeding MAX_UNIF_STEPS. Recovery: Err(OccursCheck) after the limit; decompose the goal first.

Threats worth knowing (§26): T1 an attacker crate using unsafe to bypass the private constructor, answered by private field layout and compiler-enforced privacy; T2 deeply nested input, answered by a depth counter rejecting beyond 4096; T4 a bogus certificate from an external SMT oracle, answered by feeding all oracle output through recheck_proof; T6 a tampered serialised proof, answered by a SHA-256 hash over kernel version plus proof bytes checked before recheck; T11 proof files written by one kernel version and checked by another, answered by embedding the kernel semver and rejecting a mismatch. T3 mentions a term-size cap (default 10^7 nodes) and cites §4 for it, as do §33.2 bottleneck 2 and §36 item 1 ("§4 cap: 10⁷ nodes"), but §4's table lists MAX_TERM_DEPTH and MAX_PROOF_NODES and no term-size row (§26 T3, §33.2, §36, §4).

How it compares

  • HOL Light has a kernel of about 400 lines of OCaml, the same simple type theory, and implicit (unchecked) proof terms, with automation via MESON and METIS (§35). prove is its direct descendant in logic and uses it as the differential-testing oracle, and is larger "due to Rust verbosity" while targeting the same trust model (§35, ADR-22).
  • Coq / Rocq uses the Calculus of Inductive Constructions with a roughly 50,000-line kernel and fully checked proof terms (§35). That fits work needing dependent types and certified extraction; prove chose simple type theory to keep the kernel auditable (§35, ADR-03).
  • Lean 4 has a roughly 10,000-line core, dependent types and full dependent unification (§35). The blueprint borrows only its de Bruijn representation strategy (§35).
  • Isabelle/HOL has a roughly 30,000-line kernel, the same HOL logic, no proof terms by default, and blast, auto and Sledgehammer (§35). prove's tp-logic and tp-auto are analogous to its outer reasoner, minus the external-prover call-out, which is deferred (§35, §39).

The comparison row for the tactic model reads "LCF Thm -> Thm combinators", while ADR-10 defines a tactic as Goal -> (Vec<Goal>, Justification) (§35, §9 ADR-10).

If you only remember three things

Soundness is bought by making theorems unforgeable: Thm is an abstract type that only ten primitive rules (plus two definition principles) can build, so the trusted part is one small crate (§3, P2, P3). Everything clever, namely parsing, tactics, unification and resolution, is untrusted and must hand the kernel a rule sequence to replay, so its bugs cost completeness and never truth (P4, P12, MM3). Resources are capped at every layer so that hitting a limit means "failed", and an optional independent recheck_proof narrows trust to the checker (P10, P8, MM4).

Words used here

  • TCB (trusted computing base): the code whose correctness must be assumed; only tp-kernel here.
  • LCF discipline: theorems are an abstract type whose only constructors are the kernel's rules.
  • Thm: the abstract type of proved sequents; its constructor is private.
  • de Bruijn index: a number naming a bound variable by how many binders away it sits.
  • Alpha-equivalence: equality up to renaming of bound variables; here plain structural equality.
  • Conservative extension: a definition that cannot introduce inconsistency.
  • Tactic / justification: a goal-reducing step, and the function that rebuilds the theorem.
  • Unification: finding a substitution that makes two terms equal; FO or Miller-pattern here.
  • Resolution: a refutation-complete proof procedure for first-order logic.
  • de Bruijn criterion: trust only a small independent proof checker, not the proof producer.
