⬜ Phase 0 — Skeleton, Discrete-Event Engine & CI §12

Objectives

Stand up the Cargo workspace with all 22 crates as empty skeletons, and build the discrete-event core: SimTime, Event, EventQueue, and the simulation loop. Establish CI (lint, build, unit tests) before any protocol logic exists.

Deliverable

A runnable sim-core binary that drives a synthetic workload of no-op events through the queue, prints a deterministic replay hash, and exits.

Acceptance
  • Sustained event throughput ≥ 5,000,000 events/second on the synthetic workload (M3).
  • Event-queue depth handles 10,000,000 pending events without reallocation failure (M9).
  • Replay-hash identical across 10 repeated runs from the same seed (I11, M11 = 100%).
  • Zero event-ordering violations (I4) across a 1,000,000-event synthetic run.
Fixtures
  • scheduler_ordering.json — asserts strictly non-decreasing dispatch timestamps.
  • timer_rollover.json — exercises timer-wheel bucket boundary edge cases.
  • replay_seed_a.json — golden replay hash for a fixed seed and workload.
Pitfalls
  • Priority inversion: a low-priority event with an earlier timestamp starves a logically-critical timer if the heap comparator ties break inconsistently.
  • Hidden nondeterminism: an unseeded HashMap iteration order or system-clock read inside dispatch logic silently breaks I11 without any visible test failure until a rerun diverges.
  • Timer bucket overflow: a burst of same-timestamp timers overflowing a bucket's fixed capacity if bucket sizing assumptions are violated.
  • Zero-delay event cascades: an event that schedules another event at the same SimTime can recurse unboundedly if not capped, exhausting the call stack.

⬜ Phase 1 — Layered Protocol-Stack Scaffolding & Message Passing §13

Objectives

Build the ProtocolStack scaffolding (NAS, RRC, PDCP, RLC, MAC, PHY-abstraction) as typed SDU/PDU boundaries with no procedure logic yet — only message-passing plumbing between layers and between UE and eNodeB across the Uu boundary.

Deliverable

A UE and an eNodeB exchange a scaffolded "hello" message through the full stack (NAS down through PHY-abstraction, across Uu, back up through the peer stack) with no procedure semantics, only correct layering and event-driven delivery.

Acceptance
  • Every layer transition is total (P2): a fuzzed message reaching a layer in any defined state either transitions or is explicitly rejected — never panics.
  • Message round-trip latency across the full stack (both directions) <= 6 simulated transport hops as configured.
  • Zero shared-mutable-state violations detected by the ownership lint in CI (ADR-08).
Fixtures
  • layer_passthrough.json — asserts a message traverses all six layers in order.
  • unhandled_message_panic_free.json — fuzzes every layer with out-of-state messages, asserts no panics (P2).
Pitfalls
  • A layer that silently drops an unrecognized message instead of emitting a defined rejection breaks P2's exhaustiveness guarantee at runtime even if it compiles.
  • PDCP/RLC sequence-number fields left uninitialized across a scaffolded round-trip mask a real monotonicity bug that only surfaces once Phase 9 exercises real reordering.
  • Uu delivery scheduled with zero transport delay collapses causal ordering assumptions that later phases rely on for latency measurement.

⬜ Phase 2 — PHY/Channel Abstraction & Cell Model §14

Objectives

Implement sim-phy's analytic SINR/BLER channel model and the cell model (ENodeB topology, coverage) that MAC/RLC/RRC react to, per ADR-06 and P7.

Deliverable

A static two-cell topology where a stationary UE's SINR is computed each TTI and fed into a MAC-level success/failure decision, observable via metrics — with no scheduling or RACH yet.

Acceptance
  • SINR computation deterministic given UE/cell positions and seed (P10).
  • BLER-mapped transport-block success rate matches the configured analytic curve within 0.5% over 100,000 simulated TTIs.
  • Channel model evaluation cost does not exceed 5% of total per-event dispatch time (M3 gate maintained).
Fixtures
  • sinr_static_topology.json — golden SINR values for a fixed two-cell layout.
  • bler_curve_calibration.json — checks the success-rate-vs-SINR curve against the configured analytic model.
Pitfalls
  • A channel model recomputed per layer instead of once per TTI silently desynchronizes MAC and RRC success/failure views of the same instant.
  • Floating-point nondeterminism across platforms in the SINR formula breaks I11 unless the arithmetic is pinned to a deterministic order of operations.
  • A BLER curve with a discontinuity at the configured SINR threshold produces oscillating success/failure at cell-edge UEs that looks like a scheduler bug but is a channel-model artifact.

⬜ Phase 3 — Cell Search, SIB Acquisition & RACH §15

Objectives

Implement the cell-search/SIB-acquisition sequence (§8.3) and the RACH four-step exchange (§8.4), including contention resolution and collision handling.

Deliverable

A UE population performs cell search, acquires SIBs, and completes RACH against a configured cell, with a subset of UEs deliberately colliding on preamble selection to exercise contention resolution.

Acceptance
  • RACH contention-resolution success rate at nominal preamble-pool load ≥ 99% (M14).
  • SIB acquisition completes in ≤ 4 simulated TTIs from synchronization (named fixture, not a 3GPP-mandated figure).
  • Preamble collision correctly triggers backoff-and-retry for exactly the colliding UEs, never for uninvolved UEs.
Fixtures
  • rach_four_step_success.json — golden message-order trace for a clean RACH.
  • rach_collision_backoff.json — two UEs colliding, asserting correct Msg4 contention outcome and backoff timing.
  • sib_acquisition_order.json — asserts MIB before SIB1 before SIB2.
Pitfalls
  • A backoff timer drawn from the same PRNG stream as an unrelated component silently breaks determinism (ADR-17) if the seed derivation is not per-component.
  • Contention resolution that resolves by UE arrival order rather than by the 3GPP-specified temporary-identity match produces a plausible-looking but non-conformant trace (violates P13).
  • A preamble pool sized without reference to the SINR/cell-load model from Phase 2 produces unrealistic collision rates that mask real contention-resolution bugs.

⬜ Phase 4 — The RRC State Machine and Connection Setup §16

Objectives

Implement the complete RrcState transition function (Idle, Connecting, Connected, with Inactive reserved for the Phase 11 5G extension) and the RRC connection-establishment procedure of §8.5, closing the gap between "UE has completed RACH" (Phase 3) and "UE holds an active RRC connection" ready to carry NAS signaling.

Deliverable

A UE that has just completed Phase 3's RACH performs the full three-message RRC connection setup (§8.5) and transitions Idle → Connecting → Connected, with a trace showing every transition and its triggering message, and with a T300-expiry rollback path exercised by a deliberately delayed ConnectionSetup.

Acceptance
  • RRC connection setup latency (simulated) < 50 ms at nominal load (M5, matches §4).
  • Connection-setup success rate ≥ 99.5% across 100,000 attempts at nominal RACH-success precondition.
  • Exactly 3 messages per successful setup (ConnectionRequest, ConnectionSetup, ConnectionSetupComplete) — any deviation fails the fixture.
  • Zero I1 violations (two simultaneous RRC states for one UE) across a 1,000,000-UE-event stress fixture.
  • T300 expiry correctly rolls back 100% of deliberately-delayed setups to Idle within one configured timer period.
Fixtures
  • rrc_connection_setup_success.json — golden 3-message trace for a clean setup.
  • rrc_t300_expiry_rollback.json — delayed ConnectionSetup, asserts rollback to Idle.
  • rrc_reestablishment_after_rlf.json — radio-link failure mid-Connected, asserts re-establishment sequence and FM-1 telemetry.
  • rrc_state_invariant_stress.json — 1,000,000 concurrent transitions, asserts zero I1 violations.
Pitfalls
  • Double-transition race — manifestation: a UE briefly reports two RRC states in trace output; root cause: the transition function mutates state before validating the precondition, so a re-entrant call during dispatch overwrites a not-yet-committed transition; debug method: replay under sim-replay with per-transition tracing at max verbosity; signal: rrc_state_gauge momentarily reports an invalid enum discriminant; recovery: halt and treat as an I1 violation per §7's methodology.
  • T300 timer ownership leak — manifestation: a UE stuck in Connecting indefinitely; root cause: the T300 timer was scheduled but never registered with the per-UE timer-wheel ownership registry (I9); debug method: query orphaned_timer_count; signal: nonzero orphaned_timer_count with no corresponding rollback event; recovery: forced rollback to Idle plus a regression fixture.
  • Piggyback payload leakage — manifestation: RRC logic branches on NAS message content; root cause: a developer inspected the piggybacked Attach Request instead of treating it as opaque, violating P6; debug method: ownership/dependency lint in CI (ADR-08's sibling check) flags the cross-layer read; signal: CI lint failure, not a runtime symptom; recovery: refactor to pass the NAS PDU as an opaque Bytes-like type.
  • Re-establishment vs fresh-setup confusion — manifestation: a re-established connection is indistinguishable from a fresh one in metrics; root cause: FM-1's re-establishment path reuses the setup transition without a distinguishing trigger tag; debug method: inspect sim-tracing span attributes for the trigger field; signal: handover_outcome_histogram- adjacent metrics undercount RLF events; recovery: tag the trigger explicitly at emission.

⬜ Phase 5 — NAS Attach / Registration §17

Objectives

Implement the LTE attach procedure of §8.6 end-to-end at the NAS layer: the 11-message sequence from RRC-carried Attach Request through Attach Complete, including the EmmState transition function (Deregistered→Registering→Authenticating→Registered), building on Phase 4's RRC connection.

Deliverable

A UE with an active RRC connection (Phase 4) completes the full 11-message attach sequence of §8.6 and reaches EmmState::Registered with an allocated GUTI, observable in a call-flow trace matching the §8.6 message order exactly.

Acceptance
  • Attach procedure latency (simulated) < 300 ms at nominal load (M4, matches §4).
  • Exactly 11 NAS/RRC messages per successful attach (M8, matches §4's signaling-load target from TS 24.301/36.331).
  • Zero I8 violations (GUTI collision) across a 100,000-UE fixture with concurrent attaches.
  • Attach rejected (not silently dropped) for 100% of malformed or out-of-state Attach Request fixtures.
Fixtures
  • attach_full_sequence_success.json — golden 11-message trace matching §8.6.
  • attach_guti_uniqueness_stress.json — 100,000 concurrent attaches, asserts zero I8 violations.
  • attach_reject_already_registered.json — Attach Request from an already-Registered UE, asserts defined rejection.
  • attach_malformed_ie_reject.json — malformed information element, asserts parser rejection without panic.
Pitfalls
  • GUTI reuse across concurrent attaches — manifestation: two UEs briefly share a GUTI in trace output; root cause: the identity table's allocation check races with an in-flight deallocation from a just-completed detach; debug method: replay under sim-replay with identity-table tracing; signal: nonzero guti_collision_count; recovery: reallocate per I8's defined recovery and add the interleaving as a regression fixture.
  • EmmState skip on retransmitted Attach Request — manifestation: a UE appears to re-attach from Registered without a detach; root cause: a retransmitted (duplicated in transport) Attach Request is processed as a fresh attempt rather than recognized as a duplicate; debug method: inspect the NAS sequence-number/transaction-ID field in the trace; signal: attach-success-rate metric double-counts; recovery: dedupe on NAS transaction ID before EmmState transition.
  • Stubbed-security-phase false confidence — manifestation: attach fixtures pass in Phase 5 despite no real AKA logic existing; root cause: steps 4–7 are intentionally pass-through stubs (§17.2) and the fixture only checks message order, not security-context validity; debug method: cross-check against I3's assertion, which is not yet wired to this phase's code path; signal: none — this is a documentation risk, not a runtime one; recovery: Phase 6's acceptance criteria explicitly re-run attach_full_sequence_success.json with real AKA wired in to close the gap.
  • Core-session stub masking bearer defects — manifestation: attach succeeds but the default bearer is silently absent; root cause: Create Session Request/Response stubs (steps 8–9) always report success in this phase; debug method: Phase 7's bearer-existence assertion (I2) will catch this once wired; signal: none in Phase 5 alone; recovery: treat as a known, tracked stub boundary, not a defect, until Phase 7.

⬜ Phase 6 — EPS-AKA / 5G-AKA Authentication and the Key Hierarchy §18

Objectives

Implement §8.7's EPS-AKA sequence and §8.8's key-hierarchy derivation with symbolic keys (ADR-10), replacing Phase 5's authentication/security-mode stubs with real vector generation, RES/XRES comparison, and KeNB derivation; shape the extension to 5G-AKA and the 5G key hierarchy for Phase 11 reuse.

Deliverable

A UE completes Phase 5's attach with real EPS-AKA wired in: the HSS generates a vector, the MME forwards RAND/AUTN, the UE returns RES, the MME validates against XRES, and KASME/KeNB are derived at both ends before Security Mode Command/Complete completes — I3 is now enforceable end-to-end. A negative fixture demonstrates a RES/XRES mismatch triggering FM-3.

Acceptance
  • AKA round trip (vector request through KeNB derivation) adds < 20 ms simulated latency to the attach sequence, within M4's 300 ms attach budget.
  • RES/XRES mismatch correctly triggers FM-3 in 100% of deliberately-mismatched fixtures, never a silent accept.
  • Zero I3 violations (protected message before security context) across a 100,000-attach fixture.
  • Zero I14 violations (dual ACTIVE security contexts for one UE) across a re-authentication stress fixture.
  • Algorithm-downgrade attempts rejected in 100% of fixtures (T3 mitigation).
Fixtures
  • eps_aka_success.json — golden vector-request-through-KeNB-derivation trace matching §8.7/§8.8.
  • eps_aka_res_mismatch.json — RES != XRES, asserts FM-3 and no security-context establishment.
  • key_hierarchy_derivation_golden.json — golden symbolic KeyToken chain for a fixed seed.
  • security_downgrade_reject.json — asserts algorithm-downgrade rejection (T3).
  • dual_security_context_stress.json — re-authentication race, asserts zero I14 violations.
Pitfalls
  • Premature protected-message dispatch — manifestation: a protected NAS/RRC message observed before Security Mode Complete; root cause: the I3 dispatch guard checks Option<SecurityContext> presence but not its pending-vs-ACTIVE sub-state, so a mid-derivation context reads as present; debug method: assert on lifecycle sub-state, not mere presence; signal: protected_before_aka_count nonzero; recovery: reject and re-run Security Mode Command.
  • KeNB re-derivation on NAS-count rollover — manifestation: KeNB silently changes value without a triggering procedure; root cause: the NAS uplink count feeding KeNB derivation wrapped without a defined rollover edge; debug method: compare key_hierarchy_derivation_golden.json across a long-run fixture; signal: replay-hash mismatch (I11); recovery: define and fixture the rollover edge before Phase 7 depends on a stable KeNB.
  • Dual active context on retry storm — manifestation: two ACTIVE security contexts coexist momentarily; root cause: a retransmitted Authentication Request triggers a second authentication racing the original's completion; debug method: HSS/UDM + MME/AMF context-table trace; signal: dual_security_context_count; recovery: invalidate the stale context per I14.
  • Symbolic-key confusion with real crypto — manifestation: a reviewer assumes KeyToken values carry real security strength; root cause: ADR-10's rationale is easy to forget once the chain "looks like" real AKA; debug method: code-review checklist, not a runtime check; signal: none automated; recovery: keep KeyToken(u128) unexported outside sim-nas/sim-rrc/sim-epc, making misuse a compile error.
  • Downgrade check ordering — manifestation: a downgrade is accepted before rejection logic runs; root cause: algorithm-selection validation placed after KeNB derivation rather than before, so weak-algorithm keys are already derived when the rejection fires; debug method: trace-order inspection of security_downgrade_reject.json; signal: derivation events precede the rejection event; recovery: reorder validation ahead of derivation (P8).

  • QCI-to-priority inversion under load — manifestation: a QCI-9 (default) bearer's traffic is scheduled ahead of a QCI-1 (conversational voice) bearer's; root cause: the MAC scheduler's simplified round-robin/proportional-fair model (ADR-12) does not yet consult QCI priority; debug method: per-bearer scheduling-order trace; signal: latency-budget fixture failure for QCI-1; recovery: documented as a known Phase 7 scope boundary under ADR-12, flagged for §31/§34 if it becomes load-bearing.

  • Paging-channel timing conflated with real SDR — manifestation: a reviewer assumes this phase's paging-cycle timing reflects real DRX/paging-channel timing; root cause: this phase deliberately abstracts paging-channel scheduling per the SDR-bridge deferral; debug method: none — a documentation risk, not a runtime one; recovery: §37's deferred-features register is the canonical pointer for real paging-channel fidelity.

  • Zero I5 violations (UE left unserved) across a 100,000-handover stress fixture, including the rejection-rollback path.
  • Zero data loss beyond the configured reordering window during forwarding, verified against I6.
  • Rejection-triggered rollback completes within one configured admission-response timeout in 100% of fixtures.
Fixtures
  • x2_handover_success.json — golden 9-message trace matching §8.10.
  • x2_handover_admission_reject_rollback.json — target rejects, asserts I5 rollback (FM-2).
  • s1_handover_mme_mediated.json — golden S1 handover trace with MME-mediated signaling substituted for direct X2.
  • handover_data_forwarding_reorder.json — asserts I6-bounded reassembly of forwarded PDUs.
Pitfalls
  • Path switch race with data forwarding — manifestation: user-plane packets arrive at the source cell after the SGW has already switched the downlink path to the target; root cause: Path Switch Request/Acknowledge (steps 7–8) is not gated on forwarding-buffer drain confirmation; debug method: trace forwarding-buffer state against the path-switch acknowledge timestamp; signal: dropped-packet count spikes during handover; recovery: gate path switch on forwarding drain, add as a regression fixture.
  • UE Context Release before path switch confirms — manifestation: the source-side context disappears while the UE is still mid-handover; root cause: step 9 fires on a fixed timer rather than being gated on step 8's acknowledgment, violating P8's ordering discipline; debug method: HandoverContext state-trace inspection; signal: handover_outcome_histogram records a rollback with no source context to roll back to; recovery: gate release strictly on path-switch acknowledgment.
  • Reordering-window overflow during forwarding — manifestation: forwarded PDCP PDUs are discarded even though they arrived within a reasonable interval; root cause: the target cell's reorder buffer window is sized for steady-state traffic, not the burst of forwarded-plus-new PDUs at handover; debug method: reorder_window_violation_count spikes specifically during handover windows, not steady state; signal: this metric; recovery: size the reorder window with a handover-specific burst allowance (I6, FM-8).
  • S1-vs-X2 code-path divergence — manifestation: S1 and X2 handover produce structurally different HandoverContext traces even though both should end in the same terminal states; root cause: the S1 substitution was implemented as a separate function rather than the same state machine with a different transport binding, violating this phase's reuse intent; debug method: diff x2_handover_success.json and s1_handover_mme_mediated.json terminal-state shape; signal: fixture divergence in HandoverState sequencing, not just message content; recovery: refactor to share the HandoverContext state machine, varying only the transport.

⬜ Phase 10 — Multi-UE Scenarios, Core-Network Elements and Signaling-Load Metrics §22

Objectives

Scale the simulator to many concurrent UEs across many cells, flesh out the core-network elements (MME/SGW/PGW/HSS) as full logical-element state machines rather than per-procedure stubs, and build the signaling-load-metrics model that feeds §30/§34.

Deliverable

A 100,000-UE, 2,000-cell scenario runs for a full 24-simulated-hour horizon, mixing attach, handover, paging, and TAU procedures at realistic concurrency, sustaining §4's throughput/latency targets, and producing per-cell signaling-load metrics plus a deterministic replay hash.

Acceptance
  • Sustained event throughput ≥ 5,000,000 events/second at full 100,000-UE, 2,000-cell scale (M3).
  • Simulated-to-wall-clock ratio ≥ 100:1 at 10,000 UEs (M12, matches §4).
  • Zero regressions in any Phase 4–9 negative fixture re-run at scale — I1, I2, I3, I5, I6, I8, I12, I13, I14 all zero-violation across the full run.
  • Per-cell signaling load reported for 100% of cells with nonzero UE population.
  • Replay-hash identical across 3 repeated full-scale runs from the same seed (I11, M11 = 100%).
Fixtures
  • multi_ue_100k_mixed_procedures.json — golden aggregate-metrics trace for the full-scale mixed-procedure scenario.
  • signaling_load_per_cell_report.json — asserts per-cell signaling-load computation against a golden reference.
  • phase4_9_regression_at_scale.json — re-runs every prior phase's negative fixtures under full concurrency.
Pitfalls
  • Concurrency masking a per-UE invariant bug — manifestation: an invariant violation (e.g. I1) never appears at low UE count but appears above a concurrency threshold; root cause: a shared-state bug violating P5 only manifests under contention; debug method: bisect the UE-count threshold at which the violation first appears under sim-replay; signal: an I#-violation counter nonzero only above a specific scale; recovery: fix the ownership violation and add that concurrency level as a permanent regression fixture.
