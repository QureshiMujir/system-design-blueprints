225 — Cellular Protocol Basics (LTE/5G Simulation)

Project Number: 225

Project Name: Cellular Protocol Basics (LTE/5G Simulation)

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from scratch in Rust, a discrete-event simulation of the LTE and 5G cellular control-plane and user-plane protocol stacks at message and state-machine fidelity. The simulator models User Equipment (UE), the radio access network (eNodeB for LTE, gNB for 5G NR), and the core-network control elements (MME/AMF for mobility management, SGW/UPF for user-plane forwarding, HSS/UDM for subscriber and security data) as independent state machines driven by a single deterministic event queue. Each node runs a layered protocol stack — NAS, RRC, PDCP, RLC, MAC, and a simplified PHY abstraction — and the simulator reproduces the message sequences and timing of the key 3GPP procedures: cell search and system-information acquisition, random access (RACH), RRC connection establishment, attach/registration, authentication and key agreement (AKA), bearer/PDU-session setup, handover (X2/Xn for LTE, S1/N2 paths), paging, and idle/connected-mode mobility. The engine drives many concurrent UEs across many cells and produces latency, throughput, and signaling-load metrics from the resulting deterministic event trace.

Boundaries

Provides: layered protocol state machines (NAS/RRC/PDCP/RLC/MAC); message-sequence-accurate procedures (RACH, RRC setup, attach, AKA, bearer/PDU-session setup, handover, paging); a discrete-event engine scaling to many UEs and cells; a simplified analytic PHY/channel abstraction (an SINR-to-BLER-to-success mapping) driving MAC behavior; LTE EPC and 5G core logical elements; deterministic replay from a seed; latency/throughput/signaling-load metrics; call-flow conformance traces checked against the 3GPP-specified sequences.

Delegates: real RF signal processing — out of scope entirely; SIM/USIM cryptographic hardware and real cryptographic primitives are represented symbolically (keys as opaque tokens, not real crypto engines, per ADR-10); GTP-U/GTP-C and Diameter/HTTP-2-based SBI transport are modeled as typed message-passing abstractions, not byte-accurate wire encodings (ADR-18); IMS/voice/SIP are not modeled.

Does NOT provide: SDR integration, an OFDM/waveform-level PHY, ASN.1 binary wire compatibility with commercial stacks, real eNodeB/gNB interoperability, full 3GPP conformance certification, production carrier billing or IMS.

Non-Goals

Not an SDR platform. Not an OFDM modem. Not a production core network. This is the cellular control-plane protocol simulator among sibling networking blueprints: TCP-IP-Stack (project 33) covers the general internet transport/network layers; TLS-Handshake (project 48) covers the cryptographic handshake protocol in isolation. This project's load-bearing concerns are specifically the layered cellular protocol state machines (NAS/RRC/PDCP/RLC/MAC), the attach/handover procedures as 3GPP-specified message sequences, and the discrete-event simulation of many concurrent UEs across cells. The detailed RF/OFDM physical layer is explicitly a simplified analytic abstraction — never modeled to signal fidelity.

LTE-First, 5G-Extension Path

Phases 0 through 10 build and harden the LTE (E-UTRAN/EPC) call flows. Phase 11 extends the same discrete-event engine and layered-stack abstraction to 5G NR (gNB, AMF, UPF, RRC-Inactive), reusing the shared state-machine and message-passing infrastructure rather than forking it (P14).

Deployment Model

A discrete-event simulation library (sim-core, sim-events, sim-clock) plus a scenario execution harness (sim-cli, sim-scenarios) — not a running network service. Scenarios are declarative topology-and-traffic descriptions; a run produces a deterministic event trace, metrics, and call-flow conformance verdicts.

Users / Operators

Network engineers studying 3GPP call flows without lab hardware; students learning cellular protocol architecture; researchers experimenting with mobility, scheduling, and signaling-load models.

What Later Phases Unlock

Multi-cell handover studies; signaling-storm and denial-of-service scenario replay; 5G RRC-Inactive and QoS-flow experiments; differential validation against ns-3 LTE/5G-LENA and srsRAN/OAI traces.

Rust Rationale

Enum-driven exhaustive modeling of protocol states and messages — a match must handle every state-by-message combination, so an unhandled transition is a compile error, mirroring the real-world cost of an unhandled message in a live stack (P2). Ownership rules make per-UE, per-bearer state ownership explicit, matching this simulator's core invariant of single-owner mutable protocol state (P5). No garbage collector, so the discrete-event loop's latency is not perturbed by GC pauses when measuring simulated procedure latencies. Cargo/crates.io ecosystem gives structured logging, serialization, and property-testing tooling for free.

Rejected languages: Python — too slow for 100,000+ simulated UEs, weak state-machine exhaustiveness checking. Go — weaker sum-type modeling of protocol messages, GC pauses complicate timing-precision claims. C++ — memory-safety risk in message parsers is exactly the failure class Rust's borrow checker forecloses, and this simulator's parsers handle adversarial/fuzzed input starting Phase 11.

Prerequisites

Networking fundamentals (OSI/TCP-IP layering); finite-state-machine design; discrete-event simulation methodology (event scheduling, simulated clocks); basic wireless/RF vocabulary (SINR, fading, cell) sufficient to consume the PHY abstraction without needing to implement it.

2. Why Build This

  • protocol state-machine implementation at 3GPP fidelity
  • deterministic discrete-event simulation architecture
  • layered-stack message-passing design (NAS/RRC/PDCP/RLC/MAC)
  • cellular control-plane architecture (EPC and 5GC)
  • authentication and key-hierarchy reasoning (EPS-AKA/5G-AKA)
  • mobility and handover procedure modeling
  • signaling-load and latency analysis
  • call-flow conformance verification methodology
  • failure-injection and chaos methodology applied to a real standard
  • observability-first systems engineering
  • queueing and scheduling reasoning at the MAC layer
  • replay-driven deterministic debugging

Historically, LTE and 5G are among the largest deployed distributed protocol systems in the world; understanding EPC/5GC decomposition, RRC state transitions, NAS signaling, bearer management, and mobility semantics gives direct insight into modern carrier infrastructure, large-scale mobility systems, and latency-sensitive distributed protocols generally.

What Mastery Looks Like

  • Explaining, from memory, the RACH four-step exchange and why contention resolution exists — demonstrated in Phase 3.
  • Tracing the full attach call flow (RRC setup → NAS attach → AKA → bearer setup) message-by-message against TS 24.301 and TS 23.401 — demonstrated in Phase 5.
  • Deriving the LTE key hierarchy (K → CK/IK → KASME → KeNB → user-plane keys) and explaining what each key protects — demonstrated in Phase 6.
  • Producing a handover trace showing data forwarding and interruption-time measurement against the 3GPP target — demonstrated in Phase 9.
  • Running a 10,000-UE scenario and reading its signaling-load and latency metrics to find a bottleneck — demonstrated in Phase 10.
  • Extending an LTE abstraction to 5G NR (RRC-Inactive, AMF/UPF) without rewriting the discrete-event core — demonstrated in Phase 11.
  • Explaining why the PHY is abstracted to an SINR/BLER mapping without losing protocol-level correctness — demonstrated in Phase 2.

Scenario Driver. Parses scenario manifests (topology, UE population, traffic, fault schedule), seeds the deterministic PRNG, and hands an executable graph to the engine. Owns scenario lifecycle boundaries; contains no protocol logic.

Discrete-Event Engine. Owns the global event queue and simulation loop. Every state transition anywhere in the system is a reaction to a dequeued Event; the engine guarantees non-decreasing timestamp processing (I4) and deterministic replay from a seed (I11, P3, P10).

UE. Runs the full client-side layered stack (NAS, RRC, PDCP, RLC, MAC, PHY abstraction) plus mobility state. Each UE is an independent state machine with single ownership of its own context (P5).

eNodeB / gNB. Runs the network-side RRC, PDCP, RLC, MAC (with scheduler), and the same PHY abstraction, terminating the Uu air interface toward UEs and the S1/N2 and X2/Xn interfaces toward the core network and peer base stations. Scheduling decisions are made here (P7, P9).

Core Network. MME/AMF (mobility/session management), SGW/UPF (user-plane forwarding), HSS/UDM (subscriber and security data) — modeled as logically separated state machines communicating over typed message boundaries mirroring S1/N2 and S11/N11-equivalent interfaces (P9).

Radio Channel Abstraction. Produces an SINR value per UE per cell per TTI from a simple analytic propagation model; feeds MAC/PHY success/failure decisions (P7, ADR-06).

Mobility Model. Drives UE position/velocity and triggers cell-reselection and handover-measurement events consumed by RRC.

Metrics Collector. Consumes the event trace to compute procedure latencies, throughput, and signaling-load statistics, and to feed call-flow conformance checks (sim-conformance).

The Uu air interface (UE ↔ eNodeB/gNB) and the S1/N2 and X2/Xn interfaces (base station ↔ core, base station ↔ base station) are drawn explicitly as message boundaries — every message crossing them is a typed, loggable Message value, never shared memory.

6. Design Principles

  • P1 — Message/state-machine fidelity: a procedure is correct when its message sequence and state transitions match the 3GPP call flow, not when RF is modeled.
  • P2 — Every protocol layer is a state machine with a defined behavior for every message in every state; an unhandled message is a dropped call.
  • P3 — The discrete-event clock is the single source of time; every latency is measured in simulated time, so results are deterministic and reproducible from a seed.
  • P4 — Security context precedes protected traffic: no user-plane or protected NAS/RRC message is exchanged before the AKA-derived security context is established.
  • P5 — State ownership is single and explicit: a UE's protocol-stack state, a bearer's context, and a cell's scheduler state each have exactly one owning component.
  • P6 — Layer boundaries are typed SDU/PDU contracts, not shared mutable memory — NAS talks to RRC only through defined message types, mirroring 3GPP layering.
  • P7 — The PHY is abstracted to an SINR-to-success mapping deliberately — MAC/RLC/RRC react to success/failure and channel quality, not waveforms.
  • P8 — Failure paths are first-class, not afterthoughts — every procedure has a defined rejection/failure/rollback edge.
  • P9 — The core network is modeled as logical functions with well-defined interfaces (S1/N2-equivalent), not a monolith, matching 3GPP's own decomposition.
  • P10 — Determinism over throughput: a scenario run must be bit-reproducible from its seed even under bounded parallel execution.
  • P11 — Backpressure is explicit everywhere: every queue (event queue, RLC/PDCP buffers, MAC HARQ buffers) has a bounded capacity and defined overflow behavior.
  • P12 — Observability is mandatory infrastructure: every procedure emits a structured trace sufficient to reconstruct its call flow without re-running the simulation.
  • P13 — Conformance is continuously verified: the simulated message order for each procedure is checked against the 3GPP-specified sequence on every CI run.
  • P14 — Scope is LTE-first, 5G-shaped: every abstraction (event, message, state machine) is designed so the Phase 11 5G extension reuses it rather than forking it.

8.14 Discrete-Event Simulation Model

Event — (SimTime, EventKind, target). Event queue — a min-heap ordered by SimTime (I4). Simulation loop (named steps): (1) pop earliest event; (2) advance simulated clock to its timestamp; (3) dispatch to target state machine; (4) state machine emits zero or more new events; (5) push new events; (6) repeat until queue empty or run horizon reached. Mobility model — a scheduled recurring event per UE that updates position/velocity and may emit a measurement-report event consumed by RRC.

8.15 Worked End-to-End Example

UE powers on → cell search + SIB acquisition (§8.3) → RACH (§8.4) → RRC connection setup (§8.5) → NAS attach carried in RRC Setup Complete (§8.6) → EPS-AKA (§8.7) establishes security context (I3) → default bearer setup (§8.9) → UE enters RRC-Connected with active default bearer → mobility model reports degrading source-cell SINR → measurement report triggers X2 handover (§8.10) → UE ends up RRC-Connected on the target cell with the same bearer context intact (I5).

8.16 Failure / Malformed Examples

  • RACH collision: two UEs select the same preamble in the same RACH occasion; both receive the same RAR; contention resolution (Msg4) fails for one, which backs off and retries (FM-4).
  • Authentication failure: UE's computed RES does not match XRES (stale/replayed vector, T2); MME rejects and either re-runs AKA or releases the connection (FM-3).
  • Handover failure: target eNodeB rejects Handover Request (admission failure); source eNodeB never receives Acknowledge before its timer expires; UE rolls back to the source cell per I5 (FM-2).
  • Paging timeout: UE does not respond to paging within the tracking-area window; MME/AMF re-pages up to a bounded retry count, then marks the UE unreachable (FM-6).
  • Dropped RRC message: the transport fabric drops an RRC Connection Setup message under injected loss; the UE's T300 timer expires and it returns to Idle (FM-9).
  • Out-of-order PDCP PDU: a retransmission race during handover data forwarding delivers PDCP PDUs outside the reordering window; the receiver discards and requests retransmission (I6, FM-8).

12. Phase 0 — Skeleton, Discrete-Event Engine & CI

12.1 Objectives

Stand up the Cargo workspace with all 22 crates as empty skeletons, and build the discrete-event core: SimTime, Event, EventQueue, and the simulation loop. Establish CI (lint, build, unit tests) before any protocol logic exists.

12.2 Detailed Implementation Steps

The event queue is a binary min-heap ordered by SimTime (ADR-03), enforcing I4 (non-decreasing timestamp processing) at the pop path. The simulation loop follows the named steps in §8.14: pop, advance clock, dispatch, collect emitted events, push, repeat. Seeding follows ADR-17 — a single deterministic PRNG derived from the scenario seed feeds every random draw in the run, which is the mechanism behind I11 (replay-hash identity). Per Banks/Carson/Nelson & Nicol's event-scheduling algorithm (§5, Required Reading), the priority-queue push/pop are the dominant per-event cost and are benchmarked from this phase onward (M3, M9).

12.3 Deliverable

A runnable sim-core binary that drives a synthetic workload of no-op events through the queue, prints a deterministic replay hash, and exits.

12.4 Acceptance Criteria

  • Sustained event throughput ≥ 5,000,000 events/second on the synthetic workload (M3).
  • Event-queue depth handles 10,000,000 pending events without reallocation failure (M9).
  • Replay-hash identical across 10 repeated runs from the same seed (I11, M11 = 100%).
  • Zero event-ordering violations (I4) across a 1,000,000-event synthetic run.

12.5 Conformance Fixtures

  • scheduler_ordering.json — asserts strictly non-decreasing dispatch timestamps.
  • timer_rollover.json — exercises timer-wheel bucket boundary edge cases.
  • replay_seed_a.json — golden replay hash for a fixed seed and workload.

12.6 Pitfalls

  • Priority inversion: a low-priority event with an earlier timestamp starves a logically-critical timer if the heap comparator ties break inconsistently.
  • Hidden nondeterminism: an unseeded HashMap iteration order or system-clock read inside dispatch logic silently breaks I11 without any visible test failure until a rerun diverges.
  • Timer bucket overflow: a burst of same-timestamp timers overflowing a bucket's fixed capacity if bucket sizing assumptions are violated.
  • Zero-delay event cascades: an event that schedules another event at the same SimTime can recurse unboundedly if not capped, exhausting the call stack.

12.7 Performance Concerns

Heap allocation churn from boxing EventKind variants; cache misses walking the binary heap at depth; excessive tracing-span allocation if sim-tracing hooks are wired in before sampling is bounded.

12.8 Edge Cases

Simultaneous timestamps from independent components; zero-delay timers; queue exactly at capacity; replay from a corrupted or truncated seed file.

12.9 Failure Analysis

A corrupted event-ordering path is the single highest-severity Phase 0 defect class: it invalidates every invariant downstream that assumes I4 and I11. Detection is the replay-hash mismatch check (I11); recovery is a halt plus full event-log dump for bisection, never a silent continue.

12.10 Operational Notes

Emit from Phase 0 onward: scheduler depth, event dispatch p50/p99, timer-insert latency, replay-mismatch count. CI runs scheduler_ordering.json and replay_seed_a.json on every commit (ADR-22).

13. Phase 1 — Layered Protocol-Stack Scaffolding & Message Passing

13.1 Objectives

Build the ProtocolStack scaffolding (NAS, RRC, PDCP, RLC, MAC, PHY-abstraction) as typed SDU/PDU boundaries with no procedure logic yet — only message-passing plumbing between layers and between UE and eNodeB across the Uu boundary.

13.2 Detailed Implementation Steps

Per P6, each layer exposes only typed message in/out; no shared mutable state crosses a layer boundary. sim-transport implements the Uu/S1/N2/X2/Xn boundaries as explicit Message deliveries scheduled as EventKind::RadioArrival events (I7 — no message processed before its arrival event fires). This mirrors srsRAN's lib/src/ layer separation (Required Reading, Reference Implementations) but without PHY/RF code. RLC/PDCP sequence numbering scaffolding is introduced here (fields only; monotonicity enforcement lands with real traffic in Phase 9) — see TS 36.322 and TS 36.323.

13.3 Deliverable

A UE and an eNodeB exchange a scaffolded "hello" message through the full stack (NAS down through PHY-abstraction, across Uu, back up through the peer stack) with no procedure semantics, only correct layering and event-driven delivery.

13.4 Acceptance Criteria

  • Every layer transition is total (P2): a fuzzed message reaching a layer in any defined state either transitions or is explicitly rejected — never panics.
  • Message round-trip latency across the full stack (both directions) <= 6 simulated transport hops as configured.
  • Zero shared-mutable-state violations detected by the ownership lint in CI (ADR-08).

13.5 Conformance Fixtures

  • layer_passthrough.json — asserts a message traverses all six layers in order.
  • unhandled_message_panic_free.json — fuzzes every layer with out-of-state messages, asserts no panics (P2).

13.6 Pitfalls

  • A layer that silently drops an unrecognized message instead of emitting a defined rejection breaks P2's exhaustiveness guarantee at runtime even if it compiles.
  • PDCP/RLC sequence-number fields left uninitialized across a scaffolded round-trip mask a real monotonicity bug that only surfaces once Phase 9 exercises real reordering.
  • Uu delivery scheduled with zero transport delay collapses causal ordering assumptions that later phases rely on for latency measurement.

13.7 Performance Concerns

Per-message boxing/cloning across six layer boundaries; excessive Message enum size inflating per-event memory if variants are not kept small.

13.8 Edge Cases

A message addressed to a UE that has been torn down mid-transit; a message that crosses Uu but targets a cell that has since been removed from the topology.

13.9 Failure Analysis

A mis-wired layer boundary (e.g. RRC calling PDCP fields directly rather than through a typed message) reintroduces the coupling P6 exists to prevent; the ownership/dependency lint in CI is the primary defense, with pitfalls captured as new fixtures if bypassed.

13.10 Operational Notes

Trace every cross-layer and cross-Uu message with a correlation ID (P12) from this phase onward — this correlation ID is the backbone every later call-flow trace (§8, §28) depends on.

14. Phase 2 — PHY/Channel Abstraction & Cell Model

14.1 Objectives

Implement sim-phy's analytic SINR/BLER channel model and the cell model (ENodeB topology, coverage) that MAC/RLC/RRC react to, per ADR-06 and P7.

14.2 Detailed Implementation Steps

The channel model computes an SINR per UE per cell per TTI from a simple analytic path-loss function (Rappaport, Required Reading — PHY abstraction only, not RF fidelity per §1 non-goals). MAC (sim-mac) maps SINR to a block-error-rate curve and derives success/failure for each transport block (P7); this is the entire PHY surface exposed to higher layers. Cell topology (CellId, coverage radius, neighbor list) is fixed per scenario and consumed by the mobility model (Phase 8) for handover triggers later.

14.3 Deliverable

A static two-cell topology where a stationary UE's SINR is computed each TTI and fed into a MAC-level success/failure decision, observable via metrics — with no scheduling or RACH yet.

14.4 Acceptance Criteria

  • SINR computation deterministic given UE/cell positions and seed (P10).
  • BLER-mapped transport-block success rate matches the configured analytic curve within 0.5% over 100,000 simulated TTIs.
  • Channel model evaluation cost does not exceed 5% of total per-event dispatch time (M3 gate maintained).

14.5 Conformance Fixtures

  • sinr_static_topology.json — golden SINR values for a fixed two-cell layout.
  • bler_curve_calibration.json — checks the success-rate-vs-SINR curve against the configured analytic model.

14.6 Pitfalls

  • A channel model recomputed per layer instead of once per TTI silently desynchronizes MAC and RRC success/failure views of the same instant.
  • Floating-point nondeterminism across platforms in the SINR formula breaks I11 unless the arithmetic is pinned to a deterministic order of operations.
  • A BLER curve with a discontinuity at the configured SINR threshold produces oscillating success/failure at cell-edge UEs that looks like a scheduler bug but is a channel-model artifact.

14.7 Performance Concerns

Recomputing SINR for every UE-cell pair rather than only serving-cell-relevant pairs scales quadratically with topology size; must be bounded to neighbor cells only.

14.8 Edge Cases

A UE exactly on a cell boundary; a UE with no cell in range (SINR below any usable threshold); a topology with a single cell (no handover candidate).

14.9 Failure Analysis

An incorrect BLER mapping silently biases every downstream procedure's success rate, producing misleading Phase 3+ conformance results; this phase's calibration fixture (bler_curve_calibration.json) is the primary guard and must be re-run whenever the analytic model's parameters change.

14.10 Operational Notes

Export SINR distribution and transport-block success-rate metrics per cell from this phase onward; these become the basis for the RACH collision-probability model in §34.

15. Phase 3 — Cell Search, SIB Acquisition & RACH

15.1 Objectives

Implement the cell-search/SIB-acquisition sequence (§8.3) and the RACH four-step exchange (§8.4), including contention resolution and collision handling.

15.2 Detailed Implementation Steps

Cell search is modeled as an abstracted synchronization event (P7 — no PSS/SSS waveform correlation) followed by MIB/SIB1/SIB2 delivery as ordinary RadioArrival events (I7). RACH follows TS 36.321's four-step procedure exactly at the message level: Preamble → RAR → Msg3 → Msg4 contention resolution. Preamble collision (two UEs selecting the same preamble in the same RACH occasion) is modeled explicitly, exercising I6-adjacent reordering logic in Msg3 delivery and driving the RACH-collision-probability model developed in §34. Backoff on collision follows an exponential model (P8 — failure paths are first-class).

15.3 Deliverable

A UE population performs cell search, acquires SIBs, and completes RACH against a configured cell, with a subset of UEs deliberately colliding on preamble selection to exercise contention resolution.

15.4 Acceptance Criteria

  • RACH contention-resolution success rate at nominal preamble-pool load ≥ 99% (M14).
  • SIB acquisition completes in ≤ 4 simulated TTIs from synchronization (named fixture, not a 3GPP-mandated figure).
  • Preamble collision correctly triggers backoff-and-retry for exactly the colliding UEs, never for uninvolved UEs.

15.5 Conformance Fixtures

  • rach_four_step_success.json — golden message-order trace for a clean RACH.
  • rach_collision_backoff.json — two UEs colliding, asserting correct Msg4 contention outcome and backoff timing.
  • sib_acquisition_order.json — asserts MIB before SIB1 before SIB2.

15.6 Pitfalls

  • A backoff timer drawn from the same PRNG stream as an unrelated component silently breaks determinism (ADR-17) if the seed derivation is not per-component.
  • Contention resolution that resolves by UE arrival order rather than by the 3GPP-specified temporary-identity match produces a plausible-looking but non-conformant trace (violates P13).
  • A preamble pool sized without reference to the SINR/cell-load model from Phase 2 produces unrealistic collision rates that mask real contention-resolution bugs.

15.7 Performance Concerns

RACH occasions recurring on a fixed schedule across thousands of UEs generate a disproportionate share of Phase 3 events; the collision-detection check must stay O(1) per occasion, not O(UEs).

15.8 Edge Cases

All UEs in a RACH occasion selecting distinct preambles (no collision case); a preamble pool exhausted under load; a UE that collides on every retry up to the maximum retry count.

15.9 Failure Analysis

Persistent RACH collisions under configured load indicate an undersized preamble pool relative to attach/reattach concurrency (FM-4); detection is the contention-resolution mismatch counter, recovery is backoff-and-retry, and forensics is the RACH attempt trace.

15.10 Operational Notes

Export RACH collision rate and contention-resolution success rate per cell — this becomes the M14 gate and feeds the §34 RACH collision-probability model.

16. Phase 4 — The RRC State Machine and Connection Setup

16.1 Objectives

Implement the complete RrcState transition function (Idle, Connecting, Connected, with Inactive reserved for the Phase 11 5G extension) and the RRC connection-establishment procedure of §8.5, closing the gap between "UE has completed RACH" (Phase 3) and "UE holds an active RRC connection" ready to carry NAS signaling.

16.2 Detailed Implementation Steps

Encode §8.2's transition table as an explicit match over (RrcState, RrcMessage) per ADR-08 and P2: every state/message combination is either a defined transition or a defined rejection, never a silent drop. TS 36.331 §5.3 (RRC connection establishment) governs the Idle→Connecting→Connected sequence of §8.5 — ConnectionRequest moves Idle to Connecting; the T300 supervision timer (I9 — every timer has exactly one owner, and firing it deterministically transitions the owning state machine) guards Connecting and rolls back to Idle on expiry (P8). ConnectionSetupComplete carries the NAS Attach Request as an opaque piggybacked payload — RRC forwards it without inspecting it (P6, typed SDU/PDU boundary between NAS and RRC). I1 (exactly one RRC state per UE at any instant) is asserted at every transition-function call site, not only at construction, catching a double-transition bug the moment it happens rather than downstream. RRC re-establishment (radio-link failure while Connected) follows the same state machine with a distinct trigger edge, per §8.2's Connected→Idle failure edge and FM-1. srsRAN's lib/src/rrc/ (Required Reading, Reference Implementations) models the transition function as free of scheduler/PHY assumptions; that lesson is applied directly here — the RRC crate (sim-rrc) has zero dependency on sim-mac's scheduler internals, only on the typed Message contract (P6, ADR-07).

16.3 Deliverable

A UE that has just completed Phase 3's RACH performs the full three-message RRC connection setup (§8.5) and transitions Idle → Connecting → Connected, with a trace showing every transition and its triggering message, and with a T300-expiry rollback path exercised by a deliberately delayed ConnectionSetup.

16.4 Acceptance Criteria

  • RRC connection setup latency (simulated) < 50 ms at nominal load (M5, matches §4).
  • Connection-setup success rate ≥ 99.5% across 100,000 attempts at nominal RACH-success precondition.
  • Exactly 3 messages per successful setup (ConnectionRequest, ConnectionSetup, ConnectionSetupComplete) — any deviation fails the fixture.
  • Zero I1 violations (two simultaneous RRC states for one UE) across a 1,000,000-UE-event stress fixture.
  • T300 expiry correctly rolls back 100% of deliberately-delayed setups to Idle within one configured timer period.

16.5 Conformance Fixtures

  • rrc_connection_setup_success.json — golden 3-message trace for a clean setup.
  • rrc_t300_expiry_rollback.json — delayed ConnectionSetup, asserts rollback to Idle.
  • rrc_reestablishment_after_rlf.json — radio-link failure mid-Connected, asserts re-establishment sequence and FM-1 telemetry.
  • rrc_state_invariant_stress.json — 1,000,000 concurrent transitions, asserts zero I1 violations.

16.6 Pitfalls

  • Double-transition race — manifestation: a UE briefly reports two RRC states in trace output; root cause: the transition function mutates state before validating the precondition, so a re-entrant call during dispatch overwrites a not-yet-committed transition; debug method: replay under sim-replay with per-transition tracing at max verbosity; signal: rrc_state_gauge momentarily reports an invalid enum discriminant; recovery: halt and treat as an I1 violation per §7's methodology.
  • T300 timer ownership leak — manifestation: a UE stuck in Connecting indefinitely; root cause: the T300 timer was scheduled but never registered with the per-UE timer-wheel ownership registry (I9); debug method: query orphaned_timer_count; signal: nonzero orphaned_timer_count with no corresponding rollback event; recovery: forced rollback to Idle plus a regression fixture.
  • Piggyback payload leakage — manifestation: RRC logic branches on NAS message content; root cause: a developer inspected the piggybacked Attach Request instead of treating it as opaque, violating P6; debug method: ownership/dependency lint in CI (ADR-08's sibling check) flags the cross-layer read; signal: CI lint failure, not a runtime symptom; recovery: refactor to pass the NAS PDU as an opaque Bytes-like type.
  • Re-establishment vs fresh-setup confusion — manifestation: a re-established connection is indistinguishable from a fresh one in metrics; root cause: FM-1's re-establishment path reuses the setup transition without a distinguishing trigger tag; debug method: inspect sim-tracing span attributes for the trigger field; signal: handover_outcome_histogram- adjacent metrics undercount RLF events; recovery: tag the trigger explicitly at emission.

16.7 Performance Concerns

The transition-function match is on the per-event hot path for every RRC-bearing event; keeping RrcMessage variants small and avoiding heap allocation in the common-case branches matters at 100,000-UE scale (§4). T300 timers add one timer-wheel entry per in-flight setup; at high attach concurrency (Phase 5 onward) this must not become the dominant timer-wheel occupant relative to other procedures' timers.

16.8 Edge Cases

A ConnectionSetup that arrives after T300 has already fired (late message, must be discarded, not processed into a stale Connecting state); simultaneous RRC release and a just-arrived ConnectionSetupComplete racing on the same UE; a UE that RACHes successfully but whose ConnectionRequest is lost in transport (exercises T300 with zero eNodeB-side state, distinct from the delayed-response case).

16.9 Failure Analysis

A silently-dropped ConnectionSetup (rather than an explicit rejection) is the highest-risk Phase 4 defect: it violates P2's exhaustiveness guarantee and manifests only as a T300 timeout that looks identical to genuine radio loss, masking a real code defect behind an expected-looking failure mode. Detection is the CI ownership lint (structural) plus a targeted fixture that asserts every reachable state emits a defined outcome for every message in RrcMessage (rrc_state_invariant_stress.json); recovery is closing the missing match arm and adding the specific message/state pair as a permanent regression case.

16.10 Operational Notes

Emit RRC state-transition spans with the triggering message and elapsed time in T300 from this phase onward (P12); rrc_state_gauge and setup-success-rate become permanent dashboard metrics (§26). The handover-failure-debug runbook's initial triage step (distinguishing RLF from a genuine handover failure) depends on the FM-1 trigger tagging established here.

17. Phase 5 — NAS Attach / Registration

17.1 Objectives

Implement the LTE attach procedure of §8.6 end-to-end at the NAS layer: the 11-message sequence from RRC-carried Attach Request through Attach Complete, including the EmmState transition function (Deregistered→Registering→Authenticating→Registered), building on Phase 4's RRC connection.

17.2 Detailed Implementation Steps

TS 24.301 (NAS protocol for EPS, Required Reading) governs the message set and ordering; §8.6's 11-step table is the exact sequence the conformance fixtures assert. The MME's ue_contexts table (§11 Core Schema) tracks EmmState per UE, following the same exhaustive-match discipline as RRC (P2, ADR-08) — an Attach Request received while a UE is already Registered is a defined rejection, not a silent re-processing. Identity handling follows ADR-14 (opaque IMSI/GUTI tokens): a fresh attach allocates a GUTI from the MME's identity table, and I8 (GUTI uniqueness within a core-network instance) is asserted on allocation, catching a collision at the moment it would occur rather than downstream in paging (Phase 8). The Authentication Request/Response pair (steps 4–5) and Security Mode Command/Complete pair (steps 6–7) are stubbed as pass-through in this phase — Phase 6 fills in EPS-AKA's actual vector generation and key derivation, so I3 (security context precedes protected traffic) is only fully enforceable once Phase 6 lands; this phase asserts the message order is correct (P13) without yet asserting the security payload's cryptographic correctness. Create Session Request/Response (steps 8–9) toward SGW/PGW are likewise stubbed pass-through, deferred to Phase 7's real bearer allocation.

17.3 Deliverable

A UE with an active RRC connection (Phase 4) completes the full 11-message attach sequence of §8.6 and reaches EmmState::Registered with an allocated GUTI, observable in a call-flow trace matching the §8.6 message order exactly.

17.4 Acceptance Criteria

  • Attach procedure latency (simulated) < 300 ms at nominal load (M4, matches §4).
  • Exactly 11 NAS/RRC messages per successful attach (M8, matches §4's signaling-load target from TS 24.301/36.331).
  • Zero I8 violations (GUTI collision) across a 100,000-UE fixture with concurrent attaches.
  • Attach rejected (not silently dropped) for 100% of malformed or out-of-state Attach Request fixtures.

17.5 Conformance Fixtures

  • attach_full_sequence_success.json — golden 11-message trace matching §8.6.
  • attach_guti_uniqueness_stress.json — 100,000 concurrent attaches, asserts zero I8 violations.
  • attach_reject_already_registered.json — Attach Request from an already-Registered UE, asserts defined rejection.
  • attach_malformed_ie_reject.json — malformed information element, asserts parser rejection without panic.

17.6 Pitfalls

  • GUTI reuse across concurrent attaches — manifestation: two UEs briefly share a GUTI in trace output; root cause: the identity table's allocation check races with an in-flight deallocation from a just-completed detach; debug method: replay under sim-replay with identity-table tracing; signal: nonzero guti_collision_count; recovery: reallocate per I8's defined recovery and add the interleaving as a regression fixture.
  • EmmState skip on retransmitted Attach Request — manifestation: a UE appears to re-attach from Registered without a detach; root cause: a retransmitted (duplicated in transport) Attach Request is processed as a fresh attempt rather than recognized as a duplicate; debug method: inspect the NAS sequence-number/transaction-ID field in the trace; signal: attach-success-rate metric double-counts; recovery: dedupe on NAS transaction ID before EmmState transition.
  • Stubbed-security-phase false confidence — manifestation: attach fixtures pass in Phase 5 despite no real AKA logic existing; root cause: steps 4–7 are intentionally pass-through stubs (§17.2) and the fixture only checks message order, not security-context validity; debug method: cross-check against I3's assertion, which is not yet wired to this phase's code path; signal: none — this is a documentation risk, not a runtime one; recovery: Phase 6's acceptance criteria explicitly re-run attach_full_sequence_success.json with real AKA wired in to close the gap.
  • Core-session stub masking bearer defects — manifestation: attach succeeds but the default bearer is silently absent; root cause: Create Session Request/Response stubs (steps 8–9) always report success in this phase; debug method: Phase 7's bearer-existence assertion (I2) will catch this once wired; signal: none in Phase 5 alone; recovery: treat as a known, tracked stub boundary, not a defect, until Phase 7.

17.7 Performance Concerns

The MME's ue_contexts HashMap is on the attach hot path at 100,000-UE scale; keying by UeId (a u64) rather than Imsi (a String) avoids string-hashing overhead per lookup. Identity-table allocation must not scan the full table per allocation as UE count grows — a free-list or generation counter keeps allocation O(1).

17.8 Edge Cases

An Attach Request for a UE with no HSS-provisioned subscriber record (reject, not panic); a UE that disconnects (RRC release) mid-attach before Attach Complete; two Attach Requests from the same IMSI arriving out of order at the MME.

17.9 Failure Analysis

An identity-allocation race under concurrent attach load (I8) is the highest-severity Phase 5 defect class because it corrupts the MME's ability to address the UE for every subsequent procedure — paging (Phase 8), handover path-switch (Phase 9), and TAU all depend on GUTI correctness. Detection is the guti_collision_count telemetry; recovery is reallocation per I8; forensics is the attach-sequence trace bisected under sim-replay to the exact interleaving that produced the collision, captured as a permanent fixture.

17.10 Operational Notes

Attach success rate and attach-latency percentiles become permanent dashboard metrics from this phase onward (§26); the aka-failure-investigation runbook's precondition-check step (is this an attach-sequence defect or an AKA defect) depends on this phase's message-order fixtures being independently green before Phase 6 is blamed.

18. Phase 6 — EPS-AKA / 5G-AKA Authentication and the Key Hierarchy

18.1 Objectives

Implement §8.7's EPS-AKA sequence and §8.8's key-hierarchy derivation with symbolic keys (ADR-10), replacing Phase 5's authentication/security-mode stubs with real vector generation, RES/XRES comparison, and KeNB derivation; shape the extension to 5G-AKA and the 5G key hierarchy for Phase 11 reuse.

18.2 Detailed Implementation Steps

TS 33.401 governs EPS-AKA (§8.7); the HSS generates an authentication vector (RAND, AUTN, XRES, KASME) symbolically per ADR-10 — KeyToken values are opaque u128s, never real cryptographic output, because protocol-level correctness does not require cryptographic strength (P1). MME→UE carries RAND/AUTN, UE→MME returns RES per §8.7 steps 3–5; the MME's RES==XRES comparison gates I3 (security context precedes protected traffic) — a mismatch triggers FM-3 and either a re-run or a release, never a silent accept (P8). §8.8's key-hierarchy table drives derivation: K→CK/IK→KASME→KeNB→KRRCint/KRRCenc/KUPenc, each a pure symbolic function of its parent KeyToken plus a context value (the NAS uplink count for KeNB), never randomness independent of the seed (ADR-17, I11). Security Mode Command/Complete (Phase 5 steps 6–7) now carry real algorithm-selection fields; a downgrade attempt — choosing a weaker algorithm than advertised — is a defined rejection path (P8), the primary defense against T3. Basin, Dreier, Hirschi, Radomirovic, Sasse & Stettler's formal analysis of 5G-AKA (Required Reading) informs the 5G key-hierarchy extension (K→CK/IK→KAUSF→KSEAF→KAMF→KgNB, TS 33.501) built here in symbolic form for Phase 11, and directly motivates T2 (replay of authentication vectors) and T7 (key desync) in §24 — a freshness/sequence field on the authentication vector is this phase's primary defense against T2.

18.3 Deliverable

A UE completes Phase 5's attach with real EPS-AKA wired in: the HSS generates a vector, the MME forwards RAND/AUTN, the UE returns RES, the MME validates against XRES, and KASME/KeNB are derived at both ends before Security Mode Command/Complete completes — I3 is now enforceable end-to-end. A negative fixture demonstrates a RES/XRES mismatch triggering FM-3.

18.4 Acceptance Criteria

  • AKA round trip (vector request through KeNB derivation) adds < 20 ms simulated latency to the attach sequence, within M4's 300 ms attach budget.
  • RES/XRES mismatch correctly triggers FM-3 in 100% of deliberately-mismatched fixtures, never a silent accept.
  • Zero I3 violations (protected message before security context) across a 100,000-attach fixture.
  • Zero I14 violations (dual ACTIVE security contexts for one UE) across a re-authentication stress fixture.
  • Algorithm-downgrade attempts rejected in 100% of fixtures (T3 mitigation).

18.5 Conformance Fixtures

  • eps_aka_success.json — golden vector-request-through-KeNB-derivation trace matching §8.7/§8.8.
  • eps_aka_res_mismatch.json — RES != XRES, asserts FM-3 and no security-context establishment.
  • key_hierarchy_derivation_golden.json — golden symbolic KeyToken chain for a fixed seed.
  • security_downgrade_reject.json — asserts algorithm-downgrade rejection (T3).
  • dual_security_context_stress.json — re-authentication race, asserts zero I14 violations.

18.6 Pitfalls

  • Premature protected-message dispatch — manifestation: a protected NAS/RRC message observed before Security Mode Complete; root cause: the I3 dispatch guard checks Option<SecurityContext> presence but not its pending-vs-ACTIVE sub-state, so a mid-derivation context reads as present; debug method: assert on lifecycle sub-state, not mere presence; signal: protected_before_aka_count nonzero; recovery: reject and re-run Security Mode Command.
  • KeNB re-derivation on NAS-count rollover — manifestation: KeNB silently changes value without a triggering procedure; root cause: the NAS uplink count feeding KeNB derivation wrapped without a defined rollover edge; debug method: compare key_hierarchy_derivation_golden.json across a long-run fixture; signal: replay-hash mismatch (I11); recovery: define and fixture the rollover edge before Phase 7 depends on a stable KeNB.
  • Dual active context on retry storm — manifestation: two ACTIVE security contexts coexist momentarily; root cause: a retransmitted Authentication Request triggers a second authentication racing the original's completion; debug method: HSS/UDM + MME/AMF context-table trace; signal: dual_security_context_count; recovery: invalidate the stale context per I14.
  • Symbolic-key confusion with real crypto — manifestation: a reviewer assumes KeyToken values carry real security strength; root cause: ADR-10's rationale is easy to forget once the chain "looks like" real AKA; debug method: code-review checklist, not a runtime check; signal: none automated; recovery: keep KeyToken(u128) unexported outside sim-nas/sim-rrc/sim-epc, making misuse a compile error.
  • Downgrade check ordering — manifestation: a downgrade is accepted before rejection logic runs; root cause: algorithm-selection validation placed after KeNB derivation rather than before, so weak-algorithm keys are already derived when the rejection fires; debug method: trace-order inspection of security_downgrade_reject.json; signal: derivation events precede the rejection event; recovery: reorder validation ahead of derivation (P8).

18.7 Performance Concerns

HSS vector generation is O(1) symbolic, cheap; the key-derivation chain is a fixed-depth pure function, negligible per-attach cost; the dominant cost remains the transport-hop latency of the multi-message AKA/security round trip, not compute — matching §18.4's latency budget rather than a throughput concern.

18.8 Edge Cases

NAS uplink count exactly at its rollover boundary; a UE that retries Authentication Response after the MME has already timed out the original attempt; an HSS with no provisioned key material for a given IMSI (reject, not panic); simultaneous authentication attempts for the same UE arising from a retried attach.

18.9 Failure Analysis

A RES/XRES comparison is not itself timing-sensitive at this fidelity (no side-channel is modeled, per §1 non-goals), but a comparison that accepts on partial match is a critical defect masking FM-3 entirely. Detection is the negative fixture eps_aka_res_mismatch.json, which must fail loudly the moment a mismatch is ever accepted; forensics is the AKA-sequence trace showing the exact RES/XRES pair that should have failed.

18.10 Operational Notes

AKA success/failure counts and key-derivation-chain integrity checks become permanent metrics from this phase onward; the aka-failure-investigation runbook (§26) is the primary consumer of eps_aka_res_mismatch-class telemetry, and its first triage step is distinguishing an AKA defect from Phase 5's attach-sequence stub boundary (§17.6).

21. Phase 9 — Handover (X2/Xn then S1/N2) with Data Forwarding

21.1 Objectives

Implement §8.10's X2 handover sequence (9-step) with PDCP-level data forwarding, extend to S1 handover (MME-mediated, no X2 available), and shape the abstraction for Phase 11's Xn/N2 reuse; enforce I5 (a handover completes served-by-target or rolls back, never leaves the UE unserved).

21.2 Detailed Implementation Steps

TS 36.300 governs the X2 handover call flow (§8.10); a Measurement Report triggers on degrading source-cell SINR relative to a target-cell threshold, fed by Phase 2's channel model through Phase 8's mobility tick. HandoverContext{ue, source, target, state} (§11) tracks Preparing→Forwarding→Completing→RolledBack as an explicit state machine (ADR-08), mirroring RRC's own exhaustiveness discipline (P2). Handover Request/Acknowledge (X2, steps 2–3) is direct eNodeB-to-eNodeB per ADR-09's logical-element modeling; data forwarding (step 5) moves buffered PDCP PDUs from source to target, and I6 (RLC/PDCP sequence numbers monotonic, reordering bounded) governs the target's reassembly of forwarded-plus-new PDUs — a race here is FM-8. Path Switch Request/Acknowledge (steps 7–8) toward the MME updates the SGW's downlink path, and UE Context Release (step 9) tears down the source-side context only after the path switch confirms, never before (P8) — a HandoverContext that never reaches Completing rolls back to source per I5, never leaving the UE double-served or unserved. S1 handover substitutes MME-mediated Handover Required/Command signaling between steps 2–4 in place of direct X2 messaging (§8.10's note), reusing the same HandoverContext state machine with only the transport path differing. This phase's abstraction is deliberately shaped so Phase 11's Xn (5G-to-5G) and N2 (5G-to-4G interworking) handover paths substitute AMF/UPF for MME/SGW without forking the state machine (P14). Full distributed multi-host simulation federation for handover across simulator instances is out of scope and deferred (PhaseDeferred("§21 Handover — distributed multi-host simulation federation")).

21.3 Deliverable

A UE in RRC-Connected on a source cell with degrading SINR triggers a Measurement Report, completes the 9-step X2 handover sequence, and ends RRC-Connected on the target cell with its bearer context intact (I5, matching §8.15's worked example) and zero data loss beyond the configured PDCP reordering window (I6). A negative fixture demonstrates target-cell admission rejection correctly rolling the UE back to the source cell.

21.4 Acceptance Criteria

  • Handover interruption time (simulated), LTE X2, < 50 ms (M6, matches §4).
  • 8–10 signaling messages per successful X2 handover (M10, matches §4/TS 36.300).
  • Zero I5 violations (UE left unserved) across a 100,000-handover stress fixture, including the rejection-rollback path.
  • Zero data loss beyond the configured reordering window during forwarding, verified against I6.
  • Rejection-triggered rollback completes within one configured admission-response timeout in 100% of fixtures.

21.5 Conformance Fixtures

  • x2_handover_success.json — golden 9-message trace matching §8.10.
  • x2_handover_admission_reject_rollback.json — target rejects, asserts I5 rollback (FM-2).
  • s1_handover_mme_mediated.json — golden S1 handover trace with MME-mediated signaling substituted for direct X2.
  • handover_data_forwarding_reorder.json — asserts I6-bounded reassembly of forwarded PDUs.

21.6 Pitfalls

  • Path switch race with data forwarding — manifestation: user-plane packets arrive at the source cell after the SGW has already switched the downlink path to the target; root cause: Path Switch Request/Acknowledge (steps 7–8) is not gated on forwarding-buffer drain confirmation; debug method: trace forwarding-buffer state against the path-switch acknowledge timestamp; signal: dropped-packet count spikes during handover; recovery: gate path switch on forwarding drain, add as a regression fixture.
  • UE Context Release before path switch confirms — manifestation: the source-side context disappears while the UE is still mid-handover; root cause: step 9 fires on a fixed timer rather than being gated on step 8's acknowledgment, violating P8's ordering discipline; debug method: HandoverContext state-trace inspection; signal: handover_outcome_histogram records a rollback with no source context to roll back to; recovery: gate release strictly on path-switch acknowledgment.
  • Reordering-window overflow during forwarding — manifestation: forwarded PDCP PDUs are discarded even though they arrived within a reasonable interval; root cause: the target cell's reorder buffer window is sized for steady-state traffic, not the burst of forwarded-plus-new PDUs at handover; debug method: reorder_window_violation_count spikes specifically during handover windows, not steady state; signal: this metric; recovery: size the reorder window with a handover-specific burst allowance (I6, FM-8).
  • S1-vs-X2 code-path divergence — manifestation: S1 and X2 handover produce structurally different HandoverContext traces even though both should end in the same terminal states; root cause: the S1 substitution was implemented as a separate function rather than the same state machine with a different transport binding, violating this phase's reuse intent; debug method: diff x2_handover_success.json and s1_handover_mme_mediated.json terminal-state shape; signal: fixture divergence in HandoverState sequencing, not just message content; recovery: refactor to share the HandoverContext state machine, varying only the transport.

21.7 Performance Concerns

Handover events cluster at cell edges under realistic mobility, so the measurement-report-to-trigger path must avoid an O(cells) neighbor scan per report — index each cell's neighbor list once at topology load (Phase 2) and reuse it rather than recomputing per event.

21.8 Edge Cases

A UE that triggers a second Measurement Report while a handover is already Preparing (must not spawn a concurrent HandoverContext for the same UE, P5); a target cell at scheduler capacity (I10) rejecting admission; a UE crossing back to the source cell immediately after completing handover to the target (ping-pong, bounded by a hysteresis/backoff policy).

21.9 Failure Analysis

FM-2 (handover failure) is the highest-visibility Phase 9 defect class because it is user-facing (interruption time) even when correctly rolled back. Detection is the admission-rejection response or the Acknowledge-timeout path; recovery is rollback to source per I5; forensics is the HandoverContext state trace bisected under sim-replay to distinguish a genuine admission failure from a code defect that only resembles one.

21.10 Operational Notes

Handover success rate, interruption-time percentiles, and rollback rate become permanent dashboard metrics (§26); the handover-failure-debug runbook's core workflow — distinguish RLF (FM-1, Phase 4) from true handover failure (FM-2) — depends on the trigger tagging established in both phases.

22. Phase 10 — Multi-UE Scenarios, Core-Network Elements and Signaling-Load Metrics

22.1 Objectives

Scale the simulator to many concurrent UEs across many cells, flesh out the core-network elements (MME/SGW/PGW/HSS) as full logical-element state machines rather than per-procedure stubs, and build the signaling-load-metrics model that feeds §30/§34.

22.2 Detailed Implementation Steps

Building on Phases 4–9's per-procedure correctness, this phase drives concurrent multi-UE scenarios at the target scale (100,000 UEs, 2,000 cells, §4) and validates that the discrete-event engine (Phase 0) holds its throughput/queue-depth targets under a real procedure mix, not only Phase 0's synthetic workload. Core-network elements (ADR-09's logical-element modeling) gain explicit per-element capacity limits and load metrics — MME attach-processing rate, SGW/PGW session-table size, HSS lookup latency — informed by Law's Simulation Modeling and Analysis (Required Reading) chapters on verification, validation, and output analysis: a multi-UE scenario's aggregate metrics are trustworthy only if the individually-verified single-UE procedures of Phases 4–9 remain correct under concurrency, so this phase's acceptance criteria explicitly re-run every prior phase's negative fixtures at scale. Signaling-load metrics (ADR-15, in-process histogram aggregation) are computed per cell per procedure type (attach, handover, paging) and checked against §4's per-procedure message-count targets (M8, M10) at aggregate scale, feeding §34's back-of-envelope model. Horizontal scenario sharding across a Kubernetes-orchestrated fleet of simulator instances is out of scope and deferred (PhaseDeferred("§22 Multi-UE Scenarios — Kubernetes-orchestrated horizontal scenario sharding")) — this phase targets single-host scale per §4, not distributed scale-out.

22.3 Deliverable

A 100,000-UE, 2,000-cell scenario runs for a full 24-simulated-hour horizon, mixing attach, handover, paging, and TAU procedures at realistic concurrency, sustaining §4's throughput/latency targets, and producing per-cell signaling-load metrics plus a deterministic replay hash.

22.4 Acceptance Criteria

  • Sustained event throughput ≥ 5,000,000 events/second at full 100,000-UE, 2,000-cell scale (M3).
  • Simulated-to-wall-clock ratio ≥ 100:1 at 10,000 UEs (M12, matches §4).
  • Zero regressions in any Phase 4–9 negative fixture re-run at scale — I1, I2, I3, I5, I6, I8, I12, I13, I14 all zero-violation across the full run.
  • Per-cell signaling load reported for 100% of cells with nonzero UE population.
  • Replay-hash identical across 3 repeated full-scale runs from the same seed (I11, M11 = 100%).

22.5 Conformance Fixtures

  • multi_ue_100k_mixed_procedures.json — golden aggregate-metrics trace for the full-scale mixed-procedure scenario.
  • signaling_load_per_cell_report.json — asserts per-cell signaling-load computation against a golden reference.
  • phase4_9_regression_at_scale.json — re-runs every prior phase's negative fixtures under full concurrency.

22.6 Pitfalls

  • Concurrency masking a per-UE invariant bug — manifestation: an invariant violation (e.g. I1) never appears at low UE count but appears above a concurrency threshold; root cause: a shared-state bug violating P5 only manifests under contention; debug method: bisect the UE-count threshold at which the violation first appears under sim-replay; signal: an I#-violation counter nonzero only above a specific scale; recovery: fix the ownership violation and add that concurrency level as a permanent regression fixture.
  • Core-element capacity limit silently unenforced — manifestation: MME/SGW/PGW/HSS accept unbounded load with no rejection; root cause: the per-element capacity limits (§22.2) were added to metrics but never wired into an actual admission/rejection check, violating P11's backpressure discipline; debug method: load a scenario deliberately exceeding a configured element's capacity; signal: no rejection observed despite exceeding configured capacity; recovery: wire the capacity check as an explicit bounded-queue/reject path.
  • Signaling-load double-counting across procedures — manifestation: aggregate signaling load exceeds the sum of per-procedure targets; root cause: a message shared across two procedure classifications (e.g. an RRC message that is both connection-setup and paging-response) is counted in both buckets; debug method: cross-check signaling_load_per_cell_report.json totals against a per-message single-classification invariant; signal: sum mismatch; recovery: classify each message to exactly one procedure bucket.
  • Replay-hash divergence only at full scale — manifestation: the replay hash matches at low UE count but diverges at 100,000 UEs; root cause: an unseeded iteration order (e.g. a HashMap walked during metrics aggregation) produces visible divergence only once enough entries exist to reorder unpredictably; debug method: bisect scale under sim-replay per §12.9's methodology; signal: replay_hash_mismatch_count nonzero only above a threshold; recovery: replace the unseeded iteration with a deterministic order (sorted keys or an insertion-order structure).

22.7 Performance Concerns

At 100,000 UEs the event queue (Phase 0) must sustain 10,000,000 pending events (M9) without reallocation stalls; per-UE state must hold under 4 KB (M13) to keep total footprint bounded (§34); metrics aggregation itself must not become a bottleneck — histogram updates are O(1) per event, never a full-population scan per tick.

22.8 Edge Cases

A scenario with wildly uneven cell population (one hotspot cell at capacity, most cells near-empty); a scenario that ramps from 0 to 100,000 UEs within the first simulated hour (attach-storm-adjacent, see FM-7); a 24-simulated-hour run crossing multiple TAU/mobility cycles for every UE.

22.9 Failure Analysis

FM-7 (event-queue starvation) is the primary new failure class introduced at this phase's scale — a burst of same-timestamp events (recall Phase 0's zero-delay-cascade pitfall) compounded across 100,000 UEs can starve the dispatch loop. Detection is dispatch-latency p99 exceeding a configured threshold; recovery is bounding same-timestamp event fan-out per component (P11); forensics is the scheduler-depth trace correlated with the specific procedure mix active at the starvation point.

22.10 Operational Notes

This phase's signaling-load-per-cell metric and per-element capacity metrics become the primary soak-test dashboard (§26, §28); the signaling-storm-reproduction runbook depends on this phase's per-cell load baseline to distinguish an anomalous storm from expected peak load.

23. Phase 11 — The 5G Extension, Call-Flow Conformance and Performance Hardening

23.1 Objectives

Extend the shared LTE abstraction to 5G NR per P14/ADR-04 — gNB, AMF, SMF, UPF, UDM, RRC-Inactive, 5G-AKA/5G key hierarchy, Xn/N2 handover, PDU sessions with 5QI — and close the project with call-flow-conformance hardening and performance hardening against §4's full target set.

23.2 Detailed Implementation Steps

TS 38.300/TS 38.331 (NR RRC/overall description), TS 23.501/TS 23.502 (5G system architecture/procedures), TS 33.501 (5G security), TS 24.501 (5G NAS) govern the extension; every LTE abstraction built in Phases 0–10 is reused, not forked (P14). RrcState::Inactive (reserved in §8.2's table) is activated with a defined RRC Release-with-suspend / Resume Request pair; MmState mirrors EmmState's shape; FiveGCore{amf, smf, upf, udm} (§11) reuses CoreNetwork's single-ownership pattern (P5); the 5G key hierarchy (K→CK/IK→KAUSF→KSEAF→KAMF→KgNB, per §18.2 and Basin, Dreier, Hirschi, Radomirovic, Sasse & Stettler 2018) derives with the same symbolic-KeyToken discipline (ADR-10); PDU-session establishment (§8.9) reuses the bearer-setup state machine with 5QI substituted for QCI (ADR-13); Xn and N2 handover reuse Phase 9's HandoverContext per §21.2's design intent. Call-flow conformance (P13, ADR-20) is hardened project-wide: every fixture from Phases 3–10 is re-verified against its 3GPP sequence as a named CI gate (§28), and differential comparison against ns-3 5G-LENA traces validates the extension specifically. Performance hardening re-validates every §4 target at full 5G-inclusive scale. A full OFDM/waveform-level PHY replacement is deferred (PhaseDeferred("§23 5G Extension — full OFDM/waveform-level PHY replacement")) — the PHY abstraction (ADR-06, Phase 2) is reused unchanged for 5G, per P7.

23.3 Deliverable

A mixed LTE/5G scenario runs UEs attaching to gNBs via RRC-Inactive-aware state transitions, completing 5G-AKA and PDU-session establishment with 5QI classes, undergoing Xn handover between gNBs and N2 interworking handover to/from an eNodeB, with every 3GPP-specified message sequence (LTE and 5G) verified against a named conformance fixture in the same CI run, and every §4 performance target re-validated at full combined scale.

23.4 Acceptance Criteria

  • 100% of Phase 3–10 LTE conformance fixtures remain green unmodified — no regression from the 5G extension (P14's reuse-not-fork discipline).
  • 5G PDU-session establishment latency and Xn handover interruption time (M7, < 30 ms) meet §4's 5G-specific targets.
  • Differential comparison against ns-3 5G-LENA traces matches on message order for 100% of compared procedures (§28 gate).
  • All 24 §4 constraints re-validated at full mixed LTE/5G scale within their stated targets.
  • Zero new I#-violations introduced by the 5G extension across a mixed-scenario stress fixture.

23.5 Conformance Fixtures

  • fivegc_registration_success.json — golden 5G registration (NAS/RRC) trace, TS 24.501/38.331.
  • xn_handover_success.json — golden Xn handover trace, gNB-to-gNB.
  • n2_interworking_handover.json — golden N2 handover trace, 5G-to-4G.
  • pdu_session_5qi_setup.json — golden PDU-session establishment trace with 5QI.
  • differential_5g_lena_comparison.json — message-order diff against an ns-3 5G-LENA reference trace.

23.6 Pitfalls

  • RRC-Inactive resume treated as a fresh setup — manifestation: Resume Request produces the same message count as a full connection setup; root cause: Inactive→Connected calls the fresh-setup path instead of its own lighter resume path; debug method: message-count diff vs rrc_connection_setup_success.json; signal: identical counts where 5G implies fewer; recovery: implement the resume path distinctly per TS 38.331.
  • 5G key hierarchy silently reusing LTE KeyToken values — manifestation: KAMF/KgNB are bit-identical to an LTE UE's KASME/KeNB under the same seed; root cause: the 5G derivation was copy-pasted from Phase 6 without changing its context inputs; debug method: compare key_hierarchy_derivation_golden.json against the 5G equivalent; signal: identical values across paths that should differ; recovery: parameterize derivation context per hierarchy.
  • N2 interworking handover skipping core-selection logic — manifestation: N2 handover always targets the same core type regardless of the target cell's RAT; root cause: the reused HandoverContext (§21.2) lacks the core-type decision N2 requires; debug method: n2_interworking_handover.json asserts correct AMF-to-MME transition; signal: fixture target-core mismatch; recovery: add explicit core-type selection to the extension.
  • Differential comparison masked by abstraction-level mismatch — manifestation: the 5G-LENA diff reports spurious mismatches; root cause: 5G-LENA includes PHY detail this simulator abstracts (ADR-06/P7), so a full-trace diff flags PHY-only differences; debug method: restrict comparison to RRC/NAS message order; signal: false-positive mismatch count; recovery: scope the comparator to layers this simulator claims fidelity for (P1).
  • Performance hardening regressing an LTE-only target — manifestation: M4 attach latency regresses though no LTE code changed; root cause: shared abstractions carry added 5G event-kind variants, inflating per-event dispatch cost (§16.7 recurring); debug method: per-event-kind dispatch-cost profiling; signal: M3/M4 regression in re-validation; recovery: keep EventKind/Message variants small as 5G extension adds more.

23.7 Performance Concerns

Every shared enum (EventKind, Message, the RrcState/MmState pairing) grows with 5G variants; per §16.7's and §23.6's regression pitfall, variant growth must not inflate the common-case dispatch cost for LTE-only events — boxing large 5G-specific payloads behind an indirection, rather than inlining them into the shared enum, keeps the hot path's cache footprint stable.

23.8 Edge Cases

A UE that performs N2 interworking handover mid-PDU-session-establishment (session context must transfer, not restart); an RRC-Inactive UE that is paged (5G paging targets Inactive as well as Idle, unlike LTE); a mixed scenario where an LTE-only cell has zero 5G-capable neighbors (Xn/N2 handover candidates must correctly exclude it).

23.9 Failure Analysis

A conformance regression introduced by the 5G extension into a previously-green LTE fixture (§23.4's first criterion) is the highest-severity Phase 11 defect, violating P14's reuse-not-fork promise. Detection is the Phase 3–10 fixture suite re-run in the same CI job as the new 5G fixtures (ADR-20, ADR-22); recovery is bisecting the shared-abstraction change that caused it, never an LTE-specific special case that would itself violate P14.

23.10 Operational Notes

This phase's differential-comparison gate against ns-3 5G-LENA becomes a permanent CI job (§28, §29); the project's full §4 constraint table is re-published as the final operational-readiness baseline (§26) at the close of Phase 11, and every subsequent change to any crate is measured against it.

Alerting Philosophy

Alert on rate-of-change and threshold breach against the §4/§30 targets, not on individual invariant violations — those halt the run immediately per §7's methodology and are a hard stop, not an alerting concern. Alerting exists for degrading trends across scenario runs (e.g. handover-success-rate trending down across CI runs), not per-event noise.

SLOs

  • Attach success rate ≥ 99.5% per soak run.
  • Handover success rate ≥ 99% per soak run.
  • Zero invariant violations per CI run — a hard gate, not a percentage SLO.
  • Replay-hash determinism 100% (I11) — any miss is a release blocker, never a tolerated defect rate.

Incident Response

An invariant violation halts the run (§7) and is treated as a release-blocking defect, not a production incident to triage — there is no production traffic, only scenario runs. "Incident response" here means: reproduce under sim-replay, bisect, fix, add a regression fixture, re-run the full conformance suite (§28) before closing.

Runbooks (docs/runbooks/)

  • call-flow-mismatch-triage.md — first response to any §28 conformance-gate failure; isolates which procedure's trace diverges from its 3GPP-specified sequence.
  • handover-failure-debug.md — distinguishes FM-1 (RLF) from FM-2 (true handover failure) using the trigger tagging established in Phase 4/Phase 9.
  • non-determinism-hunt.md — bisection procedure for FM-10, starting from the hidden-nondeterminism pitfall classes catalogued in §12.6/§22.6.
  • signaling-storm-reproduction.md — reproduces T5/FM-7-adjacent signaling-storm conditions from a captured per-cell load baseline (§22.10).
  • aka-failure-investigation.md — triages FM-3, starting by distinguishing Phase 5's intentional stub boundary (§17.6) from a genuine Phase 6 AKA defect.

Backup / Restore of Scenarios

Scenario files (TOML/RON, ADR-16) plus their seed are the unit of backup — a scenario and its seed fully reconstruct a run (I11), so "backup" is committing the scenario file and seed to version control, and "restore" is sim-replay from that seed. Event-trace snapshots (sim-persistence) are periodically checkpointed during long soak runs so a crash mid-run resumes from the last checkpoint rather than replaying from time zero, meeting §4's <30 second RTO.

Deployment Topology

Single-host batch execution (§1 Deployment Model) — no live service topology. CI runs the full conformance suite (§28) per commit (ADR-22); soak runs execute on dedicated benchmark hosts (§30) outside the per-commit CI loop due to their duration.

Canary / Rollback / Migration

"Canary" is running the full §28 conformance suite plus one soak run on a release-candidate build before tagging a release (§29); "rollback" is reverting to the last tagged release's pinned Cargo.lock (ADR-24), since there is no live deployment to roll back; "migration" applies to scenario-format and trace-format versions (§27) — a version field on each file determines which parser/reader handles it, with prior versions supported per §27's deprecation policy.

27. Compatibility & Versioning

LTE-vs-5G Feature Parity and the Shared Abstraction

Per P14/ADR-04, every abstraction (Event, Message, state machine) is designed once and reused for 5G, not forked. Parity tracking: RRC (Idle/Connected shared, Inactive is 5G-only), NAS/MM (state shapes mirror each other), bearer/PDU-session (QCI/5QI substitution only), handover (HandoverContext shared, Xn/N2 substitute transport per §21.2/§23.2), AKA/key hierarchy (structurally identical chain, different derivation inputs per TS 33.401 vs TS 33.501). A parity table is maintained under docs/ and re-validated at every Phase-11-and- later release (§23.4's regression discipline).

3GPP-Release Tracking

Each TS reference in §5 is pinned to a specific release at blueprint-lock time; a 3GPP release bump is evaluated for message-sequence impact before any fixture is updated — fixtures never silently drift with an upstream spec change.

Scenario-Format Versioning

Scenario files (ADR-16) carry an explicit version field; sim-config supports the current version plus at least one prior minor version during the deprecation window below, and rejects — never silently reinterprets — an unrecognized version.

Trace-Format Versioning

Call-flow traces (sim-tracing) carry a version field independent of the scenario format's version; a trace-format bump requires updating sim-conformance's fixture readers before any new fixture using the new format is accepted into CI (ADR-22).

Message-Encoding Versioning

Internal Message/NasMessage/RrcMessage enum variants are additive-only within a minor version (ADR-23); a breaking variant change (removal or semantic change of an existing variant) requires a major workspace version bump.

API Stability

sim-core, sim-events, sim-clock are the stability-anchor crates (most depended-upon, per §10's repository layout); their public APIs follow the same additive-only discipline as message encodings until a documented major-version boundary.

Migration

A scenario or trace file below the currently-supported version range is migrated via a one-time sim-cli conversion command, never auto-upgraded silently mid-run — silently rewriting input state mid-run would break replay-hash trust in the original file (I11).

Deprecation

A deprecated scenario/trace-format version is supported for exactly one subsequent minor release after its replacement ships, then rejected with a pointer to the migration command — mirroring ADR-23's coherent-workspace policy rather than independent per-crate deprecation timelines.

SemVer

The workspace releases as a single SemVer unit (ADR-23) through Phase 11: patch = fixture/documentation/bugfix, minor = additive message/scenario-format variants, major = any breaking change to Event, Message, scenario format, or trace format.

28. Testing & Verification Strategy

Unit Testing

Per-layer transition functions (NAS/RRC/PDCP/RLC/MAC) unit-tested exhaustively against every state/message pair (P2); key-derivation functions (§18) unit-tested against golden symbolic-token chains.

Integration Testing

Cross-layer message flow (Phase 1) and cross-node procedures (attach, AKA, bearer setup, handover, paging) integration-tested end-to-end per each phase's §N.5 fixtures.

Property-Based Testing

  • Every UE is in exactly one RRC state at all times (I1) — property-tested via randomized transition sequences asserting the invariant holds after every step.
  • The event queue processes events in timestamp order (I4) — property-tested via randomized event insertion, asserting non-decreasing pop order.
  • A completed handover leaves the UE served by exactly one cell (I5) — property-tested via randomized handover-trigger sequences including deliberate admission rejections.
  • The security context exists before any protected message is exchanged (I3) — property-tested via randomized message-ordering fuzzing of the pre/post-AKA boundary.
  • Sequence numbers are monotonic within the reordering window (I6) — property-tested via randomized PDU delivery orderings including forwarding-burst scenarios (§21.6).

Call-Flow Conformance (CI Gate)

The named CI gate (ADR-20, ADR-22): every procedure's message sequence is asserted against its 3GPP-specified sequence (§8's tables) on every commit. Phase-specific fixtures (§16.5 through §23.5) are the fixture inventory; §23.4 requires 100% of Phase 3–10 fixtures green alongside new 5G fixtures in the same CI run — a fixture regression anywhere blocks merge.

Differential Testing

Message-order comparison against ns-3 LTE (Phase 0's scheduler-design lesson) and 5G-LENA (Phase 11, differential_5g_lena_comparison.json) traces where feasible; against srsRAN/OAI reference behavior for RRC/PDCP/RLC/MAC layer separation (Required Reading, applied Phase 1/Phase 4/Phase 9); against Open5GS/free5GC core call-flow shape (Phase 7/Phase 10/Phase 11) where documented traces exist.

Fuzzing

NAS/RRC message parsers and the scenario parser (ADR-21) — attach_malformed_ie_reject.json and equivalent per-phase malformed-input fixtures anchor the corpus; T4/T10 in §24 are the threat classes this defends against.

Chaos Testing

Radio-link failures (FM-1), dropped messages (FM-9, via sim-faults), and cell outages mid-procedure are injected against in-flight procedures from every phase, asserting the procedure's defined failure edge (P8) fires rather than an unhandled panic or hang.

Deterministic Replay

Every fixture and every soak run is replayed from its seed and checked for an identical replay hash (I11); non-determinism-hunt.md is the runbook when this fails.

Soak Testing

The Phase 10 100,000-UE, 24-simulated-hour scenario (§22.3) is the primary soak fixture, re-run before every release (§29) to catch FM-7 (event-queue starvation)-class defects that only manifest over long runs.

Fault Injection

sim-faults injects drops, RLF, and handover-admission failures at configurable rates; every phase's negative fixtures (§N.5) are fault-injection scenarios at the single-procedure grain, and §22's phase4_9_regression_at_scale.json is the multi-procedure grain.

Performance-Regression Gating

Every §30 M# target is re-measured in CI on a fixed benchmark workload per commit affecting a perf-sensitive crate (sim-core, sim-events, sim-clock, sim-mac); a regression beyond a configured tolerance blocks merge, tying directly to §4's constraint table.

29. Build & Release Engineering

Reproducible Builds

Pinned toolchain version plus a committed Cargo.lock (ADR-24) — required because replay-hash trust (I11) extends to build reproducibility: a build-dependent codegen difference could otherwise masquerade as a determinism defect.

Artifact Signing

Release binaries and the sim-conformance fixture bundle are signed at release time; signature verification is a precondition for consuming a fixture bundle in an external CI context.

SBOM

A software bill of materials is generated per release, enumerating the 22-crate workspace plus all third-party dependencies pinned in Cargo.lock — supports dependency auditing below.

Release Channels

A single release channel per ADR-23's coherent-workspace policy — no separate stable/beta split during Phases 0–11; a release-candidate tag undergoes the full §28 conformance suite plus one soak run (§26's canary definition) before promotion to a release tag.

CI/CD Topology

Single monorepo pipeline (ADR-22): build, unit, integration, property tests, the call-flow-conformance job (§28), fuzz smoke execution, and (on release-candidate tags only) the soak run and differential-comparison job.

Version Stamping

Every build embeds the workspace SemVer (§27), the git commit hash, and the Cargo.lock hash into the binary's --version output, enabling exact reproduction of any release artifact.

Provenance / Attestation

Build provenance (source commit, toolchain version, build environment) is attested and attached to each release artifact alongside its SBOM and signature.

Dependency Auditing

Cargo.lock dependencies are audited against a known-vulnerability database on every release and on a recurring schedule between releases; an audit finding blocks release promotion until resolved or explicitly waived with a documented rationale.

30. Performance Engineering

Methodology

The discrete-event engine's throughput (M3) is bounded by the binary min-heap's (ADR-03) push/pop cost, O(log n) in queue depth (§31); per-event dispatch cost is dominated by EventKind/Message enum size and any heap allocation in the common-case match arms (§16.7, §23.7's variant-growth pitfall), so keeping these small and boxing large/rare payloads is the primary lever. Per-UE state cost (M13, < 4 KB) is measured directly from ProtocolStack plus identity plus bearer-table memory per UE, checked in CI against a fixed-size assertion. The simulated-to-wall-clock ratio (M12) is measured on the Phase 10 soak workload (§22.3) at 10,000 UEs as the primary benchmark point, and tracked as UE count scales toward the 100,000-UE ceiling (§4). Scaling to many UEs is validated by re-running the same benchmark at 1,000/10,000/100,000 UEs and checking that throughput degrades sub-linearly, not super-linearly, as component-indexed lookups (tracking-area indexing §20.7, neighbor-list indexing §21.7) replace any O(n) scan identified during development. Allocation in the event loop is profiled with a heap-allocation tracker on the benchmark workload; the target is zero per-event heap allocation on the steady-state hot path once the queue and component tables are warmed. Tail latency (p99, p999) of a run's dispatch loop is tracked separately from mean throughput because FM-7 (event-queue starvation) manifests as a tail-latency pathology invisible in a mean-throughput number.

31. Scalability Analysis

  • Events scale with UEs × procedures/UE × mobility rate — each UE contributes a roughly fixed set of procedure-driven events per simulated hour (attach once, periodic TAU, occasional handover, periodic paging-eligible windows), so total event volume is approximately linear in UE count for a fixed scenario mix, matching M1/M3's joint scaling assumption.
  • Event-queue operations are O(log n) per push/pop in queue depth (ADR-03's binary min-heap) — at M9's 10,000,000-event depth ceiling, this bounds per-event dispatch cost even at maximum sustained load.
  • Per-UE state is linear in UE count (M13's < 4 KB budget × UE count = total footprint) — §22.7 validates this holds in practice, not only in the schema's design intent.
  • Signaling load per cell bounds cell density — a cell's attach+handover+paging message rate against a control-plane budget (§34) caps how many UEs a single cell can serve before signaling load, not radio capacity, becomes the binding constraint, a deliberate simplification per ADR-06/P7's abstraction level.
  • Scaling UEs and cells independently: UE count scales event volume; cell count scales topology/neighbor-list size and, via tracking-area indexing (§20.7), paging fan-out cost — the two dimensions are validated separately in Phase 10's benchmark sweep.
  • Parallelizing independent regions: event-target partitions with no cross-partition dependency (e.g. UEs on cells with no shared core-network element) can dispatch concurrently under bounded parallel execution (ADR-17); the ordering constraint that limits this is I4 (non-decreasing timestamp order) combined with I7 (no message processed before its arrival event) — any partition sharing a core-network element (MME/AMF, SGW/UPF) serializes through that element's single-owner state (P5), the practical ceiling on parallelism, not queue mechanics.
  • Practical scenario-size ceiling: bounded jointly by §4's 100,000-UE/2,000-cell/ 10,000,000-event-queue-depth targets, whichever binds first for a given scenario's procedure mix; the primary levers to push the ceiling further are (a) sharding cells across simulator instances (deferred, §22.2's Kubernetes-sharding item) and (b) reducing per-event allocation to raise the sustainable throughput ceiling (§30's methodology).

32. Mental Models & First Principles

  • MM1 — Insight: a cellular network is a giant distributed state machine whose job is to keep a moving UE continuously reachable; every procedure maintains that reachability invariant across mobility. Prediction: any new procedure added to the simulator must define what happens to reachability during its execution, not just its happy path. Bug class without it: a handover or paging procedure with a "successful" terminal state that leaves the UE unreachable in an unmodeled intermediate window. Resolves §7 (I5, I13), §21.
  • MM2 — Insight: message-sequence correctness is a stronger and more useful correctness notion than waveform fidelity for this project's purpose (P1) — the 3GPP specs are themselves state-machine specifications for everything above the PHY. Prediction: a defect in this simulator almost always shows up as a wrong or missing message in a trace, not a numerical drift. Bug class without it: chasing PHY-level "realism" investments that never move a call-flow-conformance number. Resolves §1, §28.
  • MM3 — Insight: every timer is a promise about the future that some other part of the system is relying on (I9) — a lost or double-fired timer breaks a promise another state machine assumed was kept. Prediction: any procedure with a supervision timer needs an explicit test for "timer never fires" and "timer fires twice," not only "timer fires once correctly." Bug class without it: a T300-class timer silently orphaned, leaving a UE stuck in an intermediate state forever. Resolves §7 (I9), §16, §20.
  • MM4 — Insight: identity (IMSI/GUTI/SUPI) is the addressing layer underneath every procedure — every later phase (paging, handover, TAU) assumes the identity layer from Phase 5 is correct, so an identity bug is a foundation crack, not a local defect. Prediction: an identity-allocation race under load (I8) manifests downstream, in paging or handover, before it manifests where it originated. Bug class without it: debugging a Phase 8 paging failure for hours before realizing the root cause is a Phase 5 GUTI collision. Resolves §7 (I8), §17, §20.
  • MM5 — Insight: determinism is not a nice-to-have property layered on top of a discrete-event simulator — it is the simulator's actual claim to being a scientific instrument (P10); without it, every reported metric is a one-off anecdote, not a reproducible measurement. Prediction: any hidden source of nondeterminism (unseeded HashMap iteration, system-clock reads) eventually surfaces as a hard-to-reproduce flaky test, usually far downstream from its actual location. Bug class without it: chasing a "flaky" Phase 10 soak-test failure that is actually a Phase 0 iteration-order bug. Resolves §7 (I11), §12, §22.
  • MM6 — Insight: security-context establishment is a strict prerequisite gate, not a parallel concern (P4, I3) — the entire protected-message universe is downstream of one boolean (has AKA completed), so getting that gate wrong invalidates everything after it. Prediction: any new protected-message type added in a later phase must be checked against the I3 guard from day one of that phase's work, not retrofitted. Bug class without it: a new 5G message type (Phase 11) that bypasses the I3-equivalent check because the guard was per-message-type rather than structural. Resolves §7 (I3), §18, §23.
  • MM7 — Insight: a handover is fundamentally a two-phase-commit-shaped problem (prepare on target, commit by switching path, only then release source) even though 3GPP doesn't name it that way — recognizing the shape means the same failure-mode vocabulary (partial commit, rollback, never leave both sides uncommitted) applies. Prediction: any handover-adjacent bug looks like a classic distributed-transaction bug — a resource released before its replacement is confirmed — once traced. Bug class without it: releasing the source-cell context on a fixed timer instead of gating it on target confirmation. Resolves §7 (I5), §21.
  • MM8 — Insight: the core network's logical decomposition (MME/SGW/PGW/HSS, or AMF/SMF/UPF/UDM) exists because 3GPP separates concerns by function, and that separation is itself a scalability lever, not incidental structure (ADR-09) — the state each element owns is exactly the state that must serialize through it under concurrency (P5). Prediction: the practical parallelism ceiling in Phase 10 traces directly back to which elements a given scenario's UEs share. Bug class without it: trying to parallelize handover-heavy scenarios without noticing every handover serializes through the same MME instance. Resolves §9 (ADR-09), §22, §31.

ns-3 (LTE module) and 5G-LENA form a discrete-event network simulator with statistical/analytic RAN and scheduler models and no real radio; their calendar-queue-style event-scheduling design (Required Reading, applied Phase 0) is the closest architectural sibling to this project's own discrete-event core (ADR-02, ADR-03), and 5G-LENA's traces are this project's Phase 11 differential-testing reference (§28). The key contrast against srsRAN/OAI: ns-3/5G-LENA is a pure simulator like this project, trading real-radio interoperability for scale and reproducibility — exactly this project's own trade-off (ADR-05).

Amarisoft is a commercial real-radio LTE/5G test-and-lab platform, referenced here only for its documented call-flow traces as an independent differential-comparison source (§28) where public documentation permits; it is not an architectural model for this project's own design, unlike the other four systems.

34. Back-of-Envelope Capacity Model

  1. Semantic procedures per UE per simulated hour ≈ 8 (1 attach amortized across the run + 6 handovers + 1 TAU under a typical mobility profile) → procedure rate ≈ 8 / 3600 ≈ 0.00222 /s per UE.
  2. Semantic messages per simulated second across the fleet = UEs × procedure rate × avg messages/procedure = 100,000 × 0.00222/s × 9 ≈ 2,000 messages/sim-second (9 is the mean of the 8–10 handover and 11 attach message counts, §4).
  3. Discrete events per simulated second (fan-out factor ≈ 3 events per semantic message: arrival, processing, ancillary timer) = 2,000 × 3 = 6,000 events/sim-second.
  4. Required wall-clock event throughput at M12's ≥ 100:1 sim:wall ratio = 6,000 events/sim-second × 100 sim-seconds/wall-second = 600,000 events/wall-second.
  5. Headroom against M3's 5,000,000 events/second engine capacity = 5,000,000 / 600,000 ≈ 8.3× — the engine's sustained-throughput target is sized well above nominal demand, reserving headroom for burst scenarios (attach storms, T5).
  6. Event-queue op cost at M9's 10,000,000-event depth ceiling (ADR-03's binary min-heap, O(log n)): log2(10,000,000) ≈ 23.3 comparisons per push/pop, the per-operation cost that, multiplied against M3's 5,000,000 ops/second target, sets the minimum comparator-and-heap- walk efficiency the implementation must hit.
  7. Per-UE state footprint × UE count = total footprint: 4 KB × 100,000 UEs = 400,000 KB ≈ 390 MB — well within a single host's memory budget, confirming M13's target is workable at M1's UE ceiling.
  8. Signaling load per cell = (attaches + handovers + paging)/s per cell × messages each. At 100,000 UEs over 2,000 cells (§4), average 50 UEs/cell; using step 1's per-UE procedure rate: 0.00222 × 50 × 9 ≈ 1.0 message/sec/cell nominal signaling load — a T5/FM-7 signaling storm is defined as a large multiple of this baseline (§26's alerting philosophy is trend-based, not an absolute threshold).
  9. Handover interruption time = sum of the X2 sequence's message latencies: 9 messages (§8.10) at an assumed ≈ 5 ms simulated transport-hop latency each ≈ 45 ms, just under M6's 50 ms target — consistent with §4's target being tight but achievable, and explaining why §21.7's neighbor-list-indexing performance concern matters (added per-hop overhead risks breaching M6).
  10. RACH collision probability at nominal load: for k UEs contending over a preamble pool of size N in one RACH occasion, collision probability for at least one collision ≈ 1 − (1 − 1/N)^(k−1); at a nominal contention size k = 20 and pool N = 64, probability ≈ 1 − (63/64)^19 ≈ 1 − 0.746 ≈ 0.254 per occasion — motivating M14's ≥ 99% contention-resolution success target as the recovery mechanism (backoff-and-retry, §15.2), not collision avoidance.
  11. Simulated-to-wall-clock ratio sanity check at 10,000 UEs (M12's actual measurement point): scaling steps 3–4 down by 10× (10,000 UEs) gives ≈ 600 events/sim-second demanded, requiring 60,000 events/wall-second at a 100:1 ratio — well inside the 5,000,000 events/second ceiling, reinforcing that M12's ratio is achievable with substantial margin at the smaller benchmark point where it is actually measured.

36. Alternative Architectures (Roads Not Taken)

36.1 Full System-Level Simulator with a Detailed OFDM PHY

[UE PHY: OFDM waveform] <-- fading/channel --> [gNB PHY: OFDM waveform]
        |                                             |
   [MAC / RLC / PDCP / RRC]                   [MAC / RLC / PDCP / RRC]
        |                                             |
      [NAS]  <----------- N2 / S1 ------------->  [Core NFs]

Winning regime: PHY-layer research — scheduler algorithms under realistic fading, link-adaptation studies — where waveform-level accuracy is the actual research question. REAL embodying system: ns-3 with the 5G-LENA module. Why rejected: this project's load-bearing concern is call-flow/state-machine fidelity (P1), and OFDM-level detail multiplies simulation cost by orders of magnitude for no benefit to the message-sequence questions this simulator answers (§1 non-goals).

36.2 Real-Radio SDR Stack

[UE: SDR + srsUE stack] == real RF over the air == [gNB: SDR + srsENB stack]
                                    |
                              [Core: EPC / 5GC]

Winning regime: interoperability testing against real commercial UEs/networks, lab validation, spectrum research. REAL embodying system: srsRAN, OpenAirInterface. Why rejected: requires SDR hardware and real-time constraints, precludes the 100,000-UE/ 2,000-cell scale target (§4) and the deterministic-replay guarantee (I11) this project depends on — real RF is inherently non-repeatable bit-for-bit.

36.3 Time-Stepped Engine (Fixed-Tick Simulation)

tick 0 -> update all UEs/cells -> tick 1 -> update all UEs/cells -> tick 2 -> ...

Winning regime: workloads where events are dense relative to the tick granularity, e.g. replaying a fixed-rate RF fading trace where ticks map directly to trace samples (ADR-02's rejected-alternative note). REAL embodying system: fixed-TTI-loop system-level simulators (ns-3's own PHY sublayer ticks per-TTI inside its outer discrete-event loop). Why rejected: this project's events (attach, handover, paging) are sparse relative to any tick fine enough to resolve them, so fixed-tick stepping wastes cycles idling through empty ticks at the 100,000-UE scale target (ADR-02).

36.4 Emulation: Real NF Software in Containers with Simulated UEs

[simulated UE stack] --N1/N2 (real HTTP/2 SBI)--> [Open5GS AMF container] -- [SMF] -- [UPF]

Winning regime: core-network integration testing, validating a real core's behavior against synthetic UE load, operational rehearsal for a real 5G-core deployment. REAL embodying system: Open5GS/free5GC run in Docker/Kubernetes with a synthetic UE-simulator front end. Why rejected: real SBI/HTTP-2 wire encoding and NF process orchestration are exactly the fidelity layer ADR-18 explicitly excludes (typed message-passing abstraction, not byte-accurate wire encoding), and container-orchestration overhead precludes the deterministic single-process replay guarantee (I11, ADR-17) this project's correctness claim depends on.

38. Glossary

  • UE — User Equipment; the mobile device/subscriber terminal.
  • eNodeB — LTE radio access network base station.
  • gNB — 5G NR radio access network base station.
  • EPC — Evolved Packet Core; the LTE core network (MME/SGW/PGW/HSS).
  • 5GC — 5G Core network (AMF/SMF/UPF/UDM).
  • MME — Mobility Management Entity; LTE control-plane core element.
  • AMF — Access and Mobility Management Function; 5G equivalent of MME.
  • SGW — Serving Gateway; LTE user-plane anchor toward the PGW.
  • PGW — Packet Data Network Gateway; LTE user-plane anchor toward external networks.
  • UPF — User Plane Function; 5G equivalent of SGW/PGW.
  • HSS — Home Subscriber Server; LTE subscriber/security-data store.
  • UDM — Unified Data Management; 5G equivalent of HSS.
  • NAS — Non-Access Stratum; mobility/session-management signaling between UE and MME/AMF.
  • RRC — Radio Resource Control; radio-resource signaling between UE and eNodeB/gNB.
  • PDCP — Packet Data Convergence Protocol; sequencing/ciphering-placeholder layer.
  • RLC — Radio Link Control; segmentation, ARQ, reordering layer.
  • MAC — Medium Access Control; scheduling, HARQ, multiplexing layer.
  • PHY — Physical layer; here, an analytic SINR/BLER abstraction, not a waveform model.
  • RRC Idle — RRC state with no active radio connection.
  • RRC Connected — RRC state with an active radio connection.
  • RRC Inactive — 5G RRC state suspending the radio connection for fast resume.
  • EMM — EPS Mobility Management; LTE NAS-layer mobility state machine.
  • MM — Mobility Management; 5G NAS-layer mobility state machine (EMM's equivalent).
  • RACH — Random Access Channel procedure; how a UE gains initial uplink access.
  • preamble — the random-access signal a UE transmits in step 1 of RACH.
  • RAR — Random Access Response; step 2 of RACH.
  • contention resolution — RACH step 4, resolving which UE "won" a shared preamble.
  • SIB — System Information Block; broadcast cell-configuration information.
  • MIB — Master Information Block; the first broadcast block a UE reads.
  • attach — the LTE procedure by which a UE registers with the core network (the 5G equivalent term is registration).
  • AKA — Authentication and Key Agreement; the challenge-response authentication procedure.
  • IMSI — International Mobile Subscriber Identity; LTE permanent subscriber identity.
  • SUPI — Subscription Permanent Identifier; 5G permanent subscriber identity.
  • GUTI — Globally Unique Temporary Identity; LTE temporary identity.
  • SUCI — Subscription Concealed Identifier; 5G's concealed form of the SUPI.
  • KASME — LTE key derived from CK/IK and the serving-network identity.
  • KeNB — LTE key derived from KASME, securing the RRC/user-plane context at an eNodeB.
  • KAMF — 5G key derived analogous to KASME, held by the AMF.
  • KgNB — 5G key derived analogous to KeNB, held by the gNB.
  • bearer — an LTE logical data-transport channel with an associated QoS class (QCI).
  • PDU session — the 5G equivalent of a bearer, associated with a 5QI.
  • QCI — QoS Class Identifier; LTE bearer QoS class.
  • 5QI — 5G QoS Identifier; 5G PDU-session QoS class.
  • handover — the procedure moving a UE's active connection from one cell to another.
  • X2 — the LTE eNodeB-to-eNodeB interface used for direct handover signaling.
  • Xn — the 5G gNB-to-gNB interface, X2's 5G equivalent.
  • S1 — the LTE eNodeB-to-MME/SGW interface.
  • N2 — the 5G gNB-to-AMF interface, S1's 5G equivalent.
  • paging — the procedure notifying an Idle UE of pending downlink data or signaling.
  • TAU — Tracking Area Update; a lightweight periodic/mobility-triggered re-registration.
  • GTP — GPRS Tunneling Protocol; user-plane (GTP-U) and control-plane (GTP-C) tunneling.
  • SBI — Service-Based Interface; 5G core's HTTP/2-based inter-NF interface.
  • discrete-event simulation — a simulation paradigm advancing time only at event timestamps, not fixed ticks.
  • event queue — the ordered data structure (here, a binary min-heap) holding pending events.
  • SINR — Signal-to-Interference-plus-Noise Ratio; the channel-quality metric driving the PHY abstraction.
  • BLER — Block Error Rate; the transport-block failure probability derived from SINR.
  • radio-link failure — an unexpected loss of the RRC-Connected radio link (FM-1).
  • tracking area — the geographic grouping of cells within which paging is dispatched without a fresh location update.
  • replay hash — the deterministic checksum of an event trace, used to verify I11.
