Decisions (§9) · 28 ADRs

ADR-01

Implementation language

Chosen

Rust, stable, MSRV pinned

Rejected

Java, Go, C++

When the rejected choice is right

a team with zero Rust experience and a hard 4-week deadline, where Debezium-on-JVM reuse dominates

Why: swallowed-error risk is the dominant CDC failure mode (§1); Rust's Result discipline surfaces it at review time

ADR-02

Async runtime topology

Chosen

Tokio, one runtime per source connector, sinks share an executor

Rejected

one global runtime; per-sink runtimes

When the rejected choice is right

a single-source, single-sink deployment where isolation buys nothing and thread count matters more

Why: isolates a slow sink from head-of-line-blocking a fast source (§3)

ADR-03

Default serialization codec

Chosen

Avro + Confluent-compatible registry

Rejected

Protobuf-only, JSON-only

When the rejected choice is right

a proto-first downstream fleet already standardized on Protobuf end to end

Why: clearest schema-evolution resolution rules (Avro spec Sections 5–6); industry default for Kafka CDC

ADR-04

Debug/legacy codec

Chosen

JSON, opt-in

Rejected

none (Avro-only)

When the rejected choice is right

never for production topics — JSON's informal schema is a FAIL if selected as the primary codec

Why: human-readable payloads for local debugging and legacy consumers with no Avro tooling

ADR-05

Sink delivery-guarantee model

Chosen

engine is sink-aware (DeliveryGuarantee enum per sink)

Rejected

one generic guarantee level for all sinks

When the rejected choice is right

a single-sink deployment where the sink's guarantee is fixed and never queried dynamically

Why: Kafka offers idempotent/transactional; Iceberg offers atomic commit; a generic model would either overclaim or under-use

ADR-06

Default offset store

Chosen

compacted Kafka topic cdc.offsets

Rejected

Postgres table; embedded Raft

When the rejected choice is right

a deployment with no Kafka cluster at all (ADR-07 applies)

Why: free durability/replication/compaction when Kafka is already a dependency (Kreps 2011)

ADR-07

Alternate offset store

Chosen

Postgres durable table, ON CONFLICT + generation fencing

Rejected

none beyond ADR-06/ADR-08

When the rejected choice is right

a Kafka-centric deployment where a second storage dependency is pure overhead

Why: non-Kafka deployments still need a durable, atomically-updatable store

ADR-08

Sealed-appliance offset store

Chosen

embedded 3–5-node Raft cluster

Rejected

relying on local disk only

When the rejected choice is right

any deployment that already has Kafka or Postgres reachable — Raft's operational cost is unjustified

Why: no external dependency at all for air-gapped/appliance deployments

ADR-09

Initial-load algorithm

Chosen

Debezium-style consistent snapshot + HWM-LSN (P6)

Rejected

stream-from-now (miss history); scan-then-stream-from-arbitrary-point (gap/overlap)

When the rejected choice is right

a table small enough (< 1 GB) that a brief write-freeze during scan is acceptable and simpler

Why: the only algorithm with a provably gap-free, bounded-overlap handover

ADR-10

Kafka delivery mode

Chosen

idempotent producer by default; transactional opt-in for EOS

Rejected

acks=0/acks=1 fire-and-forget

When the rejected choice is right

a metrics/analytics pipeline tolerant of occasional duplicate counting, where transactional overhead isn't justified

Why: idempotence closes within-session duplicates for free; transactional closes across-session duplicates (Wang 2017)

ADR-11

Iceberg commit model

Chosen

single atomic metadata-pointer swap per batch (I12)

Rejected

append-without-commit-tracking

When the rejected choice is right

never — this is the only correct Iceberg write path for CDC

Why: Iceberg's native commit primitive; matches CDC's per-batch durability need

ADR-12

Iceberg delete representation

Chosen

equality-delete files for CDC deletes/updates

Rejected

position-delete files

When the rejected choice is right

a compaction job rewriting files, which does know positions and converts equality→position deletes

Why: the writer doesn't know the row's file position at CDC time, only its key

ADR-13

DDL routing

Chosen

schema-history topic, deny-by-default on data topics (P7, I7)

Rejected

replay DDL directly to data consumers

When the rejected choice is right

a pipeline whose only consumer is the engine's own schema-history replay tool

Why: prevents downstream index-rebuild stampedes on every ALTER

ADR-14

Offset-store write model

Chosen

single-writer per connector, generation-fenced (I9, I14)

Rejected

multi-writer with last-write-wins

When the rejected choice is right

never — multi-writer is rejected outright for this store

Why: prevents split-brain double-processing after a zombie restart

ADR-15

Partitioning key

Chosen

source table primary key (P9, I3)

Rejected

round-robin; hash of full row

When the rejected choice is right

a sink that only ever needs aggregate throughput and explicitly disclaims per-key order

Why: preserves per-key order, the one ordering guarantee downstream consumers can rely on

ADR-16

Backpressure mechanism

Chosen

bounded tokio::mpsc channels between every stage (I11)

Rejected

unbounded channels

When the rejected choice is right

a bounded, well-characterized batch workload where memory headroom is already 10x the max burst

Why: converts an OOM risk into a visible, alertable lag metric

ADR-17

Heartbeat cadence

Chosen

10 s fixed interval on quiet tables (I2)

Rejected

When the rejected choice is right

Why: bounds WAL/binlog retention growth on databases with long idle periods

ADR-18

Retry/backoff policy

Chosen

Rejected

When the rejected choice is right

Why: bounds the time a poison message blocks its partition before isolation

Roads not taken (§35)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Trigger-based capture (audit-table triggers / classic Oracle GoldenGate extract)

┌────────────┐  AFTER INSERT/UPDATE/DELETE   ┌──────────────────┐
│ Source table│ ─────────────────────────────▶│ shadow audit table│
└────────────┘        trigger fires            └────────┬─────────┘
                                                          │ polled by
                                                   ┌──────▼────────┐
                                                   │ capture process│──▶ sink
                                                   └────────────────┘

Regime where it wins: a source database with no WAL/binlog-level replication access at all (a locked-down managed-DB tier, or an older engine version lacking logical decoding). Real embodying system: Oracle GoldenGate's classic (trigger-based) capture mode, used before Oracle's integrated (redo-log-based) capture became the default. Why this blueprint rejects it: every trigger fire is an extra write on the primary's hot path (this design's §4 explicitly forbids adding write-path overhead to the source), and a trigger-based audit table has no natural offset model as clean as an LSN/GTID — cursoring through it correctly under concurrent writes is a harder problem than reading an already-ordered log.

Query-based / polling CDC (timestamp-column watermark polling)

┌────────────┐        SELECT * WHERE           ┌──────────────┐
│ Source table│ ◀──── updated_at > $watermark ──│ poll worker   │──▶ sink
└────────────┘        (repeat on interval)      └──────────────┘

Regime where it wins: a source with no log access whatsoever and no trigger permission either — a REST API or SaaS data source, the common case for many ELT connectors. Real embodying system: Apache Sqoop's incremental (--incremental append/lastmodified) import mode, and the polling-mode connectors in Airbyte/Fivetran for sources without native CDC support. Why this blueprint rejects it: a last_modified watermark cannot see hard deletes at all (a deleted row simply vanishes from the next poll's result set, indistinguishable from "it was never queried"), and cannot see intermediate updates between polls — exactly the two failure modes MM1 names as the reason the log is the right primitive.

Transactional outbox pattern (application-mediated event emission)

┌────────────────────────────┐  same DB transaction  ┌───────────────┐
│ Application write + outbox │──────────────────────▶│ outbox table  │
│ table insert (one commit)  │                        └──────┬────────┘
└────────────────────────────┘                                │ tailed by
                                                        ┌──────▼────────┐
                                                        │ CDC tailer     │──▶ sink
                                                        │ (reads outbox  │
                                                        │  as if a table)│
                                                        └────────────────┘

Regime where it wins: a greenfield service willing to change its write path, where the event shape itself (not just the row diff) needs to be application-authored rather than inferred from a row's before/after state. Real embodying system: the pattern Debezium itself documents and supports via its "outbox event router" SMT, and the pattern catalogued in Stopford's Designing Event-Driven Systems (Required Reading). Why this blueprint rejects it as the primary architecture: it requires every application write path to be modified and disciplined into using the outbox table, which this project's non-goals explicitly exclude (§1: "does NOT provide application-level dual-write") — this design instead infers events from the log a database already writes, requiring zero application changes.

Version/watermark-based change tracking (row-version, no event payload)

┌────────────┐  version column bumped   ┌───────────────────┐
│ Source table│ ────────────────────────▶│ change-tracking   │
│ (PK + ver)  │   on every write         │ metadata (PK+ver)  │
└────────────┘                           └─────────┬──────────┘
                                                    │ consumer re-queries
                                                    │ current row by PK
                                             ┌──────▼────────┐
                                             │ consumer's own │──▶ sink
                                             │ SELECT by PK   │
                                             └────────────────┘

Regime where it wins: a consumer that only needs to know which rows changed and can cheaply re-query the source for current state (no need for the actual before/after diff or delete history beyond "this key no longer exists"). Real embodying system: SQL Server's native Change Tracking feature (lighter-weight than SQL Server CDC, tracks only primary-key-plus-version, no row history). Why this blueprint rejects it: it carries no event payload at all — every consumer must re-query the source for current state, which reintroduces read load on the primary this design exists to avoid, and it cannot represent an UPDATE's specific field-level diff, which several of this design's transform-chain stages (§19.2, field-level masking) depend on having.
