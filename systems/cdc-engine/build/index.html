⬜ Phase 0 — Skeleton, Governance & Hello-CDC Smoke Test §12

Objectives

Stand up the repository (§10) at production-scaffold quality; land governance files; produce a walking skeleton that proves the offset-commit-after-sink-ack ordering (I1) end to end on the smallest possible slice: one Postgres INSERT to one Kafka record. No decoding logic beyond a single hard-coded message shape yet.

Deliverable

make compose-up && make test exits 0 with one passing integration test (tests/hello_cdc_smoke.rs): insert one row, observe one Kafka record, observe the offset topic advance.

Acceptance

make bootstrap && make build && make test return exit code 0 on a clean checkout. The smoke test asserts: Kafka record key equals the inserted row's primary key (1); record payload contains amount=42; the LSN recorded in cdc.offsets is strictly greater than the LSN recorded immediately before the test began. Wall-clock budget for the full make test run: ≤ 90 seconds.

Fixtures
Fixture Purpose Expected output
tests/hello_cdc_smoke.rs end-to-end offset-after-sink ordering (I1) one Kafka record + advanced cdc.offsets entry
tests/slot_cleanup.rs replication slot released on test teardown pg_replication_slots row count returns to 0
tests/malformed_bootstrap.rs wal_level != logical at startup cdc-source-pg refuses to start with a named config error
Pitfalls
  • wal_level=logical requires a Postgres restart; forgetting the compose flag makes CREATE_REPLICATION_SLOT fail with a misleading generic error, not a clear "wal_level" message — the connector's own startup check (fixture malformed_bootstrap.rs) exists specifically to give a better error than Postgres does.
  • The smoke-test slot leaks if the test panics mid-run; a Drop-impl test fixture that always issues DROP_REPLICATION_SLOT is mandatory, or repeated CI runs fill the container's disk within a few hundred iterations (I2's failure mode, observed early).
  • Asserting the offset advanced before the Kafka delivery callback returns races the producer; always await producer.flush() (or the callback) before reading cdc.offsets.

⬜ Phase 1 — Postgres Logical Replication Source (`pgoutput`) §13

Objectives

Implement the full pgoutput decoder (§8.1) against a real replication stream: parse every message type B/C/R/I/U/D/T/Y/M, maintain the relation cache, and produce correct ChangeEvents for inserts, updates, and deletes under both REPLICA IDENTITY DEFAULT and FULL.

Deliverable

cdc-source-pg decodes a live pgbench-driven Postgres 16 instance into a correct ChangeEvent stream, inspectable via cdc-cli's run --dry-run mode (prints decoded events without sinking).

Acceptance

Decoding the debezium-pg corpus (10,000 captured pgoutput message streams from a reference Debezium-Postgres pipeline) produces ChangeEvent JSON serializations identical to the reference modulo a documented, exhaustive list of field-ordering differences (fixture conformance/corpora/debezium-pg/). A property test over 10,000 generated REPLICA IDENTITY FULL update sequences asserts before.is_some() on every Op::Update. A 1-hour pgbench run at 1,000 TPS produces zero parse errors and zero panics (fixture bench-pgbench-1h).

Fixtures
Fixture Purpose Expected output
conformance/corpora/debezium-pg/*.bin 10K captured pgoutput streams byte-identical decode modulo documented diffs
fuzz_targets/parse_pgoutput.rs seed corpus malformed/truncated message resilience zero panics over 24h fuzz run
tests/replica_identity_full.rs before-image completeness before.is_some() on every generated Update
tests/toast_unchanged.rs TOAST u tag propagation before marks the column "unchanged", never Null
Pitfalls
  • TOAST-unchanged (u) columns in the O tuple must decode to an "unchanged" marker, not Null — conflating them silently corrupts every downstream diff of that column.
  • REPLICA IDENTITY DEFAULT tables carry only the primary key in O; a pipeline expecting full pre-images gets a partial one and must either accept it explicitly (accept-partial-before-image=true) or the connector refuses the table.
  • The Standby Status Update's +1 offset is exclusive-upper-bound; an off-by-one here silently stalls slot advancement (I2) without any visible error until disk pressure appears hours later.
  • CREATE PUBLICATION FOR ALL TABLES (or omitting an explicit publication) streams the entire database including system catalogs — almost never intended; the connector enforces an explicit table list.

⬜ Phase 2 — Consistent Snapshot & High-Water-Mark Cutover §14

Objectives

Implement the Debezium-standard initial-load algorithm (P6, ADR-09): a gap-free, bounded-overlap handover from "table scan" to "live stream" using the USE_SNAPSHOT slot-creation option, and the DBZ-1031 incremental-snapshot mechanism for online resync of a single table without stopping the pipeline.

Deliverable

cdc snapshot --table public.orders against a live 1M-row table completes and hands off to streaming with zero missed rows and zero unaccounted-for duplicates beyond the documented overlap window.

Acceptance

The snapshot-cutover conformance bucket (100 captured snapshot-then-stream sequences) passes: snapshot rows plus streamed rows equal the table's final state with zero missing rows (fixture snapshot_cutover.gap_free). A property test asserts, for every snapshot run, snapshot_hwm_lsn == slot_consistent_point_lsn exactly (I5). The incremental-snapshot path resyncs a 1M-row table while a concurrent 1,000 TPS write workload runs, with zero rows missed (fixture snapshot_cutover.incremental).

Fixtures
Fixture Purpose Expected output
conformance/corpora/snapshot-cutover/*.json 100 gap-free-cutover scenarios snapshot ∪ stream = final table state, no gaps
tests/hwm_equals_consistent_point.rs I5 property test equality holds on 1,000 generated snapshots
tests/incremental_resync_under_load.rs DBZ-1031 online resync zero rows missed at 1M rows + 1K TPS concurrent writes
Pitfalls
  • Creating the slot after the snapshot transaction (instead of USE_SNAPSHOT at slot creation) reopens the very gap this algorithm exists to close — the snapshot's LSN would exceed the slot's start LSN, and events in between are silently un-streamed unless a separate reconciliation pass is added. USE_SNAPSHOT must be first.
  • A long-running snapshot transaction holds the slot's start LSN back, growing WAL retention for the transaction's whole duration; a 100 GB table's multi-hour snapshot requires operator monitoring of confirmed_flush_lsn lag and disk usage (I2's failure mode, amplified).
  • A crashed snapshot connection mid-scan leaves the slot open at the consistent point but the snapshot rows partial; the connector must restart the entire snapshot from the same consistent point (idempotent re-emission, absorbed by sink idempotency), never resume mid-table.
  • The DBZ-1031 signal table must sit in a schema the connector can write to and the publication does not filter out; a filtered signal table causes the connector to wait forever for chunk boundaries that never arrive in the stream.

⬜ Phase 3 — MySQL Binlog Source (ROW Format + GTID) §15

Objectives

Implement a second, structurally different source connector (cdc-source-mysql) proving the SourceConnector/Offset abstraction (§11.1, §11.4) generalizes: MySQL's poll-then-stream wire protocol, GTID-set offsets (§8.3) instead of LSNs, and ROW-format event decoding (§8.2).

Deliverable

cdc-source-mysql decodes a live sysbench oltp_read_write-driven MySQL 8 instance into correct ChangeEvents, inspectable via the same cdc-cli run --dry-run used for Postgres in Phase 1.

Acceptance

Decoding the debezium-mysql corpus (10,000 captured binlog streams from a reference Debezium-MySQL pipeline) produces identical ChangeEvents (fixture conformance/corpora/debezium-mysql/). A property test over 10,000 generated GTID-set operations asserts add is idempotent and contains(g) is true iff g lies in any stored range. A 1-hour sysbench oltp_read_write run produces zero parse errors (fixture bench-sysbench-1h).

Fixtures
Fixture Purpose Expected output
conformance/corpora/debezium-mysql/*.bin 10K captured binlog streams byte-identical ChangeEvent decode
tests/gtid_set_idempotent.rs GTID-set arithmetic property test 10K generated ops, add idempotent, contains correct
tests/binlog_row_image_minimal_refused.rs startup guard connector refuses to start under minimal
fuzz_targets/parse_binlog_rows.rs seed corpus malformed row-event resilience zero panics over 24h fuzz run
Pitfalls
  • binlog_row_image=minimal (non-default) emits only changed columns plus the primary key; a pipeline that doesn't check this at startup silently produces partial after images that look complete. The connector reads the session variable at connect time and refuses to proceed under minimal.
  • GTID-set string parsing (uuid:1-5:7-9,uuid2:1) is fiddly — empty sets, single-transaction sets, and merged adjacent ranges must all round-trip correctly; a parser bug here resumes from the wrong position with no other symptom until data is silently missing.
  • Schema drift between a cached TABLE_MAP_EVENT and a newly altered table — the parser must refresh its cache on the next TABLE_MAP_EVENT, or the following rows event misparses column offsets entirely (a silent corruption, not a crash, since binary layouts don't self-describe bounds).
  • Non-XA storage engines emit QUERY_EVENT with text "COMMIT" instead of XID_EVENT as the transaction-boundary marker; the reorder buffer must accept either uniformly (I4 does not care which marker closed the transaction, only that one did).

⬜ Phase 4 — Reorder Buffer & Transactional Ordering §16

Objectives

Implement cdc-core::reorder, the shared component both Phase 1 and Phase 3 stamp events into: a bounded, per-transaction buffer that turns raw decoded records into atomically-emitted, correctly ordered ChangeEvent batches (I3, I4).

Deliverable

cdc-core::reorder passes a differential test against the Postgres kernel's own reorderbuffer.c behavior (Required Reading, Reference Implementations) on a shared corpus of interleaved-transaction WAL streams.

Acceptance

The ordering.per_key conformance bucket (10,000 events across 1,000 keys with deliberately interleaved cross-key transactions) shows reorder_out_of_order_total == 0 (I3). A fault-injection test that reorders the underlying byte stream (simulating network reordering) still emits transactions in commit order at the buffer's output (fixture reorder-fuzz). Memory usage for the largest fixture transaction (10,000 rows, 1 KB each ≈ 10 MB) stays under the 512 MB per-transaction ceiling (§4) without spilling.

Fixtures
Fixture Purpose Expected output
conformance/corpora/ordering/*.json 10K events / 1K keys, interleaved txns zero reorder_out_of_order_total
fuzz_targets/reorder_buffer.rs byte-level reordering fuzz I3/I4 hold under 24h fuzz run
tests/torn_transaction_refused.rs I4 property test unbalanced Begin/Commit markers rejected, never partially emitted
tests/large_txn_spill.rs byte-bound spill path transactions > 512 MB spill to disk, never OOM
Pitfalls
  • A transaction that never sees its Commit/XID_EVENT marker (connection dropped mid-transaction) must be dropped on reconnect, not held forever — the buffer's open-transaction map is keyed with a liveness timestamp and stale entries are purged on reconnect at the pre-transaction offset.
  • Treating QUERY_EVENT(BEGIN/COMMIT) and XID_EVENT as different transaction shapes (rather than interchangeable boundary markers) silently breaks ordering for non-XA MySQL engines — the buffer must treat any recognized boundary marker uniformly (mirrors Pitfall 15.6).
  • A byte-size spill implemented as an unbounded temp-file-per-transaction can itself become a resource exhaustion vector under a pathological workload (many large concurrent transactions); the spill path is itself bounded by max_open_txns (§4).
  • Sequence-number stamping that resets on reconnect (rather than persisting across it) breaks downstream consumers relying on strictly increasing per-key sequence numbers as a dedup key.

Objectives

Implement cdc-schema: a Confluent-API-compatible registry client (ADR-22), the Avro codec (ADR-03), and the FULL-compatibility enforcement (P5) that gates every schema registration before its events are emitted (I6).

Deliverable

cdc-schema registers, resolves, and enforces compatibility against a live Confluent-compatible registry instance (docker-compose's schema-registry service), driving the Avro codec end to end.

Acceptance

Avro encoding of the CDC envelope produces byte-identical output to the Debezium reference Avro encoder across the corpus's 10,000-event sample (fixture avro-envelope-diff). The compatibility checker's verdict matches the Confluent registry's verdict on a 1,000-case differential corpus (fixture compat-differential) with zero divergence. A property test asserts decode(encode(event)) == event for 10,000 generated events across every FieldType variant.

Fixture Purpose Expected output
conformance/corpora/schema-evolution/compat-pass/* changes that must be accepted under FULL registry accepts every case

Pitfalls
  • Avro union branch order is part of the wire format — ["null","string"] and ["string","null"] are different schemas at the byte level; I13 fixes null-first as an invariant, not a convention callers must remember.
  • The Decimal logical type encodes as bytes plus precision/scale annotation; a consumer that ignores the annotation reads raw bytes as if they were the final value — cross-validated against Java's BigDecimal decode in the differential fixture.
  • A registry-accepted schema change can still break a specific consumer whose code references fields by name/order outside the registry's resolution rules — the compatibility check is necessary, not sufficient (documented, not solved, in this phase; consumer-side testing is a downstream responsibility).
  • TopicNameStrategy's one-schema-per-topic assumption breaks for a polymorphic topic (multiple record types on one topic) — out of scope for this phase's default; RecordNameStrategy is a documented, not implemented, alternative.

⬜ Phase 6 — Kafka Sink: Idempotent Producer & Transactional EOS §18

Objectives

Implement cdc-sink-kafka: idempotent-producer delivery as the default (ADR-10), transactional delivery as an opt-in EOS path (ADR-10, I12's sibling for Kafka), and the per-key partitioner matching the router's partitioning contract (ADR-15).

Deliverable

cdc-sink-kafka durably commits a batch either in idempotent mode (default) or transactional mode (opt-in), verified against a live Kafka + Schema Registry docker-compose stack.

Acceptance

The kafka_eos.transactional conformance bucket (1,000 transaction-boundary scenarios) shows zero partial transactions visible to an isolation.level=read_committed consumer (fixture kafka-eos-transactional). A 30-minute fault-injection test (broker kill, producer pause, network partition) under EOS configuration shows zero duplicate events at the consumer (fixture kafka-eos-fault-injection). The kafka_eos.zombie_fence bucket (50 zombie-producer scenarios) shows the older transactional.id instance fenced and the newer instance succeeding, 50/50.

Fixtures
Fixture Purpose Expected output
conformance/corpora/kafka-eos/transactional/* 1K txn-boundary crash scenarios zero partial transactions at read_committed
conformance/corpora/kafka-eos/zombie-fence/* 50 zombie-producer scenarios older instance fenced, newer succeeds, every case
tests/idempotent_no_duplicate.rs within-session dedup broker rejects duplicate (PID, seq) pairs

Pitfalls
  • A non-unique transactional.id across two producer instances causes the broker to fence one arbitrarily — deterministic, monotonic ids (pipeline_id-generation) are required, never a randomly generated id per restart (which defeats fencing entirely).
  • The consumer-side default isolation.level is read_uncommitted, which sees aborted transactions — EOS without explicitly setting read_committed on every downstream consumer is silent correctness loss disguised as a working pipeline.
  • Producer-id space (a 64-bit broker-side resource) can fragment under a workload with millions of short-lived producer instances — long-lived producers per pipeline, not per-batch, is the intended usage.
  • Tuning max.in.flight.requests.per.connection above 5 silently disables the ordering guarantee idempotence depends on for retries — the idempotent-producer contract caps this at 5 and the sink refuses a higher configured value rather than accepting it silently.

⬜ Phase 7 — S3/Iceberg Sink & Transform Chain §19

Objectives

Implement cdc-sink-s3-iceberg (atomic per-batch commit, ADR-11/I12; equality-delete representation, ADR-12) and cdc-core::transform (the SMT-style transform chain, P13/ADR-24) exercised end to end against this second, structurally different sink.

Deliverable

cdc-sink-s3-iceberg commits partitioned Parquet + equality-delete files to a MinIO-backed S3 bucket, readable back via a standard Iceberg reader, with the transform chain applying a field-rename and a field-mask stage in the same pipeline run.

Acceptance

The iceberg.equality_delete conformance bucket (10,000 deletes + 10,000 updates across 100 tables) shows the reader's final state matches source state with deleted rows absent (fixture iceberg-equality-delete). The iceberg.commit_conflict bucket (two concurrent committers on one table, 100 scenarios) shows one commit succeeding and the other retrying without corruption (fixture iceberg-commit-conflict, I12). Sink throughput ≥ 50 MB/s per partition (M9) at 32 KB Parquet row-group size with Snappy compression. The transform chain's rename/mask/filter stages pass a 500-case differential corpus against hand-computed expected output.

Fixtures
Fixture Purpose Expected output
conformance/corpora/iceberg/equality-delete/* 10K deletes + 10K updates, 100 tables reader state matches source, zero deleted rows visible
conformance/corpora/iceberg/commit-conflict/* 100 concurrent-committer scenarios one commits, one retries, zero corruption (I12)
tests/transform_chain_differential.rs rename/mask/filter correctness 500-case corpus, exact match to hand-computed output
tests/small_file_batching.rs commit-interval batching ≤ configured files/day at 1K-partition, 60s-interval workload
Pitfalls
  • Committing on every event (rather than batching by interval/size) produces a small-file storm — 1,000 partitions committing every second is 86M files/day; the sink batches to a configurable interval (default 60 s) and byte size (default 128 MB), whichever comes first.
  • Equality-delete files are read-time-expensive (every delete file scans against every overlapping data file) — necessary at write time (the writer doesn't know row positions), but requires a separate, regularly scheduled compaction job (not run by this engine, §1's delegation boundary) converting them to position-deletes.
  • Multiple concurrent committers on the same table without single-committer-per-table-per-pipeline discipline (ADR-11) cause a retry storm that can exceed the sink's own throughput in extreme cases.
  • A transform stage that performs I/O (e.g., an external lookup) violates P13 and makes the chain untestable/unreplayable in isolation — the trait signature (&self, no async I/O primitive threaded through) makes this a compile-time-visible smell, not an outright impossibility, so code review remains the final gate.

⬜ Phase 8 — Offset Durability & Restart Semantics §20

Objectives

Implement cdc-offset's three backends (compacted Kafka topic default, ADR-06; Postgres table, ADR-07; embedded Raft, ADR-08) and prove I1/I9/I14 hold across crash-and-restart at every stage boundary in the pipeline.

Deliverable

A pipeline configured against each of the three offset-store backends survives a scripted 24-hour restart-storm (engine killed and restarted every 60 seconds) with zero events lost.

Acceptance

A property test over 10,000 generated (crash_point, restart) scenarios asserts the consumer-side event set equals the would-be event set of an uncrashed pipeline, modulo duplicates the sink de-duplicates (fixture crash-point-fuzz, I1). The Postgres offset-store backend passes a Jepsen-style network-partition fault injection between engine and Postgres with zero offset regressions (I9, fixture offset-store-partition). The 24-hour restart-storm test (fixture restart-storm-24h) loses zero events across all three backends.

Fixtures
Fixture Purpose Expected output
tests/crash_point_fuzz.rs 10K crash/restart scenarios consumer event set matches uncrashed baseline (I1)
conformance/corpora/jepsen/offset-store-partition/* network partition, Postgres offset backend zero offset regressions (I9)
tests/restart_storm_24h.rs 24h restart-storm, all 3 backends zero events lost
tests/generation_fencing.rs I9/I14 property test a stale-generation write is a no-op, never applied
Pitfalls
  • Committing the offset before the sink's SinkAck exists is the single most severe bug class this phase exists to prevent — the type-level enforcement in §11.5 makes it hard to write by accident, but a backend implementation that bypasses the Sink::commit_batch return value (e.g., a fire-and-forget async write) reopens the hole silently.
  • A generation counter that resets to zero on container redeploy (rather than persisting alongside the offset) lets a zombie writer overwrite a valid, newer offset — the generation must be read back and incremented, never reinitialized.
  • Raft cluster tail-of-log divergence after a lost-quorum event is rare but real; a per-commit checksum in the offset record lets the read path detect and refuse a divergent tail rather than silently trusting it.
  • The Kafka-backend read path must project the compacted topic correctly — reading a non-compacted view (e.g., before compaction has run) can return a stale offset that looks valid but isn't the true latest.

⬜ Phase 9 — Schema Evolution End-to-End §21

Objectives

Prove the five schema-change classes (add, drop, rename, type-change, and their combinations) survive end-to-end — source DDL to registry to consumer decode — under continuous churn, closing the loop opened by Phase 5's registration gate (I6) with the source connectors' DDL detection (Phase 1 §13, Phase 3 §15).

Deliverable

A 10-scenario schema-change suite (add-nullable, add-non-nullable, drop, rename, type-widen, type-narrow, reorder, alias, default-change, doc-change) replays end-to-end with correct consumer-side decode for every scenario against both Postgres and MySQL sources.

Acceptance

The schema_evolution.suite conformance bucket (10 scenarios × both sources) passes with zero decode errors (fixture schema-evolution-suite). The compatibility checker's verdict matches the Confluent registry's verdict on a 1,000-case differential corpus with zero divergence (reusing and extending Phase 5's fixture, §17.5). A 24-hour churn test (random DDL applied every 10 seconds across both sources) shows zero schema-related DLQ events (fixture schema-churn-24h).

Fixtures
Fixture Purpose Expected output
conformance/corpora/schema-evolution/suite/* 10 change classes × 2 sources correct decode, every case
tests/schema_churn_24h.rs continuous DDL churn zero schema-related DLQ events over 24h
tests/ddl_never_on_data_topic.rs I7 property test zero DDL events observed on any data topic

Pitfalls
  • A column added without a default cannot satisfy backward compatibility (old data has no value to read) — the connector's DDL-to-schema translation always carries forward an explicit default (NULL or a typed default) rather than omitting it.
  • A rename expressed as DROP COLUMN + ADD COLUMN (rather than RENAME COLUMN, or without an Avro alias) loses history — old data under the old name becomes unreachable under the new schema; the connector's DDL parser distinguishes a true rename from a drop-add pair where it can (Postgres ALTER TABLE ... RENAME COLUMN is unambiguous; MySQL's CHANGE COLUMN is used analogously).
  • A type change applied at the database before the registry has accepted the corresponding schema update creates a window where in-flight events go to the DLQ (I6) until the schema catches up — documented as the expected, safe behavior, not a bug, but surprising to an operator seeing sudden DLQ growth.
  • Doc/comment-only changes (no wire-format impact) still register a new SchemaId under a strict reading of Avro compatibility — the compatibility checker treats these as compatible-and-cheap, never rejecting them, to avoid needless DLQ churn on no-op-shaped changes.

Pitfalls
  • Batching too aggressively (e.g., a 10-second flush interval) directly inflates p99 latency to match — the 100 ms default is a deliberate choice, only relaxed with explicit, documented operator consent.
  • Compressing very small batches wastes CPU for no ratio benefit — the linger.ms=10/ batch.size=1MB Kafka tuning (§18.7) is the floor below which compression stops paying for itself.
  • A skewed key distribution silently sends most events to one worker; without the HotKeyAlert this manifests only as a mysterious tail-latency regression with no obvious root cause.
  • Running the 30-day soak as a PR-blocking gate (rather than a scheduled, advisory-until-Sealed job) makes every PR wait a month — it must gate a release milestone (Appendix B, §39), never routine merges.
