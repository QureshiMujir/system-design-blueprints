103 — Change Data Capture (CDC) Engine from Scratch

Project Number: 103

Project Name: Change Data Capture (CDC) Engine from Scratch

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a log-based Change Data Capture engine that tails the durable write-ahead interfaces of Postgres (logical decoding via the pgoutput output plugin over a replication slot) and MySQL (row-format binary log with GTID positioning), normalizes every row-level mutation into one ChangeEvent schema (§11), buffers and reorders events per source transaction (Phase 4, §16), evolves schemas under a registry compatibility policy (Phase 5, §17), and delivers to pluggable sinks — Kafka with idempotent-or-transactional exactly-once (Phase 6, §18), S3/Iceberg with atomic per-commit columnar output (Phase 7, §19) — under an explicit at-least-once-by-default, exactly-once-where-the-sink-supports-it delivery contract, with durable offsets committed only after sink durability (I1), snapshot-then-stream initial loads via the high-water-mark LSN trick (Phase 2, §14), dead-letter isolation of poison events (P10), and an SMT-style transform chain for field rename/mask/filter in flight (Phase 7, §19.2).

Phase-0 deliverable (numbered modules/crates, full tree in §10):

  1. cdc-core — ChangeEvent/Offset/Schema/Value types, SourceConnector/Sink/ SchemaRegistry traits, reorder-buffer skeleton, router skeleton, DLQ envelope, heartbeat protocol.
  2. cdc-source-pg — Postgres logical-replication client stub: slot lifecycle, START_REPLICATION handshake, no decode logic yet.
  3. cdc-sink-kafka — Kafka producer stub in idempotent mode only.
  4. cdc-offset — Kafka-compacted-topic offset store stub.
  5. cdc-cli — the cdc binary wiring the above into the Hello-CDC smoke test (Phase 0, §12.3).

System boundaries.

  • Provides: source connectors for Postgres and MySQL; per-transaction reorder + per-key ordering; schema-registry-mediated evolution; Kafka and S3/Iceberg sinks; a transform chain; durable offset commit; snapshot-then-stream cutover; DLQ with alerting.
  • Delegates: durability of the source database's own WAL/binlog (read-only tailer, never a writer); the schema registry's storage engine (we are a client, ADR-03); Kafka/Iceberg's own replication and durability (we rely on their commit contracts, ADR-06/ADR-11); Iceberg delete-file compaction (a separate scheduled job we coordinate with, never run ourselves, §19.6).
  • Does NOT provide: application-level dual-write; a message bus of its own; a general stream-processing/query engine with joins and windows (that is a downstream consumer's job, e.g. project #102/#105, ADR-19/ADR-20); a control-plane UI; synchronous replication.

Non-goals: request/response replication; multi-master conflict resolution; a general ETL/ELT scheduler; a data catalog; row-level encryption key management (delegated to the sink's own encryption-at-rest, Threat Model T9).

Deployment model: one long-running connector process per source database, one or more sink worker processes, coordinating only through the shared offset store (§11.2) and schema registry (§11.6). No shared mutable state between connector processes; each is independently restartable under I1/I3.

Target users/operators: data-platform engineers operating the connectors; on-call SREs diagnosing replication-slot lag, DLQ growth, and schema-registry rejections under time pressure (Operational Readiness, §25; runbooks named there).

What later phases unlock: Phase 4's reorder buffer (§16) is a reusable seam for any future source that streams unordered log records; Phase 5's registry client (§17) is reusable for any future sink codec; Phase 7's Iceberg sink (§19) unlocks OLAP consumption without a second bespoke pipeline. Connectors and sinks not built here plug into the same SourceConnector/Sink traits (§11.4, §11.5) — PhaseDeferred("Deferred Features Register").

Recommended language: Rust (stable channel, MSRV pinned, ADR-01). CDC's dominant risk is silent data loss on a swallowed error path, not raw CPU — the bottleneck is the source database's log-read rate and the sink's commit rate (§4), not the engine's instruction count. Rust's Result-must-be-handled discipline plus ownership turns a swallowed error into a compile-time or review-time event. Rejected: Java (Debezium's own language — GC pauses interact badly with the replication-slot heartbeat deadline of I2; checked exceptions are routinely caught-and-logged in practice, which is exactly the swallowed-error failure mode this project exists to avoid); Go (weaker sum-type support makes the Op/Value variant modeling of §11.3 leakier, and the nil-error idiom repeats the Java swallowing risk); C++ (manual memory management raises the cost of every parser hot path in §8/§13 without a matching throughput win, since §4 shows the ceiling is I/O-bound, not CPU-bound).

Prerequisites: Postgres WAL + logical decoding + replication slots; MySQL row-format binlog + GTID sets; the at-least-once/exactly-once/effectively-once delivery hierarchy (Treat 2015, Wang 2017); Avro/Protobuf schema-evolution resolution rules; the operational fact that an abandoned replication slot retains WAL on the primary until consumed (I2).

Estimated timeline: Phase 0 in 2 weeks; the full system (Phases 0–10, §12–§22) in 7–9 months.

Deferred features (flagged here; each anchored and resolved in the Deferred Features Register, §36): MongoDB change-stream source — PhaseDeferred("Deferred Features Register"); SQL Server CDC-table source — PhaseDeferred("Deferred Features Register"); Pulsar sink — PhaseDeferred("Deferred Features Register"); GDPR forget-tooling — PhaseDeferred("Deferred Features Register"); cross-region active-active CDC — PhaseDeferred("Deferred Features Register").

2. Why Build This

CDC is the connective tissue of modern data infrastructure: every warehouse fed from an operational Postgres/MySQL database, every event-driven service reacting to "an order was placed" without polling, every search index mirroring a table at sub-second freshness, every audit log needing the actual (before, after) diff of an UPDATE — all of them are CDC pipelines whether the team building them used the phrase or not. The field's foundational lesson, written down by Kreps (2013): the database's write-ahead log is the source of truth; the table is a materialized view of the log. Building this system from scratch is the only way to internalize why that claim is true rather than that it is true.

Why it matters architecturally. A CDC engine forces you to own, end to end, four things most engineers only ever consume: (1) a foreign wire protocol you did not design (Postgres logical replication, MySQL's COM_BINLOG_DUMP_GTID); (2) an offset model with no natural total order across sources (LSN vs GTID set); (3) a reorder buffer that turns "the database streamed me records" into "the consumer sees coherent committed transactions" (Postgres's own reorderbuffer.c is the reference); (4) a delivery-guarantee lattice (at-most-once / at-least-once / exactly-once) that is provably impossible to get generically right (Treat 2015) and must instead be engineered per sink.

Why it matters historically. Debezium (Morling et al., Red Hat, building on ideas from LinkedIn's Databus lineage) made log-based CDC an open-source default; Maxwell's Daemon (Zendesk) proved the MySQL-only pattern earlier and smaller; Kafka Connect (Kreps, Narkhede, Rao 2011) supplied the runtime contract (SourceTask, offset topics) most CDC connectors still target; AWS DMS and Fivetran/Airbyte are the commercial/SaaS wrappers most engineers meet CDC through — none of which is the log-based idea itself, only a packaging of it.

The engineering muscles it builds: reading a byte-level wire protocol from a spec (§8.1); building a bounded reorder buffer under a strict atomicity invariant (I4); reasoning about a provably-impossible-to-generalize delivery guarantee (P3) and making it operationally sound anyway (idempotent sinks); designing a schema-evolution contract that survives a rolling deployment (P5); building an offset-commit protocol whose ordering is the entire difference between "at least once" and "silent data loss" (I1).

Cross-links to sibling systems: project #102 (a streaming/stream-processing engine) consumes this project's Kafka topic as an ordinary source — no direct coupling, only the wire contract (ADR-19); project #105 (an OLAP/Flink-class engine) consumes the Iceberg table this project commits to (ADR-20); this project's schema registry client (§17) is the same shape any future Avro/Protobuf producer in the portfolio would build.

Four properties recur throughout this document. First, source and sink are fully decoupled by the ChangeEvent schema and the registry: a Postgres source can feed a Kafka sink and an Iceberg sink simultaneously, and adding a sink never touches a source (ADR-05). Second, the offset store is committed strictly after the sink's durability ack (I1); restart correctness reduces to "replay from the last durable offset, rely on at-least-once plus sink idempotency." Third, the reorder buffer (trust boundary: process-internal, no network) is what turns a raw log tail into a stream of coherent committed transactions — its correctness is the difference between this engine and tail -f on the WAL. Fourth, snapshot and streaming share one downstream code path; a snapshot event is a synthetic prefix of the same stream, never a parallel track. Concurrency boundaries: one Tokio runtime per source connector (ADR-02) isolates a slow sink from head-of-line-blocking a fast source; sink workers share an executor. Persistence boundaries: the offset store and the schema registry are the only durable external dependencies besides the source DB and the sink itself.

6. Design Principles

  1. The log is the source of truth (P1). The WAL/binlog is the authoritative record; the table is a materialized view. The engine reads the log, never polls the table. Tradeoff: log-tailing requires replication privileges the table-polling alternative would not; operationally this means slot/binlog hygiene (I2) becomes a first-class concern. Violating it (polling a last_modified column instead) reintroduces missed deletes and lost intermediate updates — see Alternative Architecture §35.2.
  2. Events are immutable (P2). Once emitted from the reorder buffer, an event is never mutated; schema evolution produces new events under new schema-ids, never rewrites of old ones (Helland 2015). Tradeoff: storage grows monotonically; compaction/TTL is a sink-side concern, not the engine's. Violating it breaks every downstream consumer's replay guarantee.
  3. At-least-once is the default; exactly-once is opt-in (P3). Every committed source transaction reaches every sink at least once; the sink is responsible for idempotency unless the sink is transactional. Treat (2015) is the linguistic clarification; Wang (2017) the engineering answer. Tradeoff: consumers not designed for duplicates will double-apply; the registry docs this contract per sink (DeliveryGuarantee, §11.5). Violating it (silently claiming exactly-once everywhere) is the single most common CDC vendor overclaim.
  4. Offset commit is the linchpin of restart correctness (I1, P4). Order: read → emit → sink commits → offset commits. Reversing it loses data on crash; committing offset first duplicates silently and permanently (no way to detect it happened). This is the only correct order and it is enforced at the type level (§11.5's Sink::commit_batch signature).
  5. Schema evolution must be FULL-compatible by registry policy (P5). A breaking schema change is a deployment incident, not a design choice. Default compatibility mode FULL (ADR-03); column rename via Avro alias is supported, rename-without-alias is rejected at registration. Tradeoff: FULL is stricter than BACKWARD-only, rejecting some changes a looser policy would allow; operationally this catches breakage before it ships instead of after.
  6. Snapshot-then-stream via the high-water-mark LSN trick (P6). CREATE_REPLICATION_SLOT ... USE_SNAPSHOT binds the slot's consistent_point to the snapshot transaction's view; resuming START_REPLICATION from that LSN is gap-free and bounded-overlap. Reversing the creation order (slot after snapshot) reopens the gap this trick exists to close (Pitfall §14.6).
  7. DDL is explicit, never replayed to data sinks by default (P7). DDL routes to a schema-history topic the engine consumes on restart; a data consumer that rebuilds an index on every ALTER is a foot-gun. DDL is allowlisted per pipeline. Violating it turns every schema change into a downstream stampede.
  8. Tombstones for deletes, per-sink default (P8). A delete emits Op::Delete plus, where the sink is Kafka, a separate tombstone record (null value, same key) so log-compaction can garbage collect. The tombstone is optional per tombstones.on.delete; Iceberg's equality-delete mechanism makes a Kafka-style tombstone redundant there.
  9. Key-based partitioning preserves per-key order only (I3, P9). The partition key is the source table's primary key. Same-row events are strictly ordered; cross-row events are not. Helland's (2016) consistency taxonomy is the frame: this is a deliberately weaker-than-global guarantee, documented at every sink boundary.
  10. DLQ is mandatory, never optional (P10). A poison message (undecodable, incompatible, sink-rejected past max_retries) is routed to a per-pipeline DLQ with the original payload and error trace, alerted, and the pipeline continues. A configuration without a DLQ is refused at startup (Invariant I10).
  11. Replication hygiene is non-negotiable (I2, P11). An abandoned Postgres slot retains WAL forever; heartbeats on quiet tables keep confirmed_flush_lsn advancing every 10 s. CI asserts the heartbeat ticks on a 24-hour-quiet table.
  12. Conformance is the contract (P12). The conformance suite (§27) gates every promotion; a regression against a named fixture is a merge block, not a warning.
  13. Transforms are pure and declarative (P13). The transform chain (Kafka Connect SMT analogue, §19.2) is an ordered list of stateless, side-effect-free stages (rename, mask, filter, key-extract); no stage may perform I/O or hold cross-event state. Violating it turns a transform into an untestable, unreplayable side channel.
  14. Backpressure propagates end-to-end, never buffers unboundedly (I11, P14). A slow sink slows the router, which slows the reorder buffer, which slows the source connector's consumption, which raises replication lag visibly at the source (ADR-16's bounded-channel design). Violating it (unbounded internal queues) trades a visible, alertable lag for an invisible OOM.

These are enforced at the type level where possible (Offset is non-Default/non-Copy, §11.1; Sink::commit_batch takes the batch and returns before offset commit can occur, §11.5) and by code review otherwise.

8. Domain Model / Protocol / Data Model

8.1 Postgres pgoutput wire format

pgoutput emits message types identified by a single ASCII byte, following CREATE_REPLICATION_SLOT <slot> LOGICAL pgoutput and START_REPLICATION SLOT <slot> LOGICAL <lsn>:

Code Message Payload Drives
B Begin final LSN, commit timestamp, XID reorder-buffer txn open (I4)
C Commit flags, commit LSN, end LSN, timestamp reorder-buffer txn flush (I4)
R Relation OID, namespace, name, replica identity, columns relation cache update (§13.2)
I Insert relation OID, N (new) tuple Op::Insert
U Update relation OID, optional O/K (old/key) tuple + N tuple Op::Update
D Delete relation OID, O/K tuple Op::Delete
T Truncate relation count, flags, OID list Op::Truncate
Y Type type OID, namespace, name type-OID cache (non-builtin types)
M Message logical decoding message (out-of-band) ignored by default; extension point

Tuple columns are tagged: n (null), u (unchanged TOAST — only in O tuples), t (text-format, length-prefixed UTF-8, resolved against the Relation message's type-OID map). The Relation message is cached by OID; Insert/Update/Delete reference it. REPLICA IDENTITY DEFAULT carries only the primary key in O; REPLICA IDENTITY FULL carries every column — the connector refuses tables with DEFAULT identity unless accept-partial-before-image=true is set (Pitfall §13.6).

8.2 MySQL binlog ROW-format event types

A typical transaction: GTID_EVENT, QUERY_EVENT(BEGIN), TABLE_MAP_EVENT, WRITE_ROWS_EVENT_V2 (repeated), XID_EVENT.

Event Code Significance
FORMAT_DESCRIPTION_EVENT 0x0F first event of every binlog file; declares layout
TABLE_MAP_EVENT 0x13 maps a table id to (schema, table, column types)
WRITE_ROWS_EVENT_V2 0x1E inserts
UPDATE_ROWS_EVENT_V2 0x1F updates, before + after row images
DELETE_ROWS_EVENT_V2 0x20 deletes
GTID_EVENT 0x21 declares the GTID of the next transaction
XID_EVENT 0x10 transaction commit marker
QUERY_EVENT 0x02 DDL; also BEGIN/COMMIT text on non-XA engines

A row-image event carries a present-column bitmap, a null bitmap (indexed only over present columns), then per-present-non-null-column binary values whose layout follows the most recent TABLE_MAP_EVENT for that table id. Decode order: for each declared column, consult the present-bitmap; if absent, value is Null; if present, consult the null-bitmap at its rank among present columns; if null, value is Null; otherwise decode per the column's TABLE_MAP-declared type. An unknown table id (no preceding TABLE_MAP_EVENT) is a hard decode error, never a silent skip.

8.3 GTID set model

A GTID is (server_uuid, transaction_number); a GTID set is a union of numeric ranges per UUID, e.g. 3E11FA47-71CA-11E1-9E33-C80AA9429562:1-100,7C8FBE...:1-50. Membership test: for a candidate (uuid, n), the set contains it iff some range for uuid covers n. Merge: adjacent/overlapping ranges for the same UUID coalesce into one range (idempotent under repeated add). GTID sets survive replica promotion and topology change — the reason MySQL CDC standardizes on them over raw (file, position) pairs.

8.4 ChangeEvent state machine (connector lifecycle)

State Entry condition Valid transitions Exit action
Init process start, no durable offset found → Snapshotting begin consistent snapshot (P6)
Resuming process start, durable offset found → Streaming reconnect at stored offset
Snapshotting Init → Streaming (on HWM reached) emit synthetic Insert events per row
Streaming Snapshotting/Resuming → Paused | → Draining | → Error tail log, emit ChangeEvents
Paused backpressure (I11) sustained > pause_threshold_ms → Streaming (on drain) stop consuming from source socket
Draining SIGTERM received → Stopped flush in-flight batches, commit final offset
Error unrecoverable decode/connection fault → Streaming (after backoff) | → Stopped (max retries) log with tx_id/offset context, alert
Stopped drain complete or max retries exhausted (terminal) release replication slot handle (not drop it)

8.5 Worked example — one INSERT, byte to event

INSERT INTO public.orders (id, amount) VALUES (1, 42) on a table with REPLICA IDENTITY DEFAULT produces, on the wire: a B message (XID, LSN 100), an R message (OID 16400, columns id:int8, amount:int8) if not already cached, an I message (OID 16400, tuple tag N, values t 1, t 42), a C message (commit LSN 108). The connector decodes this into ChangeEvent { source: {connector:"postgres", table:"orders"}, op: Insert{after: {id:1, amount:42}}, offset: PostgresLsn{lsn:108, flushed:0}, tx_id: Some(TxnId(xid)) } only after the reorder buffer sees the matching C for the B it opened (I4) — the R/I messages alone never produce output.

8.6 Malformed-input example

A truncated pgoutput Insert message (buffer ends mid-tuple, e.g. after the column-count byte but before any column tag) is a ParseError::UnexpectedEof, never a partial ChangeEvent; the connector reconnects and reprocesses from the last confirmed LSN. A binlog row event referencing a table id with no prior TABLE_MAP_EVENT in the current connection's cache is ParseError::UnknownTable, treated identically — a hard stop and reconnect, never a best-effort guess at column layout.

8.7 Failure-path example

Engine crashes after Sink::commit_batch returns Ok (Kafka broker has the batch, acks=all) but before cdc-offset's commit call completes. On restart, the stored offset is the previous batch's; the engine re-reads and re-emits the already-committed batch. The Kafka idempotent producer's sequence-number check (or, under EOS, the transactional fencing) makes the re-send a no-op at the broker, and any at-least-once consumer downstream de-duplicates on the row's primary key — this is I1's guarantee in action, and the reason no sink may be configured without an idempotency or transactional story (ADR-05).

                 Array(Box<FieldType>), Map(Box<FieldType>) }
enum Value { Null, Bool(bool), I64(i64), F64(f64), Str(String), Bytes(Vec<u8>),

struct SchemaVersion(pub u32);   // monotonically increasing per subject (I6)

Ownership: Schema is Arc-shared across every ChangeEvent of one batch (avoids per-event schema clone). Field.aliases is the Avro-rename mechanism (§17.6). Compatibility: FieldType additions are additive; removing a variant is a wire-breaking change gated by ADR-27's SemVer policy on cdc-core.

11.4 SourceConnector trait

trait SourceConnector: Send + Sync + 'static {
    fn start(&self, start: Option<Offset>) -> Result<EventStream, SourceError>;
    fn ack(&self, offset: &Offset) -> Result<(), SourceError>;
    fn connector_kind(&self) -> &'static str;
}
type EventStream = Pin<Box<dyn Stream<Item = Result<ChangeEvent, SourceError>> + Send>>;

start(None) triggers a consistent snapshot first (P6), then streams from the HWM. ack advances the server-side cursor (Postgres Standby Status Update; MySQL has no explicit ack — GTID positioning is implicit in the next COM_BINLOG_DUMP_GTID). Concurrency: one live stream per connector instance; ack may be called from a different task than start's consumer.

11.5 Sink trait

trait Sink: Send + Sync + 'static {
    fn commit_batch(&self, batch: Vec<ChangeEvent>) -> Result<SinkAck, SinkError>;  // MUST NOT
                                                                                     // return Ok
                                                                                     // before durable
    fn delivery_guarantee(&self) -> DeliveryGuarantee;
}
struct SinkAck { committed_through: Offset, durable_at: Instant }
enum DeliveryGuarantee { AtLeastOnce, ExactlyOnceIdempotent, ExactlyOnceTransactional }

The signature is the I1 contract made physical: the engine's offset-commit call site takes SinkAck::committed_through as its only legal input, so committing before this value exists is a type error, not a discipline error.

11.6 SchemaRegistry trait

trait SchemaRegistry: Send + Sync + 'static {
    fn register(&self, subject: &str, schema: &Schema) -> Result<SchemaId, RegistryError>;  // I6
    fn get_by_id(&self, id: SchemaId) -> Result<Schema, RegistryError>;
    fn get_latest(&self, subject: &str) -> Result<(SchemaId, Schema), RegistryError>;
}
struct SchemaId(pub u32);

register is the sole gate for I6: no event may carry a SchemaId that has not passed this call. RegistryError::Incompatible is a first-class variant, routed to the DLQ (I10), never swallowed.

11.7 Codec & transform surface

trait Codec: Send + Sync { fn encode(&self, e: &ChangeEvent, id: SchemaId) -> Vec<u8>;
                            fn decode(&self, buf: &[u8]) -> Result<(ChangeEvent, SchemaId), CodecError>; }

TransformStage::apply returning Ok(None) is a filter (event dropped, not an error); every stage is required to be side-effect-free and hold no cross-event state (P13) — enforced by code review and by the trait's &self (non-&mut self) receiver, which makes accidental mutable state a compile error.

Operator visibility: the error surfaces as a parse_error_total{message_type} metric spike plus a structured log line carrying the offending LSN.

14. Phase 2 — Consistent Snapshot & High-Water-Mark Cutover

14.1 Objectives

Implement the Debezium-standard initial-load algorithm (P6, ADR-09): a gap-free, bounded-overlap handover from "table scan" to "live stream" using the USE_SNAPSHOT slot-creation option, and the DBZ-1031 incremental-snapshot mechanism for online resync of a single table without stopping the pipeline.

14.2 Detailed Implementation Steps

Implement cdc-snapshot::consistent: issue CREATE_REPLICATION_SLOT cdc_test LOGICAL pgoutput USE_SNAPSHOT, capturing the returned exported-snapshot name and the slot's consistent_point LSN (I5 — these must be provably the same value, asserted by a property test, not just assumed). In a second session, SET TRANSACTION SNAPSHOT '<exported>' and SELECT * FROM <table>, emitting each row as a synthetic Op::Insert tagged with consistent_point as its offset. Close the snapshot transaction; START_REPLICATION SLOT cdc_test LOGICAL <consistent_point> resumes streaming from exactly the snapshot's LSN (P6's core claim — no gap, no gap-driven overlap beyond what idempotent sinks already absorb). Implement cdc-snapshot::incremental per the DBZ-1031 signal-table design: write a row to a source-side signal table; observe it appear in the stream (that is the chunk open/close boundary); read a chunk of the target table; interleave chunk rows with concurrently streamed events in LSN order (Required Reading: Debezium DBZ-1031 design, §5). Route every snapshot/incremental event through the same router and sinks as streamed events — no parallel code path (§3's fourth architectural property).

14.3 Deliverable

cdc snapshot --table public.orders against a live 1M-row table completes and hands off to streaming with zero missed rows and zero unaccounted-for duplicates beyond the documented overlap window.

14.4 Acceptance Criteria

The snapshot-cutover conformance bucket (100 captured snapshot-then-stream sequences) passes: snapshot rows plus streamed rows equal the table's final state with zero missing rows (fixture snapshot_cutover.gap_free). A property test asserts, for every snapshot run, snapshot_hwm_lsn == slot_consistent_point_lsn exactly (I5). The incremental-snapshot path resyncs a 1M-row table while a concurrent 1,000 TPS write workload runs, with zero rows missed (fixture snapshot_cutover.incremental).

Fixture Purpose Expected output

tests/hwm_equals_consistent_point.rs I5 property test equality holds on 1,000 generated snapshots

14.6 Pitfalls

  • Creating the slot after the snapshot transaction (instead of USE_SNAPSHOT at slot creation) reopens the very gap this algorithm exists to close — the snapshot's LSN would exceed the slot's start LSN, and events in between are silently un-streamed unless a separate reconciliation pass is added. USE_SNAPSHOT must be first.
  • A long-running snapshot transaction holds the slot's start LSN back, growing WAL retention for the transaction's whole duration; a 100 GB table's multi-hour snapshot requires operator monitoring of confirmed_flush_lsn lag and disk usage (I2's failure mode, amplified).
  • A crashed snapshot connection mid-scan leaves the slot open at the consistent point but the snapshot rows partial; the connector must restart the entire snapshot from the same consistent point (idempotent re-emission, absorbed by sink idempotency), never resume mid-table.
  • The DBZ-1031 signal table must sit in a schema the connector can write to and the publication does not filter out; a filtered signal table causes the connector to wait forever for chunk boundaries that never arrive in the stream.

14.7 Performance Concerns

Snapshot throughput target ≥ 500 MB/s aggregate (M5) via parallel snapshot-worker connections, each reading a disjoint key range of the target table under the same exported snapshot. Incremental snapshot chunk size trades resync latency (smaller chunks: faster interleaving with live writes) against per-chunk signal-table round-trip overhead (larger chunks: fewer round trips) — default chunk size 10,000 rows, tunable.

14.8 Edge Cases

A table with no primary key cannot be safely chunked by the incremental algorithm (no stable ordering key) — the connector refuses incremental snapshot on such tables and falls back to full consistent snapshot only. A snapshot started against a replica (not the primary) — refused at startup; USE_SNAPSHOT semantics assume a writable primary's slot. Concurrent DDL during a snapshot scan — the scan's REPEATABLE READ transaction is isolated from it; the DDL surfaces as a subsequent SchemaChange event once streaming resumes.

14.9 Failure Analysis

Snapshot-transaction crash mid-scan: detection is the connector's own liveness check on the snapshot session; recovery restarts the whole snapshot at the same consistent_point (never a different one — reusing the LSN keeps I5 satisfied). Incremental-snapshot signal-table miss: detection is a stall in the chunk-boundary observation with no error surfaced by Postgres itself; the connector emits a SnapshotStalledAlert after a configurable timeout (default 5 minutes) naming the missing signal-table write as the likely cause.

14.10 Operational Notes

Metrics: snapshot_rows_emitted_total, snapshot_progress_pct, snapshot_hwm_lsn, incremental_chunk_boundaries_total. Runbook docs/runbooks/schema-drift.md covers the DDL-during-snapshot interaction. Deployment: snapshot workers are ephemeral tasks within the same connector process, not separate deployables.

16. Phase 4 — Reorder Buffer & Transactional Ordering

16.1 Objectives

Implement cdc-core::reorder, the shared component both Phase 1 and Phase 3 stamp events into: a bounded, per-transaction buffer that turns raw decoded records into atomically-emitted, correctly ordered ChangeEvent batches (I3, I4).

16.2 Detailed Implementation Steps

Implement a transaction-id-keyed map (tx_id → Vec<ChangeEvent>), opened on a Begin/GTID_EVENT boundary marker and flushed atomically on the matching Commit/XID_EVENT marker, discarded entirely on an explicit rollback signal — applying Helland's (2015) immutability frame (P2) at the buffer boundary: nothing downstream ever sees a partial transaction (I4). Enforce the per-key ordering invariant (I3, Helland 2016's consistency taxonomy) by stamping every event with (source, tx_id, offset, sequence) before it leaves the buffer, and routing same-key events through the same downstream partition (P9) so the router's stable partitioning preserves the buffer's commit order. Bound the map at max_open_txns (§4: 4,096) and per-transaction byte size (§4: 512 MB) — a transaction exceeding the byte bound spills to a temp file keyed by tx_id (named, never silent) rather than growing the in-memory map unboundedly (I11's backpressure principle applied to the buffer itself, not just inter-stage channels). Implement the debugging simulator harness referenced in §7's methodology: replay a captured stream with injected out-of-order delivery and assert I3/I4 hold at every commit boundary.

16.3 Deliverable

cdc-core::reorder passes a differential test against the Postgres kernel's own reorderbuffer.c behavior (Required Reading, Reference Implementations) on a shared corpus of interleaved-transaction WAL streams.

16.4 Acceptance Criteria

The ordering.per_key conformance bucket (10,000 events across 1,000 keys with deliberately interleaved cross-key transactions) shows reorder_out_of_order_total == 0 (I3). A fault-injection test that reorders the underlying byte stream (simulating network reordering) still emits transactions in commit order at the buffer's output (fixture reorder-fuzz). Memory usage for the largest fixture transaction (10,000 rows, 1 KB each ≈ 10 MB) stays under the 512 MB per-transaction ceiling (§4) without spilling.

16.5 Conformance Fixtures

Fixture Purpose Expected output
conformance/corpora/ordering/*.json 10K events / 1K keys, interleaved txns zero reorder_out_of_order_total
fuzz_targets/reorder_buffer.rs byte-level reordering fuzz I3/I4 hold under 24h fuzz run
tests/torn_transaction_refused.rs I4 property test unbalanced Begin/Commit markers rejected, never partially emitted

16.6 Pitfalls

  • A transaction that never sees its Commit/XID_EVENT marker (connection dropped mid-transaction) must be dropped on reconnect, not held forever — the buffer's open-transaction map is keyed with a liveness timestamp and stale entries are purged on reconnect at the pre-transaction offset.
  • Treating QUERY_EVENT(BEGIN/COMMIT) and XID_EVENT as different transaction shapes (rather than interchangeable boundary markers) silently breaks ordering for non-XA MySQL engines — the buffer must treat any recognized boundary marker uniformly (mirrors Pitfall 15.6).
  • A byte-size spill implemented as an unbounded temp-file-per-transaction can itself become a resource exhaustion vector under a pathological workload (many large concurrent transactions); the spill path is itself bounded by max_open_txns (§4).
  • Sequence-number stamping that resets on reconnect (rather than persisting across it) breaks downstream consumers relying on strictly increasing per-key sequence numbers as a dedup key.

16.7 Performance Concerns

The open-transaction map is the primary allocation surface in the whole pipeline; pooling Vec<ChangeEvent> allocations per transaction slot (rather than allocating fresh per transaction) keeps steady-state allocation near zero for typical (small) transactions. Lock contention: the map is sharded by tx_id hash to avoid a single mutex bottleneck at 100K events/sec (M1/M2).

16.8 Edge Cases

Two transactions with colliding tx_ids across a reconnect boundary (Postgres XIDs wrap at 2^32) — the buffer scopes tx_id uniqueness to a single connection epoch, never across reconnects. A zero-row transaction (Begin immediately followed by Commit, e.g., an empty explicit transaction) — emits nothing, advances the offset, never errors. A transaction whose only content is a Truncate — emitted as a single Op::Truncate event, not expanded per-row.

16.9 Failure Analysis

A torn transaction (Commit without a matching Begin, or vice versa) is a hard invariant violation (I4) — the buffer aborts the current connection and reconnects at the last confirmed pre-transaction offset rather than guessing at recovery. Blast radius: bounded to the current connector; already-flushed transactions are unaffected. Detection is immediate (the assertion in §7's methodology fires in the simulator before this ever reaches production).

16.10 Operational Notes

Metrics: reorder_open_txns, reorder_buffer_bytes{tx_id} (cardinality-bounded via aggregation, not per-tx_id label), reorder_spill_total, reorder_out_of_order_total (paged at > 0). Tracing: one span per open transaction, matching Phase 1/3's Begin→Commit span convention. No schema/migration concerns — the buffer is purely in-process, in-memory-plus-spill state.

17.1 Objectives

17.2 Detailed Implementation Steps

Implement client.rs: register/get-by-id/get-latest against the Confluent Schema Registry HTTP API (Required Reading, RFCs/Specifications) under subject naming TopicNameStrategy (<topic>-value) (ADR-22). Implement avro_evolution.rs: build an Avro record schema from cdc-core::Schema (§11.3), wrapping the row schema in a Debezium-style envelope (op, ts_ms, source, before, after) — a schema-shape convention borrowed deliberately for cross-tool familiarity (Required Reading: Debezium reference implementation). Enforce nullable-union ordering with null always first (I13) at schema-construction time, never left to caller discipline. Implement compat.rs: the FULL compatibility check (P5, ADR-03) — a schema change is accepted only if it is simultaneously backward- and forward-compatible per the Avro resolution rules (Avro spec Section 6, Required Reading). Wire register as a hard gate before the codec layer emits any event under the new SchemaId (I6) — a rejected registration routes the affected events to the DLQ (I10), never to a stale schema-id.

17.3 Deliverable

cdc-schema registers, resolves, and enforces compatibility against a live Confluent-compatible registry instance (docker-compose's schema-registry service), driving the Avro codec end to end.

17.6 Pitfalls

  • Avro union branch order is part of the wire format — ["null","string"] and ["string","null"] are different schemas at the byte level; I13 fixes null-first as an invariant, not a convention callers must remember.
  • The Decimal logical type encodes as bytes plus precision/scale annotation; a consumer that ignores the annotation reads raw bytes as if they were the final value — cross-validated against Java's BigDecimal decode in the differential fixture.
  • A registry-accepted schema change can still break a specific consumer whose code references fields by name/order outside the registry's resolution rules — the compatibility check is necessary, not sufficient (documented, not solved, in this phase; consumer-side testing is a downstream responsibility).
  • TopicNameStrategy's one-schema-per-topic assumption breaks for a polymorphic topic (multiple record types on one topic) — out of scope for this phase's default; RecordNameStrategy is a documented, not implemented, alternative.

17.7 Performance Concerns

Registry lookups are cached by SchemaId (M6/M7 targets: ≤ 1 ms cached, ≤ 50 ms cold) — a cache miss only occurs on first sight of a schema-id, never per-event in steady state. Avro encoding avoids intermediate serde_json-style dynamic representations; the encoder writes directly from cdc-core::Value to the Avro binary wire format.

17.8 Edge Cases

A schema registration racing across two connector instances for the same subject (both observing the same DDL independently, e.g., during a brief dual-write window) — the registry's own atomic-registration semantics resolve this; both connectors converge on the same SchemaId. A registry temporarily unreachable during a DDL event — the connector buffers the pending SchemaChange event (bounded by I11's backpressure) and retries registration with the ADR-18 backoff policy rather than dropping it.

17.9 Failure Analysis

A RegistryError::Incompatible on registration routes every event depending on the rejected schema to the DLQ (I10) with the registry's rejection reason in the error trace — never silently dropped, never emitted under the previous schema-id (which would misrepresent the row's actual shape). Blast radius: bounded to the one table/subject whose DDL triggered the rejection; other tables' pipelines are unaffected (per-subject isolation).

Deployment: the registry itself is an external dependency (not deployed by this project); cdc-schema is a client library linked into every connector and sink process.

18. Phase 6 — Kafka Sink: Idempotent Producer & Transactional EOS

18.1 Objectives

Implement cdc-sink-kafka: idempotent-producer delivery as the default (ADR-10), transactional delivery as an opt-in EOS path (ADR-10, I12's sibling for Kafka), and the per-key partitioner matching the router's partitioning contract (ADR-15).

18.2 Detailed Implementation Steps

Implement producer.rs: an idempotent producer (enable.idempotence=true, which forces acks=all, bounded in-flight requests, and unlimited retries per the Kafka producer contract, Required Reading — Narkhede/Shapira/Palino). The broker-assigned producer id (PID) plus per-partition sequence numbers reject duplicate sends within a session — the mechanism behind Design Principle P3's "at-least-once with no within-session duplicates" claim. Implement transactional.rs: a transactional producer keyed by a deterministic transactional.id (<pipeline_id>-<generation>, ADR-27's versioning discipline extended to a runtime identity) so broker-side fencing (KIP-98, Required Reading) correctly retires a zombie instance on restart; bind the offset commit to the same transaction via send_offsets_to_transaction (Wang 2017's engineering answer to Treat 2015's impossibility claim, applied directly — this is I1/ADR-10's exactly-once path). Implement partition.rs: hash the event's key (the source table's primary key, P9/ADR-15) to a partition, matching the router's own partitioning so per-key order survives the hop into Kafka (I3).

18.3 Deliverable

cdc-sink-kafka durably commits a batch either in idempotent mode (default) or transactional mode (opt-in), verified against a live Kafka + Schema Registry docker-compose stack.

18.4 Acceptance Criteria

The kafka_eos.transactional conformance bucket (1,000 transaction-boundary scenarios) shows zero partial transactions visible to an isolation.level=read_committed consumer (fixture kafka-eos-transactional). A 30-minute fault-injection test (broker kill, producer pause, network partition) under EOS configuration shows zero duplicate events at the consumer (fixture kafka-eos-fault-injection). 18.6 Pitfalls

  • A non-unique transactional.id across two producer instances causes the broker to fence one arbitrarily — deterministic, monotonic ids (pipeline_id-generation) are required, never a randomly generated id per restart (which defeats fencing entirely).
  • The consumer-side default isolation.level is read_uncommitted, which sees aborted transactions — EOS without explicitly setting read_committed on every downstream consumer is silent correctness loss disguised as a working pipeline.
  • Producer-id space (a 64-bit broker-side resource) can fragment under a workload with millions of short-lived producer instances — long-lived producers per pipeline, not per-batch, is the intended usage.
  • Tuning max.in.flight.requests.per.connection above 5 silently disables the ordering guarantee idempotence depends on for retries — the idempotent-producer contract caps this at 5 and the sink refuses a higher configured value rather than accepting it silently.

18.7 Performance Concerns

Kafka producer compression defaults to zstd (better ratio than snappy at comparable CPU cost for this workload's payload sizes). Batching (linger.ms=10, batch.size=1MB) trades a small latency tax against throughput; M3/M4's p50/p99 targets are derived assuming this default. Transactional commit latency (M8: ≤ 100 ms p99 at 1 MB batch) is dominated by the two-phase send_offsets_to_transaction + commit_transaction round trip, not by encoding cost.

18.8 Edge Cases

A transaction that spans a producer restart mid-batch (crash between begin_transaction and commit_transaction) — the new producer instance's init_transactions call aborts the prior instance's in-flight transaction as part of fencing, and the reorder buffer's re-emission (I4) supplies the same batch again. A topic with fewer partitions than the router's configured worker count — the sink logs a HotKeyAlert-adjacent warning and workers share partitions rather than silently dropping the excess.

18.9 Failure Analysis

A broker unavailable during commit_batch surfaces as SinkError::Unavailable, retried per ADR-18's backoff policy (100 ms → 60 s, 8 attempts) before DLQ routing (I10) — the offset is never committed for this batch until a retry succeeds, preserving I1. Blast radius: bounded to the sink worker for the affected partition range; other partitions' workers continue independently.

Runbook coverage: broker-unavailable and zombie-fencing scenarios in docs/runbooks/triage.md. Deployment: sink workers are stateless beyond their in-flight batch; a crashed worker restarts and resumes from the last durable offset with no manual intervention.

19. Phase 7 — S3/Iceberg Sink & Transform Chain

19.1 Objectives

Implement cdc-sink-s3-iceberg (atomic per-batch commit, ADR-11/I12; equality-delete representation, ADR-12) and cdc-core::transform (the SMT-style transform chain, P13/ADR-24) exercised end to end against this second, structurally different sink.

19.2 Detailed Implementation Steps

Implement writer.rs: a Parquet writer per partition (default partition spec: day(ts_ms) plus optional bucket(key, N), matching Iceberg's native partitioning idiom, Required Reading — Iceberg reference implementation). Implement equality_delete.rs: for Op::Delete and the pre-image half of Op::Update, author an equality-delete file keyed on the row's primary key (ADR-12's rationale — the writer knows the key, not the row's file position, at CDC time). Implement commit.rs: a single atomic metadata-pointer swap per batch via the catalog's transaction API (I12 — a crash mid-write must never publish a partial snapshot; the swap is the only visibility-changing operation). Implement cdc-core::transform: an ordered Vec<Box<dyn TransformStage>> (§11.7) executed between the schema-registry stage and the codec stage (§3's architecture diagram), providing rename/mask/filter/key-extract stages as the built-in set, mirroring Kafka Connect's SMT framework (Required Reading, Reference Implementations) — every stage pure, stateless, side-effect-free (P13), enforced by the trait's &self receiver (§11.7).

19.3 Deliverable

19.4 Acceptance Criteria

The iceberg.equality_delete conformance bucket (10,000 deletes + 10,000 updates across 100 tables) shows the reader's final state matches source state with deleted rows absent (fixture iceberg-equality-delete). The iceberg.commit_conflict bucket (two concurrent committers on one table, 100 scenarios) shows one commit succeeding and the other retrying without corruption (fixture iceberg-commit-conflict, I12). Sink throughput ≥ 50 MB/s per partition (M9) at 32 KB Parquet row-group size with Snappy compression. The transform chain's rename/mask/filter stages pass a 500-case differential corpus against hand-computed expected output.

19.6 Pitfalls

  • Committing on every event (rather than batching by interval/size) produces a small-file storm — 1,000 partitions committing every second is 86M files/day; the sink batches to a configurable interval (default 60 s) and byte size (default 128 MB), whichever comes first.
  • Equality-delete files are read-time-expensive (every delete file scans against every overlapping data file) — necessary at write time (the writer doesn't know row positions), but requires a separate, regularly scheduled compaction job (not run by this engine, §1's delegation boundary) converting them to position-deletes.
  • Multiple concurrent committers on the same table without single-committer-per-table-per-pipeline discipline (ADR-11) cause a retry storm that can exceed the sink's own throughput in extreme cases.
  • A transform stage that performs I/O (e.g., an external lookup) violates P13 and makes the chain untestable/unreplayable in isolation — the trait signature (&self, no async I/O primitive threaded through) makes this a compile-time-visible smell, not an outright impossibility, so code review remains the final gate.

19.7 Performance Concerns

Parquet writer allocation is bounded by row-group size (32 KB default); Snappy compression is read-optimized (query-time decompression dominates over write-time compression ratio for this workload). The transform chain's per-event cost is O(stages) with no I/O, keeping it off the critical allocation path entirely.

19.8 Edge Cases

A schema change arriving mid-batch for an Iceberg-sinked table — the sink syncs the Iceberg table schema (its own native evolution mechanism) with the CDC source schema before the first write of a new column, or the Parquet write fails fast rather than silently coercing types. A transform stage's filter dropping every event in a batch — commit_batch still runs (an empty commit is valid, advances nothing but consumes no incorrect state).

19.9 Failure Analysis

A commit conflict (concurrent committer detected by the catalog) surfaces as SinkError::Conflict, retried with the batch's data re-validated against the new table snapshot before retry — never blindly reapplied, since the underlying partition spec or schema may have changed between attempts. Blast radius: bounded to the retrying committer; the other committer's snapshot remains valid and readable throughout (I12).

19.10 Operational Notes

Deployment: the sink coordinates with, but never triggers, the operator-scheduled Iceberg compaction job (§1's delegation boundary, restated operationally). Rollback: reverting the transform chain's configuration takes effect on the next batch, no migration required (transforms are stateless, P13).

20. Phase 8 — Offset Durability & Restart Semantics

20.1 Objectives

Implement cdc-offset's three backends (compacted Kafka topic default, ADR-06; Postgres table, ADR-07; embedded Raft, ADR-08) and prove I1/I9/I14 hold across crash-and-restart at every stage boundary in the pipeline.

20.2 Detailed Implementation Steps

Implement kafka.rs: commit producing a keyed record (connector_id → Offset::to_bytes()) to the compacted cdc.offsets topic (§11.1's to_bytes); read projecting the latest record per key from the compacted topic on startup. Implement pg.rs: a cdc_offsets table (connector_id, offset_kind, offset_value, committed_at, generation) with an INSERT ... ON CONFLICT (connector_id) DO UPDATE ... WHERE cdc_offsets.generation <= EXCLUDED.generation guard — the generation check is I9/I14's mechanism made concrete: a lower-or-equal generation write is silently absorbed as a no-op, never regresses the stored offset. Implement raft.rs: a 3–5-node embedded Raft cluster (ADR-08) whose committed log entries are the offset store; failover is Raft leader election, no separate reconciliation step. Wire every backend behind the same commit/read interface so the choice is a deployment-time configuration, not a compile-time fork (ADR-06/07/08 are mutually exclusive per deployment, not per build). Implement the crash-point fuzzer (referenced in §7's methodology) injecting a process kill at each of: after source-read, after sink-ack, after offset-write — and assert the observed consumer-side event set always equals the at-least-once contract's guarantee (§8.7's worked example, generalized).

20.3 Deliverable

A pipeline configured against each of the three offset-store backends survives a scripted 24-hour restart-storm (engine killed and restarted every 60 seconds) with zero events lost.

20.6 Pitfalls

  • Committing the offset before the sink's SinkAck exists is the single most severe bug class this phase exists to prevent — the type-level enforcement in §11.5 makes it hard to write by accident, but a backend implementation that bypasses the Sink::commit_batch return value (e.g., a fire-and-forget async write) reopens the hole silently.
  • A generation counter that resets to zero on container redeploy (rather than persisting alongside the offset) lets a zombie writer overwrite a valid, newer offset — the generation must be read back and incremented, never reinitialized.
  • Raft cluster tail-of-log divergence after a lost-quorum event is rare but real; a per-commit checksum in the offset record lets the read path detect and refuse a divergent tail rather than silently trusting it.
  • The Kafka-backend read path must project the compacted topic correctly — reading a non-compacted view (e.g., before compaction has run) can return a stale offset that looks valid but isn't the true latest.

20.7 Performance Concerns

Offset commits are batched at the same cadence as sink commits (no separate high-frequency write path) — commit frequency is bounded by the router's batching interval (§19.7's linger.ms-style default), not by per-event overhead. The Postgres backend's ON CONFLICT upsert is a single index-keyed row write, O(1) regardless of connector count.

20.8 Edge Cases

Two connector instances for the same connector_id running simultaneously (an operator error, not a supported configuration) — the generation-fencing mechanism (I9/I14) ensures only the higher-generation writer's offsets are honored; the other is effectively fenced without a separate leader-election protocol. An offset-store backend switch (e.g., Kafka → Postgres) mid-deployment — requires an explicit one-time offset migration tool (out of scope for this phase; noted as an operational procedure, not automated).

20.9 Failure Analysis

An offset-store write failure (network partition, broker unavailable) blocks the next batch's offset commit but never the sink commit that already succeeded — the engine retries the offset write with ADR-18's backoff, and on prolonged failure pauses source consumption (I11) rather than proceeding without a durable offset. Detection: offset_commit_lag_ms climbing past an alert threshold. Forensic artifact: the last successfully committed offset plus the pending (uncommitted) SinkAck.

20.10 Operational Notes

Metrics: offset_commit_total{backend}, offset_commit_lag_ms, offset_regression_rejected_total (I9), generation_current. Runbook: docs/runbooks/triage.md covers offset-store unavailability triage across all three backends. Deployment: the offset-store backend is chosen per deployment via config, never mixed within one deployment.

21.1 Objectives

Prove the five schema-change classes (add, drop, rename, type-change, and their combinations) survive end-to-end — source DDL to registry to consumer decode — under continuous churn, closing the loop opened by Phase 5's registration gate (I6) with the source connectors' DDL detection (Phase 1 §13, Phase 3 §15).

21.2 Detailed Implementation Steps

Implement the five change classes per Avro's resolution rules (Required Reading, Avro spec Section 6, P5): column add with default (compatible both ways); column add without default (rejected under FULL, ADR-03); column drop (requires the dropped field to have had a default, per FULL's backward leg); column rename via aliases (§11.3's Field.aliases, I13's union-ordering invariant applies identically); column type-change restricted to Avro-compatible promotions (int→long, float→double, string↔bytes with care).   • A column added without a default cannot satisfy backward compatibility (old data has no value to read) — the connector's DDL-to-schema translation always carries forward an explicit default (NULL or a typed default) rather than omitting it.

21.7 Performance Concerns

21.8 Edge Cases

A DDL applied to a table with no rows yet — registers the schema with no data-plane impact (no in-flight events pending against the old schema to reconcile).

21.9 Failure Analysis

25. Operational Readiness

Metrics (Prometheus exposition, ADR-25): every named counter/gauge in §7's invariant table and §23/§24's threat/failure tables, plus per-phase metrics named in each phase's N.10. Cardinality is bounded deliberately (e.g., reorder_buffer_bytes is aggregated, never labeled per tx_id, §16.10).

Tracing: tracing crate spans (ADR-25) exported via OpenTelemetry; one span per source transaction (Begin→Commit/XID, §13.10/§15.10), child spans per pipeline stage a ChangeEvent passes through, correlated by tx_id end to end.

Structured logging: every log line carries connector_kind, offset, and tx_id where applicable (§12.10) — the minimum context needed to correlate a log line to a specific §7 invariant check.

Dashboards: one per source connector (decode rate, parse-error rate, slot/binlog lag), one per sink (commit latency, DLQ rate, delivery-guarantee-specific metrics), one aggregate (end-to-end p50/p99, §4's M3/M4).

Alerting philosophy: alert on the invariant, not the symptom — e.g., page on slot_lag_bytes > 50 GB (I2's threshold) rather than on "disk usage high" generically, so the alert names the runbook to open.

SLOs: 99.9% monthly availability of the engine process (§4); end-to-end p99 ≤ 1,000 ms (M4) measured over a rolling 5-minute window; zero data loss (I1) as a hard SLO with no error budget.

Incident response: the on-call engineer's first action for any P0 is cdc inspect-dlq (checks for poison-message storms) and the aggregate dashboard's per-stage lag breakdown (localizes the failing stage per §24's failure-mode table).

Named runbooks (docs/runbooks/):

  • R1 — poison-in-dlq.md: triage a DLQ growth alert (FM5); root-cause via the DLQ envelope's error trace; replay via cdc inspect-dlq --replay after the fix.
  • R2 — slot-full-disk.md: triage slot_lag_bytes alert (FM1/T6); confirm the abandoned consumer; DROP_REPLICATION_SLOT; resnapshot (§14).
  • R3 — schema-drift.md: triage a schema-registration rejection (FM3/T3); the ten-scenario recovery playbook from §21.10.
  • R4 — triage.md: the general first-response index, pointing to R1–R3 and to §24's failure table by symptom.

Backup/restore: the engine holds no primary data of its own (source DB and sinks own their data); "backup" here means the offset store's own backup policy (Kafka topic replication factor 3; Postgres backend follows the host Postgres's own backup schedule; Raft follows its own snapshot policy) — restoring the offset store to a point-in-time and resuming is equivalent to a controlled crash-restart (§20).

Deployment topology: one connector process per source database; sink workers scaled independently per partition count (§22.2); no shared mutable state (§1).

Canary/rolling-upgrade/rollback: a new connector version resumes from the same durable offset (Offset's wire format is versioned, ADR-27) — canary a new version on one partition's worker first, verify reorder_out_of_order_total and dlq_writes_total stay flat, then roll the rest. Rollback is symmetric: revert the binary, resume from the same offset.

26. Compatibility & Versioning

Wire compatibility: the ChangeEvent Avro envelope (§17.2) is versioned via the schema registry's own SchemaId; Offset::to_bytes (§11.1) is a tagged CBOR encoding so adding a future offset variant is additive, never wire-breaking for existing variants.

Storage compatibility: the offset-store schemas (Kafka topic value format, Postgres cdc_offsets table shape, §20.2) are versioned independently of cdc-core's SemVer (ADR-27) — a offset-store schema migration is an explicit, documented operational procedure, never implicit.

Schema-evolution policy: FULL compatibility is the default and the floor (P5, ADR-03); a pipeline may opt into a looser mode only via explicit configuration, logged as a deviation from the safe default.

API stability: cdc-core's public traits (SourceConnector, Sink, SchemaRegistry, TransformStage, §11.4–11.7) are the only stable public surface; internal module layouts under crates/*/src/ may change between minor versions.

Migration policy: an offset-store backend switch (§20.8) requires the documented one-time migration procedure, never an automatic silent conversion (a silent conversion risks masking an I9 violation).

Deprecation policy: a deprecated trait method carries a #[deprecated] annotation for one minor version before removal; removal is a major-version (SemVer) event.

SemVer policy (ADR-27): cdc-core's public trait surface follows strict SemVer; all workspace crates version in lockstep so an operator reasons about one number for the whole deployment's compatibility.

Rolling-upgrade guarantees: any two adjacent minor versions of a connector or sink can run simultaneously against the same offset store and schema registry without data loss — verified as part of the canary procedure in §25.

Unit tests: per-module, covering every named function/type in §11 in isolation (parser dispatch, GTID-set arithmetic, Avro union construction).

Integration tests: the docker-compose-backed suite (§10, §12) exercising real Postgres/MySQL/ Kafka/Schema-Registry/MinIO instances — tests/hello_cdc_smoke.rs (§12.5) is the minimal case; each phase adds its own (§13.5, §14.5, …, §22.5).

Property tests: every invariant in §7 has a corresponding property test (I3's ordering property, I4's torn-transaction rejection, I5's HWM-equals-consistent-point, I9's generation-fencing) — listed per-phase in each N.5.

Differential tests: decode-output comparisons against the debezium-pg/debezium-mysql corpora (§13.5/§15.5) and the Confluent-registry compatibility differential (§17.5/§21.4) — the discipline of "match a real reference implementation's output," not just "matches our own model."

Fuzzing (ADR-26): cargo-fuzz targets for every untrusted-input parser (parse_pgoutput, parse_binlog_rows, avro_evolution, reorder_buffer, §10) run nightly for 24h canaries (fuzz.yml), gating the Sealed milestone (Appendix B).

Chaos / fault injection: the jepsen/ harness's nemesis scripts (partition, pause, kill) and checker invariant checkers (§7's methodology) — three named scenarios in §22 (partition_under_ load, sink_election, offset_store_failover).

Deterministic replay: the crash-point fuzzer (§20.2/§20.5) replays captured streams with injected crash points at every stage boundary, deterministically reproducing any failure.

29. Performance Engineering

Methodology: benchmark under criterion (cdc-bench, §10) for micro-benchmarks (parser throughput, Avro encode cost) and the conformance/runner's aggregate mode (§22) for end-to-end targets; profile with perf/heaptrack for allocation and cache-locality analysis, correlating against the M# targets below. Tail-latency analysis uses the full p50/p95/p99 histogram, never an average — a CDC pipeline's operator-visible pain is almost always a tail-latency, not mean-latency, problem.

Allocation analysis: the reorder buffer (§16.7) and the wire-format parsers (§13.7/§15.7) are the two dominant allocation surfaces; both target zero per-event heap allocation below 100 columns, verified via heaptrack (fixture alloc-profile-heaptrack, §22.4).

Lock contention: the reorder buffer's tx_id-sharded map (§16.7) is the only shared-mutable-state hot path; sharding count is tuned to keep contention below a measurable threshold at M1/M2's target throughput.

Cache analysis: the hot-path parser's working set is sized to fit L2 per §4's constraint (≤ 256 KB per relation); the relation/table-map cache (§13.7) is the dominant resident structure.

Syscall overhead: batched I/O at every layer (§22.2) amortizes syscall cost; the Postgres Standby Status Update (10 s cadence, I2) and the MySQL COM_REGISTER_SLAVE (once at connect) are the only fixed-cadence syscalls outside the data path itself.

30. Scalability Analysis

What stays constant: per-event allocation cost (O(1) below 100 columns, §29); registry lookup cost after warm cache (O(1), M6); offset-commit cost per batch (O(1) upsert, §20.7).

What grows, and its Big-O: reorder-buffer memory grows with the largest concurrently open transaction's row count (O(n) in rows, bounded by §4's 512 MB ceiling, spilling beyond it, §16.2); relation/table-map cache grows O(tables) with a small constant per entry (§4: ≤ 4 MB per active table); DLQ storage grows O(poison-rate × time) until operator remediation (§24, FM5).

Named bottlenecks, in order: (1) source database's own log-read rate (the I/O-bound defining property of §4 — no amount of engine tuning moves this ceiling); (2) sink commit rate (Kafka broker throughput, Iceberg catalog commit latency); (3) reorder-buffer lock contention under extreme cross-transaction concurrency (§16.7's sharding mitigates but does not eliminate); (4) schema-registry round trip on a registration cache miss (rare, once-per-DDL, §17.7).

Horizontal scaling: one connector process per source database is the horizontal unit for sources (no further horizontal split within one source's log — the log is inherently sequential); sink workers scale horizontally per partition count (§22.2), bounded by the topic's/table's partition-spec granularity.

Vertical scaling: more cores directly raise sink-worker parallelism (§22.2's N = core count default) and reorder-buffer shard count; it does not raise the source connector's own throughput past the source database's log-read ceiling (§4).

Sharding/partitioning: primary-key-based partitioning (ADR-15) is the sharding key throughout — consistent from the router (§3) through the Kafka partitioner (§18.2) to the Iceberg partition spec (§19.2, bucket(key, N)).

Coordination overhead: the offset store's single-writer-per-connector model (ADR-14) avoids any distributed-consensus overhead on the hot path; the embedded-Raft backend (ADR-08) is the one place consensus overhead is paid, and only for sealed-appliance deployments that chose it.

Practical ceiling and levers beyond it: the practical ceiling is the source database's WAL/binlog generation rate under peak write load (§4, §33); the levers beyond it are read-replica-sourced CDC (streaming from a replica's own logical-decoding-capable copy, trading replication lag for reduced primary load — noted, not built, here) and horizontal sharding of the source database itself (each shard gets its own connector process, a deployment-level scaling strategy requiring no engine change).

31. Mental Models & First Principles

  • MM1 — The log is the source of truth; the table is a cache of it. Compressed insight (Kreps 2013): every "what changed" question is answerable from the log alone; the table only ever answers "what is." Predicts: any design that polls the table for changes (Alternative Architecture §35.2) will miss deletes and intermediate updates. Bug class without it: building a "CDC" system on updated_at polling that silently drops hard deletes. Applied in: §3, §13, Design Principle P1.
  • MM2 — A transaction is a boundary, not a burst of independent rows. Predicts: any component that processes rows one at a time without a matching transaction context will violate I4 the moment two related rows must appear or vanish together. Bug class without it: emitting an Update's new row before its old row has been accounted for, corrupting an aggregate mid-flight. Applied in: §16 (reorder buffer), I4.
  • MM3 — Exactly-once is a property of the sink, not the pipe. Predicts: any claim of "exactly-once" that doesn't name which specific sink property (idempotent key, transactional commit) makes it true is marketing, not engineering (Treat 2015). Bug class without it: assuming a non-idempotent, non-transactional sink is safe under retries, then losing correctness silently under the first network blip. Applied in: §18, Design Principle P3, ADR-05.
  • MM4 — Commit the side effect before the pointer that claims it happened. Compressed insight behind I1: any two-step "do X, then record that X happened" protocol is only crash-safe in that order. Predicts: reversing offset-commit and sink-commit order always produces silent data loss on crash, with no other symptom until the gap is discovered downstream. Bug class without it: the single most common CDC engine bug across every implementation this domain has ever produced. Applied in: §11.5, §20, I1.
  • MM5 — Ordering is a resource you spend, not a property you get for free. Predicts: a system that wants global order pays a partition-count-of-one throughput ceiling; a system that wants throughput must relax to per-key order and push the "did these two different rows race" question downstream (Helland 2016). Bug class without it: promising global ordering to a consumer while fanning out across N partitions for throughput. Applied in: §16, Design Principle P9, §30.
  • MM6 — A schema-compatibility mode is a promise about deployment order, not about data. Predicts: BACKWARD-only compatibility silently breaks a rolling deployment where producers upgrade first; FULL is the only mode that makes "producers and consumers upgrade in any order" true. Bug class without it: choosing BACKWARD because it sounds safer, then breaking production on the next rolling deploy. Applied in: §17, Design Principle P5, ADR-03.
  • MM7 — A snapshot is just a synthetic prefix of the same log, not a different mechanism. Predicts: any design that treats "the historical dump" and "the live stream" as two different code paths will eventually diverge in subtle semantic ways (different null-handling, different type coercion). Bug class without it: a snapshot-emitted row that decodes differently than a streamed row for the same underlying value. Applied in: §3 (fourth architectural property), §14, Design Principle P6.
  • MM8 — Backpressure that isn't visible is backpressure that becomes an outage. Predicts: an unbounded internal queue converts a slow-sink problem (visible as rising lag, cheaply diagnosed) into a memory-exhaustion crash (invisible until it happens, expensively diagnosed). Bug class without it: "just buffer it in memory, we'll catch up later" as an unstated design decision that becomes a 3 a.m. OOM page. Applied in: §16, Design Principle P14, I11.

Debezium made the single decision that most differentiates it from this design: run inside Kafka Connect's task-management runtime rather than as a standalone process, trading operational simplicity (one more moving part, Connect itself) for the entire Kafka Connect ecosystem's tooling (REST management API, existing operator familiarity) — the niche where that wins is any shop already running Kafka Connect for other connectors, where a Connect-native CDC connector is zero marginal operational surface.

Maxwell's Daemon made the opposite bet from Debezium: stay MySQL-only and skip the generalized-connector-framework layer entirely, trading source breadth for a dramatically smaller codebase and simpler mental model — the niche where that wins is a MySQL-only shop that finds Debezium's Kafka-Connect scaffolding and multi-source abstraction layer to be pure overhead for a problem they only have in one dimension.

AWS DMS made the decision to be a managed, source-and-target-matrix service rather than an open-source library — trading configurability and transparency (you cannot read its reorder-buffer source) for zero operational ownership — the niche where that wins is a team already fully committed to AWS that values "no infrastructure to run" over "understand exactly what the pipeline is doing," especially for one-time migrations rather than long-lived streaming pipelines.

Netflix DBLog (Andreakis & Papapanagiotou, Netflix, published at IEEE ICDE 2020) made the decision to replace the REPEATABLE READ-transaction-freeze snapshot (this design's P6, and Debezium's default) with a watermark-based algorithm that never blocks writes and never holds a long-running transaction open — trading a more complex interleaving algorithm for the ability to pause/resume/select which tables to snapshot on the fly, without a write-freezing transaction — the niche where that wins is a large multi-tenant fleet where a long-held snapshot transaction's lock/WAL-retention footprint (this design's own Pitfall §14.6) is operationally unacceptable at scale.

33. Back-of-Envelope Capacity Model

All numbers chain from the System Constraints table (§4).

  1. Ingest bandwidth = 100,000 events/sec (§4 M1) × 1 KB avg event = 100 MB/s sustained per connector — the number every downstream network/NIC provisioning decision starts from.
  2. WAL/binlog retention risk window = 10 GB alert threshold (§4) ÷ 100 MB/s = 100 seconds of consumer downtime before the warning threshold trips; 50 GB page threshold ÷ 100 MB/s = 500 seconds (≈ 8.3 min) before the page fires — this is why I2's 10-second heartbeat matters: it bounds "quiet-table" retention growth to a small multiple of the heartbeat interval, not the full write-rate.
  3. Reorder-buffer memory for the largest transaction = 512 MB ceiling (§4) ÷ 1 KB avg row = ≈ 512,000 rows before spill — chained directly into Phase 4's spill-path design (§16.2).
  4. Per-connector open-transaction map footprint = 4,096 max open txns (§4) × (assume 1 KB average buffered bytes per newly opened, mostly-empty txn) = ≈ 4 MB baseline map overhead before any transaction grows large — small relative to the 512 MB single-transaction ceiling, confirming the map's own bookkeeping is not the memory risk; individual large transactions are.
  5. Iceberg small-file rate = (86,400 seconds/day ÷ 60 s commit interval, §19.6) × 1,000 partitions = 1,440,000 files/day without batching by size; with the 128 MB byte-size floor also applied (whichever triggers first), realistic file count drops by roughly the ratio of average partition write-rate to 128 MB — the reason ADR-11/§19.6 mandate both a time and a size trigger, not time alone.
  6. Snapshot duration for a 1 TB table = 1,000,000 MB ÷ 500 MB/s aggregate (§4 M5) = 2,000 seconds (≈ 33 minutes) at full parallel throughput — chained into §14's operator guidance on monitoring slot lag during long-running snapshots.
  7. Schema-registry cache footprint = (assume 10,000 distinct schema versions across a large fleet) × (assume 2 KB average serialized schema) = ≈ 20 MB registry-client cache — negligible against the 4 MB-per-table memory ceiling multiplied across even a few thousand tables.
  8. DLQ write rate at a pessimistic 100 ppm poison rate = 100,000 events/sec (§4 M1) × 0.0001 = 10 DLQ writes/sec per connector at peak ingest — the number the DLQ alerting threshold (§23 T5) is tuned against; sustained rates meaningfully above this indicate a systemic issue (FM5), not isolated poison messages.
  9. Heartbeat topic overhead = 1 heartbeat event / 10 s (§4) × (assume 10,000 quiet tables in a large fleet) = 1,000 heartbeat events/sec worst case — small relative to the 100,000 events/sec per-connector ceiling (M1), confirming heartbeat overhead never competes meaningfully with real data-plane throughput.
  10. FD budget check = 1,024 FD ceiling (§4) ÷ (1 replication socket + ~4 sink sockets + ~10 log/metric file handles per connector) ≈ headroom for ≈ 68 concurrent logical connections' worth of FDs before the ceiling — confirms the FD budget is not the practical concurrency limit; the reorder-buffer's 4,096-open-txn bound (item 4 above) binds first.

35. Alternative Architectures (Roads Not Taken)

35.1 Trigger-based capture (audit-table triggers / classic Oracle GoldenGate extract)

┌────────────┐  AFTER INSERT/UPDATE/DELETE   ┌──────────────────┐
│ Source table│ ─────────────────────────────▶│ shadow audit table│
└────────────┘        trigger fires            └────────┬─────────┘
                                                          │ polled by
                                                   ┌──────▼────────┐
                                                   │ capture process│──▶ sink
                                                   └────────────────┘

Regime where it wins: a source database with no WAL/binlog-level replication access at all (a locked-down managed-DB tier, or an older engine version lacking logical decoding). Real embodying system: Oracle GoldenGate's classic (trigger-based) capture mode, used before Oracle's integrated (redo-log-based) capture became the default. Why this blueprint rejects it: every trigger fire is an extra write on the primary's hot path (this design's §4 explicitly forbids adding write-path overhead to the source), and a trigger-based audit table has no natural offset model as clean as an LSN/GTID — cursoring through it correctly under concurrent writes is a harder problem than reading an already-ordered log.

35.2 Query-based / polling CDC (timestamp-column watermark polling)

┌────────────┐        SELECT * WHERE           ┌──────────────┐
│ Source table│ ◀──── updated_at > $watermark ──│ poll worker   │──▶ sink
└────────────┘        (repeat on interval)      └──────────────┘

Regime where it wins: a source with no log access whatsoever and no trigger permission either — a REST API or SaaS data source, the common case for many ELT connectors. Real embodying system: Apache Sqoop's incremental (--incremental append/lastmodified) import mode, and the polling-mode connectors in Airbyte/Fivetran for sources without native CDC support. Why this blueprint rejects it: a last_modified watermark cannot see hard deletes at all (a deleted row simply vanishes from the next poll's result set, indistinguishable from "it was never queried"), and cannot see intermediate updates between polls — exactly the two failure modes MM1 names as the reason the log is the right primitive.

35.3 Transactional outbox pattern (application-mediated event emission)

┌────────────────────────────┐  same DB transaction  ┌───────────────┐
│ Application write + outbox │──────────────────────▶│ outbox table  │
│ table insert (one commit)  │                        └──────┬────────┘
└────────────────────────────┘                                │ tailed by
                                                        ┌──────▼────────┐
                                                        │ CDC tailer     │──▶ sink
                                                        │ (reads outbox  │
                                                        │  as if a table)│
                                                        └────────────────┘

Regime where it wins: a greenfield service willing to change its write path, where the event shape itself (not just the row diff) needs to be application-authored rather than inferred from a row's before/after state. Real embodying system: the pattern Debezium itself documents and supports via its "outbox event router" SMT, and the pattern catalogued in Stopford's Designing Event-Driven Systems (Required Reading). Why this blueprint rejects it as the primary architecture: it requires every application write path to be modified and disciplined into using the outbox table, which this project's non-goals explicitly exclude (§1: "does NOT provide application-level dual-write") — this design instead infers events from the log a database already writes, requiring zero application changes.

35.4 Version/watermark-based change tracking (row-version, no event payload)

┌────────────┐  version column bumped   ┌───────────────────┐
│ Source table│ ────────────────────────▶│ change-tracking   │
│ (PK + ver)  │   on every write         │ metadata (PK+ver)  │
└────────────┘                           └─────────┬──────────┘
                                                    │ consumer re-queries
                                                    │ current row by PK
                                             ┌──────▼────────┐
                                             │ consumer's own │──▶ sink
                                             │ SELECT by PK   │
                                             └────────────────┘

Regime where it wins: a consumer that only needs to know which rows changed and can cheaply re-query the source for current state (no need for the actual before/after diff or delete history beyond "this key no longer exists"). Real embodying system: SQL Server's native Change Tracking feature (lighter-weight than SQL Server CDC, tracks only primary-key-plus-version, no row history). Why this blueprint rejects it: it carries no event payload at all — every consumer must re-query the source for current state, which reintroduces read load on the primary this design exists to avoid, and it cannot represent an UPDATE's specific field-level diff, which several of this design's transform-chain stages (§19.2, field-level masking) depend on having.

37. Glossary

  • At-least-once — a delivery guarantee where every event reaches its destination one or more times; the engine's default contract (P3).
  • At-most-once — a delivery guarantee where an event may be lost but never duplicated; rejected as the default (ADR-10).
  • Avro — a binary serialization format with a schema-resolution model (writer schema vs. reader schema) this design's default codec relies on (ADR-03).
  • Backpressure — the propagation of a downstream slowdown to upstream producers via bounded queues, preventing unbounded buffering (I11).
  • Binlog (binary log) — MySQL's write-ahead record of every data-modifying statement; the CDC tap point for MySQL sources (§8.2).
  • ChangeEvent — this design's normalized representation of one row-level mutation, shared across every source and sink (§11.2).
  • Codec — the layer converting a ChangeEvent to/from wire bytes (Avro/JSON, §11.7).
  • Compatibility mode — a schema registry policy (BACKWARD/FORWARD/FULL/etc.) governing which schema changes are accepted (§17.2).
  • Consistent snapshot — a table scan taken at a fixed, LSN-anchored point in time, handed off gap-free to streaming (§14, P6).
  • DDL (Data Definition Language) — schema-changing statements (CREATE/ALTER/DROP); routed to the schema-history topic only (I7, P7).
  • Dead-letter queue (DLQ) — the isolation destination for undecodable or rejected events (P10, I10).
  • Delivery guarantee — the specific contract (AtLeastOnce/ExactlyOnceIdempotent/ ExactlyOnceTransactional) a sink offers (§11.5).
  • Effectively-once — the practical, engineering approximation of "exactly-once" achieved via idempotency or transactionality, since true exactly-once delivery is provably impossible in general (Treat 2015).
  • Equality delete — an Iceberg delete-file representation keyed by column values rather than row position; this design's choice for CDC deletes (ADR-12).
  • Exactly-once — a delivery guarantee where every event reaches its destination exactly one time; a sink-dependent property in this design, never an engine-wide default (P3).
  • Fencing — a mechanism (deterministic transactional id, generation counter) preventing a stale writer instance from corrupting state after a restart (I9, I14, T9).
  • GTID (Global Transaction Identifier) — a (server_uuid, transaction_number) pair identifying a MySQL transaction across topology changes (§8.3).
  • Heartbeat — a periodic synthetic event keeping a replication slot/binlog cursor advancing on quiet tables (I2, P11).
  • High-water-mark (HWM) LSN — the LSN a consistent snapshot is anchored to, matched exactly to the replication slot's consistent_point (I5, P6).
  • Idempotent producer — a Kafka producer mode preventing broker-side duplicate writes within one producer session via producer-id/sequence-number tracking (§18.2).
  • Incremental snapshot — the DBZ-1031 signal-table-driven online resync mechanism, usable without stopping streaming (§14.4).
  • Invariant — a system property (I1…I14) that must hold at every point in execution, enforced and telemetered per §7.
  • LSN (Log Sequence Number) — Postgres's monotonic position marker within the WAL, the basis of the PostgresLsn offset variant (§11.1).
  • Logical decoding — Postgres's mechanism for converting WAL records into a structured, consumer-readable stream via an output plugin (pgoutput, §8.1).
  • Offset — a source-specific position marker (PostgresLsn/MysqlGtidSet) recording how far a connector has consumed (§11.1).
  • pgoutput — Postgres's built-in logical-decoding output plugin, the wire format this design's Postgres connector parses (§8.1).
  • Reorder buffer — the component coalescing per-transaction events and enforcing atomic, ordered emission (§16, I3, I4).
  • Replica identity — a Postgres per-table setting (DEFAULT/FULL/NOTHING) controlling how much of the old row an UPDATE/DELETE carries (§13.4).
  • Replication slot — a Postgres server-side object retaining WAL for a logical-decoding consumer until acknowledged (§8.1, I2).
  • Schema registry — an external service assigning and validating schema versions under a compatibility policy (§17, §11.6).
  • SchemaId — a registry-assigned integer identifying a specific registered schema version (§11.6).
  • SinkAck — the durability acknowledgment returned by Sink::commit_batch, the sole input to the offset-commit call site (§11.5, I1).
  • Single Message Transform (SMT) — Kafka Connect's term for a pure, per-record transform stage; this design's TransformStage trait is the analogue (§11.7, P13, ADR-24).
  • Snapshot — see Consistent snapshot / Incremental snapshot.
  • Standby Status Update — the periodic message a Postgres logical-replication client sends to advance the server's confirmed_flush_lsn (§13.2).
  • TABLE_MAP_EVENT — a MySQL binlog event mapping a table id to its schema for subsequent row events (§8.2).
  • Tombstone — a null-valued Kafka record with a deleted row's key, enabling log-compaction cleanup (P8).
  • Transactional producer — a Kafka producer mode providing atomic multi-partition, cross-restart-safe commits via a fenced transactional.id (§18.2, ADR-10).
  • Transform chain — the ordered sequence of pure TransformStage implementations applied between schema registration and codec encoding (§11.7, P13).
  • WAL (Write-Ahead Log) — Postgres's durable, sequential record of every change, the ultimate source of truth this design reads from (P1, MM1).
