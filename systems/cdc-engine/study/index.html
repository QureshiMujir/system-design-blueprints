31. Mental Models & First Principles

  • MM1 — The log is the source of truth; the table is a cache of it. Compressed insight (Kreps 2013): every "what changed" question is answerable from the log alone; the table only ever answers "what is." Predicts: any design that polls the table for changes (Alternative Architecture §35.2) will miss deletes and intermediate updates. Bug class without it: building a "CDC" system on updated_at polling that silently drops hard deletes. Applied in: §3, §13, Design Principle P1.
  • MM2 — A transaction is a boundary, not a burst of independent rows. Predicts: any component that processes rows one at a time without a matching transaction context will violate I4 the moment two related rows must appear or vanish together. Bug class without it: emitting an Update's new row before its old row has been accounted for, corrupting an aggregate mid-flight. Applied in: §16 (reorder buffer), I4.
  • MM3 — Exactly-once is a property of the sink, not the pipe. Predicts: any claim of "exactly-once" that doesn't name which specific sink property (idempotent key, transactional commit) makes it true is marketing, not engineering (Treat 2015). Bug class without it: assuming a non-idempotent, non-transactional sink is safe under retries, then losing correctness silently under the first network blip. Applied in: §18, Design Principle P3, ADR-05.
  • MM4 — Commit the side effect before the pointer that claims it happened. Compressed insight behind I1: any two-step "do X, then record that X happened" protocol is only crash-safe in that order. Predicts: reversing offset-commit and sink-commit order always produces silent data loss on crash, with no other symptom until the gap is discovered downstream. Bug class without it: the single most common CDC engine bug across every implementation this domain has ever produced. Applied in: §11.5, §20, I1.
  • MM5 — Ordering is a resource you spend, not a property you get for free. Predicts: a system that wants global order pays a partition-count-of-one throughput ceiling; a system that wants throughput must relax to per-key order and push the "did these two different rows race" question downstream (Helland 2016). Bug class without it: promising global ordering to a consumer while fanning out across N partitions for throughput. Applied in: §16, Design Principle P9, §30.
  • MM6 — A schema-compatibility mode is a promise about deployment order, not about data. Predicts: BACKWARD-only compatibility silently breaks a rolling deployment where producers upgrade first; FULL is the only mode that makes "producers and consumers upgrade in any order" true. Bug class without it: choosing BACKWARD because it sounds safer, then breaking production on the next rolling deploy. Applied in: §17, Design Principle P5, ADR-03.
  • MM7 — A snapshot is just a synthetic prefix of the same log, not a different mechanism. Predicts: any design that treats "the historical dump" and "the live stream" as two different code paths will eventually diverge in subtle semantic ways (different null-handling, different type coercion). Bug class without it: a snapshot-emitted row that decodes differently than a streamed row for the same underlying value. Applied in: §3 (fourth architectural property), §14, Design Principle P6.
  • MM8 — Backpressure that isn't visible is backpressure that becomes an outage. Predicts: an unbounded internal queue converts a slow-sink problem (visible as rising lag, cheaply diagnosed) into a memory-exhaustion crash (invisible until it happens, expensively diagnosed). Bug class without it: "just buffer it in memory, we'll catch up later" as an unstated design decision that becomes a 3 a.m. OOM page. Applied in: §16, Design Principle P14, I11.

5. Required Reading

Books

  • Kleppmann, M. — Designing Data-Intensive Applications (O'Reilly, 2017). Ch. 5 (Replication: leader-based log shipping, replication lag) and Ch. 11 (Stream Processing: change-data-capture, event sourcing, log/table duality). Extract: the log-is-the-source-of-truth argument and the derived-data-system framing. Applied in: §3, §14 (Phase 2), Design Principle P1.
  • Narkhede, N., Shapira, G., Palino, T. — Kafka: The Definitive Guide (O'Reilly, 2017). Chapters on producer internals (idempotence, sequence numbers) and Kafka Connect. Extract: the SourceTask/offset-topic model, the idempotent-producer sequence-number contract. Applied in: §18 (Phase 6), ADR-06.
  • Akidau, T., Chernyak, S., Lax, R. — Streaming Systems (O'Reilly, 2018). Ch. 1–3 (watermarks, windows, the vocabulary of unbounded data) and Ch. 5 (exactly-once). Extract: why "exactly-once" means "effectively-once" in practice. Applied in: §18 (Phase 6), Design Principle P3.
  • Stopford, B. — Designing Event-Driven Systems (O'Reilly, 2018). Chapters on event sourcing, derived data, the single-writer principle, message-layer schema evolution. Extract: the transactional-outbox alternative architecture. Applied in: §35 (Alternative Architectures).
  • Petrov, A. — Database Internals (O'Reilly, 2019). Part II, replication chapters (log shipping, WAL mechanics, quorum replication). Extract: why WAL is the natural CDC tap point. Applied in: §8 (Domain Model), §13 (Phase 1).
  • Campbell, L., Majors, C. — Database Reliability Engineering (O'Reilly, 2017). Chapters on backup/replication operational practice, on-call ergonomics. Extract: the runbook discipline applied in Operational Readiness. Applied in: §25 (Operational Readiness).

Papers

  • Kreps, J. (2013). The Log: What every software engineer should know about real-time data's unifying abstraction. LinkedIn Engineering blog. The foundational essay; "the log is the source of truth." Applied in: §2, Design Principle P1.
  • Kreps, J., Narkhede, N., Rao, J. (2011). Kafka: a Distributed Messaging System for Log Processing. NetDB Workshop, 2011. The original Kafka architecture paper. Applied in: §18 (Phase 6), ADR-06.
  • Akidau, T. et al. (2015). The Dataflow Model: A Practical Approach to Balancing Correctness, Latency, and Cost in Massive-Scale, Unbounded, Out-of-Order Data Processing. VLDB 2015. Watermarks and windowing for unbounded streams. Applied in: §16 (Phase 4, ordering discipline).
  • Helland, P. (2015). Immutability Changes Everything. CIDR 2015. The frame for append-only event logs as the right system primitive. Applied in: Design Principle P2.
  • Helland, P. (2016). The Many Faces of Consistency. Communications of the ACM 59(7). The taxonomy behind per-key vs. global ordering. Applied in: Design Principle P9, §16 (Phase 4).
  • Kleppmann, M. (2015). Bottled Water: Real-time integration of PostgreSQL and Kafka. Confluent Engineering Blog. The first practical Postgres-to-Kafka CDC pipeline (via pglogical), ancestor of Debezium's Postgres connector. Applied in: §13 (Phase 1), §32 (Comparative Architecture).
  • Kleppmann, M. (2014). Turning the Database Inside-Out. Strange Loop conference talk. The intellectual case for log-as-primary pre-dating Debezium. Applied in: §2, §35 (Alternative Architectures).
  • Treat, T. (2015). You Cannot Have Exactly-Once Delivery. Industry engineering blog. The vocabulary clarification behind Design Principle P3. Applied in: §18 (Phase 6), Design Principle P3.
  • Wang, G. (2017). Exactly-Once Semantics Are Possible: Here's How Apache Kafka Does It. Confluent Engineering Blog. The engineering answer to Treat's claim — idempotent producer + transactional API. Applied in: §18 (Phase 6), ADR-10.

Reference Implementations

  • Debezium (github.com/debezium/debezium) — debezium-connector-postgres, debezium-connector-mysql, debezium-core (Envelope, SourceInfo, the DBZ-1031 incremental-snapshot signal-table design). Lesson: the consistent-snapshot handshake order. Pitfall not to copy: its JVM GC-pause exposure under back-pressure. Applied in: §13/§14 (Phase 1/2), ADR-01.
  • Maxwell's Daemon (github.com/zendesk/maxwell) — the MySQL-only binlog tailer. Lesson: a minimal binlog-to-JSON pipeline without Kafka Connect's scaffolding, useful as the simplest correct design point. Applied in: §15 (Phase 3), §32 (Comparative Architecture).
  • Apache Kafka / Kafka Connect (github.com/apache/kafka, connect/runtime) — SourceConnector/SourceTask, the compacted offset topic, the Single Message Transform (SMT) framework. Lesson: the transform-chain contract this project's cdc-core::transform mirrors. Applied in: §19 (Phase 7 transform chain), ADR-06/ADR-24.
  • Postgres source (src/backend/replication/logical/{decode,reorderbuffer,snapbuild}.c) — the reference implementation of logical decoding and the in-kernel reorder buffer. Lesson: how the kernel itself buffers uncommitted transactions; pitfall not to copy: it optimizes for kernel memory, not for a bounded client-side heap (I4 differs deliberately). Applied in: §13/§16 (Phase 1/4).
  • wal2json (github.com/eulerto/wal2json) — an alternative logical-decoding output plugin. Lesson: a JSON-emitting cross-reference for validating the pgoutput decoder's semantics. Applied in: §13 (Phase 1), §13.5 fixtures.
  • Apache Iceberg (github.com/apache/iceberg, core/) — manifest/snapshot/equality-delete implementation. Lesson: atomic metadata-pointer swap as the commit primitive. Applied in: §19 (Phase 7).

RFCs / Specifications

  • PostgreSQL Documentation, Chapter 49 — Logical Decoding. Replication slots, CREATE_REPLICATION_SLOT/START_REPLICATION, the pgoutput wire format. Applied in: §13 (Phase 1), §8.1.
  • MySQL Reference Manual, Chapters 5.4.4, 17.1.3, 17.2.1 — Binary Log, GTID-Based Replication, Row-Based Logging. Event types, GTID set string format. Applied in: §15 (Phase 3), §8.2.

  • Apache Kafka KIP-98 (Exactly-Once Delivery and Transactional Messaging) and KIP-618 (Exactly-Once Source Connectors). The transactional-producer/consumer contract. Applied in: §18 (Phase 6), ADR-10.

Glossary (§37) · 40 terms · site-wide glossary

At-least-once
a delivery guarantee where every event reaches its destination one or more times; the engine's default contract (P3).
At-most-once
a delivery guarantee where an event may be lost but never duplicated; rejected as the default (ADR-10).
Avro
a binary serialization format with a schema-resolution model (writer schema vs. reader schema) this design's default codec relies on (ADR-03).
Backpressure
the propagation of a downstream slowdown to upstream producers via bounded queues, preventing unbounded buffering (I11).
Binlog (binary log)
MySQL's write-ahead record of every data-modifying statement; the CDC tap point for MySQL sources (§8.2).
ChangeEvent
this design's normalized representation of one row-level mutation, shared across every source and sink (§11.2).
Codec
the layer converting a ChangeEvent to/from wire bytes (Avro/JSON, §11.7).
Compatibility mode
a schema registry policy (BACKWARD/FORWARD/FULL/etc.) governing which schema changes are accepted (§17.2).
Consistent snapshot
a table scan taken at a fixed, LSN-anchored point in time, handed off gap-free to streaming (§14, P6).
DDL (Data Definition Language)
schema-changing statements (CREATE/ALTER/DROP); routed to the schema-history topic only (I7, P7).
Dead-letter queue (DLQ)
the isolation destination for undecodable or rejected events (P10, I10).
Delivery guarantee
the specific contract (AtLeastOnce/ExactlyOnceIdempotent/ ExactlyOnceTransactional) a sink offers (§11.5).
Effectively-once
the practical, engineering approximation of "exactly-once" achieved via idempotency or transactionality, since true exactly-once delivery is provably impossible in general (Treat 2015).
Equality delete
an Iceberg delete-file representation keyed by column values rather than row position; this design's choice for CDC deletes (ADR-12).
Exactly-once
a delivery guarantee where every event reaches its destination exactly one time; a sink-dependent property in this design, never an engine-wide default (P3).
Fencing
a mechanism (deterministic transactional id, generation counter) preventing a stale writer instance from corrupting state after a restart (I9, I14, T9).
GTID (Global Transaction Identifier)
a (server_uuid, transaction_number) pair identifying a MySQL transaction across topology changes (§8.3).
Heartbeat
a periodic synthetic event keeping a replication slot/binlog cursor advancing on quiet tables (I2, P11).
High-water-mark (HWM) LSN
the LSN a consistent snapshot is anchored to, matched exactly to the replication slot's consistent_point (I5, P6).
Idempotent producer
a Kafka producer mode preventing broker-side duplicate writes within one producer session via producer-id/sequence-number tracking (§18.2).
Incremental snapshot
the DBZ-1031 signal-table-driven online resync mechanism, usable without stopping streaming (§14.4).
Invariant
a system property (I1…I14) that must hold at every point in execution, enforced and telemetered per §7.
LSN (Log Sequence Number)
Postgres's monotonic position marker within the WAL, the basis of the PostgresLsn offset variant (§11.1).
Logical decoding
Postgres's mechanism for converting WAL records into a structured, consumer-readable stream via an output plugin (pgoutput, §8.1).
Offset
a source-specific position marker (PostgresLsn/MysqlGtidSet) recording how far a connector has consumed (§11.1).
pgoutput
Postgres's built-in logical-decoding output plugin, the wire format this design's Postgres connector parses (§8.1).
Reorder buffer
the component coalescing per-transaction events and enforcing atomic, ordered emission (§16, I3, I4).
Replica identity
a Postgres per-table setting (DEFAULT/FULL/NOTHING) controlling how much of the old row an UPDATE/DELETE carries (§13.4).
Replication slot
a Postgres server-side object retaining WAL for a logical-decoding consumer until acknowledged (§8.1, I2).
Schema registry
an external service assigning and validating schema versions under a compatibility policy (§17, §11.6).
SchemaId
a registry-assigned integer identifying a specific registered schema version (§11.6).
SinkAck
the durability acknowledgment returned by Sink::commit_batch, the sole input to the offset-commit call site (§11.5, I1).
Single Message Transform (SMT)
Kafka Connect's term for a pure, per-record transform stage; this design's TransformStage trait is the analogue (§11.7, P13, ADR-24).
Snapshot
see Consistent snapshot / Incremental snapshot.
Standby Status Update
the periodic message a Postgres logical-replication client sends to advance the server's confirmed_flush_lsn (§13.2).
TABLE_MAP_EVENT
a MySQL binlog event mapping a table id to its schema for subsequent row events (§8.2).
Tombstone
a null-valued Kafka record with a deleted row's key, enabling log-compaction cleanup (P8).
Transactional producer
a Kafka producer mode providing atomic multi-partition, cross-restart-safe commits via a fenced transactional.id (§18.2, ADR-10).
Transform chain
the ordered sequence of pure TransformStage implementations applied between schema registration and codec encoding (§11.7, P13).
WAL (Write-Ahead Log)
Postgres's durable, sequential record of every change, the ultimate source of truth this design reads from (P1, MM1).
