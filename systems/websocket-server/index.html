In one paragraph

A WebSocket server keeps one TCP connection open between a client and your process as a persistent two-way channel, reusing HTTP's Upgrade step so it passes the same proxies and firewalls (§2). This design builds RFC 6455 in Rust with no external WebSocket-protocol crate: the HTTP Upgrade handshake, the binary frame codec, message reassembly, Ping/Pong and the close handshake, plus RFC 7692 compression and TLS through rustls (§1). It is checked against the external Autobahn|Testsuite (§1, ADR-17). It ships as one binary, one process per host, cloned behind an L4 load balancer (§1). Its users are systems engineers building protocol mastery (§1), so the point is mastery, not shipping speed (ADR-03).

The problem, concretely

HTTP's baseline is a stateless request/response model (§5), and the earlier answers to a persistent two-way channel (long-polling, "Comet" hacks) were ad hoc (§2). After WebSocket's Upgrade step the socket carries binary frames instead of HTTP (§3 Handshake).

That stream is where the naive approach breaks. The first mistake is assuming one read() returns exactly one frame. TCP delivers arbitrary chunks, so a parser written that way fails as soon as a frame is split (MM1, §14.6). A second mistake is treating a frame and a message as the same thing. A peer may fragment any message at any time, so code that expects one recv() per message breaks (MM3). A third is trusting the length field. A crafted 64-bit length near u64::MAX can wrap a buffer offset or trigger an allocation abort (P1, P12, T3). The fourth is letting buffers grow. A slow client that never reads can make the server buffer without limit, and one stalled client can take the whole process down (P3, FM-4). The blueprint's own arithmetic shows how fast that adds up: a full 256-frame queue of 4 KiB frames is 1 MiB per connection, which is 48.8 GiB at 50,000 connections (§32 item 8). The last is waiting forever for a peer to answer a Close. A hung peer then holds server resources indefinitely (MM5).

How it works, end to end

Follow one connection through the boxes of §3's diagram. Each box is a file under src/:

 TCP LISTENER -> TLS (opt.) -> HANDSHAKE -> CONNECTION task (one per socket)
 main.rs         tls.rs        handshake.rs
 read half:  FRAME PARSER -> REASSEMBLER -> CONTROL/CLOSE -> APPLICATION (echo)
             frame/parser.rs reassembly.rs  control.rs, close.rs
             EXTENSIONS (deflate): between the wire and the reassembler / serializer
 write half: SERIALIZER -> BACKPRESSURE QUEUE (bounded) -> single writer -> socket
             frame/serializer.rs  backpressure.rs
 METRICS / TRACING: metrics.rs
  1. Listener and TLS. main.rs accepts a TCP connection and spawns one tokio task for it. From there every byte is attacker-controlled (§3, ADR-10). For wss://, tls.rs runs the rustls handshake first, so everything after it sees only plaintext (§3, P9, §21).
  2. Handshake. handshake.rs parses the HTTP request with httparse, checks Connection: Upgrade, Upgrade: websocket and version 13, computes Sec-WebSocket-Accept and writes the 101 response (§13.2, ADR-18). A bad request gets 400 (426 for the wrong version) and a close (§13.2, §13.9).
  3. Connection. connection.rs owns the socket for its life and splits it into a read half and a write half, and the write half moves into a separate writer task (§18.2, I11).
  4. Frame parser and reassembler. frame/parser.rs turns bytes into a FrameHeader plus a borrowed payload slice, or says it needs more bytes (§14.2, §11). reassembly.rs glues fragments of one Text or Binary message together, and control frames bypass it (§3, I8, §16.2 step 5).
  5. Control and close. control.rs answers Pings and close.rs runs the close state machine (§17.3). Close code and reason are the only state that outlives the socket (§3).
  6. Extensions. extensions/deflate.rs sits between the wire and the reassembler and serializer, and RSV1 means "compressed" only if it was negotiated (§3, P11).
  7. Application. echo_server.rs is the reference application, and the codec has no echo logic (§3, §19.1).
  8. Serializer and queue. frame/serializer.rs writes unmasked frames and hands the bytes to one bounded queue (backpressure.rs), never to the socket (§15.2 steps 3 and 6). The single writer task is the only thing that touches the write half (§3, ADR-11).

metrics.rs exports the counters, and tracing opens a span per connection and per frame (§3, ADR-16, §24).

The core ideas

The handshake: proving the server speaks WebSocket (§13, I1)

The client sends a 16-byte one-time value (a nonce), base64-encoded, as Sec-WebSocket-Key (§36). The server appends a fixed constant, hashes the result with SHA-1, base64-encodes the digest and returns it as Sec-WebSocket-Accept (§8 steps 2 and 4, §13.2 step 4). The constant, 258EAFA5-E914-47DA-95CA-C5AB0DC85B11, is the GUID (§8, §36).

The result depends on the key and nothing else (I1). The acceptance test is the RFC's own example: the key dGhlIHNhbXBsZSBub25jZQ== must give exactly s3pPLMBiTxaQ9kYGzzhZRbK+xOo=, with no tolerance (§13.4). The state goes Connecting, Upgrading, Open (§13.1), and a bare \n line end is rejected (§13.6).

The frame: a small binary header, a mask and a pull-based parser (§8, §14)

Every frame starts with two bytes. The first holds FIN (last frame of a message), three reserved bits (RSV1–3) and a 4-bit opcode. The second holds the MASK bit and a 7-bit length (§8). That 7-bit field is a switch. The values 0–125 are the length itself, 126 means the next 2 bytes hold a big-endian 16-bit length, and 127 means the next 8 bytes hold a 64-bit length whose top bit must be 0 (§8). Client frames then carry a 4-byte masking key, and the payload is XORed with it, byte i with key byte i mod 4 (§14.2 steps 5 and 7). Masking is not encryption. The key travels in plaintext, and its only job is to defeat caching proxies that react to byte patterns (MM2, T7).

Wire bytes (§8's worked example, "Hi") Meaning
81 FIN=1, opcode 0x1 (Text)
82 MASK=1, length 2
37 FA 21 3D the masking key
7F 93 48 69 ("Hi") XOR the key: 48^37=7F, 69^FA=93

Direction is fixed. Client frames must have MASK=1 (I2), and server frames never do (I3). The send path FrameSink::send_frame has no mask-key parameter, which §15.2 step 3 says makes a masked server frame a compile error, but the FrameHeader it takes still has masked and mask_key fields (§11).

The parser is a pull-based state machine. It is a pure function from the bytes so far to one of Incomplete { needed }, Frame(header, payload) or ProtocolError (§11, §14.3). If the buffer is short it returns Incomplete and is called again with more bytes (§14.2 step 6). A frame split across 2, 3 or 7 reads must give the identical header to the frame parsed whole (§14.4). Before it allocates anything, the parser checks the decoded length against the §4 ceilings (§14.2 step 4, P1).

The blueprint contradicts itself on its malformed-input example. §8 says the bytes 81 FE 00 7E ... are a client frame with the MASK bit unset, which should trigger I2. But §8's own header layout puts MASK in the top bit of the second byte, and FE = 1111 1110 has that bit set (MASK=1, length code 126), so these bytes are a masked frame (§8, I2).

Fragmentation: messages are not frames (§16, MM3)

A message may arrive as several frames. A Text or Binary frame with FIN=0 starts one. Continuation frames (opcode 0x0) extend it. The frame with FIN=1 ends it (§16.2, §8). The Reassembler keeps an active_opcode and a buffer (§11). A three-step trace of the blueprint's interleaving test (§16.4):

  1. Text frame, FIN=0: set active_opcode, append the payload, check the running size (§16.2 step 1).
  2. A Ping arrives mid-message: it goes straight to control.rs, leaves active_opcode and the buffer untouched, and its Pong is sent before the message completes (P7, I14, §16.2 step 5).
  3. Continuation frame, FIN=1: validate the text as UTF-8, clear active_opcode, deliver the whole message (§16.2 step 4).

The size check runs after every fragment, not once at the end (I9, ADR-13). The same goes for UTF-8 validity, which is checked incrementally so a bad message gets Close 1007 early (ADR-15, I12). A continuation with no open message, or a new data frame while one is open, is a protocol error and gets Close 1002 (I5, I8, §16.9). A message sent as one frame (FIN=1, nothing open) skips the buffer (§16.2 step 3).

Control frames and the close handshake: every wait has a clock (§17)

Ping, Pong and Close are control frames. Their payload is at most 125 bytes (I6, §4). Every Ping gets exactly one Pong with the identical payload (I14). The server also pings first: every 30 seconds, and if no Pong comes within 90 seconds it force-closes and records code 1006 locally (§17.2 step 3, §4, I13, ADR-19).

The connection state machine has six states: Connecting, Upgrading, Open, ClosingLocal, ClosingRemote, Closed (§11). The close handshake runs in four steps (§17.2 steps 4–7):

  1. Receive a Close: check the status code (I7), enter ClosingRemote, and echo a Close with the same code (or 1000 if the peer sent none).
  2. Send a Close: enter ClosingLocal and start a 5-second timer (§4).
  3. Receive the peer's echo: enter Closed, cancel the timers and close the TCP socket.
  4. Timer fires first: force the TCP shutdown and record 1006 locally.

Step 4 exists because "wait for the peer" is not a valid end state (MM5, P10). P14 says each WsError variant maps to exactly one close code; §11's comments give, for example, 1002 for protocol violations, 1007 for bad UTF-8 and 1009 for oversized messages (P14, §11).

One writer, one bounded queue (§18, ADR-11, ADR-12)

All outbound frames go into a single bounded channel of 256 frames, and one task owns the socket's write half (§4, P5, §18.2). This rules out frame interleaving by construction, because the write half is moved into the writer task at connect time (P5, I11).

When the queue is full the server disconnects that connection instead of buffering more (ADR-12, §18.2 step 7), and only that connection is affected (§18.9). The blueprint frames this as deciding who pays for a slow consumer: unbounded buffers only move the out-of-memory failure downstream (MM4).

permessage-deflate: the same bits, a different meaning (§20, P11)

The client may offer compression in Sec-WebSocket-Extensions; the server may accept a subset of the offered parameters, never invent others (§20.2 steps 1 and 2). If it was agreed, RSV1 means the payload is compressed; if not, any set RSV bit is a protocol error (P11, I4, MM6). The decompressed size, not the compressed wire size, is checked against the same max_message_size while decompressing, so a small compressed payload that expands to a huge size is stopped mid-stream with Close 1009 (§20.2 step 6, §20.9, T6). Whether the compression window resets between messages follows the negotiated no_context_takeover flags (§20.2 step 5).

The trade-offs — where engineers disagree

Hand-roll the protocol (ADR-03)

Chosen: hand-rolled from RFC 6455, because the project's goal is protocol mastery, not the fastest path to shipping (§9). Rejected: depend on tungstenite (§9). When the rejected choice is right: in a production service where correctness per hour outweighs pedagogy (§9). The design still uses tungstenite as a dev-only differential-test oracle, never as a runtime dependency (§26).

One async task per connection (ADR-10)

Chosen: a tokio task per connection, since OS threads cap concurrency near 10k because of per-thread stack memory (§9). Rejected: OS thread-per-connection (§9). When the rejected choice is right: CPU-bound handlers that need blocking syscalls and full OS scheduling isolation (§9).

Disconnect on queue overflow (ADR-12)

Chosen: a bounded channel of 256 frames, then disconnect the slow peer, so one slow consumer cannot exhaust memory (§9, §4, P3). Rejected: unbounded buffering (§9). When the rejected choice is right: short-lived batch jobs with a known small total message count (§9).

Check size per fragment (ADR-13)

Chosen: an incremental check during reassembly, which rejects an oversized message before the full buffer is allocated (§9, P6). Rejected: a single check after the whole message is reassembled (§9). When the rejected choice is right: when max_message_size is so small that early rejection adds no measurable benefit (§9). The failure it guards against is FM-2 (P6, §23).

Compression: build it, but measure before enabling (ADR-08)

Chosen: implement permessage-deflate in Phase 8, because the Autobahn compression test classes need it and real deployments are bandwidth-constrained (§9). Rejected: omit it entirely (§9). When the rejected choice is right: latency-sensitive small-message workloads where deflate CPU cost exceeds the bandwidth saved (§9). The blueprint says §32 item 3 motivates measuring before a fleet-wide enable: 48 KiB instead of 16 KiB per connection, 2.34 GiB at 50,000 (§32 item 3, §20.7).

TLS inside the process (ADR-09)

Chosen: in-process rustls, which keeps wss:// self-contained (§9). Rejected: terminate TLS at a reverse proxy such as nginx or Envoy (§9). When the rejected choice is right: production fleets that already run a proxy fleet for certificate rotation and ALPN (§9).

Masking speed: scalar loop first (ADR-07)

Chosen: a scalar byte loop, with a word-at-a-time fallback measured at the M-table gate, which is portable and fast enough for the §4 targets (§9). Rejected: SIMD intrinsics (§9). When the rejected choice is right: once p99 CPU per connection is the bottleneck above about 50k msgs/sec (§9, M7). The design's own model puts masking at about 0.5% of one core at 10,000 msgs/sec (§32 item 5).

Roads not taken (§34, §35)

Thread-per-connection (§34 alt 1) wins at moderate connection counts (up to a few thousand) with CPU-bound handlers that need blocking calls. Apache mpm_prefork/mpm_worker and Java servlet containers work this way. It loses here because per-thread stack memory (typically 1–8 MiB) caps concurrency far below the 50,000-connection target (§34, §4).

Single-threaded event loop (§34 alt 2) wins when the workload is mostly I/O wait. Node.js ws and the Redis core loop do this. It loses here because aggregate throughput is capped at one core's masking and compression capacity (§34, M7, M10).

Actor model (§34 alt 3) wins when supervision trees, hot reload and let-it-crash isolation are first-class needs. Phoenix Channels on Erlang/OTP do this. It loses here because Rust ownership already isolates each connection (I11), and this scope is a single-application server (§34).

Deferred features (§35) each wait for a trigger: subprotocol negotiation (§13) for a client that needs it, HTTP/2 bootstrapping (§21) for HTTP/2-only load balancers, the Autobahn compression corpus as a CI gate (§26) for deflate becoming default-on, and horizontal sharding (§29) for an instance nearing the §4 50,000-connection ceiling (§35).

What must never be false

  • I1: the accept value is a pure function of the client key. Noticed by a diff against handshake_vectors.json; counter handshake_accept_mismatch_total.
  • I2: every client-to-server frame has MASK=1. Noticed by a bit check on the second byte; unmasked_client_frame_total.
  • I3 and I11: no server frame has MASK=1; one task holds the write half. §7 calls both compile-time guarantees (type, ownership) with no telemetry; I3 adds a serializer debug-assert.
  • I4: RSV1–3 are zero unless an accepted extension owns that bit. Noticed by a bit check after the negotiation lookup; reserved_bits_violation_total.
  • I5 and I8: a continuation frame only follows an unfinished data frame, and no new data message starts while one is open (control frames excepted). Noticed by an opcode/state check in feed; fragmentation_violation_total for both.
  • I6: control-frame payload is at most 125 bytes. Noticed by a length check before the payload is read; control_frame_too_large_total.
  • I7: close status codes are registered or in the 3000–4999 application range. Noticed by a range lookup; invalid_close_code_total.
  • I9: a reassembled message never exceeds max_message_size. Noticed by a running-total comparison per fragment; oversized_message_total.
  • I10: every accepted connection eventually reaches Closed. Noticed by state-machine exhaustiveness and the gauge connections_stuck_gauge, which should be 0.
  • I12: a Text message is valid UTF-8 before it reaches the application. Noticed by the incremental validator; invalid_utf8_total.
  • I13: a connection idle past 3 times the Ping interval is force-closed. Noticed by timer expiry; idle_timeout_disconnect_total.
  • I14: each Ping gets exactly one identical-payload Pong, sent before further data from that peer is processed. Noticed by a reply-ordering assert in tests (fragmentation.rs); ping_pong_latency_histogram.

What breaks in production

FM-2: memory grows under fragmented-message load. A per-connection memory gauge trends up. The cause is the I9 check applied only after completion, a regression of ADR-13. There is no automatic recovery, since this is the failure being guarded against: roll back and redeploy. The forensics are a heap profile correlated with oversized_message_total (§23).

FM-3: connections stuck in Upgrading. connections_stuck_gauge stays above 0. The root cause is a missing or misconfigured handshake timeout (T8). The timeout should force-close, and if the gauge does not clear, an operator restarts the instance (§23). No §4 row gives that timeout a value, and §13's steps contain none, although T8 points there (T8, §4, §13.2).

FM-5: Ping timeouts during large uploads. ping_pong_latency_histogram p99 spikes. The cause is P7 violated, with control frames queued behind data reassembly. There is no automatic recovery: roll back. A timestamp trace of frame arrival against Pong-sent is the forensic aid (§23).

FM-6: a higher-than-baseline rate of close code 1006. The cause is a network partition, a peer crash, the 5-second close timeout firing legitimately, or a bug; close_code_histogram shows it. The forced shutdown is the designed fallback, and the operator tells a network issue from a server bug (§23, §17.9, §24 runbook (c)).

FM-7: half-open connections exhaust file descriptors or memory. idle_timeout_disconnect_total stays flat while the connection count grows. The cause is I13 not firing, or a misconfigured Ping interval (P13). Recover by closing idle connections through an admin endpoint (§23, §24).

FM-9: a decompression bomb succeeds. Memory spikes with a single connection's inbound compressed frames. The cause is the T6 guard missing or checking the compressed size rather than the decompressed size. Kill the connection and patch the check. The compressed-versus-decompressed ratio log is the forensic aid (§23, §20.9).

Threats worth knowing (§22):

  • T3, integer-overflow misparse from a crafted 64-bit length, is stopped by checking the length against available bytes and the §4 ceilings (P12). Close 1002; oversized_length_field_total.
  • T4, a fragmentation bomb of millions of tiny continuation frames, is stopped by the per-fragment check (ADR-13). Close 1009; oversized_message_total.
  • T6, a decompression bomb, is stopped by the streaming size check on decompressed bytes (§20.9). Close 1009; decompression_bomb_rejected_total.
  • T8, slow-loris connection exhaustion by starting handshakes and never finishing, is met by a handshake-phase timeout that is distinct from the post-Open idle timeout (I13). The detection is timer expiry; handshake_timeout_total.

The blueprint disagrees with itself on four of these numbers; both sides are given, unresolved:

  • Connection ceiling. §4, §21.2, §29 and §32 use 50,000 connections per instance, while M8 and the Phase 6 gate sustain 10,000 (§28, §18.4), and the comparative table gives this design's ceiling as "~10k conns/instance @ M8 target" (§31).
  • What limits it. §29 names per-connection memory as the first ceiling, around 50k on an 8 GiB instance, but §32 item 2 puts 50,000 plain connections at 781 MiB, "comfortably within" 8 GiB, and item 3 says 2.34 GiB "still fits" (§29, §32 item 2, §32 item 3).
  • The 50 µs target. §4 scopes it to the round trip "parse+dispatch+serialize", §14.4 to "parse+dispatch", and M3 to "frame parse latency" only (§4, §14.4, §28).
  • The 64 MiB serializer test. §15.4 and M5 serialize a 64 MiB payload, which §15.4 calls "the §4 message-size ceiling", but §4 also caps a single frame at 16 MiB and rejects larger ones with 1009 (§15.4, M5, §4).

How it compares

  • tungstenite-rs chose to be fully I/O-agnostic: a pure Read/Write state machine with no bundled runtime. That is right when you must embed WebSocket support in an existing custom event loop instead of adopting tokio (§31).
  • uWebSockets (C++) chose hand-managed memory and a custom epoll loop. That is right in extreme-throughput regimes (millions of messages per second per core), where its authors were willing to trade away the overhead Rust's safety guarantees add (§31).
  • ws (Node.js) chose a single-threaded event loop with garbage-collected memory. That is right when the rest of the stack is already Node.js and one runtime and one deploy artifact outweigh raw per-core throughput (§31).
  • python-websockets chose one asyncio coroutine per connection. That is right when development speed and Python ecosystem integration, for example ML-serving stacks, matter more than raw throughput (§31).

Questions to test yourself

  1. Trace exactly what happens, state by state, if a Ping frame arrives as the 3rd byte of a 50-fragment Text message's 27th fragment. — Hint: §16.2 step 5 and I14, then §17.2 step 1.
  2. If max_message_size were checked only after full reassembly instead of incrementally, what specific attack becomes possible that ADR-13's chosen approach prevents? — Hint: T4 and FM-2.
  3. Walk through why a close-handshake timeout is necessary even though RFC 6455 defines a clean bidirectional close sequence — what specifically can go wrong without it? — Hint: MM5, T11 and §17.2 step 7.
  4. Explain the exact interaction between the single-writer invariant (I11) and the bounded backpressure queue (ADR-12) — could either exist without the other and still prevent frame interleaving? — Hint: §18.2 steps 1–2 and §18.9; compare the "violating it" sentences of P3 and P5.
  5. Trace the complete lifecycle of a connection that never sends a single WebSocket frame after a successful handshake, until it is finally cleaned up — which invariant and which timer is responsible, and what is the maximum time it can linger? — Hint: I13, §4 and §17.4.

If you only remember three things

Every length is checked before it is trusted (P1), every buffer has a ceiling (I9, ADR-12), and every wait for a peer has a timeout (I13, P10, MM5). A message can span many frames, and RSV1's meaning depends on what was negotiated (MM3, MM6). Exactly one task writes to a socket, and the design makes violating that structurally impossible (I11, ADR-11).

Words used here

  • Frame: one wire unit with a small header and a payload; the atom the parser works on (§36).
  • Message: the logical unit an application sends, possibly made of many frames (MM3, §36).
  • Opcode: the 4-bit field that says what kind of frame this is (§8).
  • Fragmentation: splitting one message across frames (§36, §16).
  • Control frame: Ping, Pong or Close; at most 125 bytes and never fragmented (§36, I6).
  • Masking key: the 4-byte value a client XORs into its payload; not a secret (§36, MM2).
  • Handshake: the HTTP/1.1 Upgrade exchange that turns a TCP connection into a framed one (§36).
  • GUID (magic string): the fixed constant appended to the client key before hashing (§36, §8).
  • RSV1–3: reserved header bits that a negotiated extension may claim (I4, §36).
  • Close code: the 16-bit status in a Close frame that says why the connection ended (§36, §11).
  • Backpressure: slowing or stopping a producer when its consumer cannot keep up (§36, P3).
