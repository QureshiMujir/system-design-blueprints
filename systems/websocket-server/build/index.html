✅ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the crate skeleton, the error taxonomy, the opcode/header types, and a TCP listener stub that accepts and immediately closes a connection — proving the module graph links before any protocol logic exists.

Deliverable

A compiling binary that accepts a TCP connection on a configurable port and closes it immediately; Opcode, WsError, FrameHeader, ConnectionState types exist and are unit tested for exhaustiveness (every enum variant has at least one test referencing it).

Acceptance
  • cargo build --release exits 0 with zero warnings under #![deny(unsafe_code)].
  • cargo test --lib passes ≥ 8 unit tests covering all four skeleton types.
  • A raw nc localhost <port> connection is accepted and closed within 50 ms (manual smoke test, not yet in tests/).
  • WsError has exactly 9 variants, each with a documented close-code mapping comment.
Fixtures

tests/conformance/frame_vectors.json — created empty (schema only: {header, bytes, expect} per row) in this phase; populated starting Phase 2 (§14.5).

Pitfalls
  • Forgetting #[non_exhaustive] considerations on WsError — adding a variant later is a breaking change for downstream matchers; document this now (see §25).
  • Binding to 0.0.0.0 by default in a skeleton and forgetting to make it configurable before Phase 9's TLS work needs a specific bind address.

✅ Phase 1 — HTTP Upgrade Handshake §13

Objectives

Implement the full RFC 6455 §4.2 handshake: parse the client's HTTP/1.1 Upgrade request, validate every required header, compute Sec-WebSocket-Accept, and write the 101 Switching Protocols response, transitioning ConnectionState::Connecting → Upgrading → Open.

Deliverable

src/handshake.rs with parse_request, compute_accept_key, build_response — fully testable without a live socket via in-memory byte slices.

Acceptance
  • compute_accept_key("dGhlIHNhbXBsZSBub25jZQ==") returns exactly "s3pPLMBiTxaQ9kYGzzhZRbK+xOo=" (the RFC 6455 §1.3 worked example) — byte-exact match, no tolerance.
  • handshake_vectors.json (≥10 cases: valid, missing key, wrong version, malformed base64, missing Upgrade header) all pass.
  • Handshake latency p50 ≤ 1 ms per §4 (measured in benches/).
  • Invalid handshake never advances ConnectionState past Upgrading.
Fixtures

tests/conformance/handshake_vectors.json — populated with the RFC 6455 §1.3 worked example plus ≥9 negative cases.

Pitfalls
  • Case-sensitivity bugs: Upgrade/upgrade header name comparison must be case-insensitive per RFC 7230 §3.2, but header values like websocket are also case-insensitive per RFC 6455 §4.2.1 — conflating the two rules is a common bug.
  • Trailing CRLF handling: httparse expects \r\n\r\n terminator; a client sending bare \n is technically noncompliant but some browsers historically tolerated it — decide and document the stance (this blueprint: strict, reject).
  • Forgetting the subprotocol-negotiation non-goal (PhaseDeferred("§13")) and accidentally echoing back Sec-WebSocket-Protocol from the request — must not happen in v1.

✅ Phase 2 — Frame Parser (Decode Path) §14

Objectives

Implement the RFC 6455 §5.2 frame-header state machine: decode FIN/RSV/opcode, MASK and the three payload-length encodings, the masking key, and unmask the payload — returning Incomplete, Frame, or ProtocolError per read.

Deliverable

src/frame/parser.rs with a FrameParser exposing parse(&mut self, buf: &[u8]) -> ParseOutcome — no I/O inside; pure function of bytes in, outcome out.

Acceptance
  • All rows of frame_vectors.json (≥30 cases spanning every opcode, all 3 length encodings, masked/unmasked, RSV-set) parse to the exact expected FrameHeader or exact expected WsError variant.
  • Parsing a frame split across 2, 3, and 7 separate read()-sized chunks produces the identical FrameHeader as parsing it whole (round-trip in roundtrip.json).
  • p50 parse+dispatch latency ≤ 50 µs per §4 (measured via benches/frame_bench.rs).
  • Zero heap allocations in the parse path for frames ≤ 125-byte payload (verified via a #[global_allocator] counting harness in tests).
Fixtures

tests/conformance/frame_vectors.json fully populated (≥30 rows); fixtures/roundtrip.json created with ≥10 split-read scenarios.

Pitfalls
  • Off-by-one in the 126/127 length branch — the value 126 or 127 in the 7-bit field is the sentinel, never a literal length of 126/127 bytes directly.
  • Forgetting P12's available-bytes check before reading the extended length, causing an out-of-bounds slice panic on a truncated buffer (Rust panics, not UB, but still a DoS via repeated crashes — see T3).
  • Treating Incomplete as an error instead of "come back with more bytes" — a common first-pass bug that breaks under any TCP fragmentation (Stevens, §5 books).

✅ Phase 3 — Frame Serializer (Encode Path) §15

Objectives

Implement the outbound half of §8's wire format: build correctly-encoded, unmasked server-to-client frames for every opcode, honoring I3 and the three length encodings symmetrically to Phase 2's decode path.

Deliverable

src/frame/serializer.rs with serialize(header, payload) -> BytesMut; a round-trip test harness that feeds every serializer output back through the Phase 2 parser.

Acceptance
  • Every row in fixtures/roundtrip.json survives serialize(parse(bytes)) == bytes for server-originated frames (masking asymmetry means client-originated frames round-trip differently — documented explicitly in the test).
  • Zero test cases produce a MASK=1 output frame (I3), enforced by a static assertion plus a fuzz test of 10,000 random payloads.
  • Serialization of a 64 MiB payload (the §4 message-size ceiling) completes in ≤ 5 ms.
Fixtures

fixtures/roundtrip.json extended with server-originated rows (reusing the Phase 2 file, same fixture, additional rows tagged "direction": "server").

Pitfalls
  • Accidentally reusing the client-side masking code path for server frames — the type system (no mask-key parameter on the server send path) should make this a compile error, not merely a runtime bug, per I3's "structural guarantee" telemetry note in §7.
  • Byte-order bugs on the 16-bit/64-bit extended length (must be big-endian per RFC 6455 §5.2, easy to accidentally use native/little-endian on x86).

✅ Phase 4 — Message Reassembly & Fragmentation §16

Objectives

Implement Reassembler (§11): accumulate FIN=0/continuation sequences into one logical Text/Binary message while control frames (Ping/Pong/Close) bypass it entirely per P7.

Deliverable

src/reassembly.rs with Reassembler::feed(frame) -> ReassemblyOutcome (either Pending, Complete(Message), or Error(WsError)).

Acceptance
  • fragmentation.rs integration tests (≥12 cases) cover: 1-frame message, 2-frame, 50-frame fragmented message, Ping interleaved mid-fragmentation, oversized fragmented message (triggers I9 at fragment 3 of an unbounded sequence, not only at the end).
  • A 50-fragment message reassembles correctly with total reassembly latency ≤ 1 ms for a 1 MiB total payload.
  • Interleaved-Ping test asserts the Pong is sent before the fragmented message completes (I14's ordering guarantee, verified via timestamp comparison in the test).
Fixtures

tests/fragmentation.rs — no separate JSON fixture; test cases are constructed programmatically (frame sequences are easier to express as Rust literals than JSON here, matching the source draft's original assessment of this section).

Pitfalls
  • Checking I9 only when the message completes rather than per-fragment (ADR-13 explicitly locks the incremental approach) — a naive port from a non-streaming decoder gets this wrong first.
  • Forgetting P7: routing a Ping through the reassembler's buffer instead of bypassing it, which would incorrectly reset or corrupt active_opcode.

✅ Phase 5 — Control Frames & Close Handshake §17

Objectives

Implement Ping/Pong auto-reply (I14) and the bidirectional close handshake (P10) with its timeout, covering both clean close (codes 1000/1001) and abnormal termination (1006).

Deliverable

src/control.rs (Ping/Pong) and src/close.rs (CloseCode, close state machine) fully wired into connection.rs's state transitions.

Acceptance
  • close_codes.json fixture (≥15 rows: every RFC-6455-registered code plus 3 invalid codes plus 2 app-range codes) validates/normalizes exactly as specified by I7.
  • A Ping sent mid-large-message-transfer receives a Pong within 5 ms (interleaving test, shared with §16.4).
  • A peer that never echoes Close triggers force-shutdown at exactly the 5 s timeout ± 50 ms (measured in an integration test using a mock non-responding peer).
  • Idle-timeout (I13) fires within 90 s ± 1 s of the last received frame/Pong.
Fixtures

tests/conformance/close_codes.json populated (≥15 rows).

Pitfalls
  • Replying to a Ping with a new payload instead of echoing the exact bytes received — RFC 6455 §5.5.2 requires byte-identical echo.
  • Not canceling the idle-timer on every received frame (not just Pong) — I13's "no frames" clause includes data frames, not only keepalive traffic.
  • Sending a second Close frame after already having sent one (RFC 6455 §5.5.1 — the Close frame may be sent at most once per direction).

✅ Phase 6 — Connection State Machine & Concurrency §18

Objectives

Wire the per-connection tokio task (ADR-10): own the socket, drive ConnectionState (§11) end-to-end, enforce the single-writer invariant (I11) via the bounded backpressure queue (ADR-11/12), and integrate the read loop with §14/§16's parser and reassembler.

Deliverable

src/connection.rs with run_connection(socket) -> impl Future spawning the reader/writer task pair; src/backpressure.rs with the bounded-channel wrapper type.

Acceptance
  • 10,000 concurrent connections sustained in a load test with p99 frame round-trip ≤ 500 µs (§4 target), memory ≤ 16 KiB/connection idle (§4).
  • A deliberately slow consumer (test harness that never reads) is disconnected within 256-frame-queue-depth × per-frame-time, not left buffering unboundedly (verified via a bounded-memory assertion in tests/integration_echo.rs).
  • No test run exhibits two concurrent writers to one socket (I11), verified by a #[cfg(test)] write-counter guard that panics on concurrent access.
  • Idle-timeout fires within 90 s ± 1 s under load (shared acceptance with §17.4).
Fixtures

Shared with tests/integration_echo.rs (§19.5) — load-test scenarios are parameterized, not separately fixture-filed.

Pitfalls
  • Holding a lock or RefCell across an .await point — classic async-Rust footgun (Gjengset, §5 books) that silently breaks under a multi-threaded tokio runtime.
  • Using an unbounded channel "temporarily" during development and forgetting to bound it before merging (directly regresses ADR-12/P3).
  • Spawning the writer task per-message instead of once-per-connection — defeats the purpose of a persistent single-writer task and reintroduces interleaving risk.

✅ Phase 7 — Echo Server Binary & Integration §19

Objectives

Ship src/bin/echo_server.rs: the reference application wired atop Phases 0–6, echoing every received Text/Binary message verbatim, serving as the integration validation target and the binary Autobahn|Testsuite connects to.

Deliverable

A runnable echo_server binary; tests/integration_echo.rs driving it end-to-end over a real TCP socket (not in-process mocks) for at least the handshake + echo + close path.

Acceptance
  • integration_echo.rs sends 1,000 messages of random size (1 B–1 MiB) and asserts byte-identical echo for all 1,000.
  • Autobahn|Testsuite (fixtures/autobahn_report/index.json) reports 100% pass on the core suite (cases 1.–9., excluding the deferred compression cases 12./13., per PhaseDeferred("§26")).
  • Graceful shutdown with 100 open connections completes in ≤ 30 s and every connection reaches Closed with code 1001 (not 1006).
  • Cold start (bind + ready-to-accept) completes in ≤ 200 ms (§4).
Fixtures

tests/integration_echo.rs; fixtures/autobahn_report/index.json (generated artifact, checked into CI as a regression baseline per §27).

Pitfalls
  • Echoing a message back through a different opcode than received (e.g., replying to Binary with Text) — must preserve the original opcode exactly.
  • Forgetting that Autobahn's client mode expects the server to not mask outbound frames (I3) — a masked echo response fails nearly every Autobahn case at once, a good canary if it happens.

✅ Phase 8 — permessage-deflate Extension (RFC 7692) §20

Objectives

Negotiate and apply RFC 7692 permessage-deflate: parse the Sec-WebSocket-Extensions offer, agree on server_no_context_takeover/client_no_context_takeover/window-bits parameters, and (de)compress payloads transparently to the reassembler/serializer.

Deliverable

src/extensions/deflate.rs with negotiation parsing and a DeflateCodec wrapping the compress/decompress paths; integrated into handshake.rs and frame/{parser,serializer}.rs.

Acceptance
  • Negotiation fixture set (≥8 cases: no offer, basic offer, both context-takeover flags, window-bits variants, malformed offer) all resolve per RFC 7692 §7.1.
  • A 1 MiB highly-compressible payload (repeated byte pattern) round-trips correctly and the wire size is ≥90% smaller than uncompressed (measured, not asserted).
  • A crafted 1 KiB compressed payload that would decompress to >64 MiB is rejected before full decompression completes (decompression-bomb guard, T6), verified with a streaming size-check test.
  • context_takeover disabled correctly resets compressor state between messages (verified by byte-identical output regardless of prior message content).
Fixtures

New fixture tests/conformance/deflate_negotiation.json (≥8 rows); Autobahn's compression cases (12./13.) remain PhaseDeferred("§26") as a blocking CI gate but are run informationally.

Pitfalls
  • Forgetting the decompression-bomb guard (I9 applied to decompressed size) — the single most security-relevant pitfall in this phase (T6).
  • Resetting the compression window when the negotiated flag says not to (or vice versa) — silently produces garbage on the second message of a multi-message exchange, not the first, making this bug easy to miss in minimal tests.
  • Applying RSV1 semantics without checking that deflate was actually negotiated for this connection — apply P11 strictly, per-connection, not globally.

✅ Phase 9 — TLS (wss://) & Production Hardening §21

Objectives

Terminate TLS in-process via rustls (ADR-09) ahead of the handshake layer, add certificate loading/rotation, and finalize production-hardening concerns (graceful shutdown edge cases, resource limits) deferred from earlier phases.

Deliverable

src/tls.rs with build_acceptor(config) -> TlsAcceptor; echo_server gains a --tls config section; full wss:// end-to-end test.

Acceptance
  • A wss:// client (using a self-signed test cert) completes handshake + echo + close end-to-end, with TLS handshake latency contributing ≤7 ms of the §4 8 ms p99 handshake budget.
  • Certificate rotation (replacing the PEM file) is picked up within 60 s without dropping existing connections (verified by an in-flight-connection-survives-rotation test).
  • Connection attempt #50,001 (exceeding the semaphore limit) is rejected at the TCP accept layer with a clean connection refusal, not accepted-then-dropped.
  • cargo audit (ADR-22-adjacent supply-chain check, §27) reports zero known vulnerabilities in the TLS dependency chain at release time.
Fixtures

tests/tls_integration.rs (new, self-signed test cert generated at test-build time, not committed to the repo per §27's secrets hygiene).

Pitfalls
  • Placing the frame parser (§14) ahead of the TLS unwrap — instantly breaks everything; P9 exists specifically to make this ordering mistake structurally obvious in code review.
  • Blocking the async runtime on synchronous cert-file reads on the hot accept path — cert loading must happen at startup/rotation time only, never per-connection.
  • Self-signed test certs accidentally shipped in a way that could be mistaken for production certs — keep test fixtures clearly namespaced and never committed with real domain names.
