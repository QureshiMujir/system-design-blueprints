81 — WebSocket Server from Scratch

Project Number: 81

Project Name: WebSocket Server from Scratch

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a standards-conformant RFC 6455 WebSocket server in Rust with zero external WebSocket-protocol crates: the HTTP Upgrade handshake, the binary frame codec (parse + serialize), fragmentation/reassembly, control-frame handling (Ping/Pong/Close), the close handshake, permessage-deflate (RFC 7692), and wss:// (TLS) — validated against Autobahn|Testsuite and a bundled conformance fixture set.

Phase-0 deliverable (repo skeleton + correctness kernel), as a numbered module list:

  1. error — WsError taxonomy mapped to RFC 6455 close codes.
  2. frame::opcode — Opcode enum, RFC 6455 §5.2 wire values.
  3. frame::header — FrameHeader struct, all bit-fields.
  4. handshake — HTTP Upgrade request/response types (empty logic, Phase 1 fills it).
  5. connection — ConnectionState enum skeleton.
  6. main — TCP listener stub that accepts and immediately closes (proves the skeleton links).

System boundaries:

  • Provides: RFC 6455 handshake, frame codec, fragmentation, control frames, close handshake, permessage-deflate, TLS termination, an echo-server reference binary, conformance fixtures, Autobahn integration.
  • Delegates: TCP transport to the OS kernel; TLS record layer to rustls; async scheduling to tokio; SHA-1/Base64 primitives to audited crates (ADR-04, ADR-05); HTTP/1.1 header tokenizing to httparse (ADR-18).
  • Does NOT provide: an HTTP/1.1 general-purpose server, a pub/sub or room/broadcast layer, a client library, a reverse proxy, HTTP/2 or HTTP/3 transport, browser-side JS.

Non-goals (with deferred-feature anchors, resolved in §35):

  • Sec-WebSocket-Protocol subprotocol negotiation — PhaseDeferred("§13").
  • RFC 8441 WebSocket-over-HTTP/2 bootstrapping — PhaseDeferred("§21").
  • Full Autobahn compression fuzz corpus (cases 12./13.) as a CI gate — PhaseDeferred("§26").
  • Horizontal sharding / multi-node connection routing — PhaseDeferred("§29").

Deployment model: single self-contained binary (echo_server), one process per host, horizontally cloned behind an L4 load balancer (sticky-by-connection, not sticky-by-request, because a WebSocket connection is long-lived — see §29).

Target users: systems engineers building protocol mastery; teams evaluating whether to hand-roll a WS layer vs adopt tungstenite/uWebSockets (see §31).

Language: Rust — memory safety without a GC pause on the hot frame-parsing path (ADR-01); rejected: Go (GC pauses under §4 p99 budget), C (manual memory safety burden on an attacker-controlled parser), Node.js (single-threaded event loop caps per-core throughput, ADR-10).

Prerequisites: TCP/IP fundamentals (Stevens, §5), async Rust (Future, .await), base64 / SHA-1 as black-box primitives, HTTP/1.1 header syntax.

Timeline: 10 phases (§12–§21), each independently testable; Phase 0–3 (kernel + handshake + codec) is the minimum viable conformance target; Phase 4–9 add reassembly, control frames, concurrency, the echo binary, permessage-deflate, and TLS.

Deferred beyond v1 (register in §35): subprotocol negotiation, HTTP/2 bootstrapping, the full Autobahn compression fuzz corpus as a blocking CI gate, and horizontal sharding.

2. Why Build This

RFC 6455 is the smallest protocol that forces mastery of five orthogonal systems skills at once: (1) a byte-exact binary state-machine parser over a stream that arrives in arbitrary chunks, (2) a security-critical bit (the mask) whose absence is a protocol violation in one direction and mandatory in the other, (3) message reassembly across an unbounded number of frames with control-frame interleaving, (4) a bidirectional close handshake with a defined abnormal-termination fallback, and (5) an extension-negotiation mechanism (RFC 7692) that changes the meaning of the RSV1 bit post-negotiation. No CRUD-style tutorial exercises any of these; a WebSocket server is the first project where "read the RFC and get it exactly right" is the only way to pass Autobahn|Testsuite.

Architectural/historical significance: WebSocket (Fette & Melnikov, RFC 6455, 2011) was the first IETF-standardized answer to the "persistent bidirectional channel over HTTP infrastructure" problem that earlier long-polling/Comet hacks solved ad hoc; it reuses the HTTP Upgrade mechanism (RFC 7230 §6.7) specifically so it survives the same proxies and firewalls HTTP does, rather than requiring a new port/protocol allow-list.

Cross-links to sibling systems: tungstenite-rs/tokio-tungstenite are the reference this blueprint deliberately does not depend on (ADR-03) but validates against; uWebSockets (C++) is the low-level performance ceiling this design is benchmarked against (§29, §31); Kafka's and gRPC's own framing layers face the same "length-prefixed frame over a byte stream" problem solved here (§8) with different tradeoffs (no masking, different length encodings).

Calibration value: a correct, Autobahn-passing implementation is externally verifiable (§26) — unlike many hand-rolled systems, "did I get it right" has a machine-checkable answer, making this an unusually good calibration exercise for protocol-level engineering discipline.

What Mastery Looks Like

  • Derive Sec-WebSocket-Accept by hand (SHA-1 + Base64 over key+GUID) and explain why the GUID exists (Phase 1, §13).
  • Parse a frame header byte-by-byte off a hex dump, including all three payload-length encodings, without a debugger (Phase 2, §14).
  • Explain why server-to-client frames must never be masked while client-to-server frames must always be masked, and what attack the asymmetry defeats (Phase 2, §14; I2/I3).
  • Reassemble an interleaved Ping/fragmented-Text sequence correctly, including replying to the Ping before the Text message completes (Phase 4/5, §16/§17).
  • Drive a full close handshake to completion, including the case where the peer never replies (Phase 5, §17; FM-6).
  • Negotiate and apply permessage-deflate context takeover correctly, including the no_context_takeover parameter (Phase 8, §20).
  • Reason about the CPU/memory tradeoff of enabling compression per §29 and §32's back-of-envelope model.
  • Explain, with numbers, why this design caps concurrency where it does and what the next lever is (Phase 6, §18; §29).

TCP Listener — accepts connections, spawns one tokio task per connection (ADR-10); trust boundary starts here (all bytes past this point are attacker-controlled). TLS Termination — optional per-connection rustls handshake (§21); if absent, the plaintext path runs directly into the Handshake box; concurrency boundary: TLS state is owned by the connection task, never shared. Handshake — parses the HTTP/1.1 Upgrade request with httparse (ADR-18), computes Sec-WebSocket-Accept (RFC 6455 §4.2.2), negotiates extensions (RFC 7692), and writes the 101 response; after this box the socket is WebSocket-framed, never HTTP again. Frame Parser — a pull-based state machine (§14) that turns a byte cursor into FrameHeader + payload slices; persistence boundary: none (in-memory only, bounded by max_message_size, I9). Reassembler — accumulates fragmented Text/Binary messages (§16); control frames bypass it entirely (I8). Extensions — permessage-deflate (de)compression sits between the wire and the reassembler/serializer (§20); RSV1 on the wire means "compressed" only when negotiated. Control/Close — Ping→Pong auto-reply, Pong bookkeeping, and the close handshake state machine (§17); persistence boundary: close-code and reason are the only state that outlives the socket (into metrics). Application (echo) — the Phase-7 reference binary; the codec has no built-in echo logic, keeping the domain model transport-agnostic. Backpressure Queue — a single bounded mpsc per connection (ADR-11/ADR-12) enforcing I11; the single writer task is the only thing allowed to touch the socket's write half. Metrics/Tracing — tracing spans per connection/frame (ADR-16), exported per §24.

6. Design Principles

P1 — Validate before allocating. Rule: never allocate a reassembly/payload buffer sized by an attacker-controlled length field before that length passes the §4 ceilings. Tradeoff: an extra branch per frame header. Operational implication: caps worst-case memory per connection deterministically. Violating it: a single crafted 64-bit length field claiming 2^63 bytes triggers an allocation abort (DoS), see T3.

P2 — Masking direction is non-negotiable. Rule: client→server frames MUST be masked, server→client frames MUST NOT be (RFC 6455 §5.1). Tradeoff: none — this is a MUST in the spec, not a tunable. Operational implication: any received unmasked client frame is immediately a protocol error (I2). Violating it: caching-proxy poisoning attacks the masking bit specifically defeats (RFC 6455 §10.3).

P3 — Backpressure before buffering. Rule: a connection whose peer cannot keep up with outbound frames is throttled at the bounded queue (§4), never given an unbounded buffer. Tradeoff: slow consumers get disconnected instead of silently falling behind forever. Operational implication: bounds worst-case per-connection memory under write pressure. Violating it: memory grows unbounded per slow client — a single stalled client can OOM the process (FM-4).

P4 — Fail closed on malformed control data. Rule: a Close frame with an invalid status code, or a control frame exceeding 125 bytes, is treated as a protocol error, not best-effort tolerated. Tradeoff: stricter than some deployed servers; costs conformance against noncompliant clients. Operational implication: Autobahn conformance (§26) requires this strictness. Violating it: fails Autobahn cases 5.* and 7.*.

P5 — Single writer per connection. Rule: exactly one task owns the socket's write half; all outbound frames funnel through one bounded channel (ADR-11). Tradeoff: one extra hop (channel send) per outbound message. Operational implication: eliminates frame interleaving from concurrent writers by construction (I11). Violating it: two tasks writing concurrently corrupt the frame stream — the peer sees an unparseable byte sequence.

P6 — Reassembly buffer is bounded, not elastic. Rule: the per-message reassembly buffer never grows past max_message_size (§4); the check happens per-fragment, not only at the end. Tradeoff: cannot support unbounded streaming messages. Operational implication: caps peak per-connection memory during fragmented uploads (I9). Violating it: a fragmented message with millions of tiny continuation frames exhausts memory before any single frame looks anomalous (FM-2).

P7 — Control frames preempt data-frame reassembly. Rule: Ping/Pong/Close may arrive mid-fragmentation and MUST be processed immediately, not queued behind the in-progress message (RFC 6455 §5.4). Tradeoff: the reassembler must track two independent cursors. Operational implication: keepalive stays responsive even during large message transfer. Violating it: a large upload blocks Ping replies past the timeout, causing a false-dead disconnect (FM-5).

P8 — One parser, one state machine, never recursive. Rule: frame parsing is a flat state machine over an explicit cursor (§14), never recursive descent over nested frames (WebSocket frames don't nest, but naive ports from other codecs sometimes assume they do). Tradeoff: slightly more verbose than a recursive parser combinator. Operational implication: stack depth is O(1) regardless of input, immune to stack-exhaustion attacks. Violating it: a crafted input could exhaust stack via unbounded recursion (T5).

P9 — TLS terminates before WebSocket framing, never after. Rule: rustls owns the TLS record layer; the frame parser only ever sees plaintext WebSocket bytes (§21). Tradeoff: cannot inspect WebSocket frames at a TLS-unaware middlebox. Operational implication: clean layering — the codec (§14/§15) is TLS-agnostic and testable without TLS. Violating it: mixing TLS record boundaries with WS frame boundaries produces undecryptable garbage.

P10 — The close handshake is bidirectional and has a timeout. Rule: after sending or receiving a Close frame, wait up to the §4 close-handshake timeout for the peer's Close echo before forcing TCP shutdown (RFC 6455 §7.1.1). Tradeoff: a slightly slower clean shutdown vs. an instant close(). Operational implication: distinguishes a clean close (both sides exchanged Close, code 1000/1001) from abnormal termination (code 1006). Violating it: fails Autobahn case 7.1.* (opening handshake close-code checks) and hides real network failures behind a fake "clean" close.

P11 — Extensions are opt-in and change wire semantics only after negotiation succeeds. Rule: RSV1 means "payload is compressed" only if permessage-deflate was negotiated in the handshake (RFC 7692 §6); absent negotiation, any RSV bit set is a protocol error (I4). Tradeoff: extension code must be reachable from, but not required by, the core codec. Operational implication: keeps the RFC-6455-only path fully independent and testable. Violating it: interpreting RSV1 as "compressed" without negotiation corrupts uncompressed payloads that happen to have that bit set by a buggy peer.

P12 — Every extended length is checked against bytes actually available, not just declared. Rule: the 16-bit/64-bit extended-length fields are read only after confirming the buffer holds that many header bytes; the payload length itself is checked against §4 ceilings before any payload read is attempted. Tradeoff: an extra length-vs-buffer comparison per frame. Operational implication: prevents integer-overflow or buffer-over-read bugs common in hand-rolled C parsers (Rust's bounds checks catch the memory-safety half; this principle catches the protocol-semantics half). Violating it: a 64-bit length field near u64::MAX added to a buffer offset can wrap and misparse subsequent frames (T3).

P13 — Keepalive is server-initiated, not passive. Rule: the server sends a Ping on a fixed interval (§4) and tracks outstanding Pongs; it does not rely solely on the client to detect a dead peer. Tradeoff: extra periodic timer per connection. Operational implication: detects NAT-timeout / silently-dropped connections proactively (ADR-19). Violating it: half-open connections accumulate, consuming FDs and memory with no application traffic (FM-7).

P14 — Structured errors carry enough context to choose a close code. Rule: every WsError variant maps deterministically to exactly one RFC 6455 close code (§11); handling code never re-derives the code from a string message. Tradeoff: the error enum must be kept in sync with the RFC 6455 §7.4 code registry. Operational implication: close codes sent to peers are always spec-correct, which Autobahn checks (§26). Violating it: sending code 1000 (normal) for what was actually a protocol violation misleads clients and fails conformance.

Value Name Fragmentable Notes

Payload-length encoding table:

7-bit field value Meaning
0–125 Actual payload length, no extension
126 Next 2 bytes = unsigned 16-bit big-endian length
127 Next 8 bytes = unsigned 64-bit big-endian length (MSB must be 0 per RFC 6455 §5.2)

State-transition / handshake sequence table (client C, server S):

Step Actor Action Precondition Postcondition
1 C TCP connect — Socket open
2 C Send HTTP/1.1 GET with Upgrade: websocket, Sec-WebSocket-Key: <b64 16B>, Sec-WebSocket-Version: 13 — Server buffer has request bytes
3 S Parse request (httparse), validate headers Full header block received HandshakeRequest built or WsError::InvalidHandshake
4 S Compute Sec-WebSocket-Accept = base64(SHA-1(key + 258EAFA5-E914-47DA-95CA-C5AB0DC85B11)) Step 3 succeeded Accept value ready (I1)
5 S Send 101 Switching Protocols + accept header Step 4 done Connection state → Open
6 C/S Exchange WebSocket frames State = Open Frames parsed/serialized per §14/§15
7 Either Send Close frame Any time State → ClosingLocal or ClosingRemote
8 Peer Echo Close frame Received Close State → Closed, TCP shutdown

Worked example (client masked Text frame "Hi", masking key 0x37FA213D):

Unmasked payload Hi = 0x48 0x69. XOR with repeating key bytes 37 FA 21 3D: 0x48^0x37=0x7F, 0x69^0xFA=0x93. Wire bytes: 81 82 37 FA 21 3D 7F 93 — 81=FIN=1, opcode=0x1 (Text); 82=MASK=1, len=2; then 4-byte key, then 2 masked payload bytes.

Malformed-input example: wire bytes 81 FE 00 7E ... — MASK bit unset (FE = 1111 1110, top bit of second byte is MASK; here it's the payload-length top bit region, illustrating a client frame sent with MASK=0) → RFC 6455 §5.1 violation → WsError::UnmaskedClientFrame → I2 detection fires → Close 1002 sent, connection dropped, no payload buffered (P4).

Failure-path example: server receives a complete Text message whose reassembled bytes are 0x48 0xFF 0xFE (invalid UTF-8 continuation bytes) → I12 fails at finalize() → WsError::InvalidUtf8 → close.rs maps to code 1007 → server sends Close(1007, "invalid UTF-8") → waits ≤5s (§4) for peer's Close echo → TCP shutdown regardless (P10).

13. Phase 1 — HTTP Upgrade Handshake

13.1 Objectives

Implement the full RFC 6455 §4.2 handshake: parse the client's HTTP/1.1 Upgrade request, validate every required header, compute Sec-WebSocket-Accept, and write the 101 Switching Protocols response, transitioning ConnectionState::Connecting → Upgrading → Open.

13.2 Detailed Implementation Steps

  1. Read into a growable buffer (ADR-06) until httparse::Request::parse reports a complete header block (ADR-18) — apply P1: cap the buffer at a header-size limit before parsing.
  2. Validate Connection: Upgrade, Upgrade: websocket, Sec-WebSocket-Version: 13 (reject with 426 if version mismatches, per RFC 6455 §4.4) — apply RFC 6455 §4.2.1.
  3. Extract Sec-WebSocket-Key; validate it decodes as exactly 16 bytes of base64 (RFC 4648) — apply I1's precondition.
  4. Compute accept key: base64(sha1(key ++ "258EAFA5-E914-47DA-95CA-C5AB0DC85B11")) — apply I1 directly, using the sha1/base64 crates per ADR-04/ADR-05.
  5. Parse Sec-WebSocket-Extensions header if present; attempt permessage-deflate negotiation (ADR-08) — deferred logic stub in this phase, real in §20/Phase 8.
  6. Write the 101 response with Upgrade, Connection, Sec-WebSocket-Accept headers.
  7. Transition ConnectionState to Open; hand off the socket to the Phase 2 frame parser.
  8. On any validation failure, apply P14: map to WsError::InvalidHandshake, respond 400 Bad Request, close the TCP connection — never proceed to framing mode.

13.3 Deliverable

src/handshake.rs with parse_request, compute_accept_key, build_response — fully testable without a live socket via in-memory byte slices.

13.4 Acceptance Criteria

  • compute_accept_key("dGhlIHNhbXBsZSBub25jZQ==") returns exactly "s3pPLMBiTxaQ9kYGzzhZRbK+xOo=" (the RFC 6455 §1.3 worked example) — byte-exact match, no tolerance.
  • handshake_vectors.json (≥10 cases: valid, missing key, wrong version, malformed base64, missing Upgrade header) all pass.
  • Handshake latency p50 ≤ 1 ms per §4 (measured in benches/).
  • Invalid handshake never advances ConnectionState past Upgrading.

13.5 Conformance Fixtures

tests/conformance/handshake_vectors.json — populated with the RFC 6455 §1.3 worked example plus ≥9 negative cases.

13.6 Pitfalls

  • Case-sensitivity bugs: Upgrade/upgrade header name comparison must be case-insensitive per RFC 7230 §3.2, but header values like websocket are also case-insensitive per RFC 6455 §4.2.1 — conflating the two rules is a common bug.
  • Trailing CRLF handling: httparse expects \r\n\r\n terminator; a client sending bare \n is technically noncompliant but some browsers historically tolerated it — decide and document the stance (this blueprint: strict, reject).
  • Forgetting the subprotocol-negotiation non-goal (PhaseDeferred("§13")) and accidentally echoing back Sec-WebSocket-Protocol from the request — must not happen in v1.

13.7 Performance Concerns

SHA-1 + base64 over a 16–24 byte key is sub-microsecond; the dominant cost is the initial read() syscall and TCP handshake RTT, not the crypto — do not over-optimize this path.

13.8 Edge Cases

  • Multiple Sec-WebSocket-Key headers (malformed request) — reject, don't take the first.
  • Extremely long header lines (potential DoS) — bounded by the header-size cap from step 1.
  • HTTP/1.0 request line (GET / HTTP/1.0) — reject; RFC 6455 requires HTTP/1.1.

13.9 Failure Analysis

Failure class: malformed/incomplete handshake. Detection: httparse parse error or header validation failure. Auto recovery: none — connection is rejected with 400/426 and closed; the client must retry with a corrected request (no server-side retry logic).

13.10 Operational Notes

Emit handshake_accept_mismatch_total and per-failure-reason counters (§24) so a fleet-wide spike in handshake rejections is visible before it becomes a client-facing incident.

14. Phase 2 — Frame Parser (Decode Path)

14.1 Objectives

Implement the RFC 6455 §5.2 frame-header state machine: decode FIN/RSV/opcode, MASK and the three payload-length encodings, the masking key, and unmask the payload — returning Incomplete, Frame, or ProtocolError per read.

14.2 Detailed Implementation Steps

  1. Read byte 0: extract fin, rsv (apply I4 — reject if any RSV bit set and no extension negotiated), opcode (apply the §8 opcode table; unknown opcode → WsError).
  2. Read byte 1: extract masked (apply I2 — MUST be 1 for inbound frames) and the 7-bit length field.
  3. Branch on the 7-bit length value (apply §8's payload-length table): 0–125 direct; 126 → read 2 more bytes big-endian; 127 → read 8 more bytes big-endian, reject if the MSB is set (RFC 6455 §5.2 forbids negative-looking lengths) — apply P12: check against bytes available, not just declared.
  4. Compare decoded payload_len against max_message_size/frame ceilings (§4) — apply I9 and P1 before allocating anything.
  5. If masked, read the 4-byte masking key.
  6. Read payload_len bytes; if the buffer is short, return Incomplete { needed } — never block, this is a pull parser (apply the Click pipeline lesson, §5 papers).
  7. Unmask in place: payload[i] ^= mask_key[i % 4] — apply I2's precondition (masking key is Some here by construction).
  8. Return ParseOutcome::Frame(header, payload) — zero-copy borrow of the input buffer.

14.3 Deliverable

src/frame/parser.rs with a FrameParser exposing parse(&mut self, buf: &[u8]) -> ParseOutcome — no I/O inside; pure function of bytes in, outcome out.

14.4 Acceptance Criteria

  • All rows of frame_vectors.json (≥30 cases spanning every opcode, all 3 length encodings, masked/unmasked, RSV-set) parse to the exact expected FrameHeader or exact expected WsError variant.
  • Parsing a frame split across 2, 3, and 7 separate read()-sized chunks produces the identical FrameHeader as parsing it whole (round-trip in roundtrip.json).
  • p50 parse+dispatch latency ≤ 50 µs per §4 (measured via benches/frame_bench.rs).
  • Zero heap allocations in the parse path for frames ≤ 125-byte payload (verified via a #[global_allocator] counting harness in tests).

14.5 Conformance Fixtures

tests/conformance/frame_vectors.json fully populated (≥30 rows); fixtures/roundtrip.json created with ≥10 split-read scenarios.

14.6 Pitfalls

  • Off-by-one in the 126/127 length branch — the value 126 or 127 in the 7-bit field is the sentinel, never a literal length of 126/127 bytes directly.
  • Forgetting P12's available-bytes check before reading the extended length, causing an out-of-bounds slice panic on a truncated buffer (Rust panics, not UB, but still a DoS via repeated crashes — see T3).
  • Treating Incomplete as an error instead of "come back with more bytes" — a common first-pass bug that breaks under any TCP fragmentation (Stevens, §5 books).

14.7 Performance Concerns

The mask XOR loop (§8) is the hottest per-byte code path; ADR-07 locks a scalar word-at-a-time approach for v1 — revisit only if benches/ shows M7 missed (§28).

14.8 Edge Cases

  • Zero-length payload (valid — e.g., a Ping with no data).
  • Length exactly 125, 126, 127 (boundary values for the encoding switch).
  • 64-bit length with MSB set (must reject per RFC 6455 §5.2, not silently truncate).
  • A frame header split exactly at the boundary between the 2-byte prefix and the extended length field.

14.9 Failure Analysis

Failure class: malformed frame header. Detection: any of I2/I4/I6/I9 checks failing. Auto recovery: none at the parser level — the caller (connection.rs, §18) maps the WsError to a Close code and terminates; the parser itself never retries or tolerates.

14.10 Operational Notes

Every ProtocolError outcome increments a per-WsError-variant counter (§24) — this is the primary signal for distinguishing "buggy client" traffic from active probing (T1–T3).

15. Phase 3 — Frame Serializer (Encode Path)

15.1 Objectives

Implement the outbound half of §8's wire format: build correctly-encoded, unmasked server-to-client frames for every opcode, honoring I3 and the three length encodings symmetrically to Phase 2's decode path.

15.2 Detailed Implementation Steps

  1. Given an Opcode, fin flag, and payload slice, select the length encoding per §8's table — apply the same three-way branch as §14.2 step 3, in reverse.
  2. Write byte 0: fin << 7 | opcode — apply I4's inverse: never set RSV bits unless an extension (§20) explicitly requested it for this frame.
  3. Write byte 1: MASK bit forced to 0 (apply I3 — structurally, FrameSink::send_frame has no mask-key parameter, making violation a compile error, not a runtime check).
  4. Write the length field (7-bit direct, or 126+u16, or 127+u64) per ADR-20's reused BytesMut buffer.
  5. Write the payload bytes verbatim (no masking, per I3).
  6. Hand the completed byte sequence to the backpressure queue (§18), never to the socket directly — apply P5/I11.

15.3 Deliverable

src/frame/serializer.rs with serialize(header, payload) -> BytesMut; a round-trip test harness that feeds every serializer output back through the Phase 2 parser.

15.4 Acceptance Criteria

  • Every row in fixtures/roundtrip.json survives serialize(parse(bytes)) == bytes for server-originated frames (masking asymmetry means client-originated frames round-trip differently — documented explicitly in the test).
  • Zero test cases produce a MASK=1 output frame (I3), enforced by a static assertion plus a fuzz test of 10,000 random payloads.
  • Serialization of a 64 MiB payload (the §4 message-size ceiling) completes in ≤ 5 ms.

15.5 Conformance Fixtures

fixtures/roundtrip.json extended with server-originated rows (reusing the Phase 2 file, same fixture, additional rows tagged "direction": "server").

15.6 Pitfalls

  • Accidentally reusing the client-side masking code path for server frames — the type system (no mask-key parameter on the server send path) should make this a compile error, not merely a runtime bug, per I3's "structural guarantee" telemetry note in §7.
  • Byte-order bugs on the 16-bit/64-bit extended length (must be big-endian per RFC 6455 §5.2, easy to accidentally use native/little-endian on x86).

15.7 Performance Concerns

BytesMut reuse (ADR-20) avoids a per-frame allocation; verify via the same allocation- counting harness used in §14.4 that steady-state serialization is allocation-free after warmup.

15.8 Edge Cases

  • Serializing a 0-byte payload (valid Pong reply with no data, I14).
  • Serializing exactly at the 125/126/127 boundary (mirrors §14.8).
  • Serializing a Close frame with no status code at all (valid per RFC 6455 §7.1.5, distinct from status code 1005 which is never sent on the wire, only inferred locally).

15.9 Failure Analysis

Failure class: payload exceeds u64 length representability — practically unreachable given the §4 64 MiB ceiling, but the serializer asserts on it defensively rather than producing a corrupt frame.

15.10 Operational Notes

frame_bench.rs (§28, M-table) gates serializer throughput in CI; a regression beyond the M-table threshold fails the build before merge (§27).

16. Phase 4 — Message Reassembly & Fragmentation

16.1 Objectives

Implement Reassembler (§11): accumulate FIN=0/continuation sequences into one logical Text/Binary message while control frames (Ping/Pong/Close) bypass it entirely per P7.

16.2 Detailed Implementation Steps

  1. On a data frame (Text/Binary) with FIN=0: set active_opcode, append payload to buffer, apply I9's incremental size check (ADR-13) after every append.
  2. On a continuation frame (opcode 0x0): apply I5/I8 — reject if active_opcode is None; otherwise append, re-checking I9.
  3. On a data frame with FIN=1 and no prior fragment (active_opcode is None): treat as a complete single-frame message, skip the buffer entirely (zero-copy fast path).
  4. On the final continuation frame (FIN=1): apply I12 — validate UTF-8 incrementally (ADR-15) if active_opcode == Text; clear active_opcode; hand the complete message to the application layer.
  5. On any control frame arriving mid-fragmentation: apply P7 — dispatch immediately to control.rs/close.rs (§17), do not touch active_opcode/buffer at all.
  6. On a protocol violation (I5/I8/I9/I12 failure): apply P14's error mapping, propagate the WsError up to connection.rs for the Close sequence.

16.3 Deliverable

src/reassembly.rs with Reassembler::feed(frame) -> ReassemblyOutcome (either Pending, Complete(Message), or Error(WsError)).

16.4 Acceptance Criteria

  • fragmentation.rs integration tests (≥12 cases) cover: 1-frame message, 2-frame, 50-frame fragmented message, Ping interleaved mid-fragmentation, oversized fragmented message (triggers I9 at fragment 3 of an unbounded sequence, not only at the end).
  • A 50-fragment message reassembles correctly with total reassembly latency ≤ 1 ms for a 1 MiB total payload.
  • Interleaved-Ping test asserts the Pong is sent before the fragmented message completes (I14's ordering guarantee, verified via timestamp comparison in the test).

16.5 Conformance Fixtures

tests/fragmentation.rs — no separate JSON fixture; test cases are constructed programmatically (frame sequences are easier to express as Rust literals than JSON here, matching the source draft's original assessment of this section).

16.6 Pitfalls

  • Checking I9 only when the message completes rather than per-fragment (ADR-13 explicitly locks the incremental approach) — a naive port from a non-streaming decoder gets this wrong first.
  • Forgetting P7: routing a Ping through the reassembler's buffer instead of bypassing it, which would incorrectly reset or corrupt active_opcode.

16.7 Performance Concerns

buffer growth uses BytesMut::reserve in chunks (ADR-06) rather than reallocating per fragment — verify no O(n²) reallocation pattern under a 10,000-fragment adversarial message (bounded by I9 well before this matters in practice, but the algorithm should not regress).

16.8 Edge Cases

  • A message that is exactly 1 fragment (FIN=1 on the first frame) — must use the fast path in step 3, not the buffer.
  • A Close frame arriving mid-fragmentation — apply P7 and P10 together: the close handshake begins immediately, the in-progress reassembly buffer is discarded, not delivered.
  • Two back-to-back Pings mid-fragmentation — both must be replied to in order (I14).

16.9 Failure Analysis

Failure class: fragmentation-sequence violation (I5/I8). Detection: opcode/state mismatch in feed(). Recovery: WsError::FragmentationViolation → Close 1002 (no partial delivery of the malformed message to the application).

16.10 Operational Notes

oversized_message_total and fragmentation_violation_total (§7 telemetry columns) are the two counters operators should alert on for a client sending adversarially-fragmented input (T4).

17. Phase 5 — Control Frames & Close Handshake

17.1 Objectives

Implement Ping/Pong auto-reply (I14) and the bidirectional close handshake (P10) with its timeout, covering both clean close (codes 1000/1001) and abnormal termination (1006).

17.2 Detailed Implementation Steps

  1. On Ping: apply I14 — immediately enqueue a Pong with the identical payload via the single writer (P5); never defer behind other queued frames.
  2. On Pong: record the round-trip time for the ping_pong_latency_histogram (§7); apply I13's bookkeeping (this Pong clears the current keepalive deadline).
  3. Implement the server-initiated Ping timer per ADR-19/P13: every 30 s (§4), send a Ping; if no Pong within 90 s, apply I13 — force-close with local code 1006.
  4. On receiving a Close frame: apply I7 (validate the status code); if valid, transition ConnectionState::ClosingRemote; echo a Close frame with the same code (or 1000 if the peer sent none) per P10.
  5. On sending a Close frame (application- or error-initiated): transition ConnectionState::ClosingLocal; start the §4 5-second close-timeout timer.
  6. On receiving the peer's echoed Close (completing the handshake from either side): transition to Closed, cancel timers, close the TCP socket cleanly.
  7. On close-timeout expiry (peer never echoes): apply P10's fallback — force TCP shutdown, record code 1006 locally (the peer's actual reason, if any, is unknowable — FM-6).

17.3 Deliverable

src/control.rs (Ping/Pong) and src/close.rs (CloseCode, close state machine) fully wired into connection.rs's state transitions.

17.4 Acceptance Criteria

  • close_codes.json fixture (≥15 rows: every RFC-6455-registered code plus 3 invalid codes plus 2 app-range codes) validates/normalizes exactly as specified by I7.
  • A Ping sent mid-large-message-transfer receives a Pong within 5 ms (interleaving test, shared with §16.4).
  • A peer that never echoes Close triggers force-shutdown at exactly the 5 s timeout ± 50 ms (measured in an integration test using a mock non-responding peer).
  • Idle-timeout (I13) fires within 90 s ± 1 s of the last received frame/Pong.

17.5 Conformance Fixtures

tests/conformance/close_codes.json populated (≥15 rows).

17.6 Pitfalls

  • Replying to a Ping with a new payload instead of echoing the exact bytes received — RFC 6455 §5.5.2 requires byte-identical echo.
  • Not canceling the idle-timer on every received frame (not just Pong) — I13's "no frames" clause includes data frames, not only keepalive traffic.
  • Sending a second Close frame after already having sent one (RFC 6455 §5.5.1 — the Close frame may be sent at most once per direction).

17.7 Performance Concerns

Ping/Pong bookkeeping is O(1) per event (a single timestamp compare-and-reset) — no measurable overhead expected; not a candidate for the M-table (§28).

17.8 Edge Cases

  • Close frame with a 1-byte payload (invalid — status code needs exactly 2 bytes minimum, RFC 6455 §5.5.1) — must reject as malformed, mapped to I7's normalization path.
  • Simultaneous close: both peers send Close within the same round-trip — both sides must still reach Closed correctly (test both orderings).
  • A Pong received with no matching outstanding Ping — logged, not an error (RFC 6455 §5.5.3 permits unsolicited Pongs).

17.9 Failure Analysis

Failure class: close-handshake timeout (peer unresponsive). Detection: 5 s timer expiry (FM-6). Auto recovery: force TCP shutdown, record 1006. Manual recovery: none needed — this is the designed fallback, not an incident.

17.10 Operational Notes

close_code_histogram (bucketed by code) is the primary operational signal for distinguishing normal client disconnects (1000/1001) from a fleet-wide protocol problem (spike in 1002/1007) — feeds directly into §24's dashboards.

18. Phase 6 — Connection State Machine & Concurrency

18.1 Objectives

Wire the per-connection tokio task (ADR-10): own the socket, drive ConnectionState (§11) end-to-end, enforce the single-writer invariant (I11) via the bounded backpressure queue (ADR-11/12), and integrate the read loop with §14/§16's parser and reassembler.

18.2 Detailed Implementation Steps

  1. Split the accepted socket into read/write halves (or the TLS-wrapped equivalent, §21); move the write half exclusively into a dedicated writer task — apply I11 structurally (Blandy et al., §5 books, on ownership across .await).
  2. Spawn the writer task owning a bounded mpsc::Receiver<BytesMut> (§4 depth 256) — apply ADR-11/ADR-12/P3 directly.
  3. In the reader task's loop: read() into the ADR-06 growable buffer, feed bytes to FrameParser (§14), route Frame outcomes to Reassembler (§16) or control.rs/ close.rs (§17) by opcode.
  4. On ParseOutcome::Incomplete, loop back to read() without processing — apply the SEDA staged-pipeline lesson (§5 papers) of never blocking a stage on partial input.
  5. On any WsError from any stage, apply P14: build the corresponding Close frame, send it via the writer task's channel, transition state, and let the close-timeout (§17) drive final teardown — never panic! on attacker-controlled input.
  6. Enforce I13 (idle timeout) and P13 (Ping interval) via a tokio::time::interval selected alongside the read future in the task's main select loop.
  7. On writer-channel-full (backpressure overflow, P3): apply ADR-12 — disconnect the slow consumer rather than blocking the reader indefinitely.

18.3 Deliverable

src/connection.rs with run_connection(socket) -> impl Future spawning the reader/writer task pair; src/backpressure.rs with the bounded-channel wrapper type.

18.4 Acceptance Criteria

  • 10,000 concurrent connections sustained in a load test with p99 frame round-trip ≤ 500 µs (§4 target), memory ≤ 16 KiB/connection idle (§4).
  • A deliberately slow consumer (test harness that never reads) is disconnected within 256-frame-queue-depth × per-frame-time, not left buffering unboundedly (verified via a bounded-memory assertion in tests/integration_echo.rs).
  • No test run exhibits two concurrent writers to one socket (I11), verified by a #[cfg(test)] write-counter guard that panics on concurrent access.
  • Idle-timeout fires within 90 s ± 1 s under load (shared acceptance with §17.4).

18.5 Conformance Fixtures

Shared with tests/integration_echo.rs (§19.5) — load-test scenarios are parameterized, not separately fixture-filed.

18.6 Pitfalls

  • Holding a lock or RefCell across an .await point — classic async-Rust footgun (Gjengset, §5 books) that silently breaks under a multi-threaded tokio runtime.
  • Using an unbounded channel "temporarily" during development and forgetting to bound it before merging (directly regresses ADR-12/P3).
  • Spawning the writer task per-message instead of once-per-connection — defeats the purpose of a persistent single-writer task and reintroduces interleaving risk.

18.7 Performance Concerns

Task-per-connection (ADR-10) scales to the §4 50k-connection ceiling on typical cloud-instance memory; beyond that, per-task overhead (stack + scheduler bookkeeping) becomes the dominant cost — tracked as the primary lever in §29.

18.8 Edge Cases

  • Peer resets the connection mid-read (ECONNRESET) — must be treated as an abnormal close (1006), not propagated as a panic.
  • Writer channel closed (writer task panicked) while reader still active — reader must detect the closed channel and terminate gracefully, not hang.
  • Extremely bursty traffic (all 256 queue slots filled within one scheduler tick) — verify overflow-disconnect logic doesn't misfire on legitimate bursts within budget.

18.9 Failure Analysis

Failure class: backpressure overflow (slow consumer). Detection: bounded-channel send returns "full" (ADR-12). Auto recovery: disconnect that connection only — no cross-connection impact (isolation verified by FM-4).

18.10 Operational Notes

Per-connection task count is exported as a gauge (§24); a sustained approach to the §4 50k ceiling should page before hitting the FD limit, not after (§29's scaling lever discussion).

19.1 Objectives

  1. Load Config (ADR-21) from config.toml + env overrides; bind the TCP listener from Phase 0's skeleton, now with the full handshake/framing pipeline attached.

  3. Wire graceful shutdown (§4: ≤30 s drain): on SIGTERM, stop accepting new connections, send Close(1001) to all open connections, wait for their close handshakes or the per-connection 5 s timeout (§17), then exit.

  5. Provide a companion Autobahn client-mode config (scripts/run_autobahn.sh, ADR-17) that points the Autobahn fuzzing client at this binary's bound port.

19.3 Deliverable

A runnable echo_server binary; tests/integration_echo.rs driving it end-to-end over a real TCP socket (not in-process mocks) for at least the handshake + echo + close path.

19.4 Acceptance Criteria

  • Autobahn|Testsuite (fixtures/autobahn_report/index.json) reports 100% pass on the core suite (cases 1.–9., excluding the deferred compression cases 12./13., per PhaseDeferred("§26")).

19.5 Conformance Fixtures

tests/integration_echo.rs; fixtures/autobahn_report/index.json (generated artifact, checked into CI as a regression baseline per §27).

19.6 Pitfalls

  • Echoing a message back through a different opcode than received (e.g., replying to Binary with Text) — must preserve the original opcode exactly.
  • Forgetting that Autobahn's client mode expects the server to not mask outbound frames (I3) — a masked echo response fails nearly every Autobahn case at once, a good canary if it happens.

19.7 Performance Concerns

The echo path itself adds negligible overhead (one BytesMut clone) atop the codec — Autobahn's own client-side rate is the practical ceiling for this phase's benchmarks, not the server.

19.8 Edge Cases

  • Autobahn's case 9.* suite (large/many frames) exercises the §4 message-size ceiling directly — verify the 64 MiB cap doesn't reject Autobahn's own within-spec large-message cases (tune the ceiling if Autobahn's default exceeds it, or configure Autobahn's client limit down to match — document the choice).
  • SIGTERM received while a connection is mid-handshake (not yet Open) — must not hang the shutdown drain waiting on a connection that never reaches a closeable state.

19.9 Failure Analysis

Failure class: Autobahn regression (a previously-passing case starts failing). Detection: CI diff against the checked-in baseline report (§27). Recovery: bisect the offending commit before merge — this is a release-blocking gate (§27), not a warning.

19.10 Operational Notes

The Autobahn report artifact is retained per release (§27) as the conformance evidence trail — referenced directly by §26's testing strategy.

20. Phase 8 — permessage-deflate Extension (RFC 7692)

20.1 Objectives

Negotiate and apply RFC 7692 permessage-deflate: parse the Sec-WebSocket-Extensions offer, agree on server_no_context_takeover/client_no_context_takeover/window-bits parameters, and (de)compress payloads transparently to the reassembler/serializer.

20.2 Detailed Implementation Steps

  1. During handshake (§13, extending step 5): parse Sec-WebSocket-Extensions: permessage-deflate; ... parameters into ExtensionParams (§11) — apply RFC 7692 §6 directly.
  2. If negotiation succeeds, respond with the agreed parameter subset (RFC 7692 §5 —server may accept a subset of offered parameters, never invent unoffered ones) — apply P11.
  3. On the decode path (§14, after unmasking): if RSV1 is set and deflate is negotiated, decompress via flate2's raw-deflate reader before handing bytes to the reassembler (§16) — apply RFC 1951 (the DEFLATE format itself, cited in §5).
  4. On the encode path (§15): compress the message payload via flate2's raw-deflate writer, set RSV1, before serializing the frame header — apply P11's inverse.
  5. Implement context takeover per the negotiated no_context_takeover flags: reset the compressor/decompressor's sliding window after each message if the flag is set, else preserve it across messages (RFC 7692 §7.2.1) — apply ADR-08 directly.
  6. Cap decompressed message size against the same max_message_size ceiling (§4) — apply I9 to the decompressed size, not the compressed wire size, closing a decompression-bomb vector (T6).

20.3 Deliverable

src/extensions/deflate.rs with negotiation parsing and a DeflateCodec wrapping the compress/decompress paths; integrated into handshake.rs and frame/{parser,serializer}.rs.

20.4 Acceptance Criteria

  • Negotiation fixture set (≥8 cases: no offer, basic offer, both context-takeover flags, window-bits variants, malformed offer) all resolve per RFC 7692 §7.1.
  • A 1 MiB highly-compressible payload (repeated byte pattern) round-trips correctly and the wire size is ≥90% smaller than uncompressed (measured, not asserted).
  • A crafted 1 KiB compressed payload that would decompress to >64 MiB is rejected before full decompression completes (decompression-bomb guard, T6), verified with a streaming size-check test.
  • context_takeover disabled correctly resets compressor state between messages (verified by byte-identical output regardless of prior message content).

20.5 Conformance Fixtures

New fixture tests/conformance/deflate_negotiation.json (≥8 rows); Autobahn's compression cases (12./13.) remain PhaseDeferred("§26") as a blocking CI gate but are run informationally.

20.6 Pitfalls

  • Forgetting the decompression-bomb guard (I9 applied to decompressed size) — the single most security-relevant pitfall in this phase (T6).
  • Resetting the compression window when the negotiated flag says not to (or vice versa) — silently produces garbage on the second message of a multi-message exchange, not the first, making this bug easy to miss in minimal tests.
  • Applying RSV1 semantics without checking that deflate was actually negotiated for this connection — apply P11 strictly, per-connection, not globally.

20.7 Performance Concerns

Compression is CPU-bound; the §32 back-of-envelope model quantifies the CPU-per-connection cost added by enabling deflate — operators should measure before enabling it fleet-wide (ADR-08's rejected-alternative regime).

20.8 Edge Cases

  • Client offers permessage-deflate with parameters the server doesn't support (e.g., an unsupported window-bits value) — server must respond without the extension, not fail the handshake (RFC 7692 §5).
  • A message that doesn't compress well (already-compressed data, e.g. JPEG bytes) — must still round-trip correctly even though the "compressed" output is larger than the input.

20.9 Failure Analysis

Failure class: decompression bomb / resource exhaustion. Detection: streaming decompressed- size check exceeds max_message_size mid-stream. Recovery: abort decompression immediately, Close 1009, apply P1's fail-before-full-allocation discipline to compressed data too.

20.10 Operational Notes

Track compression_ratio_histogram and CPU-time-per-connection separately for deflate-enabled vs. plain connections (§24) — this is the primary signal for the ADR-08 enable/disable decision per deployment.

21. Phase 9 — TLS (wss://) & Production Hardening

21.1 Objectives

Terminate TLS in-process via rustls (ADR-09) ahead of the handshake layer, add certificate loading/rotation, and finalize production-hardening concerns (graceful shutdown edge cases, resource limits) deferred from earlier phases.

21.2 Detailed Implementation Steps

  1. Load a rustls::ServerConfig from a PEM cert+key pair (path from Config, ADR-21) — apply RFC 2818's TLS-over-HTTP model, adapted here to TLS-over-WebSocket.
  2. Wrap the accepted TcpStream in a rustls TlsAcceptor before handing it to §13's handshake parser — apply P9 strictly: the handshake/frame code is TLS-unaware by construction, it only ever sees plaintext.
  3. Add a certificate hot-reload path (watch the cert file, rebuild ServerConfig on change) so cert rotation doesn't require a process restart — operational requirement from §24.
  4. Finalize resource limits: enforce the §4 50k-connection ceiling with an explicit Semaphore at accept time, rejecting new TCP connections (not WebSocket-level) beyond the limit — apply P1's "fail before over-committing" pattern one layer up the stack.
  5. Wire the full graceful-shutdown sequence (§19.2 step 3) to also close the TLS listener socket first, preventing new connections during drain.

21.3 Deliverable

src/tls.rs with build_acceptor(config) -> TlsAcceptor; echo_server gains a --tls config section; full wss:// end-to-end test.

21.4 Acceptance Criteria

  • A wss:// client (using a self-signed test cert) completes handshake + echo + close end-to-end, with TLS handshake latency contributing ≤7 ms of the §4 8 ms p99 handshake budget.
  • Certificate rotation (replacing the PEM file) is picked up within 60 s without dropping existing connections (verified by an in-flight-connection-survives-rotation test).
  • Connection attempt #50,001 (exceeding the semaphore limit) is rejected at the TCP accept layer with a clean connection refusal, not accepted-then-dropped.
  • cargo audit (ADR-22-adjacent supply-chain check, §27) reports zero known vulnerabilities in the TLS dependency chain at release time.

21.5 Conformance Fixtures

tests/tls_integration.rs (new, self-signed test cert generated at test-build time, not committed to the repo per §27's secrets hygiene).

21.6 Pitfalls

  • Placing the frame parser (§14) ahead of the TLS unwrap — instantly breaks everything; P9 exists specifically to make this ordering mistake structurally obvious in code review.
  • Blocking the async runtime on synchronous cert-file reads on the hot accept path — cert loading must happen at startup/rotation time only, never per-connection.
  • Self-signed test certs accidentally shipped in a way that could be mistaken for production certs — keep test fixtures clearly namespaced and never committed with real domain names.

21.7 Performance Concerns

TLS handshake CPU cost (RSA/ECDSA key exchange) is the dominant addition to connection setup latency; session resumption (TLS 1.3 PSK) is a lever if p99 handshake latency approaches the §4 8 ms ceiling under load — tracked as a scaling lever in §29.

21.8 Edge Cases

  • Client attempts a plaintext ws:// connection against a TLS-only listener — must fail fast with a clear TLS handshake error, not hang waiting for a ClientHello that never arrives correctly.
  • Cert file deleted/corrupted mid-rotation-watch — must keep serving the last-known-good ServerConfig, not crash or fall back to no TLS.

21.9 Failure Analysis

Failure class: certificate expiry. Detection: rustls handshake failures spike; a proactive expiry-countdown metric (§24) should page well before expiry, not after clients start failing.

21.10 Operational Notes

TLS handshake failure rate and certificate days-until-expiry are both first-class SLO inputs (§24) — an expired cert is a fully preventable outage class for this design.

24. Operational Readiness

Metrics (exported via src/metrics.rs, Prometheus-style): connection count gauge, per-WsError-variant counters, close_code_histogram, ping_pong_latency_histogram, backpressure_overflow_disconnect_total, compression_ratio_histogram, tls_handshake_failure_total, per-phase latency histograms (handshake, parse, serialize).

Tracing: one tracing span per connection (ADR-16), child spans per frame at debug verbosity only (frame-level spans at info verbosity would be far too high-cardinality for production, per Palmieri §5).

Structured logging: JSON-formatted logs keyed by connection ID; every close event logs the final CloseCode and the state-machine path taken (clean vs. timeout-forced).

Dashboards: (1) connection lifecycle funnel (Connecting→Upgrading→Open→Closing→Closed counts), (2) close-code distribution over time, (3) per-connection memory outlier tracker, (4) TLS cert expiry countdown.

SLOs: handshake success rate ≥ 99.9%; p99 frame round-trip ≤ 500 µs (§4); close-timeout- forced rate < 0.1% of all closes (a proxy for "peers behaving well").

Runbooks: (a) handshake-rejection-spike → check LB header forwarding (FM-1); (b) connections-stuck-in-Upgrading → verify handshake-timeout config (FM-3); (c) 1006-rate spike → correlate with network infra alerts before assuming a server bug (FM-6).

Backup/restore: not applicable — the server is stateless (§4 RTO=0); no persisted state to back up.

Deployment topology: N identical instances behind an L4 (not L7) load balancer — WebSocket connections are long-lived, so L7 request-based routing/health-checking assumptions don't apply; sticky-by-connection only.

Canary/rollback: canary a new binary version to 1% of new connections (existing connections are never migrated mid-flight, per statelessness); rollback = redeploy the prior binary, existing connections on the canary drain naturally via graceful shutdown.

Migration: no schema/storage migration exists in v1 (stateless); a future session- resumption feature (not in scope, §35) would need one.

25. Compatibility & Versioning

Wire format: RFC 6455 framing is itself version-locked at Sec-WebSocket-Version: 13; this server rejects any other version per §13.2 step 2 — there is no internal wire-format versioning to manage beyond what the RFC already fixes.

Extension versioning: permessage-deflate parameters (§20) are renegotiated per-connection at handshake time; no persisted extension state crosses a server restart (statelessness, §4 RTO=0), so extension-version skew across a rolling upgrade is a non-issue — each new connection negotiates fresh against whichever binary version accepted it.

API stability: WsError (§11) is explicitly documented as not #[non_exhaustive] in v1 (§12.6) — adding a new variant is a breaking change for any downstream code matching exhaustively; this is an intentional tradeoff favoring exhaustiveness-checking during active development over external API stability (revisit if/when this becomes a published library rather than an application binary).

SemVer: the echo_server binary and its Config schema (ADR-21) follow SemVer; a breaking Config field rename/removal is a major version bump; new optional fields with defaults are minor.

Deprecation: no deprecated fields exist yet in v1; the policy going forward is a minimum one-minor-version deprecation warning (logged) before removal in the next major.

Rolling-upgrade guarantees: because connections are stateless and negotiate fresh per connection, a rolling upgrade across instances behind the load balancer is safe without draining the whole fleet at once — each instance drains via graceful shutdown (§24) independently.

26. Testing & Verification Strategy

Unit tests: every type in §11 (opcode, header, error taxonomy) exhaustiveness-tested; compute_accept_key against the RFC 6455 §1.3 worked example (§13.4).

Integration tests: tests/integration_echo.rs (§19.5), tests/fragmentation.rs (§16.5), tests/tls_integration.rs (§21.5) — all drive the binary over real TCP sockets.

Property tests: round-trip property (serialize(parse(x)) == x for server-originated frames, §15.4) fuzzed over random valid FrameHeader+payload combinations (proptest).

Differential tests: cross-check this implementation's frame_vectors.json outcomes against tungstenite's parser on the same byte sequences (dev-dependency only, never a runtime dependency, preserving ADR-03) — a mismatch is investigated, not auto-trusted either direction.

Fuzzing: cargo fuzz target over the raw frame-parser entry point (§14), seeded from frame_vectors.json; CI runs a bounded fuzz budget per PR, a longer budget nightly.

Chaos: integration tests that inject ECONNRESET, truncated TLS records, and mid-handshake disconnects (§18.8, §21.8 edge cases) to verify no panics, only clean WsError/close-code paths.

Deterministic replay: frame_vectors.json/close_codes.json/handshake_vectors.json are the deterministic-replay corpus — any bug found in production is first reduced to a fixture row before being fixed, preventing regression.

Soak: a 24-hour soak test holding 10,000 idle-then-active connections, asserting no memory growth beyond the §4 per-connection ceiling times connection count (catches slow leaks §14.4's unit tests can't).

Conformance: Autobahn|Testsuite (§19.4/§19.9) is the external RFC 6455 conformance oracle; the full compression corpus (cases 12./13.) runs informationally only, per PhaseDeferred("§26"), until Phase 8's deflate work graduates from experimental (§35).

Perf-regression gating: benches/frame_bench.rs results are compared against the §28 M-table thresholds in CI; a regression beyond threshold fails the build (§27).

Invariant traceability: every I1–I14 (§7) has at least one fixture row or integration test asserting it directly; every phase's §N.5 fixtures are cross-indexed against the invariant(s) they cover (documented inline in each fixture file's schema comment).

29. Scalability Analysis

Constant regardless of connection count: per-frame parse/serialize cost (O(1) in frame size, amortized O(n) in payload bytes, never in connection count); handshake cost per connection.

Grows with connection count: total memory (O(n) × §4's per-connection ceiling); scheduler bookkeeping (tokio task count); FD count (1:1 with connections).

Grows with message rate × connection count: aggregate CPU (dominated by masking XOR and, if enabled, deflate compression — M7/M10).

Named bottlenecks, in order encountered as load scales up:

  1. Per-connection memory (§4: 16 KiB idle, 48 KiB with deflate) — first ceiling hit, around the 50k-connection mark on a typical 8 GiB instance (§32's derivation).
  2. FD limit — second ceiling, typically raised via ulimit well past the memory ceiling, so rarely the binding constraint in practice.
  3. Single-core CPU saturation from masking XOR + deflate under high message rate — third ceiling, addressed by ADR-07's SIMD lever (rejected-choice-wins regime) before horizontal scaling.
  4. Single-instance connection ceiling (~50k) — the practical ceiling for this design as specified; beyond it, horizontal scale-out is required (PhaseDeferred("§29")).

Horizontal scaling: N stateless instances behind an L4 load balancer (§24); since no cross-connection state exists (no rooms/broadcast in this design's scope, §1), horizontal scaling is embarrassingly parallel — the only work is connection distribution, not data sharding.

Vertical scaling: more cores primarily help CPU-bound masking/compression throughput (M7/M10), not connection-count ceiling, which is memory-bound (item 1 above).

Sharding: not applicable in v1 (no shared state to shard); would become relevant only if a future broadcast/pub-sub layer were added (explicitly out of scope, §1).

Practical ceiling and levers beyond it: ~50k connections/instance is the practical ceiling (§4); levers beyond it, in order of effort: (a) raise per-connection memory efficiency further (smaller default buffers, ADR-06 tuning), (b) horizontal scale-out (PhaseDeferred("§29")), (c) a future connection-routing layer for session affinity if application-level state is ever added.

30. Mental Models & First Principles

MM1 — A frame parser is a pull-based state machine, not a push-based event source. Predicts: the parser must tolerate being called with 1 byte or 1 million bytes and produce the same result either way. Bug class without it: parsers that assume a full frame arrives in one read(), breaking under real TCP fragmentation. Resolving §: §14.

MM2 — Masking is a protocol-level poison-pill defense, not encryption. Predicts: masking never needs a secret key management story (the key is sent in plaintext on the wire); its entire purpose is defeating byte-pattern-dependent caching proxies. Bug class without it: treating the mask key as security-sensitive and over-engineering its handling, or conversely treating masking as optional "obfuscation" that can be relaxed. Resolving §: §8, §22 (T7).

MM3 — A message is a logical unit; a frame is a wire unit; they are not the same thing. Predicts: fragmentation is purely a wire-level chunking concern invisible to the application once reassembled. Bug class without it: application code that assumes 1 recv() == 1 frame == 1 message, breaking the moment a peer fragments (which RFC 6455 explicitly permits any implementation to do at any time). Resolving §: §16.

MM4 — Backpressure is a design decision about who pays for a slow consumer, not a bug to eliminate. Predicts: every unbounded-buffer "fix" for a backpressure symptom just moves the OOM further downstream. Bug class without it: chasing memory leaks that are actually correctly-functioning unbounded buffers doing exactly what they were told. Resolving §: §18, §23 (FM-4).

MM5 — A close handshake needs a timeout because "wait for the peer" is not a valid terminal state. Predicts: any protocol with a bidirectional handshake needs an explicit timeout/fallback, or a single hung peer holds server resources indefinitely. Bug class without it: connections that never reach Closed, silently leaking. Resolving §: §17, §23 (FM-6).

MM6 — An extension changes wire semantics, not just adds new message types. Predicts: the same bit pattern (RSV1 set) means different things depending on negotiated state, so extension-aware code must be state-dependent, not purely a function of the bytes on the wire. Bug class without it: RSV1 misinterpreted identically regardless of whether the extension was actually negotiated for that connection. Resolving §: §20.

MM7 — Statelessness turns "scale horizontally" into a load-balancing problem, not a data problem. Predicts: this design's scale-out story never needs consensus, replication, or sharding — only connection distribution. Bug class without it: over-engineering a coordination layer for a system that has no shared state to coordinate. Resolving §: §29.

MM8 — Every attacker-controlled length field is a potential allocation-size attack vector until proven bounded. Predicts: any length read directly off the wire needs a ceiling check before it touches an allocator. Bug class without it: length-prefixed protocols are a classic DoS vector precisely because this check is easy to skip. Resolving §: §14 (P1, P12), §22 (T3, T4).

32. Back-of-Envelope Capacity Model

  1. Per-connection idle memory (from §4): read buffer 4 KiB + write buffer 4 KiB + state (ConnectionState, Reassembler empty buffer, timers) ≈ 8 KiB ⇒ 16 KiB total.

  2. Memory at 50,000 connections, no compression: 50,000 × 16 KiB = 800,000 KiB ≈ 781 MiB — comfortably within an 8 GiB instance, leaving headroom for the OS/runtime.

  3. Memory at 50,000 connections, with permessage-deflate (§4: 48 KiB/conn): 50,000 × 48 KiB = 2,400,000 KiB ≈ 2.34 GiB — still fits an 8 GiB instance but with meaningfully less headroom; this is the number that motivates ADR-08's "measure before fleet-wide enable" stance.

  4. File descriptors at 50,000 connections: 1 FD/connection + a handful for listener/logging ⇒ ~50,050 FDs, requiring ulimit -n raised well above the Linux default (1024) — sized directly from §4's connection ceiling.

  5. Aggregate masking-XOR CPU at peak message rate: assume 10,000 msgs/sec at 1 KiB average payload = 10 MiB/s of XOR work; at M7's ≥2 GB/s/core target, that's ≈0.5% of one core — negligible, confirming masking is never the CPU bottleneck at this scale.

  6. Aggregate compression CPU, deflate enabled, same message rate: compression is roughly 10–50× more CPU-expensive per byte than XOR (typical flate2/zlib measurements) ⇒ 10 MiB/s × ~30× ≈ 300 MiB/s-equivalent of compressor work ⇒ at a rough ~500 MiB/s/core compression throughput, ≈0.6 cores dedicated to compression at this message rate — the first real CPU cost in the design, directly informing the M10/ADR-08 enable decision.

  7. Bandwidth at 50,000 connections, 1 KiB messages, 10 msgs/sec/connection: 50,000 × 1 KiB × 10/s = 500,000 KiB/s ≈ 488 MiB/s ≈ 3.9 Gbps — sized directly from a plausible per-connection chat-app-style rate, showing network egress, not CPU, dominates at this traffic shape.

  8. Backpressure queue memory ceiling per connection: 256 frames (§4) × a conservative 4 KiB average frame size = 1 MiB worst-case per connection if every queue is completely full simultaneously; at 50,000 connections that's a worst-case 48.8 GiB — far exceeding typical instance memory, which is exactly why ADR-12's disconnect-on-overflow policy exists rather than tolerating that worst case.

  9. Handshake CPU cost at peak connection-churn: SHA-1 over a 36-byte input (16-byte key

    • 20-byte GUID... actually key+GUID string ≈ 60 bytes) takes low-single-digit microseconds; even at 10,000 new connections/sec, that's ≈0.01–0.05 cores — confirms M1's 1 ms p50 target is dominated by I/O, not the SHA-1 computation itself.

  10. TLS handshake CPU at the same churn rate: a modern ECDSA TLS 1.3 handshake costs roughly 0.1–1 ms of CPU depending on hardware; at 10,000 new connections/sec that's ≈1–10 cores dedicated purely to TLS handshakes at peak churn — the number that justifies session-resumption (§21.7) as the first lever if handshake-heavy churn patterns (e.g., mobile clients reconnecting frequently) dominate the workload.

34. Alternative Architectures (Roads Not Taken)

Alternative 1 — Thread-per-connection (OS threads, blocking I/O).

[conn 1] --- OS thread 1 --- blocking read()/write()
[conn 2] --- OS thread 2 --- blocking read()/write()
[conn N] --- OS thread N --- blocking read()/write()

Regime where it wins: moderate connection counts (≤ a few thousand) with CPU-bound per-message handlers that benefit from full OS scheduler preemption and the ability to call blocking syscalls freely without an async runtime's cooperative-scheduling constraints. Real system: Apache HTTP Server's mpm_prefork/mpm_worker model embodies this for HTTP; classic Java servlet containers do the same for WebSocket via blocking servlet I/O. Rejected here because per-thread stack memory (typically 1–8 MiB) caps concurrency far below the §4 50,000-connection target (Pariag et al., EuroSys 2007, §5).

Alternative 2 — Single-threaded event loop (one reactor, no task-per-connection).

        ┌─────────────────────────────┐
        │   single-threaded reactor    │
        │  epoll_wait() → dispatch     │
        │  conn1.on_readable()         │
        │  conn2.on_readable()         │
        │  ... connN.on_readable()     │
        └─────────────────────────────┘

Regime where it wins: workloads dominated by I/O wait rather than CPU, where avoiding multi-core synchronization overhead entirely outweighs the inability to use more than one core. Real system: Node.js's ws library (§31) and Redis's core event loop both embody this. Rejected here because it caps aggregate throughput to a single core's masking/ compression capacity (§28 M7/M10), whereas tokio's multi-threaded work-stealing scheduler (ADR-02) uses all available cores for the same workload.

Alternative 3 — Actor-model / message-passing-only architecture (no shared mutable connection state, every connection a supervised actor).

[Supervisor] ─spawns─▶ [Conn Actor 1] ──mailbox──▶ (frame in/out)
             ─spawns─▶ [Conn Actor 2] ──mailbox──▶ (frame in/out)
             ─spawns─▶ [Conn Actor N] ──mailbox──▶ (frame in/out)

Regime where it wins: systems needing supervision trees, hot-code-reload, and let-it-crash fault isolation at the individual-connection level as a first-class primitive, not just as an emergent property of task isolation. Real system: Erlang/Elixir's Phoenix Channels (built on OTP actors) embodies this for WebSocket at scale. Rejected here because Rust's ownership model already gives per-connection isolation (I11's structural guarantee) without needing a full actor runtime's message-passing overhead for what is, in this design's scope, a single-application (not multi-tenant-fault-domain) server.

36. Glossary

  • Autobahn|Testsuite — external RFC 6455/7692 conformance-testing tool (Crossbar.io), the fuzzing oracle used in §26.
  • Backpressure — a mechanism that slows or stops a producer when a consumer cannot keep up, preventing unbounded buffering (§6 P3).
  • BytesMut — a growable, mutable byte-buffer type (bytes crate) used for zero-copy frame construction (ADR-06, ADR-20).
  • Close code — a 16-bit status code sent in a Close frame's payload indicating why the connection is closing (RFC 6455 §7.4, §11 CloseCode).
  • Continuation frame — opcode 0x0; carries the next chunk of a fragmented message (§8).
  • Context takeover — whether a permessage-deflate compressor/decompressor's sliding window persists across messages on one connection (RFC 7692 §7.2.1, §20).
  • Control frame — Ping, Pong, or Close (opcodes 0x8–0xA); ≤125-byte payload, never fragmented (§8, I6).
  • Data frame — Text or Binary (opcodes 0x1–0x2); the only frame types that may be fragmented (§8).
  • DEFLATE — the compression algorithm (RFC 1951) underlying permessage-deflate (§20).
  • Extended payload length — the 16-bit or 64-bit length field present when the 7-bit length field encodes 126 or 127 (§8).
  • Extension negotiation — the Sec-WebSocket-Extensions header exchange that enables optional wire-format behaviors like permessage-deflate (§20).
  • FIN bit — the frame-header bit indicating whether this is the final frame of a message (§8).
  • Fragmentation — splitting one logical message across multiple frames (§8, §16).
  • Frame — a single RFC 6455 wire unit; the atomic unit the parser/serializer operate on (§8, §11).
  • GUID (WebSocket magic string) — 258EAFA5-E914-47DA-95CA-C5AB0DC85B11, concatenated with the client key before SHA-1 hashing (RFC 6455 §4.2.2, §13).
  • Handshake — the HTTP/1.1 Upgrade request/response exchange that transitions a TCP connection into WebSocket framing mode (§8, §13).
  • httparse — the crate used to tokenize the HTTP/1.1 handshake request (ADR-18).
  • Idle timeout — the duration after which a connection with no frame/Pong activity is force-closed (I13, §4).
  • Masking key — a 4-byte value XOR'd against a client frame's payload (§8, P2).
  • Message — the logical unit an application sends/receives, possibly reassembled from multiple frames (§8, §16, MM3).
  • mpsc — multi-producer single-consumer channel; used for the bounded writer queue (ADR-11, §18).
  • Opcode — the 4-bit field identifying frame type (Text, Binary, Close, Ping, Pong, Continuation) (§8, §11).
  • permessage-deflate — the RFC 7692 WebSocket compression extension (§20).
  • Ping/Pong — control frames used for liveness/keepalive; every Ping gets exactly one Pong reply (I14, §17).
  • Protocol error — any violation of an RFC 6455 MUST, mapped to a specific close code via WsError (§11, P14).
  • Reassembler — the component accumulating fragmented messages into one logical unit (§11, §16).
  • RSV1/RSV2/RSV3 — reserved frame-header bits, repurposed by extensions when negotiated (§8, I4, P11).
