Hard questions (§33)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why must Sec-WebSocket-Accept be a deterministic function of the client's key rather than a server-chosen random value? (§8, §13)
  2. Trace exactly what happens, state by state, if a Ping frame arrives as the 3rd byte of a 50-fragment Text message's 27th fragment. (§16, §17)
  3. Why does I3 make server-side masking a compile-time impossibility rather than a runtime check, and what class of bug does that eliminate that I2's runtime check does not? (§7, §11)
  4. If max_message_size were checked only after full reassembly instead of incrementally, what specific attack becomes possible that ADR-13's chosen approach prevents? (§9, §22 T4)
  5. Why is TLS termination placed structurally before the frame parser rather than the frame parser being made "TLS-aware"? What principle does this violate if reversed? (§6 P9, §21)
  6. Derive, from the §4 constraints alone, why 50,000 is the approximate connection ceiling for a single instance rather than some order-of-magnitude larger or smaller number. (§4, §32)
  7. What exactly changes in RSV1's meaning before vs. after a successful permessage-deflate negotiation, and why is this a hazard that P11 exists specifically to prevent? (§6, §20)
  8. Why does the design choose task-per-connection over both OS-thread-per-connection and a single-threaded event loop, and under what load characteristics would each rejected alternative actually be the better choice? (§9 ADR-10, §29, §31)
  9. Walk through why a close-handshake timeout is necessary even though RFC 6455 defines a clean bidirectional close sequence — what specifically can go wrong without it? (§17, §23 FM-6)
  10. Why is the decompression-bomb guard (T6) checking the decompressed size during streaming rather than the compressed size on the wire, and what would break if it checked the wrong one? (§20, §22)
  11. Explain the exact interaction between the single-writer invariant (I11) and the bounded backpressure queue (ADR-12) — could either exist without the other and still prevent frame interleaving? (§7, §9, §18)
  12. Why does this blueprint reject an unbounded read/write buffer even though it would simplify the code, and what specific §32 number quantifies the cost of that simplicity if it were adopted? (§6 P3/P6, §32)
  13. If Autobahn|Testsuite passed 100% on cases 1–9 but the compression cases (12./13.) were never run, what could still be silently broken, and why does §35's deferred- feature framing treat that as an acceptable, explicit tradeoff rather than a gap? (§26, §35)
  14. Compare how this design's statelessness simplifies horizontal scaling (§29) against what would change if a future broadcast/room feature were added — name the new system-design class this would introduce. (§29, §34)
  15. Why does the design pin the async runtime to tokio (ADR-02) rather than remaining runtime-agnostic like tungstenite-rs (§31), and what concrete capability is traded away by that choice? (§9, §31)
  16. Explain precisely why UTF-8 validation (I12) is applied incrementally per fragment rather than only once at message completion, tracing the specific Autobahn/attack scenario this ordering choice defends against. (§7, §9 ADR-15, §16)
  17. What would have to be true about a deployment's traffic pattern for the "when rejected choice wins" column of ADR-07 (SIMD masking) to actually trigger, and how would an operator detect that threshold had been crossed? (§9, §24, §28 M7)
  18. Trace the complete lifecycle of a connection that never sends a single WebSocket frame after a successful handshake, until it is finally cleaned up — which invariant and which timer is responsible, and what is the maximum time it can linger? (§7 I13, §17)

30. Mental Models & First Principles

MM1 — A frame parser is a pull-based state machine, not a push-based event source. Predicts: the parser must tolerate being called with 1 byte or 1 million bytes and produce the same result either way. Bug class without it: parsers that assume a full frame arrives in one read(), breaking under real TCP fragmentation. Resolving §: §14.

MM2 — Masking is a protocol-level poison-pill defense, not encryption. Predicts: masking never needs a secret key management story (the key is sent in plaintext on the wire); its entire purpose is defeating byte-pattern-dependent caching proxies. Bug class without it: treating the mask key as security-sensitive and over-engineering its handling, or conversely treating masking as optional "obfuscation" that can be relaxed. Resolving §: §8, §22 (T7).

MM3 — A message is a logical unit; a frame is a wire unit; they are not the same thing. Predicts: fragmentation is purely a wire-level chunking concern invisible to the application once reassembled. Bug class without it: application code that assumes 1 recv() == 1 frame == 1 message, breaking the moment a peer fragments (which RFC 6455 explicitly permits any implementation to do at any time). Resolving §: §16.

MM4 — Backpressure is a design decision about who pays for a slow consumer, not a bug to eliminate. Predicts: every unbounded-buffer "fix" for a backpressure symptom just moves the OOM further downstream. Bug class without it: chasing memory leaks that are actually correctly-functioning unbounded buffers doing exactly what they were told. Resolving §: §18, §23 (FM-4).

MM5 — A close handshake needs a timeout because "wait for the peer" is not a valid terminal state. Predicts: any protocol with a bidirectional handshake needs an explicit timeout/fallback, or a single hung peer holds server resources indefinitely. Bug class without it: connections that never reach Closed, silently leaking. Resolving §: §17, §23 (FM-6).

MM6 — An extension changes wire semantics, not just adds new message types. Predicts: the same bit pattern (RSV1 set) means different things depending on negotiated state, so extension-aware code must be state-dependent, not purely a function of the bytes on the wire. Bug class without it: RSV1 misinterpreted identically regardless of whether the extension was actually negotiated for that connection. Resolving §: §20.

MM7 — Statelessness turns "scale horizontally" into a load-balancing problem, not a data problem. Predicts: this design's scale-out story never needs consensus, replication, or sharding — only connection distribution. Bug class without it: over-engineering a coordination layer for a system that has no shared state to coordinate. Resolving §: §29.

MM8 — Every attacker-controlled length field is a potential allocation-size attack vector until proven bounded. Predicts: any length read directly off the wire needs a ceiling check before it touches an allocator. Bug class without it: length-prefixed protocols are a classic DoS vector precisely because this check is easy to skip. Resolving §: §14 (P1, P12), §22 (T3, T4).

Required reading (§5)

Books

  • W. Richard Stevens — TCP/IP Illustrated, Volume 1: The Protocols (Addison-Wesley, 1993), Ch. 17–18 (TCP data flow, retransmission, Nagle). Extract: why a WebSocket frame parser must never assume one read() returns one frame. Applied in §14 / Phase 2.
  • W. Richard Stevens, Bill Fenner, Andrew M. Rudoff — UNIX Network Programming, Volume 1, 3rd ed. (Addison-Wesley, 2003), Ch. 6 (I/O Multiplexing: select/poll). Extract: readiness-based event loops and partial-write handling. Applied in §18 / Phase 6.
  • Jim Blandy, Jason Orendorff, Leonora F. S. Tindall — Programming Rust, 2nd ed. (O'Reilly, 2021), Ch. 19 (Concurrency), Ch. 21 (Async). Extract: ownership across .await points, Send/Sync bounds for shared connection state. Applied in §18 / Phase 6.
  • Jon Gjengset — Rust for Rustaceans (No Starch Press, 2021), Ch. 4 (Error Handling), Ch. 8 (Asynchronous Programming). Extract: typed error taxonomies that map cleanly to protocol-level close codes. Applied in §11 / Core Schema.
  • Martin Kleppmann — Designing Data-Intensive Applications (O'Reilly, 2017), Ch. 4 (Encoding and Evolution). Extract: framing/length-prefixing tradeoffs and forward/backward wire-format compatibility. Applied in §25 / Compatibility & Versioning.
  • Luca Palmieri — Zero To Production In Rust (self-published, 2022), Ch. 3–4 (structured logging, telemetry, tracing instrumentation). Extract: span-per-request patterns adapted here to span-per-connection/span-per-frame. Applied in §24 / Operational Readiness.

Papers

  • Welsh, M., Culler, D., Brewer, E. — "SEDA: An Architecture for Well-Conditioned, Scalable Internet Services," SOSP 2001. Contribution: staged event-driven architecture with admission control as a backpressure mechanism. Applied in §18 / Phase 6.
  • von Behren, R., Condit, J., Brewer, E. — "Why Events Are a Bad Idea (for High-Concurrency Servers)," HotOS 2003. Contribution: critique of pure event-driven models vs. threads. Applied in §9 (ADR-02, ADR-10 tradeoff analysis).
  • Pariag, D., Brecht, T., Harji, A., Buhr, P., Shukla, A., Cherenson, A. — "Comparing the Performance of Web Server Architectures," EuroSys 2007. Contribution: empirical thread-pool vs. event-driven comparison under load. Applied in §29 / Scalability Analysis.
  • Han, S., Marshall, S., Chun, B.-G., Ratnasamy, S. — "MegaPipe: A New Programming Interface for Scalable Network I/O," OSDI 2012. Contribution: per-core listening sockets reduce lock contention at high connection counts. Applied in §29.
  • Fielding, R. T. — Architectural Styles and the Design of Network-based Software Architectures, PhD dissertation, UC Irvine, 2000. Contribution: formalizes HTTP's stateless request/response model, the baseline WebSocket's persistent connection breaks from. Applied in §2 / Why Build This.
  • Kohler, E., Morris, R., Chen, B., Jannotti, J., Kaashoek, M. F. — "The Click Modular Router," ACM TOCS 18(3), 2000. Contribution: composable packet-processing pipeline model. Applied in §14 / Phase 2 (parse → validate → dispatch pipeline).
  • Nielsen, H. F., Gettys, J., Baird-Smith, A., et al. — "Network Performance Effects of HTTP/1.1, CSS1, and PNG," SIGCOMM 1997. Contribution: quantifies persistent-connection latency wins over per-request connections. Applied in §2.
  • Ousterhout, J. — "Why Threads Are A Bad Idea (for most purposes)," USENIX Winter Technical Conference invited talk, 1996. Contribution: threading hazards (races, deadlocks) motivating a single-writer-per-connection invariant. Applied in §7 (I11).

Reference Implementations

  • tungstenite-rs (github.com/snapview/tungstenite-rs) — study src/protocol/frame.rs, src/handshake/. Lesson: I/O-independent state-machine codec. Pitfall: unbounded buffer growth if max_message_size isn't configured. Applied in §14 / §16.
  • tokio-tungstenite (github.com/snapview/tokio-tungstenite) — study src/lib.rs, src/compat.rs. Lesson: wrapping a sync codec in an async Sink/Stream. Pitfall: backpressure is only as strong as the underlying AsyncWrite. Applied in §18.
  • uWebSockets (github.com/uNetworking/uWebSockets) — study src/WebSocketProtocol.h. Lesson: zero-copy in-place XOR unmasking. Pitfall: manual memory management raises UB risk that Rust's ownership model avoids by construction. Applied in §29 / §31.
  • Autobahn|Testsuite (github.com/crossbario/autobahn-testsuite) — study testsuite/websocket/cases/. Lesson: exhaustive conformance case IDs (1.–13.) covering masking, fragmentation, UTF-8, compression edge cases. Pitfall: fuzz cases assume a specific error→close-code mapping; deviating fails silently unless checked. Applied in §26.
  • ws (github.com/websockets/ws, Node.js) — study lib/receiver.js, lib/sender.js. Lesson: separate Receiver/Sender classes mirror the decode/encode split used here. Pitfall: relies on the drain event, not a true bounded queue, for backpressure. Applied in §9 (ADR-11).
  • python-websockets (github.com/python-websockets/websockets) — study src/websockets/protocol.py. Lesson: one coroutine models the whole connection lifecycle state machine. Pitfall: doesn't generalize to non-async/non-single-task runtimes. Applied in §18.

Glossary (§36) · 37 terms · site-wide glossary

Autobahn|Testsuite
external RFC 6455/7692 conformance-testing tool (Crossbar.io), the fuzzing oracle used in §26.
Backpressure
a mechanism that slows or stops a producer when a consumer cannot keep up, preventing unbounded buffering (§6 P3).
BytesMut
a growable, mutable byte-buffer type (bytes crate) used for zero-copy frame construction (ADR-06, ADR-20).
Close code
a 16-bit status code sent in a Close frame's payload indicating why the connection is closing (RFC 6455 §7.4, §11 CloseCode).
Continuation frame
opcode 0x0; carries the next chunk of a fragmented message (§8).
Context takeover
whether a permessage-deflate compressor/decompressor's sliding window persists across messages on one connection (RFC 7692 §7.2.1, §20).
Control frame
Ping, Pong, or Close (opcodes 0x8–0xA); ≤125-byte payload, never fragmented (§8, I6).
Data frame
Text or Binary (opcodes 0x1–0x2); the only frame types that may be fragmented (§8).
DEFLATE
the compression algorithm (RFC 1951) underlying permessage-deflate (§20).
Extended payload length
the 16-bit or 64-bit length field present when the 7-bit length field encodes 126 or 127 (§8).
Extension negotiation
the Sec-WebSocket-Extensions header exchange that enables optional wire-format behaviors like permessage-deflate (§20).
FIN bit
the frame-header bit indicating whether this is the final frame of a message (§8).
Fragmentation
splitting one logical message across multiple frames (§8, §16).
Frame
a single RFC 6455 wire unit; the atomic unit the parser/serializer operate on (§8, §11).
GUID (WebSocket magic string)
258EAFA5-E914-47DA-95CA-C5AB0DC85B11, concatenated with the client key before SHA-1 hashing (RFC 6455 §4.2.2, §13).
Handshake
the HTTP/1.1 Upgrade request/response exchange that transitions a TCP connection into WebSocket framing mode (§8, §13).
httparse
the crate used to tokenize the HTTP/1.1 handshake request (ADR-18).
Idle timeout
the duration after which a connection with no frame/Pong activity is force-closed (I13, §4).
Masking key
a 4-byte value XOR'd against a client frame's payload (§8, P2).
Message
the logical unit an application sends/receives, possibly reassembled from multiple frames (§8, §16, MM3).
mpsc
multi-producer single-consumer channel; used for the bounded writer queue (ADR-11, §18).
Opcode
the 4-bit field identifying frame type (Text, Binary, Close, Ping, Pong, Continuation) (§8, §11).
permessage-deflate
the RFC 7692 WebSocket compression extension (§20).
Ping/Pong
control frames used for liveness/keepalive; every Ping gets exactly one Pong reply (I14, §17).
Protocol error
any violation of an RFC 6455 MUST, mapped to a specific close code via WsError (§11, P14).
Reassembler
the component accumulating fragmented messages into one logical unit (§11, §16).
RSV1/RSV2/RSV3
reserved frame-header bits, repurposed by extensions when negotiated (§8, I4, P11).
rustls
the pure-Rust TLS library used for wss:// termination (ADR-09, §21).
SHA-1
the hash function used to compute Sec-WebSocket-Accept (RFC 3174, §13).
Sec-WebSocket-Accept
the handshake response header proving the server understood the handshake (RFC 6455 §4.2.2, I1).
Sec-WebSocket-Key
the client's base64-encoded 16-byte handshake nonce (§13).
Sec-WebSocket-Version
the handshake header declaring protocol version; this server requires exactly 13 (§13).
tokio
the async runtime this design is built on (ADR-02).
tungstenite
the reference WebSocket library this design deliberately avoids depending on, while validating against its test vectors (ADR-03, §5, §26).
Upgrade mechanism
the HTTP/1.1 feature (RFC 7230 §6.7) that allows a connection to switch protocols after a 101 Switching Protocols response (§13).
UTF-8 validation
the check applied to reassembled Text-message payloads (I12, RFC 6455 §8.1).
wss://
the TLS-secured WebSocket URI scheme, implemented in §21.
