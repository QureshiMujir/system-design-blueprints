203 — Geo-Partitioned Database from Scratch

Project Number: 203

Project Name: Geo-Partitioned Database from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition. A geo-partitioned database is a distributed, replicated, transactional key-value store that shards its keyspace into partitions bound to geographic regions, replicates each partition via quorum consensus across region-local replica sets, and exposes tunable-consistency reads/writes routed by locality. This blueprint specifies such a system built from first principles in Rust: a Raft-replicated LSM storage engine, a transaction coordinator running two-phase commit over Raft-replicated intents, a metadata control plane owning partition-to-region placement, and a locality-aware routing gateway — plus the observability, deterministic-simulation, and conformance infrastructure required to operate it in production.

Phase 0 deliverable — crates and services (see §10 tree, §37 inventory):

  1. protocol — wire schemas: Protobuf messages, framing, codec.
  2. topology-controller — placement reconciliation loop, rebalance throttling.
  3. gateway — routing-gateway binary: locality-aware dispatch, admission control.
  4. raft-engine — raft-replica-engine: quorum replication, elections, log.
  5. replication-log — WAL, segment rotation, catch-up streaming, retention.
  6. storage-engine — lsm-storage-engine: memtable, SSTable, compaction, MVCC.
  7. txn-coordinator — transaction-coordinator: timestamp oracle, locks, 2PC.
  8. metadata-service — topology maps, partition ownership, lease authority.
  9. observability — metrics/tracing/replay-capture exporters.
  10. admin-cli — operator command surface.
  11. simulator — deterministic-simulator: fault injection, scheduler.
  12. benchmark-runner — Criterion-based workload driver.
  13. conformance-harness — fixture-driven conformance suite runner.

System boundaries.

  • Provides: partitioned KV storage, quorum-replicated durability, serializable transactions bounded to a declared partition set, locality-aware routing, deterministic crash recovery, deep observability.
  • Delegates: service discovery to Kubernetes DNS, certificate issuance to an external CA (cert-manager-compatible), cold snapshot archival to S3-compatible object storage, alert routing to Alertmanager, container orchestration to Kubernetes StatefulSets.
  • Does NOT provide (Phase 0): OLAP execution, arbitrary cross-partition joins, unbounded multi-master conflict resolution, full ANSI SQL, serverless multi-tenant isolation, hyperscaler-parity global placement optimization.

Non-goals: parity with Spanner/CockroachDB Cloud turnkey global SLAs in Phase 0; non-Linux hosts; non-x86_64 targets before Phase 6; a general-purpose cost-based query optimizer; synchronous multi-region writes faster than speed-of-light RTT allows (§4 inter-region RTT budget is a floor, not a target to beat).

Deployment model: Linux x86_64 only. Kubernetes StatefulSet per regional node pool, or bare-metal with systemd units. One Raft consensus group per shard range. Dedicated control-plane nodes run metadata-service + topology-controller, isolated from data-plane replica nodes. Minimum 3 regions; odd-numbered replication factor (3 or 5, per §4).

Target operators: systems engineers, distributed-systems researchers, platform/SRE teams, database implementers.

What later phases unlock (deferred beyond Phase 9, registered in §35):

  • PhaseDeferred("§21") — online partition splitting, adjacent to the migration mechanics built in Phase 9.
  • PhaseDeferred("§18") — CDC and external replication, adjacent to the metadata/replication-log boundary built in Phase 6.
  • PhaseDeferred("§19") — multi-tenant resource governance, adjacent to the admission-control path built in Phase 7.
  • PhaseDeferred("§15") — follower reads, adjacent to the lease-read mechanics built in Phase 3.
  • PhaseDeferred("§16") — online schema evolution, HTAP execution, and vectorized execution, adjacent to the storage-engine boundary built in Phase 4.

Recommended language: Rust 1.82+. Rationale: memory safety without GC pauses keeps p99 write latency (§4) free of stop-the-world pauses during compaction bursts; an ownership model that makes replicated-state mutation exclusivity a compile-time property directly supports P1 and P9 (§6); a mature async ecosystem (Tokio, quinn/QUIC) suits the RPC fan-out in §13; a strong type system encodes protocol invariants (WalEntry, TxnRecord, §11) so illegal states are unrepresentable; a well-defined unsafe boundary contains the lock-free and io_uring code that cannot be avoided in a storage engine. Rejected — Go: GC pauses interact badly with the p99 write-latency budget in §4, and its weaker aliasing discipline permits accidental concurrent mutation of replicated state, which directly violates P1. Rejected — C++: the memory-safety burden on a codebase with this much unsafe-adjacent concurrency (lock-free queues, direct IO) raises defect rates beyond what a correctness-first system (priority order: correctness, observability, maintainability, performance) can tolerate; Rust's borrow checker converts a class of these defects into compile errors instead of production incidents.

Prerequisites: distributed systems theory, consensus algorithms, OS internals (scheduler, page cache, io_uring), storage-engine internals (WAL, LSM, compaction), concurrency and synchronization, TCP/TLS/QUIC internals, serialization protocols (Protobuf), failure-recovery theory, distributed tracing.

Estimated timeline: Phase 0 (repo skeleton + correctness kernel, §12): 2–3 weeks. Full system through Phase 9 to single-cluster production-grade stabilization: 8–12 months, including hardening beyond the raw phase durations in Appendix B (§38). Multi-region hardening beyond that: an additional 6 months.

2. Why Build This

This project teaches geo-aware replication semantics, distributed transaction coordination, deterministic consensus integration, locality-aware routing, quorum-safety engineering, storage-engine internals, operational failure containment, distributed observability, and online topology migration — as one coherent system, not isolated katas.

Historically, geo-partitioned systems sit at the convergence of distributed databases (Bigtable, Spanner, CockroachDB), networking systems (QUIC, service meshes), consensus engines (Raft, Paxos), log-structured storage engines (LevelDB, RocksDB lineage), control planes (Kubernetes-style reconciliation loops), and fault-tolerant orchestration (Jepsen-style verification, chaos engineering).

The project exercises lock-free concurrency, WAL durability, snapshot recovery, quorum management, distributed tracing, scheduler design, compaction engineering, cross-region replication economics, and backpressure propagation end-to-end, where each subsystem's failure mode is another subsystem's invariant — a WAL torn write is a Raft replay bug is a transaction-coordinator recovery path.

Related projects: distributed KV stores (etcd, TiKV), Raft consensus engines, SQL query planners, log-structured storage engines (RocksDB), RPC frameworks (tonic/gRPC), Kubernetes-style controllers, metadata control planes (CockroachDB pkg/kv), service meshes, observability stacks (Prometheus/OpenTelemetry).

Calibration value: implementing this system permanently raises capability in distributed-correctness reasoning, operational reasoning under partial failure, debugging via deterministic replay, tail-latency performance analysis, and systems API design — skills that transfer directly to any consensus-backed or replicated system, not just databases.

What Mastery Looks Like

  • Can prove why monotonic commit-index advancement (I3) is necessary and sufficient for replay-safe recovery — exercised building raft-engine in §15 (Phase 3).
  • Can diagnose a split-brain incident from term/epoch telemetry alone, without a debugger — exercised in §22 Threat Model and §15.9 Failure Analysis.
  • Can reason quantitatively about LSM write-amplification tradeoffs instead of qualitatively — exercised in §16 (Phase 4) and §28 Performance Engineering.
  • Can design a timestamp oracle that survives coordinator crash mid-commit without violating serializability — exercised in §17 (Phase 5).
  • Can build a deterministic simulator that reproduces a distributed bug from a seed alone — exercised in §20 (Phase 8).
  • Can derive a capacity model from first principles instead of quoting vendor numbers — exercised in §32 Back-of-Envelope Capacity Model.
  • Can articulate, for every architectural decision, the concrete regime in which the rejected alternative would have been correct — exercised across §9 ADR Table and §34 Alternative Architectures.
  • Can route a request by locality and degrade gracefully under partition-map staleness — exercised in gateway, §19 (Phase 7).

Client Applications — untrusted external boundary; speak the protocol wire schema over QUIC/TLS 1.3 only (ADR-07, ADR-18); never address a replica directly.

gateway (Routing Gateway Layer) — trust boundary terminates client TLS, authenticates (RBAC), enforces admission control against a bounded ingress queue (P3), and dispatches by locality using a cached partition map from metadata-service. Retries are budgeted, not unbounded (pitfall in §19.6).

txn-coordinator — stateless except for durable TxnRecord metadata (§11); owns the timestamp oracle, write-intent lifecycle, and deadlock detection; issues 2PC prepare/commit against the owning raft-engine groups. Protocol boundary: every message crossing into a replica group is a Protobuf AppendEntries-family message (§8).

metadata-service / topology-controller — sole authority for partition ownership, lease assignment, and topology epoch; topology-controller is the reconciliation loop that plans placement changes and enqueues them, epoch-fenced against metadata-service's serialized topology store (P9, I2).

raft-engine — one consensus group per shard range (§4 cap: 7 replicas max); concurrency boundary is one active writer (leader) per partition per epoch; commit index is monotonic (I3) and is the handoff point to storage-engine.

replication-log — durability boundary: WAL fsync precedes any visibility (I1, StorageEngine guarantee in §11); owns segment rotation, snapshot markers, catch-up streaming to lagging followers, and retention/truncation policy.

storage-engine — MVCC over an LSM tree: memtable (mutable, in-memory) → immutable SSTable flush → background compaction; bloom filters bound negative-lookup cost; persistence boundary is the same fsync point replication-log enforces.

observability + simulator + admin-cli — external interfaces: Prometheus scrape endpoint, OTLP trace export, structured JSON log stream, deterministic replay capture (consumed by simulator and conformance-harness), and the admin-cli operator surface (topology inspection, drains, canaries).

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every replicated state transition is a pure function of (state, input) · Tradeoff: forbids wall-clock reads inside the apply path, forces logical/hybrid clocks · Operational: simulator (§20) replays every mutation bit-for-bit · Violated: replicas silently diverge and consensus corrupts with no crash to alert on.
  • P2 — Crash-Only Recovery. Rule: recovery paths assume abrupt termination; no code path may depend on graceful shutdown for correctness · Tradeoff: doubles the testing surface, every path exercised via SIGKILL as well as SIGTERM · Operational: simulator fault injection kills processes mid-write (§20.5) · Violated: a "clean shutdown only" bug becomes a data-loss bug the first time the process OOMs.
  • P3 — Backpressure Everywhere. Rule: every queue is bounded and instrumented, no unbounded channel anywhere in the write or replication path · Tradeoff: overload surfaces sooner as shed requests instead of hidden latency · Operational: queue depth exported per stage (§24) with alert thresholds · Violated: memory grows unbounded under load until an OOM-kill takes the whole node, not just the offending request.
  • P4 — Observability By Default. Rule: no subsystem ships without metrics and structured traces wired before feature code · Tradeoff: adds roughly 10–15% implementation time per phase · Operational: observability exporters are a Phase 0 dependency of every other crate · Violated: an incident becomes undebuggable because the relevant span was never emitted.
  • P5 — Replayability First. Rule: every consensus mutation must be replayable from persisted logs alone · Tradeoff: forbids optimizations that skip logging "obviously safe" mutations · Operational: conformance-harness replays every fixture's WAL and diffs resulting state · Violated: crash recovery cannot reconstruct state and a replica must be rebuilt from a healthy peer instead of its own log.
  • P6 — Bounded Resource Usage. Rule: memory growth is bounded under all reachable states, including sustained partial failure · Tradeoff: bounded memtables and intent tables force earlier flush or abort under load · Operational: bound checks are asserted inside the deterministic simulator, not merely documented · Violated: a slow follower causes leader-side buffering to grow until the OS kills the node.
  • P7 — Stable Wire Compatibility. Rule: protocol evolution is additive only, no field removal or renumbering across a minor version · Tradeoff: accumulates deprecated fields prunable only at major-version boundaries · Operational: protocol Protobuf schemas are diffed against the previous release in CI (§25) · Violated: a rolling upgrade partitions the cluster into two wire-incompatible camps.
  • P8 — No Hidden Coordination. Rule: any cross-node coordination is an explicit, measurable RPC, never coordination-by-side-effect · Tradeoff: more explicit RPCs than an implicit design, but every one is traceable · Operational: every coordination point carries a trace span named after its RPC method · Violated: a race reproducible only under specific network timing, undiagnosable from logs alone.
  • P9 — Ownership Clarity. Rule: exactly one authoritative lease owner exists per partition per epoch · Tradeoff: writes block during lease transfer instead of being served by whichever replica is closest · Operational: metadata-service exposes leaseholder-per-partition as a queryable, alertable fact · Violated: two nodes both believe they own a partition and accept conflicting writes (I2 violation).
  • P10 — Fail Closed. Rule: any state transition whose safety is uncertain rejects the write rather than guesses · Tradeoff: availability drops during ambiguous network conditions in exchange for never silently corrupting data · Operational: fencing tokens (§8) reject stale-leader writes at the storage-engine boundary · Violated: a demoted leader's in-flight write lands after a newer leader already committed a conflicting one.
  • P11 — Explicit Time Semantics. Rule: every timestamp's ownership, source, and skew tolerance is documented and visible in telemetry · Tradeoff: hybrid-logical-clock bookkeeping costs bytes per record versus trusting wall-clock alone · Operational: clock-skew metric (§24) alerts before it can violate the 250 ms tolerance in §4 · Violated: cross-region transaction ordering silently reorders under skew nobody was watching.
  • P12 — Isolation Of Failure Domains. Rule: a single region's failure must not corrupt or block progress in healthy regions · Tradeoff: some cross-region operations degrade to region-local semantics during a partition rather than block globally · Operational: gateway sheds cross-region routes independently per target region (§19) · Violated: one region's disk-full condition cascades into cluster-wide write stalls.

8. Domain Model — Partitioning, Replication & Transaction Protocol

Partition key (routes every request; owned by metadata-service, immutable once assigned):

PartitionKey:
  tenant_id: u64
  geographic_region: RegionId
  logical_shard: u32
  hash_suffix: u32

Replication message (Raft AppendEntries family; owned by raft-engine, wire-serialized via protocol):

AppendEntries:
  term: u64
  leader_id: NodeId
  prev_log_index: u64
  prev_log_term: u64
  entries: Vec<WalEntry>
  leader_commit: u64

MVCC tuple (owned by storage-engine; one physical row per (key, version)):

VersionedRow:
  key: Bytes
  version_ts: HybridLogicalTimestamp
  txn_id: TxnId
  tombstone: bool
  payload: Bytes

Transaction states (owned by txn-coordinator, persisted in TxnRecord, §11):

State Meaning
Pending active transaction, intents not yet replicated
Prepared write intents replicated to all owning Raft groups
Committed durable, visible to subsequent reads at commit_ts
Aborted rollback completed, intents released

Canonical commit sequence:

Client -> gateway -> txn-coordinator
txn-coordinator -> raft-engine (leader, per owning partition)
leader -> followers (AppendEntries)
followers -> leader (Ack, quorum)
leader -> storage-engine (apply at commit index)
txn-coordinator -> Client (commit_ts)

Malformed input classes (must be rejected, never silently coerced): duplicate transaction IDs, stale term appends, invalid snapshot checksums, non-monotonic timestamps, partition-key hash-suffix mismatch with declared range.

Canonical failure path — leader crash during prepare:

leader crash mid-prepare
  -> election timeout fires on followers
  -> new leader elected (higher term)
  -> new leader replays WAL from last snapshot
  -> commit index recovery (I3)
  -> txn-coordinator resolves in-flight TxnRecord (Prepared -> Committed or Aborted)

11. Core Schema & Types

All types below are declarations only (no method bodies); annotations record ownership, mutation policy, concurrency discipline, persistence, wire serialization, and compatibility policy.

NodeDescriptor:
  node_id: NodeId
  region: RegionId
  az: AvailabilityZone
  address: SocketAddr
  capacity_weight: f32
  state: NodeState

Ownership: metadata-service. Mutation: replace-on-write, versioned by topology epoch (I2, I7). Concurrency: immutable snapshot reads via Arc<NodeDescriptor>; topology updates serialized through topology-controller. Persistence: metadata store (Raft-replicated within control-plane group). Serialization: Protobuf, partition.proto. Compatibility: additive fields only (ADR-06, P7).

PartitionDescriptor:
  partition_id: PartitionId
  key_range: KeyRange
  replicas: Vec<NodeId>
  leaseholder: NodeId
  epoch: u64

Ownership: metadata-service, cached read-only in gateway. Mutation: epoch-fenced compare-and-swap only (I2, I7). Concurrency: gateway cache refreshed via subscription stream, never mutated in place. Persistence: metadata store. Serialization: Protobuf, partition.proto. Compatibility: epoch field is never reused across schema versions (I7).

TxnRecord:
  txn_id: TxnId
  begin_ts: HybridLogicalTimestamp
  commit_ts: Option<HybridLogicalTimestamp>
  state: TxnState
  write_set: Vec<PartitionKey>
  coordinator_id: NodeId

Ownership: txn-coordinator, durable. Mutation: single-writer per txn_id, monotonic state transitions (Pending→Prepared→{Committed,Aborted}). Concurrency: guarded by lock_table entries keyed on write_set (P9). Persistence: replicated via owning raft-engine groups (2PC intents). Serialization: Protobuf, transaction.proto. Compatibility: state enum is append-only (P7).

WalEntry:
  lsn: LogSequenceNumber
  term: u64
  checksum: Crc32c
  payload: Bytes

Ownership: replication-log. Mutation: append-only, never edited in place (I1, P5). Concurrency: single-writer per partition (one leader per epoch, I2). Persistence: fsync before ack (P2, I1). Serialization: custom binary framing, append-only, chosen over a JSON WAL for encode/decode cost on the fsync hot path. Compatibility: payload schema versioned inside protocol; lsn/term/checksum framing is stable across all versions.

SnapshotManifest:
  snapshot_id: SnapshotId
  applied_index: u64
  sstable_refs: Vec<SstableRef>
  checksum: Crc32c

Ownership: storage-engine, referenced by replication-log for catch-up streaming. Mutation: immutable once written (I4). Concurrency: readable concurrently by any number of catch-up streams. Persistence: immutable SST bundle (I4). Serialization: Protobuf. Compatibility: sstable_refs format versioned; readers must support the two most recent manifest versions (§25).

PartitionKey:
  tenant_id: u64
  geographic_region: RegionId
  logical_shard: u32
  hash_suffix: u32

Ownership: metadata-service assigns ranges; gateway and storage-engine consume, never reassign. Mutation: immutable once assigned. Concurrency: read-only after creation, safe to share across threads. Persistence: embedded in every VersionedRow key. Serialization: Protobuf, partition.proto. Compatibility: field order fixed; new locality dimensions append new fields, never repurpose existing ones.

VersionedRow:
  key: Bytes
  version_ts: HybridLogicalTimestamp
  txn_id: TxnId
  tombstone: bool
  payload: Bytes

Ownership: storage-engine. Mutation: immutable once flushed to an SSTable; only the memtable copy is mutable pre-flush. Concurrency: MVCC — multiple versions coexist, readers select by version_ts (I13). Persistence: WAL then SSTable. Serialization: internal binary row format, not wire-exposed directly. Compatibility: tombstone retention governed by compaction policy (§16).

trait StorageEngine:
  fn put(key: Bytes, value: Bytes, ts: HybridLogicalTimestamp) -> Result<(), StorageError>
  fn get(key: Bytes, ts: HybridLogicalTimestamp) -> Result<Option<Bytes>, StorageError>
  fn delete(key: Bytes, ts: HybridLogicalTimestamp) -> Result<(), StorageError>
  fn flush_memtable() -> Result<SnapshotManifest, StorageError>
  fn create_snapshot() -> Result<SnapshotManifest, StorageError>

Ownership: implemented by storage-engine, consumed by raft-engine's apply loop. Mutation: put/ delete append new MVCC versions, never mutate existing ones. Concurrency: get is lock-free against concurrent put via MVCC snapshot isolation (I13). Persistence: guarantees atomic WAL-before-visibility (I1), snapshot isolation, deterministic compaction ordering (I11). Serialization: n/a (in-process trait). Compatibility: trait signature is a Phase-4 (§16) contract; additive methods only across minor versions.

LeaseRecord:
  partition_id: PartitionId
  holder: NodeId
  epoch: u64
  fencing_token: u64
  expires_at: HybridLogicalTimestamp

Ownership: metadata-service. Mutation: renewed via epoch-fenced heartbeat, never extended past expires_at without a new epoch (I2, I7). Concurrency: single authoritative writer per partition_id. Persistence: metadata store. Serialization: Protobuf. Compatibility: fencing_token is a hard invariant field, never removable (P7 exception requires an RFC-style deprecation, §25).

12. Phase 0 — Foundation & Toolchain

12.1 Objectives

  • Establish deterministic builds, repository governance, CI pipelines, dependency policy, and reproducible development environments.
  • Stand up the correctness kernel: the protocol crate skeleton, workspace-wide lint policy, and an unsafe-code review gate.
  • Scope: no networking, no storage, no consensus yet — this phase is pure toolchain plus skeleton.
  • Constraint introduced: every crate added after this phase must compile under the same clippy::all deny list and pass cargo vet (ADR-04).

12.2 Detailed Implementation Steps

  • Initialize the Cargo workspace (Cargo.toml, Cargo.lock) with 13 member crates per §10; pin the toolchain via rust-toolchain.toml (Rust 1.82, ADR-01).
  • Define lint policy: #![deny(unsafe_op_in_unsafe_fn)] workspace-wide; unsafe blocks require a // SAFETY: comment reviewed under a dedicated CODEOWNERS rule — P2's crash-only discipline extends to the review process itself.
  • Configure clippy deny lists in the Makefile lint target; wire into .github/workflows/ci.yml.
  • Author crates/protocol/proto/{replication,partition,transaction}.proto skeletons with reserved field numbers — the first concrete artifact of P7 (stable wire compatibility), applied from day one.
  • Implement tracing bootstrap in crates/observability/src/tracing.rs: OTLP exporter init, environment-driven sampling ratio (P4).
  • Configure structured JSON logging (ADR-10) with mandatory fields trace_id, span_id, node_id.
  • Establish the Prometheus metrics registry in crates/observability/src/metrics.rs as a process-wide singleton that is injected, never global-mutable (P8).
  • Implement the conformance-harness runner skeleton discovering fixtures under conformance/fixtures/ by directory convention.
  • Define benchmark-runner contracts: a WorkloadSpec trait declaration (no bodies) consumed by Criterion benches (ADR-15).
  • Reference-implementation lesson applied: etcd's minimal raft package boundary (§5) motivates keeping protocol free of dependencies on every other crate.

12.3 Deliverable

A reproducible Cargo workspace that compiles in CI with a deterministic lockfile, emits structured logs and OTLP traces from a no-op bootstrap binary, and executes an empty benchmark-runner and conformance-harness pass.

12.4 Acceptance Criteria

  • CI green on Linux x86_64 for 3 consecutive runs with an identical Cargo.lock hash.
  • cargo clippy --workspace -- -D warnings exits 0.
  • A structured log line containing trace_id is emitted within 500 ms of process start.
  • conformance-harness discovers and executes fixtures/config/minimal.toml and fixtures/logs/bootstrap.json (§12.5) with exit code 0.
  • benchmark-runner --list enumerates ≥ 1 registered WorkloadSpec with zero panics.

12.5 Conformance Fixtures

  • fixtures/config/minimal.toml — smallest valid node config; expected: process starts, exposes a metrics endpoint on the configured port within 2 s.
  • fixtures/logs/bootstrap.json — expected structured-log schema for the first 10 startup log lines; expected output: schema validates against protocol's log-field contract.
  • fixtures/config/malformed_env.toml — invalid environment-override syntax; expected: startup aborts with a structured error, not a panic (P10).

12.6 Pitfalls

  • Nondeterministic build environments — manifestation: CI passes locally, fails in a clean container; root cause: an unpinned transitive dependency or system OpenSSL version; debug via cargo tree --duplicates; signal: Cargo.lock diff between runs; recovery: pin via [patch], add to the ADR-04 vetted list.
  • Tracing cardinality explosion — manifestation: the OTLP collector OOMs within hours; root cause: a per-request unique value used as a metric label instead of a trace attribute; debug via a Prometheus cardinality query; signal: unbounded scrape_samples_scraped growth; recovery: move high-cardinality fields to trace attributes only (P4).
  • Dependency drift — manifestation: a transitive dependency silently upgrades between releases; root cause: missing cargo vet enforcement in CI; debug via cargo vet diff; signal: CI vet-audit step fails; recovery: pin the exact version, re-run vet.

12.7 Performance Concerns

  • Startup allocation spikes from eagerly initializing all 13 crates' metrics registries — batch registration behind a single injected registry.
  • Excessive logging overhead if every call formats strings eagerly — use tracing's lazy field evaluation gated by the configured sampling ratio.
  • Workspace compile-time growth — mitigated via sccache in CI; not correctness-relevant, but blocks every downstream phase if unaddressed.

12.8 Edge Cases

  • Missing config file — startup fails closed with a specific exit code, not a silent default (P10).
  • Invalid environment-variable overrides — rejected with a structured validation error naming the offending key.
  • Toolchain version mismatch between CI and rust-toolchain.toml — CI fails the job rather than using whatever rustc happens to be on $PATH.

12.9 Failure Analysis

Broken CI pipelines block all downstream phases (§13–§21) — this phase has no partial-failure containment because nothing downstream exists yet. Blast radius: the entire project timeline. Detection: CI status. Containment: the pipeline itself must be idempotent and re-runnable without manual state cleanup. Postmortem guidance: any CI flakiness found here must be root-caused before Phase 1 starts — flaky CI compounds silently across the remaining nine phases.

12.10 Operational Notes

Metrics: process_start_total, config_validation_failures_total. Tracing: root span node.bootstrap. Structured-log fields: trace_id, span_id, node_id, config_hash. Deployment: none yet — no runtime service exists. Rollback: revert the workspace commit; no data-plane state exists. Migration: n/a. Compatibility: this phase fixes the log-field and metric-naming conventions every later phase must follow without deviation.

13. Phase 1 — Wire Protocol & Networking

13.1 Objectives

  • Implement secure, multiplexed node-to-node and client-to-gateway networking over QUIC.
  • Scope: transport and framing only — application-level routing logic is Phase 7 (gateway, §19).
  • Constraint introduced: every RPC carries a correlation ID and completes within a timeout budget derived from §4's RTT assumptions.

13.2 Detailed Implementation Steps

  • Implement QUIC transport in crates/protocol/src/wire.rs via the quinn crate (ADR-07); TLS 1.3 via rustls (ADR-18, RFC 8446).
  • TLS bootstrap: mutual TLS for node-to-node, single-sided TLS for client-to-gateway.
  • Protocol framing in crates/protocol/src/codec.rs: length-prefixed Protobuf frames (ADR-06); frame header carries correlation_id and protocol_version.
  • Bounded ingress queues per connection (P3, I8), sized from §4's max-connections budget.
  • Timeout propagation: every RPC carries a deadline; downstream calls inherit the remaining budget, never re-issue a fresh timeout (P8).
  • Retry metadata: attempt count and idempotency_key carried in the frame header (supports I10).
  • Compression negotiation: optional zstd per stream, negotiated at handshake.
  • Protocol compatibility negotiation: protocol_version checked against a supported range; RFC 9000 §17 framing pins down the transport-level frame types this layer builds on.
  • Applied theory anchor: RFC 9000 (QUIC) for stream multiplexing; ADR-07 for the transport choice; P3 for the ingress-queue bound.

13.3 Deliverable

Secure, multiplexed node-to-node RPC over QUIC/TLS 1.3, exercised by a loopback echo service, with frame-level fuzzing passing in CI.

13.4 Acceptance Criteria

  • Sustains 10,000 concurrent streams on a single connection without frame-reordering errors.
  • fuzz/fuzz_targets/frame_fuzz.rs runs 1,000,000 iterations with zero panics.
  • p50 loopback RTT < 1 ms, p99 < 5 ms on localhost (sanity bound below the §4 intra-region 5 ms budget).
  • fixtures/protocol/malformed_frame.bin and fixtures/protocol/stale_protocol_version.bin (§13.5) both rejected with a structured error, zero panics.

13.5 Conformance Fixtures

  • fixtures/protocol/malformed_frame.bin — truncated frame header; expected: connection-level error and reset, no partial state left in the ingress queue.
  • fixtures/protocol/stale_protocol_version.bin — frame declaring an unsupported protocol_version; expected: rejected before handshake completion with a version-mismatch error.
  • fixtures/protocol/replay_frame.bin — a previously-accepted frame replayed verbatim; expected: rejected via idempotency_key dedup (I10), never double-applied.

13.6 Pitfalls

  • Head-of-line blocking — manifestation: one slow stream stalls unrelated streams; root cause: framing layered incorrectly on top of QUIC's own multiplexing; debug via tokio-console's per-stream latency view; signal: correlated latency spikes across unrelated streams; recovery: verify each logical request maps to its own QUIC stream.
  • Unbounded buffers — manifestation: memory grows under a slow-consumer client; root cause: a missing per-connection queue bound (violates P3/I8); debug via heap profiling under sustained load; signal: queue_depth{stage="ingress"} climbing without bound; recovery: enforce the bound, shed the connection.
  • TLS session-resumption cache growth — manifestation: gradual node memory creep; root cause: no eviction policy; recovery: bound the cache, evict LRU.

13.7 Performance Concerns

  • Serialization overhead — mitigate via zero-copy Bytes slicing where the schema allows.
  • TLS handshake amplification — mitigate via connection pooling and 0-RTT resumption for idempotent reads only, never for mutating RPCs.
  • Syscall overhead per frame — batch small frames where request semantics allow, never across distinct idempotency_keys.

13.8 Edge Cases

  • Partial frame writes under backpressure — must not corrupt subsequent frames; the framing layer resynchronizes on the next valid length prefix or resets the connection.
  • Retransmission storms under lossy inter-region links (§4: 60–180 ms RTT) — QUIC's own loss recovery must not be duplicated by an application-level retry storm; retry budgets are capped.
  • Clock skew affecting deadline propagation — deadlines are relative durations, never absolute wall-clock (P11).

13.9 Failure Analysis

Network instability causes retry cascades if retry budgets are not capped per P3 — detection via a gateway_retries spike; blast radius contained to the affected connection pool, not the whole node, because ingress queues are bounded per connection (I8); recovery: circuit-break the unhealthy peer, resume via exponential backoff with jitter; operator visibility via per-peer connection health in admin-cli.

13.10 Operational Notes

Metrics: rpc_latency_seconds{method}, frame_decode_errors_total, queue_depth{stage="ingress"}. Tracing: every RPC traced with span rpc.<method>, correlation_id as an attribute. Structured-log fields: correlation_id, peer_node_id, protocol_version. Deployment: linked into every service binary, no independent rollout. Rollback: protocol_version negotiation keeps N and N-1 binaries interoperable during a rolling restart (P7).

14. Phase 2 — WAL & Replication Log

14.1 Objectives

  • Implement durable, append-only, replayable WAL storage feeding raft-engine.
  • Scope: log persistence, segment lifecycle, replay — not consensus ordering itself (Phase 3, §15).
  • Constraint introduced: every committed entry must be fsync'd before any ack crosses the process boundary (I1).

14.2 Detailed Implementation Steps

  • Segment rotation in crates/replication-log/src/segment.rs: fixed-size segments rotated at a configurable byte threshold, each header carrying a monotonic segment ID.
  • Checksums: CRC32c per WalEntry (§11), verified on every read, not only at write time (I1).
  • fsync policy in crates/replication-log/src/wal.rs: 5–20 ms batching window (§4 WAL fsync interval); group-commit multiple pending entries per fsync to amortize syscall cost.
  • Replay scanner in crates/replication-log/src/replay.rs: sequential forward scan from the last snapshot's applied_index, verifying checksum and LSN monotonicity (I1, I3).
  • Torn-write detection: a trailing entry with a valid length prefix but invalid checksum is treated as the crash boundary (P2), distinct from true interior corruption.
  • Corruption quarantine: any interior checksum failure quarantines the segment and pages an operator.
  • Snapshot markers: SnapshotManifest (§11) references embedded in the log stream bound replay scan length.
  • Retention manager: truncates segments strictly older than the oldest referenced snapshot, never ahead of the slowest-catching-up follower (interacts with raft-engine membership, Phase 3).
  • Applied theory anchor: Verbitski et al. 2017 (Aurora, §5) "log-is-the-database" informs keeping replication-log authoritative over storage-engine's on-disk state; P5 and I1 anchor the fsync-before-ack ordering.

14.3 Deliverable

A durable, crash-recoverable WAL crate — append, fsync-batched commit, checksum-verified replay, and segment retention — exercised standalone via conformance-harness without raft-engine attached.

14.4 Acceptance Criteria

  • Crash-replay succeeds against fixtures/wal/torn_write.wal and fixtures/wal/truncated_segment.wal (§14.5) with correct recovery point in both cases.
  • Checksum corruption injected mid-segment is detected within one scan pass across 10,000 randomized corruption trials, 100% detection rate.
  • Group-commit batches ≥ 8 entries per fsync under a 20 ms window at 5,000 writes/s synthetic load.
  • WAL amplification measured ≤ 2.5x payload bytes (§4 ceiling) across the write-throughput benchmark.

14.5 Conformance Fixtures

  • fixtures/wal/torn_write.wal — segment ending mid-entry; expected: replay stops cleanly at the last valid entry, no corruption alarm.
  • fixtures/wal/truncated_segment.wal — segment missing trailing bytes; expected: treated as a crash boundary, same as above.
  • fixtures/wal/interior_corruption.wal — a non-trailing entry with a bad checksum; expected: quarantine alarm, replay halts before the corrupted entry, operator paged.
  • fixtures/wal/duplicate_lsn.wal — two entries sharing an LSN; expected: rejected at replay as an I1/I3 violation, never silently accepted.

14.6 Pitfalls

  • Partial fsync assumptions — manifestation: data loss survives a power-failure test that should have been safe; root cause: assuming fsync() flushes the drive's volatile write cache without an explicit device flush; debug via power-fail injection in simulator (§20); signal: replay recovers fewer entries than were acked; recovery: verify device flush semantics against the §4 NVMe assumption.
  • WAL truncation races — manifestation: retention truncates a segment a slow follower still needs; root cause: retention computed against the fastest follower instead of the slowest; debug via replication-lag metrics correlated with truncation events; signal: follower catch-up fails with "segment not found"; recovery: gate truncation on the slowest known follower's acked index.
  • Checksum collision blind spot — manifestation: rare corruption undetected; root cause: CRC32c is not cryptographic and undetected under adversarial input (T8); mitigation scope is accidental corruption only, adversarial tampering is addressed via signed snapshots (§22).

14.7 Performance Concerns

  • fsync batching is the dominant lever on write throughput; too aggressive a window raises RPO risk (§4: RPO < 5 s) beyond the fsync interval ceiling.
  • Page-cache pressure — large segment sizes compete with storage-engine's page-cache-resident SSTable blocks; segment size is tuned independently of the 128 MB SSTable target.
  • Replay-scan cost on startup is bounded by the 90 s startup recovery target (§4); snapshot markers exist specifically to cap this scan length.

14.8 Edge Cases

  • Disk full mid-fsync — fails the write closed (P10), propagates as backpressure to the apply loop.
  • Checksum collision (rare) — the accepted false-negative rate is documented, never claimed as zero.
  • Segment rotation racing a concurrent flush — rotation is a single-writer operation per partition.
  • Clock skew affecting segment timestamps — LSN ordering, never wall-clock, drives any correctness decision (P11).

14.9 Failure Analysis

Corrupted WAL forces replica rebuild from a healthy peer's snapshot — detection via wal_gap_total (I1); blast radius contained to the single replica, since Raft quorum (Phase 3) tolerates a minority unavailable; containment: the quarantined replica stops serving immediately, does not participate in quorum until rebuilt; recovery: snapshot install from the current leaseholder; postmortem guidance: distinguish torn-write (expected, P2) from interior corruption (unexpected, files a defect) in every writeup.

14.10 Operational Notes

Metrics: wal_fsync_duration_seconds, wal_gap_total, wal_amplification_ratio, segment_retention_lag_bytes. Tracing: span wal.append, wal.replay. Structured-log fields: segment_id, lsn, partition_id. Deployment: co-located with raft-engine per partition. Rollback: WAL format is versioned; rollback requires WAL backward-readability (§25). Migration: segment-format changes require a documented path in docs/adr/.

15. Phase 3 — Consensus Engine (Raft)

15.1 Objectives

  • Implement Raft replicated-state-machine semantics: leader election, log replication, quorum commit, membership changes.
  • Scope: consensus ordering and safety only — applying committed entries to storage is Phase 4's boundary (§16).
  • Constraint introduced: no entry is visible to storage-engine before a quorum-certified commit index (I6).

15.2 Detailed Implementation Steps

  • Election timers and heartbeat scheduling in crates/raft-engine/src/election.rs: randomized election timeout per Ongaro's dissertation (§5) to avoid split-vote storms.
  • Commit advancement in crates/raft-engine/src/replica.rs: leader advances commit index only after matchIndex from a strict majority (I6); followers apply up to leader_commit (§8).
  • Membership transitions in crates/raft-engine/src/membership.rs: joint-consensus two-phase reconfiguration (Ongaro ch. 4) avoids a window where two disjoint majorities could both commit.
  • Snapshot install in crates/raft-engine/src/snapshot.rs: lagging followers receive a SnapshotManifest (§11) instead of full log replay when behind the retention window.
  • Log compaction coordinated with replication-log's retention manager (§14) — Raft log truncation never precedes the snapshot it would require for replay.
  • Quorum tracking in crates/raft-engine/src/log.rs: per-entry ack bitmap, majority computed against the current membership epoch, never a stale one (I2, I7).
  • Lease optimization: leader lease (LeaseRecord, §11/§8) allows local reads without a quorum round-trip within the lease's validity window, bounded by the §4 clock-skew tolerance (P11).
  • Applied theory anchor: Ongaro and Ousterhout 2014 (Raft paper, §5) for the core algorithm; I2, I3, I6, I7 for the safety properties; ADR-02 for the algorithm choice itself.

15.3 Deliverable

A fault-tolerant replicated log passing Jepsen-inspired linearizability checks under randomized network-partition injection from simulator (§20).

15.4 Acceptance Criteria

  • Jepsen-inspired consistency checks pass across 500 randomized partition scenarios, zero linearizability violations.
  • Quorum safety validated: no commit observed without majority ack in 100,000 simulated election events (I6).
  • Leader election converges within 5 s p99 under simulated single-node failure.
  • fixtures/raft/split_brain.json and fixtures/raft/stale_leader.json (§15.5) both resolve without a safety violation.

15.5 Conformance Fixtures

  • fixtures/raft/split_brain.json — two nodes each believing themselves leader post-partition-heal; expected: higher-term leader wins, the lower-term one steps down within one heartbeat interval, no dual commit observed.
  • fixtures/raft/stale_leader.json — a partitioned-away leader attempting to commit after quorum has moved on; expected: rejected via fencing token (I7, P10) at the storage boundary.
  • fixtures/raft/membership_change_race.json — a membership change overlapping a leader election; expected: the joint-consensus phase resolves deterministically, no majority-ambiguity window.

15.6 Pitfalls

  • Election storms — manifestation: repeated elections with no stable leader under moderate packet loss; root cause: election timeout too close to the heartbeat interval, or non-randomized timeout; debug via the leader-transition timeline in admin-cli; signal: raft_leader_transitions_total spike; recovery: widen the randomized timeout range.
  • Stale term acceptance — manifestation: a follower applies an AppendEntries from an old term; root cause: term comparison ordered incorrectly relative to log matching; debug via replaying fixtures/raft/stale_leader.json; signal: I2/I7 violation alarm; recovery: enforce the term check strictly before any log mutation.
  • Snapshot-install starvation — manifestation: a follower repeatedly falls behind the retention window before finishing install; root cause: retention window too tight relative to inter-region RTT (§4: 60–180 ms); recovery: widen retention or throttle snapshot transfer bandwidth adaptively.

15.7 Performance Concerns

  • Replication batching amortizes per-RPC overhead; batch size tuned against the §4 p99 cross-region write budget (< 250 ms).
  • Heartbeat fanout cost grows with Raft group size, bounded by the §4 max-group-size of 7.
  • Lease-read hot path avoids a quorum round-trip entirely — the single largest local-read latency lever, supporting the §4 p50 < 4 ms target.

15.8 Edge Cases

  • Asymmetric partitions (A reaches B, B cannot reach A) — must not produce a stable dual-leader state; term comparison resolves this even under one-directional connectivity.
  • Delayed followers beyond the snapshot retention window are forced to full snapshot install rather than incremental catch-up.
  • Simultaneous quorum loss (more than a minority down) — the system fails closed (P10): no new leader elected, writes reject rather than risk uncertain state.
  • Clock skew affecting lease-read validity — lease reads disabled beyond the §4 250 ms skew tolerance.

15.9 Failure Analysis

Consensus divergence (a simulator-detected safety violation) triggers immediate replica fencing and a page — the highest-severity failure class, since it can corrupt downstream storage-engine state; detection via replay_divergence_total (I12) and quorum-count assertions (I6); blast radius: bounded to the affected partition's Raft group, never cross-partition, because each group has an independent membership and term space (P12); recovery: quarantine, rebuild from a verified-good peer's snapshot, file a defect against the simulator for the missing assertion that should have caught it earlier (I12 methodology, §7).

15.10 Operational Notes

Metrics: raft_commit_latency_seconds, raft_leader_transitions_total, raft_quorum_short_commits_total, fencing_token_regressions_total. Tracing: span raft.append_entries, raft.election. Structured-log fields: term, partition_id, leader_id, commit_index. Deployment: one raft-engine instance per partition replica, co-located with replication-log. Rollback: membership-change format is versioned; rolling back mid-reconfiguration is disallowed by policy until the change completes or aborts.

16. Phase 4 — Storage Engine (MVCC LSM)

16.1 Objectives

  • Implement persistent MVCC storage over an LSM tree: memtable, immutable SSTable flush, background compaction, bloom filters.
  • Scope: local storage-engine correctness — cross-partition transaction semantics are Phase 5 (§17).
  • Constraint introduced: every read observes a consistent MVCC snapshot per I13, regardless of concurrent compaction.

16.2 Detailed Implementation Steps

  • Memtable in crates/storage-engine/src/memtable.rs: skip-list-backed sorted in-memory buffer, bounded size (P6), flush triggered at a configurable threshold.
  • Immutable flush pipeline in crates/storage-engine/src/sstable.rs: memtable → immutable SSTable at the §4 target size of 128 MB, block-based format with a sparse index.
  • Bloom filters in crates/storage-engine/src/bloom.rs: bound negative-lookup cost, sized against the expected key cardinality per partition.
  • Compaction scheduler in crates/storage-engine/src/compaction.rs: leveled compaction (per the RocksDB reference implementation, §5) selecting overlapping SSTable ranges to bound the §4 write-amplification ceiling (< 15x).
  • MVCC visibility checks in crates/storage-engine/src/mvcc.rs: a read at timestamp ts returns the highest version_ts <= ts that is not a tombstone (I13); anchored to the LSM-tree paper (O'Neil et al. 1996, §5) for the sorted-run merge structure underneath.
  • Tombstone retention: deletion markers retained until compacted past all open snapshot horizons, to prevent tombstone resurrection.
  • Compression: per-block, negotiated independently of the wire-level compression in §13.
  • Applied theory anchor: Bigtable (Chang et al. 2006, §5) for the SSTable/compaction lineage; I4, I11, I13 for the safety properties; P6 for bounded memtable growth.

16.3 Deliverable

A persistent, crash-recoverable MVCC storage engine implementing the StorageEngine trait (§11), exercised standalone against conformance/fixtures/storage/ without raft-engine attached.

16.4 Acceptance Criteria

  • Snapshot reads return correct results across 10,000 randomized concurrent-compaction interleavings (fixtures/storage/mvcc_visibility.json, §16.5).
  • Compaction regression suite passes on fixtures/storage/compaction_overlap.json with zero visibility mismatches (I11).
  • Write amplification measured < 15x (§4 ceiling) at steady state under the write-throughput benchmark.
  • Bloom-filter false-positive rate ≤ 1% at the configured bits-per-key setting, measured against a 10M-key synthetic dataset.

16.5 Conformance Fixtures

  • fixtures/storage/mvcc_visibility.json — writes and reads interleaved across a compaction boundary; expected: reads return the version visible at their timestamp, unaffected by concurrent compaction.
  • fixtures/storage/compaction_overlap.json — overlapping key ranges across multiple SSTable levels; expected: compacted output preserves identical live-key visibility to the pre-compaction inputs (I11).
  • fixtures/storage/tombstone_resurrection.json — a delete, then compaction, then a read at a timestamp before the delete; expected: the old value never resurfaces.
  • fixtures/storage/partial_flush.json — a crash mid-memtable-flush; expected: recovery replays the WAL to reconstruct the unflushed portion, no data loss beyond the §4 RPO bound (< 5 s).

16.6 Pitfalls

  • Compaction stalls — manifestation: write throughput collapses under sustained load; root cause: compaction falling behind flush rate, memtable count growing unbounded; debug via the compaction_backlog trend; signal: backlog growth rate exceeds compaction throughput; recovery: throttle writes (I8) until the backlog drains, never let memory grow unbounded (P6).
  • Tombstone resurrection — manifestation: a deleted key reappears after compaction; root cause: a tombstone compacted away before all snapshots that could observe its absence have closed; debug via replaying fixtures/storage/tombstone_resurrection.json; signal: I11/I13 conformance failure; recovery: track the oldest open snapshot horizon, never compact a tombstone past it.
  • Bloom-filter false-positive cascades — manifestation: read latency degrades under high fan-out; root cause: bits-per-key too low for actual key cardinality; recovery: retune per the RocksDB tuning guide's guidance (§5) against measured cardinality, not defaults.

16.7 Performance Concerns

  • Write amplification is the central LSM tradeoff; leveled compaction bounds it below 15x (§4) at the cost of more compaction IO than size-tiered compaction would use.
  • Cache misses — bloom filters and block indexes are sized to stay page-cache resident; NUMA awareness (§4) matters because cross-socket access to a hot block index measurably regresses p95.
  • Compaction IO competing with WAL fsync IO on the same NVMe device is scheduled to avoid starving the fsync path, which is on the critical path for I1/P2.

16.8 Edge Cases

  • Overlapping snapshots held open across a compaction cycle must not block compaction indefinitely; bounded snapshot lifetime is enforced (interacts with P6).
  • Partial flush failures (crash mid-flush) — the WAL remains authoritative until the flush's SnapshotManifest is durably committed (I4).
  • Schema drift in the payload format is versioned independently inside protocol; storage-engine treats payload bytes as opaque.
  • Disk full during compaction must abort cleanly and retry, never leaving a half-written SSTable visible to readers.

16.9 Failure Analysis

SSTable corruption (checksum failure) requires manifest rebuild — detection via compaction_visibility_mismatches_total and per-block checksum verification on read; blast radius contained to the affected partition's storage state, replayable from replication-log's WAL (P5, I1) since storage is a derived view of the log, per the Aurora "log-is-the-database" lesson (§5); containment: the affected SSTable is quarantined, reads served from other levels/replicas during rebuild; recovery: replay WAL from the last good snapshot; operator visibility via admin-cli storage inspect.

16.10 Operational Notes

Metrics: compaction_backlog, write_amplification_ratio, bloom_false_positive_rate, sstable_flush_duration_seconds. Tracing: span storage.flush, storage.compact. Structured-log fields: partition_id, sstable_id, level. Deployment: co-located with raft-engine per partition replica. Rollback: SSTable block format is versioned (§25); a rollback binary must read the two most recent format versions. Migration: format changes ship behind a feature flag gated by cluster epoch.

17. Phase 5 — Transaction Coordinator

17.1 Objectives

  • Implement distributed transaction orchestration: timestamp assignment, write intents, two-phase commit over Raft-replicated partitions, deadlock detection.
  • Scope: serializable isolation for transactions bounded to a declared partition set (§1 non-goal: unbounded distributed joins).
  • Constraint introduced: no transaction commits without every partition's intent reaching quorum first.

17.2 Detailed Implementation Steps

  • Timestamp oracle in crates/txn-coordinator/src/timestamp_oracle.rs: hybrid-logical clock issuing monotonically increasing begin_ts/commit_ts (P11), adapted from Spanner's TrueTime lesson (§5) without dedicated clock hardware.
  • Intent records: TxnRecord.write_set (§11) populated at Pending, replicated to each owning partition's raft-engine as a provisional write before Prepared.
  • Lock table in crates/txn-coordinator/src/lock_table.rs: per-key intent locks released on Committed/Aborted, never leaked across a coordinator restart (recoverable from durable TxnRecord, P2).
  • Deadlock detector in crates/txn-coordinator/src/deadlock.rs: wait-for-graph cycle detection, periodic sweep on a configurable interval, victim selection by youngest-transaction rule.
  • Prepare/commit flow in crates/txn-coordinator/src/intent.rs: 2PC where "prepare" is itself a Raft-replicated write, anchored to Calvin's (§5) determinism lesson — the commit decision is a deterministic function of all partitions' prepare acks, exactly replayable.
  • Rollback replay: an aborted transaction's intent removal is itself WAL-logged (P5), so a crashed coordinator recovers the correct rollback state from replay, not in-memory bookkeeping.
  • Conflict detection: write-write conflicts detected at prepare time via intent-lock contention; write-skew anomalies checked against fixtures/txn/write_skew.json (§17.5).
  • Applied theory anchor: Gray and Reuter's recovery/concurrency-control chapters (§5) for 2PC recovery semantics; I9, I10, I13 for the safety properties; P9 for lock-ownership clarity.

17.3 Deliverable

Serializable distributed transactions across a bounded partition set, with coordinator-crash recovery verified via simulator-injected mid-commit kills.

17.4 Acceptance Criteria

  • Transaction isolation verified as serializable across 50,000 randomized concurrent-transaction trials with zero anomalies detected.
  • Rollback recovery passes 1,000 coordinator-crash-mid-commit trials with 100% correct resolution (Prepared → deterministically Committed or Aborted, never left Pending).
  • fixtures/txn/deadlock_cycle.json resolves within 3 detection-sweep intervals with the correct victim aborted.
  • p99 commit latency for a single-partition transaction < 12 ms local, < 250 ms cross-region (§4).

17.5 Conformance Fixtures

  • fixtures/txn/deadlock_cycle.json — three transactions holding a circular wait-for dependency; expected: the detector breaks the cycle by aborting the youngest transaction, the other two proceed.
  • fixtures/txn/write_skew.json — two transactions each reading a value the other will modify without direct key overlap; expected: serializable isolation rejects the anomaly, unlike plain snapshot isolation.
  • fixtures/txn/coordinator_crash_prepared.json — coordinator killed after all partitions ack prepare but before commit is recorded; expected: recovery deterministically resolves to Committed.
  • fixtures/txn/partial_visibility.json — a crash between partition A's commit apply and partition B's; expected: no reader ever observes A's write without B's (I13).

17.6 Pitfalls

  • Lock leaks — manifestation: a key remains locked indefinitely after its owning coordinator crashes; root cause: lock release tied to in-memory coordinator state instead of durable TxnRecord state; debug via lock_wait histogram tail growth; signal: a lock held longer than the longest legitimate transaction duration; recovery: recover lock state from durable TxnRecord on restart, never from memory alone (P2).
  • Orphan intents — manifestation: a partition's storage-engine holds an intent no coordinator will ever resolve; root cause: the coordinator crashed before writing any durable TxnRecord at all; debug via a periodic intent sweep against active TxnRecords; signal: intent age exceeds a sweep threshold with no matching record; recovery: sweep and abort orphaned intents past a timeout.
  • Timestamp skew across regions — manifestation: two coordinators observe inconsistent commit ordering; root cause: hybrid-logical clock drift exceeding the §4 250 ms tolerance; recovery: reject commits when local clock-skew telemetry exceeds tolerance (P11, P10).

17.7 Performance Concerns

  • Contention hotspots — a small set of frequently written keys serializes through the lock table; mitigated by shorter transaction spans and earlier conflict detection, not by weakening isolation.
  • Coordinator bottlenecks — coordinators are intentionally stateless (§3) so horizontal scale-out is a deployment decision, not a code change.
  • 2PC round-trip cost dominates cross-region commit latency (§4: p99 < 250 ms); batching independent transactions' prepare RPCs to the same partition amortizes network overhead.

17.8 Edge Cases

  • Coordinator crash during commit (after prepare, before commit record) — must resolve deterministically on recovery (fixtures/txn/coordinator_crash_prepared.json).
  • Timestamp skew beyond tolerance — commits reject rather than risk non-serializable ordering (P10).
  • Read-only transactions racing a concurrent commit must observe a consistent snapshot (I13), never a partial commit.
  • Deadlock cycles spanning more than two transactions — the detector must handle arbitrary cycle length, not just pairwise deadlock.

17.9 Failure Analysis

Prepared-but-unresolved transactions after a coordinator crash require recovery from durable TxnRecord state before any new transaction touching the same keys can proceed — detection via lock-table entries with no live coordinator heartbeat; blast radius: bounded to the specific keys in the crashed transaction's write set, not the whole partition, because locks are per-key (P9); recovery: a recovery coordinator (any live txn-coordinator instance) resumes resolution from the durable record; operator visibility via lock_wait histograms and admin-cli txn inspect.

17.10 Operational Notes

Metrics: txn_conflict_rate, lock_wait_seconds (histogram), deadlocks_detected_total, txn_commit_latency_seconds. Tracing: span txn.prepare, txn.commit, with transaction lineage carried as a trace attribute across every partition touched. Structured-log fields: txn_id, coordinator_id, partition_ids. Deployment: stateless, horizontally scaled behind gateway. Rollback: TxnRecord schema is append-only (P7); rollback binaries must still parse newer optional fields as unknown-and-ignored.

18. Phase 6 — Metadata Service & Topology Control

18.1 Objectives

  • Implement the cluster metadata authority: partition ownership, lease distribution, topology versioning, placement rules, node draining.
  • Scope: metadata correctness and convergence — actual data migration is Phase 9 (§21).
  • Constraint introduced: every metadata read is epoch-fenced against the current topology version (I2, I7).

18.2 Detailed Implementation Steps

  • Region descriptors in crates/metadata-service/src/topology.rs: NodeDescriptor (§11) registry per region, updated via a serialized write path (no concurrent topology mutation, P8).
  • Partition ownership: PartitionDescriptor (§11) records keyed by partition_id, mutated only via epoch-fenced compare-and-swap.
  • Lease distribution in crates/metadata-service/src/lease.rs: issues LeaseRecord (§11) with a monotonic fencing_token per partition (I7); renewal is itself Raft-replicated within the control-plane's own small consensus group, distinct from data-plane groups.
  • Topology versioning: every mutation increments a global epoch; readers cache a (descriptor, epoch) pair, a lower epoch is always treated as stale, never silently accepted (I2).
  • Placement rules in crates/metadata-service/src/placement_rules.rs: declarative constraints (e.g. replicas must span ≥ 2 AZs) validated before any placement change is accepted — this phase validates rules, Phase 9 (§21) executes rebalancing under them.
  • Node draining: a draining node stops accepting new leaseholder assignments; existing leases transfer via the normal epoch-fenced path, never force-killed mid-lease.
  • Applied theory anchor: CockroachDB's pkg/kv range-descriptor design (§5) for the descriptor/epoch pattern; I2, I7, P9 for the safety properties; ADR-02's Raft choice reused for the control-plane's own consensus group.

18.3 Deliverable

A consistent cluster metadata authority — topology reads/writes with epoch-fenced safety, exercised against conformance/fixtures/metadata/ including simulated rapid topology churn.

18.4 Acceptance Criteria

  • Topology convergence verified: 1,000 randomized concurrent placement-change trials converge to a single consistent view across all metadata-service replicas within 2 s.
  • fixtures/metadata/stale_epoch.json and fixtures/metadata/overlapping_ranges.json (§18.5) both rejected, zero silent acceptance.
  • Lease-renewal p99 < 50 ms under nominal load.
  • Node draining completes within the §4 graceful-shutdown-drain budget of 30 s for a node holding ≤ 500 leases.

18.5 Conformance Fixtures

  • fixtures/metadata/stale_epoch.json — a placement change submitted against an epoch older than the current one; expected: rejected with a stale-epoch error, no partial application.
  • fixtures/metadata/overlapping_ranges.json — two PartitionDescriptors whose key ranges overlap; expected: rejected at validation time, never persisted.
  • fixtures/metadata/rapid_churn.json — 100 placement changes submitted within 1 s; expected: serialized correctly, final state matches the last-accepted change, no lost updates.
  • fixtures/metadata/lease_overlap.json — two lease grants for the same partition and epoch; expected: rejected, I2 violation alarm never silently swallowed.

18.6 Pitfalls

  • Stale caches — manifestation: gateway routes to a leaseholder that has already lost its lease; root cause: cache TTL longer than the lease-renewal interval; debug via correlating fixtures/gateway/stale_route.json-style failures with cache-refresh timing; signal: elevated NotLeaseholder error rate; recovery: subscribe to topology-change events instead of polling a fixed TTL.
  • Split ownership — manifestation: two nodes briefly both act as leaseholder; root cause: the epoch check performed before, not after, acquiring the local write lock; debug via lease-overlap alarm telemetry; signal: I2 violation; recovery: reorder the check-then-act sequence, add the missing simulator assertion (I12).
  • Metadata fanout amplification — manifestation: every gateway polling metadata-service directly overloads it; root cause: no caching/subscription layer; recovery: push-based topology-change streaming instead of pull-based polling.

18.7 Performance Concerns

  • Metadata fanout is bounded via subscription streaming rather than per-request lookups, sized against the §4 max-connections and max-partitions-per-node budgets.
  • Cache invalidation must be fast enough that stale-route errors stay rare without defeating the cache's purpose through over-invalidation.
  • The control-plane Raft group is kept small and separate from data-plane groups so control-plane latency does not compete with data-plane commit latency for CPU/IO.

18.8 Edge Cases

  • Rapid topology churn must serialize correctly without dropping intermediate states a concurrent reader might depend on.
  • Simultaneous node failures affecting multiple leaseholders at once — lease reassignment proceeds independently per partition, never blocking on a global lock (P12).
  • Clock skew affecting lease expiry — validity windows are padded against the §4 250 ms skew tolerance.
  • Schema drift in placement rules across a rolling upgrade — old and new rule schemas coexist during the upgrade window (P7).

18.9 Failure Analysis

Metadata corruption or unavailability blocks all routing cluster-wide — a severe blast-radius failure class; detection via epoch-mismatch telemetry and control-plane Raft health; containment: the control-plane's own small Raft group (odd replica count, same I2/I6 discipline as data-plane) tolerates a minority failure without full outage; recovery: control-plane leader re-election, cached topology at gateways provides a bounded grace window before hard-failing routing decisions; postmortem guidance: every topology change is fully audited (§18.10) specifically to support this class of incident review.

18.10 Operational Notes

Metrics: topology_epoch, lease_renewal_latency_seconds, placement_rule_violations_total, metadata_fanout_qps. Tracing: span metadata.lease_renew, metadata.placement_change. Structured-log fields: epoch, partition_id, node_id, change_type. Deployment: dedicated control-plane nodes, isolated from data-plane (§1). Rollback: topology schema is epoch-versioned; a rollback binary must still honor epochs issued by a newer binary during the rollback window.

19. Phase 7 — Routing Gateway

19.1 Objectives

  • Implement locality-aware, admission-controlled request routing as the externally reachable cluster endpoint.
  • Scope: routing, auth, admission — not transaction semantics (Phase 5) or storage (Phase 4).
  • Constraint introduced: every accepted request is shed or routed within the admission-control queue bound (I8) before its deadline expires.

19.2 Detailed Implementation Steps

  • Partition cache in crates/gateway/src/router.rs: subscribes to metadata-service topology-change events (§18) rather than polling; routes by PartitionKey.geographic_region (§8) to the nearest healthy leaseholder.
  • Retry semantics in crates/gateway/src/retry.rs: capped attempt count with exponential backoff and jitter, respecting the caller's remaining deadline budget (P8), reusing I10's idempotency_key.
  • Auth middleware in crates/gateway/src/auth.rs: RBAC check before admission, TLS client-cert or token-based identity (ADR-18).
  • Admission control in crates/gateway/src/admission.rs: bounded ingress queue (I8) with a load-shedding policy that rejects new requests before existing ones are starved.
  • Request prioritization: control-plane and health-check traffic prioritized over bulk client traffic within the admission queue.
  • Congestion handling: per-target-region circuit breaking (P12) — a struggling region's saturation does not degrade routing to healthy regions.
  • Applied theory anchor: Dynamo's (DeCandia et al. 2007, §5) locality/availability tradeoff reasoning informs the admission-vs-shed policy; P3, P12, I8 anchor the backpressure and isolation properties.

19.3 Deliverable

An externally reachable, authenticated cluster endpoint performing locality-validated routing, load-shedding under saturation, and per-region circuit breaking, exercised under synthetic partial-region outage in simulator.

19.4 Acceptance Criteria

  • Locality routing validated: 99% of requests route to a leaseholder in the client's declared region when one exists, across 100,000 synthetic requests.
  • fixtures/gateway/stale_route.json and fixtures/gateway/auth_failure.json (§19.5) both handled without a request hang — bounded resolution within the admission queue's configured timeout.
  • Load-shedding activates within 200 ms of the ingress queue reaching 90% of its I8 bound, verified under a 10x traffic-spike synthetic load.
  • Sustains the §4 max-connections/node budget (50,000) without ingress-queue overflow.

19.5 Conformance Fixtures

  • fixtures/gateway/stale_route.json — a cached partition map pointing at a former leaseholder; expected: NotLeaseholder triggers one cache-refresh-and-retry, not an unbounded retry loop.
  • fixtures/gateway/auth_failure.json — an invalid or expired credential; expected: rejected pre-admission with a structured error, never queued.
  • fixtures/gateway/region_outage.json — a target region unreachable; expected: circuit breaks for that region specifically, requests to other regions unaffected (P12).
  • fixtures/gateway/queue_saturation.json — ingress queue at capacity; expected: new requests shed with a structured retriable error, existing queued requests unaffected.

19.6 Pitfalls

  • Retry storms — manifestation: transient partition-map staleness triggers synchronized retries across many clients, overloading the correct leaseholder the instant it's found; root cause: no jitter on retry backoff; debug via correlated retry-timing histograms; signal: gateway_retries spikes in lockstep; recovery: add jitter, cap the total retry budget per request.
  • Cache poisoning — manifestation: a gateway instance's partition cache diverges from reality and stays wrong; root cause: a subscription stream silently dropped without reconnect-and-resync; debug via comparing gateway cache epoch against the current metadata-service epoch; signal: elevated stale-route errors from one specific instance; recovery: detect subscription gaps, force a full resync.
  • Connection churn under retry — manifestation: TLS handshake overhead dominates under high retry rates; recovery: reuse connections across retries to the same peer rather than reconnecting.

19.7 Performance Concerns

  • Connection churn is mitigated via connection pooling keyed by target node, not target request.
  • TLS overhead — 0-RTT resumption for idempotent reads only, never mutating requests (avoids replay risk, I10).
  • Admission-queue depth directly trades p99 latency for throughput, tuned against the §4 p95/p99 local-read budgets.

19.8 Edge Cases

  • Stale partition maps during a rapid topology-churn window (§18.8) are bounded by one refresh-and-retry cycle, never unbounded retries.
  • Simultaneous multi-region client traffic during a single region's outage — routing to healthy regions remains unaffected (P12).
  • Deadline exhaustion mid-retry — the gateway returns a deadline-exceeded error rather than retrying past the caller's budget.
  • Malformed auth tokens are rejected structurally before any RBAC lookup, avoiding wasted work.

19.9 Failure Analysis

Gateway overload propagates cluster-wide if admission control fails to shed load in time — detection via ingress-queue-depth telemetry (I8) crossing threshold; blast radius: without per-region circuit breaking this would be cluster-wide, but P12 bounds it to the affected region's traffic share; recovery: load-shedding activates automatically, operators can additionally force a manual circuit break via admin-cli; postmortem guidance: any incident where shedding activated too late is a bug in threshold tuning, not a capacity problem, until proven otherwise.

19.10 Operational Notes

Metrics: gateway_retries, queue_depth{stage="ingress"}, requests_shed_total, circuit_breaker_state{region}. Tracing: span gateway.route, gateway.admit. Structured-log fields: client_region, target_region, partition_id, auth_principal. Deployment: horizontally scaled, stateless except for the partition cache (rebuildable from a fresh subscription). Rollback: routing logic is version-gated behind a feature flag tied to cluster epoch (P7).

20. Phase 8 — Observability & Deterministic Simulation

20.1 Objectives

  • Implement metrics, distributed tracing, and the deterministic fault-injection simulator that validates every invariant in §7 under adversarial scheduling.
  • Scope: introspection and verification infrastructure — this phase proves already-built features are correct, it does not add data-plane features.
  • Constraint introduced: every invariant in §7 must have exactly one corresponding simulator assertion before this phase's deliverable is accepted.

20.2 Detailed Implementation Steps

  • Prometheus exporters in crates/observability/src/metrics.rs: the registry established in Phase 0 (§12) now populated by every crate's real metrics (ADR-12, Prometheus Exposition Format).
  • OpenTelemetry traces in crates/observability/src/tracing.rs: OTLP export wired to every span established across Phases 1–7 (ADR-11, OTLP spec).
  • Correlation IDs verified end-to-end from gateway ingress through txn-coordinator, raft-engine, storage-engine, closing the loop opened in Phase 1 (§13).
  • Replay capture in crates/observability/src/replay_capture.rs: persists every consensus mutation's input in a format simulator can consume deterministically (P5, I12).
  • Deterministic scheduler in crates/simulator/src/scheduler.rs: a logical-time event scheduler replacing wall-clock and OS thread scheduling for test runs, anchored to FoundationDB's simulation-first testing philosophy (§5).
  • Fault injection in crates/simulator/src/fault_injection.rs: network partitions, disk corruption, clock skew, node crash — each parameterized by a seed for reproducibility (I12).
  • Audit streams: every metadata and admin-cli action logged to an append-only audit stream, separate from operational logs, for the incident-forensics use case in §23.
  • Profiling hooks: perf/eBPF-compatible symbol tables preserved in release builds to support §28's flamegraph tooling.
  • Applied theory anchor: Zhou et al. 2021 (FoundationDB, §5) for the simulation-first philosophy; I12 for the deterministic-replay invariant this phase exists to enforce; P4, P5 for observability and replayability.

20.3 Deliverable

Full-stack distributed tracing stitched across every service, a deterministic simulator capable of reproducing any injected fault from a seed, and one simulator assertion mapped to each of the 13 invariants in §7.

20.4 Acceptance Criteria

  • Traces stitched across all 5 core services (gateway, txn-coordinator, raft-engine, replication-log, storage-engine) for 100% of a 10,000-request synthetic trace sample.
  • fixtures/observability/trace_replay.json and fixtures/simulation/partition_matrix.json (§20.5) both reproduce identical results across 100 repeated runs with the same seed (I12).
  • All 13 invariants from §7 have a passing, named simulator assertion; zero invariants without coverage.
  • Simulated fault injection (partition, disk corruption, clock skew, node crash) each independently reproducible from a logged seed within the same test run.

20.5 Conformance Fixtures

  • fixtures/observability/trace_replay.json — a captured trace of a cross-region transaction; expected: replaying the same input sequence reproduces an identical span tree.
  • fixtures/simulation/partition_matrix.json — a matrix of network-partition scenarios across 3 regions; expected: every scenario resolves without a safety-invariant violation, reproducible byte-for-byte from its seed.
  • fixtures/simulation/simultaneous_quorum_loss.json — more than a minority of replicas unreachable simultaneously; expected: the system fails closed (P10), no split-brain, fully reproducible.
  • fixtures/simulation/nondeterministic_timer_regression.json — a regression fixture for a previously-found hidden nondeterminism bug (a real timer source leaking into the deterministic scheduler); expected: the detector flags any non-seeded time source used inside the apply path.

20.6 Pitfalls

  • Cardinality explosion — manifestation: the metrics backend OOMs weeks after Phase 0's bootstrap looked fine; root cause: a label added later (e.g. per-txn_id) that Phase 0's review gate didn't anticipate; debug via a /metrics cardinality audit; signal: unbounded scrape_samples_scraped growth; recovery: move the offending label to trace attributes, add a lint rule against high-cardinality metric labels.
  • Trace sampling bias — manifestation: p99 latency looks better in traces than in raw metrics; root cause: head-based sampling disproportionately drops the slow, high-latency traces; recovery: tail-based sampling, or unconditional sampling of any span exceeding a latency threshold.
  • Nondeterministic timers — manifestation: simulator runs diverge between two runs with the same seed; root cause: a real wall-clock read leaked into replicated-state logic despite P1; debug via bisecting the divergent run against a clean one; signal: I12 replay_divergence_total; recovery: route every time read through the deterministic scheduler's logical clock, add a CI check forbidding SystemTime::now() outside the observability timestamp boundary.

20.7 Performance Concerns

  • Tracing overhead — sampling ratio tuned to keep steady-state overhead low while retaining 100% sampling of error and high-latency spans; overhead measured, not assumed.
  • Simulator scalability — logical-time simulation is CPU-bound, not wall-clock-bound; scaling the simulated cluster size is bounded by single-machine CPU, a scaling concern distinct from the data-plane concerns in §29.
  • Replay-capture storage growth is bounded by a retention window, oldest captures pruned first (P6-adjacent discipline applied to observability data itself).

20.8 Edge Cases

  • Missing correlation IDs (a caller bypassing the standard client library) must degrade to a best-effort trace root, never crash the receiving service.
  • Simulator seed collisions across parallel CI runs — seeds derive from a run-unique namespace, never from wall-clock alone.
  • Audit-stream write failures must not block the operation being audited (P3), but must alert loudly since a gap in the audit trail is itself a security-relevant event (T6, rogue operators, §22).

20.9 Failure Analysis

Poor observability blocks incident resolution — this phase's purpose is preventing that failure mode, so its own failure analysis is reflexive: detection is "an incident took longer than expected to diagnose because a span/metric was missing"; blast radius is time-to-resolution on every future incident, not a single outage; recovery: the missing telemetry is added and backfilled into simulator's assertion set (I12) so the gap cannot recur silently; postmortem guidance explicitly requires answering what telemetry would have made this instant to diagnose.

20.10 Operational Notes

Metrics: trace_sampling_ratio, replay_divergence_total, simulator_assertions_covered_total, audit_write_failures_total. Tracing: this phase is where tracing becomes end-to-end; span naming (<crate>.<operation>) is locked as a compatibility contract (§25). Structured-log fields: seed (simulator runs only), assertion_id. Deployment: simulator and benchmark-runner run in CI and pre-release gates, not in production. Rollback: n/a for simulator; OTLP/Prometheus wire formats are externally standardized, not versioned by this project.

21. Phase 9 — Adaptive Geo-Placement & Online Rebalancing

21.1 Objectives

  • Implement latency-aware, throttled partition placement optimization: access heatmaps, migration planning, safe execution validated by Phase 6's rules (§18).
  • Scope: the first data-plane feature explicitly deferred at Phase 0 (§1, §35) — online partition splitting and full CDC remain deferred beyond this phase.
  • Constraint introduced: no migration runs without the migration planner's throttle explicitly permitting it against current cluster load.

21.2 Detailed Implementation Steps

  • Access heatmaps in crates/topology-controller/src/heatmap.rs: per-partition read/write frequency and per-region latency-contribution tracking, sourced from observability metrics (§20) rather than a separate collection path (P4).
  • Migration planner in crates/topology-controller/src/placement.rs: proposes placement changes as epoch-fenced PartitionDescriptor updates (§11, §18) — the planner never mutates ownership directly, it submits candidates for metadata-service to validate and accept.
  • Rebalance throttling in crates/topology-controller/src/rebalance.rs: bounds concurrent in-flight migrations against the §4 compaction-write-amplification and network-RTT budgets, so rebalancing itself never becomes the availability incident it's meant to prevent.
  • Migration execution: a partition migration is a snapshot install (§14, §16 SnapshotManifest) to the new replica set followed by an epoch-fenced ownership cutover, never a live unreplicated copy.
  • Applied theory anchor: Spanner's (Corbett et al. 2012, §5) latency-aware placement motivation for why this matters; CockroachDB's pkg/kv range-splitting lesson (§5, explicit pitfall: do not copy full online-split scope yet — sibling deferral in §35) for how much to build now; I2, I7, P9 anchor the safety of the ownership cutover.

21.3 Deliverable

A working migration planner and throttled executor that relocates a hot partition to a lower-latency region without violating I2/I7, measured end-to-end via simulator-injected access-pattern shifts.

21.4 Acceptance Criteria

  • Migration correctness verified: 500 randomized hotspot-migration trials complete with zero I2/I7 violations and zero data loss (fixtures/placement/hotspot_migration.json, §21.5).
  • Rebalance throttle caps concurrent migrations such that compaction write-amplification stays under the §4 15x ceiling throughout every trial.
  • Migration completion time for a 128 MB partition (§4 SSTable target) under 90 s intra-region, under 5 min cross-region (matching the §4 RTO budget).
  • Zero client-visible write rejections during a migration's cutover window beyond one bounded NotLeaseholder retry (reusing the §19 gateway retry path).

21.5 Conformance Fixtures

  • fixtures/placement/hotspot_migration.json — a partition whose access heatmap shifts sharply toward a new region; expected: the planner proposes a migration, the throttle admits it, cutover completes with no I2/I7 violation.
  • fixtures/placement/simultaneous_region_outage.json — a migration target region becomes unreachable mid-migration; expected: the migration aborts cleanly, ownership remains with the original replica set (fail closed, P10), no partial cutover.
  • fixtures/placement/throttle_saturation.json — more migration candidates than the throttle admits; expected: excess candidates queue, none bypass the throttle, no availability regression.
  • fixtures/placement/migration_storm_regression.json — a regression fixture for a previously-found bug where heatmap noise triggered repeated back-and-forth migrations; expected: a cooldown window suppresses re-migration of a partition within a configured interval.

21.6 Pitfalls

  • Migration storms — manifestation: a partition migrates back and forth repeatedly with no net latency benefit; root cause: heatmap noise (short-lived access spikes) triggering the planner without a cooldown window; debug via replaying fixtures/placement/migration_storm_regression.json; signal: migration_events_total for the same partition_id exceeding a rate threshold; recovery: add a minimum cooldown interval per partition, require sustained heatmap signal rather than a single spike.
  • Rebalance IO pressure — manifestation: compaction backlog (§16) grows during a wave of migrations; root cause: the throttle bound set against migration count rather than actual IO/compaction budget consumed; recovery: throttle against the same write-amplification ceiling §4 already defines, not an independently invented limit.
  • Ownership-cutover race with a concurrent lease renewal — manifestation: a brief window where both old and new replica sets believe they might be authoritative; root cause: cutover epoch bump and lease renewal not sequenced through the same compare-and-swap path; recovery: route both through metadata-service's single epoch-fenced mutation path (P8).

21.7 Performance Concerns

  • Rebalance IO pressure directly competes with foreground compaction and WAL fsync IO on the same NVMe device (§4); the throttle bound is explicitly calibrated against the same write-amplification and RTT budgets used everywhere else, not a separately invented number.
  • Snapshot-transfer bandwidth for cross-region migrations is bounded by inter-region RTT/bandwidth assumptions (§4: 60–180 ms RTT); migration-time estimates must account for this, not assume intra-region bandwidth.
  • Heatmap computation must stay cheap relative to the request path it observes — sampled, not exhaustive, per-request accounting.

21.8 Edge Cases

  • Simultaneous region outages during an in-flight migration must abort cleanly, never leaving ownership ambiguous (fixtures/placement/simultaneous_region_outage.json).
  • A migration target region itself becoming overloaded mid-migration — the throttle must be able to abort and choose a different target, not force through a bad decision.
  • Clock skew affecting cooldown-window enforcement — cooldown timers use the same hybrid-logical clock discipline as everything else (P11), not wall-clock deltas across regions.
  • Schema drift in PartitionDescriptor during a rolling upgrade spanning a migration — migration logic tolerates both old and new descriptor shapes mid-upgrade (P7).

21.9 Failure Analysis

Incorrect placement destabilizes latency cluster-wide if left unchecked — detection via the same per-region latency telemetry the heatmap consumes, correlated against migration_events_total; blast radius: bounded to the specific partitions being migrated, because cutover is epoch-fenced per-partition (P9, P12), never a cluster-wide freeze; recovery: abort in-flight migrations, revert to metadata-service's last-known-good ownership record; postmortem guidance: every migration is fully audited (§21.10) specifically so a bad placement decision can be traced back to the heatmap signal that triggered it.

21.10 Operational Notes

Metrics: migration_events_total, migration_duration_seconds, rebalance_throttle_admitted_total, rebalance_throttle_queued_total. Tracing: span placement.plan, placement.migrate. Structured-log fields: partition_id, source_region, target_region, migration_id. Deployment: topology-controller runs on dedicated control-plane nodes alongside metadata-service (§18). Rollback: migration format reuses the versioned SnapshotManifest (§11); a rollback binary mid-migration must be able to complete or safely abort using only its own version's semantics.

25. Compatibility & Versioning

Wire compatibility: additive Protobuf evolution only (P7, ADR-06); no field removal or renumbering within a minor version; protocol schemas diffed against the previous release in CI.

Rolling upgrades: supported across exactly one minor version at a time (N and N+1 binaries interoperate; N and N+2 are not guaranteed to). protocol_version negotiation (§13) enforces this at the transport layer.

WAL backward readability: mandatory — a rollback binary must read WAL segments written by the newer binary within the same major version (§14.10).

Snapshot versioning: SnapshotManifest (§11) carries a format version; readers support the two most recent versions concurrently (§16.10).

Feature flags: gated by cluster topology epoch (§18), never by binary version alone, so a feature activates only once every node in the cluster has upgraded — closing the window where mixed-version behavior could diverge (P1).

Schema drift handling: every phase's Edge Cases subsection explicitly covers rolling-upgrade schema drift for that phase's owned types; there is no single central migration mechanism because each type (TxnRecord, PartitionDescriptor, WalEntry, …) owns its own additive-evolution discipline.

29. Scalability Analysis

Primary bottlenecks: consensus coordination (per-partition quorum RTT, §15, MM1 §30), metadata fanout (§18), compaction bandwidth (§16), gateway saturation (§19), transaction hotspotting on frequently-written keys (§17).

Scaling strategy: partition splitting (deferred beyond Phase 9, PhaseDeferred("§21"), §35) to reduce per-partition hot-key contention; locality routing (§19) to keep reads local rather than scaling cross-region bandwidth; adaptive placement (§21) to migrate hot partitions toward their access pattern; follower reads (deferred, PhaseDeferred("§15"), §35) to offload read traffic from the leaseholder; batching (§13, §15) to amortize per-RPC and per-fsync overhead as load grows.

Horizontal scale-out adds nodes and partitions, not larger individual Raft groups — the §4 max Raft-group-size ceiling of 7 is a hard bound, not a target to grow past; C6 (§32) shows why heartbeat fanout makes larger groups counterproductive well before 7 is reached in practice for most workloads.

30. Mental Models & First Principles

  • MM1 — Consensus Is A Serialization Point, Not A Speed Bump. Insight: every write funnels through one leader per partition; throughput scales by adding partitions, never by speeding a single Raft group past its quorum-RTT floor. Predicts: adding CPU to one node never raises single-partition write throughput past the quorum-RTT ceiling. Bug class without it: chasing single-node CPU optimization when the fix is repartitioning. Applies in §15 and §29.
  • MM2 — The WAL Is The Database; Everything Else Is A Cache. Insight: storage-engine state is fully derivable from replication-log; SSTables are an optimization, not the source of truth. Predicts: any storage corruption is recoverable without data loss as long as the WAL is intact. Bug class without it: hand-patching corrupted SSTables instead of replaying from WAL, risking silent divergence. Applies in §14 and §16.
  • MM3 — Epochs Convert Time Into A Comparable Integer. Insight: comparing wall-clock time across nodes is unsafe under skew; comparing epoch/term integers is always safe. Predicts: any "who owns this now" bug is solvable by finding the skipped epoch comparison. Bug class without it: adding wall-clock timeouts to fix ownership races, reintroducing the skew problem. Applies in §15 and §18.
  • MM4 — Backpressure Converts Overload Into Latency Into Errors, Deliberately. Insight: a bounded queue turns silent memory growth into visible, alertable request shedding — that trade is the point. Predicts: unbounding a queue to "fix" dropped requests causes an OOM under the next real spike. Bug class without it: removing bounds and reintroducing P3 violations. Applies in §13 and §19.
  • MM5 — Determinism Is A Testing Strategy, Not Just A Correctness Property. Insight: a deterministic apply path makes bugs reproducible from a seed, turning an unreproducible distributed heisenbug into a bisectable log divergence. Predicts: any nondeterminism smuggled into the apply path eventually shows up as an unexplained simulator divergence. Bug class without it: "fixing" flaky tests with retries instead of finding hidden nondeterminism. Applies in §20.
  • MM6 — Write Amplification Is A Conserved Quantity, Not A Bug. Insight: LSM compaction trades write amplification for read amplification and space amplification; the tradeoff is chosen, not eliminated. Predicts: "fixing" write amplification by disabling compaction moves the cost to read latency and disk space instead. Bug class without it: tuning compaction to zero write-amp and being surprised reads get slow. Applies in §16 and §28.
  • MM7 — A Lease Is A Time-Bounded Promise, Not A Lock. Insight: a lease is valid only because everyone agrees on a clock-skew bound; treating it as an infinite lock ignores that dependency. Predicts: any lease bug that reproduces only under load or across regions is a skew-tolerance violation, not a locking bug. Bug class without it: adding more locking around lease checks instead of tightening skew bounds. Applies in §15 and §18.
  • MM8 — Every ADR's Sixth Column Is The Real Insurance Policy. Insight: knowing when a rejected alternative becomes correct prevents cargo-culting a decision into a context where it no longer applies. Predicts: copying ADR-05 (custom LSM) into a low-write-volume analytics tool is a mis-transplanted decision. Bug class without it: architecture decisions ossify into dogma disconnected from their justifying constraints. Applies in §9 and §34.

  • CockroachDB — chose a single unified storage/SQL binary over separating storage and query layers; wins when operators want turnkey Postgres-wire-compatible SQL without assembling a stack.
  • TiKV/TiDB — chose to split the storage layer (TiKV) from the SQL layer (TiDB) as independently deployable systems; wins when a team wants a distributed KV store usable by multiple query engines, not one SQL dialect.
  • Spanner — chose dedicated TrueTime hardware (GPS/atomic clocks) over algorithmic clock synchronization; wins when an organization controls its own datacenters and can afford dedicated timing hardware for tighter external-consistency bounds than a hybrid-logical clock gives.
  • FoundationDB — chose to unbundle the transaction layer from storage entirely and invest in deterministic simulation before scale-out correctness; wins when correctness-under-simulation is valued over ecosystem breadth and multiple data-model layers must share one substrate.

32. Back-of-Envelope Capacity Model

  • C1 — Raft Group Memory Footprint. 8,000 partitions/node (§4) × ~2 KB per group's in-memory state (log indices, membership) = 16 MB, trivial against the 16 GB replica process budget (§4).
  • C2 — Replica Processes per Node. 64 GB node ceiling (§4) ÷ 16 GB replica process budget (§4) = 4 co-located replica processes/node before hitting the memory ceiling.
  • C3 — Memtable RAM per Node. 8,000 partitions/node × a 256 KB bounded memtable (P6) = 2 GB, leaving headroom for bloom filters and block indexes within the 16 GB per-process ceiling (§4).
  • C4 — WAL Write Rate. 50 MB/s sustained payload rate × 2.5x WAL amplification (§4 ceiling) = 125 MB/s on-disk WAL bytes/s, well under typical NVMe sequential-write throughput (≥ 500 MB/s).
  • C5 — Combined Device IO. 50 MB/s payload × up to 15x compaction write amplification (§4) = 750 MB/s compaction IO, + 125 MB/s WAL IO (C4) = 875 MB/s combined, requiring an NVMe device rated above 1 GB/s sustained write to avoid contention.
  • C6 — Heartbeat Fanout. 7 max replicas/group (§4) × 8,000 partitions/node = 56,000 heartbeat targets/node per interval; at a 150 ms interval, 56,000 ÷ 0.15 s ≈ 373,333 heartbeats/s, which must be batched (§15.7) rather than sent as discrete RPCs.
  • C7 — File Descriptor Budget. 8,000 partitions/node × 2 fds/partition (WAL segment + manifest) = 16,000 fds + 50,000 max connections (§4) = 66,000 fds, comfortably inside the 250,000 FD budget (§4).
  • C8 — Cross-Region Commit Floor. 60 ms minimum inter-region RTT (§4) × 2 round trips (2PC prepare + commit) = 120 ms floor, leaving 250 − 120 = 130 ms of margin under the p99 cross-region write budget (§4) for queueing, fsync, and serialization.
  • C9 — Availability Budget. (1 − 0.9995) × 30 days × 24 h × 60 min = 0.0005 × 43,200 min = 21.6 min of allowed downtime per month at the 99.95% target (§4), covering planned and unplanned time combined.
  • C10 — SSTables per Partition. A 10 GB partition ÷ 128 MB SSTable target size (§4) = 78 base-level SSTables per partition, before additional levels — bounds the bloom/index memory in C3.
  • C11 — Cross-Region Snapshot Transfer. 128 MB snapshot bundle (§4 target size) ÷ 50 MB/s assumed inter-region transfer rate = 2.56 s transfer time, excluding the C8 RTT setup cost, well inside the 5-minute RTO (§4).
  • C12 — Startup Replay Budget. 90 s startup target (§4) − 2.56 s snapshot transfer (C11) = 87.44 s remaining for WAL replay, which at a conservative 50,000 entries/s replay rate allows replaying up to ≈ 4.37M WAL entries before violating the startup budget.

34. Alternative Architectures (Roads Not Taken)

Alt A — Leaderless Quorum Replication

Client
  |--write(W acks required)--> Replica 1 --\
  |--write(W acks required)--> Replica 2 ---+--> quorum W met -> ack
  |--write(W acks required)--> Replica 3 --/
  read(R replicas queried) -> read-repair on divergence

Real system: Cassandra / Dynamo (§5, §31). Regime where it wins: workloads tolerating eventual consistency that need maximum write availability during a partition — session state, time-series ingestion, wide-column stores with no cross-key transactional requirement. Why rejected: this blueprint requires serializable cross-partition transactions (§17) and single-lease ownership (I2); leaderless quorum replication has no natural place to run 2PC coordination or maintain a monotonic commit index (I3).

Alt B — Deterministic Pre-Ordering

Txn requests --> Sequencer (batches into epochs)
                     |
                     v
        Epoch N schedule replicated to all replicas
                     |
                     v
   every replica executes schedule N independently, deterministically

Real system: Calvin (Thomson et al. 2012, §5). Regime where it wins: workloads with read/write sets known before execution and very high transaction throughput requirements, where the sequencer's batching cost amortizes across huge batches. Why rejected: this blueprint's transactions discover their write set during execution (§17), not upfront — exactly the case Calvin's sequencer-based determinism handles poorly without a separate read/write-set analysis pass this blueprint does not budget for in Phase 0 (§1).

Alt C — Unbundled Transaction/Storage Layers

+------------------+       versioned reads/writes      +-------------------+
| Transaction Layer | <--------------------------------> | Storage Server Tier|
| (stateless)       |                                    | (independent scale) |
+------------------+                                    +-------------------+

Real system: FoundationDB (Zhou et al. 2021, §5). Regime where it wins: when multiple query/data-model layers (document, SQL, graph) must share one transactional storage substrate, and correctness-by- simulation is prioritized over the fastest path to one integrated SQL-like surface. Why rejected: this blueprint's Phase 0 scope (§1) is a single, integrated geo-partitioned KV/SQL-like surface, not a layered platform for multiple data models — the unbundling cost is not justified until that platform ambition exists (tracked only as a later-phase unlock, not a Phase 0 architecture, §1).

36. Glossary

  • Leaseholder — the authoritative, writable replica for a partition at a given epoch.
  • SSTable — immutable sorted-string table, the on-disk unit of storage-engine.
  • WAL — write-ahead log, the durable, append-only record replication-log maintains.
  • MVCC — multi-version concurrency control, storing multiple timestamped versions per key.
  • Compaction — the background process merging SSTables to bound read/write/space amplification.
  • Tombstone — a deletion marker retained until compaction can safely remove the underlying key.
  • Quorum — a majority replication set within a Raft group, required to commit an entry.
  • Snapshot — a point-in-time, checksum-verified persisted state boundary.
  • Epoch — a monotonic topology-generation number used to fence stale metadata.
  • Intent — a provisional transactional write, replicated before a transaction's final commit.
  • Fencing token — a monotonic value that invalidates a demoted leader's stale writes.
  • Replay — deterministic re-execution of a persisted log to reconstruct state.
  • Backpressure — a flow-control mechanism that bounds queue growth under overload.
  • Raft term — an election epoch within the Raft consensus algorithm.
  • Manifest — a metadata index describing the storage files belonging to a snapshot.
  • Partition — a contiguous key range owned by one Raft consensus group.
  • Shard — used interchangeably with partition in this blueprint's routing context.
  • Hybrid logical clock (HLC) — a clock combining physical time and a logical counter for causally-ordered, skew-tolerant timestamps.
  • Commit index — the highest log index known to be committed within a Raft group.
  • Membership change — a reconfiguration of a Raft group's replica set.
  • Joint consensus — Raft's two-phase membership-change protocol avoiding disjoint majorities.
  • Bloom filter — a probabilistic structure bounding negative-lookup cost in an SSTable.
  • Memtable — the mutable, in-memory sorted buffer preceding an SSTable flush.
  • Write amplification — the ratio of bytes written to disk versus payload bytes written.
  • Read amplification — the number of storage reads needed to answer one logical read.
  • Space amplification — the ratio of on-disk size to logical data size.
  • Leveled compaction — a compaction strategy bounding write amplification via sorted levels.
  • Anti-entropy — background reconciliation of replica divergence, used by leaderless systems.
  • Circuit breaker — a mechanism that stops routing to a target once it is deemed unhealthy.
  • Admission control — the gateway policy deciding which requests are accepted versus shed.
  • Idempotency key — a client-supplied token making a retried write safe to apply at most once.
  • Correlation ID — an identifier threading one logical request across every RPC hop.
  • Span — one traced operation's duration and metadata within a distributed trace.
  • Trace — the full tree of spans for one logical request.
  • OTLP — the OpenTelemetry Protocol used to export traces, metrics, and logs.
  • Deterministic simulation — testing methodology replaying faults from a seed for bit-for-bit reproducibility.
  • Fault injection — deliberately introducing failures (partition, crash, corruption) under test.
  • Torn write — an incomplete WAL entry left by a crash mid-write, distinct from true corruption.
  • Split brain — a state where two nodes both believe themselves the authoritative leader.
  • Write skew — a serializability anomaly where transactions read disjoint keys the other modifies.
  • Deadlock — a cycle of transactions each waiting on a lock the other holds.
  • Two-phase commit (2PC) — a commit protocol requiring all participants to prepare before commit.
  • Timestamp oracle — the service issuing monotonically increasing transaction timestamps.
  • Cutover — the moment a partition's ownership formally transfers to a new replica set.
  • Rebalancing — redistributing partitions across nodes to relieve hotspots or restore balance.
  • RTO — recovery time objective, the maximum acceptable time to restore service after a failure.
  • RPO — recovery point objective, the maximum acceptable data loss window after a failure.
