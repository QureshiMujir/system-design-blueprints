33. Hard Questions (Self-Examination)

  • Q1. If a network partition isolates a minority of a Raft group for exactly the §4 clock-skew tolerance window, does the majority side's §15 lease ever become unsafe to trust, and why does §7's I7 fencing token — not the lease timer alone — close the gap?
  • Q2. Why does the §17 transaction coordinator's crash-recovery path depend on the §14 WAL's replayability guarantee (P5) rather than on the coordinator's own local state, and what breaks if that dependency were inverted?
  • Q3. Given the §4 p99 cross-region write budget of 250 ms and the two-round-trip floor derived in §32 (C8), how much latency margin remains for §19's gateway-side admission-control queueing before the budget is violated, and what should degrade first?
  • Q4. Why is a compaction stall (§16, §23 FM-7) a backpressure problem to solve with I8 rather than a capacity problem to solve with more disk, given the write-amplification ceiling in §4?
  • Q5. If §21's migration planner and §18's lease-renewal path both mutate PartitionDescriptor state, why does routing both through the same epoch-fenced compare-and-swap (§11, P8) prevent the race described in §21.6, and what would a naive two-lock implementation get wrong?
  • Q6. Why does §30's MM2 imply that §16's SSTable-corruption failure mode (§16.9) is never a data-loss incident by itself, and under what condition from §14's retention manager would that stop being true?
  • Q7. Why does §9's ADR-02 lock in Raft over EPaxos for operational clarity, and under what workload shape from §29's scalability analysis would that tradeoff flip, given §34's Alt A explores a different regime instead?
  • Q8. Why does §22's threat T8 (WAL tampering) require signed snapshots rather than the same CRC32c checksum §14 already uses for accidental corruption, given both defend the same file?
  • Q9. §7's I13 (atomic visibility) and §17's 2PC prepare/commit flow both claim to prevent partial commits; which is load-bearing if storage-engine's apply loop crashes between two partitions' applies, and which is redundant?
  • Q10. Why does §19's gateway retry policy reuse the same idempotency_key mechanism as §7's I10 instead of defining its own retry-safety property, and what would duplicate under load if it didn't?
  • Q11. Given §28's M9 (leader-election convergence < 5 s) and §23's FM-1 (leader crash), what does §32's C6 heartbeat-fanout arithmetic imply about the maximum safe heartbeat interval before election convergence itself becomes the bottleneck?
  • Q12. §6's P10 (fail closed) and §15's simultaneous-quorum-loss edge case both prescribe rejecting writes under uncertainty; why is this the same decision as §21's migration-abort-on-target-outage, and what single invariant from §7 do all three ultimately protect?
  • Q13. Why does §5's Aurora citation (log-is-the-database) justify §14's replication-log being authoritative over §16's storage-engine, but not justify making §18's metadata-service similarly subordinate to any single log?
  • Q14. If §20's deterministic simulator finds a divergence that §7's I12 assertion should have caught, what does that imply about the debugging-methodology paragraph closing §7, and how does §30's MM5 explain why the fix belongs in the simulator before the code path?
  • Q15. Why does §4's NUMA-awareness requirement interact with §16's bloom-filter/block-index residency argument but not meaningfully with §13's QUIC transport layer, given both are performance-sensitive hot paths?
  • Q16. §9's ADR-21 locks in a hybrid-logical clock over pure wall-clock time; trace how a violation of that choice would surface first — an §7 I9 failure or an §17 write-skew fixture failure — and justify which fires first.
  • Q17. Why does §35's deferral of online partition splitting (registered against §21) not also require deferring §21's migration planner itself, and what does §18 gain by keeping the two decisions separate?
  • Q18. 30. Mental Models & First Principles

  • MM1 — Consensus Is A Serialization Point, Not A Speed Bump. Insight: every write funnels through one leader per partition; throughput scales by adding partitions, never by speeding a single Raft group past its quorum-RTT floor. Predicts: adding CPU to one node never raises single-partition write throughput past the quorum-RTT ceiling. Bug class without it: chasing single-node CPU optimization when the fix is repartitioning. Applies in §15 and §29.
  • MM2 — The WAL Is The Database; Everything Else Is A Cache. Insight: storage-engine state is fully derivable from replication-log; SSTables are an optimization, not the source of truth. Predicts: any storage corruption is recoverable without data loss as long as the WAL is intact. Bug class without it: hand-patching corrupted SSTables instead of replaying from WAL, risking silent divergence. Applies in §14 and §16.
  • MM3 — Epochs Convert Time Into A Comparable Integer. Insight: comparing wall-clock time across nodes is unsafe under skew; comparing epoch/term integers is always safe. Predicts: any "who owns this now" bug is solvable by finding the skipped epoch comparison. Bug class without it: adding wall-clock timeouts to fix ownership races, reintroducing the skew problem. Applies in §15 and §18.
  • MM4 — Backpressure Converts Overload Into Latency Into Errors, Deliberately. Insight: a bounded queue turns silent memory growth into visible, alertable request shedding — that trade is the point. Predicts: unbounding a queue to "fix" dropped requests causes an OOM under the next real spike. Bug class without it: removing bounds and reintroducing P3 violations. Applies in §13 and §19.
  • MM5 — Determinism Is A Testing Strategy, Not Just A Correctness Property. Insight: a deterministic apply path makes bugs reproducible from a seed, turning an unreproducible distributed heisenbug into a bisectable log divergence. Predicts: any nondeterminism smuggled into the apply path eventually shows up as an unexplained simulator divergence. Bug class without it: "fixing" flaky tests with retries instead of finding hidden nondeterminism. Applies in §20.
  • MM6 — Write Amplification Is A Conserved Quantity, Not A Bug. Insight: LSM compaction trades write amplification for read amplification and space amplification; the tradeoff is chosen, not eliminated. Predicts: "fixing" write amplification by disabling compaction moves the cost to read latency and disk space instead. Bug class without it: tuning compaction to zero write-amp and being surprised reads get slow. Applies in §16 and §28.
  • MM7 — A Lease Is A Time-Bounded Promise, Not A Lock. Insight: a lease is valid only because everyone agrees on a clock-skew bound; treating it as an infinite lock ignores that dependency. Predicts: any lease bug that reproduces only under load or across regions is a skew-tolerance violation, not a locking bug. Bug class without it: adding more locking around lease checks instead of tightening skew bounds. Applies in §15 and §18.
  • MM8 — Every ADR's Sixth Column Is The Real Insurance Policy. Insight: knowing when a rejected alternative becomes correct prevents cargo-culting a decision into a context where it no longer applies. Predicts: copying ADR-05 (custom LSM) into a low-write-volume analytics tool is a mis-transplanted decision. Bug class without it: architecture decisions ossify into dogma disconnected from their justifying constraints. Applies in §9 and §34.

5. Required Reading

Books

  • Designing Data-Intensive Applications — Martin Kleppmann (2017), ch. 5–9: replication topologies, partitioning schemes, consistency models; applied in §8 and §18.
  • Database Internals — Alex Petrov (2019), ch. 2–7: WAL design, LSM structure, compaction strategies; applied in §14 and §16.
  • Transaction Processing: Concepts and Techniques — Jim Gray and Andreas Reuter (1992), recovery and concurrency-control chapters: ARIES-style recovery, two-phase locking; applied in §17.
  • Distributed Systems — Andrew S. Tanenbaum and Maarten van Steen (3rd ed., 2017), clocks and fault-model chapters: logical clocks, distributed coordination; applied in §6 and §22.
  • Consensus: Bridging Theory and Practice — Diego Ongaro, Ph.D. dissertation, Stanford University (2014), ch. 3–6: membership transitions, log safety, leader-election proofs; applied in §15.
  • Linux Kernel Development — Robert Love (3rd ed., 2010), scheduler and IO chapters: CFS scheduling behavior, block-layer IO paths; applied in §13 and §28.
  • TCP/IP Illustrated, Volume 1 — W. Richard Stevens (1994), retransmission and congestion chapters: RTT estimation, congestion backoff; applied in §13.

Papers

  • "Bigtable: A Distributed Storage System for Structured Data" — Chang et al., 2006, OSDI: sparse column families over sorted immutable files → informs SSTable and compaction layout; applied in §16.
  • "Spanner: Google's Globally-Distributed Database" — Corbett et al., 2012, OSDI: TrueTime-bounded external consistency → informs clock-skew tolerance and cross-region ordering; applied in §17 and §21.
  • "Dynamo: Amazon's Highly Available Key-value Store" — DeCandia et al., 2007, SOSP: quorum reads/writes and anti-entropy repair → informs quorum-tuning tradeoffs; applied in §15.
  • "Calvin: Fast Distributed Transactions for Partitioned Database Systems" — Thomson et al., 2012, SIGMOD: deterministic pre-ordered transaction scheduling → informs replay determinism; applied in §17.
  • "No Compromises: Distributed Transactions with Consistency, Availability, and Performance" — Dragojević et al., 2015, SOSP (FaRM): RDMA-backed commit protocol → informs 2PC latency budgeting; applied in §17.
  • "In Search of an Understandable Consensus Algorithm" — Ongaro and Ousterhout, 2014, USENIX ATC (Raft paper): leader election and log replication → direct basis for raft-engine; applied in §15.
  • "The Log-Structured Merge-Tree" — O'Neil, Cheng, Gawlick, O'Neil, 1996, Acta Informatica: amortized write cost via sorted runs and rolling merges → basis for storage-engine compaction; applied in §16.
  • "Amazon Aurora: Design Considerations for High Throughput Cloud-Native Relational Databases" — Verbitski et al., 2017, SIGMOD: log-is-the-database, quorum-durable storage decoupled from compute → informs the replication-log/storage-engine split; applied in §14 and §16.
  • "FoundationDB: A Distributed Unbundled Transactional Key-Value Store" — Zhou et al., 2021, SIGMOD: layered transaction/storage architecture validated by deterministic simulation → informs simulator design; applied in §20.

Reference Implementations

  • cockroachdb/cockroach — study pkg/kv and pkg/storage: range-descriptor plus one-Raft-group-per-range design; pitfall: do not copy its full distributed-SQL scope into Phase 0; applied in §18.
  • tikv/tikv — study components/raftstore: region metadata and multi-raft scheduling on one process; pitfall: do not adopt region-merge before online partition splitting lands (deferred, §21); applied in §15 and §21.
  • apple/foundationdb — study the storage-server scheduling model: deterministic-simulation-first testing philosophy over ad hoc integration tests; pitfall: do not treat unit tests as a substitute for the simulator investment; applied in §20.
  • etcd-io/etcd — study the raft package: a minimal, storage-agnostic Raft library boundary; pitfall: do not couple the Raft state machine directly to disk layout the way early revisions did; applied in §15.
  • facebook/rocksdb — study db/compaction internals: leveled-compaction write-amplification tuning; pitfall: do not default to universal compaction for a latency-sensitive OLTP workload; applied in §16.
  • apache/cassandra — study the Merkle-tree anti-entropy repair path (nodetool repair): gossip-driven eventual consistency at scale; pitfall: do not adopt its unbounded multi-master conflict resolution — this blueprint explicitly rejects that (§1 non-goals); applied in §18.

RFCs / Specifications

  • RFC 9000 — QUIC transport: connection multiplexing, 0-RTT, per-stream loss recovery; applied in §13.
  • RFC 8446 — TLS 1.3: handshake simplification and downgrade-attack resistance; applied in §13 and §22.
  • OpenTelemetry Protocol Specification (OTLP) v1.0.0 — span, metric, and log wire encoding; applied in §20.
  • Prometheus Exposition Format — text-based metrics scrape encoding consumed by the Prometheus server; applied in §20.

Glossary (§36) · 47 terms · site-wide glossary

Leaseholder
the authoritative, writable replica for a partition at a given epoch.
SSTable
immutable sorted-string table, the on-disk unit of storage-engine.
WAL
write-ahead log, the durable, append-only record replication-log maintains.
MVCC
multi-version concurrency control, storing multiple timestamped versions per key.
Compaction
the background process merging SSTables to bound read/write/space amplification.
Tombstone
a deletion marker retained until compaction can safely remove the underlying key.
Quorum
a majority replication set within a Raft group, required to commit an entry.
Snapshot
a point-in-time, checksum-verified persisted state boundary.
Epoch
a monotonic topology-generation number used to fence stale metadata.
Intent
a provisional transactional write, replicated before a transaction's final commit.
Fencing token
a monotonic value that invalidates a demoted leader's stale writes.
Replay
deterministic re-execution of a persisted log to reconstruct state.
Backpressure
a flow-control mechanism that bounds queue growth under overload.
Raft term
an election epoch within the Raft consensus algorithm.
Manifest
a metadata index describing the storage files belonging to a snapshot.
Partition
a contiguous key range owned by one Raft consensus group.
Shard
used interchangeably with partition in this blueprint's routing context.
Hybrid logical clock (HLC)
a clock combining physical time and a logical counter for causally-ordered, skew-tolerant timestamps.
Commit index
the highest log index known to be committed within a Raft group.
Membership change
a reconfiguration of a Raft group's replica set.
Joint consensus
Raft's two-phase membership-change protocol avoiding disjoint majorities.
Bloom filter
a probabilistic structure bounding negative-lookup cost in an SSTable.
Memtable
the mutable, in-memory sorted buffer preceding an SSTable flush.
Write amplification
the ratio of bytes written to disk versus payload bytes written.
Read amplification
the number of storage reads needed to answer one logical read.
Space amplification
the ratio of on-disk size to logical data size.
Leveled compaction
a compaction strategy bounding write amplification via sorted levels.
Anti-entropy
background reconciliation of replica divergence, used by leaderless systems.
Circuit breaker
a mechanism that stops routing to a target once it is deemed unhealthy.
Admission control
the gateway policy deciding which requests are accepted versus shed.
Idempotency key
a client-supplied token making a retried write safe to apply at most once.
Correlation ID
an identifier threading one logical request across every RPC hop.
Span
one traced operation's duration and metadata within a distributed trace.
Trace
the full tree of spans for one logical request.
OTLP
the OpenTelemetry Protocol used to export traces, metrics, and logs.
Deterministic simulation
testing methodology replaying faults from a seed for bit-for-bit reproducibility.
Fault injection
deliberately introducing failures (partition, crash, corruption) under test.
Torn write
an incomplete WAL entry left by a crash mid-write, distinct from true corruption.
Split brain
a state where two nodes both believe themselves the authoritative leader.
Write skew
a serializability anomaly where transactions read disjoint keys the other modifies.
Deadlock
a cycle of transactions each waiting on a lock the other holds.
Two-phase commit (2PC)
a commit protocol requiring all participants to prepare before commit.
Timestamp oracle
the service issuing monotonically increasing transaction timestamps.
Cutover
the moment a partition's ownership formally transfers to a new replica set.
Rebalancing
redistributing partitions across nodes to relieve hotspots or restore balance.
RTO
recovery time objective, the maximum acceptable time to restore service after a failure.
RPO
recovery point objective, the maximum acceptable data loss window after a failure.
