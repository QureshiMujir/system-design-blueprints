3. Architectural Overview

Canonical architecture:

+-------------------------------------------------------------------+
|                       Client Applications                         |
+------------------------------+--------------------------------+---+
                               | QUIC/TLS 1.3 (trust boundary)
                               v
+-------------------------------------------------------------------+
|  gateway  (Routing Gateway Layer)                                 |
|  locality routing | admission control | auth | conn pooling       |
|  bounded ingress queue (backpressure boundary)                    |
+---------------+--------------------------------+------------------+
                | intra-cluster RPC               |
                v                                  v
+----------------------------+   +-----------------------------------+
| txn-coordinator            |   | metadata-service /                |
| timestamp oracle | locks   |   | topology-controller               |
| deadlock detector          |   | partition map | leases | placement|
+--------------+-------------+   +----------------+-------------------+
               | 2PC intents                       | epoch-fenced reads
               v                                    v
+-------------------------------------------------------------------+
|                    Regional Replica Groups (per shard range)      |
| +-----------------------+   +-----------------------------------+ |
| | raft-engine           |   | replication-log                  | |
| | quorum | elections    |<->| WAL | segments | snapshot markers | |
| | commit index (I3)     |   | catch-up streaming                | |
| +-----------+-----------+   +----------------+-------------------+ |
|             | apply loop (concurrency boundary: 1 writer/partition)|
|             v                                                     |
| +-------------------------------------------------------------+   |
| | storage-engine                                               |   |
| | memtable | SSTable | compaction | bloom filters | MVCC       |   |
| | (persistence boundary: fsync before ack)                    |   |
| +-------------------------------+-----------------------------+   |
+---------------------------------|---------------------------------+
                                   v
+-------------------------------------------------------------------+
|  observability + simulator + admin-cli                            |

+-------------------------------------------------------------------+

Client Applications — untrusted external boundary; speak the protocol wire schema over QUIC/TLS 1.3 only (ADR-07, ADR-18); never address a replica directly.

gateway (Routing Gateway Layer) — trust boundary terminates client TLS, authenticates (RBAC), enforces admission control against a bounded ingress queue (P3), and dispatches by locality using a cached partition map from metadata-service. Retries are budgeted, not unbounded (pitfall in §19.6).

txn-coordinator — stateless except for durable TxnRecord metadata (§11); owns the timestamp oracle, write-intent lifecycle, and deadlock detection; issues 2PC prepare/commit against the owning raft-engine groups. Protocol boundary: every message crossing into a replica group is a Protobuf AppendEntries-family message (§8).

metadata-service / topology-controller — sole authority for partition ownership, lease assignment, and topology epoch; topology-controller is the reconciliation loop that plans placement changes and enqueues them, epoch-fenced against metadata-service's serialized topology store (P9, I2).

raft-engine — one consensus group per shard range (§4 cap: 7 replicas max); concurrency boundary is one active writer (leader) per partition per epoch; commit index is monotonic (I3) and is the handoff point to storage-engine.

replication-log — durability boundary: WAL fsync precedes any visibility (I1, StorageEngine guarantee in §11); owns segment rotation, snapshot markers, catch-up streaming to lagging followers, and retention/truncation policy.

storage-engine — MVCC over an LSM tree: memtable (mutable, in-memory) → immutable SSTable flush → background compaction; bloom filters bound negative-lookup cost; persistence boundary is the same fsync point replication-log enforces.

observability + simulator + admin-cli — external interfaces: Prometheus scrape endpoint, OTLP trace export, structured JSON log stream, deterministic replay capture (consumed by simulator and conformance-harness), and the admin-cli operator surface (topology inspection, drains, canaries).

8. Domain Model — Partitioning, Replication & Transaction Protocol

Partition key (routes every request; owned by metadata-service, immutable once assigned):

PartitionKey:
  tenant_id: u64
  geographic_region: RegionId
  logical_shard: u32
  hash_suffix: u32

Replication message (Raft AppendEntries family; owned by raft-engine, wire-serialized via protocol):

AppendEntries:
  term: u64
  leader_id: NodeId
  prev_log_index: u64
  prev_log_term: u64
  entries: Vec<WalEntry>
  leader_commit: u64

MVCC tuple (owned by storage-engine; one physical row per (key, version)):

VersionedRow:
  key: Bytes
  version_ts: HybridLogicalTimestamp
  txn_id: TxnId
  tombstone: bool
  payload: Bytes

Transaction states (owned by txn-coordinator, persisted in TxnRecord, §11):

State Meaning
Pending active transaction, intents not yet replicated
Prepared write intents replicated to all owning Raft groups
Committed durable, visible to subsequent reads at commit_ts
Aborted rollback completed, intents released

Canonical commit sequence:

Client -> gateway -> txn-coordinator
txn-coordinator -> raft-engine (leader, per owning partition)
leader -> followers (AppendEntries)
followers -> leader (Ack, quorum)
leader -> storage-engine (apply at commit index)
txn-coordinator -> Client (commit_ts)

Malformed input classes (must be rejected, never silently coerced): duplicate transaction IDs, stale term appends, invalid snapshot checksums, non-monotonic timestamps, partition-key hash-suffix mismatch with declared range.

Canonical failure path — leader crash during prepare:

leader crash mid-prepare
  -> election timeout fires on followers
  -> new leader elected (higher term)
  -> new leader replays WAL from last snapshot
  -> commit index recovery (I3)
  -> txn-coordinator resolves in-flight TxnRecord (Prepared -> Committed or Aborted)
