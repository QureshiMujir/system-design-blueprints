Hard questions (§34)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does the tri-color invariant (I1) need a write barrier but concurrent compaction (Phase 8) needs a read barrier as well — what specifically changes between "concurrent marking" and "concurrent moving"? (§18, §20)
  2. Derive the card-table memory overhead at a 1 GiB heap from first principles, then explain why halving the card size does not simply halve the false-positive rescan rate. (§17, §33)
  3. Why is Cheney's copying collector's "half the heap is wasted" cost acceptable for a nursery but would be unacceptable for the old generation? (§16, §17)
  4. Trace exactly what breaks if the card table is cleared at minor-GC entry instead of epilogue, using the worked example in the Domain Model. (§8, §17, I6)
  5. Why does Bacon-Rajan cycle collection need a "roots buffer" at all if reference counting already reclaims everything with count zero? (§13, §5)
  6. Compare the memory-overhead regime where a per-object remembered set beats a card table against the regime in this blueprint's Phase 5 choice — under what write density does the alternative win? (§17, ADR table §9)
  7. Why does this blueprint reject ZGC-style coloured pointers for Phase 8 even though they achieve a tighter pause-time floor than Brooks pointers? (§20, §32, ADR-0019)
  8. Explain why floating garbage is fundamentally different from fragmentation as a collector cost, and why one collector kind in this blueprint can have one without the other. (§15, §19, I13)
  9. Using the Back-of-Envelope model, show why the remembered-set bound at 8 GiB stays within budget but would not necessarily stay within budget at 64 GiB without a design change — what design change would restore the bound? (§30, §33)
  10. Why must "compute new addresses" happen entirely before "update pointers" in mark-compact, and what specific bug results from interleaving them? (§15, MM2)
  11. What is the exact difference between the strong tri-color invariant (Dijkstra) and the weak tri-color invariant (Yuasa/SATB), and why does this blueprint pick a different one per phase rather than one for all concurrent/incremental kinds? (§18, §19, ADR-0004)
  12. Why does a host with no compiler cooperation (no stack maps) force this design toward BDW-style conservative scanning, and what correctness property does precise scanning buy back that conservative scanning cannot? (§12, §32, MM7)
  13. Explain why the region-based collector (Phase 9) needs a cost-estimation model for collection-set selection rather than simply always evacuating the lowest-occupancy regions greedily. (§21, §29)
  14. Why is a gc_panic the correct response to an RC underflow (I3) rather than clamping the count to zero and continuing? (§13, §24 FM-3)
  15. Trace the full path of a promotion failure from detection to recovery, and explain why repeated failures are a heap-sizing signal rather than a correctness bug. (§17, §24 FM-5)
  16. Why does this blueprint's Phase 6 ship only the Dijkstra barrier and defer SATB to Phase 7, rather than shipping both from the start? (§18, §19, P8)
  17. Using the Comparative Architecture Table and the Alternative Architectures section, explain the one structural reason Go's runtime GC never needs a read barrier at all, unlike this blueprint's Phase 8. (§32, §35)
  18. Why does a safepoint model built on cooperative polling make precise stack maps possible, and what would break if the collector instead used only asynchronous signal-based interruption? (§12, MM7)
  19. Explain how the pacer's mutator-assist mechanism (§19) is structurally a feedback controller, and identify what "disturbance" and "control input" correspond to in GC terms. (§19, MM8)
  20. Why does this blueprint's Deferred Features Register defer NUMA-awareness rather than building it into Phase 9 directly, given that region-based collectors are exactly where NUMA placement would matter most? (§21, §36)

31. Mental Models & First Principles

  1. MM1 — A tri-color mark is a graph-coloring invariant, not a scheduling trick. The insight: white/grey/black is exactly "unvisited/frontier/done" in a BFS/DFS reachability search, and the invariant (no black→white edge, I1) is what makes interrupting that search safe. Predicts: any barrier that fails to preserve the invariant drops live objects, regardless of how clever its scheduling is. Bug class without it: engineers "optimize" a barrier by skipping it under load, not realizing the invariant — not the barrier's frequency — is the safety property. Applied in §18, §19.
  2. MM2 — A moving collector's compaction is a topological sort with side effects. The insight: computing new addresses before updating pointers (§15.2) is exactly "compute the permutation before applying it" — the two-pass split exists because permutation application and permutation computation cannot interleave safely. Predicts: any attempt to fuse the passes for "efficiency" corrupts the graph. Bug class without it: single-pass compaction bugs that only manifest on specific object orderings. Applied in §15.
  3. MM3 — A read barrier is the mirror image of a write barrier. The insight: a write barrier protects the collector's view of the graph from mutator writes; a read barrier protects the mutator's view of the graph from collector relocation (§20). Predicts: any concurrent-moving design needs exactly one of {read barrier, handle indirection} — there is no design that needs neither (P12). Bug class without it: assuming a write-barrier-only concurrent design (Phase 7's kind) can be naively extended to also move objects (it cannot, without §20's read barrier). Applied in §20.
  4. MM4 — Floating garbage is not a bug, it's a knob. The insight: a concurrent collector's "start-of-mark snapshot" (SATB, I10) necessarily retains some garbage until the next cycle — bounding it (I13) is a pacing problem, not a correctness problem. Predicts: chasing floating garbage to zero necessarily costs pause time or throughput elsewhere — there is no free lunch. Bug class without it: engineers treating nonzero floating garbage as always a defect and over-engineering it away at a throughput cost nobody asked for. Applied in §19.
  5. MM5 — The card table is a lossy compression of "which pointers changed." The insight: card granularity (512 B) trades false-positive rescanning (multiple objects per dirty card) for bounded metadata size (§33) — it is a Bloom-filter-shaped tradeoff, not a precise data structure. Predicts: shrinking card size always trades metadata memory for scan precision, in either direction, with no "correct" size independent of workload. Bug class without it: tuning card size to chase a metric without understanding the fundamental tradeoff axis. Applied in §17, §33.
  6. MM6 — Every generational hypothesis is an empirical bet, not a theorem. The insight: "most objects die young" (Lieberman, Hewitt 1983, §5) is a measured property of typical workloads, not a law — a workload that violates it (long-lived-object-heavy) makes generational collection actively worse than a single-generation kind. Predicts: no generational collector is uniformly better; the comparative table (§32) exists because the "best" collector is workload- dependent. Bug class without it: assuming generational is strictly an improvement and never benchmarking against a non-generational baseline for a given workload. Applied in §17, §32.
  7. MM7 — A safepoint is a rendezvous, not an interrupt. The insight: cooperative polling (ADR-0006) means the mutator agrees to stop at specific points, unlike an async signal-based interrupt — this is what makes precise stack-map scanning possible at all (the compiler knows the exact live-register state at a poll point). Predicts: a host that cannot guarantee poll-site density (e.g. a tight native loop with no GC-visible call) needs either a trap-page fallback or conservative scanning. Bug class without it: assuming any thread can be "GC-paused" at an arbitrary instruction, which breaks precise root scanning. Applied in §12, §22.
  8. MM8 — Pacing is control theory, not a fixed threshold. The insight: the mutator-assist pacer (§19, applied from Hudson 2018) is a feedback controller — allocation rate is the disturbance, assist strength is the control input, floating garbage/pause time are the outputs being bounded. Predicts: a fixed (non-adaptive) threshold pacer either over-throttles common-case workloads or under-throttles bursty ones — only a feedback design handles both. Bug class without it: hand-tuned static pacing constants that regress the moment workload shape shifts. Applied in §19, §22.

Reference Implementations

  • Boehm-Demers-Weiser conservative GC (bdwgc, github.com/ivmai/bdwgc) — study alloc.c/mark.c; lesson: a decades-hardened conservative scanner and free-list allocator, applied §12, §14 (conservative fallback scanner, free-list allocator); pitfall not to copy: its stack-scan heuristics assume a C ABI without precise stack maps — do not reuse them once precise scanning (§12, §15) is available.
  • Go runtime (runtime/mgc.go, runtime/mbarrier.go, runtime/mheap.go) — study the hybrid write barrier and the pacer; lesson: concurrent mark pacing tied to allocation rate (§19, §25); pitfall: Go's barrier assumes a cooperative, fully-precise compiler — do not port it verbatim to a conservative-root host.
  • V8 Orinoco (src/heap/) — study incremental marking and parallel scavenging; lesson: generational + incremental compose cleanly (§17+§18); pitfall: V8's object model bakes in JS-specific hidden classes, not reusable for a generic gc_typeinfo_t host.
  • HotSpot (hotspot/share/gc/{g1,shenandoah,z}) — study G1's remembered sets, Shenandoah's Brooks pointers, ZGC's coloured pointers; lesson: three different concurrent strategies at the same JVM, proving there is no single right answer (§32, §35); pitfall: all three assume a JIT emits precise stack maps and safepoints — this project's conservative fallback path has no HotSpot analogue.
  • OCaml multicore runtime (runtime/gc_*.c) — study the minor/major generational split with per-domain nurseries; lesson: per-thread nurseries reduce cross-thread allocation contention (informs §21 region design); pitfall: OCaml's value representation (tagged integers) does not map onto this project's untagged gc_word_t header.

RFCs / Specifications

  • ISO/IEC 9899:2011 (C11), sec. 6.2.4 (storage durations), sec. 7.22 (memory management functions) — applied §11 (gc_word_t, atomics).
  • POSIX.1-2017, sec. 2.9 (threads), mmap/mprotect/madvise — applied §12, §20 (arena and read-barrier trap page).

Glossary (§37) · 53 terms · site-wide glossary

Allocator
the subsystem handing out heap memory to the mutator (bump, free-list, or region-grain, per collector kind).
Arena
an mmap-backed contiguous address range the allocator carves objects from.
Bacon-Rajan cycle collector
a synchronous algorithm that reclaims reference- counted cycles RC alone cannot (§13).
Bump-pointer allocation
allocation by incrementing a free pointer; O(1), no free-list search.
Card table
a side table marking which fixed-size heap regions ("cards") were written since the last scan (§17).
Cheney's algorithm
an iterative semispace copying-collection algorithm using a scan/free pointer pair (§16).
Collector kind
the selected algorithm (gc_config_t.collector_kind); switchable without ABI change (P1).
Compaction
relocating live objects to eliminate fragmentation (§15).
Concurrent marking
tracing performed on worker threads while the mutator continues running (§19).
Conservative scanning
treating ambiguous stack words as candidate pointers without compiler cooperation (§12, §14).
Deferred Features Register
the table (§36) tracking every out-of-scope feature and its un-defer trigger.
Dijkstra (incremental-update) barrier
a write barrier greying a black object's newly-written white child, preserving the strong tri-color invariant (§18).
Fixture (conformance)
a named .gc test program with an expected live-set outcome (§27).
Floating garbage
objects unreachable at end-of-mark but retained until the next cycle (§19, I13).
Forwarding pointer
the relocated address of an object stored in its old header during compaction/copying (§15, §16).
Free list
a per-size-class linked list of reusable heap chunks (§14).
Generational hypothesis
the empirical claim that most objects die young (Lieberman, Hewitt 1983, §5).
Handle table
host-owned indirection layer letting the mutator survive object movement without holding raw pointers across a safepoint (§15, P12).
Handshake
a protocol synchronizing mutator and collector threads at a safepoint (§19).
Heap
the managed address space containing all GC-tracked objects (§8).
Humongous object
an object exceeding the region-size threshold, spanning multiple regions (§21).
Incremental marking
tracing broken into bounded time slices (§18).
Invariant
a property the collector must never violate (tri-color, RC non-negativity, etc., §7).
Large Object Space (LOS)
a dedicated allocation area for objects too big for size-classed free lists (§14).
Live set
the set of objects reachable from roots at a given instant.
Mark bit / mark bitmap
the per-object (or bitmap-encoded) flag recording reachability during tracing.
Mark queue / mark stack
the worklist of grey objects awaiting slot scanning (§14, §19).
Mutator
the application code allocating and mutating the heap (§3).
Mutator assist
pacer-triggered marking work performed by the allocating thread itself to throttle allocation rate (§19, P13).
Nursery
the young generation, typically a semispace pair (§17).
Object header
the fixed metadata word preceding an object's payload (§11).
Old generation
the tenured portion of the heap holding promoted, longer-lived objects (§17).
Pacer
the feedback controller bounding floating garbage and pause time via mutator assist (§19, MM8).
Precise scanning
root scanning using compiler-supplied stack maps, exact rather than conservative (§12, P3).
Promotion
moving a surviving nursery object into the old generation (§17).
Read barrier
code on every load ensuring the mutator never observes a half-relocated object (§20).
Reference counting (RC)
reclamation by tracking per-object incoming-pointer counts (§13).
Region
a fixed-size heap chunk independently classified (free/eden/survivor/ old/humongous) in the region-based collector (§21).
Relocation set
the subset of regions chosen for evacuation in a given cycle (§20, §21).
Remembered set
a per-region or per-object record of incoming cross-region/ cross-generation pointers (§17, §21).
Root set
the set of pointers known to the collector without tracing (globals plus thread stacks, §8).
Safepoint
a program point where the mutator can safely be paused for GC cooperation (§12, MM7).
SATB (Snapshot-At-The-Beginning)
a barrier style logging the pre-write pointer value to preserve the start-of-mark snapshot (Yuasa 1990, §19).
Semispace
one of a pair of equal-size heap halves used by a copying collector (§16).
Size class
a fixed allocation-size bucket used by the free-list allocator (§14).
Sliding compaction
Lisp-2/break-table compaction that slides objects to new addresses in address order (§15).
Sweep
reclaiming unmarked objects after a mark phase completes (§14).
Tenuring threshold
the survival-count age at which a nursery object is promoted (§17).
Tri-color marking
the white/grey/black reachability-state model underlying incremental and concurrent tracing (§8, §18, MM1).
Type-info descriptor
(gc_typeinfo_t) — host-supplied per-type metadata describing pointer-slot offsets (§11).
Work-stealing deque
a lock-free double-ended queue letting idle mark workers steal work from busy peers (Chase-Lev, §19, ADR-0012).
Write barrier
code on every pointer store maintaining a collector invariant (card-marking, Dijkstra, or SATB, §17–§19).
Yuasa barrier
see SATB.
