In one paragraph

A garbage collector finds the memory a running program no longer needs and takes it back, so the author never frees objects by hand. This design is a C11 library that a virtual machine or compiler runtime links into its own process (§1). It is built as a ladder of collector strategies, from reference counting at the bottom to a concurrent, compacting one at the top, each chosen by one config field behind one unchanged interface (§1, P1, P2). The end goal is a p99 pause of at most 10 ms on a 1 GiB heap under an allocation-heavy test workload (§1, §4). The host process is the operator, watching the telemetry the collector emits (§1, P5).

The problem, concretely

Most objects a program allocates die young (§17.1, MM6). At the design's reference size, a 1 GiB heap of 32-byte objects holds up to 33,554,432 objects that a mark phase must be able to visit in one cycle (§33 item 1). The simplest fix is to count, for each object, how many pointers refer to it, and free it at zero. That fails on a cycle: two objects that point at each other keep each other's count above zero forever, even when nothing else can reach them, so the memory leaks (§35 A1, §13.5 fixture rc/02_simple_cycle.gc).

The next fix is to start from the program's known entry points, follow every pointer, and free what was not reached (tracing). That works for cycles, but a simple tracer stops the program for the whole trace. Its pause is "proportional to live set, no target" (§4), and over many cycles the free memory splinters into unusable gaps (§14.7). Moving the survivors together cures the gaps, but a moved object invalidates every raw pointer to it, so the host must go through a handle table or the collector needs a read barrier (§15.2, P12). Making the collector run alongside the program removes the long pause, but then the program can change the object graph while it is being traced, which needs barriers on every store and a pacer to keep the program from out-allocating the collector (§2, §19.2, P13). Every step down the ladder fixes one pressure and creates the next, which is why the blueprint builds all of them side by side (§2).

How it works, end to end

Follow one object through the boxes of §3's diagram, condensed here:

        | gc_alloc / gc_write_barrier / gc_read_barrier / gc_safepoint / gc_add_root / gc_collect
        v
 Public ABI  include/gc.h   (trust boundary host <-> collector; frozen for v1.x)
        v

        v

        v

        v

  1. The host calls gc_alloc through include/gc.h with a gc_typeinfo_t that says where the object's pointer slots are. The collector never infers layout (§8, §3). include/gc.h is frozen so that swapping collector kinds never changes a host (P1).
  2. The allocator hands back memory. Bump-pointer allocation (src/alloc/bump.c, over an mmap arena in src/alloc/arena.c) is the nursery path. Size-classed free lists (src/alloc/freelist.c) serve the old generation, and oversized objects go to the Large Object Space (src/alloc/los.c) (§12.2, §14.2, §3).
  3. The host registers roots, meaning the pointers the collector knows without tracing, through gc_add_root and gc_thread_attach (src/roots/globals.c, src/roots/registers.c). Stack roots are precise when the host supplies stack maps (src/roots/precise.c) or conservative otherwise (src/roots/conservative.c) (§8, §12.2, §14.2, P3).
  4. When the host stores a pointer, the compiled-in barrier runs: none for Phases 0–4, else exactly one style per collector kind: card marking, Dijkstra, or SATB (§8, P8). Code in src/barriers/ implements them (§17.2, §18.2, §19.2).
  5. The mutator reaches a safepoint (src/core/safepoint.c), a point where it agrees to stop for the collector (§12.2, MM7). The collector dispatches on collector_kind (src/core/gc.c, §1).
  6. The tracer colours objects white, grey and black from the roots. Concurrent kinds use mark workers (src/concurrent/worker.c), a coordinator (src/concurrent/coordinator.c) and a pacer (src/concurrent/pacer.c) (§3, §19.2).
  7. One reclaim back end then runs: sweep (src/tracers/mark_sweep.c), sliding compaction (src/compact/slide.c), Cheney copy with forwarding (src/compact/forwarding.c), or concurrent evacuation of a relocation set (src/compact/relocation_set.c) (§14.2, §15.2, §16.2, §20.2).
  8. The collector emits one gc_event_t to the host's on_event callback (P5, §25). Offline, the Rust harness/ runs the same seeded workload through a reference oracle and diffs live sets (§7, §27).

The core ideas

Reference counting and its cycle hole (§13)

State: a 16-bit count in the object header, saturating at 65,535. On saturation the count moves to a side table keyed by address (§13.2). Every pointer store pays an increment or decrement, so the blueprint targets at most 15 ns per write (§13.4, §13.7). A count that would go below zero is a host bug, so it calls gc_panic("rc underflow") instead of clamping to zero (I3, §13.9).

Cycles are handled by Bacon-Rajan cycle collection. An object whose count was decremented but not to zero is a possible cycle member, so it goes into a bounded roots buffer. When the buffer fills, three passes run inline: mark_grey, scan, collect_white (§13.2). Fixture rc/02_simple_cycle.gc builds a two-node cycle and expects it "reclaimed by cycle collector, not by RC alone" (§13.5). The classic bug is forgetting to re-increment during "scan-black" (§13.6). Phase 1 is single-threaded; a debug assert rejects threads (§13.2).

Tracing with three colours, then sweeping (§8, §14, MM1)

Plain words: start at the roots and mark everything you can reach; whatever is unmarked is garbage. The colour model (tri-color marking) names the three states of an object during that search (§8):

From Event To
white (unvisited) root-scanned, or greyed by a barrier grey (frontier)
grey its slots are scanned by a mark worker black (done); white children become grey
white still white at sweep time reclaimed
black mutator writes a white pointer into it (Dijkstra) black; the child is greyed
any mutator overwrites a pointer during a SATB epoch unchanged; the old value is logged grey

The rule that makes it safe to interrupt the search is that no black object may point to a white one (I1, MM1). The Phase 2 collector marks with an explicit stack, never recursion, and a full stack triggers a deferred re-scan rather than dropping work (I8, §14.2). Sweep then walks the heap in address order, frees unmarked objects to size-classed free lists (16, 24, 32 … 8192 bytes), and clears the mark bit on survivors. Forgetting that clear causes a "double mark" next round (§14.2, §14.6). Address-order walking only works if every object's size is computable from its header (I11).

Moving objects: sliding compaction and Cheney copying (§15, §16, MM2)

Plain words: sweeping leaves gaps, so move the survivors together. Sliding compaction takes three passes (§15.2): (1) compute every object's new address in address order and store it in the header's forwarding slot; (2) rewrite every pointer, in the heap and in roots, to the new address; (3) slide the objects into place in address order, so a destination is never overwritten before it is read. MM2 explains why the passes cannot be fused: computing a permutation and applying it cannot interleave safely (§15.6).

Cheney copying instead splits memory into two equal semispaces and copies only the live objects (§16.1). A three-step trace, using fixture copy/01_multi_root_same_object.gc (§16.5):

  1. Root R1 points at object X. X is not yet forwarded, so copy it to the free pointer in to-space, set its forwarded flag, record the forwarding address, advance the free pointer (§16.2).
  2. Root R2 also points at X. X is already forwarded, so return the existing address; there is one copy and both roots are updated (§16.2, §16.5).
  3. A scan pointer trails the free pointer through to-space, forwarding each copied object's children iteratively until scan catches free (§16.2).

Cost is proportional to the live data, not the heap, but half the heap is unusable at any instant (§16.7). Moving breaks raw pointers, so a moving kind needs a host handle table or a read barrier (P12).

Generations and the card table (§8, §17)

The bet (generational hypothesis): most objects die young (§17.1, MM6). The nursery is a pair of semispaces collected by Cheney copying; an object whose 4-bit age passes the tenuring threshold (default 4) is promoted to the old generation (§17.2). The hazard is an old object pointing at a young one, which a minor collection would otherwise miss. A card table records which 512-byte cards were written (§17.2, ADR-0022). The blueprint's worked example (§8):

  1. Old object A and young object B exist. The mutator runs A.slot = B.
  2. gc_write_barrier stores B, tests gc_is_old(A) && gc_is_young(B), and marks the card holding &A.slot dirty. Store comes first, mark second (I5).
  3. At the next minor collection the collector scans the dirty cards instead of the whole old generation, treats A as an implicit root, copies B if live, and updates A.slot to the forwarding address.
  4. The card is cleared in the minor-GC epilogue, never at entry (I6, §17.6).

Card table size is heap size divided by card size at one byte per card: 2 MiB for 1 GiB (§33 item 2).

Concurrent marking: two barriers and a pacer (§18, §19)

Incremental marking (Phase 6) cuts marking into slices of at most budget_ns via gc_step. The mutator is paused during each slice, so this is not yet concurrent (§18.2, §18.6). Its Dijkstra barrier says: on obj.slot = val, if obj is black then grey val, so no black-to-white edge ever exists (§18.2).

Concurrent marking (Phase 7) runs mark workers beside the mutator, each with a work-stealing deque (ADR-0012, §19.2). Its SATB barrier (snapshot-at-the-beginning) has a fixed order: read the old value, write the new one, log the old one (I10). The log preserves the heap as it stood when marking began. Marking is done only when all queues are empty and all workers idle at the same moment, behind a release-acquire fence (I2, §19.2). A short stop-the-world final remark then reconciles the log (§19.2).

Objects unreachable at end of mark but kept until the next cycle are floating garbage, a knob, not a bug (MM4, I13). The pacer is a feedback controller (MM8): once allocation passes a heap-growth target, the allocating thread does mutator assist, a little marking proportional to the bytes it allocated (§19.2, P13). The blueprint words the outcome for an object un-rooted mid-mark three ways: §19.2 says snapshot-unreachable objects "are collected even if the mutator un-roots them mid-mark", fixture concurrent/01_satb_snapshot.gc expects "still collected (or retained)" (§19.5), and MM4 says the snapshot necessarily retains some garbage until the next cycle.

Concurrent compaction: the Brooks pointer and the read barrier (§20, MM3)

Moving objects while the program runs adds a new danger: a load can land on a half-moved object (§20.1). The mirror-image fix to a write barrier is a read barrier, which protects the mutator's view from relocation (MM3). With Brooks pointers every object has a forwarding slot that normally points at itself, every read goes through it, and relocation copies the object and then flips the slot with a compare-and-swap, never a plain store (§20.2, §20.6, I4). A read that races the swap retries instead of seeing torn state (§20.8). The collector picks the regions with the lowest live ratio first, caps the set to fit the pacing budget, and excludes regions currently being allocated into (§20.2, §20.6). The barrier must be inlined at every load and stay within 5 cycles; only this kind pays for it (M9, §20.4, §20.6, P8).

The trade-offs — where engineers disagree

Implementation language: C11 (ADR-0001)

Chosen: C11, for a deterministic ABI, no hidden runtime and trivial FFI from any host language (§9 ADR-0001, §1). Rejected: C++ (hidden control flow on the barrier path), Rust (unsafe almost everywhere in a moving collector), Go (two competing collectors), Zig (sanitizer support lags) (§1). When the rejected choice is right: "Rust wins when the host itself is Rust-only and FFI cost dominates; C++ wins if the host already forbids C linkage entirely" (§9 ADR-0001). Rust is still used for the test harness (ADR-0002, §1).

Root scanning: precise, with a conservative fallback (ADR-0003)

Chosen: precise scanning from host-supplied stack maps, with a Boehm-style conservative scanner for hosts that cannot supply them (P3, §9 ADR-0003). Rejected: conservative-only and precise-only. When the rejected choice is right: conservative-only, when hosting a legacy C codebase with no compiler cooperation (§9 ADR-0003, §35 A2). The blueprint disagrees with itself on the default: P7 says "default build is conservative-scanning," while P3 and ADR-0003 make precise the default and warn that defaulting to conservative wastes memory (P7, P3, ADR-0003).

Write-barrier style: Dijkstra in Phase 6, SATB in Phase 7 (ADR-0004)

Chosen: Dijkstra incremental-update for the incremental kind and SATB for the concurrent kind, never both live at once. SATB lowers mutator overhead for high-churn work, and Dijkstra is simpler for incremental-only (§9 ADR-0004, P8). Rejected: pure Dijkstra everywhere, or pure SATB everywhere. When the rejected choice is right: pure SATB, when floating-garbage tolerance is generous and mutator overhead must be minimal. Pure Dijkstra, when strict eager reclamation matters more than barrier cost (§9 ADR-0004).

Concurrent-compaction barrier: Brooks pointer, not coloured pointers (ADR-0019)

Chosen: Brooks-pointer indirection, which is simpler to debug and portable across 48-bit and 57-bit virtual address layouts (§9 ADR-0019, §20.2). Rejected: ZGC-style coloured pointers, which keep colour bits in unused high address bits and check them in a load barrier (§20.2). When the rejected choice is right: when register pressure from the extra indirection load dominates and a 64-bit address space with free high bits is guaranteed, which is ZGC's actual regime (§9 ADR-0019).

Card size: 512 bytes (ADR-0022)

Chosen: 512 bytes, which is 8 cache lines, balancing table memory against how precisely a dirty card points at the written object (§9 ADR-0022, §4, MM5). Rejected: 256 bytes and 4 KiB. When the rejected choice is right: 4 KiB page-granularity cards, when the card table's footprint at heaps of 64 GiB or more must be minimised and coarser remembered-set precision is acceptable (§9 ADR-0022, §30).

Roads not taken

Pure reference counting (§35 A1) wins for mostly acyclic graphs that need deterministic, immediate reclamation with no stop-the-world pause at all, such as real-time audio or media pipelines. It is rejected because cycles need a tracing pass anyway (§13, §35 A1).

Fully conservative, non-moving collection (§35 A2) wins when hosting unmodified C/C++ with no compiler cooperation and no tolerance for handle tables or read barriers; Boehm-style collectors work this way. It is rejected as the only strategy because fragmentation accumulates under long-running, size-varied workloads (§35 A2, P3).

A single-generation coloured-pointer collector (§35 A3) wins when a sub-millisecond pause floor matters more than throughput and a 64-bit address space with free high bits is guaranteed. It is rejected for portability, and because the generational split already buys most of the throughput needed (§35 A3, ADR-0019).

Per-actor isolated heaps (§35 A4) win for massively concurrent share-nothing workloads, where each process's pause must be independent of total heap size. They are rejected because the target hosts share one large mutable object graph by design (§35 A4, §1).

The deferred register (§36) holds ten features, among them a Windows port, threaded compaction, coloured-pointer compaction and NUMA-aware placement, each with its un-defer trigger (§36).

What must never be false

  • I1: no black object points directly to a white one during incremental or concurrent marking. Noticed by a debug-build re-scan assert and tricolor_violations (debug only). Recovery is gc_panic.
  • I2: every reachable object is marked before any destructive phase. Noticed by the queue-empty, all-workers-idle handshake (marked_objects).
  • I3: a reference count never underflows. A debug assert; gc_panic("rc underflow").
  • I4: a forwarding-pointer write is atomic with respect to concurrent readers (Phase 8). Noticed by TSan and a debug canary; the cas_retries counter spikes.
  • I5: a card is dirtied only after the store it guards is visible. A conformance fixture replays the race under TSan; watch cards_dirtied.
  • I6: the card table is cleared at the end of a minor collection, never the start. Noticed by the negative fixture 03_torn_barrier.gc; cards_dirtied against expected.
  • I7: the root set is complete before any trace begins. A snapshot hash is compared across the handshake (roots_scanned).
  • I8: mark-stack overflow defers work and never drops it. A high-water-mark counter detects it.
  • I9: a forwarding bit, once set, stays set until its epoch ends. A debug-build epoch-tag assert.
  • I10: SATB log entries hold the pre-write pointer value. A concurrent-mutation fixture checks it; bytes_floating_estimate is the telemetry field.
  • I11: the heap is parsable at every safepoint. A heap-walk fixture compares swept_objects against the expected count; an unparsable heap is gc_panic.
  • I12: max_heap_bytes is a hard ceiling, even transiently during compaction. Noticed through GC_COLLECT_ON_OOM events and bytes_before/bytes_after.
  • I13: floating garbage stays within the pacer bound, default at most 5% of heap. Sampled per cycle in bytes_floating_estimate; the next cycle's slice budget shrinks.
  • I14: every ptr_offsets entry lies inside the object, pointer-aligned. A debug validator at gc_alloc raises gc_panic("bad typeinfo").

What breaks in production

  • FM-1: a live object is silently reclaimed. Cause: a tri-color violation (I1), a missed root (I7), or a sweep before marking finished. Detected by the debug re-scan assert or an oracle diff mismatch. No automatic recovery: restart the process and bisect with --debug-poison replay (§24).
  • FM-2: a dangling pointer after relocation. Cause: a non-CAS forwarding update (I4) or a read barrier that was not inlined. Detected by a TSan report or the header canary. Fatal, so the fix is a CI gate requiring a TSan-clean build (§24, §20.9).
  • FM-4: the card table drops an old-to-young pointer. Cause: mark-then-store ordering (I5) or clearing cards at minor-GC entry (I6). Detected by conformance generational/02_card_table_race.gc under TSan. Fix the ordering and rerun the generational bucket (§24).
  • FM-5: repeated promotion failure. Symptom: the old generation is chronically too small for the promotion rate. Detected by a consecutive-failure counter. The heap resizer grows the heap automatically, and an operator raises max_heap_bytes if it is already at the ceiling (§24, §17.9). It is a sizing signal, not a correctness bug (§34 Q15).
  • FM-7: the SATB log grows without bound. Cause: a mutator that floods the log faster than marking drains it. Detected by a log-size alert. The pacer raises mutator-assist aggressiveness (P13); an operator can lower pause_target_ms_p99 or add workers (§24).
  • FM-8: silent fallback to the wrong collector. Cause: a misconfiguration such as pause_target_ms_p99 = 0 with a concurrent kind. Detected by the gc_new validator, which returns an error code and never substitutes a kind. Fix gc_config_t and restart (§24, §22.9).
  • FM-9: a 24-hour soak leak in concurrent compaction. Cause: a relocation set that included active allocation regions, or a missed forwarding cleanup. Detected by an ASan/MSan soak report; recovery is a restart, and the soak gates the release (§24, §28).
  • FM-10: the C collector and the Rust oracle disagree. This is the general safety net catching a bug no targeted fixture covered. Detected by a differential run over 10,000 randomized graphs. Bisect to the divergent fixture and add it as a named regression (§24, §27).

Threats worth knowing (§23). The host is trusted, so the whole surface is what crosses gc.h (§23). T2, type confusion from a malformed gc_typeinfo_t, is rejected at allocation by the debug validator (I14). T4, a conservative scan retaining garbage because an integer looks like a pointer, is "by design, not a vulnerability" and is tracked by a retention-rate metric (P3). T5, a wrong barrier order or missing fence in the concurrent paths, is caught by TSan in CI and never ships with a report open (ADR-0010). T6, runaway allocation, hits the max_heap_bytes ceiling (I12) and calls a user-supplied callback instead of aborting. T9, a torn read from a miscompiled read barrier, is answered by forced inlining and CAS-only forwarding (I4).

How it compares

  • HotSpot G1 uses uniform regions classified as eden, survivor or old, with no separate semispace nursery, and its pause is "tens of ms (region-tunable)". That suits predictability across a very wide heap-size range. Phase 9 borrows the region idea but keeps the Phase 5 nursery underneath (§32).
  • Shenandoah is the closest ancestor of Phase 8: concurrent Brooks-pointer compaction with SATB and no generational split. It is the right choice when simplicity and not depending on unused high address bits matter more than the last bit of pause time (§32, ADR-0019).
  • ZGC (pre-generational) uses coloured pointers and a load barrier for sub-millisecond typical pauses. The price is a hard dependency on a 64-bit address space with reserved high bits, which this design declines for portability (§32, ADR-0019).
  • Go's runtime GC is non-moving and fully concurrent with a hybrid Dijkstra-plus-Yuasa barrier. It pays no read-barrier or compaction cost and accepts fragmentation risk, which its size-classed allocator bounds well enough for typical Go workloads (§32).
  • BDW GC is non-moving, conservative and stop-the-world, with pauses that grow with heap size. That is right for hosting an unmodified C/C++ codebase where precise roots cannot be retrofitted (§32, §35 A2).

  2. Trace exactly what breaks if the card table is cleared at minor-GC entry instead of epilogue, using the worked example in the Domain Model. (§8, §17, I6) — Hint: §8's worked example and §17.6 name the lost write.

If you only remember three things

A collector is a ladder of compromises, and each rung (counting, tracing, moving, generations, concurrency) buys one property at the price of the next problem, so none is "best" without a workload (§2, MM6). Every concurrent or moving design stands on a barrier that keeps the collector's and the program's views of the heap consistent: write barriers protect the collector from the program, and a read barrier protects the program from relocation (I1, MM3, P12). Pause time is a budget that the pacer defends with mutator assist, and some floating garbage is the price of staying inside it (§4, MM4, P13).

Words used here

  • Mutator: the application code that allocates and changes the heap (§3).
  • Root set: the pointers known without tracing: globals plus thread stacks (§8).
  • Tri-color marking: white means unvisited, grey means frontier, black means done (§8, MM1).
  • Write barrier: code on every pointer store that keeps a collector invariant true (§8).
  • Read barrier: code on every load so the mutator never sees a half-moved object (§20).
  • Safepoint: a point where the mutator agrees to pause for the collector (MM7).
  • Floating garbage: dead objects kept until the next cycle because of the start-of-mark snapshot (§19, I13).
  • Semispace: one of two equal halves of a copying collector's space (§16).
  • Card table: one flag per 512-byte card, saying "something in here was written" (§17).
  • Handle table: a host-owned indirection layer that survives object movement (§15, P12).
  • Mutator assist: marking done by the allocating thread to slow its allocation (§19, P13).
  • Pacer: the feedback controller that bounds floating garbage and pause time (§19, MM8).
