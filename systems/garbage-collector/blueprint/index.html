1. Goal & Scope

Goal. Build a portable, embeddable tracing garbage collector, hostable by a virtual machine or compiled-language runtime, that walks the full historical lineage of GC technique — reference counting, mark-sweep, mark-compact, semispace copying, generational collection with write barriers, incremental tri-color marking, concurrent marking with SATB, and concurrent compaction via a read barrier — ending in a collector that sustains p99 pause ≤ 10 ms on a 1 GiB heap under a synthetic allocation-heavy workload. Each algorithmic stage is a real, switchable, benchmarked collector strategy selected by gc_config_t.collector_kind, not a sketch discarded once the next stage lands.

Phase-0 deliverable (the correctness kernel; §12), as a numbered list of modules/files:

  1. include/gc.h — the public ABI, frozen for the v1.x line.
  2. include/gc_types.h — object header, type-info descriptor, tri-color tag.
  3. src/core/gc.c — lifecycle (gc_new/gc_destroy), dispatch table over collector_kind.
  4. src/alloc/bump.c — single-threaded bump-pointer allocator over an mmap arena.
  5. src/core/safepoint.c — safepoint poll stub (cooperative, no-op collector Phase-0).
  6. src/roots/globals.c + src/roots/registers.c — root registration (gc_add_root, gc_thread_attach), exercised but not yet collected against.
  7. src/main_harness.c — synthetic binary-tree/graph workload driver.
  8. harness/ (Rust) — differential-oracle scaffold, FFI bindings, proptest harness.
  9. conformance/positive/alloc/, conformance/runner.c — the executable Phase-0 spec.

System boundaries.

  • Provides: allocation, root tracking, tracing (mark/sweep/compact/copy in later phases), write/read barriers, safepoint cooperation, structured GC event telemetry.
  • Delegates: thread creation/scheduling (host owns threads; collector only requests safepoint cooperation), stack-map emission for precise roots (host compiler emits them), syscall dispatch beyond mmap/mprotect/madvise, object layout policy beyond the pointer-slot descriptor contract.
  • Does NOT provide: a language runtime, a bytecode interpreter, a JIT, distributed collection across processes (§30), persistent/durable heaps (deferred, §36), or security sandboxing of untrusted host input — the host is a trusted caller (§23).

Non-goals. Not a general-purpose memory allocator for non-GC-managed memory (that is rank-30's Memory Allocator project, reused as the arena substrate beneath src/alloc/); not a language front end; not a real-time/hard-deadline collector (soft p99 targets only, no worst-case pause bound below the operating-system scheduler's own jitter floor).

Deployment model. Statically or dynamically linked library (libgc.a/libgc.so) embedded in a host process; no network listener, no external service; one collector instance (gc_t) per host heap, one heap per process in v1.0 (cross-process sharing is PhaseDeferred("§30")).

Target users/operators. Language-runtime engineers embedding the collector into a VM or compiler backend (this workspace's rank-33 Virtual-Machine and rank-32→33 Compiler projects are the reference hosts); the "operator" at runtime is the host process's own observability pipeline consuming gc_event_t telemetry (§25).

What later phases unlock. Phase 1 unlocks deterministic, low-latency reclamation for acyclic graphs (RC). Phase 2–4 unlock tracing correctness and compaction. Phase 5 unlocks generational throughput. Phase 6–7 unlock bounded and then fully concurrent pause times. Phase 8 unlocks concurrent compaction (no long stop-the-world even for defragmentation). Phase 9 unlocks region-grain pause-time control at multi-GiB heaps. Phase 10 unlocks production hosting: tuning, telemetry, and two real integration examples.

Recommended language: C11. Rationale — deterministic ABI with no hidden runtime (no GC-inside-the-GC problem, no exception unwinding across the barrier hot path, no vtable indirection on the allocation fast path); direct address arithmetic on object headers and forwarding pointers; trivial FFI from any host language (C, C++, Rust, Go, JVM via JNI); stdatomic.h gives portable lock-free primitives for concurrent marking (Phase 7) without a language-runtime scheduler underneath it.

Rejected languages:

  • C++ — richer type system, but exceptions and implicit constructors/destructors make the "no hidden allocation, no hidden control flow on the barrier path" guarantee harder to audit; every barrier call site would need noexcept discipline enforced by convention rather than the language.
  • Rust — memory safety is attractive, but a moving/concurrent collector's core operations (raw pointer forwarding, torn-read-tolerant header bit tricks, conservative stack scanning) are unsafe almost everywhere, forfeiting the borrow checker's benefit where it matters most; still, Rust is the right tool for the harness (a separate, memory-safe process that does not touch the GC's own hot path) — see ADR-0001.
  • Go — cannot host itself: embedding a GC-managed heap inside a language whose runtime already carries its own GC creates two competing collectors and undefined root-set ownership.
  • Zig — comptime and manual allocator control are appealing, but v1.0 toolchain maturity and cross-platform sanitizer support (TSan/MSan) lag C11+Clang; revisit post v1.0 (not deferred formally — a tooling risk, not a scoped feature).

Prerequisites. C11 and stdatomic.h; the C object/memory model (strict aliasing, alignment, storage duration); OS-level memory management (mmap, mprotect, madvise, page faults, signal-safe suspension); happens-before/release-acquire/sequential consistency; cache-line/false-sharing/TLB/NUMA fundamentals; GC-internals-level familiarity with at least one production runtime (HotSpot, Go, V8, or CoreCLR); Rust to the level of unsafe, Pin, MaybeUninit, FFI, and proptest, for the harness only.

Estimated timeline. Phase 0: 1 week. Full system (Phase 0–10): 16–18 weeks of focused engineering (Phase 9 is the sole stretch-weighted phase; §39 gives per-phase durations).

Deferred features (full register at §36): Windows/MSVC port PhaseDeferred("§12.1"); threaded (Jonkers) compaction PhaseDeferred("§15.6"); ZGC-style coloured-pointer compaction PhaseDeferred("§20.2"); NUMA-aware placement PhaseDeferred("§21.7"); compressed 32-bit references PhaseDeferred("§11"); off-heap weak refs/finalizer ordering PhaseDeferred("§11"); persistent-memory heap backend PhaseDeferred("§10"); distributed cross-process collection PhaseDeferred("§30"); external audit sign-off PhaseDeferred("§39"); full DaCapo port PhaseDeferred("§29").

2. Why Build This

  • The cost of correctness is learned, not read. Conservative stack scanning is approximate and retains garbage; precise scanning needs compiler cooperation. Both have irreducible costs that only show up under sustained load, not in a unit test.
  • Every production GC is a negotiated compromise, never a pure algorithm: generational trades old-gen scan cost for young-gen throughput; compacting trades copy cost for cache locality and zero fragmentation; concurrent trades pause time for barrier overhead and floating garbage. Building all of them side by side is the only way to feel the tradeoff surface rather than recite it.
  • Almost every modern runtime's operational character is its GC: HotSpot G1/ Shenandoah/ZGC, Go's runtime, V8 Orinoco, CoreCLR, OCaml multicore, BEAM — throughput, pause profile, warm-up curve, and working-set size are GC properties before they are language properties.
  • Hosting is where the engineering lives. A GC that is elegant in isolation but cannot be embedded by a VM or compiler is a toy; the ABI, the barrier contract, and the safepoint protocol are harder than any single tracing algorithm.
  • The empirical discipline. GCs are tuned against measured workloads, not derived from first principles alone; the harness (gcbench-class synthetic graphs, a DaCapo subset, differential oracle testing) is half the engineering effort, matching how real GC teams work.
  • Sibling-system calibration. This project sits directly above rank-30's Memory Allocator (arena/size-class substrate reused in src/alloc/) and directly beneath the rank-33 Virtual-Machine and Compiler projects (which host it and emit its stack maps and barrier call sites) — building it forces precise API contracts with both neighbors.

What Mastery Looks Like (5–8 competencies, each tied to a phase):

  1. Derive the tri-color invariant from first principles and explain why both Dijkstra incremental-update and Yuasa SATB barriers preserve it differently — Phase 6 (§18).
  2. Explain why every moving collector needs either a handle-indirection layer or a read barrier, and name the concrete failure if neither exists — Phase 3 and Phase 8 (§15, §20).
  3. Compute, from heap size and card size, the exact remembered-set memory overhead of a generational collector, and explain when a per-object remembered set beats a card table — Phase 5 (§17).
  4. Reason about floating garbage as a function of mutator allocation rate and mark-cycle duration, and design a pacer that bounds it — Phase 7 (§19).
  5. Distinguish a load barrier (ZGC coloured pointers) from a Brooks-pointer indirection barrier and state the exact register-pressure/branch-prediction tradeoff between them — Phase 8 (§20).
  6. Explain why conservative stack scanning is unsound in the presence of compaction and what precise stack maps buy back — Phase 0 and Phase 3 (§12, §15).
  7. Design a conformance harness that differentially tests a tracing collector against a reference oracle across 10,000 randomized graphs and explain why this catches bugs unit tests miss — Phase 0 (§12).
  8. Read a real GC's source (Go, HotSpot G1/Shenandoah/ZGC, BDW) and identify which historical paper each subsystem descends from — §5 (Required Reading), applied throughout Phase 1–9.

Mutator — application threads; the only actor that allocates and mutates heap slots; cooperates via safepoint polls and inline barriers, never suspended except at a safepoint. Public ABI — the sole trust and stability boundary; frozen shape across every collector-kind swap (P1, §6). Allocator — per-kind strategy (bump for the semispace nursery, size-classed free-list for old gen, region-grain for Phase 9, LOS for oversized objects). Roots — precise (compiler-supplied stack maps) or conservative (Boehm-style word scan); both feed the same root set contract. Barriers — the concurrency boundary's write side: Dijkstra incremental-update (Phase 6), Yuasa SATB (Phase 7), card-table (Phase 5), and the read barrier (Phase 8) that makes concurrent compaction sound. Tracer — tri-color state machine and the work-stealing mark queues; identical across mark-sweep/compact/copy, only the post-mark action differs. Sweep/Compact/Copy — the three reclamation back ends selected per collector kind; never combined incoherently (Phase boundaries in §9 ADR-0004 lock which pairs exist). Heap layout — the persistence-boundary-free, process-lifetime-only address space; card table and remembered sets scale with heap size (quantified §4, §33). OS substrate — the only external interface; no network, no filesystem beyond optional trace-log output (§25).

6. Design Principles

  1. P1 — One ABI, many collectors. include/gc.h does not change as the implementation walks RC → concurrent-compacting. Tradeoff: the ABI must be conservative enough on day one to support the eventual read barrier. Violating it (leaking a collector-kind-specific type into the ABI) breaks every host integration built against an earlier phase.
  2. P2 — Switchable at build or runtime. gc_config_t.collector_kind selects the algorithm; the harness exercises every kind against the same workloads. Operational implication: a regression in one kind must not silently fall through to another kind's code path (tested by §27's per-kind conformance buckets).
  3. P3 — Precise where it counts, conservative where it must. The reference root scanner is precise for hosts emitting stack maps; a Boehm-style conservative scanner exists for hosts that cannot. Tradeoff: conservative retains more garbage (quantified §33); violating this by defaulting to conservative even when precise is available wastes reclaimable memory silently.
  4. P4 — Hosted, not hosted-on. The collector does not own threads, scheduling, or syscall dispatch; it cooperates through safepoints and barriers. Breaking this (e.g. collector spawning its own mutator-visible threads without host consent) makes embedding impossible in a host with its own thread-pool policy.
  5. P5 — Observable by default. Every collection emits a gc_event_t (timestamps, byte counts, live/dead ratios, worklist stats). Operational implication: no "quiet" collector kind — silence is treated as a monitoring gap, not a feature.
  6. P6 — Reproducible. Seeded allocation (rng_seed), deterministic worklist order under a debug flag, snapshot/replay of GC events. Violating it (nondeterministic worklist order in debug builds) breaks differential testing against the oracle (§27).
  7. P7 — Safety-first defaults. Allocation that may trigger a collection is explicit; pointer interiorness is documented per call; default build is conservative-scanning. Tradeoff: safer defaults cost some throughput versus an all-precise, no-safety-net build.
  8. P8 — No silent leaks of complexity. Read barriers exist only in the concurrent- compacting kind (Phase 8); simpler kinds never pay their cost. Violating it (compiling the read barrier into every kind) regresses P2's throughput for mark-sweep users.
  9. P9 — Portability as a constraint, not a wish. Compiles on Linux x86-64/ARM64, macOS arm64, FreeBSD x86-64. Windows is PhaseDeferred("§12.1"). Violating it by depending on a Linux-only syscall (e.g. userfaultfd) without a portable fallback breaks three of four reference targets.
  10. P10 — Documented contracts. Every barrier, safepoint, and root enrolment is documented in docs/abi.md with exact host obligations. Violating it produces "works on my host" integrations that break on the next one.
  11. P11 — The tri-color invariant is load-bearing, not advisory. Every concurrent or incremental kind must maintain it (weak or strong form, I1); violating it silently drops live objects — the single worst class of GC bug (FM-1, §24).
  12. P12 — Moving collectors need an indirection story. Any kind that relocates objects (compact, copy, concurrent-compact) requires either a host-side handle table (Phase 3) or a read barrier (Phase 8); there is no third option that stays correct under concurrent mutation.
  13. P13 — Pacing over panic. When the mutator outpaces the collector (allocation rate exceeds mark/sweep throughput), the collector throttles the mutator (mutator assist, §19) before it OOMs; an unthrottled allocator racing an under-resourced collector is a design defect, not a workload problem.
  14. P14 — Telemetry precedes tuning. No tuning knob (§25) ships without the gc_event_t field that lets an operator observe its effect; a knob without a metric is unmaintainable (violates P5 by omission).

Debugging methodology. A deterministic simulator (harness/src/model/) runs the Rust reference oracle and the C collector side by side over the same seeded workload (P6/I-table); every invariant above has one corresponding assertion in the simulator, and a debug build (-DGC_DEBUG_INVARIANTS) compiles the same assertions into the C collector so the two can be run identically under CI (§27).

8. Domain Model

Object model. Every heap object is a payload preceded by a gc_header_t (one machine word, §11). The header encodes color (2 bits), age (4 bits), a forwarding flag, and (when not forwarding) a compressed pointer to the object's gc_typeinfo_t. The host supplies gc_typeinfo_t once per type at startup; the collector never infers layout.

Heap model. The heap is partitioned into: a nursery (two semispaces, Phase 4+), an old generation (free-list or region-grain, Phase 2/5/9), a Large Object Space (LOS, for objects ≥ 1/8 region size), and metadata (card table, mark bitmap, remembered sets). A region (Phase 9) generalizes "old generation" into fixed-size (1 MiB) chunks independently classified as free/eden/survivor/old/humongous.

Root model. Roots are globals (registered once via gc_add_root) and per-thread stack roots (registered via gc_thread_attach, scanned per collection). Precise roots come from host-supplied stack maps; conservative roots come from a word-by-word scan of the C stack between two guard addresses, testing each word for "points into a valid object header."

Write-barrier model. A write barrier is code inserted at every pointer-store site. Which barrier fires depends on collector kind: none (Phase 0–4), card-marking (Phase 5, old→young), Dijkstra incremental-update (Phase 6), or SATB (Phase 7). Exactly one barrier style is compiled in per collector kind (P8) — never a superset.

State tables.

Tri-color state transitions (Phase 6+):

From Event To Barrier action
White root-scanned or greyed by barrier Grey pushed to mark queue
Grey slots scanned by mark worker Black children greyed if white
White survives to sweep without being greyed reclaimed (garbage) freed at sweep
Black mutator writes a white pointer into it (Dijkstra) Black (child greyed) gc_write_barrier greys child
any mutator overwrites a pointer during SATB epoch (Yuasa) unchanged old value logged grey before overwrite

Object lifecycle across collector kinds:

Kind Allocate Trace Reclaim Move?
Mark-sweep (§14) free-list mark (DFS/iterative) sweep (free-list rebuild) no
Mark-compact (§15) free-list mark slide (Lisp-2/break-table) yes (in place, 3-pass)

Worked example — minor collection with a card table (Phase 5). Heap has old object A at region 3, young object B in the nursery. Mutator executes A.slot = B (gc_write_barrier(gc, A, &A.slot, B)): the barrier stores B into the slot, tests gc_is_old(A) && gc_is_young(B), and — true — marks the card containing &A.slot dirty (I5). At the next minor collection, the collector scans dirty cards instead of the whole old generation, finds A.slot pointing at B, treats A as an implicit root, and copies B (if live) into the surviving nursery semispace, updating A.slot to the forwarding address. The card is cleared at minor-GC epilogue (I6), never at entry.

Malformed-input example. Host calls gc_alloc(gc, 32, typeinfo) where typeinfo->n_ptr_slots == 3 but typeinfo->ptr_offsets == {0, 8, 40} — offset 40 exceeds size == 32 (violates I14). The debug-mode typeinfo validator (P7) rejects the allocation at the call site with gc_panic("bad typeinfo: offset 40 >= size 32") rather than allowing the tracer to later read garbage as a pointer during mark.

Failure-path example. During concurrent compaction (Phase 8), a mutator thread reads a stale (non-forwarded) pointer to an object mid-relocation because its read barrier was miscompiled (inlining failure, N.6 pitfall §20). Detection: the conformance negative fixture 04_torn_relocation.gc (§20.5) replays this under TSan and the debug canary in the header's unused bits reports a torn read (I4's CAS-retry counter spikes). Recovery: none at runtime — this is a fatal build-correctness bug caught in CI before release, not a production-recoverable condition (FM-3, §24).

Ownership/concurrency/persistence summary: gc_typeinfo_t is host-owned, read-only to the collector, never freed by it. gc_header_t is collector-owned and mutated only under the invariants of §7; concurrent mutation (Phase 7/8) requires atomics (stdatomic.h, ADR-0015). gc_config_t is copied at gc_new() and immutable thereafter — no live tuning of collector_kind mid-process. gc_event_t has no persistence; the host callback is responsible for any durable log. 12.1 Objectives

Stand up the production-bar scaffold (§10) and the smallest working ABI slice: a bump-pointer toy allocator plus root registration, proving the public ABI (gc.h) is real before any tracing algorithm exists (P1, P4).

12.2 Detailed Implementation Steps

  • Write governance files (README, CHANGELOG in Keep-a-Changelog format, CONTRIBUTING, CODE_OF_CONDUCT, SECURITY with a 90-day disclosure window), LICENSES/ split per ADR-0018/ADR-0002.

  • include/gc.h lands with the full v1.0 ABI surface (§11's gc_t/gc_config_t signatures) marked stable — later phases add behavior, never change this header's shape (P1).
  • src/alloc/bump.c implements a single-threaded bump allocator over an mmap-backed arena (src/alloc/arena.c); allocation past capacity returns NULL — no collection triggers yet, this phase builds the allocation fast path only.
  • src/core/safepoint.c lands a no-op-collector-compatible safepoint poll stub so the ABI shape (gc_safepoint) is exercised from Phase 0 onward.
  • src/roots/globals.c + src/roots/registers.c implement gc_add_root/ gc_thread_attach, producing a populated gc_rootset_t dumpable via gc_dump_roots() — exercised even though nothing collects against it yet (I7's handshake contract is established here, enforced starting Phase 2).
  • src/main_harness.c builds a configurable-depth binary-tree workload; harness/ (Rust) stands up FFI bindings (ffi.rs) and the proptest scaffold, with the reference oracle (model/) stubbed to a trivial "never collects" implementation.
  • conformance/positive/alloc/ gets its first two fixtures; conformance/runner.c compiles and executes .gc fixtures against the current collector_kind.

A statically-linked libgc.a exposing the full gc.h ABI, a passing conformance/positive/alloc/ bucket, and examples/01_hello_alloc.c runnable end-to-end.

make build && make test exits 0; examples/01_hello_alloc.c completes 100,000,000 allocations in ≤ 3 seconds on the reference machine (§4); conformance/positive/alloc/ reports 100% Pass in report.json; gc_new/gc_destroy round-trip leaks zero bytes under ASan.

12.6 Pitfalls

  • Do not fold roots into globals — they are distinct invariants (I7) tested separately.
  • Do not let any algorithmic decision leak into the public ABI; the host selects via gc_config.collector_kind only (P1, ADR-0001).
  • Resist landing more than the bump-pointer toy this phase — the point is locking the scaffold, not building a real collector (P2 depends on a stable baseline to diff against).

12.7 Performance Concerns

Bump allocation must stay branch-predictor-friendly: one comparison (capacity check) plus one pointer add, no loop, no function-call overhead on the hot path (inlined in gc.h, P1). Arena reservation (mmap) is lazy-committed — no page faulting until first touch, keeping gc_new under the 5 ms startup budget (§4).

12.8 Edge Cases

Zero-size allocation request; allocation exactly at arena boundary; gc_thread_attach called twice for the same thread; gc_add_root called with a NULL slot pointer; gc_destroy called while a root is still registered (must not crash, must free the rootset table).

12.9 Failure Analysis

If the arena mmap fails (address space exhaustion), gc_new returns NULL rather than crashing; the host is responsible for reporting this upward. No blast radius beyond the failed gc_new call — no partial global state is mutated on failure (constructor atomicity).

12.10 Operational Notes

gc_event_t telemetry is wired but empty this phase (no collections happen); the on_event callback contract is still exercised via a synthetic Phase-0 test event so host integrations can validate their consumer before real events exist.

13. Phase 1 — Reference Counting

13.1 Objectives

Ship a non-cycle-collecting reference-counting kind (GC_KIND_RC), then layer Bacon-Rajan synchronous cycle collection on top — RC is a real production choice (CPython, Swift, Objective-C ARC), not a toy stepping stone.

13.2 Detailed Implementation Steps

  • Reserve 16 bits of gc_header_t.bits for the reference count (saturating at 65,535; on saturation, fall back to a side table keyed by object address, matching Swift's overflow strategy — applied from Bacon, Rajan ECOOP 2001, §5).
  • gc_rc_inc/gc_rc_dec (signatures in gc_internal.h) manipulate the count; Phase 1 is explicitly single-threaded (P7 safety-first default) — a debug-build assert rejects multi-threaded use until Phase 7's atomic RC variant.
  • Maintain a roots buffer: objects whose count was decremented but not to zero (potential cycle members), per Bacon-Rajan's mark_grey/scan/collect_white three-pass algorithm (ADR-0004 territory: this is the one kind with no write barrier at all — the roots buffer substitutes for one).
  • The roots buffer is bounded (gc_config_t-tunable); on fill, a synchronous cycle collection runs inline (I3 governs the underflow check throughout).
  • Host integration: compiler-emitted increment/decrement at every assignment site (the Compiler project, rank 33, emits these call sites at IR level, §22.4).
  • Rust harness: a proptest emits randomized graphs with edge add/remove operations and asserts the collector's live-set matches the reference oracle (P6).

13.3 Deliverable

GC_KIND_RC passing the conformance/positive/rc/ bucket including cycle-reclamation fixtures, plus a microbenchmark of per-pointer-write RC overhead.

13.4 Acceptance Criteria

100% pass on conformance/positive/rc/ (≥12 fixtures); per-write RC overhead ≤15 ns measured on the reference machine (benchmarks/results/phase1_rc.csv); cycle collector reclaims 100% of injected cyclic garbage across 10,000 randomized graphs (I3, oracle-diffed).

13.6 Pitfalls

Naive RC is unsound under concurrency — Phase 1 explicitly rejects multi-threaded use at runtime rather than silently racing (I3). Bacon-Rajan's "scan" phase decrements once per internal pointer; forgetting to re-increment during "scan-black" is the classic bug (applied from Bacon, Rajan ECOOP 2001, §5) — caught by the oracle diff, not by inspection.

13.7 Performance Concerns

RC's per-write cost is paid on every pointer store, unlike a tracing collector's amortized-at-GC-time cost — this is RC's defining tradeoff (ADR-0004's rationale column) and the reason Phase 2+ moves to tracing for throughput-sensitive workloads. Cache effects: the roots buffer should stay cache-resident (default capacity sized to fit in L2) to avoid the cycle-detection pass itself thrashing cache.

13.8 Edge Cases

Self-referential single-node cycle; a finalizer that resurrects an object mid-cycle- collection; RC saturation racing a decrement (single-threaded only, but ordering still matters); a root removed while still holding the last reference (must decrement to zero, not leak).

13.9 Failure Analysis

An RC underflow (I3) is treated as fatal (gc_panic) rather than clamped to zero, because clamping would hide a use-after-free-class bug in the host's increment/decrement emission — the blast radius of silently continuing is worse than a crash (FM-3, §24).

13.10 Operational Notes

gc_event_t gains bytes_freed/marked_objects semantics specific to RC (marked here means "visited during cycle scan"); the roots-buffer high-water mark is exposed for tuning the buffer-fill threshold (§25).

14. Phase 2 — Mark-Sweep

14.1 Objectives

Ship the first tracing collector (GC_KIND_MARK_SWEEP), stop-the-world, establishing the semantic baseline (I1/I2) that every later kind is differentially validated against.

14.2 Detailed Implementation Steps

  • Root scan (precise or conservative, P3) followed by an iterative mark (explicit mark stack, never recursive — avoids C-stack blowup on deep graphs, I8's overflow handler triggers a deferred-mark re-scan pass when the stack is exhausted).
  • src/alloc/freelist.c: size-classed free lists at 16, 24, 32 … 8192 bytes; O(1) allocation from a non-empty class; larger requests route to LOS (src/alloc/los.c, backed directly by mmap); coalescing runs at sweep time (I11's parsability invariant is what makes coalescing safe).
  • Sweep (src/tracers/mark_sweep.c) walks the heap in address order (I11), frees unmarked objects to the free list, clears the mark bit on survivors (a forgotten clear here reproduces as a "double mark" bug next round — N.6).
  • Conservative stack scan (src/roots/conservative.c) treats every stack word as a candidate pointer, testing membership in a valid object header range (Boehm-style, applied from BDW GC, §5); precise scan (src/roots/precise.c) consumes host-supplied stack maps.
  • Eager sweep chosen for Phase 2 (P2/ADR territory: lazy sweep deferred to a stretch optimization, not a blueprint phase) — simplicity over pause-time, since Phase 2 makes no pause-time promise (§4).

14.3 Deliverable

A complete single-threaded mark-sweep collector; gcbench passes with results recorded in benchmarks/results/phase2.json.

14.4 Acceptance Criteria

The Rust oracle agrees with the C collector's live-set computation on 10,000 randomized graphs (100% match, I2); gcbench BinaryTrees depth 18 completes in ≤180 seconds (M2, §29); zero mark-bit-clear regressions across 1,000 consecutive collection cycles in a soak fixture.

Forgetting to clear the mark bit at sweep's end produces a double-mark next round with undefined retention behavior — tested explicitly (fixture 03). Conservative stack scanning needs a guard variable on the caller's frame to find the stack's lower bound; pthread_getattr_np is wrong on macOS (platform-specific pitfall, src/platform/ darwin.c uses pthread_get_stackaddr_np instead).

14.7 Performance Concerns

Free-list fragmentation grows over many cycles without compaction (motivates Phase 3); size-classed allocation trades some internal fragmentation for O(1) allocation time — the classic mark-sweep tradeoff (ADR territory, ties to Phase 3's compaction rationale).

14.8 Edge Cases

An object whose only reference is a conservative false-positive (retained, not a bug — documented behavior of P3); a free-list class that empties mid-sweep and must fall back to a slower class-search; a root removed between mark and sweep (must not cause a use-after-free — resolved by I2's ordering).

14.9 Failure Analysis

An unparsable heap (I11 violated, e.g. a corrupted free-list header) is detected by the conformance heap-walk fixture and is fatal (gc_panic) — sweep cannot safely continue once address-order walking breaks (FM-3, §24).

14.10 Operational Notes

gc_event_t.marked_objects/swept_objects are the primary Phase-2 telemetry fields; docs/algorithms/mark_sweep.md documents the sweep-style choice (eager) for operators tuning pause expectations.

15. Phase 3 — Mark-Compact

15.1 Objectives

Ship the first compacting collector (GC_KIND_MARK_COMPACT), eliminating free-list fragmentation at the cost of moving objects — the first kind requiring P12's indirection story.

15.2 Detailed Implementation Steps

  • Mark phase reuses Phase 2's mark (§14.2) unchanged.
  • Compact (src/compact/slide.c) runs Lisp-2/break-table sliding compaction in three passes: (1) compute new addresses by walking the heap in address order, storing each in the header's forwarding slot; (2) update every pointer slot (heap and roots) via forwarding lookup; (3) slide objects to their new address in address order so a destination is never overwritten before it is read (ordering is the load-bearing correctness fact here, not an implementation detail — ADR-0020).
  • The header's bits word is repurposed: when fwd? is set, the high bits hold the forwarding address instead of the typeinfo pointer (I9); the typeinfo pointer is cached in a side table indexed by old address during the compaction window only.
  • Host contract: the mutator must never hold a raw pointer across a safepoint under this kind — it indirects through a host-owned handle table (P12); this is the price of compaction and is documented in docs/abi.md.

15.3 Deliverable

GC_KIND_MARK_COMPACT behind gc_config.collector_kind; the harness verifies an unchanged live set across compaction on 10,000 randomized graphs.

15.4 Acceptance Criteria

Heap fragmentation drops ≥95% after compaction on the pathological "spaghetti" fixture (M4, §29); live-set parity with the oracle across all 10,000 randomized graphs (100%); zero pointer-update misses detected by a post-compaction full-heap pointer scan.

15.5 Conformance Fixtures

Fixture Purpose Expected Output

mark_compact/02_self_ref.gc object referencing itself forwarding resolves correctly, no infinite loop
mark_compact/03_multi_root_forward.gc same object forwarded via multiple roots all roots updated to the same new address
mark_compact/04_typeinfo_sidetable.gc typeinfo lookup during forwarding window correct typeinfo recovered post-compaction

15.6 Pitfalls

The two-pass ordering is strict: all new addresses must be computed before any pointer is updated — interleaving the passes corrupts the graph (this is the correctness-critical detail ADR-0020 exists to lock down). Threaded (Jonkers) compaction is a rejected stretch alternative — PhaseDeferred("§15.6") — because its pointer-reversal trick is materially harder to debug than the side-table approach (ADR-0020's "when the rejected choice wins" column: memory-constrained embedded hosts only). The handle table is a host concern; do not bake it into the collector (P4).

15.7 Performance Concerns

Three full-heap passes cost more than mark-sweep's two (mark+sweep); this is the throughput-for-locality trade compaction makes (ADR-0020 rationale) — cache locality post-compaction is the payoff, measurable as improved sweep/scan times in later cycles.

15.8 Edge Cases

A humongous object that spans what would be multiple regions in Phase 9 (Phase 3 has no regions yet — LOS objects are simply excluded from sliding); a forwarding chain of length >1 (must not occur by construction — single-pass forwarding, tested by fixture 02); the side table itself running out of capacity mid-compaction (escalates to a major-GC retry with a larger side table).

15.9 Failure Analysis

A pointer-update pass that misses a slot (e.g. a root registered after pass 2 begins, violating I7) leaves a dangling pointer — detected by the post-compaction full-heap pointer scan in debug builds; fatal in release (FM-1, §24).

15.10 Operational Notes

gc_event_t.compacted_objects and a fragmentation-ratio metric (computed before/after) are the operator-facing signals; docs/algorithms/mark_compact.md documents the handle-table host obligation (P12).

16. Phase 4 — Copying (Semispace, Cheney)

16.1 Objectives

Ship the classical Cheney semispace collector (GC_KIND_COPY): two semispaces, live objects copied from-space → to-space, from-space discarded wholesale — O(live), not O(heap), collection cost.

16.2 Detailed Implementation Steps

  • Two semispaces of equal size; allocation is bump-pointer into the active (to-space) semispace (§12's bump allocator is reused verbatim here, P1's "one ABI" paying off).
  • Forwarding (src/compact/forwarding.c): on first visit, copy the object to the current free pointer in to-space, set header.forwarded, record the forwarding address, advance free; on a repeat visit (already in to-space or already forwarded), return the existing forwarding address (named after Cheney 1970, §5, applied here).
  • Cheney's scan pointer trails the free pointer through to-space — objects copied but not yet scanned for their own outgoing pointers are processed iteratively (never recursively, matching Baker 1978's incremental-copying precedent, §5) until scan catches free.
  • Interior pointers are disallowed under GC_KIND_COPY (documented constraint) because forwarding a pointer into the middle of a moved object requires knowing the object's start address, which the naive forwarding table does not track.

16.3 Deliverable

GC_KIND_COPY working end to end; the forwarding slot is exercised including the case where the same pointee is forwarded via multiple roots (single copy, multiple updated pointers).

16.4 Acceptance Criteria

Throughput on gcbench BinaryTrees exceeds Phase 2 mark-sweep by ≥2× (M3, §29); zero duplicate copies detected across 10,000 randomized graphs (each live object copied exactly once, oracle-diffed); to-space never exceeds its reserved semispace size.

16.5 Conformance Fixtures

Fixture Purpose Expected Output
copy/01_multi_root_same_object.gc one object, two roots single copy, both roots updated
copy/02_half_heap_waste.gc measures effective capacity usable heap == semispace size, not full arena
copy/03_interior_pointer_reject.gc (negative) attempted interior pointer rejected at gc_alloc/typeinfo validation
copy/04_deep_chain_iterative.gc very deep object chain completes without C-stack growth (iterative scan)

16.6 Pitfalls

Cheney's copying loop is iterative by construction — writing a recursive variant even for a test defeats the entire point of the algorithm (stack-depth independence) and must be rejected in review. A pointer into the interior of a Cheney-managed object is hard to forward correctly; the constraint is enforced, not merely documented (typeinfo validator, P7).

16.7 Performance Concerns

Half the heap is unusable at any instant — this is the trade Cheney makes for O(live) cost (§4/§33 quantify the effective-capacity impact); the trade earns its place when the surviving fraction of a nursery is small, the common case for short-lived allocations (Appel 1989, §5).

16.8 Edge Cases

An object exactly at the to-space capacity boundary during copying (must trigger promotion-failure-style escalation, foreshadowing Phase 5's promotion failure, §17.5); a root pointing at an already-forwarded object (must resolve to the existing forwarding address, not re-copy); a self-referential object (forwards correctly, single copy).

16.9 Failure Analysis

If to-space fills before all reachable objects are copied (the semispace was undersized), the collector must abort the copy cleanly and escalate rather than overrun to-space's reserved bounds — detected by a bounds check on every forward call, fatal (gc_panic) if triggered (this scenario recurs, resolved properly, in Phase 5's promotion-failure handling).

16.10 Operational Notes

gc_event_t.bytes_before/bytes_after directly report live-set size post-copy; docs/algorithms/copy.md documents the half-heap-waste tradeoff for operators sizing the nursery (§25).

17. Phase 5 — Generational Collection

17.1 Objectives

Ship GC_KIND_GENERATIONAL: young generation via Cheney copying (§16), old generation via free-list mark-sweep/compact (§14/§15), exploiting the generational hypothesis (most objects die young — Lieberman, Hewitt 1983, §5).

17.2 Detailed Implementation Steps

  • Heap shape: [to-space | from-space | old-gen regions... | LOS]; allocation lands in to-space; a minor collection copies live nursery objects to the other semispace, promoting objects whose age (header's 4-bit field) exceeds the tenuring threshold (default 4, optionally adaptive on survival rate as in HotSpot).
  • Old-to-young pointers are the hazard this phase exists to solve: a card table (src/barriers/card_table.c) segments the heap into 512-byte cards (ADR-0022); the write barrier sets the dirty bit for the card containing a modified slot whenever gc_is_old(obj) && gc_is_young(val) (I5's store-then-mark ordering is the correctness-critical detail — reversed order admits a lost-update race, §8's worked example walks this exactly).
  • The card table is cleared only at minor-GC epilogue (I6) — clearing at entry loses concurrent writes made during the collection itself.
  • Per-object remembered sets are the rejected alternative (ADR-0004 territory, see §9's ADR table): faster for sparse old→young patterns, slower for dense ones; card table is the primary implementation, remembered sets deferred to Phase 9's region-grain design (§21.2) where per-region granularity changes the tradeoff.
  • Promotion failure (old gen cannot accommodate a promotion) escalates the current collection to a major collection (mark-sweep/compact over old gen, final copy over nursery); repeated promotion failures signal an undersized heap to the resizer (§22.1).

17.3 Deliverable

GC_KIND_GENERATIONAL end to end; the card-table write barrier benchmarked at <5 cycles in the non-dirtying case on both an Apple M-series and an x86-64 Zen 4 reference machine.

17.4 Acceptance Criteria

gcbench BinaryTrees runs ≥3× faster than Phase 4's pure-copy kind at a 1 GiB heap (M4, §29); write-barrier overhead ≤5 cycles non-dirtying (M5, §4); zero lost old→young pointers across a 24-hour card-table race-replay fixture under TSan.

17.5 Conformance Fixtures

Fixture Purpose Expected Output

generational/02_card_table_race.gc concurrent write during minor GC no lost pointer (I5)
generational/03_promotion_failure.gc old gen exhausted mid-promotion escalates to major GC, no crash
generational/04_finalizer_resurrection.gc old finalizer resurrects young object resurrected object survives next minor GC

17.6 Pitfalls

Card-clear-at-start-not-end is the single most common generational GC bug (I6); the write-barrier's store-then-mark order is the second (I5) — reversing either admits a race where a concurrently-written pointer is silently dropped. Cross-generation references through finalizers deserve explicit attention: an old finalizer may resurrect a young object, requiring the finalizer queue itself to act as a root during the resurrection window (fixture 04).

17.7 Performance Concerns

The card table's own memory footprint scales with heap size (quantified §33: 1 GiB heap / 512 B cards = 2 MiB of card-table metadata); card size (ADR-0022) is chosen to balance this footprint against remembered-set scan precision — a coarser card scans more false-positive old objects per dirty card, a finer card costs more table memory.

17.8 Edge Cases

An object promoted then immediately becomes garbage (must still be collectible by the next major GC, not stuck as permanently retained); a card that straddles two objects where only one is old→young (both objects rescanned, correctness preserved at a minor precision cost); adaptive tenuring threshold oscillation under a bursty allocation pattern (bounded by a hysteresis band in the resizer, §22.1).

17.9 Failure Analysis

A repeated promotion-failure cascade (old gen chronically full) is detected via a counter on consecutive promotion failures; recovery is the heap resizer lifting max_heap_bytes-bounded growth, or — if already at the ceiling — escalating to GC_COLLECT_ON_OOM and the host's OOM callback (FM-5, §24).

17.10 Operational Notes

gc_event_t.bytes_promoted and card-table dirty-fraction are the key generational telemetry; docs/tuning.md documents the tenuring-threshold knob and its interaction with growth_ratio (§25).

18. Phase 6 — Incremental Marking

18.1 Objectives

Ship GC_KIND_INCREMENTAL: break marking into bounded time slices interleaved with mutator execution — this does not eliminate pauses, it caps their length (I1's tri-color invariant becomes load-bearing starting this phase, P11).

18.2 Detailed Implementation Steps

  • Tri-color state (§8's state table): white (unvisited), grey (visited, unscanned slots), black (visited, scanned slots); the tri-color invariant (I1) forbids a black object holding a direct pointer to a white one.
  • Dijkstra incremental-update barrier (src/barriers/write_barrier.c, applied from Dijkstra et al. 1978, §5): on obj.slot = val, if obj is black, grey val — this maintains the strong tri-color invariant (no black→white edge ever exists, even transiently).
  • SATB (Yuasa) is explicitly deferred to Phase 7 (§19) where its different work-distribution profile suits concurrent marking better (ADR-0004) — Phase 6 ships Dijkstra only (P8: no unpaid complexity for a kind that does not need it).
  • gc_step(budget_ns) (signature in gc.h) processes the mark queue until either the queue empties or the time budget expires; the host calls it from the allocator's slow path or a periodic timer (P13's pacing-over-panic principle applies here in its simplest form: bounded slices, not yet full concurrent pacing).
  • Mark queue sizing: the queue must accommodate the largest expected fan-out; runtime expansion on overflow is acceptable but must be exercised in conformance (I8).

18.3 Deliverable

GC_KIND_INCREMENTAL end to end, meeting a 5 ms p99 pause budget on the gcbench LargeAlloc workload at a 256 MiB heap.

18.4 Acceptance Criteria

p99 pause ≤5 ms on gcbench LargeAlloc, 256 MiB heap (M6, §29); write-barrier overhead recorded in benchmarks/results/phase6_barrier.csv; zero tri-color-invariant violations across a 10,000-iteration debug-build stress fixture (I1).

18.5 Conformance Fixtures

Fixture Purpose Expected Output
incremental/01_slice_budget.gc verifies gc_step respects budget_ns no slice exceeds budget + 10% jitter
incremental/02_dijkstra_barrier.gc black object gains white child child greyed immediately (I1)
incremental/03_queue_overflow.gc mark queue exceeds initial capacity expands correctly, no lost work (I8)
incremental/04_pause_p99.gc gcbench LargeAlloc, 256 MiB p99 pause ≤5 ms

18.6 Pitfalls

Incremental marking is not concurrent marking — the mutator is paused during each slice; conflating the two is a common design-review mistake this phase must explicitly guard against (concurrency proper arrives in Phase 7, §19). An undersized mark queue that silently drops overflow work (rather than expanding or deferring) reintroduces I2 violations.

18.7 Performance Concerns

Slice-budget granularity trades pause-cap tightness against total marking overhead (more, smaller slices mean more scheduling overhead per slice); gc_step's call frequency from the allocator slow path must not itself become a throughput bottleneck (amortized against allocation batch size).

18.8 Edge Cases

A slice budget of zero (must process at least one work item to guarantee progress, not spin); a mutator that never calls back into gc_step naturally (host must wire a periodic timer fallback); marking that completes exactly at a slice boundary (must transition cleanly to sweep without an extra empty slice).

18.9 Failure Analysis

A tri-color invariant violation (I1) detected by the debug-build re-scan assert is treated as fatal — it indicates a missing or misordered barrier call site, a build-correctness bug caught in CI (§27), not a runtime-recoverable condition (FM-1, §24).

18.10 Operational Notes

gc_event_t slice-count and per-slice duration histogram are the operator-facing signals for tuning budget_ns; docs/algorithms/incremental.md documents the Dijkstra-only barrier choice for this kind.

19. Phase 7 — Concurrent Marking

19.1 Objectives

Ship GC_KIND_CONCURRENT: the mark phase runs in worker threads fully concurrently with the mutator; the collector pauses the mutator only at root-scan start and final remark — the mutator is never blocked for the bulk of marking (§4's defining property).

19.2 Detailed Implementation Steps

  • SATB write barrier (src/barriers/write_barrier_satb.c, applied from Yuasa 1990, §5): on obj.slot = val, read the old value, store the new value, then log the old value grey if the collector is in GC_PHASE_CONCURRENT_MARK (I10's ordering: read-old, write, log-old — never write-then-read, which would log the wrong value).
  • The SATB log preserves the start-of-mark snapshot: objects unreachable in that snapshot are collected even if the mutator un-roots them mid-mark (this is what "snapshot-at-the-beginning" means operationally).
  • Mark workers (src/concurrent/worker.c): N threads (default min(ncpu, 8), §4), each with a Chase-Lev work-stealing deque (ADR-0012, applied from Herlihy, Shavit ch. 10, §5) so an idle worker steals from a busy peer.
  • The coordinator (src/concurrent/coordinator.c) tracks the global "marking done" condition (I2): all queues empty and all workers idle simultaneously — a release-acquire fence at the handshake (Herlihy, Shavit ch. 3, §5) prevents phantom retention from cross-thread visibility gaps.
  • Pacing (src/concurrent/pacer.c, Go-style, applied from Hudson 2018, §5): the collector sets a heap-growth target; allocation past the target performs "mutator assist" — a small amount of marking proportional to bytes allocated (P13).
  • Final remark: a short stop-the-world phase reconciles the SATB log with the live set, rescans changed roots, and produces the final mark bitmap; budgeted at <5 ms on a 1 GiB heap (§4).
  • Floating garbage (objects unreachable at end-of-mark but retained until next cycle, I13) is measured and reported via gc_event_t.bytes_floating_estimate.

19.3 Deliverable

GC_KIND_CONCURRENT sustaining p99 pause <10 ms on gcbench BinaryTrees + LargeAlloc at a 1 GiB heap; TSan-clean across the synthetic harness.

19.4 Acceptance Criteria

p99 pause ≤10 ms at 1 GiB heap (M7, §29); mutator throughput hit ≤10% vs stop-the-world equivalent (M11, §29); SATB log bounded — a pathological mutator flooding it triggers documented backpressure rather than unbounded growth; zero TSan reports across a 24-hour soak.

19.5 Conformance Fixtures

Fixture Purpose Expected Output
concurrent/01_satb_snapshot.gc object unrooted mid-mark still collected (or retained) per snapshot semantics
concurrent/02_work_stealing.gc uneven fan-out across workers idle workers steal, no worker starves
concurrent/03_mutator_assist.gc allocation-heavy mutator assist throttles allocator, no OOM
concurrent/04_satb_flood.gc (negative) pathological SATB log growth backpressure triggers, bounded memory

19.6 Pitfalls

The SATB barrier must execute its old-value read before the store — reversed order reads a half-modified slot and logs garbage (I10). Workers must agree on the start-of-mark snapshot; cross-thread visibility bugs here manifest as phantom retention and require an explicit release-acquire fence at the handshake, not a plain store. Unsigned wrap in mutator-assist accounting is a documented historical Go bug class (Hudson 2018, §5) — the assist counter uses a signed type with an explicit overflow check.

19.7 Performance Concerns

Work-stealing deque contention grows with worker count past the point where the mark work itself parallelizes well; the default min(ncpu, 8) cap (§4) reflects measured diminishing returns past 8 workers on the reference machines. The SATB log's memory footprint scales with mutation rate during marking, not with heap size — this is the dimension the pacer must bound (I13).

19.8 Edge Cases

A root added after marking starts but before the handshake completes (I7 requires it be captured, not silently dropped); a worker crashing mid-mark (fatal — no partial-mark recovery, FM-1); the SATB log growing during a mutator burst that outpaces the assist throttle (pacer must escalate assist aggressiveness, not merely log a warning).

19.9 Failure Analysis

A cross-thread visibility bug at the marking-done handshake manifests as either premature sweep (live objects reclaimed, I2 violated — catastrophic) or a hung collector (marking-done never detected — a liveness bug, not a safety one); both are caught by the conformance race-replay fixtures under TSan before release, never tolerated in production (FM-1, §24).

19.10 Operational Notes

gc_event_t.worklist_steals, bytes_floating_estimate, and per-worker idle-time are the concurrent-kind telemetry surface; docs/algorithms/concurrent.md documents the SATB backpressure mechanism for operators diagnosing a flooded log.

20. Phase 8 — Concurrent Compaction

20.1 Objectives

Ship GC_KIND_CONCURRENT_COMPACT: compaction runs concurrently with the mutator too, requiring a read barrier so mutator loads never observe a half-relocated object — the second half of P12's indirection story, now without a stop-the-world compaction pause.

20.2 Detailed Implementation Steps

  • Brooks-pointer style (locked, ADR-0019, applied from Flood et al., Shenandoah, MPLR 2016, §5): each object's header carries a forwarding slot that normally self-points; reads dereference through it; relocation copies the object and atomically (CAS, I4) updates the forwarding pointer.
  • ZGC-style coloured pointers (Lidén, Karlsson 2018, §5) are the rejected alternative for this phase: pointer colour bits live in unused high bits of a 64-bit virtual address, and a load barrier checks them; ADR-0019's sixth column names the regime where they win (register-pressure-dominated workloads on a guaranteed 64-bit VA layout) — this project ships Brooks pointers for portability and debuggability instead, revisited as an alternative architecture (§35).
  • Relocation-set selection (src/compact/relocation_set.c): choose regions by lowest live-ratio first (most reclaimed space per unit of copy work); cap the set so a cycle's compaction work fits the pacing budget (P13, shared machinery with Phase 7's pacer).
  • The read barrier is inlined at every load (P8's "no unpaid complexity" is inverted here — this is the one kind that pays for it, by design); failure to inline collapses throughput (N.6).

20.3 Deliverable

GC_KIND_CONCURRENT_COMPACT sustaining p99 pause <10 ms at a 1 GiB heap with no significant fragmentation growth after a 24-hour soak.

20.4 Acceptance Criteria

p99 pause ≤10 ms (M8, §29); read-barrier overhead ≤5 cycles per load on reference architectures (M9, §29); 24-hour soak ends with zero leaks, zero TSan reports, zero MSan reports (M15, §29).

20.5 Conformance Fixtures

Fixture Purpose Expected Output
concurrent_compact/01_brooks_forward.gc read during relocation always resolves to current location (I4)
concurrent_compact/02_relocation_set.gc region selection by live-ratio lowest-occupancy regions chosen first
concurrent_compact/03_cas_forwarding.gc concurrent forwarding-pointer update CAS succeeds or retries bounded (I4)
concurrent_compact/04_torn_relocation.gc (negative) miscompiled/non-inlined read barrier TSan/debug canary detects torn read (§8 failure-path example)

20.6 Pitfalls

The read barrier is hot — failure to inline it into every load collapses throughput (the single most consequential Phase-8 implementation mistake). The forwarding-pointer update must be a CAS, never a plain store, or a torn read produces a dangling pointer (I4). The relocation set must exclude the regions currently being allocated into, or the collector compacts the very memory it is handing out (a self-inflicted race).

20.7 Performance Concerns

The read barrier's per-load cost (§4's ≤5-cycle budget) is the central Phase-8 engineering constraint — every design choice in this phase (Brooks vs coloured pointers, relocation-set cap sizing) is ultimately in service of holding that budget while still making forward compaction progress.

20.8 Edge Cases

A read racing a relocation's CAS (must retry, not read torn state, I4); a relocation set so large it cannot finish within the pacing budget (must be capped, partial progress carried to the next cycle); an object pinned by a conservative root during active relocation (must be excluded from the current relocation set, not corrupted).

20.9 Failure Analysis

A non-inlined or miscompiled read barrier is the phase's signature catastrophic bug (§8's failure-path worked example) — caught in CI by the TSan-instrumented negative fixture, never a production-recoverable condition; a CAS-retry storm (I4's counter spiking) signals contention that should escalate to a smaller relocation set next cycle, not indefinite retrying (FM-2, §24).

20.10 Operational Notes

gc_event_t.cas_retries and per-cycle relocation-set size are the operator-facing signals; docs/algorithms/concurrent.md's Phase-8 section documents the read-barrier inlining requirement as a build-verification checklist item (§28).

21. Phase 9 — Region-Based Collection

21.1 Objectives

Ship GC_KIND_REGION (G1-style, applied from Detlefs et al., ISMM 2004, §5): the heap divides into fixed 1 MiB regions (ADR-0021), each independently classified, giving pause-time control at multi-GiB heaps that a monolithic old generation cannot.

21.2 Detailed Implementation Steps

  • Region states (state table): free (available), eden (nursery allocation), survivor (post-one-minor-GC), old (tenured), humongous (spans multiple regions).
  • Per-region remembered sets (src/barriers/remembered_set.c): each region tracks "regions whose objects point into me," implemented as a fine-grained card-table-of- card-tables — finding roots into a collection-set region without scanning the whole heap (this generalizes Phase 5's single card table to per-region granularity, ADR-0022's tradeoff revisited at region scale).
  • A concurrent refinement thread (src/concurrent/worker.c reused) processes the dirty-card log and updates remembered sets concurrently with the mutator, decoupling remembered-set maintenance from the collection pause itself.
  • Pause-time goal: the host specifies pause_target_ms_p99; the collector chooses a collection set whose evacuation work fits the budget using a cost-estimation model trained on prior cycles (this is the phase where §4's pause budget becomes an explicit input rather than an emergent property).

21.3 Deliverable

GC_KIND_REGION working behind a feature flag; the cost-estimation model documented and benchmarked.

21.4 Acceptance Criteria

Pause-time goal met within ±20% on gcbench workloads (M10, §29); remembered-set memory overhead measured and bounded at an 8 GiB heap (≤15% of live set, M9); zero missed cross-region references across 10,000 randomized graphs with region-crossing edges.

21.6 Pitfalls

Region remembered sets are the dominant memory overhead at large heaps — tested explicitly at 8 GiB (N.4); a naive per-region remembered set without the card-table-of- card-tables refinement scales quadratically with region count and must be rejected in design review.

21.7 Performance Concerns

NUMA-aware region placement (allocating region-local, biasing work-stealing to same-node workers) is PhaseDeferred("§21.7") — the reference target is single-node; multi-node placement is deferred pending a concrete multi-socket host requirement (§36).

21.8 Edge Cases

A humongous object exactly at the region-size threshold (boundary rounding must be deterministic and documented); a collection set whose actual evacuation cost exceeds the cost model's estimate mid-cycle (must degrade gracefully — partial evacuation carried forward, not abandoned); remembered-set refinement falling behind the dirty- card log's growth rate under a write-heavy mutator (refinement thread count scales with backlog, bounded by worker_threads).

21.9 Failure Analysis

A remembered-set refinement backlog that grows unbounded signals either an undersized refinement worker pool or a pathological write pattern; detection is a backlog-depth threshold alert, recovery is scaling refinement workers within the configured cap or, if capped, falling back to a full old-gen remembered-set rebuild (FM-6, §24).

22. Phase 10 — Tuning, Observability & Host Integration

22.1 Objectives

Make the collector shippable: hostable, observed, and tunable by someone other than its author — the phase that turns eleven algorithmic kinds into one operable product.

22.2 Detailed Implementation Steps

  • Heap sizing policy: initial size 16 MiB (§4); growth when post-collection live set exceeds 70% (growth_ratio default 1.5×); shrink when live set is under 30%, to live-set × 1.25× slack, returning pages via madvise(DONTNEED) (P14: every knob here ships with the telemetry field that lets an operator observe its effect).
  • Pause budgeting: the pacer (§19/§21) translates pause_target_ms_p99 into per-cycle work limits; adaptive — a missed budget informs the next cycle's limit downward.
  • Tracing: every collection emits gc_event_t streamed to a user-supplied callback (typical sinks: JSON-Lines file per ADR-0016, OTLP push, or an in-process ring buffer for low-overhead sampling).
  • Hosting examples: examples/03_vm_integration/ drives the workspace's rank-33 Virtual-Machine project through gc_alloc/gc_write_barrier/gc_safepoint with precise stack maps; examples/04_compiler_integration/ shows the Compiler project emitting write-barrier prologues at IR level (P4's "hosted, not hosted-on" made concrete).
  • docs/tuning.md documents all seven tunable knobs (heap size, young-gen size, pause target, growth ratio, region size, worker count, card size) with empirical guidance per workload class, closing the loop opened by P14.

The VM-integration example runs the harness's tree workload with zero manual gc_collect calls; the compiler-integration example generates correct write-barrier prologues verified against the fixture oracle.

22.6 Pitfalls

A tuning knob shipped without its corresponding telemetry field is unmaintainable in production — violates P14 by omission and must be caught in review, not discovered by an operator later. Growth/shrink hysteresis without a slack factor causes thrashing (grow, shrink, grow) under a workload oscillating near the 70%/30% thresholds.

22.7 Performance Concerns

madvise(DONTNEED) returning pages to the OS while a sleeping mutator thread still holds a pointer into the returned range is a real historical GC bug class; the return- to-OS step is enforced only at a safepoint, never asynchronously (ties back to I11's parsability requirement holding across the shrink operation).

22.8 Edge Cases

A host that never calls gc_safepoint frequently enough for shrink to ever trigger (documented as a host obligation, not a collector bug); a workload that oscillates exactly at the growth/shrink threshold (bounded by the 1.25× slack factor, N.6); the on_event callback itself throwing/erroring in a host with exceptions (documented as undefined behavior — the callback contract requires it not to unwind across the ABI boundary).

22.9 Failure Analysis

A host misconfiguration (e.g. pause_target_ms_p99 = 0 combined with a concurrent kind) is detected at gc_new and rejected with a documented error code rather than silently falling back to a stop-the-world kind — configuration errors must be loud, not silently degraded (FM-8, §24).

26. Compatibility & Versioning

Wire compatibility. Not applicable — no network protocol (§4). Storage compatibility. Not applicable — no persistence boundary. ABI stability. gc.h's function signatures are frozen for the v1.x line (P1); an ABI break requires a v2.0 major bump (ADR-0017, SemVer 2.0.0). Schema evolution. gc_typeinfo_t and gc_config_t may gain new optional trailing fields within a minor version (host recompiles against the new header; old hosts using the old header size continue to work via a versioned struct-size field checked at gc_new). API stability. GC_KIND_* enum values never change their integer meaning once shipped; a new kind is always a new, higher enum value. Deprecation policy. A deprecated collector_kind is retained for at least one full major version with a compile-time warning before removal. Rolling-upgrade guarantees. Because there is no cross-process or cross-host state, "rolling upgrade" reduces to "each host process independently picks its own libgc version" — no coordination protocol is needed, unlike a distributed system.

30. Scalability Analysis

Stays constant. Public ABI shape (P1) regardless of heap size; write-barrier cost per store (O(1), §4). Grows. Card-table memory: O(heap_size / card_size) — 1 GiB / 512 B = 2 MiB (§33); remembered-set memory at region granularity: O(regions × cross-region-reference density), the dominant overhead at large heaps (§21.6, tested at 8 GiB); mark-queue memory: O(graph fan-out), bounded by I8's overflow handling. Named bottlenecks in order: (1) read-barrier per-load cost at very high allocation rates (Phase 8) — the tightest per-operation budget in the system (≤5 cycles, M9); (2) remembered-set memory at multi-GiB heaps (Phase 9) — bookkeeping cost outgrows the reclaimed-space benefit past a heap-size-dependent point; (3) work-stealing deque contention past ~8 concurrent workers (§19.7) — the practical ceiling on mark parallelism on current hardware. Horizontal/vertical scaling. Vertical only in v1.0: bigger heap, more worker threads, larger regions — all within one process. Horizontal (sharding the heap across processes) is PhaseDeferred("§30") — cross- process collection requires a shared-memory or message-passing coordination protocol this blueprint does not specify. Coordination overhead. Confined to intra-process handshakes (marking-done, §19; refinement backlog, §21) — no network coordination exists in v1.0. Practical ceiling. ~64 GiB heap on a single host before remembered- set and card-table metadata overhead (§33) becomes the dominant memory cost rather than the live set itself. Levers beyond the ceiling: coarser card/region granularity (ADR-0022's "when the rejected choice wins" — page-granularity cards trade precision for metadata size), or exiting single-process scaling entirely via the deferred distributed-collection feature (§36).

31. Mental Models & First Principles

  1. MM1 — A tri-color mark is a graph-coloring invariant, not a scheduling trick. The insight: white/grey/black is exactly "unvisited/frontier/done" in a BFS/DFS reachability search, and the invariant (no black→white edge, I1) is what makes interrupting that search safe. Predicts: any barrier that fails to preserve the invariant drops live objects, regardless of how clever its scheduling is. Bug class without it: engineers "optimize" a barrier by skipping it under load, not realizing the invariant — not the barrier's frequency — is the safety property. Applied in §18, §19.
  2. MM2 — A moving collector's compaction is a topological sort with side effects. The insight: computing new addresses before updating pointers (§15.2) is exactly "compute the permutation before applying it" — the two-pass split exists because permutation application and permutation computation cannot interleave safely. Predicts: any attempt to fuse the passes for "efficiency" corrupts the graph. Bug class without it: single-pass compaction bugs that only manifest on specific object orderings. Applied in §15.
  3. MM3 — A read barrier is the mirror image of a write barrier. The insight: a write barrier protects the collector's view of the graph from mutator writes; a read barrier protects the mutator's view of the graph from collector relocation (§20). Predicts: any concurrent-moving design needs exactly one of {read barrier, handle indirection} — there is no design that needs neither (P12). Bug class without it: assuming a write-barrier-only concurrent design (Phase 7's kind) can be naively extended to also move objects (it cannot, without §20's read barrier). Applied in §20.
  4. MM4 — Floating garbage is not a bug, it's a knob. The insight: a concurrent collector's "start-of-mark snapshot" (SATB, I10) necessarily retains some garbage until the next cycle — bounding it (I13) is a pacing problem, not a correctness problem. Predicts: chasing floating garbage to zero necessarily costs pause time or throughput elsewhere — there is no free lunch. Bug class without it: engineers treating nonzero floating garbage as always a defect and over-engineering it away at a throughput cost nobody asked for. Applied in §19.
  5. MM5 — The card table is a lossy compression of "which pointers changed." The insight: card granularity (512 B) trades false-positive rescanning (multiple objects per dirty card) for bounded metadata size (§33) — it is a Bloom-filter-shaped tradeoff, not a precise data structure. Predicts: shrinking card size always trades metadata memory for scan precision, in either direction, with no "correct" size independent of workload. Bug class without it: tuning card size to chase a metric without understanding the fundamental tradeoff axis. Applied in §17, §33.
  6. MM6 — Every generational hypothesis is an empirical bet, not a theorem. The insight: "most objects die young" (Lieberman, Hewitt 1983, §5) is a measured property of typical workloads, not a law — a workload that violates it (long-lived-object-heavy) makes generational collection actively worse than a single-generation kind. Predicts: no generational collector is uniformly better; the comparative table (§32) exists because the "best" collector is workload- dependent. Bug class without it: assuming generational is strictly an improvement and never benchmarking against a non-generational baseline for a given workload. Applied in §17, §32.
  7. MM7 — A safepoint is a rendezvous, not an interrupt. The insight: cooperative polling (ADR-0006) means the mutator agrees to stop at specific points, unlike an async signal-based interrupt — this is what makes precise stack-map scanning possible at all (the compiler knows the exact live-register state at a poll point). Predicts: a host that cannot guarantee poll-site density (e.g. a tight native loop with no GC-visible call) needs either a trap-page fallback or conservative scanning. Bug class without it: assuming any thread can be "GC-paused" at an arbitrary instruction, which breaks precise root scanning. Applied in §12, §22.
  8. MM8 — Pacing is control theory, not a fixed threshold. The insight: the mutator-assist pacer (§19, applied from Hudson 2018) is a feedback controller — allocation rate is the disturbance, assist strength is the control input, floating garbage/pause time are the outputs being bounded. Predicts: a fixed (non-adaptive) threshold pacer either over-throttles common-case workloads or under-throttles bursty ones — only a feedback design handles both. Bug class without it: hand-tuned static pacing constants that regress the moment workload shape shifts. Applied in §19, §22.

HotSpot G1 trades a separate young-generation semispace for uniform regions classified by role (eden/survivor/old) — it wins when pause-time predictability across a very wide heap-size range matters more than the raw throughput a dedicated bump-allocated nursery gives (this blueprint's Phase 9 borrows G1's region idea but keeps Phase 5's semispace nursery underneath it, a hybrid this blueprint chose over G1's fully uniform regions).

ZGC (pre-generational design) wins on the tightest pause-time floor of any system in this table (sub-millisecond) by using coloured pointers and a load barrier instead of an extra memory indirection — the cost is a hard dependency on a 64-bit virtual address space with reserved high bits, a constraint this blueprint's Phase 8 explicitly avoids taking (ADR-0019's rejected-alternative column) in favor of portability.

Go's runtime GC wins by never moving objects at all in the collector's hot path — non-moving concurrent mark-sweep with a hybrid write barrier avoids every read-barrier and compaction cost this blueprint pays in Phase 8, at the price of permanent fragmentation risk that Go accepts because its allocator's size-classing bounds it well enough for typical Go workloads.

BDW GC wins purely on integration simplicity: no compiler cooperation, no stack maps, conservative scanning throughout — the right choice for hosting an existing, unmodified C/C++ codebase where this blueprint's precise-root machinery (§12, P3) cannot be retrofitted at all.

33. Back-of-Envelope Capacity Model

All numbers chained from §4's System Constraints table; average object size assumed 32 bytes (consistent with the domain-model worked example, §8).

  1. Max live objects at reference heap. max_heap_bytes / avg_object_size = 1,073,741,824 B / 32 B = 33,554,432 objects (~33.5M) — the upper bound the mark phase must be able to visit within a single cycle.
  2. Card-table metadata size. max_heap_bytes / card_size_bytes × 1 byte/card = 1,073,741,824 / 512 = 2,097,152 bytes (2 MiB) — matches ADR-0022's stated rationale for choosing 512 B over a coarser size.
  3. Region count at reference heap. max_heap_bytes / region_size_bytes = 1,073,741,824 / 1,048,576 = 1,024 regions — the granularity Phase 9's collection-set selection operates over.
  4. Nursery semispace capacity in objects. (young_gen_bytes / 2) / avg_object_size = (67,108,864 / 2) / 32 = 1,048,576 objects per semispace fill before a minor collection is forced.
  5. Peak bump-allocation byte rate. M1 target × avg_object_size = 400,000,000 × 32 B = 12.8 GB/s theoretical peak byte-touch rate on the allocation fast path — the number the arena's page-fault behavior must sustain without becoming the bottleneck.
  6. Time to fill one nursery semispace at peak rate. semispace_bytes / peak_byte_rate = 33,554,432 B / 12,800,000,000 B/s ≈ 2.6 ms — the theoretical minimum minor-GC interval under sustained peak allocation, bounding how often the write barrier and root-scan machinery must be able to run.
  7. Worst-case SATB log growth rate (unthrottled). M1 target × 8 bytes/log-entry = 400,000,000 × 8 B = 3.2 GB/s — the rate the pacer (§19, I13) must be able to throttle against; this is why P13 (pacing over panic) is a hard design principle, not an optimization.
  8. Remembered-set worst-case bound at 8 GiB heap. regions = 8,589,934,592 / 1,048,576 = 8,192 regions; a region-to-region cross-reference bitmap is regions² / 8 bits = 8,192² / 8 = 8,388,608 bytes (8 MiB) worst case — well under the M9 target of ≤15% of an 8 GiB live set (≤1.2 GiB budget), confirming the region design's remembered-set overhead is bounded in the regime this blueprint targets.
  9. Read-barrier absolute time budget. M9 target (≤5 cycles) / reference clock (3.5 GHz) ≈ 1.43 ns per load — the number every Phase 8 read-barrier implementation decision is ultimately measured against.
  10. Arena mmap call count at startup. max_heap_bytes / typical_arena_chunk (128 MiB) = 1,073,741,824 / 134,217,728 = 8 calls, comfortably inside the ≤16 FD budget (§4).
  11. Mark-worker worklist memory ceiling. worker_threads × deque_capacity × pointer_size = 8 × 65,536 × 8 B = 4,194,304 bytes (4 MiB) — the memory budget the Chase-Lev deques (§19, ADR-0012) must fit within across all workers.
  12. Startup budget check. gc_new's mmap reservation is a single O(1) syscall regardless of max_heap_bytes (no page faulting yet, §12.7) — confirms the ≤5 ms startup target (§4) holds independent of heap size, unlike every other number above which scales with it.

35. Alternative Architectures (Roads Not Taken)

A1 — Pure reference counting as the primary strategy (no tracing at all).

[obj A: rc=2] --> [obj B: rc=1] --> [obj C: rc=1]
      ^                                   |
      +---- cycle: C --> A (rc=1) <-------+
   (cycle unreachable from roots, RC alone never reclaims it)

Regime where it wins: workloads with mostly-acyclic object graphs and a hard requirement for deterministic, immediate reclamation (no stop-the-world pause of any kind, ever) — e.g. real-time audio/media pipelines. Real system: CPython (pre-3.x cycle detector) and Swift ARC, both RC-primary. Rejected here because acyclic-only RC cannot reclaim cycles without a periodic tracing pass (Bacon-Rajan, §13) — at that point the design has re-introduced tracing anyway, just as a bolt-on rather than the primary strategy this blueprint's Phase 2+ builds deliberately.

A2 — Fully conservative, non-moving collection as the sole strategy (no compaction, ever).

[free-list class 32B] -> [obj][obj][free][obj] -> never moved, never compacted

Regime where it wins: hosting arbitrary, unmodified C/C++ code with zero compiler cooperation and no tolerance for the handle-indirection or read-barrier machinery that moving collectors require. Real system: BDW GC (bdwgc), used inside numerous language runtimes precisely because it needs no cooperation. Rejected as this blueprint's sole strategy because permanent non-moving allocation accumulates fragmentation that no amount of free-list tuning fully avoids under long-running, size-varied workloads — this blueprint keeps conservative scanning as a fallback (P3) but not as the only reclamation strategy.

A3 — Single-generation, coloured-pointer concurrent collector (ZGC pre-generational style, no young/old split at all).

64-bit pointer: [unused hi bits: color] [47-bit address]
load barrier checks color bits on every read, remaps/relocates lazily

Regime where it wins: workloads where the sub-millisecond pause-time floor matters more than raw throughput and a guaranteed 64-bit VA space with free high bits is available — very large heaps where even a generational young-gen pause is unacceptable. Real system: ZGC prior to its generational mode (JDK 15–20). Rejected here (ADR-0019) in favor of Brooks pointers for portability across VA-space layouts and because a generational split (Phase 5) already buys most of the throughput this blueprint needs without ZGC's specific hardware/OS assumptions.

A4 — Per-actor isolated heaps, no shared heap at all (BEAM-style).

[Process P1 heap] [Process P2 heap] [Process P3 heap] ...
   independent GC        independent GC        independent GC
   msg copy across  <-- no shared pointers -->  msg copy across

Regime where it wins: massively concurrent, share-nothing workloads where per-process pause times must be independent of total system heap size — telecom-style soft- real-time systems. Real system: Erlang/BEAM, where each process has its own small heap and collections are per-process, never system-wide. Rejected here because this blueprint's target hosts (a VM/compiler runtime, §1) share one large mutable object graph by design — adopting per-actor isolation would require redesigning the host's own memory model, out of scope for a general-purpose embeddable collector.

37. Glossary

  • Allocator — the subsystem handing out heap memory to the mutator (bump, free-list, or region-grain, per collector kind).
  • Arena — an mmap-backed contiguous address range the allocator carves objects from.
  • Bacon-Rajan cycle collector — a synchronous algorithm that reclaims reference- counted cycles RC alone cannot (§13).
  • Bump-pointer allocation — allocation by incrementing a free pointer; O(1), no free-list search.
  • Card table — a side table marking which fixed-size heap regions ("cards") were written since the last scan (§17).
  • Cheney's algorithm — an iterative semispace copying-collection algorithm using a scan/free pointer pair (§16).
  • Collector kind — the selected algorithm (gc_config_t.collector_kind); switchable without ABI change (P1).
  • Compaction — relocating live objects to eliminate fragmentation (§15).
  • Concurrent marking — tracing performed on worker threads while the mutator continues running (§19).
  • Conservative scanning — treating ambiguous stack words as candidate pointers without compiler cooperation (§12, §14).
  • Deferred Features Register — the table (§36) tracking every out-of-scope feature and its un-defer trigger.
  • Dijkstra (incremental-update) barrier — a write barrier greying a black object's newly-written white child, preserving the strong tri-color invariant (§18).
  • Fixture (conformance) — a named .gc test program with an expected live-set outcome (§27).
  • Floating garbage — objects unreachable at end-of-mark but retained until the next cycle (§19, I13).
  • Forwarding pointer — the relocated address of an object stored in its old header during compaction/copying (§15, §16).
  • Free list — a per-size-class linked list of reusable heap chunks (§14).
  • Generational hypothesis — the empirical claim that most objects die young (Lieberman, Hewitt 1983, §5).
  • Handle table — host-owned indirection layer letting the mutator survive object movement without holding raw pointers across a safepoint (§15, P12).
  • Handshake — a protocol synchronizing mutator and collector threads at a safepoint (§19).
  • Heap — the managed address space containing all GC-tracked objects (§8).
  • Humongous object — an object exceeding the region-size threshold, spanning multiple regions (§21).
  • Incremental marking — tracing broken into bounded time slices (§18).
  • Invariant — a property the collector must never violate (tri-color, RC non-negativity, etc., §7).
  • Large Object Space (LOS) — a dedicated allocation area for objects too big for size-classed free lists (§14).
  • Live set — the set of objects reachable from roots at a given instant.
  • Mark bit / mark bitmap — the per-object (or bitmap-encoded) flag recording reachability during tracing.
  • Mark queue / mark stack — the worklist of grey objects awaiting slot scanning (§14, §19).
  • Mutator — the application code allocating and mutating the heap (§3).
  • Mutator assist — pacer-triggered marking work performed by the allocating thread itself to throttle allocation rate (§19, P13).
  • Nursery — the young generation, typically a semispace pair (§17).
  • Object header — the fixed metadata word preceding an object's payload (§11).
  • Old generation — the tenured portion of the heap holding promoted, longer-lived objects (§17).
  • Pacer — the feedback controller bounding floating garbage and pause time via mutator assist (§19, MM8).
  • Precise scanning — root scanning using compiler-supplied stack maps, exact rather than conservative (§12, P3).
  • Promotion — moving a surviving nursery object into the old generation (§17).
  • Read barrier — code on every load ensuring the mutator never observes a half-relocated object (§20).
  • Reference counting (RC) — reclamation by tracking per-object incoming-pointer counts (§13).
  • Region — a fixed-size heap chunk independently classified (free/eden/survivor/ old/humongous) in the region-based collector (§21).
  • Relocation set — the subset of regions chosen for evacuation in a given cycle (§20, §21).
  • Remembered set — a per-region or per-object record of incoming cross-region/ cross-generation pointers (§17, §21).
  • Root set — the set of pointers known to the collector without tracing (globals plus thread stacks, §8).
  • Safepoint — a program point where the mutator can safely be paused for GC cooperation (§12, MM7).
  • SATB (Snapshot-At-The-Beginning) — a barrier style logging the pre-write pointer value to preserve the start-of-mark snapshot (Yuasa 1990, §19).
  • Semispace — one of a pair of equal-size heap halves used by a copying collector (§16).
  • Size class — a fixed allocation-size bucket used by the free-list allocator (§14).
  • Sliding compaction — Lisp-2/break-table compaction that slides objects to new addresses in address order (§15).
  • Sweep — reclaiming unmarked objects after a mark phase completes (§14).
  • Tenuring threshold — the survival-count age at which a nursery object is promoted (§17).
  • Tri-color marking — the white/grey/black reachability-state model underlying incremental and concurrent tracing (§8, §18, MM1).
  • Type-info descriptor (gc_typeinfo_t) — host-supplied per-type metadata describing pointer-slot offsets (§11).
  • Work-stealing deque — a lock-free double-ended queue letting idle mark workers steal work from busy peers (Chase-Lev, §19, ADR-0012).
  • Write barrier — code on every pointer store maintaining a collector invariant (card-marking, Dijkstra, or SATB, §17–§19).
  • Yuasa barrier — see SATB.
