34. Mental Models & First Principles

Eight compressed models that reorganize how you think about data lineage. Each names what it predicts, the bug class that arises when you build without it, and the section that depends on it most.

MM1 — Lineage is a DAG, not a log. The compressed insight: provenance is structured (a directed acyclic derivation graph), not a flat sequence of events. A log tells you what happened; the DAG tells you what depends on what — those are fundamentally different query shapes. A log supports "what ran?" — the DAG supports "what is affected if X changes?" and "what produced Y?" What it predicts: transitive closure (impact/root-cause) is a graph traversal, not a log scan. Column-level edges are graph edges, not log fields. Time-travel is a snapshot of the DAG at a (valid, tx) cut, not a log replay. Bug class without it: building a flat event store and trying to answer closure queries with correlated log scans — O(n²) and wrong. Every lineage "query" degrades into a full-table join. Resolving section: §8.3 (the lineage graph), §16 (closure queries), §33 (scalability — why bounded traversal is the scaling lever, not scan optimization).

MM2 — Capture fidelity is the binding constraint, not query speed. The compressed insight: the system is capture-fidelity-bound (§2.7). You can build the fastest graph traversal engine in the world; if a column edge is missing, the root-cause answer is silently wrong. Query speed is a second-order concern. What it predicts: every design decision where capture correctness and query performance trade off must resolve in favor of capture (principle 7). The recall=1.0 contract (I9) is not negotiable even under parser performance pressure. Bug class without it: optimizing the SQL parser for speed by dropping "rare" predicate-column dependencies — results in recall < 1.0, corrupted root-cause, and no observable symptom until an incident. Resolving section: §2.7, §4.3, §15 (Phase 3), §6 (principle 7), §7 (I9).

MM3 — Idempotency is a graph-correctness property, not a network property. The compressed insight: most engineers think of idempotency as "retries are safe at the network layer." In a lineage graph, idempotency is a graph-correctness property: a re-delivered event must produce exactly the same edge set in the graph — not an extra copy. Duplicate edges distort every closure, impact analysis, and root-cause ranking that follows. What it predicts: content-addressed node ids (I5) and event-level dedup keys (I7) are both required — one collapses duplicate nodes, the other collapses duplicate edges from the same run. Neither alone is sufficient. Bug class without it: a network partition causes a producer to retry 3×; the graph now has 3 copies of every edge from that run; impact blast radius is 3× inflated; root-cause ranking is wrong. Resolving section: §8.13 (idempotency + content-addressing), §14 (Phase 2), §7 (I5/I7).

MM4 — Time is two-dimensional; conflating the axes is an audit bug. The compressed insight: valid-time ("when was this lineage true in the world?") and transaction-time ("when did we learn it?") are independent axes. "Lineage as of 2025-01-01" is ambiguous without specifying which axis. GDPR audit asks "what data flowed into report R as of the breach date?" — that is a tx-time query ("what did we know then?"), not a valid-time query. What it predicts: every time-travel query must state which axis or both (§8.12). A supersede/correction appends at a new tx-time without altering the old valid-time record — the audit sees the mistake and the fix, both correctly. Bug class without it: a single-axis temporal store that conflates valid-time and tx-time produces audit answers that leak future-known facts (a query at tx=T1 returns an edge recorded at tx=T2>T1) — an audit admissibility failure. Resolving section: §8.12 (bitemporal semantics), §18 (Phase 6), §6 (principle 6), §7 (I13).

MM5 — Conservative column lineage: false negatives are invisible, false positives are visible. The compressed insight: a missed column dependency (false negative) silently corrupts every downstream root-cause and impact analysis — the blast radius is falsely narrowed and the wrong column is exonerated. An extra column dependency (false positive) merely widens the blast radius — the operator sees more candidates, some spurious, but the real cause is still present. What it predicts: the corpus acceptance test must enforce recall = 1.0 as a hard gate (I9); precision ≥ 0.85 is best-effort. Any "optimization" that drops a dependency is a correctness regression, not a performance win (principle 7). Bug class without it: a parser that drops GROUP BY columns from dependencies (common mistake) — sales_daily.region has no upstream; a region-dimension change is invisible to impact analysis. Resolving section: §4.3, §8.5, §15 (Phase 3), §7 (I9).

MM6 — The graph engine is borrowed; the semantic layer is owned. The compressed insight: #84 Graph DB is a dependency for node/edge storage and adjacency traversal primitives. This system owns the semantic layer on top: PROV-DM relations, bitemporal edge annotations, cycle detection, snapshot reads, and the lineage query semantics. The two must never bleed into each other. What it predicts: all #84-specific code lives in exactly one module (graph::store_84). If #84's API changes, exactly one module needs updating. Every higher crate speaks PROV semantics, never #84 primitives. Bug class without it: a crate that imports #84's node type directly and scatters #84 API calls — when #84 upgrades its node representation, the entire codebase breaks, not a single adapter. Resolving section: §3.2 (graph box narrative), §9 (ADR-4/9), §13 (Phase 1), §6 (principle 9).

MM7 — Merkle-chaining is not optional decoration; unverifiable provenance is inadmissible. The compressed insight: for compliance use cases (GDPR, SOX, audit), a lineage record that cannot be proven untampered is legally inadmissible. Appending a Merkle chain to every event is cheap (one hash per event); omitting it makes the entire history untrustworthy for audit. "We think the lineage is correct" is not a compliance answer. What it predicts: the integrity layer (P7) must be wired into the ingest path from the start, not bolted on later. The verify operation (≥1M events/s, §4) must be cheap enough that auditors run it as a matter of routine. Forensics (binary search over the chain) must locate a tampered entry precisely. Bug class without it: a lineage store that logs events to a plain file — an attacker (or a bug, or an ops mistake) edits entry 7 of 10,000; there is no way to detect it; the audit answer for that entry is untrustworthy. Resolving section: §19 (Phase 7), §6 (principle 10), §7 (I10), §26 (threat model).

MM8 — Bounded traversal is a correctness property, not a performance trade-off. The compressed insight: bounding closure queries (max hops, max results, deadline) is not a performance optimization — it is a correctness invariant for a production system. An unbounded closure on a hub node (e.g., a central users table) is not "slow" — it is a server hang that blocks all other queries. The bound, with a truncated flag on partial results, is the correct answer: honest about incompleteness, always available. What it predicts: the bounds (I8) are enforced unconditionally, not configurable to "unlimited." A caller who needs deeper traversal makes multiple bounded calls or narrows the starting set. Every result envelope carries truncated: bool so the caller knows. Bug class without it: a closure API with a default max_hops=∞ that works fine on test data (small graphs) and hangs the production server the first time an operator runs impact("users") on the 10M-node production graph. Resolving section: §4.2, §8.7, §16 (Phase 4), §6 (principle 8), §7 (I8).

Required reading (§5)

5.1 Books

  • Moreau & Groth, Provenance: An Introduction to PROV (2013) — the definitive PROV-DM/PROV-O treatment: entities/activities/agents, the relation algebra, bundles. The data model spec for prov-core. (applies: §8.1, Phase 0)
  • Snodgrass, Developing Time-Oriented Database Applications in SQL (2000) — bitemporal modeling: valid-time vs transaction-time, temporal joins, snapshot semantics. The basis for the temporal store. (applies: §8.12, Phase 6)
  • Aho, Lam, Sethi, Ullman, Compilers (Dragon, 2e) — ch.2–6 (lexing, parsing, syntax-directed translation), and scope/symbol-table resolution. The SQL parser + column-binding. (applies: §8.5, Phase 3)
  • Garcia-Molina, Ullman, Widom, Database Systems: The Complete Book — query plans / relational algebra (the logical plan we parse to), MVCC/snapshot isolation intuition. (applies: §3.5, §8.3, Phase 1)
  • Cormen et al., Introduction to Algorithms (CLRS) — graph traversal, transitive closure, topological sort, cycle detection (DFS back-edges). The query engine. (applies: §8.7, Phase 4)
  • Kleppmann, Designing Data-Intensive Applications — event sourcing, idempotency, change data capture, derived/materialized state. The capture + ingestion model. (applies: §8.13, Phase 2)
  • Anderson, Security Engineering (3e) — tamper-evident logging, hash chains, audit. The integrity layer. (applies: §26, Phase 7)

5.2 Papers

  • Moreau et al., "PROV-DM: The PROV Data Model" (W3C Recommendation, 2013) — the normative model: types + relations + constraints. The contract prov-core implements. (applies: §8.1, Phase 0)
  • Cheney, Chiticariu, Tan, "Provenance in Databases: Why, How, and Where" (FnTDB, 2009) — the canonical taxonomy of provenance kinds (why/how/where). Frames what column lineage must capture. (applies: §8.5, Phase 3)
  • Green, Karvounarakis, Tannen, "Provenance Semirings" (PODS 2007) — algebraic foundations of how-provenance through relational operators. Informs conservative column derivation. (applies: §4.3, Phase 3)
  • Cui, Widom, Wiener, "Tracing the Lineage of View Data in a Warehousing Environment" (TODS 2000) — lineage of derived/aggregated views; the root-cause-of-a-value problem. Directly relevant to Phase 5. (applies: §8.14, Phase 5)
  • Halevy et al., "Goods: Organizing Google's Datasets" (SIGMOD 2016) — dataset-scale provenance/metadata at Google; capture from logs/runtime, not annotations. The capture philosophy. (applies: §3.2, Phase 2/8)
  • OpenLineage spec + "OpenLineage: An Open Standard for Lineage Metadata" (project docs/whitepaper) — the run/job/dataset event model + facets. The ingest contract. (applies: §8.8, Phase 2)
  • Carata et al., "A Primer on Provenance" (CACM 2014) — provenance across systems (files, workflows, OS); the breadth of capture mechanisms. (applies: §8.4, Phase 8)
  • Muniswamy-Reddy et al., "Provenance-Aware Storage Systems" (USENIX ATC 2006) — capturing provenance at the storage/runtime layer; the instrumentation-hook approach. (applies: §8.4, Phase 8)
  • Interlandi et al., "Titian: Data Provenance Support in Spark" (VLDB 2015) — fine-grained (row/column) lineage in a dataflow engine; the column-extraction precedent. (applies: §8.5, Phase 3)
  • Lamport, "Time, Clocks, and the Ordering of Events" (CACM 1978) + vector clocks (#95) — ordering events from many producers; causality when timestamps disagree. (applies: §8.10, Phase 2)
  • Merkle, "A Digital Signature Based on a Conventional Encryption Function" (CRYPTO 1987) — hash trees; the tamper-evidence primitive (#71). (applies: §19, Phase 7)

5.3 Reference Implementations

  • OpenLineage / Marquez — the event spec + a reference lineage store/API. Study; do not copy. Lesson: the run/job/dataset event model, facets, the REST surface. Pitfall: Marquez's relational (Postgres) backing differs from our graph-on-#84 model. (applies: §8.8, Phase 2)
  • Apache Atlas — type system, entity/relationship model, lineage propagation, audit. Lesson: a rich metadata-type model + lineage edges. Pitfall: JVM/HBase-heavy; very broad governance scope we deliberately exclude. (applies: §8.1, Phase 0)
  • DataHub (LinkedIn) — metadata graph + lineage + column-level lineage + search. Lesson: column-level lineage UX + the graph-index split + search. Pitfall: huge surface (we take lineage only). (applies: §8.5, §21, Phase 3/9)
  • Egeria — open metadata + governance, PROV-aligned. Lesson: standards-based metadata interchange. Pitfall: enterprise-integration scope beyond ours. (applies: §6, Phase 0)
  • sqlglot / Apache Calcite (parser + lineage) — SQL parsing + (sqlglot) column-level lineage extraction. Lesson: the column-derivation algorithm over a parsed plan. Pitfall: full-dialect ambition; we ship a subset. (applies: §8.5, Phase 3)
  • dbt (column-level lineage via dbt-core + artifacts) — lineage from a transformation DAG + compiled SQL. Lesson: model-graph + compiled-SQL provenance. Pitfall: dbt-specific; we ingest the generic OL event it emits. (applies: §8.4, Phase 2/8)

Glossary (§40) · 39 terms · site-wide glossary

Activity (PROV)
something that acts on/produces entities over time; here, a job run.
Agent (PROV)
something responsible for an activity; a person, service, or pipeline.
Append-only
facts are added, never mutated/deleted in place (GC reclaims out-of-window history only).
Bitemporal
modeling two time axes: valid-time + transaction-time (§8.12, §18).
Blast radius
the downstream set affected by a change (impact analysis result).
Closure (transitive)
the set of all entities reachable up/downstream via wasDerivedFrom (§8.7, §16).
Column-level lineage
wasDerivedFrom edges between individual columns (vs whole datasets); extracted by SQL/plan parse (§8.5, §15).
Conservative (column lineage)
never drop a real dependency (recall = 1.0); over-reporting allowed (§4.3, I9).
Content-addressed id
a node/edge id = hash of its identifying fields; same logical thing → same id (§8.2, I5).
Coverage (column)
the fraction of a query's path that has column-level (not just dataset) edges (I12).
DAG (derivation)
the directed acyclic graph of wasDerivedFrom (cycles forbidden, I1).
Dataset-level lineage
lineage at table/dataset granularity (always present, §8.4).
Dedup / idempotency
collapsing re-delivered events so a retry yields one edge set (§8.13, I7).
Entity (PROV)
a thing with provenance; here, a dataset or column version (§8.1).
Granularity
dataset-level vs column-level (the lineage resolution, §8.4).
Hub node
a super-connected dataset (e.g. users) with very high edge fan-out; requires bounded traversal (§4.2, §33).
Impact analysis
the downstream closure (what a change affects); forward BFS (§8.14, §17).
Lineage
the record of where data came from, how it was transformed, and what it feeds.
Merkle chain
a hash chain making the event log tamper-evident (#71, §19, I10).
MVCC
multi-version concurrency control; readers take a snapshot, writers append; no blocking (§3.5, I11).
OpenLineage (OL)
the open standard for run/job/dataset lineage events (the ingest contract, §8.8).
Oracle
the in-memory reference implementation; the correctness ground truth (§12, principle 15).
Partial result
a closure that hit bounds (k/R/deadline) and was truncated; flagged truncated=true (I8).
Provenance
the origin + derivation history of data (the why/how/where of a value).
PROV-DM
the W3C provenance data model (entities/activities/agents + relations, §8.1).
Pull-based capture
scraping / log-mining lineage without producer instrumentation (§38.A, contrast with push).
Push-based capture
producers emit OpenLineage events; the primary capture mechanism (§8.4, ADR-8).
Recall
fraction of true dependencies that are captured; recall = 1.0 is the contract (I9).
Root-cause
the upstream closure under a predicate (what produced a flagged value), ranked (§8.14, §17).
RunContext
the (job, run id, valid-time, tx-time, agent) carried on every edge (§8.2, I4).
Snapshot
a (valid,tx) cut of the graph; every read is against one (MVCC, §11.3, I11/I13).
Supersede
a corrected edge appended at a new tx-time; the old edge is retained (§8.12, I3).
Tamper-evidence
the property that any alteration of history is detectable (Merkle/signing, §19, I10).
Time-travel
querying lineage "as of" a past (valid,tx) time (§8.12, §18).
Transaction-time
when a fact was recorded in the system (the tx axis of the bitemporal model).
Valid-time
when a fact was true in the modeled world (the valid axis of the bitemporal model).
wasDerivedFrom
the PROV relation: one entity was derived from another (the lineage edge, §8.1).
wasGeneratedBy / used
a run produced / read a dataset (attribute the transform, §8.1).
Why/how/where provenance
which inputs influenced (why), the transformation (how), the source location (where).
