367 — Data Lineage + Provenance System

Goal: Implement, from scratch in Rust, a data lineage + provenance system: capture where every dataset/table/column came from, what transformed it, and what it feeds — as a versioned, bitemporal provenance DAG grounded in the W3C PROV-DM model (Entities, Activities, Agents; relations wasGeneratedBy / used / wasDerivedFrom / wasAssociatedWith / wasInformedBy). Capture is push-based (OpenLineage-style run/job/dataset events), augmented by SQL/query-plan parsing for column-level lineage and runtime instrumentation hooks; ingestion is idempotent. The graph is stored on a versioned/temporal store (cross-link #84 Graph DB, a dependency) and answers transitive upstream/downstream closure, column-level propagation, impact analysis (blast radius of a change/incident), root-cause (what upstream produced a bad value), and time-travel ("lineage as of T"). Provenance is tamper-evident (Merkle, #71) and optionally signed — trustable for audit/compliance (GDPR/SOX data-flow). Crates: prov-core / capture / graph / query / integrity / api / cabi / bench / conformance. It models the OpenLineage/Marquez + DataHub + Apache Atlas + Egeria + Google Goods family — not a general graph database (#84, the dependency), a CDC engine (#103, a source), a distributed tracing system (#132, the analogy only), or a data catalog/UI. Correctness is validated against a deterministic in-memory reference oracle and differential tests over recorded OpenLineage event streams; column lineage against a hand-labeled SQL corpus.

1. Goal

1.1 Engineering Definition

  • Build a from-scratch data lineage + provenance system: PROV-DM model → push capture (OpenLineage events) + SQL/plan parse (column lineage) → versioned/bitemporal lineage graph (over #84) → closure/impact/root-cause/time-travel queries → tamper-evidence (Merkle/signing, #71) → REST/gRPC API.
  • Granularity: dataset/table → column/field lineage. Column-level is the hard, high-value tier, derived from SQL/query-plan parsing — not guessed.
  • Provenance model: every lineage edge is a PROV relation carrying a run context (job, run id, timestamp, agent) — lineage is event-sourced, not hand-maintained.

1.2 System Boundaries

  • In scope: PROV-DM entity/activity/agent + relation types with dataset/column references; OpenLineage-compatible event ingest (idempotent); a SQL + logical-query-plan parser that extracts column-level derivation edges; a versioned, bitemporal lineage graph store (built on #84); transitive closure (up/down, k-hop, bounded); column-level propagation; impact analysis (downstream blast radius); root-cause (upstream contribution); time-travel ("as of T"); Merkle-chained tamper-evidence + optional Ed25519 event signing; a search index over datasets/columns/jobs; REST + gRPC + a linctl CLI.
  • Out of scope (non-goals): a general graph database engine → #84 (dependency; storage + traversal substrate); a CDC engine → #103 (a source we ingest from); a stream processor → #105 / #215 (sources); a distributed tracing system → #132 (the analogy: "provenance is tracing for data" — different system, not reused); a data lake table format → #214 (we ingest its snapshot provenance); a build system → #136 (we ingest content-addressed build provenance); a data catalog UI / metadata governance product → PhaseDeferred("§1.7"); specific connector SDKs (Spark/dbt/Airflow plugins) → PhaseDeferred("§1.7"); ML-based column-lineage inference (we do deterministic SQL parsing only) → PhaseDeferred("§1.7"); cross-org federation → PhaseDeferred("§1.7").

1.3 Deployment Model

  • A Rust library + a lineage-server daemon (lineaged) exposing REST/gRPC, backed by #84 for graph storage (embedded or remote). Capture is push: producers POST OpenLineage events to an ingest endpoint, or link the capture library and call its instrumentation API directly. A linctl CLI for ingest, query (upstream/downstream/impact/root-cause), time-travel, integrity verification, and a single-process simulation mode. Shared-nothing producers; the server is the single writer to the graph (or sharded — §scalability).

1.4 Target Users

  • Data/platform engineers who must understand how column-level lineage is actually derived, how a provenance DAG is versioned and queried, and how blast-radius/root-cause analysis works mechanically; data-governance/compliance teams needing trustable data-flow records.
  • Downstream/adjacent: data platforms that ingest from #103/#105/#215 (CDC/stream), #214 (table format), #136 (build) and need a queryable provenance layer; auditors using tamper-evident lineage for GDPR/SOX.

1.5 Phase 0 Deliverable — crates/modules

  1. prov-core — PROV-DM types: Entity/Activity/Agent, relations, DatasetRef/ColumnRef, RunContext, content-addressed node ids, error types.
  2. graph — versioned/bitemporal lineage graph store over #84: node/edge model, append-only revisions, valid-time/transaction-time, snapshot reads.
  3. capture — OpenLineage event ingest (idempotent dedup), SQL + query-plan parser → column-level edges, instrumentation API.
  4. query — transitive up/downstream closure, column propagation, impact analysis, root-cause, time-travel; bounded traversal.
  5. integrity — Merkle chaining of events/revisions (#71), optional Ed25519 signing, verification.
  6. api — REST + gRPC + search index; the lineage server (lineaged).
  7. cabi — C ABI (+ FFI-friendly layer).
  8. bench / conformance — ingest throughput + closure-latency harness; in-memory reference oracle + OpenLineage differential + SQL-corpus column-lineage accuracy + tamper-evidence + fuzz.

1.6 What Later Phases Unlock

  • P0 skeleton + PROV-DM + oracle → P1 versioned graph store → P2 dataset-level capture (OL events, idempotent) → P3 column/field lineage (SQL/plan parse) → P4 closure queries → P5 impact + root-cause → P6 temporal/bitemporal + time-travel → P7 integrity (Merkle + tamper-evidence + signing) → P8 scale ingestion (CDC/stream/log connectors) → P9 search + API → P10 retention/compaction/GC → P11 C ABI → P12 performance hardening → P13 conformance/fuzz/bench.

1.8 Estimated Timeline

  • Phase 0: 8–12 weeks (PROV-DM types + the versioned graph model over #84 + idempotent OL ingest + a closure query + the in-memory oracle).
  • Full P1–P13: 12–16 months part-time. Long poles: P3 (column-level SQL/plan parsing — genuinely hard, the headline value), P4–P5 (closure/impact/root-cause at graph scale), P6 (bitemporal correctness), P8 (heterogeneous ingestion).

1.9 Recommended Language & Rationale

  • Rust. (a) Capture parses untrusted SQL/events from many producers — memory safety + a real type system make the parser/ingest path auditable and panic-free across the trust boundary; (b) async ingestion at high event rates with bounded buffers/backpressure fits Rust's async + ownership model; (c) reuses #84 (graph) and #71 (Merkle) directly; (d) no GC pauses to perturb closure-query tail latency on large graphs; (e) extern "C" ABI so polyglot producers/consumers can drive it.
  • Rejected: Java/JVM (the Atlas/DataHub lineage — excellent ecosystem, but GC tail latency on graph traversal, heavier ABI/embedding story, and "from scratch" learning is muddier behind a framework); Python (the dbt/Spark/OpenLineage-client lineage — fine for the producer side and SQL parsing prototypes, far too slow + unsafe for the high-rate ingest/closure data plane); Go (great for the server/ingest, weaker for the parser's algebraic data types and zero-copy graph work, GC jitter); C/C++ (the raw control is unnecessary and the untrusted-SQL parser is exactly where memory-safety bugs become CVEs).

1.10 Prerequisites

  • Provenance theory (W3C PROV-DM/PROV-O; the why-vs-where-vs-how provenance distinction); graph data structures + traversal (BFS/DFS, transitive closure, cycle detection, topological order); compilers/parsing (SQL lexing/parsing, logical query plans, scope/binding resolution for column derivation); databases (bitemporal modeling — valid-time vs transaction-time, snapshot isolation, MVCC intuition); content-addressing + Merkle structures + signatures; event-sourcing + idempotency. Strongly recommended prior: #84 Graph DB (dependency), #71 Merkle Tree (tamper-evidence), #95 Vector Clocks (event causality), #103 CDC / #105 Stream Processing (ingestion sources), #132 Distributed Tracing (the analogy to internalize and then not conflate).

2. Why Build This

2.1 Unique Knowledge Taught

  • Provenance as a first-class data model (PROV-DM). Entities (datasets/columns), Activities (jobs/runs), Agents (people/services) + the relation algebra (used, wasGeneratedBy, wasDerivedFrom, wasInformedBy, wasAssociatedWith). The difference between where (source location), why (which inputs influenced), and how (the transformation) provenance.
  • Column-level lineage from SQL. The genuinely hard part: parse a query, resolve column scopes/bindings through projections/joins/subqueries/CTEs/aggregations, and emit conservative wasDerivedFrom edges per output column. Why SELECT * and aggregates and CASE make this subtle.
  • Bitemporal provenance. Valid-time ("when was this lineage true in the world") vs transaction-time ("when did we learn it") — and why time-travel queries need both. The DAG is append-only + versioned, never mutated in place.
  • Closure at scale + impact/root-cause. Transitive closure as the core query; impact analysis = downstream reachable set (blast radius); root-cause = upstream contribution under a predicate; why these must terminate (cycle detection) and stay bounded on million-node graphs.
  • Tamper-evident provenance. Merkle-chaining events so audit lineage is verifiable, and why "provenance you can't trust" is worthless for compliance.

2.2 Why It Matters

  • Every mature data platform (Atlas, DataHub, OpenLineage/Marquez, Egeria, Google's Goods, Databricks Unity Catalog lineage) is this: a provenance graph capturing what produced what, queried for impact and root-cause. When a dashboard breaks, "what upstream changed?" is a lineage query; when GDPR asks "where does this PII flow?", that is a downstream closure; when a bad value appears, root-cause walks the provenance DAG. Lineage is the connective tissue of data governance and incident response.

2.3 Engineering Muscles

  • Data modeling against a formal standard (PROV-DM); parser/compiler engineering (SQL → column derivation); graph algorithms (closure, cycle detection, bounded traversal) on a backing store; bitemporal/versioned storage design; event-sourcing + idempotency; content-addressing + Merkle + signing; high-rate ingestion with backpressure; differential + corpus-based testing of a parser; API design for graph queries.

2.4 Production Concepts Exercised

  • Event-sourced provenance capture; idempotent ingest; column-level lineage extraction; bitemporal/time-travel queries; impact/root-cause analysis; tamper-evident audit trails; retention/compaction/GC of an append-only graph; search over a metadata graph; multi-source ingestion (CDC/stream/log).

2.5 Cross-Links

  • #84 Graph DB — dependency; the lineage graph's storage + traversal substrate. We model nodes/edges/versions on top of it; we do not reimplement a graph engine.
  • #71 Merkle Tree — dependency; tamper-evidence of the event/revision log.
  • #95 Vector Clocks — event causality / ordering when events arrive out of order from many producers.
  • #103 CDC Engine / #105 Stream Processing / #215 CDC Replication — ingestion sources (P8): change events and stream jobs emit lineage we capture.
  • #214 Data Lake Table Format — a source of table/snapshot provenance (which snapshot produced which).
  • #136 Build System — a source of content-addressed build provenance (which inputs/version built which artifact) — the same wasDerivedFrom shape, different domain.
  • #132 Distributed Tracing — the analogy, not a reuse: provenance is "tracing for data" (spans↔activities, trace↔derivation chain), but tracing is request-scoped/ephemeral and this is durable/versioned. Internalize the parallel; do not conflate the systems.

2.6 Calibration Value

  • You leave able to read OpenLineage/Marquez, DataHub, and Apache Atlas and explain every lineage edge, the column-level extraction, the temporal model, and the query semantics — and to reason about why a data incident's root cause is a graph walk and how to make lineage trustable for audit.

2.7 The capture-fidelity wall — the defining constraint

  • #84 (graph DB) is traversal/storage-bound; #132 (tracing) is request-rate-bound; this system is capture-fidelity-bound — the scarce resource is complete, correct lineage. A query is only as good as the edges captured.
  • Consequence 1: column lineage is conservative or wrong. A dropped dependency (false negative) silently breaks impact/root-cause; the parser must never under-report a real derivation (I9), even at the cost of over-reporting.
  • Consequence 2: ingestion must be idempotent. Producers retry; the same OL event arriving twice must yield one edge (I7), or the graph self-corrupts with duplicates that distort closure.
  • Consequence 3: lineage is a DAG; cycles are a capture bug. Derivation cannot be circular; a cycle means a mis-attributed edge → detect, reject, alarm (I1) — and closure queries must terminate regardless (I8).
  • Consequence 4: time is two-dimensional. "Lineage as of T" needs valid-time and transaction-time, or audit answers are wrong about what was known when.
  • Consequence 5: trust requires tamper-evidence. For compliance, an unverifiable provenance record is inadmissible — Merkle-chaining is not optional decoration.
  • This single fact (a query is only as good as the captured edges) reorganizes every decision: capture correctness > query speed, and conservatism > precision.

2.8 What Mastery Looks Like

  • P0 — PROV-DM fluency: given a real ETL job, you can draw the entity/activity/agent graph with correct relation types, assign content-addressed ids, and explain why a cycle would be a capture bug. Gained in Phase 0.
  • P1 — Graph-model depth: you can explain how bitemporal edges map to a versioned store, why append-only is necessary for audit, and how MVCC snapshot reads decouple readers from writers. Gained in Phase 1.
  • P2 — Capture engineering: you can trace an OpenLineage event end-to-end from POST to committed edge, explain the dedup scheme, and know why canonicalization precedes hashing. Gained in Phase 2.
  • P3 — Column-lineage parsing: you can walk through a SQL query with CTEs and aggregations, resolve column scopes, and enumerate every conservative wasDerivedFrom edge — including predicate columns. You understand why recall=1.0 is non-negotiable. Gained in Phase 3.
  • P4–P5 — Query reasoning: you can predict a closure's output on a diamond DAG, explain the hub-node hazard and why bounds are mandatory, and articulate when root-cause ranking puts the wrong result first. Gained in Phases 4–5.
  • P6 — Temporal fluency: given an audit question ("what did we know at T about lineage on date V?"), you can construct the correct bitemporal snapshot and explain what a correction-without-deletion looks like in the graph. Gained in Phase 6.
  • P7 — Trust engineering: you can explain why Merkle-chaining is necessary even on an append-only store, what a tamper forensics binary search finds, and the threat model for a production lineage audit trail. Gained in Phase 7.

3.2 Box Narratives

  • producers. External: Spark/dbt/Airflow jobs, #103 CDC, #105 stream jobs, #136 builds. They emit OpenLineage-style events (run start/complete with input/output datasets) and/or raw SQL/query plans. Untrusted input crossing into capture.
  • capture. The ingest front door. (a) OL event ingest: validate, dedup (idempotency key → I7), translate to PROV facts. (b) SQL/query-plan parser: lex/parse SQL, build a logical plan, resolve column scopes, emit conservative column-level wasDerivedFrom edges (I9). (c) instrumentation API: a library producers link to emit events directly. (d) source connectors (P8): adapters for CDC/stream/log sources. Hands PROV facts to prov-core/graph and raw events to integrity.
  • prov-core. The PROV-DM vocabulary every other crate speaks. Entity (a dataset/column version), Activity (a job run), Agent (a person/service); relations wasGeneratedBy/used/wasDerivedFrom/wasAssociatedWith/wasInformedBy. DatasetRef/ColumnRef (namespaced, stable identities), RunContext (job, run id, timestamps, agent). Node ids are content-addressed for dedup/idempotency. The normative type set.
  • graph. The versioned, bitemporal lineage DAG, stored on #84. Nodes = dataset/column/job versions; edges = PROV relations annotated with valid-time + transaction-time + the run context. Append-only revisions (never mutate in place); snapshot reads ("as of T"). Enforces the DAG invariant (cycle detection, I1) and idempotency at the storage layer. Owns the mapping from PROV facts to #84's node/edge primitives — but not the traversal engine itself (that is #84).
  • query. The query engine over the graph: transitive up/downstream closure (bounded, terminating — I8), column-level propagation (follow column edges), impact analysis (downstream reachable set = blast radius), root-cause (upstream contribution under a predicate — what produced a flagged value), and time-travel (closure as of a (valid,tx) time). Pure reads; deterministic given a snapshot.
  • integrity. Tamper-evidence: every captured event/revision appended to a Merkle-chained log (#71); optional Ed25519 signing of events by producers; verify recomputes the chain and checks signatures. Makes lineage admissible for audit (principle: provenance must be trustable).
  • api. The lineaged server: REST + gRPC endpoints for ingest + all query types; a search index over dataset/column/job names + facets. linctl CLI wraps it. The external interface + trust boundary.
  • bench / conformance. Ingest-throughput + closure-latency harness; the in-memory reference oracle (a simple, slow, obviously-correct lineage model — the trusted result); OpenLineage differential (replay recorded event streams, compare to oracle); SQL-corpus column-lineage accuracy (hand-labeled queries → precision/recall, with recall = 1.0 required, I9); tamper-evidence tests; fuzz (SQL parser, event parser).

3.3 Boundaries

  • Trust boundary: the ingest API (OL events, SQL, plans from many producers) and the C/query API. All input is validated; SQL is parsed defensively (resource-bounded, panic-free, I15). Producers are semi-trusted; signed events raise trust for audit.
  • Concurrency boundary: many concurrent ingest writers vs many concurrent query readers. The graph is append-only → writers append revisions; readers take snapshots → MVCC-style read/write separation (no read blocks a write).
  • Persistence boundary: #84 is the durable store; integrity's Merkle log is a second durable artifact (the tamper-evidence chain). The line between "PROV facts in the graph" and "raw events in the Merkle log" is explicit.
  • Temporal boundary: valid-time (world time of the lineage fact) vs transaction-time (when we recorded it). All writes stamp both; all reads choose a (valid,tx) snapshot. This boundary is the source of every time-travel subtlety.
  • Granularity boundary: dataset-level edges (always present) vs column-level edges (present only when a SQL/plan parse succeeded). Queries declare which granularity they need; column queries degrade gracefully to dataset-level where column edges are absent (and say so — I12).

3.4 Data-flow walk — capturing + querying one ETL job

  1. A dbt/Spark job runs INSERT INTO sales_daily SELECT date, SUM(amount) FROM orders GROUP BY date. It emits an OL event: run r1, job etl.sales_daily, inputs [orders], outputs [sales_daily], plus the SQL.
  2. capture ingests: dedups on r1's idempotency key (I7), creates Activity(run=r1), Entity(orders@v), Entity(sales_daily@v'); emits used(r1, orders) + wasGeneratedBy(sales_daily, r1) (dataset-level).
  3. The SQL parser resolves columns: sales_daily.date wasDerivedFrom orders.date; sales_daily.amount wasDerivedFrom orders.amount (through the SUM). Conservative: the aggregate keeps the dependency (I9). Column edges added.
  4. integrity appends the raw OL event to the Merkle log (I10); if the producer signed it, the signature is stored.
  5. graph writes all edges with valid_time = run.event_time, tx_time = now, run ctx r1 — append-only revision (I3); cycle check passes (orders ≠ downstream of sales_daily, I1).
  6. Later, sales_daily.amount looks wrong. Root-cause query: walk upstream column edges from sales_daily.amount → orders.amount, ranked by run recency → the operator inspects orders.amount's producing run.
  7. orders schema changes. Impact analysis query: downstream closure from orders → {sales_daily, … and everything sales_daily feeds} = the blast radius, returned with paths.
  8. An auditor asks "what did lineage look like on 2026-01-01?" Time-travel: closure over the snapshot tx_time ≤ 2026-01-01 → the graph as we knew it then (I13). verify confirms the Merkle chain is intact (I10).

3.5 Concurrency model (writers, readers, snapshots)

  • Ingest writers (a pool) validate + dedup + append revisions; appends are serialized at the per-node level (a node's revision chain is ordered) but parallel across nodes. Idempotency (I7) makes a duplicate append a no-op.
  • Query readers take a snapshot (a (valid,tx) point) and traverse without locking writers — append-only + MVCC means a reader sees a consistent past; concurrent writes are simply invisible to it (I3/I13).
  • Cycle detection runs at write time (adding an edge that would close a derivation cycle is rejected, I1) — never at query time (queries must always terminate, I8).
  • The Merkle log is appended by a single ordered writer (or a per-shard ordered writer) so the chain is well-defined (I10); ingest enqueues, the log writer drains.
  • Search index updates are derived from committed graph writes (eventually consistent with the graph; the graph is the source of truth, the index is a cache — I14).
  • Synchronization: no global lock on the read path; writers coordinate only on a node's revision chain and the Merkle log tail. Readers are wait-free against writers.

4.1 Worked freshness budget (capture→queryable)

  • Path: receive event → validate (~50µs) → dedup lookup (~100µs) → SQL parse if present (~1–5ms) → emit PROV facts → graph append (~1–10ms incl #84 write) → visible to snapshot reads.
  • Dataset-level (no SQL): dominated by the #84 append → sub-millisecond to low-ms → p95 < 2 s holds with huge headroom even under batching/backpressure.
  • Column-level: SQL parse dominates (1–5 ms typical, more for huge queries) → still < 2 s unless a pathological query; resource bounds (I15) cap parse time so one giant query can't blow the budget.
  • Implication: freshness is gated by #84 write latency + SQL parse, not by query load (readers don't block writers, §3.5). The constraint table's 2 s p95 is a soft real-time target for incident response, not a hard deadline.

4.2 Worked closure cost (why bounded traversal is mandatory)

  • Closure from a node visits the reachable sub-DAG. Unbounded, on a 100M-edge graph, a hub dataset (e.g. a central users table feeding thousands of downstreams) could reach millions of nodes → seconds + huge result.
  • Therefore every closure is bounded: max hops k (default 8), max result size R (default 10k), and a deadline → returns a partial, marked result rather than hanging (I8). Impact analysis surfaces "result truncated at k hops / R nodes" so the operator knows to narrow.
  • Cost model: closure ≈ O(V' + E') over the reached sub-DAG, bounded by min(reachable, R); with #84 adjacency lookups at ~µs each, R=10k nodes → low-tens-of-ms → meets the p50 < 50 ms target.
  • Hub hazard: a few super-connected nodes dominate; the query exposes per-hop fan-out so a users-table impact query is understood as "intentionally huge," not a bug.

4.3 Worked column-lineage conservatism (the recall=1.0 contract)

  • A SELECT a + b AS c makes c wasDerivedFrom {a, b} — both, never one. A CASE WHEN x THEN a ELSE b END AS c → c wasDerivedFrom {x, a, b} (the predicate counts). A SUM(amount) AS total → total wasDerivedFrom amount.
  • The rule: every column referenced in the expression that produces an output column is an upstream dependency — including predicate/filter columns that gate the value (a WHERE region='US' makes outputs depend on region for why-provenance). Over-reporting (an unused column) is acceptable; under-reporting is a bug (I9).
  • SELECT * → every source column maps to its same-named output (resolved against the source schema; if schema unknown, fall back to a dataset-level edge + mark column-incomplete, I12).
  • Implication: the corpus test asserts recall = 1.0 (every hand-labeled true edge is present) and precision ≥ 0.85 (few spurious edges). The asymmetry is the whole philosophy: a missed edge silently corrupts root-cause/impact; an extra edge merely widens a blast radius (visible, recoverable).

6. Design Principles

  1. Provenance is event-sourced, never hand-edited. Every edge is created by a captured event (a run/SQL/plan), carrying its RunContext. Violation: manually-curated lineage drifts from reality and can't be trusted or reproduced.
  2. The lineage graph is an append-only, versioned DAG. Revisions are added; nodes/edges are never mutated or deleted in place (GC reclaims, it does not rewrite). Violation: in-place mutation destroys history → time-travel and audit are impossible.
  3. Derivation is acyclic; cycles are capture bugs. A wasDerivedFrom cycle is rejected at write time and alarmed (I1). Violation: a cycle makes closure non-terminating and root-cause meaningless.
  4. Column lineage is conservative: never drop a real dependency. Recall = 1.0 is the contract; over-reporting is acceptable, under-reporting is a bug (I9). Violation: a missed edge silently corrupts every downstream root-cause/impact answer — the worst failure (invisible).
  5. Ingestion is idempotent. Content-addressed ids + idempotency keys make a re-delivered event a no-op (I7). Violation: duplicate edges from retries distort closure counts and weights.
  6. Time is bitemporal: stamp valid-time and transaction-time on every fact. Violation: "as of T" answers are wrong about what was true vs what was known → audit failures.
  7. Capture correctness over query performance. A correct-but-slow edge beats a fast-but-missing one. Violation: optimizing the parser by dropping "rare" derivations breaks principle 4.
  8. Closure queries always terminate and are bounded. Hops k, result size R, deadline; partial results are marked, never a hang (I8). Violation: an unbounded closure on a hub node hangs the server.
  9. Graph storage delegates to #84; we own the model, not the engine. Nodes/edges/traversal primitives are #84's; bitemporal + PROV semantics are ours. Violation: reimplementing a graph engine duplicates #84, drifts, wastes effort.
  10. Provenance must be trustable: tamper-evident by default. Events Merkle-chained (#71); signing optional but supported (I10). Violation: unverifiable lineage is inadmissible for compliance.
  11. Graceful degradation across granularity. A column query falls back to dataset-level where column edges are absent, and says so (I12). Violation: silently returning dataset-level for a column query misleads the operator.
  12. Observability of every captured edge and every query. Emit per-ingest (source, dedup hit, parse success, edges added) and per-query (hops, nodes visited, truncated?) telemetry. Violation: opaque capture → can't tell why lineage is incomplete.
  13. Stable API + event-format compatibility. OL ingest version + query API version are negotiated; incompatible producers are refused or adapted. Violation: silent format drift drops or corrupts edges.
  14. Bounded resources on the untrusted parse path. SQL parsing is time/depth/memory-bounded (I15); one giant/malicious query cannot exhaust the server. Violation: a crafted query is a DoS.
  15. Correctness anchored to the in-memory oracle. Every capture+query path is checked against a simple, obviously-correct reference model. Violation: no oracle → lineage bugs are undebuggable (the graph "looks fine").

8. Domain Model — PROV-DM, Lineage Graph, Capture, Queries

8.1 PROV-DM core (the model)

  • Three node kinds: Entity (a thing with provenance — a dataset version, a column version), Activity (something that acts on/produces entities over time — a job run), Agent (something responsible — a person, a service, a pipeline).
  • Core relations: used(Activity, Entity) (a run read a dataset), wasGeneratedBy(Entity, Activity) (a run produced a dataset), wasDerivedFrom(Entity, Entity) (one entity derived from another — the lineage edge), wasAssociatedWith(Activity, Agent) (who ran it), wasInformedBy(Activity, Activity) (a run triggered/fed another).
  • Lineage = the transitive closure of wasDerivedFrom (+ used/wasGeneratedBy to attribute the transform). Column lineage = wasDerivedFrom between ColumnRef entities.

8.2 References + identities

  • DatasetRef { namespace, name, version } — a stable, namespaced dataset identity (e.g. postgres://prod/public.orders@v37). ColumnRef { dataset: DatasetRef, column }.
  • RunContext { job: JobRef, run_id, event_time (valid-time), recorded_at (tx-time), agent: AgentRef, facets }.
  • Content-addressed ids (I5): node_id = hash(kind, namespace, name, version); same logical entity from two sources collapses to one node → cross-source lineage joins automatically.
  • Versions: a dataset's schema/content version makes Entity instances distinct over time → the graph naturally records "orders@v37 → orders@v38."

8.3 The lineage graph (bitemporal, versioned, over #84)

  • Nodes: dataset/column/job/agent entities (content-addressed). Edges: PROV relations, each annotated with (valid_time, tx_time, run_context, granularity).
  • Append-only revisions (I3): a new fact adds nodes/edges with a fresh tx_time; superseding facts add new edges (e.g. a re-run) without deleting old ones.
  • Bitemporal: valid_time = when the lineage was true in the world (the run's event time); tx_time = when we recorded it. Both stamped on every edge (I4).
  • DAG constraint on wasDerivedFrom (I1): inserting an edge that closes a derivation cycle is rejected.
  • Storage: mapped onto #84's node/edge primitives; #84 owns adjacency/traversal, graph owns the bitemporal + PROV semantics layer.

8.5 Column-lineage extraction (the hard part)

  • Parse SQL → AST → logical plan (projections, joins, filters, aggregations, CTEs, subqueries). Resolve each output column's expression; collect every input ColumnRef referenced → emit output_col wasDerivedFrom input_col for each (conservative, I9).
  • Scope resolution: track table aliases, CTE bindings, subquery scopes, USING/NATURAL JOIN column merging. Unqualified columns resolved against the in-scope tables' schemas.
  • Predicate/filter columns count for why-provenance (a WHERE/JOIN ON/CASE condition column influences which rows produce the output).
  • SELECT * expansion needs the source schema; if unknown → dataset-level edge + column-incomplete flag (I12).
  • Aggregates (SUM, COUNT(DISTINCT), window funcs) → the aggregated input column(s) are dependencies; GROUP BY columns are dependencies of the grouped output.

8.6 Worked column-lineage example

INSERT INTO sales_daily(d, total, region) AS

FROM orders o JOIN customers c ON o.cust_id = c.id
WHERE o.status = 'paid' GROUP BY o.order_date, c.region;

→ sales_daily.d      wasDerivedFrom orders.order_date
→ sales_daily.total  wasDerivedFrom orders.amount
→ sales_daily.region wasDerivedFrom customers.region
→ (why) all three also gated by orders.status, orders.cust_id, customers.id (join+filter) — conservative edges

8.8 OpenLineage event model (ingest contract)

8.12 Bitemporal time-travel — what "as of T" means

  • Two clocks: valid-time (world time the lineage was true) and transaction-time (system time we recorded it). A fact is a point/interval in this 2-D space.
  • as_of(tx = T): "what did we know at T" → filter edges with tx_time ≤ T. Audit's primary mode (reproduces a past belief).
  • as_of(valid = V): "what was true at V" → filter edges whose valid-interval contains V. Models lineage that changed in the world (a pipeline rewired on date V).
  • Combined as_of(valid=V, tx=T): "what we knew at T about the world at V" — the full bitemporal query (Snodgrass). Both filters compose, then traverse (I13).
  • Corrections: if we learn on tx=T2 that a past edge (valid=V) was wrong, we append a retraction/supersede at T2 — the old fact still exists at tx≤T2 (audit can see the mistake), the new fact applies at tx≥T2. Nothing is rewritten (I3).
  • Use cases: GDPR audit ("what data flowed into report R as of the breach date"), regression debugging ("did lineage change between releases"), reproducing a past impact analysis.

8.13 Idempotency + content-addressing (why retries are safe)

  • Producers retry on network failure → the same OL event arrives N times. Without idempotency, N duplicate edges → closure over-counts, impact blast radius inflates.
  • Idempotency key (I7): hash(runId, eventType, eventTime, canonical(payload)). A dedup table records seen keys; a re-delivery is a no-op.
  • Content-addressed node ids (I5): two events naming the same dataset (even from different sources/producers) hash to the same node → cross-source lineage joins for free, and a re-ingest doesn't fork the node.
  • Edge dedup: an edge id = hash(src_node, dst_node, relation, run_id) → the same run's same edge re-ingested collapses; a new run's same logical edge is a distinct (versioned) edge (preserving history, I3).
  • Subtlety: valid retries (same content) dedup; a genuinely changed re-run (new run id) does not dedup — it adds a new versioned edge. The key includes the run id precisely so corrections create history rather than silently overwriting.

8.14 Impact analysis vs root-cause — the two directions (the headline queries)

  • Impact analysis (downstream): "if orders changes/breaks, what is affected?" → forward closure from orders = the blast radius. Used before a schema migration, during an incident ("what dashboards consume this?"), for GDPR ("where does this PII flow?").
  • Root-cause (upstream): "sales_daily.total is wrong — what produced it?" → reverse closure from the flagged entity, ranked by run recency + path length, optionally filtered by a predicate (which upstream run touched it in the bad window). Used in incident response to localize the fault.
  • Both are bounded (I8) and carry run context on each edge → the answer is not just "which nodes" but "which runs/jobs on the path" (the actionable part: the job to fix).
  • Column-level sharpens both: dataset-level impact says "orders affects sales_daily"; column-level says "orders.amount affects sales_daily.total specifically" → a far smaller, precise blast radius (don't re-validate columns that don't depend on the change). This is the entire value proposition of P3 — and why recall = 1.0 (I9) matters: a missed column edge means a missed root cause or a falsely-narrowed blast radius.
  • Why two queries, not one: they traverse opposite directions over the same DAG, but rank/filter differently (root-cause cares about recency and a predicate; impact cares about completeness and paths). Conflating them produces a tool that does neither well.

12. Phase 0 — Skeleton: PROV-DM model + in-memory oracle

12.1 Objectives

  • Stand up the workspace + prov-core; depend on #84 and #71.
  • Define the PROV-DM types (Entity/Activity/Agent, relations, DatasetRef/ColumnRef, RunContext), content-addressed NodeId/EdgeId (I5/I7).
  • Build the in-memory reference oracle: a simple, slow, obviously-correct lineage model (HashMaps + naive closure) — the trusted result for every later phase (principle 15).

12.2 Detailed Implementation Steps (ADR-3/5/25; P1/P2/P15)

  • prov-core::{entity,activity,agent,relation} — the PROV-DM node + relation types with correct role typing (I2).
  • prov-core::{dataset_ref,column_ref,run_context} — namespaced refs + the required RunContext (I4).
  • prov-core::nodeid — content-addressed id = hash(kind,namespace,name,version); EdgeId = hash(src,dst,rel,run_id) (I5/I7).
  • conformance::oracle — an in-memory graph (HashMap<NodeId,Node> + adjacency HashMap<NodeId,Vec<Edge>>), naive reverse/forward BFS closure, naive cycle detection. No bitemporal, no bounds — just correct.
  • linctl skeleton: ingest a hand-written PROV fact, print a node.

12.3 Deliverable

  • Construct PROV facts, build the in-memory oracle, run a tiny upstream/downstream closure by hand; linctl node <id> prints it.

12.4 Acceptance Criteria

  • NodeId is stable + content-addressed (same logical entity → same id, I5); collisions for distinct entities are negligible.
  • Oracle closure matches a hand-computed result on a 5-node graph.
  • PROV type roles validated (an Agent can't be wasGeneratedBy, I2).

12.5 Conformance Fixtures

  • closure/tiny_upstream.json, closure/tiny_downstream.json, badinput/prov_type_violation.json.

12.6 Pitfalls

  • Content-address over the wrong fields → unstable ids → dedup fails / nodes fork (I5). Pin the canonical field set + ordering.
  • PROV role confusion (Entity vs Activity) → invalid relations. Type the relations so illegal pairings don't compile/construct.
  • Oracle that is "clever" → not trustable. Keep it naive (the whole point is obvious correctness).

12.7 Performance Concerns

  • None yet; the oracle is intentionally O(V+E) naive. Establish measurement scaffolding only.

12.8 Edge Cases

  • Empty graph; a self-referential edge (must be rejected as a 1-cycle later, flagged now); duplicate node insert (id collapses, I5).

12.9 Failure Analysis

  • A wrong NodeId scheme silently forks every entity → every closure is wrong → exhaustive id-stability tests + the oracle guard it.

12.10 Operational Notes

  • tracing init; document the content-addressing scheme in docs/prov-mapping.md; the oracle is the conformance backbone (ADR-25).

13. Phase 1 — Versioned lineage graph store over #84

13.1 Objectives

  • Build the real graph layer on #84: the node/edge model, append-only revisions (I3), and snapshot reads (I11) — the durable substitute for the oracle's HashMaps. (Bitemporal filtering lands in P6; this phase ships single-time append-only + revisions.)

13.2 Detailed Implementation Steps (ADR-4/7/16; I1/I3/I5/I7/I11; P9)

  • graph::model — map PROV nodes/edges onto #84's node/edge primitives (properties = relation, granularity, run ctx, timestamps).
  • graph::store_84 — the #84 adapter: create node, create edge, adjacency lookup (out_edges/in_edges). #84 owns traversal primitives (principle 9).
  • graph::revision — append-only Revision/RevisionBatch; each append gets a monotonic rev + tx_time (I3).
  • graph::dedup — node/edge dedup by content id (I5/I7) at the storage layer.
  • graph::cycle_check — DFS/Tarjan over the affected region on WasDerivedFrom insert; reject a cycle (I1).
  • graph::snapshot — a read view fixed at a rev/tx_time; reads ignore later revisions (MVCC, I11). (Single tx-time axis here; valid-time deferred to P6.)

13.3 Deliverable

  • Append PROV facts to the #84-backed graph; read them back via snapshot; the same facts fed to graph + oracle produce identical adjacency. linctl ingests + queries against the real store.

13.4 Acceptance Criteria

  • Append-only: no API mutates a committed edge (I3); re-append of the same edge dedups (I7).
  • Snapshot reads are consistent under concurrent appends (I11) — a reader at rev=k never sees rev>k.
  • Cycle insertion rejected (I1); graph adjacency == oracle adjacency on recorded fixtures.

13.5 Conformance Fixtures

  • closure/graph_vs_oracle_adjacency.json, temporal/snapshot_consistency.json, badinput/cycle_insert.json.

13.6 Pitfalls

  • Leaking #84's API shape into upper crates → coupling. Keep store_84 the only #84-aware module (principle 9).
  • Cycle check over the whole graph on every insert → O(V) per write. Scope it to the affected region (ancestors of dst / descendants of src).
  • Snapshot torn reads if a reader sees a half-committed revision → commit a revision atomically (all-or-nothing batch) (I11).
  • Dedup race: two writers append the same new node → use the content id as the storage key so the second is a no-op (I7).

13.7 Performance Concerns

  • Write path = #84 node/edge creates → batch a RevisionBatch into one #84 transaction to amortize.
  • Adjacency lookup latency is #84's; cache hot hub nodes' adjacency at the query layer (P4), not here.
  • Cycle check cost bounded by the affected region, not graph size.

13.8 Edge Cases

  • First revision (empty graph); a node referenced before defined (forward ref → create placeholder, fill on definition); a self-edge (1-cycle, rejected I1).

13.9 Failure Analysis

  • A snapshot bug → queries see inconsistent cuts → temporal/snapshot_consistency + a concurrent ingest/read stress test guard it; docs/failure-analysis/snapshot-skew.md.
  • A cycle slipping through → non-terminating closure later → cycle-check fuzz + the I8 bound as a backstop.

13.10 Operational Notes

  • IngestTrace.append_us, Revision.rev; document the #84 mapping in docs/prov-mapping.md; the graph is the source of truth, never edited out-of-band (principle 1/2).

14. Phase 2 — Dataset-level capture: OpenLineage events, idempotent ingest

14.1 Objectives

  • Ingest OpenLineage run/job/dataset events (push), translate to PROV facts, and commit dataset-level edges — idempotently (I7). The capture front door for the common case (no SQL yet).

14.2 Detailed Implementation Steps (ADR-8/13; I2/I4/I7/I15; P6/P1; Kleppmann Ch.11; OpenLineage spec)

  • capture::openlineage — parse the OL RunEvent JSON (event type, run, job, inputs, outputs, event_time, facets); validate (I2/I15).
  • capture::event_ingest — translate: each input → used(run, ds); each output → wasGeneratedBy(ds, run); output wasDerivedFrom each input (dataset-level); wasAssociatedWith(run, agent). Commit on COMPLETE (policy-configurable).
  • capture::idempotency — dedup table keyed by hash(runId,eventType,eventTime,canonical(payload)) (I7); a re-delivery is a no-op returning dedup_hit.
  • instrument_api — a thin library API so a producer can emit events directly (same path).
  • Wire event_time → valid_time, now → tx_time on every edge (I4); (bitemporal querying still P6).

14.3 Deliverable

  • POST OL events (or call the instrument API) → dataset-level lineage in the graph; replay the same stream twice → identical graph (I7). examples/ingest_ol.

14.4 Acceptance Criteria

  • Differential: replay a recorded OL event stream → graph adjacency == oracle fed the same events (the OpenLineage differential, ADR-25).
  • Idempotency: ingest each event N times → exactly one edge set (I7); dedup_hit true on repeats.
  • Determinism: same stream → identical graph hash (I6; content-addressed ids).

14.5 Conformance Fixtures

  • openlineage/etl_stream.jsonl (a recorded run sequence), openlineage/replay_idempotent.json, openlineage/dataset_lineage_vs_oracle.json.

14.6 Pitfalls

  • COMPLETE-before-START / out-of-order events → reconcile by run id; don't commit conflicting edges (use valid-time / #95 if clocks disagree, §8.10).
  • Idempotency key over a non-canonical payload → two encodings of the same event don't dedup → canonicalize (sort keys, normalize) before hashing (I7).
  • Treating START edges as final → premature/partial lineage; commit on COMPLETE or flag partial.
  • A failed run (FAIL/ABORT) still has lineage value (it used inputs) → record the run + inputs, flag outputs as not-produced.

14.7 Performance Concerns

  • Ingest is the hot path (§4: 50k events/s) → batch commits, async (202), bounded queue (I8/principle 14).
  • Dedup lookup must be O(1) (hash table / #84 key existence); the dedup table is itself bounded (LRU + persisted set) — see P10.
  • JSON parsing overhead → reuse buffers; the OL schema is small.

14.8 Edge Cases

  • An event with no inputs (a source ingest); no outputs (a sink); duplicate datasets in inputs (dedup); a run with the same dataset as input and output (a self-edge → cycle check, I1).

14.9 Failure Analysis

  • Duplicate edges from a dedup bug → inflated blast radius → replay_idempotent fixture + a "replay 100×" CI check; docs/failure-analysis/duplicate-edge.md.
  • A mistranslation (wrong relation direction) → backwards lineage → the oracle differential (I3) catches it.

14.10 Operational Notes

  • IngestTrace (source, dedup_hit, edges_added); the ingest queue depth + backpressure are dashboard metrics; document the OL ingest contract version (principle 13).

15. Phase 3 — Column/field-level lineage: SQL + query-plan parsing

15.1 Objectives

  • Extract column-level wasDerivedFrom edges by parsing the SQL a job ran (or its query plan) — conservatively (recall = 1.0, I9). The headline value, the hardest phase.

15.2 Detailed Implementation Steps (ADR-9/10; I9/I12/I15; P4/P7; Dragon Book Ch.2–6; Cheney et al. 2009; Green et al. 2007; Interlandi et al. 2015)

  • capture::sql_lexer + sql_parser — a hand-written recursive-descent parser for the supported SQL subset (SELECT/projections/FROM/JOIN/WHERE/GROUP BY/HAVING/CTE/subquery/CASE/aggregates); resource-bounded (depth/tokens/time, I15).
  • capture::plan — lower the AST to a logical plan (project, join, filter, aggregate, scan) — the structure column resolution walks.
  • capture::scope_resolve — resolve table aliases, CTE bindings, subquery scopes; resolve each (qualified/unqualified) column reference to a source ColumnRef against the SchemaCatalog.
  • capture::column_lineage — for each output column, collect every referenced input column (projection expr + predicate/filter/join columns that gate it) → emit out_col wasDerivedFrom in_col (conservative, I9). SELECT * → schema expansion or ColumnIncomplete (I12).
  • Wire into ingest: if an OL event carries a sql facet (or columnLineage facet), run extraction; on parse failure → dataset-level edge + column-incomplete flag (I12).

15.3 Deliverable

  • Ingest a job with SQL → column-level lineage in the graph; examples/sql_column_lineage shows per-output-column derivation; coverage reported (I12).

15.4 Acceptance Criteria

  • SQL corpus: recall = 1.0 (every hand-labeled true edge present, I9) — a CI hard gate; precision ≥ 0.85.
  • Aggregates/CASE/joins/CTEs/subqueries resolved per §8.5; predicate columns included (why-provenance).
  • Parse is bounded (I15): a pathological query rejected within the time/depth limit, not a hang; column-incomplete on unsupported syntax (I12).
  • Column lineage matches the oracle's hand-labeled edges on the corpus.

15.5 Conformance Fixtures

  • sql_corpus/*.sql + sql_corpus/*.expected.json (hand-labeled column edges: projections, aggregates, CASE, joins, CTEs, subqueries, SELECT *); sql_corpus/unsupported.sql (→ column-incomplete); badinput/sql_dos.sql (bounded reject, I15).

15.6 Pitfalls

  • Aggregates dropping the input dependency (SUM(x) → must keep x) → the classic recall failure (I9). Test every aggregate.
  • Predicate columns omitted → why-provenance lost (WHERE region=… makes outputs depend on region). Include filter/join/CASE-condition columns.
  • Unqualified column ambiguity across joined tables → resolve against the in-scope schemas; if truly ambiguous and unresolvable → conservative: attribute to all candidates (over-report, I9) + flag.
  • CTE/subquery scope leakage → a column resolved to the wrong scope → backwards/wrong edge. Rigorous scope stacking.
  • SELECT * without schema → can't enumerate columns → ColumnIncomplete + dataset edge (I12), never silently drop.

15.7 Performance Concerns

  • Parse dominates column-capture latency (§4.1: 1–5 ms typical) → bounded so one giant query can't blow freshness (I15).
  • Schema catalog lookups for resolution → cache hot schemas.
  • Column-capture throughput (5k events/s) << dataset-only (50k) → parse is the cost; producers can pre-extract (OL columnLineage facet) to skip it.

15.8 Edge Cases

  • SELECT 1 AS c (constant, no upstream column → no derivation edge, correct); a AS x, a AS y (one input, two outputs); recursive CTE (bounded depth, I15); window function OVER (PARTITION BY p) → p is a dependency; UNION (each branch contributes).

15.9 Failure Analysis

  • A missed column edge (recall < 1.0) is the worst failure — silent, corrupts root-cause/impact (I9). The corpus recall=1.0 CI gate is the primary net; escapes become corpus regressions; docs/failure-analysis/missed-column-edge.md.
  • A parser hang/crash on crafted SQL → fuzz (fuzz/sql_parse) + the I15 bounds; ASAN/Miri.

15.10 Operational Notes

  • IngestTrace.{parse_complete,column_edges,parse_us}; tools/coverage_report shows column-lineage coverage % (which tables have column edges); document the supported SQL subset in docs/sql-subset.md (principle 13).

16. Phase 4 — Closure queries: transitive up/downstream

16.1 Objectives

  • Implement the core query: bounded transitive upstream/downstream closure + column propagation, over a snapshot, deterministic and always-terminating (I6/I8).

16.2 Detailed Implementation Steps (ADR-12; I6/I8/I12; CLRS §22; §4.2)

  • query::closure — bounded BFS: reverse (in_edges, upstream) / forward (out_edges, downstream) over WasDerivedFrom (+ attribute via used/wasGeneratedBy); stop at max_hops / max_results / deadline (I8).
  • query::column_propagate — closure restricted to Granularity::Column edges; falls back to dataset-level + coverage flag where column edges absent (I12).
  • query::bounds — the bound enforcement (hops, result size, deadline) + truncated/hops_reached reporting (I8).
  • Result envelope: nodes + edges + paths + truncated flag; ordered deterministically (I6).
  • Hot-hub adjacency cache at the query layer (a few super-connected nodes dominate, §4.2).

16.3 Deliverable

  • linctl upstream/downstream <ref> --hops k returns the closure with paths; column mode reports coverage. examples/impact_query (the downstream case).

16.4 Acceptance Criteria

  • Closure == oracle's naive closure on fixtures (I6), within the same bounds.
  • Always terminates: a hub node (1M reachable) returns a bounded, truncated-marked result within the deadline (I8) — never hangs.
  • p50 < 50 ms, p95 < 300 ms for k≤8 on a 1M-node graph (§4).
  • Determinism: same query + snapshot → identical result_hash (I6).

16.5 Conformance Fixtures

  • closure/upstream_k_hops.json, closure/downstream_blast.json, closure/hub_truncation.json (I8), closure/column_propagation.json, closure/column_degraded.json (I12).

16.6 Pitfalls

  • Forgetting the visited-set → revisiting nodes in a DAG with diamond paths → exponential blowup. Maintain a visited set (it's a DAG but with shared ancestors).
  • Unbounded closure on a hub → hang (I8). Bounds are mandatory, not optional (principle 8).
  • Direction confusion (upstream vs downstream = in vs out edges) → backwards answers. Test both against the oracle.
  • Column propagation silently returning dataset-level → mislead (I12). Always report coverage.

16.7 Performance Concerns

  • Closure ≈ O(V'+E') over the reached sub-DAG, bounded by R (§4.2); #84 adjacency lookups at µs each.
  • Cache hot-hub adjacency (a users table's neighbors) → avoid re-fetching from #84 per query.
  • Bound result streaming so a large closure doesn't materialize fully in memory before the bound hits.

16.8 Edge Cases

  • A node with no upstream (a source) / no downstream (a sink); k=0 (just the node); a disconnected node; a closure that exactly hits max_results (boundary of truncated).

16.9 Failure Analysis

  • A wrong closure (missing nodes) → incomplete impact/root-cause → the oracle differential (I6) + per-fixture checks; a missing column edge upstream (P3) surfaces here as a missing reachable node.
  • A non-terminating closure (cycle slipped past I1, or bound bug) → the deadline (I8) is the backstop + a cycle-fuzz CI.

16.10 Operational Notes

  • QueryTrace.{hops_reached,nodes_visited,truncated,col_coverage}; per-hop fan-out exposed so a "huge but intentional" hub query is understood (§4.2); document closure semantics in docs/api-spec.md.

17. Phase 5 — Impact analysis + root-cause

17.1 Objectives

  • Build the two headline analyses on top of closure (§8.14): impact (downstream blast radius + the runs/jobs on each path) and root-cause (upstream contribution to a flagged value, ranked + predicate-filtered).

17.2 Detailed Implementation Steps (ADR-12; I4/I8/I9/I12; §8.14; Cui et al. TODS 2000)

  • query::impact — forward closure + annotate each path with the RunContext of its edges (which job/run propagates the change) → an actionable "what's affected + by which pipeline" result.
  • query::root_cause — reverse closure from a flagged ColumnRef, ranked by query::rank (run recency × path length × predicate match); optional Predicate filters to the runs touching the value in a bad window.
  • query::rank — the ranking heuristic (recent runs + short paths score higher; a wasDerivedFrom through a recently-failed run ranks first).
  • Column-level sharpening: impact/root-cause prefer column edges (precise blast radius) and report when degraded to dataset-level (I12).

17.3 Deliverable

  • linctl impact <ref> (blast radius + jobs) and linctl root-cause <col> --since T (ranked upstream); examples/root_cause.

17.4 Acceptance Criteria

  • Impact returns the complete downstream set (bounded, I8) + the correct runs/jobs on each path (vs oracle).
  • Root-cause ranking puts the most-likely upstream first on labeled incident fixtures (recent/failed-run-on-path ranks high).
  • Column-level impact is strictly narrower than dataset-level on column-rich fixtures (the precision win, §8.14).

17.5 Conformance Fixtures

  • closure/impact_with_jobs.json, closure/root_cause_ranked.json, closure/incident_localization.json (a seeded bad-value scenario), closure/column_vs_dataset_blast.json.

17.6 Pitfalls

  • Impact without run context → "what" but not "which job to fix" → annotate every path edge with its RunContext (I4).
  • Root-cause ranking that ignores recency → buries the actual cause among ancient lineage → recency is a primary rank factor.
  • A predicate filter that drops too much (excludes a contributing run) → violates conservatism (I9) → filter ranks, don't prune the closure.
  • Confusing the two directions (§8.14) → a tool that does neither well.

17.7 Performance Concerns

  • Same closure cost (§4.2) + a cheap ranking pass; ranking is O(result), negligible vs traversal.
  • Predicate evaluation per edge → keep predicates simple (run-id/time/job filters), not arbitrary expressions.

17.8 Edge Cases

  • A flagged value with no upstream (a source — root cause is the source); multiple equally-ranked causes (return all, tied); an impact query on a leaf (empty blast radius); a predicate matching nothing (empty ranked list, not error).

17.9 Failure Analysis

  • A missed root cause = a missed column/dataset edge upstream (P3/P2) → traces back to capture conservatism (I9); the corpus + incident fixtures are the net; docs/runbooks/incident-rootcause.md.
  • A falsely-narrow blast radius = an under-reported edge → same root cause; impact deliberately over-includes (conservative) to avoid this.

17.10 Operational Notes

  • QueryTrace per analysis; runbooks incident-rootcause.md + impact-before-migration.md; impact/root-cause are the operator-facing value — document their semantics + ranking in docs/api-spec.md.

18. Phase 6 — Temporal / bitemporal model + time-travel

18.1 Objectives

  • Add the second time axis: bitemporal edges (valid-time + transaction-time) and time-travel queries ("lineage as of T"), with corrections via append-only supersede (I13/I3).

18.2 Detailed Implementation Steps (ADR-6/7; I3/I11/I13; §8.12; Snodgrass 2000)

  • graph::bitemporal — every edge carries BiTemporal{valid, tx} (P2 stamped valid+tx already; this phase makes them queryable intervals); supersede = a new edge at a new tx-time, old retained (I3).
  • graph::snapshot (extend) — a Snapshot{as_of_tx, as_of_valid} filters edges: tx_time ≤ as_of_tx and (if set) valid-interval contains as_of_valid (I13).
  • query::time_travel — wrap any closure/impact/root-cause in a bitemporal snapshot (§8.12); the traversal then runs over the filtered cut.
  • Corrections/retractions: an API to supersede a wrong edge (append a retraction at tx=now); the old edge remains visible at tx ≤ now (audit sees the mistake, I3).

18.3 Deliverable

  • linctl upstream <ref> --as-of-tx 2026-01-01 returns the graph as known then; corrections append, never overwrite. examples/time_travel.

18.4 Acceptance Criteria

  • Time-travel == oracle-at-T (an oracle replaying only events with tx ≤ T) on fixtures (I13).
  • A supersede leaves the old edge visible at earlier tx (I3) and the new edge at later tx; no in-place mutation.
  • as_of(valid=V, tx=T) composes both filters correctly (Snodgrass semantics, §8.12).
  • Time-travel read overhead < 2× a latest read (§4).

18.5 Conformance Fixtures

  • temporal/as_of_tx.json, temporal/as_of_valid.json, temporal/bitemporal_combined.json, temporal/supersede_correction.json (I3), temporal/before_data_exists.json (empty result).

18.6 Pitfalls

  • Conflating valid-time and tx-time → wrong audit answers (the canonical bitemporal bug). Stamp + filter both, always (principle 6).
  • A correction that deletes the old edge → destroys audit history (violates I3). Supersede, never delete.
  • Snapshot filtering applied after traversal instead of before → traverses through edges that didn't exist at T → wrong cut. Filter adjacency at the snapshot boundary (I13).
  • Open valid-intervals ([V, ∞)) for "still true" lineage → handle the unbounded upper bound.

18.7 Performance Concerns

  • Bitemporal filter adds a per-edge interval check → keep intervals as two i64s, branch-predictable; index by tx-time in #84 for as_of_tx pruning.
  • Time-travel reads touch more historical edges (superseded ones) → the < 2× overhead target bounds this; GC (P10) caps history growth.

18.8 Edge Cases

  • A query at exactly a supersede boundary (tx == correction time → which edge? define: tx ≤ T includes the correction at T); valid-interval boundary inclusivity; a node created and superseded within the same tx (define ordering).

18.9 Failure Analysis

  • A time-travel answer that includes future-known facts → leaks information across the tx boundary → as_of_tx + oracle-at-T differential is the net; docs/failure-analysis/snapshot-skew.md.
  • Audit non-reproducibility (T gives different answers run-to-run) → determinism (I6) + fixed snapshot ordering.

18.10 Operational Notes

  • QueryTrace.{snapshot_tx, as_of_valid}; document the bitemporal semantics + correction model in docs/prov-mapping.md; time-travel is the audit/compliance feature (GDPR/SOX) — its correctness is contractual (Compatibility & Versioning).

19. Phase 7 — Integrity: Merkle tamper-evidence + signing

19.1 Objectives

  • Make provenance trustable: Merkle-chain every captured event/revision (#71), support optional Ed25519 event signing, and provide verify — so audit lineage is tamper-evident (I10, principle 10).

19.2 Detailed Implementation Steps (ADR-14/15; I10; #71; Anderson 3e; Merkle 1987)

  • integrity::merkle_log — an append-only hash-chained log over #71: each entry = hash(prev_root, canonical(event)); the running MerkleRoot commits the whole history (I10).
  • integrity::sign — optional Ed25519 (RFC 8032): a producer signs an event with its key; the signature is stored with the event; wasAssociatedWith ties it to the signing agent.
  • integrity::verify — recompute the chain over a range; check it matches the stored roots; verify signatures against producer public keys; emit MerkleVerify/verify_fail.
  • integrity::forensics — on a verify failure, locate the first divergent entry (binary search over the chain) → which event/range was tampered.
  • Wire: ingest appends to the Merkle log (I10) as it commits to the graph (§8.11); periodic root anchoring (a published root for external attestation).

19.3 Deliverable

  • Every ingested event chained; linctl verify --range … confirms integrity or pinpoints tampering; signed events verified against producer keys. scripts/verify_chain.sh.

19.4 Acceptance Criteria

  • verify over an intact chain returns true ≥ 1M events/s (§4); a single flipped byte anywhere makes verify fail and forensics locates it (I10).
  • Signed events verify against the right public key; a forged signature is rejected.
  • The Merkle root is stable + reproducible for a given event sequence (determinism).

19.5 Conformance Fixtures

  • integrity/chain_intact.json, integrity/chain_tampered.json (flipped byte → verify fail + located), integrity/signed_event.json, integrity/forged_signature.json.

19.6 Pitfalls

  • Hashing a non-canonical event encoding → chain non-reproducible / false tamper alarms → canonicalize before hashing (same as idempotency, I7/I10).
  • A single global Merkle writer becoming a bottleneck → per-shard chains (one ordered writer each) + a periodic aggregated root (§3.5).
  • Storing signatures but never verifying on read → false sense of trust. verify must actually re-check.
  • Key management out of scope but must be acknowledged (producer key distribution is an operational concern, partially deferred).

19.7 Performance Concerns

  • Chaining adds one hash per event → cheap (hardware SHA); verify is a linear hash sweep (≥ 1M/s).
  • Signing (Ed25519) is on the producer; verification on ingest/read is fast but optional (policy SigningPolicy).
  • The Merkle log is a second durable write per event → batch + a dedicated log writer so it doesn't gate ingest latency (§3.5).

19.8 Edge Cases

  • Empty chain (root = hash of nothing, defined); an unsigned event under a signing-required policy (reject or flag per policy); chain across a server restart (persist the tail root); a re-org attempt (append-only forbids it, I3).

19.9 Failure Analysis

  • Tampering detected → verify_fail + forensics range → docs/runbooks/tamper-alert.md (escalate, quarantine the range, audit). The blast radius is "which events can no longer be trusted."
  • A chain-reproducibility bug → false positives erode trust → canonicalization tests + a "verify after every CI ingest" check.

19.10 Operational Notes

  • IngestTrace/integrity metrics: merkle_root, verify_fail; publish periodic roots for external attestation; document the trust model + key handling in docs/threat-model.md; this is the compliance/audit backbone.

20. Phase 8 — Scale ingestion: CDC / stream / log / build connectors

20.1 Objectives

  • Capture lineage from non-OL sources: #103 CDC, #105/#215 stream, #214 table-format snapshots, #136 builds, and runtime/log instrumentation — all normalized to the same PROV facts (§8.4).

20.2 Detailed Implementation Steps (ADR-8/13; I5/I7/I8; §8.4; Halevy et al. SIGMOD 2016; Muniswamy-Reddy et al. 2006)

  • capture::connectors — adapter trait: a connector consumes a source's events and emits the normalized OlRunEvent/PROV facts (so the rest of the pipeline is source-agnostic).
  • CDC adapter (#103/#215): a change-event (table T, op, snapshot) → wasGeneratedBy/wasDerivedFrom at the table/row-set granularity; idempotent (I7) on the CDC offset.
  • Stream adapter (#105): a stream job's input/output topics/tables → dataset edges; window/job context in RunContext.
  • Table-format adapter (#214): snapshot S' derived from S → wasDerivedFrom(S', S) (snapshot provenance).
  • Build adapter (#136): content-addressed build (inputs → artifact) → wasDerivedFrom(artifact, input) (the same shape, build domain).
  • Instrumentation/log adapter: parse runtime logs/provenance-aware storage events (Goods/PASS style) → PROV facts.

20.3 Deliverable

  • Lineage captured from at least CDC + stream + build sources via connectors, normalized into the graph; linctl queries span sources (cross-source join via content ids, I5).

20.4 Acceptance Criteria

  • Each connector's output, fed to the graph, == oracle fed the equivalent normalized events.
  • Idempotent across source-specific retries (I7): CDC offset / build hash / snapshot id dedup.
  • Cross-source lineage joins: a dataset produced by a Spark job (OL) and consumed by a CDC stream resolves to one node (I5).

20.5 Conformance Fixtures

  • openlineage/cdc_normalized.json, openlineage/stream_normalized.json, openlineage/build_provenance.json, openlineage/cross_source_join.json (I5).

20.6 Pitfalls

  • Each source's identity scheme differs → must map to the canonical DatasetRef/content id (I5) or nodes fork and cross-source lineage breaks. The normalization layer is the critical correctness point.
  • CDC volume can dwarf OL events → backpressure + batching (I8); per-table aggregation to avoid an edge per row.
  • Source-specific idempotency keys (CDC offset vs OL run id) → each connector defines its dedup key (I7).
  • A connector leaking source-specific types upward → keep adapters at the boundary (mirror principle 9 for sources).

20.7 Performance Concerns

  • CDC/stream are high-volume → the ingest throughput target (§4) is stressed here; aggregate row-level changes to dataset/row-set edges.
  • Connectors run as separate ingest producers → the bounded ingest queue (I8) governs them all.

20.8 Edge Cases

  • A CDC event for a table never seen via OL (create the node from CDC); a build with no recorded inputs (a source artifact); a stream job with dynamic topics (resolve at runtime); a snapshot chain (S→S'→S'' — a derivation path).

20.9 Failure Analysis

  • A connector mis-mapping identities → forked nodes → broken cross-source lineage → cross_source_join fixture + content-id stability tests (I5); docs/failure-analysis/lineage-gap.md.
  • A high-volume source overwhelming ingest → backpressure (I8) protects the server; the source's lag is the symptom (a freshness metric).

20.10 Operational Notes

  • IngestTrace.source distinguishes connectors; per-source freshness + volume dashboards; document each connector's identity mapping + dedup key; specific vendor SDKs remain PhaseDeferred (we ship the adapter trait + the listed sources).

22. Phase 10 — Retention, compaction, GC

22.1 Objectives

  • Bound storage growth of an append-only, bitemporal graph: policy-driven retention, compaction, and GC that reclaim space without rewriting history within the retention window (principle 2/I3).

22.2 Detailed Implementation Steps (ADR-22; I3/I10/I11/I13; §11.11 RetentionPolicy)

  • graph::gc_hooks — a RetentionPolicy (keep N versions / valid-time window / compact-after age, §11.11); identify GC-eligible revisions (older than retention, superseded).
  • Compaction: collapse a long chain of superseded edges into a summary beyond the retention window (e.g. keep the current + a checkpoint, drop intermediate superseded versions) — append-only-safe (the kept facts are immutable; only out-of-window history is reclaimed).
  • The dedup table (P2/I7) GC: bound it (LRU + a persisted seen-set with a TTL aligned to retention) so it doesn't grow unbounded.
  • The Merkle log (P7) retention: archive/anchor old chain segments (keep the root, archive the body) — preserves verifiability of retained ranges.
  • Hooks into #84's storage reclamation (we drive policy; #84 reclaims, principle 9).

22.3 Deliverable

  • A configurable retention policy that bounds graph + dedup + Merkle-log growth; linctl gc --dry-run reports what would be reclaimed; storage stays bounded under continuous ingest.

22.4 Acceptance Criteria

  • Storage growth bounded by the policy under a sustained ingest workload (§4); within-window history fully preserved (time-travel still correct, I13).
  • GC never removes a fact still inside the retention/valid-time window; never breaks an intact Merkle chain for retained ranges (I10).
  • Determinism: GC is idempotent (running it twice = once).

22.5 Conformance Fixtures

  • temporal/retention_window.json, temporal/compaction_preserves_window.json (time-travel within window still == oracle), integrity/archived_chain_verify.json.

22.6 Pitfalls

  • Compaction that drops an in-window superseded edge → breaks time-travel for an audit date inside retention (I13). The window boundary is the hard line.
  • GC racing with a reader at an old snapshot → the reader's snapshot must pin its needed history (or be told it aged out). Coordinate GC with active snapshots (MVCC, I11).
  • An unbounded dedup table silently OOMs the server over months → it must be GC'd too (often forgotten).
  • Breaking the Merkle chain on archive → verifiability lost → archive the body, keep the root + a re-anchor (I10).

22.7 Performance Concerns

  • GC is a background job → must not gate ingest/query (run off the hot path).
  • Compaction reduces traversal cost (fewer superseded edges) → a perf win for time-travel reads.
  • Reclamation is #84's; we batch GC operations to amortize.

22.8 Edge Cases

  • Retention = ∞ (keep everything — valid, just unbounded); a fact exactly at the window boundary; GC with active old-snapshot readers; a never-superseded edge (keep until valid-time window expires).

22.9 Failure Analysis

  • Over-aggressive GC corrupting in-window time-travel → the compaction_preserves_window fixture is the gate; the blast radius is "audit answers for reclaimed dates are gone" (irreversible) → conservative defaults.
  • Unbounded growth (GC disabled/buggy) → storage exhaustion → growth dashboards + alerts.

22.10 Operational Notes

  • gc_reclaimed, dedup_table_size, storage-growth metrics; linctl gc --dry-run before applying; document the retention policy + its audit implications (a reclaimed window can't be queried) in runbooks; GC policy is a compliance decision (how long must lineage be retained).

33. Scalability Analysis

  • Graph scaling: 10M nodes / 100M edges per server before sharding; closure cost is O(reached sub-DAG) bounded by R (I8) → interactive even at scale because results, not the graph, are bounded.
  • The capture-fidelity wall: the limit is complete, correct capture, not raw size — a query is only as good as the edges (§2.7); column recall=1.0 (I9) + idempotency (I7) are the scaling-relevant correctness properties.
  • Sharding (the large-scale lever): partition the graph by namespace/domain across multiple #84 instances + lineaged shards; cross-shard lineage edges (a dataset in shard A feeding shard B) need a cross-shard closure (scatter-gather over shards) — deferred (PhaseDeferred), but content-addressed ids (I5) make cross-shard joins well-defined.
  • Ingest scaling: horizontal lineaged ingest nodes behind a load balancer; per-node bounded queue (I8); the dedup table must be shared/partitioned consistently (a sharding correctness point).
  • Hub-node hazard: a few super-connected datasets (users, events) dominate closure cost → adjacency caching + bounds (§4.2); their blast radius is intentionally large (not a bug).
  • Storage scaling: append-only + bitemporal grows unbounded without GC → retention/compaction (P10) is the scaling control; history within the window is preserved (I13).
  • What does NOT scale here (by design): the graph engine (that is #84's job); the sources (CDC/stream are #103/#105). This system scales the capture, modeling, and querying of provenance over a delegated graph store.
  • Search scaling: the inverted index is a derived cache (I14), rebuildable + shardable independently of the graph.

34. Mental Models & First Principles

Eight compressed models that reorganize how you think about data lineage. Each names what it predicts, the bug class that arises when you build without it, and the section that depends on it most.

MM1 — Lineage is a DAG, not a log. The compressed insight: provenance is structured (a directed acyclic derivation graph), not a flat sequence of events. A log tells you what happened; the DAG tells you what depends on what — those are fundamentally different query shapes. A log supports "what ran?" — the DAG supports "what is affected if X changes?" and "what produced Y?" What it predicts: transitive closure (impact/root-cause) is a graph traversal, not a log scan. Column-level edges are graph edges, not log fields. Time-travel is a snapshot of the DAG at a (valid, tx) cut, not a log replay. Bug class without it: building a flat event store and trying to answer closure queries with correlated log scans — O(n²) and wrong. Every lineage "query" degrades into a full-table join. Resolving section: §8.3 (the lineage graph), §16 (closure queries), §33 (scalability — why bounded traversal is the scaling lever, not scan optimization).

MM2 — Capture fidelity is the binding constraint, not query speed. The compressed insight: the system is capture-fidelity-bound (§2.7). You can build the fastest graph traversal engine in the world; if a column edge is missing, the root-cause answer is silently wrong. Query speed is a second-order concern. What it predicts: every design decision where capture correctness and query performance trade off must resolve in favor of capture (principle 7). The recall=1.0 contract (I9) is not negotiable even under parser performance pressure. Bug class without it: optimizing the SQL parser for speed by dropping "rare" predicate-column dependencies — results in recall < 1.0, corrupted root-cause, and no observable symptom until an incident. Resolving section: §2.7, §4.3, §15 (Phase 3), §6 (principle 7), §7 (I9).

MM3 — Idempotency is a graph-correctness property, not a network property. The compressed insight: most engineers think of idempotency as "retries are safe at the network layer." In a lineage graph, idempotency is a graph-correctness property: a re-delivered event must produce exactly the same edge set in the graph — not an extra copy. Duplicate edges distort every closure, impact analysis, and root-cause ranking that follows. What it predicts: content-addressed node ids (I5) and event-level dedup keys (I7) are both required — one collapses duplicate nodes, the other collapses duplicate edges from the same run. Neither alone is sufficient. Bug class without it: a network partition causes a producer to retry 3×; the graph now has 3 copies of every edge from that run; impact blast radius is 3× inflated; root-cause ranking is wrong. Resolving section: §8.13 (idempotency + content-addressing), §14 (Phase 2), §7 (I5/I7).

MM4 — Time is two-dimensional; conflating the axes is an audit bug. The compressed insight: valid-time ("when was this lineage true in the world?") and transaction-time ("when did we learn it?") are independent axes. "Lineage as of 2025-01-01" is ambiguous without specifying which axis. GDPR audit asks "what data flowed into report R as of the breach date?" — that is a tx-time query ("what did we know then?"), not a valid-time query. What it predicts: every time-travel query must state which axis or both (§8.12). A supersede/correction appends at a new tx-time without altering the old valid-time record — the audit sees the mistake and the fix, both correctly. Bug class without it: a single-axis temporal store that conflates valid-time and tx-time produces audit answers that leak future-known facts (a query at tx=T1 returns an edge recorded at tx=T2>T1) — an audit admissibility failure. Resolving section: §8.12 (bitemporal semantics), §18 (Phase 6), §6 (principle 6), §7 (I13).

MM5 — Conservative column lineage: false negatives are invisible, false positives are visible. The compressed insight: a missed column dependency (false negative) silently corrupts every downstream root-cause and impact analysis — the blast radius is falsely narrowed and the wrong column is exonerated. An extra column dependency (false positive) merely widens the blast radius — the operator sees more candidates, some spurious, but the real cause is still present. What it predicts: the corpus acceptance test must enforce recall = 1.0 as a hard gate (I9); precision ≥ 0.85 is best-effort. Any "optimization" that drops a dependency is a correctness regression, not a performance win (principle 7). Bug class without it: a parser that drops GROUP BY columns from dependencies (common mistake) — sales_daily.region has no upstream; a region-dimension change is invisible to impact analysis. Resolving section: §4.3, §8.5, §15 (Phase 3), §7 (I9).

MM6 — The graph engine is borrowed; the semantic layer is owned. The compressed insight: #84 Graph DB is a dependency for node/edge storage and adjacency traversal primitives. This system owns the semantic layer on top: PROV-DM relations, bitemporal edge annotations, cycle detection, snapshot reads, and the lineage query semantics. The two must never bleed into each other. What it predicts: all #84-specific code lives in exactly one module (graph::store_84). If #84's API changes, exactly one module needs updating. Every higher crate speaks PROV semantics, never #84 primitives. Bug class without it: a crate that imports #84's node type directly and scatters #84 API calls — when #84 upgrades its node representation, the entire codebase breaks, not a single adapter. Resolving section: §3.2 (graph box narrative), §9 (ADR-4/9), §13 (Phase 1), §6 (principle 9).

MM7 — Merkle-chaining is not optional decoration; unverifiable provenance is inadmissible. The compressed insight: for compliance use cases (GDPR, SOX, audit), a lineage record that cannot be proven untampered is legally inadmissible. Appending a Merkle chain to every event is cheap (one hash per event); omitting it makes the entire history untrustworthy for audit. "We think the lineage is correct" is not a compliance answer. What it predicts: the integrity layer (P7) must be wired into the ingest path from the start, not bolted on later. The verify operation (≥1M events/s, §4) must be cheap enough that auditors run it as a matter of routine. Forensics (binary search over the chain) must locate a tampered entry precisely. Bug class without it: a lineage store that logs events to a plain file — an attacker (or a bug, or an ops mistake) edits entry 7 of 10,000; there is no way to detect it; the audit answer for that entry is untrustworthy. Resolving section: §19 (Phase 7), §6 (principle 10), §7 (I10), §26 (threat model).

MM8 — Bounded traversal is a correctness property, not a performance trade-off. The compressed insight: bounding closure queries (max hops, max results, deadline) is not a performance optimization — it is a correctness invariant for a production system. An unbounded closure on a hub node (e.g., a central users table) is not "slow" — it is a server hang that blocks all other queries. The bound, with a truncated flag on partial results, is the correct answer: honest about incompleteness, always available. What it predicts: the bounds (I8) are enforced unconditionally, not configurable to "unlimited." A caller who needs deeper traversal makes multiple bounded calls or narrows the starting set. Every result envelope carries truncated: bool so the caller knows. Bug class without it: a closure API with a default max_hops=∞ that works fine on test data (small graphs) and hangs the production server the first time an operator runs impact("users") on the 10M-node production graph. Resolving section: §4.2, §8.7, §16 (Phase 4), §6 (principle 8), §7 (I8).

OpenLineage / Marquez chose a relational (Postgres) backing for its reference lineage store because it targets the common case — simple dataset-level lineage that fits naturally into foreign-key joins (runs → jobs → datasets). The winning regime: teams that already operate Postgres and need a lightweight, standards-compatible lineage store with no graph-engine dependency. The trade-off: closure queries become multi-hop SQL self-joins, which are painful at scale and absent from the public API. The event spec itself (producer-side OpenLineage) is the real contribution and is system-agnostic.

Apache Atlas chose a property-graph engine (JanusGraph/HBase) and a rich type system because its target is enterprise governance — metadata types (Hive tables, HDFS files, Spark processes) modeled as first-class entities with relationships and classification. The winning regime: a Hadoop/HBase ecosystem where the backing store is already operated, the governance scope is broad (classifications, policies, tags), and lineage is one feature among many. The trade-off: the JVM/HBase stack is heavy, column-level lineage is limited, and the temporal model is thin for audit.

DataHub chose a Kafka-event + Elasticsearch + graph-metadata architecture because it targets the full metadata platform problem — not just lineage, but search, discovery, ownership, schema history, and column-level lineage surfaced in a rich UI. The winning regime: organizations that want a unified metadata platform and can operate the Kafka/ES stack. The trade-off: the surface area is intentionally large; lineage is one layer in a much broader system, and the temporal model is not first-class bitemporal.

Egeria chose an open-metadata interchange standard + pluggable repository because its target is multi-system governance — federating metadata across many enterprise tools (databases, ETL systems, BI platforms) that each own part of the metadata graph. The winning regime: large enterprises with heterogeneous toolchains that need standards-based interoperability and cannot centralize all metadata in one store. The trade-off: the scope is vast and the lineage query model is not the focus; closure queries over the federated graph are not a first-class API.

Google Goods chose pull-based scraping + log mining because it targets a world where producers cannot be instrumented — Goods ingested dataset metadata from Google's internal systems (Bigtable, Spanner, GFS) by reading storage logs and crawl data, not by asking jobs to emit events. The winning regime: environments where producers are legacy, third-party, or otherwise unmodifiable and annotation is infeasible. The trade-off: lineage is approximate and coarse (dataset-level only, no column-level); the scraping pipeline adds latency and the metadata is less complete than push-based capture.

36. Back-of-Envelope Capacity Model

All numbers derived step-by-step from §4 System Constraints. Formula shown before the derived number.

E1 — OL event payload size A typical OpenLineage RunEvent (JSON): run/job metadata (~200 bytes) + 2–5 input/output datasets with schema (~300 bytes each) + facets (~100 bytes) ≈ 1 KB per event (no SQL). With SQL facet: add the SQL string, median ~500 bytes → ~1.5 KB per event with column lineage. Derived: median event payload = 1–1.5 KB.

E2 — Ingest bandwidth Formula: bandwidth = event_rate × payload_size Dataset-level: 50,000 events/s × 1 KB = 50 MB/s ingest bandwidth. Column-level: 5,000 events/s × 1.5 KB = 7.5 MB/s ingest bandwidth. Derived: dataset-level ingest requires ~50 MB/s network + write bandwidth; column-level ~7.5 MB/s. Implication: a 1 Gbit/s network link is not the bottleneck; #84 write throughput and SQL parse CPU are.

E3 — Graph storage (nodes + edges) Formula: storage = nodes × node_size + edges × edge_size Assumptions (§4 graph scale): 10M nodes / 100M edges. Node: NodeId (32 bytes) + DatasetRef/ColumnRef (avg 80 bytes) + metadata ≈ 150 bytes/node. Edge: EdgeId (32 bytes) + src/dst NodeIds (64 bytes) + relation (1 byte) + RunContext (avg 100 bytes) + bitemporal timestamps (16 bytes) ≈ 220 bytes/edge. 10M × 150 B + 100M × 220 B = 1.5 GB + 22 GB ≈ 24 GB raw graph data. With #84 storage overhead (indexes, B-tree padding) ≈ 3–4× → ~75–100 GB for a fully-loaded single server. Derived: a 10M-node / 100M-edge graph fits in ~100 GB of storage.

E4 — Average edge count per node Formula: avg_edges = total_edges / total_nodes = 100M / 10M = 10 edges/node Median is lower (most datasets have 1–3 edges); hub nodes (e.g. users) may have 10k–100k edges. The mean is pulled up by hubs. Derived: mean 10 edges/node; plan for hub nodes at 4–5 orders of magnitude above mean.

E5 — Closure RAM cost (working set) Formula: closure_ram = max_result_nodes × (node_size + visited_set_entry) × concurrent_queries max_result_nodes R = 10,000; node_size in result = ~200 bytes; visited-set entry = ~40 bytes (NodeId + hash). Per query: 10,000 × 240 B = 2.4 MB. At 100 concurrent closure queries: 100 × 2.4 MB = 240 MB. Derived: closure working set = ~250 MB at 100 concurrent queries. Fits easily in a 16 GB server.

E6 — Merkle hash rate Formula: hash_rate = verify_target / hash_cost_per_event Target: ≥ 1M events/s verify throughput (§4). SHA-256 on modern hardware: ~500 MB/s; at 1.5 KB/event: 500 MB/s / 1.5 KB ≈ 333k hashes/s per core. To hit 1M events/s: ceil(1M / 333k) = 3 cores dedicated to verify. Derived: Merkle verify at 1M events/s requires ~3 CPU cores on modern hardware.

E7 — Dedup table size Formula: dedup_table = event_rate × retention_window × entry_size Retention window for dedup (how long to remember seen events to catch retries): 24 hours (a generous retry window). 50,000 events/s × 86,400 s × 72 bytes/entry (EventId + timestamp) = 50k × 86,400 × 72 B ≈ 311 GB. That is too large to keep entirely in RAM → use a Bloom filter (false-positive rate ≤ 0.1%) + a persisted hash set for definitive checks. Bloom filter for 50k × 86,400 = 4.32B events at 0.1% FPR: n × log2(1/p) / ln(2) ≈ 4.32B × 10 bits / 0.693 ≈ 6.2 GB of bits → feasible in RAM. Derived: dedup requires a ~6 GB Bloom filter + a persisted LRU set; naive RAM table is infeasible at 50k/s over 24 h.

E8 — Column-edge storage overhead Formula: col_edge_overhead = dataset_edges × avg_columns × edge_size If each dataset has an average of 15 columns and all are captured: 100M dataset-level edges × 15 = 1.5B potential column edges. In practice, column lineage is available for ~40% of datasets (those with SQL facets): 0.4 × 1.5B × 220 B = 132 GB additional storage. Derived: column-level lineage approximately doubles total edge storage vs dataset-level alone (~100 GB → ~230 GB).

E9 — SQL parse budget vs freshness target Formula: parse_budget = freshness_target − overhead = 2,000 ms − 200 ms = 1,800 ms Non-parse overhead: validate (~50 µs) + dedup (~100 µs) + graph append (~10 ms) + Merkle append (~1 ms) ≈ 12 ms. Available for SQL parse: 1,988 ms → ~2 s for even the most complex query. At I15 bounds (max_depth=50, max_tokens=10k, max_time=500ms), parse is capped at 500 ms. Derived: the I15 parse time limit of 500 ms is the binding constraint on freshness, not the graph write.

E10 — Storage growth rate under retention policy Formula: growth_rate = event_rate × edge_size × (1 − compaction_ratio) At 50k events/s, each producing ~5 edges on average: 50k × 5 × 220 B = 55 MB/s raw edge writes. Per day: 55 MB/s × 86,400 s ≈ 4.7 TB/day without compaction. With compaction (superseded edges GC'd after retention window, keeping ~10% of history): 4.7 TB/day × 0.1 = 470 GB/day net growth. At a 30-day retention window: 470 GB/day × 30 ≈ 14 TB steady-state storage. Derived: a 30-day retention window at 50k events/s with 90% compaction requires ~14 TB steady-state. Plan for 20–25 TB with headroom.

37. Hard Questions (Self-Examination)

Twenty staff-level questions. Each names the resolving section (which must exist in this document). Each requires synthesis of two or more sections to answer correctly.

  1. Why does recall=1.0 matter more than precision for column lineage, and what invariant + section enforces it? Recall=1.0 means no real dependency is missed. A false negative (missed edge) silently corrupts every downstream impact and root-cause query — the blast radius is falsely narrowed, the root cause is falsely exonerated, and neither failure is observable without the ground-truth corpus. A false positive (extra edge) merely widens the blast radius — the operator sees a spurious candidate but the real cause is still present. The asymmetry means the cost of a miss is unbounded (invisible, corrupts production answers), while the cost of a spurious edge is bounded (visible, recoverable). Enforced by I9 + corpus CI gate. Resolving: §4.3 (conservatism contract), §8.5 (column extraction rule), §15 (Phase 3), §6 (principle 4).

  2. How does the bitemporal model prevent an audit answer from leaking future-known facts? Every edge carries two timestamps: valid-time (when the lineage was true in the world) and transaction-time (when we recorded it). A time-travel query as_of(tx=T) filters edges to tx_time ≤ T before traversal — edges recorded after T are invisible to this query. This means a correction applied at tx=T2>T1 does not contaminate a query at T1: the old (possibly wrong) edge is still the answer at T1, and the correction is visible only at T2 onward. A single-axis store (only valid-time or only tx-time) cannot make this guarantee. Resolving: §8.12 (bitemporal semantics), §18 (Phase 6), §7 (I13), §26 (threat model: information leak via time-travel).

  3. Why must cycle detection happen at write time, not at query time? A derivation cycle (A wasDerivedFrom B wasDerivedFrom A) makes transitive closure non-terminating: BFS from A visits B, then visits A again, and loops. If detected at query time, the only safe response is a deadline-based abort (I8) — which returns a wrong/incomplete answer. If detected at write time (I1), the cycle-closing edge is rejected before it enters the graph, so the invariant "the derivation graph is acyclic" is maintained globally and no query can ever encounter a cycle. The deadline (I8) is a backstop for cycles that slip past (e.g., a multi-hop cycle involving multiple concurrent writes), not the primary defense. Resolving: §3.5 (concurrency model), §7 (I1/I8), §13 (Phase 1), §16 (Phase 4).

  4. What is the difference between content-addressed node ids and idempotency-key dedup, and why are both required? Content-addressed node ids (I5) ensure that two events naming the same logical dataset (even from different producers/sources) hash to the same NodeId — preventing node-forking and enabling cross-source lineage joins. Idempotency-key dedup (I7) ensures that the same event delivered N times produces exactly one edge set — preventing duplicate edges from retries. The two are complementary: without I5, two events produce two nodes for the same dataset and the graph is fragmented; without I7, one event replayed N times produces N edge copies and closure counts are inflated. A retry of event E from producer A and a separate event E' from producer B naming the same dataset both need both mechanisms: I5 collapses the node, I7 collapses the duplicate edges from E's retries. Resolving: §8.13 (idempotency + content-addressing), §7 (I5/I7), §14 (Phase 2).

  5. Why is the in-memory oracle the correctness backbone, and what would break without it? The oracle is a simple, obviously-correct reference implementation — naive HashMaps + BFS, no bitemporal, no bounds, no performance considerations. Every capture path and every query type is checked against it (ADR-25, principle 15). Without it, the only correctness check is "the system agrees with itself" — which catches bugs only if two code paths agree, not if both are wrong. The oracle catches bugs where the graph and query engine are self-consistent but wrong (e.g., a wasDerivedFrom edge stored in the wrong direction — the system traverses it consistently but backwards). The SQL corpus + tamper tests + differential replay all use the oracle as the ground truth. Resolving: §3.2 (bench/conformance box), §6 (principle 15), §12 (Phase 0), §25 (Phase 13).

  6. How does the SQL column-lineage parser handle a CASE expression, and what is the capture-conservatism rule for predicates? A CASE WHEN cond THEN expr_a ELSE expr_b END AS out_col creates a dependency of out_col on every column referenced in cond, expr_a, and expr_b — all three, not just the branch taken at runtime. The conservatism rule (§4.3) states: every column referenced in the expression that produces an output column is an upstream dependency, including predicate/filter/gate columns. This is why-provenance (§8.5): even if cond is status = 'paid' and status is a filter condition, out_col's value depends on which rows pass the filter — so status is a dependency. Omitting predicate columns is the second most common recall failure after dropping aggregate inputs. Resolving: §4.3, §8.5, §8.6, §15.6 (pitfalls), §7 (I9).

  7. Why does the capture→queryable freshness target (p95 < 2 s) not constrain query throughput? The freshness budget (§4.1) is the latency from event receipt to the edge being visible in a snapshot read. Query throughput is independent: readers take a snapshot (a fixed (valid, tx) cut) and traverse without locking writers (MVCC, I11). A read at snapshot S does not block an ingest write, and an ingest write does not block a read at S. The freshness constraint is end-to-end write latency (validate → dedup → parse → graph append → Merkle append); the query constraint is traversal latency over a committed snapshot. The two pipelines are orthogonal. Resolving: §3.5 (concurrency model), §4.1 (freshness budget), §7 (I11), §24 (Phase 12: performance hardening).

  8. When does a column-level impact query give a strictly narrower blast radius than a dataset-level query, and when does it not? Column-level impact is narrower when: (a) the column that changed (orders.amount) has a subset of dependents compared to the whole dataset (orders) — only sales_daily.total depends on orders.amount, whereas orders feeds 20 downstream datasets. Column-level eliminates the 19 irrelevant datasets. When it is NOT narrower: if the changed column feeds every downstream dataset (e.g., a primary-key column orders.id that participates in every join), column-level and dataset-level blast radii converge. Also: when column edges are absent (I12), the system degrades to dataset-level and reports it — the result is no worse than dataset-level, but the precision win is lost. Resolving: §8.14 (impact vs root-cause), §17 (Phase 5), §7 (I9/I12), §4.3.

  9. What happens if two producers assign different namespaces to the same physical dataset, and how does the system handle it? Two producers with different namespace conventions (e.g., postgres://prod/public.orders vs warehouse://prod/orders) produce different DatasetRef values → different content-addressed NodeIds → two separate nodes in the graph. Cross-source lineage between these "two" datasets is broken. The correct fix is namespace normalization in the connector/capture layer (§20.6 pitfalls): the adapter maps source-specific identities to a canonical DatasetRef before content-addressing. If the normalization is missing, cross-source lineage gaps appear as "no lineage" for a real flow — a lineage gap (§27 failure class). Content-addressed ids (I5) make cross-source joins automatic once normalization is correct, but cannot compensate for missing normalization. Resolving: §8.2, §8.13, §20.6, §27 (lineage gap failure class), §7 (I5).

  10. Why is the dedup table bounded by a Bloom filter rather than a plain in-memory hash set, and what are the failure modes of each? A plain in-memory hash set for 50k events/s over a 24-hour retry window requires ~311 GB (§36 E7) — infeasible. A Bloom filter at 0.1% false-positive rate requires ~6.2 GB. The Bloom filter trades a small false-positive rate (a unique event is occasionally treated as a duplicate — a very rare no-op) for feasible memory. The failure mode of a Bloom filter: a false positive (an event that was NOT previously seen is treated as a duplicate and dropped). This is a lineage gap — a real edge is not recorded. The mitigation: a persisted LRU hash set for definitive checks on Bloom-filter positives (two-level dedup: Bloom says "maybe seen" → consult the persisted set for certainty). Resolving: §36 (E7 dedup table capacity), §8.13 (idempotency), §22 (Phase 10: GC of the dedup table), §27 (lineage gap failure class).

  11. How does the system ensure that a correction (a retracted wrong edge) does not contaminate audit answers for dates before the correction? A correction is represented as a new edge at tx_time = now (the correction time), not as a deletion or in-place mutation of the old edge (I3, append-only). The old edge remains in the graph at its original tx_time. A time-travel query as_of(tx=T1) where T1 < correction_time filters edges to tx_time ≤ T1 — the old (wrong) edge is included, the correcting edge is excluded. The audit sees the world as it was known at T1 — including the mistake. A query as_of(tx=T2) where T2 ≥ correction_time includes the correcting edge. This is the correct Snodgrass bitemporal semantics: the correction creates a new entry in the tx-time dimension without altering the past. Resolving: §8.12 (bitemporal), §18.6 (pitfalls: correction-that-deletes), §7 (I3/I13), §29 (temporal semantics stability guarantee).

  12. What is the hub-node hazard and what are the three independent mechanisms that guard against it? A hub node is a central dataset (e.g., users, events) that feeds thousands of downstream datasets. An impact query from a hub node has a blast radius of potentially millions of nodes — an unbounded traversal would hang the server. Three independent mechanisms guard against this: (1) Bounded BFS (I8): max_hops k (default 8) and max_results R (default 10k) terminate the traversal and mark the result truncated=true — the server always returns. (2) Hot-hub adjacency cache (§16.7, §32): the hub's neighbor list is cached in RAM so the first N adjacency lookups are sub-microsecond rather than #84 round-trips. (3) Per-hop fan-out telemetry (QueryTrace.hops_reached): the operator can see the fan-out profile and understand "this hub is intentionally large" rather than treating it as a bug. Resolving: §4.2, §7 (I8), §16.7, §32, §33.

  13. Why does the SQL parser need to handle SELECT * specially, and what is the graceful-degradation path? SELECT * means "all columns from the source table(s)." To emit column-level wasDerivedFrom edges, the parser must know what columns * expands to — which requires the source table's schema (from the SchemaCatalog). If the schema is known: expand * to the explicit column list and emit per-column edges normally. If the schema is unknown: the parser cannot enumerate the columns, so per-column edges cannot be emitted. The graceful-degradation path (I12) is: emit a dataset-level wasDerivedFrom edge (always available) and set parse_complete = false / flag ColumnIncomplete. The query layer reports col_coverage < 1.0 so the operator knows column edges are absent here. Silently returning no edges (neither column nor dataset) would be a lineage gap — the worst failure (§27). Resolving: §8.5, §15.6 (pitfalls), §7 (I9/I12), §27 (lineage gap).

  14. How does the MVCC snapshot model allow concurrent ingest and query without locking, and what is the theoretical guarantee? The graph is append-only (I3): ingest writers only add new nodes/edges to new revisions; they never modify or delete existing data. A query reader takes a snapshot — a fixed (valid_time, tx_time) cut — at the start of its traversal. Because writes only append and never mutate, the snapshot's data is immutable from the reader's perspective: no writer can change what was committed at or before the snapshot point. The reader traverses a stable, consistent cut without holding any lock. The theoretical guarantee: a reader at snapshot rev=k never sees rev>k and never sees a partially-committed revision (revisions are committed atomically, I11). This is the MVCC property: readers and writers are fully concurrent, neither blocks the other. Resolving: §3.5 (concurrency model), §7 (I3/I11), §13 (Phase 1), §24 (Phase 12: performance hardening).

  15. What is the difference between impact analysis and root-cause at the algorithmic level, and when does conflating them produce wrong answers? Impact analysis: forward BFS (downstream) from the changed/broken entity, collecting all reachable entities + the RunContext on each path. Root-cause: reverse BFS (upstream) from the flagged entity, ranked by run recency × path length × predicate match. The directions are opposite; the ranking criteria are different (impact cares about completeness and which jobs propagate; root-cause cares about recency and which job last touched the bad value). Conflating them produces wrong answers when: (1) a "bidirectional" tool traverses both directions and returns the union — the operator cannot tell what is affected vs what contributed; (2) applying impact ranking to root-cause (completeness over recency) buries the most recent contributing run behind ancient lineage; (3) applying root-cause ranking (recency filter) to impact (prunes the closure to recent runs only) falsely narrows the blast radius. Resolving: §8.14, §17 (Phase 5), §16 (Phase 4).

  16. Why must the Merkle log have a single ordered writer per shard, and what breaks if it has multiple concurrent writers? A hash chain is a sequence: entry[n] = hash(entry[n-1], event_n). For the chain to be well-defined and verifiable, entries must be appended in a strict total order — each entry's hash includes the previous entry's hash. Two concurrent writers would each compute a "next hash" over the same entry[n-1] → two different entry[n] values → a fork in the chain → the chain is no longer a linear sequence → verify cannot reconstruct a single chain → tamper detection is broken. The mitigation (§3.5/§19.6): a single ordered writer per shard (or per-shard chains + a periodic aggregated root). The ingest path enqueues events; the log writer serializes them. Resolving: §3.5, §19.2, §19.6 (pitfalls), §7 (I10).

  17. How does the system recover from a search index drift (I14), and why is the graph always the source of truth? If the search index diverges from the graph (a committed graph write that the index missed), search results are wrong — datasets that exist in the graph are missing from search. Recovery: the index is a derived cache (I14, ADR-18) — it is rebuilt by re-scanning the committed graph. The graph is the source of truth because it is the durable, Merkle-chained record of all lineage facts; the index is merely a query-acceleration structure. If the index is wrong and the graph is correct, a rebuild restores the index to a consistent state. If both are wrong, the graph is still authoritative (Merkle-verifiable). The index can never be more correct than the graph; it can only be a subset. Resolving: §7 (I14), §21 (Phase 9), §27 (stale search failure class), §29 (Compatibility & Versioning).

  18. What is the PROV-DM entity/activity/agent distinction, and why does it matter for column-lineage modeling? In PROV-DM: an Entity is a thing (a dataset version, a column version); an Activity is something that occurred over time and acted on entities (a job run); an Agent is something responsible for an activity (a person, a service). The wasDerivedFrom relation is between two Entities (a column derived from another column). The used and wasGeneratedBy relations connect Activities to Entities. The wasAssociatedWith relation connects an Activity to an Agent. For column lineage: sales_daily.total (Entity) wasDerivedFrom orders.amount (Entity) is the lineage edge. The Activity (run r1) is how — not the lineage edge itself. Confusing an Activity with an Entity (e.g., modeling a job as an Entity and putting it in a wasDerivedFrom chain) breaks the PROV role invariant (I2) and corrupts the closure semantics (the job appears in the blast radius as if it were a dataset). Resolving: §8.1 (PROV-DM core), §11.1 (type signatures), §7 (I2), §12 (Phase 0).

  19. Why does content-addressing the node id require a carefully chosen canonical field set, and what happens if the set is wrong? The NodeId is hash(kind, namespace, name, version) — a deterministic function of the fields that define the logical identity of a dataset/column. If the canonical field set is too narrow (e.g., omitting namespace): two datasets with the same name but different namespaces (prod.orders vs staging.orders) hash to the same id → they are conflated into one node → lineage from prod and staging is indistinguishable → incorrect blast radius + root-cause. If the field set is too broad (e.g., including a description field that changes): the same logical dataset produces different ids across events → node-forking → cross-source lineage breaks, dedup fails, every query for the "old" id misses history. The canonical field set must exactly capture the logical identity — stable, complete, and no more. Resolving: §8.2 (references + identities), §7 (I5), §12.6 (pitfalls), §8.13 (idempotency subtlety).

  20. Why is the conformance phase (Phase 13) the definition of "done" rather than "the system passes its own tests"? Phase 13 defines correctness against three independent ground truths: (a) the in-memory oracle (a separately-implemented, obviously-correct reference — principle 15); (b) the hand-labeled SQL corpus (human expert annotations of column dependencies — I9); (c) tamper-evidence tests (Merkle chain integrity — I10). "The system passes its own tests" is a circular guarantee — if both the system and its tests have the same bug (e.g., both agree that SUM(x) has no column dependency), the test passes and the bug ships. The oracle and corpus are external ground truths that cannot share the implementation bug. A recall < 1.0 on the corpus is a CI-blocking failure regardless of what the system's own column-lineage tests say. Resolving: §6 (principle 15), §7 (I6/I9/I10), §12 (Phase 0 oracle), §25 (Phase 13).

Winning regime: teams that already operate Postgres, want a lightweight lineage store with a standard SQL query interface, have no graph engine expertise, and whose graphs are small enough that recursive CTEs are acceptable (< 1M nodes, < 5 hops typical). The OpenLineage event spec is the real value; Marquez's Postgres backing is a pragmatic starting point.

Real system: Marquez (the OpenLineage reference implementation) — stores jobs, runs, and datasets as relational tables in Postgres and exposes lineage via REST with SQL-backed traversal. Widely deployed for small-to-medium lineage graphs.

Why rejected: (1) Recursive CTEs in Postgres for multi-hop closure (k=8, R=10k) are orders of magnitude slower than BFS over a native graph adjacency structure — the p50 < 50 ms target is unreachable at 1M nodes. (2) Bitemporal modeling in a relational schema requires temporal tables + interval joins — complex, slow, and not first-class. (3) Column-level lineage edges are many (§36 E8: ~1.5B at full coverage) — a relational edge table at this scale has severe join performance issues. (4) The learning objective is building a graph-native lineage system; using Postgres teaches ORM, not graph traversal.

  └──────────────────────────────────────────────────────────┘

Winning regime: environments that already operate Kafka + Flink as the data platform backbone, want lineage as a streaming application, and need the event log as the durable record (Kafka's retention is the lineage audit log). Teams that think in "streaming SQL" rather than graph traversal find this model natural.

Real system: LinkedIn's internal lineage system (pre-DataHub) used a Kafka-based event pipeline to capture and materialize lineage views. Apache Flink's provenance tracking (Titian, VLDB 2015) uses a dataflow-native approach where lineage is streamed alongside data.

Why rejected: (1) Materialized pre-computed upstream/downstream sets are fast for point lookups but cannot answer arbitrary k-hop queries or column-level propagation without re-materializing all views — the view explosion is O(datasets²) in the worst case. (2) Bitemporal time-travel over materialized views requires snapshotting the entire view set at each interesting time — expensive and complex. (3) Kafka is a durable event log but not a tamper-evident one (no Merkle chaining, no chain-verify API) — the integrity requirement (I10) is not met natively. (4) The learning objective is graph-native closure + PROV-DM modeling; a streaming materialized-view system teaches Flink/Kafka, not graph algorithms.

40. Glossary

  • Activity (PROV) — something that acts on/produces entities over time; here, a job run.
  • Agent (PROV) — something responsible for an activity; a person, service, or pipeline.
  • Append-only — facts are added, never mutated/deleted in place (GC reclaims out-of-window history only).
  • Bitemporal — modeling two time axes: valid-time + transaction-time (§8.12, §18).
  • Blast radius — the downstream set affected by a change (impact analysis result).
  • Closure (transitive) — the set of all entities reachable up/downstream via wasDerivedFrom (§8.7, §16).
  • Column-level lineage — wasDerivedFrom edges between individual columns (vs whole datasets); extracted by SQL/plan parse (§8.5, §15).
  • Conservative (column lineage) — never drop a real dependency (recall = 1.0); over-reporting allowed (§4.3, I9).
  • Content-addressed id — a node/edge id = hash of its identifying fields; same logical thing → same id (§8.2, I5).
  • Coverage (column) — the fraction of a query's path that has column-level (not just dataset) edges (I12).
  • DAG (derivation) — the directed acyclic graph of wasDerivedFrom (cycles forbidden, I1).
  • Dataset-level lineage — lineage at table/dataset granularity (always present, §8.4).
  • Dedup / idempotency — collapsing re-delivered events so a retry yields one edge set (§8.13, I7).
  • Entity (PROV) — a thing with provenance; here, a dataset or column version (§8.1).
  • Granularity — dataset-level vs column-level (the lineage resolution, §8.4).
  • Hub node — a super-connected dataset (e.g. users) with very high edge fan-out; requires bounded traversal (§4.2, §33).
  • Impact analysis — the downstream closure (what a change affects); forward BFS (§8.14, §17).
  • Lineage — the record of where data came from, how it was transformed, and what it feeds.
  • Merkle chain — a hash chain making the event log tamper-evident (#71, §19, I10).
  • MVCC — multi-version concurrency control; readers take a snapshot, writers append; no blocking (§3.5, I11).
  • OpenLineage (OL) — the open standard for run/job/dataset lineage events (the ingest contract, §8.8).
  • Oracle — the in-memory reference implementation; the correctness ground truth (§12, principle 15).
  • Partial result — a closure that hit bounds (k/R/deadline) and was truncated; flagged truncated=true (I8).
  • Provenance — the origin + derivation history of data (the why/how/where of a value).
  • PROV-DM — the W3C provenance data model (entities/activities/agents + relations, §8.1).
  • Pull-based capture — scraping / log-mining lineage without producer instrumentation (§38.A, contrast with push).
  • Push-based capture — producers emit OpenLineage events; the primary capture mechanism (§8.4, ADR-8).
  • Recall — fraction of true dependencies that are captured; recall = 1.0 is the contract (I9).
  • Root-cause — the upstream closure under a predicate (what produced a flagged value), ranked (§8.14, §17).
  • RunContext — the (job, run id, valid-time, tx-time, agent) carried on every edge (§8.2, I4).
  • Snapshot — a (valid,tx) cut of the graph; every read is against one (MVCC, §11.3, I11/I13).
  • Supersede — a corrected edge appended at a new tx-time; the old edge is retained (§8.12, I3).
  • Tamper-evidence — the property that any alteration of history is detectable (Merkle/signing, §19, I10).
  • Time-travel — querying lineage "as of" a past (valid,tx) time (§8.12, §18).
  • Transaction-time — when a fact was recorded in the system (the tx axis of the bitemporal model).
  • Valid-time — when a fact was true in the modeled world (the valid axis of the bitemporal model).
  • wasDerivedFrom — the PROV relation: one entity was derived from another (the lineage edge, §8.1).
  • wasGeneratedBy / used — a run produced / read a dataset (attribute the transform, §8.1).
  • Why/how/where provenance — which inputs influenced (why), the transformation (how), the source location (where).
