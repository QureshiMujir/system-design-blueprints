⬜ Phase 0 — Skeleton: PROV-DM model + in-memory oracle §12

Objectives
  • Stand up the workspace + prov-core; depend on #84 and #71.
  • Define the PROV-DM types (Entity/Activity/Agent, relations, DatasetRef/ColumnRef, RunContext), content-addressed NodeId/EdgeId (I5/I7).
  • Build the in-memory reference oracle: a simple, slow, obviously-correct lineage model (HashMaps + naive closure) — the trusted result for every later phase (principle 15).
Deliverable
  • Construct PROV facts, build the in-memory oracle, run a tiny upstream/downstream closure by hand; linctl node <id> prints it.
Acceptance
  • NodeId is stable + content-addressed (same logical entity → same id, I5); collisions for distinct entities are negligible.
  • Oracle closure matches a hand-computed result on a 5-node graph.
  • PROV type roles validated (an Agent can't be wasGeneratedBy, I2).
Fixtures
  • closure/tiny_upstream.json, closure/tiny_downstream.json, badinput/prov_type_violation.json.
Pitfalls
  • Content-address over the wrong fields → unstable ids → dedup fails / nodes fork (I5). Pin the canonical field set + ordering.
  • PROV role confusion (Entity vs Activity) → invalid relations. Type the relations so illegal pairings don't compile/construct.
  • Oracle that is "clever" → not trustable. Keep it naive (the whole point is obvious correctness).

⬜ Phase 1 — Versioned lineage graph store over #84 §13

Objectives
  • Build the real graph layer on #84: the node/edge model, append-only revisions (I3), and snapshot reads (I11) — the durable substitute for the oracle's HashMaps. (Bitemporal filtering lands in P6; this phase ships single-time append-only + revisions.)
Deliverable
  • Append PROV facts to the #84-backed graph; read them back via snapshot; the same facts fed to graph + oracle produce identical adjacency. linctl ingests + queries against the real store.
Acceptance
  • Append-only: no API mutates a committed edge (I3); re-append of the same edge dedups (I7).
  • Snapshot reads are consistent under concurrent appends (I11) — a reader at rev=k never sees rev>k.
  • Cycle insertion rejected (I1); graph adjacency == oracle adjacency on recorded fixtures.
Fixtures
  • closure/graph_vs_oracle_adjacency.json, temporal/snapshot_consistency.json, badinput/cycle_insert.json.
Pitfalls
  • Leaking #84's API shape into upper crates → coupling. Keep store_84 the only #84-aware module (principle 9).
  • Cycle check over the whole graph on every insert → O(V) per write. Scope it to the affected region (ancestors of dst / descendants of src).
  • Snapshot torn reads if a reader sees a half-committed revision → commit a revision atomically (all-or-nothing batch) (I11).
  • Dedup race: two writers append the same new node → use the content id as the storage key so the second is a no-op (I7).

⬜ Phase 2 — Dataset-level capture: OpenLineage events, idempotent ingest §14

Objectives
  • Ingest OpenLineage run/job/dataset events (push), translate to PROV facts, and commit dataset-level edges — idempotently (I7). The capture front door for the common case (no SQL yet).
Deliverable
  • POST OL events (or call the instrument API) → dataset-level lineage in the graph; replay the same stream twice → identical graph (I7). examples/ingest_ol.
Acceptance
  • Differential: replay a recorded OL event stream → graph adjacency == oracle fed the same events (the OpenLineage differential, ADR-25).
  • Idempotency: ingest each event N times → exactly one edge set (I7); dedup_hit true on repeats.
  • Determinism: same stream → identical graph hash (I6; content-addressed ids).
Fixtures
  • openlineage/etl_stream.jsonl (a recorded run sequence), openlineage/replay_idempotent.json, openlineage/dataset_lineage_vs_oracle.json.
Pitfalls
  • COMPLETE-before-START / out-of-order events → reconcile by run id; don't commit conflicting edges (use valid-time / #95 if clocks disagree, §8.10).
  • Idempotency key over a non-canonical payload → two encodings of the same event don't dedup → canonicalize (sort keys, normalize) before hashing (I7).
  • Treating START edges as final → premature/partial lineage; commit on COMPLETE or flag partial.
  • A failed run (FAIL/ABORT) still has lineage value (it used inputs) → record the run + inputs, flag outputs as not-produced.

⬜ Phase 3 — Column/field-level lineage: SQL + query-plan parsing §15

Objectives
  • Extract column-level wasDerivedFrom edges by parsing the SQL a job ran (or its query plan) — conservatively (recall = 1.0, I9). The headline value, the hardest phase.
Deliverable
  • Ingest a job with SQL → column-level lineage in the graph; examples/sql_column_lineage shows per-output-column derivation; coverage reported (I12).
Acceptance
  • SQL corpus: recall = 1.0 (every hand-labeled true edge present, I9) — a CI hard gate; precision ≥ 0.85.
  • Aggregates/CASE/joins/CTEs/subqueries resolved per §8.5; predicate columns included (why-provenance).
  • Parse is bounded (I15): a pathological query rejected within the time/depth limit, not a hang; column-incomplete on unsupported syntax (I12).
  • Column lineage matches the oracle's hand-labeled edges on the corpus.
Fixtures
  • sql_corpus/*.sql + sql_corpus/*.expected.json (hand-labeled column edges: projections, aggregates, CASE, joins, CTEs, subqueries, SELECT *); sql_corpus/unsupported.sql (→ column-incomplete); badinput/sql_dos.sql (bounded reject, I15).
Pitfalls
  • Aggregates dropping the input dependency (SUM(x) → must keep x) → the classic recall failure (I9). Test every aggregate.
  • Predicate columns omitted → why-provenance lost (WHERE region=… makes outputs depend on region). Include filter/join/CASE-condition columns.
  • Unqualified column ambiguity across joined tables → resolve against the in-scope schemas; if truly ambiguous and unresolvable → conservative: attribute to all candidates (over-report, I9) + flag.
  • CTE/subquery scope leakage → a column resolved to the wrong scope → backwards/wrong edge. Rigorous scope stacking.
  • SELECT * without schema → can't enumerate columns → ColumnIncomplete + dataset edge (I12), never silently drop.

⬜ Phase 4 — Closure queries: transitive up/downstream §16

Objectives
  • Implement the core query: bounded transitive upstream/downstream closure + column propagation, over a snapshot, deterministic and always-terminating (I6/I8).
Deliverable
  • linctl upstream/downstream <ref> --hops k returns the closure with paths; column mode reports coverage. examples/impact_query (the downstream case).
Acceptance
  • Closure == oracle's naive closure on fixtures (I6), within the same bounds.
  • Always terminates: a hub node (1M reachable) returns a bounded, truncated-marked result within the deadline (I8) — never hangs.
  • p50 < 50 ms, p95 < 300 ms for k≤8 on a 1M-node graph (§4).
  • Determinism: same query + snapshot → identical result_hash (I6).
Fixtures
  • closure/upstream_k_hops.json, closure/downstream_blast.json, closure/hub_truncation.json (I8), closure/column_propagation.json, closure/column_degraded.json (I12).
Pitfalls
  • Forgetting the visited-set → revisiting nodes in a DAG with diamond paths → exponential blowup. Maintain a visited set (it's a DAG but with shared ancestors).
  • Unbounded closure on a hub → hang (I8). Bounds are mandatory, not optional (principle 8).
  • Direction confusion (upstream vs downstream = in vs out edges) → backwards answers. Test both against the oracle.
  • Column propagation silently returning dataset-level → mislead (I12). Always report coverage.

⬜ Phase 5 — Impact analysis + root-cause §17

Objectives
  • Build the two headline analyses on top of closure (§8.14): impact (downstream blast radius + the runs/jobs on each path) and root-cause (upstream contribution to a flagged value, ranked + predicate-filtered).
Deliverable
  • linctl impact <ref> (blast radius + jobs) and linctl root-cause <col> --since T (ranked upstream); examples/root_cause.
Acceptance
  • Impact returns the complete downstream set (bounded, I8) + the correct runs/jobs on each path (vs oracle).
  • Root-cause ranking puts the most-likely upstream first on labeled incident fixtures (recent/failed-run-on-path ranks high).
  • Column-level impact is strictly narrower than dataset-level on column-rich fixtures (the precision win, §8.14).
Fixtures
  • closure/impact_with_jobs.json, closure/root_cause_ranked.json, closure/incident_localization.json (a seeded bad-value scenario), closure/column_vs_dataset_blast.json.
Pitfalls
  • Impact without run context → "what" but not "which job to fix" → annotate every path edge with its RunContext (I4).
  • Root-cause ranking that ignores recency → buries the actual cause among ancient lineage → recency is a primary rank factor.
  • A predicate filter that drops too much (excludes a contributing run) → violates conservatism (I9) → filter ranks, don't prune the closure.
  • Confusing the two directions (§8.14) → a tool that does neither well.

⬜ Phase 6 — Temporal / bitemporal model + time-travel §18

Objectives
  • Add the second time axis: bitemporal edges (valid-time + transaction-time) and time-travel queries ("lineage as of T"), with corrections via append-only supersede (I13/I3).
Deliverable
  • linctl upstream <ref> --as-of-tx 2026-01-01 returns the graph as known then; corrections append, never overwrite. examples/time_travel.
Acceptance
  • Time-travel == oracle-at-T (an oracle replaying only events with tx ≤ T) on fixtures (I13).
  • A supersede leaves the old edge visible at earlier tx (I3) and the new edge at later tx; no in-place mutation.
  • as_of(valid=V, tx=T) composes both filters correctly (Snodgrass semantics, §8.12).
  • Time-travel read overhead < 2× a latest read (§4).
Fixtures
  • temporal/as_of_tx.json, temporal/as_of_valid.json, temporal/bitemporal_combined.json, temporal/supersede_correction.json (I3), temporal/before_data_exists.json (empty result).
Pitfalls
  • Conflating valid-time and tx-time → wrong audit answers (the canonical bitemporal bug). Stamp + filter both, always (principle 6).
  • A correction that deletes the old edge → destroys audit history (violates I3). Supersede, never delete.
  • Snapshot filtering applied after traversal instead of before → traverses through edges that didn't exist at T → wrong cut. Filter adjacency at the snapshot boundary (I13).
  • Open valid-intervals ([V, ∞)) for "still true" lineage → handle the unbounded upper bound.

⬜ Phase 7 — Integrity: Merkle tamper-evidence + signing §19

Objectives
  • Make provenance trustable: Merkle-chain every captured event/revision (#71), support optional Ed25519 event signing, and provide verify — so audit lineage is tamper-evident (I10, principle 10).
Deliverable
  • Every ingested event chained; linctl verify --range … confirms integrity or pinpoints tampering; signed events verified against producer keys. scripts/verify_chain.sh.
Acceptance
  • verify over an intact chain returns true ≥ 1M events/s (§4); a single flipped byte anywhere makes verify fail and forensics locates it (I10).
  • Signed events verify against the right public key; a forged signature is rejected.
  • The Merkle root is stable + reproducible for a given event sequence (determinism).
Fixtures
  • integrity/chain_intact.json, integrity/chain_tampered.json (flipped byte → verify fail + located), integrity/signed_event.json, integrity/forged_signature.json.
Pitfalls
  • Hashing a non-canonical event encoding → chain non-reproducible / false tamper alarms → canonicalize before hashing (same as idempotency, I7/I10).
  • A single global Merkle writer becoming a bottleneck → per-shard chains (one ordered writer each) + a periodic aggregated root (§3.5).
  • Storing signatures but never verifying on read → false sense of trust. verify must actually re-check.
  • Key management out of scope but must be acknowledged (producer key distribution is an operational concern, partially deferred).

⬜ Phase 8 — Scale ingestion: CDC / stream / log / build connectors §20

Objectives
  • Capture lineage from non-OL sources: #103 CDC, #105/#215 stream, #214 table-format snapshots, #136 builds, and runtime/log instrumentation — all normalized to the same PROV facts (§8.4).
Deliverable
  • Lineage captured from at least CDC + stream + build sources via connectors, normalized into the graph; linctl queries span sources (cross-source join via content ids, I5).
Acceptance
  • Each connector's output, fed to the graph, == oracle fed the equivalent normalized events.
  • Idempotent across source-specific retries (I7): CDC offset / build hash / snapshot id dedup.
  • Cross-source lineage joins: a dataset produced by a Spark job (OL) and consumed by a CDC stream resolves to one node (I5).
Fixtures
  • openlineage/cdc_normalized.json, openlineage/stream_normalized.json, openlineage/build_provenance.json, openlineage/cross_source_join.json (I5).
Pitfalls
  • Each source's identity scheme differs → must map to the canonical DatasetRef/content id (I5) or nodes fork and cross-source lineage breaks. The normalization layer is the critical correctness point.
  • CDC volume can dwarf OL events → backpressure + batching (I8); per-table aggregation to avoid an edge per row.
  • Source-specific idempotency keys (CDC offset vs OL run id) → each connector defines its dedup key (I7).
  • A connector leaking source-specific types upward → keep adapters at the boundary (mirror principle 9 for sources).

⬜ Phase 9 — Search + API (REST/gRPC, lineaged server) §21

Objectives
  • Expose the system: a search index over datasets/columns/jobs, REST + gRPC endpoints for ingest + all queries, the lineaged server, and the linctl CLI.
Deliverable
  • lineaged serving REST + gRPC; linctl search "orders", linctl impact …, etc.; the full system usable end-to-end. docker-compose up brings up lineaged + #84.
Acceptance
  • All query types reachable via REST + gRPC with consistent results (== linctl == oracle).
  • Search returns the right nodes by name/facet; the index reconciles to the graph (I14) — no drift after a rebuild.
  • Ingest is async + backpressured (I8); the API versions the OL ingest + query formats (principle 13).
Fixtures
  • openlineage/api_ingest_roundtrip.json, closure/api_query_parity.json (REST==gRPC==oracle), badinput/api_malformed.json (I15), openlineage/search_index.json.
Pitfalls
  • Search index drifting from the graph (a write the index missed) → stale/missing search results (I14). Derive the index from committed graph writes + a periodic reconcile job.
  • REST/gRPC returning different results → a serialization/semantics gap → the parity fixture gates it.
  • Synchronous ingest blocking producers under load → async (202) + bounded queue (I8).
  • Unbounded query params (k=∞, R=∞) from the API → clamp to ServerConfig limits (I8/I15).

⬜ Phase 10 — Retention, compaction, GC §22

Objectives
  • Bound storage growth of an append-only, bitemporal graph: policy-driven retention, compaction, and GC that reclaim space without rewriting history within the retention window (principle 2/I3).
Deliverable
  • A configurable retention policy that bounds graph + dedup + Merkle-log growth; linctl gc --dry-run reports what would be reclaimed; storage stays bounded under continuous ingest.
Acceptance
  • Storage growth bounded by the policy under a sustained ingest workload (§4); within-window history fully preserved (time-travel still correct, I13).
  • GC never removes a fact still inside the retention/valid-time window; never breaks an intact Merkle chain for retained ranges (I10).
  • Determinism: GC is idempotent (running it twice = once).
Fixtures
  • temporal/retention_window.json, temporal/compaction_preserves_window.json (time-travel within window still == oracle), integrity/archived_chain_verify.json.
Pitfalls
  • Compaction that drops an in-window superseded edge → breaks time-travel for an audit date inside retention (I13). The window boundary is the hard line.
  • GC racing with a reader at an old snapshot → the reader's snapshot must pin its needed history (or be told it aged out). Coordinate GC with active snapshots (MVCC, I11).
  • An unbounded dedup table silently OOMs the server over months → it must be GC'd too (often forgotten).
  • Breaking the Merkle chain on archive → verifiability lost → archive the body, keep the root + a re-anchor (I10).

⬜ Phase 11 — C ABI §23

Objectives
  • Expose a stable C ABI (+ FFI-friendly layer) so polyglot producers (ingest) and consumers (query) can drive the system; safe across the boundary (I15).
Deliverable
  • liblineage.so/.a + lineage.h; examples/run_from_c.c ingests an event + runs an impact query from C.
Acceptance
  • A C program ingests + queries with results identical to the Rust/linctl path.
  • No UB across the boundary (I15): bad args → LIN_EINVAL; an internal panic → LIN_EINTERNAL (caught); ASAN-clean.
  • Buffer ownership documented + correct (no leaks/double-free) under an ASAN integration test.
Fixtures
  • badinput/cabi_null_args.json, badinput/cabi_bad_json.json, openlineage/cabi_ingest_parity.json (C path == Rust path).
Pitfalls
  • Buffer lifetime: who frees the result? → explicit lineage_free; document it; ASAN test it.
  • Panics crossing FFI = UB → catch_unwind at every entry (I15).
  • String encoding (UTF-8) across the boundary → validate at entry.
  • Handle misuse (use-after-free of a server handle) → opaque handles + validation.

⬜ Phase 12 — Performance hardening §24

Objectives
  • Close gaps to the §4 targets at scale: ingest throughput, closure latency on a 1M+-node graph, column-parse rate, and time-travel overhead — via profiling, caching, batching, and #84 access tuning.
Deliverable
  • §4 targets met under bench: ingest tput, closure p50/p95 on 1M nodes, column-parse rate, time-travel < 2× overhead; scaling curves.
Acceptance
  • Ingest ≥ 50k events/s (dataset) / ≥ 5k (column); closure p50 < 50 ms / p95 < 300 ms at 1M nodes; freshness p95 < 2 s; time-travel < 2× latest-read.
  • No correctness regression (re-run the full oracle differential + corpus + integrity verify).
Fixtures
  • golden/ingest_throughput.json, golden/closure_latency_scaling.json, golden/parse_rate.json, golden/timetravel_overhead.json.
Pitfalls
  • A cache (hot-hub adjacency, schema) going stale vs the graph → wrong results → invalidate on the relevant append (the graph is truth, I14).
  • Optimizing the parser by dropping derivations → breaks recall=1.0 (I9). Perf must not touch capture conservatism (principle 7).
  • Batching ingest too aggressively → freshness regression (§4.1). Balance batch size vs the 2 s p95.
  • A micro-opt that helps one graph shape regresses another → the bench matrix (varied graph shapes) gates merges.

⬜ Phase 13 — Conformance, differential, fuzz, benchmarks §25

Objectives
  • Lock correctness + performance: differential vs the in-memory oracle, the SQL-corpus accuracy gate (recall=1.0, I9), tamper-evidence tests, fuzzing the untrusted parsers, determinism goldens, and reproducible benchmarks.
Deliverable
  • make conformance green; make fuzz (CI-budget) green; make bench report meeting §4.
Acceptance
  • 100 % differential pass (graph + all query types == oracle, I6); SQL corpus recall = 1.0 (I9), precision ≥ 0.85.
  • Fuzz: no panic/crash/UB on the parsers within the budget (I15); tamper tests detect + locate every injected tamper (I10).
  • Determinism goldens stable; bench meets §4 (ingest, closure, parse, freshness, time-travel).
Fixtures
  • Full conformance/: openlineage/, sql_corpus/, closure/, temporal/, integrity/, badinput/, golden/ + a docker-compose (lineaged + #84) harness.
Pitfalls
  • Corpus recall slipping below 1.0 on a parser change → the hard CI gate (I9); a regression must add the missed query to the corpus.
  • Fuzz finds a parser hang/crash → fix + add as a regression fixture; the I15 bounds are the backstop.
  • Determinism hash breaking on a legitimate change (new edge type) → version the goldens with the model/format version (principle 13).
  • Differential flakiness from non-determinism → fixed snapshots + content-addressed ids (I5/I6) make it deterministic.
