3.2 Box Narratives

  • producers. External: Spark/dbt/Airflow jobs, #103 CDC, #105 stream jobs, #136 builds. They emit OpenLineage-style events (run start/complete with input/output datasets) and/or raw SQL/query plans. Untrusted input crossing into capture.
  • capture. The ingest front door. (a) OL event ingest: validate, dedup (idempotency key → I7), translate to PROV facts. (b) SQL/query-plan parser: lex/parse SQL, build a logical plan, resolve column scopes, emit conservative column-level wasDerivedFrom edges (I9). (c) instrumentation API: a library producers link to emit events directly. (d) source connectors (P8): adapters for CDC/stream/log sources. Hands PROV facts to prov-core/graph and raw events to integrity.
  • prov-core. The PROV-DM vocabulary every other crate speaks. Entity (a dataset/column version), Activity (a job run), Agent (a person/service); relations wasGeneratedBy/used/wasDerivedFrom/wasAssociatedWith/wasInformedBy. DatasetRef/ColumnRef (namespaced, stable identities), RunContext (job, run id, timestamps, agent). Node ids are content-addressed for dedup/idempotency. The normative type set.
  • graph. The versioned, bitemporal lineage DAG, stored on #84. Nodes = dataset/column/job versions; edges = PROV relations annotated with valid-time + transaction-time + the run context. Append-only revisions (never mutate in place); snapshot reads ("as of T"). Enforces the DAG invariant (cycle detection, I1) and idempotency at the storage layer. Owns the mapping from PROV facts to #84's node/edge primitives — but not the traversal engine itself (that is #84).
  • query. The query engine over the graph: transitive up/downstream closure (bounded, terminating — I8), column-level propagation (follow column edges), impact analysis (downstream reachable set = blast radius), root-cause (upstream contribution under a predicate — what produced a flagged value), and time-travel (closure as of a (valid,tx) time). Pure reads; deterministic given a snapshot.
  • integrity. Tamper-evidence: every captured event/revision appended to a Merkle-chained log (#71); optional Ed25519 signing of events by producers; verify recomputes the chain and checks signatures. Makes lineage admissible for audit (principle: provenance must be trustable).
  • api. The lineaged server: REST + gRPC endpoints for ingest + all query types; a search index over dataset/column/job names + facets. linctl CLI wraps it. The external interface + trust boundary.
  • bench / conformance. Ingest-throughput + closure-latency harness; the in-memory reference oracle (a simple, slow, obviously-correct lineage model — the trusted result); OpenLineage differential (replay recorded event streams, compare to oracle); SQL-corpus column-lineage accuracy (hand-labeled queries → precision/recall, with recall = 1.0 required, I9); tamper-evidence tests; fuzz (SQL parser, event parser).

3.3 Boundaries

  • Trust boundary: the ingest API (OL events, SQL, plans from many producers) and the C/query API. All input is validated; SQL is parsed defensively (resource-bounded, panic-free, I15). Producers are semi-trusted; signed events raise trust for audit.
  • Concurrency boundary: many concurrent ingest writers vs many concurrent query readers. The graph is append-only → writers append revisions; readers take snapshots → MVCC-style read/write separation (no read blocks a write).
  • Persistence boundary: #84 is the durable store; integrity's Merkle log is a second durable artifact (the tamper-evidence chain). The line between "PROV facts in the graph" and "raw events in the Merkle log" is explicit.
  • Temporal boundary: valid-time (world time of the lineage fact) vs transaction-time (when we recorded it). All writes stamp both; all reads choose a (valid,tx) snapshot. This boundary is the source of every time-travel subtlety.
  • Granularity boundary: dataset-level edges (always present) vs column-level edges (present only when a SQL/plan parse succeeded). Queries declare which granularity they need; column queries degrade gracefully to dataset-level where column edges are absent (and say so — I12).

3.4 Data-flow walk — capturing + querying one ETL job

  1. A dbt/Spark job runs INSERT INTO sales_daily SELECT date, SUM(amount) FROM orders GROUP BY date. It emits an OL event: run r1, job etl.sales_daily, inputs [orders], outputs [sales_daily], plus the SQL.
  2. capture ingests: dedups on r1's idempotency key (I7), creates Activity(run=r1), Entity(orders@v), Entity(sales_daily@v'); emits used(r1, orders) + wasGeneratedBy(sales_daily, r1) (dataset-level).
  3. The SQL parser resolves columns: sales_daily.date wasDerivedFrom orders.date; sales_daily.amount wasDerivedFrom orders.amount (through the SUM). Conservative: the aggregate keeps the dependency (I9). Column edges added.
  4. integrity appends the raw OL event to the Merkle log (I10); if the producer signed it, the signature is stored.
  5. graph writes all edges with valid_time = run.event_time, tx_time = now, run ctx r1 — append-only revision (I3); cycle check passes (orders ≠ downstream of sales_daily, I1).
  6. Later, sales_daily.amount looks wrong. Root-cause query: walk upstream column edges from sales_daily.amount → orders.amount, ranked by run recency → the operator inspects orders.amount's producing run.
  7. orders schema changes. Impact analysis query: downstream closure from orders → {sales_daily, … and everything sales_daily feeds} = the blast radius, returned with paths.
  8. An auditor asks "what did lineage look like on 2026-01-01?" Time-travel: closure over the snapshot tx_time ≤ 2026-01-01 → the graph as we knew it then (I13). verify confirms the Merkle chain is intact (I10).

3.5 Concurrency model (writers, readers, snapshots)

  • Ingest writers (a pool) validate + dedup + append revisions; appends are serialized at the per-node level (a node's revision chain is ordered) but parallel across nodes. Idempotency (I7) makes a duplicate append a no-op.
  • Query readers take a snapshot (a (valid,tx) point) and traverse without locking writers — append-only + MVCC means a reader sees a consistent past; concurrent writes are simply invisible to it (I3/I13).
  • Cycle detection runs at write time (adding an edge that would close a derivation cycle is rejected, I1) — never at query time (queries must always terminate, I8).
  • The Merkle log is appended by a single ordered writer (or a per-shard ordered writer) so the chain is well-defined (I10); ingest enqueues, the log writer drains.
  • Search index updates are derived from committed graph writes (eventually consistent with the graph; the graph is the source of truth, the index is a cache — I14).
  • Synchronization: no global lock on the read path; writers coordinate only on a node's revision chain and the Merkle log tail. Readers are wait-free against writers.

8. Domain Model — PROV-DM, Lineage Graph, Capture, Queries

8.1 PROV-DM core (the model)

  • Three node kinds: Entity (a thing with provenance — a dataset version, a column version), Activity (something that acts on/produces entities over time — a job run), Agent (something responsible — a person, a service, a pipeline).
  • Core relations: used(Activity, Entity) (a run read a dataset), wasGeneratedBy(Entity, Activity) (a run produced a dataset), wasDerivedFrom(Entity, Entity) (one entity derived from another — the lineage edge), wasAssociatedWith(Activity, Agent) (who ran it), wasInformedBy(Activity, Activity) (a run triggered/fed another).
  • Lineage = the transitive closure of wasDerivedFrom (+ used/wasGeneratedBy to attribute the transform). Column lineage = wasDerivedFrom between ColumnRef entities.

8.2 References + identities

  • DatasetRef { namespace, name, version } — a stable, namespaced dataset identity (e.g. postgres://prod/public.orders@v37). ColumnRef { dataset: DatasetRef, column }.
  • RunContext { job: JobRef, run_id, event_time (valid-time), recorded_at (tx-time), agent: AgentRef, facets }.
  • Content-addressed ids (I5): node_id = hash(kind, namespace, name, version); same logical entity from two sources collapses to one node → cross-source lineage joins automatically.
  • Versions: a dataset's schema/content version makes Entity instances distinct over time → the graph naturally records "orders@v37 → orders@v38."

8.3 The lineage graph (bitemporal, versioned, over #84)

  • Nodes: dataset/column/job/agent entities (content-addressed). Edges: PROV relations, each annotated with (valid_time, tx_time, run_context, granularity).
  • Append-only revisions (I3): a new fact adds nodes/edges with a fresh tx_time; superseding facts add new edges (e.g. a re-run) without deleting old ones.
  • Bitemporal: valid_time = when the lineage was true in the world (the run's event time); tx_time = when we recorded it. Both stamped on every edge (I4).
  • DAG constraint on wasDerivedFrom (I1): inserting an edge that closes a derivation cycle is rejected.
  • Storage: mapped onto #84's node/edge primitives; #84 owns adjacency/traversal, graph owns the bitemporal + PROV semantics layer.

8.4 Capture mechanisms

Mechanism Source Granularity Phase

Stream-job lineage #105/#215 dataset P8
Build provenance #136 content-addressed builds artifact P8
Table-format snapshots #214 dataset/snapshot P8
  • All mechanisms produce the same PROV facts; capture normalizes them. Column-level comes only from SQL/plan parsing (or an OL columnLineage facet).

8.5 Column-lineage extraction (the hard part)

  • Parse SQL → AST → logical plan (projections, joins, filters, aggregations, CTEs, subqueries). Resolve each output column's expression; collect every input ColumnRef referenced → emit output_col wasDerivedFrom input_col for each (conservative, I9).
  • Scope resolution: track table aliases, CTE bindings, subquery scopes, USING/NATURAL JOIN column merging. Unqualified columns resolved against the in-scope tables' schemas.
  • Predicate/filter columns count for why-provenance (a WHERE/JOIN ON/CASE condition column influences which rows produce the output).
  • SELECT * expansion needs the source schema; if unknown → dataset-level edge + column-incomplete flag (I12).
  • Aggregates (SUM, COUNT(DISTINCT), window funcs) → the aggregated input column(s) are dependencies; GROUP BY columns are dependencies of the grouped output.

8.6 Worked column-lineage example

INSERT INTO sales_daily(d, total, region) AS
SELECT o.order_date AS d, SUM(o.amount) AS total, c.region AS region
FROM orders o JOIN customers c ON o.cust_id = c.id
WHERE o.status = 'paid' GROUP BY o.order_date, c.region;

→ sales_daily.d      wasDerivedFrom orders.order_date
→ sales_daily.total  wasDerivedFrom orders.amount
→ sales_daily.region wasDerivedFrom customers.region
→ (why) all three also gated by orders.status, orders.cust_id, customers.id (join+filter) — conservative edges
Recall = 1.0: every referenced source column appears upstream of some output (I9).

8.7 Query semantics

Query Definition Algorithm
Upstream closure(n,k) all entities reaching n via wasDerivedFrom* within k hops bounded reverse-BFS (I8)
Downstream closure(n,k) all entities n reaches (its blast radius) bounded forward-BFS (I8)
Column propagation(c) closure restricted to column edges BFS over ColumnRef edges
Impact analysis(n) downstream closure + the runs/jobs on each path forward-BFS + edge run-ctx
Root-cause(c, pred) upstream columns contributing to a flagged value, ranked reverse-BFS + run-recency ranking
Time-travel(query, T) the query evaluated over snapshot tx_time ≤ T (valid_time ⊇ T optional) bitemporal filter then traverse (I13)
  • All read-only, deterministic on a snapshot (I6), bounded (I8).

8.8 OpenLineage event model (ingest contract)

  • A RunEvent { eventType: START|RUNNING|COMPLETE|FAIL|ABORT, run{runId}, job{namespace,name}, inputs[], outputs[], eventTime, facets }.
  • Datasets carry facets: schema (columns), columnLineage (explicit column edges), sql (the query), dataSource.
  • Idempotency (I7): the (runId, eventType, eventTime) tuple + content hash is the dedup key.
  • COMPLETE finalizes the run's edges; START/RUNNING may be partial → edges are committed on COMPLETE (or on a configurable policy).

8.9 State machines

  • Run lifecycle: Started → Running → {Completed → (edges committed) | Failed/Aborted → (run recorded, partial edges flagged)}.
  • Edge lifecycle: Captured → Validated → (cycle-checked I1) → Committed(tx_time) → [Superseded by a newer run | GC-eligible after retention]. No Deleted (append-only, I3).
  • Ingest: Received → Deduped(I7) → {Parsed | ParseFailed→column-incomplete I12} → Committed → Merkle-appended(I10).

8.12 Bitemporal time-travel — what "as of T" means

  • Two clocks: valid-time (world time the lineage was true) and transaction-time (system time we recorded it). A fact is a point/interval in this 2-D space.
  • as_of(tx = T): "what did we know at T" → filter edges with tx_time ≤ T. Audit's primary mode (reproduces a past belief).
  • as_of(valid = V): "what was true at V" → filter edges whose valid-interval contains V. Models lineage that changed in the world (a pipeline rewired on date V).
  • Combined as_of(valid=V, tx=T): "what we knew at T about the world at V" — the full bitemporal query (Snodgrass). Both filters compose, then traverse (I13).
  • Corrections: if we learn on tx=T2 that a past edge (valid=V) was wrong, we append a retraction/supersede at T2 — the old fact still exists at tx≤T2 (audit can see the mistake), the new fact applies at tx≥T2. Nothing is rewritten (I3).
  • Use cases: GDPR audit ("what data flowed into report R as of the breach date"), regression debugging ("did lineage change between releases"), reproducing a past impact analysis.

8.13 Idempotency + content-addressing (why retries are safe)

  • Producers retry on network failure → the same OL event arrives N times. Without idempotency, N duplicate edges → closure over-counts, impact blast radius inflates.
  • Idempotency key (I7): hash(runId, eventType, eventTime, canonical(payload)). A dedup table records seen keys; a re-delivery is a no-op.
  • Content-addressed node ids (I5): two events naming the same dataset (even from different sources/producers) hash to the same node → cross-source lineage joins for free, and a re-ingest doesn't fork the node.
  • Edge dedup: an edge id = hash(src_node, dst_node, relation, run_id) → the same run's same edge re-ingested collapses; a new run's same logical edge is a distinct (versioned) edge (preserving history, I3).
  • Subtlety: valid retries (same content) dedup; a genuinely changed re-run (new run id) does not dedup — it adds a new versioned edge. The key includes the run id precisely so corrections create history rather than silently overwriting.

8.14 Impact analysis vs root-cause — the two directions (the headline queries)

  • Impact analysis (downstream): "if orders changes/breaks, what is affected?" → forward closure from orders = the blast radius. Used before a schema migration, during an incident ("what dashboards consume this?"), for GDPR ("where does this PII flow?").
  • Root-cause (upstream): "sales_daily.total is wrong — what produced it?" → reverse closure from the flagged entity, ranked by run recency + path length, optionally filtered by a predicate (which upstream run touched it in the bad window). Used in incident response to localize the fault.
  • Both are bounded (I8) and carry run context on each edge → the answer is not just "which nodes" but "which runs/jobs on the path" (the actionable part: the job to fix).
  • Column-level sharpens both: dataset-level impact says "orders affects sales_daily"; column-level says "orders.amount affects sales_daily.total specifically" → a far smaller, precise blast radius (don't re-validate columns that don't depend on the change). This is the entire value proposition of P3 — and why recall = 1.0 (I9) matters: a missed column edge means a missed root cause or a falsely-narrowed blast radius.
  • Why two queries, not one: they traverse opposite directions over the same DAG, but rank/filter differently (root-cause cares about recency and a predicate; impact cares about completeness and paths). Conflating them produces a tool that does neither well.

Design principles (§6)

  • Provenance is event-sourced, never hand-edited. Every edge is created by a captured event (a run/SQL/plan), carrying its RunContext. Violation: manually-curated lineage drifts from reality and can't be trusted or reproduced.
  • The lineage graph is an append-only, versioned DAG. Revisions are added; nodes/edges are never mutated or deleted in place (GC reclaims, it does not rewrite). Violation: in-place mutation destroys history → time-travel and audit are impossible.
  • Derivation is acyclic; cycles are capture bugs. A wasDerivedFrom cycle is rejected at write time and alarmed (I1). Violation: a cycle makes closure non-terminating and root-cause meaningless.
  • Column lineage is conservative: never drop a real dependency. Recall = 1.0 is the contract; over-reporting is acceptable, under-reporting is a bug (I9). Violation: a missed edge silently corrupts every downstream root-cause/impact answer — the worst failure (invisible).
  • Ingestion is idempotent. Content-addressed ids + idempotency keys make a re-delivered event a no-op (I7). Violation: duplicate edges from retries distort closure counts and weights.
  • Time is bitemporal: stamp valid-time and transaction-time on every fact. Violation: "as of T" answers are wrong about what was true vs what was known → audit failures.
  • Capture correctness over query performance. A correct-but-slow edge beats a fast-but-missing one. Violation: optimizing the parser by dropping "rare" derivations breaks principle 4.
  • Closure queries always terminate and are bounded. Hops k, result size R, deadline; partial results are marked, never a hang (I8). Violation: an unbounded closure on a hub node hangs the server.
  • Graph storage delegates to #84; we own the model, not the engine. Nodes/edges/traversal primitives are #84's; bitemporal + PROV semantics are ours. Violation: reimplementing a graph engine duplicates #84, drifts, wastes effort.
  • Provenance must be trustable: tamper-evident by default. Events Merkle-chained (#71); signing optional but supported (I10). Violation: unverifiable lineage is inadmissible for compliance.
  • Graceful degradation across granularity. A column query falls back to dataset-level where column edges are absent, and says so (I12). Violation: silently returning dataset-level for a column query misleads the operator.
  • Observability of every captured edge and every query. Emit per-ingest (source, dedup hit, parse success, edges added) and per-query (hops, nodes visited, truncated?) telemetry. Violation: opaque capture → can't tell why lineage is incomplete.
  • Stable API + event-format compatibility. OL ingest version + query API version are negotiated; incompatible producers are refused or adapted. Violation: silent format drift drops or corrupts edges.
  • Bounded resources on the untrusted parse path. SQL parsing is time/depth/memory-bounded (I15); one giant/malicious query cannot exhaust the server. Violation: a crafted query is a DoS.
  • Correctness anchored to the in-memory oracle. Every capture+query path is checked against a simple, obviously-correct reference model. Violation: no oracle → lineage bugs are undebuggable (the graph "looks fine").
