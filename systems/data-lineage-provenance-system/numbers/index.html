Assumptions: a single backing #84 instance (sharding deferred to §scalability); SQL inputs in the supported dialect subset (full-dialect deferred); producers send well-formed-ish OL events (malformed handled defensively, not assumed); valid-time supplied by producers (defaults to receipt time if absent); column-level only where a parse succeeds (graceful degradation, I12).

4.1 Worked freshness budget (capture→queryable)

  • Path: receive event → validate (~50µs) → dedup lookup (~100µs) → SQL parse if present (~1–5ms) → emit PROV facts → graph append (~1–10ms incl #84 write) → visible to snapshot reads.
  • Dataset-level (no SQL): dominated by the #84 append → sub-millisecond to low-ms → p95 < 2 s holds with huge headroom even under batching/backpressure.
  • Column-level: SQL parse dominates (1–5 ms typical, more for huge queries) → still < 2 s unless a pathological query; resource bounds (I15) cap parse time so one giant query can't blow the budget.
  • Implication: freshness is gated by #84 write latency + SQL parse, not by query load (readers don't block writers, §3.5). The constraint table's 2 s p95 is a soft real-time target for incident response, not a hard deadline.

4.2 Worked closure cost (why bounded traversal is mandatory)

  • Closure from a node visits the reachable sub-DAG. Unbounded, on a 100M-edge graph, a hub dataset (e.g. a central users table feeding thousands of downstreams) could reach millions of nodes → seconds + huge result.
  • Therefore every closure is bounded: max hops k (default 8), max result size R (default 10k), and a deadline → returns a partial, marked result rather than hanging (I8). Impact analysis surfaces "result truncated at k hops / R nodes" so the operator knows to narrow.
  • Cost model: closure ≈ O(V' + E') over the reached sub-DAG, bounded by min(reachable, R); with #84 adjacency lookups at ~µs each, R=10k nodes → low-tens-of-ms → meets the p50 < 50 ms target.
  • Hub hazard: a few super-connected nodes dominate; the query exposes per-hop fan-out so a users-table impact query is understood as "intentionally huge," not a bug.

4.3 Worked column-lineage conservatism (the recall=1.0 contract)

  • A SELECT a + b AS c makes c wasDerivedFrom {a, b} — both, never one. A CASE WHEN x THEN a ELSE b END AS c → c wasDerivedFrom {x, a, b} (the predicate counts). A SUM(amount) AS total → total wasDerivedFrom amount.
  • The rule: every column referenced in the expression that produces an output column is an upstream dependency — including predicate/filter columns that gate the value (a WHERE region='US' makes outputs depend on region for why-provenance). Over-reporting (an unused column) is acceptable; under-reporting is a bug (I9).
  • SELECT * → every source column maps to its same-named output (resolved against the source schema; if schema unknown, fall back to a dataset-level edge + mark column-incomplete, I12).
  • Implication: the corpus test asserts recall = 1.0 (every hand-labeled true edge is present) and precision ≥ 0.85 (few spurious edges). The asymmetry is the whole philosophy: a missed edge silently corrupts root-cause/impact; an extra edge merely widens a blast radius (visible, recoverable).

36. Back-of-Envelope Capacity Model

All numbers derived step-by-step from §4 System Constraints. Formula shown before the derived number.

E1 — OL event payload size A typical OpenLineage RunEvent (JSON): run/job metadata (~200 bytes) + 2–5 input/output datasets with schema (~300 bytes each) + facets (~100 bytes) ≈ 1 KB per event (no SQL). With SQL facet: add the SQL string, median ~500 bytes → ~1.5 KB per event with column lineage. Derived: median event payload = 1–1.5 KB.

E2 — Ingest bandwidth Formula: bandwidth = event_rate × payload_size Dataset-level: 50,000 events/s × 1 KB = 50 MB/s ingest bandwidth. Column-level: 5,000 events/s × 1.5 KB = 7.5 MB/s ingest bandwidth. Derived: dataset-level ingest requires ~50 MB/s network + write bandwidth; column-level ~7.5 MB/s. Implication: a 1 Gbit/s network link is not the bottleneck; #84 write throughput and SQL parse CPU are.

E3 — Graph storage (nodes + edges) Formula: storage = nodes × node_size + edges × edge_size Assumptions (§4 graph scale): 10M nodes / 100M edges. Node: NodeId (32 bytes) + DatasetRef/ColumnRef (avg 80 bytes) + metadata ≈ 150 bytes/node. Edge: EdgeId (32 bytes) + src/dst NodeIds (64 bytes) + relation (1 byte) + RunContext (avg 100 bytes) + bitemporal timestamps (16 bytes) ≈ 220 bytes/edge. 10M × 150 B + 100M × 220 B = 1.5 GB + 22 GB ≈ 24 GB raw graph data. With #84 storage overhead (indexes, B-tree padding) ≈ 3–4× → ~75–100 GB for a fully-loaded single server. Derived: a 10M-node / 100M-edge graph fits in ~100 GB of storage.

E4 — Average edge count per node Formula: avg_edges = total_edges / total_nodes = 100M / 10M = 10 edges/node Median is lower (most datasets have 1–3 edges); hub nodes (e.g. users) may have 10k–100k edges. The mean is pulled up by hubs. Derived: mean 10 edges/node; plan for hub nodes at 4–5 orders of magnitude above mean.

E5 — Closure RAM cost (working set) Formula: closure_ram = max_result_nodes × (node_size + visited_set_entry) × concurrent_queries max_result_nodes R = 10,000; node_size in result = ~200 bytes; visited-set entry = ~40 bytes (NodeId + hash). Per query: 10,000 × 240 B = 2.4 MB. At 100 concurrent closure queries: 100 × 2.4 MB = 240 MB. Derived: closure working set = ~250 MB at 100 concurrent queries. Fits easily in a 16 GB server.

E6 — Merkle hash rate Formula: hash_rate = verify_target / hash_cost_per_event Target: ≥ 1M events/s verify throughput (§4). SHA-256 on modern hardware: ~500 MB/s; at 1.5 KB/event: 500 MB/s / 1.5 KB ≈ 333k hashes/s per core. To hit 1M events/s: ceil(1M / 333k) = 3 cores dedicated to verify. Derived: Merkle verify at 1M events/s requires ~3 CPU cores on modern hardware.

E7 — Dedup table size Formula: dedup_table = event_rate × retention_window × entry_size Retention window for dedup (how long to remember seen events to catch retries): 24 hours (a generous retry window). 50,000 events/s × 86,400 s × 72 bytes/entry (EventId + timestamp) = 50k × 86,400 × 72 B ≈ 311 GB. That is too large to keep entirely in RAM → use a Bloom filter (false-positive rate ≤ 0.1%) + a persisted hash set for definitive checks. Bloom filter for 50k × 86,400 = 4.32B events at 0.1% FPR: n × log2(1/p) / ln(2) ≈ 4.32B × 10 bits / 0.693 ≈ 6.2 GB of bits → feasible in RAM. Derived: dedup requires a ~6 GB Bloom filter + a persisted LRU set; naive RAM table is infeasible at 50k/s over 24 h.

E8 — Column-edge storage overhead Formula: col_edge_overhead = dataset_edges × avg_columns × edge_size If each dataset has an average of 15 columns and all are captured: 100M dataset-level edges × 15 = 1.5B potential column edges. In practice, column lineage is available for ~40% of datasets (those with SQL facets): 0.4 × 1.5B × 220 B = 132 GB additional storage. Derived: column-level lineage approximately doubles total edge storage vs dataset-level alone (~100 GB → ~230 GB).

E9 — SQL parse budget vs freshness target Formula: parse_budget = freshness_target − overhead = 2,000 ms − 200 ms = 1,800 ms Non-parse overhead: validate (~50 µs) + dedup (~100 µs) + graph append (~10 ms) + Merkle append (~1 ms) ≈ 12 ms. Available for SQL parse: 1,988 ms → ~2 s for even the most complex query. At I15 bounds (max_depth=50, max_tokens=10k, max_time=500ms), parse is capped at 500 ms. Derived: the I15 parse time limit of 500 ms is the binding constraint on freshness, not the graph write.

E10 — Storage growth rate under retention policy Formula: growth_rate = event_rate × edge_size × (1 − compaction_ratio) At 50k events/s, each producing ~5 edges on average: 50k × 5 × 220 B = 55 MB/s raw edge writes. Per day: 55 MB/s × 86,400 s ≈ 4.7 TB/day without compaction. With compaction (superseded edges GC'd after retention window, keeping ~10% of history): 4.7 TB/day × 0.1 = 470 GB/day net growth. At a 30-day retention window: 470 GB/day × 30 ≈ 14 TB steady-state storage. Derived: a 30-day retention window at 50k events/s with 90% compaction requires ~14 TB steady-state. Plan for 20–25 TB with headroom.
