1. Goal & Scope

Engineering definition. An online inference serving stack is a distributed control plane and runtime that accepts model-execution requests over a stable wire protocol, schedules them onto heterogeneous CPU/GPU workers under bounded queues, batches compatible requests dynamically, executes them against versioned model artifacts, and returns results with a reconstructable audit trail — while holding tail-latency, isolation, and durability budgets fixed under load. It is the same problem shape as an OLTP query engine wearing a tensor-execution runtime: admission control, placement, execution, and replay durability, not a training pipeline.

Phase 0 Deliverable

Phase 0 (§12) ships the correctness kernel and skeleton for every subsystem the full system needs:

  1. gateway — stateless gRPC/HTTP-2 ingress, auth, quota, tracing entry.
  2. router — tenant/model routing table, draining coordination.
  3. admission — bounded-queue admission controller, token-bucket quotas.
  4. batching — dynamic batch engine, timeout wheel, padding policy.
  5. scheduler — lease-based placement, NUMA/GPU-aware scoring.
  6. runtime-worker — crash-isolated execution process, ONNX/TensorRT executors.
  7. registry — immutable model manifest, staged rollout, rollback.
  8. replay — append-only replay/audit log, deterministic reconstruction.
  9. telemetry — non-blocking metrics/traces/structured-log pipeline.
  10. protocol — protobuf/gRPC wire schema, conformance fixtures.
  11. auth — JWT + mTLS middleware.
  12. allocator — pinned-memory pools, allocation tracking.
  13. storage — S3-compatible artifact cache with local NVMe tier.
  14. testing — deterministic simulation clock, fixture loader.
  15. control-plane — admin API for deployments/config, orthogonal to the data plane.

Phase 0 intentionally supports: ONNX execution, stateless inference, CPU + single-GPU execution, gRPC transport, deterministic replay, static/dynamic batching, rolling model deployment.

Deferred beyond this blueprint's ten phases (registered with matching anchors in §35):

  • speculative decoding — PhaseDeferred("§17") (would extend the runtime-worker execution path)
  • WASM inference plugins — PhaseDeferred("§17") (an alternative RuntimeExecutor backend, §11)
  • RDMA transport — PhaseDeferred("§13") (an alternative to the gRPC/HTTP-2 transport, ADR-06)
  • client-side request hedging — PhaseDeferred("§14") (a routing/admission-layer latency tactic, Dean & Barroso, §5)

Provides: low-latency synchronous and streaming inference RPCs; dynamic batching; lease-based GPU/CPU placement; versioned model rollout with rollback; deterministic replay of any completed request; per-tenant fairness and quota enforcement; OpenTelemetry-native observability.

Delegates: identity-provider token issuance (consumes JWTs, does not mint them); object-store durability (consumes S3-compatible APIs, does not implement erasure coding); container scheduling (runs under Kubernetes/systemd, does not reimplement a cluster scheduler for pod placement); TLS certificate issuance (consumes cert-manager/ACME output).

Does NOT provide: model training, feature engineering, notebook environments, distributed training orchestration, model architecture search, AutoML, general MLOps workflow orchestration, or general-purpose data-lake infrastructure. These are explicit non-goals, not deferrals — no phase reintroduces them.

Deployment model: Linux-first distributed runtime. Targets: bare metal, Kubernetes, single-node developer clusters, GPU-enabled cloud instances, edge inference nodes. Every crate binary is a single static-ish executable (cargo build --release) behind an OCI image (ADR-15) or a systemd unit for bare metal/edge.

Target operators: infrastructure engineers, ML platform engineers, inference-runtime developers, SREs, backend engineers integrating model APIs, operators running latency-sensitive serving fleets.

What later phases unlock: Phase 4 (§16) unlocks cluster-wide GPU placement; Phase 5 (§17) unlocks real ONNX/TensorRT execution; Phase 6 (§18) unlocks safe model rollout/rollback; Phase 7 (§19) unlocks deterministic replay for incident forensics; Phase 8 (§20) unlocks tensor parallelism and dynamic graph compilation; Phase 9 (§21) unlocks multi-region replication and elastic cold-start pooling.

Recommended language: Rust. Rationale: deterministic ownership (no GC pause amplification under p99 budgets, §4), a mature async ecosystem (Tokio, ADR-07) with production-grade gRPC tooling (tonic/prost), safe FFI boundaries into CUDA/TensorRT/ONNX Runtime, and a lock-free concurrency ecosystem (crossbeam) suited to scheduler hot paths. Rejected: Go — GC pause amplification directly conflicts with the p99 < 120 ms budget (§4) under GPU-bound tail load; C++ — memory-safety defects in scheduler/queue code are the dominant historical root cause of split-brain and OOB-read incidents in comparable systems, and Rust's FFI story into CUDA/TensorRT is equivalently mature without that risk. Secondary tooling: Python only for benchmark/fixture generation, Bash for CI orchestration.

Prerequisites: Linux internals, NUMA architecture, lock-free concurrency, async runtimes, RPC protocols, distributed systems consistency semantics, protobuf/gRPC, memory allocators, the CUDA execution model, TCP networking, OpenTelemetry, storage engines, queueing theory, schedulers, rate limiting, backpressure control, deterministic replay systems, flamegraph/eBPF profiling, Kubernetes primitives.

Estimated timeline: Phase 0 — 8-12 weeks for an experienced systems engineer. Full distributed production system (§12–§19) — 8-14 months. Advanced GPU scheduling and distributed execution (§20–§21) — an additional 6-12 months.

2. Why Build This

Online inference serving is one of the dominant distributed-systems workloads in production computing: it fuses distributed scheduling, storage, high-performance networking, memory management, heterogeneous compute orchestration, admission control, and failure isolation into one latency-critical control loop. Building it exercises tail-latency engineering, memory-fragmentation analysis, batching optimization, heterogeneous scheduling, crash recovery, and replayability — the same competencies that separate a systems engineer who has shipped a serving fleet from one who has only read about it.

Historically relevant systems: TensorFlow Serving, Triton Inference Server, Ray Serve, BentoML, KServe, TorchServe, Envoy Proxy, Apache Kafka, CockroachDB's scheduling layer, the Kubernetes/Borg scheduler lineage. Cross-disciplinary domains this project draws from:

  • Can integrate a foreign-language runtime (ONNX Runtime/TensorRT via CUDA) behind a safe Rust executor trait with crash isolation — gained in Phase 5 (§17).
  • Can design an immutable artifact-versioning system with staged rollout and sub-60-second rollback — gained in Phase 6 (§18).
  • Can build a deterministic replay subsystem that reconstructs any request's execution from a durable append-only log — gained in Phase 7 (§19).
  • Can reason about distributed tensor parallelism and dynamic graph compilation trade-offs at the scheduler level — gained in Phase 8 (§20).
  • Can design multi-region replication and cold-start pooling without breaking the isolation and replay invariants established in earlier phases — gained in Phase 9 (§21).

3.2 Subsystem Responsibilities

API Gateway (crate gateway) terminates external connections: authentication, authorization, payload validation (16 MB cap, §4), quota enforcement, request tracing initialization, protocol negotiation. Intentionally stateless — no routing or scheduling state lives here. Trust boundary: untrusted external traffic becomes an authenticated, tenant-scoped request. Failure implications: malformed-traffic amplification, tenant-isolation bypass, replay spoofing (see Threat Model, §22).

Request Router (crate router) performs model-to-worker routing, tenant-aware partitioning, sticky-session semantics, topology-aware routing, drain coordination during rollout. Concurrency boundary: async dispatch, no shared mutable routing table across requests (P6). Persistence boundary: none — the routing table is a rebuildable in-memory projection of registry state. Operational implication: incorrect routing directly moves p99 latency (I4).

Admission Controller (crate admission) enforces queue budgets, concurrency limits, overload shedding, fairness, tenant isolation. Critical invariant: no unbounded queue growth (I1).

Dynamic Batch Engine (crate batching) aggregates shape-compatible requests into execution batches: timeout handling, fairness preservation, microbatch construction, padding-policy enforcement. Failure mode: latency amplification from oversized batching windows (Pitfall, §15.6).

Scheduler Core (crate scheduler) performs worker selection, GPU placement, memory-fit validation, model-residency planning, fairness accounting. Dominant scaling bottleneck at cluster sizes beyond ~500 workers (§29). Concurrency boundary: per-lease ownership, no global mutable placement table (ADR-08).

Runtime Worker Pool (crate runtime-worker) owns model memory residency, execution threads, CUDA streams, execution queues, allocator management. Crash-isolation boundary: one OS process per worker; a worker crash cannot corrupt another worker's state (I9).

Inference Runtime (inside runtime-worker, behind the RuntimeExecutor trait, §11) provides ONNX execution, TensorRT integration, tensor validation, execution-graph dispatch, memory binding. FFI boundary: isolated behind a stable executor trait so CUDA/TensorRT failures cannot propagate undefined behavior into the scheduler.

Telemetry Pipeline (crate telemetry) captures metrics, traces, structured logs, scheduler decisions, replay identifiers, queue timing. Critical invariant: telemetry emission must never block inference execution (I7) — enforced via a bounded MPSC with drop-oldest overflow.

Replay + Audit Store (crate replay) persists request metadata, deterministic execution traces, scheduler decisions, rollout history, failure snapshots for debugging, postmortems, regression reproduction, and conformance replay. Persistence boundary: append-only log (I2).

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every scheduler decision, batch composition, and routing operation must be reconstructable from durable inputs. · Tradeoff: forbids randomized tie-breaking and wall-clock-only ordering in hot paths. · Operational: replay (§19) must regenerate byte-identical scheduler traces. · Violated: replay divergence (Pitfall §19.6) makes incident postmortems unfalsifiable.
  • P2 — Backpressure Everywhere. Rule: every queue (admission, batch, telemetry, replay-write) is bounded with an explicit shed policy. · Tradeoff: bounded queues reject load a naive unbounded queue would silently absorb. · Operational: queue_depth_limit_violation fires before OOM. · Violated: unbounded growth hides overload until the node OOMs cluster-wide (I1).
  • P3 — Crash-Only Workers. Rule: workers tolerate SIGKILL at any point; recovery is restart-driven, never mutable in-place repair. · Tradeoff: forfeits partial-state salvage that a graceful-degradation path could offer. · Operational: worker_restart_count and lease reassignment on heartbeat expiry. · Violated: in-place repair after partial GPU-memory corruption risks silent wrong-answer inference (I9).
  • P4 — Observability by Default. Rule: every critical-path operation emits a trace span, a metric, and a correlation ID with zero opt-in configuration. · Tradeoff: baseline telemetry overhead (< 3% CPU, §4) even when nobody is watching. · Operational: dashboards derive directly from span names, no bespoke per-team instrumentation. · Violated: an uninstrumented path is invisible exactly when it fails (I7).
  • P5 — Stable Wire Compatibility. Rule: protocol compatibility never breaks within a major version; fields are append-only. · Tradeoff: dead fields accumulate until the next major bump. · Operational: compatibility test suite gates every release (I4). · Violated: an SDK on N-1 silently misparses responses mid-rollout.
  • P6 — Explicit Ownership. Rule: shared mutable state is minimized; state transitions happen via atomic snapshot swap, not in-place mutation under a lock. · Tradeoff: extra allocation per snapshot versus in-place mutation's lower allocation, higher contention. · Operational: worker and routing-table updates are atomic-pointer swaps (§11). · Violated: torn reads under concurrent mutation produce inconsistent placement decisions.
  • P7 — Resource Accounting is Mandatory. Rule: every tenant, queue, model, and worker carries a measurable, enforced budget. · Tradeoff: bookkeeping overhead on every admission decision. · Operational: quota tables are queryable via the control-plane API. · Violated: one tenant's spike silently starves every other tenant (I3).
  • P8 — Replayability First. Rule: every scheduler decision and execution result is reconstructable from the append-only replay log. · Tradeoff: durability-write latency on the critical path (bounded to < 2 s, §4). · Operational: replay determinism target > 99.99% (§18.4 analog, §19.4). · Violated: an incident with no replay trail cannot be root-caused (I2).
  • P9 — Isolation Before Throughput. Rule: no throughput optimization may cross a tenant-isolation boundary. · Tradeoff: forgoes cross-tenant batch coalescing that would raise GPU utilization. · Operational: per-tenant fairness variance monitored continuously (I3). · Violated: cross-tenant batching leaks timing side-channels and starves low-volume tenants.
  • P10 — Bounded Memory Usage. Rule: every allocator (host and pinned-GPU) exposes a hard ceiling and rejects allocation past it rather than growing unbounded. · Tradeoff: legitimate bursty workloads see admission rejection instead of graceful degradation. · Operational: allocator telemetry exports current/ceiling per pool (I8). · Violated: unbounded growth triggers the OOM killer mid-batch, losing every in-flight request in that batch.
  • P11 — Fail Closed on Ambiguity. Rule: when a state transition's correctness cannot be verified (partial model load, expired lease, unknown schema version), the system refuses the operation rather than guessing. · Tradeoff: availability loss during ambiguous windows versus best-effort continuation. · Operational: residency state machine (§16.2) rejects execution against partially-loaded models (I5). · Violated: guessing on ambiguous state is the direct cause of the model-residency and replay-integrity invariant classes (I5, I2).
  • P12 — Single Writer Per Mutable Resource. Rule: every mutable resource (lease, batch queue slot, artifact manifest) has exactly one owning writer at a time, enforced by lease expiry or atomic CAS, never by advisory convention. · Tradeoff: writer handoff latency (lease-expiry window) versus lock-free multi-writer throughput. · Operational: lease uniqueness enforced by the scheduler's lease manager (§16.2, I6). · Violated: two workers holding the same lease is the precondition for double-execution and corrupted replay records.

I9 Worker state after crash is fully reconstructable from the durable log. Crash-only recovery (P3). Runtime worker + replay (§17, §19) Post-restart reconciliation check worker_restart_count Restart, replay-driven lease reacquire
I10 Batch composition is reproducible from the replay log for a given batch_id. Determinism over convenience (P1). Batch engine (§15) Batch-replay hash comparison batch_replay_divergence_total Reject non-reproducing replay, flag for review
I11 Artifact content hash is fixed once published to the registry. Registry entries must be forensically stable (P8). Model registry (§18) Checksum verification on fetch artifact_checksum_mismatch_total Reject artifact, alert, re-publish under new version
I12 Duplicate request_id within the replay window is rejected, not re-executed. Idempotency under retry storms (P2, P1). Admission controller + replay index (§14, §19) Replay-index dedup lookup duplicate_request_rejected_total Return cached terminal state

Debugging methodology. Every invariant above is validated by exactly one assertion inside a deterministic simulator (crate testing, §11): a virtual clock (SimClock, §11) replaces wall-clock time, RNG is seeded, and network/GPU faults are injected via the same fixture format used in each phase's Conformance Fixtures (N.5). One assertion per invariant means a violated invariant maps to exactly one failing test, not a diffuse integration-test failure — the simulator runs the full request lifecycle (§8.2) with fault injection at each state-machine transition (§8.3) and diffs the resulting replay log against the expected trace.

11. Core Schema & Types

WorkerDescriptor — ownership: scheduler-owned, workers publish updates via heartbeat; mutation: immutable snapshot, replaced by atomic-pointer swap (P6); concurrency: Arc<WorkerDescriptor>, lock-free reads; persistence: transient, rebuilt from heartbeat stream on scheduler restart; serialization: protobuf, internal-only (not wire-versioned); compatibility: additive-fields only.

struct WorkerDescriptor
    worker_id: WorkerId
    node_id: NodeId
    numa_zone: NumaZoneId
    gpu_inventory: Vec<GpuDescriptor>
    memory_capacity_bytes: u64
    active_leases: Vec<LeaseId>
    health_state: HealthState
    runtime_version: SemVer

BatchDescriptor — ownership: batch engine, single-writer until dispatch (P12); mutation: mutable during accumulation, frozen at dispatch; concurrency: owned by one batching-engine task, no cross-task sharing; persistence: transient, snapshot written to replay at dispatch (I10); serialization: protobuf, internal; compatibility: additive-fields only.

struct BatchDescriptor
    batch_id: BatchId
    model_key: ModelKey
    request_ids: Vec<RequestId>
    tensor_shape: TensorShape
    creation_timestamp: MonotonicTs
    dispatch_deadline: MonotonicTs
    estimated_memory_bytes: u64

ReplayRecord — ownership: replay store, append-only writer; mutation: immutable once appended (P1, I2); concurrency: single-writer append log, many-reader; persistence: durable, append-only file/log-structured store; serialization: protobuf, wire-versioned (I4); compatibility: append-only field evolution, enforced by CI (ADR-19 analog).

struct ReplayRecord
    replay_id: ReplayId
    scheduler_decision: SchedulerDecisionRef
    worker_assignment: WorkerId
    serialized_request: Bytes
    runtime_metadata: RuntimeMetadata
    execution_hash: Blake3Hash

SchedulerLease — ownership: scheduler lease manager, single owning worker (I6, P12); mutation: revoked on expiry, never mutated in place; concurrency: CAS-based acquire/release; persistence: transient with replay-log audit trail; serialization: protobuf, internal; compatibility: additive-fields only.

struct SchedulerLease
    lease_id: LeaseId
    worker_id: WorkerId
    model_key: ModelKey
    expiration_timestamp: MonotonicTs
    resource_vector: ResourceVector
    fencing_token: u64

TenantQuota — ownership: admission controller; mutation: updated via control-plane API, applied atomically; concurrency: Arc<TenantQuota> snapshot per tenant, swapped on update; persistence: durable in control-plane config store; serialization: protobuf; compatibility: additive-fields.

struct TenantQuota
    tenant_id: TenantId
    max_queue_depth: u32
    max_concurrency: u32
    tokens_per_second: f64
    fairness_weight: f64

ModelManifest — ownership: registry, immutable once published (I11); mutation: none post-publish; concurrency: read-only after publish, safe for unsynchronized concurrent reads; persistence: durable in registry metadata store; serialization: protobuf; compatibility: new versions are new manifests, never in-place edits.

struct ModelManifest
    model_key: ModelKey
    version: SemVer
    content_hash: Blake3Hash
    artifact_uri: Uri
    tensor_input_spec: TensorSpec
    tensor_output_spec: TensorSpec
    rollout_state: RolloutState

AdmissionTicket — ownership: admission controller, per-request; mutation: state advances forward only through §8.3's state machine; concurrency: owned by the request's async task; persistence: transient; serialization: not wire-exposed; compatibility: internal-only, no compat guarantee.

struct AdmissionTicket
    request_id: RequestId
    tenant_id: TenantId
    enqueue_timestamp: MonotonicTs
    state: RequestState
    shed_reason: Option<ShedReason>

RuntimeExecutor trait — ownership: implemented per backend (ONNX, TensorRT); mutation: methods take &mut self for load/unload, &self for execute/health; concurrency: not Sync — one executor instance per worker thread pool slot; persistence: n/a (in-memory runtime object); serialization: n/a; compatibility: trait is the executor stability boundary (§3.2).

trait RuntimeExecutor
    fn load_model(&mut self, manifest: &ModelManifest) -> Result<(), LoadError>;
    fn unload_model(&mut self, model_key: &ModelKey) -> Result<(), UnloadError>;
    fn execute_batch(&self, batch: &BatchDescriptor) -> Result<BatchOutput, ExecError>;
    fn health_check(&self) -> HealthState;
    fn collect_runtime_metrics(&self) -> RuntimeMetrics;

RoutingTableSnapshot — ownership: router, rebuilt from registry + scheduler state; mutation: whole-snapshot atomic swap, never partial mutation (P6); concurrency: Arc<RoutingTableSnapshot>, lock-free reads on the request-dispatch hot path; persistence: none, rebuildable; serialization: internal only; compatibility: n/a.

struct RoutingTableSnapshot
    generation: u64
    tenant_partitions: HashMap<TenantId, PartitionId>
    model_routes: HashMap<ModelKey, Vec<WorkerId>>
    draining_workers: HashSet<WorkerId>

13.6 Pitfalls

  • mTLS cert-rotation race. Manifestation: brief window of connection rejects during rotation. Root cause: old and new cert not overlapped. Mitigation: dual-cert overlap window during rotation.

13.7 Performance Concerns

TLS handshake cost dominates cold-connection latency — mitigate via session resumption; allocator churn from per-request protobuf deserialization — mitigate via buffer pooling; serialization overhead on large tensor payloads approaching the 16 MB cap.

13.8 Edge Cases

Half-open TCP sessions after a client-side crash; duplicated request_id from a retrying client (must be idempotent, I12); replayed authentication tokens outside their validity window; a client that sets replay_enabled=true but never completes the request (partial replay artifact, §19.8).

13.9 Failure Analysis

Gateway saturation causes queue spillover into the admission controller and cluster-wide tail amplification (P2). Detection: connection_accept_latency histogram p99 crossing threshold. Blast radius: bounded to the gateway's own accept queue if admission-controller backpressure (§14) holds; unbounded if it does not. Containment: L4 load-balancer health-check ejection of the saturated gateway instance. Manual recovery: scale the gateway tier horizontally (stateless, §3.2).

13.10 Operational Notes

Gateway dashboards are mandatory before production traffic (P4); deploy behind an L4 load balancer, never expose gateway pods directly; mTLS cert rotation is automated, not a manual runbook step. Metrics: connection_accept_latency, gateway_request_total{error_code}. Trace span: gateway.ingress. Structured-log fields: request_id, tenant_id, error_code.

  • Scheduler cache staleness. Manifestation: placements target an already-evicted worker. Root cause: cache invalidation lagging the registry generation counter. 16.8 Edge Cases

16.9 Failure Analysis

Containment: lease invalidation via a forced fencing-token bump across all active leases. Detection: lease_conflict_total (I6) crossing zero unexpectedly. Manual recovery: operator-triggered scheduler failover using tools/scheduler-debug snapshots.

16.10 Operational Notes

Metrics: scheduler_decision_latency, lease_conflict_total, starvation_window_seconds (shared with I3). Trace span: scheduler.place. Rollback: a bad scoring-function deploy is reverted via the experimental release channel (ADR-18) before promotion to stable.

19.6 Pitfalls

  • Replay divergence. Manifestation: replayed execution hash differs from the original. Root cause: a code path reading wall-clock time instead of SimClock during the original execution. Debugging: bisect the execution trace for a non-deterministic input (RNG, wall-clock, HashMap iteration order). Recovery: replace the offending call with the deterministic equivalent; flag historical records recorded before the fix as divergence_suspect rather than silently trusting them.
  • Telemetry storms. Manifestation: exporter queue saturates, triggering the drop-oldest path under normal load, not just incidents. Root cause: sampling rate too low for current cardinality. Mitigation: adaptive sampling keyed off current exporter-queue depth.
  • Replay-log compaction data loss. Manifestation: a compacted record is missing on read. Root cause: compaction boundary computed before a concurrent writer's fsync completed. Mitigation: compaction watermark must be strictly behind the last fsync-confirmed offset.

19.7 Performance Concerns

Exporter-queue pressure under high span-cardinality workloads; serialization overhead of the structured-log pipeline at high request rates; replay-log compaction I/O competing with the live write path for NVMe bandwidth (mitigate via compaction rate-limiting).

19.8 Edge Cases

Partial replay artifacts from a worker crash mid-write; missing spans when a trace-context propagation hop is skipped (e.g., a fire-and-forget internal call); replay of a request whose artifact has since been garbage-collected (§18.2 step 15) — must fail closed (P11), not reconstruct against a different artifact version; clock skew (§4) between SimClock and a cross-region replica's clock (relevant ahead of §21).

19.9 Failure Analysis

Telemetry-pipeline outage degrades debugging capability but inference execution must continue unaffected (I7) — this is the load-bearing test of the non-blocking invariant. Detection: exporter health-check failure. Blast radius: observability only, never correctness, by construction. Manual recovery: restart the exporter sidecar; replay log itself is unaffected since it is a separate durable write path from the metrics/trace exporters.

19.10 Operational Notes

Replay-retention policy is mandatory and audited (§18.10 cross-reference); replay export requires RBAC-gated access (ADR-17). Metrics: telemetry_drop_total (I7), replay_checksum_mismatch_total (I2), batch_replay_divergence_total (I10). Trace span: telemetry.export. Structured-log fields: request_id, trace_id, replay_token.

20. Phase 8 — Advanced Scheduling: Tensor Parallelism and Dynamic Graph Compilation

20.1 Objectives

Undefer tensor parallelism and dynamic graph compilation, both out of scope for §1's Phase 0 deliverable: extend the scheduler (§16) to place a single model's execution across multiple GPUs and to select between precompiled and dynamically compiled execution graphs per request shape.

20.2 Detailed Implementation Steps

  1. Extend WorkerDescriptor (§11) with a gpu_group_id field for tensor-parallel shard membership.
  2. Add a shard-placement scorer in scheduler/src/placement.rs requiring all shards of a tensor-parallel group to satisfy NUMA/PCIe-topology locality (extends §16.2 step 4/5).
  3. Add a cross-shard lease group: one logical lease spanning N physical SchedulerLease records, fenced together (extends I6 to a group invariant).
  4. Add an execution-graph cache keyed on (model_key, input_shape_bucket) distinguishing precompiled graphs from dynamically compiled ones.
  5. Add a graph-compilation decision point in the runtime worker: below a shape-frequency threshold, dispatch to a generic interpreted path; above it, trigger ahead-of-time compilation.
  6. Add compilation-latency budgeting so a cold compile never blocks the request that triggered it — the triggering request executes on the interpreted path (fail-closed-on-ambiguity analog, P11).
  7. Add cross-shard collective-communication telemetry (shard_sync_latency_ns).
  8. Add shard-failure containment: one shard's crash fails the whole tensor-parallel group's in-flight batch, but only that group (bounded blast radius, extends I9).
  9. Add a compiled-graph cache-eviction policy under memory pressure, LRU-by-compile-cost.
  10. Add replay support for graph-selection decisions (extends I10 to cover which graph variant ran).
  11. Add a scheduling-simulation extension (§16.2 step 19) covering multi-shard placement failures.
  12. Add benchmark coverage comparing interpreted vs. compiled-graph latency distributions.
  13. Add conformance fixtures for shard-count mismatches and partial-shard placement failures.
  14. Add telemetry for compiled-graph cache-hit ratio.
  15. Add a rollback path: disabling tensor parallelism for a model_key reverts to single-GPU placement without a full redeploy (feature-flag registry, §12.2 step 17).
  16. Add cross-shard deadline propagation so all shards share one execution deadline.
  17. Add NUMA/PCIe topology discovery feeding the shard-placement scorer.
  18. Add documentation of the shard-group replay format in docs/architecture.md.

20.3 Deliverable

A model_key flagged for tensor parallelism executes as a coordinated multi-GPU shard group with a single logical lease; frequently-shaped requests transparently upgrade to a compiled execution graph without operator intervention.

20.4 Acceptance Criteria

Shard-group placement succeeds or fails atomically (0 partial-shard placements across 1,000 induced trials in fixtures/scheduling/shard_placement.json); compiled-graph path reduces p50 latency by

20% over the interpreted path for shapes above the compilation-frequency threshold; cross-shard deadline propagation keeps all shards within 1 ms of each other's effective deadline.

20.5 Conformance Fixtures

  • fixtures/scheduling/shard_placement.json — induced partial-capacity cluster; expected: atomic accept/reject, 0 partial-shard grants.
  • fixtures/scheduling/graph_compile_cold.json — first-seen shape bucket; expected: interpreted-path execution, compilation triggered asynchronously, cache populated for next request.
  • fixtures/scheduling/shard_failure.json — one shard crashes mid-execution; expected: whole group fails cleanly, other shard-groups on the same workers unaffected.

20.6 Pitfalls

  • Shard-group partial placement. Manifestation: some shards land, others don't, corrupting the group. Root cause: non-atomic multi-shard lease acquisition. Mitigation: two-phase lease acquisition — reserve all shards, commit only if all reservations succeed (extends P12).
  • Compile-cache thrash. Manifestation: compiled-graph cache-hit ratio collapses under high-shape-cardinality traffic. Root cause: eviction policy not accounting for compile cost. Mitigation: LRU-by-compile-cost eviction (§20.2 step 9), not plain LRU.
  • Cross-shard deadline skew. Manifestation: one shard times out while siblings are still running, wasting GPU cycles. Mitigation: shared-deadline propagation (§20.2 step 16) enforced at dispatch, not per-shard independently.

20.7 Performance Concerns

Collective-communication overhead (shard-sync) can dominate for small tensor-parallel groups — only worth it above a model-size threshold; compiled-graph compilation itself is CPU/GPU-cycle expensive and must be rate-limited against the telemetry-overhead-class budget (§4 analog); topology-unaware shard placement adds cross-PCIe-switch latency.

20.8 Edge Cases

A shard group where one shard's worker is evicted mid-execution; a compile request racing a concurrent cache-eviction of the same cache slot; a model_key transitioning from tensor-parallel to single-GPU mid-rollout; a compiled graph whose cached version becomes incompatible after a runtime executor upgrade.

20.9 Failure Analysis

A shard-group failure's blast radius is bounded to that group's in-flight batch — sibling shard-groups on the same physical workers are unaffected because leases are per-group, not per-worker (extends I6). Detection: shard_sync_latency_ns timeout or a shard health-probe failure. Manual recovery: operator disables tensor parallelism for the affected model_key via the rollback path (§20.2 step 15) pending root-cause.

20.10 Operational Notes

Shard-group topology and compiled-graph cache state are exportable via the scheduler debug snapshot (§16.10) extended with shard-group fields. Metrics: shard_sync_latency_ns, compiled_graph_cache_hit_ratio. Trace span: scheduler.place_shard_group. Deployment: tensor parallelism is opt-in per model_key via the feature-flag registry, never cluster-wide by default.

21. Phase 9 — Multi-Region Replication and Elastic Cold-Start Pooling

21.1 Objectives

Undefer multi-region replication and serverless cold-start pooling, both out of scope for §1's Phase 0 deliverable: replicate registry/replay durability across regions and maintain a warm-worker pool to bound cold-start latency for infrequently used models.

21.2 Detailed Implementation Steps

  1. Add cross-region artifact replication in storage/src/s3_backend.rs, async and eventually consistent, never blocking a local publish (extends ADR-04).
  2. Add cross-region replay-log replication with region-local durability first, cross-region replication best-effort (preserves I2's local guarantee unconditionally).
  3. Add a region-affinity field to RoutingTableSnapshot (§11) so tenants can pin to a home region.
  4. Add cross-region failover routing: on home-region unavailability, the gateway (§13) fails over to the nearest healthy region within the RTO budget (§4, < 10 min).
  5. Add a warm-worker pool manager tracking a small standing set of pre-loaded-but-idle workers per frequently-cold model tier.
  6. Add cold-start prediction: a lightweight heuristic (recent-request-rate decay) deciding which models stay warm-pooled versus fully evicted.
  7. Add pool-scale-out triggers tied to admission-queue depth (§14.2 step 5) crossing a threshold for a model with no warm worker available.
  8. Add pool-scale-in triggers on sustained idle, respecting the graceful-shutdown window (§4, 30 s).
  9. Add cross-region conflict resolution for registry publishes that race across regions (last- writer-wins on content hash, never on wall-clock timestamp — determinism, P1).
  10. Add cross-region telemetry aggregation distinguishing per-region metrics from cluster-global rollups.
  11. Add a region-partition simulation extension to the Phase-0 SimClock harness covering inter-region replication lag.
  12. Add conformance fixtures for region failover and warm-pool cold-start latency.
  13. Add cost/utilization telemetry for the warm-pool (warm_pool_utilization_ratio).
  14. Add a manual region-failover admin API endpoint (control-plane, §12.2).
  15. Add cross-region compatibility checks: a region running an older wire version rejects replication from a newer one until upgraded (extends I4 across regions).
  16. Add replication-lag alerting distinct from the intra-region RPO budget (§4).
  17. Add documentation of the region-failover runbook in docs/runbooks/.
  18. Add a warm-pool eviction audit trail feeding the replay log (P8).

21.3 Deliverable

A tenant's traffic survives full home-region unavailability by failing over within the RTO budget; infrequently used models serve their first post-idle request from a warm pool instead of paying a full 15 s cold-start (§4).

21.4 Acceptance Criteria

Region failover completes within the 10-minute RTO (§4) in fixtures/multiregion/failover.json; warm-pool hit reduces cold-start latency from the 15 s worker-startup budget (§4) to < 2 s for pooled models in fixtures/multiregion/warmpool_hit.json; 0 lost replay records across a simulated region partition of up to the RPO budget's duration (< 5 s, §4).

21.5 Conformance Fixtures

  • fixtures/multiregion/failover.json — induced home-region outage; expected: failover completes within RTO, 0 duplicate-request execution (I12 across regions).
  • fixtures/multiregion/warmpool_hit.json — request against a warm-pooled cold model; expected: execution latency < 2 s, no full model-load path taken.
  • fixtures/multiregion/replication_conflict.json — concurrent cross-region publish of the same model_key; expected: deterministic content-hash-based resolution, not wall-clock-based.

21.6 Pitfalls

  • Replication lag masking data loss. Manifestation: cross-region replica appears healthy but is missing recent replay records. Root cause: best-effort replication silently falling behind under network partition. Mitigation: replication-lag alerting (§21.2 step 16) distinct from the local RPO check — never assume cross-region replication satisfies the local durability guarantee (I2).
  • Warm-pool thrash. Manifestation: pool scale-out/scale-in oscillates under bursty-but-sparse traffic. Root cause: cold-start-prediction heuristic reacting to noise, not signal. Mitigation: hysteresis in the scale-out/scale-in triggers (§21.2 steps 7-8).
  • Cross-region duplicate execution. Manifestation: a failed-over request executes twice, once in each region. Root cause: I12's dedup index is region-local, not cross-region-aware. Mitigation: the failover path must consult the origin region's replay index before executing, even in degraded mode (extends I12).

21.7 Performance Concerns

Cross-region replication bandwidth competes with the artifact-download budget (§4, 25GbE); warm-pool standing capacity is a direct cost/latency tradeoff — oversized pools waste GPU capacity, undersized pools defeat the purpose; failover routing decision latency must not itself become a tail-latency contributor.

21.8 Edge Cases

A region partition that heals mid-failover, requiring reconciliation of two regions' independent progress; a warm-pooled model whose manifest is superseded while pooled (must reload, not serve stale); simultaneous home-region outages for two regions that are each other's failover target (must degrade to a third region or fail closed, P11); clock skew (§4) across regions affecting replication-order resolution.

21.9 Failure Analysis

A home-region outage's blast radius is contained to that region's tenants during the failover window (bounded by the 10-minute RTO, §4); cross-region replication failures degrade replay completeness for the affected window but never corrupt local durability (I2 stays region-local and unconditional). Detection: replication-lag alert plus region health-check failure. Manual recovery: admin-triggered manual failover via the control-plane endpoint (§21.2 step 14) if automatic failover does not trigger within budget.

21.10 Operational Notes

Region-failover runbooks are mandatory operator documentation (docs/runbooks/); warm-pool utilization is a P4-required dashboard alongside cost telemetry. Metrics: warm_pool_utilization_ratio, cross-region replication_lag_seconds. Trace span: multiregion.failover. Deployment: warm-pool sizing is per-region config, tuned independently per regional traffic pattern, never a single global constant.

24. Operational Readiness

Metrics strategy. Mandatory metrics across every phase: request latency (p50/p95/p99), scheduler decision latency, queue age, GPU utilization, allocator fragmentation ratio, replay lag, worker restart count, admission rejection rate, cross-region replication lag. Every metric maps to exactly one invariant (§7) or one §28 target — a metric with no owning invariant or target is removed, not accumulated (P4 without accumulation debt).

Alerting philosophy. Alerts fire only for actionable conditions: customer-visible degradation (p99 breach, §4), invariant violations (any I1-I12 detection signal, §7), or budget exhaustion (error budget, §4). No alert fires on a metric with no runbook — every alert in docs/runbooks/ has a corresponding page.

Deployment strategy. Rolling upgrades with per-shard draining (§14.2 step 4); canary deployment for model rollout (§18) and for binary releases via the release-channel ladder (§27); automated rollback triggered by acceptance-criteria regression in any phase's N.4 target; schema-compatibility checks (I4) gate every deploy, not just major-version deploys.

On-call ergonomics. Every P1/P2 alert links directly to: the owning invariant (§7), the relevant phase's Failure Analysis (N.9), and a docs/runbooks/ page. No alert requires an on-call engineer to first locate the owning subsystem — the alert payload names it.

25. Compatibility & Versioning

Wire compatibility. Protobuf fields are append-only (§11); field removal is forbidden within a major version (I4). New optional fields (e.g., shard-group metadata, §20) never change the meaning of an existing field. SemVer 2.0.0 (§5) governs the wire-schema major/minor/patch semantics.

Storage compatibility. The replay schema (§19, I2) is append-only — a schema evolution adds a new record variant, never reinterprets an old one. The registry manifest schema (§18, I11) follows the same rule: a manifest is versioned data, not a mutable row.

Upgrade guarantees. N-1 worker compatibility is required during rolling upgrade (I4): a router on version N must be able to dispatch to a worker on version N-1 for the duration of a rollout. The compatibility test suite (§26) gates every release against this guarantee before promotion past the experimental channel (§27, ADR-18).

Cross-region versioning (§21). A region running an older wire version rejects replication input from a newer region until it upgrades — this extends I4 across the replication boundary rather than allowing silent partial-understanding of newer fields.

26. Testing & Verification Strategy

Unit testing. Required coverage: scheduler scoring functions (§16), queue semantics (§14), runtime allocators (§17, I8), replay-record encode/decode (§19, I2). Every N.4 acceptance criterion across all ten phases has at least one corresponding unit or integration test.

Integration testing. Scenarios: rolling deployment (§18), worker crash recovery (§17, I9), full replay reconstruction (§19, I2), shard-group placement (§20), region failover (§21). Each scenario runs against the Phase-0 SimClock harness (§12.2 step 9) for determinism.

Fuzzing. Targets: protobuf decoders (fuzz/fuzz_targets/proto_decode.rs), tensor-shape validators (tensor_validate.rs), replay-log parsers (replay_parse.rs) — all via cargo-fuzz (ADR-13). Fuzzing runs on a schedule (.github/workflows/fuzz.yml), not only pre-release.

Chaos testing. Faults injected: packet loss, worker crashes, scheduler restarts, artifact corruption, region partition (§21), shard failure (§20). Chaos runs assert on the same invariants (§7) as the deterministic simulator — a chaos-induced invariant violation is a P1 bug, not an expected outcome.

Conformance suite. Every phase's N.5 fixtures are aggregated into conformance/ and run as a single gate before any release-channel promotion (§27); a new fixture is added for every incident postmortem (§23 Forensics column) that reveals a gap.

27. Build & Release Engineering

Reproducible builds. Pinned toolchain (rust-toolchain.toml, ADR-19), deterministic linker flags, immutable Cargo.lock. Two clean-room builds from the same commit produce identical binary hashes (§12.4 acceptance criterion) — this is verified on every CI run, not just at release time.

Supply-chain verification. SBOM generation (SPDX format, §5) on every build; dependency scanning via cargo-deny (ADR-03) blocking critical/high advisories; signed release artifacts verified before deployment (T8, T10, §22).

Release channels. Three channels: experimental (every merge to main), stable (weekly promotion after the conformance suite and 24h soak pass), LTS (quarterly, extended patch support, ADR-18). Promotion between channels requires the full N.4 acceptance-criteria set across all ten phases to pass, not just the changed phase's.

28. Performance Engineering

Benchmarking strategy. Criterion-based benchmarks (ADR-12) for gateway throughput, scheduler latency, batch efficiency, GPU utilization, replay overhead — one benchmark file per concern in benchmarks/ (§10). Every benchmark asserts against a §4 budget, not just reports a number.

Profiling workflow. Tools: perf and flamegraphs (Gregg, §5) for CPU hot paths; eBPF for syscall/scheduler-latency tracing; tokio-console-class introspection for the async reactor (gateway/router/admission, never the runtime-worker's dedicated execution threads, §17.6); NVIDIA Nsight for CUDA-stream and kernel-launch analysis.

Tail-latency analysis. Focus areas: queue amplification (Dean & Barroso, §5) at the admission and batch layers; allocator pauses under fragmentation pressure (§4 <15% budget); GPU synchronization stalls from oversubscribed CUDA streams (§17.7).

29. Scalability Analysis

Bottlenecks. Primary scaling ceilings, in order of onset: scheduler coordination (§16, becomes dominant past ~500 nodes per the horizontal-scaling budget, §4); telemetry ingestion (§19, exporter fanout grows with request rate, not node count); model distribution (§18, artifact-fetch bandwidth bounded by the 25GbE assumption, §4); GPU-memory fragmentation (§17, worsens with model-cardinality, not raw request rate).

Horizontal scaling. Stateless ingress (gateway, §13) scales linearly with no coordination overhead; partitioned scheduler domains (a §16 extension not yet built in Phase 4, candidate future work) would relax the 500-node linear-scaling ceiling; the distributed artifact cache (§18) already scales read fan-out independent of write (publish) rate.

Metadata scaling. Registry metadata (§18) partitions by tenant, deployment, and model family — this bounds any single registry replica's working set to one partition's manifests, not the global set, which is what keeps rollback latency (M9, §28) flat as tenant count grows toward the 50,000 ceiling (§4).

Cross-region scaling (§21). Multi-region replication adds a second scaling axis orthogonal to cluster size: per-region capacity scales independently, but replication-lag (T9, §22) grows with the number of regions squared if replication is naively all-to-all — the region-affinity routing (§21.2 step 3) exists specifically to avoid needing all-to-all replication for the common case.

30. Mental Models & First Principles

  • MM1 — Batching is a latency/throughput exchange rate, not free throughput. Every millisecond of batch window borrowed from the latency budget buys queueing-theory throughput. Predicts: batch- window tuning has a hard ceiling set by the p50 budget (§4). Bug class without it: unbounded adaptive batch growth chasing throughput past the latency budget. Applies in §15.
  • MM2 — Leases are the concurrency-control primitive, not locks. A lease is time-bounded and fencible; a lock is not. Predicts scheduler behavior under partition (fencing, not blocking). Bug class without it: treating a distributed lease as a mutex and blocking on acquisition instead of failing closed. Applies in §16.
  • MM3 — Crash-only is a simplification, not a compromise. Restart-driven recovery is strictly simpler to verify than in-place partial repair. Predicts fewer recovery-path bugs over the system's lifetime. Bug class without it: "smart" partial-recovery code that reintroduces the corruption it was meant to fix. Applies in §17.
  • MM4 — Replay determinism is a testability property, not a nice-to-have. If a system can't replay a request, it can't prove a fix worked. Predicts incident MTTR directly. Bug class without it: shipping without a replay path and discovering the gap during the first real incident. Applies in §19.
  • MM5 — Backpressure without shedding is just a bigger buffer. A bounded queue with no shed policy only delays the OOM, it doesn't prevent it. Predicts eventual outage under sustained overload regardless of queue-size tuning. Bug class without it: bounded-but-blocking-forever enqueue code. Applies in §14.
  • MM6 — Fragmentation is a placement problem, not an allocator problem. GPU-memory fragmentation under heterogeneous model sizes is fundamentally bin-packing. Predicts fragmentation growth with model-size variance, not request rate. Bug class without it: trying to fix fragmentation purely with a smarter allocator instead of residency-aware placement. Applies in §16 and §17.
  • MM7 — Tail latency is dominated by the slowest constituent, not the average. p99 is set by fan-out and hedging behavior (Dean & Barroso, §5), not mean service time. Predicts why hedging and batching tradeoffs matter more than mean-case optimization. Bug class without it: optimizing average latency while p99 silently degrades. Applies in §14 and §28.
  • MM8 — Immutability turns concurrency bugs into staleness bugs. Immutable manifests and artifacts convert torn-write bugs into stale-read bugs, which are strictly easier to detect and bound. Predicts registry correctness under concurrent publish. Bug class without it: mutable- in-place metadata racing under concurrent access. Applies in §18.

32. Back-of-Envelope Capacity Model

  • C1 — FD budget check. 50,000 max concurrent requests/node × 4 FDs/request = 200,000 FDs, matching the 200k FD budget (§4) exactly.
  • C2 — Per-tenant queue memory ceiling. 10,000 max queue depth/tenant × 2 KB/AdmissionTicket = 20 MB per fully-saturated tenant queue, inside per-node memory (§4).
  • C3 — Cluster-wide tenant queue memory, worst case. 50,000 max tenants × 20 MB (C2) = 1,000 GB theoretical ceiling, bounded in practice by the per-node concurrent-tenant fraction, not raw tenant count.
  • C4 — Model-artifact NVMe cache footprint. 20 GB max artifact size × 10 concurrently resident models/node = 200 GB, inside the 512 GB max node memory (§4), leaving 312 GB headroom.
  • C5 — Worker startup transfer time. 20 GB artifact ÷ 1.5 GB/s effective NVMe-to-HBM transfer = 13.3 s, inside the 15 s worker-startup budget (§4).
  • C6 — Scheduler heartbeat fanout cost. 2,000 max cluster workers × 1 heartbeat/2s = 1,000 heartbeats/s per scheduler replica; 1,000 × 500 µs decision budget (§4) = 0.5 CPU-s/s, 50% of one core.
  • C7 — Replay-write bandwidth. 50,000 max concurrent requests/node × 1 KB/ReplayRecord ÷ 12 ms mean p50 residency (§4) = 4.17M records/s theoretical peak, driving the compaction requirement (§19.2 step 14).
  • C8 — GPU fragmentation ceiling, absolute. 24 GB GPU × 15% max fragmentation (§4) = 3.6 GB unusable-but-allocated headroom the residency scorer (§16) must plan around.
  • C9 — Storage amplification, absolute cost. 20 GB max artifact × 1.8x amplification target (§4) = 36 GB total stored per artifact version across the NVMe cache and object-store replica.
  • C10 — Error budget in request-equivalents. 21.6 min/month error budget × 60 s/min × 50,000 req/s peak throughput (§4) = 64.8M request-equivalents of monthly budget, sized against the 99.95% availability target.

33. Hard Questions (Self-Examination)

  • Q1. If the scheduler's placement-scoring loop (§16) must stay under the 500 µs decision budget (§4) while also accounting for tensor-parallel shard grouping (§20), which scoring term gets cut first under CPU pressure, and which invariant (§7) does cutting it risk?
  • Q2. Given the batch-formation window is bounded to 0.5-8 ms (§4) and the admission controller (§14) sheds load at queue-depth 10,000/tenant, at what arrival rate does the batch window become irrelevant because admission has already shed the excess?
  • Q3. Replay determinism (§19) requires SimClock everywhere, but multi-region replication (§21) introduces cross-region clock skew — how does replay distinguish legitimate cross-region ordering ambiguity from a real determinism bug?
  • Q4. Model-registry immutability (§18) and the compiled-graph cache (§20) both cache derived artifacts keyed on content — what invalidates the compiled-graph cache when the underlying manifest is superseded, and how does that differ from artifact GC in §18?
  • Q5. Warm-pool cold-start mitigation (§21) and fragmentation-aware placement (§16) pull in opposite directions — how should the scheduler arbitrate, and which §4 budget breaks first if it arbitrates wrong?
  • Q6. The crash-only worker principle (§17) says never repair in place, but tensor-parallel shard groups (§20) share a logical lease across physical leases — does a single-shard crash still satisfy crash-only, or does group semantics quietly reintroduce partial-repair behavior?
  • Q7. Telemetry must never block inference (§19), yet compiled-graph selection (§20) depends on timely telemetry-derived shape-frequency signals — what happens to graph-selection quality when telemetry backpressure triggers drop-oldest?
  • Q8. Fairness accounting (§14, §16) is per-tenant, but tensor-parallel shard groups (§20) consume multiple workers per logical request — does fairness accounting need to weight by shard count, and what breaks in TenantQuota (§11) if it doesn't?
  • Q9. Rollback (§18) and canary promotion share one rollout-state machine — if a canary is mid-promotion when rollback triggers, which state wins, and does the answer differ for a tensor-parallel model (§20) with shard-group state to unwind?
  • Q10. The replay-log compaction job and forensic export tooling (§19) both read the append-only log — what ordering guarantee must compaction respect, relative to the replay-durability-delay budget (§4), so a forensic export mid-compaction never sees a torn view?
  • Q11. Cross-region failover (§21) must complete within the RTO (§4), but re-establishing scheduler leases (§16) in the failover region requires fencing every ambiguous lease — does fencing-token generation scale linearly with cluster size, and does that fit inside the RTO at the cluster-size ceiling (§4)?
  • Q12. GPU-fragmentation-aware placement (§16) and the batch engine's padding policy (§15) both consume the same fragmentation budget (§4) — if both subsystems independently believe they have headroom, what detects the double-counted budget before a placement fails?
  • Q13. Wire-compatibility (§13, §25) guarantees N-1 SDK compatibility, but tensor-parallel and dynamic-graph-compilation fields (§20) are additive to the wire schema — does an N-1 SDK's ignorance of shard-group fields silently break replay reconstruction (§19) for requests it originated?
  • Q14. Deferred RDMA transport (§35, anchored at §13) would change the gateway's trust-boundary assumptions (§3) — which Threat Model rows (§22) would need re-derivation before RDMA could be undeferred, and why doesn't gRPC-over-TCP's current mitigation set simply carry over?
  • Q15. The admission controller's retry-budget accounting (§14) and the scheduler's lease-expiration recovery (§16) both re-queue work under failure — under a correlated multi-worker failure, can these two independent retry paths compound into a retry storm?
  • Q16. Multi-region replication (§21) makes the registry's immutable-once-published guarantee (§18) a per-region fact until replication completes — what is the actual consistency window, and which §32 capacity number bounds how long a cross-region reader can observe a stale manifest?
  • Q17. Speculative decoding, deferred at §17 and registered at §35, would produce variable-length outputs per request within a batch — what invariant in §15 would need redesign, not just extension, before speculative decoding could be undeferred?
  • Q18. The scheduler's fairness invariant (§16) and the warm-pool manager's cold-start prediction heuristic (§21) both make resource-allocation decisions ahead of demand — if the heuristic starts favoring one tenant's model family, does that constitute a fairness-invariant violation even though warm-pooling isn't itself a §16 scheduling decision?

34. Alternative Architectures (Roads Not Taken)

Alt A — Single-Process Multi-Model Server

+------------------------------------------+
|  One OS process                          |
|  +----------+ +----------+ +----------+  |
|  | Model A  | | Model B  | | Model C  |  |
|  +----------+ +----------+ +----------+  |
|  Shared HTTP server, shared memory space |
+------------------------------------------+

Wins when: model count is small, no cross-tenant isolation is needed, and the ops team wants zero cluster complexity. Embodied by: early single-node TensorFlow Serving deployments. Rejected because: fails tenant isolation (P9) and the horizontal-scaling target (§4, linear to 500 nodes) — a single process cannot span workers, and a crash takes every co-hosted model down at once (violates I9's bounded blast-radius intent).

Alt B — Actor-Model Distributed Scheduling

+---------+   +---------+   +---------+
| Actor A |   | Actor B |   | Actor C |   <- Ray core task/actor scheduler
+----+----+   +----+----+   +----+----+
     \            |             /
      \           |            /
       +----------+-----------+
       |   Ray Object Store    |
       +------------------------+

Wins when: inference is one stage in a broader distributed-Python pipeline needing general task composability. Embodied by: Ray Serve (Moritz et al., §5). Rejected because: general-purpose actor scheduling does not provide lease-based fencing (I6) or deterministic replay (P1, I2) without substantial custom layering on top of Ray core — this blueprint needs those as first-class, not bolted on.

Alt C — Fully Serverless, Cold-Start-Every-Time

Request -> [cold-start container] -> load model -> execute -> teardown
           (repeat in full for every request with no idle model)

Wins when: traffic is extremely bursty/infrequent and 15 s+ cold starts (§4) are acceptable. Embodied by: early FaaS-wrapped inference deployments (AWS Lambda + container image model loading). Rejected because: violates the p99 < 120 ms budget (§4) for any request that isn't already warm, and doesn't fit the elastic middle ground chosen in §21 (bounded warm-pool, not full serverless).

Alt D — Sidecar-per-Model-Instance via Service Mesh

+---------------------+
| K8s Pod              |
| +-----------------+ |
| | Runtime sidecar  | |    <- Triton/TFServing container
| +-----------------+ |
| +-----------------+ |
| | Mesh proxy       | |    <- Istio/Envoy handles routing, mTLS
| +-----------------+ |
+---------------------+

Wins when: the team is fully committed to Kubernetes-native tooling and wants autoscaling/canary handled by the mesh, not custom code. Embodied by: KServe's default deployment pattern. Rejected because: it delegates scheduling and batching entirely to the runtime underneath and the mesh — this blueprint needs first-class control over lease-based placement (§16) and dynamic batching (§15) that a mesh-sidecar model doesn't expose.

36. Glossary

  • Admission Control — the bounded-queue overload-protection layer between the router and the batch engine (§14).
  • Artifact Manifest — the immutable metadata record describing a published model version (§11, §18).
  • Backpressure — propagating a bounded-capacity signal upstream instead of buffering unboundedly (P2).
  • Batch Window — the maximum time a request waits for compatible peers before dispatch (§4, 0.5-8 ms).
  • Canary Deployment — a partial-traffic rollout of a new model version before full promotion (§18).
  • Compiled Graph — an ahead-of-time-compiled execution plan for a frequent input-shape bucket (§20).
  • Content Hash — the Blake3 digest identifying an immutable artifact (§11, I11).
  • Cross-Shard Deadline — a single execution deadline shared by every shard in a tensor-parallel group (§20).
  • Determinism — the property that identical inputs and clock state always produce identical outputs and traces (P1).
  • Drain Mode — graceful removal of a worker from routing before lease revocation (§14, §16).
  • Fairness Weight — a per-tenant scheduling weight bounding starvation (§11 TenantQuota, I3).
  • Fencing Token — a monotonically increasing value invalidating a stale lease holder's writes (I6).
  • Fragmentation — unusable memory segmentation from variable-size allocation over time (§4, §16).
  • Graceful Shutdown Window — the 30 s budget for draining in-flight work before SIGKILL (§4).
  • Lease — a time-bounded, fencible placement grant binding a batch to a worker (§11 SchedulerLease, I6).
  • Microbatch — a fallback batch of size 1 (or below target) dispatched at the timeout ceiling (§15).
  • Model Residency — the state of a model being fully loaded into a worker's execution memory (I5).
  • NUMA — non-uniform memory access; a memory-locality property the scheduler must be aware of (§4, §16).
  • Padding Policy — the rule set governing tensor-shape normalization inside a batch (§15).
  • Pinned Memory — non-pageable host memory used for faster host-device transfer (§17).
  • Placement Score — the scheduler's fitness metric combining NUMA, GPU-fit, and residency terms (§16).
  • Queue Age — how long a request has waited in the admission queue (§14).
  • Region Affinity — a tenant's preferred home region for routing under multi-region replication (§21).
  • Replay Determinism — the property that a replayed request reconstructs a byte-identical execution trace (I10, §19).
  • Replay Token — the identifier binding an InferenceResponse to its durable replay record (§8.4).
  • Residency Scoring — placement preference favoring workers that already have the target model loaded (§16).
  • RPO — Recovery Point Objective; maximum acceptable data loss window on failure (§4, < 5 s).
  • RTO — Recovery Time Objective; maximum acceptable time to restore service (§4, < 10 min).
  • Runtime Executor — the trait boundary isolating ONNX/TensorRT execution from the scheduler (§11).
  • Scheduler Domain — a placement-coordination partition of the cluster (§29, candidate future work).
  • Shard Group — the set of workers jointly executing one tensor-parallel model instance (§20).
  • Shed — rejecting a request rather than queueing it past a bounded limit (P2, I1).
  • Staged Rollout — the sequence of rollout states from canary through full promotion (§11 RolloutState, §18).
  • Starvation — a tenant's requests systematically failing to clear the queue due to unfair scheduling (I3).
  • Tail Latency — high-percentile (p95/p99) response delay, dominated by the slowest constituent (MM7, §5 Dean & Barroso).
  • Tenant — the logical multi-tenancy isolation boundary (§8, §11).
  • Tensor Parallelism — sharding a single model's execution across multiple GPUs as one logical unit (§20).
  • Warm Pool — a standing set of pre-loaded, idle workers reducing cold-start latency (§21).
  • Wire Compatibility — the guarantee that older SDKs remain functional across a rolling upgrade (I4, P5).
  • Worker Eviction — forced removal of a stale or unhealthy worker from the scheduler's registry (§16).
