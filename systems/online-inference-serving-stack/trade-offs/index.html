Decisions (§9) · 24 ADRs

ADR-01

Primary language

Chosen

Rust

Rejected

Go, C++

When the rejected choice is right

Go wins for short-lived CLI tooling with no tail-latency SLO; C++ wins when embedding directly into an existing C++/CUDA codebase with heavy template reuse

Why: Deterministic ownership, no GC pause amplification under p99 budget (§4)

ADR-02

Build system

Chosen

Cargo workspace

Rejected

Bazel/Buck2

When the rejected choice is right

Bazel wins past ~50 polyglot services needing a shared remote build cache across Rust+Python+C++

Why: Native Rust ergonomics, no polyglot build graph needed at 15-crate scale

ADR-03

Dependency policy

When the rejected choice is right

Unrestricted wins for internal prototypes with no supply-chain review budget

Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Single-Process Multi-Model Server

+------------------------------------------+
|  One OS process                          |
|  +----------+ +----------+ +----------+  |
|  | Model A  | | Model B  | | Model C  |  |
|  +----------+ +----------+ +----------+  |
|  Shared HTTP server, shared memory space |
+------------------------------------------+

Wins when: model count is small, no cross-tenant isolation is needed, and the ops team wants zero cluster complexity. Embodied by: early single-node TensorFlow Serving deployments. Rejected because: fails tenant isolation (P9) and the horizontal-scaling target (§4, linear to 500 nodes) — a single process cannot span workers, and a crash takes every co-hosted model down at once (violates I9's bounded blast-radius intent).

Alt B — Actor-Model Distributed Scheduling

+---------+   +---------+   +---------+
| Actor A |   | Actor B |   | Actor C |   <- Ray core task/actor scheduler
+----+----+   +----+----+   +----+----+
     \            |             /
      \           |            /
       +----------+-----------+
       |   Ray Object Store    |
       +------------------------+

Wins when: inference is one stage in a broader distributed-Python pipeline needing general task composability. Embodied by: Ray Serve (Moritz et al., §5). Rejected because: general-purpose actor scheduling does not provide lease-based fencing (I6) or deterministic replay (P1, I2) without substantial custom layering on top of Ray core — this blueprint needs those as first-class, not bolted on.

Alt C — Fully Serverless, Cold-Start-Every-Time

Request -> [cold-start container] -> load model -> execute -> teardown
           (repeat in full for every request with no idle model)

Wins when: traffic is extremely bursty/infrequent and 15 s+ cold starts (§4) are acceptable. Embodied by: early FaaS-wrapped inference deployments (AWS Lambda + container image model loading). Rejected because: violates the p99 < 120 ms budget (§4) for any request that isn't already warm, and doesn't fit the elastic middle ground chosen in §21 (bounded warm-pool, not full serverless).

Alt D — Sidecar-per-Model-Instance via Service Mesh

+---------------------+
| K8s Pod              |
| +-----------------+ |
| | Runtime sidecar  | |    <- Triton/TFServing container
| +-----------------+ |
| +-----------------+ |
| | Mesh proxy       | |    <- Istio/Envoy handles routing, mTLS
| +-----------------+ |
+---------------------+

Wins when: the team is fully committed to Kubernetes-native tooling and wants autoscaling/canary handled by the mesh, not custom code. Embodied by: KServe's default deployment pattern. Rejected because: it delegates scheduling and batching entirely to the runtime underneath and the mesh — this blueprint needs first-class control over lease-based placement (§16) and dynamic batching (§15) that a mesh-sidecar model doesn't expose.
