⬜ Phase 0 — Repository Bootstrap and Deterministic Foundations §12

Objectives

Establish deterministic build foundations, repository governance, CI validation, baseline observability contracts, and protocol schemas before any subsystem logic exists. Introduces the reproducibility (ADR-19) and dependency-policy (ADR-03) constraints every later phase inherits. Scope: workspace skeleton, protocol crate, CI matrix, telemetry abstraction, SimClock harness.

Deliverable

Workspace builds (cargo build --workspace); CI passes on the matrix; the protocol crate compiles and its fixtures round-trip; a no-op telemetry pipeline emits one trace span end-to-end; two clean-room builds produce identical binary hashes.

Acceptance

cargo test --workspace passes with 0 failures; two independent clean builds produce identical SHA-256 binary hashes; SBOM generated for all 15 crates; CI wall-clock runtime < 15 minutes; 0 critical/high cargo-deny advisories; fixtures/proto/valid_request.pb round-trips losslessly.

Fixtures
  • fixtures/proto/valid_request.pb — well-formed InferenceRequest; expected: decodes and re-encodes byte-identical.
  • fixtures/proto/invalid_field.pb — malformed field 7 (priority out of enum range); expected: decode error, not a panic.
  • fixtures/replay/minimal.trace — single-record replay log; expected: SimClock replay reconstructs the identical ReplayRecord (I2).
Pitfalls
  • Non-deterministic dependency versions. Manifestation: CI drift between runs. Root cause: unpinned transitive deps. Debugging: diff Cargo.lock across CI runs. Signal: lockfile mismatch in PR diff. Recovery: cargo update --locked gate in CI (ADR-19).
  • Trace-schema drift. Manifestation: dashboards silently stop populating. Root cause: span-field rename without a compatibility shim. Debugging: diff exported OTel schema against the pinned contract. Signal: telemetry_drop_total unexpectedly rising. Recovery: schema compatibility check as a CI gate (I7-adjacent).
  • Reproducible-build false negatives. Manifestation: identical source, different hash. Root cause: embedded build timestamp or absolute path in debug info. Debugging: diffoscope the two binaries. Signal: hash-compare CI step fails intermittently. Recovery: strip timestamps, use relative paths in linker flags.

⬜ Phase 1 — Gateway and Protocol Surface §13

Objectives

Implement secure network ingress: request validation, tracing, authentication, and quota enforcement (P4, P7). Introduces the trust boundary from §3.2 and the wire-compatibility invariant (I4). Builds on the protocol crate and telemetry abstraction from Phase 0 (§12).

Deliverable

External clients submit InferenceRequests over gRPC/HTTP-2; tracing works end-to-end from ingress through a stub downstream call; malformed requests are rejected with a typed error before reaching the router.

Acceptance

Sustains 25,000 req/s synthetic load with 0 dropped connections; 0 memory growth beyond 5% over a 24-hour soak; p99 ingress overhead < 5 ms (inside the p99 < 120 ms budget, §4); 100% of malformed fixtures in fixtures/gateway/ rejected with the correct error_code.

Fixtures
  • fixtures/gateway/oversized_payload.pb — 17 MB payload; expected: 400, error_code=PAYLOAD_TOO_LARGE.
  • fixtures/gateway/invalid_jwt.bin — expired signature; expected: 401, no downstream call made.
  • fixtures/gateway/malformed_protobuf.bin — truncated wire bytes; expected: decode error, not panic.
  • fixtures/gateway/timeout_propagation.json — deadline replay case; expected: downstream call cancelled at deadline, not after.
Pitfalls
  • Header amplification. Manifestation: single small request expands into gigabytes of trace metadata. Root cause: unbounded metadata propagation through the tracing context. Mitigation: header-count and per-header-size caps (§13.2 step 18).
  • Keepalive storms. Manifestation: connection-accept latency spikes under idle-connection churn. Mitigation: idle-connection enforcement with a bounded keepalive timeout.
  • mTLS cert-rotation race. Manifestation: brief window of connection rejects during rotation. Root cause: old and new cert not overlapped. Mitigation: dual-cert overlap window during rotation.

⬜ Phase 2 — Routing and Admission Control §14

Objectives

Implement deterministic routing and overload protection (P2, I1). Introduces the bounded-queue admission model that every downstream subsystem (batching, scheduler) depends on for backpressure propagation. Builds on the gateway's authenticated request stream (§13).

Deliverable

Requests route deterministically to the correct tenant/model partition; overload is shed with a typed error before consuming scheduler or worker resources; fairness variance is measurable via telemetry.

Acceptance

No queue exceeds the 10,000-entry per-tenant cap (§4) under 2x synthetic overload; starvation detector fires within 5 s of an induced imbalance in fixtures/admission/fairness_replay.json; fairness variance < 5% across 10 equal-weight tenants under load.

Fixtures
  • fixtures/admission/fairness_replay.json — 10-tenant weighted load; expected: variance < 5%.
  • fixtures/admission/overload_rejection.json — 3x rated load; expected: 100% of excess shed with error_code=OVERLOADED, 0% queue-depth breach.
  • fixtures/admission/draining.json — mid-rollout drain; expected: 0 requests routed to a draining worker after drain-complete signal.
Pitfalls
  • Retry storms. Manifestation: cascading queue collapse under transient failure. Root cause: unbudgeted client retries. Mitigation: retry-budget accounting (§14.2 step 11; Dean & Barroso, §5).
  • Tenant starvation. Manifestation: one tenant's requests never clear the queue. Detection: queue_age_seconds histogram tail. Mitigation: weighted-fair-queueing rebalance (I3).
  • Routing-cache staleness. Manifestation: requests routed to an already-drained worker. Root cause: generation-counter race between drain-signal and cache invalidation. Debugging: compare cache generation against router's authoritative generation. Recovery: force cache invalidation on drain-signal receipt, not on a timer.

⬜ Phase 3 — Dynamic Batch Engine §15

Objectives

Implement dynamic batching to trade a bounded latency window for GPU throughput (§4 batch-formation window 0.5-8 ms). Builds on admission-controller output (§14) and feeds the scheduler (§16).

Deliverable

Dynamic batching is operational: shape-compatible requests coalesce into batches within the configured window and dispatch to the scheduler with a reproducible batch_id.

Acceptance

Throughput improves > 3x over unbatched dispatch under fixtures/batching/synthetic_load.json; p99 latency stays under the 120 ms budget (§4) at 3x throughput; batch-replay hash matches original dispatch hash for 100% of fixtures/batching/batch_replay.json (I10).

Fixtures
  • fixtures/batching/incompatible_tensor.json — mismatched shapes; expected: rejected pre-batch, error_code=SHAPE_MISMATCH.
  • fixtures/batching/timeout_expiry.json — sub-minimum-batch timeout; expected: microbatch fallback dispatch at exactly the window ceiling.
  • fixtures/batching/batch_replay.json — replay of a committed batch; expected: identical batch_id, request-set, and padding decision on replay (I10).
Pitfalls
  • Oversized batching windows. Manifestation: latency spikes exceeding p95 budget. Root cause: adaptive sizing overshooting under bursty load. Debugging: correlate batch_formation_latency with queue-depth trace. Recovery: cap the adaptive window at the 8 ms ceiling (§4) unconditionally.
  • Padding amplification. Manifestation: GPU memory waste and reduced effective batch size. Root cause: shape-bucketing granularity too coarse. Mitigation: fragmentation estimator gate (§15.2 step 16) rejecting a padding choice above the < 15% budget (§4).
  • Batch-scheduler deadlock. Manifestation: requests stall indefinitely in BATCHED state. Detection: stagnant_batch_seconds metric. Root cause: lease acquisition failure not triggering batch requeue. Recovery: requeue-on-lease-failure with exponential backoff.

⬜ Phase 4 — Scheduler Core §16

Objectives

Implement cluster-wide placement and resource coordination: lease-based worker assignment, NUMA/GPU-aware scoring, fairness accounting (I3, I6, P12). Builds on batch descriptors from §15; becomes the dominant scaling bottleneck at cluster sizes beyond 500 nodes (§29).

Deliverable

Distributed placement is operational: batches are leased to specific workers under NUMA/GPU-aware scoring, with stale-worker eviction and lease-conflict fencing enforced.

Acceptance

Scheduler decision latency < 500 µs p99 (§4); stale workers evicted within 5 s of missed heartbeat deadline; fairness variance < 3% across fixtures/scheduler/lease_replay.json's 10-tenant mix; 0 duplicate-lease grants across 10,000 induced heartbeat races.

Fixtures
  • fixtures/scheduler/stale_heartbeat.json — worker misses 3 heartbeat intervals; expected: evicted within 5 s, leases reassigned.
  • fixtures/scheduler/gpu_exhaustion.json — placement request exceeding free GPU memory cluster-wide; expected: error_code=NO_CAPACITY, no partial placement.
  • fixtures/scheduler/lease_replay.json — replay of 10,000 lease grants; expected: 0 duplicate fencing tokens, identical placement decisions on replay (I2).
Pitfalls
  • Scheduler cache staleness. Manifestation: placements target an already-evicted worker. Root cause: cache invalidation lagging the registry generation counter. Debugging: compare cache generation to registry generation at placement time. Recovery: reject and retry placement on generation mismatch, never place against a stale snapshot.
  • GPU overcommit. Manifestation: runtime OOM inside a worker after placement succeeded. Root cause: memory-fit estimation underestimating activation memory. Mitigation: conservative headroom margin in placement scoring (§16.2 step 6).
  • Split-brain scheduler elections. Manifestation: two scheduler replicas both believe they hold leadership. Root cause: missing term-fencing (Raft, §5). Mitigation: fencing tokens on every lease grant (I6) invalidate the losing replica's in-flight grants.

⬜ Phase 5 — Runtime Workers and ONNX/TensorRT Execution §17

Objectives

Implement the real execution environment: crash-isolated workers running ONNX/TensorRT inference against leased batches (I5, I9, P3). Builds on scheduler leases (§16); this is the phase where inference correctness first becomes measurable, not simulated.

Deliverable

Real model inference is operational end-to-end: a leased batch executes against a loaded ONNX or TensorRT model and returns output_tensors (§8.4) with a verifiable execution_hash.

Acceptance

Inference correctness verified against fixtures/runtime/golden_outputs.json (bit-exact for ONNX CPU, tolerance 1e-5 for TensorRT FP16); 0 GPU memory leaks after a 24-hour soak (RSS/VRAM delta < 1%); worker restart completes in < 10 s (§4); 100% of fixtures/runtime/cuda_oom.json cases reject cleanly with error_code=NO_CAPACITY, 0 process crashes.

Fixtures
  • fixtures/runtime/corrupted_model.onnx — truncated model file; expected: load_model returns LoadError, worker stays healthy.
  • fixtures/runtime/cuda_oom.json — allocation request exceeding free VRAM; expected: rejected pre-execution, worker health unaffected.
  • fixtures/runtime/execution_timeout.json — a kernel exceeding timeout_ms; expected: stream cancelled, error_code=DEADLINE_EXCEEDED, worker remains healthy.
  • fixtures/runtime/golden_outputs.json — reference tensors for 5 canonical models; expected: bit-exact (CPU) / 1e-5 tolerance (TensorRT FP16) match.
Pitfalls
  • GPU fragmentation. Manifestation: allocation failures despite sufficient nominal free memory. Root cause: variable-size tensor allocations over time without a size-bucketed pool. Mitigation: pinned-memory pool bucketing (§17.2 step 5) plus the fragmentation estimator from §15.2 step 16.
  • Runtime deadlocks. Manifestation: worker stalls with no progress and no crash. Root cause: CUDA-stream synchronization blocking the execution thread pool without a timeout. Debugging: tokio-console-class introspection is not applicable here since these are dedicated OS threads — use perf/eBPF stack sampling (Gregg, §5) on the stalled thread. Recovery: execution-timeout handling (§17.2 step 8) forcibly cancels the stream.
  • Blocking the async reactor. Manifestation: unrelated gRPC connections on the same worker process start timing out. Root cause: CPU-bound tensor work scheduled onto the Tokio reactor instead of the dedicated thread pool (tokio-rs/tokio reference pitfall, §5). Recovery: strict separation enforced in code review; add a lint/runtime assertion that execution never runs on a Tokio worker thread.

⬜ Phase 6 — Model Registry and Artifact Management §18

Objectives

Implement durable model-lifecycle management: immutable manifests, staged rollout, and sub-60-second rollback (I11, P8). Builds on the artifact-storage decision (ADR-04) and feeds the runtime worker's model-load pipeline (§17.2 step 3).

Deliverable

Deployments are manageable end-to-end through registry APIs: publish, canary, promote, and rollback all operate on immutable, checksum-verified artifacts with a full audit trail.

Acceptance

Rollback completes in < 60 s from trigger to traffic cutover (§4 analog); checksum validation is enforced on 100% of fetches (0 unverified reads reach a worker); artifact cache-hit ratio > 85% under fixtures/registry/steady_state_load.json; 0 partial-artifact executions across 1,000 induced interrupted-download trials.

Fixtures
  • fixtures/registry/checksum_mismatch.bin — artifact with corrupted trailing bytes; expected: fetch rejected, artifact_checksum_mismatch_total incremented (I11).
  • fixtures/registry/rollback_replay.json — a rollback sequence; expected: replay reconstructs identical rollout-state transitions (P8).
  • fixtures/registry/staged_rollout.json — canary-to-full promotion; expected: traffic percentage matches configured canary weight at each stage, ± 1%.
Pitfalls
  • Partial artifact downloads. Manifestation: a worker loads a truncated model. Root cause: non-atomic write during download. Mitigation: atomic rename semantics — download to a temp path, checksum-verify, then atomically rename into the cache (§18.2 step 9).
  • Registry metadata drift. Manifestation: two registry replicas disagree on the active version for a model_key. Root cause: mutable-in-place metadata update instead of append-only manifest publish. Mitigation: immutable manifests (§18.2 step 1) — "updates" are always new manifests.
  • Cache thrashing under multi-tenant load. Manifestation: cache-hit ratio drops below the 85% target. Root cause: LRU eviction interacting badly with round-robin multi-model traffic. Mitigation: residency-score-aware eviction shared with the scheduler's model-residency scoring (§16.2 step 7).

⬜ Phase 7 — Telemetry, Replay, and Auditability §19

Objectives

Implement production-grade observability and deterministic replay (I2, I7, P4, P8). Builds on the Phase-0 telemetry abstraction (§12.2 step 7) and every prior phase's replay-record emission points.

Deliverable

Full request replay is available end-to-end: any completed request's scheduler decision, batch composition, and execution result are reconstructable from the durable log, byte-for-byte.

Acceptance

Replay determinism > 99.99% across fixtures/replay/determinism_suite.json (10,000 replayed requests); telemetry overhead < 3% CPU (§4) measured under peak synthetic load; replay-log compaction reduces storage by > 40% with 0 data loss on fixtures/replay/compaction_regression.json.

Fixtures
  • fixtures/replay/determinism_fixture.json — 10,000-request replay batch; expected: > 99.99% byte- identical reconstruction.
  • fixtures/replay/malformed_trace.bin — corrupted trace record; expected: skipped with a forensic log entry, not a crash of the replay reader.
  • fixtures/replay/divergence.trace — an intentionally non-deterministic recorded case (wall-clock leak); expected: divergence detector flags it (§19.6).
Pitfalls
  • Replay divergence. Manifestation: replayed execution hash differs from the original. Root cause: a code path reading wall-clock time instead of SimClock during the original execution. Debugging: bisect the execution trace for a non-deterministic input (RNG, wall-clock, HashMap iteration order). Recovery: replace the offending call with the deterministic equivalent; flag historical records recorded before the fix as divergence_suspect rather than silently trusting them.
  • Telemetry storms. Manifestation: exporter queue saturates, triggering the drop-oldest path under normal load, not just incidents. Root cause: sampling rate too low for current cardinality. Mitigation: adaptive sampling keyed off current exporter-queue depth.
  • Replay-log compaction data loss. Manifestation: a compacted record is missing on read. Root cause: compaction boundary computed before a concurrent writer's fsync completed. Mitigation: compaction watermark must be strictly behind the last fsync-confirmed offset.

⬜ Phase 8 — Advanced Scheduling: Tensor Parallelism and Dynamic Graph Compilation §20

Objectives

Undefer tensor parallelism and dynamic graph compilation, both out of scope for §1's Phase 0 deliverable: extend the scheduler (§16) to place a single model's execution across multiple GPUs and to select between precompiled and dynamically compiled execution graphs per request shape.

Deliverable

A model_key flagged for tensor parallelism executes as a coordinated multi-GPU shard group with a single logical lease; frequently-shaped requests transparently upgrade to a compiled execution graph without operator intervention.

Acceptance

Shard-group placement succeeds or fails atomically (0 partial-shard placements across 1,000 induced trials in fixtures/scheduling/shard_placement.json); compiled-graph path reduces p50 latency by

20% over the interpreted path for shapes above the compilation-frequency threshold; cross-shard deadline propagation keeps all shards within 1 ms of each other's effective deadline.

Fixtures
  • fixtures/scheduling/shard_placement.json — induced partial-capacity cluster; expected: atomic accept/reject, 0 partial-shard grants.
  • fixtures/scheduling/graph_compile_cold.json — first-seen shape bucket; expected: interpreted-path execution, compilation triggered asynchronously, cache populated for next request.
  • fixtures/scheduling/shard_failure.json — one shard crashes mid-execution; expected: whole group fails cleanly, other shard-groups on the same workers unaffected.
Pitfalls
  • Shard-group partial placement. Manifestation: some shards land, others don't, corrupting the group. Root cause: non-atomic multi-shard lease acquisition. Mitigation: two-phase lease acquisition — reserve all shards, commit only if all reservations succeed (extends P12).
  • Compile-cache thrash. Manifestation: compiled-graph cache-hit ratio collapses under high-shape-cardinality traffic. Root cause: eviction policy not accounting for compile cost. Mitigation: LRU-by-compile-cost eviction (§20.2 step 9), not plain LRU.
  • Cross-shard deadline skew. Manifestation: one shard times out while siblings are still running, wasting GPU cycles. Mitigation: shared-deadline propagation (§20.2 step 16) enforced at dispatch, not per-shard independently.

⬜ Phase 9 — Multi-Region Replication and Elastic Cold-Start Pooling §21

Objectives

Undefer multi-region replication and serverless cold-start pooling, both out of scope for §1's Phase 0 deliverable: replicate registry/replay durability across regions and maintain a warm-worker pool to bound cold-start latency for infrequently used models.

Deliverable

A tenant's traffic survives full home-region unavailability by failing over within the RTO budget; infrequently used models serve their first post-idle request from a warm pool instead of paying a full 15 s cold-start (§4).

Acceptance

Region failover completes within the 10-minute RTO (§4) in fixtures/multiregion/failover.json; warm-pool hit reduces cold-start latency from the 15 s worker-startup budget (§4) to < 2 s for pooled models in fixtures/multiregion/warmpool_hit.json; 0 lost replay records across a simulated region partition of up to the RPO budget's duration (< 5 s, §4).

Fixtures
  • fixtures/multiregion/failover.json — induced home-region outage; expected: failover completes within RTO, 0 duplicate-request execution (I12 across regions).
  • fixtures/multiregion/warmpool_hit.json — request against a warm-pooled cold model; expected: execution latency < 2 s, no full model-load path taken.
  • fixtures/multiregion/replication_conflict.json — concurrent cross-region publish of the same model_key; expected: deterministic content-hash-based resolution, not wall-clock-based.
Pitfalls
  • Replication lag masking data loss. Manifestation: cross-region replica appears healthy but is missing recent replay records. Root cause: best-effort replication silently falling behind under network partition. Mitigation: replication-lag alerting (§21.2 step 16) distinct from the local RPO check — never assume cross-region replication satisfies the local durability guarantee (I2).
  • Warm-pool thrash. Manifestation: pool scale-out/scale-in oscillates under bursty-but-sparse traffic. Root cause: cold-start-prediction heuristic reacting to noise, not signal. Mitigation: hysteresis in the scale-out/scale-in triggers (§21.2 steps 7-8).
  • Cross-region duplicate execution. Manifestation: a failed-over request executes twice, once in each region. Root cause: I12's dedup index is region-local, not cross-region-aware. Mitigation: the failover path must consult the origin region's replay index before executing, even in degraded mode (extends I12).
