Decisions (§9) · 28 ADRs

ADR-01

Implementation language

Chosen

Rust (edition 2021, MSRV 1.78)

Rejected

Go, C++

When the rejected choice is right

Go wins when team Go expertise dominates, throughput SLO is loose (>100ms P99 acceptable), and rapid feature iteration outweighs tail latency — e.g., an internal batch-only inference proxy with no streaming

Why: No GC tail latency; memory safety; mature async networking; linkerd2-proxy precedent

ADR-02

Async runtime

Chosen

tokio (1.x, multi-thread scheduler)

Rejected

async-std, smol, glommio

When the rejected choice is right

glommio wins on bare-metal single-NUMA-node deployment where io_uring and thread-per-core isolation eliminate cross-thread wakeup overhead at >500k req/s

Why: Largest ecosystem; well-tested under high connection counts; tokio-compat for hyper/tonic

ADR-03

HTTP/1.1 + HTTP/2 server

Chosen

hyper (1.x)

Rejected

actix-web, axum (wraps hyper), h2 direct

When the rejected choice is right

axum wins when route-dispatch ergonomics matter more than raw throughput (e.g., internal admin API gateway with dozens of typed handlers and no streaming)

Why: Hyper is the foundational layer; minimal overhead; full HTTP/2 server push & trailers

ADR-04

gRPC

Chosen

tonic (0.11+)

Rejected

grpc-sys (C bindings), tower-grpc

When the rejected choice is right

grpc-sys wins when the existing backend ecosystem is entirely C++ and zero-copy interop with a shared protobuf memory arena is required — e.g., a Triton-only deployment with custom C++ filters

Why: Pure Rust; built on hyper + prost; streaming first-class; interop with vLLM gRPC API

ADR-05

Build system

Chosen

Cargo (workspace)

Rejected

Bazel, Buck2

When the rejected choice is right

Bazel wins when the router must compile with a multi-language monorepo (C++/Python/Rust) sharing Protobuf definitions and requiring hermetic cross-compilation for multiple hardware targets

Why: Native Rust toolchain; workspace for 11 crates; reproducible via Cargo.lock; no Bazel overhead

ADR-06

Protobuf/gRPC code generation

Chosen

prost + tonic-build

Rejected

protobuf (official), prost-build alone

When the rejected choice is right

protobuf-official (with grpc-sys) wins when reflection-based gRPC server (grpc.reflection.v1alpha) is required for runtime schema discovery by a polyglot ops toolchain

Why: prost generates idiomatic Rust structs; tonic-build integrates build.rs; no runtime reflection

ADR-07

JSON serialization

Chosen

serde_json + serde (derive)

Rejected

simd-json, rmp-serde

When the rejected choice is right

simd-json wins at ≥1 GB/s JSON ingress throughput (e.g., high-fanout event logging pipelines) where SIMD acceleration is measurably dominant; rmp-serde wins on internal binary-only paths where wire format is not human-readable

Why: Standard; serde derive zero-cost; simd-json not stable API for production

ADR-08

Request ID

Chosen

ulid crate (Ulid)

Rejected

uuid v4, snowflake, nanoid

When the rejected choice is right

Snowflake wins in a single data-center deployment with a centralized ID service where millisecond-precision sortability and 64-bit compact IDs are required for high-throughput log join

Why: ULID: monotonic, sortable, URL-safe; no coordination; 128-bit entropy; good for distributed tracing correlation

ADR-09

Metrics

Chosen

metrics crate facade + metrics-exporter-prometheus

Rejected

opentelemetry-metrics, statsd, miette

When the rejected choice is right

OpenTelemetry-metrics wins when the organization mandates a single telemetry SDK across traces + metrics + logs with push-based OTLP to a vendor-managed backend (e.g., Grafana Cloud, Honeycomb)

Why: metrics facade is zero-cost; swap exporter without changing instrumentation sites; Prometheus pull model standard

ADR-10

Distributed tracing

Chosen

opentelemetry + tracing crate + tracing-opentelemetry

Rejected

jaeger-client (deprecated), zipkin native

When the rejected choice is right

Zipkin wins in brownfield environments where the entire observability stack is Zipkin-based and the cost of migrating trace storage is prohibitive

Why: tracing integrates with tokio spans; opentelemetry standard; OTLP exporter; GRPC trace propagation

ADR-11

Structured logging

Chosen

tracing + tracing-subscriber (JSON formatter)

Rejected

log crate + env_logger, slog

When the rejected choice is right

slog wins in high-frequency embedded or edge scenarios where tracing's span machinery overhead is measurable and structured async context is not needed (e.g., a bare-metal proxy with sub-microsecond logging budgets)

Why: tracing spans carry context (request_id, model, backend_id) automatically; JSON for log aggregators

ADR-12

Configuration format

Chosen

TOML (config crate + toml)

Rejected

YAML, JSON, HCL

When the rejected choice is right

HCL wins when the deployment is Terraform/Nomad-native and operators already manage infrastructure in HCL, making config format unification reduce cognitive load and tooling surface

Why: TOML: unambiguous; config crate supports layered overrides (file + env vars + CLI flags)

ADR-13

Async channel primitives

Chosen

tokio::sync::{mpsc, broadcast, watch}

Rejected

crossbeam, flume, async-channel

When the rejected choice is right

crossbeam wins in mixed sync+async code where bounded channels must be used from both thread-pool workers and async tasks without spawning a runtime, e.g., a CPU-bound pipeline stage in a Rayon thread pool

Why: tokio-native; watch for config broadcast; mpsc for pipeline stages; broadcast for health updates

ADR-14

Concurrency for shared state

Chosen

Arc<RwLock<T>> (tokio::sync::RwLock)

Rejected

Mutex everywhere, lock-free structures, dashmap

When the rejected choice is right

dashmap wins when the shared map is write-heavy under high concurrency (e.g., per-request mutable state with thousands of concurrent writers) and lock contention on RwLock becomes a measured bottleneck

Why: RwLock: read-heavy workloads (routing, registry); async-aware; dashmap considered but RwLock simpler invariants

ADR-15

HTTP connection pooling (outbound)

Chosen

hyper-util PoolClient + custom pool wrapper

Rejected

reqwest (too high-level), hyper direct only

When the rejected choice is right

reqwest wins for low-concurrency admin/sidecar clients where convenience (redirect, cookie, form encoding) outweighs the overhead of hyper-util and the number of concurrent connections is <10

Why: hyper-util provides HTTP/2 multiplexed pooling; custom wrapper adds circuit-breaker + per-backend limits

ADR-16

Hashing for PrefixHash

Chosen

SHA-256 (sha2 crate), truncated to 16 bytes

Rejected

xxHash, FNV, blake3

When the rejected choice is right

blake3 wins when PrefixHash computation is on the critical path for requests with >4 KB prompt prefixes and the SIMD throughput advantage (>3× SHA-256) is a measured bottleneck

Why: SHA-256: collision resistance adequate; sha2 pure Rust; 16-byte truncation sufficient for radix tree key

ADR-17

Testing framework

Chosen

cargo test (unit) + nextest (CI)

Rejected

criterion-only, proptest-only

When the rejected choice is right

proptest-only wins for pure algorithmic crates (e.g., PrefixTree eviction logic) where the entire correctness argument is property-based and no integration harness is needed

Why: nextest: parallel, faster CI; unit tests per crate; integration tests in tests/

ADR-18

Property-based / fuzz testing

Chosen

proptest (property) + cargo-fuzz (libFuzzer)

Rejected

quickcheck, AFL

When the rejected choice is right

AFL wins on embedded targets or non-Linux environments where LLVM sanitizer support is unavailable but persistent mode fuzzing via AFL++ forkserver is feasible

Why: proptest: deterministic shrinking; cargo-fuzz: LLVM coverage-guided; fuzz targets in infr-bench/fuzz/

ADR-19

Benchmark harness

Chosen

criterion (micro) + infr-bench crate (load/chaos)

Rejected

hyperfine (CLI-only), divan

When the rejected choice is right

divan wins for simple before/after regressions in a crate with many small pure-function benchmarks where criterion's statistical overhead and warm-up time inflate CI benchmark suite duration past an acceptable gate

Why: criterion: statistical micro-benchmarks for routing/queue hot paths; infr-bench: full end-to-end load generation

ADR-20

CI/CD pipeline

Chosen

GitHub Actions (matrix: stable + MSRV 1.78)

Rejected

CircleCI, Buildkite, Jenkins

When the rejected choice is right

Buildkite wins when CI must run on self-hosted GPU nodes for model-serving integration tests, and GitHub Actions hosted runners lack GPU access or network access to on-premise model registries

Why: GitHub Actions native to repo; matrix tests MSRV; clippy + rustfmt + deny + audit in CI

ADR-21

Dependency audit

Chosen

cargo-audit + cargo-deny (licenses + advisories)

Rejected

snyk, dependabot alone

When the rejected choice is right

Snyk wins in polyglot organizations where a single security platform must scan Rust, Python, and container layers with a unified dashboard and policy engine, making per-ecosystem tools operationally fragmented

Why: cargo-deny: license policy + advisory DB; cargo-audit: RustSec; CI-blocking on high-severity CVEs

ADR-22

Container image

Chosen

distroless/cc-debian12 base; multi-stage Dockerfile

Rejected

Alpine (musl compat issues), full Ubuntu

When the rejected choice is right

Alpine wins when image size is the primary constraint (e.g., edge deployments with <100 MB image budget) and musl compatibility has been verified with the full dependency tree including ring and rustls

Why: distroless: minimal attack surface; multi-stage: build in rust:1.78 official, copy binary only

ADR-23

Orchestration interface

Chosen

Kubernetes-compatible (emit metrics for HPA; /healthz, /readyz endpoints)

Rejected

Nomad, raw VMs

When the rejected choice is right

Nomad wins in regulated environments (financial, air-gapped) where Kubernetes control-plane attack surface is a compliance blocker and existing Nomad infrastructure is already mature

Why: K8s dominant for LLM serving infra; HPA consumes custom metrics via Prometheus adapter; /readyz gates traffic

ADR-24

Security: TLS termination

Chosen

rustls (0.23+) via tokio-rustls

Rejected

OpenSSL (via openssl-sys), native-tls

When the rejected choice is right

OpenSSL wins when FIPS 140-2 Level 2 certification is mandated by a government or financial-sector contract and rustls + ring's FIPS module has not yet received the required validation for the target environment

Why: rustls: memory-safe; no C deps; FIPS-certified ring backend available; mTLS for backend auth

ADR-25

Release versioning

Chosen

SemVer; cargo workspace version sync

Rejected

CalVer, manual per-crate

When the rejected choice is right

CalVer wins for an operational release train (e.g., 2024.Q3.1) where version numbers must communicate release cadence and time-based support windows to downstream SRE consumers, not API compatibility

Why: SemVer: standard for Rust crates; workspace version in root Cargo.toml propagated to all crates

ADR-26

Reproducible builds

Chosen

Cargo.lock committed; rust-toolchain.toml pinned; Dockerfile ARG RUST_VERSION

Rejected

Nix flakes, hermetic Bazel

When the rejected choice is right

Nix flakes win when byte-for-byte binary reproducibility is required for supply-chain attestation (e.g., SLSA Level 3 provenance), where Cargo.lock alone does not guarantee identical build environments across OS versions

Why: rust-toolchain.toml: pins toolchain per repo; Cargo.lock: exact dep versions; sufficient for binary reproducibility

ADR-27

Documentation

Chosen

rustdoc (all public APIs; #![deny(missing_docs)]); architecture docs in docs/ Markdown

Rejected

mdBook, Notion

When the rejected choice is right

mdBook wins when the documentation audience is primarily non-Rust engineers (e.g., ML platform teams consuming the gRPC API) and a navigable multi-chapter book with cross-references outweighs inline rustdoc

Why: rustdoc: inline with code; deny(missing_docs) enforces coverage; architecture ADRs as Markdown for PR review

ADR-28

Inter-crate API stability

Chosen

infr-core types are #[non_exhaustive] enums where future variants expected

Rejected

sealed traits, pub(crate) only

When the rejected choice is right

pub(crate) wins when the crate boundary is internal-only and no downstream consumers outside the workspace exist, making the #[non_exhaustive] constraint an unnecessary friction on exhaustive pattern matching in tests

Why: #[non_exhaustive]: allows adding variants without semver break; downstream crates must handle _ match arms

Alternative Architectures (Roads Not Taken)

AA1 — Sidecar Proxy Model (Envoy + xDS control plane)

  Client
    │
    ▼
┌─────────────────────────────────────────────────────┐
│  Ingress LB (L7, TLS termination)                   │
└─────────────────┬───────────────────────────────────┘

                  ▼
         ┌─────────────┐
         │  xDS Control│
         │    Plane    │  (Istio / custom)
         └──────┬──────┘
                │
       ┌────────┴────────┐
       ▼                 ▼
 ┌──────────┐      ┌──────────┐
 │  vLLM    │      │  vLLM    │   (backends)

 └──────────┘      └──────────┘

Regime where this wins: heterogeneous backend fleet (multiple model servers: Triton, vLLM, TGI) where a unified L7 proxy policy layer is already mandated by the platform team, and per-sidecar circuit breaking + mTLS is required by a zero-trust security posture. Real system: Istio + Envoy. Why rejected for this design: Envoy has no LLM-semantic routing (KV-cache prefix affinity, SLO-deadline admission, token-budget-aware scheduling) — these require custom Lua/WASM filters or an out-of-band control plane. The operational complexity of running xDS is higher than a purpose-built router. The sidecar model introduces a hop per request, doubling streaming relay latency.

AA2 — Centralized Scheduler with Worker Pull (Orca/vLLM iteration-level)

  Client → REST/gRPC
    │
    ▼
┌─────────────────────────────────────────────────────┐
│  Centralized Scheduler (single process)             │
│  - Global batch window (iteration-level scheduling) │
│  - All replicas pull next batch from scheduler      │
│  - Token budget tracking across all replicas        │
└──────────────────────────┬──────────────────────────┘
                           │  pull
              ┌────────────┼────────────┐
              ▼            ▼            ▼
         ┌────────┐   ┌────────┐   ┌────────┐
         │ Worker │   │ Worker │   │ Worker │
         │ GPU    │   │ GPU    │   │ GPU    │
         └────────┘   └────────┘   └────────┘

Regime where this wins: homogeneous GPU fleet, all replicas running the same model, and iteration-level continuous batching is the primary optimization target (maximizing MFU). The scheduler has global visibility of all in-flight sequences and can make globally-optimal batch decisions. Real system: vLLM's internal scheduler (within a single vLLM instance), Orca (P1). Why rejected: a centralized scheduler is a single point of failure and a serialization bottleneck for the entire fleet. At 500 backends, the scheduler's O(sequences × replicas) matching loop becomes the bottleneck. This design uses a distributed router (each router instance operates independently) and delegates iteration-level scheduling to individual backends — the router makes routing decisions, not batching decisions.

AA3 — Gossip-Based Distributed KV-Cache Index

  ┌──────────┐    gossip     ┌──────────┐
  │ Router 1 │◄─────────────►│ Router 2 │
  │PrefixTree│               │PrefixTree│
  └────┬─────┘               └────┬─────┘
       │                          │
       ▼                          ▼
  ┌─────────────────────────────────────┐
  │  Shared KV-Cache Index (gossip)     │
  │  prefix_hash → {BackendId, version} │
  └───────────────┬─────────────────────┘
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
  ┌────────┐ ┌────────┐ ┌────────┐
  │Backend │ │Backend │ │Backend │
  └────────┘ └────────┘ └────────┘

Regime where this wins: large multi-router deployments (>50 router instances) where per-instance PrefixTree divergence causes significant cross-instance cache miss penalty. A gossip-based distributed index allows all routers to share prefix occupancy information with eventual consistency (similar to how Maglev handles consistent hashing across nodes). Real system: Mooncake (P6) uses a distributed KV transfer store with a global index. Why rejected (current phase): gossip protocol adds complexity (vector clocks, anti-entropy, partition handling), increases memory per router (full fleet PrefixTree), and the current design's session affinity via consistent hashing (ADR-08) already reduces cross-instance cache misses when L4 LB uses prefix_hash-based ECMP. Gossip is listed in Deferred Features Register for >50-instance deployments.
