4.2 Scaling Assumptions

  • Horizontal: linear scale-out; each router pod is independent; no coordination protocol.
  • Vertical: memory-bound at ~50K inflight (512 MB); CPU-bound at ~200K req/s on 16-core (profiled async task overhead).
  • Backend fleet growth: O(N) registry scan on route is acceptable up to N=1,000; PrefixTree match is O(prefix_len), independent of fleet size.
  • Model count: ≤ 100 distinct ModelId per router; per-model queue and PrefixTree namespace.
  • Adapter count: ≤ 1,000 AdapterId per model; adapter inventory fits in HashMap in L3 cache.

Back-of-Envelope Capacity Model

All numbers derived from §4 System Constraints. Formulas shown; verify against actual hardware profiling.

Input constraints (§4):

  • Target: 50,000 req/s per router instance
  • Max inflight: 100,000 (I4, I5 bounded)
  • Backends: up to 500 per instance (Scalability Analysis practical ceiling)
  • Avg prompt prefix: 2,048 tokens × 4 bytes/token = 8,192 bytes
  • Avg output tokens: 256 tokens (streaming, one token = 4 bytes)
  • NIC: 10 GbE = 1.25 GB/s (upgrade path: 100 GbE)

Calculation 1 — Router NIC bandwidth at 50k req/s

Output stream rate = 50,000 req/s × 256 tokens × 4 B/token
                   = 50,000 × 1,024 B
                   = 51,200,000 B/s ≈ 50 MB/s outbound
Input payload rate = 50,000 req/s × 8,192 B/req
                   = 409,600,000 B/s ≈ 400 MB/s inbound
Total NIC demand   = 450 MB/s << 1,250 MB/s (10 GbE)

10 GbE is sufficient at 50k req/s. NIC becomes the bottleneck at ~140k req/s (400MB×140k/50k = 1.12 GB/s). Upgrade to 100 GbE before horizontal scale is exhausted.

Calculation 2 — Router CPU cycles per request (routing hot path)

PrefixTree lookup:      ~500 ns  (ArcSwap read + radix walk 8 nodes)
Policy evaluation:      ~200 ns  (RouteReason enum + SLO check)
Lease acquire:          ~100 ns  (AtomicU64 fetch_add)
Queue enqueue:          ~150 ns  (mpsc send)
Total per-request:      ~950 ns ≈ 1 µs

At 50k req/s: 50,000 × 1 µs = 50 ms/s of CPU
Per core (3 GHz, 1 IPC): 1 core can do 3×10^9 / 950 ≈ 3.1M lookups/s
Cores needed for routing: 50,000 / 3,100,000 = 0.016 cores

Routing hot path is not CPU-bound; tokio I/O wait dominates. 4 worker threads saturate at >>50k req/s routing.

Calculation 3 — Lease table memory at 100k inflight

Lease struct = RequestId(16B) + BackendId(4B) + deadline(8B) + padding(4B) = 32 B
HashMap overhead: load factor 0.75 → capacity = 100,000 / 0.75 ≈ 133,333 slots
Slot size: 32B payload + 8B key pointer + 8B value pointer = 48B
Total: 133,333 × 48B = 6.4 MB

Lease table at max inflight = 6.4 MB. Negligible. Even at 1M inflight: 64 MB.

Calculation 4 — PrefixTree memory at 10k entries/model × 100 models

Per entry: prefix_hash(16B) + BackendId set (avg 3 IDs × 4B) + timestamp(8B) = 36B
Per model: 10,000 entries × 36B = 360 KB
At 100 active models: 100 × 360 KB = 36 MB
HashMap index overhead (× 2): 72 MB

PrefixTree for 100 models fits in 72 MB. At 1,000 models: 720 MB — set max_models_in_tree = 200 and evict cold models.

Calculation 5 — Health probe bandwidth to backend fleet

Probe payload: 512 B (JSON metrics response, gzip)
Probe rate: 500 backends × 1 Hz = 500 probes/s
Probe bandwidth: 500 × 512 B = 256 KB/s inbound (negligible)
At 20 router instances: 20 × 500 = 10,000 probes/s per backend fleet
Backend probe load: 10,000 req/s of /metrics — non-trivial for small replicas

Mitigation: use Prometheus pull model (backends expose /metrics, Prometheus scrapes, routers read Prometheus API) — reduces to 500 req/s to Prometheus.

Calculation 6 — Autoscale signal emission rate

Signal rate: 1,000 models × debounce 1 Hz = 1,000 signals/s
Signal payload: 64 B (model_id + queue_depth + ttft_p99 + kv_util)
Total: 1,000 × 64 B/s = 64 KB/s — negligible

Calculation 7 — Scheduler fairness loop overhead

Per-model scan: 1,000 models × 500 replicas × 10 ns comparison = 5 ms per epoch
Epoch: 100 ms
Scheduler CPU: 5ms / 100ms = 5% of one core

At 10k models: 50 ms per epoch → exceeds 100 ms epoch → scheduler bottleneck. Mitigation: hierarchical scheduler (tenant→model tree, skip inactive tenants).

Calculation 8 — Streaming relay buffer memory

Active streams: 100k inflight × 10% streaming = 10,000 active SSE streams
Buffer per stream: 1 token × 4B = 4B (relay zero-copy, no accumulation)
Buffer total: 10,000 × 4 B = 40 KB (relay) + 64 KB (H2 flow-control window) × 10,000 = 640 MB H2 windows

H2 receive windows dominate at scale. Cap per-stream H2 window to 16 KB: 10,000 × 16 KB = 160 MB. Acceptable.
