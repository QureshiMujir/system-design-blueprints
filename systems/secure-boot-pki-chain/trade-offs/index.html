Decisions (§9) · 30 ADRs

ADR-001

Implementation language

Chosen

Rust (verifier no_std, tools std)

Rejected

C, C++, Zig, Go

When the rejected choice is right

C wins when integrating into an existing C-only RoT codebase (e.g. existing Cortex-M RTOS with a C HAL and no Rust cross-target support) — TCB size and toolchain portability dominate safety concerns.

Why: Memory safety in TCB, no GC, no_std, audited const-time crates, cross-compile to bare metal.

ADR-002

Verifier allocation

Chosen

Caller-supplied arena, zero global heap

Rejected

global allocator, alloc everywhere

When the rejected choice is right

Global allocator wins in a hosted 2nd-stage bootloader running on a rich OS with megabytes of RAM, where dynamic cert chain sizes and CRL growth matter more than SRAM budgets.

Why: Bounded 256 KB SRAM; no fragmentation/OOM; deterministic.

ADR-003

unsafe policy

Chosen

#![forbid(unsafe_code)] except reviewed crypto/FFI + sim mmap

Rejected

liberal unsafe

When the rejected choice is right

Liberal unsafe wins when wrapping a FIPS-certified C/asm crypto module required by regulatory mandate — the FFI boundary is unavoidable; audit depth substitutes for the Rust safety guarantee.

Why: Minimize TCB UB surface; cargo-geiger gate.

ADR-004

Default signature scheme

Chosen

Ed25519

Rejected

RSA-PKCS1v1.5, plain ECDSA

When the rejected choice is right

RSA-PSS wins in regulated environments (e.g. FIPS 140-3 level 3 HSM with no Ed25519 support) or when interoperating with an existing PKI that mandates RSA.

Why: Deterministic, fast verify, no nonce-reuse footgun, small sigs.

ADR-005

RSA padding (when RSA used)

Chosen

RSA-PSS (3072)

Rejected

PKCS#1 v1.5

When the rejected choice is right

PKCS#1 v1.5 wins when interoperating with a legacy system (e.g. HSM or CA that only supports v1.5) where re-provisioning is impossible and the threat model excludes chosen-ciphertext attacks on the signature.

Why: Provable security (P5); avoid Bleichenbacher-class issues.

ADR-006

ECDSA curve

Chosen

NIST P-256

Rejected

P-384 default, secp256k1

When the rejected choice is right

P-384 wins in environments with a formal 192-bit security requirement (e.g. US government systems mandating Suite B at the higher level). secp256k1 wins only in Bitcoin/blockchain contexts with hardware acceleration for it.

Why: Interop + perf; P-384 optional via hash_alg=SHA-384.

ADR-007

Hash

Chosen

SHA-256 default, SHA-384 optional

Rejected

SHA-1, MD5, SHA-3 (deferred)

When the rejected choice is right

SHA-384 wins when FIPS/Suite-B mandates 192-bit security equivalence across all primitives. SHA-3 wins post a SHA-2 length-extension or collision announcement.

Why: FIPS 180-4; SHA-1 only as legacy SKI key-id, never for integrity.

ADR-008

Crypto libs

Chosen

RustCrypto (ed25519-dalek,p256,rsa(verify),sha2,subtle)

Rejected

hand-rolled, OpenSSL FFI

When the rejected choice is right

OpenSSL FFI wins when a FIPS 140-3 validated module is contractually required — the certification applies only to the OpenSSL binary, not to RustCrypto.

Why: Audited, const-time-aware, no_std-capable; verify-only RSA avoids signing timing bugs.

ADR-009

DER/X.509 parsing

Chosen

Custom canonical-DER reader + der/x509-cert types, validation re-implemented

Rejected

OpenSSL X.509, fully hand-rolled

When the rejected choice is right

OpenSSL X.509 wins in a high-interop scenario (e.g. validating arbitrary web-PKI chains from partners' CAs) where tolerance for BER and non-canonical encodings is needed for compatibility.

Why: Control attack surface, enforce canonical-only, reuse vetted struct decoders.

ADR-010

Manifest serialization

Chosen

Custom fixed big-endian binary + TLV

Rejected

Protobuf, CBOR, ASN.1

When the rejected choice is right

Protobuf/CBOR wins for a rich hosted tooling format where schema evolution and human tooling (gRPC, JSON interop) matter more than parse simplicity — e.g. a cloud-side manifest database not in the TCB.

Why: Deterministic, zero-copy, tiny parser, no schema-evolution ambiguity in TCB.

ADR-011

Revocation transport

Chosen

dbx (offline, authoritative) + CRL + OCSP/stapled

Rejected

OCSP-only, CRL-only

When the rejected choice is right

OCSP-only wins for a fleet of always-online servers with sub-hour revocation SLA needs, where CRL size grows too large to ship with images and devices always have network access.

Why: Offline boot needs dbx; OCSP for freshness; stapling for offline-with-freshness.

ADR-012

TPM model

Chosen

TPM 2.0 subset simulator (PCR/extend/quote/seal/NV)

Rejected

full TPM 2.0, TPM 1.2

When the rejected choice is right

Full TPM 2.0 wins when building a general-purpose TPM library that must interoperate with arbitrary TPM 2.0 command sequences from UEFI/OS drivers, not just a fixed measured-boot workload.

Why: Enough for measured boot + attestation; full set deferred.

ADR-013

Hardware model

Chosen

Deterministic host simulator (RoT/OTP/NV/PCR/A-B)

Rejected

QEMU+real firmware, hardware lab

When the rejected choice is right

QEMU+real firmware wins when validating silicon-specific timing, MMU quiescing, or DMA-controller behavior that the host simulator cannot faithfully model — required before production tape-out.

Why: Reproducible, replayable, CI-friendly; no silicon needed.

ADR-014

Build system

Chosen

Cargo workspace + cargo make + cross

Rejected

bazel, make-only

When the rejected choice is right

Bazel wins in a multi-language monorepo (Rust + C firmware + Python tooling + Proto IDL) where hermetic cross-language builds and distributed caching across thousands of engineers justify the complexity.

Why: Native Rust, multi-target, reproducible.

ADR-015

Cross-targets

Chosen

aarch64-none, riscv64imac-none, x86_64-none + host

Rejected

single target

When the rejected choice is right

A single target wins in a product-specific embedded project where exactly one silicon variant is ever supported and CI budget cannot absorb a 3× matrix.

Why: RoT silicon diversity; prove portability.

ADR-016

Dependency policy

Chosen

cargo-deny allowlist; pinned; cargo-vet for TCB deps

Rejected

unpinned, permissive

When the rejected choice is right

Unpinned with floating patch-ranges wins in a hosted application (non-TCB) where keeping dependencies current for security patches matters more than bit-identical reproducibility.

Why: Supply-chain integrity for a TCB.

ADR-017

Testing/fuzzing

Chosen

cargo test + proptest + cargo-fuzz(libFuzzer) + AFL++ corpus

Rejected

manual only

When the rejected choice is right

Manual-only testing wins in a protocol with a formally verified reference model (e.g. a TLA+-proved spec) where fuzz coverage is subsumed by exhaustive state-space exploration.

Why: Adversarial parsers demand fuzz + property tests.

ADR-018

UEFI Secure Boot relationship

Chosen

Studied reference; map PK/KEK/db/dbx → our anchor/CRL/dbx; do not re-implement UEFI

Rejected

re-implement UEFI SB

When the rejected choice is right

Re-implementing UEFI SB wins when the platform must boot standard UEFI OS images (Windows, standard Linux distributions) and cannot use a custom manifest format — the UEFI variable store and PE authenticode signing are non-negotiable.

Why: Learn the model, ship a leaner custom one; interop only via concepts.

ADR-019

Logging/observability

Chosen

Structured event log (NV) on device; tracing JSON in tools/services

Rejected

printf, ad hoc

When the rejected choice is right

Printf/ad hoc wins in a ROM-stage context with < 4 KB of code budget where every byte of the structured-log serializer is unaffordable.

Why: Pre-OS observability + attestation needs structured, replayable log.

ADR-020

Metrics (services)

Chosen

OpenTelemetry/Prometheus for attestation verifier + OCSP responder

Rejected

none

When the rejected choice is right

No metrics wins in an air-gapped signing station with no outbound network and no external SRE team — operational visibility comes from manual audit logs, not time-series metrics.

Why: Operate revocation/attestation as real services.

ADR-021

Serialization (tools/log)

Chosen

CBOR for event-log export + JSON for human/CI

Rejected

When the rejected choice is right

XML wins when integrating with an enterprise PKI ecosystem (e.g. Microsoft CA) where all existing tooling expects XML/XSD schemas and CBOR tooling is unavailable.

ADR-022

Attestation format

Why: Aligns with RATS/EAT direction; reuse COSE tooling.

ADR-023

Files on disk wins in a developer-only environment (CI key for testing, never production) with a threat model that excludes insider threats and the PKCS#11 stack is unavailable.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-A — Online-Only Attestation-Gated Boot

OTP (PK-hash)  ─▶  ROM  ─▶  verify(SPL, sig)  ─▶  SPL  ─▶  ...
                                                        │
                                              Attestation verifier
                                              (remote, online)
                                              ─▶ release boot key
                                              (otherwise: halt)

Regime where it wins: Always-online server fleet (cloud instances, managed datacenter) where the network is available at every boot, revocation is sub-second (the verifier can see CRL/OCSP in real time), and the threat model accepts that a network partition = no boot (acceptable for a managed fleet with manual overrides). Real system that embodies it: Google's Shielded VMs with vTPM attestation — boot only completes after the Compute Engine infrastructure verifies the attestation quote and releases disk encryption keys. Why this blueprint rejected it: Boot-time network dependency fails for embedded/IoT devices (no network at first boot, or ever), introduces availability coupling (network partition = unbootable), and forces a service dependency into what must be an offline, deterministic, O(1) operation. The RTO guarantee (§4: ≤ 1 reboot) is unachievable if it requires an external service.

Alt-B — Static Hash of Public Keys (No X.509 Chain)

OTP: hash(leaf_PK)  ─▶  ROM  ─▶  verify(SPL, sig, leaf_PK)
                                  (no chain; leaf directly fused)

Regime where it wins: Ultra-minimal RoT with severe code-size constraints (< 4 KB TCB), single signing key per device model, no requirement for key rotation without re-fusing, and no multi-level PKI policy (no EKU, no pathLen, no name constraints). Correct for a simple IoT sensor with a 10-year key lifecycle and a single vendor. Real system that embodies it: RISC-V SiFive secure boot in some configurations, and many custom embedded bootloaders that simply store a raw Ed25519 public key in OTP and verify directly against it. Why this blueprint rejected it: No key rotation without burning a new fuse or re-provisioning devices in the field. No ability to issue intermediate signing keys for different product lines or signing teams. No revocation short of fuse-burning. This blueprint targets a fleet with key lifecycle management, intermediate HSMs, and the ability to cross-sign during rotation — which requires X.509 path validation.

Alt-C — TPM-Mandatory Measured-and-Enforced Boot (No Verifier in ROM)

ROM  ─▶  TPM extends measurements  ─▶  policy-sealed disk key
         (no sig check in ROM)          unseals only if PCRs match
                                         (TPM enforces, not ROM)

Regime where it wins: x86 server or workstation where a standard TPM 2.0 chip is present (mandated by Win11/Azure Assured Workloads), the ROM is not programmable by the OEM for verification logic, and disk encryption (BitLocker/dm-crypt with TPM sealing) is the enforcement mechanism — the disk simply won't decrypt if the boot chain deviated. Real system that embodies it: Linux Measured Boot with systemd-stub + TPM2 PCR-sealed LUKS keys; Microsoft BitLocker on Windows with TPM 2.0 policy sealing. Why this blueprint rejected it: Sealing + unsealing requires a TPM chip present and functional at every boot; our target is RoT-class silicon without a discrete TPM (the TPM behavior is simulated). More critically, seal/unseal enforcement only protects data confidentiality — it does not prevent booting a tampered OS that simply lacks access to the sealed secret. Verified-boot (signature check before jump) stops execution of unauthorized code; measured-boot + sealing only prevents secret release to it. We need both, and for bare-metal embedded targets the verifier-in-ROM is the primary gate.

Alt-D — Certificate Transparency / Append-Only Log Instead of dbx

Signing CA  ─▶  CT Log  ─▶  SCT (signed cert timestamp)
                                 embedded in manifest
Device  ─▶  verify SCT signature + log inclusion  ─▶  Accept/Reject
            (revocation = log entry; device checks the log)

Regime where it wins: Large-scale web PKI where CT logs provide an auditable, append-only record of all issued certificates and revocation is implicit via log monitoring and browser policy (e.g. CAA + CT required in browsers). The ecosystem trust model is "if it's in the CT log under a trusted CA, it's valid" rather than "only certs we explicitly allow." Real system that embodies it: HTTPS certificate ecosystem managed by browsers (Chrome/Firefox CT policy); Apple ATS requires CT SCTs. Why this blueprint rejected it: CT log inclusion proofs require network access to the log at boot time, or a pre-fetched inclusion proof embedded in the manifest (large; complex freshness semantics). CT does not provide revocation — it provides auditability; revocation in CT-land is still CRL/OCSP. For offline embedded boot, an append-only remote log is the wrong tool: the authoritative offline revocation primitive is the dbx denylist, which ships with the image and requires no network.
