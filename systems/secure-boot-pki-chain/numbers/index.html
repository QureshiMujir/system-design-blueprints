Back-of-Envelope Capacity Model

Derived from §4 System Constraints. Formula shown for each; no asserted-only numbers.

C1 — Payload hash time (SHA-256, SW, 1 GHz core). From §4: SHA-256 throughput ≥ 200 MB/s on 1 GHz. Payload = 4 MB. time = payload / throughput = 4 × 10^6 B / (200 × 10^6 B/s) = 20 ms. Budget from §4: ≤ 20 ms. Margin: 0 ms at floor — HW SHA must be used for larger payloads or tighter targets.

C2 — Ed25519 signature verify contribution. Ed25519 verify on a 1 GHz core ≈ 50–100 µs (standard benchmarks for Cortex-A; conservatively 0.1 ms). Four stages × 0.1 ms = 0.4 ms. Negligible vs §4 cumulative budget of 120 ms.

C3 — Total cumulative verify budget vs ceiling. From §4: ≤ 120 ms cumulative crypto. C1 (4×SHA, 4 stages, 4 MB each) = 4 × 20 ms = 80 ms. C2 (Ed25519 ×4) = 0.4 ms. X.509 path (3-cert × 4 stages, from §4: ≤ 2 ms each) = 4 × 2 ms = 8 ms. Sum = 88.4 ms. Margin: 120 − 88.4 = 31.6 ms headroom. At RSA-PSS-3072 (from §4: p95 ≤ 40 ms/stage), cumulative = 4 × 40 ms = 160 ms > 120 ms ceiling → RSA requires HW acceleration or smaller payloads per stage.

C4 — Arena working set for SPL stage. From §4: ≤ 16 KB scratch arena. Manifest (fixed header + TLV): ≤ 64 KB per §8.2 (parsing rules). At SPL stage only the header+body fit in arena; payload streamed. Arena breakdown: ManifestHeader = ~80 B; cert chain (3 certs × ≤ 2 KB/cert DER) = 6 KB; OCSP staple ≤ 2 KB; TLV overhead ≤ 1 KB. Total = ~9.1 KB < 16 KB budget. Margin: 6.9 KB.

C5 — dbx denylist SRAM bound. From §4: ≤ 256 MB RSS for sim host; device SRAM = 256 KB. dbx entry = 20 B (KeyId) or 48 B (SHA-384 hash). At 256 KB with 10 % reserved: 25 KB for dbx = 1,310 KeyId entries or 536 hash entries. At 100 revocations/year × 10 years = 1,000 entries — barely fits by KeyId; hash-prefix filter recommended beyond 500 entries.

C6 — Event log NV budget. From §8.8: 10 PCRs × 1 extend per boot. Event log entry = 80 B (pcr_index=4B, event_type=4B, digest_count=4B, 1×SHA-256 digest=32B, event_size=4B, event_data≈32B). 10 stages × 80 B = 800 B per boot. 1,000 boots before NV truncation = 800 KB NV log. Real NV is ≤ 64 KB on most SoCs → truncate after ~80 boots, mark truncation in log header. Design: rolling log with a 64 KB ring + a pointer.

C7 — OCSP responder fleet load. From §4: attestation verifier 99.9 % availability. Fleet = N devices; each checks in at boot (assume 1 boot/day). OCSP check = 1 req/device/boot. At N = 1 M devices, 1 req/device/day = ~11.6 req/s average; burst at scheduled maintenance window = 10× = 116 req/s. OCSP response = 1 Ed25519 sign + 0.1 ms = ≤ 10 k req/s per core (I/O-bound before CPU-bound). 1 core easily serves 116 req/s; fleet of 3 cores with LB provides ample redundancy.

C8 — CRL size for large fleet. CRL entry = serial (16 B) + revocation time (4 B) + reason (1 B) ≈ 21 B. At 10,000 revoked certs over fleet lifetime: 210 KB raw + DER overhead ≈ 300 KB. Shipping with every image update: 300 KB added to manifest TLV or a side file — acceptable. At 1 M revocations: 21 MB → delta-CRL required; base CRL issued quarterly, delta daily.

C9 — PCR extend latency per boot chain. From §4: ≤ 50 µs/extend. 10 stages = 10 extends × 50 µs = 500 µs = 0.5 ms. SHA-256 of (PCR‖measurement) = 64 B → at 200 MB/s SW = 0.32 µs per extend. Simulator: O(1) deterministic; negligible vs total boot time.

C10 — TCB code size budget. From §4: ≤ 64 KB .text target, hard cap 96 KB. Breakdown estimate: sbpki-codec ≈ 8 KB; sbpki-crypto (verify wrappers, no RustCrypto inline, only dispatch) ≈ 10 KB; sbpki-x509 path engine ≈ 12 KB; sbpki-revoke (dbx/CRL/OCSP) ≈ 8 KB; sbpki-verify orchestrator ≈ 4 KB; arena ≈ 0.5 KB; types/errors ≈ 2 KB. Subtotal (excluding crypto library code): ~44.5 KB. RustCrypto Ed25519-dalek verify stripped = ~8 KB; SHA-256 = ~4 KB. Total ≈ 56.5 KB < 64 KB target. RSA-PSS adds ~12 KB → combined multi-algo build = ~68 KB → feature-gate to stay under 96 KB cap.

C11 — Attestation verifier throughput. From §4: attestation verifier 99.9 % availability; p95 verify-quote ≤ 50 ms. Quote verify = AK cert chain validate (≤ 2 ms) + Ed25519 quote sig (≤ 0.1 ms) + log replay (10 extends × ≤ 1 µs each = 0.01 ms) ≈ 2.1 ms. At p95 = 50 ms budget, 95 % of headroom is network RTT + service overhead. Single stateless verifier process: ~500 req/s per core (network-bound). At 116 req/s fleet load (C7), 1 core sufficient; 3-instance fleet satisfies 99.9 % availability SLO.

C12 — Fuse bank exhaustion horizon. OTP fuses: PK-hash = 256 bits = 32 fuse-bytes (one-time write); min_svn_floor = 32 bits = 4 fuse-bytes. Total OTP consumed: 36 bytes. NV counter: write-many, model as erase-write flash: 100,000 write cycles minimum. At 1 SVN bump/quarter (security fix rate) = 4/year → NV counter exhaustion in 100,000 / 4 = 25,000 years. OTP exhaustion: never (only written once at provisioning).
