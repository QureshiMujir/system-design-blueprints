308 — Secure Boot + PKI Chain

Project Number: 308

Project Name: Secure Boot + PKI Chain

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build, from scratch, an end-to-end verified + measured boot chain wired to a real PKI — the union of (a) a stage-by-stage trust chain ROM → SPL → bootloader → kernel → initramfs/init where each stage cryptographically verifies the next before transfer of control and extends measurements into a TPM-style PCR bank, and (b) the X.509 certificate authority hierarchy, trust-anchor store, and revocation machinery that anchors those signatures. Deliverable runs against a host-side hardware simulator (no real ROM/fuses/TPM required): deterministic, replayable models of the Root-of-Trust (RoT), one-time-programmable (OTP) fuses, monotonic NV counters, and a TPM 2.0-subset PCR engine.

Precise engineering terms:

  • Verifier core (sbpki-verify, #![no_std]-capable): parse a signed manifest, validate its X.509 chain to a fused trust anchor, check revocation (CRL/OCSP/dbx), enforce anti-rollback (SVN ≥ stored min), constant-time signature verify, fail-closed on any error.
  • PKI tooling (sbpki-ca, std-hosted): create root/intermediate/leaf certs, sign manifests, emit CRLs, run OCSP responder, manage trust-anchor + denylist stores.
  • Measured-boot engine (sbpki-tpm, simulator): PCR-extend PCR[i] ← H(PCR[i] ‖ measurement), append event log, seal/unseal secrets to PCR policy, produce signed quotes for remote attestation.
  • Chain orchestrator (sbpki-sim, std-hosted): models RoT immutability, fuse/OTP key-hash storage, NV monotonic counters, A/B slots; sequences staged loaders end-to-end and is the substrate every phase produces artifacts against.

1.1 System Boundaries

In scope: signed-image/manifest format + parser/verifier; RFC 5280 path validation engine; trust-anchor + revocation (CRL, OCSP, stapled OCSP, dbx hash/key denylist); key hierarchy + ceremony tooling (offline root, HSM-resident intermediates simulated by a PKCS#11-shaped backend); measured boot (PCR bank, event log, quote/verify, seal/unseal); anti-rollback (OTP + NV SVN/counter model); A/B + recovery state machine; full ROM→init chain in simulator; conformance vectors; fuzzing; performance budgets.

Out of scope (non-goals): real silicon ROM mask programming; physical fuse burning; a production HSM (we model the interface and threat properties, not FIPS-certified hardware); full TPM 2.0 (we implement a subset: PCRs, extend, quote, seal/unseal, NV — not the entire command set); UEFI firmware re-implementation (UEFI Secure Boot is a studied reference, see ADR-018, not a build target); secure runtime (post-init userspace integrity, IMA/EVM) — handed off, see PhaseDeferred("FINAL_BLUEPRINT §23.10"); defeating arbitrary fault-injection/glitching at the gate level (physical countermeasures noted, partly out of scope, mitigated only by redundancy + re-verification, see Threat Model).

1.2 Deployment Model

Two artifacts ship:

  1. sbpki-verify static no_std library + thin verify-shim binary — intended to be linked into a first-stage loader on real hardware later, or run inside sbpki-sim now. Zero heap in the hot path (bump/arena allocator over a caller-supplied buffer).
  2. sbpki-toolkit std-hosted CLI bundle (ca, sign, crl, ocsp, tpmsim, attest, sim) — runs on a developer/CI host or a signing workstation.

Operators: release/signing engineers (run ceremonies, rotate keys, publish CRLs/dbx), platform-security engineers (own the verifier + trust-store policy), SREs of the attestation verifier service.

1.3 Phase 0 Deliverable — Modules

  1. sbpki-types — shared types: Manifest, CertChainRef, Svn, PcrIndex, Digest, KeyId, VerifyError, no_std + serde-optional.
  2. sbpki-codec — manifest binary (de)serialization, DER reader/writer, length-delimited TLV.
  3. sbpki-crypto — constant-time signature verify (Ed25519 / ECDSA-P256 / RSA-PSS-3072), SHA-256/384, RNG abstraction.
  4. sbpki-x509 — RFC 5280 path validation engine, name constraints, EKU/keyUsage, basicConstraints/pathLen.
  5. sbpki-revoke — CRL parse/verify, OCSP client + stapling, dbx denylist (hash/key).
  6. sbpki-verify — orchestrates codec+crypto+x509+revoke+rollback into the stage verifier (no_std).
  7. sbpki-tpm — PCR bank, extend, event log, quote, seal/unseal (simulator).
  8. sbpki-nv — OTP fuse model + monotonic NV counter model + SVN store.
  9. sbpki-ab — A/B slot + recovery state machine.
  10. sbpki-sim — RoT/ROM/SPL/loader staging harness; wires 1–9 end-to-end.
  11. sbpki-ca — CA hierarchy, signing ceremonies, CRL/OCSP issuance, key lifecycle.
  12. sbpki-cli — operator surface over all of the above.
  13. sbpki-conformance — vector loader + differential harness.
  14. sbpki-fuzz — fuzz targets for codec/x509/revoke parsers.

1.4 What Later Phases Unlock

Phase 1 (types/codec) → Phase 2 (crypto) → Phase 3 (manifest verify) → Phase 4 (X.509 path) → Phase 5 (revocation) → Phase 6 (anti-rollback) → Phase 7 (TPM/measured) → Phase 8 (attestation) → Phase 9 (A/B recovery) → Phase 10 (full-chain sim) → Phase 11 (CA + ceremonies) → Phase 12 (conformance/fuzz/perf/hardening). Each phase consumes the prior phases' normative APIs; nothing is re-derived.

1.7 Recommended Language — Rust (rationale, exact)

Reason Why it is load-bearing here
Memory safety in a TCB Verifier is the Trusted Computing Base; a single OOB read/UAF in a manifest/DER parser is a full secure-boot bypass. Rust removes the entire class without a GC.
#![no_std] core sbpki-verify must link into a first-stage loader with no allocator/OS; Rust compiles no_std with an explicit core/alloc split.
No GC, deterministic Boot has hard latency budgets (§4) and no runtime; GC pauses / nondeterminism are unacceptable.
Const-time crypto crates subtle, ed25519-dalek, p256, rsa (verify path) and sha2 offer audited constant-time / side-channel-aware primitives; we wrap, not reinvent.
Cross-compilation aarch64-unknown-none, riscv64imac-unknown-none-elf, x86_64-unknown-none targets are first-class via rustup/cargo, matching real RoT silicon.
unsafe is auditable TCB policy: #![forbid(unsafe_code)] everywhere except a tiny, reviewed sbpki-crypto FFI shim and sbpki-sim mmap; cargo-geiger enforces.
Strong type modeling Newtypes (Svn, KeyId, PcrIndex) + exhaustive enum error sets make fail-closed the default — an unhandled variant won't compile.

Hosted tooling (ca, ocsp, sim) uses std; the verifier core stays no_std + alloc-optional.

2. Why Build This

2.1 Unique Systems Knowledge Taught

  • The exact ordering discipline of verified boot: verify-before-execute, never execute-then-check — and why TOCTOU between "verify image in flash" and "jump to image in RAM" is the canonical bug.
  • The difference and complementarity of verified (gate transfer-of-control) vs measured (record, decide later via attestation/sealing) boot.
  • How a hash of a public key (not the key) is the smallest immutable RoT secret, and how the chain bootstraps trust from one fused value.
  • Full RFC 5280 path validation as an executable algorithm, not a checkbox: basicConstraints/pathLen, keyUsage/EKU code-signing, name constraints, validity windows, signature chaining.
  • Revocation as a distributed-systems problem: CRL freshness, OCSP availability vs privacy, stapling, and why an offline boot path needs dbx-style explicit denylists rather than online checks.
  • Anti-rollback as the bridge between cryptography and hardware state: SVN/monotonic counters in OTP/NV, and the unbrick/recovery tension it creates.
  • TPM measured boot + remote attestation: PCR extend chains, the TCG event log as a replayable ledger, quotes signed by an AK, and sealing secrets to a future PCR policy.

2.2 Historical / Architectural Significance

Secure boot is the foundation every higher trust system assumes: confidential computing, disk encryption auto-unlock, attested fleets, supply-chain integrity (SLSA), and OS verified-boot (Android Verified Boot, ChromeOS verified boot, Apple Secure Boot, UEFI Secure Boot) all terminate at a root of trust this project re-creates. Understanding it converts "the platform is trusted" from an assumption into a chain you can audit link-by-link.

2.3 Engineering Muscles Developed

Adversarial parsing (untrusted DER/manifest bytes); constant-time / fail-closed coding; state-machine design with crash/power-loss safety; deterministic simulation of hardware; cryptographic protocol implementation against test vectors; threat modeling with an explicit attacker; reproducible/signed release engineering (you become both the thing-that-signs and the thing-that-verifies).

2.4 Production Engineering Concepts Exercised

Trust boundaries; fail-closed defaults; idempotent/atomic flash updates; A/B + watchdog anti-bricking; revocation propagation SLAs; key ceremony + custody; observability of a thing that runs before the OS (early-boot logging via event log + persisted verdict); differential + fuzz + conformance testing of security-critical parsers.

2.6 Calibration Value

After this, "is the platform trustworthy?" becomes a precise, debuggable question. You can read any vendor's secure-boot whitepaper and map it to PK/KEK/db/dbx + SVN + PCR primitives, spot the TOCTOU/rollback gaps, and reason about revocation latency and brick risk quantitatively.

2.7 What Mastery Looks Like

  • Adversarial parser design (Phase 1–2): write a zero-heap, canonical-DER-only manifest parser that passes Wycheproof negative vectors, rejects every non-canonical encoding, and survives 1000 CPU-h of fuzzing with no crashes or UB.
  • Full RFC 5280 path validation as executable code (Phase 4): implement the §17.1 state machine — pathLen, name constraints, EKU, name-chaining, validity, revocation — and explain exactly why PKIX chose each rule and what attack it closes.
  • Revocation systems engineering (Phase 5): design a fail-closed revocation stack (dbx → stapled OCSP → online OCSP → CRL) that works on a disconnected device, specify freshness tolerances, and quantify the gap between "key compromised" and "revocation reaches every device."
  • TPM measured boot end-to-end (Phase 7–8): extend PCRs in the right order, produce a COSE_Sign1 quote, write a remote verifier that replays the event log to recheck PCR values, and seal a secret to a PCR policy with a migration story for benign OS updates.
  • Anti-rollback hardware semantics (Phase 6): model OTP/NV monotone counters, implement power-loss-atomic shadow+flip commits, and articulate exactly why committing SVN at verify-time (rather than mark-good) bricks devices.
  • PKI key ceremony engineering (Phase 11): run a witnessed, hashed signing ceremony, design a key-rotation with dual-signing overlap that requires no device re-fusing, and write the revocation runbook triggered by a leaf-key compromise.
  • Full-chain simulator design (Phase 10): build a deterministic, fault-injectable, seed-replayable simulator that exercises TOCTOU, glitch-skip, and power-loss scenarios and produces byte-identical transcripts across machines.
  • TCB hardening and supply-chain integrity (Phase 12): apply #![forbid(unsafe_code)] + cargo-geiger + cargo-deny + cargo-vet, produce a reproducible build with CycloneDX SBOM and SLSA provenance, and run differential conformance against OpenSSL/tpm2-tools to surface intentional divergences.

Per-box detail (one paragraph each):

  • Root CA (offline): Air-gapped, the trust origin. Its key signs intermediates and emits the top-level CRL/dbx. Never online; used only in ceremonies (§11). The hash of its public key (or the PK itself) is what gets fused into device OTP — the single immutable anchor.
  • Intermediate Signing CA (HSM): Day-to-day issuer of leaf signing keys; HSM-resident so the offline root rarely activates. Has its own CRL. pathLen constrains it from minting further CAs. Rotatable and cross-signable without re-fusing devices (§11).
  • Leaf Signing Key (HSM): Signs manifests. EKU = code-signing only. Short-lived; high rotation; the unit revoked first on compromise.
  • Manifest + image: The release artifact. Manifest is a compact binary structure (detached signature over a canonical digest of itself + payload), carrying SVN, key id, cert-chain reference, flags (§8).
  • Trust Anchor store: On device, the fused PK-hash plus (optionally) a small mutable allowlist of cross-signed anchors for migration. Read-only post-provision; the verifier roots all chains here.
  • CRL / dbx denylist + OCSP responder: Revocation surfaces. CRL = signed list of revoked serials; dbx = explicit hash/key denylist usable offline; OCSP = online per-cert status, optionally stapled into the manifest for offline use.
  • Boot ROM (RoT, immutable): First code to run; mask-fixed; reads the fused PK-hash, verifies+measures SPL, jumps only on Accept. Cannot be updated — bugs here are unrecoverable, so it is minimal.
  • SPL / 1st-stage loader / 2nd-stage bootloader / Kernel: Each stage links/calls sbpki-verify to validate the next image's manifest and extends a PCR before transfer. Order is invariant (§7).
  • sbpki-verify (no_std TCB): The pipeline codec → x509 → revoke → rollback → crypto, returning Verdict::Accept or Verdict::Reject(reason). Single point where fail-closed is enforced; zero heap in hot path; deterministic.
  • OTP fuses / NV counter store: OTP holds PK-hash + minimum-SVN (write-once); NV holds the monotonic rollback counter (write-many, monotone). Modeled by sbpki-nv.
  • sbpki-tpm (PCR): PCR bank, extend, TCG-style event log, quote (signed PCR snapshot), seal/unseal of secrets to a PCR policy. Modeled deterministically.
  • sbpki-ab (A/B + recovery): Slot selection, boot-attempt counter, watchdog, fallback to other slot or signed recovery image; commits SVN only after a successful boot ("mark good").
  • Attestation Verifier (remote): Off-device service that checks a quote + event log against expected PCR values and policy, then releases a secret / admits the device to a fleet.

6. Design Principles

  1. Fail-closed, always. Any error — parse, signature, expiry, revocation, rollback, OOM, timeout — yields Verdict::Reject. There is no "warn and continue." Tradeoff: a transient OCSP outage can refuse a valid boot → mitigated by stapled-OCSP + dbx offline path, never by skipping. Violation breaks: a single permissive branch = full bypass.
  2. Verify before execute (no TOCTOU). The bytes verified MUST be the bytes executed: hash the image in the buffer you will jump to, lock/quiesce it (no concurrent DMA), then transfer. Violation breaks: attacker swaps flash/RAM between check and use.
  3. Constant-time on secret-dependent paths. Signature verify, digest compare, and key-id match use constant-time compares (subtle::ConstantTimeEq). Violation breaks: timing oracle leaks which byte of a forged signature/digest is wrong → forgery acceleration.
  4. Minimal TCB. Verifier is #![no_std], #![forbid(unsafe_code)] (except a reviewed crypto/FFI shim), ≤ 96 KB .text. Every dependency is a liability. Tradeoff: re-implement vs import — import only audited crypto; re-implement parsers to control attack surface.
  5. Zero heap in the hot path. Manifest/X.509 parsing runs over a caller-supplied scratch arena; no global allocator at SPL stage. Violation breaks: heap fragmentation/OOM in 256 KB SRAM = unbootable or DoS.
  6. Canonical-only parsing. Accept only canonical DER and one manifest byte layout; reject non-canonical/ambiguous encodings (BER indefinite-length, redundant length forms). Violation breaks: parser differentials → signature-bypass via re-encoding.
  7. Roots fused, not configured. The trust anchor is the OTP PK-hash; mutable trust state (cross-sign allowlist) is additive only and itself signed. Violation breaks: a writable root = evil-maid replaces trust.
  8. Monotonicity is hardware-anchored. SVN/min-SVN and the rollback counter live in OTP/NV with monotone semantics enforced by the model; software cannot decrement them. Violation breaks: rollback to a vulnerable signed image.
  9. Measure everything you load, even if you also verify it. PCR-extend each stage + its config before transfer; the event log records what and why. Tradeoff: measured ≠ enforced — attestation/sealing decides later. Violation breaks: no forensic/attestation record of a tampered-but-rejected attempt.
  10. Determinism + replayability. Same inputs (images, certs, fuses, NV, time) → identical verdict, identical PCR sequence, identical event log; the simulator is seeded. Violation breaks: non-reproducible attestation; un-debuggable boot failures.
  11. Explicit, total error taxonomy. VerifyError is a closed enum; every reject path carries a machine-readable reason code persisted to the event log. Violation breaks: "it just won't boot" with no diagnosis.
  12. Anti-bricking is a first-class invariant. Every flash/commit step is power-loss-atomic; A/B + recovery + watchdog guarantee some signed image boots. Violation breaks: a failed update bricks the device permanently.
  13. Revocation must reach the offline path. Online OCSP is best-effort; dbx (hash/key denylist) is the authoritative offline kill-switch shipped with images. Violation breaks: a revoked-but-still-trusted key boots indefinitely on disconnected devices.
  14. Separation of signing and verifying. Signing infra (keys, ceremonies, HSM) is a distinct trust domain from the device verifier; the device holds no signing capability. Violation breaks: device compromise = ability to forge.
  15. Observability before the OS. The verifier records verdicts + measurements to an NV-backed event log readable post-boot/by attestation; nothing security-relevant is silent. Violation breaks: incidents are invisible until userspace, by which point trust may already be lost.

8. Domain Model / Formats / State Machines

8.1 Signed Manifest — byte layout

All multi-byte integers big-endian. Fixed header then TLV body then signature trailer. Signature covers header ‖ body (the signed region), NOT the trailer.

offset  size  field                description
0x00    4     magic                "SBPK" = 0x53 0x42 0x50 0x4B
0x04    1     format_version       0x01 (bump = incompatible layout)
0x05    1     header_version       minor, additive fields only
0x06    2     flags                bit0 RECOVERY, bit1 AB_SLOT_B, bit2 OCSP_STAPLED,
                                   bit3 DEBUG_UNLOCK_OK, bit4 DUAL_SIGNED, bits5-15 reserved=0
0x08    2     sig_alg              1=Ed25519, 2=ECDSA-P256, 3=RSA-PSS-3072
0x0A    2     hash_alg             1=SHA-256, 2=SHA-384
0x0C    4     svn                  monotonic security version number (anti-rollback)
0x10    4     image_id             stage role: 1=SPL,2=BOOTLOADER,3=KERNEL,4=INITRD,5=RECOVERY
0x14    8     payload_len          length of the payload image in bytes
0x1C    32/48 payload_digest       SHA-256(32) or SHA-384(48) of payload (hash_alg)
...     20    key_id               SHA-1/“SKI”-style 160-bit id of leaf signing key
...     2     chain_ref_len        length of cert-chain-reference TLV body
...     N     chain_ref            TLV: DER cert chain OR a URI/serial reference (see 8.4)
...     2     tlv_count            number of optional TLV records following
...     M     tlv_body             optional TLVs: STAPLED_OCSP, BUILD_META, MIN_SVN_HINT,
                                   DUAL_SIG (second signature for cross-sign migration)
====   ----   END OF SIGNED REGION ====
...     2     sig_len              signature length (Ed25519=64, P256≈70-72 DER, RSA-PSS=384)
...     L     signature            detached sig over SHA-x(signed_region) by key_id

8.2 Manifest grammar (EBNF)

manifest      = header , body , sig_trailer ;
header        = magic , fmt_ver , hdr_ver , flags , sig_alg , hash_alg ,
                svn , image_id , payload_len , payload_digest , key_id ;
magic         = 0x53 0x42 0x50 0x4B ;
body          = chain_ref_len , chain_ref , tlv_count , { tlv } ;
chain_ref     = der_chain | uri_ref ;            (* tag-discriminated, 8.4 *)
tlv           = tlv_tag , tlv_len , tlv_value ;
tlv_tag       = STAPLED_OCSP | BUILD_META | MIN_SVN_HINT | DUAL_SIG ;
sig_trailer   = sig_len , signature ;
signed_region = header , body ;                  (* signature input *)

Parsing rules (normative): bounded total length (≤ 64 KB header+body for SPL stage; payload streamed/hashed separately); tlv_len must not exceed remaining buffer; unknown tlv_tag with critical-bit set ⇒ Reject, else skip; duplicate critical TLV ⇒ Reject; trailing bytes after signature ⇒ Reject; payload_len must equal actual streamed length or Reject.

8.3 Verification pipeline — sequence

Stage_N                sbpki-verify                    sbpki-nv / sbpki-tpm
  │  load manifest(N+1) into arena                          │
  │ ───────────────▶ parse_header() ── bad? ─▶ Reject(MALFORMED)
  │                  parse_body()  ── noncanon? ─▶ Reject(NONCANONICAL)
  │                  resolve_chain(chain_ref) ── ◀── trust_anchor (OTP PK-hash)
  │                  x509_path_validate() ── fail? ─▶ Reject(PATH/EXPIRED/EKU/...)
  │                  revoke_check(dbx,CRL,OCSP) ── revoked? ─▶ Reject(REVOKED)
  │                  read min_svn ◀───────────────────────── sbpki-nv
  │                  if svn < min_svn ─▶ Reject(ROLLBACK)
  │                  stream payload → hash → cmp payload_digest (CT) ── ne? ─▶ Reject(DIGEST)
  │                  verify_sig(signed_region, key) (CT) ── bad? ─▶ Reject(SIGNATURE)
  │ ◀─────────────── Verdict::Accept
  │  extend PCR[image_id_bank] ───────────────────────────▶ sbpki-tpm (record event)
  │  lock region / quiesce DMA
  │  (only on later "mark good") commit min_svn ◀──────────▶ sbpki-nv (monotone CAS)
  │  JUMP →

8.4 Cert-chain reference TLV

chain_ref_tag : 0x01 = DER_CHAIN  → value = concat(DER leaf, DER intermediate[, ...])
                0x02 = URI_REF     → value = utf8 URI + 4-byte CRC (offline: must be cached/stapled)
                0x03 = ANCHOR_IDX  → value = 1-byte index into device cross-sign allowlist

On device offline boot, only DER_CHAIN (self-contained) and ANCHOR_IDX are usable; URI_REF requires a cache.

8.5 X.509 path-validation state (per RFC 5280 sec. 6.1)

State tuple advanced cert-by-cert (leaf→root):

{ working_public_key, working_issuer_name, max_path_len,
  permitted_subtrees, excluded_subtrees, explicit_policy, valid_eku_set }

Transition checks per cert: signature(prev_key) → validity(now) → issuer==prev.subject → basicConstraints(CA=true for non-leaf) → pathLen decrement (Reject if 0) → keyUsage(keyCertSign for CAs / digitalSignature for leaf) → EKU ⊇ codeSigning (leaf) → name-constraints permit subject/SAN → revocation status. Terminal: working_issuer == trust_anchor AND anchor key matches OTP PK-hash.

8.6 Anti-rollback NV model

OTP (write-once):   pk_hash[32], min_svn_floor[u32]   (factory floor)
NV  (monotone):     rollback_ctr[u32]  (== effective min_svn; CAS: new ≥ old or fault)
SVN decision:       effective_min = max(min_svn_floor, rollback_ctr)
                    accept iff manifest.svn ≥ effective_min
commit (mark-good): rollback_ctr ← max(rollback_ctr, booted.svn)  // only after WDT-confirmed boot

8.7 A/B + recovery state machine

states: { TRY_A, TRY_B, ACTIVE_A, ACTIVE_B, RECOVERY, BRICK_GUARD }
vars:   slot_tries[A], slot_tries[B] (decrement on attempt), active_slot, recovery_present

POWER_ON ─▶ pick highest-priority slot with tries>0
  TRY_x: verify(slot_x)
     Accept  ─▶ boot; set bootonce; start WDT
        WDT_kick_before_timeout ─▶ mark slot_x good (tries reset, commit SVN) ─▶ ACTIVE_x
        WDT_timeout/crash       ─▶ tries[x]-- ; reboot
     Reject  ─▶ tries[x]=0 ; try other slot
  both tries==0 ─▶ RECOVERY: verify(recovery_image)
     Accept ─▶ boot recovery (re-provision/repair)
     Reject ─▶ BRICK_GUARD: halt, surface fault, await external recovery (out of scope to auto-fix)

8.8 Measured boot — PCR assignment + event log

PCR Measures
0 Boot ROM / RoT firmware identity
1 RoT config / fuse state digest
2 SPL / 1st-stage loader image
3 SPL config (DTB, env)
4 2nd-stage bootloader image
5 Bootloader config / GPT
6 (reserved)
7 Trust-anchor + dbx state digest
8 Kernel image
9 initramfs / cmdline

Event log entry (TCG_PCR_EVENT2-shaped):

{ pcr_index:u32, event_type:u32, digest_count:u32,
  digests:[ {alg_id:u16, digest:[u8;N]} ], event_size:u32, event_data:[u8] }

event_data carries the human/machine reason (e.g. image_id, key_id, verdict reason). Log is append-only, persisted to NV, replayable: recompute PCR[i] by folding entries.

8.9 Worked examples

  • Happy path: valid Ed25519 leaf, chain to fused anchor, dbx clean, svn=7 ≥ min 5 → Accept; PCR8 extended; WDT kicked; min_svn→7.
  • Rollback attempt: valid signature, svn=3 < effective_min 5 → Reject(ROLLBACK{img=3,min=5}); no PCR commit of acceptance; A/B tries other slot.
  • Revoked leaf: signature valid, but leaf key_id in dbx → Reject(REVOKED).
  • Malformed: trailing bytes after signature → Reject(MALFORMED_TRAILING).
  • Failure path: OCSP unreachable, no stapled OCSP, dbx clean, flag not requiring online → policy decides; if policy=strict → Reject(REVOCATION_UNKNOWN), else accept on dbx-clean (configurable, default strict for kernel, lenient for recovery).

11. Core Schema and Core Types

Normative APIs. Signatures are illustrative (≤ 2 lines), not implementations (CRITICAL RULE 10).

11.1 Identity, version, digest newtypes (sbpki-types)

struct Svn(u32);                  // monotone; Ord; no public decrement
struct KeyId([u8; 20]);           // SKI-style 160-bit signer id
struct PcrIndex(u8);              // 0..=23
enum HashAlg { Sha256, Sha384 }   // maps hash_alg field
enum SigAlg { Ed25519, EcdsaP256, RsaPss3072 }
struct Digest { alg: HashAlg, bytes: [u8; 48] /* len = alg */ }
struct ImageId(u8);               // 1=SPL..5=RECOVERY
  • Ownership: all Copy/Clone, value types, no interior mutability. Persistence: Svn/KeyId/Digest serialize fixed-width big-endian. Compatibility: adding a SigAlg variant is a format_version bump (ADR-010). Concurrency: immutable, Send + Sync.

11.2 Error + verdict (sbpki-types)

enum VerifyError {                 // closed, exhaustive (Principle 11)
  Malformed(MalformKind), NonCanonical, ChainUnresolved, PathInvalid(PathErr),
  Expired, NotYetValid, EkuMissing, ConstraintViolation, Revoked(RevokeKind),
  RevocationUnknown, Rollback{img:Svn,min:Svn}, DigestMismatch, BadSignature,
  ArenaExhausted, Timeout, PolicyDenied }
enum Verdict { Accept, Reject(VerifyError) }   // never silently anything else
  • Every VerifyError has a stable u16 reason code persisted to the event log. Verdict is the only type the loader branches on (I1, Principle 1).

11.3 Manifest (sbpki-codec)

struct ManifestHeader { magic:[u8;4], fmt_ver:u8, hdr_ver:u8, flags:Flags,
  sig_alg:SigAlg, hash_alg:HashAlg, svn:Svn, image_id:ImageId,
  payload_len:u64, payload_digest:Digest, key_id:KeyId }
struct Manifest<'a> { header:ManifestHeader, chain_ref:ChainRef<'a>,
  tlvs:TlvSlice<'a>, signature:&'a [u8], signed_region:&'a [u8] }
fn parse<'a>(buf:&'a [u8], arena:&mut Arena) -> Result<Manifest<'a>, VerifyError>;
  • Zero-copy: borrows buf (the flash/RAM image); signed_region is a subslice (no re-serialization → no canonicalization gap, I2/I8). Mutation: none (read-only view). Serialization: write(&Manifest, &mut [u8]) round-trips byte-identically (conformance gate).

11.4 Canonical DER reader (sbpki-codec)

struct DerReader<'a> { /* cursor over &'a [u8] */ }
fn read_tlv(&mut self) -> Result<DerTlv<'a>, VerifyError>; // rejects non-minimal length, indefinite-len
  • Enforces canonical DER only (I8): minimal length encoding, definite length, sorted SET OF where required. No allocation; returns borrowed slices.

11.5 Crypto traits (sbpki-crypto)

trait Verifier { fn verify(&self, msg:&[u8], sig:&[u8], key:&PublicKey) -> bool; } // constant-time
trait Hasher  { fn update(&mut self, b:&[u8]); fn finish(self) -> Digest; }
trait Clock   { fn now_unix(&self) -> u64; }                 // injected (ADR-028)
trait Rng     { fn fill(&mut self, out:&mut [u8]); }         // injected (ADR-029); not used in verify
enum PublicKey { Ed25519([u8;32]), EcdsaP256(EcPoint), RsaPss{ n:&[u8], e:u32 } }
  • verify MUST be constant-time w.r.t. message/sig contents (Principle 3); returns bool, never leaks which check failed. No heap; RSA verify uses no CRT (P7).

11.6 X.509 path engine (sbpki-x509)

struct Cert<'a> { tbs:&'a [u8], spki:PublicKey, issuer:Name<'a>, subject:Name<'a>,
  not_before:u64, not_after:u64, bc:BasicConstraints, ku:KeyUsage, eku:EkuSet,
  name_constraints:Option<NameConstraints<'a>>, serial:&'a [u8], sig:&'a [u8], sig_alg:SigAlg }
struct PathState { working_key:PublicKey, max_path_len:Option<u8>,
  permitted:SubtreeSet, excluded:SubtreeSet, valid_eku:EkuSet }
fn validate(chain:&[Cert], anchor:&TrustAnchor, clock:&dyn Clock,
            rev:&dyn RevocationSource) -> Result<KeyId, VerifyError>;
  • Returns the validated leaf KeyId on success (then matched against manifest key_id). anchor must hash-match OTP PK-hash (I6). Pure given inputs+clock (I10).

11.7 Trust anchor + revocation (sbpki-x509 / sbpki-revoke)

struct TrustAnchor { pk:PublicKey, pk_hash:[u8;32], cross_sign_allow:&[PublicKey] }
trait RevocationSource { fn status(&self, cert:&Cert, clock:&dyn Clock) -> RevStatus; }
enum RevStatus { Good, Revoked, Unknown }
struct Dbx<'a> { revoked_keyids:&'a [KeyId], revoked_hashes:&'a [Digest] } // offline denylist
struct Crl<'a> { issuer:Name<'a>, this_update:u64, next_update:u64, revoked:&'a [(Serial,u64)], sig:&'a [u8] }
struct OcspResp<'a> { cert:Serial, status:RevStatus, produced_at:u64, this_update:u64, next_update:u64, sig:&'a [u8] }
  • Resolution order: dbx (authoritative offline) → stapled OCSP → fresh OCSP (online) → CRL. Unknown under strict policy ⇒ RevocationUnknown reject (Principle 13, §8.9). CRL/OCSP signatures validated up the same chain.

11.8 NV / OTP (sbpki-nv)

trait Otp  { fn pk_hash(&self) -> [u8;32]; fn min_svn_floor(&self) -> Svn; fn is_locked(&self) -> bool; }
trait NvCounter { fn read(&self) -> Svn; fn commit_ge(&mut self, v:Svn) -> Result<(), NvError>; } // monotone CAS
fn effective_min(otp:&dyn Otp, nv:&dyn NvCounter) -> Svn; // max(floor, counter)
  • commit_ge accepts only v ≥ current; lower ⇒ NvError::Regress (I4). OTP write-once; second write ⇒ fault. Persistence: model is power-loss-atomic (write-ahead shadow + flip).

11.9 TPM subset (sbpki-tpm)

struct PcrBank { pcrs:[Digest; 24], alg:HashAlg }
fn extend(&mut self, idx:PcrIndex, m:&Digest);            // PCR[i] = H(PCR[i] ‖ m)
struct EventLog { entries:Vec<Event> }                     // append-only; replayable
fn quote(&self, sel:PcrSelection, nonce:&[u8], ak:&AttestKey) -> Quote;     // COSE_Sign1-shaped
fn seal(&self, secret:&[u8], policy:PcrPolicy) -> SealedBlob;               // bind to future PCRs
fn unseal(&self, blob:&SealedBlob, now:&PcrBank) -> Result<Vec<u8>, SealErr>;
  • extend is O(1), deterministic; never resets a PCR (extend-only). quote binds (PCR digest ‖ nonce) → unforgeable + fresh (I15). unseal succeeds iff current PCRs satisfy policy.

11.10 A/B + verifier orchestrator (sbpki-ab, sbpki-verify)

enum AbState { TryA, TryB, ActiveA, ActiveB, Recovery, BrickGuard }
struct Slot { id:char, tries:u8, priority:u8, svn:Svn }
fn select(&self) -> Option<&Slot>;            // highest priority with tries>0
fn on_verify(&mut self, slot:char, v:Verdict);// Reject → tries=0; Accept → boot+WDT
fn mark_good(&mut self, slot:char, nv:&mut dyn NvCounter); // commits svn (I12)

// verifier entry point (the TCB API)
fn verify_stage(buf:&[u8], payload:&mut dyn Read, anchor:&TrustAnchor,
  rev:&dyn RevocationSource, otp:&dyn Otp, nv:&dyn NvCounter,
  clock:&dyn Clock, arena:&mut Arena) -> Verdict;
  • verify_stage is the single normative TCB call: pure, no heap, returns Verdict; the loader extends PCR + jumps only on Accept (I1). mark_good is the only path that bumps NV, and only post-WDT (I12, anti-brick I11).

11.11 Arena (sbpki-verify)

struct Arena<'a> { buf:&'a mut [u8], top:usize }
fn alloc(&mut self, n:usize, align:usize) -> Result<&mut [u8], VerifyError>; // ArenaExhausted on overflow
  • Bump allocator over caller buffer (I9, ADR-002); reset between stages; high-water mark exported for the ≤ 16 KB budget (§4). No free (stage-scoped lifetime).

12. Phase 1 — Core Types, Arena, and Manifest Codec

12.1 Objectives

Establish sbpki-types + sbpki-codec + the Arena. Lock the manifest binary layout (§8.1) and canonical-DER reader (§11.4). No crypto yet; parsing + round-trip only. Constraint introduced: zero-heap, zero-copy, no_std.

12.2 Detailed Implementation Steps

  • sbpki-types: Svn,KeyId,PcrIndex,HashAlg,SigAlg,Digest,ImageId,Flags,VerifyError,Verdict (§11.1–11.2, ADR-001). Derive Copy/Clone/PartialEq; manual Ord for Svn (I4 monotone invariant). Assign stable u16 reason codes for every VerifyError (I10, P11).
  • Arena (sbpki-verify::arena, used here for testing): bump alloc over &mut [u8], align-up, ArenaExhausted on overflow, high-water mark (ADR-002, P5, I9).
  • sbpki-codec::manifest: parse(buf,arena) reads fixed header (bounds-checked field by field), then body TLVs, then signature trailer; produces Manifest<'a> with signed_region = exact subslice [0..sig_offset). write(&Manifest,&mut [u8]) for round-trip (ADR-010, I8, §8.1).
  • sbpki-codec::der_reader: DerReader enforcing minimal-length DER, definite length only, depth limit, length ≤ remaining (X.690 canonical DER, P11, I8, ADR-009).
  • sbpki-codec::tlv: TLV iterator with critical-bit handling, duplicate-critical rejection, unknown-non-critical skip (§8.2 EBNF, P6 canonical-only).
  • Observability hook: parser emits a structured ParseTrace (offsets of each field) behind a trace feature for manifest-inspect (P15, ADR-019).

12.3 Deliverable

A library that parses/round-trips manifests and reads canonical DER, no_std, zero-heap. manifest-inspect tool decodes a .sbpk file showing every field offset + the signed region span.

12.4 Acceptance Criteria

  • Round-trip identity on all positive manifest vectors (write(parse(x)) == x), byte-exact.
  • 100 % of malformed vectors → correct VerifyError variant (no panics, no UB).
  • Arena high-water ≤ 16 KB on largest vector. Builds clean for all three -none targets.
  • #![forbid(unsafe_code)] holds; cargo-geiger = 0 unsafe in these crates.

12.6 Pitfalls

  • Integer overflow in length math (offset + len): use checked arithmetic; manifestation = OOB read; detect via fuzz + debug_assert; recovery = Reject.
  • Signed-region drift: recomputing/normalizing bytes before hashing breaks I2/I8; root cause = re-serializing instead of subslicing; debug via byte-diff of signed_region vs source.
  • Alignment in arena: misaligned borrow of multi-byte fields; on strict-align targets (some aarch64 configs) = fault; align-up in alloc.
  • TLV critical-bit confusion: treating unknown-critical as skippable = silent acceptance of attacker TLV; enforce Reject.

12.7 Performance Concerns

Single linear pass, cache-friendly (sequential reads). No allocation. Avoid per-field function-call overhead by inlining bounds checks. Branch-predict the happy path (valid magic/version). Payload is not loaded here — only header+body (≤ 64 KB), keeping working set tiny.

12.8 Edge Cases

Zero-length manifest; header truncated mid-field; payload_len=0; payload_len=u64::MAX (reject as exceeding policy); duplicate non-critical TLV (allowed, first wins or last wins — define: first wins, doc it); empty cert-chain ref; max-depth DER nesting (reject beyond limit).

12.9 Failure Analysis

Breaks: a parser bug = accept-malformed = potential downstream bypass. Detection: fuzz crash / vector mismatch. Blast radius: entire verifier (TCB). Containment: parser is pure + bounded; no state escapes on error. Recovery: Reject + event-log MALFORMED code. Postmortem: replay the offending bytes through manifest-inspect.

12.10 Operational Notes

manifest-inspect is the field tool for "why won't this image parse." Reason codes are stable across versions (compat). No deployment surface (library). Format fmt_ver bump = coordinated release (Compatibility Guarantees).

13. Phase 2 — Cryptographic Verification Primitives

13.1 Objectives

sbpki-crypto: constant-time signature verification for Ed25519 / ECDSA-P256 / RSA-PSS-3072, SHA-256/384 hashing, and injected Clock/Rng traits. Verify-only (no signing in TCB). Constraint: constant-time, no heap, no CRT.

13.2 Detailed Implementation Steps

  • Wrap RustCrypto: ed25519-dalek (verify), p256 (ECDSA verify), rsa (PSS verify path only), sha2. Expose Verifier/Hasher traits (§11.5, ADR-008, R7).
  • ct module: ct_eq(&[u8],&[u8]) -> Choice via subtle; all digest/key-id comparisons route through it (P8/Kocher 1996, P3/§6 P3 constant-time).
  • verify(msg,sig,key): dispatch on SigAlg; decode sig (P256 DER → (r,s) with canonical checks; reject high-S per malleability rule for determinism); PSS with MGF1-SHA-x, salt-len = hash-len (P5/Bellare-Rogaway 1996, ADR-005).
  • No CRT path in RSA verify — import verify-only, never private-key code (P7/Boneh-DeMillo-Lipton 1997, ADR-008).
  • Clock/Rng traits + a FixedClock/SeededRng test impl (deterministic, ADR-028/029, I10).
  • Streaming hash API so payload (up to GBs) hashes without buffering (§11.3 payload is Read, P6/Ed25519 determinism, ADR-004).
  • Side-channel hooks: feature ct-audit runs dudect-style timing checks in CI (P8, P10, §6 P3).

13.3 Deliverable

A crypto crate passing RFC test vectors + Wycheproof edge vectors for all three schemes, no_std, constant-time digest compare. Streaming SHA over arbitrary readers.

13.4 Acceptance Criteria

  • 100 % pass on RFC 8032 (Ed25519), FIPS 186-5/Wycheproof (ECDSA-P256), RFC 8017/Wycheproof (RSA-PSS) verify vectors, incl. all negative cases.
  • High-S ECDSA, non-canonical R/S, wrong-salt PSS, all-zero sig → false/reject.
  • ct-audit shows no message-dependent timing on the compare path (t-stat below threshold).
  • Verify latency within §4 budgets on the bench host (scaled note for 1 GHz target).

13.6 Pitfalls

  • ECDSA malleability (s and n−s both valid): accept-both breaks determinism + can confuse dedup/replay; enforce low-S.
  • PSS parameter confusion (salt len / MGF hash mismatch): silent accept of malformed; pin salt=hash-len, MGF1=hash.
  • Non-constant-time compare of digest/key-id: timing oracle; route every compare through ct_eq.
  • Using a signing-capable RSA path: brings CRT + timing risk into TCB; import verify-only, no private-key code in no_std crate (P7).
  • Reading payload into RAM to hash: blows SRAM budget; stream it.

13.7 Performance Concerns

Ed25519 verify ≈ tens of µs; RSA-PSS-3072 verify is a single exponentiation with small e (3 or 65537) — cheap. SHA-256 dominates for large images: ensure compiler autovectorizes / uses HW SHA on capable targets (feature-gated sha-ni/armv8-crypto). Stream in ≥ 64 KB chunks to amortize call overhead. No allocation.

13.8 Edge Cases

Empty message; sig length wrong for alg; key all-zeros / not on curve (P256 reject); RSA modulus not 3072-bit; SHA over zero-length input (defined KAT); chunk boundary exactly at hash block size; payload length mismatch vs payload_len (caught by streaming counter).

13.9 Failure Analysis

Breaks: a verify bug = forgeable signatures = total compromise. Detection: Wycheproof negative-vector failure. Blast radius: TCB. Containment: verify returns bool; any decode error → false (fail-closed). Recovery: Reject. Postmortem: capture the sig/key/msg triple; replay against reference (OpenSSL) in differential harness.

13.10 Operational Notes

Algorithm agility via SigAlg in the manifest enables migration (Ed25519→PQ later). Constant-time guarantee is a documented security property in SECURITY.md. No runtime config — alg is per-image. ct-audit is a CI gate, not a runtime cost.

14. Phase 3 — Manifest Verifier (Integrity + Signature, pre-PKI)

14.1 Objectives

sbpki-verify::pipeline wiring codec + crypto into a single-cert verifier: parse manifest → stream-hash payload → compare digest (CT) → verify signature against a directly trusted key (the fused PK, before full chains). Establishes the verify_stage skeleton + Verdict flow. Constraint: pure, no heap, deterministic (I10).

14.2 Detailed Implementation Steps

  • verify_stage(buf, payload, anchor, …) (§11.10, ADR-001/002) minimal form: skip X.509/revocation/rollback (stubbed to Good/no-op) — only header parse, payload digest, signature vs anchor.pk when key_id matches (P1/Arbaugh 1997 verify-before-execute, §6 P1).
  • Enforce I2/P2: hash payload from the same source bytes the loader will execute; assert payload_len consumed (TOCTOU prevention, §7 I2).
  • MalformKind/reason-code propagation into a (test) event sink (P11, §6 P11 explicit error taxonomy, ADR-019).
  • Differential check vs a Python reference signer/verifier (scripts/gen_vectors.py) for cross-impl agreement (P9/Wycheproof methodology, ADR-030).
  • Wire Arena reset per call; export high-water (ADR-002, I9, §11.11).

14.3 Deliverable

verify_stage that, given a manifest signed directly by the anchor key + the payload, returns Accept/Reject(reason). examples/sign_and_boot.rs (partial) signs an image with the anchor key and verifies it.

14.4 Acceptance Criteria

  • Valid (anchor-signed) image → Accept; any tamper (1-bit in payload, header, or sig) → correct Reject.
  • Digest + signature compares are constant-time (inherited from Phase 2).
  • Deterministic: 1000× repeat → identical verdict + identical arena high-water.
  • Zero heap; ≤ 16 KB arena; per-call latency within §4 verify budget for 4 MB image.

15. Phase 4 — X.509 Path Validation Engine (RFC 5280)

15.1 Objectives

sbpki-x509: full leaf→root path validation against a fused trust anchor — signature chaining, validity windows, basicConstraints/pathLen, keyUsage/EKU(code-signing), name constraints. Replace Phase 3's direct-key path with chain resolution. Constraint: canonical-DER only, pure, ≤ 2 ms / 3-cert chain.

15.2 Detailed Implementation Steps

  • cert module: decode TBSCertificate fields needed for validation (§11.6) via der + x509-cert struct decoders, but run our own validation logic (ADR-009, R8/webpki) to control semantics.
  • path::validate(chain, anchor, clock, rev) implementing the RFC 5280 sec. 6.1 state machine (§8.5, P11/RFC 5280 sec. 6.1): iterate leaf→…→anchor; per step do the seven checks (§8.5); decrement max_path_len; intersect EKU; update name-constraint subtrees.
  • constraints: basicConstraints CA flag + pathLen; reject CA-as-leaf and over-long paths (RFC 5280 sec. 4.2.1.9, I14).
  • eku: require id-kp-codeSigning (1.3.6.1.5.5.7.3.3) in leaf EKU; anyExtendedKeyUsage handling (reject if policy forbids) (RFC 5280 sec. 4.2.1.12, I14, §6 P7 fail-closed).
  • name_constraints: permitted/excluded subtrees over directoryName/dNSName/etc.; RFC 5280 sec. 4.2.1.10 semantics; reject on excluded match / outside permitted (B3/Ristić chapters 1–5).
  • validity: not_before ≤ clock.now ≤ not_after; explicit injected clock (I13, ADR-028, §6 P10 determinism).
  • Anchor binding: terminal issuer's key MUST hash-match anchor.pk_hash (== OTP, I6, §6 P7); else ChainUnresolved.
  • Integrate into verify_stage: resolve chain_ref (§8.4) → validate → match returned KeyId to manifest key_id → then signature verify (Phase 2, P1/Arbaugh 1997 trust chain).

15.3 Deliverable

A path-validation engine that accepts valid 2–4 cert code-signing chains rooted at the anchor and rejects every RFC 5280 violation class with a specific reason. chain-lint tool validates a chain against profiles offline.

15.4 Acceptance Criteria

  • 100 % correct on a matrix of valid + each violation class (expired, not-yet-valid, bad-EKU, missing-keyUsage, CA-as-leaf, pathLen-exceeded, name-constraint-excluded, wrong-issuer, broken-sig, wrong-anchor).
  • Differential agreement with OpenSSL/webpki on a shared corpus (modulo code-signing-EKU policy differences, documented).
  • ≤ 2 ms per 3-cert chain on bench host; zero heap (arena).
  • Canonical-DER enforced: non-canonical cert → NonCanonical, not silent accept.

15.9 Failure Analysis

Breaks: accepting an invalid chain = trusting an unauthorized signer = bypass. Detection: violation-matrix vectors + differential. Blast radius: TCB. 15.10 Operational Notes

Cert profiles (templates/cert_profiles/) are the authoring contract for the CA (Phase 11) — keep validator + profiles in lockstep (drift = valid certs rejected). Clock source on device must be trustworthy enough for validity (note: secure-boot often runs before NTP; use a coarse trusted time or rollback-counter as a monotonic proxy — documented tradeoff). Anchor change = re-provision (rare, ceremony-gated).

16. Phase 5 — Revocation: dbx, CRL, OCSP, Stapling

16.1 Objectives

sbpki-revoke: authoritative offline dbx (hash/key denylist) + CRL + online/stapled OCSP, integrated into path validation with a fail-closed policy. Flip Phase 3's revocation stub to real. Constraint: offline path must work (dbx), online is best-effort with strict-default policy (Principle 13).

16.2 Detailed Implementation Steps

  • dbx: parse a signed denylist (key_ids + image/cert hashes); consulted first; a match ⇒ Revoked immediately (§11.7, ADR-011, §6 P13 offline revocation). dbx itself is signed by the anchor/KEK-equivalent and version-monotone (R3/edk2 dbx model).
  • crl: DER CRL parse (RFC 5280, P11): issuer, thisUpdate/nextUpdate, revoked serials + dates; verify CRL signature up the chain; nextUpdate < now ⇒ stale ⇒ under strict policy treat as Unknown→reject (ADR-024, §6 P1 fail-closed).
  • ocsp::client: build OCSP request (cert serial + issuer hash), verify OCSP response signature (delegated responder cert w/ id-kp-OCSPSigning EKU), check producedAt/thisUpdate/nextUpdate freshness + nonce (RFC 6960, ADR-011).
  • stapled: OCSP response embedded in manifest TLV (STAPLED_OCSP, §8.2); usable offline; freshness window enforced (B3/Ristić CRL/OCSP tradeoffs, §6 P13).
  • policy: resolution order dbx → stapled → fresh OCSP (online, ≤ 2 s timeout) → CRL; per-image_id strictness (kernel=strict, recovery=lenient-on-dbx-clean, §8.9, ADR-011). Unknown under strict ⇒ RevocationUnknown reject (§6 P1 fail-closed, I7).
  • Integrate RevocationSource into sbpki-x509::path (called per cert) and into the manifest-level leaf check (§11.7, I7).

16.3 Deliverable

A revocation subsystem that blocks revoked keys/serials/hashes via dbx offline, via CRL/OCSP when present, and refuses-on-unknown under strict policy. cmd_crl/cmd_ocsp (Phase 11) interop with it.

16.4 Acceptance Criteria

  • Revoked-via-dbx → Revoked with no network. Revoked-via-CRL/OCSP → Revoked. Good → pass. Unknown+strict → RevocationUnknown reject; Unknown+lenient(recovery)+dbx-clean → pass.
  • OCSP response with wrong responder EKU / bad sig / stale / nonce-mismatch → reject.
  • Stale CRL (nextUpdate passed) handled per policy (strict reject).
  • No silent skip on OCSP timeout (falls to stapled/CRL/dbx, never to "Good").

Breaks: a revoked-but-accepted key boots = compromise persists post-revocation. Detection: revocation vectors; periodic dbx coverage audit. Recovery: publish dbx + new SVN; bump min-SVN to force-skip the revoked image. Postmortem: revocation reason + propagation timeline.

16.10 Operational Notes

Revocation publish runbook (docs/runbooks/): on key compromise → add to dbx + CRL + OCSP, sign, distribute (CDN ≤ 24 h, OCSP ≤ 1 h, §4). Metrics on OCSP responder: request rate, status mix, latency, signature-failure count. Strict-vs-lenient policy is a documented, version-gated decision; changing it = compat event. dbx version is itself attested (PCR7, §8.8).

17. Phase 6 — Anti-Rollback: OTP, Monotonic NV, SVN Enforcement

17.1 Objectives

sbpki-nv: model OTP fuses (PK-hash, min-SVN floor, write-once) and a monotonic NV counter; enforce svn ≥ effective_min in verify_stage; commit SVN only post-mark-good (I3/I4/I12). Constraint: power-loss-atomic, software cannot decrement (I4, I8 monotone).

17.2 Detailed Implementation Steps

  • otp: pk_hash(), min_svn_floor(), is_locked(); second write → OtpError::AlreadyWritten (write-once, I6, §6 P7 immutable root). Modeled as a file/region with a lock bit (B8/Barr §7 flash semantics).
  • nv_counter: read() + commit_ge(v) monotone compare-and-set; lower ⇒ NvError::Regress (I4, §6 P8). Backing model uses a write-ahead shadow + atomic flip (atomic_commit) so power-loss leaves old-or-new, never torn (P4/NIST SP 800-193, I11).
  • svn_store: effective_min = max(floor, counter) (§8.6, P13/AVB rollback-index model, R5/libavb); helper consulted by the verifier rollback stage (I3).
  • Wire into verify_stage: after path+revocation, before signature accept-finalization, check manifest.svn ≥ effective_min else Rollback{img,min} (ADR-013, §8.3 pipeline, I3).
  • Commit path: mark_good (Phase 9) calls commit_ge(booted.svn) — only after WDT-confirmed boot, never at verify time (I12, §6 P12 anti-brick).
  • Fault model hook: sbpki-sim can inject power-loss between shadow-write and flip to test atomicity (P4/NIST SP 800-193 recover model, ADR-013).

17.3 Deliverable

An NV/OTP model + SVN enforcement that rejects downgrade-to-vulnerable images, with power-loss-atomic counter commits and write-once OTP. examples/rollback_demo.rs shows a downgrade rejected.

17.4 Acceptance Criteria

  • svn < effective_min → Rollback; svn ≥ effective_min → pass (subject to other checks).
  • commit_ge rejects any decrement (Regress); accepts equal/greater.
  • OTP second write fails; PK-hash/floor immutable post-lock.
  • Power-loss injection between shadow + flip: post-recovery counter is exactly old or exactly new (never torn), verified across 10k injected faults.

17.6 Pitfalls

  • Committing SVN at verify time (not after boot success): bricks on a bad-but-signed image whose SVN was already burned; commit only post-mark-good (I12).
  • Non-atomic counter write: torn write → ambiguous min → either bypass (lower) or brick (higher); use shadow+flip.
  • floor vs counter confusion: forgetting max(floor,counter) lets a factory-floor downgrade slip; always combine.
  • u32 wrap: SVN near u32::MAX; saturate, never wrap.
  • Burning min-SVN too eagerly on every boot: exhausts rollback range / fuse writes; advance only when shipping a security fix.

17.7 Performance Concerns

Reads are O(1) cheap. Commit is the only "slow" op (modeled flash write ≤ 10 ms, §4) and happens once per successful update, off the boot-critical path (after mark-good). No allocation. NV write amplification bounded by "advance on security fix only."

17.8 Edge Cases

17.9 Failure Analysis

Breaks: accepting a low-SVN image = rollback to a patched vulnerability = re-exploitation. Detection: rollback vectors; counter-regress alarm (I4). Blast radius: device-local. Containment: monotone CAS prevents decrement even under bug. Recovery: ship higher-SVN image + dbx the old one. Postmortem: counter history + which SVN was attempted.

17.10 Operational Notes

SVN bumping policy is a release-engineering decision (bump on security-relevant change, Build and Release Engineering). Counter is attested (its value reflected in PCR/event log). Recovery-floor separation is a documented anti-brick provision. Monotonic-counter exhaustion (fuse banks finite) is a long-horizon concern — design counter as NV (write-many monotone), reserve OTP for the floor only.

18. Phase 7 — Measured Boot: PCR Bank, Extend, Event Log

18.1 Objectives

sbpki-tpm: TPM-2.0-subset PCR bank with extend-only semantics, append-only TCG-style event log, and integration so each stage measures itself + config + trust state before transfer (I5, §8.8). Constraint: deterministic, replayable, extend-only (never reset).

18.2 Detailed Implementation Steps

  • pcr: PcrBank{pcrs:[Digest;24]}; extend(idx,m) = pcrs[idx]=H(pcrs[idx] ‖ m) (§11.9, B4/Arthur ch.12, P12/TCG Firmware Profile); init to all-zero (or vendor reset value); never expose a reset (I5).
  • eventlog: append Event{pcr_index,event_type,digests[],event_data} (§8.8, P12/TCG_PCR_EVENT2 format) on every extend; persisted to NV (sbpki-nv); fold-replay to recompute any PCR (B4/Arthur ch.13, I10).
  • Wire measurement points into the chain (Phase 10 consumes): ROM measures SPL→PCR2; SPL config→PCR3; bootloader→PCR4; trust-anchor+dbx digest→PCR7; kernel→PCR8; initrd+cmdline→PCR9 (§8.8 PCR table, R4/tpm2-tools pcrextend).
  • event_data carries image_id, key_id, verdict reason → the log is the pre-OS audit trail (§6 P9/P15, ADR-019, ADR-021 CBOR).
  • eventlog-replay tool: read log → recompute PCRs → diff vs reported (§8.8, R4/eventlog-replay semantics).
  • Hook verify_stage to emit a measurement event regardless of Accept/Reject (record tampered-but-rejected attempts too) (P2/Parno 2010 completeness, I5).

18.3 Deliverable

A PCR engine + event log where extending a known sequence yields known PCR values, and the log replays to the same values. cmd_tpmsim extends/reads PCRs; eventlog-replay verifies.

18.4 Acceptance Criteria

  • Known extend sequence → known PCR digests (golden vectors, both SHA-256 and SHA-384 banks).
  • Event-log replay recomputes PCRs bit-exactly (I10).
  • Extend is order-sensitive (swapping two measurements changes the PCR) — proven by vector.
  • Reject paths still emit a measurement event (completeness, I5).

19. Phase 8 — Remote Attestation: Quote, Verify, Seal/Unseal

19.1 Objectives

sbpki-tpm::quote/seal + an attestation verifier (sbpki-cli cmd_attest): produce a quote (signed PCR snapshot + nonce) by an Attestation Key (AK), verify it remotely against expected PCR policy + event log, and seal/unseal secrets to a PCR policy (I15). Constraint: freshness-bound (nonce), unforgeable (AK sig), deterministic verify.

19.2 Detailed Implementation Steps

  • quote(sel,nonce,ak): compute quote_digest = H(PCR_select_digest ‖ nonce); sign with AK (Ed25519); wrap in a COSE_Sign1-shaped envelope (ADR-022, B4/Arthur ch.13, P12/TCG) carrying selected PCR values + event-log reference (I15).
  • AK provisioning (modeled): AK is an Ed25519 key whose public part is certified by the intermediate CA (an AK cert) — links device identity to the PKI (P2/Parno 2010 attestation trust chain, P15/SGX Explained on attestation). Full EK→AK enrollment deferred (§1.5).
  • Verifier (cmd_attest verify): challenge with random nonce → receive quote + event log → verify AK cert chain (reuse sbpki-x509, §11.6) → verify quote signature → recompute PCRs from event log (Phase 7 replay, I10) → compare to expected golden policy → emit Admit/Deny + reason (ADR-022, I15).
  • seal(secret,policy): encrypt secret bound to a target PCR policy (modeled with an AEAD keyed by a value derived from the policy + a device-bound key) (B4/Arthur ch.22). unseal(blob,now_pcrs): release iff current PCRs satisfy policy.
  • Policy language: a set of (pcr_index → expected_digest) plus optional event-log predicates (e.g. "kernel image_id == X") (P14/ChromiumOS vboot seal design, ADR-012).

19.3 Deliverable

An attestation round-trip: device quotes its boot state, a remote verifier admits/denies based on policy, and a sealed secret unseals only in the expected boot state. examples/attest_demo.rs demonstrates Admit + secret release; tampering flips to Deny + seal-fail.

19.4 Acceptance Criteria

  • Valid quote (correct AK, fresh nonce, expected PCRs) → Admit; wrong PCR / stale nonce / forged AK sig → Deny with reason.
  • Event-log replay must equal quoted PCRs or Deny (consistency, I15).
  • Sealed secret unseals only when PCRs match policy; any measurement change → SealErr::PolicyUnmet.
  • Nonce replay (reuse old quote) → Deny (freshness).

  • Not verifying the AK chain: an unauthenticated AK = anyone attests anything; validate AK cert to anchor.
  • TOCTOU between quote and use: PCRs can change after quote; bind decisions to the quoted state + short validity.

Quote = one Ed25519 sign over a small digest (≤ 5 ms, §4). Verify = chain validate + one sig verify + log replay (replay = N hash folds, N=#events, cheap). 19.9 Failure Analysis

Breaks: false Admit = untrusted device joins fleet / gets secrets; false Deny = good device locked out. Detection: attestation vectors; Admit/Deny rate monitoring. Blast radius: fleet trust + sealed-secret confidentiality. Containment: fail-closed verifier (Deny on any doubt). Recovery: re-provision AK / re-seal; rotate fleet secret if Admit was wrongly granted. Postmortem: quote + log + policy diff.

19.10 Operational Notes

Attestation verifier is a real service: metrics (Admit/Deny/latency), tracing per challenge, alert on Deny-rate spike (possible fleet compromise or bad rollout). Golden PCR policy is versioned per release (a new kernel → new expected PCR8) — coordinate with Build and Release Engineering. Seal/unseal migration on update is a runbook. AK enrollment ceremony deferred (§1.5) but its interface is fixed here.

20. Phase 9 — A/B Slots, Recovery, and Anti-Bricking

20.1 Objectives

sbpki-ab: dual-bank A/B image selection, boot-attempt counting, watchdog-gated mark-good, fallback to the other slot, then to a signed recovery image, with a brick-guard terminal state (I11/I12, §8.7). Constraint: some signed image always boots; every commit power-loss-atomic.

20.2 Detailed Implementation Steps

  • slot: Slot{id,tries,priority,svn}; select() picks highest-priority slot with tries>0 (§11.10, I11).
  • statemachine: implement §8.7 transitions (P4/NIST SP 800-193 Detect/Recover model, R5/libavb slot-verify, P14/vboot A/B): TryX→verify→Accept(boot+WDT)/Reject(tries=0); WDT timeout→tries--; both exhausted→Recovery; recovery fail→BrickGuard (§6 P12 anti-brick).
  • watchdog: a countdown the booted image must "kick" (mark_good) within the window; else the next reset decrements tries (simulated by sbpki-sim, ADR-013, I11).
  • markgood: on WDT-confirmed boot, reset slot tries + commit_ge(svn) (the only SVN bump, I12, §6 P12, ADR-002).
  • Recovery slot: a separate signed image with its own (lower) SVN floor (§17.8) so it can always run; verified by the same verify_stage (P4/NIST SP 800-193 Recover, I11).
  • Atomic slot-metadata updates via sbpki-nv::atomic_commit (shadow+flip); power-loss leaves a consistent state (B8/Barr §7, §6 P12, I12).
  • Integrate with anti-rollback: a slot's SVN is committed only after success; a rejected/failed slot never bumps min-SVN (I3, I4, §8.6).

20.3 Deliverable

An A/B + recovery state machine that survives a corrupt/failed slot by falling back, boots recovery when both slots fail, and never bricks (always reaches a bootable signed image or a diagnosable BrickGuard). examples/ab_recovery_demo.rs corrupts slot A and shows fallback → B → recovery.

20.4 Acceptance Criteria

  • Corrupt slot A (bad sig) → tries[A]=0 → boots B.
  • B boots but crashes pre-kick (WDT timeout) → tries[B]-- → retry/other slot/recovery.
  • Both slots fail → recovery image boots.
  • Power-loss during slot-metadata commit (10k injected) → state always consistent (no torn metadata, no double-brick).
  • mark-good is the only path that bumps SVN; verified by audit.

20.6 Pitfalls

  • Committing SVN before mark-good: a slot that verifies but fails to run bumps min-SVN → can brick the other good-but-lower slot; commit only post-kick (I12).
  • Watchdog too short: legitimate slow boot trips WDT → false fallback loop; size window to worst-case boot + margin.
  • Recovery sharing the rollback floor: a min-SVN bump that excludes recovery = unrecoverable; recovery uses a separate floor (§17.8).
  • Non-atomic slot flip: torn "active slot" pointer → boots neither/both; shadow+flip.
  • Tries underflow: decrement below zero; saturate at 0 = "exhausted."

20.7 Performance Concerns

Slot selection O(slots)=O(2). Metadata read/write tiny. Watchdog is timer-based, no busy loop. Fallback adds at most one reboot cycle (RTO ≤ 1 reboot, §4). Recovery verify is one more verify_stage. No allocation.

20.8 Edge Cases

First boot (both slots fresh, tries=max); identical SVN in both slots (priority breaks tie); recovery missing/unprovisioned → straight to BrickGuard with clear reason; update writes slot B while booted from A (atomic, A stays bootable); both slots same image (degenerate but valid); WDT kicked but boot later hangs (next reset handles); priority inversion (define deterministic priority).

20.9 Failure Analysis

Breaks: a brick = field RMA / dead device; an infinite fallback loop = unavailability. Detection: boot-attempt counter, fallback events, BrickGuard alarm. Blast radius: device-local (but fleet-wide if a bad rollout hits all). Containment: A/B isolates a bad update to one slot; recovery is the last resort. Recovery: boot recovery → re-flash good image → mark-good. Postmortem: slot tries history + which stage failed + reason codes.

20.10 Operational Notes

A/B + WDT is the anti-bricking contract (Principle 12). Rollout strategy: update inactive slot, reboot once, auto-mark-good on success, else auto-fallback (canary-friendly, Operational Readiness). Recovery image is rarely updated, separately signed, lower SVN floor. Fleet dashboards: fallback rate (a spike = bad release), BrickGuard count (must stay ~0). Rollback of a release = let A/B fall back to the previous good slot (no re-flash needed).

21. Phase 10 — Full-Chain Simulator (ROM → init)

21.1 Objectives

sbpki-sim: wire crates 1–9 into a deterministic, replayable boot harness modeling RoT/ROM/SPL/2nd-stage/kernel/init, OTP/NV, PCRs, A/B — the runnable substrate proving the whole chain end-to-end. Constraint: deterministic given a seed + scenario; fault-injectable.

21.2 Detailed Implementation Steps

  • rot/rom: immutable first stage holding the fused PK-hash; verifies+measures SPL; jumps only on Accept (I1, P1/Arbaugh 1997 AEGIS, B5/Proudler ch.4–6 RTM).
  • spl/loader/stage: generic stage runner: load next image+manifest into a modeled memory region, call verify_stage, extend PCR, (optionally) inject TOCTOU/DMA to prove I2 defenses, transfer control (R1/U-Boot FIT, R2/TF-A CoT, ADR-013).
  • wiring: assemble the chain with injected Clock, Otp, NvCounter, PcrBank, RevocationSource, A/B state (§11.5/11.8/11.9/11.10, ADR-028/029).
  • replay: record (scenario, seed, inputs) → deterministic transcript (verdicts, PCR sequence, event log); re-run yields identical transcript (I10, §6 P10, ADR-013).
  • Scenario DSL (TOML): define images, signatures, certs, fuses, NV state, faults (corrupt-slot, power-loss, glitch-skip-check), expected outcome (P4/NIST SP 800-193 scenario taxonomy, R9/vboot_reference scenario).
  • Fault injection: model a glitch that skips a verify branch → must be caught by redundant re-check (defense-in-depth, Threat Model T7, B9/Bhunia §9 fault injection).

21.3 Deliverable

cmd_sim run scenario.toml boots the full chain in the simulator and prints the verdict per stage, the PCR bank, the event log, and the A/B state. Replays bit-exactly.

21.4 Acceptance Criteria

  • Happy-path scenario boots ROM→init with all Accepts + expected PCRs + committed SVN.
  • Each negative scenario (tamper at any stage, rollback, revoked, corrupt slot) halts at the right stage with the right reason + falls back correctly.
  • Replay of any scenario reproduces the transcript byte-for-byte across runs/machines.
  • TOCTOU/glitch scenarios are detected (redundant check) or contained (fail-closed).

21.9 Failure Analysis

Breaks: a sim that's wrong gives false confidence. Detection: cross-check sim semantics against reference impls (R1/R5/R9) on shared scenarios; differential. Blast radius: confidence in the whole project. Containment: sim is test-only (not the device verifier — same sbpki-verify runs in both). Recovery: fix sim model; re-run all scenarios. Postmortem: transcript diff.

21.10 Operational Notes

The sim is the CI gate for end-to-end behavior and the demo vehicle (examples/). It is not shipped to devices — the device links sbpki-verify directly, ensuring the same code is tested and deployed. Scenario corpus doubles as regression suite + documentation of intended behavior.

22. Phase 11 — PKI: CA Hierarchy, Ceremonies, Revocation Issuance

22.1 Objectives

sbpki-ca + sbpki-cli: build the offline-root → HSM-intermediate → leaf signing hierarchy, run signing ceremonies, sign manifests, issue CRLs + run an OCSP responder, and support rotation / cross-signing / dual-signing for migration. Constraint: device holds no signing key (Principle 14); root offline; intermediates HSM-resident (modeled via PKCS#11).

22.2 Detailed Implementation Steps

  • root/intermediate/leaf: generate keys + X.509 certs matching templates/cert_profiles/ (code-signing EKU, correct basicConstraints/pathLen, name constraints) — validated by the same sbpki-x509 (lockstep, §15.10, B3/Ristić ch.1–5, P11/RFC 5280, ADR-009).
  • ceremony: scripted, witnessed signing flow (templates/ceremony_script.md.tmpl); produces a hashed, logged transcript (scripts/ceremony_witness.sh); root key only ever used here (air-gapped model, §6 P14 separation, ADR-023).
  • pkcs11: PKCS#11-shaped backend (softhsm in dev, real HSM in prod, §1.5 defer real transport) so intermediate/leaf private keys never leave the token (key custody, §6 P14, ADR-023).
  • cmd_sign: given an image + leaf key (via PKCS#11) + chain, emit a signed manifest (§8.1, ADR-010); supports DUAL_SIG (two signatures: old + new key) during migration (§8.2 DUAL_SIG TLV, §6 P12).
  • crl_issue: build + sign CRLs (RFC 5280, P11) per issuer; cmd_crl publish (ADR-024, §6 P13 revocation).
  • ocsp_responder: a service answering OCSP (RFC 6960) with a delegated responder cert (id-kp-OCSPSigning); supports producing stapled responses for embedding (ADR-011, R6/BoringSSL OCSP).
  • rotation: key-rollover flow — cross-sign the new intermediate with the old (and/or anchor), dual-sign manifests during the overlap, then retire the old; no device re-fusing required because chains still terminate at the fused anchor (or a cross-signed, anchor-trusted bridge) (B3/Ristić cross-signing, ADR-018 UEFI mapping).

22.3 Deliverable

A complete PKI toolkit: mint a 3-tier hierarchy, sign images, issue/publish CRLs, serve OCSP, and execute a key rotation with dual-signing — all verifiable by sbpki-verify. examples/sign_and_boot.rs runs end-to-end against this CA.

22.4 Acceptance Criteria

  • Certs minted by sbpki-ca validate under sbpki-x509 (profiles ↔ validator lockstep) and reject when profiles are violated.
  • A manifest signed via PKCS#11 leaf verifies in the sim chain (Phase 10).
  • CRL/OCSP issued here are correctly honored by Phase 5 (revoked serial blocked).
  • Key rotation with dual-signing: old and new manifests both verify during overlap; after retiring old key (dbx the old leaf), only new verifies.
  • Ceremony produces a tamper-evident, hashed transcript.

22.6 Pitfalls

  • Root online / key on disk: defeats the offline-root model; enforce PKCS#11 + air-gap ceremony for root.
  • Profile/validator drift: CA mints certs the verifier rejects (or vice-versa) → fleet-wide boot failures; single source of truth for profiles + CI cross-check.
  • Rotation without overlap: retiring old key before new propagates bricks devices that only trust old chains; dual-sign + cross-sign overlap window.
  • Reusing one key for sign + OCSP: separate responder key with OCSPSigning EKU; reuse weakens custody + EKU semantics.
  • Unbounded leaf lifetime: long-lived leaves widen compromise blast radius; short-lived + frequent rotation.

22.7 Performance Concerns

Signing is host/HSM-bound, off the device path; batch signing scales with cores. OCSP responder is a service: cache signed responses (status changes slowly), pre-sign stapled responses; latency dominated by signature op + network. CRL size grows with revocations — segment/delta-CRL for large fleets (Scalability Analysis).

22.8 Edge Cases

Ceremony interrupted (resume from transcript / abort); HSM unavailable (signing blocked — fail-closed, no fallback to file key); cross-sign loop (A signs B signs A) — detect + reject; expired intermediate mid-rotation; OCSP for a cert from a retired issuer; dual-signed manifest where one sig is valid and one corrupt (define: require the expected-for-this-device sig to be valid; §8.9 policy).

22.9 Failure Analysis

Breaks: signing-infra compromise = attacker mints valid images (worst case, supply-chain). Detection: ceremony transcripts, HSM audit logs, anomalous signing volume. Blast radius: entire fleet trusting that key until revoked. Containment: HSM custody limits key extraction; offline root limits root abuse; dbx is the kill-switch. Recovery: revoke compromised key (dbx + CRL + OCSP), rotate, bump min-SVN, re-sign. Postmortem: which key, custody timeline, propagation.

22.10 Operational Notes

Runbooks: signing ceremony, key rotation, revocation publish (docs/runbooks/). Threshold/quorum (m-of-n) root signing deferred (§1.5) — interface reserved. Key lifecycle: offline root (years), HSM intermediate (1–2 yr, rotatable), leaf (weeks/per-release). Revocation SLAs (§4) are operational commitments. SBOM + provenance of signing tools themselves (Build and Release Engineering) — the signer is also in scope for supply-chain integrity.

Operational Readiness

  • Metrics: (services) OCSP req-rate/status-mix/latency/sig-failures; attestation Admit/Deny/latency; (fleet via attestation reports) boot-verdict mix, fallback rate, rollback-reject rate, BrickGuard count, dbx-version distribution.

  • Structured logging: event log = CBOR (machine) + JSON (human); every entry carries stable reason code + image_id/key_id.
  • Dashboards: Fleet Trust (verdicts, dbx version), Revocation (OCSP/CRL health, revoked-but-booting count), Attestation (Admit/Deny, deny-reason breakdown), Anti-Brick (fallback/recovery/BrickGuard rates), Signing (ceremony/rotation status, HSM health).

  • Incident response: key compromise → revoke+rotate runbook; bad rollout → halt rollout + rely on A/B fallback; brick wave → recovery campaign.
  • Runbooks (docs/runbooks/): signing ceremony, key rotation, revocation publish, recovery/unbrick, golden-PCR update, dbx publish.
  • Backup/restore: CA key backups (HSM-wrapped, geographically split, quorum to restore); revocation/CRL state versioned + mirrored; restore drills quarterly.
  • Deployment topology: verifier = linked library on device (no service); OCSP responder + attestation verifier = stateless services behind LB + CDN for CRL/dbx distribution.
  • Canary / rolling / rollback: update inactive A/B slot → reboot one device cohort → auto-mark-good or auto-fallback; expand cohort on success; rollback = let A/B fall back (no re-flash). Recovery image updated rarely, separately.
  • Migration: format fmt_ver bumps + algorithm migration via dual-signing + cross-signed intermediates (§11); golden-PCR + cert-profile changes versioned per release.

Compatibility Guarantees

  • Wire/format compatibility: format_version (manifest) = incompatible-change gate; header_version = additive-only (new optional TLVs). A verifier MUST reject a higher format_version it doesn't understand (fail-closed), accept additive header_version.
  • Cert/CRL/OCSP compatibility: strict RFC 5280/6960 DER; canonical-only. New extensions: non-critical = ignorable, critical-unknown = reject.
  • Storage compatibility: OTP layout (PK-hash + floor) is fixed at provisioning (immutable). NV counter + event-log record formats are versioned with a format byte; readers handle ≤ current version.
  • API stability: verify_stage signature + Verdict/VerifyError reason codes are a stable contract (frozen at Phase 3/12). Adding a VerifyError variant is a minor bump (reason codes never reused/renumbered).
  • Schema evolution: new SigAlg/HashAlg → format_version bump; dual-signing bridges the transition.
  • Deprecation policy: deprecated algorithms (e.g. SHA-1 anywhere but legacy SKI) refused by default; a deprecated key is dbx'd, not silently distrusted.
  • SemVer: crates follow SemVer; sbpki-verify (TCB) treats any behavior change affecting Accept/Reject as at least minor, security fixes as patch with advisory.
  • Rolling-upgrade guarantees: A/B ensures a device always runs old-or-new; dual-signed images verify under both old and new trust state during rotation overlap; golden-PCR policy is versioned so attestation tolerates a staged fleet.

Testing Strategy

  • Unit: every parser field, every X.509 check, every revocation branch, NV monotonicity, PCR extend, A/B transitions.
  • Integration: full verify_stage over real chains; sim boot scenarios (Phase 10).
  • Differential: X.509 vs OpenSSL/webpki; PCR/quote vs tpm2-tools semantics; rollback vs libavb rollback-index semantics; signature vs reference signers. Intentional divergences pre-classified.
  • Property (proptest): parse∘write = identity; verify is deterministic; monotone counter never decreases; A/B always reaches a bootable-or-BrickGuard state; canonical-DER rejects all non-canonical re-encodings.
  • Fuzzing (cargo-fuzz+AFL++): manifest, DER, X.509 path, CRL, OCSP; sanitizers; structure-aware; ≥ 1000 CPU-h; 0 crash/UB; all errors typed.
  • Chaos / fault injection: power-loss at every NV/slot step; glitch-skip a verify branch; corrupt NV/log; random scenario soak — all deterministically replayable.
  • Deterministic replay: every sim run + every found bug captured as a seeded transcript/fixture (regression).
  • Soak: long-running random-scenario sim (millions of boots) watching for nondeterminism/leaks.
  • Conformance/compatibility: the master vector corpus (Phase 12) incl. Wycheproof; cross-version format compatibility tests.
  • Performance regression: criterion baselines gated in CI (>5 % = fail).
  • Const-time: ct-audit (dudect-style) on verify/compare paths.

Build and Release Engineering

  • Reproducible builds: pinned rust-toolchain.toml + Cargo.lock; SOURCE_DATE_EPOCH; strip embedded paths/timestamps; reproducible.yml rebuilds + diffs hashes (bit-identical gate).
  • Artifact signing: release binaries + the signing tools themselves signed (we dogfood our PKI); detached signatures + checksums published.
  • SBOM: CycloneDX 1.5 per artifact (ADR-026); dependency graph + licenses (cargo-deny).
  • Provenance: in-toto / SLSA-style attestation of the build (source→artifact); verified at release.
  • Release channels: nightly (fuzz/bench), beta (conformance-gated), stable (all gates + reproducible). Verifier (TCB) on a slower, more-scrutinized cadence than tooling.
  • CI/CD topology: matrix build/test (targets × features) → fuzz (nightly) → conformance + differential → reproducible-build → release (sign + SBOM + provenance + publish).
  • Version stamping: crate version + git hash + format versions embedded in --version and in build provenance.
  • Dependency auditing: cargo-deny (advisories/licenses/sources) + cargo-vet (trusted reviews) for TCB deps; renovate-style pinned bumps reviewed.
  • Supply-chain verification: consumers verify artifact signature + provenance before linking the verifier; HSM/ceremony transcripts archived.

Performance Engineering

  • Benchmarking: criterion micro-benches (verify by scheme/size, path validation, hash, PCR extend) + an end-to-end boot-chain budget bench inside the sim with a cycle-cost model for a 1 GHz RoT core.
  • Profiling: perf + flamegraphs on the verify hot path; confirm SHA dominates and is HW/SIMD-accelerated where available; confirm chain-validate is a handful of sig-verifies.
  • Allocator analysis: dhat/heaptrack on an std mirror of the no_std path to prove zero heap in verify_stage; arena high-water tracked per stage (≤ 16 KB).
  • Lock analysis: verifier is single-threaded/lock-free (pure function); services use bounded thread pools — contention only in OCSP/attestation, measured.
  • Cache analysis: sequential parsing = good locality; certs/manifests small + hot; dbx sorted for branch-friendly binary search.
  • Syscall analysis: verifier does none (library); tools stream payload in ≥ 64 KB chunks to amortize I/O.
  • Throughput targets: SHA-256 ≥ 200 MB/s (1 GHz SW) → 4 MB ≤ 20 ms; full chain crypto ≤ 120 ms (§4).
  • Tail latency: ensure pathological certs/CRL/dbx can't inflate p99 (bounded sizes + depth caps); measure distributions, not means.
  • Key optimization: verify + measure share a single payload hash pass (Phase 7) — never hash an image twice.

Scalability Analysis

  • Device verifier: O(1) per boot, per device — no scaling concern by construction; bounded memory + code size are the limits (§4).
  • Bottlenecks: (a) SHA over large images (CPU-bound, mitigated by HW SHA); (b) OCSP responder under fleet-wide cert-status load; (c) CRL size growth with cumulative revocations; (d) attestation verifier under simultaneous fleet check-in.
  • Horizontal scaling: OCSP responder + attestation verifier are stateless → scale linearly behind a load balancer; CRL/dbx distributed via CDN/mirrors (read-mostly, cacheable).
  • Vertical scaling: batch signing scales with cores/HSM throughput; not on any device-critical path.
  • Sharding/partitioning: revocation data partitioned by issuer; delta-CRLs to bound transfer size; OCSP responses cached + pre-signed (status changes slowly).
  • Replication pressure: revocation + golden-PCR state replicated to mirrors; eventual consistency acceptable within the propagation SLA (§4).
  • Coordination overhead: none on device (no consensus in boot); services coordinate only on revocation publish (low frequency).
  • Network fanout: attestation = N devices × periodic check-in → size verifier fleet to peak check-in; stagger schedules.
  • Storage growth: event logs bounded per device (NV-capped, oldest-truncated with a marker); CA-side issuance/revocation logs grow with fleet — archived/rotated.
  • Metadata scaling: dbx grows with revocations → bound + use hash-prefix filters; min-SVN advances slowly (only on security fixes) so rollback range is preserved.

Mental Models & First Principles

MM1 — The Fused Hash is the Entire Trust. Expert insight: the OTP PK-hash is not a key; it is the root of all trust. Everything downstream — signatures, chains, revocation, attestation — is only as strong as the immutability of that 32-byte value. What it predicts: any mutable "root" (writable register, EEPROM not locked, a signed-config-selects-root scheme) is attackable without breaking cryptography. Bug class without it: "configurable root of trust" that accepts any root whose signature verifies — evil-maid swaps the root pointer. Applied in: §7 I6, §6 P7, Phase 6 (§17.2 OTP lock), §11.8.

MM2 — Verify-Before-Execute is a Total Order. Expert insight: the invariant "verify(N+1) = Accept" must complete before the CPU's program counter can reach stage N+1's entry point. It is not "verify and then execute later" or "execute with a guard." What it predicts: any async/deferred verification path has a TOCTOU window exploitable by DMA or flash DMA attacks. Bug class without it: transfer-of-control to unverified code even when verify returns Accept, if the jump site is checked separately from the verified buffer. Applied in: §7 I1/I2, §8.3 pipeline, Phase 3 (§14.2), §3 architectural overview.

MM3 — Constant-Time is a Specification Constraint, Not an Implementation Detail. Expert insight: any comparison or branch on a secret-derived value creates a timing oracle; the entire function must be data-oblivious — not just the final compare. What it predicts: a "constant-time signature verify" that has a branch on the number of leading zero bytes in the public key still leaks. Bug class without it: partial timing oracle that reduces verification to a search with ≈ 256 × n queries instead of 2^256. Applied in: §6 P3, Phase 2 (§13.2 ct module, ct-audit), §11.5, §6 Pitfalls P8/Kocher.

MM4 — Revocation is a Distributed Systems Problem, Not a Crypto Problem. Expert insight: once a key is revoked, the challenge is not "can we mark it revoked?" (trivial) but "does every device know it is revoked before it boots again?" (a replication/freshness problem). What it predicts: an offline device will boot a revoked-key-signed image for exactly the duration of its disconnection plus the revocation propagation latency. Bug class without it: treating revocation as synchronous — an online OCSP-only scheme silently passes on network failure. Applied in: §5.2 revoke policy, Phase 5 (§5.2 dbx-first design), §6 P13, Scalability Analysis.

MM5 — Anti-Rollback is a Hardware Contract, Not a Software Policy. Expert insight: if the minimum SVN is stored in software-writable memory, rollback protection is only as strong as the software that enforces it — which the attacker controls. The monotonic guarantee must come from a medium the verifier itself cannot decrement. What it predicts: a "monotonic counter" in a writable flash page or a software variable is trivially bypassed by reflashing. Bug class without it: SVN enforcement in software with a writable counter → attacker resets counter to 0, boots any signed image. Applied in: §7 I3/I4, Phase 6 (§17.2 OTP/NV model), §8.6, §6 P8.

MM6 — Measured Boot Records; Verified Boot Enforces. Expert insight: a PCR extend is not an access control — it records what ran, it does not prevent anything from running. The enforcement comes from attestation (refusing to release a secret) or sealing (the secret physically won't unseal in the wrong state). Conflating measurement with enforcement produces a "measured boot" that still boots attacker code, just with a different PCR. Bug class without it: removing verified-boot (signature check) and keeping measured-boot, then concluding the platform is "still attested" — it is, but it attests the attacker's code. Applied in: §3 (verified vs measured distinction), Phase 7 (§18.2), Phase 8 (§8.2), §6 P9.

MM7 — Parser Differentials are Signature Bypasses. Expert insight: if two implementations parse the same byte sequence differently — e.g., one accepts BER indefinite-length, the other expects DER — the signer signs using one parser's view and the verifier accepts using another's, potentially verifying a modified body. The canonical-only rule is not pedantry; it is the closure of a bypass class. Bug class without it: malformed DER where a re-encoding (e.g., non-minimal length) causes the verifier to hash a different signed_region than the signer did. Applied in: §7 I8, §6 P6/P8, §8.2 parsing rules, Phase 1 (§1.2 canonical check), Phase 12 (§23.2 differential).

MM8 — The Arena Allocator is a Security Boundary. Expert insight: in a TCB with 256 KB SRAM and no MMU, a heap allocation failure during verification must yield a typed Reject, not a crash, a partial-state accept, or an "out of memory, skipping cert chain check." The arena is not just a performance optimization; it is the mechanism that makes "OOM = fail-closed" achievable. Bug class without it: heap OOM mid-path-validation leaves the verifier's state machine partially advanced; depending on where it is interrupted, it may return Accept or an uninitialized verdict. Applied in: §7 I9, §6 P5, Phase 1 (§1.2 arena), §11.11, §4 constraint table.

MM9 — Mark-Good is the Commit Point. Expert insight: the SVN monotone counter must advance only after the new image has proven it can boot successfully. "Advance on verify" bricks the device if the image passes verification but then crashes at runtime (bad filesystem, corrupted config, HW incompatibility). The watchdog-gated mark-good is the two-phase commit of the boot update protocol. Bug class without it: advancing min-SVN at verify time → the only good slot is now below the new floor → permanent brick. Applied in: §7 I12, §8.7 A/B state machine, Phase 6 (§17.2 commit path), Phase 9 (§20.2 markgood), §6 P12.

MM10 — Attestation is Only as Strong as the Event Log's Completeness. Expert insight: a quote snapshots PCR values; a verifier replays the event log to confirm why those values are what they are. If the event log is incomplete (missed a measurement, truncated, tampered), the PCRs can be consistent with the log yet not consistent with what actually ran. The policy "PCR8 matches expected kernel" is only meaningful if every extension into PCR8 is logged. Bug class without it: a stage that extends PCR8 but does not append an event log entry → attestation verifier cannot distinguish "correct kernel" from "attacker kernel that extends the right hash." Applied in: Phase 7 (§18.2 log+PCR atomic), §7 I5, §8.2 event-log replay, §6 P15.

UEFI Secure Boot: chose a writable NVRAM variable (PK) as the trust anchor, sacrificing immutability for field provisioning flexibility. This wins for the PC ecosystem where OEM, enterprise, and end-user key management must coexist on the same hardware without fuse programming — essential for the diversity of the x86 platform market.

Android Verified Boot (AVB): chose RPMB (Replay Protected Memory Block) as the anti-rollback medium and a flat per-partition rollback index instead of X.509 chains. This wins for high-volume Android OEM silicon where RPMB is universally available, the signing hierarchy is controlled end-to-end by one vendor per device, and the complexity of X.509 path validation in the bootloader is not justified.

Arm Trusted Firmware-A (TF-A) CoT: chose a firmware-descriptor-driven Chain of Trust (a structured C array of image/cert/key descriptors) rather than a general X.509 validator, trading generality for minimalism in BL1/BL2 TCB. This wins when silicon vendors supply a fixed boot flow with a known cert structure and do not need field-configurable CA hierarchies.

Apple Secure Boot (Apple Silicon): chose a fully Apple-managed PKI with no field provisioning of the trust anchor — every Apple device trusts the Apple Root CA, and key ceremonies are entirely internal. This wins when vertical control of the entire hardware + software stack is possible and the threat model excludes the OEM/Enterprise customization use case; it enables the tightest possible supply-chain integrity at the cost of zero user/enterprise reconfigurability.

Back-of-Envelope Capacity Model

Derived from §4 System Constraints. Formula shown for each; no asserted-only numbers.

C1 — Payload hash time (SHA-256, SW, 1 GHz core). From §4: SHA-256 throughput ≥ 200 MB/s on 1 GHz. Payload = 4 MB. time = payload / throughput = 4 × 10^6 B / (200 × 10^6 B/s) = 20 ms. Budget from §4: ≤ 20 ms. Margin: 0 ms at floor — HW SHA must be used for larger payloads or tighter targets.

C2 — Ed25519 signature verify contribution. Ed25519 verify on a 1 GHz core ≈ 50–100 µs (standard benchmarks for Cortex-A; conservatively 0.1 ms). Four stages × 0.1 ms = 0.4 ms. Negligible vs §4 cumulative budget of 120 ms.

C3 — Total cumulative verify budget vs ceiling. From §4: ≤ 120 ms cumulative crypto. C1 (4×SHA, 4 stages, 4 MB each) = 4 × 20 ms = 80 ms. C2 (Ed25519 ×4) = 0.4 ms. X.509 path (3-cert × 4 stages, from §4: ≤ 2 ms each) = 4 × 2 ms = 8 ms. Sum = 88.4 ms. Margin: 120 − 88.4 = 31.6 ms headroom. At RSA-PSS-3072 (from §4: p95 ≤ 40 ms/stage), cumulative = 4 × 40 ms = 160 ms > 120 ms ceiling → RSA requires HW acceleration or smaller payloads per stage.

C4 — Arena working set for SPL stage. From §4: ≤ 16 KB scratch arena. Manifest (fixed header + TLV): ≤ 64 KB per §8.2 (parsing rules). At SPL stage only the header+body fit in arena; payload streamed. Arena breakdown: ManifestHeader = ~80 B; cert chain (3 certs × ≤ 2 KB/cert DER) = 6 KB; OCSP staple ≤ 2 KB; TLV overhead ≤ 1 KB. Total = ~9.1 KB < 16 KB budget. Margin: 6.9 KB.

C5 — dbx denylist SRAM bound. From §4: ≤ 256 MB RSS for sim host; device SRAM = 256 KB. dbx entry = 20 B (KeyId) or 48 B (SHA-384 hash). At 256 KB with 10 % reserved: 25 KB for dbx = 1,310 KeyId entries or 536 hash entries. At 100 revocations/year × 10 years = 1,000 entries — barely fits by KeyId; hash-prefix filter recommended beyond 500 entries.

C6 — Event log NV budget. From §8.8: 10 PCRs × 1 extend per boot. Event log entry = 80 B (pcr_index=4B, event_type=4B, digest_count=4B, 1×SHA-256 digest=32B, event_size=4B, event_data≈32B). 10 stages × 80 B = 800 B per boot. 1,000 boots before NV truncation = 800 KB NV log. Real NV is ≤ 64 KB on most SoCs → truncate after ~80 boots, mark truncation in log header. Design: rolling log with a 64 KB ring + a pointer.

C7 — OCSP responder fleet load. From §4: attestation verifier 99.9 % availability. Fleet = N devices; each checks in at boot (assume 1 boot/day). OCSP check = 1 req/device/boot. At N = 1 M devices, 1 req/device/day = ~11.6 req/s average; burst at scheduled maintenance window = 10× = 116 req/s. OCSP response = 1 Ed25519 sign + 0.1 ms = ≤ 10 k req/s per core (I/O-bound before CPU-bound). 1 core easily serves 116 req/s; fleet of 3 cores with LB provides ample redundancy.

C8 — CRL size for large fleet. CRL entry = serial (16 B) + revocation time (4 B) + reason (1 B) ≈ 21 B. At 10,000 revoked certs over fleet lifetime: 210 KB raw + DER overhead ≈ 300 KB. Shipping with every image update: 300 KB added to manifest TLV or a side file — acceptable. At 1 M revocations: 21 MB → delta-CRL required; base CRL issued quarterly, delta daily.

C9 — PCR extend latency per boot chain. From §4: ≤ 50 µs/extend. 10 stages = 10 extends × 50 µs = 500 µs = 0.5 ms. SHA-256 of (PCR‖measurement) = 64 B → at 200 MB/s SW = 0.32 µs per extend. Simulator: O(1) deterministic; negligible vs total boot time.

C10 — TCB code size budget. From §4: ≤ 64 KB .text target, hard cap 96 KB. Breakdown estimate: sbpki-codec ≈ 8 KB; sbpki-crypto (verify wrappers, no RustCrypto inline, only dispatch) ≈ 10 KB; sbpki-x509 path engine ≈ 12 KB; sbpki-revoke (dbx/CRL/OCSP) ≈ 8 KB; sbpki-verify orchestrator ≈ 4 KB; arena ≈ 0.5 KB; types/errors ≈ 2 KB. Subtotal (excluding crypto library code): ~44.5 KB. RustCrypto Ed25519-dalek verify stripped = ~8 KB; SHA-256 = ~4 KB. Total ≈ 56.5 KB < 64 KB target. RSA-PSS adds ~12 KB → combined multi-algo build = ~68 KB → feature-gate to stay under 96 KB cap.

C11 — Attestation verifier throughput. From §4: attestation verifier 99.9 % availability; p95 verify-quote ≤ 50 ms. Quote verify = AK cert chain validate (≤ 2 ms) + Ed25519 quote sig (≤ 0.1 ms) + log replay (10 extends × ≤ 1 µs each = 0.01 ms) ≈ 2.1 ms. At p95 = 50 ms budget, 95 % of headroom is network RTT + service overhead. Single stateless verifier process: ~500 req/s per core (network-bound). At 116 req/s fleet load (C7), 1 core sufficient; 3-instance fleet satisfies 99.9 % availability SLO.

C12 — Fuse bank exhaustion horizon. OTP fuses: PK-hash = 256 bits = 32 fuse-bytes (one-time write); min_svn_floor = 32 bits = 4 fuse-bytes. Total OTP consumed: 36 bytes. NV counter: write-many, model as erase-write flash: 100,000 write cycles minimum. At 1 SVN bump/quarter (security fix rate) = 4/year → NV counter exhaustion in 100,000 / 4 = 25,000 years. OTP exhaustion: never (only written once at provisioning).

Answer requires: Phase 5 (§5.2 OCSP responder EKU check), Phase 4 (§15.2 EKU semantics), §7 I14, §11.7 (RevocationSource), §16.5 conformance fixture (ocsp_badeku).

  20. A device with 256 KB SRAM is booting a 16 MB kernel. Answer requires: §4 (SRAM ≤ 256 KB, arena ≤ 16 KB), §8.3 (pipeline: stream payload → hash), §7 I2/I9, Phase 3 (§14.2 streaming hash, payload as Read), §11.5 (streaming Hasher trait).

Alternative Architectures (Roads Not Taken)

Alt-A — Online-Only Attestation-Gated Boot

OTP (PK-hash)  ─▶  ROM  ─▶  verify(SPL, sig)  ─▶  SPL  ─▶  ...
                                                        │
                                              Attestation verifier
                                              (remote, online)
                                              ─▶ release boot key
                                              (otherwise: halt)

Regime where it wins: Always-online server fleet (cloud instances, managed datacenter) where the network is available at every boot, revocation is sub-second (the verifier can see CRL/OCSP in real time), and the threat model accepts that a network partition = no boot (acceptable for a managed fleet with manual overrides). Real system that embodies it: Google's Shielded VMs with vTPM attestation — boot only completes after the Compute Engine infrastructure verifies the attestation quote and releases disk encryption keys. Why this blueprint rejected it: Boot-time network dependency fails for embedded/IoT devices (no network at first boot, or ever), introduces availability coupling (network partition = unbootable), and forces a service dependency into what must be an offline, deterministic, O(1) operation. The RTO guarantee (§4: ≤ 1 reboot) is unachievable if it requires an external service.

Alt-B — Static Hash of Public Keys (No X.509 Chain)

OTP: hash(leaf_PK)  ─▶  ROM  ─▶  verify(SPL, sig, leaf_PK)
                                  (no chain; leaf directly fused)

Regime where it wins: Ultra-minimal RoT with severe code-size constraints (< 4 KB TCB), single signing key per device model, no requirement for key rotation without re-fusing, and no multi-level PKI policy (no EKU, no pathLen, no name constraints). Correct for a simple IoT sensor with a 10-year key lifecycle and a single vendor. Real system that embodies it: RISC-V SiFive secure boot in some configurations, and many custom embedded bootloaders that simply store a raw Ed25519 public key in OTP and verify directly against it. Why this blueprint rejected it: No key rotation without burning a new fuse or re-provisioning devices in the field. No ability to issue intermediate signing keys for different product lines or signing teams. No revocation short of fuse-burning. This blueprint targets a fleet with key lifecycle management, intermediate HSMs, and the ability to cross-sign during rotation — which requires X.509 path validation.

Alt-C — TPM-Mandatory Measured-and-Enforced Boot (No Verifier in ROM)

ROM  ─▶  TPM extends measurements  ─▶  policy-sealed disk key
         (no sig check in ROM)          unseals only if PCRs match
                                         (TPM enforces, not ROM)

Regime where it wins: x86 server or workstation where a standard TPM 2.0 chip is present (mandated by Win11/Azure Assured Workloads), the ROM is not programmable by the OEM for verification logic, and disk encryption (BitLocker/dm-crypt with TPM sealing) is the enforcement mechanism — the disk simply won't decrypt if the boot chain deviated. Real system that embodies it: Linux Measured Boot with systemd-stub + TPM2 PCR-sealed LUKS keys; Microsoft BitLocker on Windows with TPM 2.0 policy sealing. Why this blueprint rejected it: Sealing + unsealing requires a TPM chip present and functional at every boot; our target is RoT-class silicon without a discrete TPM (the TPM behavior is simulated). More critically, seal/unseal enforcement only protects data confidentiality — it does not prevent booting a tampered OS that simply lacks access to the sealed secret. Verified-boot (signature check before jump) stops execution of unauthorized code; measured-boot + sealing only prevents secret release to it. We need both, and for bare-metal embedded targets the verifier-in-ROM is the primary gate.

Alt-D — Certificate Transparency / Append-Only Log Instead of dbx

Signing CA  ─▶  CT Log  ─▶  SCT (signed cert timestamp)
                                 embedded in manifest
Device  ─▶  verify SCT signature + log inclusion  ─▶  Accept/Reject
            (revocation = log entry; device checks the log)

Regime where it wins: Large-scale web PKI where CT logs provide an auditable, append-only record of all issued certificates and revocation is implicit via log monitoring and browser policy (e.g. CAA + CT required in browsers). The ecosystem trust model is "if it's in the CT log under a trusted CA, it's valid" rather than "only certs we explicitly allow." Real system that embodies it: HTTPS certificate ecosystem managed by browsers (Chrome/Firefox CT policy); Apple ATS requires CT SCTs. Why this blueprint rejected it: CT log inclusion proofs require network access to the log at boot time, or a pre-fetched inclusion proof embedded in the manifest (large; complex freshness semantics). CT does not provide revocation — it provides auditability; revocation in CT-land is still CRL/OCSP. For offline embedded boot, an append-only remote log is the wrong tool: the authoritative offline revocation primitive is the dbx denylist, which ships with the image and requires no network.

Glossary

Term Definition (implementation-relevant)
Root of Trust (RoT) The immutable code/data (boot ROM + fused PK-hash) that begins the trust chain; cannot be updated, so it is minimal.
Verified boot Each stage cryptographically verifies the next before transferring control; failure halts/falls back.
Measured boot Each stage records (PCR-extends) a measurement of the next; decision deferred to attestation/sealing.
TCB (Trusted Computing Base) The code whose correctness is required for security — here sbpki-verify + crypto; kept no_std, minimal, forbid(unsafe).
Manifest The compact signed metadata structure (§8.1) describing an image: digest, SVN, key id, chain ref, flags, signature.
Detached signature A signature stored separately from (not embedding) the signed bytes; here over signed_region.
SVN (Security Version Number) Monotonic integer in a manifest used for anti-rollback; must be ≥ device's effective minimum.
OTP / fuse One-time-programmable memory; write-once; holds PK-hash + SVN floor (immutable post-provision).
Monotonic NV counter Non-volatile counter that only increases (compare-and-set ≥); the effective rollback floor.
Anti-rollback Refusing to boot an image whose SVN < stored minimum, preventing downgrade to a patched vulnerability.
PCR (Platform Configuration Register) A TPM register updated only by extend (PCR=H(PCR‖m)); accumulates a tamper-evident measurement chain.
Extend The PCR update operation; order-sensitive, irreversible (extend-only).
Event log Append-only TCG-format record of every measurement; replays to reconstruct PCR values.
Quote A signed (by AK) snapshot of selected PCRs + a verifier nonce; the attestation evidence.
AK (Attestation Key) The key that signs quotes; its public part is certified by the PKI, linking device identity to attestation.
Remote attestation A verifier challenges a device, checks its quote + event log against expected PCR policy, and admits/denies.
Sealing / unsealing Encrypting a secret bound to a PCR policy; it unseals only when the platform is in the expected (measured) state.
X.509 The certificate format; chains leaf→intermediate→root carry public keys + constraints (RFC 5280).
Path validation The RFC 5280 sec. 6.1 algorithm verifying a cert chain: signatures, validity, constraints, EKU, name constraints, revocation.
basicConstraints / pathLen Extension marking a cert as a CA and limiting how many sub-CAs may follow.
keyUsage / EKU Allowed uses of a key; code-signing requires EKU id-kp-codeSigning (1.3.6.1.5.5.7.3.3).
Name constraints Limits on the subject/SAN names a CA may issue (permitted/excluded subtrees).
Trust anchor The root the chain must terminate at; on device, the fused PK-hash (immutable).
CRL (Certificate Revocation List) A signed list of revoked cert serials with validity window (thisUpdate/nextUpdate).
OCSP Online Certificate Status Protocol; per-cert revocation status over the network (RFC 6960).
OCSP stapling An OCSP response embedded in the manifest so revocation status is available offline.
dbx An explicit denylist of forbidden key ids / image hashes, shipped with images; the offline revocation kill-switch (UEFI-derived term).
PK / KEK / db / dbx UEFI Secure Boot key hierarchy (Platform Key / Key Exchange Key / allow db / deny dbx); studied reference (ADR-018).
Signing ceremony A controlled, witnessed, logged procedure for using an offline/HSM key.
HSM Hardware Security Module; stores private keys so they never leave the device (modeled via PKCS#11).
Cross-signing One CA signing another's certificate so chains validate under multiple roots during migration.
Dual-signing Attaching two signatures (old + new key) to a manifest during a rotation overlap.
A/B (slots) Two image banks; updates write the inactive one, enabling safe rollback by booting the other.
Mark-good Committing a booted slot as successful (resets tries, bumps SVN) only after a watchdog-confirmed boot.
Watchdog (WDT) A timer the booted image must kick; expiry triggers fallback, preventing boot-loop bricks.
Brick / anti-bricking A permanently-unbootable device; prevented by A/B + recovery + watchdog (some signed image always boots).
Recovery image A separately-signed, lower-SVN-floor image booted when both A/B slots fail.
Fail-closed Any error → reject/deny; never warn-and-continue (Principle 1).
Constant-time Execution time independent of secret/attacker-controlled data, defeating timing oracles.
TOCTOU Time-of-check-to-time-of-use race; here, swapping image bytes between verify and execute.
Canonical DER The unique minimal ASN.1 encoding; accepting only it prevents parser-differential bypasses.
Fault injection / glitching Physically perturbing voltage/clock to skip a check; mitigated by redundancy/fail-closed (physical part out of scope).
Arena allocator A bump allocator over a caller buffer; zero-heap, deterministic, stage-scoped (no free).
Verdict The verifier's sole output: Accept or Reject(reason); the only value loaders branch on.
COSE_Sign1 CBOR Object Signing & Encryption single-signer structure; the quote envelope shape (ADR-022).
