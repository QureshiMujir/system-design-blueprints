⬜ Phase 1 — Core Types, Arena, and Manifest Codec §12

Objectives

Establish sbpki-types + sbpki-codec + the Arena. Lock the manifest binary layout (§8.1) and canonical-DER reader (§11.4). No crypto yet; parsing + round-trip only. Constraint introduced: zero-heap, zero-copy, no_std.

Deliverable

A library that parses/round-trips manifests and reads canonical DER, no_std, zero-heap. manifest-inspect tool decodes a .sbpk file showing every field offset + the signed region span.

Acceptance
  • Round-trip identity on all positive manifest vectors (write(parse(x)) == x), byte-exact.
  • 100 % of malformed vectors → correct VerifyError variant (no panics, no UB).
  • Arena high-water ≤ 16 KB on largest vector. Builds clean for all three -none targets.
  • #![forbid(unsafe_code)] holds; cargo-geiger = 0 unsafe in these crates.

File Purpose Expected
manifests/valid_ed25519_min.sbpk minimal valid header parse Ok, round-trip eq
manifests/valid_all_tlvs.sbpk every optional TLV present parse Ok
manifests/bad_magic.sbpk wrong magic Malformed(Magic)
manifests/trailing_bytes.sbpk bytes after sig Malformed(Trailing)
manifests/tlv_len_overflow.sbpk TLV len > buffer Malformed(Length)
manifests/dup_critical_tlv.sbpk duplicate critical TLV Malformed(DupCritical)
certs/der_noncanon_len.der non-minimal length NonCanonical
Pitfalls
  • Integer overflow in length math (offset + len): use checked arithmetic; manifestation = OOB read; detect via fuzz + debug_assert; recovery = Reject.
  • Signed-region drift: recomputing/normalizing bytes before hashing breaks I2/I8; root cause = re-serializing instead of subslicing; debug via byte-diff of signed_region vs source.
  • Alignment in arena: misaligned borrow of multi-byte fields; on strict-align targets (some aarch64 configs) = fault; align-up in alloc.
  • TLV critical-bit confusion: treating unknown-critical as skippable = silent acceptance of attacker TLV; enforce Reject.

⬜ Phase 2 — Cryptographic Verification Primitives §13

Objectives

sbpki-crypto: constant-time signature verification for Ed25519 / ECDSA-P256 / RSA-PSS-3072, SHA-256/384 hashing, and injected Clock/Rng traits. Verify-only (no signing in TCB). Constraint: constant-time, no heap, no CRT.

Deliverable

A crypto crate passing RFC test vectors + Wycheproof edge vectors for all three schemes, no_std, constant-time digest compare. Streaming SHA over arbitrary readers.

Acceptance
  • 100 % pass on RFC 8032 (Ed25519), FIPS 186-5/Wycheproof (ECDSA-P256), RFC 8017/Wycheproof (RSA-PSS) verify vectors, incl. all negative cases.
  • High-S ECDSA, non-canonical R/S, wrong-salt PSS, all-zero sig → false/reject.
  • ct-audit shows no message-dependent timing on the compare path (t-stat below threshold).
  • Verify latency within §4 budgets on the bench host (scaled note for 1 GHz target).
Fixtures
File Purpose Expected
wycheproof/ed25519.json EdDSA edge vectors match expected pass/fail
wycheproof/ecdsa_p256_sha256.json ECDSA incl. malleability reject high-S/non-canonical
wycheproof/rsa_pss_3072_sha256.json PSS edge reject bad salt/MGF
crypto/sha256_nist.json,sha384_nist.json hash KATs exact digests
crypto/forged_sig_flip.bin single-bit-flipped valid sig reject
Pitfalls
  • ECDSA malleability (s and n−s both valid): accept-both breaks determinism + can confuse dedup/replay; enforce low-S.
  • PSS parameter confusion (salt len / MGF hash mismatch): silent accept of malformed; pin salt=hash-len, MGF1=hash.
  • Non-constant-time compare of digest/key-id: timing oracle; route every compare through ct_eq.
  • Using a signing-capable RSA path: brings CRT + timing risk into TCB; import verify-only, no private-key code in no_std crate (P7).
  • Reading payload into RAM to hash: blows SRAM budget; stream it.

⬜ Phase 3 — Manifest Verifier (Integrity + Signature, pre-PKI) §14

Objectives

sbpki-verify::pipeline wiring codec + crypto into a single-cert verifier: parse manifest → stream-hash payload → compare digest (CT) → verify signature against a directly trusted key (the fused PK, before full chains). Establishes the verify_stage skeleton + Verdict flow. Constraint: pure, no heap, deterministic (I10).

Deliverable

verify_stage that, given a manifest signed directly by the anchor key + the payload, returns Accept/Reject(reason). examples/sign_and_boot.rs (partial) signs an image with the anchor key and verifies it.

Acceptance
  • Valid (anchor-signed) image → Accept; any tamper (1-bit in payload, header, or sig) → correct Reject.
  • Digest + signature compares are constant-time (inherited from Phase 2).
  • Deterministic: 1000× repeat → identical verdict + identical arena high-water.
  • Zero heap; ≤ 16 KB arena; per-call latency within §4 verify budget for 4 MB image.

File Purpose Expected

Pitfalls
  • Hashing the wrong region (including trailer): breaks signature semantics; hash exactly signed_region.
  • Early-return ordering leaks: returning before fully consuming payload can mask a length mismatch; consume + verify length last.
  • Stub revocation defaulting to Good: fine in Phase 3 but MUST flip to fail-closed in Phase 5 — leave a #[cfg]/TODO-gate tracked in BUILD_PLAN.
  • Reusing arena across calls without reset: stale bytes → nondeterminism; assert top==0 at entry.

⬜ Phase 4 — X.509 Path Validation Engine (RFC 5280) §15

Objectives

sbpki-x509: full leaf→root path validation against a fused trust anchor — signature chaining, validity windows, basicConstraints/pathLen, keyUsage/EKU(code-signing), name constraints. Replace Phase 3's direct-key path with chain resolution. Constraint: canonical-DER only, pure, ≤ 2 ms / 3-cert chain.

Deliverable

A path-validation engine that accepts valid 2–4 cert code-signing chains rooted at the anchor and rejects every RFC 5280 violation class with a specific reason. chain-lint tool validates a chain against profiles offline.

Acceptance
  • 100 % correct on a matrix of valid + each violation class (expired, not-yet-valid, bad-EKU, missing-keyUsage, CA-as-leaf, pathLen-exceeded, name-constraint-excluded, wrong-issuer, broken-sig, wrong-anchor).
  • Differential agreement with OpenSSL/webpki on a shared corpus (modulo code-signing-EKU policy differences, documented).
  • ≤ 2 ms per 3-cert chain on bench host; zero heap (arena).
  • Canonical-DER enforced: non-canonical cert → NonCanonical, not silent accept.

Pitfalls
  • Path building vs validation conflation: we only validate a presented chain (no AIA fetching on device); building belongs to tooling. Mixing them on device adds network + complexity = attack surface.
  • EKU intersection bug: forgetting that an empty/absent EKU on a CA means "unconstrained" vs leaf-must-have-codeSigning; encode the asymmetry explicitly.
  • Name-constraint IP/DNS encoding: wrong subtree-matching (suffix vs prefix) → over/under-restriction; test both.
  • Trusting AKI/SKI to chain instead of name+signature: AKI/SKI are hints, not authorization; chain by issuer-name + signature verification.
  • pathLen off-by-one: pathLenConstraint=0 means it may sign leaves but no further CA; decrement carefully.

⬜ Phase 5 — Revocation: dbx, CRL, OCSP, Stapling §16

Objectives

sbpki-revoke: authoritative offline dbx (hash/key denylist) + CRL + online/stapled OCSP, integrated into path validation with a fail-closed policy. Flip Phase 3's revocation stub to real. Constraint: offline path must work (dbx), online is best-effort with strict-default policy (Principle 13).

Deliverable

A revocation subsystem that blocks revoked keys/serials/hashes via dbx offline, via CRL/OCSP when present, and refuses-on-unknown under strict policy. cmd_crl/cmd_ocsp (Phase 11) interop with it.

Acceptance
  • Revoked-via-dbx → Revoked with no network. Revoked-via-CRL/OCSP → Revoked. Good → pass. Unknown+strict → RevocationUnknown reject; Unknown+lenient(recovery)+dbx-clean → pass.
  • OCSP response with wrong responder EKU / bad sig / stale / nonce-mismatch → reject.
  • Stale CRL (nextUpdate passed) handled per policy (strict reject).
  • No silent skip on OCSP timeout (falls to stapled/CRL/dbx, never to "Good").

Pitfalls
  • OCSP-skip-on-error = soft-fail: the classic bypass; never default Unknown→Good for kernel (strict). Make policy explicit + tested.
  • Unsigned/under-verified CRL/OCSP: must verify the responder/issuer chain + EKU, else attacker forges "Good."
  • Freshness windows: clock skew vs nextUpdate; define tolerance; without a trusted clock early in boot, prefer dbx (monotone) over time-based CRL.
  • dbx growth: large denylist blows SRAM; bound size, use sorted + binary search; spill policy to a hash-prefix filter.
  • Nonce omission: OCSP without nonce is replayable; require nonce online; stapled relies on freshness window.

⬜ Phase 6 — Anti-Rollback: OTP, Monotonic NV, SVN Enforcement §17

Objectives

sbpki-nv: model OTP fuses (PK-hash, min-SVN floor, write-once) and a monotonic NV counter; enforce svn ≥ effective_min in verify_stage; commit SVN only post-mark-good (I3/I4/I12). Constraint: power-loss-atomic, software cannot decrement (I4, I8 monotone).

Deliverable

An NV/OTP model + SVN enforcement that rejects downgrade-to-vulnerable images, with power-loss-atomic counter commits and write-once OTP. examples/rollback_demo.rs shows a downgrade rejected.

Acceptance
  • svn < effective_min → Rollback; svn ≥ effective_min → pass (subject to other checks).
  • commit_ge rejects any decrement (Regress); accepts equal/greater.
  • OTP second write fails; PK-hash/floor immutable post-lock.
  • Power-loss injection between shadow + flip: post-recovery counter is exactly old or exactly new (never torn), verified across 10k injected faults.
Fixtures
File Purpose Expected
rollback/svn_below_min.sbpk svn=3, min=5 Rollback{3,5}
rollback/svn_equal_min.sbpk svn=5, min=5 pass
rollback/svn_above_min.sbpk svn=7, min=5 pass, commit→7 on mark-good
rollback/counter_regress.json commit_ge(lower) Regress
rollback/otp_double_write.json write OTP twice AlreadyWritten

Pitfalls
  • Committing SVN at verify time (not after boot success): bricks on a bad-but-signed image whose SVN was already burned; commit only post-mark-good (I12).
  • Non-atomic counter write: torn write → ambiguous min → either bypass (lower) or brick (higher); use shadow+flip.
  • floor vs counter confusion: forgetting max(floor,counter) lets a factory-floor downgrade slip; always combine.
  • u32 wrap: SVN near u32::MAX; saturate, never wrap.
  • Burning min-SVN too eagerly on every boot: exhausts rollback range / fuse writes; advance only when shipping a security fix.

⬜ Phase 7 — Measured Boot: PCR Bank, Extend, Event Log §18

Objectives

sbpki-tpm: TPM-2.0-subset PCR bank with extend-only semantics, append-only TCG-style event log, and integration so each stage measures itself + config + trust state before transfer (I5, §8.8). Constraint: deterministic, replayable, extend-only (never reset).

Deliverable

A PCR engine + event log where extending a known sequence yields known PCR values, and the log replays to the same values. cmd_tpmsim extends/reads PCRs; eventlog-replay verifies.

Acceptance
  • Known extend sequence → known PCR digests (golden vectors, both SHA-256 and SHA-384 banks).
  • Event-log replay recomputes PCRs bit-exactly (I10).
  • Extend is order-sensitive (swapping two measurements changes the PCR) — proven by vector.
  • Reject paths still emit a measurement event (completeness, I5).
Fixtures
File Purpose Expected
tpm/extend_seq_sha256.json ordered measurements golden PCR set
tpm/extend_seq_sha384.json SHA-384 bank golden PCR set
tpm/eventlog_replay.json log → PCRs replay == reported
tpm/order_sensitivity.json swapped order different PCR (detect)
tpm/reject_still_measures.json rejected stage event present
Pitfalls
  • Resetting a PCR: extend-only is the security property; any reset path = forge measurements; do not implement reset (except modeled hardware reset at power-on).
  • Measuring after transfer: measure the exact bytes loaded, before jump (TOCTOU with I2); same buffer as verify.
  • Log/PCR divergence: if an extend isn't logged (or vice-versa), replay breaks attestation; make extend+log atomic.
  • Banks confusion: mixing SHA-256 and SHA-384 banks; keep per-bank PCRs separate; quote selects bank.
  • event_data unbounded: cap size; large event blobs blow NV log budget.

⬜ Phase 8 — Remote Attestation: Quote, Verify, Seal/Unseal §19

Objectives

sbpki-tpm::quote/seal + an attestation verifier (sbpki-cli cmd_attest): produce a quote (signed PCR snapshot + nonce) by an Attestation Key (AK), verify it remotely against expected PCR policy + event log, and seal/unseal secrets to a PCR policy (I15). Constraint: freshness-bound (nonce), unforgeable (AK sig), deterministic verify.

Deliverable

An attestation round-trip: device quotes its boot state, a remote verifier admits/denies based on policy, and a sealed secret unseals only in the expected boot state. examples/attest_demo.rs demonstrates Admit + secret release; tampering flips to Deny + seal-fail.

Acceptance
  • Valid quote (correct AK, fresh nonce, expected PCRs) → Admit; wrong PCR / stale nonce / forged AK sig → Deny with reason.
  • Event-log replay must equal quoted PCRs or Deny (consistency, I15).
  • Sealed secret unseals only when PCRs match policy; any measurement change → SealErr::PolicyUnmet.
  • Nonce replay (reuse old quote) → Deny (freshness).

Pitfalls
  • Missing nonce / replay: quote without verifier-chosen nonce is replayable; always challenge-response.
  • Not verifying the AK chain: an unauthenticated AK = anyone attests anything; validate AK cert to anchor.
  • TOCTOU between quote and use: PCRs can change after quote; bind decisions to the quoted state + short validity.
  • Sealing to PCRs you don't control: sealing to a PCR that legitimately changes (e.g. cmdline) bricks unseal across benign updates; pick stable PCRs + a migration story (re-seal on update).
  • Comparing PCRs non-constant-time / partial: compare full selected set; mismatch on any → Deny.

⬜ Phase 9 — A/B Slots, Recovery, and Anti-Bricking §20

Objectives

sbpki-ab: dual-bank A/B image selection, boot-attempt counting, watchdog-gated mark-good, fallback to the other slot, then to a signed recovery image, with a brick-guard terminal state (I11/I12, §8.7). Constraint: some signed image always boots; every commit power-loss-atomic.

Deliverable

An A/B + recovery state machine that survives a corrupt/failed slot by falling back, boots recovery when both slots fail, and never bricks (always reaches a bootable signed image or a diagnosable BrickGuard). examples/ab_recovery_demo.rs corrupts slot A and shows fallback → B → recovery.

Acceptance
  • Corrupt slot A (bad sig) → tries[A]=0 → boots B.
  • B boots but crashes pre-kick (WDT timeout) → tries[B]-- → retry/other slot/recovery.
  • Both slots fail → recovery image boots.
  • Power-loss during slot-metadata commit (10k injected) → state always consistent (no torn metadata, no double-brick).
  • mark-good is the only path that bumps SVN; verified by audit.
Fixtures
File Purpose Expected
ab/corrupt_slot_a.json bad sig in A fallback to B
ab/crash_before_kick.json WDT timeout on B tries-- then retry
ab/both_fail_recovery.json A & B exhausted recovery boots
ab/recovery_fail_brickguard.json recovery also bad BrickGuard (diagnosable halt)
ab/powerloss_slot_commit.json fault mid-commit consistent metadata
ab/markgood_commits_svn.json successful boot SVN committed once
Pitfalls
  • Committing SVN before mark-good: a slot that verifies but fails to run bumps min-SVN → can brick the other good-but-lower slot; commit only post-kick (I12).
  • Watchdog too short: legitimate slow boot trips WDT → false fallback loop; size window to worst-case boot + margin.
  • Recovery sharing the rollback floor: a min-SVN bump that excludes recovery = unrecoverable; recovery uses a separate floor (§17.8).
  • Non-atomic slot flip: torn "active slot" pointer → boots neither/both; shadow+flip.
  • Tries underflow: decrement below zero; saturate at 0 = "exhausted."

⬜ Phase 10 — Full-Chain Simulator (ROM → init) §21

Objectives

sbpki-sim: wire crates 1–9 into a deterministic, replayable boot harness modeling RoT/ROM/SPL/2nd-stage/kernel/init, OTP/NV, PCRs, A/B — the runnable substrate proving the whole chain end-to-end. Constraint: deterministic given a seed + scenario; fault-injectable.

Deliverable

cmd_sim run scenario.toml boots the full chain in the simulator and prints the verdict per stage, the PCR bank, the event log, and the A/B state. Replays bit-exactly.

Acceptance
  • Happy-path scenario boots ROM→init with all Accepts + expected PCRs + committed SVN.
  • Each negative scenario (tamper at any stage, rollback, revoked, corrupt slot) halts at the right stage with the right reason + falls back correctly.
  • Replay of any scenario reproduces the transcript byte-for-byte across runs/machines.
  • TOCTOU/glitch scenarios are detected (redundant check) or contained (fail-closed).
Fixtures
File Purpose Expected
sim/happy_full_chain.toml clean boot all Accept, golden PCRs
sim/tamper_kernel.toml bad kernel sig halt at kernel stage
sim/rollback_bootloader.toml low-SVN bootloader Rollback halt
sim/revoked_leaf.toml dbx-revoked signer Revoked halt

Pitfalls
  • Hidden nondeterminism (HashMap iteration, ambient time/RNG, thread scheduling): breaks replay; use ordered maps, injected Clock/Rng, single-threaded boot.
  • Sim diverging from intended hardware semantics: e.g., modeling OTP as writable; keep the model honest to the §8.6/§8.7 contracts.
  • Skipping the re-check that defends against glitches: a single verify branch is glitchable; model + require redundancy where the threat model demands.
  • Memory-region aliasing letting verify + execute see different bytes: enforce the same buffer (I2).

⬜ Phase 11 — PKI: CA Hierarchy, Ceremonies, Revocation Issuance §22

Objectives

sbpki-ca + sbpki-cli: build the offline-root → HSM-intermediate → leaf signing hierarchy, run signing ceremonies, sign manifests, issue CRLs + run an OCSP responder, and support rotation / cross-signing / dual-signing for migration. Constraint: device holds no signing key (Principle 14); root offline; intermediates HSM-resident (modeled via PKCS#11).

Deliverable

A complete PKI toolkit: mint a 3-tier hierarchy, sign images, issue/publish CRLs, serve OCSP, and execute a key rotation with dual-signing — all verifiable by sbpki-verify. examples/sign_and_boot.rs runs end-to-end against this CA.

Acceptance
  • Certs minted by sbpki-ca validate under sbpki-x509 (profiles ↔ validator lockstep) and reject when profiles are violated.
  • A manifest signed via PKCS#11 leaf verifies in the sim chain (Phase 10).
  • CRL/OCSP issued here are correctly honored by Phase 5 (revoked serial blocked).
  • Key rotation with dual-signing: old and new manifests both verify during overlap; after retiring old key (dbx the old leaf), only new verifies.
  • Ceremony produces a tamper-evident, hashed transcript.

File Purpose Expected

Pitfalls
  • Root online / key on disk: defeats the offline-root model; enforce PKCS#11 + air-gap ceremony for root.
  • Profile/validator drift: CA mints certs the verifier rejects (or vice-versa) → fleet-wide boot failures; single source of truth for profiles + CI cross-check.
  • Rotation without overlap: retiring old key before new propagates bricks devices that only trust old chains; dual-sign + cross-sign overlap window.
  • Reusing one key for sign + OCSP: separate responder key with OCSPSigning EKU; reuse weakens custody + EKU semantics.
  • Unbounded leaf lifetime: long-lived leaves widen compromise blast radius; short-lived + frequent rotation.

⬜ Phase 12 — Conformance, Fuzzing, Performance, Hardening §23

Objectives

sbpki-conformance + sbpki-fuzz + benchmarks + hardening pass: prove correctness against the full vector corpus (incl. Wycheproof + malformed + negative), fuzz all parsers to the §4 budget, meet performance budgets, and complete the security-hardening checklist before lock. Constraint: ≥ 99.5 % positive / 100 % negative vector pass; ≥ 1000 CPU-h fuzz clean.

Deliverable

A green conformance run, a clean fuzz campaign, benchmark numbers within budget, and a signed hardening report — the project's "specification — locked" evidence package. CI enforces all of it on every PR.

Acceptance
  • ≥ 99.5 % positive vectors Accept-as-expected; 100 % negative vectors Reject-with-correct-reason.
  • ≥ 1000 CPU-h fuzz across targets, 0 crashes / 0 UB / 0 untyped errors.
  • All §4 latency + memory + code-size budgets met on bench host + cross-targets (size).
  • Differential parity with reference impls (documented intentional divergences only).
  • cargo-geiger 0 unsafe outside the reviewed shim; cargo-deny/vet clean; reproducible build bit-identical.

Pitfalls
  • Fuzzers finding only shallow bugs: without structure-awareness they stall at the magic check; seed corpora + arbitrary for deep coverage.
  • Differential false-positives: reference impls differ on code-signing-EKU / policy; pre-classify intentional divergences so CI isn't noisy.
  • Benchmark noise: host jitter masks regressions; pin CPU, disable turbo, many iterations, compare distributions not means.
  • Coverage gaps in negative space: a missing reject vector = an untested bypass; enumerate every VerifyError variant ↔ ≥1 vector.
  • Reproducibility drift: timestamps/paths embedded in artifacts; strip + pin (SOURCE_DATE_EPOCH).
