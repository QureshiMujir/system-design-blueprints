Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If the OCSP responder is unavailable and no stapled response is in the manifest, but the dbx is clean, what verdict does verify_stage return for a kernel image, and for a recovery image? Why are they different? Answer requires: §5.2 (policy resolution order), Phase 5 (§5.2 per-image-id strictness), §8.9 (happy/failure path examples), §6 P1 (fail-closed), §6 P13 (offline revocation).
  2. An attacker has obtained a valid signed manifest with SVN=7 from a compromised build system, but the device currently has min_svn=5. What must the attacker also control to successfully boot this image on a device that has already booted SVN=7 once (mark-good has fired)? Answer requires: §8.6 (effective_min), Phase 6 (§17.2 commit_ge semantics), §7 I3/I4, §6 P8 (monotone hardware anchor), Phase 9 (§20.2 mark-good).
  3. A device boots, extends PCR8 with the correct kernel digest, then is rebooted by an attacker with a patched kernel that has the same digest (collision scenario). What is the attestation verifier's response, and what is the actual security boundary here? Answer requires: Threat Model (T1, T3), Phase 7 (§18.2 extend semantics), Phase 8 (§8.2 attestation), §6 P3 (no cryptographic collision of SHA-256 breaks the system), §8.8 (PCR8 role).
  4. Key rotation: the leaf signing key is compromised 48 hours after a fleet-wide image push. What is the sequence of operations to stop further compromise, and what is the blast radius for devices that have already booted the compromised-key-signed image? Answer requires: Phase 11 (§11.2 rotation), Phase 5 (§5.2 dbx publish), Operational Readiness (revocation runbook), §4 (revocation SLA: dbx ≤ 24h), Threat Model T5.
  5. Why does the verifier check revocation (dbx/CRL/OCSP) before signature verification, and what is the security consequence of reversing the order? Answer requires: §8.3 (pipeline ordering), §6 P1 (fail-closed), §11.7 (resolution order), §5.2 revoke (dbx authoritative), Phase 5 (§5.2 first-consulted). Answer: reversing order means a revoked key's signature is cryptographically valid — it passes sig verify — and only then is checked against dbx, but by then the verifier has done signature work that could leak timing information about the key.
  6. What prevents a malicious intermediate CA (whose private key is stolen) from issuing a new leaf cert that passes verify_stage's path validation, if the intermediate's cert serial is on the CRL but the dbx does not contain the intermediate's key-id? Answer requires: Phase 4 (§15.2 path validation), Phase 5 (§5.2 CRL per-cert), §11.7 (CRL called per cert in chain), §6 P1 (strict Unknown→Reject), §15.10 (revocation policy per cert).
  7. A power-loss occurs between the NV counter shadow-write and the atomic flip. After the device reboots, what is the effective min_svn, and how does the verifier respond to an image with SVN=6 when the counter was being advanced from 5 to 6? Answer requires: Phase 6 (§17.2 atomic_commit shadow+flip), §8.6 (effective_min formula), §7 I4 (monotone invariant), §11.8 (NvCounter semantics), §6 P12 (anti-brick).
  8. The attestation verifier's golden PCR policy is version N. A device has booted with version N+1 kernel (new PCR8 value). The attestation verifier still has version N policy. What happens, and what is the operational procedure to unblock the device? Answer requires: Phase 8 (§19.10 golden-PCR update), Operational Readiness (golden-PCR versioning runbook), Compatibility Guarantees (rolling-upgrade guarantees), Phase 7 (§18.10 PCR contract with attestation verifier).
  9. Why must signed_region be a zero-copy subslice of the input buffer rather than a re-serialized copy, and what is the exact bypass scenario if it is re-serialized? Answer requires: §8.1 manifest layout (signed_region definition), §7 I2/I8, §6 P6 (canonical-only), Phase 1 (§1.6 pitfalls signed-region drift), Phase 3 (§14.2 enforce I2), Threat Model T11.
  10. An A/B update pushed to slot B passes signature verification and begins booting but hangs before kicking the watchdog. After the WDT expires and the device reboots, what are the exact state variables changed, and what is the earliest point the SVN could be committed? Answer requires: §8.7 A/B state machine, Phase 9 (§20.2 watchdog/mark-good), §7 I12, Phase 6 (§17.2 commit only post-mark-good), §4 (WDT ≤ 30 s, RTO ≤ 1 reboot).
  11. If the DER parser accepts indefinite-length encoding (BER) and a signing tool encodes the cert chain in definite-length DER, can an attacker craft an indefinite-length re-encoding of the same chain that produces a different byte sequence for the signed_region hash? Answer requires: §7 I8 (canonical-only invariant), §8.2 (parsing rules normative), Phase 1 (§1.2 DerReader), Phase 4 (§15.2 NonCanonical), §6 P6 (canonical-only), Threat Model T11.
  12. What is the minimum information an offline device (never connected, dbx from 6 months ago) can use to detect that a boot image's signing key has been compromised, and why is this design choice a fundamental tradeoff? Answer requires: §6 P13 (dbx offline kill-switch), Phase 5 (§5.2 dbx ships with image), Threat Model T6 (stale revocation), Scalability Analysis (revocation propagation), §4 (revocation SLA ≤ 24h to dbx).
  13. A pathLen=0 intermediate CA is used to issue a sub-CA. What exact check in verify_stage catches this, and what is the error code emitted? Answer requires: Phase 4 (§15.2 constraints pathLen check), §8.5 (path state machine pathLen decrement), §7 I14, §11.6 (PathState.max_path_len), §11.2 (VerifyError.PathInvalid(PathLen)).
  14. Why does the recovery image need a separate, lower SVN floor instead of sharing the primary floor, and what specific boot sequence demonstrates the brick scenario if they share a floor? Answer requires: Phase 6 (§17.8 recovery-floor separation), Phase 9 (§20.2 recovery slot), §8.7 (A/B state machine RECOVERY state), §7 I11 (anti-brick), §6 P12.
  15. An attestation verifier receives a quote where the event log replays to PCR values that differ from the quoted PCRs by exactly one extend event. What does this imply about the device's boot, and what should the verifier do? Answer requires: Phase 8 (§8.2 log-replay consistency check), §8.5 attestation conformance fixture (quote_log_mismatch), §7 I15, Phase 7 (§18.2 extend+log atomic), Threat Model T10.
  16. How does the DUAL_SIG TLV enable key rotation without requiring device re-fusing, and what verifier logic change (if any) is needed to accept it? Answer requires: §8.1 manifest layout (DUAL_SIG flag), §8.2 EBNF (tlv_tag DUAL_SIG), Phase 11 (§11.2 rotation dual-sign), Compatibility Guarantees (rolling-upgrade), ADR-010 TLV extension semantics.
  17. The TCB has #![forbid(unsafe_code)] but a reviewed FFI shim in sbpki-crypto uses unsafe for a hardware SHA accelerator. What is the minimal soundness argument that the overall system remains memory-safe, and how does cargo-geiger enforce the boundary? Answer requires: §1.7 language rationale (unsafe policy), ADR-003, Phase 2 (§13.2 FFI shim), Phase 12 (§23.2 cargo-geiger), §6 P4 (minimal TCB).
  18. If two concurrent DMA engines are transferring to the same region being verified, what invariant is violated and at what point in the pipeline does it become exploitable? Answer requires: §7 I2 (TOCTOU), §8.3 pipeline (lock/quiesce DMA step), Threat Model T3, Phase 10 (§21.2 TOCTOU inject), §6 P2 (verify before execute).
  19. The OCSP responder's delegated responder cert has EKU containing only id-kp-OCSPSigning. A client presents an OCSP response signed by a cert with id-kp-OCSPSigning AND id-kp-codeSigning. Should the verifier accept or reject this response, and why? Answer requires: Phase 5 (§5.2 OCSP responder EKU check), Phase 4 (§15.2 EKU semantics), §7 I14, §11.7 (RevocationSource), §16.5 conformance fixture (ocsp_badeku).
  20. A device with 256 KB SRAM is booting a 16 MB kernel. Walk the exact memory path from flash to the verify/hash operation — which bytes are in SRAM at any given moment, and what invariant prevents a TOCTOU exploit at each step? Answer requires: §4 (SRAM ≤ 256 KB, arena ≤ 16 KB), §8.3 (pipeline: stream payload → hash), §7 I2/I9, Phase 3 (§14.2 streaming hash, payload as Read), §11.5 (streaming Hasher trait).

Mental Models & First Principles

MM1 — The Fused Hash is the Entire Trust. Expert insight: the OTP PK-hash is not a key; it is the root of all trust. Everything downstream — signatures, chains, revocation, attestation — is only as strong as the immutability of that 32-byte value. What it predicts: any mutable "root" (writable register, EEPROM not locked, a signed-config-selects-root scheme) is attackable without breaking cryptography. Bug class without it: "configurable root of trust" that accepts any root whose signature verifies — evil-maid swaps the root pointer. Applied in: §7 I6, §6 P7, Phase 6 (§17.2 OTP lock), §11.8.

MM2 — Verify-Before-Execute is a Total Order. Expert insight: the invariant "verify(N+1) = Accept" must complete before the CPU's program counter can reach stage N+1's entry point. It is not "verify and then execute later" or "execute with a guard." What it predicts: any async/deferred verification path has a TOCTOU window exploitable by DMA or flash DMA attacks. Bug class without it: transfer-of-control to unverified code even when verify returns Accept, if the jump site is checked separately from the verified buffer. Applied in: §7 I1/I2, §8.3 pipeline, Phase 3 (§14.2), §3 architectural overview.

MM3 — Constant-Time is a Specification Constraint, Not an Implementation Detail. Expert insight: any comparison or branch on a secret-derived value creates a timing oracle; the entire function must be data-oblivious — not just the final compare. What it predicts: a "constant-time signature verify" that has a branch on the number of leading zero bytes in the public key still leaks. Bug class without it: partial timing oracle that reduces verification to a search with ≈ 256 × n queries instead of 2^256. Applied in: §6 P3, Phase 2 (§13.2 ct module, ct-audit), §11.5, §6 Pitfalls P8/Kocher.

MM4 — Revocation is a Distributed Systems Problem, Not a Crypto Problem. Expert insight: once a key is revoked, the challenge is not "can we mark it revoked?" (trivial) but "does every device know it is revoked before it boots again?" (a replication/freshness problem). What it predicts: an offline device will boot a revoked-key-signed image for exactly the duration of its disconnection plus the revocation propagation latency. Bug class without it: treating revocation as synchronous — an online OCSP-only scheme silently passes on network failure. Applied in: §5.2 revoke policy, Phase 5 (§5.2 dbx-first design), §6 P13, Scalability Analysis.

MM5 — Anti-Rollback is a Hardware Contract, Not a Software Policy. Expert insight: if the minimum SVN is stored in software-writable memory, rollback protection is only as strong as the software that enforces it — which the attacker controls. The monotonic guarantee must come from a medium the verifier itself cannot decrement. What it predicts: a "monotonic counter" in a writable flash page or a software variable is trivially bypassed by reflashing. Bug class without it: SVN enforcement in software with a writable counter → attacker resets counter to 0, boots any signed image. Applied in: §7 I3/I4, Phase 6 (§17.2 OTP/NV model), §8.6, §6 P8.

MM6 — Measured Boot Records; Verified Boot Enforces. Expert insight: a PCR extend is not an access control — it records what ran, it does not prevent anything from running. The enforcement comes from attestation (refusing to release a secret) or sealing (the secret physically won't unseal in the wrong state). Conflating measurement with enforcement produces a "measured boot" that still boots attacker code, just with a different PCR. Bug class without it: removing verified-boot (signature check) and keeping measured-boot, then concluding the platform is "still attested" — it is, but it attests the attacker's code. Applied in: §3 (verified vs measured distinction), Phase 7 (§18.2), Phase 8 (§8.2), §6 P9.

MM7 — Parser Differentials are Signature Bypasses. Expert insight: if two implementations parse the same byte sequence differently — e.g., one accepts BER indefinite-length, the other expects DER — the signer signs using one parser's view and the verifier accepts using another's, potentially verifying a modified body. The canonical-only rule is not pedantry; it is the closure of a bypass class. Bug class without it: malformed DER where a re-encoding (e.g., non-minimal length) causes the verifier to hash a different signed_region than the signer did. Applied in: §7 I8, §6 P6/P8, §8.2 parsing rules, Phase 1 (§1.2 canonical check), Phase 12 (§23.2 differential).

MM8 — The Arena Allocator is a Security Boundary. Expert insight: in a TCB with 256 KB SRAM and no MMU, a heap allocation failure during verification must yield a typed Reject, not a crash, a partial-state accept, or an "out of memory, skipping cert chain check." The arena is not just a performance optimization; it is the mechanism that makes "OOM = fail-closed" achievable. Bug class without it: heap OOM mid-path-validation leaves the verifier's state machine partially advanced; depending on where it is interrupted, it may return Accept or an uninitialized verdict. Applied in: §7 I9, §6 P5, Phase 1 (§1.2 arena), §11.11, §4 constraint table.

MM9 — Mark-Good is the Commit Point. Expert insight: the SVN monotone counter must advance only after the new image has proven it can boot successfully. "Advance on verify" bricks the device if the image passes verification but then crashes at runtime (bad filesystem, corrupted config, HW incompatibility). The watchdog-gated mark-good is the two-phase commit of the boot update protocol. Bug class without it: advancing min-SVN at verify time → the only good slot is now below the new floor → permanent brick. Applied in: §7 I12, §8.7 A/B state machine, Phase 6 (§17.2 commit path), Phase 9 (§20.2 markgood), §6 P12.

MM10 — Attestation is Only as Strong as the Event Log's Completeness. Expert insight: a quote snapshots PCR values; a verifier replays the event log to confirm why those values are what they are. If the event log is incomplete (missed a measurement, truncated, tampered), the PCRs can be consistent with the log yet not consistent with what actually ran. The policy "PCR8 matches expected kernel" is only meaningful if every extension into PCR8 is logged. Bug class without it: a stage that extends PCR8 but does not append an event log entry → attestation verifier cannot distinguish "correct kernel" from "attacker kernel that extends the right hash." Applied in: Phase 7 (§18.2 log+PCR atomic), §7 I5, §8.2 event-log replay, §6 P15.

Glossary · 45 terms · site-wide glossary

Root of Trust (RoT)
The immutable code/data (boot ROM + fused PK-hash) that begins the trust chain; cannot be updated, so it is minimal.
Verified boot
Each stage cryptographically verifies the next before transferring control; failure halts/falls back.
Measured boot
Each stage records (PCR-extends) a measurement of the next; decision deferred to attestation/sealing.
TCB (Trusted Computing Base)
The code whose correctness is required for security — here sbpki-verify + crypto; kept no_std, minimal, forbid(unsafe).
Manifest
The compact signed metadata structure (§8.1) describing an image: digest, SVN, key id, chain ref, flags, signature.
Detached signature
A signature stored separately from (not embedding) the signed bytes; here over signed_region.
SVN (Security Version Number)
Monotonic integer in a manifest used for anti-rollback; must be ≥ device's effective minimum.
OTP / fuse
One-time-programmable memory; write-once; holds PK-hash + SVN floor (immutable post-provision).
Monotonic NV counter
Non-volatile counter that only increases (compare-and-set ≥); the effective rollback floor.
Anti-rollback
Refusing to boot an image whose SVN < stored minimum, preventing downgrade to a patched vulnerability.
PCR (Platform Configuration Register)
A TPM register updated only by extend (PCR=H(PCR‖m)); accumulates a tamper-evident measurement chain.
Extend
The PCR update operation; order-sensitive, irreversible (extend-only).
Event log
Append-only TCG-format record of every measurement; replays to reconstruct PCR values.
Quote
A signed (by AK) snapshot of selected PCRs + a verifier nonce; the attestation evidence.
AK (Attestation Key)
The key that signs quotes; its public part is certified by the PKI, linking device identity to attestation.
Remote attestation
A verifier challenges a device, checks its quote + event log against expected PCR policy, and admits/denies.
Sealing / unsealing
Encrypting a secret bound to a PCR policy; it unseals only when the platform is in the expected (measured) state.
X.509
The certificate format; chains leaf→intermediate→root carry public keys + constraints (RFC 5280).
Path validation
The RFC 5280 sec. 6.1 algorithm verifying a cert chain: signatures, validity, constraints, EKU, name constraints, revocation.
basicConstraints / pathLen
Extension marking a cert as a CA and limiting how many sub-CAs may follow.
keyUsage / EKU
Allowed uses of a key; code-signing requires EKU id-kp-codeSigning (1.3.6.1.5.5.7.3.3).
Name constraints
Limits on the subject/SAN names a CA may issue (permitted/excluded subtrees).
Trust anchor
The root the chain must terminate at; on device, the fused PK-hash (immutable).
CRL (Certificate Revocation List)
A signed list of revoked cert serials with validity window (thisUpdate/nextUpdate).
OCSP
Online Certificate Status Protocol; per-cert revocation status over the network (RFC 6960).
OCSP stapling
An OCSP response embedded in the manifest so revocation status is available offline.
dbx
An explicit denylist of forbidden key ids / image hashes, shipped with images; the offline revocation kill-switch (UEFI-derived term).
PK / KEK / db / dbx
UEFI Secure Boot key hierarchy (Platform Key / Key Exchange Key / allow db / deny dbx); studied reference (ADR-018).
Signing ceremony
A controlled, witnessed, logged procedure for using an offline/HSM key.
HSM
Hardware Security Module; stores private keys so they never leave the device (modeled via PKCS#11).
Cross-signing
One CA signing another's certificate so chains validate under multiple roots during migration.
Dual-signing
Attaching two signatures (old + new key) to a manifest during a rotation overlap.
A/B (slots)
Two image banks; updates write the inactive one, enabling safe rollback by booting the other.
Mark-good
Committing a booted slot as successful (resets tries, bumps SVN) only after a watchdog-confirmed boot.
Watchdog (WDT)
A timer the booted image must kick; expiry triggers fallback, preventing boot-loop bricks.
Brick / anti-bricking
A permanently-unbootable device; prevented by A/B + recovery + watchdog (some signed image always boots).
Recovery image
A separately-signed, lower-SVN-floor image booted when both A/B slots fail.
Fail-closed
Any error → reject/deny; never warn-and-continue (Principle 1).
Constant-time
