⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the 15-crate Cargo workspace (§10) as compilable stubs with public signatures only. Establish the error taxonomy, ID newtypes, and the deterministic simulator scaffold that every later phase's fixtures attach assertions to. Wire CI and toolchain pinning before any allocator logic exists. Constraint introduced this phase: no crate may contain an unsafe block yet — that budget opens in Phase 2 (§14) under P10.

Deliverable

A workspace that builds all 15 crates as empty-bodied public-API stubs; cargo build --workspace succeeds; CI pipeline green; the simulator scaffold runs a zero-assertion smoke pass.

Acceptance
  • Cold cargo build --workspace completes in < 90 s on a 16-core CI runner.
  • All 15 crates from §10 present with a compiling manifest and crate root.
  • cargo test --workspace exits 0 with ≥ 1 smoke test per crate (≥ 15 total).
  • fixtures/bootstrap/workspace_manifest_missing_crate.toml causes CI to fail fast with a named missing-crate diagnostic, never a silent skip.
Fixtures
  • fixtures/bootstrap/workspace_manifest_valid.toml — golden manifest; expected: clean build.
  • fixtures/bootstrap/workspace_manifest_missing_crate.toml — malformed; expected: CI fails fast with a named diagnostic.
  • fixtures/bootstrap/config_default.toml — replay of default config load; expected: byte-identical Config struct across 100 reloads (determinism smoke test, P1).
Pitfalls
  1. Workspace-wide feature unification silently enabling unsafe-gated features early — manifestation: cargo-geiger count nonzero in Phase 0; root cause: shared feature flags across crates; debugging: cargo tree -e features; signal: ADR-17 gate fails in CI; recovery: split feature flags per crate.
  2. CI runners lacking perf_event_open capability silently skip topology jobs; root cause: missing CAP_PERFMON in the runner container; debugging: inspect the perf.yml job log; signal: job reports 0 tests run, not a failure; recovery: assert nonzero test count explicitly in the job.
  3. Simulator scaffold reads wall-clock time instead of a fixed seed; root cause: placeholder Instant::now() call; debugging: diff two simulator runs; signal: non-reproducible smoke output; recovery: force an injected MonotonicNs source (ADR-20).

⬜ Phase 1 — Topology Discovery Foundation §13

Objectives

Implement canonical NUMA topology discovery and normalization: parse firmware topology data, validate it against the CPU map, and publish an immutable snapshot every later phase reads (I12). Introduces the startup-latency constraint (< 250 ms, §4) and the degraded-mode fallback (P12).

Deliverable

A runnable topology-discovery binary (cli-tools::topology_dump) that parses a real or synthetic SRAT/ SLIT pair and prints the normalized node graph plus a validation verdict.

Acceptance
  • Parses topologies with 1–64 NUMA nodes (§4 ceiling) without reallocation past a preallocated bound.
  • Rejects fixtures/topology/malformed_srat_missing_node.bin with AllocatorError::TopologyFault, not a panic.
  • Cold startup discovery completes in < 250 ms for a 64-node synthetic topology (§4).
  • fuzz/fuzz_targets/topology.rs runs 24 h without a crash or an unbounded-memory finding.
Fixtures
  • conformance/topology/topology_dual_socket.json — 2-node golden fixture; expected: clean parse, symmetric distance matrix.
  • conformance/topology/topology_quad_socket.json — 4-node golden fixture with asymmetric NPS4 distances; expected: clean parse, validator accepts asymmetry within the 1.3×–4.5× band.
  • conformance/topology/malformed_srat_missing_node.bin — SRAT references a CPU absent from the CPU map; expected: validator rejection, degraded mode entered, topology_fault telemetry emitted.
Pitfalls
  1. BIOS/firmware inconsistencies between SRAT and the live CPU map on hot-pluggable hardware — manifestation: validator false-positive rejection; root cause: firmware published a superset of physically present CPUs; debugging: diff SRAT dump against cpu_map.rs output; signal: rejection rate spikes only on specific hardware SKUs; recovery: treat absent-but-SRAT-listed CPUs as Reserved, not fatal.
  2. Asymmetric distance matrices on NPS4-style AMD topologies misread as corruption — root cause: validator's initial symmetry assumption was too strict; debugging: compare against vendor-published distance tables; signal: rejection only on AMD EPYC NPS4; recovery: relax symmetry check to a tolerance band, not exact equality.
  3. CPU hotplug races during startup validation — manifestation: intermittent validator failure; root cause: CPU map read mid-hotplug event; debugging: replay conformance/topology fixtures with a simulated hotplug injection; signal: non-reproducible locally, reproducible under simulator; recovery: snapshot the CPU map once, atomically, before validation begins.
  4. Sparse CPU masks on memory-only ("CPU-less") NUMA nodes misclassified as invalid — root cause: validator assumed every node has ≥ 1 CPU; recovery: add explicit memoryless: bool to NodeDescriptor rather than rejecting the node.

⬜ Phase 2 — Page Allocator Core §14

Objectives

Implement the node-local physical page allocator: descriptor table, free-list hierarchy, and the allocation fast path with remote fallback. Introduces the first unsafe code (P10) and the first real lock-contention surface (P11). Establishes p50 < 120 ns and remote-ratio < 8 % as measured, not aspirational, targets (§4).

Deliverable

A functional page allocator: cli-tools can drive a synthetic allocation/free workload against it and report locality and latency percentiles.

Acceptance
  • p50 allocation latency < 200 ns under single-threaded microbenchmark (tightens to the < 120 ns §4 target once Phase 3's slab fast path is in place).
  • Zero corruption findings across a 10M-operation stress run using conformance/allocator/ fragmented_pages.bin as the initial arena state.
  • Remote-allocation ratio < 8 % under a node-local-biased synthetic workload (§4).
  • Replay reconstruction from conformance/allocator/remote_alloc_replay.bin matches live state exactly.
Fixtures
  • conformance/allocator/fragmented_pages.bin — pre-fragmented arena state; expected: allocator degrades gracefully, fragmentation stays < 18 % (§4) rather than failing allocation.
  • conformance/allocator/remote_alloc_replay.bin — recorded remote-fallback sequence; expected: deterministic replay reconstructs identical ownership state (I1, I5).
  • fixtures/allocator/aba_race_injection.bin — replay case injecting a delayed free between CAS read and write; expected: generation counter (I10) prevents ABA reuse.
Pitfalls
  1. ABA corruption on the remote-free queue under high churn — manifestation: a freed page reused while a stale reference still holds it; root cause: pointer reuse without a generation check; debugging: replay fixtures/allocator/aba_race_injection.bin under the simulator; signal: generation. wrap_near_miss telemetry; recovery: generation counter bump on every ownership transition (I10).
  2. Free-list cycles from a double-insert bug — manifestation: allocator livelocks walking a cyclic free list; root cause: insert path not idempotent under a race; debugging: cycle detector in the simulator's assertion for I1; recovery: quarantine + arena rebuild (P3).
  3. Cacheline bouncing on the shared remote-free queue head under many-writer contention — manifestation: p99 latency spikes under 32+ thread fan-in; root cause: single queue head cacheline hot across sockets; debugging: perf c2c cacheline-contention report; recovery: per-source-node remote-free sub-queues (extends ADR-08's queue design).

⬜ Phase 3 — Slab Allocator §15

Objectives

Implement the NUMA-aware small-object slab subsystem sitting above the page allocator: size classes, per-thread magazines, and remote-free batching. Targets p99 small-object allocation < 1 µs and fragmentation < 15 % (tighter than §4's 18 % system ceiling, since slab is the dominant allocation path).

Deliverable

A small-object allocator layered over Phase 2's page allocator, swappable in place of the raw page path for allocations below the hugepage threshold.

Acceptance
  • p99 small-object (≤ 4 KB) allocation latency < 1 µs under an 8-thread contended microbenchmark.
  • Fragmentation < 15 % after a 1-hour churn-heavy synthetic workload (fixtures/slab/churn_1h.bin).
  • Zero corruption findings across fixtures/slab/magazine_refill_race.bin replayed 1000×.
Fixtures
  • fixtures/slab/churn_1h.bin — recorded high-churn alloc/free sequence; expected: fragmentation stays below 15 % throughout, not just at steady state.
  • fixtures/slab/magazine_refill_race.bin — concurrent refill-from-depot race; expected: no double- issued object, no lost object (I1 extended to slab granularity).
  • fixtures/slab/oversized_object_reject.bin — allocation request above the largest size class; expected: rejected to the page allocator path, not silently truncated.
Pitfalls
  1. Freelist poisoning pattern mismatched between slab and page allocator layers — manifestation: false- positive corruption alerts; root cause: two independent poison-byte conventions; debugging: compare slab::cache and allocator-core::checksum poison constants; recovery: single shared poison-pattern constant.
  2. Remote-free storms when a thread migrates across sockets mid-run (e.g. after a scheduler rebalance) — manifestation: sudden queue-depth spike on one node; root cause: the thread's magazine still holds objects from its old node; debugging: correlate sched_getcpu migration events with remote_free. queue_depth; recovery: magazine flush-on-migration hook (feeds into Phase 5's policy engine).
  3. Branch misprediction in size-class lookup on skewed allocation-size distributions — manifestation: p99 latency regression despite low contention; root cause: size-class table lookup not sorted by observed frequency; debugging: perf record branch-miss annotation; recovery: reorder size-class table by production allocation-size histogram.

⬜ Phase 4 — Hugepage Manager §16

Objectives

Implement explicit 2 MB / 1 GB hugepage reservation, replacing reliance on transparent hugepages (THP) for allocator-controlled determinism (ADR-23). Targets hugepage allocation latency < 50 µs and success ratio > 95 % (§4).

Deliverable

2 MB and 1 GB hugepage allocation and reservation, integrated as a fallback step in the §8 allocation sequence ahead of remote-node fallback for large allocations.

Acceptance
  • Hugepage allocation success ratio > 95 % when the configured reservation pool is not exhausted (§4).
  • Hugepage allocation latency < 50 µs, measured via benchmarks/alloc_latency.rs extended with a hugepage-path mode.
  • 100 % of hugepage-backed allocations pass the hugepage::alignment validator in fixtures/hugepage/alignment_sweep.bin (10,000 allocations at randomized sizes).
Fixtures
  • fixtures/hugepage/alignment_sweep.bin — 10,000 randomized-size allocation requests; expected: every hugepage-backed result is 2 MB/1 GB aligned, no exceptions.
  • fixtures/hugepage/pool_exhaustion_fallback.bin — reservation pool exhausted mid-run; expected: transparent fallback to 4 KB pages, hugepage.fallback telemetry emitted, no allocation failure.
  • fixtures/hugepage/mixed_page_size_replay.bin — interleaved 4 KB/2 MB/1 GB allocations; expected: fragmentation accounting stays consistent across all three page sizes.
Pitfalls
  1. Hugepage fragmentation from partial pool exhaustion — manifestation: success ratio drops below 95 % despite apparently free capacity; root cause: free hugepages exist but are the wrong size class (2 MB free, 1 GB requested); debugging: hugepage.pool_state dump by size class; recovery: size-class-aware reservation budgeting, not a single pooled counter.
  2. TLB shootdown amplification when migrating a hugepage-backed region — manifestation: migration of a single 1 GB page causes a system-wide TLB shootdown storm; root cause: naive whole-region invalidation (per Gaud et al. 2014's finding); debugging: perf stat -e tlb_flush; recovery: batch shootdowns across concurrent migration tasks rather than one per page (feeds Phase 6 design).
  3. Page-split overhead when a hugepage-backed allocation is freed partially — manifestation: unexpected latency spike on free; root cause: the allocator attempted a partial-region free, which requires splitting the hugepage; recovery: forbid partial free of a hugepage-backed allocation at the API level (§11 AllocationRequest.hugepage_allowed is all-or-nothing).

⬜ Phase 5 — NUMA Policy Engine §17

Objectives

Implement placement heuristics: locality scoring, preferred-node selection, and balancing thresholds that consume topology distance data (§13) without ever allocating memory directly (P5). Targets a 40 % reduction in remote accesses relative to a naive round-robin placement baseline.

Deliverable

An adaptive placement layer: policy directives consumed by allocator-core's allocation fast path (Phase 2) and migration's task queue (Phase 6), inspectable via policy-trace dumps.

Acceptance
  • Remote-access ratio reduced by ≥ 40 % versus round-robin baseline on fixtures/policy/ mixed_workload_8node.bin.
  • Scoring overhead adds < 50 ns to the allocation fast path (bounded fraction of the p50 120 ns budget, §4).
  • Zero oscillation events (a node flip-flopping preferred-status more than 3× in 60 s) across a 1-hour soak using fixtures/policy/oscillation_stress.bin.
Fixtures
  • fixtures/policy/mixed_workload_8node.bin — recorded 8-node allocation pattern with known-optimal placement; expected: scoring converges to within 5 % of optimal remote-ratio.
  • fixtures/policy/oscillation_stress.bin — adversarial workload designed to flip preferred-node scoring; expected: balancing thresholds include hysteresis, no flip-flopping.
  • fixtures/policy/conflicting_affinity.bin — two threads with explicit, contradictory pinning hints on the same allocation path; expected: deterministic tie-break (lower ThreadId wins), not nondeterministic.
Pitfalls
  1. Oscillating policies where two nodes repeatedly trade "preferred" status — manifestation: migration engine (Phase 6) receives contradictory recommendations within seconds; root cause: balancing threshold has no hysteresis band; debugging: replay fixtures/policy/oscillation_stress.bin; signal: policy.recommendation_flip_count spikes; recovery: add a minimum-dwell-time hysteresis before a new recommendation can reverse the previous one.
  2. Migration thrashing induced by overly aggressive balancing thresholds during a legitimately bursty workload — root cause: workload classification misclassified a burst as sustained imbalance; debugging: correlate policy.workload_class with migration.task_enqueue_rate; recovery: require sustained imbalance across N consecutive scoring windows before recommending migration.
  3. Scoring overhead creeping onto the fast path as more signals are added — manifestation: p50 latency regresses past 120 ns; root cause: scoring called synchronously inside the allocation path rather than precomputed per-epoch; recovery: precompute per-node scores once per epoch, allocation path reads a cached score.

⬜ Phase 6 — Migration Engine §18

Objectives

Implement asynchronous, rate-limited page migration that acts on Phase 5's recommendations: queueing, worker execution, heatmap-driven prioritization, and rollback on failure. Targets migration failure rate < 0.1 % and bandwidth-safe rate limiting (< 1 % CPU overhead, §4).

Deliverable

Online locality repair: a background subsystem that measurably reduces remote-allocation ratio over time on a running process without operator intervention, inspectable via migration dashboards.

Acceptance
  • Migration failure rate < 0.1 % across fixtures/migration/sustained_repair_1h.bin.
  • Migration scheduling overhead stays < 1 % CPU (§4) measured via perf stat during the same fixture.
  • 100 % of Pinned-state pages in fixtures/migration/pinned_page_reject.bin are correctly rejected before entering Candidate (I4 enforcement).
Fixtures
  • fixtures/migration/sustained_repair_1h.bin — 1-hour recorded workload with induced locality drift; expected: remote-ratio trends downward, failure rate < 0.1 %.
  • fixtures/migration/pinned_page_reject.bin — migration recommendation targeting a Pinned page; expected: rejected pre-queue, migration.pin_violation telemetry (I4).
  • fixtures/migration/dirty_page_during_copy.bin — a write races the Copying state; expected: task restarts, no stale copy committed, no data loss.
Pitfalls
  1. Migration storms where many tasks queue simultaneously after a topology or workload shift — manifestation: bandwidth collapse, other allocator operations stall; root cause: rate limiter applies per-task, not globally; debugging: migration.queue_depth + perf stat -e mem_bw; recovery: global token-bucket rate limiter shared across all migration workers, not per-worker.
  2. Stale mappings after a migration completes but the caller's cached pointer wasn't invalidated — manifestation: caller reads from the old physical location transiently; root cause: Remapping and caller notification aren't atomic; debugging: replay fixtures/migration/dirty_page_during_copy.bin; recovery: Verified state gate ensures no Complete transition until all references are confirmed updated.
  3. Rollback loop where a repeatedly-failing task is retried indefinitely at the same priority — manifestation: one bad page starves the queue; root cause: rollback requeues without backoff; recovery: exponential backoff with a max-retry-then-abandon policy, surfaced to telemetry for operator review.

⬜ Phase 7 — Reclaim and Pressure Handling §19

Objectives

Implement memory-pressure detection and reclaim: cold-page scanning, pressure propagation, and emergency reclaim under cgroup v2 memory-controller limits (§4 deployment assumption). Targets stability under synthetic pressure without triggering an OOM kill.

Deliverable

A pressure-resilient allocator: stays within cgroup v2 memory limits under sustained allocation pressure without an OOM kill, verified against a synthetic pressure-generation harness.

Acceptance
  • Stable (no OOM kill, no crash) across fixtures/reclaim/sustained_pressure_2h.bin at 95 % of the cgroup memory.max limit.
  • Emergency reclaim activation rate < 1 per hour under the same fixture (throttling should resolve pressure before emergency reclaim is needed in the common case).
  • Zero I11 violations (reclaim of a Pinned/Migrating page) across 10M scanner cycles in fixtures/reclaim/state_conflict_stress.bin.
Fixtures
  • fixtures/reclaim/sustained_pressure_2h.bin — 2-hour recorded workload approaching the cgroup limit; expected: throttling engages, no OOM kill, pressure stabilizes.
  • fixtures/reclaim/state_conflict_stress.bin — scanner races against concurrent pinning/migration; expected: zero I11 violations, all conflicts resolved by skip-and-requeue.
  • fixtures/reclaim/global_pressure_collapse.bin — adversarial fixture driving pressure past the emergency-reclaim threshold; expected: emergency path activates, system remains responsive (bounded p99, not frozen).
Pitfalls
  1. Reclaim oscillation where the scanner reclaims a page just before it would have been reused locally — manifestation: reclaimed memory immediately re-requested from a remote node, worsening locality; root cause: scanner's coldness threshold too aggressive relative to access-pattern periodicity; debugging: correlate reclaim.page_reclaimed timestamps against subsequent alloc.remote_ratio spikes; recovery: raise the coldness dwell-time threshold, informed by the workload classification from Phase 5.
  2. Pressure propagation lag from the cgroup controller causing reactive-too-late throttling — manifestation: allocator only starts throttling after the limit is already breached; root cause: polling interval for memory.pressure too coarse; recovery: subscribe to the cgroup v2 pressure notification file descriptor (event-driven) rather than polling.
  3. Emergency reclaim scanning contending with the allocation fast path's lock striping — manifestation: p99 latency spike coincides with every emergency-reclaim activation; recovery: emergency reclaim takes a strictly bounded number of pages per pass and yields, never a single unbounded sweep.

⬜ Phase 8 — Observability and Replay §20

Objectives

Implement full deterministic observability: structured logging, tracing spans, the replay WAL, and crash- dump support, making every prior phase's allocator state transition reconstructable after the fact (P1, P6). This phase turns the assertions used internally by every earlier phase's fixtures into an operator- facing capability.

Deliverable

A replayable allocator: given a WAL segment and a starting snapshot, cli-tools::replay_inspect reconstructs and displays the full allocator state at any recorded sequence number.

Acceptance
  • Replay determinism verified: 1000 independent replays of fixtures/replay/golden_1h_session.bin produce byte-identical reconstructed state.
  • WAL append overhead < 3 % of allocation-path latency (§4), measured via benchmarks/alloc_latency.rs with WAL enabled vs. disabled.
  • Crash-dump generation completes in < 5 s (matches the graceful-shutdown budget, §4) for a 64 TB resident-state process.
Fixtures
  • fixtures/replay/golden_1h_session.bin — 1-hour recorded session across all subsystems; expected: deterministic, byte-identical reconstruction across repeated replays.
  • conformance/replay/replay_basic.bin — minimal single-node allocate/free/migrate sequence; expected: smallest reproducible replay-correctness fixture, used in CI on every commit.
  • conformance/replay/malformed_wal.bin — a WAL segment with a sequence gap (I5 violation); expected: replay.sequence_gap detected, reconstruction falls back to last-verified snapshot, never silently skips the gap.
Pitfalls
  1. Excessive telemetry overhead once every subsystem's spans are enabled simultaneously — manifestation: fast-path latency creeps past the < 3 % WAL budget when spans are counted alongside it; root cause: span emission and WAL append compete for the same ring-buffer bandwidth; debugging: perf stat comparison of WAL-only vs. WAL+spans; recovery: separate ring buffers per concern, sized independently.
  2. WAL fsync amplification under high allocation rates — manifestation: p99 latency spikes correlate with fsync intervals; root cause: fsync-per-record is too conservative, fsync-never risks I5/RPO violation; recovery: batched fsync on a bounded interval matching the < 1 s RPO target (§4), not per-record.
  3. Replay divergence where reconstruction disagrees with recorded live-state telemetry — manifestation: a replayed state doesn't match what was observed live; root cause: a non-deterministic input (e.g. a stray wall-clock read) leaked into a decision path; debugging: bisect the WAL segment by sequence range until the divergence point is isolated; recovery: audit and remove the non-deterministic input, treat as a P1 violation bug.

⬜ Phase 9 — Conformance, Fuzzing & Production Hardening §21

Objectives

Close the loop: continuous fuzzing and differential replay testing (stress correctness across every prior phase), plus the operational hardening — canary deployment, rolling upgrades, chaos testing — that makes the system production-ready. This is the terminal phase; nothing downstream introduces new subsystems.

Deliverable

A continuously-verified, production-hardened runtime: 72-hour soak-stable, canary-validated, rollback- tested, ready for the release process defined in §27.

Acceptance
  • 72-hour soak stability with zero invariant violations (§7) under combined chaos injection.
  • Fuzz targets (topology.rs, allocator.rs, metadata.rs) each reach 24-hour crash-free runs with no new coverage plateau evasion (measured via cargo-fuzz corpus growth rate).
  • Rolling upgrade from the prior minor version completes with zero allocation-serving downtime on fixtures/hardening/rolling_upgrade_v_n_minus_1.bin.
  • Rollback from a canary failure completes within the < 60 s RTO (§4).
Fixtures
  • fixtures/hardening/rolling_upgrade_v_n_minus_1.bin — recorded dual-version traffic split; expected: zero downtime, compatible replay across the version boundary.
  • fixtures/hardening/chaos_combined_injection.bin — simultaneous forced-OOM + migration-interruption + lock-starvation; expected: every subsystem degrades per its documented failure-analysis section, no undocumented crash.
  • fixtures/hardening/canary_rollback_trigger.bin — canary traffic exceeding an error-budget threshold; expected: automatic rollback triggers within the RTO budget.
Pitfalls
  1. Non-deterministic fuzz failures that don't reproduce outside the fuzzer's exact input — manifestation: a crash reported once, never again; root cause: a genuine race condition rather than a deterministic parsing bug; debugging: minimize the reproducer under the deterministic simulator (Phase 0), not the raw fuzzer, since the simulator controls scheduling; recovery: store the minimized reproducer permanently in the fuzz corpus regardless of reproducibility difficulty.
  2. Version skew during a rolling upgrade where the new binary's metadata layout is incompatible despite passing the additive-schema check — manifestation: a subtle field-interpretation mismatch; root cause: an additive field's default value differs in meaning between versions; debugging: replay fixtures/hardening/rolling_upgrade_v_n_minus_1.bin against both binaries and diff; recovery: add an explicit compatibility test to §26 for every schema change, not just a layout-size check.
  3. Canary traffic too small to statistically distinguish a regression from noise — manifestation: a real regression ships past canary; root cause: canary percentage set without a power calculation against the observed metric variance; recovery: size the canary traffic percentage against the §4 latency targets' expected variance, not a fixed 1 % default.
