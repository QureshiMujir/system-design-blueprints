192 — NUMA Memory Manager from Scratch

Project Number: 192

Project Name: NUMA Memory Manager from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition. Build a NUMA-topology-aware userspace memory manager for Linux x86_64/ARM64 multi-socket servers: a page-and-slab allocator whose placement, migration, and reclaim decisions are driven by hardware distance data (ACPI SRAT/SLIT), exposed through a stable C-ABI-compatible Rust runtime API, with deterministic replay of every allocator state transition. The system is a hybrid of a kernel-inspired allocator core (SLUB/buddy lineage) and a userspace NUMA policy engine (Solaris locality groups lineage), not a reimplementation of either.

Phase 0 deliverable — crates/services stood up:

  1. topology — ACPI SRAT/SLIT parsing, node/CPU normalization.
  2. allocator-core — page descriptor table, free-list hierarchy, state machine.
  3. arena — per-node allocation domains, remote-free queues.
  4. slab — size-classed small-object allocator.
  5. hugepage — 2 MB / 1 GB explicit reservation manager.
  6. reclaim — pressure-triggered page reclaim.
  7. migration — asynchronous page relocation engine.
  8. policy — placement/locality scoring engine.
  9. telemetry — metrics + OpenTelemetry span emission.
  10. replay — write-ahead log and deterministic reconstruction.
  11. runtime-api — public malloc/free/policy surface.
  12. cli-tools — operator inspection binaries.
  13. benchmarks — Criterion + perf harnesses.
  14. fuzz — cargo-fuzz targets.
  15. conformance — fixture-driven correctness suite.

System boundaries.

Provides: NUMA topology discovery and normalization; node-local page and slab allocation; explicit hugepage reservation; asynchronous locality-repair migration; pressure-aware reclaim; deterministic replay and crash forensics; a stable runtime API for embedding.

Delegates: virtual-to-physical page table maintenance (Linux kernel via mmap/mbind); CPU scheduling and thread placement (Linux CFS/EEVDF); physical DRAM interleave and firmware-level topology reporting (ACPI/BIOS); network transport for exported telemetry (sidecar process).

Does NOT provide: a general-purpose operating system, a hypervisor, distributed shared memory, a garbage collector, a swap-subsystem replacement, or a kernel module replacing Linux VM. It never patches the kernel page-fault path.

Non-goals: cross-host memory pooling, GPU memory management, transparent-huge-page kernel reimplementation, CPU scheduling policy, live kernel patching.

Deployment model. Single-process shared library runtime, four embedding modes — static link, LD_PRELOAD dynamic intercept, in-process runtime embedding (runtime-api crate), and a standalone benchmarking daemon — plus an optional sidecar telemetry exporter. Primary targets: bare-metal NUMA servers, cgroup v2 containers, Kubernetes stateful workloads pinned with topologyManager.

Target operators: SRE and infrastructure teams operating multi-socket fleets; performance engineers attributing tail-latency regressions to memory locality; kernel-adjacent runtime teams embedding the allocator into a database, actor runtime, or dataplane.

What later phases unlock: adaptive NUMA balancing (§17), tiered/CXL memory support (PhaseDeferred("§18")), persistent-memory-aware policies (PhaseDeferred("§19")), heterogeneous memory scheduling, ML-guided placement (PhaseDeferred("§17")), RDMA-aware placement (PhaseDeferred("§21")), allocator-aware external schedulers.

Recommended language: Rust 1.82+. Rationale: explicit ownership eliminates use-after-free in intrusive free-list code without GC pause interference in the allocation fast path; #[repr(C)] and std::sync::atomic give byte-exact control over metadata layout (needed for I3, I6); unsafe blocks are lexically isolated and auditable (P10) versus C++'s ambient unsafety; reproducible builds via cargo --locked and a pinned toolchain satisfy ADR-19 without bespoke tooling. Rejected: C++ (header-only ODR hazards complicate the reproducible-build ADR, no built-in data-race detection at compile time); Zig (2024-era ecosystem lacked mature tracing/OpenTelemetry/Criterion equivalents required by §26/§28, immature NUMA syscall bindings). Unsafe Rust is mandatory for: page metadata manipulation, intrusive lists, lock-free queues, cacheline alignment, NUMA syscall bindings, and allocator-core internals — nowhere else.

Prerequisites: virtual memory internals; Linux memory management (buddy/SLUB); CPU cache hierarchy and coherence protocols; NUMA architecture (distance matrices, interleave); lock-free programming and the C11/Rust memory model; page-table fundamentals; TLB behavior; hugepage mechanics; profiling methodology (perf, eBPF); storage allocator design; classical synchronization algorithms.

Timeline. Phase 0: 10 weeks (topology skeleton + correctness kernel + CI). Full system (Phases 0–9): 9–14 months for a team of 3–5 systems engineers, gated by §26 soak criteria, not calendar time.

2. Why Build This

NUMA memory behavior sets the scalability ceiling of multi-socket systems more often than algorithmic complexity does: cross-socket access penalties of 1.3×–4.5× (§4) convert a linear-scaling workload into one that regresses past 2–4 sockets once remote-access ratio crosses the noise floor. Most production memory incidents are locality collapses, not leaks — a workload that was node-local at launch drifts remote as threads migrate and pages age, and nothing detects the drift until p99 latency triples.

This project teaches, end to end: allocator architecture (arena/slab/page hierarchy); page lifecycle engineering (state machines, ownership, migration); cacheline-aware concurrency (false-sharing avoidance, lock striping); memory placement policy design; latency tail debugging; topology-aware scheduling interaction; lock-contention elimination; fragmentation control; memory observability; and hardware-aware systems engineering generally.

Historically relevant systems: the Linux buddy allocator and SLUB slab allocator; jemalloc; tcmalloc; mimalloc; Solaris locality groups (lgrp framework); the Windows NUMA scheduler; Seastar's per-shard memory subsystem; DPDK rte_mempool. Cross-linked domains: kernels, databases, schedulers, actor runtimes, storage engines, distributed coordination, hypervisors, GPU memory managers, object stores, network dataplanes — all of which either embed an allocator with these exact tradeoffs or are victims of getting them wrong.

What Mastery Looks Like

  • Diagnose a production locality collapse from telemetry alone (remote-allocation ratio, migration rate, lock-contention histograms) without attaching a debugger — competency built in §17 and §24.
  • Design and implement a NUMA-aware slab allocator with per-thread magazines and bounded remote-free batching — built in §15.
  • Reason quantitatively about cross-socket access penalty and translate it into a placement policy — built in §17.
  • Build a deterministic replay system that reconstructs allocator state transition-by-transition from a WAL, and use it to root-cause a corruption bug — built in §20.
  • Design rate-limited, rollback-capable asynchronous page migration that never destabilizes the system it is trying to repair — built in §18.
  • Attribute tail latency (p99, not mean) to a specific subsystem using flamegraphs, perf stat, and cacheline-heatmap tooling — built in §28.
  • Operate a large-memory (64 TB address space) system through a production incident using the runbooks and forensics built in §23 and §24.

Runtime API Layer (runtime-api) — the only compatibility-locked surface (§25); exposes allocation, policy override, arena lifecycle, and diagnostics endpoints; must remain ABI-stable across minor releases because embedding applications compile allocator assumptions directly into their binaries.

NUMA Policy Engine (policy) — computes placement using topology distances, workload affinity, thread ownership history, and pressure signals (I8); never allocates directly (P5); emits placement directives consumed by allocator-core. Violating this separation (letting the policy engine touch free lists) is the single most common design regression covered in §33.

Allocation Engine (allocator-core, arena, slab, hugepage) — owns every hot-path operation: slab caches, page allocation, remote-free handling, hugepage reservation, fragmentation accounting, cacheline-aware free lists. Bounded latency (P8) is prioritized over absolute memory efficiency.

Migration Engine (migration) — repairs locality degradation asynchronously and rate-limited (P2) using page heatmaps, migration cost estimates, and topology distance; never runs synchronously inside an allocation call.

Metadata Subsystem (replay, page-descriptor tables inside allocator-core) — the single authoritative store for page descriptors, ownership maps, and replay lineage; corruption detection here is mandatory (I1, I3).

Topology Layer (topology) — normalizes ACPI/kernel topology into a stable, immutable-after-startup internal representation (I12) consumed by every subsystem above it.

Linux Kernel Interfaces — isolates every syscall and kernel-facing integration; centralizes error translation; the only layer where unsafe crosses a real trust boundary (P10).

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every placement and migration decision must be reconstructable from the replay log alone. Tradeoff: forgoes randomized load-balancing heuristics that are easier to tune. Operational: replay divergence is treated as a P0 bug, not a flake. Violated: debugging a locality regression degrades into guesswork because the decision that caused it cannot be replayed.
  • P2 — Backpressure Everywhere. Rule: every queue (remote-free, migration, reclaim) is bounded with an explicit drop/reject policy. Tradeoff: bursty workloads see early throttling instead of unbounded buffering. Operational: queue-depth telemetry is mandatory at every boundary. Violated: an unbounded migration queue during a topology change causes cascading latency collapse (FM-5).
  • P3 — Crash-Only Semantics. Rule: subsystems recover through restart/reconstruction from the WAL, never through in-place partial repair. Tradeoff: costs a full arena rebuild (< 60 s RTO) instead of a cheaper targeted patch. Operational: no code path may special-case "repair this one corrupt record." Violated: an ad hoc metadata patch silently reintroduces the corruption it was meant to fix.
  • P4 — NUMA Locality First. Rule: remote memory access is treated as a correctness-adjacent performance failure, tracked with the same rigor as a bug. Tradeoff: sacrifices some allocation throughput to keep remote-allocation ratio under 8 % (§4). Operational: every allocation records its locality outcome. Violated: a workload silently drifts to 40 % remote allocations with no alert (I8).
  • P5 — Explicit Ownership. Rule: every page has exactly one authoritative allocator owner at all times (I1). Tradeoff: forecloses lock-free multi-owner sharing schemes that could reduce contention further. Operational: ownership transfer is a single atomic CAS, never a two-step handoff. Violated: double-ownership causes a double-free indistinguishable from memory corruption.
  • P6 — Replayability Before Optimization. Rule: the replay WAL stays on even when its overhead is measurable (< 3 %, §4), and is never disabled to chase a benchmark number. Tradeoff: gives up the last 3 % of throughput available from a WAL-less build. Operational: WAL-disabled builds are fuzz/bench-only, never shipped. Violated: a production incident has no forensic trail (§24).
  • P7 — Observability by Default. Rule: every allocator state transition emits structured telemetry without an opt-in flag. Tradeoff: baseline telemetry cardinality cost is paid on every deployment. Operational: telemetry emission must never block the allocation fast path (I13). Violated: an operator cannot answer "why did p99 spike at 03:14" without redeploying with debug flags.
  • P8 — Bounded Tail Latency. Rule: p99 latency (§4) is optimized ahead of mean throughput whenever they conflict. Tradeoff: rejects allocator designs (e.g. global compaction passes) that improve mean throughput at the cost of occasional stalls. Operational: any code path that can hold a lock > 3 µs is a design defect, not a tuning target. Violated: a rare compaction pass causes a 50× p99 spike invisible in mean-latency dashboards.
  • P9 — Stable Metadata Layouts. Rule: allocator metadata (PageDescriptor, NodeDescriptor) cannot drift silently across builds; layout changes are versioned (ADR-05, §25). Tradeoff: costs explicit migration tooling for every metadata schema change. Operational: a checksum over the metadata layout is validated at startup. Violated: a rolling upgrade reads a page descriptor with the wrong field offsets and silently corrupts state.
  • P10 — Isolation of Unsafe Code. Rule: unsafe blocks are confined to page-metadata manipulation, intrusive lists, lock-free queues, cacheline alignment, and NUMA syscall bindings — nowhere else. Tradeoff: some hot-path code that could be marginally faster with broader unsafe use stays safe and slightly slower. Operational: cargo-geiger gates unsafe growth in CI (ADR-17). Violated: an unsafe block leaks into policy-engine code and a single scoring bug becomes a memory-safety CVE.
  • P11 — Lock Minimization. Rule: contention must be measurable (per-lock hold-time histogram) and attributable to a specific subsystem. Tradeoff: forgoes a single global allocator lock's implementation simplicity. Operational: any new lock requires a documented expected hold-time budget. Violated: an unmeasured lock becomes a silent throughput ceiling discovered only under production load (FM-6).
  • P12 — Fail Closed. Rule: unknown or malformed topology states disable optimization (degraded mode) rather than guessing a placement. Tradeoff: gives up locality optimization entirely on unusual hardware rather than risk a wrong guess. Operational: degraded mode is a first-class, tested state, not an error path. Violated: the allocator "guesses" a NUMA node for a malformed SRAT entry and silently places memory on the wrong socket for the life of the process.

8. Domain Model — Page and Allocation Lifecycle

Page states.

State Description
Free Unallocated, on a node-local free list
Reserved Topology-reserved (not yet allocator-owned)
Slab Slab-managed small object region
Huge Hugepage-managed (2 MB / 1 GB)
Migrating Migration in flight — see Migration State Machine
Reclaiming Reclaim scan/relocation in progress
Pinned Non-migratable (embedder contract, I4)
Poisoned Corruption suspected — quarantined

Allocation sequence (fallback chain, each step attempted in order):

Thread → Thread Cache → Arena → Node Page Allocator → Hugepage Fallback
       → Remote Node Fallback → OOM Handler

Allocation request structure (fields, no bodies):

AllocationRequest:
  size_class: SizeClass;
  alignment: u32;
  numa_policy: NumaPolicy;
  preferred_node: NodeId;
  migration_allowed: bool;
  hugepage_allowed: bool;
  locality_generation: u32;

Migration state machine.

Idle → Candidate → Queued → Copying → Remapping → Verified → Complete
                       │
                       └──────────────→ Failed

Any state may transition to Failed; Failed transitions back to Idle after rollback (§18). No state skips Verified en route to Complete — this is the enforcement point for I4 and I5 jointly.

Failure path example — malformed topology: SRAT node references a CPU absent from the CPU map → topology validator fails → allocator enters degraded mode (P12) → all allocations for that boot are marked non-optimized → telemetry emits topology_fault (see §13 N.9).

11. Core Schema & Types

Signatures only — no bodies. Every type is annotated: Own (who mutates it), Sync (concurrency discipline), Persist (WAL/snapshot participation), Wire (serialization), Compat (evolution rule).

NodeDescriptor:
  node_id: NodeId;
  cpu_mask: CpuMask;
  memory_ranges: Vec<PhysRange>;
  distance_vector: Vec<u16>;
  arena_set: Vec<ArenaId>;
  reclaim_state: ReclaimState;
  migration_budget: u32;

Own: topology at startup only. Sync: immutable after publish (I12), read via Arc snapshot, no locks. Persist: written once to snapshot at startup, never to the WAL. Wire: internal only, never crosses the runtime-api boundary. Compat: additive fields only, ADR-05 versioned.

PageDescriptor:
  physical_addr: PhysAddr;
  owner: OwnerId;
  state: PageState;
  refcount: AtomicU32;
  slab_class: Option<SizeClass>;
  checksum: u32;
  generation: AtomicU32;

Own: allocator-core, transferred via CAS on owner+state (P5, I1). Sync: per-field atomics, no descriptor-level lock (P11). Persist: every state transition appended to WAL (replay::record). Wire: fixed #[repr(C)] layout, checksum covers all fields but itself. Compat: layout-versioned, checked at startup against I6/ADR-05.

Arena:
  arena_id: ArenaId;
  node_id: NodeId;
  free_lists: FreeListHierarchy;
  slab_caches: Vec<SlabCacheRef>;
  remote_free_queue: MpmcQueue<PageHandle>;
  pressure_metrics: PressureSnapshot;

Own: arena, one arena owns exactly one node's pages (I9). Sync: free lists lock-striped by size class (P11); remote-free queue lock-free (ADR-08). Persist: reconstructed from page-descriptor scan on restart, not independently persisted. Wire: internal only. Compat: n/a — process-local, rebuilt each boot.

MigrationTask:
  task_id: TaskId;
  source_node: NodeId;
  target_node: NodeId;
  page_list: Vec<PageHandle>;
  priority: MigrationPriority;
  enqueue_ts: MonotonicNs;

Own: migration::queue, single-writer-enqueue / single-worker-dequeue per priority band. Sync: bounded MPMC queue (P2, I2). Persist: task lifecycle events appended to WAL for replay of migration decisions. Wire: internal; task IDs referenced in telemetry (migration.task_id). Compat: additive fields only.

ReplayRecord:
  sequence: u64;
  thread_id: ThreadId;
  event_type: EventType;
  node_id: NodeId;
  allocation_size: u32;
  latency_ns: u32;

Own: replay::record, append-only, one writer per node shard. Sync: monotonic sequence enforced at append (I5). Persist: this is the WAL record — the unit of durability. Wire: fixed binary layout (ADR-05), versioned header. Compat: major-version-pinned (§25); minor versions add optional trailing fields only.

AllocationRequest:
  size_class: SizeClass;
  alignment: u32;
  numa_policy: NumaPolicy;
  preferred_node: NodeId;
  migration_allowed: bool;
  hugepage_allowed: bool;
  locality_generation: u32;

Own: caller-constructed, consumed once by runtime-api::malloc_api. Sync: stack-local, no shared mutability. Persist: not persisted directly; outcome recorded via ReplayRecord. Wire: crosses the runtime-api boundary, ABI-stable (ADR-05, §25). Compat: additive fields with default values only.

Compatibility guarantees (all types above): additive schema evolution only; reserved fields mandatory in every #[repr(C)] struct; replay format version pinned by major release (§25); a metadata migration tool is required before any layout change ships.

12.2 Detailed Implementation Steps

  • Cargo.toml workspace manifest declaring all 15 member crates (ADR-15); rust-toolchain.toml pins the exact compiler (ADR-19).
  • allocator-core/src/lib.rs: AllocatorError enum (TopologyFault, Corruption, Exhaustion, PolicyReject, MigrationFailed) and ID newtypes NodeId(u16), ArenaId(u32), PageHandle(u64) — signatures only, per §11.

  • replay/src/lib.rs: stub ReplayRecord (§11) and a NullSink satisfying P6 before a real WAL exists.

  • .github/workflows/ci.yml: build + cargo test --workspace + cargo-vet dependency check (ADR-03).
  • TOML config loader (ADR-15-adjacent tooling choice), loaded once at startup and treated as immutable thereafter (P1 anchor).

12.3 Deliverable

A workspace that builds all 15 crates as empty-bodied public-API stubs; cargo build --workspace succeeds; CI pipeline green; the simulator scaffold runs a zero-assertion smoke pass.

12.4 Acceptance Criteria

  • Cold cargo build --workspace completes in < 90 s on a 16-core CI runner.
  • All 15 crates from §10 present with a compiling manifest and crate root.
  • cargo test --workspace exits 0 with ≥ 1 smoke test per crate (≥ 15 total).
  • fixtures/bootstrap/workspace_manifest_missing_crate.toml causes CI to fail fast with a named missing-crate diagnostic, never a silent skip.

12.5 Conformance Fixtures

  • fixtures/bootstrap/workspace_manifest_valid.toml — golden manifest; expected: clean build.
  • fixtures/bootstrap/workspace_manifest_missing_crate.toml — malformed; expected: CI fails fast with a named diagnostic.
  • fixtures/bootstrap/config_default.toml — replay of default config load; expected: byte-identical Config struct across 100 reloads (determinism smoke test, P1).

12.6 Pitfalls

  1. Workspace-wide feature unification silently enabling unsafe-gated features early — manifestation: cargo-geiger count nonzero in Phase 0; root cause: shared feature flags across crates; debugging: cargo tree -e features; signal: ADR-17 gate fails in CI; recovery: split feature flags per crate.
  2. CI runners lacking perf_event_open capability silently skip topology jobs; root cause: missing CAP_PERFMON in the runner container; debugging: inspect the perf.yml job log; signal: job reports 0 tests run, not a failure; recovery: assert nonzero test count explicitly in the job.
  3. Simulator scaffold reads wall-clock time instead of a fixed seed; root cause: placeholder Instant::now() call; debugging: diff two simulator runs; signal: non-reproducible smoke output; recovery: force an injected MonotonicNs source (ADR-20).

12.7 Performance Concerns

Workspace compile-time growth as crates accumulate — mitigated with sccache in CI; this is a developer-iteration concern, not a runtime one. No allocation-path performance concerns exist yet: Phase 0 introduces zero hot-path code.

12.8 Edge Cases

  • NodeId/ArenaId value 0 reserved as an "unset" sentinel, never a valid runtime ID (validated starting Phase 1).
  • Config file absent at startup falls back to a documented built-in default, never a panic.
  • Single-NUMA-node development hosts must still pass the simulator's zero-assertion smoke run.

12.9 Failure Analysis

A Phase 0 failure is always a build/CI failure, never a runtime allocator failure — no allocator exists yet. Blast radius is contained to CI; production impact is impossible. Detection: CI status. Containment: branch protection blocks merge on ci.yml failure. Recovery: fix and re-push; no rollback procedure is needed since nothing is deployed.

12.10 Operational Notes

Metrics: none emitted yet — telemetry exists only as a no-op sink. Tracing spans: bootstrap. workspace_init (single span, verifies P7 wiring end to end). Structured-log fields: crate_name, build_profile. Deployment: none — Phase 0 produces no deployable artifact, only a CI-verified skeleton.

13. Phase 1 — Topology Discovery Foundation

13.1 Objectives

Implement canonical NUMA topology discovery and normalization: parse firmware topology data, validate it against the CPU map, and publish an immutable snapshot every later phase reads (I12). Introduces the startup-latency constraint (< 250 ms, §4) and the degraded-mode fallback (P12).

13.2 Detailed Implementation Steps

  • topology/src/srat.rs: ACPI SRAT parser (ACPI Specification, Section 5.2.16) producing per-node CPU and memory-range entries.
  • topology/src/slit.rs: ACPI SLIT parser (ACPI Specification, Section 5.2.17) producing the node distance matrix referenced by I8 and §4's 1.3×–4.5× penalty assumption.
  • topology/src/cpu_map.rs: cross-references SRAT CPU entries against /sys-equivalent CPU affinity data; flags any CPU referenced by SRAT but absent from the live CPU map.
  • topology/src/validator.rs: startup validation pass — distance-matrix symmetry check, CPU-mask completeness check; failure here triggers degraded mode (P12, I12).
  • topology/src/node.rs: NodeDescriptor (§11) construction and the arena-set assignment each node gets before arena (Phase 2) exists to consume it.
  • topology/src/snapshot.rs: publishes the immutable post-validation snapshot via Arc, satisfying the read-without-locks pattern from McKenney & Slingwine 1998 (RCU-style immutable read path).
  • Synthetic topology generator (for conformance) and the first fuzz/fuzz_targets/topology.rs target.

13.3 Deliverable

A runnable topology-discovery binary (cli-tools::topology_dump) that parses a real or synthetic SRAT/ SLIT pair and prints the normalized node graph plus a validation verdict.

13.4 Acceptance Criteria

  • Parses topologies with 1–64 NUMA nodes (§4 ceiling) without reallocation past a preallocated bound.
  • Rejects fixtures/topology/malformed_srat_missing_node.bin with AllocatorError::TopologyFault, not a panic.
  • Cold startup discovery completes in < 250 ms for a 64-node synthetic topology (§4).
  • fuzz/fuzz_targets/topology.rs runs 24 h without a crash or an unbounded-memory finding.

13.5 Conformance Fixtures

  • conformance/topology/topology_dual_socket.json — 2-node golden fixture; expected: clean parse, symmetric distance matrix.
  • conformance/topology/topology_quad_socket.json — 4-node golden fixture with asymmetric NPS4 distances; expected: clean parse, validator accepts asymmetry within the 1.3×–4.5× band.
  • conformance/topology/malformed_srat_missing_node.bin — SRAT references a CPU absent from the CPU map; expected: validator rejection, degraded mode entered, topology_fault telemetry emitted.

13.6 Pitfalls

  1. BIOS/firmware inconsistencies between SRAT and the live CPU map on hot-pluggable hardware — manifestation: validator false-positive rejection; root cause: firmware published a superset of physically present CPUs; debugging: diff SRAT dump against cpu_map.rs output; signal: rejection rate spikes only on specific hardware SKUs; recovery: treat absent-but-SRAT-listed CPUs as Reserved, not fatal.
  2. Asymmetric distance matrices on NPS4-style AMD topologies misread as corruption — root cause: validator's initial symmetry assumption was too strict; debugging: compare against vendor-published distance tables; signal: rejection only on AMD EPYC NPS4; recovery: relax symmetry check to a tolerance band, not exact equality.
  3. CPU hotplug races during startup validation — manifestation: intermittent validator failure; root cause: CPU map read mid-hotplug event; debugging: replay conformance/topology fixtures with a simulated hotplug injection; signal: non-reproducible locally, reproducible under simulator; recovery: snapshot the CPU map once, atomically, before validation begins.
  4. Sparse CPU masks on memory-only ("CPU-less") NUMA nodes misclassified as invalid — root cause: validator assumed every node has ≥ 1 CPU; recovery: add explicit memoryless: bool to NodeDescriptor rather than rejecting the node.

13.7 Performance Concerns

Topology parsing allocations must be bounded and preallocated (64-node ceiling known at startup, §4); unbounded per-entry heap allocation during SRAT parsing would blow the 250 ms startup budget on large topologies. Cacheline alignment of the node-map array matters because every subsystem reads it on the hot path (I12) — misalignment causes cross-cacheline reads on every lookup.

13.8 Edge Cases

  • Zero-distance anomalies (a node reporting distance 0 to a non-self node) — rejected as malformed, not silently clamped.
  • Memoryless NUMA nodes (CPU-only, e.g. some accelerator topologies) — modeled explicitly, never dropped from the node set.
  • Sparse or non-contiguous CPU masks — validated per-bit, not assumed contiguous.

13.9 Failure Analysis

Topology corruption is detected at startup and forces the allocator into degraded mode (P12): every allocation for that process lifetime is marked non-optimized (no placement scoring, uniform round-robin across nodes). Blast radius is process-wide but latency-bounded — never a crash. Containment: degraded mode is a tested, first-class state (§7 methodology), not an error path. Recovery: process restart with corrected firmware/CPU-map data; no in-place topology repair is attempted (P3).

13.10 Operational Notes

Metrics: topology.checksum, topology.node_distance_p99, topology.parser_failures. Tracing spans: topology.discover, topology.validate. Structured-log fields: node_count, validation_verdict, degraded_mode: bool. Deployment: no rollback path needed — topology is re-derived every boot, not migrated across versions.

14. Phase 2 — Page Allocator Core

14.1 Objectives

Implement the node-local physical page allocator: descriptor table, free-list hierarchy, and the allocation fast path with remote fallback. Introduces the first unsafe code (P10) and the first real lock-contention surface (P11). Establishes p50 < 120 ns and remote-ratio < 8 % as measured, not aspirational, targets (§4).

14.2 Detailed Implementation Steps

  • allocator-core/src/page.rs: PageDescriptor (§11) table, indexed by physical address, sized to the 64 TB / 4 KB page ceiling from §4; ownership transitions via atomic CAS on owner+state (P5, I1).
  • allocator-core/src/freelist.rs: per-node, per-size-class intrusive free-list hierarchy — design informed by Evans 2006's extent management and Berger et al. 2000's per-thread-heap fallback ordering.
  • allocator-core/src/lockstripe.rs: lock striping across free-list shards, applying Calciu et al. 2013's node-partitioned cohorting to keep cross-socket cache-line traffic off the fast path (P11).
  • arena/src/remote_free.rs: lock-free MPMC remote-free queue (Michael & Scott 1996, ADR-08), bounded per I2/P2.
  • allocator-core/src/checksum.rs: per-descriptor checksum (I3) and poison-pattern fill on free.
  • Allocation fast path: Thread Cache → Arena → Node Page Allocator → Remote Node Fallback → OOM Handler (§8 sequence), implemented without a hugepage step yet (that arrives in Phase 4).
  • benchmarks/alloc_latency.rs: Criterion harness measuring p50/p95/p99 against §4 targets.

14.3 Deliverable

A functional page allocator: cli-tools can drive a synthetic allocation/free workload against it and report locality and latency percentiles.

14.4 Acceptance Criteria

  • p50 allocation latency < 200 ns under single-threaded microbenchmark (tightens to the < 120 ns §4 target once Phase 3's slab fast path is in place).
  • Zero corruption findings across a 10M-operation stress run using conformance/allocator/ fragmented_pages.bin as the initial arena state.
  • Remote-allocation ratio < 8 % under a node-local-biased synthetic workload (§4).
  • Replay reconstruction from conformance/allocator/remote_alloc_replay.bin matches live state exactly.

14.5 Conformance Fixtures

  • conformance/allocator/fragmented_pages.bin — pre-fragmented arena state; expected: allocator degrades gracefully, fragmentation stays < 18 % (§4) rather than failing allocation.
  • conformance/allocator/remote_alloc_replay.bin — recorded remote-fallback sequence; expected: deterministic replay reconstructs identical ownership state (I1, I5).
  • fixtures/allocator/aba_race_injection.bin — replay case injecting a delayed free between CAS read and write; expected: generation counter (I10) prevents ABA reuse.

14.6 Pitfalls

  1. ABA corruption on the remote-free queue under high churn — manifestation: a freed page reused while a stale reference still holds it; root cause: pointer reuse without a generation check; debugging: replay fixtures/allocator/aba_race_injection.bin under the simulator; signal: generation. wrap_near_miss telemetry; recovery: generation counter bump on every ownership transition (I10).
  2. Free-list cycles from a double-insert bug — manifestation: allocator livelocks walking a cyclic free list; root cause: insert path not idempotent under a race; debugging: cycle detector in the simulator's assertion for I1; recovery: quarantine + arena rebuild (P3).
  3. Cacheline bouncing on the shared remote-free queue head under many-writer contention — manifestation: p99 latency spikes under 32+ thread fan-in; root cause: single queue head cacheline hot across sockets; debugging: perf c2c cacheline-contention report; recovery: per-source-node remote-free sub-queues (extends ADR-08's queue design).

14.7 Performance Concerns

TLB pressure from scattered page allocation defeats locality gains even when the node choice is correct — track via perf stat TLB-miss counters. False sharing between adjacent PageDescriptor entries in the table is a documented mimalloc-class pitfall; pad or batch descriptors to cacheline boundaries. Lock-hold time on any free-list shard must stay under the 3 µs ceiling (§4, I7 methodology).

14.8 Edge Cases

  • Exhausted local node with remote nodes available — must fall back per the §8 sequence, never return OOM prematurely.
  • Corrupted free list detected mid-walk — abort the walk, quarantine the arena (P3), never attempt partial repair.
  • Concurrent free of the same PageHandle from two threads (embedder bug) — must be detected via I1's ownership check and rejected, not silently double-freed.

14.9 Failure Analysis

Detected corruption (checksum mismatch, I3) triggers arena quarantine: the affected arena stops serving new allocations, in-flight allocations drain, and the arena rebuilds from the last verified snapshot + WAL replay (RTO < 60 s, §4). Blast radius is contained to the affected node's arena; other nodes continue serving. Operator visibility: allocator.quarantine_active{node_id} gauge.

14.10 Operational Notes

Metrics: alloc.locality_ratio, alloc.remote_ratio, alloc.lock_contention_ns, alloc.p50/p95/p99. Tracing spans: alloc.fastpath, alloc.remote. Structured-log fields: node_id, size_class, fallback_reason. Rollback: an allocator-core version bump requires the metadata-migration tool (§11) before a rolling upgrade proceeds.

15. Phase 3 — Slab Allocator

15.1 Objectives

Implement the NUMA-aware small-object slab subsystem sitting above the page allocator: size classes, per-thread magazines, and remote-free batching. Targets p99 small-object allocation < 1 µs and fragmentation < 15 % (tighter than §4's 18 % system ceiling, since slab is the dominant allocation path).

15.2 Detailed Implementation Steps

  • slab/src/sizeclass.rs: size-class table following Bonwick 1994's object-caching model — fixed classes, not first-fit, to keep the fast path branch-free.
  • slab/src/magazine.rs: per-thread magazine cache with depot refill, directly applying Bonwick & Adams 2001's magazine layer over arena's shared free lists (P11 anchor: magazines eliminate per-allocation lock acquisition on the fast path).
  • slab/src/cache.rs: slab metadata (checksum per I3), slab-to-arena binding, quarantine-on-corruption hook shared with Phase 2's arena quarantine path.
  • slab/src/aging.rs: slab aging/eviction so long-idle slabs return pages to the node page allocator rather than pinning fragmented capacity indefinitely.
  • Remote-free batching: instead of Phase 2's per-page remote-free enqueue, slab batches frees by source thread before enqueueing (reduces queue contention per Michael & Scott 1996's amortization guidance).
  • Allocation sampling hook for telemetry (every Nth allocation records a full stack-free stack trace for later fragmentation/leak analysis).

15.3 Deliverable

A small-object allocator layered over Phase 2's page allocator, swappable in place of the raw page path for allocations below the hugepage threshold.

15.4 Acceptance Criteria

  • p99 small-object (≤ 4 KB) allocation latency < 1 µs under an 8-thread contended microbenchmark.
  • Fragmentation < 15 % after a 1-hour churn-heavy synthetic workload (fixtures/slab/churn_1h.bin).
  • Zero corruption findings across fixtures/slab/magazine_refill_race.bin replayed 1000×.

15.5 Conformance Fixtures

  • fixtures/slab/churn_1h.bin — recorded high-churn alloc/free sequence; expected: fragmentation stays below 15 % throughout, not just at steady state.
  • fixtures/slab/magazine_refill_race.bin — concurrent refill-from-depot race; expected: no double- issued object, no lost object (I1 extended to slab granularity).
  • fixtures/slab/oversized_object_reject.bin — allocation request above the largest size class; expected: rejected to the page allocator path, not silently truncated.

15.6 Pitfalls

  1. Freelist poisoning pattern mismatched between slab and page allocator layers — manifestation: false- positive corruption alerts; root cause: two independent poison-byte conventions; debugging: compare slab::cache and allocator-core::checksum poison constants; recovery: single shared poison-pattern constant.
  2. Remote-free storms when a thread migrates across sockets mid-run (e.g. after a scheduler rebalance) — manifestation: sudden queue-depth spike on one node; root cause: the thread's magazine still holds objects from its old node; debugging: correlate sched_getcpu migration events with remote_free. queue_depth; recovery: magazine flush-on-migration hook (feeds into Phase 5's policy engine).
  3. Branch misprediction in size-class lookup on skewed allocation-size distributions — manifestation: p99 latency regression despite low contention; root cause: size-class table lookup not sorted by observed frequency; debugging: perf record branch-miss annotation; recovery: reorder size-class table by production allocation-size histogram.

15.7 Performance Concerns

Branch prediction in the size-class dispatch is the single largest fast-path cost after lock elimination (mimalloc's page.c establishes this pattern). Allocator cache misses on magazine refill from depot are amortized by refilling in batches (Bonwick & Adams 2001), not one object at a time. Slab metadata checksum computation must stay off the fast-free path — computed lazily on refill, not on every free.

15.8 Edge Cases

  • Oversized objects (above largest size class) — routed to the page allocator directly, never forced into an ill-fitting slab.
  • Slab exhaustion with the depot also empty — triggers a page-allocator refill request, and if that fails, AllocatorError::Exhaustion, never a silent block.
  • A thread exits while its magazine still holds live objects — magazine contents return to the depot, not leaked.

15.9 Failure Analysis

Slab corruption (checksum mismatch) quarantines the individual slab, not the whole arena — a narrower blast radius than Phase 2's page-level quarantine, since slab corruption is more localized. Recovery: affected slab's live objects are presumed suspect and the slab is rebuilt from the page allocator; telemetry flags which size class was affected for postmortem correlation.

15.10 Operational Notes

Metrics: slab.fragmentation_ratio, slab.magazine_hit_rate, slab.refill_latency_ns, slab. checksum_fail. Tracing spans: slab.refill, slab.alloc_fastpath. Dashboards: slab occupancy by size class. Structured-log fields: size_class, magazine_state.

16. Phase 4 — Hugepage Manager

16.1 Objectives

Implement explicit 2 MB / 1 GB hugepage reservation, replacing reliance on transparent hugepages (THP) for allocator-controlled determinism (ADR-23). Targets hugepage allocation latency < 50 µs and success ratio > 95 % (§4).

16.2 Detailed Implementation Steps

  • hugepage/src/reservation.rs: explicit hugetlbfs-backed reservation at startup, sized from a configured budget, never grown dynamically mid-run (predictability anchor: P1).
  • hugepage/src/alignment.rs: alignment validator enforcing I6 — every hugepage-backed allocation is 2 MB/1 GB aligned, checked before the mapping is handed to a caller.
  • hugepage/src/fallback.rs: transparent fallback to standard 4 KB pages when the hugepage pool is exhausted, recording the fallback reason for telemetry (never a silent downgrade).
  • Fragmentation accounting shared with allocator-core's page descriptor table, since a hugepage reservation removes 512 (2 MB) or 262144 (1 GB) 4 KB pages from the standard pool atomically.
  • Migration support hook: a Huge-state page (§8) must be migratable as a single unit, not split — this constrains Phase 6's migration engine design (Gaud et al. 2014's finding that hugepages amplify the cost of a wrong placement directly motivates why migration must handle hugepages as first-class units, not defer them).

16.3 Deliverable

2 MB and 1 GB hugepage allocation and reservation, integrated as a fallback step in the §8 allocation sequence ahead of remote-node fallback for large allocations.

16.4 Acceptance Criteria

  • Hugepage allocation success ratio > 95 % when the configured reservation pool is not exhausted (§4).
  • Hugepage allocation latency < 50 µs, measured via benchmarks/alloc_latency.rs extended with a hugepage-path mode.
  • 100 % of hugepage-backed allocations pass the hugepage::alignment validator in fixtures/hugepage/alignment_sweep.bin (10,000 allocations at randomized sizes).

16.5 Conformance Fixtures

  • fixtures/hugepage/alignment_sweep.bin — 10,000 randomized-size allocation requests; expected: every hugepage-backed result is 2 MB/1 GB aligned, no exceptions.
  • fixtures/hugepage/pool_exhaustion_fallback.bin — reservation pool exhausted mid-run; expected: transparent fallback to 4 KB pages, hugepage.fallback telemetry emitted, no allocation failure.
  • fixtures/hugepage/mixed_page_size_replay.bin — interleaved 4 KB/2 MB/1 GB allocations; expected: fragmentation accounting stays consistent across all three page sizes.

16.6 Pitfalls

  1. Hugepage fragmentation from partial pool exhaustion — manifestation: success ratio drops below 95 % despite apparently free capacity; root cause: free hugepages exist but are the wrong size class (2 MB free, 1 GB requested); debugging: hugepage.pool_state dump by size class; recovery: size-class-aware reservation budgeting, not a single pooled counter.
  2. TLB shootdown amplification when migrating a hugepage-backed region — manifestation: migration of a single 1 GB page causes a system-wide TLB shootdown storm; root cause: naive whole-region invalidation (per Gaud et al. 2014's finding); debugging: perf stat -e tlb_flush; recovery: batch shootdowns across concurrent migration tasks rather than one per page (feeds Phase 6 design).
  3. Page-split overhead when a hugepage-backed allocation is freed partially — manifestation: unexpected latency spike on free; root cause: the allocator attempted a partial-region free, which requires splitting the hugepage; recovery: forbid partial free of a hugepage-backed allocation at the API level (§11 AllocationRequest.hugepage_allowed is all-or-nothing).

16.7 Performance Concerns

Page-split overhead (see Pitfall 3) is avoided entirely by design rather than optimized, since Gaud et al. 2014 shows splitting cost on NUMA systems is non-linear with distance. Reservation-time zero-fill avoidance (MAP_HUGETLB without pre-zeroing where the kernel allows deferred zero-fill) keeps the < 50 µs allocation-latency target achievable.

16.8 Edge Cases

  • Mixed page sizes within one arena — fragmentation accounting must track each size class independently, never a single blended ratio.
  • A reservation request larger than any single NUMA node's memory (§4 per-node ceiling) — rejected at request time, never silently spread across nodes without a policy decision (that's Phase 5's job).
  • Hugepage pool configured to zero at startup (operator disabled hugepages) — allocator must run correctly with 100 % standard-page fallback, not treat this as a fault.

16.9 Failure Analysis

Hugepage exhaustion is not a fault — it is an expected, telemetered fallback path (P12-adjacent: fail toward the safe standard-page behavior, not toward an allocation failure). Genuine failure is an alignment violation (I6), which quarantines the specific reservation and forces standard-page fallback for that request only — blast radius is one allocation, not the whole pool.

16.10 Operational Notes

Metrics: hugepage.success_ratio, hugepage.fallback_count, hugepage.pool_state{size_class}. Tracing spans: hugepage.reserve, hugepage.fallback. Structured-log fields: requested_size_class, fallback_reason. Deployment: hugepage pool sizing is a per-host operator configuration, not baked into the binary — a rolling upgrade must not change the reservation semantics without a documented migration note (§25).

17. Phase 5 — NUMA Policy Engine

17.1 Objectives

Implement placement heuristics: locality scoring, preferred-node selection, and balancing thresholds that consume topology distance data (§13) without ever allocating memory directly (P5). Targets a 40 % reduction in remote accesses relative to a naive round-robin placement baseline.

17.2 Detailed Implementation Steps

  • policy/src/scoring.rs: locality-score function combining topology distance (I8), thread ownership history, and current pressure signals (Lameter's NUMA overview framing informs the distance-weighted scoring model); emits a directive, never allocates (P5 anchor).
  • policy/src/affinity.rs: thread-affinity inheritance — a spawned thread inherits its parent's preferred-node hint unless explicitly overridden via the runtime-api policy-override endpoint.
  • policy/src/balancing.rs: balancing thresholds that trigger a migration recommendation (not action) when a node's allocation share deviates > 10 % from even distribution (§4 NUMA imbalance target).
  • Workload classification: a lightweight heuristic distinguishing steady-state from bursty allocation patterns, since a bursty workload should not trigger the same balancing aggressiveness as a steady one (avoids the oscillation pitfall below).
  • Policy trace emission: every scoring decision recorded with its inputs, enabling P1-style replay of why a placement was chosen, distinct from Phase 8's allocator-event WAL.
  • PhaseDeferred("§17") — ML-guided placement scoring (register in §35): the scoring function stays a fixed heuristic in v1; a learned model is an explicit un-defer trigger, not a silent future swap.

17.3 Deliverable

An adaptive placement layer: policy directives consumed by allocator-core's allocation fast path (Phase 2) and migration's task queue (Phase 6), inspectable via policy-trace dumps.

17.4 Acceptance Criteria

  • Remote-access ratio reduced by ≥ 40 % versus round-robin baseline on fixtures/policy/ mixed_workload_8node.bin.
  • Scoring overhead adds < 50 ns to the allocation fast path (bounded fraction of the p50 120 ns budget, §4).
  • Zero oscillation events (a node flip-flopping preferred-status more than 3× in 60 s) across a 1-hour soak using fixtures/policy/oscillation_stress.bin.

17.5 Conformance Fixtures

  • fixtures/policy/mixed_workload_8node.bin — recorded 8-node allocation pattern with known-optimal placement; expected: scoring converges to within 5 % of optimal remote-ratio.
  • fixtures/policy/oscillation_stress.bin — adversarial workload designed to flip preferred-node scoring; expected: balancing thresholds include hysteresis, no flip-flopping.
  • fixtures/policy/conflicting_affinity.bin — two threads with explicit, contradictory pinning hints on the same allocation path; expected: deterministic tie-break (lower ThreadId wins), not nondeterministic.

17.6 Pitfalls

  1. Oscillating policies where two nodes repeatedly trade "preferred" status — manifestation: migration engine (Phase 6) receives contradictory recommendations within seconds; root cause: balancing threshold has no hysteresis band; debugging: replay fixtures/policy/oscillation_stress.bin; signal: policy.recommendation_flip_count spikes; recovery: add a minimum-dwell-time hysteresis before a new recommendation can reverse the previous one.
  2. Migration thrashing induced by overly aggressive balancing thresholds during a legitimately bursty workload — root cause: workload classification misclassified a burst as sustained imbalance; debugging: correlate policy.workload_class with migration.task_enqueue_rate; recovery: require sustained imbalance across N consecutive scoring windows before recommending migration.
  3. Scoring overhead creeping onto the fast path as more signals are added — manifestation: p50 latency regresses past 120 ns; root cause: scoring called synchronously inside the allocation path rather than precomputed per-epoch; recovery: precompute per-node scores once per epoch, allocation path reads a cached score.

17.7 Performance Concerns

Scoring must be O(1) on the allocation fast path — any per-allocation graph walk over the distance matrix violates the p50 budget. Precomputation per topology-epoch (triggered only on I12 snapshot change, which is rare) amortizes the cost. Policy-trace emission uses the same lock-free ring buffer pattern as I13 to avoid blocking.

17.8 Edge Cases

  • Conflicting explicit affinities from two cooperating threads — deterministic tie-break, never a race- dependent outcome (fixtures/policy/conflicting_affinity.bin).
  • A topology snapshot change (I12 violation recovery path, rare) mid-scoring-epoch — scoring must detect the epoch boundary and recompute, never score against a stale snapshot.
  • Single-node topology (no NUMA effects possible) — policy engine must degrade to a no-op scorer, not error out.

17.9 Failure Analysis

A policy-engine failure (e.g. a scoring panic) must never propagate to the allocation fast path — the allocator falls back to round-robin placement and telemetry flags policy.disabled. Blast radius: locality degrades, but allocation itself never fails, since P5 keeps the policy engine strictly advisory. Recovery: restart the policy subsystem in isolation; no arena rebuild required.

17.10 Operational Notes

Metrics: policy.remote_ratio_delta, policy.recommendation_flip_count, policy.scoring_latency_ns. Tracing spans: policy.score, policy.recommend. Structured-log fields: workload_class, recommended_node, dwell_time_ms. Policy traces are exposed via runtime-api::diagnostics for live operator inspection.

18. Phase 6 — Migration Engine

18.1 Objectives

Implement asynchronous, rate-limited page migration that acts on Phase 5's recommendations: queueing, worker execution, heatmap-driven prioritization, and rollback on failure. Targets migration failure rate < 0.1 % and bandwidth-safe rate limiting (< 1 % CPU overhead, §4).

18.2 Detailed Implementation Steps

  • migration/src/queue.rs: bounded priority queue of MigrationTask (§11), rate-limited per I2/P2, fed by Phase 5's balancing recommendations, never by direct application code.
  • migration/src/heatmap.rs: page access-frequency heatmap (sampled, not exhaustive) determining which cold pages are cheap to leave and which hot pages justify migration cost — this is the layer where Gaud et al. 2014's hugepage-migration-cost finding is operationalized: hugepage-backed hot pages get a cost multiplier before being queued.
  • migration/src/worker.rs: migration worker pool executing the state machine (§8): Candidate → Queued → Copying → Remapping → Verified → Complete, using move_pages(2)/migrate_pages(2) under the unsafe boundary (P10).
  • migration/src/rollback.rs: rollback path for Failed transitions — restores the original mapping and requeues the task at lower priority, never silently drops it.
  • Dirty-page validation before Remapping: a page written to during Copying invalidates the copy and restarts the task rather than committing a stale copy (this is the single most safety-critical check in the state machine).
  • PhaseDeferred("§18") — CXL memory-tiering-aware migration cost model (register in §35): v1 treats all DRAM nodes uniformly; CXL-attached memory's different bandwidth/latency profile is an explicit un-defer trigger.

18.3 Deliverable

Online locality repair: a background subsystem that measurably reduces remote-allocation ratio over time on a running process without operator intervention, inspectable via migration dashboards.

18.4 Acceptance Criteria

  • Migration failure rate < 0.1 % across fixtures/migration/sustained_repair_1h.bin.
  • Migration scheduling overhead stays < 1 % CPU (§4) measured via perf stat during the same fixture.
  • 100 % of Pinned-state pages in fixtures/migration/pinned_page_reject.bin are correctly rejected before entering Candidate (I4 enforcement).

18.5 Conformance Fixtures

  • fixtures/migration/sustained_repair_1h.bin — 1-hour recorded workload with induced locality drift; expected: remote-ratio trends downward, failure rate < 0.1 %.
  • fixtures/migration/pinned_page_reject.bin — migration recommendation targeting a Pinned page; expected: rejected pre-queue, migration.pin_violation telemetry (I4).
  • fixtures/migration/dirty_page_during_copy.bin — a write races the Copying state; expected: task restarts, no stale copy committed, no data loss.

18.6 Pitfalls

  1. Migration storms where many tasks queue simultaneously after a topology or workload shift — manifestation: bandwidth collapse, other allocator operations stall; root cause: rate limiter applies per-task, not globally; debugging: migration.queue_depth + perf stat -e mem_bw; recovery: global token-bucket rate limiter shared across all migration workers, not per-worker.
  2. Stale mappings after a migration completes but the caller's cached pointer wasn't invalidated — manifestation: caller reads from the old physical location transiently; root cause: Remapping and caller notification aren't atomic; debugging: replay fixtures/migration/dirty_page_during_copy.bin; recovery: Verified state gate ensures no Complete transition until all references are confirmed updated.
  3. Rollback loop where a repeatedly-failing task is retried indefinitely at the same priority — manifestation: one bad page starves the queue; root cause: rollback requeues without backoff; recovery: exponential backoff with a max-retry-then-abandon policy, surfaced to telemetry for operator review.

18.7 Performance Concerns

Bandwidth collapse is the dominant risk: migration competes with application memory traffic for the same inter-socket interconnect. The global rate limiter (Pitfall 1's fix) must be tuned against the measured cross-node bandwidth ceiling from §4's NUMA assumptions, not a fixed constant. TLB shootdown batching (carried over from Phase 4) applies here at scale — batch shootdowns across concurrently completing tasks.

18.8 Edge Cases

  • A page pinned during an in-flight migration (race between pin request and Copying) — the pin request must block until the current task resolves, or abort the task, never leave an ambiguous state.
  • Target node becomes unavailable (hotplug removal) mid-migration — task transitions to Failed, rolls back to source, never partially commits to a vanished node.
  • Hugepage-backed page migration (Phase 4 constraint: whole-unit only) — the state machine must treat a 1 GB page as one task, never split it mid-migration.

18.9 Failure Analysis

A migration failure is contained to the single task — the source page's ownership never leaves the source node until Verified succeeds, so a failed migration leaves the system exactly where it started (P3 crash-only semantics applied at task granularity, not process granularity). Forensics: the full state- machine transition history for a task is in the replay WAL (§20), enabling exact reconstruction of what was attempted and where it diverged.

18.10 Operational Notes

Metrics: migration.task_success_rate, migration.queue_depth, migration.bandwidth_used_pct, migration.rollback_count. Tracing spans: migration.execute, migration.rollback. Dashboards: migration pressure, locality-repair trend line. Structured-log fields: task_id, source_node, target_node, final_state.

19. Phase 7 — Reclaim and Pressure Handling

19.1 Objectives

Implement memory-pressure detection and reclaim: cold-page scanning, pressure propagation, and emergency reclaim under cgroup v2 memory-controller limits (§4 deployment assumption). Targets stability under synthetic pressure without triggering an OOM kill.

19.2 Detailed Implementation Steps

  • reclaim/src/scanner.rs: cold-page detection using the heatmap infrastructure shared with Phase 6 (migration::heatmap), scanning at a rate bounded to avoid competing with the allocation fast path.
  • reclaim/src/pressure.rs: pressure-signal propagation from the cgroup v2 memory controller (memory.pressure, per the cgroup-v2 RFC in §5) into arena::pressure_metrics (§11).
  • reclaim/src/throttle.rs: allocator throttling under sustained pressure — new allocations are delayed (not rejected) proportionally to pressure severity, applying P8's bounded-tail-latency principle even under duress: throttling has its own p99 budget, it does not become unbounded.
  • Emergency reclaim path: a last-resort synchronous reclaim triggered only when throttling has failed to relieve pressure within a bounded window — explicitly distinguished from the normal async scanner path (I11 enforcement: never reclaims a Pinned or Migrating page even under emergency pressure).
  • Reclaim queue: bounded (P2), feeding page-state transitions back into allocator-core::page (Phase 2).
  • PhaseDeferred("§19") — persistent-memory-aware reclaim policy (register in §35): v1 treats all reclaimed memory as uniform DRAM; PMEM's asymmetric write cost is an explicit un-defer trigger.

19.3 Deliverable

A pressure-resilient allocator: stays within cgroup v2 memory limits under sustained allocation pressure without an OOM kill, verified against a synthetic pressure-generation harness.

19.4 Acceptance Criteria

  • Stable (no OOM kill, no crash) across fixtures/reclaim/sustained_pressure_2h.bin at 95 % of the cgroup memory.max limit.
  • Emergency reclaim activation rate < 1 per hour under the same fixture (throttling should resolve pressure before emergency reclaim is needed in the common case).
  • Zero I11 violations (reclaim of a Pinned/Migrating page) across 10M scanner cycles in fixtures/reclaim/state_conflict_stress.bin.

19.5 Conformance Fixtures

  • fixtures/reclaim/sustained_pressure_2h.bin — 2-hour recorded workload approaching the cgroup limit; expected: throttling engages, no OOM kill, pressure stabilizes.
  • fixtures/reclaim/state_conflict_stress.bin — scanner races against concurrent pinning/migration; expected: zero I11 violations, all conflicts resolved by skip-and-requeue.
  • fixtures/reclaim/global_pressure_collapse.bin — adversarial fixture driving pressure past the emergency-reclaim threshold; expected: emergency path activates, system remains responsive (bounded p99, not frozen).

19.6 Pitfalls

  1. Reclaim oscillation where the scanner reclaims a page just before it would have been reused locally — manifestation: reclaimed memory immediately re-requested from a remote node, worsening locality; root cause: scanner's coldness threshold too aggressive relative to access-pattern periodicity; debugging: correlate reclaim.page_reclaimed timestamps against subsequent alloc.remote_ratio spikes; recovery: raise the coldness dwell-time threshold, informed by the workload classification from Phase 5.
  2. Pressure propagation lag from the cgroup controller causing reactive-too-late throttling — manifestation: allocator only starts throttling after the limit is already breached; root cause: polling interval for memory.pressure too coarse; recovery: subscribe to the cgroup v2 pressure notification file descriptor (event-driven) rather than polling.
  3. Emergency reclaim scanning contending with the allocation fast path's lock striping — manifestation: p99 latency spike coincides with every emergency-reclaim activation; recovery: emergency reclaim takes a strictly bounded number of pages per pass and yields, never a single unbounded sweep.

19.7 Performance Concerns

Reclaim scanning cost must stay off the allocation fast path entirely — it runs on a dedicated background thread reading the same heatmap Phase 6 populates, avoiding duplicated instrumentation cost. Pressure- signal propagation latency directly bounds how early throttling can engage; an event-driven subscription (Pitfall 2's fix) is strictly better than any polling interval choice.

19.8 Edge Cases

  • Global pressure collapse (all nodes simultaneously near their limit) — emergency reclaim must not starve any single node disproportionately; fairness across nodes is required even under duress.
  • A page becomes cold, is queued for reclaim, then is immediately re-accessed before the scan completes — must be detected and dequeued, never reclaimed out from under an active reader.
  • cgroup limit lowered dynamically by an external operator mid-run — pressure propagation must react to the new limit within one propagation cycle, not require a restart.

19.9 Failure Analysis

Pressure escalation that outruns both throttling and emergency reclaim is the one scenario where the allocator may legitimately reject an allocation (AllocatorError::Exhaustion) rather than violate a memory limit — this is a deliberate, telemetered choice, not a crash. Forensics: reclaim.pressure_trace records the full escalation timeline (throttle engaged → emergency triggered → rejection) for postmortem.

19.10 Operational Notes

Metrics: reclaim.pressure_level, reclaim.throttle_delay_ns, reclaim.emergency_activations, reclaim.cold_pages_scanned. Tracing spans: reclaim.scan, reclaim.emergency. Structured-log fields: cgroup_limit_bytes, pressure_source. Pressure metrics are mandatory in every deployment — they cannot be disabled, per P7.

20. Phase 8 — Observability and Replay

20.1 Objectives

Implement full deterministic observability: structured logging, tracing spans, the replay WAL, and crash- dump support, making every prior phase's allocator state transition reconstructable after the fact (P1, P6). This phase turns the assertions used internally by every earlier phase's fixtures into an operator- facing capability.

20.2 Detailed Implementation Steps

  • replay/src/wal.rs: append-only binary WAL (ADR-04, ADR-05) writing ReplayRecord (§11) for every allocation, free, migration, and reclaim state transition, with monotonic per-node sequencing (I5).
  • replay/src/record.rs: the fixed, versioned binary layout itself — a #[repr(C)] struct with a reserved-fields policy per §11's compatibility guarantee.
  • replay/src/reconstruct.rs: deterministic reconstruction — replays the WAL from a snapshot and produces allocator state identical to the live state at the recorded sequence number, the mechanism the §7 debugging methodology depends on.
  • telemetry/src/spans.rs: lock-free ring-buffer span emitter (I13) feeding OpenTelemetry (ADR-10) without blocking the fast path — spans named per the operational-notes convention established in every prior phase (alloc.fastpath, migration.execute, etc.).
  • Crash-dump support: ELF-format snapshot (ADR-19-adjacent tooling) captured on an unrecoverable panic, containing the last N WAL records plus the current metadata-subsystem state.
  • Deterministic timestamp source: CLOCK_MONOTONIC_RAW for intervals, a logical replay clock for ordering (ADR-20) — wall-clock time is never used to determine WAL ordering.

20.3 Deliverable

A replayable allocator: given a WAL segment and a starting snapshot, cli-tools::replay_inspect reconstructs and displays the full allocator state at any recorded sequence number.

20.4 Acceptance Criteria

  • Replay determinism verified: 1000 independent replays of fixtures/replay/golden_1h_session.bin produce byte-identical reconstructed state.
  • WAL append overhead < 3 % of allocation-path latency (§4), measured via benchmarks/alloc_latency.rs with WAL enabled vs. disabled.
  • Crash-dump generation completes in < 5 s (matches the graceful-shutdown budget, §4) for a 64 TB resident-state process.

20.5 Conformance Fixtures

  • fixtures/replay/golden_1h_session.bin — 1-hour recorded session across all subsystems; expected: deterministic, byte-identical reconstruction across repeated replays.
  • conformance/replay/replay_basic.bin — minimal single-node allocate/free/migrate sequence; expected: smallest reproducible replay-correctness fixture, used in CI on every commit.
  • conformance/replay/malformed_wal.bin — a WAL segment with a sequence gap (I5 violation); expected: replay.sequence_gap detected, reconstruction falls back to last-verified snapshot, never silently skips the gap.

20.6 Pitfalls

  1. Excessive telemetry overhead once every subsystem's spans are enabled simultaneously — manifestation: fast-path latency creeps past the < 3 % WAL budget when spans are counted alongside it; root cause: span emission and WAL append compete for the same ring-buffer bandwidth; debugging: perf stat comparison of WAL-only vs. WAL+spans; recovery: separate ring buffers per concern, sized independently.
  2. WAL fsync amplification under high allocation rates — manifestation: p99 latency spikes correlate with fsync intervals; root cause: fsync-per-record is too conservative, fsync-never risks I5/RPO violation; recovery: batched fsync on a bounded interval matching the < 1 s RPO target (§4), not per-record.
  3. Replay divergence where reconstruction disagrees with recorded live-state telemetry — manifestation: a replayed state doesn't match what was observed live; root cause: a non-deterministic input (e.g. a stray wall-clock read) leaked into a decision path; debugging: bisect the WAL segment by sequence range until the divergence point is isolated; recovery: audit and remove the non-deterministic input, treat as a P1 violation bug.

20.7 Performance Concerns

WAL append and span emission are both lock-free ring-buffer writers (I13's pattern generalized) — any lock on this path would violate both P8 and the < 3 % WAL overhead budget. Batched fsync (Pitfall 2's fix) trades a small RPO increase for a large latency-variance reduction, tuned against the §4 RPO ceiling explicitly, not left as a free parameter.

20.8 Edge Cases

  • Partial WAL writes from a crash mid-append — the reconstruction path must detect a truncated final record (via a length-prefixed or checksum-terminated record format) and discard it, never interpret garbage as a valid record.
  • Clock skew between the monotonic latency clock and the logical replay clock after a suspend/resume cycle — the logical clock is unaffected (it's sequence-based, not wall-clock-based), which is exactly why ADR-20 rejected wall-clock ordering.
  • Replay of a WAL segment spanning a metadata-layout version boundary (§25) — reconstruction must detect the version header and either upgrade or refuse, never silently misinterpret field offsets.

20.9 Failure Analysis

Replay divergence (Pitfall 3) is the most severe failure category in this phase because it undermines every other phase's forensic guarantee — it is treated as a release-blocking defect, not a known issue. Detection: automated differential replay-vs-live comparison runs continuously in the soak environment (§26). Containment: a divergence-triggering WAL segment is preserved verbatim for offline bisection.

20.10 Operational Notes

Metrics: replay.wal_append_latency_ns, replay.fsync_batch_size, telemetry.emit_stall_ns (I13). 21. Phase 9 — Conformance, Fuzzing & Production Hardening

21.1 Objectives

Close the loop: continuous fuzzing and differential replay testing (stress correctness across every prior phase), plus the operational hardening — canary deployment, rolling upgrades, chaos testing — that makes the system production-ready. This is the terminal phase; nothing downstream introduces new subsystems.

21.2 Detailed Implementation Steps

  • fuzz/fuzz_targets/allocator.rs and fuzz/fuzz_targets/metadata.rs: cargo-fuzz targets (ADR-13) exercising allocator-core and replay::record against corrupted/adversarial input, building on Phase 1's topology.rs target.
  • conformance differential harness: replays fixtures from every phase (§13–§20) against both the current build and the prior release build, flagging any behavioral divergence not explained by an ADR or a documented PhaseDeferred change.
  • Race injectors and synthetic-topology generators exercising the simulator (Phase 0 scaffold) at scale — this is where the per-invariant assertions from §7's methodology paragraph are run continuously, not just on demand.
  • Canary deployment tooling (scripts/run_fuzz.sh extended, plus release-channel gating from ADR-18): a new build serves a small traffic percentage under full telemetry before promotion.
  • Rolling-upgrade validation: two allocator versions running simultaneously in a soak environment, verifying the §25 one-major-version overlap compatibility guarantee holds under real traffic.
  • Chaos testing: forced OOM, migration interruption, lock starvation injection — verifying every subsystem's failure-analysis section (§13.9–§20.9) actually holds under combined, not isolated, fault injection.

21.3 Deliverable

A continuously-verified, production-hardened runtime: 72-hour soak-stable, canary-validated, rollback- tested, ready for the release process defined in §27.

21.4 Acceptance Criteria

  • 72-hour soak stability with zero invariant violations (§7) under combined chaos injection.
  • Fuzz targets (topology.rs, allocator.rs, metadata.rs) each reach 24-hour crash-free runs with no new coverage plateau evasion (measured via cargo-fuzz corpus growth rate).
  • Rolling upgrade from the prior minor version completes with zero allocation-serving downtime on fixtures/hardening/rolling_upgrade_v_n_minus_1.bin.
  • Rollback from a canary failure completes within the < 60 s RTO (§4).

21.5 Conformance Fixtures

  • fixtures/hardening/rolling_upgrade_v_n_minus_1.bin — recorded dual-version traffic split; expected: zero downtime, compatible replay across the version boundary.
  • fixtures/hardening/chaos_combined_injection.bin — simultaneous forced-OOM + migration-interruption + lock-starvation; expected: every subsystem degrades per its documented failure-analysis section, no undocumented crash.
  • fixtures/hardening/canary_rollback_trigger.bin — canary traffic exceeding an error-budget threshold; expected: automatic rollback triggers within the RTO budget.

21.6 Pitfalls

  1. Non-deterministic fuzz failures that don't reproduce outside the fuzzer's exact input — manifestation: a crash reported once, never again; root cause: a genuine race condition rather than a deterministic parsing bug; debugging: minimize the reproducer under the deterministic simulator (Phase 0), not the raw fuzzer, since the simulator controls scheduling; recovery: store the minimized reproducer permanently in the fuzz corpus regardless of reproducibility difficulty.
  2. Version skew during a rolling upgrade where the new binary's metadata layout is incompatible despite passing the additive-schema check — manifestation: a subtle field-interpretation mismatch; root cause: an additive field's default value differs in meaning between versions; debugging: replay fixtures/hardening/rolling_upgrade_v_n_minus_1.bin against both binaries and diff; recovery: add an explicit compatibility test to §26 for every schema change, not just a layout-size check.
  3. Canary traffic too small to statistically distinguish a regression from noise — manifestation: a real regression ships past canary; root cause: canary percentage set without a power calculation against the observed metric variance; recovery: size the canary traffic percentage against the §4 latency targets' expected variance, not a fixed 1 % default.

21.7 Performance Concerns

Fuzz amplification — a single malformed input can trigger disproportionately expensive recovery paths (e.g. repeated arena rebuilds) if the fuzzer discovers a corruption-inducing input that also happens to be cheap to generate repeatedly; rate-limit recovery-path fuzzing separately from the main corpus. Telemetry cardinality from chaos-testing combined injection can overwhelm the sidecar exporter (ADR-06); chaos runs use a sampled telemetry mode to avoid this becoming its own bottleneck.

21.8 Edge Cases

  • Rolling migration mismatches where a page migrated by the old binary is inspected by the new binary mid-upgrade — the migration state machine (§8) must be versioned identically to the metadata layout (§11), or the upgrade must drain in-flight migrations before proceeding.
  • A chaos-injected fault landing during another chaos-injected fault's recovery window — the combined- injection fixture must include overlapping-fault timing, not just sequential faults.
  • Fuzz corpus growth exceeding CI storage budget — corpus is periodically minimized and deduplicated, not allowed to grow unbounded.

21.9 Failure Analysis

Automated triage reports classify every fuzz/chaos finding by which invariant (§7) or ADR it violates, feeding directly into the postmortem template (§24). A finding that doesn't map to any documented invariant is treated as a specification gap, not just a bug — it triggers a review of whether §7 needs a new invariant.

Deployment: canary → full rollout gated on the release-channel trains (ADR-18); rollback is a first-class, rehearsed operation, not an emergency improvisation. 25. Compatibility & Versioning

Additive schema evolution only for every §11 type — a field may be added with a default value, never removed or reinterpreted, within a major version. Replay format (ReplayRecord, ADR-05) is major- version-pinned; minor versions may add optional trailing fields only, checked via the version header described in §20.8. The runtime-api ABI is stable within a major version — an embedding application compiled against 1.x continues to load against any 1.y.

Rolling upgrades support exactly one major-version overlap: the N and N+1 binaries may run simultaneously against the same WAL/snapshot format during a rollout, verified continuously by §21's rolling-upgrade fixture. A metadata migration tool (referenced throughout §11's compatibility guarantees) is mandatory before any layout change ships — no layout change is "documentation only."

Deprecation policy: a field or endpoint marked deprecated remains functional for one full major version cycle before removal, with a CHANGELOG.md entry and a docs/adr/ record explaining the replacement. Version negotiation on the runtime-api boundary is explicit — a caller queries the supported API version before relying on a feature introduced after 1.0.

26. Testing & Verification Strategy

Unit tests: freelist integrity (I1, I9), alignment correctness (I6), lock-ordering static checks (I7), checksum computation (I3).

Integration tests: multi-node allocation pressure across the full arena/slab/hugepage stack; migration correctness end to end through the state machine (§8); reclaim-under-cgroup-limit scenarios.

Property-based testing (ADR-12): allocation/free conservation (every allocated byte is eventually either freed or attributable to a live handle — no phantom leak); replay determinism (§20.4); ownership uniqueness under randomized concurrent operation interleavings, generated rather than hand-written.

Fuzzing (ADR-13): fuzz/fuzz_targets/topology.rs, allocator.rs, metadata.rs — 24-hour minimum crash-free bar per target before merge, extended to continuous background fuzzing post-merge (§21).

Chaos testing: forced OOM, migration interruption mid-state-machine, lock starvation injection, combined-fault injection (§21.8) — verifying every phase's N.9 failure-analysis section holds under compound, not just isolated, faults.

Soak testing: 72-hour sustained-allocation run (§21.4) with zero invariant violations, superseding the source material's shorter 7-day-at-lower-intensity target with a denser, chaos-injected 72-hour bar that exercises more state transitions per wall-clock hour.

Differential testing: every release candidate's fixture replay is compared against the prior release's replay output (§21.2); any unexplained divergence blocks promotion out of the rc channel (ADR-18).

27. Build & Release Engineering

Reproducibility (ADR-19): pinned toolchain via rust-toolchain.toml; hermetic Docker builds with a locked base-image digest; cargo build --locked enforced in CI — a build is bit-for-bit reproducible given the same source commit and toolchain pin, a prerequisite for §20's forensic bisection.

Artifact signing: Sigstore keyless signing on every release artifact; provenance attestations (SLSA-style) attached to each build, verifiable by an operator before deployment.

SBOM: CycloneDX generation on every build, diffed in CI against the previous release (feeds T8's dependency-compromise detection).

Release channels (ADR-18): nightly (every merge to main, no soak requirement) → rc (weekly, requires the 72-hour soak from §21) → stable (promoted from a soak-clean rc, requires canary success per §21.4). No channel skips the one before it.

CI/CD: topology-matrix testing (1/2/4/8/16/64-node synthetic topologies, §13); performance- regression gates comparing every candidate against the §4/§28 target table with a documented tolerance band; fuzz gates (24 h minimum per changed crate); replay-determinism gates (§20.4's 1000-replay check run on every rc candidate, not just periodically).

Packaging (ADR-15): one crate per subsystem, workspace-versioned together for v1 (a single version number covers all 15 crates) to avoid the cross-crate compatibility matrix a fully independent versioning scheme would require.

28. Performance Engineering

Methodology: every performance claim in this document is measured via the same three tools — Criterion (benchmarks/) for statistically rigorous microbenchmarks, perf stat/flamegraphs for production-representative profiling, and the deterministic simulator (§7 methodology) for reproducing a specific contention or corruption scenario in isolation. Mean-latency-only dashboards are explicitly insufficient (MM7, §30) — every target below is a percentile, not a mean, and p99 attribution to a named subsystem is mandatory before a regression is considered understood.

Cache analysis: false-sharing detection via perf c2c on every new shared data structure before it ships (the mimalloc/jemalloc-class pitfalls in §14.6 and §15.6 were both found this way); cacheline heatmaps guide PageDescriptor/Arena field ordering to keep hot fields on one cacheline and cold fields on another.

29. Scalability Analysis

Bottlenecks (in expected order of appearance as core count grows): remote-free queue contention first (mitigated by per-source-node sub-queues, §14.6); migration bandwidth ceiling second (bounded by the CPU-to-bandwidth relationship in §32's C4); metadata-subsystem cache misses third (the PageDescriptor table's sheer size, §32's C1, means even sequential scans are memory-bandwidth-bound); topology-lock contention is explicitly not a bottleneck by design, since I12 makes the topology snapshot read-only after startup.

Horizontal scaling: allocator instances are isolated per process (§9 ADR-15's packaging choice does not imply cross-process sharing) — scaling to more processes is an orchestration-layer concern (Kubernetes topologyManager), not an allocator-internal one. §33's Q8 examines whether this reintroduces a bottleneck at the process-manager level; it does not, because each process's arenas are independent.

Vertical scaling: supports the full §4 ceiling — 2048 CPUs, 64 NUMA nodes, 64 TB memory — as a single-process deployment; scaling beyond this ceiling is explicitly out of scope (§1 non-goals).

Metadata scaling: hierarchical sharding is required past roughly 16 nodes (empirically, contention on a single global page-descriptor index becomes measurable there) — the descriptor table is sharded per-node from Phase 2 onward specifically to avoid needing a later migration to sharded metadata.

30. Mental Models & First Principles

  • MM1 — Locality Is a Correctness-Adjacent Property. Compressed insight: treat remote access like a latent bug, not a slowdown. Predicts: locality regressions surface as a remote-ratio percentage before they surface as p99. Bug class without it: silent latency creep dismissed as noise until a customer escalation. Applies in §17.
  • MM2 — Fast Paths Are Zero-Decision Paths. Compressed insight: any per-allocation branch on shared state is a scalability bet against you. Predicts: adding "just one check" measurably degrades p50. Bug class without it: cumulative small checks that each look free in isolation. Applies in §14.
  • MM3 — Bounded Queues Convert the Failure Mode, They Don't Eliminate It. Compressed insight: backpressure trades unbounded latency for bounded rejection — you still need a reject policy. Predicts: a "fixed" unbounded-growth bug that just adds a bound with no reject path silently deadlocks instead. Bug class without it: assuming a bound alone is sufficient. Applies in §18.
  • MM4 — Replay Determinism Is a Design Constraint, Not a Feature. Compressed insight: one stray non- deterministic input anywhere poisons every downstream replay. Predicts: replay divergence that "sometimes" reproduces is always a real bug, never a flake. Bug class without it: dismissing intermittent replay mismatches as noise. Applies in §20.
  • MM5 — Ownership Transfer Must Be Atomic or It's a Race. Compressed insight: any two-step handoff has a window. Predicts: double-free/double-use bugs cluster exactly at handoff boundaries (migration, reclaim). Bug class without it: "temporarily" shared ownership during a state transition. Applies in §7.
  • MM6 — Degraded Mode Beats a Guess. Compressed insight: an allocator that doesn't know the topology should say so, not guess. Predicts: a guessed placement on malformed input pins memory to the wrong socket for the process's entire life, not just once. Bug class without it: silent misplacement treated as a one-time hiccup. Applies in §13.
  • MM7 — Tail Latency Hides in Rare Code Paths. Compressed insight: p99 is dominated by paths taken under 1 % of the time. Predicts: mean-latency dashboards miss the actual regression entirely. Bug class without it: "the average looks fine" masking a rare multi-microsecond lock hold. Applies in §28.
  • MM8 — Every Capacity Number Must Trace to a Measured Constraint. Compressed insight: an unsourced number in a capacity model is a guess wearing a table's clothing. Predicts: capacity plans built on assumed rather than derived numbers fail the first time deployed hardware doesn't match the assumption. Bug class without it: sizing decisions that can't be re-derived when hardware changes. Applies in §32.

32. Back-of-Envelope Capacity Model

  • C1 — Page Descriptor Table. 64 TB ÷ 4 KB page = 17,179,869,184 pages (§4) × 48 B/descriptor (§11) = 824.6 GB = 768 GiB = 1.17 % of 64 TB, inside the < 2.5 % §4 metadata ceiling.
  • C2 — WAL Append Overhead. 32 B/ReplayRecord ÷ ~9 GB/s ring-buffer append bandwidth = 3.56 ns/record ÷ 120 ns p50 budget (§4) = 2.96 %, just inside the < 3 % replay-journal ceiling.
  • C3 — Slab Header Overhead. 64 nodes × 16,384 slabs/node × 64 B header/slab = 67,108,864 B = 64 MiB fleet-wide, negligible against C1's 768 GiB, confirming page descriptors dominate metadata overhead.
  • C4 — Migration Worker CPU-to-Bandwidth Ceiling. 1 % of 2048 CPUs (§4) = 20.48 core-equivalents × ~5 GB/s memcpy-class throughput/core = 102.4 GB/s aggregate migration bandwidth ceiling.
  • C5 — Remote-Ratio Latency Budget. 8 % remote ratio (§4) × (4.5× − 1) penalty multiplier × 120 ns local p50 = 33.6 ns added mean latency = 153.6 ns total, inside the 900 ns p95 ceiling (§4).
  • C6 — Hugepage Reservation Budget. 64 TB ÷ 64 nodes = 1 TB/node (§4); 10 % reservation = 100 GB/node ÷ 1 GB/hugepage × 64 nodes = 6,400 hugepages fleet-wide = 6.4 TB, 10 % of the 64 TB ceiling.
  • C7 — Fragmentation Budget. 64 TB × 18 % ceiling (§4) = 11.52 TB max tolerated unusable memory; 64 TB − 11.52 TB = 52.48 TB guaranteed-usable floor.
  • C8 — Amplification-Adjusted Usable Capacity. 64 TB physical ÷ 1.15× amplification ceiling (§4) = 55.65 TB of logical demand guaranteed servable before physical exhaustion.
  • C9 — FD Budget Headroom. 256 sampled perf_event FDs + 64 per-node WAL handles + 16 eBPF FDs + 50 misc = 386 FDs of the 1024 budget (§4), leaving 638 FDs headroom for the embedding application.
  • C10 — Availability Error Budget. (1 − 0.9999) × 365.25 × 24 × 60 min/year = 52.6 min/year allowed downtime (§4) ÷ 60 s RTO ceiling per incident = ≈ 52 full-RTO incidents/year before SLA breach.
  • C11 — Per-Node Startup Budget. 250 ms startup ceiling (§4) ÷ 64 nodes = 3.9 ms/node average SRAT/SLIT parse-and-validate budget (§13).
  • C12 — Shard Utilization From Max Lock Hold. 1 ÷ 120 ns p50 fast-path latency (§4) = 8.33M ops/sec aggregate fast-path rate at full saturation ÷ 64 node-shards (§4) = 130,208 ops/sec/shard × 3 µs max lock hold (§4) = 39.1 % worst-case shard utilization from lock-hold alone.

34. Alternative Architectures (Roads Not Taken)

Alt A — Kernel-Resident NUMA Allocator

+-------------------------------------------+
|         Every process on the host          |
+---------------------+-----------------------+
                      v
+-------------------------------------------+
|   Linux mm/ patch: SLUB + buddy + AutoNUMA  |
|   (single shared allocator, kernel-owned)   |
+-------------------------------------------+

Wins when every process on a host must benefit from NUMA-aware allocation uniformly, with no per- application embedding step. Embodied by Linux's own SLUB/buddy allocator plus AutoNUMA balancing. Rejected here because this project targets library-level control with rapid iteration for one embedding process (§1); a kernel patch has multi-year upstream review cycles incompatible with the 9–14 month full-system timeline (§1) and cannot expose the replay/observability surface (§20) this design requires.

Alt B — Share-Nothing Per-Core Runtime

Core 0 -- exclusive pool 0        Core 1 -- exclusive pool 1
   ^  no cross-core allocation       ^  no cross-core allocation
   |                                 |
Application thread pinned forever to one core, forever

Wins for async dataplane workloads that already pin exactly one thread per core for the process's lifetime. Embodied by Seastar's per-shard memory subsystem. Rejected here because §1's target operators include conventional thread-pool database and actor-runtime embedders where thread-to-core pinning is not guaranteed — forcing that assumption would break the embedding model this project promises.

Alt C — Garbage-Collected NUMA-Aware Heap

Mutator threads --> GC-managed heap regions (NUMA-tagged)
                         |
                    GC relocates objects across regions
                    during collection (stop-the-world or
                    concurrent, but always GC-driven)

Wins for managed-language workloads where the collector already owns object lifetime and can freely relocate objects during collection. Embodied by the HotSpot JVM's -XX:+UseNUMA NUMA-aware allocation for its garbage collectors. Rejected here because §1's target workloads (databases, dataplanes, OLTP engines) cannot tolerate GC pause semantics or object-relocation-during-use — P8's bounded-tail-latency principle is incompatible with a GC-driven relocation model.

Alt D — Distributed Shared Memory Across Hosts

Host A page table <--network page fault/coherence--> Host B page table
        (a single page can live on either host, migrated over the wire)

Wins for workloads whose working set genuinely exceeds one host's NUMA fabric and must span multiple machines transparently. Embodied by Li & Hudak's Ivy distributed shared memory system (1989), the foundational page-based DSM design. Rejected here because §1 explicitly excludes distributed shared memory as a non-goal — cross-host page coherence introduces network-partition failure modes entirely outside this design's single-host threat model (§22).

36. Glossary

  • Arena — NUMA-local allocation domain owning exactly one node's free lists and slab caches.
  • Slab — fixed-size object allocation region managed by size class.
  • Magazine — per-thread cache layer over a slab's shared depot (Bonwick & Adams 2001).
  • Size Class — a fixed allocation-size bucket used by the slab allocator's dispatch table.
  • Depot — the shared per-slab-class object pool magazines refill from.
  • Locality Score — the placement-affinity metric computed by the NUMA policy engine.
  • Replay WAL — the deterministic, append-only allocator event log used for reconstruction.
  • Remote Free — a free operation whose target arena is on a different node than the freeing thread.
  • Hugepage — a 2 MB or 1 GB hardware page mapping, explicitly reserved via hugetlbfs.
  • NUMA Distance — the relative access-cost value between two nodes from the SLIT table.
  • Reclaim — the memory-recovery process that returns cold pages to the free pool under pressure.
  • TLB Shootdown — cross-core translation-invalidation synchronization triggered by a page move.
  • Heatmap — sampled access-frequency metadata used to prioritize migration and reclaim targets.
  • Poison Pattern — a fixed fill-byte sequence written on free, used to detect use-after-free.
  • Generation Counter — an ABA-mitigation version field bumped on every ownership transition.
  • Migration Storm — an uncoordinated burst of migration tasks that collapses available bandwidth.
  • Pressure Signal — telemetry indicating approaching memory exhaustion, sourced from cgroup v2.
  • Topology Snapshot — the immutable-after-startup hardware map published by the topology layer.
  • Pinning — a per-page flag preventing migration or reclaim (I4, I11).
  • Fragmentation — the fraction of reserved capacity that is free but unusable for a given request.
  • Local Allocation — an allocation served from the requesting thread's own NUMA node.
  • Remote Allocation — an allocation served from a NUMA node other than the requester's own.
  • Degraded Mode — the safety-first fallback state entered when topology validation fails (P12).
  • Free List — an intrusive linked structure of unallocated pages or objects within an arena/slab.
  • Page Descriptor — the per-page metadata record tracking owner, state, checksum, and generation.
  • Node Descriptor — the per-NUMA-node metadata record tracking CPUs, memory ranges, and distances.
  • Ownership — the single-authoritative-owner relationship a page or object has at all times (I1).
  • Checksum — a per-descriptor integrity value validated on every metadata access (I3).
  • ABA Problem — a concurrency hazard where a value is read, changed, and changed back, hiding a race.
  • CAS (Compare-And-Swap) — the atomic primitive used for lock-free ownership transitions.
  • Lock Striping — partitioning a lock's protected state across shards to reduce contention (P11).
  • Backpressure — an explicit bounded-queue reject/delay policy applied at every subsystem boundary.
  • Crash-Only Semantics — the design discipline of recovering only via restart/reconstruction (P3).
  • Soak Test — a long-duration sustained-load test (72 h, §21) verifying zero invariant violations.
  • Canary Deployment — serving a small traffic percentage to a new build under full telemetry.
  • Rolling Upgrade — running two allocator versions simultaneously during a release rollout.
  • SBOM — a CycloneDX-format software bill of materials generated on every build.
  • Sigstore — the keyless artifact-signing infrastructure used for release provenance.
  • Cold Page — a page whose heatmap access frequency has fallen below the reclaim/migration threshold.
  • Emergency Reclaim — the bounded, synchronous last-resort reclaim path under severe pressure.
  • Throttling — delaying (not rejecting) new allocations proportionally to pressure severity.
  • RTO — recovery time objective, the maximum time to restore service after a failure.
  • RPO — recovery point objective, the maximum tolerable data-loss window.
  • SRAT / SLIT — the ACPI System Resource Affinity Table and System Locality Distance Information Table, the firmware sources of NUMA topology data.
  • cgroup v2 — the Linux control-group hierarchy version whose memory controller drives pressure signals into the reclaim subsystem.
  • THP — transparent hugepages, the kernel's automatic (non-explicit) hugepage mechanism this design deliberately does not rely on (ADR-23).
  • Workload Classification — the policy engine's heuristic distinction between steady-state and bursty allocation patterns.
