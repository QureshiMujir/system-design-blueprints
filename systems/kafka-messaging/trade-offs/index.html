Decisions (§9) · 37 ADRs

ADR-01

Language

Chosen

Rust

Rejected

Java/Scala, Go, C++

When the rejected choice is right

Java/Scala wins for fastest access to existing Kafka ecosystem/tooling when GC pauses are tolerable; Go wins for small internal tools valuing hiring pool over tail latency; C++ wins when a team already owns a mature C++ allocator/RPC stack

Why: no GC pause on hot path; zero-copy control; memory-safe fuzzed decoders

ADR-02

Async runtime

Chosen

Tokio, thread-per-core executor pinned per partition-shard

Rejected

async-std, hand-rolled epoll/io_uring reactor, blocking-thread-per-connection

When the rejected choice is right

a hand-rolled reactor wins for a bespoke zero-overhead scheduler a team is willing to own (Seastar-style); blocking threads win for a tiny fixed-low-connection-count internal broker

Why: mature ecosystem (rustls); tokio-uring support for the log I/O path

ADR-03

Core primitive

Chosen

partitioned append-only log, offset-addressed

Rejected

broker-managed queue (per-message ack), topic-based pub/sub dispatch

When the rejected choice is right

a broker-managed queue wins for genuine task/RPC-style distribution with heterogeneous per-message retry/priority needs (§36)

Why: enables replay/fan-out/time-travel at O(1) marginal cost (P1)

ADR-04

Segment file design

Chosen

flat append-only .log per segment, fixed roll size, separate .index/.timeindex

Rejected

single unbounded log file, LSM-style sorted-run levels

When the rejected choice is right

unbounded single file wins only for a toy build with no retention; LSM levels win for keyed random-access workloads (LSM-Tree-Storage's domain)

Why: bounded segments make retention/compaction/recovery independently-deletable units

ADR-05

Index density/format

Chosen

sparse, 4,096-byte interval, 8/12-byte fixed-width mmap'd entries

Rejected

dense per-record index, no index, B-tree

When the rejected choice is right

dense index wins when point-offset lookups dominate and RAM is free; B-tree wins for keyed-access engines

Why: O(segment_bytes/interval) index memory, bounded scan tail

ADR-06

Read path

Chosen

OS page cache + sendfile zero-copy

Rejected

user-space read cache, O_DIRECT self-managed pool

When the rejected choice is right

O_DIRECT + self-managed pool wins when precise eviction control beats kernel LRU approximation (Redpanda); user-space cache wins once TLS/compression already force a copy

Why: shared across processes, survives restarts warm, skips userspace copy (P11)

ADR-07

Record-batch format

Chosen

Kafka record-batch v2, per-batch compression

Rejected

per-record compression, unbatched flat framing

When the rejected choice is right

per-record compression wins only for ultra-latency-sensitive acks=0 single-record produce

Why: amortizes CRC/header overhead, larger compression dictionary window

ADR-08

Compression codecs

Chosen

pluggable gzip/Snappy/LZ4/Zstandard, per-topic

Rejected

single mandatory codec, none

When the rejected choice is right

no compression wins when CPU, not I/O, is the bottleneck (already-compressed payloads); gzip-only wins for a single-audited-codec regulated environment

Why: LZ4/Zstd best throughput/ratio default; gzip for legacy compatibility

ADR-09

Checksum

Chosen

CRC-32C (RFC 3385) over attributes-through-records

Rejected

CRC-32, none, SHA-256

When the rejected choice is right

SHA-256 wins if the checksum must also be a tamper-evidence/security control (out of this system's threat model, T2)

Why: hardware-accelerated (SSE4.2), near-free per-batch validation

ADR-10

Produce ack model

Chosen

client-selectable acks∈{0,1,all} + min.insync.replicas (P3)

Rejected

single fixed durability level, synchronous quorum write

When the rejected choice is right

a fixed always-quorum level wins when misconfiguration risk must be eliminated entirely (§36 per-partition Raft)

Why: exposes the full latency/durability tradeoff instead of hiding it

ADR-11

Idempotent producer

Chosen

per-partition (id, epoch, sequence) dedup window

Rejected

broker-side content-hash dedup, no idempotence

When the rejected choice is right

content-hash dedup wins only with untrusted/legacy producers that cannot carry sequence numbers

Why: O(1) sequence check, cheaper than hashing, works for identical-content records

ADR-12

Replication protocol

Chosen

leader/follower, dynamic ISR + high watermark

Rejected

per-partition Raft/Paxos quorum, chain replication

When the rejected choice is right

per-partition Raft wins when a single non-misconfigurable durability knob is worth the extra round trip (Redpanda)

Why: tunable durability at lower steady-state latency than synchronous quorum commit

ADR-13

HW propagation

Chosen

piggybacked on follower Fetch responses

Rejected

dedicated HW-gossip RPC, client-computed HW

When the rejected choice is right

dedicated gossip wins for very large ISR sets where piggyback metadata would balloon

Why: reuses the required Fetch RPC, no extra round trip

ADR-14

Leader election / unclean policy

Chosen

controller-driven from current ISR; unclean disabled by default

Rejected

unclean always allowed, client-side election

When the rejected choice is right

always-allow-unclean wins for best-effort/telemetry topics where availability strictly dominates durability

Why: default-safe, matches P3's durability contract

ADR-15

Controller design

Chosen

self-managed metadata Raft (KRaft, KIP-500)

Rejected

external coordination service (ZooKeeper), etcd

When the rejected choice is right

an external service wins when the org already runs one at scale for other systems

Why: removes a whole external distributed system from the deployment (P8)

ADR-16

Metadata storage

Chosen

replicated log of MetadataRecords, self-hosted

Rejected

relational metadata store, in-memory-only

When the rejected choice is right

a relational store wins when SQL-queryable metadata and transactional consistency matter more than replay

Why: metadata-as-a-log gives the same replay/audit properties as data (P1)

ADR-17

Producer partitioning

Chosen

key-hash (murmur2), sticky for null keys

Rejected

round-robin per-record, random

When the rejected choice is right

pure round-robin wins with zero ordering requirement and maximal spread priority

Why: preserves per-key ordering (P2) while maximizing batch size for unkeyed traffic

ADR-18

Consumer-group coordination

Chosen

broker-side coordinator, incremental cooperative rebalance default (KIP-429)

Rejected

client-side-only coordination, eager rebalance default

When the rejected choice is right

eager rebalancing wins for small stable groups (<10) prioritizing simplicity

Why: avoids full-stop pauses on membership change

ADR-19

Offset storage

Chosen

broker-side compacted internal store (client remains authoritative, P9)

Rejected

client-only external store, ZooKeeper-stored offsets

When the rejected choice is right

external store wins when offsets must commit atomically with a non-Kafka side effect (dual-write pattern)

Why: survives consumer restarts without an external durable store

ADR-20

Transaction coordinator

Chosen

dedicated coordinator, transaction log, 2PC control records (KIP-98)

Rejected

idempotence-only (no transactions), client-side app-level 2PC

When the rejected choice is right

idempotence-only wins when no workload needs multi-partition atomicity

Why: atomic multi-partition visibility without client-implemented distributed commit

ADR-21

Retention policy

Chosen

time/size-based, independent of consumer position (I12)

Rejected

consumer-acked-gated retention, infinite retention only

When the rejected choice is right

acked-gated retention wins for genuine task-queue workloads — the queue model this project rejects (ADR-03)

Why: keeps the log a data-lifetime policy decoupled from consumers (P1)

ADR-22

Compaction design

Chosen

background dirty-ratio-triggered offset-map rewrite

Rejected

online in-place compaction per write, no compaction

When the rejected choice is right

no compaction wins when no topic needs changelog/keyed-latest-value semantics

Why: amortizes offset-map cost; in-place would serialize the hot append path

ADR-23

Quota enforcement

Chosen

Rejected

When the rejected choice is right

hard rejection wins when a fail-fast signal, not added latency, is the desired tenant SLA contract

Why: visible (measurable latency), lossless (P12)

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Per-partition Raft (Redpanda's model), replacing ISR/HW with a consensus quorum.

Producer --> [Partition Leader] --Raft AppendEntries--> [Follower 1]
                    |                                    [Follower 2]
                    +--commit once majority acks-------------+
             (write acknowledged only after quorum commit,
              no separate HW concept — commit IS the guarantee)

Winning regime: environments where durability must never be silently misconfigurable and the extra quorum round-trip latency is acceptable. Real embodying system: Redpanda. Rejected here because ADR-12 explicitly wants the tunable acks/ISR tradeoff space (P3) exposed to the operator rather than fixed — an educational build benefits from studying both durability models as distinct mechanisms, and this blueprint chose the one that teaches the ISR/HW distinction (P4, I2-I4) directly.

Alternative 2 — Segmented storage split from serving brokers (Pulsar's model).

[Broker A] --\                    [Bookie 1] (ledger fragments)
[Broker B] ---+-- reads/writes -->[Bookie 2] (ledger fragments)
[Broker C] --/                    [Bookie 3] (ledger fragments)
   (brokers are stateless; any broker can serve any partition
    by attaching to that partition's ledgers on demand)

Winning regime: elastic compute/storage scaling and instant broker failover (no re-replication needed, just ledger reattachment). Real embodying system: Apache Pulsar (with Apache BookKeeper). Rejected here because it requires operating two clustered systems (brokers + BookKeeper) — this blueprint's scope (ADR-04) is a single broker-local storage engine, which is both simpler to build end-to-end in the phase plan (§12-§23) and the more common production topology this specification's target users will actually operate.

Alternative 3 — Classic broker-managed queue with per-message acknowledgement (RabbitMQ's default model).

Producer --> [Exchange] --route--> [Queue] --deliver--> Consumer
                                      |  (per-message ack/nack state
                                      |   tracked server-side; unacked
                                      +-> messages redelivered on nack/timeout)

Winning regime: genuine task/RPC-style distribution with heterogeneous per-message retry and priority needs, where "processed" should mean "gone." Real embodying system: RabbitMQ (classic queues). Rejected here per ADR-03/P1 — this project's entire pedagogical point is the log primitive and the replay/fan-out properties a queue's per-message state destroys; building the queue model instead would teach a different (also valuable, but different) lesson, covered by sibling PubSub-Messaging (rank 206), not this project.

Alternative 4 — Shared-storage / object-store-backed log, trading latency for elastic, cheap storage.

Producer --> [Stateless Broker] --write--> [Object Store (S3-compatible)]
                     ^                            |
                     +-------- read-back ---------+
        (no local broker disk at all; durability and
         replication delegated entirely to the object store)

Winning regime: workloads that can tolerate higher produce/fetch latency (object-store round trips) in exchange for near-zero storage-management overhead and effectively unlimited retention at low cost. Real embodying system: WarpStream (Kafka-protocol-compatible, S3-backed, acquired by Confluent in 2024). Rejected here because §4's latency targets (single-digit-to- low-double-digit-ms produce latency) are incompatible with object-store round-trip times, and this blueprint's pedagogical focus is precisely the local segmented-log/page-cache/zero-copy discipline (P10, P11) that an object-store-backed design deliberately gives up.
