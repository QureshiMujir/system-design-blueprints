In one paragraph

This is a from-scratch distributed log broker: not a message queue but a partitioned, replicated, append-only commit log in which every record is addressed by a number, its offset (§1). Producers append; consumers read from an offset they choose, and their position is a committed offset the client owns, never per-message acknowledgement state kept by the server (§1, P1, P9). Segmented storage, replication through an in-sync replica set, consumer coordination and transactions are all views computed over that one primitive (§1). It runs as a single broker in development and as a replicated cluster (replication factor 3 typical) with a 3- or 5-node controller quorum in production, used by application teams that stream events and run by platform SREs (§1).

The problem, concretely

The naive design is a queue: the broker remembers, per message, whether a subscriber has acknowledged it, and an acknowledged message is gone (§36 Alternative 3). That fits task distribution, but it destroys what a log gets for free, replay and fan-out (P1, §36 Alternative 3). In a queue "consumed" means "removed", and the blueprint names the resulting bug class: building server-side per-consumer delivery state because the engineer assumes consumed must mean removed (§32 MM1). The log instead keeps records until time or size retention removes them, whatever readers have done (I12), so a reader's position is one integer per partition (P1).

The blueprint's worked example shows it (§8.11). Producer P1 sends three records with key "user-42" to partition 3 of topic clicks at acks=all, with leader A and followers B and C. A's log end moves from 1000 to 1003; B and C fetch and append; the high watermark becomes min(1003, 1003, 1003) = 1003, and A acknowledges. Consumer group analytics fetches from offset 1000, receives the three records by sendfile, and commits offset 1003 under generation 7 (§8.11). Reading changed nothing on the broker: any consumer can rewind to any retained offset at zero marginal server cost (§32 MM1).

The second naive move is to acknowledge before the copies exist. If leader A had acknowledged offsets 90–99 at acks=1 and then crashed while follower B's log-end offset was only 90, offsets 90–99 are gone: the producer was told "success" for records no surviving replica holds (§8.6). The blueprint's lesson is that "durability is a config value, not a given" (§2), and the rest of the design makes that trade explicit (P3).

How it works, end to end

The architecture diagram stacks the request path from a producer's socket down to the disk, with replication, the controller and the coordinators below it (§3). Lightly adapted:

 Producers ──produce──►  Network layer / request router (kbroker-net): TLS · SASL · quota gate
 Consumers ──fetch────►        │                               │
          Produce handler (acks, seq dedup)          Fetch handler (long-poll, HW gate)
                     (both in kbroker-broker)
                               │ append                        │ read (offset → position)
                      Log manager (kbroker-log): segment files · OffsetIndex · TimeIndex
                               │ sendfile / mmap               │ fsync
                      Page cache / zero-copy path        Retention + compaction workers
                               ▲ replicate (Fetch RPC, long-poll)
                      Replica fetcher · ISR manager · HW tracker   (kbroker-replication)
                               │ epoch / ISR updates
                      Controller + metadata log (kbroker-controller, KRaft-style Raft)
                               │ group / txn state (compacted, own logs)
                      Group coordinator (kbroker-group) · Transaction coordinator (kbroker-txn)
                      Quota manager (kbroker-quota) · telemetry on every box

Follow one record. The network layer (kbroker-net) terminates TLS, authenticates the client with SASL, demultiplexes pipelined requests by correlation id and is the quota enforcement point before anything reaches a handler (§3, P12); the budgets themselves live in the quota manager (kbroker-quota), which delays responses rather than dropping them (§3, I14). The produce handler in kbroker-broker checks that this broker leads the partition, that the batch's CRC matches and that the producer's sequence number is the next one expected (§8.3, I1, I5, I7). The log manager (kbroker-log) appends the batch to the partition's active segment, a sequential write, and advances the leader's log-end offset (§8.3). If the producer asked for acks=all, the request waits in the produce purgatory until the high watermark reaches its offset (§3, §8.3). Followers pull new batches through the replica fetcher in kbroker-replication with long-poll Fetch RPCs, and the high watermark travels back piggybacked on Fetch responses rather than in a separate RPC (§3, ADR-13). The HW tracker recomputes the high watermark, the minimum log-end offset over the in-sync set, which is the only point up to which consumers may read (§8.3, §8.5, I2). A consumer's fetch is located through the sparse index and sent straight from the OS page cache with sendfile, or parks in a fetch purgatory until the high watermark advances or maxWaitMs expires, whichever comes first (§8.4, ADR-06, P11). The consumer later commits its offset to the group coordinator (kbroker-group) (§8.4, §8.9); transactional writes go through the transaction coordinator (kbroker-txn) (§3, P13). In the background, retention deletes old segments by time or size whatever consumers have read (I12), and compaction rewrites segments to keep the latest record per key (§8.10). The controller (kbroker-controller) runs a Raft-replicated metadata log, the KRaft-style design, as the single source of truth for partition assignment, leader election and ISR bookkeeping (§3, ADR-15, P8).

The core ideas

Offsets, segments and a deliberately sparse index (§8.2)

Each partition is a directory of segment files named by the first offset they contain, each with a companion offset index and time index; the blueprint's example directory holds a segment that starts at offset 0 and the next one, rolled at offset 12345 (§8.2). The index is sparse on purpose: one 8-byte entry per 4,096 bytes of log, so a 1 GiB segment needs about 2 MiB of index (§4, §34 item 5). A read for offset O takes four steps (§8.2):

  1. Binary-search the in-memory list of segment base offsets for the segment S with S.baseOffset ≤ O < nextSegment.baseOffset (any O below 12345 lands in the first segment).
  2. Binary-search S's memory-mapped offset index for the largest entry with relativeOffset ≤ O − S.baseOffset, which gives a byte position P.
  3. Seek the .log file to P.
  4. Scan forward, decoding batch headers, until the batch with baseOffset ≤ O ≤ baseOffset + lastOffsetDelta.

The design target is 2 ms for any offset in a 10 GB log, which allows an index binary search plus a scan of at most 4 KB (§14.4, M7).

Two pointers, and what acks buys (§8.5, §8.7, MM2, MM5)

Each replica has a log-end offset (LEO), one past its last written record. The partition's high watermark (HW) is the minimum LEO over the in-sync replica set, and a fetch may return offsets below HW only (§8.5, I2). The gap [HW, LEO) is data not yet on every in-sync replica, so it stays invisible (§8.5, P4); in §8.11's example all three replicas reach LEO 1003, so HW = min(1003, 1003, 1003) = 1003 (§8.11). The blueprint's phrase: the high watermark "is a promise about what cannot be un-said" (§32 MM2). A replica is evicted from the in-sync set when it has not caught up with the leader's LEO for longer than replica.lag.time.max.ms (default 10,000 ms), and re-admitted when its LEO reaches HW (§8.5, §4).

A producer chooses how much of this to wait for (§8.7, §4):

acks setting What holds the record at ack time RPO Produce p99
0 nobody confirms unbounded 0.5 ms
1 the leader, not yet replicated leader's unreplicated tail (≈ single-digit ms of records) 8 ms
all, min.insync.replicas=1 the leader; ISR may be size 1 same as acks=1 if ISR shrank to 1 —
all, min.insync.replicas=2, RF=3 at least two replicas 0, unless ≥ 2 of 3 replicas fail simultaneously 20 ms (RF=3, ISR=3)

The trap is the third row: acks=all looks safe but degrades to acks=1 once the in-sync set shrinks to the leader alone (§8.7, §35 question 2). The blueprint calls acks and min.insync.replicas "the receipt" for durability that is "a purchase, not a default" (§32 MM5).

Leader epochs: a fence, not a clock (§8.6, MM4)

Every leadership change increments an epoch. A follower that rejoins presents its last epoch and offset; the new leader answers OffsetForLeaderEpoch with where that epoch ended, and the follower truncates to the point both agree on before fetching under the new epoch (§8.6, P5). The blueprint's worked example (§8.6):

Step Event Epoch B LEO C LEO
1 A leads, writes 0–99; B has all of it, C only to 80 5 100 80
2–3 A crashes; the controller elects B, the only ISR member alive 6 100 80
4 C fetches from B, presenting (epoch 5, offset 80) 6 100 80
5 B answers OffsetForLeaderEpoch(5) → 100 6 100 80
6 C truncates to min(80, 100) = 80 (a no-op here), then fetches from 80 under epoch 6 6 100 100
7 leader-epoch-checkpoint records (epoch 6, startOffset 100) 6 100 100

Keying truncation on epochs rather than timestamps is what keeps it correct under clock skew; truncation keyed on timestamps "will misbehave" there (§32 MM4, P5).

Exactly one owner per partition, enforced by generation (§8.9, MM7)

A consumer group shares a topic's partitions among its members. The coordinator's state machine runs Empty → PreparingRebalance → CompletingRebalance → Stable: once the join window closes the group leader computes an assignment, and its SyncGroup distributes it (§8.9). A missed heartbeat or a new member triggers a rebalance; under the default cooperative protocol only the partitions that must move are revoked and reassigned (§8.9, ADR-18). Every OffsetCommit carries the group's generation id, and a commit for a partition the member no longer owns under the current generation is rejected (§8.9, I11) — in §8.11 the analytics group commits offset 1003 with generationId=7 (§8.11). The blueprint calls the protocol "a distributed lock service in disguise" (§32 MM7).

Idempotence and transactions as control records (§8.8)

An idempotent producer gets (producerId, producerEpoch) from InitProducerId and numbers its batches; each partition's ProducerStateManager tracks the highest sequence seen over the last 5 batches (§8.8). sequence == lastSeen + 1 is accepted; a sequence inside the last-5 range is a duplicate, re-acknowledged without re-append; a larger gap returns OUT_OF_ORDER_SEQUENCE and forces the producer to reinitialize (§8.8, I5, P6). Transactions build on that identity in a 10-step protocol (§8.8):

  1. The producer registers each partition it touches with AddPartitionsToTxn; the coordinator appends that to its transaction log.
  2. On EndTransaction, the coordinator writes PrepareCommit or PrepareAbort to its log, then sends WriteTxnMarkers so every involved leader appends a control record.
  3. After all partitions acknowledge, it writes CompleteCommit or CompleteAbort; a read_committed consumer advances its last stable offset past the transaction only on seeing the control record (§8.8, I10, P13).

A coordinator that crashes mid-commit rescans the transaction log on recovery and completes any hanging Prepare* state (§8.8).

Compaction keeps keys, not history (§8.10, MM6)

For keyed topics, the dirty ratio is the bytes written since the last compaction point divided by total bytes; a partition becomes eligible once it reaches min.cleanable.dirty.ratio (0.5), and the worker builds a key → latest-offset map over the dirty segments and rewrites them forward keeping only the latest record per key (§8.10, §4). A deletion is a record with a null value, a tombstone, which survives delete.retention.ms past compaction so lagging consumers still see the deletion, and is dropped on the next pass (§8.10, I6). The capacity model's example: at a 0.5 ratio on a 1 GiB segment range, about 512 MiB is dirty, which one worker at 100 MB/s clears in about 5.1 s (§34 item 8). Compaction "never claims to remember what a value used to be" (§32 MM6).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust, for no garbage-collector pause on the append/fetch hot path, control of zero-copy I/O and memory-safe fuzzed decoders (§1, ADR-01). Rejected: Java/Scala, Go, C++ (ADR-01). When the rejected choice is right: Java/Scala for the fastest access to the existing Kafka ecosystem and tooling when GC pauses are tolerable; Go for small internal tools that value the hiring pool over tail latency; C++ when a team already owns a mature C++ allocator and RPC stack (ADR-01).

The core primitive: a log, not a queue (ADR-03)

Chosen: a partitioned, append-only, offset-addressed log, which gives replay, fan-out and time travel at O(1) marginal cost (ADR-03, P1). Rejected: a broker-managed queue with per-message acknowledgement, or topic-based pub/sub dispatch (ADR-03). When the rejected choice is right: genuine task or RPC-style distribution with heterogeneous per-message retry and priority needs, where "processed" should mean "gone" (ADR-03, §36 Alternative 3) — the sibling PubSub-Messaging blueprint's territory (§1).

Replication: in-sync replicas and a high watermark, not Raft per partition (ADR-12)

Chosen: leader/follower replication with a dynamic in-sync set and a high watermark, for tunable durability at lower steady-state latency than a synchronous quorum commit (ADR-12). Rejected: per-partition Raft or Paxos quorum, chain replication (ADR-12). When the rejected choice is right: when a single, non-misconfigurable durability knob is worth the extra round trip — Redpanda's choice (ADR-12, §36 Alternative 1).

Read path: the OS page cache and sendfile (ADR-06)

Chosen: no user-space cache; reads ride the OS page cache, which is shared across processes and survives restarts warm, and go to the socket by sendfile without a userspace copy (ADR-06, P11). The mental model: a user-space cache re-implementing what the OS already does "will underperform, not outperform" a well-sized page cache (§32 MM3). Rejected: a user-space read cache, or O_DIRECT with a self-managed buffer pool (ADR-06). When the rejected choice is right: O_DIRECT with a self-managed pool when precise eviction control beats the kernel's LRU approximation (Redpanda); a user-space cache once TLS or compression already force a copy (ADR-06).

Ack model: client-selectable, not fixed (ADR-10)

Chosen: acks ∈ {0, 1, all} plus min.insync.replicas, exposing the full latency/durability trade-off instead of hiding it (ADR-10, P3). Rejected: a single fixed durability level, or a synchronous quorum write (ADR-10). When the rejected choice is right: a fixed always-quorum level, when misconfiguration risk must be eliminated entirely (ADR-10, §36 Alternative 1).

Controller: a self-managed metadata Raft, not ZooKeeper (ADR-15)

Chosen: a KRaft-style replicated metadata log, which removes a whole external distributed system from the deployment (ADR-15, P8). Rejected: an external coordination service (ZooKeeper), or etcd (ADR-15). When the rejected choice is right: when the organisation already runs such a service at scale for other systems (ADR-15).

Retention: independent of consumers (ADR-21)

Chosen: time- and size-based retention that ignores consumer position, keeping data lifetime decoupled from consumers (ADR-21, I12, P1). Rejected: retention gated on consumer acknowledgement, or infinite retention only (ADR-21). When the rejected choice is right: genuine task-queue workloads — the queue model this project rejects (ADR-21, ADR-03).

Roads not taken (§36)

Per-partition Raft (Redpanda) acknowledges a write only after quorum commit, with no separate high-watermark concept; it wins where durability must never be silently misconfigurable and the extra quorum round trip is acceptable, and is rejected because ADR-12 wants the acks/ISR trade-off space exposed and this build teaches the ISR/HW distinction directly (§36 Alternative 1).

Storage split from serving brokers (Apache Pulsar with BookKeeper) makes brokers stateless, so failover needs no re-replication; it wins for elastic compute/storage scaling and instant broker failover, and is rejected because it means operating two clustered systems (§36 Alternative 2).

A classic broker-managed queue with per-message acknowledgement (RabbitMQ classic queues) wins for task or RPC-style distribution with per-message retry and priority needs; it is rejected per ADR-03 and P1 and is covered by the sibling PubSub-Messaging blueprint (§36 Alternative 3).

An object-store-backed log (WarpStream) trades latency for near-zero storage management and effectively unlimited cheap retention; it is rejected because §4's single-digit-to-low-double-digit millisecond produce latency targets are incompatible with object-store round trips (§36 Alternative 4).

Deferred, not rejected (§37): tiered storage waits until local retention storage cost exceeds the operator's local-disk budget (ADR-24); a stream-processing DSL, a schema registry and cross-cluster geo-replication are future projects; SASL OAUTHBEARER / mTLS enterprise auth is slated for Phase 11 (§37).

What must never be false

Each line gives the invariant, then how the system notices a violation (§7).

  • I1 — offsets in a partition are gapless, monotonic and immutable; the startup segment scan checks continuity, log.offset.gap.count.
  • I2 — a consumer never fetches past the high watermark; a fetch-offset assertion in kbroker-sim, and fetch.above_hw.count must stay 0.
  • I3 — a follower's log is a byte-identical prefix of its leader's at the same epoch; the OffsetForLeaderEpoch divergence check on leader change, replica.divergence.offset.
  • I4 — a record acked at acks=all is on every ISR member at ack time; the Jepsen-style linearizability checker (§28).
  • I5 — an idempotent producer's duplicate retry is deduplicated by (producerId, epoch, sequence); a sequence-gap/duplicate property test, produce.duplicate.count.
  • I6 — compaction keeps the latest record per live key and never drops a key's final record before tombstone retention elapses; a post-compaction key-completeness fixture.
  • I7 — every sparse index entry points at a valid record-batch boundary; a CRC mismatch on a batch located via the index, index.corrupt.count.
  • I8 — the metadata log has exactly one active leader per epoch; stale-epoch writes are rejected, controller.epoch.
  • I9 — a partition has exactly one leader per epoch, or briefly none during election; brokers reject stale-epoch LeaderAndIsr, partition.leaderless.duration.
  • I10 — a committed transaction's records become visible to read_committed consumers atomically; fault injection killing the coordinator mid-commit, txn.hanging.count.
  • I11 — an offset commit succeeds only for a partition the member owns under the current generation; an ILLEGAL_GENERATION assertion test, offset_commit.rejected.count.
  • I12 — retention deletes by time or size only, never by consumer position; a fixture with a slow or absent group, log.start_offset.
  • I13 — on restart, bytes below the recovery point are trusted and bytes above it re-validated before serving; a missing or stale recovery point triggers a full scan, recovery.scan.duration.
  • I14 — a quota-throttled client's excess bytes are delayed, never dropped or duplicated; throttle time correlates with latency, not loss, quota.throttle_time_ms.

What breaks in production

  • FM-1 — under-replicated partitions climb cluster-wide. Disk or network saturation on some brokers slows followers; the under_replicated_partitions metric, §26's #1 alert, shows it. ISR shrink isolates the slow replicas automatically; operators add capacity, throttle the offending producer or rebalance leadership (FM-1).
  • FM-2 — silent data loss after an unclean leader election. The ISR shrank to one member and that member was lost; it is recognized as §8.13's scenario in the postmortem. There is no automatic recovery, since the loss is real by design; restore from a mirrored cluster or backup if one exists, otherwise accept it and notify downstream consumers (FM-2, §8.13).
  • FM-3 — log divergence between a promoted follower and the old leader. A leader was promoted without epoch-based truncation, a shipped bug rather than a config issue; an I3 assertion fails in kbroker-sim or the Jepsen harness. The fix is a hotfix: roll back the release and reconcile divergent replicas from a known-good source (FM-3, P5).
  • FM-4 — a stuck ISR shrink cascades into unavailability. A second replica degrades while the first is still evicted, dropping below min.insync.replicas, typically from a correlated infrastructure failure; acks=all producers fail fast with NOT_ENOUGH_REPLICAS instead of silently losing durability. Operators add replica capacity, or lower min.insync.replicas as an explicit durability decision (FM-4).
  • FM-5 — a rebalance storm. session.timeout.ms is too aggressive for real client pauses; a rebalance.count rate alert fires, and cooperative rebalancing bounds the blast radius. The fix is configuration — raise the timeout or adopt static membership — not code (FM-5, §35 question 14).
  • FM-7 — page-cache thrashing. Consumers lag past the data held in the page cache and reads fall to disk; fetch p99 spikes in step with consumer_lag. It is a capacity-planning miss, answered by adding RAM per §34's page-cache sizing model or more consumer instances (FM-7).
  • FM-8 — zero copy silently defeated. TLS or re-compression on the fetch path without kTLS offload halves fetch throughput; fetch.sendfile.count drops to near zero. Enable kTLS if the kernel supports it, or accept the cost and re-plan capacity (FM-8, P11, §32 MM8).
  • FM-11 — the controller quorum is down. A majority of controller nodes is down or partitioned, so reassignment and election freeze; controller.metadata_log.lag grows and elections fail. Existing data-plane leaders keep serving because the controller is separate from the data path; restoring the quorum majority is the fix (FM-11, P8).

Threats a reader should know (§24): T1 an unauthenticated client reading a sensitive topic, answered by mandatory SASL plus deny-by-default per-topic ACLs; T2 a crafted batch exploiting the decoder, answered by cargo-fuzz and bounds-checked varint parsing; T3 a decompression bomb, answered by a declared-size ceiling check before allocation; T8 a replayed produce request with a captured (producerId, epoch), rejected by epoch fencing once the legitimate producer has reinitialized; T10 quota bypass through a spoofed client.id, answered by keying quotas on the authenticated SASL principal.

How it compares

  • Apache Kafka uses the same leader/follower ISR and high-watermark scheme and client-owned offsets, on a JVM thread pool per request type (§33). That trade-off is the industry default because it lets operators dial latency against durability explicitly (§33).
  • Redpanda replaces ISR/HW with per-partition Raft on a Seastar thread-per-core design, removing the unclean-election trade-off at the cost of an extra round trip on every acknowledged write (§33). That fits operators who cannot be trusted to configure durability and would rather pay latency unconditionally (§33).
  • Apache Pulsar splits segments from brokers into BookKeeper ledgers, with broker-tracked cursors per subscription (§33). Brokers become stateless and failover instant, which wins when elastic, independent compute/storage scaling matters more than running one clustered system (§33).
  • NATS JetStream uses log-structured streams with embedded storage and Raft groups per stream, on the Go runtime (§33). It wins where lightweight embedded streaming with a minimal operational footprint matters more than deep offset and consumer-group semantics (§33).
  • RabbitMQ Streams adds a log-structured extension to the classic broker, with per-message ack for classic queues and offsets for streams (§33). It wins when an existing RabbitMQ deployment needs log semantics for some workloads, at the cost of two delivery paradigms in one broker (§33).

  4. Why does this design's compaction guarantee ("latest value per key") not imply "audit trail of every value a key ever had," and what happens to a consumer that assumed otherwise? — Hint: §8.10 and MM6.
  5. Why does an unclean leader election "lose" data that was already acknowledged, and in what precise sense was that data never actually as durable as the acknowledgement implied? — Hint: §8.13 and MM5.

If you only remember three things

A log is a queue that forgot to delete, and that forgetting is what buys replay and fan-out (§32 MM1). Readers stop at the high watermark because durability is not yet decided above it, and acks with min.insync.replicas is the receipt for how much durability you bought (§32 MM2, MM5). Leader epochs are a fence, not a clock: after a failover, replicas agree on history by asking where the previous epoch ended, never by comparing timestamps (§32 MM4, §8.6).

Words used here

  • Offset — the monotonic number that addresses one record inside one partition (§38).
  • Partition — one ordered, append-only, offset-addressed log; a topic is a named set of them (§38).
  • Segment — one bounded file of a partition's log plus its index files; the unit retention and compaction delete (§38).
  • Log-end offset (LEO) — the next offset a replica will write (§38, §8.5).
  • High watermark (HW) — the minimum LEO across the in-sync replicas; the fetch visibility limit (§8.5).
  • In-sync replica (ISR) — a replica caught up within the configured lag bound (§38).
  • Leader epoch — a monotonic counter, bumped on every leadership change, that fences stale leaders (§38).
  • acks / min.insync.replicas — the producer's acknowledgement level, and the minimum ISR size an acks=all write needs (§38).
  • Idempotent producer — a producer whose retries are deduplicated by sequence number (§38).
  • Control record — a marker record telling a partition's consumers a transaction committed or aborted (§38).
  • Consumer group / generation — consumers sharing a topic's partitions, and the id of the group's current membership that gates offset commits (§38).
  • Rebalance — reassigning partitions among group members when membership changes (§38).
  • Compaction / tombstone — keeping only the latest record per key; a null-value record marks a key for removal (§38).
  • Zero copy / page cache — moving bytes from the OS file cache to the socket without a userspace copy (§38).
  • KRaft / metadata log — the controller's self-managed Raft-replicated log of cluster state (§38).
