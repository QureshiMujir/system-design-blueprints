1. Goal & Scope

Kafka Messaging specifies a from-scratch distributed log broker: a partitioned, replicated, append-only commit log addressed by monotonic offsets — not a message queue. Every subsystem (segmented storage, replication, consumer coordination, transactions) is a view computed over the log primitive. The broker durably persists records in per-partition segment files, replicates them via a leader/in-sync-replica-set (ISR) protocol with high-watermark-gated visibility, and exposes two request paths: produce (append) and fetch (offset-addressed read). Consumer position is client-owned (a committed offset), never server-tracked per-message acknowledgement state.

Phase-0 deliverable — numbered list of crates (workspace kbroker):

  1. kbroker-types — core schema/types (TopicPartition, Offset, LeaderEpoch, …), no logic.
  2. kbroker-record — record-batch wire format, CRC-32C, compression codecs.
  3. kbroker-log — segmented log, sparse offset/time index, retention, compaction.
  4. kbroker-protocol — wire-protocol codec: API keys, versions, request/response framing.
  5. kbroker-net — connections, TLS/SASL, request router, quota enforcement point.
  6. kbroker-broker — produce handler, fetch handler, wired to kbroker-log.
  7. kbroker-replication — replica fetcher, ISR manager, HW tracker, leader-epoch truncation.
  8. kbroker-controller — controller election, metadata log (KRaft-style), assignment.
  9. kbroker-group — group coordinator, rebalance protocol, offset store.
  10. kbroker-txn — transaction coordinator, transaction log, control records.
  11. kbroker-quota — quota manager.
  12. kbroker-sim — deterministic simulation harness + Jepsen-style fault-injection driver.
  13. kbroker-cli — admin CLI (topics, configs, reassignment, groups).
  14. kbroker-bin — the brokerd binary composing all of the above.

Boundaries. Provides: log storage, replication, produce/fetch, consumer groups, transactions, compaction/retention, quotas, KRaft-style controller metadata. Delegates: TLS to rustls, compression to zstd/lz4/snap/flate2, page-cache management to the OS. Does not provide: a stream-processing DSL, a schema registry, a connector framework, general pub/sub topic dispatch (delegated to sibling PubSub-Messaging, rank 206), a general replication library (delegated to sibling Replication-Protocol, rank 208), or keyed merge-tree storage (delegated to sibling LSM-Tree-Storage).

Non-goals. Not a task queue with per-message acknowledgement/redelivery — contrast PubSub-Messaging (rank 206), whose per-subscriber delivery state and ack/nack semantics are exactly what this design replaces with a client-owned offset (P1, P9). Not a general pub/sub dispatcher — no routed subject/exchange fan-out, no message selectors; a "topic" here is a named set of ordered, offset-addressed partitions. Not a reusable consensus/replication library — the ISR/high-watermark scheme is this system's specific durability mechanism, not a generic abstraction (that generality is Replication-Protocol's concern, rank 208). No stream-processing DSL (no KStreams/Flink-equivalent transform layer). No keyed merge-tree storage engine — the log is flat and offset-ordered; compaction rewrites whole segments, never a leveled sorted-run merge (contrast LSM-Tree-Storage).

Deployment model. Single broker (development); replicated cluster, RF 3 typical (production); controller quorum of 3 or 5 nodes running the KRaft-style metadata Raft (ADR-15). Brokers may co-locate the controller role in small clusters, separate it in large ones.

Users / operators. Application teams producing/consuming event streams; platform SREs operating the cluster (topic creation, reassignment, quota administration); downstream CDC/stream-processing systems as consumers of this log.

What later phases unlock. §15 (Phase 3) unlocks durable single-node produce/fetch; §18 (Phase 6) unlocks multi-broker durability; §20 (Phase 8) unlocks the controller/metadata log; §21 (Phase 9) unlocks horizontally scaled parallel consumption; §22 (Phase 10) unlocks exactly-once semantics and retention economics; §23 (Phase 11) unlocks verified consistency under fault injection.

Language: Rust. Rationale: no GC pause on the append/fetch hot path (tail-latency critical, §4); sendfile/io_uring zero-copy without JVM off-heap workarounds; ownership statically removes the UAF/double-free class a fuzzed wire decoder must be safe against. Rejected: Java/ Scala (GC pauses defeat the p99 fetch target in §4; off-heap buffer juggling for zero-copy is a historic Kafka pain point); Go (GC + scheduler jitter unsuitable for a thread-per-core, io_uring-driven design; weaker control of record-batch memory layout); C++ (manual-lifetime footguns with no corresponding benefit once Rust removes the class).

Prerequisites. Replication/consensus theory (ISR quorums, Raft), on-disk log structures (segment files, sparse indexing), the page-cache-and-sendfile I/O model, TCP framing and backpressure, CRC/checksum theory, distributed transaction protocols (2PC).

Timeline. Phase 0 (§12): 2 weeks. Full system (§12–§23): 9–12 months, small dedicated team; a single-engineer credible MVP (§12–§18) in 4–5 months.

2. Why Build This

  • The unifying abstraction of modern data infrastructure: event sourcing, CDC, microservice integration, and stream processing all sit atop a partitioned commit log.
  • Teaches replication durability contracts (ISR/HW) as distinct from consensus quorums — the two are commonly conflated and the distinction is the crux of most Kafka incidents.
  • Teaches on-disk log engineering: segment rollover, sparse indexing, page-cache-first I/O, zero-copy transfer — a different storage discipline than a keyed LSM engine.
  • Teaches wire-protocol design under live version negotiation (every API key independently versioned) — a harder compatibility problem than a single monolithic schema version.
  • Teaches distributed coordination without an external service: a self-managed metadata Raft (KRaft) replacing ZooKeeper — direct, hands-on consensus engineering (cross-links Replication-Protocol, rank 208, which studies consensus generally; this project studies one concrete, production-proven application of it).
  • Teaches the consumer-group rebalance protocol — a genuinely hard distributed-membership problem most engineers only ever consume as a client, never build.
  • Teaches exactly-once semantics as a systems problem (idempotence + 2PC control records), not a marketing checkbox.
  • Calibration value: after this project, "the log is the database" (Aurora), "sequential I/O beats random memory at scale," and "durability is a config value, not a given" are lived engineering facts, not slogans.

What Mastery Looks Like

  • Explain why offset semantics make replay and fan-out free, and why that is the design choice separating a log from a queue — tied to §12 (Phase 0) and §15 (Phase 3).
  • Derive the exact durability guarantee bought by acks=all + min.insync.replicas and state its RPO without hedging — tied to §18 (Phase 6).
  • Diagnose an unclean-leader-election data-loss incident from leader-epoch history alone — tied to §19 (Phase 7).
  • Design a cooperative-rebalance-safe consumer group that never triggers a rebalance storm — tied to §21 (Phase 9).
  • Implement exactly-once semantics via idempotent producer + two-phase commit markers and prove no partial visibility under coordinator crash — tied to §22 (Phase 10).
  • Quantify when page-cache thrashing defeats the zero-copy fetch path and detect it in production — tied to §16 (Phase 4) and §23 (Phase 11).
  • Run a Jepsen-style fault-injection campaign and correctly interpret an ISR/HW consistency violation — tied to §23 (Phase 11) and §28.

Network Layer / Request Router (kbroker-net). Terminates TLS 1.3 (ADR-25), authenticates via SASL (ADR-26), demultiplexes pipelined requests by correlation id, and is the quota enforcement point (P12) before any request reaches a handler.

Produce Handler. Validates leadership, CRC, and producer sequence contiguity (I1, I5, I7) before appending; implements the acks state machine and the produce purgatory that blocks acks=all callers until the high watermark advances past their offset (P3, P4).

Fetch Handler. Serves offset-addressed reads gated at the high watermark (I2); implements long-poll parking in a fetch purgatory bounded by maxWaitMs; drives the zero-copy path.

Log Manager (kbroker-log). Owns segment files, the sparse OffsetIndex/TimeIndex, append/read paths, retention, and compaction — the persistence boundary all other components cross through, never around.

Page Cache / Zero-Copy Path. No user-space cache is built (ADR-06); reads ride the OS page cache and sendfile/splice directly to the socket (P10, P11).

Retention + Compaction Workers. Background threads independent of consumer position (I12); delete aged/oversized segments and rewrite dirty-ratio-triggered compacted segments (P7).

Replica Fetcher / ISR Manager / HW Tracker. Followers pull via long-poll Fetch RPCs; the ISR manager tracks per-replica lag and shrink/expand eligibility; the HW tracker computes min(LEO) over the ISR and is the sole visibility gate (P4, I3, I4).

Controller + Metadata Log (kbroker-controller). A self-managed Raft-replicated metadata log (KRaft-style, KIP-500) is the single source of truth for partition assignment, leader election, and ISR bookkeeping (P8, I8, I9) — never a broker's unilateral decision.

Group Coordinator / Offset Store. One broker per group hash-routes membership, drives the join/sync/heartbeat/rebalance protocol (§8), and hosts the durable offset-commit cache (P9, I11).

Transaction Coordinator. Hash-routed per transactional id; drives the two-phase commit-marker protocol over a dedicated transaction log (P13, I10).

Quota Manager (kbroker-quota). Enforces per-client-id/user byte-rate budgets by delaying responses, never by dropping or unboundedly queuing (P12, I14).

Telemetry. Every box above emits Prometheus metrics, OpenTelemetry spans, and structured logs (§26); this is not a bolt-on layer, it is wired into each boundary crossing.

6. Design Principles

P1. The log is the primitive. Every higher abstraction (topic, partition, consumer position, transaction) is a view over an append-only offset-addressed log; no component owns hidden per-message state server-side. Tradeoff: replay/fan-out become free at the cost of the server never knowing whether a message was "processed" — that moves entirely to the client's committed offset. Operationally, position is one integer per partition, not a delivery-count per message. Violating it (server-side per-message ack state) collapses replay/fan-out and turns this into a queue (contrast rank-206 PubSub-Messaging).

P2. Ordering is a partition-local contract, not a topic-wide one. Records are strictly ordered within a partition; there is no cross-partition order. Tradeoff: parallelism (partitions fan out to independent leaders) is bought by giving up total order; the producer's partition key IS the ordering contract. Violating it (assuming global order) causes silent reordering bugs invisible until multi-partition load appears.

P3. Durability is exactly what acks and the ISR bought. The acknowledgement level plus min.insync.replicas defines the durability contract; the operator can trade it away, but only knowingly. Tradeoff: acks=all costs a replication round trip to buy zero-loss-on-single- failure; acks=1 buys low latency but loses the leader's unreplicated tail on crash. Violating it (defaulting to acks=1 silently) is the most common real-world Kafka data-loss incident class.

P4. The high watermark is the visibility gate, not the write gate. A leader accepts writes to its log-end-offset (LEO) immediately, but a fetch never returns above the high watermark (HW) — the offset replicated to every ISR member. Tradeoff: a small visibility delay buys the guarantee that anything read cannot vanish on failover. Violating it (serving reads above HW) is a linearizability violation (Herlihy & Wing, 1990).

P5. Leader epochs, not timestamps, resolve log divergence. Every leader change increments a monotonic epoch; a follower truncates to the last offset both leader and follower agree on within an epoch, found via OffsetForLeaderEpoch, never via wall-clock comparison. Violating it reproduces the historic Kafka divergence bug class KIP-101 fixed.

P6. Idempotence is a producer-scoped sequence space, not a broker-wide dedup cache. A broker deduplicates (producerId, producerEpoch, sequence) per partition over a bounded window, not by content hash. Tradeoff: cheap O(1) dedup vs. the requirement that producers request InitProducerId and never skip sequence numbers. Violating it (skipping epoch fencing) lets a zombie producer duplicate or resurrect stale writes.

P7. Compaction preserves keys, not messages. Compaction guarantees the latest record survives for every non-tombstoned key; it makes no promise about intermediate values. Violating it (compacting a topic whose "key" is unique per message) silently deletes data users assumed was retained.

P8. The controller owns metadata; brokers own data. Partition assignment, leader election, and ISR bookkeeping are controller decisions serialized into a replicated metadata log; a data broker never unilaterally declares itself leader. Violating it (self-election) reintroduces the split-brain classes ZooKeeper-based deployments fought.

P9. Consumer position is client state, replicated for convenience. The committed offset is authoritative; the broker's offset store is a durable convenience cache the client can override. Violating it (treating the broker as responsible for reconciling delivery) reintroduces server-side per-message ack state (contrast P1).

P10. Sequential I/O is the whole performance model. Every hot-path write/read is a sequential append or scan through the page cache; random I/O occurs only at sparse-index lookups and cold-cache misses. Violating it (in-place record mutation) destroys the throughput model this design is built on.

P11. Zero-copy is a promise the whole stack must keep. The fetch path uses sendfile/ splice without a userspace copy; any interposed transform (TLS, re-compression) breaks it and must be justified explicitly. Violating it silently (enabling TLS/re-compression without measuring) is the most common "why did throughput halve" incident.

P12. Backpressure is expressed as quotas, not unbounded queues. Every client has a byte-rate quota; the broker throttles by delaying responses, never by dropping or growing an unbounded buffer. Violating it (unbounded per-connection buffering) is a resource-exhaustion vector (T4, §24).

P13. Transactions are atomic across partitions via control records, not a global lock. Atomicity comes from per-partition commit/abort control records coordinated through a two-phase protocol; no cross-partition lock is held. Violating it (skipping the abort-marker path on coordinator failure) permanently stalls read_committed consumers behind an open transaction.

P14. Every number in this design is a chosen tradeoff, not a law of nature. Segment size, index density, ISR lag bound, dirty-ratio trigger, and quota windows are all operator-tunable; §4's defaults encode one point on a latency/durability/cost curve. Violating it (treating defaults as hard limits) causes under- or over-provisioning at scale.

Fixed header = 61 bytes before records. CRC coverage: CRC-32C is computed over every byte from attributes (inclusive) through the end of the last record (inclusive) — baseOffset, batchLength, partitionLeaderEpoch, magic, and crc itself are excluded, since crc must be readable before validation begins.

8.1.1 Record (within a batch), varint-encoded: length (zigzag varint, bytes following) · attributes (int8, reserved) · timestampDelta (zigzag varint, relative to firstTimestamp) · offsetDelta (zigzag varint, relative to baseOffset) · keyLength (zigzag varint, −1 = null) · key (keyLength bytes) · valueLength (zigzag varint, −1 = null = tombstone for compaction) · value (valueLength bytes) · headersCount (zigzag varint) · headers (headerKeyLen, headerKey, headerValueLen, headerValue, repeated).

8.2 Segment File Layout

<topic>-<partition>/
  00000000000000000000.log         # record batches, base offset 0
  00000000000000000000.index       # OffsetIndex: sparse (relOffset, position)
  00000000000000000000.timeindex   # TimeIndex: sparse (timestamp, relOffset)
  00000000000000012345.log         # next segment, rolled at base offset 12345
  leader-epoch-checkpoint          # (epoch, startOffset) pairs
  partition.metadata               # partition-level config snapshot

OffsetIndex entry = 8 bytes: relativeOffset (int32, offset − segment baseOffset) + position (int32, byte offset in .log). TimeIndex entry = 12 bytes: timestamp (int64) + relativeOffset (int32). Density: one entry per index.interval.bytes (default 4,096) of log growth, written for both indexes together.

Offset-lookup procedure, fetch(partition, offset O): (1) binary-search the in-memory sorted segment base-offset list → segment S with S.baseOffset ≤ O < nextSegment.baseOffset. (2) binary-search S's mmap'd OffsetIndex for the largest entry with relativeOffset ≤ O − S.baseOffset → byte position P. (3) seek .log to P. (4) linear-scan forward decoding batch headers until the batch with baseOffset ≤ O ≤ baseOffset + lastOffsetDelta is found. (5) return records from that batch onward up to max_bytes / the long-poll budget. Timestamp lookup (ListOffsets by timestamp) is analogous over TimeIndex.

8.3 Log-Append Path (sequence table)

Step Actor Action
1 Producer sends ProduceRequest with a RecordBatch to the partition leader
2 Leader validates leadership (else NOT_LEADER_OR_FOLLOWER), CRC (else CORRUPT_MESSAGE), sequence contiguity (I5, else OUT_OF_ORDER_SEQUENCE)
3 Leader (kbroker-log) appends to active segment (sequential write), advances LEO
4 Leader updates OffsetIndex/TimeIndex if index.interval.bytes crossed
5 Leader acks=0: no ack; acks=1: ack now; acks=all: park in produce purgatory awaiting HW ≥ appended offset
6 Followers fetch new batch, append locally, advance follower LEO
7 Leader (ISR mgr) recomputes HW = min(LEO over ISR); advances if increased
8 Leader (purgatory) acks=all callers with offset ≤ new HW are unblocked and acked

8.4 Log-Read (Fetch) Path (sequence table)

Step Actor Action
1 Consumer sends FetchRequest(partition, fetchOffset, maxBytes, maxWaitMs, minBytes)
2 Leader validates fetchOffset ∈ [logStartOffset, HW] (else OFFSET_OUT_OF_RANGE)
3 Leader offset-lookup procedure (8.2) locates byte position
4 Leader bytes available ≥ minBytes → sendfile immediately
5 Leader else park in fetch purgatory up to maxWaitMs (long poll)
6 Leader on HW advance or maxWaitMs expiry (first wins) → complete with available bytes
7 Consumer decodes batches, advances local position, later commits offset (8.9)

8.5 ISR / High-Watermark Model

Display equations: LEO(replica) = last written offset + 1. HW(partition) = min({ LEO(r) : r ∈ ISR(partition) }). Visibility bound: a fetch may return offset < HW(partition) only.

ISR shrink (exact condition): replica r is evicted when (now − r.lastCaughtUpTimeMs) > replica.lag.time.max.ms (default 10,000 ms), where lastCaughtUpTimeMs is the last time r.LEO ≥ leader.LEO at the start of r's fetch request. ISR expand (exact condition): r is re-added when r.LEO ≥ HW(partition) at fetch time, refreshing lastCaughtUpTimeMs whenever r.LEO ≥ leader.LEO.

State Trigger Next State Effect on HW
In ISR, caught up fetch with r.LEO ≥ leader.LEO remains in ISR eligible to raise HW
In ISR, lagging lag exceeds replica.lag.time.max.ms evicted HW over shrunk ISR; shrink event logged
Out of ISR, catching up fetch with r.LEO ≥ HW re-added eligible once fully caught up
Leader always always in ISR —

LEO vs. HW: LEO is the leader's private "how much I've written" pointer, advancing instantly on append. HW is the cluster's "how much is safe to read" pointer, advancing only once all ISR members match. Consumers see only up to HW; [HW, LEO) is uncommitted-to-all- replicas data (P4).

8.6 Leader Epoch and Truncation — Worked Example

Setup: partition P, RF=3, {A(leader, epoch 5), B, C}. A wrote offsets 0–99 in epoch 5, replicated fully to B (LEO 100), C only to offset 80 (LEO 80), when A crashes.

Step Event Epoch A LEO B LEO C LEO
1 A leader, writes 0–99 5 100 100 80
2 A crashes — — 100 80
3 Controller elects B (only ISR member alive) 6 — 100 80
4 C fetches from B, presents (epoch 5, offset 80) 6 — 100 80
5 B answers OffsetForLeaderEpoch(5) → end-of-epoch-5 offset = 100 6 — 100 80
6 C truncates to min(80, 100) = 80 (no-op here), fetches 80→ under epoch 6 6 — 100 100
7 leader-epoch-checkpoint on all brokers records (epoch 6, startOffset 100) 6 — 100 100

Divergence example (real loss): if A had instead acked offsets 90–99 at acks=1 (not acks=all) before crashing, and B's LEO was only 90, offsets 90–99 are gone — the producer was told "success" for records no surviving replica holds. This is exactly the RPO acks=1 buys (§4, P3).

Level Durability Guarantee RPO

acks=1 leader has appended locally, not yet replicated leader's unreplicated tail at crash

8.8 Idempotent Producer and Transactions

Sequence-number model: producer requests (producerId, producerEpoch) via InitProducerId; each partition's ProducerStateManager tracks the highest sequence seen per (producerId, epoch) over the last 5 batches. sequence == lastSeen + 1 → accept, advance window. sequence within the last-5 recorded range → duplicate, re-acknowledge without re-append (I5). A larger unexpected gap → OUT_OF_ORDER_SEQUENCE, forcing producer reinitialization (P6).

Transaction protocol (sequence table, KIP-98):

Step Actor Action
1 Producer FindCoordinator(transactionalId) locates the transaction coordinator
2 Producer InitProducerId → coordinator bumps epoch, fences prior epoch (zombie fencing)
3 Producer AddPartitionsToTxn for each partition touched → coordinator appends to txn log
4 Producer produces records tagged transactional, (producerId, epoch)
5 Producer EndTransaction(commit | abort)
6 Coordinator writes PrepareCommit/PrepareAbort to the transaction log
7 Coordinator sends WriteTxnMarkers control record to every partition leader involved
8 Leaders append the ControlRecord, marking the transaction's records committed/aborted
9 Coordinator after all partitions ack, writes CompleteCommit/CompleteAbort
10 Consumer (read_committed) advances LSO past the transaction only on observing the control record; coordinator crash-recovery rescans the txn log and completes any hanging Prepare* state

Offset-commit model: OffsetCommit(groupId, generationId, memberId, {partition→(offset, metadata)}), validated against I11; stored in the group coordinator's compacted offset store. OffsetFetch returns the last committed offset or none, and the consumer applies auto.offset.reset (earliest/latest/none).

8.10 Retention and Compaction

Retention worker scans segments per partition, deletes segments whose max timestamp < now − retention.ms, or whose deletion keeps partition size under retention.bytes; the active segment is never deleted. Compaction: dirty ratio = dirtyBytes ÷ totalBytes (bytes written since the last compaction point); eligible once dirty ratio ≥ min.cleanable.dirty.ratio (0.5, §4); build an offset map (key → latest offset) over dirty segments; rewrite forward only the latest record per key (or a tombstone within delete.retention.ms). Tombstone-retention rule: a null-value record for key K survives delete.retention.ms past compaction so lagging consumers still observe the deletion, then is dropped on the next pass (I6).

8.11 Worked End-to-End Example

Producer P1 sends 3 records, key "user-42", topic clicks partition 3, acks=all, RF=3 (leader A, followers B/C, min.insync.replicas=2). A: LEO 1000→1003. B, C fetch and append, LEO→1003. ISR={A,B,C}; HW = min(1003,1003,1003) = 1003. A acks all 3 records to P1. Consumer group analytics fetches partition 3 from offset 1000, maxWaitMs=500: HW=1003 ≥ requested → immediate sendfile of the 3 records; consumer processes, commits offset 1003 via OffsetCommit(groupId="analytics", generationId=7).

8.12 Malformed-Input Examples

  • CRC mismatch: recomputed CRC-32C ≠ stored crc → CORRUPT_MESSAGE; batch rejected before append (produce) or fetch aborted with a corruption alert (read) — never partially applied.
  • Batch length exceeds request: batchLength claims more bytes than remain in the received buffer → INVALID_RECORD, connection-level framing error, no partial decode.
  • Out-of-range offset fetch: fetchOffset < logStartOffset or > HW → OFFSET_OUT_OF_RANGE; client calls ListOffsets and resets per auto.offset.reset.
  • Sequence-number gap: baseSequence ≠ lastSeen + 1 → OUT_OF_ORDER_SEQUENCE; producer must call InitProducerId again.
  • Produce to a non-leader: a follower-holding broker receives a ProduceRequest for that partition → NOT_LEADER_OR_FOLLOWER; client refreshes Metadata and retries.
  • Offset commit for an unowned partition: references a partition outside the member's current assignment (post-rebalance race) → ILLEGAL_GENERATION/UNKNOWN_MEMBER_ID; client rejoins the group.

8.13 Failure-Path Example: Unclean Leader Election

Partition P, RF=3. B and C are network-partitioned (alive, unreachable) and evicted from ISR after replica.lag.time.max.ms; ISR shrinks to {A}. A continues at acks=all, min.insync.replicas=1 (degraded but available), appending offsets 5000–5049, then suffers a fatal disk failure. B and C rejoin the network with LEO ≤ 4999. With unclean.leader.election.enable=true, the controller elects B though it is not in the last known ISR, restoring availability. Exactly what is lost: offsets 5000–5049 (50 records), acknowledged at acks=all under a degraded min.insync.replicas=1 ISR — the RPO for that window was exactly this. With unclean.leader.election.enable=false, the partition instead stays unavailable until A recovers — trading availability for the zero-loss guarantee. This is the documented Kafka unclean-leader-election tradeoff and the exact scenario Kingsbury's Jepsen analyses probe for.

12. Phase 0 — Skeleton, Segment Append/Read, CI

12.1 Objectives

Stand up the workspace (§10's 14 crates), a single-partition Log (§11) that appends raw byte records and reads them back sequentially, and CI. No wire protocol, no replication, no compression yet — establishes the persistence boundary (§3) all later phases build on.

12.2 Detailed Implementation Steps

kbroker-types: define TopicPartition, Offset, LeaderEpoch (P1's addressing scheme). kbroker-log: implement Segment as a single .log file opened O_APPEND; Log::append writes length-prefixed raw byte records sequentially (ADR-04, P10); Log::read_from(offset) linear-scans from file start (no index yet — I7's index-boundary invariant is introduced in §14). Startup recovery scan (I13) validates the last record is fully written by checking the declared length against remaining file bytes; truncates on partial-write detection. CI (.github /workflows/ci.yml, ADR-32) runs cargo test + cargo clippy + cargo fmt --check on every PR.

12.3 Deliverable

A brokerd-embeddable Log that appends and reads back records from one partition on local disk, with cargo test green in CI.

12.4 Acceptance Criteria

Sustained sequential append ≥ 200 MB/s on NVMe (single partition, no fsync); kill -9 mid-write followed by restart loses at most the last unterminated record (I13); fixture fixtures/append_1m_records.bin round-trips byte-identical through append→read for 1,000,000 records.

12.5 Conformance Fixtures

fixtures/append_basic.bin — 100 records, verifies offset order (I1). fixtures/ truncated_write.bin — a file with a deliberately partial last record, expects recovery-scan truncation. fixtures/empty_segment.bin — zero-record segment, expects clean open/close. fixtures/power_loss_sim.bin — simulated kill -9 at 17 injected byte offsets, expects no corruption above the recovery point (I13).

12.6 Pitfalls

Assuming write(2) is atomic across process crash — it is not; a partial write must be detected by length-prefix validation, not assumed absent. Root cause: page-cache-buffered writes are not durable until fsync; signal: recovery-scan finds a record whose declared length exceeds remaining bytes; debug via truncated_write.bin; recovery: truncate to last fully-written record (I13). Forgetting O_APPEND and relying on external seek-then-write races the writer against itself under concurrent access — enforced instead by single-writer- per-partition (I1).

12.7 Performance Concerns

Every append is a syscall; batching multiple records per write(2) call (introduced fully in §13) is deferred here but the API is shaped to allow it. Avoid fsync per record in this phase — it caps throughput at disk seek latency, not sequential bandwidth (P10).

12.8 Edge Cases

Zero-length record, maximum-length record (bounded by batch.length field width, introduced §13), concurrent read during an in-flight append (reader must never see a torn write), restart immediately after segment creation with zero records written.

12.9 Failure Analysis

Disk full mid-append → write(2) returns ENOSPC; the append must fail atomically (no partial record persisted) and surface to the caller, never silently truncate valid data. Detection: integration test fills a small tmpfs partition. Blast radius: single partition unavailable for writes; recovery: operator frees space, broker retries.

12.10 Operational Notes

Metrics: log.append.bytes_total, log.recovery.duration_ms. No rollback/migration concerns yet (single-file format, versioned from §14 onward).

13. Phase 1 — Record-Batch Format, CRC, Compression

13.1 Objectives

Replace Phase 0's raw byte records with the full record-batch v2 wire layout (§8.1): CRC-32C validation and per-batch compression (ADR-07, ADR-08, ADR-09).

13.2 Detailed Implementation Steps

kbroker-record: implement RecordBatch encode/decode exactly per §8.1's byte-layout table (base offset, batch length, partition leader epoch, magic, CRC, attributes, timestamps, producer fields, records count) and §8.1.1's varint Record layout. CRC-32C (RFC 3385) computed over attributes-through-end-of-records per §8.1's coverage rule — implement using the hardware crc32c intrinsic where available (ADR-09). Compression: pluggable CompressionType (ADR-08) wrapping the records payload before CRC computation, using flate2 (gzip, RFC 1952), snap (Snappy), lz4_flex (LZ4), zstd (Zstandard) crates — each validated against its published format specification (§5 RFCs/Specifications). kbroker-log::Log::append now takes a RecordBatch, not raw bytes.

13.3 Deliverable

kbroker-record round-trips a RecordBatch through encode→disk→decode with CRC validation, for all four compression codecs plus uncompressed.

13.4 Acceptance Criteria

CRC validation rejects 100% of single-bit-flip corruption in a 10,000-trial fuzz corpus; round-trip encode/decode is byte-identical for fixtures/batch_roundtrip_{codec}.bin (5 files, one per codec + none); compression ratio ≥ 2.5x on fixtures/compressible_payload.bin (repetitive JSON) for zstd.

13.5 Conformance Fixtures

fixtures/batch_roundtrip_none.bin, _gzip.bin, _snappy.bin, _lz4.bin, _zstd.bin — encode/decode parity per codec. fixtures/crc_mismatch.bin — single flipped bit, expects CORRUPT_MESSAGE (§8.12). fixtures/batch_length_overflow.bin — batchLength field exceeding buffer size, expects INVALID_RECORD without a partial decode (§8.12).

13.6 Pitfalls

Computing CRC over the wrong byte range (including baseOffset/magic) breaks interop with any real Kafka client — verify against §8.1's exact coverage statement. Root cause: copy-pasting a CRC helper without re-deriving the covered range; signal: kcat-equivalent client rejects every batch; debug via a byte-for-byte diff against a real Kafka-produced batch. Decompression bombs (T3, §24): a small compressed batch expanding to gigabytes — mitigated by enforcing recordsCount and a max-decompressed-size ceiling before allocating the output buffer.

13.7 Performance Concerns

Compression is CPU-bound and sits directly in the produce hot path; codec choice trades CPU for network/disk bytes (ADR-08). CRC-32C with hardware acceleration costs ≈ 1 cycle/byte; verify via a microbenchmark that the software fallback path is never silently used on CRC32C-capable hardware.

13.8 Edge Cases

Empty batch (zero records), a batch with only tombstone (null-value) records, maximum recordsCount, a compressed batch whose declared batchLength is correct but whose compressed payload is truncated (decompression must fail cleanly, not read out-of-bounds).

13.9 Failure Analysis

A decompression bomb that isn't bounded before allocation risks broker OOM — this is the security-relevant instance of a performance pitfall; see T3 (§24) for the threat-model treatment and the same mitigation (declared-size ceiling check before allocation).

13.10 Operational Notes

Metrics: record_batch.crc_failures_total, record_batch.compression_ratio (per codec). Per-topic compression codec is a config value, not a code change — operators can switch codecs without a broker rebuild.

14. Phase 2 — Sparse Offset/Time Index, Recovery on Restart

14.1 Objectives

Add the sparse OffsetIndex/TimeIndex (§8.2, ADR-05) enabling O(log n)-then-scan offset lookup instead of Phase 0's linear scan from file start; harden crash recovery (I13) now that segments carry index files that must stay consistent with the log.

14.2 Detailed Implementation Steps

kbroker-log::index: implement OffsetIndex (8-byte entries: relativeOffset, position) and TimeIndex (12-byte entries: timestamp, relativeOffset) as mmap'd fixed-width arrays (ADR-05), appended once per index.interval.bytes (default 4,096, §4) of log growth alongside each batch append. Implement the offset-lookup procedure exactly as five named steps in §8.2 (binary-search segment list → binary-search index → seek → linear-scan batch headers → return). On startup, if the recovery-point file (I13) is stale or absent, rebuild both index files by rescanning the segment and re-validating every batch's CRC (I7).

14.3 Deliverable

Offset-addressed and timestamp-addressed (ListOffsets-equivalent) lookup against a multi-segment log, with index rebuild verified after a simulated unclean shutdown.

14.4 Acceptance Criteria

Offset lookup for any offset in a 10 GB log completes in ≤ 2 ms (index binary search + ≤4 KB scan); index rebuild after unclean shutdown completes within segment_bytes / 500 MB/s per segment (§34's recovery-time model); fixtures/index_rebuild_after_crash.bin produces an index byte-identical to one built incrementally.

14.5 Conformance Fixtures

fixtures/sparse_index_lookup.bin — 50,000 records across 12 segments, verifies exact-offset and nearest-preceding lookups. fixtures/index_rebuild_after_crash.bin — index files deleted, expects full rebuild matching original. fixtures/misaligned_index_entry.bin — a deliberately corrupted index entry pointing mid-batch, expects I7's detection (CRC mismatch on the mis-resolved batch) and index rebuild, not a decode crash.

14.6 Pitfalls

Writing an index entry before the corresponding batch is durably appended risks I7 violations on crash (an index entry resolving to a not-yet-written position). Root cause: index-write and log-write ordering swapped; signal: misaligned_index_entry.bin-style corruption after a crash test; debug via forcing a crash between the two writes in kbroker-sim; recovery: always write the log record first, index entry second, and treat any index entry beyond the log's current size as invalid on recovery.

14.7 Performance Concerns

mmap'd index files avoid a syscall per lookup but pull pages into RAM — index memory scales with segment_bytes / index.interval.bytes per open segment (quantified in §34); denser indexes trade RAM for a shorter linear-scan tail (P14).

14.8 Edge Cases

Offset lookup for the very last (uncommitted) record in the active segment; timestamp lookup for a timestamp before the first record (returns earliest offset) or after the last (returns none, per real Kafka's ListOffsets semantics); index file present but log segment missing (corrupt deployment, must fail loudly, not silently serve stale data).

14.9 Failure Analysis

A corrupt index causing a wrong-offset read is caught by I7's CRC-boundary check downstream, never trusted blindly — this is why index corruption degrades to "slow rebuild," not "wrong data served." Blast radius: one partition's recovery time increases; no data-correctness impact given I7 enforcement.

14.10 Operational Notes

Metrics: index.lookup.duration_ms, index.rebuild.count. Rebuilding all indexes on every restart (rather than trusting recovery-point) is a valid degraded-but-safe operational fallback when recovery-point tracking itself is suspected corrupted.

15. Phase 3 — Produce Path, Acknowledgement Levels

15.1 Objectives

Implement the produce handler (§3, §8.3): leadership/CRC/sequence validation, the acks state machine (P3, ADR-10), and — even single-broker — the produce purgatory mechanism that acks=all will later block on once replication exists (§18).

15.2 Detailed Implementation Steps

kbroker-broker::produce: validate leadership (single-broker Phase 3 is trivially always leader; the check is wired now so §17 needs no rework), validate CRC (§13, I7), validate sequence contiguity against ProducerStateManager (I5, P6) — introduce InitProducerId handling in kbroker-broker even though full idempotence semantics land in §22, since the sequence-window bookkeeping must exist before replication complicates it. Implement AckLevel (§11): acks=0 returns immediately post-enqueue; acks=1 returns after Log::append durably returns; acks=all parks the request in a purgatory keyed by (partition, offset) that (in this single-broker phase) resolves immediately since HW = LEO with no followers — the purgatory's replication-driven wakeup path is exercised for real in §18.

15.3 Deliverable

A single-broker brokerd accepting ProduceRequests over the wire protocol (§14's protocol crate now carries Produce/ApiVersions/Metadata) at all three ack levels, sequence-deduping idempotent producer retries.

15.4 Acceptance Criteria

Produce throughput ≥ 400 MB/s sustained at acks=1 (single broker, NVMe, batched 16 KB requests); p99 produce latency ≤ 8 ms at acks=1 per §4; fixtures/idempotent_retry.bin — a duplicated batch (same producerId/epoch/sequence) is acknowledged without a second append (I5); fixtures/sequence_gap.bin returns OUT_OF_ORDER_SEQUENCE (§8.12).

15.5 Conformance Fixtures

fixtures/produce_acks0.bin, _acks1.bin, _acksall.bin — one per ack level, verifying response timing semantics. fixtures/idempotent_retry.bin — exact duplicate batch. fixtures/ sequence_gap.bin — a gap beyond the last-5-batches window. fixtures/produce_to_non_leader.bin — (stubbed single-broker; exercised fully in §17) expects NOT_LEADER_OR_FOLLOWER once multi-broker leadership checks are live.

15.6 Pitfalls

Acknowledging acks=all before HW actually reflects the write (trivial to get wrong once followers exist in §17-18) — caught here by wiring the purgatory's interface correctly even though single-broker HW=LEO makes the bug unobservable yet; a regression test asserting ack_all_latency ≈ ack_1_latency in single-broker mode catches accidental early-return logic before §18 makes the difference load-bearing. Sequence-window eviction bugs: keeping only the last 5 batches per (producerId,epoch) means a producer retrying after a 6th batch already elapsed is wrongly treated as a gap — bounded by producer.id.expiration.ms, not batch count alone, in a full implementation; document the exact window semantics precisely (P6).

15.7 Performance Concerns

Batching multiple records per produce RPC amortizes wire-protocol framing overhead (ADR-07); CRC computation (§13) and sequence-check are both O(batch), not O(records), keeping the hot path allocation-light. Lock contention on ProducerStateManager per partition must be sharded per-partition, never a single global lock (P10, ADR-02's thread-per-core shard model).

15.8 Edge Cases

Producer sends acks=all with min.insync.replicas unset (defaults apply); a produce request spanning a segment roll boundary mid-batch (must not split a batch across segments — a batch is always fully contained in one segment); a zero-record produce request (rejected as malformed, not silently accepted).

15.9 Failure Analysis

A broker crash between Log::append returning and an acks=1 response being sent loses that ack in flight — the producer sees a timeout, not a false failure, and must retry idempotently (I5 makes the retry safe). Detection: client-side timeout; recovery: idempotent retry, no duplicate.

15.10 Operational Notes

Metrics: produce.latency_ms (histogram, per ack level), produce.bytes_in_total, produce.sequence_gap.count. InitProducerId churn (frequent producer restarts) is visible as producer_id.init.count and should correlate with client-side restart events, not broker issues.

16. Phase 4 — Fetch Path, Long Poll, Zero-Copy

16.1 Objectives

Implement the fetch handler (§3, §8.4): HW-gated offset-addressed reads, long-poll parking, and the zero-copy sendfile path (P10, P11, ADR-06).

16.2 Detailed Implementation Steps

kbroker-broker::fetch: validate fetchOffset ∈ [logStartOffset, HW] (I2, else OFFSET_OUT_OF_RANGE); use the offset-lookup procedure (§8.2) to locate the byte position; if minBytes is already satisfied, invoke sendfile(log_fd, socket_fd, position, len) directly — no userspace buffer copy (P11). If not satisfied, park the request in a fetch purgatory keyed by partition, woken on either HW advance (from the ISR manager, wired fully in §18) or maxWaitMs expiry, whichever first (§8.4's seven-step sequence table). Verify the zero-copy path with a strace/perf-based test asserting a sendfile(2) syscall appears and no read/write pair on the data path when TLS is disabled (ADR-25 notes TLS breaks this — tracked, not solved, here).

16.3 Deliverable

A fetch handler serving long-poll reads at the high watermark boundary, with a measured zero-copy path on the plaintext transport.

16.4 Acceptance Criteria

Fetch throughput ≥ 800 MB/s from page cache (single broker, plaintext, per §4); p99 long-poll wakeup latency ≤ 5 ms after HW advances; fixtures/fetch_at_hw_boundary.bin confirms a fetch requesting an offset exactly at HW returns zero records (not an error) and completes only after maxWaitMs or a subsequent HW advance; zero sendfile syscall count regressions gated in bench-regression.yml (ADR-32).

16.5 Conformance Fixtures

fixtures/fetch_offset_out_of_range.bin — offset below logStartOffset and above HW, both paths, expects OFFSET_OUT_OF_RANGE (§8.12). fixtures/long_poll_timeout.bin — no new data within maxWaitMs, expects an empty-but-successful response at expiry. fixtures/ long_poll_early_wakeup.bin — a produce arrives mid-park, expects wakeup before maxWaitMs.

16.6 Pitfalls

Serving a fetch above HW because the fetch handler reads LEO instead of HW is a direct I2 violation — manifestation: a consumer observes a record later erased by unclean failover; root cause: handler queried the wrong offset accessor; debug via kbroker-sim's per-fetch HW assertion; signal: fetch.above_hw.count nonzero; recovery: none — this is a shipped-bug rollback, not an operational recovery. A long-poll purgatory that never times out under sustained low traffic leaks parked-request memory — bounded by enforcing maxWaitMs as a hard timer, not a best-effort one.

16.7 Performance Concerns

sendfile is defeated by TLS (P11) — kernel TLS (kTLS) offload is the mitigation path, tracked as a Phase-11 hardening item (§23), not solved here; measure, don't assume, that zero-copy holds once TLS is enabled later. Purgatory implementation must avoid a per-request timer thread — use a single hashed-timer-wheel to bound O(log n) timeout management across thousands of parked fetches (P10's syscall-budget discipline extends to timer management).

16.8 Edge Cases

minBytes larger than the entire partition's available data (must not block forever — bounded by maxWaitMs regardless); a fetch spanning a segment boundary (must stitch batches from two segments transparently); a fetch offset that is valid but the segment was just deleted by retention between validation and read (must re-validate or retry, not read a dangling fd).

16.9 Failure Analysis

A slow consumer causing fetch purgatory buildup is a capacity problem, not a correctness one — detection via fetch.purgatory.depth metric; blast radius is memory pressure on the broker, contained by a purgatory-size ceiling that rejects new long-polls with a retriable error past threshold.

16.10 Operational Notes

Metrics: fetch.latency_ms (histogram), fetch.bytes_out_total, fetch.purgatory.depth, fetch.sendfile.count (verifies P11 in production, not just in the benchmark harness).

17. Phase 5 — Leader/Follower Replication, Replica Fetcher

17.1 Objectives

Multi-broker replication: followers pull from the leader via long-poll Fetch RPCs (Wang et al. 2015; Petrov, Database Internals, replication chapter), advancing follower LEO (§8.3 step 6). ISR/HW wiring lands fully in §18 — this phase makes replication data flow, not yet the durability contract.

17.2 Detailed Implementation Steps

kbroker-replication::fetcher: each follower broker runs one FetcherCursor (§11) per partition it replicates, issuing Fetch RPCs to the current leader with next_fetch_offset, long-polling exactly like a consumer (reusing §16's fetch handler design — replication is "just another consumer" at the protocol level, per Kreps 2011). On response, kbroker-log::Log::append applies the batch locally (sequential write, P10) and advances the follower's LEO. Leader-side: track each follower's reported LEO from its Fetch requests (ADR-13's piggyback mechanism, laid groundwork here, HW computed fully in §18). Broker startup now also resolves partition leadership from the (stubbed pre-controller, real in §20) metadata assignment.

17.3 Deliverable

A 3-broker cluster where a follower's log becomes byte-identical to the leader's for a continuously-produced partition, verified by content hash comparison.

17.4 Acceptance Criteria

Follower replication lag ≤ 50 ms at steady state under §4's throughput target; killing a follower and restarting it catches up to the leader within segment_bytes_behind / 500 MB/s (bounded catch-up rate); fixtures/replica_catch_up_after_restart.bin verifies byte-identical logs post-recovery.

17.5 Conformance Fixtures

fixtures/replica_steady_state.bin — 3 brokers, sustained produce, periodic hash comparison. fixtures/replica_catch_up_after_restart.bin — follower killed and restarted mid-stream. fixtures/replica_network_partition.bin — follower partitioned for 30s then reconnected, expects it resumes fetching from its last cursor without data loss or duplication.

17.6 Pitfalls

Treating replication as a separate protocol from consumer fetch (rather than reusing §16's fetch handler) doubles the maintained code paths and doubles the chance of an HW-gating bug (I2) existing in one path but not the other — root cause: premature specialization; debug by diffing the two fetch implementations; recovery: unify onto one fetch handler parameterized by caller type (P1's "one primitive" principle applied to code structure, not just data model). Unbounded fetcher retry on a partitioned follower can spin-loop wastefully — bounded by exponential backoff on repeated Fetch failures.

17.7 Performance Concerns

Each follower's fetcher thread/task must not block on a single partition's long-poll while other partitions from the same leader are ready — replication fetch requests should batch multiple partitions per RPC (as real Kafka does) to bound RPC count, not partition count (ADR-02's thread-per-core sharding applies here too).

17.8 Edge Cases

A follower that was never in the ISR (freshly added replica, e.g. after reassignment) doing a full historical catch-up from logStartOffset, not just recent offsets; a leader with zero followers currently reachable (degrades toward the §8.13 failure-path scenario, formalized in §18-19); duplicate Fetch requests from a follower after a spurious retry (must be idempotent — re-fetching the same offset range is safe, unlike a produce retry).

17.9 Failure Analysis

A follower whose disk is slower than the leader's produce rate falls permanently behind — detection via replica.lag.bytes trending upward without bound; this is the precursor to an ISR eviction (§18) and, if all followers are this slow, a cluster-wide durability degradation that must page before an actual failure compounds it.

17.10 Operational Notes

Metrics: replica.lag.messages, replica.lag.bytes, replica.fetch.latency_ms. This phase's correctness is necessary but not sufficient for durability — §18's ISR/HW gate is what actually turns replicated bytes into a durability guarantee (P4).

18. Phase 6 — ISR Set, High-Watermark Advancement

18.1 Objectives

Wire the ISR manager and HW tracker (§8.5, P3, P4) for real: acks=all now genuinely blocks until the high watermark advances past the produced offset, and the ISR shrink/expand state machine (§8.5 table) governs which replicas count.

18.2 Detailed Implementation Steps

kbroker-replication::isr: implement Isr (§11) with last_caught_up_ms per replica, applying the exact shrink condition ((now − lastCaughtUpTimeMs) > replica.lag.time.max.ms, default 10,000 ms, §4) and expand condition (r.LEO ≥ HW at fetch time) from §8.5. HighWatermark computation: HW = min(LEO over ISR), recomputed on every follower Fetch response (ADR-13). Wire the produce purgatory (§15.2, stubbed) to genuinely unblock only when HW advances past the acked offset (I4). Emit ISR-shrink/expand events to the metadata log (stubbed controller interface, real in §20) since ISR membership is cluster-visible state (P8).

18.3 Deliverable

acks=all producers observably wait for real multi-broker replication before acknowledgement; an induced follower slowdown triggers a measurable ISR shrink event.

18.4 Acceptance Criteria

acks=all p99 latency ≤ 20 ms at RF=3 (§4); ISR shrink fires within replica.lag.time.max.ms + 500ms of an induced 15-second follower stall (fixtures/induced_follower_stall.bin); HW never advances past the minimum ISR-member LEO in 100,000 simulated produce/replicate interleavings (kbroker-sim property test, I4).

18.5 Conformance Fixtures

fixtures/isr_shrink_on_stall.bin — one follower paused 15s, expects eviction and logged event. fixtures/isr_expand_on_catchup.bin — evicted follower resumes, expects re-admission once LEO ≥ HW. fixtures/acks_all_blocks_until_hw.bin — asserts the produce response is not sent before HW crosses the produced offset, using an injected artificial replication delay.

18.6 Pitfalls

Computing HW as min(LEO over all replicas) instead of min(LEO over ISR only) silently demotes durability to the slowest replica cluster-wide, even one already correctly evicted — manifestation: acks=all latency spikes to match a dead/lagging replica instead of ignoring it; root cause: HW computation read the full replica set, not the current ISR; debug via comparing isr.size against the replica count at the moment of the latency spike; recovery: fix the computation to filter by current ISR membership. A stuck ISR shrink (evicted replica never recovers, and the operator never reduces RF) cascades toward min.insync.replicas unavailability if a second replica also degrades — this is FM-class material (§25).

18.7 Performance Concerns

HW recomputation on every follower Fetch response must be O(ISR size), not O(log size) — maintain the per-replica LEO map incrementally, never rescan the log to derive it. Purgatory wakeup on HW advance must batch-wake all satisfied waiters in one pass, not one wakeup per waiter causing thundering-herd lock contention (P10's lock-contention discipline).

18.8 Edge Cases

ISR shrinks to exactly min.insync.replicas (still available, degraded); ISR shrinks below min.insync.replicas (produce at acks=all must now fail with a retriable NOT_ENOUGH_REPLICAS error, not silently downgrade durability); simultaneous shrink and expand events racing on the same replica within one lag-check interval.

18.9 Failure Analysis

ISR shrinking to 1 member (the leader alone) is the exact precondition for the §8.13 unclean- election data-loss scenario — this phase's telemetry (isr.size == 1 sustained) is the leading indicator operators must alert on (§26: "under-replicated partitions... is one of the two alerts that matter").

18.10 Operational Notes

Metrics: isr.size, isr.shrink_count, isr.expand_count, under_replicated_partitions (count of partitions with isr.size < replication_factor — the single most important operational signal in this whole system, per §26).

19. Phase 7 — Leader Epochs, Truncation, Leader Election

19.1 Objectives

Implement leader-epoch fencing and follower truncation (§8.6, P5, I3) and controller-driven leader election on failure — closing the exact data-divergence bug class KIP-101 fixed.

19.2 Detailed Implementation Steps

kbroker-replication::epoch: maintain the leader-epoch-checkpoint file (§8.2) as an ordered list of (LeaderEpoch, startOffset) pairs, appended on every leader change. Implement OffsetForLeaderEpoch request handling: given a requested epoch, return the end-offset of that epoch on the responding broker's log (§8.6's worked example). Follower truncation procedure: on becoming a follower of a new leader/epoch, issue OffsetForLeaderEpoch for its last known epoch, truncate its log to min(own LEO, returned end-offset) before resuming fetch (I3). Leader election (stubbed controller, formalized in §20): on leader failure, elect from the current ISR by default; implement unclean.leader.election.enable as a per-topic config gate (ADR-14) that, when true, permits electing a non-ISR replica and logs the exact offset range at risk (§8.13).

19.3 Deliverable

A killed leader triggers automatic re-election from the ISR, with followers correctly truncating to the epoch-fenced divergence point — reproduce §8.6's worked example as an integration test.

19.4 Acceptance Criteria

Leader failover completes ≤ 5 s (§4); fixtures/epoch_divergence_recovery.bin reproduces §8.6's exact scenario and asserts follower log becomes a byte-identical prefix of the new leader's (I3); fixtures/unclean_election_data_loss.bin reproduces §8.13 and asserts the lost-offset range is logged with exact bounds, not silently swallowed.

19.5 Conformance Fixtures

fixtures/epoch_divergence_recovery.bin — §8.6's worked example, byte-for-byte. fixtures/ clean_election_no_loss.bin — ISR-only election, asserts zero data loss. fixtures/ unclean_election_data_loss.bin — §8.13's scenario, asserts the exact 50-offset loss window is both real (data verifiably gone) and observable (logged/metriced, not silent).

19.6 Pitfalls

Using wall-clock timestamps instead of OffsetForLeaderEpoch to decide truncation reproduces the historic Kafka data-divergence bug (P5) — manifestation: two replicas silently diverge after a leader change under clock skew; root cause: timestamp-based truncation compared un-synchronized clocks; debug via injecting clock skew in kbroker-sim and asserting I3 still holds; recovery: the fix is architectural (switch to epoch-based truncation), not operational. Failing to persist the leader-epoch-checkpoint durably before acking a leader-change means a crash mid-transition loses the fencing information needed for the next election.

19.7 Performance Concerns

OffsetForLeaderEpoch must be O(number of epochs), not O(log size) — the checkpoint file is small (one entry per leader change, not per record) and fits in memory per partition.

19.8 Edge Cases

A follower requesting OffsetForLeaderEpoch for an epoch older than the leader's oldest retained checkpoint entry (must return the earliest known offset, not fail); two leader changes in rapid succession before any follower catches up to either; a follower that was offline across multiple epoch changes needing to walk the checkpoint chain across several epochs, not just the most recent one.

19.9 Failure Analysis

An unclean election is not a bug — it is a configured tradeoff whose exact cost (§8.13) must be computed and logged every time it fires, feeding directly into the postmortem process (§25) and the "exactly what was lost" question every such incident must answer.

19.10 Operational Notes

Metrics: leader_election.count, leader_election.unclean_count, leader_election.duration_ms, replica.truncation.offset_range. Runbook docs/runbooks/unclean-election-decision.md (§26) governs the manual decision to enable unclean election on a specific topic during an incident.

20. Phase 8 — Controller and Metadata Log

20.1 Objectives

Replace every phase's stubbed controller interface with a real self-managed metadata Raft (KRaft-style, KIP-500, ADR-15): partition assignment, leader election (§19), and ISR bookkeeping (§18) become genuine controller decisions serialized into a replicated MetadataRecord log (P8, I8, I9).

20.2 Detailed Implementation Steps

kbroker-controller::raft: implement leader election among a 3- or 5-node controller quorum (Ongaro & Ousterhout 2014's Raft algorithm — election timeout, majority vote, log replication to majority before commit) purpose-built for the metadata-log workload, not general application data. metadata_log: append MetadataRecord variants (TopicRecord, PartitionRecord, LeaderChangeRecord, ProducerIdsRecord, §11) as the sole authoritative cluster state; brokers subscribe to this log exactly like consumers subscribe to a topic (P1 applied to the control plane itself — "eating your own dog food," ADR-16). assignment: implement a partition-assignment strategy (round-robin across brokers with rack-awareness) invoked on topic creation and broker join/leave. Controller epoch fencing (I8): every LeaderAndIsr write is tagged with the issuing controller's epoch; a broker rejects a write from a stale epoch.

20.3 Deliverable

A 3-controller, 3-broker cluster where controller leader election, partition assignment, and LeaderAndIsr propagation all flow through the metadata log — killing the controller leader elects a successor without cluster-wide data-plane disruption.

20.4 Acceptance Criteria

Controller failover ≤ 5 s (§4); fixtures/controller_failover.bin asserts no dual-controller write is ever accepted (I8) across 10,000 simulated concurrent-election trials; partition assignment for a 100-partition topic across 10 brokers completes ≤ 2 s and is rack-aware (no single rack holds all replicas of any partition).

20.5 Conformance Fixtures

fixtures/controller_failover.bin — kill controller leader mid-metadata-write, assert clean re-election. fixtures/dual_controller_fencing.bin — simulate a stale controller attempting a write post-election, assert rejection (I8). fixtures/rack_aware_assignment.bin — 3-rack, 9-broker cluster, assert no partition's replicas share a rack when avoidable.

20.6 Pitfalls

Allowing a broker to accept a LeaderAndIsr from any controller without epoch-checking reintroduces exactly the split-brain class ZooKeeper-based deployments fought (Hunt et al. 2010, Chandra/Griesemer/Redstone 2007) — manifestation: two brokers both believe they lead the same partition; root cause: missing epoch fence at the broker's LeaderAndIsr handler; debug via dual_controller_fencing.bin; recovery: reject stale-epoch writes, the stale controller steps down on rejection (I8's enforced-at column).

20.7 Performance Concerns

Metadata-log replication is on the critical path of every leader election and partition reassignment, but not of the data-plane produce/fetch hot path (P8's separation) — controller quorum size (3 vs 5) trades election-quorum latency for fault tolerance, not data-plane throughput.

20.8 Edge Cases

A controller-quorum minority partition (2 of 5 controllers isolated) must remain unable to elect a leader (no split-brain even among controllers themselves — this is Raft's own guarantee, inherited, not reimplemented); a topic-creation request arriving during an in-progress controller election (must queue or reject with a retriable error, never silently drop).

20.9 Failure Analysis

A controller-quorum outage (majority of controller nodes down) freezes all leader elections/reassignments cluster-wide, though existing leaders continue serving produce/fetch uninterrupted (P8's separation of control and data planes) — this is a documented, bounded degradation mode, not a full outage, and must be communicated as such in on-call runbooks.

20.10 Operational Notes

Metrics: controller.epoch, controller.election.count, controller.metadata_log.lag. Runbook implication: a controller-quorum election is invisible to data-plane SLOs unless it also triggers broker leader elections — dashboards must distinguish the two failure domains.

21. Phase 9 — Consumer Groups and Rebalance Protocol

21.1 Objectives

Implement the group coordinator and the full rebalance protocol (§8.9, P9, I11): join, sync, heartbeat, and the incremental cooperative variant (KIP-429, ADR-18) as the default assignor.

21.2 Detailed Implementation Steps

kbroker-group::coordinator: hash-route each GroupId to a coordinator broker; implement the RebalanceState machine (§11, §8.9 table) exactly — Empty → PreparingRebalance → CompletingRebalance → Stable, with heartbeat-driven expiry re-entering PreparingRebalance (eager) or triggering an incremental two-phase revoke-then-assign (cooperative, KIP-429). rebalance: the group leader (first joiner) computes the Assignment (§11) using a pluggable strategy (range, round-robin, sticky, cooperative-sticky); coordinator distributes via SyncGroup. offsets: implement OffsetCommit/OffsetFetch validated against GenerationId (I11) — a commit for a partition outside the member's current assignment is rejected with ILLEGAL_GENERATION, never silently accepted (§8.12's malformed-input example).

21.3 Deliverable

A 50-member consumer group that rebalances on scale-up/scale-down/failure with the cooperative assignor, verified against zero duplicate and zero missed record consumption across the rebalance boundary.

21.4 Acceptance Criteria

Rebalance duration ≤ 1 s for 500 members under cooperative rebalancing, ≤ 6 s under eager (§4); fixtures/cooperative_rebalance_scaleup.bin and _scaledown.bin assert zero records double-delivered or skipped across the partition-ownership transition; fixtures/ offset_commit_unowned_partition.bin asserts ILLEGAL_GENERATION (I11).

21.5 Conformance Fixtures

fixtures/join_sync_heartbeat_basic.bin — single-member group lifecycle. fixtures/ cooperative_rebalance_scaleup.bin — member count 10→50 mid-stream. fixtures/ rebalance_storm.bin — aggressive session.timeout.ms inducing repeated rebalances, asserts the storm is detectable (not that it's prevented — mitigation is operational, §26). fixtures/ offset_commit_unowned_partition.bin — post-rebalance race, §8.12.

21.6 Pitfalls

An aggressive session.timeout.ms causing rebalance storms under transient GC pauses or network blips — manifestation: sustained rebalance.count climbing with no actual membership change intent; root cause: session timeout shorter than realistic client-side pause durations; debug via correlating rebalance events with client heartbeat gaps; recovery: raise session.timeout.ms or adopt static membership (group.instance.id) to survive brief disconnects without triggering a rebalance at all. Offset-commit races: a member commits an offset for a partition it just lost ownership of in a concurrent rebalance — I11's generation check is the only correct guard; anything relying on timing assumptions instead will eventually produce duplicate or skipped processing.

21.7 Performance Concerns

JoinGroup/SyncGroup fan-in at the coordinator for a large group (500+ members) must not serialize member processing — batch the assignment computation and distribution rather than handling members one at a time; cooperative rebalancing's whole performance argument is avoiding the O(members × partitions) full-stop pause of eager rebalancing.

21.8 Edge Cases

A member that never sends SyncGroup after JoinGroup (must time out, not hang the whole group in CompletingRebalance forever); duplicate JoinGroup from the same member due to a client-side retry (must be idempotent within the same generation); a group with zero members committing offsets (rejected — no active generation).

21.9 Failure Analysis

A stuck rebalance (leader crashes before SyncGroup) blocks the entire group's consumption until the coordinator's rebalance timeout fires — blast radius is the whole group, not just the crashed member; detection via rebalance.duration_ms exceeding rebalance.timeout.ms; recovery is automatic (coordinator times out and restarts PreparingRebalance) but the consumption gap during the stall is a real availability cost worth alerting on.

21.10 Operational Notes

Metrics: rebalance.count, rebalance.duration_ms, consumer_lag (per partition, per group — "the two alerts that matter" per §26, alongside under-replicated partitions). Runbook docs/runbooks/rebalance-storm-mitigation.md (§26).

22. Phase 10 — Retention, Compaction, Transactions, Quotas

22.1 Objectives

Implement the remaining data-lifecycle and correctness features: time/size retention and key-based compaction (§8.10, P7, I6, I12), the full transaction protocol (§8.8, P13, I10, KIP-98), and quota enforcement (P12, I14).

22.2 Detailed Implementation Steps

kbroker-log::retention: background worker per partition deleting segments by age (retention.ms) or aggregate size (retention.bytes), never touching the active segment (I12). kbroker-log::compaction: compute dirty ratio (dirtyBytes/totalBytes), trigger a compaction pass at min.cleanable.dirty.ratio ≥ 0.5 (§4); build the offset-map (key→latest offset) over dirty segments; rewrite forward only the latest record per key plus live tombstones within delete.retention.ms (I6, §8.10). kbroker-txn::coordinator: implement InitProducerId epoch fencing, AddPartitionsToTxn, the PrepareCommit/PrepareAbort → WriteTxnMarkers → CompleteCommit/CompleteAbort sequence exactly per §8.8's ten-step table (Gray & Lamport 2006's transaction-commit framing; KIP-98); implement consumer-side LSO gating for read_committed (I10). kbroker-quota::manager: per-client-id/user byte-rate tracking, response-delay throttling (P12, I14) — never rejection, never unbounded queuing (ADR-23).

22.3 Deliverable

Compacted topics retaining only the latest value per key; a transactional produce-consume round-trip demonstrating atomic multi-partition visibility under a killed coordinator; a throttled client observably delayed, not dropped.

22.4 Acceptance Criteria

Compaction throughput ≥ 100 MB/s per worker (§4); fixtures/compaction_key_preservation.bin asserts every live key's latest value survives 10 compaction passes; fixtures/ txn_coordinator_crash_recovery.bin asserts zero partial visibility across a coordinator kill mid-2PC (I10); fixtures/quota_throttle_delay.bin asserts a client exceeding its quota experiences increased quota.throttle_time_ms with zero dropped/duplicated bytes (I14).

22.5 Conformance Fixtures

fixtures/compaction_key_preservation.bin, fixtures/compaction_tombstone_retention.bin — a tombstone surviving exactly delete.retention.ms then dropping. fixtures/ txn_coordinator_crash_recovery.bin — coordinator killed at each of the ten §8.8 steps in turn. fixtures/quota_throttle_delay.bin — sustained over-quota client. fixtures/ read_committed_isolation.bin — asserts an aborted transaction's records never surface to a read_committed consumer.

22.6 Pitfalls

Compaction never catching up (dirty ratio growing unbounded) when producer throughput exceeds compaction throughput — manifestation: disk usage on a compacted topic grows without bound; root cause: insufficient compaction worker parallelism relative to write rate; debug via compaction.dirty_ratio trending upward with no plateau; recovery: add compaction threads or reduce per-partition write rate (P14 — the dirty-ratio trigger is tunable, not a law). A transaction stuck at PrepareCommit because the coordinator crashed before sending all WriteTxnMarkers blocks read_committed consumers indefinitely until coordinator-recovery rescans the transaction log — bounded by transaction.max.timeout.ms, must page if exceeded.

22.7 Performance Concerns

Compaction's offset-map build is O(dirty records) in time and O(unique keys) in memory — high key cardinality on a compacted topic is a real capacity-planning input (§34), not free. Quota enforcement must not add measurable latency to clients under quota — the check is O(1) per request (a token-bucket read), with cost only appearing as intentional delay once over budget.

22.8 Edge Cases

A key whose only record is a tombstone (never had a "real" value) — retained then dropped per the same tombstone-retention rule (I6); a transaction touching a partition that undergoes leader election mid-transaction (control records must still reach the new leader); a quota window boundary where a burst exactly straddles two measurement intervals (must not double- count or under-count).

22.9 Failure Analysis

An unbounded compaction backlog is a slow-burn failure — it doesn't page immediately but eventually exhausts disk on affected partitions; detection is exactly the compaction.dirty_ratio trend, and the runbook docs/runbooks/compaction-catch-up.md (§26) governs the manual intervention (temporarily add compaction capacity, throttle producers on that topic).

22.10 Operational Notes

Metrics: retention.segments_deleted, compaction.dirty_ratio, compaction.backlog_bytes, txn.hanging.count, quota.throttle_time_ms. Runbook docs/runbooks/disk-full-remediation.md (§26) covers the retention-outrun-by-producers scenario directly.

23. Phase 11 — Jepsen-Style Verification, Chaos, Perf Hardening

23.1 Objectives

Close the loop on every durability claim in §8 and every invariant in §7 with fault-injected verification (Kingsbury's Jepsen analyses as the named methodology); harden performance to §4's full targets under real, not simulated, faults.

23.2 Detailed Implementation Steps

kbroker-sim::faults (deterministic, in-process) plus a real-cluster Jepsen-style harness (external, kbroker-cli-driven): implement fault generators — kill a leader mid-produce, partition a follower, fill a disk, skew a clock, SIGSTOP a broker (simulating a GC-pause analogue even though Rust has no GC, to model any long scheduling stall). Implement a linearizability checker (Herlihy & Wing 1990) validating I2, I3, I4, I10 specifically — these four require genuine inter-process fault injection to falsify per §7's debugging methodology. Perf hardening: verify sendfile survives once TLS (ADR-25) is enabled (P11's promise, flagged as unresolved in §16.7) via kernel TLS (kTLS) offload; profile and eliminate any remaining lock contention on the produce/fetch hot path (P10) using perf record / flamegraphs.

23.3 Deliverable

A signed-off Jepsen-style report showing zero linearizability violations across 24 hours of combined fault injection at full §4 throughput, plus a perf report confirming all §30 M-table targets are met under TLS.

23.4 Acceptance Criteria

Zero I2/I3/I4/I10 violations across ≥ 500 fault-injection trials (fixtures/jepsen_report.json); sendfile syscall count with TLS+kTLS enabled within 5% of the plaintext baseline measured in §16; produce/fetch p99 latency (§4) held within target under a 24-hour chaos soak with leader kills every 10 minutes.

23.5 Conformance Fixtures

fixtures/jepsen_leader_kill_midproduce.json, fixtures/jepsen_follower_partition.json, fixtures/jepsen_disk_full.json, fixtures/jepsen_clock_skew.json, fixtures/jepsen_sigstop_pause.json — one report per fault class, each asserting the linearizability checker found zero I2/I3/I4/I10 violations. fixtures/perf_regression_ktls.bin — zero-copy verification under TLS.

23.6 Pitfalls

Trusting an in-process deterministic simulation alone (§7's methodology) without ever running the real-cluster Jepsen harness leaves the four fault-requiring invariants (I2-I4, I10) formally unverified against real OS/network behavior — the two methods are complementary, not substitutes (ADR-30). A SIGSTOP-simulated pause revealing a false linearizability violation because the checker itself has a race is a checker bug, not a broker bug — validate the checker against a known-correct reference trace first.

23.7 Performance Concerns

kTLS offload availability is kernel-version-dependent — verify the CI/production kernel actually supports it (ADR-25/ADR-32's kernel-matrix concern) before asserting the zero-copy- under-TLS acceptance criterion; a kernel without kTLS support means TLS genuinely defeats zero-copy (P11) and this must be reported honestly, not masked.

23.8 Edge Cases

Two simultaneous fault classes (disk-full on the follower during a leader kill) — the harness must support composable fault injection, not just one fault at a time, since real incidents compound. A clock-skew fault large enough to move a broker's clock backward (must not break CreateTime-based timestamp monotonicity assumptions anywhere they're load-bearing).

23.9 Failure Analysis

Any linearizability violation found here is a release blocker, not a documented limitation — this phase's entire purpose is to make that distinction enforceable rather than aspirational.

23.10 Operational Notes

The Jepsen-style harness and its fixtures become a permanent regression gate (nightly-chaos. yml, ADR-32), not a one-time Phase-11 exercise — every subsequent change to kbroker-replication, kbroker-txn, or kbroker-log re-runs this suite before release (§28, §29).

26. Operational Readiness

Named metrics: under_replicated_partitions, isr.shrink_count / isr.expand_count, replica.lag.messages / replica.lag.bytes, HW-advance rate (hw.advance_rate), request- handler idle ratio (request_handler.idle_ratio), produce/fetch latency percentiles (produce.latency_ms, fetch.latency_ms), log-flush latency (log.flush.duration_ms), compaction backlog and dirty ratio (compaction.backlog_bytes, compaction.dirty_ratio), rebalance rate and duration (rebalance.count, rebalance.duration_ms), consumer lag (consumer_lag, per group per partition).

Tracing spans: one span per request stage (network-decode → handler → log-append/read → replication-wait → response-encode), OpenTelemetry-compatible (ADR-28), correlated by request id across broker-to-broker hops for replication and controller RPCs.

Structured logging: JSON, leveled (ADR-27); every ISR shrink/expand, leader election, and transaction state transition is logged at WARN or above with the exact offsets/epochs involved — these are the events a postmortem (§25) reconstructs from first.

Dashboards: cluster-overview (under-replicated partitions, ISR health, controller epoch), per-topic (produce/fetch latency, retention/compaction health), per-consumer-group (lag, rebalance rate), per-broker (disk, page-cache hit rate, FD usage against §4's budget).

Alerting philosophy — stated plainly: under-replicated partitions and consumer lag are the two alerts that matter. Every other metric is diagnostic once one of those two fires; neither should be buried among dozens of equally-weighted alerts.

SLOs: availability per §4 (99.95% broker, 99.99% cluster); produce/fetch latency SLOs directly from §4's p99 targets; error budget burn tracked against NOT_ENOUGH_REPLICAS and OFFSET_OUT_OF_RANGE rates.

Incident response: on-call triages via the two headline alerts, drills into the relevant runbook below, and records the exact lost-offset range (if any, per §8.13/§19.9) in the postmortem.

Runbooks (docs/runbooks/): under-replicated-partition.md (diagnose slow/dead replicas, FM-1), unclean-election-decision.md (the manual availability-vs-durability call, §19), partition-reassignment.md (moving replicas with throttled bandwidth), disk-full- remediation.md (FM-6/T5), compaction-catch-up.md (FM-6), rebalance-storm-mitigation.md (FM-5).

Backup/restore: cross-cluster mirroring (deferred, §37) is the primary DR mechanism; local backup is segment-file archival to object storage, restorable by replaying archived segments into a fresh log directory and rebuilding indexes (§14's index-rebuild procedure applies identically to a restored segment).

Deployment topology: brokers and controllers on separate node pools in production (co-located only in small/dev clusters); rack-aware placement (§20) spanning ≥3 failure domains for RF=3.

Canary / rolling upgrade / rollback / migration: canary one broker per rack first; rolling restart one broker at a time, waiting for under_replicated_partitions to return to zero before proceeding to the next (broker-by-broker restart procedure); rollback is the same procedure in reverse, gated on the inter-broker protocol version (§27) supporting both versions simultaneously; migration (e.g. a config-format change) is staged through the controller's metadata-log schema evolution (§27).

27. Compatibility & Versioning

The wire protocol's per-API-key version negotiation (ApiVersions handshake) is the central compatibility mechanism: each request type is independently versioned, letting a broker support a range of client versions simultaneously without a single monolithic protocol version gate — this is what makes a rolling upgrade possible at all.

Record-format magic-byte evolution: the record-batch magic byte (§8.1) versions the wire layout itself; a broker serving an older-magic consumer must down-convert on the fly (re-encoding batches), which is CPU cost proportional to fetch volume — operators should track down_conversion.rate as a signal to upgrade lagging clients.

Index format changes: an OffsetIndex/TimeIndex format change (§8.2) is versioned per-segment; old-format segments remain readable until compacted/rolled away, never requiring a stop-the-world index migration.

Metadata log schema evolution: MetadataRecord variants (§11) are additive-only across versions — new record types or fields are introduced behind a metadata-log version gate the controller negotiates cluster-wide before use, mirroring the same discipline KIP-500's design applies to KRaft.

Client-broker compatibility matrix: a broker at version N supports clients as old as N−3 minor versions (a 3-release deprecation window) for standard APIs; ApiVersions is itself never deprecated.

Inter-broker protocol version during a rolling upgrade: brokers negotiate the lowest common inter-broker protocol version until every broker in the cluster is upgraded, then an explicit inter.broker.protocol.version bump unlocks new inter-broker features — this two-step process is what guarantees a rolling upgrade never requires cluster downtime.

API stability / deprecation / SemVer: the wire protocol follows the per-API-key versioning above (not workspace SemVer); the kbroker-* crates follow standard SemVer for their Rust APIs independent of wire-protocol versioning.

Migration: a topic-config schema change ships as an additive MetadataRecord field with a documented default, never a breaking rewrite of existing records.

28. Testing & Verification Strategy

Unit: per-crate (§10), covering encode/decode round-trips, index arithmetic, ISR state-transition logic in isolation.

Integration: multi-broker docker-compose-based clusters (§10) exercising produce/ replicate/fetch/rebalance end-to-end.

Property-based (ties to §7 invariants): offsets are gapless and monotonic under concurrent produce (I1); a follower's log is always a prefix of the leader's at the same epoch (I3); an idempotent producer's retries never duplicate (I5); compaction preserves the latest value per key (I6); a consumer never reads beyond the high watermark (I2). Each runs as a proptest suite inside kbroker-sim (ADR-30), asserted after every simulated event per §7's methodology.

Differential: a real Apache Kafka client (e.g. librdkafka or the Java client) driven against this broker, comparing byte-level record batches and observed behavior against a real Kafka broker under the same workload — the strongest guard against subtle wire-protocol divergence (§27).

A Jepsen-style consistency test is a named deliverable, not an afterthought: §23's harness is exactly this, because the durability claims in §8 (I2, I3, I4, I10) are the kind only fault injection can falsify — a passing unit-test suite says nothing about behavior under a killed leader or a partitioned follower.

Fuzzing (ADR-31): the record-batch decoder and the wire-protocol request decoder are the primary targets (T2, T3, §24) — both are untrusted-input parsers reachable from any network client before authentication completes in some code paths.

Chaos (§23): kill a leader mid-produce, partition a follower, fill a disk, skew a clock, SIGSTOP a broker to simulate a long scheduling pause — each tied to I2/I3/I4/I10 and to FM-1 through FM-12 (§25).

Deterministic replay: kbroker-sim records every simulated event stream; a failing property test's exact interleaving is replayable byte-for-byte for debugging, not just re-run-and-hope.

Soak: 24-hour continuous produce/fetch/rebalance/compaction workload (§23.4) verifying no resource leak (FD count, memory) and no latency-percentile drift.

Fault injection / conformance / perf-regression gating: all wired into CI (§29) — conformance fixtures (each phase's N.5) run on every PR; the Jepsen-style suite and soak run nightly (nightly-chaos.yml); perf-regression gating (§30's M-table) blocks merge on regression beyond a defined threshold.

31. Scalability Analysis

What stays constant vs. grows (Big-O): append is O(1) amortized and sequential per partition (P10); fetch by offset is O(log n) through the sparse index (§8.2) then a bounded sequential scan; compaction is O(dirty records) in time, O(unique keys) in memory per pass (§22.7); replication fan-out is O(ISR size) per leader, independent of total partition count elsewhere in the cluster. Per-partition overhead — not total bytes — is the real scaling limit: each partition costs a file handle per open segment, an index memory footprint (§34), and a replication-fetcher slot; a cluster with few large partitions scales further than one with many small ones at equal total throughput.

Named bottlenecks, in order: (1) partition count driving open file-handle count (§4's FD budget) and per-partition index memory — this is the first ceiling hit in practice, well before raw throughput; (2) controller metadata size — the metadata log's total MetadataRecord count grows with partition/topic count and bounds controller catch-up time on failover (§20); (3) replication fan-out — each additional replica adds a fetcher slot and network path per partition, and RF is a multiplier on both storage and replication network traffic.

Horizontal scaling: by partition count (more partitions spread load across more broker-hosted leaders) and by broker count (more brokers absorb more partition-leaders); neither is free — see the named bottlenecks above.

Coordination overhead: the controller quorum (§20) does not sit on the data-plane hot path (P8's separation), so its overhead is bounded to election/reassignment events, not per-request; however, controller catch-up time after failover does grow with metadata-log size, making metadata compaction (analogous to §8.10's data-log compaction, applied to the metadata log itself) a real operational concern past ~100,000 partitions.

Practical ceiling and levers beyond it: ~200,000 partitions/cluster and ~4,000/broker (§4) is the practical ceiling for this design before FD exhaustion and controller metadata size dominate; levers beyond it are tiered storage (deferred, §37 — reduces local FD/disk pressure by moving cold segments off-broker), larger batches (amortizes per-request overhead, raising effective per-partition throughput without adding partitions), and fewer, larger partitions where the workload's ordering/parallelism requirements allow it (P2, P14).

32. Mental Models & First Principles

MM1. A log is a queue that forgot to delete, and that forgetting is what buys replay, fan-out, and time travel. Predicts: any consumer can rewind to any retained offset at zero marginal server cost. Bug class without it: building server-side per-consumer delivery state (reinventing a queue) because the engineer assumes "consumed" must mean "removed." Resolved in §1, §8.10 (Kreps 2013).

MM2. The high watermark is a promise about what cannot be un-said — reads stop there because durability is not yet decided above it. Predicts: consumers reading up to LEO instead of HW will eventually observe a record that unclean failover erases. Bug class without it: treating LEO and HW as interchangeable "current position" numbers. Resolved in §8.5, §7 (I2, I4).

MM3. Sequential disk access beats random memory access at scale, which is why this design fights for the page cache instead of building a cache. Predicts: a user-space cache re-implementing what the OS already does will underperform, not outperform, a well-sized page cache. Bug class without it: engineers build a custom LRU cache "for control" and find it strictly slower once measured. Resolved in §3, §9 (ADR-06), §30.

MM4. Leader epoch is a fence, not a clock — it answers "which history are we in," never "when did this happen." Predicts: any truncation logic keyed on timestamps instead of epochs will misbehave under clock skew. Bug class without it: the historic Kafka log-divergence bug class. Resolved in §8.6, §19 (P5).

MM5. Durability is a purchase, not a default — acks and min.insync.replicas are the receipt. Predicts: an operator who never reads the receipt will eventually be surprised by an RPO they didn't choose. Bug class without it: silent acks=1 deployments treated as "basically durable." Resolved in §4, §8.7 (P3).

MM6. Compaction is a promise about keys, not about history — it never claims to remember what a value used to be. Predicts: using a compacted topic as an audit log of every historical value will silently lose intermediate states. Bug class without it: assuming compaction is "just retention with extra steps." Resolved in §8.10, §22 (P7).

MM7. A consumer group's rebalance protocol is a distributed lock service in disguise — one partition, one owner, enforced by generation, not by trust. Predicts: any offset commit or processing logic that doesn't check its generation id will eventually double-process or skip data across a rebalance boundary. Bug class without it: the exact FM-9 offset-commit race. Resolved in §8.9, §21 (I11).

MM8. Zero-copy is a chain, and a chain breaks at its weakest interposed layer. Predicts: adding TLS, compression re-encoding, or any userspace transform anywhere on the fetch path silently reintroduces the copy the whole storage design was built to avoid. Bug class without it: "why did throughput halve after we enabled TLS" incidents. Resolved in §16, §23 (P11).

Apache Kafka made the ISR/high-watermark tradeoff the industry default: async replication with tunable durability, winning wherever operators need to dial latency against durability explicitly rather than accept one fixed synchronous cost — the majority of general-purpose event-streaming deployments.

Apache Pulsar's segment-versus-partition storage split is the other most instructive contrast: decoupling brokers (stateless serving) from storage (BookKeeper ledgers) lets either scale independently and makes broker failover instant (no data to re-replicate, just a new broker claiming the same ledgers) — it wins wherever elastic, independent compute/storage scaling matters more than the operational simplicity of one clustered system.

34. Back-of-Envelope Capacity Model

  1. Retention storage per cluster = produce throughput × retention seconds × replication factor = 600 MB/s × 604,800 s (7 days) × 3 = 1,088,640,000 MB ≈ 1.09 PB cluster-wide for full-retention, full-throughput operation (§4).
  2. Page-cache sizing for the consumer-lag window = throughput × lag window seconds. For a 10-minute (600 s) lag tolerance at 600 MB/s: 600 MB/s × 600 s = 360,000 MB ≈ 352 GB of page cache needed cluster-wide to keep reads off disk for a consumer lagging up to 10 minutes (P10, ADR-06).
  3. Disk write bandwidth required per broker = produce throughput × replication factor (since followers write too) = 200 MB/s (per-broker share of 600 MB/s across a 3-broker cluster) × 3 = 600 MB/s per broker, comfortably under the 3 GB/s NVMe assumption (§4).
  4. Network bandwidth per broker = produce-in + replication-out + fetch-out. Produce-in: 200 MB/s. Replication-out (to 2 followers): 200 MB/s × 2 = 400 MB/s. Fetch-out (assume 1x throughput for consumers): 200 MB/s. Total ≈ 800 MB/s per broker, requiring at least a 10 GbE NIC (1.25 GB/s) with headroom.
  5. Index memory and file handles = partitions × segments-per-partition × index-bytes-per-segment. At 4,000 partitions/broker (§4), 1 GiB segments, 7-day retention at an average 150 KB/s/partition ⇒ ~86 GB/partition/week ⇒ ~86 segments/partition; index size per segment ≈ segment_bytes / index.interval.bytes × 8 bytes = (1 GiB / 4096) × 8 ≈ 2 MiB. Total index memory ≈ 4,000 × 86 × 2 MiB ≈ 688 GiB if all segments' indexes were mmap'd simultaneously — in practice only the active + recently-accessed segments' indexes are resident, but this is exactly why partition count, not total bytes, is the binding constraint (§31). File handles: 4,000 partitions × ~3 open files (log, index, timeindex) for the active segment ≈ 12,000 FDs, within the 65,536 ceiling (§4) with room for connections.
  6. Records per batch to hit a throughput target given per-request overhead: assume 50 µs fixed overhead per produce request and a 2,000,000 records/s target (§4) at 100 bytes/record = 200 MB/s ÷ 100 bytes = 2,000,000 records/s needed; at, say, 10,000 requests/s sustainable (100 µs/request round-trip budget), each request must carry 2,000,000 / 10,000 = 200 records/batch minimum to hit the target.
  7. Recovery time after a broker restart = segment bytes to validate ÷ scan rate. For a broker holding 4,000 partitions × 1 GiB active segment ≈ 4 TiB of "hot" data needing CRC re-validation above the recovery point (I13, worst case = no valid recovery point), at an assumed 500 MB/s single-threaded scan rate: 4 TiB / 500 MB/s ≈ 8,192 s (≈ 2.3 h) worst case — motivating parallelizing the scan across partitions (each partition's segments are independent) to bring this down to minutes in practice.
  8. Compaction wall clock at the stated dirty ratio = dirty bytes ÷ compaction throughput. At min.cleanable.dirty.ratio = 0.5 (§4) on a 1 GiB segment range, dirty bytes ≈ 512 MiB; at 100 MB/s per worker (§4, M11): 512 MiB / 100 MB/s ≈ 5.1 s per triggered compaction pass on one segment range — scaling linearly with the number of simultaneously dirty partitions divided by available compaction worker threads.

Winning regime: environments where durability must never be silently misconfigurable and the extra quorum round-trip latency is acceptable. Real embodying system: Redpanda. Rejected here because ADR-12 explicitly wants the tunable acks/ISR tradeoff space (P3) exposed to the operator rather than fixed — an educational build benefits from studying both durability models as distinct mechanisms, and this blueprint chose the one that teaches the ISR/HW distinction (P4, I2-I4) directly.

Alternative 2 — Segmented storage split from serving brokers (Pulsar's model).

[Broker A] --\                    [Bookie 1] (ledger fragments)
[Broker B] ---+-- reads/writes -->[Bookie 2] (ledger fragments)
[Broker C] --/                    [Bookie 3] (ledger fragments)
   (brokers are stateless; any broker can serve any partition
    by attaching to that partition's ledgers on demand)

Winning regime: elastic compute/storage scaling and instant broker failover (no re-replication needed, just ledger reattachment). Real embodying system: Apache Pulsar (with Apache BookKeeper). Rejected here because it requires operating two clustered systems (brokers + BookKeeper) — this blueprint's scope (ADR-04) is a single broker-local storage engine, which is both simpler to build end-to-end in the phase plan (§12-§23) and the more common production topology this specification's target users will actually operate.

Alternative 3 — Classic broker-managed queue with per-message acknowledgement (RabbitMQ's default model).

Producer --> [Exchange] --route--> [Queue] --deliver--> Consumer
                                      |  (per-message ack/nack state
                                      |   tracked server-side; unacked
                                      +-> messages redelivered on nack/timeout)

Winning regime: genuine task/RPC-style distribution with heterogeneous per-message retry and priority needs, where "processed" should mean "gone." Real embodying system: RabbitMQ (classic queues). Rejected here per ADR-03/P1 — this project's entire pedagogical point is the log primitive and the replay/fan-out properties a queue's per-message state destroys; building the queue model instead would teach a different (also valuable, but different) lesson, covered by sibling PubSub-Messaging (rank 206), not this project.

Alternative 4 — Shared-storage / object-store-backed log, trading latency for elastic, cheap storage.

Producer --> [Stateless Broker] --write--> [Object Store (S3-compatible)]
                     ^                            |
                     +-------- read-back ---------+
        (no local broker disk at all; durability and
         replication delegated entirely to the object store)

Winning regime: workloads that can tolerate higher produce/fetch latency (object-store round trips) in exchange for near-zero storage-management overhead and effectively unlimited retention at low cost. Real embodying system: WarpStream (Kafka-protocol-compatible, S3-backed, acquired by Confluent in 2024). Rejected here because §4's latency targets (single-digit-to- low-double-digit-ms produce latency) are incompatible with object-store round-trip times, and this blueprint's pedagogical focus is precisely the local segmented-log/page-cache/zero-copy discipline (P10, P11) that an object-store-backed design deliberately gives up.

38. Glossary

Topic — a named, configured collection of ordered partitions. Partition — the unit of parallelism, ordering, and replication; an append-only offset-addressed log. Offset — a monotonic integer address of a record within a partition (P1). Log-end offset (LEO) — the next offset a replica will write; its private write-progress pointer. High watermark (HW) — the highest offset replicated to every ISR member; the fetch visibility boundary (P4). Log- start offset — the lowest offset still retained; advances as retention deletes segments. Segment — a bounded-size append-only file plus its index files; the retention/compaction unit. Sparse index — an index recording one entry per configured byte interval rather than per record, trading lookup precision for memory (ADR-05). Offset index / time index — the two sparse index files mapping offset→byte-position and timestamp→offset respectively. Record batch — the wire/storage unit containing one or more records plus a shared header, CRC, and compression (§8.1). Magic byte — the record-batch format version field. Tombstone — a record with a null value, marking a key for eventual removal under compaction. Leader — the replica accepting writes for a partition. Follower — a replica replicating from the leader. Replica — any broker hosting a copy (leader or follower) of a partition. In-sync replica (ISR) — a replica caught up within the configured lag bound; membership in the durability contract (§8.5). ISR shrink / expand — eviction/re-admission of a replica from the ISR set. Under-replicated partition — a partition whose ISR size is below its replication factor; the primary alerting signal (§26). Leader epoch — a monotonic counter fencing stale leaders and resolving log divergence (P5). Truncation — a follower discarding log tail beyond the point it and the new leader agree on. Unclean leader election — electing a leader from outside the last known ISR, trading availability for possible data loss (§8.13). Acks — the producer-selected acknowledgement level (0/1/all) defining the durability contract (P3). min.insync.replicas — the minimum ISR size required for an acks=all write to succeed. Idempotent producer — a producer whose retries are deduplicated by sequence number, never producing duplicates (P6). Producer epoch — fences a producer's stale/zombie incarnation. Sequence number — per-partition, per-producer-epoch monotonic counter used for dedup (I5). Transaction coordinator — the broker role driving a transaction's two-phase commit. Control record — a marker record signaling a transaction's commit/abort to a partition's consumers. Consumer group — a set of consumer instances cooperatively consuming a topic, one partition owned by at most one member at a time. Group coordinator — the broker role managing a group's membership and offsets. Generation — a monotonically increasing id for a group's current membership epoch, gating offset commits (I11). Rebalance — the protocol re-assigning partitions among group members on membership change. Cooperative rebalance — an incremental rebalance variant moving only affected partitions (KIP-429). Session timeout — the heartbeat-miss duration after which a member is considered dead. Offset commit — a consumer's durable record of its next-to-read position per partition. Consumer lag — the gap between a partition's high watermark and a consumer group's committed offset; the second headline alert (§26). Retention — the time/size policy governing segment deletion, independent of consumer position (I12). Compaction — background rewriting that retains only the latest record per key (P7). Dirty ratio — the fraction of a partition's bytes written since the last compaction pass; the compaction trigger. Zero copy — transferring data from page cache to socket without a userspace buffer copy (sendfile/splice, P11). Page cache — the OS's cache of recently-accessed file bytes; this design's sole read cache (ADR-06). Tiered storage — archiving cold segments to object storage, deferred in this blueprint (§37). Quota — a per-principal byte-rate budget enforced by response delay (P12). Throttle time — the delay imposed on a quota-exceeding client's response. Controller — the cluster role owning partition assignment, leader election, and ISR bookkeeping via a replicated metadata log (P8). Metadata log — the controller's own replicated event log of cluster state (ADR-16). KRaft — the self-managed metadata-Raft design (KIP-500) replacing an external coordination service. Produce/fetch purgatory — the parking structure holding requests pending a condition (HW advance, timeout) before responding. Long poll — a fetch that blocks up to a bound waiting for data rather than returning immediately empty. CRC-32C — the Castagnoli CRC variant (RFC 3385) used for record-batch integrity (ADR-09). Varint — a variable-length integer encoding used throughout the record layout (§8.1.1). Compression codec — the pluggable algorithm (gzip/Snappy/LZ4/Zstandard) compressing a record batch. read_committed — a consumer isolation level excluding uncommitted/aborted transactional records. Last stable offset (LSO) — the boundary up to which read_committed consumers may read, gated by open transactions. Static membership — a consumer identifying itself with a stable instance id to survive brief disconnects without triggering a rebalance. Rack-aware placement — spreading a partition's replicas across failure domains (racks/zones) during assignment (§20).
