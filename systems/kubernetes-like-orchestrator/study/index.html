Mental Models & First Principles

  1. MM1 — Desired state minus observed state equals the controller's work queue. Predicts: a reconciler degrades gracefully when the diff is computed against fresh state; the queue is bounded by divergent-object count, not event volume. Without it: a counter-based reconciler under-counts after a crash and runs permanently short of replicas, with no self-healing trigger. Applied: §6 (P5, Idempotent reconciliation), Phase 7 (ReplicaSet replica-count logic), Phase 11 (Job completion accounting).

  2. MM2 — Level-triggered systems trade per-event efficiency for crash-recovery correctness. Predicts: any missed event self-heals at the next resync; controllers always act on current state, so the event payload is irrelevant to correctness. Without it: one dropped "Pod deleted" event means the replication slot is never refilled — silently and permanently — until a human notices. Applied: §6 (P2), Phase 4 (DeltaFIFO enqueue-key discipline: keys, not objects), Phase 7 (RS reconcile counts actual Pods, not deltas).

  3. MM3 — MVCC watch: a revision is a global Lamport clock; a watcher is a log consumer starting from a known offset. Predicts: the safe compaction floor is min(active-watcher start revisions); compacting below it produces a 410 for that client. Without it: you compact past a live watcher, triggering a cascade of 410s that forces every controller to relist the entire store simultaneously — a thundering herd under high churn. Applied: §7 (I1, I8, I14), Phase 1 (compactor guard against min-watcher RV), Phase 3 (BOOKMARK keeps client RV ahead of the compaction front).

  4. MM4 — Optimistic concurrency: correct retry requires re-reading state, not replaying the original intent. Predicts: two conflicting writers converge because the loser re-reads the winner's committed outcome and recomputes the diff against it. Without it: a "retry the same write" loop re-applies an already-obsolete diff; two controllers oscillate writing contradictory values indefinitely. Applied: §6 (P4, I3), Phase 2 (registry CAS on resourceVersion), Phase 5 (bind 409 → re-enqueue + fresh cache snapshot).

  5. MM5 — Control-plane/data-plane separation: the fast path must never block on the consistent brain. Predicts: kubelet and kube-proxy continue operating during any control-plane outage; only new mutations stall, never existing workloads. Without it: a kubelet that calls the apiserver per probe, or a proxy that consults the store per packet, kills live traffic on any control-plane partition. Applied: §6 (P6), Phase 6 (kubelet autonomy test: CP down, containers keep running), Phase 8 (proxy level-trigger resync on timer, not per-packet).

  6. MM6 — Leader election via a leased object is a distributed mutex with a TTL fence. Predicts: worst-case split-brain window is exactly one lease duration; the non-renewing leader's Lease expires and it must stop acting. Without it: two controller-managers both reconcile Deployments — spawning duplicate Pods and issuing contradictory scale writes indefinitely. Applied: §7 (I10, ADR-11), Phase 3 (Lease CAS renew with monotonic clock, ADR-30), Phase 7 (leader-elected controller-manager).

  7. MM7 — Scheduling is a constraint-satisfaction problem: filter (feasibility) then score (preference), never mixed. Predicts: a new placement constraint requires only a new FilterPlugin; scoring before filtering wastes cycles on infeasible nodes and inflates latency. Without it: a monolithic function mixing resource-fit and soft-affinity in one O(nodes²) loop blows the 100 ms p99 budget (§4) at 1k nodes. Applied: §4 (≥ 100 Pods/s, ≤ 100 ms p99), Phase 5 (filter → score → bind plugin framework), Phase 13 (node sampling caps worst-case filter cost at 5k nodes).

  8. MM8 — Raft: revisions are assigned at FSM apply time, not at propose time; the committed log order is the only valid clock. Predicts: a leader replaced between propose and apply would assign a lower revision to the same log slot if assignment happens at propose, breaking monotonicity. Without it: watch clients relying on I1 (globally monotonic RV) observe revision regressions and incorrectly infer data loss or silently skip events. Applied: §7 (I1), Phase 12 (revision assigned only at FSM apply after quorum commit), Phase 12 (ReadIndex confirms apply index before serving linearizable reads).

  9. MM9 — Owner refs + finalizers form a distributed reference-counting protocol; deletion is a multi-step rendezvous. Predicts: a Deployment→RS→Pod cascade takes at minimum three reconcile cycles (one per ownership level) and is safe across any crash at any intermediate point. Without it: instant hard deletes leak every external resource (LBs, PVCs, DNS) whenever the finalizer-owning controller crashes between delete and cleanup. Applied: §6 (P8, I6, I7), Phase 2 (soft-delete: set deletionTimestamp first), Phase 7 (GC owner-graph foreground deletion), Phase 11 (StatefulSet PVC retain policy on scale-down).

  10. MM10 — Workqueue discipline (dedupe + rate-limit + exponential backoff) is the apiserver's natural backpressure valve. Predicts: 10k Pod deletes coalesce to one reconcile per RS key per window; a permanently failing key backs off without starving healthy keys. Without it: each delete triggers an immediate reconcile; a crashlooping Pod causes an unbounded retry storm that OOMs the controller and floods the store, exhausting the 65k FD budget (§4). Applied: §6 (P10, ADR-10), Phase 4 (token-bucket + per-item backoff implementation), Phase 9 (quota burst serialization).

5. Required Reading

Books

  • Kubernetes in Action (Lukša) → applied in §8.2, Phase 6 — chs. 4–11. Extract: Pod lifecycle, controller behaviors, Service/Endpoints semantics, the user-visible contract you must reproduce.
  • Programming Kubernetes (Hausenblas & Schimanski) → applied in §4 (informers/workqueue), Phase 4 — chs. 1–3. Extract: informer/lister/workqueue mechanics, the client-go control-loop pattern you reimplement in apimachinery.
  • Designing Data-Intensive Applications (Kleppmann) → applied in §1 (MVCC/WAL), Phase 12 — chs. 5, 7, 9. Extract: replication, isolation, consensus vocabulary for the store and leader election.
  • Site Reliability Engineering (Google) → applied in Operational Readiness, Phase 10 — chs. 4, 21, 22. Extract: SLO/error-budget framing, handling overload, addressing cascading failures in a control plane.
  • Database Internals (Petrov) → applied in Phase 1 (B+tree, WAL, MVCC) — chs. 2–4, 6. Extract: B+tree pages, MVCC, WAL — the store's storage layer.
  • Operating Systems: Three Easy Pieces → applied in Phase 6 (cgroup/namespace isolation) — virtualization + concurrency parts. Extract: namespaces/cgroups mental model behind CRI isolation.
  • The Linux Programming Interface (Kerrisk) → applied in Phase 6 (cgroups/proc), Phase 8 — chs. 28–29 (cgroups via proc), 59–61 (sockets). Extract: what the runtime and proxy actually call.
  • Distributed Systems (van Steen & Tanenbaum) → applied in Phase 12 (failure detectors, replication) — chs. 6–8. Extract: failure detectors, consistency models, replication for Phase 12.

Papers

  • Borg: Large-scale cluster management at Google (Verma et al., EuroSys 2015) → applied in §3 (control/data-plane split), Phase 5, Phase 7 — the lineage: alloc/task model, scheduling, machine sharing. Implementation relevance: the control-plane/data-plane split and "everything is a controller."
  • Omega: flexible, scalable schedulers (Schwarzkopf et al., EuroSys 2013) → applied in §6 (optimistic concurrency), Phase 2, Phase 5 — shared-state scheduling, optimistic concurrency on a cell store. Relevance: why CAS over resourceVersion beats a central lock.
  • Large-scale cluster management at Google with Borg + the Kubernetes design papers → applied in §6 (level-triggered controllers), Phase 7 — the declarative reconcile model. Relevance: level-triggered controllers.
  • In Search of an Understandable Consensus Algorithm (Ongaro & Ousterhout, Raft, 2014) → applied in Phase 3 (leader election), Phase 12 — leader election + log replication. Relevance: Phase 12 store replication and Phase 3 leader election.
  • Paxos Made Simple (Lamport, 2001) → applied in Phase 12 (consensus baseline) — the consensus baseline Raft simplifies; read for first principles.
  • The Chubby lock service (Burrows, OSDI 2006) → applied in Phase 3 (lease-based coordination), Phase 7 — lease-based coordination, the leader-election pattern. Relevance: controller-manager single-writer.
  • CAP twelve years later (Brewer, 2012) → applied in §4 (CP store / AP data-plane), Phase 12 — consistency/availability tradeoff. Relevance: store CP choice, data-plane AP autonomy.
  • Sparrow / distributed scheduling literature → applied in Phase 13 (sampling, scaling) — late-binding, batch sampling. Relevance: scaling the scheduler beyond a single loop (Phase 13).
  • The seminal work on epidemic/gossip dissemination → applied in Phase 12 (contrast with watch model), Scalability Analysis — relevant to node-status fanout at scale; contrast with the watch model.

Reference Implementations

  • kubernetes/kubernetes → applied in Phase 0 (apimachinery scheme/codecs), Phase 4 (informer/DeltaFIFO) — staging/src/k8s.io/apimachinery (scheme, codecs, meta), apiserver/pkg/registry (REST strategies), client-go/tools/cache (informer/DeltaFIFO), pkg/scheduler (framework plugins), pkg/kubelet (PodWorkers, prober). Lesson: the registry-strategy and informer patterns. Pitfall to avoid: do not copy its sprawling internal API versioning machinery — keep one internal version + one served version Phase 0.
  • etcd → applied in Phase 1 (MVCC/watch/compaction), Phase 12 — mvcc/ (KV, watch, compaction), raft/. Lesson: revision-based watch, watchable store. Pitfall: do not reimplement the full v3 lease/txn surface initially.
  • k3s → applied in Phase 0 (multicall binary packaging) — single-binary packaging, embedded store. Lesson: multicall binary + all-in-one mode. Pitfall: its many vendored shims hide the core; read for packaging only.
  • containerd / CRI → applied in Phase 6 (sandbox/CRI surface) — pkg/cri. Lesson: sandbox model, the CRI gRPC surface. Pitfall: don't pull in the full plugin graph; a thin shim suffices.
  • kube-proxy → applied in Phase 8 (iptables/IPVS backends) — pkg/proxy/{iptables,ipvs,userspace}. Lesson: three dataplane backends behind one interface. Pitfall: iptables rule explosion at scale (motivates IPVS).
  • MetalLB / kube-router → applied in Phase 8 (minimal dataplane programming) — small, readable proxy/networking code. Lesson: minimal dataplane programming.

RFCs / Specifications

  • OCI Runtime Spec → applied in Phase 6 (cri-shim OCI adapter) + OCI Image Spec — container exec + image layout (delegated to #35/#166 but the shim must honor them).
  • CNI Specification (v1.0.0) → applied in Phase 6 (ADD/DEL/CHECK, IPAM result) — ADD/DEL/CHECK contract, IPAM result schema.
  • CRI (Container Runtime Interface) protobuf → applied in Phase 6 (RuntimeService/ImageService gRPC) — RuntimeService + ImageService gRPC.
  • JSON Patch (RFC 6902) → applied in Phase 0 (patch engine), Phase 2 + JSON Merge Patch (RFC 7386) + Strategic Merge Patch — the three PATCH semantics the apiserver serves.
  • HTTP/1.1 (RFC 7230–7235) → applied in Phase 2 (REST), Phase 3 (chunked watch streams) + HTTP/2 (RFC 7540) — watch over chunked transfer / streams.
  • SPDX / SemVer → applied in Phase 0 (CI/release skeleton), Build & Release Engineering — versioning + SBOM for release engineering.

Glossary · 33 terms · site-wide glossary

Reconcile
drive observed state toward desired; idempotent loop.
Level-triggered
act on current state, not on the triggering event.
resourceVersion (RV)
opaque monotonic token for watch resume + CAS.
generation / observedGeneration
spec change counter / last-reconciled value (progress).
Owner reference
child→parent link for cascading GC.
Finalizer
string gating deletion until cleanup runs.
Informer
local cache fed by list+watch, emitting deltas.
Lister
read-through accessor over an informer cache.
Workqueue
rate-limited, deduped, backoff queue between watch and reconcile.
DeltaFIFO
queue preserving per-key deltas incl. final delete state.
Strategy (registry)
per-resource default/validate/prepare hooks.
Admission
mutating+validating gate before persistence.
CAS
compare-and-swap on RV; optimistic concurrency.
Bind
set Pod.spec.nodeName, committing a schedule.
Filter/Score
scheduler feasibility / preference plugins.
CRI
Container Runtime Interface (gRPC kubelet↔runtime).
Sandbox / pause
Pod's shared-namespace holder container.
CNI
Container Network Interface (ADD/DEL network plumbing).
PodWorker
per-Pod serialized lifecycle goroutine.
Probe
liveness/readiness/startup health check.
Endpoints
Service→ready-Pod-IP mapping.
VIP
Service virtual IP, load-balanced by proxy.
kube-proxy backends
userspace / iptables / IPVS.
Lease
coordination object for leader election + node heartbeat.
Eviction
control-plane removal of Pods from a failing node.
MVCC
multi-version concurrency control (revisioned KV).
Compaction
reclaiming old MVCC revisions.
Watch cache
apiserver in-memory replica serving reads + watches.
Quota

node-restriction
