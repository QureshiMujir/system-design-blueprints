Decisions (§9) · 30 ADRs

01

Language

Chosen

Go 1.22+

Rejected

Rust, C++, Java

When the rejected choice is right

Latency-critical or footprint-constrained components with no GC pause budget (a dataplane packet loop, an embedded node agent at tight RAM): Rust or C++ win, trading iteration speed and the Go-native ecosystem for deterministic tail latency and zero managed-runtime overhead

Why: ecosystem 1:1, goroutine control loops, GC fine for control plane

02

Build

Chosen

Go modules + Makefile

Rejected

Bazel

When the rejected choice is right

Monorepos with deeply nested transitive deps where hermetic caching of every dep is worth the Starlark investment and CI cache-hit rate is the primary constraint

Why: single-repo, fast go build; Bazel overkill Phase 0

03

Dependency policy

Chosen

stdlib-first; vetted minimal deps

Rejected

vendor-everything

When the rejected choice is right

Security-critical supply chains or regulated environments where every transitive dep must be audited and vendoring provides an immutable, reviewable snapshot at the cost of repo size

Why: auditability; fewer supply-chain surfaces

04

Store engine

Chosen

embedded MVCC B+tree (bbolt-style) + WAL

Rejected

sqlite, raw files

When the rejected choice is right

Write-heavy workloads where relational integrity and query expressiveness (joins, secondary indexes) outweigh the MVCC watch-index; SQLite wins when the query pattern is ad-hoc and the object model is not a KV log

Why: page-cache friendly, txn + watch index natural

05

Store replication

Chosen

single-node Phase 0 → Raft (Phase 12)

Rejected

Paxos, external etcd

When the rejected choice is right

Operationally mature teams that already run etcd clusters and want battle-tested replication, lease, and watch semantics without implementing Raft; external etcd wins when the learning objective is already met elsewhere

Why: learn it; Raft understandable; etcd would hide the point

06

Wire codec

Chosen

JSON (served) + protobuf (internal store)

Rejected

JSON-only, CBOR

When the rejected choice is right

Extremely bandwidth-constrained or latency-sensitive networks (e.g. edge IoT, satellite links) where binary compactness of CBOR or protobuf end-to-end eliminates the JSON parse cost even at the API edge

Why: JSON debuggable at API edge; protobuf compact at rest

07

API transport

Chosen

net/http (HTTP/1.1 + HTTP/2) + TLS

Rejected

gRPC for north API

When the rejected choice is right

Internal microservice-to-microservice communication where both sides are generated from a proto schema, bidirectional streaming is needed, and REST discoverability is irrelevant; gRPC wins on the north API when clients are controlled and schema evolution is via proto IDL

Why: REST+watch is the contract; gRPC reserved for CRI

08

CRI transport

Chosen

gRPC over unix socket

Rejected

HTTP

When the rejected choice is right

Debugging or audit scenarios where inspecting raw control-plane traffic with curl or a proxy is more valuable than the CRI spec compliance; HTTP-over-socket wins when runtime is under active development and live introspection matters most

Why: matches CRI spec, streaming exec

09

Async model

Chosen

goroutines + channels + context

Rejected

callback reactor

When the rejected choice is right

CPU-bound, I/O-bound, or latency-SLA-critical data planes (e.g. a packet processing loop) where goroutine scheduling jitter is unacceptable and an explicit event-loop with no preemption (epoll reactor or io_uring) gives predictable tail latency

Why: idiomatic, cancelation via context

10

Concurrency primitive

Chosen

workqueue (rate-limited, deduped) + RWMutex caches

Rejected

actor framework

When the rejected choice is right

Distributed actor systems (e.g. Erlang/Akka-style) where location-transparent message passing, supervision trees, and mailbox backpressure are the primary design primitives and the actor framework provides built-in distribution; wins when failure isolation is per-actor, not per-queue

Why: matches client-go, debuggable

11

Leader election

Chosen

Lease object + CAS renew

Rejected

external ZK/Chubby

When the rejected choice is right

Geographically distributed or multi-cluster deployments where an external coordination service (ZooKeeper, etcd) already exists and is operated at high reliability; external ZK/Chubby wins when the self-hosted lease would add a dependency bootstrap cycle

Why: self-hosted, dogfoods own API

12

Scheduler arch

Chosen

single-queue framework (filter/score plugins)

Rejected

shared-state multi-sched

When the rejected choice is right

Clusters with heterogeneous workload classes (ML training, batch, latency-sensitive serving) that benefit from gang scheduling, resource-offer semantics, or framework-specific placement logic; Omega shared-state or Mesos two-level wins when scheduling policy diversity cannot be expressed as plugin weights

Why: simplest correct; Phase 13 scales it

13

Proxy backend

Chosen

userspace default; iptables + IPVS pluggable

Rejected

eBPF-only

When the rejected choice is right

Environments where eBPF is stable and available (Linux 5.10+), scale demands O(1) dataplane programming, and L7/identity-aware policy is required; eBPF wins when iptables sync latency or conntrack overhead becomes measurable at the target service count

Why: iptables ubiquitous; eBPF deferred (Phase 8, §8.10)

14

Logging

Chosen

structured slog (JSON)

Rejected

printf

When the rejected choice is right

Append-only audit pipelines, log-shipping infrastructure, or multi-consumer fan-out systems where a structured binary log format (protobuf framing) provides indexable, schema-versioned, compact records and human readability is a secondary concern

Why: machine-parseable, leveled

15

Metrics

Chosen

Prometheus text exposition /metrics

Rejected

statsd

When the rejected choice is right

Push-based collection environments (e.g. short-lived batch jobs, functions-as-a-service) where scrape timing misses ephemeral processes; statsd/push wins when job lifetime is shorter than the Prometheus scrape interval

Why: pull model, ecosystem standard

16

Tracing

Chosen

OpenTelemetry spans (request → admission → store)

Rejected

none

When the rejected choice is right

Performance-critical inner loops or homogeneous microservice meshes where the overhead of span context propagation per operation is measurable and sampling cannot reduce it adequately; "none" wins when trace cardinality exceeds storage budget and logs + metrics already cover latency attribution

Why: cross-component latency attribution

17

Testing

Chosen

go test + envtest-style integration + fixtures

Rejected

mocks-only

When the rejected choice is right

Pure unit-test suites for stateless algorithmic logic (codec round-trips, scheduler scoring math) where spinning a real store adds test-cycle time without exercising additional invariants; mocks-only wins for sub-millisecond property tests

Why: exercise real store + apiserver

18

Fuzzing

Chosen

go-fuzz on decoders + patch engine

Rejected

none

When the rejected choice is right

Mature, slow-changing parsers where the input grammar is well-specified and fuzz coverage is already high; "none" wins when the decoder is generated from a tight schema with no hand-written parsing branches

Why: malformed-object resilience

19

CI/CD

Chosen

GitHub Actions: build/test/lint/conformance

Rejected

Jenkins

When the rejected choice is right

Organizations with existing Jenkins infrastructure, custom build-farm hardware, or compliance requirements that prohibit SaaS CI; Jenkins wins when hermetic builds on owned hardware are a regulatory constraint

Why: repo-native

Packaging

Chosen

multicall static binary + Dockerfile

Rejected

per-role images Phase 1

When the rejected choice is right

Large-scale production deployments where per-role images enable independent update, rollback, and vulnerability patching of individual components without rebuilding the multicall binary; per-role images win when image layer caching and SBOM granularity matter

Why: one artifact, all-in-one dev

Orchestration of self

Chosen

systemd units (host) + compose (dev)

Rejected

k8s-on-k8s

When the rejected choice is right

Production Kubernetes clusters where the control plane itself can be self-hosted (kubeadm-style), providing the full Kubernetes API for health checks, rolling upgrades, and scaling of the orchestrator's own components

Security tooling

govulncheck + gosec + trivy image scan

Rejected

none

Fully air-gapped environments with no internet access where pulling scanner DB updates is impossible; manual audit or an offline DB snapshot wins when network policies prohibit outbound scanner traffic

Why: supply-chain hygiene

Release eng

Chosen

one internal + one served (v1) + conversion fns

served==stored

Small, stable APIs with a single served version and no migration path planned; served==stored wins when the complexity of conversion functions exceeds the benefit and the API surface is locked

Authn

Chosen

client-cert + bearer-token (static Phase 0)

Rejected

OIDC

When the rejected choice is right

Production clusters with an existing identity provider (Dex, Okta, Google Workspace) where OIDC tokens provide short-lived, auditable, group-scoped credentials with zero manual rotation overhead

Authz

Chosen

node-restriction + coarse RBAC (verbs×resources)

Rejected

full RBAC matrix

When the rejected choice is right

Multi-tenant clusters with complex, attribute-based access control (ABAC) requirements, per-resource fine-grained verbs, and dynamic role binding; full RBAC matrix wins when namespace-level coarse rules leave privilege gaps

Why: least-privilege node, simple rules

Time

Chosen

monotonic clock for timeouts, wall for timestamps

Rejected

wall-only

When the rejected choice is right

Distributed systems spanning wide-area networks or multiple data centers where network partitions cause measurable wall-clock skew between nodes, requiring monotonic-only timekeeping for all lease and timeout logic regardless of NTP accuracy

Why: skew-resilient leases

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-A — Monolithic Single-Master Scheduler + State (Borg-style)

┌────────────────────────────────────────────────────────┐
│                    Borgmaster (single process)           │
│  ┌──────────┐  ┌──────────┐  ┌──────────────────────┐  │
│  │ in-memory│  │scheduler │  │  admission / authz    │  │
│  │ cell state│  │ (direct) │  │  (all in one binary) │  │
│  └────┬─────┘  └────┬─────┘  └──────────────────────┘  │
│       │ replicated   │ bind direct                       │
│       ▼              ▼                                   │
│  Chubby (Paxos) ─── master lock                         │
└────────────────────────────────────────────────────────┘
         │ (push notifications, no watch API)
    ╔════╧════╗   ╔════════╗   ╔════════╗
    ║ Borglet ║   ║Borglet ║   ║Borglet ║
    ╚═════════╝   ╚════════╝   ╚════════╝

Wins when: scheduling throughput is the primary constraint (single-process direct scheduling skips network round-trips); cell is a single administrative unit with no external API consumers; operator count is small and can tolerate scheduled maintenance windows for upgrades.

Embodied by: Google Borg (Verma et al., EuroSys 2015).

Why rejected here:

  • In-memory state means a master restart requires a full cluster rescan (Borgmaster takes ~10 min to recover a large cell per Verma et al. 2015); this blueprint requires RTO ≤ 60 s (§4).
  • No external watch API: third-party controllers must be compiled into Borgmaster — impossible to build the Phase 4 informer/workqueue pattern as a separate library.
  • Tight scheduler + state + admission coupling makes unit-testing each layer impossible in isolation; a scheduler bug can corrupt in-memory state directly without the registry CAS gate (I3).
  • Contradicts the core Phase 0–Phase 4 learning objective: building store, registry, and informer as separately testable, crash-only-restartable units requires them to be separate processes.

Alt-B — Two-Level Resource Offers (Mesos-style)

┌──────────────────────────────────────┐
│   Mesos Master (resource allocator)   │
│  ┌──────────┐  ┌────────────────────┐ │
│  │  DRF     │  │  offer allocator   │ │
│  │  (fair)  │  │  (resource → fmwk) │ │
│  └──────────┘  └────────────────────┘ │
└──────┬───────────────────┬────────────┘
       │ Resource Offer     │ Resource Offer
       ▼                    ▼
 ┌──────────┐        ┌──────────────┐
 │ Marathon │        │ Spark / etc  │
 │(app fmwk)│        │ (batch fmwk) │
 └──────────┘        └──────────────┘
       │ Accept / Decline
       ▼
 ┌──────────┐
 │Mesos Agent│
 └──────────┘

Wins when: a single cluster runs heterogeneous workloads with incompatible scheduling semantics (Spark gang-scheduling + Marathon long-running services + chronos batch) and each framework must implement custom placement logic that cannot be expressed as plugin weights in a single scheduler; DRF fair-sharing across frameworks is a hard requirement.

Embodied by: Apache Mesos + Marathon (Hindman et al., NSDI 2011).

Why rejected here:

  • Offer-accept adds a mandatory second RTT per placement (offer → framework decision → accept → task launch); at §4's 5 ms RTT, this doubles minimum bind latency before even considering the store write.
  • Frameworks can decline offers indefinitely and hoard resources; the cluster appears free but is functionally fragmented — a correctness problem, not just a performance one.
  • Marathon's REST API is imperative (create-container-now), not spec/status separated; after a controller crash, there is no store-level truth to reconcile against (violates §6 P1 and every §7 invariant that requires a canonical revision).
  • Three independent failure domains (Mesos master + ZooKeeper quorum + per-framework schedulers) vs this blueprint's one (ADR-20 single-binary), tripling the operational reasoning surface for Phase 0.

Alt-C — Single-Binary Multi-Region Federated Raft (Nomad-style)

┌─────────────────────────────────────────────────────┐
│              Nomad Server Cluster (3-5 nodes)         │
│  ┌──────────────────────────────────────────────┐    │
│  │  Raft FSM: job registry + allocation state   │    │
│  │  Scheduler (bin-packing) — all in one binary │    │
│  │  API server — HCL + JSON interface           │    │
│  └──────────────────────────────────────────────┘    │
└──────────┬────────────────────┬─────────────────────┘
           │ gossip (Serf)       │ gossip
    ╔══════╧════╗         ╔══════╧════╗
    ║Nomad Client║         ║Nomad Client║
    ║(task driver)║        ║(task driver)║
    ╚════════════╝         ╚════════════╝

Wins when: operational simplicity is the primary constraint (one binary, no external dependencies beyond Go runtime); workloads are polyglot (containers, JVM, raw binaries, VMs via QEMU driver); multi-region federation with a single API is needed; teams cannot afford the operational overhead of managing etcd separately.

Embodied by: HashiCorp Nomad.

Why rejected here:

  • Single-binary coupling prevents incremental testing: a scheduler bug requires running the full Raft FSM to reproduce, rather than injecting a mock store into the Phase 5 unit tests.
  • Blocking-query long-poll lacks MVCC watch semantics (I1, I8): no compaction-guarded resume-from-RV means an informer cache has no correct relist-on-gap behavior — every 410-equivalent forces a full resync.
  • HCL job spec has no spec/status separation (§6 P7): observedGeneration has no equivalent, making rollout correctness (D.4) unverifiable — you cannot distinguish "applied" from "converged."
  • Gossip membership (Serf) provides eventual consistency on node liveness, weaker than Lease-CAS (ADR-11) under partition; a controller can act on a node that has partitioned, transiently violating I10.

Alt-D — Shared-State Optimistic-Concurrency Multi-Scheduler (Omega-style)

┌─────────────────────────────────────────────────────┐
│               Shared Cell State (Omega store)         │
│  ┌─────────────────────────────────────────────────┐ │
│  │  Object state with per-resource version locks   │ │
│  │  (optimistic CAS, not a single serialized write)│ │
│  └──────┬──────────────────────┬───────────────────┘ │
└─────────┼──────────────────────┼─────────────────────┘
          │ read full state       │ read full state
          ▼                       ▼
   ┌─────────────┐         ┌─────────────┐
   │ Scheduler A │         │ Scheduler B │
   │(ML training)│         │(serving)    │
   └──────┬──────┘         └──────┬──────┘
          │ CAS write              │ CAS write
          └──────────────┬─────────┘
                  conflict → retry

Wins when: the cluster must support multiple, simultaneously active scheduler implementations with different placement policies (e.g. gang-scheduling for ML + latency-aware for serving + batch bin-packing) that must co-exist on the same node pool without a two-level offer round-trip; scheduling throughput (parallelism) is more important than placement optimality; and retry-on-conflict overhead is acceptable given low contention in practice.

Embodied by: Omega (Schwarzkopf et al., EuroSys 2013).

Why rejected here:

  • Optimistic retry is efficient only when contention is low; contention is low only when schedulers target distinct resource domains. A 50-node Phase 0 cluster (§1) with one workload class has every scheduler competing for the same general-purpose nodes — conflict probability grows with scheduler count, not inversely.
  • A shared-state store with per-resource CAS is a second consistency layer orthogonal to the MVCC store (Phase 1); it requires its own invariants analogous to I3 but across concurrent readers, doubling the invariant surface area to reason about and test.
  • Multiple schedulers need a starvation-prevention mechanism for the bind slot: when two schedulers score the same node as best for different Pods simultaneously, the loser must re-search the entire feasible set (not just retry one node), reintroducing distributed coordination analogous to ADR-12 but without the simplicity of a single queue.
  • Phase 13 node-sampling already achieves the §4 scale target (≥ 100 Pods/s at 5k nodes, ≤ 100 ms p99) within the single-queue framework with no retry overhead and no second consistency layer; the Omega model buys parallelism at a cost this blueprint does not need until well beyond Phase 13 scale.
