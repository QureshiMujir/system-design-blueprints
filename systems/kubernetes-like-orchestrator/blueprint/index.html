1. Goal

Build a container orchestrator with a declarative, level-triggered control plane and a node-local data plane, from scratch. The system reconciles observed cluster state toward user-declared desired state through independent control loops, schedules Pods onto Nodes, and runs containers via a CRI shim.

In scope (Phase 0 deliverable):

  1. apiserver — declarative REST API, resource versioning, optimistic concurrency, watch streams, admission chain.
  2. store — MVCC key-value backend with watch + compaction (embedded; Raft-replicated later).
  3. scheduler — predicate/filter + priority/score + bind cycle.
  4. kubelet — node agent; Pod sync loop; probes; status reporting.
  5. cri-shim — Container Runtime Interface adapter over an OCI runtime.
  6. controller-manager — ReplicaSet, Deployment, Node, Endpoints, GC controllers; leader election.
  7. kube-proxy — Service VIP dataplane (userspace + iptables/IPVS backends).
  8. orctl — CLI: apply/get/describe/delete/logs/watch.
  9. apimachinery — shared types, codecs, scheme, informers, workqueue.

System boundaries. Manages: Pods, controllers, scheduling, Service VIPs, node lifecycle. Delegates: container exec to OCI runtime (project #35), image pull to a registry (#166), CNI plugin to an external binary, persistent storage to CSI later.

Non-goals (Phase 0): multi-master HA store (single embedded store first), full RBAC matrix (coarse authz first), StatefulSet/DaemonSet/Job (added post-0), HPA/VPA autoscaling (#269), Ingress controllers, network policy enforcement, CSI volume attach, webhook admission servers (in-tree admission only), CRD/aggregated API, audit-to-SIEM.

Deployment model. Single binary per role or one hyperorc multicall binary. Local dev: all roles in one process (--all-in-one). Cluster: 1 control-plane host + N worker hosts. Node agent runs as PID-1-adjacent daemon. Linux x86-64/aarch64; cgroup v2; namespaces.

Target users. Platform engineers learning orchestration internals; operators running small clusters (≤ 50 nodes, ≤ 5k Pods Phase 0); developers studying reconciliation, watch caches, and scheduling.

What later phases unlock. Raft-replicated store (3/5-node quorum); StatefulSet/DaemonSet/Job; horizontal autoscaling; admission webhooks; CRDs; network policy; CSI; topology-aware scheduling; priority/preemption; graceful node drain; multi-tenancy.

Deferred features, each gated behind a PhaseDeferred(...) anchor that resolves to the Operational-Notes subsection (§N.10) of the phase that will build it, and recorded in the Deferred Features Register:

  • Raft store replication — PhaseDeferred("FINAL_BLUEPRINT §12.10").
  • CSI volume lifecycle — PhaseDeferred("FINAL_BLUEPRINT §11.10").
  • Webhook admission — PhaseDeferred("FINAL_BLUEPRINT §9.10").
  • eBPF dataplane (Cilium-style) — PhaseDeferred("FINAL_BLUEPRINT §8.10").
  • GPU/device plugins — PhaseDeferred("FINAL_BLUEPRINT §6.10").

Estimated timeline. Phase 0: 12–14 weeks (1–2 engineers). Full spec: 9–14 months.

Recommended language: Go. Rationale: green-threaded concurrency (goroutine-per-watch, per-reconcile) matches the control-loop model; net/http + encoding/json give a first-class declarative API with low ceremony; structural typing eases the scheme/codec layer; the orchestration ecosystem (etcd, gRPC, OCI, CNI) is Go-native, so reference reading maps 1:1; GC pauses are acceptable for a control plane (not a dataplane hot loop). Rejected: Rust (borrow checker friction against the heavily-shared informer cache and reflection-style scheme; slower iteration); C++ (no memory safety, weak std concurrency); Java (heap/latency footprint on node agents).

Prerequisites. Linux namespaces + cgroup v2; OCI runtime/image specs; MVCC + watch semantics; level- vs edge-triggered control theory; optimistic concurrency control; distributed-systems failure models (partition, partial failure); HTTP/1.1 chunked + HTTP/2 streaming; iptables/netfilter and IPVS; basic Raft (for Phase 12).

2. Why Build This

  • Declarative reconciliation — the single most transferable idea in modern infra: store desired state, observe actual, drive the delta to zero, forever. Generalizes to Terraform (#267), GitOps, controllers everywhere.
  • Level-triggered design — why orchestrators survive lost events and crashes where edge-triggered (event-callback) systems silently wedge. You will feel the difference when you kill the controller mid-rollout and it heals.
  • Watch + informer cache — how to expose a consistent, resumable event stream over MVCC storage without hammering the store; resourceVersion bookmarks, relist-on-gap, delta FIFO.
  • Optimistic concurrency — compare-and-swap on resourceVersion instead of locks; how distributed writers stay correct without a global mutex.
  • Scheduling as constraint solving — predicates (hard feasibility) then priorities (soft scoring); the same filter/score shape as resource allocators (#201) and ML serving schedulers (#254).
  • Control-plane/data-plane split — slow consistent brain, fast local muscle; identical to SDN (#217), service mesh (#164), load balancers (#66).
  • Cross-links. Store ↔ #36 etcd-like KV, #37 Raft; runtime ↔ #35 container runtime; registry ↔ #166; proxy ↔ #66 load balancer, #82 reverse proxy; scheduler ↔ #200 distributed scheduler, #201 resource allocator; leader election ↔ #198; CNI ↔ #156/#157 networking; observability ↔ #132/#133.
  • Calibration. After this, "eventual consistency under partial failure" stops being a phrase and becomes a set of mechanical reflexes: idempotent writes, generation/observedGeneration, finalizers, owner refs, exponential-backoff workqueues. This is the backbone project of the cloud-native curriculum.

What Mastery Looks Like — finishing this blueprint means you can:

  • Design a level-triggered reconciliation loop from scratch, explain why it heals after any crash without replay of missed events, and identify the exact bug class (state drift) a naive edge-triggered alternative produces (Phase 0, Phase 4)
  • Build an MVCC key-value store with watch semantics — implement revision assignment, watcher fan-out, compaction guarded by min-watcher-RV, and WAL crash recovery — and explain every invariant (I1, I8, I14) that makes the watch stream resumable (Phase 1, Phase 3)
  • Implement optimistic concurrency across a distributed set of controllers without any cross-object locks, and derive the correct retry discipline so conflicting writes converge instead of oscillating (Phase 2, Phase 7)
  • Build a pluggable scheduling framework (filter/score/bind), tune the cache snapshot pattern, reason about O(nodes) vs O(nodes²) complexity for affinity plugins, and extend it to priority/preemption without starvation (Phase 5, Phase 13)
  • Operate a production kubelet that is autonomous under control-plane outage — re-adopts containers on restart, never kills running Pods on apiserver loss, and surfaces every failure mode with probe metrics and structured events (Phase 6)
  • Design and deploy a Raft-replicated store, reason about linearizable vs lease reads, membership change safety, and revision-monotonicity across leader elections — and wire it under the existing MVCC/watch API transparently (Phase 12)
  • Write a conformance suite and chaos harness that proves all fourteen system invariants (§7), runs every crash scenario, and gates release on quantitative SLO targets from §4 (Phase 10)

Per-box.

  • apiserver — the only writer to store. Stateless, horizontally scalable. Terminates auth, runs the admission chain (mutating then validating), enforces schema + optimistic concurrency, and fans out watch streams. All other components are clients; they never touch store directly. This is the single serialization point that makes the cluster reasoned-about.
  • store — MVCC KV: every key carries a monotonically increasing global revision; watchers resume from a revision; compaction reclaims old revisions. Phase 0 embeds a single-node MVCC engine (BoltDB-style B+tree pages + in-memory watch index). Phase 12 promotes it to a Raft group.
  • registry (REST) — per-resource strategy objects implementing Create/Get/List/Update/Delete/Watch with defaulting, validation, and resourceVersion CAS. Maps REST verbs to store ops; owns the metadata lifecycle (uid, generation, creationTimestamp, deletionTimestamp, finalizers).
  • admission chain — ordered mutating plugins (defaulting, owner-ref injection, resource-quota debit) then validating plugins (schema, immutable-field, quota check). Webhook plugins deferred (Phase 9, §9.10).
  • informer caches — per-controller local replicas of a resource type, populated by an initial List then kept live by a Watch; deliver Add/Update/Delete deltas into a workqueue. The mechanism that lets dozens of controllers observe state without melting the store.
  • scheduler — watches unbound Pods (spec.nodeName==""), runs filter (feasibility: resources, taints, affinity, ports) then score (spread, least-allocated), then issues a Bind write that sets nodeName. Stateless; restart-safe (re-derives from store).
  • controller-manager — hosts reconciler loops: ReplicaSet (Pod count), Deployment (rollout/rollback over ReplicaSets), Node (heartbeat→Ready/NotReady, eviction), Endpoints (Service↔Pod IP mapping), GC (orphan deletion via owner refs). Leader-elected so exactly one instance acts.
  • kube-proxy — per-node; watches Services + Endpoints; programs the local dataplane so a Service VIP load-balances to ready backend Pod IPs. Backends: userspace (portal proxy, debuggable), iptables (DNAT chains), IPVS (hash/RR/least-conn).
  • kubelet — per-node agent; watches Pods bound to its node; drives each Pod's lifecycle through a PodWorker; runs liveness/readiness/startup probes; mounts volumes; reports Pod + Node status back to apiserver. The data-plane reconciler.
  • cri-shim — translates kubelet's CRI gRPC (RunPodSandbox, CreateContainer, StartContainer, ...) into OCI runtime calls; manages the pause/sandbox container, shared network namespace, and image unpacking.
  • dataplane (iptables/IPVS) — kernel-level packet rewriting installed by kube-proxy; the fast path that needs no control-plane round trip per packet.

Boundaries. Trust: control plane ↔ node (mTLS, node identity, node-restriction authz). Concurrency: every controller is an independent loop; the workqueue + optimistic CAS are the only synchronization. Persistence: only store persists; everything else is a cache rebuildable from store. Protocol: REST/watch (north), CRI gRPC (kubelet↔shim), CNI exec (shim↔plugin), Raft (store↔store, Phase 12).

6. Design Principles

  1. P1 — Declarative desired state, never imperative commands. Clients write what they want; controllers compute how. Tradeoff: indirection vs robustness. Operationally: any client can re-declare and the system converges. Violation: an imperative "create container X now" API has no truth to reconcile against after a crash — state drifts permanently.
  2. P2 — Level-triggered, not edge-triggered. Reconcile against current observed state, not against the event that woke you. Tradeoff: periodic resync cost vs correctness under lost events. Violation: missing one "Pod deleted" event leaks the Pod forever; level-triggered relist heals it.
  3. P3 — The store is the single source of truth. All durable state lives in store; every other component is a cache rebuildable from it. Tradeoff: store is the bottleneck + SPOF (until Phase 12). Violation: a controller caching authoritative state means a restart loses cluster truth.
  4. P4 — Optimistic concurrency, no cross-object locks. Writes carry resourceVersion; conflicting writes lose and retry. Tradeoff: retry churn under contention vs no lock-ordering deadlocks. Violation: pessimistic locks across objects deadlock controllers against each other.
  5. P5 — Idempotent reconciliation. Running a reconcile twice with the same input yields the same result. Tradeoff: must dedupe by identity (owner refs, names) not by "did I already act." Violation: non-idempotent create on retry spawns duplicate Pods.
  6. P6 — Data plane survives control-plane outage. Running containers keep running when apiserver/scheduler/controllers are down. Tradeoff: stale node config during partitions. Violation: a kubelet that kills Pods when it loses the apiserver turns a control-plane blip into an outage.
  7. P7 — Generation / observedGeneration for progress. spec bumps metadata.generation; controllers record status.observedGeneration. Tradeoff: extra status writes. Violation: clients cannot tell "applied" from "in flight," and rollouts look done before they are.
  8. P8 — Owner references + finalizers for lifecycle. Children point at owners; finalizers gate deletion until cleanup runs. Tradeoff: deletion is multi-step, not instant. Violation: deleting a Deployment orphans ReplicaSets and Pods; missing finalizers leak external resources.
  9. P9 — Watch over poll. Controllers consume change streams from a local informer, not periodic full lists. Tradeoff: watch-cache memory + relist-on-gap complexity. Violation: N controllers polling LIST melts the store at scale.
  10. P10 — Backpressure + bounded workqueues everywhere. Rate-limited, deduped, exponential-backoff queues between watch and reconcile. Tradeoff: latency under burst. Violation: unbounded reconcile fanout OOMs the controller and stampedes the apiserver.
  11. P11 — Explicit API versioning + conversion. Served versions convert to one internal version; storage version is pinned. Tradeoff: conversion code. Violation: persisting the served wire shape freezes the API forever.
  12. P12 — Crash-only components. Every process can be kill -9'd and restarts clean by re-reading store. Tradeoff: no in-memory-only invariants. Violation: graceful-only shutdown logic rots and fails exactly during the incident.
  13. P13 — Observable by default. Every loop emits queue depth, reconcile latency, error counters, and per-object events. Tradeoff: cardinality management. Violation: a wedged controller is invisible until users complain.
  14. P14 — Least privilege between roles. Node identity ≠ admin; the node-restriction plugin limits what a kubelet can write. Tradeoff: authz complexity. Violation: a compromised node rewrites the whole cluster.

8.4 Watch protocol

Phase 1 — Store: MVCC KV + Watch + Compaction

1.1 Objectives

A single-node revisioned KV with transactional CAS, ordered watch from any revision, and safe compaction. This is the durability + watch substrate the apiserver builds on.

1.2 Detailed Implementation Steps

  • store/backend: B+tree page store (copy-on-write pages) + WAL (append record {rev, key, val, op}); fsync policy (batch-commit, group-fsync every N ms or M writes). (Petrov "Database Internals" chs. 2–4; ADR-04)
  • store/mvcc: key→(createRev, modRev, version) index in a B+tree; value keyed by (key, modRev) so history is retained until compaction.
  • Txn: single writer goroutine; evaluate Compare (modRev equals/less/greater) → apply Then|Else Ops atomically → assign next global revision → append WAL → ack. This is the CAS that powers I3/I5. (Ongaro & Ousterhout Raft 2014; I3, I5)
  • store/watch: watcher registry keyed by range; on commit, fan out events to watchers whose range intersects, in revision order (I8). Synthesize BOOKMARK periodically. (Burns et al. ACM Queue 2016; I8, I14)
  • store/compactor: drop value versions with modRev < compactRev, except keep the latest per key; guard with min(activeWatcherStartRev) (I14). (I14; ADR-04)
  • Recovery: on boot, replay WAL after last checkpoint; rebuild watch index lazily.

1.3 Deliverable

store binary/lib: put/get/range/txn/watch/compact; survives kill -9 mid-write and recovers to last committed revision.

1.4 Acceptance Criteria

  • Crash-consistency: 10k random writes + kill at random points → recovered state equals last acked revision (no torn writes).
  • Watch from RV=v delivers exactly the events with rev>v, in order, no dupes (sequence assertion).
  • Compaction with a live watcher at old RV does not drop needed revisions (I14 test).
  • Write p99 ≤ 5 ms (group-fsync, local SSD); range(1k keys) ≤ 10 ms.

1.5 Conformance Fixtures

store/txn-cas-success, store/txn-cas-fail, store/watch-resume-after-gap, store/compact-guard, store/crash-replay-seed (WAL image + expected state).

1.6 Pitfalls

  • fsync per write → throughput collapse. Batch + group-commit; measure with store_commit_batch_size.
  • Watch fan-out under lock → commit latency spikes. Hand events to per-watcher buffered channels; drop slow watchers to Gone rather than block the writer.
  • Compacting a revision a watcher needs → 410 storms / data loss. Always clamp compactRev to min watcher RV.
  • Torn WAL record on crash → corrupt replay. CRC each record; stop replay at first bad CRC (that's the crash point).

1.7 Performance Concerns

Group-commit amortizes fsync. COW pages avoid in-place corruption but amplify writes (target ≤ 3×, §4). Watch buffers bound memory; slow-watcher eviction prevents head-of-line blocking. Range reads hit page cache; keep keys sorted by (resource, namespace, name) for locality.

1.8 Edge Cases

Empty range; watch on not-yet-existing key; compactRev in the future (reject); revision overflow (int64 — practically unreachable, but assert); concurrent compaction + watch registration.

1.9 Failure Analysis

Store corruption ⇒ cluster truth lost. Detection: CRC + page checksums + decode validation (I13). Containment: single writer + WAL means recovery to a consistent point. Recovery: replay; if WAL corrupt past point P, recover to P and alert. Forensics: WAL is the audit log of every mutation.

1.10 Operational Notes

Metrics: store_revision, store_commit_seconds, store_db_bytes, store_watchers, compact_revision, wal_fsync_seconds. Runbook store-corrupt.md: stop apiserver, snapshot db file, attempt replay-to-point, restore from last good snapshot. Backup = periodic db snapshot + WAL ship (see Operational Readiness).

Phase 2 — apiserver: REST Registry + Optimistic Concurrency

2.1 Objectives

Serve declarative CRUD with resourceVersion CAS, per-resource strategy (default/validate/generation), subresources (/status), and content negotiation (JSON/protobuf). The single writer to store.

2.2 Detailed Implementation Steps

  • apiserver/server: http mux, TLS, GVR routing /{group}/{version}/namespaces/{ns}/{resource}/{name}[/status]. (ADR-07; ADR-27)
  • registry: generic Store over Object mapping verbs→store Txn; assigns uid/RV/creationTimestamp on create (I2); CAS modRev on update (I3); generation bump on spec change (I4). (Schwarzkopf et al. Omega 2013; I3, I4)
  • Per-resource Strategy (Pod, Deployment, ...): PrepareForCreate clears status; PrepareForUpdate preserves status + immutable fields; ValidateCreate/Update.
  • Subresources: /status writes status only (I9); /scale for Deployment/RS replicas.
  • Deletion: set deletionTimestamp + gracePeriod; if finalizers present, soft-delete (I6); GC/owner controllers later remove finalizers. (I6; ADR-27)
  • PATCH: JSON/merge/strategic dispatch by Content-Type. (RFC 6902, RFC 7386; ADR-06)
  • Content negotiation: Accept: application/json|application/vnd.hyperorc.protobuf.

2.3 Deliverable

orctl apply/get/describe/delete round-trips against a live apiserver; conflicting updates return 409; status subresource enforced.

2.4 Acceptance Criteria

  • Create→Get→Update(stale RV)→409→refetch→Update(ok) sequence passes.
  • Spec edit bumps generation; status edit does not (I4).
  • Delete with finalizer → object persists with deletionTimestamp until finalizer removed.
  • 10k objects: List(namespace) ≤ 50 ms (cache, Phase 4) / ≤ 150 ms (store).

2.5 Conformance Fixtures

api/create-get, api/update-conflict, api/status-subresource, api/delete-finalizer, api/patch-strategic, api/list-paginate, malformed/spec-status-cross-write (reject 403).

2.6 Pitfalls

  • Letting clients write status → controllers and users fight. Enforce subresource split (I9).
  • Not bumping generation correctly → rollouts never converge (observedGeneration mismatch). Hash spec, compare.
  • Hard-deleting with finalizers → external leak. Soft-delete path mandatory.
  • RV as int vs opaque string → clients do arithmetic on it. Treat RV as opaque token at the API edge.

2.7 Performance Concerns

Admission + validation are per-write CPU. List without cache hits store; add field/label index. Protobuf at store halves bytes. Avoid full-object decode when only metadata is needed (metadata-only list path).

2.8 Edge Cases

Create with client-set RV (reject); update changing immutable field (reject 422); namespace mismatch in body vs URL (reject); dry-run apply (validate, no write); server-side apply field ownership (defer to Phase 19/20).

2.9 Failure Analysis

A broken CAS lets two writers clobber each other → lost updates → controllers oscillate. Detection: update_conflict_total near zero is suspicious (CAS not engaged). Containment: registry is the only writer. Recovery: clients retry on 409. Forensics: store WAL shows the exact overwrite.

2.10 Operational Notes

Metrics: apiserver_request_duration{verb,resource,code}, apiserver_inflight, update_conflict_total, create_conflict_total. Trace span per request: authn→authz→admission→store. Log every 4xx/5xx with object ref. Runbook apiserver-down.md.

Phase 3 — Watch Endpoint + Leader Election Substrate

3.1 Objectives

Expose resumable watch streams over the store's watch, plus the Lease-based leader election controllers depend on (I10).

3.2 Detailed Implementation Steps

  • endpoints watch handler: ?watch=1&resourceVersion=V → chunked HTTP stream of typed events; translate store events → API events (decode + version convert); emit BOOKMARK on interval. (Burns et al. ACM Queue 2016; I8, ADR-07)
  • On V older than store compactRev → respond 410 Gone (client relists). (I14; I8)
  • client/rest watch client: reconnect, track last RV, relist on Gone.
  • controllers/leaderelection: acquire Lease via CAS create/update; renew every leaseDuration/3; on renew failure beyond duration, release; observers see holderIdentity change. (Burrows "Chubby" OSDI 2006; I10, ADR-11) (ADR-30; I10)

3.3 Deliverable

A client can watch Pods and see live changes; killing the writer and resuming from last RV loses nothing. One of N controller-managers wins the lease; killing it lets another take over within leaseDuration.

3.4 Acceptance Criteria

  • Watch resume after disconnect at RV=v misses zero events with RV>v (I8).
  • Compacted RV → 410 → relist → resume (no crash, no dup).
  • Leader failover ≤ leaseDuration (default 15 s); never two active leaders (I10) under clock skew ≤ 500 ms.

3.5 Conformance Fixtures

watch/resume-clean, watch/resume-after-compact-410, watch/bookmark-advances-rv, lease/acquire-renew, lease/failover, lease/double-leader-prevented.

3.6 Pitfalls

  • Slow watcher blocks the store writer → cluster-wide write stall. Per-watcher buffered channel; evict slow watchers to 410.
  • Renewing lease on wall clock during NTP step → spurious failover. Use monotonic clock for renew interval.
  • Not emitting BOOKMARK → clients hold very old RV → 410 storms after compaction. Bookmark periodically.

3.7 Performance Concerns

One goroutine + one store-watch channel per client connection — FD/goroutine budget (§4: 65k). Coalesce: many informers for the same resource can share one upstream store-watch (Phase 4 shared informer). HTTP/2 multiplexes watches over fewer connections.

3.8 Edge Cases

Watch with future RV (wait or error — choose: wait up to timeout); watch across compaction boundary mid-stream (send 410 inline); leader renew exactly at expiry (treat as lost); network partition isolating the current leader (it must stop acting — fence via lease expiry).

3.9 Failure Analysis

Two leaders ⇒ double reconcile ⇒ duplicate Pods, fighting rollouts. Detection: leader_changes_total spike + duplicate-action alarms. Containment: lease CAS makes it structurally impossible absent clock skew > tolerance. Recovery: shorten lease, fix NTP. Forensics: holderIdentity history in Lease object.

3.10 Operational Notes

Metrics: watch_events_total, watch_restarts_total, watch_open_connections, leader_is_leader{name}, leader_changes_total. Alert: leader_changes spike. Tracing: tag spans with holderIdentity.

Phase 4 — Informers, Listers, Workqueues (Client Machinery)

4.1 Objectives

The shared informer cache + DeltaFIFO + rate-limited workqueue that every controller and the scheduler consume. Watch-once, serve-many.

4.2 Detailed Implementation Steps

  • client/informer: List (sync) → populate indexed cache.Store → Watch (live) → deliver Add/Update/Delete to handlers; relist on Gone; HasSynced gates controller start. (Burns et al. ACM Queue 2016; I8)
  • DeltaFIFO: dedupe + coalesce per object key; preserve delete (with final state) so handlers see it.
  • SharedInformerFactory: one informer per (resource); multiple handlers share it (memory + store-watch savings). (ADR-10; P9)
  • client/workqueue: rate-limited (token bucket + per-item exponential backoff), deduped (set semantics), delayed (AddAfter). (P10; ADR-10)
  • Lister: read-through the cache by namespace/name + label selector. (P3; ADR-09)

4.3 Deliverable

A controller skeleton: informer → enqueue key → workqueue → reconcile(key) → requeue. Reusable across all controllers + scheduler.

4.4 Acceptance Criteria

  • N handlers on one resource cause exactly one upstream watch.
  • Burst of 10k events coalesces so reconcile sees latest state per key (no 10k redundant reconciles).
  • Backoff caps retries; Forget resets backoff on success.
  • Informer relist on 410 repopulates without losing deletes.

4.5 Conformance Fixtures

informer/list-then-watch, informer/relist-on-gone, informer/delete-final-state, workqueue/dedupe-coalesce, workqueue/exponential-backoff, workqueue/forget-resets.

4.6 Pitfalls

  • Missing delete events → leaked objects (level-trigger violated). DeltaFIFO must synthesize delete with last-known state on relist.
  • Hot-looping on a permanently failing item → CPU burn + store stampede. Exponential backoff + max retries → drop to dead-letter + event.
  • Mutating cached objects → cross-controller corruption. Hand out DeepCopies (principle from §11).
  • Thundering herd on startup → all controllers list at once. Jitter + shared informers.

4.7 Performance Concerns

Cache memory ∝ object count × size; metadata-only informers where spec/status unneeded. Index by label for O(1) selector serving. Workqueue dedupe bounds reconcile rate; backoff bounds store pressure (principle 10).

4.8 Edge Cases

Object created and deleted before first list (never seen — acceptable, level-trigger); resourceVersion regression after relist (always move forward); handler panics (recover, requeue, don't kill the loop); very large object churn (bound FIFO, apply backpressure upstream).

4.9 Failure Analysis

A wedged workqueue (all items max-backoff) silently stops reconciliation while looking alive. Detection: workqueue_depth rising + reconcile_total flat. Containment: per-controller queues isolate blast radius. Recovery: bounce controller (crash-only) → relist → fresh queue. Forensics: dead-letter items with last error.

4.10 Operational Notes

Metrics: workqueue_depth, workqueue_adds_total, workqueue_retries_total, workqueue_work_duration, informer_lag_seconds, informer_resyncs_total. These are the primary controller-health signals for every later phase.

Phase 5 — Scheduler: Filter → Score → Bind

5.1 Objectives

Bind unscheduled Pods to feasible, well-scored nodes via a pluggable framework, with CAS bind (I5) and restart-safe stateless operation.

5.2 Detailed Implementation Steps

  • Watch Pods where spec.nodeName=="" → enqueue.
  • scheduler/cache: node snapshot (allocatable − sum(requests of assigned pods)); kept live via informers. (Verma et al. Borg EuroSys 2015; ADR-12)
  • Filter plugins: NodeResourcesFit (requests ≤ allocatable), TaintToleration, NodeAffinity/Selector, PodAffinity/AntiAffinity, NodePorts (hostPort conflict), NodeUnschedulable. (Verma et al. Borg EuroSys 2015; I5, P1)
  • Score plugins: LeastAllocated (spread load), BalancedResourceAllocation, PodTopologySpread, ImageLocality; weighted sum → pick max (tie-break random for fairness). (ADR-12; P4)
  • Bind: write spec.nodeName via CAS (409 → re-enqueue); reserve in cache optimistically (un-reserve on bind failure). (I5; ADR-12; Schwarzkopf et al. Omega 2013)
  • Unschedulable Pods → backoff queue with reasons in status conditions; retry on cluster change (node added, pod deleted).

5.3 Deliverable

orctl apply pod.yaml → scheduler binds to a node within latency target; infeasible Pods report a clear Unschedulable reason.

5.4 Acceptance Criteria

  • Feasibility correct: never bind a Pod whose requests exceed node allocatable (I5 + resource invariant).
  • Spread: 3 replicas across 3 equal nodes land 1-per-node.
  • Bind p99 ≤ 100 ms over 1k feasible nodes; throughput ≥ 100 binds/s.
  • Restart mid-schedule loses no Pods (re-derives from store).

5.5 Conformance Fixtures

sched/fit-basic, sched/spread-replicas, sched/taint-toleration, sched/affinity-anti, sched/hostport-conflict, sched/unschedulable-reason, sched/bind-conflict-409.

5.6 Pitfalls

  • Cache divergence from store → schedule onto a full node. Reconcile cache from informer; treat bind 409 as authoritative.
  • Scoring O(pods²) for affinity → latency blowup at scale. Precompute topology maps; cap candidate nodes (sample, Phase 13).
  • Not reserving optimistically → two pods race onto the last slot. Reserve in cache between filter and bind.
  • Starvation of large Pods → small pods always win the slot. Backoff queue + priority (Phase 17).

5.7 Performance Concerns

Filter is O(nodes); score is O(feasible × plugins). Short-circuit filters (cheapest first); cap feasible set via node sampling at large N (Phase 13). Snapshot the cache per cycle to avoid lock churn. Avoid allocations in the inner loop (reuse score buffers).

5.8 Edge Cases

Zero feasible nodes (Pending+reason); all nodes equal score (random tie-break for fairness); node deleted between filter and bind (bind 409 → re-enqueue); Pod deleted mid-cycle (drop); hostPort exhaustion; affinity that references not-yet-existing pods.

5.9 Failure Analysis

A scheduler bug that overcommits a node → kubelet OOM-kills, Pods crashloop. Detection: node_pressure, pod_oom_total, bind-vs-capacity audit. Containment: NodeResourcesFit is the hard gate; kubelet eviction is the backstop. Recovery: cordon node, reschedule. Forensics: per-cycle filter/score trace.

5.10 Operational Notes

Metrics: scheduler_schedule_attempts_total{result}, scheduler_e2e_duration, scheduler_pending_pods, scheduler_unschedulable_pods{reason}. Event on every bind + every unschedulable reason (operator-visible via orctl describe pod).

Phase 6 — Kubelet + CRI Shim: Pods Actually Run

6.1 Objectives

The node agent that turns a bound Pod into running containers via CRI, runs probes, reports status, and is autonomous under control-plane outage (principle 6).

6.2 Detailed Implementation Steps

  • kubelet watches Pods with spec.nodeName==self; PodWorker per Pod uid serializes create/update/kill. (Burns et al. ACM Queue 2016; P6, ADR-09)
  • SyncPod: compute desired vs actual containers → RunPodSandbox (pause container, network ns) → CNI ADD (veth, IP) → image pull (ImageService) → CreateContainer+StartContainer per container, ordered with init containers first.
  • cri-shim: implement RuntimeService/ImageService over OCI runtime (#35) + image store (#166); sandbox holds the shared net/IPC ns; containers join it. (CRI protobuf spec; ADR-08)
  • Probes: liveness (restart on fail), readiness (gate endpoints), startup (delay liveness); exec/http/tcp handlers with periodSeconds/failureThreshold. (P5; I12)
  • Status: aggregate containerStatuses → Pod phase + conditions; write via /status subresource; set podIP from CNI result. (I9; P7)
  • Volumes: emptyDir, hostPath, configMap/secret projection (mount as files); CSI deferred (Phase 11, §11.10).
  • Restart policy: Always/OnFailure/Never with exponential crashloop backoff.

6.3 Deliverable

A scheduled nginx Pod runs, gets an IP, passes readiness, and serves traffic; orctl logs streams stdout; killing kubelet leaves the container running and it re-adopts on restart.

6.4 Acceptance Criteria

  • Pod start ≤ 5 s (image cached); readiness gates Pod Ready condition.
  • Liveness failure restarts the container, bumps restartCount, applies backoff.
  • kubelet restart re-adopts running sandboxes (no kill-and-recreate).
  • Control-plane down: running Pods keep running; kubelet retries status when it returns (principle 6).

6.5 Conformance Fixtures

kubelet/run-basic, kubelet/init-containers-order, kubelet/readiness-gates-ready, kubelet/liveness-restart, kubelet/crashloop-backoff, kubelet/readopt-on-restart, kubelet/cp-outage-autonomy.

6.6 Pitfalls

  • Kill-and-recreate on kubelet restart → unnecessary downtime. Reconcile against actual sandbox state (query CRI), adopt existing.
  • Probe storms → CPU/exec overhead. Jitter probes; cache results within period.
  • Leaked sandboxes/IPs on crash → resource exhaustion. Garbage-collect orphaned sandboxes + CNI DEL on reconcile.
  • Status write races → flapping conditions. Single status writer per Pod (the PodWorker).
  • Init-container ordering bug → app starts before deps. Strict sequential init, fail Pod if init fails per policy.

6.7 Performance Concerns

Image pull dominates start; cache + parallelize layer fetch (#166). Sandbox create is a syscall-heavy path; batch where possible. Probe exec spawns processes — bound concurrency. Status updates are writes to apiserver — coalesce, don't write on every probe tick.

6.8 Edge Cases

Image pull failure (ImagePullBackOff); container OOM (restart per policy, record reason); node reboot (re-adopt or recreate); disk pressure → eviction; CNI ADD failure (Pod stuck, retry); two Pods claim same hostPort (second fails); graceful termination (SIGTERM → grace → SIGKILL).

6.9 Failure Analysis

kubelet crash-loop ⇒ node effectively gone ⇒ node controller evicts its Pods after timeout ⇒ reschedule elsewhere. Detection: node Ready=False, kubelet heartbeat gap. Containment: per-node blast radius; control plane reschedules. Recovery: restart kubelet (crash-only re-adopt). Forensics: CRI state + kubelet log + container exit codes.

6.10 Operational Notes

Metrics: kubelet_pod_start_duration, kubelet_running_pods, kubelet_pleg_relist, probe_total{type,result}, container_restarts_total, image_pull_duration. Node heartbeat = Lease renew every 10 s. Runbook node-notready.md. orctl describe node shows conditions, capacity, allocatable.

Phase 7 — Controllers: ReplicaSet, Deployment, Node, Endpoints, GC

7.1 Objectives

The reconcilers that implement higher-level intent: maintain replica counts, roll out Deployments over ReplicaSets, detect dead nodes, map Services→Pod IPs, and garbage-collect orphans.

7.2 Detailed Implementation Steps

  • ReplicaSet: observe Pods matching selector owned by RS; create/delete to hit spec.replicas; set owner refs + blockOwnerDeletion; update status (replicas/readyReplicas, observedGeneration). (Burns et al. ACM Queue 2016; I7, P5)
  • Deployment: own ReplicaSets; on template change create new RS; RollingUpdate honoring maxSurge/maxUnavailable; scale old down / new up gradually; rollback on failure; record conditions (Progressing/Available); revision history. (I4; P7; ADR-12)
  • Node: consume kubelet Lease heartbeat → Ready/NotReady; on NotReady > evictionTimeout, mark node + evict (delete) its Pods so owners reschedule (I11). (Burrows "Chubby" OSDI 2006; I11, ADR-11)
  • Endpoints: for each Service, list ready Pods matching selector → write Endpoints subsets (I12 readiness gate).
  • GarbageCollector: build owner graph; delete objects whose owners are gone (foreground/background/orphan policies); honor finalizers (I6/I7). (I6, I7; P12)
  • Namespace: on delete, drive Terminating → delete contained objects → remove finalizer.

7.3 Deliverable

apply Deployment(replicas=3) → 3 Pods running; edit image → rolling update with no full outage; delete Deployment → cascading delete of RS + Pods; kill a node → its Pods reschedule.

7.4 Acceptance Criteria

  • RS converges replica count under Pod deletion (delete a Pod → recreated).
  • Rolling update maintains ≥ replicas−maxUnavailable ready throughout (availability invariant).
  • observedGeneration tracks spec generation (rollout "done" only when truly done, I4/principle 7).
  • Cascading delete leaves zero orphans (I7); node loss reschedules within evictionTimeout + schedule latency.

7.5 Conformance Fixtures

ctlr/rs-heals-deleted-pod, ctlr/deploy-rolling-no-outage, ctlr/deploy-rollback, ctlr/node-eviction, ctlr/endpoints-ready-only, ctlr/gc-cascade, ctlr/namespace-terminating.

7.6 Pitfalls

  • Edge-triggered replica math → miss a delete, run short forever. Level-trigger: count actual every reconcile.
  • Rollout reads stale status → declares done early. Gate on observedGeneration + readyReplicas, not on having issued the scale.
  • Owner-ref cycles → GC livelock. Detect cycles; break with policy.
  • Premature node eviction on transient heartbeat gap → mass reschedule storm. Require sustained NotReady + rate-limit evictions.
  • Endpoints include unready Pods → traffic to cold backends. Strict readiness gate (I12).

7.7 Performance Concerns

GC graph build is O(objects); cache the owner index, update incrementally. Rolling update issues many writes; batch scale steps. Node controller scans all nodes on a timer; keep O(nodes) and event-driven where possible. Endpoints rewrite on every Pod change — debounce.

7.8 Edge Cases

Selector overlap (two RS select same Pods — adoption rules by owner ref); maxUnavailable=0 + no surge headroom (rollout stalls — surfaced as condition); node flaps Ready/NotReady (hysteresis); deleting owner mid-rollout; Pod stuck Terminating (force-delete path); Service with no matching Pods (empty Endpoints).

7.9 Failure Analysis

A wedged deployment controller freezes all rollouts cluster-wide. Detection: reconcile_total{controller=deployment} flat + queue depth rising. Containment: per-controller queue; leader failover restarts it (crash-only). Recovery: bounce controller-manager; it relists and resumes (level-trigger). Forensics: Deployment conditions + RS revision history tell the rollout story.

7.10 Operational Notes

Metrics per controller: reconcile_total{controller,result}, reconcile_duration, workqueue_depth. Events on every scale/rollout step (operator-visible). orctl rollout status/undo deploy/x. Runbook rollout-stuck.md, node-eviction-storm.md.

Phase 8 — Service Dataplane: kube-proxy

8.1 Objectives

Make a Service VIP load-balance to ready backend Pod IPs via the kernel dataplane, with userspace/iptables/IPVS backends behind one interface, on every node.

8.2 Detailed Implementation Steps

  • Watch Services + Endpoints → desired VIP→backends map. (Burns et al. ACM Queue 2016; I12, ADR-13)
  • userspace backend: a local listener per Service; accept→pick backend (RR)→proxy. Slow but debuggable; the reference oracle.
  • iptables backend: per-Service KUBE-SERVICES chain → DNAT to a per-Service set of KUBE-SEP-<hash> chains with statistic probability for load spread; NodePort via PREROUTING. (ADR-13; I12)
  • IPVS backend: virtual server per VIP, real servers per backend; scheduler rr/wrr/lc; far fewer rules at scale. (ADR-13; P4)
  • Health: only program Ready endpoints (I12); remove on NotReady.
  • Idempotent sync: compute desired ruleset, diff against installed, apply minimal changes; full resync on a timer (level-trigger). (P5; ADR-13)

8.3 Deliverable

curl <ClusterIP>:port round-robins across ready backend Pods; scaling the Deployment changes the backend set within sync latency; NodePort reachable from outside.

8.4 Acceptance Criteria

  • Traffic only ever reaches Ready Pods (I12).
  • Backend set converges ≤ 2 s after Endpoints change.
  • IPVS handles 1k Services with far fewer kernel rules than iptables (rule-count assertion).
  • proxy restart re-derives rules from store (crash-only), no traffic black hole beyond sync window.

8.5 Conformance Fixtures

proxy/clusterip-roundrobin, proxy/nodeport, proxy/only-ready-endpoints, proxy/scale-updates-backends, proxy/ipvs-rulecount, proxy/resync-idempotent.

8.6 Pitfalls

  • Non-idempotent rule writes → duplicate/conflicting chains, packet drops. Diff-and-apply; never blind-append.
  • iptables rule explosion → multi-second sync, latency. Motivates IPVS at scale; measure proxy_sync_duration vs service count.
  • Stale conntrack after backend change → existing connections pinned to dead Pod. Flush conntrack entries for removed backends.
  • Programming unready endpoints → connection resets. Strict readiness (I12).

8.7 Performance Concerns

iptables sync is O(services × backends) and serialized by the kernel lock — batch with iptables-restore. IPVS uses a hash table (O(1) lookup) — preferred at scale. Conntrack table sizing under churn. NodePort adds a hop; document.

8.8 Edge Cases

Service with zero ready backends (reject connection / drop); session affinity (clientIP stickiness); overlapping NodePorts; VIP reuse after Service delete (clean conntrack); large fan-out (1000 backends) probability rounding in iptables.

8.9 Failure Analysis

A proxy bug blackholes a Service cluster-wide-per-node. Detection: synthetic probe to VIP, proxy_endpoints_ready vs actual, connection-reset rate. Containment: per-node; other nodes unaffected. Recovery: resync (idempotent) or restart proxy. Forensics: diff installed ruleset vs desired.

8.10 Operational Notes

Metrics: proxy_sync_duration, proxy_rules_total{backend}, proxy_endpoints_programmed, proxy_stale_conntrack_flushed. Runbook service-blackhole.md. Backend selectable per node via flag for A/B.

Phase 9 — Admission, Validation, Defaulting, Authz

9.1 Objectives

The in-tree admission chain (mutating→validating), resource quota, defaulting, and least-privilege authz (node-restriction + coarse RBAC) — the gate that keeps the store clean (I13) and the cluster secure.

9.2 Detailed Implementation Steps

  • Mutating plugins (ordered): defaulting (fill spec defaults), owner-ref injection, resource-request defaults from LimitRange, namespace-exists check. (I13; ADR-09; P2)
  • Validating plugins: schema validation, immutable-field check, ResourceQuota debit (atomic with create), Pod security basics (no privileged unless allowed). (I3; ADR-04; P5)
  • Authn: client-cert (CN=identity, O=groups) + static bearer tokens. (ADR-28; ADR-29)
  • Authz: node-restriction (a kubelet may only modify its own Node + Pods bound to it, I9/I11 enforcement); coarse RBAC = (subject, verb, resource, namespace) allow rules. (ADR-29; I9, I11; P14)
  • Webhook admission: PhaseDeferred("FINAL_BLUEPRINT §9.10").

9.3 Deliverable

Bad objects are rejected at the door with field-precise errors; quota over-commit blocked; a kubelet token cannot edit another node's Pods.

9.4 Acceptance Criteria

  • Invalid object → 422 with JSON path of the bad field.
  • Quota: creating beyond namespace quota → 403; debit is atomic (no over-commit under concurrency).
  • node-restriction: cross-node write → 403 (security test).
  • Defaulting deterministic (same input → same defaults).

9.5 Conformance Fixtures

admit/default-applied, admit/immutable-field-rejected, admit/quota-blocks-overcommit, authz/node-restriction-denied, authz/rbac-allow-deny, authn/cert-identity.

9.6 Pitfalls

  • Quota race → two creates both pass the check, both debit, over-commit. Make check+debit a single store Txn (CAS on quota object).
  • Order-dependent mutation → defaulting after validation. Lock order: mutate-all then validate-all.
  • Over-broad node token → node compromise = cluster compromise. node-restriction mandatory (principle 14).
  • Non-deterministic defaults → conversion/round-trip drift. Pure defaulting functions.

9.7 Performance Concerns

Admission is per-write CPU; keep plugins cheap and short-circuit on first validation failure. Quota Txn contention under burst create — shard quota by namespace. Cert verification cached per connection.

9.8 Edge Cases

Dry-run (run admission, skip write); quota exactly at limit; deleting frees quota (credit on delete); token with no rules (deny-all); cert expiry mid-watch; conflicting mutating plugins (define order, document).

9.9 Failure Analysis

A broken validating plugin lets malformed objects into the store → decode failures everywhere (I13 breach). Detection: decode_error_total post-write (should be zero). Containment: validation is the gate; add read-side decode guard as defense-in-depth. Recovery: quarantine bad objects, fix plugin, re-validate. Forensics: admission audit log (who wrote what, allowed/denied).

9.10 Operational Notes

Metrics: admission_duration{plugin}, admission_denied_total{plugin,reason}, authz_denied_total{reason}, quota_usage{namespace,resource}. Audit log every admit decision. Runbook admission-rejecting-everything.md (usually a bad plugin or expired cert).

Phase 10 — Observability, Conformance, End-to-End

10.1 Objectives

Wire metrics/traces/logs/events across all components; ship the conformance suite; run a full e2e (apply → schedule → run → serve → scale → rollout → delete) green.

10.2 Detailed Implementation Steps

  • observability: Prometheus /metrics per component; OTel spans threaded request→admission→store and reconcile→action; structured slog with object refs + trace IDs; Event API (orctl get events). (ADR-15, ADR-16; P13)
  • Conformance runner: load fixtures, drive apiserver, assert outcomes, emit conformance.report.json (Pass/Fail/Deferred per bucket). (ADR-17; ADR-25)
  • e2e harness: spin all-in-one + 2 workers (compose), run the golden scenario, assert convergence + serving. (ADR-21; P6)
  • Dashboards: control-plane (request rate/latency/errors, store revision/latency, watch health), scheduler (pending/latency), controllers (queue depth/reconcile), node (Pods, probes, restarts), proxy (sync, endpoints).
  • Chaos hooks: kill apiserver/store/scheduler/kubelet mid-scenario; assert recovery + data-plane autonomy. (P6; P12; Burns et al. ACM Queue 2016)

10.3 Deliverable

make conformance + make e2e both green; dashboards render against the dev cluster; chaos run proves crash-only recovery and data-plane autonomy.

10.4 Acceptance Criteria

  • Conformance buckets (api, watch, scheduler, controllers, kubelet, proxy, admission) all Pass.
  • e2e golden scenario converges within latency targets (§4).
  • Chaos: kill each component → cluster heals; running Pods never stop when only the control plane is killed (principle 6).
  • SLOs defined + measured (availability, reconcile latency, schedule latency).

10.5 Conformance Fixtures

e2e/golden-deploy-svc-scale-rollout, chaos/kill-apiserver, chaos/kill-store-recover, chaos/kill-scheduler, chaos/kill-kubelet-autonomy, slo/latency-budgets.

10.6 Pitfalls

  • High-cardinality metrics (per-pod labels) → Prometheus OOM. Bound label cardinality; aggregate per-node/per-controller.
  • Trace gaps across async hops → can't follow a request into a reconcile. Propagate trace context through the workqueue item.
  • Flaky e2e from timing → false failures. Assert on convergence (poll-until) not fixed sleeps.

10.7 Performance Concerns

Metrics scrape cost; cap series. Tracing sampling (1–10%) to bound overhead. Event volume can flood store — rate-limit + dedupe events (aggregate "x happened N times").

10.8 Edge Cases

Clock skew during chaos (leases); partial scrape; e2e on slow CI (generous timeouts but assert ordering); event storm during mass reschedule.

10.9 Failure Analysis

Without observability, every later incident is blind. This phase IS the failure-analysis capability. Validate that each invariant (§7) has a corresponding metric + a debug invariant probe.

10.10 Operational Notes

This phase defines the operational contract for Operational Readiness (see that section). Every metric named here is referenced by the runbooks and SLOs below. Conformance report is the gate for any "Done" claim.

Phase 11 — Workload Controllers: StatefulSet, DaemonSet, Job/CronJob

11.1 Objectives

Extend the controller set beyond stateless Deployments to ordered/stable-identity (StatefulSet), per-node (DaemonSet), and run-to-completion (Job/CronJob) workloads — the remaining first-class workload kinds.

11.2 Detailed Implementation Steps

  • StatefulSet: stable network identity (<name>-<ordinal>) + stable storage (PVC-per-ordinal, CSI deferred to §11.10); ordered create/scale-up (0,1,2...), reverse delete; OrderedReady vs Parallel pod-management policy; updateStrategy RollingUpdate with partition. (I5; ADR-12; P7)
  • DaemonSet: one Pod per eligible node (respecting taints/affinity); reconcile on node add/remove; rolling update node-by-node with maxUnavailable. (Verma et al. Borg EuroSys 2015; P5, ADR-12)
  • Job: run N completions with parallelism P; track succeeded/failed; backoffLimit; activeDeadlineSeconds; completion modes (NonIndexed/Indexed). (P5; I4; ADR-09)
  • CronJob: schedule (cron expr) → create Jobs; concurrencyPolicy (Allow/Forbid/Replace); startingDeadlineSeconds; missed-schedule handling. (I15; P7; ADR-30)
  • All: owner refs to the controller, observedGeneration, status conditions.

11.3 Deliverable

apply StatefulSet(replicas=3) yields web-0,web-1,web-2 in order; DaemonSet lands one Pod per node and follows node additions; Job runs to completion and stops; CronJob fires on schedule.

11.4 Acceptance Criteria

  • StatefulSet scaling 3→5 replicas creates web-3 only after web-2 is Ready, then web-4 after web-3 is Ready (strict order); identity (name + PVC) stable across a reschedule (fixture sts/stable-identity-reschedule).
  • DaemonSet count == eligible node count (e.g. 10/10 nodes) within the §4 reconcile latency p99 ≤ 2 s budget after a node join (fixture ds/follows-node-add).
  • Job with completions=5, parallelism=2 reaches Complete at exactly 5 successes; a 6th consecutive failure trips backoffLimit=5 and marks the Job Failed (fixture job/backofflimit).
  • CronJob with concurrencyPolicy=Forbid skips a new run if the prior Job from the last schedule tick is still active; concurrencyPolicy=Replace kills it within one grace period (fixture cron/concurrency-forbid).

11.5 Conformance Fixtures

sts/ordered-create, sts/stable-identity-reschedule, sts/rolling-partition, ds/one-per-node, ds/follows-node-add, job/completions-parallelism, job/backofflimit, cron/schedule-fires, cron/concurrency-forbid.

11.6 Pitfalls

  • StatefulSet ordering races → web-2 created before web-1 ready. Gate each ordinal on predecessor Ready (OrderedReady).
  • DaemonSet ignores taints → Pods unschedulable on tainted nodes. Apply node eligibility = scheduler predicates.
  • Job double-counting on controller restart → over/under completions. Count actual Pod terminal states each reconcile (level-trigger), not a running tally.
  • CronJob missed-schedule storm → many Jobs after downtime. Cap catch-up via startingDeadlineSeconds.

11.7 Performance Concerns

StatefulSet ordered reconcile is inherently serial — bound by per-Pod readiness latency. DaemonSet reconcile is O(nodes) on node churn — index by node. Job/CronJob status writes scale with completions — batch.

11.8 Edge Cases

StatefulSet PVC retention on scale-down (retain vs delete policy); DaemonSet on a node being drained; Job pod deleted externally (recreate vs count as failure per policy); CronJob clock skew vs schedule; Indexed Job gaps.

11.9 Failure Analysis

A StatefulSet stuck mid-ordinal blocks the whole set. Detection: sts_ready_replicas < desired + reconcile flat. Containment: per-StatefulSet; others unaffected. Recovery: fix the blocking Pod (often storage/probe); the set resumes ordering. Forensics: ordinal Ready timeline.

11.10 Operational Notes

Metrics: sts_replicas{ready}, ds_desired_vs_scheduled, job_active/succeeded/failed, cronjob_last_schedule_time. Events on each ordinal/Job creation. Runbooks: statefulset-stuck.md, cronjob-overrun.md.

Phase 12 — Raft-Replicated Store (HA Control Plane)

12.1 Objectives

Replace the single-node store with a Raft group (3 or 5 members) for control-plane availability and durability, preserving the exact MVCC + watch semantics §1 defined. Fulfils PhaseDeferred("FINAL_BLUEPRINT §12.10").

12.2 Detailed Implementation Steps

  • store/raft: leader election, log replication, commit on quorum; the replicated log entries are store Txns. (Ongaro & Ousterhout Raft 2014; ADR-05)
  • Linearizable reads via ReadIndex (confirm leadership before serving) or lease-read optimization; followers serve stale-OK reads if requested. (Ongaro & Ousterhout Raft 2014; I1, ADR-05)
  • Snapshotting: periodic state snapshot + log truncation; install-snapshot to lagging/new members. (ADR-05; I14)
  • Membership change: single-server add/remove (joint consensus or one-at-a-time) for safe reconfiguration. (Ongaro & Ousterhout Raft 2014; ADR-05)
  • apiserver → store client routes writes to leader (redirect on follower); watch served from any member's local state at its applied index.
  • Revision assignment now happens at Raft apply time (still globally monotonic, I1) — the committed log order defines revisions.

12.3 Deliverable

A 3-node control plane tolerating one node loss with no write interruption beyond election; reads linearizable; new member catches up via snapshot.

12.4 Acceptance Criteria

  • Kill the leader → new leader ≤ election timeout; no committed write lost; revisions stay monotonic.
  • Linearizable read never returns stale committed data (ReadIndex test).
  • Add a member → catches up via snapshot + log; quorum math correct (2/3, 3/5).
  • Watch continuity across leader change (clients resume from RV, I8).

12.5 Conformance Fixtures

raft/leader-failover-no-loss, raft/readindex-linearizable, raft/snapshot-catchup, raft/membership-add-remove, raft/watch-across-failover, raft/quorum-loss-readonly.

12.6 Pitfalls

  • Serving reads from a deposed leader → stale reads (split-brain reads). ReadIndex/lease confirm leadership.
  • Revision divergence if assigned before commit. Assign at apply, after quorum commit.
  • Snapshot without log-truncation guard → unbounded log. Truncate only below the snapshot index retained by all needed members.
  • Membership change under partition → split quorum. One-at-a-time change keeps overlapping majorities.

12.7 Performance Concerns

Every write now costs a quorum round-trip (RTT-bound, §4 assumes ≤ 5 ms). Batch + pipeline log entries; group-commit at the leader. Reads via lease avoid round-trips. Snapshot transfer is bandwidth-heavy — throttle. Write throughput ceiling drops vs single-node (consensus tax).

12.8 Edge Cases

Quorum loss (2 of 3 down) → read-only/unavailable for writes (CP choice); network partition isolating leader (it steps down on failed heartbeats); slow follower (snapshot rather than replay); clock skew (Raft uses logical terms, not clocks — safe); disk-full on a member.

12.9 Failure Analysis

Loss of quorum ⇒ no writes (by design, CP). Detection: raft_quorum_healthy=0, leader=none. Containment: data-plane autonomy holds (principle 6) — running Pods unaffected. Recovery: restore a member to regain quorum; never force-elect with stale data. Forensics: Raft log + term history.

12.10 Operational Notes

Metrics: raft_term, raft_commit_index, raft_leader, raft_proposals_pending, raft_replication_lag, raft_snapshot_duration. Runbooks: quorum-lost.md, add-control-plane-node.md, disk-full-member.md. Backup = Raft snapshot; restore rebuilds a member.

Phase 13 — Scheduler Scaling: Priority, Preemption, Sampling

13.1 Objectives

Scale and sharpen scheduling: Pod priority classes, preemption of lower-priority Pods to admit higher, and candidate-node sampling to bound latency at large node counts. Builds the scheduler-scaling work adjacent to the GPU/device-plugin deferral (PhaseDeferred("FINAL_BLUEPRINT §6.10")).

13.2 Detailed Implementation Steps

  • PriorityClass objects; Pods carry priority; pending high-priority Pods may preempt. (Verma et al. Borg EuroSys 2015; ADR-12)
  • Preemption: when no node fits, find the node where evicting the fewest/lowest-priority Pods makes room; set victims' deletionTimestamp with grace; respect PodDisruptionBudget (best-effort). (ADR-12; I5; Verma et al. Borg EuroSys 2015)
  • Node sampling: at large N, score only a sampled feasible subset (e.g. percentage with a floor) to cap per-cycle cost; preserves quality statistically. (Schwarzkopf et al. Omega 2013; ADR-12)
  • Multiple scheduler profiles (different plugin weights) selectable per Pod via schedulerName. (ADR-12; P4)
  • Backoff queue improvements: move-to-active on relevant cluster events (node added, pod deleted) rather than blind retry.

13.3 Deliverable

A high-priority Pod preempts a low-priority Pod when the cluster is full; scheduling latency stays bounded at 5k nodes via sampling; profiles route Pods to different scoring policies.

13.4 Acceptance Criteria

  • Preemption admits the high-priority Pod and evicts minimal victims; never preempts equal-or-higher priority.
  • Sampling keeps bind p99 ≤ 100 ms at 5k nodes (vs O(N) blowup).
  • Profiles produce different placements per weights (differential test).
  • No starvation: a repeatedly-preempted victim eventually reschedules or reports a clear reason.

13.5 Conformance Fixtures

sched/preempt-minimal-victims, sched/no-preempt-equal-priority, sched/sampling-latency-bound, sched/profiles-differ, sched/preemption-respects-pdb, sched/no-starvation.

13.6 Pitfalls

  • Preemption thrash → A preempts B, B reschedules and preempts A. Priority ordering + backoff prevent oscillation.
  • Sampling misses the only fit → false unschedulable. Floor the sample size; fall back to full scan when sampled set is infeasible.
  • Ignoring PDB → preemption violates availability guarantees. Honor PDB best-effort, surface when impossible.

13.7 Performance Concerns

Preemption search is O(nodes × victims) — cap candidates and victim-set size. Sampling trades optimality for latency — tune sample percentage vs placement quality. Profiles multiply plugin work — share filter results across profiles where possible.

13.8 Edge Cases

All nodes equally full of equal-priority Pods (no preemption possible → Pending); victim with a finalizer (eviction blocked → pick another); preemption racing a concurrent bind (CAS resolves); priority inversion via affinity.

13.9 Failure Analysis

A preemption bug that evicts the wrong (higher-priority) Pods degrades critical workloads. Detection: preemption_victims_total{priority} (should be lower-priority only) + audit. Containment: priority check is the hard gate. Recovery: disable preemption (flag), fix, re-enable. Forensics: per-decision preemption trace.

13.10 Operational Notes

Metrics: scheduler_preemption_attempts_total, scheduler_preemption_victims, scheduler_sampled_nodes, scheduler_profile_used{name}. Events naming victims + reason. Runbook preemption-thrash.md.

Compatibility & Versioning

  • Wire (API): served v1 is stable; additive fields only within a major; removal requires a new version + deprecation window (2 minors). JSON + protobuf both supported.
  • Storage: storage version pinned (ADR-27); on bump, a one-time migration re-encodes objects; never read-break old data.
  • Schema evolution: new optional fields default safely; immutable fields enforced; conversion functions are pure + round-trippable.
  • API stability: verbs/paths stable; orctl pins a min server version; skew policy: client ≤ server by one minor.
  • Rolling upgrade: mixed-version control plane tolerated within one minor (conversion bridges); kubelet ≤ control-plane version.
  • Deprecation policy: announce → warn (response header Warning) → remove after 2 minors. SemVer: breaking=major, additive=minor, fix=patch.

Scalability Analysis

  • Bottleneck #1 store: single-writer revision assignment caps write throughput; mitigations: batch commit, shard by resource (later), Raft adds read replicas but not write throughput. Ceiling ~ a few k writes/s.
  • Bottleneck #2 watch fan-out: memory + CPU ∝ watchers × event rate; mitigations: shared informers, BOOKMARK, metadata-only, watch cache in apiserver.
  • Bottleneck #3 scheduler: single queue O(nodes) filter; mitigations: node sampling (score a feasible subset), multiple scheduler profiles, eventual shared-state (Phase 13).
  • Bottleneck #4 proxy: iptables O(services×backends) sync; mitigation: IPVS hash table → effectively flat.
  • Horizontal scaling: apiserver (stateless, scale reads); workers (linear with nodes); controllers (leader-elected, one active — vertical).
  • Vertical scaling: store RAM (watch cache + index); apiserver CPU (admission/decode).
  • Storage growth: MVCC history + events; compaction + event TTL bound it.
  • Coordination overhead: leader election + lease renew is O(1); Raft (Phase 12) adds quorum round-trips per write.
  • Metadata scaling: object count drives cache memory across all controllers — the practical cluster-size limiter.

Mental Models & First Principles

  1. MM1 — Desired state minus observed state equals the controller's work queue. Predicts: a reconciler degrades gracefully when the diff is computed against fresh state; the queue is bounded by divergent-object count, not event volume. Without it: a counter-based reconciler under-counts after a crash and runs permanently short of replicas, with no self-healing trigger. Applied: §6 (P5, Idempotent reconciliation), Phase 7 (ReplicaSet replica-count logic), Phase 11 (Job completion accounting).

  2. MM2 — Level-triggered systems trade per-event efficiency for crash-recovery correctness. Predicts: any missed event self-heals at the next resync; controllers always act on current state, so the event payload is irrelevant to correctness. Without it: one dropped "Pod deleted" event means the replication slot is never refilled — silently and permanently — until a human notices. Applied: §6 (P2), Phase 4 (DeltaFIFO enqueue-key discipline: keys, not objects), Phase 7 (RS reconcile counts actual Pods, not deltas).

  3. MM3 — MVCC watch: a revision is a global Lamport clock; a watcher is a log consumer starting from a known offset. Predicts: the safe compaction floor is min(active-watcher start revisions); compacting below it produces a 410 for that client. Without it: you compact past a live watcher, triggering a cascade of 410s that forces every controller to relist the entire store simultaneously — a thundering herd under high churn. Applied: §7 (I1, I8, I14), Phase 1 (compactor guard against min-watcher RV), Phase 3 (BOOKMARK keeps client RV ahead of the compaction front).

  4. MM4 — Optimistic concurrency: correct retry requires re-reading state, not replaying the original intent. Predicts: two conflicting writers converge because the loser re-reads the winner's committed outcome and recomputes the diff against it. Without it: a "retry the same write" loop re-applies an already-obsolete diff; two controllers oscillate writing contradictory values indefinitely. Applied: §6 (P4, I3), Phase 2 (registry CAS on resourceVersion), Phase 5 (bind 409 → re-enqueue + fresh cache snapshot).

  5. MM5 — Control-plane/data-plane separation: the fast path must never block on the consistent brain. Predicts: kubelet and kube-proxy continue operating during any control-plane outage; only new mutations stall, never existing workloads. Without it: a kubelet that calls the apiserver per probe, or a proxy that consults the store per packet, kills live traffic on any control-plane partition. Applied: §6 (P6), Phase 6 (kubelet autonomy test: CP down, containers keep running), Phase 8 (proxy level-trigger resync on timer, not per-packet).

  6. MM6 — Leader election via a leased object is a distributed mutex with a TTL fence. Predicts: worst-case split-brain window is exactly one lease duration; the non-renewing leader's Lease expires and it must stop acting. Without it: two controller-managers both reconcile Deployments — spawning duplicate Pods and issuing contradictory scale writes indefinitely. Applied: §7 (I10, ADR-11), Phase 3 (Lease CAS renew with monotonic clock, ADR-30), Phase 7 (leader-elected controller-manager).

  7. MM7 — Scheduling is a constraint-satisfaction problem: filter (feasibility) then score (preference), never mixed. Predicts: a new placement constraint requires only a new FilterPlugin; scoring before filtering wastes cycles on infeasible nodes and inflates latency. Without it: a monolithic function mixing resource-fit and soft-affinity in one O(nodes²) loop blows the 100 ms p99 budget (§4) at 1k nodes. Applied: §4 (≥ 100 Pods/s, ≤ 100 ms p99), Phase 5 (filter → score → bind plugin framework), Phase 13 (node sampling caps worst-case filter cost at 5k nodes).

  8. MM8 — Raft: revisions are assigned at FSM apply time, not at propose time; the committed log order is the only valid clock. Predicts: a leader replaced between propose and apply would assign a lower revision to the same log slot if assignment happens at propose, breaking monotonicity. Without it: watch clients relying on I1 (globally monotonic RV) observe revision regressions and incorrectly infer data loss or silently skip events. Applied: §7 (I1), Phase 12 (revision assigned only at FSM apply after quorum commit), Phase 12 (ReadIndex confirms apply index before serving linearizable reads).

  9. MM9 — Owner refs + finalizers form a distributed reference-counting protocol; deletion is a multi-step rendezvous. Predicts: a Deployment→RS→Pod cascade takes at minimum three reconcile cycles (one per ownership level) and is safe across any crash at any intermediate point. Without it: instant hard deletes leak every external resource (LBs, PVCs, DNS) whenever the finalizer-owning controller crashes between delete and cleanup. Applied: §6 (P8, I6, I7), Phase 2 (soft-delete: set deletionTimestamp first), Phase 7 (GC owner-graph foreground deletion), Phase 11 (StatefulSet PVC retain policy on scale-down).

  10. MM10 — Workqueue discipline (dedupe + rate-limit + exponential backoff) is the apiserver's natural backpressure valve. Predicts: 10k Pod deletes coalesce to one reconcile per RS key per window; a permanently failing key backs off without starving healthy keys. Without it: each delete triggers an immediate reconcile; a crashlooping Pod causes an unbounded retry storm that OOMs the controller and floods the store, exhausting the 65k FD budget (§4). Applied: §6 (P10, ADR-10), Phase 4 (token-bucket + per-item backoff implementation), Phase 9 (quota burst serialization).

Kubernetes — made the watch cache and informer pattern the canonical control-plane primitives; its single most important architectural decision relative to Borg is externalizing all state into etcd, making the apiserver a stateless HTTP facade that can be horizontally replicated. This separation means admission plugins, scheduler, and controllers all work against the same store truth via CAS without any in-process coupling. Wins when: extensibility via CRDs and admission webhooks is required, the cluster must run third-party operators written by teams outside the platform team, or when the ecosystem of tooling (Helm, ArgoCD, Crossplane) is a hard requirement.

Google Borg — retained all scheduling state in-memory inside Borgmaster, which is the direct reason a single Borgmaster can schedule at rates an etcd-backed system cannot match: there is no store serialization tax per bind. The tradeoff is that Borgmaster recovery from a restart requires a full rescan of the cluster, taking minutes at Google scale. Wins when: the scheduling throughput ceiling (not availability or extensibility) is the binding constraint, the cell is operated as a closed administrative unit with no need for a public API consumed by third parties, and the organization can tolerate scheduled Borgmaster maintenance windows.

HashiCorp Nomad — its defining decision is shipping Raft replication, scheduling, API serving, and the job state machine into a single statically-linked binary with zero external runtime dependencies beyond the Go standard library. This collapses the operational surface to one systemd unit per server node. The cost is that every concern (consensus protocol, scheduler, API) shares a failure domain: a scheduler bug can corrupt the Raft FSM. Wins when: operational simplicity is the primary constraint (small teams, no dedicated platform engineers), the workload is polyglot (raw binaries, JVM, VMs via the QEMU driver, and containers all scheduled by the same system), or when multi-region federation with a single API endpoint is needed without a separate federation layer.

Apache Mesos + Marathon — the two-level offer model is Mesos's single differentiating decision: the Mesos master allocates resources using Dominant Resource Fairness and presents them as offers to framework schedulers, which then accept or decline. This gives each framework (Spark, Marathon, Chronos) full control over placement logic without modifying the core. The fundamental cost is that the offer-accept round trip adds latency and creates resource fragmentation when frameworks are picky. Wins when: the cluster runs heterogeneous workloads with fundamentally incompatible scheduling semantics that cannot be expressed as plugin weight differences, or when DRF cross-framework fairness is a hard regulatory or SLA requirement.

Docker Swarm mode — embeds the entire orchestration stack (manager election via SwarmKit Raft, service scheduling, load balancer VIP programming) directly into the Docker daemon process, requiring no additional infrastructure beyond Docker itself. The absence of a watch API and informer pattern means third-party controllers cannot be built against it. Wins when: the cluster is small (< 50 nodes), all workloads are Docker Swarm services, the team's existing investment is in Docker Compose files (which translate directly to Swarm), and zero additional infrastructure processes are a hard constraint.

Back-of-Envelope Capacity Model

All items derive from §4 System Constraints values; every figure traces to a named §4 row or an explicit stated assumption. Items are ordered from storage → throughput → latency → cost to match the design sequence.

  1. Object store size at max objects. Starting from §4: ≤ 10k objects, average object ~3 KB (Pod spec + status). Raw data: 10k × 3 KB = 30 MB. With MVCC history (§4: ≤ 3× amplification): 30 MB × 3 = 90 MB. WAL overhead (≈ 1.5× live data during burst): ~135 MB peak store on disk. Design consequence: a 1 GB store RAM budget (§4) is dominated by the watch index and page cache, not raw object bytes; the real pressure is the in-memory watcher registry.

  2. Watch event throughput at 5k Pods × churn rate. Assume 1% of Pods churning per minute in steady state (Phase 0 target cluster): 5k × 0.01 / 60 ≈ 0.83 Pod events/s. Each event ≈ 3 KB JSON. Fan-out: ≤ 65k open watch connections (§4 FD budget); at 100 active watchers per resource: 0.83 events/s × 3 KB × 100 = 249 KB/s outbound watch traffic. Design consequence: per-watcher buffered channel sizing must tolerate 10× bursts (mass reschedule: 5k events in seconds) without stalling the store writer; each buffer = 256 entries at 3 KB ≈ 768 KB per watcher; 100 watchers ≈ 75 MB in-flight — within the 2 GB apiserver RAM budget (§4).

  3. Scheduler throughput ceiling. §4 target: ≥ 100 Pods/s bind. Filter phase: 50-node cluster (Phase 0 ≤ 50 nodes) × 6 filter plugins = 300 predicate evaluations/cycle. At 1 µs/predicate: 0.3 ms filter time. Score: 50 nodes × 4 score plugins = 200 score calls at 2 µs each = 0.4 ms. Store bind write p99 ≤ 200 ms (§4). Cycle time dominated by bind: 200 ms → theoretical max 5 binds/s per serial goroutine. To hit 100 binds/s: parallelize bind goroutines or pipeline (optimistic reserve + async bind). Design consequence: ADR-12 single-queue works for Phase 0 (≤ 50 nodes, burst bind not the bottleneck); Phase 13 node-sampling is essential only past 500 nodes.

  4. apiserver FD budget. §4: ≤ 65,536 FDs. One FD per watch connection + one per gRPC CRI connection. At 50 nodes with 4 controllers + scheduler each opening 8 informers: 50 × (4+1) × 8 = 2k watch FDs. Leaves 63k+ for user clients. Design consequence: a 50-node Phase 0 cluster is well within budget; the 65k ceiling becomes binding at ~8k nodes with one watch per controller per resource — the shared-informer pattern (Phase 4) is the mitigation.

  5. Store write p99 budget. §4: apiserver write p99 ≤ 200 ms = admission + store fsync. Admission target ≤ 10 ms (in-tree plugins, no webhook). Remaining budget for store: 190 ms. §4 store write p99 target ≤ 5 ms (M1). Group-commit batches: at 100 concurrent writes, one fsync amortized across 100 = 5 ms / 100 = 50 µs per write if perfectly batched, or full 5 ms if serialized. Design consequence: group-fsync every N ms or M writes (Phase 1) is not optional at 100 concurrent writers; without it, write p99 blows the 200 ms apiserver budget.

  6. Reconcile staleness budget. §4: reconcile latency p99 ≤ 2 s desired→action. Components: watch delivery lag p99 ≤ 1 s (§4, M5) + workqueue dequeue (≤ 50 ms at low depth) + reconcile compute (≤ 10 ms for RS diff) + apiserver write p99 ≤ 200 ms = ≤ 1.26 s nominal. 2 s target leaves 740 ms margin for queue backlog under burst. Design consequence: the watch lag budget (1 s, M5) is the dominant term; BOOKMARK intervals must be ≤ 900 ms to keep clients from drifting to stale compaction-edge revisions.

  7. Node heartbeat failure detection window. §4: node heartbeat every 10 s lease renew; NotReady at 40 s. Worst case: heartbeat sent at T=0, next due at T=10, missed; controller sees NotReady at T=40. Clock skew §4 ≤ 500 ms. Effective detection window: 40 s + 500 ms skew = 40.5 s. Pod eviction starts after NotReady + evictionTimeout (default 5 min in Kubernetes; set by operator here). Design consequence: the 40 s NotReady threshold must be tuned against NTP drift; at 500 ms skew (§4), a lease duration of 40 s gives only 80× skew headroom — adequate but not generous.

  8. RAM ceiling for informer caches. Assume 5k Pods at 3 KB each = 15 MB per full-Pod informer. Controller-manager runs RS/Deploy/Node/Endpoints/GC/Namespace controllers: 6 controllers × various resource types, ~10 informers total. At 10k objects average per informer: 10 × 10k × 3 KB = 300 MB. Plus workqueue items (≤ 64 B each, 10k deep): 640 KB negligible. Design consequence: 1 GB controller-manager RAM budget requires metadata-only informers for resources where controllers only need labels/generation (e.g. the GC controller reading all object metadata), cutting per-informer cost by ~10×.

  9. iptables rule count at service ceiling. Phase 0: ≤ 50 nodes, but no explicit service count cap. Assume 500 Services × 10 backends = 5k KUBE-SEP chains. iptables-restore at 5k rules: ~100 ms sync time (empirically observed in kube-proxy benchmarks at this scale, consistent with §4 M10 ≤ 2 s). At 5k Services × 10 backends = 50k rules: sync time ~1–2 s, approaching the M10 budget. Design consequence: ADR-13 IPVS backend must activate before 500 Services to keep M10 within budget; the iptables backend is the correct default only for Phase 0 scale.

  10. Raft write latency at Phase 12 cluster. §4: network RTT ≤ 5 ms intra-cluster. Raft write = leader → follower append → follower fsync → ack → leader commit. Minimum: 1 RTT (5 ms) + 2 fsyncs (5 ms each, M1) = 15 ms. Store write budget was 190 ms (item 5 above); Raft adds 10 ms overhead = 25 ms total store latency, still within the 190 ms budget. At quorum of 3 (need 2/3 acks): single slow follower does not block commit (the other follower acks). Design consequence: §4 write p99 ≤ 200 ms holds under Raft at LAN RTT; the budget erodes if network RTT exceeds 30 ms (e.g. cross-AZ), motivating a single-AZ control plane for Phase 12.

  11. Startup warm-up cost vs serving deadline. §4: control-plane startup ≤ 10 s to serving. Components: store WAL replay + index rebuild (proportional to db size; at 90 MB on-disk, ~500 MB/s sequential read = 0.18 s), watch-cache warm (one LIST per resource type; 10 resource types × 10k objects × 3 KB = 300 MB at 1 Gbit LAN = 2.4 s), admission plugin init (< 10 ms). Total: ~2.6 s nominal. Design consequence: WAL replay dominates only if the WAL is unbounded; periodic checkpointing (Phase 1) caps WAL scan to the last checkpoint interval; at 10 s startup budget (§4), a checkpoint every 60 s limiting WAL to ~6 s of writes ≈ 6k commits at 1k/s keeps replay well under 1 s.

  12. Storage amplification ceiling at MVCC history depth. §4: ≤ 3× storage amplification pre-compaction. At 10k objects × 3 KB base = 30 MB. If compaction runs every C revisions and average write-rate is W objects/s, history depth = C / compaction_period × W. To stay under 3×: MVCC history ≤ 2 × 30 MB = 60 MB live delta. At W = 100 writes/s (all-object churn) and a compaction period of 60 s: 60 s × 100 writes × 3 KB avg = 18 MB delta — well under the 60 MB ceiling. If W = 500/s (burst load): 500 × 60 × 3 KB = 90 MB → 3× breached. Design consequence: compaction period must adapt to write rate; a fixed 60 s interval is safe at Phase 0 scale (§4 ≤ 50 nodes, low churn) but requires a write-rate feedback loop for Phase 12 scale.

  • Optimistic retry is efficient only when contention is low; contention is low only when schedulers target distinct resource domains.   • Multiple schedulers need a starvation-prevention mechanism for the bind slot: when two schedulers score the same node as best for different Pods simultaneously, the loser must re-search the entire feasible set (not just retry one node), reintroducing distributed coordination analogous to ADR-12 but without the simplicity of a single queue.

Domain Deep Dive — The Reconciliation Pipeline End to End

The whole system is one pattern repeated: watch → cache → enqueue → reconcile → write (CAS) → observe. Understanding this loop in full is understanding the orchestrator.

D.1 The pipeline, stage by stage

store.Watch(rev) ─▶ apiserver watch endpoint ─▶ informer (List+Watch) ─▶ DeltaFIFO
   ▲                                                                          │
   │ CAS write (RV)                                                           ▼ OnAdd/Update/Delete
apiserver registry ◀── reconcile(key) ◀── workqueue (dedupe+backoff) ◀── enqueue key
  1. List+Watch bootstrap. Informer does an initial List at revision R0, populating its indexed cache; then Watch(R0) for the live tail. HasSynced() flips true after the initial list — controllers must wait for it or they reconcile against an empty world and delete everything (a classic, catastrophic bug).
  2. DeltaFIFO coalescing. Rapid changes to one object collapse to its latest state per key, but a delete is preserved with the object's last-known state (so the handler can clean up). This is why level-triggered reconcile never needs the event payload — only the key.
  3. Enqueue keys, not objects. Handlers enqueue namespace/name, never the object. By the time reconcile(key) runs, it re-reads the current object from the lister. This is the mechanical heart of level-triggering: you always act on now, never on the stale event that woke you.
  4. Workqueue discipline. Dedupe (one key in flight at a time), rate-limit (token bucket), per-item exponential backoff on error, Forget on success. A key that keeps erroring backs off but never blocks other keys.
  5. Reconcile = pure function of observed state. Read desired (spec) + actual (owned objects via lister) → compute diff → issue minimal idempotent writes. Return Result{Requeue, RequeueAfter} to ask for another pass.
  6. CAS write closes the loop. Writes carry the object's resourceVersion; a concurrent change makes the write lose (409) and the controller re-enqueues. No locks, no coordination — the store's single-writer + RV is the only synchronization primitive.

D.2 Worked trace: deleting a Pod under a Deployment

t0  user: orctl delete pod web-xyz   (web-xyz owned by RS web-1, owned by Deploy web)
t1  apiserver: set deletionTimestamp; kubelet on node N sees it via its Pod watch
t2  kubelet: SIGTERM container, grace period, SIGKILL, CNI DEL, remove finalizer
t3  apiserver: finalizers empty → physically delete → store emits DELETE @ rev R
t4  RS informer: DeltaFIFO delivers Delete(web-xyz) → enqueue key "ns/web-1"
t5  RS reconcile("ns/web-1"): lister shows 2 pods, spec.replicas=3 → diff=+1
t6  RS: create pod web-abc (ownerRef=web-1) via apiserver  [idempotent: keyed by count, not by "I saw a delete"]
t7  scheduler: web-abc has nodeName="" → filter→score→bind nodeName=M (CAS)
t8  kubelet on M: watch shows web-abc bound → RunPodSandbox→pull→start→readiness
t9  endpoints-ctlr: web-abc Ready → add its IP to Service Endpoints (I12)
t10 RS status: readyReplicas back to 3, observedGeneration unchanged (spec didn't change)

Note what is absent: no component told another "I deleted a Pod, please make a new one." Each loop independently observed the world and converged. Kill any component between t4 and t9 and, on restart, it relists and resumes exactly here — that is crash-only + level-triggered working together.

D.3 Why optimistic concurrency, not locks

Two controllers (say RS controller and a user orctl scale) may write the same RS concurrently. With locks you'd need a global lock order across all object types to avoid deadlock — impossible as the type set grows. With CAS: both read RV=v, both compute, both attempt write@v; the store commits one (now RV=v+1), the other gets 409, re-reads RV=v+1, recomputes, retries. The diff is recomputed against fresh state, so the retry is correct, not just safe. Contention shows up as update_conflict_total — a healthy amount is normal; a flat zero means CAS isn't engaged (a bug); a spike means hot-object contention (shard or debounce).

D.4 The three clocks of progress

  • resourceVersion — storage time; for watch resume + CAS only; opaque to clients.
  • generation — spec-change counter; bumped only when desired state changes.
  • observedGeneration — last generation a controller fully reconciled; the only honest "are we there yet" signal. A rollout is done iff observedGeneration == generation && readyReplicas == replicas. Reading status without checking observedGeneration is how dashboards lie about rollout completion.
