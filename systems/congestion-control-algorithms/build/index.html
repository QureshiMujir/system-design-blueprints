⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the Cargo workspace (§10), the cc-api trait, cc-time monotonic clock, a share-nothing per-flow actor, the invariant framework, and a null controller — the minimal loop that accepts events and enforces I1/I7/I8 with zero real algorithm. Establishes determinism (P2) and observability (P7) before any CC math exists.

Deliverable

A binary that runs a single flow through NullController under LogicalClock, emits metrics, and panics on any I1/I7/I8 breach. make sim runs it end to end.

Acceptance
  • Workspace builds; clippy -D warnings clean; cargo fmt --check clean.
  • Send-gate rejects any send that would make inflight > cwnd — verified by invariant_i1.rs (0 breaches over 10,000 randomized sends).
  • WallClock import in any crates/cc-* (except cc-time) fails compilation (I7 test).
  • Actor rejects a second writer at compile time (I8 doc-test).
Fixtures
filename purpose expected output
fixtures/null_flow_basic.bin happy-path send/ack loop inflight ≤ cwnd throughout; 0 breaches
fixtures/i1_overshoot.bin send beyond cwnd (malformed) send-gate rejects; cc_i1_breach_total=0 sends admitted
fixtures/i7_wallclock.rs compile-fail test build error (regression guard)
fixtures/replay_roundtrip.bin record→replay identity bit-identical trace (I9 baseline)
Pitfalls
  • Using Instant::now() in logic → nondeterminism; root cause: convenience; detect via I7 type ban; signal: replay divergence (FM-6); recovery: route through Clock.
  • Shared-mutable flow state via Arc<Mutex<>> → contention + I8 violation; use actor ownership.
  • Telemetry on the hot path allocating → tail spikes (P5); use lock-free counters.
  • Off-by-one in byte vs packet cwnd → silent over-send; lock byte-based units (§8).

⬜ Phase 1 — RTT & Delivery-Rate Estimation §13

Objectives

Build cc-rate: the min-RTT windowed filter (I3), the BtlBw windowed-max filter (I4), and the delivery-rate sampler on the tcp_rate.c model (I5), plus app-limited detection — the single estimator every controller consumes (P9). No control decisions yet.

Deliverable

cc-rate produces a validated RateSample per ACK, feeding NullController; a replay of a recorded ACK stream yields identical filter outputs run-to-run (I9).

Acceptance
  • min-RTT within 1% of ground-truth propagation delay on a fixed-delay sim link.
  • Delivery-rate estimate within 3% of true link rate on a saturated 1 Gbps sim link.
  • Zero rate-inflation events under an ACK-compression fixture (I5).
  • Estimator update < 2 µs p99 (M3) measured by benchmarks micro-bench.
Fixtures
filename purpose expected output
fixtures/rate_saturated_1g.bin full-rate link delivery_rate within 3% of 1 Gbps
fixtures/rate_app_limited.bin idle sender gaps app-limited samples excluded from BtlBw
fixtures/ack_compression.bin burst ACKs (FM-7) no rate inflation; cc_ack_aggreg_ns>0
fixtures/minrtt_step.bin RTT step change min-RTT tracks after 10 s window (I3)
fixtures/rate_replay_regress.bin determinism guard identical filter trace over 1000 runs
Pitfalls
  • Measuring rate over ACK-arrival interval → ACK compression inflates BtlBw (FM-7); measure over send interval (tcp_rate.c lesson).
  • min-RTT never refreshing on a persistently queued path → stale RTprop; force ProbeRTT later (I13).
  • Counting retransmitted bytes as delivered → double counting; exclude is_retransmit.
  • Delayed ACKs mis-timing samples; use timestamp echo (RFC 7323) where present.

⬜ Phase 2 — Reno/NewReno AIMD Baseline §14

Objectives

Implement cc-reno: slow-start, congestion avoidance (additive increase), multiplicative decrease on loss, NewReno fast recovery (RFC 5681, RFC 6582 semantics), and IW10 init (Dukkipati 2010) — the packet-conservation baseline (P1) and the differential floor against the kernel.

Deliverable

cc-reno runs a single flow to steady state on a lossy sim link producing the canonical AIMD sawtooth; differential test against Linux tcp_reno on the same netem profile (P13).

Acceptance
  • Throughput within 5% of the Mathis model MSS/(RTT·√p) on p ∈ {0.01, 0.1}% loss links.
  • cwnd sawtooth peak/trough ratio ≈ 2.0 ± 5% (multiplicative decrease correctness).
  • Differential vs Linux tcp_reno: cwnd trajectory correlation ≥ 0.95 on fixtures/reno_kernel_diff.pcapng.
  • Never violates I1/I6 across 10,000 randomized loss events.
Fixtures
filename purpose expected output
fixtures/reno_sawtooth.bin AIMD steady state peak/trough ≈ 2.0
fixtures/reno_slowstart_iw10.bin IW10 startup initial cwnd = 10·MSS
fixtures/reno_fast_recovery.bin 1 loss, partial ACKs recovers without RTO (NewReno)
fixtures/reno_kernel_diff.pcapng differential oracle cwnd corr ≥ 0.95 vs kernel
fixtures/reno_mathis_regress.bin throughput model within 5% of Mathis prediction
Pitfalls
  • Halving on every dup-ACK instead of once per loss epoch → cwnd collapse; gate by recovery epoch.
  • Slow-start overshoot causing a large first loss burst; IW10 + pacing (Phase 4) mitigates.
  • Counting SACKed bytes wrong in fast recovery (NewReno partial ACK); follow RFC 6582.
  • Integer division truncation in additive increase → stalls at small cwnd.

⬜ Phase 3 — CUBIC (RFC 9438) §15

Objectives

Implement cc-cubic: the cubic window-growth function W(t)=C(t−K)³+W_max, the TCP-friendly region, fast convergence, and RFC 9438 constants (C=0.4, β=0.7) — the modern loss-based default that this project must match against Linux CUBIC (Ha 2008; RFC 9438).

Deliverable

cc-cubic sustains high-BDP throughput and matches Linux CUBIC's cwnd curve within tolerance; examples/run_cubic.rs on a 100 ms/1 Gbps link reproduces the concave-then-convex growth.

Acceptance
  • Throughput within 5% of Linux CUBIC on 100 ms/1 Gbps (M7) via fixtures/cubic_kernel_diff.pcapng.
  • K computation within 1 ULP of the RFC 9438 reference on fixtures/cubic_k_vectors.bin.
  • Fast convergence yields ≥ 15% faster convergence for a new flow vs no-FC on a shared bottleneck.
  • No fixed-point overflow at 100 Gbps·200 ms BDP (fixtures/cubic_highbdp.bin).
Fixtures
filename purpose expected output
fixtures/cubic_growth_curve.bin concave/convex growth matches W(t) reference within 1%
fixtures/cubic_k_vectors.bin K math vectors within 1 ULP of RFC 9438
fixtures/cubic_tcp_friendly.bin low-BDP region cwnd ≥ Reno estimate
fixtures/cubic_kernel_diff.pcapng differential oracle throughput within 5% (M7)
fixtures/cubic_highbdp.bin 100 Gbps overflow guard no overflow, monotonic W
Pitfalls
  • Fixed-point overflow in (t−K)³ at high BDP (the exact kernel pitfall #1); use 64-bit scaled math.
  • Resetting epoch_start on every ACK → growth stalls; reset only on loss/idle.
  • Forgetting the TCP-friendly region → CUBIC underperforms Reno on LANs.
  • Using wall-clock for t → nondeterministic curve (I7).

⬜ Phase 4 — Pacing Engine & Packet Scheduler §16

Objectives

Implement cc-pacing: a hashed/hierarchical timer wheel (Varghese), send-deadline queue, hrtimer/timerfd backend, and burst limiter converting pacing_rate into paced sends (P14, I2, I14) — the prerequisite for BBR and for taming CUBIC's bursts.

Deliverable

Paced output whose inter-packet gaps match pacing_rate within jitter budget; CUBIC + pacing shows visibly lower transient queueing than CUBIC bursts on the sim.

Acceptance
  • Pacing jitter p99 < 100 µs (M2) on fixtures/pacing_jitter.bin at 64-core load.
  • Burst amplification < 2% of pacing rate over any 1 ms window.
  • Zero I2 (monotonicity) breaches over 10^7 scheduled packets.
  • Timer wheel O(1) insert/expire verified by micro-bench (no O(n) scan).
Fixtures
filename purpose expected output
fixtures/pacing_jitter.bin jitter under load p99 < 100 µs (M2)
fixtures/pacing_burst_cap.bin burst limiter ≤ 2% amplification
fixtures/pacing_wheel_scale.bin 100k timers O(1) expire, no scan
fixtures/pacing_monotonic.bin deadline order (I2) 0 regressions
fixtures/pacing_replay_regress.bin determinism identical schedule (I9)
Pitfalls
  • Kernel timer coalescing merging pacing wakeups → bursts; use hi-res slot / fq offload.
  • CPU migration changing TSC base → jitter (FM-12); pin actor to core, use CLOCK_MONOTONIC_RAW.
  • Pacing rate 0 (idle) causing division/stall; guard rate ≥ floor.
  • Over-arming timers per packet → wheel overflow; batch by deadline slot.

⬜ Phase 5 — BBR v1 (BtlBw/RTprop Model) §17

Objectives

Implement cc-bbr: the BBR v1 state machine (Startup/Drain/ProbeBW/ProbeRTT), BtlBw/RTprop model, pacing_gain/cwnd_gain schedule, and app-limited handling (Cardwell 2016; I4, I13, I14) — model-based control operating at Kleinrock's optimal point (MM4).

Deliverable

cc-bbr reaches full BtlBw within a few RTT and holds inflight near 1·BDP with bounded queue; examples/bbr_vs_cubic.rs demonstrates the model on a shared bottleneck.

Acceptance
  • BtlBw converges within 3 RTT of Startup (M6) on fixtures/bbr_startup.bin.
  • Steady-state queue occupancy ≤ 1.5·BDP (M8) on a deep-buffer link (bufferbloat resistance).
  • ProbeRTT fires ≥ once/10 s (I13) verified in fixtures/bbr_probertt.bin.
  • Differential vs Linux tcp_bbr: BtlBw estimate within 5% on fixtures/bbr_kernel_diff.pcapng.

⬜ Phase 6 — Loss Detection: RACK-TLP & RTO §18

Objectives

Implement cc-loss: RACK time-based loss detection with a monotonic reordering window (RFC 8985, I15), Tail Loss Probe, and the RFC 6298 RTO with SRTT/RTTVAR and bounds (I12) — so controllers cut window on genuine loss, not reordering (P13).

Deliverable

cc-loss distinguishes reordering from loss and drives correct recovery for reno/cubic/bbr; a reordering fixture no longer triggers a spurious window cut.

Acceptance
  • Spurious retransmissions < 0.1% under 3-packet reordering on fixtures/rack_reorder.bin.
  • RTO never below 1 s without timestamps (I12) — 0 violations over 10^6 samples.
  • TLP recovers tail loss without RTO in ≥ 95% of single-tail-loss cases.
  • Differential vs Linux RACK: loss-detection timing within 1 RTT on fixtures/rack_kernel_diff.pcapng.
Fixtures
filename purpose expected output
fixtures/rack_reorder.bin 3-pkt reordering <0.1% spurious retransmit (I15)
fixtures/rack_tail_loss.bin tail loss TLP recovers, no RTO
fixtures/rto_backoff.bin repeated loss RTO doubles, capped 60 s (I12)
fixtures/rack_dsack_undo.bin spurious-loss undo cwnd cut reverted on DSACK
fixtures/rack_kernel_diff.pcapng differential oracle timing within 1 RTT
Pitfalls
  • Fixed reorder window → either spurious loss (too small) or slow detection (too large); grow on DSACK (I15).
  • RTO too low → spurious RTO storm (FM-8); enforce 1 s floor (I12).
  • Counting a TLP as a loss signal → false cwnd cut; treat probe distinctly.
  • Ignoring DSACK → cannot undo spurious cuts; implement DSACK-based undo.

⬜ Phase 7 — ECN / DCTCP / L4S & AQM Coupling §19

Objectives

Implement cc-ecn: classic ECN response (RFC 3168), DCTCP proportional reduction via alpha (Alizadeh 2010, I11), and L4S/ECT(1) scalable marking (RFC 9331), coupled to CoDel/fq_codel AQM (Nichols 2012) — the datacenter/low-latency path and the direct bufferbloat remedy (FM-1).

Deliverable

Under an ECN-marking bottleneck, cc-ecn holds queue sojourn low with near-zero loss; DCTCP mode achieves sub-millisecond queueing in the datacenter sim profile.

Acceptance
  • DCTCP queue sojourn p99 < 1 ms on the 10 µs-RTT datacenter fixture (bufferbloat resistance).
  • alpha tracks CE fraction within 5% on fixtures/dctcp_alpha.bin.
  • CE reduces window at most once per RTT (I11) — 0 violations.
  • L4S mode keeps p99 queue < 1 ms while coexisting with a classic flow (RFC 9332 coupling).
Fixtures
filename purpose expected output
fixtures/ecn_classic.bin RFC 3168 response 1 reduction per marked RTT (I11)
fixtures/dctcp_alpha.bin alpha tracking within 5% of CE fraction
fixtures/dctcp_datacenter.bin 10 µs-RTT DC link sojourn p99 < 1 ms
fixtures/l4s_coupled.bin DualQ coexistence L4S p99 queue < 1 ms
fixtures/ecn_mangle.bin CE-mark tampering (T4) detected, sample rejected
Pitfalls
  • Reacting to each CE mark like a loss in classic mode → over-reduction; once per RTT (I11).
  • DCTCP alpha EWMA gain wrong → oscillation; use g = 1/16 (Alizadeh 2010).
  • Deploying scalable (L4S) response on a classic bottleneck → unfairness; require ECT(1) + AQM.
  • ECN field mangled by a middlebox (T4) → wrong signal; validate accurate-ECN counts.
  • Real incident anchor: unmanaged deep buffers ("bufferbloat," Gettys 2011 public writeups) are the motivation — AQM + ECN is the documented remedy.

Deliverable

A reproducible sim that replays any recorded run bit-for-bit and a CI lane that differentially compares every algorithm to the kernel on a topology.

Acceptance

  • Simulator throughput ≥ 2 M packet-events/s/core (M4).
  • Differential lane passes for reno/cubic/bbr within each phase's kernel-diff tolerance.
  • Fuzzers run ≥ 1 h with 0 crashes/panics on ack_parser and replay_decoder.

⬜ Phase 9 — Kernel `tcp_congestion_ops` & QUIC (RFC 9002) Integration + Hardening §21

Objectives

Ship the core CC logic unchanged behind two production backends: a Linux kernel module implementing tcp_congestion_ops via the cc-ffi crate (ADR-25) and a QUIC sender adapter (cc-quic, RFC 9002); plus production hardening — reproducible builds, SBOM, signing, rollout (§27) — proving the trait boundary (P8) is real.

Deliverable

The same cc-cubic/cc-bbr runs (a) as a loadable kernel CC module carrying real TCP traffic and (b) as a QUIC sender, both matching the userspace simulator within tolerance.

Acceptance
  • Kernel module carries a real iperf3 flow with cwnd/RTT within 2% of userspace (M12) on fixtures/kernel_iperf.pcapng; 0 kernel panics over a 1 h soak.
  • QUIC adapter passes RFC 9002 loss-recovery vectors on fixtures/quic_rfc9002.bin.
  • Reproducible build: two builds byte-identical (sha256 match); SBOM generated; artifacts signed.
  • No unsafe outside cc-ffi (ADR-25) — enforced by #![forbid(unsafe_code)] elsewhere.

filename purpose expected output

fixtures/quic_rfc9002.bin QUIC loss recovery matches RFC 9002 vectors
fixtures/repro_build.txt reproducible build two builds identical sha256
fixtures/ffi_miri.rs unsafe surface Miri clean
fixtures/rollout_canary.bin canary gate promote only if M-table green
Pitfalls
  • Fixed-point overflow / different rounding in kernel vs userspace → divergence; share the math crate (ref-impl pitfall #1, §15).
  • Blocking or allocating in a kernel callback → soft-lockup; the shim must be allocation-free (P5).
  • QUIC ACK-frame delay vs TCP ACK semantics mishandled (ref-impl QUICHE pitfall); normalize in the adapter.
  • unsafe leaking outside cc-ffi (T9); enforce forbid(unsafe_code).
