220 — Congestion Control Algorithms (BBR/CUBIC) from Scratch

Project Number: 220

Project Name: Congestion Control Algorithms (BBR/CUBIC) from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from scratch, a deterministic userspace congestion-control laboratory plus a thin kernel-integration path that implements the canonical transport congestion-control algorithms — loss-based (Reno/NewReno AIMD, CUBIC per RFC 9438) and model-based (BBR v1, with v2/v3-ready extension points) — behind one stable pluggable controller trait, driven by a shared RTT/delivery-rate estimator, a high-resolution pacing engine, RACK-TLP loss detection (RFC 8985), and ECN/DCTCP/L4S signalling (RFC 3168, RFC 9331). The system runs against a bit-reproducible discrete-event network simulator and a Linux netem/tc emulation harness, differentially validated against the real kernel stack. It is a specification for a teaching-grade, research-grade congestion-control implementation, not a full transport stack.

Phase-0 deliverable — modules/crates (numbered):

  1. cc-api — the CongestionController trait, lifecycle hooks, RateSample/AckInfo types.
  2. cc-time — monotonic clock abstraction, logical simulation clock, timestamp wrappers.
  3. cc-rate — RTT filter (min-RTT windowed) + delivery-rate sampler (tcp_rate.c model).
  4. cc-pacing — pacing engine: timer wheel, deadline queue, hrtimer/timerfd backends.
  5. cc-cubic — CUBIC controller (RFC 9438 window growth, TCP-friendly region, fast conv.).
  6. cc-bbr — BBR v1 state machine (Startup/Drain/ProbeBW/ProbeRTT), BtlBw/RTprop model.
  7. cc-reno — Reno/NewReno AIMD + slow-start + fast recovery (packet-conservation baseline).
  8. cc-sim — deterministic discrete-event simulator (link, queue, delay, loss models).
  9. cc-replay — event-log record/replay, checkpointing, divergence detection.
  10. cc-telemetry — metrics (Prometheus), tracing (OpenTelemetry), structured logs.
  11. cc-conformance — fixture corpus + differential oracle harness (vs Linux netns).
  12. cc-tools — netem controller, benchmark runner (iperf/tcp_probe-style), trace import.

System boundaries.

  • Provides: congestion-control decision logic (cwnd + pacing rate), RTT/BW estimation, loss detection, ACK processing, pacing, ECN response, deterministic simulation, replay, telemetry, conformance/differential testing, kernel tcp_congestion_ops shim.
  • Delegates: actual packet I/O (kernel sockets / simulator link), TLS/QUIC crypto, routing, NIC drivers, AQM at the router (uses fq/fq_codel/CoDel but does not reimplement the qdisc), Grafana/Prometheus server processes.
  • Does NOT provide: a full TCP/IP or QUIC stack, reliable-transport reassembly, NIC offload (TSO/GRO) implementation, a production kernel scheduler, or a switch dataplane.

Non-goals: replacing the Linux stack; a novel CC algorithm as a research contribution; multipath transport; RDMA; satellite-specific tuning (all PhaseDeferred, see §35).

Deployment model: single-node developer laptop for the simulator; a small containerized benchmark cluster (Docker + docker-compose) with self-hosted CI runners that own network namespaces; optional kernel-module load on a disposable VM (Linux 6.x) for the FFI path.

Target users/operators: transport implementers, kernel networking engineers, CC researchers, performance engineers, and SREs debugging throughput/latency regressions.

What later phases unlock: Phase 1 estimation → Phase 2 AIMD baseline → Phase 3 CUBIC → Phase 4 pacing → Phase 5 BBR → Phase 6 RACK-TLP loss detection → Phase 7 ECN/DCTCP/L4S → Phase 8 simulation+replay+differential → Phase 9 kernel/QUIC integration + hardening.

Recommended language: Rust. Rationale: (a) memory safety without GC across concurrent per-flow state and FFI to the kernel; (b) deterministic, no-GC latency for the ACK/pacing hot path (M1, M2); (c) zero-cost trait dispatch for the pluggable controller (P8); (d) mature proptest/cargo-fuzz for property + fuzz testing (§26); (e) first-class #[repr(C)] FFI for the tcp_congestion_ops shim (Phase 9). Rejected: C — memory-unsafe estimator/pacing code is the exact defect class this project studies, and refactors are unsafe (kept only inside the vetted ffi crate, ADR-25); C++ — weaker default safety and dependency reproducibility, and no proptest/cargo-fuzz parity; Go — GC pauses violate the µs-scale pacing budget (M2) and select-driven scheduling adds nondeterminism hostile to replay (P2, I9).

Prerequisites: TCP/IP internals; AIMD & control-loop intuition; queueing theory (BDP, Little's law); Linux tc/qdisc/netem; monotonic time & timer wheels; lock-free/actor concurrency; eBPF & kernel tracepoints; statistical benchmarking.

Timeline: Phase 0 ≈ 4 weeks; estimation+AIMD+CUBIC ≈ 8 weeks; pacing+BBR ≈ 8 weeks; loss/ECN ≈ 6 weeks; sim/replay/differential ≈ 6 weeks; kernel/QUIC/hardening ≈ 8 weeks. Full system ≈ 9–10 months for one engineer, ≈ 5 months for a pair.

Deferred features (each registered in §35): multipath CC PhaseDeferred("§35"); RDMA/DCQCN PhaseDeferred("§35"); programmable-switch feedback PhaseDeferred("§35"); satellite/LEO adaptation PhaseDeferred("§35"); ML-assisted heuristics PhaseDeferred("§35"); BBRv3 full parity PhaseDeferred("§35").

2. Why Build This

  • Unique systems knowledge: congestion control is the single feedback loop that keeps the Internet from collapse (Jacobson 1988). Building it teaches how a purely end-to-end control law infers a hidden path (bottleneck rate, propagation delay, queue) from only ACK timing.
  • The two philosophies, side by side: loss-based AIMD (CUBIC) fills the buffer and reads loss as the signal; model-based BBR estimates BtlBw/RTprop and paces to the bandwidth-delay product. Implementing both exposes why bufferbloat exists and why BBR was invented.
  • Architectural/historical significance: AIMD → RED → Vegas → BIC → CUBIC → DCTCP → CoDel → BBR → L4S is 35 years of the field's evolution; each step is a reaction to a measured failure of the prior. You rebuild that lineage as running code.
  • Engineering muscles: µs-scale timing and pacing; allocation-free hot paths; windowed min/max filters; deterministic discrete-event simulation; differential testing against a reference kernel; fairness/latency tail analysis; FFI safety to kernel code.
  • Cross-links (sibling systems): #219-class QUIC transport (shares RFC 9002 CC), datacenter RPC frameworks (DCTCP/L4S), storage replication (throughput under loss), service meshes (tail latency), and any timer-wheel/scheduler project (Varghese, Network Algorithmics).
  • Calibration value: after this, "the network is slow" resolves into named, measurable phenomena — bufferbloat, RTT unfairness, ACK compression, incast, spurious RTO — each with a telemetry signal and a control-law explanation.

What Mastery Looks Like

  • Derive the BDP for any path and predict cwnd/pacing behavior of Reno, CUBIC, and BBR on it — built in Phase 3 (§15) and Phase 5 (§17).
  • Explain and reproduce bufferbloat, then show how pacing + AQM + BBR each attack it — Phase 4 (§16), Phase 5 (§17), Phase 7 (§19).
  • Estimate delivery rate and min-RTT correctly under delayed/aggregated ACKs — Phase 1 (§13).
  • Implement RACK-TLP and distinguish reordering from genuine loss — Phase 6 (§18).
  • Build a bit-reproducible simulator and differentially validate against the real kernel — Phase 8 (§20).
  • Read a production throughput/latency incident from cwnd/pacing/RTT telemetry — Phase 7 (§19) and §24.
  • Ship CC as a kernel tcp_congestion_ops module and as a QUIC (RFC 9002) sender without changing the core logic — Phase 9 (§21).

  • cc-tools: stateless operator/CI surface; every command emits CI-parseable JSON; owns impairment setup (netem/tc) and benchmark orchestration. Never touches flow state.
  • cc-telemetry: the observability plane; converts every CC transition into a metric/span/log with a monotonic timestamp (I7) and a replay correlation id. Sits outside the trust boundary.
  • Congestion Runtime Core: load-bearing; owns all flow state behind per-flow actors (I8).
  • cc-rate: turns ACK/loss events into a RateSample (delivery rate + RTT); the only estimator, shared by every controller (P9).
  • cc-api / controller: the pluggable CongestionController; exactly one of reno/cubic/bbr is bound per flow; produces cwnd + pacing rate (P8).
  • cc-pacing: converts pacing rate into send deadlines via a timer wheel; bounds burst (P14).
  • cc-loss: RACK-TLP + RTO; classifies loss vs reordering; feeds on_loss (Phase 6).
  • Transport integration: exactly one backend binds at a time — simulator, kernel shim, or QUIC adapter — so the core logic is backend-agnostic (P13).
  • cc-replay / netem / QUIC: the three egress sinks; the replay tap makes any run reproducible.

6. Design Principles

  • P1 — Packet conservation. Rule: inject a new segment into the network only when an in-flight one departs (an ACK) or the window explicitly grows. Tradeoff: strict self-clocking limits burstiness but caps utilization on ACK loss. Operational: inflight ≤ cwnd always (I1). Violation: line-rate bursts → queue overflow → congestion collapse (Jacobson 1988).
  • P2 — Determinism over convenience. Rule: every decision is a pure function of (state, event, seed); no wall-clock, no unseeded RNG, no thread-scheduling dependence. Tradeoff: forbids ad-hoc Instant::now() in logic. Operational: replay is bit-identical (I9, M9). Violation: regressions become unreproducible; differential testing is worthless.
  • P3 — Model the path, don't merely react to loss. Rule: estimate the path's physical properties (BtlBw, RTprop) as first-class state; treat loss as one signal among several. Tradeoff: estimation error can mis-pace. Operational: BBR's BtlBw/RTprop (I4, I3). Violation: pure loss-based control fills every buffer → bufferbloat (FM-1).
  • P4 — Monotonic time only. Rule: all timing from a monotonic source; wall clock never enters a control or pacing calc. Tradeoff: cannot cross-correlate to UTC without a mapping. Operational: I7. Violation: NTP steps corrupt RTT samples → pacing chaos (FM-12).
  • P5 — Allocation-free hot path. Rule: ACK processing, rate sampling, and pacing use only pre-allocated ring buffers and fixed state. Tradeoff: pre-sizing wastes memory on idle flows. Operational: M5; p99 stays under M1. Violation: allocator jitter spikes tail latency.
  • P6 — Backpressure everywhere; no unbounded queue. Rule: every channel/queue is bounded and exposes occupancy + drop counters. Tradeoff: drops under overload instead of buffering. Operational: ADR-23. Violation: memory blow-up and hidden latency (bufferbloat internally).
  • P7 — Observability by default. Rule: every state transition (slow-start↔CA, ProbeBW phase, loss epoch) emits a metric/span. Tradeoff: telemetry CPU cost. Operational: §24 dashboards. Violation: production CC incidents become undebuggable.
  • P8 — One pluggable controller trait. Rule: reno/cubic/bbr implement an identical CongestionController; nothing else knows which is bound. Tradeoff: the trait must be the superset of all algorithms' hooks. Operational: §11, ADR-05. Violation: algorithm-specific leakage into pacing/estimation defeats differential testing.
  • P9 — Separate estimation from control. Rule: cc-rate produces RateSample; controllers only consume it. Tradeoff: one estimator must serve loss- and model-based control. Operational: tcp_rate.c model shared. Violation: each algorithm re-deriving RTT/BW causes drift and duplicated bugs.
  • P10 — Fail visibly, crash-only. Rule: invariant breaches panic (in sim) or quarantine the flow and emit an alert; no silent clamping. Tradeoff: a bad flow is killed, not limped along. Operational: §23. Violation: silent corruption of BW estimates propagates network-wide.
  • P11 — Fairness is a first-class, measured metric. Rule: every algorithm reports Jain's fairness index and RTT-fairness ratio in CI. Tradeoff: fairness vs throughput is a real tension (BBR vs CUBIC). Operational: §28 M-table, FM-3/FM-4. Violation: deploying an algorithm that starves incumbents (the BBR-v1 lesson, Ware 2019).
  • P12 — Bounded per-flow state. Rule: flow state size is O(1) regardless of path RTT/BW or history. Tradeoff: fixed-size sample rings can drop old samples. Operational: §4 table, I-set. Violation: memory grows with BDP → OOM on high-BDP paths.
  • P13 — Differential correctness against the real kernel. Rule: the same scenario is run against cc-* and the Linux stack; divergence beyond a tolerance is a failing test. Tradeoff: requires netns and self-hosted CI. Operational: §20, ADR-16. Violation: a "correct-looking" reimplementation that silently mispredicts real behavior.
  • P14 — Pace, don't burst; cwnd is a budget, pacing is a rate. Rule: cwnd bounds inflight; the pacing engine spreads sends at BtlBw·gain. Tradeoff: pacing needs high-res timers (cost). Operational: I14, §16. Violation: cwnd-only sending emits line-rate bursts → transient queueing and loss (MM8).

Debugging methodology. The deterministic simulator (cc-sim) runs with one assertion per invariant enabled; a property-test campaign (proptest, §26) drives randomized ACK/loss/ECN sequences and, on any I# breach, minimizes the input and emits the smallest failing replay frame (I9) so the bug reproduces bit-for-bit outside the fuzzer.

8. Domain Model / Protocol / Data Model

Time & units. All times are MonotonicNs (u64 ns since an arbitrary epoch). Windows (cwnd) and rates are byte-based (not packet-based) to match QUICHE and modern Linux. Rate = bytes/second.

Controller lifecycle (state the CC API drives).

             on_packet_sent(pkt)        on_ack(RateSample)         on_loss(range)
   SEND ───────────────────────▶ INFLIGHT ───────────────▶ (update cwnd/pacing) ───▶ SEND
                                     │                                   ▲
                                     └────── on_loss / RTO ──────────────┘  (recovery)

CUBIC state machine (RFC 9438).

  SLOW_START ──(cwnd ≥ ssthresh)──▶ CONGESTION_AVOIDANCE ──(loss/ECN)──▶ FAST_RECOVERY
       ▲                                     │  cubic growth: W(t)=C(t−K)^3 + W_max        │
       └──────────────(RTO / exit)───────────┴────────────(recover, ssthresh=β·W_max)─────┘

W_max = window at last reduction; K = cbrt(W_max·(1−β)/C); β = 0.7, C = 0.4 (RFC 9438). TCP-friendly region tracks Reno-estimated window; fast convergence lowers W_max on successive losses.

BBR v1 state machine (Cardwell 2016).

  STARTUP ──(BtlBw plateau: <25% gain over 3 RTT)──▶ DRAIN ──(inflight ≤ BDP)──▶ PROBE_BW
     │  gain=2/ln2 (~2.89)              gain=1/2.89                 │  8-phase gain cycle
     │                                                             │  [1.25,0.75,1,1,1,1,1,1]
     └───────────────────────── PROBE_RTT (every ≥10 s) ◀──────────┘  cwnd=4·MSS, ~200 ms

RateSample (delivery-rate estimation, tcp_rate.c model). Each ACK yields: delivery_rate = (delivered − delivered_at_send) / (now − send_time); app-limited samples are flagged and excluded from BtlBw max-filter (I4, I5).

Packet / ACK wire fields consumed (not a full TCP header — the CC-relevant subset).

Segment {  seq:u64, len:u32, send_ts:MonotonicNs, delivered_at_send:u64,
           is_app_limited:bool, is_retransmit:bool, ecn: EcnCodepoint }
AckBlock {  ack_ts:MonotonicNs, cumulative_ack:u64, sack_ranges:[Range<u64>],
           ecn_ce_count:u64,          // RFC 3168 accurate-ECN feedback
           ts_echo:u32 }              // RFC 7323 timestamp echo

State-transition table (BBR ProbeBW gain cycle, one RTT per row).

phase pacing_gain cwnd_gain intent
0 1.25 2 probe up: seek more bandwidth
1 0.75 2 drain the queue the probe created
2–7 1.00 2 cruise at BtlBw for 6 RTT

Worked example (BDP). 100 Mbps, RTprop 40 ms ⇒ BDP = 100e6/8 · 0.040 = 500,000 B ≈ 333 MSS (1500 B). BBR targets cwnd ≈ 2·BDP = 1,000,000 B; steady inflight ≈ 1·BDP; CUBIC would grow past BDP until the buffer fills and drops (FM-1).

Malformed input example. ACK with cumulative_ack > highest sent seq (optimistic ACK, T2): rejected by the send-cause/inflight audit (I1, I10); sample discarded, cc_bad_ack_total incremented, flow flagged, no cwnd growth credited.

Failure-path example (ACK compression, FM-7). Aggregated ACKs arrive in a burst ⇒ measured interval shrinks ⇒ naive delivery_rate inflates ⇒ BtlBw over-estimate ⇒ over-pacing ⇒ queue build-up ⇒ RTT spike. Mitigation: the sampler measures over the send-time span, not the ack-arrival span, and the ACK-aggregation estimator (cc_ack_aggreg_ns) inflates the cwnd allowance rather than the rate (I5).

13.1 Objectives

Build cc-rate: the min-RTT windowed filter (I3), the BtlBw windowed-max filter (I4), and the delivery-rate sampler on the tcp_rate.c model (I5), plus app-limited detection — the single estimator every controller consumes (P9). No control decisions yet.

14. Phase 2 — Reno/NewReno AIMD Baseline

14.1 Objectives

Implement cc-reno: slow-start, congestion avoidance (additive increase), multiplicative decrease on loss, NewReno fast recovery (RFC 5681, RFC 6582 semantics), and IW10 init (Dukkipati 2010) — the packet-conservation baseline (P1) and the differential floor against the kernel.

14.2 Detailed Implementation Steps

  • Implement slow-start: cwnd += acked bytes until ssthresh; IW = 10·MSS (Dukkipati 2010, applied here).
  • Implement congestion avoidance: cwnd += MSS·MSS/cwnd per RTT (AIMD additive increase, Jacobson 1988; P1).

15. Phase 3 — CUBIC (RFC 9438)

15.1 Objectives

Implement cc-cubic: the cubic window-growth function W(t)=C(t−K)³+W_max, the TCP-friendly region, fast convergence, and RFC 9438 constants (C=0.4, β=0.7) — the modern loss-based default that this project must match against Linux CUBIC (Ha 2008; RFC 9438).

15.2 Detailed Implementation Steps

  • Implement the cubic growth: compute K = cbrt(W_max·(1−β)/C) and W(t) in fixed-point (avoid the kernel's overflow pitfall at 100 Gbps, ref-impl lesson #1); update per ACK using epoch_start (I7 monotonic).
  • Implement the TCP-friendly region: track a Reno-estimated tcp_cwnd; use max(cubic, tcp) so CUBIC is never slower than Reno on low-BDP paths (RFC 9438).
  • Implement fast convergence: on a loss with cwnd < W_max, set W_max = cwnd·(1+β)/2 to yield bandwidth to new flows (Ha 2008; P11).
  • Multiplicative decrease β=0.7 (gentler than Reno's 0.5); enforce I6; hook cc-loss and cc-ecn (Phase 7).
  • Emit epoch and region telemetry (P7); differential vs kernel tcp_cubic.c (P13, ADR-16).

15.3 Deliverable

cc-cubic sustains high-BDP throughput and matches Linux CUBIC's cwnd curve within tolerance; examples/run_cubic.rs on a 100 ms/1 Gbps link reproduces the concave-then-convex growth.

15.4 Acceptance Criteria

  • Throughput within 5% of Linux CUBIC on 100 ms/1 Gbps (M7) via fixtures/cubic_kernel_diff.pcapng.
  • K computation within 1 ULP of the RFC 9438 reference on fixtures/cubic_k_vectors.bin.
  • Fast convergence yields ≥ 15% faster convergence for a new flow vs no-FC on a shared bottleneck.
  • No fixed-point overflow at 100 Gbps·200 ms BDP (fixtures/cubic_highbdp.bin).

Kernel/userspace clock source mismatch (I7); module unload mid-flow (drain); QUIC 0-RTT and connection migration (cwnd carry-over); mixed TCP+QUIC on one host; ABI change across kernel versions (§25).

21.9 Failure Analysis

A kernel bug can panic the host (blast radius = node); QUIC adapter bug affects userspace flows only. Detection: soak + differential (P13). Recovery: unload module (runbook), fall back to stock CUBIC. Forensics: kernel trace + dmesg; QUIC replay. Long-term: keep FFI surface minimal (ADR-25).

21.10 Operational Notes

Metrics: cc_backend (sim|kernel|quic), cc_ffi_unsafe_calls_total, cc_build_repro_ok. Runbook: docs/runbooks/kernel-module.md. Rollout: canary → rolling upgrade → rollback to stock CUBIC (§24). Compatibility: kernel ABI + QUIC wire versioned (§25).

25. Compatibility & Versioning

  • Wire/protocol: the project consumes standard TCP/QUIC ACK semantics; it introduces no new wire format. ECN negotiation and accurate-ECN feedback are per-flow, capability-gated.
  • Replay/storage: ReplayHeader.version (u16) + append-only ReplayFrame fields (ADR-10); a newer reader replays older logs via version negotiation; CRC32C guards integrity (I9).
  • Schema evolution: Protocol Buffers (prost, ADR-09) for config/metrics — fields are add-only, never renumbered; removed fields are reserved.
  • API stability: CongestionController (P8) is SemVer-governed; a hook addition is a minor bump with a default; a hook signature change is a major bump.
  • Algorithm identity: ReplayHeader.algo (u8) tags reno/cubic/bbr and version (e.g. CUBIC RFC 9438 vs legacy 8312) so replays are unambiguous.
  • Migration: switching a flow's algorithm is runtime-selectable; state does not carry across algorithms (fresh estimator warm-up).
  • Deprecation policy: two-minor-version deprecation window; deprecated hooks emit cc_deprecated_use_total.
  • SemVer: MAJOR.MINOR.PATCH; kernel ABI and QUIC wire compatibility documented per release.
  • Rolling-upgrade guarantee: a node running version N interoperates with N−1 for the entire release; canary + rollback (§24) gate every change.

29. Scalability Analysis

  • Constant vs grows: per-flow work is O(1) per ACK (P12) — cwnd/rate/loss updates are fixed cost; total CPU is O(flows · ACK-rate). Memory is O(flows) at ≤ 5 KB/flow (§4, §32).
  • Named bottlenecks, in order: (1) pacing timer fan-out (100 K armed timers, T12) — the wheel must stay O(1); (2) telemetry cardinality (T6) — bounded series; (3) ACK-processing CPU (M1) at high aggregate ACK rate; (4) replay-log write bandwidth (ADR-11); (5) differential-test kernel throughput (I/O-bound).
  • Horizontal scaling: simulator shards by flow across cores (share-nothing actors, ADR-05); benchmark cluster shards topologies across nodes (ADR-21); replay workers parallelize by segment.
  • Vertical scaling: NUMA-pin actor pools ≥ 32 cores (§4); hot state one cache line; fq offload moves pacing to the NIC.
  • Sharding/partitioning: flows partition by hash to actor pools; no cross-partition state (I8), so no coordination overhead on the hot path.
  • Coordination overhead: only telemetry aggregation and checkpoint flush cross cores — both off the hot path (P7, FM-10).
  • Practical ceiling & levers: ≈ 250 K active paced flows/core (pacing + ACK budget). Levers beyond it: fq NIC pacing offload, coarser telemetry sampling, larger pacing-wheel slots, more cores/nodes. True multi-node CC (multipath) is PhaseDeferred("§35").

30. Mental Models & First Principles

  • MM1 — A flow is a control loop around a pipe with a queue. Insight: sender = controller, network = plant, ACKs = feedback. Predicts: stability/oscillation follow control theory (gain, delay). Bug class without it: tuning constants blindly and getting sawtooth instability. Resolves in: §6 (P1), §3.
  • MM2 — BDP is the memory of the network. Insight: BDP = BtlBw · RTprop bytes are "in flight" with no queue. Predicts: cwnd below BDP under-utilizes; above BDP fills the buffer. Bug class: sizing cwnd/buffers wrong → under-use or bufferbloat. Resolves in: §8 (worked example), §32.
  • MM3 — Loss-based CC fills the buffer by design. Insight: AIMD only backs off after a drop, so it must first fill and overflow the queue. Predicts: CUBIC bufferbloat on deep buffers (FM-1). Bug class: expecting low latency from a loss-based algorithm on a dumb deep buffer. Resolves in: §15 (Phase 3), §19 (Phase 7).
  • MM4 — Two numbers describe the path (Kleinrock's optimal point). Insight: BtlBw and RTprop fully characterize the pipe; operating at exactly BDP inflight maximizes rate and minimizes delay simultaneously. Predicts: BBR's target. Bug class: believing you must trade throughput for latency. Resolves in: §17 (Phase 5), I4.
  • MM5 — You can't measure max-BW and min-RTT at the same time. Insight: probing bandwidth builds a queue (inflates RTT); measuring RTprop needs an empty queue (sacrifices rate) — so you must alternate. Predicts: BBR's ProbeBW/ProbeRTT split; Vegas's delay signal. Bug class: trusting an RTT sample taken while probing up. Resolves in: §17 (Phase 5), I3/I13.
  • MM6 — ACKs are the clock; break the clock and you break the controller. Insight: self-clocking (P1) times sends to the network's own pace. Predicts: ACK compression/thinning destabilizes rate estimates (FM-7). Bug class: estimating rate over ACK-arrival time. Resolves in: §13 (Phase 1, I5), §8.
  • MM7 — Fairness is emergent, not guaranteed. Insight: fairness arises from all flows sharing the same feedback law; mix laws (BBR + CUBIC) and one starves the other. Predicts: BBR-v1 vs CUBIC starvation (Ware 2019, FM-4). Bug class: deploying a new algorithm and assuming it coexists. Resolves in: §23 (FM-4), §17 (Phase 5), P11.
  • MM8 — cwnd is a budget; pacing is a rate. Insight: cwnd bounds how much is in flight; pacing controls how fast it leaves — decoupling them removes bursts. Predicts: cwnd-only senders burst at line rate and self-inflict loss. Bug class: shipping cwnd without pacing on a high-BDP path. Resolves in: §16 (Phase 4, I14), P14.

32. Back-of-Envelope Capacity Model

Each number derives from the §4 System Constraints table (formula shown).

  1. BDP of a reference WAN path. BDP = BtlBw · RTprop. From §4 max 100 Gbps and RTT 100 µs–800 ms, take 10 Gbps × 40 ms: 10e9/8 · 0.040 = 50,000,000 B ≈ 50 MB in flight — cwnd must reach this to fill the pipe (MM2).
  2. Per-flow memory. §4: ≤ 512 B hot + ≤ 4 KB cold ≈ 4.5 KB/flow; round to 5 KB for headers.
  3. Flow-table RAM. flows · per-flow = 1,000,000 · 5 KB = 5 GB — matches the §4 ≤ 5 GB ceiling; sets the memory budget for a max-scale sim node.
  4. ACK CPU budget. §4 ACK p99 < 10 µs ⇒ one core sustains 1 / 10 µs = 100,000 ACKs/s at the tail; at p50 2 µs, 500,000 ACKs/s. So ~250 K active flows/core at ~1–2 ACKs/s each with headroom (the §29 ceiling).
  5. Pacing timer load. §4: 100 K armed timers, 1 ms wheel tick ⇒ 100,000 / 0.001 s = 100,000,000 timer-slot touches/s worst case — must be O(1)/slot (Varghese), else the wheel is the bottleneck (§29 #1).
  6. Simulator wall-clock for a run. §4: ≥ 2 M events/s/core. A 60 s, 1 Gbps, 1500 B-packet flow = 1e9/8/1500 · 60 ≈ 5,000,000 packets → ~2 events each = 10 M events → 10e6 / 2e6 = 5 s/core.
  7. Replay-log size. §4: ≤ 40 B/event. At 500 K events/s (§4 telemetry): 500,000 · 40 B · 3600 s = 72 GB/hour at full rate — so segment + rotate (ADR-11) and sample; the ≤ 512 MB/hour §4 target holds only at ≈ 3,600 events/s, i.e. logging is sampled ~140:1 at peak.
  8. Telemetry bandwidth. §4: 500 K events/s × ~64 B/metric-sample = 32 MB/s ⇒ the ≤ 1 GB buffer drains in 1 GB / 32 MB/s ≈ 31 s, matching the < 60 s pipeline-restart RTO (§4).
  9. FD budget check. §4: 250 K FDs/node; at 1 socket + 1 timerfd per flow ⇒ 125 K flows/node FD-limited — below the 250 K-active-flow CPU ceiling, so FDs bound before CPU on real sockets (sim flows use no FDs).
  10. Bufferbloat delay. A 1 Gbps link with a 1 MB dumb buffer adds queue delay = 1e6·8 / 1e9 = 8 ms — quantifies why loss-based CC (MM3) inflates RTT and why AQM/BBR target ≤ 1.5·BDP (M8).

34. Alternative Architectures (Roads Not Taken)

ALT-1 — Kernel-only (no userspace lab). Implement CC purely as in-kernel tcp_congestion_ops modules, tested only with live traffic.

  app → socket → [kernel CC module] → NIC → wire
                   (no sim, no replay)

Wins: zero FFI overhead, exact production semantics, ships directly. Embodied by: the mainline Linux stack. Rejected because: no determinism/replay (I9) and no cheap fast iteration — every experiment needs a kernel build and a live path; violates P2 and the teaching goal.

ALT-2 — Pure discrete-event simulation (no kernel/QUIC). Everything lives in a simulator; never touch a real stack.

  [event queue] → [link/queue/loss model] → [CC under test] → metrics

Wins: fully deterministic, fastest iteration, trivial fault injection. Embodied by: ns-3. Rejected because: no ground truth — a simulator can be internally consistent yet wrong vs the real kernel; this blueprint keeps the sim but adds the differential oracle (§20, P13) precisely to avoid ALT-2's blind spot.

ALT-3 — In-network / AQM-centric. Push control into routers: RED/CoDel/PIE + ECN do the work; endpoints stay simple.

  sender → [router AQM: mark/drop by queue] → receiver
             (control lives in the network)

Wins: protects all flows regardless of endpoint algorithm; low latency without endpoint changes. Embodied by: fq_codel / L4S DualQ (RFC 9332). Rejected as the sole architecture because: it requires cooperative infrastructure the sender can't assume end-to-end; this blueprint uses AQM (§19) but keeps end-to-end control as the primary lever (Jacobson 1988 end-to-end principle).

ALT-4 — Centralized rate allocation (SDN/host-agent). A controller computes per-flow rates from a global view; hosts enforce.

  hosts → telemetry → [central allocator] → rate grants → hosts enforce

Wins: near-optimal allocation and isolation in a single administrative domain. Embodied by: datacenter systems like Google BwE / Swift-style host congestion control. Rejected because: it needs a trusted central view and low-latency control plane — impossible across the public Internet; retained only as a datacenter-mode idea (PhaseDeferred("§35")).

36. Glossary

  • ACK compression — ACKs bunched by cross-traffic/aggregation so they arrive in a burst, inflating naive delivery-rate estimates (FM-7).
  • AIMD — Additive-Increase/Multiplicative-Decrease, the Reno control law (Jacobson 1988).
  • App-limited — an interval where the sender had no data to send; its rate samples must not lower BtlBw (I4).
  • AQM — Active Queue Management (RED, CoDel, PIE); drops/marks before the queue is full.
  • BDP — Bandwidth-Delay Product = BtlBw · RTprop; bytes in flight with an empty queue (MM2).
  • BBR — Bottleneck Bandwidth and Round-trip propagation time; model-based CC (Cardwell 2016).
  • BtlBw — estimated bottleneck bandwidth (windowed-max delivery rate, I4).
  • Bufferbloat — excessive standing queue in an over-large buffer causing high latency (FM-1).
  • Congestion collapse — throughput → 0 under retransmission storms (Jacobson 1988, FM-2).
  • Congestion window (cwnd) — sender's upper bound on in-flight bytes (a budget, MM8, I1).
  • Congestion avoidance — the additive-increase phase after slow-start (RFC 5681).
  • CUBIC — cubic-window loss-based CC, Linux default (RFC 9438).
  • DCTCP — Data Center TCP; ECN-proportional window reduction via alpha (Alizadeh 2010, I11).
  • Delivery rate — bytes delivered per unit send-time interval (tcp_rate.c model, I5).
  • DSACK — Duplicate SACK; signals a spurious retransmission, enabling undo (I15).
  • ECN — Explicit Congestion Notification; routers mark instead of drop (RFC 3168).
  • ECT(0)/ECT(1)/CE — ECN codepoints; ECT(1) marks L4S-scalable traffic (RFC 9331).
  • Fast convergence — CUBIC's extra W_max reduction to yield bandwidth to new flows (Ha 2008).
  • Fast recovery — post-loss phase that avoids returning to slow-start (NewReno, RFC 6582).
  • Flow actor — the single-writer owner of one flow's state (I8, ADR-05).
  • fq / fq_codel — Linux fair-queue / fair-queue-CoDel qdiscs; pacing + AQM.
  • hrtimer / timerfd — high-resolution kernel timers used by the pacing backend (ADR-07).
  • Inflight bytes — sent but unacknowledged bytes; must stay ≤ cwnd (I1).
  • IW10 — initial window of 10 segments at connection start (Dukkipati 2010).
  • Jain's fairness index — a 0–1 measure of how equally a bottleneck is shared (P11).
  • Kleinrock's optimal point — inflight = BDP: max throughput and min delay together (MM4).
  • L4S — Low Latency, Low Loss, Scalable throughput architecture (RFC 9330).
  • min-RTT / RTprop — the propagation-delay estimate (windowed-min RTT, I3).
  • Monotonic clock — non-decreasing, NTP-immune time source (CLOCK_MONOTONIC_RAW, I7).
  • Optimistic ACK — an ACK for data not yet received; an attack/defect (T2).
  • Pacing — spacing packet sends at a target rate rather than bursting (P14, MM8).
  • Pacing gain / cwnd gain — BBR multipliers on rate and window (I14, §8).
  • Packet conservation — inject new data only as old data leaves the network (P1).
  • ProbeBW / ProbeRTT — BBR states that probe bandwidth vs refresh RTprop (§17, I13).
  • QUIC — encrypted userspace transport; CC per RFC 9002.
  • RACK-TLP — time-based loss detection + Tail Loss Probe (RFC 8985, I15).
  • RED — Random Early Detection AQM (Floyd/Jacobson 1993).
  • Replay divergence — a replayed run producing a different trace than recorded (FM-6, I9).
  • RTO — Retransmission TimeOut (SRTT + 4·RTTVAR, floor 1 s, RFC 6298, I12).
  • RTT — round-trip time (one delivery-rate/RTT sample per ACK).
  • SACK — Selective Acknowledgment (RFC 2018); enables precise loss detection.
  • Self-clocking — using ACK arrivals as the transmit clock (MM6, P1).
  • Slow start — exponential cwnd growth at connection start until ssthresh (RFC 5681).
  • Sojourn time — how long a packet sits in a queue; CoDel's control signal (Nichols 2012).
  • ssthresh — slow-start threshold separating slow-start from congestion avoidance.
  • Tail latency — high-percentile (p99/p999) latency behavior (Gregg; M1/M2).
  • TCP-friendly region — CUBIC's fallback so it is never slower than Reno (RFC 9438).
  • Timer wheel — hashed/hierarchical O(1) timer structure for pacing (Varghese, §16).
  • Windowed max/min filter — O(1) filter tracking max/min over a time/RTT window (I3, I4).
