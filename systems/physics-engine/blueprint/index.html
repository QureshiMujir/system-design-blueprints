171 — Physics Engine (Rigid Body + Collision)

Project Number: 171

Project Name: Physics Engine (Rigid Body + Collision)

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from scratch in Python, a fixed-timestep rigid-body physics engine covering the full pipeline from broad-phase culling through narrow-phase collision detection, contact manifold generation and persistence, a sequential-impulse constraint solver with warm starting and position correction, friction and restitution, joints, sleeping/islands, and continuous collision detection (CCD). The engine is a library: it owns body state, shape geometry, collision detection, and constraint solving, and exposes a step(dt) entry point plus a query interface (raycast, overlap, AABB query). It does not own a scene graph, an entity-component system, a render loop, or input handling — those belong to the sibling blueprint Game-Engine-Core (rank 172). The integration seam is exact: Game-Engine- Core's fixed-update loop calls World.step(dt) once per tick and reads back RigidBody transforms through a stable snapshot API (§11); Game-Engine-Core owns entity identity, this engine owns BodyId identity, and the two are joined by a one-to-one mapping table that Game-Engine-Core maintains, not this engine. This blueprint does not re-specify the ECS, the main loop, or asset loading.

Phase-0 deliverable (packages, importable as physics.*):

  1. physics.math — Vec2, Vec3, Quat, Mat3, Transform and their algebra.
  2. physics.body — RigidBody, MassData, InertiaTensor, BodyId allocation.
  3. physics.shapes — Shape variants and the SupportFunction contract.
  4. physics.determinism — the replay/hash harness and fixed-step driver.
  5. physics.world — the World container and step(dt) orchestration (empty pipeline until later phases fill it in).

Boundaries. Provides: rigid-body dynamics, collision detection (broad + narrow phase), constraint solving (contacts + joints), sleeping, CCD, spatial queries, a determinism harness. Delegates: rendering (Game-Engine-Core / a renderer blueprint), input, asset pipelines, networking/lockstep transport (a networked game built on this engine owns input serialization; this engine only guarantees that identical inputs replay identically). Does NOT provide: soft bodies, cloth, fluids, a full articulated-robotics (Featherstone reduced-coordinate) solver, vehicle-specific tire models, GPU acceleration, a scene graph or editor.

Non-goals, explicit: not soft bodies; not fluids; not a full articulated-robotics solver (hinge-chain joints are provided; a generalized reduced-coordinate solver is not — see ADR-16). Deployment model: (a) a Python library imported by a host application; (b) a headless CLI determinism harness that steps a scene N times and diffs state hashes, usable in CI with no display; (c) a visual debugger that consumes the debug-draw seam (§3) but is implemented and owned outside this blueprint. Users/operators: the game or simulation developer embedding the library; this blueprint's own CI (regression and determinism gate); a researcher validating a scenario against an analytic solution. Later phases unlock: joints unlock hinge/chain/vehicle-chassis composition (vehicle tire models remain out of scope); CCD unlocks projectile-heavy gameplay without tunnelling; the query interface unlocks AI raycasts and trigger volumes for Game-Engine-Core.

Language: Python 3.11+, chosen because the entire pedagogical point of this blueprint is that the constraint-solver math must be inspectable and steppable in a REPL — see ADR-01. Rejected: C++ (matches Bullet/Box2D natively but defeats the inspectability goal); Rust (memory safety is attractive but the borrow checker fights the highly aliased mutable body/island/contact graph this engine needs at exactly the phases where understanding matters most); C (no safety net, too low-level for the teaching goal). Honest numeric-core statement: NumPy (structure-of-arrays) carries bulk per-body state (positions, velocities, orientations) for vectorized integration and AABB refresh, but the sequential-impulse solver's inner loop is inherently data-dependent (each constraint's solve reads the just-updated velocity of its neighbors) and does not vectorize in NumPy — it remains a pure-Python loop, and will be the dominant cost at body/contact counts beyond a few thousand (§30). A compiled hot-path extension (Cython or a Rust core via PyO3) is the identified escalation and is explicitly deferred: PhaseDeferred("§30 Performance Engineering").

Prerequisites: linear algebra (vector/matrix algebra, change of basis, eigendecomposition for principal inertia axes); rotational dynamics (angular velocity, torque, the inertia tensor, quaternion algebra); numerical methods (stability of explicit vs. implicit integrators, per Press et al.); classical mechanics (Newtonian and Lagrangian formulations, per Baraff & Witkin).

Timeline: twelve phases (Phase 0–11), summarized with durations in §40 Appendix B; total order-of-magnitude estimate is 14–20 engineering-weeks for one engineer working part-time, front-loaded (Phases 0–2 are the highest-leverage weeks: get the integrator and shape contract right before collision and solving are built on top of them).

Deferrals in this document use PhaseDeferred("<real anchor>") and are collected in §37; every anchor names a heading that exists in this file.

2. Why Build This

  • Iterative numerical methods, applied: sequential impulses are Gauss-Seidel on a sparse LCP with a deadline — the clearest hands-on encounter with convergence, under-iteration, and residual error most engineers ever get.
  • Geometry that must terminate: GJK/EPA force you to reason about simplex degeneracy, floating-point tolerance, and algorithmic termination guarantees, not just "the math".
  • Determinism as a design constraint, not an afterthought: lockstep-replay correctness changes what "correct" means for every downstream choice (contact ordering, iteration count, float precision).
  • Energy and stability as first-class metrics: a physics engine is one of the few systems where "is it correct" has a literal, measurable, physical answer (energy drift, momentum conservation).
  • Systems-engineering practice: islands, sleeping, broad/narrow-phase separation, and CCD are a compact case study in staged filtering, incremental computation, and opt-in cost (pay only for what moves fast).
  • Direct lineage to shipped, studied systems: Box2D, Bullet, Chipmunk2D, Rapier, and MuJoCo are all reachable, readable references for every design decision here.

What Mastery Looks Like

  • You can explain, without notes, why semi-implicit Euler is preferred to explicit Euler for constrained rigid bodies, and show the energy-drift number that proves it (Phase 1, §13).
  • You can derive the effective mass of a contact constraint from first principles and explain why warm starting changes convergence, not correctness (Phase 7–8, §19–§20).
  • You can explain GJK termination and EPA's expanding-polytope loop well enough to spot a degenerate-simplex bug by inspection (Phase 6, §18).
  • You can explain why position correction is a separate NGS pass rather than a velocity-level bias, and what breaks if you get that wrong (Phase 9, §21).
  • You can reason about island partitioning and explain exactly why a static body must never merge two islands into one (Phase 9, §21).
  • You can quote the tunnelling-threshold-velocity formula for a given shape and timestep and know, from that number alone, whether CCD is mandatory (Phase 10, §22, §34).
  • You can look at a jittering stack and, from the invariant table (§7) alone, name the two or three most likely root causes before opening a debugger.

World owns all bodies, shapes, joints, the broad-phase structure, and the manifold cache; it is the only mutable root. The integrator advances velocities from forces (gravity, applied impulses) using semi-implicit Euler (P10) and never touches position directly. The broad phase (a spatial hash promoted to a dynamic BVH, ADR-07) produces a candidate-pair queue cheaply and conservatively — false positives are expected, false negatives are a correctness bug (P5). The narrow phase dispatches by shape-pair type: analytic routines for primitive pairs, SAT for convex polytopes, GJK/EPA as the general-convex fallback (ADR-08), producing ContactManifolds. The manifold cache matches new manifolds against last-frame manifolds by feature-id to carry over accumulated impulses for warm starting (P4, P12). The island manager partitions the contact/joint graph via union-find, excluding static bodies as bridges (I13), and schedules each island for independent solving. The constraint solver runs the sequential-impulse velocity pass (contacts and joints share one solver, P13), incorporating restitution and friction, then a separate NGS position-correction pass resolves residual penetration without touching velocity (P2, ADR-13). The sleeping manager applies per-body energy thresholds with island-level consensus (P8) after the solve. The CCD pass runs only for bodies flagged bullet, using conservative advancement to find time-of-impact and re-integrating the remainder of the step (P11). The query interface reuses the dynamic BVH for raycasts and overlap queries. The debug-draw seam and the determinism harness are both consumption points: the former is drawn by a renderer owned elsewhere, the latter drives the CI replay gate (§28).

6. Design Principles

P1. Iteration count is a documented accuracy dial, not a magic constant. Every stability or convergence claim in this document names the iteration count it holds at (default: 8 velocity, 3 position). Tradeoff: more iterations buy accuracy at linear cost. Violating it: silently changing SolverConfig.velocity_iterations in one scene invalidates every energy/penetration claim made elsewhere in this document for that scene.

P2. Position error is corrected by a soft, bounded position pass, never by teleporting a body. Teleporting injects an instantaneous, unbounded velocity discontinuity — energy from nowhere. Tradeoff: the NGS pass costs a second traversal of the constraint graph per step. Violating it: a "quick fix" that snaps a penetrating body out produces an energy spike visible as a stack popping apart on contact (I1, FM-4).

P3. The step is deterministic given (state, timestep, contact ordering); contact ordering is itself part of the specification. Tradeoff: canonical sorting of pairs costs a sort per step. Violating it: hash-map iteration order for contacts makes two runs of the identical scene diverge, breaking replay (I4, T9).

P4. Warm starting persists impulses by feature-id, not by pair-index. Pair indices are not stable across a broad-phase resort; feature-ids are. Tradeoff: feature-id computation and matching costs time per manifold. Violating it: warm start silently degrades to a cold start every frame, manifesting as soft, jittery contacts with no error thrown (FM-7).

P5. Broad phase is a filter, never a source of truth. False positives are cheap (the narrow phase rejects them); false negatives are a correctness bug — a missed contact is a missed collision. Tradeoff: a conservative (padded) broad-phase AABB costs extra candidate pairs. Violating it: tightening AABBs to save narrow-phase work reintroduces tunnelling-by-omission even at low speed.

P6. Every shape is described purely through a support-function contract. SAT and GJK/EPA both consume the same SupportFunction interface (§11); adding a new convex shape never touches the solver or the broad phase. Violating it: a shape-specific narrow-phase special case that bypasses the support-function contract creates a second, divergent code path that will silently miss edge cases the general path already handles.

P7. The solver only ever produces impulses that satisfy the constraint's inequality, never its violation. Contact normal impulses are unilateral (≥ 0, I8); friction impulses are bounded by the cone/pyramid (I9). Violating it: a negative accumulated normal impulse is not a "soft" contact, it is a solver defect that will pull bodies together.

P8. Sleeping is an island-level consensus, never a per-body shortcut. One awake body in an island keeps the entire island awake (P8, I5). Tradeoff: a single twitching body prevents an otherwise-settled 20-box stack from sleeping. Violating it: per-body sleeping lets a "sleeping" body sit inside a still-moving neighbor, producing an invisible, unresolved interpenetration that resurfaces as a pop when the neighbor eventually stops.

P9. A NaN is quarantined at first detection, never propagated. One body's NaN velocity, left unchecked, poisons every constraint it touches within one solver pass, then the whole island the next step. Enforced at the integrator boundary and the solver's post-iteration check (I6, I11).

P10. The default integrator is symplectic (semi-implicit Euler); any departure is a named, deliberate substitution. Explicit Euler's systematic energy gain and implicit Euler's per-step cost are both documented alternatives (ADR-05), never silent swaps.

P11. Continuous collision detection is opt-in per body. CCD cost is O(bullets × candidates); bodies not flagged bullet pay nothing for it (ADR-18). Violating it: enabling CCD globally is a straightforward but unbounded performance regression at scale (§30, §34).

P12. Manifold persistence degrades gracefully, never catastrophically. A manifold whose features fail to match across frames falls back to a fresh, un-warmed contact — never a crash, never a stale, wrong-normal contact carried forward. Tradeoff: an occasional one-frame softness at a manifold-matching failure.

P13. Contacts and joints share one constraint solver. A joint is a constraint with a fixed bias target; a contact is a constraint with a zero-or-positive bias. Unifying them under one iteration loop and one accumulator model means one performance budget and one place to fix convergence bugs (§19, §22).

P14. The timestep is an engine-wide constant, not a per-call parameter. Mixing timesteps within one run invalidates every stability and determinism claim that depends on a fixed dt (I10, P1, P3). World.step() accepts dt as an assertion target, not a free variable; a caller that varies it is asserting a new, undocumented simulation.

8. Domain Model

Rigid-body state. A body's state is the tuple (x, q, v, ω, m, I): position x ∈ R³, orientation quaternion q (unit, ‖q‖ = 1), linear velocity v ∈ R³, angular velocity ω ∈ R³ (world frame), mass m (or m⁻¹ = 0 for static/kinematic), and body-local inertia tensor I_local (a symmetric 3×3 matrix).

World-space inertia tensor.

I_world⁻¹ = R · I_local⁻¹ · Rᵀ,   R = mat3(q)

recomputed every step from the current orientation (Eberly, ch. 2).

Integration schemes, compared. Explicit Euler: v(t+dt) = v(t) + a(t)·dt, x(t+dt) = x(t) + v(t)·dt — uses the old velocity for position; systematically gains energy on oscillatory/constrained systems (unconditionally unstable for stiff constraints per Press et al., ch. 16). Semi-implicit (symplectic) Euler: v(t+dt) = v(t) + a(t)·dt, x(t+dt) = x(t) + v(t+dt)·dt — uses the new velocity for position; quasi-symplectic, bounded energy oscillation rather than systematic gain (Hairer, Lubich & Wanner, ch. 6). RK4: fourth-order accurate for smooth forces but does not respect the symplectic structure and is markedly more expensive per step; rejected as the default (ADR-05). This engine uses semi-implicit Euler exclusively in its core phases (P10).

Quaternion integration.

q(t+dt) = normalize( q(t) + 0.5 · dt · ω_quat · q(t) ),   ω_quat = (ωx, ωy, ωz, 0)

Renormalized every step (I7) to counter first-order integration drift (Eberly, ch. 4).

Constraint formulation. A constraint is C(x) = 0 (or ≥ 0 for inequalities); differentiating, Ċ = J·v, where J is the constraint Jacobian and v stacks both bodies' linear/angular velocities. The impulse magnitude enforcing the constraint in one solve:

λ = − (J·v + b) / (J · M⁻¹ · Jᵀ),   m_eff = 1 / (J · M⁻¹ · Jᵀ)
v' = v + M⁻¹ · Jᵀ · λ

where b is the constraint bias term (restitution target, joint drift correction, or the position-error bias in a soft formulation) and m_eff is the effective mass (Baraff & Witkin).

Sequential-impulse update with warm starting. Per velocity iteration, per contact point: compute relative velocity along the constraint direction, compute λ, accumulate λ_total = clamp(λ_total + λ, lo, hi) (I8, I9), apply only the delta λ_total_new − λ_total_old as the impulse. At the start of a step, the previous step's λ_total (matched by feature-id, P4) is applied immediately before iterating — this is warm starting (Catto 2005).

Friction cone and its pyramid approximation. The exact Coulomb cone is √(λ_t1² + λ_t2²) ≤ μ·λ_n. This engine uses the pyramid approximation — clamp each tangent axis independently: |λ_t1| ≤ μ·λ_n, |λ_t2| ≤ μ·λ_n — cheaper, anisotropic at the pyramid corners, accepted per ADR-14.

Restitution and the resting-contact special case. Target relative velocity along the normal after impact: v_n' = −e · v_n (e = restitution coefficient), but only when v_n exceeds a velocity threshold (restitution_velocity_threshold, e.g. 1.0 m/s); below threshold, restitution is treated as zero to suppress infinite-bounce jitter (Catto's resting-contact special case, ADR-15).

Baumgarte vs. soft-constraint (CFM/ERP) position stabilization. Baumgarte mixes a fraction β of positional error directly into the velocity constraint's bias: b = (β/dt)·C(x); simple but couples position error into velocity, risking energy injection at high β (Baumgarte 1972). The soft-constraint (CFM/ERP) formulation instead treats the constraint as a damped spring with an error-reduction parameter and a constraint-force-mixing term, decoupling stiffness from the velocity solve (Catto 2011). This engine's ADR-13 selects a third option — a separate NGS position-only pass — informed by both but coupling neither into the velocity solve.

Continuous collision detection: the time-of-impact condition. For body A moving at relative velocity v_rel toward B with current separation d(t), conservative advancement finds the largest t_advance such that d(t) − v_rel_bound · t_advance ≥ 0; TOI is reached when t_advance falls below a tolerance, or exceeds 1.0 (no impact this step) (Mirtich & Canny; Ericson ch. 9-adjacent material).

SAT Axis Enumeration (Convex Polytopes)

Step Action
1 Enumerate candidate separating axes: face normals of A, face normals of B, cross products of edge pairs (A-edge × B-edge)
2 For each axis, project both polytopes' vertices; compute the interval overlap
3 If any axis has zero or negative overlap, the polytopes are separated — stop, no contact
4 If all axes overlap, the minimum-overlap axis is the contact normal and its overlap the penetration depth
5 Classify the minimum axis as face-type (A or B) or edge-edge; dispatch to face-clipping (face-type) or edge-closest-point (edge-edge) manifold generation

Contact Manifold Structure and Persistence

A ContactManifold holds up to 4 ContactPoints per body pair, keyed by a ManifoldKey (canonical (BodyId, BodyId) pair plus shape-pair type). Each ContactPoint carries a feature_id (derived from the SAT/GJK witness features: vertex/edge/face indices on each shape). Persistence rule: at the start of a narrow- phase pass, new contact points are matched to the previous frame's points by feature_id; a match carries over normal_impulse and tangent_impulse for warm starting (I12); an unmatched new point starts cold; an old point with no match this frame is dropped.

Island Construction Rule

Union-find over the graph whose nodes are dynamic/kinematic bodies and whose edges are active contacts and joints; static bodies are never inserted as graph nodes — an edge to a static body terminates there rather than linking two dynamic components (I13). Each resulting component is one Island, solved independently.

Worked Numeric Example — Single 2-Body Contact, One Solver Iteration

Body A: mass 1 kg, v_A = (0, −2, 0) m/s (falling). Body B: static (m⁻¹ = 0). Contact normal n = (0, 1, 0), restitution e = 0.5, penetration = 0.01 m (below slop, so bias contribution from position is 0 this iteration). Relative velocity along normal: v_n = (v_A − v_B)·n = −2. Effective mass: m_eff = 1 / (1/m_A + 0) = 1 kg (B is static, contributes 0). Restitution bias: v_n magnitude (2 m/s) exceeds restitution_velocity_threshold (1 m/s), so target v_n' = −e·v_n = −0.5 × (−2) = 1.0 (bodies must separate at 1 m/s). Impulse: λ = −m_eff · (v_n − v_n') = −1 × (−2 − 1) = 3 N·s. Clamp: λ_total = max(0, 0 + 3) = 3 (I8, satisfied — no clamping needed here). Apply: v_A' = v_A + (λ/m_A)·n = (0, −2, 0) + (0, 3, 0) = (0, 1, 0) m/s — body A now moves away from B at 1 m/s, matching the restitution target exactly in one iteration because this is a single, uncoupled contact (no friction, no second body degrees of freedom involved).

Degenerate-Input Examples

  • Zero-area shape: a ConvexPolytope with 3 or fewer non-coplanar vertices has no well-defined face normal for SAT; narrow phase must detect this at load time and reject or degrade to a point/segment analytic case rather than run SAT on an empty face list.
  • Coincident points: two bodies with identical center positions and zero initial separation produce an undefined SAT/GJK direction on the first frame; the implementation must pick a canonical fallback axis (e.g., world-up) rather than propagate a zero-vector normalize (NaN, I6).
  • Infinite-mass pair: two static/kinematic bodies reporting a contact (a scene authoring error) must be dropped before island construction — solving a constraint between two m⁻¹ = 0 bodies produces m_eff = ∞, a divide-by-zero.
  • Deep initial overlap: a body spawned already deeply interpenetrating another (penetration far exceeding normal per-step correction capability) must have its position correction rate-limited (max_position_correction per iteration) rather than resolved in one step, which would otherwise inject a large one-frame impulse masquerading as a legitimate contact response.

Failure-Path Example

A scene loads a ConvexPolytope whose vertex list, due to a bad import, contains one vertex far outside the intended hull (a malformed-mesh scenario, see T2). Narrow phase's SAT step computes a face normal using that outlier vertex, producing a wildly incorrect separating-axis test that reports "no collision" against a body that is visibly overlapping. Detection: the conformance suite's degenerate-geometry fixture (§17 Phase 5 N.5) loads exactly this shape and asserts a bounded penetration depth; failing that assertion is the signal. Recovery: shape validation at load time (convex-hull sanity check, e.g., every face's vertices coplanar within tolerance) rejects the malformed shape before it reaches the solver, converting a silent wrong-answer into a load-time PhysicsError.

12. Phase 0 — Skeleton, Math Types, Determinism Harness and CI

12.1 Objectives

Establish the package skeleton (§10), the Vec2/Vec3/Quat/Mat3/Transform math types (§11), a fixed-step World.step(dt) stub that enforces I10, and a determinism harness that can replay a trivial scene and hash its state — before any physics exists, so every later phase inherits a working CI gate.

12.2 Detailed Implementation Steps

  1. Implement Vec3/Quat/Mat3 algebra per §11 signatures; unit-test against known identities (dot/cross anticommutativity, quaternion multiplication associativity) — ADR-03 fixes float64 throughout.
  2. Implement Transform composition and inversion.
  3. Implement RigidBody/BodyId allocation (monotonic, never reused, per §11).
  4. Implement World.step(dt) as a no-op pipeline that only enforces I10 (rejects a non-matching dt) and increments a step counter.
  5. Implement physics.determinism: a state-hash function over all body transforms/velocities, and a CLI harness that steps a scene N times and compares hashes across two independent runs (P3, I4 foundation).
  6. Wire CI (ADR-27): GitHub Actions matrix running unit tests and the determinism harness on a trivial one-body scene.

12.3 Deliverable

An importable physics package with working math types, an empty-pipeline World.step(dt), and a passing CI job that runs the determinism harness on a zero-gravity, zero-body scene and a one-static-body scene.

12.4 Acceptance Criteria

  • Vec3/Quat/Mat3 unit tests: 100% pass, including quaternion normalize round-trip within 1e-9 (float64 precision headroom against the 1e-6 I7 bound).
  • World.step(0.01) called after configuring dt=1/60 raises PhysicsError (I10 enforced from Phase 0 onward).
  • Determinism harness: two independent runs of fixtures/phase0_empty.json for 600 steps produce identical state hashes (bit-exact, same platform, §4).
  • CI matrix (Linux + macOS, pinned Python/NumPy) green on every commit to main.

12.5 Conformance Fixtures

  • conformance/replay/phase0_empty.json — zero bodies, 600 steps; expected: identical hash across 2 runs.
  • conformance/replay/phase0_one_static.json — one static body, 600 steps; expected: state unchanged (static bodies never integrate), identical hash.
  • tests/unit/test_quat.py::test_normalize_roundtrip — random unit quaternions, integrate zero angular velocity for 1000 steps, assert drift < 1e-9.

12.6 Pitfalls

  • Reusing BodyId after removal: breaks I11 quarantine tracking later; manifestation is a quarantine flag silently attaching to the wrong body. Root cause: naive free-list reuse. Debug method: assert monotonic allocation in a property test now, before any body-removal code exists. Signal: none yet (Phase 0 has no removal) — this is a preventive fixture, not a live bug.
  • Float32 creeping in via a NumPy default dtype: np.array([...]) defaults to float64 on most platforms but an explicit dtype=np.float32 copy-paste from an online example silently violates ADR-03. Debug method: a dtype assertion helper wrapping every NumPy array construction in physics.math. Signal: determinism harness passes locally but produces different hashes across CI runners with different default BLAS builds.
  • CI running on a single OS: hides platform-dependent float behavior until Phase 11. Root cause: convenience. Fix now, cheaply, while there's nothing to break.

12.7 Performance Concerns

Not yet meaningful (no bodies simulated at scale), but the state-hash function's cost (O(bodies)) must be excluded from StepStats step-time accounting so later performance fixtures aren't polluted by harness overhead (§30).

12.8 Edge Cases

  • World.step(dt) called with dt <= 0: rejected (I10 extension — zero and negative are non-physical, not just "wrong fixed value").
  • Empty scene (zero bodies): must still produce a stable, defined hash (not an exception) — the empty-scene fixture is the simplest possible determinism regression tripwire.

12.9 Failure Analysis

If the two-run determinism harness diverges even on an empty scene, the bug is in the harness or hashing itself (e.g., hashing an uninitialized memory region, or including a wall-clock timestamp by mistake) — this must be fixed before any other phase begins, since every later phase's CI gate depends on this harness being trustworthy.

12.10 Operational Notes

The CI job from this phase becomes the permanent gate (§26, §28); its runtime budget (target < 2 minutes for Phase 0's trivial fixtures) is a baseline against which later phases' growing conformance suite is measured for CI-time regression.

13. Phase 1 — Integrator and Free-Body Motion

13.1 Objectives

Implement semi-implicit Euler integration of a single free (unconstrained) body under gravity and applied forces, and validate it against closed-form analytic solutions — the first point where "correct" has a numeric, checkable answer.

13.2 Detailed Implementation Steps

  1. Implement force/torque accumulation and the per-step clear (P14: fixed dt only, enforced since Phase 0).
  2. Implement semi-implicit Euler velocity update: v += (F/m + gravity)·dt using the pre-update velocity for force integration, and position update using the post-update velocity (P10, ADR-05) — this ordering is the entire semi-implicit distinction from explicit Euler and must be tested explicitly.
  3. Implement quaternion integration and renormalization (§8 equations, I7).
  4. Implement linear/angular damping as an exponential per-step decay factor.
  5. Build the analytic-comparison fixtures: projectile motion (x(t) = x0 + v0·t + 0.5·g·t²) and a torque-free spinning body (angular momentum conserved).

13.3 Deliverable

A single dynamic body under gravity and an initial velocity follows the analytic projectile trajectory within tolerance; a torque-free spinning body's angular momentum is conserved within tolerance over 600 steps.

13.4 Acceptance Criteria

  • Projectile position error vs. analytic x(t) ≤ 0.1% of total displacement at t = 5s, dt = 1/60 (Press et al. ch. 16 truncation-error expectation).
  • Energy drift for a frictionless, gravity-free spinning body ≤ 1%/simulated second over 60s (I1, matching §4's bound, at SolverConfig defaults per P1).
  • Quaternion norm stays within 1e-6 of 1.0 for the entire 600-step run (I7).

13.5 Conformance Fixtures

  • conformance/analytic/projectile.json — v0=(5,10,0), g=(0,-9.81,0), 5s; expected: position matches closed form within 0.1%.
  • conformance/analytic/energy_drift_free_spin.json — torque-free body, nonzero initial angular velocity, 60s; expected: energy drift ≤ 1% (this is the fixture referenced by I1 and §4's energy-drift bound).
  • conformance/analytic/damping_decay.json — known linear damping coefficient; expected: velocity decays as the analytic exponential within 0.5%.

13.6 Pitfalls

  • Using pre-update velocity for position (explicit Euler by accident): manifestation is systematic energy gain, not loss; root cause is a copy-paste of the force-integration line into the position-integration step without swapping which velocity is read; debug method: the energy-drift fixture catches this immediately (I1 is directional — gain, not just any drift); signal: StepStats.total_kinetic_energy trending up monotonically; recovery: fix ordering, add a regression test asserting the ordering.
  • Forgetting quaternion renormalization: manifestation is slow orientation drift invisible over 10 steps but visible over 10,000; root cause: I7 not enforced; debug method: a long-run (10,000-step) free-spin fixture; signal: StepStats-equivalent quat-norm sample trending away from 1.0.
  • Damping applied before force integration: subtly wrong decay curve; root cause: ordering; debug method: compare against the closed-form exponential fixture.

13.7 Performance Concerns

Single-body integration is O(1); this phase's performance budget is dominated by the fixture harness, not the engine. Establish the per-body integration cost baseline here (§30 M-series targets reference this number).

13.8 Edge Cases

  • Zero mass with body_type=Dynamic (authoring error, not Static): must raise PhysicsError rather than divide by zero computing inv_mass.
  • Extremely large initial velocity (numerical-overflow adjacent): position update must not silently produce inf; a magnitude sanity check logs a warning (this becomes the velocity-clamp discussed in FM-4 later).

13.9 Failure Analysis

A body that "explodes" (velocity trending to inf) at this phase, with no constraints yet in the system, isolates the bug to the integrator itself — there is no solver to blame yet. This is the cheapest point in the whole build to catch an integration-order bug, which is exactly why Millington's phased build order (ch. 3–5) puts the integrator before any collision code.

13.10 Operational Notes

The energy-drift fixture from this phase is re-run, unmodified, at every later phase's conformance pass (§28) as a regression tripwire — a later phase that somehow perturbs the integrator (e.g., a careless refactor) is caught here before it's confused with a solver bug.

14. Phase 2 — Shapes, AABBs and the Support-Function Contract

14.1 Objectives

Implement the Shape variants (Sphere, Box, Capsule, ConvexPolytope, Plane) and the SupportFunction contract (P6), plus per-shape AABB computation, without yet wiring any broad or narrow phase — geometry in isolation, testable in isolation.

14.2 Detailed Implementation Steps

  1. Implement Sphere, Box, Capsule shapes and their support(d) functions per the §8 support-function table.
  2. Implement ConvexPolytope with load-time hull validation (coplanarity check per face, rejecting the degenerate zero-area case from §8) — this is where DegenerateShapeError is first raised.
  3. Implement Plane as an analytic-only static shape, explicitly excluded from the SupportFunction contract (§8).
  4. Implement per-shape AABB computation from the support function (AABB extent along each axis = support in ± that axis direction) — this reuses P6's contract rather than a shape-specific special case.
  5. Implement MassData/InertiaTensor computation per shape (§8 equations: box, sphere formulas; Eberly ch. 2) and the parallel-axis theorem for future compound use.

14.3 Deliverable

Every core shape type constructs, validates, computes a correct AABB, and reports mass/inertia matching the closed-form formulas for that primitive.

14.4 Acceptance Criteria

  • Sphere/Box/Capsule AABB matches the analytic bound within floating-point epsilon (1e-9) for 1,000 randomized orientation/position samples.
  • Box inertia tensor matches I_x = m(b²+c²)/12 etc. within 1e-9 relative error.
  • Malformed ConvexPolytope (fixture: 3 collinear points) raises DegenerateShapeError at construction, not at first collision query.

14.5 Conformance Fixtures

  • conformance/degenerate/zero_area_polytope.json — 3 collinear vertices; expected: DegenerateShapeError at load.
  • tests/unit/test_shapes.py::test_aabb_randomized — 1,000 randomized transforms per shape type; expected: AABB contains all support-sampled extreme points.
  • tests/unit/test_mass_data.py::test_box_inertia_analytic — box vs. formula.

14.6 Pitfalls

  • AABB computed from vertex list directly instead of the support function: works for ConvexPolytope but silently breaks P6 (a special case that will diverge from Capsule's support-based AABB later). Debug method: code review checklist item, not a runtime signal — this is a design discipline pitfall, not a numeric one.
  • Parallel-axis theorem sign error: manifestation is a compound body (used starting Phase 5+) rotating around the wrong effective axis; root cause: I_offset = I_local + m·(d²·Identity − d⊗d) term computed with a transposed outer product. Debug method: analytic fixture (sphere on a stick, §8-style worked case) compared to hand-computed expectation.
  • Hull validation too strict: rejecting a legitimately thin but valid polytope (e.g., a flat plank) as "zero-area" when it's actually a thin box. Fix: coplanarity/degeneracy check operates on triangle area, not bounding extent.

14.7 Performance Concerns

AABB recomputation is O(shapes) per body per step (Phase 3+ onward); this phase establishes that cost as a per-shape constant, budgeted against the broad-phase update cost in §30 (M-series targets).

14.8 Edge Cases

  • A Capsule with zero half-height degenerates to a Sphere; support function must still return correct results (not divide by a zero segment length).
  • A ConvexPolytope with exactly 4 non-coplanar vertices (a tetrahedron, the minimal valid 3D convex hull) must validate successfully — the boundary case just above the rejected 3-collinear-point case.

14.9 Failure Analysis

A wrong AABB (too tight) manifests two phases later as a missed broad-phase pair (P5 violation) — this phase's fixtures exist specifically to catch that class of bug before broad phase exists to obscure its origin.

14.10 Operational Notes

Shape validation errors (DegenerateShapeError) are the first line of defense described in §24's T2 (malicious/malformed mesh) and are exercised again by the fuzzer in Phase 11 (§23) against a much larger, adversarial input space.

15. Phase 3 — Broad Phase: Spatial Hash, Then Dynamic BVH

15.1 Objectives

Implement the BroadPhase protocol (§11) with two backends — a spatial hash (simple, first) and a dynamic BVH (the production-path promotion, ADR-07) — and validate both against a brute-force O(n²) pair list for correctness before either is trusted for performance.

15.2 Detailed Implementation Steps

  1. Implement SpatialHash: uniform-cell hashing of padded AABBs (P5 — padding makes false positives cheap and expected), producing a candidate PairKey set per update.
  2. Implement DynamicBvh: a binary tree of fattened AABBs with refit-and- rotate updates on proxy movement (Gottschalk et al. 1996's hierarchy construction lesson, adapted to a dynamic/incremental setting rather than OBBTree's static build).
  3. Implement canonical PairKey ordering and the pre-solve sort (ADR-19) — this is the first point where I4's contact-ordering determinism becomes real, since pair order feeds narrow phase next.
  4. Cross-validate: for a battery of randomized scenes, assert SpatialHash, DynamicBvh, and a brute-force O(n²) reference all report the identical set of overlapping pairs (order may differ pre-sort; the set must match).
  5. Benchmark both backends against the studied sweep-and-prune alternative (§8 comparison table) to confirm the ADR-07 crossover point empirically (feeds §34's back-of-envelope numbers).

15.3 Deliverable

A BroadPhase implementation (both backends) that produces a correct, conservative candidate-pair set for scenes up to 10,000 static + 1,000 dynamic proxies, with the BVH backend selected as the default per ADR-07.

15.4 Acceptance Criteria

  • Pair-set equivalence with brute-force O(n²) reference: 100% match (no false negatives, P5) across 50 randomized scene fixtures.
  • DynamicBvh query cost: p95 ≤ log2(n) × 200ns for n = 10,000 proxies (§4).
  • Broad-phase update cost for 1,000 moving proxies ≤ 2ms (contributes to the 16ms step budget, §4).

15.5 Conformance Fixtures

  • conformance/replay/broadphase_bruteforce_diff.json — 50 randomized scenes; expected: zero false negatives vs. brute force (a false negative here is a P5 violation and fails the build).
  • benchmarks/bench_broadphase.py — spatial hash vs. BVH vs. SAP at n = {100, 1000, 10000}; expected: crossover point recorded and compared against the §34 derivation.

15.6 Pitfalls

  • Unpadded AABBs: a body moving fast enough within one step exits its broad-phase AABB before the next update, producing a false negative (P5 violation) invisible until Phase 10's CCD work reveals it. Debug method: this phase's fixtures should include a fast-moving body specifically to catch this early, even though CCD proper isn't built yet.
  • BVH refit without rotation: a BVH that only refits (grows) node bounds without ever rebalancing degrades to O(n) query cost after sustained churn. Signal: query-latency p99 (§4) creeping up over a long-running soak test (§28) even though body count is constant.
  • Hash-set iteration for pair output: violates I4/ADR-19 immediately — the canonical sort must be applied before pairs leave this stage, not left for narrow phase to assume.

15.7 Performance Concerns

This is the first phase where O(n²) vs. O(n log n) actually matters (§31); the brute-force reference is kept only as a correctness oracle, never as a production path past n ≈ 200 (documented in the benchmark harness).

15.8 Edge Cases

  • Coincident AABBs (two bodies spawned at the exact same position): must produce a valid pair, not a degenerate hash-cell collision that's silently dropped.
  • A proxy that moves so far in one step that its BVH refit requires re-inserting rather than adjusting in place — the implementation must detect this (movement exceeds fattening margin) and re-insert rather than silently leave a stale bound.

15.9 Failure Analysis

A missed pair here is invisible until narrow phase or a much later CCD fixture reveals a tunnelling-like symptom with no CCD explanation — the brute-force differential fixture (15.5) exists specifically so this class of bug is caught at its source, not three phases downstream.

15.10 Operational Notes

StepStats gains its first two real counters this phase: candidate-pair count and broad-phase update time, both tracked per §26's operational metrics and gated by §30's M-series performance targets.

16. Phase 4 — Narrow Phase for Primitive Pairs

16.1 Objectives

Implement analytic narrow-phase routines for the primitive shape pairs (sphere-sphere, sphere-box, sphere-capsule, sphere-plane, capsule-capsule, capsule-plane, box-plane), producing single- or dual-point ContactManifolds, ahead of the general SAT/GJK-EPA machinery (ADR-08's cheap-first dispatch).

16.2 Detailed Implementation Steps

  1. Implement the shape-pair dispatch table (ADR-08) keyed by (kind_a, kind_b), normalized so (Sphere, Box) and (Box, Sphere) route to one routine with argument order handled internally.
  2. Implement sphere-sphere: center distance vs. radius sum, analytic normal and single contact point.
  3. Implement sphere-box, sphere-capsule: closest-point-on-shape routines (Ericson ch. 5), comparing to sphere radius.
  4. Implement box-plane, capsule-plane: analytic half-space penetration tests against each shape's extreme points along the plane normal (using the support function, P6, so Plane's exclusion from the contract doesn't force a special AABB path elsewhere).
  5. Assign feature_ids even for analytic single-point contacts (§8 persistence rule applies uniformly, P4) so warm starting (Phase 8) works without a special case for primitive pairs.

16.3 Deliverable

All primitive shape pairs produce correct manifolds (normal, depth, feature-id) validated against hand-computed geometric expectations.

16.4 Acceptance Criteria

  • Sphere-sphere overlap depth accurate to 1e-9 relative error across 1,000 randomized configurations.
  • Sphere-box closest-point matches brute-force sampling (10,000 sample points on box surface) within 1e-6.
  • Box-plane and capsule-plane penetration depth exact (analytic, zero tolerance beyond float64 rounding) for axis-aligned test cases.

16.5 Conformance Fixtures

  • conformance/analytic/sphere_sphere_overlap.json — 1,000 randomized pairs; expected depth within 1e-9.
  • conformance/analytic/sphere_box_closest_point.json — brute-force cross-check, 10,000 samples; expected within 1e-6.
  • conformance/degenerate/coincident_centers.json — two spheres at identical centers (§8 degenerate-input example); expected: a canonical fallback normal (world-up), not a NaN from normalizing a zero vector (I6).

16.6 Pitfalls

  • Normalizing a zero-length vector when two shapes are exactly coincident: produces NaN, violating I6 immediately. Root cause: missing the degenerate-input guard from §8. Debug method: the coincident-centers fixture (16.5) is the direct regression test. Signal: StepStats.nan_quarantine_count incrementing on a scene with no physically unusual setup.
  • Wrong closest-point-on-box formula for a point inside the box: sphere centers that start inside a box (deep initial overlap, §8) need a different branch (project to nearest face) than centers outside (clamp to box extents); conflating the two produces a wrong normal direction exactly when the contact matters most (deep penetration).
  • Feature-id collisions across unrelated pairs: if feature-ids are computed from raw memory addresses or array indices rather than a stable shape-local encoding, two different body pairs can produce identical feature-ids, corrupting Phase 8's warm-start matching (P4 violation).

16.7 Performance Concerns

Analytic routines are O(1) per pair and dominate narrow-phase cost at low body counts; this phase's fixtures establish the per-pair-type cost baseline that SAT (Phase 5) and GJK/EPA (Phase 6) are compared against in §30.

16.8 Edge Cases

  • Sphere exactly tangent to a plane (depth exactly 0): must not oscillate between "touching" and "not touching" across float rounding — a small tolerance band (penetration_slop-adjacent) prevents contact-creation flicker.
  • Capsule with half-height 0 (degenerates to sphere, per Phase 2): capsule- plane routine must handle this without a divide-by-zero on segment length.

16.9 Failure Analysis

A wrong analytic normal (e.g., box-plane using the box's local up axis instead of the world-transformed one) manifests as a body appearing to collide correctly at identity orientation but incorrectly the moment it's rotated — the randomized-orientation fixtures in 16.5 are structured specifically to catch orientation-dependent bugs, not just position-dependent ones.

16.10 Operational Notes

The dispatch table built here is the single seam SAT (Phase 5) and GJK/EPA (Phase 6) plug into; no later phase should need to modify this phase's dispatch mechanism, only add rows to it (ADR-08).

17. Phase 5 — SAT for Convex Polytopes and Manifold Generation

17.1 Objectives

Implement the Separating Axis Theorem for convex-polytope pairs (including box-box as the common case) with face-clipping multi-point manifold generation, resolving the single-point-contact tipping problem analytic routines can't handle for flat-face-on-flat-face resting contact.

17.2 Detailed Implementation Steps

  1. Implement the SAT axis-enumeration procedure exactly per the §8 decision table (Ericson, ch. 4-5 lineage) and ADR-08's SAT-for-polytopes dispatch: face normals of A, face normals of B, edge-cross-edge axes.
  2. Implement per-axis interval projection and overlap computation; track the minimum-overlap axis and its magnitude.
  3. Classify the minimum axis as face-type or edge-edge (§8); for face-type, select reference face (on the body whose face normal is the minimum axis) and incident face (most anti-parallel face on the other body).
  4. Implement face clipping: clip the incident face's polygon against the reference face's four side planes (Sutherland-Hodgman-style clipping, named as a step, not transcribed as code, per the no-code rule), producing up to 4 contact points with per-point depth along the reference normal.
  5. Implement edge-edge closest-point contact generation for the edge-type minimum axis case (a single contact point, not clipped).
  6. Assign feature-ids from (face index, vertex/edge index) pairs so Phase 8's warm-start matching has a stable, collision-resistant key (fixing the Phase 4 pitfall class at its most complex source).

17.3 Deliverable

Box-box and general convex-polytope pairs produce multi-point manifolds; a 10-box stack rests without single-point tipping.

17.4 Acceptance Criteria

  • Box-box SAT overlap axis matches brute-force separating-axis search within 1e-9 across 1,000 randomized orientation pairs.
  • Face-clipped manifold point count: exactly 4 for face-on-face box contact at identity-ish relative orientation (within 5° of parallel faces).
  • 10-box stack (fixture box_stack_10.json): linear-velocity RMS < 0.01 m/s by t = 5s using this phase's manifolds alone (velocity solver stubbed to a trivial projection for this phase's isolated test, full solver arrives Phase 7).

17.5 Conformance Fixtures

  • conformance/analytic/sat_box_box_axis.json — 1,000 randomized pairs vs. brute-force axis search; expected match within 1e-9.
  • conformance/degenerate/thin_box_clip.json — a box with one dimension near zero (near-degenerate, not rejected at Phase 2 since it's not literally zero-area); expected: clipping still produces a valid, non-NaN manifold.
  • conformance/replay/box_stack_10.json — 10-box stack, 300 steps; expected: manifold point count stable at 4 per face-contact once settled.

17.6 Pitfalls

  • Clipping in the wrong reference frame: performing the clip in one body's local frame while the other face's vertices are still in world frame produces garbage points; root cause: inconsistent frame bookkeeping in a procedure with many intermediate transforms. Debug method: assert all clip-stage vertices are in world frame at the start of face-clipping, as a cheap runtime check during development.
  • Wrong reference-face selection near-tie: when two candidate axes have nearly equal overlap (a box balanced exactly on an edge), reference-face selection can flip between faces frame-to-frame under float noise, producing manifold-matching failure (I12) and warm-start loss (FM-7) even though the physical configuration is stable. Mitigation: a small hysteresis margin favoring the previous frame's reference face when overlap values are within tolerance.
  • EPA returning a wrong normal on deep overlap is a Phase 6 pitfall, but its SAT analog appears here too: at deep initial overlap (§8 degenerate example), the minimum-overlap axis can be numerically ambiguous between two nearly-equal axes, producing a normal that's technically valid but visually wrong (e.g., pushing a box sideways instead of up). Debug method: the deep-overlap degenerate fixture (§8) exercised specifically against SAT here, not just GJK/EPA in Phase 6.

17.7 Performance Concerns

SAT is O(faces_A × faces_B + edges_A × edges_B) per pair; for boxes this is constant (6 faces, 3 unique edge directions each ⇒ 15 axes, matching the classical box-box SAT axis count), but general convex polytopes with many faces make this phase's cost scale with hull complexity — informing the GJK/EPA fallback decision in ADR-08 for high-vertex-count hulls.

17.8 Edge Cases

  • Exactly-parallel reference and incident faces (the common resting-contact case): clip must produce the full 4-point rectangle intersection, not degenerate to fewer points from a boundary-inclusive/exclusive clipping bug.
  • A polytope pair touching only at a single vertex (vertex-vertex contact): SAT's face/edge classification must still produce a valid single-point manifold rather than failing to classify the minimum axis at all.

17.9 Failure Analysis

A stack that tips over slowly (not immediately) is diagnostic of a manifold-point-count bug specifically (dropping to 1-2 points intermittently) rather than a solver bug — this phase's box_stack_10.json fixture isolates that class by stubbing the solver to a trivial normal-only projection, so a failure here cannot be blamed on Phase 7's not-yet-built sequential-impulse solver.

17.10 Operational Notes

Face-clipping's intermediate polygon (before reduction to ≤4 points) is exposed via tools/manifold_inspector.py (§10) for offline debugging of manifold shape, used again in Phase 9's jitter-diagnosis runbook (§26).

18. Phase 6 — GJK/EPA for General Convex Shapes

18.1 Objectives

Implement GJK (overlap/distance) and EPA (penetration depth) as the general fallback for convex shape pairs not covered by analytic routines or SAT (ADR-08), consuming the same SupportFunction contract (P6) so no shape- specific narrow-phase code is needed.

18.2 Detailed Implementation Steps

  1. Implement the Minkowski-difference support function support_AB(d) = support_A(d) - support_B(-d) (Gilbert, Johnson & Keerthi
    1. built directly on the SupportFunction protocol from Phase 2.
  2. Implement GJK's simplex-evolution loop per the §8 decision table: pick initial direction, compute support point, test if it passes the origin, reduce the simplex to its closest Voronoi feature, repeat, capped at 32 iterations (van den Bergen 1999's robustness guidance).
  3. Implement simplex-reduction logic for point/line/triangle/tetrahedron cases explicitly (named steps, not transcribed code).
  4. Implement EPA: given GJK's terminating tetrahedron (containing the origin), iteratively find the closest polytope face, expand by the support point in that face's direction, re-triangulate, until no further expansion exceeds tolerance (van den Bergen 2001), capped at 32 iterations.
  5. Derive witness points on A and B from the final GJK/EPA state to seed ContactPoint.local_a/local_b and a feature-id from the terminating simplex/polytope feature indices.
  6. Wire GJK/EPA as the dispatch fallback (ADR-08) for any shape pair not matched by an analytic or SAT route, and as a differential cross-check against SAT for box-box pairs in conformance testing (agreement within tolerance validates both implementations against each other).

18.3 Deliverable

Arbitrary convex ConvexPolytope pairs (and any primitive pair, as a slower path) resolve correctly via GJK/EPA, validated against SAT on shared cases and against analytic solutions on primitive cases.

18.4 Acceptance Criteria

  • GJK overlap/no-overlap classification matches SAT's classification on 1,000 randomized box-box pairs, 100% agreement.
  • EPA penetration depth matches SAT's overlap-axis depth within 1% on the same 1,000 box-box pairs (differential cross-validation, not just each algorithm self-consistency).
  • GJK terminates within 32 iterations on 99.9% of a 10,000-case randomized convex-polytope battery; the remaining 0.1% terminate via the iteration cap and are logged, not crashed (§8 termination table).
  • EPA normal error vs. analytic ground truth ≤ 1° on axis-aligned deep-overlap test cases.

18.5 Conformance Fixtures

  • conformance/differential/gjk_vs_sat_boxbox.json — 1,000 pairs; expected: overlap classification 100% agreement, depth within 1%.
  • conformance/degenerate/near_degenerate_simplex.json — nearly coplanar/ collinear support points (a thin sliver polytope); expected: GJK terminates within the iteration cap, does not loop forever (this is the direct regression fixture for the "GJK fails to terminate" pitfall).
  • conformance/degenerate/deep_overlap_epa_normal.json — two boxes overlapping by 80% of their extent; expected: EPA normal within 1° of the analytically-known correct axis.

18.6 Pitfalls

  • GJK failing to terminate on a near-degenerate simplex: a step-time spike (or an infinite loop without the cap); root cause: closest-point-to- origin on a nearly coplanar triangle is numerically unstable; debug via the near-degenerate-simplex fixture (18.5) plus iteration-count telemetry; signal: GJK iteration count approaching the cap on unremarkable pairs; recovery: the iteration cap plus a documented "assume no overlap" fallback.
  • EPA returning a wrong normal on deep overlap: a body ejected sideways instead of upward; root cause: the GJK tetrahedron handed to EPA doesn't robustly contain the origin at extreme overlap, so the first "closest face" is arbitrary; debug via the deep-overlap fixture (18.5) against a known-correct axis; signal: ejection direction inconsistent across repeated runs of the identical scene (an I4 smell if it varies at all).
  • Scale-dependent epsilon (the documented Bullet lesson, §5): a fixed absolute tolerance that works at meter-scale fails at millimeter- or kilometer-scale; mitigation: tolerance scaled to the pair's combined bounding-radius, documented as a supported-scene-scale assumption.

18.7 Performance Concerns

GJK/EPA is markedly more expensive per pair than SAT or analytic routines (§30 M-series target: GJK/EPA pair cost ≤ 10× the analytic sphere-sphere cost); it is the documented fallback, not the default, path (ADR-08) — a scene that routes most pairs through GJK/EPA is a modeling mismatch (too many general convex hulls, too few primitives), not a performance bug.

18.8 Edge Cases

  • Two shapes with a shared, exactly-touching face after GJK/EPA classifies them as "overlapping by epsilon" — the boundary between "just touching" and "just separated" must be handled by the same tolerance-slop logic used elsewhere (§8 contact-creation flicker), not a GJK-specific special case.
  • A sphere passed through GJK/EPA (rather than the Phase 4 analytic route, as a differential cross-check) must produce the same answer as the analytic formula within tolerance — this is itself a standing conformance fixture, not a one-time check.

18.9 Failure Analysis

An EPA normal that varies between two runs of the same frozen scene is a determinism bug (I4) hiding inside a geometry algorithm, not the solver — easy to misattribute. The differential fixture (18.5) pins this down by running EPA twice on frozen input and diffing the normal bit-for-bit, isolated from any solver or integrator interaction.

18.10 Operational Notes

GJK/EPA iteration counts are added to StepStats (mean and max per step) so a production scene's narrow-phase cost profile is visible in the same telemetry used for broad-phase counters (§26), enabling a quick "is this scene GJK/EPA-heavy" diagnosis without a profiler.

19. Phase 7 — Sequential-Impulse Velocity Solver With Restitution

19.1 Objectives

Implement the sequential-impulse velocity solver (Catto 2009, ADR-10) for contacts, including the restitution bias and its resting-contact special case (ADR-15), replacing the stubbed trivial-projection solver used to isolate Phases 5–6's manifold fixtures.

19.2 Detailed Implementation Steps

  1. Implement VelocityConstraint construction per manifold point: Jacobian (§8 contact-constraint form), effective mass, and bounds (I8: lower=0, upper=∞ for the normal constraint).
  2. Implement the restitution bias term: compute v_n at contact-generation time (pre-solve), apply the velocity-threshold gate (ADR-15), and set the constraint's bias accordingly.
  3. Implement the per-iteration sequential-impulse update (§8 equations): compute relative velocity, compute and clamp the accumulated impulse, apply only the delta impulse to both bodies' linear/angular velocity.
  4. Implement SolverConfig.velocity_iterations (default 8, P1) as the outer loop count; implement the canonical constraint-ordering pass (ADR-19) immediately before the loop.
  5. Wire the whole velocity solve into World.step's pipeline at stage 7 (§8 step-pipeline table), operating per-island (islands are still trivial — one island per connected pair — until Phase 9's full island manager).

19.3 Deliverable

Two colliding bodies resolve via sequential impulses with correct restitution behavior; the Phase 5 box-stack fixture now uses the real solver instead of the trivial stub and remains stable.

19.4 Acceptance Criteria

  • Elastic two-sphere collision (e=1.0): momentum conserved within 1% of analytic (§4 restitution accuracy target).
  • Restitution-threshold gating verified: a resting contact (v_n below threshold) produces zero bounce over 300 steps, not a decaying infinite bounce (the §8 worked numeric example's exact scenario, now run for real).
  • box_stack_10.json (from Phase 5) re-run with the real solver: linear- velocity RMS < 0.01 m/s by t = 5s at 8 velocity iterations (P1-scoped claim).

19.5 Conformance Fixtures

  • conformance/analytic/elastic_collision_momentum.json — two spheres, e=1.0, head-on; expected: momentum conserved within 1%.
  • conformance/analytic/resting_contact_no_bounce.json — box resting on plane, low approach velocity; expected: zero visible bounce over 300 steps.
  • conformance/replay/box_stack_10_real_solver.json — same scene as Phase 5's fixture, real solver; expected: RMS < 0.01 m/s by t = 5s.

19.6 Pitfalls

  • Forgetting to clamp the accumulated impulse (I8): a negative accumulated normal impulse pulls bodies together instead of pushing; manifestation is bodies accelerating into each other on "contact"; debug method: assert normal_impulse >= 0 after every accumulation as a standing invariant check (I8), not just a one-time test.
  • Restitution bias applied every iteration instead of once per manifold point per step: re-adding the bias term each of the 8 iterations amplifies restitution far beyond the intended coefficient; root cause: confusing "bias is part of the per-iteration formula" with "bias is recomputed per iteration" — it is computed once from pre-solve velocity and held fixed across the iteration loop.
  • Restitution threshold using post-solve velocity: must gate on the pre-solve approach velocity (the velocity that existed before this step's solve began), not a mid-iteration value, or the gate becomes self-referential and unstable.

19.7 Performance Concerns

Solver cost is O(contacts × velocity_iterations) per step (§30, §34); this phase establishes the per-constraint-solve cost baseline in nanoseconds, directly feeding the §34 back-of-envelope max-contacts derivation.

19.8 Edge Cases

  • Simultaneous restitution and near-zero mass ratio extremes (a light body bouncing off a heavy one): effective mass computation must not lose precision catastrophically (float64 headroom is generous here, but the fixture exists to confirm it, not assume it).
  • A manifold with fewer than the previous frame's point count (feature matching partially fails): the solver must handle a variable point count per manifold per step without indexing past the array bounds.

19.9 Failure Analysis

Bodies gaining energy on contact (bouncing higher than restitution predicts) isolates to this phase's bias-application-per-iteration pitfall specifically; distinguishing it from Phase 1's integrator energy-gain bug is done by checking whether the gain only appears at contact events (this phase) vs. continuously (Phase 1) — a diagnostic distinction worth stating explicitly since both present as "energy goes up."

19.10 Operational Notes

StepStats.velocity_iterations_used is introduced this phase (even though it's currently always equal to the configured count — early termination on convergence is a documented non-goal in the core phases, since a fixed iteration count is what every stability claim in this document assumes, P1).

20. Phase 8 — Friction and Warm Starting

20.1 Objectives

Implement Coulomb friction (pyramid approximation, ADR-14) coupled to the normal impulse, and warm starting (Catto 2005, P4/ADR-12) keyed by feature-id, closing the gap between "solved" and "stable at low iteration counts."

20.2 Detailed Implementation Steps

  1. Implement two tangent-direction computation from the contact normal via a stable arbitrary-basis construction (never degenerate for any normal direction, including axis-aligned ones).
  2. Implement per-tangent VelocityConstraints with bounds [-mu * normal_impulse, +mu * normal_impulse] (I9), recomputed each iteration from the current accumulated normal impulse (the pyramid bound moves as the normal impulse converges).
  3. Implement the friction solve pass interleaved with the normal-impulse pass per manifold point per iteration (Catto 2009's ordering: normal, then friction, same iteration).
  4. Implement warm starting: at the start of the velocity solve (before the iteration loop), apply each manifold point's previous-step normal_impulse/tangent_impulse_1/tangent_impulse_2 (matched via feature_id, I12) directly as an initial impulse application.
  5. Implement the manifold-matching step (§8 persistence rule) as a discrete pipeline stage (stage 5 in the §8 step-pipeline table) ahead of island construction, so warm-start data is available before the solver runs.

20.3 Deliverable

An inclined-plane friction fixture slides at the analytically-predicted angle; the box-stack fixture remains stable with friction enabled at the default 8 iterations, without the artificially higher iteration count a frictionless stack might tolerate.

20.4 Acceptance Criteria

  • Inclined-plane slide-threshold angle within 2° of atan(mu) for mu ∈ {0.2, 0.5, 0.8} (§4 friction accuracy target).
  • Warm-started box stack (box_stack_10.json, re-run) settles to RMS < 0.01 m/s by t = 3s (faster than Phase 7's cold-start t = 5s bound — the quantified warm-starting improvement, Catto 2005's central claim, made concrete here).
  • Cold-start-vs-warm-start differential fixture: identical final resting state (within tolerance) but measurably different convergence-iteration count to reach it.

20.5 Conformance Fixtures

  • conformance/analytic/inclined_plane_friction.json — mu ∈ {0.2,0.5,0.8}; expected: slide angle within 2° of atan(mu).
  • conformance/replay/box_stack_10_warm_start.json — same scene, warm start enabled; expected: settle time ≤ 3s vs. Phase 7's 5s cold-start baseline.
  • conformance/replay/warm_start_vs_cold_start_diff.json — same scene, two solver configs; expected: converged state matches within tolerance, warm start's per-step max-penetration trace is uniformly lower or equal.

20.6 Pitfalls

  • Recomputing tangent basis every iteration instead of once per manifold point per step: causes the tangent directions to "wobble" relative to each other across iterations if the basis-construction formula isn't perfectly stable, producing spurious energy in the tangential plane. Fix: compute tangents once, at manifold-generation time, hold fixed for the step's iteration loop.
  • Friction bound using the previous iteration's normal impulse instead of the current one: a one-iteration lag in the pyramid bound understates available friction right when the normal impulse is still converging (early iterations), manifesting as a box appearing to slide slightly at step start even at high friction coefficients — subtle, only visible in a per-iteration trace, not the final state.
  • Manifold-matching failure causing warm-start loss and visible softness (the class named in the phase arc): when feature-ids fail to match across frames (e.g., because Phase 5's reference-face hysteresis wasn't implemented and the reference face flips), warm start silently falls back to cold every frame, and a stack that should be rigid looks slightly springy. Debug method: StepStats.manifold_match_rate (I12's telemetry) dropping below ~95% on an otherwise-static scene is the direct signal.

20.7 Performance Concerns

Friction roughly doubles the per-manifold-point solver cost (two extra constraints per point); warm starting reduces the effective iteration count needed for a given accuracy, partially offsetting that cost — both effects are measured together in this phase's benchmark and feed §30's solver-cost model.

20.8 Edge Cases

  • A contact normal exactly aligned with a coordinate axis: the arbitrary- tangent-basis construction must not degenerate (a naive cross(normal, world_up) fails when normal ≈ world_up) — use a conditional fallback axis.
  • Warm-starting a manifold point whose stored impulse now exceeds the current frame's friction bound (normal impulse dropped since last frame): the applied warm-start impulse must be clamped to the current bound before use, not applied unclamped and corrected only on the first iteration.

20.9 Failure Analysis

A stack that is stable when warm-started from a cold boot (first ever run) but destabilizes after a save/load cycle (§27: warm-start state is explicitly not persisted, only recomputed) is expected behavior, not a bug — one frame of reduced convergence quality after load is a documented, accepted cost (§11 manifold annotation), distinguishable from a real regression by checking whether stability recovers within a few steps.

20.10 Operational Notes

StepStats.manifold_match_rate becomes a standing dashboard metric (§26) from this phase forward — it is the earliest, cheapest signal for the "warm-start loss" failure class (FM-7) across all later phases, including production scenes far more complex than this phase's fixtures.

21. Phase 9 — Position Correction, Islands and Sleeping

21.1 Objectives

Implement the NGS position-correction pass (ADR-13), the full island manager (union-find excluding static bridges, I13), and island-level sleeping consensus (P8) — closing out the core single-threaded simulation loop.

21.2 Detailed Implementation Steps

  1. Implement PositionConstraint construction from each manifold point: current penetration depth (recomputed post-position-integration, since position has moved since the manifold was generated), and max_correction (a per-iteration cap, §8 deep-overlap handling).
  2. Implement the NGS position solve: iterate position_iterations (default 3, P1) times, each iteration recomputing depth and applying a bounded, velocity-untouched positional correction along the contact normal (P2 — never teleport; the correction is bounded and iterative, not instantaneous).
  3. Implement the island-construction union-find exactly per the §8 rule: dynamic/kinematic bodies are graph nodes, static bodies terminate an edge rather than linking components (I13) — this is the direct fix for the "static body bridges two islands" defect class documented in the source material this blueprint supersedes.
  4. Implement the sleep state machine (§8 table): per-body velocity-threshold timers feeding an island-level AllAwake → Settling → Asleep consensus (P8), and the wake path (Asleep → AllAwake on any impulse exceeding wake_impulse_threshold, I5).
  5. Wire sleeping bodies to skip both integration and solving entirely (I14) — verified by a CPU-time-by-state profile, not just a state-flag check.

21.3 Deliverable

The box_stack_10.json fixture settles, sleeps, and consumes zero solver CPU while asleep; a static body bridging two separate stacks correctly keeps them as two islands, not one.

21.4 Acceptance Criteria

  • Max penetration after the position pass ≤ penetration_slop (2mm, I2) on the settled box stack.
  • 20-box stack (the §4 max-stable-stack target) settles and remains with linear-velocity RMS < 0.01 m/s for 60s continuous simulation.
  • Two 10-box stacks sharing one static floor body: island count = 2 once settled (I13's direct regression test), not 1.
  • Sleeping stack: StepStats.sleeping_body_count = 20, solver CPU time for those bodies = 0 (I14) within one step of reaching Asleep.

21.5 Conformance Fixtures

  • conformance/replay/box_stack_20_stable_60s.json — the §4 max-stack-height fixture; expected: RMS < 0.01 m/s sustained for 60s.
  • conformance/replay/two_stacks_shared_static_floor.json — I13's direct test; expected: island_count = 2, never 1, at every step post-settle.
  • conformance/replay/sleep_wake_cycle.json — settle, sleep, apply an external impulse to one body, confirm the whole island wakes (I5) and the correct island only (not a neighboring, untouched island).

21.6 Pitfalls

  • Stack sink from insufficient position correction: slow, continuous penetration growth over many seconds even though I2's per-step bound looks satisfied in isolation; root cause: max_correction capped too aggressively relative to position_iterations; debug via a 60s+ soak fixture, since sink is a slow-integral effect; signal: StepStats.max_penetration trending up slowly rather than plateauing.
  • Jitter from over-aggressive Baumgarte-style bias: even though ADR-13 selects NGS specifically to avoid this, an NGS pass that accidentally feeds position-error correction back into velocity reproduces the same jitter class; debug: assert the position pass never writes to linear_velocity/angular_velocity, only transform (a unit-test- checked code invariant).
  • Energy injection from the position pass: correcting position without respecting max_correction on a deep-overlap fixture (§8) produces a large one-step position jump that manifests as an apparent velocity spike (delta position ÷ dt) one step after a deep-overlap contact begins; debug via the deep-overlap fixture re-run through the full pipeline, not just SAT/GJK-EPA in isolation.
  • Static body bridging two islands (the defect I13 exists to prevent): a union-find that treats every body identically regardless of body_type reintroduces exactly this bug; two_stacks_shared_static_floor is the standing regression test.

21.7 Performance Concerns

Island partitioning is the parallelism boundary this document commits to (ADR-20 notes core-phase parallelism is not implemented, but the partitioning itself is prerequisite infrastructure for it); union-find cost is near-linear in bodies+edges and is budgeted as a small fraction of the 16ms step (§4, §30).

21.8 Edge Cases

  • A single body with a self-joint (authoring error: a joint connecting a body to itself) must be rejected at joint-creation time, not silently produce a degenerate one-node island.
  • An island with zero contacts but one joint (two bodies connected only by a distance joint, not touching): must still be a valid island and solved normally — islands are not contact-only.
  • A body that wakes mid-step (external force applied via API between two step() calls) must be fully integrated and solved that same step, not deferred one step behind its wake event.

21.9 Failure Analysis

A stack stable for 5 seconds (Phase 5/7's fixture duration) but sinking over 60 seconds is invisible to every earlier phase's fixtures — precisely why this phase introduces the first long-duration soak fixture (§28 ties this to the soak-testing strategy); a phase testing only short-duration stability cannot claim the §4 60-second energy-drift and stack-stability bounds.

21.10 Operational Notes

The docs/runbooks/jitter-diagnosis.md runbook (§10, §26) is authored against this phase's failure modes: jitter and sink are first fully diagnosable once position correction, islands, and sleeping are all present, since an isolated position-solver bug and an island mis-partitioning bug can otherwise present identically.

22. Phase 10 — Joints and Continuous Collision Detection

22.1 Objectives

Implement the Joint variants (Distance, Revolute, Prismatic, Ball, Weld, Motor) as sequential-impulse constraints sharing the Phase 7–9 solver (P13), and conservative-advancement CCD (ADR-18) scoped to bodies flagged bullet.

22.2 Detailed Implementation Steps

  1. Implement each Joint variant's constraint-Jacobian construction (§11 type signatures): DistanceJoint (1 DOF constrained, distance preserved), RevoluteJoint (5 DOF constrained, 1 rotational DOF free, plus optional angle limits and MotorJoint-style drive), PrismaticJoint (5 DOF constrained, 1 translational DOF free, plus limits), BallJoint (3 DOF constrained, all rotation free), WeldJoint (6 DOF constrained, all relative motion locked), MotorJoint (drives relative velocity toward a target, bounded by max_torque).
  2. Implement joint limits as one-sided inequality constraints (reusing the I8-style clamp machinery from contacts, per P13's unification) rather than a separate limit-solving code path.
  3. Wire joints into the same velocity-solve iteration loop as contacts (stage 7, §8 pipeline table) and into island construction (a joint edge behaves like a contact edge for union-find purposes, still respecting I13 for any joint to/from a static body).
  4. Implement conservative advancement (§8 TOI condition, Mirtich & Canny 1995): for each bullet-flagged body, compute swept-AABB broad-phase candidates, then iteratively advance by t_advance = d / v_rel_bound until t_advance exceeds 1.0 (no impact) or falls below tolerance (impact located).
  5. Implement the CCD re-integration loop: on TOI hit, rewind to TOI, generate a contact, run one solve pass, integrate the remaining (1 - TOI) * dt, capped at a maximum CCD sub-iteration count per step (bounding the pathological repeated-near-miss cost, a named pitfall).

22.3 Deliverable

A 4-box chain hangs from a RevoluteJoint and swings to rest under damping; a small fast body thrown at a thin wall is stopped by CCD rather than tunnelling through it.

22.4 Acceptance Criteria

  • 4-box revolute chain: total mechanical energy strictly non-increasing (damping present) over 10s, no visible stretching (anchor separation stays within penetration_slop-equivalent joint tolerance, 2mm).
  • CCD fixture: a 0.05m-radius sphere at 50 m/s against a 0.02m-thick wall at dt = 1/60 (naive per-step travel 0.83m vastly exceeds wall thickness — §34's tunnelling-threshold derivation) is stopped across 100 approach angles.
  • CCD sub-iteration cap enforced: no single step spends more than 8 TOI sub-iterations (documented cap) regardless of scene adversarial-ness.

22.5 Conformance Fixtures

  • conformance/replay/revolute_chain_4box.json — expected: energy non-increasing, anchor separation ≤ 2mm throughout.
  • conformance/replay/ccd_bullet_vs_thin_wall.json — 100 randomized approach angles; expected: zero tunnelling events.
  • conformance/degenerate/ccd_repeated_near_miss.json — an adversarial scene with many near-tangent bullet trajectories; expected: CCD sub-iteration cap respected, step time bounded (not just correctness, also the cap's own regression test).

22.6 Pitfalls

  • Tunnelling of fast small bodies not flagged bullet: a modeling/authoring pitfall, not an engine bug — CCD is opt-in (P11); debug via a scene-validation lint (scripts/) flagging any body whose per-step travel exceeds its own smallest extent, surfaced as a warning.
  • Joint stiffness vs. solver iteration count: an under-iterated WeldJoint (6 DOF, stiffest joint type) "stretches" visibly at 8 velocity iterations under load, while a BallJoint (3 DOF) looks fine at the same count; debug via per-joint-type convergence fixtures at a fixed iteration count, so stiffness regressions are caught per-type.
  • CCD eating the step's time budget on repeated near-misses: a bullet with several near-tangent candidates produces many small TOI advances that consume the sub-iteration cap without resolving a real contact; mitigation: the documented cap (22.2 step 5) plus a fallback accepting the remaining dt uncorrected if the cap is hit (logged, not silent).
  • Rotational CCD gap: a fast-spinning (not fast-translating) thin body can still tunnel via rotation alone; a named, accepted limitation (§8, ADR-18), not a bug to fix in the core phases — raised so it isn't mistaken for one during Phase 10 debugging.

22.7 Performance Concerns

CCD cost is O(bullets × broad-phase-candidates × TOI-iterations); with the sub-iteration cap and opt-in bullet flag (P11), it is bounded and excluded from the 1,000-body/16ms budget unless bullets are present (§30, §34 derives the threshold velocity where CCD becomes mandatory).

22.8 Edge Cases

  • A bullet-flagged body that starts the step already overlapping its target (CCD is unnecessary, discrete collision already handles it): TOI computation must return t=0 gracefully, not treat this as a near-degenerate CCD failure.
  • A RevoluteJoint with lower_angle == upper_angle (a fully locked hinge, equivalent to a partial weld): must be solved as a valid, if degenerate, limit configuration, not rejected at construction.
  • Two bullets colliding with each other (both fast-moving): CCD must consider bullet-vs-bullet pairs, not just bullet-vs-static/slow-dynamic (a narrower, easier-to-miss scope decision, made explicit in ADR-18).

22.9 Failure Analysis

A joint that "explodes" under load, distinct from a contact-solver explosion, isolates to a joint-specific Jacobian sign error or an unbounded motor target — per-joint-type fixtures (one per Joint variant) exist so a WeldJoint bug and a RevoluteJoint bug are never conflated during triage.

22.10 Operational Notes

The docs/runbooks/tunnelling-triage.md runbook (§10, §26) walks the scene-validation lint from 22.6 first — most tunnelling reports trace back to a body that should have been flagged bullet, not a conservative- advancement defect.

23. Phase 11 — Query Interface, Conformance Suite and Perf Hardening

23.1 Objectives

Implement the raycast/overlap query interface (reusing the dynamic BVH, ADR-21), assemble the full conformance suite (differential, property, fuzzing) into one CI gate, and perform the performance hardening pass that validates every §4/§30 numeric target against the real implementation.

23.2 Detailed Implementation Steps

  1. Implement raycast(origin, direction, max_distance) -> RaycastHit via BVH traversal (broad prune) followed by per-shape analytic/GJK ray tests (narrow confirm), mirroring the broad/narrow-phase split used for collision (P6 reuse: ray-vs-shape tests are themselves support-function- compatible where practical).
  2. Implement overlap(shape, transform) -> list[BodyId] similarly.
  3. Assemble the property-test suite (Hypothesis-based, ADR-25): momentum/ angular-momentum conservation, pendulum-period-matches-analytic, penetration-monotonic-decrease-across-position-iterations, and the two-run bit-identical replay property (tying together I1, I3, I4 as executable properties rather than one-off fixtures).
  4. Assemble the fuzzing harness (ADR-26) against the scene loader and the narrow-phase geometry path (including the near-degenerate-simplex case from Phase 6), running as a scheduled CI job (§10 .github/workflows/ fuzz.yml).
  5. Run the perf-hardening pass: profile the full pipeline at the §4 target body/contact counts, identify the top cost centers (expected: the solver's pure-Python inner loop, per ADR-02's honest admission), and record the actual numbers against every §30 M-series target, updating PhaseDeferred("§30 Performance Engineering") items that remain unresolved rather than silently dropping them.

23.3 Deliverable

A complete, CI-gated conformance suite (unit, property, differential, fuzz, replay, soak) and a query interface sufficient for Game-Engine-Core's AI raycasts and trigger volumes; a recorded, honest performance report against every §4 target.

23.4 Acceptance Criteria

  • Raycast query latency: p50 ≤ 5µs, p95 ≤ 25µs, p99 ≤ 100µs against a 10,000-proxy BVH (§4, restated here as the phase's direct acceptance gate).
  • Full conformance suite (all fixtures from Phases 0–10) green in one CI run.
  • Fuzzing harness: 1 hour of coverage-guided fuzzing on the scene loader and narrow-phase path produces zero unhandled exceptions (all inputs either succeed or raise a documented PhysicsError subtype).
  • Perf-hardening report: every §30 M-series target measured and recorded (pass/fail per row), not estimated.

23.5 Conformance Fixtures

  • conformance/replay/raycast_latency_10k_proxies.json — latency percentiles measured against the §4 targets.
  • tests/property/test_conservation.py — Hypothesis-generated random elastic-collision scenarios; expected: momentum/angular momentum conserved within 1% for every generated case.
  • fuzz/fuzz_scene_loader.py, fuzz/fuzz_narrowphase.py — 1-hour runs; expected: zero unhandled exceptions.

23.6 Pitfalls

  • Raycast against the BVH reusing stale fattened AABBs: a query structure that shares the dynamic BVH's fattened (padded) bounds without a narrow-phase confirm step returns false-positive hits; fix: the broad/narrow split (23.2 step 1) is mandatory for queries exactly as it is for collision (P5's logic applies identically to queries). Query results without the narrow confirm are a correctness bug, not an acceptable approximation.
  • Determinism-loss from a hash-ordered pair iteration resurfacing here: even though ADR-19/I4 fixed this in Phase 3, a query-path shortcut that iterates a Python set of candidate proxies (rather than the canonical sorted order) for tie-breaking in an "closest of several equidistant hits" raycast case can reintroduce nondeterminism specifically in query results — the property test (23.5) must cover queries, not only the step pipeline.
  • Fuzzer finding a crash the conformance suite never would: coverage- guided fuzzing on the narrow-phase path (particularly near-degenerate simplices, Phase 6) routinely finds inputs no human-authored fixture would think to write; the correct response is always to add the found input as a permanent named fixture (§28), not just patch and move on.

23.7 Performance Concerns

This phase is where the ADR-02 honest numeric-core admission is confronted directly with real numbers: if the pure-Python solver loop cannot meet the §4 1,000-body/16ms target, the correct output of this phase is a clearly recorded gap and a PhaseDeferred("§30 Performance Engineering") entry pointing at the native-extension escalation — not a quiet lowering of the target.

23.8 Edge Cases

  • A raycast with max_distance = 0 or negative: must return "no hit" rather than an ill-defined query.
  • An overlap query against a shape with zero volume (degenerate, should have been rejected at Phase 2 construction, but a defense-in-depth check here confirms the query path doesn't independently reintroduce the bug).

23.9 Failure Analysis

A conformance-suite fixture that passes in isolation but fails when run as part of the full assembled suite (this phase's integration step) usually indicates hidden cross-fixture state leakage (e.g., a module-level BodyId counter not reset between fixtures) — the assembled-suite run introduced in this phase is specifically designed to catch that class of bug, which per-fixture CI runs in earlier phases could not.

23.10 Operational Notes

From this phase forward, the conformance suite assembled here is the permanent regression gate referenced throughout §26/§28; every subsequent change to the engine (post-blueprint, in the actual coding phase) runs against it unmodified except for deliberate, reviewed additions.

27. Compatibility & Versioning

World-snapshot format is versioned independently of the library's SemVer (ADR-29): a snapshot carries an explicit format version integer; loading a snapshot with an unknown or unsupported version raises PhysicsError rather than attempting a best-effort parse. Shape/joint schema evolution: new Shape/Joint variants are additive (new tagged-union cases); removing or renaming a field is a breaking (major-version) change per SemVer. Solver- parameter semantics across versions: SolverConfig field meanings (e.g., penetration_slop's units and effect) are locked once released — a version that changes what a parameter means (not just its default) is a major-version bump, since it silently invalidates every consumer's tuned scene.

Determinism guarantees, and exactly what invalidates them (§4, ADR-30): bit-exact same-platform reproduction holds only when the compiler/interpreter build, NumPy build (BLAS backend), FMA-contraction setting, and libm implementation are identical between two runs. Any of the following invalidates the guarantee: a different Python/NumPy build (even a patch version, if it changes the underlying BLAS), a different CPU architecture (x86 vs. ARM — the historical PhysX lesson, §33), or compiler flags that enable FMA contraction inconsistently between builds. This is documented, not solved — cross-platform bit-exactness is an explicit non-goal (ADR-30).

API stability: the public physics.* surface (§10) follows SemVer; a minor version may add fields/methods, a patch fixes bugs without behavior changes to documented invariants, a major version may change solver defaults or SolverConfig semantics. Migration: a CHANGELOG.md entry accompanies every version bump that changes simulation behavior, cross-referencing the exact ADR or invariant affected. Deprecation: a deprecated field/method is marked for one full minor-version cycle before removal. Rolling-upgrade guarantees: none — this is an embedded library, not a service; "rolling upgrade" means recompiling the host application against the new version and re-running the full conformance suite (§28) before deployment.

28. Testing & Verification Strategy

Unit (ADR-25): per-module tests for math types, shape construction, mass/inertia formulas (Phase 0–2 fixtures).

Integration: full-pipeline scenario tests (a scene loaded, stepped N times, final state asserted) — the box_stack_10/box_stack_20 fixtures and the revolute-chain fixture (Phases 5, 7–10).

Property-based (Hypothesis, ADR-25), tied to invariants: momentum and angular momentum conserved in an elastic collision within tolerance (I1- adjacent, ties to §23.5's test_conservation.py); a frictionless pendulum's period matches the analytic value (ties to Phase 1's analytic fixtures); penetration monotonically decreases across position iterations (I2, tested per-iteration, not just post-pass); the same scene stepped twice yields bit-identical state (I4, the core determinism property).

Differential: against Box2D on shared 2D-projectable scenarios (box-box resting contact, restitution) — informed by the Box2D reference lineage (§5); against analytic closed-form solutions (projectile, pendulum, inclined-plane friction threshold, elastic-collision momentum) per Phase 1, 7, 8 fixtures.

Fuzzing (ADR-26): the scene loader (T1, T2, T6) and the narrow-phase geometry path (T2, T3, degenerate simplices from Phase 6) as primary targets, run as a scheduled CI job (§10 fuzz.yml), 1-hour minimum duration per Phase 11's hardening pass (§23.4).

Chaos / fault injection: deliberately corrupting a body's velocity to NaN mid-run and confirming quarantine (I6/I11) rather than propagation; deliberately overflowing the contacts-per-step cap (T8) and confirming graceful degradation rather than a crash.

Deterministic replay with divergence bisection: scripts/ run_determinism_harness.sh runs a scene twice, and on a hash mismatch, bisects the step range to the first diverging step (FM-8, the §26 replay-divergence-bisect.md runbook's mechanism).

Conformance scenario suite: the full assembled set from Phases 0–11 (§23.3), the permanent regression gate.

Perf-regression gating: benchmarks/ results compared against the §30 M-series targets on every release-candidate build (ADR-27, ADR-29); a regression beyond a documented tolerance blocks release.

31. Scalability Analysis

What stays constant vs. grows (Big-O): broad-phase cost moves from O(n²) (naive pairwise, the correctness oracle only, §15.7) to O(n log n) (dynamic BVH, ADR-07); narrow-phase cost is linear in candidate pairs times per-pair-type cost (analytic constant, SAT proportional to hull complexity, GJK/EPA the bounded-iteration fallback); solver cost is strictly linear in contacts × iterations (§34); island partitioning is near-linear in bodies+edges and is the structural enabler of parallelism (ADR-20), even though this blueprint's core phases do not exploit it within the pure-Python core.

Named bottlenecks, in order: (1) the pure-Python sequential-impulse solver inner loop (ADR-02's documented, honest cost center, dominant past a few thousand contacts); (2) GJK/EPA fallback overuse when the shape mix is too general-convex-heavy relative to primitives (§18.7); (3) broad-phase degradation under extreme clustering if the spatial hash isn't promoted to the BVH in time (ADR-07's crossover, §34); (4) CCD cost under an adversarial bullet-heavy scene (§22.7, bounded by the sub-iteration cap).

Parallel scaling across islands and its determinism cost: islands are, by construction, independent solve units (I13) — the theoretical parallelism ceiling is one thread/process per island. This blueprint's core phases do not implement that parallelism (ADR-20: Python's GIL makes CPU- bound threading counterproductive for the pure-Python core); realizing it requires the native-extension escalation already named in ADR-02, at which point cross-island parallelism is free of cross-island determinism cost (islands don't interact within a step) but still requires a canonical island-processing order if any global aggregate (e.g., a total-energy sum) is computed from the results, per P3's ordering discipline generalized.

Practical body/contact ceiling and the levers beyond it: the pure-Python core's practical ceiling is on the order of a few thousand active contacts before step time exceeds the 16ms budget (§34 derives the exact number); the lever beyond that ceiling is the deferred native core (PhaseDeferred("§30 Performance Engineering")), not a change to the algorithms themselves — the sequential-impulse/NGS/BVH architecture in this document is not the bottleneck, the interpreter is.

32. Mental Models & First Principles

MM1. A constraint solver is Gauss-Seidel on a sparse system with a deadline. Predicts: every visual artefact (jitter, softness, slow settling) is a convergence story, not a physics story. Bug class without it: chasing a "physics bug" by tweaking restitution/friction coefficients when the real issue is iteration count or ordering. Resolved in §19, §20.

MM2. Restitution and friction are inequalities you project onto, not forces you apply. Predicts: the solver clamps, it doesn't compute a closed-form force. Bug class without it: trying to "add a friction force" directly to the integrator instead of bounding an impulse in the solver. Resolved in §8, §19.

MM3. Determinism is a property of the whole pipeline's order, not just its arithmetic. Predicts: two runs with identical float operations in a different order can diverge. Bug class without it: assuming IEEE 754 compliance alone guarantees replay-safety, then being surprised by hash- map iteration nondeterminism. Resolved in §15, §7 (I4).

MM4. Broad phase trades false positives for zero false negatives. Predicts: a broad phase that looks "wasteful" (many rejected candidate pairs) is working correctly; a broad phase that looks "efficient" (few candidates) but misses one is catastrophic. Bug class without it: tightening AABBs to "optimize" and silently reintroducing missed contacts. Resolved in §8, §15 (P5).

MM5. Warm starting is memory across an otherwise-stateless iteration. Predicts: solver quality at a fixed iteration count is bounded by how well last frame's answer seeds this frame's guess. Bug class without it: doubling iteration count to fix jitter when the real fix is restoring warm-start continuity. Resolved in §20 (P4).

MM6. An island is the unit of independence, and static bodies are not nodes. Predicts: two physically separate structures sharing one static anchor must simulate as if they've never met. Bug class without it: a shared floor silently serializing unrelated stacks, then blaming the solver for a slowdown that's actually a partitioning bug. Resolved in §21 (I13).

MM7. Sleeping is a claim about the whole island, not a body. Predicts: one twitching body keeps 19 settled neighbors "awake" on paper even though nothing is visibly moving. Bug class without it: per-body sleep heuristics that let a sleeping body silently sit inside a still-settling neighbor. Resolved in §21 (P8).

MM8. A support function is the only vocabulary collision detection needs to speak. Predicts: adding a new convex shape should never require touching SAT, GJK, or the solver. Bug class without it: shape-specific narrow-phase special cases that quietly diverge from the general path on edge cases the general path already handled. Resolved in §14, §18 (P6).

34. Back-of-Envelope Capacity Model

Step budget (from §4): 1000 ms ÷ 60 Hz = 16.667 ms per step.

Max contacts from solver cost: assume 60% of the step budget (10 ms = 10,000,000 ns) is allotted to the velocity + friction solve (§30's M1/M6/M7 split). Measured per-constraint cost (Phase 7 benchmark baseline, M6) ≈ 1,000 ns in the pure-Python core (ADR-02). With friction roughly doubling per-point cost (M7) and 8 velocity iterations (P1): effective cost per contact = 8 × 1,000 ns × 2 = 16,000 ns. Max contacts = 10,000,000 ÷ 16,000 ≈ 625 contacts — consistent with, and slightly above, §4's 500-contact sustained target (the margin absorbs position-solve and telemetry overhead).

Broad-phase crossover (naive vs. BVH): naive O(n²) cost ≈ n(n-1)/2 × 20 ns (a cheap AABB overlap test); BVH cost ≈ n·log2(n) × 150 ns (higher per-node constant from tree traversal in Python). Setting them equal: (n−1)×10 ≈ 150·log2(n). At n ≈ 100: log2(100) ≈ 6.64, RHS ≈ 996, LHS = 99×10 = 990 — approximately equal. Crossover n ≈ 100: below that, naive O(n²) is competitive; above it, BVH promotion (ADR-07) is mandatory, matching §4's "≤5,000 candidate pairs at 1,000-body density" framing (well past the crossover, BVH is the only viable structure).

Memory per step: 1,000 bodies × 512 B (M14) = 512,000 B (500 KB); 500 contacts × 256 B (M14) = 128,000 B (125 KB). Total live per-step state ≈ 625 KB — small enough that cache locality (SoA layout, ADR-02) matters far more than raw footprint.

Tunnelling threshold velocity: threshold = shape/wall thickness ÷ dt. For the §22 CCD fixture's 0.02 m wall at dt = 1/60 s (0.01667 s): threshold = 0.02 ÷ 0.01667 ≈ 1.2 m/s. Any relative approach velocity above this against that wall risks tunnelling in one discrete step — far below the fixture's dramatic 50 m/s test case, underscoring that CCD is mandatory for any fast body against thin geometry, not just bullets in the literal sense.

Penetration recovery rate (NGS position pass): with a per-iteration correction fraction β ≈ 0.2 and position_iterations = 3 (P1), depth after one step's position pass: depth × (1−β)³ = depth × 0.512. Starting from a 5 cm (0.05 m) initial overlap, reducing to below penetration_slop (0.002 m) requires 0.8ⁿ × 0.05 ≤ 0.002 → 0.8ⁿ ≤ 0.04 → n ≥ ln(0.04)/ln(0.8) ≈ 14.4 total iterations, i.e. ⌈14.4 / 3⌉ = 5 steps (≈ 83 ms at 60 Hz) to recover a 5 cm deep-overlap start to within tolerance.

Energy-drift estimate for semi-implicit Euler: per Hairer, Lubich & Wanner's quasi-symplectic bound, the per-step energy error oscillates rather than growing secularly, with amplitude scaling with dt but not accumulating monotonically. Phase 1's energy_drift_free_spin.json fixture measures this directly rather than relying on the bound alone; the §4/§13 target (≤1% drift per simulated second at dt = 1/60 s) is set with generous headroom above the quasi-symplectic bound's expected behavior, which is why I1's enforcement is a measured regression fixture, not a purely analytic guarantee.

36. Alternative Architectures (Roads Not Taken)

A1. Global LCP/MLCP solved via a direct pivoting method (e.g., Lemke's algorithm).

[body velocities] --Jacobian--> [LCP: w = Mz+q, w>=0, z>=0, w.z=0]
                                         │
                                  direct pivot solve
                                         │
                                 exact simultaneous z

Winning regime: small (tens of bodies), tightly-coupled scenes needing an exact simultaneous solution (offline research validation, near-singular configurations). Embodying system: research LCP solvers built on Stewart & Trinkle (1996) / Anitescu & Potra (1997)'s formulations. Rejected because pivoting methods scale poorly with contact count (worse than linear) and offer no natural warm-start analog — wrong tradeoff for this blueprint's real-time, large-contact-count target (§4).

A2. Position-based dynamics / XPBD.

[positions] --project constraints directly--> [corrected positions]
                          │
                  (no separate velocity solve;
                   velocity derived from Δposition/dt)

Winning regime: highly deformable, mass-varying, or very stiff systems (cloth, soft bodies — this blueprint's explicit non-goals) where unified position-space projection outperforms a velocity-space solver. Embodying system: XPBD as used in cloth/soft-body engines. Rejected here because this blueprint's domain (rigid bodies only) doesn't need XPBD's chief advantage (unconditional stability for arbitrarily stiff, deformable constraints) and would sacrifice the well-understood, directly citable sequential-impulse lineage (Catto's papers, §5) for a formulation this blueprint's rigid-body-only scope doesn't require.

A3. Fully implicit/variational integrator with Newton iterations (MuJoCo's convex-optimization approach).

[state] --formulate contact as smooth, convex optimization--> [Newton solve]
                                         │
                              implicit, per-step convergence
                                         │
                                  next state (soft contact)

Winning regime: contact-rich robotic manipulation research needing smooth gradients through contact (differentiable simulation) and tolerating higher per-step cost for accuracy. Embodying system: MuJoCo. Rejected because Newton-iteration-per-step cost is incompatible with §4's 16 ms real-time budget at the target body/contact counts, and this blueprint's teaching goal (an inspectable sequential-impulse solver, §2) is better served by the simpler, more widely-cited Catto lineage.

A4. Penalty/spring-damper contact model.

[penetration depth] --k*depth + c*velocity--> [applied force, no LCP]
                                         │
                                 integrated like any other force

Winning regime: extremely simple engines where implementation speed outweighs stability guarantees, or soft, squishy contact is the desired visual (arcade-style games). Embodying system: early physics engines and many simplified game-jam implementations use penalty forces directly. Rejected because penalty forces require a stiff spring constant to avoid visible sinking, which in turn demands a very small dt or an implicit integrator for stability (Press et al., ch. 16) — reintroducing exactly the stiffness-vs-stability tradeoff this blueprint's sequential-impulse solver (ADR-10) was chosen specifically to avoid.

38. Glossary

  • AABB — Axis-Aligned Bounding Box; the broad-phase's coarse bound (§8).
  • BVH — Bounding Volume Hierarchy; this engine's dynamic broad-phase promotion target (ADR-07).
  • Baumgarte stabilization — mixing a fraction of positional error into the velocity constraint's bias (§8); studied, not the primary mechanism here (ADR-13).
  • BodyId — the opaque, monotonic handle identifying a RigidBody (§11).
  • Broad phase — the coarse, conservative pair-filtering stage (§8, P5).
  • Bullet (flag) — a per-body opt-in marking a body for CCD (P11, ADR-18).
  • CCD — Continuous Collision Detection; catches fast-body tunnelling (§8, §22).
  • CFM/ERP — Constraint Force Mixing / Error Reduction Parameter; the soft-constraint alternative to Baumgarte (Catto 2011, §8).
  • Conservative advancement — the TOI-search procedure used for CCD (§8, Mirtich & Canny 1995).
  • Contact manifold — the set of persisted contact points between two bodies (§8, §11).
  • Coulomb friction — the |impulse_t| ≤ μ·impulse_n friction law (§8).
  • Degrees of freedom (DOF) — the independent motion parameters a constraint restricts or leaves free (§22).
  • Determinism — bit-exact reproduction given identical (state, dt, ordering) on one platform (§4, ADR-30).
  • Distance joint — a joint preserving a fixed anchor-to-anchor length (§11).
  • Effective mass — the scalar mass term reducing a constraint to a 1-DOF impulse problem (§8).
  • EPA — Expanding Polytope Algorithm; penetration-depth computation from a GJK simplex (§8, §18).
  • Feature-id — a stable identifier for the geometric feature underlying a contact point, used for manifold matching (§8, P4).
  • Friction cone — the exact Coulomb bound; approximated here by a pyramid (§8, ADR-14).
  • GJK — Gilbert-Johnson-Keerthi distance algorithm (§8, §18).
  • Inertia tensor — the 3×3 matrix mapping angular acceleration to torque (§8).
  • Island — a connected component of contact/joint-linked bodies, solved independently (§8, §21).
  • Jacobian (constraint) — the matrix relating body velocities to a constraint's rate of change (§8).
  • LCP — Linear Complementarity Problem; the mathematical formulation underlying contact resolution (§8, §36).
  • Manifold persistence — carrying contact points and their impulses across frames by feature-id (§8, P4).
  • Minkowski difference — the set {a - b : a∈A, b∈B}, whose containment of the origin indicates overlap (§8, §18).
  • Narrow phase — the exact per-pair collision-detection stage (§8).
  • NGS — Nonlinear Gauss-Seidel; this engine's position-correction pass (ADR-13, §21).
  • Penetration slop — the tolerated residual penetration below which correction stops (I2, §4).
  • Projected Gauss-Seidel (PGS) — the iterative method underlying sequential impulses (§8, ADR-10).
  • ProxyId — a broad-phase-internal handle for a tracked AABB (§11).
  • Quaternion drift — numerical departure of a quaternion's norm from 1.0 under integration (§8, I7).
  • Resting contact — a contact with near-zero approach velocity, triggering restitution's special case (§8, ADR-15).
  • Restitution — the bounciness coefficient governing post-collision separation velocity (§8).
  • Revolute joint — a hinge joint, one free rotational DOF (§11, §22).
  • SAT — Separating Axis Theorem (§8, §17).
  • Semi-implicit Euler — the integrator using post-update velocity for the position step (§8, P10, ADR-05).
  • Sequential impulse — the per-constraint iterative impulse solver (§8, ADR-10).
  • Simplex — a 1–4 point set (point/line/triangle/tetrahedron) used by GJK (§8, §18).
  • Sleeping — suspending integration/solving for a settled island (§8, P8, I14).
  • Spatial hash — the uniform-cell broad-phase structure, this engine's initial backend (§8, ADR-07).
  • StepStats — the per-step telemetry record (§11, §26).
  • Support function — the direction → extreme point contract every convex shape implements (§8, P6).
  • Symplectic integrator — an integrator approximately preserving a Hamiltonian system's structure, bounding energy drift (§8, Hairer/Lubich/Wanner).
  • Time of impact (TOI) — the fractional-step time at which two swept shapes first touch (§8, §22).
  • Warm starting — applying the previous step's accumulated impulse as this step's initial guess (§8, P4, ADR-12).
  • Weld joint — a joint locking all six relative DOF between two bodies (§11, §22).
  • Witness point — a point on a shape's surface identified by GJK/EPA as the closest/deepest feature (§8, §18).
  • XPBD — Extended Position-Based Dynamics; the position-space alternative studied in §36.
