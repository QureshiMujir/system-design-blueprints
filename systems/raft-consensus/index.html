In one paragraph

Raft keeps one single-writer replicated log on a group of 3, 5 or 7 servers, giving strongly consistent replicated state while up to ⌊(N−1)/2⌋ of them fail (§1, §4, MM1). This design is a Rust library implementing the full protocol of Ongaro's dissertation — election, replication, persistence, membership change, snapshots — plus pre-vote, leader transfer, learners, ReadIndex reads, batching and pipelining (§1). Its defining property: the protocol core performs no I/O and owns no clock; every effect leaves through an outbox the caller drains, the precondition for a deterministic simulator (§4, P1, P3). Systems engineers link it into a host application such as the workspace's key-value store; it is not a sidecar (§1).

The problem, concretely

Each naive shortcut has a named failure. Answering a client before a majority has acknowledged the entry ("fire and forget" persistence) is wrong because commit is a property of a majority, not of the leader's local disk: the leader's own fsync guarantees nothing until a majority also holds the entry (MM3). Two leaders in one term can commit conflicting entries, which is why the first invariant is "at most one leader per term" (I1). And a node that replies as durable, then crashes, comes back with a promise that is false on restart — the "committing on a lie" bug class (P6).

AppendEntries reply handling is ~30 lines of dissertation pseudocode and ~300 in any production library: slow followers, out-of-order replies, step-down on stale replies, snapshot delivery (§2). The §8.7 failure path shows how subtle "correct" is: leader A durably appends entry 100 at term 5 and crashes before any follower acknowledges it; B is elected at term 6 having last matched entry 99; entry 100 never had a majority, so B's log legitimately lacks it, and when A rejoins as a follower, B's AppendEntries forces truncate_suffix(100) on A — the safety-preserving outcome, not data loss (§8.7, I2, I4). The library builds these rules once behind a small, stable trait surface so downstream systems need not re-derive them (§1).

How it works, end to end

 Application (impl StateMachine)   <-- apply(idx, term, bytes) ----------------+
        | propose(bytes)                                                      |
        v                                                                     |
 +----------------------------------------------------------------------------+---+
 | raft  (protocol core — sync, message-driven, no I/O, no clock)                 |
 |   RaftNode (the FSM) --> Role state --> step()/tick() dispatch --> Outbox      |
 |       |         Follower/PreCandidate/Candidate/Leader/Learner    messages/    |
 |       v                                                           persist/     |
 |   RaftLog  |  Election & Progress  |  Snapshot coordinator        apply/       |
 |   (log/commit)  (replication)         (InstallSnapshot)           snapshot/    |
 +-------|---------------|-------------------|-----------------------events-------+
         v               v                   v                          v
   raft-storage      raft-net            raft-sim                   consumer drains
   LogStorage /      Transport /         deterministic scheduler    Outbox, drives
   StableStore /     tonic gRPC (mTLS)   + fault injector           step/tick, fsyncs
   Snapshotter       raft-jepsen: real-process nemesis harness

Follow one client command through the boxes of the §3 diagram above:

  1. The host calls RaftNode::propose(bytes) on the leader (crates/raft/src/node.rs); RaftNode owns no threads, no clock and no sockets, so the call only mutates memory (§3, §11.7, P1).
  2. The entry goes into RaftLog, the in-memory window over the log plus the snapshot anchor, committed and last_applied; per-follower Progress decides what to send to whom (§3, §11.11).
  3. Nothing has happened outside memory yet. Disk writes wait as PersistOps in Outbox::persist and outgoing messages in Outbox::messages; the caller must drain_outbox() after every step/tick, and no callback ever fires from inside (§11.6, P3).
  4. raft-storage performs the write — LogStorage::append fsyncs inside — and the caller reports back with on_persisted(id); any reply depending on that write waits for the ack (§11.9, I7).
  5. raft-net sends the messages over tonic gRPC with mutual TLS through the async Transport::send; tokio is confined to this crate (§11.10, ADR-02, ADR-04).
  6. Each follower's step(from, msg) runs the log consistency check, persists the entries, and replies success=true, match_index only after its own fsync (§8.3, §8.5, §16, I3).
  7. Back on the leader, step raises that follower's match_index; maybe_advance_commit moves committed forward once a majority of voters hold the index, never backwards (§16, I6).
  8. Committed entries land in Outbox::apply; the host feeds them to StateMachine::apply(idx, term, bytes), which returns bytes, strictly in index order (§11.6, §11.8, §14, I5).

tick(elapsed) fires election timeouts and heartbeats and, like step, performs no I/O (§3), so raft-sim drives real RaftNodes under a seeded scheduler, checking all fourteen invariants after every step, and raft-jepsen drives real binaries under real faults (§20, §21).

The core ideas

Terms and roles: a state machine, not a flag byte (§8.4, MM2)

A term is a logical clock for "who may I trust right now", not an election counter: a message carrying a lower term is stale information to discard, not older information to merge (MM2). Every message carries term first, so the step-down check runs before any other dispatch (§8.1). Roles are a real enum — Follower | PreCandidate | Candidate | Leader | Learner — each carrying only the state that role needs (§3). The main transitions (§8.4):

From Event To Side effects
Follower election timeout PreCandidate send PreVote to all voters, no term bump (P8)
PreCandidate pre-vote majority Candidate current_term += 1, voted_for = self, persist, send RequestVote
Candidate vote majority Leader append no-op (I4), init Progress for all peers, start heartbeats
Leader higher term in any reply Follower persist new term, step down
Any RequestVote/AppendEntries with higher term Follower persist term, reset voted_for

The §8.5 trace on a 5-node cluster: A's timer fires and it sends PreVote{term=T+1}; B and C grant because their logs are not more up to date, giving A a 3-of-5 pre-vote majority; A becomes Candidate, persists current_term=T+1 and sends RequestVote; B and C grant; A becomes Leader and appends a no-op at (T+1, idx=N+1); once B and C persist it and reply match_index=N+1, maybe_advance_commit sees a majority and sets committed=N+1 (§8.5). The pre-vote round exists so a partitioned-then-healed minority cannot disturb a healthy leader (without it, term-inflation storms follow every partition heal); the price is one extra round trip before every election, even a legitimate one (P8, MM7).

Who may lead, and why the no-op matters (§15, I1, I4)

A node grants its vote only if (a) the candidate's term is at least its own, (b) it has not voted this term or already voted for this candidate, and (c) the candidate's log is at least as up to date — last term wins, ties broken by last index (§15). Clause (c) is the Election Restriction. Leader Completeness: an entry committed in term T is in every leader's log for every later term (I4). §15 calls the Election Restriction "what makes I4 provable" and the no-op on election "the single rule that makes Leader Completeness provable"; I4's row lists both (§15, I4). A new leader may not commit earlier-term entries by counting replicas — the "Figure 8" hazard — so it appends a blank no-op at its own term, and once that commits the older entries are committable (§8.5, §15, §16, I4). Otherwise an entry at index N from current_term commits when a majority of voters report match_index >= N (§16). For the same reason no linearizable read is served until the term's no-op commits (I13).

Log matching and conflict repair (§8.6, §16, I3)

Log Matching says that if two logs hold the same (index, term) pair, every entry before it is identical, so a follower can adopt a leader's log by index and term alone (I3). Each AppendEntriesReq carries prev_log_index and prev_log_term, and the follower checks them before accepting anything (§8.1, §16). The §8.6 example: a follower whose log ends at index 40 receives prev_log_index=50; it cannot verify the term, so it replies success=false, conflict_index=41, conflict_term=None, and the leader's maybe_decr_next jumps next_index straight to 41 instead of stepping back one index per round trip (§8.6). On the leader each follower has a Progress in one of three states: Probe sends one entry at a time to find the divergence point, Replicate pipelines without waiting for the previous batch's acknowledgement, and Snapshot is used once a follower's next_index is below the leader's first_index, so it needs InstallSnapshot (§11.11, §16, §18). Pipelining has a trap — an unguarded stale success=false from a slow follower can move next_index backwards — and a ceiling: at most max_inflight (256) in-flight AppendEntries per follower, after which only that peer's stream pauses (§4, §16, I6, I12). Back-to-back proposals collapse into one AppendEntriesReq at tick time; the design target is at least 4× the throughput of batching disabled (§16, §28 M9).

Three persistent shapes and persist-then-reply (§8.3, P2, P6, I7)

Only three things ever touch disk: the log, the stable state (current_term plus voted_for) and the snapshot (P2). The §8.3 table says what is persisted and what is re-derived:

Field Persisted? When, or where it comes from
current_term yes before any vote or AppendEntries reply
voted_for yes before RequestVoteReply{granted=true}
log entries yes before AppendEntriesReply{success=true}
commit_index, last_applied no re-derived (last_applied from the state-machine snapshot)
next_index[], match_index[] no leader-only, rebuilt on election

The rule binding them is persist-then-act: the API forces the protocol to record a PersistOp and block the dependent reply until on_persisted arrives, so a term bump, a vote, an appended entry or a snapshot chunk is durable before the paired reply leaves the outbox (P6, I7). The default backend is redb, where every append or stable-state write is one Durability::Immediate transaction and log and stable-state records carry a CRC32C trailer (§8.2, §13, ADR-05). On restart a node loads its stable state, loads the newest snapshot, re-anchors the log at snapshot_last.index + 1, loads the entries after that anchor, and starts as a Follower unconditionally (§13, I8).

Changing membership without two disjoint majorities (§17, P7, I9)

Switching from configuration C_old to C_new in one step has a known unsafe interleaving — the disjoint double-majority race (P7, ADR-08). Joint consensus goes through a middle state instead: the leader appends an EnterJoint entry; once it commits the cluster is in C_old,new, where every commit and every election needs a majority of old_voters and a majority of new_voters; the leader then appends LeaveJoint, and once that commits the cluster is in C_new (§17). Only one change may be in flight — change_membership returns an error while PendingConfigChange is set — because overlapping changes reintroduce the race (I9). Learners receive the log through the same AppendEntries path but count toward no quorum; promotion to voter is refused until the learner's match_index is within catch_up_window (default 1,000) of last_index, so a lagging new voter cannot stall commitment (§4, §17). If the change removes the leader it steps down after LeaveJoint commits; and because a removed node keeps running, raft-net drops its messages (§17, I14).

Snapshots and linearizable reads (§18, §19, MM5, MM8)

A snapshot is a compressed prefix of the log, not a separate source of truth — which is why it must embed the Configuration as of its last included index, or a restored node cannot find its peers (MM5, P13, I10). The trigger is a log larger than snapshot_size_threshold (64 MiB) with the state machine at least snapshot_min_entries (10,000) ahead of the last snapshot (§18). Capture goes through Outbox::snapshot and StateMachine::snapshot; then RaftLog::compact_prefix shrinks the log while keeping first_index = snapshot_last.index + 1 (§18, I8). A follower whose next_index is below the leader's first_index receives InstallSnapshot in fixed 1 MiB chunks, each with a CRC32C trailer, written to a temp file and renamed into place only after the final check passes (§18, ADR-07, ADR-21).

A ReadIndex read never appends to the log: the leader (1) records the current committed index, (2) confirms it is still leader with a heartbeat round to a majority, (3) waits until last_applied reaches the recorded index, and (4) runs the read against the state machine (§19); a follower gets the index from the leader and waits locally (FollowerRead). Lease reads skip the heartbeat round within lease_timeout < min_election_timeout, trading the clock-free proof for latency, so they need an explicit bounded-clock-skew acknowledgement and are off by default (§19, P9, MM8).

The trade-offs — where engineers disagree

Protocol core execution model: sync step/tick, not async (ADR-03)

Chosen: a sync, message-driven core, because the simulator needs deterministic, reentrant-free stepping (ADR-03, P1, P3). Rejected: an async core (async fn step). When the rejected choice is right: a pure client-facing gateway with no correctness-ordering requirement — ordinary async code is fine there, which is why raft-net is async and raft is not (ADR-03).

Membership change: joint consensus (ADR-08)

Chosen: joint consensus through C_old,new, for correctness — single-server change has a known unsafe interleaving (ADR-08, P7). Rejected: single-server, one-at-a-time change, which is what hashicorp/raft ships (§31). When the rejected choice is right: a statically bootstrapped cluster whose membership is fixed for its entire lifetime — the unsafe code path simply goes unused (ADR-08).

Linearizable reads: ReadIndex baseline, lease reads opt-in (ADR-09)

Chosen: ReadIndex, so correctness never silently depends on clock synchronisation (ADR-09, P9). Rejected: lease reads only. When the rejected choice is right: NTP-disciplined clocks plus hard latency SLOs where ReadIndex's heartbeat round trip is unacceptable (ADR-09).

Default log backend: redb (ADR-05)

Chosen: a pure-Rust crash-safe B-tree — crash-safe out of the box and replaceable later (ADR-05). Rejected: a custom mmap log or raw segment files; the file backend ships only as a reference (§3, §13). When the rejected choice is right: extreme append rates above 200k appends/s on a single node, where a hand-tuned io_uring raw-segment log avoids B-tree overhead (ADR-05).

Snapshot transfer: streamed 1 MiB chunks (ADR-07)

Chosen: fixed-size streamed chunks, so a lagging follower cannot block the leader and memory stays bounded (ADR-07, P12). Rejected: single-shot transfer. When the rejected choice is right: snapshots reliably under 8 MiB, where single-shot's simplicity outweighs streaming's complexity (ADR-07).

Default transport: gRPC via tonic (ADR-04)

Chosen: gRPC, for interoperability with the KV-store project and external tooling (ADR-04). Rejected: custom framed TCP, QUIC. When the rejected choice is right: intra-rack deployments under 0.1 ms per hop, where HTTP/2 framing taxes p99 and custom framed TCP wins; lossy WAN links favour QUIC's independent-stream loss recovery, which is exactly the trigger for the deferred QUIC transport (ADR-04, §35).

Roads not taken (§34)

Multi-Paxos — two-phase Prepare/Accept per instance, a stable leader skipping Prepare; wins when any replica may propose and leader election is delegated to an external mechanism (Chubby, Spanner); rejected because without an explicit leader concept it is harder to reason about operationally and far harder to implement correctly from the paper alone (§34).

Viewstamped Replication — primary/backup with PREPARE/PREPARE-OK and a view change on primary failure; wins when replication and recovery should be separately specified layers (close to MongoDB replica sets); rejected because its view change is described with less operational precision than Raft's election (§34).

Zab — PROPOSE/ACK/COMMIT broadcast with a recovery phase; wins when the system is a coordination service whose API and protocol are co-designed (ZooKeeper); rejected because the goal here is an embeddable library (§34).

Chain Replication — writes flow head to tail, reads at the tail need no quorum; wins for extremely read-heavy, write-light workloads (FAWN-KV); rejected because reconfiguration reshapes the whole chain and write latency is O(chain length) hops instead of O(1) parallel fan-out (§34, §4).

Deferred register — BFT, Multi-Raft, flexible quorums, witnesses, QUIC and a TLA+ model each wait on an un-defer trigger, e.g. Multi-Raft once the single-group ceiling is hit (§35).

What must never be false

  • I1 — at most one leader per term; assert_election_safety and the election_restriction property test; raft.election.win > 1 per term alarms.
  • I2 — a leader never overwrites or deletes its own log; a debug assertion on leader-role truncate; raft.log.leader_truncate_attempt should never fire.
  • I3 — identical (index, term) means identical preceding entries; the log_matching property test over 1,024 histories; raft.replicate.conflict rate.
  • I4 — an entry committed in term T is in every later leader's log; the leader_completeness property test; a violation is unrecoverable data loss.
  • I5 — no two servers apply different commands at the same index; state_machine_safety test and the Jepsen checker; raft.apply.index monotonicity.
  • I6 — committed never decreases; debug_assert!(new_committed >= committed); raft.commit.regression_attempt.
  • I7 — every term bump, vote, append and snapshot chunk is durable before its reply; negative fixture reorder-persist-before-reply; raft.persist.lag_ms.
  • I8 — first_index = snapshot_last.index + 1 always; the crash_recovery.rs property test; raft.log.first_index versus raft.snapshot.last_index, alert on drift.
  • I9 — at most one membership change in flight; fixture concurrent-membership-change-rejected; raft.config.change_rejected{reason="pending"}.
  • I10 — every snapshot embeds its configuration; fixture install-with-config-restore; raft.snapshot.capture.done{config_present=true}.
  • I11 — same seed and scenario give a byte-identical simulator trace; CI re-runs a seed twice and diffs report.json.
  • I12 — in-flight AppendEntries per follower never exceeds max_inflight; a unit test asserts the guard fires at max_inflight+1; raft.replicate.backpressure{peer}.
  • I13 — no ReadIndex is served until the term's no-op is committed; negative fixture read-with-no-noop-pending; raft.read_index.rejected{reason="no_noop"}.
  • I14 — a removed node is neither replicated to nor listened to; fixture remove-voter-messages-dropped; raft.net.dropped{reason="not_in_config"}.

Every invariant maps to a method on raft-sim::invariants::InvariantChecker, run after every simulated step; a violation emits a minimal reproducing trace (seed, scenario, step index) (§7, §20).

What breaks in production

  • FM-1 — leader churn, repeated elections. The election timeout sits too close to the RTT, or pre-vote is disabled; raft.election.start above 1/min is the tell; nothing recovers automatically — widen the timeout and re-enable pre-vote (§23, §15).
  • FM-2 — one follower permanently lagging. Its Progress is stuck in Probe from a conflict-hint bug; raft.replicate.send{to} sits near zero for that peer; restart the follower, then replace the node, using the Progress dump from raft-cli status (§23, §16).
  • FM-3 — a node will not restart after a crash. An undetected torn write, or the log and snapshot anchors disagree; the startup consistency check fails and the node refuses to start as leader-eligible; recovery is the restore-from-snapshot.md runbook (§23).
  • FM-4 — reconfiguration stuck. One side's joint quorum is unreachable, so PendingConfigChange never resolves; detected by its age; restore the unreachable node or submit a corrective ConfigChangeRequest (§23, §17).
  • FM-6 — a client observes a linearizability violation. Lease reads were enabled with an insufficient skew bound, or the no-op guard has a bug; the Jepsen checker finds it with a counter-example; it is release-blocking — disable lease reads and roll back (§23, §21).
  • FM-7 — leader OOM under replication load. Unbounded pipelining to a stalled follower; a memory alert fires while raft.replicate.backpressure is absent; the Progress::full guard should prevent this, so its absence is the bug; restart the leader, audit max_inflight (§23, I12).
  • FM-9 — no leader anywhere. A total partition or a majority of voters down; raft.election.win is absent cluster-wide; nothing automatic helps, and that is correct — the cluster is unavailable, not unsafe (§23, I1).
  • FM-12 — compaction breaks log/snapshot continuity. A bug bypassed the compact_prefix precondition; the first_index = snapshot_last.index + 1 assertion fires; debug builds abort, release builds refuse further compaction; restore the node from a good snapshot (§23, I8).

Threats (§22): T1 forgery by an unauthenticated peer — mutual TLS by default; T3 replay of a captured AppendEntriesReq — TLS freshness plus rejection of any stale-term message (I1); T4 disk bit-rot — a CRC32C trailer on every log record and snapshot chunk, and no advancing committed past a bad record; T6 a fully compromised voter — out of scope, since Raft assumes crash faults, not Byzantine ones (§22, §34); T9 a follower that stalls without disconnecting — bounded max_inflight/max_msg_bytes (P12, I12).

How it compares

  • etcd/raft ships the protocol core as a bare state machine with a Ready()-based I/O loop the caller drives — the direct ancestor of this blueprint's step/tick/Outbox split; its niche is embeddability into very different storage and transport stacks (etcd, CockroachDB, TiKV) (§31).
  • hashicorp/raft chose a batteries-included transport, an in-process FSM callback model, single-server membership change and lease-based reads; its niche is single-deployment simplicity (Consul, Nomad), where a swappable transport is not worth the complexity this design accepts for cross-project reuse (§31).
  • tikv/raft-rs ported etcd/raft near-literally into Rust rather than redesigning around ownership; its niche is minimal divergence from a battle-tested Go implementation, whereas this design leans further into type-state roles and the Outbox for the simulator (§31).
  • ZooKeeper / Zab put a coordination-service API (znodes, watches, ephemeral nodes) on top of its broadcast protocol, with local reads and sync() for linearizable ones; its niche is exactly "a coordination service", which is why the blueprint studies Zab but does not adopt its API shape (§31).
  • logcabin/logcabin is Ongaro's own reference implementation; its niche is ground truth for dissertation ambiguity, not production use (it is unmaintained), so it is treated as a citation source rather than a model (§31).

  2.   3. What specific unsafe interleaving does joint consensus prevent that single-server membership change cannot, and why does one extra committed entry close it — synthesize §17 Phase 5 with §6 P7. — Hint: the both-majorities rule in §17 and the rationale column of ADR-08.
  4. Why does the simulator's determinism guarantee depend on banning HashMap outright rather than merely seeding its hasher deterministically — synthesize §20 Phase 8 (I11) with §11's use of BTreeSet/BTreeMap throughout the core types. — Hint: §20's pitfalls and MM6.
  5. Why must InstallSnapshot embed the configuration rather than relying on the receiver's already-known peer list — synthesize §18 Phase 6 (I10) with §17 Phase 5's concurrent-membership-change possibility. — Hint: MM5 and P13.

If you only remember three things

Commit is a property of a majority, not of the leader's disk, and nothing is promised to anyone before it has been fsynced (MM3, P6). A term is a trust clock, and the Election Restriction plus the no-op on election are what make "committed" survive a change of leader (MM2, I1, I4). The protocol core does no I/O and owns no clock, so the deterministic simulator — not the protocol code — is where the library's correctness is actually earned (P1, P10, §2).

Words used here

  • Heartbeat — an empty AppendEntriesReq the leader sends to maintain authority.
  • Term — a logical period of leadership, bumped on every real election.
  • Quorum — a majority of voters in the current Configuration; both sets under Joint.
  • Commit / committed — an entry a majority of voters durably hold; only then may it be applied.
  • Election Restriction — a vote goes only to a candidate whose log is at least as up to date.
  • No-op — the blank entry a new leader appends so prior-term entries become committable.
  • Pre-Vote — a term-preserving vote solicitation before a real election.
  • Outbox — what step/tick emit for the caller to drain: messages, persists, applies, events.
  • Progress — the leader's per-follower flow-control state: next_index, match_index, state.
  • Joint Consensus — the two-phase membership change through C_old,new.
  • Learner — a non-voting replica that receives the log but counts toward no quorum.
  • ReadIndex — a linearizable read: confirm leadership by heartbeat, wait for applied >= committed.
