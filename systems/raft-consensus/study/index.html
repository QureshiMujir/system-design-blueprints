30. Mental Models & First Principles

  • MM1 — A Raft cluster is a single-writer replicated log, not N independent databases. Predicts: any write path bypassing the leader is definitionally not linearizable. Bug class without it: an engineer adds a "fast write path" on a follower for latency and silently breaks State Machine Safety. Applied in §16 Phase 4, I5/I6.
  • MM2 — Term is a logical clock for "who may I trust right now," not an election counter. Predicts: a message carrying a lower term is stale information to discard, not older information to reconcile. Bug class without it: a node tries to "merge" a lower-term message instead of ignoring it, reintroducing stale-leader writes. Applied in §15 Phase 3, I1.
  • MM3 — Commit is a property of a majority, not of the leader's local disk. Predicts: a leader's own fsync completing guarantees nothing about durability until a majority also holds the entry. Bug class without it: responding to a client before majority ack — "fire and forget" persistence. Applied in §16 Phase 4, I6, P6.
  • MM4 — The log is the state machine's only legitimate input channel. Predicts: any side-channel mutation of the FSM (an operator "just this once" direct edit) desyncs replicas silently and permanently. Bug class without it: manual out-of-band data fixes applied to one replica. Applied in §14 Phase 2, I5.
  • MM5 — A snapshot is a compressed prefix of the log, not a separate source of truth. Predicts: a snapshot missing the embedded configuration is definitionally incomplete, because configuration lives inside the log stream itself. Bug class without it: a hand-rolled snapshot format that forgets configuration and strands a restored node with no peers. Applied in §18 Phase 6, P13, I10.
  • MM6 — Determinism is a property of the whole call graph, not of any one function. Predicts: one nondeterministic call reachable from step() invalidates every invariant test built on the simulator, even unrelated-looking ones. Bug class without it: "it's just a UUID generator, how could that matter" reasoning. Applied in §20 Phase 8, I11.
  • MM7 — Pre-vote separates "can I win" from "do I commit to trying." Predicts: a system without this separation cannot avoid disturbing a working leader after any transient network hiccup. Bug class without it: unnecessary leader churn misdiagnosed as "network flakiness" instead of a protocol design gap. Applied in §15 Phase 3, P8.
  • MM8 — ReadIndex trades latency for a clock-free safety proof; lease reads trade the proof for latency. Predicts: enabling lease reads without verifying clock discipline is an availability/latency choice masquerading as a configuration flag. Applied in §19 Phase 7, P9.

5. Required Reading

Books

  • Kleppmann, Martin. Designing Data-Intensive Applications. O'Reilly, 2017. Ch. 5 "Replication" (leader-based replication, sync/async trade-offs); Ch. 8 "The Trouble with Distributed Systems" (partial failure, clocks); Ch. 9 "Consistency and Consensus" (linearizability, total order broadcast, consensus). Applied in §7 (invariants), §19 Phase 7 (ReadIndex linearizability).
  • Petrov, Alex. Database Internals. O'Reilly, 2019. Part II, "Distributed Systems" — chapters on failure detection, leader election, replication, and consistency models, including a direct treatment of Raft's log-replication design. Applied in §13 Phase 1 (log/storage layout), §16 Phase 4 (replication).
  • Cachin, Christian; Guerraoui, Rachid; Rodrigues, Luís. Introduction to Reliable and Secure Distributed Programming, 2nd ed. Springer, 2011. The consensus and total-order-broadcast chapters (abstraction specifications, reductions between problems). Applied in §7 (I1–I5 stated as abstract properties before their Raft-specific enforcement).
  • Lynch, Nancy A. Distributed Algorithms. Morgan Kaufmann, 1996. Part on fault-tolerant consensus — FLP impossibility and the solvability results that motivate every practical consensus protocol's timing assumptions. Applied in §4 (why election timeout must exceed RTT) and §33 Hard Questions (HQ on FLP and partial synchrony).
  • Tanenbaum, Andrew S.; Van Steen, Maarten. Distributed Systems: Principles and Paradigms, 3rd ed., 2017. Chapters on consistency & replication and on fault tolerance (reliable group communication, distributed commit). Applied in §17 Phase 5 (membership change as a distributed-commit problem).
  • Ghosh, Sukumar. Distributed Systems: An Algorithmic Approach, 2nd ed. CRC Press, 2014. Chapters on agreement protocols and fault-tolerant broadcast. Applied in §22 Threat Model (Byzantine-vs-crash-fault framing, why Raft assumes the latter).
  • Birman, Kenneth P. Guide to Reliable Distributed Systems. Springer, 2012. Chapters on virtual synchrony and group communication, the historical alternative to quorum-based consensus. Applied in §34 Alternative Architectures (contrast with Viewstamped Replication's view-change model).

Papers

  • Ongaro, Diego; Ousterhout, John. "In Search of an Understandable Consensus Algorithm (Extended Version)." USENIX ATC, 2014. The Raft paper. Applied throughout — §15/§16/§17 Phases 3–5 implement it directly.
  • Ongaro, Diego. Consensus: Bridging Theory and Practice. PhD dissertation, Stanford University, 2014. The canonical full reference — membership change (Ch. 4), log compaction (Ch. 5), client interaction/linearizability (Ch. 6). Applied in §17 Phase 5 (joint consensus, Ch. 4), §18 Phase 6 (snapshots, Ch. 5), §19 Phase 7 (ReadIndex, Ch. 6).
  • Lamport, Leslie. "The Part-Time Parliament." ACM TOCS 16, 1998. The original Paxos paper. Applied in §31 Comparative Architecture Table and §34 Alternative Architectures (Multi-Paxos contrast).
  • Lamport, Leslie. "Paxos Made Simple." ACM SIGACT News 32, 2001. The accessible restatement. Applied in §34 (Multi-Paxos sketch).
  • Junqueira, Flavio P.; Reed, Benjamin C.; Serafini, Marco. "Zab: High-performance broadcast for primary-backup systems." DSN, 2011. Applied in §31 and §34 (Zab comparison and alternative).
  • Oki, Brian M.; Liskov, Barbara. "Viewstamped Replication: A New Primary Copy Method to Support Highly-Available Distributed Systems." PODC, 1988. Applied in §34 Alternative Architectures (Viewstamped Replication sketch).
  • Fischer, Michael J.; Lynch, Nancy A.; Paterson, Michael S. "Impossibility of Distributed Consensus with One Faulty Process." JACM 32, 1985. The FLP result. Applied in §33 Hard Questions (why Raft relies on randomised timeouts, not a deterministic decision procedure, to circumvent FLP in practice).
  • Howard, Heidi; Schwarzkopf, Malte; Madhavapeddy, Anil; Crowcroft, Jon. "Flexible Paxos: Quorum Intersection Revisited." OPODIS, 2016. Applied in §35 Deferred Features Register (flexible quorums) and §19 Phase 7 (why ReadIndex's heartbeat quorum equals the replication quorum today).
  • Burrows, Mike. "The Chubby Lock Service for Loosely-Coupled Distributed Systems." OSDI, 2006. Applied in §31 Comparative Architecture Table (Multi-Paxos-backed lock service as a real embodiment).
  • van Renesse, Robbes; Schneider, Fred B. "Chain Replication for Supporting High Throughput and Availability." OSDI, 2004. Applied in §34 Alternative Architectures (Chain Replication sketch).
  • Moraru, Iulian; Andersen, David G.; Kaminsky, Michael. "There Is More Consensus in Egalitarian Parliaments." SOSP, 2013. (EPaxos.) Applied in §33 Hard Questions (leaderless-consensus trade-off question).
  • Kingsbury, Kyle. Jepsen analyses (etcd, Consul, CockroachDB), jepsen.io, 2014–. Applied in §23 Failure Modes & Recovery and §21 Phase 9 (fault-injection scenario design directly modelled on Jepsen nemeses).
  • Abadi, Daniel. "Consistency Tradeoffs in Modern Distributed Database System Design." IEEE Computer 45, 2012. Applied in §19 Phase 7 (ReadIndex vs. lease-read framing under PACELC).
  • Wilson, Will. "Testing Distributed Systems with Deterministic Simulation." Strange Loop, 2014. Applied in §20 Phase 8 (the raft-sim architecture is a direct descendant).

Reference Implementations

  • etcd-io/raft (Go; module moved out of etcd-io/etcd as of etcd v3.5). Study raft.go, node.go, log.go, progress.go, read_only.go, confchange/, rafttest/. Lesson: progress.go's Probe/Replicate/Snapshot state machine is the cleanest published model for leader-side flow control — mirrored in Progress/ ProgressState (§11, §16 Phase 4). Pitfall: its single-threaded Ready()-loop API couples storage and network flushing in a way that is easy to copy uncritically; this blueprint keeps them as separate Outbox categories instead (P3).
  • tikv/raft-rs — the closest-in-shape Rust port. Study src/raft.rs, src/raft_log.rs. Lesson: shows the exact ergonomics of translating etcd/raft's design into Rust's ownership model — applied directly in §11 Core Schema & Types' signature choices. Pitfall: it exposes more internal mutability through RefCell-like patterns than this blueprint allows (P4 forbids shared mutable state, enforced from §12 Phase 0 onward).
  • hashicorp/raft — the original Go implementation, opinionated long-lived-RPC transport, in-process FSM. Useful counterpoint: study its raft.go election/replication loop. Pitfall: its LogStore/StableStore/SnapshotStore traits are close to this blueprint's (§11.9) but its transport is not swappable at the same granularity as raft-net's Transport trait.
  • logcabin/logcabin — Diego Ongaro's own reference implementation accompanying the dissertation. Study Server/RaftConsensus.cc. Lesson: the closest artefact to "what the dissertation author actually built" — applied in §17 Phase 5 to resolve joint-consensus ambiguity the dissertation text leaves underspecified. Pitfall: C++03-era code, unmaintained — read for the algorithm, not for API design.
  • lni/dragonboat — a high-throughput Go implementation with witness replicas and multi-Raft sharding already built. Lesson: its witness-replica design is the direct model for the deferred witness-replica feature (§35). Pitfall: its multi-Raft sharding couples transport and storage more tightly than this blueprint's crate boundaries allow.

RFCs / Specifications

  • raft.github.io — protocol summary and interactive visualisation. Applied in §15 Phase 3 onboarding (the visualisation is the fastest way to internalise the election dance before writing election.rs).
  • Protocol Buffers Language Guide (proto3) — the wire-format specification underlying raft.proto (ADR-15). Applied in §8 Domain Model (wire layouts).
  • RFC 7540 — Hypertext Transfer Protocol Version 2 (HTTP/2) — the transport tonic's gRPC implementation runs over (ADR-04). Applied in §16 Phase 4 (why message framing and flow control interact with HTTP/2 stream-level flow control).
  • RFC 8446 — The Transport Layer Security (TLS) Protocol Version 1.3 — the mutual-TLS baseline raft-net requires by default (§22 Threat Model).

Glossary (§36) · 41 terms · site-wide glossary

AppendEntries
The RPC the leader uses to replicate log entries and to heartbeat.
Apply
Feeding a committed entry to the state machine (§14 Phase 2).
Backpressure
The bounded-inflight discipline (max_inflight, max_msg_bytes) that prevents a leader from OOMing against a slow follower (P12, I12).
Catch-up Window
The maximum lag (catch_up_window, default 1,000) a candidate voter may have before promotion is allowed (§17 Phase 5).
Commit / Committed
A log entry is committed once a majority of voters durably hold it; only then may it be applied (I6).
Configuration
The set of voters and learners; Stable or Joint (§11.4).
Conformance Fixture
A named JSON file describing setup/steps/expected outbox, run by the portable conformance runner (§21 Phase 9, §11.16).
Deterministic Simulator
raft-sim; produces byte-identical traces for a fixed seed and scenario (I11, §20 Phase 8).
Election Restriction
A node grants its vote only if the candidate's log is at least as up-to-date as its own (§15 Phase 3, I1).
Election Safety
At most one leader per term (I1).
FollowerRead
Linearizable reads served by a follower via ReadIndex forwarding (§19 Phase 7).
First-Index Continuity
first_index = snapshot_last.index + 1 after every compaction (I8).
Heartbeat
An empty AppendEntriesReq the leader sends to maintain authority.
InstallSnapshot
The RPC used to send a snapshot to a lagging follower (§18 Phase 6).
Invariant
A protocol-level correctness property (I1–I14, §7) checked by InvariantChecker after every simulated step.
Jepsen
The fault-injection/linearizability-checking methodology (Kingsbury, §5) this blueprint's raft-jepsen (§21 Phase 9) directly models.
Joint Consensus
The two-phase membership-change protocol via C_old,new (P7, §17 Phase 5).
Leader Append-Only
A leader never overwrites or deletes its own log entries (I2).
Leader Completeness
Every committed entry is present in the log of every future leader (I4).
Leader Transfer
A graceful handoff of leadership via TimeoutNow (§15 Phase 3).
Learner
A non-voting replica that receives the log but is excluded from every quorum computation (§17 Phase 5).
Lease Read
An opt-in, clock-bounded linearizable-read optimisation (P9, §19 Phase 7).
Log Matching
Identical (index, term) implies identical preceding entries (I3).
Match Index
The highest index the leader has confirmed replicated to a given follower (§11.11).
Membership Change
A ConfigChangeRequest adding/removing voters or learners (§17 Phase 5).
Next Index
The next index the leader will send to a given follower (§11.11).
No-op
A blank entry the leader appends on election to enable committing prior-term entries (I4, §15 Phase 3).
Outbox
The drained-by-caller container for messages, persistence requests, apply requests, snapshot ops, and events emitted by step/tick (P3, §11.6).
PersistOp
A queued durability request the caller must perform before the protocol proceeds past the dependent action (I7).
Pre-Vote
A term-preserving vote solicitation used before a real election, to avoid disturbing a healthy leader (P8, §15 Phase 3).
Progress
The leader's per-follower flow-control state (next_index, match_index, ProgressState, §11.11).
Quorum
A majority of voters in the current Configuration (both sets, under Joint).
ReadIndex
The linearizable-read protocol confirming leadership via heartbeat and waiting for applied >= committed (I13, §19 Phase 7).
RequestVote
The RPC a candidate uses to solicit votes.
State Machine Safety
No two servers ever apply different entries at the same index (I5).
Stable State
The persisted current_term and voted_for pair (§8.3).
Term
A logical period of leadership; bumped on every real election (MM2).
TimeoutNow
The message a leader sends to trigger an immediate election on a leader-transfer target (§15 Phase 3).
Voter
A node that participates in elections and counts toward commitment quorums.
Wire Format Additive Evolution
The rule that proto fields are added, never repurposed or removed, enabling mixed-version rolling upgrades (P11, §25).
Witness Replica
A non-voting, quorum-counted replica holding only term/index metadata, reducing storage cost in geo-distributed deployments (§35, deferred).
