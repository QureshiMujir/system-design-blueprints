39 — Raft Consensus Library

Project Number: 39

Project Name: Raft Consensus Library

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a production-grade Raft consensus library in Rust — a sync, message-driven protocol core plus pluggable storage/transport crates plus a deterministic simulator and an external Jepsen-style fault-injection harness — implementing the full protocol of Ongaro's dissertation (leader election, log replication, safety properties, persistence/crash recovery, joint-consensus membership change, snapshots/InstallSnapshot) plus the optimisations every production Raft library ships (pre-vote, leader transfer, learners, ReadIndex linearizable reads, batching, pipelining), so that downstream systems in this workspace (the Distributed Key-Value Store, project 38; the Distributed Job Queue, project 40; the Service Discovery System, project 42) can obtain strongly consistent replicated state through a small, stable trait surface instead of each re-deriving consensus.

Phase-0 deliverable — numbered modules/crates:

  1. raft — protocol core: roles, election, replication, membership, snapshot, read-index, outbox (§11).
  2. raft-storage — persistence trait + redb / file / memory backends (§11, §13).
  3. raft-net — transport trait + tonic gRPC implementation (§11, §16).
  4. raft-sim — deterministic simulator: scheduler, fault injector, invariant checker (§20).
  5. raft-jepsen — external nemesis harness over real Linux network namespaces (§21).
  6. raft-cli — operator CLI: status, add/remove voter, transfer, snapshot (§10).
  7. conformance — portable, JSON-fixture protocol conformance runner (§21).
  8. benchmarks — Criterion suites gated in CI (§28).

System boundaries.

  • Provides: single-Raft-group strong consistency (linearizable writes and, via ReadIndex, linearizable reads), crash-safe persistence, safe membership reconfiguration, log compaction, a pluggable StateMachine trait, an operator CLI, and a deterministic correctness harness reusable by any consumer.
  • Delegates: transport encryption (mutual TLS is a raft-net feature, not enforced by the protocol core), application-level idempotency (I5, §7), sharding/partitioning across multiple Raft groups (Multi-Raft — Deferred Features Register), and disk-level bit-rot correction beyond CRC32C trailers (delegated to the filesystem/RAID layer).
  • Does NOT provide: Byzantine fault tolerance (a compromised node breaks safety by design — §22), cross-datacentre WAN-optimised replication (intra-datacentre RTT is the design point — §4), a managed control plane, or erasure-coded log storage (Deferred Features Register).

Non-goals (each PhaseDeferred("Deferred Features Register")):

  • Byzantine fault tolerance — PhaseDeferred("Deferred Features Register").
  • Multi-Raft (sharded groups sharing transport/disk) — PhaseDeferred("Deferred Features Register").
  • Flexible quorums (independent election/replication quorum sizing) — PhaseDeferred("Deferred Features Register").
  • Witness (non-voting, quorum-counted) replicas — PhaseDeferred("Deferred Features Register").
  • no_std embedded build of the protocol core — PhaseDeferred("Deferred Features Register").
  • In-memory-only (volatile) Raft mode — PhaseDeferred("Deferred Features Register").
  • Raft over QUIC transport — PhaseDeferred("Deferred Features Register").
  • TLA+ formal model of the protocol core — PhaseDeferred("Deferred Features Register").
  • Erasure-coded log storage — PhaseDeferred("Deferred Features Register").
  • Managed/hosted control plane and commercial dashboards — PhaseDeferred("Deferred Features Register").

Deployment model. A single Raft group is 3, 5, or 7 voter processes (odd, §4) plus zero or more learners, one process per node, intra-datacentre (same region, cross-AZ tolerated), communicating over mutual-TLS gRPC (raft-net), each with local NVMe storage (raft-storage). The library links into a host application process; it does not run as a sidecar.

Target users/operators. Systems engineers building the next layer (KV stores, queues, locks, discovery) who need to own the consensus path rather than depend on a managed service, plus the on-call engineer who must debug a stuck cluster at 3 a.m. from the raft-cli and the runbooks in docs/runbooks/.

What later phases unlock. Phase 0 (§12) unlocks a compilable, governed workspace. Phases 1–2 (§13–§14) unlock a storage and application contract. Phases 3–5 (§15–§17) unlock a safe replicated log. Phase 6 (§18) unlocks unbounded log growth via compaction. Phase 7 (§19) unlocks linearizable reads. Phases 8–9 (§20–§21) unlock the correctness harness that every later consumer relies on before trusting the library in production.

Recommended language: Rust (1.78+ stable). Rationale: type-state role modelling (Role::Follower|Candidate|PreCandidate|Leader|Learner as a real enum, not a flag byte), deterministic destructors for outbox/persistence resource cleanup, and no GC pauses that would jitter election timers (a stop-the-world pause longer than min_election_timeout is a spurious leader-change). Rejected: Go — etcd/raft and hashicorp/raft prove it works, but GC pauses interact with election timing and the workspace's testing strategy (type-state, loom model-checking) leans on Rust's ownership model. Rejected: C++ — comparable determinism, but no equivalent to cargo's reproducible dependency story or to proptest/madsim's ecosystem maturity for this specific testing strategy. Rejected: Java/JVM — GC pauses are a harder problem for sub-200ms election timeouts than in Go.

Prerequisites. Async Rust (tokio) for the transport crate; comfort with finite-state machines; one prior consensus or replication protocol studied (Paxos, Zab, primary-backup) so Raft's simplifications are legible by contrast; the Ongaro dissertation (§5) read before Phase 3 begins; willingness to write several times more test code than protocol code (§26).

Estimated timeline. Phase 0 (§12): 3–4 weeks. Full library (Phases 0–9, §12–§21, to the depth of etcd/raft/tikv/raft-rs): 4–6 months, dominated by the simulator (§20) and conformance suite (§21), not by the protocol code itself (§27 Final Notes analogue in §26).

2. Why Build This

  • Raft won the open-source consensus space because Ongaro & Ousterhout (§5) optimised explicitly for understandability over ZAB/Paxos — but "understandable" is not "easy to ship": every production Raft library (etcd/raft, hashicorp/raft, tikv/raft-rs, dragonboat) spent years hardening corner cases the dissertation only hints at.
  • AppendEntries reply handling is ~30 lines of dissertation pseudocode and ~300 lines in any production library — the gap is slow followers, out-of-order replies, step-down on stale replies, interaction with snapshot delivery (§16). Writing those 300 lines is the only way to internalise the corner cases; reading about them is not the same skill.
  • The deterministic simulator (§20) is the single most valuable artefact, not the protocol implementation — FoundationDB's correctness reputation rests on the same technique (Wilson 2014, §5); Jepsen's bug-finding reputation (Kingsbury, §5) is the next layer up. Both layers are first-class deliverables here, not afterthoughts.
  • Strong consistency is becoming uncomfortable to fully outsource — workload-aware replica placement, custom snapshot compression, cross-region read leases, and application-defined linearizability boundaries all require owning the consensus path; owning it once here lets every later workspace project stop hand-waving about agreement.
  • Cross-links: the Distributed Key-Value Store (project 38) is the first consumer of StateMachine/LogStorage (§11); the Distributed Job Queue (project 40) and Service Discovery System (project 42) are the next two; any future primary-election or distributed-lock project in the workspace should consume this library rather than hand-roll leader election.
  • Calibration value. A engineer who ships this cannot be fooled by a vague "we use Raft under the hood" claim in a vendor's architecture doc — they know exactly what "under the hood" must contain: the three persistent shapes (P2), the outbox discipline (P3), the no-op-on-election rule (I4), and the simulator (P10).

What Mastery Looks Like (competencies gained, each tied to a named phase):

  • Can explain, from memory, why a freshly elected leader must commit a no-op before counting replicas toward commitment of prior-term entries — the Figure-8 hazard — after §15 Phase 3.
  • Can design a leader-side flow-control scheme (Progress states, inflight windows) that cannot OOM against one slow follower — after §16 Phase 4.
  • Can reason about joint-consensus quorum arithmetic (C_old ∧ C_new majorities) well enough to catch a single-server-membership-change bug in review — after §17 Phase 5.
  • Can design a chunked, resumable bulk-transfer protocol (InstallSnapshot) that does not stall a leader's other replication streams — after §18 Phase 6.
  • Can implement a linearizable-read protocol without assuming bounded clock skew (ReadIndex) and explain when the bounded-skew shortcut (lease reads) is and is not safe — after §19 Phase 7.
  • Can build a deterministic, seed-reproducible distributed-systems simulator — the single highest-leverage distributed-systems testing skill — after §20 Phase 8.
  • Can run and interpret a Jepsen-style linearizability check against a real binary under real network-namespace faults — after §21 Phase 9.
  • Can redesign the whole system around a fundamentally different consensus protocol (Multi-Paxos, Zab, Viewstamped Replication, Chain Replication) and state precisely what trades — after §34 Alternative Architectures.

RaftNode (the FSM). Owns no threads, no clock, no sockets (P1). Public surface is step(from, Message), tick(elapsed), propose(bytes), change_membership(...), read_index(ctx), drain_outbox(), on_persisted(id), on_snapshot(ev) (§11.7). All state transitions are synchronous and total.

Role state. Follower | PreCandidate | Candidate | Leader | Learner, an enum (never a flag byte), each carrying only the state relevant to that role (§11, §15 Phase 3).

step()/tick() dispatch. step handles inbound Message variants (§11.5); tick advances logical time, firing election timeouts and heartbeats. Neither performs I/O; both only mutate in-memory state and push into Outbox (P1, P3).

Outbox. Messages to send, persistence requests (PersistOp), state-machine apply requests, snapshot ops, and observability Events — drained by the caller after every step/tick (§11.6, P3).

RaftLog. The in-memory sliding window over the log plus the snapshot anchor (snapshot_last), committed, last_applied (§11, §13 Phase 1, I8).

Election & Progress. Election timers, vote bookkeeping, and per-follower Progress (next_index/match_index/inflight window) that drives replication flow control (§15–§16 Phases 3–4, I12).

Snapshot coordinator. Capture/compaction/InstallSnapshot streaming state machine (§18 Phase 6, I10).

raft-storage. LogStorage / StableStore / Snapshotter traits plus redb (default), file (reference), and memory (test/sim) backends (§11.9, §13 Phase 1).

raft-net. Transport trait plus a tonic gRPC implementation with mutual TLS as a feature (§11.10, §22 Threat Model).

raft-sim. The deterministic scheduler, network/disk/clock fault injector, and the InvariantChecker that runs every invariant (I1–I14, §7) after every simulated step (§20 Phase 8).

raft-jepsen. An out-of-process harness driving real binaries under real Linux network namespaces with a Knossos-style linearizability checker over recorded histories (§21 Phase 9).

All later sections stay consistent with this diagram: the same crate names, module names, and type names recur unchanged in §10 (Repository Layout), §11 (Core Schema & Types), every phase, and Appendix A (§37).

4. System Constraints

Defining property: the protocol core performs no I/O and owns no clock — every constraint below is therefore expressed either as a caller-facing bound (memory, throughput, latency) or a configuration default in §11's Settings struct.

Learners 0–32 per cluster (soft cap) Non-voting; bounded by leader fan-out bandwidth (§32 capacity model).
Steady-state memory (leader, 3-node, at M-table throughput) ≤ 256 MiB heap §28 M6; includes inflight AppendEntries buffers, Progress maps, in-memory log window.
Sustained throughput 50,000 committed ops/s 256-byte payload, 3-node cluster, commodity NVMe SSD, batching enabled (§28 M1).

Availability / failure budget Tolerates ⌊(N-1)/2⌋ simultaneous voter failures without losing availability I1, I4; a >⌊(N-1)/2⌋ failure loses availability, not safety.
RTO (leader crash) 2–4× election timeout, p95 ≤ 1.2 s Detection (missed heartbeats) + pre-vote round + election round.
RTO (node replaced) Bounded by catch_up_window (default 1000 entries) at replication throughput §17 Phase 5.
Backpressure ceiling Leader pauses a peer's stream at max_inflight; never queues unboundedly I12.

6. Design Principles

  • P1 — Protocol core is a pure state machine. Rule: no tokio::time::sleep, mio::Poll, or TcpStream reachable from the raft crate; everything driven by step(message)/tick(elapsed). Tradeoff: forfeits async ergonomics inside the core. Operational implication: this is the precondition for the deterministic simulator (§20). Violating it: any nondeterministic call (thread spawn, wall-clock read) inside step silently breaks simulator replay and hides races until production.
  • P2 — Exactly three persistent shapes. Rule: log, stable state (currentTerm + votedFor), snapshot — no more. Tradeoff: some optimisations need extra plumbing above these three rather than a fourth persisted shape. Operational implication: durability code review scope stays at three fsync paths. Violating it: an ad hoc fourth persisted shape bypasses the persist-then-act discipline (P6, I7) and causes silent data loss on crash.
  • P3 — Outbox, not callbacks. Rule: step/tick only push into Outbox (§11.6); the caller drains it; no callback fires from inside step. Tradeoff: caller must run an explicit drain loop every call. Operational implication: reentrancy is impossible by construction, so the simulator's replay is exact (I11). Violating it: a callback firing from inside step can re-enter the same RaftNode mid-transition and corrupt state.
  • P4 — No shared mutable state between nodes. Rule: cross-node communication is messages only; each RaftNode owns its data. Tradeoff: every fact needed by a peer must be message-carried, no shortcuts. Operational implication: the simulator can schedule any interleaving without hidden races (§20). Violating it: introduces races invisible to single-threaded testing, reproducible only under specific network timing.
  • P5 — Term bumps and role changes are observable events. Rule: every Term mutation and role transition emits an Event (§11.6). Tradeoff: an emission call at every mutation site. Operational implication: production dashboards and the simulator's invariant checker consume the same event stream (§24). Violating it: an unobservable term bump defeats the audit trail used to diagnose split-vote storms.
  • P6 — Persist-then-act, never act-then-persist. Rule: the API forces recording a PersistOp and blocking forward progress on that action until on_persisted is called. Tradeoff: adds one fsync round-trip of latency before certain replies. Operational implication: this is the single most load-bearing rule in the system (I7). Violating it: the "committing on a lie" bug class — a node replies as durable, crashes, and the promise is false on restart.
  • P7 — Joint consensus, not single-server membership change. Rule: every membership change transits C_old,new before C_new (dissertation Ch. 4; §17 Phase 5). Tradeoff: two committed entries and more round trips versus a single-entry change. Operational implication: eliminates the known unsafe single-server-change interleaving (ADR-08). Violating it: reintroduces the disjoint-double-majority race documented on the raft-dev mailing list.
  • P8 — Pre-vote before every real election. Rule: a candidate campaigns with PreVote (no term bump) before it actually increments its term (dissertation Section 9.6; §15 Phase 3). Tradeoff: one extra RTT before every election, even legitimate ones. Operational implication: a partitioned-then-healed minority cannot disturb a healthy leader. Violating it: reproduces term-inflation storms after every partition heal.
  • P9 — ReadIndex is the unconditional read path; lease reads are opt-in. Rule: every build supports ReadIndex without configuration (§19 Phase 7, I13); lease reads require an explicit bounded-clock-skew acknowledgement. Tradeoff: ReadIndex costs one heartbeat RTT per linearizable read. Operational implication: correctness never silently depends on clock synchronisation. Violating it (enabling lease reads without a skew bound) risks serving stale reads across an undetected leadership change.
  • P10 — The simulator is a first-class deliverable. Rule: raft-sim ships as its own crate with its own conformance suite (§20 Phase 8), not as a test fixture buried in raft/tests/. Tradeoff: a whole extra crate with its own release cadence. Operational implication: the correctness budget of the entire library depends on it running continuously in CI (§26). Violating it (skipping it) correlates with every publicly known Raft-library correctness incident (Wilson 2014, §5).
  • P11 — The wire format is versioned and additive by default. Rule: every message struct carries reserved fields and a version tag from Phase 0 (§12). Tradeoff: message structs are larger than a minimal encoding. Operational implication: rolling upgrades (§25) never require a synchronised whole-cluster restart. Violating it: an older-binary follower silently misparses a newer leader's message instead of rejecting it cleanly.
  • P12 — Backpressure is explicit and bounded everywhere. Rule: max_inflight, max_msg_bytes, snapshot_chunk_size are hard ceilings, never soft targets (§4, I12). Tradeoff: throughput is capped below theoretical link speed. Operational implication: a leader can never OOM itself replicating to one slow follower. Violating it: an unbounded pipeline exhausts leader memory the first time a follower stalls.
  • P13 — Configuration lives inside the log and inside every snapshot. Rule: every snapshot embeds the Configuration as of its last_included_index (dissertation Section 5.4; §18 Phase 6, I10). Tradeoff: snapshot format complexity increases. Operational implication: a node restored from a snapshot always knows its peers without an external bootstrap file. Violating it: a restored node cannot locate quorum and needs manual rejoin.
  • P14 — Every acceptance criterion is a number, a fixture, or a checked property. Rule: no phase's N.4 Acceptance Criteria (§12–§21) may read "works" or "robust" — every criterion in this blueprint's own phase sections carries a number or a named fixture. Tradeoff: specs take longer to write up front. Operational implication: CI gates a release without a human judgment call. Violating it: exactly the failure this blueprint corrects for.

8. Domain Model / Protocol / Data Model

8.1 RPC wire formats (proto3, ADR-15)

message RequestVoteReq   { uint64 term=1; uint64 candidate_id=2; uint64 last_log_index=3;
                            uint64 last_log_term=4; bool pre_vote=5; }
message RequestVoteReply { uint64 term=1; bool vote_granted=2; bool pre_vote=3; }

message AppendEntriesReq   { uint64 term=1; uint64 leader_id=2; uint64 prev_log_index=3;
                              uint64 prev_log_term=4; repeated LogEntryProto entries=5;
                              uint64 leader_commit=6; }
message AppendEntriesReply { uint64 term=1; bool success=2; uint64 match_index=3;
                              optional uint64 conflict_term=4; optional uint64 conflict_index=5; }

message InstallSnapshotReq   { uint64 term=1; uint64 leader_id=2; uint64 last_included_index=3;
                                uint64 last_included_term=4; ConfigurationProto config=5;
                                uint64 offset=6; bytes data=7; bool done=8; fixed32 crc32c=9; }
message InstallSnapshotReply { uint64 term=1; uint64 bytes_received=2; }

message TimeoutNowReq { uint64 term=1; uint64 leader_id=2; }

message ReadIndexHeartbeatReq   { uint64 term=1; uint64 heartbeat_round=2; }
message ReadIndexHeartbeatReply { uint64 term=1; uint64 heartbeat_round=2; bool ack=3; }

Every message carries term first (I1's step-down check runs before any other dispatch, §15 Phase 3). Field numbers are locked once shipped (ADR-15, P11): additive-only evolution.

8.2 Log record layout (on-disk, redb backend, ADR-05)

log_entries table key = big-endian Index (u64); value = LogEntryProto bytes + 4-byte CRC32C trailer. stable_state table: single key 0, value = StableStateProto (current_term, voted_for) + CRC32C trailer, one redb transaction (Durability:: Immediate) per write (P2, P6, I7). snapshot_meta table: key = last_included_index, value = SnapshotMetaProto (last_included_term, config, checksum, size_bytes).

8.3 Persistent state (dissertation Section 5.1, mapped to StableState, §11)

Field Persisted Volatile equivalent
current_term yes, before any vote/AppendEntries reply —
voted_for yes, before RequestVoteReply{granted=true} —
log entries yes, before AppendEntriesReply{success=true} RaftLog.entries (in-memory window)
commit_index no (rederived) RaftLog.committed
last_applied no (rederived from state-machine snapshot) RaftLog.last_applied
next_index[], match_index[] no (leader-only, rebuilt on election) Progress map

8.4 Raft server state-transition table

From Event To Side effects
Follower election timeout PreCandidate send PreVote to all voters (P8)
PreCandidate pre-vote majority Candidate current_term += 1, voted_for = self, persist, send RequestVote
PreCandidate pre-vote fails / higher term seen Follower reset election timer
Candidate vote majority Leader append no-op (I4), init Progress for all peers, start heartbeats
Candidate AppendEntries from valid leader Follower reset election timer
Candidate election timeout PreCandidate retry pre-vote with new randomised timeout
Leader higher term observed in any reply Follower persist new term, step down
Leader TimeoutNow self-issued (leader transfer) (peer becomes Candidate) leader ceases proposing, target skips election timeout wait
Any RequestVote/AppendEntries with higher term Follower (same role if already Follower) persist term, reset voted_for
Learner promoted (config change commits) Follower (voter-eligible) begins participating in elections/commitment

8.5 Worked example — election + first commit (5-node cluster, terms omitted for brevity)

  1. Node A's election timer fires (Follower→PreCandidate). A sends PreVote{term=T+1} to B,C,D,E.
  2. B,C reply granted=true (their logs are not more up-to-date than A's). A has pre-vote majority (3 of 5, self included) → Candidate: current_term=T+1, persists, sends RequestVote.
  3. B,C grant (I1's up-to-date check passes); A becomes Leader, appends a no-op at (T+1, idx=N+1), sends AppendEntries to all.
  4. B,C persist and reply success=true, match_index=N+1. A's maybe_advance_commit sees majority (A,B,C) ⇒ committed=N+1. The no-op is now committed under the Leader Completeness rule (I4); any client proposal committed in a prior term is now safely committable too.

8.6 Malformed-input example

AppendEntriesReq{ prev_log_index=50, prev_log_term=3, entries=[...] } arrives at a follower whose log ends at index 40. The follower cannot verify prev_log_term because index 50 does not exist locally → replies success=false, conflict_index=41, conflict_term=None (dissertation Section 3.5 footnote's "log too short" case). The leader's maybe_decr_next (§16 Phase 4) uses conflict_index to jump next_index down to 41 directly instead of decrementing one at a time.

8.7 Failure-path example

Leader A crashes after durably appending entry 100 at term 5 but before any follower acknowledges it. B is elected leader at term 6 (having last matched entry 99). Per I4, entry 100 from term 5 was never committed (no majority), so B's log legitimately does not contain it; when A rejoins as a follower, AppendEntries from B forces truncate_suffix(100) on A, discarding the uncommitted entry — this is the correct, safety-preserving outcome, not data loss (I2 permits truncation on followers only; A is now a follower).

13. Phase 1 — Log Storage, Persistence & Crash Recovery

13.1 Objectives

Build the log abstraction (RaftLog), the three storage backends (redb/memory/ file), and the crash-recovery discipline (I7, I8) end to end — before any protocol code that depends on it exists (P2, P6).

13.2 Detailed Implementation Steps

  • RaftLog (§11): first_index()/last_index()/term(idx)/slice(lo,hi,cap)/append/ truncate_suffix/compact_prefix, maintaining first_index = snapshot_last.index + 1 after every compaction (I8).
  • Truncation rule (dissertation Section 3.5): a follower truncates its suffix at the first conflicting (index, term); must handle the conflict lying at or before the local snapshot anchor (I3, ADR-05).
  • Compaction rule: compact_prefix(up_to) requires up_to <= committed <= last_applied (I8); the log never self-initiates compaction — only the snapshot coordinator does (§18 Phase 6).
  • redb backend (ADR-05): three tables (log_entries, stable_state, snapshot_meta, §8.2); every append/save_state is one Durability::Immediate transaction (P6, I7).
  • file backend: raw segment files <dir>/log/00000001.seg, 64 MiB rolls, CRC32C trailer per record, truncate-to-last-good-record on open (torn-write recovery).
  • memory backend: BTreeMap-keyed, no fsync semantics — used only by raft-sim/tests (I11 depends on this backend having zero hidden nondeterminism).
  • Recovery sequence on startup: load StableState, load most recent snapshot, re-anchor log at snapshot_last.index + 1, load entries after that anchor, initialise role to Follower unconditionally (dissertation Section 3.5, I8).
  • Reentrant persistence acks: PersistId monotonically increasing, acknowledged in any order; RaftNode tracks a high-water mark, not a strict FIFO (I7).

13.3 Deliverable

raft-storage crate with all three backends implementing LogStorage/StableStore/ Snapshotter (§11.9), each passing the same shared conformance test module.

13.4 Acceptance Criteria

  • cargo test -p raft-storage green across all three backends, exercising append/truncate/compact.
  • 1,000 random "kill-9 mid-write" sequences per backend recover to a consistent state (tests/crash_recovery.rs), zero divergence.
  • Property test asserts first_index <= committed <= last_applied <= last_index holds after every generated operation sequence, 1,024 cases (proptest, ADR-12).
  • loom-model-checked commit ordering for the file backend's fdatasync sequencing, zero interleaving violations across the model-checker's exhaustive schedule space.

13.5 Conformance Fixtures

  • fixtures/replication/torn-write-mid-append.json → expected: recovery truncates to last CRC-valid record.
  • fixtures/replication/compact-below-applied-rejected.json (malformed/negative) → expected: compact_prefix returns an error, log unchanged.
  • fixtures/replication/first-index-continuity-after-compact.json → expected: I8 holds after compaction.
  • fixtures/replication/reorder-persist-before-reply.json (negative, I7) → expected: reply is withheld until on_persisted acks.

13.6 Pitfalls

  • Off-by-one between physical offset and logical Index — the single most common bug class in any Raft implementation; assert the convention on every helper.
  • Letting term(idx) panic instead of returning Result — the protocol legitimately asks about indices it has not seen yet (§8.6 malformed example).
  • fsync() semantics differ across filesystems; macOS needs fcntl(F_FULLFSYNC), not plain fsync — document in docs/operator-guide.md.

13.7 Performance Concerns

  • redb's B-tree has O(log n) per-key overhead versus a raw segment's O(1) append — acceptable at the M1 throughput target (§28) but the reason ADR-05's "when rejected wins" column exists.
  • slice(lo, hi, cap) must trim by byte budget without an extra copy pass — single-pass accumulation (§8, no algorithm transcribed here — implementers name the technique in code review against ADR-05).
  • Log-entry CRC32C computation is on the hot append path; benchmark it separately from the transaction commit cost (§28 M1).

13.8 Edge Cases

  • Empty log (first_index() == last_index() + 1, i.e., log has zero entries past the snapshot anchor).
  • slice request whose lo equals snapshot_last.index exactly (must return the snapshot-anchor term via the sentinel path, not an out-of-bounds error).
  • Concurrent compact_prefix and append calls from different logical callers within one step() — must not interleave (single &mut self call per step, P4).
  • Disk full mid-append (file backend) — must fail the transaction atomically, not partially write.

13.9 Failure Analysis

Symptom: node fails to restart after crash. Root causes: torn write not detected (missing CRC check), or stable-state/log anchor mismatch. Detection: startup consistency check comparing snapshot_meta.last_included_index against log_entries first key. Blast radius: single node, contained by cluster majority continuing without it (I1). Containment: node refuses to rejoin as leader-eligible until its own consistency check passes. Recovery path: docs/runbooks/restore-from-snapshot.md — wipe local storage, rejoin as a fresh learner, let InstallSnapshot (§18 Phase 6) rebuild it. Operator visibility: raft.storage.consistency_check_failed alert.

13.10 Operational Notes

Metrics: raft.log.first_index, raft.log.last_index, raft.log.committed gauges (I8 drift alerting, §7). Structured log line on every torn-write recovery event, tagged with the backend name. Deployment: the file backend is documented as a reference implementation, not the deployment default (ADR-05); operators choosing it must read docs/runbooks/restore-from-snapshot.md first. Migration: switching backends requires a full InstallSnapshot-driven rebuild, never an in-place format conversion (no format converter is in scope, §1 non-goals).

14. Phase 2 — State Machine Interface & Apply Path

14.1 Objectives

Nail the StateMachine contract (§11.8) the protocol core never inspects: apply ordering, idempotency responsibility split, snapshot capture/restore round-tripping (P13, I5).

14.2 Detailed Implementation Steps

  • StateMachine trait as specified in §11.8; the protocol hands entries to apply strictly monotonically by Index — any retry of an already-applied entry is a defect (I5).
  • Idempotency is the application's responsibility, not the protocol's — document this split explicitly in docs/api-reference.md; project 38's KV store uses MVCC revisions for its own idempotency, referencing this same contract (§1 cross-project trait surface).
  • snapshot(last_applied) is invoked when the snapshot coordinator (§18 Phase 6) needs to compact; must not block the apply path — the protocol does not hold any lock during snapshot capture (P12 analogue: no unbounded blocking on the hot apply path).
  • restore(snap) must produce a state machine bit-for-bit equivalent (by observable behaviour) to one that applied every entry up to last_applied directly.
  • Reference FSMs: CounterFsm (examples/counter) — trivial, used by every simulator scenario (§20 Phase 8); BankFsm (examples/bank) — account transfers with overdraft rejection, used by the linearizability checker (§19 Phase 7, §21 Phase 9); KvToyFsm (examples/kv-toy) — mimics project 38's apply path at 1/10th scale, exercising MVCC apply ordering.
  • Snapshotable streaming trait (§11) wraps a state machine's snapshot bytes for chunked transfer without requiring the whole snapshot resident in memory at once (ADR-07, feeds §18 Phase 6).

14.3 Deliverable

StateMachine trait shipped in raft's public API plus three reference implementations in examples/, each passing the shared apply_path conformance suite.

14.4 Acceptance Criteria

  • cargo test -p raft --test apply_path verifies monotonic apply ordering, snapshot capture/restore round-trip equivalence, and correct restore-over-existing-FSM behaviour, across all three reference FSMs.
  • CounterFsm, BankFsm, KvToyFsm each apply 1,000,000 synthetic entries with zero ordering violations (I5), measured by a monotonicity assertion on every apply call.
  • BankFsm rejects 100% of synthetic overdraft attempts injected by the test harness.

14.5 Conformance Fixtures

  • fixtures/replication/apply-out-of-order-rejected.json (negative) → expected: harness asserts the protocol never calls apply out of index order (this is a protocol-side fixture, not an FSM-side one).
  • fixtures/snapshot/restore-round-trip-bankfsm.json → expected: post-restore state equals pre-snapshot state bit-for-bit.
  • fixtures/replication/kvtoy-mvcc-ordering.json → expected: revision numbers strictly increase with apply order.

14.6 Pitfalls

  • Letting apply block indefinitely — the protocol stalls entirely behind one slow apply call; document the contract as "returns in low single-digit milliseconds; long work belongs downstream of the returned bytes."
  • Assuming snapshot() is cheap — project 38's snapshot can be tens of gigabytes; the protocol must not hold any internal lock across that call.
  • Forgetting that restore may be called at bootstrap (from local disk) or mid-run (from a received InstallSnapshot) — both paths must produce an identical FSM state.

14.7 Performance Concerns

  • Apply-path latency directly caps end-to-end commit-to-visible latency; keep apply allocation-light (no full-log-entry clone beyond the bytes already owned by Outbox).
  • KvToyFsm's MVCC revision bump must be O(1) per apply to avoid skewing the apply-path benchmark away from measuring the protocol itself (§28 M3).

14.8 Edge Cases

  • apply called with a zero-length command (a valid, if unusual, client proposal).
  • snapshot requested at last_applied == 0 (empty state machine, fresh cluster).
  • restore called twice in a row without an intervening apply (must be idempotent from the protocol's perspective — the FSM fully replaces its state each time).

14.9 Failure Analysis

Symptom: state machines diverge across nodes despite identical committed logs. Root cause: a non-deterministic apply implementation (e.g., using wall-clock time or unordered iteration inside the FSM). Detection: the simulator's cross-node state-hash comparison after each batch of applies (§20 Phase 8). Blast radius: silent data divergence, the most dangerous class because it is invisible until a read is compared across replicas. Containment: docs/api-reference.md mandates FSM determinism as a contract requirement, enforced by a fuzz target (fuzz/log_entry_roundtrip.rs) that diffs two FSM instances fed the same input. Recovery: none automatic — a divergent FSM is a StateMachine implementation defect, out of the protocol's control by design (I5 only guarantees identical input, not identical implementation behaviour).

14.10 Operational Notes

Metrics: raft.apply.latency_ms histogram, raft.apply.index gauge. Every restore call emits a structured log event with (last_applied.index, last_applied.term, snapshot_bytes). Deployment implication: an FSM implementation change that alters apply's observable behaviour for existing committed entries is a breaking change requiring a paired ADR in the consuming project (§25 Compatibility & Versioning).

15. Phase 3 — Leader Election, Pre-Vote, Leader Transfer & Safety Properties

15.1 Objectives

Implement the full election protocol (basic election, pre-vote, leader transfer) plus the safety restrictions that make it correct (Election Restriction, Leader Completeness) and the property-based tests that lock them in (P1, P5, P8, I1, I4).

15.2 Detailed Implementation Steps

  • Roles: Follower | PreCandidate | Candidate | Leader | Learner (§8.4 state-transition table; §11.7), distinct structs inside the Role enum — no shared flag byte. Election timeout: randomised min_election_timeout..max_election_timeout (150–300 ms, §4), seeded; raft-sim overrides the seed for determinism (I11).
  • Pre-vote (dissertation Section 9.6, P8): before bumping its term, a Follower becomes PreCandidate and sends PreVoteReq with the up-to-date check but no term mutation; only a pre-vote majority triggers the real Candidate transition and the term bump.
  • RequestVote grant rule (dissertation Section 3.4, I1): grant iff (a) candidate's term ≥ local term; (b) not yet voted this term, or already voted for this candidate; (c) candidate's log is at least as up-to-date (last_log_term wins ties broken by last_log_index) — the Election Restriction, what makes I4 provable.
  • Persist-then-reply (P6, I7): every term bump and vote cast is pushed onto Outbox::persist and the paired reply is withheld until on_persisted acks.
  • Leader recognition: majority of voters in the current Configuration; under Joint, both old_voters and new_voters majorities are required (§17 Phase 5 dependency). Heartbeats: leader emits empty AppendEntriesReq every heartbeat_interval (50 ms, §4).
  • No-op on election (dissertation Section 3.6.2, I4): a freshly elected leader appends a no-op entry so prior-term entries become committable under the new term — the single rule that makes Leader Completeness provable; skipping it is the "Figure 8" bug (§26).
  • Leader transfer (dissertation Section 3.10): current leader picks a caught-up target, sends TimeoutNowReq; target immediately starts an election, skipping its own timeout wait. Must reject a transfer target not present in the current Configuration (I14).
  • Safety properties as testable predicates: Election Restriction (I1), Log Matching (I3, enforced in §16 Phase 4), Leader Append-Only (I2), Leader Completeness (I4), State Machine Safety (I5, §14 Phase 2) — asserted by raft-sim::invariants::InvariantChecker over arbitrary generated cluster histories (ADR-11, ADR-12).

15.3 Deliverable

election.rs implementing pre-vote → vote → leader transitions and leader transfer, passing a property-test suite that runs 1,024 random cluster histories per property.

15.4 Acceptance Criteria

  • cargo test -p raft --test leader_election: a 5-node cluster elects a leader within 4 × max_election_timeout (1,200 ms), measured across 100 runs.
  • Property test election_restriction: 1,024 random histories, zero violations of I1.
  • Property test leader_completeness: 1,024 random histories, zero violations of I4.
  • Scenario test: two candidates start elections simultaneously; exactly one wins (I1 assertion, not a specific-winner check). Leader-transfer scenario: target becomes leader within 3 election timeouts (900 ms) of TimeoutNowReq, across 50 runs.

15.5 Conformance Fixtures

  • fixtures/election/vote-grant-up-to-date.json, vote-reject-stale-log.json, vote-reject-stale-term.json.
  • fixtures/election/pre-vote-grant.json, pre-vote-reject-healthy-leader.json.
  • fixtures/election/no-op-on-election.json → expected: leader's first committed entry after winning is a Noop at its own term.
  • fixtures/election/leader-transfer-rejects-non-member-target.json (negative, I14).
  • fixtures/election/persist-before-reply-vote.json (negative, I7) — reorders the persistence ack after the reply and asserts the runner flags the ordering violation.

15.6 Pitfalls

  • Forgetting to persist voted_for before replying — the single most-cited Raft bug (I7); build persist-then-reply into the API surface, do not rely on review.
  • Re-using the candidate's term on an unsuccessful election instead of incrementing it — silently violates the term-monotonicity half of I1.
  • Pre-vote subtlety: a PreVoteReq's term is one ahead of the candidate's actual current term (not yet bumped) — a naive RequestVote handler reused for PreVote applies the wrong comparison branch; test both paths independently (P8).
  • Leader transfer to a node not in the current Configuration must be rejected at the API boundary, not discovered later as a dropped message (I14).

15.7 Performance Concerns

  • Randomised election timeout must use a per-node PRNG seeded independently (via raft-sim's scheduler in tests) — a shared seed across nodes correlates timeouts and defeats the randomisation's split-vote-avoidance purpose.
  • Heartbeat coalescing: when a leader has many followers, batch the per-tick heartbeat send loop rather than issuing N independent Outbox::messages pushes with duplicated term/commit fields recomputed per peer.
  • Pre-vote adds one RTT to every election attempt — acceptable against the §4 election latency target (200 ms p95) because pre-vote failures are rare in a healthy cluster.

15.8 Edge Cases

  • Simultaneous elections from two nodes whose randomised timeouts fire in the same tick (deterministic under raft-sim) — resolved by I1's grant rule, not scheduling luck.
  • A candidate receiving AppendEntries from an equal-term leader while campaigning must step down to Follower even though its own term did not change (dissertation Section 3.4).
  • Leader transfer issued while a PendingConfigChange is in flight (I9) — reject the transfer until the pending change resolves.
  • A PreVoteReq arriving at a node that just started a real election must not grant a pre-vote it would refuse as a real vote.

15.9 Failure Analysis

Symptom: repeated leader churn with no underlying network partition. Root cause: election timeout too close to network RTT, or pre-vote disabled. Detection: raft.election.start rate exceeding 1/minute sustained. Blast radius: degraded write availability cluster-wide, no safety violation (I1 holds). Containment: widen min_election_timeout/ max_election_timeout via config reload. Recovery: docs/runbooks/ handle-split-brain-suspect.md (also covers election-storm diagnosis). Postmortem guidance: check pre_vote config before suspecting a network issue.

15.10 Operational Notes

Metrics: raft.term.bump{from,to,reason}, raft.role.change{from,to}, raft.election.start{term}, raft.election.win{term}, raft.election.lose{term,reason} (naming convention locked at §12 Phase 0). Every term bump and role change is tracing-instrumented (ADR-14, P5). pre_vote is a supported degraded-mode config fallback (§4), documented in docs/operator-guide.md, never removed.

16. Phase 4 — Log Replication, Pipelining & Batching

16.1 Objectives

Build AppendEntries request/reply handling, leader-side per-follower flow control (Progress), the commitment rule, and the pipelining/batching optimisations real systems ship, in one phase (P3, P12, I3, I6, I12).

16.2 Detailed Implementation Steps

  • Per-follower Progress (§11.11): next_index, match_index, and a ProgressState::{Probe, Replicate, Snapshot} state machine — Probe sends one entry at a time to find the divergence point; Replicate pipelines; Snapshot is fed by §18 Phase 6 (design modelled on etcd/raft's progress.go, §5).
  • AppendEntriesReq (dissertation Section 3.5, §8.1): carries prev_log_index, prev_log_term, entries, leader_commit; receiver runs the consistency check before accepting (I3).
  • Conflict resolution: on consistency-check failure, the follower returns conflict_term/conflict_index (dissertation Section 3.5 footnote); the leader's maybe_decr_next uses the hint to jump next_index directly (§8.6 malformed example).
  • Pipelining: while Replicate, the leader does not wait for the previous batch's ack before sending the next; the follower tolerates out-of-order replies and the leader advances match_index monotonically, never regressing it from a stale reply (P4, I6).
  • Commitment rule (dissertation Section 3.6.2, I4, I6): an entry at index N from current_term commits when a majority of voters have match_index >= N; prior-term entries are never committed by counting replicas directly — the "Figure 8" hazard, closed by the no-op rule (§15 Phase 3).
  • Backpressure (P12, I12): each Progress's inflight window is bounded by max_inflight (256, §4); Progress::full gates maybe_send_append; a saturated peer is paused, others unaffected. Batching: back-to-back proposals collapse into one AppendEntriesReq at tick time (§28 M9). Heartbeat coalescing (from §15 Phase 3): a shared committed/term computed once per tick, not once per peer.

16.3 Deliverable

replication.rs + progress.rs implementing pipelined, batched AppendEntries replication with correct conflict resolution and commitment under both stable and joint configurations.

16.4 Acceptance Criteria

  • cargo test -p raft --test log_replication: linear replication, conflict-and-truncate, pipelined out-of-order replies, joint-consensus commitment, and the Figure-8 scenario (asserting the prior-term entry is not committed until the new-term no-op is) all green.
  • Property test log_matching: for any pair of nodes at any point, if both have an entry at the same (index, term), all preceding entries are identical — 1,024 random histories, zero violations (I3).
  • Benchmark replicate_3node_256B_50k_rps (benchmarks/replication.rs, ADR-13) meets the 50,000 ops/s target (§4, §28 M1) with batching enabled.
  • Microbenchmark shows ≥ 4× throughput improvement from batching versus batching disabled, on the same hardware.

16.5 Conformance Fixtures

  • fixtures/replication/linear-append.json, conflict-and-truncate.json, pipelined-out-of-order.json, batched-append.json.
  • fixtures/replication/figure-8-not-committed.json (negative) → expected: prior-term entry stays uncommitted through the described interleaving.
  • fixtures/replication/figure-8-committed-with-noop.json → expected: same entry commits once the no-op lands.
  • fixtures/replication/commit-rule-joint-both-majorities.json (§17 Phase 5 cross-reference).

16.6 Pitfalls

  • Pipelining introduces an ordering hazard: a stale success=false reply from a slow follower can move next_index backwards if not guarded — use recent_active and per-message sequence hints (I6).
  • Running the commitment check against the wrong configuration snapshot during a joint transition — must use both old_voters and new_voters majorities, never one alone (§17 Phase 5, I9).
  • Crashing the node on a malformed AppendEntriesReq — must return success=false and let the leader recover via conflict hints, never panic (§8.6).

16.7 Performance Concerns

  • Cache locality: Progress map keyed by NodeId should be a flat BTreeMap, not a HashMap (I11 — determinism for the simulator — and cache-friendly iteration for small N).
  • Batching amplifies serialization cost per message; slice(lo, hi, cap) (§13 Phase 1) must trim by max_msg_bytes (§4) before serialization, not after.
  • Tail latency: p99.9 commit latency (§4, §28 M2) is allocator-sensitive under batching churn — mimalloc (ADR-22) is load-bearing here, not cosmetic.

16.8 Edge Cases

  • AppendEntriesReq with zero entries (a pure heartbeat) must still advance leader_commit processing on the follower.
  • A follower whose log is longer than the leader's at a lower term (stale leftover entries from a former leader) — conflict resolution must truncate correctly even when the follower's log is ahead in raw length.
  • Reordered replies delivered after a leader has already stepped down (I6: must not resurrect stale match_index state for a role the node no longer holds).
  • max_msg_bytes smaller than a single entry's encoded size — must send that one entry anyway (never wedge on an unsatisfiable cap).

16.9 Failure Analysis

Symptom: a follower falls permanently behind despite a healthy network. Root cause: Progress stuck in Probe due to a conflict-hint bug repeatedly resolving to the same index. Detection: raft.replicate.send{to} event rate near zero for one peer while others progress normally. Blast radius: reduced fault tolerance (one fewer usable voter for quorum) but no safety violation. Containment: leader-side alert on stalled Progress beyond N × heartbeat_interval. Recovery: operator forces a leader-transfer-free restart of the stalled follower; if it does not resync, docs/runbooks/replace-failed-node.md.

16.10 Operational Notes

Metrics: raft.replicate.send{to,prev_index,count}, raft.replicate.commit{index,term}, raft.replicate.backpressure{peer}, raft.replicate.conflict{peer} (naming convention locked at §12 Phase 0). Deployment: max_inflight/max_msg_bytes are hot-reloadable config knobs (§4); changing them does not require a restart. Compatibility: AppendEntriesReq's additive proto fields (P11) allow a mixed-version cluster during rolling upgrade to still replicate correctly at the lowest common field set.

17. Phase 5 — Membership Changes, Joint Consensus & Learners

17.1 Objectives

Implement safe membership reconfiguration via joint consensus (dissertation Section 4.3), formalise learners as first-class non-voting replicas, and fold in the leader-transfer interaction from §15 Phase 3 where a membership change removes the current leader (P7, I9, I10, I14).

17.2 Detailed Implementation Steps

  • Two-phase change (P7, dissertation Section 4.3): a change from C_old to C_new proceeds via Configuration::Joint; the leader appends an EnterJoint ConfigChange entry; once committed (both-majority rule below), the cluster is in C_old,new; the leader then appends LeaveJoint; once committed, the cluster is in C_new.
  • Decision rule under joint (§16 Phase 4 cross-reference, I9): an entry commits under Joint only when replicated to a majority of old_voters and a majority of new_voters — both quorums required, never either alone.
  • Election rule under joint: a candidate is elected only with votes from a majority of old_voters and a majority of new_voters (I1 extended to the joint case).
  • Removing the leader: if the change removes the current leader, it steps down once LeaveJoint commits; the remaining cluster runs a normal election (§15 Phase 3).
  • Learners (§11.4, formalised here): receive the log via the same AppendEntries path but are excluded from every quorum computation in both election and commitment; promotion to voter is itself a subsequent ConfigChangeRequest.
  • Catch-up gate before promotion: the leader rejects a promotion to voter until the candidate's match_index is within catch_up_window (default 1,000, §4) of last_index — prevents a freshly added, lagging voter from stalling commitment.
  • Single-in-flight guard (I9): change_membership rejects a new ConfigChangeRequest while PendingConfigChange is set; caller must retry after resolution.
  • Removed-node transport enforcement (I14): raft-net drops inbound messages from a NodeId no longer present in Configuration; the removed process itself is not told to shut down by the protocol — that is an operator action (docs/runbooks/ replace-failed-node.md).

17.3 Deliverable

membership.rs implementing joint-consensus entry/leave transitions, learner add/promote/ remove, and the single-in-flight guard, integrated with the commitment and election rules from §15–§16.

17.4 Acceptance Criteria

  • Cluster-growth test: 3-node → 5-node → back to 3-node, zero committed-entry loss across the full sequence, measured by comparing committed-entry hashes before and after.
  • Leader-swap test: remove the current leader, add a replacement node, assert continuity of committed entries (no gap, no duplicate) across the swap.
  • Learner test: add a learner, verify it catches up to within catch_up_window (1,000 entries) inside 30 seconds at replication throughput (§4), promote it, verify it can vote in the next election.
  • Concurrency-guard test: a second change_membership call while one is pending returns RaftError synchronously, zero silent drops.

17.5 Conformance Fixtures

  • fixtures/membership/enter-joint.json, leave-joint.json, add-voter-with-catchup.json, remove-voter.json, swap-leader.json.
  • fixtures/membership/learner-add.json, learner-promote.json.
  • fixtures/membership/concurrent-membership-change-rejected.json (negative, I9).
  • fixtures/membership/remove-voter-messages-dropped.json (I14).

17.6 Pitfalls

  • Allowing two membership changes in flight at once — the single most dangerous bug class here; the protocol must reject any new change while PendingConfigChange is set, with no exception path (I9).
  • Counting only one of the two quorums (old_voters or new_voters) during a joint transition — silently breaks I1 under specific membership-change timings.
  • Assuming a removed node stops running on its own — it does not; the transport must drop its messages, and the operator runbook must spell out the actual process shutdown (I14).
  • Promoting a learner before it has caught up — a slow new voter can then stall every future commit by being counted toward a majority it cannot satisfy in time.

17.7 Performance Concerns

  • Configuration::Joint doubles the quorum-intersection computation on every commitment check — keep both voter sets as BTreeSet<NodeId> for O(log n) membership tests, not Vec linear scans, to avoid regressing §28 M1 throughput during a reconfiguration window.
  • Catch-up for a new voter runs at full replication throughput — bounded by the same max_inflight/max_msg_bytes knobs as steady-state replication (§16 Phase 4, P12), so a catch-up in progress competes for the same backpressure budget as normal traffic.

17.8 Edge Cases

  • A membership change that removes a majority of old_voters in one step (rejected by construction — joint consensus requires overlapping quorums, but implementers must verify the API surface actually prevents submitting such a request, not just that the commit rule would handle it awkwardly).
  • Leader transfer requested to a node that is currently a learner, not yet a voter — must be rejected (§15 Phase 3, I14 cross-reference).
  • A learner removed while mid-catch-up — the leader must stop sending it entries immediately, not after its next scheduled tick.
  • Network partition isolating exactly the new-configuration-only nodes during C_old,new — commitment correctly stalls (neither quorum alone suffices) until the partition heals; this is a liveness cost, not a safety violation.

17.9 Failure Analysis

Symptom: reconfiguration never completes (PendingConfigChange stuck). Root cause: the joint-quorum entry cannot commit because one side's majority is unreachable. Detection: raft.config.enter_joint age exceeds a threshold with no matching leave_joint. Blast radius: available under the old configuration's quorum but cannot finish reconfiguring. Containment: alert on PendingConfigChange age. Recovery: bring the unreachable node back, or issue a corrective ConfigChangeRequest removing it — never a manual file edit bypassing the log (P13).

17.10 Operational Notes

Metrics: raft.config.enter_joint{old,new}, raft.config.leave_joint{final} (locked naming convention, §12 Phase 0). Runbooks: promote-learner.md, replace-failed-node.md (§10, §24). Compatibility: a Configuration::Joint value must round-trip through the wire format and every snapshot unchanged across a rolling upgrade (P11, I10) — this is tested by the install-with-config-restore fixture (§18 Phase 6).

18. Phase 6 — Snapshots & InstallSnapshot

18.1 Objectives

Add log compaction and chunked InstallSnapshot delivery so a leader can serve a multi-gigabyte snapshot to a lagging follower without stalling replication to healthy followers (P13, I10, ADR-07, ADR-21).

18.2 Detailed Implementation Steps

  • Trigger: snapshot when log size exceeds snapshot_size_threshold (64 MiB, §4) and the state machine is at least snapshot_min_entries (10,000) ahead of the last snapshot.
  • Capture: protocol enqueues SnapshotOp::Capture into Outbox::snapshot; the state machine captures via StateMachine::snapshot (§14 Phase 2) and reports completion via on_snapshot.
  • Compaction: once durable, RaftLog::compact_prefix(snapshot_last) shrinks the log (§13 Phase 1, I8) — the log never initiates this itself.
  • InstallSnapshotReq (§8.1, §11): sent when a follower's next_index is below the leader's first_index; carries last_included_index, last_included_term, embedded Configuration (P13, I10, dissertation Section 5.4), offset, data, done, crc32c.
  • Streaming: fixed 1 MiB chunks (ADR-21); follower writes to a temp file, validates the CRC trailer on done, atomically renames into place — never a partial file visible under the final name.
  • Leader-side concurrency: Progress::Snapshot marks that follower ineligible for normal Replicate-state traffic until the transfer completes (§16 Phase 4 — snapshot transfer must not block replication to other followers).
  • Follower-side install: on done=true, the follower calls StateMachine::restore (§14 Phase 2) with the reconstructed snapshot bytes, then re-anchors its own RaftLog at last_included_index + 1.
  • Bootstrap-time snapshot restore (§13 Phase 1 cross-reference): if a snapshot exists with a later last_applied than the log's first entry, restore it before replaying any log entries.

18.3 Deliverable

snapshot.rs implementing capture-trigger, streamed InstallSnapshot send/receive, and compaction, integrated with Progress's per-follower state machine.

18.4 Acceptance Criteria

  • Scenario test: a 3-node cluster, one node partitioned long enough to fall behind the snapshot threshold, heals, and receives a full snapshot to rejoin — measured end-to-end under 90 seconds at the §4 snapshot-throughput target.
  • Concurrency test: the leader continues replicating to non-lagging followers at the §28 M1 throughput target while a snapshot streams to a lagging one.
  • raft-sim's slow_follower scenario (§20 Phase 8) completes under randomised snapshot-delivery delays with zero invariant violations across 100 seeds.
  • 1 GiB snapshot streams to a lagging follower in ≤ 60 s over a 1 Gbps simulated link (§4, §28 M7).

18.5 Conformance Fixtures

  • fixtures/snapshot/capture-trigger.json, install-streaming.json.
  • fixtures/snapshot/install-with-config-restore.json (I10 — asserts a restored node can locate its peers with zero external bootstrap file).
  • fixtures/snapshot/snapshot-while-replication-continues.json.
  • fixtures/snapshot/abort-mid-stream.json (negative — a follower crash mid-transfer leaves no partial file visible; resumed transfer starts clean, not from a corrupt temp file).

18.6 Pitfalls

  • Forgetting to embed Configuration in the snapshot — leaves a restored node unable to find its peers, a class of outage requiring manual operator intervention to fix (P13, I10).
  • Streaming a snapshot in-band of normal AppendEntries traffic — blocks replication to every follower, not just the lagging one; Progress::Snapshot must be a distinct state precisely to prevent this (§16 Phase 4).
  • Not validating the CRC trailer before renaming the temp file into place — a truncated or corrupted transfer becomes a silently-accepted bad snapshot.

18.7 Performance Concerns

  • Chunk size (1 MiB, ADR-21) trades transfer-protocol overhead against per-chunk memory footprint; do not stream chunks larger than max_msg_bytes (§4) or the transport's own framing limits are violated.
  • Snapshot capture must not hold the state machine's apply-path lock (§14 Phase 2); measure capture latency separately from apply latency in benchmarks.
  • Cold-start recovery from a 1 GiB snapshot must complete within 30 s (§4, §28 M8) — dominated by disk read throughput and FSM restore cost, not network.

18.8 Edge Cases

  • A follower that crashes mid-transfer and rejoins — must resume from a clean state (no partial temp file adopted), effectively restarting the transfer, not corrupting it.
  • Snapshot capture triggered while a membership change is PendingConfigChange — the snapshot must embed whichever Configuration (stable or joint) is authoritative at last_included_index (§17 Phase 5).
  • InstallSnapshot arriving at a follower that has, in the meantime, already caught up via normal AppendEntries (a race between two recovery paths) — the follower must discard the now-stale snapshot rather than regress its last_applied.

18.9 Failure Analysis

Symptom: a lagging follower never receives a snapshot despite being far behind. Root cause: the leader's Progress state failed to transition into Snapshot (stuck in Probe, repeatedly probing an index the leader has already compacted away). Detection: raft.replicate.send targeting an index below the leader's own first_index — a protocol-level contradiction. Blast radius: one permanently unavailable voter, reducing fault tolerance. Containment: an explicit guard in maybe_send_append that forces a transition to Snapshot state the moment next_index < first_index, rather than allowing Probe to retry indefinitely. Recovery: docs/runbooks/restore-from-snapshot.md.

18.10 Operational Notes

Metrics: raft.snapshot.capture.start/done{index,term,bytes}, raft.snapshot.send.start/chunk/done{to,index,term,offset}, raft.snapshot.install.start/done{index,term} (locked naming convention, §12 Phase 0). Deployment: snapshot_size_threshold/snapshot_chunk_size are hot-reloadable (§4). Compatibility: the snapshot wire format is additive-only (P11) so a mixed-version cluster mid-upgrade can still exchange snapshots at the lowest common field set.

19. Phase 7 — ReadIndex & Linearizable Reads

19.1 Objectives

Implement linearizable reads without appending to the log: ReadIndex as the unconditional baseline, lease reads as an explicit opt-in, and FollowerRead for read-load spreading (P9, I13, dissertation Section 6.4).

19.2 Detailed Implementation Steps

  • ReadIndex on the leader (dissertation Section 6.4): (1) record committed as the read's required index; (2) confirm leadership via a heartbeat round to a majority (ReadIndexHeartbeatReq/Reply, §8.1); (3) wait until last_applied >= committed recorded at step 1; (4) execute the read against the state machine.
  • Guard (I13): a leader must not serve read_index until it has committed its own term's no-op (§15 Phase 3, I4) — otherwise it cannot know which entries are truly committed under its own term.
  • ReadIndex on followers (FollowerRead): a follower forwards the read to the leader, receives back the index to wait for, and locally waits for last_applied to reach it before responding — spreads read load without weakening linearizability (project 38's KV store is the first consumer of this path, §1).
  • Lease reads (opt-in, P9): a leader holding quorum-confirmed leadership within lease_timeout < min_election_timeout (§4) may serve reads without a heartbeat round trip; requires an explicit bounded-clock-skew acknowledgement in config (Abadi's PACELC framing, §5) — off by default.
  • ReadIndexState/PendingRead (§11.13): a leader tracks pending reads keyed by heartbeat_round; a stepped-down leader fails all pending reads rather than silently dropping them.

19.3 Deliverable

read_index.rs implementing ReadIndex (baseline), FollowerRead (forwarding), and lease-reads (opt-in), gated by the I13 no-op guard.

19.4 Acceptance Criteria

  • Linearizability test: BankFsm (§14 Phase 2) under 1,000 concurrent transfers and reads, checked via a Knossos-style linearizability checker (§21 Phase 9), zero violations.
  • FollowerRead test: a follower serves reads meeting the same linearizability bar as the leader, verified by the same checker run against follower-served reads specifically.
  • Guard test: read_index called before the term's no-op commits returns RaftError synchronously in 100% of attempts (I13), never silently serves a possibly-stale read.
  • Lease-read test (opt-in path only): with lease_timeout configured, read latency drops below the ReadIndex heartbeat-RTT floor by at least 50%, measured against the ReadIndex baseline on identical hardware.

19.5 Conformance Fixtures

  • fixtures/readindex/read-on-leader.json, read-on-follower-via-leader.json.
  • fixtures/readindex/read-with-no-noop-pending.json (negative, I13).
  • fixtures/readindex/read-after-partition-heal.json — asserts a former-minority leader cannot serve a stale read once it recognises the partition (I1 interaction).

19.6 Pitfalls

  • Serving ReadIndex without the no-op guard — the leader cannot yet distinguish "committed under my term" from "possibly uncommitted," breaking linearizability silently (I13, I4).
  • Enabling lease reads with unbounded clock skew — unsafe by construction; document the assumption prominently and require an explicit opt-in flag, never a default.
  • Forgetting to fail pending reads on step-down — a stepped-down leader that still answers a queued ReadIndexHeartbeatReply risks serving a read that is no longer authoritative.

19.7 Performance Concerns

  • ReadIndex's heartbeat round trip is the dominant cost — batch pending reads sharing the same heartbeat_round rather than issuing one heartbeat per read.
  • FollowerRead forwarding adds one extra network hop versus reading locally on the leader; document this trade-off in docs/operator-guide.md for read-heavy workloads.
  • Lease reads remove the heartbeat RTT entirely but require clock-skew monitoring overhead (NTP drift metrics) that ReadIndex does not need.

19.8 Edge Cases

  • A read requested immediately after an election, before the no-op has had time to commit — correctly rejected by I13, not silently delayed indefinitely (bounded by one heartbeat interval, per §15 Phase 3's no-op-commit latency).
  • A follower's read_index request racing a leadership change mid-flight — the follower must detect the term change in the leader's reply and retry against the new leader, not treat a stale reply as authoritative.
  • Lease read requested on a node that is not actually the leader (stale local role state) — must fail closed, never silently serve a non-leader's view.

19.9 Failure Analysis

Symptom: a client observes a linearizability violation (a "time travel" read). Root cause candidates: lease reads enabled with insufficient clock-skew bound, or a bug in the no-op guard allowing ReadIndex before term-safety is established. Detection: the Jepsen linearizability checker (§21 Phase 9) flags the violating history. Blast radius: correctness-visible to the application layer — the most severe class of bug this blueprint can produce. Containment: lease reads ship disabled by default specifically to keep this blast radius opt-in only. Recovery: none automatic; this is a release-blocking defect, not an operational incident — the property and Jepsen suites exist to catch it before merge (§26 Testing Strategy).

19.10 Operational Notes

Metrics: raft.read_index.start{ctx,committed}, raft.read_index.done{ctx,index}, raft.read_index.rejected{reason} (locked naming convention, §12 Phase 0). Deployment: read_index is on by default (P9, §4); lease_timeout is opt-in and documented in red in docs/operator-guide.md. Compatibility: FollowerRead forwarding requires all nodes to speak the ReadIndexHeartbeat message variant — gated behind a cluster-wide capability check during rolling upgrade (§25).

20. Phase 8 — Deterministic Simulator

20.1 Objectives

Build raft-sim, the correctness budget of the entire library (P10): a single-threaded, seed-reproducible scheduler driving real RaftNode instances through fault-injected scenarios, checking every invariant (I1–I14) after every step.

20.2 Detailed Implementation Steps

  • Architecture (Wilson 2014, §5): a single-threaded Simulator (§11.14) advances logical time in discrete units; each RaftNode is a participant; messages queue per-link with a configurable delay distribution; the scheduler picks the next event deterministically from the seeded PRNG (ADR-11).
  • Determinism (I11): fixed seed + fixed scenario ⇒ byte-identical report.json every run. HashMap iteration, std::time::Instant, and rand::thread_rng are banned inside the raft crate and lint-enforced in CI (P1, P4).
  • Faults (fault.rs): drop, delay, duplicate, partition, kill-node, slow-disk, disk-full, clock-skew — each scheduled at a logical time via the same event queue as normal messages, never as an out-of-band side channel.
  • Invariant checking (invariants.rs): after every step, InvariantChecker runs all fourteen checks (I1–I14, §7); a violation aborts the run and dumps a minimal reproducing trace (seed, scenario, step index) rather than a stack trace.
  • Canonical scenarios (scenarios/): partition_heal, slow_follower, message_reorder, message_dup, leader_kill, disk_full — a dozen total, each a small declarative DSL over cluster shape + fault timeline.
  • Reporting (report.rs): every run emits raft-sim-report.json with seed, scenario, duration, commits/second, faults injected, and any invariant violations — consumed by both CI and tools/trace-viewer (§10).

20.3 Deliverable

raft-sim crate running all canonical scenarios against real RaftNode/RaftLog/ StateMachine instances (the memory storage backend, §13 Phase 1) with a locked JSON report schema.

20.4 Acceptance Criteria

  • cargo test -p raft-sim runs 12 canonical scenarios in under 60 seconds.
  • simulator.yml (§10 CI workflow) runs with RAFT_SIM_SEEDS=1024 for 2 hours on a schedule, zero invariant violations, report uploaded as a build artefact.
  • The invariant checker, run against a known-broken commit (a deliberately reintroduced Figure-8 bug, §15/§16 Phases 3–4), produces a minimal trace pinpointing the exact violating step within 5 seconds of replay.
  • Determinism check (I11): the same seed run twice produces byte-identical report.json, verified in CI on every PR touching crates/raft or crates/raft-sim.

20.5 Conformance Fixtures

  • raft-sim/tests/smoke.rs — not JSON fixtures but scenario names asserted present: partition_heal, slow_follower, message_reorder, message_dup, leader_kill, disk_full, plus six more covering joint-consensus and snapshot-during-partition composites.
  • A negative "known-broken commit" fixture retained in notes/design-discussions.md as a regression anchor for the invariant checker's own test suite.

20.6 Pitfalls

  • Any std::time::Instant reachable from the raft crate breaks the simulator silently until a rare seed exposes it — lint for it in CI, do not rely on code review alone.
  • HashMap iteration order is not deterministic across Rust versions; BTreeMap is — forbid HashMap in crates/raft via a clippy lint allow-list inversion.
  • A zero-delay message distribution "tests" nothing — the per-link delay distribution must be configurable and exercised across a realistic range, or real interleavings are never covered.

20.7 Performance Concerns

  • The scheduler's event queue is a hot path at 1,024-seed CI scale; a binary heap keyed by logical time keeps next_event() at O(log n) rather than O(n) linear scan.
  • Report generation (report.rs) must not perturb the simulation itself — collect metrics into a pre-allocated buffer, flush only at run end.

20.8 Edge Cases

  • A scenario where every node is partitioned from every other simultaneously (total network split) — the simulator must confirm zero commits occur, not merely that it does not crash.
  • A fault scheduled at a logical time past the scenario's run_until deadline — must be a no-op, not an error.
  • Two faults scheduled at the identical logical time (partition heal and a leader kill in the same tick) — resolved deterministically by the seeded PRNG's tie-break, never by wall-clock arrival order.

20.9 Failure Analysis

Symptom: a CI-flagged invariant violation with a seed that does not reproduce locally. Root cause: an unintended source of nondeterminism (thread-local state, a system call returning host-specific data) leaking into the simulation. Detection: the determinism check itself (§20.4) — a diff between two same-seed runs. Blast radius: erodes trust in every other simulator-verified guarantee until root-caused. Containment: the CI lint banning HashMap/Instant/thread_rng in crates/raft (§20.6) is the primary defense; a new source requires extending that lint, not just fixing the one instance. Recovery: bisect via git bisect driven by the determinism check as the automated test.

20.10 Operational Notes

The simulator is not deployed — it is a CI/pre-release artefact. Reports are retained 90 days (matches CI artefact policy, §12 Phase 0). tools/trace-viewer (§10) renders a report.json violation trace as a sequence diagram for human debugging. Any consumer project (KV Store #38, Job Queue #40, Service Discovery #42) integrating a new StateMachine is expected to add at least one scenario exercising its FSM through raft-sim before its first production deployment.

21. Phase 9 — Fault Injection & Conformance Suite

21.1 Objectives

Package the protocol-level correctness guarantees into two portable artefacts: an out-of-process Jepsen-style nemesis harness (raft-jepsen) validating real binaries under real Linux network-namespace faults, and a portable JSON-fixture conformance runner other Raft implementations can be checked against (§5 Kingsbury citation, ADR-18).

21.2 Detailed Implementation Steps

  • raft-jepsen architecture: each node runs as a real child process; the harness manipulates iptables, tc, and signal delivery directly (not simulated, ADR-18's "when rejected wins" case for in-process faults); a Knossos-style linearizability checker runs offline against the recorded history (§19 Phase 7, I5).
  • Nemeses (nemesis.rs, §11.15): random partitions (50% of links cut for 30 s), leader kills, clock skew via libfaketime, disk delays via dmsetup, packet duplication via nft — each implementing the Nemesis trait (arm/fire/heal).
  • Histories (history.rs): every client operation recorded with invocation/response timestamps; checked against a sequential specification of the state machine (BankFsm, §14 Phase 2).
  • Scenarios (scenarios/*.toml): reproducible, versioned declarative fault timelines — partition.toml, clock-skew.toml, kill-leader.toml.
  • Conformance runner (conformance/src/runner.rs, §11.16): loads a ConformanceFixture (JSON: setup, steps, expected outbox), drives a RaftNode directly (no network, no simulator scheduler — a third, minimal-dependency test surface), and emits a Pass/Fail/Deferred outcome per fixture with a blueprint_ref for any Deferred case.
  • Fixture categories (matches §15–§19 phase fixtures, aggregated here): Election, Replication, Membership, Snapshot, ReadIndex — roughly 150 fixtures total across the five categories, including negative (malformed) and replay/regression cases.

21.3 Deliverable

raft-jepsen running a 60-minute partition-and-kill scenario against a real 5-node cluster, plus conformance running ~150 fixtures via make conformance, both wired into CI (.github/workflows/simulator.yml-adjacent scheduled jobs, not gated on every PR).

21.4 Acceptance Criteria

  • 60-minute Jepsen-style run against a 5-node cluster with random partitions and leader kills asserts linearizability of BankFsm via the Knossos-style checker, zero violations.
  • A scenario reproducing "a minority-partition leader serves a stale read" is included and asserted to not manifest, because ReadIndex's heartbeat round (§19 Phase 7, I13) structurally prevents it.
  • make conformance returns exit code 0 with zero Deferred outcomes for every Phase-0-through-Phase-9 surface (§12–§21).
  • Conformance report schema documented in docs/api-reference.md, versioned (P11-consistent additive evolution).

21.5 Conformance Fixtures

  • The ~150 fixtures themselves are the deliverable of this phase; representative names: fixtures/election/leader-becomes.json, fixtures/replication/commit-rule.json, fixtures/membership/swap-leader.json (aggregated from §15–§18, formalised into the shared runner format here), plus this phase's own: fixtures/readindex/read-after-partition-heal.json (cross-referenced from §19).
  • raft-jepsen/scenarios/kill-leader.toml — not a JSON fixture but a versioned scenario file, its own conformance unit (must remain reproducible across harness versions).

21.6 Pitfalls

  • Jepsen-style tests are slow and flaky by nature — run on a schedule, never gate every PR on a 60-minute run (§27 Build & Release Engineering).
  • Linearizability checking is exponential in history length — bound history length and prune aggressively, or the checker itself becomes the bottleneck.
  • Fixtures depending on Instant::now() or unpinned RNG seeds are non-portable across hosts — pin every clock value and seed in the fixture format itself.

21.7 Performance Concerns

  • The conformance runner's per-fixture startup cost (constructing a fresh RaftNode) must stay low enough that 150 fixtures run in well under a minute — no shared mutable fixture state (§11.16) is what makes this parallelisable across fixtures.
  • raft-jepsen's network-namespace manipulation (iptables/tc) has real syscall overhead — budget scenario setup/teardown time separately from the 60-minute measured window.

21.8 Edge Cases

  • A conformance fixture whose expected outbox includes a PersistOp — the runner must simulate the persistence ack (on_persisted) itself, since there is no real disk in this minimal test surface.
  • A Jepsen nemesis that fires while another is still active (compound faults) — the harness must serialize arm/fire/heal calls per nemesis instance to avoid an undefined double-fault state.
  • A fixture encoding a message with a term from the future relative to the fixture's declared initial state — must be accepted (that is normal protocol behaviour, not malformed input) and produce a step-down.

21.9 Failure Analysis

Symptom: raft-jepsen reports a linearizability violation. Root cause: this is the highest-severity finding this blueprint's testing strategy can produce — treat as a release blocker, not a flaky test, until root-caused via the recorded history. Detection: the Knossos-style checker's counter-example output. Blast radius: potentially every consumer relying on linearizable reads/writes. Containment: the 60-minute run is scheduled, not PR-gating, specifically so a violation is caught before a release tag, not after. Recovery: bisect using the recorded history replayed against raft-sim (§20 Phase 8) to reproduce deterministically, then fix and add a permanent regression fixture to conformance/fixtures/.

21.10 Operational Notes

raft-jepsen and conformance are release-gating artefacts, not runtime components — they do not ship to production. CI cadence: conformance on every PR (make conformance, fast); Jepsen-style runs nightly/pre-release only (§27). The conformance report and Jepsen history are both retained as release evidence in audits/reviews/ equivalents (tracked in docs/compliance-mapping.md).

24. Operational Readiness

  • Metrics. Every event follows the naming convention locked at §12 Phase 0 and emitted throughout §15–§21, exported via tracing + an OpenTelemetry bridge (ADR-14). Core gauges: raft.log.{first,last,committed,last_applied}_index, raft.role, raft.term.
  • Tracing. Every step/tick call is a span; election, replication, snapshot, and read-index sub-operations are child spans — enabling a single trace to show "why did this commit take 40ms" end to end.
  • Structured logging. JSON-structured, one line per state transition (role change, term bump, config change, snapshot event) — never printf-style free text for anything feeding an alert.
  • Dashboards. Per-cluster: leader identity + term over time, commit latency percentiles (§28 M2), replication lag per follower, election rate, snapshot transfer progress.
  • Alerting philosophy. Alert on invariant-adjacent telemetry (§7's Telemetry column) and on SLO breach (§28 M-table), never on raw error counts alone — a single transient raft.replicate.conflict is expected; a sustained rate is not.
  • SLOs. Commit latency p99 ≤ 25 ms (§4, M2); election-after-partition-heal p95 ≤ 200 ms (§4, M5); zero invariant violations (hard SLO, any violation pages immediately, not batched).
  • Incident response. First action on any paging alert: raft-cli status across the cluster to establish current leader/term/committed-index skew before touching config.
  • Named runbooks (§10): bring-up-cluster.md, promote-learner.md, replace-failed-node.md, restore-from-snapshot.md, handle-split-brain-suspect.md.
  • Backup/restore. A snapshot plus the log entries after it is the backup unit; restore-from-snapshot.md is the restore procedure; no separate backup format exists (P2 — three persistent shapes only).
  • Deployment topology. One process per node, intra-datacentre, behind the operator's own service mesh for discovery; raft-net does not implement peer discovery itself (§1 delegates).
  • Canary/rolling-upgrade/rollback. One node at a time, oldest binary version first; wire-format additive-only (P11) makes N and N+1 interoperate during the window; rollback is symmetric (redeploy the prior binary, no data migration needed, §25).

25. Compatibility & Versioning

  • Wire compatibility. All proto messages (§8.1) are additive-only past v1.0 (P11); a field is never repurposed or removed, only deprecated and ignored.
  • Storage compatibility. The redb/file on-disk layouts (§8.2) are versioned via a format-version byte in snapshot_meta; a minor-version upgrade must read all prior minor versions; a major-version bump requires an explicit migration path (out of scope to build until a major bump is actually needed — §35 Deferred Features Register tracks this).
  • API stability. Until v1.0, every public type is #[non_exhaustive]; every breaking change requires a paired ADR (§9 process). After v1.0, breaking changes follow the deprecation policy in docs/operator-guide.md (minimum one minor version of deprecation warning before removal).
  • Cross-project contract. StateMachine, LogStorage, StableStore, Snapshotter, Transport (§11) are the explicit contract with project 38 (KV Store); any change to these five traits requires a paired ADR in the consuming project referencing this blueprint's ADR (§9).
  • Migration. Switching storage backends (§13 Phase 1) is a full InstallSnapshot-driven rebuild, never an in-place format converter (no converter is in scope, §1).
  • Deprecation policy. A deprecated config knob (§4) warns for one minor version, then is rejected (hard error, not silently ignored) in the next.
  • SemVer policy. Patch: bugfixes, no API change. Minor: additive API, additive wire fields. Major: any breaking change to the five cross-project traits or to the wire format's non-additive semantics.
  • Rolling-upgrade guarantees. A cluster of any two adjacent minor versions interoperates fully (replication, election, snapshot transfer); more than one minor version apart is unsupported and refused at the transport handshake capability check.

26. Testing & Verification Strategy

  • Unit tests. Per-module, colocated with source (crates/*/src/**), covering pure logic (log slicing, conflict-hint computation, quorum arithmetic) in isolation.
  • Integration tests. Per-crate tests/ directories (§10) — leader_election.rs, log_replication.rs, membership.rs, snapshot.rs, read_index.rs, apply_path.rs, each phase's §N.5 fixtures (§15–§19).
  • Property tests (proptest, ADR-12): election_restriction, log_matching, leader_completeness, state_machine_safety — 1,024 random cluster histories each, tied directly to I1, I3, I4, I5 (§7).
  • Differential testing. raft-storage's three backends run the identical shared test module (§13 Phase 1) so behaviour is checked to be identical across redb/file/ memory.
  • Fuzzing (fuzz/, ADR-12): append_entries_decode, install_snapshot_decode, log_entry_roundtrip — wire-format decode paths, run under cargo-fuzz/libFuzzer continuously.
  • Chaos / fault injection. raft-sim (§20 Phase 8) for in-process, deterministic faults; raft-jepsen (§21 Phase 9) for real out-of-process kernel-level faults — two distinct layers, not redundant (ADR-18's "when rejected wins" explains why both exist).
  • Deterministic replay. Every raft-sim violation reproduces exactly from its seed (I11) — this is what makes a bug report actionable rather than "it happened once."
  • Soak testing. simulator.yml scheduled job runs 1,024 seeds × 24h simulated time each, nightly (§20 Phase 8).
  • Fault injection cadence. raft-jepsen's 60-minute run is nightly/pre-release, never PR-gating (§21 Phase 9, flakiness pitfall).
  • Conformance. conformance (§21 Phase 9) runs ~150 fixtures on every PR, fast (< 1 minute), gating merge.
  • Performance-regression gating. benchmarks/ (ADR-13) runs in CI; a regression past the §28 M-table thresholds fails the build (§27).
  • Tie-back to invariants. Every property test name maps to an invariant ID (§7); every phase's N.5 fixtures map to that phase's cited invariants/ADRs (§15–§21) — there is no test in this suite without a named correctness property it defends.

27. Build & Release Engineering

  • Reproducible builds. Cargo.lock committed; rust-toolchain.toml pins the compiler (ADR-01); CI builds are hermetic (no network access mid-build beyond the initial dependency fetch, verified against the lockfile hash).
  • Artifact signing. Release binaries and container images are signed (cosign or equivalent) before publication; signatures verified by docker-compose.yml's pull policy in the reference deployment.
  • SBOM. Generated per release (cargo-cyclonedx or equivalent) and attached to the GitHub release; feeds docs/compliance-mapping.md.
  • Release channels. main (unstable, every merge), tagged vX.Y.Z (stable, SemVer per §25), no separate "nightly" channel — the simulator's own nightly cadence (§20 Phase 8) substitutes for one.
  • CI/CD topology. .github/workflows/{ci,conformance,simulator,release,security}.yml (§10, §12 Phase 0): ci.yml on every push; conformance.yml on every PR; simulator.yml nightly (1,024 seeds); release.yml on tag push; security.yml (cargo audit/cargo deny, §22 T12) on every PR and nightly.
  • Version stamping. Every binary embeds its git SHA and Cargo.toml version via build.rs; raft-cli status reports it for on-call triage.
  • Provenance/attestation. Release workflow produces SLSA-style build provenance attached to the GitHub release, alongside the SBOM.
  • Dependency auditing. cargo audit (known vulnerabilities) and cargo deny (license policy against ADR-20's Apache-2.0/commercial split) both gate CI.

29. Scalability Analysis

  • Stays constant regardless of load: the three persistent shapes (P2), the O(1) per-message term-check dispatch, the fixed election/heartbeat timing knobs (§4).
  • Grows with cluster size N (voters): quorum-intersection computation O(N) per commitment check (O(2N) under joint consensus, §17 Phase 5); leader fan-out bandwidth O(N) (each follower gets its own replication stream); Progress map size O(N).
  • Grows with log length: RaftLog in-memory window is bounded by the snapshot anchor (I8), so steady-state memory is O(entries since last snapshot), not O(total log history) — this is the entire point of compaction (§18 Phase 6).
  • Grows with payload size: replication bandwidth is O(throughput × payload size) (§32 Back-of-Envelope Capacity Model derives the exact number from §4).
  • Named bottlenecks in order of first-hit: (1) leader CPU for per-follower serialization at high fan-out (N > 7 voters, §4's recommended ceiling); (2) leader network egress bandwidth at high learner fan-out (§4's soft cap of 32 learners); (3) disk fsync latency on the stable-state/log hot path (P6, I7) — this is the irreducible floor under commit latency (M2) because every commit requires at least one majority of fsyncs; (4) single-Raft-group throughput ceiling once (1) and (2) are optimised — addressed only by Multi-Raft sharding (§35 Deferred Features Register), not by tuning this library further.
  • Horizontal scaling: not applicable within one Raft group (consensus is fundamentally a single-writer-per-term design, I1) — horizontal scale comes from running multiple independent Raft groups (Multi-Raft, deferred) each owning a shard of the keyspace.
  • Vertical scaling: faster NVMe reduces the fsync floor (item 3 above) directly; faster network reduces items 1–2; neither raises the fundamental one-writer-per-term ceiling.
  • Sharding/partitioning: out of this library's scope by design (§1) — a consumer (e.g., project 38's KV store) shards at the application layer, running N independent RaftNode groups, one per shard, sharing raft-net's transport plumbing but not its log.
  • Coordination overhead: joint-consensus reconfiguration (§17 Phase 5) is the only operation whose cost grows with how often membership changes, not with steady-state load — infrequent by design (operator-driven, not workload-driven).
  • Practical ceiling: ~50,000–100,000 committed ops/s per Raft group on the reference hardware profile (§4, M1), bounded primarily by fsync latency (item 3) and leader CPU (item 1); the lever beyond that ceiling is Multi-Raft, not further single-group tuning (§35, §34 Alternative Architectures).

30. Mental Models & First Principles

  • MM1 — A Raft cluster is a single-writer replicated log, not N independent databases. Predicts: any write path bypassing the leader is definitionally not linearizable. Bug class without it: an engineer adds a "fast write path" on a follower for latency and silently breaks State Machine Safety. Applied in §16 Phase 4, I5/I6.
  • MM2 — Term is a logical clock for "who may I trust right now," not an election counter. Predicts: a message carrying a lower term is stale information to discard, not older information to reconcile. Bug class without it: a node tries to "merge" a lower-term message instead of ignoring it, reintroducing stale-leader writes. Applied in §15 Phase 3, I1.
  • MM3 — Commit is a property of a majority, not of the leader's local disk. Predicts: a leader's own fsync completing guarantees nothing about durability until a majority also holds the entry. Bug class without it: responding to a client before majority ack — "fire and forget" persistence. Applied in §16 Phase 4, I6, P6.
  • MM4 — The log is the state machine's only legitimate input channel. Predicts: any side-channel mutation of the FSM (an operator "just this once" direct edit) desyncs replicas silently and permanently. Bug class without it: manual out-of-band data fixes applied to one replica. Applied in §14 Phase 2, I5.
  • MM5 — A snapshot is a compressed prefix of the log, not a separate source of truth. Predicts: a snapshot missing the embedded configuration is definitionally incomplete, because configuration lives inside the log stream itself. Bug class without it: a hand-rolled snapshot format that forgets configuration and strands a restored node with no peers. Applied in §18 Phase 6, P13, I10.
  • MM6 — Determinism is a property of the whole call graph, not of any one function. Predicts: one nondeterministic call reachable from step() invalidates every invariant test built on the simulator, even unrelated-looking ones. Bug class without it: "it's just a UUID generator, how could that matter" reasoning. Applied in §20 Phase 8, I11.
  • MM7 — Pre-vote separates "can I win" from "do I commit to trying." Predicts: a system without this separation cannot avoid disturbing a working leader after any transient network hiccup. Bug class without it: unnecessary leader churn misdiagnosed as "network flakiness" instead of a protocol design gap. Applied in §15 Phase 3, P8.
  • MM8 — ReadIndex trades latency for a clock-free safety proof; lease reads trade the proof for latency. Predicts: enabling lease reads without verifying clock discipline is an availability/latency choice masquerading as a configuration flag. Applied in §19 Phase 7, P9.

32. Back-of-Envelope Capacity Model

Every number below is derived from §4's System Constraints table; none is asserted standalone.

  1. Per-follower replication bandwidth = throughput × payload = 50,000 ops/s × 256 B = 12.8 MB/s per follower stream (before wire overhead).
  2. Effective per-follower bandwidth with overhead = 12.8 MB/s × (1 + 32⁄256) ≈ 14.4 MB/s, using §4's 24–40 B/entry overhead midpoint (32 B) against a 256 B payload.
  3. Leader egress bandwidth, 3-node cluster = 2 followers × 14.4 MB/s ≈ 28.8 MB/s ≈ 230 Mbps — well under a commodity 1–10 Gbps NIC.
  4. In-memory log window at steady state = snapshot_min_entries (10,000, §4) × ~288 B/entry (256 B payload + 32 B overhead) ≈ 2.9 MB — trivial against the 256 MiB memory ceiling (M6), leaving headroom for inflight buffers.
  5. Worst-case per-follower inflight buffer = max_inflight (256) × ~288 B/entry ≈ 73.7 KB — far under the 1 MiB max_msg_bytes cap, showing max_inflight, not message size, is the binding constraint at this payload size.
  6. Steady-state FD count (7 voters + 32 learners) = 1 listener + 6 peer voters + 32 learner connections = 39 FDs, under the 64-FD budget (§4).
  7. Snapshot transfer theoretical floor = 1 GiB ÷ 125 MB/s (1 Gbps) ≈ 8.6 s; the §4/M7 target of 60 s leaves ≈ 7× headroom for chunking overhead and follower disk write speed.
  8. Cold-start read floor = 1 GiB ÷ ~2 GB/s typical NVMe sequential read ≈ 0.5 s; against the 30 s M8 target, this implies FSM restore itself must complete in ≲ 29.5 s for a 1 GiB state — the dominant cost is application-level restore, not disk I/O.
  9. Commit latency floor ≈ 1 fsync (~0.1–0.5 ms on NVMe) + 1 network RTT (< 1 ms intra-AZ, §4) ≈ 0.6–1.5 ms; against the p50 M2 target of 5 ms, this leaves ≈ 3.5–4.4 ms of margin for serialization and batching overhead.
  10. Raw log growth before compaction = 50,000 ops/s × 86,400 s/day × 288 B/entry ≈ 1.24 TB/day at sustained M1 throughput — this is why compaction is a frequent background operation, not a rare event, at this workload.
  11. Compaction trigger interval = snapshot_size_threshold (64 MiB, §4) ÷ (50,000 ops/s × 288 B/entry ≈ 14.4 MB/s) ≈ 4.4 s of sustained full-rate writes between compactions — implying raft-storage's compaction path (§13 Phase 1) must itself be cheap enough to run roughly every 4–5 seconds without perturbing commit latency (M2).
  12. Election-detection floor = min_election_timeout (150 ms) must exceed 2× network RTT (< 1 ms intra-AZ) by a comfortable margin (§4) — at ~150× the RTT floor, this confirms the default timeout range is dominated by avoiding spurious elections under GC/scheduling jitter, not by RTT itself.

34. Alternative Architectures (Roads Not Taken)

34.1 Multi-Paxos

Proposer --Prepare(n)--> Acceptors --Promise--> Proposer
Proposer --Accept(n,v)-> Acceptors --Accepted--> Proposer
(stable leader skips Prepare phase once it holds a Promise majority)

Regime where it wins: systems that need per-instance flexibility in which replica proposes (no single elected leader requirement baked into the protocol identity) — useful when leader election itself is delegated to an external, already-solved mechanism. Real embodying system: Google Chubby (Burrows, OSDI 2006, §5), Google Spanner. Why rejected: Paxos's two-phase-per-instance structure without an explicit leader concept is harder to reason about operationally and far harder to implement correctly from the paper alone — precisely the gap Ongaro & Ousterhout (§5) built Raft to close; this blueprint's whole premise (§2) is that understandability compounds into correctness.

34.2 Viewstamped Replication

Client -> Primary: request
Primary -> Backups: PREPARE(view, op, opnum)
Backups -> Primary: PREPARE-OK
Primary -> Client: reply (after f+1 acks, matches this blueprint's majority rule)
(view change on primary failure, analogous to a Raft election)

Regime where it wins: designs prioritizing a clean separation between the replication protocol and the recovery/view-change protocol as independently specified layers. Real embodying system: the original VR papers (Oki & Liskov, PODC 1988, §5); conceptually close to MongoDB's replica-set primary/secondary model. Why rejected: VR predates the "understandability as a design goal" framing and its view-change protocol is described with less operational precision than Raft's election protocol — this blueprint's ADR-08 (joint consensus) and ADR-03 (sync core testability) both lean on Raft's more explicit mechanical specification.

34.3 Zab (ZooKeeper Atomic Broadcast)

Leader -> Followers: PROPOSE(zxid, txn)
Followers -> Leader: ACK
Leader -> Followers: COMMIT(zxid)   // majority ACKs required
(recovery phase re-establishes epoch + syncs followers before normal-case broadcast resumes)

Regime where it wins: a system that is itself a coordination service (locks, configuration, group membership) rather than a general-purpose embeddable library — the API (znodes, watches) and the protocol are co-designed. Real embodying system: Apache ZooKeeper. Why rejected: Zab's specification and API are inseparable from ZooKeeper's own coordination-service semantics (§31); this blueprint's Phase-0 goal (§1) is a reusable trait-based library other systems embed with their own state machines, which Zab was never designed to be.

34.4 Chain Replication

Client writes -> Head -> Node2 -> Node3 -> ... -> Tail -> ack to Client
Client reads  -> Tail (always strongly consistent, no quorum math needed)

Regime where it wins: extremely read-heavy, write-light workloads where reads at the tail are free of any quorum computation and throughput scales by adding chain length without a leader-fan-out bottleneck. Real embodying system: van Renesse & Schneider's original chain replication (OSDI 2004, §5); conceptually present in FAWN-KV. Why rejected: chain reconfiguration on a node failure requires reshaping the whole chain topology (more disruptive than Raft's per-entry majority commitment), and write latency is O(chain length) sequential hops rather than O(1) parallel fan-out — a poor fit for this blueprint's commit-latency targets (§4, M2) at cluster sizes beyond 3–5 nodes.

36. Glossary

  • AppendEntries. The RPC the leader uses to replicate log entries and to heartbeat.
  • Apply. Feeding a committed entry to the state machine (§14 Phase 2).
  • Backpressure. The bounded-inflight discipline (max_inflight, max_msg_bytes) that prevents a leader from OOMing against a slow follower (P12, I12).
  • Catch-up Window. The maximum lag (catch_up_window, default 1,000) a candidate voter may have before promotion is allowed (§17 Phase 5).
  • Commit / Committed. A log entry is committed once a majority of voters durably hold it; only then may it be applied (I6).
  • Configuration. The set of voters and learners; Stable or Joint (§11.4).
  • Conformance Fixture. A named JSON file describing setup/steps/expected outbox, run by the portable conformance runner (§21 Phase 9, §11.16).
  • Deterministic Simulator. raft-sim; produces byte-identical traces for a fixed seed and scenario (I11, §20 Phase 8).
  • Election Restriction. A node grants its vote only if the candidate's log is at least as up-to-date as its own (§15 Phase 3, I1).
  • Election Safety. At most one leader per term (I1).
  • FollowerRead. Linearizable reads served by a follower via ReadIndex forwarding (§19 Phase 7).
  • First-Index Continuity. first_index = snapshot_last.index + 1 after every compaction (I8).
  • Heartbeat. An empty AppendEntriesReq the leader sends to maintain authority.
  • InstallSnapshot. The RPC used to send a snapshot to a lagging follower (§18 Phase 6).
  • Invariant. A protocol-level correctness property (I1–I14, §7) checked by InvariantChecker after every simulated step.
  • Jepsen. The fault-injection/linearizability-checking methodology (Kingsbury, §5) this blueprint's raft-jepsen (§21 Phase 9) directly models.
  • Joint Consensus. The two-phase membership-change protocol via C_old,new (P7, §17 Phase 5).
  • Leader Append-Only. A leader never overwrites or deletes its own log entries (I2).
  • Leader Completeness. Every committed entry is present in the log of every future leader (I4).
  • Leader Transfer. A graceful handoff of leadership via TimeoutNow (§15 Phase 3).
  • Learner. A non-voting replica that receives the log but is excluded from every quorum computation (§17 Phase 5).
  • Lease Read. An opt-in, clock-bounded linearizable-read optimisation (P9, §19 Phase 7).
  • Log Matching. Identical (index, term) implies identical preceding entries (I3).
  • Match Index. The highest index the leader has confirmed replicated to a given follower (§11.11).
  • Membership Change. A ConfigChangeRequest adding/removing voters or learners (§17 Phase 5).
  • Next Index. The next index the leader will send to a given follower (§11.11).
  • No-op. A blank entry the leader appends on election to enable committing prior-term entries (I4, §15 Phase 3).
  • Outbox. The drained-by-caller container for messages, persistence requests, apply requests, snapshot ops, and events emitted by step/tick (P3, §11.6).
  • PersistOp. A queued durability request the caller must perform before the protocol proceeds past the dependent action (I7).
  • Pre-Vote. A term-preserving vote solicitation used before a real election, to avoid disturbing a healthy leader (P8, §15 Phase 3).
  • Progress. The leader's per-follower flow-control state (next_index, match_index, ProgressState, §11.11).
  • Quorum. A majority of voters in the current Configuration (both sets, under Joint).
  • ReadIndex. The linearizable-read protocol confirming leadership via heartbeat and waiting for applied >= committed (I13, §19 Phase 7).
  • RequestVote. The RPC a candidate uses to solicit votes.
  • State Machine Safety. No two servers ever apply different entries at the same index (I5).
  • Stable State. The persisted current_term and voted_for pair (§8.3).
  • Term. A logical period of leadership; bumped on every real election (MM2).
  • TimeoutNow. The message a leader sends to trigger an immediate election on a leader-transfer target (§15 Phase 3).
  • Voter. A node that participates in elections and counts toward commitment quorums.
  • Wire Format Additive Evolution. The rule that proto fields are added, never repurposed or removed, enabling mixed-version rolling upgrades (P11, §25).
  • Witness Replica. A non-voting, quorum-counted replica holding only term/index metadata, reducing storage cost in geo-distributed deployments (§35, deferred).
