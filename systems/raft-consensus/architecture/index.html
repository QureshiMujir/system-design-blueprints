RaftNode (the FSM). Owns no threads, no clock, no sockets (P1). Public surface is step(from, Message), tick(elapsed), propose(bytes), change_membership(...), read_index(ctx), drain_outbox(), on_persisted(id), on_snapshot(ev) (§11.7). All state transitions are synchronous and total.

Role state. Follower | PreCandidate | Candidate | Leader | Learner, an enum (never a flag byte), each carrying only the state relevant to that role (§11, §15 Phase 3).

step()/tick() dispatch. step handles inbound Message variants (§11.5); tick advances logical time, firing election timeouts and heartbeats. Neither performs I/O; both only mutate in-memory state and push into Outbox (P1, P3).

Outbox. Messages to send, persistence requests (PersistOp), state-machine apply requests, snapshot ops, and observability Events — drained by the caller after every step/tick (§11.6, P3).

RaftLog. The in-memory sliding window over the log plus the snapshot anchor (snapshot_last), committed, last_applied (§11, §13 Phase 1, I8).

Election & Progress. Election timers, vote bookkeeping, and per-follower Progress (next_index/match_index/inflight window) that drives replication flow control (§15–§16 Phases 3–4, I12).

Snapshot coordinator. Capture/compaction/InstallSnapshot streaming state machine (§18 Phase 6, I10).

raft-storage. LogStorage / StableStore / Snapshotter traits plus redb (default), file (reference), and memory (test/sim) backends (§11.9, §13 Phase 1).

raft-net. Transport trait plus a tonic gRPC implementation with mutual TLS as a feature (§11.10, §22 Threat Model).

raft-sim. The deterministic scheduler, network/disk/clock fault injector, and the InvariantChecker that runs every invariant (I1–I14, §7) after every simulated step (§20 Phase 8).

raft-jepsen. An out-of-process harness driving real binaries under real Linux network namespaces with a Knossos-style linearizability checker over recorded histories (§21 Phase 9).

8. Domain Model / Protocol / Data Model

8.1 RPC wire formats (proto3, ADR-15)

message RequestVoteReq   { uint64 term=1; uint64 candidate_id=2; uint64 last_log_index=3;
                            uint64 last_log_term=4; bool pre_vote=5; }
message RequestVoteReply { uint64 term=1; bool vote_granted=2; bool pre_vote=3; }

message AppendEntriesReq   { uint64 term=1; uint64 leader_id=2; uint64 prev_log_index=3;
                              uint64 prev_log_term=4; repeated LogEntryProto entries=5;
                              uint64 leader_commit=6; }
message AppendEntriesReply { uint64 term=1; bool success=2; uint64 match_index=3;
                              optional uint64 conflict_term=4; optional uint64 conflict_index=5; }

message InstallSnapshotReq   { uint64 term=1; uint64 leader_id=2; uint64 last_included_index=3;
                                uint64 last_included_term=4; ConfigurationProto config=5;
                                uint64 offset=6; bytes data=7; bool done=8; fixed32 crc32c=9; }
message InstallSnapshotReply { uint64 term=1; uint64 bytes_received=2; }

message TimeoutNowReq { uint64 term=1; uint64 leader_id=2; }

message ReadIndexHeartbeatReq   { uint64 term=1; uint64 heartbeat_round=2; }
message ReadIndexHeartbeatReply { uint64 term=1; uint64 heartbeat_round=2; bool ack=3; }

Every message carries term first (I1's step-down check runs before any other dispatch, §15 Phase 3). Field numbers are locked once shipped (ADR-15, P11): additive-only evolution.

8.2 Log record layout (on-disk, redb backend, ADR-05)

log_entries table key = big-endian Index (u64); value = LogEntryProto bytes + 4-byte CRC32C trailer. stable_state table: single key 0, value = StableStateProto (current_term, voted_for) + CRC32C trailer, one redb transaction (Durability:: Immediate) per write (P2, P6, I7). snapshot_meta table: key = last_included_index, value = SnapshotMetaProto (last_included_term, config, checksum, size_bytes).

8.3 Persistent state (dissertation Section 5.1, mapped to StableState, §11)

Field Persisted Volatile equivalent
current_term yes, before any vote/AppendEntries reply —
voted_for yes, before RequestVoteReply{granted=true} —
log entries yes, before AppendEntriesReply{success=true} RaftLog.entries (in-memory window)
commit_index no (rederived) RaftLog.committed
last_applied no (rederived from state-machine snapshot) RaftLog.last_applied
next_index[], match_index[] no (leader-only, rebuilt on election) Progress map

8.4 Raft server state-transition table

From Event To Side effects
Follower election timeout PreCandidate send PreVote to all voters (P8)
PreCandidate pre-vote majority Candidate current_term += 1, voted_for = self, persist, send RequestVote
PreCandidate pre-vote fails / higher term seen Follower reset election timer
Candidate vote majority Leader append no-op (I4), init Progress for all peers, start heartbeats
Candidate AppendEntries from valid leader Follower reset election timer
Candidate election timeout PreCandidate retry pre-vote with new randomised timeout
Leader higher term observed in any reply Follower persist new term, step down
Leader TimeoutNow self-issued (leader transfer) (peer becomes Candidate) leader ceases proposing, target skips election timeout wait
Any RequestVote/AppendEntries with higher term Follower (same role if already Follower) persist term, reset voted_for
Learner promoted (config change commits) Follower (voter-eligible) begins participating in elections/commitment

8.5 Worked example — election + first commit (5-node cluster, terms omitted for brevity)

  1. Node A's election timer fires (Follower→PreCandidate). A sends PreVote{term=T+1} to B,C,D,E.
  2. B,C reply granted=true (their logs are not more up-to-date than A's). A has pre-vote majority (3 of 5, self included) → Candidate: current_term=T+1, persists, sends RequestVote.
  3. B,C grant (I1's up-to-date check passes); A becomes Leader, appends a no-op at (T+1, idx=N+1), sends AppendEntries to all.
  4. B,C persist and reply success=true, match_index=N+1. A's maybe_advance_commit sees majority (A,B,C) ⇒ committed=N+1. The no-op is now committed under the Leader Completeness rule (I4); any client proposal committed in a prior term is now safely committable too.

8.6 Malformed-input example

AppendEntriesReq{ prev_log_index=50, prev_log_term=3, entries=[...] } arrives at a follower whose log ends at index 40. The follower cannot verify prev_log_term because index 50 does not exist locally → replies success=false, conflict_index=41, conflict_term=None (dissertation Section 3.5 footnote's "log too short" case). The leader's maybe_decr_next (§16 Phase 4) uses conflict_index to jump next_index down to 41 directly instead of decrementing one at a time.

8.7 Failure-path example

Leader A crashes after durably appending entry 100 at term 5 but before any follower acknowledges it. B is elected leader at term 6 (having last matched entry 99). Per I4, entry 100 from term 5 was never committed (no majority), so B's log legitimately does not contain it; when A rejoins as a follower, AppendEntries from B forces truncate_suffix(100) on A, discarding the uncommitted entry — this is the correct, safety-preserving outcome, not data loss (I2 permits truncation on followers only; A is now a follower).
