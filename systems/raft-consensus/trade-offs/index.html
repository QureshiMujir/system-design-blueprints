Decisions (§9) · 22 ADRs

ADR-01

Language

Chosen

Rust 1.78+ stable, no nightly

Rejected

Go 1.22

When the rejected choice is right

Team has zero Rust experience and must ship an MVP in <4 weeks — Go's simpler concurrency model gets there faster

Why: Type-state role modelling, no GC pauses on election timers

ADR-02

Async runtime scope

Chosen

tokio 1.x confined to raft-net only

Rejected

async-std, smol

When the rejected choice is right

A minimal embedded target where tokio's footprint is too large — smol wins for near-no_std builds (§35)

Why: Ecosystem maturity, prost/tonic alignment

ADR-03

Protocol core execution model

Chosen

Sync, message-driven (step/tick)

Rejected

Async core (async fn step)

When the rejected choice is right

A pure client-facing gateway with no correctness ordering requirement — ordinary async code is fine there (why raft-net is async and raft is not)

Why: Simulator requires deterministic, reentrant-free stepping (P1, P3)

ADR-04

Default transport

Chosen

gRPC via tonic

Rejected

Custom framed TCP, QUIC

When the rejected choice is right

Intra-rack deployments (<0.1 ms/hop) where HTTP/2 framing overhead taxes p99 — custom framed TCP wins; lossy WAN links favor QUIC's independent-stream loss recovery

Why: Interop with project 38's KV store and external tooling

ADR-05

Default log backend

Chosen

Rejected

When the rejected choice is right

Extreme append rates (>200k appends/s single node) where a hand-tuned io_uring raw-segment log avoids B-tree overhead

Why: Crash-safe out of the box, replaceable later

ADR-06

Stable-state storage

When the rejected choice is right

ADR-07

Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Multi-Paxos

Proposer --Prepare(n)--> Acceptors --Promise--> Proposer
Proposer --Accept(n,v)-> Acceptors --Accepted--> Proposer
(stable leader skips Prepare phase once it holds a Promise majority)

Regime where it wins: systems that need per-instance flexibility in which replica proposes (no single elected leader requirement baked into the protocol identity) — useful when leader election itself is delegated to an external, already-solved mechanism. Real embodying system: Google Chubby (Burrows, OSDI 2006, §5), Google Spanner. Why rejected: Paxos's two-phase-per-instance structure without an explicit leader concept is harder to reason about operationally and far harder to implement correctly from the paper alone — precisely the gap Ongaro & Ousterhout (§5) built Raft to close; this blueprint's whole premise (§2) is that understandability compounds into correctness.

Viewstamped Replication

Client -> Primary: request
Primary -> Backups: PREPARE(view, op, opnum)
Backups -> Primary: PREPARE-OK
Primary -> Client: reply (after f+1 acks, matches this blueprint's majority rule)
(view change on primary failure, analogous to a Raft election)

Regime where it wins: designs prioritizing a clean separation between the replication protocol and the recovery/view-change protocol as independently specified layers. Real embodying system: the original VR papers (Oki & Liskov, PODC 1988, §5); conceptually close to MongoDB's replica-set primary/secondary model. Why rejected: VR predates the "understandability as a design goal" framing and its view-change protocol is described with less operational precision than Raft's election protocol — this blueprint's ADR-08 (joint consensus) and ADR-03 (sync core testability) both lean on Raft's more explicit mechanical specification.

Zab (ZooKeeper Atomic Broadcast)

Leader -> Followers: PROPOSE(zxid, txn)
Followers -> Leader: ACK
Leader -> Followers: COMMIT(zxid)   // majority ACKs required
(recovery phase re-establishes epoch + syncs followers before normal-case broadcast resumes)

Regime where it wins: a system that is itself a coordination service (locks, configuration, group membership) rather than a general-purpose embeddable library — the API (znodes, watches) and the protocol are co-designed. Real embodying system: Apache ZooKeeper. Why rejected: Zab's specification and API are inseparable from ZooKeeper's own coordination-service semantics (§31); this blueprint's Phase-0 goal (§1) is a reusable trait-based library other systems embed with their own state machines, which Zab was never designed to be.

Chain Replication

Client writes -> Head -> Node2 -> Node3 -> ... -> Tail -> ack to Client
Client reads  -> Tail (always strongly consistent, no quorum math needed)

Regime where it wins: extremely read-heavy, write-light workloads where reads at the tail are free of any quorum computation and throughput scales by adding chain length without a leader-fan-out bottleneck. Real embodying system: van Renesse & Schneider's original chain replication (OSDI 2004, §5); conceptually present in FAWN-KV. Why rejected: chain reconfiguration on a node failure requires reshaping the whole chain topology (more disruptive than Raft's per-entry majority commitment), and write latency is O(chain length) sequential hops rather than O(1) parallel fan-out — a poor fit for this blueprint's commit-latency targets (§4, M2) at cluster sizes beyond 3–5 nodes.
