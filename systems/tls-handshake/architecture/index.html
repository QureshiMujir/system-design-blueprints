Byte-stream transport adapter. Owns the socket or loopback pipe; performs no parsing or crypto; the untrusted-peer-input boundary begins the instant a byte crosses this adapter into the record layer.

Record layer. Fragments outbound records to the max size, reassembles inbound fragments, and is the sole owner of TrafficKeys and sequence numbers — the secret-material boundary starts here and everything below in the diagram may hold live key material.

Message parser/encoder. Bounds-checked length-prefixed decode of handshake messages from decrypted record-layer bytes; the buffer boundary — every length field is validated against remaining buffer length before a single byte is trusted.

Handshake state machine. ClientState/ServerState enums; the sole authority on which message is legal next; drives the transcript hash, key schedule, and alert subsystem.

Transcript-hash accumulator. Running hash over every handshake message in wire order; consumed by the key schedule's Derive-Secret calls and by Finished/ CertificateVerify.

Key schedule engine. Implements the HKDF-Extract/Expand-Label/Derive-Secret chain of RFC 8446 section 7.1, producing early, handshake and application secrets and, downstream, TrafficKeys.

ECDHE key-exchange module. Wraps tls-crypto's X25519/P-256 traits; produces the shared secret consumed once by the key schedule and then dropped.

Certificate parser and path validator. Reads untrusted DER from the peer; the second major untrusted-input boundary; never trusted until the full RFC 5280 chain validates to a trust anchor.

Signature verifier. Verifies RSA-PSS/ECDSA/Ed25519 signatures over the exact TLS 1.3 CertificateVerify signed-content construction (RFC 8446 section 4.4.3).

PSK/ticket store. Holds resumption secrets and session tickets; ticket keys are themselves secret material and covered by the same zeroization discipline.

Alert subsystem. The only path by which any component reports a fatal condition; every fatal alert aborts the connection — never a silent accept (I6).

8.3 Record Layer Wire Format

TLSPlaintext / TLSCiphertext outer header (RFC 8446 section 5.1):

Field Size Value
ContentType type 1 byte 20=alert, 21=change_cipher_spec (compat only), 22=handshake, 23=application_data
legacy_record_version 2 bytes always 0x0303 (TLS 1.2, frozen for middlebox compatibility)
length 2 bytes length of the following opaque payload, ≤ 2^14+256
fragment / encrypted_record variable plaintext (pre-encryption) or AEAD ciphertext

TLSInnerPlaintext (the AEAD plaintext, before encryption — RFC 8446 section 5.2):

Field Size Value
content variable the real handshake/application/alert bytes
type 1 byte the real ContentType, hidden inside encryption
zeros 0+ bytes padding, length is a policy choice, not protocol-fixed

Per-record nonce construction (RFC 8446 section 5.3):

nonce = static_iv  XOR  ( 0*(iv_len - 8) || seq_number_as_64bit_big_endian )

static_iv is the per-direction IV from the key schedule; seq_number starts at 0 for the first record protected under a given traffic secret and increments by 1 per record, never resetting except on an explicit key update (RFC 8446 section 4.6.3), which derives fresh traffic secrets and resets the sequence number to 0 under the new key.

8.4 Handshake Message Formats (byte layout)

ClientHello:

Field Size
legacy_version 2 bytes, 0x0303
random 32 bytes
legacy_session_id 0-32 bytes, length-prefixed
cipher_suites 2+ bytes each, length-prefixed vector
legacy_compression_methods 1 byte, must be [0x00]
extensions length-prefixed vector of Extension

Extension (generic):

Field Size
extension_type 2 bytes
extension_data length-prefixed opaque

Extensions relevant to Phase 0: supported_versions (list of 2-byte versions), supported_groups (list of NamedGroup), key_share (vector of KeyShareEntry: NamedGroup + length-prefixed public key bytes), signature_algorithms (list of SignatureScheme), pre_shared_key (list of PskIdentity + binder list), psk_key_exchange_modes (list of 1-byte mode: psk_ke=0, psk_dhe_ke=1).

ServerHello:

Field Size
legacy_version 2 bytes, 0x0303
random 32 bytes (HelloRetryRequest sentinel or downgrade sentinel may live here)
legacy_session_id_echo 0-32 bytes
cipher_suite 2 bytes
legacy_compression_method 1 byte, 0x00
extensions length-prefixed vector (must include supported_versions=0x0304, key_share)

8.5 Key Schedule — Derivation Chain (RFC 8446 section 7.1)

              0
              |
      HKDF-Extract(salt=0, PSK or 0)                =  Early Secret
              |
              +--> Derive-Secret(., "ext binder" | "res binder", "")     = binder_key
              +--> Derive-Secret(., "c e traffic", ClientHello)          = client_early_traffic_secret
              +--> Derive-Secret(., "e exp master", ClientHello)         = early_exporter_master_secret
              |
      Derive-Secret(Early Secret, "derived", "")     =  salt for next Extract
              |
      HKDF-Extract(salt=above, IKM=(EC)DHE secret)   =  Handshake Secret
              |
              +--> Derive-Secret(., "c hs traffic", CH..SH)   = client_handshake_traffic_secret
              +--> Derive-Secret(., "s hs traffic", CH..SH)   = server_handshake_traffic_secret
              |
      Derive-Secret(Handshake Secret, "derived", "") =  salt for next Extract
              |
      HKDF-Extract(salt=above, IKM=0)                =  Master Secret
              |
              +--> Derive-Secret(., "c ap traffic", CH..server Finished) = client_application_traffic_secret_0
              +--> Derive-Secret(., "s ap traffic", CH..server Finished) = server_application_traffic_secret_0
              +--> Derive-Secret(., "exp master",   CH..server Finished) = exporter_master_secret
              +--> Derive-Secret(., "res master",   CH..client Finished) = resumption_master_secret

Where HKDF-Expand-Label(Secret, Label, Context, Length) expands to HKDF-Expand(Secret, HkdfLabel, Length) with HkdfLabel encoding Length, the ASCII string "tls13 " || Label, and Context; and Derive-Secret(Secret, Label, Messages) = HKDF-Expand-Label(Secret, Label, Transcript-Hash(Messages), Hash.length). Each traffic secret is expanded once more into (write_key, write_iv) via HKDF-Expand-Label(secret, "key", "", key_length) and HKDF-Expand-Label(secret, "iv", "", 12).

Worked derivation, abridged (X25519, AES-128-GCM, SHA-256, no PSK): Early Secret = HKDF-Extract(salt=0x00*32, ikm=0x00*32). Handshake Secret = HKDF-Extract(salt=Derive-Secret(EarlySecret,"derived",""), ikm=ECDHE_shared_secret). client_handshake_traffic_secret = Derive-Secret(HandshakeSecret, "c hs traffic", Transcript(ClientHello..ServerHello)). This exact chain, with concrete byte values, is matched bit-for-bit against RFC 8448 section 3's published test vectors in Phase 1's N.5 fixtures.

8.6 ECDHE Computation (X25519, named steps)

  1. Generate 32 random bytes as the private scalar; clamp per RFC 7748 section 5 (clear bits 0-2 and bit 255, set bit 254) — delegated to x25519-dalek.
  2. Compute the public key as scalar * base_point(9).
  3. Place the public key bytes in the key_share extension's KeyShareEntry.
  4. On receipt of the peer's KeyShareEntry, compute shared_secret = scalar * peer_public_key (Montgomery ladder, constant-time, delegated).
  5. Reject an all-zero output (a low-order-point attack indicator) before use.
  6. Feed shared_secret into the key schedule's Handshake Secret extract and then drop it (zeroize) — it is never needed again.

8.7 Transcript-Hash Accumulation Rule

The transcript hash is the running output of the negotiated hash function (SHA-256 or SHA-384) over the concatenation, in wire order, of every HandshakeMessage's type+length+body bytes (never the record-layer framing). On HelloRetryRequest, the first ClientHello is replaced with a synthetic single record: message_hash(1) || len(32 or 48) || Hash(first ClientHello) before HelloRetryRequest and the second ClientHello are appended (P13, RFC 8446 section 4.4.1).

8.8 Certificate Path-Validation Algorithm (named steps, RFC 5280 section 6)

  1. Build the candidate chain from the leaf certificate to a self-signed root, using Authority Key Identifier/Subject Key Identifier matching where present.
  2. For each certificate, verify the issuer's signature over the subject certificate using the algorithm named in signatureAlgorithm.
  3. Check the validity period (notBefore/notAfter) against the current time for every certificate in the chain.
  4. Check basicConstraints: every non-leaf certificate must have CA:TRUE and, if pathLenConstraint is present, the remaining chain length must not exceed it.
  5. Check keyUsage: the leaf's key usage must permit digitalSignature (or keyEncipherment for RSA key-exchange fallback, out of Phase 0 scope).
  6. Check nameConstraints on every intermediate against the leaf's subject/SAN.
  7. Check the leaf's Subject Alternative Name against the expected peer hostname.
  8. Check the root against the configured TrustAnchor set.
  9. Revocation posture (decision table below) is applied last, after structural validation succeeds.

Decision table:

Check Pass Condition Failure Alert
Signature issuer key verifies subject signature bad_certificate
Validity period now within [notBefore, notAfter] for every cert certificate_expired
Name constraints leaf name permitted by every intermediate's constraint bad_certificate
Basic constraints every non-leaf has CA:TRUE, path length respected bad_certificate
Key usage leaf permits digitalSignature bad_certificate
Revocation OCSP-stapled response fresh and Good, or policy allows unknown certificate_revoked
Trust anchor root matches configured TrustAnchor unknown_ca

8.9 Signature Schemes — Signed-Content Construction

TLS 1.3 CertificateVerify (RFC 8446 section 4.4.3) signs, not the transcript hash directly, but:

signed_content = 0x20 * 64  ||  context_string  ||  0x00  ||  Transcript-Hash
context_string  = "TLS 1.3, server CertificateVerify"   (or "client CertificateVerify")

The 64 space (0x20) bytes and null separator exist specifically to prevent cross-protocol signature-reuse attacks (a signature valid under this construction cannot be replayed as a valid signature under an unrelated protocol's format).

8.13 Malformed-Input Examples

  • ClientHello with no mutually supported key_share group -> server sends HelloRetryRequest naming a supported group (not a fatal alert — a legitimate retry path, RFC 8446 section 4.1.4).
  • A Certificate message received in WaitEncryptedExtensions (skipped EncryptedExtensions) -> unexpected_message, fatal, per I6.
  • A certificate chain whose intermediate lacks CA:TRUE -> bad_certificate per section 8.8's decision table.
  • A Finished whose HMAC does not match the locally computed value over the transcript -> bad_record_mac, fatal, connection aborts with no partial trust extended to any preceding message (P4).
  • A record that fails AEAD authentication (tag mismatch) -> bad_record_mac, fatal, no partial plaintext is ever exposed to the caller.
  • 0-RTT early data replaying a previously-seen ticket without a fresh, unused single-use marker -> server rejects the early data (I10), continues the handshake without it, does not treat this as fatal to the rest of the handshake.
  • ServerHello.random containing the TLS 1.2 or TLS 1.1 downgrade sentinel while negotiating TLS 1.3 -> illegal_parameter, fatal, per I7.

8.14 Failure-Path Example (end-to-end)

Client sends ClientHello proposing X25519 only. Server does not support X25519 (only P-256 configured). Server has no common key_share -> checks supported_groups for a mutually acceptable group (P-256 present) -> sends HelloRetryRequest naming P-256 -> client resets transcript per P13, re-sends ClientHello with a P-256 key_share -> handshake proceeds normally from §8.11 step 2. If instead no group is mutually supported at all, server sends fatal handshake_failure and the connection closes without ever entering a keyed state.
