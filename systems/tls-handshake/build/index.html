⬜ Phase 0 — Skeleton, Record Layer Framing & CI §12

Objectives

Stand up the workspace (ADR-01, ADR-27), the crate boundaries of §1's Phase-0 list, and the TlsPlaintext/TlsInnerPlaintext/TlsCiphertext framing types from §8.3 with no crypto yet — pure byte-layout parse/encode. Wire CI (ADR-26) so every later phase lands on a green build.

Deliverable

A workspace that builds, with tls-record::TlsPlaintext/TlsCiphertext round-tripping through encode/decode on fixture byte arrays, and a green CI pipeline.

Acceptance
  • cargo build --workspace and cargo clippy --workspace -- -D warnings exit 0.
  • TlsPlaintext::decode round-trips against 5 fixture records in conformance/ covering each ContentType value.
  • A record with length exceeding 2^14+256 (§4) is rejected with record_overflow, verified by a named fixture oversized_record.bin.
  • CI pipeline (.github/workflows/ci.yml) passes on a clean clone.
Fixtures
  • conformance/malformed_messages/oversized_record.bin — length field exceeding max; expected: decode returns record_overflow.
  • conformance/malformed_messages/truncated_record.bin — length field exceeds actual buffer; expected: decode returns decode_error, not a panic.
  • conformance/malformed_messages/five_content_types.bin — one record per ContentType value; expected: each decodes with the correct discriminant.
Pitfalls
  • Treating legacy_record_version as meaningful for negotiation — it is frozen at 0x0303 by RFC 8446 section 5.1 and must never gate logic.
  • Panicking on a truncated length prefix instead of returning decode_error — this crate boundary is the first line of defense against malformed input (P11's spirit applied early).
  • Allocating a buffer sized by an attacker-controlled length field before validating it against the actual bytes available — validate length against remaining() first.
  • Forgetting that TlsInnerPlaintext's trailing content-type byte means the "content" length is length - 1 - padding_len, an off-by-one trap.

⬜ Phase 1 — HKDF and the Key Schedule §13

Objectives

Implement tls-core's KeySchedule engine exactly per RFC 8446 section 7.1: HKDF- Extract, HKDF-Expand-Label, and Derive-Secret, matched bit-for-bit against the RFC 8448 section 3 test vectors (I8, P7).

Deliverable

tls-core::KeySchedule producing every §8.5 secret and the derived TrafficKeys (key + IV) for AES-128-GCM, matched against RFC 8448 vectors.

Acceptance
  • All RFC 8448 section 3 intermediate values (Early Secret, Handshake Secret, Master Secret, all seven traffic/exporter/resumption secrets) match published vectors byte-for-byte — the acceptance gate is the vector match itself, not a subjective "derivation looks right."
  • HkdfLabel encoding matches a hand-computed fixture for a known label/context/length triple.
  • A wrong label string (mutation-tested: flip one byte of "c hs traffic") produces a derivation that diverges from the vector — proving the test actually discriminates.
Fixtures
  • conformance/rfc8448_vectors/simple_1rtt.json — full secret schedule for RFC 8448's "Simple 1-RTT Handshake" section, all seven secrets plus traffic keys.
  • conformance/rfc8448_vectors/hello_retry_request.json — RFC 8448's HRR-flow vectors, exercising the transcript reset (P13) at the key-schedule boundary.
  • conformance/rfc8448_vectors/resumption_psk.json — RFC 8448's resumption vectors, exercising Early Secret keyed by PSK rather than all-zero IKM.
Pitfalls
  • Confusing HKDF-Expand-Label's context parameter with the raw messages — it must be the transcript hash, not the message bytes, except inside Derive-Secret itself where the hashing happens.
  • Off-by-one in HkdfLabel's length prefix (RFC 8446 section 7.1 specifies exact byte widths) — a byte-level fixture catches this, a "looks about right" review does not.
  • Reusing a Secret for both HKDF-Extract salt and as a Derive-Secret input without checking which stage's transcript boundary applies (RFC 8448's HRR vectors specifically exercise this).
  • Deriving traffic keys before the key schedule has actually reached the corresponding stage — a KeyScheduleStage guard should make this a compile-time or immediate runtime error, not a silent wrong-secret bug.

⬜ Phase 2 — X25519 ECDHE and Shared-Secret Derivation §14

Objectives

Implement the ECDHE key-exchange module over X25519 (RFC 7748) per §8.6's named steps, behind the tls-crypto::KeyExchange trait (ADR-03, ADR-04), feeding the key schedule built in Phase 1.

Deliverable

tls-crypto::KeyExchange implementations for X25519 and P-256, integration-tested by computing a shared secret between two locally generated key pairs and feeding it through Phase 1's key schedule to reproduce an RFC 8448 vector's Handshake Secret.

Acceptance
  • X25519 shared-secret computation matches RFC 7748 section 6.1's test vectors byte-for-byte.
  • P-256 ECDH matches a published SP 800-56A / NIST CAVP-style test vector.
  • The all-zero-output rejection path is exercised by a crafted low-order public key fixture (conformance/malformed_messages/low_order_point.bin) and produces a fatal illegal_parameter, not a silent zero secret.
  • A constant-time verification pass (Phase 11's dudect harness, run early here as a smoke check) shows no measurable timing correlation between the private scalar and computation time, within the harness's statistical threshold.
Fixtures
  • conformance/rfc8448_vectors/x25519_shared_secret.json — RFC 7748 section 6.1 vectors.
  • conformance/malformed_messages/low_order_point.bin — a known X25519 low-order point as peer public key; expected: illegal_parameter, not a zero-valued shared secret silently accepted.
  • conformance/malformed_messages/wrong_length_key_share.bin — a key_share public value of the wrong byte length for its named group; expected: decode_error.
Pitfalls
  • Trusting the wrapped crate's default behavior without verifying it rejects low-order points — some X25519 implementations silently accept them, producing a predictable shared secret.
  • Not zeroizing the raw scalar and shared secret immediately after use — they are needed exactly once (§8.6 step 6) and are pure liability afterward (I5).
  • Mixing up which side's public key goes into shared_secret() — a same-side bug (computing my_priv * my_pub instead of my_priv * peer_pub) produces a plausible-looking but wrong secret that only surfaces as a Finished-verification failure three phases later.

⬜ Phase 3 — AEAD Record Protection §15

Objectives

Implement the record layer's AEAD protect/unprotect path (tls-record::seal/open) over AES-128-GCM, AES-256-GCM and ChaCha20-Poly1305, with the exact per-record nonce construction from §8.3 (I2, P5).

Deliverable

tls-record::RecordLayer sealing and opening records under all three AEAD algorithms, with a fixture suite proving nonce correctness and authentication-failure handling.

Acceptance
  • Seal-then-open round-trips correctly for AES-128-GCM, AES-256-GCM and ChaCha20-Poly1305 against RFC 5116/RFC 8439-style test vectors.
  • A record decrypted with a deliberately wrong key produces bad_record_mac, not a panic and not garbage plaintext exposed to the caller.
  • A fixture asserting that two sequential records under the same key produce different nonces (sequence number 0 vs 1) and that the ciphertexts differ even for identical plaintext — proving nonce derivation is live, not accidentally frozen at zero.
  • The rekey-before-wraparound guard fires in a fixture that artificially sets send_seq near 2^64 - 1 (not a real 2^64-record test, which is infeasible to run, but a boundary-condition unit test of the trigger logic).
Fixtures
  • conformance/rfc8448_vectors/aes128gcm_record.json — a captured RFC 8448 handshake's first application-data record, exact ciphertext bytes.
  • conformance/malformed_messages/bad_record_mac.bin — a record with a flipped ciphertext byte; expected: open returns bad_record_mac.
  • conformance/malformed_messages/replayed_record.bin — a record with a sequence number that has already been consumed; expected: rejected (implementation detail: the sequence counter itself prevents constructing this legitimately, so this fixture exercises the defensive check on the receive path if seq is ever externally supplied).
Pitfalls
  • Constructing the nonce from the sequence number in host byte order instead of big-endian — produces a plausible-looking but wrong nonce that fails interop silently until Phase 11.
  • Exposing partially-decrypted plaintext before the AEAD tag check completes — some streaming AEAD APIs decrypt-then-verify; this implementation must verify-then-expose, never the reverse (I9's authenticated-before-trusted principle).
  • Forgetting the AAD (the 5-byte outer header) in either seal or open — omission is a spec deviation that silently produces non-interoperable ciphertext.
  • Treating ChaCha20-Poly1305's 96-bit nonce and AES-GCM's 96-bit nonce as identical in construction without checking each cipher's actual IV-length requirement from its own RFC (8439 vs 5288/5289) — they happen to match at 12 bytes in TLS 1.3's usage, but the code should not hardcode this coincidence without a citation-backed comment.

⬜ Phase 4 — Handshake Message Parsing and Encoding §16

Objectives

Implement tls-handshake's message codec: typed encode/decode for every §8.4 message and extension, bounds-checked per P11, feeding the transcript hash (I3) as messages are consumed.

Deliverable

A complete encode/decode round-trip for every Phase-0-scope message type, integrated with the transcript-hash accumulator.

Acceptance
  • Every message type round-trips encode -> decode -> encode to byte-identical output against 12+ named fixtures (one per message type plus HRR and NewSessionTicket variants).
  • The legacy_compression_methods nonzero-value fixture produces illegal_parameter.
  • The PSK binder fixture (conformance/rfc8448_vectors/resumption_psk.json, reused from Phase 1) verifies correctly when computed over the correct partial transcript and fails when computed over the full transcript by mistake — proving the test actually discriminates the subtle partial-transcript rule.
  • Every decoder rejects a length field exceeding remaining buffer with decode_error, verified by a fuzz-derived corpus of 20+ truncated fixtures.
Fixtures
  • conformance/malformed_messages/{client_hello,server_hello,encrypted_extensions, certificate,certificate_verify,finished,new_session_ticket,hello_retry_request}.bin — one well-formed fixture per type for round-trip testing.
  • conformance/malformed_messages/nonzero_compression.bin — legacy_compression_methods != [0x00]; expected illegal_parameter.
  • conformance/malformed_messages/binder_over_full_transcript.bin — a PSK binder computed incorrectly over the full transcript instead of the partial one; expected: binder verification fails.
Pitfalls
  • Computing the PSK binder over the wrong transcript slice (RFC 8446 section 4.2.11 is explicit that the binder covers ClientHello up to but excluding the binder list itself) — an easy one-message-too-many bug.
  • Parsing extension_data generically before dispatching on extension_type, then re-parsing typed data from an already-consumed cursor — prefer decode functions that take an explicit sub-slice per extension, bounded by the extension's own length.
  • Validating an extension's outer length but not cross-checking it against the sum of its inner vector lengths — a mismatch here is a classic parser-differential bug (a decoder might silently ignore trailing garbage another implementation rejects).

⬜ Phase 5 — Client Handshake State Machine to Finished §17

Objectives

Implement ClientState's full transition table (§8.1) as an exhaustive, typestate- encoded state machine (ADR-08, P1), driving Phase 1's key schedule, Phase 2's ECDHE, and Phase 4's message codec to a verified Connected state.

Deliverable

A client-side state machine that completes a full 1-RTT handshake to Connected against a fixture server transcript (RFC 8448) and correctly rejects every §8.13 malformed-input example.

Acceptance
  • Client reaches Connected and derives application traffic secrets matching RFC 8448 section 3's vectors, replaying a captured server transcript through the state machine (not yet a live peer — that is Phase 11).
  • Every out-of-order message fixture (Certificate before EncryptedExtensions, Finished before CertificateVerify) produces unexpected_message (I6) from every applicable state, not just the "obvious" ones.
  • The HRR fixture (conformance/rfc8448_vectors/hello_retry_request.json) completes to Connected with a correctly-reset transcript (I13).
  • The downgrade-sentinel fixture produces illegal_parameter regardless of whether the rest of the handshake would otherwise succeed.
Fixtures
  • conformance/rfc8448_vectors/simple_1rtt.json — drives the client to Connected.
  • conformance/rfc8448_vectors/hello_retry_request.json — drives the HRR retry path.
  • conformance/malformed_messages/downgrade_sentinel.bin — a ServerHello.random with the TLS 1.2 downgrade sentinel present; expected illegal_parameter.
  • conformance/malformed_messages/out_of_order_*.bin — one fixture per illegal transition in §8.1's table.
Pitfalls
  • Checking the downgrade sentinel only in an error-handling branch instead of unconditionally — reproduces exactly the class of bug the sentinel exists to catch (an attacker who successfully forces version negotiation "looks like" the happy path).
  • Trusting Certificate/CertificateVerify content before Finished verifies (P4) — Phase 5 must structurally defer any use of the certificate's authority (e.g. exposing the peer identity to the application) until after Connected.
  • Handling HelloRetryRequest as "just another ServerHello" without the transcript special-case (P13) — produces a Finished value that fails against any fully compliant peer.

⬜ Phase 6 — Server Handshake State Machine §18

Objectives

Implement ServerState's full transition table (§8.2), mirroring Phase 5's discipline on the server side, including parameter selection and the HelloRetryRequest-issuing path.

Deliverable

A server-side state machine that completes a full 1-RTT handshake (including the HRR branch) to Connected against fixture client transcripts.

Acceptance
  • Server reaches Connected and derives secrets matching RFC 8448 vectors when driven by the vector suite's client-side messages.
  • The HRR-issuance path is exercised end-to-end: a ClientHello offering only an unsupported group triggers HRR naming a supported one, and a correctly-formed second ClientHello completes the handshake.
  • A second HRR attempt (malformed test harness feeding two mismatches in a row) produces fatal illegal_parameter (I13), not an infinite retry loop.
  • handshake_failure fires when zero mutually acceptable groups exist, verified by a named fixture.
Fixtures
  • conformance/rfc8448_vectors/simple_1rtt.json — server-side replay to Connected.
  • conformance/malformed_messages/no_common_group.bin — ClientHello offering zero mutually supported groups; expected handshake_failure.
  • conformance/malformed_messages/double_hrr_mismatch.bin — a second ClientHello still not matching the HRR's requested group; expected illegal_parameter.
Pitfalls
  • Deriving the handshake traffic secrets before finishing parameter selection (cipher suite must be locked in before the hash function used by the key schedule is known).
  • Allowing an unbounded HRR retry loop instead of enforcing the single-retry limit (I13) — a naive implementation might treat each mismatch as "try again," which is both a spec violation and a DoS amplification vector (T-adjacent to §24).
  • Sending EncryptedExtensions before the handshake traffic secrets are actually installed on the send side — an ordering bug that produces ciphertext under the wrong (or absent) key.

⬜ Phase 7 — X.509 Certificate Parsing (Hardened DER) §19

Objectives

Implement tls-cert's hardened ASN.1/DER reader and the X.509 certificate model (RFC 5280), the first component to consume fully untrusted, adversarial byte input end-to-end (P11, ADR-10).

Deliverable

tls-cert's DER reader and X509Fields extraction, hardened against the adversarial certificate corpus, with zero crashes under the Phase 11 fuzz gate (a gate whose initial run starts in this phase and continues through Phase 11).

Acceptance
  • Parses a corpus of 20+ real-world certificates (self-signed test fixtures covering RSA-2048, RSA-3072, ECDSA-P256, Ed25519 subject keys) without error.
  • Rejects every adversarial fixture in conformance/adversarial_certs/ with decode_error or bad_certificate, never a panic — this is a zero-crash gate, not a "handles most cases" gate.
  • A 24-hour libFuzzer smoke run (full campaign is Phase 11) on fuzz_targets/ der_parser.rs finds zero crashes and zero ASan/UBSan findings.
  • The recursion-depth guard rejects a crafted deeply-nested SEQUENCE fixture at the configured maximum, verified by a named fixture, not merely "eventually stack overflows are prevented in practice."
Fixtures
  • conformance/adversarial_certs/deeply_nested_sequence.der — recursion-depth attack; expected decode_error.
  • conformance/adversarial_certs/oversized_length_claim.der — a length field claiming more bytes than the buffer contains; expected decode_error, not an overread.
  • conformance/adversarial_certs/indefinite_length_ber.der — BER indefinite-length encoding (invalid in strict DER); expected decode_error (DER, not BER, is the accepted grammar — ADR-10).
  • conformance/adversarial_certs/oversized_chain.der — a chain exceeding §4's max length/size; expected rejection before per-certificate parsing begins (T10).
  • conformance/adversarial_certs/valid_rsa_ecdsa_ed25519.der — three well-formed fixtures, one per supported key algorithm, for the positive-path test.
Pitfalls
  • Allocating a buffer sized by a claimed DER length before validating it against actual remaining bytes — the canonical DER-parser overread bug (P11).
  • Accepting BER's indefinite-length form when only strict DER is specified for X.509 (RFC 5280 requires DER, not general BER) — a parser that is "helpfully" lenient here widens the attack surface ADR-10 exists to narrow.
  • Treating a certificate's extensions as optional-and-ignorable when basicConstraints/keyUsage absence has security meaning (RFC 5280 section 4.2.1.9: absence of basicConstraints on a CA certificate is itself often treated as non-CA) — an omission bug here is a validation-bypass precursor to Phase 8.
  • No recursion-depth limit, relying on "DER doesn't nest that deep in practice" — this is exactly the informal assumption a fuzzer exists to falsify.

⬜ Phase 8 — Certificate Path Validation and Signature Verification §20

Objectives

Implement PathValidator per §8.8's named steps and decision table (RFC 5280 section 6), and SignatureVerifier for RSA-PSS/ECDSA/Ed25519 over the exact §8.9 signed-content construction, replacing Phase 5/6's stubs (I4, P3).

Deliverable

A working PathValidator and SignatureVerifier integrated into both client and server state machines, replacing the Phase 5/6 stubs, tested against the full adversarial certificate corpus from Phase 7 plus new chain-level fixtures.

Acceptance
  • A valid 3-certificate chain validates successfully; every single-field mutation (wrong signature, expired validity, missing CA:TRUE, wrong keyUsage, name-constraint violation, untrusted root) is individually rejected with the correct alert from §8.8's decision table — not merely "some mutation is caught."
  • RSA-PSS, ECDSA-P256 and Ed25519 CertificateVerify signatures verify correctly against fixtures signed by a real reference implementation (OpenSSL-generated).
  • The "goto fail" regression test asserts SignatureVerifier::verify is never called when PathValidator::validate returned an error in the same code path (a structural, call-order test, not just a behavioral one).
  • Constant-time verification pass (Phase 11) shows no timing correlation for RSA-PSS verification across valid/invalid signature inputs.
Fixtures
  • conformance/adversarial_certs/valid_chain_leaf_intermediate_root.der — the positive-path fixture, three real certificates.
  • conformance/adversarial_certs/chain_wrong_signature.der, chain_expired.der, chain_missing_ca_true.der, chain_bad_key_usage.der, chain_name_constraint_violation.der, chain_untrusted_root.der — one mutation per decision-table row (§8.8), each expected to fail with its specific named alert.
  • conformance/rfc8448_vectors/certificate_verify_{rsapss,ecdsa,ed25519}.json — signature fixtures per algorithm.
Pitfalls
  • The "goto fail" class itself: an early-return bug where a validation step's error path falls through to a success path — mitigated not just by "write correct code" but by the structural test in N.4.
  • Verifying CertificateVerify over the raw transcript hash instead of the §8.9 wrapped construction — verifies against a non-compliant peer but fails against every RFC-8446-compliant one, a silent interop trap.
  • Checking basicConstraints presence but not its CA:TRUE value (an intermediate with CA:FALSE must still be rejected as a non-CA acting as an issuer).
  • Treating OCSP-staple absence as equivalent to staple-says-good — ADR-12's soft-fail is a deliberate policy choice, distinguishable in telemetry from an actual "good" response.

⬜ Phase 9 — Transcript Hash, Downgrade Protection and Alerts §21

Objectives

Harden and centralize the transcript-hash accumulator (already used since Phase 4), formalize downgrade-sentinel handling (already begun in Phase 5), and implement the complete alert subsystem (§8.10) as the sole path for fatal-condition reporting (I6, I11, P10).

Deliverable

A centralized, single-owner transcript-hash component and a complete alert subsystem, integrated so that every prior phase's ad hoc error paths now route through send_fatal_alert.

Acceptance
  • A fixture asserting exactly one TranscriptHash::update() call per handshake message across a full recorded handshake — proving I3 by construction, not just by the final hash matching.
  • Every alert in §8.10's catalogue has at least one fixture that triggers it via the actual code path that would raise it in production (not a synthetic direct construction) — 18+ named fixtures.
  • The single-retry HRR guard (I13) and the downgrade-sentinel check (I7) are both re-verified as still passing after the alert-subsystem consolidation (regression gate).
  • close_notify is distinguishable from every fatal alert in a fixture asserting the connection remains in a "clean shutdown" telemetry state, not an "error" one.
Fixtures
  • conformance/malformed_messages/alert_catalogue/*.bin — 18 fixtures, one per AlertDescription value, each triggered via its real code path.
  • conformance/rfc8448_vectors/hello_retry_request.json — re-run against the consolidated transcript component.
  • conformance/malformed_messages/close_notify_graceful.bin — a clean shutdown sequence, expected: no error telemetry, connection state Closed(graceful).
Pitfalls
  • Leaving any earlier phase's ad hoc TlsError return without routing through send_fatal_alert — this phase's job is specifically to find and close those gaps, since a fatal condition that doesn't send an alert leaves the peer without diagnostic information and may leave the local state ambiguous (I11's exact concern).
  • Conflating close_notify (warning-level, graceful) with a fatal alert in shared handling code — they must be structurally distinguished (AlertLevel), not just by convention.
  • Re-triggering retry_reset() on a second, illegitimate HelloRetryRequest instead of rejecting it outright (I13) — the single-call guard must be enforced here, not merely hoped for.

⬜ Phase 10 — Session Resumption, Tickets and 0-RTT Early Data §22

Objectives

Implement PSK-based session resumption (NewSessionTicket, pre_shared_key), ticket encryption/rotation (ADR-16), and 0-RTT early data with its explicit replay-risk scoping (P9, I10, ADR-15).

Deliverable

Working PSK resumption (both psk_ke and psk_dhe_ke modes) and opt-in 0-RTT early data with single-use anti-replay enforcement, integrated into both state machines.

Acceptance
  • A resumption handshake (§8.12) completes and derives secrets matching RFC 8448's resumption vectors byte-for-byte.
  • Resumed handshake CPU cost, measured in benchmarks/handshake_throughput.rs, shows the ratio predicted in §34 (symmetric-only cost, no signature verification) against a full handshake.
  • A 0-RTT early-data fixture is accepted on first presentation and rejected (I10) on a simulated replay of the same ticket, verified as two distinct fixtures with distinct expected outcomes.
  • Ticket-key rotation is exercised by a fixture presenting a ticket encrypted under a key one rotation period old — accepted; and under a key two rotation periods old — rejected.
Fixtures
  • conformance/rfc8448_vectors/resumption_psk.json — resumption secret schedule, reused from Phase 1/4, now exercised end-to-end through both state machines.
  • conformance/malformed_messages/zero_rtt_replay.bin — a second presentation of a consumed 0-RTT ticket; expected: early data rejected, 1-RTT handshake still completes.
  • conformance/malformed_messages/expired_ticket_key.bin — a ticket encrypted under a rotated-out key; expected: PSK rejected, server falls back to a fresh full handshake.
Pitfalls
  • Enabling 0-RTT by default rather than opt-in per data type (P9 explicitly forbids this) — the replay risk must be a deliberate application-level choice.
  • Deriving the Early Secret from an all-zero IKM on a resumed handshake by mistake (copy-paste from the non-PSK path) — must use the actual resumption PSK.
  • Forgetting psk_dhe_ke's fresh ECDHE step, treating resumption as symmetric-only even when forward secrecy is mandated — psk_ke-only mode sacrifices forward secrecy and should be a distinct, clearly-labeled configuration choice, not the silent default (ADR-14).
  • Ticket single-use marking scoped only to the ticket label without considering that an attacker might replay before the marker propagates in a multi-server fleet — document this as a known limitation of in-memory single-node marking versus a shared-store design (T-relevant, see §24 T7).

⬜ Phase 11 — Interop Testing, Fuzzing, Conformance and Perf Hardening §23

Objectives

Validate every prior phase against real TLS stacks (the ultimate conformance oracle), run the full fuzzing campaign to a zero-crash gate, execute the constant-time verification pass, and close out performance targets against §4/§30.

Deliverable

A green interop matrix against three real TLS stacks in both roles, a 72-hour zero-crash fuzz campaign result, a passing constant-time verification report, and a perf-regression-gated CI pipeline meeting §30's targets.

Acceptance
  • 6/6 interop combinations complete a full handshake and exchange application data successfully; resumption succeeds in every combination where the peer supports TLS 1.3 resumption; 0-RTT succeeds where the peer supports it (some peers may not enable 0-RTT by default — documented per-peer in the interop matrix results, not treated as a failure of this implementation).
  • Zero crashes and zero ASan/UBSan findings across the full 72-hour fuzz campaign on all three fuzz targets — this is the explicit gate, not "very few" crashes.
  • The constant-time harness reports no statistically significant timing divergence for AEAD, ECDHE and signature-verification paths, at the harness's configured confidence threshold.
  • Every §30 performance target (M1-M12) is met or the PR is blocked by the perf-regression gate.
Fixtures
  • conformance/rfc8448_vectors/* — full re-run against every interop peer's live transcript for cross-validation, not just the static RFC 8448 vectors.
  • conformance/malformed_messages/* — full corpus re-run as fault-injection input to each live interop peer to confirm this implementation's alerts are themselves well-formed and accepted by real peers as valid alerts.
  • New: conformance/interop_transcripts/{openssl,boringssl,rustls}_{client,server}.pcap — captured interop-matrix transcripts promoted to permanent regression fixtures.
Pitfalls
  • Treating a single successful interop run as sufficient — interop bugs are often intermittent (e.g. triggered only by a specific extension ordering a particular peer version happens to send); the matrix must run repeatedly across peer version updates, not once and done.
  • Running the fuzz campaign for a short smoke duration and calling it complete — deep parser bugs (recursion, arithmetic overflow) often require sustained corpus evolution over many hours to surface (this phase's 72-hour figure is a floor, not a target to shortcut).
  • Interpreting a constant-time harness's "no divergence detected" as a formal proof — it is a statistical test with a detection floor (dudect-style tools have known limits); document this honestly rather than overclaiming.
