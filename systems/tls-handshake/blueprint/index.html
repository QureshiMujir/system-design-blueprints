48 — TLS/SSL Handshake

Project Number: 48

Project Name: TLS/SSL Handshake

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from scratch in Rust, a from-scratch TLS 1.3 (RFC 8446) handshake engine and record layer: the full client and server handshake state machines (ClientHello through Finished, HelloRetryRequest, 0-RTT early data, and post-handshake NewSessionTicket), the key schedule (HKDF-Extract / HKDF-Expand-Label / Derive-Secret producing the early, handshake and application secret trees), ECDHE key exchange over X25519 and P-256, AEAD record protection (AES-128/256-GCM and ChaCha20-Poly1305) with correct per-record nonce construction, an X.509 certificate parser and RFC 5280 path validator, signature verification for RSA-PSS, ECDSA and Ed25519, and session resumption via PSK and tickets. The engine is delivered as a library exposing a streaming (sans-io) state machine plus a record layer; it does not own a socket. The work is organized as 12 phases (§12-§23), each independently testable, each gated by fixtures and — where interop is meaningful — by a live handshake against a real TLS stack.

Phase-0 deliverable — crate list:

  1. tls-core — HKDF, key schedule, Secret/TrafficKeys types, transcript-hash accumulator, cipher-suite registry.
  2. tls-crypto — trait boundary (Aead, KeyExchange, Signer, Verifier, Hash) wrapping audited primitive crates; no primitive math lives above this trait.
  3. tls-record — TlsPlaintext/TlsInnerPlaintext/TlsCiphertext, AEAD seal/open, sequence-number-driven nonce construction, fragmentation.
  4. tls-handshake — message parser/encoder, ClientState/ServerState machines, alert subsystem.
  5. tls-cert — hardened DER/ASN.1 reader, X.509 certificate model, RFC 5280 path validator.
  6. tls-net — thin adapter from the sans-io state machine to a Read + Write or AsyncRead + AsyncWrite transport, for example programs and tests only.

Boundaries. Provides: the full TLS 1.3 protocol state machine, key schedule, record layer, certificate parsing and path validation, alert handling, resumption. Delegates: the raw curve arithmetic (X25519, P-256), AEAD primitives (AES-GCM, ChaCha20-Poly1305) and signature math (RSA, ECDSA, Ed25519) to audited crates (x25519-dalek, p256, aes-gcm, chacha20poly1305, ring for RSA-PSS) behind the tls-crypto trait boundary — see ADR-03. This is a deliberate choice: re-implementing constant-time field arithmetic is a distinct research project (side-channel engineering) from protocol correctness, and mixing the two would dilute the handshake-state-machine and key-schedule focus that is this project's mastery target. Does NOT provide: a certificate authority, a trust-store distribution mechanism, DTLS, QUIC's packet protection layer, or a general-purpose ASN.1 codec beyond what X.509 requires.

Non-goals (Phase 0). TLS 1.3 only; TLS 1.2 interoperability is PhaseDeferred("RFC 8446 Appendix D — Backward Compatibility"). No QUIC transport integration in Phase 0 — PhaseDeferred("RFC 9001 — Using TLS to Secure QUIC"). Not a full PKI/CA: no certificate issuance, no OCSP responder, no CT log — only client-side path validation of a chain presented by a peer.

Deployment model. A library, not a daemon: a streaming handshake state machine (ClientState/ServerState) that consumes and produces byte buffers with no I/O of its own (the "sans-io" pattern — see ADR-19, and the rustls precedent in §33), plus a record layer usable independently for post-handshake data. Usable as either TLS client or TLS server from the same crate family. tls-net is an optional convenience adapter for tests and examples, not the shipped contract.

Users/operators. Protocol implementers embedding TLS into a custom transport (embedded targets, in-process test harnesses, future QUIC integration); security engineers studying the handshake state machine and key schedule as a teaching artifact; CI-driven interop testers exercising the engine against OpenSSL/BoringSSL/rustls.

What later phases unlock. Phase 7-8 unlock real peer authentication (certificate parsing and path validation) so Phase 9's downgrade protection and alert subsystem have something to protect; Phase 10's resumption and 0-RTT are only safe once Phase 9's transcript-hash and anti-downgrade machinery are load-bearing; Phase 11's interop suite is the only phase that can retroactively falsify every earlier phase's fixture-only "acceptance."

Rust + rationale. The borrow checker and ownership model make secret-material lifetime and zeroization checkable at compile time (a Secret that is moved cannot be read from twice); the type system encodes the handshake state machine as an enum whose variants carry only the fields legal in that state, making an "impossible transition" a compile error rather than a runtime bug (see P1, ADR-08); performance is competitive with C in the record-layer hot path without a garbage collector's pause-time tax. Rejected: C — the language of Heartbleed (CVE-2014-0160) and the "goto fail" bug class; manual memory management is precisely the class of bug this project is trying to make structurally impossible. Go — memory-safe, but the reference stdlib (crypto/tls) already exists in Go and offers no new lesson, and its GC pause profile is a poor match for a record layer's latency floor. Python — throughput on the record layer's per-byte AEAD path would be 1-2 orders of magnitude short of §4's targets.

Prerequisites. Modern applied cryptography (AEAD, Diffie-Hellman/ECDH, digital signatures, HKDF and key derivation); ASN.1 BER/DER encoding and X.509 certificate structure (RFC 5280); explicit state-machine design and the cost of implicit/permissive transitions (Beurdouche et al. 2015).

Timeline. 12 phases, each 3-10 working days at a disciplined pace; Phase 0-3 (skeleton through AEAD) roughly 2 weeks; Phase 4-6 (message codec through server state machine) roughly 3 weeks; Phase 7-9 (certificates through alerts) roughly 3 weeks; Phase 10-11 (resumption through interop hardening) roughly 3 weeks. Total: 11-13 weeks at a sustainable pace.

Deferrals. PhaseDeferred("RFC 8446 Appendix D — Backward Compatibility") (TLS 1.2), PhaseDeferred("RFC 9001 — Using TLS to Secure QUIC") (QUIC integration), PhaseDeferred("RFC 9147 — DTLS 1.3") (datagram transport), PhaseDeferred("RFC 8446 section 4.3.2 — CertificateRequest") (mutual TLS / client certificates, Phase 12+), PhaseDeferred("RFC 6962 — Certificate Transparency") (CT log verification), PhaseDeferred("RFC 8879 — TLS Certificate Compression") (certificate compression).

2. Why Build This

Ubiquity — every HTTPS/gRPC/SMTP-STARTTLS byte on the internet crosses this protocol. Black-box risk — practitioners configure cipher suites and trust stores without a model of what breaks and why. State-machine-attack literacy — FREAK, SKIP and the SMACK family (Beurdouche et al. 2015) exist because implementations accepted transitions the spec never sanctioned. Key-schedule literacy — HKDF and Derive-Secret are simple on paper and error-prone in practice (label-string typos silently produce a working-looking but insecure key). Constant-time literacy — Lucky 13, the Bleichenbacher/ROBOT lineage, and Logjam are timing and downgrade oracles, not math breaks. Certificate-parsing literacy — DER is a classic hostile-input surface (parser differentials, the "goto fail" validation-bypass class). AEAD-nonce literacy — nonce reuse under a fixed key is a full confidentiality break for GCM and ChaCha20-Poly1305 alike. Protocol-versus-crypto separation — delegating primitives to audited crates while owning the protocol logic is itself a design skill (ADR-03).

What Mastery Looks Like

  • Can draw the full client and server state-transition tables from memory, including every alert edge — demonstrated in Phase 5 and Phase 6.
  • Can derive, by hand, every secret in the RFC 8446 key schedule for a captured handshake and match it against the RFC 8446 appendix vectors — demonstrated in Phase 1.
  • Can explain why a nonce must never repeat under a fixed AEAD key and what breaks if it does — demonstrated in Phase 3.
  • Can name the exact DER structures a hostile certificate can weaponize and defend against each — demonstrated in Phase 7 and Phase 8.
  • Can trace a downgrade attack and show exactly which field of ServerHello.random defeats it — demonstrated in Phase 9.
  • Can articulate the 0-RTT replay tradeoff well enough to decide, per-application, whether to enable it — demonstrated in Phase 10.
  • Can run and interpret an interop matrix against OpenSSL, BoringSSL and rustls and diagnose a real interop break from a packet capture — demonstrated in Phase 11.

Byte-stream transport adapter. Owns the socket or loopback pipe; performs no parsing or crypto; the untrusted-peer-input boundary begins the instant a byte crosses this adapter into the record layer.

Record layer. Fragments outbound records to the max size, reassembles inbound fragments, and is the sole owner of TrafficKeys and sequence numbers — the secret-material boundary starts here and everything below in the diagram may hold live key material.

Message parser/encoder. Bounds-checked length-prefixed decode of handshake messages from decrypted record-layer bytes; the buffer boundary — every length field is validated against remaining buffer length before a single byte is trusted.

Handshake state machine. ClientState/ServerState enums; the sole authority on which message is legal next; drives the transcript hash, key schedule, and alert subsystem.

Transcript-hash accumulator. Running hash over every handshake message in wire order; consumed by the key schedule's Derive-Secret calls and by Finished/ CertificateVerify.

Key schedule engine. Implements the HKDF-Extract/Expand-Label/Derive-Secret chain of RFC 8446 section 7.1, producing early, handshake and application secrets and, downstream, TrafficKeys.

ECDHE key-exchange module. Wraps tls-crypto's X25519/P-256 traits; produces the shared secret consumed once by the key schedule and then dropped.

Certificate parser and path validator. Reads untrusted DER from the peer; the second major untrusted-input boundary; never trusted until the full RFC 5280 chain validates to a trust anchor.

Signature verifier. Verifies RSA-PSS/ECDSA/Ed25519 signatures over the exact TLS 1.3 CertificateVerify signed-content construction (RFC 8446 section 4.4.3).

PSK/ticket store. Holds resumption secrets and session tickets; ticket keys are themselves secret material and covered by the same zeroization discipline.

Alert subsystem. The only path by which any component reports a fatal condition; every fatal alert aborts the connection — never a silent accept (I6).

Reference Implementations

  1. rustls (rustls/src/) — client/hs.rs, server/hs.rs (typed per-state handlers), msgs/handshake.rs (message codec). Lesson: sans-io typed-state design eliminates whole bug classes at compile time. Pitfall not to copy: rustls's msgs layer trusts nothing before a full round-trip through its own bounds-checked Reader — do not shortcut that with direct slicing.
  2. OpenSSL (ssl/statem/) — statem_clnt.c, statem_srvr.c. Lesson: the original explicit state-machine rewrite (post-"flag soup" era) that followed the "goto fail" and Heartbleed incidents. Pitfall: the state tables are C macros over a shared mutable connection struct — easy to lose track of what is initialized in which state; do not replicate the mutable-shared-struct pattern.
  3. BoringSSL (ssl/handshake_client.cc, ssl/handshake_server.cc) — Lesson: Google's fork simplified OpenSSL's state machine and added strict record-size and alert handling. Pitfall: BoringSSL intentionally has no stable ABI/API guarantee — do not copy its API shape as if it were a stable contract to mirror.
  4. s2n-tls (tls/) — s2n_client_hello.c, s2n_handshake_io.c. Lesson: the small-and-auditable goal, state machine driven by a table of function pointers indexed by (mode, state). Pitfall: s2n's table-of-handlers pattern hides the transition legality checks inside the handler bodies rather than in the type system — prefer the type-level encoding (ADR-08).
  5. miTLS / Project Everest — Lesson: formally verified handshake and record layer (F*-verified, compiled via HACL*). Pitfall: full formal verification is a distinct, much larger effort (§36) — do not attempt partial verification and call it equivalent assurance.
  6. Go crypto/tls (src/crypto/tls/handshake_client_tls13.go, handshake_server_tls13.go) — Lesson: clean separation of key-schedule computation (tls13/key_schedule.go) from state-machine flow. Pitfall: Go's GC makes true secret zeroization unenforceable — do not assume a "zero the buffer" pattern is sufficient without checking allocator behavior in the target language.

6. Design Principles

P1 — The handshake is an explicit state machine; every state names its exact accepted message set. Rule: ClientState/ServerState variants enumerate legal next messages; anything else is unexpected_message. Tradeoff: more enum variants than a generic "handshake in progress" flag. Operational implication: adding a message type requires touching every state's match arm, which is friction by design. Violating it recreates precisely the FREAK/SKIP vulnerability class (Beurdouche et al. 2015) — an implicitly-permissive transition accepted a weakened key-exchange message out of order.

P2 — Secret-dependent operations are constant-time or they are timing oracles. Rule: branch-on-secret-byte and table-index-by-secret-byte are banned in tls-crypto and the key schedule; the ban is testable (Phase 11 dudect-style harness). Tradeoff: constant-time code is sometimes measurably slower than a branchy fast path. Operational implication: every new comparison of secret material uses a constant-time equality primitive, never ==. Violating it is the Lucky 13 / Bleichenbacher / ROBOT lineage.

P3 — A certificate is validated before its public key is used; validation failure is a fatal alert, never a warning. Rule: PathValidator::validate must return Ok before SignatureVerifier is invoked with that certificate's key. Tradeoff: strict ordering costs a small amount of latency (chain must fully validate before signature check proceeds) versus opportunistic parallel validation. Operational implication: no code path may call the verifier on an unvalidated chain "just to check." Violating it is the 2014 Apple "goto fail" bug: a validation function returned success on an error path, silently disabling signature checking.

P4 — The transcript hash binds every handshake message; nothing is trusted before Finished verifies. Rule: the accumulator ingests every message in wire order, including messages whose content will later be authenticated; Finished's HMAC covers the full transcript. Tradeoff: none of the handshake's earlier messages (ServerHello, EncryptedExtensions, Certificate) are individually authenticated as they arrive — trust is deferred entirely to Finished. Operational implication: application code must never consume decrypted handshake data before the local Finished check passes. Violating it means a tampered message goes undetected until (if ever) something downstream trips.

P5 — An AEAD nonce is never reused under a fixed key. Rule: nonce = static IV XOR big-endian sequence number; the sequence number is monotonic and a rekey is forced before wraparound. Tradeoff: strict sequential ordering forbids out-of-order record processing at the AEAD layer. Operational implication: any redesign that reorders records (e.g. for a future QUIC integration) must carry its own nonce derivation, not reuse this one blindly. Violating it is a full confidentiality and (for GCM) forgery break — nonce reuse under a fixed key is catastrophic, not merely weak.

P6 — Downgrade must be cryptographically detectable, not merely discouraged. Rule: a TLS 1.3-capable server that negotiates a lower version writes a fixed sentinel into ServerHello.random (RFC 8446 section 4.1.3); a TLS 1.3 client checks for it unconditionally. Tradeoff: none — this is pure defense-in-depth against active network attackers, at zero performance cost. Operational implication: the check happens even on a handshake that "worked," because that is exactly the scenario a downgrade attacker engineers. Violating it recreates the DROWN/Logjam class of version-rollback attack.

P7 — Key-schedule label strings are exact-byte specification text, not free-form. Rule: every HKDF-Expand-Label call uses the literal ASCII label from RFC 8446 section 7.1 (e.g. "c hs traffic"), verified against the RFC 8448 test vectors. Tradeoff: none — deviation is simply wrong, not a design choice. Operational implication: label strings are declared as named constants, tested individually, never concatenated ad hoc. Violating it silently produces a working-looking but non-interoperable and potentially insecure derivation.

P8 — The record layer's content-type field is authenticated, not merely advisory. Rule: in TLS 1.3 the real content type travels inside the AEAD-protected TLSInnerPlaintext, stripped only after successful AEAD open. Tradeoff: the outer record header is always application_data, so passive observers cannot distinguish handshake from application traffic (a deliberate privacy property). Operational implication: no code path may branch on the outer ContentType for anything but routing to the AEAD-open step. Violating it reintroduces a metadata side-channel TLS 1.3 explicitly closed relative to TLS 1.2.

P9 — 0-RTT early data is explicitly marked replayable and never used for non-idempotent operations by default. Rule: EarlyData carries a replayable: true tag through the API; the server-side anti-replay mechanism (or its absence) is a first-class configuration, not an implementation detail. Tradeoff: 0-RTT's latency win is real but bounded to use cases tolerant of replay. Operational implication: an application must opt in per-request-type, never globally, to send data over 0-RTT. Violating it is a request-replay vulnerability with no cryptographic fix — this is a protocol-level limitation, not a bug to patch.

P10 — Every fatal condition produces exactly one alert and then the connection terminates. Rule: TlsError variants map 1:1 onto RFC 8446 section 6 alert descriptions; the state machine transitions to a terminal Closed state on any fatal alert, sent or received. Tradeoff: no "soft recovery" from a fatal alert — by design, TLS does not support mid-handshake renegotiation of a failed step. Operational implication: alert-sending code paths are exhaustively tested per state (Phase 9). Violating it risks a connection continuing in an undefined, partially-keyed state.

P11 — DER parsing is bounds-checked against the declared length before any byte is interpreted as a value. Rule: parse_tag_length validates the claimed length against remaining buffer length before any nested parse recurses. Tradeoff: strict bounds checking costs a small constant overhead per TLV versus an unchecked fast parse. Operational implication: recursive DER descent carries an explicit depth limit (T4, DoS guard) in addition to the length check. Violating it is the classic DER-parser buffer-overread/attacker-controlled-recursion attack surface.

P12 — Secret material is zeroized at the end of its epoch and never logged. Rule: every Secret/TrafficKeys/ticket-encryption-key type implements zero-on-drop; the logging subsystem's redaction list is enforced by a lint, not convention. Tradeoff: zero-on-drop has a small, constant per-drop cost. Operational implication: a debug Display/Debug impl on any secret type is a compile-time error, not a runtime mistake to catch in review. Violating it turns a debug log into a key-exfiltration channel.

P13 — A HelloRetryRequest is a fresh transcript-hash checkpoint, not a restart. Rule: per RFC 8446 section 4.1.4, the original ClientHello is replaced in the transcript by a synthetic message_hash record before HelloRetryRequest and the second ClientHello are appended. Tradeoff: this is a deliberately unusual transcript-construction rule that must be special-cased once, precisely, rather than inferred generically. Operational implication: the transcript accumulator exposes an explicit retry_reset() operation rather than allowing ad hoc reconstruction. Violating it produces a Finished value that fails to verify against a fully compliant peer despite a "correct-looking" handshake.

8.3 Record Layer Wire Format

TLSPlaintext / TLSCiphertext outer header (RFC 8446 section 5.1):

Field Size Value
ContentType type 1 byte 20=alert, 21=change_cipher_spec (compat only), 22=handshake, 23=application_data
legacy_record_version 2 bytes always 0x0303 (TLS 1.2, frozen for middlebox compatibility)
length 2 bytes length of the following opaque payload, ≤ 2^14+256
fragment / encrypted_record variable plaintext (pre-encryption) or AEAD ciphertext

TLSInnerPlaintext (the AEAD plaintext, before encryption — RFC 8446 section 5.2):

Field Size Value
content variable the real handshake/application/alert bytes
type 1 byte the real ContentType, hidden inside encryption
zeros 0+ bytes padding, length is a policy choice, not protocol-fixed

Per-record nonce construction (RFC 8446 section 5.3):

nonce = static_iv  XOR  ( 0*(iv_len - 8) || seq_number_as_64bit_big_endian )

static_iv is the per-direction IV from the key schedule; seq_number starts at 0 for the first record protected under a given traffic secret and increments by 1 per record, never resetting except on an explicit key update (RFC 8446 section 4.6.3), which derives fresh traffic secrets and resets the sequence number to 0 under the new key.

This exact chain, with concrete byte values, is matched bit-for-bit against RFC 8448 section 3's published test vectors in Phase 1's N.5 fixtures.

8.6 ECDHE Computation (X25519, named steps)

  1. Generate 32 random bytes as the private scalar; clamp per RFC 7748 section 5 (clear bits 0-2 and bit 255, set bit 254) — delegated to x25519-dalek.
  2. Compute the public key as scalar * base_point(9).
  3. Place the public key bytes in the key_share extension's KeyShareEntry.
  4. On receipt of the peer's KeyShareEntry, compute shared_secret = scalar * peer_public_key (Montgomery ladder, constant-time, delegated).
  5. Reject an all-zero output (a low-order-point attack indicator) before use.
  6. Feed shared_secret into the key schedule's Handshake Secret extract and then drop it (zeroize) — it is never needed again.

8.7 Transcript-Hash Accumulation Rule

The transcript hash is the running output of the negotiated hash function (SHA-256 or SHA-384) over the concatenation, in wire order, of every HandshakeMessage's type+length+body bytes (never the record-layer framing). On HelloRetryRequest, the first ClientHello is replaced with a synthetic single record: message_hash(1) || len(32 or 48) || Hash(first ClientHello) before HelloRetryRequest and the second ClientHello are appended (P13, RFC 8446 section 4.4.1).

8.8 Certificate Path-Validation Algorithm (named steps, RFC 5280 section 6)

  1. Build the candidate chain from the leaf certificate to a self-signed root, using Authority Key Identifier/Subject Key Identifier matching where present.
  2. For each certificate, verify the issuer's signature over the subject certificate using the algorithm named in signatureAlgorithm.
  3. Check the validity period (notBefore/notAfter) against the current time for every certificate in the chain.
  4. Check basicConstraints: every non-leaf certificate must have CA:TRUE and, if pathLenConstraint is present, the remaining chain length must not exceed it.
  5. Check keyUsage: the leaf's key usage must permit digitalSignature (or keyEncipherment for RSA key-exchange fallback, out of Phase 0 scope).
  6. Check nameConstraints on every intermediate against the leaf's subject/SAN.
  7. Check the leaf's Subject Alternative Name against the expected peer hostname.
  8. Check the root against the configured TrustAnchor set.
  9. Revocation posture (decision table below) is applied last, after structural validation succeeds.

Decision table:

Check Pass Condition Failure Alert
Signature issuer key verifies subject signature bad_certificate
Validity period now within [notBefore, notAfter] for every cert certificate_expired
Name constraints leaf name permitted by every intermediate's constraint bad_certificate
Basic constraints every non-leaf has CA:TRUE, path length respected bad_certificate
Key usage leaf permits digitalSignature bad_certificate
Revocation OCSP-stapled response fresh and Good, or policy allows unknown certificate_revoked
Trust anchor root matches configured TrustAnchor unknown_ca

8.9 Signature Schemes — Signed-Content Construction

TLS 1.3 CertificateVerify (RFC 8446 section 4.4.3) signs, not the transcript hash directly, but:

signed_content = 0x20 * 64  ||  context_string  ||  0x00  ||  Transcript-Hash
context_string  = "TLS 1.3, server CertificateVerify"   (or "client CertificateVerify")

The 64 space (0x20) bytes and null separator exist specifically to prevent cross-protocol signature-reuse attacks (a signature valid under this construction cannot be replayed as a valid signature under an unrelated protocol's format).

8.13 Malformed-Input Examples

  • ClientHello with no mutually supported key_share group -> server sends HelloRetryRequest naming a supported group (not a fatal alert — a legitimate retry path, RFC 8446 section 4.1.4).
  • A Certificate message received in WaitEncryptedExtensions (skipped EncryptedExtensions) -> unexpected_message, fatal, per I6.
  • A certificate chain whose intermediate lacks CA:TRUE -> bad_certificate per section 8.8's decision table.
  • A Finished whose HMAC does not match the locally computed value over the transcript -> bad_record_mac, fatal, connection aborts with no partial trust extended to any preceding message (P4).
  • A record that fails AEAD authentication (tag mismatch) -> bad_record_mac, fatal, no partial plaintext is ever exposed to the caller.
  • 0-RTT early data replaying a previously-seen ticket without a fresh, unused single-use marker -> server rejects the early data (I10), continues the handshake without it, does not treat this as fatal to the rest of the handshake.
  • ServerHello.random containing the TLS 1.2 or TLS 1.1 downgrade sentinel while negotiating TLS 1.3 -> illegal_parameter, fatal, per I7.

8.14 Failure-Path Example (end-to-end)

Client sends ClientHello proposing X25519 only. Server does not support X25519 (only P-256 configured). Server has no common key_share -> checks supported_groups for a mutually acceptable group (P-256 present) -> sends HelloRetryRequest naming P-256 -> client resets transcript per P13, re-sends ClientHello with a P-256 key_share -> handshake proceeds normally from §8.11 step 2. If instead no group is mutually supported at all, server sends fatal handshake_failure and the connection closes without ever entering a keyed state.

11. Core Schema & Types

Signatures only; no bodies. Untrusted-peer-input fields are marked [PEER].

// immutable, Copy, no secret material, compatibility: legacy 0x0303 frozen by RFC 8446

    send_seq: SequenceNumber, recv_seq: SequenceNumber }
// owns SECRET material; single-threaded per direction; not persisted; not Clone

// mutation: increment-only, checked-add with rekey trigger before overflow (I2); Copy

// derived per-record from static_iv XOR seq (§8.3); zeroized immediately after AEAD call; not logged

    SendEncryptedExtensions, SendCertRequestOrCert, SendCertificate, SendCertVerify,
    SendFinished, WaitClientFinished, Connected, Closed }

// mutation: append-only via update(); retry_reset() callable exactly once (I13); not persisted; not Clone

enum KeyScheduleStage { Early, Handshake, Application }

12. Phase 0 — Skeleton, Record Layer Framing & CI

12.1 Objectives

Stand up the workspace (ADR-01, ADR-27), the crate boundaries of §1's Phase-0 list, and the TlsPlaintext/TlsInnerPlaintext/TlsCiphertext framing types from §8.3 with no crypto yet — pure byte-layout parse/encode. Wire CI (ADR-26) so every later phase lands on a green build.

12.2 Detailed Implementation Steps

  1. Create the Cargo workspace with the six crates from §1's numbered list; pin the toolchain in rust-toolchain.toml (ADR-27).
  2. Implement ContentType, ProtocolVersion as specified in §11 — plain enums/newtypes, no logic.
  3. Implement TlsPlaintext/TlsCiphertext encode/decode per the byte layout in §8.3; enforce the length field against the max record size in §4 (I12-adjacent bounds discipline, applied early even though DER parsing is Phase 7).
  4. Implement a length-prefix reader utility (read_u8_vec, read_u16_vec) shared by tls-record and later tls-handshake — bounds-checked against remaining buffer per P11's general principle.
  5. Wire GitHub Actions CI: build, test, clippy -D warnings per ADR-26; stub the fuzz and interop jobs (real targets land Phase 7 and Phase 11).
  6. Write BUILD_PLAN.md and BLUEPRINT_LOG.md scaffolding referenced in §10.

12.3 Deliverable

A workspace that builds, with tls-record::TlsPlaintext/TlsCiphertext round-tripping through encode/decode on fixture byte arrays, and a green CI pipeline.

12.4 Acceptance Criteria

  • cargo build --workspace and cargo clippy --workspace -- -D warnings exit 0.
  • TlsPlaintext::decode round-trips against 5 fixture records in conformance/ covering each ContentType value.
  • A record with length exceeding 2^14+256 (§4) is rejected with record_overflow, verified by a named fixture oversized_record.bin.
  • CI pipeline (.github/workflows/ci.yml) passes on a clean clone.

12.5 Conformance Fixtures

  • conformance/malformed_messages/oversized_record.bin — length field exceeding max; expected: decode returns record_overflow.
  • conformance/malformed_messages/truncated_record.bin — length field exceeds actual buffer; expected: decode returns decode_error, not a panic.
  • conformance/malformed_messages/five_content_types.bin — one record per ContentType value; expected: each decodes with the correct discriminant.

12.6 Pitfalls

  • Treating legacy_record_version as meaningful for negotiation — it is frozen at 0x0303 by RFC 8446 section 5.1 and must never gate logic.
  • Panicking on a truncated length prefix instead of returning decode_error — this crate boundary is the first line of defense against malformed input (P11's spirit applied early).
  • Allocating a buffer sized by an attacker-controlled length field before validating it against the actual bytes available — validate length against remaining() first.
  • Forgetting that TlsInnerPlaintext's trailing content-type byte means the "content" length is length - 1 - padding_len, an off-by-one trap.

12.7 Performance Concerns

Framing is not the throughput bottleneck (§4's record-layer target is dominated by Phase 3's AEAD cost) — Phase 0 should prioritize correctness and bounds-safety over micro-optimizing the length-prefix reader; premature buffer-pooling here is deferred to Phase 11's perf hardening pass.

12.8 Edge Cases

  • Zero-length fragment (empty handshake message continuation) — must decode without error, produce an empty body.
  • Maximum-length fragment exactly at 2^14+256 — must decode, not be rejected as oversized (boundary-inclusive check).
  • A record whose ContentType byte is an unassigned value (RFC 8446 section 5.1 reserves handling of unknown types to the next layer) — Phase 0 should pass it through untyped rather than reject at this layer.

12.9 Failure Analysis

  • Manifestation: CI green but a fuzz target (added Phase 11) later finds a panic on a crafted length field. Root cause: Phase 0's bounds check validated length against a buffer that had already been over-allocated. Debug method: replay the fuzz corpus entry through tools/transcript_dump. Signal: panic backtrace pointing into TlsPlaintext::decode. Recovery: add the missing bounds check, add the corpus entry as a permanent regression fixture in conformance/.

12.10 Operational Notes

Phase 0's crates have no runtime configuration surface yet — no ticket keys, no trust anchors. BLUEPRINT_LOG.md should record the exact toolchain version pinned, since that pin is what makes the ADR-27 reproducibility guarantee meaningful later.

13. Phase 1 — HKDF and the Key Schedule

13.1 Objectives

Implement tls-core's KeySchedule engine exactly per RFC 8446 section 7.1: HKDF- Extract, HKDF-Expand-Label, and Derive-Secret, matched bit-for-bit against the RFC 8448 section 3 test vectors (I8, P7).

13.2 Detailed Implementation Steps

  1. Wrap the hkdf/hmac/sha2 crates behind tls-crypto's Hash/Kdf traits (ADR-03, ADR-06) — no hand-rolled HMAC.
  2. Implement HkdfLabel encoding exactly per RFC 8446 section 7.1: 2-byte length, length-prefixed "tls13 " || Label string, length-prefixed context.
  3. Implement HKDF-Expand-Label(secret, label, context, length) as a thin wrapper over HKDF-Expand with the HkdfLabel as info (Krawczyk 2010's HKDF scheme, applied directly).
  4. Implement Derive-Secret(secret, label, messages) = HKDF-Expand-Label(secret, label, Transcript-Hash(messages), Hash.length), taking the live TranscriptHash accumulator as input.
  5. Implement KeySchedule as a KeyScheduleStage-gated state machine (Early -> Handshake -> Application) per §8.5's derivation chain; each stage consumes the prior stage's Derive-Secret(..., "derived", "") as the next HKDF-Extract salt.
  6. Declare every label string ("c hs traffic", "s hs traffic", "c ap traffic", "s ap traffic", "exp master", "res master", "ext binder", "res binder", "derived", "key", "iv") as named constants (P7) — never inline string literals at call sites.
  7. Load RFC 8448 section 3's vectors into conformance/rfc8448_vectors/ and assert byte-exact equality at every derivation step, not just the final traffic keys.

13.3 Deliverable

tls-core::KeySchedule producing every §8.5 secret and the derived TrafficKeys (key + IV) for AES-128-GCM, matched against RFC 8448 vectors.

13.4 Acceptance Criteria

  • All RFC 8448 section 3 intermediate values (Early Secret, Handshake Secret, Master Secret, all seven traffic/exporter/resumption secrets) match published vectors byte-for-byte — the acceptance gate is the vector match itself, not a subjective "derivation looks right."
  • HkdfLabel encoding matches a hand-computed fixture for a known label/context/length triple.
  • A wrong label string (mutation-tested: flip one byte of "c hs traffic") produces a derivation that diverges from the vector — proving the test actually discriminates.

13.5 Conformance Fixtures

  • conformance/rfc8448_vectors/simple_1rtt.json — full secret schedule for RFC 8448's "Simple 1-RTT Handshake" section, all seven secrets plus traffic keys.
  • conformance/rfc8448_vectors/hello_retry_request.json — RFC 8448's HRR-flow vectors, exercising the transcript reset (P13) at the key-schedule boundary.
  • conformance/rfc8448_vectors/resumption_psk.json — RFC 8448's resumption vectors, exercising Early Secret keyed by PSK rather than all-zero IKM.

13.6 Pitfalls

  • Confusing HKDF-Expand-Label's context parameter with the raw messages — it must be the transcript hash, not the message bytes, except inside Derive-Secret itself where the hashing happens.
  • Off-by-one in HkdfLabel's length prefix (RFC 8446 section 7.1 specifies exact byte widths) — a byte-level fixture catches this, a "looks about right" review does not.
  • Reusing a Secret for both HKDF-Extract salt and as a Derive-Secret input without checking which stage's transcript boundary applies (RFC 8448's HRR vectors specifically exercise this).
  • Deriving traffic keys before the key schedule has actually reached the corresponding stage — a KeyScheduleStage guard should make this a compile-time or immediate runtime error, not a silent wrong-secret bug.

13.7 Performance Concerns

Each HKDF-Expand-Label call costs 1-3 microseconds (§4); a full handshake performs roughly a dozen such calls, so key-schedule cost is a rounding error next to ECDHE and signature verification (§34) — do not over-engineer for speed here at the cost of vector-match clarity.

13.8 Edge Cases

  • Zero-length context (e.g. Derive-Secret(..., "derived", "")) — must encode as a zero-length opaque, not omit the length prefix.
  • PSK-less handshake — Early Secret's IKM is all-zero, not absent; verify the all-zero-32-byte IKM path explicitly.
  • SHA-384 cipher suites — the same chain with a different Hash.length; verify the engine is generic over hash algorithm, not hardcoded to 32 bytes.

13.9 Failure Analysis

  • Manifestation: Finished verification fails against a real peer (rustls) in Phase 11's interop suite, despite all RFC 8448 vectors passing. Root cause: RFC 8448's vectors don't cover every cipher suite/curve combination; a subtly wrong Hash.length parameterization for SHA-384 only shows up against a live peer. Debug method: dump both sides' transcript hash at each step via tools/transcript_dump and diff. Signal: divergence appears at a specific Derive-Secret call. Recovery: add the missing cipher-suite/hash combination to the vector suite as a permanent regression fixture.

13.10 Operational Notes

The key-schedule engine has no runtime configuration — it is pure function of transcript + PSK/DHE input. Any operational issue traces to either a wrong transcript (Phase 9's domain) or a wrong DHE/PSK input (Phase 2/Phase 10's domain), not to this phase's code once vectors pass.

14. Phase 2 — X25519 ECDHE and Shared-Secret Derivation

14.1 Objectives

Implement the ECDHE key-exchange module over X25519 (RFC 7748) per §8.6's named steps, behind the tls-crypto::KeyExchange trait (ADR-03, ADR-04), feeding the key schedule built in Phase 1.

14.2 Detailed Implementation Steps

  1. Define tls-crypto::KeyExchange trait: generate() -> (PrivateKey, PublicKey), shared_secret(priv, peer_pub) -> Result<SharedSecret, TlsError>.
  2. Implement the NamedGroup::X25519 variant over x25519-dalek (Bernstein 2006's Curve25519 construction, delegated per ADR-03), including clamping per RFC 7748 section 5 — verify the wrapped crate performs clamping rather than assuming it.
  3. Implement the low-order-point / all-zero-output rejection (§8.6 step 5) — reject a shared secret of all zero bytes before it reaches the key schedule (P2's constant-time discipline applies to this check: compare in constant time, don't short-circuit on the first nonzero byte in a way that leaks which byte).
  4. Wire KeyShareEntry construction/parsing into the ClientHello/ServerHello key_share extension codec (builds on Phase 0's length-prefix utilities).
  5. Feed the computed SharedSecret into KeySchedule's Handshake Secret extract (Phase 1's engine) and zeroize the SharedSecret immediately after (I5, P12).
  6. Add the NamedGroup::Secp256r1 (P-256) variant over the p256 crate as the second mandatory group (ADR-04), sharing the same trait boundary.

14.3 Deliverable

tls-crypto::KeyExchange implementations for X25519 and P-256, integration-tested by computing a shared secret between two locally generated key pairs and feeding it through Phase 1's key schedule to reproduce an RFC 8448 vector's Handshake Secret.

14.4 Acceptance Criteria

  • X25519 shared-secret computation matches RFC 7748 section 6.1's test vectors byte-for-byte.
  • P-256 ECDH matches a published SP 800-56A / NIST CAVP-style test vector.
  • The all-zero-output rejection path is exercised by a crafted low-order public key fixture (conformance/malformed_messages/low_order_point.bin) and produces a fatal illegal_parameter, not a silent zero secret.
  • A constant-time verification pass (Phase 11's dudect harness, run early here as a smoke check) shows no measurable timing correlation between the private scalar and computation time, within the harness's statistical threshold.

14.5 Conformance Fixtures

  • conformance/rfc8448_vectors/x25519_shared_secret.json — RFC 7748 section 6.1 vectors.
  • conformance/malformed_messages/low_order_point.bin — a known X25519 low-order point as peer public key; expected: illegal_parameter, not a zero-valued shared secret silently accepted.
  • conformance/malformed_messages/wrong_length_key_share.bin — a key_share public value of the wrong byte length for its named group; expected: decode_error.

14.6 Pitfalls

  • Trusting the wrapped crate's default behavior without verifying it rejects low-order points — some X25519 implementations silently accept them, producing a predictable shared secret.
  • Not zeroizing the raw scalar and shared secret immediately after use — they are needed exactly once (§8.6 step 6) and are pure liability afterward (I5).
  • Mixing up which side's public key goes into shared_secret() — a same-side bug (computing my_priv * my_pub instead of my_priv * peer_pub) produces a plausible-looking but wrong secret that only surfaces as a Finished-verification failure three phases later.

14.7 Performance Concerns

X25519 costs 40-60 microseconds, P-256 80-120 microseconds (§4) — dominant contributors to full-handshake CPU cost (§34) but each computed exactly once per handshake, so no caching or precomputation is warranted beyond what the underlying crate already does.

14.8 Edge Cases

  • Peer offers a key_share for a NamedGroup this implementation does not support — must fall through to the HelloRetryRequest path (§8.14), not error immediately if an alternative mutually-supported group exists in supported_groups.
  • Peer's key_share public value has the correct length but is otherwise an invalid curve point (not necessarily low-order) — X25519's design (Bernstein 2006) makes all 32-byte strings valid inputs to the function, so this specific edge case is X25519-immune by construction, unlike P-256 where point-validation matters more.

14.9 Failure Analysis

  • Manifestation: handshake completes locally in fixture tests but Phase 11's interop run against BoringSSL fails Finished verification. Root cause: P-256 point de-compression or validation mismatch between p256 crate's conventions and BoringSSL's. Debug method: capture the exact key_share bytes exchanged via tools/transcript_dump and compare against a bssl-generated reference. Signal: shared secret diverges despite identical input bytes. Recovery: align point encoding convention (compressed vs uncompressed) with RFC 8446 section 4.2.8's requirement.

14.10 Operational Notes

No runtime configuration beyond which NamedGroups are enabled/offered — a deployment choosing to disable P-256 and run X25519-only reduces supported_groups accordingly; document this as a compatibility tradeoff (some legacy peers require P-256).

15. Phase 3 — AEAD Record Protection

15.1 Objectives

Implement the record layer's AEAD protect/unprotect path (tls-record::seal/open) over AES-128-GCM, AES-256-GCM and ChaCha20-Poly1305, with the exact per-record nonce construction from §8.3 (I2, P5).

15.2 Detailed Implementation Steps

  1. Define tls-crypto::Aead trait: seal(key, nonce, aad, plaintext) -> ciphertext, open(key, nonce, aad, ciphertext) -> Result<plaintext, TlsError>, over the aes-gcm and chacha20poly1305 crates (ADR-03, ADR-05).
  2. Implement nonce construction exactly per §8.3's display equation: XOR the per-direction static_iv with the big-endian 64-bit sequence number, left-padded with zeros to the IV length (RFC 8446 section 5.3).
  3. Implement RecordLayer::seal: build TLSInnerPlaintext (content + real type + optional padding), AEAD-seal with the outer record header as additional authenticated data (AAD) per RFC 8446 section 5.2, increment send_seq (I2).
  4. Implement RecordLayer::open: AEAD-open, strip the trailing real-type byte (and any zero padding) only after successful authentication (I9) — never expose plaintext on authentication failure.
  5. Implement the rekey-before-wraparound guard (I2): when send_seq/recv_seq approaches 2^64 - 1, trigger a KeyUpdate (RFC 8446 section 4.6.3) before overflow is possible.
  6. Wire AAD construction (the 5-byte outer record header: type, version, length) into both seal and open, matching RFC 8446 section 5.2's additional_data definition.

15.3 Deliverable

tls-record::RecordLayer sealing and opening records under all three AEAD algorithms, with a fixture suite proving nonce correctness and authentication-failure handling.

15.4 Acceptance Criteria

  • Seal-then-open round-trips correctly for AES-128-GCM, AES-256-GCM and ChaCha20-Poly1305 against RFC 5116/RFC 8439-style test vectors.
  • A record decrypted with a deliberately wrong key produces bad_record_mac, not a panic and not garbage plaintext exposed to the caller.
  • A fixture asserting that two sequential records under the same key produce different nonces (sequence number 0 vs 1) and that the ciphertexts differ even for identical plaintext — proving nonce derivation is live, not accidentally frozen at zero.
  • The rekey-before-wraparound guard fires in a fixture that artificially sets send_seq near 2^64 - 1 (not a real 2^64-record test, which is infeasible to run, but a boundary-condition unit test of the trigger logic).

15.5 Conformance Fixtures

  • conformance/rfc8448_vectors/aes128gcm_record.json — a captured RFC 8448 handshake's first application-data record, exact ciphertext bytes.
  • conformance/malformed_messages/bad_record_mac.bin — a record with a flipped ciphertext byte; expected: open returns bad_record_mac.
  • conformance/malformed_messages/replayed_record.bin — a record with a sequence number that has already been consumed; expected: rejected (implementation detail: the sequence counter itself prevents constructing this legitimately, so this fixture exercises the defensive check on the receive path if seq is ever externally supplied).

15.6 Pitfalls

  • Constructing the nonce from the sequence number in host byte order instead of big-endian — produces a plausible-looking but wrong nonce that fails interop silently until Phase 11.
  • Exposing partially-decrypted plaintext before the AEAD tag check completes — some streaming AEAD APIs decrypt-then-verify; this implementation must verify-then-expose, never the reverse (I9's authenticated-before-trusted principle).
  • Forgetting the AAD (the 5-byte outer header) in either seal or open — omission is a spec deviation that silently produces non-interoperable ciphertext.
  • Treating ChaCha20-Poly1305's 96-bit nonce and AES-GCM's 96-bit nonce as identical in construction without checking each cipher's actual IV-length requirement from its own RFC (8439 vs 5288/5289) — they happen to match at 12 bytes in TLS 1.3's usage, but the code should not hardcode this coincidence without a citation-backed comment.

15.7 Performance Concerns

AES-128-GCM with hardware AES-NI reaches 2,000-4,000 MB/s/core; ChaCha20-Poly1305 without AES-NI reaches 700-1,200 MB/s/core (§4) — cipher-suite negotiation should prefer AES-GCM only when hardware acceleration is actually present (a runtime CPU feature check), otherwise ChaCha20-Poly1305 is both faster and side-channel-safer on software-only implementations (Bernstein's original ChaCha/Poly1305 design rationale).

15.8 Edge Cases

  • Zero-length application-data record (a legal but unusual record) — must seal/open correctly, producing a minimal TLSInnerPlaintext of just the real-type byte.
  • Maximum-length record at exactly 2^14 plaintext bytes before AEAD expansion — must not exceed 2^14+256 ciphertext bound (§4) after the AEAD tag and any padding are added.
  • A KeyUpdate message arriving mid-stream — must correctly derive fresh traffic secrets and reset the sequence number to 0 under the new key (RFC 8446 section 4.6.3), while the old key remains valid for any already-in-flight records until the update is acknowledged.

15.9 Failure Analysis

  • Manifestation: intermittent bad_record_mac under high-throughput load testing only, not in single-record fixture tests. Root cause: a race in sequence-number increment when the record layer is (incorrectly) shared across threads without synchronization. Debug method: reproduce under cargo test -- --test-threads=1 to confirm the race, then add a targeted concurrent-access regression test. Signal: failure rate correlates with thread count. Recovery: document RecordLayer as !Sync explicitly (or add proper synchronization) and add the constraint to §11's type annotations retroactively.

15.10 Operational Notes

Cipher-suite selection is a deployment-time policy choice (which AEAD algorithms are offered/accepted) — document the AES-NI-availability heuristic from N.7 as an operational runbook note so operators understand why the same binary might prefer different suites on different hardware.

16. Phase 4 — Handshake Message Parsing and Encoding

16.1 Objectives

Implement tls-handshake's message codec: typed encode/decode for every §8.4 message and extension, bounds-checked per P11, feeding the transcript hash (I3) as messages are consumed.

16.2 Detailed Implementation Steps

  1. Implement the generic HandshakeMessage envelope (1-byte type, 3-byte length, body) over Phase 0's length-prefix utilities.
  2. Implement ClientHello/ServerHello encode/decode per §8.4's byte layout, including the legacy_compression_methods fixed-value check (must be [0x00], RFC 8446 section 4.1.2 — a nonzero value is illegal_parameter).
  3. Implement the Extension generic envelope, then typed decoders for supported_versions, supported_groups, key_share, signature_algorithms, pre_shared_key, psk_key_exchange_modes (§8.4), each validating its own internal length prefixes against the outer extension length (P11).
  4. Implement EncryptedExtensions, Certificate (certificate_list container, entries opaque DER at this phase — parsed in Phase 7), CertificateVerify, Finished message bodies.
  5. Wire every decode call to push the raw message bytes into the live TranscriptHash accumulator (I3) before or as part of dispatch — never after downstream processing, to avoid a code path that consumes a message without recording it.
  6. Implement the binder computation/verification for pre_shared_key (RFC 8446 section 4.2.11): an HMAC over the transcript up to but not including the binder list itself — a genuinely tricky partial-transcript case, tested explicitly.

16.3 Deliverable

A complete encode/decode round-trip for every Phase-0-scope message type, integrated with the transcript-hash accumulator.

16.4 Acceptance Criteria

  • Every message type round-trips encode -> decode -> encode to byte-identical output against 12+ named fixtures (one per message type plus HRR and NewSessionTicket variants).
  • The legacy_compression_methods nonzero-value fixture produces illegal_parameter.
  • The PSK binder fixture (conformance/rfc8448_vectors/resumption_psk.json, reused from Phase 1) verifies correctly when computed over the correct partial transcript and fails when computed over the full transcript by mistake — proving the test actually discriminates the subtle partial-transcript rule.
  • Every decoder rejects a length field exceeding remaining buffer with decode_error, verified by a fuzz-derived corpus of 20+ truncated fixtures.

16.5 Conformance Fixtures

  • conformance/malformed_messages/{client_hello,server_hello,encrypted_extensions, certificate,certificate_verify,finished,new_session_ticket,hello_retry_request}.bin — one well-formed fixture per type for round-trip testing.
  • conformance/malformed_messages/nonzero_compression.bin — legacy_compression_methods != [0x00]; expected illegal_parameter.
  • conformance/malformed_messages/binder_over_full_transcript.bin — a PSK binder computed incorrectly over the full transcript instead of the partial one; expected: binder verification fails.

16.6 Pitfalls

  • Computing the PSK binder over the wrong transcript slice (RFC 8446 section 4.2.11 is explicit that the binder covers ClientHello up to but excluding the binder list itself) — an easy one-message-too-many bug.
  • Parsing extension_data generically before dispatching on extension_type, then re-parsing typed data from an already-consumed cursor — prefer decode functions that take an explicit sub-slice per extension, bounded by the extension's own length.
  • Validating an extension's outer length but not cross-checking it against the sum of its inner vector lengths — a mismatch here is a classic parser-differential bug (a decoder might silently ignore trailing garbage another implementation rejects).

16.7 Performance Concerns

Message parsing is not on §4's throughput-critical path (that is the record layer, Phase 3) but is on the latency-critical path for handshake round-trip time — avoid unnecessary allocation/copying in the decode path (e.g. borrow sub-slices rather than copying into new Vecs where the resulting type's lifetime allows it).

16.8 Edge Cases

  • A ClientHello with zero extensions (legal in principle, though RFC 8446 section 9.2 mandates several for TLS 1.3 compliance — reject as missing_extension if supported_versions is absent).
  • An extension appearing twice (e.g. two key_share extensions) — RFC 8446 forbids duplicate extensions; must reject with illegal_parameter, not silently take the last one.
  • A Certificate message with zero entries in certificate_list — legal only in a PSK-only handshake where no certificate is sent at all (the message itself is skipped, not sent empty) — an empty list on a non-PSK handshake is decode_error.

16.9 Failure Analysis

  • Manifestation: interop failure against OpenSSL specifically on the pre_shared_key extension only. Root cause: OpenSSL and this implementation disagree on binder-computation transcript boundary due to an off-by-one in which bytes count as "up to but excluding the binder list." Debug method: dump both sides' exact byte ranges fed to the binder HMAC via tools/transcript_dump. Signal: binder value mismatch despite identical ClientHello bytes on the wire. Recovery: re-derive the exact boundary from RFC 8446 section 4.2.11's pseudocode and add a permanent fixture at that exact boundary.

16.10 Operational Notes

The message codec has no runtime configuration; any parsing issue is a code bug, not an operator misconfiguration — the runbook for this class of failure is docs/runbooks/interop-break-diagnosis.md.

17. Phase 5 — Client Handshake State Machine to Finished

17.1 Objectives

Implement ClientState's full transition table (§8.1) as an exhaustive, typestate- encoded state machine (ADR-08, P1), driving Phase 1's key schedule, Phase 2's ECDHE, and Phase 4's message codec to a verified Connected state.

17.2 Detailed Implementation Steps

  1. Implement ClientState::Start -> send ClientHello with key_share (Phase 2), supported_versions, signature_algorithms, supported_groups.
  2. Implement the WaitServerHello transition, branching on whether the received message is a full ServerHello or a HelloRetryRequest (same wire format, distinguished by the random field's fixed HRR value, RFC 8446 section 4.1.4) — the HRR path resets the transcript (P13, TranscriptHash::retry_reset()) and loops back to Start with a second ClientHello carrying the server's requested group.
  3. Immediately after a full ServerHello, compute the ECDHE shared secret (Phase 2) and derive the Handshake Secret and both handshake traffic secrets (Phase 1), rekeying the record layer's receive side before parsing EncryptedExtensions (which arrives encrypted).
  4. Implement WaitEncryptedExtensions -> WaitCertOrCertRequest -> WaitCertificate/skip -> WaitCertVerify: parse but do not yet trust Certificate (path validation is Phase 8; Phase 5 stores the chain and defers validation calls behind a trait so Phase 8 can plug in without restructuring the state machine).
  5. Implement WaitCertVerify -> WaitFinished: verify CertificateVerify's signature over the §8.9 signed-content construction (stub SignatureVerifier calls Phase 8's real implementation; Phase 5 tests against a fixed test key so it need not block on Phase 8 landing).
  6. Implement WaitFinished: verify the server Finished HMAC against the transcript (I3, P4); on success derive the Master Secret and application traffic secrets (Phase 1); on failure, fatal bad_record_mac, transition to Closed.
  7. Implement SendFinished -> Connected: compute and send the client Finished, rekey the send side to application traffic, transition to Connected.
  8. Implement the mandatory downgrade-sentinel check (I7, P6) unconditionally in WaitServerHello, independent of whether the rest of the handshake "looks fine."

17.3 Deliverable

A client-side state machine that completes a full 1-RTT handshake to Connected against a fixture server transcript (RFC 8448) and correctly rejects every §8.13 malformed-input example.

17.4 Acceptance Criteria

  • Client reaches Connected and derives application traffic secrets matching RFC 8448 section 3's vectors, replaying a captured server transcript through the state machine (not yet a live peer — that is Phase 11).
  • Every out-of-order message fixture (Certificate before EncryptedExtensions, Finished before CertificateVerify) produces unexpected_message (I6) from every applicable state, not just the "obvious" ones.
  • The HRR fixture (conformance/rfc8448_vectors/hello_retry_request.json) completes to Connected with a correctly-reset transcript (I13).
  • The downgrade-sentinel fixture produces illegal_parameter regardless of whether the rest of the handshake would otherwise succeed.

17.5 Conformance Fixtures

  • conformance/rfc8448_vectors/simple_1rtt.json — drives the client to Connected.
  • conformance/rfc8448_vectors/hello_retry_request.json — drives the HRR retry path.
  • conformance/malformed_messages/downgrade_sentinel.bin — a ServerHello.random with the TLS 1.2 downgrade sentinel present; expected illegal_parameter.
  • conformance/malformed_messages/out_of_order_*.bin — one fixture per illegal transition in §8.1's table.

17.6 Pitfalls

  • Checking the downgrade sentinel only in an error-handling branch instead of unconditionally — reproduces exactly the class of bug the sentinel exists to catch (an attacker who successfully forces version negotiation "looks like" the happy path).
  • Trusting Certificate/CertificateVerify content before Finished verifies (P4) — Phase 5 must structurally defer any use of the certificate's authority (e.g. exposing the peer identity to the application) until after Connected.
  • Handling HelloRetryRequest as "just another ServerHello" without the transcript special-case (P13) — produces a Finished value that fails against any fully compliant peer.

17.7 Performance Concerns

The client state machine's cost is dominated by Phase 2's ECDHE and Phase 8's signature verification (deferred here to a stub) — the state-machine dispatch itself (a match on an enum) is sub-microsecond and not a target for optimization.

17.8 Edge Cases

  • Server sends CertificateRequest (mutual TLS) — Phase 0 scope has no client certificate to present; the client must still parse and correctly skip this optional message per §8.1's table, deferring actual client-cert support (PhaseDeferred("RFC 8446 section 4.3.2 — CertificateRequest")).
  • Server omits Certificate/CertificateVerify entirely (PSK-only mode) — the state machine must route WaitCertOrCertRequest directly to WaitFinished when psk_key_exchange_modes negotiation indicates PSK-only (this edge case's full wiring completes in Phase 10).

17.9 Failure Analysis

  • Manifestation: client hangs in WaitCertVerify against a real peer that sent a valid CertificateVerify in Phase 11. Root cause: Phase 5's stub SignatureVerifier accepts a fixed test key's signature format only, incompatible with a live peer's actual key. Debug method: confirm via tools/transcript_dump that the message arrived and was well-formed; the bug is isolated to the deferred Phase 8 dependency, not the state machine itself. Recovery: this is expected and resolved when Phase 8 lands — document the dependency explicitly in BUILD_PLAN.md so it is not mistaken for a Phase 5 regression.

17.10 Operational Notes

No runtime configuration; the state machine's only external dependency at this phase is the (stubbed) certificate verifier, tracked as a known gap until Phase 8.

18. Phase 6 — Server Handshake State Machine

18.1 Objectives

Implement ServerState's full transition table (§8.2), mirroring Phase 5's discipline on the server side, including parameter selection and the HelloRetryRequest-issuing path.

18.2 Detailed Implementation Steps

  1. Implement ServerState::Start -> ChooseParameters: parse ClientHello, select a mutually supported cipher suite, group, and signature scheme; if no offered key_share matches a supported group but supported_groups contains one, transition to SendHelloRetryRequest; if no group is mutually acceptable at all, fatal handshake_failure.
  2. Implement SendServerHello: construct ServerHello with the selected key_share, compute the ECDHE shared secret (Phase 2), derive the Handshake Secret and both handshake traffic secrets (Phase 1), rekey the record layer before sending EncryptedExtensions (which is itself encrypted).
  3. Implement SendEncryptedExtensions -> SendCertRequestOrCert -> SendCertificate -> SendCertVerify: sign the transcript per §8.9 (stub-verified against Phase 8's real signer once it lands, same staged dependency as Phase 5).
  4. Implement SendFinished: compute the server Finished HMAC over the transcript (I3), send it, derive the Master Secret and application traffic secrets, rekey the send side to application traffic.
  5. Implement WaitClientFinished: verify the client Finished; on success transition to Connected; on failure fatal bad_record_mac.
  6. Implement the HelloRetryRequest issuance path fully: construct HRR with the key_share extension naming the server's chosen group, apply the transcript special-case (P13) on the server side symmetrically to Phase 5's client-side handling, and enforce that a second mismatched ClientHello after HRR is fatal illegal_parameter (only one retry permitted, I13).

18.3 Deliverable

A server-side state machine that completes a full 1-RTT handshake (including the HRR branch) to Connected against fixture client transcripts.

18.4 Acceptance Criteria

  • Server reaches Connected and derives secrets matching RFC 8448 vectors when driven by the vector suite's client-side messages.
  • The HRR-issuance path is exercised end-to-end: a ClientHello offering only an unsupported group triggers HRR naming a supported one, and a correctly-formed second ClientHello completes the handshake.
  • A second HRR attempt (malformed test harness feeding two mismatches in a row) produces fatal illegal_parameter (I13), not an infinite retry loop.
  • handshake_failure fires when zero mutually acceptable groups exist, verified by a named fixture.

18.5 Conformance Fixtures

  • conformance/rfc8448_vectors/simple_1rtt.json — server-side replay to Connected.
  • conformance/malformed_messages/no_common_group.bin — ClientHello offering zero mutually supported groups; expected handshake_failure.
  • conformance/malformed_messages/double_hrr_mismatch.bin — a second ClientHello still not matching the HRR's requested group; expected illegal_parameter.

18.6 Pitfalls

  • Deriving the handshake traffic secrets before finishing parameter selection (cipher suite must be locked in before the hash function used by the key schedule is known).
  • Allowing an unbounded HRR retry loop instead of enforcing the single-retry limit (I13) — a naive implementation might treat each mismatch as "try again," which is both a spec violation and a DoS amplification vector (T-adjacent to §24).
  • Sending EncryptedExtensions before the handshake traffic secrets are actually installed on the send side — an ordering bug that produces ciphertext under the wrong (or absent) key.

18.7 Performance Concerns

Server-side full-handshake cost is dominated by the same ECDHE + signature-generation pair as the client's verification cost (§34) — signature generation is typically cheaper than verification for ECDSA (asymmetric cost), a detail worth confirming against the specific curve/algorithm chosen in benchmarking (Phase 11).

18.8 Edge Cases

  • Client offers multiple key_share entries across several groups — server must select according to its own preference order among mutually supported groups, not simply the client's first offered one (a negotiation-policy choice, document as configurable).
  • Client's ClientHello is itself a second-attempt after HRR but the connection state tracking the first attempt was lost (e.g. server restart) — must be treated as a fresh Start (stateless server design implication), not an error, since HRR itself is designed to be resumable from a stateless server per RFC 8446 section 4.1.4.

18.9 Failure Analysis

  • Manifestation: load-test reveals the server's HRR path causes elevated CPU under a flood of ClientHellos each offering an unsupported group. Root cause: HRR issuance still performs full parameter-selection logic per request with no rate limiting. Debug method: profile under benchmarks/handshake_throughput.rs with an adversarial-group-mix workload. Signal: CPU-per-handshake for HRR-triggering requests significantly exceeds the non-HRR baseline. Recovery: this is a DoS surface tracked as T10 in §24; mitigation (rate limiting) is a Phase 11 hardening item, not a Phase 6 correctness bug.

18.10 Operational Notes

Group/cipher-suite preference order is server-operator configuration; document the default preference order (X25519 over P-256, AES-128-GCM over ChaCha20-Poly1305 when AES-NI is detected per Phase 3 N.7) in docs/runbooks/.

19. Phase 7 — X.509 Certificate Parsing (Hardened DER)

19.1 Objectives

Implement tls-cert's hardened ASN.1/DER reader and the X.509 certificate model (RFC 5280), the first component to consume fully untrusted, adversarial byte input end-to-end (P11, ADR-10).

19.2 Detailed Implementation Steps

  1. Implement parse_tag_length(buf) -> Result<(Tag, Length, &[u8]), TlsError>: read the DER tag byte, then the length (short-form or long-form per X.690), validating the claimed length against buf.len() before returning — no nested parse may proceed on an unvalidated length (P11).
  2. Implement an explicit recursion-depth counter threaded through every nested parse call (parse_sequence, parse_set); reject with decode_error past a fixed maximum depth (T4's DoS guard) — this is the direct mitigation for attacker-controlled-recursion DER attacks.
  3. Implement parse_integer, parse_bitstring, parse_oid, parse_utf8string, parse_utctime/parse_generalizedtime as minimal, X.509-scoped DER primitives — not a general BER/CER-tolerant codec (ADR-10's rationale: smaller grammar, smaller attack surface).
  4. Implement Certificate::from_der(bytes) -> Result<X509Fields, TlsError> extracting: serialNumber, signatureAlgorithm, issuer, validity (notBefore/notAfter), subject, subjectPublicKeyInfo, extensions (basicConstraints, keyUsage, subjectAltName, nameConstraints, authorityKeyIdentifier, subjectKeyIdentifier).
  5. Implement Certificate::subject_public_key() -> Result<SubjectPublicKey, TlsError> dispatching on the subjectPublicKeyInfo algorithm OID to RSA/ECDSA/Ed25519 key forms, feeding Phase 8's signature verifier.
  6. Enforce §4's max-chain-length and max-chain-byte-size limits (T10) at the CertChain construction boundary, before any per-certificate parsing begins.

19.3 Deliverable

tls-cert's DER reader and X509Fields extraction, hardened against the adversarial certificate corpus, with zero crashes under the Phase 11 fuzz gate (a gate whose initial run starts in this phase and continues through Phase 11).

19.4 Acceptance Criteria

  • Parses a corpus of 20+ real-world certificates (self-signed test fixtures covering RSA-2048, RSA-3072, ECDSA-P256, Ed25519 subject keys) without error.
  • Rejects every adversarial fixture in conformance/adversarial_certs/ with decode_error or bad_certificate, never a panic — this is a zero-crash gate, not a "handles most cases" gate.
  • A 24-hour libFuzzer smoke run (full campaign is Phase 11) on fuzz_targets/ der_parser.rs finds zero crashes and zero ASan/UBSan findings.
  • The recursion-depth guard rejects a crafted deeply-nested SEQUENCE fixture at the configured maximum, verified by a named fixture, not merely "eventually stack overflows are prevented in practice."

19.5 Conformance Fixtures

  • conformance/adversarial_certs/deeply_nested_sequence.der — recursion-depth attack; expected decode_error.
  • conformance/adversarial_certs/oversized_length_claim.der — a length field claiming more bytes than the buffer contains; expected decode_error, not an overread.
  • conformance/adversarial_certs/indefinite_length_ber.der — BER indefinite-length encoding (invalid in strict DER); expected decode_error (DER, not BER, is the accepted grammar — ADR-10).
  • conformance/adversarial_certs/oversized_chain.der — a chain exceeding §4's max length/size; expected rejection before per-certificate parsing begins (T10).
  • conformance/adversarial_certs/valid_rsa_ecdsa_ed25519.der — three well-formed fixtures, one per supported key algorithm, for the positive-path test.

19.6 Pitfalls

  • Allocating a buffer sized by a claimed DER length before validating it against actual remaining bytes — the canonical DER-parser overread bug (P11).
  • Accepting BER's indefinite-length form when only strict DER is specified for X.509 (RFC 5280 requires DER, not general BER) — a parser that is "helpfully" lenient here widens the attack surface ADR-10 exists to narrow.
  • Treating a certificate's extensions as optional-and-ignorable when basicConstraints/keyUsage absence has security meaning (RFC 5280 section 4.2.1.9: absence of basicConstraints on a CA certificate is itself often treated as non-CA) — an omission bug here is a validation-bypass precursor to Phase 8.
  • No recursion-depth limit, relying on "DER doesn't nest that deep in practice" — this is exactly the informal assumption a fuzzer exists to falsify.

19.7 Performance Concerns

Parsing a typical 3-certificate chain costs low tens of microseconds — negligible next to signature verification (§4, §34); do not trade parsing rigor (bounds checks, recursion limits) for parsing speed here.

19.8 Edge Cases

  • A certificate with a critical extension this parser does not recognize — RFC 5280 section 4.2 requires rejecting the certificate if a critical extension is unrecognized; a non-critical unrecognized extension may be skipped.
  • Multiple subjectAltName entries of mixed types (DNS name, IP address) — the parser must extract all DNS-name entries for Phase 8's hostname check, not just the first.
  • A certificate using an unsupported signature algorithm OID entirely — must produce unsupported_certificate, not attempt a best-effort parse of the signature bytes.

19.9 Failure Analysis

  • Manifestation: the 24-hour fuzz smoke run finds a crash on a length field computed as length * 2 internally overflowing a 32-bit accumulator on certain platforms. Root cause: the length-accumulation arithmetic used an unchecked multiply/add instead of Rust's checked arithmetic. Debug method: minimize the crashing input via cargo fuzz tmin, replay through tools/transcript_dump. Signal: panic message naming an arithmetic overflow location. Recovery: switch to checked_mul/checked_add throughout the length-parsing path, add the minimized crash as a permanent fuzz-corpus regression fixture.

19.10 Operational Notes

No runtime configuration beyond max_chain_length/max_chain_bytes (§4, T10), exposed as constructor parameters on PathValidator so operators can tighten limits in high-threat deployments.

20. Phase 8 — Certificate Path Validation and Signature Verification

20.1 Objectives

Implement PathValidator per §8.8's named steps and decision table (RFC 5280 section 6), and SignatureVerifier for RSA-PSS/ECDSA/Ed25519 over the exact §8.9 signed-content construction, replacing Phase 5/6's stubs (I4, P3).

20.2 Detailed Implementation Steps

  1. Implement chain building: given a leaf-first CertChain (Phase 7), match each certificate's issuer against the next certificate's subject (and authorityKeyIdentifier/subjectKeyIdentifier where present) to confirm ordering, rejecting a chain that does not form a single linear path.
  2. Implement signature verification between chain certificates (each certificate's signature verified by the next one's public key), using SignatureVerifier (built in step 5 below) — this is distinct from the CertificateVerify signature over the transcript.
  3. Implement the validity-period check across every certificate in the chain against wall-clock time at validation, per §8.8 step 3.
  4. Implement basicConstraints/pathLenConstraint and keyUsage checks per §8.8 steps 4-5, and nameConstraints/hostname-matching per steps 6-7, using Phase 7's extracted subjectAltName entries.
  5. Implement SignatureVerifier over tls-crypto's wrapped ring (RSA-PSS per RFC 8017), p256/ecdsa (ECDSA per FIPS 186-5), and ed25519-dalek (Ed25519 per RFC 8032), verifying over the exact §8.9 signed_content construction (the 64 space-bytes, context string, null separator, transcript hash) — never a bare transcript-hash signature.
  6. Wire PathValidator::validate as a hard gate before any SignatureVerifier::verify call in Phase 5/6's WaitCertVerify/SendCertVerify states (I4, P3) — the ordering itself, not just the individual checks, is the acceptance criterion (this is precisely the "goto fail" lesson).
  7. Implement OCSP-staple checking (ADR-12): if a stapled OCSP response is present, verify its signature and freshness and honor a revoked status as fatal certificate_revoked; if absent, soft-fail per ADR-12's policy (log + proceed).

20.3 Deliverable

A working PathValidator and SignatureVerifier integrated into both client and server state machines, replacing the Phase 5/6 stubs, tested against the full adversarial certificate corpus from Phase 7 plus new chain-level fixtures.

20.4 Acceptance Criteria

  • A valid 3-certificate chain validates successfully; every single-field mutation (wrong signature, expired validity, missing CA:TRUE, wrong keyUsage, name-constraint violation, untrusted root) is individually rejected with the correct alert from §8.8's decision table — not merely "some mutation is caught."
  • RSA-PSS, ECDSA-P256 and Ed25519 CertificateVerify signatures verify correctly against fixtures signed by a real reference implementation (OpenSSL-generated).
  • The "goto fail" regression test asserts SignatureVerifier::verify is never called when PathValidator::validate returned an error in the same code path (a structural, call-order test, not just a behavioral one).
  • Constant-time verification pass (Phase 11) shows no timing correlation for RSA-PSS verification across valid/invalid signature inputs.

20.5 Conformance Fixtures

  • conformance/adversarial_certs/valid_chain_leaf_intermediate_root.der — the positive-path fixture, three real certificates.
  • conformance/adversarial_certs/chain_wrong_signature.der, chain_expired.der, chain_missing_ca_true.der, chain_bad_key_usage.der, chain_name_constraint_violation.der, chain_untrusted_root.der — one mutation per decision-table row (§8.8), each expected to fail with its specific named alert.
  • conformance/rfc8448_vectors/certificate_verify_{rsapss,ecdsa,ed25519}.json — signature fixtures per algorithm.

20.6 Pitfalls

  • The "goto fail" class itself: an early-return bug where a validation step's error path falls through to a success path — mitigated not just by "write correct code" but by the structural test in N.4.
  • Verifying CertificateVerify over the raw transcript hash instead of the §8.9 wrapped construction — verifies against a non-compliant peer but fails against every RFC-8446-compliant one, a silent interop trap.
  • Checking basicConstraints presence but not its CA:TRUE value (an intermediate with CA:FALSE must still be rejected as a non-CA acting as an issuer).
  • Treating OCSP-staple absence as equivalent to staple-says-good — ADR-12's soft-fail is a deliberate policy choice, distinguishable in telemetry from an actual "good" response.

20.7 Performance Concerns

Signature verification (60-150 microseconds, §4) and chain validation dominate full-handshake CPU alongside ECDHE (§34) — precisely why resumption (Phase 10) exists as the primary real-world optimization; never "speed up" verification by skipping a decision-table check.

20.8 Edge Cases

  • A chain where the leaf certificate is also directly a configured trust anchor (self-signed trusted leaf) — must validate without requiring a separate root certificate in the presented chain.
  • A chain with an intermediate that has expired but whose signature over the leaf was made while still valid — RFC 5280's validity check is evaluated at validation time (now), not at signing time, so this must still fail certificate_expired.
  • Multiple candidate paths to different trust anchors from an ambiguous chain (cross- signed intermediates) — Phase 0 scope picks the first structurally valid path found and does not implement full RFC 4158-style path-building search; document this as a scoped limitation, not silently mishandle it.

20.9 Failure Analysis

  • Manifestation: a real-world certificate chain captured in Phase 11 interop testing fails validation that browsers accept. Root cause: an overly strict hostname comparison rejects a matching SAN entry (RFC 5280 mandates case-insensitive DNS name comparison). Debug method: diff the decision-table trace against OpenSSL's verify output for the identical chain. Signal: rejection isolated to the name-constraints step. Recovery: fix the comparison to be case-insensitive per RFC 5280 section 7.2, add the chain as a regression fixture.

20.10 Operational Notes

Trust-anchor configuration (Vec<TrustAnchor>) is operator-supplied, not bundled — see docs/runbooks/certificate-expiry-response.md for the runbook covering a trust-anchor or leaf-certificate nearing expiry in a live deployment.

21. Phase 9 — Transcript Hash, Downgrade Protection and Alerts

21.1 Objectives

Harden and centralize the transcript-hash accumulator (already used since Phase 4), formalize downgrade-sentinel handling (already begun in Phase 5), and implement the complete alert subsystem (§8.10) as the sole path for fatal-condition reporting (I6, I11, P10).

21.2 Detailed Implementation Steps

  1. Consolidate TranscriptHash into a single owned component per connection, with update() called from exactly one dispatch point per message (auditable via a compile-time exhaustiveness check on the message-type match), closing any gap left by earlier phases' incremental wiring.
  2. Implement retry_reset()'s exact synthetic-record construction (§8.7): replace the first ClientHello with message_hash(1) || len || Hash(first_ClientHello), single-call-guarded (I13).
  3. Implement the server-side downgrade-sentinel write path: when a TLS-1.3-capable server negotiates a lower version (out of Phase 0 scope functionally, but the sentinel-writing code must exist and be tested so Phase 0's TLS-1.3-only server still correctly demonstrates the mechanism against a hypothetical downgraded negotiation in fixture form) — document this as testable-but-inactive given ADR-02's TLS-1.3-only scope.
  4. Implement the complete Alert encode/decode and the AlertDescription ↔ TlsError mapping (ADR-20) for every entry in §8.10's catalogue.
  5. Implement the alert-dispatch integration: every fatal condition detected anywhere in tls-record, tls-handshake, or tls-cert surfaces through a single send_fatal_alert(description) call that both sends the wire alert and transitions the local state machine to Closed (I11) — no code path may skip the send-then-close ordering.
  6. Implement close_notify handling: a Warning-level alert that triggers graceful shutdown, distinguished from every fatal alert both in the type system (AlertLevel) and in the state-machine's handling (no Closed-as-error state for a clean close).

21.3 Deliverable

A centralized, single-owner transcript-hash component and a complete alert subsystem, integrated so that every prior phase's ad hoc error paths now route through send_fatal_alert.

21.4 Acceptance Criteria

  • A fixture asserting exactly one TranscriptHash::update() call per handshake message across a full recorded handshake — proving I3 by construction, not just by the final hash matching.
  • Every alert in §8.10's catalogue has at least one fixture that triggers it via the actual code path that would raise it in production (not a synthetic direct construction) — 18+ named fixtures.
  • The single-retry HRR guard (I13) and the downgrade-sentinel check (I7) are both re-verified as still passing after the alert-subsystem consolidation (regression gate).
  • close_notify is distinguishable from every fatal alert in a fixture asserting the connection remains in a "clean shutdown" telemetry state, not an "error" one.

21.5 Conformance Fixtures

  • conformance/malformed_messages/alert_catalogue/*.bin — 18 fixtures, one per AlertDescription value, each triggered via its real code path.
  • conformance/rfc8448_vectors/hello_retry_request.json — re-run against the consolidated transcript component.
  • conformance/malformed_messages/close_notify_graceful.bin — a clean shutdown sequence, expected: no error telemetry, connection state Closed(graceful).

21.6 Pitfalls

  • Leaving any earlier phase's ad hoc TlsError return without routing through send_fatal_alert — this phase's job is specifically to find and close those gaps, since a fatal condition that doesn't send an alert leaves the peer without diagnostic information and may leave the local state ambiguous (I11's exact concern).
  • Conflating close_notify (warning-level, graceful) with a fatal alert in shared handling code — they must be structurally distinguished (AlertLevel), not just by convention.
  • Re-triggering retry_reset() on a second, illegitimate HelloRetryRequest instead of rejecting it outright (I13) — the single-call guard must be enforced here, not merely hoped for.

21.7 Performance Concerns

Transcript-hash updates are O(message length) SHA-256/384 operations, already accounted for in §34's key-schedule cost estimate — no additional overhead is introduced by consolidation, only correctness/auditability.

21.8 Edge Cases

  • An alert received while already in a terminal Closed state (e.g. a peer sending a duplicate alert) — must be handled without panicking, simply ignored or logged, since the connection is already unusable.
  • A close_notify received mid-handshake (before Connected) — RFC 8446 treats an unexpected early close as equivalent to a fatal handshake_failure from the perspective of the peer's incomplete state, even though the alert itself is warning-level.

21.9 Failure Analysis

  • Manifestation: a fuzz target in Phase 11 discovers a code path (an obscure extension-parsing error inside tls-handshake) that returns a TlsError without ever calling send_fatal_alert, leaving the connection silently stuck. Root cause: an early-phase error return that predates this phase's consolidation was missed. Debug method: grep every TlsError construction site against every send_fatal_alert call site, diff for gaps (a scriptable audit, scripts/check_constant_time.sh's sibling audit script). Signal: a connection object that is neither Connected nor Closed after an error. Recovery: route the missed path through send_fatal_alert, add an exhaustiveness lint to CI preventing future gaps.

21.10 Operational Notes

Alert telemetry (per-AlertDescription counters) is the primary signal for docs/runbooks/handshake-failure-triage.md — an operator seeing a spike in a specific alert type should consult that runbook's per-alert diagnostic tree.

22. Phase 10 — Session Resumption, Tickets and 0-RTT Early Data

22.1 Objectives

Implement PSK-based session resumption (NewSessionTicket, pre_shared_key), ticket encryption/rotation (ADR-16), and 0-RTT early data with its explicit replay-risk scoping (P9, I10, ADR-15).

22.2 Detailed Implementation Steps

  1. Implement NewSessionTicket construction (server, post-handshake message) carrying an encrypted ResumptionSecret plus ticket_lifetime, ticket_age_add, and an opaque label (§11's SessionTicket).
  2. Implement ticket encryption under a rotating AES-256-GCM key (ADR-16): a TicketKeyStore holding the current and previous key, rotating every 24 hours, rejecting tickets encrypted under a key older than the rotation window.
  3. Implement client-side ticket storage and the pre_shared_key/ psk_key_exchange_modes extension construction on a subsequent ClientHello, including binder computation (built in Phase 4, exercised here end-to-end).
  4. Implement server-side PSK selection: match the client's offered ticket against the TicketKeyStore, decrypt, verify the binder (Phase 4), and key the Early Secret from the resumption PSK (Phase 1's KeySchedule, Early stage) instead of an all-zero IKM.
  5. Implement psk_dhe_ke mode (mandatory support, ADR-14): even on a resumed handshake, perform a fresh ECDHE (Phase 2) for forward secrecy, feeding both PSK and DHE input into the Handshake Secret per §8.5.
  6. Implement 0-RTT early data (ADR-15): client sends EarlyData immediately after ClientHello under keys derived from the early traffic secret (§8.5); server either accepts (processes early data, echoes acceptance) or rejects (skips early data, proceeds with 1-RTT only) — wire both paths in the state machines.
  7. Implement the server-side single-use ticket marker for anti-replay (I10, P9): a ticket, once presented and accepted for 0-RTT, is marked consumed; a second presentation for 0-RTT is rejected (early data not accepted) even though the 1-RTT portion of the handshake may still proceed via PSK resumption.

22.3 Deliverable

Working PSK resumption (both psk_ke and psk_dhe_ke modes) and opt-in 0-RTT early data with single-use anti-replay enforcement, integrated into both state machines.

22.4 Acceptance Criteria

  • A resumption handshake (§8.12) completes and derives secrets matching RFC 8448's resumption vectors byte-for-byte.
  • Resumed handshake CPU cost, measured in benchmarks/handshake_throughput.rs, shows the ratio predicted in §34 (symmetric-only cost, no signature verification) against a full handshake.
  • A 0-RTT early-data fixture is accepted on first presentation and rejected (I10) on a simulated replay of the same ticket, verified as two distinct fixtures with distinct expected outcomes.
  • Ticket-key rotation is exercised by a fixture presenting a ticket encrypted under a key one rotation period old — accepted; and under a key two rotation periods old — rejected.

22.5 Conformance Fixtures

  • conformance/rfc8448_vectors/resumption_psk.json — resumption secret schedule, reused from Phase 1/4, now exercised end-to-end through both state machines.
  • conformance/malformed_messages/zero_rtt_replay.bin — a second presentation of a consumed 0-RTT ticket; expected: early data rejected, 1-RTT handshake still completes.
  • conformance/malformed_messages/expired_ticket_key.bin — a ticket encrypted under a rotated-out key; expected: PSK rejected, server falls back to a fresh full handshake.

22.6 Pitfalls

  • Enabling 0-RTT by default rather than opt-in per data type (P9 explicitly forbids this) — the replay risk must be a deliberate application-level choice.
  • Deriving the Early Secret from an all-zero IKM on a resumed handshake by mistake (copy-paste from the non-PSK path) — must use the actual resumption PSK.
  • Forgetting psk_dhe_ke's fresh ECDHE step, treating resumption as symmetric-only even when forward secrecy is mandated — psk_ke-only mode sacrifices forward secrecy and should be a distinct, clearly-labeled configuration choice, not the silent default (ADR-14).
  • Ticket single-use marking scoped only to the ticket label without considering that an attacker might replay before the marker propagates in a multi-server fleet — document this as a known limitation of in-memory single-node marking versus a shared-store design (T-relevant, see §24 T7).

22.7 Performance Concerns

Resumed handshakes at 40,000-60,000/core/second versus 3,000-4,500 for full handshakes (§4) is roughly an order of magnitude improvement — the ratio derivation is worked in §34; this is the primary motivation for resumption's existence and should be the headline number in any deployment-facing documentation.

22.8 Edge Cases

  • Client offers a ticket that the server's current TicketKeyStore cannot decrypt (e.g. issued by a different server instance in a fleet with unsynchronized keys) — must fail closed to a fresh full handshake, not fatally error the connection.
  • 0-RTT early data arrives but the server ultimately selects a different cipher suite than the one the ticket was issued under — must reject the early data (cipher-suite mismatch invalidates the early traffic secret's derivation) while still completing the 1-RTT handshake.
  • A ticket's ticket_age_add-obfuscated age, when de-obfuscated, indicates an age exceeding ticket_lifetime — must reject as an expired PSK, not merely a suspiciously-timed one.

22.9 Failure Analysis

  • Manifestation: in a two-server-fleet interop test, resumption works when the same server issues and receives the ticket, but fails across servers. Root cause: TicketKeyStore's rotating key is generated independently per server instance with no shared coordination. Debug method: confirm via ticket-key fingerprint logging (non-secret metadata only, per P12) that the two servers hold different keys. Signal: ticket decryption failures correlate exactly with cross-server presentation. Recovery: document the shared-ticket-key coordination requirement (§26) as a fleet-deployment operational dependency, not a code bug — the code correctly fails closed.

22.10 Operational Notes

Ticket-key rotation and cross-fleet coordination is covered by docs/runbooks/ticket-key-rotation.md; 0-RTT opt-in policy is an application-level configuration decision documented alongside ADR-15's tradeoff.

23. Phase 11 — Interop Testing, Fuzzing, Conformance and Perf Hardening

23.1 Objectives

Validate every prior phase against real TLS stacks (the ultimate conformance oracle), run the full fuzzing campaign to a zero-crash gate, execute the constant-time verification pass, and close out performance targets against §4/§30.

23.2 Detailed Implementation Steps

  1. Stand up the interop matrix (ADR-26, scripts/run_interop_matrix.sh): this implementation as client against OpenSSL/BoringSSL/rustls servers, and as server against the same three as clients — 6 combinations minimum, each exercising full handshake, resumption, and 0-RTT where the peer supports it.
  2. Promote the Phase 7/9 fuzz smoke runs to full campaigns: fuzz_targets/ der_parser.rs, fuzz_targets/message_parser.rs, fuzz_targets/record_layer.rs, each run under ASan/UBSan for a minimum sustained 72-hour CI-scheduled campaign (Krawczyk, Paterson & Wee 2013's record-layer analysis and the Heartbleed lineage both motivate treating the record layer as a first-class fuzz target).
  3. Implement the constant-time verification pass (ADR-07): a dudect-style statistical timing harness (scripts/check_constant_time.sh) over the AEAD path, ECDHE, and signature verification, run against both a "should be constant" input class and a deliberately varying one, confirming no measurable divergence within the harness's statistical threshold.
  4. Implement differential testing: feed the same corpus of handshake messages and certificates through this implementation's parser and a reference parser (e.g. OpenSSL's ASN.1 dump tooling), diffing structured output for divergence.
  5. Implement deterministic replay of every captured interop-matrix transcript as a permanent regression fixture (closing the loop: a real interop break becomes a fixture, per N.9's discipline in every prior phase).
  6. Run perf-regression gating against §30's targets table (benchmarks/ handshake_throughput.rs, benchmarks/record_throughput.rs) as a named CI gate, failing a PR that regresses a tracked metric beyond a configured tolerance.
  7. Execute fault injection: truncated records, reordered messages (fed directly to the state machine bypassing normal ordering, to test that the state machine itself — not just the transport — rejects them), and injected alerts mid-handshake.

23.3 Deliverable

A green interop matrix against three real TLS stacks in both roles, a 72-hour zero-crash fuzz campaign result, a passing constant-time verification report, and a perf-regression-gated CI pipeline meeting §30's targets.

23.4 Acceptance Criteria

  • 6/6 interop combinations complete a full handshake and exchange application data successfully; resumption succeeds in every combination where the peer supports TLS 1.3 resumption; 0-RTT succeeds where the peer supports it (some peers may not enable 0-RTT by default — documented per-peer in the interop matrix results, not treated as a failure of this implementation).
  • Zero crashes and zero ASan/UBSan findings across the full 72-hour fuzz campaign on all three fuzz targets — this is the explicit gate, not "very few" crashes.
  • The constant-time harness reports no statistically significant timing divergence for AEAD, ECDHE and signature-verification paths, at the harness's configured confidence threshold.
  • Every §30 performance target (M1-M12) is met or the PR is blocked by the perf-regression gate.

23.5 Conformance Fixtures

  • conformance/rfc8448_vectors/* — full re-run against every interop peer's live transcript for cross-validation, not just the static RFC 8448 vectors.
  • conformance/malformed_messages/* — full corpus re-run as fault-injection input to each live interop peer to confirm this implementation's alerts are themselves well-formed and accepted by real peers as valid alerts.
  • New: conformance/interop_transcripts/{openssl,boringssl,rustls}_{client,server}.pcap — captured interop-matrix transcripts promoted to permanent regression fixtures.

23.6 Pitfalls

  • Treating a single successful interop run as sufficient — interop bugs are often intermittent (e.g. triggered only by a specific extension ordering a particular peer version happens to send); the matrix must run repeatedly across peer version updates, not once and done.
  • Running the fuzz campaign for a short smoke duration and calling it complete — deep parser bugs (recursion, arithmetic overflow) often require sustained corpus evolution over many hours to surface (this phase's 72-hour figure is a floor, not a target to shortcut).
  • Interpreting a constant-time harness's "no divergence detected" as a formal proof — it is a statistical test with a detection floor (dudect-style tools have known limits); document this honestly rather than overclaiming.

23.7 Performance Concerns

This phase is where §30's targets are actually measured and enforced for the first time end-to-end (earlier phases measure components in isolation); a full-handshake measurement here may reveal that component-level targets don't compose linearly (e.g. cache effects across the full call chain) — treat any such gap as a finding to document in docs/performance/, not silently absorb.

23.8 Edge Cases

  • An interop peer that implements a TLS 1.3 draft version's quirks (some older rustls/ BoringSSL builds shipped pre-final-RFC draft behavior) — document per-peer-version compatibility notes rather than silently special-casing quirky behavior into the core state machine.
  • A fuzz-discovered crash that only reproduces under a specific allocator or optimization level — must be reproducible in the exact CI configuration that will gate future PRs, not just in a local debug build.

23.9 Failure Analysis

  • Manifestation: the perf-regression gate fails on record-layer throughput with no corresponding code change in tls-record. Root cause: an upstream dependency bump (e.g. aes-gcm minor version) silently changed SIMD dispatch on the CI runner's CPU. Debug method: bisect via Cargo.lock diff against the last-known-good benchmark run. Signal: regression correlates with a dependency bump, not a source change. Recovery: pin the dependency, file an upstream issue, document as a supply-chain-sensitive perf dependency (ADR-29).

23.10 Operational Notes

The interop matrix and fuzz campaign results are the primary artifacts referenced by §28's testing strategy and §29's CI/CD topology; a release is not cut (§29) without a green run of both within the release window.

26. Operational Readiness

Named metrics. full_handshakes_per_second, resumed_handshakes_per_second, handshake_failure_rate_by_alert (labeled by AlertDescription), average_round_trips, zero_rtt_accept_reject_rate, cert_validation_failure_rate (labeled by decision-table row), record_decrypt_failure_rate, rekey_count.

Tracing spans. One span per handshake phase (send_client_hello, derive_handshake_secret, verify_certificate_chain, verify_finished, derive_app_secret), nested under a per-connection root span, so a slow or failed handshake can be attributed to a specific phase without replaying a full capture.

Structured logging with mandatory secret redaction. All logging goes through tracing; secret-bearing types have no Debug/Display impl (ADR-23, enforced at compile time, not by convention) — a log statement that would need to print a Secret simply cannot compile.

Dashboards. Handshake success rate and latency percentiles (p50/p95/p99) by handshake type (full/resumed/0-RTT); alert-type breakdown; certificate-validation failure breakdown by decision-table row; fuzz/interop CI gate status as a release readiness dashboard.

Alerting philosophy. Alert on rate-of-change (a sudden spike in handshake_failure_rate_by_alert for one specific alert type) rather than absolute thresholds, since baseline failure rates vary by deployment (public internet-facing vs. internal-only). Page on: unknown_ca spike (likely a broken trust-anchor rotation), bad_record_mac spike (possible active attack or client-population key mismatch), constant-time CI gate failure (blocks release, does not page in production).

SLOs. 99.9% of full handshakes complete within 2 round trips and 5ms compute budget; 99.99% of resumed handshakes complete within 1 round trip and 0.5ms compute budget; zero tolerance for a fatal-alert-without-telemetry gap (FM-class incidents).

Incident response. Named runbooks under docs/runbooks/: handshake-failure- triage.md (alert-type-driven decision tree), certificate-expiry-response.md (proactive rotation before FM-4), interop-break-diagnosis.md (packet-capture diff methodology for FM-6), suspected-timing-leak-investigation.md (escalation path when the constant-time harness or an external report suggests a timing oracle, tied to T2), ticket-key-rotation.md (fleet-wide key coordination, tied to FM-5).

Backup/restore of ticket keys. TicketKeyStore's current and previous key are the only stateful secret requiring backup consideration in a fleet deployment; backup is out of scope for a single-node deployment (tickets simply fail closed to full handshake on key loss, an acceptable degradation per ADR-16).

Deployment topology. A server fleet behind a load balancer requires either sticky sessions (no shared-state requirement) or a shared TicketKeyStore (for resumption to work across nodes, per FM-5's failure mode) — document both options with their tradeoffs.

Canary/rollback/migration. Canary a new release against the interop matrix in a staging environment before fleet-wide rollout; rollback is a version pin (no persistent state migration required, since tickets/sessions are ephemeral and fail closed safely); a ticket-format version bump (§27) requires a migration window where both old and new formats are accepted before old-format tickets age out naturally.

27. Compatibility & Versioning

TLS version negotiation and middlebox-compatibility mode. Per RFC 8446 section D.4, this implementation sends a fake change_cipher_spec and a non-empty legacy_session_id to maximize compatibility with middleboxes that assume TLS 1.2 framing; version negotiation itself is exclusively via supported_versions, never the legacy legacy_version field (frozen at 0x0303, ADR-02).

Cipher-suite and named-group negotiation. Server preference order is configurable (Phase 6 N.10); client offers all locally-supported suites/groups and accepts the server's selection provided it is a subset of what was offered.

Certificate and signature-algorithm agility. New signature schemes are added by extending SignatureScheme and SignatureVerifier's dispatch (Phase 8) without touching the state machine — the state machine is agnostic to which scheme is negotiated.

Ticket format versioning. SessionTicket's opaque label embeds a format-version byte; a server rejects (fails closed to full handshake) a ticket whose version it does not recognize, rather than attempting a best-effort parse.

Interoperability as the primary compatibility contract. The interop matrix (Phase 11, §28) is the enforceable contract — a change that breaks any of the 6 combinations is treated as a compatibility regression regardless of RFC-conformance arguments in isolation.

API stability of the state-machine interface. ClientState/ServerState's public transition API follows SemVer; internal state variants may be added/removed across minor versions provided the public transition function signatures remain stable.

Deprecation of weak algorithms. RSA-PKCS1v1.5 signatures (retained only for certificate-chain compatibility, ADR-13) and any cipher suite weaker than the §4 targets are flagged in CHANGELOG.md for a two-minor-version deprecation window before removal.

SemVer and the guarantee of interop with compliant RFC 8446 peers. Patch releases never change wire behavior; minor releases may add new negotiable options (new curves, new signature schemes) without breaking existing negotiation; major releases may change the public API but never intentionally break interop with an RFC-8446-compliant peer.

28. Testing & Verification Strategy

Unit. Per-crate unit tests for every codec, every crypto-trait implementation, every DER primitive (Phase 0-2, Phase 7).

Integration. Full handshake over an in-process loopback pipe (tests/ handshake_loopback.rs), resumption (tests/resumption.rs), 0-RTT (tests/zero_rtt.rs).

Property. The key schedule matches the RFC 8446 appendix vectors bit-for-bit (I8, tied to Phase 1 N.5's RFC 8448 fixtures); an AEAD nonce never repeats across a connection's records, checked via a proptest generating arbitrary record counts up to a large bound (I2, tied to Phase 3 N.5); the transcript hash is order-sensitive, checked via a proptest that permutes message order and asserts the hash differs (I3, tied to Phase 9 N.5); a tampered handshake message always fails Finished, checked via a proptest flipping a random byte in a random message and asserting Finished verification fails (I3/I11, tied to Phase 5/6 N.5); path validation accepts a valid chain and rejects every single-field mutation of it, checked via an exhaustive mutation-test harness (I4, tied to Phase 8 N.4/N.5).

Interoperability testing against OpenSSL, BoringSSL and rustls as both client and server, as a named CI gate — the ultimate conformance oracle (Phase 11 §23.2), since RFC-text conformance in isolation does not guarantee two independent implementations actually agree on wire behavior.

Differential testing of the DER parser against a reference ASN.1 dump tool (Phase 11 §23.2 step 4), surfacing parser-behavior divergence RFC text alone cannot.

Fuzzing. The certificate/DER parser, the handshake message parser, and the record layer as primary targets (T4, T9), with a zero-crash and zero-sanitizer-finding gate under ASan/UBSan (Phase 7 initial smoke run, Phase 11 full 72-hour campaign).

Constant-time verification pass (dudect-style, ADR-07) as a named deliverable of Phase 11, covering AEAD, ECDHE and signature verification (T2, P2).

Chaos. Fault injection into the transport adapter (tls-net) simulating dropped, reordered, and duplicated records, verifying the record layer's sequence-number discipline (I2) holds under adversarial transport conditions, not just adversarial peer content.

Deterministic replay of every captured interop-matrix transcript as a permanent regression fixture (Phase 11 §23.2 step 5), so a once-fixed interop bug can never silently regress.

Soak. A multi-hour sustained-load run exercising full and resumed handshakes at a steady rate, watching for FM-10's unbounded-memory-growth failure mode specifically.

Fault injection. Truncated records, reordered messages fed directly to the state machine (bypassing transport-level reordering to isolate state-machine-level handling), and injected alerts mid-handshake (Phase 11 §23.2 step 7), tied to T1 and I6.

TLS 1.3 test vectors. RFC 8448's full vector suite, consumed across Phase 1, 2, 4, 5, 6, 8, 10 as each phase's respective conformance fixtures — not a one-time check but a running regression suite through every phase that touches the handshake.

Perf-regression gating (Phase 11 §23.2 step 6) against §30's targets table, tied to every M# ID.

29. Build & Release Engineering

Reproducible builds. Pinned Rust toolchain (rust-toolchain.toml) and committed Cargo.lock (ADR-27); CI builds inside the pinned Dockerfile image, not the runner's ambient toolchain.

Artifact signing. Release artifacts (source tarballs, any prebuilt binaries for example programs) are signed with a project release key; signatures published alongside CHANGELOG.md entries.

SBOM. A software bill of materials generated per release (cargo-cyclonedx or equivalent), with cryptographic dependencies (x25519-dalek, p256, aes-gcm, chacha20poly1305, ring, ed25519-dalek) flagged for the extra scrutiny in ADR-29.

Release channels. main (unreleased), tagged releases following SemVer (§27); no "nightly" channel for a library where wire-format stability matters more than feature velocity.

CI/CD topology. Per-PR: build, test, clippy -D warnings, fuzz-smoke (short duration), interop-matrix smoke (a reduced subset of the full 6-combination matrix). Nightly: full 72-hour-rolling fuzz campaign (accumulating corpus across nights, not restarting), full interop matrix, constant-time verification pass. Release-gated: all of the above must be green within the release window, plus a full non-rolling fuzz run and a fresh interop matrix run against current peer versions.

Version stamping. Build metadata embeds the exact commit hash and toolchain version, surfaced via a version() API call for operational diagnostics.

Provenance/attestation. CI-produced artifacts carry SLSA-style provenance attestation tying the artifact to the exact CI run, commit, and dependency lockfile that produced it.

Dependency auditing with special scrutiny on cryptographic dependencies. cargo audit runs on every CI build; any version bump to a crate in the crypto dependency list (tls-crypto's wrapped crates) requires an explicit manual review entry in CHANGELOG.md, not an automatic merge, per ADR-29's escalated scrutiny policy.

30. Performance Engineering

Methodology. The handshake's cost is fundamentally asymmetric-crypto-bound (one ECDHE, one signature verification, one certificate-chain validation), while the record layer's cost is symmetric-crypto-bound (AEAD per byte) — these two regimes are measured and targeted separately, never conflated into a single "TLS is fast/slow" number. Allocation in the hot record-layer path is minimized (buffer reuse across records within a connection). The constant-time-versus-speed tension (P2) means some optimizations available to a non-security-sensitive codec are structurally unavailable here — this is treated as a fixed cost, not a target for future "optimization." AEAD hardware acceleration (AES-NI) is detected at runtime and factored into cipher-suite preference (Phase 3 N.10). Session resumption (Phase 10) is the dominant real-world optimization lever, not record-layer micro-tuning. Tail latency (p99) is tracked separately from mean latency, since a single slow signature verification (e.g. RSA-3072 on a loaded core) can dominate p99 even when mean latency looks healthy.

31. Scalability Analysis

What stays constant vs grows. Per-connection state is O(1) after the handshake completes (fixed-size TrafficKeys, sequence counters, §11) — it does not grow with connection lifetime absent a KeyUpdate, which itself resets rather than grows state. Handshake CPU is dominated by one ECDHE operation and one signature verification (O(1) per handshake, independent of any prior state) — this is the reason resumption (replacing both with a single symmetric HKDF chain) yields the order-of-magnitude improvement in §34. Record-layer cost is linear in bytes transferred, O(n) in the AEAD sense, with a small constant per-record overhead (the 5-byte header plus AEAD tag).

Named bottlenecks in order. (1) Signature verification and ECDHE dominate full-handshake CPU (§34's arithmetic), which is precisely why resumption exists — this is the single most important scaling lever in the whole system. (2) Certificate-chain parsing and validation is the second-order cost, scaling with chain length (bounded by T10's DoS guard). (3) Record-layer AEAD cost scales with application-data volume, not connection count, and is the target of AES-NI hardware acceleration. (4) Ticket-key coordination in a multi-node fleet (FM-5) is a coordination bottleneck, not a compute one — it scales with fleet size, not connection volume.

Scaling across cores and connections. The handshake engine has no shared mutable state across connections beyond the (optionally shared) TicketKeyStore and trust anchors — full handshakes scale linearly with core count up to the point where the shared TicketKeyStore's read lock becomes contended (mitigated by a read-mostly lock or per-core key cache).

Session-cache and ticket-key coordination cost in a server fleet. A shared TicketKeyStore requires either a coordinated key-derivation scheme (all nodes derive the same rotating key from a shared master secret and a synchronized rotation clock) or a shared low-latency store (e.g. a small encrypted key distributed via the deployment's existing secret-management infrastructure) — this coordination cost is amortized across all resumptions in the fleet and is cheap relative to the full-handshake cost it avoids.

Practical connection-rate ceiling and the levers beyond it. At M1's 3,000-4,500 full handshakes/second/core, a modest multi-core server reaches tens of thousands of full handshakes/second; beyond that ceiling the levers are, in order of impact: resumption (M2's order-of-magnitude improvement), 0-RTT (shaves a full round trip's wall-clock latency, §34), and hardware AEAD acceleration (record-layer throughput, orthogonal to handshake rate but relevant to overall server capacity under mixed handshake/data workloads).

32. Mental Models & First Principles

MM1 — A TLS handshake is an authenticated key exchange whose entire security reduces to two questions: is the transcript intact, and is the peer who they claim. Predicts: every message in the handshake exists to answer one of these two questions (certificate/CertificateVerify answer the second, Finished answers the first). Without it: a reader treats each message as an independent feature rather than seeing the unifying structure, making it easy to miss why an omission (e.g. skipping the transcript-hash update for one message) is catastrophic rather than cosmetic. Resolves §8.11's worked sequence and §7's invariants I3/I4.

MM2 — The state machine is the security boundary; most TLS CVEs are not broken cryptography but an accepted transition that should have been refused. Predicts: a security review of this codebase should spend disproportionate time on ClientState/ServerState's match arms, not on the AEAD wrapper code (which is delegated to audited crates per ADR-03 and therefore lower-risk by construction). Without it: effort misallocates toward re-auditing primitives that are already audited upstream while the actually-novel, actually-risky code (the state machine) gets less scrutiny. Resolves P1, ADR-08, §24 T1.

MM3 — Constant time is a correctness property, not a performance property, because a timing difference is an oracle and an oracle is a full break. Predicts: a "slightly slower but constant-time" implementation is strictly preferable to a "faster but variable-time" one for any secret-dependent operation — there is no acceptable tradeoff curve here, unlike most performance-vs-correctness tensions. Without it: a well-intentioned optimization (an early-exit comparison, a branch-predicted fast path) silently reintroduces the Lucky 13/Bleichenbacher/ROBOT lineage. Resolves P2, ADR-07, §24 T2.

MM4 — A certificate's public key is worthless until the chain to it is validated; validation and use must never race or interleave. Predicts: any code path that holds a reference to an unvalidated certificate's public key alongside a validated one's is a latent goto-fail bug waiting for a refactor to trigger it. Without it: a "just this once" shortcut (e.g. checking a cached key before revalidating) looks safe in review but is the exact structural shape of the 2014 Apple bug. Resolves P3, I4, §24 T5.

MM5 — Key material has an epoch, and an epoch has a well-defined end; a secret that outlives its epoch is a liability with no offsetting benefit. Predicts: every Secret/TrafficKeys should have an obvious answer to "when does this die," and code that cannot answer that question is holding secret material too long. Without it: secrets accumulate in memory "just in case," widening the window for a memory- disclosure bug (Heartbleed-class) to leak something valuable. Resolves P12, I5, ADR-21.

MM6 — HKDF's Extract/Expand split exists because entropy extraction and key expansion are different problems with different failure modes. Predicts: a key-schedule bug is more likely to be a wrong salt/ikm pairing at an Extract step than a wrong length at an Expand step, because Extract steps are where this implementation chains one stage's output into the next stage's input (§8.5). Without it: debugging a key-schedule mismatch searches the wrong half of the derivation first. Resolves P7, I8, Phase 1.

MM7 — Every AEAD nonce is a promise never to repeat under a given key; the promise is enforced by structure (a monotonic counter), not by hope. Predicts: any future redesign that introduces out-of-order record delivery (e.g. a QUIC integration, §36) must independently re-derive its nonce-uniqueness argument rather than inheriting this one, because the monotonic-sequence-number structure this argument relies on may not hold under reordering. Without it: a well-meaning port of this record layer to a reordering transport silently reintroduces nonce reuse. Resolves P5, I2, §24 T3.

MM8 — 0-RTT trades a cryptographic guarantee (freshness) for a latency win, and no implementation choice can buy the guarantee back — only usage discipline can. Predicts: any proposed "fix" for 0-RTT replay that lives purely in the protocol implementation (rather than in what the application chooses to send over 0-RTT) is addressing the wrong layer. Without it: engineers repeatedly attempt to "solve" 0-RTT replay in the library and are repeatedly disappointed, since the problem is inherent to the network model (a replayed packet is indistinguishable from a retransmitted one at the transport layer). Resolves P9, I10, ADR-15, §24 T7.

MM9 — A downgrade attack only needs to succeed once per connection to fully compromise it; the sentinel is a one-shot, unconditional check for exactly this reason. Predicts: any code path that makes the sentinel check conditional on "handshake otherwise looks successful" has already lost, because that is exactly the attacker's target state. Without it: a refactor that moves the check into an error-handling branch (rather than the unconditional happy path) reintroduces the vulnerability it was meant to close. Resolves P6, I7, §24 T6.

The sans-io, typed-per-state design is the single most instructive contrast for this project (ADR-19, ADR-08): by making illegal transitions a compile error rather than a runtime check, an entire CVE class (implicit-permissive- transition bugs) becomes structurally unreachable rather than merely tested-against. It wins wherever embeddability and compile-time state-machine safety matter more than matching a decades-old C API surface.

OpenSSL. The post-Heartbleed, post-"goto fail" explicit state-machine rewrite (ssl/statem/) is itself evidence for P1/ADR-08: OpenSSL's own history shows an implicit, flag-soup state model produced exactly the vulnerability class this project structures around from day one. It wins on sheer ecosystem ubiquity and feature breadth (TLS 1.0-1.3, DTLS, engines) that a from-scratch Phase-0-scoped project deliberately does not attempt to match.

BoringSSL. Google's fork narrowed OpenSSL's API surface and hardened its record handling, trading API stability (explicitly no stable ABI) for a smaller, more auditable surface tailored to Google's own deployment needs. It wins in a deployment that controls both ends of the API contract and values a smaller attack surface over API portability.

s2n-tls. The small-and-auditable goal — a deliberately compact codebase reviewable in full by a human — is the second most instructive contrast: it demonstrates that "can be fully read and understood" is itself a security property, achievable without full formal verification. It wins in a regulated environment (AWS's own compliance needs) where auditability is a hard requirement and a large, feature-complete implementation is a liability.

miTLS / Project Everest. Full formal verification (F* refinement types compiled via HACL* to verified C) is the third most instructive contrast — it proves protocol and implementation correctness against a formal model rather than testing against a finite fixture/fuzz/interop suite as this project does. It wins where the threat model demands mathematical proof rather than empirical confidence (e.g. a national-security-grade deployment), at a development-cost multiple this project's Phase-0 scope does not attempt to match (§36).

34. Back-of-Envelope Capacity Model

Full-handshake CPU cost, decomposed (from §4/§30's M7-M11): X25519 ECDHE (~50 μs)

  • signature generation, server-side ECDSA-P256 (~50 μs, asymmetric-cheaper-than- verify) + signature verification, client-side ECDSA-P256 (~80 μs) + certificate-chain parse/validate for a 3-cert chain (~30 μs) ≈ 210 microseconds of pure crypto/parse cost per full handshake (server-side view; client-side is similar with roles swapped). At 210 μs/handshake, one core's theoretical ceiling is 1,000,000 / 210 ≈ 4,760 handshakes/second/core, matching M1's 3,000-4,500 target once scheduling/allocation overhead (roughly 10-25%) is subtracted.

Resumed-handshake CPU cost (symmetric only): HKDF-Extract/Expand chain (~5 μs total across the schedule) + AEAD key derivation (~2 μs) + Finished HMAC verify (~2 μs) ≈ ~10 microseconds per resumed handshake. Ceiling: 1,000,000 / 10 = 100,000 handshakes/second/core theoretical, matching M2's 40,000-60,000 target once overhead is subtracted. Ratio: resumption is roughly 20-25x cheaper than a full handshake — the arithmetic that motivates ADR-14/ADR-15 and Phase 10's entire existence.

Record-layer throughput from AEAD cost: AES-128-GCM with AES-NI hardware acceleration runs at roughly 0.5-1 cycle/byte; at a 3 GHz core, that is 3,000,000,000 / 0.75 ≈ 4 GB/s theoretical, matching M5's 2,000-4,000 MB/s target once framing/copy overhead is subtracted. Without AES-NI, software AES-GCM costs roughly 5-8 cycles/byte, dropping to 400-600 MB/s — this is exactly why ChaCha20-Poly1305 (software-optimized to ~2-3 cycles/byte, no hardware dependency, ~1,000-1,500 MB/s at 3 GHz) is preferred absent AES-NI (Phase 3 N.7, M6).

Nonce space and the practical rekey point. The nonce space is 2^64 records (§8.3's 64-bit sequence number). AES-GCM's safety margin (NIST SP 800-38D) recommends rekeying well before 2^32 records under a single key for the strongest confidentiality bound in adversarial settings; at a sustained 4 GB/s (M5) and an average 1,400-byte record, 2^32 records is 2^32 * 1,400 bytes ≈ 6 TB of data before a conservative rekey, comfortably beyond any single connection's realistic lifetime but explicitly enforced by I2's rekey-before-wraparound guard as a defense-in-depth measure, not a practically-reachable limit in normal operation.

Per-connection memory (buffers + key schedule + certificate state): two TrafficKeys (32-byte key + 12-byte IV each, both directions, roughly 200 bytes with overhead) + transcript-hash state (~100 bytes) + a 3-certificate chain retained for the connection's lifetime for potential renegotiation-adjacent diagnostics (~3-6 KB typical) + record-layer buffers sized to the max record (2^14+256 bytes, both directions ≈ 33 KB) ≈ roughly 36-40 KB worst case, consistent with M12's 16-32 KB target for a connection that has dropped its certificate-chain retention post- handshake (the more common steady-state figure).

Handshake bandwidth (certificate chain dominates the ServerHello flight): a typical 3-certificate chain (leaf + intermediate + root, each 1-2 KB DER-encoded) is roughly 3-6 KB, dwarfing the rest of the handshake's message bytes (ClientHello/ ServerHello/EncryptedExtensions/Finished together total well under 1 KB) — this is why certificate-chain size is a first-class §4 constraint (T10) and why certificate compression (RFC 8879, PhaseDeferred) is a real bandwidth optimization for high-latency/low-bandwidth links.

0-RTT savings at a stated RTT: at a representative 50 ms round-trip time, a 1-RTT handshake costs 2 round trips of wall-clock latency before application data flows (100 ms) versus 0-RTT's 1 round trip (50 ms) — a 50 ms savings per connection, which compounds significantly for a client establishing many short-lived connections (e.g. a mobile client reconnecting frequently), the concrete number behind ADR-15's "0-RTT's latency win is real" claim.

35. Hard Questions (Self-Examination)

  1. If PathValidator::validate and SignatureVerifier::verify are two separate calls (§20.2 step 6), what structurally prevents a future refactor from swapping their order or calling verify first "as an optimization"? (resolves P3, I4, §20.4)
  2. Given that RFC 8448's vectors don't cover every cipher-suite/hash-length combination (§13.9's failure analysis), how much residual risk remains that a SHA-384 path has a subtle bug the vector suite cannot catch? (resolves §13, §23, §28)
  3. Is the single-retry HelloRetryRequest guard (I13) actually enforceable if a malicious client simply opens a new connection after a rejected retry — does the guard protect anything beyond a single TCP connection's resource cost? (resolves I13, §18.6, §24 T10)
  4. The downgrade sentinel (I7) protects against an active MITM rewriting ServerHello — but what protects against a MITM that instead blocks the connection entirely to force a client's application-level fallback to plaintext HTTP? (resolves P6, §24 T6, and explicitly: nothing in this project's scope — a non-goal worth naming precisely)
  5. §34 assumes a 3-certificate chain as typical — how does the capacity model change for a deployment with a 6-certificate chain (some real-world CA hierarchies), and does T10's chain-length limit (10 certificates) leave enough headroom? (resolves §4, §34, §24 T10)
  6. ADR-12's OCSP soft-fail policy means an attacker who can block network access to an OCSP responder effectively disables revocation checking — is soft-fail actually the right default, or does it trade too much security for interop? (resolves ADR-12, §8.8, §24 T5-adjacent)
  7. Given MM8's claim that 0-RTT replay cannot be "solved" at the protocol layer, is ADR-15's opt-in-per-data-type design sufficient, or does it merely relocate the footgun to application developers who may not understand the tradeoff? (resolves P9, ADR-15, §24 T7)
  8. §31 claims per-connection state is O(1) — does the certificate-chain retention noted in §34's memory model (for renegotiation-adjacent diagnostics) actually violate this claim, and if so, should that retention be dropped post-handshake by default? (resolves §31, §34, §11)
  9. The constant-time verification pass (Phase 11) is explicitly a statistical test with a detection floor (§23.6) — what is the actual confidence this project can claim about constant-time guarantees versus what a reader might assume from "passed the constant-time gate"? (resolves ADR-07, §23, MM3)
  10. FM-5 (ticket-key desynchronization) is documented as "the code correctly fails closed" — but does failing closed to a full handshake fleet-wide under a misconfiguration create a DoS-like load spike (every resumption attempt becomes a full handshake) that itself needs a named mitigation? (resolves FM-5, §26, §31)
  11. §36 lists TLS 1.2 dual-stack as a rejected alternative citing the SMACK paper — but this project's own state machine still has to parse a legacy legacy_record_version field for middlebox compatibility (§27) — is that itself a smaller-scale version of the same composite-state-machine risk? (resolves ADR-02, §27, §24 T1)
  12. Is the trust placed in x25519-dalek/p256/ring (ADR-03) itself a single point of failure that undermines the "we own the protocol logic" framing — what would actually change in this project's threat model if one of those crates had a supply-chain compromise? (resolves ADR-03, ADR-29, §24 T12)
  13. §8.9's CertificateVerify signed-content construction includes a context string specifically to prevent cross-protocol signature reuse — does this project's signature-verification code path make it structurally impossible to accidentally verify a signature made for a different context string, or merely conventionally unlikely? (resolves §8.9, §20.6, P3)
  14. Given §34's arithmetic showing resumption is 20-25x cheaper than a full handshake, does ADR-14's decision to support both ticket-only and PSK-cache resumption modes actually earn its complexity, or would a ticket-only default capture most of the real-world benefit at lower implementation risk? (resolves ADR-14, §22, §34)
  15. §33 names miTLS's full formal verification as an alternative this project rejects for cost reasons — at what point would this project's fixture/fuzz/ interop-based confidence (§28) actually be falsified by a bug a formal model would have caught, and how would the team know? (resolves §28, §33, §36)
  16. The transcript hash (I3) binds every handshake message, but the accumulator itself (§11's TranscriptHash) is a single mutable running-hash state — what happens to the invariant's guarantee if a future concurrency-motivated refactor makes message ingestion order non-deterministic under concurrent processing? (resolves I3, §11, MM1)
  17. §22.6 flags in-memory single-node 0-RTT replay marking as a known limitation in a multi-server fleet (T7) — what is the actual attacker-observable window of replay opportunity this leaves open, quantified? (resolves T7, §22, §26)
  18. §4 sets a max certificate chain byte size of 64 KB — does this square with §34's observation that certificate compression (RFC 8879, deferred) would meaningfully reduce handshake bandwidth, or is compression solving a problem this limit already bounds adequately? (resolves §4, §34, §37)

38. Glossary

Handshake — the RFC 8446 message exchange (ClientHello through Finished) that negotiates parameters and establishes shared secrets before application data flows. Record layer — the framing and AEAD-protection layer beneath the handshake, carrying every content type over TLSPlaintext/TLSCiphertext (§8.3). AEAD — Authenticated Encryption with Associated Data, providing confidentiality and integrity in one primitive (RFC 5116). Nonce — the per-record unique input to the AEAD cipher, derived from the static IV XOR sequence number (§8.3). ECDHE — Elliptic-Curve Diffie-Hellman Ephemeral key exchange, providing forward secrecy. X25519 — the Curve25519-based Diffie-Hellman function (RFC 7748). Key share — the KeyShareEntry extension value carrying a party's ephemeral public key. Key schedule — the RFC 8446 section 7.1 derivation chain producing every secret from PSK/DHE input (§8.5). HKDF — HMAC-based Key Derivation Function (RFC 5869), split into Extract and Expand. Extract — HKDF's entropy-concentration step, producing a pseudorandom key from possibly-weak input keying material. Expand- Label — TLS 1.3's HKDF-Expand wrapper encoding a label string and context (§8.5). Derive-Secret — the TLS-1.3-specific wrapper binding a derived secret to the current transcript hash. Early secret — the first key-schedule stage, keyed by PSK or zero. Handshake secret — the second stage, keyed by the ECDHE shared secret. Master secret — the third stage, from which application and resumption secrets derive. Traffic secret — a per-direction, per-epoch secret from which TrafficKeys (key + IV) are expanded. Transcript hash — the running hash over every handshake message in wire order (§8.7), the basis of Finished and CertificateVerify. Finished — the HMAC over the transcript proving possession of the corresponding traffic secret (§8.1). CertificateVerify — the signature over the transcript proving possession of the certificate's private key (§8.9). PSK — Pre-Shared Key, used for resumption. Session ticket — an opaque, encrypted label a server issues for later PSK resumption (§11). Resumption — establishing a connection using a previously-negotiated PSK instead of a fresh full handshake. 0-RTT / early data — application data sent before the handshake completes, keyed by the early traffic secret, explicitly replayable (P9). Replay — resubmission of a previously observed message/ticket to trigger an unintended repeated effect (T7). HelloRetryRequest (HRR) — a ServerHello-shaped message requesting a different key_share group, triggering a transcript-hash special case (P13). Downgrade protection — the ServerHello.random sentinel mechanism detecting forced version rollback (§8.1, I7). ALPN — Application-Layer Protocol Negotiation (RFC 7301), an extension negotiating the post-handshake application protocol. SNI — Server Name Indication (RFC 6066), an extension carrying the requested hostname. Path validation — the RFC 5280 process confirming a certificate chain terminates at a trusted root (§8.8). Trust anchor — a locally-configured root certificate or key accepted as an ultimate authority. Chain building — constructing the ordered certificate path from leaf to root. RSA-PSS — Probabilistic Signature Scheme for RSA (RFC 8017), TLS 1.3's mandated RSA signature mode. ECDSA — Elliptic Curve Digital Signature Algorithm (FIPS 186-5). Ed25519 — the EdDSA signature scheme over Curve25519 (RFC 8032). Constant time — an implementation property where execution time is independent of secret input values (P2). Timing oracle — a side channel where measurable timing variance leaks information about a secret. Padding oracle — a specific timing/error oracle arising from padding validation (Vaudenay 2002). State-machine attack — an attack exploiting an implicitly- permissive protocol state transition (Beurdouche et al. 2015). Alert — the TLS protocol's fatal/warning signaling message (§8.10). close_notify — the warning-level alert signaling a graceful connection shutdown. Middlebox compatibility mode — RFC 8446 Appendix D's cosmetic conformance to TLS 1.2 framing for legacy-middlebox tolerance. Sans-io — an I/O model where a state machine consumes/produces buffers with no socket ownership (ADR-19). Basic constraints — an X.509 extension marking a certificate as a CA and optionally limiting path length. Key usage — an X.509 extension restricting a key's permitted cryptographic operations. Name constraints — an X.509 extension restricting the namespace a CA may issue certificates for. OCSP stapling — a server-supplied, signed revocation status for its own certificate, avoiding a client-side network round trip. Cipher suite — the negotiated combination of key exchange, AEAD, and hash algorithm for a connection. Named group — an identifier for a Diffie-Hellman/ECDHE group (NamedGroup, §11).
