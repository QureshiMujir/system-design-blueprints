In one paragraph

Before a browser and a server can exchange private data, they must agree on secret keys and each must be sure who it is talking to. This blueprint designs a from-scratch Rust implementation of that opening conversation in TLS 1.3 (the handshake), together with the layer that encrypts every message afterwards (the record layer) (§1). It ships as a library whose state machines read and write byte buffers and never own a socket (§1, ADR-19). Its defining idea: the protocol logic is written here, while the raw cryptographic arithmetic is delegated to audited crates behind one trait boundary (§1, ADR-03). The people who run it are protocol implementers embedding TLS in custom transports, security engineers studying the handshake as a teaching artifact, and CI-driven interop testers (§1).

The problem, concretely

Two programs that have never met must agree on a secret over a network an attacker can read and rewrite. The blueprint reduces the whole handshake to two questions: is the sequence of messages intact, and is the peer who it claims to be (MM1). Everything in the design exists to answer one of those two questions. Certificate and CertificateVerify answer the second, and Finished answers the first (MM1).

A concrete failure shows why this is hard to get right. A client offers only one key-exchange group (X25519), but the server is configured for P-256 only. The server cannot proceed with the client's offer, so it asks for a retry naming P-256, and the client re-sends its first message. If no group is mutually supported, the server aborts with a fatal alert before any key exists (§8.14). That small negotiation already forces a special rule for how the earlier messages are remembered (P13, §8.7).

The blueprint's motivation list explains what goes wrong when the rules are implemented loosely (§2). Implementations that accepted a message the specification never allowed at that point produced the FREAK, SKIP and SMACK family of attacks (§2, P1). A key-derivation label typed wrongly yields a connection that looks fine but is insecure (§2, P7). Reusing a nonce under one key is a full confidentiality break (§2, P5). A certificate parser that reads hostile bytes is a classic attack surface, and the 2014 "goto fail" bug let signature checking silently switch off (§2, P3). The blueprint's summary: most TLS CVEs are not broken cryptography but an accepted transition that should have been refused (MM2).

How it works, end to end

Follow one full handshake through the boxes of §3. This diagram is adapted from §3: the original has more boxes, but this keeps its data flow.

 network bytes
   -> tls-net            (transport adapter; owns no crypto state)
   -> tls-record         (AEAD open/seal, nonce = static_iv XOR seq#; holds TrafficKeys)
   -> codec              (tls-handshake: bounds-checked parse/encode of handshake messages)
   -> ClientState / ServerState        (decides which message is legal next)
        |-- Transcript-hash accumulator (running SHA-256/384 over all messages)
        |-- Key schedule engine         (tls-core: HKDF chain -> secrets -> TrafficKeys)
        |-- ECDHE module                (tls-crypto: X25519 / P-256)
        |-- Certificate parser + path validator (tls-cert) -> signature verifier
        |-- PSK / ticket store          (tls-core)
        `-- Alert subsystem             (the only path for reporting a fatal condition)
  1. Transport adapter (tls-net). It owns the socket or loopback pipe and does no parsing or crypto. The untrusted-input boundary starts the moment bytes cross it (§3). It is a convenience for tests and examples, not the shipped contract (§1).
  2. Record layer (tls-record). It fragments and reassembles records, and is the sole owner of TrafficKeys and sequence numbers. The secret-material boundary starts here (§3, §1).
  3. Message codec (tls-handshake). Every length field is checked against the remaining buffer before a single byte is trusted (§3, P11).
  4. Handshake state machine (ClientState / ServerState). It is the sole authority on which message is legal next, and it drives the transcript hash, the key schedule and the alert subsystem (§3, P1).
  5. Key schedule engine (tls-core). It chains HKDF steps into early, handshake and application secrets, then into TrafficKeys (§3, §8.5). The ECDHE shared secret is consumed once and dropped (§3, §8.6).
  6. Certificate parser and path validator (tls-cert). It reads untrusted DER and trusts nothing until the whole chain validates to a trust anchor (§3, I4). The signature verifier then checks the CertificateVerify signature (§3, §8.9).
  7. Alert subsystem (tls-handshake). Every fatal alert aborts the connection, never a silent accept (§3). (§3 attributes this to I6, while the terminal-state rule is I11 (§7).)

The message order for a full handshake is: ClientHello, ServerHello, then (under handshake keys) EncryptedExtensions, Certificate, CertificateVerify, Finished from the server, then Finished from the client, then application data under application keys (§8.11). tls-crypto wraps the audited primitives (x25519-dalek, p256, aes-gcm, chacha20poly1305, ring for RSA-PSS), and no primitive math lives above that trait (§1).

The core ideas

A state machine where only listed messages are legal (§8.1, §8.2, P1)

In each state the code names the exact messages it will accept, and anything else is a fatal unexpected_message (P1, I6). The client table runs Start, WaitServerHello, WaitEncryptedExtensions, WaitCertOrCertRequest, WaitCertificate, WaitCertVerify, WaitFinished, SendFinished and Connected (§8.1). The server table runs Start, ChooseParameters, then Send* states for each server message, WaitClientFinished and Connected (§8.2). In both, a fatal alert in any state leads to Closed (§8.1, §8.2). The blueprint encodes this as a typed enum per state, so an illegal transition fails to compile (ADR-08). The cost is friction on purpose: adding a message type means touching every state's match arm (P1).

A three-step trace from the failure-path example (§8.14, §8.2):

Step Event State afterwards
1 Client sends ClientHello offering only X25519 server in ChooseParameters (no key share match)
2 Server sends HelloRetryRequest naming P-256 server back to Start, awaiting a 2nd ClientHello
3 Client re-sends ClientHello with a P-256 key share handshake proceeds as in §8.11 step 2

A second HelloRetryRequest is an error. The client table says illegal_parameter (§8.1), and the server table says illegal_parameter on a second mismatch (§8.2), while I13 gives the recovery as a fatal unexpected_message (§7). Both texts stand as written. The blueprint's own debugging method is to find which invariant's enforcement point did or did not fire, and to work backward along the data flow in §3 (§7).

The key schedule: one chain, three stages (§8.5, P7, MM6)

Plain words: instead of one big key, the protocol grows a ladder of secrets. Each rung is mixed with a fresh ingredient and a fingerprint of the conversation so far. The HKDF Extract step concentrates entropy (§38), and the Expand step does key expansion, a different problem (MM6). Adapted from §8.5:

 (PSK or 0) --Extract-->  Early Secret      -> binder_key, client_early_traffic_secret
     Derive-Secret(., "derived", "") = salt for the next Extract
 (EC)DHE secret --Extract--> Handshake Secret -> "c hs traffic", "s hs traffic"   (over CH..SH)
     Derive-Secret(., "derived", "") = salt for the next Extract
 0 --Extract-->          Master Secret      -> "c ap traffic", "s ap traffic", "exp master"
                                               (over CH..server Finished), "res master"
                                               (over CH..client Finished)

Derive-Secret(Secret, Label, Messages) is HKDF-Expand-Label(Secret, Label, Transcript-Hash(Messages), Hash.length), and each traffic secret expands once more into a write key and a 12-byte IV (§8.5). Labels are exact ASCII strings declared as named constants, checked against the RFC 8448 test vectors (P7, I8). A wrong label produces a derivation that looks working but is not interoperable and may be weak (P7). The blueprint predicts that a key-schedule bug is likelier to be a wrong salt/ikm pairing at an Extract step than a wrong length at an Expand step (MM6).

The record layer and the never-repeat nonce (§8.3, P5, P8)

Every record is protected by an AEAD cipher (encryption plus integrity in one primitive), and each record needs a unique one-time number (nonce). The blueprint builds it as static_iv XOR the 64-bit big-endian sequence number, with the sequence number starting at 0 per traffic secret and incrementing by 1 per record (§8.3). The sequence number never resets except on a key update, which derives fresh traffic secrets (§8.3). Reusing a nonce under one key is a full confidentiality break, and for GCM a forgery break (P5). The price is that records must be processed strictly in order at the AEAD layer (P5, MM7).

The real content type travels inside the encrypted TLSInnerPlaintext, and the outer header always says application_data, so an observer cannot tell handshake from application traffic (P8, §8.3). Code must not branch on the outer type before the AEAD open succeeds (P8, I9).

The transcript hash and what Finished proves (§8.7, §8.9, P4, P13)

The transcript hash is a running hash over every handshake message in wire order, using message bytes and never record framing (§8.7). Finished is an HMAC over the full transcript (P4), and the CertificateVerify signature covers 0x20 * 64 || context_string || 0x00 || Transcript-Hash (§8.9). The 64 spaces and the null byte exist to stop a signature being replayed under another protocol's format (§8.9). Consequence: none of ServerHello, EncryptedExtensions or Certificate is authenticated as it arrives. Trust is deferred entirely to Finished, so application code must not consume decrypted handshake data before the local Finished check passes (P4).

After a retry, the first ClientHello is replaced in the transcript by a synthetic message_hash record holding the hash of that ClientHello, before the retry request and second ClientHello are appended (§8.7, P13). The accumulator exposes an explicit retry_reset() (P13). A second HRR or a missing reset produces an unverifiable transcript (I13), and getting the rule wrong yields a Finished value a compliant peer will not verify (P13).

Downgrade is handled in the same spirit. A server that negotiates a lower version writes a fixed sentinel into ServerHello.random, and a TLS 1.3 client checks it unconditionally, even on a handshake that "worked" (P6, ADR-17). A match is a fatal illegal_parameter (I7, §8.10).

Certificate path validation: check the chain before using the key (§8.8, P3, I4)

Plain words: path validation is the process that confirms a certificate chain ends at a trusted root, and a trust anchor is a locally configured root accepted as an ultimate authority (§38). The validator runs these steps: build the chain from the leaf to a root, verify each issuer's signature, check validity dates, check basicConstraints (every non-leaf must be a CA, path length respected), check keyUsage, check nameConstraints, match the hostname against the leaf's Subject Alternative Name, match the root against the configured trust anchors, and apply the revocation policy last (§8.8). Failure alerts per check are fixed: bad_certificate, certificate_expired, certificate_revoked, unknown_ca (§8.8).

The ordering rule is the heart: PathValidator::validate must return Ok before SignatureVerifier is ever called with that certificate's key, and no path may call the verifier on an unvalidated chain "just to check" (P3, I4). MM4 states the reasoning: holding an unvalidated key beside a validated one is the structural shape of the 2014 "goto fail" bug.

Two signature checks get two different alerts. A bad CertificateVerify signature maps to decrypt_error in the client table (§8.1), while a failed issuer signature in the chain maps to bad_certificate (§8.8). The alert catalogue lists both: bad_certificate for a certificate that is "structurally invalid or signature fails", and decrypt_error for "signature verification fails" (§8.10).

Resumption and 0-RTT: trading cost and freshness (§8.12, §22, P9, MM8)

Resumption means the server issues an opaque, encrypted session ticket for later use (§38). On return, the client presents it as a pre-shared key (PSK) (§8.12). The sequence is: ClientHello with pre_shared_key and a binder over a partial transcript; the server verifies the binder and selects the PSK; the Early Secret is keyed by the resumption PSK; a fresh ECDHE is still performed in psk_dhe_ke mode for forward secrecy; the rest repeats the full handshake's steps 4 to 12 (§8.12, §22.2).

The blueprint describes the cost of that step two ways. §8.12's heading says "PSK, no fresh ECDHE", and §31 says resumption replaces the ECDHE and the signature verification with a single symmetric HKDF chain. §8.12 step 4 and §22.2 step 5 instead perform a fresh ECDHE in psk_dhe_ke mode, which §22.2 marks as mandatory support. The resumed-handshake cost in §34 counts symmetric work only.

0-RTT early data lets the client send application bytes immediately after ClientHello (§22.2). It shaves a full round trip (§31, §34), but a replayed packet is indistinguishable from a retransmitted one, so no implementation choice can buy freshness back (MM8). The design therefore marks early data replayable in the API, makes it opt-in per request type, and tracks a ticket as consumed after one accepted use (P9, ADR-15, I10, §22.2). On a replay, the server rejects the early data and carries on with the rest of the handshake (I10, §8.13, §22.5, §24 T7). The server table instead lists unexpected_message for a detected replay (§8.2). The two texts disagree and are both reproduced here as written.

Tickets are encrypted under a key rotated every 24 hours, with a 7-day maximum lifetime (ADR-16, §4). The key store holds the current and previous key and rejects tickets encrypted under a key older than the rotation window (§22.2); a fixture accepts a ticket one rotation period old and rejects one two periods old (§22.4). A ticket the server cannot decrypt must fail closed to a full handshake, not an error (§22.8).

The trade-offs — where engineers disagree

Representing the handshake: typed states over flag soup (ADR-08)

Chosen: an explicit typed enum per state, with exhaustive matching, so illegal transitions do not compile. The lesson taken is that implicit permissiveness in flag-tracked state is the root of FREAK/SKIP (ADR-08). Rejected: booleans such as "hello sent" and "cert received" (ADR-08). When the rejected choice is right: a disposable one-off test stub that never parses untrusted network input, such as a throwaway local-only smoke script (ADR-08).

Cryptography: wrap audited crates (ADR-03)

Chosen: x25519-dalek, p256, aes-gcm, chacha20poly1305 and ring behind the tls-crypto trait. Constant-time field arithmetic is a separate side-channel research project, and audited crates already carry that assurance (ADR-03, §1). Rejected: reimplementing field arithmetic from scratch (ADR-03). When the rejected choice is right: when the goal is specifically side-channel research, for example a HACL*-style formally verified primitives project (ADR-03).

Version scope: TLS 1.3 only (ADR-02)

Chosen: TLS 1.3 only in Phase 0, to avoid the composite state machine the SMACK paper showed dangerous (ADR-02). A version-branching table roughly doubles the transition surface (§36 A1). Rejected: a TLS 1.2 dual stack (ADR-02). When the rejected choice is right: when the deployment must interoperate with legacy middleboxes that never upgraded, for example some industrial control systems (ADR-02).

Early data: supported but opt-in (ADR-15)

Chosen: 0-RTT supported, opt-in per data type, off by default. The latency win is real, and the replay risk is manageable when scoped (ADR-15, P9). Rejected: not implementing 0-RTT at all (ADR-15). When the rejected choice is right: a deployment with zero tolerance for any replay risk, for example a payment-authorization channel (ADR-15).

Revocation: staple when present, soft-fail when absent (ADR-12)

Chosen: check an OCSP-stapled response when present and log-and-proceed when absent. Hard-fail would break interop with the many real servers that do not staple, and CRL fetching adds a network dependency mid-handshake (ADR-12). Rejected: hard-fail on missing OCSP, and CRL fetching (ADR-12). When the rejected choice is right: a high-security enterprise deployment that mandates revocation checking, for example a financial PKI with a CRL distribution SLA (ADR-12). The blueprint itself asks whether soft-fail trades too much security for interop, since an attacker who blocks the responder disables revocation checking (§35 item 6).

I/O model: sans-io over an owning socket (ADR-19)

Chosen: a state machine that takes byte buffers in and out and owns no socket, for embeddability, fixture-driven testing and a possible future QUIC integration (ADR-19). Rejected: a blocking API that owns the socket (ADR-19). When the rejected choice is right: a simple demo CLI tool that prioritizes a five-line quick-start over embeddability (ADR-19). An owning-socket API can be built as a thin adapter over a sans-io core, which is what tls-net is, but not the reverse without a rewrite (§36 A3).

Downgrade protection: a sentinel, not the version field (ADR-17)

Chosen: the ServerHello.random sentinel. The version field alone is what DROWN/Logjam-class attacks manipulate, while the sentinel is cryptographically bound into the transcript (ADR-17). Rejected: relying on the version field alone (ADR-17). When the rejected choice is right: a closed deployment pinned to TLS 1.3 on both endpoints with no version negotiation, so there is no downgrade surface for the sentinel to protect (ADR-17).

Roads not taken (§36, §37)

TLS 1.2 dual stack (§36 A1) wins for legacy middleboxes and clients that never upgraded, as in OpenSSL and BoringSSL, and is rejected because it multiplies the transition surface (§36 A1, ADR-02).

Formal verification (§36 A2), as in miTLS / Project Everest, wins when the threat model demands mathematical proof rather than fixture, fuzz and interop confidence. It is rejected as a much larger research effort, and the empirical confidence model is called a bounded tradeoff, not an oversight (§36 A2, §28).

An owning-socket blocking design (§36 A3) wins for a simple CLI demo where a five-line quick-start matters more than embeddability (§36 A3).

QUIC integration (§36 A4) wins for a transport already committed to QUIC, where QUIC's packet protection replaces the record layer entirely. It is deferred because RFC 9001 needs the traffic secrets exposed to an external packet-protection layer, which this project's record-layer-owns-the-secrets design does not yet support cleanly (§36 A4, §3).

The deferred register (§37) also lists DTLS 1.3, mutual TLS, Certificate Transparency, certificate compression, a post-quantum hybrid key exchange, P-384/P-521 and CRL-based revocation, each with an un-defer trigger. The mutual TLS row defers CertificateRequest (§1, §37). The state tables still carry an optional CertificateRequest step (§8.1, §8.2), and §17.8 says the client must parse and skip it while client-certificate support stays deferred.

What must never be false

  • I1: no application data is sent or accepted before the handshake completes, except 0-RTT data marked replayable. Noticed by a state-machine assertion; counter handshake_incomplete_data_rejected (§7).
  • I2: an AEAD nonce is never reused under a key. Noticed by a sequence-number overflow check; counter rekey_triggered; recovery is a forced key update (§7).
  • I3: the transcript hash includes every handshake message in order. Noticed by fixture replay tests; a skipped message aborts with decode_error (§7).
  • I4: a peer chain is validated to a trust anchor before its key authenticates anything. Noticed by the chain-validation fixture suite; counter cert_validation_failure by reason (§7).
  • I5: a secret is zeroized after its epoch and never logged. Noticed by a static lint plus a manual memory-scan test; no counter, since absence is the goal (§7).
  • I6: an unexpected message in any state aborts with unexpected_message. Noticed by a per-state negative fixture; counter unexpected_message_alert by state (§7).
  • I7: downgrade to a lower version is detected through the ServerHello.random sentinel. Noticed by a fixture with the sentinel present; counter downgrade_detected (§7).
  • I8: key-schedule label strings match the RFC exactly. Noticed by a byte-exact vector test, a build-time gate (§7).
  • I9: the outer record ContentType is never trusted before the AEAD open succeeds. Noticed by a fixture where a wrong outer type still opens correctly; failure gives bad_record_mac (§7).
  • I10: 0-RTT early data is never accepted twice for one ticket without an anti-replay mechanism. Noticed by a replay fixture; counter early_data_replay_rejected (§7).
  • I11: every fatal alert moves the connection to a terminal closed state. Noticed by a fixture per alert type; counters fatal_alert_sent and fatal_alert_received (§7).
  • I12: DER recursion depth and declared length are bounds-checked before interpretation. Noticed by an adversarial-DER fuzz corpus; counter der_parse_rejected by reason (§7).
  • I13: HelloRetryRequest triggers the synthetic transcript rule exactly once per handshake. Noticed by a fixture replaying an HRR handshake; telemetry hrr_count per connection, which must be at most 1 (§7).

What breaks in production

  • FM-1: a handshake hangs in a Wait* state. The peer never sends the expected message, or the transport drops packets. A handshake-timeout watchdog detects it, but that watchdog belongs to the transport layer, not to this library. The connection is torn down on timeout, and tools/transcript_dump shows the last message received (§25).
  • FM-2: repeated bad_record_mac from one peer. Root causes are a key-schedule mismatch, clock skew affecting ticket validity, or an active tamper attempt. Per-connection error-rate telemetry detects it. There is no automatic recovery because the failure is fatal by design (I11); the operator reconnects fresh without resumption and compares transcript hashes at the divergence point (§25).
  • FM-3: an unknown_ca spike across many connections. The trust-anchor bundle is out of date or a CA rotation has not propagated. The cert_validation_failure counter by reason spikes; recovery is updating the bundle (§25).
  • FM-5: resumption silently falls back to full handshakes fleet-wide. Ticket-key rotation is desynchronized across the fleet. The resumption-rate metric drops, and the server correctly fails closed to a full handshake. Recovery is synchronizing ticket-key distribution (§25, §22.9). The blueprint asks whether that fail-closed fallback itself creates a load spike that needs a named mitigation (§35 item 10).
  • FM-8: the 0-RTT acceptance rate is unexpectedly zero. The anti-replay store may be misconfigured to reject all early data, or clock skew breaks ticket age validation. §25 names the metric 0_rtt_accept_reject_rate, while §26's metric list spells it zero_rtt_accept_reject_rate. The fix is checking NTP and the anti-replay store (§25).
  • FM-9: the constant-time harness flags a regression. A new code path introduced a secret-dependent branch or table lookup. The CI constant-time job fails and the build is blocked; code review finds and removes the branch (§25, P2).
  • FM-10: memory grows without bound under load. A Secret or TrafficKeys type is not being dropped, such as a leaked Rc or reference cycle. The per-connection memory metric exceeds the §4 target; the fix is patching the leak and adding a regression test (§25).
  • FM-11: a false-positive downgrade rejection. A legitimate TLS 1.3 handshake is refused because of an off-by-one in the 8-byte sentinel constant. downgrade_detected fires on connections that should be clean. The fix is correcting the comparison and adding a regression fixture (§25, I7).

Threats a reader should know (§24):

  • T1 is a state-machine attack that slips a message legal in a weaker historical variant into the wrong place. The answer is the typed state machine, with a fixture for every illegal transition (P1, ADR-08).
  • T3 is nonce reuse from a repeated sequence number or a failed rekey at wraparound. The answer is the monotonic sequence number plus rekey-before-wraparound (I2, P5).
  • T5 is a certificate-validation bypass through an early-return bug. The answer is the hard validate-before-verify gate plus a structural call-order test (I4, P3).
  • T6 is an active attacker forcing TLS 1.2 or a weak suite. The answer is the unconditionally checked sentinel (I7, P6).
  • T7 is replay of captured 0-RTT data to repeat a non-idempotent effect. The answer is single-use ticket marking plus opt-in per data type (I10, P9, ADR-15). The blueprint concedes that in-memory single-node marking leaves a window in a multi-server fleet (§22.6, §35 item 17).

T12 (a compromised cryptographic dependency) cites a 29th ADR for extra scrutiny on crypto crates (§24), as do §23.9, §29 and §35 item 12, but the ADR table stops at ADR-28 (§9).

Where the blueprint's own numbers disagree, both sides are given here as written:

  • Round trips. §4 gives the 1-RTT full handshake as "2 round trips wall-clock" and 0-RTT as 1 round trip, and §34 uses the same 2-versus-1 count. §5 describes TLS 1.3 as collapsing the handshake "from 2-RTT to 1-RTT".
  • ChaCha20-Poly1305 throughput. §34's text gives about 1,000-1,500 MB/s at 3 GHz, while §4 and M6 target 700-1,200 MB/s (§34, §4, §30).
  • Signing cost. §34 says its decomposition comes from §4/§30's M7-M11, but those rows list ECDHE and verification costs only; the ~50 µs server-side ECDSA signing figure appears in §34 alone (§34, §4, §30).
  • Resumed-handshake cost. §34's ~10 µs counts symmetric work only, while §8.12 step 4 and §22.2 step 5 perform a fresh ECDHE in psk_dhe_ke mode.
  • Memory. §34's worst case of roughly 36-40 KB includes a certificate chain retained "for potential renegotiation-adjacent diagnostics", while ADR-18 says TLS 1.3 removed renegotiation entirely. §34 calls the figure consistent with the 16-32 KB target only for a connection that has dropped the chain, and §35 item 8 asks whether that retention should be dropped by default.
  • Ticket lifetime. Tickets may live 7 days (§4, ADR-16), while the key store keeps only the current and previous key under 24-hour rotation (§22.2), and a ticket two rotation periods old is rejected (§22.4). The blueprint does not say which bound governs.

How it compares

  • rustls chose a sans-io, typed-per-state design, so illegal transitions are compile errors (§33). That fits wherever embeddability and compile-time state-machine safety matter more than matching a decades-old C API surface (§33).
  • OpenSSL chose an explicit table-driven state machine after a rewrite, and owns the socket (§33). It wins on ecosystem ubiquity and breadth (TLS 1.0 to 1.3, DTLS, engines), and its own history is evidence for P1 and ADR-08 (§33).
  • BoringSSL chose a simplified state machine and a narrower, hardened API, giving up a stable ABI (§33). That fits a deployment that controls both ends of the API contract (§33).
  • s2n-tls chose a table of function pointers indexed by (mode, state) and a deliberately compact, fully readable codebase (§33, §5). It fits a regulated environment where auditability is a hard requirement (§33).
  • miTLS / Project Everest chose full formal verification, with an F* model compiled via HACL* to verified C (§33). That fits a threat model demanding mathematical proof, at a development cost this project does not attempt to match (§33, §36).

If you only remember three things

The whole handshake answers two questions, whether the transcript is intact and whether the peer is who it claims, and it defers all trust to Finished (MM1, P4). Most TLS failures are an accepted transition that should have been refused, so the state machine is the security boundary and the cryptographic primitives are delegated (MM2, ADR-03, ADR-08). Resumption and 0-RTT buy large cost and latency wins (§34), but 0-RTT gives up freshness that only application discipline can restore (MM8, P9).

Words used here

  • Handshake: the opening exchange that agrees on parameters and secrets before data flows (§38).
  • Record layer: the framing and encryption layer beneath the handshake (§38, §8.3).
  • AEAD: encryption that also proves the data was not changed (§38).
  • Nonce: the per-record unique input to the cipher, built from the IV and a sequence number (§38, §8.3).
  • ECDHE: a key exchange using fresh temporary keys, giving forward secrecy (§38).
  • Key schedule: the chain of derivations that produces every secret from the PSK and DHE inputs (§38, §8.5).
  • Transcript hash: the running hash over every handshake message in order (§38, §8.7).
  • Finished: an HMAC over the transcript, proving possession of the matching traffic secret (§38).
  • CertificateVerify: a signature over the transcript, proving possession of the certificate's key (§38).
  • HelloRetryRequest: a server message asking the client to retry with a different key-share group (§38, P13).
  • PSK / session ticket: a pre-shared key, and the opaque encrypted label used to resume with it (§38).
  • 0-RTT / early data: application data sent before the handshake completes, explicitly replayable (§38, P9).
  • Sans-io: a state machine that consumes and produces buffers and owns no socket (§38, ADR-19).
  • Trust anchor: a locally configured root accepted as an ultimate authority (§38).
  • Zeroization: overwriting secret memory before it is released (§38, P12).
