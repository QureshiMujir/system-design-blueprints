Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If PathValidator::validate and SignatureVerifier::verify are two separate calls (§20.2 step 6), what structurally prevents a future refactor from swapping their order or calling verify first "as an optimization"? (resolves P3, I4, §20.4)
  2. Given that RFC 8448's vectors don't cover every cipher-suite/hash-length combination (§13.9's failure analysis), how much residual risk remains that a SHA-384 path has a subtle bug the vector suite cannot catch? (resolves §13, §23, §28)
  3. Is the single-retry HelloRetryRequest guard (I13) actually enforceable if a malicious client simply opens a new connection after a rejected retry — does the guard protect anything beyond a single TCP connection's resource cost? (resolves I13, §18.6, §24 T10)
  4. The downgrade sentinel (I7) protects against an active MITM rewriting ServerHello — but what protects against a MITM that instead blocks the connection entirely to force a client's application-level fallback to plaintext HTTP? (resolves P6, §24 T6, and explicitly: nothing in this project's scope — a non-goal worth naming precisely)
  5. §34 assumes a 3-certificate chain as typical — how does the capacity model change for a deployment with a 6-certificate chain (some real-world CA hierarchies), and does T10's chain-length limit (10 certificates) leave enough headroom? (resolves §4, §34, §24 T10)
  6. ADR-12's OCSP soft-fail policy means an attacker who can block network access to an OCSP responder effectively disables revocation checking — is soft-fail actually the right default, or does it trade too much security for interop? (resolves ADR-12, §8.8, §24 T5-adjacent)
  7. Given MM8's claim that 0-RTT replay cannot be "solved" at the protocol layer, is ADR-15's opt-in-per-data-type design sufficient, or does it merely relocate the footgun to application developers who may not understand the tradeoff? (resolves P9, ADR-15, §24 T7)
  8. §31 claims per-connection state is O(1) — does the certificate-chain retention noted in §34's memory model (for renegotiation-adjacent diagnostics) actually violate this claim, and if so, should that retention be dropped post-handshake by default? (resolves §31, §34, §11)
  9. The constant-time verification pass (Phase 11) is explicitly a statistical test with a detection floor (§23.6) — what is the actual confidence this project can claim about constant-time guarantees versus what a reader might assume from "passed the constant-time gate"? (resolves ADR-07, §23, MM3)
  10. FM-5 (ticket-key desynchronization) is documented as "the code correctly fails closed" — but does failing closed to a full handshake fleet-wide under a misconfiguration create a DoS-like load spike (every resumption attempt becomes a full handshake) that itself needs a named mitigation? (resolves FM-5, §26, §31)
  11. §36 lists TLS 1.2 dual-stack as a rejected alternative citing the SMACK paper — but this project's own state machine still has to parse a legacy legacy_record_version field for middlebox compatibility (§27) — is that itself a smaller-scale version of the same composite-state-machine risk? (resolves ADR-02, §27, §24 T1)
  12. Is the trust placed in x25519-dalek/p256/ring (ADR-03) itself a single point of failure that undermines the "we own the protocol logic" framing — what would actually change in this project's threat model if one of those crates had a supply-chain compromise? (resolves ADR-03, ADR-29, §24 T12)
  13. §8.9's CertificateVerify signed-content construction includes a context string specifically to prevent cross-protocol signature reuse — does this project's signature-verification code path make it structurally impossible to accidentally verify a signature made for a different context string, or merely conventionally unlikely? (resolves §8.9, §20.6, P3)
  14. Given §34's arithmetic showing resumption is 20-25x cheaper than a full handshake, does ADR-14's decision to support both ticket-only and PSK-cache resumption modes actually earn its complexity, or would a ticket-only default capture most of the real-world benefit at lower implementation risk? (resolves ADR-14, §22, §34)
  15. §33 names miTLS's full formal verification as an alternative this project rejects for cost reasons — at what point would this project's fixture/fuzz/ interop-based confidence (§28) actually be falsified by a bug a formal model would have caught, and how would the team know? (resolves §28, §33, §36)
  16. The transcript hash (I3) binds every handshake message, but the accumulator itself (§11's TranscriptHash) is a single mutable running-hash state — what happens to the invariant's guarantee if a future concurrency-motivated refactor makes message ingestion order non-deterministic under concurrent processing? (resolves I3, §11, MM1)
  17. §22.6 flags in-memory single-node 0-RTT replay marking as a known limitation in a multi-server fleet (T7) — what is the actual attacker-observable window of replay opportunity this leaves open, quantified? (resolves T7, §22, §26)
  18. §4 sets a max certificate chain byte size of 64 KB — does this square with §34's observation that certificate compression (RFC 8879, deferred) would meaningfully reduce handshake bandwidth, or is compression solving a problem this limit already bounds adequately? (resolves §4, §34, §37)

32. Mental Models & First Principles

MM1 — A TLS handshake is an authenticated key exchange whose entire security reduces to two questions: is the transcript intact, and is the peer who they claim. Predicts: every message in the handshake exists to answer one of these two questions (certificate/CertificateVerify answer the second, Finished answers the first). Without it: a reader treats each message as an independent feature rather than seeing the unifying structure, making it easy to miss why an omission (e.g. skipping the transcript-hash update for one message) is catastrophic rather than cosmetic. Resolves §8.11's worked sequence and §7's invariants I3/I4.

MM2 — The state machine is the security boundary; most TLS CVEs are not broken cryptography but an accepted transition that should have been refused. Predicts: a security review of this codebase should spend disproportionate time on ClientState/ServerState's match arms, not on the AEAD wrapper code (which is delegated to audited crates per ADR-03 and therefore lower-risk by construction). Without it: effort misallocates toward re-auditing primitives that are already audited upstream while the actually-novel, actually-risky code (the state machine) gets less scrutiny. Resolves P1, ADR-08, §24 T1.

MM3 — Constant time is a correctness property, not a performance property, because a timing difference is an oracle and an oracle is a full break. Predicts: a "slightly slower but constant-time" implementation is strictly preferable to a "faster but variable-time" one for any secret-dependent operation — there is no acceptable tradeoff curve here, unlike most performance-vs-correctness tensions. Without it: a well-intentioned optimization (an early-exit comparison, a branch-predicted fast path) silently reintroduces the Lucky 13/Bleichenbacher/ROBOT lineage. Resolves P2, ADR-07, §24 T2.

MM4 — A certificate's public key is worthless until the chain to it is validated; validation and use must never race or interleave. Predicts: any code path that holds a reference to an unvalidated certificate's public key alongside a validated one's is a latent goto-fail bug waiting for a refactor to trigger it. Without it: a "just this once" shortcut (e.g. checking a cached key before revalidating) looks safe in review but is the exact structural shape of the 2014 Apple bug. Resolves P3, I4, §24 T5.

MM5 — Key material has an epoch, and an epoch has a well-defined end; a secret that outlives its epoch is a liability with no offsetting benefit. Predicts: every Secret/TrafficKeys should have an obvious answer to "when does this die," and code that cannot answer that question is holding secret material too long. Without it: secrets accumulate in memory "just in case," widening the window for a memory- disclosure bug (Heartbleed-class) to leak something valuable. Resolves P12, I5, ADR-21.

MM6 — HKDF's Extract/Expand split exists because entropy extraction and key expansion are different problems with different failure modes. Predicts: a key-schedule bug is more likely to be a wrong salt/ikm pairing at an Extract step than a wrong length at an Expand step, because Extract steps are where this implementation chains one stage's output into the next stage's input (§8.5). Without it: debugging a key-schedule mismatch searches the wrong half of the derivation first. Resolves P7, I8, Phase 1.

MM7 — Every AEAD nonce is a promise never to repeat under a given key; the promise is enforced by structure (a monotonic counter), not by hope. Predicts: any future redesign that introduces out-of-order record delivery (e.g. a QUIC integration, §36) must independently re-derive its nonce-uniqueness argument rather than inheriting this one, because the monotonic-sequence-number structure this argument relies on may not hold under reordering. Without it: a well-meaning port of this record layer to a reordering transport silently reintroduces nonce reuse. Resolves P5, I2, §24 T3.

MM8 — 0-RTT trades a cryptographic guarantee (freshness) for a latency win, and no implementation choice can buy the guarantee back — only usage discipline can. Predicts: any proposed "fix" for 0-RTT replay that lives purely in the protocol implementation (rather than in what the application chooses to send over 0-RTT) is addressing the wrong layer. Without it: engineers repeatedly attempt to "solve" 0-RTT replay in the library and are repeatedly disappointed, since the problem is inherent to the network model (a replayed packet is indistinguishable from a retransmitted one at the transport layer). Resolves P9, I10, ADR-15, §24 T7.

MM9 — A downgrade attack only needs to succeed once per connection to fully compromise it; the sentinel is a one-shot, unconditional check for exactly this reason. Predicts: any code path that makes the sentinel check conditional on "handshake otherwise looks successful" has already lost, because that is exactly the attacker's target state. Without it: a refactor that moves the check into an error-handling branch (rather than the unconditional happy path) reintroduces the vulnerability it was meant to close. Resolves P6, I7, §24 T6.

Required reading (§5)

Books

  • Ferguson, Schneier & Kohno, Cryptography Engineering — chs. 4 (block ciphers/modes), 7 (key negotiation), 8 (implementation pitfalls). Extract: why nonce-misuse and padding oracles are implementation, not math, failures. Applied in Phase 3.
  • Katz & Lindell, Introduction to Modern Cryptography — chs. 3 (PRFs/PRPs), 12 (digital signatures), 13 (public-key encryption). Extract: formal security definitions behind AEAD and signature schemes. Applied in Phase 3 and Phase 8.
  • Aumasson, Serious Cryptography — chs. 6 (AES), 7 (stream ciphers/ChaCha), 14 (TLS chapter itself). Extract: side-by-side AEAD construction comparison. Applied in Phase 3.
  • Ristić, Bulletproof TLS and PKI — chs. 3 (protocol), 6 (chain of trust), 9 (deployment pitfalls). Extract: real-world chain-validation failure modes. Applied in Phase 8.
  • Rescorla, SSL and TLS: Designing and Building Secure Systems — chs. on handshake protocol and record layer (TLS 1.2-era, read for historical contrast). Extract: why TLS 1.3 collapsed the handshake from 2-RTT to 1-RTT. Applied in Phase 5 and §27.
  • Menezes, van Oorschot & Vanstone, Handbook of Applied Cryptography — ch. 10 (key establishment), ch. 11 (digital signatures). Extract: formal ECDH and signature derivation math underlying tls-crypto. Applied in Phase 2 and Phase 8.
  • Anderson, Security Engineering — ch. 5 (cryptography), ch. 21 (network attack). Extract: systems-level view of why protocol state machines are attack surface. Applied in §24 (Threat Model).

Papers

  • Krawczyk 2010, "Cryptographic Extraction and Key Derivation: The HKDF Scheme" (CRYPTO) — formal basis for HKDF-Extract/Expand. Applied in Phase 1.
  • Krawczyk & Wee 2016, "The OPTLS Protocol and TLS 1.3" (EuroS&P) — the design basis of the TLS 1.3 key schedule. Applied in Phase 1 and Phase 5.
  • Dowling, Fischlin, Günther & Stebila 2015, "A Cryptographic Analysis of the TLS 1.3 Handshake Protocol Candidates" (CCS) — multi-stage-key-exchange security proof. Applied in Phase 5 and Phase 6.
  • Beurdouche et al. 2015, "A Messy State of the Union: Taming the Composite State Machines of TLS" (IEEE S&P) — the SMACK/state-machine-attack paper. Applied in Phase 5, Phase 6 and §24.
  • Krawczyk, Paterson & Wee 2013, "On the Security of the TLS Protocol: A Systematic Analysis" (CRYPTO) — record-layer and handshake composition analysis. Applied in Phase 3 and Phase 9.
  • Aviram et al. 2016, "DROWN: Breaking TLS Using SSLv2" (USENIX Security) — cross- protocol/downgrade attack lineage. Applied in Phase 9.
  • Adrian et al. 2015, "Imperfect Forward Secrecy: How Diffie-Hellman Fails in Practice" (Logjam, CCS) — weak-group downgrade attack. Applied in Phase 2 and Phase 9.
  • Böck, Somorovsky & Young 2018, "Return Of Bleichenbacher's Oracle Threat" (ROBOT, USENIX Security) — padding-oracle lineage still relevant to RSA key exchange fallback paths. Applied in Phase 8 and §24.
  • Al Fardan & Paterson 2013, "Lucky Thirteen: Breaking the TLS and DTLS Record Protocols" (IEEE S&P) — timing-oracle case study. Applied in Phase 3 and §28.
  • Bernstein 2006, "Curve25519: New Diffie-Hellman Speed Records" (PKC) — the X25519 field-arithmetic design this project delegates to x25519-dalek. Applied in Phase 2.

Reference Implementations

  • rustls (rustls/src/) — client/hs.rs, server/hs.rs (typed per-state handlers), msgs/handshake.rs (message codec). Lesson: sans-io typed-state design eliminates whole bug classes at compile time. Pitfall not to copy: rustls's msgs layer trusts nothing before a full round-trip through its own bounds-checked Reader — do not shortcut that with direct slicing.
  • OpenSSL (ssl/statem/) — statem_clnt.c, statem_srvr.c. Lesson: the original explicit state-machine rewrite (post-"flag soup" era) that followed the "goto fail" and Heartbleed incidents. Pitfall: the state tables are C macros over a shared mutable connection struct — easy to lose track of what is initialized in which state; do not replicate the mutable-shared-struct pattern.
  • BoringSSL (ssl/handshake_client.cc, ssl/handshake_server.cc) — Lesson: Google's fork simplified OpenSSL's state machine and added strict record-size and alert handling. Pitfall: BoringSSL intentionally has no stable ABI/API guarantee — do not copy its API shape as if it were a stable contract to mirror.
  • s2n-tls (tls/) — s2n_client_hello.c, s2n_handshake_io.c. Lesson: the small-and-auditable goal, state machine driven by a table of function pointers indexed by (mode, state). Pitfall: s2n's table-of-handlers pattern hides the transition legality checks inside the handler bodies rather than in the type system — prefer the type-level encoding (ADR-08).
  • miTLS / Project Everest — Lesson: formally verified handshake and record layer (F*-verified, compiled via HACL*). Pitfall: full formal verification is a distinct, much larger effort (§36) — do not attempt partial verification and call it equivalent assurance.
  • Go crypto/tls (src/crypto/tls/handshake_client_tls13.go, handshake_server_tls13.go) — Lesson: clean separation of key-schedule computation (tls13/key_schedule.go) from state-machine flow. Pitfall: Go's GC makes true secret zeroization unenforceable — do not assume a "zero the buffer" pattern is sufficient without checking allocator behavior in the target language.

Glossary (§38) · 52 terms · site-wide glossary

Handshake
the RFC 8446 message exchange (ClientHello through Finished) that negotiates parameters and establishes shared secrets before application data flows.
Record layer
the framing and AEAD-protection layer beneath the handshake, carrying every content type over TLSPlaintext/TLSCiphertext (§8.3).
AEAD
Authenticated Encryption with Associated Data, providing confidentiality and integrity in one primitive (RFC 5116).
Nonce
the per-record unique input to the AEAD cipher, derived from the static IV XOR sequence number (§8.3).
ECDHE
Elliptic-Curve Diffie-Hellman Ephemeral key exchange, providing forward secrecy.
X25519
the Curve25519-based Diffie-Hellman function (RFC 7748).
Key share
the KeyShareEntry extension value carrying a party's ephemeral public key.
Key schedule
the RFC 8446 section 7.1 derivation chain producing every secret from PSK/DHE input (§8.5).
HKDF
HMAC-based Key Derivation Function (RFC 5869), split into Extract and Expand.
Extract
HKDF's entropy-concentration step, producing a pseudorandom key from possibly-weak input keying material.
Expand- Label
TLS 1.3's HKDF-Expand wrapper encoding a label string and context (§8.5).
Derive-Secret
the TLS-1.3-specific wrapper binding a derived secret to the current transcript hash.
Early secret
the first key-schedule stage, keyed by PSK or zero.
Handshake secret
the second stage, keyed by the ECDHE shared secret.
Master secret
the third stage, from which application and resumption secrets derive.
Traffic secret
a per-direction, per-epoch secret from which TrafficKeys (key + IV) are expanded.
Transcript hash
the running hash over every handshake message in wire order (§8.7), the basis of Finished and CertificateVerify.
Finished
the HMAC over the transcript proving possession of the corresponding traffic secret (§8.1).
CertificateVerify
the signature over the transcript proving possession of the certificate's private key (§8.9).
PSK
Pre-Shared Key, used for resumption.
Session ticket
an opaque, encrypted label a server issues for later PSK resumption (§11).
Resumption
establishing a connection using a previously-negotiated PSK instead of a fresh full handshake.
0-RTT / early data
application data sent before the handshake completes, keyed by the early traffic secret, explicitly replayable (P9).
Replay
resubmission of a previously observed message/ticket to trigger an unintended repeated effect (T7).
HelloRetryRequest (HRR)
a ServerHello-shaped message requesting a different key_share group, triggering a transcript-hash special case (P13).
Downgrade protection
the ServerHello.random sentinel mechanism detecting forced version rollback (§8.1, I7).
ALPN
Application-Layer Protocol Negotiation (RFC 7301), an extension negotiating the post-handshake application protocol.
SNI
Server Name Indication (RFC 6066), an extension carrying the requested hostname.
Path validation
the RFC 5280 process confirming a certificate chain terminates at a trusted root (§8.8).
Trust anchor
a locally-configured root certificate or key accepted as an ultimate authority.
Chain building
constructing the ordered certificate path from leaf to root.
RSA-PSS
Probabilistic Signature Scheme for RSA (RFC 8017), TLS 1.3's mandated RSA signature mode.
ECDSA
Elliptic Curve Digital Signature Algorithm (FIPS 186-5).
Ed25519
the EdDSA signature scheme over Curve25519 (RFC 8032).
Constant time
an implementation property where execution time is independent of secret input values (P2).
Timing oracle
a side channel where measurable timing variance leaks information about a secret.
Padding oracle
a specific timing/error oracle arising from padding validation (Vaudenay 2002).
State-machine attack
an attack exploiting an implicitly- permissive protocol state transition (Beurdouche et al. 2015).
Alert
the TLS protocol's fatal/warning signaling message (§8.10).
close_notify
the warning-level alert signaling a graceful connection shutdown.
Middlebox compatibility mode
RFC 8446 Appendix D's cosmetic conformance to TLS 1.2 framing for legacy-middlebox tolerance.
Sans-io
an I/O model where a state machine consumes/produces buffers with no socket ownership (ADR-19).
Zeroization
overwriting secret memory with zero (or another fixed pattern) before deallocation (P12).
DER
Distinguished Encoding Rules, the strict-subset ASN.1 encoding used by X.509 (RFC 5280 delta ADR-10).
X.509
the ITU-T certificate format standard.
Basic constraints
an X.509 extension marking a certificate as a CA and optionally limiting path length.
Key usage
an X.509 extension restricting a key's permitted cryptographic operations.
Name constraints
an X.509 extension restricting the namespace a CA may issue certificates for.
OCSP stapling
a server-supplied, signed revocation status for its own certificate, avoiding a client-side network round trip.
Cipher suite
the negotiated combination of key exchange, AEAD, and hash algorithm for a connection.
Named group
an identifier for a Diffie-Hellman/ECDHE group (NamedGroup, §11).
Signature scheme
an identifier for a signature algorithm/hash combination (SignatureScheme, §11). ---
