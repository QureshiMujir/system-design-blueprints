Decisions (§9) · 28 ADRs

ADR-01

Implementation language

Chosen

Rust

Rejected

C, Go, Python

When the rejected choice is right

C wins when targeting a platform with no Rust toolchain (rare embedded MCUs)

Why: Ownership model enforces secret lifetime/zeroization; type system encodes state machine

ADR-02

Protocol version scope

Chosen

TLS 1.3 only, Phase 0

Rejected

TLS 1.2 dual-stack

When the rejected choice is right

TLS 1.2 wins when the deployment must interoperate with legacy middleboxes that never upgraded, e.g. some industrial control systems

Why: Avoids the composite-state-machine complexity the SMACK paper (Beurdouche et al. 2015) showed dangerous

ADR-03

Crypto-primitive strategy

Chosen

Wrap audited crates (x25519-dalek, p256, aes-gcm, chacha20poly1305, ring) behind tls-crypto trait

Rejected

Reimplement field arithmetic from scratch

When the rejected choice is right

Reimplementing wins when the goal is specifically side-channel research (e.g. a HACL*-style formally verified primitives project)

Why: Constant-time field arithmetic is a distinct side-channel-engineering research project; audited crates already carry that assurance

ADR-04

Curve support

Chosen

X25519 (mandatory) + P-256 (mandatory), P-384/P-521 deferred

Rejected

X448, Curve25519 custom Montgomery ladder

When the rejected choice is right

P-384/P-521 win when a deployment mandates FIPS 186-5 P-384 for compliance (e.g. some US federal systems)

Why: RFC 7748 defaults; X25519 dominates real-world deployment

ADR-05

AEAD support

Chosen

AES-128-GCM, AES-256-GCM, ChaCha20-Poly1305

Rejected

AES-CCM, custom AEAD

When the rejected choice is right

AES-CCM wins on constrained IoT hardware lacking GCM's parallel-multiply acceleration

Why: RFC 5288/5289 and RFC 8439 cover the deployed cipher-suite space

ADR-06

Key-schedule/HKDF implementation

Chosen

Own KeySchedule engine over the hkdf/hmac crates

Rejected

Hand-rolled HMAC

When the rejected choice is right

Hand-rolled HMAC wins only in a from-scratch-crypto-primitives variant of this project

Why: Test against RFC 8448 vectors directly; HMAC math is not the learning target here

ADR-07

Constant-time discipline enforcement

Chosen

subtle-crate comparisons + a dudect-style statistical test in CI (Phase 11)

Rejected

Manual code review only

When the rejected choice is right

Manual review alone wins only for a throwaway prototype never exposed to network input

Why: Manual review reliably misses subtle timing leaks (Lucky 13 precedent)

ADR-08

State-machine representation

Chosen

Explicit typed enum per state, exhaustive match, illegal transitions uncompilable

Rejected

Flag-soup (booleans tracking "hello sent", "cert received" etc.)

When the rejected choice is right

Flag soup wins only in a disposable one-off test stub that never parses untrusted network input, e.g. a throwaway local-only smoke script

Why: Beurdouche et al. 2015's central lesson: implicit permissiveness in flag-based state tracking is the FREAK/SKIP root cause

ADR-09

Buffering / record-layer memory model

Chosen

Fixed-capacity ring buffer per direction, bounded by §4's 2^14+256 max record

Rejected

Unbounded growable Vec

When the rejected choice is right

Unbounded Vec wins in a trusted-peer-only test harness with no adversarial input

Why: Bounds memory under a DoS-flood peer (T10)

ADR-10

Certificate-parsing strategy

Chosen

Own hardened ASN.1/DER reader purpose-built for X.509

Rejected

Generic third-party ASN.1 crate

When the rejected choice is right

A general ASN.1 crate wins when the project must also parse unrelated ASN.1-encoded formats (e.g. PKCS#7/CMS) beyond X.509

Why: DER parsing is a classic attack surface (P11); a purpose-built, minimal-grammar parser has a smaller attack surface than a general BER/DER/CER codec

ADR-11

Path-validation approach

Chosen

Own RFC 5280 section 6 validator

Rejected

Delegate to OS trust store via FFI

When the rejected choice is right

OS trust-store delegation wins in a production deployment needing OS-level CA-bundle updates and revocation feeds without redeploying

Why: Full ownership of validation logic is the learning target; also enables reproducible cross-platform testing

ADR-12

Revocation strategy

Chosen

OCSP stapling checked when present, soft-fail (log + proceed) when absent, Phase 0

Rejected

Hard-fail on missing OCSP; CRL fetching

When the rejected choice is right

Hard-fail wins in a high-security enterprise deployment mandating revocation checking (e.g. financial PKI with a CRL distribution SLA)

Why: Hard-fail breaks interop with the large fraction of real servers that don't staple; CRL fetching adds a network dependency mid-handshake

ADR-13

Signature-algorithm set

Chosen

RSA-PSS-2048/3072, ECDSA-P256/P384, Ed25519

Rejected

RSA-PKCS1v1.5 (legacy)

When the rejected choice is right

Verifying a legacy CA-issued certificate chain whose intermediate/root signatures predate RSA-PSS — the cert signatures (not the CertificateVerify) may require PKCS1v1.5, so it stays in the chain-verification path only

Why: RFC 8446 mandates PSS over PKCS1v1.5 for TLS 1.3 signatures; PKCS1v1.5's structure enabled the Bleichenbacher/ROBOT lineage

ADR-14

Session resumption model

Chosen

Both PSK cache (in-memory) and encrypted tickets

Rejected

Ticket-only, PSK-cache-only

When the rejected choice is right

Ticket-only wins in a horizontally-scaled fleet with no shared session cache; PSK-cache-only wins in a single-process embedded deployment

Why: Tickets scale statelessly across a server fleet; a local cache is faster for a single long-lived process

ADR-15

0-RTT support

Chosen

Supported, opt-in per data type, off by default

Rejected

Not implemented

When the rejected choice is right

Not-implemented wins in a deployment with zero tolerance for any replay risk, e.g. a payment-authorization channel

Why: 0-RTT's 1-round-trip latency win is real and requested by users; the replay risk is manageable when scoped (P9)

ADR-16

Ticket encryption and rotation

Chosen

AES-256-GCM-encrypted ticket, symmetric key rotated every 24h, 7-day max ticket lifetime

Rejected

Long-lived static ticket key

When the rejected choice is right

A static key wins only in a short-lived test/demo deployment with no real threat model

Why: Bounds the blast radius of a ticket-key compromise; matches RFC 8446 section 4.6.1 guidance

ADR-17

Downgrade-protection mechanism

Chosen

ServerHello.random sentinel per RFC 8446 section 4.1.3

Rejected

Rely on version field alone

When the rejected choice is right

A closed deployment pinned to TLS 1.3 on both endpoints with no version negotiation at all, where there is no downgrade surface for the sentinel to protect

Why: The version field alone is exactly what DROWN/Logjam-class attacks manipulate; the sentinel is cryptographically bound into the transcript

ADR-18

Alert-handling policy

Chosen

Fatal alert => immediate terminal state, no retry

Rejected

Attempt graceful renegotiation on some alerts

When the rejected choice is right

A TLS 1.2 implementation, where warning-level alerts and renegotiation are part of the protocol and a non-fatal alert legitimately continues the connection

Why: TLS 1.3 removed renegotiation entirely; treating any fatal alert as recoverable reintroduces undefined intermediate states

ADR-19

I/O model

Chosen

Sans-io state machine (byte buffers in/out, no socket ownership)

Rejected

Owning-socket blocking API

When the rejected choice is right

Owning-socket wins for a simple demo CLI tool prioritizing a five-line quick-start over embeddability

Why: Embeddability (custom transports, future QUIC integration, easy fixture-driven testing) — the rustls lesson

ADR-20

Error taxonomy

Chosen

TlsError enum mapping 1:1 to RFC 8446 alert descriptions

Rejected

String-based error messages

When the rejected choice is right

String errors win only in a throwaway prototype with no programmatic error handling needed

Why: Enables exhaustive match-based handling and fixture testing per alert type

ADR-21

Zeroization

Chosen

zeroize crate, Drop impl on every secret-bearing type

Rejected

Rely on Rust's default drop (no explicit zero)

When the rejected choice is right

Non-secret session state, or a platform whose allocator guarantees zero-on-free, where an explicit zeroization pass over that buffer is redundant

Why: Default drop does not guarantee memory is overwritten, only deallocated; secret residue can persist and be read via a later allocation

ADR-22

RNG source

Chosen

OS CSPRNG via rand::rngs::OsRng

Rejected

Custom PRNG

When the rejected choice is right

Non-cryptographic randomness such as retry-backoff jitter or load-spreading, where a CSPRNG's cost and entropy draw are unjustified

Why: Cryptographic randomness (ClientHello.random, ephemeral keys) must be indistinguishable from true random; rolling a custom PRNG is a well-known way to introduce a subtle predictability bug

ADR-23

Logging with secret redaction

Chosen

Structured tracing spans, redaction enforced by a type-level Debug-suppression on secret types

Rejected

Ad hoc println! debugging

When the rejected choice is right

Logging non-secret protocol metadata — handshake type, negotiated cipher, alert codes — on a code path where no key material is ever in scope

Why: Ad hoc logging is exactly how secret material leaks into logs (P12); a type-level ban is enforced even when a developer forgets

ADR-24

Testing strategy

Chosen

Property tests (proptest) + fixture-driven unit/integration + interop CI gate

Rejected

Unit tests only

When the rejected choice is right

Unit-tests-only wins in early Phase 0 skeleton work before the state machine exists to property-test

Why: Property tests catch invariant violations (I1-I13) that example-based tests miss; interop is the only real conformance oracle

ADR-25

Fuzzing

Chosen

cargo-fuzz/libFuzzer on DER parser, message parser, record layer

Rejected

No fuzzing

When the rejected choice is right

A formally-verified message parser (miTLS / HACL*-style), where machine-checked proofs of memory safety subsume the coverage fuzzing would provide

Why: These are the three untrusted-input surfaces (§3); fuzzing is the standard technique for finding parser bugs at this class (Heartbleed-lineage)

ADR-26

CI/CD

Chosen

GitHub Actions: build+test+clippy+fuzz-smoke+interop matrix per PR, nightly full fuzz

Rejected

Manual pre-release testing only

When the rejected choice is right

Manual-only wins only for a single-developer prototype not yet accepting external contributions

Why: Manual testing does not scale to the fixture and interop-matrix volume this project requires

ADR-27

Packaging/release/reproducibility

Chosen

Cargo workspace, SemVer, reproducible builds via pinned toolchain + Cargo.lock

Rejected

Unpinned floating dependency versions

When the rejected choice is right

An internal non-published experiment chasing the newest crypto-crate security fixes, where reproducibility is not yet a requirement

Why: A cryptographic library with floating dependencies risks silently picking up a compromised or regressed crate version

ADR-28

Licensing

Chosen

Dual MIT/Apache-2.0 (Rust ecosystem convention)

Rejected

GPL

When the rejected choice is right

GPL wins when the project's governance specifically requires copyleft, e.g. a project explicitly positioned against proprietary forks

Why: Matches the licensing of the audited crates it wraps (x25519-dalek, ring, etc.), avoiding license-compatibility friction

36. Alternative Architectures (Roads Not Taken)

A1 — TLS 1.2 dual-stack support.

   +----------------------+
   | Composite State      |
   | Machine (1.2 + 1.3)  |
   |  - version-branch    |
   |    at every state    |
   |  - 2x transition     |
   |    table surface     |
   +----------------------+

Winning regime: a deployment that must interoperate with legacy middleboxes or clients that never upgraded (some industrial/embedded fleets). Embodied by: OpenSSL, BoringSSL (both support 1.2 and 1.3 in one codebase). Rejected here because the composite state machine is exactly the complexity Beurdouche et al. 2015's SMACK paper showed dangerous — a version-branching state table roughly doubles the transition surface an attacker can probe for an implicit-permissive edge (ADR-02).

A2 — Formally verified implementation.

   +----------------------+       +-------------------+
   | F* Protocol Model    |  -->  | HACL*-verified     |
   | (refinement types)   |       | primitives, compiled|
   +----------------------+       | to verified C       |
                                  +-------------------+

Winning regime: a threat model demanding mathematical proof of correctness rather than empirical fixture/fuzz/interop confidence (e.g. a national-security-grade or safety-critical deployment). Embodied by: miTLS / Project Everest. Rejected here: full formal verification is a distinct, much larger research effort than a Phase-0-scoped protocol-implementation project can absorb (§33's cost tradeoff) — this project's confidence model is deliberately empirical (§28), a documented and bounded tradeoff, not an oversight.

A3 — Owning-socket blocking design.

   +----------------------+
   | TlsSocket             |
   |  owns TcpStream       |
   |  .connect()/.accept() |
   |  .read()/.write()     |
   |  blocks on I/O        |
   +----------------------+

Winning regime: a simple CLI demo or scripting use case where a five-line quick-start matters more than embeddability into a custom transport or a future async/QUIC integration. Embodied by: OpenSSL's traditional SSL*/BIO API, most textbook TLS examples. Rejected here: the sans-io state machine (ADR-19) is strictly more general — an owning-socket API can always be built as a thin adapter over a sans-io core (exactly what tls-net is, §10), but the reverse is not true without a rewrite; the rustls-versus-OpenSSL API-shape contrast (§33) is the direct precedent for this choice.

A4 — QUIC integration (TLS 1.3 as QUIC's handshake layer).

   +----------------------+       +----------------------+
   | tls-handshake         |  -->  | QUIC Packet Protection|
   | (unchanged: CH..Fin)  |       | (replaces record layer|
   |                       |       | entirely, RFC 9001)   |
   +----------------------+       +----------------------+

Winning regime: a transport already committed to QUIC (HTTP/3 and beyond) where TLS 1.3 provides only the handshake and key-derivation logic while QUIC's own packet protection (distinct framing, distinct anti-replay, distinct loss-recovery integration) replaces this project's record layer entirely. Embodied by: quinn/ rustls QUIC integration, Go's quic-go. Rejected in Phase 0: RFC 9001's integration requires exposing the key schedule's traffic secrets to an external packet-protection layer in a way this project's record-layer-owns-the-secrets design (§3) does not yet support cleanly — PhaseDeferred("RFC 9001 — Using TLS to Secure QUIC"), a real future extension point once the handshake/record-layer boundary in §3 is proven stable.
