Decisions (§9) · 23 ADRs

ADR-01

Implementation language

Chosen

C11

Rejected

Rust, C++, Python

When the rejected choice is right

When targeting a safety-critical embedded system where Rust's ownership model prevents entire classes of memory bugs; or when building a Rust-native HPC framework like Rayon

Why: MPI standard specifies a C binding with exact function signatures. ABI compatibility requires C. All production MPI runtimes are C.

ADR-02

Build system

Chosen

CMake 3.20+

Rejected

GNU Make, Bazel, Meson

When the rejected choice is right

When targeting embedded bare-metal with no CMake support — use GNU Make; or for Google-internal monorepo — use Bazel

Why: CMake is the standard for C/C++ HPC projects; used by MPICH and Open MPI. Supports cross-compilation and CTest integration.

ADR-03

Intra-node transport

Chosen

UNIX domain sockets (UDS)

Rejected

TCP loopback, shared memory only, named pipes

When the rejected choice is right

When the intra-node process count exceeds UDS connection limits, or when processes are on different hosts — use TCP

Why: UDS provides lower latency than TCP loopback (no TCP stack overhead). Named pipes are unidirectional. UDS supports passing file descriptors (needed for shmem handshake).

ADR-04

Shared memory API

Chosen

POSIX shm_open + mmap

Rejected

System V shmget, memfd_create, anonymous mmap

When the rejected choice is right

When targeting macOS only and memfd is available, or when needing anonymous mappings without filesystem namespace — use memfd_create

Why: POSIX shm is portable across Linux and macOS. Named segments are inspectable in /dev/shm for debugging. System V IPC is deprecated.

ADR-05

Inter-node transport

Chosen

TCP sockets (BSD socket API)

Rejected

RDMA/verbs (UCX/libfabric), UDP with reliability, MPI over NCCL

When the rejected choice is right

When sub-microsecond latency is required and InfiniBand hardware is available — use RDMA/verbs (MVAPICH2/UCX approach)

Why: TCP is available on every cluster without special hardware. RDMA requires InfiniBand or RoCE NICs. The transport vtable allows adding RDMA later.

ADR-06

Wire serialization

Chosen

Custom fixed-layout binary struct

Rejected

XDR, MessagePack, protobuf, Cap'n Proto

When the rejected choice is right

When interoperability with existing MPI implementations is required, or when debugging across heterogeneous clusters — use XDR or MessagePack for human-readable inspection

Why: Fixed 32-byte header has zero serialization overhead. Size is static_assert enforced. No dependency on external serialization library.

ADR-07

Wire byte order

Chosen

Network byte order (big-endian) for all multi-byte fields

Rejected

Host byte order, little-endian always

When the rejected choice is right

When all cluster nodes are the same architecture (e.g., x86-only datacenter) and max throughput matters — use host byte order with a compile-time homogeneous flag

Why: Network byte order is the universal standard for wire protocols (TCP/IP, XDR, MPI). Prevents silent data corruption on heterogeneous clusters. CI lint enforces htonl/ntohl usage.

ADR-08

Connection model

Chosen

Pre-connect all pairs at MPI_Init (Phase 0); lazy connect threshold at Phase 1+

Rejected

Connect on first send, connection pooling, shared connection broker

When the rejected choice is right

When deploying on a cluster with an existing workload manager (SLURM/PBS) — use the scheduler's launch mechanism; when SSH-based multi-node deployment is standard — use mpiexec.hydra

Why: Pre-connect guarantees MPI_Send never blocks on connection setup. Simplifies the send path. Startup cost is bounded and measurable.

ADR-09

Thread safety level

Chosen

MPI_THREAD_FUNNELED (only main thread calls MPI)

Rejected

MPI_THREAD_SINGLE, MPI_THREAD_SERIALIZED, MPI_THREAD_MULTIPLE

When the rejected choice is right

When building a high-performance multi-threaded MPI library used by OpenMP+MPI hybrid codes — use MPI_THREAD_MULTIPLE with per-communicator locking

Why: Funneled is sufficient for all Phase 0–10 use cases. THREAD_MULTIPLE requires per-operation locking throughout the match engine and transport, adding complexity before correctness is established.

ADR-10

Memory allocator

Chosen

System malloc/free (glibc)

Rejected

jemalloc, tcmalloc, custom pool allocator

When the rejected choice is right

When message sizes vary over 6+ orders of magnitude and allocation patterns are unpredictable — use jemalloc; when latency is paramount and object sizes are known at compile time — use a stack allocator

Why: System malloc is sufficient for Phase 0–5. Request pool uses a hand-rolled freelist for the hot path. External allocators add a dependency and complicate ASan integration.

ADR-11

PRQ/UMQ data structure

Chosen

Linked list (Phase 0); ring buffer for UMQ

Rejected

Lock-free queue, B-tree index, hash table

When the rejected choice is right

When lock-free queue is needed for THREAD_MULTIPLE support and message rates exceed 1M/s — use a Michael-Scott queue or Disruptor ring buffer

Why: Linked list is correct, simple, and auditable. Queue depth is bounded (I3). Lock-free structures add complexity before correctness is established.

ADR-12

Test framework

Chosen

CMocka (C unit testing, mocking support)

Rejected

Google Test, Unity, Check

When the rejected choice is right

When targeting a C++ codebase that already uses Google Test — use Google Test; when targeting embedded with no dynamic allocation — use Unity

Why: CMocka is pure C, supports mock objects for transport injection, and integrates with CTest. Google Test requires C++.

ADR-15

ADR-19

Memory error detection

Chosen

AddressSanitizer (ASan) + ThreadSanitizer (TSan)

Rejected

Valgrind/Memcheck, Electric Fence

When the rejected choice is right

When full memory-layout analysis is needed (heap profiling, full call stacks on every allocation) — use Valgrind; when targeting macOS where sanitizers have lower overhead — prefer Instruments

Why: ASan/TSan are 2–3× slower than uninstrumented code; Valgrind is 10–50×. ASan integrates with the fuzzer (AFL++ ASan target). CI runs the full conformance suite under ASan on every PR.

ADR-20

Datatype descriptor representation

Chosen

Linked list of type_map_entry_t (offset, basetype, count)

Rejected

Flat descriptor array, recursive tree

When the rejected choice is right

When the type system requires O(1) lookup by type ID and types are never nested — use a flat descriptor array

Why: Linked list naturally represents the recursive structure of derived types (type_vector of type_struct). Array requires pre-flattening. Tree traversal is the natural pack/unpack algorithm.

ADR-21

Collective algorithm selection

Chosen

Static hint table keyed by (collective, N_threshold, msg_threshold)

Rejected

Auto-tuning at runtime, hard-coded per collective

When the rejected choice is right

When workload characteristics are unknown at compile time and vary significantly across runs — use online auto-tuning (MPICH's MPIR_CVAR mechanism or MPI_T interface)

Why: Static table is auditable, reproducible, and testable. Auto-tuning requires profiling infrastructure not yet built. The table is configurable via MPI_SCRATCH_COLL_HINTS without recompilation.

ADR-22

Target platform

Chosen

Linux x86-64 (glibc 2.31+)

Rejected

Linux + RDMA, Windows (MS-MPI), macOS

When the rejected choice is right

When InfiniBand hardware is available and maximum bandwidth is required — extend to Linux+RDMA; when Windows MPI interoperability is needed — add Windows support

Why: Linux x86-64 is the universal HPC platform. All reference implementations (MPICH, Open MPI) support it first. macOS lacks memfd and has restricted POSIX shm.

Roads not taken (§35)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1 — PGAS / One-Sided-First (OpenSHMEM / UPC / GASNet)

Process 0: [Local Heap] <--symm addr--> [Shared Segment]
Process 1: [Local Heap] <--symm addr--> [Shared Segment]
                               |
              shmem_put(target_addr, src, len, pe=1)
              -- no matching recv required --
              -- target address is symmetric (same virtual addr on all PEs) --

In PGAS (Partitioned Global Address Space), every process exposes a symmetric heap — the same virtual address on every PE maps to that PE's local memory via RDMA. A shmem_put is a one-sided write with no matching receive; progress is implicit via RDMA hardware completion queues. There are no message envelopes, no tag matching, no UMQ.

Regime where it wins: Irregular, pointer-chasing access patterns (sparse matrix-vector multiply, graph analytics, stencil codes with dynamic boundaries) where the sender knows the destination address but cannot predict when the receiver will be ready. PGAS eliminates the overhead of envelope matching and receiver-side buffering entirely.

Real system embodying it: OpenSHMEM 1.5 specification (openshmem.org); reference implementation: Sandia OpenSHMEM (§5 R7). Also: UPC (Unified Parallel C), Co-Array Fortran, GASNet (Lawrence Berkeley National Laboratory).

Why rejected here: Two-sided MPI is the dominant HPC programming model and the learning objective (§2). PGAS requires symmetric memory allocation — all PEs must call shmem_malloc with the same size in the same order, a severe constraint. PGAS has no collective communication model comparable to MPI collectives. This project's goal is MPI conformance; PGAS is a different abstraction entirely.

Alt-2 — Active Messages Runtime (AM-based MPI like GASNet or early Cray SHMEM)

Sender:
  AM_send(target_pe=1, handler_fn_id=42, args..., payload)
  -- returns immediately --

Target PE 1:
  [AM handler thread wakes on network interrupt]
  -> calls registered handler_fn[42](args..., payload)
  -> handler runs in target's context; may modify local state

In an active-messages runtime, a send delivers both data AND a handler function identifier. On arrival, the target machine executes the registered handler in a lightweight context. There is no separate receive — the handler IS the receive operation. This enables completely asynchronous, handler-driven communication.

Regime where it wins: Fine-grained irregular communication where message arrivals must trigger immediate computation (e.g., distributed hash table operations, dynamic load balancing, task-based runtimes). Active messages achieve lower latency than two-sided because there is no poll-for-receive step — the hardware interrupt drives the handler.

Real system embodying it: GASNet (gasnet.lbl.gov) — the transport layer underlying UPC and Titanium. Early Cray T3D/T3E SHMEM used active-message semantics. Chapel's runtime uses GASNet AM for remote procedure calls.

Why rejected here: Active messages require a handler registration API and a trusted handler table — significantly more complex ABI than MPI's stateless send/receive. Security: a handler executing in the target's context with attacker-controlled arguments is a remote code execution vector. The MPI standard is defined in terms of two-sided matching, not active messages; building MPI semantics on top of AM adds a translation layer without simplifying the implementation.

Alt-3 — Sockets-Only Portability Layer (TCP-only, no UDS/SHM)

All ranks -> TCP loopback (127.0.0.1) for intra-node
All ranks -> TCP Ethernet for inter-node
No POSIX shared memory. No UNIX domain sockets.
Single transport: tcp.c handles all cases.

A sockets-only implementation uses TCP for all communication — both intra- and inter-node. POSIX shm and UDS are eliminated entirely. The implementation is a pure subset of BSD sockets.

Regime where it wins: Maximum portability across operating systems (Linux, macOS, Windows, AIX, Solaris) and environments (containers without shm_open access, sandboxes with restricted syscalls). A Docker container with --ipc=none cannot use shm_open; a sockets-only implementation works in any container. Also wins when the implementation must be audited and the auditor is unfamiliar with POSIX IPC.

Real system embodying it: MPICH's ch3:sock channel implements TCP sockets only, no shared memory shortcuts. Microsoft MPI also uses WinSock2 exclusively.

Why rejected here: TCP loopback latency is 50+ µs (§4) vs. UDS at 5 µs (§4) — a 10× latency penalty for intra-node communication. For shared-memory RMA (§21 Phase 9), TCP would require a server thread on the target to receive PUT messages — adding complexity and a round-trip that POSIX shm eliminates entirely. The whole point of UDS/shm is to exploit the OS's knowledge that both endpoints are on the same kernel.

Alt-4 — Task-Based Async Runtime (Charm++, HPX, Legion)

Task graph:
  [Task A: matrix_mul local_rows] --> [Reduction task at root]
        |  (on completion)
  [Task B: stencil update] --> [Halo exchange async]

Runtime: schedules tasks across PEs based on data availability.
No explicit MPI_Send/Recv -- data movement is implicit in task dependencies.

Task-based runtimes model parallel computation as a DAG of tasks with data dependencies. Communication is implicit: when Task B on PE 1 needs data produced by Task A on PE 0, the runtime automatically transfers it. There are no explicit send/receive calls.

Regime where it wins: Irregular, dynamic parallelism where the task graph is not known at compile time (adaptive mesh refinement, N-body simulations with load imbalance, sparse direct solvers). Task runtimes can overlap communication and computation automatically without the programmer reasoning about non-blocking operations. They also handle load imbalance via work stealing.

Real system embodying it: Charm++ (Illinois, charmplusplus.org); HPX (STE||AR Group, hpx.stellar-group.org); Legion (Stanford/NVIDIA, legion.stanford.edu); PaRSEC (ICL UTK).

Why rejected here: Task-based runtimes require a fundamentally different programming model — no existing MPI code runs on Charm++ without a complete rewrite. The learning objective (§2) is MPI, not task-based parallelism. Task runtimes have higher runtime overhead for bulk-synchronous workloads (matrix multiply, FFT) where the communication pattern is regular and statically known — exactly the benchmark workloads this project targets.
