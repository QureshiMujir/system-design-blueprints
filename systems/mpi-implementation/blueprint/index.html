1. Goal & Scope

1.1 What Is Being Built

This project implements a basic but standards-conformant Message Passing Interface (MPI) runtime from scratch in C. The deliverable is a shared-memory-capable MPI library — libmpi_scratch.so — exposing a subset of the MPI-3.1 standard API sufficient to run real parallel programs: matrix multiplication, parallel sorting, numerical PDE solvers, and Monte Carlo simulations. The runtime manages process spawning, rank assignment, communicator semantics, point-to-point message passing, collective operations, and non-blocking request tracking. It uses UNIX domain sockets (UDS) and POSIX shared memory for intra-node transport, and TCP sockets for inter-node transport in Phase 1+.

The implementation does NOT wrap Open MPI, MPICH, or any existing MPI distribution. Every data structure, every protocol decision, every wire format, and every synchronization primitive is designed and implemented from the ground up against the MPI-3.1 specification.

1.2 System Boundaries

Dimension Detail
Provides libmpi_scratch.so with a MPI-3.1 subset C API; pmgrd process manager daemon; mpirun_scratch launcher; conformance test harness (20+ programs)

1.3 Non-Goals

  • This project is not a production MPI runtime for cluster workloads.
  • Performance parity with MPICH or Open MPI is not a goal; correctness and pedagogical clarity are.
  • Support for more than 1,024 ranks (lazy connect) is not a goal.
  • MPI-4.0 features beyond the ULFM fault-tolerance stub (Phase 10 / §22) are not a goal.

1.4 Deployment Model

The library is deployed as a single-node shared library for Phases 0–2 (intra-process communication via UDS). From Phase 1 onward, multi-node deployment over TCP loopback or LAN is supported. The process manager daemon (pmgrd) runs on a head node or the local machine; MPI processes are spawned by mpirun_scratch. No container runtime or MPI-over-container support is required.

1.5 Target Users

Graduate students and engineers studying HPC systems; developers building parallel applications who want to understand MPI semantics at the implementation level; candidates preparing for systems design interviews at HPC-oriented organizations.

1.9 Recommended Language

C (C11) is the only correct choice for this domain. Rationale:

  • The MPI standard specifies a C binding with exact function signatures. Implementing in C means the library is ABI-compatible with programs compiled against standard MPI headers.
  • All production MPI runtimes (Open MPI, MPICH, MVAPICH2) are implemented in C. Studying the standard through C reveals every implicit assumption about memory layout, alignment, and pointer semantics.
  • Rust would be a valid second choice for safety guarantees but cannot export the exact C ABI without extensive unsafe boundaries. Python is unsuitable for performance-critical transport.

1.10 Prerequisites

The reader must already understand:

  • C11: struct layout, pointer arithmetic, void * semantics, function pointers, restrict.
  • POSIX APIs: fork(), exec(), socket(), bind(), connect(), send(), recv(), shm_open(), mmap(), sem_open(), pthread_mutex_lock().
  • Operating systems: process vs. thread, virtual memory, file descriptors, signals, pipes.
  • Computer architecture: cache lines, memory barriers (__sync_synchronize, __atomic_*), NUMA topology basics.
  • Networking: TCP socket lifecycle, select()/poll()/epoll(), endianness.
  • Linear algebra: matrix operations (needed to write and interpret conformance benchmarks).
  • MPI user-level experience: having written at least one MPI program using Open MPI or MPICH.

2. Why Build This

2.1 What You Learn That No Other Project Teaches

Building an MPI runtime from scratch forces mastery of a uniquely dense intersection of systems concerns:

Process management at scale. Spawning N processes, distributing rank-to-socket address mappings, synchronizing startup across all ranks before MPI_Init returns — this is a distributed systems bootstrap problem with no off-the-shelf solution. You implement your own process manager daemon, your own rank table distribution protocol, and your own barrier to confirm all ranks are alive.

Message matching semantics. MPI's matching rules (source rank, tag, communicator context ID) create a three-dimensional matching space. Implementing the unexpected message queue — where a message arrives before the receiver posts a MPI_Recv — forces you to reason about ordering guarantees, memory reclamation, and the ABA problem in lock-free queues.

Collective algorithm design. There is no single correct algorithm for MPI_Bcast. A binomial tree has O(log N) latency. A flat tree saturates the root's bandwidth. Recursive halving-doubling achieves optimal bandwidth for MPI_Allreduce. Implementing these algorithms and benchmarking the crossover points teaches algorithm engineering that applies directly to distributed systems design.

Derived datatypes and serialization. MPI's derived datatype system (MPI_Type_vector, MPI_Type_struct, MPI_Type_indexed) is a portable description of non-contiguous memory layouts. Implementing the pack/unpack engine for these types is equivalent to implementing a zero-copy serialization system with scatter-gather I/O.

One-sided RMA. MPI_Put / MPI_Get over shared memory windows with epoch-based synchronization (MPI_Win_fence, MPI_Win_lock) introduces the full complexity of memory consistency models and distributed cache coherence — concepts that underlie every modern distributed key-value store.

2.3 Calibration Value

After completing this project, every subsequent distributed systems project will be evaluated against a much higher baseline. You will instinctively ask:

  • What is the message-passing pattern (point-to-point vs. collective)?
  • What is the matching semantic (ordered vs. unordered delivery)?
  • What is the synchronization cost at barriers?
  • What is the effective bandwidth utilization?

These questions — native to MPI programmers — transfer directly to gRPC pipeline design, Kafka consumer group coordination, and Kubernetes pod scheduling.

2.4 What Mastery Looks Like

Completing all phases produces demonstrable, phase-anchored skills:

  • Implementing a two-queue message matcher (Phase 0 / Phase 1): You can build a posted-receive queue and unexpected-message queue from scratch, reason about FIFO ordering per (source, tag, comm) triple, and handle queue overflow correctly.
  • Selecting eager vs. rendezvous by message size (Phase 2 / §14): You can derive the crossover threshold from the α-β cost model, implement both protocol paths, and measure empirically that the threshold is correctly placed.
  • Deriving collective algorithm complexity from the α-β model (Phase 3 / §15): You can write out the step-complexity and bandwidth-cost of binomial tree broadcast and recursive halving-doubling allreduce, select the correct algorithm for a given (N, message_size) pair, and verify the selection with microbenchmarks.
  • Building a pack/unpack engine for non-contiguous memory (Phase 7 / §19): You can implement MPI_Type_vector and MPI_Type_struct pack/unpack, handle nested derived types, and verify correctness against the MPI-3.1 §4 datatype layout rules.
  • Implementing epoch-based RMA synchronization (Phase 9 / §21): You can implement MPI_Win_fence, MPI_Win_lock/MPI_Win_unlock, reason about the active-target vs. passive-target synchronization models, and prove memory visibility across ranks.
  • Diagnosing deadlock and UMQ overflow in a live MPI job (Phase 10 / §22): You can identify deadlock from send/recv ordering mismatches, set MPI_SCRATCH_UMQ_DEPTH to avoid overflow, and use MPI_Errhandler to capture and log faults without aborting the job.

3.2 Subsystem Descriptions

MPI API Shim Layer. This is the public surface of the library. Every function exported from libmpi_scratch.so lives here. The shim validates arguments (null buffer checks, valid rank bounds, valid communicator handles), resolves MPI_Datatype sizes by querying the datatype registry, and calls into the match engine or transport layer. It also sets errno-style error codes and invokes the registered error handler on failure.

Communicator Manager. A communicator (MPI_Comm) is a context: a group of ranks plus a unique integer context ID. MPI_COMM_WORLD is context 0. MPI_Comm_split creates new contexts by collective agreement. The comm manager maintains the group membership table and context ID allocator. Every message carries a context ID in its envelope to prevent cross-communicator message leakage.

Match Engine. MPI message matching is not FIFO in the global sense — it is FIFO per (source, tag, communicator) triple. The match engine maintains two queues: the posted receive queue (PRQ) for MPI_Recv calls waiting for data, and the unexpected message queue (UMQ) for messages that arrived before a matching MPI_Recv. On MPI_Send, the engine checks the PRQ; on MPI_Recv, it checks the UMQ. This dual-queue design is the core of every MPI implementation.

Collective Engine. Implements tree-based and ring-based algorithms for each collective. Algorithm selection is runtime-configurable: a hint table maps (collective, N, message_size) to algorithm. The engine uses only the point-to-point send/recv interface — no collective-specific transport shortcuts in Phase 0. This ensures correctness before optimization.

Transport Abstraction Layer. A vtable (function pointer struct) abstracts the transport. Each entry in the rank table has an associated transport pointer. Intra-node ranks use UDS; inter-node ranks use TCP. The abstraction allows future addition of shared-memory (shmem) and RDMA transports without changing upper layers.

Intra-Node Transport (UDS). UNIX domain sockets provide kernel-mediated IPC with lower overhead than TCP loopback. For large messages (above a configurable threshold, default 64 KB), the transport switches to POSIX shared memory (shm_open + mmap) with a semaphore handshake — avoiding two kernel copies.

Inter-Node Transport (TCP). A persistent TCP connection is established per rank pair during MPI_Init. Nagle's algorithm is disabled (TCP_NODELAY) to prevent latency spikes on small messages. The connection table is populated from the rank table distributed by pmgrd.

Process Manager Daemon (pmgrd). The daemon is the equivalent of Open MPI's orted or MPICH's hydra. It reads a hostfile, forks child processes (or SSH-es to remote nodes), passes rank assignments and address tables via the control channel, and collects exit codes. It signals all children on SIGTERM and aggregates non-zero exit codes as the launcher's exit code.

Runtime State. Each MPI process maintains a singleton mpi_world_t structure (allocated during MPI_Init). This contains the rank, world size, communicator table, transport table, request pool, unexpected queue, posted receive queue, datatype registry, and error handler table. All MPI operations access state through this struct rather than global variables, enabling future support for multi-threaded MPI (MPI_THREAD_MULTIPLE).

6. Design Principles

The following 12 principles govern every design and implementation decision in this project. Each principle is stated as a precise rule, with its tradeoff, operational implication, and the failure mode that results from violating it. Inline citations refer to the Required Reading table in §5.

P1 — Specification Fidelity Over Performance

Rule: Every observable behavior of the library must match the MPI-3.1 standard specification exactly, even when a deviation would improve performance. Performance optimizations are permitted only when the specification explicitly allows latitude (e.g., algorithm choice for collectives). [MPI-3.1 (S1); MPICH as reference implementation (R1)]

Tradeoff: Strict adherence occasionally forces less efficient code paths (e.g., FIFO ordering in the match engine even when a LIFO search would reduce cache misses).

Operational implication: Every function docstring must cite the MPI-3.1 section it implements. A conformance test must exist before any optimization lands.

Violation consequence: Programs that rely on standard behavior will silently produce wrong results or deadlock. Cross-implementation portability is destroyed. The library cannot be used as a teaching tool because it teaches wrong semantics.

P2 — Layered Architecture with Clean Interfaces

Rule: The system is organized in layers: API shim → match engine → transport abstraction → transport implementation. Each layer communicates with the layer below it only through a defined interface (vtable or function pointer struct). No layer may call into a non-adjacent layer. [ADR-02 layered architecture; Gropp 1996 ADI design (P2)]

Tradeoff: Indirection through vtables costs one pointer dereference per call. This is negligible at message granularity but must be considered for sub-microsecond paths.

Operational implication: Adding a new transport (e.g., RDMA in Phase 11) requires implementing only the transport vtable. All layers above are unaffected.

Violation consequence: Cross-layer coupling makes unit testing impossible, transport replacement breaks the entire stack, and correctness bugs in the transport layer corrupt match engine state.

P3 — Protocol Costs Are Modeled Before Implementation

Rule: Before implementing any communication protocol, the designer must write out the α-β cost model (or LogGP model for long messages) for the proposed algorithm and compare it against alternatives. The cost model must be included in the design note for that protocol. [P11 LogGP model (Alexandrov et al. 1995); ADR-06]

Tradeoff: Protocol analysis adds upfront time. The benefit is that algorithm selection is defensible and the crossover thresholds (e.g., eager vs. rendezvous) are derived, not guessed.

Operational implication: The eager/rendezvous threshold in §14 and the collective algorithm selection table in §8.5 are both derived from written cost models checked into the design notes directory.

Violation consequence: Algorithm selection becomes cargo-culted. The threshold is either too low (wasting rendezvous setup overhead for small messages) or too high (blowing UMQ memory for large messages), causing MPI_ERR_INTERN at runtime.

P4 — No Mutable Global State

Rule: All runtime state is owned by the mpi_world_t struct, which is allocated during MPI_Init and freed during MPI_Finalize. No module-level global variables are permitted. Functions that need runtime state receive a pointer to mpi_world_t. [ADR-01 no globals]

Tradeoff: Every function signature is slightly longer. Internal functions carry an extra parameter.

Operational implication: Two MPI instances can coexist in the same process (for testing). The state machine is easily inspectable from a debugger by printing the struct.

Violation consequence: Global state prevents multi-instance testing, makes thread safety analysis impossible, and introduces initialization-order bugs that are nearly impossible to reproduce in CI.

P5 — Message Ordering Is FIFO Per (Source, Tag, Communicator)

Rule: The match engine guarantees FIFO delivery order within a (source rank, tag, communicator context ID) triple, exactly as required by MPI-3.1 §3.5. It does NOT guarantee FIFO ordering across different triples. The PRQ and UMQ are both searched in insertion order within a triple. [P1 MPI-3.1 §3.5 ordering (S1)]

Tradeoff: FIFO search in the PRQ requires scanning from the head; a skip-list or hash would be faster for large queues but adds implementation complexity disproportionate to Phase 0 requirements.

Operational implication: The conformance test phase1/ordering.c sends multiple messages with the same (source, tag, comm) and verifies receipt order. This test is a regression gate.

Violation consequence: Programs that rely on ordering (e.g., a distributed FIFO work queue built on MPI) silently corrupt results. The violation is extremely difficult to debug because the failure is intermittent and ordering-dependent.

P6 — Transport Abstraction Isolates Wire Format from Matching Semantics

Rule: The match engine knows nothing about the physical transport (UDS, TCP, shared memory). The transport layer knows nothing about message matching. The wire header carries only what is needed for routing and demultiplexing: magic, context_id, source rank, dest rank, tag, message length, and message type. [P2 Gropp 1996 ADI design (P2)]

Tradeoff: A tight coupling between transport and matcher could reduce copies (e.g., writing directly into the PRQ buffer). This optimization is PhaseDeferred to Phase 6.

Operational implication: The UDS and TCP transports share the same wire header struct. The match engine is tested with a mock transport that injects headers without any real socket I/O.

Violation consequence: Transport-specific matching logic prevents swapping transports. Testing the match engine requires a real network, making CI fragile and slow.

P7 — Errors Are Returned, Not Crashed Upon

Rule: Every function that can fail returns an MPI error code. Internal functions return -1 and set a thread-local error string. No function calls abort() or exit() except MPI_Abort. The registered error handler is invoked on every error before returning to the caller. [MPI-3.1 §8.3 error handling (S1)]

Tradeoff: Return-code-based error handling requires disciplined checking at every call site. The compiler cannot enforce it. goto cleanup patterns are required in every function with multiple failure paths.

Operational implication: The conformance test harness sets a custom error handler that writes errors to a log file instead of aborting, allowing the full test suite to run even when individual tests inject errors.

Violation consequence: A library that calls abort() on any error is unusable in production. A job scheduler running 1,000 ranks cannot tolerate a single rank calling abort() — it kills the entire job without leaving a diagnostic trace.

P8 — Connections Are Pre-Established at MPI_Init

Rule: All data connections between rank pairs are established during MPI_Init (Phase 0: all-to-all; Phase 1+: lazy connect up to a configurable threshold). By the time MPI_Init returns, no subsequent MPI_Send or MPI_Recv call may block on connection establishment. [ADR-08 pre-connect]

Tradeoff: Pre-connecting all N×(N-1)/2 pairs at init time costs O(N²) file descriptors and startup latency. This is the reason §4 caps practical N at 64 for all-to-all and 1,024 for lazy connect.

Operational implication: MPI_Init startup time is a hard requirement (§4 table). A test that measures MPI_Init latency for N=4 and N=64 is part of Phase 0 acceptance criteria.

Violation consequence: Connection establishment during MPI_Send introduces latency spikes that corrupt timing-sensitive conformance benchmarks. It also creates a deadlock risk if two ranks simultaneously attempt to connect to each other.

P9 — Unexpected Message Queue Has a Hard Depth Limit

Rule: The UMQ has a maximum depth of MPI_SCRATCH_UMQ_DEPTH (default 4,096). When the limit is reached, the sender is blocked (backpressure) rather than allowing unbounded memory growth. The depth watermark is emitted as a gauge metric. [P4 Brightwell 2004 UMQ overflow analysis (P4)]

Tradeoff: Blocking the sender on UMQ overflow introduces latency on the send side. The alternative — dropping messages or growing the queue unboundedly — is worse: silent data loss or OOM.

Operational implication: The environment variable MPI_SCRATCH_UMQ_DEPTH allows tuning without recompilation. The Phase 2 stress test deliberately overflows the UMQ and verifies that backpressure engages without deadlock.

Violation consequence: Without a depth limit, a sender that sends faster than the receiver processes will exhaust process memory. This is the canonical UMQ overflow failure mode documented in Brightwell 2004.

P10 — Shared Memory Segments Use Collision-Resistant Names

Rule: POSIX shared memory segment names include the pmgrd PID and a 64-bit nonce generated at MPI_Init time. This prevents co-tenant collision on multi-user systems. Segment names follow the pattern /mpi_scratch_<pmgrd_pid>_<nonce>_<rank_pair>. [ADR-04 POSIX shm (S2); ADR-10]

Tradeoff: Longer segment names are harder to read in /dev/shm listings but are operationally required on shared systems (HPC login nodes).

Operational implication: The system invariant I11 enforces this at shm_open time. A test runs two MPI jobs simultaneously on the same node and verifies no shared memory name collision occurs.

Violation consequence: Two MPI jobs running simultaneously on the same node silently share memory segments. This produces data corruption that is reproducible only on multi-user systems, making it nearly impossible to debug.

P11 — Wire Protocol Is Version-Stamped and Magic-Checked

Rule: Every wire message begins with a 4-byte magic number (0x4D504921, ASCII MPI!) and a 1-byte protocol version field. The receiver validates both before parsing any other field. A magic mismatch closes the connection and marks the remote rank as failed. [ADR-07 network byte order; ADR-06]

Tradeoff: Four bytes of overhead per message. At 8-byte payload messages (minimum latency benchmark), this is 33% overhead. This is acceptable for correctness guarantees.

Operational implication: The magic check is the first line of transport_recv_header(). The CI lint rule enforces that no struct-to-wire assignment bypasses htonl. System invariant I4 and I5 enforce this at runtime and build time respectively.

Violation consequence: A misrouted TCP connection (e.g., a stray connection from a port scanner or another MPI job) passes garbage data into the match engine, corrupting the PRQ or UMQ with no error indication.

P12 — MPI_Finalize Is a Collective Operation

Rule: MPI_Finalize is not a unilateral shutdown. It sends MSG_FIN to all peers and waits for MSG_FIN from all N-1 peers before closing sockets. A timeout (MPI_SCRATCH_FINALIZE_TIMEOUT_SEC, default 30s) triggers MPI_Abort if not all peers finalize. [MPI-3.1 §8.7 finalize semantics (S1)]

Tradeoff: Blocking finalize adds latency at job end. For very large N, the all-to-all MSG_FIN exchange takes O(N) time. This is acceptable because job end is not latency-critical.

Operational implication: System invariant I8 enforces this. The finalize conformance test launches 4 ranks, has rank 0 finish its work first, and verifies that rank 0's MPI_Finalize does not return until all other ranks also call MPI_Finalize.

Violation consequence: A rank that closes its sockets before peers finish causes SIGPIPE or ECONNRESET on active sends in other ranks. The job appears to succeed but the last messages are silently lost, corrupting numerical results with no error indication.

8. Domain Model / Protocol / Data Model

8.1 Fundamental Concepts

An MPI job is a fixed set of N processes called ranks (numbered 0 through N-1). Ranks communicate by sending and receiving messages. A message is identified by a five-tuple: (source rank, destination rank, tag, communicator context ID, message length). The communicator is a named scope for communication: MPI_COMM_WORLD is the default communicator containing all N ranks. Additional communicators can be created by collective agreement (§17 / Phase 5).

Envelope vs. Body. The message envelope contains the matching fields (source, dest, tag, context_id). The body contains the actual data bytes. The match engine operates on envelopes; the transport layer moves both together (for eager messages) or separately (for rendezvous).

Eager vs. Rendezvous. For messages below MPI_EAGER_LIMIT (default 64 KB), the sender transmits header+body immediately without waiting for receiver readiness. For larger messages, the sender transmits only the header (a rendezvous request); the receiver replies with a ready-to-receive acknowledgement; then the sender transmits the body. This prevents large messages from consuming UMQ memory.

Request Lifecycle. Non-blocking operations return an MPI_Request handle. The handle transitions through states: REQ_PENDING → REQ_IN_PROGRESS → REQ_COMPLETED. MPI_Wait blocks until REQ_COMPLETED. MPI_Test returns immediately with a flag. MPI_Cancel sets REQ_CANCELLED if the message has not yet been matched.

Datatype. Every send/recv specifies an MPI_Datatype describing the memory layout of each element. Basic types (MPI_INT, MPI_DOUBLE) map directly to C primitives. Derived types (MPI_Type_vector, MPI_Type_struct) describe non-contiguous layouts. The datatype registry maps handles to size/extent descriptors.

8.2 Wire Protocol

Every message transmitted over UDS or TCP begins with a fixed 32-byte header (mpi_wire_header_t), enforced by static_assert(sizeof(mpi_wire_header_t) == 32, ...):

Byte offset   Field                  Type        Description
──────────────────────────────────────────────────────────────
  0           magic                  uint32_t    0x4D504921 ("MPI!")
  4           version                uint8_t     Protocol version (current: 1)
  5           msg_type               uint8_t     MSG_DATA, MSG_ACK, MSG_FIN, MSG_ERR
  6           flags                  uint8_t     EAGER(0x01), RENDEZVOUS_REQ(0x02), RENDEZVOUS_ACK(0x04)
  7           _pad                   uint8_t     Reserved, must be zero
  8           context_id             uint32_t    Communicator context ID
 12           source_rank            uint32_t    Sending rank
 16           dest_rank              uint32_t    Destination rank
 20           tag                    int32_t     Message tag (MPI_ANY_TAG = -1)
 24           msg_length             uint32_t    Body length in bytes (0 for control messages)
 28           request_id             uint32_t    Matches rendezvous req to ack; 0 for eager

All multi-byte fields are stored in network byte order (big-endian). The sender calls mpi_wire_header_hton() before write; the receiver calls mpi_wire_header_ntoh() after read. This is enforced by a CI lint rule (I5).

8.3 Process Manager Protocol

pmgrd uses a simple line-oriented control protocol over a UNIX domain socket (control channel, distinct from data channels). The protocol has four message types:

Direction Message Format Semantics
pmgrd → rank RANK_TABLE <N> <json_array> JSON Delivers the rank→(host, port, pid) table to each spawned process
rank → pmgrd RANK_READY <rank> Text Rank has opened all data connections and is ready
pmgrd → all GO Text Sent when all N ranks have sent RANK_READY; triggers return from MPI_Init
rank → pmgrd EXIT <rank> <exit_code> Text Rank is exiting; pmgrd aggregates exit codes

The control channel uses SOCK_STREAM. Each message is terminated by \n. pmgrd runs an event loop (poll) on all N control sockets plus its own stdin until all ranks exit.

8.4 Matching State Machine

The match engine implements a finite state machine with two queues:

  MPI_Send called                           MPI_Recv called
       │                                         │
       ▼                                         ▼
  Search PRQ for matching recv            Search UMQ for matching msg
       │                                         │
    Found? ──YES──► copy data ◄──YES──── Found?
       │                                         │
      NO                                        NO
       │                                         │
       ▼                                         ▼
  Receive from transport                  Enqueue in PRQ (wait for msg)
       │
       ▼
  Match against PRQ
       │
    Found? ──YES──► deliver, remove from PRQ
       │
      NO
       │
       ▼
  Enqueue in UMQ (unexpected arrival)

The PRQ is a linked list of mpi_posted_recv_t structs. The UMQ is a ring buffer of mpi_unexp_msg_t structs bounded by MPI_SCRATCH_UMQ_DEPTH. Both are searched linearly for Phase 0; hash-indexed search is PhaseDeferred to Phase 6.

Wildcard matching: MPI_ANY_SOURCE (source_rank = -1) matches any source. MPI_ANY_TAG (tag = -1) matches any tag. Context_id is never wildcarded.

MPI_Bcast Binomial tree O(log N) O(log N · α) O(log N · m/β) Small messages, all N

8.6 Worked Example: MPI_Allreduce with 4 Ranks

Scenario: 4 ranks each hold a local double value. Goal: all ranks end with the sum of all 4 values.

Phase 0 (flat reduce + broadcast, for pedagogical simplicity):

  1. Ranks 1, 2, 3 each send their value to rank 0 (3 × MPI_Send).
  2. Rank 0 receives 3 values (3 × MPI_Recv), adds them to its own value.
  3. Rank 0 broadcasts the result to ranks 1, 2, 3 (MPI_Bcast = 3 × MPI_Send from rank 0).

Total messages: 6. Latency: 2 × (1 × α + 8 bytes/β). Bandwidth: 6 × 8 bytes.

Phase 4 (recursive halving-doubling, optimal):

Step 1: Rank 0 ↔ Rank 2 exchange and accumulate. Rank 1 ↔ Rank 3 exchange and accumulate. Step 2: Rank 0 ↔ Rank 1 exchange and accumulate. Rank 2 ↔ Rank 3 exchange and accumulate.

After 2 steps (log₂ 4 = 2), all ranks hold the global sum. Total messages: 8 (4 sends + 4 recvs). Latency: 2 × α. Bandwidth: 2 × 8 bytes per rank.

Crossover: The Phase 4 algorithm is faster for N ≥ 4 and any message size. The Phase 0 algorithm ships first because correctness must be verified before the optimization is introduced.

All types declared in include/mpi_types.h. No function bodies appear here — only struct/enum signatures with per-field semantic annotations. Function pointer slots in vtables carry a 2-line comment (purpose + precondition/postcondition); no body.

§11.1 mpi_world_t — Global World State

Ownership: single owner (runtime/world.c) | Mutation: init/finalize only, then read-only | Concurrency: read-shared after MPI_Init; no concurrent mutation | Serialization: never serialized

/* mpi_world_t — singleton; one instance per process, allocated in MPI_Init */
typedef struct mpi_world_t {
    int            rank;            /* this process's rank in MPI_COMM_WORLD; immutable post-init */
    int            size;            /* total number of ranks; immutable post-init */
    rank_table_t  *rank_table;      /* heap-allocated; owned here; freed in MPI_Finalize */
    transport_ops_t transport;      /* vtable copy; backends fill at init; immutable post-init */
    mpi_comm_t    *comm_world;      /* pointer into comm_table[0]; not owned (comm_table owns) */
    struct {
        int        fd;              /* connected socket to pmgrd; owned; closed in Finalize */
        char       addr[64];        /* pmgrd address string (e.g., "127.0.0.1:7777\0") */
    } pmgr;                         /* process-manager connection; init-time only after handshake */
    struct {
        void      *pool_mem;        /* base of request_pool slab; owned; freed in Finalize */
        size_t     pool_sz;         /* byte size of the slab; set at init; immutable post-init */
    } req_pool;                     /* backing storage for mpi_request_t freelist */
    int            initialized;     /* 0 = pre-init, 1 = active, 2 = finalized; read by all */
    int            thread_level;    /* MPI_THREAD_* constant negotiated at MPI_Init_thread */
} mpi_world_t;

§11.2 mpi_comm_t — Communicator Descriptor

Ownership: comm_table (runtime/comm_table.c) | Mutation: MPI_Comm_dup creates new slot; MPI_Comm_free decrements refcount | Concurrency: refcount modified atomically; other fields immutable after creation | Serialization: comm ID only (4 bytes) transmitted in wire header

/* mpi_comm_t — one entry per active communicator; MPI_COMM_WORLD is index 0 */
typedef struct mpi_comm_t {
    int            comm_id;         /* unique integer ID; MPI_COMM_WORLD = 0 */
    int            rank;            /* caller's rank within this communicator */
    int            size;            /* number of ranks in this communicator */
    int           *rank_map;        /* rank_map[local] = global_rank; heap; owned here */
    _Atomic int    refcount;        /* incremented by Comm_dup; freed when hits 0 */
    mpi_comm_t    *parent;          /* NULL for MPI_COMM_WORLD; else the source comm */
    prq_entry_t   *prq_head;        /* head of posted-receive queue for this comm */
    umq_entry_t   *umq_head;        /* head of unexpected-message queue for this comm */
} mpi_comm_t;

§11.3 rank_entry_t / rank_table_t — Rank Address Registry

Ownership: mpi_world_t.rank_table | Mutation: write-once at MPI_Init; read-only thereafter | Concurrency: safe to read concurrently after init | Serialization: transmitted in pmgrd manifest (packed binary)

/* rank_entry_t — network address of one rank; populated from pmgrd manifest */
typedef struct rank_entry_t {
    int            rank;            /* global rank index */
    char           host[256];       /* null-terminated hostname or IP string */
    uint16_t       port;            /* TCP listen port for this rank */
    int            local_rank;      /* rank within same host (-1 = remote) */
    int            conn_fd;         /* established TCP/UDS socket fd; -1 = not connected */
} rank_entry_t;

/* rank_table_t — flat array of all rank descriptors */
typedef struct rank_table_t {
    rank_entry_t  *entries;         /* heap array [0..size-1]; owned here */
    int            size;            /* number of entries == MPI_COMM_WORLD size */
} rank_table_t;

§11.4 transport_ops_t — Transport Vtable

Ownership: embedded by value in mpi_world_t | Mutation: filled once during transport_init; immutable thereafter | Concurrency: all function pointers read-only after init | Serialization: never serialized

/* transport_ops_t — pluggable transport backend; all functions are non-NULL post-init */
typedef struct transport_ops_t {
    /* connect_all — establish connections to all remote ranks.
     * Pre: rank_table fully populated. Post: all rank_entry_t.conn_fd valid. */
    int  (*connect_all)(mpi_world_t *world);

    /* send_wire — send exactly len bytes from buf to rank dest.
     * Pre: conn_fd[dest] valid. Post: all bytes enqueued or error returned. */
    int  (*send_wire)(mpi_world_t *world, int dest, const void *buf, size_t len);

    /* recv_wire — receive exactly len bytes from rank src into buf.
     * Pre: conn_fd[src] valid. Post: buf filled or error returned. */
    int  (*recv_wire)(mpi_world_t *world, int src, void *buf, size_t len);

    /* poll_any — non-blocking check for any incoming data across all fds.
     * Pre: none. Post: returns rank of ready fd, or -1 if none ready. */
    int  (*poll_any)(mpi_world_t *world);

    /* teardown — close all connections and release transport resources.
     * Pre: MPI_Finalize in progress. Post: all fds closed; no further calls valid. */
    void (*teardown)(mpi_world_t *world);
} transport_ops_t;

§11.5 mpi_wire_header_t — On-Wire Message Header

Ownership: stack-allocated at send/recv callsite; not heap-owned | Mutation: filled by sender; read by receiver; never mutated in flight | Concurrency: no sharing; one header per in-flight message | Serialization: transmitted verbatim; byte-order enforced by htonl/ntohl at boundary

/* mpi_wire_header_t — fixed 32-byte header prepended to every message on the wire */
typedef struct __attribute__((packed)) mpi_wire_header_t {
    uint32_t   magic;       /* 0x4D504921 ("MPI!"); receiver validates before processing */
    uint32_t   version;     /* protocol version; currently 1; mismatch → MPI_ERR_INTERN */
    int32_t    src_rank;    /* sender's global rank; network byte order */
    int32_t    dst_rank;    /* destination global rank; network byte order */
    int32_t    tag;         /* message tag; MPI_ANY_TAG sentinel = -1 */
    int32_t    comm_id;     /* communicator ID; MPI_COMM_WORLD = 0 */
    uint32_t   payload_len; /* byte length of payload following this header */
    uint32_t   checksum;    /* CRC32 of the payload bytes; 0 = disabled */
} mpi_wire_header_t;

_Static_assert(sizeof(mpi_wire_header_t) == 32,
               "mpi_wire_header_t must be exactly 32 bytes");

§11.6 mpi_envelope_t / prq_entry_t / umq_entry_t — Queue Entries

Ownership: heap-allocated by match engine; freed on successful match | Mutation: enqueue writes all fields; dequeue reads; no in-place mutation | Concurrency: PRQ/UMQ protected by per-comm mutex (Phase 0 funneled) | Serialization: envelope fields echoed verbatim from wire header

/* mpi_envelope_t — message-matching key extracted from wire header or post call */
typedef struct mpi_envelope_t {
    int  src_rank;   /* MPI_ANY_SOURCE (-1) permitted in posted receives */
    int  dst_rank;   /* always concrete (the local rank) */
    int  tag;        /* MPI_ANY_TAG (-1) permitted in posted receives */
    int  comm_id;    /* must match exactly */
} mpi_envelope_t;

/* prq_entry_t — one posted-receive request waiting for a matching message */
typedef struct prq_entry_t {
    mpi_envelope_t  envelope;   /* match key; wildcards allowed */
    void           *buf;        /* application-provided receive buffer; not owned */
    size_t          count;      /* element count (in units of datatype) */
    int             datatype;   /* MPI datatype handle */
    mpi_request_t  *request;    /* associated request object; owned by request_pool */
    prq_entry_t    *next;       /* intrusive linked list; NULL = end of queue */
} prq_entry_t;

/* umq_entry_t — one arrived message with no matching posted receive */
typedef struct umq_entry_t {
    mpi_envelope_t  envelope;   /* match key from wire header; no wildcards */
    void           *payload;    /* heap copy of message payload; owned here */
    size_t          payload_len;/* byte size of payload */
    umq_entry_t    *next;       /* intrusive linked list; NULL = end of queue */
} umq_entry_t;

§11.7 mpi_request_t / request_pool_t — Non-Blocking Request Handles

Ownership: request_pool_t freelist owns backing memory | Mutation: status/flags updated by progress engine; user calls MPI_Wait to consume | Concurrency: status field updated atomically; other fields immutable after MPI_Isend/Irecv | Serialization: request handle (pointer) never serialized; opaque to application

/* request_state_t — lifecycle of a non-blocking operation */
typedef enum request_state_t {
    REQ_INACTIVE  = 0,   /* slot is free in the pool */
    REQ_PENDING   = 1,   /* operation posted; completion not yet signaled */
    REQ_COMPLETE  = 2,   /* operation complete; MPI_Wait may harvest */
    REQ_CANCELLED = 3,   /* MPI_Cancel called; no completion event */
} request_state_t;

/* mpi_request_t — handle returned by MPI_Isend / MPI_Irecv */
typedef struct mpi_request_t {
    _Atomic request_state_t  state;     /* updated by progress engine; read by MPI_Wait */
    mpi_envelope_t           envelope;  /* copy of matching envelope */
    void                    *buf;       /* app buffer (recv: filled on complete; send: read-only) */
    size_t                   count;     /* element count */
    int                      datatype;  /* MPI datatype handle */
    int                      is_send;   /* 1 = send request, 0 = recv request */
    mpi_request_t           *pool_next; /* freelist linkage; NULL when in use */
} mpi_request_t;

/* request_pool_t — fixed-size freelist of request objects (no malloc on hot path) */
typedef struct request_pool_t {
    mpi_request_t *slots;       /* flat slab of REQ_POOL_SIZE objects; owned by world */
    mpi_request_t *free_head;   /* head of freelist; NULL = pool exhausted */
    int            capacity;    /* total number of slots (compile-time constant) */
    int            in_use;      /* currently active (not-free) slots */
} request_pool_t;

12. Phase 0 — Process Model and Bootstrap

12.1 Objectives

Stand up the minimum viable MPI runtime on a single Linux host:

  • Implement pmgrd: a process-manager daemon that fork+exec's N rank processes, distributes the rank address table, and coordinates the ALL_READY barrier before releasing ranks into MPI_Init.
  • Author the ABI header (mpi_scratch.h) so rank processes link against libmpi_scratch.so with signatures matching MPI-3.1.
  • Establish the UDS transport: one bidirectional SOCK_STREAM socket per rank-pair, pre-connected during MPI_Init (P8, ADR-03).
  • Implement blocking point-to-point: MPI_Send and MPI_Recv over the UDS backend.
  • Implement the dissemination barrier: MPI_Barrier using ⌈log₂N⌉ rounds of pairwise message exchange.
  • Package the above as libmpi_scratch.so and ship a minimal mpirun_scratch launcher.

12.2 Detailed Implementation Steps

Step 1 — pmgrd fork+exec model (P4, ADR-08). mpirun_scratch calls fork() N times; each child exec()s the user binary with environment variables MPI_SCRATCH_RANK=<r>, MPI_SCRATCH_SIZE=<N>, MPI_SCRATCH_PMGRD_ADDR=<unix_socket_path>. pmgrd opens a control-channel SOCK_STREAM server; each rank connects on startup. (ADR-03 — UDS for intra-node control; ADR-08 — pre-connect model.)

Step 2 — MPI_Init eleven-step sequence (P8, I6, I9)

The canonical bootstrap sequence is:

1.  Validate: argc/argv non-NULL or both NULL (P1 §4.1 allows NULL on some platforms).
2.  Allocate mpi_world_t on the heap; zero-initialise.            (P4 no globals)
3.  Read MPI_SCRATCH_RANK / MPI_SCRATCH_SIZE from environ.
4.  Connect control socket to pmgrd; send RANK_READY <rank>.
5.  Block on pmgrd control socket; receive RANK_TABLE <N> <json>.
6.  Build rank_table_t from the JSON manifest.                    (I9)
7.  Open UDS listen socket; bind to a per-rank named path.
8.  Send LISTEN_READY <rank> <socket_path> to pmgrd.
9.  Block until pmgrd sends GO (all N ranks LISTEN_READY).        (ALL_READY barrier)
10. Connect to all peers with rank > self (lower-rank connects to higher). (ADR-08)
11. Set g_world->initialized = 1; emit metric mpi_init_duration_ms.

Step 3 — MPI_Send / MPI_Recv over UDS (P5, P6, I4, I5). Wire format: 32-byte mpi_wire_header_t (§11.5) followed by payload. Sender calls mpi_wire_header_hton() before write(); receiver calls mpi_wire_header_ntoh() after read() (I5, ADR-07). Partial write()/read() are retried in a loop until len bytes are transferred — partial sends are a documented pitfall on UDS under high load (P11, ADR-06).

Step 4 — Dissemination barrier (P12, I10). The barrier proceeds in ⌈log₂N⌉ rounds. In round r (0-indexed) rank i exchanges a one-byte MSG_BARRIER_TOKEN with rank (i + 2^r) mod N. Each rank blocks until it has received the token for round r before advancing. (§8.5 complexity table; ADR-21 static algorithm selection.)

Step 5 — MPI_Finalize teardown (P12, I8). Each rank sends MSG_FIN to all N-1 peers and blocks on poll() until N-1 MSG_FIN messages are received. Timeout controlled by MPI_SCRATCH_FINALIZE_TIMEOUT_SEC. pmgrd gathers EXIT messages after all ranks close control sockets.

12.6 Pitfalls

  • Partial sends on UDS. write() on a SOCK_STREAM socket may return fewer bytes than requested if the kernel send buffer is full. The send loop must retry until len bytes are confirmed written; a one-shot write() is a latent correctness bug.
  • READY race. A rank that sends LISTEN_READY before calling listen() may cause the first connect() from a peer to get ECONNREFUSED. Step 8 must follow step 7 strictly; add a listen() call before LISTEN_READY.
  • MPI_Finalize deadlock. If any rank calls MPI_Finalize without having consumed all messages in its UMQ, peers waiting for a matching receive will block forever. All messages must be consumed before MPI_Finalize.
  • Environment variable limits. Passing large rank tables via environment variables hits execve argument+environment size limits (typically 128 KB on Linux). For N > 64, use the pmgrd control socket to deliver the rank table post-exec, not via environment.
  • POLLHUP on UDS. If a rank crashes before sending MSG_FIN, surviving ranks' poll() call returns POLLHUP on the dead rank's fd. This must be treated as an implicit MSG_FIN with an error flag, not an infinite block.

12.7 Performance Concerns

  • UDS ping-pong target: p50 < 5 µs for 8-byte payload. Achieving this requires: no Nagle-equivalent delay on SOCK_STREAM (UDS has none), no user-space buffering, and the send/recv loop entering the kernel in a single write()+read() pair.
  • O(N²) pre-connect cost. MPI_Init connects all N×(N-1)/2 pairs. For N=64 this is 2,016 socket pairs. Connection time is dominated by bind()+connect() latency (~5 µs/pair on Linux), giving ~10 ms for N=64. This is within the 200 ms budget.
  • Dissemination barrier round count. ⌈log₂N⌉ message round-trips. For N=4: 2 rounds, 8 messages total. Measure per-barrier latency; a barrier over N=4 with UDS should complete in < 100 µs.

12.8 Edge Cases

  • NULL argc/argv. MPI-3.1 §4.1 permits MPI_Init(NULL, NULL). The init code must not dereference argc/argv before checking for NULL.
  • MPI_PROC_NULL. A send to MPI_PROC_NULL must return MPI_SUCCESS immediately and transmit nothing; a recv from MPI_PROC_NULL must fill the status with source=MPI_PROC_NULL and count=0 without blocking.
  • N=1 self-send. A single-rank job attempting MPI_Send(rank=0, dest=0) must not deadlock. The send path must detect dest == self and route to a local loopback queue rather than attempting a socket send to self.
  • pmgrd not found. If MPI_SCRATCH_PMGRD_ADDR is absent or the socket path does not exist, MPI_Init must return MPI_ERR_INTERN with a diagnostic log, not silently hang.

13. Phase 1 — Point-to-Point Communication (Full Envelope Semantics)

13.1 Objectives

Extend blocking P2P to the full MPI envelope specification:

  • Implement wildcard matching: MPI_ANY_SOURCE and MPI_ANY_TAG in posted receives, with FIFO ordering per (source, tag, context_id) triple (P5, I2).
  • Implement MPI_Sendrecv and MPI_Sendrecv_replace for deadlock-free simultaneous send+receive.
  • Implement MPI_Probe (blocking) and MPI_Iprobe (non-blocking) to inspect the next matching message without consuming it.
  • Implement MPI_Get_count to retrieve the byte count of a received message from its MPI_Status.
  • Enforce MPI_TAG_UB (upper bound for valid tags, minimum 32767 per MPI-3.1 §3.6).
  • Wire up MPI_Status fields: MPI_SOURCE, MPI_TAG, MPI_ERROR populated on every MPI_Recv completion.

13.2 Detailed Implementation Steps

Step 1 — Wildcard matching in the PRQ/UMQ scan (P5, I2, ADR-11)

The PRQ scanner in match/prq.c must treat src_rank == MPI_ANY_SOURCE (-1) as matching any source, and tag == MPI_ANY_TAG (-1) as matching any tag. context_id is never wildcarded (I1). The PRQ is scanned in insertion order (FIFO) per triple to satisfy MPI-3.1 §3.5 (P5, I2). The UMQ scanner in match/umq.c uses the same wildcard predicate; first matching entry in insertion order is promoted. (ADR-11 — linked list for Phase 0/1; ring-buffer UMQ bounded by I3.)

/* wildcard match predicate — illustrative signature only, no body */
static bool envelope_matches(const mpi_envelope_t *posted,
                              const mpi_envelope_t *arrived);

Step 2 — MPI_Sendrecv deadlock avoidance (P5, P6)

MPI_Sendrecv posts the recv to the PRQ first, then issues the send. This ordering prevents the classic deadlock where two ranks each call MPI_Send before MPI_Recv and fill each other's kernel buffers. The implementation uses the existing blocking MPI_Send/MPI_Recv primitives after ensuring the recv is registered (P5 FIFO, P6 transport isolation).

Step 3 — MPI_Probe / MPI_Iprobe (P1, I2)

MPI_Probe calls MPI_Recv_probe_internal, which performs the UMQ scan and PRQ scan without removing the entry. If no match is found, it blocks by calling transport.recv_wire() once and re-scanning. MPI_Iprobe performs one scan and returns flag=0 immediately if nothing matches. Both functions populate MPI_Status with the envelope of the matching (but unconsumed) message. (ADR-11 linked list makes non-destructive scan trivial.)

Step 4 — MPI_Get_count (P1, ADR-06)

MPI_Get_count(status, datatype, count) divides status->_ucount (stored raw byte count) by sizeof(datatype). If the division is not exact, returns MPI_UNDEFINED. The raw byte count is written into MPI_Status._ucount by the recv path from the payload_len field of the wire header (ADR-06 wire format).

Step 5 — MPI_TAG_UB enforcement (P1, I4)

Add validation in MPI_Send/MPI_Recv entry points: tag < 0 || tag > MPI_TAG_UB → return MPI_ERR_TAG. MPI_TAG_UB is queried via MPI_Comm_get_attr(MPI_COMM_WORLD, MPI_TAG_UB, &ub, &flag). The implementation stores MPI_TAG_UB = 1073741823 (2³⁰ − 1) as the compile-time default; overridable via MPI_SCRATCH_TAG_UB env var.

13.6 Pitfalls

  • Wildcard recv bypasses FIFO per-triple. If the scan does not preserve insertion order within a (ANY_SOURCE, tag, context_id) scope, messages from different sources can overtake each other in ways that violate application assumptions. Test any_source specifically verifies arrival-order delivery.
  • MPI_Probe does not consume. A common mistake is to implement MPI_Probe by dequeueing the UMQ entry. The entry must remain in place; only the subsequent MPI_Recv removes it. Removing it in Probe causes the message to be "lost" if the process does not immediately call Recv.
  • MPI_Sendrecv with same send and receive buffer. MPI_Sendrecv_replace requires copying the send data before overwriting the buffer. Not handling this case causes self-corruption.
  • MPI_Get_count on truncated message. If payload_len % sizeof(datatype) != 0, the count is undefined. Return MPI_UNDEFINED (-1), not zero or a truncated integer, to match spec.

13.7 Performance Concerns

  • Wildcard scan cost. A wildcard MPI_ANY_SOURCE recv scans the entire UMQ linearly. For deep queues near MPI_SCRATCH_UMQ_DEPTH, this is O(4096) comparisons per recv. For Phase 1 this is acceptable; a hash-indexed UMQ is PhaseDeferred. Emit prq_search_depth histogram metric to track this.
  • MPI_Probe spin. Applications that MPI_Probe in a tight loop burn CPU waiting for messages. The Phase 1 implementation blocks in poll() on the transport fd rather than spinning. This avoids 100% CPU usage at the cost of a kernel wakeup.

13.8 Edge Cases

  • MPI_ANY_SOURCE with N=1. A single-rank job calling MPI_Recv(MPI_ANY_SOURCE) must not deadlock. It should return MPI_ERR_RANK if no self-send is in flight, or complete if a prior MPI_Send(dest=0) was issued.
  • Zero-byte message with wildcard. MPI_Send(count=0) is legal. A wildcard MPI_ANY_TAG recv must match it; MPI_Get_count returns 0; MPI_Status is fully populated.
  • Tag = MPI_ANY_TAG in MPI_Send. Sending with tag = MPI_ANY_TAG (-1) is illegal; return MPI_ERR_TAG. Only receives may use the wildcard sentinel.
  • MPI_Probe followed by different-source recv. An application that calls MPI_Probe(MPI_ANY_SOURCE) then MPI_Recv(src=1) when the probed message was from src=2: the recv should deliver the src=2 message (UMQ order) or block for the src=1 message depending on which arrives first. The implementation must not assert-fail on this mismatch.

14. Phase 2 — Envelope, Matching, and Rendezvous Protocol

14.1 Objectives

Extend the transport and match engine to handle large messages correctly and add the three additional send modes:

  • Implement the eager/rendezvous threshold protocol: messages below MPI_EAGER_LIMIT (default 64 KB) use eager send; messages at or above use RTS/CTS rendezvous (P3, ADR-06, I3).
  • Implement MPI_Ssend (synchronous send): does not return until the receiver has posted MPI_Recv, guaranteeing the receiver has entered the matching call.
  • Implement MPI_Bsend (buffered send): copies the message into a user-provided buffer attachment, allowing MPI_Bsend to return before the receiver is ready.
  • Implement MPI_Rsend (ready send): caller asserts the receiver has already posted MPI_Recv; if not, behavior is erroneous (used for performance, not safety).
  • Bound the UMQ (I3) and verify that rendezvous prevents OOM on large message flows.

14.2 Detailed Implementation Steps

Step 1 — Eager/rendezvous threshold (P3, I3, P11, ADR-06)

The threshold is derived from the LogGP model (P11, Alexandrov et al. 1995): eager is preferred when α + m/β < 2α + mₛ/β (where mₛ is the small header size); crossover at m = α·β. For UDS at α ≈ 5 µs and β ≈ 10 GB/s, crossover ≈ 50 KB; set MPI_EAGER_LIMIT=65536 as the rounded default (ADR-21 static table).

The wire header flags field (§8.2) encodes EAGER(0x01), RENDEZVOUS_REQ(0x02), RENDEZVOUS_ACK(0x04). Eager path: send header+body in one write(). Rendezvous path:

Sender:   write(header + flags=RENDEZVOUS_REQ, body_len, no body)
Receiver: read header → post body buffer → write(header + flags=RENDEZVOUS_ACK)
Sender:   read ACK → write(body, body_len bytes)

request_id field in the header correlates RTS with CTS (ADR-06 wire format).

Step 2 — MPI_Ssend (P1, P3)

MPI_Ssend adds a synchronous-send flag to the wire header. The sender blocks after transmitting the header until it receives a MSG_SSEND_ACK control message from the receiver. The receiver sends MSG_SSEND_ACK when MPI_Recv is posted and the envelope matches. This guarantees the "synchronous" contract: the sender does not complete until the receiver has entered the matching receive. (P3 — cost model note: Ssend adds exactly 1 RTT to every send.)

Step 3 — MPI_Bsend (P1, P3, I3)

MPI_Buffer_attach(buf, size) registers a user-provided buffer. MPI_Bsend copies the message payload into the attached buffer (up to its remaining capacity) and returns immediately, regardless of receiver readiness. The background send proceeds asynchronously using a progress thread in Phase 6; for Phase 2, the copy is made and the actual send is deferred to the next call that enters the progress engine (i.e., the next MPI_Recv call on this rank). Buffer overflow → MPI_ERR_BUFFER. (I3 — UMQ bounded; Bsend's buffer is a separate user-managed pool.)

Step 4 — MPI_Rsend (P1)

MPI_Rsend sets a RSEND flag in the wire header. If no matching receive is posted when the message arrives (i.e., it would go to UMQ), the receiver logs MPI_ERR_INTERN and drops the message per spec (behavior is erroneous when the receiver has not posted). In practice, MPI_Rsend is used only in tightly synchronized patterns where the application guarantees ordering.

Step 5 — UMQ backpressure verification (P9, I3, ADR-11)

The umq_insert() function checks umq.in_use >= MPI_SCRATCH_UMQ_DEPTH before inserting. On overflow, the recv thread blocks the sending rank by holding the UDS recv buffer (not calling read()) until space is available. This provides backpressure without dropping messages. Emit umq_depth gauge metric on each insert.

14.6 Pitfalls

  • Rendezvous ACK ordering. If the receiver sends the RENDEZVOUS_ACK before allocating the receive buffer, a fast sender may start writing body bytes before the buffer pointer is set. The ACK must be sent only after the body buffer is allocated and the receive is fully registered.
  • Ssend ACK lost on receiver crash. If the receiver crashes after posting MPI_Recv but before sending MSG_SSEND_ACK, the sender blocks forever. Add a MPI_SCRATCH_SSEND_TIMEOUT_SEC knob (default 60s) to detect this.
  • Bsend buffer overflow. If the user attaches a buffer too small for the pending sends, MPI_Bsend returns MPI_ERR_BUFFER. Document that MPI_Buffer_detach must be called to reclaim the buffer after all sends complete; calling it while sends are pending blocks.
  • UMQ backpressure deadlock. If rank A is backing up rank B's UMQ (B is not reading), and rank B is simultaneously blocking on a send to rank A, both ranks deadlock. The backpressure mechanism must not hold UDS recv buffers while a send is in progress on the same rank.

14.7 Performance Concerns

  • Rendezvous overhead per message. Each rendezvous add 1 RTT (RTS + CTS) before the body transfer. For a 1 MB message over UDS with α=5 µs, this is 10 µs of overhead vs. ~100 µs for the body transfer — 10% overhead. Acceptable. Document the measured overhead in benchmarks/ CSV output.
  • Eager threshold tuning. MPI_EAGER_LIMIT is a compile-time default but overridable via env. Too high a threshold risks OOM (large messages pile up in UMQ); too low wastes RTTs on small messages. The LogGP derivation in docs/adr/ADR-06-wire-format.md shows the derivation.
  • Bsend extra copy. MPI_Bsend copies the payload into the attached buffer before sending. For large messages this doubles memory bandwidth. Document this cost in include/mpi_api.h Bsend docstring.

14.8 Edge Cases

  • Zero-byte rendezvous. A zero-byte message should use the eager path regardless of threshold (no body to transfer). The rendezvous path with body_len=0 must not block waiting for a body that never arrives.
  • MPI_Bsend with buffer smaller than one message. Return MPI_ERR_BUFFER immediately; do not partial-copy.
  • Ssend to self (dest == rank). Must not deadlock. The implementation should detect dest == self and route through the loopback queue with the Ssend ACK generated internally.
  • Rendezvous with MPI_ANY_SOURCE receiver. The wildcard receiver must match the RTS header's source rank and send the CTS back to that specific source, not broadcast it.

15. Phase 3 — Collective Operations: Broadcast and Reduce

15.1 Objectives

Implement the first tier of collective operations on top of the Phase 0–2 P2P substrate:

  • Implement MPI_Bcast using the binomial tree algorithm for small messages (P3 Thakur 2005, ADR-21).
  • Implement MPI_Reduce with all standard reduction operators (MPI_SUM, MPI_MAX, MPI_MIN, MPI_PROD, MPI_LAND, MPI_LOR, MPI_BAND, MPI_BOR) using the binomial tree algorithm (P6, I10).
  • Implement MPI_Allreduce as a reduce-then-broadcast (Phase 3 default) and as recursive halving-doubling for power-of-2 N (§8.5 algorithm table, ADR-21).
  • Implement the ring allreduce algorithm for large messages and non-power-of-2 N.

15.2 Detailed Implementation Steps

Step 1 — Binomial tree broadcast (P3 Thakur 2005, P6, ADR-21). The binomial tree over N ranks with root r proceeds in ⌈log₂N⌉ steps. In step k (0-indexed), each rank that already has the data sends to rank (self + 2^k) mod N if that rank has not yet received. The static algorithm selection table (ADR-21) selects binomial tree for m < MPI_SCRATCH_BCAST_LARGE_MSG (default 16 KB) and pipeline for larger messages.

ASCII — binomial tree bcast, N=8, root=0:
Step 0: 0 → 4
Step 1: 0 → 2, 4 → 6
Step 2: 0 → 1, 2 → 3, 4 → 5, 6 → 7

Internal message tags use the range reserved by MPI_SCRATCH_COLL_TAG_BASE (default 2³⁰) to avoid collision with user tags (I10, ADR-21).

Step 2 — Binomial tree reduce (P3 Thakur 2005, P6, I10)

Reduce is the mirror of broadcast: in step k, a rank receives from its peer and applies the reduction operator to its local buffer. The root collects the final result. Operator dispatch uses a function pointer table reduce_ops[MPI_SUM] etc. For non-commutative operations (MPI_SUM is commutative; MPI_REPLACE is not), the tree must preserve left-to-right rank ordering. (Thakur 2005 — §3.2 reduce correctness for non-commutative operators.)

/* reduce_op_fn_t — illustrative signature; no body */
typedef void (*reduce_op_fn_t)(const void *in, void *inout,
                               int count, int datatype);

Step 3 — MPI_Allreduce: reduce-then-broadcast (P6, ADR-21). Phase 3 default: MPI_Allreduce = MPI_Reduce(root=0) + MPI_Bcast(root=0). Cost: 2·⌈log₂N⌉·α + 2·⌈log₂N⌉·m/β. Not optimal but trivially correct. Used for N not a power of 2 or m < threshold.

Step 4 — Recursive halving-doubling Allreduce (P3 Thakur 2005, ADR-21). For N = 2^k, the halving-doubling algorithm achieves optimal latency and bandwidth in ⌈log₂N⌉ steps. In step k, ranks i and i XOR 2^k exchange their partial sums and both accumulate. After ⌈log₂N⌉ steps all ranks hold the global result. Cost: ⌈log₂N⌉·α + ⌈log₂N⌉·m/β.

Step 5 — Ring allreduce for large messages (P3 Thakur 2005, ADR-21). For large m (default: m > MPI_SCRATCH_RING_ALLREDUCE_THRESHOLD = 1 MB), use the ring allreduce: each rank sends a chunk to its right neighbor and receives a chunk from its left neighbor, accumulating over N-1 scatter steps, then N-1 gather steps. Cost: 2·(N-1)/N·m/β + 2·(N-1)·α ≈ 2·m/β + 2·N·α. Optimal for large m.

Step 6 — Collective tag reservation (I10, ADR-21). MPI_SCRATCH_COLL_TAG_BASE = 0x40000000. Every collective allocates tags in the range [COLL_TAG_BASE, COLL_TAG_BASE + max_coll_tags). User tags are validated to be < MPI_TAG_UB which is set ≤ COLL_TAG_BASE - 1. This provides strict separation (I10).

15.6 Pitfalls

  • Non-commutative reduce ordering. MPI_SUM on integers is commutative, but the standard still requires that the result is as if ranks contributed in rank order (for reproducibility across runs). The binomial tree reduce must accumulate in rank order at each node.
  • Collective deadlock from unbalanced calls. If one rank calls MPI_Bcast while another calls MPI_Reduce (both using the same communicator), the internal tag collision causes both to block. This is a user error per MPI-3.1 §5.1, but the implementation should detect it via I10 tag collision counter.
  • Allreduce on non-power-of-2 N. The halving-doubling algorithm requires N to be a power of 2. The static dispatch table (ADR-21) must fall back to reduce-then-bcast for non-power-of-2 N.
  • Root rank validation. MPI_Reduce and MPI_Bcast require 0 ≤ root < size. Return MPI_ERR_ROOT otherwise; do not proceed to the algorithm.

15.7 Performance Concerns

  • Binomial tree bcast latency. For N=16, the tree has depth 4 (⌈log₂16⌉). Each hop adds 1 RTT ≈ 10 µs over UDS. Total bcast latency ≈ 40 µs for a 4-byte int. Record this in the OSU benchmark CSV.
  • Ring allreduce bandwidth efficiency. Each rank sends and receives (N-1)/N × m bytes per scatter phase, effectively achieving (1 - 1/N) of peak bandwidth. For N=4, this is 75% utilization. Document in benchmarks/osu_allreduce.c output.
  • Operator dispatch overhead. The function pointer dispatch for the reduce operator adds one indirect call per element. For 1024 doubles this is negligible. For Phase 3, correctness takes priority over SIMD vectorization of the operator.

15.8 Edge Cases

  • MPI_Bcast with N=1. Root is rank 0; no sends needed; returns immediately.
  • MPI_Reduce with count=0. Legal; root receives a zero-element result; no memory access; MPI_Status populated with count=0.
  • MPI_Allreduce with MPI_IN_PLACE. Not required in Phase 3 (PhaseDeferred to Phase 5). Document the PhaseDeferred("FINAL_BLUEPRINT §17") anchor in the MPI_IN_PLACE branch.
  • MPI_Reduce operator MPI_MINLOC / MPI_MAXLOC. PhaseDeferred to Phase 5; return MPI_ERR_OP for these in Phase 3 with a clear log message.

16.1 Objectives

  • Implement MPI_Allgather (all ranks receive the gather result) and MPI_Alltoall (pairwise exchange: each rank sends a distinct chunk to every other rank).
  • Implement MPI_Scatterv and MPI_Gatherv (variable-length variants: sendcounts[] and displs[] arrays per rank).
  • Verify the ring allreduce algorithm for large messages (shipped in Phase 3 but validated at production scale here: 4096 doubles, N=4).
  • Validate distributed matrix multiply using MPI_Scatter/MPI_Gather on a 512×512 matrix with 4 ranks as an integration-level correctness gate.

16.2 Detailed Implementation Steps

Step 1 — MPI_Scatter / MPI_Gather flat tree (P3 Thakur 2005, I10, ADR-21). MPI_Scatter(root=r): root sends sendcount elements to each rank using N-1 MPI_Send calls in rank order (0 to N-1, skipping self). Each non-root rank calls one MPI_Recv. The flat tree is O(N) messages; binomial or pipeline scatter is PhaseDeferred.

MPI_Scatter, N=4, root=0, sendcount=2:
  Root sends [buf+0×2×extent .. buf+1×2×extent) → rank 1
  Root sends [buf+1×2×extent .. buf+2×2×extent) → rank 2  (illustrative only)
  Root sends [buf+2×2×extent .. buf+3×2×extent) → rank 3
  Root uses  [buf+0×2×extent .. buf+1×2×extent) locally

All collective tags reserved from MPI_SCRATCH_COLL_TAG_BASE (I10, P7 Pjedinec & Hoefler shared mem considerations deferred). (ADR-21 static selection: flat tree for Phase 4; recursive-halving scatter PhaseDeferred.)

Step 2 — MPI_Allgather (P3 Thakur 2005, I10, ADR-21). MPI_Allgather = MPI_Gather(root=0) + MPI_Bcast(root=0) for Phase 4 (ring allgather PhaseDeferred). Each rank receives a copy of the gathered buffer. Cost: O(N) messages for gather + O(log N) for bcast.

Step 3 — MPI_Alltoall pairwise exchange (P3 Thakur 2005, I10, ADR-21). Each rank sends a distinct sendcount-element chunk to every other rank, including itself (local copy for self). Implementation: nested loop — rank i sends to rank j (j ≠ i) for all j; rank i receives from rank j for all j. To avoid deadlock, use MPI_Sendrecv in each pair (i, j) with j > i. For Phase 4, the pairwise exchange is O(N²) messages; van de Geijn & Watts optimal algorithm is PhaseDeferred. (ADR-21 static selection.)

Step 4 — MPI_Scatterv / MPI_Gatherv (P1, ADR-21). MPI_Scatterv generalizes scatter with per-rank sendcounts[] and displs[] arrays. Root sends sendcounts[r] elements starting at byte offset displs[r] × extent from the sendbuf. Non-roots receive recvcount elements. Validation: sendcounts[r] ≥ 0 for all r; displs[] may be non-contiguous (gaps are legal; overlaps are erroneous per spec). MPI_Gatherv is symmetric.

Step 5 — Ring allreduce validation at 4096 doubles (P3 Thakur 2005, I10). The ring allreduce was implemented in Phase 3. Phase 4 adds the integration benchmark: 4096 doubles per rank, N=4, MPI_SUM, result compared element-wise against sequential reference. This exercises the ring allreduce at a message size of 4096 × 8 = 32 KB per rank, above the eager threshold, exercising the rendezvous path within the ring steps.

Step 6 — 512×512 matrix multiply integration test (P3, P7). Distribute a 512×512 matrix A by row-blocks to N=4 ranks (128 rows each via MPI_Scatter). Each rank computes its block of A × B (B is broadcast via MPI_Bcast). Gather row-block results to root via MPI_Gather. Root verifies the assembled result against a sequential reference matrix multiply. This exercises the full scatter-bcast-compute-gather pipeline. (P7 Pjedinec & Hoefler 2012 — shared-memory path deferred but the communication pattern is validated here.)

16.6 Pitfalls

  • Scatter/gather root participates. The root rank both sends to peers and copies its own chunk locally (via memcpy, not MPI_Send). A common mistake is to have the root send to itself over the socket, causing a self-deadlock.
  • MPI_Alltoall deadlock. If all N ranks simultaneously try to MPI_Send before any calls MPI_Recv, all N sends fill their peer's kernel buffers and all block. The pairwise MPI_Sendrecv approach avoids this but requires the nested loop to pair (i,j) correctly.
  • Scatterv overlap. If displs[r] + sendcounts[r] > displs[r+1], the sent chunks overlap. This is erroneous per spec; validate and return MPI_ERR_COUNT if detected.
  • Allgather vs. Allreduce confusion. MPI_Allgather concatenates, not reduces. Test allgather_correctness explicitly checks that the gathered values are the raw sent values, not sums.
  • Matrix multiply reference tolerance. 512×512 double-precision multiply accumulates rounding error. The tolerance 1e-6 is appropriate; using exact integer comparison will fail due to floating-point non-associativity.

16.7 Performance Concerns

  • Flat scatter is O(N) serial sends from root. For N=64, root makes 63 sequential MPI_Send calls. Latency is 63 × RTT ≈ 63 × 10 µs = 630 µs for a small message. Document this in benchmarks/ and note that the binomial scatter (PhaseDeferred) reduces this to O(log N) serial hops.
  • Alltoall message volume. N=4 ranks × N chunks = 16 messages. N=64 = 4,096 messages. For Phase 4 (N ≤ 16), this is manageable. Emit a warning log if N > 16 and MPI_Alltoall is called: LOG_WARN "MPI_Alltoall N=%d: O(N^2) pairwise exchange; consider N<=16 for Phase 4".
  • Matrix multiply benchmark. The 512×512 test is a correctness gate, not a performance gate. Record elapsed time in CI; flag if > 30 s (a regression indicator). Performance optimization of the local DGEMM is out of scope.

16.8 Edge Cases

  • MPI_Scatter with sendcount=0. Legal; root sends zero-element buffers; all ranks receive zero-element buffers; no memory access; MPI_Status populated.
  • MPI_Gather with non-contiguous recvbuf. The root's recvbuf must be large enough for N × recvcount elements. Validate recvbuf != NULL at root; at non-root, recvbuf is ignored (may be NULL).
  • MPI_Alltoall with N=1. Single rank; local copy only; no messages sent.
  • MPI_Scatterv with a rank having sendcount=0. That rank receives a zero-byte message. The receiver must handle count=0 recv without blocking, and MPI_Get_count must return 0.
  • MPI_Gatherv displs not sorted. The spec allows unsorted displs (arbitrary placement in recvbuf). The implementation must use displs[r] as the exact byte offset, not assume contiguous placement.

17. Phase 5 — Communicators and Groups

17.1 Objectives

Implement the MPI communicator and group subsystem. Provide safe context isolation between communicators so that messages sent on MPI_COMM_WORLD are never matched by receives posted on a duplicated communicator or a split sub-communicator. Support all standard group set operations and the full MPI_Comm_split / MPI_Comm_dup / MPI_Comm_create lifecycle. Stub MPI_Intercomm_create with PhaseDeferred.

17.2 Detailed Implementation Steps

Group handle and descriptor (P4 — no globals; all state in mpi_world_t): Define MPI_Group as an opaque index into mpi_world_t.group_table[].

typedef struct {
    int  size;
    int *world_ranks;   /* translation table: group_rank → world_rank */
    int  refcount;
} group_desc_t;

MPI_GROUP_EMPTY maps to a zero-size entry. MPI_GROUP_NULL is the sentinel −1.

Context ID allocation (P2 — Gropp 1996 context ID scheme; ADR-01): Context IDs are 32-bit unsigned integers. Allocation is collective: each rank proposes a locally unique candidate, then MPI_Allreduce(MPI_MAX) over the parent communicator selects the highest proposal. The result is stored in comm_desc_t.context_id. Invariant I1: a (context_id, src_rank, tag) triple uniquely identifies a message universe across all communicators in the job.

Communicator descriptor:

typedef struct {
    uint32_t     context_id;
    MPI_Group    group;       /* ranks in this communicator */
    errhandler_t errhandler;
    int          refcount;
} comm_desc_t;

mpi_world_t.comm_table[] is the flat array; MPI_Comm is an index into it.

MPI_Comm_create (ADR-01): Collective on parent comm. Each rank calls group_contains(new_group, my_world_rank). Ranks not in the group return MPI_COMM_NULL. Participating ranks allocate a context ID via Allreduce(MAX) and populate a new comm_desc_t.

MPI_Comm_split (P2 — Gropp context ID; I1 — context_id invariant): Each rank contributes a (color, key, world_rank) triple. An MPI_Allgather of all N triples produces the full list. Discard entries with color == MPI_UNDEFINED. Sort remaining by (color, key, world_rank). Partition into color groups; assign contiguous rank indices within each group. Allocate a new context ID per color group via Allreduce(MAX) scoped to that partition.

MPI_Comm_dup: Allocates a new context ID via Allreduce(MAX) on the source communicator, copies the group reference (increments refcount), sets errhandler = MPI_ERRORS_ARE_FATAL.

MPI_Comm_free: Decrements comm_desc_t.refcount. When it reaches zero: decrement group_desc_t.refcount; if that reaches zero, free world_ranks array; return context ID to the free pool (circular bitset in mpi_world_t.context_id_pool).

Group set operations: MPI_Group_union, MPI_Group_intersection, MPI_Group_difference operate on sorted world_ranks arrays using standard merge-step algorithms. MPI_Group_incl / MPI_Group_excl copy a filtered world_ranks subset. All produce a new group_desc_t; caller must MPI_Group_free the result.

MPI_Intercomm_create: Returns MPI_ERR_UNSUPPORTED_OPERATION and logs PhaseDeferred("## 17. Phase 5 — Communicators and Groups").

18. Phase 6 — Non-Blocking Operations and Request Objects

18.1 Objectives

Implement the full non-blocking point-to-point API: MPI_Isend, MPI_Irecv, MPI_Wait, MPI_Test, MPI_Waitall, MPI_Waitany, MPI_Request_free, MPI_Cancel, and persistent requests (MPI_Send_init, MPI_Recv_init, MPI_Start). Requests must progress via a dedicated background thread without requiring the application thread to poll. The request pool must be bounded and leak-free across repeated cycles.

18.2 Detailed Implementation Steps

Request descriptor (I7 — request lifecycle; ADR-10 — request pool):

typedef enum { REQ_FREE, REQ_PENDING, REQ_COMPLETE, REQ_CANCELLED } req_state_t;
typedef struct {
    req_state_t   state;
    req_kind_t    kind;       /* SEND | RECV | PERSISTENT_SEND | PERSISTENT_RECV */
    void         *buf;
    int           count;
    MPI_Datatype  datatype;
    int           peer_rank;
    int           tag;
    MPI_Comm      comm;
    MPI_Status    status;
    bool          cancelled;
} request_desc_t;

MPI_Request is an index into mpi_world_t.request_pool[], a fixed-size array of ADR-10-bounded size (default 4 096 entries). Allocation is O(1) via a free-list head pointer.

MPI_Isend (P8 — pre-connect; I7): If count * datatype_size ≤ EAGER_THRESHOLD (8 KiB): copy buffer into an internal eager slot, post the send immediately, set state = REQ_PENDING. Background thread delivers eagerly. If larger: post an RTS (Ready-To-Send) control message; transition to REQ_PENDING; background thread completes the rendezvous handshake.

MPI_Irecv (I3 — UMQ bounded): Insert a posted-receive queue (PRQ) entry keyed by (comm, src, tag). Return REQ_PENDING handle. If a matching unexpected message already sits in the UMQ, dequeue it immediately and copy/transition to REQ_COMPLETE.

Background progress thread (ADR-09 — THREAD_SERIALIZED): One thread per process, started at MPI_Init. Calls poll() over all open FDs with a 1 ms timeout. On readable FD: receive envelope, match against PRQ, deliver payload, mark request REQ_COMPLETE. Holds mpi_world_t.progress_mutex during state transitions; application threads acquire the same mutex before inspecting request state (THREAD_SERIALIZED model).

MPI_Wait: Spin-sleep loop: acquire mutex, check state == REQ_COMPLETE, release mutex, sleep 100 µs if not complete. Copy status from descriptor, transition state = REQ_FREE, return handle to pool.

MPI_Test: Single non-blocking mutex acquire; return flag=1 if complete, flag=0 otherwise. Never sleeps.

MPI_Waitall: Iterate MPI_Wait over the array sequentially. Document that out-of-order completion is not exploited in this phase (future optimization noted in ADR-10).

MPI_Waitany: Poll all requests in round-robin until one is complete; return its index and status.

MPI_Request_free: If state == REQ_PENDING, mark as detached (application no longer owns it); background thread frees on completion. If already REQ_COMPLETE, free immediately.

MPI_Cancel: If state == REQ_PENDING and message not yet matched: remove PRQ entry, set state = REQ_CANCELLED, cancelled = true. If already in flight: cancel is advisory; status.cancelled reflects actual outcome via MPI_Test_cancelled.

Persistent requests (MPI_Send_init / MPI_Recv_init): Allocate a descriptor with kind = PERSISTENT_*, store parameters, return handle. MPI_Start transitions state from REQ_FREE to REQ_PENDING and posts the operation. MPI_Request_free on a persistent request frees the descriptor only if state != REQ_PENDING.

18.6 Pitfalls

  • Progress thread starvation — if the application holds progress_mutex for > 5 ms, the background thread cannot deliver messages; MPI_Wait will spin-sleep indefinitely. Enforce mutex hold-time assertion in debug builds.
  • Eager buffer exhaustion — if all eager slots fill before the background thread drains them, MPI_Isend blocks. Size the eager pool at 2 × request_pool_size × EAGER_THRESHOLD bytes and emit LOG_WARN at 80% occupancy.
  • Persistent request double-start — calling MPI_Start on a request in REQ_PENDING state is an error (MPI_ERR_REQUEST). Assert in debug builds; return error code in release.
  • MPI_Cancel after match — once a receive is matched and data copy has begun, cancellation is no longer possible; status.cancelled must be 0. Document this race in the API header.

18.7 Performance Concerns

  • Background thread wakes every 1 ms even when idle (ADR-09). On high-core-count machines this wastes one hardware thread. Future optimization: adaptive sleep using eventfd notification from MPI_Isend. Document as TODO(ADR-10-future).
  • MPI_Waitall is O(N) sequential; for N > 64, a future implementation may use a completion bitmap. Current phase documents this limit.
  • Rendezvous for large messages adds one round-trip latency. Applications sending many large messages should use persistent requests to amortize the RTS overhead.

18.8 Edge Cases

  • MPI_Isend to self (peer_rank == my_rank): must still go through the progress thread path, not a direct buffer copy, to preserve ordering semantics with other outstanding sends.
  • MPI_Irecv with MPI_ANY_SOURCE and MPI_ANY_TAG: PRQ entry uses wildcard slots; first matching message from any source wins.
  • Zero-count MPI_Isend / MPI_Irecv: must complete immediately with MPI_SUCCESS; no bytes transferred; status.count == 0.
  • MPI_Waitall with MPI_REQUEST_NULL entries in the array: skip null entries without error (MPI standard §3.7.3).
  • Overflow of request pool: MPI_Isend returns MPI_ERR_INTERN with message "request pool exhausted" in MPI_Error_string.

19. Phase 7 — Derived Datatypes

19.1 Objectives

Implement the MPI derived datatype system: contiguous, vector, hvector, indexed, and struct types. Provide MPI_Type_commit / MPI_Type_free, extent and true-extent queries, and a pack/unpack engine that walks the descriptor tree to assemble non-contiguous data into a flat byte buffer for transmission. Integrate with the send/receive path so that predefined types send directly while derived types are packed transparently.

19.2 Detailed Implementation Steps

Datatype descriptor (ADR-20 — tagged union descriptor; P2 — layered architecture):

typedef struct mpi_type_desc {
    dt_class_t   cls;       /* CONTIGUOUS | VECTOR | HVECTOR | INDEXED | STRUCT */
    MPI_Aint     lb, ub;    /* lower/upper bound for extent */
    MPI_Aint     true_lb, true_ub;
    size_t       size;      /* total byte footprint of one element */
    bool         committed;
    union {
        struct { int count; struct mpi_type_desc *base; }          contig;
        struct { int count, blocklength, stride; struct mpi_type_desc *base; } vector;
        struct { int count, blocklength; MPI_Aint stride_bytes; struct mpi_type_desc *base; } hvector;
        struct { int count; int *blocklens; MPI_Aint *displacements; struct mpi_type_desc *base; } indexed;
        struct { int count; int *blocklens; MPI_Aint *displacements; struct mpi_type_desc **bases; } strct;
    } u;
} dt_desc_t;

MPI_Datatype is an index into mpi_world_t.type_table[].

MPI_Type_contiguous (P10 — Träff 2012 datatype pack): Creates a descriptor with cls = CONTIGUOUS, count copies of oldtype. Sets size = count * oldtype.size, lb = oldtype.lb, ub = oldtype.lb + count * oldtype.extent.

MPI_Type_vector: cls = VECTOR. count blocks of blocklength elements separated by stride elements (not bytes) of oldtype. Extent = (count-1)*stride*oldtype_extent + blocklength*oldtype_extent. Use stride * oldtype.extent for byte displacement in pack loop.

MPI_Type_create_hvector: Identical to vector but stride is in bytes (MPI_Aint). Used for C struct field alignment (I5 — byte order).

MPI_Type_indexed: Variable-length blocks at variable displacements (in elements). Allocates int[] arrays for blocklens and displacements. Extent = max(displs[i] + blocklens[i]) * base_extent.

MPI_Type_create_struct: Each block may have a different base type. Displacement array is in bytes (MPI_Aint). Extent = max(displacements[i] + blocklens[i] * bases[i].extent). This is the canonical way to describe a C struct for MPI transmission.

MPI_Type_commit: Validates descriptor (extent ≥ 0, size > 0 for non-empty types), sets committed = true. Returns MPI_ERR_TYPE if already committed (idempotent per standard — actually a no-op; re-commit is allowed). Sets true_lb and true_ub by scanning all block extents ignoring explicit lb/ub markers.

MPI_Type_get_extent / MPI_Type_get_true_extent: Read lb/ub and true_lb/true_ub from descriptor.

Pack/unpack engine (P10 — Träff 2012 datatype pack): mpi_pack(src, count, type, dst_buf, dst_size, position) walks the descriptor tree recursively. At each CONTIGUOUS leaf, issues a single memcpy. For VECTOR / HVECTOR: loop count blocks, compute byte offset as block_idx * stride_bytes, recurse on base type. For INDEXED / STRUCT: iterate displacement array, recurse. mpi_unpack is the symmetric reverse.

Send/recv integration (P2 — layered arch): In mpi_send_envelope(): if MPI_Type_is_predefined(datatype), pass buffer pointer directly to transport. Else: allocate a flat pack buffer, call mpi_pack, send the flat buffer, free on completion. Receiver calls mpi_unpack after flat buffer arrives.

19.6 Pitfalls

  • Extent vs. size confusion — extent includes padding between elements (for array indexing); size is the actual byte footprint. The pack engine must use size, not extent, for memcpy lengths. Mismatch produces silent data corruption.
  • Stride sign — MPI_Type_vector stride may be negative (reverse stride). The pack engine must handle negative strides without underflowing the source pointer. Assert src_ptr >= src_base in debug mode.

  • MPI_Type_free while in flight — an application may free a type after posting MPI_Isend but before the send completes. The pack buffer is allocated before the type is freed, so this is safe only if packing happens synchronously in MPI_Isend. Document this requirement in include/mpi_datatype.h.

19.7 Performance Concerns

  • The recursive pack engine allocates a flat buffer on every derived-type send. For repeated sends of the same type, use a pre-allocated pack buffer per request descriptor (ADR-10) to eliminate per-call malloc. Mark as TODO(ADR-10-datatype).
  • Deeply nested types (e.g., vector-of-vector-of-struct) produce deep recursion. Cap descriptor nesting depth at 16; return MPI_ERR_TYPE for deeper compositions. Document in API header.
  • MPI_Type_create_struct allocates two heap arrays (blocklens, displacements). For structs with ≤ 8 fields, use inline arrays in the descriptor union to avoid heap fragmentation.

19.8 Edge Cases

  • MPI_Type_contiguous with count = 0: valid; produces a type of size 0 and extent 0. Pack is a no-op.
  • MPI_Type_vector with blocklength = 0: valid; no bytes packed per block, only stride advance.
  • MPI_Type_create_struct with a single field: equivalent to MPI_Type_create_hvector(1, blocklength, 0, base).
  • Negative lower bound (set via MPI_LB marker in MPI_Type_create_struct): must be preserved in lb field; affects extent but not pack byte count.
  • MPI_Type_free on a predefined type: returns MPI_ERR_TYPE; predefined descriptors are read-only.

20. Phase 8 — Topology and Virtual Cartesian Grids

20.1 Objectives

Implement the MPI Cartesian topology API: MPI_Cart_create, MPI_Cart_coords, MPI_Cart_rank, MPI_Cart_shift, MPI_Dims_create, and MPI_Cart_sub. Topology is pure metadata — it does not change routing, socket layout, or message delivery. It provides structured rank-to-coordinate mappings for stencil and grid applications.

20.2 Detailed Implementation Steps

Topology descriptor (ADR-22 — portability; I10 — collective ordering):

typedef struct {
    int   ndims;
    int  *dims;        /* size of each dimension */
    bool *periods;     /* periodic flag per dimension */
    bool  reorder;     /* hint: may reorder ranks for locality (not implemented) */
} cart_topo_t;

Attach cart_topo_t *topo to comm_desc_t. Non-topology communicators leave topo = NULL.

MPI_Cart_create (I10 — collective ordering; P8 — pre-connect): Collective on input communicator. Validate: product(dims) == comm_size. If reorder == true, note that rank reordering is not implemented and log LOG_INFO "cart_create: reorder ignored". Allocate cart_topo_t, copy dims and periods arrays. Create a new communicator via MPI_Comm_create with the same group (no rank reordering). Attach topo to the new comm_desc_t.

MPI_Cart_coords (row-major C order): Convert rank to ndims-dimensional coordinates using successive modulo/division in row-major order. coords[ndims-1] = rank % dims[ndims-1]; rank /= dims[ndims-1]; repeat for remaining dimensions. O(ndims) time, no allocation.

MPI_Cart_rank: Inverse of MPI_Cart_coords. For each dimension, apply periodic wrap: coord = ((coords[i] % dims[i]) + dims[i]) % dims[i] if periods[i]; else return MPI_ERR_ARG if out-of-range. Accumulate rank as rank = rank * dims[i] + coord. O(ndims) time.

MPI_Cart_shift (I10): Given direction and disp, compute source and destination ranks for a neighbor exchange. Get own coordinates via MPI_Cart_coords. Offset coords[direction] by ±disp. Apply periodic wrap if periods[direction]; else return MPI_PROC_NULL for out-of-range coordinates. Convert back via MPI_Cart_rank. This is a local operation — no communication.

MPI_Dims_create: Factorize nnodes into ndims balanced dimensions. Algorithm: sort free dimensions (those with dims[i] == 0) descending by remaining factor; greedily assign largest factor that divides evenly. Prefer balanced output: minimize max(dims) - min(dims). O(sqrt(nnodes)) trial division.

MPI_Cart_sub (P8 — pre-connect; I10): remain_dims boolean array selects which dimensions to keep. Compute color from the coordinates of the non-remaining dimensions; use MPI_Comm_split(color, key=coords_of_remaining) to create sub-communicators. Attach a reduced cart_topo_t with only the remaining dimensions.

21.1 Objectives

21.2 Detailed Implementation Steps

Window descriptor (ADR-04 — POSIX shm; P10 — zero-copy; P11 — shm transport):

typedef struct {
    void     *base;           /* local window base address */

MPI_Win_create (P10; P11; I11 — shm name nonce): Collective on communicator. Each rank allocates a POSIX shm object named "/mpi_scratch_win_<jobid>_<commid>_<rank>_<nonce>" where nonce is a 64-bit random value (I11). Exchange base addresses, sizes, and shm names via MPI_Allgather. Intra-node peers open each other's shm fds and mmap them; inter-node peers record the remote address for RMA message routing. Initialize win_mutex and set in_epoch = false.

MPI_Win_fence (P10): Issues MPI_Barrier on the window's communicator. Sets in_epoch = !in_epoch (alternating open/close epochs). Assert hints (MPI_MODE_NOSTORE, MPI_MODE_NOPUT, etc.) are accepted but not acted upon; log LOG_DEBUG "fence: assert hints accepted but not implemented".

MPI_Put (P10; ADR-04): Check in_epoch == true; return MPI_ERR_RMA_SYNC if not. Intra-node: memcpy(remote_mmap_ptr + target_disp * disp_unit, origin_buf, origin_count * origin_type.size). Inter-node: send RMA_PUT{target_rank, target_disp, disp_unit, byte_count, payload} message; delivery is asynchronous; fence barrier ensures completion.

MPI_Get (P10): Intra-node: memcpy(origin_buf, remote_mmap_ptr + target_disp * disp_unit, count * type.size). Inter-node: send RMA_GET_REQ message; block until RMA_GET_RESP received with payload; copy into origin_buf.

MPI_Accumulate (P10): Acquire win_mutex. Intra-node: apply op element-wise between origin_buf and remote_mmap_ptr + disp using the predefined operation's function pointer. Inter-node: send RMA_ACCUM{op, target_disp, count, type, payload} message; target applies atomically under its win_mutex. Release mutex.

MPI_Win_free (P10; ADR-04): Collective. MPI_Barrier to ensure all RMA ops complete. Unmap intra-node shm (munmap). Close fds. shm_unlink for own shm object (I11). Free remote_bases, remote_sizes, shm_names, shm_fds arrays. Destroy win_mutex. Return slot to win_table.

21.6 Pitfalls

  • MPI_Win_fence is not free — it issues a full MPI_Barrier. Applications calling fence in a tight loop suffer O(N) synchronization overhead per iteration. Document: prefer bulk RMA between fence pairs.
  • shm name collision — using a deterministic name based only on rank and comm ID causes collisions between concurrent jobs on the same node (I11). Always include a per-job nonce (64-bit random at MPI_Init; broadcast to all ranks).
  • MPI_Accumulate under mutex — for intra-node accumulation, the window mutex is per-window (not per-element). High-concurrency accumulation serializes all N ranks. Document this bottleneck; future work may use per-cache-line locks.
  • Inter-node MPI_Get blocks — unlike MPI_Put, MPI_Get requires a synchronous response (RMA_GET_RESP). This may stall the calling rank if the target rank is busy. The fence at epoch close guarantees eventual delivery but not latency.

21.7 Performance Concerns

  • Intra-node MPI_Put / MPI_Get are pure memcpy after the window is created — no system calls in the critical path. This is the primary performance benefit of ADR-04.
  • MPI_Win_create issues one MPI_Allgather and one shm_open per intra-node peer. For N=1 024 with 32 ranks per node, each rank opens 31 shm fds. Document the fd limit (ulimit -n); recommend at least 64 * ranks_per_node.
  • MPI_Accumulate under win_mutex serializes all accumulations targeting the same window. For reduction patterns, MPI_Reduce is more efficient; MPI_Accumulate is appropriate only for scattered updates.

21.8 Edge Cases

  • Window of size 0: valid (MPI_Win_create with size = 0); MPI_Put / MPI_Get with count = 0 are no-ops.
  • MPI_Put where origin and target are the same rank: intra-node path applies; memcpy of overlapping regions is undefined behavior if ranges overlap — validate and return MPI_ERR_RMA_CONFLICT.
  • disp_unit = 1 (byte addressing): all displacement arithmetic is in bytes; disp * disp_unit == disp. Verify in test_put_get.c with disp_unit = sizeof(int) and disp_unit = 1 variants.
  • MPI_Win_free called while inter-node RMA ops are in flight: the MPI_Barrier inside free ensures all remote puts/gets are complete before shm unmap. Without this barrier, the remote target may read from an unmapped region.
  • Multiple windows on the same communicator: each gets an independent win_table slot and independent shm names. They do not share mutexes.

22. Phase 10 — Fault Tolerance and Error Handling

22.1 Objectives

Implement MPI error handling infrastructure: custom error handlers, predefined handlers (MPI_ERRORS_RETURN, MPI_ERRORS_ARE_FATAL), MPI_Abort, MPI_Error_string, MPI_Error_class, and process failure detection. Provide a finalize timeout mechanism. Stub MPI_Comm_revoke with PhaseDeferred. All error paths must be reachable by test fixtures with zero abort side effects when MPI_ERRORS_RETURN is active.

22.2 Detailed Implementation Steps

Error handler descriptor (P7 — errors return not abort; ADR-09 — THREAD_SERIALIZED error delivery):

typedef void (*MPI_Comm_errhandler_fn)(MPI_Comm *, int *, ...);
typedef struct {
    errhandler_kind_t  kind;   /* RETURN | FATAL | CUSTOM */
    MPI_Comm_errhandler_fn fn; /* only for CUSTOM */
    int                refcount;
} errhandler_desc_t;

MPI_Errhandler is an index into mpi_world_t.errhandler_table[]. Predefined handles: MPI_ERRORS_RETURN = 0, MPI_ERRORS_ARE_FATAL = 1. Both are statically initialized at MPI_Init.

MPI_Comm_create_errhandler: Allocates a new errhandler_desc_t with kind = CUSTOM and stores the function pointer. Returns a handle.

MPI_Comm_set_errhandler: Sets comm_desc_t.errhandler = handle. Decrements old handle's refcount; increments new handle's refcount.

MPI_Comm_get_errhandler: Returns comm_desc_t.errhandler; increments refcount (caller must free).

Error dispatch (P7; ADR-09): Every internal error path calls dispatch_error(comm, errcode). If errhandler.kind == RETURN: store errcode, return to caller. If kind == FATAL: log error with rank/file/line, then call MPI_Abort(MPI_COMM_WORLD, errcode). If kind == CUSTOM: acquire progress_mutex (THREAD_SERIALIZED), call fn(&comm, &errcode), release mutex.

MPI_Abort (I8 — finalize blocks; I6 — initialized flag): Sends an ABORT{errorcode} control message to pmgrd. pmgrd broadcasts SIGTERM to all ranks' process groups and then exits with errorcode. On receipt of SIGTERM, each rank calls exit(errorcode). MPI_Abort does not return.

Process failure detection: The progress thread monitors all peer FDs with poll(). On POLLHUP | POLLERR for a peer FD: mark rank_table[peer].status = RANK_FAILED in mpi_world_t. Log LOG_ERROR "rank <n> connection lost". Subsequent sends to or receives from that rank return MPI_ERR_PROC_FAILED. Full ULFM recovery (MPI_Comm_revoke, MPI_Comm_shrink) is deferred: PhaseDeferred("## 22. Phase 10 — Fault Tolerance and Error Handling").

MPI_Comm_revoke stub: Returns MPI_ERR_UNSUPPORTED_OPERATION and logs PhaseDeferred("## 22. Phase 10 — Fault Tolerance and Error Handling").

Finalize timeout (I8; I6): MPI_Finalize sends FIN to all peers and waits for N−1 FIN responses. A watchdog timer fires after MPI_SCRATCH_FINALIZE_TIMEOUT_SEC seconds (default 30, configurable). On timeout: log LOG_WARN "finalize timeout: missing FIN from ranks <bitmap>" where <bitmap> lists non-responding rank IDs. Then call MPI_Abort(MPI_COMM_WORLD, MPI_ERR_FINALIZE_TIMEOUT).

MPI_Error_string: Table lookup in src/error/error_strings.c mapping errcode integers to human-readable strings. Returns "Unknown error" for unrecognized codes. String length ≤ MPI_MAX_ERROR_STRING.

MPI_Error_class: Maps errcode to its error class (e.g., MPI_ERR_PROC_FAILED → MPI_ERR_PROC_FAILED; MPI_ERR_TRUNCATE → MPI_ERR_OTHER). Defined by lookup table initialized at MPI_Init.

22.6 Pitfalls

  • MPI_ERRORS_ARE_FATAL swallows all errors — default handler on MPI_COMM_WORLD is MPI_ERRORS_ARE_FATAL; any errored call aborts the job. Applications that want to recover must explicitly install MPI_ERRORS_RETURN. Document the default in include/mpi_error.h.
  • MPI_Abort called from signal handler — MPI_Abort is async-signal-safe only if pmgrd communication uses write() (not printf or malloc). Implement abort_send using a fixed-size stack buffer and write() to the pmgrd socket.
  • Finalize timeout and custom errhandler interaction — if the timeout fires and the comm has a custom errhandler, the handler is invoked before MPI_Abort. Ensure the handler is not re-entrant with the progress thread by holding progress_mutex during invocation (ADR-09).
  • MPI_Comm_revoke stub return value — some MPI libraries return MPI_SUCCESS from stubs. Return MPI_ERR_UNSUPPORTED_OPERATION explicitly; log PhaseDeferred. Applications testing for revoke support must check the return code.

22.7 Performance Concerns

  • dispatch_error acquires progress_mutex for custom handlers (ADR-09). In the common case (MPI_ERRORS_RETURN), no lock is taken. Do not add mutex overhead to the return-only path.
  • MPI_Error_string is a table lookup: O(1) with a sorted array + binary search. Total table size is ≤ 128 entries; linear scan is acceptable.
  • Finalize timeout uses a timer_settime POSIX timer, not a polling thread. Zero steady-state overhead after the timer is armed.
  • Process failure detection piggybacks on the existing poll() loop in the progress thread. No additional FDs or threads are required.

22.8 Edge Cases

  • MPI_Abort called before MPI_Init (I6 — initialized flag): log LOG_ERROR "MPI_Abort called before MPI_Init" and call exit(errorcode) directly, bypassing pmgrd.
  • MPI_Finalize called twice: second call returns MPI_ERR_OTHER (I6). Do not send duplicate FIN messages.
  • Custom errhandler that calls MPI_Abort internally: the abort path must not recurse into the dispatch loop. Set a dispatching flag in mpi_world_t and skip handler invocation if already set.
  • MPI_Comm_free_errhandler on a predefined handler (MPI_ERRORS_RETURN, MPI_ERRORS_ARE_FATAL): no-op with MPI_SUCCESS. Predefined handles are never freed.
  • MPI_Error_string with errcode = MPI_SUCCESS: returns "Success", resultlen = 7.

26. Compatibility Guarantees

26.1 MPI Standard Conformance

  • Target: MPI-3.1 subset (Phases 0–10). Functions implemented listed per phase in Appendix B.
  • NOT conformant to: MPI_T (tools interface), MPI-IO, dynamic process management (MPI_Comm_spawn), generalized requests (MPI_Grequest_*).
  • MPI-4.0 partial: MPI_Comm_revoke stub (Phase 10); full ULFM PhaseDeferred("## 22. Phase 10 — Fault Tolerance and Error Handling").

26.2 ABI Stability

  • include/mpi.h: function signatures match MPI-3.1 C binding exactly — programs compiled against Open MPI headers link against libmpi_scratch.so without recompilation (same typedef aliases).
  • Handle types (MPI_Comm, MPI_Datatype, MPI_Op, MPI_Request, MPI_Win, MPI_Group): all defined as int or pointer types matching the standard ABI.
  • MPI_Status layout: matches the standard's required fields (MPI_SOURCE, MPI_TAG, MPI_ERROR).

26.3 Wire Format Versioning

  • mpi_wire_header_t version field (uint16_t at offset 4): currently 0x0001.
  • Future versions increment this field; receivers reject mismatched versions with MPI_ERR_OTHER.
  • No backward compatibility guarantee between versions — all processes in a job must use the same library version.

26.4 Deprecation Policy

  • No public API is deprecated within a major version.
  • Internal types (mpi_internal.h) have no stability guarantee.
  • Environment variable names (MPI_SCRATCH_*) are stable within a major version.

26.5 Rolling Upgrade

  • Not supported: all ranks must run the same library version. Mixed-version clusters produce undefined behavior due to wire format assumptions.

29.4 Optimization Priority

  1. Transport send path (highest impact): Eliminate one buffer copy on the eager intra-node UDS path by using sendmsg with an iovec (header + payload delivered in a single syscall, zero intermediate copy).
  2. Match engine (medium): UMQ scan is O(depth) linear. Switch to a hash table keyed on (source_rank, tag, context_id) when depth exceeds 64 entries.
  3. Request pool (low): Already O(1) alloc/free. Verify no false sharing between adjacent pool entries by confirming each entry is aligned to 64 bytes.
  4. Barrier latency (medium): Dissemination algorithm is O(log N) rounds. At N > 64, evaluate hardware multicast if the interconnect supports it.
  5. Collective algorithm crossover: Empirically measure the eager-to-rendezvous crossover point for each message size; update MPI_EAGER_LIMIT in the configuration based on benchmark results rather than relying on the compile-time default.

30.2 Horizontal vs. Vertical Scaling

Vertical scaling (more cores, single node): UDS transport scales well as long as message rates stay below the kernel socket buffer limit. The primary vertical bottleneck is global_lock: contention becomes measurable at N=16 cores. Mitigation: replace global_lock with per-rank locks, enabling MPI_THREAD_MULTIPLE at the cost of increased lock complexity.

Horizontal scaling (multiple nodes over TCP): TCP RTT on a typical LAN is 50–200 µs. A binomial broadcast at N=256 traverses 8 hops, adding 400–1600 µs of latency. The practical ceiling for latency-sensitive applications over TCP is approximately N=64 processes.

30.4 Scaling Levers

  1. Lazy connection: Connect to a peer on first message rather than during MPI_Init. Reduces O(N²) startup connections to O(active_pairs), which is O(N) or less for sparse communication patterns.
  2. Per-rank locks instead of global_lock: Unlocks MPI_THREAD_MULTIPLE support and eliminates the primary vertical scaling bottleneck, at the cost of additional lock ordering discipline to prevent deadlock.
  3. Hash-indexed UMQ: Replace the linear UMQ scan with a hash table keyed on (source_rank, tag, context_id), delivering O(1) match performance regardless of unexpected-message queue depth.
  4. Pipelined binary tree broadcast: Bandwidth-optimal for large messages; pipeline stages allow concurrent in-flight data across all tree levels simultaneously.
  5. RDMA transport: Replaces TCP with 2–8 µs per-hop latency; requires UCX or libfabric integration. (PhaseDeferred — no section exists yet; use Deferred Features Register anchor rdma-transport.)

31. Mental Models & First Principles

MM1 — Eager/rendezvous is a latency-vs-memory tradeoff, not a free optimization.

Compressed insight: Eager push guarantees low latency but requires the runtime to buffer the message if no matching MPI_Recv is posted. Rendezvous adds one RTT of latency but transfers no data until the receiver is ready, eliminating buffer copies. The threshold MPI_EAGER_LIMIT is a knob trading latency for memory pressure.

What it predicts: Below threshold, latency dominates; above threshold, buffer exhaustion dominates.

Bug class without it: Setting MPI_EAGER_LIMIT=∞ on a system with large messages causes OOM when UMQ holds many buffered payloads.

Applied in: §4 (System Constraints, eager limit row), §6 P3, §8.2 (wire header RTS/CTS), §14 Phase 2, §30.2 scaling analysis.

MM2 — Message matching is ordered per (communicator, source, tag) triple, not globally.

Compressed insight: MPI §3.5 guarantees that if rank A sends two messages to rank B with the same tag and communicator, they are received in send order. It makes NO guarantee about ordering between different source ranks or different tags. The match engine must enforce per-pair FIFO, not global FIFO.

What it predicts: A global FIFO would serialize all communication — both incorrect per spec and catastrophically slow.

Bug class without it: Implementing a global message queue that delivers messages in wall-clock arrival order — this passes most tests but fails any program that sends with MPI_ANY_SOURCE and expects per-source ordering.

Applied in: §6 P5, §7 I2, §8.4 (matching state machine), §13 Phase 1.

MM3 — Unexpected messages need a separate queue; the dual-queue (PRQ+UMQ) is not an optimization but a semantic requirement.

Compressed insight: MPI does not require the sender to wait for a matching MPI_Recv before sending. The runtime must buffer (in UMQ) or match (against PRQ) on message arrival. Without UMQ, every MPI_Send would block until a matching MPI_Recv is posted — turning MPI into synchronous channels, breaking any program that sends before the receiver is ready.

What it predicts: A single-queue implementation passes tests where sends and receives are perfectly synchronized, but fails in real programs.

Bug class without it: Deadlock in ping-pong where rank 0 sends to rank 1 before rank 1 posts its recv.

Applied in: §6 P9, §7 I3, §8.4, §11 (prq_entry_t / umq_entry_t types), §12 Phase 0.

MM4 — Collectives are latency-optimal or bandwidth-optimal, never both simultaneously.

Compressed insight: Binomial tree bcast has O(log N × α) latency but sends the full message along each of log N tree edges — bandwidth wasted by redundant copies at intermediate nodes. Ring allreduce has O(N × α) latency but O(count/N × β) bandwidth per step — bandwidth-optimal at large count. The crossover (log N × α / (N × α) = log N / N) determines which algorithm wins.

What it predicts: For small messages (latency-dominated), binomial tree wins; for large messages (bandwidth-dominated), ring wins.

Bug class without it: Using binomial tree for 100 MB allreduce saturating root's NIC.

Applied in: §6 P6, §8.5 (collective complexity table), §15 Phase 3, §16 Phase 4, §29.4 optimization priority.

MM5 — Progress requires either a dedicated thread or explicit polling; no free lunch.

Compressed insight: Non-blocking MPI_Isend/Irecv must make forward progress even when the calling thread is computing. This requires either (a) a background progress thread that calls poll() on all FDs, or (b) the application explicitly calling MPI_Test to trigger progress. Without progress, MPI_Wait after Isend can hang forever if the receiver is also blocking in MPI_Wait without a progress thread.

What it predicts: A runtime without a progress thread fails any overlap test.

Bug class without it: MPI_Isend + 1 second compute + MPI_Wait — the wait blocks because no progress happened during compute.

Applied in: §6 P8, §7 I7, §18 Phase 6, §29.4.

MM6 — Communicator context IDs prevent cross-communicator message leakage; the ID must be in every envelope.

Compressed insight: Two ranks communicating on MPI_COMM_WORLD and on a sub-communicator created by MPI_Comm_split can have the same rank numbers and tag values. Without a context_id in the envelope, messages cross communicator boundaries. The context_id must be established collectively so all ranks agree.

What it predicts: Any implementation that matches on (source, tag) only — omitting context_id — will have library code (which uses internal communicators) leak messages into user communicators.

Bug class without it: MPI_Comm_dup isolation test fails — send on WORLD matched by recv on dup.

Applied in: §6 P2, §7 I1, §8.1 (envelope definition), §11 (mpi_envelope_t), §17 Phase 5.

MM7 — Connection setup cost is O(N²); this dominates MPI_Init for large N and must be accounted for at design time.

Compressed insight: Establishing all-to-all connections at MPI_Init means N processes each open N-1 sockets — O(N²) total connect/accept syscalls plus O(N²) FDs held. At N=64, this is 4096 connections taking ~80 seconds. Prediction: a system designed without this insight discovers at N=64 that MPI_Init is slower than the actual computation.

What it predicts: A system designed without this insight discovers at N=64 that MPI_Init is slower than the actual computation.

Bug class without it: Setting ulimit to default 1024 FDs and hitting EMFILE at N=32.

Applied in: §4 (FD budget row), §24 scalability, §30.1 (O(N²) row), §30.4 (lazy connection lever).

MPICH: MPICH's key architectural bet is the Abstract Device Interface (ADI), now ADI4. Every transport (shared memory, TCP, RDMA, OFI) plugs into a single channel/netmod interface, allowing MPICH to run on any network by swapping one module. This wins in research environments where portability across wildly different interconnects matters more than peak performance on any one — it is the standard against which all MPI conformance is measured (§6 P2, Gropp & Lusk 1996).

Open MPI: Open MPI's distinguishing choice is the Modular Component Architecture (MCA), which decomposes the runtime into independently versioned, run-time selectable components for transport (BTL), collectives (coll), process management (pml), and more. This wins in production HPC clusters where system administrators need to swap components (e.g., upgrade the InfiniBand BTL without recompiling the MPI library) and where third-party vendor components (NVIDIA NCCL-based coll) need to plug in without forking the runtime.

MVAPICH2: MVAPICH2's defining decision is first-class InfiniBand RDMA support — it bypasses the kernel TCP stack entirely for inter-node communication, achieving 1–2 µs latency vs. 50+ µs for TCP. This wins on InfiniBand clusters running large-scale scientific simulations where inter-node latency is the dominant cost (§6 P6, Panda et al. 2013). It loses on Ethernet-only clusters where its complexity does not pay off.

Intel MPI: Intel MPI's distinguishing feature is auto-tuning via online profiling and the MPI_T (tools interface) to expose internal parameters. It integrates with Intel VTune Profiler and Intel Advisor for automatic collective algorithm selection. This wins in production workflows on Intel Xeon clusters where an operator wants push-button performance tuning without manual algorithm selection — particularly for irregular collective patterns that a static table (like this design's §9 ADR-21) cannot anticipate.

Microsoft MPI: Microsoft MPI's key decision is Windows-native deployment using Windows Job Objects for process management, WinSock2 for transport, and IOCP for async progress. This wins when the target platform is a Windows HPC Server cluster, which historically dominated academic and financial modeling workloads that predated Linux dominance in HPC. It loses on any Linux/InfiniBand cluster.

33. Back-of-Envelope Capacity Model

All numbers derived from §4 System Constraints. Show formula for each.

C1 — Eager buffer memory for one outstanding unexpected message: From §4: mpi_wire_header_t = 32 bytes; UMQ entry overhead = 64 bytes; max eager payload = MPI_EAGER_LIMIT = 65,536 bytes. Per UMQ entry: 64 + 65,536 = 65,600 bytes ≈ 64 KB.

C2 — Total UMQ buffer memory at full depth: From §4: UMQ depth limit = 4,096 entries × 65,600 bytes/entry = 268,697,600 bytes ≈ 256 MB. This is the worst-case heap for the unexpected queue. In practice most UMQ entries hold small messages — median real UMQ memory is 1–5 MB.

C3 — FD budget per rank at N=64 (all-to-all): From §4: N−1 = 63 data FDs (one per peer) + 1 pmgrd control FD + 3 stdio FDs = 67 FDs per rank. Total FDs in job: 64 ranks × 67 = 4,288 FDs (well within ulimit 65536; exceeds default 1024 → must set ulimit before launch).

C4 — Startup connection time at N=64: From §4: MPI_Init at N=64 estimated < 5 s with all-to-all connections. Per-connection cost estimate: 5 s / (64 × 63) = 5 / 4032 ≈ 1.24 ms per connection (includes fork+exec + TCP handshake).

C5 — Allreduce time estimate (ring algorithm, N=16, 1 MB message, UDS): From §4: α (UDS p50) = 5 µs; bandwidth = 5 GB/s → β = 1 / 5 GB/s = 0.2 ns/byte. Ring allreduce: 2 × (N−1) steps, each transferring count/N bytes. Step latency = α + (count/N) × β = 5 µs + (1,048,576 / 16) × 0.2 ns = 5 µs + 65,536 × 0.2 ns = 5 µs + 13.1 µs = 18.1 µs per step. Total: 2 × 15 steps × 18.1 µs = 543 µs. (Compare: target §29.3 M7 = <150 µs for 1 KB N=4; this is 1 MB N=16, so 543 µs is consistent.)

C6 — Binomial bcast time estimate (N=8, 1 MB message, TCP loopback): From §4: α (TCP loopback p50) = 50 µs; TCP bandwidth = 1 GB/s → β = 1 ns/byte. Depth = ceil(log2(8)) = 3 rounds. Time = depth × (α + M × β) = 3 × (50 µs + 1,048,576 × 1 ns) = 3 × (50 µs + 1,049 µs) = 3 × 1,099 µs = 3,297 µs ≈ 3.3 ms.

C7 — Recursive halving-doubling allreduce time (N=8, 1 KB message, TCP): From §4: α = 50 µs; 1 KB = 1,024 bytes; β = 1 ns/byte. log2(8) = 3 rounds, each: α + M×β = 50 µs + 1,024 ns ≈ 51 µs. Total: 3 × 51 µs = 153 µs. (Matches §29.3 M7 target of <150 µs — this is N=8 not N=4; N=4 gives 2×51 = 102 µs.)

C8 — Request pool memory: From §4: mpi_request_t = 128 bytes; pool size = 1,024 requests. Pool heap: 1,024 × 128 = 131,072 bytes = 128 KB (contiguous slab; fits in L2 cache).

C9 — Per-communicator memory overhead: From §4: group table = 4 × N bytes (world_ranks array of int). At N=64: mpi_comm_t overhead per communicator = 4 × 64 = 256 bytes + struct overhead ≈ 320 bytes. At 1,000 communicators: 320 KB total — negligible.

C10 — Wire header overhead fraction for small messages: From §4: mpi_wire_header_t = 32 bytes. For an 8-byte message: overhead = 32 / (32 + 8) = 80% of bytes are header. For a 1 KB message: overhead = 32 / (32 + 1024) = 3%. This is why latency (not bandwidth) dominates for small messages — the 80% header fraction makes bandwidth irrelevant for 8B; reducing α (latency) is the only lever.

35. Alternative Architectures (Roads Not Taken)

Alt-1 — PGAS / One-Sided-First (OpenSHMEM / UPC / GASNet)

Process 0: [Local Heap] <--symm addr--> [Shared Segment]
Process 1: [Local Heap] <--symm addr--> [Shared Segment]
                               |
              shmem_put(target_addr, src, len, pe=1)
              -- no matching recv required --
              -- target address is symmetric (same virtual addr on all PEs) --

In PGAS (Partitioned Global Address Space), every process exposes a symmetric heap — the same virtual address on every PE maps to that PE's local memory via RDMA. A shmem_put is a one-sided write with no matching receive; progress is implicit via RDMA hardware completion queues. There are no message envelopes, no tag matching, no UMQ.

Regime where it wins: Irregular, pointer-chasing access patterns (sparse matrix-vector multiply, graph analytics, stencil codes with dynamic boundaries) where the sender knows the destination address but cannot predict when the receiver will be ready. PGAS eliminates the overhead of envelope matching and receiver-side buffering entirely.

Real system embodying it: OpenSHMEM 1.5 specification (openshmem.org); reference implementation: Sandia OpenSHMEM (§5 R7). Also: UPC (Unified Parallel C), Co-Array Fortran, GASNet (Lawrence Berkeley National Laboratory).

Why rejected here: Two-sided MPI is the dominant HPC programming model and the learning objective (§2). PGAS requires symmetric memory allocation — all PEs must call shmem_malloc with the same size in the same order, a severe constraint. PGAS has no collective communication model comparable to MPI collectives. This project's goal is MPI conformance; PGAS is a different abstraction entirely.

Alt-2 — Active Messages Runtime (AM-based MPI like GASNet or early Cray SHMEM)

Sender:
  AM_send(target_pe=1, handler_fn_id=42, args..., payload)
  -- returns immediately --

Target PE 1:
  [AM handler thread wakes on network interrupt]
  -> calls registered handler_fn[42](args..., payload)
  -> handler runs in target's context; may modify local state

In an active-messages runtime, a send delivers both data AND a handler function identifier. On arrival, the target machine executes the registered handler in a lightweight context. There is no separate receive — the handler IS the receive operation. This enables completely asynchronous, handler-driven communication.

Regime where it wins: Fine-grained irregular communication where message arrivals must trigger immediate computation (e.g., distributed hash table operations, dynamic load balancing, task-based runtimes). Active messages achieve lower latency than two-sided because there is no poll-for-receive step — the hardware interrupt drives the handler.

Real system embodying it: GASNet (gasnet.lbl.gov) — the transport layer underlying UPC and Titanium. Early Cray T3D/T3E SHMEM used active-message semantics. Chapel's runtime uses GASNet AM for remote procedure calls.

Why rejected here: Active messages require a handler registration API and a trusted handler table — significantly more complex ABI than MPI's stateless send/receive. Security: a handler executing in the target's context with attacker-controlled arguments is a remote code execution vector. The MPI standard is defined in terms of two-sided matching, not active messages; building MPI semantics on top of AM adds a translation layer without simplifying the implementation.

Alt-3 — Sockets-Only Portability Layer (TCP-only, no UDS/SHM)

All ranks -> TCP loopback (127.0.0.1) for intra-node
All ranks -> TCP Ethernet for inter-node
No POSIX shared memory. No UNIX domain sockets.
Single transport: tcp.c handles all cases.

A sockets-only implementation uses TCP for all communication — both intra- and inter-node. POSIX shm and UDS are eliminated entirely. The implementation is a pure subset of BSD sockets.

Regime where it wins: Maximum portability across operating systems (Linux, macOS, Windows, AIX, Solaris) and environments (containers without shm_open access, sandboxes with restricted syscalls). A Docker container with --ipc=none cannot use shm_open; a sockets-only implementation works in any container. Also wins when the implementation must be audited and the auditor is unfamiliar with POSIX IPC.

Real system embodying it: MPICH's ch3:sock channel implements TCP sockets only, no shared memory shortcuts. Microsoft MPI also uses WinSock2 exclusively.

Why rejected here: TCP loopback latency is 50+ µs (§4) vs. UDS at 5 µs (§4) — a 10× latency penalty for intra-node communication. For shared-memory RMA (§21 Phase 9), TCP would require a server thread on the target to receive PUT messages — adding complexity and a round-trip that POSIX shm eliminates entirely. The whole point of UDS/shm is to exploit the OS's knowledge that both endpoints are on the same kernel.

Alt-4 — Task-Based Async Runtime (Charm++, HPX, Legion)

Task graph:
  [Task A: matrix_mul local_rows] --> [Reduction task at root]
        |  (on completion)
  [Task B: stencil update] --> [Halo exchange async]

Runtime: schedules tasks across PEs based on data availability.
No explicit MPI_Send/Recv -- data movement is implicit in task dependencies.

Task-based runtimes model parallel computation as a DAG of tasks with data dependencies. Communication is implicit: when Task B on PE 1 needs data produced by Task A on PE 0, the runtime automatically transfers it. There are no explicit send/receive calls.

Regime where it wins: Irregular, dynamic parallelism where the task graph is not known at compile time (adaptive mesh refinement, N-body simulations with load imbalance, sparse direct solvers). Task runtimes can overlap communication and computation automatically without the programmer reasoning about non-blocking operations. They also handle load imbalance via work stealing.

Real system embodying it: Charm++ (Illinois, charmplusplus.org); HPX (STE||AR Group, hpx.stellar-group.org); Legion (Stanford/NVIDIA, legion.stanford.edu); PaRSEC (ICL UTK).

Why rejected here: Task-based runtimes require a fundamentally different programming model — no existing MPI code runs on Charm++ without a complete rewrite. The learning objective (§2) is MPI, not task-based parallelism. Task runtimes have higher runtime overhead for bulk-synchronous workloads (matrix multiply, FFT) where the communication pattern is regular and statically known — exactly the benchmark workloads this project targets.

37. Glossary

ADI (Abstract Device Interface): The internal layering boundary in MPICH between the MPI API and the transport channel. Equivalent in this design: transport_ops_t vtable (§9 ADR-01, R1).

Allgather: A collective operation in which every rank contributes a buffer and every rank receives the concatenation of all contributions. Equivalent to MPI_Gather(root=0) + MPI_Bcast(root=0) for Phase 4; ring allgather is PhaseDeferred (§16).

Allreduce: A collective that applies a reduction operator across all ranks and distributes the result to every rank. Implemented in Phase 3 as reduce-then-broadcast; ring allreduce for large messages in Phase 4 (§15, §16).

Backpressure: The mechanism by which a full UMQ blocks the sender from sending more messages, preventing unbounded memory growth (I3, P9, §14 Phase 2).

Binomial Tree: A recursive communication tree topology used for broadcast and reduce collectives. At step k, each active rank communicates with its partner at distance 2^k. Depth is O(log N); used for MPI_Bcast and MPI_Reduce in Phase 3 (§15).

BSP (Bulk Synchronous Parallel): A parallel computation model with alternating computation supersteps and barrier synchronization phases. MPI's collective operations map naturally onto the BSP superstep boundary.

BTL (Byte Transfer Layer): Open MPI's transport abstraction layer, analogous to this design's transport_ops_t vtable. Each BTL handles one network type (TCP, shared memory, InfiniBand). (R2, §32)

Collective Operation: An MPI operation that must be called by all ranks in a communicator. Collectives include MPI_Bcast, MPI_Reduce, MPI_Scatter, MPI_Gather, MPI_Allreduce, MPI_Barrier, and MPI_Alltoall. Collective semantics require that all ranks enter the call before any rank may exit (§15, §16).

Communicator: An MPI object that encapsulates a group of ranks and a communication context. Every MPI operation is scoped to a communicator. MPI_COMM_WORLD is the default communicator containing all ranks (§11.2, mpi_comm_t).

Context ID: A unique integer assigned to each communicator that is included in every message envelope. Messages sent on communicator A cannot be received by a posted recv on communicator B, even if source rank and tag match, because context_id differs (I1, §11.2).

Datatype: An MPI abstraction describing the memory layout of a message buffer. Built-in datatypes (MPI_INT, MPI_DOUBLE) map directly to C primitive types. Derived datatypes (MPI_Type_vector, MPI_Type_struct) describe non-contiguous layouts and are PhaseDeferred to Phase 7 (§19, §11.8).

Deadlock: A state where two or more ranks each block waiting for the other to progress, with no rank able to advance. The classic MPI deadlock: two ranks each call MPI_Send before MPI_Recv, filling kernel buffers. MPI_Sendrecv prevents this by posting the recv first (§13.2 Step 2).

Dissemination Barrier: A barrier algorithm with O(log N) rounds. In round k, each rank sends to and receives from its partner at offset 2^k. All ranks are synchronized after ceil(log2(N)) rounds. Used for MPI_Barrier in Phase 0 (§12, §15).

Eager Protocol: A message delivery strategy where the sender transmits the message payload immediately without waiting for a receive to be posted. Appropriate for small messages where buffering in the UMQ is acceptable. Used for messages below MPI_EAGER_LIMIT (default 64 KB) (§14, I3).

Epoch (RMA): The interval between MPI_Win_fence calls during which MPI_Put, MPI_Get, and MPI_Accumulate are valid. Calls outside an active epoch are a usage error and return MPI_ERR_RMA_SYNC (§21, Phase 9).

Envelope: The four-tuple (source_rank, destination_rank, tag, context_id) that identifies a message for matching purposes. An arriving message is matched against posted receives by comparing envelopes, with wildcard support for source and tag (§11.6, mpi_envelope_t).

Extent: The distance in bytes between the start of one element and the start of the next element in a datatype array. For MPI_INT, extent == sizeof(int). For derived datatypes, extent is the distance from the first byte of the lower bound to the last byte of the upper bound plus one (§11.8, mpi_datatype_desc_t.extent).

False Sharing: A cache-performance problem where two threads modify adjacent but logically independent variables that reside on the same cache line. Relevant to the progress thread accessing request state alongside user-thread reads of the same request pool (§18, Phase 6).

Group: An ordered set of MPI process ranks. Every communicator is associated with a group. Group operations (MPI_Group_union, MPI_Group_intersection, MPI_Group_difference) create new groups that can be used to construct new communicators via MPI_Comm_create (§17, Phase 5).

Hydra: The process manager used by MPICH. Hydra handles process spawning, PMI key-value exchange, and process teardown. In this design, pmgrd fills the equivalent role (§8.3, §9 ADR-08, §32).

LogP Model: A parallel performance model parameterized by Latency (L), overhead (o), gap (g), and Processors (P). Used to predict collective algorithm performance and to reason about the crossover point between eager and rendezvous protocols (§14, §33).

Match Engine: The subsystem responsible for comparing arriving message envelopes against posted receive requests and routing messages to the correct buffer. Implemented in match/prq.c and match/umq.c (§11.6, §12, §13).

MPI_IN_PLACE: A sentinel buffer pointer indicating that the send and receive buffers for a collective are the same memory region. Reduces buffer allocation for in-place allreduce. PhaseDeferred to Phase 5 (§15, §17).

MPI_PROC_NULL: A sentinel rank value (-2 in this implementation) that makes MPI_Send and MPI_Recv silently no-op. Used to simplify boundary handling in stencil codes without conditional logic (§8.2, mpi_constants.h).

Non-Blocking Operation: An MPI communication operation that returns immediately with a request handle, allowing the application to overlap computation with communication. Includes MPI_Isend, MPI_Irecv, MPI_Wait, MPI_Test. PhaseDeferred to Phase 6 (§18, §11.7).

NUMA (Non-Uniform Memory Access): A memory architecture where access latency depends on which NUMA node the memory resides on relative to the accessing CPU. Relevant to the shared-memory transport backend: allocating shared regions on the correct NUMA node reduces latency (§9 ADR-01, §32).

Pack/Unpack Engine: The subsystem that serializes non-contiguous derived datatype buffers into a contiguous byte stream for transmission, and deserializes them on receipt. Implemented in datatype/pack.c (§19, Phase 7).

PMI (Process Management Interface): A standard API between the process manager and MPI processes for key-value store operations and barrier synchronization. MPICH uses PMI2/PMIx; this design uses a custom text protocol in pmgrd (§8.3, §9 ADR-08).

pmgrd: The process manager daemon in this implementation. Spawns MPI processes, distributes rank tables, manages teardown. Equivalent to MPICH's hydra_pmi_proxy or Open MPI's orted (§8.3, §12 Phase 0).

PRQ (Posted Receive Queue): A linked list of pending MPI_Recv requests that have been registered by the application but have not yet been matched by an arriving message. Each entry holds the envelope (with optional wildcards), the receive buffer pointer, and the associated request handle (§11.6, prq_entry_t).

Rank: An integer identifier for a process within a communicator. Ranks are zero-indexed. Rank within MPI_COMM_WORLD is globally unique; rank within a sub-communicator is local to that communicator (§11.1, §11.2).

Rank Table: The runtime data structure mapping each rank to its transport endpoint (host, port, UDS path, FD, transport type). Built during MPI_Init and referenced by every send/receive (§11 rank_table_t, §12 Phase 0).

Recursive Halving-Doubling: A collective algorithm pattern used for allreduce and reduce-scatter. In the halving phase, each rank exchanges partial results with partners at decreasing distances, halving the problem size each round. In the doubling phase, results are distributed back. Achieves O(log N) rounds with 2(N-1)/N bandwidth efficiency (§15, §16).

Rendezvous Protocol: A message delivery strategy for large messages where the sender first transmits a Ready-to-Send (RTS) control message and waits for a Clear-to-Send (CTS) reply before transmitting the payload. Prevents unbounded UMQ growth by ensuring the receiver has buffer space before payload transmission begins (§14, Phase 2, I3).

Ring Allreduce: An allreduce algorithm where ranks are arranged in a logical ring. Each rank sends to its right neighbor and receives from its left neighbor in N-1 rounds. Achieves near-optimal bandwidth utilization for large messages; used for large allreduce in Phase 4 (§16).

SPMD (Single Program Multiple Data): The parallel programming model where all ranks execute the same program but operate on different data partitions. MPI programs are inherently SPMD: every rank calls MPI_Init and runs the same binary, branching on rank (§1, §2).

Tag: A non-negative integer attached to a message that allows the receiver to distinguish between messages from the same source. The sentinel MPI_ANY_TAG (-1) matches any tag in a posted receive. Valid tags are in [0, MPI_TAG_UB] (§13, mpi_wire_header_t).

Transport Abstraction Layer: The vtable-based abstraction (transport_ops_t) that decouples the match engine and collective algorithms from the underlying network transport. Concrete backends include TCP, UNIX domain sockets, and POSIX shared memory (§9 ADR-01, §11.4).

ULFM (User-Level Failure Mitigation): An MPI Forum extension proposal that adds fault-tolerant communicator operations including MPI_Comm_revoke, MPI_Comm_shrink, and MPI_Comm_agree. MPI_Comm_revoke is stubbed as PhaseDeferred in Phase 10 (§22).

UMQ (Unexpected Message Queue): A bounded queue of messages that arrived before a matching MPI_Recv was posted. Bounded at MPI_SCRATCH_UMQ_DEPTH (4096 entries by default) to prevent unbounded memory growth; overflow triggers backpressure on the sender (I3, §11.6, umq_entry_t).

Window (RMA): An MPI memory region registered for one-sided remote access via MPI_Win_create. Other ranks may perform MPI_Put, MPI_Get, and MPI_Accumulate on the window within an active epoch. Windows are freed with MPI_Win_free (§21, Phase 9).

Wire Header: The 32-byte fixed-format binary header prepended to every message in this implementation. Contains magic number, version, msg_type, source_rank, dest_rank, tag, context_id, data_length (§8.2, §11 mpi_wire_header_t, I4).
