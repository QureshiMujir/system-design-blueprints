⬜ Phase 0 — Process Model and Bootstrap §12

Objectives

Stand up the minimum viable MPI runtime on a single Linux host:

  • Implement pmgrd: a process-manager daemon that fork+exec's N rank processes, distributes the rank address table, and coordinates the ALL_READY barrier before releasing ranks into MPI_Init.
  • Author the ABI header (mpi_scratch.h) so rank processes link against libmpi_scratch.so with signatures matching MPI-3.1.
  • Establish the UDS transport: one bidirectional SOCK_STREAM socket per rank-pair, pre-connected during MPI_Init (P8, ADR-03).
  • Implement blocking point-to-point: MPI_Send and MPI_Recv over the UDS backend.
  • Implement the dissemination barrier: MPI_Barrier using ⌈log₂N⌉ rounds of pairwise message exchange.
  • Package the above as libmpi_scratch.so and ship a minimal mpirun_scratch launcher.
Deliverable
  • libmpi_scratch.so containing MPI_Init, MPI_Finalize, MPI_Comm_rank, MPI_Comm_size, MPI_Send, MPI_Recv, MPI_Barrier.
  • mpirun_scratch launcher binary (fork+exec model, local only).
  • pmgrd daemon binary.
  • Conformance fixtures: ping_pong, ring_pass, barrier_sync (see §12.5).
  • docs/runbooks/debugging-hang.md documenting the ALL_READY hang and MPI_Finalize deadlock runbooks.

Pitfalls
  • Partial sends on UDS. write() on a SOCK_STREAM socket may return fewer bytes than requested if the kernel send buffer is full. The send loop must retry until len bytes are confirmed written; a one-shot write() is a latent correctness bug.
  • READY race. A rank that sends LISTEN_READY before calling listen() may cause the first connect() from a peer to get ECONNREFUSED. Step 8 must follow step 7 strictly; add a listen() call before LISTEN_READY.
  • MPI_Finalize deadlock. If any rank calls MPI_Finalize without having consumed all messages in its UMQ, peers waiting for a matching receive will block forever. All messages must be consumed before MPI_Finalize.
  • Environment variable limits. Passing large rank tables via environment variables hits execve argument+environment size limits (typically 128 KB on Linux). For N > 64, use the pmgrd control socket to deliver the rank table post-exec, not via environment.
  • POLLHUP on UDS. If a rank crashes before sending MSG_FIN, surviving ranks' poll() call returns POLLHUP on the dead rank's fd. This must be treated as an implicit MSG_FIN with an error flag, not an infinite block.

⬜ Phase 1 — Point-to-Point Communication (Full Envelope Semantics) §13

Objectives

Extend blocking P2P to the full MPI envelope specification:

  • Implement wildcard matching: MPI_ANY_SOURCE and MPI_ANY_TAG in posted receives, with FIFO ordering per (source, tag, context_id) triple (P5, I2).
  • Implement MPI_Sendrecv and MPI_Sendrecv_replace for deadlock-free simultaneous send+receive.
  • Implement MPI_Probe (blocking) and MPI_Iprobe (non-blocking) to inspect the next matching message without consuming it.
  • Implement MPI_Get_count to retrieve the byte count of a received message from its MPI_Status.
  • Enforce MPI_TAG_UB (upper bound for valid tags, minimum 32767 per MPI-3.1 §3.6).
  • Wire up MPI_Status fields: MPI_SOURCE, MPI_TAG, MPI_ERROR populated on every MPI_Recv completion.
Deliverable
  • Updated match/prq.c and match/umq.c supporting wildcard envelopes.
  • api/point_to_point.c entries for MPI_Sendrecv, MPI_Probe, MPI_Iprobe, MPI_Get_count.
  • Conformance fixtures: tag_matching, any_source, sendrecv_deadlock_free, probe_ordering (see §13.5).
  • Updated include/mpi_api.h with full MPI_Status struct and MPI_TAG_UB constant.

Pitfalls
  • Wildcard recv bypasses FIFO per-triple. If the scan does not preserve insertion order within a (ANY_SOURCE, tag, context_id) scope, messages from different sources can overtake each other in ways that violate application assumptions. Test any_source specifically verifies arrival-order delivery.
  • MPI_Probe does not consume. A common mistake is to implement MPI_Probe by dequeueing the UMQ entry. The entry must remain in place; only the subsequent MPI_Recv removes it. Removing it in Probe causes the message to be "lost" if the process does not immediately call Recv.
  • MPI_Sendrecv with same send and receive buffer. MPI_Sendrecv_replace requires copying the send data before overwriting the buffer. Not handling this case causes self-corruption.
  • MPI_Get_count on truncated message. If payload_len % sizeof(datatype) != 0, the count is undefined. Return MPI_UNDEFINED (-1), not zero or a truncated integer, to match spec.

⬜ Phase 2 — Envelope, Matching, and Rendezvous Protocol §14

Objectives

Extend the transport and match engine to handle large messages correctly and add the three additional send modes:

  • Implement the eager/rendezvous threshold protocol: messages below MPI_EAGER_LIMIT (default 64 KB) use eager send; messages at or above use RTS/CTS rendezvous (P3, ADR-06, I3).
  • Implement MPI_Ssend (synchronous send): does not return until the receiver has posted MPI_Recv, guaranteeing the receiver has entered the matching call.
  • Implement MPI_Bsend (buffered send): copies the message into a user-provided buffer attachment, allowing MPI_Bsend to return before the receiver is ready.
  • Implement MPI_Rsend (ready send): caller asserts the receiver has already posted MPI_Recv; if not, behavior is erroneous (used for performance, not safety).
  • Bound the UMQ (I3) and verify that rendezvous prevents OOM on large message flows.
Deliverable
  • Updated src/transport/uds.c with rendezvous RTS/CTS state machine.
  • Updated api/point_to_point.c with MPI_Ssend, MPI_Bsend, MPI_Buffer_attach, MPI_Buffer_detach, MPI_Rsend.
  • Conformance fixtures: rendezvous_1mb, ssend_ordering, bsend_delivers, rsend_misuse (see §14.5).
  • Updated MPI_EAGER_LIMIT documented in include/mpi_constants.h.

Pitfalls
  • Rendezvous ACK ordering. If the receiver sends the RENDEZVOUS_ACK before allocating the receive buffer, a fast sender may start writing body bytes before the buffer pointer is set. The ACK must be sent only after the body buffer is allocated and the receive is fully registered.
  • Ssend ACK lost on receiver crash. If the receiver crashes after posting MPI_Recv but before sending MSG_SSEND_ACK, the sender blocks forever. Add a MPI_SCRATCH_SSEND_TIMEOUT_SEC knob (default 60s) to detect this.
  • Bsend buffer overflow. If the user attaches a buffer too small for the pending sends, MPI_Bsend returns MPI_ERR_BUFFER. Document that MPI_Buffer_detach must be called to reclaim the buffer after all sends complete; calling it while sends are pending blocks.
  • UMQ backpressure deadlock. If rank A is backing up rank B's UMQ (B is not reading), and rank B is simultaneously blocking on a send to rank A, both ranks deadlock. The backpressure mechanism must not hold UDS recv buffers while a send is in progress on the same rank.

⬜ Phase 3 — Collective Operations: Broadcast and Reduce §15

Objectives

Implement the first tier of collective operations on top of the Phase 0–2 P2P substrate:

  • Implement MPI_Bcast using the binomial tree algorithm for small messages (P3 Thakur 2005, ADR-21).
  • Implement MPI_Reduce with all standard reduction operators (MPI_SUM, MPI_MAX, MPI_MIN, MPI_PROD, MPI_LAND, MPI_LOR, MPI_BAND, MPI_BOR) using the binomial tree algorithm (P6, I10).
  • Implement MPI_Allreduce as a reduce-then-broadcast (Phase 3 default) and as recursive halving-doubling for power-of-2 N (§8.5 algorithm table, ADR-21).
  • Implement the ring allreduce algorithm for large messages and non-power-of-2 N.
  • Enforce collective ordering invariant I10: all ranks must enter a collective in the same order; internal tags are communicator-scoped to prevent collision with user P2P messages.
  • All collectives use MPI_COMM_WORLD in Phase 3; communicator generalization is Phase 5.
Deliverable
  • src/collective/bcast.c — binomial tree and pipeline variants.
  • src/collective/reduce.c — binomial tree, all 8 operators.
  • src/collective/allreduce.c — reduce-then-bcast, halving-doubling, ring variants.
  • Updated src/collective/barrier.c — dissemination barrier already in Phase 0; verify tag isolation.
  • Conformance fixtures: bcast_int, reduce_sum, allreduce_correctness (see §15.5).

Pitfalls
  • Non-commutative reduce ordering. MPI_SUM on integers is commutative, but the standard still requires that the result is as if ranks contributed in rank order (for reproducibility across runs). The binomial tree reduce must accumulate in rank order at each node.
  • Collective deadlock from unbalanced calls. If one rank calls MPI_Bcast while another calls MPI_Reduce (both using the same communicator), the internal tag collision causes both to block. This is a user error per MPI-3.1 §5.1, but the implementation should detect it via I10 tag collision counter.
  • Allreduce on non-power-of-2 N. The halving-doubling algorithm requires N to be a power of 2. The static dispatch table (ADR-21) must fall back to reduce-then-bcast for non-power-of-2 N.
  • Root rank validation. MPI_Reduce and MPI_Bcast require 0 ≤ root < size. Return MPI_ERR_ROOT otherwise; do not proceed to the algorithm.

⬜ Phase 4 — Collective Operations: Scatter, Gather, Allreduce (Ring), Alltoall §16

Objectives

Complete the full Phase 4 collective suite:

  • Implement MPI_Scatter (root distributes distinct chunks to each rank) and MPI_Gather (root collects one chunk from each rank) using the flat tree algorithm (§8.5, ADR-21).

Pitfalls
  • Scatter/gather root participates. The root rank both sends to peers and copies its own chunk locally (via memcpy, not MPI_Send). A common mistake is to have the root send to itself over the socket, causing a self-deadlock.
  • MPI_Alltoall deadlock. If all N ranks simultaneously try to MPI_Send before any calls MPI_Recv, all N sends fill their peer's kernel buffers and all block. The pairwise MPI_Sendrecv approach avoids this but requires the nested loop to pair (i,j) correctly.
  • Scatterv overlap. If displs[r] + sendcounts[r] > displs[r+1], the sent chunks overlap. This is erroneous per spec; validate and return MPI_ERR_COUNT if detected.
  • Allgather vs. Allreduce confusion. MPI_Allgather concatenates, not reduces. Test allgather_correctness explicitly checks that the gathered values are the raw sent values, not sums.
  • Matrix multiply reference tolerance. 512×512 double-precision multiply accumulates rounding error. The tolerance 1e-6 is appropriate; using exact integer comparison will fail due to floating-point non-associativity.

  • Extent vs. size confusion — extent includes padding between elements (for array indexing); size is the actual byte footprint. The pack engine must use size, not extent, for memcpy lengths. Mismatch produces silent data corruption.

  • Uncommitted type in send — check committed == true at the entry of every send/receive path. Return MPI_ERR_TYPE immediately; do not attempt to pack.
  • MPI_Type_free while in flight — an application may free a type after posting MPI_Isend but before the send completes. The pack buffer is allocated before the type is freed, so this is safe only if packing happens synchronously in MPI_Isend. Document this requirement in include/mpi_datatype.h.

⬜ Phase 9 — One-Sided Communication (RMA) §21

Objectives

Implement the MPI one-sided (RMA) communication API: MPI_Win_create, MPI_Win_fence, MPI_Put, MPI_Get, MPI_Accumulate, and MPI_Win_free. Intra-node transfers use POSIX shared memory for zero-copy performance (ADR-04). Inter-node transfers use explicit RMA message types. Pitfalls
  • MPI_Win_fence is not free — it issues a full MPI_Barrier. Applications calling fence in a tight loop suffer O(N) synchronization overhead per iteration. Document: prefer bulk RMA between fence pairs.
  • shm name collision — using a deterministic name based only on rank and comm ID causes collisions between concurrent jobs on the same node (I11). Always include a per-job nonce (64-bit random at MPI_Init; broadcast to all ranks).
  • MPI_Accumulate under mutex — for intra-node accumulation, the window mutex is per-window (not per-element). High-concurrency accumulation serializes all N ranks. Document this bottleneck; future work may use per-cache-line locks.
  • Inter-node MPI_Get blocks — unlike MPI_Put, MPI_Get requires a synchronous response (RMA_GET_RESP). This may stall the calling rank if the target rank is busy. The fence at epoch close guarantees eventual delivery but not latency.
