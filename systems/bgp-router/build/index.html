⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the Cargo workspace (§10), CI matrices, and a minimal correctness kernel: bgp-core's primitive types compiled and property-tested, plus a deterministic simulator harness skeleton that later phases attach invariant assertions to (§7's debugging methodology). No network I/O yet.

Deliverable

cargo build --all-targets --workspace succeeds on Linux/macOS/x86_64 and aarch64; all five CI workflows (§10 .github/workflows/) run green on an empty/no-op basis; BIRD and FRRouting interop containers build.

Acceptance

cargo build --all-targets exits 0 in ≤ 120 s cold (§4 build-time budget); Prefix ordering property test (prop_prefix_ord_matches_bytes) passes 10,000 random cases; interop containers boot and respond to birdc show status / vtysh -c "show version" within 10 s.

Fixtures

fixtures/prefix_ord_v4.json (16 hand-picked IPv4 prefixes with expected trie order) → expected: matches Patricia-trie insertion order; fixtures/prefix_ord_v6.json (IPv6 equivalent) → same; fixtures/ workspace_smoke.toml (minimal valid config) → bgp-config loads it without error (used again from Phase 1 onward).

Pitfalls

CI matrix caching the BIRD/FRR container builds is slow uncached (~8 min); cache by image digest. BGP's well-known port 179 requires CAP_NET_BIND_SERVICE even in CI containers — use rootless port remapping in the interop harness rather than granting the capability broadly. Prefix ordering must sort by address bytes then length, not length-then-bytes, or the trie's longest-prefix-match invariant breaks silently (only surfaces in Phase 3).

⬜ Phase 1 — Message Codec §13

Objectives

Implement encode/decode for all five BGP-4 message types (§8.2) with strict length and flag validation (I4, P12) and zero panics on malformed input.

Deliverable

bgp-codec crate: Codec::decode/Codec::encode (§11) for every Message variant; round-trip property test (decode(encode(m)) == m) for randomly generated valid messages.

Acceptance

100% round-trip pass over 50,000 proptest-generated valid messages (ADR-17); UPDATE decode p50 ≤ 5 µs, p99 ≤ 25 µs on a 1 KB message (M1, §31, measured via bgp-bench); zero panics over the attribute_decode fuzz corpus seed set (§39-listed fixtures) after a 10-minute local run.

Fixtures

fixtures/open_basic.bin → decodes to OpenMessage{version:4, my_as:64500,...}; fixtures/update_full_attrs.bin (all 13 path attributes populated) → full round-trip; fixtures/update_truncated_len.bin (Total Path Attribute Length claims more bytes than present) → CodecError::MalformedAttributeList (I4); fixtures/update_extlen_flag.bin (a 300-byte AS_PATH with Extended-Length flag set) → decodes correctly, regression-guards the pitfall below; fixtures/notification_cease.bin → decodes to ErrorCode::Cease.

Pitfalls

Reading a 1-byte length when the Extended-Length flag (bit 4) is set truncates large attributes (I4) — the single most common BGP codec bug across implementations (§26 FM-1's CVE lineage); the attribute type byte's bit 7 is reserved, not part of the type value, and must be masked off before matching on type code; the 16-byte marker is historically all-1s and some peers (rarely) still validate it — encode it as all-1s even though RFC 4271 marks the check optional today.

⬜ Phase 2 — Finite State Machine & TCP Transport §14

Objectives

Implement the full RFC 4271 §8 state machine (§8.1) over a real TCP transport with MD5 authentication (RFC 2385) and GTSM (RFC 5082), establishing sessions end-to-end with BIRD/FRRouting in the interop containers from Phase 0.

Deliverable

bgp-fsm + bgp-tcp crates; a two-node interop test establishing Established state against a real BIRD container over TCP-MD5 within the LAN session-establishment budget (M7, §31).

Acceptance

Every one of the 6×28 (State, Event) cells is exercised by the exhaustive coverage test (I10) with zero FsmError fallthroughs on the valid-input subset; session establishes against BIRD and FRRouting within 5 s (M7); hold-timer expiry (simulated by pausing KEEPALIVEs) transitions to Idle and withdraws all routes within hold_time + 1 s.

Fixtures

fixtures/fsm_happy_path.trace (Idle→...→Established event sequence) → expected final state Established; fixtures/fsm_collision.trace (simultaneous-open race, two BGP Identifiers) → expected: lower-ID connection survives; fixtures/fsm_hold_expiry.trace (no KEEPALIVE for hold_time) → expected: Idle + WithdrawAllRoutes; fixtures/ md5_mismatch.pcap → expected: TCP handshake never completes (silent per §8.1 malformed-input note).

Pitfalls

A missing (State, Event) arm silently deadlocks a session with no error (I10 exists specifically to prevent this — the coverage test, not code review, is the actual defense); TCP-MD5 mismatches produce no NOTIFICATION at all (packets are dropped at the kernel level) — the only observable signal is a session stuck in Active/Connect indefinitely, which is why §27's runbook for this scenario leads with "check MD5 key parity" before anything BGP-specific; negotiated Hold Time of exactly 0 disables keepalives entirely per RFC 4271 §4.4 — a legal but unusual configuration that must not be treated as a bug.

⬜ Phase 3 — RIB Model (Adj-RIB-In / Loc-RIB / Adj-RIB-Out) §15

Objectives

Implement the three-stage RIB pipeline (§8.3) for IPv4 unicast: Adj- RIB-In ingest, a provisional (no-op-filter) pass-through to Loc-RIB, and Adj-RIB-Out construction — establishing the Patricia-trie-indexed table (ADR-06) that Phase 4's best-path and Phase 6's IPv6 extension build directly on.

Deliverable

bgp-rib crate; a three-peer test topology (two eBGP + one iBGP) with Adj-RIB-In/Loc-RIB/Adj-RIB-Out state inspectable via bgp-cli's show bgp <prefix> (interactive shell stub, full CLI in Phase 12).

Acceptance

LocRib::insert for a 1.2M-route synthetic full table completes in ≤ 60 s (M3, §31); a withdraw for a prefix absent from Adj-RIB-In is a documented no-op, verified by a zero-side-effect property test; I1 and I6 fixtures (§15.5) pass with zero false negatives across 10,000 proptest-generated AS_PATHs.

Fixtures

fixtures/rib_own_as_loop.json (AS_PATH contains local AS 64500) → expected: rejected at Adj-RIB-In, bgp_loop_reject_total increments (I1); fixtures/rib_spurious_withdraw.json (WITHDRAW for a never-seen prefix) → expected: silent no-op, debug-level log only; fixtures/ rib_implicit_withdraw.json (two UPDATEs for the same prefix from the same peer) → expected: second supersedes first in Adj-RIB-Out with no explicit WITHDRAW frame emitted; fixtures/rib_full_table_v4.json.gz (1.2M synthetic routes) → import completes within budget (M3).

Pitfalls

An UPDATE containing both a withdrawn entry and an NLRI entry for the same prefix (legal per wire format, ambiguous in intent) — this design treats it as withdraw-then-reannounce, documented explicitly (§26 FM-5 depends on this ordering); forgetting I6 (split-horizon) at the Adj-RIB-Out stage rather than Adj-RIB-In stage produces a 2-node routing loop that is invisible in unit tests with only one peer.

⬜ Phase 4 — Best-Path Decision Process §16

Objectives

Implement the ten-tie-breaker deterministic decision function (§8.4, P1, P9, I2) as a pure function over LocRib candidates, with a differential test harness comparing against BIRD and FRRouting on identical synthetic inputs.

Deliverable

bgp-bestpath crate; a differential-test binary that feeds identical synthetic route sets to this implementation, BIRD, and FRRouting and diffs the chosen best route (feeds M8/M9, §31).

Acceptance

100% best-path agreement with BIRD and FRRouting (M8, M9, §31) across a 5,000-case differential corpus; select_best on 5 candidates completes in ≤ 1 µs p50 (M2); the totality property test (prop_bestpath_no_unresolved_tie, I2) passes 10,000 random candidate sets with zero ties surviving all ten stages.

Fixtures

fixtures/bestpath_localpref_tiebreak.json → LOCAL_PREF 200 beats 100; fixtures/bestpath_aspath_set_length.json (AS_SEQUENCE len 3 vs AS_SET len 5) → the AS_SEQUENCE route wins (I3, regression-guards the §8's pitfall); fixtures/bestpath_med_cross_as.json (different upstream AS, MED 50 vs 100) → MED ignored, falls through to next tie-break (I13); fixtures/bestpath_full_tie.json (identical through stage 9) → stage 10 (peer address) resolves deterministically (P9).

Pitfalls

Comparing MED across different upstream ASes (I13) inverts intended traffic engineering — the single most commonly miscited tie-breaker in operator forums; treating an AS_SET segment's length as its element count instead of 1 (I3) silently inverts the shortest-AS-PATH preference; forgetting that LOCAL_PREF is never sent over eBGP (§8.2) and defaulting to 0 for eBGP-received routes without an explicit per-peer default-local-pref policy.

⬜ Phase 5 — Route Policy Engine §17

Objectives

Implement the typed import/export filter DSL (§8.5, P3, ADR-04) with parse-time type-checking and a pure evaluator (I9), replacing Phase 3's provisional no-op filter pass-through.

Deliverable

bgp-filter crate; bgpd --check-config validates a filter file and reports the first type error with line/column, without touching any live route (P3).

Acceptance

Parse-time rejection of 100% of a 200-case malformed-filter corpus (undeclared fields, non-exhaustive branches, type mismatches) with a line-numbered diagnostic; filter evaluation latency ≤ 100 ns p50 for a 3-rule filter (M10, §31); zero observable side effects across a 1,000-case prop_filter_purity property test (I9).

Fixtures

fixtures/filter_reject_as_path.dsl (§8.5 R1) → route with AS 64513 in path is rejected; fixtures/filter_med_local_pref.dsl (§8.5 R2) → MED > 1000 sets LOCAL_PREF 50; fixtures/filter_undeclared_field.dsl (typo'd field name) → parse-time TypeError::UnknownField at the reported line; fixtures/filter_nonexhaustive.dsl (missing terminal on one branch) → parse-time TypeError::NonExhaustive.

Pitfalls

A free-form config would let a typo'd field name silently no-op (AS7007-class risk, §26 FM-1) — the type checker exists specifically to convert this into a build-time failure (P3); AS-path regex patterns using ambiguous anchoring ([= * 100 * =] vs [= 100 =], "anywhere" vs "exact") are a frequent operator-error source — the grammar (§8.5) requires explicit anchors, no implicit "anywhere" default.

⬜ Phase 6 — Multiprotocol BGP (IPv6 Unicast) §18

Objectives

Generalize the RIB (already (AFI,SAFI)-indexed per P8) to populate a second address family — IPv6 unicast — via MP_REACH_NLRI/ MP_UNREACH_NLRI (RFC 4760), with zero RIB-schema migration (P8's payoff).

Deliverable

bgp-mp crate; a dual-stack interop session against BIRD/FRRouting exchanging both IPv4 and IPv6 unicast routes over one TCP session.

Acceptance

IPv6 UPDATE round-trip (encode/decode via MP_REACH_NLRI) passes on a 5,000-case property test; a dual-stack session negotiates both AFIs in one OPEN capability exchange and exchanges routes in both families within the M7 (§31) session-establishment budget; zero cross-family contamination verified by a fixture asserting an IPv6 withdraw never affects the IPv4 table for the same numeric prefix bit-pattern.

Fixtures

fixtures/mp_capability_negotiation.bin → OPEN advertises (AFI=2,SAFI=1) and (AFI=1,SAFI=1) together; fixtures/ mp_reach_ipv6_nexthop.bin → decodes a 2001:db8::/32 route with a 2001:db8::1 next-hop; fixtures/mp_unreach_zero_nlri.bin (zero-length NLRI in MP_UNREACH) → decodes as a valid family-scoped end-of-RIB marker, regression-guarding the ambiguity noted in Phase 8 (§20.6).

Pitfalls

Forgetting that NEXT_HOP for non-IPv4-unicast families lives inside MP_REACH_NLRI, not the base NEXT_HOP attribute — a common decode bug that silently produces a zero/garbage next-hop for IPv6 routes; failing to negotiate the Multiprotocol capability before sending any MP attribute causes strict peers to NOTIFICATION-reject the session entirely (treat capability negotiation as a precondition, not best- effort).

⬜ Phase 7 — Route Reflection §19

Objectives

Implement RFC 4456 route reflection to break the O(n²) iBGP full-mesh ceiling (§32), enforcing loop-freedom via ORIGINATOR_ID/CLUSTER_LIST (I7, I8) rather than relying on the eBGP AS_PATH mechanism, which does not apply within an AS.

Deliverable

bgp-rr crate; a three-router iBGP topology (one RR, two clients) where a route learned by client A propagates to client B via the RR without a direct client-A–client-B session.

Acceptance

A route from client A reaches client B's Loc-RIB within the I12 convergence budget (§7) via the RR only; CLUSTER_LIST loop fixtures (§19.5) reject 100% of injected loop cases; ORIGINATOR_ID is never added to a route already carrying one (idempotent re-reflection).

Fixtures

fixtures/rr_basic_reflection.json → client A's route appears in client B's Adj-RIB-In with ORIGINATOR_ID = A's router-ID and CLUSTER_LIST = [RR's cluster-id]; fixtures/rr_cluster_loop.json (injected route already carrying this RR's cluster-id) → rejected (I8); fixtures/rr_next_hop_unchanged.json → NEXT_HOP is untouched by reflection (unlike eBGP's next-hop-self behavior).

Pitfalls

Reflecting a route to another non-client without adding ORIGINATOR_ID/ CLUSTER_LIST breaks loop detection for the next hop in the reflection chain; changing NEXT_HOP during reflection (an eBGP habit) breaks reachability, since iBGP next-hops must remain the originating eBGP router's address unless next-hop-self is explicitly configured (a distinct, non-default policy knob, out of Phase 7's baseline).

⬜ Phase 8 — Graceful Restart §20

Objectives

Implement RFC 4724 graceful restart so a planned bgpd restart (or a brief peer-side outage) does not trigger a network-wide withdraw-then- reannounce churn cascade, trading a bounded stale-route window for avoided reconvergence cost (P7, ADR-09).

Deliverable

bgp-gr crate; a test harness that kills and restarts one peer's bgpd process mid-session and verifies the other peer's Loc-RIB retains that peer's routes as stale throughout the outage window, without a FIB withdrawal (Phase 11 dependency, deferred assertion until §23).

Acceptance

Stale-route retention holds for the full configured restart-time (default 120 s ± 1 s, ADR-09) with zero premature withdrawal; end-of- RIB correctly clears the stale flag for every family that sent one, independently per (AFI,SAFI); a restart that exceeds restart-time purges all that peer's stale routes and triggers best-path recomputation exactly once per affected prefix (not once per stale route individually — batched).

Fixtures

fixtures/gr_capability_negotiation.bin → OPEN carries GR capability with restart_time=120, per-family forwarding-preserved flags set; fixtures/gr_stale_retention.trace (session drop, no reconnect within 120s) → routes purged at t=120s exactly, not earlier; fixtures/ gr_eor_ipv4.bin (zero-NLRI UPDATE) → clears stale for (AFI=1,SAFI=1) only; fixtures/gr_eor_mp_ipv6.bin (zero-NLRI MP_UNREACH) → clears stale for (AFI=2,SAFI=1) only, regression- guarding the ambiguity in §20.6.

Pitfalls

End-of-RIB for the base IPv4-unicast family is a plain zero-NLRI UPDATE, while for every MP-BGP family it is a zero-NLRI MP_UNREACH_NLRI — conflating the two (treating any zero-NLRI UPDATE as "all families done") produces a partial-GR bug where non-IPv4 stale routes linger past their intended clear point; a restart-time set too short causes legitimate slow-reconnecting peers to have routes purged and re-churned anyway, defeating the purpose of GR (ADR-09's tradeoff made explicit).

⬜ Phase 9 — Route-Flap Damping §21

Objectives

Implement RFC 2439 route-flap damping, opt-in and default-off per RFC 7196 guidance (ADR-10, P7), to suppress a persistently-oscillating route without suppressing normal single-transition route changes.

Deliverable

bgp-rfd crate, disabled by default (ADR-10); an opt-in test harness that flaps a synthetic peer session on a fixed interval and verifies suppression engages at the configured threshold and disengages at the reuse threshold.

Acceptance

Penalty accrual and decay match the RFC 2439 half-life formula within 1% over a 24-hour simulated timeline (accelerated clock in test); suppression engages within one flap-interval of crossing the suppress threshold and disengages within one decay-check interval of crossing the reuse threshold; a GR-driven restart (§20) accrues zero penalty, verified by a dedicated fixture.

Fixtures

fixtures/rfd_penalty_accrual.json (10 flaps over 1 hour) → penalty trajectory matches the RFC 2439 formula within 1%; fixtures/ rfd_suppress_reuse_cycle.json → suppression at penalty ≥ 2000, reuse at penalty ≤ 750; fixtures/rfd_gr_exempt.json (a GR-negotiated restart) → zero penalty accrued (§20.2 cross-guard).

Pitfalls

RFC 7196 documents that blanket always-on damping penalizes normal internet route dynamics (multihomed sites, mobile anycast) more than it helps — hence ADR-10's default-off; failing to exempt GR-driven restarts from penalty accrual defeats Phase 8's entire purpose (a planned maintenance restart would itself trigger damping, the opposite of the intended stability trade).

⬜ Phase 10 — RPKI Origin Validation & Security Hardening §22

Objectives

Implement RFC 6811 BGP Prefix Origin Validation against an RFC 6480 RPKI-derived ROA (Route Origin Authorization) cache, closing the AS7007-class (§26 FM-1) and Pakistan-Telecom-class (§26 FM-2) leak/ hijack surface at the origin-AS layer, and harden max-prefix and session-security defenses.

Deliverable

bgp-rpki crate; an end-to-end test where a route with a valid ROA is accepted, a route with an Invalid origin (ROA exists, AS mismatch) is rejected by a default policy, and NotFound (no ROA) passes through unless explicitly filtered.

Acceptance

RTR client correctly classifies 100% of a 500-case ROA-vs-route test matrix (valid, invalid-origin, invalid-max-length, not-found); a default-configured router rejects Invalid-classified routes within one best-path recomputation cycle of ROA cache update; the AS7007 and Pakistan-Telecom incident replays (§25, §26) both fail to cause a blackhole/hijack against this router's default configuration (validated end-to-end in Phase 12's conformance run, §24).

Fixtures

fixtures/rpki_valid_origin.json → Valid, accepted; fixtures/ rpki_invalid_origin_mismatch.json (ROA says AS 64500, route says AS 64599) → Invalid, rejected by default policy; fixtures/ rpki_not_found.json (no covering ROA) → NotFound, passes (operator policy decides); fixtures/rpki_as7007_replay.json (AS7007's 1997 full-table origination pattern) → rejected by max-prefix (I11) before RPKI even applies, demonstrating defense-in-depth.

Pitfalls

RPKI origin validation defends against a wrong-origin-AS hijack but does not validate the AS_PATH itself — a valid-looking path through a legitimately-authorized-but-compromised AS is undetected by RFC 6811 alone (this is exactly what BGPsec, RFC 8205, addresses, deferred §39); treating NotFound as equivalent to Invalid over-rejects the majority of the internet's currently-unsigned prefix space — RFC 6811 explicitly treats them as distinct classifications.

⬜ Phase 11 — FIB Integration (Linux Netlink) §23

Objectives

Implement the FibBackend trait (§11, P6) against Linux netlink, making Loc-RIB's best routes (§8.3, §16) forwarding-effective, while keeping bgp-fib-mock (§10) as the default backend for every prior phase's tests.

Deliverable

bgp-fib-linux crate; an end-to-end test showing a Loc-RIB best-path change reflected in ip route show within the FIB-install latency budget (M4, §31).

Acceptance

FIB install rate ≥ 10,000 routes/s sustained (M4); a full 1.2M-route synthetic table installs completely within a bounded batch window (derived from M3+M4, §32); a route whose next-hop is unresolvable (§23.8) fails installation with a logged reason, never a silent drop.

Fixtures

fixtures/fib_install_basic.json → 203.0.113.0/24 via 198.51.100.1 appears in ip route show table main with proto bgp; fixtures/fib_unresolvable_nexthop.json (next-hop with no covering kernel route) → install fails, bgp_fib_install_failed_total{reason= "unresolvable_nexthop"} increments; fixtures/fib_bulk_1_2m.json.gz → full-table install completes within budget (M3+M4 derived, §32).

Pitfalls

A next-hop with no route in the kernel table fails installation silently if error codes from the netlink recv_ack are not checked — always check the ack; CAP_NET_ADMIN is required for netlink route writes, distinct from CAP_NET_BIND_SERVICE needed for the BGP listener itself (§14) — a container missing either capability fails differently and must be distinguished in diagnostics.

⬜ Phase 12 — Conformance, Interop, Fuzzing & Canary §24

Objectives

Assemble the full conformance-bucket suite (§10 conformance/buckets/) across every prior phase's fixtures, run continuous differential interop against BIRD and FRRouting, run the fuzz-target corpus continuously in CI, and execute the 30-day full-table canary as the long-tail safety net before any release is cut (§30).

Deliverable

A single make conformance target running all buckets; fuzz.yml running all six targets nightly with corpus persistence; a canary report artifact (docs/performance/canary-report-<date>.md) committed per soak run.

Acceptance

100% of named fixtures across all 13 phases pass (§13.5–§23.5, enumerated exhaustively in the bucket suite manifest); fuzz targets sustain ≥ 10,000 exec/s (M11, §31) with zero crashes over a 24-hour CI run; the 30-day canary shows RSS growth ≤ 5% over the full window and zero FIB-vs-Loc-RIB drift events (M12, §31).

Fixtures

conformance/buckets/manifest.json (auto-generated index of every named fixture from §13.5–§23.5, cross-checked for completeness against this phase's own acceptance criterion); fixtures/fuzz_corpus_seed/ (one seed file per fuzz target, versioned); fixtures/canary_baseline.json (expected steady-state memory/FIB-count baseline for drift comparison).

Pitfalls

A fixture added in an earlier phase but never wired into the bucket manifest silently stops being checked in CI — the manifest-completeness self-check (§24.5) exists specifically to catch this class of regression; interop CI flakiness from container startup races is a common false-negative source — mitigate with an explicit readiness probe (birdc show status / vtysh -c "show version") before running any session-establishment assertion, not a fixed sleep.
