1. Goal & Scope

A BGP-4 control-plane router: a long-running daemon that establishes and maintains BGP sessions with configured peers over TCP port 179, exchanges UPDATE messages carrying path-vector routes, maintains a three-stage RIB pipeline (Adj-RIB-In → Loc-RIB → Adj-RIB-Out, §8) per RFC 4271, runs a deterministic best-path decision process (§8.4), applies a typed import/export route-policy engine (§8.5), and programs the resulting best routes into the local FIB. This is the control plane only: packet forwarding is delegated to the kernel or an external forwarding ASIC; this project never touches the data-plane fast path.

Phase-0 deliverable — numbered modules/crates:

  1. bgp-core — wire-agnostic types (Prefix, AsPath, PathAttributes, RouteId).
  2. bgp-codec — BGP-4 message encode/decode (OPEN/UPDATE/NOTIFICATION/KEEPALIVE).
  3. bgp-fsm — the RFC 4271 §8 finite state machine.
  4. bgp-tcp — TCP transport, port 179, TCP-MD5 (RFC 2385).
  5. bgp-rib — Adj-RIB-In / Loc-RIB / Adj-RIB-Out tables, IPv4 unicast.
  6. bgp-bestpath — the best-path decision process.
  7. bgp-config — minimal static peer configuration loader.
  8. bgpd — the daemon binary wiring the above.

System boundaries. Provides: BGP-4 session management, UPDATE processing, RIB maintenance, deterministic best-path selection, typed import/export policy, FIB programming via Linux netlink, RPKI origin validation, route reflection, graceful restart, route-flap damping, MP-BGP for IPv4/IPv6 unicast. Delegates: packet forwarding (kernel/ASIC fast path), IGP metric computation (consumes IGP cost as an input; does not run OSPF/IS-IS), physical/out-of-band session security beyond TCP-MD5 and GTSM. Does NOT provide (permanently out of scope, not deferred): a full network operating system, an SDN multi-tenant route-server product, MPLS label distribution protocols (LDP, RSVP-TE), an IGP implementation.

Non-goals. Not a route-server with per-tenant RIB isolation; not a web-based looking-glass UI; not a general-purpose packet-forwarding engine.

Deployment model. Single-process daemon, one instance per router, one TCP listener on port 179, one task per peer, shared Loc-RIB behind short-lived locks. Runs on bare metal or in a network-namespace-isolated container with CAP_NET_ADMIN (netlink, TCP-MD5) and CAP_NET_BIND_SERVICE (port 179).

Target users/operators. Network engineers operating a transit or peering AS, or an enterprise multihomed edge; on-call engineers debugging session flaps, RIB divergence, and route hijacks.

What later phases unlock. MP-BGP for IPv6 unicast (Phase 6, §18) generalizes the RIB to any (AFI, SAFI); route reflection (Phase 7, §19) removes the O(n²) iBGP full-mesh ceiling; graceful restart (Phase 8, §20) removes the churn cost of planned maintenance; route-flap damping (Phase 9, §21) trades convergence speed for stability under a flapping peer; RPKI origin validation (Phase 10, §22) closes the AS7007-class hijack/leak surface; FIB integration (Phase 11, §23) makes routes forwarding-effective.

Recommended language: Rust 1.78+ (edition 2021). Rationale: a malformed-attribute parser bug in a memory-unsafe language is a remote code-execution surface reachable from every eBGP peer on the internet — this is not hypothetical (§26 FM-1 cites the FRRouting/Quagga CVE history); Rust's ownership model converts that entire bug class into a compile-time error, at zero runtime GC cost, which matters because the hold-timer (§8.1) can be negotiated as low as a few seconds and a stop-the-world GC pause is itself a session-reset trigger. Rejected: C — the exact bug class above (buffer overflow in variable-length attribute parsing) is FRR's and Quagga's real CVE history; no compile-time safety net. Go — GC pauses interact badly with the hold-timer/keepalive budget in §4; a 200 ms stop-the-world pause under load can trip a 3 s hold timer. Python/Java — boxed- object overhead multiplies the ~500 B/route budget (§4) by 4-8×, which is disqualifying at the 1.2M-route full-table scale in §4.

Prerequisites. TCP/IP internals; finite-state-machine design; graph/path algorithms (AS-path loop detection is a path-vector, not link-state, technique); binary wire-format parsing; systems programming with async I/O and bounded channels.

Estimated timeline. Phase 0 (repo skeleton + correctness kernel): 3 weeks. Full system (Phase 0 through Phase 12, §12–§24): 10 months.

Deferred features (detailed in the Deferred Features Register, §38): VPNv4/VPNv6 MPLS L3VPN (RFC 4364) PhaseDeferred("§38"); EVPN (RFC 7432) PhaseDeferred("§38"); BGP-LS (RFC 7752) PhaseDeferred("§38"); BGP Flowspec (RFC 5575) PhaseDeferred("§38"); BGPsec path signing (RFC 8205) PhaseDeferred("§38"); a gRPC control-plane API PhaseDeferred("§38"); SR-MPLS/SRv6 route distribution PhaseDeferred("§38").

2. Why Build This

BGP is the only protocol every packet on the public internet is implicitly routed by, and it is the canonical teaching example of path-vector routing, eventual-consistency-under-policy, and the gap between "correct on the wire" and "correct under a hundred simultaneously-misbehaving peers." The base spec (RFC 4271, 104 pages) reads as a straightforward message exchange; the production reality — 1.2M IPv4 routes, hundreds of eBGP peers, arbitrarily malformed attributes, AS-path loops, iBGP full-mesh scaling, route-flap storms — is a multi-year systems exercise. Building it teaches: (1) a strict finite-state-machine discipline under adversarial network conditions, (2) a three-stage data pipeline (Adj-RIB-In → policy → Loc-RIB → policy → Adj-RIB-Out) that recurs in every routing/policy system, (3) a deterministic decision algorithm (best-path) that must produce the same answer on every router or the network doesn't converge, (4) the scaling failure of naive full-mesh iBGP and the route-reflection fix, (5) the security model of a protocol with no built-in authentication of route origin (RPKI retrofits this).

Architecturally/historically, BGP is the last-surviving inter- domain path-vector protocol at internet scale (its rivals — EGP, IDRP — did not survive); it is deployed on every default-free-zone router (FRRouting, BIRD, GoBGP, OpenBGPD are its production embodiments, compared in §34) and is the template for every later attempt at policy-driven distributed routing (data-center BGP/EVPN fabrics, SD-WAN overlay control planes). It sits alongside DNS as one of the two protocols an outage in which is front-page news (AS7007 1997, Pakistan Telecom/YouTube 2008 — both cited in §26).

Engineering muscles built: wire-format parsing under adversarial input; finite-state-machine correctness under timer races; building a pure decision function (best-path) that must be identical across independent implementations run by different companies; designing a policy DSL that fails safe at parse time, not at 3 a.m. in production; reasoning about global convergence from purely local per-router rules.

Cross-links to sibling systems. Compare to a distributed consensus system (Raft/Paxos): BGP has no consensus — best-path is decided independently per router from locally-visible information, and global convergence is an emergent, provably-imperfect property (Griffin & Wilfong's stable-paths result, §5). Compare to a database query planner: the RIB pipeline (Adj-RIB-In → policy → Loc-RIB) is structurally the same shape as a query optimizer's logical → physical plan pipeline. Compare to a compiler: the filter DSL (§8.5) is a small statically-typed language with its own AST and evaluator, the same shape as a compiler's semantic-analysis pass.

Calibration value. A correct implementation must simultaneously hold: RFC 4271's literal wire format, the best-path algorithm's ten deterministic tie-breakers, the iBGP-vs-eBGP re-advertisement rule, and a hostile-input parser — under a hold timer measured in seconds. Very few systems combine "protocol literalism," "distributed determinism," and "hard real-time-ish response budget" this tightly.

  • Explain why iBGP full-mesh is O(n²) and how route reflection breaks the mesh at the cost of the free-choice property (Griffin & Wilfong) — built in Phase 7 (§19).

Six load-bearing properties. First, the Adj-RIB-In is the per-peer, per-AFI "as received" record — a trust boundary between an untrusted peer and this router's decision logic; nothing downstream of it trusts peer input directly. Second, the filter engine is the only mutation point between Adj-RIB-In and Loc-RIB (import) and between Loc-RIB and Adj-RIB-Out (export) — a concurrency boundary is not needed here because the filter engine is pure (I9, §7). Third, Loc-RIB is the single per-AFI/SAFI authoritative table; best-path selection (§16) is a pure function over its per-prefix candidate set. Fourth, the FIB programmer is a protocol boundary: it consumes a "best route changed" event stream and is fully decoupled from BGP session state — it can be swapped for a mock backend (bgp-fib-mock) in conformance tests without touching any BGP logic. Fifth, each peer session is an isolated concurrency boundary (one task, one channel pair) so a single flapping/hostile peer cannot corrupt another peer's state — only Loc-RIB and the filter engine are shared, behind short critical sections. Sixth, the persistence boundary is intentionally absent in Phase 0-11: all RIB state is in-memory and rebuilt from peer re-establishment; Phase 12's conformance suite treats this as an explicit design choice (ADR-14, §9), not an oversight.

Reference Implementations

  • BIRD (CZ-NIC/bird): proto/bgp/ (FSM + attribute codec), filter/ (typed filter DSL). Lesson: a filter language type-checked at parse time eliminates a whole class of operator error — applied in §17. Pitfall not to copy: BIRD's filter grammar overloads int for both plain integers and pair-encoded communities; we keep them distinct types (ADR-04, §9).
  • FRRouting (FRRouting/frr): bgpd/bgp_fsm.c (state machine), zebra/ (RIB-to-FIB abstraction). Lesson: decoupling the FIB programmer behind an IPC boundary (zebra) lets multiple protocol daemons share one FIB safely — applied in §3, §23. Pitfall: zebra's IPC adds a serialization hop we avoid by keeping the FIB programmer in-process (ADR-07, §9).
  • GoBGP (osrg/gobgp): internal/pkg/table/ (RIB representation), pkg/server/ (gRPC control API). Lesson: an RPC-exposed control plane makes BGP programmable from external controllers — applied in the deferred gRPC API design (§38). Pitfall: GoBGP's global mutex around the whole RIB serializes all peers; we use per-AFI/SAFI table locks instead (I9, applied in §7).
  • OpenBGPD (openbgpd-portable): session.c (minimal FSM), rde.c (route decision engine). Lesson: a small, security-focused codebase with a privilege-separated session process is a strong security posture — applied in §22, §25 T-4. Pitfall: OpenBGPD's single-threaded RDE caps throughput; we accept per-peer concurrency instead (P2, §6).
  • Quagga (Quagga-project, predecessor to FRR): bgpd/bgp_route.c (best-path tie-breakers). Lesson: the exact ordering of the ten RFC 4271 §9.1 tie-breakers, applied in §16 (Best-Path Decision Process). Pitfall: Quagga's historical CVEs in variable-length attribute parsing (§26 FM-1) are applied as the rationale for Rust (§1) and for strict length-field validation (I4, applied in §7).

6. Design Principles

  • P1 — Pure best-path selection. best_path is a total function of its candidate-route inputs and static configuration; no hidden clock/IO. Tradeoff: forces IGP cost to be snapshotted, not queried live, at comparison time. Operational implication: the algorithm is fuzzable and differential-testable (§24) without a live network. Violation cost: two routers with identical RIBs could pick different best routes — routing loops (I1).
  • P2 — Per-peer state isolation. Each peer owns one task, one Adj-RIB-In, one Adj-RIB-Out. Tradeoff: per-peer memory overhead vs a shared table. Operational implication: a hostile/flapping peer's blast radius is one task, killable independently. Violation cost: cross-peer memory corruption on a single malformed message.
  • P3 — Typed filter DSL, parse-time errors. Policy is compiled to an AST before any route touches it. Tradeoff: less flexible than a free-form scripting config. Operational implication: a broken policy fails bgpd --check-config, not 3 a.m. production. Violation cost: AS7007-class blackhole from an unfiltered default (§26 FM-1).
  • P4 — Independent Adj-RIBs per peer per AFI/SAFI. Tradeoff: storage amplification up to 800× (§4). Operational implication: soft reconfiguration (re-apply policy without re-requesting routes) is possible. Violation cost: a shared-mutable-RIB design can't soft-reconfigure without a full session bounce.
  • P5 — Loc-RIB is the sole FIB input; no bypass paths. Tradeoff: every route must pass full best-path selection before reaching the FIB, even in a degenerate single-peer case. Operational implication: FIB state is always explainable from Loc-RIB state. Violation cost: a bypass path is an un-auditable route in the FIB (I5).
  • P6 — FIB integration via an abstract dataplane trait. Tradeoff: an indirection layer over a direct netlink call. Operational implication: bgp-fib-mock (§10) lets conformance tests run without root/CAP_NET_ADMIN. Violation cost: untestable FIB logic.
  • P7 — Graceful restart and route-flap damping are configurable, not load-bearing for correctness. Tradeoff: an operator can disable both and still have a correct (if less stable) router. Operational implication: damping defaults off per RFC 7196 (ADR-10). Violation cost: baking damping into best-path would make the "pure function" of P1 false (damping has state and time).
  • P8 — Multiprotocol-capable RIB from Phase 0. The RIB is indexed by (AFI, SAFI) from the first line of code, even though only IPv4 unicast is populated pre-Phase-6. Tradeoff: more indirection than a single flat IPv4 table. Operational implication: Phase 6 (§18) adds IPv6 with zero RIB-schema migration. Violation cost: an IPv4-only RIB requires a breaking schema change to add IPv6 later.
  • P9 — Determinism in every tie-breaker. The final best-path tie-breaker (router-ID, then peer address) is total — no two distinct routes ever compare equal. Tradeoff: a meaningless-looking tie-breaker (peer address) as the final word. Operational implication: every router in an AS converges to the identical best route given identical inputs (I1, I2). Violation cost: persistent best-path oscillation (Griffin & Wilfong, §5).
  • P10 — No global mutable state; configuration is per-instance. Tradeoff: every module takes explicit config, no statics/globals. Operational implication: multiple bgpd instances can run in one process for testing (§24). Violation cost: test pollution across instances.
  • P11 — Attribute interning. Identical PathAttributes sets (common on multi-peer eBGP fan-in) are stored once, referenced by Arc. Tradeoff: an interning table adds a lookup on insert. Operational implication: meets the ≤500 B/route budget (§4, M6). Violation cost: naive per-route storage blows the 1 GiB ceiling at full-table scale.
  • P12 — Strict fail-closed attribute validation. Any malformed, truncated, or contradictory attribute triggers a NOTIFICATION and session reset, never a best-effort partial-accept. Tradeoff: one bad attribute drops the whole session, not just one route. Operational implication: matches RFC 4271 §6.3's mandated behavior. Violation cost: silently accepting a malformed AS_PATH can install a routing loop (I1, §26 FM-4).
  • P13 — Observability is a first-class output, not an afterthought. Every state transition, RIB mutation, and policy decision emits a structured event with a stable field schema (§27). Tradeoff: logging/metrics overhead on the hot decode path. Operational implication: production incidents are debuggable from telemetry alone. Violation cost: the "30 ms to converge" problem statement (§2) is undebuggable without it.

8. Domain Model

8.1 The BGP Finite State Machine (RFC 4271 §8)

Six states: Idle → Connect → Active → OpenSent → OpenConfirm → Established. The transition table below covers the load-bearing subset (full table has 28 events × 6 states; the remainder are symmetric error/stop handling collapsed into the _ → Idle rows).

State      | Event                    | Next State  | Actions
-----------|--------------------------|-------------|----------------------------
Idle       | ManualStart/AutoStart    | Connect     | StartConnectRetryTimer, InitiateTCP
Connect    | Tcp_CR_Acked/Confirmed   | OpenSent    | StopConnectRetryTimer, SendOPEN, StartHoldTimer(240)
Connect    | ConnectRetryTimer_Expire | Connect     | RestartConnectRetryTimer, InitiateTCP
Connect    | TcpConnectionFails       | Active      | RestartConnectRetryTimer
Active     | Tcp_CR_Acked/Confirmed   | OpenSent    | StopConnectRetryTimer, SendOPEN, StartHoldTimer(240)
Active     | ConnectRetryTimer_Expire | Connect     | RestartConnectRetryTimer, InitiateTCP
OpenSent   | BGPOpen                  | OpenConfirm | SendKEEPALIVE, StartKeepaliveTimer, negotiate HoldTime (I13n/a)
OpenSent   | BGPHeaderErr/OpenMsgErr  | Idle        | SendNOTIFICATION, ReleaseResources
OpenSent   | HoldTimer_Expires        | Idle        | SendNOTIFICATION(HoldTimerExpired)
OpenConfirm| KeepAliveMsg             | Established | SyncRIB (send full initial UPDATE set)
OpenConfirm| NotifMsg/HoldTimerExpire | Idle        | ReleaseResources
Established| UpdateMsg                | Established | ProcessUpdate → RIB pipeline (§8.3)
Established| KeepAliveMsg             | Established | RestartHoldTimer
Established| HoldTimer_Expires        | Idle        | SendNOTIFICATION(HoldTimerExpired), WithdrawAllRoutes
Established| UpdateMsgErr             | Idle        | SendNOTIFICATION(UpdateMessageError), WithdrawAllRoutes
any        | TcpConnectionFails       | Idle        | ReleaseResources, WithdrawAllRoutes
any        | unhandled (State,Event)  | Idle        | SendNOTIFICATION(FsmError) — I10 forbids reaching this row

Collision detection (RFC 4271 §6.8): when two TCP connections to the same peer race (both sides open simultaneously), the connection whose initiator has the higher BGP Identifier wins; the other is closed with Cease/ConnectionCollisionResolution.

Worked example. Peer AS 64512, local AS 64500, both configured with Hold Time 90s. ManualStart fires → Connect, TCP SYN sent. TCP handshake completes → Tcp_CR_Acked → OpenSent, our OPEN sent (Version=4, MyAS=64500, HoldTime=90, BGPID=10.0.0.1), local HoldTimer armed at 240s (interim value until negotiation completes). Peer's OPEN arrives (MyAS=64512, HoldTime=90, BGPID=10.0.0.2) → BGPOpen event → OpenConfirm; negotiated Hold Time = min(90,90) = 90s, Keepalive = 30s; KEEPALIVE sent. Peer's KEEPALIVE arrives → KeepAliveMsg → Established; SyncRIB sends the full initial Adj-RIB-Out. Steady state: KEEPALIVE every 30s resets the 90s hold timer on each side.

Malformed-input example. Peer sends an OPEN with Version=3 → BGPOpen event evaluated, version check fails → BGPOpenMsgErr → Idle, NOTIFICATION(OpenMessage, subcode UnsupportedVersionNumber, data = supported version 4) sent, TCP connection closed, connect-retry timer restarts per configured backoff.

Failure-path example. Session Established, peer stops sending KEEPALIVE (process hang on the peer side). Local HoldTimer (90s) expires with no KEEPALIVE/UPDATE received → HoldTimer_Expires → Idle; NOTIFICATION(HoldTimerExpired) sent (best-effort, TCP may already be dead); every route in that peer's Adj-RIB-In is withdrawn, triggering best-path re-selection for every affected prefix (I12 convergence budget applies per-prefix).

8.2 The UPDATE Message and Path Attributes (RFC 4271 §4.3)

UPDATE wire layout:
+------------------------+
| Withdrawn Routes Len(2)|
| Withdrawn Routes (var) |  each: (prefix-len:1, prefix-bytes:var)
| Total Path Attr Len (2)|
| Path Attributes (var)  |  see attribute layout below
| NLRI (var)             |  each: (prefix-len:1, prefix-bytes:var)
+------------------------+

Path attribute layout:
+------------------------+
| Flags (1)  | TypeCode(1)|  flags: Optional|Transitive|Partial|ExtLen
| Length (1 or 2, per ExtLen flag)                     |
| Value (var, per TypeCode)                            |
+------------------------+
Type Attribute Category Semantics
1 ORIGIN well-known mandatory 0=IGP, 1=EGP, 2=Incomplete; I13-adjacent tiebreak input
2 AS_PATH well-known mandatory segments: 1=AS_SET, 2=AS_SEQUENCE, 3=AS_CONFED_SEQUENCE, 4=AS_CONFED_SET (RFC 5065)
3 NEXT_HOP well-known mandatory IPv4 egress address (IPv4 unicast only; else via MP_REACH_NLRI)
4 MULTI_EXIT_DISC optional non-transitive u32, lower wins, only same-upstream-AS (I13)
5 LOCAL_PREF well-known (iBGP only) u32, higher wins, never sent eBGP
6 ATOMIC_AGGREGATE well-known discretionary zero-length flag: do not de-aggregate
7 AGGREGATOR optional transitive (AS:2/4, router-id:4) of the aggregator
8 COMMUNITY (RFC 1997) optional transitive list of (AS:2, value:2) policy tags
9 ORIGINATOR_ID optional non-transitive RR-injected; loop defense (I8)
10 CLUSTER_LIST optional non-transitive RR-injected list of cluster-ids; loop defense (I8)
14 MP_REACH_NLRI (RFC 4760) optional non-transitive (AFI, SAFI, next-hop, NLRI) for non-IPv4-unicast families
15 MP_UNREACH_NLRI (RFC 4760) optional non-transitive (AFI, SAFI, withdrawn NLRI); zero-NLRI = GR end-of-RIB (§20)
16 EXTENDED_COMMUNITIES (RFC 4360) optional transitive 8-byte typed tags (route-target, etc.), deferred use (§38)
17 AS4_PATH (RFC 6793) optional transitive 4-byte-AS carrier for legacy 2-byte peers
18 AS4_AGGREGATOR (RFC 6793) optional transitive 4-byte-AS aggregator carrier
32 LARGE_COMMUNITY (RFC 8092) optional transitive (AS:4, fn:4, param:4) — solves 16-bit-AS community limit

Attribute parsing pitfalls (I4). The Extended-Length flag (bit 4 of the flags byte) decides a 1-byte vs 2-byte length field; misreading it truncates or overruns the attribute. The attribute type occupies only the low 7 bits (bit 7 reserved). The Partial flag, once set by any AS along the path, is propagated unchanged, never cleared. An attribute with the Optional flag clear that this router does not recognize is a NOTIFICATION-triggering error (well-known attributes must be known); an unrecognized Optional-Transitive attribute is retained and re-advertised with Partial set; an unrecognized Optional-Non-transitive attribute is silently dropped.

Worked example (UPDATE decode). Peer AS 64512 sends an UPDATE advertising 203.0.113.0/24 with ORIGIN=IGP, AS_PATH=(SEQUENCE [64512]), NEXT_HOP=198.51.100.1, MED=100, COMMUNITY=[(64512,100)]. Decode produces one Route { prefix: 203.0.113.0/24, attrs: {...}, source_peer: 64512 }; inserted into that peer's Adj-RIB-In (§8.3); triggers import-policy evaluation (§8.5) and, if accepted, a best-path re-run for that prefix (§8.4).

Malformed-input example. The same UPDATE but with Total Path Attribute Length field claiming 40 bytes while only 30 bytes remain in the message: decode fails length validation (I4) before any attribute is parsed → NOTIFICATION(UpdateMessage, subcode MalformedAttributeList) → FSM UpdateMsgErr → session reset, full Adj-RIB-In withdrawal for that peer.

Failure-path example. An UPDATE contains AS_PATH = SEQUENCE [64512, 64500] where 64500 is this router's own AS: I1 rejects the route at Adj-RIB-In insert (loop detection) before it ever reaches Loc-RIB; the withdrawal-vs-acceptance decision is logged with reason loop_own_as (telemetry bgp_loop_reject_total).

8.3 RIB Model: Adj-RIB-In → Loc-RIB → Adj-RIB-Out

Three logical tables per (AFI, SAFI), per §3's pipeline:

  • Adj-RIB-In (per peer): routes as received, pre-import-policy — the trust boundary (§3).
  • Loc-RIB: the per-AFI/SAFI authoritative table; one entry per prefix holding the current best route plus all surviving candidates (post-import-policy, pre-best-path-elimination).
  • Adj-RIB-Out (per peer): routes to advertise to that peer, post-export-policy; the basis for implicit-withdraw semantics (a new UPDATE for a prefix supersedes the prior one without an explicit withdraw).
Prefix lifecycle state machine (per (peer, prefix)):
  Absent --UPDATE(nlri)--> AdjRibIn::Present --import accept--> LocRib::Candidate
  LocRib::Candidate --best-path win--> LocRib::Best --export accept--> AdjRibOut::Advertised
  LocRib::Candidate --best-path loss--> LocRib::Candidate (retained, not advertised)
  AdjRibIn::Present --WITHDRAW/session-reset--> Absent --triggers--> LocRib re-selection

Worked example. Prefix 203.0.113.0/24 received from peers A (LOCAL_PREF 100) and B (LOCAL_PREF 200). Both pass import policy → both become LocRib::Candidate. Best-path (§8.4) picks B's route on LOCAL_PREF (tie-break 1) → B's route is LocRib::Best; A's route remains LocRib::Candidate (retained for fast failover if B withdraws). Export policy runs for every peer other than B (split-horizon, I6) and for B's own re-advertisement rules; Adj-RIB-Out entries generated.

Malformed-input example. A WITHDRAW for 203.0.113.0/24 arrives from peer C, who never advertised that prefix (no matching Adj-RIB-In entry): per RFC 4271, this is silently ignored — not an error — logged at debug level only (bgp_spurious_withdraw_total).

Failure-path example. Peer B's session resets (hold-timer expiry, §8.1): all of B's Adj-RIB-In entries are withdrawn atomically; Loc-RIB re-runs best-path for every affected prefix; 203.0.113.0/24 falls back to A's route (LOCAL_PREF 100), and Adj-RIB-Out for every other peer regenerates an UPDATE reflecting the new best route (implicit withdraw of the old, per Adj-RIB-Out bookkeeping, §26 FM-5).

8.4 Best-Path Decision Process (RFC 4271 §9.1)

Ten deterministic tie-breakers, applied in order until one produces a strict winner:

1. Highest LOCAL_PREF                         (P9, I2)
2. Locally originated (network/aggregate)      wins over learned
3. Shortest AS_PATH length (AS_SET counts 1)   (I3)
4. Lowest ORIGIN (IGP < EGP < Incomplete)
5. Lowest MED, only same immediate-upstream AS (I13)
6. eBGP-learned over iBGP-learned
7. Lowest IGP cost to NEXT_HOP (snapshotted, P1)
8. Lowest router-ID (or ORIGINATOR_ID if present, RR case)
9. Shortest CLUSTER_LIST (route-reflection case, §19)
10. Lowest peer TCP source address              (total order, P9)

Worked example. Candidates for 203.0.113.0/24: Route X (LOCAL_PREF 100, AS_PATH len 3, eBGP), Route Y (LOCAL_PREF 100, AS_PATH len 2, eBGP). Tie-break 1 ties (100=100); tie-break 2 ties (neither local); tie-break 3 resolves: Y (len 2) wins.

Malformed-input example. A candidate route with an absent MED (no MULTI_EXIT_DISC attribute) is treated as MED=0 (the RFC-4271 default reading, ADR-16), not as "missing → skip tie-break 5" — this distinction is a common implementation divergence (BIRD/FRR agree on default-0; documented explicitly to keep interop, §24).

Failure-path example. Two candidates tie through tie-break 9 (identical router-ID due to operator misconfiguration, §26 FM-3): tie-break 10 (peer TCP source address) is total and always resolves — I2 guarantees no unresolved tie ever reaches the FIB, even under this misconfiguration; the resulting choice is stable but arbitrary from the operator's perspective, which is why router-ID uniqueness is a Threat-Model item (T-9, §25).

8.5 Route Policy (Import/Export Filter Engine)

Grammar (EBNF), the typed filter DSL:

filter      = "filter" ident "{" stmt* "}" ;
stmt        = if_stmt | assign_stmt | call_stmt | terminal_stmt ;
if_stmt     = "if" cond "then" stmt_block ["else" stmt_block] ;
cond        = aspath_match | community_match | numeric_cmp ;
aspath_match= "bgp_path" "~" aspath_pattern ;
numeric_cmp = field ("<"|">"|"=") literal ;
assign_stmt = field "=" expr ;
call_stmt   = field "." method "(" args ")" ;
terminal_stmt = "accept" | "reject" ;
field       = "bgp_local_pref" | "bgp_med" | "bgp_community"
            | "bgp_origin" | "bgp_next_hop" ;

Semantics table (worked example as data, not as executable script):

Rule Condition Action
R1 bgp_path matches pattern [* 64513 *] reject (deny transit via AS 64513)
R2 bgp_med > 1000 set bgp_local_pref = 50 (deprioritize)
R3 (unconditional, last rule) add community (64500,100), accept

Malformed-input example. A filter referencing an undeclared field (bgp_locl_pref, a typo) fails at parse time (P3) with a type-checker error naming the unknown field — the route stream is never touched, unlike a runtime-typed config that would silently no-op.

Failure-path example. A filter with no reachable accept/reject on some execution path (e.g., an if with no else and no trailing terminal) is rejected at parse time by an exhaustiveness check (ADR-04 extension); this closes the "falls through, ambiguous default" failure mode present in the original draft of this design (corrected during this revision).

13. Phase 1 — Message Codec

13.1 Objectives

Implement encode/decode for all five BGP-4 message types (§8.2) with strict length and flag validation (I4, P12) and zero panics on malformed input.

13.2 Detailed Implementation Steps

Implement the 19-byte header parse (marker/length/type) first, gated on RFC 4271 §4.1's length-includes-header rule (I4); implement OPEN with its optional-parameters/capabilities list (RFC 6793 4-byte-AS capability, RFC 4760 multiprotocol capability); implement UPDATE's withdrawn-routes / path-attributes / NLRI triple, applying the attribute flags table (§8.2) and the Extended-Length bit exactly per P12's fail-closed rule; implement NOTIFICATION and KEEPALIVE (trivial, zero-length); implement ROUTE-REFRESH (RFC 2918) for completeness. Every decode function returns Result<_, CodecError> — no panics (ADR-12 fuzzing assumes this as a precondition).

13.3 Deliverable

bgp-codec crate: Codec::decode/Codec::encode (§11) for every Message variant; round-trip property test (decode(encode(m)) == m) for randomly generated valid messages.

13.4 Acceptance Criteria

100% round-trip pass over 50,000 proptest-generated valid messages (ADR-17); UPDATE decode p50 ≤ 5 µs, p99 ≤ 25 µs on a 1 KB message (M1, §31, measured via bgp-bench); zero panics over the attribute_decode fuzz corpus seed set (§39-listed fixtures) after a 10-minute local run.

13.5 Conformance Fixtures

fixtures/open_basic.bin → decodes to OpenMessage{version:4, my_as:64500,...}; fixtures/update_full_attrs.bin (all 13 path attributes populated) → full round-trip; fixtures/update_truncated_len.bin (Total Path Attribute Length claims more bytes than present) → CodecError::MalformedAttributeList (I4); fixtures/update_extlen_flag.bin (a 300-byte AS_PATH with Extended-Length flag set) → decodes correctly, regression-guards the pitfall below; fixtures/notification_cease.bin → decodes to ErrorCode::Cease.

13.6 Pitfalls

Reading a 1-byte length when the Extended-Length flag (bit 4) is set truncates large attributes (I4) — the single most common BGP codec bug across implementations (§26 FM-1's CVE lineage); the attribute type byte's bit 7 is reserved, not part of the type value, and must be masked off before matching on type code; the 16-byte marker is historically all-1s and some peers (rarely) still validate it — encode it as all-1s even though RFC 4271 marks the check optional today.

13.7 Performance Concerns

Attribute parsing allocates a Vec per list-valued attribute (communities, AS_PATH segments) — for the 200,000 UPDATEs/s burst budget (§4) this must use a pre-sized Vec::with_capacity from the declared attribute length, not repeated reallocation; avoid intermediate string formatting on the hot decode path (only format on error, which is cold).

13.8 Edge Cases

Zero-length AS_PATH (a locally-originated route via network statement upstream — legal); withdrawn-routes list present with zero entries (legal, common in KEEPALIVE-adjacent no-op UPDATEs); an attribute type code this router doesn't recognize (§8.2's Optional/Transitive handling — must preserve, not drop, if transitive); a 4096-byte oversized message (BGP's classic 4096-byte cap, or the RFC 8654 extended-message 65535 cap if negotiated) exceeding the buffer.

13.9 Failure Analysis

A truncated-length attribute (I4) triggers NOTIFICATION(UpdateMessage, MalformedAttributeList) and the FSM (§14) resets to Idle, withdrawing the whole peer's Adj-RIB-In (§8.3) — blast radius is one peer, not the router process, because P12's fail-closed validation runs before any attribute value is trusted. Detection is immediate (decode fails synchronously); forensic artifact is the raw offending bytes, logged at error level with the peer id (P13).

13.10 Operational Notes

Emit bgp_codec_reject_total{reason} (I4) on every decode failure, labeled by CodecError variant, so an operator can distinguish "peer sent garbage" from "we have a codec bug" by reason-code distribution across peers. No migration/compatibility concerns yet — the wire format is fixed by RFC 4271, not versioned by this project.

14. Phase 2 — Finite State Machine & TCP Transport

14.1 Objectives

Implement the full RFC 4271 §8 state machine (§8.1) over a real TCP transport with MD5 authentication (RFC 2385) and GTSM (RFC 5082), establishing sessions end-to-end with BIRD/FRRouting in the interop containers from Phase 0.

14.2 Detailed Implementation Steps

Encode the (State, Event) transition table (§8.1, I10) as an exhaustive match with a compile-time-checked total-coverage test — no _ => catch-all permitted in the table itself (only the test asserts totality, per I10); wire the connect-retry/hold/keepalive timers on the monotonic clock (ADR-22); implement TCP-MD5 via setsockopt(TCP_MD5SIG) (Linux-specific, ADR-08) and GTSM (TTL=255 send, ≥254 receive, RFC 5082); implement collision detection (RFC 4271 §6.8) comparing BGP Identifiers; wire a BFD liveness-detection hook (interface only — full BFD session state machine is out of Phase-0-12 scope, flagged in §39).

14.3 Deliverable

bgp-fsm + bgp-tcp crates; a two-node interop test establishing Established state against a real BIRD container over TCP-MD5 within the LAN session-establishment budget (M7, §31).

14.4 Acceptance Criteria

Every one of the 6×28 (State, Event) cells is exercised by the exhaustive coverage test (I10) with zero FsmError fallthroughs on the valid-input subset; session establishes against BIRD and FRRouting within 5 s (M7); hold-timer expiry (simulated by pausing KEEPALIVEs) transitions to Idle and withdraws all routes within hold_time + 1 s.

14.5 Conformance Fixtures

fixtures/fsm_happy_path.trace (Idle→...→Established event sequence) → expected final state Established; fixtures/fsm_collision.trace (simultaneous-open race, two BGP Identifiers) → expected: lower-ID connection survives; fixtures/fsm_hold_expiry.trace (no KEEPALIVE for hold_time) → expected: Idle + WithdrawAllRoutes; fixtures/ md5_mismatch.pcap → expected: TCP handshake never completes (silent per §8.1 malformed-input note).

14.6 Pitfalls

A missing (State, Event) arm silently deadlocks a session with no error (I10 exists specifically to prevent this — the coverage test, not code review, is the actual defense); TCP-MD5 mismatches produce no NOTIFICATION at all (packets are dropped at the kernel level) — the only observable signal is a session stuck in Active/Connect indefinitely, which is why §27's runbook for this scenario leads with "check MD5 key parity" before anything BGP-specific; negotiated Hold Time of exactly 0 disables keepalives entirely per RFC 4271 §4.4 — a legal but unusual configuration that must not be treated as a bug.

14.7 Performance Concerns

Timer-check granularity: polling all 800 peers' timers (§4) on a single tick must not become an O(n²) scan — use a min-heap keyed by next deadline, not a linear scan per tick; TCP-MD5 setsockopt cost is one-time per connection, not per-packet, so it does not sit on the hot decode path.

14.8 Edge Cases

Simultaneous-open collision (§8.1's collision detection); a peer that completes TCP handshake but never sends OPEN (must still respect the connect-retry timer, not hang forever); a peer sending OPEN with an unsupported capability — negotiate down (ignore the unsupported capability), never NOTIFICATION unless the capability is Optional Parameter type unsupported entirely (§8.1's malformed-input example); clock skew between connect-retry-timer restarts and monotonic-clock wraparound (astronomically unlikely on Instant, documented not ignored).

14.9 Failure Analysis

A TCP-MD5 key mismatch manifests as a session permanently stuck outside Established with zero NOTIFICATIONs — by design, per RFC 2385's threat model (§25 T-4) — so detection relies on absence-of-progress telemetry (bgp_fsm_state{peer} gauge stuck), not an error counter. Containment is automatic (P2: per-peer task isolation means one stuck peer never affects others); recovery is manual (operator fixes the key on one side) once the runbook (§27) narrows the cause.

14.10 Operational Notes

Emit bgp_fsm_state{peer_id} as a gauge (I10) and bgp_fsm_transition_total{from,to,event} as a counter (P13); the docs/runbooks/session-wont-establish.md runbook (§27) is written against this phase's telemetry. Rolling upgrade: a bgpd restart resets all FSMs to Idle and re-establishes from scratch (ADR-14 — no persistence) unless Graceful Restart (Phase 8, §20) is negotiated.

16. Phase 4 — Best-Path Decision Process

16.1 Objectives

Implement the ten-tie-breaker deterministic decision function (§8.4, P1, P9, I2) as a pure function over LocRib candidates, with a differential test harness comparing against BIRD and FRRouting on identical synthetic inputs.

16.2 Detailed Implementation Steps

Implement AsPath::path_length (I3) with the AS_SET-counts-as-1 rule (RFC 4271 §9.1.2.2); implement the ten-stage comparator as an ordered chain of total (never-partial) comparisons ending in the router-ID/peer- address tie-breaker (P9, I2); gate MED comparison on same-immediate- upstream-AS (I13, ADR-16's missing-MED-as-0 convention); wire LocRib::select_best to re-run only for prefixes whose candidate set actually changed (an optimization, not a correctness requirement, justified against M2's ≤1 µs-on-5-candidates budget).

16.3 Deliverable

bgp-bestpath crate; a differential-test binary that feeds identical synthetic route sets to this implementation, BIRD, and FRRouting and diffs the chosen best route (feeds M8/M9, §31).

16.4 Acceptance Criteria

100% best-path agreement with BIRD and FRRouting (M8, M9, §31) across a 5,000-case differential corpus; select_best on 5 candidates completes in ≤ 1 µs p50 (M2); the totality property test (prop_bestpath_no_unresolved_tie, I2) passes 10,000 random candidate sets with zero ties surviving all ten stages.

16.5 Conformance Fixtures

fixtures/bestpath_localpref_tiebreak.json → LOCAL_PREF 200 beats 100; fixtures/bestpath_aspath_set_length.json (AS_SEQUENCE len 3 vs AS_SET len 5) → the AS_SEQUENCE route wins (I3, regression-guards the §8's pitfall); fixtures/bestpath_med_cross_as.json (different upstream AS, MED 50 vs 100) → MED ignored, falls through to next tie-break (I13); fixtures/bestpath_full_tie.json (identical through stage 9) → stage 10 (peer address) resolves deterministically (P9).

16.6 Pitfalls

Comparing MED across different upstream ASes (I13) inverts intended traffic engineering — the single most commonly miscited tie-breaker in operator forums; treating an AS_SET segment's length as its element count instead of 1 (I3) silently inverts the shortest-AS-PATH preference; forgetting that LOCAL_PREF is never sent over eBGP (§8.2) and defaulting to 0 for eBGP-received routes without an explicit per-peer default-local-pref policy.

16.7 Performance Concerns

The ten-stage comparator must short-circuit at the first strictly-resolving stage (most comparisons resolve at stage 1 or 3 in practice) — a benchmark should confirm p50 latency is dominated by early-exit cases, not by always evaluating all ten stages; avoid allocating a new Vec per comparison call on the hot re-selection path.

16.8 Edge Cases

A candidate set of exactly one route (trivially "best," but still must pass through the same function — no special-cased single-candidate shortcut that could diverge from the general algorithm); all candidates from the same peer (occurs transiently during Adj-RIB-In replay after a session reset); a route with atomic_aggregate set (does not itself affect any tie-breaker, but must round-trip through unchanged, verified by encode/decode symmetry with Phase 1).

16.9 Failure Analysis

A best-path disagreement between two routers in the same AS (I2 violated at the network level, not just unit-test level) produces a persistent forwarding loop or blackhole — this is why M8/M9's 100% differential-agreement target against two independent real implementations exists as a release gate (§30), not merely a nice-to- have benchmark.

16.10 Operational Notes

Emit bgp_bestpath_recompute_total{prefix_count} and bgp_bestpath_latency_seconds histograms (P13, M2); a best-path disagreement discovered in production (via the differential harness run periodically against live RIB snapshots, §29) triggers immediate paging — silent divergence is the single worst outcome this phase can produce.

17.1 Objectives

Implement the typed import/export filter DSL (§8.5, P3, ADR-04) with parse-time type-checking and a pure evaluator (I9), replacing Phase 3's provisional no-op filter pass-through.

17.2 Detailed Implementation Steps

Implement the EBNF grammar (§8.5) as a recursive-descent parser producing the FilterStmt/Expr AST (§11); implement the exhaustiveness check (§8.5's failure-path example) rejecting any statement path lacking a terminal accept/reject at parse time, not runtime; implement FilterEngine::evaluate (I9) as a pure interpreter over the AST with no mutable global state; wire import filters between Adj-RIB-In and Loc-RIB and export filters between Loc-RIB and Adj-RIB-Out (§3's filter-engine boundary), replacing Phase 3's stub.

17.3 Deliverable

bgp-filter crate; bgpd --check-config validates a filter file and reports the first type error with line/column, without touching any live route (P3).

17.4 Acceptance Criteria

Parse-time rejection of 100% of a 200-case malformed-filter corpus (undeclared fields, non-exhaustive branches, type mismatches) with a line-numbered diagnostic; filter evaluation latency ≤ 100 ns p50 for a 3-rule filter (M10, §31); zero observable side effects across a 1,000-case prop_filter_purity property test (I9).

17.5 Conformance Fixtures

fixtures/filter_reject_as_path.dsl (§8.5 R1) → route with AS 64513 in path is rejected; fixtures/filter_med_local_pref.dsl (§8.5 R2) → MED > 1000 sets LOCAL_PREF 50; fixtures/filter_undeclared_field.dsl (typo'd field name) → parse-time TypeError::UnknownField at the reported line; fixtures/filter_nonexhaustive.dsl (missing terminal on one branch) → parse-time TypeError::NonExhaustive.

17.6 Pitfalls

A free-form config would let a typo'd field name silently no-op (AS7007-class risk, §26 FM-1) — the type checker exists specifically to convert this into a build-time failure (P3); AS-path regex patterns using ambiguous anchoring ([= * 100 * =] vs [= 100 =], "anywhere" vs "exact") are a frequent operator-error source — the grammar (§8.5) requires explicit anchors, no implicit "anywhere" default.

17.7 Performance Concerns

The AST interpreter must avoid re-parsing or re-type-checking on every route (parse once at config load, evaluate the pre-built AST per route) — verified by a benchmark showing evaluation cost independent of filter complexity beyond the first invocation; AS-path regex matching uses a precompiled automaton, not a fresh regex compile per route.

17.8 Edge Cases

An empty filter body (implicit reject, per the exhaustiveness rule — never implicit accept, P12's fail-closed spirit applied to policy); a filter referencing a community that does not exist yet on the route (comparison against an absent field evaluates to a defined "absent" sentinel, not a parse-time-only-detectable error); nested if/else up to a bounded depth (parser rejects unbounded recursion beyond a documented limit to bound stack use on adversarially large config files).

17.9 Failure Analysis

A filter that would fall through with no terminal action is caught at bgpd --check-config time, before any config reload — this closes the original design's ambiguous-default failure mode (documented in §8.5) where a production reload could silently start accepting everything. Detection is structural (parser rejects the file); there is no runtime failure mode for this class once Phase 5 ships.

17.10 Operational Notes

bgpd --check-config is the operational entrypoint for policy changes (§29's compatibility policy requires it in every deploy pipeline); emit bgp_filter_eval_total{filter_name,result} (P13) so an operator can audit which rule is actually firing on production traffic without guessing from the DSL source alone.

Generalize the RIB (already (AFI,SAFI)-indexed per P8) to populate a second address family — IPv6 unicast — via MP_REACH_NLRI/ MP_UNREACH_NLRI (RFC 4760), with zero RIB-schema migration (P8's payoff).

18.2 Detailed Implementation Steps

Implement the Multiprotocol capability negotiation in OPEN (RFC 4760, capability code 1, carrying (AFI,SAFI) pairs); implement MP_REACH_NLRI/MP_UNREACH_NLRI encode/decode (§8.2's attribute table, types 14/15) carrying an IPv6 NEXT_HOP (since the base NEXT_HOP attribute is IPv4-only, per §8.2); extend AdjRibIn/LocRib/ AdjRibOut instantiation to a second (Afi::Ipv6, Safi::Unicast) table (P8: no schema change, only a new table key); extend best-path (Phase 4, §16) to operate per-(AFI,SAFI) — already true by construction since select_best takes a (Afi,Safi)-scoped PrefixTable.

18.3 Deliverable

bgp-mp crate; a dual-stack interop session against BIRD/FRRouting exchanging both IPv4 and IPv6 unicast routes over one TCP session.

18.4 Acceptance Criteria

IPv6 UPDATE round-trip (encode/decode via MP_REACH_NLRI) passes on a 5,000-case property test; a dual-stack session negotiates both AFIs in one OPEN capability exchange and exchanges routes in both families within the M7 (§31) session-establishment budget; zero cross-family contamination verified by a fixture asserting an IPv6 withdraw never affects the IPv4 table for the same numeric prefix bit-pattern.

18.5 Conformance Fixtures

fixtures/mp_capability_negotiation.bin → OPEN advertises (AFI=2,SAFI=1) and (AFI=1,SAFI=1) together; fixtures/ mp_reach_ipv6_nexthop.bin → decodes a 2001:db8::/32 route with a 2001:db8::1 next-hop; fixtures/mp_unreach_zero_nlri.bin (zero-length NLRI in MP_UNREACH) → decodes as a valid family-scoped end-of-RIB marker, regression-guarding the ambiguity noted in Phase 8 (§20.6).

18.6 Pitfalls

Forgetting that NEXT_HOP for non-IPv4-unicast families lives inside MP_REACH_NLRI, not the base NEXT_HOP attribute — a common decode bug that silently produces a zero/garbage next-hop for IPv6 routes; failing to negotiate the Multiprotocol capability before sending any MP attribute causes strict peers to NOTIFICATION-reject the session entirely (treat capability negotiation as a precondition, not best- effort).

18.7 Performance Concerns

A second (AFI,SAFI) table doubles trie memory for dual-stack peers — within the ≤1 GiB budget (§4, M6) only because interning (P11) is per-attribute-set, not per-family, so shared attribute sets across families still deduplicate.

18.8 Edge Cases

A peer that negotiates IPv6 capability but never sends an IPv6 route (legal, must not be treated as an error); an MP_REACH_NLRI attribute present alongside a non-empty base NLRI field in the same UPDATE (technically permitted by the wire format for mixed-family messages; this design treats the two NLRI lists as independent, never merged).

18.9 Failure Analysis

A next-hop-extraction bug for IPv6 (§18.6) manifests as routes installed with an unreachable/zero next-hop — caught by Phase 11's FIB installation, which rejects a route whose next-hop has no covering route in the kernel table (§23.9), not silently blackholed.

18.10 Operational Notes

show bgp ipv6 unicast in bgp-cli (Phase 12) mirrors show bgp with an explicit family selector; telemetry labels (bgp_locrib_prefix_count {afi="ipv6",safi="unicast"}) follow the same schema as IPv4 (P13, no per-family metric-name drift, per §29 compatibility policy).

19. Phase 7 — Route Reflection

19.1 Objectives

Implement RFC 4456 route reflection to break the O(n²) iBGP full-mesh ceiling (§32), enforcing loop-freedom via ORIGINATOR_ID/CLUSTER_LIST (I7, I8) rather than relying on the eBGP AS_PATH mechanism, which does not apply within an AS.

19.2 Detailed Implementation Steps

Implement cluster-id configuration and RR-client-vs-non-client peer classification (Halabi Ch. 5, §5); on re-advertisement from an RR to a non-client iBGP peer, inject ORIGINATOR_ID (if absent) and prepend this router's cluster-id onto CLUSTER_LIST (RFC 4456 §8); on ingest, reject any route whose CLUSTER_LIST already contains this router's own cluster-id (I8); extend Adj-RIB-Out's re-advertisement rule (I7) to allow iBGP-to-iBGP forwarding specifically for RR-client relationships, overriding the Phase 3 default.

19.3 Deliverable

bgp-rr crate; a three-router iBGP topology (one RR, two clients) where a route learned by client A propagates to client B via the RR without a direct client-A–client-B session.

19.4 Acceptance Criteria

A route from client A reaches client B's Loc-RIB within the I12 convergence budget (§7) via the RR only; CLUSTER_LIST loop fixtures (§19.5) reject 100% of injected loop cases; ORIGINATOR_ID is never added to a route already carrying one (idempotent re-reflection).

19.5 Conformance Fixtures

fixtures/rr_basic_reflection.json → client A's route appears in client B's Adj-RIB-In with ORIGINATOR_ID = A's router-ID and CLUSTER_LIST = [RR's cluster-id]; fixtures/rr_cluster_loop.json (injected route already carrying this RR's cluster-id) → rejected (I8); fixtures/rr_next_hop_unchanged.json → NEXT_HOP is untouched by reflection (unlike eBGP's next-hop-self behavior).

19.6 Pitfalls

Reflecting a route to another non-client without adding ORIGINATOR_ID/ CLUSTER_LIST breaks loop detection for the next hop in the reflection chain; changing NEXT_HOP during reflection (an eBGP habit) breaks reachability, since iBGP next-hops must remain the originating eBGP router's address unless next-hop-self is explicitly configured (a distinct, non-default policy knob, out of Phase 7's baseline).

19.7 Performance Concerns

CLUSTER_LIST growth is bounded by reflection-chain depth (rarely > 3 in practice) so the loop-check scan cost is negligible relative to best-path recomputation (§16); RR fan-out (one client update reflected to N other clients) is O(N) UPDATE generations, budgeted within M5 (§31) per-peer UPDATE-generation cost.

19.8 Edge Cases

A client peer that is also configured as an RR for a different cluster (hierarchical RR, legal per RFC 4456); a route with a pre-existing CLUSTER_LIST from a different AS's RR (must not be confused with this router's own cluster-id — exact match only, I8); a misconfigured cluster-id shared accidentally by two independent RRs (§26 FM-3, detected by cross-RR loop rejection firing unexpectedly).

19.9 Failure Analysis

A misconfigured CLUSTER_LIST (two RRs sharing one cluster-id by operator error) manifests as routes mysteriously failing to reflect between the two RRs' clients — I8 rejects them as false-positive loops; detection is via bgp_rr_loop_reject_total spiking on routes that should have propagated; the runbook (§27) for "route not propagating within iBGP" leads with a cluster-id uniqueness check.

19.10 Operational Notes

show bgp reflected-routes (Phase 12 CLI) filters Loc-RIB entries carrying a non-empty CLUSTER_LIST; emit bgp_rr_reflect_total{cluster_id} (P13) so an operator can see per-cluster reflection volume during a topology change.

20. Phase 8 — Graceful Restart

20.1 Objectives

Implement RFC 4724 graceful restart so a planned bgpd restart (or a brief peer-side outage) does not trigger a network-wide withdraw-then- reannounce churn cascade, trading a bounded stale-route window for avoided reconvergence cost (P7, ADR-09).

20.2 Detailed Implementation Steps

Negotiate the Graceful Restart capability (flags, restart-time, per-AFI/SAFI forwarding-state-preserved flag) during OPEN; on the non-restarting side, upon session loss to a GR-capable peer, mark that peer's Adj-RIB-In routes stale (retained in Loc-RIB candidacy, not withdrawn) and arm a restart-timer at the negotiated restart-time (default 120 s, ADR-09); on reconnect, the restarting peer re-sends its full route set followed by an end-of-RIB marker (a zero-NLRI UPDATE for IPv4 unicast, or a zero-NLRI MP_UNREACH_NLRI per family, §8.2); the non-restarting side purges any stale route not refreshed before end-of-RIB or before the restart-timer expires, whichever comes first.

20.3 Deliverable

bgp-gr crate; a test harness that kills and restarts one peer's bgpd process mid-session and verifies the other peer's Loc-RIB retains that peer's routes as stale throughout the outage window, without a FIB withdrawal (Phase 11 dependency, deferred assertion until §23).

20.4 Acceptance Criteria

Stale-route retention holds for the full configured restart-time (default 120 s ± 1 s, ADR-09) with zero premature withdrawal; end-of- RIB correctly clears the stale flag for every family that sent one, independently per (AFI,SAFI); a restart that exceeds restart-time purges all that peer's stale routes and triggers best-path recomputation exactly once per affected prefix (not once per stale route individually — batched).

20.5 Conformance Fixtures

fixtures/gr_capability_negotiation.bin → OPEN carries GR capability with restart_time=120, per-family forwarding-preserved flags set; fixtures/gr_stale_retention.trace (session drop, no reconnect within 120s) → routes purged at t=120s exactly, not earlier; fixtures/ gr_eor_ipv4.bin (zero-NLRI UPDATE) → clears stale for (AFI=1,SAFI=1) only; fixtures/gr_eor_mp_ipv6.bin (zero-NLRI MP_UNREACH) → clears stale for (AFI=2,SAFI=1) only, regression- guarding the ambiguity in §20.6.

20.6 Pitfalls

End-of-RIB for the base IPv4-unicast family is a plain zero-NLRI UPDATE, while for every MP-BGP family it is a zero-NLRI MP_UNREACH_NLRI — conflating the two (treating any zero-NLRI UPDATE as "all families done") produces a partial-GR bug where non-IPv4 stale routes linger past their intended clear point; a restart-time set too short causes legitimate slow-reconnecting peers to have routes purged and re-churned anyway, defeating the purpose of GR (ADR-09's tradeoff made explicit).

20.7 Performance Concerns

Marking routes stale must be O(peer's route count), not O(total Loc-RIB size) — implemented as a flag on the peer's Adj-RIB-In entries, checked lazily during best-path candidate iteration, not a full Loc-RIB scan; batching the post-purge best-path recomputation (§20.2) avoids an O(N) individual-recompute storm on a single large peer's GR timeout.

20.8 Edge Cases

A peer restarting so fast the TCP connection never fully drops (must still process the new OPEN's GR capability correctly, not assume a fresh session implies no prior GR state); a peer that negotiates GR but crashes without ever reconnecting (routes purged cleanly at timer expiry, no special-cased "never came back" branch needed beyond the existing timer path); GR interacting with route-flap damping (Phase 9, §21) — a GR-driven restart must not itself accumulate flap penalty, since it is a planned event, not instability (cross-phase consideration flagged here, enforced in §21.2).

20.9 Failure Analysis

A GR-capable peer that never sends end-of-RIB (buggy peer implementation) leaves stale routes lingering until the restart-timer forcibly purges them — bounded by ADR-09's 120 s default, so the blast radius is time-bounded even under a misbehaving peer; detection via a bgp_gr_stale_route_count{peer} gauge that should reach zero well before timer expiry in the healthy case.

20.10 Operational Notes

show bgp neighbor <peer> graceful-restart (Phase 12 CLI) surfaces negotiated capability and current stale-route count; emit bgp_gr_restart_total{peer} and bgp_gr_stale_purge_total{peer,reason} (P13); the maintenance runbook (§27) documents the expected GR sequence for a planned bgpd upgrade.

21. Phase 9 — Route-Flap Damping

21.1 Objectives

Implement RFC 2439 route-flap damping, opt-in and default-off per RFC 7196 guidance (ADR-10, P7), to suppress a persistently-oscillating route without suppressing normal single-transition route changes.

21.2 Detailed Implementation Steps

Implement a per-(peer,prefix) penalty counter incremented on each flap event (route withdrawal followed by reannouncement, or an attribute change deemed flap-worthy per configuration); implement exponential decay with a configurable half-life (default 15 min, RFC 2439); implement suppress/reuse thresholds (default 2000/750) gating whether a route is withheld from best-path candidacy while suppressed; explicitly exclude Graceful-Restart-driven route changes (Phase 8, §20) from penalty accrual — a planned restart is not instability (cross-phase guard flagged in §20.8).

21.3 Deliverable

bgp-rfd crate, disabled by default (ADR-10); an opt-in test harness that flaps a synthetic peer session on a fixed interval and verifies suppression engages at the configured threshold and disengages at the reuse threshold.

21.4 Acceptance Criteria

Penalty accrual and decay match the RFC 2439 half-life formula within 1% over a 24-hour simulated timeline (accelerated clock in test); suppression engages within one flap-interval of crossing the suppress threshold and disengages within one decay-check interval of crossing the reuse threshold; a GR-driven restart (§20) accrues zero penalty, verified by a dedicated fixture.

21.5 Conformance Fixtures

fixtures/rfd_penalty_accrual.json (10 flaps over 1 hour) → penalty trajectory matches the RFC 2439 formula within 1%; fixtures/ rfd_suppress_reuse_cycle.json → suppression at penalty ≥ 2000, reuse at penalty ≤ 750; fixtures/rfd_gr_exempt.json (a GR-negotiated restart) → zero penalty accrued (§20.2 cross-guard).

21.6 Pitfalls

RFC 7196 documents that blanket always-on damping penalizes normal internet route dynamics (multihomed sites, mobile anycast) more than it helps — hence ADR-10's default-off; failing to exempt GR-driven restarts from penalty accrual defeats Phase 8's entire purpose (a planned maintenance restart would itself trigger damping, the opposite of the intended stability trade).

21.7 Performance Concerns

Penalty update must be O(1) per flap event (M-table target, §31), not a full-table rescan; decay computation is lazy (computed on read, from elapsed time since last update), not a background timer ticking every prefix — avoids an O(total-suppressed-count) periodic sweep.

21.8 Edge Cases

A route that flaps exactly at the suppress threshold boundary (must suppress, not require strictly-greater-than by an off-by-one); a suppressed route whose peer session itself resets (Adj-RIB-In entry removed entirely — the penalty state must be discarded, not retained indefinitely, to bound memory); damping interacting with route reflection (Phase 7) — a reflected route's flap history is tracked per-reflector, not inherited from the original announcer.

21.9 Failure Analysis

Damping enabled against operator intent (a config error) manifests as legitimate routes intermittently missing from the FIB during normal multihoming failover — detectable via bgp_rfd_suppressed_count unexpectedly non-zero on a network with no known instability; the default-off posture (ADR-10) makes this a config-review failure mode, not a silent-by-default one.

21.10 Operational Notes

show bgp dampened-routes (Phase 12 CLI) lists currently-suppressed prefixes with penalty and time-to-reuse; emit bgp_rfd_penalty{peer,prefix} and bgp_rfd_suppressed_count gauges (P13); enabling damping is a config-diffed, reviewed change per §29's compatibility policy, not a runtime toggle without review.

22. Phase 10 — RPKI Origin Validation & Security Hardening

22.1 Objectives

Implement RFC 6811 BGP Prefix Origin Validation against an RFC 6480 RPKI-derived ROA (Route Origin Authorization) cache, closing the AS7007-class (§26 FM-1) and Pakistan-Telecom-class (§26 FM-2) leak/ hijack surface at the origin-AS layer, and harden max-prefix and session-security defenses.

22.2 Detailed Implementation Steps

Implement an RTR (RPKI-to-Router protocol, RFC 8210) client consuming a ROA cache from an external validator (e.g., Routinator, rpki-client — this router is an RTR client, not a validator, per §1's scope boundary); classify each received route as Valid/Invalid/ NotFound per RFC 6811's algorithm (origin AS + max-length match against the ROA set); wire the classification as an input to the policy engine (Phase 5, §17) so operators can write a filter rule if bgp_origin_validation = invalid then reject; enforce max-prefix limits (I11) per peer as a hard defense independent of RPKI.

22.3 Deliverable

bgp-rpki crate; an end-to-end test where a route with a valid ROA is accepted, a route with an Invalid origin (ROA exists, AS mismatch) is rejected by a default policy, and NotFound (no ROA) passes through unless explicitly filtered.

22.4 Acceptance Criteria

RTR client correctly classifies 100% of a 500-case ROA-vs-route test matrix (valid, invalid-origin, invalid-max-length, not-found); a default-configured router rejects Invalid-classified routes within one best-path recomputation cycle of ROA cache update; the AS7007 and Pakistan-Telecom incident replays (§25, §26) both fail to cause a blackhole/hijack against this router's default configuration (validated end-to-end in Phase 12's conformance run, §24).

22.5 Conformance Fixtures

fixtures/rpki_valid_origin.json → Valid, accepted; fixtures/ rpki_invalid_origin_mismatch.json (ROA says AS 64500, route says AS 64599) → Invalid, rejected by default policy; fixtures/ rpki_not_found.json (no covering ROA) → NotFound, passes (operator policy decides); fixtures/rpki_as7007_replay.json (AS7007's 1997 full-table origination pattern) → rejected by max-prefix (I11) before RPKI even applies, demonstrating defense-in-depth.

22.6 Pitfalls

RPKI origin validation defends against a wrong-origin-AS hijack but does not validate the AS_PATH itself — a valid-looking path through a legitimately-authorized-but-compromised AS is undetected by RFC 6811 alone (this is exactly what BGPsec, RFC 8205, addresses, deferred §39); treating NotFound as equivalent to Invalid over-rejects the majority of the internet's currently-unsigned prefix space — RFC 6811 explicitly treats them as distinct classifications.

22.7 Performance Concerns

ROA-cache lookups must be O(prefix-bit-length) (trie-indexed, same structure as ADR-06's Patricia trie) to avoid becoming the new bottleneck on the 200,000 UPDATEs/s burst path (§4); RTR cache updates are incremental (serial-number-based per RFC 8210), not full-table refetches, to avoid a full best-path re-run on every ROA change.

22.8 Edge Cases

A ROA covering a less-specific prefix than the announced route with a max-length constraint violated (Invalid by max-length, distinct from origin mismatch — both map to Invalid but are logged with distinct reasons); an RTR session to the validator itself dropping (this router must continue operating on its last-known-good ROA cache, not fail open to "accept everything" nor fail closed to "reject everything"); a ROA for this router's own originated prefix that is itself misconfigured (an operator self-inflicted RPKI outage — documented as a distinct incident class in §26).

22.9 Failure Analysis

An RTR session loss to the validator is contained by continuing to serve the last-known-good cache (bounded staleness, logged) rather than either extreme fail-mode; a misconfigured ROA for one's own prefix (over-restrictive max-length) causes valid own-originated routes to be marked Invalid by other routers' validators on the internet at large — outside this router's control but documented in the runbook (§27) as "check your own ROA first" before assuming a peer or transit issue.

22.10 Operational Notes

show bgp rpki cache (Phase 12 CLI) surfaces ROA cache size, last update serial, and RTR session health; emit bgp_rpki_classification_total{result} and bgp_rtr_session_up gauge (P13); RPKI cache staleness beyond a configured threshold triggers an operational alert (§27), distinct from an RTR session-down alert.

23. Phase 11 — FIB Integration (Linux Netlink)

23.1 Objectives

Implement the FibBackend trait (§11, P6) against Linux netlink, making Loc-RIB's best routes (§8.3, §16) forwarding-effective, while keeping bgp-fib-mock (§10) as the default backend for every prior phase's tests.

23.2 Detailed Implementation Steps

Implement install_route/withdraw_route (§11) via RTM_NEWROUTE/RTM_DELROUTE netlink messages, tagged with protocol id 12 (BGP, per the Linux routing-protocol registry) so ip route distinguishes BGP-installed routes from static/other-protocol ones; subscribe to Loc-RIB's RibChange::BestPathChanged event stream (I5) as the sole trigger for FIB writes — no polling; implement recursive next-hop resolution (a BGP next-hop not directly connected requires an IGP-resolved egress) by querying the kernel's existing route table; implement ECMP (equal-cost multipath) by installing all tied best routes when Phase 4's tie-breakers produce a true multi-path tie under an explicit multipath policy (a Phase-11 extension, not part of the single-winner §16 baseline — flagged distinctly here since it changes select_best's single-winner contract only under this opt-in).

23.3 Deliverable

bgp-fib-linux crate; an end-to-end test showing a Loc-RIB best-path change reflected in ip route show within the FIB-install latency budget (M4, §31).

23.4 Acceptance Criteria

FIB install rate ≥ 10,000 routes/s sustained (M4); a full 1.2M-route synthetic table installs completely within a bounded batch window (derived from M3+M4, §32); a route whose next-hop is unresolvable (§23.8) fails installation with a logged reason, never a silent drop.

23.5 Conformance Fixtures

fixtures/fib_install_basic.json → 203.0.113.0/24 via 198.51.100.1 appears in ip route show table main with proto bgp; fixtures/fib_unresolvable_nexthop.json (next-hop with no covering kernel route) → install fails, bgp_fib_install_failed_total{reason= "unresolvable_nexthop"} increments; fixtures/fib_bulk_1_2m.json.gz → full-table install completes within budget (M3+M4 derived, §32).

23.6 Pitfalls

A next-hop with no route in the kernel table fails installation silently if error codes from the netlink recv_ack are not checked — always check the ack; CAP_NET_ADMIN is required for netlink route writes, distinct from CAP_NET_BIND_SERVICE needed for the BGP listener itself (§14) — a container missing either capability fails differently and must be distinguished in diagnostics.

23.7 Performance Concerns

Individual netlink round-trips (~1 ms each per the original design's measurement) do not meet the 10,000 routes/s budget (M4) — batch multiple RTM_NEWROUTE messages into a single netlink multi-message send with one combined ack-wait, verified by a benchmark comparing per-route vs batched netlink throughput.

23.8 Edge Cases

A best-path change that is a pure attribute change with an unchanged next-hop (must still generate a FIB write if any FIB-relevant field — e.g., ECMP membership — changed, but should skip the netlink call entirely if truly nothing FIB-relevant changed, an optimization not a correctness requirement); a next-hop that becomes unresolvable after successful installation (the IGP withdraws the covering route) — detected by a periodic reconciliation pass (§23.10), not assumed permanent.

23.9 Failure Analysis

netlink permission denial (missing CAP_NET_ADMIN) fails every install call identically and immediately at daemon startup — detectable via a startup self-check that attempts one no-op netlink call before accepting any peer session, failing fast rather than discovering the gap only when the first real route needs installing.

23.10 Operational Notes

A periodic FIB-reconciliation pass (interval configurable, default 60 s) diffs Loc-RIB's best routes against the live kernel table and re-asserts any drift (defense against out-of-band kernel-table mutation by another process); emit bgp_fib_install_total{result} and bgp_fib_reconcile_drift_total (P13); show bgp fib-status (Phase 12 CLI) surfaces the last reconciliation pass's drift count.

24. Phase 12 — Conformance, Interop, Fuzzing & Canary

24.1 Objectives

Assemble the full conformance-bucket suite (§10 conformance/buckets/) across every prior phase's fixtures, run continuous differential interop against BIRD and FRRouting, run the fuzz-target corpus continuously in CI, and execute the 30-day full-table canary as the long-tail safety net before any release is cut (§30).

24.2 Detailed Implementation Steps

Wire every phase's named fixtures (§13.5 through §23.5) into one CI-run bucket suite, gated on every PR (ADR-19); implement the six fuzz targets (open_decode, update_decode, attribute_decode, notification_decode, config_parse, differential_bird — the last comparing this router's and BIRD's FIB output for identical random valid UPDATEs, exercising I2/M8 continuously rather than only at unit- test time); implement the interop CI matrix establishing eBGP and iBGP sessions against BIRD and FRRouting containers and asserting best-path agreement (M8, M9); implement the 30-day canary harness peering with a public route-server feed (or a recorded full-table replay where a live peering is unavailable) and asserting stable memory and FIB consistency over the run.

24.3 Deliverable

A single make conformance target running all buckets; fuzz.yml running all six targets nightly with corpus persistence; a canary report artifact (docs/performance/canary-report-<date>.md) committed per soak run.

24.4 Acceptance Criteria

100% of named fixtures across all 13 phases pass (§13.5–§23.5, enumerated exhaustively in the bucket suite manifest); fuzz targets sustain ≥ 10,000 exec/s (M11, §31) with zero crashes over a 24-hour CI run; the 30-day canary shows RSS growth ≤ 5% over the full window and zero FIB-vs-Loc-RIB drift events (M12, §31).

24.5 Conformance Fixtures

conformance/buckets/manifest.json (auto-generated index of every named fixture from §13.5–§23.5, cross-checked for completeness against this phase's own acceptance criterion); fixtures/fuzz_corpus_seed/ (one seed file per fuzz target, versioned); fixtures/canary_baseline.json (expected steady-state memory/FIB-count baseline for drift comparison).

24.6 Pitfalls

A fixture added in an earlier phase but never wired into the bucket manifest silently stops being checked in CI — the manifest-completeness self-check (§24.5) exists specifically to catch this class of regression; interop CI flakiness from container startup races is a common false-negative source — mitigate with an explicit readiness probe (birdc show status / vtysh -c "show version") before running any session-establishment assertion, not a fixed sleep.

24.7 Performance Concerns

Full bucket-suite runtime (~15 min including full-table fixtures) must not become the PR-merge bottleneck — split into a fast required-to- merge subset (excludes the 1.2M-route full-table fixtures) and a full nightly run, so per-PR latency stays low while nightly coverage stays complete.

24.8 Edge Cases

A fuzz-found crash that only reproduces under a specific corpus seed (must be checked into the persisted corpus, not discarded, so the regression is permanently guarded — ADR-12's continuous-fuzzing premise depends on corpus persistence, not ephemeral runs); an interop disagreement between this router and BIRD that is traced to a BIRD- specific non-standard extension (documented as a known deviation, not silently special-cased away — §29's compatibility notes record it).

24.9 Failure Analysis

An interop divergence discovered in CI (M8/M9 miss) blocks release (§30) until resolved by either a fix or a documented, reviewed ADR explaining the intentional deviation — never silently waived; a canary failure (RSS growth beyond 5% or any FIB drift) blocks the next release train regardless of how many other gates passed, since it is the only signal that exercises real multi-day production-like conditions.

24.10 Operational Notes

The canary report (§24.3) is the primary artifact reviewed before tagging a release (§30); bgp_canary_rss_bytes and bgp_canary_fib_drift_total (P13) feed the release-gating dashboard; a failed nightly fuzz run pages the on-call rotation the same as a production incident, reflecting that a crash-causing input found today is a production vulnerability tomorrow.

28. Compatibility & Versioning

Wire compatibility. The BGP-4 wire format (RFC 4271 and its extensions, §8.2) is externally standardized and never versioned by this project; capability negotiation (OPEN's optional parameters) handles per-peer feature differences at the protocol layer, not via project versioning. Storage compatibility. N/A — no persistent RIB state (ADR-14); configuration file schema is versioned independently (see below). Schema evolution (config). bgp-config's file schema carries an explicit schema_version field; a version bump that removes or renames a field is a SemVer major bump (ADR-20) and ships with a migration note in CHANGELOG.md. API stability. The CLI (bgp-cli, §27) and any future gRPC API (§39, deferred) follow SemVer independently of the core daemon version; a CLI-breaking change is a major bump on the CLI crate specifically. Migration. Config migrations are additive-preferred (new optional fields default to prior behavior); breaking migrations ship a bgpd --migrate-config tool. Deprecation policy. A deprecated config field or filter DSL construct emits a bgpd --check-config warning for at least one minor version before removal in the next major version. SemVer policy (ADR-20): patch = bugfix, no behavior change to wire/config semantics; minor = additive feature (new AFI/SAFI, new filter construct), backward compatible; major = any wire-adjacent behavior change (e.g., a best-path tie-breaker default change) or config-breaking change. Rolling-upgrade guarantees. Any two adjacent minor versions interoperate over BGP (external wire compatibility is unaffected by internal version); a major version bump documents any interop-relevant behavior change explicitly in CHANGELOG.md and, where it affects best-path determinism (I2), requires a network-wide coordinated upgrade window, called out explicitly in the release notes.

32. Scalability Analysis

What stays constant. Per-message decode cost (M1) is O(1) in table size; per-peer task memory overhead is O(1) per peer, not O(table size); the filter engine's evaluation cost (M10) is O(filter complexity), independent of RIB size. What grows, with Big-O. Loc-RIB memory is O(unique prefixes × interned-attribute-set count) (P11 keeps the constant small); trie lookup is O(prefix bit length), effectively O(32) or O(128), not O(table size) (ADR-06); iBGP full-mesh session count is O(n²) in router count absent route reflection — the named bottleneck this project's Phase 7 (§19) exists to remove; Adj- RIB-In storage amplification is O(peer count) per prefix in the worst case (§4). Named bottlenecks in order. (1) iBGP full-mesh O(n²) session scaling — removed by route reflection (§19); (2) netlink per-route-call overhead — removed by batching (§23.7); (3) single-core decode saturation at ~200K UPDATEs/s (§4) — the next lever is sharding decode across cores by peer, deferred (§39) since Phase 0-12's 800-peer/single-core budget does not require it. Horizontal/vertical scaling. Vertical: more cores parallelize independent peer tasks (P2) but Loc-RIB writes remain serialized per-(AFI,SAFI) (a coordination-overhead ceiling); horizontal: BGP has no native horizontal-scale-out for one router's RIB — the standard lever is route reflection/confederation to scale the network, not scale one router's process (§19). Sharding/partitioning. Per-(AFI,SAFI) table partitioning (P8) is the only partitioning this design does internally; partitioning within a single (AFI,SAFI) table (e.g., by prefix range across cores) is a deferred optimization (§39) not required at the 1.2M-route scale in §4. Coordination overhead. Bounded to short critical sections per Loc-RIB write (P2); no distributed-consensus coordination exists in this design — each router decides independently (MM1, §33), which is the source of BGP's stable-paths convergence subtlety (Griffin & Wilfong, §5). Practical ceiling and levers beyond it. This design's practical ceiling is a full-internet-table single router (~1.2M IPv4 + 200K IPv6, §4); beyond that (a route-server serving many downstream views, or a next-generation internet with a 10× larger table) the next levers are: decode sharding by peer across cores, a partitioned Loc-RIB, and RIB persistence (removing the full-table-reimport-on-restart cost that ADR-14 currently accepts).

33. Mental Models & First Principles

  • MM1 — BGP is a distributed database with no consensus; each router computes its own answer from locally-visible state. Predicts: two routers can legitimately disagree transiently, and global convergence is emergent, not coordinated. Bug class without it: assuming a network-wide "current best route" exists as a single fact rather than per-router state. Applied in §16, §32.
  • MM2 — The FSM is a contract, not a suggestion; an unhandled (State,Event) pair is a silent deadlock, not a crash. Predicts: the worst FSM bugs are invisible until the exact event ordering that hits the gap occurs. Bug class without it: treating "it works in testing" as sufficient without exhaustive (State,Event) coverage (I10). Applied in §14.
  • MM3 — Loop-freedom in path-vector routing is self-describing, not centrally coordinated: the AS_PATH itself is the loop detector. Predicts: any place that skips inspecting the full AS_PATH (e.g., a fast-path optimization) reintroduces the loop risk BGP was designed to prevent. Bug class without it: silent routing loops from partial AS_PATH validation. Applied in §8.1, §16, §32.
  • MM4 — Route-flap damping trades convergence speed for stability — a CAP-like tradeoff, not a free lunch. Predicts: always-on damping looks safer but actively harms legitimately-dynamic routes (RFC 7196). Bug class without it: enabling damping by default and being surprised by suppressed-but-legitimate multihomed failover. Applied in §21.
  • MM5 — iBGP full-mesh is O(n²); route reflection breaks the mesh at the cost of the free-choice property (Griffin & Wilfong). Predicts: a route reflector can, in pathological configurations, hide a route a full-mesh topology would have chosen — a real, not hypothetical, correctness-vs-scalability trade. Bug class without it: assuming route reflection is "free" scaling with zero semantic cost. Applied in §19, §38.
  • MM6 — Policy is a pure function; any side effect in the filter engine is a bug, not a feature. Predicts: a filter that "sometimes" behaves differently on identical input has a purity violation somewhere, not a legitimate stateful policy need. Bug class without it: policy debugging that assumes non-determinism is normal. Applied in §17 (I9).
  • MM7 — The RIB pipeline (Adj-RIB-In → policy → Loc-RIB → policy → Adj-RIB-Out) is structurally the same shape as a compiler's front-end → middle-end → back-end. Predicts: bugs that would be "type errors" in a compiler (an ill-typed filter field) should be caught at the same pipeline stage a compiler would catch them — parse/type-check time, not codegen/runtime. Bug class without it: policy errors surfacing as production route anomalies instead of config-validation failures. Applied in §8.5, §17.
  • MM8 — MED is only a hint, scoped to a single upstream AS; treating it as a global priority is a category error. Predicts: any cross-AS MED comparison produces results the sending AS never intended. Bug class without it: "always-compare-MED" configurations that invert traffic-engineering intent. Applied in §16 (I13).

BIRD made the single-process, integrated-filter-language decision this design's ADR-04/ADR-07 are directly modeled on; it wins in the regime of a single operator wanting one auditable binary with a powerful, uniform policy language and no IPC hop — its niche is service-provider and research-network deployments valuing filter expressiveness over multi-protocol-daemon modularity. FRRouting made the opposite call on FIB integration: a zebra IPC boundary lets independent routing daemons (OSPF, BGP, static) share one FIB safely; it wins wherever multiple protocol daemons must coexist and be independently restartable without one taking down another — its niche is large multi-protocol networking-OS deployments (and it is the direct descendant of Quagga, §5). GoBGP made programmability the central decision, exposing a gRPC control API as the primary interface rather than a CLI; it wins in SDN/controller-driven architectures where BGP is one programmable component wired into a larger automation system, not an operator-facing router in isolation. OpenBGPD made security-through-minimalism and privilege separation the central decision, splitting the untrusted-input-parsing session process from the trusted route-decision engine (RDE); it wins in security- conscious, smaller-scale deployments (OpenBSD's own default router use case) where a smaller trusted-computing-base outweighs raw throughput or programmability.

35. Back-of-Envelope Capacity Model

  • Full dual-stack route count = 1,200,000 (IPv4) + 200,000 (IPv6) = 1,400,000 routes (from §4).
  • Per-route memory ≈ 500 B (interned attributes, P11, from §4) ⇒ memory footprint = 1,400,000 × 500 B ≈ 700 MB, within the ≤ 1 GiB ceiling (M6, §31) with headroom for process overhead.
  • Worst-case Adj-RIB-In amplification = 700 MB × 800 peers (§4 peer ceiling) ÷ interning-deduplication-factor. With P11 interning assuming ~50× attribute-set reuse across peers in a real topology (empirically typical for transit peers sharing upstream attribute patterns): effective footprint ≈ 700 MB × 800 ÷ 50 ≈ 11.2 GB worst-realistic-case, bounding the operator-facing "how much RAM do I need for 800 full-table peers" question.
  • Full-table import bandwidth = 1,200,000 routes × ~500 B wire encoding (attributes + NLRI) ≈ 600 MB ÷ 60 s import budget (M3, §31) ⇒ ≥ 10 MB/s sustained decode+insert throughput required.
  • UPDATE decode CPU budget = 200,000 UPDATEs/s (§4 burst rate) × 5 µs/decode (M1 p50, §31) = 1.0 core-second per wall-second at peak ⇒ a single core saturates decode alone at the burst rate, motivating the sharding-by-peer lever noted in §32 as the next scale step.
  • FIB install throughput requirement = 1,200,000 routes ÷ 60 s import budget (M3) ⇒ ≥ 20,000 routes/s needed at worst case, exceeding the M4 target of 10,000/s by 2× — this is why §23.7 mandates batched netlink calls (10× per-route speedup cited from the original design's measurement) rather than one-route-per-syscall.
  • File-descriptor budget = 800 peers × 1 FD + 16 fixed (§4) = 816 FDs, well within default Linux ulimit -n (1024) but flagged explicitly in docs/runbooks/ since a default-lowered ulimit (256, common in constrained containers) would need explicit raising.
  • Convergence-time chain = decode (5 µs, M1) + filter (≤ 100 ns, M10) + RIB insert (sub-µs, §15.7) + best-path (≤ 1 µs, M2) + FIB install (≤ 100 µs at 10,000 routes/s, M4) ≈ ≈ 110 µs compute-only per route — the remaining budget up to I12's 200 ms convergence SLO is dominated by network RTT (§4's 150 ms worst-case eBGP RTT assumption) and KEEPALIVE/timer granularity, not by this router's own processing.

37. Alternative Architectures (Roads Not Taken)

ALT-1 — Link-state-style flooded topology database instead of path-vector.

      [R1]---[R2]           Every router floods full topology;
       |  \  / |             each computes shortest path locally
      [R3]-[R4]-[R5]         via Dijkstra over a shared graph view.

Regime where it wins: within a single administrative domain with trusted routers and a bounded topology size (this is exactly what OSPF/IS-IS already do intra-domain). Real system: OSPF/IS-IS themselves, and historically IDRP's link-state-adjacent proposals for inter-domain routing. Why rejected here: inter-domain routing spans untrusted administrative boundaries at internet scale (tens of thousands of ASes) — flooding a full topology across mutually distrusting operators leaks sensitive internal topology and does not scale computationally the way per-router path-vector state does; BGP's path-vector approach deliberately trades full-topology awareness for policy opacity and inter-AS trust minimization.

ALT-2 — Centralized SDN route-controller (single decision point).

        [Central Controller]      Controller computes all routes;
         /       |        \       routers are dumb forwarders that
      [R1]      [R2]      [R3]    just install what they're told.

Regime where it wins: a single-operator data-center or WAN fabric under one administrative domain where global optimization (e.g., traffic-engineering-optimal routing) matters more than per-router autonomy — exactly the RouteFlow/SDX research line and modern SD-WAN overlay controllers. Real system: Google's B4/Espresso-style SDN-controlled WAN routing. Why rejected here: this project's scope (§1) is a general-purpose BGP-4 router interoperating with arbitrary external ASes that do not share a controller — a centralized controller has no jurisdiction over a competitor's AS, so BGP's per-router distributed decision-making is not a design choice this project can opt out of at the inter-domain boundary, even though it remains valid within a single operator's own network.

ALT-3 — Full iBGP mesh, no route reflection, ever.

   [R1]--[R2]      Every iBGP router peers directly with every
    | \  / |       other — O(n²) sessions, no reflector needed,
   [R3]--[R4]      full "free choice" property preserved (§19).

Regime where it wins: small ASes (roughly ≤ 20-30 routers) where O(n²) session count is operationally trivial and the correctness guarantee of full free-choice best-path selection (no reflector-induced hiding, §19, MM5) is worth the mesh-management overhead. Real system: this is the default, unmodified iBGP topology many small enterprise/campus networks run today. Why rejected as this project's only mode: at transit-AS scale (hundreds of routers, §4), O(n²) session management becomes the dominant operational cost — this is precisely the motivation for building route reflection (§19) as a first-class phase rather than treating full-mesh as sufficient.

ALT-4 — Distance-vector (RIP-style) inter-domain routing.

   [R1] --3--> [R2] --2--> [R3]     Routers exchange only a metric,
                                     not a path; count-to-infinity
                                     loops require split-horizon +
                                     poison-reverse workarounds.

Regime where it wins: small, low-churn networks where path information's memory/bandwidth cost isn't justified — classic RIP deployments. Real system: RIP itself, and its descendants in small enterprise networks. Why rejected here: distance-vector's count-to-infinity problem is exactly the failure mode path-vector's AS_PATH (I1, MM3) was invented to structurally prevent at internet scale — an inter-domain protocol spanning thousands of independently operated ASes with no shared trust cannot rely on split-horizon/ poison-reverse heuristics that only bound, rather than eliminate, the loop risk.

39. Glossary

  • Adj-RIB-In: per-peer, per-(AFI,SAFI) table of received routes, pre-import-policy (§8.3).
  • Adj-RIB-Out: per-peer, per-(AFI,SAFI) table of routes to advertise, post-export-policy (§8.3).
  • AFI: Address Family Identifier (e.g., 1 = IPv4, 2 = IPv6, RFC 4760).
  • AS: Autonomous System, an independently routed network under one administrative control.
  • AS_PATH: the path-vector attribute listing every AS a route has traversed (§8.2).
  • AS_SET: an unordered AS group, produced by route aggregation; counts as length 1 in best-path (I3).
  • AS_SEQUENCE: an ordered AS list, the common case for AS_PATH segments.
  • AS_CONFED_SEQUENCE / AS_CONFED_SET: confederation-internal AS_PATH segment types (RFC 5065).
  • BFD: Bidirectional Forwarding Detection, a sub-second liveness protocol (hook only, §39 deferred full impl).
  • BGP: Border Gateway Protocol, the inter-domain path-vector routing protocol (RFC 4271).
  • BGPsec: RFC 8205's cryptographic AS_PATH signing extension (deferred, §38).
  • CLUSTER_LIST: route-reflector loop-prevention attribute (§8.2, I8).
  • COMMUNITY: a 32-bit policy tag attribute (RFC 1997, §8.2).
  • Confederation: an AS split into member sub-ASes appearing as one AS externally (RFC 5065).
  • eBGP: External BGP, a session between routers in different ASes.
  • Extended Community: a 64-bit typed policy tag (RFC 4360, §38 deferred usage).
  • FIB: Forwarding Information Base, the kernel/hardware forwarding table (§23).
  • Flowspec: BGP-carried traffic-filtering rules (RFC 5575, deferred §38).
  • FSM: Finite State Machine, RFC 4271 §8's six-state session lifecycle (§8.1, §14).
  • GR: Graceful Restart, RFC 4724's session-loss churn-avoidance mechanism (§20).
  • GTSM: Generalized TTL Security Mechanism, an off-path attack defense (RFC 5082, §14).
  • Hold Timer: the negotiated session-liveness timeout; expiry transitions the FSM to Idle (§8.1).
  • iBGP: Internal BGP, a session between routers within the same AS.
  • IGP: Interior Gateway Protocol (OSPF, IS-IS); supplies the IGP-cost tie-breaker input (§8.4).
  • Keepalive: the periodic liveness message resetting the peer's Hold Timer (§8.1).
  • Large Community: a 96-bit policy tag solving the 16-bit-AS Community limit (RFC 8092).
  • LOCAL_PREF: an iBGP-only per-route preference attribute; higher wins in best-path (§8.2, §8.4).
  • Loc-RIB: the per-(AFI,SAFI) authoritative post-import-policy, post-best-path route table (§8.3).
  • MED: Multi-Exit Discriminator, an inter-AS-boundary tie-breaker scoped to same-upstream-AS (§8.4, I13).
  • MP-BGP: Multiprotocol BGP, RFC 4760's generalization of BGP to any (AFI,SAFI) family.
  • NLRI: Network Layer Reachability Information, the prefix list carried in an UPDATE (§8.2).
  • NEXT_HOP: the egress address attribute for a route (§8.2; IPv6/other families use MP_REACH_NLRI's next-hop).
  • NOTIFICATION: the BGP message type signaling a session-terminating error (§8.2, §11).
  • OPEN: the BGP session-initiation message carrying capabilities (§8.2, §11).
  • ORIGIN: the route-origin-type attribute (IGP/EGP/Incomplete, §8.2, §8.4).
  • ORIGINATOR_ID: the route-reflector-injected attribute identifying the originating router (§8.2, I7, I8).
  • Path attribute: any of the RFC 4271 §4.3 route-metadata fields carried in an UPDATE (§8.2).
  • Patricia trie: the radix-tree structure used for longest-prefix-match RIB lookup (ADR-06, §11).
  • Prefix: an IP address plus a mask length, the unit of routing (§11).
  • RIB: Routing Information Base, the general term covering Adj-RIB-In/Loc-RIB/Adj-RIB-Out (§8.3).
  • Route Reflector (RR): an iBGP router that relaxes the no-iBGP-to-iBGP-reflection rule for its clients (§19).
  • Route-flap damping (RFD): RFC 2439's penalty-based route-oscillation suppression mechanism (§21).
  • RPKI: Resource Public Key Infrastructure, the cryptographic basis for origin validation (RFC 6480, §22).
  • RTR: RPKI-to-Router protocol, the cache-distribution protocol this router consumes as a client (RFC 8210, §22).
  • SAFI: Subsequent Address Family Identifier, refines an AFI to a specific route type (e.g., unicast vs VPN).
  • Split-horizon: the rule that a route is never re-advertised to the peer it was learned from (§8.3, I6).
  • Stable Paths Problem: Griffin & Wilfong's formalization of when BGP-like policy configurations converge (§5, §36).
  • TCP-MD5: the TCP option authenticating BGP sessions via a shared key (RFC 2385, §14).
  • UPDATE: the BGP message type carrying route announcements and withdrawals (§8.2, §11).
