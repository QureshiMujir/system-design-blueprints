Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If a court order compels the owner to unlock the vault (T3, §24), does P10's threshold custody actually protect anything the owner personally holds all M shares of? (§24, §14)
  2. Does the pointer-register LWW merge (P8, §18) ever silently discard a concurrent write's intended meaning, even though the losing ObjectRef remains reachable — and would a user notice? (P8, §18)
  3. Why does twinadapt enforce scope at the retrieval layer instead of trusting the capability check alone (§20) — what specific I13 failure mode does the retrieval-layer redundancy close that verification alone does not? (I13, §20)
  4. Is the 25-year format-readability commitment (P4, §22) actually falsifiable before 25 years pass, or is it an unverifiable promise until it's tested by time? (P4, §22)
  5. Does federating relay traffic across operators (§21, §31) meaningfully reduce T7 risk if all federated relays are hosted by the same cloud provider's infrastructure? (T7, §31)
  6. What happens to a ConsentGrant's attenuation chain (P6, §20) if the root Capability it descends from is itself revoked mid-inference — does I4 propagate through the proof chain or only check the leaf? (I4, §20)
  7. Why is Argon2id's memory-hardness (M4, §34) sufficient against a well-funded adversary but not against a nation-state with custom memory-dense ASICs — where does the security margin actually come from? (M4, §34)
  8. Does the 90-day offline-tolerance ceiling (§4) interact badly with the recovery-share collusion window (T9, §34) — does a long-offline device's stale revocation set create a window an attacker could exploit? (§4, T9)
  9. Is the canary-object defense against prompt-injection exfiltration (§20, T11) itself detectable and avoidable by a sufficiently capable adversarial model that infers which objects are canaries from their access pattern? (T11, §20)
  10. Why does migration (§22) get a sanctioned exception to P3's immutability while nothing else does — is the exception narrow enough that it can't be abused as a precedent for other "just this once" mutability requests? (P3, §22)
  11. Does the dual-format read path (§22) introduce its own attack surface — could a malicious sync peer force a device to permanently prefer the old, weaker format during the Migrating window? (§22, T5)
  12. If redb (ADR-04) is abandoned upstream in 15 years, does the archived reference decoder (§22, P4) actually decouple from it, or only from its API, not its on-disk assumptions? (ADR-04, §22)
  13. Is the 5,000 verifications/s target (M12, §34) achievable without a shared issuer-key cache becoming a new single point of correctness — what happens to M12's throughput the instant the cache is cold? (M12, §17)
  14. Does the Shamir threshold's information-theoretic guarantee (P10, I5) survive a side-channel where the share-issuance process itself (timing, ordering) leaks which shares were issued to whom? (P10, §24)
  15. Why is capability caveat monotonicity (I13) checked at verification and not solely at issuance — what specific replay or collusion scenario (§24) does verification-time enforcement close that issuance-time enforcement alone would miss?
  16. Does the relay's connector-trigger scheduling (§21) leak information about a user's connector configuration (which sources exist) even though it never holds connector credentials? (§21, T7)
  17. If a twin's local inference model itself is later found to memorize training data, does P14's "consumer, not co-owner" framing (§20) actually prevent a distinct exfiltration vector unrelated to prompt injection? (P14, T11)
  18. Is the 32-device sync-fanout ceiling (§4, §31) a genuine architectural limit of the CRDT/capability design, or an arbitrary number that could be revisited without touching any invariant? (§4, §31)

32. Mental Models & First Principles

MM1. Sovereignty is a key-custody problem wearing a product costume. Predicts: evaluate any feature proposal by "who can decrypt," never by UI framing. Bug class without it: server-side convenience features (search, dedup) silently reintroducing platform custody. Resolves via P1, T1 (§24).

MM2. A capability is a fact about the past, not the present — validity must be re-checked, never cached as settled. Predicts revocation must be enforced at use, not trusted from an issuance-time cache. Bug class without it: stale-cache authorization bugs indistinguishable from "was never enforced." Resolves via I4, §17.

MM3. Content addressing turns "delete" into a policy question, not a mechanism. Predicts storage grows monotonically absent GC; "delete" always means tombstone-then-eventual-key-destruction. Bug class without it: treating a tombstone as a physical delete, breaking DAG references. Resolves via P3, §13.

MM4. The twin is a bounded reader, never a co-owner. Predicts any design granting the model standing access instead of per-request scoped access reproduces platform-AI-memory failures. Bug class without it: consent-scope creep, prompt-injection exfiltration. Resolves via P6, P14, §20.

MM5. An untrusted relay is a scheduling and store-and-forward problem, never a trust problem. Predicts relay compromise manifests only as denial-of-service. Bug class without it: any code path silently requiring relay cooperation for confidentiality. Resolves via P1, §21.

MM6. Format durability is a promise that must be verifiable independent of any future implementation. Predicts the archived reference decoder must never silently depend on live crate versions. Bug class without it: format lock-in disguised as "just re-run the migration tool," except the tool itself has bit-rotted. Resolves via P4, §22.

MM7. Recovery and compromise are the same math, pointed in opposite directions. Predicts the k-of-n threshold analysis that protects against share loss also bounds collusion risk (§34). Bug class without it: choosing a threshold for availability alone while ignoring the collusion tradeoff. Resolves via P10, T9 (§24).

MM8. Crypto agility is a header field, not a rewrite. Predicts algorithm migration is always additive (a new algo_id), never a flag day. Bug class without it: hardcoded-algorithm assumptions that make P4's 25-year commitment undeliverable once that algorithm is deprecated. Resolves via P12, §22.

Required reading (§5)

Books

  • Ferguson, Schneier, Kohno — Cryptography Engineering — ch. 4 (Block Ciphers), ch. 8 (Key Negotiation) — extract: AEAD mode-selection reasoning, key-negotiation hygiene. Applied in §9 (ADR-08, ADR-10).
  • Kleppmann — Designing Data-Intensive Applications — ch. 5 (Replication), ch. 9 (Consistency and Consensus) — extract: replica-convergence tradeoffs, CRDT vs. consensus. Applied in Phase 6 (§18).
  • Anderson — Security Engineering (3rd ed.) — ch. 6 (Access Control), ch. 21 (Network Attack and Defense) — extract: capability vs. ACL failure modes, revocation-propagation design. Applied in Phase 5 (§17), Phase 7 (§19).
  • Van Steen & Tanenbaum — Distributed Systems (3rd ed., 2017) — ch. 7 (Consistency and Replication), ch. 9 (Security) — extract: capability-based access-control models, Byzantine assumptions for an untrusted relay. Applied in §7, §9.
  • Okasaki — Purely Functional Data Structures — ch. 2–3 (persistence and amortization) — extract: immutable, structure-sharing data-structure discipline. Applied in §11, Phase 1 (§13).
  • Boneh & Shoup — A Graduate Course in Applied Cryptography — the secret-sharing chapter, the key-derivation chapter — extract: threshold-scheme soundness proofs, KDF composition safety. Applied in Phase 2 (§14), §8.

Papers

  • Shamir, 1979, CACM, "How to Share a Secret" — threshold secret sharing — keyring recovery shares. Applied in Phase 2 (§14).
  • Shapiro, Preguiça, Baquero, Zawirski, 2011, INRIA RR-7506, "Conflict-free Replicated Data Types" — CRDT convergence proofs — syncd merge. Applied in Phase 6 (§18).
  • Marlinspike & Perrin, Signal docs, "The X3DH Key Agreement Protocol" — asynchronous key agreement — device-pairing sessions. Applied in Phase 2 (§14), Phase 6 (§18).
  • Marlinspike & Perrin, Signal docs, "The Double Ratchet Algorithm" — forward-secret session ratcheting — syncd/twinadapt session keys. Applied in §18, §20.
  • Birgisson, Politz, Clarkson, Chong, Erlingsson, Taly, 2014, NDSS, "Macaroons: Cookies with Contextual Caveats" — attenuated bearer capabilities — capd caveat design. Applied in Phase 5 (§17).
  • Benet, 2014, "IPFS: Content Addressed, Versioned, P2P File System" — content addressing + Merkle-DAG — objstore addressing model. Applied in §8, Phase 1 (§13).
  • Wilcox-O'Hearn & Warner, 2008, StorageSS, "Tahoe-LAFS: The Least-Authority Filesystem" — capability-based encrypted storage — objstore/capd design precedent. Applied in §8, §33.
  • Biryukov, Dinu, Khovratovich, 2016, "Argon2: The Memory-Hard Function for Password Hashing and Proof-of-Work" — memory-hard KDF tuning — keyring master-key derivation. Applied in Phase 2 (§14), §4.
  • Berners-Lee et al., Solid protocol specification and papers — decentralized personal-data pods — relay/objstore custody precedent. Applied in §33.

Reference Implementations

  • Solid Community Server — repo solid/community-server — dirs src/authorization/, src/storage/ — lesson: WAC/ACP-style authorization layered over an LDP store — pitfall: ACL-shaped authorization does not attenuate (contrast P2). Applied in §9 (ADR-13), §33.
  • Bluesky atproto monorepo, PDS package — repo bluesky-social/atproto — dirs packages/pds/src/repo/, packages/pds/src/account-manager/ — lesson: content-addressed per-user repo with signed commits — pitfall: single-operator custody of the PDS key defeats self-sovereignty unless self-hosted. Applied in §33.
  • Perkeep (formerly Camlistore) — repo perkeep/perkeep — dirs pkg/blob/, pkg/schema/ — lesson: content-addressed personal storage with a generic schema layer — pitfall: search index tightly coupled to one deployment topology. Applied in §8, §33.
  • Tahoe-LAFS — repo tahoe-lafs/tahoe-lafs — dirs src/allmydata/mutable/, src/allmydata/immutable/ — lesson: capability-URIs as the sole access path to encrypted shares — pitfall: capability leakage via any logging path defeats the whole model. Applied in §7 (I3), §33.
  • Automerge — repo automerge/automerge — dirs rust/automerge/src/op_set/, rust/automerge/src/sync/ — lesson: op-based CRDT with a compact binary sync protocol — pitfall: unbounded op-log growth without periodic compaction (FM-3). Applied in Phase 6 (§18).
  • age — repo FiloSottile/age — dirs age/, plugin.go — lesson: small, auditable file-encryption format with a clean recipient-stanza design — pitfall: no built-in key-rotation story, must be layered externally. Applied in §8, §9 (ADR-11).

Glossary (§38) · 47 terms · site-wide glossary

Vault
the complete, per-owner encrypted personal datastore (objects, index, keys, capability log, audit log).
Object ref (ObjectRef)
a 32-byte BLAKE3 digest of ciphertext, the sole address of a stored object (I2, P3).
Content address
an identifier derived from content itself (here, ciphertext), not chosen by the writer.
AEAD
authenticated encryption with associated data; here ChaCha20-Poly1305 or XChaCha20-Poly1305 (ADR-08).
Nonce
a per-encryption unique value; reuse under the same key breaks AEAD confidentiality (I6).
AAD
associated authenticated data; unencrypted but integrity-protected header fields (§8).
HKDF
HMAC-based key derivation function (RFC 5869); expands a master secret into per-purpose keys (§8).
Derivation path
the info-string identifying a specific HKDF expansion step (§8, §11).
Master key (MK)
the L0 root key derived from a passphrase or HSM-wrapped seed (§8).
Key wrapping
encrypting one key under another for storage (ADR-11).
Shamir share (RecoveryShare)
one polynomial-evaluation fragment of a Shamir secret-sharing split (P10, §11).
Threshold (M-of-N)
the minimum share count required to reconstruct a secret.
Capability
a signed, attenuable, time-bounded bearer credential granting scoped access (P2, §11).
Caveat
a restriction embedded in a capability, narrowing its scope (§8, §11).
Attenuation
deriving a narrower child capability from a parent, never broadening (P2, I13).
UCAN
User Controlled Authorization Networks, the capability token format used (ADR-12).
DID
Decentralized Identifier, the identity-anchor format for issuer/audience fields (ADR-13).
Ingest cursor (IngestCursor)
a per-source, monotonically advancing connector fetch position (I8, §11).
CRDT
Conflict-free Replicated Data Type; a merge structure with mathematically guaranteed convergence (§18).
Tombstone
a logical-delete marker superseding an object without physically erasing it (P3).
Twin adapter (twinadapt)
the in-process module running model inference over vault contents under consent (P14, §20).
Consent grant (ConsentGrant)
a Capability-shaped, revocable authorization for twin inference (P6, §11).
Audit entry (AuditEntry)
one hash-chained, append-only record of a read or inference event (I10, §11).
Relay
the untrusted store-and-forward hop between devices, ciphertext-only (P1, §21).
Merkle-DAG
a directed acyclic graph of content-addressed nodes, each referencing children by hash (§8).
Pointer register
an LWW, vector-clock-stamped mapping from a logical name to its current ObjectRef (P8, §8).
Vector clock
a per-replica counter set used to order concurrent events without a shared clock.
Connector
a WASM-sandboxed module implementing fetch(cursor) against a third-party data source (§8).
ConnectorSpec
the manifest declaring a connector's source, version, and required capabilities (§11).
Revocation set
the CRDT-replicated set of invalidated capabilities, checked at every verification (I4).
Argon2id
a memory-hard password-hashing/KDF algorithm (RFC 9106) used for master-key derivation (ADR-09).
X3DH
the Extended Triple Diffie-Hellman asynchronous key-agreement protocol (Signal docs), used for device pairing (§14).
Double Ratchet
a forward-secret session-key ratcheting algorithm (Signal docs), used for twin remote-inference sessions (§20).
Canary object
a decoy ObjectRef seeded to detect illegitimate retrieval or exfiltration (§20).
Verifiable Credential (VC)
a W3C-standardized, portable, signed claim format, used to export consent state (ADR-14, §20).
Format version
the byte tag identifying an EncryptedObject's on-disk/wire layout revision (I14).
Crypto agility
the design property that algorithm choice travels with data rather than being hardcoded (P12).
Reference decoder
a frozen, dependency-vendored implementation preserved for long-term format readability (P4, §22).
Migration
the sanctioned, checkpointed re-encryption of a vault from one format/algorithm to another (§22).
Lifecycle state
one of a vault's named operating modes: Provisioning, Active, Locked, Recovery, Migrating, Archived, Destroyed (§8).
Conformance suite
the CI-blocking assembly of the invariant simulator, fuzz corpora, KAT vectors, and performance gate (§23).
KAT (Known-Answer Test)
a fixed input/output vector pair used to verify a cryptographic primitive's correctness against a published standard.
Soak test
an extended-duration run (here, 72 hours) verifying stability and bounded resource growth under sustained load (§23).
SBOM
Software Bill of Materials, an inventory of build dependencies for supply-chain auditability (ADR-23).
Padding bucket
a fixed-size bin objects are rounded up into before transmission, to blur size-based metadata leakage (§21).
Blast radius
the scope of compromise or failure a single key, device, or credential leak can cause (P5).
Fail-closed
the design discipline of rejecting on ambiguity or unrecognized input, never default-permitting (I13).
