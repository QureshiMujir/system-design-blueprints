Project Number: 17

Project Name: Aeon

1. Goal & Scope

Aeon is a self-sovereign personal-data vault: an end-to-end-encrypted, content-addressed datastore that a user's own devices operate directly, paired with connector contracts that ingest data from third-party services, a capability-based authorization layer that lets applications query the vault without ever holding the underlying ciphertext or plaintext, and a twin adapter that runs local or remote model inference over vault contents strictly under an explicit, revocable consent grant. The system's defining property: no operator of shared infrastructure (relay, connector host, model provider) ever holds a decryption key (P1) or an implicit standing grant (P2) — every access is a capability, every capability expires, every read is audited (I3).

Phase-0 deliverable (module boundary, one module = one compiled crate):

  1. vaultd — local vault daemon: process supervising key state, exposing the local RPC surface to the SDK.
  2. keyring — key manager: master-key custody, HKDF derivation, recovery-share issuance/reconstruction (Shamir).
  3. objstore — content-addressed encrypted object store: append-only object writes, retrieval by ObjectRef.
  4. indexer — index + query engine: maintains queryable metadata over objstore without ever persisting plaintext outside the client boundary.
  5. connectors — connector runtime: sandboxed ingest adapters (WASM) with cursor-based incremental fetch.
  6. capd — capability issuer + verifier: issues, attenuates, and verifies UCAN-style capability tokens.
  7. syncd — sync/replication engine: multi-device CRDT merge over metadata, pointer-register merge over binary objects.
  8. twinadapt — twin adapter: consent-gated inference bridge (local or remote model backend).
  9. auditlog — hash-chained, append-only log of every capability check and every consent-gated read.
  10. sdk — client SDK: language bindings (Rust core, WASM/TS bindings) for app integration.
  11. relay — optional hosted relay: zero-knowledge store-and-forward for offline-device sync and connector scheduling; never holds a key.

System boundaries. Provides: encrypted storage, key custody, capability-scoped queries, connector ingestion, consent-gated inference, multi-device sync, audit trail, format-migration tooling. Delegates: model weights/training (external providers behind twinadapt), identity-provider federation beyond DID resolution, the UI/app layer (consumed via sdk). Does NOT provide: a general-purpose object store (schema is personal-data-shaped, not S3-compatible), a public social graph or discovery layer, server-side plaintext search (search runs client-side or inside twinadapt's consent boundary only).

Non-goals: multi-tenant organizational vaults (PhaseDeferred("§1")), a blockchain-anchored public index (rejected — see Alternative Architectures Roads Not Taken), a marketplace for third-party connectors at v1 (PhaseDeferred("§1")), server-side plaintext full-text search, hardware-security-module custody for individual users (PhaseDeferred("§1")).

Deployment model: local-first — the vault is fully functional on one device with vaultd + objstore + keyring + indexer running locally, no network required. A self-hosted relay is optional, used only for multi-device sync and connector scheduling while devices are not directly reachable. A hosted relay (Aeon-operated or third-party) is supported identically because relay is zero-knowledge (P1) — trust in the operator reduces to availability, never confidentiality.

Users/operators: end users (own one or more vaults across devices), connector authors (third-party or self-written WASM modules), relay operators (self-hosted or commercial), twin-adapter model providers (local runtime or remote inference API, gated by ConsentGrant).

Later phases unlock: Phase 4 (§16) a general connector ecosystem; Phase 6 (§18) real multi-device continuity; Phase 8 (§20) the portable AI twin itself; Phase 9 (§21) hosted relay for users without always-on infrastructure; Phase 10 (§22) the multi-decade durability guarantee.

Language: Rust, workspace of the eleven crates above. Rationale: constant-time crypto primitives with auditable dependency provenance (ring, chacha20poly1305, argon2, hkdf crates), no GC pause inside the capability-verification hot path (M6), a single codebase cross-compiles to WASM for sdk bindings and for sandboxing connectors (ADR-17) under wasmtime. Rejected languages: Go — GC pauses complicate constant-time guarantees and its crypto ecosystem is weaker for AEAD/HKDF composition; Node/TypeScript — acceptable only for SDK bindings, unsuitable for the core crypto boundary (larger dependency supply chain, no memory-safety-without-GC); Swift/Kotlin — would fragment core vault logic into two native rewrites, doubling audit surface against P1's guarantee.

Prerequisites: applied cryptography (AEAD, KDFs, key hierarchies), CRDT theory (Shapiro et al. 2011), capability-based security (macaroons, UCAN, SPKI/SDSI), content-addressed storage (IPFS/IPLD), distributed-systems failure modes (partial writes, clock skew, replay).

Timeline: Phase 0 in 3 weeks; full system (Phase 0 through Phase 11) in 22 months.

2. Why Build This

  • Key-custody-as-product: sovereignty is not a UI theme, it is a key-management architecture (MM1).
  • Capability-based authorization is the only access-control model that survives a compromised or malicious intermediary (relay, connector host) — ACLs cannot (P2, T1).
  • Content addressing + Merkle-DAG (IPFS/IPLD, Benet 2014) generalizes to any personal-data shape without a bespoke schema per data type.
  • CRDT merge (Shapiro et al. 2011; Automerge) is the only offline-first multi-writer model that avoids centralized lock-step consensus.
  • Consent-as-capability unifies "app access" and "AI access" under one revocable, auditable primitive — the twin adapter is not a special case (P6).
  • Format-durability engineering (multi-decade readability) is a discipline distinct from storage redundancy — most systems conflate the two and fail the former (P4).
  • Real incidents ground the threat model: the 2017 Equifax breach (centralized custody of derived identity data; one compromise cascades system-wide) and the 2018 Cambridge Analytica data-custody failure (implicit, unrevoked third-party access framed as a product feature) are the two failure patterns Aeon is structurally built to prevent (P1, P2, T4).
  • Cross-links: objstore is IPFS/IPLD-shaped; capd is UCAN/macaroon-shaped; syncd is Automerge-shaped; keyring is Tahoe-LAFS/Shamir-shaped; relay is Solid-pod/Bluesky-PDS-shaped, minus their custody assumptions.

What Mastery Looks Like

  • Derive a key hierarchy where compromising one collection key never exposes another (Phase 2, §14).
  • Design a capability format whose caveats attenuate monotonically and whose revocation cannot be replayed (Phase 5, §17).
  • Reason about CRDT convergence for structured data vs. content-addressed immutability for binary blobs, and know when each applies (Phase 6, §18).
  • Build a connector contract that is idempotent under replay and resilient to cursor drift (Phase 4, §16).
  • Explain why a consent grant is structurally a capability, not a separate permission system (Phase 8, §20).
  • Specify a byte format and justify a 25-year readability commitment without assuming any one vendor's SDK survives (Phase 10, §22).
  • Diagnose nonce reuse under a shared AEAD key: why it is catastrophic, how it is detected operationally, and how key rotation with re-wrap prevents recurrence (Phase 1 §13, Phase 11 §23).
  • Run a conformance suite that gates a distributed cryptographic system's correctness, not merely its features (Phase 11, §23).

vaultd — local daemon process boundary; every other module runs inside it as a library or a sandboxed sub-process (connectors); the only network-crossing module is syncd via relay.

keyring — holds the key hierarchy in memory only while unlocked; persists only wrapped keys and recovery-share metadata; never exposes raw key material across the RPC boundary (I1).

objstore — append-only encrypted object store; objects addressed by ObjectRef (ciphertext hash); writes are immutable, updates are new objects plus a tombstone (P3, I2).

indexer — maintains query structures (inverted index, metadata B-tree) over decrypted-in-memory metadata; never persists plaintext to disk; rebuilds from objstore + keyring on demand.

connectors — WASM-sandboxed ingest adapters; each holds only the capability it needs (least privilege) and a persisted IngestCursor; network egress mediated by a host-provided fetch shim, rate-limited per ADR-17.

capd — issues and verifies UCAN-style Capability tokens; verification is local (no network round trip) for cached issuer keys; consults the revocation set maintained jointly by auditlog and syncd.

syncd — merges CRDT metadata ops (Automerge) and pointer-register updates across devices; the only module that talks to relay; transport is QUIC, payload is always ciphertext.

twinadapt — bridges a TwinRequest to a local or remote model backend; every invocation requires a live ConsentGrant scoped to specific collections; queries objstore/indexer through the same capability path as any other client (P14).

auditlog — append-only, hash-chained log of every capability check (I3) and consent-gated read; the forensic backbone for the Threat Model (§24) and Failure Modes (§25).

sdk — the only supported integration surface for apps; wraps local RPC to vaultd; never embeds keys.

relay — optional store-and-forward for offline multi-device sync and connector-scheduling triggers; sees ciphertext and capability tokens only, never plaintext or raw keys (P1); a compromised relay can deny service, never confidentiality.

6. Design Principles

P1. The server never holds a decryption key. Relay and any hosted component operate on ciphertext and capability tokens only. Tradeoff: no server-side plaintext search or cross-user dedup. Operational implication: relay compromise is a denial-of-service risk, not a confidentiality risk. Violating it: any server-side plaintext cache collapses the sovereignty guarantee to "trust the operator" (T1).

P2. Every grant is a capability with an expiry, never an ACL row. Access is a signed, attenuable, time-bounded Capability, not a mutable row keyed by identity. Tradeoff: no instant global-permission audit via a single table scan; must walk issuance chains. Operational implication: revocation is set-membership, not row deletion. Violating it: ACL rows silently outlive the intent that created them (the Cambridge Analytica pattern).

P3. Content addressing implies immutability. ObjectRef is a hash of ciphertext; there is no in-place mutation. Tradeoff: "delete" is logical (tombstone) unless followed by key destruction. Operational implication: storage grows monotonically absent GC. Violating it: mutable objects break every downstream cache and sync assumption keyed on ObjectRef stability.

P4. Format readability outlives the vendor. The on-disk/on-wire format is documented independently of any implementation, with a frozen version byte (I14) and an archived reference decoder. Tradeoff: format changes require an explicit migration phase (§22), never a silent schema drift. Operational implication: a user can recover data with only the spec, 25 years on. Violating it: proprietary format lock-in reproduces exactly the platform-custody failure Aeon exists to prevent.

P5. The key hierarchy separates blast radius. The master key never encrypts data directly; HKDF-derived per-collection and per-object keys bound compromise to one collection (§8). Tradeoff: more keys to rotate on compromise. Operational implication: rotation is scoped, not vault-wide. Violating it: one leaked object key exposing a sibling collection means the hierarchy is flat in practice.

P6. Consent is a first-class object, not implicit trust in an adapter. ConsentGrant is issued, scoped, and revocable exactly like Capability (P2's shape reused). Tradeoff: every twin invocation pays a verification cost (near M6). Operational implication: consent scope is auditable identically to any other capability check. Violating it: an adapter with standing, unscoped access reproduces the platform-AI-memory failure mode this system targets.

P7. Local-first: writes commit locally before sync. vaultd never blocks a local write on network availability. Tradeoff: eventual, not immediate, cross-device consistency. Operational implication: conflict resolution is a CRDT-merge concern (P8), not a write-path concern. Violating it: any write path gated on relay reachability defeats the offline-tolerance constraint (§4).

P8. CRDT merge only where join semantics are well-defined; otherwise last-writer-wins with a vector-clock stamp. Structured metadata merges via Automerge; binary objects merge via a pointer-register (LWW) over immutable ObjectRefs, never byte-level CRDT over ciphertext. Tradeoff: LWW can silently drop a concurrent write's content (only the pointer wins) — mitigated by keeping the losing ObjectRef reachable (P3) for reconciliation. Operational implication: syncd needs two merge code paths, not one. Violating it: CRDT merge over encrypted binary payloads is either impossible (ciphertext has no semantic join) or a confidentiality bug (join logic needs plaintext).

P9. Connectors are idempotent under replay. A connector's fetch(cursor) may be invoked twice for the same cursor without duplicating ingested objects, because ingestion is content-addressed (P3) — replay produces the same ObjectRef. Tradeoff: connectors cannot express "always create a new object" semantics; updates must be modeled explicitly. Operational implication: cursor-drift bugs (FM-4) are contained to duplicate fetch attempts, not duplicate data. Violating it: a connector that content-addresses over an include-timestamp field defeats idempotency.

P10. Recovery shares below threshold reconstruct nothing. Shamir (1979): any M-1 of N shares carry zero information-theoretic content about the secret. Tradeoff: losing N-M+1 shares permanently loses the vault. Operational implication: share-custody policy matters as much as the threshold math. Violating it: a "helper" scheme that leaks partial key material under fewer than M shares (e.g. naive XOR splitting) is not secret sharing at all.

P11. Every read is capability-checked and audit-logged before plaintext leaves the client boundary. No read path bypasses capd + auditlog. Tradeoff: every read pays verification latency (M6). Operational implication: the audit log is a complete read ledger, usable for forensics. Violating it: a "fast path" read that skips the check is indistinguishable, post-breach, from a capability system that was never enforced.

P12. Crypto agility: algorithm IDs travel with ciphertext, never assumed. EncryptedObject.algo_id (§8) is authoritative; no code path assumes a fixed AEAD algorithm. Tradeoff: verifier code branches on algo_id, a slightly larger attack surface than one hardcoded algorithm. Operational implication: algorithm migration is additive, never a flag day. Violating it: a hardcoded algorithm assumption makes P4's 25-year commitment undeliverable once that algorithm is deprecated.

P13. Revocation propagates faster than the typical capability TTL, or synchronously at reconnect. Online devices see revocation within the M7 bound; offline devices enforce it at the reconnect handshake regardless of how long they were offline (§4). Tradeoff: reconnect handshake pays a revocation-set fetch. Operational implication: no capability's effective lifetime is ever "offline duration," only "TTL or revocation, whichever is sooner." Violating it: trusting a cached, unrevoked capability after reconnecting reopens exactly the replay window I4 exists to close.

P14. The twin adapter is a consumer of the vault, not a co-owner of keys. twinadapt never receives raw key material; it receives decrypted query results scoped by a ConsentGrant, inside the same process boundary as vaultd (§3). Tradeoff: remote-model backends never see plaintext unless the user explicitly consents per-request via a distinct, narrower caveat. Operational implication: local inference is the default trust boundary; remote inference is opt-in, never silent. Violating it: an adapter that caches keys "for performance" becomes a second keyring, doubling P5's blast-radius surface.

Content Address & Merkle-DAG

ObjectRef = BLAKE3 digest of the ciphertext, never the plaintext (avoids confirmation-of-file attacks against the storage layer, T6). Objects with a parent_ref field in aad form a Merkle-DAG (IPFS/IPLD model, Benet 2014); collections are DAG roots whose children are content-addressed leaves plus a CRDT-managed index of live pointers (P8). Client-side plaintext-hash deduplication is optional and never surfaces to objstore or relay.

Connector Contract

ConnectorSpec declares source_id, spec_version, capabilities_required (a caveat set, least privilege), and rate_limit. The ingest interface is conceptually fetch(cursor: IngestCursor) -> (records, next_cursor); idempotency follows from content addressing (P9) — replaying the same cursor re-derives identical ObjectRefs, so duplicate fetch attempts never duplicate stored data. Cursor advancement is monotonic per source_id (I8); rate limiting is a token bucket enforced by the WASM host (ADR-17).

Capability Token Format

Fields: issuer (DID), audience (DID), exp, nbf, caveats: Vec<Caveat>, proof (optional parent Capability, forming an attenuation chain), sig. Verification steps: (1) parse and schema-check; (2) verify the signature chain to a trusted issuer or root; (3) check exp/nbf against a skew-tolerant clock (ADR-24); (4) check caveat monotonicity against the parent proof chain; (5) check the revocation set (I4); (6) match requested resource+action against caveats; (7) audit-log the check (I3).

Sync / CRDT Merge Semantics

Structured metadata (contacts, notes, index annotations) merges via an op-based CRDT (Shapiro et al. 2011; Automerge). Binary objects never merge at the byte level — a CRDT-managed pointer register (LWW, vector-clock-stamped) tracks which ObjectRef is "current" for a logical name; the losing write's ObjectRef remains reachable under P3 for manual reconciliation (P8).

Worked Example

Connector photos-v1 calls fetch(cursor), returning 250 records; each is content-addressed as an ObjectRef and wrapped under the photos collection key CK_photos (per the derivation table above). IngestCursor.seq advances by 250. indexer updates the inverted index with EXIF-derived metadata only, held decrypted-in-memory, never persisted as plaintext.

Malformed-Input Examples

  • EncryptedObject with header_len exceeding the remaining buffer → reject before touching key material (VaultError decode path).
  • Capability with an unrecognized Caveat variant → reject closed per I13 (unknown caveats never default-permit).
  • IngestCursor token replayed against a mismatched source_id → reject per I8's per-source monotonicity check.

Failure-Path Example

relay unreachable mid-sync: syncd continues applying local ops (P7), queues outbound SyncOps, retries with backoff bounded by the M5 bandwidth budget. On reconnect, MergeResult.conflicts_resolved reports any concurrent pointer-register updates that raced during the outage.

/// Ownership: vaultd-owned, immutable after creation.
/// Mutation: none (new VaultId = new vault).
/// Concurrency: Copy, Send, Sync.
/// Persistence: stored in vault manifest header.
/// Serialization: CBOR, 16-byte form.
/// Compatibility: format-version-independent (I14 covers payload, not this).
pub struct VaultId([u8; 16]);

/// Ownership: objstore-owned; derived, never chosen by caller.
/// Mutation: none — content-addressed (I2, P3).
/// Concurrency: Copy, Send, Sync.
/// Persistence: primary key in objstore's redb table (ADR-04).
/// Serialization: CBOR, 32-byte BLAKE3 digest of ciphertext.
/// Compatibility: stable across format versions (hash domain fixed at v1).
pub struct ObjectRef([u8; 32]);

/// Ownership: objstore-owned on disk; keyring-owned in memory pre-persist.
/// Mutation: none post-write (I2).
/// Concurrency: Send, not Sync (owns ciphertext buffer).
/// Persistence: objstore record, byte layout in §8.
/// Serialization: raw bytes per §8 layout table, not CBOR-wrapped.
/// Compatibility: version + algo_id fields gate decode path (P12, I14).
pub struct EncryptedObject { header: ObjectHeader, nonce: [u8; 24], aad: Vec<u8>, ciphertext: Vec<u8>, mac: [u8; 16] }

/// Ownership: keyring-owned, never crosses the RPC boundary (I1).
/// Mutation: replaced wholesale on rotation (I11), never edited in place.
/// Concurrency: !Send, zeroized on drop.
/// Persistence: never persisted raw; only wrapped form persists.
/// Serialization: not serializable (compile-time enforced).
/// Compatibility: tied to DerivationPath's algorithm tag.
pub struct KeyHandle { raw: SecretBytes32, algo: AeadAlgo }

/// Ownership: keyring-owned, deterministic from vault topology.
/// Mutation: append-only (new levels append, existing levels immutable).
/// Concurrency: Copy, Send, Sync.
/// Persistence: derivable, not persisted (recomputed from HKDF info string).

/// Ownership: keyring-owned during issuance; user-custodied after export.

/// Compatibility: threshold/index fields versioned per Shamir scheme id.
pub struct RecoveryShare { index: u8, threshold: u8, scheme: u8, payload: SecretBytes }

/// Ownership: capd-owned (issuance), holder-owned (bearer) after issuance.
/// Mutation: none — attenuation creates a new Capability referencing a parent.
/// Concurrency: Send, Sync (no secret material beyond a signature).
/// Persistence: capability log adjacent to objstore; revocation set in capd.
/// Serialization: CBOR, UCAN-compatible wire form (ADR-12).

/// Ownership: embedded in Capability, immutable.
/// Mutation: none.
/// Concurrency: Send, Sync.

/// Ownership: connectors-owned, authored by the connector developer.

/// Mutation: monotonic advance only (I8).

12.1 Objectives

  • Stand up the 11-crate Cargo workspace (ADR-01, ADR-02).
  • Implement the crypto core: AEAD (ADR-08), HKDF (ADR-10), Argon2id (ADR-09) wrappers.
  • Wire CI (ADR-21) with a fuzz-job stub (ADR-20).
  • Establish the EncryptedObject format skeleton (§8) without persistence.

12.2 Detailed Implementation Steps

  • crates/objstore/src/format.rs: define the byte layout (§8), encode/decode respecting P12 and I14.
  • crates/keyring/src/hierarchy.rs: HKDF derivation path per the §8 table (RFC 5869).
  • crates/keyring Argon2id wrapper per RFC 9106, parameters from §4 (m=256 MiB, t=3, p=4).
  • AEAD wrapper: ChaCha20-Poly1305 (RFC 8439) plus an XChaCha20-Poly1305 variant (ADR-11).
  • Workspace-level cargo-deny policy file (ADR-03).
  • CI matrix: build+test on stable Rust, clippy, fmt (ADR-21).
  • KAT vectors from RFC 8439/RFC 9106/RFC 5869 ingested into conformance/kat/.

12.3 Deliverable

cargo build --workspace succeeds; cargo test --workspace passes; CI green on a clean clone; objstore::format encode/decode round-trips a synthetic EncryptedObject byte-identical.

12.4 Acceptance Criteria

  • 100% of RFC 8439 KAT vectors pass (chacha20poly1305_kat.txt).
  • 100% of RFC 9106 Argon2id KAT vectors pass (argon2id_kat.txt).
  • HKDF output matches RFC 5869 test vectors (hkdf_kat.txt).
  • CI pipeline completes in ≤ 6 min wall clock.
  • Zero clippy warnings at -D warnings.

12.5 Conformance Fixtures

  • chacha20poly1305_kat.txt — RFC 8439 known-answer vectors; expected ciphertext+tag match.
  • argon2id_kat.txt — RFC 9106 known-answer vectors; expected derived-key match.
  • hkdf_kat.txt — RFC 5869 known-answer vectors.
  • format_roundtrip.bin — synthetic EncryptedObject; encode→decode byte-identical.
  • format_malformed_header_len.bin — header_len exceeding buffer; expects reject.

12.6 Pitfalls

  • Treating Argon2id parameters as a compile-time constant instead of a versioned, embeddable set — breaks P12's crypto agility if parameters must change; manifests as an unmigratable vault; debug by grepping for hardcoded Argon2 params outside keyring::hierarchy; recover by embedding a params struct in the vault manifest.
  • Conflating ChaCha20-Poly1305's 12-byte nonce with XChaCha20-Poly1305's 24-byte nonce in the byte layout — manifests as decode panics; detected by KAT-vector length assertions; recovered by branching strictly on algo_id.
  • CI caching a stale cargo-deny lockfile across runs, masking a newly vulnerable dependency (T8) — detected by a scheduled (not only PR-triggered) cargo-deny check; recovered by cache-busting on lockfile hash change.

12.7 Performance Concerns

  • AEAD wrapper must avoid intermediate buffer copies — benchmark against M3 (150 MB/s/core) via benchmarks/aead_throughput.rs before Phase 1 begins.
  • Argon2id parameters (m=256 MiB) fix a floor on per-unlock memory pressure — must not regress below the §4 450 ms target on reference hardware.

12.8 Edge Cases

  • Zero-length plaintext AEAD encryption must still produce a valid MAC.
  • Argon2id invoked with p exceeding available cores must degrade gracefully, never deadlock.
  • HKDF info-string collision across two DerivationPaths must be structurally impossible (namespaced per §8 table).

12.9 Failure Analysis

  • A broken KAT vector blocks CI merge (fail-closed): blast radius — no code lands until fixed; detection — CI red; recovery — bisect the crypto-wrapper commit, re-run conformance/kat/.
  • A cargo-deny policy violation (banned license or known CVE) blocks release (ADR-21, ADR-23); recovery — dependency swap or vendored patch.

12.10 Operational Notes

  • tracing spans wrap every AEAD/HKDF/Argon2id call (ADR-18), tagged with algo_id/DerivationPath, feeding §26 dashboards from Phase 0 onward.
  • No migration or rollback concern yet — no persisted format exists until Phase 1 (§13).

13. Phase 1 — Local Encrypted Object Store

13.1 Objectives

  • Implement objstore persistence: writes commit to redb (ADR-04), content-addressed by ObjectRef (I2).
  • Enforce nonce uniqueness (I6) via a counter-plus-random-prefix nonce generator.
  • Implement tombstone-based logical delete (P3).

13.2 Detailed Implementation Steps

  • objstore::write: derive ObjectRef = BLAKE3(ciphertext) post-encryption; write via a redb MVCC transaction (ADR-04); reject on hash mismatch (I2).
  • Nonce generator: monotonic per-KeyHandle counter prefixed with a per-process random salt; counter checkpoint persisted to survive crash (I6, P12).
  • Tombstone record: a distinguished EncryptedObject variant (flags bit) referencing the superseded ObjectRef.
  • WAL-backed crash recovery via redb's native transaction log, satisfying the RTO ≤ 15 min bound (§4).

13.3 Deliverable

A CLI-invokable objstore that ingests a directory of files, writes them as EncryptedObjects, and reads them back byte-identical; nonce uniqueness held under 100,000 sequential writes.

13.4 Acceptance Criteria

  • 100,000 writes, zero nonce collisions (nonce_stress.bin, I6).
  • AEAD throughput ≥ 150 MB/s/core measured by benchmarks/aead_throughput.rs (M3).
  • Crash-injected write (kill -9 mid-transaction) recovers to last-committed state within the 15 min RTO bound (§4).
  • Tombstoned-object read returns a VaultError variant distinguishing "deleted" from "not found".

13.5 Conformance Fixtures

  • nonce_stress.bin — 100k sequential writes; expects zero I6 violations.
  • crash_mid_write.script — kills the process mid-transaction; expects clean WAL replay.
  • tombstone_roundtrip.bin — write, tombstone, read; expects "deleted" not "not found".
  • hash_mismatch_replay.bin — corrupted ciphertext with a stale ObjectRef; expects I2 rejection.

13.6 Pitfalls

  • Reusing a nonce counter across process restarts without persisting the checkpoint — manifests as an I6 violation under a crash loop; root cause: counter reset to 0; debug via nonce_reuse_detected_total; recovery: force key rotation for the affected KeyHandle (FM-1).
  • Treating tombstones as physical deletes — manifests as broken Merkle-DAG parent references (§8) when a referenced child is gone; debug via a DAG-integrity scan; recovery: never physically delete before an explicit GC epoch (I9-adjacent).
  • Unbounded redb transaction size during bulk ingest — manifests as a memory spike during Phase 4 connector ingest; debug via a transaction-size histogram; recovery: batch commits per N objects.

13.7 Performance Concerns

  • Write-path allocation: reuse ciphertext buffers across writes to avoid per-object heap churn under the M1 ingest throughput target (40 MB/s).
  • redb MVCC read amplification under concurrent readers during a long write transaction — batch write transactions to bound reader staleness.

13.8 Edge Cases

  • Write of a zero-byte object (valid ciphertext + MAC, no payload).
  • Two objects with colliding BLAKE3 prefixes truncated for an index — must use the full 32-byte digest, never a truncated one for lookup.
  • Tombstone written for an ObjectRef never written — must reject, not silently succeed.

13.9 Failure Analysis

  • Disk-full mid-write: redb transaction aborts atomically, no partial EncryptedObject persists; detection — VaultError::Io; recovery — free space, retry write; forensics — WAL intact for audit.
  • Silent bit-flip on disk: detected at read time via MAC verification failure; never silently returns corrupted plaintext.

13.10 Operational Notes

  • objstore_write_latency_seconds and objstore_bytes_written_total metrics (ADR-19) exported from Phase 1 onward.
  • No rollback concern this phase — format version fixed at 0x01; migration begins at Phase 10 (§22).

14. Phase 2 — Key Hierarchy & Recovery

14.1 Objectives

  • Implement the full HKDF derivation chain L0→L3 (§8).
  • Implement Shamir secret sharing for RecoveryShare issuance/reconstruction (P10; Shamir 1979).
  • Implement key rotation with re-wrap (I11).

14.2 Detailed Implementation Steps

  • keyring::hierarchy: HKDF-Expand per level using the §8 info strings (RFC 5869); each level's KeyHandle zeroized on drop.
  • keyring::recovery: Shamir (M,N) split over MK using a GF(256) polynomial; reconstruction requires exactly M shares (I5); property-tested against P10.
  • Key-rotation state machine: mark the old KeyHandle "rotating", re-wrap every derived object key, then destroy (I11); driven by keyring::wrap (ADR-11).
  • X3DH-derived session keys (Marlinspike & Perrin) at L3 for device pairing, preparing Phase 6 sync sessions (§18).

14.3 Deliverable

A CLI tool issuing N=5, M=3 recovery shares for a test vault and reconstructing MK from any 3; a rotation drill re-wrapping 10,000 object keys with zero I11 violations.

14.4 Acceptance Criteria

  • Reconstruction succeeds from all 10 of C(5,3) share combinations (shamir_recon.bin).
  • Reconstruction from 2 shares yields provably zero information (shamir_below_threshold.bin, P10).
  • Key rotation re-wraps 10,000 object keys in ≤ 90 s wall clock, zero rotation_incomplete_total (I11).
  • Argon2id-derived MK matches the §4 450 ms target ± 50 ms on reference hardware.

14.5 Conformance Fixtures

  • shamir_recon.bin — all 10 combinations of 3-of-5 shares; expects correct MK reconstruction.
  • shamir_below_threshold.bin — 2-of-5 shares; expects the zero-information property holds.
  • rotation_drill.bin — 10k objects, full rotation; expects zero incomplete re-wraps.
  • hkdf_derivation_chain.bin — L0→L3 derivation; expects match against RFC 5869 vectors composed per §8.

14.6 Pitfalls

  • Naive XOR-based "secret sharing" instead of Shamir's polynomial scheme — manifests as partial-information leakage below threshold, violating P10; detected by an entropy property test; recovery: replace with GF(256) Shamir.
  • Rotating a collection key without re-wrapping every derived object key first (I11) — manifests as orphaned ciphertext, unreadable after old-key destruction; root cause: rotation state machine skipped a checkpoint; debug via rotation_incomplete_total; recovery: halt destruction, resume from last checkpoint.
  • Deriving L2 object keys directly from MK instead of via CK_i — manifests as a P5 blast-radius violation; debug via derivation-path audit; recovery: re-derive strictly through the hierarchy.

14.7 Performance Concerns

  • Shamir reconstruction cost scales with polynomial degree (M-1); bounded by M ≤ 10 in practice, negligible against Argon2id's 450 ms floor.
  • Rotation re-wrap throughput must sustain ≥ 100 objects/sec to keep the 10k-object drill under the 90 s target (§14.4).

14.8 Edge Cases

  • M > N misconfiguration at share-issuance time — must reject at issuance, not reconstruction.
  • Duplicate share index submitted twice during reconstruction — deduplicated, never double-counted toward threshold.
  • Rotation triggered while a share-reconstruction (Recovery state, §8) is in progress — serialized, never concurrent.

14.9 Failure Analysis

  • Share loss below threshold (FM-6): vault permanently unrecoverable; detection — reconstruction attempt returns VaultError; no auto recovery exists by design (P10); manual recovery — none, this is the intended failure mode, disclosed to the user at issuance.
  • Rotation crash mid-re-wrap: state-machine checkpoint allows resume; blast radius — temporary dual-readability (old+new key both valid) until re-wrap completes; old key never destroyed before completion (I11).

14.10 Operational Notes

  • rotation_progress_ratio gauge (ADR-19) exported during any active rotation.
  • Recovery-share issuance is logged to auditlog as a distinct AuditEntry action type, never logging the share payload itself.

15.1 Objectives

  • Build indexer's inverted index and metadata B-tree over decrypted-in-memory records; the index never persists plaintext (P11, I1).
  • Implement a query planner/executor meeting the §4 latency targets.

15.2 Detailed Implementation Steps

  • indexer::inverted: token-level postings keyed by decrypted metadata fields, rebuilt from objstore + keyring on daemon start, never persisted (I1).
  • indexer::query: planner selects a point-lookup (ObjectRef direct) vs. a range/FTS path per §4's two latency tiers.
  • Capability-scoped query: every result row filtered through capd.verify() per-ObjectRef before returning (I3), not only at the query boundary.
  • Index-entry byte budget fixed at 96 B/entry (32 B content hash + 32 B metadata pointer + 32 B posting overhead), feeding the §34 capacity model.

15.3 Deliverable

A query CLI answering point and range queries against a 1M-object synthetic vault within the §4 latency table, with capability-filtered results matching a known-answer expected set.

15.4 Acceptance Criteria

  • Point-lookup p50/p95/p99 ≤ 8 ms/40 ms/120 ms on a 1M-object index (query_1m_point.bin, M2).
  • Range/FTS query p50/p95/p99 ≤ 25 ms/90 ms/250 ms (query_1m_range.bin).
  • Cold index rebuild from objstore completes in ≤ 90 s for 1M objects (index_rebuild_cold.bin).
  • Zero results returned for an out-of-scope ObjectRef (query_scope_leak.bin).

15.5 Conformance Fixtures

  • query_1m_point.bin — 1M-object synthetic vault; point-lookup latency histogram.
  • query_1m_range.bin — same vault; range/FTS latency histogram.
  • query_scope_leak.bin — adversarial query for out-of-scope ObjectRefs; expects zero leakage.
  • index_rebuild_cold.bin — full rebuild timing fixture.

15.6 Pitfalls

  • Filtering capability scope only at query-planning time, not per returned row — manifests as a scope leak when a plan later widens; detected by query_scope_leak.bin; recovery: enforce I3 at row-emission time.
  • Persisting index entries with plaintext metadata "for speed" — an I1 violation, silent until a disk forensic audit; detected by the boundary-crossing fuzzer (§23); recovery: purge and rebuild index in-memory-only.
  • Unbounded index growth without eviction near the 50M-object ceiling (§4) — manifests as OOM; detected by index-RAM monitoring; recovery: sharded index (§31).

15.7 Performance Concerns

  • Posting-list intersection must avoid full-list materialization for large postings — use skip-list intersection to hold p99 under 250 ms (§4).
  • Index rebuild is single-threaded by default; parallelize across objstore shards to meet the 90 s cold-rebuild target for 1M objects.

15.8 Edge Cases

  • Query against an empty vault (zero objects) — returns an empty result set, never an error.
  • Query racing a concurrent tombstone write — never returns a tombstoned object (read-your-writes within a session).
  • Metadata field absent on some ingested records — planner treats as null, never crashes.

15.9 Failure Analysis

  • Index corruption (FM-8): detected via a periodic checksum scan of index structures; blast radius — query results degrade, never silently wrong (fail-closed to "rebuild required"); recovery — full rebuild from objstore (source of truth).
  • Planner selects the wrong latency tier under adversarial metadata: detected by latency-tier telemetry mismatch; recovery — planner heuristic patch plus a regression fixture.

15.10 Operational Notes

  • query_latency_seconds histogram, tagged by tier (point/range), feeds the §30 performance-regression gate.
  • Index rebuild is the only migration-adjacent operation this phase; full format migration is Phase 10 (§22).

16.1 Objectives

  • Rate limiting: a token bucket enforced at the WASM host boundary (ADR-17), configured via ConnectorSpec.rate_limit.

16.3 Deliverable

photos-v1 ingests a 10,000-record mock library end-to-end into objstore; the cursor advances monotonically; a replayed fetch produces zero duplicate ObjectRefs.

16.4 Acceptance Criteria

  • 10,000-record ingest completes at ≥ 40 MB/s sustained (M1).
  • Replay of an already-committed cursor produces zero new ObjectRefs (connector_replay_dedup.bin).
  • Cursor-drift fixture (connector_cursor_drift.bin) is detected and halted per I8, never silently ingested.

16.5 Conformance Fixtures

  • connector_replay_dedup.bin — replay the same cursor twice; expects zero duplicate ObjectRefs.
  • connector_cursor_drift.bin — out-of-order cursor delivered; expects I8 rejection and connector halt.
  • connector_rate_limit_burst.bin — burst exceeding the token bucket; expects throttling, not failure.
  • connector_oauth_refresh.bin — expired access token, valid refresh token; expects transparent refresh.

16.6 Pitfalls

  • Content-addressing over a payload that embeds a fetch timestamp — defeats P9 idempotency; manifests as duplicate ObjectRefs on replay; debug by diffing AAD across "duplicate" objects; recovery: strip the timestamp from the content-addressed payload, carry it in a separate mutable index field.
  • WASM host granting the sandbox a capability broader than ConnectorSpec.capabilities_required — manifests as a connector "phoning home" or reaching a different collection; debug via a capability-scope audit; recovery: least-privilege capability re-derivation.
  • OAuth refresh token stored unwrapped alongside connector code — manifests as T4 (connector token theft); debug via a keyring boundary audit; recovery: move token custody into a dedicated wrapped KeyHandle.

16.7 Performance Concerns

  • WASM sandbox call overhead per fetch() invocation must stay below 1 ms to avoid dominating the 40 MB/s ingest budget at small record sizes.
  • Rate-limit token-bucket refill granularity must not introduce visible stalls above the connector's configured rate.

16.8 Edge Cases

  • Source API returns zero records for a valid cursor — the cursor still advances (an empty page is not an error).
  • Source API returns a cursor identical to the one submitted (no progress) — the connector must detect this and halt rather than loop.
  • Connector crashes mid-fetch after partial records committed — resumable from the last committed cursor, no duplicate ingest (P9).

16.9 Failure Analysis

  • Cursor drift causing duplicate ingest (FM-4): detected by I8's monotonicity check; blast radius contained to a single connector's next fetch; recovery — halt, operator reviews cursor state, resumes from last known-good.
  • Connector token theft (T4): detected by anomalous fetch-volume telemetry; recovery — revoke the connector's Capability (I4), rotate the underlying OAuth token.

16.10 Operational Notes

  • connector_ingest_bytes_total, connector_cursor_seq gauges (ADR-19) per source_id.

17. Phase 5 — Capability Issuance & Verification

17.1 Objectives

  • Implement capd issuance (UCAN, ADR-12) and the verification pipeline (§8's seven steps).
  • Implement DID-based issuer/audience (ADR-13) and revocation-set lookup (I4).

17.2 Detailed Implementation Steps

  • capd::issue: constructs Capability per the §8 fields, signs with the issuer DID key, supports attenuation via a proof chain (macaroons-style caveat narrowing, Birgisson et al. 2014).
  • capd::verify: implements the seven verification steps (§8) in order, short-circuiting on first failure (fail-closed, I13).
  • Revocation set: maintained as a CRDT-replicated set (syncd-adjacent, prefiguring §18), so revocation is visible across devices without a central authority.
  • Clock-skew tolerance (ADR-24): exp/nbf checked against a monotonic-plus-NTP-checked wall clock with a configurable skew window.

17.3 Deliverable

An issuance+verification CLI round trip: issue a Capability, attenuate it twice (narrower caveats each time), verify the attenuated chain, then revoke and verify rejection.

17.4 Acceptance Criteria

  • Verification p50/p95 ≤ 300 µs/1.2 ms for a cached issuer key (M6, §4).
  • An attenuation chain of depth 3 verifies correctly in 100% of capability_chain_valid.bin cases.
  • A revoked capability replay is rejected in 100% of capability_replay.bin cases (I4).
  • A clock-skew fixture within ± 5 min tolerance is accepted; beyond ± 5 min it is rejected (capability_clock_skew.bin).

17.5 Conformance Fixtures

  • capability_chain_valid.bin — depth-3 attenuation chain; expects valid verification.
  • capability_replay.bin — revoked-then-replayed capability; expects rejection (I4).
  • capability_clock_skew.bin — exp/nbf under varying skew; expects accept within tolerance, reject beyond.
  • capability_unknown_caveat.bin — an unrecognized Caveat variant; expects fail-closed rejection (I13).

17.6 Pitfalls

  • Verifying only the leaf capability's signature, not the full proof chain to a trusted root — manifests as a forged mid-chain attenuation passing verification; debug via a chain-walk audit; recovery: enforce recursive verification to root.
  • Accepting an unrecognized Caveat variant as "no restriction" (fail-open) instead of rejecting — directly violates I13; debug via caveat_unenforced_total; recovery: default-deny unknown variants.
  • Caching issuer keys without a grace-period boundary — manifests as legitimate capabilities rejected immediately after issuer key rotation; debug via a capability_sig_failures_total spike correlated with the rotation event; recovery: grace-period key cache (I7).

17.7 Performance Concerns

  • Signature verification must avoid a network round trip for cached issuer keys to hold the 300 µs p50 target (M6); network fallback only on cache miss.
  • Revocation-set lookup must be O(1) (hash-set membership), not a linear scan, to avoid dominating verification latency as the revoked set grows.

17.8 Edge Cases

  • Capability with nbf in the future relative to the skew-tolerant clock — rejected as not-yet-valid, distinct from an invalid-signature rejection.
  • Attenuation chain where a child caveat is broader than its parent — rejected (monotonicity violation, I13).
  • Simultaneous issuance and revocation of the same capability (race) — revocation wins if it lands before first use (fail-safe ordering).

17.9 Failure Analysis

  • Capability replay (T5): detected by I4's revocation-set check; blast radius — a single rejected request, no data exposure; recovery — none needed, correct behavior.
  • Clock skew invalidating capabilities (FM-5): detected by a spike in the exp/nbf rejection metric; root cause — device clock drift beyond the skew tolerance; recovery — NTP resync, reissue the capability.

17.10 Operational Notes

  • capability_verify_latency_seconds, capability_revocation_set_size metrics (ADR-19).
  • Issuer key rotation follows the same re-wrap discipline as I11, logged distinctly in auditlog.

18. Phase 6 — Multi-Device Sync & CRDT Merge

18.1 Objectives

  • Implement syncd's Automerge integration (ADR-15) for structured metadata and the pointer-register merge (P8) for binary objects.
  • Implement QUIC transport (ADR-06) to relay, ciphertext-only.

18.2 Detailed Implementation Steps

  • syncd::crdt: wraps Automerge document ops as SyncOp::CrdtOp, applies via Automerge's merge (Shapiro et al. 2011 convergence guarantees).
  • syncd::pointer: an LWW pointer register keyed by logical name, vector-clock-stamped (§8); the non-winning ObjectRef remains reachable (P3).
  • syncd::transport: a QUIC client/server (quinn) exchanging SyncOp batches with relay; payload is always EncryptedObject/Capability ciphertext (P1).
  • Device pairing: an X3DH-derived session key (§14) establishes an authenticated channel per device pair before first sync.

18.3 Deliverable

Two simulated devices converge on an identical CRDT document and pointer-register state after a scripted sequence of concurrent, offline-then-reconnected edits.

18.4 Acceptance Criteria

  • CRDT convergence: 100% state equality across devices after merge (sync_convergence_concurrent.bin).
  • Pointer-register conflict resolved deterministically, same winner on both devices (sync_pointer_conflict.bin).
  • Sync bandwidth ≤ 5 MB/device/day steady-state under the scripted workload (M5, §4).
  • A reconnect-after-90-day-offline fixture triggers a full resync per the offline-tolerance ceiling (§4).

18.5 Conformance Fixtures

  • sync_convergence_concurrent.bin — concurrent edits on 2 devices; expects convergent state.
  • sync_pointer_conflict.bin — concurrent pointer updates; expects a deterministic LWW winner plus a reachable loser.
  • sync_replay_idempotent.bin — duplicate SyncOp delivery; expects apply-twice = apply-once (I12).
  • sync_offline_90d.bin — device offline 90 days; expects a forced full resync, never silent data loss.

18.6 Pitfalls

  • Attempting CRDT merge over encrypted binary payloads directly — either impossible or a confidentiality bug (P8); debug via a merge-path type audit; recovery: route binary objects exclusively through the pointer register.
  • Unbounded Automerge op-log growth without periodic compaction (FM-3) — manifests as steadily increasing sync bandwidth beyond M5; debug via op-log size trend; recovery: a scheduled compaction epoch plus tombstone GC (I9).
  • Treating relay as authoritative for merge order — a hidden centralization violating P7; debug via a relay-outage drill showing devices still converge peer-to-peer once reconnected; recovery: merge order derived from vector clocks, never relay arrival order.

18.7 Performance Concerns

  • SyncOp batching must amortize QUIC stream overhead; too-small batches waste round trips, too-large batches spike per-sync latency.
  • Automerge document size must be sharded per collection to bound per-sync CPU cost as the vault approaches the 50M-object ceiling (§31).

18.8 Edge Cases

  • Two devices offline simultaneously, each queuing conflicting pointer updates — resolved only at first mutual reconnect, never against relay alone.
  • Partial SyncOp batch delivery (connection drops mid-batch) — a batch is never partially applied.
  • Device clock skew affecting vector-clock comparison — vector clocks are logical, not wall-clock-based, structurally immune to skew (contrast T10's effect on capabilities).

18.9 Failure Analysis

  • CRDT tombstone growth (FM-3): detected by op-log size telemetry; blast radius — degraded sync bandwidth, never data loss; recovery — trigger compaction, extend GC epoch coordination (I9).
  • Relay outage stalling sync (FM-7): detected by a sync-lag gauge; blast radius — devices continue operating locally (P7), no write blocked; recovery — automatic resume on relay reachability, no manual intervention.

18.10 Operational Notes

  • sync_lag_seconds, sync_bandwidth_bytes_total metrics (ADR-19) per device pair.
  • Relay version and syncd version negotiate a compatible SyncOp wire version at connection handshake (§27).

19. Phase 7 — Revocation & Audit Log

19.1 Objectives

  • Implement full capability-revocation propagation (P13; RFC 7009 conceptual parallel) and the hash-chained auditlog (I10).

19.2 Detailed Implementation Steps

  • capd::revocation: revocation entries replicated as a CRDT set via syncd (§18), propagated to online devices within the M7 60 s bound.
  • Reconnect handshake: any device reconnecting to relay or a peer fetches the current revocation set before accepting any cached capability as valid (P13).
  • auditlog::append: each AuditEntry hashes the previous entry's digest into prev_hash (I10), forming a tamper-evident chain.
  • auditlog::scan: a periodic chain-verification job detects any break, feeding auditlog_chain_break_total.

19.3 Deliverable

A revocation drill: revoke a capability, observe propagation to 5 simulated online devices within 60 s, and immediate enforcement at a 6th device's reconnect after being offline; an auditlog chain-verification pass over 100,000 entries.

19.4 Acceptance Criteria

  • Revocation visible to all online devices within 60 s p99 (M7, §4).
  • An offline device enforces revocation synchronously at reconnect, independent of offline duration (P13).
  • auditlog chain verification over 100,000 entries completes with zero auditlog_chain_break_total.
  • A deliberately corrupted chain entry is detected within one scan cycle (auditlog_tamper.bin).

19.5 Conformance Fixtures

  • revocation_propagation_5device.bin — 5 online devices; expects ≤ 60 s propagation.
  • revocation_reconnect_offline.bin — device offline then reconnecting; expects synchronous enforcement.
  • auditlog_chain_100k.bin — 100k-entry chain; expects zero verification breaks.
  • auditlog_tamper.bin — deliberately altered mid-chain entry; expects detection.

19.6 Pitfalls

  • Propagating revocation only via periodic relay polling — manifests as propagation delay exceeding M7 under low poll frequency; debug via a propagation-latency histogram; recovery: push-based revocation over the QUIC channel (ADR-06), polling only as fallback.
  • Appending to auditlog without holding a write lock across the hash-chain update — manifests as a race producing two entries with the same prev_hash (a silent fork); debug via chain-fork detection in the scan job; recovery: serialize appends through a single-writer actor.
  • An auditlog compaction/retention policy dropping entries needed for a chain-verification scan — manifests as false-positive chain breaks; debug via a retention-policy audit; recovery: chain-verification-aware retention, never drop below the last verified checkpoint.

19.7 Performance Concerns

  • Hash-chaining cost is O(1) per append (a single hash of the previous digest plus the entry); must never become O(n) by re-hashing the whole log.
  • A chain-verification scan over 100,000 entries must complete without blocking live appends (a read-only snapshot scan).

19.8 Edge Cases

  • Revocation issued for a capability that was never used — still enters the revocation set (idempotent no-op enforcement).
  • Two revocations issued concurrently for the same capability from two devices — CRDT set union handles this without conflict.
  • An auditlog scan running during an active key-rotation drill (§14) — must not misinterpret rotation-related AuditEntry rows as tampering.

19.9 Failure Analysis

  • Revocation propagation delay (M7 miss): detected by an SLO breach on propagation latency; blast radius — a revoked capability usable slightly longer than intended on a slow-reconnecting device; recovery — investigate the push path, check relay health.
  • Auditlog hash-chain break (FM-10): detected by the scan job; blast radius — forensic trust in the log segment after the break is degraded; recovery — restore from the last verified checkpoint, treat the gap as a security incident requiring a full session audit.

19.10 Operational Notes

  • revocation_propagation_seconds, auditlog_entries_total, auditlog_chain_break_total metrics (ADR-19).
  • Revocation and audit-log data are exempt from the §22 format-migration deferral — both must remain readable across every format version (P4).

20.6 Pitfalls

  • Enforcing scope only at the prompt-construction step instead of the retrieval layer — a prompt-injected follow-up request can still walk past a prompt-level filter; manifests as twin_scope_fuzz.bin failures; debug via retrieval-layer trace; recovery: filter every retrieved record against caveats before it ever reaches the model context.
  • remote_model silently used as a fallback when local_model is unavailable, bypassing the reserved-caveat check — manifests as an unconsented remote call; debug via twin_scope_rejections_total gaps; recovery: fail closed, never auto-escalate backend.
  • Canary objects swept up by routine tombstone GC (I9), silently losing detection coverage over time — debug via canary-population count drift; recovery: exempt canaries from the standard GC epoch.
  • Consent-grant attenuation implemented as freestanding reissuance instead of a proof-chain child — permits scope creep (T11-adjacent, FM-9); debug via chain-monotonicity fuzzer; recovery: require every attenuated grant to carry its parent in proof.
  • Double Ratchet session desync after a twinadapt process restart causing transport decrypt failure on the next remote call — debug via ratchet-state audit; recovery: reinitiate the X3DH handshake (§14) for that session.

20.7 Performance Concerns

  • local_model cold-start (model load) dominates tail latency; keep a warm inference pool to hold the M8 p95 bound.
  • Retrieval must stay within the existing §4 query-latency budget; twinadapt adds inference time on top, never re-implements its own slower query path.
  • Ratchet handshake cost is paid once per new remote session, not per request, to avoid dominating the remote path's latency.

20.8 Edge Cases

  • ConsentGrant expiring mid-multi-turn conversation — each turn re-checks validity independently (P11), no cached "still consented" assumption across turns.
  • Scope resolves to zero records (empty collection) — the model receives an explicit empty-context signal, never a silent fabrication risk.
  • Revocation arriving mid-in-flight inference — the already-open read completes (single check-then-read per P11), but the next turn is blocked.

20.9 Failure Analysis

  • Prompt-injection exfiltration attempt (T11, FM-11): detected by twin_canary_triggered_total; blast radius contained to the single blocked response; recovery — revoke the ConsentGrant, quarantine the poisoning source object, audit the session via auditlog.
  • Consent-scope creep (FM-9): detected by the chain-monotonicity fuzzer; recovery — patch the verifier's caveat table, replay historical grants for audit, revoke any grant found broader than its parent.

20.10 Operational Notes

  • twin_inference_latency_seconds, twin_scope_rejections_total, twin_canary_triggered_total metrics (ADR-19).
  • A user-facing "what my twin can see" view is built directly from auditlog scans — no separate consent-state store to drift out of sync.

21. Phase 9 — Relay & Self-Host Deployment

21.1 Objectives

  • Implement relay::forward's ciphertext-only store-and-forward (P1) and relay::schedule's connector-trigger scheduling.
  • Package a self-host deployment: static musl binaries in a distroless container (ADR-22), a docker-compose.yml dev/self-host stack (§10).
  • Minimize relay-observable metadata leakage (T7) via size-bucket padding and batched delivery windows.

21.2 Detailed Implementation Steps

  • relay::forward: accepts EncryptedObject/Capability/SyncOp blobs over QUIC (ADR-06), retains ciphertext only until every target device acks or a TTL expires; never inspects payload beyond the wire envelope (P1).
  • relay::schedule: fires connector-trigger wakeups (webhook or cron-style) without ever holding connector credentials — those remain wrapped under a KeyHandle on the owning device (P5).
  • Metadata-leakage minimization: object sizes rounded up into fixed padding buckets before transmission; delivery batched into a bounded window (~2 s) to blur per-object timing correlation (mitigates T7); relay retains no persistent peer-graph log, only ephemeral in-memory routing state.
  • Multi-relay federation: a vault may shard traffic across N independently operated relays so no single operator observes a full device graph — a deployment option, not a default (§31).
  • Packaging: Dockerfile builds a distroless, non-root image from a static musl binary (ADR-22); docker-compose.yml composes a local vaultd + relay stack for self-host operators.

21.3 Deliverable

A self-hosted docker-compose.yml stack forwarding SyncOp/EncryptedObject batches among 3 simulated devices, with a packet capture confirming zero plaintext on the wire and a statistical size-distribution test confirming padding-bucket indistinguishability across content types.

21.4 Acceptance Criteria

  • Relay forwarding throughput ≥ 200 MB/s per instance on reference hardware (M9).
  • Zero plaintext bytes observed in a full-session tcpdump capture (relay_plaintext_leak.bin).
  • Padding-bucket size distribution statistically indistinguishable (chi-square test, p > 0.05) across photo/text/metadata object classes (relay_metadata_padding.bin).
  • A 2-relay federation split leaves no single relay observing > 50% of one device's traffic (relay_federation_split.bin).
  • Unacked blobs purge exactly at TTL, never before (relay_ttl_expiry.bin).

21.5 Conformance Fixtures

  • relay_forward_roundtrip.bin — 3-device forwarding drill; expects correct delivery, zero data loss.
  • relay_plaintext_leak.bin — full-session packet capture; expects zero plaintext bytes.
  • relay_metadata_padding.bin — mixed content-type batch; expects statistically indistinguishable padded sizes.
  • relay_federation_split.bin — 2-relay federated routing; expects ≤ 50% traffic-share visibility per relay.
  • relay_ttl_expiry.bin — one device never acks; expects purge exactly at TTL boundary.

21.6 Pitfalls

  • Unpadded object sizes leaking content-type via size correlation (a photo-sized blob is distinguishable from a note) — a T7 manifestation; debug via the padding-distribution audit; recovery: coarsen the bucket set.
  • Relay logging fine-grained timestamps that enable cross-device traffic-analysis correlation — debug via a log-field audit against §26's privacy-preserving logging policy; recovery: coarsen logged timestamps to bucket granularity, drop per-connection detail beyond aggregate counters.
  • Container running as root inside the distroless image, widening the blast radius of a relay compromise (T1) — debug via an image-scan policy check; recovery: enforce a non-root USER directive in Dockerfile.
  • TTL purge racing a slow-reconnecting device, deleting a blob it hasn't yet acked — manifests as a silent sync gap indistinguishable from "not yet delivered"; recovery: TTL must exceed the §4 90-day offline-tolerance ceiling's short-term case, or the device forces a full resync (§4) instead of assuming loss.
  • Naive round-robin "federation" across relays operated by the same entity, which defeats the confidentiality benefit despite nominal multi-relay routing — recovery: require federation partners to be independently operated for the T7 mitigation to hold.

21.7 Performance Concerns

  • QUIC 0-RTT reconnect (ADR-06) must hold up under high device-churn self-host deployments; connection-migration support avoids re-handshake cost.
  • The batching window trades latency for metadata protection; widen it only within the M5 sync-bandwidth budget's tolerance, never enough to breach §4's sync targets.

21.8 Edge Cases

  • Relay process restart mid-forward — re-delivery is safe because forwarded objects are content-addressed (P3) and sync ops are idempotent (I12), so redundant delivery never duplicates state.
  • A device permanently offline beyond the TTL — its queued blobs purge; on eventual reconnect it triggers a full resync per the §4 90-day offline-tolerance boundary, not a partial catch-up.
  • Connector-trigger scheduling firing while the target vault is in the Locked state (§8) — the trigger queues, it is never dropped.

21.9 Failure Analysis

  • Relay compromise (T1): detected by anomalous forwarding-volume telemetry; blast radius is denial-of-service only, never confidentiality loss (P1); recovery — operator rotates the relay's identity keys, clients repoint to a backup or self-hosted relay.
  • Metadata leakage via traffic analysis (T7): detected by the periodic padding-distribution audit; recovery — tighten bucket granularity, widen the batching window, or move to a federated topology (§31).

21.10 Operational Notes

  • relay_forward_bytes_total, relay_active_connections, relay_blob_ttl_expired_total metrics (ADR-19).
  • Named runbook docs/runbooks/relay-incident.md covers suspected relay compromise response.

22. Phase 10 — Format Durability & Migration Tooling

22.1 Objectives

  • Implement tools/vault-migrate (§10): a full-vault re-encrypt/format-migration CLI honoring crypto agility (P12, I14).
  • Maintain an archived, dependency-frozen reference decoder satisfying the 25-year readability commitment (P4, §4).
  • Implement the dual-format read path for the Migrating lifecycle state (§8).

22.2 Detailed Implementation Steps

  • vault-migrate: decrypts every EncryptedObject under its current algo_id/version (I14), re-encrypts under the target algorithm (P12), and mints a new ObjectRef — migration is the one sanctioned exception to P3's immutability, gated exclusively behind the Migrating lifecycle state (§8).
  • Merkle-DAG pointer rewrite: every parent_ref and pointer-register entry referencing a migrated object is atomically updated in the same transactional unit as the re-encrypt (mirrors the tombstone-vs-physical-delete discipline of §13.6).
  • Checkpointed resume: migration progress is durably checkpointed per-object-batch, so a crash mid-migration resumes without reprocessing already-migrated objects (the same discipline I11 applies to key rotation).
  • Dual-format read path: while Migrating, reads dispatch on EncryptedObject.version (I14) — new-format objects first, old-format fallback — so the vault stays usable mid-migration.
  • Archived reference decoder (P4): a frozen, dependency-vendored decoder for each historical format version, decoupled from the live redb/ciborium crate versions, checked in under docs/adr/ alongside its originating ADR, so the 25-year commitment (§4) survives independent of future crate churn.
  • Multi-device rollout gating: the old key is never destroyed (I11-style discipline) until every registered device (≤ 32, §4) has acknowledged migration completion.

22.3 Deliverable

vault-migrate migrates a 100,000-object v1 vault to a v2 format (new algo_id) with byte-identical recovered plaintext, resumable after a simulated crash at the 50% checkpoint, verified against the archived v1 decoder as ground truth.

22.4 Acceptance Criteria

  • 100,000-object migration completes with zero plaintext mismatches against the pre-migration corpus (migrate_v1_to_v2_100k.bin).
  • Crash-resume at 50% reprocesses zero already-migrated objects (migrate_crash_resume.script).
  • The archived v1 decoder decodes a frozen migrate_kat_v1_decode.bin vector correctly, independent of the live crate's current dependency versions.
  • Full-vault migration throughput ≥ 20 GB/hour per core (M10).
  • Old key destruction blocked until all registered devices ack (migrate_dual_read_path.bin exercises the dual-format window).

22.5 Conformance Fixtures

  • migrate_v1_to_v2_100k.bin — full 100k-object migration; expects byte-identical plaintext recovery.
  • migrate_crash_resume.script — kill mid-migration at 50%; expects clean checkpoint resume, zero reprocessing.
  • migrate_kat_v1_decode.bin — frozen v1 KAT vector; expects the archived decoder reproduces canonical plaintext.
  • migrate_pointer_rewrite.bin — DAG with diamond references; expects every parent_ref updated exactly once, no orphans.
  • migrate_dual_read_path.bin — mixed v1/v2 objects mid-migration; expects transparent version-dispatched reads.

22.6 Pitfalls

  • Re-encrypting objects without atomically updating their parent_ref/pointer-register entries — manifests as a broken Merkle-DAG post-migration, the migration-time analogue of §13.6's tombstone pitfall; debug via a DAG-integrity scan; recovery: wrap re-encrypt + pointer-rewrite in one transaction.
  • No durable migration checkpoint, so a crash forces a full restart-from-zero — manifests as unbounded migration wall-clock on a 2 TB vault (§34); debug via checkpoint-hash absence; recovery: checkpoint every N-object batch (mirrors I11's rotation checkpointing).
  • Archived reference decoder silently linking against the live crate's current ciborium/HKDF versions instead of a vendored, frozen copy — defeats P4's 25-year commitment the moment that live crate has a breaking change; debug via a dependency-graph audit of the archived decoder; recovery: vendor-freeze its dependencies at migration-authoring time.
  • Destroying the old key before every device has acknowledged migration — a device that hasn't migrated yet loses readability entirely; debug via the device-ack completeness gauge; recovery: never destroy before 100% ack (I11-style discipline, FM-12).
  • KAT vectors regenerated from the new implementation rather than preserved from the original — validates self-consistency, not correctness, silently masking a decode regression; recovery: pin KAT ground truth to the original implementation's output at authoring time.

22.7 Performance Concerns

  • Full re-encrypt is AEAD-throughput-bound (M3, 150 MB/s/core); parallelize across DAG-independent subtrees to approach M10's 20 GB/hour/core aggregate target.
  • Checkpoint-write overhead must stay under 2% of total migration wall-clock, or checkpointing itself becomes the bottleneck.

22.8 Edge Cases

  • An object referenced by two parents (a DAG diamond) is migrated and re-addressed exactly once, never duplicated (dedup keyed on the pre-migration ObjectRef).
  • Migration invoked on an already-fully-migrated vault — detected via the version field, a clean no-op.
  • Tombstoned objects: the tombstone marker itself migrates (small, format-relevant); the already-inert underlying ciphertext is not re-encrypted before its eventual GC.

22.9 Failure Analysis

  • Cipher-migration re-wrap failure (FM-12): partial migration leaves some objects unreadable on devices that already advanced past the dual-format window; detected by dual-format-read fallback failures; recovery — resume from the last durable checkpoint, cross-check against the archived reference decoder.
  • Migration checkpoint corruption: detected via checkpoint-hash mismatch on resume; recovery — restart from the last verified checkpoint, worst case a full restart bounded by the §4 RTO.

22.10 Operational Notes

  • migration_progress_ratio gauge (ADR-19).
  • Named runbook docs/runbooks/format-migration.md.
  • Migration is the single phase explicitly permitted to violate P3's object-identity stability, and only inside the Migrating lifecycle state (§8).

23. Phase 11 — Conformance Suite & Performance Hardening

23.1 Objectives

  • Assemble the full I1–I14 deterministic simulator (§7) into a CI-blocking conformance suite (ADR-21).
  • Extend the fuzz targets (objstore_decode.rs, capd_verify.rs, §10) and freeze a KAT vector suite for the AEAD (RFC 8439) and KDF (RFC 9106).
  • Wire a performance-regression gate across all M1–M12 targets (§30) into CI.

23.2 Detailed Implementation Steps

  • conformance/sim (§7, §10) drives scripted device/relay/connector fault injections with one assertion per invariant (I1–I14), now wired as a CI-blocking make conformance target (ADR-21).
  • Fuzz coverage: objstore_decode.rs extended to cover connector-ingested records too, since ingestion enters through the same EncryptedObject decode path (§8) — no separate connector-payload fuzz binary is needed, keeping the fuzz-target set matched to §10; capd_verify.rs covers malformed Capability/ConsentGrant tokens uniformly (P6's shape reuse).
  • KAT suite: canonical (key, nonce, plaintext, ciphertext) vectors for ChaCha20-Poly1305 pinned to RFC 8439's published test vectors, and Argon2id vectors pinned to RFC 9106's, stored under conformance/kat/ (§10); ground truth is the RFC text, never the project's own prior output.
  • Performance-regression gate: the three existing benchmarks/*.rs harnesses (§10) are extended to also assert against M8–M12 via companion conformance fixtures capturing twin-inference and relay-throughput timings, rather than introducing new benchmark crates — keeping AEAD/query/KDF as the three canonical harnesses.
  • Soak test: a 72-hour continuous simulated multi-device workload (ingest + sync + query + twin) run via conformance/sim, asserting zero invariant violations and bounded memory growth.

23.3 Deliverable

A single make conformance target running the full sim (I1–I14), the fuzz corpora, the KAT suite, and the performance-regression gate, exiting non-zero on any invariant violation, KAT mismatch, or performance regression beyond tolerance.

23.4 Acceptance Criteria

  • Full I1–I14 simulator run: zero violations across 1,000,000 scripted steps (conformance_full_sim.bin).
  • KAT suite: 100% match against RFC 8439/RFC 9106 published vectors (kat_aead.bin, kat_kdf.bin).
  • Both fuzz corpora run 1,000,000 iterations each with zero unexpected panics.
  • 72-hour soak completes with zero invariant violations and < 1% resident-memory growth (soak_72h.script).
  • Performance gate fails CI if AEAD throughput regresses below 140 MB/s/core (a 5% tolerance under M3's 150 MB/s target) or any M8–M12 target regresses beyond its stated tolerance (perf_regression_gate.bin).

23.5 Conformance Fixtures

  • conformance_full_sim.bin — 1M-step scripted fault-injection run; expects zero I1–I14 violations.
  • kat_aead.bin — RFC 8439 ChaCha20-Poly1305 vectors; expects exact match.
  • kat_kdf.bin — RFC 9106 Argon2id vectors; expects exact match.
  • soak_72h.script — 72-hour multi-device workload; expects zero invariant violations, bounded memory growth.
  • perf_regression_gate.bin — replays the M1–M12 benchmark suite; expects all targets within tolerance.

23.6 Pitfalls

  • A stale, never-minimized fuzz seed corpus creates false confidence — it stops discovering new bug classes; debug via coverage-plateau detection; recovery: scheduled corpus-minimization and coverage-guided reseeding (fuzz.yml, §10).
  • KAT vectors sourced only from the project's own implementation instead of the RFC's published vectors validates self-consistency, not correctness; recovery: pin to RFC 8439/9106 ground truth, never regenerate from the implementation under test.
  • A performance-regression tolerance set too loose (e.g. 50%) never fires, letting regressions creep in across many small PRs; recovery: tighten the band, add a trend dashboard (§26) alongside the hard CI gate.
  • Soak testing on idle/non-representative hardware misses realistic memory growth under load; recovery: soak against the same reference-hardware profile used for the §4 targets.
  • The sim harness logging a caught invariant violation and continuing, rather than hard-failing — silently turns a conformance breach into a passing CI run; recovery: any I1–I14 violation must abort the run non-zero, per §7's original methodology.

23.7 Performance Concerns

  • Fuzz-target iteration rate, not just corpus size, determines whether the 1M-iteration bar fits CI time budgets — instrument and gate on iterations/sec.
  • Soak-test resource sampling must run out-of-process, or the sampler itself perturbs the memory-growth measurement it's trying to capture.

23.8 Edge Cases

  • A fuzz input landing exactly at a buffer-length boundary (header_len equal to the remaining buffer) — must reject cleanly, never off-by-one panic.
  • A KAT vector with a zero-length plaintext — must still produce the RFC-specified ciphertext/tag.
  • The soak test surviving a mid-run key rotation (§14) without any invariant violation.
  • The performance gate running on a CI runner with cold caches — must warm up before measuring, or the §4 p50 targets fail spuriously.

23.9 Failure Analysis

  • A performance regression breaching any M1–M12 target (a §30 gate failure): detected by CI; blast radius is a blocked merge only, never a production impact; recovery — bisect the regressing commit, revert or optimize before re-merge.
  • A fuzz-discovered panic in the shared objstore_decode.rs path (a new crash class): detected by cargo-fuzz; recovery — minimize the crash input, add it as a permanent regression fixture, patch the decode path to reject rather than panic.

23.10 Operational Notes

  • conformance_suite_duration_seconds, fuzz_corpus_size, perf_regression_detected_total metrics (ADR-19).
  • Conformance-suite results are archived per release (§29) as part of the release provenance record.

  • Single-binary self-host (Phase 9, §21) is the reference topology; managed-relay and multi-relay federation (§31) are deployment options layered on the same relay crate, never a different trust model (P1 holds regardless of topology).

Canary / Rollback / Migration

  • Canary releases via the GitHub Actions release channel (ADR-21); rollback is a version pin (§27's SemVer discipline); format migration is exclusively the Phase 10 tool (§22), never an ad-hoc data patch.

27. Compatibility & Versioning

  • On-disk format version: EncryptedObject.version (I14) embedded in every object header (§8); unversioned objects are rejected, never assumed-latest.
  • Crypto agility: algo_id (P12) travels with ciphertext; algorithm migration is additive via tools/vault-migrate (§22), never a hardcoded flag day.
  • Capability format versioning: UCAN wire form (ADR-12); caveat schema versioned independently of the vault format (§11) — a caveat-set change never forces a full-vault migration.
  • Connector API pinning: ConnectorSpec.spec_version (§11) gates the WASM sandbox ABI (ADR-17); a connector built against an old spec_version runs against a shimmed-compatible ABI or is refused, never silently mismatched.
  • Schema evolution: CBOR's self-describing form (ADR-05) plus #[non_exhaustive] error/caveat enums (§11) allow additive fields without breaking older readers.
  • Deprecation policy: a deprecated format version, ADR decision, or connector spec_version is supported for at least 2 major releases before removal, tracked in CHANGELOG.md (§10).
  • SemVer: every crate and the CLI follow SemVer; a breaking on-disk or wire change is a major bump and requires a corresponding Phase-10-style migration path.
  • Rolling-upgrade guarantees: the dual-format read path (§22, Migrating lifecycle state, §8) guarantees a vault stays readable/writable throughout any format transition across a ≤ 32-device fleet (§4).
  • Multi-decade readability commitment: ≥ 25 years, backed by the archived reference decoder (§22) and the frozen-dependency discipline described there (P4).

28. Testing & Verification Strategy

  • Unit: per-module (§10 crates), covering pure functions (HKDF derivation, Caveat parsing, byte-layout encode/decode).
  • Integration: cross-crate flows — issue→verify (I3, I4, I7, I13), ingest→index→query (I2, I8), sync→merge→resolve (I12, P8).
  • Property (proptest, ADR-20): encrypt/decrypt round-trip holds for arbitrary payloads (I2, I6); CRDT convergence holds for arbitrary concurrent op interleavings (I12, Shapiro et al. 2011); capability attenuation is monotonically narrowing across arbitrary caveat sequences (I13, P2).
  • Differential: vault-migrate's output diffed against the archived reference decoder's independent decode (P4, §22).
  • Fuzzing (cargo-fuzz, ADR-20): objstore_decode.rs (malformed EncryptedObject and connector-ingested records, §23), capd_verify.rs (malformed Capability/ConsentGrant).
  • Chaos: conformance/sim (§7) scripted device/relay/connector fault injection, one assertion per I1–I14.
  • Deterministic replay: any invariant violation dumps the full op trace for byte-identical replay (§7's methodology).
  • Soak: the 72-hour multi-device workload (soak_72h.script, §23).
  • Fault injection: crash_mid_write.script (§13), migrate_crash_resume.script (§22).
  • KAT: kat_aead.bin (RFC 8439), kat_kdf.bin (RFC 9106) — ground truth is the RFC text, never the implementation under test (§23).
  • Performance-regression gating: the M1–M12 table (§30) gates CI via perf_regression_gate.bin (§23).
  • Every property/fuzz/chaos check above ties back to a specific invariant (I1–I14) and to the originating phase's N.5 fixture set — no test exists without a named invariant or fixture anchor.

31. Scalability Analysis

  • Constant regardless of vault size: capability verification latency (M6, O(1) hash-set revocation lookup); AEAD throughput per core (M3).
  • Grows with vault size: objstore storage (O(n) objects, monotonic absent GC per P3); indexer RAM (O(n) until sharded, §34); sync bandwidth (O(devices × ops/day), M5).
  • Named bottlenecks, in order: (1) index RAM ceiling — 50,000,000 objects (§4) before a single-process indexer OOMs; (2) device-fanout ceiling — 32 devices/vault (§4) bounding syncd's CRDT/pointer-register coordination cost; (3) single-relay throughput (M9) under a self-hosted, non-federated topology; (4) migration wall-clock (M10) on a near-2 TB vault (§34).
  • Horizontal scaling: shard the index by collection-hash bucket beyond the 50M ceiling, running multiple indexer instances federated by collection; shard relay traffic across independently operated relays (§21's federation option).
  • Vertical scaling: more cores linearly improve AEAD (M3), Argon2id parallel-lane derivation (bounded by the chosen p parameter, §4), and query-planner concurrency.
  • Sharding: index shards are collection-scoped, never object-scoped, so a capability's CollectionScope caveat (§8) naturally maps to shard boundaries.
  • Coordination overhead: CRDT merge cost (Automerge, ADR-15) grows with concurrent-editor count per shared collection — bounded in practice by the single-owner, ≤ 32-device model (§4), not by an organization-scale multi-writer assumption (PhaseDeferred("§1")).
  • Practical ceiling: 2 TB/vault, 50,000,000 objects, 32 devices (§4). Levers beyond it: sharded federated indexing, multi-relay federation, or an opt-in server-assisted index for owners who accept partial custody delegation (a rejected default, §36).

32. Mental Models & First Principles

MM1. Sovereignty is a key-custody problem wearing a product costume. Predicts: evaluate any feature proposal by "who can decrypt," never by UI framing. Bug class without it: server-side convenience features (search, dedup) silently reintroducing platform custody. Resolves via P1, T1 (§24).

MM2. A capability is a fact about the past, not the present — validity must be re-checked, never cached as settled. Predicts revocation must be enforced at use, not trusted from an issuance-time cache. Bug class without it: stale-cache authorization bugs indistinguishable from "was never enforced." Resolves via I4, §17.

MM3. Content addressing turns "delete" into a policy question, not a mechanism. Predicts storage grows monotonically absent GC; "delete" always means tombstone-then-eventual-key-destruction. Bug class without it: treating a tombstone as a physical delete, breaking DAG references. Resolves via P3, §13.

MM4. The twin is a bounded reader, never a co-owner. Predicts any design granting the model standing access instead of per-request scoped access reproduces platform-AI-memory failures. Bug class without it: consent-scope creep, prompt-injection exfiltration. Resolves via P6, P14, §20.

MM5. An untrusted relay is a scheduling and store-and-forward problem, never a trust problem. Predicts relay compromise manifests only as denial-of-service. Bug class without it: any code path silently requiring relay cooperation for confidentiality. Resolves via P1, §21.

MM6. Format durability is a promise that must be verifiable independent of any future implementation. Predicts the archived reference decoder must never silently depend on live crate versions. Bug class without it: format lock-in disguised as "just re-run the migration tool," except the tool itself has bit-rotted. Resolves via P4, §22.

MM7. Recovery and compromise are the same math, pointed in opposite directions. Predicts the k-of-n threshold analysis that protects against share loss also bounds collusion risk (§34). Bug class without it: choosing a threshold for availability alone while ignoring the collusion tradeoff. Resolves via P10, T9 (§24).

MM8. Crypto agility is a header field, not a rewrite. Predicts algorithm migration is always additive (a new algo_id), never a flag day. Bug class without it: hardcoded-algorithm assumptions that make P4's 25-year commitment undeliverable once that algorithm is deprecated. Resolves via P12, §22.

Solid anchors identity and access control to WAC/ACP layered over an LDP resource store; the reference-implementation lesson (§5) is that ACL-shaped authorization does not attenuate — a granted permission has no natural narrowing operation the way a UCAN caveat chain does (contrast P2), which is exactly the failure mode Aeon's capability model is built to avoid.

Bluesky's AT Protocol PDS demonstrates a content-addressed, signed per-user repository at real scale, validating Aeon's addressing choice; its gap, per the reference-implementation lesson (§5), is that a hosted PDS operator retains custody of the repo signing key unless the user self-hosts, reproducing exactly the platform-custody dependency P1 exists to remove.

Tahoe-LAFS is the closest architectural cousin: capability-URIs are the sole access path to encrypted shares, with no separate ACL layer — the lesson Aeon inherits directly (§5) is that capability leakage via any logging path defeats the entire model, which is why I1 and the boundary-crossing fuzzer (§23) treat "never log plaintext or capability material" as a zero-tolerance invariant rather than a best practice.

Perkeep's generic content-addressed schema layer over personal blobs validates the ObjectRef/Merkle-DAG domain model (§8), but its search index is tightly coupled to one deployment topology (§5) — Aeon avoids this by keeping the indexer an in-memory, rebuildable-from-objstore structure that never becomes a second source of truth.

Apple's iCloud Advanced Data Protection proves end-to-end encryption can ship at consumer scale with device-held keys and no vendor decryption capability, matching P1's posture, but its authorization and sync models are closed and vendor-specific, and it has no analog to a portable, capability-scoped twin adapter (P6, P14) or an open, migratable on-disk format (P4) — the two dimensions where Aeon's design diverges most sharply from a "sovereign iCloud."

34. Back-of-Envelope Capacity Model

  1. Index RAM ceiling. 50,000,000 objects (§4) × 96 B/index-entry (32 B content hash + 32 B metadata pointer + 32 B posting overhead, §15.2) = 4,800,000,000 B ≈ 4.8 GB index RAM at the object ceiling.
  2. Full re-encrypt wall clock, single core. 2 TB vault ceiling (§4) = 2,097,152 MB ÷ 150 MB/s AEAD throughput (M3) = 13,981 s ≈ 3.9 hours per core; parallelized across 8 DAG-independent-subtree workers ≈ 29 min, consistent with M10's ≥ 20 GB/hour/core aggregate target.
  3. Sync bandwidth, full device fleet. 32 devices (§4 ceiling) × 5 MB/device/day (M5) = 160 MB/day aggregate steady-state traffic across a single vault's device fleet.
  4. Argon2id attacker cost per guess. m=256 MiB, t=3, p=4 → 450 ms/derivation (§4, M4, RFC 9106 recommended parameters). Attacker cost per guess ≈ 256 MiB memory-time product + 450 ms compute. Brute-forcing a 40-bit-entropy passphrase space (2^40 ≈ 1.1×10^12 guesses) sequentially at 450 ms/guess = 1.1×10^12 × 0.45 s ≈ 4.95×10^11 s ≈ ~15,700 core-years — the memory-hardness (256 MiB/guess) additionally blocks cheap GPU/ASIC parallelism that a compute-only KDF would permit.
  5. Capability verification throughput. 1 ÷ 300 µs (M6 p50, single-threaded, cached issuer key) ≈ 3,333 verifications/s/core; batched/pipelined across cores meets M12's ≥ 5,000 verifications/s target with ≤ 2 cores at p50, headroom retained for p95's 1.2 ms tail.
  6. Recovery-share arithmetic. For the §14 worked example (N=5, M=3): given independent per-share loss probability p=0.05, P(lose ≥ 3 of 5) = C(5,3)p³(1-p)² + C(5,4)p⁴(1-p) + C(5,5)p⁵ = 10×(0.05)³×(0.95)² + 5×(0.05)⁴×(0.95) + (0.05)⁵ ≈ 0.001128 + 0.0000297 + 0.0000003 ≈ 0.00116, ~0.12% annual vault-loss probability under this share-loss model — the same threshold math (P10) bounds T9's collusion risk in the opposite direction (fewer shares required to reconstruct = easier collusion, MM7).
  7. Query index-entry byte budget cross-check. 96 B/entry (§15.2) × 1,000,000-object synthetic benchmark vault (§15.3) = 96 MB index RAM for the M2 latency-gate fixture — well under a reference laptop's working set, explaining why the M2 latency table is achievable without sharding at that scale.
  8. Relay padding overhead. A 4-bucket scheme (4 KB / 64 KB / 1 MB / 16 MB, §21) padding a uniformly distributed mix of object sizes in (0, bucket] yields an expected ~50% padding overhead per bucket in the worst case, averaging to roughly 30–40% aggregate bandwidth overhead across a realistic mixed workload — the T7 mitigation's bandwidth cost, traded against the M5 5 MB/device/day budget's headroom.

35. Hard Questions (Self-Examination)

  1. If a court order compels the owner to unlock the vault (T3, §24), does P10's threshold custody actually protect anything the owner personally holds all M shares of? (§24, §14)
  2. Does the pointer-register LWW merge (P8, §18) ever silently discard a concurrent write's intended meaning, even though the losing ObjectRef remains reachable — and would a user notice? (P8, §18)
  3. Why does twinadapt enforce scope at the retrieval layer instead of trusting the capability check alone (§20) — what specific I13 failure mode does the retrieval-layer redundancy close that verification alone does not? (I13, §20)
  4. Is the 25-year format-readability commitment (P4, §22) actually falsifiable before 25 years pass, or is it an unverifiable promise until it's tested by time? (P4, §22)
  5. Does federating relay traffic across operators (§21, §31) meaningfully reduce T7 risk if all federated relays are hosted by the same cloud provider's infrastructure? (T7, §31)
  6. What happens to a ConsentGrant's attenuation chain (P6, §20) if the root Capability it descends from is itself revoked mid-inference — does I4 propagate through the proof chain or only check the leaf? (I4, §20)
  7. Why is Argon2id's memory-hardness (M4, §34) sufficient against a well-funded adversary but not against a nation-state with custom memory-dense ASICs — where does the security margin actually come from? (M4, §34)
  8. Does the 90-day offline-tolerance ceiling (§4) interact badly with the recovery-share collusion window (T9, §34) — does a long-offline device's stale revocation set create a window an attacker could exploit? (§4, T9)
  9. Is the canary-object defense against prompt-injection exfiltration (§20, T11) itself detectable and avoidable by a sufficiently capable adversarial model that infers which objects are canaries from their access pattern? (T11, §20)
  10. Why does migration (§22) get a sanctioned exception to P3's immutability while nothing else does — is the exception narrow enough that it can't be abused as a precedent for other "just this once" mutability requests? (P3, §22)
  11. Does the dual-format read path (§22) introduce its own attack surface — could a malicious sync peer force a device to permanently prefer the old, weaker format during the Migrating window? (§22, T5)
  12. If redb (ADR-04) is abandoned upstream in 15 years, does the archived reference decoder (§22, P4) actually decouple from it, or only from its API, not its on-disk assumptions? (ADR-04, §22)
  13. Is the 5,000 verifications/s target (M12, §34) achievable without a shared issuer-key cache becoming a new single point of correctness — what happens to M12's throughput the instant the cache is cold? (M12, §17)
  14. Does the Shamir threshold's information-theoretic guarantee (P10, I5) survive a side-channel where the share-issuance process itself (timing, ordering) leaks which shares were issued to whom? (P10, §24)
  15. Why is capability caveat monotonicity (I13) checked at verification and not solely at issuance — what specific replay or collusion scenario (§24) does verification-time enforcement close that issuance-time enforcement alone would miss?
  16. Does the relay's connector-trigger scheduling (§21) leak information about a user's connector configuration (which sources exist) even though it never holds connector credentials? (§21, T7)
  17. If a twin's local inference model itself is later found to memorize training data, does P14's "consumer, not co-owner" framing (§20) actually prevent a distinct exfiltration vector unrelated to prompt injection? (P14, T11)
  18. Is the 32-device sync-fanout ceiling (§4, §31) a genuine architectural limit of the CRDT/capability design, or an arbitrary number that could be revisited without touching any invariant? (§4, §31)

36. Alternative Architectures (Roads Not Taken)

(a) Server-side encryption with a hosted HSM and conventional ACLs

User <--TLS--> App Server --keys--> HSM
                   |
                   v
              Encrypted DB (ACL rows)

Winning regime: enterprise deployments needing centralized audit and instant global-permission revocation via a single ACL table scan. Real embodying system: a typical SaaS backend with an AWS CloudHSM/KMS-backed encryption-at-rest layer. Rejected here because the server (and its ACL table) becomes the trust root — P1 and P2 both fail structurally the moment the HSM operator can decrypt on the owner's behalf.

(b) Blockchain/DID-anchored public index with off-chain blobs

DID Anchor (chain) --index--> Off-chain Blob Store
      ^                              |
      |________signed pointer________|

Winning regime: scenarios needing a globally auditable, censorship-resistant pointer registry independent of any single host. Real embodying system: IPFS/IPLD paired with an ENS-style DID anchor. Rejected here (also a stated non-goal, §1) because a public chain permanently leaks the existence and update cadence of a user's records even if payloads are encrypted — a metadata-leakage profile (T7) worse than an untrusted-but-private relay.

(c) Local-only vault, no sync, manual export

Device A: [vault] --manual export/import--> Device B: [vault]

Winning regime: a single-device, air-gapped use case where any network sync is itself an unacceptable attack surface. Real embodying system: a KeePass-style local password vault with manual file copy across devices. Rejected here because it fails the multi-device, ≤ 60 s revocation-propagation requirement (M7, §4) outright — offline-only can't propagate anything.

(d) Enclave-based confidential-compute twin instead of local inference

App --> Attested Enclave (SGX/SEV) --decrypt-in-enclave--> Model --> Result

Winning regime: a remote-inference need where local hardware cannot run the model at all, but the operator is untrusted. Real embodying system: confidential-computing offerings (e.g. Azure confidential VMs, AWS Nitro Enclaves) running attested inference workloads. Rejected as the default here because enclave attestation shifts trust to the chip vendor's root of trust and firmware supply chain (a new T8-class surface) instead of eliminating a remote trust dependency — it remains an available opt-in path under the existing remote_model reserved-caveat design (§20), never the default per P14.

38. Glossary

  • Vault — the complete, per-owner encrypted personal datastore (objects, index, keys, capability log, audit log).
  • Object ref (ObjectRef) — a 32-byte BLAKE3 digest of ciphertext, the sole address of a stored object (I2, P3).
  • Content address — an identifier derived from content itself (here, ciphertext), not chosen by the writer.
  • AEAD — authenticated encryption with associated data; here ChaCha20-Poly1305 or XChaCha20-Poly1305 (ADR-08).
  • Nonce — a per-encryption unique value; reuse under the same key breaks AEAD confidentiality (I6).
  • AAD — associated authenticated data; unencrypted but integrity-protected header fields (§8).
  • HKDF — HMAC-based key derivation function (RFC 5869); expands a master secret into per-purpose keys (§8).
  • Derivation path — the info-string identifying a specific HKDF expansion step (§8, §11).
  • Master key (MK) — the L0 root key derived from a passphrase or HSM-wrapped seed (§8).
  • Key wrapping — encrypting one key under another for storage (ADR-11).
  • Shamir share (RecoveryShare) — one polynomial-evaluation fragment of a Shamir secret-sharing split (P10, §11).
  • Threshold (M-of-N) — the minimum share count required to reconstruct a secret.
  • Capability — a signed, attenuable, time-bounded bearer credential granting scoped access (P2, §11).
  • Caveat — a restriction embedded in a capability, narrowing its scope (§8, §11).
  • Attenuation — deriving a narrower child capability from a parent, never broadening (P2, I13).
  • UCAN — User Controlled Authorization Networks, the capability token format used (ADR-12).
  • DID — Decentralized Identifier, the identity-anchor format for issuer/audience fields (ADR-13).
  • Ingest cursor (IngestCursor) — a per-source, monotonically advancing connector fetch position (I8, §11).
  • CRDT — Conflict-free Replicated Data Type; a merge structure with mathematically guaranteed convergence (§18).
  • Tombstone — a logical-delete marker superseding an object without physically erasing it (P3).
  • Twin adapter (twinadapt) — the in-process module running model inference over vault contents under consent (P14, §20).
  • Consent grant (ConsentGrant) — a Capability-shaped, revocable authorization for twin inference (P6, §11).
  • Audit entry (AuditEntry) — one hash-chained, append-only record of a read or inference event (I10, §11).
  • Relay — the untrusted store-and-forward hop between devices, ciphertext-only (P1, §21).
  • Merkle-DAG — a directed acyclic graph of content-addressed nodes, each referencing children by hash (§8).
  • Pointer register — an LWW, vector-clock-stamped mapping from a logical name to its current ObjectRef (P8, §8).
  • Vector clock — a per-replica counter set used to order concurrent events without a shared clock.
  • Connector — a WASM-sandboxed module implementing fetch(cursor) against a third-party data source (§8).
  • ConnectorSpec — the manifest declaring a connector's source, version, and required capabilities (§11).
  • Revocation set — the CRDT-replicated set of invalidated capabilities, checked at every verification (I4).
  • Argon2id — a memory-hard password-hashing/KDF algorithm (RFC 9106) used for master-key derivation (ADR-09).
  • X3DH — the Extended Triple Diffie-Hellman asynchronous key-agreement protocol (Signal docs), used for device pairing (§14).
  • Double Ratchet — a forward-secret session-key ratcheting algorithm (Signal docs), used for twin remote-inference sessions (§20).
  • Canary object — a decoy ObjectRef seeded to detect illegitimate retrieval or exfiltration (§20).
  • Verifiable Credential (VC) — a W3C-standardized, portable, signed claim format, used to export consent state (ADR-14, §20).
  • Format version — the byte tag identifying an EncryptedObject's on-disk/wire layout revision (I14).
  • Crypto agility — the design property that algorithm choice travels with data rather than being hardcoded (P12).
  • Reference decoder — a frozen, dependency-vendored implementation preserved for long-term format readability (P4, §22).
  • Migration — the sanctioned, checkpointed re-encryption of a vault from one format/algorithm to another (§22).
  • Lifecycle state — one of a vault's named operating modes: Provisioning, Active, Locked, Recovery, Migrating, Archived, Destroyed (§8).
  • Conformance suite — the CI-blocking assembly of the invariant simulator, fuzz corpora, KAT vectors, and performance gate (§23).
  • KAT (Known-Answer Test) — a fixed input/output vector pair used to verify a cryptographic primitive's correctness against a published standard.
  • Soak test — an extended-duration run (here, 72 hours) verifying stability and bounded resource growth under sustained load (§23).
  • SBOM — Software Bill of Materials, an inventory of build dependencies for supply-chain auditability (ADR-23).
  • Padding bucket — a fixed-size bin objects are rounded up into before transmission, to blur size-based metadata leakage (§21).
  • Blast radius — the scope of compromise or failure a single key, device, or credential leak can cause (P5).
  • Fail-closed — the design discipline of rejecting on ambiguity or unrecognized input, never default-permitting (I13).
