⬜ Phase 0 — Skeleton, Crypto Core & CI §12

Objectives
  • Stand up the 11-crate Cargo workspace (ADR-01, ADR-02).
  • Implement the crypto core: AEAD (ADR-08), HKDF (ADR-10), Argon2id (ADR-09) wrappers.
  • Wire CI (ADR-21) with a fuzz-job stub (ADR-20).
  • Establish the EncryptedObject format skeleton (§8) without persistence.
Deliverable

cargo build --workspace succeeds; cargo test --workspace passes; CI green on a clean clone; objstore::format encode/decode round-trips a synthetic EncryptedObject byte-identical.

Acceptance
  • 100% of RFC 8439 KAT vectors pass (chacha20poly1305_kat.txt).
  • 100% of RFC 9106 Argon2id KAT vectors pass (argon2id_kat.txt).
  • HKDF output matches RFC 5869 test vectors (hkdf_kat.txt).
  • CI pipeline completes in ≤ 6 min wall clock.
  • Zero clippy warnings at -D warnings.
Fixtures
  • chacha20poly1305_kat.txt — RFC 8439 known-answer vectors; expected ciphertext+tag match.
  • argon2id_kat.txt — RFC 9106 known-answer vectors; expected derived-key match.
  • hkdf_kat.txt — RFC 5869 known-answer vectors.
  • format_roundtrip.bin — synthetic EncryptedObject; encode→decode byte-identical.
  • format_malformed_header_len.bin — header_len exceeding buffer; expects reject.
Pitfalls
  • Treating Argon2id parameters as a compile-time constant instead of a versioned, embeddable set — breaks P12's crypto agility if parameters must change; manifests as an unmigratable vault; debug by grepping for hardcoded Argon2 params outside keyring::hierarchy; recover by embedding a params struct in the vault manifest.
  • Conflating ChaCha20-Poly1305's 12-byte nonce with XChaCha20-Poly1305's 24-byte nonce in the byte layout — manifests as decode panics; detected by KAT-vector length assertions; recovered by branching strictly on algo_id.
  • CI caching a stale cargo-deny lockfile across runs, masking a newly vulnerable dependency (T8) — detected by a scheduled (not only PR-triggered) cargo-deny check; recovered by cache-busting on lockfile hash change.

⬜ Phase 1 — Local Encrypted Object Store §13

Objectives
  • Implement objstore persistence: writes commit to redb (ADR-04), content-addressed by ObjectRef (I2).
  • Enforce nonce uniqueness (I6) via a counter-plus-random-prefix nonce generator.
  • Implement tombstone-based logical delete (P3).
Deliverable

A CLI-invokable objstore that ingests a directory of files, writes them as EncryptedObjects, and reads them back byte-identical; nonce uniqueness held under 100,000 sequential writes.

Acceptance
  • 100,000 writes, zero nonce collisions (nonce_stress.bin, I6).
  • AEAD throughput ≥ 150 MB/s/core measured by benchmarks/aead_throughput.rs (M3).
  • Crash-injected write (kill -9 mid-transaction) recovers to last-committed state within the 15 min RTO bound (§4).
  • Tombstoned-object read returns a VaultError variant distinguishing "deleted" from "not found".
Fixtures
  • nonce_stress.bin — 100k sequential writes; expects zero I6 violations.
  • crash_mid_write.script — kills the process mid-transaction; expects clean WAL replay.
  • tombstone_roundtrip.bin — write, tombstone, read; expects "deleted" not "not found".
  • hash_mismatch_replay.bin — corrupted ciphertext with a stale ObjectRef; expects I2 rejection.
Pitfalls
  • Reusing a nonce counter across process restarts without persisting the checkpoint — manifests as an I6 violation under a crash loop; root cause: counter reset to 0; debug via nonce_reuse_detected_total; recovery: force key rotation for the affected KeyHandle (FM-1).
  • Treating tombstones as physical deletes — manifests as broken Merkle-DAG parent references (§8) when a referenced child is gone; debug via a DAG-integrity scan; recovery: never physically delete before an explicit GC epoch (I9-adjacent).
  • Unbounded redb transaction size during bulk ingest — manifests as a memory spike during Phase 4 connector ingest; debug via a transaction-size histogram; recovery: batch commits per N objects.

⬜ Phase 2 — Key Hierarchy & Recovery §14

Objectives
  • Implement the full HKDF derivation chain L0→L3 (§8).
  • Implement Shamir secret sharing for RecoveryShare issuance/reconstruction (P10; Shamir 1979).
  • Implement key rotation with re-wrap (I11).
Deliverable

A CLI tool issuing N=5, M=3 recovery shares for a test vault and reconstructing MK from any 3; a rotation drill re-wrapping 10,000 object keys with zero I11 violations.

Acceptance
  • Reconstruction succeeds from all 10 of C(5,3) share combinations (shamir_recon.bin).
  • Reconstruction from 2 shares yields provably zero information (shamir_below_threshold.bin, P10).
  • Key rotation re-wraps 10,000 object keys in ≤ 90 s wall clock, zero rotation_incomplete_total (I11).
  • Argon2id-derived MK matches the §4 450 ms target ± 50 ms on reference hardware.
Fixtures
  • shamir_recon.bin — all 10 combinations of 3-of-5 shares; expects correct MK reconstruction.
  • shamir_below_threshold.bin — 2-of-5 shares; expects the zero-information property holds.
  • rotation_drill.bin — 10k objects, full rotation; expects zero incomplete re-wraps.
  • hkdf_derivation_chain.bin — L0→L3 derivation; expects match against RFC 5869 vectors composed per §8.
Pitfalls
  • Naive XOR-based "secret sharing" instead of Shamir's polynomial scheme — manifests as partial-information leakage below threshold, violating P10; detected by an entropy property test; recovery: replace with GF(256) Shamir.
  • Rotating a collection key without re-wrapping every derived object key first (I11) — manifests as orphaned ciphertext, unreadable after old-key destruction; root cause: rotation state machine skipped a checkpoint; debug via rotation_incomplete_total; recovery: halt destruction, resume from last checkpoint.
  • Deriving L2 object keys directly from MK instead of via CK_i — manifests as a P5 blast-radius violation; debug via derivation-path audit; recovery: re-derive strictly through the hierarchy.

⬜ Phase 3 — Index & Query §15

Objectives
  • Build indexer's inverted index and metadata B-tree over decrypted-in-memory records; the index never persists plaintext (P11, I1).
  • Implement a query planner/executor meeting the §4 latency targets.
Deliverable

A query CLI answering point and range queries against a 1M-object synthetic vault within the §4 latency table, with capability-filtered results matching a known-answer expected set.

Acceptance
  • Point-lookup p50/p95/p99 ≤ 8 ms/40 ms/120 ms on a 1M-object index (query_1m_point.bin, M2).
  • Range/FTS query p50/p95/p99 ≤ 25 ms/90 ms/250 ms (query_1m_range.bin).
  • Cold index rebuild from objstore completes in ≤ 90 s for 1M objects (index_rebuild_cold.bin).
  • Zero results returned for an out-of-scope ObjectRef (query_scope_leak.bin).
Fixtures
  • query_1m_point.bin — 1M-object synthetic vault; point-lookup latency histogram.
  • query_1m_range.bin — same vault; range/FTS latency histogram.
  • query_scope_leak.bin — adversarial query for out-of-scope ObjectRefs; expects zero leakage.
  • index_rebuild_cold.bin — full rebuild timing fixture.
Pitfalls
  • Filtering capability scope only at query-planning time, not per returned row — manifests as a scope leak when a plan later widens; detected by query_scope_leak.bin; recovery: enforce I3 at row-emission time.
  • Persisting index entries with plaintext metadata "for speed" — an I1 violation, silent until a disk forensic audit; detected by the boundary-crossing fuzzer (§23); recovery: purge and rebuild index in-memory-only.
  • Unbounded index growth without eviction near the 50M-object ceiling (§4) — manifests as OOM; detected by index-RAM monitoring; recovery: sharded index (§31).

⬜ Phase 4 — First Connector & Ingest Cursors §16

Objectives
  • Implement the connectors WASM sandbox runtime (ADR-17) hosting a first real connector.
  • Implement IngestCursor persistence and monotonicity (I8).
  • Implement an OAuth 2.0 (RFC 6749) handshake for third-party source auth.
Deliverable

photos-v1 ingests a 10,000-record mock library end-to-end into objstore; the cursor advances monotonically; a replayed fetch produces zero duplicate ObjectRefs.

Acceptance
  • 10,000-record ingest completes at ≥ 40 MB/s sustained (M1).
  • Replay of an already-committed cursor produces zero new ObjectRefs (connector_replay_dedup.bin).
  • Cursor-drift fixture (connector_cursor_drift.bin) is detected and halted per I8, never silently ingested.
  • OAuth token refresh succeeds per section 6 of RFC 6749 without user re-consent inside the token's validity window.
Fixtures
  • connector_replay_dedup.bin — replay the same cursor twice; expects zero duplicate ObjectRefs.
  • connector_cursor_drift.bin — out-of-order cursor delivered; expects I8 rejection and connector halt.
  • connector_rate_limit_burst.bin — burst exceeding the token bucket; expects throttling, not failure.
  • connector_oauth_refresh.bin — expired access token, valid refresh token; expects transparent refresh.
Pitfalls
  • Content-addressing over a payload that embeds a fetch timestamp — defeats P9 idempotency; manifests as duplicate ObjectRefs on replay; debug by diffing AAD across "duplicate" objects; recovery: strip the timestamp from the content-addressed payload, carry it in a separate mutable index field.
  • WASM host granting the sandbox a capability broader than ConnectorSpec.capabilities_required — manifests as a connector "phoning home" or reaching a different collection; debug via a capability-scope audit; recovery: least-privilege capability re-derivation.
  • OAuth refresh token stored unwrapped alongside connector code — manifests as T4 (connector token theft); debug via a keyring boundary audit; recovery: move token custody into a dedicated wrapped KeyHandle.

⬜ Phase 5 — Capability Issuance & Verification §17

Objectives
  • Implement capd issuance (UCAN, ADR-12) and the verification pipeline (§8's seven steps).
  • Implement DID-based issuer/audience (ADR-13) and revocation-set lookup (I4).
Deliverable

An issuance+verification CLI round trip: issue a Capability, attenuate it twice (narrower caveats each time), verify the attenuated chain, then revoke and verify rejection.

Acceptance
  • Verification p50/p95 ≤ 300 µs/1.2 ms for a cached issuer key (M6, §4).
  • An attenuation chain of depth 3 verifies correctly in 100% of capability_chain_valid.bin cases.
  • A revoked capability replay is rejected in 100% of capability_replay.bin cases (I4).
  • A clock-skew fixture within ± 5 min tolerance is accepted; beyond ± 5 min it is rejected (capability_clock_skew.bin).
Fixtures
  • capability_chain_valid.bin — depth-3 attenuation chain; expects valid verification.
  • capability_replay.bin — revoked-then-replayed capability; expects rejection (I4).
  • capability_clock_skew.bin — exp/nbf under varying skew; expects accept within tolerance, reject beyond.
  • capability_unknown_caveat.bin — an unrecognized Caveat variant; expects fail-closed rejection (I13).
Pitfalls
  • Verifying only the leaf capability's signature, not the full proof chain to a trusted root — manifests as a forged mid-chain attenuation passing verification; debug via a chain-walk audit; recovery: enforce recursive verification to root.
  • Accepting an unrecognized Caveat variant as "no restriction" (fail-open) instead of rejecting — directly violates I13; debug via caveat_unenforced_total; recovery: default-deny unknown variants.
  • Caching issuer keys without a grace-period boundary — manifests as legitimate capabilities rejected immediately after issuer key rotation; debug via a capability_sig_failures_total spike correlated with the rotation event; recovery: grace-period key cache (I7).

⬜ Phase 6 — Multi-Device Sync & CRDT Merge §18

Objectives
  • Implement syncd's Automerge integration (ADR-15) for structured metadata and the pointer-register merge (P8) for binary objects.
  • Implement QUIC transport (ADR-06) to relay, ciphertext-only.
Deliverable

Two simulated devices converge on an identical CRDT document and pointer-register state after a scripted sequence of concurrent, offline-then-reconnected edits.

Acceptance
  • CRDT convergence: 100% state equality across devices after merge (sync_convergence_concurrent.bin).
  • Pointer-register conflict resolved deterministically, same winner on both devices (sync_pointer_conflict.bin).
  • Sync bandwidth ≤ 5 MB/device/day steady-state under the scripted workload (M5, §4).
  • A reconnect-after-90-day-offline fixture triggers a full resync per the offline-tolerance ceiling (§4).
Fixtures
  • sync_convergence_concurrent.bin — concurrent edits on 2 devices; expects convergent state.
  • sync_pointer_conflict.bin — concurrent pointer updates; expects a deterministic LWW winner plus a reachable loser.
  • sync_replay_idempotent.bin — duplicate SyncOp delivery; expects apply-twice = apply-once (I12).
  • sync_offline_90d.bin — device offline 90 days; expects a forced full resync, never silent data loss.
Pitfalls
  • Attempting CRDT merge over encrypted binary payloads directly — either impossible or a confidentiality bug (P8); debug via a merge-path type audit; recovery: route binary objects exclusively through the pointer register.
  • Unbounded Automerge op-log growth without periodic compaction (FM-3) — manifests as steadily increasing sync bandwidth beyond M5; debug via op-log size trend; recovery: a scheduled compaction epoch plus tombstone GC (I9).
  • Treating relay as authoritative for merge order — a hidden centralization violating P7; debug via a relay-outage drill showing devices still converge peer-to-peer once reconnected; recovery: merge order derived from vector clocks, never relay arrival order.

⬜ Phase 7 — Revocation & Audit Log §19

Objectives
  • Implement full capability-revocation propagation (P13; RFC 7009 conceptual parallel) and the hash-chained auditlog (I10).
Deliverable

A revocation drill: revoke a capability, observe propagation to 5 simulated online devices within 60 s, and immediate enforcement at a 6th device's reconnect after being offline; an auditlog chain-verification pass over 100,000 entries.

Acceptance
  • Revocation visible to all online devices within 60 s p99 (M7, §4).
  • An offline device enforces revocation synchronously at reconnect, independent of offline duration (P13).
  • auditlog chain verification over 100,000 entries completes with zero auditlog_chain_break_total.
  • A deliberately corrupted chain entry is detected within one scan cycle (auditlog_tamper.bin).
Fixtures
  • revocation_propagation_5device.bin — 5 online devices; expects ≤ 60 s propagation.
  • revocation_reconnect_offline.bin — device offline then reconnecting; expects synchronous enforcement.
  • auditlog_chain_100k.bin — 100k-entry chain; expects zero verification breaks.
  • auditlog_tamper.bin — deliberately altered mid-chain entry; expects detection.
Pitfalls
  • Propagating revocation only via periodic relay polling — manifests as propagation delay exceeding M7 under low poll frequency; debug via a propagation-latency histogram; recovery: push-based revocation over the QUIC channel (ADR-06), polling only as fallback.
  • Appending to auditlog without holding a write lock across the hash-chain update — manifests as a race producing two entries with the same prev_hash (a silent fork); debug via chain-fork detection in the scan job; recovery: serialize appends through a single-writer actor.
  • An auditlog compaction/retention policy dropping entries needed for a chain-verification scan — manifests as false-positive chain breaks; debug via a retention-policy audit; recovery: chain-verification-aware retention, never drop below the last verified checkpoint.

⬜ Phase 8 — Twin Adapter & Consent Protocol §20

Objectives
  • Implement twinadapt's in-process consent-checked query + inference pipeline (P6, P14, §8's seven-step protocol).
  • Implement ConsentGrant issuance/verification as an attenuated Capability (P2, P6, I13) with a reserved CollectionScope("remote-inference") caveat gating any non-local backend.
  • Represent exportable consent as a W3C Verifiable Credential (ADR-14) for cross-device audit portability.
  • Harden the retrieval path against prompt-injection exfiltration via hard scope enforcement plus canary detection.
Deliverable

examples/consent_flow (§10): issue a ConsentGrant scoped to one collection; invoke local_model successfully; attempt remote_model without the reserved caveat (rejected); reissue with the caveat and complete a ratcheted remote_model call; export the grant as a VC and verify it externally.

Acceptance
  • local_model inference latency p50/p95 ≤ 250 ms / 900 ms for a 4k-token context on reference hardware (M8).
  • Zero out-of-scope content returned across 10,000 fuzzed prompt-injection payloads (twin_scope_fuzz.bin).
  • Canary-exfiltration detection rate 100% across twin_prompt_injection_canary.bin's adversarial corpus.
  • remote_model invocation without the reserved caveat rejected in 100% of twin_remote_caveat_missing.bin cases (I13).
  • Exported VC round-trips through an external W3C VC verifier without error (twin_vc_export_roundtrip.bin).
Fixtures
  • twin_consent_issue.bin — issue + attenuate a ConsentGrant twice; expects narrowing-only attenuation (I13).
  • twin_scope_fuzz.bin — 10,000 fuzzed prompts attempting scope escape; expects zero leakage.
  • twin_prompt_injection_canary.bin — poisoned ingested content instructing exfiltration; expects canary detection before return.
  • twin_remote_caveat_missing.bin — remote_model call lacking the reserved caveat; expects rejection.
  • twin_vc_export_roundtrip.bin — VC export/import cycle; expects byte-stable claims and valid external verification.
Pitfalls
  • Enforcing scope only at the prompt-construction step instead of the retrieval layer — a prompt-injected follow-up request can still walk past a prompt-level filter; manifests as twin_scope_fuzz.bin failures; debug via retrieval-layer trace; recovery: filter every retrieved record against caveats before it ever reaches the model context.
  • remote_model silently used as a fallback when local_model is unavailable, bypassing the reserved-caveat check — manifests as an unconsented remote call; debug via twin_scope_rejections_total gaps; recovery: fail closed, never auto-escalate backend.
  • Canary objects swept up by routine tombstone GC (I9), silently losing detection coverage over time — debug via canary-population count drift; recovery: exempt canaries from the standard GC epoch.
  • Consent-grant attenuation implemented as freestanding reissuance instead of a proof-chain child — permits scope creep (T11-adjacent, FM-9); debug via chain-monotonicity fuzzer; recovery: require every attenuated grant to carry its parent in proof.
  • Double Ratchet session desync after a twinadapt process restart causing transport decrypt failure on the next remote call — debug via ratchet-state audit; recovery: reinitiate the X3DH handshake (§14) for that session.

⬜ Phase 9 — Relay & Self-Host Deployment §21

Objectives
  • Implement relay::forward's ciphertext-only store-and-forward (P1) and relay::schedule's connector-trigger scheduling.
  • Package a self-host deployment: static musl binaries in a distroless container (ADR-22), a docker-compose.yml dev/self-host stack (§10).
  • Minimize relay-observable metadata leakage (T7) via size-bucket padding and batched delivery windows.
Deliverable

A self-hosted docker-compose.yml stack forwarding SyncOp/EncryptedObject batches among 3 simulated devices, with a packet capture confirming zero plaintext on the wire and a statistical size-distribution test confirming padding-bucket indistinguishability across content types.

Acceptance
  • Relay forwarding throughput ≥ 200 MB/s per instance on reference hardware (M9).
  • Zero plaintext bytes observed in a full-session tcpdump capture (relay_plaintext_leak.bin).
  • Padding-bucket size distribution statistically indistinguishable (chi-square test, p > 0.05) across photo/text/metadata object classes (relay_metadata_padding.bin).
  • A 2-relay federation split leaves no single relay observing > 50% of one device's traffic (relay_federation_split.bin).
  • Unacked blobs purge exactly at TTL, never before (relay_ttl_expiry.bin).
Fixtures
  • relay_forward_roundtrip.bin — 3-device forwarding drill; expects correct delivery, zero data loss.
  • relay_plaintext_leak.bin — full-session packet capture; expects zero plaintext bytes.
  • relay_metadata_padding.bin — mixed content-type batch; expects statistically indistinguishable padded sizes.
  • relay_federation_split.bin — 2-relay federated routing; expects ≤ 50% traffic-share visibility per relay.
  • relay_ttl_expiry.bin — one device never acks; expects purge exactly at TTL boundary.
Pitfalls
  • Unpadded object sizes leaking content-type via size correlation (a photo-sized blob is distinguishable from a note) — a T7 manifestation; debug via the padding-distribution audit; recovery: coarsen the bucket set.
  • Relay logging fine-grained timestamps that enable cross-device traffic-analysis correlation — debug via a log-field audit against §26's privacy-preserving logging policy; recovery: coarsen logged timestamps to bucket granularity, drop per-connection detail beyond aggregate counters.
  • Container running as root inside the distroless image, widening the blast radius of a relay compromise (T1) — debug via an image-scan policy check; recovery: enforce a non-root USER directive in Dockerfile.
  • TTL purge racing a slow-reconnecting device, deleting a blob it hasn't yet acked — manifests as a silent sync gap indistinguishable from "not yet delivered"; recovery: TTL must exceed the §4 90-day offline-tolerance ceiling's short-term case, or the device forces a full resync (§4) instead of assuming loss.
  • Naive round-robin "federation" across relays operated by the same entity, which defeats the confidentiality benefit despite nominal multi-relay routing — recovery: require federation partners to be independently operated for the T7 mitigation to hold.

⬜ Phase 10 — Format Durability & Migration Tooling §22

Objectives
  • Implement tools/vault-migrate (§10): a full-vault re-encrypt/format-migration CLI honoring crypto agility (P12, I14).
  • Maintain an archived, dependency-frozen reference decoder satisfying the 25-year readability commitment (P4, §4).
  • Implement the dual-format read path for the Migrating lifecycle state (§8).
Deliverable

vault-migrate migrates a 100,000-object v1 vault to a v2 format (new algo_id) with byte-identical recovered plaintext, resumable after a simulated crash at the 50% checkpoint, verified against the archived v1 decoder as ground truth.

Acceptance
  • 100,000-object migration completes with zero plaintext mismatches against the pre-migration corpus (migrate_v1_to_v2_100k.bin).
  • Crash-resume at 50% reprocesses zero already-migrated objects (migrate_crash_resume.script).
  • The archived v1 decoder decodes a frozen migrate_kat_v1_decode.bin vector correctly, independent of the live crate's current dependency versions.
  • Full-vault migration throughput ≥ 20 GB/hour per core (M10).
  • Old key destruction blocked until all registered devices ack (migrate_dual_read_path.bin exercises the dual-format window).
Fixtures
  • migrate_v1_to_v2_100k.bin — full 100k-object migration; expects byte-identical plaintext recovery.
  • migrate_crash_resume.script — kill mid-migration at 50%; expects clean checkpoint resume, zero reprocessing.
  • migrate_kat_v1_decode.bin — frozen v1 KAT vector; expects the archived decoder reproduces canonical plaintext.
  • migrate_pointer_rewrite.bin — DAG with diamond references; expects every parent_ref updated exactly once, no orphans.
  • migrate_dual_read_path.bin — mixed v1/v2 objects mid-migration; expects transparent version-dispatched reads.
Pitfalls
  • Re-encrypting objects without atomically updating their parent_ref/pointer-register entries — manifests as a broken Merkle-DAG post-migration, the migration-time analogue of §13.6's tombstone pitfall; debug via a DAG-integrity scan; recovery: wrap re-encrypt + pointer-rewrite in one transaction.
  • No durable migration checkpoint, so a crash forces a full restart-from-zero — manifests as unbounded migration wall-clock on a 2 TB vault (§34); debug via checkpoint-hash absence; recovery: checkpoint every N-object batch (mirrors I11's rotation checkpointing).
  • Archived reference decoder silently linking against the live crate's current ciborium/HKDF versions instead of a vendored, frozen copy — defeats P4's 25-year commitment the moment that live crate has a breaking change; debug via a dependency-graph audit of the archived decoder; recovery: vendor-freeze its dependencies at migration-authoring time.
  • Destroying the old key before every device has acknowledged migration — a device that hasn't migrated yet loses readability entirely; debug via the device-ack completeness gauge; recovery: never destroy before 100% ack (I11-style discipline, FM-12).
  • KAT vectors regenerated from the new implementation rather than preserved from the original — validates self-consistency, not correctness, silently masking a decode regression; recovery: pin KAT ground truth to the original implementation's output at authoring time.

⬜ Phase 11 — Conformance Suite & Performance Hardening §23

Objectives
  • Assemble the full I1–I14 deterministic simulator (§7) into a CI-blocking conformance suite (ADR-21).
  • Extend the fuzz targets (objstore_decode.rs, capd_verify.rs, §10) and freeze a KAT vector suite for the AEAD (RFC 8439) and KDF (RFC 9106).
  • Wire a performance-regression gate across all M1–M12 targets (§30) into CI.
Deliverable

A single make conformance target running the full sim (I1–I14), the fuzz corpora, the KAT suite, and the performance-regression gate, exiting non-zero on any invariant violation, KAT mismatch, or performance regression beyond tolerance.

Acceptance
  • Full I1–I14 simulator run: zero violations across 1,000,000 scripted steps (conformance_full_sim.bin).
  • KAT suite: 100% match against RFC 8439/RFC 9106 published vectors (kat_aead.bin, kat_kdf.bin).
  • Both fuzz corpora run 1,000,000 iterations each with zero unexpected panics.
  • 72-hour soak completes with zero invariant violations and < 1% resident-memory growth (soak_72h.script).
  • Performance gate fails CI if AEAD throughput regresses below 140 MB/s/core (a 5% tolerance under M3's 150 MB/s target) or any M8–M12 target regresses beyond its stated tolerance (perf_regression_gate.bin).
Fixtures
  • conformance_full_sim.bin — 1M-step scripted fault-injection run; expects zero I1–I14 violations.
  • kat_aead.bin — RFC 8439 ChaCha20-Poly1305 vectors; expects exact match.
  • kat_kdf.bin — RFC 9106 Argon2id vectors; expects exact match.
  • soak_72h.script — 72-hour multi-device workload; expects zero invariant violations, bounded memory growth.
  • perf_regression_gate.bin — replays the M1–M12 benchmark suite; expects all targets within tolerance.
Pitfalls
  • A stale, never-minimized fuzz seed corpus creates false confidence — it stops discovering new bug classes; debug via coverage-plateau detection; recovery: scheduled corpus-minimization and coverage-guided reseeding (fuzz.yml, §10).
  • KAT vectors sourced only from the project's own implementation instead of the RFC's published vectors validates self-consistency, not correctness; recovery: pin to RFC 8439/9106 ground truth, never regenerate from the implementation under test.
  • A performance-regression tolerance set too loose (e.g. 50%) never fires, letting regressions creep in across many small PRs; recovery: tighten the band, add a trend dashboard (§26) alongside the hard CI gate.
  • Soak testing on idle/non-representative hardware misses realistic memory growth under load; recovery: soak against the same reference-hardware profile used for the §4 targets.
  • The sim harness logging a caught invariant violation and continuing, rather than hard-failing — silently turns a conformance breach into a passing CI run; recovery: any I1–I14 violation must abort the run non-zero, per §7's original methodology.
