Decisions (§9) · 31 ADRs

ADR-01

Implementation language

Chosen

Rust (edition 2021, MSRV pinned)

Rejected

C, C++, Go, Python

When the rejected choice is right

C wins when linking into a C ABI render-farm with zero Rust toolchain deployment budget; Python wins for quick single-page batch scripts where correctness > performance

Why: Memory safety on hostile input; C-class raster speed; fuzzing tooling

ADR-02

Project structure

Chosen

Cargo workspace, one crate per subsystem

Rejected

single monolith crate

When the rejected choice is right

Monolith wins when the team is 1 person with zero subsystem boundary discipline and compile time is the bottleneck

Why: Independent fuzz targets, faster incremental builds, clear ownership boundaries

ADR-03

Dependency policy

Chosen

Minimal; vendor/own codecs; audited crates only

Rejected

freely pull crates

When the rejected choice is right

Freely pulling crates wins in a rapid-prototype context where time-to-market outweighs supply-chain risk and the deployment is not internet-facing

Why: Each dep is attack surface; codecs are the CVE epicenter — own or audit them

ADR-04

Source access

Chosen

mmap (memmap2) + &[u8] slices; zero-copy

Rejected

read whole file into Vec

When the rejected choice is right

Heap-load wins for tiny (<1 MB) PDFs in a WASM environment where mmap is unavailable

Why: Random-access by offset; avoid huge heap allocs for 200 MB+ files

ADR-05

Lexer strategy

Chosen

Byte-oriented, zero-copy slices, no regex

Rejected

char/string-based, regex

When the rejected choice is right

Regex wins for a quick one-off text-extraction script where correctness matters only for well-formed ASCII PDFs

Why: Speed + no UTF-8 assumptions (PDF tokens are bytes); regex too slow/unsafe for binary

ADR-06

Object cache

Chosen

Lazy resolve, HashMap<ObjId,Object> + LRU eviction

Rejected

eager parse all objects

When the rejected choice is right

Eager parse wins for a small embedded device parsing the same 10-object PDF repeatedly where startup latency matters and memory fits

Why: Open huge docs fast; bounded memory

ADR-07

Xref strategy

Chosen

Classic table + xref stream + ObjStm + scan-rebuild

Rejected

trust one form only

When the rejected choice is right

Trusting only the classic table wins for an archival ingestor processing only known-well-formed ISO-32000-certified outputs

Why: Real corpus needs all four; rebuild is mandatory for in-the-wild files

ADR-08

Filter pipeline

Chosen

Hardcoded per-filter wins when there is exactly one filter and dispatch overhead is measured on an embedded processor

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1 — Process-Sandbox Architecture (PDFium / Chromium model)

 Browser Process           Renderer Process (sandboxed)
 ┌─────────────┐           ┌──────────────────────────────┐
 │ Action host │ ←IPC────► │  pdfcore (parse + render)    │
 │ JS sandbox  │           │  C ABI / Skia GPU raster     │
 │ UI / nav    │           │  Seccomp / pledge filter     │
 └─────────────┘           └──────────────────────────────┘

Regime where it wins: Interactive browser PDF viewers needing JavaScript action execution, form filling, annotation editing, and GPU-accelerated rendering at 60 fps. The sandbox provides memory-safety guarantees that compensate for C++ usage.
Real system: PDFium inside Chromium — every Chrome tab rendering a PDF uses this exact architecture.
Why rejected here: This blueprint targets an embeddable render library and a batch render farm. There is no browser process, no GPU requirement, and no interactive actions needed. The sandbox overhead (IPC marshaling, process spawn) adds latency incompatible with M5–M7 targets. Refuse-by-construction (ADR-31) eliminates the need for a separate action sandbox.

Alt-2 — Streaming, Single-Pass Parser (SAX-style)

 PDF bytes
    │
    ▼
  streaming
  tokenizer ──► object handler callbacks ──► direct render pipeline
    │            (no xref-driven                (no lazy resolve,
    │             random access)                 no object graph)
    ▼
  EOF

Regime where it wins: Ultra-low-memory embedded environments (printers, e-readers) processing linearized PDFs front-to-back where random access is unavailable and memory is measured in KB, not MB. Works correctly only for well-formed linearized PDFs.
Real system: Some embedded PDF viewers in laser printers (e.g., PCL/PDF firmware stacks) use a single-pass architecture for linearized PDFs, resolving only the first page before the rest of the file arrives.
Why rejected here: The vast majority of real-world PDFs are not well-formed linearized PDFs. Random access via xref is required for: resolving /Length references, incremental updates (the newest definition is at the end), any object referenced before it appears in file order. A single-pass design degrades to a full rebuild for these files — the common case.

Alt-3 — GPU-Accelerated Rasterizer (Skia / wgpu model)

 Content interpreter
        │
        ▼
   Display list           GPU pipeline
   ┌──────────────┐       ┌────────────────────────────────┐
   │ draw_path()  │──────►│  vertex shader → fragment      │
   │ draw_glyph() │       │  MSAA coverage                 │
   │ draw_image() │       │  blend on GPU framebuffer      │
   └──────────────┘       └────────────────────────────────┘

Regime where it wins: Interactive PDF viewers rendering at > 30 fps with complex vector content (technical drawings, architectural plans), where GPU parallelism delivers 10–100× rasterization throughput vs CPU scanline. Also wins for MSAA anti-aliasing quality at high DPI.
Real system: PDFium's Skia backend in Chromium; Foxit's GPU renderer. Skia itself powers Flutter's PDF rendering.
Why rejected here: The deployment target is a server-side batch render farm and an embeddable library, not an interactive viewer. GPU is not available in the server context. GPU rasterization introduces non-determinism (driver-dependent AA, floating-point coverage) that breaks the determinism invariant (§4.4, MM6). GPU rendering is registered as PhaseDeferred("FINAL_BLUEPRINT §appendix") for a future interactive-viewer phase.

Alt-4 — PostScript Interpreter Backend

 PDF content stream
        │
        ▼
   PDF→PS transpiler         PostScript interpreter
   ┌────────────────┐        ┌─────────────────────────────┐
   │ content ops →  │───────►│  full Ghostscript PS engine │
   │ PS equivalents │        │  imaging model              │
   └────────────────┘        └─────────────────────────────┘

Regime where it wins: When an existing, battle-tested PostScript interpreter (Ghostscript) is already deployed and the primary goal is correctness of output for print production, not performance. PDF is a restricted PostScript dialect; a PS engine can, in principle, handle any conforming PDF by translation.
Real system: Ghostscript's pdf2ps pipeline (deprecated in favor of its native PDF interpreter, but historically dominant for prepress). Some RIPs in commercial printers use this approach.
Why rejected here: PDF is not PostScript. PDF 1.4+ transparency, xref streams, CID fonts, and AES encryption have no PostScript equivalents — the transpiler would need to implement all of PDF anyway. Ghostscript is a C program with its own CVE history. The translation layer adds latency and loses the ability to lazy-resolve PDF objects. This design builds the PDF engine directly, preserving lazy resolution, bounded resources, and Rust memory safety throughout.
