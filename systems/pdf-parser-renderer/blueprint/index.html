386 — PDF Parser + Renderer from Scratch

Project Number: 386 Project Name: PDF Parser + Renderer from Scratch Owner: Mujir Qureshi Document: FINAL_BLUEPRINT.md Status: specification — locked

1. Goal

1.1 What is built

A library + CLI that parses, resolves, interprets, and rasterizes PDF documents end-to-end, from raw bytes to RGBA bitmaps, with no external PDF engine.

  • File-structure parse → header, body, cross-reference (xref), trailer, startxref, %%EOF; incremental updates; linearization-aware.
  • COS object model → all 9 object kinds (null, bool, int, real, string, name, array, dict, stream) + indirect references; lazy object graph keyed by (num,gen).
  • Xref resolution → classic 20-byte tables, PDF 1.5 xref streams, object streams (ObjStm), /Prev chains, hybrid-reference files, scan-rebuild on corruption.
  • Filter/codec pipeline → FlateDecode (+ PNG/TIFF predictors), LZWDecode, ASCII85Decode, ASCIIHexDecode, RunLengthDecode, DCTDecode (baseline JPEG), CCITTFaxDecode (G3/G4).
  • Content-stream interpreter → postfix operator machine over a graphics-state stack (CTM, clip, color, text state); path/text/image/XObject operators.
  • Rasterizer → scanline polygon fill (non-zero + even-odd winding), stroking (width/cap/join/dash), anti-aliasing via signed-area coverage; shared engine with #385 TrueType rasterizer.
  • Text engine → simple fonts (Type1/TrueType/Type3), composite fonts (Type0/CID), encodings + /Differences, CMaps, /ToUnicode, Standard-14 metrics.
  • Image pipeline → image XObjects, inline images, image masks, soft masks (/SMask), color-key masking.
  • Page compositor → alpha, separable blend modes, background flatten → page bitmap.

1.3 Explicit non-goals

  • NOT a PDF editor/writer beyond optional incremental save (PhaseDeferred("FINAL_BLUEPRINT §24.10")). No content authoring.
  • NOT a JavaScript/launch-action executor — /JS, /JavaScript, /Launch, /OpenAction, /SubmitForm, /ImportData, /URI actions are parsed but never executed (security policy, §6, Threat Model). Refused by default.
  • NOT a PDF/A or PDF/UA validator — no conformance-level certification (PhaseDeferred("FINAL_BLUEPRINT §appendix")). Rendering only.
  • NOT AcroForm/XFA interactive forms beyond rendering existing field appearance streams. Field recalculation, XFA template rendering deferred (PhaseDeferred("FINAL_BLUEPRINT §24.10")).
  • NOT JBIG2 / JPXDecode (JPEG2000) decoders in Phase 0 (PhaseDeferred("FINAL_BLUEPRINT §25.10")). Placeholder gray fill + telemetry.
  • NOT soft-mask luminosity groups in full (constant alpha CA/ca shipped; group transparency partial, PhaseDeferred("FINAL_BLUEPRINT §24.10")).

1.4 Deployment model

  • pdfcore library (Rust crate) — embeddable parse + render API; no_std-friendly core where feasible (alloc required).
  • pdfcli binary — subcommands: render <in.pdf> --page N --dpi D -o out.png, dump <in.pdf> [--obj N G], text <in.pdf> --page N, xref <in.pdf>, info <in.pdf>.
  • Distribution: static binary, library crate, optional C ABI (PhaseDeferred("FINAL_BLUEPRINT §appendix")).

Renderer authors, document-tooling engineers, archival/ingest pipelines, forensic/analysis tooling, search-indexer text extractors. Operators running batch render farms.

Decision: Rust. PDF input is adversarial (a renderer is a parser of attacker-controlled data); memory safety is the dominant non-functional requirement; raster needs C-level speed. C/C++ rejected — the entire history of PDF CVEs (heap overflows in JPEG/JBIG2 decoders, UAF in object resolution) stems from memory unsafety on hostile input. Python rejected — too slow for per-pixel raster and offers no real sandbox for native codecs.

  • Cryptography — RC4, AES-CBC, MD5/SHA, key derivation for the standard security handler.

2. Why Build This

2.1 Unique systems knowledge taught

  • Recursive descent over a hybrid binary/text grammar — tokens are textual but streams are length-delimited binary; the lexer must straddle both.
  • Random-access object resolution via xref — unlike streaming parsers, PDF is read back-to-front (%%EOF → startxref → xref → trailer → catalog), then lazily by offset.
  • Lazy object graph — a (num,gen) keyed cache; objects materialized on demand; reference cycles must be detected.
  • Filter/codec pipelines — composable decode chains (/Filter [/ASCII85Decode /FlateDecode]) with per-stage /DecodeParms.
  • Postfix content-stream interpreter — a stack machine with a layered graphics-state save/restore discipline (q/Q).
  • Vector rasterization — converting Bézier paths to pixels with sub-pixel coverage.
  • Font program embedding — extracting and interpreting embedded Type1/CFF/TrueType programs and mapping character codes → glyph IDs → outlines.

2.2 Historical & architectural significance

  • Adobe Carousel / COS (Carousel Object System) — the 1993 object model underpinning every PDF.
  • ISO 32000-1:2008 (PDF 1.7) and ISO 32000-2:2020 (PDF 2.0) — the format frozen as an international standard.
  • pdf.js (Mozilla), MuPDF (Artifex), Poppler, PDFium (Google/Chromium) — the canonical open renderers; this project re-derives their core from first principles.
  • PDF descends from PostScript (PLRM); its imaging model is a restricted, page-at-a-time PostScript.

2.3 Engineering muscles developed

Defensive parsing of hostile input; offset/length reconciliation; lazy evaluation with caching; codec implementation; stack-machine interpretation; floating-point geometry and fixed-point raster; cryptographic key derivation; differential testing against reference renderers; fuzzing-driven hardening.

2.5 Production engineering concepts exercised

Bounded resource enforcement (decompression bombs, recursion caps), crash-resistance on malformed input, observability of every repaired/rejected object, reproducible deterministic rendering, supply-chain hygiene for codec crates, SLO-driven render latency.

2.6 Calibration value

PDF is the archetypal hostile-format parser: a single binary blob, attacker-controlled, with a self-referential offset table, nested compression, embedded font programs, and an entire imaging language. Building it raises permanent capability in defensive parsing, codec engineering, and graphics — a renderer that survives a fuzzing corpus is proof of staff-level robustness discipline.

2.7 What Mastery Looks Like

  • Defensive parser architect (Phase 0–3): Given a novel binary format with attacker-controlled lengths and offsets, you design a bounds-checked lexer, a lazy-resolution graph, and a scan-rebuild fallback without referencing existing implementations.
  • Codec and pipeline engineer (Phase 4): You implement FlateDecode + PNG predictors + LZW from their normative specs (RFC 1951, RFC 2083, Welch 1984) as composable, fuzz-hardened stages; you detect zip-bombs via a running ratio guard before buffer exhaustion.
  • Graphics-state machine designer (Phase 6–7): You reason about CTM concatenation order, q/Q stack discipline, clip-path intersection semantics, and signed-area scanline coverage without needing a reference engine — and you catch the 10 common pitfalls before writing a line.
  • Font-program interpreter (Phase 9–10): You parse CFF INDEXes, execute Type2 charstrings with correct subr-bias, map CIDs via identity or a lookup stream, and extract Unicode via ToUnicode CMaps; you can diagnose a mojibake CJK page from a metric trace.
  • Security and cryptography integrator (Phase 12): You implement the PDF standard security handler key-derivation chain (R2–R6), apply decrypt-before-decode ordering, and validate /U against an empty password without mishandling PKCS#7 padding.
  • Robustness and observability owner (Phase 13): You drive a renderer from zero-panic on the Isartor malformed corpus + 24 h fuzz green + ≥95% SSIM vs two oracle renderers; you build the observability layer so "why is this page blank?" is answerable from a single trace tree.
  • Differential-testing practitioner (all phases): You use pdf.js and MuPDF as ground-truth oracles via SSIM comparison, distinguish legitimate AA differences from real bugs, and build a CI gate that catches pixel regressions automatically.

3.2 Per-box descriptions

lexer. Byte-oriented zero-copy scanner over a &[u8]. Classifies bytes into whitespace (NUL TAB LF FF CR SP), delimiters (( ) < > [ ] { } / %), and regular characters. Emits tokens: integers, reals, literal strings (balanced-paren with escapes + octal), hex strings, names (/ + #-escapes), array/dict open/close, stream/endstream/obj/endobj/R/keyword. No allocation for token bodies — slices into the source. Trust boundary: every read bounds-checked against the buffer end; never trusts a declared length.

cos. Recursive-descent parser turning tokens into Object. Handles all 9 kinds plus the 3-token reference lookahead N G R vs the integer N. Enforces nesting caps (array/dict depth ≤ MAX_NEST) to stop stack-exhaustion attacks. Stream objects parse the dict, then read from after the stream keyword EOL marker for /Length bytes (with reconciliation if /Length lies). Does not decode stream bytes — that is filters.

xref (resolver). The random-access heart. Reads startxref from the file tail, parses the classic xref table (subsections of 20-byte entries) or a PDF 1.5 xref stream (/Type /XRef, /W, /Index), follows the /Prev chain merging older entries under newer, and resolves object-stream members (/ObjStm). On any inconsistency (bad offset, missing object, malformed table) it triggers rebuild: a linear scan for N G obj markers reconstructs the table. Exposes resolve(ObjId) → Result<Object> backed by a cache, with cycle detection.

doc (document model). Navigates the logical hierarchy: trailer /Root → Catalog → /Pages page tree. Walks /Kids//Count, materializes leaf Page nodes, applies attribute inheritance (/Resources, /MediaBox, /CropBox, /Rotate inherited down the tree). Detects cyclic/over-deep page trees. Produces a flat page index for random page access.

Resource resolver. Given a page (or nested form/Type3 scope), resolves the /Resources dictionary's sub-dictionaries — /Font, /XObject, /ColorSpace, /ExtGState, /Pattern, /Shading, /ProcSet. Resource scope is stacked: a form XObject inherits the parent resources unless it declares its own. Name lookups (/F1, /Im0) resolve to indirect objects; missing entries fall back with telemetry.

filters. A composable decode chain. Each Filter consumes raw bytes + /DecodeParms and yields decoded bytes. Chains apply in array order. Includes FlateDecode (DEFLATE + zlib header) with PNG/TIFF predictors, LZWDecode (variable-width codes, early-change), ASCII85Decode, ASCIIHexDecode, RunLengthDecode, DCTDecode (delegated to JPEG decoder, yields raw samples), CCITTFaxDecode (G3/G4). Enforces a decompression-ratio cap (zip-bomb guard).

content lexer + interpreter. A second tokenizer over decoded content bytes (reuses lexer primitives but treats operators as keywords). The interpreter is a postfix stack machine: operands push onto an operand stack; an operator keyword pops its arity and dispatches. Unknown operators are skipped (operand stack cleared) per the compatibility rule. An operator budget caps total executed operators.

graphics state machine. The mutable rendering context: current transformation matrix (CTM), clip path, fill/stroke color + color space, line width/cap/join/miter/dash, alpha (CA/ca), blend mode, and a nested TextState. q pushes a copy; Q pops. Stack underflow on Q is clamped (never negative) with telemetry. The CTM maps user space → device space; composed with the page's rotation/flip transform.

path builder. Accumulates the current path from construction operators (m l c v y re h). Beziers stored as control points; flattened later. Painting operators (S s f f* B b n) hand the path to the rasterizer with the active winding rule and paint (fill vs stroke vs clip). W/W* set a pending clip applied at the next path-painting op.

text engine. Maintains text-space matrices (Tm text matrix, Tlm line matrix) and text state (font, size, spacing, leading, scale, rise, render mode). Showing operators (Tj TJ ' ") decode the string into character codes via the font's encoding/CMap, look up glyph IDs and advance widths, position each glyph via the text-rendering matrix, and emit glyph outlines (or Type3 sub-content) to the rasterizer. Owns font loading and glyph sourcing.

font loader. Builds a Font from a font dictionary: simple (Type1/TrueType/Type3) or composite (Type0). Loads embedded programs (/FontFile Type1, /FontFile2 TrueType via #385, /FontFile3 CFF/OpenType), builds the code→glyph mapping (encoding + /Differences, or CMap + /CIDToGIDMap), and width tables (/Widths or /W//DW). Falls back to Standard-14 metrics when unembedded.

image pipeline. Handles image XObjects (/Subtype /Image) and inline images (BI … ID … EI). Decodes sample data through the filter chain, interprets bits-per-component + color space → RGBA, applies /ImageMask (1-bit stencil), /SMask (soft alpha), and color-key masking. Blits into device space honoring the CTM (with bilinear/nearest sampling).

raster (shared with #385). Flattens Bézier curves to line segments (adaptive tolerance), runs a scanline sweep accumulating signed-area coverage per pixel for anti-aliasing, applies the winding rule, intersects with the clip mask, and produces a coverage buffer the compositor blends with the paint. Reused verbatim from #385 for glyph fills.

page compositor. Blends coverage × color into the destination bitmap using the active alpha and blend mode (Normal, Multiply, Screen, Overlay, Darken, Lighten, …). Applies page /Rotate and the y-flip (PDF origin bottom-left → image origin top-left). Emits the final Gray8/RGBA8 buffer.

api / cli. The public surface: open a document, enumerate pages, render a page at a DPI/scale to a bitmap, extract text, dump objects. The CLI wraps these for shell use and batch pipelines.

4.4 Numeric & determinism

  • Raster fixed-point: 26.6 (64ths) for scanline coordinates; float for CTM composition then quantized.
  • DPI/scale range: 1–7200 DPI; scale 0.01×–100×; reject outside.
  • Determinism: identical input bytes + identical render params → bit-identical output bitmap (no time/random/threading nondeterminism in pixel path).
  • No panic on malformed input: every parse/decode path returns Result; the process must never abort on hostile data. Panics are bugs caught by fuzzing.

4.5 Startup / availability

  • Document open (parse xref + catalog, no page render): ≤ 5 ms for a 10 MB file; ≤ 50 ms for 200 MB with xref streams.
  • Library has no global mutable state; safe for concurrent multi-document use.
  • Render farm SLO: 99.9% of pages render without crash; ≥ 99% within p99 latency.

6. Design Principles

  1. Untrusted input is hostile. Every byte read is attacker-controlled. Bounds-check every offset, length, index, and count; never trust a declared /Length, /Size, /N, /W, or array length. Tradeoff: extra branches per access. Operational: zero memory-safety CVEs is the bar. Violation: a single unchecked offset = OOB read → infoleak or crash (the entire poppler/pdfium CVE history).

  2. Lazy object resolution. Parse objects on demand by xref offset; cache the resolved Object keyed by (num,gen). Tradeoff: cache memory vs re-parse cost. Operational: opening a 1000-page file must not parse all pages. Violation: eager full-document parse blows memory and latency on huge files; cannot stream.

  3. Recover, don't crash. Real PDFs are broken — wrong /Length, dangling xref offsets, missing endobj. On structural failure, rebuild by scanning for N G obj markers and reconcile. Tradeoff: repaired files may render imperfectly. Operational: emit xref_rebuilds telemetry. Violation: refusing broken files makes the renderer useless (the vast majority of in-the-wild PDFs have minor corruption).

  4. Determinism. Same bytes + same render params → bit-identical pixels. No wall-clock, no RNG, no thread-order dependence in the pixel path. Tradeoff: limits some parallel raster strategies. Operational: enables golden-image differential testing. Violation: flaky tests, irreproducible bug reports, untrustworthy archival rendering.

  5. Bounded resources. Cap decompression ratio, recursion depth, operator count, object count, pixel count. Tradeoff: may reject pathological-but-legitimate files (rare). Operational: every cap is configurable + emits telemetry on hit. Violation: a 10 KB zip-bomb PDF allocates 50 GB → OOM kill = DoS.

  6. No code execution. Never run /JS, /JavaScript, /Launch, /OpenAction, /SubmitForm, /ImportData, /GoToR, /URI. Parse them as data, refuse to act. Tradeoff: no interactive behavior. Operational: log actions_refused. Violation: the dominant PDF attack class (malicious actions) becomes live; remote code/data exfiltration.

  7. Separation of model vs render. doc/cos/xref produce a pure object/document model; content/graphics/raster consume it. Tradeoff: an extra layer. Operational: parser bugs vs render bugs are independently testable (object dump vs golden image). Violation: tangled code where a font bug corrupts xref state.

  8. Filters as a composable pipeline. Each codec is a Filter decode stage; chains compose in array order with per-stage /DecodeParms. Tradeoff: indirection. Operational: add a codec without touching the parser. Violation: hardcoded filter handling can't express [/ASCII85Decode /FlateDecode] chains; breaks real files.

  9. Graphics state is a stack discipline. q pushes, Q pops a full gstate copy; clip and CTM travel with it. Tradeoff: per-q copy cost (mitigate with copy-on-write). Operational: track q/Q balance; clamp underflow. Violation: unbalanced q/Q (common in broken content) corrupts the CTM/clip for the rest of the page → garbage output.

  10. Color managed but pragmatic. Implement device + CIE + ICCBased + Indexed + Separation/DeviceN; do not require a full external CMM — minimal internal ICC interpretation + heuristics. Tradeoff: not pixel-perfect ICC fidelity. Operational: colorspace_fallbacks metric. Violation: demanding full ICC blocks rendering of most files for marginal accuracy.

  11. Observability of every rejected/repaired object. Every dropped object, repaired xref, unsupported filter, missing glyph, clamped stack is counted + traceable. Tradeoff: telemetry overhead. Operational: "why is this page blank?" answerable from metrics. Violation: silent failures = undebuggable render farm.

  12. Spec-conformance over leniency, but lenient where real files demand. Default to ISO 32000 behavior; add tolerant fallbacks only for documented real-world breakage, each behind a recorded quirk. Tradeoff: maintaining a quirks list. Operational: quirks are logged so we know which files needed them. Violation: either rigid (rejects real files) or chaotically lenient (renders garbage as if correct).

  13. Fixed-point, integer-exact raster core. Scanline coverage uses 26.6 fixed-point; winding accumulation is integer-exact. Tradeoff: fixed-point edge cases. Operational: determinism + speed. Violation: float coverage → platform-dependent rounding → non-deterministic edges.

  14. Codec crates are vendored and audited. FlateDecode/LZW/CCITT/JPEG implemented in-tree or as audited dependencies; never link a memory-unsafe C codec into the hot path. Tradeoff: more code to own. Operational: fuzzed independently. Violation: a JPEG/JBIG2 heap overflow in a C dep reintroduces the exact CVE class we chose Rust to avoid.

  15. Scope refusal is explicit. Unsupported features (JBIG2, JPX, XFA) return a typed Unsupported* outcome with telemetry and a graceful visual fallback (gray box), never a silent wrong render. Tradeoff: visible gaps. Operational: unsupported_filter counts drive the blueprint. Violation: pretending to support a codec produces corrupted images users trust.

8.2 COS object grammar (EBNF)

object       = boolean | integer | real | string | name
             | array | dictionary | stream | null | reference ;

boolean      = "true" | "false" ;
integer      = [ "+" | "-" ] digit { digit } ;
real         = [ "+" | "-" ] ( digit { digit } "." { digit }
                             | "." digit { digit } ) ;
null         = "null" ;

string       = literal_string | hex_string ;
literal_string = "(" { lit_char | balanced_parens | escape } ")" ;
escape       = "\" ( "n"|"r"|"t"|"b"|"f"|"("|")"|"\"
                   | octal3 | line_continuation ) ;
hex_string   = "<" { hex_digit | whitespace } ">" ;   (* odd count → pad 0 *)

name         = "/" { name_char | "#" hex_digit hex_digit } ;

array        = "[" { object } "]" ;
dictionary   = "<<" { name object } ">>" ;            (* keys are names *)

stream       = dictionary "stream" ( CRLF | LF ) raw_bytes ( EOL )? "endstream" ;
               (* raw_bytes length = /Length (reconciled); never trust blindly *)

reference    = integer integer "R" ;                  (* object num, gen, R *)
indirect_obj = integer integer "obj" object "endobj" ;

Lexer notes: % begins a comment to EOL (except inside strings/streams). Whitespace = {NUL,TAB,LF,FF,CR,SP}. Delimiters = (){}<>[]/%. A number followed by another number followed by R is a reference; the parser needs 2-token lookahead to disambiguate 3 0 R (ref) from 3 0 (two integers, e.g. in an array). < may start a hex string or (<<) a dict — peek the next byte.

8.3 Cross-reference streams (PDF 1.5+)

A stream object replacing the classic table:

<< /Type /XRef /Size N /Root ... /W [w1 w2 w3] /Index [s1 c1 s2 c2 ...]
   /Prev offset /Filter /FlateDecode /Length L >>
stream
<binary fields, each entry = w1+w2+w3 bytes>
endstream
  • /W = byte widths of the 3 fields per entry: [type, field2, field3].
  • Field types: 0 = free (field2 = next free obj, field3 = gen); 1 = in-use (field2 = byte offset, field3 = gen); 2 = compressed (field2 = ObjStm object number, field3 = index within stream).
  • /Index = [start count …] pairs naming which object numbers the table covers (default [0 Size]).
  • A field width of 0 means a default value (type defaults to 1).

8.4 Object streams (ObjStm)

<< /Type /ObjStm /N n /First f /Length L [/Extends prev] /Filter ... >>
stream
<n pairs: objnum offset> ... (offsets relative to /First)
<object 1 bytes><object 2 bytes>...
endstream
  • Holds n non-stream objects packed together (compressed once → space saving).
  • /N = object count; /First = byte offset (in decoded stream) where the first object body begins; the header is n (objnum offset) integer pairs.
  • Rule: an ObjStm may not contain stream objects, the /Encrypt dict, or another ObjStm; gen number of compressed objects is implicitly 0.

8.7 Fonts

Simple fonts (/Subtype /Type1 | /TrueType | /Type3, single-byte codes 0–255):

  • /BaseFont, /FirstChar, /LastChar, /Widths (array, indexed by code−FirstChar, in glyph-space /1000).
  • /Encoding = base (/StandardEncoding,/WinAnsiEncoding,/MacRomanEncoding) optionally with /Differences [code /name …].
  • /FontDescriptor → /Flags, /FontBBox, /ItalicAngle, /Ascent, /Descent, /CapHeight, /StemV, and one of /FontFile (Type1), /FontFile2 (TrueType), /FontFile3 (CFF/OpenType).
  • Type3: /FontMatrix, /CharProcs (name → content stream defining each glyph), /Encoding, /Resources; glyphs are mini content streams (recursion-capped).

Composite fonts (/Subtype /Type0, multi-byte codes):

  • /Encoding = /Identity-H//Identity-V (code = 2-byte CID) or a named/embedded CMap (code → CID).
  • /DescendantFonts [ <CIDFont> ] where CIDFont is /CIDFontType0 (CFF) or /CIDFontType2 (TrueType) with /CIDSystemInfo, /CIDToGIDMap (/Identity or a stream), /W (per-CID widths), /DW (default width).
  • /ToUnicode = a CMap stream mapping codes → Unicode for text extraction (not rendering).

Standard-14: Helvetica (×4), Times (×4), Courier (×4), Symbol, ZapfDingbats — metrics built-in (AFM tables) so unembedded standard fonts render with correct widths via a substitute outline.

8.9 Coordinate system

  • Default user space: origin bottom-left, +x right, +y up, unit = 1/72 inch.
  • CTM maps user → device space; built by cm concatenation atop the initial device transform.
  • Initial device transform: flips y (device origin top-left) and scales by DPI/72; rotates per page /Rotate.
  • Text space: Trm = [Tfs·Th 0 0 Tfs 0 Trise] × Tm × CTM (text rendering matrix); glyph space → text space via the font matrix (Type3) or /1000 scaling (others).

    Null,
    Bool(bool),
    Int(i64),
    Real(f64),
    Str(PdfString),
    Name(Name),
    Array(Vec<Object>),
    Dict(Dict),

  • Ownership: Object owns its children (Vec/Dict). Stream::raw is a byte range into the source (zero-copy until decoded). decoded is interior-mutable (OnceCell) — decode-on-first-use.
  • Mutation: Object is immutable post-parse except Stream.decoded. Concurrency: Document cache shared read; OnceCell/Mutex guard lazy decode for Send + Sync.
  • Serialization: debug dump via tools/object-dumper; no on-disk format (this is a reader).
  • Compatibility: the Object enum is the stable internal API; new object kinds are forbidden (PDF has exactly 9).

12. Phase 0 — Repo Skeleton + Byte Lexer + Tail Detection

12.1 Objectives

Bootstrap workspace; byte scanner; detect %PDF-, startxref, %%EOF; emit the full PDF token grammar. No object parsing yet.

12.2 Detailed Implementation Steps

(Applies: P1 ISO 32000-1 sec. 7.2 lexical conventions; ADR-04 mmap zero-copy; ADR-05 byte-oriented no-regex; P1/P2 for stream framing reference)

  • crates/lexer/scanner.rs — Scanner{ buf:&[u8], pos:usize }; byte classifier class(b)->{Ws,Delim,Regular}; next_token()->Option<Token>. Enforces I1 (every read bounds-checked against buf.len()).
  • crates/lexer/token.rs — enum Token{ Int(i64),Real(f64),LitStr(Range),HexStr(Range),Name(Range),ArrOpen,ArrClose,DictOpen,DictClose,Keyword(Range),Comment(Range),Eof }; struct Span{start,end}.
  • Header detect: scan first 1024 bytes for %PDF-(\d).(\d); record version; tolerate leading junk (offset shift recorded as header_offset). Implements P3 (recover, don't crash).
  • Tail detect: from EOF, reverse-scan for last %%EOF, then preceding startxref, parse the integer offset. Per P3: accept trailing garbage (real files have it).
  • Number lexing: integer vs real (presence of .); reject lone +/-/. → bad_token, resync. I10 enforced.
  • Literal-string lexer: balanced-paren counter, escape decode (\n\r\t\b\f\(\)\\, octal \ddd, line-continuation \<EOL>).
  • Hex-string lexer: collect hex digits ignoring whitespace; odd count → pad trailing 0 (per ISO 32000-1 sec. 7.3.4.3).
  • Name lexer: after /, decode #xx hex escapes; stop at delimiter/ws. Per P1 (untrusted input) check #xx completeness.
  • Comment: % → consume to EOL (suppressed token).

12.3 Deliverable

pdfcli stub + lexer crate that tokenizes any byte stream; cli xref prints header version, startxref offset, %%EOF position.

12.4 Acceptance Criteria

  • Tokenize the §8.1 sample → exact expected token sequence.
  • 100% of bytes accounted for (no infinite loop, pos strictly advances).
  • Fuzz fuzz_lexer 1M execs, zero panics, zero hangs (op-per-byte bound).
  • Header/tail detection correct on 20 valid + 10 junk-prefixed fixtures.

12.5 Conformance Fixtures

hello.pdf (token golden); junk_prefix.pdf (header not at 0); trailing_garbage.pdf (bytes after %%EOF); crlf.pdf / lf.pdf / cr.pdf (EOL variants); no_eof.pdf (malformed — must report, not crash).

12.6 Pitfalls

  • Treating PDF as UTF-8 → multibyte corruption; PDF is bytes (root cause: char-based scanner). Detect: non-ASCII in names. Fix: byte API only.
  • Comments inside strings consumed as comments → desync. Root cause: % handled before string context. Fix: string lexer ignores %.
  • startxref offset read as decimal with leading zeros / whitespace → parse fail. Fix: tolerant integer parse.
  • Reverse-scan for %%EOF matching an earlier occurrence in content. Fix: scan from true EOF, accept last.

Performance Engineering

  • Lazy parse + object cache: never parse unrequested objects; cache resolved objects (LRU, §4.1) — measured by cache_hit_ratio. Cold-open of a 1000-page doc parses only xref + catalog.
  • Cache locality: Object children inline in Vec/IndexMap; intern hot names (/Type,/Length,/Filter) to avoid repeated byte allocations.
  • Stream decode reuse: decode each ObjStm/image once, cache the decoded buffer; never re-decode per member/occurrence.
  • Rasterizer buffer reuse: pool edge tables + coverage masks across paths/glyphs (per render thread); avoid per-path allocation.
  • Glyph caching: outline cache by (font,gid); rendered-coverage cache by (font,gid,subpixel-bin,scale) — text-heavy pages hit this hard.
  • Image scaling: integer-nearest for downscale, bilinear otherwise; precompute inverse CTM for source sampling; tile huge images.
  • SIMD blits: vectorize coverage→RGBA compositing and predictor (Paeth) loops where the target supports it (feature-gated).
  • Benchmarking: criterion benches per stage (benchmarks/render_bench.rs): tokenize/sec, resolve/sec, inflate MB/sec, fill Mpix/sec, end-to-end page render for each content class. CI gate on regression.
  • Profiling methodology: pprof/perf → flamegraphs (docs/performance/flamegraph-guide.md); identify hot stages (typically inflate, rasterizer fill, IDCT). Allocator analysis via dhat to catch alloc churn.
  • Tail latency: p99 driven by vector-heavy pages (many paths) + large images; bound by op budget + image ceiling; investigate via per-stage span durations.

Mental Models & First Principles

MM1 — PDF is a random-access object graph, not a sequential stream.
Insight: The file must be read back-to-front (%%EOF → startxref → xref → catalog) before any content is interpreted. Objects are materialized by offset, not by file order.
What it predicts: Opening a huge PDF should be O(xref size), not O(file size). Latency is proportional to xref parse + catalog walk, not total bytes.
Bug class without it: Sequential parsers that read from byte 0 miss linearization hints and fail on files with junk at the start; they also force full-file parse.
Applied in: §8.1 physical structure; Phase 0 tail detection; Phase 2 lazy resolve; §4.5 open latency target.

MM2 — The xref is a versioned namespace; newer always wins.
Insight: Incremental updates append new object definitions without erasing old ones. The /Prev chain is an ordered log; resolution always returns the latest definition for an (ObjId).
What it predicts: A correctly built XrefTable after merge will always surface the post-increment version of any modified object.
Bug class without it: A merge that picks an older offset over a newer one produces stale content — the classic "why does signing corrupt a PDF?" bug.
Applied in: I3; Phase 3 /Prev merge; §8.3 xref stream semantics.

MM3 — The graphics state is a stack of snapshots; q/Q balance is an invariant.
Insight: Every q saves a full copy of the rendering context. Every Q restores it. Any paint operation operates on the top of the stack. A content stream that qs without matching Q leaks its mutated state forward.
What it predicts: A cm inside a balanced q/Q pair has zero effect outside it. An unbalanced extra Q corrupts the CTM for the rest of the page.
Bug class without it: Broken content (common in practice) corrupts clip/color/CTM state indefinitely forward — produces garbage rendering with no error signal.
Applied in: I5; §6 P9; Phase 6 gstate machine; §11.3 GraphicsState.

MM4 — PDF filters are composable, not monolithic; every codec is hostile input.
Insight: A stream's content is encoded through an ordered chain of codecs (/Filter [/ASCII85Decode /FlateDecode]). Each stage is independently decodeable and independently attacker-controlled. A decompression bomb exists at exactly one stage.
What it predicts: Ratio guards must be applied per-stage, not on the final output. Any stage can be a DoS vector; each needs an independent budget.
Bug class without it: Applying a single ratio cap at the chain end allows a deep-chain attack where stage 1 expands 100× and stage 2 expands 200× for a 20,000× net ratio.
Applied in: I8; §6 P8; Phase 4 filter pipeline; §11.5 run_filter_chain.

MM5 — Font programs are embedded interpreters; their inputs are untrusted.
Insight: A /FontFile (Type1), /FontFile2 (TrueType), or /FontFile3 (CFF/OpenType) is a binary program — a charstring interpreter is a small VM. Maliciously crafted charstrings can trigger infinite loops, stack overflows, or OOB access in an unchecked interpreter.
What it predicts: CFF/Type1 interpreters need explicit op-count caps, stack-depth limits, and subroutine-call-depth limits, exactly as a sandboxed VM does.
Bug class without it: An unbounded charstring interpreter loops indefinitely on a crafted glyph, consuming CPU without triggering the content-stream op budget.
Applied in: I9; Phase 9 text/cff.rs, text/type1.rs; Threat Model (font program parsing threat).

MM6 — Determinism is a design property, not a runtime guarantee.
Insight: Identical input + identical render params must produce bit-identical pixel output. This is not automatic: floating-point rounding, thread scheduling, and global state all destroy it.
What it predicts: The coverage accumulator must be fixed-point (26.6 integer), the operation order must be deterministic (no thread nondeterminism in the pixel path), and clocks/RNG must be excluded.
Bug class without it: Non-deterministic rendering means golden-image differential tests are unreliable, archival renders are not reproducible, and "why does this PDF look different on two machines?" is unanswerable.
Applied in: §4.4 numeric/determinism; §6 P4; ADR-15 shared rasterizer; ADR-30 reproducibility.

MM7 — Actions and JavaScript are a separate attack class; refuse-by-construction beats sanitize.
Insight: The dominant class of PDF exploits (Müller et al. 2019–21, P15) are not parser bugs but action bugs: malicious PDFs execute /JS, /Launch, /OpenAction to exfiltrate data or run code. Sanitizing action content is intractable; refusing to execute it is a single policy decision.
What it predicts: A renderer that parses action objects but never dispatches them eliminates the entire class, at the cost of no interactive behavior.
Bug class without it: Any action executor (even a minimal one) introduces a sandbox-escape attack surface proportional to the completeness of the executor.
Applied in: I14; §6 P6; ADR-31; Threat Model (embedded JS/actions row); Phase 5 catalog parse.

MM8 — Text extraction and rendering are independent paths; conflating them corrupts both.
Insight: /ToUnicode maps character codes → Unicode for extraction. It has nothing to do with glyph selection or advance widths during rendering. CID→GID mapping drives rendering; /ToUnicode drives extraction.
What it predicts: A renderer that uses /ToUnicode for glyph lookup will produce wrong glyphs for any font where the CID→GID mapping differs from the Unicode mapping.
Bug class without it: CJK glyphs render incorrectly, or extraction produces wrong Unicode from fonts where /ToUnicode is provided but CID→GID follows a separate path.
Applied in: §6 P7 separation of model vs render; Phase 10 text/tounicode.rs vs text/cid.rs; §11.6 Font types.

pdfium (Chromium/Google): Made the decision to accept C++ complexity in exchange for Skia's GPU-accelerated raster and production battle-hardening at Google-scale. The compensating control is Chrome's multi-process sandbox, which contains memory-safety exploits. Wins in interactive browser PDF viewing at 60+ fps where GPU parallelism is available.

MuPDF (Artifex): Made the decision to write a tight, allocation-minimal C raster ("Fitz") for maximum throughput on embedded and server targets. The setjmp/longjmp error model is fragile but efficient; the payoff is the smallest-footprint capable renderer available. Wins in embedded/IoT environments (e-readers, printers) where binary size and per-page latency in constrained RAM matter more than memory safety.

Poppler: Made the decision to back the rasterizer with Cairo (an external, system-linked vector library) rather than owning the raster engine. This gives high-quality Cairo output and desktop integration at the cost of a system dependency and Cairo's overhead. Wins in desktop Linux GUI applications (Evince, GNOME Documents) where Cairo is already a system dependency and rendering quality for screen display is the primary goal.

pdf.js (Mozilla): Made the decision to implement entirely in JavaScript (now also WASM-compilable), gaining memory safety and browser integration at the cost of throughput. JavaScript GC eliminates buffer-overflow exploits. JavaScript execution is the oracle for "what a browser PDF viewer sees". Wins as a zero-install, sandboxed browser PDF viewer and as a differential-testing oracle for this project.

Back-of-Envelope Capacity Model

All numbers derived step-by-step from System Constraints (§4).

1. Page bitmap memory (Letter, 150 DPI, RGBA8)

W = 8.5 in × 150 DPI = 1275 px
H = 11 in × 150 DPI = 1650 px
Bitmap = W × H × 4 bytes = 1275 × 1650 × 4 = 8,415,000 B ≈ 8 MB per page

Check: well under the §4 ceiling of 4 × page_px × bpp = 4 × 2,103,750 × 1 = ~8 MB (Gray8 4× is a conservative ceiling for intermediate buffers).

2. Decompression bomb threshold (§4.3, 200:1 cap)

Max stream input before bomb: cap_output / ratio = 512 MB / 200 = 2.56 MB input triggers abort
A 2.6 MB Flate stream claiming 200× expansion → abort at 512 MB output (I8)

3. Object cache ceiling (§4.1, 256 MB LRU)

Average resolved object size: ~500 B (dict + children inline)
Objects cached at ceiling: 256 MB / 500 B = ~524,288 objects
A 1-million-object PDF → ~50% cache hit rate at ceiling; rest resolved on-demand

4. Glyph cache sizing (§4.1, 32 MB LRU)

Average glyph outline (Path, 20 segments): ~20 × 32 B = 640 B
Glyphs at ceiling: 32 MB / 640 B = ~52,000 glyph outlines cached
A font with 65,536 glyphs: ~80% hit rate for a typical corpus (Zipf distribution of glyph usage)

5. Render-farm FD budget (100 concurrent documents)

Per-doc FDs: 1 mmap (source file) + 1 (metrics socket) + 2 (log pipe) = 4 FDs
100 docs: 400 FDs; well under typical per-process limit of 65,536

6. Xref table memory (1 million objects)

Per-entry: ObjId(6 B) + XrefEntry(12 B) = 18 B in HashMap
HashMap overhead (~1.5×): 18 × 1.5 = 27 B/entry
1M entries: 27 MB → fits comfortably in 256 MB object-cache ceiling

7. Filter chain bandwidth (FlateDecode, 150 DPI Letter page)

Page content stream (typical text+vector): ~50 KB compressed
Inflate at 150 MB/s (M4): 50 KB / 150 MB/s = 0.33 ms
Image streams: up to 5 MB compressed; inflate: 5 MB / 150 MB/s = 33 ms
→ Inflate is rarely the bottleneck for text pages; can dominate image-heavy pages

8. Rasterizer throughput check (M10, 200 Mpix/s)

Letter page at 150 DPI: 1275 × 1650 = 2,103,750 px
Time at 200 Mpix/s: 2,103,750 / 200,000,000 = 10.5 ms
→ Rasterizer alone can fill a full Letter page in ~10 ms (consistent with M7 ≤ 8 ms for simple pages at cache-warm)

9. Glyph coverage cache per render (text-heavy, 1000 glyphs)

Rendered coverage per glyph (12pt, 150 DPI, ~16×20 px): 320 B
1000 unique (font, gid, scale-bin) combos: 320 KB → negligible vs 32 MB cache
→ Text-heavy pages fit entirely in glyph cache after first pass; subsequent pages are cache-warm

10. Parallel page render scaling (N cores)

Per-page CPU: ~8 ms (M7 text), ~25 ms (M8 mixed), ~120 ms (M9 vector)
Amdahl's law: shared state = RwLock on object cache (read-mostly → near-zero contention)
Ideal throughput: N pages/core; measured ceiling: ~0.9N (5–10% RwLock write overhead on cold-miss bursts)
At 16 cores: 16 × 0.9 = 14.4× throughput vs single-threaded for text pages

Alternative Architectures (Roads Not Taken)

Alt-1 — Process-Sandbox Architecture (PDFium / Chromium model)

 Browser Process           Renderer Process (sandboxed)
 ┌─────────────┐           ┌──────────────────────────────┐
 │ Action host │ ←IPC────► │  pdfcore (parse + render)    │
 │ JS sandbox  │           │  C ABI / Skia GPU raster     │
 │ UI / nav    │           │  Seccomp / pledge filter     │
 └─────────────┘           └──────────────────────────────┘

Regime where it wins: Interactive browser PDF viewers needing JavaScript action execution, form filling, annotation editing, and GPU-accelerated rendering at 60 fps. The sandbox provides memory-safety guarantees that compensate for C++ usage.
Real system: PDFium inside Chromium — every Chrome tab rendering a PDF uses this exact architecture.
Why rejected here: This blueprint targets an embeddable render library and a batch render farm. There is no browser process, no GPU requirement, and no interactive actions needed. The sandbox overhead (IPC marshaling, process spawn) adds latency incompatible with M5–M7 targets. Refuse-by-construction (ADR-31) eliminates the need for a separate action sandbox.

Alt-2 — Streaming, Single-Pass Parser (SAX-style)

 PDF bytes
    │
    ▼
  streaming
  tokenizer ──► object handler callbacks ──► direct render pipeline
    │            (no xref-driven                (no lazy resolve,
    │             random access)                 no object graph)
    ▼
  EOF

Regime where it wins: Ultra-low-memory embedded environments (printers, e-readers) processing linearized PDFs front-to-back where random access is unavailable and memory is measured in KB, not MB. Works correctly only for well-formed linearized PDFs.
Real system: Some embedded PDF viewers in laser printers (e.g., PCL/PDF firmware stacks) use a single-pass architecture for linearized PDFs, resolving only the first page before the rest of the file arrives.
Why rejected here: The vast majority of real-world PDFs are not well-formed linearized PDFs. Random access via xref is required for: resolving /Length references, incremental updates (the newest definition is at the end), any object referenced before it appears in file order. A single-pass design degrades to a full rebuild for these files — the common case.

Alt-3 — GPU-Accelerated Rasterizer (Skia / wgpu model)

 Content interpreter
        │
        ▼
   Display list           GPU pipeline
   ┌──────────────┐       ┌────────────────────────────────┐
   │ draw_path()  │──────►│  vertex shader → fragment      │
   │ draw_glyph() │       │  MSAA coverage                 │
   │ draw_image() │       │  blend on GPU framebuffer      │
   └──────────────┘       └────────────────────────────────┘

Regime where it wins: Interactive PDF viewers rendering at > 30 fps with complex vector content (technical drawings, architectural plans), where GPU parallelism delivers 10–100× rasterization throughput vs CPU scanline. Also wins for MSAA anti-aliasing quality at high DPI.
Real system: PDFium's Skia backend in Chromium; Foxit's GPU renderer. Skia itself powers Flutter's PDF rendering.
Why rejected here: The deployment target is a server-side batch render farm and an embeddable library, not an interactive viewer. GPU is not available in the server context. GPU rasterization introduces non-determinism (driver-dependent AA, floating-point coverage) that breaks the determinism invariant (§4.4, MM6). GPU rendering is registered as PhaseDeferred("FINAL_BLUEPRINT §appendix") for a future interactive-viewer phase.

Alt-4 — PostScript Interpreter Backend

 PDF content stream
        │
        ▼
   PDF→PS transpiler         PostScript interpreter
   ┌────────────────┐        ┌─────────────────────────────┐
   │ content ops →  │───────►│  full Ghostscript PS engine │
   │ PS equivalents │        │  imaging model              │
   └────────────────┘        └─────────────────────────────┘

Regime where it wins: When an existing, battle-tested PostScript interpreter (Ghostscript) is already deployed and the primary goal is correctness of output for print production, not performance. PDF is a restricted PostScript dialect; a PS engine can, in principle, handle any conforming PDF by translation.
Real system: Ghostscript's pdf2ps pipeline (deprecated in favor of its native PDF interpreter, but historically dominant for prepress). Some RIPs in commercial printers use this approach.
Why rejected here: PDF is not PostScript. PDF 1.4+ transparency, xref streams, CID fonts, and AES encryption have no PostScript equivalents — the transpiler would need to implement all of PDF anyway. Ghostscript is a C program with its own CVE history. The translation layer adds latency and loses the ability to lazy-resolve PDF objects. This design builds the PDF engine directly, preserving lazy resolution, bounded resources, and Rust memory safety throughout.
