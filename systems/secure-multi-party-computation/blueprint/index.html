392 — Secure Multi-Party Computation (MPC) from Scratch

Project Number: 392

Project Name: Secure Multi-Party Computation (MPC) from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

1.1 Precise Engineering Scope

Build a self-contained, from-scratch Secure Multi-Party Computation (MPC) framework in Rust enabling N parties to jointly evaluate a function f(x₁,…,x_N) over private inputs while revealing only the output and nothing else about any party's input beyond what the output implies. The system implements the full classical MPC stack bottom-up: finite-field arithmetic (prime field F_p and binary field GF(2)), linear secret sharing (additive mod p, Shamir (t,n) threshold), oblivious transfer (base 1-of-2 OT via Diffie–Hellman / Naor–Pinkas, IKNP OT extension, correlated/random OT), Beaver multiplication triples (offline preprocessing + online multiplication), arithmetic-circuit MPC (BGW-style with degree reduction, GMW-arithmetic with triples), boolean MPC (GMW over OT, Yao's Garbled Circuits with point-and-permute, free-XOR, half-gates), a party + transport abstraction (in-process simulated channels + pluggable network transport) with round/communication accounting, an offline/online preprocessing split, and applications (secure addition, multiplication, comparison, basic private set intersection, millionaires'/auction demo).

The threat model target is semi-honest (honest-but-curious): corrupted parties follow the protocol but try to learn from their view. Security is simulation-based (a corrupted coalition's view is simulatable from its inputs+outputs). Malicious security (authenticated shares, SPDZ-style MACs, cut-and-choose for garbling, OT with consistency checks) is explicitly deferred to a stretch phase. The contract is seeded-deterministic test transcripts for reproducibility, with all security-relevant randomness drawn from a CSPRNG; the framework is educational and NOT audited / NOT production cryptography.

1.3 Non-Goals

  • No malicious/active security: no SPDZ MACs, no authenticated garbling, no OT consistency checks beyond sketches — PhaseDeferred("FINAL_BLUEPRINT §Phase 13").
  • No homomorphic-encryption triple generation as a shipped path (sketched, cross-linked to 391) — PhaseDeferred("FINAL_BLUEPRINT §Phase 6").
  • No silent OT / VOLE / PCG correlated randomness — PhaseDeferred("FINAL_BLUEPRINT §Phase 4").
  • No production transport security (TLS cert mgmt, PKI, mutual auth hardening) — transport is pluggable but the network layer is reference-grade.
  • No GPU/SIMD-accelerated field or AES kernels beyond optional intrinsics — PhaseDeferred("FINAL_BLUEPRINT §Phase 11").
  • No general circuit compiler / high-level MPC DSL; circuits are built via a builder API + a small Bristol-format reader.
  • No verifiable secret sharing (VSS) / distributed key generation beyond the relation to 379 — sketched only.
  • No constant-round generic MPC beyond Yao (2-party) and BMR (sketched).

1.4 Intended Deployment Model

  • Library crates consumed by Rust code: instantiate Party objects, wire Channels (in-proc or network), choose a protocol (BgwArith, GmwBool, YaoGc), supply private inputs, run, collect output.
  • Simulator harness (mpc-sim): runs all N parties as threads/tasks in one process over in-memory channels with a seeded transcript recorder — the primary test/教学 vehicle; deterministic, replayable, communication-accounted.
  • Network mode (mpc-net): each party a separate process; length-prefixed framed messages over TCP; a coordinator/bootstrap for peer discovery; same protocol code, different Channel impl.
  • CLI (mpc-cli): millionaires --party 0 --input 42 --peers ..., psi, sum, run --circuit f.bristol --protocol gmw. Single function evaluation per invocation.

1.10 Language Selection — Rust

MPC's cost lives in three hot kernels — finite-field arithmetic, OT extension (AES + matrix transpose over millions of OTs), and garbled-circuit evaluation (AES-based hashing per gate) — and the protocol layer demands exhaustive case analysis over gate/share/message types where a missed variant is a silent security bug. Rust gives exact control over memory layout for field words and 128-bit label Blocks, zero-cost abstractions for share/gate generics, exhaustive enum + match that makes gate-type and protocol-message completeness a compile-time guarantee, fearless concurrency for the simulator (N parties as tasks) and for batched OT/garbling, and a strong crypto ecosystem (aes, sha2, chacha20, curve25519-dalek, rand_core, subtle for constant-time). No GC pauses interfere with timing-sensitive kernels, and constant-time primitives (subtle::ConstantTimeEq) are first-class. Python is rejected: the OT-extension/field kernels are the project and interpreter overhead forces a C extension, defeating "from scratch"; C++ is rejected for memory-safety and tooling friction at equal performance, and because exhaustive match on protocol messages prevents an entire class of security-relevant omissions. All crates — field, rng, sharing, transport, OT, triples, circuit, arithmetic, boolean, protocol, applications, CLI — are Rust.

2. Why Build This

2.1 Unique Systems Knowledge Taught

  • Why addition of secret shares is free (local) but multiplication is hard (needs interaction/correlated randomness) — the central structural fact of linear-sharing MPC.
  • How oblivious transfer is the universal primitive for boolean MPC, and how OT extension (IKNP) amortizes expensive base OTs into millions of cheap ones via a PRG + a matrix transpose.
  • How Beaver triples decouple the expensive multiplication into an input-independent offline phase and a cheap online phase of two openings + local arithmetic.
  • How Yao's garbled circuits turn a boolean circuit into encrypted truth tables, and how free-XOR (a global secret offset Δ) and half-gates drive communication toward 2 ciphertexts per AND gate.
  • Why semi-honest security is precisely "the corrupted parties' joint view is simulatable from inputs+outputs," and where that breaks if a party deviates (motivating malicious security).
  • How rounds vs. communication trade off across protocols (Yao constant-round but heavy; GMW low-bandwidth but depth-many rounds), and why circuit AND-depth is the latency driver.

2.2 Historical and Architectural Significance

MPC begins with Yao's 1982/1986 garbled circuits (two-party) and the 1987–88 generality results: GMW (Goldreich–Micali–Wigderson, any function, OT-based) and BGW (Ben-Or–Goldwasser–Wigderson, information-theoretic, honest majority). Beaver (1991) introduced multiplication triples; IKNP (Ishai–Kilian–Nissim–Petrank 2003) made OT extension practical; free-XOR (Kolesnikov–Schneider 2008) and half-gates (Zahur–Rosulek–Evans 2015) made garbling fast; SPDZ (Damgård et al. 2012) brought efficient malicious security. These protocols underpin real deployments: private set intersection (contact discovery), secure auctions (Danish sugar-beet auction, 2008), privacy-preserving analytics, threshold signing, and federated computation. Reconstructing the stack from scratch demystifies "computing on encrypted data" into concrete algebra (sharing), combinatorics (OT/garbling), and protocol engineering (rounds, transport, preprocessing).

2.3 Engineering Muscles Developed

  • Constant-time, side-channel-aware low-level crypto kernels (field ops, AES-based PRF).
  • Bit-level and matrix-transpose engineering for OT extension throughput.
  • Designing protocols as state machines over a typed message/channel layer with strict round discipline.
  • Reasoning about information leakage at every boundary and encoding it as invariants.
  • Decomposing computation into offline/online phases and managing correlated-randomness stores.
  • Deterministic multi-party simulation + replay for debugging distributed protocols.

2.4 Production Engineering Concepts Exercised

  • Reproducible seeded transcripts for tests vs. CSPRNG in real runs — and never confusing the two.
  • Communication/round accounting as first-class telemetry (the real cost metric of MPC).
  • Graceful, loud failure on malformed messages, share/degree mismatch, reconstruction below threshold, and OT/garble inconsistencies.
  • Preprocessing material as a consumable resource with exhaustion guards (don't run online without enough triples/OTs).
  • A clean trust boundary: what each party sees is auditable; the simulator can assert "view reveals nothing beyond output."

2.6 Calibration Value

After this project, "compute on private data" becomes a transparent pipeline: share inputs → evaluate a circuit gate-by-gate (free linear ops, interactive multiplications via triples/OT/garbling) → reconstruct only the output. The engineer can quantify the cost of a private computation (field-muls, OTs, ciphertexts, rounds, bytes), explain why XOR is free and AND costs an OT/ciphertext, predict that Yao is constant-round but bandwidth-heavy while GMW is depth-many rounds, and debug a wrong result by replaying a seeded transcript and inspecting each party's view.

What Mastery Looks Like — finishing this blueprint means you can:

  • Build Shamir (t,n) secret sharing from scratch — sample degree-t polynomials, Lagrange-interpolate mod p, and argue the information-theoretic privacy of any ≤t shares (Phase 2).

3.2 Subsystem Descriptions

mpc-field — Owns finite-field arithmetic. Fp is a prime field with a fixed modulus (configurable, ≤128-bit) using Montgomery (or Barrett) reduction for constant-time multiplication; provides add/sub/mul/inverse (Fermat or extended-Euclid, constant-time path), pow, batch inversion, and uniform sampling from a SecureRng. Block is a 128-bit word interpreted as a GF(2^128) element (for free-XOR labels) and as a vector of GF(2) bits (for boolean shares/OT), with xor (= GF(2) add) and the GF(2^128) multiply used by some hashing. No protocol logic; pure algebra + sampling. The field modulus and reduction are the trust anchor for all sharing/triple correctness.

mpc-rng — The randomness boundary. SecureRng wraps a CSPRNG (ChaCha20 or AES-CTR DRBG) for all security-relevant randomness in real runs. TranscriptRng is a seedable, deterministic generator used only in tests to make transcripts replayable; the type system and config keep the two from being confused (production refuses a seeded RNG). Provides domain-separated key derivation (label keys, OT seeds, share randomness) so independent random streams never collide. Every place that "samples randomness" routes through here — a single auditable faucet.

mpc-share — Linear secret sharing. AdditiveShare over F_p (or GF(2)): a secret s split into N shares summing to s; addition and scalar multiplication are local. ShamirShare: a secret embedded as p(0) of a degree-t polynomial, shares are p(i); reconstruct uses Lagrange interpolation over any t+1 points; refresh re-randomizes shares (add a sharing of 0) for proactive security/leakage hygiene. Tracks polynomial degree (Shamir multiplication doubles degree → motivates BGW degree reduction). Directly mirrors portfolio 379. Enforces the privacy invariant: any ≤t shares are uniform/independent of the secret.

mpc-transport — The communication abstraction and cost meter. The Channel trait offers typed send<T>/recv<T> between ordered party endpoints; an in-process implementation uses bounded queues (for the simulator), and a network implementation frames length-prefixed serialized messages over TCP. A broadcast helper implements echo/relay broadcast for the semi-honest setting. Every send increments a round/byte accounting counter — communication is the dominant MPC cost and is treated as first-class telemetry. No protocol semantics; just reliable, accounted, typed message passing.

mpc-ot — Oblivious transfer. Base 1-of-2 OT via a Diffie–Hellman / Naor–Pinkas construction on curve25519: sender holds (m₀,m₁), receiver holds choice bit b, learns m_b only, sender learns nothing about b. IKNP OT extension turns κ base OTs (with roles reversed) into m OTs of long strings via a PRG and a bit-matrix transpose, the throughput-critical kernel. Random-OT (R-OT) and correlated-OT (C-OT) variants feed triple generation and GMW AND gates. Sender/receiver state machines with transcript hooks; the privacy invariants (receiver hides b, sender hides m_{1−b}) are enforced and tested here.

mpc-triples — Beaver multiplication triples. Generates secret-shared (⟨a⟩,⟨b⟩,⟨c⟩) with c=a·b, a,b uniform, in an offline (input-independent) phase using OT (Gilboa multiplication / OT-based product sharing) — an HE-based path is sketched and cross-linked to 391. A triple store holds preprocessed triples; the consumption API hands them to the online multiplication and guards against exhaustion. A test-mode opening verifies c=a·b. This crate embodies the offline/online split that defines modern arithmetic MPC.

mpc-circuit — Circuit IR and description. A Gate enum (Input, Add, Mul, ScalarMul, Xor, And, Inv/Not, Output) with wire indices; arithmetic circuits over F_p and boolean circuits over GF(2); a builder API and a Bristol-format reader for standard test circuits (AES, adders, comparators). Computes topological order, depth, width, and AND-depth/multiplicative-depth (the round-count driver). Decoupled from how gates are evaluated; consumed by both mpc-arith and mpc-bool.

mpc-arith — Arithmetic-circuit MPC over F_p. Addition/scalar gates are local on shares (free). Multiplication gates use Beaver triples: parties open d=x−a, e=y−b, then compute ⟨z⟩=⟨c⟩+d⟨b⟩+e⟨a⟩+d·e. The BGW variant instead multiplies Shamir shares locally (degree doubles) then performs degree reduction via a re-sharing/Lagrange step, requiring honest majority t<N/2. Input sharing distributes each party's private value; output reconstruction opens only the designated output wires. The first crate that produces a private computation result.

mpc-bool — Boolean MPC. GMW: XOR/NOT gates are local on additive GF(2) shares; AND gates consume a (boolean) Beaver triple or a 1-of-4 OT, costing interaction per AND and rounds proportional to AND-depth. Yao garbled circuits (two-party): the garbler assigns two random labels per wire, builds encrypted truth tables with point-and-permute (signal bits select the row), free-XOR (label₁=label₀⊕Δ for a global Δ so XOR gates are free), and half-gates (2 ciphertexts per AND); the evaluator obtains its input labels via OT and decrypts gate-by-gate, then decodes the output. Two complementary boolean paradigms with opposite round/bandwidth profiles.

mpc-protocol — Orchestration. The Protocol trait abstracts setup → preprocess → online → output; concrete protocols (BgwArith, GmwBool, YaoGc) are selected and configured with a security parameter and party set. Schedules rounds, distributes inputs, wires the preprocessing store to the online phase, and delivers outputs. Owns the round discipline (no party advances until the round's messages arrive) and the leakage contract (only outputs are revealed). The seam between "what to compute" and "how parties coordinate."

mpc-app — Applications. Secure sum (additive sharing + open), secure multiplication (triples), secure comparison (bit-decomposition / DGK-style less-than), basic private set intersection (OT-/hashing-based), the millionaires' problem (Yao/GMW comparison), and a sealed-bid auction (max + identity of winner). Each is a worked, runnable demonstration that the lower layers compose into useful private computations, with explicit leakage statements (what the output reveals).

6. Design Principles

P1. Linear Operations Are Free; Multiplication Costs Interaction

Addition, subtraction, and scalar multiplication of shares are local (no communication); multiplication needs correlated randomness (triples) or degree reduction (BGW) or OT (GMW AND). Tradeoff: circuit design favors low multiplicative/AND depth. Violation: treating multiplication as local produces shares that don't reconstruct to the product — silently wrong results.

P2. The Randomness Faucet Is Single, Typed, and Auditable

All security-relevant randomness flows through mpc-rng::SecureRng; tests use TranscriptRng (seeded) and production refuses a seeded RNG. Tradeoff: a small indirection cost. Violation: an ad-hoc rand::random() in a kernel makes a real run insecure (predictable shares/labels) while passing tests.

P3. Semi-Honest Means the View Is Simulatable

Every protocol must admit a simulator producing a corrupted coalition's view from its inputs+outputs alone. Tradeoff: extra masking/re-randomization steps that look "unnecessary." Violation: a missing re-randomization (e.g., opening x·y instead of x−a) leaks a private value even though the final output is correct.

P4. One Field, One Endianness, One Label Format — Everywhere

Field modulus, byte order of serialized field elements, label/Block bit layout, and signal-bit (point-and-permute) convention are fixed and identical across crates and across the wire. Violation: two parties disagreeing on byte order or signal bit silently compute a different function or fail to decrypt a gate.

P5. Offline/Online Separation Is Strict

Preprocessing (triples, OTs, garbled tables) is input-independent and may run ahead; the online phase consumes it and must never generate fresh correlated randomness that depends on inputs out-of-band. Tradeoff: a preprocessing store + exhaustion bookkeeping. Violation: leaking input-dependence into the offline phase breaks the security argument and the cost model.

P6. Round Discipline Is Explicit and Enforced

No party advances past round r until all round-r messages have arrived; rounds are counted. Tradeoff: explicit barriers/state machines instead of fire-and-forget. Violation: out-of-order message consumption causes deadlock, wrong reads, or (network) silent desync.

P7. Fail Loud, Before Revealing Anything

Malformed message, degree/share mismatch, sub-threshold reconstruction attempt, OT/garble inconsistency, or triple exhaustion are detected and fail before any output is opened. Tradeoff: validation overhead. Violation: a half-run protocol may open partial intermediate values, leaking inputs.

P8. Constant-Time Where Secrets Branch

Field inverse, share comparisons, OT choice handling, and label selection use constant-time primitives (subtle) so timing doesn't leak secret bits. Tradeoff: no data-dependent fast paths in secret code. Violation: a secret-dependent branch is a timing side channel that defeats the cryptographic guarantee.

P9. Communication Is the Cost Metric, and It Is Measured

Bytes and rounds per party are first-class telemetry; protocols report them. Tradeoff: accounting hooks in the transport. Violation: optimizing CPU while ignoring a chatty protocol misses the real bottleneck (MPC is communication-bound).

P10. Reconstruction Reveals Only Designated Outputs

Only wires marked Output (and agreed by all parties) are reconstructed; intermediate shares are never opened in the clear. Violation: opening an intermediate wire for "debugging" in a real run is a privacy breach — debug only via seeded simulation.

P11. Determinism in Tests, Never in Production Security

Seeded transcripts make tests replayable and protocol bugs reproducible, but the same mechanism in a real run is catastrophic. The build/config enforces the split (P2). Violation: shipping the test RNG.

P12. Gate and Message Types Are Exhaustive Enums

Gate, OT message, share, and protocol-step types are closed enums matched exhaustively, so adding a variant forces every handler to address it. Violation: a catch-all _ => arm hides an unhandled (and possibly insecure) case.

8.2 Finite Fields and Encoding (P4)

F_p: fixed prime modulus p (configurable; default examples: 2^61−1 Mersenne for fast reduction, or a 128-bit prime). Elements stored in Montgomery form for constant-time multiplication; conversion to/from canonical form at the serialization boundary. Wire byte order is little-endian fixed-width (⌈log₂ p⌉ rounded to bytes). GF(2): a single bit; vectors packed into Blocks. Block is a u128 (or [u8;16]); bit i of a block is a definite, documented position (lsb-first). Free-XOR uses GF(2^128) with a fixed irreducible polynomial for the (rare) field-multiply in some hash constructions; the common operation is XOR (GF(2) vector add). All parties MUST agree on (p, byte order, block bit layout, signal-bit position) — encoded as a versioned FieldConfig exchanged at setup (I12).

8.3 Secret Sharing (Additive + Shamir)

Additive (N-party, threshold N−1 for privacy): to share s∈F_p, sample s₁,…,s_{N−1} uniform, set s_N = s − Σ s_i. Reconstruct = Σ. XOR-additive for GF(2). Local: ⟨s+s'⟩=⟨s⟩+⟨s'⟩, ⟨α·s⟩=α·⟨s⟩. Shamir (t,n): pick random degree-t polynomial p with p(0)=s; share to party i is p(i) (i=1..n). Reconstruct from any t+1 shares via Lagrange:

s = Σ_{i∈S} p(i) · Π_{j∈S, j≠i} (0 − x_j)/(x_i − x_j)   (mod p)

Privacy (I1): any ≤t shares are uniform/independent of s (information-theoretic). refresh() adds a fresh sharing of 0 (re-randomize without changing the secret). Multiplication of Shamir shares multiplies the polynomials → degree 2t, requiring degree reduction (BGW) to return to degree t (I15) and honest majority 2t<n.

8.4 Oblivious Transfer (Base + IKNP Extension)

Base 1-of-2 OT (Naor–Pinkas / DH): over a group with generator g. Receiver with bit b: pick k, send B = g^k if b=0 else B = h·g^k (h = sender's public element). Sender derives two keys, encrypts m₀,m₁; receiver decrypts only m_b (I5). IKNP extension (turn κ base OTs into m OTs):

Roles reversed for base OTs. Receiver has choice vector r∈{0,1}^m.
Receiver builds m×κ matrices T0,T1 with T0⊕T1 = r⊗1 (each row = r_i repeated).
Base OT (sender=IKNP receiver) transfers one column-seed per base OT.
Sender obtains Q (m×κ) with Q = T0 ⊕ (r outer s) where s = sender's base choices.
Transpose to row form; sender's per-OT masks H(Q_j), H(Q_j⊕s); receiver computes H(T_j).

The bit-matrix transpose (m×κ → κ×m) is the throughput kernel; AES-NI for the PRG H. R-OT (random OT): outputs are pseudo-random (no inputs); C-OT (correlated OT): m₁=m₀⊕Δ for a fixed correlation — directly used by GMW AND and triple generation. Receiver privacy: sender never learns r; sender privacy: receiver learns one message per OT (I5).

8.5 Beaver Multiplication Triples (Offline + Online)

Offline: generate shared (⟨a⟩,⟨b⟩,⟨c⟩), c=a·b (I4). Two-party OT-based product sharing (Gilboa): to share a·b where party P holds a, party Q holds b, use OTs over the bit-decomposition of b to obliviously transfer a·2^i masked shares; sum gives additive shares of a·b. N-party extends pairwise. Online multiplication of ⟨x⟩,⟨y⟩ using triple (⟨a⟩,⟨b⟩,⟨c⟩):

1. locally compute ⟨d⟩ = ⟨x⟩ − ⟨a⟩,  ⟨e⟩ = ⟨y⟩ − ⟨b⟩
2. OPEN d and e (one round; reveals nothing — a,b mask x,y)   (P3, I9)
3. locally set ⟨z⟩ = ⟨c⟩ + d·⟨b⟩ + e·⟨a⟩ + d·e
   (only one party adds the public d·e term, or all add 1/N share)

Cost: 2 openings + local field ops per MUL (P1). Security: d,e are uniform (mask by fresh a,b), leaking nothing about x,y (P3). The triple is consumed (I14).

8.7 Boolean MPC — GMW

Shares are GF(2) additive (xor). XOR(a,b) = ⟨a⟩⊕⟨b⟩ local (free, P1). NOT(a) = flip one party's share. AND(a,b) needs interaction: either a boolean Beaver triple (same as §8.5 over GF(2)) or a 1-of-4 OT: parties' shares (a_i,b_i) define a function table; an OT lets them obtain shares of a·b without revealing inputs. Rounds = AND-depth (one batched round per AND layer). Communication per AND = O(κ) (one OT / one triple opening). Low bandwidth, many rounds — the GMW profile.

8.8 Boolean MPC — Yao Garbled Circuits (2-Party)

Garbler assigns each wire two labels W⁰,W¹∈{0,1}^κ. Free-XOR (I7): pick global Δ (lsb=1); set W¹ = W⁰⊕Δ for every wire. Then XOR gate output label = input₀⊕input₁ (free, no ciphertext). Point-and-permute: the lsb of each label is a signal bit (random per wire) that selects the garbled-table row, hiding the truth value. Half-gates (I8): each AND gate is garbled into 2 ciphertexts (generator half + evaluator half), each an AES-based hash of input labels XOR an output label. Garbler sends garbled tables + its own input labels + output decoding; evaluator obtains its input labels via OT (one 1-of-2 OT per evaluator input bit, choice = its input bit, I5), then decrypts gate-by-gate following signal bits, obtaining exactly one output label per gate (I8), and decodes outputs. Constant-round (independent of depth), bandwidth ∝ #AND gates.

8.9 Worked Example — Millionaires' Problem (2-party, Yao)

Inputs: Alice a (l-bit), Bob b (l-bit). Output: 1 iff a>b (both learn, or one).
Circuit: l-bit comparator (a>b) — ~l AND gates, l XOR gates.
1. Garbler (Alice) garbles the comparator: labels per wire, Δ, half-gate tables.
2. Alice sends her input-wire labels (for bits of a) + garbled tables + output map.
3. Bob (evaluator) runs l OTs: choice = bit_i(b), receives label for his wire i (I5).
4. Bob evaluates gate-by-gate → output label; decodes to bit (a>b).
5. Reveal output (and to Alice if agreed). Leakage: exactly the 1 output bit (P10).

Phase 1 — Finite fields + blocks + CSPRNG

1.1 Objectives

Build mpc-field (Fp Montgomery prime field, Block 128-bit GF(2)/GF(2^128) word) and mpc-rng (CSPRNG SecureRng, seeded TranscriptRng for tests, domain-separated KDF). Lock byte order/bit layout (P4, I12) and the randomness faucet (P2, I11). Constant-time secret ops (P8, I16). Everything builds on this algebra + randomness.

1.2 Detailed Implementation Steps

  • field/montgomery.rs: Montgomery R, R², mont_mul, to/from_mont; constant-time; Mersenne fast path for default prime. (ADR-4, ADR-6; I16)
  • field/fp.rs: Fp add/sub/mul/inverse (Fermat a^(p-2) const-time, or const-time ext-Euclid), pow, random, to/from_le_bytes (I12), batch_inverse. (Shoup, Ch. 4; I16, P8) (ADR-4, P4; I12)
  • field/block.rs + gf2.rs + pack.rs: Block(u128) xor, gf128_mul, lsb (signal bit, I7); pack/unpack GF(2) bit vectors.
  • rng/secure.rs: ChaChaRng impl SecureRng; rng/transcript.rs: deterministic seeded RNG (tests); prod_rng() refuses fixed seed (I11). (P2, ADR-5; P11)
  • rng/kdf.rs: domain-separated key derivation; sample.rs: uniform Fp/Block sampling.

1.3 Deliverable

Fp arithmetic with const-time mul/inverse; Block xor/lsb; CSPRNG + seeded test RNG; cargo test -p mpc-field -p mpc-rng green.

1.4 Acceptance Criteria

  • Field axioms: a+(-a)=0, a·a⁻¹=1 (a≠0), distributivity on random vectors.
  • batch_inverse matches per-element inverse; inverse(0)=None (CtOption).
  • Round-trip to_le_bytes→from_le_bytes identity; rejects wrong length (I12).
  • Seeded TranscriptRng reproduces identical streams; prod_rng() refuses a fixed seed (I11, P2).
  • Field-mul throughput ≥ 100M mul/sec single-core (M3, §4.1); batch_inverse ≥ 3× faster than per-element cost at batch ≥ 4.

1.6 Pitfalls

  • Non-constant-time inverse (data-dependent branches) is a timing side channel (P8, I16); use subtle.
  • Montgomery domain confusion (mixing canonical + Montgomery values) yields silently wrong products.
  • Endianness drift between to_le_bytes and the wire codec breaks cross-party agreement (I12, P4).
  • Reusing a TranscriptRng stream across domains (no separation) correlates "independent" randomness.

1.7 Performance Concerns

  • mont_mul is the field hot path; keep limbs in registers, avoid bounds checks. Mersenne fast path for the default prime is a large win.
  • batch_inverse turns n inverses into 1 inverse + 3n muls — use whenever ≥2 inversions.

1.8 Edge Cases

  • inverse(0) → None. Modulus near 2^128 (limb carry). Block lsb on all-zero/all-one. Empty byte slice rejected.

1.9 Failure Analysis

A wrong field-mul corrupts every share, triple, and label downstream. Detection: field axiom + codec fixtures; later, triple c=a·b openings. Blast radius: the entire stack. Containment: field is the most-tested foundation.

1.10 Operational Notes

tracing span tags field-op counts in benchmarks. Runbook "wrong result" starts here: verify modulus, Montgomery conversion, byte order. prod_rng refusal is logged loudly (P2).

Phase 2 — Secret sharing (additive + Shamir)

2.1 Objectives

Build mpc-share: additive sharing (mod p / xor), Shamir (t,n) with Lagrange reconstruction, refresh, and local add/scalar-mul (P1). Enforce privacy (I1), correct reconstruction (I2, I3). Sibling to portfolio 379.

2.2 Detailed Implementation Steps

  • share/additive.rs: share_additive(s,n) (n−1 uniform + remainder), reconstruct_additive (Σ); GF(2) xor variant.
  • share/shamir.rs: random degree-t polynomial with p(0)=s; evaluate at x=1..n; degree tracking field. (BGW 1988; I1, I15)
  • share/lagrange.rs: Lagrange interpolation at x=0 over any subset; reconstruct_shamir requires >t points (I2) → InsufficientShares otherwise. (Shoup, Ch. 3; P7)
  • share/refresh.rs: add a fresh sharing of 0 (re-randomize) (proactive hygiene). (P3, ADR-11; I1)
  • Local ops: add_shares, scalar_mul (free, P1); degree of sum = max, of scalar-mul = same. (P1, GMW 1987; I3)

2.3 Deliverable

Share any Fp value additively and via Shamir; reconstruct from a threshold subset; refresh; local linear ops; cargo test -p mpc-share green.

2.4 Acceptance Criteria

  • Additive: Σ shares = secret; any N−1 shares uniform/independent of secret (I1, statistical test).
  • Shamir: reconstruct from any t+1 of n shares = secret (I2); ≤t shares reveal nothing (I1).
  • reconstruct with ≤t shares → InsufficientShares (P7).
  • refresh preserves the secret, changes individual shares; local add/scalar-mul reconstruct correctly (P1, I3).
  • Privacy statistical test over ≥ 10,000 random-secret trials: ≤t-share marginals within 2⁻²⁰ of uniform (I1, sharing/privacy_marginal.json).

2.6 Pitfalls

  • Lagrange coefficients computed over integers instead of mod p give wrong reconstruction; all arithmetic in Fp.
  • Allowing reconstruction from exactly t shares (off-by-one) silently breaks privacy/threshold (I2).
  • Reusing the same polynomial randomness across secrets correlates shares (P2).
  • Degree bookkeeping: forgetting that Shamir multiplication doubles degree leads to un-reconstructable products (I15, deferred to BGW).

2.7 Performance Concerns

  • Sharing is O(n) per secret; reconstruction is O(t²) naive Lagrange or O(t log t) with precomputed barycentric weights. Batch-share many secrets sharing one polynomial-evaluation pass.

2.8 Edge Cases

  • t=0 (secret = constant poly, all shares equal — no privacy; reject/ warn). t=n−1 (max). Duplicate x-coordinates rejected (DuplicatePoint). Secret = 0 (valid).

2.9 Failure Analysis

A reconstruction bug yields wrong outputs; a privacy bug leaks inputs silently. Detection: threshold + privacy-marginal fixtures. Blast radius: every protocol's input/output handling. Recovery: tools/share-inspect dumps shares + reconstructs in test mode only (never prod, P10).

2.10 Operational Notes

share-inspect is a test/debug tool that opens shares — guarded behind a test-only flag (P10, P11). Threshold parameters (t,n) recorded in protocol config (I12). Property tests assert I1/I2/I3 over random secrets.

Phase 3 — Party + transport abstraction

3.1 Objectives

Build mpc-transport: the Channel trait (typed send/recv/broadcast), in-proc channels (simulator), TCP framed transport (network), echo broadcast (ADR 19), and round/byte accounting (P9, I10). Define the Party and message-framing model. Round discipline (P6).

3.2 Detailed Implementation Steps

  • transport/channel.rs: Channel trait; Message marker (serde); CommStats.
  • transport/inproc.rs: bounded MPSC queues per directed pair; deterministic ordering for the simulator. (P6, ADR-17; I10)
  • transport/net.rs + frame.rs: length-prefixed framing over tokio TCP; bincode serialization; per-message length cap (anti-DoS). (P7, §4.1; ADR-16)
  • transport/broadcast.rs: echo broadcast (each party relays; semi-honest sufficient).
  • transport/accounting.rs: increment bytes/rounds on each send; expose stats() (P9). (P9, ADR-23; §4.1)
  • Round barrier helper: collect all expected round-r messages before proceeding (I10, P6). (P6, ADR-6; I10)

3.3 Deliverable

Two+ parties exchange typed messages in-proc and over TCP; broadcast works; comm stats reported; round barrier enforced; cargo test -p mpc-transport green.

3.4 Acceptance Criteria

  • In-proc and network channels deliver identical message sequences for the same protocol.
  • CommStats accurately counts bytes + rounds per peer (P9).
  • Oversized message (> 16 MiB, §4.1 message size cap) → Malformed/rejected (anti-DoS).
  • Round barrier blocks until all round-r messages arrive; out-of-order → buffered or RoundDesync (I10, P6).

3.6 Pitfalls

  • Unbounded queues mask backpressure and can OOM under a chatty protocol; bound them.
  • Mixing serialization formats/byte order between in-proc and net diverges results (I12, P4).
  • Deadlock if two parties both block on recv before either sends; protocols must follow the round schedule (P6).
  • Network partial reads: framing must reassemble full length-prefixed messages.

3.7 Performance Concerns

  • Network: batch small messages per round (coalesce) to amortize TCP overhead; comm dominates MPC cost (P9). In-proc: avoid per-message allocation; reuse buffers.
  • Serialization overhead is on the hot path for OT/garble batches; use compact bincode + fixed-width field codec.

3.8 Edge Cases

  • Single party (degenerate; no channels). Party sends to self (rejected/no-op). Connection drop mid-round → Closed → abort (semi-honest: no recovery, just clean failure). Zero-byte message.

3.9 Failure Analysis

A desync or framing bug stalls or corrupts the protocol. Detection: round-barrier + inproc-vs-net fixtures; RoundDesync. Blast radius: the whole run hangs/aborts. Recovery: tools/comm-report shows per-round message counts; transcript-diff compares expected vs actual.

3.10 Operational Notes

tracing spans per round + per peer emit byte/round counts → the comm-budget telemetry (P9). Network mode logs connection lifecycle. Runbook "desync" → check round schedule + barrier. Comm budget asserted in the simulator (refuse if a protocol exceeds its stated round/byte bound).

Phase 4 — Oblivious transfer (base + IKNP extension)

4.1 Objectives

Build mpc-ot: base 1-of-2 OT (Naor–Pinkas / DH on Ristretto), IKNP OT extension (κ base OTs → m extended OTs via PRG + bit-matrix transpose), and R-OT/C-OT variants. Enforce OT security both sides (I5) and IKNP correctness (I6). The universal primitive for boolean MPC + triples.

4.2 Detailed Implementation Steps

  • ot/base.rs: Naor–Pinkas over curve25519-dalek Ristretto; sender (m₀,m₁), receiver bit b → m_b (§8.4, I5); AES/SHA for the message-masking hash. (Naor–Pinkas 2001; ADR-7)
  • ot/iknp.rs: reverse-role base OTs seed κ PRG columns; receiver builds T0/T1 from choice vector; sender obtains Q; masks via fixed-key AES H (§8.4). (IKNP 2003; ADR-9)
  • ot/transpose.rs: cache-efficient m×κ → κ×m bit-matrix transpose (Eklundh / SSE-style); the throughput kernel. (ALSZ 2013; I6, §4.1)
  • ot/rot.rs (random OT) + ot/cot.rs (correlated OT, m₁=m₀⊕Δ): feed triples + GMW AND. (IKNP 2003; I4, ADR-8)
  • Transcript hooks for seeded replay (tests); reject self-transfer (SelfTransfer).

4.3 Deliverable

Base OT transfers one of two Blocks; IKNP produces m correct OTs from κ base OTs; R-OT/C-OT variants; cargo test -p mpc-ot green; IKNP matches a base-OT oracle (I6).

4.4 Acceptance Criteria

  • Base OT: receiver obtains exactly m_b; cannot derive m_{1−b}; sender learns nothing of b (I5, view test).
  • IKNP: extended OT outputs equal base-seeded values for the receiver's choices (I6) over batch ≥ 2^16.
  • C-OT correlation holds: m₁=m₀⊕Δ for the fixed Δ.
  • Throughput ≥ 1M OTs/sec single-core (AES-NI + transpose) (§4.1).

4.5 Conformance Fixtures

Fixture Purpose Expected

ot/iknp_oracle.json I6 matches base-OT
ot/cot_correlation.json C-OT m₁=m₀⊕Δ
ot/receiver_privacy.json I5 sender view ⊥ b

4.6 Pitfalls

  • Transpose bugs corrupt a subset of OTs only on certain batch sizes — pad to alignment, test odd sizes.
  • Using a non-fixed-key or non-RO hash for H breaks the security argument; use fixed-key AES per IKNP/ALSZ.
  • Reusing base-OT seeds across IKNP batches breaks security (P2); fresh seeds per session.
  • A malicious receiver could cheat IKNP (correlation attack) — out of scope (semi-honest); note KOS check as deferred (§Phase 13).

4.7 Performance Concerns

  • The bit-matrix transpose is cache-bound; block it (e.g., 128×128 tiles) and use AES-NI for the PRG. This kernel sets OT throughput (§4.1).
  • Batch OTs (≥2^16) to amortize base-OT + transpose setup; stream rather than buffer huge batches (memory).

4.8 Edge Cases

  • m not a multiple of 128 (transpose padding). Single OT (degenerate; base OT directly). All-zero / all-one choice vector. Δ with lsb≠1 for derived free-XOR use (handled in bool, I7).

4.9 Failure Analysis

A subtle OT bug leaks m_{1−b} or b, or yields wrong extended OTs → wrong triples/AND gates. Detection: base-OT oracle + view fixtures; C-OT correlation. Blast radius: triples + GMW + Yao input OTs. Recovery: transcript-diff on the OT transcript; isolate base vs. extension.

4.10 Operational Notes

tracing reports OTs/sec, transpose time, base-OT setup time → OT-throughput telemetry. Runbook "ot-fail" → check transpose alignment, fixed-key AES, base-OT seeds. Seeded transcripts make OT bugs reproducible (test only, P11).

Phase 5 — Beaver triples (offline gen + online multiplication)

5.1 Objectives

Build mpc-triples: offline generation of shared (⟨a⟩,⟨b⟩,⟨c⟩) with c=a·b via OT (Gilboa product sharing), a consumable triple store with exhaustion guards (I14), and the online multiplication primitive (§8.5). Embodies the offline/online split (P5, I13) and triple correctness (I4).

5.2 Detailed Implementation Steps

  • triples/gen_ot.rs: OT-based product sharing — to additively share a·b from a@P and b@Q, run OTs over the bits of b transferring masked a·2^i terms; combine to additive shares of a·b. N-party via pairwise products + local sums. (Beaver 1991; I4, ADR-12)
  • triples/store.rs: TripleStore holding preprocessed triples; take() with Exhausted guard (I14); provenance tag = offline (I13). (P5, P7; ADR-12)
  • triples/verify.rs: test-mode verify_triple_open opens a,b,c and checks c=a·b (I4) — tests only (P10). (I4, ADR-24; P10)
  • Online multiplication API in mpc-arith (Phase 6 consumes): open d=x−a, e=y−b; combine (§8.5, §8.10).
  • HE-based generation sketch in gen_he.rs (deferred, cross-link 391): PhaseDeferred("FINAL_BLUEPRINT §Phase 6"). (P5, ADR-12; Phase 6)

5.3 Deliverable

Generate batches of valid Beaver triples offline; store + consume them; online multiply two secret-shared values correctly; cargo test -p mpc-triples green.

5.4 Acceptance Criteria

  • Generated triples satisfy c=a·b, a,b uniform (I4, test-open over a batch).
  • Online multiply ⟨x⟩·⟨y⟩ reconstructs to x·y (I4) for random x,y; opened d,e uniform (leakage test, P3).
  • take() on empty store → Exhausted (I14, P5/P7).
  • Triple provenance is offline/input-independent (I13).
  • Triple generation batch ≥ 1,000 triples verifies c=a·b with zero failures (I4, M12: ≥3,900 triples/sec single-core at 128-bit prime).

5.5 Conformance Fixtures

Fixture Purpose Expected

triples/online_mul.json online reconstruct x·y
triples/de_uniform.json P3 d,e uniform

5.6 Pitfalls

  • Forgetting the d·e public term (or adding it from every party instead of once) gives wrong product shares (§8.5).
  • Generating triples that depend on inputs (leaking into offline) breaks security + cost model (I13, P5).
  • Opening x·y or x,y directly instead of the masked d,e leaks inputs (P3) even with a correct result.
  • Insufficient triples mid-circuit stalls online; pre-count required triples = #MUL/#AND gates (I14).

5.7 Performance Concerns

  • Triple generation is the offline bottleneck (many OTs per triple); batch and parallelize across cores. Online multiplication is cheap (2 openings + local) — the offline/online split moves cost off the critical path (P5).
  • Triple store should stream from generation, not buffer the entire offline output in memory.

5.8 Edge Cases

  • a=0 or b=0 (valid triple, c=0). Multiplying a share by a public constant uses ScalarMul (no triple). N=2 vs N>2 generation paths. Batch size 0.

5.9 Failure Analysis

A bad triple yields a wrong multiplication → wrong output, hard to localize. Detection: test-open c=a·b + online-mul reconstruct fixtures. Blast radius: every MUL/AND gate. Recovery: regenerate triples; verify_triple_open (test) bisects gen vs. consume.

5.10 Operational Notes

tracing reports triples/sec (offline), store depth, triples consumed per circuit (P9, I14). Runbook "bad-triple" → check product-sharing OTs + d·e term. Offline/online provenance logged (I13). Exhaustion is a loud pre-online refusal (P7).

Phase 6 — Arithmetic-circuit MPC (BGW / GMW-arithmetic)

6.1 Objectives

Build mpc-arith: the arithmetic evaluator over F_p — local Add/ScalarMul (free, P1), Beaver multiplication (consumes triples, §8.5), BGW degree reduction (Shamir-share multiply then re-share to degree t, I15, honest majority), input sharing, output reconstruction (only outputs, I9). First end-to-end private computation result.

6.2 Detailed Implementation Steps

  • arith/input.rs: each party shares its private input to all (additive or Shamir); collect input wires.
  • arith/eval.rs: walk Circuit in topological order; Add/ScalarMul local; dispatch Mul to Beaver or BGW; batch independent multiplications into one round (minimize rounds, P6/P9). (P1, GMW 1987; ADR-12)
  • arith/beaver.rs: online multiplication (open d,e; combine §8.10); consume TripleStore (I14). (Beaver 1991; I4, §8.5)
  • arith/bgw.rs: multiply Shamir shares locally (degree 2t), each party re-shares its product share via a fresh degree-t polynomial, parties Lagrange-combine to a degree-t sharing of the product (I15); requires 2t<n. (BGW 1988; I15, ADR-11)
  • arith/output.rs: reconstruct only Output wires (I9, I10); never intermediate wires (P10). (P3, P10; I9)

6.3 Deliverable

Evaluate an arithmetic circuit (e.g., dot product, weighted sum, polynomial) over N parties' private inputs; reveal only the output; both Beaver and BGW multiplication paths work; cargo test -p mpc-arith green.

6.4 Acceptance Criteria

  • Secure sum / dot-product / a·b+c reconstruct to the cleartext result (I3, I4).
  • Beaver path: round count = #multiplication-layers (batched); BGW path: degree after reduction = t (I15).
  • Only output wires opened (transcript audit, I9, P10).
  • BGW honest-majority parameter 2t<n enforced (e.g. n=5 ⇒ t≤1 shares tolerated); violation → config error.

6.6 Pitfalls

  • Opening intermediate multiplication results instead of using triples/reduction leaks values (P3, P10).
  • BGW degree reduction errors leave degree-2t shares that need >n points to reconstruct (I15) — wrong/failed output.
  • Not batching independent multiplications inflates round count (P9) — group by circuit layer.
  • Mixing additive and Shamir sharing in one evaluator without conversion corrupts arithmetic (one scheme per evaluator, or explicit conversion).

6.7 Performance Concerns

  • Round count is dominated by multiplicative depth (batched layers); minimize by circuit design + batching (P9). Local linear ops are free (P1). Communication per multiplication = O(N) field elements (openings).
  • For many parallel multiplications, coalesce all d,e openings of a layer into one broadcast round.

6.8 Edge Cases

  • Circuit with only linear gates (no triples needed; one output round). Single multiplication. N=2 (additive + triples, no honest majority needed). Output wire = input wire (passthrough).

6.9 Failure Analysis

A wrong multiplication or premature opening corrupts the result or leaks inputs. Detection: dot-product + output-only fixtures; BGW degree assert. Blast radius: the computation's correctness + privacy. Recovery: replay seeded transcript; transcript-diff per round; check triple consumption order.

6.10 Operational Notes

tracing reports per-layer rounds, multiplications, triples consumed, bytes (P9). Output reconstruction logged as the single revealing event (I9). Runbook "wrong result (arith)" → field → sharing → triple → opening order. BGW parameter 2t<n checked at setup (I12).

Phase 7 — Boolean MPC via GMW (XOR free, AND via OT/triples)

7.1 Objectives

Build the GMW path in mpc-bool: additive GF(2) shares, XOR/NOT local (free, P1), AND via a boolean Beaver triple or 1-of-4 OT (§8.7), rounds = AND-depth. Low-bandwidth, depth-many-rounds boolean MPC. Complements Yao (Phase 8).

7.2 Detailed Implementation Steps

  • bool/gmw.rs: GF(2) additive shares; XOR = xor of shares (local); NOT = flip one party's share. (GMW 1987; P1, I3)
  • AND gate: consume a boolean Beaver triple (same online formula over GF(2), §8.5) or run a 1-of-4 OT encoding the AND truth table; produce a share of a·b. (Beaver 1991; I4, ADR-12)
  • Layer batching: all AND gates at the same depth run in one round (OT/opening batch) (P6, P9). (P9, ADR-13; §4.1)
  • Integrate with mpc-circuit boolean circuits + Bristol reader (Phase 9) for standard circuits (AES, adder).
  • Output reconstruction: open only output wires (I9). (P10, I9; ADR-15)

7.3 Deliverable

Evaluate a boolean circuit (e.g., 64-bit adder, equality, comparator) over parties' private bit-inputs via GMW; reveal only outputs; cargo test -p mpc-bool (GMW) green.

7.4 Acceptance Criteria

  • XOR/NOT local (no communication); AND consumes one OT/triple per gate (P1).
  • Boolean adder/comparator reconstruct to the cleartext result.
  • Round count = AND-depth (batched layers) (P6, P9); e.g. a 64-bit comparator (AND-depth=64, M10) completes in exactly 64 batched rounds.
  • Only output wires opened (I9, P10).

7.5 Conformance Fixtures

7.6 Pitfalls

  • Treating AND as local (like XOR) is the classic GMW error — silently wrong shares (P1).
  • Not batching same-depth ANDs explodes rounds (network latency dominates) (P9).
  • 1-of-4 OT table ordering must match the share convention (P4) or AND yields wrong bit.
  • Forgetting NOT only flips one party's share (flipping all double-negates) → wrong result.

  • GMW is communication-light per gate but round-heavy (one per AND layer); latency × AND-depth dominates over a WAN (P9). Batch aggressively. AND triple generation reuses Phase 5/4 (OT).
  • For high AND-depth circuits, Yao (constant-round, Phase 8) may win despite higher bandwidth — the round/bandwidth tradeoff.

7.8 Edge Cases

  • Circuit with no AND gates (fully local; one output round). Single AND. Constant inputs (0/1). NOT of a constant. N>2 GMW (pairwise AND via triples).

7.9 Failure Analysis

A wrong AND or local-treatment bug corrupts results. Detection: adder/comparator fixtures with known outputs; AND-cost + round fixtures. Blast radius: the boolean computation. Recovery: replay transcript; isolate AND gate via single-gate fixtures; check OT/triple path.

7.10 Operational Notes

tracing reports AND-depth, rounds, OTs/triples consumed, bytes (P9). Runbook "wrong result (gmw)" → XOR/NOT locality → AND OT/triple → batching. Round count asserted vs AND-depth in the simulator (comm budget).

Phase 8 — Yao garbled circuits (2-party)

8.1 Objectives

Build the Yao path in mpc-bool: garbling with point-and-permute + free-XOR (I7) + half-gates (2 ciphertexts/AND, I8), OT for the evaluator's input labels (I5), gate-by-gate evaluation, and output decode. Constant-round 2-party boolean MPC; complements GMW. BMR (multi-party) sketched/deferred.

8.2 Detailed Implementation Steps

  • bool/freexor.rs: sample global Δ (lsb=1, I7); per-wire label₀ random, label₁=label₀⊕Δ; XOR gate output label = xor of input₀ labels (free, no ciphertext). (Kolesnikov–Schneider 2008; I7, ADR-14)
  • bool/garble.rs + halfgate.rs: per AND gate, build 2 half-gate ciphertexts via fixed-key AES hash of input labels + gate index, encrypting the output label; signal bits (lsb) order the rows (point-and-permute). (Zahur–Rosulek–Evans 2015; I8, ADR-9)
  • bool/evaluate.rs: evaluator holds one label per wire; for XOR, xor labels; for AND, decrypt the row selected by input signal bits → exactly one valid output label (I8).
  • OT for evaluator inputs: one 1-of-2 OT per evaluator input bit (choice = input bit) → its input-wire label (I5); garbler sends its own input labels directly. (IKNP 2003; I5, ADR-8)
  • bool/decode.rs: map final output labels → bits via the output decoding table; reveal only outputs (I9). (P10, I9; ADR-14)

8.3 Deliverable

Garble + evaluate a boolean circuit (e.g., AES-128, comparator) between 2 parties; output matches the plaintext circuit; XOR free, AND = 2 ciphertexts; cargo test -p mpc-bool (Yao) green.

8.4 Acceptance Criteria

  • Garbled circuit evaluates to the same output as the plaintext circuit (I8) for all input pairs (truth-table check on small circuits; AES test vector on AES-128).
  • Free-XOR invariant: every wire's two labels differ by Δ, lsb(Δ)=1 (I7).
  • Each AND gate decrypts to exactly one valid output label (I8); 2 ciphertexts/AND, 0 for XOR.
  • Evaluator obtains input labels via OT without revealing its input (I5); only outputs decoded (I9).

8.5 Conformance Fixtures

Fixture Purpose Expected

garble/freexor_invariant.json I7 wire1=wire0⊕Δ
garble/halfgate_count.json half-gates 2 ctx/AND, 0/XOR

8.6 Pitfalls

  • Δ lsb≠1 breaks point-and-permute decryption (I7) — assert at garbling.
  • Reusing a label/gate-index in the AES hash across gates breaks security (PRF reuse); include a unique tweak per gate.
  • Wrong signal-bit (PnP) row selection decrypts the wrong row → garbage or ambiguous label (I8, DecodeAmbiguous).
  • Garbler and evaluator disagreeing on circuit/topology or label format computes the wrong function (P4, I12).
  • Half-gate generator/evaluator ciphertext roles swapped → evaluation fails.

8.7 Performance Concerns

  • Garbling/evaluation is AES-bound (fixed-key AES-NI); target several M gates/sec. XOR free (no AES); AND = 2 AES + 2 ciphertexts. Bandwidth ∝ #AND gates × 32 B.
  • Constant round (one OT round + sending tables) — latency-insensitive vs GMW; bandwidth-heavy. Pipeline garbling↔evaluation for large circuits (garble-and-send streaming).

8.8 Edge Cases

  • Circuit with only XOR gates (no ciphertexts; free). Single AND. Constant wires. Evaluator with no inputs (garbler-only inputs). Output = input (passthrough). AES-128 (the canonical large garbled circuit).

8.9 Failure Analysis

A garbling bug yields wrong/ambiguous output. Detection: AES-vector + truth-table + free-XOR fixtures. Blast radius: the 2-party computation. Recovery: transcript-diff; isolate to a gate via small-circuit truth tables; verify Δ/PnP/half-gate hash tweak.

8.10 Operational Notes

tracing reports gates/sec (garble + eval), ciphertexts sent, AND count, OT count (P9). Runbook "garble-mismatch" → Δ lsb → PnP signal bits → half-gate hash tweak → label format. BMR (multi-party garbling) is PhaseDeferred("FINAL_BLUEPRINT §Phase 8"). Output decode is the single revealing step (I9).

Threat Model

The framework targets a semi-honest (honest-but-curious), static adversary corrupting up to t parties: corrupted parties follow the protocol exactly but pool their views to learn about honest inputs. The attack surface is (1) the messages on the wire (a corrupted party's transcript), (2) untrusted inputs/circuits fed to a party, and (3) the transport (network bytes). Malicious deviation is out of scope (deferred §Phase 13) and is stated loudly in SECURITY. The core security property: a corrupted coalition's joint view is simulatable from its inputs+outputs (P3) — nothing else leaks.

Fundamental ceilings: communication (bytes × rounds) is the dominant cost of MPC, not local CPU — the protocol's round/bandwidth profile (set by AND/mul-depth and #AND gates) is the scaling limit, and over a WAN, round count (latency) dominates, flipping the GMW↔Yao choice. Party count scales pairwise (triples, openings, broadcasts); honest-majority protocols (BGW) cap corruption at t<N/2. Pushing to large N or deep circuits is a protocol-choice and batching problem, not a kernel-speed problem; and malicious security (deferred) adds a documented constant-factor (MACs + sacrifice + checks) on top of all of the above.

Mental Models & First Principles

  1. MM1 — Linear operations on shares are free; multiplication is the only hard operation. Predicts: which gates require interaction (MUL/AND) vs which are local (ADD/XOR/scalar-mul). Without it: you attempt to implement multiplication as a local operation and produce shares that add to x·y − noise instead of x·y, silently. Applied: P1, §8.6, Phase 5, Phase 6, Phase 7.

  2. MM2 — Simulation-based security is an equivalence of two distributions, not a property of one execution. Predicts: whether a protocol leaks — ask "does there exist a PPT simulator S producing a view indistinguishable from the real view?" Without it: you judge security by "the output is correct," missing that a correct output can still leak partial information about inputs through intermediate values. Applied: P3, §7 (I1, I9), Phase 12.

  3. MM3 — Offline/online split moves correlated-randomness cost off the input-aware critical path. Predicts: the online phase's cost is just 2 field openings + local ops per MUL, regardless of how expensive triple generation is. Without it: you generate triples during the online phase (input-dependent randomness), violating I13 and eliminating the cost amortization property. Applied: P5, §8.5, Phase 5, Phase 10.

  4. MM4 — The IKNP matrix transpose is the throughput kernel, not the cryptography. Predicts: OT-extension throughput is bounded by cache-bandwidth × AES-NI rate on the m×κ transpose, not by base-OT count. Without it: you benchmark OT extension on small batches and conclude it is slow, missing the 2^16+ batch threshold where AES-NI amortizes dominantly. Applied: §8.4, Phase 4, Phase 11.

  5. MM5 — Free-XOR is a global structural secret, not a per-gate choice. Predicts: XOR gates cost zero ciphertexts if and only if Δ is kept secret from the evaluator and is global across all wires. Without it: you generate a fresh Δ per gate (OR expose it), breaking the label invariant I7 and making point-and-permute decrypt the wrong rows. Applied: §8.8, §7 (I7), Phase 8, ADR-14.

  6. MM6 — AND-depth, not gate count, drives GMW round complexity; gate count drives Yao bandwidth. Predicts: for a circuit with AND-depth d and A AND-gates, GMW costs d × RTT and A × κ bits bandwidth; Yao costs O(1) × RTT and A × 32 B bandwidth. The crossover is at RTT × d ≈ A × 32 B / link-speed. Without it: you always choose the same protocol for all circuits, leaving 10–100× performance on the table for WAN vs LAN. Applied: §4.1, §8.7, Phase 7, Phase 8, Phase 11.

  7. MM7 — A Beaver triple is a pre-committed random multiplication, not correlated randomness in the traditional sense. Predicts: the correctness of online multiplication requires that a,b are independent of x,y at the time of opening d=x−a, e=y−b; any correlation between the triple generation and the online inputs is a security break. Without it: you reuse or leak triples across protocol runs, creating a joint distribution on (d,e,x,y) that violates the uniformity requirement (I4). Applied: §8.5, Phase 5, Threat Model.

  8. MM8 — Communication is the dominant cost of MPC, not CPU; round-count is the dominant latency driver. Predicts: optimizing AES kernels while ignoring round count is the wrong priority on a WAN; the correct metric is (bytes × bandwidth-delay product) + (rounds × RTT). Without it: you profile CPU throughput and declare victory while a WAN run takes 100× longer due to AND-depth × RTT. Applied: P9, §4.1, Phase 11, Scalability Analysis.

  9. MM9 — Secret sharing is information-theoretically private; OT-based garbling is computationally private. Predicts: BGW (Shamir-based, information-theoretic honest majority) and Yao/GMW (computational, OT-based) have fundamentally different trust assumptions — BGW is secure even against unbounded adversaries within the honest majority; Yao/GMW requires the OT to be computationally secure. Without it: you compare the two paradigms on speed alone and miss that they have incompatible security models for different threat environments. Applied: §8.3, §8.6, Phase 6, Phase 7, Phase 8, Threat Model.

  10. MM10 — The point-and-permute signal bit is a permutation key, not a truth value. Predicts: the signal bit selects which ciphertext row the evaluator decrypts without revealing whether the wire carries 0 or 1; it must be random per wire (not derived from the label value) or the evaluator learns the wire's truth value trivially. Without it: you set the signal bit = lsb(label) with Δ having lsb=1, making the signal bit reveal the wire value (the known free-XOR correlation), a complete break of PnP security. Applied: §8.8, §7 (I7, I8), Phase 8, ADR-14.

Back-of-Envelope Capacity Model

  1. Field element size. From §4.1: prime ≤128-bit, default 64-bit Mersenne-like. At 64-bit: 1 field element = 8 B. At 128-bit: 16 B. All per-message estimates below use 16 B (worst-case; 64-bit halves them). Design consequence: choose 64-bit prime unless the application requires 128-bit security on field elements (rare; κ=128 applies to labels/OT, not necessarily F_p).

  2. Base-OT bandwidth (κ=128 OTs). From §4.1: κ=128 base OTs seed IKNP. Each Naor–Pinkas OT over Ristretto: a Ristretto point is 32 B; sender sends ≈2 group elements (32 B each), receiver sends 1 (32 B). Total per session ≈ κ × 3 × 32 B = 128 × 96 B ≈ 12 KB. Design consequence: base-OT setup is a one-time sub-ms cost; amortized over millions of extended OTs it is negligible. Matches §4.1 "κ=128 base OTs seed IKNP for arbitrarily many extended OTs."

  3. IKNP OT-extension bandwidth per OT. From §4.1: κ=128 security parameter; each extended OT transfers 2 × κ-bit ciphertexts from sender = 2 × 16 B = 32 B sender-side. Receiver sends a κ-bit correction column per OT batch ≈ κ/m overhead per OT (negligible for m ≥ 2^16). At 1M OTs: sender transmits ~32 MB; receiver ~2 MB (choices + corrections). At target ≥1M OTs/sec: OT bandwidth = ~32 MB/s upstream per session — feasible on LAN, tight on WAN 10 Mbps. Design consequence: batching ≥ 2^16 OTs per session is necessary to amortize base-OT setup (§4.1).

  4. Garbled-circuit bandwidth per AND gate. From §4.1: half-gates = 2 ciphertexts × 16 B = 32 B/AND; XOR = 0 B. AES-128 circuit (Bristol): ~36,000 AND-gates → 36,000 × 32 B ≈ 1.15 MB per garbled AES evaluation. At garbling rate ≥5M gates/sec (§4.1): time to garble AES ≈ 36,000 / 5,000,000 ≈ 7 ms. Design consequence: garbling latency is CPU-bound (7 ms) not bandwidth-bound (1.15 MB over LAN); streaming garble↔send wins over buffering for large circuits.

  5. GMW AND communication per gate. From §4.1: κ=128-bit security; each AND via 1-of-4 OT or boolean triple opening ≈ O(κ) bits = 16 B/AND (half-gate OT path). For an l=64-bit comparator: AND-depth ≈ 64; AND-count ≈ 64. Total comm ≈ 64 × 16 B = 1 KB. Rounds = AND-depth = 64 (from §4.1 GMW rounds = O(AND-depth)). At 100 ms RTT (WAN): latency = 64 × 100 ms = 6.4 s. Same comparator in Yao: 64 × 32 B = 2 KB, 1 RTT ≈ 100 ms. Design consequence: WAN comparison latency favors Yao over GMW by ~64× for this circuit (confirming Scalability Analysis).

  6. Beaver triple offline cost (OT-based). From §4.1 and §8.5: each arithmetic triple requires ≈ 2 × bit-length(p) OTs for Gilboa product sharing (one OT per bit of b). At 128-bit prime: 2 × 128 = 256 OTs/triple. At ≥1M OTs/sec (§4.1): triple generation rate ≥ 1,000,000 / 256 ≈ 3,900 triples/sec (single-core). At 64-bit prime: ≈7,800 triples/sec. Design consequence: for a circuit with T MUL gates, offline phase needs T × 256 OTs; pre-generate in bulk before online to avoid startup latency. Startup budget §4.1 < 500 ms → at 3,900 triples/sec: ≤1,950 triples in 500 ms limit; for larger circuits, batch offline before the clock starts.

  7. Preprocessing store size. From §4.1 and §8.5: each Beaver triple holds 3 field elements (a,b,c shares). At 128-bit prime: 3 × 16 B = 48 B/triple. For 100,000 triples: 4.8 MB. For 1M triples: 48 MB. Design consequence: stream the preprocessing store; do not buffer 1M triples in memory simultaneously unless RAM is not a constraint (§4.1 "Memory: bounded; stream large batches").

  8. Round overhead for Beaver online multiplication. From §4.1 and §8.10: each Beaver MUL layer = 1 round (batch open d,e for all same-depth MULs). At N parties, each broadcasts (di,ei): N × 2 field elements = N × 32 B per MUL layer (128-bit prime). At N=5 parties: 160 B/round. At 100 ms RTT: latency per MUL layer = 100 ms. For a circuit with 10 multiplicative layers: 1 second online latency over WAN. Design consequence: minimize multiplicative depth aggressively in circuit design; add a free linear precomputation pass to merge consecutive MUL layers where algebraically possible.

  9. Total communication for N-party arithmetic MPC (Beaver, L layers, M muls/layer). Per MUL: 2 × N field-element broadcasts = 2 × N × 16 B = 32N B (at 128-bit). For N=3, L=10 layers, M=100 muls/layer: 10 × 100 × 3 × 32 B = 96 KB total. Rounds = L = 10. Design consequence: arithmetic MPC is communication-light per gate; the offline triple generation cost dominates, not the online bytes.

  10. OT extension batching threshold. From §4.1: base-OT setup cost = κ=128 DH operations on Ristretto (≈128 × ~50 µs each ≈ 6.4 ms, though batched implementations achieve lower). Break-even: batch of m extended OTs amortizes 6.4 ms setup. At 1M OTs/sec extended throughput: 6.4 ms setup → minimum profitable batch ≈ 6,400 OTs. §4.1 specifies batch ≥ 2^16 = 65,536 OTs. Design consequence: never call IKNP with m < 2^16; use R-OT/C-OT pre-generation batches sized to the circuit's AND-count.

  11. Statistical security masking size. From §4.1: s=40-bit statistical security. Comparison masking (DGK-style) adds 40-bit masks → comparison operands padded from l bits to l+40 bits. For l=64: operands become 104-bit → circuit grows ≈104/64 ≈ 1.6× in AND-count. Design consequence: the s=40 choice is the tradeoff point between mask bit-growth (circuit cost) and statistical soundness; increasing s to 80 roughly doubles AND-depth for comparison circuits.

  12. Yao garbling memory for AES-128. From §4.1 and §8.8: AES-128 Bristol circuit ≈ 36,000 AND-gates. Garbled table: 36,000 × 2 × 16 B = 1.15 MB. Wire labels in evaluator memory: ≈ 160 wires × 16 B = 2.6 KB at a time (streaming evaluation). Total garbled circuit in memory: ≈ 1.15 MB. Design consequence: for circuits with millions of AND-gates, stream garbled tables from garbler to evaluator; do not buffer the whole garbled circuit on either side.

Hard Questions (Self-Examination)

  1. If you increase the Shamir threshold t from N/3 to N/2 − 1, what changes in the BGW degree-reduction step, and why does the original BGW honest-majority requirement 2t < n emerge from this? (§8.3, §8.6, Phase 6, I15, MM9)

  2. The IKNP protocol reverses sender/receiver roles between the base OT and the extension OT. Walk through why this reversal is necessary: which party holds the choice bits in the base OT vs the extension, and what invariant on the resulting Q matrix guarantees receiver privacy? (§8.4, Phase 4, I5, I6, MM4)

  3. A developer argues that since opened values d=x−a and e=y−b are "just noise," there is no need to use a fresh triple (a,b,c) per multiplication. Precisely why is triple reuse a security violation? Which invariant and principle does it break, and what does the simulator argument expose? (§8.5, P3, Phase 5, I4, I13, MM7)

  4. You want to evaluate a 100-deep AND-circuit with 10,000 AND-gates over a WAN with RTT=200 ms. Compute the latency for GMW and for Yao, cite the relevant §4.1 constraint values, and state the exact breakeven condition. (§4.1, Phase 7, Phase 8, Phase 11, MM6, MM8)

  5. Free-XOR requires that the global Δ remain hidden from the evaluator. What happens if the evaluator learns Δ? Trace the consequence through the point-and-permute mechanism and the half-gate ciphertext construction. (§8.8, §7 (I7, I8), Phase 8, ADR-14, MM5, MM10)

  6. How does the offline/online split interact with the FieldConfig versioning and I12? (P4, P5, Phase 1, Phase 5, I12, I13, ADR-4, ADR-18)

  7. The BGW protocol achieves information-theoretic security; GMW achieves computational security. If you replace the OT in GMW with a perfectly-secure OT (hypothetically), does GMW become information-theoretically secure? What is the fundamental structural obstacle? (§8.3, §8.6, §8.7, Phase 6, Phase 7, ADR-11, ADR-13, MM9)

  8. Trace a single AND gate through the entire Yao pipeline: garbler assigns labels → builds half-gate ciphertexts → evaluator receives labels (OT for its input, directly for garbler's) → evaluator selects row → decrypts → obtains output label.   9. If mpc-rng::TranscriptRng is accidentally used in a production run (the config check fails silently), what is the exact attack?   10. The Bristol-format AES-128 circuit has approximately 36,000 AND-gates. Under Yao half-gates, how many bytes does the garbler send? Under GMW with κ=128, how many bytes total and how many rounds? Show the derivation from §4.1 values. (§4.1, Phase 8, Phase 7, ADR-8, ADR-14, MM6, Back-of-Envelope Capacity Model item 4 — Garbled-circuit bandwidth per AND gate)

  11. You discover that verify_triple_open (Phase 5) is called in a production run (not test mode) and one party opens a,b,c to all others. What exactly is leaked, which principle and invariant forbid this, and why does the security argument collapse even if c=a·b is confirmed? (P10, Phase 5, I4, I9, I13, ADR-15, MM3)

  12. Compare the trust model of Sharemind's 3-party Shamir deployment (Bogetoft et al. 2009) to this design's N-party semi-honest model. Specifically: what does the 3-party assumption enable that is unavailable in the general N-party semi-honest setting, and what does it foreclose? (Comparative Architecture Table, §8.3, Threat Model, Phase 2, ADR-11)

  13. The Channel trait's broadcast is implemented as echo relay. In the semi-honest setting, why is this sufficient? Write out the exact property that Byzantine broadcast would add, and identify the phase and invariant that currently assume echo broadcast is adequate. (§8 Domain Model, Phase 3, I10, ADR-19, Threat Model)

  14. Alternative Architectures (Roads Not Taken)

Alt-A: Garbled-Circuit-Only 2PC Stack (Yao + Half-Gates)

  Garbler (Alice)                Evaluator (Bob)
  +-----------------+            +-----------------+
  | assign labels   |            |                 |
  | build half-gate |--tables--->| gate-by-gate    |
  | tables (AES-NI) |            | evaluate        |
  | send input      |--labels--->| (signal bits)   |
  | labels directly |            |                 |
  |                 |<-OT round->| OT: input labels|
  |                 |            | decode output   |
  +-----------------+            +-----------------+
  No sharing layer. No triple store.
  No N>2 extension. Pure 2-party.

Wins when: the computation is strictly 2-party, AND-depth is large (WAN latency budget favors constant-round), bandwidth is not the bottleneck, and the implementation must be minimal (no sharing, no offline store, no triple generation).

Embodied by: EMP-toolkit (emp-sh2pc), which achieves very high garbling throughput by stripping the framework to OT + half-gate garbling with no N-party generality.

Why rejected here: this design targets N≥2 parties (BGW/GMW arithmetic), which requires a sharing layer, offline triple generation, and a transport abstraction. A garbled-circuit-only stack cannot extend to N>2 without BMR (itself deferred, §Phase 8), cannot support arithmetic circuits natively (no Beaver triples), and does not teach the BGW/Shamir side of the MPC design space (§1.1, ADR-13).

Alt-B: FHE-Based Outsourced Computation (Single-Server, Non-Interactive)

  Party 1          Party 2         Server (cloud)
  +--------+       +--------+      +-------------------+
  | encrypt|       | encrypt|      | eval f(ct1, ct2)  |
  | input  |--ct-->|        |--ct->| under BFV/CKKS HE |
  +--------+       +--------+      | (no interaction)  |
                                   | return ciphertext |
                                   +-------------------+
  Parties jointly decrypt result.
  No rounds during computation. No OT. No sharing.

Wins when: the computation is outsourced to a single cloud server, parties need zero interaction during evaluation, latency requirements prohibit any round-trip, and the circuit is arithmetic and compatible with BFV/CKKS noise bounds.

Embodied by: Microsoft SEAL and OpenFHE deployments for private inference and outsourced analytics.

Why rejected here: FHE-based computation requires a single trusted server or a threshold decryption scheme, which does not satisfy the N-party peer model where no single party learns inputs (§1.1, Threat Model). FHE is also restricted to arithmetic circuits of bounded multiplicative depth (noise growth), incompatible with the deep boolean circuits (AES garbling) that are a primary correctness target (Phase 8). The educational goal is to demystify the MPC stack by building it from primitives — substituting FHE would collapse most of Phase 4 (OT), Phase 5 (triples), Phase 7 (GMW), and Phase 8 (Yao).

Alt-C: TEE-Based Secure Computation (SGX Enclaves)

  Party 1          Party 2         SGX Enclave (server)
  +--------+       +--------+      +----------------------+
  | TLS to |       | TLS to |      | remote attestation   |
  | enclave|--in-->|        |--in->| execute f in enclave |
  +--------+       +--------+      | memory encrypted by  |
                                   | SGX; OS cannot read  |
                                   +----------------------+
  Trust assumption: Intel + hardware, not cryptographic.

Wins when: the function f is arbitrary (RAM, loops, arbitrary code), parties trust Intel's attestation chain, deployment timeline is short (no custom MPC protocol engineering), and side-channel attacks (Spectre/Meltdown on enclaves) are acceptable within the threat model.

Embodied by: Gramine and Occlum TEE runtimes, which run unmodified application code inside SGX enclaves with TLS attestation.

Why rejected here: the trust assumption is fundamentally different — TEE-based security relies on hardware manufacturer trust and physical tamper-resistance, not cryptographic simulation-based proofs (P3, Threat Model). Side-channel attacks on SGX (cache-timing, page-fault channels) undermine the security argument in ways that are not captured by the semi-honest simulation model. Most critically, this design's engineering goal is to understand MPC from cryptographic first principles (§1.1, §2.1); a TEE approach replaces that with an attestation-and-TLS engineering problem and teaches nothing about secret sharing, OT, or garbled circuits.

Alt-D: GMW Boolean Sharing with Interactive AND Gates and No Preprocessing (Pure Online)

  Party 1  Party 2  ... Party N
     |        |             |
     +--XOR gates: local----+
     |        |             |
     +--AND: 1-of-4 OT------+  (online, per gate, per layer)
     |        |             |
     [repeat for AND-depth rounds]
     |        |             |
     +--output reconstruct--+
  No offline phase. No triple store. OT run inline.

Wins when: the circuit changes between evaluations so precomputed triples cannot be reused, the party count is N=2 and the online OT is cheap (LAN), and simplicity of the implementation (no offline infrastructure, no store) is the priority.

Embodied by: ABY (Demmler–Schneider–Zohner 2015, NDSS) in its GMW-boolean mode, which supports both offline-preprocessed and online-only AND evaluation.

Why rejected here: pure online GMW without preprocessing places the OT cost on the critical (input-aware) path, increasing online latency by the full OT cost per AND layer — precisely the cost the offline/online split (P5, I13) is designed to move off. The Beaver-triple model (Phase 5) decouples OT cost from online latency and is architecturally cleaner for teaching the offline/online design pattern (§2.1, §8.5, ADR-12).
