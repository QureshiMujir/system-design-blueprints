212 — HTAP Engine (Hybrid OLTP/OLAP)

Project Number: 212

Project Name: HTAP Engine (Hybrid OLTP/OLAP)

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

The HTAP Engine is a from-scratch Hybrid Transactional/Analytical Processing database that serves OLTP point reads/writes and OLAP scans/aggregations against one logical table, over fresh (sub-second-lag) data, without an ETL hop to a separate warehouse. Its core mechanism is a dual-store architecture per Sikka et al. 2012 and Färber et al. 2012 (the SAP HANA papers): a write-optimized row delta store absorbs transactions, a delta-to-main merge worker periodically folds committed deltas into a read-optimized compressed columnar main store, and an MVCC version manager provides snapshot isolation that spans both representations so an analytical query sees one consistent view regardless of which store(s) it touches. A query router classifies incoming access as point (routed to the row store) or scan/aggregate (routed to the column store, or both when a query must see un-merged deltas) — Özcan, Tian & Tözün 2017 (the HTAP survey) frame this router decision as the central HTAP query-processing problem. A resource governor isolates the two workloads so a heavy analytical scan cannot starve the OLTP latency SLO — the "isolation problem" the HTAP survey identifies as HTAP's hardest unsolved operational concern.

Phase-0 deliverable — the crate list:

  1. htap-row-store — the write-optimized delta store (row layout, in-place update chains)
  2. htap-wal — write-ahead log and durability
  3. htap-mvcc — timestamp allocation, version chains, snapshot/visibility
  4. htap-column-store — the compressed columnar main store
  5. htap-merge — the delta-to-main merge worker and scheduling policy
  6. htap-vector-exec — the vectorized scan/aggregate executor
  7. htap-router — the query router / access-path chooser
  8. htap-governor — the resource governor (CPU/memory caps for analytics)
  9. htap-catalog — table/column metadata
  10. htap-bench — the CH-benCHmark-style mixed-workload harness
  11. htap-telemetry — metrics/tracing/logging
  12. htap-cli — an operator CLI (create table, run txn, run scan, inspect freshness)

Boundaries. Provides: single-node dual row/column storage, MVCC snapshot isolation spanning both stores, delta-merge, a query router, a resource governor, a vectorized analytical executor, WAL durability. Delegates: multi-node distribution/replication (deferred), a full SQL frontend and cost-based optimizer beyond the router's rule-based access-path decision (deferred), disk-tiered storage beyond an in-memory-first design (deferred). Does NOT provide: cross-region consensus, GPU execution, adaptive/ML-driven query optimization.

Non-goals — sibling contrasts. This is not SQL-Database (Project 21): 21 is OLTP-only — a classic relational engine with a row store and B-tree indexes, no columnar path, no analytical-freshness concern at all. This is not Data-Lake-Table-Format (Project 214): 214 is analytics-only over object-storage files with no transactional path, and its freshness is bounded by batch snapshot commits (minutes-to-hours), not sub-second. THIS project's defining, load-bearing property — its reason to exist — is serving both OLTP and OLAP workloads over one continuously fresh logical table with one MVCC snapshot semantics. Also non-goals for Phase 0: a distributed multi-node deployment (that is the TiDB/TiFlash pattern discussed and rejected as the primary design in §36), a full ANSI SQL frontend (a constrained query surface suffices to exercise the router and both executors), adaptive/ML-driven optimization, GPU execution.

Isolation level: MVCC snapshot isolation (the Berenson et al. isolation-level taxonomy), enforced identically whether a read touches the row store, the column store, or both (I1). Serializable anomalies (write skew) are explicitly out of scope for Phase 0 — snapshot isolation is the locked target.

Deployment model: a single-node, in-memory-first engine. The row delta store and hot MVCC versions live in memory; the columnar main store is memory-resident with WAL-backed persistence; disk is used for WAL and checkpoints, not as the primary access path in Phase 0 (ADR-16).

Users/operators: database engineers studying HTAP internals, OLTP application authors who need fresh embedded analytics without standing up a warehouse, and SREs who must operate the mixed workload without one side starving the other.

What later phases unlock: Phase 5 (§17) unlocks a live delta-to-main pipeline; Phase 6 (§18) unlocks cross-store consistent snapshots — the freshness-plus-consistency core of the whole project; Phase 7 (§19) unlocks workload-aware routing; Phase 8 (§20) unlocks safe co-location of OLTP and OLAP under one resource budget; Phase 11 (§23) unlocks a validated mixed CH-benCHmark gate proving both workloads hold simultaneously.

Rust + rationale: ownership rules make the row/column dual-representation and MVCC version-chain lifetimes checkable at compile time; no GC pause can appear in the OLTP write path on the critical p99 budget (§4); safe concurrency primitives make the resource governor's cross-thread accounting auditable. Rejected languages: C++ — memory-safety burden across two storage representations sharing MVCC versions is exactly where use-after-free bugs live, and the cost of that risk is unacceptable in a correctness-first HTAP engine; Go — GC pauses are incompatible with the p99 OLTP latency target in §4 and interfere unpredictably with the resource governor's timing guarantees; Java — JIT warm-up and GC pauses compromise both the OLTP tail and vectorized-scan throughput, and the JVM's opaque memory layout works against the columnar compression goals in §8.4.

Prerequisites: transaction processing (Gray & Reuter), columnar storage and compression, MVCC and snapshot isolation, basic query optimization (access-path selection).

Timeline: Phase 0 ~3 weeks; Phases 1-11 (§13-§23) ~34-40 weeks in aggregate; hardening and the mixed-benchmark gate (Phase 11, §23) an additional 4-6 weeks.

Deferrals: PhaseDeferred("§36 TiDB/TiFlash separate-columnar-Raft-replica model") for multi-node distribution; PhaseDeferred("§31 Scalability Analysis, distributed HTAP") for cross-node analytical execution; PhaseDeferred("§27 Compatibility & Versioning, query interface") for a full SQL frontend; PhaseDeferred("§34 Back-of-Envelope Capacity Model, disk-tiered storage") for spilling the column store to disk as primary storage.

2. Why Build This

  • one store, two workloads: no ETL lag, no dual-write inconsistency, no reconciliation job
  • the delta/main pattern (SAP HANA, Färber et al. 2012 / Sikka et al. 2012) as the canonical production HTAP design
  • MVCC snapshot isolation as the mechanism that makes freshness safe rather than merely fast
  • the fork/snapshot alternative (HyPer, Kemper & Neumann 2011) as a contrasting first-principles design worth understanding even though rejected here
  • vectorized execution (MonetDB/X100, Boncz et al. 2005) as the OLAP-side performance unlock
  • resource isolation as the unsolved-in-practice HTAP problem the survey (Özcan et al. 2017) names explicitly
  • delta-merge scheduling as a scheduling-theory problem hiding inside a storage engine
  • direct contrast with SQL-Database-21 (OLTP-only) and Data-Lake-214 (stale analytics) clarifies exactly what HTAP buys over each sibling project
  • learning where "one logical table, two physical layouts" breaks, and what invariants must hold for it not to lie to a query

What Mastery Looks Like

  • Explaining precisely why no single physical layout is simultaneously row-optimal and column-optimal, and defending the dual-store answer against the alternatives in §36 (tied to Phase 3, §15, and Phase 4, §16)
  • Implementing a delta-to-main merge that is provably row-set-preserving under concurrent writes (tied to Phase 5, §17)
  • Proving snapshot isolation holds across the row/column boundary with a Jepsen/Elle-style isolation checker (tied to Phase 6, §18)
  • Building a query router whose access-path choice is measurably correct against the decision table in §8.5 (tied to Phase 7, §19)
  • Building a resource governor that holds an OLTP SLO under a concurrent full-table scan (tied to Phase 8, §20)
  • Diagnosing and bounding MVCC version-chain bloat from a long-running analytical query (tied to Phase 10, §22)
  • Running and passing a mixed CH-benCHmark gate where OLTP throughput and OLAP latency both hold simultaneously (tied to Phase 11, §23)
  • Articulating the freshness-vs-consistency distinction crisply enough to explain why "recent" and "correct" are different guarantees (tied to §8.3 and §32)

Query Router. Classifies every incoming access as point, range, scan, or aggregate (§8.5) and dispatches it to the OLTP point executor, the vectorized scan executor, or both when a scan must additionally read un-merged deltas. It is the mechanism by which the dual store avoids ever forcing one representation to serve a workload it is not suited for (P4).

OLTP Point Executor. Performs indexed row-store lookups and single-row/small-range writes with the p50/p95/p99 latency budget of §4. Its cache and branch profile is deliberately opposite that of the scan executor (P12, ADR-12), which is why it is a separate code path rather than a shared one.

Vectorized Scan Executor. Processes columnar batches (2,048-row vectors) using SIMD-friendly predicate evaluation and aggregation, in the MonetDB/X100 hyper-pipelining style (Boncz et al. 2005). It reads the columnar main store and, for freshness, the frozen portion of the row delta store not yet merged (§8.3).

Row Delta Store. The write-optimized home for new and recently-updated tuples (P1). Rows here are mutable via version-chain updates and are the target of every OLTP write until a merge relocates them.

Columnar Main Store. The read-optimized, compressed home for merged data (§8.4). Segments are immutable once sealed (I4) so scans require no locks — the same discipline underlying C-Store (Stonebraker et al. 2005) and MonetDB/X100.

Delta-to-Main Merge Worker. Periodically (size- or time-triggered, P6) freezes a consistent slice of the row delta store, encodes it into new columnar segments, and atomically publishes a segment manifest (§8.2). It is the single mechanism that keeps the two stores one logical table.

MVCC Version Manager. Allocates monotonic timestamps, maintains version chains, and evaluates the visibility equation (§8.3) identically whether a version's home is the row store or a column-store segment (I1, I3).

Freshness/Visibility Tracker. Measures the lag between a transaction's commit and the moment it is visible to analytics (§8.6, §4), and is the source of the freshness-lag alert (§26, I10).

Resource Governor. Enforces CPU/memory caps on the analytical path and reserves a disjoint core set for OLTP (ADR-13), so a heavy scan cannot silently erode the OLTP SLO (I6, P3).

WAL/Durability Layer. Every committed transaction is durable here before acknowledgment (I5), independent of which store eventually holds the tuple's merged representation.

6. Design Principles

  • P1: One copy of the data, two representations — writes land in a row delta store and analytics read a columnar main store, and the delta-merge is the single mechanism that keeps them one logical table (Sikka et al. 2012).
  • P2: MVCC snapshot isolation must span both stores so an analytical query sees a consistent snapshot including the freshest committed deltas — freshness without consistency is worse than lag (Özcan et al. 2017).
  • P3: Analytics must never starve transactions — a resource governor caps analytical CPU/memory so the OLTP latency SLO holds even under a heavy scan (the HTAP isolation problem, Özcan et al.).
  • P4: The query router sends point access to the row store and scans to the column store, because forcing one representation to serve both is exactly the compromise HTAP exists to avoid.
  • P5: The columnar main store is immutable between merges — append-only segments need no locks for scanning (I4), the same discipline C-Store and MonetDB/X100 rely on.
  • P6: Delta-merge is size- or time-triggered, never ad hoc — an explicit scheduling policy (Phase 9, §21) is required so freshness lag is bounded and predictable.
  • P7: MVCC version chains must be bounded by aggressive, snapshot-aware GC — unbounded growth from a long analytical query is a first-class failure mode (FM-4), not an edge case.
  • P8: WAL-before-visibility holds regardless of which store a transaction eventually lands in — durability precedes both row-store visibility and eventual column-store representation.
  • P9: Compression is chosen per column by data characteristics (dictionary for low cardinality, RLE for runs, bit-packing for bounded ranges) — one scheme for all columns wastes the compression budget in §4.
  • P10: Vectorized execution processes data in cache-resident batches (MonetDB/X100) — tuple-at-a-time interpretation is disqualifying against the OLAP throughput targets in §4.
  • P11: The freshness target is a first-class SLO, not a best-effort side effect of the merge — it is measured (§26), alerted on, and tested (§28) like OLTP latency.
  • P12: Point access and scan access are architecturally separate executors sharing only the MVCC visibility rule, because point-optimal and scan-optimal execution have opposite cache and instruction-count profiles.
  • P13: Row/column consistency is externally verifiable — the same key read at the same snapshot must return an identical value whether served from the row store, the column store, or a merge in flight (I3), and this is differentially tested, not assumed.
  • P14: The delta-to-main merge must be row-set-preserving under concurrency — no row lost, duplicated, or double-counted across the row-to-column move (I2), verified by a dedicated property test (§28).

8. Domain Model

8.1 The Dual-Store Model

Dimension Row Delta Store Columnar Main Store
Layout row-major, tuple-per-slot column-major, per-column arrays
Workload OLTP writes, point reads OLAP scans, aggregations
Mutability mutable, in-place update chains immutable between merges (I4)
Compression none/light (row overhead dominates) heavy: dictionary, RLE, bit-packing
Indexing primary-key hash/B-tree zone maps / min-max per segment
Typical size small, bounded by merge trigger (§4) large, holds the bulk of historical + recent data

Worked example, a row's life: INSERT lands in the row delta store with (xmin=commit_ts, xmax=∞); it is immediately readable by point queries and by any analytical query once committed, via the freshness tracker (§8.6); the delta-merge worker selects it into a merge batch when the delta store crosses 256 MB / 5,000,000 rows (§4, ADR-06); the merge writes it into a new columnar segment with dictionary-coded columns (§8.4); the merge commits a new segment manifest at merge_ts; MVCC marks the version's home as the column-store segment; the row delta store's copy becomes GC-eligible once no live snapshot needs it (I7).

8.2 The Delta-Merge Algorithm

Named steps:

  1. Trigger evaluation — size or time threshold crossed (P6, ADR-06)
  2. Merge-set selection — freeze a consistent slice of the delta store at merge_ts
  3. Column projection — transform frozen rows into per-column arrays
  4. Encoding — apply dictionary/RLE/bit-pack per column (§8.4)
  5. Segment write — write new immutable segment(s), compute zone maps
  6. Manifest commit — atomically publish the segment manifest at merge_ts
  7. Visibility flip — MVCC marks merge_ts as the new main-store horizon
  8. Delta reclamation — mark merged delta rows GC-eligible once no live snapshot predates merge_ts (I7)

Worked merge: the delta store holds 5,000,000 rows; a merge worker at 200 MB/s (§4) processes the frozen 256 MB delta in ~1.3 s; during that window OLTP continues writing into a fresh delta segment (double-buffered delta, ADR-08); freshness lag equals the time from the oldest un-merged commit to its segment's manifest commit — bounded by trigger interval plus merge duration (§34 shows the arithmetic).

8.3 MVCC Across Both Stores

Version representation: MvccVersion { home: RowDelta | Column(segment_id), xmin, xmax, chain_next }.

Snapshot/visibility rule:

visible(v, snapshot_ts) :=
    (v.xmin <= snapshot_ts) AND (v.xmax > snapshot_ts OR v.xmax = NULL)

applied identically whether v.home is RowDelta or Column(segment_id) — I1, I3.

Worked example: an analytical query takes snapshot_ts = T. It scans the column store (all segments with merge_ts <= T) and additionally scans the row delta store for rows with xmin <= T not yet merged (i.e. their eventual segment's merge_ts > T or they remain un-merged) — this union is the "hybrid scan," the mechanism by which freshness and snapshot consistency coexist (Neumann, Mühlbauer & Kemper 2015's MVCC discipline, adapted here to a dual store rather than HyPer's single fork).

8.6 The Freshness Model

freshness_lag = merge_trigger_wait + merge_duration

where merge_trigger_wait is bounded by the earlier of the time-since-last-merge threshold and the size-threshold crossing time. §34 chains this into a numeric worked example.

8.7 The Resource-Isolation Model

The governor enforces analytics_cpu_used <= cap_cpu AND analytics_mem_used <= cap_mem (ADR-13); OLTP threads run on a reserved core set disjoint from the analytics pool so no OS-scheduler-level interference occurs; a cap violation triggers throttling (reduced analytical batch concurrency) before the governor escalates to killing a query (I6).

8.8 The OLTP-vs-OLAP Tension and Its Resolution

Row-optimal writes want narrow, localized mutations (one page touched per write); column-optimal scans want wide, sequential, compressed reads (one column touched per scan, many rows). No single physical layout is optimal for both (Abadi et al. 2008). The dual store resolves this by paying a bounded memory premium (§34) to keep two representations reconciled by the delta-merge, rather than compromising either representation to serve the other.

8.10 Malformed / Hard Examples

  • An analytical query racing a delta-merge: the query takes a snapshot at T; the merge commits at merge_ts = T - epsilon; the query must include the newly merged segment and must not double-count the same rows still present in the row delta store — resolved by I2 + I9.
  • A snapshot that must span un-merged deltas — resolved by the hybrid scan (§8.3).
  • A heavy scan starving transactions — resolved by resource-governor caps (§8.7, Phase 8, §20).
  • A merge that stalls and the delta store grows unbounded — detected by the delta-store-size alert (§26), remedied by a forced out-of-cycle merge (I10 recovery).
  • A row/column value divergence — caught by the row/column consistency differential test (I3, §28); root-caused to either an encoding bug or a missed merge-set row.
  • MVCC bloat from a long analytical query — bounded by GC watermark tracking the oldest active snapshot (Phase 10, §22); if a query holds a snapshot open indefinitely, an operator alert fires (§26) rather than allowing silent unbounded growth.

8.11 Failure-Path Example

The merge worker crashes mid-write of a new segment (after step 5, before step 6 manifest commit, §8.2). On restart, the merge scanner finds the partially-written segment has no corresponding manifest entry, discards it as orphaned, and re-triggers the merge from the last committed manifest. No data is lost, because the frozen delta rows remain in the row delta store until GC-eligible per I7, which requires manifest commit first.

8.12 Catalog and Schema Evolution

Schema changes (add/drop column) are the one operation that must touch the row delta store and the column main store atomically, per I11. The catalog manager commits a new schema version only once both stores can read and write consistently under it: the row store's tuple layout gains/drops the field immediately (rows are already mutable), while the column store's effect is deferred — new segments written by the next delta-merge encode the new schema, and existing sealed segments are read under their original schema with the missing/extra column synthesized (default value on add, ignored on drop) until the next full re-encode. This two-speed schema application is why DDL is blocked for the duration of an in-flight merge (§17.8, T12): a schema change racing a merge could otherwise produce a segment whose manifest and whose actual encoded columns disagree on schema version, which I11's cross-check would then have to detect after the fact rather than prevent.

Worked example: an operator adds a nullable region column to a table mid-operation. The catalog commits schema version v2 at timestamp schema_ts. All new row-store tuples after schema_ts carry the region field; a concurrent analytical query with snapshot_ts < schema_ts must not see the column at all (I1's scope rule applied to schema, not just data); a query with snapshot_ts >= schema_ts sees region as NULL for any pre-existing merged segment (schema v1) and as its actual value for anything written under v2. The next delta-merge re-encodes only the rows it merges under v2; older sealed v1 segments are not eagerly rewritten, which is why segment manifests (§11) carry their own schema-version tag rather than inheriting the catalog's current version implicitly.

Failure interaction: if a governor policy hot-reload (T11, I13) and a schema commit race at the same instant, the catalog manager's schema-version commit takes precedence and the policy reload retries at the next epoch — schema convergence (I11) is never allowed to wait on an unrelated resource-policy decision.

  10. Build a long-analytical-query stress test: hold a snapshot open for minutes while sustaining OLTP write load, and measure memory growth and GC backlog.

22.3 Deliverable

An MVCC GC subsystem that reclaims dead versions within the §4 cadence target under normal operation, and degrades gracefully (alerting, throttling, or explicit forced expiry) rather than unbounded memory growth when a long analytical query holds a snapshot open.

  • GC sweep interval ≤ 1 s and backlog ≤ 100,000 dead versions under steady-state load (§4)
  • Zero premature reclamations (I7) across 100,000 GC-vs-snapshot-registration race trials
  • Memory growth under a 10-minute held-open snapshot with concurrent OLTP load stays within the §4 memory-footprint budget (2.5x raw dataset), bounded by the long-query alert firing and (if configured) admission throttling
  • Long-query alert fires within 1 s of crossing the configured threshold, 100% of trials

22.6 Pitfalls

  • Watermark computed from a stale snapshot registry, allowing GC to run ahead of an actually-active long query (the exact I7 violation mode).
  • Column-segment reclamation granularity too coarse, retaining an entire segment for one long-lived row's sake (acceptable trade-off, but must be measured, not accidental).
  • Forced expiry silently corrupting a query's in-flight result rather than surfacing a clear SnapshotExpired error (§11 error taxonomy).
  • GC backlog throttling interacting badly with the Phase 8 governor's own throttling, compounding into an unintended double-throttle.

22.7 Performance Concerns

  • GC sweep cost scaling with total live version count.
  • Watermark-recomputation frequency vs. accuracy trade-off.
  • Segment-level reclamation bookkeeping overhead for very large tables.

22.8 Edge Cases

  • Two long-running queries with different snapshot timestamps, requiring the watermark to track the older of the two.
  • A long query that itself never terminates (crashed client, orphaned snapshot) — must eventually be reaped by a timeout distinct from the alert threshold.
  • GC running with zero active snapshots (should reclaim everything eligible immediately).

22.9 Failure Analysis

Unbounded memory growth: correlate version-chain-depth and GC-backlog telemetry against the active-snapshot registry to identify the oldest held snapshot; if the watermark is correct but reclamation still lags, the fault is sweep throughput, not correctness — distinguishing this from an I7 violation is the key triage step, matching the debugging methodology in §7.

27. Compatibility & Versioning

Columnar-format versioning: the Arrow-compatible segment format (ADR-04) is versioned per segment manifest; a version bump requires a documented upgrade path that can read all prior segment versions without a blocking rewrite.

Row/delta and WAL format: WalRecord framing (§11) is versioned; rolling upgrades require that a newer engine version can replay WAL written by the immediately prior minor version (append-only field evolution, mirroring ADR-30's protobuf-style discipline referenced in the ADR table's testing/CI rows).

MVCC/snapshot semantics stability: the visibility equation (§8.3) and the invariants in §7 are considered part of the stable contract — any change to I1-I12 requires a major-version bump and an explicit migration note.

Query/SQL interface: the constrained query surface (ADR-20) evolves additively; new predicate/aggregate support is additive, never redefining existing semantics.

Merge-format compatibility: a segment manifest written by version N must remain readable by version N+1's merge worker and scan executor; manifest schema changes are additive fields only, gated by I11's schema-convergence discipline.

API stability: the CLI and any embedding API follow SemVer; breaking changes require a major bump.

Migration: schema changes (add/drop column) apply atomically across both stores per I11, with a documented migration step recorded in CHANGELOG.md.

Deprecation: deprecated CLI commands or config keys are retained for two minor releases with a warning, then removed, matching the salvaged project's original deprecation window.

SemVer: MAJOR for any I1-I12 or WAL/segment-format breaking change; MINOR for additive query-surface or config features; PATCH for bug fixes with no format or semantics change.

31. Scalability Analysis

What stays constant: WAL append cost per transaction (O(1) in row width); zone-map lookup cost per segment (O(1) amortized via pruning).

What grows, with Big-O: OLTP throughput is bounded by the row-store write path and MVCC conflict-detection cost, roughly O(1) per transaction absent contention, degrading under hot-row skew (Phase 1, §13); OLAP scan cost is linear in scanned columns × rows, cut by compression (§4's 4x target) and column pruning (Phase 4, §16); delta-merge cost grows with delta size, O(n) in rows merged, with encoding cost dominant for high-cardinality columns (Phase 5, §17); MVCC version count grows with concurrent long-running queries, O(writes × oldest-open-snapshot-age) absent GC (Phase 10, §22); the fundamental memory cost of keeping two representations is the HTAP memory premium quantified in §34.

Named bottlenecks: the timestamp allocator and transaction table under very high OLTP concurrency (single-node ceiling); the merge worker's single-threaded-per-table serialization (§21.2 step 5) under many concurrently write-heavy tables; the governor's cross-core cache interference even with disjoint core pinning (§20.7); the hybrid scan's row-delta union cost scaling with un-merged delta size right after a write burst (§18.7).

The freshness-vs-throughput tension: tightening the merge trigger (lower freshness lag) increases merge frequency and thus OLTP interference (§17.7, §21); loosening it improves OLTP headroom but risks breaching the freshness SLO (I10) — this tradeoff is tuned, not eliminated, and is the direct subject of §21's adaptive scheduling.

The OLTP-vs-OLAP-isolation tension at scale: as analytical query volume grows, the governor's cap must shrink per-query share or reject excess queries — resource isolation trades analytical concurrency for OLTP protection, and beyond a certain analytical query rate the single-node governor cannot admit all analytical demand without either breaching the OLTP SLO or queuing analytical queries indefinitely.

Single-node limits and what a distributed HTAP changes: this project's Phase 0-11 scope is single-node (§1); TiDB/TiFlash's approach (Huang et al. 2020) — a separate columnar replica fed via Raft log shipping — removes the single-node CPU/memory ceiling entirely by physically isolating OLTP and OLAP onto different machines, at the cost of replication lag replacing in-process freshness lag as the dominant staleness source (§33, §36).

Practical data-size and mixed-workload ceilings: the §4 memory-footprint bound (2.5x raw dataset) caps single-node dataset size at available RAM ÷ 2.5; beyond that, disk-tiered storage (deferred, §1) or a distributed architecture (§36) are the two levers, the latter changing the freshness mechanism entirely rather than merely adding capacity.

Wide-table memory scaling: tables with many columns amplify the per-row version-header overhead disproportionately relative to their compressed columnar footprint, because MvccVersion metadata (§11) is charged once per row regardless of column count while compression benefits (§8.4) scale with column count — a 200-column table sees a smaller relative memory premium from the dual-store design than a 5-column table, since the columnar side's compression savings dominate a larger absolute byte count. This is the concrete justification for ADR-07's per-tuple in-line version chain being revisited (per §35's hard question on ADR-07/ADR-16 crossover) only once average row width crosses a threshold where Hekaton-style out-of-line versioning's indirection cost is repaid by avoiding hot-row bloat.

32. Mental Models & First Principles

  • MM1: OLTP wants rows and OLAP wants columns — HTAP's entire trick is to keep both representations of one logical table and reconcile them with a delta-merge, paying memory to avoid ETL lag (Özcan et al. 2017).
  • MM2: Freshness and consistency are not the same thing — the hard part of HTAP is not showing recent data but showing a consistent recent snapshot that spans un-merged deltas and the main store (§8.3, §18).
  • MM3: The enemy is interference — a heavy scan and a latency-critical transaction share a machine, and without a resource governor the analytics silently eat the OLTP SLO (§20).
  • MM4: Immutability is what makes analytics cheap — the columnar main store needs no locks for scanning precisely because it never changes between merges (I4); mutability is pushed entirely into the small row delta store where it's affordable.
  • MM5: A merge is a transaction, not a background chore — it must be snapshot-consistent, crash-recoverable, and row-set-preserving (I2), or the entire dual-store premise collapses.
  • MM6: Compression is a per-column decision, not a per-table one — treating all columns identically wastes the exact budget (§4's 4x target) that makes columnar storage worth the complexity.
  • MM7: A resource cap is only as good as its accounting granularity — coarse accounting lets a hostile or merely unlucky query evade the governor entirely (T1).
  • MM8: GC correctness is a race against the oldest reader, not the average one — a single long-held snapshot, not aggregate load, is what determines whether GC can proceed (I7, Phase 10).
  • MM9: The query router's job is not optimization, it's classification — HTAP does not need a full cost-based optimizer to get most of the benefit of routing point access away from scans and vice versa (ADR-10).
  • MM10: Every dual-store design (HANA's delta/main, HyPer's fork, TiDB's replica) is answering the same question — where does the second representation live, and how is it kept in sync — with a different point in the freshness/isolation/complexity space (§33).

SAP HANA's delta/main split is the direct architectural ancestor of this project (§1, P1) — its central lesson is that a merge worker, not a fork or a replica, can keep two representations of one table consistent within a single process, at the cost of building and correctly scheduling that merge (§17, §21). HyPer's VM-snapshot fork (Kemper & Neumann 2011) is elegant precisely because it needs no merge logic at all — the OS's copy-on-write gives it a consistent snapshot for free — but that elegance is bought with freshness granularity tied to fork frequency, which is why it is contrasted rather than adopted here (§36). TiDB/TiFlash's Raft-replica-to-columnar model (Huang et al. 2020) trades in-process complexity for physical isolation, moving the freshness bottleneck from a merge worker to network replication lag, and is the natural next step once this project's single-node scope (§1, §31) is outgrown. DuckDB is included specifically as the OLAP-only contrast named in §1's non-goals — it has no transactional path at all, making it a useful differential-testing reference (§28) for the analytical side without being a competing HTAP design.

34. Back-of-Envelope Capacity Model

  1. Raw dataset: assume 100,000,000 rows × 200 bytes/row (row-store representation) = 20 GB raw row bytes.
  2. Row-store memory: 20 GB (bounded by the delta-store trigger, §4, so only a fraction is live at once — the row store's steady-state footprint is the delta threshold, 256 MB, not the full 20 GB).
  3. Column-store memory: 20 GB ÷ compression ratio (§4 target ≥ 4x) = 5 GB compressed columnar bytes for the merged bulk of the dataset.
  4. Version overhead: assume 16 versions/row p99 (§4, M9) × 100,000,000 rows × 32 bytes/version header = 51.2 GB worst case, but bounded in practice by GC cadence (§4: ≤1 s sweep) keeping live version count far below the p99 ceiling — steady-state estimate at 2 versions/row average × 32 bytes = 6.4 GB.
  5. HTAP memory premium: total ≈ 0.256 GB (delta) + 5 GB (column) + 6.4 GB (versions) ≈ 11.66 GB, vs. 20 GB for keeping only a single row-store representation of the same data uncompressed — the dual-store design is memory-cheaper here specifically because compression on the bulk (column) side outweighs the version-chain overhead, i.e. the "premium" is paid in complexity, not necessarily in raw bytes, provided compression holds (§4 M5).
  6. Delta-merge cost and frequency: delta size 256 MB ÷ merge throughput 200 MB/s (§4, M6) = 1.28 s merge duration; at the ADR-06 hybrid trigger, a merge fires roughly every time 256 MB accumulates — under a 50,000 txns/sec OLTP load at 200 bytes/txn-row, that's 10 MB/s of new data, so a merge fires roughly every 25.6 s.
  7. Freshness lag as a function of merge frequency: freshness_lag = merge_trigger_wait + merge_duration (§8.6) ≈ 25.6 s (worst case, right after a merge, before the next trigger) is far above the §4 sub-second target — this reveals the real tuning lever: the 256 MB/5M-row threshold in §4 is a ceiling, and Phase 9's adaptive scheduling (§21.2 step 2) must shrink the effective trigger window (e.g. a parallel time-based trigger at ~200-400 ms) to hit the ≤500 ms p99 freshness target, trading merge frequency (and thus OLTP interference, step 9 below) for freshness.
  8. OLAP scan time: 100,000,000 rows × 1 column scanned × 2 bytes/row (compressed, post-dictionary) ÷ 4 GB/s/core scan bandwidth (§4, M3) ≈ 0.05 s per core for a single-column scan; a 5-column aggregate scan ≈ 0.25 s per core, well within the ≤2 s target (M4) even before zone-map pruning is applied.
  9. OLTP-SLO headroom under a concurrent scan: governor caps analytics at ≤50% cores/≤40% RAM (§4); on an 8-core node that reserves 4 cores for OLTP — at 50,000 txns/sec ÷ 4 cores ≈ 12,500 txns/sec/core, which must independently satisfy the p99 ≤5 ms budget (M2); the arithmetic shows the governor's cap is the primary lever, not per-transaction optimization, once the reserved-core count is fixed.
  10. MVCC version growth from a long analytical query: at 50,000 txns/sec write rate × 200 bytes/row-version × a 60-second held-open snapshot = 50,000 × 60 × 200 bytes ≈ 600 MB of otherwise-reclaimable versions retained for that query's duration — this is the concrete number behind the Phase 10 long-query alert threshold and the §4 memory-footprint budget's safety margin.
  11. CH-benCHmark mixed-throughput target: chaining steps 6-9, the combined target (§30, M13) is OLTP ≥ 50,000 txns/sec sustained while the governor holds analytics to its cap and freshness lag (tuned per step 7) stays ≤500 ms p99 — all three simultaneously, which is why §23's benchmark measures them as one scorecard rather than three independent numbers.

36. Alternative Architectures (Roads Not Taken)

A. Two separate systems with ETL.

   OLTP DB  --(batch ETL, minutes-hours)-->  Analytical Warehouse
     ^                                              |
     |                                              v
  transactions                                 reports/BI

Winning regime: a workload where analytical freshness of hours is genuinely acceptable and operational simplicity of two independently-scaled systems outweighs any freshness benefit. Real embodying system: the classic OLTP-database-plus-data-warehouse pattern this project's sibling Data-Lake-Table-Format (214) formalizes on the analytical side. Rejected here because it reintroduces exactly the ETL lag and dual-write/reconciliation complexity that HTAP exists to eliminate (§1 non-goals).

B. HyPer's fork/VM-snapshot approach.

   OLTP Process (row store)
        |
        | fork() copy-on-write
        v
   Analytical Snapshot Process
   (consistent as-of fork time)

Winning regime: a read-mostly analytical workload over a table with a low OLTP update rate, where fork frequency can be high enough (sub-second forks) without the copy-on-write page-fault overhead degrading OLTP throughput. Real embodying system: HyPer (Kemper & Neumann 2011). Rejected as the primary design here because freshness granularity is coupled to fork frequency, and frequent forking under this project's target OLTP write rate (§4, M1) would impose copy-on-write overhead directly on the OLTP path — the opposite of P3's isolation principle.

C. Single-format store with both row and column indexes.

   +-----------------------------------------+
   |         Single Physical Store            |
   |  row-major base + secondary col index    |
   +-----------------------------------------+

Winning regime: a workload with modest analytical query volume where maintaining a full second representation is not justified, and "good enough" columnar-like access via secondary indexing suffices. Real embodying system: traditional RDBMS column-store secondary indexes (the pattern SQL-Database-21's non-HTAP design represents). Rejected here because neither workload gets its optimal physical layout (§8.8) — the entire premise of this project is that row-optimal and column-optimal layouts are genuinely different, not that one layout with clever indexing can serve both at the throughput targets in §4.

D. TiDB/TiFlash separate-columnar-Raft-replica model.

   TiKV (row engine) --Raft log-->  TiFlash (columnar replica)
        ^                                    |
    OLTP txns                          OLAP queries

Winning regime: a workload requiring true multi-node horizontal scale and physical fault isolation between OLTP and OLAP, where network replication lag (seconds) is an acceptable freshness bound. Real embodying system: TiDB + TiFlash (Huang et al. 2020). Rejected as the primary design here because it is explicitly out of scope for the single-node Phase 0-11 arc (§1, §31) — it is the natural next architecture once this project's single-node ceiling (§31) is reached, and is named as the un-defer trigger for distributed scope in §37.
