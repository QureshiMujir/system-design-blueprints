⬜ Phase 0 — Skeleton, Row Store Foundation, WAL, and CI §12

Objectives

Establish a reproducible Rust workspace, the minimal row-oriented htap-row-store capable of durable single-row insert/get, a working htap-wal with fsync-backed durability, and a CI pipeline that gates every later phase. No MVCC, no columnar path, and no router exist yet — this phase proves the skeleton and the row/WAL foundation the rest of the engine builds on (P1, P8).

Deliverable

A runnable single-node daemon that accepts a put/get via the CLI, persists via WAL with group-commit fsync, and recovers its DeltaStore state deterministically after a simulated crash.

Acceptance
  • WAL write throughput ≥ 200 MB/s sustained group-commit (feeds the §4 OLTP budget)
  • Crash-recovery replay of a 1 GB WAL completes in ≤ 90 s and reconstructs identical DeltaStore state (byte-for-byte tuple comparison) on 100/100 runs
  • Reproducible build hashes stable across two clean builds (ADR-28)
  • Zero WAL checksum false negatives across 10,000 injected torn-write fixtures (I12)
Fixtures
  • fixtures/wal/torn_write.wal — truncated mid-record
  • fixtures/wal/reordered_records.wal — out-of-LSN-order records (I12)
  • fixtures/rowstore/crash_before_ack.fixture — crash between WAL append and ack (I5)
  • fixtures/runtime/queue_overflow.json — bounded-queue rejection behavior (ADR-29)
Pitfalls
  • Group-commit batching introduces ack latency if the batch window is too wide — bounds must respect the p99 OLTP target in §4.
  • fsync storms under bursty writes if segment rotation isn't pipelined with active writes.
  • Recovery scanner accepting a partially-written trailing record as valid — must truncate to last-good LSN (I12), not attempt to parse it.
  • Telemetry allocation on the hot write path skewing the very latency numbers being measured.

⬜ Phase 1 — OLTP Transactions and Point Access on the Row Store §13

Objectives

Implement the transaction lifecycle (§8.9) and the OLTP point executor (P12, ADR-12) over the row store from Phase 0, without MVCC multi-versioning yet — single-version, latch-based concurrency, to isolate transaction-boundary correctness from visibility correctness (deferred to Phase 2, §14).

Deliverable

A transactional row store supporting concurrent point reads/writes with commit/abort semantics and durable, replayable transaction logs, exercised through the CLI's txn begin/put/commit commands.

Acceptance
  • OLTP throughput ≥ 50,000 txns/sec single-node under a point-write-heavy synthetic load (§4 target)
  • Point-write p99 latency ≤ 5 ms under the same load (§4)
  • Zero lost updates across 100,000 concurrent conflicting-write trials (I5, ADR-18)
  • Rollback correctness: 100% of aborted transactions leave zero visible trace (validated against WAL before-images)
Fixtures
  • fixtures/txn/concurrent_conflict.fixture — two txns writing the same row
  • fixtures/txn/abandoned_txn.fixture — a txn that never commits or aborts
  • fixtures/txn/rollback_partial_write.fixture
Pitfalls
  • Latch inversion between the primary-key index and the row page leading to deadlock.
  • Optimistic conflict detection starving a writer under sustained contention on a hot row.
  • Rollback forgetting to release held latches, stalling subsequent transactions.
  • Treating an abandoned (never committed/aborted) transaction as committed by omission.

⬜ Phase 2 — MVCC Snapshot Isolation on the Row Store §14

Objectives

Replace Phase 1's single-version latching with full MVCC: monotonic timestamp allocation (I8), version chains (§11), and the visibility rule (§8.3) — scoped to the row store only, since the column store does not exist until Phase 3. This phase proves snapshot isolation correctness in the simplest possible setting before the cross-store complexity of Phase 6.

Deliverable

A row store with full MVCC snapshot isolation: concurrent transactions each see a consistent point-in-time view, validated by a property-based test suite.

Acceptance
  • Snapshot-isolation property test passes 100,000 randomized concurrent-transaction schedules with zero I1 violations
  • MVCC version-chain depth stays ≤ 16 p99 under sustained mixed read/write load (§4)
  • GC reclaims versions within 1 s of the oldest active snapshot advancing (feeds §4 GC cadence target)
  • Zero premature reclamation (I7) across 10,000 long-reader-vs-GC race trials
Fixtures
  • fixtures/mvcc/write_skew.fixture
  • fixtures/mvcc/phantom_read.fixture
  • fixtures/mvcc/long_reader_vs_gc.fixture (I7)
  • fixtures/mvcc/timestamp_wraparound.fixture (I8)
Pitfalls
  • Timestamp wraparound or non-monotonic allocation under clock adjustment (I8).
  • GC racing a snapshot that is pinned but not yet registered — a registration-ordering bug.
  • Version-chain traversal cost growing unbounded if GC falls behind under write-heavy load.
  • Confusing "committed" with "visible" — a transaction can commit before its effects are visible to a snapshot taken at an earlier timestamp; conflating the two breaks I1.

⬜ Phase 3 — The Columnar Main Store and Compression §15

Objectives

Implement ColumnStore, Column, and the three encodings (Dictionary, Rle, BitPacked) per §8.4 and §11, as an immutable, append-only structure (I4) — with no merge worker yet (Phase 5) and no scan executor yet (Phase 4). This phase isolates columnar-format correctness and compression-ratio measurement from execution concerns.

Deliverable

A standalone, immutable columnar store that can be bulk-loaded with test data and queried for raw decoded values, with measured compression ratios reported per encoding.

Acceptance
  • Combined compression ratio ≥ 4x vs. raw row bytes on the TPC-H-style synthetic dataset (§4)
  • Zero panics or OOB reads across 24 hours of columnar-decoder fuzzing (ADR-25)
  • Zone-map pruning correctly excludes 100% of segments outside a predicate's value range in property tests
  • Segment immutability enforced: 100% of post-seal write attempts rejected (I4)
Fixtures
  • fixtures/columnar/low_cardinality.fixture (dictionary)
  • fixtures/columnar/sorted_runs.fixture (RLE)
  • fixtures/columnar/bounded_ints.fixture (bit-packing)
  • fixtures/columnar/corrupted_segment.fixture (fuzz regression)
Pitfalls
  • Choosing dictionary encoding for a high-cardinality column, inflating rather than shrinking size.
  • RLE degrading to worse-than-raw size on unsorted, high-churn data.
  • Zone maps computed before final sort order is applied, making them useless for pruning.
  • Fuzz-found: a malformed dictionary index pointing outside the dictionary array.

⬜ Phase 4 — Vectorized Analytical Scan on the Column Store §16

Objectives

Implement the vectorized scan executor (P10, ADR-11) over the columnar main store from Phase 3: batch-at-a-time predicate evaluation, aggregation, and SIMD-friendly decoding, in the MonetDB/X100 hyper-pipelining style (Boncz et al. 2005).

Deliverable

A vectorized analytical executor capable of running SELECT agg(col) FROM table WHERE predicate over the Phase 3 column store at the throughput targets in §4.

Acceptance
  • OLAP scan throughput ≥ 4 GB/s per core; ≥ 500M rows/sec aggregate at 8 cores (§4)
  • Analytical query latency ≤ 2 s for a single-table scan+aggregate over 100M rows (§4)
  • Zero result divergence across 10,000 differential trials vs. the naive reference executor
  • Zone-map skip rate ≥ 90% on a range-predicate benchmark with a sorted merge key
Fixtures
  • fixtures/scan/aggregate_large.fixture
  • fixtures/scan/null_heavy_vector.fixture
  • fixtures/scan/skewed_group_by.fixture
  • fixtures/scan/pruned_columns.fixture
Pitfalls
  • Materializing full intermediate vectors between operators, defeating cache residency.
  • SIMD misalignment from decoding directly into non-aligned buffers.
  • Zone-map skip logic evaluated after decode instead of before, wasting the pruning benefit.
  • NUMA-oblivious batch scheduling causing cross-socket memory traffic under partitioned scan.

⬜ Phase 5 — The Delta-to-Main Merge §17

Objectives

Implement the DeltaMerge worker (§8.2, §11) that folds committed row-delta-store rows into new columnar segments, making the two stores in Phases 2 and 3 into one logical table for the first time (P1, P14, Sikka et al. 2012).

Deliverable

A working delta-to-main merge pipeline that periodically converts row-delta-store content into columnar segments without losing or duplicating rows, measurable end-to-end via the CLI's merge status command.

Acceptance
  • Delta-merge throughput ≥ 200 MB/s per worker (§4)
  • OLTP p99 latency degrades ≤ 10% during an active merge, measured under concurrent load (§4)
  • Zero row-set mismatches (I2) across 10,000 merge cycles under concurrent writers
  • Merge-crash recovery (§8.11 scenario) recovers to a consistent state in 100/100 injected-crash trials with no orphaned or duplicated segments
Fixtures
  • fixtures/merge/concurrent_writes_during_merge.fixture
  • fixtures/merge/crash_before_manifest_commit.fixture (§8.11)
  • fixtures/merge/row_count_reconciliation.fixture (I2)
  • fixtures/merge/racing_analytical_query.fixture (I9 groundwork for Phase 6)
Pitfalls
  • Freezing the merge set without a consistent snapshot boundary, admitting a partially-committed transaction into the merge.
  • Forgetting to double-buffer, causing OLTP writers to block on the frozen delta during merge (violates the §4 impact bound).
  • Committing the manifest before the segment write is fully durable, risking an orphaned manifest reference on crash.
  • Delta reclamation racing a snapshot registration, violating I7 before Phase 6 even introduces the harder cross-store visibility problem.

⬜ Phase 6 — MVCC Snapshot Isolation Spanning Both Stores §18

Objectives

Extend Phase 2's row-store-only MVCC to span the row delta store and the columnar main store via the hybrid scan (§8.3), making freshness and consistency coexist for the first time — the load-bearing core of the entire project (P2, I1, I3, I9, Neumann/Mühlbauer/Kemper 2015; Özcan et al. 2017).

Deliverable

A cross-store MVCC engine where an analytical query at any snapshot timestamp returns results identical to a row-store-only reference, whether or not a merge is concurrently in flight, verified by the Elle-style isolation checker.

Acceptance
  • Zero isolation-checker violations across 1,000,000 randomized concurrent OLTP+OLAP schedules (I1, I3)
  • Zero merge-visibility leaks (I9) across 100,000 racing-merge-vs-query trials
  • Freshness lag p99 ≤ 500 ms under the §4 merge-trigger configuration
  • Row/column consistency divergence rate = 0 across the full differential suite (I3)
Fixtures
  • fixtures/cross-mvcc/racing_merge_vs_snapshot.fixture (I9)
  • fixtures/cross-mvcc/hybrid_scan_reconciliation.fixture (I1, I3)
  • fixtures/cross-mvcc/long_query_spanning_merge_boundary.fixture
  • fixtures/cross-mvcc/elle_isolation_schedule.fixture
Pitfalls
  • Double-counting a row present in both the frozen delta being merged and the not-yet-visible new segment.
  • Treating merge_ts as an approximation rather than an exact MVCC timestamp, breaking I9's strict inequality.
  • Running the hybrid scan's row-delta half without the same visibility equation as its column half, silently reintroducing scope-dependent semantics (violates I1).
  • Underestimating the cost of the hybrid scan's row-delta union on freshness-sensitive queries issued right after a write burst.

⬜ Phase 7 — The Query Router §19

Objectives

Implement QueryRouter (§8.5, §11, P4, ADR-10) to classify incoming queries into AccessPath::{PointRow, ScanColumn, Hybrid} and dispatch to the correct executor from Phases 1, 4, or the Phase 6 hybrid scan — the first phase where OLTP and OLAP requests share a single entry point.

Deliverable

A query router that correctly and measurably dispatches point access to the row store and scan/aggregate access to the column store, with hybrid fallback for freshness-sensitive queries, exercised via the CLI explain command.

Acceptance
  • Router routing-correctness ≥ 99.9% against the cost oracle on a 10,000-query synthetic mix (§8.5 decision table)
  • Zero incorrect results from mis-routing (fallback to Hybrid guarantees correctness; measured is only performance impact) across 100,000 mixed-workload queries
  • Point-route dispatch overhead ≤ 50 μs (must not erode the §4 OLTP point-latency budget)
  • Mixed OLTP+OLAP workload through the router shows no I1/I3 violations (regression check against Phase 6's isolation checker)
Fixtures
  • fixtures/router/point_vs_scan_mix.fixture
  • fixtures/router/freshness_forced_hybrid.fixture
  • fixtures/router/misclassification_fallback.fixture
  • fixtures/router/mixed_oltp_olap_concurrent.fixture
Pitfalls
  • Selectivity estimates stale relative to actual data distribution, causing systematic mis-routing.
  • Router dispatch overhead itself becoming a measurable tax on OLTP point latency (must be sub-microsecond-class logic, not a full cost-based plan).
  • Failing to force Hybrid for a query racing an in-flight merge, silently reintroducing an I9-class bug at the router layer.
  • Treating Hybrid as a rare fallback when, under bursty write load, it may become the common case — under-provisioning for it.

⬜ Phase 8 — The Resource Governor (Isolating Analytics from OLTP) §20

Objectives

Implement ResourceGovernor (§8.7, §11, P3, I6, ADR-13) so a heavy analytical scan through the Phase 7 router cannot erode the OLTP SLO from §4 — the operational half of the HTAP isolation problem (Özcan et al. 2017).

Deliverable

A resource governor that measurably holds the OLTP p99 SLO from §4 while a concurrent heavy analytical scan runs at its capped resource budget, demonstrated via the CLI's governor status command showing live cap utilization.

Acceptance
  • OLTP p99 latency degrades ≤ 15% under full governor-capped analytical load (§4 interference bound)
  • Governor cap violations detected and throttled within 100 ms of threshold crossing
  • Zero governor-bypass incidents across the T1 threat-model adversarial test suite (§24)
  • Governor accounting overhead ≤ 2% of total analytical query CPU time
Fixtures
  • fixtures/governor/full_scan_at_peak_oltp.fixture
  • fixtures/governor/cap_bypass_attempt.fixture (T1)
  • fixtures/governor/throttle_then_kill.fixture
  • fixtures/governor/hot_reload_policy.fixture
Pitfalls
  • Cap enforcement that measures CPU/memory too coarsely (per-second sampling) to catch a burst before it breaches the OLTP SLO.
  • Reserved-core pinning fighting the OS scheduler if cgroup configuration is inconsistent with in-process core assignment (ADR-13's rejected-alternative regime).
  • Killing an analytical query mid-scan without releasing its pinned MVCC snapshot, risking an I7-class leak.
  • Throttling algorithm oscillating (reduce concurrency, SLO recovers, restore concurrency, SLO breaks again) instead of converging.

⬜ Phase 9 — Merge Scheduling and Delta-Store Management §21

Objectives

Generalize Phase 5's single merge-trigger logic into a full scheduling policy (P6, ADR-06) that balances freshness against OLTP interference and delta-store growth, and integrate it with the Phase 8 governor so merge work itself is resource-accounted.

Deliverable

A merge-scheduling subsystem that keeps freshness lag within the §4 target across steady, bursty, and idle write-rate profiles, with delta-store size bounded and merge work resource-accounted under the governor.

Acceptance
  • Freshness lag p99 ≤ 500 ms across all three tested write-rate profiles (§4)
  • Delta-store size never exceeds 2x the configured threshold (§4) even under sustained bursty writes, via emergency-merge triggering
  • Zero concurrent-merge violations (at most one merge per table in flight) across 10,000 trigger-storm trials
  • Merge scheduling overhead ≤ 1% of total engine CPU at steady state
Fixtures
  • fixtures/scheduling/bursty_write_profile.fixture
  • fixtures/scheduling/idle_then_burst.fixture
  • fixtures/scheduling/trigger_storm.fixture
  • fixtures/scheduling/multi_table_fairness.fixture
Pitfalls
  • Adaptive tuning oscillating between aggressive and lax thresholds instead of converging (mirrors the Phase 8 throttling-oscillation pitfall).
  • Emergency out-of-cycle merges competing with the governor's analytics cap in a way that starves the merge itself (a scheduling deadlock between P6 and P3).
  • Multi-table fairness starving a low-write-volume table indefinitely behind a high-write-volume table's merges.
  • Stalled-merge detection false-positiving on a merge that is simply large and legitimately slow.

⬜ Phase 10 — MVCC Version GC and Long-Analytical-Query Handling §22

Objectives

Generalize Phase 2's first-cut GC into the full GcCursor watermark discipline (§11, ADR-17, I7, P7) spanning both stores, and explicitly handle the long-running-analytical-query scenario that Phase 6 and Phase 8 both flagged as a bloat risk.

Deliverable

An MVCC GC subsystem that reclaims dead versions within the §4 cadence target under normal operation, and degrades gracefully (alerting, throttling, or explicit forced expiry) rather than unbounded memory growth when a long analytical query holds a snapshot open.

Acceptance
  • GC sweep interval ≤ 1 s and backlog ≤ 100,000 dead versions under steady-state load (§4)
  • Zero premature reclamations (I7) across 100,000 GC-vs-snapshot-registration race trials
  • Memory growth under a 10-minute held-open snapshot with concurrent OLTP load stays within the §4 memory-footprint budget (2.5x raw dataset), bounded by the long-query alert firing and (if configured) admission throttling
  • Long-query alert fires within 1 s of crossing the configured threshold, 100% of trials
Fixtures
  • fixtures/gc/premature_reclaim_race.fixture (I7)
  • fixtures/gc/long_held_snapshot.fixture
  • fixtures/gc/backlog_throttle.fixture
  • fixtures/gc/forced_expiry_opt_in.fixture
Pitfalls
  • Watermark computed from a stale snapshot registry, allowing GC to run ahead of an actually-active long query (the exact I7 violation mode).
  • Column-segment reclamation granularity too coarse, retaining an entire segment for one long-lived row's sake (acceptable trade-off, but must be measured, not accidental).
  • Forced expiry silently corrupting a query's in-flight result rather than surfacing a clear SnapshotExpired error (§11 error taxonomy).
  • GC backlog throttling interacting badly with the Phase 8 governor's own throttling, compounding into an unintended double-throttle.

⬜ Phase 11 — Mixed HTAP Benchmark, Chaos, and Performance Hardening §23

Objectives

Integrate every prior phase into a CH-benCHmark-style mixed workload (concurrent TPC-C-style OLTP transactions and TPC-H-style OLAP analytics) as the project's primary correctness-and-performance gate, then harden the engine against chaos scenarios spanning all ten invariants (I1-I12) and the full ADR set (§9).

Deliverable

A passing CH-benCHmark run demonstrating OLTP throughput, OLAP latency, and freshness lag all simultaneously within the §4 targets, plus a chaos/soak test report showing graceful degradation (not data loss or unbounded resource growth) under every injected fault.

Acceptance
  • CH-benCHmark mixed run: OLTP ≥ 50,000 txns/sec AND OLAP single-table scan+aggregate ≤ 2 s AND freshness lag p99 ≤ 500 ms, all concurrently sustained for the full benchmark duration (§4, §34's chained target)
  • Zero data loss and zero I1-I12 violations across all chaos scenarios
  • 24-hour soak test shows zero unbounded growth in version-chain depth, delta-store size, or segment count (all plateau or oscillate within §4 bounds)
  • Perf-regression gate: zero unexplained regressions beyond the configured threshold across 30 consecutive CI runs
Fixtures
  • fixtures/bench/ch_benchmark_mixed_run.fixture
  • fixtures/chaos/scan_at_peak_oltp_full_system.fixture
  • fixtures/chaos/merge_worker_killed_mid_cycle.fixture
  • fixtures/chaos/oom_from_mvcc_bloat.fixture
  • fixtures/soak/24h_mixed_workload.fixture
Pitfalls
  • Running OLTP and OLAP benchmarks separately and summing results instead of measuring them concurrently, which hides exactly the interference the resource governor exists to prevent.
  • Chaos scenarios that are too gentle to actually exercise the failure paths named in §25.
  • Soak tests that don't run long enough to distinguish a slow leak from normal steady-state oscillation.
  • Perf-regression thresholds set so loosely that real regressions slip through, or so tightly that noise causes false CI failures.
