32. Mental Models & First Principles

  • MM1: OLTP wants rows and OLAP wants columns — HTAP's entire trick is to keep both representations of one logical table and reconcile them with a delta-merge, paying memory to avoid ETL lag (Özcan et al. 2017).
  • MM2: Freshness and consistency are not the same thing — the hard part of HTAP is not showing recent data but showing a consistent recent snapshot that spans un-merged deltas and the main store (§8.3, §18).
  • MM3: The enemy is interference — a heavy scan and a latency-critical transaction share a machine, and without a resource governor the analytics silently eat the OLTP SLO (§20).
  • MM4: Immutability is what makes analytics cheap — the columnar main store needs no locks for scanning precisely because it never changes between merges (I4); mutability is pushed entirely into the small row delta store where it's affordable.
  • MM5: A merge is a transaction, not a background chore — it must be snapshot-consistent, crash-recoverable, and row-set-preserving (I2), or the entire dual-store premise collapses.
  • MM6: Compression is a per-column decision, not a per-table one — treating all columns identically wastes the exact budget (§4's 4x target) that makes columnar storage worth the complexity.
  • MM7: A resource cap is only as good as its accounting granularity — coarse accounting lets a hostile or merely unlucky query evade the governor entirely (T1).
  • MM8: GC correctness is a race against the oldest reader, not the average one — a single long-held snapshot, not aggregate load, is what determines whether GC can proceed (I7, Phase 10).
  • MM9: The query router's job is not optimization, it's classification — HTAP does not need a full cost-based optimizer to get most of the benefit of routing point access away from scans and vice versa (ADR-10).
  • MM10: Every dual-store design (HANA's delta/main, HyPer's fork, TiDB's replica) is answering the same question — where does the second representation live, and how is it kept in sync — with a different point in the freshness/isolation/complexity space (§33).

Reference Implementations

  • SAP HANA (as described in the cited papers) — delta/main store lesson; pitfall is merge-scheduling starvation under write-heavy load — applied in Phase 5 (§17), Phase 9 (§21)
  • HyPer — fork/VM-snapshot lesson; pitfall is coarse-grained freshness tied to fork frequency — applied in §33, §36
  • TiDB + TiFlash (tiflash/ columnar engine, row engine in tikv/) — replica-to-columnar lesson; pitfall is replication lag becoming the freshness bound — applied in §33, §36
  • SingleStore (MemSQL) architecture — unified rowstore/columnstore-in-one-engine lesson; pitfall is that columnstore updates are logically delete+insert, complicating merge accounting — applied in §9 (ADR-02), Phase 5 (§17)
  • DuckDB (src/storage/) — vectorized columnar execution lesson; pitfall is that its single-writer design has no OLTP concurrency story, useful precisely as the OLAP-only contrast — applied in Phase 4 (§16), §28
  • Apache Arrow (columnar in-memory format) — normative columnar layout lesson — applied in §9 (ADR-04), Phase 3 (§15)
  • ClickHouse — MergeTree background-merge scheduling lesson, structurally analogous to delta-merge — applied in Phase 9 (§21)

Glossary (§38) · 50 terms · site-wide glossary

HTAP
Hybrid Transactional/Analytical Processing — one system serving both OLTP and OLAP over fresh data
OLTP
Online Transaction Processing — low-latency point reads/writes
OLAP
Online Analytical Processing — high-throughput scans/aggregations
ETL
Extract-Transform-Load — the batch pipeline HTAP exists to avoid
Row store
tuple-per-slot, row-major storage optimized for point access (§8.1)
Column store
column-major storage optimized for scans (§8.1)
Dual-format
maintaining two physical representations of one logical table
Delta store
the write-optimized row store absorbing new transactions (§8.1)
Main store
the read-optimized columnar store holding merged data (§8.1)
Delta-merge
the process folding delta-store rows into new columnar segments (§8.2)
MVCC
Multi-Version Concurrency Control
Snapshot isolation
a transaction sees a consistent point-in-time view (§8.3)
Version chain
the linked sequence of a row's MVCC versions (§11)
Visibility
whether a version is visible to a given snapshot timestamp (§8.3)
Commit timestamp
the monotonic timestamp assigned at transaction commit (I8)
Freshness
the lag between commit and analytics-visibility (§8.6, I10)
Staleness
the inverse of freshness — how out-of-date analytical data is
Vectorized execution
processing data in cache-resident batches rather than tuple-at-a-time (P10)
SIMD scan
Single-Instruction-Multiple-Data predicate/aggregate evaluation over a batch
Dictionary encoding
mapping low-cardinality values to integer ids (§8.4)
RLE
Run-Length Encoding — storing (value, run-length) pairs (§8.4)
Bit-packing
storing bounded-range integers in fixed-width bit slots (§8.4)
Compression
reducing storage footprint of columnar data (§4, M5)
Column pruning
decoding only the columns a query references (§16.2)
Query router
the component classifying and dispatching access paths (§8.5, ADR-10)
Access path
the chosen execution route: PointRow, ScanColumn, or Hybrid (§11)
Point access
a single-row indexed lookup or write
Scan
a sequential read over many rows of one or more columns
Aggregation
computing SUM/COUNT/MIN/MAX/AVG over a set of rows
Resource governor
the component capping analytical CPU/memory (§8.7, ADR-13)
Resource isolation
the guarantee that one workload cannot starve the other (P3, I6)
Interference
the OLTP-latency impact of concurrent analytical load
WAL
Write-Ahead Log — the durability mechanism preceding visibility (I5)
Checkpoint
a durable, periodic snapshot of recoverable state
CH-benCHmark
the mixed TPC-C + TPC-H benchmark used as the primary HTAP gate (§23, §28)
TPC-C
the standard OLTP transaction-processing benchmark
TPC-H
the standard OLAP analytical-query benchmark
Fork/snapshot
HyPer's VM copy-on-write approach to analytical consistency (§33, §36)
In-memory database
a database whose primary access path is RAM-resident data (ADR-16)
Zone map
per-segment min/max metadata used for scan pruning (§8.1, §15)
Segment manifest
the metadata descriptor published atomically at merge commit (§8.2, §11)
GC watermark
the oldest active snapshot boundary bounding safe reclamation (I7, ADR-17)
Group commit
batching multiple transactions' WAL fsync into one syscall (ADR-15)
NUMA
Non-Uniform Memory Access — memory locality relative to a CPU socket (ADR-19)
Isolation checker
an Elle/Jepsen-style tool validating cross-store snapshot consistency (§28)
Differential testing
comparing results against an independent reference implementation (§28)
Throttling
reducing resource consumption before escalating to termination (§20.2)
Merge trigger
the size- or time-based condition initiating a delta-merge (P6, ADR-06)
Hybrid scan
the union read across row-delta and column-store data at one snapshot (§8.3)
Row/column consistency
identical results from row-store and column-store reads at one snapshot (I3)
