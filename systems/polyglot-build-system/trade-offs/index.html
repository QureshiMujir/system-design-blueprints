Decisions (§9) · 28 ADRs

ADR-01

Implementation language

Chosen

Rust (stable toolchain, MSRV 1.78)

Rejected

Go, C++, OCaml, Java

When the rejected choice is right

Go wins for small scripting-heavy build tools where goroutine concurrency and fast compilation outweigh type-system guarantees; C++ wins when the build system must be embedded into an existing C++ monorepo with no Rust toolchain budget

Why: Memory safety without GC; zero-cost abstractions; strong type system for invariant encoding; cargo ecosystem; reference Buck2 precedent

ADR-02

Workspace build tool

Chosen

Cargo workspaces + cargo build

Rejected

Bazel-for-Rust, buck2

When the rejected choice is right

Bazel-for-Rust wins when the project must itself be built hermetically with cross-language deps (e.g., protobuf codegen tightly coupled to the build system's own CI); Buck2 wins for teams already standardised on Meta's tooling

Why: Self-hosting not required at bootstrap; cargo workspaces map naturally to the crate split; simplifies CI

ADR-03

Async runtime

Chosen

Tokio (multi-thread scheduler)

Rejected

async-std, smol, glommio

When the rejected choice is right

glommio wins on Linux when the workload is I/O-dominated and io_uring thread-per-core avoids context-switch overhead at very high blob throughput (>10 GB/s NVMe); smol wins for embedded targets where Tokio's binary size is prohibitive

Why: Dominant ecosystem; tokio::spawn for action parallelism; tokio::fs for async I/O; rich tooling (tokio-console)

ADR-04

Sync/async split

Chosen

Async I/O in pbs-exec / pbs-cache / pbs-remote; sync in pbs-core / pbs-loader / pbs-graph

Rejected

All-sync with rayon

When the rejected choice is right

All-sync with rayon wins for a pure-local build tool without remote execution, where async runtime overhead exceeds the benefit; also appropriate for CLI-only tools run once per invocation rather than as long-lived daemons

Why: I/O-bound phases (cache fetch, remote) benefit from async; CPU-bound phases (graph analysis, hashing) use rayon thread pool alongside tokio

ADR-05

CPU parallelism

Chosen

rayon for graph traversal + digest computation

Rejected

std::thread manual pools

When the rejected choice is right

Manual thread pools win when fine-grained priority control is needed (e.g., critical-path actions must preempt background digest hashing) and rayon's work-stealing heuristic causes priority inversion at extreme parallelism

Why: Work-stealing; composable with tokio via spawn_blocking

ADR-06

Content-hash algorithm

Chosen

SHA-256 (ring crate)

Rejected

BLAKE3, SHA-512, MD5

When the rejected choice is right

BLAKE3 wins in a standalone (non-REAPI-compatible) build system where maximum hashing throughput is the priority and compatibility with external caches is not required; SHA-512 wins in FIPS environments requiring the stronger standard

Why: REAPI mandates SHA-256; interoperability with Bazel remote caches; ring is audited, FIPS-compatible

ADR-07

CAS on-disk format

Chosen

Flat file tree sharded by 2-char hex prefix; atomic rename-into-place

Rejected

SQLite blob store, RocksDB, object storage

When the rejected choice is right

RocksDB wins when the CAS must support range scans or metadata queries (e.g., GC needs per-blob timestamps at high throughput without a separate index file); SQLite wins for single-file portability on Windows or network-mounted shares

Why: Simplest crash-safe write; no DB lock contention; files dedup via hardlinks on reflink-supporting FS; easy to inspect

ADR-08

Action cache DB

Chosen

LMDB (lmdb-rs / heed)

Rejected

RocksDB, SQLite, sled

When the rejected choice is right

RocksDB wins when write throughput exceeds LMDB's single-writer bottleneck (>100k AC puts/s in a distributed-worker scenario); SQLite WAL mode wins for embedded deployments where LMDB's fixed map size is operationally inconvenient

Why: Memory-mapped; single-writer many-reader; low latency; no background compaction; predictable write performance

ADR-09

Serialization (wire + storage)

Chosen

MessagePack (rmp-serde) for internal storage; Protocol Buffers (prost) for remote REAPI protocol

Rejected

JSON, CBOR, bincode

When the rejected choice is right

JSON wins when human readability of stored cache entries is operationally critical (e.g., debugging corrupted entries without a decode tool); bincode wins for in-process serialization where schema never crosses a version boundary

Why: msgpack: compact + schema-free evolution; protobuf: REAPI wire compatibility; JSON only for build event log (human-readable)

ADR-10

Config language

Chosen

Custom Starlark-like evaluator (starlark-rust or custom subset)

Rejected

Full Python, Lua, TOML, Jsonnet

When the rejected choice is right

Full Python wins when BUILD files must import existing utility libraries (e.g., a legacy Pants v1 migration); TOML wins for simpler projects where only declarative rule invocations are needed and no macro language is required

Why: Starlark is deterministic + hermetic + sandboxed by design; no I/O; no side effects; Bazel-familiar syntax; no import of arbitrary stdlib

ADR-11

Dependency policy

Chosen

No unsafe outside pbs-sandbox + pbs-cache (mmap); deny(unsafe_code) workspace-wide with per-crate override

Rejected

Allow unsafe freely

When the rejected choice is right

Unrestricted unsafe wins when performance profiling shows that safe abstractions introduce measurable overhead in the CAS hot path (e.g., bounds-check elimination requires unsafe slice indexing) and the team has formal memory-safety review processes

Why: Audit surface minimized; unsafe only where OS-level syscalls required

ADR-12

Error handling

Chosen

thiserror for library errors; anyhow at CLI/binary boundary

Rejected

failure, eyre, custom

When the rejected choice is right

eyre wins when rich human-readable error reports with colored backtraces and suggestions are the primary UX goal and library-level typed errors are not needed across crate boundaries

Why: thiserror: typed errors for cross-crate propagation; anyhow: ergonomic user-facing display

ADR-13

Logging

Chosen

tracing crate with tracing-subscriber

Rejected

log + env_logger, slog

When the rejected choice is right

log + env_logger wins for minimal-dependency CLI tools where the overhead of structured tracing is not justified and the operator only needs line-level log output

Why: Structured spans; integrates with tokio-console; exportable to OpenTelemetry

ADR-14

Metrics

Chosen

metrics crate + metrics-exporter-prometheus

Rejected

StatsD, custom counters

When the rejected choice is right

StatsD wins in environments where a Prometheus scrape endpoint is not feasible (e.g., short-lived CLI invocations that cannot serve HTTP) and UDP push to an aggregation agent is the standard telemetry path

Why: Prometheus pull model; standard in CI/infra tooling; metrics::counter! / metrics::histogram! macros

ADR-15

Distributed tracing

Chosen

OpenTelemetry (opentelemetry + tonic gRPC exporter)

Rejected

Jaeger-only, Zipkin

When the rejected choice is right

Jaeger-only wins in air-gapped environments already standardised on Jaeger where the added OTEL abstraction layer introduces unnecessary dependency weight

Why: OTEL is vendor-neutral; spans per action correlate with remote execution traces

ADR-16

Testing framework

Chosen

cargo test + insta (snapshot) + proptest (property)

Rejected

criterion alone, custom test harness

When the rejected choice is right

A custom test harness wins when the test suite must run without Cargo (e.g., bootstrapping the build system to test itself with pbs-exec) and cargo test's process-per-test model is too slow at scale

Why: proptest for ActionKey stability + digest roundtrip; insta for BUILD file parse snapshots; cargo test as the runner

ADR-17

Fuzzing

Chosen

cargo-fuzz (libFuzzer) targeting pbs-loader parser + pbs-cache CAS read path

Rejected

AFL++, honggfuzz

When the rejected choice is right

AFL++ wins when the fuzzing environment lacks LLVM instrumentation (e.g., cross-compiled targets on unusual architectures) or when persistent-mode fuzzing throughput exceeds libFuzzer's fork-exec overhead

Why: cargo-fuzz is idiomatic Rust; libFuzzer coverage-guided; targets: malformed BUILD, corrupted CAS blobs

ADR-18

Benchmarking

Chosen

criterion (wall-time) + custom macro-bench harness for large-graph builds

Rejected

hyperfine, manual timing

When the rejected choice is right

hyperfine wins for black-box CLI benchmarking where the binary under test cannot be instrumented and process-startup noise must be measured rather than controlled

Why: criterion: statistical; macro-bench: measures end-to-end action-graph scheduling at 10k / 100k node scale

ADR-19

CI/CD

Chosen

GitHub Actions; matrix: (linux-x86_64, linux-aarch64, macos-x86_64)

Rejected

Jenkins, CircleCI

When the rejected choice is right

Jenkins wins for on-premise enterprise environments where GitHub Actions runners cannot access internal artifact registries or require hardware-specific sandbox capabilities not available on hosted runners

Why: Actions marketplace; free for OSS; matrix covers cross-compilation test targets

ADR-20

Container / sandbox (Linux)

Chosen

Linux namespaces (unshare: mount + PID + network + IPC) via nix crate syscall wrappers

Rejected

Docker-per-action, Bubblewrap, gVisor

When the rejected choice is right

Docker-per-action wins when actions require complete OCI image environments with pre-installed system libraries that cannot be declared as ArtifactRef inputs (e.g., actions targeting a specific Ubuntu release with dynamic linker dependencies); gVisor wins in untrusted multi-tenant execution environments where kernel exploit risk mandates a second isolation layer

Why: Namespace-based: fast (no container startup); minimal overhead; full input-root isolation (I3); no Docker daemon dependency

ADR-21

Container / sandbox (macOS)

Chosen

sandbox-exec (Seatbelt) profiles restricting file reads to declared input paths

Rejected

Docker Desktop, no sandbox

When the rejected choice is right

Docker Desktop wins when macOS actions require Linux-only syscalls (e.g., building Linux binaries on a Mac developer's machine) and full Linux namespace isolation is required for correctness

Why: sandbox-exec is native macOS; acceptable isolation; caveat: less strict than Linux namespaces; documented limitation

ADR-22

Remote execution protocol

Chosen

REAPI (bazelbuild/remote-apis) over gRPC (tonic)

Rejected

Custom REST, NATS, Redis queues

When the rejected choice is right

A custom REST protocol wins for single-team deployments where REAPI's proto complexity is not justified and a simple HTTP/JSON action-dispatch API suffices; NATS wins when the execution cluster requires pub/sub fan-out to worker pools rather than request/response dispatch

Why: REAPI: industry standard; compatible with Buildbarn, Buildgrid, EngFlow caches; tonic: idiomatic async gRPC in Rust

ADR-23

IPC (daemon ↔ CLI)

Chosen

Unix domain socket + length-prefixed msgpack frames

Rejected

gRPC loopback, shared memory, REST

When the rejected choice is right

gRPC loopback wins when the daemon must be callable from clients in multiple languages (e.g., IDE plugins in Go or Python) and a machine-readable service definition is required; shared memory wins for ultra-low-latency streaming of large build event payloads where socket copy overhead is measurable

Why: Low latency; no network stack; framed protocol simple to implement; msgpack encoding reuses ADR-09

ADR-24

File watching (incremental)

Chosen

notify crate (inotify on Linux, FSEvents on macOS)

Rejected

polling, custom kernel module

When the rejected choice is right

Polling wins on network-mounted filesystems (NFS, SMB) where inotify events are not reliably delivered and correctness requires periodic digest re-check rather than event-driven invalidation

Why: Cross-platform abstraction; debounce coalescence; low latency for interactive incremental builds (Phase 11, 13)

ADR-25

Packaging / distribution

Chosen

Single statically-linked binary (pbs) per platform via cargo build --release + cross for cross-compilation; checksummed tarballs

Rejected

Homebrew formula, deb/rpm packages at launch

When the rejected choice is right

Homebrew/deb/rpm packaging wins at scale-out adoption where IT departments require system package management for auditability and upgrade coordination across developer fleets

Why: Static binary: no runtime dependency; easy to pin in CI; cross handles sysroot; packages deferred to post-MVP

ADR-26

Licensing

Chosen

Apache 2.0

Rejected

MIT, GPL, BSL

When the rejected choice is right

GPL wins if the project's primary goal is to prevent proprietary forks and ensure all derivative build systems remain open-source; BSL wins for commercial open-core models where the vendor requires a time-delayed open-source conversion

Why: Apache 2.0: patent grant; permissive; compatible with Bazel ecosystem (also Apache 2.0)

ADR-27

Reproducibility verification

Chosen

Two-build reproducibility test in CI: build once, store output digests, clean, build again, compare digest maps; failure blocks merge

Rejected

None

When the rejected choice is right

Skipping the test is justified only for prototype-phase projects where tool determinism is assumed and CI time budget is < 5 minutes total; must be re-enabled before remote cache sharing is activated

Why: Directly validates P2 / I1; catches non-deterministic tool outputs; runs in Phase 14 CI gate

ADR-28

String interning (Label / paths)

Chosen

string-interner crate for Label components; TargetId(u32) as dense interned id

Rejected

Heap-allocated strings per node, Arc<str>

When the rejected choice is right

Heap-allocated Arc<str> wins for small repos (<10k targets) where the interning overhead (HashMap lookup on every intern) exceeds the allocation savings, or where Labels must be sent across thread boundaries without a shared interner

Why: Reduces allocator pressure in large graphs (>100k nodes); enables O(1) Label equality via id comparison

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alternative 1: Demand-Driven Incremental Evaluation (Skyframe / DICE model)

  BUILD files
      |
      v
  [SkyFunction registry]
      |
   evaluate(SkyKey)  <---+
      |                  | SkyValue needed?
      v                  | → restart current SkyFunction
  [Memo table]          |   → re-enter when dependency settles
  SkyKey → SkyValue ----+
      |
   changed values propagate dirtying upward

Regime where it wins: large C++ monorepos where header dependency scanning (gcc -M) generates dynamic dep edges not knowable at BUILD-file evaluation time. Skyframe's restartable evaluation handles this naturally; PBS's topological scheduler cannot — it would require a two-phase "scan then build" model. Real system that embodies it: Bazel (Skyframe, production at Google since ~2008) and Buck2 (DICE in Rust). Why PBS rejected it: restartable evaluation requires every SkyFunction to be written as a resumable coroutine that can be interrupted and replayed; this dramatically increases the complexity of every rule implementation. PBS's design principle is that all deps are declared statically (P5), which eliminates the use case that justifies restartability.

Alternative 2: Purely Functional Derivation Store (Nix model)

  .nix expressions
        |
        v
  derivation { name, builder, args, env, src-hashes }
        |
  /nix/store/<hash>-<name>/  (immutable, content-addressed path)
        |
  no incremental: path exists → cache hit; absent → full re-eval
  no action DAG: derivation is atomic

Regime where it wins: system-level software distribution and reproducible OS configuration, where the full closure of every package (including its runtime deps) must be content-addressed and the build graph is a forest of independent derivations rather than a fine-grained action DAG. Real system that embodies it: NixOS/Nix, Guix. Why PBS rejected it: Nix's derivation is coarse-grained (one hash per package, not per source file) and has no incremental model — changing one .c file re-evaluates the entire package derivation. PBS needs per-action granularity for developer feedback-loop latency targets (< 500 ms incremental rebuild for a 1-file change, §4.1).

Alternative 3: Distributed Peer-to-Peer Content Store (IPFS-style)

  CAS nodes (developer workstations + CI machines)
        |     \
        |      \
  [DHT: Digest → peer addresses]
        |
  peer lookup → pull blob from nearest peer
        |
  no central cache server; blobs propagate epidemically

Regime where it wins: large distributed organizations where a central remote cache server is operationally infeasible (no always-on infrastructure, high network partition rate between sites) and blobs are large enough that peer-to-peer locality matters. Real system that embodies it: IPFS (content-addressed peer-to-peer file system); Pijul's content-addressed patch distribution. Why PBS rejected it: DHT lookup adds variable latency (seconds vs. milliseconds for local lookup) and the gossip propagation delay means a freshly built artifact is not immediately available to dependent machines. REAPI's client-server model provides predictable latency and the server can apply eviction policies centrally. The IPFS CIDv1 key format is also incompatible with REAPI's sha256 Digest (see S8 background note).

Alternative 4: Event-Sourced Build Log (Shake model)

  Build DB: log of (key, value, deps) triples
        |
  on rebuild: replay log; re-run key if any dep changed
        |
  "early cutoff": if re-run produces same value, don't propagate dirty upward
  (Shake's key innovation over Make)

Regime where it wins: projects where intermediate results frequently produce identical outputs despite changed inputs (e.g., a code formatter that is idempotent, or a header preprocessor that outputs the same file for minor source edits). Shake's early-cutoff optimization avoids re-running downstream actions even when an upstream action re-executed. Real system that embodies it: Shake build system (Neil Mitchell, Haskell), used in GHC's build system. Why PBS rejected it: early cutoff requires comparing the new output value to the previous stored value after every re-execution, adding an extra CAS lookup and content-hash comparison per action. PBS's verifying rebuilder (P1 taxonomy) achieves the same effect via content-addressed ActionKey: if the output digest is unchanged, downstream actions have unchanged input digests and therefore unchanged ActionKeys — they hit the action cache without re-executing. PBS gets early cutoff semantics for free from the Merkle structure of ActionKeys.
