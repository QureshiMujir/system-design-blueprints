364 — Polyglot Build System from Scratch

Project Number: 364

Project Name: Polyglot Build System from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

1.1 Precise Engineering Description

Build a Bazel-class hermetic, content-addressed, multi-language build system in Rust. BUILD files declare targets in a small Starlark-like configuration language; targets lower to a directed acyclic action graph; each action's cache key is the SHA-256 hash of its declared inputs + command + environment + toolchain digest; actions execute in hermetic sandboxes exposing only declared inputs; outputs enter a content-addressed store keyed by digest; action results are reused locally or fetched from a remote cache so a clean rebuild of unchanged inputs performs zero recompilation.

1.3 Explicit Non-Goals

  • No distributed execution scheduler (remote execution uses REAPI; the server side is out of scope).
  • No general-purpose scripting host (BUILD language is intentionally sandboxed: no I/O, no unbounded loops).
  • No IDE/language-server integration beyond the query layer.
  • No container image build or push primitives.
  • No first-class Windows support (Linux namespace sandbox is primary; macOS sandbox-exec is secondary).
  • No dependency version resolution / SAT solver (see portfolio project #135); pbs-loader takes pinned hashes.

1.4 Intended Deployment Model

Monorepo pbs-server resident daemon with inotify/FSEvents watch; large target graph (>50 k targets)
Cross-compile Host exec_platform != target_platform; toolchain resolved per action

1.5 Target Users / Operators / Developers

  • Build engineers: author BUILD files, register toolchains, write custom rules.
  • Developers: run pbs build //..., consume hermetic artifacts.
  • Platform/infra engineers: configure remote cache endpoints, eviction policy, sandbox strategy.
  • Language rule contributors: extend pbs-rules with new language support via the provider model.

1.6 Recommended Language: Rust

The core is an action graph over a content-addressed cache with hermetic, sandboxed process execution: millions of cache entries, parallel action scheduling, and FS isolation via syscalls (namespaces / sandbox-exec / symlink forests). It demands bounded-memory graph storage, fast content hashing, safe process supervision, and exhaustive enums for the target/rule/action/artifact taxonomy. Rust gives memory-safe sandbox + process control, zero-copy CAS reads, deterministic hashing, and Send/Sync-checked parallel execution. Build server, loader, rules, sandbox, cache, and remote-execution client are all Rust; language toolchains (cc/rustc/python) are invoked as external hermetic tools, not reimplemented.

1.10 Required Prerequisites

  • Linux namespace APIs (CLONE_NEWNS, MS_BIND, pivot_root / chroot) or macOS sandbox-exec profiles.
  • POSIX process supervision: fork/exec, waitpid, kill, signal masking, file-descriptor inheritance.
  • SHA-256 internals and content-addressing theory (Merkle trees, deduplication, GC via reference counting).
  • DAG algorithms: topological sort, SCC detection (Tarjan/Kosaraju), reverse-reachability.
  • Starlark/Python grammar: LL(k) or Pratt parsing, environment frames, deterministic evaluation.
  • Remote procedure call and serialization: Protocol Buffers, gRPC, streaming upload/download.
  • File system events: inotify (Linux), FSEvents (macOS), debounce, rename detection.
  • Rust concurrency: tokio async runtime, rayon for CPU-bound parallelism, crossbeam channels, Arc<Mutex<_>> vs lock-free structures.

2.2 Historical and Architectural Significance

  • Bazel (2015, open-sourced from Blaze ~2006) is the canonical reference: invented the content-addressed action-cache + hermetic sandbox pattern at Google scale.
  • Buck/Buck2 (Meta) validated the design at a second hyperscaler; Buck2 rewrote the graph engine in Rust (DICE), demonstrating Rust feasibility.
  • Pants (Twitter/Foursquare origin), Please (Thought Machine) are Go/Python variants confirming cross-language viability.
  • The REAPI (Remote Execution API) spec is the de-facto standard for sharing cache and distributing actions (used by BuildBuddy, EngFlow, Buildfarm).
  • Nix's purely-functional derivation model (Dolstra 2006) independently validated content addressing as the correct model for reproducible software deployment.
  • 'Build Systems à la Carte' (Mokhov et al., ICFP 2018) gives the formal taxonomy: pbs sits in the "suspending, constructive" cell (Shake-class scheduler + Bazel-class rebuilder).

2.3 Engineering Muscles Developed

  • Correctness-first caching: understanding that a false cache hit is architecturally worse than a cache miss.
  • Graph algorithms at scale: DAG traversal, cycle detection, and reverse-dependency queries on graphs with >100 k nodes.
  • Process isolation as a first-class concern: namespace setup, capability dropping, seccomp filtering.
  • Deterministic hashing discipline: stable serialization for ActionKey; any non-determinism is a correctness bug.
  • Protocol design: action wire format, CAS chunk upload, ExecuteRequest batching.
  • Daemon architecture: resident in-memory state, file-watch integration, request multiplexing.

2.6 Calibration Value

Engineers who complete this project can reason about: why Bazel's Skyframe uses memoization over change detection; how REAPI decouples cache topology from execution locality; why non-deterministic compilers break distributed builds; and how to design a system where correctness (I1–I10) is structurally enforced, not tested after the fact. These capabilities are directly applicable to: platform-engineering roles, build-infrastructure work, systems tooling, and the design of any compute system where caching correctness is load-bearing.

2.7 What Mastery Looks Like

  • Content-addressed store design (Phase 1, 7): given a cache-key correctness requirement, derive the write-once + digest-on-read invariant from first principles; size and shard a CAS for a given artifact throughput target without looking up prior art.
  • Hermetic sandbox construction (Phase 6): explain why symlink forests + Linux namespaces enforce I3 structurally rather than by convention; implement the mount-namespace pivot-root sequence from the clone(2) man page without scaffolding.
  • ActionKey canonicalization (Phase 5): identify every source of non-determinism in a build command (env variables, path separators, argument order, platform ABI) and write a canonical serialization that eliminates each one; predict which changes cause cache-key collisions vs. misses.
  • Incremental build correctness (Phase 11): define "incremental equivalence" formally; trace how a single-file content change propagates through a 100k-node action DAG using reverse-BFS; explain why mtime fast-paths are safe only with content-verify fallback.
  • Polyglot rule abstraction (Phase 4, 10): map language-specific compiler semantics (rustc --extern, cc -I, python PYTHONPATH) into a language-agnostic Action + Provider model without leaking language details into the scheduler or cache layers.
  • Remote execution protocol design (Phase 12): read the REAPI proto spec and implement upload, execute, download as a correct state machine; handle partial-upload races, digest mismatches, and worker non-determinism without build correctness regression.
  • Toolchain-as-input discipline (Phase 9): register a cross-compilation toolchain, trace how the compiler binary's Digest flows into every downstream ActionKey, and prove that a compiler upgrade forces a complete cache miss for the affected language subgraph.
  • Build system performance diagnosis (Phase 8, 14): given a slow build, identify whether the bottleneck is ActionKey computation, cache lookup latency, sandbox setup, or scheduler queue contention; use criterion + flamegraph to attribute wall time to the correct subsystem.

3.2 Subsystem Descriptions

pbs-loader: Reads BUILD and .bzl files from disk; lexes and parses the Starlark-like config language (functions, dicts, lists, string ops, load() statements); evaluates rule() calls to produce Target instances with typed attribute maps. Trust boundary: no I/O inside evaluation; all file reads are explicit. Input: raw bytes of BUILD files. Output: Vec<Target> per package. Concurrency: packages evaluated concurrently; per-package evaluation is single-threaded and deterministic.

pbs-rules: Implements rule-class logic. Each rule implementation receives a Target's attributes and its deps' Provider set; emits a new Provider set (files, flags, link inputs) and a list of Actions. Rule implementations are pure functions over providers — no I/O. Trust boundary: rule code runs in the same process; sandboxing is at execution time, not evaluation time. Output: (Vec<Provider>, Vec<Action>) per target.

pbs-toolchain: Registers toolchains keyed by (lang, exec_platform, target_platform); resolves the matching toolchain per action by constraint matching. Toolchain tools (compiler binary, linker) are themselves ArtifactRefs with known Digests; their digests enter every ActionKey they influence. Trust boundary: resolution is deterministic given the registered set; no network access.

pbs-graph: Holds the target DAG (BuildGraph) and the lowered action DAG (ActionGraph). Resolves dep Labels to TargetIds across packages; detects cycles and reports the cycle path; computes dirty/affected sets on input-digest change for incremental builds. Trust boundary: pure in-memory computation; no I/O. Concurrency: read-only traversal is concurrent; mutation (loading new packages) is serialized.

pbs-action: Canonicalizes an Action into its ActionKey: serializes argv, sorts input digests, sorts env, appends platform digest and toolchain digest; SHA-256 hashes the result. Produces identical keys across machines for identical content (I1). No I/O; no side effects. This module is the hermeticity contract's enforcement point for cache correctness.

pbs-exec: Reads the action DAG topologically; dispatches ready actions to a bounded tokio + rayon worker pool (width = logical cores or configured limit). Checks pbs-cache before dispatching; on hit, marks outputs available immediately. On miss, dispatches to pbs-sandbox (local) or pbs-remote. Marks outputs available on completion to unblock dependent actions. Concurrency boundary: worker pool is the only shared mutable state; action metadata is accessed via Arc-guarded graph.

pbs-sandbox: Materializes the declared input root as a symlink forest (or bind-mount tree under Linux namespaces); runs the command with a scrubbed environment and cwd set to the input root; captures declared output paths and stdout/stderr as digests; denies or detects undeclared-input reads (I3). Persistence boundary: writes only to the declared output staging area; never touches the CAS directly. On macOS: sandbox-exec profile. On Linux: CLONE_NEWNS + pivot_root.

pbs-cache: Two-layer store. CAS layer: Digest → bytes, write-once, integrity-verified on read (I4), size-bounded with LRU eviction and pinning of live outputs. Action-cache layer: ActionKey → ActionResult, populated after every successful execution, served on cache hit. Both layers are async behind a trait so they can be backed by local FS, SQLite, or a remote store. GC eviction respects in-flight action pins.

pbs-remote: Implements the REAPI-style protocol. Uploads input root + Action proto to remote CAS; sends Execute RPC; polls for ActionResult; downloads output blobs into local CAS. Also acts as a remote action cache: check before executing locally; upload result after local execution (write-through). Falls back to local on RPC failure. Verifies all downloaded digest integrity (I4, I10).

pbs-query: Evaluates query expressions (deps(), rdeps(), somepath(), allpaths(), kind()) over the target graph and action graph. Inputs: parsed query AST + read-only BuildGraph. Outputs: sorted Vec<Label> or Vec<ActionKey>. Pure, no I/O during evaluation. Concurrency: read-only; concurrent with build execution.

pbs-server: Resident daemon process. Holds the loaded BuildGraph in memory; subscribes to inotify/FSEvents on source files; on change events recomputes dirty sets and triggers incremental rebuilds. Accepts build/test/run/query requests over a Unix domain socket; multiplexes responses with a structured build-event stream. Persistence boundary: maintains graph state in memory; flushes action-cache writes to pbs-cache on disk.

pbs-cli: Entry point. Parses subcommands (build, test, run, query, clean, cache); connects to the pbs-server daemon if running, or spawns a one-shot build if not; streams build events to terminal; exits with the action's exit code on failure.

6. Design Principles

P1. Hermeticity

Statement: An action sees only its declared inputs. The sandbox enforces this; a build never depends on undeclared ambient state (system headers, $HOME, network, host toolchain on $PATH).

Mechanism: pbs-sandbox materialises an input root containing exactly the ArtifactRef set listed in Action.inputs. The process is started with a scrubbed environment, cwd set to the input root, and filesystem isolation (namespace mount on Linux / sandbox-exec on macOS) that denies opens outside the root.

Tradeoff: Materialization cost (symlink forest creation) adds latency per action. Accepted: correctness is non-negotiable; Phase 14 hermeticity tests codify it.

Operational implication: Any system dependency (libc, kernel headers, dynamic linker) must be either (a) a declared toolchain artifact, or (b) an explicitly allowed ambient path (e.g. /lib/x86_64-linux-gnu/ld.so) listed in SandboxSpec.allowed_paths.

Violation consequence: A target that reads /usr/include/openssl/ssl.h without declaring it builds on the developer's machine (with OpenSSL installed) and silently fails on CI. The resulting stale-cache entry stores an output whose inputs are actually different across machines, breaking I2.

P2. Reproducibility / Determinism

Statement: Identical inputs + command + environment + toolchain produce byte-identical outputs and therefore an identical output Digest. Non-determinism in a tool is a build-correctness bug, not a build-system bug.

Mechanism: pbs-action canonicalises all inputs before hashing (sorted file lists, normalised env). pbs-sandbox scrubs PIDs, timestamps, and $TMPDIR-seeded random paths. Phase 14 reproducibility test: two independent clean builds → diff all output digests.

Tradeoff: Enforcing determinism requires tool-level discipline. PBS cannot fix a non-deterministic compiler (e.g. debug-info paths with absolute build-time prefixes); it can only detect and report the divergence.

Operational implication: Build rules should strip absolute paths from compiler outputs (e.g. -fdebug-prefix-map). If a tool embeds __DATE__ it must be seeded from a declared environment variable.

Violation consequence: Two machines executing the same ActionKey produce different digests. The cache stores one result; the other machine considers it a hit and uses wrong outputs. Build outputs diverge silently — a correctness break harder to debug than a build failure.

P3. Content Addressing Is the Cache Key

Statement: An action's cache key is the hash of its content (inputs + command + env + platform + toolchain), never a timestamp or a path. Identical content reuses results across machines, branches, and CI runs.

Mechanism: ActionKey(Digest) = sha256(canonical(argv) ++ sorted(input digests) ++ sorted(env) ++ platform_digest ++ toolchain_digest). pbs-action owns this computation. Paths are inputs only via their content digest — a file rename with no content change does not invalidate the cache.

Tradeoff: Computing input digests requires reading source files (or trusting a mtime fast-path for unchanged files). Phase 11 mtime fast-path: skip re-hash if mtime and size are unchanged; content-verify on mtime change.

Operational implication: Remote cache sharing requires all participants to produce identical ActionKey for the same logical action. Any machine-local leakage (absolute build dir embedded in argv) breaks sharing.

Violation consequence: If ActionKey included $BUILD_DIR, every workspace would have a unique key. Remote cache hit rate collapses to zero. Cross-machine sharing disappears.

P4. Correctness Over Speed

Statement: The cache must never serve a result that a real execution would not produce. A false cache hit is the cardinal sin — worse than a slow build.

Mechanism: I2 (cache soundness): before serving a cached ActionResult, recompute the ActionKey from current inputs and verify it matches the stored key. No time-based or inode-based shortcuts when determining validity.

Tradeoff: This prevents optimistic caching tricks (e.g. "output probably hasn't changed, skip re-execution"). If an input changes by one byte, the action re-runs. Accepted: the cost of a wrong build (silent corruption) exceeds the cost of extra work.

Operational implication: pbs-cache GC must never evict a CAS blob that a live ActionResult references. GC runs against a reference set snapshot taken before eviction.

Violation consequence: A stale cache hit delivers outdated object code. A downstream binary links old and new objects together. The resulting bug is non-reproducible, environment-dependent, and hours to diagnose.

P5. Explicit Dependencies

Statement: Every input and every output is declared. The graph is complete, so incremental invalidation, remote execution, and the sandbox are all sound.

Mechanism: BUILD rules declare srcs, deps, tools, data. pbs-graph resolves these to a complete ActionGraph. pbs-sandbox enforces the invariant at execution time (I3). Any undeclared input read is denied or detected.

Tradeoff: Rule authors must enumerate all inputs, including generated headers. Omitting one input leads to a sandbox failure, not a silent wrong build. The error is fast and localised.

Operational implication: genrule outputs that are consumed as inputs to other rules must appear in the consuming rule's srcs. pbs-graph validates this statically; a missing edge is a cycle-free but incomplete graph error caught before execution.

Violation consequence: An undeclared #include of a generated header is found at compile time only if the file happens to exist in $INCLUDE_PATH. On a clean machine it fails; on a dirty machine it silently builds. Incremental invalidation is unsound: the action is not re-run when its undeclared input changes.

P6. Uniform Action Abstraction Enables Polyglot

Statement: Every language reduces to the same Action (command + digested inputs + declared outputs). The cache, sandbox, scheduler, and remote-execution layer are language-agnostic.

Mechanism: pbs-rules produces Action structs; the language (cc, rust, py, genrule) is encoded in mnemonic only. pbs-exec, pbs-cache, pbs-sandbox, pbs-remote handle only Action — no language-specific branches.

Tradeoff: Rule authors bear the burden of mapping language-specific semantics (e.g. rustc's --extern flags, cc's -I paths) into the Action.command + Action.inputs fields. The abstraction boundary must be respected.

Operational implication: Adding a new language (e.g. Java) requires only a new pbs-rules module producing valid Action objects. No changes to pbs-exec, pbs-cache, or pbs-sandbox.

Violation consequence: If pbs-exec contains a if action.mnemonic == "RustcCompile" { ... } special case, the abstraction leaks. Language-specific logic in the execution layer makes cross-language deps fragile and testing combinatorial.

P7. Incremental by Default

Statement: A rebuild re-executes only actions whose input digests changed. Unchanged subgraphs do zero work (not just "fast" work).

Mechanism: Phase 11: source files are re-digested (mtime fast-path + content verify on change). Actions whose ActionKey is unchanged find a hit in the action cache and return immediately. Only actions with changed inputs (or changed transitive deps) recompute.

Tradeoff: The action cache must be consulted for every action in the dirty frontier, adding lookup latency. For large graphs with few changes, this is dominated by the savings from avoided re-executions.

Operational implication: The action cache hit rate is the primary metric for incremental build health. A falling hit rate (Phase 10 observability) signals non-determinism or undeclared inputs.

Violation consequence: If dirty tracking is absent, every build is a clean build. A 10 000-action graph rebuilds fully on a one-line change. Developer feedback loops collapse.

P8. Parallel and Bounded

Statement: Independent actions run concurrently up to a resource bound. The scheduler never exceeds the worker / memory budget.

Mechanism: pbs-exec: topological sort → ready queue → bounded tokio::task or thread pool of min(available_parallelism, --jobs) workers. Dependents are unblocked as their inputs become available.

Tradeoff: Unbounded parallelism causes memory pressure (each action materialises an input root) and CPU contention (thrashing). Bounded concurrency sacrifices some throughput for predictable resource usage.

Operational implication: The --jobs flag caps parallelism. The memory limit per action times --jobs must fit in available RAM. pbs-sandbox input-root size should be tracked and reported (P10).

Violation consequence: Spawning all actions at once on a 10 000-action graph exhausts file descriptors, RAM, and inodes (from symlink forests). The build OOM-kills or deadlocks on fd exhaustion.

P9. Toolchains Are Inputs

Statement: The compiler is a digested input, not an ambient tool on $PATH. Changing the compiler re-keys and rebuilds everything that used it.

Mechanism: pbs-toolchain resolves a Toolchain per action; each tool (compiler binary, linker, sysroot) is an ArtifactRef with a Digest. Those digests enter the ActionKey computation (P3). A compiler version bump changes the tool Digest → changes every ActionKey that uses it → cache miss → full rebuild.

Tradeoff: Toolchains must be registered as BUILD targets (or fetched hermetically). Using the host cc on $PATH is disallowed by the sandbox unless explicitly listed.

Operational implication: Cross-compilation requires registering separate toolchains per (exec_platform, target_platform) pair. pbs-toolchain constraint matching selects the correct one per action.

Violation consequence: A toolchain upgrade that is not captured as a Digest change produces stale cache hits with outputs from the old compiler. Subtle ABI differences cause link errors or silent wrong-code bugs downstream.

P10. Observability by Default

Statement: Every action emits its ActionKey, cache hit/miss, input count, output sizes, and timing. A build is fully explainable and queryable after the fact.

Mechanism: pbs-action emits structured ActionEvent records (key, mnemonic, hit/miss, duration_ms, input_bytes, output_bytes). pbs-server aggregates them into the build event stream. pbs-query exposes graph introspection.

Tradeoff: Structured event emission adds minor per-action overhead (< 1 µs). Accepted: the cost of an unexplainable build failure is hours; the cost of a build event is microseconds.

Operational implication: Build dashboards read the event stream. Cache hit rate, critical-path latency, and sandbox overhead are first-class metrics. pbs-cli build --explain //target traces why each action ran.

Violation consequence: Without structured observability, a 40% cache-hit-rate drop is invisible until CI time doubles. Root-cause analysis requires re-implementing graph introspection ad hoc.

P11. Query and Introspection Never Mutate or Execute

Statement: Evaluating any pbs-query function (deps, rdeps, somepath, allpaths, kind) or a daemon status/read request never triggers action execution and never mutates BuildGraph or ActionGraph state.

Mechanism: pbs-query's Evaluator reads through a RwLock read guard only; pbs-server routes QueryRequest to a read-only handler path (handler.rs) that is structurally distinct from BuildRequest/TestRequest dispatch into pbs-exec.

Tradeoff: A read-only query can observe a graph snapshot that is briefly stale relative to an in-flight incremental reload (Phase 11); correctness trades a small staleness window for lock-free query throughput under RwLock readers.

Operational implication: Any new query function must be implemented purely in terms of existing graph data with no side effects; a PR adding a mutating query function is rejected in review per this principle.

Violation consequence: A query function that triggered analysis or action execution would let a read-only pbs query invocation silently start billable remote-execution work, defeating the auditability CI operators rely on when polling the graph.

P12. Single-Writer, Many-Reader Daemon State

Statement: The daemon's resident BuildGraph/ActionGraph is guarded by exactly one writer (incremental reload) at a time, with unbounded concurrent readers (queries, status, build-dispatch reads) otherwise permitted.

Mechanism: pbs-server wraps DaemonState behind Arc<RwLock<...>> (tokio::sync::RwLock, writer priority); the file watcher's incremental-reload task (watcher.rs) is the sole producer of write-locks, and every other request path acquires a read lock.

Tradeoff: Writer priority can delay a burst of concurrent queries during a reload; accepted because reload latency (Phase 11 dirty propagation) is bounded and rare relative to query volume.

Operational implication: Any new request handler must document whether it needs a read or write lock; introducing a second writer path (e.g. an in-place cache-clear RPC) requires explicit serialization against reload.

Violation consequence: Two concurrent writers (e.g. a manual graph-edit endpoint added later without serialization) could interleave partial updates, corrupting rdeps_index and producing incorrect query results or missed incremental invalidation.

8.2 Digest Model

Digest {
  hash:       [u8; 32]   -- sha256 of raw bytes
  size_bytes: u64
}
  • Digest of empty content: sha256("") = e3b0c44..., size = 0; valid, not nil.
  • Nil sentinel: Digest { hash: [0u8;32], size_bytes: 0 } — never stored in CAS; used only as zero-value.
  • Hex encoding: lowercase 64-char hex + "/" + decimal size, e.g. abc123.../42.
  • Equality: compare both hash and size_bytes; size mismatch with matching hash is a collision signal → abort.
  • CAS write-once invariant: writing same digest with different bytes → integrity error (I4).

Digest computation sequence:

source file → mmap/read bytes → sha256 stream → Digest { hash, size_bytes=len }
generated artifact → write stream → tee sha256 hasher → Digest at close

  • Source artifacts: digested at graph-load time (mtime fast-path in Phase 11).
  • Generated artifacts: digest assigned after action completes and output is captured.
  • Artifact equality: by digest only; path is cosmetic for display.

8.4 ActionKey Computation (Canonical)

Deterministic hash over:

ActionKey = sha256(
  canonical_argv          -- argv[0..n] as NUL-separated bytes
  + sorted_input_pairs    -- sort by path; each: path NUL digest_hex NUL
  + sorted_env_pairs      -- sort by key; each: key "=" value NUL; volatile vars excluded
  + platform_digest_hex   -- hex of Platform Digest
  + toolchain_digest_hex  -- hex of resolved Toolchain Digest
)

Volatile env vars excluded (scrubbed before key computation): HOME, USER, LOGNAME, TMPDIR, TEMP, TMP, TERM, COLORTERM, LS_COLORS, PWD, OLDPWD, SHELL, SHLVL, _, any *_RANDOM*, RANDOM, SRANDOM.

Worked example — cc compile:

argv:    ["clang", "-O2", "-Ifoo/include", "-c", "src/foo.c", "-o", "foo.o"]
inputs:  [("src/foo.c", d1), ("foo/include/foo.h", d2), ("tools/clang", d3)]
env:     {"CC_FLAGS": "-Wall"}
platform_digest: d4  (linux-x86_64)
toolchain_digest: d5 (clang-14.0.0)

sorted_input_pairs: ("foo/include/foo.h", hex(d2)) < ("src/foo.c", hex(d1)) < ("tools/clang", hex(d3))
ActionKey = sha256( joined canonical bytes ) = ActionKey(Digest{hash:..., size_bytes:...})

Failure-path example — env leakage:

Build 1: HOME=/home/alice → scrubbed → ActionKey K
Build 2: HOME=/home/bob  → scrubbed → ActionKey K (identical)
Correct: same result served from cache.  (I7 upheld)

Build 3: CC_REVISION=gitsha not in volatile list → different ActionKey K' → re-execution triggered.
Mitigation: expand volatile list or declare CC_REVISION in attrs.

8.5 Action State Machine

States:  PENDING → READY → DISPATCHED → [CACHE_HIT | EXECUTING] → DONE | FAILED | RETRYING

Transitions:
  PENDING    → READY       : all input actions reach DONE; input digests available
  READY      → DISPATCHED  : scheduler dequeues; worker slot acquired
  DISPATCHED → CACHE_HIT   : action-cache lookup returns ActionResult (I2)
  DISPATCHED → EXECUTING   : cache miss; spawn sandbox or remote
  EXECUTING  → DONE        : exit_code==0 + all declared outputs captured (I6)
  EXECUTING  → FAILED      : exit_code!=0 OR missing output OR integrity error
  EXECUTING  → RETRYING    : transient error (OOM, remote timeout); retry_count < max_retries
  RETRYING   → DISPATCHED  : back-off elapsed
  FAILED     → (terminal)  : propagate failure to all rdeps; build aborts (or --keep-going continues)
  CACHE_HIT  → DONE        : outputs materialized from CAS to output tree

State table:

State Scheduler sees Worker slot Cache queried Sandbox active
PENDING not eligible no no no
READY eligible no no no
DISPATCHED in-flight yes yes no
CACHE_HIT in-flight yes — no
EXECUTING in-flight yes — yes
DONE complete released — no
FAILED terminal released — no
RETRYING waiting released — no

8.8 CAS Storage Layout

cas_root/
  blobs/
    <aa>/          -- first two hex chars of sha256 (256 shards)
      <full_hex>_<size>   -- file containing raw bytes
  tmp/             -- atomic write staging (rename-into-place)
  gc/
    pinned.db      -- lmdb: ActionKey → Vec<Digest> (live output pins)
    lru.db         -- lmdb: Digest → last_access_epoch (eviction ordering)

Write protocol (atomic):

  1. Write bytes to cas_root/tmp/<random_uuid>.
  2. Verify sha256 of written bytes == claimed digest (I4).
  3. rename(tmp/uuid, blobs/aa/full_hex_size) — atomic on POSIX; idempotent if dest exists.
  4. Update lru.db last_access_epoch.

Read protocol:

  1. Open blobs/aa/full_hex_size.
  2. Stream bytes; tee into sha256 hasher.
  3. At EOF, verify hash == key; if mismatch: delete file, return IntegrityError.
  4. Update lru.db.

GC / eviction:

  • Trigger: store size > high-water mark (configurable, default 10 GB).
  • Pin set: all Digests referenced by live ActionResults in action cache.
  • Evict LRU entries not in pin set until below low-water mark.
  • GC runs in background thread; reads are not blocked; writes are paused only during final trim.

8.10 Sandbox Input Tree and Execution Semantics

Input root materialization (symlink forest strategy):

sandbox_root/
  inputs/
    <declared input paths as symlinks → CAS blobs or workspace files>
  outputs/        -- empty dirs pre-created for declared output paths
  scratch/        -- writable tmpfs (not captured)

Execution sequence:

  1. Create sandbox_root under tmpfs or dedicated sandbox mount.
  2. For each ArtifactRef in Action.inputs: create symlink inputs/path → CAS path (or workspace/path).
  3. Pre-create parent dirs for each declared output path under outputs/.
  4. Set env = Action.env (volatile vars scrubbed; I7).
  5. execve(argv[0], argv, env) with cwd = sandbox_root/inputs.
  6. On process exit: collect outputs/declared_path for each declared output.
  7. Compute digest of each output; store in CAS (I6).
  8. Deny undeclared reads: on Linux, seccomp/namespace deny open() of paths outside inputs/; on macOS, sandbox-exec profile restricts file reads. Violation → UndeclaredInputError (I3).

Output capture edge cases:

Scenario Handling
Declared output missing MissingOutputError; action FAILED
Declared output is a symlink follow; store target bytes in CAS
Undeclared file written to outputs/ ignored (not captured); warning logged
Empty output file valid; Digest with size=0; stored in CAS
Output dir instead of file error if declared path expected file
Sandbox escape via /proc/self/fd seccomp rule blocks; FAILED

8.12 Incremental Dirty Tracking Model

SourceDelta = { added: Set<Label>, removed: Set<Label>, changed_digests: Map<Label,Digest> }

dirty_set computation:
  for each changed source s in SourceDelta.changed_digests:
    old_digest = prev_snapshot[s]
    new_digest = current_digest(s)
    if old_digest != new_digest:
      mark s dirty
      propagate_dirty(rdeps(s))   // transitive upward via action graph

propagate_dirty(node):
  if node already dirty: return   // avoid re-traversal
  mark node dirty
  for each rdep of node: propagate_dirty(rdep)

Clean actions (not dirty) → served from action cache without re-execution (I8). Dirty actions → re-execute; new ActionKey if any input digest changed; old cache entry remains (may be reused if inputs revert).

Toolchain change handling:

  • Toolchain digest enters ActionKey (I9); changing compiler binary changes every ActionKey that included it → full rebuild of affected language subgraph.
  • Platform change: affects all configured targets on that platform; other platforms unchanged.

Mtime fast-path:

  • If file mtime unchanged since last snapshot: skip re-digest; assume same content.
  • Overridable with --no-mtime-shortcut for paranoid correctness.
  • Correctness guarantee: mtime fast-path can produce false-negatives (re-digest skipped) only if OS mtime precision is lost; POSIX requires 1-second precision minimum; sub-second precision used where available (stat.st_mtim.tv_nsec).

8.13 Query Language Semantics

Grammar:

query       ::= expr
expr        ::= func_call | label_pattern | "(" expr ")"
              | expr "+" expr        -- union
              | expr "-" expr        -- difference
              | expr "^" expr        -- intersect
func_call   ::= ident "(" arg_list ")"
arg_list    ::= expr ("," expr)* ("," int)?
label_pattern ::= label | ("//..." glob)
int         ::= [0-9]+

funcs:
  deps(x)           -- transitive deps of x including x
  deps(x, depth)    -- deps up to depth hops
  rdeps(universe, x)        -- rdeps of x within universe
  rdeps(universe, x, depth) -- bounded
  somepath(a, b)    -- one path from a to b; empty if none
  allpaths(a, b)    -- all paths from a to b
  kind(pattern, x)  -- filter x to targets whose rule kind matches glob pattern
  filter(pattern, x)-- filter x to labels matching regex
  labels(attr, x)   -- extract label values of attr from x
  siblings(x)       -- all targets in same package as x
  buildfiles(x)     -- BUILD files defining targets in x

Evaluation model:

  • Queries execute over the loaded target graph (not action graph).
  • rdeps requires a universe bound to avoid full-graph scan.
  • Results: sets of Labels; deterministic ordering (lexicographic).
  • Error on unresolvable label within query; missing package → error unless --keep-going.

Worked example:

query: rdeps(//..., //lib/crypto:hash, 2)
→ all targets that (transitively, ≤2 hops) depend on //lib/crypto:hash
→ [{//app:server, //lib/auth:token, //lib/crypto:hash}]

Failure-path: somepath(//a:x, //a:x) → {//a:x} (trivial path; not an error). somepath(//a:x, //z:w) when no path exists → empty set (not an error; caller checks emptiness).

  | BuildStarted        { invocation_id: Uuid, targets: Vec<Label>, flags: Map }

Phase 1 — Core Types + Content Addressing

1.1 Objectives

  • Define every canonical type in pbs-core with zero I/O dependencies.
  • Implement sha256 content addressing: Digest is the universal key for all blobs, actions, platforms.
  • Canonical Label parsing and validation: //pkg/sub:target, :local, @repo//pkg:name.
  • ActionKey computation (deferred to Phase 5, but its type scaffolding lives here).
  • Intern TargetId(u32) via a side-table; ids must be stable within a build invocation.
  • Compile-time guarantee: no std::fs, no tokio, no network in pbs-core.

1.2 Detailed Implementation Steps

Theory anchors: content-addressing from P3 (Nix), S3 (FIPS SHA-256); TargetId interning from R3 (Buck2 core/src); trait model from B3 Ch. 11; Digest as universal key from P3, P1. Every type introduced here is referenced in ADR-01 (Rust type system), ADR-06 (SHA-256), ADR-28 (interning). (applies P3, ADR-06, ADR-28, B3, S3)

Label grammar (EBNF):

label       ::= ('@' repo_name '//')? '//' pkg_path ':' target_name
              | ':' target_name

repo_name   ::= [a-zA-Z0-9_.-]+
pkg_path    ::= (segment '/')* segment | ""
target_name ::= [a-zA-Z0-9_./-]+

  • Canonical form: always emit //pkg:name; omit @ for default repo.

Property test harness: proptest in pbs-core/tests/; strategies for random valid labels and random byte slices.

1.7 Performance Concerns

  • Interner uses HashMap<Label, TargetId>; Label clone on every insert — use Arc<str> for package path segments to share allocations.
  • sha256_of called on every source file at startup; batch via rayon for large repos.
  • Digest is 40 bytes; pass by value in hot paths to avoid pointer chasing.
  • Avoid String::from_utf8 in inner loops; validate label bytes in-place.

1.8 Edge Cases

Case Handling
Label with no explicit target (: omitted) default target_name = last segment of package path
Empty package path //.:name reject; package must be non-empty or the root //
size_bytes = 0 with non-empty hash reject at construction; empty input has known sha256
Digest::from_hex with odd-length hex return Err(ParseError::OddHex)
TargetId overflow (> 2^32 targets) saturate and return Err; log fatal; build aborts

1.9 Failure Analysis

  • Wrong Digest: downstream cache serves wrong artifact. Detection: CAS integrity check on every read (I4). Blast radius: single action's outputs. Recovery: evict blob, re-execute.
  • Label intern collision: two targets share a TargetId; build produces outputs from wrong target. Detection: graph-level assertion label(id) == expected_label. Recovery: rebuild Interner from scratch.
  • Corrupted [u8;32] hash field: not possible at construction if sha2 crate is correct; ensure no unsafe transmute.

1.10 Operational Notes

  • pbs-core emits no logs; it is a pure library.
  • Expose pbs_core::diagnostics::label_stats(interner) -> LabelStats { count, max_depth } for daemon metrics.
  • Digest hex representation used in all log lines: DIGEST=<64-char-hex>/<size>.
  • All types implement serde::{Serialize, Deserialize} for persistence and wire use in later phases.

Phase 2 — BUILD Loader + Config Language

2.1 Objectives

  • Implement pbs-loader: full pipeline from raw BUILD file text to a Vec<Target>.
  • Config language: Starlark-inspired declarative subset — function calls, lists, dicts, string interpolation, integer literals, boolean; no unbounded loops, no recursion.
  • load("//path:file.bzl", "symbol") for importing macros and rule definitions from other files.
  • rule() registration: callers declare attribute schema; pbs-loader instantiates typed Targets.
  • Deterministic evaluation: given identical file contents, identical Vec<Target> output.
  • Error messages carry file + line + column; package loading is isolated (no global mutable state between packages).

Phase 5 — Action Key (Cache Key) Computation

5.1 Objectives

  • Implement pbs-action: canonical, machine-independent ActionKey = sha256(argv || sorted(input_digests) || sorted(env) || platform_digest || toolchain_digest).
  • Exclude volatile env vars (e.g. HOME, USER, TMPDIR, PATH unless explicitly declared); the exclusion list is configurable.
  • Guarantee: two builds on different machines with identical inputs, command, and toolchain produce the exact same ActionKey.
  • Key stability: key must not change across re-orderings of equivalent input lists or env maps.
  • Feed computed ActionKey into pbs-cache lookup (Phase 7) and pbs-exec scheduling (Phase 8).

5.2 Detailed Implementation Steps

Theory anchors: canonical pre-image construction from B10 (SHA-2 chapters); length-prefixed encoding to avoid ambiguity from S3 (FIPS 180-4 padding); sorted input pairs from P1 (verifying rebuilder: key must be deterministic regardless of input order); volatile env exclusion from P9 (Adams/McIntosh non-determinism sources); REAPI Digest encoding from S1, S7. (applies P3, P9, ADR-06, S3, B10)

Crate: pbs-action — files: lib.rs, key.rs, canon.rs, volatile.rs.

Canonicalization procedure (canon.rs):

STEP 1  argv        — encode as length-prefixed bytes: u32_le(n) || for each arg: u32_le(len) || utf8_bytes
STEP 2  inputs      — sort Vec<ArtifactRef> by (path_bytes, digest.hash); encode each as: path_bytes || 0x00 || digest.hash[0..32]
STEP 3  env         — filter out volatile keys; sort remaining by key; encode each as: key || 0x3D || value || 0x00
STEP 4  platform    — emit platform Digest.hash[0..32]
STEP 5  toolchain   — emit toolchain Digest.hash[0..32]; if no toolchain, emit [0u8;32]
STEP 6  sha256      — feed all bytes above in order into sha256 state; output 32 bytes = ActionKey

Volatile env filter (volatile.rs): default deny-list: ["HOME","USER","USERNAME","LOGNAME","TMPDIR","TEMP","TMP","PWD","OLDPWD","SHLVL","_","TERM","COLORTERM","DISPLAY","DBUS_SESSION_BUS_ADDRESS"]. Allow-list override via build config / declare_env in rule. Env vars not in either list: deny by default (safe default = exclude).

ActionKey type (key.rs):

struct ActionKey(pub [u8; 32]);
impl ActionKey {

    fn to_hex(&self) -> String;          // 64-char lowercase hex

Theory anchors: namespace isolation from S5 (clone/unshare man pages) and R1 (LinuxSandboxedSpawnRunner); macOS Seatbelt profiles from S6; symlink-forest materialization from R4 (Please's fs/ design); TOCTOU-safe fd-based file open from S10 (POSIX openat/O_PATH); env scrubbing from §6 P1 Hermeticity; output-capture atomic write from B8 (OSTEP journaling/rename); I3 invariant enforcement in this phase. SandboxSpec (from pbs-core): struct SandboxSpec { input_root: PathBuf, input_tree: Vec<(PathBuf, Digest)>, output_paths: Vec<PathBuf>, command: Vec<String>, env: BTreeMap<String, String> /* pre-scrubbed by pbs-action */, isolation: IsolationMode, working_dir: PathBuf /* = input_root */ }; enum IsolationMode { SymlinkForest, LinuxNamespace, MacSandboxExec, Noop }.

Materialization (materialize.rs): create input_root as a temp dir under pbs-cache's CAS blob dir (same filesystem → cheap link()/symlink()); for each (rel_path, digest) in input_tree, resolve the digest to a CAS blob path, create parent dirs, and symlink(blob_path, input_root/rel_path) (symlink forest) or link() (hardlink, same device); mark the symlink forest read-only to the child process (chmod or bind-mount ro on Linux); create input_root/.sandbox_tmp as writable scratch for TMPDIR.

Isolation (isolate.rs):

Process launch (isolate.rs):

  • Use std::process::Command; set current_dir(input_root), env_clear(), then insert scrubbed env.

  • Timeout: configurable per action; SIGKILL child process group on expiry.

Undeclared input detection (detect.rs):

  • LinuxNamespace: structural (filesystem boundary); no audit needed.
  • MacSandboxExec: sandbox-exec policy emits deny events to syslog; parse on failure.
  • SymlinkForest (fallback): optional strace -e trace=openat,open wrapper; parse output for paths outside input_root; emit SandboxWarning::UndeclaredRead.

Cleanup: remove input_root tree after capture; errors in cleanup are logged but do not fail the action.

Phase 7 — Content-Addressed Cache (CAS + Action Cache)

7.1 Objectives

  • Implement pbs-cache: CAS store (digest→bytes) + action cache (ActionKey→ActionResult).
  • Guarantee write-once, dedup, integrity-verified-on-read semantics per I4.
  • Serve cache hits by materializing outputs into the output tree from CAS.
  • Enforce size-bounded eviction (LRU with live-output pinning).
  • Provide the cache interface consumed by pbs-exec (Phase 8) and pbs-remote (Phase 12).

7.2 Detailed Implementation Steps

Theory anchors: write-once + integrity-on-read from P3 (Nix store) and P11 (content-addressed build artifacts); GC via live-reference pinning from R6 (Nix GC roots, S9 OCI manifest reference counting); LRU eviction from B4 Ch. 3 (storage engine eviction); atomic rename from B8 Ch. 36–40 (journaling/fsync); LMDB single-writer many-reader from ADR-08; I4 invariant enforced in this phase. (applies P3, P11, I4, ADR-07, ADR-08, B4, S9)

CAS layout (pbs-cache/src/cas.rs)

  • Root dir: $PBS_CACHE_DIR/cas/ partitioned by hex[0..2]/hex[2..4]/hex[4..]/.
  • Write path: compute sha256 of bytes inline, compare to declared Digest; if mismatch → reject (I4); if file exists with correct size → skip (dedup).
  • Read path: open by digest-path, sha256-verify on read, return bytes or CasError::Corrupt.
  • CasStore trait: trait CasStore: Send + Sync { fn put(&self, digest: Digest, data: &[u8]) -> Result<()>; fn get(&self, digest: &Digest) -> Result<Bytes>; fn contains(&self, digest: &Digest) -> bool; fn missing(&self, digests: &[Digest]) -> Vec<Digest>; }
  • Atomic write: write to <path>.tmp, fsync, rename (POSIX atomic).

Action cache (pbs-cache/src/action_cache.rs)

  • Flat store: $PBS_CACHE_DIR/ac/<action_key_hex> → serialized CacheEntry (bincode/msgpack).
  • ActionCache trait: trait ActionCache: Send + Sync { fn get(&self, key: &ActionKey) -> Option<ActionResult>; fn put(&self, key: ActionKey, result: ActionResult) -> Result<()>; }
  • On hit: verify all output_digests are present in CAS before returning result (prevents phantom hits).

Eviction (pbs-cache/src/eviction.rs)

  • LRU index: DashMap<Digest, AccessRecord> where AccessRecord = {atime, size_bytes}.
  • Pinset: HashSet<Digest> of outputs referenced by in-flight actions (populated by pbs-exec).
  • GC trigger: total CAS size exceeds max_cache_bytes; evict LRU entries not in pinset until below target_bytes (e.g. 0.8 × max).
  • Action cache entries evicted in LRU order concurrently with CAS GC pass.
  • Background GC thread; woken by size-threshold cross or explicit cache clean subcommand.

Output materialization (pbs-cache/src/materialize.rs)

  • Given ActionResult, iterate output_digests; fetch each from CAS; write to declared output path under $PBS_OUTPUT_ROOT.
  • Paths created atomically (tmp + rename); permissions: 0o444 for files, 0o755 for executables flagged in ActionResult.
  • stdout/stderr digests materialized to <action_key>.stdout / .stderr under a log dir.

Observability hooks

  • Counters: cache.cas.put_bytes, cache.cas.hit, cache.cas.miss, cache.cas.corrupt, cache.ac.hit, cache.ac.miss, cache.gc.evicted_bytes.
  • Structured log line per operation: {action_key, hit: bool, latency_us}.

8.1 Objectives

  • Implement pbs-exec: topological scheduling of the action DAG.
  • Bounded parallelism: N = num_cpus worker threads; configurable via --jobs.
  • Per-action pipeline: AC lookup → sandbox dispatch (Phase 6) → CAS populate + AC populate.
  • Correct unblocking: an action becomes ready only when all its input actions have completed and their outputs are in CAS.
  • Retry transient failures with backoff; propagate persistent failures up the graph.
  • Deterministic final build result regardless of scheduling order (I1, I8).

8.2 Detailed Implementation Steps

Theory anchors: verifying+topological scheduler class from P1 (Build Systems à la Carte); critical-path priority from P13 (Golgi DAG-aware scheduling); work-stealing ready queue from ADR-05 (rayon); bounded parallelism from §6 P8; AtomicUsize pending-deps counter from B3 Ch. 16 (lock-free structures); I1 + I8 invariants enforced end-to-end in this phase. (applies P1, P13, I1, I8, ADR-03, ADR-05)

Scheduler state (pbs-exec/src/scheduler.rs)

  • Input: ActionGraph (from pbs-graph); each node carries ActionKey, Action, dep edges.
  • ReadyQueue: priority queue (min-heap by critical-path length for latency minimization); Arc<Mutex<BinaryHeap<ReadyAction>>>.
  • Per-node state: Pending | Ready | Running | Done(ActionResult) | Failed(Error).
  • in_flight: AtomicUsize — live running actions; block new dispatches when >= job_limit.
  • On Done: decrement each dependent's pending_deps: AtomicUsize; when it hits 0, enqueue to ReadyQueue.

Worker pool (pbs-exec/src/worker.rs)

  • N OS threads, each running worker_loop(rx: Receiver<DispatchMsg>).
  • DispatchMsg carries ActionKey, Action, SandboxSpec, handle to CasStore + ActionCache.
  • Worker sequence per action: AC get(action_key) — hit materializes outputs and reports Done; a miss calls pbs-sandbox::run(SandboxSpec) to capture an ActionResult, puts all output bytes into CAS and the ActionResult into AC, then sends Done(action_key, result) on the completion channel.

Retry logic (pbs-exec/src/retry.rs)

  • RetryPolicy { max_attempts: u8, base_delay_ms: u64, backoff: Exponential }.
  • Retry on: SandboxError::Transient, CasError::Io, RemoteError::Unavailable.
  • No retry on: non-zero exit (build failure), SandboxError::UndeclaredInput (hermeticity violation), CacheError::Corrupt.
  • Attempt counter per ActionKey in DashMap<ActionKey, u8>.

Completion + propagation (pbs-exec/src/propagate.rs)

  • Failed action propagates Error::DepFailed to all transitive dependents without executing them.
  • Terminal nodes (no dependents): their ActionResult collected into BuildResult.
  • BuildResult { outputs: Map<Label, Vec<ArtifactRef>>, failed: Vec<(ActionKey, Error)>, timing: Vec<ActionTiming> }.

Observability

  • Span per action: {action_key, mnemonic, cache_hit, start_time, duration_us, attempt}.
  • Counters: exec.actions_total, exec.cache_hits, exec.retries, exec.failures, exec.queue_depth.
  • Critical-path log: longest chain by cumulative duration emitted at build end.

Core types (pbs-core additions): struct Constraint { key: String, value: String }; struct Platform { constraints: BTreeSet<Constraint> } (BTreeSet → deterministic digest); struct Toolchain { lang: String, exec_platform: Digest, target_platform: Digest, tools: BTreeMap<String, ArtifactRef> } (tool name → ArtifactRef). Toolchain registry (pbs-toolchain/src/registry.rs): ToolchainRegistry: Vec<RegisteredToolchain> where RegisteredToolchain = { toolchain: Toolchain, priority: i32 }; populated at load time from register_toolchain(name, toolchain_label) calls in BUILD files (pbs-loader). resolve(lang, exec_platform, target_platform) -> Result<Toolchain> filters candidates by lang, then by exec_platform.constraints ⊇ required_exec_constraints, then by target_platform.constraints ⊇ required_target_constraints, sorts by priority desc, and returns the first — erroring if empty or ambiguous.

Constraint matching (pbs-toolchain/src/constraint.rs): Platform::satisfies(required: &Platform) -> bool holds when every constraint in required appears in self (strict match — extra constraints in the candidate are allowed, missing ones reject). Constraint key namespace: os, cpu, compiler_version, abi, libc, custom.

Toolchain as action input (pbs-action integration): ActionKey computation (Phase 5) receives toolchain_digest: Digest as an explicit input via pbs-action::build_action_key(action, toolchain_digest) -> ActionKey; if the toolchain changes (e.g. compiler binary replaced), toolchain_digest changes so every affected ActionKey differs, forcing a cache miss and re-execute (I9).

Tool artifact digestion (pbs-toolchain/src/digest_tools.rs): at registration each tool path is digested via Digest::from_file(path), cached in ToolchainRegistry, and refreshed only if mtime changes (mtime fast-path, content verify); the resulting ArtifactRef for each tool is treated as an input in every action that uses it.

Cross-compilation model: exec_platform is where the action runs (host constraints, e.g. os=linux, cpu=x86_64); target_platform is what the output targets (e.g. os=linux, cpu=aarch64), declared via cc_binary(name=..., target_compatible_with=["//platforms:aarch64"]). A configured target is (Target, target_platform) with toolchain resolved per configured target; pbs-graph creates two TargetId entries for the same label under different platforms.

BUILD file declarations (pbs-loader extension): platform(name, constraint_values=[...]) declares a Platform target; toolchain(name, toolchain_type, exec_compatible_with=[], target_compatible_with=[], toolchain=...) declares one; register_toolchain("//toolchains:gcc_linux_x86") registers it globally; use_toolchain(toolchain_type) inside a rule implementation accesses the resolved toolchain provider.

Observability: log on each resolution {lang, exec_platform, target_platform, resolved_toolchain_label, toolchain_digest}; counters toolchain.resolution_total, toolchain.resolution_failures; warn if more than one matching toolchain (ambiguity resolved by priority but flagged).

9.7 Performance Concerns

Phase 11 — Incremental Rebuild

11.1 Objectives

  • Change detection: re-digest source inputs using mtime fast-path then content verification; update ArtifactRef.digest for changed sources.
  • Invalidation: recompute ActionKey for all actions whose input digests changed; discard action-cache entries with old keys automatically (cache miss causes re-execution).
  • Minimal-work rebuild: actions with unchanged ActionKey serve from cache; zero re-execution for unchanged subgraphs.
  • Toolchain/platform change: changing a toolchain re-keys every action that used that toolchain digest; full affected-set re-executes.
  • Correct I8 (incremental equivalence): incremental build output digests must equal clean build output digests.

11.2 Detailed Implementation Steps

Theory anchors: incremental equivalence formalism from P2 (Build Systems à la Carte: Theory and Practice); dirty-set by reverse-BFS from P1 (verifying rebuilder); mtime fast-path safety from B8 (OSTEP inode mtime precision); bincode + version prefix for state schema from ADR-09; inotify/FSEvents abstraction from ADR-24; I8 invariant enforced in this phase; content-verify fallback from S3 (SHA-256 streaming). (applies P1, P2, I8, ADR-24, B8, S3)

Source digest tracking (pbs-graph/src/dirty.rs)

  • SourceRecord { path: PathBuf, last_mtime: SystemTime, last_digest: Digest } — persisted in <cache_root>/source_records.bincode.
  • fn check_source(rec: &mut SourceRecord, path: &Path) -> SourceStatus — SourceStatus::Clean | Changed(Digest).
  • Mtime fast-path: if current_mtime == last_mtime, return Clean without reading file content.
  • Content verify: if mtime changed, re-hash file with sha256; if digest unchanged (mtime-only touch), update mtime, return Clean.
  • Batch check: fn scan_sources(records: &mut SourceRecordStore, sources: &[ArtifactRef]) -> Vec<(ArtifactRef, Digest)> — parallelized with rayon.

Dirty propagation (pbs-graph/src/propagate.rs)

  • Walk action DAG in topological order; for each action, collect current input digests from ArtifactRef (sources: from SourceRecordStore; generated: from previous action's ActionResult.output_digests).
  • Recompute ActionKey from current inputs; compare to stored ActionKey in IncrementalState.
  • Mark action Dirty if key differs; mark it Clean otherwise.
  • Dirty propagation: if action A is dirty, all downstream actions depending on A's outputs are also re-evaluated (their input digests include A's outputs, which may change).
  • IncrementalState { action_states: HashMap<ActionKey, ActionState>, source_records: SourceRecordStore } — persisted between builds.

Toolchain/platform re-keying: toolchain digests are part of ActionKey (Phase 9), so a changed compiler binary changes the toolchain digest; fn diff_toolchains(prev: &ToolchainRegistry, curr: &ToolchainRegistry) -> Vec<(Lang, PlatformDigest)> returns changed entries, and for each, all actions using that toolchain are marked dirty by invalidating their ActionKey in IncrementalState.

Minimal rebuild execution

  • pbs-exec reads IncrementalState; only dispatches Dirty actions to the scheduler (Phase 8).
  • Clean actions: outputs are already in CAS (from previous build); ActionResult served directly from action cache.
  • Post-build: persist updated IncrementalState atomically (rename from temp file).

File watcher integration (pbs-server)

  • pbs-server uses notify crate for inotify/FSEvents/kqueue; on file-change event, invalidate the affected source record in SourceRecordStore.
  • Debounce: collect events for 50 ms before triggering incremental scan to avoid rebuild storms on rapid saves.

Persistent state schema (pbs-graph/src/state_schema.rs)

  • Serialized via bincode + version prefix: [u32 version][bincode payload].
  • On version mismatch: discard state, perform full rebuild.

11.7 Performance Concerns

  • Source scan parallelism: rayon::par_iter over SourceRecordStore; I/O bound — use tokio::fs with bounded concurrency (32 tasks) to avoid fd exhaustion.
  • IncrementalState serialization: bincode is fast but HashMap serialization with large graphs is O(N); use BTreeMap for deterministic order + compression (zstd level 1) to reduce I/O.
  • Dirty propagation: topological walk is O(V+E); avoid re-allocating the dirty set on each build with a persistent BitVec indexed by TargetId.
  • File watcher event flood: batch debounce prevents re-triggering incremental scan per keystroke; cap event queue at 1000 events before forcing full scan.

Phase 12 — Remote Cache + Remote Execution

12.1 Objectives

  • Implement pbs-remote: REAPI-style client for remote CAS (upload/download blobs by digest) and remote execution (submit Action, receive ActionResult).
  • Remote cache: treat remote action cache as shared secondary cache across machines and CI; check before local execution.
  • Remote execution: optionally dispatch actions to a remote worker (e.g., BuildBarn, Buildfarm, EngFlow); receive result + download outputs.
  • Fallback: on remote unavailability or error, transparently fall back to local sandbox execution (Phase 6).
  • Result verification: validate returned ActionResult.output_digests against downloaded blobs (I4 + I10).
  • Enforce I10: remote and local execution must produce identical output digests for the same ActionKey.

12.2 Detailed Implementation Steps

Theory anchors: REAPI proto message shapes from S1 (remote_execution.proto) and P8 (Distributed Caching with REAPI); batch upload heuristics from P12 (Google RBE Overview); Bloom-filter for remote-present optimization from B4 Ch. 3 (probabilistic data structures); I4 + I10 invariants enforced via download digest verification; mTLS from ADR-22 (tonic gRPC); fallback circuit breaker from Failure Modes & Recovery F5. (applies P6, P8, P12, I4, I10, ADR-22, S1, S7)

Protocol layer (pbs-remote/src/proto.rs)

  • Define internal wire types mirroring REAPI google.devtools.remoteexecution.v2 (no protobuf dependency required; use prost or hand-written serde structs).
  • Key messages: RemoteAction { action_digest: Digest, do_not_cache: bool }, RemoteActionResult { exit_code: i32, output_files: Vec<OutputFile>, stdout_digest: Digest, stderr_digest: Digest }, FindMissingBlobsRequest/Response, BatchUpdateBlobsRequest/Response, ExecuteRequest/Response.
  • Transport: reqwest-based HTTP/2 client; configurable endpoint + mTLS via rustls.

CAS client (pbs-remote/src/cas_client.rs): fn find_missing(digests: &[Digest]) -> Vec<Digest> is a batch RPC returning the subset not present in remote CAS; fn upload_blobs(blobs: &[(Digest, Bytes)]) -> Result<()> batch-uploads missing blobs respecting the server max-chunk-size (default 4 MiB); fn download_blob(digest: Digest) -> Result<Bytes> downloads a single blob and verifies sha256(bytes) == digest.hash on receipt (I4); tree upload fn upload_input_root(root: &InputTree) -> Result<Digest> serializes the Directory tree and uploads all missing blobs + directory nodes recursively.

Action cache client (pbs-remote/src/ac_client.rs): fn get_action_result(key: &ActionKey) -> Option<ActionResult> is an HTTP GET returning None on 404 or transport error; fn update_action_result(key: &ActionKey, result: &ActionResult) writes through after local execution to populate the remote cache.

Execution client (pbs-remote/src/exec_client.rs): fn execute(action_digest: Digest, input_root_digest: Digest) -> Result<RemoteActionResult> long-polls or streams the Execute RPC, polling GetOperation until done = true; timeout is configurable per action (default 10 min, local fallback on deadline exceeded); retries 3 attempts on UNAVAILABLE, none on FAILED_PRECONDITION (bad input).

Integration into execution engine (pbs-exec/src/remote_dispatch.rs): RemoteDispatch implements SpawnStrategy, checked before LocalDispatch. Sequence per action: check the remote action cache (ac_client::get_action_result) — on hit, download missing outputs from remote CAS into local CAS and return the ActionResult; on cache miss, upload the input tree + action, call exec_client::execute, download outputs, and store in local CAS + remote AC; on any remote error, emit WARN remote_fallback action={} and dispatch to LocalDispatch.

Output download and verification (pbs-remote/src/output_sync.rs): fn sync_outputs(result: &RemoteActionResult, local_cas: &CasStore) -> Result<ActionResult> downloads each OutputFile not already in local CAS, verifies sha256(downloaded_bytes) == OutputFile.digest.hash, and inserts it into local CAS; a mismatch raises RemoteIntegrityError and triggers local re-execution.

Credential + config (pbs-remote/src/config.rs): RemoteConfig { endpoint: Uri, tls: TlsConfig, instance_name: String, max_batch_size: usize, exec_timeout: Duration, cache_only: bool }; cache_only = true uses remote as cache only, never submitting for remote execution — the safe default for untrusted workers.

12.7 Performance Concerns

  • Batch blob uploads: BatchUpdateBlobs amortizes RPC overhead; target 256 blobs / 4 MiB per batch; tune empirically.

Phase 13 — Query Language + Build Daemon

13.1 Objectives

  • Implement pbs-query: a structured query language over target and action graphs supporting deps(), rdeps(), somepath(), allpaths(), kind(), and set operators.

13.7 Performance Concerns

  • rdeps() reverse-index: pre-build during graph construction; O(E) space; do not recompute per query.
  • allpaths() on dense graphs: BFS with visited-set per path is O(V * E); cap path count early.
  • Daemon RwLock read path: query-heavy loads should never contend with each other; use tokio::sync::RwLock which allows concurrent readers.
  • BES serialization: serialize events off the hot action-dispatch path; use a dedicated tokio task with a bounded channel to avoid blocking pbs-exec.
  • Socket framing: length-prefix with u32 avoids repeated read() syscalls; batch small responses.
  • File watcher: notify on macOS uses FSEvents (low overhead); on Linux, inotify; limit watch roots to declared package directories, not entire filesystem.
  • Graph diff on reload: compute BTreeSet symmetric difference of package targets; avoid full graph reconstruction when only one package changed.

Criterion benchmark isolation gives each iteration a fresh temp directory for CAS to avoid cross-iteration state. Hermeticity test overhead (seccomp + clone(CLONE_NEWNS), ~5 ms per sandbox spawn) is acceptable for the test suite but not the production hot path (amortize with process reuse where safe). Tracing Strategy

  • Distributed tracing: every pbs build invocation generates a root trace span with build_id (UUID).
  • Child spans per phase: analysis, action_graph_lower, schedule, per-action execute or cache_lookup.
  • Per-action span attributes: action_key (hex prefix), mnemonic, lang, cache_result, sandbox_type, duration_ms, input_count, output_bytes.
  • Remote spans propagated via W3C traceparent header to remote-execution workers.
  • Trace backend: OpenTelemetry OTLP export; local fallback to Jaeger-format JSON in ~/.pbs/traces/.
  • Sampling: 100% for cache misses; 1% for hits; 100% for errors.

Structured Logging

  • Format: NDJSON; fields: ts (RFC3339), level, build_id, action_key, phase, message, error.
  • Log levels: ERROR for any I3/I4/I6 invariant violation; WARN for remote fallback, GC triggers; INFO for build-start/end, cache-hit summaries; DEBUG for per-action input manifests (gated by --verbose).
  • Build event stream (BES): structured proto events (BuildStarted, ActionExecuted, BuildFinished) written to ~/.pbs/bes/<build_id>.ndjson; optionally uploaded to a BES server (REAPI-compatible).
  • No secrets or env var values in logs; env vars are redacted to <scrubbed> in debug output.

Incident Response

  1. Detection: metric threshold breach or structured log ERROR triggers alert with build_id and action_key.
  2. Triage: identify failure class from F-table above; link to matching runbook.
  3. Containment: for cache poisoning → evict affected action-cache entries; for daemon loop → restart with --no-daemon flag (client mode).
  4. Root cause: inspect BES event stream for build; replay action with pbs explain-action <action_key>.
  5. Recovery: run manual recovery steps from F-table; re-enable remote cache after digest-mismatch audit.
  6. Post-mortem: mandatory for any I1–I10 invariant violation; update threat table and CI hermeticity gate.

Backup / State Management

  • CAS (local): content-addressed store is inherently self-describing; backup is rsync --checksum of CAS directory; restore by copying back (integrity self-verified on read).
  • Action cache: derived data; not backed up; loss forces re-execution (correctness not affected, only performance).
  • Daemon resident state: ephemeral; reconstructed from source files + BUILD files on restart; no backup needed.
  • Build event stream: archived to ~/.pbs/bes/; rotated daily; retained 90 days; optionally mirrored to object store.
  • Remote cache: operated by infra team; CAS blobs are write-once so backup is append-only object store snapshot.

Type / Schema Evolution (Core Types)

  • Digest: { hash: [u8;32], size_bytes: u64 } — frozen; any hash-algorithm migration introduces a new DigestV2 type alongside, not in-place.
  • ActionKey(Digest): frozen composition rule (Phase 5); changing the canonicalization algorithm is a breaking change requiring a major version bump and full cache invalidation.
  • ActionResult: additive proto fields only; output_digests map key (PathBuf) is stable.
  • Provider: typed; new provider kinds are additive; removing a provider kind requires a rule-deprecation notice (see below).
  • Target / RuleClass: new attributes are optional with defaults; removing an attribute requires a 1-release deprecation cycle.
  • CacheEntry on-disk: versioned envelope; reader upgrades old entries in place on first access.

Deprecation Policy

  1. Mark deprecated in release notes and via build-time warning in pbs-loader (e.g., deprecated attribute emits WARN log with deprecated_since and removed_in).
  2. Deprecated surface remains functional for at least 2 minor releases.
  3. Removal only in a major version increment.
  4. Deprecated rule classes emit warnings on every affected target; --strict mode turns warnings into errors.

Semantic Versioning Policy

  • MAJOR.MINOR.PATCH for the pbs binary and all published crates.
  • MAJOR bump: breaking ActionKey canonicalization change (invalidates all caches), breaking BUILD language syntax change, IPC protocol breaking change.
  • MINOR bump: new rule kinds, new query functions, new optional proto fields, new CLI flags.
  • PATCH bump: bug fixes, performance improvements, non-breaking metadata additions.
  • Crate pbs-core version is the schema anchor: every other crate declares a semver-compatible dependency on pbs-core; a MAJOR bump to pbs-core propagates a MAJOR bump to all consumers.

Cross-Reference to Domain Model and Core Types (Sections 8 and 11)

  • Digest type (Section 8 Domain Model) is the universal storage key in CAS; its wire and on-disk encoding is frozen per this section.
  • ActionKey(Digest) (Section 8, Phase 5 contract) stability is the central compatibility guarantee; changing the hash composition is a MAJOR breaking change.
  • Label canonical form (Section 8) is frozen; all query language expressions and BUILD file dep strings resolve through the same parser.
  • Provider type evolution (Section 8) follows additive-only policy; cross-language deps (Phase 10) rely on stable provider interfaces between rule sets.
  • Incremental rebuild correctness (Phase 11, I8) is preserved across MINOR upgrades because the ActionKey computation is unchanged; upgrade only invalidates entries when the MAJOR version changes the key algorithm.

Differential / Conformance Testing (vs. Bazel)

  • Reference implementation: Bazel 7.x, invoked via subprocess in CI on Linux.

  • Scope: output digest equality for actions that both systems execute; not full BUILD language compatibility.
  • Failure mode: digest mismatch triggers a report showing the differing ActionKey inputs for triage.

Determinism / Reproducibility Testing

  • Two clean builds of the same workspace on the same machine; assert every output digest is identical (I1, I2).

Graph Scaling

  • Target graph: adjacency list + interned TargetId(u32); 32-bit ID supports up to 4 × 10⁹ targets (practical ceiling: ~10 M).
  • Action graph: same representation; memory per node: ~256 B (ID + input vec pointer + ActionKey); 500 k actions ≈ 128 MB.
  • Dirty-set propagation: reverse-adjacency BFS; scales O(edges in affected subgraph); 100 k-node graph < 50 ms target.
  • Cycle detection: DFS with gray/black coloring; O(V + E); must complete < 1 s for 1 M-node graph.

Cache Scaling

Layer Scaling approach
Local CAS (disk) size-bounded LRU; evict cold blobs; GC triggered at 90% capacity; single shard
Local action cache (in-memory) LRU eviction; capacity = configurable (default 1 M entries); ~200 B/entry -> 200 MB
Remote CAS horizontally sharded by digest prefix; each shard is stateless; scale-out via consistent hashing
Remote action cache key-value store (e.g. Redis Cluster or Bigtable); scales with replication; PBS client is stateless

Execution Parallelism

  • Worker pool = min(available_cores, --jobs flag); default = logical cores.
  • At 128+ cores: ready-queue must be sharded (16 sub-queues, steal-on-idle) to avoid lock contention.
  • Remote execution: unlimited parallelism model; PBS uploads all ready actions concurrently (bounded by --remote-jobs flag, default 64); back-pressure via semaphore.

File-Watch Scaling

  • inotify / kqueue / ReadDirectoryChangesW; abstracted in pbs-server.
  • Linux: raise fs.inotify.max_user_watches to 1 M for large monorepos; document as operational requirement.
  • Debounce: coalesce events within 50 ms window before triggering incremental rebuild to avoid churn on bulk edits (e.g. git checkout).
  • Alternative for very large trees (> 500 k files): fanotify recursive watch; single fd for entire mount.

Remote Execution Scaling

  • Input root upload: batch with parallel uploads (CAS BatchUpdateBlobs); cap at 4 MB/request per REAPI spec.
  • Deduplication: check remote CAS before upload (FindMissingBlobs); skip already-present blobs.
  • Action result fan-out: CI with 100 parallel builds shares remote action cache; cache hit rate targets > 80% for incremental CI builds on the same branch.
  • Remote worker pool saturation: PBS queues Execute RPCs; REAPI server applies back-pressure via RESOURCE_EXHAUSTED; PBS retries with exponential back-off.

Metadata Scaling

  • Label interning: all Label strings interned in a global string table; reference by u32 offset; avoids per-node string duplication.
  • Provider storage: providers stored outside the action graph (separate arena); action graph nodes hold ProviderSetId(u32) indirection.
  • Build event stream: streaming JSON; no in-memory accumulation; written directly to event log file; supports 1 M+ events per build without buffering.

Coordination Overhead

  • pbs-server is single-process; no distributed coordination for local builds.
  • Remote execution coordination is stateless from the client perspective; the REAPI server handles queueing.
  • Daemon request serialization: each build/test/run request acquires a write lock on the graph; concurrent read-only queries (pbs-query) use read lock; contention becomes measurable at > 10 concurrent clients.
  • Mitigation for multi-client: per-user daemon instances; or upgrade graph lock to an MVCC snapshot model (future work, Phase 14+).

Mental Models & First Principles

MM1. A build is a pure function from source content to artifact content. The expert insight: if you model a build as f(inputs) = outputs where inputs is a set of (path, sha256-hash) pairs, caching is just memoization of f, and distributed caching is just sharing that memo table. What it predicts: any non-determinism in f breaks shared memoization. Bug class without it: developers treat builds as stateful processes and use timestamps or inode numbers as cache keys, producing stale hits when content changes without mtime changes. Applied in: §6 P3 (content addressing), Phase 5 (ActionKey = sha256 of canonical inputs), Phase 7 (CAS write-once).

MM2. The ActionKey is the hash of a hash-of-hashes: a Merkle root over the action. Input digests are themselves hashes; the ActionKey hashes those hashes (plus argv, env, platform). A change anywhere in the input tree bubbles upward. What it predicts: changing a deep transitive source invalidates exactly the ActionKeys that include it, no more. Bug class without it: using file paths instead of content hashes means cache keys collide across branches when files differ but paths match. Applied in: Phase 5 (canon.rs STEP 1–6), §8.4 (ActionKey computation canonical form), Phase 11 (dirty-set propagation reuses the same digest chain).

MM3. The sandbox is a contract, not a filter. The sandbox enforces that an action can only see what it declared. Without this mental model, developers add "extra" inputs "just in case" and the cache key becomes meaningless. What it predicts: an action that reads an undeclared file will silently succeed in dev and fail in CI when the ambient file is absent. Bug class without it: undeclared #include paths that exist on developer machines but not in CI. Applied in: Phase 6 (deny-by-default SandboxSpec), §7 I3 invariant, §6 P1 (Hermeticity).

MM4. Incremental correctness is harder than correctness from scratch. A clean build has one code path; an incremental build has two that must produce identical outputs. What it predicts: every fast-path (mtime skip, dirty-set approximation) is a potential source of silent divergence. Bug class without it: adding an mtime short-circuit that skips content verification → stale incremental results undetected until a clean build is forced. Applied in: Phase 11 (mtime fast-path with content-verify fallback), §7 I8 (incremental equivalence), Phase 14 (clean-vs-incremental digest comparison test).

MM5. Toolchains are inputs, not context. The compiler version, linker, and sysroot are logically inputs to every action they influence. Failing to model them as digested ArtifactRefs makes cache keys non-portable across machines with different ambient toolchains. What it predicts: a compiler upgrade on a CI machine produces different outputs but the same cache key, delivering stale binary artifacts from the old compiler. Bug class without it: implicit $PATH-based toolchain resolution, which is invisible to the cache. Applied in: Phase 9 (Toolchain::digest() injected into ActionKey), §7 I9 invariant, §6 P9.

MM6. The cache hit rate is the build system's health metric. A falling hit rate is a canary for correctness bugs (non-determinism, volatile key material) as much as for performance regression. What it predicts: a hit rate near 0% in CI on unchanged code means ActionKey non-determinism; a hit rate near 100% but wrong outputs means a false hit (I2 violation). Bug class without it: operators focus on wall-time latency and miss systematic cache poisoning. Applied in: Phase 10 observability (§6 P10), Operational Readiness (alert: hit rate < 60% in CI), Phase 14 (fuzz: any mutation → cache miss).

MM7. Remote execution is a trust-but-verify relationship. Remote workers are semi-trusted (see Threat Model boundary). Every downloaded output must be re-verified against its declared digest before entering the local CAS. What it predicts: a compromised or buggy worker produces wrong output that passes the ActionKey check but fails the output-digest check. Bug class without it: accepting remote ActionResult at face value, allowing a malicious server to inject arbitrary artifacts into the local build. Applied in: Phase 12 (output_sync.rs sha256 verify before local CAS insert), §7 I10 invariant, Threat Model T4 and T10.

MM8. Build system design is a tradeoff between scheduling policy and cache soundness. A "suspending" scheduler (dynamic deps) maximizes parallelism; a "topological" scheduler (static deps) maximizes cache soundness. PBS chooses the topological (verifying) scheduler because soundness is non-negotiable. What it predicts: dynamic dep discovery (e.g., gcc -M header scanning) requires a restart or suspending scheduler that PBS explicitly defers. Bug class without it: adding dynamic dep discovery to a topological scheduler produces unsound incremental builds where new deps are not tracked after the first build. Applied in: Phase 8 (topological scheduler design from P1), §1.3 non-goals (no dynamic dep discovery in Phase 1–14), Phase 4 (all deps declared statically).

This wins for small-to-medium teams that want Bazel-class hermeticity without Bazel's operational complexity. Cost: not REAPI-compatible, so it cannot interoperate with the broader Bazel remote cache ecosystem (Buildbarn, EngFlow, BuildBuddy).

All numbers derived step-by-step from the System Constraints table (§4.1). Formulas shown explicitly.

1. Action graph RAM for 500k actions:

Formula: actions × bytes_per_node
= 500,000 × 256 B (ActionKey[40B] + input_vec_ptr[16B] + state[8B] + edge_list_ptr[16B] + padding)
= 128 MB
Constraint reference: §4.1 "Memory — action graph ≤ 500 MB for 500k actions"
Verdict: 128 MB << 500 MB budget; safe with 4× headroom.

Formula: hot_blob_count × avg_blob_size
Target: 256 MB budget (§4.1 "Memory — CAS in-process ≤ 256 MB")
avg_blob_size (header files, .o files): ~16 KB typical
hot_blobs = 256 MB / 16 KB = 16,384 blobs resident
Blobs > 4 MB: streamed directly to disk (§4.1 note); never counted toward this budget.

Formula: SHA-256 throughput / bytes_per_action_canonical_payload
SHA-256 throughput (§4.1): ≥ 2 GB/s (AVX-512 / HWSHA2)
canonical_payload per action: avg 1 KB (100 inputs × 32B digest + 200B argv + 64B env)
actions_per_second = 2 GB/s ÷ 1 KB = 2,000,000 actions/s theoretical
Realistic with overhead: ~200,000 actions/s (10× safety factor for syscalls and allocation)
Constraint: §4.1 "Latency — ActionKey computation < 10 µs per action"
At 10 µs/action: 100,000 actions/s single-threaded; well within range.

Formula: concurrent_actions × avg_output_size × write_throughput_fraction
concurrent_actions = logical_cores = 32 (typical CI machine)
avg_output_size = 500 KB (.o files, .rlib files)
peak_write_rate = 32 × 500 KB = 16 MB/s

Formula: source_directories_to_watch

Alternative Architectures (Roads Not Taken)

Alternative 1: Demand-Driven Incremental Evaluation (Skyframe / DICE model)

  BUILD files
      |
      v
  [SkyFunction registry]
      |
   evaluate(SkyKey)  <---+
      |                  | SkyValue needed?
      v                  | → restart current SkyFunction
  [Memo table]          |   → re-enter when dependency settles
  SkyKey → SkyValue ----+
      |
   changed values propagate dirtying upward

Regime where it wins: large C++ monorepos where header dependency scanning (gcc -M) generates dynamic dep edges not knowable at BUILD-file evaluation time. Skyframe's restartable evaluation handles this naturally; PBS's topological scheduler cannot — it would require a two-phase "scan then build" model. Real system that embodies it: Bazel (Skyframe, production at Google since ~2008) and Buck2 (DICE in Rust). Why PBS rejected it: restartable evaluation requires every SkyFunction to be written as a resumable coroutine that can be interrupted and replayed; this dramatically increases the complexity of every rule implementation. PBS's design principle is that all deps are declared statically (P5), which eliminates the use case that justifies restartability.

Alternative 2: Purely Functional Derivation Store (Nix model)

  .nix expressions
        |
        v
  derivation { name, builder, args, env, src-hashes }
        |
  /nix/store/<hash>-<name>/  (immutable, content-addressed path)
        |
  no incremental: path exists → cache hit; absent → full re-eval
  no action DAG: derivation is atomic

Regime where it wins: system-level software distribution and reproducible OS configuration, where the full closure of every package (including its runtime deps) must be content-addressed and the build graph is a forest of independent derivations rather than a fine-grained action DAG. Real system that embodies it: NixOS/Nix, Guix. Why PBS rejected it: Nix's derivation is coarse-grained (one hash per package, not per source file) and has no incremental model — changing one .c file re-evaluates the entire package derivation. PBS needs per-action granularity for developer feedback-loop latency targets (< 500 ms incremental rebuild for a 1-file change, §4.1).

Alternative 3: Distributed Peer-to-Peer Content Store (IPFS-style)

  CAS nodes (developer workstations + CI machines)
        |     \
        |      \
  [DHT: Digest → peer addresses]
        |
  peer lookup → pull blob from nearest peer
        |
  no central cache server; blobs propagate epidemically

Regime where it wins: large distributed organizations where a central remote cache server is operationally infeasible (no always-on infrastructure, high network partition rate between sites) and blobs are large enough that peer-to-peer locality matters. Real system that embodies it: IPFS (content-addressed peer-to-peer file system); Pijul's content-addressed patch distribution. Why PBS rejected it: DHT lookup adds variable latency (seconds vs. milliseconds for local lookup) and the gossip propagation delay means a freshly built artifact is not immediately available to dependent machines. REAPI's client-server model provides predictable latency and the server can apply eviction policies centrally. The IPFS CIDv1 key format is also incompatible with REAPI's sha256 Digest (see S8 background note).

Alternative 4: Event-Sourced Build Log (Shake model)

  Build DB: log of (key, value, deps) triples
        |
  on rebuild: replay log; re-run key if any dep changed
        |
  "early cutoff": if re-run produces same value, don't propagate dirty upward
  (Shake's key innovation over Make)

Regime where it wins: projects where intermediate results frequently produce identical outputs despite changed inputs (e.g., a code formatter that is idempotent, or a header preprocessor that outputs the same file for minor source edits). Shake's early-cutoff optimization avoids re-running downstream actions even when an upstream action re-executed. Real system that embodies it: Shake build system (Neil Mitchell, Haskell), used in GHC's build system. Why PBS rejected it: early cutoff requires comparing the new output value to the previous stored value after every re-execution, adding an extra CAS lookup and content-hash comparison per action. PBS's verifying rebuilder (P1 taxonomy) achieves the same effect via content-addressed ActionKey: if the output digest is unchanged, downstream actions have unchanged input digests and therefore unchanged ActionKeys — they hit the action cache without re-executing. PBS gets early cutoff semantics for free from the Merkle structure of ActionKeys.

Glossary

Terms are alphabetical. Each definition is implementation-relevant and maps to a specific crate or type in the spine.

Term Definition
Action Atomic build step: { mnemonic, command: Vec<String>, inputs: Vec<ArtifactRef>, outputs: Vec<PathBuf>, env: Map, platform: Digest }. The unit of scheduling, sandboxing, caching, and remote execution in pbs-action.
Action cache Map ActionKey -> ActionResult stored in pbs-cache. A hit means the result of a prior identical action is reused; serves I2 (cache soundness).
Action graph DAG of Actions lowered from the target graph by pbs-graph + pbs-rules; nodes keyed by ActionKey, edges are input/output producer-consumer relationships.
ActionKey sha256(canonicalized(argv + sorted(input digests) + sorted(env) + platform digest + toolchain digest)); the cache key. Computed by pbs-action. Identical inputs across machines produce identical keys (I1).
ActionResult { exit_code, output_digests: Map<PathBuf,Digest>, stdout: Digest, stderr: Digest, metadata }. Stored in the action cache; both local execution and remote execution return this type.
ArtifactRef `{ path, digest: Digest, kind: Source
Attribute Named, typed configuration value on a Target (e.g., srcs, deps, copts). Declared in a rule's attribute schema (RuleClass) and populated at BUILD-file evaluation time.
Bazel Google's open-source hermetic build system (bazelbuild/bazel); primary design reference for PBS. Introduces Skyframe, action graph, sandbox, REAPI client, and remote cache.
BUILD file Declarative package boundary file parsed by pbs-loader; contains rule invocations that instantiate Targets. Analogous to Bazel's BUILD/BUILD.bazel.
CAS (content-addressed store) Key-value store Digest -> bytes in pbs-cache. Write-once, dedup-on-write, integrity-verified on read (I4). Also the backing store for remote execution input/output transfer in pbs-remote.
Configured target A Target evaluated in the context of a specific Platform; distinct targets with the same label but different platforms have different TargetIds and separate action graphs.
Constraint A typed key-value pair that characterizes a Platform (e.g., cpu=x86_64, os=linux). Toolchain resolution matches the set of constraints declared by a target's platform against registered toolchains.
Cross-compilation Building for a target_platform different from the exec_platform on which the build runs. pbs-toolchain resolves separate exec and target toolchains per action.
Cycle detection pbs-graph detects cycles in the target DAG via DFS; reports the full cycle path and aborts. Invariant I5: graph is always a DAG before any action is scheduled.
DAG (directed acyclic graph) The structural requirement for both the target graph and the action graph. Enforced by pbs-graph (I5); enables safe topological scheduling.
Digest { hash: [u8;32], size_bytes: u64 } where hash = sha256(bytes). Universal key throughout PBS: for source files, generated artifacts, Actions, Commands, and toolchain blobs.
Dirty tracking pbs-graph marks a configured target as dirty when any of its input digests change. Only dirty subgraphs are re-lowered and re-scheduled; clean subgraphs reuse cached results (I8).
Eviction (GC) pbs-cache evicts CAS and action-cache entries by LRU when the store exceeds its size bound; live outputs (referenced by the current build) are pinned and exempt.
Genrule A language-agnostic rule that runs an arbitrary shell command; inputs and outputs fully declared. Implemented in pbs-rules; the fallback rule for tools without a native rule set.
Hermetic An action is hermetic when it observes only its declared inputs and a scrubbed, deterministic environment. Enforced by pbs-sandbox (I3, I7). A build is hermetic when all its actions are hermetic.
Incremental build A build that reuses cached ActionResults for actions whose input digests have not changed, executing only the affected subgraph. Implemented via dirty tracking (Phase 11) and the action cache.
Label Canonical target address //package/path:name. Parsed and interned by pbs-core into { repo, package, name }. The unique identifier for a Target before platform configuration.
Mnemonic Short human-readable tag on an Action identifying its kind (e.g., CppCompile, RustLink, Genrule). Used in log output and build event streams; not part of the ActionKey.
Package A directory containing a BUILD file. The unit of visibility and loading in pbs-loader. A Label's package component identifies the package that owns the target.
Platform An immutable set of Constraint values describing an execution or target environment. Represented as its Digest in ActionKey computation. Managed by pbs-toolchain.
Provider Typed data a rule exposes to its dependents (e.g., CcInfo { headers, link_inputs }, RustCrateInfo { rlib, crate_name }). Declared by pbs-rules; flows up the action graph at analysis time.
REAPI Remote Execution API (bazelbuild/remote-apis). Defines gRPC services ContentAddressableStorage and Execution; the wire protocol implemented by pbs-remote for remote cache and remote execution.
Reproducible build A build where identical inputs produce byte-identical outputs, making the output digest stable. Non-determinism in a tool violates P2 and must be treated as a build correctness bug.
Runfiles The runtime file tree assembled for a binary or test target: the binary plus all data dependencies at declared relative paths. pbs-rules assembles a runfiles manifest; pbs-sandbox materializes it.
Rule A named function registered in pbs-rules with an attribute schema (RuleClass); when invoked in a BUILD file it instantiates a Target. Examples: cc_library, rust_binary, genrule.
Sandbox An isolated execution environment created by pbs-sandbox. Input root contains only declared inputs (symlink forest or namespace mount); environment is scrubbed; undeclared file reads are denied or detected.
Spawn strategy The dispatch mechanism for an action: local-sandbox, remote-execution, or no-sandbox (test/debug only). Configured per mnemonic or globally; resolved by pbs-exec at scheduling time.
Starlark Python-dialect configuration language (bazelbuild/starlark) used in BUILD files and .bzl extension files. pbs-loader implements a deterministic subset: no side effects, no unbounded loops, no I/O.
Symlink forest Input-tree materialization strategy: pbs-sandbox creates a temporary directory containing symlinks pointing into the CAS or source tree for each declared input. Faster than copying; revoked after action completes.
Target { label, rule: RuleClass, attrs: Map, deps: Vec<Label>, toolchains: Vec<Label> }. Instantiated by pbs-loader from a BUILD file rule invocation; the node in the target graph.
TargetId(u32) Dense interned integer identity for a configured target inside pbs-graph. Stable for the lifetime of one build graph; regenerated on graph reload. Cheaper than Label for edge storage.
Toolchain { lang, exec_platform, target_platform, tools: Map<String,ArtifactRef> }. Registered in pbs-toolchain; selected per action by constraint matching. Tool digests enter every ActionKey they influence (I9).
Undeclared input A file read by an action that was not in its declared inputs set. Detected/denied by pbs-sandbox; a violation of I3 and P1. A build with undeclared inputs is not hermetic.
Visibility A per-package policy restricting which other packages may depend on a target. Enforced during dependency resolution in pbs-graph; violation aborts analysis with a structured error.
