Back-of-Envelope Capacity Model

All numbers derived step-by-step from the System Constraints table (§4.1). Formulas shown explicitly.

1. Action graph RAM for 500k actions:

Formula: actions × bytes_per_node
= 500,000 × 256 B (ActionKey[40B] + input_vec_ptr[16B] + state[8B] + edge_list_ptr[16B] + padding)
= 128 MB
Constraint reference: §4.1 "Memory — action graph ≤ 500 MB for 500k actions"
Verdict: 128 MB << 500 MB budget; safe with 4× headroom.

2. CAS hot-blob LRU RAM for in-process cache:

Formula: hot_blob_count × avg_blob_size
Target: 256 MB budget (§4.1 "Memory — CAS in-process ≤ 256 MB")
avg_blob_size (header files, .o files): ~16 KB typical
hot_blobs = 256 MB / 16 KB = 16,384 blobs resident
Blobs > 4 MB: streamed directly to disk (§4.1 note); never counted toward this budget.

3. ActionKey computation CPU throughput:

Formula: SHA-256 throughput / bytes_per_action_canonical_payload
SHA-256 throughput (§4.1): ≥ 2 GB/s (AVX-512 / HWSHA2)
canonical_payload per action: avg 1 KB (100 inputs × 32B digest + 200B argv + 64B env)
actions_per_second = 2 GB/s ÷ 1 KB = 2,000,000 actions/s theoretical
Realistic with overhead: ~200,000 actions/s (10× safety factor for syscalls and allocation)
Constraint: §4.1 "Latency — ActionKey computation < 10 µs per action"
At 10 µs/action: 100,000 actions/s single-threaded; well within range.

4. CAS write bandwidth for a large build:

Formula: concurrent_actions × avg_output_size × write_throughput_fraction
concurrent_actions = logical_cores = 32 (typical CI machine)
avg_output_size = 500 KB (.o files, .rlib files)
peak_write_rate = 32 × 500 KB = 16 MB/s
Constraint: §4.1 "Throughput — CAS writes ≥ 500 MB/s local NVMe"
16 MB/s << 500 MB/s; CAS writes are not the bottleneck; scheduling overhead dominates.

5. inotify watch budget for a large monorepo:

Formula: source_directories_to_watch
Large monorepo: 50,000 packages × avg 2 subdirs = 100,000 watch points
Constraint: §4.1 "inotify watches ≤ 64k"
100,000 > 64k: operator must raise fs.inotify.max_user_watches to ≥ 128k for large repos.
Alternative: use fanotify recursive watch (1 fd for entire mount, Scalability Analysis).

6. Remote CAS upload bandwidth for 10k-action build:

Formula: actions_executed × avg_input_root_size × (1 - cache_hit_rate)
cache_hit_rate (warm CI): 0.80 (SLO Definitions)
actions_executed = 10,000
avg_input_root_size = 5 MB (headers + source + toolchain subset)
upload_volume = 10,000 × 5 MB × 0.20 = 10 GB per build invocation
At 1 Gbps LAN: 10 GB / 125 MB/s = 80 s upload time
Optimization: FindMissingBlobs skips already-remote blobs; effective upload ≈ 10-30% of total.
Effective upload: 1–3 GB; ≈ 8–24 s at 1 Gbps LAN.

7. Action cache index size on disk:

Formula: entries × bytes_per_entry
= 1,000,000 (§4.1 "Storage — action cache index ≤ 1 KB per entry") × 1 KB
= 1 GB on disk for 1M entries
LMDB memory-mapped: 1 GB virtual address space; acceptable.

8. File-descriptor budget for daemon:

Formula: inotify_watches + open_CAS_files + socket_connections
inotify fds: 1 fd for the inotify instance (kernel aggregates all watches)
open CAS files (hot fd cache): 256 (Performance Engineering)
socket connections: ≤ 100 concurrent clients (reasonable daemon load)
total: 1 + 256 + 100 = 357 fds << 4,096 (§4.1 daemon fd limit)
Constraint: §4.1 "File descriptors — daemon ≤ 4096 total"

9. Sandbox fd budget per action:

Formula: input_symlinks_fds + output_dirs_fds + stdio_pipes + overhead
Symlinks: 0 fds (symlinks do not consume open file descriptors)
Declared outputs pre-created dirs: ~5 fds during mkdir
stdio pipes: 3 fds (stdin, stdout, stderr)
overhead (sandbox control): ~10 fds
total per sandbox: ~18 fds << 64 (§4.1 per-sandbox limit)

10. Large-graph dirty-set propagation time:

Formula: dirty_edges_traversed × ns_per_edge
Worst case: 1 source file with fan-out 1000 (common leaf library)
edges_traversed = rdeps_of_leaf × avg_rdeps_depth = 1,000 × 5 = 5,000 edge visits
At 20 ns/edge (cache-hot BFS): 5,000 × 20 ns = 100 µs
For 100k-node graph, 1 change: 50 ms target (§4.1); budget = 500,000 edge visits
Constraint: §4.1 "Latency — incremental rebuild (1-file change) < 500 ms end-to-end"
