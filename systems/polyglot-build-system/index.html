In one paragraph

A build system decides which of thousands of compile and link commands must run and which can be skipped. This design, pbs, is a Bazel-class hermetic, content-addressed build system written in Rust (§1.1, ADR-01). BUILD files declare targets in a small Starlark-like language; targets lower to a graph of actions; each action's cache key is the SHA-256 hash of its inputs, command, environment and toolchain (§1.1). Actions run in sandboxes that expose only declared inputs, and their outputs go into a content-addressed store, so a rebuild of unchanged inputs performs zero recompilation (§1.1). It is run by a developer on a workstation, by CI against a remote cache, or as a resident daemon in a monorepo (§1.4).

The problem, concretely

Timestamps or inode numbers used as cache keys give stale hits when content changes without the timestamp changing (MM1). A target that reads /usr/include/openssl/ssl.h without declaring it builds on a developer's machine that has OpenSSL, then silently fails on CI (P1). Two machines that run the same command but get different output leave one of them using wrong results from a shared cache, and the divergence is silent, "harder to debug than a build failure" (P2). Upgrade the compiler without telling the cache and old-compiler objects are served as if they were new (P9, MM5). Put a build directory path into the key and every workspace gets a unique key, so cross-machine sharing collapses to zero hits (P3).

So the system must answer from content alone: what went into this command, did it see anything it did not declare, can a stored result be trusted, and what is the smallest set to re-run (§1.1, P4, P7). A false cache hit is worse than a slow build (P4, §2.3).

How it works, end to end

Follow one C file, src/foo.c, through the boxes of §3.1. The compile command is the blueprint's own worked example (§8.4).

                        POLYGLOT BUILD SYSTEM  (analyze -> execute -> cache)
+------------------------------------------------------------------------------------+
|   BUILD / *.bzl files ---> pbs-loader (config-language eval, rule instantiation)    |
|                                   |  Targets + attrs                                |
|                                   v                                                 |
|   pbs-rules (providers, action generation)   pbs-toolchain (platform/toolchain     |
|                                   |           resolution per action)                |
|                                   v                  |                              |
|   pbs-graph: TARGET DAG --lower--> ACTION DAG <-------+                              |
|                                   |   (deps, cycle detect, dirty tracking)          |
|                                   v                                                 |
|   pbs-action: ActionKey = sha256(argv + sorted(input digests) + env + platform + tc)|
|                                   |                                                 |
|              cache miss           v             cache hit                           |
|        +--------------------------+--------------------------+                      |
|        v                                                     v                      |
|   pbs-exec (schedule ready actions, bounded parallelism)   pbs-cache lookup          |
|        |                                                     ^                      |
|        v  local                          remote             |                       |
|   pbs-sandbox (materialize inputs,    pbs-remote (REAPI:     |                       |
|    hermetic run, capture outputs)      Execute / CAS)        |                       |
|        |                                   |                 |                       |
|        v                                   v                 |                       |
|   pbs-cache: CAS { digest -> bytes } + ACTION CACHE { ActionKey -> ActionResult } ---+
|        ^                                                                             |
|        |  pbs-query (deps/rdeps/somepath)     pbs-server (daemon: watch, resident)   |
|        +------------------------------------- pbs-cli (build/test/run/query)         |
+------------------------------------------------------------------------------------+
  1. pbs-loader reads BUILD and .bzl files and evaluates rule() calls into Target values; packages evaluate concurrently, each deterministically, with no I/O (§3.2, T1).
  2. pbs-graph resolves each dependency label to a target, checks visibility, detects cycles and builds the target DAG, then lowers it to the action DAG (§3.2, §8.6).
  3. pbs-rules runs the rule implementation for each target. It takes the providers of the dependencies (for C: CcInfo with headers, link flags, static libs) and emits new providers plus a list of Actions (§3.2, §8.7). Every language reduces to the same Action, so nothing downstream knows about C or Rust (P6).
  4. pbs-toolchain picks the toolchain by (lang, exec_platform, target_platform). The compiler binary is an ArtifactRef with a digest, and that digest enters every key it affects (§3.2, P9).
  5. pbs-action turns the action into its ActionKey (§3.2, §8.4). In the worked example the inputs are src/foo.c, foo/include/foo.h and tools/clang, the env is CC_FLAGS=-Wall, and the toolchain is clang-14.0.0 (§8.4).
  6. pbs-exec dispatches ready actions to a bounded tokio + rayon worker pool and checks pbs-cache first; on a hit the outputs are marked available at once (§3.2, ADR-04, ADR-05).
  7. On a miss pbs-sandbox runs the action locally, or pbs-remote runs it on a REAPI server and falls back to local on RPC failure. pbs-cache stores outputs in the CAS (Digest -> bytes) and the result in the action cache (ActionKey -> ActionResult) (§3.2, §8.8, §8.9).
  8. pbs-query answers deps/rdeps/somepath/allpaths/kind over the graph without executing anything; pbs-server keeps the graph resident and watches files; pbs-cli is the entry point that talks to the daemon or spawns a one-shot build (§3.2, I11, I12).

The core ideas

The action key: one fingerprint of everything that matters (§8.4, P3)

A content-addressed key means the name of a result is a hash of what produced it. The ActionKey is a SHA-256 over five parts in this order: argv as NUL-separated bytes; input (path, digest) pairs sorted by path; env pairs sorted by key with volatile variables removed; the platform digest; the toolchain digest (§8.4). A Digest is a 32-byte SHA-256 plus the byte size (§8.2), and §4.1 sizes an ActionKey at 40 bytes (§4.1). The three-build trace shows why the env rule matters:

Build Env difference Key Why (§8.4)
1 HOME=/home/alice, scrubbed K volatile variable removed
2 HOME=/home/bob, scrubbed K (identical) same result served from cache, I7 upheld
3 CC_REVISION=gitsha, not on the volatile list K' re-execution; fix by extending the list or declaring it in attrs

The default volatile list in §8.4 has HOME, USER, TMPDIR, PWD, SHELL, RANDOM and others; Phase 5's acceptance test names "all 17 default volatile vars". Invariant I7's lint lists a shorter set (HOME, USER, TMPDIR, TMP, TEMP, RANDOM, and LANG unless declared), and LANG does not appear in §8.4's list (§7 I7 versus §8.4). I7 also says only explicitly declared variables enter the key and T6 calls the rule an allowlist, while §8.4 removes listed variables and lets the undeclared CC_REVISION change the key (I7; T6; §8.4).

The sandbox: an action sees only what it declared (§8.10, I3, MM3)

The sequence: create a sandbox root; for each declared input make a symlink in inputs/ pointing at the CAS or workspace file (a symlink forest); pre-create output directories; set the scrubbed env; execve with cwd inside the input tree; collect each declared output; digest it and store it; deny reads outside inputs/ (§8.10). On Linux the isolation is namespaces (mount, PID, network, IPC); on macOS it is a sandbox-exec profile, which the blueprint itself calls "less strict" (ADR-20, ADR-21).

Outputs are checked too (I6). A missing declared output fails the action with MissingOutputError; an undeclared file written to outputs/ is ignored with a warning; an empty output file is valid (§8.10). The blueprint disagrees with itself twice here. I3 says an undeclared read gives EACCES/EPERM (§7 I3), while Phase 6's Linux test expects ENOENT (Phase 6 acceptance criteria). And pbs-sandbox "never touches the CAS directly" (§3.2), yet step 7 of §8.10 stores each output in the CAS.

The two-layer cache: bytes by hash, results by key (§8.8, §8.9, I2, I4)

The CAS is a directory tree sharded by the first two hex characters of the hash, holding <full_hex>_<size> files (§8.8, ADR-07). A write goes to tmp/, is verified against the claimed digest, then renamed into place, which is atomic on POSIX and harmless if the file already exists. A read streams bytes through a hasher; on a mismatch the file is deleted and IntegrityError is returned (§8.8, I4). The action cache is a separate LMDB table, ActionKey -> ActionResult, where a result holds exit code, a path-to-digest map of outputs, and stdout/stderr digests (§8.9, ADR-08).

Lookup recomputes the key from the action fields and asserts it equals the stored key before serving a hit (§8.9, I2). Eviction starts when the store passes a high-water mark (default 10 GB), removes least-recently-used blobs not in the pin set, and the pin set is every digest referenced by a live ActionResult (§8.8, §4.1, P4). Phase 7 proves two cases: a bit-flip in a stored blob gives CasError::Corrupt on the next read, and two puts of identical bytes make one file (Phase 7 acceptance criteria).

The action state machine: one lifecycle for every language (§8.5, P8)

Every action moves through the same states. PENDING becomes READY when all input actions are DONE; the scheduler dequeues it to DISPATCHED, which takes a worker slot and queries the cache. A hit goes to CACHE_HIT and then DONE once outputs are materialised from the CAS. A miss goes to EXECUTING (sandbox or remote), which ends in DONE (exit code 0 and all declared outputs captured), FAILED (non-zero exit, missing output, or integrity error), or RETRYING for a transient error such as OOM or a remote timeout (§8.5). A FAILED action marks all reverse dependencies failed and aborts the build, or with --keep-going continues independent subgraphs (§8.5, §8.15). Worker count is min(available_parallelism, --jobs) so a 10,000-action graph cannot exhaust file descriptors or RAM (P8).

Retries are stated inconsistently: retry_count < max_retries (§8.5), "≤ 1 retry per transient sandbox failure" (§4.1), "up to 3 retries" (Phase 8 acceptance criteria). F2 retries a missing output once, while §8.5 sends a missing output straight to FAILED (F2; §8.5).

Incremental rebuild: mark what changed, reuse the rest (§8.12, I8, P7)

For each source whose digest differs from the previous snapshot, mark it dirty and walk up the reverse dependencies, skipping nodes already dirty (§8.12). Clean actions are served from the action cache; a dirty action gets a new ActionKey if any input digest changed, and the old entry stays in case inputs revert (§8.12). A compiler swap changes every key that included the toolchain digest, so the affected language subgraph rebuilds fully (§8.12, I9). The capacity model's worst case is a leaf library with fan-out 1,000 and average depth 5: 5,000 edge visits at 20 ns each, 100 µs (Back-of-Envelope Capacity Model, item 10).

A mtime fast-path skips re-hashing a file whose modification time is unchanged, overridable with --no-mtime-shortcut (§8.12). The blueprint is not of one mind about it. §8.12 tests mtime alone, while P3 skips only when mtime and size are both unchanged (§8.12; P3); P4 says there are "no time-based or inode-based shortcuts" for validity (P4); MM4 calls every fast path, the mtime skip included, a potential source of silent divergence and pairs it with a content-verify fallback (MM4); F11 lists the mtime-only fast-path as a cause of incremental failure (F11). An action that re-runs but produces an identical output needs no special case: unchanged output digests mean unchanged downstream keys, which the blueprint calls early cutoff for free (Alternative Architectures, Alternative 4).

Remote cache and execution: trust, but verify (§8.11, I10, MM7)

Remote workers are semi-trusted (Threat Model, trust boundaries). The message flow follows REAPI (§8.11): FindMissingBlobs asks which input blobs the server lacks; BatchUpdateBlobs uploads only those; Execute starts the action; WaitExecution polls until the operation is done; BatchReadBlobs downloads the outputs. The input tree is a Merkle structure of Directory nodes: the same tree gives the same root digest, and only missing blobs are uploaded (§8.11). Every downloaded output is re-hashed against the digests in the ActionResult; a mismatch raises RemoteLocalMismatch, the remote result is discarded, and the action runs locally (§7 I10, MM7). If the remote is unreachable the build falls back to local execution rather than failing (§2.4, F5).

The trade-offs — where engineers disagree

Hash function: SHA-256 (ADR-06)

Chosen: SHA-256 via the ring crate, because REAPI mandates it and it interoperates with Bazel remote caches (ADR-06). Rejected: BLAKE3, SHA-512, MD5. When the rejected choice is right: BLAKE3, in a standalone build system with no need for compatibility with external caches and a priority on hashing throughput; SHA-512 in FIPS environments needing the stronger standard (ADR-06).

On-disk CAS: a flat file tree, not a database (ADR-07)

Chosen: files sharded by two-character hex prefix with atomic rename-into-place. It is the simplest crash-safe write, has no database lock contention, and is easy to inspect (ADR-07). Rejected: SQLite blob store, RocksDB, object storage. When the rejected choice is right: RocksDB, when the CAS must support range scans or metadata queries such as per-blob timestamps for GC at high throughput; SQLite for single-file portability on Windows or network-mounted shares (ADR-07).

Config language: a Starlark-like subset (ADR-10)

Chosen: a custom Starlark-like evaluator, because Starlark is deterministic, hermetic and sandboxed by design: no I/O, no side effects, familiar Bazel syntax (ADR-10, T1). Rejected: full Python, Lua, TOML, Jsonnet. When the rejected choice is right: full Python when BUILD files must import existing utility libraries (the blueprint's example is a legacy Pants v1 migration); TOML for simpler projects that need only declarative rule invocations and no macro language (ADR-10).

Linux sandbox: namespaces, not containers (ADR-20)

Chosen: unshared mount, PID, network and IPC namespaces via the nix crate. They are fast (no container startup), light, give full input-root isolation (I3) and need no Docker daemon (ADR-20). Rejected: Docker-per-action, Bubblewrap, gVisor. When the rejected choice is right: Docker-per-action when actions need a complete OCI image with system libraries that cannot be declared as ArtifactRef inputs; gVisor in untrusted multi-tenant execution where kernel-exploit risk calls for a second isolation layer (ADR-20).

Remote protocol: REAPI over gRPC (ADR-22)

Chosen: REAPI over tonic gRPC. It is the industry standard and works with Buildbarn, Buildgrid and EngFlow caches (ADR-22). Rejected: custom REST, NATS, Redis queues. When the rejected choice is right: custom REST for a single-team deployment where REAPI's proto complexity is not justified; NATS when the execution cluster needs pub/sub fan-out to worker pools instead of request/response dispatch (ADR-22).

Roads not taken

Demand-driven evaluation, as in Skyframe and DICE (Alternative 1): a function restarts when a dependency is not ready. It wins for large C++ monorepos whose header scanning (gcc -M) creates edges unknown at BUILD-evaluation time. Rejected: every rule would become a resumable coroutine, and pbs declares all dependencies statically (P5).

A purely functional derivation store, as in Nix (Alternative 2): one hash per package, no incremental model. It wins for system-level software distribution and reproducible OS configuration. Rejected: pbs needs per-action granularity for the under-500 ms one-file rebuild (§4.1).

A peer-to-peer content store, as in IPFS (Alternative 3): no central cache server. It wins where an always-on cache server is operationally infeasible. Rejected: variable lookup latency, gossip delay, and a key format incompatible with REAPI's SHA-256 digest.

An event-sourced build log with early cutoff, as in Shake (Alternative 4): it wins when intermediate results often come out identical despite changed inputs. Rejected: content-addressed keys already give the same effect.

The deferred register: remote execution waits for Phase 12; daemon, file watching and queries for Phase 13; conformance suite, fuzzer, large-graph benchmark and pbs pack for Phase 14 (Deferred Features Register, §1.8). The non-goals include a distributed scheduler, container image builds, first-class Windows and dependency-version solving (§1.3).

What must never be false

  • I1 identical ActionKey implies identical ActionResult. Noticed by the Phase 14 reproducibility test, which emits a DETERMINISM_FAILURE event on divergence (§7 I1).
  • I2 a hit is served only when the recomputed key matches exactly. A served result whose output digests fail re-verification raises CACHE_SOUNDNESS_VIOLATION; counters cache.hit, cache.miss, cache.soundness_violation (§7 I2).
  • I3 an action that reads an undeclared file fails in the sandbox with UndeclaredInputRead(path); metric sandbox.undeclared_read (§7 I3).
  • I4 every CAS blob satisfies sha256(bytes) == key. A read-time mismatch raises CasIntegrityError; counters cas.integrity_error, cas.read_ok (§7 I4).
  • I5 both graphs are DAGs. A cycle returns CycleError { path } and aborts before execution; event graph.cycle_detected (§7 I5).
  • I6 a successful action produces exactly its declared outputs. A missing one raises MissingOutput; metric sandbox.missing_output (§7 I6).
  • I7 the action environment is a deterministic function of the action. A lint rejects volatile variables; action.scrubbed_env_var is emitted per scrubbed variable (§7 I7).
  • I8 an incremental build equals a clean build of the same final inputs. The Phase 14 equivalence test compares digests; build.incremental_equivalence pass/fail (§7 I8).
  • I9 toolchain tool digests are part of every key they influence. A zero or missing digest returns ToolchainDigestMissing; metric toolchain.digest_missing (§7 I9).
  • I10 remote and local execution give the same result. A digest mismatch after download raises RemoteLocalMismatch; counters remote.local_mismatch, remote.verified_ok (§7 I10).
  • I11 a query or status request never executes an action or mutates graph state. A handler-boundary test asserts zero dispatches; query.mutating_attempt_blocked stays 0 (§7 I11).
  • I12 at most one writer holds the daemon's RwLock. A concurrency test asserts the second writer blocks; daemon.concurrent_writer_attempts stays 0 (§7 I12, P12).

What breaks in production

The blueprint numbers its failure modes F1 to F15 (Failure Modes & Recovery).

  • F3: a CAS blob is corrupt. Symptom: builds fail with digest_mismatch and the action re-executes repeatedly. Cause: bit-rot, a truncated write or a concurrent writer. Detection: SHA-256 check on every CAS read (I4). Recovery: evict the entry and re-execute; the operator runs pbs cache verify and checks disk health (F3).
  • F4: the sandbox silently does not isolate. Symptom: an undeclared read succeeds. Cause: no namespace or seccomp support. Detection: a startup self-test reads an out-of-tree file and expects EPERM. Recovery: automatic downgrade to best-effort isolation with a warning; long term, require a supported platform and "fail hard" (F4).
  • F5: the remote cache is unavailable. Symptom: every action runs locally; slow but no failure. Cause: a partition or a down server. Detection: timeout counter and the pbs-remote circuit breaker (3 consecutive failures, §4.1). Recovery: automatic local fallback; restore the remote and re-warm the cache (F5).
  • F6: a remote result has the wrong digest. Symptom: an integrity error after remote execution. Cause: a compromised worker or network corruption. Detection: digest verification on every downloaded blob. Recovery: discard the remote result, re-execute locally, quarantine the worker (F6, T10).
  • F7: the action key is unstable. Symptom: every build re-executes and the hit rate is near zero. Cause: a volatile variable leaking into the key, or a timestamp in the command. Detection: the hit-rate metric drops and key deltas are logged at DEBUG. Recovery: find the variable with pbs explain-key; a CI gate compares keys across two identical builds (F7, T6).
  • F11: incremental output differs from clean output. Symptom: a violation of I8. Cause: a missed invalidation. Detection: a CI job diffs clean and incremental output digests. Recovery: conservative invalidation, pbs build --no-cache, or content-hash verification instead of the mtime fast-path (F11).

Threats a reader should know (Threat Model): T1 a malicious BUILD file, answered by a config language with no exec and no I/O APIs, enforced at parse time. T4 cache poisoning through the remote, answered by re-verifying digests on every CAS download and optional HMAC signing of ActionResults. T7 a symlink pointing out of the sandbox, refused at forest construction. T13 privilege escalation out of the namespace sandbox, answered by dropping capabilities and running unprivileged. T14 a tampered compiler, which changes the toolchain digest and so the key, forcing a cache miss (I9, P9).

How it compares

  • Bazel chose Skyframe's restartable, demand-driven evaluation so dynamic dependencies such as header scanning work without declaring every edge. That fits large C++ monorepos, at the cost of a hard-to-reason-about restart protocol (Comparative Architecture Table).
  • Buck2 chose DICE, a demand-driven incremental graph in Rust, for Meta's scale; it is harder to implement correctly than a topological scheduler (Comparative Architecture Table).
  • Nix chose purely functional derivations with no incremental model. That is fine for reproducible system configuration where correctness beats speed (Comparative Architecture Table).
  • Pants v2 chose a Python rule language over a demand-driven Rust async engine. That suits large Python codebases, at the cost of harder static analysis (Comparative Architecture Table).
  • Please chose a smaller feature set, a simpler sandbox and an HTTP remote cache, which fits small teams wanting Bazel-class hermeticity; it is not REAPI-compatible (Comparative Architecture Table).

The blueprint places pbs inconsistently: §2.2 says the "suspending, constructive" cell, while MM8 and the comparative table say verifying and topological, with suspending scheduling deferred (§2.2; MM8; Comparative Architecture Table).

Questions to test yourself

  1. An action's ActionKey is identical across two machines, but the output digests differ after execution. Enumerate every possible root cause, ordered by likelihood, and describe the exact telemetry signal each one would produce. — Hint: §7 I1 and the list of what enters the key in §8.4; compare F7 and T6.
  2. How does pbs guarantee that pbs build //foo:bar on machine A and machine B (different kernel versions, different hostnames) produce byte-identical output digests for the same source tree? Identify every system component that contributes to this guarantee and every component that could silently break it. — Hint: I7 and I9 in §7, the env scrub in §8.4, and the toolchain digest in P9.
  3. Explain why the pbs sandbox uses a symlink forest rather than hard links or copies as the default materialization strategy, and describe the exact conditions under which each alternative would be preferred. — Hint: §8.10 and the Glossary entry for symlink forest.
  4. A new team member proposes adding a cache_bust = True attribute to cc_binary that forces re-execution regardless of ActionKey. Evaluate the proposal against every relevant design principle and invariant, and propose an alternative that achieves the stated goal without architectural compromise. — Hint: P4 in §6, I1 and I2 in §7, and the key definition in §8.4.
  5. Explain how the pbs provider model enforces the boundary between analysis time (no I/O) and execution time (sandboxed), and describe what would happen if a rule implementation called std::fs::read directly instead of declaring a source as an ArtifactRef input. — Hint: pbs-rules in §3.2, §8.7, P1, P5 and I3.

If you only remember three things

A build is a pure function from content to content, so the cache key is a hash of everything that went into the action and sharing a cache is just sharing a memo table (MM1, MM2, P3). The sandbox is a contract, not a filter: an action that touches an undeclared file must fail, or the key stops meaning anything (MM3, I3). Correctness beats speed everywhere, so every fast path, whether a local hit, an mtime skip or a remote result, is re-verified before it is trusted (P4, MM4, MM7).

Words used here

  • Action: one atomic build step with command, inputs, outputs, env and platform; the unit that is scheduled, sandboxed, cached and sent to a remote (Glossary, Action).
  • ActionKey: the SHA-256 over argv, sorted input digests, sorted env, platform and toolchain; the cache key (Glossary, ActionKey).
  • CAS (content-addressed store): a write-once Digest -> bytes store, verified on read (I4).
  • Digest: a 32-byte SHA-256 plus the size in bytes; the universal key (§8.2).
  • Hermetic: sees only declared inputs and a scrubbed, deterministic environment (Glossary, Hermetic; I3, I7).
  • REAPI: the remote execution API, a gRPC protocol for cache and remote runs (§8.11, ADR-22).
