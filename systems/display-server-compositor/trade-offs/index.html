Each card is one row of the blueprint's decision table: what was locked in, what was rejected, and — the column that matters most — the situation in which the rejected choice is the right one.

Decisions (§9) · 31 ADRs

1

Implementation language

Chosen

Rust (2021, MSRV pinned)

Rejected

C (wlroots/Weston), C++ (KWin), Go, Zig

When the rejected choice is right

C wins when linking directly into a kernel-mode driver or when the entire team is C-fluent and the project timeline forbids a language migration; C++ wins for compositors already deep in Qt/KDE infrastructure (KWin).

Why: object-graph lifetime safety + clean FFI to hw libs (§1.9)

2

Build / workspace

Chosen

Cargo multi-crate workspace

Rejected

single crate; CMake/meson

When the rejected choice is right

Single-crate wins for a throwaway prototype where cross-crate compile times outweigh isolation; CMake/meson win when the compositor must build alongside C libraries in a unified distro build system (e.g. a Yocto layer).

Why: crate-per-subsystem matches §10; meson is the C-world tool

3

Wire protocol

Chosen

re-implemented from wayland.xml

Rejected

link libwayland

When the rejected choice is right

Linking libwayland wins in a thin wrapper or a quick-port scenario where developer time is scarce and protocol correctness is more important than understanding the wire internals — e.g. a one-off Wayland proxy.

Why: "from scratch"; full control of the security-critical decoder

4

Protocol bindings

Chosen

build-time scanner (XML→Rust) codegen

Rejected

hand-written opcode tables; runtime parse

When the rejected choice is right

Hand-written tables win when there are only 2–3 interfaces and the XML parsing machinery is heavier than the tables themselves; runtime parse wins in an extension-loading plugin system where new protocols arrive post-compile.

Why: single source of truth (the XML), no opcode drift (I13)

5

Event loop

Chosen

self-rolled epoll reactor (calloop-style)

Rejected

tokio/async; glib mainloop

When the rejected choice is right

tokio/async wins when the compositor is embedded in a larger async service (e.g. a desktop daemon that also serves D-Bus) and the existing async executor already manages fds with known latency; glib wins in a GNOME-native compositor that must integrate GObject signals.

Why: single-thread, no async runtime in the latency path; explicit fd sources

6

Concurrency model

Chosen

single-threaded dispatch; worker pool for render/decode only

Rejected

threaded protocol dispatch

When the rejected choice is right

Threaded dispatch wins at extreme client counts (thousands of simultaneous sessions on a multi-seat kiosk server) where per-client latency can be isolated per thread and the frame budget is not a constraint (e.g. a headless Wayland test harness).

Why: lock-free object graph (I11); GC/lock pauses blow the frame budget

7

KMS API

Chosen

atomic modeset only (steady state)

Rejected

legacy drmModeSetCrtc/PageFlip

When the rejected choice is right

Legacy API wins on hardware predating atomic KMS (pre-2016 embedded SoCs, Raspberry Pi 3 BSP kernels) where the driver never gained atomic support and a legacy page-flip is the only available tear-free path.

Why: tear-free, multi-plane, TEST_ONLY validation (I15); legacy is fallback-probe only

8

Buffer allocation

Chosen

GBM for scanout; dmabuf import for clients; shm mmap

Rejected

TTM directly; custom alloc

When the rejected choice is right

TTM directly wins on AMD/Radeon hardware using RadeonSI where a compositor controls the full GPU stack and wants finer-grained BO placement and tiling; custom alloc wins on a fixed embedded SoC with a proprietary allocator that has no GBM driver.

Why: GBM/dmabuf is the standard zero-copy path (§19)

9

GPU rendering

Chosen

EGL + OpenGL ES 2.0

Rejected

Vulkan (deferred — Deferred Features Register); GL desktop

When the rejected choice is right

Vulkan wins when the compositor must drive HDR/wide-gamut color pipelines with ICC profiles, blend in a linear light space, or exploit explicit sync timeline semaphores for minimal GPU–CPU synchronization latency (see Deferred Features Register, Explicit sync row).

Why: GLES2 is the wlroots-proven minimum; Vulkan is a later renderer

10

Software fallback renderer

Chosen

CPU coverage/blend (reuse #169)

Rejected

pixman FFI; skip software

When the rejected choice is right

pixman FFI wins when production deployment includes ARM SoCs that ship a highly-tuned NEON-accelerated pixman build and the compositor's pixel throughput is dominated by blending large surfaces rather than the call overhead of FFI.

Why: headless/CI + no-GPU support; #169 is our own kernel

11

Input

Chosen

libinput + libudev (FFI)

Rejected

raw evdev hand-rolled

When the rejected choice is right

Raw evdev wins on a kiosk or embedded device with a single, known input device where libinput's device database and pointer-acceleration logic are unwanted overhead and the device's event layout is fixed and tested.

Why: acceleration/gestures/quirks are libinput's job; evdev directly is a tarpit

12

Keymaps

Chosen

xkbcommon (FFI), shared to clients as fd

Rejected

hand-rolled keymap

When the rejected choice is right

A hand-rolled keymap wins on a single-language embedded UI with a fixed 104-key QWERTY layout where the xkb rule database (several MB) is too large for the rootfs and no locale switching is ever needed.

Why: xkb is the de-facto standard; clients expect the keymap-fd contract

13

Session / privilege

Chosen

libseat (logind/seatd backend)

Rejected

suid-root; direct logind DBus

When the rejected choice is right

suid-root wins on a minimal embedded Linux image that has no D-Bus, no systemd, no logind, and no seatd — the only way to open /dev/dri/card0 and /dev/input/event* without a session manager.

Why: DRM master + input fds without root; VT-switch handling (§23, Phase 11)

14

fd passing

Chosen

sendmsg/recvmsg + SCM_RIGHTS, owned fd ring

Rejected

(none — protocol-mandated)

When the rejected choice is right

No alternative wins here — SCM_RIGHTS is the only POSIX mechanism for passing open file descriptors across Unix-domain socket boundaries; the Wayland protocol mandates it for wl_shm pools, keymaps, and dmabuf fds.

Why: the only mechanism; ownership tracked (I12)

15

Serialization (protocol)

Chosen

bespoke wire codec (§8.1)

Rejected

serde/protobuf

When the rejected choice is right

serde/protobuf wins for an extension or portal protocol layered on top of the socket — e.g. a compositor-to-compositor sync protocol or an IPC channel between the compositor and a privileged helper that is free to choose its own wire format.

Why: the wire format is fixed by the spec, not ours to choose

16

Async fence / sync

Chosen

implicit sync (dmabuf fences) first

Rejected

explicit drm_syncobj (deferred — Deferred Features Register)

When the rejected choice is right

Explicit drm_syncobj wins when the GPU workload is deeply pipelined (multiple in-flight frames, a dedicated render thread, and a dedicated scan-out thread) and over-synchronization from implicit fences is measurably costing frame latency — common on high-refresh-rate (144 Hz+) gaming compositors.

Why: implicit is simpler + universal; explicit is a later optimization

17

Logging / tracing

Chosen

tracing + spans on the repaint cycle

Rejected

log; printf

When the rejected choice is right

log + printf wins during early prototyping on a microcontroller or bare-metal environment where the tracing subscriber infrastructure is too heavy and the only output channel is a UART.

Why: latency forensics need structured spans (§14, principle 14)

18

Metrics

Chosen

in-proc counters + optional Prometheus exporter in CLI

Rejected

StatsD; none

When the rejected choice is right

StatsD wins in an ops infrastructure that already runs a StatsD → Graphite → Grafana pipeline and adding a Prometheus scrape endpoint requires a firewall exception or an incompatible monitoring agent.

Why: per-frame/latency histograms (§28)

19

Config

Chosen

TOML config + env overrides

Rejected

hard-coded; CLI-only

When the rejected choice is right

Hard-coded config wins on a dedicated single-purpose appliance (an ATM, a digital-signage kiosk, a car headunit) where the display + input + locale are fixed at manufacturing time and a mutable config file is an attack surface.

Why: outputs/scale/keymap/caps are deployment-specific

20

Testing

Chosen

cargo test + Weston test clients + headless golden images

Rejected

manual only

When the rejected choice is right

Manual-only testing wins in a rapid hardware-bring-up phase where the headless backend is not yet functional and the only way to observe compositor behavior is a live display — e.g., the first days of a new SoC port.

Why: the libwayland-client differential is the oracle (§30)

21

Fuzzing

Chosen

cargo-fuzz on the wire decoder + protocol state

Rejected

none

When the rejected choice is right

Skipping fuzzing wins only in a closed-network embedded appliance with no untrusted clients where the socket is never exposed to attacker-controlled input and the resource cost of running a fuzzer exceeds the threat model.

Why: the decoder is the trust boundary (§26)

22

CI backend

Chosen

headless backend + virtual GPU (llvmpipe)

Rejected

require real GPU

When the rejected choice is right

Requiring real GPU wins in a CI system running on physical machines (e.g. a Raspberry Pi cluster) where llvmpipe rendering diverges from hardware output in driver-specific ways that matter for the golden tests (e.g. DRM format modifier differences).

Why: hardware-free CI; on-hw is a separate manual lane

23

Color / blending

Chosen

premultiplied alpha, Porter–Duff over

Rejected

straight alpha

When the rejected choice is right

Straight alpha wins when all clients produce straight-alpha images (e.g. a legacy pipeline from a raster editor that never premultiplies) and the pre/un-multiply conversion at import/export costs more bandwidth than the blending savings.

Why: the compositing standard; premultiplied avoids fringing

24

Coordinate / sub-pixel

Chosen

wl_fixed 24.8; integer surface-local + scale

Rejected

float everywhere

When the rejected choice is right

Float everywhere wins in a pure-GPU compositing path where surface coordinates are transformed by a hardware matrix unit that natively operates in float and sub-pixel accuracy is maintained by the GPU (e.g. a game engine embedding a Wayland compositor).

Why: matches the wire type; deterministic hit-testing

25

Damage representation

Chosen

rectangle list / simple region (union, intersect)

Rejected

per-pixel mask; full-screen always

When the rejected choice is right

Per-pixel mask wins when surfaces frequently update sparse, non-rectangular regions (e.g. a terminal with cursor blink + scrollback simultaneously) where a rectangle list degenerates to hundreds of small rects but a pixel mask could scissor at sub-scanline granularity.

Why: bounded, cheap, scissor-friendly (I10)

26

Determinism mode

Chosen

XRCOMP_DETERMINISTIC (fixed clock, no real input) for tests/replay

Rejected

none

When the rejected choice is right

Omitting the determinism mode wins when the compositor is exclusively deployed on hardware where the only test path is live on-device, the golden-image CI infra is too costly to maintain, and fuzzing replaces regression testing.

Why: golden-image + event-replay reproducibility

27

Packaging

Chosen

static-ish binary + .so lib + config; systemd-friendly

Rejected

container-only

When the rejected choice is right

Container-only packaging wins for a cloud Wayland compositor (a headless remote-rendering server) where the compositor runs inside a container with a virtual GPU, there is no TTY or seat, and the host cgroup + namespace isolation replaces libseat privilege management.

Why: a compositor runs on a TTY/seat, not in a container, normally

28

License

Chosen

Apache-2.0 (clean-room from protocol XML + papers)

Rejected

GPL (copying Weston)

When the rejected choice is right

GPL wins when the compositor is a direct derivative of Weston or wlroots (code copied, not re-derived) and the shipping product is open-source — GPL is the upstream license and Apache-2.0 would require a full clean-room rewrite to be license-compatible.

Why: clean-room; no GPL contamination (§31)

29

Repo reproducibility

Chosen

pinned rust-toolchain.toml + Cargo.lock + pinned hw-lib versions

Rejected

floating

When the rejected choice is right

Floating deps win in an active research prototype where tracking upstream Mesa/libinput/libseat HEAD is the goal (to catch regressions against new driver versions) and build reproducibility is intentionally sacrificed for staying current with driver APIs.

Why: reproducible builds (§31)

30

Scene model

Chosen

retained scene graph (nodes) + damage

Rejected

immediate-mode repaint

When the rejected choice is right

Immediate-mode repaint wins on a single-surface fullscreen compositor (a game console, a kiosk) where there is exactly one client surface that changes every frame: damage tracking has zero benefit, and the retained graph's overhead (node walk, damage accumulation) is pure waste.

Why: enables partial repaint + direct scanout decisions (I10, §19)

31

Cursor

Chosen

hardware cursor plane when available, else composited

Rejected

always composited

When the rejected choice is right

Always-compositing the cursor wins when the hardware cursor plane has severe limitations (e.g. a maximum size of 64×64 at 1× but a 128-pixel HiDPI cursor is required, or the plane does not support ARGB8888 + alpha blending) and the composited cursor must match OS-level theming with full alpha.

Why: latency/power; hw cursor moves without a repaint

Roads not taken (§38)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

A. Monolithic compositor-WM (X.org / KWin model)

┌─────────────────────────────────────────────────────────┐
│  Monolithic server: window management + compositor +     │
│  input routing + protocol all in one process             │
│  ┌─────────────┐  ┌──────────────┐  ┌─────────────────┐ │
│  │ WM policy   │  │  Compositor  │  │ Protocol server │ │
│  │ (tiling/    │  │  (scene +    │  │ (socket + object│ │
│  │  stacking)  │  │   KMS)       │  │  dispatch)      │ │
│  └─────────────┘  └──────────────┘  └─────────────────┘ │
└─────────────────────────────────────────────────────────┘
         clients ─────────────────────────────►

Regime where it wins: when the WM and compositor are tightly coupled (KWin effects require per-window knowledge of window state at every frame; GNOME Shell scripting requires direct access to window metadata). A shared GObject model beats the IPC cost of a cross-process WM. Real system: KWin (KDE), Mutter (GNOME). Why this blueprint rejected it: embedding is impossible — a downstream compositor cannot use xrcomp's scene/render without also accepting xrcomp's WM policy. The wlroots insight is precisely that separating them enables an ecosystem of independent compositors.

B. Microkernel display server (Mir / Fresco model)

 ┌────────────┐     IPC      ┌────────────────────────────┐
 │ client app │ ──────────► │ Compositor service (unprivil)│
 └────────────┘             │  scene + render + protocol  │
                             └──────────┬─────────────────┘
                                        │ IPC
                             ┌──────────▼─────────────────┐
                             │ Privileged HW service       │
                             │  (DRM master, input fds)    │
                             └────────────────────────────┘

Regime where it wins: on a microkernel OS (seL4, Zephyr, QNX) where kernel services are separated by IPC and the compositor process can be unprivileged. A security-critical embedded system (automotive HUD, medical device) may want formal isolation between the display compositor and the application layer. Real system: Canonical's Mir (the multi-process mode); QNX Screen. Why this blueprint rejected it: the IPC round-trip between the privileged HW service and the compositor adds latency on every vblank event — directly conflicting with the ≤ 1-frame sample→photon target (§4.1). Linux + libseat achieves privilege separation within one process without the IPC latency.

C. GPU-side scene composition (SurfaceFlinger / Apple CoreAnimation model)

 client ──► GPU cmd buffer ──► Scene graph on GPU ──► Scanout
              (no CPU copy)     HWC decides planes
                                CPU only for policy

Regime where it wins: on mobile hardware (Android, iOS) where the SoC has a dedicated Hardware Composer (HWC) that can assign every surface directly to a hardware plane, achieving zero GPU compositing work. The compositor submits plane assignments, not rendered frames, and the HWC does the final compositing in display hardware. Real system: Android SurfaceFlinger (HWC2 path), Apple CoreAnimation. Why this blueprint rejected it: Linux DRM does not expose a generic HWC API; the closest analog is direct scanout to overlay planes (§19), which xrcomp implements for the single-surface case. Generalizing to N surfaces on N planes requires per-driver plane capability negotiation that is beyond the scope of a portable Wayland compositor; the GLES2 compositor is the fallback for the general case.

D. Async/await display server (tokio-wayland model)

  • tokio runtime
    • ├── task: client A (async socket read → dispatch)
    • ├── task: client B
    • ├── task: render worker
    • └── task: KMS backend (async vblank await)

Regime where it wins: when the compositor is embedded inside a larger async service (a desktop daemon that also handles D-Bus, portal requests, and network events) and the existing async executor already manages fds. The calloop / epoll model requires a bespoke loop; tokio can share the reactor. Real system: Smithay can be driven by an async executor; some Wayland proxies use tokio. Why this blueprint rejected it: async runtimes add scheduler overhead and indeterminate yield points on the render path. The repaint loop must hit a precise vblank deadline; an executor that might yield inside render() to service another task breaks the timing model. The single-threaded epoll loop (ADR-5) has zero scheduling overhead on the hot path.
