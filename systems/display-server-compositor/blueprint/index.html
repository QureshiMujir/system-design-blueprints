384 — Display Server / Compositor (Wayland-like)

Goal: Implement, from scratch in Rust, a production-grade Wayland display server / compositor: the Wayland wire protocol (object multiplexing, opcode dispatch, fd passing) re-implemented from the protocol XML — not linked against libwayland — plus the core protocol (wl_display/wl_registry/ wl_compositor/wl_surface/wl_shm/wl_seat/wl_output/wl_data_device), xdg-shell (xdg_wm_base/xdg_surface/xdg_toplevel/xdg_popup), subcompositor, viewporter, presentation-time, linux-dmabuf and wlr-layer-shell; a double-buffered surface tree + scene graph with damage tracking; a pluggable backend (DRM/KMS+GBM+EGL on real hardware, headless for CI, nested under X11/Wayland for development); a renderer (GLES2 + a software/pixman-like fallback); and an input stack (libinput/evdev, xkbcommon keymaps, seat + focus + serial accounting). Crates: wire / scanner / objects / protocol / shell / server / scene / backend / render / input / alloc / client / conformance / bench. It is a standalone compositor modeling the wlroots / Weston / Smithay / Mutter family — not a window-manager policy engine (a thin example WM ships on top), not a text-shaping layer (#398, a consumer), not a font rasterizer (#385, a consumer for the cursor/title chrome), not an X11 server (XWayland is an out-of-scope external bridge, §1.7). Correctness is validated by a wire-protocol differential against real libwayland clients (weston-terminal, foot, weston-simple-shm) and the Weston test-suite clients, by headless pixel-readback golden images, and by serial/lifecycle invariant checks; performance by an input-to-photon latency harness and a per-output frame-budget (16.6 ms @ 60 Hz) repaint model.

1. Goal

1.1 Engineering Definition

Build a from-scratch Wayland compositor: a single privileged process that owns the display(s) and input device(s), accepts client connections over a Unix-domain socket ($XDG_RUNTIME_DIR/wayland-N), speaks the Wayland wire protocol, maintains a per-client object graph, composites client surfaces into a scene, and scans the result out to hardware tear-free. Pipeline: wire codec + object map + socket handshake (wl_display.get_registry → globals) → wl_shm/wl_buffer/wl_surface (attach/commit, double-buffered state) → scene graph + software renderer + damage → xdg-shell (real windows) → input (seat/pointer/keyboard/touch, xkb, serials, focus) → DRM/KMS backend (atomic modeset, page-flip/vsync, hardware cursor) → GLES2 renderer (EGLImage textures, scissored damage) → linux-dmabuf zero-copy + direct scanout → subsurfaces/viewporter/presentation-time + frame scheduling → data-device (clipboard/DnD) → layer-shell + multi-output + HiDPI → session/seat management (libseat, VT switching).

1.2 System Boundaries

  • In scope: the Wayland wire format (header object_id|(size<<16|opcode), arg marshalling, SCM_RIGHTS fd passing); object lifecycle + registry + bind; wl_compositor/wl_surface (attach, damage, frame, opaque/input region, buffer transform/scale, commit, subsurface sync); wl_shm pools + wl_buffer release protocol; wl_seat + wl_pointer/wl_keyboard/wl_touch + xkb keymap fd; wl_output (geometry/mode/scale/done); xdg-shell (configure/ack handshake, toplevel/popup, interactive move/resize, positioners); wl_subcompositor/wl_subsurface; wp_viewporter; wp_presentation (feedback); zwp_linux_dmabuf_v1 (import, format/modifier negotiation); zwlr_layer_shell_v1; wl_data_device (selection + DnD) + zwp_primary_selection; DRM/KMS+GBM+EGL, headless, and nested backends; GLES2 + software renderers; libinput input; scene graph + damage + multi-output layout; a thin example WM and a thin example client toolkit (client) for testing.
  • Out of scope (non-goals): window-management policy beyond a demo WM (tiling/stacking algorithms, theming) → example only; text shaping → #398 (a consumer, §2.5); font rasterization → #385 (a consumer for cursor/title chrome); an X11 server/XWayland bridge → PhaseDeferred("Deferred Features Register"); a Vulkan renderer → PhaseDeferred("Deferred Features Register"); remote/network display (RDP/VNC/waypipe) → PhaseDeferred("Deferred Features Register"); HDR / color-management protocol → PhaseDeferred("Deferred Features Register"); explicit-sync (drm_syncobj) timeline semaphores → PhaseDeferred("Deferred Features Register") (implicit sync first); tablet/gesture/text-input/IME protocols → PhaseDeferred("Deferred Features Register").

1.3 Deployment Model

Shipped as (a) a compositor binary xrcomp runnable on a Linux TTY (takes DRM master via libseat/logind, opens input via libinput), nested in an existing X11/Wayland session (a window, for development), or headless (in-memory output, for CI); (b) a Rust library (xrcomp workspace) other compositors can embed, mirroring the wlroots "unopinionated library" model; (c) a thin example WM (xrcomp-wm) and example clients in client. The wire protocol is the public ABI: any libwayland client must connect and run unmodified. Single process, single-threaded event loop (epoll) with an optional render/decode thread pool; no in-process untrusted code.

1.4 Target Users

Compositor/graphics engineers who must understand why a display server is a protocol multiplexer + a scene compositor + a KMS driver client, not "a window manager"; engineers who need to reason about input-to-photon latency, atomic modeset, buffer-release backpressure, and why frame callbacks (not timers) throttle clients; downstream portfolio projects (#385 rasterizer renders cursor/decorations here; #398 shaping lays out window titles; #173/#380 codecs feed video surfaces; #169 software rasterizer shares the coverage/fill kernel with our software renderer).

1.9 Recommended Language & Rationale

Rust. (a) Portfolio systems default → reuse of the event-loop/epoll, tracing, and bench methodology from #53/#129/#33; (b) the compositor manipulates raw fds, mmap'd client buffers, and GPU handles where a use-after-free is a security bug — the borrow checker + a documented unsafe seam (the FFI to libdrm/gbm/EGL/libinput/xkbcommon and the mmap of client wl_shm memory) is decisive; (c) #[repr(C)] and extern "C" give clean, stable FFI to the kernel/hardware libraries that are the OS boundary (libdrm, GBM, EGL/GLES, libinput, libudev, libseat, xkbcommon) without re-implementing kernel drivers; (d) Smithay proves a safe-Rust compositor library is viable and is the closest model in our language. Rejected: C (wlroots/Weston's language — we read it for protocol semantics and KMS sequencing; no borrow checker for the object-graph lifetimes, manual wl_resource refcount bugs, the exact class of use-after-free this project is about avoiding); C++ (KWin/Qt — heavier, RAII helps but the object graph still leaks across signal/slot edges); Go (no first-class DRM/GBM/EGL story; GC pause in the repaint loop blows the 16.6 ms frame budget — a non-starter for a compositor); Zig (viable systems story, but no portfolio precedent and a smaller FFI/ecosystem for the hardware libs).

2. Why Build This

2.1 Unique Knowledge Taught

  • A display server is a protocol multiplexer, not a window manager. The compositor demuxes many clients' object graphs over one socket, enforces per-client isolation, and is itself the only KMS client — window-management policy is a thin layer on top, deliberately separated (the wlroots insight).
  • Atomic, double-buffered everything. Wayland surface state (buffer, damage, transform, frame callback) is staged and applied atomically on commit; KMS state (mode, framebuffer, planes, cursor) is staged and applied atomically on drmModeAtomicCommit. The same discipline at two layers — no partial frames, no tearing, no torn protocol state.
  • Backpressure via frame callbacks, not timers. A client that wants to animate requests a wl_surface.frame callback; the compositor fires it only when the surface was actually presented → clients self-throttle to the output's refresh, the buffer-release protocol gates buffer reuse, and the system has no busy-loop. This is the canonical "credit-based flow control" of a GUI.
  • Input-to-photon latency is a budget, not an afterthought. Where in the repaint cycle you sample input, render, and commit determines perceived latency; the compositor schedules repaints relative to the next vblank and samples input as late as possible — the same scheduling reasoning as a soft-real-time system.
  • The trust boundary is the socket. Every request carries attacker-controlled object ids, opcodes, lengths, and fds; the wire decoder is the security perimeter, and one missing bounds check is a sandbox escape.

2.2 Why It Matters

Wayland is the display stack of modern Linux (GNOME/Mutter, KDE/KWin, Sway/wlroots, the embedded/automotive stack), the successor to the 35-year-old X11 architecture. Understanding a compositor — protocol multiplexing, the scene graph, KMS scanout, input routing, the latency budget — is understanding how pixels actually reach a screen and how a multi-application GUI stays isolated, tear-free, and responsive. The wlroots library showed the field that the compositor and the WM should be separable; this project builds that separation from the wire up.

2.3 Engineering Muscles

Wire-protocol design + a code generator (scanner); object-lifetime management across a trust boundary; an epoll event loop with fd-passing and timer/idle sources; KMS atomic modeset + GBM/EGL/dmabuf buffer plumbing; a damage-tracked scene compositor; libinput/xkb input routing with serial accounting; a soft-real-time repaint scheduler tied to vblank; a differential test harness against an entrenched reference implementation (libwayland clients); session/seat privilege management (libseat/logind).

2.4 Production Concepts Exercised

Atomic state application (protocol + KMS); credit-based backpressure (frame callbacks + buffer release); zero-copy buffer sharing (dmabuf import, direct scanout to an overlay plane); partial repaint via buffer-age + damage; runtime backend/renderer abstraction (DRM vs headless vs nested; GLES2 vs software); a versioned, never-broken wire ABI (interface versioning, bind version negotiation); resource limits + input-isolation as a security contract; structured tracing of the repaint cycle for latency forensics.

2.7 What Mastery Looks Like

  • P0–P1 (wire + shm): Given a new Wayland protocol XML, you can hand-trace the exact byte sequence the scanner will emit, predict the id-range violation a misbehaving client will trigger, and design the fd-queue split that decouples SCM_RIGHTS from the recv ring — without consulting the spec.
  • P2–P3 (scene + xdg-shell): You can explain why a configure→ack serial mismatch causes a half-resized frame (I5/I7), draw the damage rectangle that results when a toplevel moves 10 px right, and diagnose a "window never appears" bug by reading the xdg-shell configure/ack event trace.
  • P4 (input + serials): You can prove, from the serial allocator's monotonic property (I7), that a background client cannot steal the clipboard, and reproduce a focus-loss bug from a kbd_focus telemetry trace alone.
  • P5–P6 (DRM/KMS + GLES2): You can read a KMS property dump, identify the plane a cursor must go to, write the AtomicState that achieves it, predict the test_commit failure mode for a modifier mismatch, and explain the y-flip between Wayland and GL coordinate systems.
  • P7 (dmabuf + direct scanout): You can trace a dmabuf from zwp_linux_dmabuf_v1.create_params through eglCreateImageKHR to the overlay plane assignment, explain why an implicit fence must be waited before texture sampling, and state the exact condition under which direct scanout disengages without a black flash.
  • P8 (scheduler): You can compute the sample→photon budget for a 120 Hz display, identify the point in the repaint loop where sampling input earliest costs exactly one additional frame of latency, and tune the vblank offset to the measured render cost.
  • P11–P13 (session + security + conformance): You can describe the privilege seam libseat enforces, write the invariant test that proves keyboard isolation holds under two concurrent clients, and explain why a cap on per-client object count (I14) is the correct DoS mitigation rather than a rate limiter.

3.2 Box Narratives

  • server (event loop). The single owner of control flow: an epoll loop over the listen socket, every client fd, the libinput fd, the DRM fd, and timer/idle sources. Per-client, it reads the recv ring + ancillary fd ring, frames messages (wire), and dispatches each request serially in arrival order (I4). Writes are buffered and flushed once per loop iteration. No protocol dispatch ever runs off this thread; only rendering/decoding may be offloaded.
  • objects. The per-client namespace: a map ObjectId → Resource. Clients allocate ids in [1, 0xFEFFFFFF]; the server allocates server-side ids from 0xFF000000 (I2). Each Resource carries its interface, negotiated version, opcode-handler table, and typed userdata. Destruction emits wl_display.delete_id so the client may recycle the id (I3). This is where every use-after-free is prevented or created.
  • protocol + shell. The object implementations. wl_display (sync/get_registry, error/delete_id), wl_registry (global/bind), wl_compositor/wl_surface (the central object — attach/damage/frame/ regions/transform/scale/commit), wl_shm pools and wl_buffer (release protocol), wl_seat and the input objects, wl_output. shell adds xdg-shell (the configure/ack lifecycle that turns a surface into a window), subcompositor, viewporter, presentation-time, linux-dmabuf, layer-shell, data-device.
  • scene. The compositor's model of what is on screen. Each wl_surface has double-buffered state: a pending set mutated by requests and a current set swapped in atomically on commit (I5). Surfaces have roles (toplevel/popup/subsurface/layer/cursor/dnd-icon) and form a tree (subsurfaces) within a scene graph (per-output, per-layer stacking). It accumulates damage (surface-local → output-local), owns the output layout (positions/transforms/scales), and answers input hit-tests via input regions.
  • alloc. The buffer boundary. wl_shm buffers are a client memfd mmap'd read-only into the compositor (CPU pixels for the software renderer or texture upload). linux-dmabuf buffers are imported as EGLImage/GBM bo for zero-copy GPU texturing and possible direct scanout. It tracks the buffer-release protocol — a buffer must be wl_buffer.released before the client may reuse it (I6) — and the negotiated format/modifier set.
  • render. Renderer + Texture traits with two backends: a GLES2 renderer (an EGL context per output/GPU, client buffers as textures via EGLImage or glTexImage2D from shm, an FBO or the GBM surface as target, glScissor to the damage region) and a software renderer (CPU coverage + alpha blend, reusing #169) for headless/no-GPU. It consumes the scene's node list + damage and produces a composited framebuffer.
  • backend. The hardware abstraction. DRM/KMS+GBM: enumerates connectors/CRTCs/encoders/planes, performs atomic modeset, allocates scanout buffers via GBM, page-flips on vblank, drives a hardware cursor plane, and (P7) assigns a fullscreen opaque surface directly to an overlay plane (direct scanout, zero compositing). headless: an in-memory framebuffer + a synthetic vblank timer (CI + golden-image readback). nested: renders into a parent X11/Wayland window for development. Emits vblank/page-flip-done, hotplug, and session-active/inactive events into the loop.
  • input. libinput (over a udev/seat-provided device fd set) produces evdev events; the seat routes them: pointer motion/button/axis with surface-local coordinates, keyboard key/modifier state via an xkbcommon keymap (shared to clients as an fd), touch, and the focus model (which surface receives keyboard input). It allocates the monotonic input serials that gate xdg-shell interactions and selection (I7). Keyboard input goes only to the focused surface — the isolation guarantee.
  • session/seat (libseat). Acquires DRM master and input-device fds without running as root, and handles VT switching (pause/resume the backend + input on session deactivate/activate). The privilege seam.
  • GPU / display hardware & input devices. The external world: the kernel DRM driver + the panel, and the evdev input devices. The compositor is a client of both.

3.3 Boundaries

  • Trust boundary: the client socket. Every request's object id, opcode, arg lengths, string/array bounds, and passed fds are attacker-controlled and validated before use (I1, I12, §26). Clients never see each other's objects, buffers, or input (the isolation contract).
  • Concurrency boundary: protocol dispatch is single-threaded (the event-loop thread); there are no locks on the object graph or scene. Only the renderer's GPU/CPU pixel work and media decode may run on a worker pool, fenced back to the loop (I11). A surface's state is only ever mutated on the loop thread.
  • Privilege boundary: DRM master + input fds are held via libseat; on VT-switch the compositor drops the GPU/input and restores on resume. No raw-root requirement.
  • Buffer boundary: client wl_shm memory is mapped read-only and its size/stride/format validated against the pool (a client shrinking a pool under us must not cause an OOB read — I8); dmabuf imports are validated against the advertised format/modifier set.

3.4 Data-flow walk — one client frame (shm, headless or DRM)

  1. Client binds wl_compositor, wl_shm, xdg_wm_base; create_surface; xdg_wm_base.get_xdg_surface + get_toplevel; commit (no buffer) → compositor sends the initial xdg_surface.configure(serial).
  2. Client ack_configure(serial), creates a wl_shm pool from a memfd, create_buffer, draws pixels, wl_surface.attach(buffer), damage, frame(cb), commit.
  3. On commit the compositor swaps pending→current SurfaceState (I5), maps/validates the buffer (I8), marks the surface mapped, and accumulates surface→output damage in the scene.
  4. The repaint scheduler, woken for the next vblank, walks the scene graph for that output, builds the damaged node list, and the renderer composites (software: blend; GLES2: textured quads scissored to damage) into the output framebuffer.
  5. The backend commits the framebuffer atomically (DRM drmModeAtomicCommit with PAGE_FLIP_EVENT; headless: schedule the synthetic vblank).
  6. On page-flip-done (vblank), the compositor sends wl_buffer.release for the now-scanned-out buffer (I6), fires the frame callback done(time) (I9) so the client may draw the next frame, and emits any wp_presentation feedback. The client, throttled by the callback, draws frame N+1.

4.1 Worked latency budget (reference)

60 Hz, one fullscreen client, DRM backend, to make the headline concrete:

  • Refresh interval: 1/60 = 16.67 ms. The compositor schedules a repaint to complete just before the next vblank.
  • Late input sampling: sample libinput at repaint start, not at event arrival → the freshest possible input enters the frame. Sampling early adds up to a full frame of staleness.
  • Render: software path must blend the damaged region within a few ms; GLES2 textured composite of a handful of quads is sub-ms on any GPU. Budget ≤ ~8 ms leaves margin.
  • Commit → scanout: drmModeAtomicCommit latches at the next vblank; the buffer is scanned out over the following refresh. So a commit "now" is visible ~1 refresh later — the irreducible 1-frame floor.
  • Total (sample→photon): ~1 refresh + render ≈ 16–21 ms p99. Direct scanout (fullscreen opaque on an overlay plane) removes the composite step entirely → just the plane flip, the minimum the hardware allows.
  • Anti-pattern: an extra back-buffer copy or rendering a frame ahead adds 16.6 ms each — the difference between a responsive and a "laggy" compositor is exactly this scheduling discipline.

6. Design Principles

  1. The wire decoder is the security perimeter; validate every byte before it becomes a pointer. Object ids, opcodes, lengths, string/array bounds, fd counts — all attacker-controlled, all checked before use (I1, I12). Violation: trusting a length → OOB read, a sandbox escape from one client into the compositor's address space.
  2. Mechanism in the compositor, policy in the WM. The server provides surfaces, input routing, scanout; where windows go and how they're decorated is a thin, replaceable layer (the wlroots split). Violation: baking tiling/stacking into the core → an unembeddable, unforkable compositor.
  3. All state application is atomic and double-buffered — at both layers. Surface state applies on commit; KMS state applies on atomic commit; never a partial frame or torn protocol state (I5). Violation: applying attach immediately → flicker/tearing and protocol races.
  4. Backpressure via frame callbacks + buffer release, never busy-loops or timers. Clients animate only when told a frame was presented; buffers can't be reused until released (I6, I9). Violation: firing frame on a timer → clients render faster than refresh, wasting GPU/power and adding latency.
  5. Damage-driven repaint; do nothing when nothing changed. A static screen triggers no compositing; a small change repaints only its bounding damage (I10). Violation: repaint-every-vblank → constant CPU/GPU load, no idle, mobile battery dead.
  6. Schedule repaints relative to the next vblank; sample input as late as possible. The repaint clock is the display, not a fixed timer; input is read at repaint start. Violation: render-ahead / early-sample → an extra frame of latency, the difference between snappy and laggy.
  7. One thread owns the object graph and scene; offload only pixels. Protocol dispatch + state mutation is single-threaded and lock-free; only render/decode may use a worker pool, fenced back (I11). Violation: touching a wl_surface from a render thread → data races on the very lifetimes Rust is here to protect.
  8. unsafe is confined to the FFI seam (libdrm/gbm/EGL/libinput/xkb) and client-buffer mmap. Everywhere else is checked Rust. Violation: unsafe leaking into the object graph → unauditable use-after-free, the bug class this project exists to eliminate.
  9. The wire ABI is forever; versions are negotiated, never broken. Interfaces are versioned; bind negotiates the min of client/server version; new requests/events only ever extend (I13). Violation: changing an opcode/signature → every existing client breaks; Wayland's whole value is the stable ABI.
  10. Buffers are zero-copy where the hardware allows. dmabuf imports texture directly; a fullscreen opaque surface scans out from its own buffer on an overlay plane (direct scanout) (I-direct). Violation: always glReadPixels/CPU-copy → bandwidth + latency + power blown.
  11. Bounded everything: objects, buffers, pool memory, recursion (subsurfaces), per-client. Every client-driven growth has a configurable cap (I14, §26). Violation: an unbounded object map → one client OOMs the compositor and takes down every other client's session.
  12. Isolation by construction: no client sees another's input, buffers, or objects. Keyboard input goes only to the focused surface; there is no global input/screencopy without an explicit, privileged protocol (I7, §26). Violation: a keylogger-as-a-client — the failure X11 is infamous for.
  13. Crash-only, per-client fault isolation. A malformed request → a wl_display.error + disconnect of that client; the compositor and all other clients continue (I1). Violation: a panic on bad input → the whole session dies because one app misbehaved.
  14. Observability by default. Every commit, repaint, page-flip, plane assignment, focus change, and protocol error is traceable with timings; latency is measurable, not guessed. Violation: an opaque repaint loop → unprofilable judder and "feels laggy" bug reports with no data.
  15. Backend/renderer/allocator are abstractions, resolved at startup. DRM vs headless vs nested; GLES2 vs software — chosen once, behind traits, so CI runs headless and dev runs nested. Violation: hard-coding DRM → no CI, no dev-on-laptop, untestable.

8. Domain Model — The Wayland Protocol

8.1 The wire format

A connection is a byte stream of 32-bit-aligned, little-endian messages plus an out-of-band fd stream (ancillary SCM_RIGHTS data). Each message:

word 0:  object_id : u32                        // sender's target object
word 1:  (size : u16 << 16) | (opcode : u16)    // size = total bytes incl. 8-byte header; opcode = request/event #
words 2..: arguments, each 32-bit aligned

Argument wire encodings:

int / uint   : 1 word (i32 / u32)
fixed        : 1 word, signed 24.8 fixed point (wl_fixed_t)         // sub-pixel coords
object       : 1 word, an object_id (0 = null)
new_id       : 1 word (known interface) | (string iface + uint version + uint id) for wl_registry.bind
string       : 1 word length (incl. trailing NUL) + UTF-8 bytes, padded to 4
array        : 1 word length (bytes) + raw bytes, padded to 4
fd           : NOT in the stream — consumed in-order from the ancillary fd queue

Requests flow client→server, events server→client; both use the identical framing. The decoder must treat size, string/array lengths, and the fd count as untrusted (I1, I8, I12).

8.2 Objects, interfaces, versions

The protocol is object-oriented over the wire. An interface (e.g. wl_surface) defines numbered requests (client→server) and events (server→client) plus enums. An object is an interface instance with an id, created by a request carrying a new_id (factory pattern). Each interface has a version; wl_registry.bind negotiates it (I13). The bootstrap object is wl_display (id 1, always present).

interface wl_compositor {
  request create_surface(new_id wl_surface);
  request create_region(new_id wl_region);
}

A surface is a rectangle of pixels with pending vs current state (I5). Requests stage pending; commit swaps:

pending: { buffer: Option<wl_buffer>, buffer_dx/dy, damage: Region (surface coords),
           buffer_damage: Region (buffer coords), opaque_region, input_region,
           frame_callbacks: Vec<wl_callback>, transform, scale, viewport(src,dst) }
on commit:  current ← pending ; pending.damage/frame cleared ; accumulate output damage ; (sub)surface tree applied

8.5 Roles and xdg-shell

A bare wl_surface has no on-screen meaning until given a role: xdg_toplevel (a window), xdg_popup (a menu/tooltip, positioned by an xdg_positioner relative to a parent), wl_subsurface (a child composited with a parent), a layer-shell layer, a cursor, or a DnD icon. A surface has exactly one role for life. xdg-shell lifecycle (the configure/ack contract):

surface.commit (no buffer) → compositor: xdg_surface.configure(serial=S)
client: xdg_surface.ack_configure(S); attach buffer; commit            // now mapped & shown
compositor (resize/maximize/focus): xdg_toplevel.configure(w,h,states[]) + xdg_surface.configure(S2)
client: ack_configure(S2); attach buffer sized w×h; commit             // atomic resize, no flicker
compositor: xdg_toplevel.close()  (request to close)  |  client: xdg_toplevel.destroy()

The serial ties a configure to the client's acknowledging commit so resizes are atomic and unambiguous (I5). Worked example — interactive resize: user drags edge → compositor sends configure(new w,h, [resizing]) each frame → client renders at that size and acks → compositor maps the new buffer; never a half-resized frame.

8.6 wl_shm buffers

A client creates a pool from a sealed memfd (wl_shm.create_pool(fd, size)), then carves wl_buffers (offset, width, height, stride, format) from it (I8). The compositor mmaps the pool read-only and reads pixels (software path) or uploads them as a texture (GLES2). The buffer-release protocol (I6): the client must not touch a buffer until wl_buffer.release. Formats: ARGB8888, XRGB8888 mandatory; others advertised via wl_shm.format.

8.7 Input — seat, focus, serials

A wl_seat advertises capabilities (pointer/keyboard/touch) and vends wl_pointer/wl_keyboard/ wl_touch. Event flow + the focus/serial model:

pointer:  enter(serial, surface, sx, sy) → motion(time, sx, sy)* → button(serial, time, btn, state)
          → axis(time, axis, value) → frame()   (frame groups one logical event)
keyboard: keymap(format, fd, size) once → enter(serial, surface, keys[]) → key(serial, time, key, state)
          → modifiers(serial, depressed, latched, locked, group) → leave(serial, surface)

Keyboard enter/key go only to the focused surface (I7). Serials are monotonic and tag every input-derived event; interactive requests (xdg_toplevel.move/resize, wl_data_device.set_selection, set_cursor) must cite a recent valid serial or are rejected (I7) — this prevents a background client from, e.g., grabbing the pointer or stealing the clipboard.

8.8 Output, layout, transform, scale

A wl_output describes a monitor: geometry(x,y,phys_w,phys_h,subpixel,make,model,transform), mode(flags,w,h,refresh), scale(factor), name/description, terminated by done. The compositor owns the layout (where each output sits in a global compositor-space coordinate system) and per-output transform (rotation/flip) and scale (HiDPI integer scale; fractional via viewporter). A surface overlapping an output gets wl_surface.enter(output); clients pick buffer scale accordingly.

8.9 Subsurfaces, viewporter, presentation-time, dmabuf (extension semantics)

  • wl_subsurface: a surface composited at an offset relative to a parent; synchronized mode caches its commits until the parent commits (atomic nested update, I16); desynchronized applies immediately.
  • wp_viewporter: a src crop rect (in buffer coords) + a dst size → scaling/cropping without a new buffer (video letterboxing, fractional scale).
  • wp_presentation: feedback(surface) → presented(tv_sec, tv_nsec, refresh, seq, flags) with the actual scanout time (for A/V sync) or discarded.
  • zwp_linux_dmabuf_v1: advertises (format, modifier) pairs; the client builds a buffer from dmabuf fd(s) + plane layout + modifier; the compositor imports it as an EGLImage (zero-copy texture / direct scanout candidate, §19).

11.12 Explicit-sync note (deferred)

drm_syncobj timeline semaphores replace implicit dmabuf fences with explicit acquire/release timeline points, eliminating over-synchronization and enabling finer pipelining. Modeled here for completeness; implementation gated PhaseDeferred("Deferred Features Register"). The buffer-release invariant (I6) generalizes to "released at the release-timeline point"; until then, implicit fences gate release.

  • Stand up the Cargo workspace (ADR-2) and the wire + objects + server + backend/headless skeleton.
  • Implement the wire codec (Message framing, all arg types, SCM_RIGHTS fd ring) and the per-client object map with id-range + version validation (I1, I2, I13).
  • Bring up the wl_display/wl_registry/wl_callback bootstrap handshake; advertise zero real globals.
  • Establish the libwayland-client differential harness + headless golden-image scaffold — the oracle.

12.2 Detailed Implementation Steps [Høgsberg "Wayland Architecture" §bootstrap; Kerrisk ch.57–63; libwayland connection.c; ADR-3/4/5]

  • wire::message/decode/encode — header codec (object|(size<<16|opcode)), arg (un)marshalling, 32-bit alignment, Fixed(24.8); wire::fdqueue — owned SCM_RIGHTS fd ring (I12, Kerrisk ch.61); wire::conn — recv/send ring buffers over recvmsg/sendmsg.
  • objects::id — ObjectId, is_client_side range check (I2); objects::map — ObjectMap + tombstones (I3, Smithay resource.rs pattern); objects::dispatch — opcode→handler with version gate (I13, ADR-4).
  • server::loop — epoll reactor + EventSource (Kerrisk ch.63, ADR-5); server::socket — $XDG_RUNTIME_DIR/wayland-N listen + accept; server::client_conn — per-client decode+dispatch in arrival order (I4).
  • protocol::display/registry/callback — get_registry, sync→done, error, delete_id (Høgsberg "Wayland Architecture").
  • backend::headless — an in-memory framebuffer + synthetic vblank timer (ADR-22).
  • conformance::libwayland_diff — spawn a real libwayland client, drive the handshake, compare event bytes; conformance::golden_image — readback the headless framebuffer to PNG (libwayland ref-impl; Weston clients).

12.3 Deliverable

  • A real libwayland (or our client) connects, runs get_registry + sync, and receives a correct global/done sequence; cargo run -p server --example run_headless boots and accepts the connection.

12.4 Acceptance Criteria

  • libwayland-client completes the bootstrap handshake byte-identically to the golden trace (I4).
  • Wire round-trip (encode∘decode) identity on a corpus of every arg type; malformed messages → typed error, never a panic (I1).
  • id-range + version violations rejected (I2, I13); Miri clean on the codec; fd ring leaks zero fds (I12).

12.5 Conformance Fixtures

  • wire/good/*.bin — one per arg type + the bootstrap sequence; wire/malformed/*.bin — short size, misaligned, OOB string/array, missing fd, bad object id.
  • traces/bootstrap.golden — the canonical handshake event order.

12.6 Pitfalls

  • size is the whole message incl. header; off-by-8 truncates every arg — assert against a hand-built message (I1).
  • SCM_RIGHTS fds arrive out-of-band and can be batched/split across recvmsg differently than messages → the fd queue must be decoupled from the byte ring (I12).
  • new_id in wl_registry.bind carries an inline interface string + version (unlike every other new_id) — special-case it.
  • Little-endian + 32-bit padding on strings/arrays — pad length includes the NUL for strings.

12.7 Performance Concerns

  • Zero-copy parse: Message borrows the recv ring; don't allocate per message. Establish the per-message dispatch budget (<10 µs) now.
  • Batch writes: buffer events, flush once per loop iteration (one sendmsg).

12.8 Edge Cases

  • Partial reads (a message split across recvmsg) → buffer until complete; client disconnect mid-message → drain + free objects (I1); fd-table exhaustion → cap (I12).

12.9 Failure Analysis

  • A wrong codec corrupts everything downstream → highest test priority; the libwayland differential is the truth. Blast radius: total. Mitigation: golden traces + fuzz from day one.

12.10 Operational Notes

  • tracing initialized; WAYLAND_DEBUG=1-style wire dump via tools/wl-dump. XRCOMP_DETERMINISTIC fixes the clock for golden runs (ADR-26).

13.9 Failure Analysis

14.1 Objectives

  • Composite multiple overlapping surfaces correctly (z-order, opaque-region occlusion, alpha blend).

14.2 Detailed Implementation Steps [ADR-25/30; Foley ch.17 region algebra; Drepper "What Every Programmer Should Know About Memory" §cache; I9/I10]

  • scene::graph/node/tree/layout — node list per output, z-order, positions; scene::region/damage — rectangle-list region algebra (union/intersect/subtract) (ADR-25, Foley ch.17).
  • scene::transform — output transform/scale (full HiDPI in P10, ADR-30).
  • render::software — composite the damaged node list back-to-front, skipping fully-occluded opaque regions (Porter & Duff 1984 over); render::damage_scissor — clip every draw to damage (I10, Drepper §cache bandwidth).
  • server::loop repaint pass — for each output with needs_repaint, build the node+damage list, render, present (headless synthetic vblank), then fire frame callbacks (I9, principle 4).

14.3 Deliverable

  • Two overlapping shm surfaces composite with correct z-order + blending; moving the top surface repaints only the damaged union; a static scene triggers zero repaints.

14.4 Acceptance Criteria

  • Composited output matches a golden PNG for a multi-surface scene (I5/I10).
  • Damaged region is a conservative superset of changed pixels (golden diff ⊆ damage) (I10); idle-frame repaint count == 0 (I10).
  • Frame callbacks fire exactly once per committed frame after present (I9).

14.5 Conformance Fixtures

  • golden/two_surfaces_zorder.png, golden/move_damage.png + the damage rect log; traces/frame_callback_once.golden.

14.6 Pitfalls

  • Damage in surface vs buffer vs output coordinates — transform carefully; a coordinate-space slip paints the wrong region (I10).
  • Opaque-region occlusion must be conservative (treat unknown as non-opaque) or you drop pixels.
  • Firing frame callbacks before present → clients race ahead (I9, principle 4).
  • An empty damage region must short-circuit the whole repaint (I10).

14.7 Performance Concerns

  • Region algebra on long rect lists is O(n²); coalesce + cap rect count, fall back to bounding box past a threshold. Partial repaint is the single biggest CPU/power win (I10).

14.8 Edge Cases

  • Fully occluded surface (skip); surface partially off-output (clip); negative positions; zero-area output; a surface on two outputs (enter both).

14.9 Failure Analysis

  • Under-damage → stale pixels on screen (visible artifact); over-damage → wasted work (perf only). Bias to over-damage on any doubt (I10). Forensics: damage_area, scene dump.

14.10 Operational Notes

  • tools/scene-dump prints the node tree + damage; trace damage_area, repaint_skipped, nodes. docs/performance/damage.md documents the model.

  • A flip-timeout or failed modeset is a black screen — the worst UX failure. The flip-timeout watchdog + re-modeset path + docs/runbooks/flip-timeout.md/gpu-hang.md are mandatory. Telemetry: atomic_commit, flip_done, flip_timeout.

  • A GPU client (weston-simple-egl, a video player) shares a dmabuf that textures with no copy; a fullscreen video/game scans out directly off its own buffer; partial repaint reuses the prior frame.

19.4 Acceptance Criteria

  • dmabuf import succeeds for advertised format/modifier pairs and textures correctly (golden vs shm path).
  • Buffer-age repaint paints a strict superset of changed pixels using the correct age (I10); a stale-age bug is detectable (visible artifact in the golden).

  • golden/dmabuf_vs_shm.png; golden/buffer_age_partial.png + the age/damage log; traces/direct_scanout_engage_disengage.golden.

19.6 Pitfalls

  • Implicit sync: the imported dmabuf carries a fence; reading before it signals → torn/garbage frame. Respect the fence (I6; explicit sync deferred — Deferred Features Register).
  • Buffer age is the count of frames since that specific buffer was current; off-by-one → under-damage → visible stale regions (I10).
  • Direct-scanout format/modifier must exactly match a plane's capability; mismatch → test_commit fails → fall back, never black-screen.
  • Disengaging direct scanout (when chrome appears over the surface) must re-enable compositing in the same atomic commit — no flash.

19.7 Performance Concerns

  • dmabuf eliminates the shm upload entirely — the biggest per-frame CPU/bandwidth win for GPU clients (principle 10).
  • Direct scanout removes the composite + an intermediate buffer — the path #291 (real-time A/V) and fullscreen games need for minimal latency + power.

  • Multi-planar formats (NV12 video); modifier-less (linear) dmabuf; an oversize buffer; a client closing a dmabuf fd early; a plane already in use by the cursor.

19.9 Failure Analysis

  • A sync/age bug shows as tearing or stale regions only under motion — the golden-under-animation tests + wp_presentation timing catch it. Direct-scanout fallback must be bulletproof (always degrade to composite). Forensics: direct_scanout, buffer_age, plane assignment dump.

19.10 Operational Notes

  • Trace direct_scanout, plane assignments, fence-wait latency. docs/performance/direct-scanout.md, docs/performance/buffer-age.md.

  • shell::presentation — feedback → presented(time, refresh, seq, flags) from the page-flip-done timestamp, or discarded (presentation-time.xml, principle 6).
  • server::loop repaint scheduler — compute the next-vblank target (Pulkkinen/Larsson §vblank-offset; Gregory ch.8 frame-pacing), schedule the repaint to finish just before it, sample input then (principle 6), fire frame callbacks at present (I9).

  • A client with subsurfaces (e.g. video + decorations) updates atomically; a video letterboxes via viewporter; wp_presentation reports accurate scanout times; clients throttle to refresh.

20.4 Acceptance Criteria

  • A synchronized-subsurface tree applies as one atomic frame with its parent (I16); recursion past the cap → protocol error.
  • wp_presentation timestamps match the actual flip time within a frame; viewporter crop/scale matches a golden.
  • Clients render exactly one frame per refresh under a frame-callback loop (no overdraw) (I9, principle 4).

20.5 Conformance Fixtures

  • golden/subsurface_atomic.png; golden/viewport_crop_scale.png; traces/presentation_feedback.golden; traces/frame_throttle_60hz.golden.

20.6 Pitfalls

  • Synchronized subsurface state must cache through arbitrary parent-commit nesting and apply in tree order; getting the order wrong tears the nested update (I16).
  • A frame callback fired late (or never) stalls an animating client; fired early wastes a frame (I9).
  • Viewporter source rect in buffer coords vs destination in surface coords — mixing them mis-scales.
  • Presentation seq/refresh must be monotonic + accurate for A/V sync to work.

20.7 Performance Concerns

  • The scheduler is the latency knob (§4); render-ahead vs late-sample is the whole ballgame. Coalesce multiple commits within a frame to the latest.

20.8 Edge Cases

  • Deeply nested subsurfaces (cap, I16); a subsurface larger than its parent; desync subsurface during a sync parent; presentation feedback on a discarded (never-shown) frame.

20.9 Failure Analysis

  • A scheduling bug manifests as judder or input lag with no crash — only RepaintTrace timings reveal it. Blast radius: perceived responsiveness of the whole session. Forensics: sample_to_render_ns, flip_latency_ns.

20.10 Operational Notes

  • Trace the full RepaintTrace; docs/performance/repaint-scheduling.md + latency-budget.md. A latency HUD overlay (debug) shows per-frame timings.

26. Threat Model

The attack surface is the client socket (every request: object ids, opcodes, lengths, strings/arrays, and passed fds — all attacker-controlled) plus untrusted buffer contents and a hostile or buggy client's resource appetite. The compositor is a privileged, long-lived process holding DRM master, input fds, and every client's buffers, so the model centers on memory safety at the wire boundary, per-client isolation, resource-exhaustion containment, and the privilege seam.

29. Compatibility & Versioning

  • Wire ABI: the wire format + the implemented interfaces/versions are a frozen contract; any libwayland client built against these interfaces runs forever (principle 9, I13). New protocol support is additive (new globals/versions), never a change to an existing opcode/signature.
  • Interface versioning: bind negotiates min(client, server) (I13); a client binding vN must work even as the server advertises vN+1. Each interface's max version is documented + tested.
  • Buffer formats: the advertised wl_shm formats and dmabuf (format, modifier) set may grow, never shrink, without a major version.
  • Configuration: xrcomp.toml keys are SemVer-stable; unknown keys warn, never fail.
  • Embedding API (Rust): the library crates' public types follow SemVer; #[non_exhaustive] on Error, Role, BufferKind, Isa-like enums so additions are non-breaking.
  • Determinism mode: XRCOMP_DETERMINISTIC (fixed clock, scripted input) is a stable contract for golden tests/replay (ADR-26).
  • Protocol extensions: experimental (z*_unstable_v*) interfaces may change with their upstream; stable (xdg_*, wp_* stable) are frozen.
  • Deprecation: an interface/version is supported for the life of the major release; removal needs a major bump + a migration note.

32. Performance Engineering

  • Latency first: the headline metric is sample→photon; the repaint scheduler's vblank offset + late input sampling (principle 6) is the primary lever, measured by bench::latency (headless model + on-hardware).
  • Idle is free: damage-driven repaint means a static screen costs ~0 CPU/GPU (I10) — verified by the idle-frame counter; this is the mobile-battery + thermal win.
  • Zero-copy: dmabuf import (no upload) + direct scanout (no composite) are the per-frame bandwidth/power levers (§19, principle 10); track engagement %.
  • No per-frame allocation: the repaint path is allocation-free in steady state; an alloc counter guards it (tail-latency jitter source).
  • Profiling: perf stat (cache/branch/IPC), flamegraphs of the loop, perf c2c for false sharing on the worker fences; GPU timing via EGL/GL timer queries.
  • Damage tightness: the rect-list region algebra is bounded (coalesce + cap); partial repaint scissors both CPU and GPU work (§14, §24).
  • Scanout bandwidth: at 4K@60 the framebuffer is ~2 GB/s of scanout; direct scanout avoids an extra composite pass over it.
  • Targets: the §4 table — enforced by the bench gate; tail latency (p99) is the smoothness metric, not mean.

33. Scalability Analysis

  • Client count: scales to the fd budget (RLIMIT_NOFILE) and the per-client caps (I14); dispatch is O(messages), the loop drains bursts FIFO (I4). Hundreds of clients are fine; the limit is buffers/fds, not CPU.
  • Surface/node count: compositing is O(visible, non-occluded surfaces × damage); opaque-region occlusion culls hidden surfaces. A desktop's dozens of windows are trivial; the cost is pixels, not objects.
  • Output count: each output is an independent repaint loop + scanout; scales to the GPU's CRTC/plane count. Beyond that, outputs share a CRTC (mirror) or are unsupported (documented).
  • Resolution/refresh: the frame budget shrinks with refresh (16.6→8.3 ms at 60→120 Hz) and the scanout bandwidth grows with resolution; direct scanout + partial repaint are the mitigations.
  • Input rate: high-frequency mice (1000 Hz) are folded into the per-frame sample (principle 6) — input rate never drives repaint rate.
  • What does NOT scale (by design): a single output's repaint is inherently serialized to its vblank; multi-GPU / PRIME offload and remote display (both deferred — see Deferred Features Register) are out of scope; the compositor is a single-node, single-process design.
  • Coordination overhead: none beyond the single loop; the worker pool (render/decode) is embarrassingly parallel per buffer (I11).

34. Mental Models & First Principles

MM1. The compositor is a protocol multiplexer, not a window manager. The server demuxes N client object graphs over N sockets and is the sole KMS client; window placement is a thin policy layer (principle 2). Predicts: separating the WM from the compositor enables compositors-as-libraries (wlroots). Bug class without it: baking tiling into the server makes it un-embeddable; every fork must re-implement the full stack. Applied: §3 (architecture), §15 (P3 xdg-shell policy split), §22 (P10 layer-shell / demo WM).

MM2. Surface state is a double-buffered state machine; commit is the only clock edge. Requests stage pending state; commit atomically swaps it to current (I5). No request can cause a partial frame. Predicts: any request that "takes effect immediately" (not at commit) creates a race. Bug class without it: attaching a buffer before committing gives the compositor a dangling reference; mid-frame updates cause tearing. Applied: §8.4, §11.4, all phases (I5 is a compositional invariant).

MM3. The wire decoder is the security perimeter; every byte is attacker-controlled. Object ids, sizes, string lengths, fd counts — all forged-able. Predicts: a single missing bounds-check is a sandbox escape. Bug class without it: OOB read from a forged size; UAF from a client id in the server's namespace (I2). Applied: §8.10, §12 (P0 wire fuzz), §26 (threat model), §30 (fuzz strategy).

MM4. Backpressure is credit-based: wl_buffer.release gates reuse, frame callback gates the next draw. The compositor holds a credit (the buffer) until it is done reading it; the client holds a credit (a frame slot) until the compositor fires the callback. Predicts: missing a release starves a single-buffered client forever; firing frame before present causes over-rendering. Bug class without it: stale-buffer tearing (I6 violation); GPU/power waste from unconstrained animation. Applied: §8.4, §13 (P1), §20 (P8 scheduler), §27 (failure mode: client buffer starvation).

MM5. Damage drives the repaint clock; vblank drives the scanout clock. Nothing repaints if nothing changed; repaints are scheduled relative to the next vblank, not a fixed timer. Predicts: a static screen costs ~0 CPU/GPU; render-ahead adds exactly one frame of latency. Bug class without it: repaint-every-tick wastes 100 % idle GPU; early-sample adds a frame of input lag. Applied: §4.1 (latency budget), §14 (P2 damage), §20 (P8 scheduler), §24 (P12 hardening, I10).

MM6. Atomic KMS commit is an all-or-nothing hardware transaction. TEST_ONLY validates the plane/mode configuration without touching hardware; PAGE_FLIP_EVENT signals when the new buffer is live. Predicts: a non-atomic modeset produces tearing or a black frame; freeing a framebuffer before its PAGE_FLIP_EVENT produces scanout-of-freed-memory. Bug class without it: I15 violations — torn frames, GPU hang on freed fb. Applied: §17 (P5 DRM/KMS), §23 (P11 VT-switch re-modeset), §27 (failure mode: tearing, black screen).

MM7. The single-threaded loop is lock-free by construction. All protocol dispatch + scene mutation happens on one thread; workers receive owned pixel buffers and return them fenced. No lock needed on the object graph or scene. Predicts: sharing any Resource or Scene handle with a worker thread introduces data races invisible at compile time. Bug class without it: I11 violations — concurrent surface mutation during a worker repaint; TOCTOU on SurfaceState. Applied: §3.3 (concurrency boundary), §6 (principle 7), §11.3 (Cx design), §25 (TSan tests).

MM8. Interface versioning is forever; bind negotiates the minimum. Interfaces never remove or renumber requests/events; a client binding vN gets exactly the API it asked for. Predicts: any opcode renumbering or signature change breaks every existing binary compiled against that interface. Bug class without it: I13 violations — a v4 client sending a v5 opcode silently corrupts state. Applied: §8.2, §8.3, §12 (P0 opcode dispatch), §29 (compatibility guarantees).

MM9. Zero-copy is a hierarchy: shm → texture upload → dmabuf → direct scanout. Each step removes a buffer copy. shm requires a CPU upload per frame; dmabuf textures without copying; direct scanout skips compositing entirely. Predicts: the biggest per-frame bandwidth saving is dmabuf import; the biggest latency saving is direct scanout. Bug class without it: always-uploading-shm wastes bandwidth for GPU clients; missed direct-scanout adds composite latency on the critical path (#291, §4.1). Applied: §13 (P1), §18 (P6), §19 (P7 dmabuf+direct scanout), §32 (performance engineering).

MM10. Serial monotonicity is the isolation protocol; a stale serial is a forgery. Interactive requests (move, resize, set_selection, start_drag) must cite a recent input serial to prove they were triggered by the user, not a background client. Predicts: a background client can never grab the pointer or steal the clipboard if serials are checked. Bug class without it: I7 violations — a malicious client sends xdg_toplevel.move with a fabricated serial and hijacks window management; the classic X11 keylogger attack. Applied: §8.7, §16 (P4 serial pool), §21 (P9 data device), §26 (threat model: clipboard/DnD theft).

Which invariant prevents a black screen on return?

  5. (§12 + §26) The fuzz harness sends a message with object_id = 0xFF000001 (a server-side id) from the client side. What invariant fires, what error is sent, and why does the compositor continue serving other clients? Now trace the same exploit for object_id = 0.

  6. (§13 + §19) A client calls wl_shm_pool.resize(new_size) smaller than an existing wl_buffer's offset + stride × height. When must the compositor detect this? How does I8's "re-validate on every access" model prevent the OOB read, and what would happen under a "validate at create" model?

  7. (§8.4 + §20) A synchronized subsurface tree has depth 5. The client commits the leaf, then the intermediate, then the root. In what order does commit apply state to current, and why is the entire tree visible only after the root commit? What does the depth cap (I16) prevent, and how is it implemented without recursion?

  8. (§4.1 + §24) At 60 Hz the render takes 9 ms. The vblank offset is currently set to −8 ms. What happens? Now recalculate the correct offset assuming 10 ms render + 1 ms margin. How does increasing refresh to 120 Hz change the arithmetic, and what breaks at 144 Hz without re-tuning?

  9. (§17 + §19 + §22) A fullscreen opaque dmabuf surface engages direct scanout. A system notification pops up as a zwlr_layer_shell_v1 overlay surface.   11. (§3 + §32 + §33) A compositor serves 200 simultaneous clients, each animating at 60 Hz with a 1080p shm surface. 38. Alternative Architectures (Roads Not Taken)

A. Monolithic compositor-WM (X.org / KWin model)

┌─────────────────────────────────────────────────────────┐
│  Monolithic server: window management + compositor +     │
│  input routing + protocol all in one process             │
│  ┌─────────────┐  ┌──────────────┐  ┌─────────────────┐ │
│  │ WM policy   │  │  Compositor  │  │ Protocol server │ │
│  │ (tiling/    │  │  (scene +    │  │ (socket + object│ │

│  └─────────────┘  └──────────────┘  └─────────────────┘ │

Regime where it wins: when the WM and compositor are tightly coupled (KWin effects require per-window knowledge of window state at every frame; GNOME Shell scripting requires direct access to window metadata). A shared GObject model beats the IPC cost of a cross-process WM. Real system: KWin (KDE), Mutter (GNOME). Why this blueprint rejected it: embedding is impossible — a downstream compositor cannot use xrcomp's scene/render without also accepting xrcomp's WM policy. The wlroots insight is precisely that separating them enables an ecosystem of independent compositors.

B. Microkernel display server (Mir / Fresco model)

 ┌────────────┐     IPC      ┌────────────────────────────┐
 │ client app │ ──────────► │ Compositor service (unprivil)│
 └────────────┘             │  scene + render + protocol  │
                             └──────────┬─────────────────┘
                                        │ IPC
                             ┌──────────▼─────────────────┐
                             │ Privileged HW service       │
                             │  (DRM master, input fds)    │
                             └────────────────────────────┘

Regime where it wins: on a microkernel OS (seL4, Zephyr, QNX) where kernel services are separated by IPC and the compositor process can be unprivileged. A security-critical embedded system (automotive HUD, medical device) may want formal isolation between the display compositor and the application layer. Real system: Canonical's Mir (the multi-process mode); QNX Screen. Why this blueprint rejected it: the IPC round-trip between the privileged HW service and the compositor adds latency on every vblank event — directly conflicting with the ≤ 1-frame sample→photon target (§4.1). Linux + libseat achieves privilege separation within one process without the IPC latency.

C. GPU-side scene composition (SurfaceFlinger / Apple CoreAnimation model)

 client ──► GPU cmd buffer ──► Scene graph on GPU ──► Scanout
              (no CPU copy)     HWC decides planes
                                CPU only for policy

Regime where it wins: on mobile hardware (Android, iOS) where the SoC has a dedicated Hardware Composer (HWC) that can assign every surface directly to a hardware plane, achieving zero GPU compositing work. The compositor submits plane assignments, not rendered frames, and the HWC does the final compositing in display hardware. Real system: Android SurfaceFlinger (HWC2 path), Apple CoreAnimation. Why this blueprint rejected it: Linux DRM does not expose a generic HWC API; the closest analog is direct scanout to overlay planes (§19), which xrcomp implements for the single-surface case. Generalizing to N surfaces on N planes requires per-driver plane capability negotiation that is beyond the scope of a portable Wayland compositor; the GLES2 compositor is the fallback for the general case.

D. Async/await display server (tokio-wayland model)

  • tokio runtime
    • ├── task: client A (async socket read → dispatch)
    • ├── task: client B
    • ├── task: render worker
    • └── task: KMS backend (async vblank await)

Regime where it wins: when the compositor is embedded inside a larger async service (a desktop daemon that also handles D-Bus, portal requests, and network events) and the existing async executor already manages fds. The calloop / epoll model requires a bespoke loop; tokio can share the reactor. Real system: Smithay can be driven by an async executor; some Wayland proxies use tokio. Why this blueprint rejected it: async runtimes add scheduler overhead and indeterminate yield points on the render path. The repaint loop must hit a precise vblank deadline; an executor that might yield inside render() to service another task breaks the timing model. The single-threaded epoll loop (ADR-5) has zero scheduling overhead on the hot path.

40. Glossary

  • Compositor / display server the process that owns the screen + input, multiplexes clients, and scans out the composited result. Here, the same process.
  • Client a Wayland application connected over the socket; isolated from other clients.
  • Wire protocol the byte-level message format (§8.1): object id + opcode/size header + typed args.
  • Object / interface / version a protocol entity, its type, and the negotiated capability level (I13).
  • wl_display the bootstrap object (id 1): get_registry, sync, error, delete_id.
  • wl_registry / global / bind the discovery mechanism: the server advertises globals; the client binds one to an object (I13).
  • wl_surface the central object: a rectangle of pixels with double-buffered state (I5).
  • Role the meaning given to a surface (toplevel/popup/subsurface/layer/cursor/dnd-icon); exactly one.
  • commit the atomic pending→current state swap (I5).
  • Double-buffered state pending (staged by requests) vs current (applied at commit).
  • wl_buffer / wl_shm / dmabuf pixel storage: shared-memory pool buffers or zero-copy GPU dmabuf.
  • Buffer release the protocol that gates client buffer reuse (I6).
  • Frame callback wl_surface.frame → done at present; the throttling primitive (I9, principle 4).
  • xdg-shell the windowing protocol: toplevels, popups, the configure/ack lifecycle (§8.5).
  • Configure / ack_configure / serial the atomic-resize handshake; serials gate interactions (I7).
  • Seat / focus / serial the input model: a seat's devices, the focused surface, monotonic event tags (I7).
  • Scene graph the retained model of on-screen surfaces: outputs → layers → nodes (ADR-30).
  • Damage the region of changed pixels; drives partial repaint (I10).
  • Backend the hardware abstraction: DRM/KMS, headless, nested.
  • DRM / KMS the kernel display API: connectors, CRTCs, encoders, planes.
  • Atomic modeset / TEST_ONLY / page-flip the tear-free state-application API (I15).
  • GBM the buffer allocator bridging GL/EGL to KMS scanout.
  • EGL / GLES2 the GPU context + rendering API of the GLES2 renderer.
  • EGLImage a dmabuf imported as a GL texture (zero-copy).
  • Plane (primary/overlay/cursor) a hardware compositing layer; direct scanout + hw cursor use these.
  • Direct scanout assigning a surface's buffer directly to a plane, bypassing compositing (§19).
  • Buffer age frames since a reused fb was last current; drives partial repaint (§19).
