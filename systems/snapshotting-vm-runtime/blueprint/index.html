341 — Snapshotting VM Runtime from Scratch

Project Number: 341

Project Name: Snapshotting VM Runtime from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build a managed bytecode VM runtime that can checkpoint (snapshot) and restore its full execution state — GC'd heap, value stack, call frames, registers/PC, threads/fibers, GC metadata, and external-resource handles — so a running program can be frozen to bytes and resumed exactly, on the same or a fresh process. Snapshots enable three workloads: boot-from-snapshot (skip init, sub-millisecond cold start, à la V8 startup snapshots / JVM CRaC / Firecracker microVM resume), fork-from-snapshot (clone a warmed VM N ways), and time-travel/checkpoint (roll back to a saved point; feeds #344 deterministic replay).

In scope: a small stack bytecode VM (svm-vm) over a precise GC'd heap (svm-heap); a stop-the-world safe point for a consistent capture; deterministic, position-independent serialization of the whole object graph (pointer→offset relocation), value stack, call frames, PC, thread/fiber state, GC metadata (svm-snap); restore that rebuilds the heap (offset→pointer relocation) and resumes (svm-restore); incremental + copy-on-write snapshots via dirty-page tracking and base+overlay delta chains (svm-cow); an external-resource manifest with reopen/lazy/virtualize/fail policies plus deterministic time/RNG (svm-resource); a self-describing, content-hashed, SemVer'd snapshot format with cross-version migration and load-time validation of untrusted snapshots (svm-format); a svm CLI + svmd daemon.

Explicit non-goals (PhaseDeferred("FINAL_BLUEPRINT §X.Y")): JIT compilation of bytecode (§12.x — interpreter only; snapshotting JIT code caches is a stretch); live cross-machine migration with open TCP connection hand-off (§Threat; we virtualize/reconnect, not splice sockets); full POSIX process checkpoint à la CRIU (§1 non-goal — we own the VM, not arbitrary processes); GPU/accelerator state (§Deferred); distributed consensus on snapshot epochs (§Scalability — single-node authority); language frontend/parser — bytecode is the input contract (§8).

Deployment model: library crates (svm-*) + svm CLI (run/snapshot/restore/fork/inspect/verify/migrate) + optional svmd daemon (snapshot-on-signal, boot-from-snapshot pool). Consumes compiled bytecode modules; produces .svm snapshot files. Feeds #344 (deterministic replay), serverless cold-start pools, test-time checkpointing.

Target users: runtime/VM engineers; serverless/edge platform engineers chasing cold-start latency; systems learners building the #31→#32→#341 lineage (VM → GC → snapshotting); reliability engineers wanting checkpoint/restore.

Phase 0 deliverable (crates/modules):

  1. svm-types — Value, ObjRef, Obj, Bytecode, Frame, VmError, Heap handles, opcode enum.
  2. svm-heap — GC'd object heap (bump + free-list regions, mark-sweep GC, object headers).
  3. svm-vm — bytecode interpreter core: value stack, call frames, PC, dispatch loop, threads/fibers scheduler skeleton.
  4. svm-cli (svm) — load a bytecode module, svm run <module> to completion.

Later phases unlock: safe point + consistent capture (§Phase 1), object-graph serialization with pointer relocation (§Phase 2), stack/frame/PC/thread capture+restore (§Phase 3/4), snapshot format + versioning + integrity (§Phase 5), resource manifest + reopen/virtualize (§Phase 6), copy-on-write/incremental + delta chains (§Phase 7), boot-from-snapshot fast start (§Phase 8), cross-version migration + untrusted-snapshot validation (§Phase 9), hardening/fuzz/differential/determinism (§Phase 10), soak/perf/release (§Phase 11).

Timeline: Phase 0 = 6–14 weeks; full = 7–11 months (the object-graph relocation correctness and the external-resource policy matrix are the long poles).

Recommended language: Rust (edition 2021, ≥1.78). Rationale (locked ADR-001): (a) we serialize raw heap memory + pointers and must control layout precisely — Rust gives #[repr(C)], explicit alignment, and unsafe pointer arithmetic without a host GC moving objects under us; (b) no host GC — the VM's own GC is the only collector, so capture sees a stable layout (a host GC would relocate the heap mid-snapshot); (c) ownership/borrow model encodes the "heap is frozen during capture" invariant; (d) snapshots are untrusted on load → memory safety + cargo fuzz/Miri on the loader (the loader is the attack surface, §Threat); (e) deterministic, allocation-controlled serialization for byte-identical snapshots (I3); (f) shares the heap/GC model with #31/#32/#244 in one workspace.

Prerequisites: VM/interpreter internals (dispatch, stack, frames — #31); garbage collection (mark-sweep, object headers, root sets — #32/#244); serialization + pointer-relocation/swizzling (persistent-object / image techniques); OS memory (mmap, mprotect, dirty-page / soft-dirty tracking); content hashing + format versioning; concurrency safe points (stop-the-world, handshake); Rust ownership, unsafe, repr(C).

2. Why Build This

  • Unique knowledge: how a live program becomes bytes and back — the inverse of loading. Pointer↔offset relocation, root enumeration, "consistency requires the world to stop," and "some state cannot be serialized (fds, time)" are the irreducible lessons of every checkpoint/restore system.
  • Historical/architectural: Smalltalk/Lisp image-based persistence (the original "snapshot the whole world"); V8 startup snapshots (boot a heap from a blob); JVM CRaC + Project CRaC; CRIU (Linux process C/R); Firecracker/QEMU microVM snapshots (resume a VM in <10 ms); Emacs unexec. This project distills the common core: stop, serialize the graph position-independently, externalize resources, restore, resume.
  • Engineering muscles: consistent-snapshot protocols (safe points); position-independent serialization (relocation tables, swizzling); incremental snapshots (dirty-page tracking, COW, delta chains — the same idea as #111 backup dedup and DB incremental backup); the external-resource problem (the part nobody warns you about) — fds/sockets/timers/RNG/wall-clock are not memory and need explicit policy; format versioning + migration; validating hostile serialized data on load.
  • Production concepts: cold-start latency (the entire serverless motivation), checkpoint/restore for fault tolerance, fork-for-isolation, deterministic logical time across restore, content-addressed integrity.
  • Cross-links: #31 VM (the interpreter we snapshot), #32 / #244 GC (heap + root sets + the collector whose metadata we capture), #111 Backup/Snapshot (content addressing, delta chains, dedup — directly reused for COW snapshots), #153 (memory allocator/arena patterns underneath the heap), #344 Deterministic Replay (snapshot = a replay checkpoint; restore + replay-log = reconstruct any moment), #50 (event loop / async runtime whose timer + I/O state needs the resource manifest).
  • Calibration: after this you can reason about any checkpoint system — "where's the safe point, how are pointers relocated, what happens to the open socket, is the format versioned, is the loader hardened" — and debug "the restored VM diverged from the captured one."

What Mastery Looks Like

  • Consistent-state capture (Phase 1): you can design and justify a stop-the-world safe-point protocol — which poll locations are necessary, what "consistent" means for a running bytecode VM, and why the pause SLO bounds the choice of poll density.
  • Pointer relocation (Phases 2 & 4): you can implement and audit the full ptr→offset / offset→ptr relocation pipeline, explain why position independence is non-negotiable across ASLR restores, and identify every class of corruption (OOB reloc, mid-object reloc, double-swizzle) and its mitigation.
  • Resource externalization (Phase 6): you can enumerate every category of un-serializable external state, assign the correct policy from {Reopen, ReopenAtOffset, LazyReconnect, Virtualize, Fail, Drop}, and explain why a raw fd in the heap is a guarantee of silent corruption on restore.
  • Incremental / COW snapshotting (Phase 7): you can reason about dirty-page tracking (mprotect vs soft-dirty), explain when a base+overlay chain must be compacted, and detect the soundness failure (a missed dirty page) using a full-vs-incremental differential.
  • Sub-millisecond cold start (Phase 8): you can explain the mmap + lazy-swizzle-on-fault boot model (Texas persistent store / Catalyzer lineage), identify the race conditions in lazy relocation, and predict when lazy equals or exceeds eager cost.
  • Loader hardening (Phase 9 & 10): you can write a total validator that rejects every class of malformed snapshot with a typed error (never a panic), cap attacker-controlled counts before allocation, and design a structure-aware fuzzing campaign for the loader.
  • Format versioning and migration (Phase 5 & 9): you can design a SemVer-gated snapshot format, write a minor-migration rule, and reason about what changes require a major bump versus what can be migrated — the same skill that applies to any long-lived binary protocol.
  • Differential correctness (Phase 10): you can implement the capture≡restore equivalence oracle (snapshot → restore → re-snapshot → byte-diff) and use it to surface silent divergences that no unit test would catch — the master technique for validating any serialization-deserialization round-trip.

Per-box: Loader — parses a bytecode module into the initial heap + main frame (the only "from source" path; everything else resumes a snapshot). Interpreter core (svm-vm) — the runtime whose state we capture: value stack, call frames (locals + return PC), program counter, threads/fibers + a cooperative scheduler; its dispatch loop polls safe points at back-edges/calls/allocations so capture can stop the world deterministically. Heap (svm-heap) — regions (bump-allocate young, free-list old), #[repr(C)] object headers (type tag, size, GC mark, forwarding slot), a mark-sweep collector, and the root set (the bridge: stack slots + frame locals + globals are GC roots and serialization roots). Resource table (svm-resource) — every external handle (fd, socket, timer, RNG stream, wall-clock reads) goes through a ResourceHandle id, never a raw fd in the heap, so capture sees ids and the manifest, not un-serializable kernel state. Safe point — a stop-the-world handshake that quiesces all threads at known-good points so the heap + stacks are internally consistent (no half-mutated object, no in-flight push) before capture. svm-cow — mprotect/soft-dirty dirty-page tracking + a dirty bitmap so incremental snapshots store only changed pages (base+overlay chains, reusing #111's delta-chain idea). Capture/serializer (svm-snap) — enumerates roots, traces the object graph, assigns each object a stable file offset, relocates pointers to offsets, and emits the heap image + relocation table + stacks/frames/PC + thread table + GC metadata + resource manifest. Snapshot format (svm-format) — the on-disk .svm: magic, SemVer, a section table, per-section CRCs, a whole-file content hash, and the embedded manifest; self-describing so a loader can validate before trusting. Restore/resume (svm-restore) — validates the untrusted snapshot first, maps the heap image, relocates offsets→pointers, rebuilds stacks/frames/PC/threads, reopens/virtualizes resources per the manifest, and resumes the dispatch loop exactly where capture stopped.

6. Design Principles

  1. Consistency requires a safe point. Capture only at a stop-the-world point where every thread is quiesced at a poll and no object is half-mutated. Tradeoff: pause time. Operational: pause is an SLO (≤ 10 ms). Violation: a snapshot mid-push or mid-object-write restores a corrupt heap/stack.
  2. Position independence (relocation, not addresses). The heap image stores offsets, never live pointers; restore relocates offsets→pointers at the new base. Violation: a snapshot only restorable at the exact same virtual address — useless across processes/ASLR.
  3. No raw external handles in the heap. Every fd/socket/timer/RNG/clock access goes through a ResourceHandle id + the manifest. Violation: a serialized fd number is meaningless on restore → use-after-free of a kernel resource.
  4. Determinism. Same VM state + same epoch ⇒ byte-identical snapshot (stable iteration order, no addresses, no timestamps in the image body). Violation: non-reproducible snapshots; impossible to diff/dedup; breaks #344 replay.
  5. The loader is an attacker. Every .svm is untrusted: validate magic/version/section table/CRC/content-hash/relocation bounds before dereferencing anything. Violation: a crafted snapshot becomes arbitrary memory corruption on restore (the project's #1 CVE class).
  6. Restore ≡ capture (semantic equivalence). A restored VM must continue indistinguishably from the captured one (same heap graph, stacks, PC, logical time). Verified differentially (I1). Violation: silent divergence — the worst bug, because it looks like it worked.
  7. Self-describing, versioned format. Every snapshot carries its format version, section table, and manifest; loaders refuse unknown majors and migrate compatible minors. Violation: an unreadable snapshot after a runtime upgrade.
  8. Incremental by dirty pages, not full rewrites. Steady-state snapshots store only changed pages over a base (COW + delta chain). Tradeoff: chain length vs restore cost (periodic compaction). Violation: O(heap) cost per checkpoint kills time-travel/frequent checkpoints.
  9. Monotonic logical time. A logical clock (and seeded RNG state) is captured and restored so time never goes backward across restore and replays deterministically. Violation: timers fire twice / negative durations / non-deterministic restore.
  10. Capture is read-only on the frozen world; restore writes once. Capture never mutates VM state (so it can be retried/aborted); restore builds the VM atomically then flips to running. Violation: a failed capture that left the heap modified can't be resumed.
  11. GC and snapshot share the root set + object model. The collector's roots/headers/forwarding fields are exactly what the serializer traces. One object model, not two. Violation: the snapshot misses an object the GC keeps (or vice versa) → dangling refs.
  12. Validate the graph, not just the bytes. Beyond CRC/hash: every relocated offset must point within the heap image to a valid object header of the declared type; cycles allowed, dangling forbidden. Violation: a structurally-valid-but-graph-invalid snapshot crashes later, far from the load.
  13. Streaming, bounded memory. Capture streams sections to the writer; restore can mmap + lazily page/relocate. Never require a full second heap copy. Violation: OOM snapshotting a heap that barely fit.
  14. Stable, SemVer'd snapshot + VM API. The .svm format and the Value/Obj/Frame schema are versioned; #344 and tooling depend on them. Violation: every release orphans old snapshots and breaks consumers.

8. Domain Model

8.1 Bytecode VM model (the runtime we snapshot)

A small stack machine. Bytecode module = constant pool + function table + code. Values are NaN-boxed-or-tagged; heap objects are GC'd.

Value   := Int(i64) | Float(f64) | Bool(b) | Nil | Ref(ObjRef)   ; ObjRef = heap object id/offset
Obj     := Str(bytes) | Array(Vec<Value>) | Map(Vec<(Value,Value)>)
         | Closure{fn:FnId, upvalues:Vec<Value>} | Struct{tag, fields:Vec<Value>}
         | ResourceRef(ResourceHandle)            ; the ONLY bridge to external state (I7)
Frame   := { fn:FnId, pc:u32, locals:Vec<Value>, ret_pc:u32, base_sp:u32 }
Thread  := { id, stack:Vec<Value>, frames:Vec<Frame>, status:{Running|Parked|Done}, fiber:Option<FiberId> }
VmState := { heap:Heap, threads:Vec<Thread>, globals:Vec<Value>, scheduler, logical_clock:u64, rng:RngState }

8.2 Object header & heap layout (normative, #[repr(C)])

ObjHeader { tag:u16, flags:u8, gc_mark:u8, size:u32, fwd:u32 }   ; fwd = forwarding/offset slot (reused by snapshot)
Heap      = regions[]; each region = mmap'd page run; objects are header+payload, 8-byte aligned
Root set  = { every Value::Ref in: thread stacks, frame locals, globals, scheduler queues }

The fwd/size/tag fields are shared by the GC (mark-sweep) and the snapshotter (offset assignment) — one object model (principle 11).

8.3 Snapshot format grammar (.svm, EBNF)

snapshot     := magic version flags section_count section_dir section* content_hash
magic        := "SVM\x01"                                  ; 4 bytes
version       := u16 major u16 minor                       ; SemVer (I11)
section_dir  := { kind:u16, offset:u64, len:u64, crc32c:u32 }*   ; one entry per section (I10)
section      := header_sec | heap_image | reloc_tbl | thread_tbl | gc_meta | resource_manifest | overlay_meta
header_sec   := { vm_abi:u32, heap_layout:u32, page_size:u32, base_hint:u64, epoch:u64, parent_hash:Opt<Hash32> }
heap_image   := { region_count, regions: { vaddr_hint:u64, len:u64, page_bytes[] }* }   ; offsets, no live ptrs (I4)
reloc_tbl    := { count:u64, entries: { at_offset:u64 }* }  ; each location holding an offset to swizzle (I5)
thread_tbl   := { count, threads: { id, status, stack_off:u64, stack_len, frames:{fn,pc,locals_off,ret_pc,base_sp}* }* }
gc_meta      := { mark_color:u8, region_free_lists, alloc_cursors, gc_epoch:u64 }
resource_manifest := { count, resources: { handle_id:u32, kind:u16, policy:u8, descriptor:bytes }* }   ; (I7)
overlay_meta := { base_hash:Hash32, dirty_page_count:u64, dirty_pages: { region:u16, page_idx:u32 }* }  ; incremental (§7)
content_hash := BLAKE3-256 over all preceding bytes                                   ; (I10)

8.4 Snapshot / restore state machine

RUNNING ──request snapshot──► REQUESTED ──safe-point reached (all threads quiesced, I6)──► FROZEN
FROZEN ──capture(read-only, I8)──► [enumerate roots → trace graph → assign offsets → relocate → emit sections]
        └─ on error/abort ──► RUNNING (state unchanged, I8/I10)
FROZEN ──capture done──► WRITING ──fsync + content-hash──► PERSISTED ──resume threads──► RUNNING

(restore, fresh process)
LOADED(bytes) ──validate magic/version/CRC/hash (I2,I10,I11)──► VERIFIED
VERIFIED ──map heap image + relocate offset→ptr (I5) ──► HEAP_READY
HEAP_READY ──rebuild stacks/frames/PC/threads──► VM_READY
VM_READY ──reopen/virtualize resources per manifest (I7) + restore clock (I9)──► RESOURCES_READY
RESOURCES_READY ──resume dispatch at saved PC──► RUNNING   (≡ captured VM, I1)
any validation failure ──► REJECTED (typed LoadError, no partial VM)

8.5 Worked example — capture & restore a tiny program

program: build map {"k": [1,2,3]}, open a file (ResourceHandle 7), park at a yield point.
VM state at safe point:
  heap: O0=Str("k"); O1=Int-array[1,2,3]; O2=Map[(Ref O0 → Ref O1)]; O3=ResourceRef(h=7)
  globals[0]=Ref O2 ; thread0.stack=[Ref O3]; thread0.frames=[{fn:main, pc:42, locals:[Ref O2]}]
  logical_clock=1000 ; rng=seed-state-X ; resource 7 = file "/data/in.log" @ offset 4096
capture (offsets assigned in trace order):
  O0@0x00  O1@0x18  O2@0x40  O3@0x60   (8-byte aligned, header+payload)
  reloc_tbl: [O2.key→0x00, O2.val→0x18, globals[0]→0x40, stack[0]→0x60, locals[0]→0x40]
  resource_manifest: { h7, kind=File, policy=ReopenAtOffset, descriptor={path:"/data/in.log", off:4096} }
  thread_tbl: t0 {stack_off, frames:[{fn:main,pc:42,locals_off,...}]}; logical_clock=1000; rng=X
restore (new process, base=0x7f...0000):
  map heap image; for each reloc entry: *at = base + stored_offset   (offset→ptr, I5)
  O2.key→&O0, O2.val→&O1, globals[0]→&O2, stack[0]→&O3, locals[0]→&O2
  resource: reopen "/data/in.log", lseek 4096, bind to h7 (policy ReopenAtOffset, I7)
  logical_clock=1000 (≥, I9); rng=X; resume thread0 at pc=42  → continues identically (I1)

8.6 Malformed / failure-path examples

  • Truncated section (dir says len=N, file has N-10) → LoadError::Truncated at validate, REJECTED before any deref (I2).
  • Reloc offset out of bounds (at_offset or stored offset ≥ heap_image len) → LoadError::BadReloc, REJECTED (I5) — the classic exploit; caught before swizzle.
  • Reloc points into the middle of an object (not a header boundary) → header-tag check fails → LoadError::BadReloc (I5/I12).
  • Content hash mismatch (one bit flipped) → LoadError::IntegrityFail, REJECTED (I10).
  • Major version newer than runtime → LoadError::Unsupported, refuse (no guessing, I11); minor-older → migrate (§9).
  • Resource manifest references a missing file under Reopen policy → restore fails the resource per policy (fail vs lazy vs virtualize); reported, VM not resumed half-wired (I7).
  • Capture requested but a thread never reaches a safe point (tight native-ish loop) → timeout → unsafe_capture telemetry, capture aborted, VM keeps RUNNING unchanged (I6/I8).
  • Cycle in object graph (O1→O2→O1) → allowed; trace uses visited-set; reloc handles back-references (not an error).
  • Overlay base hash mismatch (incremental snapshot's parent not the expected base) → LoadError::BaseMismatch, refuse to apply delta (§7).
  • Logical clock in snapshot < host wall clock on restore → clamp logical_clock up, log time_regression is not triggered (logical, not wall) — wall-clock reads go through resource policy (I9).

Phase 0 — VM Core: Bytecode Interpreter, GC'd Heap, Threads/Fibers Skeleton, CLI

0.1 Objectives

A runnable stack bytecode VM: repr(C) object heap with mark-sweep GC + root set, value stack + call frames + PC, a cooperative scheduler skeleton (single thread + parkable fibers), and svm run <module>. Establish the position-independent reference model (ObjRef = id/offset, never raw ptr) from day one so snapshotting is possible later (I4).

0.2 Detailed Implementation Steps

  • svm-types: Value, ObjRef, Obj, ObjHeader(repr(C)), Frame, Thread, opcode enum, VmError. [ADR-001 Rust layout control; ADR-004 ObjRef=offset; Wilson survey §5.Book-1 object headers]
  • svm-heap: region allocator (mmap'd page runs, bump cursor), object headers, mark-sweep GC, RootSet enumeration over stacks/frames/globals. [Wilson survey §5.Book-1; GC Handbook §5.Book-2; ADR-003; principle 11 shared root set]
  • svm-vm: bytecode loader (module → heap + main frame), dispatch loop (push/pop/add/load/store/call/ret/jmp/jz/new_array/new_map/new_str/yield/halt), call frames, PC. [Smith & Nair §5.Book-3 Ch.3–4; Dragon Ch.7 §5.Book-4; ADR-002 stack VM]
  • Cooperative scheduler skeleton: a run queue, yield parks a fiber (a heap object holding a stack+frames). [ADR-015; principle 11 (fibers are roots)]
  • svm-cli run. [ADR-017]

0.3 Deliverable

svm run prog.svmbc executes a real bytecode program (loops, arrays, maps, function calls, fibers that yield/resume) to completion; GC reclaims unreachable objects.

0.4 Acceptance Criteria

  • A fixture program (fib, map-build, fiber-pingpong) produces the expected result.
  • GC: live-object count after collection matches reachable set; no use-after-free (Miri clean on heap).
  • ObjRef is an id/offset everywhere; grep finds 0 raw *mut Obj in Value (enforces I4 precondition).
  • ≥ 50 M simple ops/s single-thread (baseline).

0.5 Conformance Fixtures

conformance/capture/_vm/{fib,arrays,maps,closures,fiber_pingpong}.svmbc + golden stdout; _gc/{cycle,unreachable} (GC correctness).

0.6 Pitfalls

  • Raw pointers leaking into Value → snapshotting impossible later; lock ObjRef=id now (I4).
  • GC root set missing a source (scheduler queue, fiber stacks) → premature free; the same miss later corrupts snapshots (principle 11).
  • Object header not repr(C)/unaligned → relocation math breaks in §2.
  • Mutable aliasing of heap during interpretation → Rust borrow fights; use an arena/index model.

0.7 Performance Concerns

Computed-goto-style match dispatch; bump-allocate hot path; RootSet iteration O(roots). No alloc per simple op. Heap regions page-aligned for §7 dirty-tracking.

0.8 Edge Cases

Empty program; deep recursion (stack growth); GC under allocation pressure; fiber that never yields; integer overflow in bytecode (wrapping/trap defined).

0.9 Failure Analysis

A heap/GC bug = wrong program result and a corrupt future snapshot. Detection: GC reachability assertion; Miri. Blast radius: the VM instance.

0.10 Operational Notes

Metrics: gc_runs, live_objects, heap_bytes, ops_per_sec, fibers. svm --version prints VM ABI + format version. The heap layout + root set defined here are the foundation every later phase serializes.

Phase 1 — Safe Point: Stop-the-World Handshake & Consistent Capture Window

1.1 Objectives

A safe point mechanism: the dispatch loop polls at back-edges/calls/allocations; on a snapshot request all threads/fibers quiesce at a poll, producing a window where the heap + every stack/frame is internally consistent (no half-written object, no in-flight push) — the precondition for any correct capture (I6).

1.2 Detailed Implementation Steps

  • Insert safe-point polls in the dispatch loop (loop back-edges, call entry, alloc). [§5.Paper-9 "GC safe points" HotSpot/V8 engineering notes; ADR-005; I6 type-enforced quiescence]
  • request_safe_point(): set a flag; each running thread, at its next poll, parks and acks; capture waits for all acks (handshake), with a timeout. [Chandy-Lamport §5.Paper-12 consistent-snapshot intuition, specialized to STW single-node; ADR-005]
  • Define "consistent": between bytecode instructions, with no partially-constructed object on the heap and no torn stack write. [principle 1; I6; Wilson survey §5.Book-1 "mutator consistency window"]
  • SafePointToken: proof that the world is frozen; required by capture() (type-enforced I6). [ADR-005; Rustonomicon §5.Book-8 type-state pattern for unsafe invariants]

1.3 Deliverable

svm snapshot --dry-run <module> runs the program, requests a safe point, confirms all threads quiesced and the heap is consistent, then resumes — no bytes written yet.

1.4 Acceptance Criteria

  • All threads reach a safe point within the timeout on cooperative workloads.
  • A consistency assertion (no object with size/tag mid-write; stack invariants hold) passes at the safe point on all fixtures.
  • capture() cannot be called without a SafePointToken (compile-time, I6).
  • Resume after a dry-run safe point continues identically (I8 precursor).

1.5 Conformance Fixtures

conformance/capture/safepoint/{multi_fiber_quiesce,alloc_heavy,timeout_tight_loop}.

1.6 Pitfalls

  • A loop with no poll → never reaches a safe point → capture hangs; ensure every back-edge polls (bounded poll distance).
  • Polling too often → interpreter overhead; balance poll density.
  • Capturing mid-allocation (object header written, payload not) → inconsistent heap; alloc is a safe-point boundary, never split.
  • A parked fiber's stack still referenced as a root → must be enumerable at the safe point (principle 11).

1.7 Performance Concerns

Safe-point poll = one predictable branch (flag check); near-free when not snapshotting. Pause time = max thread time-to-poll (bounded by poll distance) → SLO ≤ 10 ms (§4).

1.8 Edge Cases

Single-thread VM (trivial quiesce); a fiber blocked on a resource (must be parked at a safe point); nested calls at the poll; snapshot requested while GC is running (coordinate: GC is itself a safe region).

1.9 Failure Analysis

Failure to quiesce → no consistent window → capture aborts (VM unchanged, I8). Detection: quiescence timeout → unsafe_capture. A capture mid-mutation (if the safe point were buggy) → corrupt snapshot, caught later by differential (I1) — so the safe point is the first line of defense.

1.10 Operational Notes

Metrics: safepoint_latency_ms, quiesce_timeouts, poll_density. Pause is an SLO. Tracing: a span from request → all-acked → resume. This is the consistency foundation; §2 serializes the frozen world it produces.

Phase 2 — Object-Graph Serialization: Trace, Offset Assignment, Pointer→Offset Relocation

2.1 Objectives

Serialize the frozen heap into a position-independent image: trace the live object graph from roots, assign each object a stable file offset, copy headers+payloads into the image, and emit a relocation table recording every location that holds a reference so restore can swizzle offset→pointer. 0 live pointers in the image (I4); deterministic order (I3).

2.2 Detailed Implementation Steps

  • svm-snap::trace: DFS/BFS from RootSet, visited-set for cycles, stable iteration order (by root index then field order) for determinism (I3). [Wilson 1991 POS §5.Paper-7 pointer swizzling strategies; Wilson survey §5.Book-1 root enumeration; principle 2; I3/I4]
  • svm-snap::offsets: assign each visited object an 8-byte-aligned offset; build ObjRef→offset map. [Wilson 1991 POS §5.Paper-7 eager offset assignment; ADR-004 ObjRef model; principle 2]
  • svm-snap::relocate_out: copy each object into the heap-image buffer; for every Value::Ref field, write the offset (not the id/ptr) and record the field's location in the reloc_tbl (I4/I5). [Wilson 1991 POS §5.Paper-7 + Texas persistent store §5.Paper-8 relocation table; Rustonomicon §5.Book-8 unsafe pointer math; ADR-006; I4/I5]
  • Emit heap_image + reloc_tbl sections (format §8.3). [V8 snapshot src §5.RefImpl-3; ADR-006/007; §8.3 format grammar]

2.3 Deliverable

svm snapshot --heap-only <module> writes a heap-image + reloc-table (no stacks/resources yet); svm inspect dumps objects + relocations; re-capturing the same state is byte-identical (I3).

2.4 Acceptance Criteria

  • Heap image contains 0 values that look like live pointers (reloc audit scans, I4).
  • Every reloc entry's at_offset and stored offset are within the image and land on object-header boundaries (I5).
  • Object count in image = GC-live count (I12).
  • Re-capture of identical state ⇒ identical bytes (I3); cycles serialize without infinite loop.

2.5 Conformance Fixtures

conformance/capture/graph/{linear,tree,cycle,shared_subgraph,deep}, determinism/recapture_identical, malformed/_reloc_oob (negative, exercised in restore §4).

2.6 Pitfalls

  • Non-deterministic trace order (HashMap iteration) → non-reproducible snapshot (I3); use ordered traversal.
  • Forgetting a reference field in an object variant → dangling ref on restore (I5); exhaustive match per Obj variant.
  • Self/back references → must record the offset even for already-visited objects.
  • Alignment/padding mismatch between in-memory and image layout → relocation lands mid-object.
  • ResourceRef traced as a normal object → must be redirected to the manifest (handled §6), not into the heap image.

2.7 Performance Concerns

Trace is O(live objects + refs); single pass copy; streaming write (principle 13) — no second full heap copy. Reloc table is O(reference fields). Sequential image write = good IO.

2.8 Edge Cases

Empty heap; single object; a million tiny objects (reloc-table size); a giant single object (a huge array); deeply nested cycles; an object referenced from many roots (offset assigned once).

2.9 Failure Analysis

A missed/incorrect reloc = a dangling or wild pointer on restore — the corruption class. Detection: reloc audit (I4), restore-time bounds/header check (I5), differential (I1). Blast radius: the whole restored heap. This phase + §4 are the correctness heart.

2.10 Operational Notes

Metrics: objects_serialized, reloc_entries, image_bytes, capture_ms. svm inspect --graph (Graphviz of object graph). The image+reloc-table format is frozen here (SemVer, ADR-027); §4 is its exact inverse.

Phase 3 — Stack / Frame / PC / Thread & Fiber State Capture

3.1 Objectives

Capture the execution state on top of the heap graph: every thread's value stack, call frames (locals, return PC, base SP), the program counter, fiber/scheduler state, the logical clock, and RNG state — all with references relocated like the heap (I4). Together with §2 this is a complete, position-independent VM snapshot (minus resources/format wrapper).

3.2 Detailed Implementation Steps

  • svm-snap: walk each Thread → serialize stack (Values, Refs→offsets), frames ({fn, pc, locals→offsets, ret_pc, base_sp}), status. [Dragon Ch.7 §5.Book-4 activation records; ADR-002 stack VM; I4 (Refs→offsets); I5 (reloc coverage)]
  • Serialize scheduler: run queue, parked fibers (each fiber's stack/frames captured like a thread). [ADR-015 cooperative scheduler; principle 11 (fibers are VM objects = heap roots); I3 (deterministic queue order)]
  • Serialize logical_clock + RngState into header_sec (I9). [rr §5.Paper-10 deterministic replay + logical time; ADR-014; I3/I9]
  • Emit thread_tbl + gc_meta (mark color, free lists, alloc cursors) sections. [GC Handbook §5.Book-2 GC metadata; ADR-003; I12 (completeness)]
  • Extend the reloc table to cover stack/local reference locations (I5). [Wilson 1991 POS §5.Paper-7; ADR-006; I5]

3.3 Deliverable

svm snapshot <module> (no resources yet) writes a complete VM image (heap + stacks + frames + PC + threads + gc-meta + clock/rng); svm inspect shows thread/frame state.

3.4 Acceptance Criteria

  • All thread stacks/frames captured; reference slots relocated (I4/I5).
  • Logical clock + RNG present and deterministic (I3/I9).
  • GC metadata sufficient to resume the collector (free lists, cursors consistent with the heap image, I12).
  • Re-capture byte-identical (I3).

3.5 Conformance Fixtures

conformance/capture/exec/{deep_stack,many_frames,parked_fibers,scheduler_queue,clock_rng}, golden thread tables.

3.6 Pitfalls

  • Stack slots holding Refs not relocated → dangling on resume (I5); treat the stack like heap fields.
  • base_sp/ret_pc invalid after relocation → frame corruption on resume; these are indices/PCs (already position-independent) — but validate ranges.
  • Capturing a fiber mid-switch → must be at a safe point (I6); fibers park only at yields.
  • RNG/clock not captured → non-deterministic restore (I9).
  • GC mark color drift (collector mid-cycle) → coordinate with safe point (GC is a safe region, §1).

3.7 Performance Concerns

Stacks/frames are small vs heap; capture O(stack depth × threads). Negligible next to heap trace. Sequential append to the image.

3.8 Edge Cases

A thread with an empty stack; max recursion depth; thousands of parked fibers; a thread in Done status (skip resume); scheduler queue ordering (deterministic, I3).

3.9 Failure Analysis

A bad frame/PC = the restored VM executes wrong code → diverges (I1). Detection: differential capture≡restore (the equivalence harness, §Phase 10). Blast radius: that thread, then the whole VM. PC/frame ranges validated on load (I5/I12).

3.10 Operational Notes

Metrics: threads_captured, frames_captured, stack_depth_max. svm inspect --threads. Stacks+frames+PC+clock+rng complete the capturable state; §4 reverses §2+§3 into a running VM.

Phase 4 — Restore: Validation, Heap Mapping, Offset→Pointer Relocation, Resume

4.1 Objectives

The exact inverse of §2+§3: validate the (untrusted) image (I2), map the heap into memory at a fresh base, relocate offset→pointer for every reloc entry (I5), rebuild threads/stacks/frames/PC and the scheduler, restore clock/RNG/GC-meta, and resume the dispatch loop so the VM continues identically (I1).

4.2 Detailed Implementation Steps

  • svm-restore::validate: check reloc bounds + header boundaries + object counts before any deref (I2/I5/I12) — total parser. [principle 5 "loader is an attacker"; ADR-016; §5.Paper-7 Wilson 1991 (validate before swizzle); I2/I5/I12]
  • svm-restore::map: allocate/mmap the heap image at base B; reconstruct regions. [Drepper §5.Book-9 mmap/TLB behavior; ADR-013; principle 13 streaming/bounded memory; I4]
  • svm-restore::relocate_in: for each reloc entry, *at = B + stored_offset (offset→ptr); rebuild ObjRefs; verify each target is a valid object header of the declared kind (I5). [Texas persistent store §5.Paper-8 swizzle-on-load; Rustonomicon §5.Book-8 unsafe pointer math; ADR-006/021; I5; principle 12 graph validation]
  • svm-restore::rebuild: reconstruct Threads (stacks/frames/PC/status), scheduler, globals, logical_clock (≥ captured, I9), RngState, GC metadata. [Dragon Ch.7 §5.Book-4 activation record rebuild; ADR-014/015; I9 monotonic clock]
  • svm-restore::resume: enter the dispatch loop at each thread's saved PC. [Smith & Nair §5.Book-3 Ch.4 VM resumption; I1 restore≡capture; ADR-002]

4.3 Deliverable

svm restore <snapshot.svm> (resources stubbed/Drop) brings a captured VM back and continues to completion, producing the same output as if it had run uninterrupted (round-trip, I1).

4.4 Acceptance Criteria

  • Round-trip equivalence (I1): run program P to a safe point, snapshot, restore in a fresh process, finish → output identical to running P uninterrupted, across all fixtures.
  • Relocation: every offset→ptr lands on a valid header (I5); object count matches (I12).
  • Logical clock monotonic (I9); RNG continues the same sequence (I3).
  • Restore ≤ 50 ms for the medium fixture (§4).

4.5 Conformance Fixtures

conformance/restore/{roundtrip_fib,roundtrip_map,roundtrip_fibers,roundtrip_deep}, roundtrip/_recapture_after_restore_identical (snapshot→restore→snapshot ⇒ byte-identical, I1/I3).

4.6 Pitfalls

  • Dereferencing before validating → the exploit; validate fully first (principle 5, I2).
  • Off-by-base relocation (forgetting B, or double-adding) → wild pointers; centralize the B + offset swizzle.
  • Endianness / pointer-width mismatch (snapshot from a different ABI) → reject on header vm_abi (I11).
  • Resuming at a stale PC (function table changed) → guard with the bytecode/ABI hash in the header.
  • Partial restore on error → must produce no VM at all (atomic, principle 10); fail to REJECTED.

4.7 Performance Concerns

Eager relocation = O(reloc entries); mmap avoids a copy (principle 13). Lazy/swizzle-on-fault relocation deferred to §8 (boot fast path). Validation is O(image) but cache-friendly (sequential).

4.8 Edge Cases

A snapshot with no threads (just a heap — for boot images); a Done thread (skip); cyclic graph (back-refs swizzle correctly); a snapshot at the very first instruction (pc=0); the largest fixture heap (relocation cost).

4.9 Failure Analysis

Restore divergence (I1) is the worst bug — looks successful, behaves wrong. Detection: the differential round-trip harness is the primary oracle (§Phase 10). Relocation corruption → caught at validate (I5) or as a crash (fuzz, I2). Blast radius: the entire restored VM. Recovery: reject + keep the prior snapshot.

4.10 Operational Notes

Metrics: restore_ms, relocations_applied, validate_fail, restore_divergence(→0). Tracing: validate→map→relocate→rebuild→resume spans. svm verify <snapshot> runs validate without resuming (operator pre-check). This phase closes the capture/restore loop; everything after raises robustness, speed, and scope.

Phase 5 — Snapshot Format, Versioning, Integrity, svm inspect/verify

5.1 Objectives

Wrap the sections in the self-describing .svm container: magic, SemVer version, section directory, per-section CRC-32C, whole-file BLAKE3 content hash, embedded header/manifest, optional zstd on the heap image. Enforce integrity + version checks on load (I10/I11) and provide inspect/verify tooling.

5.2 Detailed Implementation Steps

  • svm-format: write/read magic (SVM\x01), {major,minor}, section directory ({kind,offset,len,crc32c}), content hash trailer. [ELF note conventions §5.Specs; ADR-007/009; I11 version gate]
  • Per-section CRC-32C on write; verify on read (I10) — locates corruption to a section. [ADR-008; I10; §5.Paper-14 BLAKE3 + CRC-32C]
  • BLAKE3-256 content hash over the whole file (minus the trailer) (I10); content-addressing key (ADR-029, link #111). [§5.Paper-14 O'Connor et al. 2020 BLAKE3; ADR-008/029; I3 determinism]
  • Version gate: refuse major>runtime; accept ≤ minor (migrate path §9) (I11). [SemVer 2.0.0 §5.Specs; ADR-009/027; I11; §5.Paper-15 Preston-Werner]
  • Optional zstd of the heap-image section before hashing (deterministic, ADR-028). [ADR-028; I3 (hash on-disk bytes)]
  • CBOR for header/manifest sections (self-describing, ADR-007). [CBOR/RFC 8949 §5.Specs; ADR-007]

5.3 Deliverable

svm snapshot emits a versioned, hashed .svm; svm verify <f> checks magic/version/CRC/hash and prints the section map; svm inspect <f> dumps header + sections + manifest without restoring.

5.4 Acceptance Criteria

  • Round-trip: write → verify → read → restore unchanged (I1).
  • Corrupt one byte → verify fails with the offending section (CRC) and a hash mismatch (I10).
  • Major-newer snapshot refused; minor-older accepted (I11).
  • Content hash is stable for identical state (I3) and matches across re-captures.

5.5 Conformance Fixtures

conformance/format/{good,bad_crc,bad_hash,bad_magic,major_newer,minor_older,zstd_image}.

5.6 Pitfalls

  • Hashing before vs after compression inconsistency → pick one (hash the on-disk bytes, ADR-028).
  • Section offsets overlapping / out of file → validate the directory before reading sections (I2).
  • Timestamps/paths in the body → non-deterministic hash (I3); keep volatile data out of the hashed body.
  • CRC vs hash redundancy confusion → CRC = per-section locality, hash = whole-file authenticity/identity; both kept.

5.7 Performance Concerns

BLAKE3 is fast (multi-GB/s); CRC-32C hardware-accelerated; zstd optional (size vs CPU tradeoff). Hashing streams alongside the write.

5.8 Edge Cases

Empty snapshot (just header); a single huge section; zstd ratio ~1 (incompressible); unknown section kind (skip if non-critical, #[non_exhaustive], ADR-027); truncated trailer.

5.9 Failure Analysis

A corrupt/forged snapshot reaching restore = corruption/exploit; the hash/CRC gate (I10) + structural validate (I2/I5) stop it. Detection: verify. Blast radius: contained at load (REJECTED). Forensics: section map + which CRC failed.

5.10 Operational Notes

Metrics: integrity_fail, version_unsupported, snapshot_bytes, compression_ratio. svm verify is the operator/CI pre-flight. The .svm format is SemVer-frozen here (ADR-027); migration (§9) handles minor evolution.

Phase 6 — External Resource Manifest: Reopen / Lazy / Virtualize Policies, Time & RNG

6.1 Objectives

Solve the crux: external state (fds, sockets, timers, RNG, wall-clock, mmap'd regions) is not serializable. Route all of it through ResourceHandle indirection + a resource manifest with per-resource policies ({Reopen, ReopenAtOffset, LazyReconnect, Virtualize, Fail, Drop}), CRaC-style before_checkpoint/after_restore hooks, and deterministic logical time + seeded RNG (I7/I9).

6.2 Detailed Implementation Steps

  • svm-resource: every fd/socket/timer/RNG/clock access goes via a ResourceHandle; the heap holds only the id (Obj::ResourceRef) — 0 raw fds serialized (I7). [CRIU §5.Paper-1 fd handling; CRaC §5.Paper-6 ResourceHandle pattern; ADR-011; I7; principle 3]
  • On capture: call before_checkpoint() per resource → ResourceDescriptor{kind, policy, blob} → resource_manifest section. [JVM CRaC org.crac §5.RefImpl-4 before_checkpoint hook; ADR-011/012; I7]
  • Policies: Reopen (file by path), ReopenAtOffset (file + lseek), LazyReconnect (socket: reconnect on first use), Virtualize (in-VM pipe/null), Fail (refuse restore if absent), Drop (discard, e.g. a closed temp). [CRIU §5.Paper-1 resource policy taxonomy; ADR-012; Appendix G policy matrix]
  • Time: a logical clock (captured/restored, monotonic, I9); wall-clock reads go through a clock resource (policy: continue logical, or re-sync to host on restore — documented). [rr §5.Paper-10 logical time + determinism; ADR-014; I3/I9]
  • RNG: seeded PRNG state captured in header_sec → deterministic stream across restore (I3/I9). [rr §5.Paper-10 deterministic RNG; ADR-014; I3]
  • On restore: after_restore(descriptor) reopens/reconnects/virtualizes per policy. [CRaC §5.Paper-6 after_restore; ADR-011/012; I7; principle 3]

6.3 Deliverable

A program that opens a file + a socket + a timer + uses RNG can be snapshotted and restored: file reopened at offset, socket lazily reconnected, timer rearmed against the logical clock, RNG continues the same sequence.

6.4 Acceptance Criteria

  • 0 raw fds/sockets in the heap image (scan, I7); every external resource has a manifest entry.
  • After restore: file reads continue from the captured offset (ReopenAtOffset); socket reconnects on first use (LazyReconnect); RNG produces the identical next values (I3); logical clock ≥ captured (I9).
  • A Fail-policy resource that's missing → restore rejected, no half-wired VM (I7).

6.5 Conformance Fixtures

conformance/resources/{file_reopen,file_offset,socket_lazy,timer_rearm,rng_continue,virtualize_pipe,fail_missing,drop_temp}.

6.6 Pitfalls

  • A raw fd captured by accident (a code path bypassing ResourceHandle) → meaningless on restore (I7); the indirection must be the only path.
  • Wall-clock determinism — true wall clock can't be deterministic; separate logical time (deterministic, I9) from wall time (a resource with a re-sync policy).
  • Socket reconnect mid-protocol → application-level resumption is the app's job; we restore the handle + a "reconnect needed" signal, not TCP sequence numbers (documented non-goal).
  • Timer double-fire across restore → rearm against the logical clock, not wall (I9).
  • mmap'd file region → captured as a resource (path+offset+prot), re-mmap'd on restore; anonymous mmap is heap (already captured).

6.7 Performance Concerns

Resource manifest is tiny (counts of handles). before/after hooks are per-resource, off the hot path. Lazy reconnect defers cost to first use (good for fork fan-out where most clones never touch the socket).

6.8 Edge Cases

A resource opened then closed before capture (not in manifest); duplicated fds (one handle, refcount); a handle referenced from multiple objects; stdin/stdout/stderr (virtualize or reopen); a timer already fired (don't rearm).

6.9 Failure Analysis

The #1 semantic bug source: a resource that "restored" but points at the wrong external state (stale offset, wrong file). Detection: resource-conformance fixtures + the descriptor blob is validated on restore. Blast radius: that resource's I/O. Recovery: policy-driven (Fail aborts; Lazy retries; Virtualize degrades).

6.10 Operational Notes

Metrics: resources_captured, unmanaged_resource(→0), reopen_fail, lazy_reconnects, time_regression(→0). Hooks are the integration point for app code (CRaC-style). docs/format/resources.md documents every policy. This is what makes snapshots usable for real programs, not just pure-compute ones.

Phase 7 — Copy-on-Write & Incremental Snapshots: Dirty-Page Tracking, Delta Chains

7.1 Objectives

Make frequent snapshots cheap: track dirty pages (via mprotect+SIGSEGV write-protection, or Linux soft-dirty PTEs), and capture incremental overlays that store only changed pages over a content-addressed base snapshot (base+overlay delta chains, reusing #111's chain idea). Enables time-travel and high-frequency checkpointing (principle 8).

7.2 Detailed Implementation Steps

  • svm-cow::dirty: a per-region page bitmap; after a base snapshot, write-protect heap pages (mprotect PROT_READ); on write fault, mark the page dirty + unprotect (or read soft-dirty from /proc/self/pagemap). [Linux soft-dirty PTEs §5.Paper-11; Love §5.Book-6 mprotect/SIGSEGV; GC Handbook §5.Book-2 write barriers; ADR-010; principle 8]
  • svm-cow::overlay: incremental capture writes only dirty pages + an overlay_meta section ({base_hash, dirty page list}). [Plank et al. §5.Paper-13 incremental checkpointing; ADR-010/029; principle 8; I1 chain≡full]
  • svm-cow::chain: base → overlay → overlay …; restore applies the base then each overlay in order (content-hash-linked, ADR-029). [Plank et al. §5.Paper-13 delta chains; Lambda on-demand loading §5.Paper-4 page-level dedup; ADR-029; link #111]
  • Chain compaction: periodically materialize a chain into a fresh base (bound restore cost). [Plank et al. §5.Paper-13 checkpoint compaction; ADR-029; principle 8 tradeoff]
  • COW fork: svm fork maps a base snapshot's pages COW into a new VM (ADR-030). [Tanenbaum §5.Book-5 mmap COW; ADR-030; §Phase 8 boot fast-path; Firecracker §5.Paper-2 fork model]

7.3 Deliverable

svm snapshot --incremental --base <hash> writes a small overlay (only dirty pages); svm restore applies base+overlays; svm fork <base> boots N VMs sharing read-only pages COW; chain compaction on demand.

7.4 Acceptance Criteria

  • Incremental snapshot size ≤ 5% of base on a steady workload (§4); restore of base+overlays ≡ a full snapshot at that point (I1).
  • Dirty-page tracking catches every mutation (no missed dirty page → no stale data on restore).
  • Overlay with a wrong base hash → rejected (BaseMismatch, §8.6).
  • Fork: N clones share base pages until written (COW); each diverges correctly.

7.5 Conformance Fixtures

conformance/incremental/{overlay_small,chain_apply,compaction,base_mismatch,fork_cow_divergence,missed_dirty_negative}.

7.6 Pitfalls

  • A missed dirty page (a write the tracker didn't see) → silent stale data on restore → divergence (I1); the tracker must be sound (every write faults or is soft-dirty-flagged).
  • Page size vs object size mismatch → an object spanning pages; track at page granularity, snapshot whole dirty pages.
  • Long delta chains → slow restore; compact periodically (tradeoff, principle 8).
  • mprotect overhead on every page after a base → batch re-protection; soft-dirty avoids per-fault cost where available.
  • Forking and then snapshotting a clone → its base is the shared base + its own overlay.

7.7 Performance Concerns

mprotect/SIGSEGV: one fault per first-write-per-page (amortized); soft-dirty: a pagemap scan at capture (no per-write cost). Incremental capture O(dirty pages) ≪ O(heap). Fork COW: O(1) to fork, pages copied lazily on write (kernel COW).

7.8 Edge Cases

A page dirtied then reverted (still captured — conservative); a write-heavy workload (overlay ≈ base → fall back to full); first snapshot (no base → full); a region grown since base (new pages all dirty); compaction during active dirty-tracking.

7.9 Failure Analysis

A soundness bug in dirty-tracking = restored VM has stale pages = divergence (I1). Detection: a "full vs base+overlay" differential (apply chain, compare to a full snapshot of the same state). Blast radius: the diverged pages → whole VM. This is the subtlest correctness risk after relocation.

7.10 Operational Notes

Metrics: dirty_pages, overlay_bytes, chain_length, compactions, fork_count, cow_faults. svm inspect --chain <hash> shows the base→overlay lineage. Incremental + COW is what makes time-travel (#344) and serverless fork-pools (§8) practical.

Phase 8 — Boot-from-Snapshot: Fast Cold Start, Lazy Relocation, Working-Set Prefetch

8.1 Objectives

Turn restore into a sub-millisecond cold start: pre-build a warmed snapshot (post-init heap), then boot by mmap-ing the image and lazily relocating pages on first access (swizzle-on-fault, Texas/Catalyzer-style) instead of eager full relocation — plus optional working-set prefetch. The serverless motivation (Firecracker/Lambda SnapStart) realized (§4: p50 ≤ 1 ms).

8.2 Detailed Implementation Steps

  • svm restore --boot <warmed.svm>: mmap the heap-image read-only/COW; defer relocation. [Catalyzer §5.Paper-3 lazy page-in; Firecracker §5.Paper-2 fast resume; ADR-013/030; principle 13]
  • Lazy relocation: install a fault handler (or a relocation-on-first-touch barrier); a page is relocated (offset→ptr) the first time it's accessed (principle 13). [Texas persistent store §5.Paper-8 swizzle-on-fault page-grained; ADR-013; I4 position independence; §Phase 4 eager relocation is the correctness reference]
  • Working-set hint: capture records hot pages (from a profiling run) → prefetch + pre-relocate them so the first request avoids faults. [Catalyzer §5.Paper-3 working-set prefetch; Lambda on-demand loading §5.Paper-4 dedup + lazy load; Drepper §5.Book-9 prefetch/TLB behavior]
  • svmd boot pool: keep N pre-mmap'd VMs warm; serve a request by handing one out (or COW-forking from a single base, ADR-030). [Firecracker §5.Paper-2 snapshot pool; ADR-018/030; §4 p50 ≤ 1 ms target]
  • Skip program init entirely — the warmed snapshot is the initialized state. [V8 startup snapshot §5.Paper-5; Catalyzer §5.Paper-3; §4 boot-from-snapshot cold start target]

8.3 Deliverable

svm restore --boot of a warmed snapshot reaches "ready to serve" in sub-ms (p50 ≤ 1 ms); svmd serves requests from a boot/fork pool; cold-start latency dashboard.

8.4 Acceptance Criteria

  • Boot-from-snapshot p50 ≤ 1 ms, p99 ≤ 5 ms for a ≤ 64 MB warmed heap (§4).
  • Lazy relocation correctness: a lazily-relocated VM ≡ an eagerly-relocated one (I1) — relocation order doesn't change semantics.
  • Working-set prefetch reduces first-request faults measurably.
  • Fork-pool clones are independent (COW divergence, §7).

8.5 Conformance Fixtures

conformance/restore/boot/{warmed_small,warmed_64mb,lazy_eq_eager,prefetch,pool_fork}.

8.6 Pitfalls

  • Lazy relocation race (two threads touch the same unrelocated page) → relocate-once with a per-page latch; idempotent swizzle.
  • A pointer relocated twice (eager + lazy paths overlap) → mark relocated pages; centralize the swizzle (shared with §4).
  • mmap base differs each boot (ASLR) → relocation must be base-relative every time (I4 — the whole point of offsets).
  • Prefetching the wrong working set → faults on the hot path; profile per workload.
  • Sharing a mutable page COW across forks → kernel COW handles it; ensure no eager write touches all pages.

8.7 Performance Concerns

mmap = no read syscall on the cold path (page-cache backed); first-touch fault + relocate is the dominant cost → minimized by prefetch. Boot is O(touched pages), not O(heap). Fork is O(1) + lazy COW. This phase is where §4's latency targets are met.

8.8 Edge Cases

A snapshot bigger than RAM (demand-paged from disk); a workload that touches the whole heap immediately (lazy ≈ eager); booting on a machine with a different page size (reject or re-page); a cold page-cache (first boot slower — measure warm vs cold).

8.9 Failure Analysis

A lazy-relocation correctness bug = divergence that only manifests on a specific access pattern → caught by lazy_eq_eager differential (I1) + fuzzing access orders. Blast radius: the VM. A boot latency regression = an SLO miss (perf-regression gate, §11).

8.10 Operational Notes

Metrics: boot_p50_us, boot_p99_us, first_touch_faults, prefetch_hits, pool_size, forks_served. svmd exposes pool depth + boot latency. This is the headline capability — fast cold start from a warmed VM image; lazy relocation + COW fork are the mechanisms.

Phase 9 — Cross-Version Migration & Validation of Untrusted Snapshots

9.1 Objectives

Two robustness pillars: (1) migrate snapshots across compatible format/schema versions (minor evolution) so old snapshots survive runtime upgrades (I11); (2) deeply validate untrusted snapshots — beyond CRC/hash — so a crafted .svm cannot corrupt the restored VM (I2/I5/I12, principle 5/12). The loader is hostile-input territory.

9.2 Detailed Implementation Steps

  • svm-migrate: registered migration rules per {from_minor → to_minor} (e.g., a new Obj variant, an added header field, a renamed section); migrate on load when minor < runtime (I11). [SemVer 2.0.0 §5.Specs; ADR-009/027; §5.Paper-15 Preston-Werner; I11]
  • Refuse major mismatches (no silent reinterpretation, I11). [ADR-009; I11; Firecracker §5.RefImpl-2 versioned format refusal]
  • svm-restore::validate hardening: section-directory bounds, no overlapping sections, reloc at_offset + stored offset within heap_image, each reloc target on an object-header boundary with a declared, valid tag (I5), object-count consistency (I12), thread/frame PC/index ranges, manifest well-formedness. [CRIU §5.Paper-1 image validation; principle 5/12; ADR-016/020; I2/I5/I12]
  • Graph validation (principle 12): a structurally valid image whose graph dangles must be rejected before resume. [principle 12; I5/I12; ADR-016; Wilson 1991 POS §5.Paper-7 graph integrity]
  • Resource-bound checks: cap object/section/reloc/thread counts vs declared sizes (anti-resource-exhaustion). [ADR-016/020; principle 5; §Phase 10 fuzz; I2]

9.3 Deliverable

svm migrate <old.svm> --to <minor> upgrades a snapshot; svm verify performs full structural+graph validation; restoring a v1 snapshot on a v2 runtime works via migration; a crafted malformed snapshot is rejected with a precise LoadError.

9.4 Acceptance Criteria

  • A snapshot written by minor N restores on runtime minor N+1 (migrated) and is semantically identical (I1/I11).
  • Major mismatch refused (I11).
  • Every malformed-fixture (malformed/**) → a typed LoadError, never a panic/OOB/crash (I2), never a corrupt VM (I5/I12).
  • Validation cost bounded (O(image), no quadratic blowup on crafted input).

9.5 Conformance Fixtures

conformance/migration/{v1_to_v2,new_obj_variant,added_field,major_refuse}, malformed/{reloc_oob,reloc_midobject,bad_tag,overlap_section,count_mismatch,dangling_ref,huge_counts,truncated}.

9.6 Pitfalls

  • Migration that loses information → a lossy upgrade; migrations must be total + tested round-trip where reversible.
  • TOCTOU in validation (validate then the bytes change) → validate a frozen buffer; restore from the validated view only.
  • Trusting any field before validating it (e.g., a count used to allocate) → cap counts vs file size first (principle 5).
  • A "valid" graph that's semantically wrong (right structure, wrong type at an offset) → tag-check every relocation target (I5/I12).
  • Migration chains (v1→v2→v3) → apply rules in sequence, hash-verify each step.

9.7 Performance Concerns

Validation is a single O(image) pass (sequential, cache-friendly); migration is O(objects touched by the rule). Both off the boot fast path (validate-then-cache, or trust internally-produced snapshots within a session).

9.8 Edge Cases

A snapshot from the future (major+1) — refuse; a snapshot from minor 0 to current — full migration chain; an empty/min snapshot; a snapshot that's all one giant object (validation must still bound work); adversarial deeply-nested graph (visited-set on validate too).

9.9 Failure Analysis

An unvalidated field reaching a deref = the exploit (arbitrary write via a crafted reloc offset). Detection: fuzz the loader (I2, §10) + every malformed fixture. Blast radius: the restoring process. This + §10 fuzzing are the security core. Migration failure → reject + keep the original.

9.10 Operational Notes

Metrics: migrations_applied, validate_reject{reason}, bad_reloc, object_count_mismatch. docs/format/svm-format.md documents the version-compat matrix. SECURITY.md: "every .svm is untrusted." This phase makes snapshots durable across upgrades and safe to load from anywhere.

Phase 10 — Hardening: Fuzz the Loader, Differential Capture≡Restore, Determinism

10.1 Objectives

Lock the three load-bearing invariants under adversarial and randomized conditions: I2 (loader never panics on arbitrary bytes — fuzz), I1 (restore ≡ capture — differential round-trip across randomized programs + access orders), I3/I9 (capture determinism + monotonic time). Miri-clean relocation unsafe.

10.2 Detailed Implementation Steps

  • cargo fuzz: load_snapshot(&[u8]), relocate, section_dir, manifest — arbitrary bytes + structure-aware (mutate valid snapshots). [ADR-020; I2; principle 5; Rustonomicon §5.Book-8 unsafe + fuzz discipline]
  • Differential capture≡restore harness: generate random VM states (random programs run to random safe points) → snapshot → restore → re-snapshot → assert byte-identical (I1/I3); also assert observable output identical to uninterrupted runs. [rr §5.Paper-10 differential replay oracle; ADR-019; I1/I3; principle 6]
  • lazy_eq_eager + chain_eq_full differentials (§8/§7) under randomized access/dirty patterns. [Texas §5.Paper-8 lazy vs eager swizzle equivalence; Plank §5.Paper-13 incremental correctness; ADR-013/010; I1]
  • Determinism harness: capture the same state twice ⇒ identical bytes (I3); restore + step ⇒ identical RNG/clock trajectory (I9). [ADR-014/026; I3/I9; rr §5.Paper-10 deterministic record/replay]
  • Miri over relocate_in/relocate_out (pointer math, unsafe); ASAN on the heap + mmap. [ADR-021; Rustonomicon/RustBelt §5.Book-8; I4/I5 unsafe pointer correctness]
  • Resource-exhaustion fuzzing: crafted huge counts → bounded rejection (§9). [ADR-016/020; principle 5 (cap counts before alloc); §Phase 9 hardening]

10.3 Deliverable

Green fuzz (24h, 0 crashes) on all loader targets; a passing randomized capture≡restore corpus; Miri-clean; a determinism report.

10.4 Acceptance Criteria

  • 0 panics/OOB across ≥ 1e9 fuzz execs on load_snapshot (I2).
  • Randomized capture→restore→re-capture byte-identical and output-identical over ≥ 10k generated states (I1/I3).
  • lazy_eq_eager and base+overlay ≡ full hold under randomized access/dirty orders (I1).
  • Miri: no UB on the relocation path; logical clock monotonic on every restore (I9).

10.5 Conformance Fixtures

fuzz/corpus/*, conformance/determinism/{recapture_identical,rng_trajectory,clock_monotonic}, roundtrip/randomized_states.

10.6 Pitfalls

  • with_capacity(attacker_count) in the loader → OOM DoS; cap vs file size (principle 5, §9).
  • Recursive validation/relocation on a crafted deep graph → stack overflow; iterate with an explicit worklist + visited set.
  • Nondeterminism leaking in (HashMap order, a stray timestamp, pointer-derived hash) → flaky recapture_identical; hunt every source (I3).
  • A fuzz "crash" that's actually a slow unit (huge alloc) → timeouts + count caps.
  • Miri false-negatives if the unsafe is hidden behind FFI → keep relocation pure-Rust + Miri-visible.

10.7 Performance Concerns

Fuzz/differential off the critical path (CI budget). Count caps are O(1). The determinism + equivalence harnesses are the real correctness investment.

10.8 Edge Cases

All-zero / all-0xFF snapshot bytes; a valid header with a garbage body; a snapshot truncated at every section boundary; a program that allocates the entire heap then snapshots; randomized fiber interleavings at the safe point.

10.9 Failure Analysis

A loader crash = RCE/DoS risk for anyone restoring an untrusted snapshot → blocks release (the hard SLO). A capture≡restore divergence = a silent correctness bug → blocks release. Both gated in CI. Forensics: the minimized fuzz input / the diverging state are saved.

10.10 Operational Notes

Metrics: fuzz_crashes(0), restore_divergence(0), nondet_snapshot(0), time_regression(0). Fuzzing + the equivalence harness are the primary safety + correctness SLOs. This phase is the gate every other phase's code must pass.

Compatibility & Versioning

Scalability Analysis

The unit is a VM instance; scaling axes are heap size (capture/restore/relocation cost grows O(live objects); dirty-tracking + boot grow O(touched pages)) and fork fan-out (one warmed snapshot → N booted VMs via COW, O(1) per fork + lazy page copy — the serverless multiplier). Bottlenecks: (1) STW pause = max thread time-to-safe-point (bounded by poll density); (2) relocation = O(reference fields) — the dominant capture/restore CPU cost; (3) delta-chain length = restore cost (bounded by compaction); (4) dirty-page tracking faults under write-heavy workloads (mitigated by soft-dirty). Ceilings: a single huge object (giant array) is captured atomically (no sub-object streaming in v1); a snapshot bigger than RAM is demand-paged on boot (mmap). No shared mutable state across instances, no distributed coordination → fork-pool scaling is linear with cores/memory. Snapshot storage scales as content-addressed blobs (dedup across overlays, link #111). Single-node snapshot authority; cross-machine migration is reconnect-based, not state-splicing (non-goal).

Mental Models & First Principles

MM1 — Consistency = a quiesced observer. A snapshot is consistent if and only if the observer (serializer) sees a world where no mutation is in flight. Any STW safe-point protocol is a specialization of this principle. Predicts: a capture mid-allocation produces a corrupt heap. Without it: you write a serializer that races with the mutator and gets heisenbug corruption. Applied: §Phase 1 (safe-point handshake), principle 1.

MM2 — Pointer = address; offset = identity. In a running process, a pointer encodes both object identity and address. After ASLR restores in a new process, the address is meaningless but the identity survives as an offset. Every serializable object graph must separate these two. Predicts: a snapshot storing raw pointers is unreloadable after ASLR. Without it: you store addresses in the image and every restore at a different base silently corrupts references. Applied: §Phase 2 ptr→offset, §Phase 4 offset→ptr, I4, ADR-004.

MM3 — The loader is the attack surface. A deserializer that trusts its input is a remote code execution vector: a crafted relocation table can direct *at = B + crafted_offset to an arbitrary address. Predicts: every unchecked count or offset is a potential OOB write. Without it: you write a fast path that dereferences reloc entries before bounds-checking them. Applied: §Phase 4/9 validate-before-deref, principle 5, I2/I5, ADR-016.

MM4 — External state is never memory. File descriptors, sockets, timers, and clocks are kernel state registered in the OS process table, not values you can copy. Their ids (fd numbers) are meaningless after exec/fork into a new process. Predicts: a heap scan that finds a raw integer that "looks like" a valid fd will silently use the wrong kernel resource on restore. Without it: you serialize fd=7 into the heap and restore it into a process where fd 7 is something else. Applied: §Phase 6 resource manifest, I7, ADR-011, principle 3.

MM5 — Incremental snapshots are sound only if the dirty-tracking is sound. An incremental snapshot stores "only changed pages." If one dirty write escapes the tracker, the overlay is missing data, and the restored VM silently diverges. Predicts: a single unkept mprotect fault or a soft-dirty reset miss corrupts the incremental chain. Without it: you assume page-protection is infallible and never test chain≡full differential. Applied: §Phase 7 dirty-page tracking, I1, ADR-010.

MM6 — Lazy relocation is correct iff swizzle is idempotent and per-page monotonic. Swizzle-on-fault relocates a page the first time it is touched. If two threads race to the same unswizzled page, or if a page is swizzled twice, pointers double-shift. Predicts: a lazy-relocation race produces wild pointers that only manifest under load. Without it: you implement lazy relocation without a per-page "already swizzled" latch. Applied: §Phase 8, I1 lazy_eq_eager differential, ADR-013.

MM7 — GC roots and snapshot roots are the same set. The GC starts from roots to find live objects; the serializer starts from roots to find all objects to snapshot. If these diverge, either the snapshot misses live objects (dangling refs on restore) or includes dead ones (snapshot bloat). Predicts: a root source added to the scheduler queue but not the serializer's root walk causes a dangling reference after restore. Without it: you maintain two separate root enumerations that drift apart. Applied: §Phase 0/2 shared RootSet, principle 11, I12.

MM8 — Logical time must be data, not wall clock. Wall-clock time is a property of the host machine at a moment in time, not of the VM's execution state. After restore, the host clock has advanced. Capturing wall-clock time means every restore sees time "jump forward," breaking timer logic and determinism. A logical clock is a VM-owned counter that advances only when the VM advances — it is data, safely captured and restored. Predicts: using SystemTime::now() in a timer will cause double-fires or negative durations after restore. Without it: timers use wall-clock deadlines and always fire immediately on restore. Applied: §Phase 3/6 logical_clock capture, I9, ADR-014.

MM9 — Format versioning must refuse before it migrates. A loader that tries to "guess" what a future-major snapshot means will silently misinterpret fields, producing a corrupt VM that passes validation. The safe invariant: refuse any major > runtime; accept minor ≤ runtime with a registered migration. Predicts: a loader that "ignores unknown fields" in a major-bumped snapshot will restore a VM whose relocation semantics changed silently. Without it: you add "backward compatibility" that silently reinterprets a new relocation format as the old one. Applied: §Phase 5/9, I11, ADR-009/027.

MM10 — The equivalence oracle beats unit tests for serialization correctness. Unit tests verify individual fields. The real failure mode is silent divergence — the VM looks restored but behaves differently two instructions later. The differential oracle (snapshot → restore → re-snapshot → byte diff AND output diff vs uninterrupted run) catches every class of serialization bug in one test. Predicts: any phase that skips the differential will ship a subtle relocation or stack-capture bug. Without it: you unit-test relocate_in in isolation and miss the interaction with frame locals. Applied: §Phase 10 capture≡restore differential, I1/I3, ADR-019.

Firecracker chose hypervisor-level checkpointing: the VMM pauses the vCPU, snapshots guest RAM + vCPU registers, and uses KVM's hardware dirty-log for incrementals. This wins when the workload is arbitrary binaries inside a Linux guest (you cannot modify them to add safe-point polls or resource hooks). This blueprint rejects it because we own the VM — adding safe-point polls in the dispatch loop gives a cleaner consistency window than ptrace-stopping arbitrary threads.

JVM CRaC chose to layer checkpoint/restore on top of the JVM's existing safe-point infrastructure (already used for GC). Resource hooks (beforeCheckpoint/afterRestore) are the same idea as this blueprint's Resource trait. CRaC wins for JVM workloads (Spring boot time drops from seconds to sub-100ms) because the JVM is the owner of all resource handles. This blueprint borrows the hook protocol (ADR-011) but builds a simpler, more explicit resource policy enum instead of relying on application-level hook registration.

CRIU chose OS-level process checkpointing: it uses ptrace, /proc, and netlink to reconstruct the entire mm + fd table + thread state of an arbitrary Linux process without any application cooperation. This wins for third-party binaries that cannot be modified. We reject it because (a) we own the VM and can design it to be snapshotable from the start, and (b) CRIU's scope (arbitrary OS state) makes the resource policy and validation far harder — the project's source code is ~100k lines vs our ~5k.

V8 startup snapshot chose to serialize only a quiescent, init-time heap (before any user code runs) into a blob that boots a fresh context. This wins for consistent, repeatable startup of a well-known built-in state — V8 saves ~100ms of JS runtime startup. We borrow the "boot from a warmed heap image" idea (§Phase 8, ADR-013/030) but extend it to a fully running VM with live resources, COW forks, and arbitrary-moment capture, which V8's snapshot was never designed for.

Back-of-Envelope Capacity Model

All derivations start from the System Constraints table (§4). Formula shown inline.

1. Heap image size (full snapshot)

  • Live heap: H = 256 MB (§4 full-capture target)
  • Overhead: reloc table + headers ≤ 20% (§4 snapshot-size constraint)
  • Reloc entries: assume 1 Ref per 24 B of live heap → 256 MB / 24 B = ~10.7M refs → 10.7M × 8 B/entry = ~85 MB reloc table
  • Section headers + CBOR sections: ~1 MB
  • Total snapshot ≤ 1.2 × 256 MB = 307 MB max (§4). At 85 MB reloc + 1 MB metadata + 256 MB heap ≈ 342 MB → high-ref-density workloads push the constraint; use zstd (ADR-028) or accept up to 1.33× for pointer-heavy heaps.

2. Capture bandwidth (streaming write)

  • Target: ≤ 100 ms for 307 MB
  • Required write bandwidth: 307 MB / 0.1 s = 3.07 GB/s → needs NVMe SSD or tmpfs; spinning disk (200 MB/s) → ~1.5 s, fails §4. For staging on tmpfs (in-memory): easily met.
  • STW portion (≤ 10 ms): relocation pass over reloc entries = 10.7M × ~10 ns/entry (cache-miss rate ~10%) = 107 ms — exceeds the STW budget at 100% cache-miss. Mitigation: keep reloc table size-bounded (streaming); sequential layout keeps miss rate low → ~10M × 1 ns = 10 ms if cache-warm.

3. Restore time (mmap + eager relocation)

  • Relocation cost: 10.7M entries × 5 ns (L1/L2 sequential) = 53 ms → within ≤ 50 ms only if cache pre-warmed; with mmap cold-start use lazy relocation (§Phase 8).
  • Validate pass: 307 MB sequential scan at ~10 GB/s = 30 ms. Within budget.
  • Total eager restore: ~53 ms (reloc) + ~30 ms (validate) = 83 ms → exceeds §4 ≤ 50 ms for cold mmap; lazy relocation reduces time-to-ready to mmap + hot-page fault latency.

4. Lazy boot latency (p50)

  • Target: p50 ≤ 1 ms for ≤ 64 MB heap (§4)
  • mmap syscall: ~10 µs
  • First request touches W = working-set pages before first meaningful work; for a warmed app: W ≈ 50–200 pages (empirical for serverless init functions)
  • Per-page fault + swizzle: ~5 µs (TLB miss + reloc of ~50 refs/page)
  • p50 = 10 µs mmap + 100 pages × 5 µs/page = 510 µs ≈ 0.5 ms ✓ (§4 ≤ 1 ms met)
  • p99: W ≈ 500 pages → 2.5 ms → misses §4 ≤ 5 ms only for very cold working sets; working-set prefetch (§Phase 8) bridges the gap.

5. Incremental snapshot size

  • Target: ≤ 5% of base on steady workload (§4)
  • Page size: 4 KB; 256 MB heap = 65,536 pages
  • Dirty pages at 5%: 0.05 × 65,536 = 3,276 pages × 4 KB = 13 MB overlay
  • Overlay metadata: 3,276 × 6 B (page index entry) = ~20 KB
  • Total incremental: ~13 MB vs 256 MB base = 5.1% — right at the target. For a write-heavy workload touching 20% of pages: 52 MB overlay = 20%, which triggers fall-back to full snapshot.

6. Safe-point pause (STW)

  • Target: p99 ≤ 10 ms (§4)
  • Poll density: every ~100 bytecodes (back-edge + call + alloc)
  • Instruction rate: 50M ops/s (§4 interpreter throughput floor)
  • Max time to next poll: 100 / 50M = 2 µs per thread
  • With 64 threads (§4 concurrency): pause waits for slowest thread; if all within 2 µs of a poll: p99 ≈ 2 µs × safety_factor(5000) ≈ 10 ms — the tight-loop (no poll) is the failure mode (§Phase 1 pitfall 1).

7. Relocation table memory (capture buffer)

  • ≤ 1.5× heap budget (§4)
  • Heap: 256 MB; reloc table: 85 MB; sections: 1 MB; streaming write buffer: 4–8 MB
  • Total capture working set: 256 + 85 + 8 ≈ 349 MB = 1.36× heap ✓ (< 1.5×)
  • In COW incremental mode: only dirty-page buffer + reloc delta → ~13 MB + ~3 MB = 16 MB additional ✓

8. Fork fan-out cost

  • mmap a 256 MB snapshot: ~10 µs (a handful of VMA operations, no data copy)
  • Per-fork COW cost: lazy — first write to each shared page triggers kernel copy (~5 µs/page)
  • For N = 1000 forks that each touch 100 pages before first diverge: 1000 × 100 × 5 µs = 500 s of CPU work, but parallelized across N cores → wall-time: 500 s / N_cores
  • Boot-pool at N = 10 pre-forked: 10 × 10 µs = 100 µs to set up the pool ✓

9. Delta chain restore cost

  • Chain length L; each overlay O(dirty pages) ≈ 13 MB
  • Restore = apply base (full load) + L × overlay (small sequential reads + page patch)
  • At L = 10 overlays: base restore (50 ms) + 10 × ~1 ms overlay apply = 60 ms → still within a relaxed budget; compact at L > 5 to keep <55 ms.

Hard Questions (Self-Examination)

  1. Why is "validate before deref" the single most important loader rule, and what two invariants (§7 Invariants) does violating it break simultaneously? — Synthesizes §Phase 4/9 validate steps, principle 5, I2/I5. A crafted at_offset that passes format checks but lands mid-object breaks both I2 (panic/OOB) and I5 (reloc target not on a header boundary).

  2. A program takes a snapshot, then its heap grows (new regions allocated), then takes an incremental snapshot. Which sections in the .svm format change, and how does the restore path handle the new regions? — Synthesizes §Phase 7 overlay_meta, §8.3 format grammar (heap_image region count), §Phase 4 restore map step. New regions appear as additional {vaddr_hint, len, page_bytes} entries in heap_image; all pages in a new region are "dirty" by definition; overlay_meta must include them.

  3. Why can the lazy relocation (§Phase 8) and the eager relocation (§Phase 4) produce byte-identical re-snapshots even though they relocate in different orders? — Synthesizes §Phase 8 lazy_eq_eager differential, I1/I3, MM2 (offset = identity). Both produce the same pointer graph because relocation is a function of (base, stored_offset) — order-independent. The re-snapshot traces in the same deterministic order (I3), so the image is identical.

  4. The safe-point STW pause SLO is p99 ≤ 10 ms. A workload has one tight loop with 10,000 iterations and no allocs, calls, or back-edges. What happens, and how would you fix it? — Synthesizes §Phase 1 pitfall 1, §Phase 1.7 performance, §4 STW constraint, ADR-005. The thread never reaches a safe-point poll → quiesce timeout → unsafe_capture, capture aborted (I8). Fix: insert a poll at the back-edge of every loop, regardless of body content.

  5. You receive a .svm snapshot where the content hash passes but the reloc table has an entry pointing to a valid offset within the heap_image that lands in the middle of a large Str object's payload. What error is returned, and which two validation checks catch it? — Synthesizes §Phase 4/9 validate, I5, §Appendix D, §8.3 reloc_tbl. The entry passes bounds check (I5 first condition) but fails the "target lands on an ObjHeader boundary with a declared valid tag" check (I5 second condition). Error: LoadError::BadReloc / E.BAD_RELOC.

  6. Explain why logical_clock = max(captured, prior) is the correct restore formula and not logical_clock = captured. What breaks if you use captured exactly and the host was suspended for an hour? — Synthesizes §Phase 3/6 logical_clock, I9, ADR-014, MM8. captured is fine for deterministic replay; but if the host wall time advanced and external code (e.g., a CRaC hook) re-syncs the clock, captured may be less than a previously-committed logical time in a log, breaking monotonicity. The formula is max(captured, prior_committed) — I9 guarantees non-regression.

  7. A socket with LazyReconnect policy is in the heap as ResourceRef(h=3). The program restores and immediately calls RESOURCE_OP h=3 send "hello". Trace the full call path from opcode to network bytes, naming every component. — Synthesizes §Phase 6 policy/hooks, Appendix G, §Phase 4 rebuild step, Appendix J RESOURCE_OP opcode. Dispatch loop → RESOURCE_OP → svm-resource::ResourceTable::get(h=3) → after_restore not yet called → lazy: call after_restore on first op → TCP reconnect → send "hello".

  8. Why does the blueprint choose cooperative (not preemptive) scheduling for fibers, and what would change in §Phase 1 if we switched to OS threads with preemptive scheduling? — Synthesizes §Phase 0/1, ADR-015, principle 1/11, §Phase 1 pitfalls. Cooperative: yield points are safe-point boundaries — we know exactly where a fiber's stack is frozen. Preemptive OS threads: safe-point must use a signal/handshake per thread (like HotSpot's) and every point in the bytecode must be a potential suspension point → more complex quiescence, signals can arrive mid-object-write without a consistent state guarantee.

  9. If two processes simultaneously restore the same base snapshot with COW fork, then both start writing, do they interfere? Name the kernel mechanism and the relevant ADR. — Synthesizes §Phase 7/8 COW fork, ADR-030, Tanenbaum §5.Book-5. No interference: the kernel COW (copy-on-write page fault) gives each process its own private copy of any page on first write. The base mmap'd pages are shared read-only until write — each fork gets an independent diverging heap. ADR-030.

  10. A migration rule upgrades Obj::Str from storing a raw Box<[u8]> to storing {bytes: Box<[u8]>, encoding: u8}. Is this a minor or major version bump? What would make it a major? — Synthesizes §Phase 5/9, Compatibility & Versioning, ADR-027, I11. Adding a field with a default (encoding=0 for UTF-8 legacy) is additive → minor (migrate on load, fill default). A major is required if the interpretation of existing bytes changes (e.g., encoding now changes what bytes[0] means — existing snapshots would be mis-decoded).

  11. The incremental overlay's base_hash doesn't match the base snapshot you have. What error is returned, what invariant it protects, and why can't you "just apply the overlay to the closest available base"? — Synthesizes §Phase 7, I1, §8.6 BaseMismatch, ADR-029. Error: LoadError::BaseMismatch. Invariant: the dirty-page set is relative to a specific base — applying it to a different base would overlay dirty data onto wrong clean pages, silently restoring a corrupted heap. The content-hash link in ADR-029 is the identity of the chain; breaking the chain breaks I1.

  12. Walk through the capture of a cycle O1→O2→O1 using the Phase 2 trace algorithm. How does the visited-set prevent infinite recursion, and what appears in the reloc table for the back-reference? — Synthesizes §Phase 2.2 trace, §8.5 worked example, I3/I4. visited-set: after visiting O1, mark visited; visit O2, add to visited; encounter O1 again → already visited, get its already-assigned offset. Back-reference in reloc_tbl: the field in O2 that references O1 gets its at_offset recorded; stored value = O1's offset. No infinite recursion because visited-set terminates the DFS.

  13. Why is BLAKE3 chosen over SHA-256 for the content hash, and in what deployment context would you switch to SHA-256? — Synthesizes §Phase 5, ADR-008, §5.Paper-14. BLAKE3: ~3× faster (multi-GB/s) than SHA-256, parallelizable, tree-mode allows incremental hashing. Switch to SHA-256: when storing snapshots in a FIPS-140-validated HSM or a government system that mandates FIPS-approved digests — BLAKE3 is not FIPS-approved as of 2025.

  14. A restored VM's restore_divergence metric fires once after 10,000 round-trips. What is the most likely root cause, and what is your debugging procedure? — Synthesizes §Phase 10, I1/I3, Failure Modes & Recovery (restore divergence), §Phase 2/3 pitfalls. Most likely: a non-determinism source in trace order (e.g., a HashMap used in the scheduler queue ordering — Appendix I). Debug: (1) binary-search the 10k to find the diverging state; (2) re-capture the state twice → if byte-diff appears, it's I3 (determinism); (3) check Appendix I checklist; (4) grep for HashMap in svm-snap/trace.rs.

  15. Why is capture() designed to be read-only on the VM state (I8), and what would break if it mutated the heap during capture? — Synthesizes §Phase 2 pitfall 5, I8, principle 10, §Phase 1 safe-point. Read-only capture means a failed or aborted capture leaves the VM in exactly its pre-capture state (resumable). If capture mutated objects (e.g., wrote offsets into live fwd fields without restoring them), an aborted capture would leave the heap with partially-overwritten headers — the VM could not resume safely. The fwd field trick: we read it for GC's forwarding, but we must restore it after capture finishes.

  16. A serverless workload snapshots 100 warm VMs and boots them as a fork-pool. Memory cost? Boot latency per request? How does this change if the VM heap grows from 64 MB to 256 MB? — Synthesizes §4 constraints, Back-of-Envelope #8/4, §Phase 7/8, ADR-030. 100 forks × 64 MB = 6.4 GB virtual, but COW physical = 64 MB base + per-fork dirty pages (lazy copy). Boot per request: ~0.5 ms (MM6 + §Back-of-Envelope #4). At 256 MB: virtual = 25.6 GB, physical base = 256 MB + dirty; p50 boot ≈ 2 ms (more working-set pages to fault in — may miss §4 ≤ 1 ms for large heaps).

  17. Explain the role of ObjHeader.fwd across two contexts: GC forwarding and snapshot offset assignment. Why is sharing this field safe? — Synthesizes §8.2 object header, §Phase 2 offset assignment, §Phase 0/2 GC design, principle 11. GC uses fwd during copying GC (forwarding pointer to new location); snapshot uses fwd to store the assigned file offset during capture. Safe because (a) this project uses mark-sweep (non-moving) GC — fwd is unused by GC during normal operation; (b) capture is read-only (I8) — after capture, fwd is restored to 0 (or never modified if we use a separate offset map).

  18. The snapshot format stores base_hint:u64 in the header. What is it used for, when can it be ignored, and what goes wrong if the loader always respects it? — Synthesizes §8.3 format grammar, §Phase 4/8, I4/ADR-004. base_hint is the virtual address where the heap was mmap'd during capture — provided as a hint to the loader to try the same base (reduces ASLR-induced relocation work for lazy swizzle). Can be ignored: always safe because offsets are position-independent (I4). If always respected: a hint from a 32-bit capture on a 64-bit restore fails (address out of range); or an ASLR system may refuse a fixed base, and the loader panics — must fall back gracefully.

Alternative Architectures (Roads Not Taken)

Alt-1 — Persistent Image (Smalltalk/Emacs unexec style)

 [VM process] ──write all memory pages to disk──► [image file]
 [reload]     ──mmap image at fixed base──────────► [resumed process]
 (no relocation: image is position-dependent; must reload at original base)

Regime where it wins: a single-process, single-machine runtime that always runs at a predictable virtual address (e.g., a classic Smalltalk image, Emacs unexec). Startup is O(1) memory mapping; no relocation overhead; simplest possible serializer. Zero-pointer-swizzle cost.

Real system: Smalltalk-80 (Squeak, Pharo image files), GNU Emacs unexec, original Lisp images (MACLISP, Interlisp).

Why this blueprint rejected it: requires a fixed virtual base address across restores. ASLR (modern OS default) invalidates position-dependent images every restore. Fork-pool (§Phase 8) requires multiple VMs at different addresses simultaneously — impossible with a fixed-base image. Cross-machine restore is impossible if the address space layouts differ. The offset-relocation design (ADR-004/006) adds ~10 ms relocation cost but buys full portability.

Alt-2 — Full Process Checkpoint (CRIU / DMTCP style)

 [host OS kernel]
    ├─ ptrace all threads (SIGSTOP)
    ├─ dump: /proc/pid/{maps,mem,fd,ns,...}
    ├─ serialize: all VMAs + kernel fd table via netlink
    └─► [criu image files]
 [restore]
    ├─ create new process with original PID/namespace
    ├─ restore all VMAs at original addresses
    └─ restore fd table via kernel helpers

Regime where it wins: checkpointing a third-party binary without source modification (a compiled C program, a Python runtime, a JVM). No cooperation from the application needed. Full POSIX state including PIDs, signals, IPC. Used for container live migration (Kubernetes pod migration), MPI job migration, forensic freezing.

Real system: CRIU (Checkpoint/Restore In Userspace), DMTCP (Distributed MultiThreaded Checkpointing), OpenVZ.

Why this blueprint rejected it: requires root and deep kernel cooperation (/proc + netlink). The implementation is ~100k lines of C handling hundreds of kernel edge cases. We own the VM — we designed it to be snapshotable. A VM-level checkpoint is ~5k lines, far safer, and does not require root or kernel patches. CRIU cannot do sub-millisecond restore (§4 p50 ≤ 1 ms) because it has to reconstruct the full OS process state; our lazy mmap path does.

Alt-3 — Whole-System Hypervisor Snapshot (Firecracker/QEMU style)

 [VMM / hypervisor]
    ├─ pause guest vCPU(s) via KVM ioctl
    ├─ snapshot: guest RAM + vCPU registers (VMSA) + device state
    ├─ dirty-page log via KVM_DIRTY_LOG (hardware-assisted)
    └─► [memory image + device state file]
 [restore]
    ├─ mmap guest RAM image
    ├─ restore vCPU via KVM_SET_REGS + KVM_SET_SREGS
    └─ restore device models (virtio queues, etc.)

Regime where it wins: checkpointing any arbitrary OS (Linux, Windows) and its applications as a unit. Hardware dirty-page tracking. Sub-100ms microVM restore (Firecracker SnapStart). Isolation: the guest cannot detect or interfere with snapshotting. Used for AWS Lambda cold-start reduction, container checkpointing in confidential computing.

Real system: Firecracker (AWS Lambda), QEMU snapshot, VMware vMotion.

Why this blueprint rejected it: requires a hypervisor (KVM), hardware virtualization, and VMM-level code. The "VM" in this blueprint is a language VM (a bytecode interpreter), not a hardware VM. Hypervisor snapshots include the entire guest OS — gigabytes of state — while we snapshot only the application's live objects (tens of MB). Hypervisor approaches cannot achieve sub-millisecond boot for a single application function because they must restore the full OS kernel context. Our lazy-mmap + swizzle-on-fault path (§Phase 8) reaches p50 ≤ 1 ms precisely because we skip the OS layer.

Alt-4 — Content-Addressed Functional Heap (Persistent Data Structure style)

 [immutable VM values]
    ├─ every "mutation" produces a new root hash
    ├─ heap = a content-addressed DAG of immutable nodes (like Git objects)
    ├─ snapshot = just the root hash (the whole history is the store)
    └─► [no serialization needed: the heap IS the snapshot]
 [restore]
    ├─ look up root hash in the object store
    └─ reconstruct the DAG lazily (lazy evaluation)

Regime where it wins: a purely functional language runtime (Haskell, Erlang-style) where mutation is rare and sharing is pervasive. Snapshots are nearly free (just record the root hash). Time-travel is trivial (keep all root hashes). Deduplication is automatic (shared subtrees). Used in content-addressed stores (Nix, Git, IPFS, some Erlang node checkpointing approaches).

Real system: Erlang/OTP hot-code upgrade + mnesia (partially), Nix store for reproducible environments, CAS-backed functional databases (Datomic).

Why this blueprint rejected it: our VM is imperative — mutation is the norm, not the exception. A content-addressed functional heap requires either an immutable value model (which breaks every SET_FIELD / STORE_LOCAL opcode) or a persistent data structure for every heap object (adds 3–5× memory overhead for structural sharing). The fast cold-start requirement (§4 p50 ≤ 1 ms) is incompatible with lazy DAG reconstruction over a content-addressed store. The dirty-page incremental approach (§Phase 7) achieves the result of "cheap incremental snapshot" without the immutability constraint.

Fork-from-snapshot Cloning a snapshot into N independent VMs (COW page sharing).
Time-travel Rolling a VM back to a saved checkpoint (feeds deterministic replay #344).
Safe point A point in execution (between instructions) where the VM state is internally consistent and capturable.
Stop-the-world (STW) Quiescing all threads/fibers at safe points so capture sees a frozen, consistent world.
Quiesce A thread reaching a safe point and parking, acknowledging the snapshot request.
Object graph The directed graph of heap objects linked by references (Value::Ref).
Relocation / swizzling Converting offsets↔pointers (capture: ptr→offset; restore: offset→ptr).
Position-independent image A heap image storing offsets, restorable at any base address (I4).
Relocation table The list of locations holding references that restore must swizzle (I5).
ObjRef A position-independent reference (id/offset), never a raw pointer.
Object header #[repr(C)] per-object metadata (tag, size, GC mark, forwarding slot).
Root set The references the GC (and serializer) start from: stacks, frame locals, globals.
Mark-sweep GC A collector that marks reachable objects from roots then sweeps the rest.
Forwarding slot A header field reused by the snapshotter to hold an object's assigned offset.
Value stack The operand stack of the bytecode interpreter.
Call frame An activation record: function id, PC, locals, return PC, base SP.
Program counter (PC) The index of the next bytecode instruction to execute.
Fiber A cooperatively-scheduled lightweight thread (a heap object holding a stack+frames).
Scheduler The VM component choosing which thread/fiber runs (cooperative here).
Logical clock A monotonic VM-internal time counter, captured/restored (I9), distinct from wall clock.
RNG state The seeded PRNG state, captured so the random stream is deterministic across restore.
Resource handle An indirection id for an external resource (fd/socket/timer/clock); the only heap↔external bridge (I7).
Resource manifest The snapshot section listing every external resource + its policy + descriptor.
Resource policy How a resource is restored: Reopen / ReopenAtOffset / LazyReconnect / Virtualize / Fail / Drop.
before_checkpoint / after_restore CRaC-style hooks to externalize a resource at capture and reopen at restore.
Heap image The raw serialized region bytes (offsets, no live pointers).
Section directory The .svm table of {kind, offset, len, CRC} describing each section.
Content hash A BLAKE3-256 digest authenticating + identifying a whole snapshot (I10).
Section CRC A CRC-32C per section locating corruption (I10).
Self-describing format A format carrying its own version + section map so a loader can validate before trusting.
Dirty page A heap page modified since the base snapshot (tracked for incremental capture).
Dirty-page tracking Detecting writes via mprotect+SIGSEGV or soft-dirty PTEs.
Soft-dirty PTE A Linux page-table bit marking a page written since a reset (/proc/pid/pagemap).
Copy-on-write (COW) Sharing pages until written; the kernel copies on the first write (fork fan-out).
Incremental snapshot / overlay A snapshot storing only pages changed over a base.
Delta chain base → overlay → overlay …, applied in order to reconstruct state (link #111).
Chain compaction Materializing a chain into a fresh base to bound restore cost.
Base hash The content hash of the base a given overlay applies to (chain identity, ADR-029).
Lazy relocation (swizzle-on-fault) Relocating a page's offsets→pointers on first access, not all up front (fast boot).
Working-set prefetch Pre-loading + pre-relocating hot pages so the first request avoids faults.
Migration Upgrading a snapshot from an older compatible format/schema minor (§9).
Untrusted snapshot A .svm from any non-trusted source; treated as hostile input + untrusted code.
Differential capture≡restore The oracle: snapshot→restore→re-snapshot is byte-identical + output-identical (I1).
VM ABI hash A digest of the bytecode module/opcode layout guarding PC/frame validity on restore.

Appendix C — Worked Capture Trace (byte-level)

VM at safe point (heap, 8-byte-aligned objects):
  O0 = Str("hi")        header{tag=STR, size=2}  payload "hi"
  O1 = Array[Int 1, Ref O0]
  O2 = Map[(Ref O0 → Ref O1)]
  globals[0] = Ref O2 ; thread0.stack = [Ref O2] ; thread0.frames=[{fn:main, pc:7, locals:[Ref O0]}]
  logical_clock=42 ; rng=seedstate

STEP 1 trace (deterministic order: globals, then stacks, then frames; DFS):
  visit O2 → O0, O1 ; visit O1 → O0(seen) ; order = [O2, O0, O1]   (stable, I3)

STEP 2 assign offsets (header 12 B + payload, align 8):
  O2 @ 0x00   (Map: 1 entry = 2 Values)
  O0 @ 0x28   (Str "hi")
  O1 @ 0x40   (Array: 2 Values)

STEP 3 relocate_out (write offsets, record reloc locations):
  heap_image[O2.entry.key]  = 0x28   reloc@(0x00 + key_field)
  heap_image[O2.entry.val]  = 0x40   reloc@(0x00 + val_field)
  heap_image[O1[1]]         = 0x28   reloc@(0x40 + elem1)
  reloc_tbl (roots/exec):
    globals[0]      → 0x00
    thread0.stack[0]→ 0x00
    thread0.locals[0]→0x28

STEP 4 emit sections:
  header_sec{ major,minor,vm_abi, epoch, logical_clock=42, rng=seedstate }
  heap_image{ regions:[{len, page_bytes}] }     ; 0 live ptrs (I4)
  reloc_tbl{ count=5, entries:[...] }
  thread_tbl{ t0:{ status=Parked, stack_off, frames:[{fn:main, pc:7, locals_off, ...}] } }
  gc_meta{ mark_color, free_lists, cursors }
  resource_manifest{ count=0 }
  content_hash = BLAKE3(all above)               ; (I10)

Appendix E — .svm Snapshot Format Byte Layout Reference

E.1 File structure (top level)

offset 0   : magic           "SVM\x01"            (4 B)
offset 4   : major            u16 LE
offset 6   : minor            u16 LE
offset 8   : flags            u16 LE  (bit0=incremental, bit1=zstd-heap, bit2=has-resources)
offset 10  : section_count    u16 LE
offset 12  : section_dir      section_count × SectionEntry
... sections (in dir order) ...
EOF-32     : content_hash     BLAKE3-256          (32 B, over bytes [0 .. EOF-32))

E.2 SectionEntry (24 B)

Field Type Meaning
kind u16 LE section kind (table E.3)
flags u16 LE per-section flags (compressed, critical)
offset u64 LE byte offset of section start in file
len u64 LE section length in bytes
crc32c u32 LE CRC-32C of the section bytes (I10)

E.3 Section kinds

kind Name Encoding Critical? Purpose
0x0001 HEADER CBOR yes vm_abi, page_size, base_hint, epoch, logical_clock, rng, parent_hash
0x0002 HEAP_IMAGE raw (opt. zstd) yes region page bytes; offsets only (I4)
0x0003 RELOC_TBL packed u64[] yes locations to swizzle (I5)
0x0004 THREAD_TBL CBOR yes threads: stack_off, frames, status
0x0005 GC_META CBOR yes mark color, free lists, cursors, gc_epoch
0x0006 RESOURCE_MANIFEST CBOR yes if has-resources handles, kinds, policies, descriptors (I7)
0x0007 OVERLAY_META CBOR yes if incremental base_hash, dirty page list (§7)
0x0008 WORKING_SET packed u32[] no hot page hints for prefetch (§8)
0x00FF UNKNOWN (future) — per flags additive kinds; skip if non-critical (ADR-027)

E.4 RELOC_TBL entry (8 B each)

count : u64 LE
entries[count] : u64 LE at_offset   ; the location (within HEAP_IMAGE / a thread stack) holding an offset
                                     ; restore: *(base + at_offset) = base + (value currently stored there)

Validation (I5): at_offset < total_relocatable_len; the stored offset < heap_image_len; the target lands on an ObjHeader boundary with a declared valid tag.

E.5 ObjHeader on-disk (12 B, #[repr(C)])

Field Type Meaning
tag u16 object kind (STR/ARRAY/MAP/CLOSURE/STRUCT/RESOURCE_REF)
flags u8 object flags
gc_mark u8 GC mark color (captured for collector resume)
size u32 payload bytes
fwd u32 forwarding/offset slot (assigned offset during capture)

E.6 RESOURCE_MANIFEST entry (CBOR map)

{ handle_id: u32, kind: u16, policy: u8, descriptor: bytes }
kind  : 1=File 2=Socket 3=Timer 4=Rng 5=Clock 6=Mmap 7=Stdio
policy: 0=Reopen 1=ReopenAtOffset 2=LazyReconnect 3=Virtualize 4=Fail 5=Drop
descriptor (per kind): File{path,off,flags} | Socket{addr,proto,state} | Timer{deadline_logical} | ...

E.7 Invariants encoded in the layout

  • No field in HEAP_IMAGE is a live pointer (I4) — all references are offsets relocated via RELOC_TBL.
  • content_hash covers everything before it (I10); per-section CRC localizes corruption.
  • major/minor gate compatibility (I11); critical-flag governs unknown-section handling (ADR-027).
  • HEAP_IMAGE may be zstd-compressed (flag); hash is over the on-disk (compressed) bytes (ADR-028, I3).

Appendix I — Determinism Sources & Mitigations (I3/I9)

Byte-identical snapshots (I3) require eliminating every source of nondeterminism from the hashed body. This is the checklist:

Source Risk Mitigation
Live pointer values differ per process (ASLR) store offsets only (I4) — never addresses in the image
HashMap/HashSet iteration order random per run ordered traversal (root index, then field order) in trace
Wall-clock timestamps differ every capture no wall time in the body; only the logical clock (data)
RNG nondeterministic stream seeded PRNG; state captured/restored (I9)
Allocation order affecting offsets depends on history offsets assigned by deterministic trace order, not alloc order
Free-list / fragmentation layout history-dependent GC_META captures the exact free-list; or compact before capture
Thread scheduling at the safe point interleaving capture at a quiesced safe point; scheduler queue serialized in order
zstd nondeterminism compressor settings fixed zstd level + params; hash the on-disk bytes (ADR-028)
Floating-point in the program NaN bit patterns preserve exact bits (Value::Float is raw bits)
Map/set objects in the VM user-level order preserve insertion order in the object representation

Monotonic logical time (I9): the logical clock only increases; on restore it is set to max(captured, prior) so it never regresses; timers fire relative to it; wall-clock reads are a separate resource with an explicit re-sync policy. The determinism/recapture_identical + rng_trajectory + clock_monotonic fixtures (§10) enforce this checklist.

  • Dragon Ch. 7 (run-time environments): activation records / call frames — exactly the Frame we serialize in §3.

  • Firecracker (NSDI 2020) + Catalyzer (ASPLOS 2020) + Lambda on-demand loading (ATC 2023): the boot-from-snapshot latency model, lazy page-in, working-set prefetch — drive §8 targets (§4 boot p50 ≤ 1 ms) and ADR-013/030.
  • JVM CRaC + org.crac: the before_checkpoint/after_restore hook protocol — svm-resource::Resource (§6, Appendix G).
  • Wilson 1991 (POS) + Texas persistent store: pointer swizzling strategies (eager vs swizzle-on-fault, page-grained) — the relocation design (§2/§4) and lazy relocation (§8).

  • rr (ATC 2017): checkpoint + deterministic replay — the link to #344; logical time + RNG capture (I9) make a snapshot a replay checkpoint.
  • Linux soft-dirty / pagemap docs: page-level dirty tracking — the cheap incremental path (§7, ADR-010).
  • BLAKE3 + SemVer: fast integrity hashing + version-compat rules — the format (§5, ADR-008/009).
