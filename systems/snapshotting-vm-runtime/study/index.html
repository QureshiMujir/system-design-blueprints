Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why is "validate before deref" the single most important loader rule, and what two invariants (§7 Invariants) does violating it break simultaneously? — Synthesizes §Phase 4/9 validate steps, principle 5, I2/I5. A crafted at_offset that passes format checks but lands mid-object breaks both I2 (panic/OOB) and I5 (reloc target not on a header boundary).
  2. A program takes a snapshot, then its heap grows (new regions allocated), then takes an incremental snapshot. Which sections in the .svm format change, and how does the restore path handle the new regions? — Synthesizes §Phase 7 overlay_meta, §8.3 format grammar (heap_image region count), §Phase 4 restore map step. New regions appear as additional {vaddr_hint, len, page_bytes} entries in heap_image; all pages in a new region are "dirty" by definition; overlay_meta must include them.
  3. Why can the lazy relocation (§Phase 8) and the eager relocation (§Phase 4) produce byte-identical re-snapshots even though they relocate in different orders? — Synthesizes §Phase 8 lazy_eq_eager differential, I1/I3, MM2 (offset = identity). Both produce the same pointer graph because relocation is a function of (base, stored_offset) — order-independent. The re-snapshot traces in the same deterministic order (I3), so the image is identical.
  4. The safe-point STW pause SLO is p99 ≤ 10 ms. A workload has one tight loop with 10,000 iterations and no allocs, calls, or back-edges. What happens, and how would you fix it? — Synthesizes §Phase 1 pitfall 1, §Phase 1.7 performance, §4 STW constraint, ADR-005. The thread never reaches a safe-point poll → quiesce timeout → unsafe_capture, capture aborted (I8). Fix: insert a poll at the back-edge of every loop, regardless of body content.
  5. You receive a .svm snapshot where the content hash passes but the reloc table has an entry pointing to a valid offset within the heap_image that lands in the middle of a large Str object's payload. What error is returned, and which two validation checks catch it? — Synthesizes §Phase 4/9 validate, I5, §Appendix D, §8.3 reloc_tbl. The entry passes bounds check (I5 first condition) but fails the "target lands on an ObjHeader boundary with a declared valid tag" check (I5 second condition). Error: LoadError::BadReloc / E.BAD_RELOC.
  6. Explain why logical_clock = max(captured, prior) is the correct restore formula and not logical_clock = captured. What breaks if you use captured exactly and the host was suspended for an hour? — Synthesizes §Phase 3/6 logical_clock, I9, ADR-014, MM8. captured is fine for deterministic replay; but if the host wall time advanced and external code (e.g., a CRaC hook) re-syncs the clock, captured may be less than a previously-committed logical time in a log, breaking monotonicity. The formula is max(captured, prior_committed) — I9 guarantees non-regression.
  7. A socket with LazyReconnect policy is in the heap as ResourceRef(h=3). The program restores and immediately calls RESOURCE_OP h=3 send "hello". Trace the full call path from opcode to network bytes, naming every component. — Synthesizes §Phase 6 policy/hooks, Appendix G, §Phase 4 rebuild step, Appendix J RESOURCE_OP opcode. Dispatch loop → RESOURCE_OP → svm-resource::ResourceTable::get(h=3) → after_restore not yet called → lazy: call after_restore on first op → TCP reconnect → send "hello".
  8. Why does the blueprint choose cooperative (not preemptive) scheduling for fibers, and what would change in §Phase 1 if we switched to OS threads with preemptive scheduling? — Synthesizes §Phase 0/1, ADR-015, principle 1/11, §Phase 1 pitfalls. Cooperative: yield points are safe-point boundaries — we know exactly where a fiber's stack is frozen. Preemptive OS threads: safe-point must use a signal/handshake per thread (like HotSpot's) and every point in the bytecode must be a potential suspension point → more complex quiescence, signals can arrive mid-object-write without a consistent state guarantee.
  9. If two processes simultaneously restore the same base snapshot with COW fork, then both start writing, do they interfere? Name the kernel mechanism and the relevant ADR. — Synthesizes §Phase 7/8 COW fork, ADR-030, Tanenbaum §5.Book-5. No interference: the kernel COW (copy-on-write page fault) gives each process its own private copy of any page on first write. The base mmap'd pages are shared read-only until write — each fork gets an independent diverging heap. ADR-030.
  10. A migration rule upgrades Obj::Str from storing a raw Box<[u8]> to storing {bytes: Box<[u8]>, encoding: u8}. Is this a minor or major version bump? What would make it a major? — Synthesizes §Phase 5/9, Compatibility & Versioning, ADR-027, I11. Adding a field with a default (encoding=0 for UTF-8 legacy) is additive → minor (migrate on load, fill default). A major is required if the interpretation of existing bytes changes (e.g., encoding now changes what bytes[0] means — existing snapshots would be mis-decoded).
  11. The incremental overlay's base_hash doesn't match the base snapshot you have. What error is returned, what invariant it protects, and why can't you "just apply the overlay to the closest available base"? — Synthesizes §Phase 7, I1, §8.6 BaseMismatch, ADR-029. Error: LoadError::BaseMismatch. Invariant: the dirty-page set is relative to a specific base — applying it to a different base would overlay dirty data onto wrong clean pages, silently restoring a corrupted heap. The content-hash link in ADR-029 is the identity of the chain; breaking the chain breaks I1.
  12. Walk through the capture of a cycle O1→O2→O1 using the Phase 2 trace algorithm. How does the visited-set prevent infinite recursion, and what appears in the reloc table for the back-reference? — Synthesizes §Phase 2.2 trace, §8.5 worked example, I3/I4. visited-set: after visiting O1, mark visited; visit O2, add to visited; encounter O1 again → already visited, get its already-assigned offset. Back-reference in reloc_tbl: the field in O2 that references O1 gets its at_offset recorded; stored value = O1's offset. No infinite recursion because visited-set terminates the DFS.
  13. Why is BLAKE3 chosen over SHA-256 for the content hash, and in what deployment context would you switch to SHA-256? — Synthesizes §Phase 5, ADR-008, §5.Paper-14. BLAKE3: ~3× faster (multi-GB/s) than SHA-256, parallelizable, tree-mode allows incremental hashing. Switch to SHA-256: when storing snapshots in a FIPS-140-validated HSM or a government system that mandates FIPS-approved digests — BLAKE3 is not FIPS-approved as of 2025.
  14. A restored VM's restore_divergence metric fires once after 10,000 round-trips. What is the most likely root cause, and what is your debugging procedure? — Synthesizes §Phase 10, I1/I3, Failure Modes & Recovery (restore divergence), §Phase 2/3 pitfalls. Most likely: a non-determinism source in trace order (e.g., a HashMap used in the scheduler queue ordering — Appendix I). Debug: (1) binary-search the 10k to find the diverging state; (2) re-capture the state twice → if byte-diff appears, it's I3 (determinism); (3) check Appendix I checklist; (4) grep for HashMap in svm-snap/trace.rs.
  15. Why is capture() designed to be read-only on the VM state (I8), and what would break if it mutated the heap during capture? — Synthesizes §Phase 2 pitfall 5, I8, principle 10, §Phase 1 safe-point. Read-only capture means a failed or aborted capture leaves the VM in exactly its pre-capture state (resumable). If capture mutated objects (e.g., wrote offsets into live fwd fields without restoring them), an aborted capture would leave the heap with partially-overwritten headers — the VM could not resume safely. The fwd field trick: we read it for GC's forwarding, but we must restore it after capture finishes.
  16. A serverless workload snapshots 100 warm VMs and boots them as a fork-pool. Memory cost? Boot latency per request? How does this change if the VM heap grows from 64 MB to 256 MB? — Synthesizes §4 constraints, Back-of-Envelope #8/4, §Phase 7/8, ADR-030. 100 forks × 64 MB = 6.4 GB virtual, but COW physical = 64 MB base + per-fork dirty pages (lazy copy). Boot per request: ~0.5 ms (MM6 + §Back-of-Envelope #4). At 256 MB: virtual = 25.6 GB, physical base = 256 MB + dirty; p50 boot ≈ 2 ms (more working-set pages to fault in — may miss §4 ≤ 1 ms for large heaps).
  17. Explain the role of ObjHeader.fwd across two contexts: GC forwarding and snapshot offset assignment. Why is sharing this field safe? — Synthesizes §8.2 object header, §Phase 2 offset assignment, §Phase 0/2 GC design, principle 11. GC uses fwd during copying GC (forwarding pointer to new location); snapshot uses fwd to store the assigned file offset during capture. Safe because (a) this project uses mark-sweep (non-moving) GC — fwd is unused by GC during normal operation; (b) capture is read-only (I8) — after capture, fwd is restored to 0 (or never modified if we use a separate offset map).
  18. The snapshot format stores base_hint:u64 in the header. What is it used for, when can it be ignored, and what goes wrong if the loader always respects it? — Synthesizes §8.3 format grammar, §Phase 4/8, I4/ADR-004. base_hint is the virtual address where the heap was mmap'd during capture — provided as a hint to the loader to try the same base (reduces ASLR-induced relocation work for lazy swizzle). Can be ignored: always safe because offsets are position-independent (I4). If always respected: a hint from a 32-bit capture on a 64-bit restore fails (address out of range); or an ASLR system may refuse a fixed base, and the loader panics — must fall back gracefully.

Mental Models & First Principles

MM1 — Consistency = a quiesced observer. A snapshot is consistent if and only if the observer (serializer) sees a world where no mutation is in flight. Any STW safe-point protocol is a specialization of this principle. Predicts: a capture mid-allocation produces a corrupt heap. Without it: you write a serializer that races with the mutator and gets heisenbug corruption. Applied: §Phase 1 (safe-point handshake), principle 1.

MM2 — Pointer = address; offset = identity. In a running process, a pointer encodes both object identity and address. After ASLR restores in a new process, the address is meaningless but the identity survives as an offset. Every serializable object graph must separate these two. Predicts: a snapshot storing raw pointers is unreloadable after ASLR. Without it: you store addresses in the image and every restore at a different base silently corrupts references. Applied: §Phase 2 ptr→offset, §Phase 4 offset→ptr, I4, ADR-004.

MM3 — The loader is the attack surface. A deserializer that trusts its input is a remote code execution vector: a crafted relocation table can direct *at = B + crafted_offset to an arbitrary address. Predicts: every unchecked count or offset is a potential OOB write. Without it: you write a fast path that dereferences reloc entries before bounds-checking them. Applied: §Phase 4/9 validate-before-deref, principle 5, I2/I5, ADR-016.

MM4 — External state is never memory. File descriptors, sockets, timers, and clocks are kernel state registered in the OS process table, not values you can copy. Their ids (fd numbers) are meaningless after exec/fork into a new process. Predicts: a heap scan that finds a raw integer that "looks like" a valid fd will silently use the wrong kernel resource on restore. Without it: you serialize fd=7 into the heap and restore it into a process where fd 7 is something else. Applied: §Phase 6 resource manifest, I7, ADR-011, principle 3.

MM5 — Incremental snapshots are sound only if the dirty-tracking is sound. An incremental snapshot stores "only changed pages." If one dirty write escapes the tracker, the overlay is missing data, and the restored VM silently diverges. Predicts: a single unkept mprotect fault or a soft-dirty reset miss corrupts the incremental chain. Without it: you assume page-protection is infallible and never test chain≡full differential. Applied: §Phase 7 dirty-page tracking, I1, ADR-010.

MM6 — Lazy relocation is correct iff swizzle is idempotent and per-page monotonic. Swizzle-on-fault relocates a page the first time it is touched. If two threads race to the same unswizzled page, or if a page is swizzled twice, pointers double-shift. Predicts: a lazy-relocation race produces wild pointers that only manifest under load. Without it: you implement lazy relocation without a per-page "already swizzled" latch. Applied: §Phase 8, I1 lazy_eq_eager differential, ADR-013.

MM7 — GC roots and snapshot roots are the same set. The GC starts from roots to find live objects; the serializer starts from roots to find all objects to snapshot. If these diverge, either the snapshot misses live objects (dangling refs on restore) or includes dead ones (snapshot bloat). Predicts: a root source added to the scheduler queue but not the serializer's root walk causes a dangling reference after restore. Without it: you maintain two separate root enumerations that drift apart. Applied: §Phase 0/2 shared RootSet, principle 11, I12.

MM8 — Logical time must be data, not wall clock. Wall-clock time is a property of the host machine at a moment in time, not of the VM's execution state. After restore, the host clock has advanced. Capturing wall-clock time means every restore sees time "jump forward," breaking timer logic and determinism. A logical clock is a VM-owned counter that advances only when the VM advances — it is data, safely captured and restored. Predicts: using SystemTime::now() in a timer will cause double-fires or negative durations after restore. Without it: timers use wall-clock deadlines and always fire immediately on restore. Applied: §Phase 3/6 logical_clock capture, I9, ADR-014.

MM9 — Format versioning must refuse before it migrates. A loader that tries to "guess" what a future-major snapshot means will silently misinterpret fields, producing a corrupt VM that passes validation. The safe invariant: refuse any major > runtime; accept minor ≤ runtime with a registered migration. Predicts: a loader that "ignores unknown fields" in a major-bumped snapshot will restore a VM whose relocation semantics changed silently. Without it: you add "backward compatibility" that silently reinterprets a new relocation format as the old one. Applied: §Phase 5/9, I11, ADR-009/027.

MM10 — The equivalence oracle beats unit tests for serialization correctness. Unit tests verify individual fields. The real failure mode is silent divergence — the VM looks restored but behaves differently two instructions later. The differential oracle (snapshot → restore → re-snapshot → byte diff AND output diff vs uninterrupted run) catches every class of serialization bug in one test. Predicts: any phase that skips the differential will ship a subtle relocation or stack-capture bug. Without it: you unit-test relocate_in in isolation and miss the interaction with frame locals. Applied: §Phase 10 capture≡restore differential, I1/I3, ADR-019.

Books

  • Wilson, Uniprocessor Garbage Collection Techniques (1992 survey) — root sets, object headers, mark-sweep; the heap whose metadata we capture. Applied: §Phase 0 heap + GC design (svm-heap object headers, RootSet), §Phase 2 root enumeration, principle 11 (shared root set).
  • Jones, Hosking, Moss, The Garbage Collection Handbook (2nd ed., 2012) — Ch. on object layout, conservative vs precise roots, write barriers. Applied: §Phase 0 #[repr(C)] header design, §Phase 7 COW dirty-tracking (write-barrier intuition), ADR-003.
  • Smith & Nair, Virtual Machines (Morgan Kaufmann, 2005) — Ch. 3–4 process/HLL VMs, state capture & resumption; the conceptual spine of checkpoint/restore. Applied: §Phase 0–4 overall VM/snapshot mental model, Appendix F state-component matrix.
  • Aho/Lam/Sethi/Ullman, Compilers (Dragon, 2nd ed., 2006) — Ch. 7 run-time environments: activation records / call frames / stacks. Applied: §Phase 3 Frame/Thread serialization, Appendix J opcode set.
  • Tanenbaum & Bos, Modern Operating Systems (4th ed., 2014) — memory management, mmap/COW, page protection. Applied: §Phase 7 dirty-page tracking (mprotect/soft-dirty), §Phase 8 mmap boot path, ADR-010/013.
  • Love, Linux System Programming (2nd ed., O'Reilly, 2013) — mmap, mprotect, signals, fds. Applied: §Phase 6 resource externalization syscalls, §Phase 7 mprotect+SIGSEGV dirty tracking, Appendix G policy matrix.
  • Klabnik & Nichols, The Rust Programming Language (2nd ed., No Starch, 2022) — ownership, unsafe, repr(C), slices. Applied: ADR-001 rationale, §Phase 0 heap layout, §Phase 2 relocation unsafe in relocate_out.rs.
  • Jung et al., RustBelt: Securing the Foundations of the Rust Programming Language (POPL 2018) / the Rustonomicon — unsafe invariants for the pointer-relocation code. Applied: §Phase 2/4 relocation correctness, §Phase 10 Miri gate on relocate_in/relocate_out.
  • Drepper, What Every Programmer Should Know About Memory (Red Hat, 2007) — cache/TLB/page behavior; sequential-access patterns. Applied: §Performance Engineering (sequential reloc table apply, mmap first-touch fault cost), §Phase 8 prefetch design.
  • Gregg, Systems Performance (2nd ed., Addison-Wesley, 2020) — profiling, flamegraphs, latency analysis. Applied: §Phase 11 perf certification, §Performance Engineering flamegraph methodology for capture/restore pauses.

Glossary · 47 terms · site-wide glossary

Snapshot / checkpoint
A serialized capture of a VM's full execution state, restorable later.
Restore / resume
Rebuilding a VM from a snapshot and continuing execution exactly.
Boot-from-snapshot
Cold-starting by restoring a warmed snapshot instead of running init (fast start).
Fork-from-snapshot
Cloning a snapshot into N independent VMs (COW page sharing).
Time-travel
Rolling a VM back to a saved checkpoint (feeds deterministic replay #344).
Safe point
A point in execution (between instructions) where the VM state is internally consistent and capturable.
Stop-the-world (STW)
Quiescing all threads/fibers at safe points so capture sees a frozen, consistent world.
Quiesce
A thread reaching a safe point and parking, acknowledging the snapshot request.
Object graph
The directed graph of heap objects linked by references (Value::Ref).
Relocation / swizzling
Converting offsets↔pointers (capture: ptr→offset; restore: offset→ptr).
Position-independent image
A heap image storing offsets, restorable at any base address (I4).
Relocation table
The list of locations holding references that restore must swizzle (I5).
ObjRef
A position-independent reference (id/offset), never a raw pointer.
Object header
#[repr(C)] per-object metadata (tag, size, GC mark, forwarding slot).
Root set
The references the GC (and serializer) start from: stacks, frame locals, globals.
Mark-sweep GC
A collector that marks reachable objects from roots then sweeps the rest.
Forwarding slot
A header field reused by the snapshotter to hold an object's assigned offset.
Value stack
The operand stack of the bytecode interpreter.
Call frame
An activation record: function id, PC, locals, return PC, base SP.
Program counter (PC)
The index of the next bytecode instruction to execute.
Fiber
A cooperatively-scheduled lightweight thread (a heap object holding a stack+frames).
Scheduler
The VM component choosing which thread/fiber runs (cooperative here).
Logical clock
A monotonic VM-internal time counter, captured/restored (I9), distinct from wall clock.
RNG state
The seeded PRNG state, captured so the random stream is deterministic across restore.
Resource handle
An indirection id for an external resource (fd/socket/timer/clock); the only heap↔external bridge (I7).
Resource manifest
The snapshot section listing every external resource + its policy + descriptor.
Resource policy
How a resource is restored: Reopen / ReopenAtOffset / LazyReconnect / Virtualize / Fail / Drop.
before_checkpoint / after_restore
CRaC-style hooks to externalize a resource at capture and reopen at restore.
Heap image
The raw serialized region bytes (offsets, no live pointers).
Section directory
The .svm table of {kind, offset, len, CRC} describing each section.
Content hash
A BLAKE3-256 digest authenticating + identifying a whole snapshot (I10).
Section CRC
A CRC-32C per section locating corruption (I10).
Self-describing format
A format carrying its own version + section map so a loader can validate before trusting.
Dirty page
A heap page modified since the base snapshot (tracked for incremental capture).
Dirty-page tracking
Detecting writes via mprotect+SIGSEGV or soft-dirty PTEs.
Soft-dirty PTE
A Linux page-table bit marking a page written since a reset (/proc/pid/pagemap).
Copy-on-write (COW)
Sharing pages until written; the kernel copies on the first write (fork fan-out).
Incremental snapshot / overlay
A snapshot storing only pages changed over a base.
Delta chain
base → overlay → overlay …, applied in order to reconstruct state (link #111).
Chain compaction
Materializing a chain into a fresh base to bound restore cost.
Base hash
The content hash of the base a given overlay applies to (chain identity, ADR-029).
Lazy relocation (swizzle-on-fault)
Relocating a page's offsets→pointers on first access, not all up front (fast boot).
Working-set prefetch
Pre-loading + pre-relocating hot pages so the first request avoids faults.
Migration
Upgrading a snapshot from an older compatible format/schema minor (§9).
Untrusted snapshot
A .svm from any non-trusted source; treated as hostile input + untrusted code.
Differential capture≡restore
The oracle: snapshot→restore→re-snapshot is byte-identical + output-identical (I1).
VM ABI hash
A digest of the bytecode module/opcode layout guarding PC/frame validity on restore.
