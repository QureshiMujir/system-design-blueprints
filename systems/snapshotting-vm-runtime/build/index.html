⬜ Phase 0 — VM Core: Bytecode Interpreter, GC'd Heap, Threads/Fibers Skeleton, CLI

Objectives

A runnable stack bytecode VM: repr(C) object heap with mark-sweep GC + root set, value stack + call frames + PC, a cooperative scheduler skeleton (single thread + parkable fibers), and svm run <module>. Establish the position-independent reference model (ObjRef = id/offset, never raw ptr) from day one so snapshotting is possible later (I4).

Deliverable

svm run prog.svmbc executes a real bytecode program (loops, arrays, maps, function calls, fibers that yield/resume) to completion; GC reclaims unreachable objects.

Acceptance
  • A fixture program (fib, map-build, fiber-pingpong) produces the expected result.
  • GC: live-object count after collection matches reachable set; no use-after-free (Miri clean on heap).
  • ObjRef is an id/offset everywhere; grep finds 0 raw *mut Obj in Value (enforces I4 precondition).
  • ≥ 50 M simple ops/s single-thread (baseline).
Fixtures

conformance/capture/_vm/{fib,arrays,maps,closures,fiber_pingpong}.svmbc + golden stdout; _gc/{cycle,unreachable} (GC correctness).

Pitfalls
  • Raw pointers leaking into Value → snapshotting impossible later; lock ObjRef=id now (I4).
  • GC root set missing a source (scheduler queue, fiber stacks) → premature free; the same miss later corrupts snapshots (principle 11).
  • Object header not repr(C)/unaligned → relocation math breaks in §2.
  • Mutable aliasing of heap during interpretation → Rust borrow fights; use an arena/index model.

⬜ Phase 1 — Safe Point: Stop-the-World Handshake & Consistent Capture Window

Objectives

A safe point mechanism: the dispatch loop polls at back-edges/calls/allocations; on a snapshot request all threads/fibers quiesce at a poll, producing a window where the heap + every stack/frame is internally consistent (no half-written object, no in-flight push) — the precondition for any correct capture (I6).

Deliverable

svm snapshot --dry-run <module> runs the program, requests a safe point, confirms all threads quiesced and the heap is consistent, then resumes — no bytes written yet.

Acceptance
  • All threads reach a safe point within the timeout on cooperative workloads.
  • A consistency assertion (no object with size/tag mid-write; stack invariants hold) passes at the safe point on all fixtures.
  • capture() cannot be called without a SafePointToken (compile-time, I6).
  • Resume after a dry-run safe point continues identically (I8 precursor).
Fixtures

conformance/capture/safepoint/{multi_fiber_quiesce,alloc_heavy,timeout_tight_loop}.

Pitfalls
  • A loop with no poll → never reaches a safe point → capture hangs; ensure every back-edge polls (bounded poll distance).
  • Polling too often → interpreter overhead; balance poll density.
  • Capturing mid-allocation (object header written, payload not) → inconsistent heap; alloc is a safe-point boundary, never split.
  • A parked fiber's stack still referenced as a root → must be enumerable at the safe point (principle 11).

⬜ Phase 2 — Object-Graph Serialization: Trace, Offset Assignment, Pointer→Offset Relocation

Objectives

Serialize the frozen heap into a position-independent image: trace the live object graph from roots, assign each object a stable file offset, copy headers+payloads into the image, and emit a relocation table recording every location that holds a reference so restore can swizzle offset→pointer. 0 live pointers in the image (I4); deterministic order (I3).

Deliverable

svm snapshot --heap-only <module> writes a heap-image + reloc-table (no stacks/resources yet); svm inspect dumps objects + relocations; re-capturing the same state is byte-identical (I3).

Acceptance
  • Heap image contains 0 values that look like live pointers (reloc audit scans, I4).
  • Every reloc entry's at_offset and stored offset are within the image and land on object-header boundaries (I5).
  • Object count in image = GC-live count (I12).
  • Re-capture of identical state ⇒ identical bytes (I3); cycles serialize without infinite loop.
Fixtures

conformance/capture/graph/{linear,tree,cycle,shared_subgraph,deep}, determinism/recapture_identical, malformed/_reloc_oob (negative, exercised in restore §4).

Pitfalls
  • Non-deterministic trace order (HashMap iteration) → non-reproducible snapshot (I3); use ordered traversal.
  • Forgetting a reference field in an object variant → dangling ref on restore (I5); exhaustive match per Obj variant.
  • Self/back references → must record the offset even for already-visited objects.
  • Alignment/padding mismatch between in-memory and image layout → relocation lands mid-object.
  • ResourceRef traced as a normal object → must be redirected to the manifest (handled §6), not into the heap image.

⬜ Phase 3 — Stack / Frame / PC / Thread & Fiber State Capture

Objectives

Capture the execution state on top of the heap graph: every thread's value stack, call frames (locals, return PC, base SP), the program counter, fiber/scheduler state, the logical clock, and RNG state — all with references relocated like the heap (I4). Together with §2 this is a complete, position-independent VM snapshot (minus resources/format wrapper).

Deliverable

svm snapshot <module> (no resources yet) writes a complete VM image (heap + stacks + frames + PC + threads + gc-meta + clock/rng); svm inspect shows thread/frame state.

Acceptance
  • All thread stacks/frames captured; reference slots relocated (I4/I5).
  • Logical clock + RNG present and deterministic (I3/I9).
  • GC metadata sufficient to resume the collector (free lists, cursors consistent with the heap image, I12).
  • Re-capture byte-identical (I3).
Fixtures

conformance/capture/exec/{deep_stack,many_frames,parked_fibers,scheduler_queue,clock_rng}, golden thread tables.

Pitfalls
  • Stack slots holding Refs not relocated → dangling on resume (I5); treat the stack like heap fields.
  • base_sp/ret_pc invalid after relocation → frame corruption on resume; these are indices/PCs (already position-independent) — but validate ranges.
  • Capturing a fiber mid-switch → must be at a safe point (I6); fibers park only at yields.
  • RNG/clock not captured → non-deterministic restore (I9).
  • GC mark color drift (collector mid-cycle) → coordinate with safe point (GC is a safe region, §1).

⬜ Phase 4 — Restore: Validation, Heap Mapping, Offset→Pointer Relocation, Resume

Objectives

The exact inverse of §2+§3: validate the (untrusted) image (I2), map the heap into memory at a fresh base, relocate offset→pointer for every reloc entry (I5), rebuild threads/stacks/frames/PC and the scheduler, restore clock/RNG/GC-meta, and resume the dispatch loop so the VM continues identically (I1).

Deliverable

svm restore <snapshot.svm> (resources stubbed/Drop) brings a captured VM back and continues to completion, producing the same output as if it had run uninterrupted (round-trip, I1).

Acceptance
  • Round-trip equivalence (I1): run program P to a safe point, snapshot, restore in a fresh process, finish → output identical to running P uninterrupted, across all fixtures.
  • Relocation: every offset→ptr lands on a valid header (I5); object count matches (I12).
  • Logical clock monotonic (I9); RNG continues the same sequence (I3).
  • Restore ≤ 50 ms for the medium fixture (§4).
Fixtures

conformance/restore/{roundtrip_fib,roundtrip_map,roundtrip_fibers,roundtrip_deep}, roundtrip/_recapture_after_restore_identical (snapshot→restore→snapshot ⇒ byte-identical, I1/I3).

Pitfalls
  • Dereferencing before validating → the exploit; validate fully first (principle 5, I2).
  • Off-by-base relocation (forgetting B, or double-adding) → wild pointers; centralize the B + offset swizzle.
  • Endianness / pointer-width mismatch (snapshot from a different ABI) → reject on header vm_abi (I11).
  • Resuming at a stale PC (function table changed) → guard with the bytecode/ABI hash in the header.
  • Partial restore on error → must produce no VM at all (atomic, principle 10); fail to REJECTED.

⬜ Phase 5 — Snapshot Format, Versioning, Integrity, `svm inspect`/`verify`

Objectives

Wrap the sections in the self-describing .svm container: magic, SemVer version, section directory, per-section CRC-32C, whole-file BLAKE3 content hash, embedded header/manifest, optional zstd on the heap image. Enforce integrity + version checks on load (I10/I11) and provide inspect/verify tooling.

Deliverable

svm snapshot emits a versioned, hashed .svm; svm verify <f> checks magic/version/CRC/hash and prints the section map; svm inspect <f> dumps header + sections + manifest without restoring.

Acceptance
  • Round-trip: write → verify → read → restore unchanged (I1).
  • Corrupt one byte → verify fails with the offending section (CRC) and a hash mismatch (I10).
  • Major-newer snapshot refused; minor-older accepted (I11).
  • Content hash is stable for identical state (I3) and matches across re-captures.
Fixtures

conformance/format/{good,bad_crc,bad_hash,bad_magic,major_newer,minor_older,zstd_image}.

Pitfalls
  • Hashing before vs after compression inconsistency → pick one (hash the on-disk bytes, ADR-028).
  • Section offsets overlapping / out of file → validate the directory before reading sections (I2).
  • Timestamps/paths in the body → non-deterministic hash (I3); keep volatile data out of the hashed body.
  • CRC vs hash redundancy confusion → CRC = per-section locality, hash = whole-file authenticity/identity; both kept.

⬜ Phase 6 — External Resource Manifest: Reopen / Lazy / Virtualize Policies, Time & RNG

Objectives

Solve the crux: external state (fds, sockets, timers, RNG, wall-clock, mmap'd regions) is not serializable. Route all of it through ResourceHandle indirection + a resource manifest with per-resource policies ({Reopen, ReopenAtOffset, LazyReconnect, Virtualize, Fail, Drop}), CRaC-style before_checkpoint/after_restore hooks, and deterministic logical time + seeded RNG (I7/I9).

Deliverable

A program that opens a file + a socket + a timer + uses RNG can be snapshotted and restored: file reopened at offset, socket lazily reconnected, timer rearmed against the logical clock, RNG continues the same sequence.

Acceptance
  • 0 raw fds/sockets in the heap image (scan, I7); every external resource has a manifest entry.
  • After restore: file reads continue from the captured offset (ReopenAtOffset); socket reconnects on first use (LazyReconnect); RNG produces the identical next values (I3); logical clock ≥ captured (I9).
  • A Fail-policy resource that's missing → restore rejected, no half-wired VM (I7).
Fixtures

conformance/resources/{file_reopen,file_offset,socket_lazy,timer_rearm,rng_continue,virtualize_pipe,fail_missing,drop_temp}.

Pitfalls
  • A raw fd captured by accident (a code path bypassing ResourceHandle) → meaningless on restore (I7); the indirection must be the only path.
  • Wall-clock determinism — true wall clock can't be deterministic; separate logical time (deterministic, I9) from wall time (a resource with a re-sync policy).
  • Socket reconnect mid-protocol → application-level resumption is the app's job; we restore the handle + a "reconnect needed" signal, not TCP sequence numbers (documented non-goal).
  • Timer double-fire across restore → rearm against the logical clock, not wall (I9).
  • mmap'd file region → captured as a resource (path+offset+prot), re-mmap'd on restore; anonymous mmap is heap (already captured).

⬜ Phase 7 — Copy-on-Write & Incremental Snapshots: Dirty-Page Tracking, Delta Chains

Objectives

Make frequent snapshots cheap: track dirty pages (via mprotect+SIGSEGV write-protection, or Linux soft-dirty PTEs), and capture incremental overlays that store only changed pages over a content-addressed base snapshot (base+overlay delta chains, reusing #111's chain idea). Enables time-travel and high-frequency checkpointing (principle 8).

Deliverable

svm snapshot --incremental --base <hash> writes a small overlay (only dirty pages); svm restore applies base+overlays; svm fork <base> boots N VMs sharing read-only pages COW; chain compaction on demand.

Acceptance
  • Incremental snapshot size ≤ 5% of base on a steady workload (§4); restore of base+overlays ≡ a full snapshot at that point (I1).
  • Dirty-page tracking catches every mutation (no missed dirty page → no stale data on restore).
  • Overlay with a wrong base hash → rejected (BaseMismatch, §8.6).
  • Fork: N clones share base pages until written (COW); each diverges correctly.
Fixtures

conformance/incremental/{overlay_small,chain_apply,compaction,base_mismatch,fork_cow_divergence,missed_dirty_negative}.

Pitfalls
  • A missed dirty page (a write the tracker didn't see) → silent stale data on restore → divergence (I1); the tracker must be sound (every write faults or is soft-dirty-flagged).
  • Page size vs object size mismatch → an object spanning pages; track at page granularity, snapshot whole dirty pages.
  • Long delta chains → slow restore; compact periodically (tradeoff, principle 8).
  • mprotect overhead on every page after a base → batch re-protection; soft-dirty avoids per-fault cost where available.
  • Forking and then snapshotting a clone → its base is the shared base + its own overlay.

⬜ Phase 8 — Boot-from-Snapshot: Fast Cold Start, Lazy Relocation, Working-Set Prefetch

Objectives

Turn restore into a sub-millisecond cold start: pre-build a warmed snapshot (post-init heap), then boot by mmap-ing the image and lazily relocating pages on first access (swizzle-on-fault, Texas/Catalyzer-style) instead of eager full relocation — plus optional working-set prefetch. The serverless motivation (Firecracker/Lambda SnapStart) realized (§4: p50 ≤ 1 ms).

Deliverable

svm restore --boot of a warmed snapshot reaches "ready to serve" in sub-ms (p50 ≤ 1 ms); svmd serves requests from a boot/fork pool; cold-start latency dashboard.

Acceptance
  • Boot-from-snapshot p50 ≤ 1 ms, p99 ≤ 5 ms for a ≤ 64 MB warmed heap (§4).
  • Lazy relocation correctness: a lazily-relocated VM ≡ an eagerly-relocated one (I1) — relocation order doesn't change semantics.
  • Working-set prefetch reduces first-request faults measurably.
  • Fork-pool clones are independent (COW divergence, §7).
Fixtures

conformance/restore/boot/{warmed_small,warmed_64mb,lazy_eq_eager,prefetch,pool_fork}.

Pitfalls
  • Lazy relocation race (two threads touch the same unrelocated page) → relocate-once with a per-page latch; idempotent swizzle.
  • A pointer relocated twice (eager + lazy paths overlap) → mark relocated pages; centralize the swizzle (shared with §4).
  • mmap base differs each boot (ASLR) → relocation must be base-relative every time (I4 — the whole point of offsets).
  • Prefetching the wrong working set → faults on the hot path; profile per workload.
  • Sharing a mutable page COW across forks → kernel COW handles it; ensure no eager write touches all pages.

⬜ Phase 9 — Cross-Version Migration & Validation of Untrusted Snapshots

Objectives

Two robustness pillars: (1) migrate snapshots across compatible format/schema versions (minor evolution) so old snapshots survive runtime upgrades (I11); (2) deeply validate untrusted snapshots — beyond CRC/hash — so a crafted .svm cannot corrupt the restored VM (I2/I5/I12, principle 5/12). The loader is hostile-input territory.

Deliverable

svm migrate <old.svm> --to <minor> upgrades a snapshot; svm verify performs full structural+graph validation; restoring a v1 snapshot on a v2 runtime works via migration; a crafted malformed snapshot is rejected with a precise LoadError.

Acceptance
  • A snapshot written by minor N restores on runtime minor N+1 (migrated) and is semantically identical (I1/I11).
  • Major mismatch refused (I11).
  • Every malformed-fixture (malformed/**) → a typed LoadError, never a panic/OOB/crash (I2), never a corrupt VM (I5/I12).
  • Validation cost bounded (O(image), no quadratic blowup on crafted input).
Fixtures

conformance/migration/{v1_to_v2,new_obj_variant,added_field,major_refuse}, malformed/{reloc_oob,reloc_midobject,bad_tag,overlap_section,count_mismatch,dangling_ref,huge_counts,truncated}.

Pitfalls
  • Migration that loses information → a lossy upgrade; migrations must be total + tested round-trip where reversible.
  • TOCTOU in validation (validate then the bytes change) → validate a frozen buffer; restore from the validated view only.
  • Trusting any field before validating it (e.g., a count used to allocate) → cap counts vs file size first (principle 5).
  • A "valid" graph that's semantically wrong (right structure, wrong type at an offset) → tag-check every relocation target (I5/I12).
  • Migration chains (v1→v2→v3) → apply rules in sequence, hash-verify each step.

⬜ Phase 10 — Hardening: Fuzz the Loader, Differential Capture≡Restore, Determinism

Objectives

Lock the three load-bearing invariants under adversarial and randomized conditions: I2 (loader never panics on arbitrary bytes — fuzz), I1 (restore ≡ capture — differential round-trip across randomized programs + access orders), I3/I9 (capture determinism + monotonic time). Miri-clean relocation unsafe.

Deliverable

Green fuzz (24h, 0 crashes) on all loader targets; a passing randomized capture≡restore corpus; Miri-clean; a determinism report.

Acceptance
  • 0 panics/OOB across ≥ 1e9 fuzz execs on load_snapshot (I2).
  • Randomized capture→restore→re-capture byte-identical and output-identical over ≥ 10k generated states (I1/I3).
  • lazy_eq_eager and base+overlay ≡ full hold under randomized access/dirty orders (I1).
  • Miri: no UB on the relocation path; logical clock monotonic on every restore (I9).
Fixtures

fuzz/corpus/*, conformance/determinism/{recapture_identical,rng_trajectory,clock_monotonic}, roundtrip/randomized_states.

Pitfalls
  • with_capacity(attacker_count) in the loader → OOM DoS; cap vs file size (principle 5, §9).
  • Recursive validation/relocation on a crafted deep graph → stack overflow; iterate with an explicit worklist + visited set.
  • Nondeterminism leaking in (HashMap order, a stray timestamp, pointer-derived hash) → flaky recapture_identical; hunt every source (I3).
  • A fuzz "crash" that's actually a slow unit (huge alloc) → timeouts + count caps.
  • Miri false-negatives if the unsafe is hidden behind FFI → keep relocation pure-Rust + Miri-visible.

⬜ Phase 11 — Soak, Performance Certification, Release

Objectives

Sustained correctness + the §4 latency/throughput targets under load, then a reproducible signed release. Prove snapshot/restore/boot/incremental at scale over long runs with bounded memory and deterministic results.

Deliverable

Green CI (build+clippy+test+miri+fuzz-smoke+differential); a soak report; a perf-certification report vs §4; a signed release (lib + svm + svmd); cold-start latency dashboard.

Acceptance
  • Soak: 0 crashes, flat memory across thousands of snapshot/restore/fork cycles, deterministic (I1/I3/I8).
  • Perf: boot p50 ≤ 1 ms / p99 ≤ 5 ms; full capture ≤ 100 ms / STW ≤ 10 ms; restore ≤ 50 ms; incremental ≤ 5% of base — all met for the reference 64–256 MB heaps (§4).
  • Determinism + never-panic SLOs from §10 hold under soak.
Fixtures

conformance/** (full), benchmarks/{capture,restore,boot,incremental,interp}/ baselines, soak scenarios.

Pitfalls
  • Memory growth across restore cycles (a resource/mmap not released on the old VM) → leak; track + assert flat (I8).
  • Latency regressions from a "correctness" fix → perf gate catches it.
  • Page-cache warmth skewing boot numbers → report cold vs warm separately (§8).
  • Nondeterminism surfacing only under load → soak runs the determinism check periodically.
