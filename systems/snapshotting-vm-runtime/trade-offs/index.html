Each card is one row of the blueprint's decision table: what was locked in, what was rejected, and — the column that matters most — the situation in which the rejected choice is the right one.

Decisions (§9) · 30 ADRs

001

Language

Chosen

Rust 2021 ≥1.78

Rejected

C, C++, Go, Zig

When the rejected choice is right

C wins when integrating with a C host that already owns the heap (CRIU, QEMU); Go wins for a networked snapshot manager that never touches raw pointers.

Why: repr(C)+unsafe for heap-image layout; no host GC over our heap; safety on untrusted loader; shared workspace #31/#32

002

VM style

Chosen

stack bytecode interpreter (computed-goto-ish match)

Rejected

register VM; AST-walk; JIT

When the rejected choice is right

Register VM wins when the snapshot also needs to capture JIT-compiled code caches (LuaJIT, V8) where the register ABI is already fixed; JIT wins when peak throughput matters more than snapshot simplicity.

Why: simple, deterministic state to snapshot; JIT code-cache snapshot deferred

003

Heap

Chosen

regions + mark-sweep GC, repr(C) headers

Rejected

host alloc only; copying GC (v1)

When the rejected choice is right

Copying/compacting GC wins when memory fragmentation matters more than snapshot simplicity (e.g., a long-running server with many small objects); host alloc wins for a thin interpreter that delegates memory ownership to an embedding application.

Why: precise roots+headers for capture; copying GC interacts with reloc — deferred to §7

004

Reference model

Chosen

ObjRef = heap offset/id (not raw ptr)

Rejected

raw *mut everywhere

When the rejected choice is right

Raw pointers win when the runtime is embedded in a larger system that already controls the allocator and guarantees the base address never changes (e.g., a fixed MMIO firmware environment).

Why: position independence (I4) baked into the model

005

Safe point

Chosen

poll at back-edges/calls/allocs; STW handshake

Rejected

preemptive signals; no safe point

When the rejected choice is right

Preemptive signals win when sub-millisecond consistent-snapshot pause is required and the runtime runs on a real-time OS with reliable signal delivery; no-safe-point wins when the runtime is single-threaded and each bytecode op is atomic (a pure interpreter with no alloc).

Why: deterministic consistency (I6); bounded pause

006

Serialization

Chosen

hand-built heap image + reloc table

Rejected

serde/bincode for the heap

When the rejected choice is right

serde wins when the "heap" is already a tree of owned Rust structs with no cross-references (no shared subgraph, no cycles) — e.g., a purely functional interpreter.

Why: serde can't relocate pointers; we need offset swizzling (principle 2)

007

Metadata encoding

Chosen

CBOR (RFC 8949) for manifest/header sections

Rejected

JSON; bespoke

When the rejected choice is right

JSON wins when human readability of the manifest is the primary requirement (debugging-first tool, not performance-sensitive); bespoke encoding wins in firmware where a CBOR decoder is too large.

Why: self-describing, deterministic, compact (heap body is raw)

008

Integrity

Chosen

BLAKE3 content hash + CRC-32C per section

Rejected

SHA-256 only; none

When the rejected choice is right

SHA-256 wins when the snapshot must be stored in a system that already mandates SHA-256 for compliance (FIPS-140 HSM, government crypto requirements); no integrity wins in a fully trusted in-process memory snapshot where latency is the only SLO.

Why: fast (§4) + per-section corruption locality (I10)

009

Format versioning

Chosen

SemVer major/minor in header; refuse major, migrate minor

Rejected

ad-hoc; no version

When the rejected choice is right

Ad-hoc versioning wins in a closed, single-vendor deployment where both producer and consumer are always upgraded atomically (e.g., a managed service where runtime and snapshot tool ship together).

Why: (I11) cross-version restore

010

Incremental

Chosen

dirty-page tracking (mprotect SIGSEGV / soft-dirty) + base+overlay

Rejected

full snapshot only

When the rejected choice is right

Full snapshot wins when the heap is small (≤ 4 MB), the workload is write-heavy touching nearly all pages, or the environment lacks mprotect (sandboxed WASM runtime).

Why: (principle 8) cheap frequent checkpoints; reuse #111 delta-chain

011

Resource model

Chosen

ResourceHandle indirection + manifest + policy enum

Rejected

serialize fds directly

When the rejected choice is right

Direct fd serialization wins in a kernel-level checkpoint tool (CRIU, DMTCP) that owns the process table and can reconstruct kernel fd state via /proc/pid/fd — infeasible here because we do not own the kernel.

Why: (I7) fds/sockets un-serializable; CRaC-style hooks

012

Resource policies

Chosen

{Reopen, ReopenAtOffset, LazyReconnect, Virtualize, Fail, Drop}

Rejected

one-size

When the rejected choice is right

One-size (always Fail) wins in a pure-compute VM that has no I/O at all — e.g., a sandbox running only deterministic bytecode with no file/network access.

Why: real resources differ (file vs socket vs timer)

013

Restore paging

Chosen

mmap heap image + eager OR lazy (swizzle-on-fault) relocation

Rejected

always copy

When the rejected choice is right

Always-copy wins when the snapshot is stored on a slow block device (network-attached storage) and the relocation pass warms the page cache, or in environments lacking anonymous mmap (e.g., some embedded RTOSes).

Why: fast boot (§8); lazy = sub-ms cold start

014

Logical time

Chosen

monotonic logical clock + seeded RNG captured

Rejected

host wall clock only

When the rejected choice is right

Host wall clock wins when determinism is not required and the application must report accurate real-world timestamps (e.g., a logging VM where log entries need wall-time accuracy).

Why: determinism + monotonicity across restore (I9)

015

Threads/fibers

Chosen

cooperative scheduler, fibers as VM objects

Rejected

OS threads only

When the rejected choice is right

OS threads win when the VM needs to exploit hardware parallelism for CPU-intensive compute (a JVM running parallel GC and computation threads) and snapshot pause cost is a secondary concern.

Why: capturable stacks (we own the scheduler); preemptive deferred

016

Loader validation

Chosen

total parser, bounds/header/type checks pre-deref

Rejected

trust the file

When the rejected choice is right

Trust-the-file wins in a closed, integrity-sealed deployment where snapshots are stored in a TPM-attested storage backend and the chain of custody is enforced externally — the in-process check then adds latency without additional security.

Why: (I2/I5) loader is attack surface

017

CLI

Chosen

clap (run/snapshot/restore/fork/inspect/verify/migrate)

Rejected

bespoke

When the rejected choice is right

Bespoke wins in a library-only embedding (no CLI at all) where the consumer integrates the API directly and does not ship a command-line tool.

Why: CRaC/criu-like UX

018

Daemon

Chosen

svmd snapshot-on-signal + boot-from-snapshot pool

Rejected

none

When the rejected choice is right

No-daemon wins for a batch tool (offline migration, one-shot restore, CI test) where a persistent pool process is operational overhead without benefit.

Why: serverless cold-start use case (§8)

019

Testing

Chosen

cargo test + proptest + differential capture≡restore

Rejected

unit-only

When the rejected choice is right

Unit-only wins in a proof-of-concept where the test surface is tiny and the full VM is too slow to run in CI — e.g., a student project testing only the serializer in isolation.

Why: (I1/I3) the equivalence oracle

020

Fuzzing

Chosen

cargo fuzz on load(&[u8]) + reloc

Rejected

none

When the rejected choice is right

No fuzzing wins in a trusted-internal tool where all snapshot producers are under the team's control and only well-formed inputs are ever processed (e.g., a closed game-save system).

Why: (I2) hostile snapshots

021

Sanitizers

Chosen

Miri on reloc/unsafe; ASAN on heap

Rejected

none

When the rejected choice is right

No sanitizers wins in a purely safe-Rust codebase with no unsafe blocks — if the relocation code is fully abstracted behind safe Rust APIs, Miri is redundant.

Why: UB-free pointer math (§Phase 2/10)

022

Bench

Chosen

criterion (capture ms, restore ms, boot µs, op/s)

Rejected

none

When the rejected choice is right

No formal benchmarking wins for a pure research or teaching tool where absolute latency targets are not commitments.

Why: §4 targets

023

Deps

Chosen

minimal, pinned, cargo deny

Rejected

many

When the rejected choice is right

Many deps wins when time-to-feature matters more than supply-chain hygiene — e.g., a rapidly prototyped internal tool that will be replaced before it reaches production.

Why: supply chain

024

Persistence

Chosen

append-only .svm + optional fsync barrier

Rejected

DB

When the rejected choice is right

A DB backend (SQLite, RocksDB) wins when snapshots must be queryable, indexed by metadata (time, module hash), or efficiently deduplicated at the page level by a storage layer that already exists.

Why: crash-consistent single file

CI

Chosen

build+clippy+test+miri+fuzz-smoke+differential

Rejected

none

When the rejected choice is right

No CI wins only as a bootstrap shortcut in the first week before any CI infrastructure is set up; in production this is always a fail.

Why: gates

026

Repro builds

Chosen

pinned toolchain, SOURCE_DATE_EPOCH, deterministic snapshot

Rejected

floating

When the rejected choice is right

Floating toolchain wins when the project tracks Rust nightly for unstable features (const-generics, SIMD intrinsics) and reproducibility is handled at the OS-image layer instead.

Why: I3

027

Versioning (API)

Chosen

SemVer on Value/Obj/Frame/.svm schema

Rejected

implicit

When the rejected choice is right

Implicit versioning wins for a single-user, single-deployment system where all snapshots are ephemeral (deleted after restore) and no tooling depends on the schema.

Why: #344 + tooling stability

028

Compression

Chosen

optional zstd on heap-image section (post-hash)

Rejected

always/never

When the rejected choice is right

Always-compress wins when snapshot storage cost dominates (many long-lived snapshots in a cold-start pool on expensive object storage); never-compress wins on a CPU-constrained edge device where zstd decode latency exceeds the I/O savings.

Why: size vs CPU; deterministic frame

029

Content addressing

Chosen

snapshots + overlay bases keyed by BLAKE3 (link #111)

Rejected

path-only

When the rejected choice is right

Path-only wins in a simple single-machine deployment where deduplication is not needed and the extra hash computation adds measurable latency per snapshot.

Why: dedup, delta-chain identity

030

Mmap COW fork

Chosen

fork = mmap snapshot pages COW, lazy relocate

Rejected

full re-restore

When the rejected choice is right

Full re-restore wins when the base snapshot is small (≤ 8 MB) and mmap/COW overhead per fork exceeds the cost of a direct memory copy — e.g., many tiny VMs in a tight loop.

Why: fast fan-out (§8 fork)

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1 — Persistent Image (Smalltalk/Emacs unexec style)

 [VM process] ──write all memory pages to disk──► [image file]
 [reload]     ──mmap image at fixed base──────────► [resumed process]
 (no relocation: image is position-dependent; must reload at original base)

Regime where it wins: a single-process, single-machine runtime that always runs at a predictable virtual address (e.g., a classic Smalltalk image, Emacs unexec). Startup is O(1) memory mapping; no relocation overhead; simplest possible serializer. Zero-pointer-swizzle cost.

Real system: Smalltalk-80 (Squeak, Pharo image files), GNU Emacs unexec, original Lisp images (MACLISP, Interlisp).

Why this blueprint rejected it: requires a fixed virtual base address across restores. ASLR (modern OS default) invalidates position-dependent images every restore. Fork-pool (§Phase 8) requires multiple VMs at different addresses simultaneously — impossible with a fixed-base image. Cross-machine restore is impossible if the address space layouts differ. The offset-relocation design (ADR-004/006) adds ~10 ms relocation cost but buys full portability.

Alt-2 — Full Process Checkpoint (CRIU / DMTCP style)

 [host OS kernel]
    ├─ ptrace all threads (SIGSTOP)
    ├─ dump: /proc/pid/{maps,mem,fd,ns,...}
    ├─ serialize: all VMAs + kernel fd table via netlink
    └─► [criu image files]
 [restore]
    ├─ create new process with original PID/namespace
    ├─ restore all VMAs at original addresses
    └─ restore fd table via kernel helpers

Regime where it wins: checkpointing a third-party binary without source modification (a compiled C program, a Python runtime, a JVM). No cooperation from the application needed. Full POSIX state including PIDs, signals, IPC. Used for container live migration (Kubernetes pod migration), MPI job migration, forensic freezing.

Real system: CRIU (Checkpoint/Restore In Userspace), DMTCP (Distributed MultiThreaded Checkpointing), OpenVZ.

Why this blueprint rejected it: requires root and deep kernel cooperation (/proc + netlink). The implementation is ~100k lines of C handling hundreds of kernel edge cases. We own the VM — we designed it to be snapshotable. A VM-level checkpoint is ~5k lines, far safer, and does not require root or kernel patches. CRIU cannot do sub-millisecond restore (§4 p50 ≤ 1 ms) because it has to reconstruct the full OS process state; our lazy mmap path does.

Alt-3 — Whole-System Hypervisor Snapshot (Firecracker/QEMU style)

 [VMM / hypervisor]
    ├─ pause guest vCPU(s) via KVM ioctl
    ├─ snapshot: guest RAM + vCPU registers (VMSA) + device state
    ├─ dirty-page log via KVM_DIRTY_LOG (hardware-assisted)
    └─► [memory image + device state file]
 [restore]
    ├─ mmap guest RAM image
    ├─ restore vCPU via KVM_SET_REGS + KVM_SET_SREGS
    └─ restore device models (virtio queues, etc.)

Regime where it wins: checkpointing any arbitrary OS (Linux, Windows) and its applications as a unit. Hardware dirty-page tracking. Sub-100ms microVM restore (Firecracker SnapStart). Isolation: the guest cannot detect or interfere with snapshotting. Used for AWS Lambda cold-start reduction, container checkpointing in confidential computing.

Real system: Firecracker (AWS Lambda), QEMU snapshot, VMware vMotion.

Why this blueprint rejected it: requires a hypervisor (KVM), hardware virtualization, and VMM-level code. The "VM" in this blueprint is a language VM (a bytecode interpreter), not a hardware VM. Hypervisor snapshots include the entire guest OS — gigabytes of state — while we snapshot only the application's live objects (tens of MB). Hypervisor approaches cannot achieve sub-millisecond boot for a single application function because they must restore the full OS kernel context. Our lazy-mmap + swizzle-on-fault path (§Phase 8) reaches p50 ≤ 1 ms precisely because we skip the OS layer.

Alt-4 — Content-Addressed Functional Heap (Persistent Data Structure style)

 [immutable VM values]
    ├─ every "mutation" produces a new root hash
    ├─ heap = a content-addressed DAG of immutable nodes (like Git objects)
    ├─ snapshot = just the root hash (the whole history is the store)
    └─► [no serialization needed: the heap IS the snapshot]
 [restore]
    ├─ look up root hash in the object store
    └─ reconstruct the DAG lazily (lazy evaluation)

Regime where it wins: a purely functional language runtime (Haskell, Erlang-style) where mutation is rare and sharing is pervasive. Snapshots are nearly free (just record the root hash). Time-travel is trivial (keep all root hashes). Deduplication is automatic (shared subtrees). Used in content-addressed stores (Nix, Git, IPFS, some Erlang node checkpointing approaches).

Real system: Erlang/OTP hot-code upgrade + mnesia (partially), Nix store for reproducible environments, CAS-backed functional databases (Datomic).

Why this blueprint rejected it: our VM is imperative — mutation is the norm, not the exception. A content-addressed functional heap requires either an immutable value model (which breaks every SET_FIELD / STORE_LOCAL opcode) or a persistent data structure for every heap object (adds 3–5× memory overhead for structural sharing). The fast cold-start requirement (§4 p50 ≤ 1 ms) is incompatible with lazy DAG reconstruction over a content-addressed store. The dirty-page incremental approach (§Phase 7) achieves the result of "cheap incremental snapshot" without the immutability constraint.
