Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If I4's cross-reader golden-state check ever fails in production rather than CI, what does that imply about the fixture corpus's coverage relative to real developer sessions? Resolving: §20, §28.
  2. Why is the keyframe cadence (§8, ADR-18) a fixed dual threshold instead of adaptive to observed replay-seek pressure, and what would adaptive cadence break? Resolving: §8, §30.
  3. Does P5's "redaction before persistence" survive the export-time re-scan design (Phase 10) without becoming redundant work, or is the re-scan proof P5 alone was never sufficient? Resolving: §16, §22.
  4. What happens to I12's quarantine-isolation guarantee the moment the optional cross-session shared blob pool (Threat Model T2) is enabled by default rather than opt-in? Resolving: §24, §22.5.
  5. Is the 10-year long-term readability commitment (§27) actually enforceable given that ADR-07's SQLite index is a derived, rebuildable projection (I6) — does the commitment apply to the frame stream alone, or does it silently depend on SQLite's own longevity? Resolving: §27, §8.
  6. If the protocol server (Phase 9) becomes the substrate for the deferred AI-summarization feature (§3's third deferral), does P12's "telemetry never leaves the machine" survive contact with a cloud-hosted summarization model? Resolving: §21, §37.
  7. Why does the differ (Phase 7) reuse no text-diff machinery for structural state (19.6), and what would change if a future record kind were "mostly text but sometimes structural"? Resolving: §19, §32.
  8. Does ADR-12's single-writer async model remain correct once the protocol server (Phase 9) needs to serve concurrent replay queries against a session the writer is still appending to? Resolving: §9, §21.
  9. What is the actual failure mode if the 8-hour soak (Phase 11) passes but a real developer's 10-hour pairing session exceeds it — is 8 hours load-bearing or an arbitrary round number? Resolving: §23, §28.
  10. Given M10's 150 ms seek budget assumes a bounded delta-chain (§34, step 9), what happens to seek latency for a pathological session where every edit is coalesced into one keyframe-spanning delta due to a capture-scheduler bug? Resolving: §34, §20.
  11. Does the export encryption scheme (ADR-14) meaningfully protect against the shared-machine threat (T5) if the recipient key itself is generated and stored on the same compromised machine? Resolving: §24, §9.
  12. If a third-party CFS reader (built against the published conformance vectors, §23.3) diverges from Chronicle's own reader only on an edge case not covered by those vectors, is that a vector-corpus gap or a specification gap? Resolving: §23, §28.
  13. Why does capability negotiation (P10) not itself need a capability-negotiation mechanism — is there a hard floor beneath which every adapter must agree, and where is it documented? Resolving: §6, §8.
  14. Does the dual-threshold session rotation (ADR-17, 24h or 8GB) interact badly with the export partial-time-range feature (Phase 10) if a user requests a range spanning a rotation boundary? Resolving: §9, §22.
  15. What is the actual blast radius if the frame-checksum algorithm (ADR-19, CRC32C) turns out to have a practical collision under adversarial construction — does I1's crash-safety guarantee degrade gracefully or catastrophically? Resolving: §9, §7.
  16. Is P8's "keyframe is a performance dial, never correctness dial" actually testable, or only falsifiable after the fact when I4 diverges — what would a positive proof look like before Phase 8 ships? Resolving: §6, §20.
  17. Does the redaction corpus's encoded-form coverage (T9) scale to redaction rules written by a third party, given the scrubber's rule-set is currently assumed to be Chronicle-maintained? Resolving: §24, §16.
  18. If the practical scaling ceiling (§31) is "more sessions, not bigger sessions", what breaks first in the protocol server (Phase 9) when a developer has hundreds of rotated sessions and queries "across all of today"? Resolving: §31, §21.

32. Mental Models & First Principles

MM1 — A session is a log, not a database. Every feature (index, replay, diff, export) is a projection over an append-only stream, never a first-class store of its own. Predicts: any feature whose implementation requires rewriting history is architecturally wrong. Bug class avoided: mutable-index-as-truth bugs where the index and the log disagree and the index wins (it never should, I6). Resolved in §8, §27.

MM2 — Capture is a producer that must never wait on a consumer. The queue (P1/P3) is the one-way valve between "an event happened" and "an event is durable". Predicts: any design letting replay, export, or protocol-server load slow down capture is a regression, not a feature interaction. Bug class avoided: editor lag caused by the very tool built to diagnose editor lag. Resolved in Phase 1 (§13), §21.6.

MM3 — Identity is content, not location. A blob's digest (P6) is what it is, not where it sits. Predicts: two sessions can share storage safely without coordination, and a byte-for-byte identical file always dedupes, regardless of when or where it was captured. Bug class avoided: location-based cache-invalidation bugs content-addressing sidesteps entirely. Resolved in §8, Phase 2 (§14).

MM4 — A keyframe is a performance dial, never a correctness dial. Changing keyframe cadence must never change what replay produces (P8), only how fast it produces it. Bug class avoided: two readers disagreeing about state because they chose different keyframes (I4). Resolved in §8, Phase 8 (§20).

MM5 — Redaction is a gate, not a filter. Nothing crosses from capture to disk unscanned (P5); this is a hard ordering constraint, not a best-effort pass applied "eventually". Bug class avoided: a race where a secret reaches disk before the scrubber runs. Resolved in Phase 4 (§16), §24 (T1, T9).

MM6 — Fail loud beats fail quiet for a format whose entire job is being evidence. A parser that guesses at a malformed byte offset instead of naming it (P13) turns a debugging tool into another thing that needs debugging. Bug class avoided: silent truncation masquerading as a successful read. Resolved in §8, Phase 0 (§12).

MM7 — Capability negotiation beats version sniffing for any protocol with more than one implementer. An adapter declares what it can do (P10) rather than Chronicle guessing from a version string. Bug class avoided: an "if version >= X" branch matrix that silently breaks on the first host not fitting the assumed version-to-feature mapping. Resolved in §8's Adapter Contract, Phase 1 (§13), Phase 9 (§21).

MM8 — Diff must be provably symmetric, not just apparently symmetric. P11's round-trip assertion exists because "looks right on the fixtures tried" is not the same claim as "provably round-trips for any valid pair". Bug class avoided: an asymmetric diff that corrupts a replay-by-diff-chain only on inputs no one happened to test. Resolved in Phase 7 (§19).

5. Required Reading

Books

  • Kleppmann, Designing Data-Intensive Applications, chapter 3 ("Storage and Retrieval" — log-structured storage, SSTables, compaction). Extract: the append-only log as the primitive storage abstraction, and why compaction is a background concern layered on top, never inline on the write path. Applied in §8.

  • Petrov, Database Internals, chapters 2–3 ("B-Tree Basics", "File Formats") and the write-ahead log chapters. Extract: page/frame layout conventions, checksum placement, and WAL group-commit patterns. Applied in §8, and in Phase 3 (§15).

  • Silberschatz, Galvin & Gagne, Operating System Concepts, the file-system journaling chapter. Extract: journaling's crash-consistency guarantees and the "is this write atomic" question applied to a single append. Applied in Phase 3 (§15).

  • Agans, Debugging: The 9 Indispensable Rules, "Quantify" and "Understand the System". Extract: measurement before hypothesis, and know-your-own-system discipline. Applied in §7's debugging methodology and in Phase 11 (§23).

  • Hunt & Thomas, The Pragmatic Programmer, the debugging section ("Tracer Bullets", rubber-ducking as a method). Extract: instrumenting a system so that failures are self-explaining. Applied in §7.

  • Knuth, The Art of Computer Programming, Volume 3: Sorting and Searching, chapter 6.4 ("Hashing"). Extract: hash table load-factor and collision-handling tradeoffs. Applied in §8's index model and Phase 2 (§14) chunk-digest lookups.

  • Beyer, Jones, Petoff & Murphy (eds.), Site Reliability Engineering, chapter 6 ("Monitoring Distributed Systems") and chapter 15 ("Postmortem Culture"). Extract: symptom-vs-cause telemetry design, and blameless failure analysis structure. Applied in Operational Readiness (§26) and Failure Modes & Recovery (§25).

Papers

  • O'Callahan, Jashinski, et al., "Engineering Record And Replay For Deployability", USENIX ATC 2017. Contribution: a deployable low-overhead record/replay design (rr) via syscall interception and scheduling control. Relevance: the negative case study for Chronicle's non-goal boundary (§1) and the overhead-budget contrast in §4. Applied in §1 and Comparative Architecture (§33).

  • Ko & Myers, "Debugging Reinvented: Asking and Answering Why and Why Not Questions about Program Behavior", ICSE 2008 (Whyline). Contribution: a question-oriented debugging model driven by execution history. Relevance: motivates capturing why state changed, not just what it became. Applied in §2 and §7's debugging methodology.

  • LaToza & Myers, "Hard-to-Answer Questions About Code", 2010 (Evaluation and Usability of Programming Languages and Tools). Contribution: a taxonomy of developer questions that existing tools answer poorly. Relevance: the questions Chronicle's replay engine (Phase 8) is built to answer. Applied in §1 and §2.

  • Sillito, Murphy & De Volder, "Questions Programmers Ask During Software Evolution Tasks", FSE 2006. Contribution: an empirical catalogue of in-flight developer questions during maintenance work. Relevance: informs which record kinds (§8) are worth capturing at all. Applied in §2 and §8.

  • Muthitacharoen, Chen & Mazières, "A Low-Bandwidth Network File System", SOSP 2001 (LBFS). Contribution: content-defined chunking via rolling hashes to minimize retransmission. Relevance: the ancestor algorithm for Chronicle's chunker. Applied in Phase 2 (§14) and §8's chunking model.

  • Xia, Jiang, Feng, et al., "FastCDC: a Fast and Efficient Content-Defined Chunking Approach for Data Deduplication", USENIX ATC 2016. Contribution: a faster CDC algorithm using gear-hash normalization. Relevance: Chronicle's chosen chunking algorithm (ADR-06). Applied in Phase 2 (§14) and §8.

  • Myers, "An O(ND) Difference Algorithm and Its Variations", Algorithmica, 1986. Contribution: the classic minimal-edit-script diff algorithm. Relevance: the core of Chronicle's snapshot differ, generalized past line-text to structural records. Applied in Phase 7 (§19) and §8's diff semantics.

  • Hipp, "SQLite: Past, Present, and Future", Proceedings of the VLDB Endowment, 2017. Contribution: design rationale for a single-file, transactional, self-contained database format used as an application file format. Relevance: justifies SQLite as the CFS index side-table engine (ADR-11). Applied in §8 and Phase 3 (§15).

Reference Implementations

  • rr (rr-debugger/rr), directories src/record_replay/ and src/ReplaySession.cpp. Lesson: how a mature record/replay tool separates capture-time-critical code from replay-time reconstruction. Pitfall: rr's fidelity comes from syscall determinism guarantees Chronicle deliberately does not attempt (§1) — do not import that ambition by accident when reading this code. Applied in §1, Comparative Architecture (§33).

  • Git, directory builtin/pack-objects.c and packfile.c (git/git). Lesson: packfile delta-encoding and the object-digest addressing model. Pitfall: git's delta base selection is a global optimization pass unsuitable for a live append-only capture stream — don't copy the batch-repack strategy into the hot path. Applied in Phase 2 (§14), §8's domain model.

  • restic (restic/restic), directory internal/chunker/. Lesson: a production content-defined chunker implementation with tunable min/max/avg chunk size. Pitfall: restic's chunker assumes a repository-wide dedupe index fits in memory; Chronicle's per-session store must degrade gracefully past that ceiling (Phase 2 pitfalls). Applied in Phase 2 (§14).

  • asciinema (asciinema/asciinema), directory asciinema/recorder.py and the cast v2 format documented in doc/asciicast-v2.md. Lesson: a minimal, streamable terminal-session encoding (timestamp, stream id, data) proven in the wild. Pitfall: cast v2 has no built-in redaction or dedupe — Chronicle must add both layers itself. Applied in Phase 5 (§17), §8.

  • SQLite (sqlite/sqlite), directory src/pager.c and src/btree.c. Lesson: page-cache and B-tree design for a single-file embedded database used as an index. Pitfall: SQLite's own crash-safety relies on its WAL/rollback-journal mode selection — Chronicle must pick and pin one mode explicitly, not rely on defaults. Applied in §8, Phase 3 (§15).

  • zstd (facebook/zstd), directory lib/compress/ and lib/dictBuilder/. Lesson: streaming frame-based compression with dictionary training for many-small-similar-blobs corpora. Pitfall: dictionary training needs a representative corpus up front — a cold session gets no benefit until Phase 2's dictionary-seeding step runs. Applied in Phase 2 (§14).

RFCs / Specifications

  • Language Server Protocol specification. Governs the shape of editor-side capability negotiation Chronicle's IDE adapter contract (§8) mirrors. Applied in §8, Phase 1 (§13).

  • Debug Adapter Protocol specification. Governs the DAP adapter's passive-observer contract and the stack/scope/variable request shapes Chronicle records verbatim. Applied in §8, Phase 6 (§18).

  • RFC 8949, Concise Binary Object Representation (CBOR). Chosen encoding for CFS record payloads. Applied in §8, §11.

  • Chrome Trace Event format. Export target for timeline visualization of a session outside Chronicle's own viewer. Applied in Phase 9 (§21), Phase 10 (§22).

  • asciinema cast v2 format. Reference encoding for terminal capture framing. Applied in Phase 5 (§17).

  • SemVer 2.0.0. Governs CFS format version negotiation and the adapter capability compatibility rules. Applied in Compatibility & Versioning (§27), §9's ADR-02.

Glossary (§38) · 49 terms · site-wide glossary

Frame
the atomic on-disk unit: magic, sequence number, record kind, payload, checksum (§8).
Record
the CBOR-encoded payload body carried by a frame; one of the RecordKind catalogue entries (§8).
Keyframe
a Full Snapshot record bounding replay cost (P8), written on a 2-minute or 200-delta cadence (ADR-18).
Delta snapshot
a Snapshot expressed as a prior snapshot digest plus a chain of EditDelta/state-change records (§8).
Content-defined chunking (CDC)
splitting a blob into variable-length chunks at content-determined boundaries (FastCDC gear hash, ADR-06) so identical sub-sequences dedupe regardless of surrounding-byte shifts.
Blob digest
the content-address (SHA-256, ADR-04) identifying a chunk; the only identity a blob has (P6).
Index footer
the CFS region mapping sequence↔offset, timestamp↔keyframe, digest↔ offset, and kind↔sequence-list, stored as an embedded SQLite page image (ADR-07).
Torn write
a frame left incomplete by a crash mid-write; detected via checksum mismatch on the trailing frame (I1).
Sealed session
a session whose Seal record and whole-file digest have been written, making it immutable (I8).
Replay cursor
the ReplayCursor object performing keyframe-plus-delta-chain state reconstruction at an arbitrary seek target (Phase 8).
Redaction rule
a pattern (regex or entropy-heuristic) in the scrubber's active rule set (P9, ADR-13) that triggers quarantine.
DAP
Debug Adapter Protocol; governs Chronicle's passive-observer debugger integration (ADR-10, §5).
PTY tap
the mechanism by which the terminal adapter observes a pseudo-terminal's input/output stream without interposing on it.
CFS
Chronicle Format Specification; the versioned, content-addressed, append-only on-disk session format (§8).
Seal-then-advance
the writer protocol of writing frame bytes, computing checksum, then only advancing the cursor (I1, Phase 0).
Quarantine
the state of a record that failed or timed out a redaction scan, held pending manual scrub rather than dropped or persisted raw (I5).
Capability negotiation
the AdapterCapabilities/ClientCapabilities handshake replacing version-sniffing (P10).
Coalescing
merging adjacent same-kind events (e.g., rapid cursor moves) under backpressure instead of blocking or dropping (P3).
Keyframe cadence
the dual threshold (time or delta-count) governing how often a Full snapshot is written (ADR-18).
Content address
an identifier derived solely from a byte sequence's digest, never from location (P6, MM3).
Dedupe ratio
raw bytes referenced ÷ unique bytes stored (§8, M9).
Snapshot
the reconstructable state of tracked buffers, debugger frame, and terminal cursor at a point in time; Full or Delta (§8).
Frame checksum
the CRC32C (ADR-19) validating a single frame's integrity, distinct from the whole-file seal digest.
Whole-file digest
the SHA-256 (ADR-04) over the entire sealed file, computed once at seal time (I8).
EditDelta
a record describing a buffer change relative to a declared base BufferState digest (I9).
BufferState
a full, self-contained snapshot of one tracked buffer's content.
VcsPosition
HEAD ref, branch name, and dirty-file digest set, captured as a VcsCheckpoint record.
TerminalChunk
a timestamped, stream-tagged (stdin/stdout) byte fragment (ADR-15).
Chunk store
the content-addressed blob storage layer, deduped via CDC (§8, Phase 2).
Capture scheduler
capture-sched's bounded queue and batcher enforcing P1/P3's never-block, coalesce-under-load discipline.
Scrubber
the redaction engine scanning records before persistence (P5, scrubber crate).
Differ
the differ crate computing symmetric structural diffs (P11, Myers 1986, ADR-16).
Replay engine
the replay crate's seek/reconstruct machinery (Phase 8).
Protocol server
the cross-tool local RPC surface (protocol-server crate, ADR-11).
Live-tail
subscribing to newly sealed frames of an in-progress session (P7, Phase 9).
Export packager
the export crate's archive-and-encrypt pipeline (Phase 10, ADR-14).
Envelope encryption
the X25519 + ChaCha20-Poly1305 recipient-scoped scheme used for exports (ADR-14).
Conformance fixture
a named .cfs file exercising a specific format or behavior guarantee, shipped the same day as the change it defends (P4).
Conformance harness
the runner comparing every fixture's actual outcome to its golden expectation, gating CI (Phase 11).
Third-party conformance vector
a published fixture subset letting an external CFS reader implementer self-verify (Phase 11).
Fault injection
deliberately simulated failures (torn write, ENOSPC, killed process) used to test recovery paths beyond unit-tested happy paths.
Soak test
an extended-duration run (8 hours) asserting no resource-growth regressions under continuous realistic load.
Rotation
starting a new session file upon reaching the 24h/8GB threshold (ADR-17).
RTO
recovery time objective; the daemon-crash-to-resumed-capture budget (§4, M15).
SBOM
software bill of materials; published per release (§29) for dependency audit.
Provenance attestation
a signed record binding a release artifact to its exact build and commit (§29).
Golden fixture / golden state
the recorded expected output a conformance test compares against (I4, §28).
Capability violation
a call for an operation outside a negotiated capability set, rejected before dispatch (I10).
Rolling upgrade
independently upgrading daemon and adapter without losing capture, guaranteed by additive-only capability evolution (§27). ---
