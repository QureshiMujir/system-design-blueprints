⬜ Phase 0 — Skeleton, CFS v0 Writer/Reader, CI §12

Objectives

Establish the workspace skeleton, freeze CFS v0's magic/header/frame layout (§8), ship a minimal writer and reader that round-trip a session with no adapters attached, and stand up CI so every subsequent phase inherits a working build/test/fixture gate (P4).

Deliverable

cfs-core crate: header/frame/record/seal modules; a chronicle record --noop CLI command that opens, writes three synthetic frames, and seals a session; a chronicle inspect command that dumps frame headers; a green CI pipeline.

Acceptance

A round-tripped session of 3 synthetic frames re-reads byte-identical; write-to-seal latency p95 ≤ 12 ms per §4; cargo clippy zero warnings; CI fails the build if a RecordKind variant is added without a corresponding conformance/fixtures/ entry (P4 enforcement begins here, not later).

Fixtures

fixtures/p0_minimal_session.cfs — 3 frames, SessionStart→2 synthetic records→Seal, expected: byte-identical round trip. fixtures/p0_truncated_header.cfs — header length field overstated, expected: reject at open with byte-offset error (P13). fixtures/p0_unsealed.cfs — no Seal record, expected: reader reports session as Flushing-recoverable, not corrupt.

Pitfalls

Forgetting to reserve tag-range headroom in RecordKind before freezing v0 — breaks additive compatibility (P2) the moment Phase 1 needs a new kind. Writing the checksum before the payload is fully flushed to the OS (defeats I1's crash guarantee — must be flush-then- checksum-then-advance, verified under fault injection, not just unit-tested happy path). Treating CI green as format-frozen without an explicit version tag — CFS v0 must be tagged, not inferred from "whatever main branch currently does".

⬜ Phase 1 — IDE Adapter, Buffer/Edit Capture §13

Objectives

Ship the first real capture source: a VS Code extension (ADR-20) emitting BufferOpen, BufferEdit, BufferClose, CursorMove, and SelectionChange records through the capture scheduler (P1, P3) into the CFS writer built in Phase 0.

Deliverable

adapters/ide-vscode extension; capture-sched crate with queue/batcher; end-to-end demo: typing in VS Code produces a growing, valid CFS session file inspectable via chronicle inspect.

Acceptance

Added editor-event latency ≤ 1 ms p95 per §4, measured via benchmarks/capture_overhead; queue never blocks the extension host thread (verified via a synthetic 10,000-event/sec burst test); every EditDelta's base_digest matches its predecessor's result_digest (I9) across a 30-minute synthetic typing fixture.

Fixtures

fixtures/p1_edit_chain.cfs — 200 sequential edits to one buffer, expected: base_digest chain validates end-to-end. fixtures/p1_coalesced_cursor_burst.cfs — 5,000 synthetic cursor events in 1 second, expected: coalesced to under 50 CursorMove records. fixtures/ p1_capability_mismatch.cfs — adapter declares no BufferEdit support, expected: core drops edit events at negotiation, not per-call (I10).

Pitfalls

Computing base_digest/result_digest synchronously on the extension host thread — violates P1 by putting hashing on the critical path; must be pushed to the scheduler's worker context. Assuming VS Code's document-change events arrive in document order under IME/composition input — they do not always, and naive sequencing corrupts the edit chain (I9 violation). Treating a rename (buffer path change with same content) as a fresh BufferOpen — loses the edit-history linkage a developer would expect.

⬜ Phase 2 — Chunking, Dedupe, Compression §14

Objectives

Implement the FastCDC chunker (ADR-06) and content-addressed blob store, and layer zstd compression (ADR-05) over stored chunks, to bring session growth from the pre-dedupe to the post-dedupe/compress target in §4.

Deliverable

chunker crate (cdc.rs, store.rs); dedupe/compression wired into the CFS writer's blob region; benchmarks/dedupe_ratio harness measuring both ratios against §4's targets.

Acceptance

Dedupe ratio ≥ 4:1 on a fixture of 50 repeated buffer saves with 90% unchanged content; residual-chunk zstd ratio ≥ 3:1; combined session growth ≤ 4 MB/hour on the Phase 1 30-minute typing fixture rerun through this phase's pipeline; digest recomputation on read adds ≤ 10% to reader latency.

Fixtures

fixtures/p2_repeated_save.cfs — same 2 MB file saved 50 times with small edits, expected: dedupe ratio ≥ 4:1. fixtures/p2_large_binary.cfs — a 10 MB near-random binary buffer, expected: dedupe ratio ~1:1 (documents the defeat case, doesn't regress it as a bug). fixtures/p2_digest_collision_injected.cfs — a deliberately corrupted digest-to-chunk mapping, expected: reader flags the specific blob (I2), not the whole session.

Pitfalls

Choosing a chunk size too small — dedupe improves marginally but per-chunk overhead (digest + index entry) dominates and net storage grows, not shrinks. Training the zstd dictionary once and never refreshing it — a dictionary trained on Phase 0/1 fixtures degrades as real-world code shapes diverge from synthetic ones. Assuming chunk boundaries are stable across a file rewrite that shifts all bytes by one (e.g., inserting a single character at the top of a file) — FastCDC's whole point is that they mostly are, but a naive fixed-size chunker would defeat dedupe here, and this must be regression-tested, not assumed.

⬜ Phase 3 — Crash-Safe Append, Index Footer §15

Objectives

Harden the writer against process crashes and disk-full conditions, and implement the index footer (§8's Timeline/Index Model) as a rebuildable SQLite-backed side table (ADR-07, Hipp 2017), closing out I1 and I6 with real fault-injection evidence, not just design intent.

Deliverable

cfs-index crate (builder.rs, query.rs); daemon startup recovery logic in crates/daemon; a fault-injection test harness wrapping the filesystem layer to simulate torn writes and disk-full mid-append.

Acceptance

RTO ≤ 2 s from simulated daemon crash to a new Recording session (§4); at most one sealed frame's worth of data at risk per crash, verified across 500 randomized crash-injection runs; index rebuild from a 1 GB fixture completes and matches the incrementally built index byte-for-byte in its digest-to-offset mapping.

Fixtures

fixtures/p3_torn_write_mid_payload.cfs — crash injected mid-BufferEdit payload write, expected: reader recovers to the last complete frame per §8's torn-write failure path. fixtures/p3_disk_full_during_flush.cfs — simulated ENOSPC during Flushing, expected: writer transitions to Suspended, no partial Seal written. fixtures/ p3_index_rebuild_1gb.cfs — large session, expected: rebuilt index matches incremental index.

Pitfalls

Fsyncing on every single frame — meets crash-safety trivially but blows the p50 write-latency budget (§4); group-commit is required, not optional. Treating "index missing" and "index stale" as the same recovery path — a missing index triggers a full rebuild (I6), a stale index (e.g., session grew since last rebuild) should ideally only need an incremental catch- up, and conflating them wastes rebuild time on large sessions. Assuming ENOSPC is the only disk-full signal — some filesystems report quota errors differently, and the writer's error handling must not special-case one error code only.

⬜ Phase 4 — Redaction / Scrubber §16

Objectives

Implement the redaction/scrubber engine (ADR-13) upstream of the chunker (P5), enforcing I3 and I5, and validate it against a corpus of known secret shapes including encoded forms before any capture is allowed to leave the local machine.

Deliverable

scrubber crate (rules.rs, entropy.rs); a default rule-set config shipped with Chronicle covering common credential shapes (API key prefixes, private key PEM headers, JWT structure, connection-string patterns); a redaction conformance corpus in conformance/fixtures/redaction/.

Acceptance

Redaction scan throughput ≥ 40 MB/s per core (§4); zero false negatives on the release- blocking corpus (P9) across ≥ 200 labeled secret-shape samples including base64/hex-encoded variants; quarantine queue drains within 5 s under normal load, never silently discards a record (I5).

Fixtures

fixtures/p4_plain_api_key.cfs — a buffer containing an unencoded API-key-shaped string, expected: redacted before persistence. fixtures/p4_base64_encoded_secret.cfs — the same secret base64-encoded inline, expected: caught by the entropy heuristic, not just regex. fixtures/p4_scrub_timeout_injected.cfs — a payload engineered to exceed the scan time budget, expected: record quarantined (I5), never written raw and never dropped.

Pitfalls

Relying on regex alone and treating entropy scanning as optional — misses exactly the encoded-secret case P9 exists to catch; both must run on every record, not just the "cheap" regex pass. Scanning after chunking instead of before — violates P5 outright and is a design regression, not a tuning issue, if it ever happens. Setting the entropy threshold too aggressively — flags ordinary compiled binary content or minified JS as high-entropy "secrets", producing redaction noise that erodes trust in the tool. Treating the quarantine queue as a dead-letter queue that operators must manually clear — it must self-drain via background re-scan (I5), with manual clearing only as a last resort.

⬜ Phase 5 — Terminal + Test-Result Capture §17

Objectives

Add the PTY tap and test-runner integration, emitting TerminalOutput/TerminalInput and TestResult records (§8's catalogue), while defending against the two failure modes unique to this source: unbounded growth from a hot terminal loop, and clock-driven ordering bugs.

Deliverable

PTY tap wired into daemon; TestResult parsers for at least one test framework per supported language ecosystem in Phase 0-1's target IDE; benchmarks extended to include a sustained-terminal-output stress case.

Acceptance

A sustained 10 MB/s synthetic terminal-output fixture produces session growth within the §4 post-dedupe budget, not unbounded growth; frame ordering remains correct (I7) even when the system clock is stepped backward mid-capture (simulated NTP correction); TestResult parsing correctly attributes pass/fail/duration for ≥ 95% of a labeled fixture corpus of real test- runner output.

Fixtures

fixtures/p5_hot_terminal_loop.cfs — a synthetic yes-style infinite-output loop capped at a fixed duration, expected: coalesced growth within budget, not runaway session size. fixtures/p5_clock_jump_mid_session.cfs — simulated backward clock step during capture, expected: sequence-number ordering (I7) unaffected. fixtures/p5_test_run_mixed_results.cfs — a test run with passes, failures, and skips, expected: TestResult records match the labeled expected output exactly.

Pitfalls

Using wall-clock timestamps as the sort key for terminal chunks instead of sequence number — directly violates I7 and produces reordered replay under any clock adjustment. Failing to cap unbounded terminal growth before it reaches the chunker — a hot loop can produce output faster than the scrubber's throughput budget (§4), and without a coalescing circuit-breaker specific to this source, the whole pipeline backs up (violates P1 transitively). Assuming test-runner output format is stable across framework versions — brittle parsers silently misattribute results; must degrade to "unstructured terminal output only" rather than emit wrong TestResult data.

⬜ Phase 6 — DAP Debugger-State Capture §18

Objectives

Implement the passive DAP proxy adapter (ADR-10) capturing DebuggerAttach, DebuggerStop, and DebuggerVariable records without ever altering debugger behavior or issuing side-effecting requests (I10).

Deliverable

adapters/dap-shim crate; passive-proxy wiring validated against at least one real DAP debug adapter (e.g., a common language's official debug adapter) in an integration test.

Acceptance

Zero observed behavioral difference in debuggee execution with the proxy attached versus detached, verified via a differential test running the same debug session both ways; DebuggerFrame capture adds ≤ 5 ms to the stop-event handling path; capability violations (I10) are rejected at the negotiation boundary in 100% of a fixture set exercising unsupported-operation attempts.

Fixtures

fixtures/p6_passive_proxy_parity.cfs — same debug session captured with and without the proxy, expected: identical debuggee-observable behavior. fixtures/ p6_capability_violation_attempt.cfs — a scenario where Chronicle's own code is made to attempt an unsupported operation, expected: rejected pre-dispatch (I10). fixtures/ p6_large_variable_tree.cfs — a debug session with a deeply nested object graph, expected: digest-referenced, not inlined, staying within the memory ceiling (§4).

Pitfalls

Issuing an evaluate request to "helpfully" pre-fetch a watch expression's current value — directly violates the passive-observer contract (ADR-10, I10) and can alter program state in languages with computed/lazy properties. Assuming all DAP adapters support the same paging model for large variable collections — must check AdapterCapabilities per session, not hardcode against one debugger's behavior observed during development. Buffering an unbounded number of stack frames for deep recursion — must cap capture depth with a documented, configurable limit rather than risk the memory ceiling (§4).

⬜ Phase 7 — Snapshot Diffing §19

Objectives

Implement the snapshot differ (§8's diff semantics) generalizing Myers' O(ND) algorithm (Myers 1986, ADR-16) from line-text diffs to structural diffs across buffers, debugger state, terminal cursor, and VCS position, satisfying P11's symmetry guarantee.

Deliverable

differ crate (diff.rs); a chronicle diff <seq_a> <seq_b> CLI command producing a human-readable structural diff; the P11 symmetry assertion wired into conformance/harness.

Acceptance

Diff computation for a 10,000-line buffer completes in ≤ 200 ms; P11 symmetry holds across 100% of the conformance fixture corpus (zero exceptions permitted — this is a correctness invariant, not a performance target); structural diffs correctly identify debugger scope additions/removals across a fixture with nested variable scopes 5 levels deep.

Fixtures

fixtures/p7_text_diff_roundtrip.cfs — two buffer snapshots with a 200-line interior edit, expected: diff + inverse-apply reproduces original digest exactly. fixtures/ p7_structural_debugger_diff.cfs — two debugger snapshots with added/removed scope variables, expected: correct add/remove/modify triples. fixtures/p7_cross_version_diff.cfs — two snapshots from schema-compatible but different minor CFS versions, expected: diff succeeds per P11's "including across schema-compatible format versions" clause.

Pitfalls

Applying the text-diff algorithm naively to non-text structural state (e.g., treating a debugger scope tree as a flat text blob) — produces technically-valid but semantically useless diffs; structural state needs its own comparison keyed by stable identifiers, not byte position. Skipping the round-trip symmetry assertion because "the algorithm is proven correct" (Myers 1986 proves the text case; the structural generalization is Chronicle's own code and needs its own proof-by-test). Assuming diff is cheap enough to compute on every frame eagerly — it is a demand-computed capability (§3), not part of the write path, per P1's critical-path rule extended to reads that could stall a UI.

⬜ Phase 8 — Replay Engine & Seek §20

Objectives

Ship the replay crate's ReplayCursor: reconstruct a Snapshot at an arbitrary sequence number or timestamp by combining the nearest keyframe with a forward delta-chain apply, honoring P8 (keyframes bound cost, never correctness) and I4 (replay determinism across independent readers).

Deliverable

replay crate (cursor.rs, seek.rs); chronicle replay --at <ts> CLI producing a human-readable reconstructed-state dump; a cross-reader golden-state comparator wired into conformance/harness (I4).

Acceptance

Seek latency p95 ≤ 150 ms per §4 measured against examples/multi-hour-session; two independent reader processes replaying the same session to the same sequence number produce byte-identical reconstructed-state digests across 100% of fixtures/p8_* (I4, zero divergence permitted); live-tail seek against a still-Recording session succeeds without the writer observing any added latency (P1 extended to a new read path).

Fixtures

fixtures/p8_seek_midkeyframe.cfs — three keyframes, seek target between keyframe 2 and 3, expected: reconstructed state matches a golden digest. fixtures/p8_live_tail.cfs — session left Recording (unsealed), expected: replay succeeds up to the last checksummed frame, no error. fixtures/p8_delta_apply_failure.cfs — an EditDelta with an injected base-digest mismatch, expected: I9 fallback to the nearest keyframe, delta_apply_failures incremented. fixtures/p8_torn_frame_seek.cfs — seek target inside a deliberately torn last frame, expected: resolves to the nearest fully-checksummed frame per I1.

Pitfalls

Replaying from session start on every seek instead of the nearest keyframe defeats P8 entirely and must be caught by benchmarking that the keyframe path is actually exercised, not assumed from code review alone. Treating an I4 divergence as a new replay-crate bug in isolation is a common misdiagnosis — per 19.9's stable-ordering lesson, divergence is frequently a differ-side non-determinism surfacing downstream, not a replay bug at all. Assuming delta-chain application is idempotent across repeated seeks to the same target is false; the cursor must reset to the keyframe base every seek, never incrementally patch a retained mutable buffer, or repeated seeks silently diverge from a fresh reader's result. Live-tail replay that races the writer's in-flight frame by trusting raw end-of-file instead of the writer's last-advanced offset will read a torn frame as sealed and corrupt the reconstructed state.

⬜ Phase 9 — Cross-Tool Protocol Server §21

Objectives

Ship protocol-server, a local RPC surface (ADR-11, ADR-21) letting third-party tools discover, query, and subscribe to live or sealed sessions, honoring P7 (a session is useful before it is complete) and I10 (capability claims are always honored, never sniffed).

Deliverable

protocol-server crate (rpc.rs, subscribe.rs); a daemon-embedded server; a reference third-party client stub in examples/ demonstrating negotiate → subscribe → replay-at round trip.

Acceptance

Metadata-query round-trip latency p95 ≤ 20 ms on loopback socket; a newly sealed frame reaches a subscribed client within 100 ms p95 of its checksum being written; a client calling an operation outside its negotiated ClientCapabilities is rejected with a named capability-violation error against fixtures/p9_capability_violation.cfs, zero silent no-ops permitted (I10).

Fixtures

fixtures/p9_negotiate_subscribe_replay.cfs — a scripted negotiate → subscribe → replay-at sequence, expected: correctly ordered responses matching a golden transcript. fixtures/p9_cross_user_socket.cfs — a connection attempt from a different OS user, expected: rejected at the socket-permission layer (T8). fixtures/p9_capability_violation.cfs — a client calls query(sessionState, at:) without negotiating it, expected: rejected, capability_violation_total incremented. fixtures/p9_live_tail_race.cfs — a subscriber connects mid-write, expected: no torn-frame delivery.

Pitfalls

Exposing the RPC surface over TCP loopback "for convenience" reopens exactly the cross-user/cross-container attack surface ADR-08 chose Unix sockets to avoid. Delivering a live-tail frame before its checksum is verified violates the same seal-then-advance discipline (I1) the writer itself follows — subscribers must see only checksum-validated frames, never a raw tail read. Unbounded list-records-by-kind queries against the index (ADR-07) can starve the writer's own index access if not rate-limited or queued on a separate path, extending P1's critical-path rule to a query surface that didn't exist before this phase. Silently expanding a client's effective capabilities because repeated calls "seem to work" violates P10 outright — every served operation must trace to an explicit negotiated capability, not inferred tolerance.

⬜ Phase 10 — Export, Sharing & Encryption at Rest §22

Objectives

Ship the export crate: shareable, optionally recipient-encrypted session archives (ADR-14) that pass a mandatory pre-export redaction re-scan (P5, P9) and never co-locate decryption key material with the artifact (I11).

Deliverable

export crate (pack.rs); chronicle export CLI with --recipient <pubkey> and --redact-only modes; export manifest schema documented in docs/; I11's static no-co-location check wired into the packager's own test suite.

Acceptance

Export of a 4 GB sealed session completes in ≤ 90 s wall clock on reference hardware (throughput ≥ 45 MB/s, above §4's 40 MB/s scrubber floor); zero archives across fixtures/p10_* contain co-located key material (I11, 100% pass, static check); a 10-minute partial export from a 3-hour session replays standalone via Phase 8's cursor with no dangling references to excluded state.

Fixtures

fixtures/p10_full_export_roundtrip.cfs — export then decrypt-and-replay, expected: byte-identical reconstructed state to the source session. fixtures/ p10_key_colocation_reject.cfs — a manifest deliberately fed embedded key material, expected: packaging aborts before any artifact is emitted (I11). fixtures/ p10_partial_time_range.cfs — a 10-minute sub-export of a 3-hour session, expected: independently replayable, no dangling state references. fixtures/p10_quarantine_isolation.cfs — a session containing a quarantined record, expected: the exported shared-index has zero references to the quarantined digest (I12). fixtures/p10_torn_export.cfs — export killed mid-write, expected: the partial artifact is detected and rejected on next open, never treated as valid.

Pitfalls

Treating capture-time redaction as sufficient and skipping the export-time re-scan ignores that rule-set updates (P9) postdating capture leave an older session exposed to today's known-secret corpus unless re-scanned at export. Placing the decryption key in a "convenience" sidecar beside the archive technically satisfies "not embedded in the manifest" while violating I11's actual intent — the check must cover co-location, not only manifest content. Assuming partial time-range export can byte-slice the CFS frame stream directly breaks keyframe/delta-chain integrity (P8); a fresh self-contained session must be materialized via replay instead. Quarantined digests may already have entered the optional cross-session shared pool (Threat Model T2) before quarantine was applied, so isolation must be re-checked at export time, never assumed from capture-time state alone.

⬜ Phase 11 — Conformance Suite & Performance Hardening §23

Objectives

Close the loop P4 opened in Phase 0: assemble the full conformance harness across every fixture and phase, stand up the CFS-reader fuzz target as the primary fuzz surface, run an 8-hour soak, and gate every §4 budget in CI.

Deliverable

conformance/harness runner invoked via scripts/run-conformance.sh; fuzz/targets/ {cfs_reader,index_rebuild,redaction_scan}; an 8-hour soak script under benchmarks/; a published third-party conformance vector subset in conformance/golden/; a CI performance- regression gate covering every §4 row.

Acceptance

100% of fixtures/p0_* through p10_* pass with zero mismatches (P4, no exceptions); cfs_reader runs 24 CPU-hours with zero crashes, hangs, or sanitizer failures before exit; the 8-hour soak completes with RSS never exceeding 400 MB burst / 150 MB steady-state (§4) and zero unbounded queue growth; all 15 §4 constraint rows have a CI-enforced gate, verified by an explicit gate-to-constraint count (15 of 15, zero ungated).

Fixtures

fixtures/p11_full_corpus_manifest.cfs — a manifest fixture enumerating every prior fixture and its expected outcome, used to catch an accidentally deleted fixture. fixtures/ p11_torn_write_injection.cfs — a fault-injection driver killing the writer at 12 distinct byte offsets within a frame, expected: I1 recovery at every offset. fixtures/ p11_enospc_midframe.cfs — simulated ENOSPC during frame-payload write, expected: the writer aborts the frame cleanly and the next open shows the correct truncation point. fixtures/ p11_thirdparty_vector_01.cfs through _12.cfs — the published external conformance vector set. fixtures/p11_malformed_fuzz_regression_*.cfs — fuzz-discovered crashers, pinned permanently once fixed, never deleted, per P4.

Pitfalls

Treating "24 CPU-hours, zero crashes" as proof of absence of bugs mistakes a lower bound for a guarantee; pair fuzz hours with coverage-guided corpus review of which record kinds the fuzzer has actually reached. Running the 8-hour soak on idle hardware with a synthetic no-op loop instead of all three adapters under simulated developer activity proves nothing about real memory growth. Gating performance regressions against a baseline captured on noisy, shared CI hardware produces flaky thresholds that erode trust in the gate faster than no gate at all — the baseline needs pinned hardware or a statistically debounced multi-run capture. Publishing third-party conformance vectors before the format is genuinely frozen risks breaking an external implementer's trust in the compatibility promise (§27) before Chronicle has even shipped externally.
