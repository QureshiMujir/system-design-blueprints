Project Number: 4

Project Name: Chronicle

1. Goal & Scope

Chronicle is a developer-context capture and replay protocol. A capture engine hooks into the IDE (via a Language Server Protocol-adjacent extension host) and the debugger (via the Debug Adapter Protocol) and records structured, deduplicated snapshots of a developer's working state: open buffers and their edit deltas, cursor and selection position, terminal and build output, test results, debugger stack/locals/watch state, and version-control position. Snapshots are serialized into the Chronicle Format Specification (CFS): a versioned, content-addressed, append-only on-disk session format. A diffing engine compares two snapshots and produces a structural delta. A cross-tool protocol server exposes a session over a local RPC surface so other tools (a CLI, a web viewer, a second IDE) can query or replay it without linking against Chronicle internals. Chronicle answers one question precisely: "what was the state of my workspace, in enough fidelity to explain a bug or reconstruct a debugging session, at time T" — and it answers that question from a single portable file, offline, indefinitely.

Phase-0 deliverable, as modules:

  1. cfs-core — CFS binary reader/writer, session header, frame framing, checksums.
  2. capture-sched — capture scheduler: batches editor events into frames off the UI thread.
  3. ide-adapter-shim — minimal buffer-open/edit event source (stubbed, real adapter in Phase 1).
  4. cli — chronicle record / chronicle inspect skeleton commands.
  5. ci — build matrix, fixture corpus, conformance harness skeleton.

Boundaries: Chronicle captures and reconstructs developer context — the human-facing state of an editing and debugging session. Non-goals, stated explicitly: Chronicle is not a deterministic instruction-level record/replay debugger like rr (O'Callahan et al., USENIX ATC 2017) — it does not capture machine state, syscall sequences, register files, or memory images, and it cannot replay non-deterministic program execution bit-for-bit. It is not a full screen-recording tool. It is not a source-control system (it references VCS position, never replaces it). It is not an APM/observability pipeline (out of scope: metrics aggregation, distributed tracing across services). It does not attempt cross-machine binary compatibility of process state — only textual/structural developer context.

Deployment model: a per-workspace background daemon (chroniclesd) started by the IDE extension on workspace open, communicating over a local Unix domain socket (named pipe on Windows). The daemon owns one open CFS file (session) at a time per workspace root; multiple workspace roots run independent daemon instances. No network service is required for local operation; the cross-tool protocol server (Phase 9) listens on the same local socket family using a distinct namespaced path. Export/share (Phase 10) is the only phase requiring network I/O, and only outbound, opt-in.

Users/operators: individual developers (primary), a team lead reviewing a shared session before code review, a support engineer asking a customer to attach a session to a bug report, and — as a downstream consumer via the cross-tool protocol — an AI coding assistant that queries recent context instead of re-deriving it from scratch. Operators of the daemon are the developers themselves; there is no multi-tenant server operator role until Phase 9's protocol server is deployed in a shared-machine configuration, which is covered by Threat Model row T5.

What later phases unlock: Phase 2 (chunking/dedupe) makes multi-hour sessions storable in tens of megabytes instead of gigabytes. Phase 4 (redaction) makes sessions safe to share outside a trust boundary. Phase 6 (DAP capture) makes a session sufficient to answer "why did this test fail" without re-running the debugger. Phase 8 (replay) turns a session from an inert file into a scrubbable timeline inside the IDE. Phase 9 (protocol server) turns Chronicle from a single-tool feature into a protocol other tools build on.

Language: Rust for cfs-core, capture-sched, the chunker/store, the differ, the replay engine, and the protocol server — chosen for predictable latency (no GC pause can land on the capture path per design principle P1), memory safety for a process that parses untrusted CFS files (including other people's shared sessions, per Threat Model row T3), a mature binary-format ecosystem (zstd, CBOR via ciborium, content hashing), and a single static binary the daemon and CLI both ship as. IDE-side adapters are written in the native extension language of each host (TypeScript for VS Code, per the dominant extension ecosystem) and talk to the Rust daemon over the local IPC socket using the CFS wire records directly — no adapter reimplements the format.

Rejected languages: Go — rejected because its garbage collector introduces latency spikes that risk violating the P99 snapshot-write budget in System Constraints (§4) at exactly the moments capture volume is highest (a large paste, a big test run); Go's goroutine model is otherwise a good fit and is revisited if profiling later shows GC is not the dominant tail (tracked as a design note, not a PhaseDeferred). C++ — rejected for the daemon core because it is a long-lived process parsing untrusted, possibly adversarial CFS files (shared sessions, malformed-file fuzz targets in Phase 11), and a memory-safety bug in the parser is a direct path to an RCE via a shared session file (Threat Model row T3); C++ remains acceptable for narrow, sandboxed native adapter shims if a host IDE requires it. Python — rejected for any component on the capture path; interpreter overhead and the GIL make it unable to meet the per-keystroke-batch overhead budget in §4 even before considering packaging complexity for a background daemon.

Prerequisites: a CFS v0 format frozen before any adapter is written (Phase 0); a redaction rule set reviewed before any capture leaves the local machine (Phase 4, gating Phase 9 and Phase 10); a conformance fixture corpus before claiming any format compatibility guarantee (Phase 11, but seeded from Phase 0 onward per Design Principle P4).

Timeline: 12 phases (Phase 0 through Phase 11), each independently shippable and gated by its own acceptance criteria; no phase depends on functionality from a later phase. Two capabilities are deliberately deferred past Phase 11: full deterministic replay of captured process memory is PhaseDeferred("Alternative Architectures (Roads Not Taken)"), and multi-user live-collaborative session merge is PhaseDeferred("Deferred Features Register"). A third deferral, AI-assisted session summarization, is PhaseDeferred("Comparative Architecture") pending the cross-tool protocol (Phase 9) existing as a stable substrate for it.

2. Why Build This

  • On-disk format design: content addressing, framing, checksums, append-only invariants.

  • Chunking and dedupe: content-defined chunking, rolling hashes, compression ratio tuning.

  • Low-overhead instrumentation: hooking a live editor and debugger without perturbing it.

  • Protocol design: LSP/DAP-style adapter contracts, capability negotiation, versioning.

  • State machines: capture lifecycle, crash-safety, torn-write recovery.

  • Diffing algorithms: structural diff over heterogeneous snapshot state, not just text.

  • Security engineering: redaction correctness, encryption at rest, threat modeling a file format that becomes evidence.

  • Systems performance: p50/p95/p99 latency budgets on a path shared with a human's keyboard.

What Mastery Looks Like

  • You can explain why capture must be off the critical path (P1) and demonstrate the queue depth telemetry that proves it, built in Phase 1.

  • You can hand a stranger a CFS file from Phase 3 and they can parse a truncated/torn-write copy of it and know exactly which suffix bytes are ignorable — because the format is self-describing per Invariant I1.

  • You can explain, with the FastCDC chunk-boundary math, why editing one line of a 50 MB generated file (Phase 2) does not re-store the whole file.

  • You can produce a redaction false-negative on a base64-encoded secret on purpose (Phase 4) and then close it, because you understand the scan is content-aware, not pattern-blind.

  • You can replay a session (Phase 8) and seek to an arbitrary timestamp in under the Performance Engineering seek-latency target, and explain why keyframes make that possible.

  • You can defend, against a skeptic, why Chronicle's forty-line diagram is not "just rr for editors" — because you can enumerate exactly what rr guarantees that Chronicle does not, and why that tradeoff is correct for this problem (§1 non-goals).

  • You can take a stranger's exported, encrypted session (Phase 10) and verify, offline, that it has not been tampered with — because the seal record and signature chain make tampering detectable, not just discouraged.

IDE adapter: subscribes to the host editor's document and selection change events, buffer open/close, and VCS HEAD movement; translates host-native events into CFS record drafts; never blocks the editor's UI thread (P1).

DAP adapter: attaches as a passive DAP middleman/observer, capturing stack frames, scope variables, watch expressions, and breakpoint state on each stop event; never issues evaluate requests that could have side effects (Pitfall in Phase 6).

Terminal/PTY tap: wraps the integrated terminal's pseudo-terminal, capturing raw byte output and timing, modeled after the asciinema cast v2 event stream.

Capture scheduler: the single choke point all three sources feed into; owns the bounded event queue, batches events into frames at the configured cadence (§4), and applies backpressure by coalescing rather than blocking (P1, P3).

Redaction/scrubber: scans every record's payload against the active RedactionRule set before any byte reaches the chunker (P9); a record that fails to scan cleanly within budget is quarantined, never silently dropped (I5).

Chunker + content-addressed store: splits blob payloads into content-defined chunks (FastCDC, Xia et al. 2016) and stores each chunk once, addressed by digest, feeding the CFS writer only new digests.

CFS writer: appends frames to the open session file, sealing each frame with a checksum before the next is started (I1); never rewrites a previously sealed byte range.

Index: a side table (SQLite-backed, per ADR-11) mapping timestamps, record kinds, and digests to byte offsets, rebuildable from the frame stream if it is lost or stale (I6).

Snapshot differ: computes structural deltas between two snapshots on demand, using an O(ND) core (Myers 1986) generalized to non-text state.

Replay engine: reconstructs a BufferState/debugger/terminal view at an arbitrary timestamp by walking keyframes forward, exposing a seekable ReplayCursor.

Protocol server: exposes query/replay/subscribe RPCs over the local socket so non-Chronicle tools can consume a session without linking cfs-core.

Export/share: packages a session (optionally a redacted, time-bounded slice) into a portable, optionally encrypted archive for cross-machine transfer.

Telemetry: local-only counters and structured logs (capture latency, queue depth, dedupe ratio) consumed by Chronicle's own operators, never transmitted by default.

6. Design Principles

P1 — Capture must never be on the editor's critical path. Rule: every capture-side operation that could block is queued, never awaited, from the point an editor event fires. Tradeoff: bounded queues can drop or coalesce under sustained overload instead of guaranteeing zero record loss. Operational implication: queue-depth telemetry is a first-class signal, not an afterthought. Violating it breaks the system by making Chronicle a source of the exact editor lag it was built to help diagnose.

P2 — The session file is append-only and self-describing. Rule: no byte, once sealed, is ever rewritten; every frame carries enough metadata to be parsed without the rest of the file. Tradeoff: correcting a bad record means writing a new "tombstone" record, never editing history. Violating it breaks crash-safety (I1) and long-term readability guarantees.

P3 — Backpressure coalesces, it does not block. Rule: when the capture queue nears capacity, adjacent same-kind events (e.g., rapid cursor moves) merge into one record instead of stalling upstream. Tradeoff: intermediate cursor positions during a fast scroll are lost. Violating it turns a burst of terminal output into an editor freeze.

P4 — Every format decision ships with a conformance fixture the same day. Rule: no CFS record kind or layout change lands without an accompanying fixture file exercising it. Tradeoff: slower to add a "quick" field to a record. Violating it means Phase 11's fuzz target has no ground truth to regress against, and format drift goes undetected for months.

P5 — Redaction happens before persistence, never after. Rule: the scrubber sits upstream of the chunker; nothing reaches disk unscanned. Tradeoff: adds fixed latency to every record even when no secret is present. Violating it means a single accidental commit-and-share can leak a credential that already exists, permanently, in a sealed file (I3).

P6 — Content addressing is the only identity a blob has. Rule: a chunk's digest is computed from its bytes and nothing else; two identical byte sequences from unrelated sessions produce the same digest. Tradeoff: digest collision handling must be explicit (collision is treated as corruption, not silently accepted). Violating it breaks dedupe correctness and makes cross-session blob sharing (Phase 10) unsound.

P7 — A session is useful before it is complete. Rule: every reader (index, replay, protocol server) must be able to operate on a session that is still being written to. Tradeoff: readers must tolerate "last frame may be incomplete" as a steady-state condition, not just a crash condition. Violating it means "live tail" queries (Phase 9) are impossible.

P8 — Keyframes bound replay cost, not correctness. Rule: a keyframe is an optimization — replay from the start of the file must always produce the same state as replay from the nearest keyframe. Tradeoff: keyframe cadence is a pure performance dial (§4), never a correctness dial. Violating it means two readers can disagree about reconstructed state depending on which keyframe they picked (I4).

P9 — The scrubber's false-negative rate is a release-blocking metric, not a best-effort target. Rule: every redaction rule-set change is validated against a corpus of known secret shapes (including encoded forms) before release. Tradeoff: rule-set updates are slower than a simple regex add. Violating it means Chronicle silently regresses from "safe to share" to "leaks credentials" with no signal to operators.

P10 — Adapters are capability-negotiated, never version-sniffed. Rule: an IDE or DAP adapter declares an AdapterCapabilities record on attach; Chronicle never infers behavior from a host's version string. Tradeoff: more upfront protocol surface for a simple adapter to implement. Violating it means every new host IDE requires a Chronicle core code change instead of an adapter-side capability flag.

P11 — Diff is symmetric and total. Rule: diff(A, B) and a reverse-applied diff(B, A) must round-trip to the original snapshot bytes for any two valid snapshots, including across schema-compatible format versions. Tradeoff: diff computation cost rises with the generality of the guarantee. Violating it silently corrupts replay-by-diff-chain (Phase 7, Phase 8).

P12 — Telemetry never leaves the machine by default. Rule: local counters and logs are opt-in to export, and export is itself a redaction-scanned artifact like any other export. Tradeoff: aggregate cross-user performance data is not automatically available to Chronicle maintainers. Violating it turns a debugging tool into a covert telemetry collector, which is disqualifying for a tool whose entire premise is developer trust.

P13 — A malformed file must fail loud, locally, and specifically. Rule: any parser error names the byte offset and the expectation that was violated; it never silently truncates or "does its best". Tradeoff: stricter parsing rejects some recoverable-looking files that a lenient parser would salvage. Violating it turns data loss into a mystery instead of a diagnosable, fixable event.

Debugging methodology: every invariant violation must be reproducible from a captured session plus a fixture file (P4) — "it happened once in production and I can't reproduce it" is treated as an unfinished investigation, not a closed one (Agans' "Quantify" rule, applied here as: instrument first, hypothesize second). When an invariant fails, the first question is always "what state did the writer or reader believe it was in" (Ko & Myers' why/why-not framing) — answered by replaying the session itself up to the failure point, because Chronicle's own format is expressive enough to debug Chronicle.

Content-Defined Chunking + Dedupe Model

Chunk boundaries are determined by a FastCDC-style gear hash (Xia et al. 2016) over blob payload bytes, target average chunk size 8 KiB, minimum 2 KiB, maximum 64 KiB. Each chunk is digested (content address, P6); the store holds one copy per unique digest per session, with an optional cross-session shared pool gated by Threat Model row T2. Dedupe ratio (§4) is measured as raw-bytes-referenced ÷ unique-bytes-stored.

Snapshot Model

A Snapshot is either Full (every tracked buffer, debugger frame, and terminal cursor state, self-contained) or Delta (references a prior snapshot digest plus a set of EditDelta/state-change records). Keyframe cadence: one Full snapshot per 2 minutes of active session time, or every 200 accumulated delta records, whichever first — this bounds replay-seek cost (§4) independent of session length (P8).

Timeline / Index Model

The index footer maps: (a) sequence number → byte offset, (b) timestamp range → nearest keyframe sequence number, (c) content digest → blob byte offset, (d) record kind → sequence number list (for filtered queries, e.g. "all TestResult records"). The index is a derived, rebuildable projection (I6) stored as an embedded SQLite page image (ADR-11, Hipp 2017) for query convenience, never as the sole record of truth.

Diff Semantics

diff(SnapshotA, SnapshotB) produces a DiffResult: a per-buffer text diff (Myers 1986, O(ND) core) plus structural diffs for non-text state (debugger scope tree, terminal cursor, VCS position) expressed as add/remove/modify triples keyed by stable field identifiers. Diff is symmetric per P11: applying the inverse diff to B reproduces A's digest exactly.

Worked Example

A developer opens main.rs, types for 40 seconds, hits a breakpoint, inspects a variable, and saves. Records emitted, in sequence: BufferOpen(main.rs) → several coalesced BufferEdit (P3) → DebuggerAttach → DebuggerStop (breakpoint) → DebuggerVariable (inspected var) → BufferEdit (save-triggered formatting) → periodic Keyframe (2-minute cadence) → eventually SessionEnd/Seal on workspace close.

Malformed-File Examples

  • Truncated header length field (declares 4096 bytes, file ends at byte 1200): reader rejects the file at open with a byte-offset error (P13), refuses to guess a shorter header.
  • Frame with payload length exceeding remaining file size: reader treats this frame as the crash boundary (I1) if it is the last frame; treats it as corruption if frames follow it (P13, contradicts I1's crash-tolerance so it is a hard reject with byte offset named).
  • Digest mismatch on a referenced blob: reader marks the specific blob corrupt (I2), continues serving other blobs, flags the session as partially untrustworthy rather than refusing the whole file.

Torn-Write / Crash-Mid-Frame Failure Path

Writer crashes after writing frame magic, sequence number, and record kind, but before the payload and checksum are flushed. On next open, the reader walks the frame stream forward; the last frame's checksum fails to validate against its (incomplete) bytes; per I1, the reader truncates its read cursor to the end of the last fully checksummed frame and reports the session as readable up to that point. The writer, on restart, does not attempt to complete the torn frame — it begins a new frame at the next sequence number, per P2's append-only rule.

12. Phase 0 — Skeleton, CFS v0 Writer/Reader, CI

12.1 Objectives

Establish the workspace skeleton, freeze CFS v0's magic/header/frame layout (§8), ship a minimal writer and reader that round-trip a session with no adapters attached, and stand up CI so every subsequent phase inherits a working build/test/fixture gate (P4).

12.2 Detailed Implementation Steps

Scaffold the Cargo workspace per §10's crates/ layout. Implement SessionHeader and FrameHeader (§11) with CBOR encode/decode (ADR-03). Implement the CFS writer's seal-then-advance append protocol (P2, I1): write frame bytes, compute CRC32C (ADR-19), write checksum, only then advance the write cursor. Implement the reader's forward frame walk with checksum validation on the trailing frame (I1). Implement Seal record writing and whole-file digest computation (I8, ADR-04). Wire CI to run cargo test, a minimal round-trip fixture, and cargo clippy on every PR (P4's "no format change without a fixture" rule starts here).

12.3 Deliverable

cfs-core crate: header/frame/record/seal modules; a chronicle record --noop CLI command that opens, writes three synthetic frames, and seals a session; a chronicle inspect command that dumps frame headers; a green CI pipeline.

12.4 Acceptance Criteria

A round-tripped session of 3 synthetic frames re-reads byte-identical; write-to-seal latency p95 ≤ 12 ms per §4; cargo clippy zero warnings; CI fails the build if a RecordKind variant is added without a corresponding conformance/fixtures/ entry (P4 enforcement begins here, not later).

fixtures/p0_minimal_session.cfs — 3 frames, SessionStart→2 synthetic records→Seal, expected: byte-identical round trip. fixtures/p0_truncated_header.cfs — header length field overstated, expected: reject at open with byte-offset error (P13). fixtures/p0_unsealed.cfs — no Seal record, expected: reader reports session as Flushing-recoverable, not corrupt.

12.6 Pitfalls

Forgetting to reserve tag-range headroom in RecordKind before freezing v0 — breaks additive compatibility (P2) the moment Phase 1 needs a new kind. Writing the checksum before the payload is fully flushed to the OS (defeats I1's crash guarantee — must be flush-then- checksum-then-advance, verified under fault injection, not just unit-tested happy path). Treating CI green as format-frozen without an explicit version tag — CFS v0 must be tagged, not inferred from "whatever main branch currently does".

12.7 Performance Concerns

Frame write path must hit the p50/p95/p99 targets in §4 with zero adapters attached — this phase's numbers are the noise floor every later phase's overhead budget is measured against. CRC32C computation must not dominate frame-write time at the modest frame sizes here; benchmark now so Phase 2's larger chunked payloads have a baseline.

12.8 Edge Cases

Empty session (header + Seal only, no records). Header claiming a CFS version this reader build does not recognize (must reject cleanly per Compatibility & Versioning, §27). A frame with payload_len of zero for a record kind that structurally requires a non-empty payload.

12.9 Failure Analysis

Symptom: reader reports "corrupt" on a file that is merely mid-write (still Recording). Root cause: reader conflated "last frame checksum invalid" with "file corrupt" instead of "file has an in-progress writer" (I1's distinction). Detection: fixture p0_unsealed.cfs exists specifically to catch this regression. Recovery: reader must check for an active writer lock file before declaring corruption, not just checksum state.

12.10 Operational Notes

CI badge and CFS version number both surface in README.md. Any CFS v0 layout change after this phase's tag requires a version bump (ADR-02) and a new fixture, per the Compatibility & Versioning policy (§27) — there is no "quick fix" path that skips this.

13. Phase 1 — IDE Adapter, Buffer/Edit Capture

13.1 Objectives

Ship the first real capture source: a VS Code extension (ADR-20) emitting BufferOpen, BufferEdit, BufferClose, CursorMove, and SelectionChange records through the capture scheduler (P1, P3) into the CFS writer built in Phase 0.

13.2 Detailed Implementation Steps

Implement the capture-sched bounded queue and batcher (P1, P3), enforcing the 250 ms/512- event cadence from §4. Implement the negotiate/emit adapter contract (§8's Adapter Contract table, P10) with AdapterCapabilities exchanged on extension activation. Hook VS Code's onDidChangeTextDocument, onDidChangeTextEditorSelection, and open/close document events; translate to EditDelta/CursorPos per §11's schemas, computing base_digest/ result_digest pairs (I9). Coalesce rapid cursor/selection events per P3 before they reach the IPC boundary (ADR-08/ADR-09).

13.3 Deliverable

adapters/ide-vscode extension; capture-sched crate with queue/batcher; end-to-end demo: typing in VS Code produces a growing, valid CFS session file inspectable via chronicle inspect.

13.4 Acceptance Criteria

Added editor-event latency ≤ 1 ms p95 per §4, measured via benchmarks/capture_overhead; queue never blocks the extension host thread (verified via a synthetic 10,000-event/sec burst test); every EditDelta's base_digest matches its predecessor's result_digest (I9) across a 30-minute synthetic typing fixture.

13.5 Conformance Fixtures

fixtures/p1_edit_chain.cfs — 200 sequential edits to one buffer, expected: base_digest chain validates end-to-end. fixtures/p1_coalesced_cursor_burst.cfs — 5,000 synthetic cursor events in 1 second, expected: coalesced to under 50 CursorMove records. fixtures/ p1_capability_mismatch.cfs — adapter declares no BufferEdit support, expected: core drops edit events at negotiation, not per-call (I10).

13.6 Pitfalls

Computing base_digest/result_digest synchronously on the extension host thread — violates P1 by putting hashing on the critical path; must be pushed to the scheduler's worker context. Assuming VS Code's document-change events arrive in document order under IME/composition input — they do not always, and naive sequencing corrupts the edit chain (I9 violation). Treating a rename (buffer path change with same content) as a fresh BufferOpen — loses the edit-history linkage a developer would expect.

13.7 Performance Concerns

Queue depth telemetry (P1) must be visible in the same benchmark run that measures latency, not a separate manual step — regressions must be caught by benchmarks/capture_overhead automatically. Large paste operations (multi-KB single edits) must not spike p99 write latency past the 40 ms budget (§4) — verify with a fixture pasting a 500 KB file.

13.8 Edge Cases

A buffer open in an unsaved/untitled state (no path). A buffer whose content is replaced entirely by an external tool (formatter) between two capture ticks — must appear as one large EditDelta, not a BufferClose/BufferOpen pair. Multiple cursors/selections in a single editor (multi-cursor editing) — one CursorMove/SelectionChange record must carry all active cursor positions, not one record per cursor.

13.9 Failure Analysis

Symptom: base_digest chain breaks intermittently under fast typing. Root cause: two BufferEdit events computed their digests concurrently on different scheduler worker threads, racing on which becomes the "current" base for the next edit. Detection: fixture p1_edit_chain.cfs run under a thread-interleaving stress harness. Recovery: per-buffer serialization in the scheduler (ordering guarantee tightened to per-buffer_id, not just per-session sequence number).

13.10 Operational Notes

The VS Code extension's marketplace listing must state plainly, per P12, that no data leaves the machine by default — this is a trust-critical first impression, not marketing copy, and is reviewed alongside Threat Model row T1 before any public release.

14. Phase 2 — Chunking, Dedupe, Compression

14.1 Objectives

Implement the FastCDC chunker (ADR-06) and content-addressed blob store, and layer zstd compression (ADR-05) over stored chunks, to bring session growth from the pre-dedupe to the post-dedupe/compress target in §4.

14.2 Detailed Implementation Steps

Implement gear-hash rolling boundary detection per Xia et al. 2016, target/min/max chunk sizes from §8's Chunking model (8 KiB/2 KiB/64 KiB). Compute BlobDigest (SHA-256, ADR-04) per chunk; store chunk once per unique digest (P6, I2). Wire the store behind BlobRef first-reference emission (§8's record catalogue) so repeat digests emit a reference, not a copy. Apply zstd compression per stored chunk, with a trained dictionary (facebook/zstd lib/dictBuilder/) seeded from the Phase 0/1 fixture corpus. Verify digest correctness by recomputing on read (I2's enforcement point).

14.3 Deliverable

chunker crate (cdc.rs, store.rs); dedupe/compression wired into the CFS writer's blob region; benchmarks/dedupe_ratio harness measuring both ratios against §4's targets.

14.4 Acceptance Criteria

Dedupe ratio ≥ 4:1 on a fixture of 50 repeated buffer saves with 90% unchanged content; residual-chunk zstd ratio ≥ 3:1; combined session growth ≤ 4 MB/hour on the Phase 1 30-minute typing fixture rerun through this phase's pipeline; digest recomputation on read adds ≤ 10% to reader latency.

14.5 Conformance Fixtures

fixtures/p2_repeated_save.cfs — same 2 MB file saved 50 times with small edits, expected: dedupe ratio ≥ 4:1. fixtures/p2_large_binary.cfs — a 10 MB near-random binary buffer, expected: dedupe ratio ~1:1 (documents the defeat case, doesn't regress it as a bug). fixtures/p2_digest_collision_injected.cfs — a deliberately corrupted digest-to-chunk mapping, expected: reader flags the specific blob (I2), not the whole session.

14.6 Pitfalls

Choosing a chunk size too small — dedupe improves marginally but per-chunk overhead (digest + index entry) dominates and net storage grows, not shrinks. Training the zstd dictionary once and never refreshing it — a dictionary trained on Phase 0/1 fixtures degrades as real-world code shapes diverge from synthetic ones. Assuming chunk boundaries are stable across a file rewrite that shifts all bytes by one (e.g., inserting a single character at the top of a file) — FastCDC's whole point is that they mostly are, but a naive fixed-size chunker would defeat dedupe here, and this must be regression-tested, not assumed.

14.7 Performance Concerns

Chunking + hashing must stay off the P1 critical path — pushed entirely into scheduler worker threads, same rule as Phase 1's digest computation. Redaction scan throughput (§4, 40 MB/s) must be measured before chunking, per P5's ordering rule — chunking a payload the scrubber hasn't cleared yet is a design error, not a performance one, and Phase 2's benchmark harness must assert ordering, not just measure speed.

14.8 Edge Cases

A chunk exactly at the maximum size boundary (64 KiB) with no natural CDC breakpoint found — must force a boundary rather than grow unbounded. A session with a single enormous buffer (generated lockfile, 50 MB) opened once and never edited — dedupe ratio here is irrelevant (no repetition to exploit) but compression ratio must still hit target on the residual chunks.

14.9 Failure Analysis

Symptom: dedupe ratio silently drops from 4:1 to 1.2:1 after an unrelated refactor. Root cause: the gear-hash normalization constant was accidentally changed alongside an unrelated chunker cleanup, shifting boundary statistics. Detection: benchmarks/dedupe_ratio run in CI against fixtures/p2_repeated_save.cfs as a regression gate, not just a manual benchmark. Recovery: pin the gear-hash table and normalization level as a reviewed constant with a comment linking Xia et al. 2016's recommended parameters.

14.10 Operational Notes

Dictionary retraining is a scheduled maintenance task (documented in docs/runbooks/), run against an updated fixture corpus whenever the conformance suite's fixture set changes materially — never run silently in production against live user sessions (P12-adjacent: no user data leaves the machine to train a shared dictionary).

15. Phase 3 — Crash-Safe Append, Index Footer

15.1 Objectives

Harden the writer against process crashes and disk-full conditions, and implement the index footer (§8's Timeline/Index Model) as a rebuildable SQLite-backed side table (ADR-07, Hipp 2017), closing out I1 and I6 with real fault-injection evidence, not just design intent.

15.2 Detailed Implementation Steps

Implement the writer's fsync-boundary policy: group-commit frames within the snapshot cadence window (§4) but fsync before acknowledging a Keyframe or Seal record specifically (Petrov's WAL group-commit pattern). Implement IndexEntry construction incrementally as frames are written, and a full-rebuild path that reconstructs the index purely from the frame stream (I6). Implement daemon-restart recovery: detect an unsealed session on chroniclesd startup, transition it to Flushing, attempt to complete the seal, and open a new session for continued capture (§8's capture state machine). Add disk-full handling: writer must detect ENOSPC-class errors and transition to Suspended rather than corrupt a partial frame.

15.3 Deliverable

cfs-index crate (builder.rs, query.rs); daemon startup recovery logic in crates/daemon; a fault-injection test harness wrapping the filesystem layer to simulate torn writes and disk-full mid-append.

15.4 Acceptance Criteria

RTO ≤ 2 s from simulated daemon crash to a new Recording session (§4); at most one sealed frame's worth of data at risk per crash, verified across 500 randomized crash-injection runs; index rebuild from a 1 GB fixture completes and matches the incrementally built index byte-for-byte in its digest-to-offset mapping.

15.5 Conformance Fixtures

fixtures/p3_torn_write_mid_payload.cfs — crash injected mid-BufferEdit payload write, expected: reader recovers to the last complete frame per §8's torn-write failure path. fixtures/p3_disk_full_during_flush.cfs — simulated ENOSPC during Flushing, expected: writer transitions to Suspended, no partial Seal written. fixtures/ p3_index_rebuild_1gb.cfs — large session, expected: rebuilt index matches incremental index.

15.6 Pitfalls

Fsyncing on every single frame — meets crash-safety trivially but blows the p50 write-latency budget (§4); group-commit is required, not optional. Treating "index missing" and "index stale" as the same recovery path — a missing index triggers a full rebuild (I6), a stale index (e.g., session grew since last rebuild) should ideally only need an incremental catch- up, and conflating them wastes rebuild time on large sessions. Assuming ENOSPC is the only disk-full signal — some filesystems report quota errors differently, and the writer's error handling must not special-case one error code only.

15.7 Performance Concerns

Index rebuild time must scale sub-linearly enough that the 1 GB fixture (15.5) completes within an operationally reasonable bound — tracked explicitly in Performance Engineering (§30) as metric M-class, not left as "however long it takes". Group-commit windowing interacts with the snapshot cadence (§4) — must not introduce a secondary, uncoordinated batching layer that fights the capture scheduler's own batching (P1, P3).

15.8 Edge Cases

A crash during index rebuild itself — must be safely restartable (rebuild is idempotent by construction since it only reads the frame stream, per I6). A session that crashes repeatedly on every restart attempt (poison session) — daemon must cap retry attempts and surface a diagnosable error rather than looping silently.

15.9 Failure Analysis

Symptom: after a crash, the daemon takes 40 seconds to resume capture, blowing the 2 s RTO target. Root cause: the recovery path was attempting a full index rebuild before allowing new capture to start, instead of resuming capture immediately and rebuilding the index in the background. Detection: benchmarks timing harness on the crash-injection suite. Recovery: decouple "resume recording" from "index is fully caught up" — the former is the RTO-gated path, the latter can lag briefly per I6's rebuildability guarantee.

15.10 Operational Notes

Crash-injection fixtures run nightly in CI, not just at Phase 3's initial implementation — this is the primary regression gate for I1 and stays in the permanent CI matrix through Phase 11 and beyond (Testing & Verification Strategy, §28).

16. Phase 4 — Redaction / Scrubber

16.1 Objectives

Implement the redaction/scrubber engine (ADR-13) upstream of the chunker (P5), enforcing I3 and I5, and validate it against a corpus of known secret shapes including encoded forms before any capture is allowed to leave the local machine.

16.2 Detailed Implementation Steps

Implement RedactionRule loading (regex patterns + Shannon-entropy heuristic scan, ADR-13) from a versioned rule-set config (TOML, per §11's annotation). Wire the scrubber as the mandatory upstream stage of the chunker pipeline built in Phase 2 (P5) — no code path may reach chunker::store without passing through scrubber::scan first. Implement the quarantine queue for records that fail to scan within budget (I5): quarantined records are held, re-scanned with relaxed batching, never dropped. Implement RedactionAudit record emission (§8's record catalogue) so every scrub action is itself part of the session's audit trail. Add entropy-based detection for base64/hex-encoded secrets, per P9's "encoded forms" requirement — plain regex alone misses these systematically.

16.3 Deliverable

scrubber crate (rules.rs, entropy.rs); a default rule-set config shipped with Chronicle covering common credential shapes (API key prefixes, private key PEM headers, JWT structure, connection-string patterns); a redaction conformance corpus in conformance/fixtures/redaction/.

16.4 Acceptance Criteria

Redaction scan throughput ≥ 40 MB/s per core (§4); zero false negatives on the release- blocking corpus (P9) across ≥ 200 labeled secret-shape samples including base64/hex-encoded variants; quarantine queue drains within 5 s under normal load, never silently discards a record (I5).

16.5 Conformance Fixtures

fixtures/p4_plain_api_key.cfs — a buffer containing an unencoded API-key-shaped string, expected: redacted before persistence. fixtures/p4_base64_encoded_secret.cfs — the same secret base64-encoded inline, expected: caught by the entropy heuristic, not just regex. fixtures/p4_scrub_timeout_injected.cfs — a payload engineered to exceed the scan time budget, expected: record quarantined (I5), never written raw and never dropped.

16.6 Pitfalls

Relying on regex alone and treating entropy scanning as optional — misses exactly the encoded-secret case P9 exists to catch; both must run on every record, not just the "cheap" regex pass. Scanning after chunking instead of before — violates P5 outright and is a design regression, not a tuning issue, if it ever happens. Setting the entropy threshold too aggressively — flags ordinary compiled binary content or minified JS as high-entropy "secrets", producing redaction noise that erodes trust in the tool. Treating the quarantine queue as a dead-letter queue that operators must manually clear — it must self-drain via background re-scan (I5), with manual clearing only as a last resort.

16.7 Performance Concerns

The 40 MB/s throughput target (§4) must hold even with both regex and entropy passes running — benchmark the combined pipeline, not each pass independently, since real-world payloads run both. Quarantine re-scan with relaxed batching must not starve normal-priority scrubbing of CPU time under sustained load (a terminal-output flood plus a quarantine backlog simultaneously is the adversarial case to benchmark).

16.8 Edge Cases

A secret split across two adjacent EditDelta records by an unlucky edit boundary — must still be caught because the scrubber scans the reconstructed buffer state, not just the raw delta bytes in isolation. A false positive on a UUID or content hash that merely looks high-entropy — the rule-set's severity tiers (§11) allow "flag but don't block" for lower-confidence matches, reviewed against the acceptance corpus. A rule-set version mismatch between the daemon and a shared/exported session's redaction audit trail.

16.9 Failure Analysis

Symptom: a private key committed to a scratch file appears unredacted in an exported session. Root cause: the rule-set's PEM-header pattern required the header on its own line, but the scratch file had it indented inside a YAML block scalar. Detection: the release-blocking corpus (16.4) is updated with this exact shape as a permanent regression fixture the moment it's found — per P4, the fix and the fixture land in the same change. Recovery: rule-set patched, existing already-persisted sessions flagged for re-scan via a follow-up scrubber pass (documented as a docs/runbooks/ procedure, since I3 cannot retroactively un-persist bytes already sealed — only flag and warn, per P2's append-only rule).

16.10 Operational Notes

Every rule-set change ships with an updated conformance-corpus run in CI (P9) before release; rule-set version is stamped into RedactionAudit records so a session's redaction provenance is always inspectable after the fact.

17. Phase 5 — Terminal + Test-Result Capture

17.1 Objectives

Add the PTY tap and test-runner integration, emitting TerminalOutput/TerminalInput and TestResult records (§8's catalogue), while defending against the two failure modes unique to this source: unbounded growth from a hot terminal loop, and clock-driven ordering bugs.

17.2 Detailed Implementation Steps

Wrap the integrated terminal's PTY (ADR-15, asciinema cast-v2-inspired framing) capturing stream-tagged, timestamped byte chunks. Route large terminal payloads through the same chunker/scrubber pipeline as buffer content (Phase 2/Phase 4 reuse, not a parallel path). Implement a hot-loop backpressure rule specific to terminal output: sustained output above a configured bytes/sec threshold triggers aggressive TerminalChunk coalescing (extends P3 to this source). Parse test-runner output (initially a small set of common formats) into structured TestResult records, cross-referencing output_ref back to the terminal chunk digest that produced it. Use the frame sequence number (I7), never wall-clock time alone, as the authoritative ordering key for terminal chunks — defends against clock jumps.

17.3 Deliverable

PTY tap wired into daemon; TestResult parsers for at least one test framework per supported language ecosystem in Phase 0-1's target IDE; benchmarks extended to include a sustained-terminal-output stress case.

17.4 Acceptance Criteria

A sustained 10 MB/s synthetic terminal-output fixture produces session growth within the §4 post-dedupe budget, not unbounded growth; frame ordering remains correct (I7) even when the system clock is stepped backward mid-capture (simulated NTP correction); TestResult parsing correctly attributes pass/fail/duration for ≥ 95% of a labeled fixture corpus of real test- runner output.

17.5 Conformance Fixtures

fixtures/p5_hot_terminal_loop.cfs — a synthetic yes-style infinite-output loop capped at a fixed duration, expected: coalesced growth within budget, not runaway session size. fixtures/p5_clock_jump_mid_session.cfs — simulated backward clock step during capture, expected: sequence-number ordering (I7) unaffected. fixtures/p5_test_run_mixed_results.cfs — a test run with passes, failures, and skips, expected: TestResult records match the labeled expected output exactly.

17.6 Pitfalls

Using wall-clock timestamps as the sort key for terminal chunks instead of sequence number — directly violates I7 and produces reordered replay under any clock adjustment. Failing to cap unbounded terminal growth before it reaches the chunker — a hot loop can produce output faster than the scrubber's throughput budget (§4), and without a coalescing circuit-breaker specific to this source, the whole pipeline backs up (violates P1 transitively). Assuming test-runner output format is stable across framework versions — brittle parsers silently misattribute results; must degrade to "unstructured terminal output only" rather than emit wrong TestResult data.

17.7 Performance Concerns

The hot-loop coalescing threshold must be tuned so normal verbose build output (e.g., a noisy compiler) is not aggressively truncated while a genuine runaway loop is contained — this is a tunable, benchmarked parameter, not a hardcoded guess. Test-result parsing must not block the terminal capture path itself (P1) — parsing happens off the hot path, consuming already-captured TerminalChunk data asynchronously.

17.8 Edge Cases

A terminal resize mid-session (must not corrupt chunk framing). Binary output written to the terminal (e.g., a progress bar using carriage-return tricks, or accidental binary cat) — must not defeat the scrubber's text-pattern assumptions; falls back to entropy-only scanning for non-UTF8 chunks. A test run that hangs indefinitely — TestResult capture must have a bounded wait, emitting a "timeout" outcome rather than blocking session capture indefinitely.

17.9 Failure Analysis

Symptom: a CI-triggered capture session grows to gigabytes within minutes. Root cause: a build tool's verbose flag was accidentally enabled, producing output faster than the coalescing threshold anticipated, and the circuit-breaker's threshold had been tuned only against interactive-developer-scale output, not CI-scale. Detection: session-growth alerting in telemetry (P12-compliant, local-only) flags the anomaly by comparing against the §4 growth budget in real time. Recovery: dynamic threshold escalation — if growth rate exceeds budget for N consecutive cadence windows, coalescing becomes more aggressive automatically, with the change itself logged as a TerminalOutput metadata marker so replay shows where fidelity was reduced.

17.10 Operational Notes

Terminal capture is the most likely source of accidental secret leakage (a printed environment variable, a pasted curl command with an API key) — Phase 4's scrubber coverage for this source is re-validated specifically, not assumed to generalize automatically from buffer-content coverage.

18. Phase 6 — DAP Debugger-State Capture

18.1 Objectives

Implement the passive DAP proxy adapter (ADR-10) capturing DebuggerAttach, DebuggerStop, and DebuggerVariable records without ever altering debugger behavior or issuing side-effecting requests (I10).

18.2 Detailed Implementation Steps

Implement the DAP proxy as a transparent pass-through between the IDE's existing DAP client and the debug adapter process, observing traffic rather than replacing either side (ADR-10). On each stopped event, capture the stack trace, scopes, and any already-open watch expressions into a DebuggerFrame (§11) — never issue a new evaluate request on Chronicle's own initiative, since evaluate can have side effects in some languages (e.g. computed properties, lazy evaluation with observable effects). Mirror AdapterCapabilities negotiation against the DAP session's own capabilities response (P10, I10) so Chronicle never assumes a capability the underlying debugger doesn't have (e.g., variable paging). Reference large variable trees by chunked digest (Phase 2 reuse) rather than inlining unbounded object graphs.

18.3 Deliverable

adapters/dap-shim crate; passive-proxy wiring validated against at least one real DAP debug adapter (e.g., a common language's official debug adapter) in an integration test.

18.4 Acceptance Criteria

Zero observed behavioral difference in debuggee execution with the proxy attached versus detached, verified via a differential test running the same debug session both ways; DebuggerFrame capture adds ≤ 5 ms to the stop-event handling path; capability violations (I10) are rejected at the negotiation boundary in 100% of a fixture set exercising unsupported-operation attempts.

18.5 Conformance Fixtures

fixtures/p6_passive_proxy_parity.cfs — same debug session captured with and without the proxy, expected: identical debuggee-observable behavior. fixtures/ p6_capability_violation_attempt.cfs — a scenario where Chronicle's own code is made to attempt an unsupported operation, expected: rejected pre-dispatch (I10). fixtures/ p6_large_variable_tree.cfs — a debug session with a deeply nested object graph, expected: digest-referenced, not inlined, staying within the memory ceiling (§4).

18.6 Pitfalls

Issuing an evaluate request to "helpfully" pre-fetch a watch expression's current value — directly violates the passive-observer contract (ADR-10, I10) and can alter program state in languages with computed/lazy properties. Assuming all DAP adapters support the same paging model for large variable collections — must check AdapterCapabilities per session, not hardcode against one debugger's behavior observed during development. Buffering an unbounded number of stack frames for deep recursion — must cap capture depth with a documented, configurable limit rather than risk the memory ceiling (§4).

18.7 Performance Concerns

The passive proxy sits directly in the path between IDE and debug adapter — any added latency here is directly felt by the developer as debugger sluggishness, making the 5 ms budget (18.4) a hard constraint, not a nice-to-have. Large variable-tree digesting must reuse Phase 2's chunker rather than re-implementing a parallel hashing path.

18.8 Edge Cases

A debug session that attaches to an already-running process (no launch, only attach) — capability negotiation must handle this DAP flow correctly. Multiple simultaneous debug threads stopped at different breakpoints. A debug adapter that crashes mid-session — the proxy must not itself crash or wedge the IDE's own DAP client connection.

18.9 Failure Analysis

Symptom: a developer reports the debugger "feels laggy" after enabling Chronicle. Root cause: the passive proxy was performing synchronous digest computation on the large- variable-tree path before forwarding the DAP response onward to the IDE, adding latency directly in the developer-visible path. Detection: differential latency benchmark (18.4) comparing proxy-attached vs. detached round-trip time per DAP message type. Recovery: forward the DAP response to the IDE immediately, capture and digest asynchronously off the critical path (P1 applied to the DAP source, mirroring Phase 1's lesson for buffer edits).

18.10 Operational Notes

Any new DAP adapter integration (a new language's debugger) is validated against the parity fixture (18.5) before being marked supported — parity is the acceptance bar, not "seems to work in manual testing".

19. Phase 7 — Snapshot Diffing

19.1 Objectives

Implement the snapshot differ (§8's diff semantics) generalizing Myers' O(ND) algorithm (Myers 1986, ADR-16) from line-text diffs to structural diffs across buffers, debugger state, terminal cursor, and VCS position, satisfying P11's symmetry guarantee.

19.2 Detailed Implementation Steps

Implement per-buffer text diffing using the O(ND) core (Myers 1986) over BufferState content, keyed by content_digest (ADR-04). Implement structural diffing for non-text state — debugger scope trees, terminal cursor position, VCS position — as add/remove/modify triples keyed by stable field identifiers (§8), reusing no text-diff machinery for these. Implement the round-trip symmetry check (P11): given DiffResult for (A, B), applying its inverse to B must reproduce A's digest exactly; wire this as an automatic assertion in the differ's test path, not a manual review step. Expose diff(SnapshotA, SnapshotB) -> DiffResult as the sole public entry point, used by both the replay engine (Phase 8) and any future UI.

19.3 Deliverable

differ crate (diff.rs); a chronicle diff <seq_a> <seq_b> CLI command producing a human-readable structural diff; the P11 symmetry assertion wired into conformance/harness.

19.4 Acceptance Criteria

Diff computation for a 10,000-line buffer completes in ≤ 200 ms; P11 symmetry holds across 100% of the conformance fixture corpus (zero exceptions permitted — this is a correctness invariant, not a performance target); structural diffs correctly identify debugger scope additions/removals across a fixture with nested variable scopes 5 levels deep.

19.5 Conformance Fixtures

fixtures/p7_text_diff_roundtrip.cfs — two buffer snapshots with a 200-line interior edit, expected: diff + inverse-apply reproduces original digest exactly. fixtures/ p7_structural_debugger_diff.cfs — two debugger snapshots with added/removed scope variables, expected: correct add/remove/modify triples. fixtures/p7_cross_version_diff.cfs — two snapshots from schema-compatible but different minor CFS versions, expected: diff succeeds per P11's "including across schema-compatible format versions" clause.

19.6 Pitfalls

Applying the text-diff algorithm naively to non-text structural state (e.g., treating a debugger scope tree as a flat text blob) — produces technically-valid but semantically useless diffs; structural state needs its own comparison keyed by stable identifiers, not byte position. Skipping the round-trip symmetry assertion because "the algorithm is proven correct" (Myers 1986 proves the text case; the structural generalization is Chronicle's own code and needs its own proof-by-test). Assuming diff is cheap enough to compute on every frame eagerly — it is a demand-computed capability (§3), not part of the write path, per P1's critical-path rule extended to reads that could stall a UI.

19.7 Performance Concerns

The 200 ms target for a 10,000-line buffer (19.4) must hold even for adversarial inputs (e.g., a file that is entirely one repeated character, which can pathologically worsen some diff implementations if not bounded) — benchmark against both realistic and adversarial fixtures. Structural diffing over deeply nested debugger scopes must not be quadratic in nesting depth; bound with an explicit depth-aware traversal strategy.

19.8 Edge Cases

Diffing two snapshots from sessions with different AdapterCapabilities (one has debugger state, one doesn't) — must produce a partial diff noting the capability gap, not error out. Diffing a snapshot against itself (identity diff, must be an empty DiffResult). Diffing across a keyframe boundary where one snapshot is Full and the other is a deep Delta chain — must resolve both to comparable full state before diffing, not diff the deltas directly against each other.

19.9 Failure Analysis

Symptom: the P11 symmetry assertion fails intermittently on large buffers only. Root cause: the structural diff for VCS dirty_paths used a HashSet-derived ordering that was not stable across runs, so the inverse-apply reproduced equivalent-but-differently-ordered state, which digested differently despite being semantically identical. Detection: the symmetry assertion in conformance/harness compares digests, which is exactly strict enough to catch this class of bug. Recovery: sort all structural diff collections by a stable key before digesting, documented as a differ-wide invariant, not a one-off fix to dirty_paths.

19.10 Operational Notes

The differ's public API (diff()) is the one piece of Chronicle's internals every downstream consumer (replay, protocol server, future UI) depends on — any signature change here is treated as a compatibility-review event equivalent to a CFS format change (ADR-02 adjacent), even though DiffResult itself is not persisted to disk.

20. Phase 8 — Replay Engine & Seek

20.1 Objectives

Ship the replay crate's ReplayCursor: reconstruct a Snapshot at an arbitrary sequence number or timestamp by combining the nearest keyframe with a forward delta-chain apply, honoring P8 (keyframes bound cost, never correctness) and I4 (replay determinism across independent readers).

20.2 Detailed Implementation Steps

Implement ReplayCursor::seek over the index footer's timestamp→keyframe map (I6, ADR-07): locate the nearest Keyframe at or before the target, then apply the intervening EditDelta/state-change chain forward, verifying each delta's declared base BufferState digest before applying (I9) and falling back to the nearest prior keyframe on mismatch (I9's recovery path). Implement full-chain replay-from-start as the explicit fallback when I4's cross-reader golden-state check detects divergence, per I4's own recovery clause. Implement live-tail seeking against an actively-Recording session (P7): the cursor only trusts frames past the writer's last-checksummed-and-advanced offset, never the file's raw EOF. Expose chronicle replay --at <seq|ts> as the CLI entry point and a library function reused verbatim by the protocol server (Phase 9) and export's partial-range materialization (Phase 10).

20.3 Deliverable

replay crate (cursor.rs, seek.rs); chronicle replay --at <ts> CLI producing a human-readable reconstructed-state dump; a cross-reader golden-state comparator wired into conformance/harness (I4).

20.4 Acceptance Criteria

Seek latency p95 ≤ 150 ms per §4 measured against examples/multi-hour-session; two independent reader processes replaying the same session to the same sequence number produce byte-identical reconstructed-state digests across 100% of fixtures/p8_* (I4, zero divergence permitted); live-tail seek against a still-Recording session succeeds without the writer observing any added latency (P1 extended to a new read path).

20.5 Conformance Fixtures

fixtures/p8_seek_midkeyframe.cfs — three keyframes, seek target between keyframe 2 and 3, expected: reconstructed state matches a golden digest. fixtures/p8_live_tail.cfs — session left Recording (unsealed), expected: replay succeeds up to the last checksummed frame, no error. fixtures/p8_delta_apply_failure.cfs — an EditDelta with an injected base-digest mismatch, expected: I9 fallback to the nearest keyframe, delta_apply_failures incremented. fixtures/p8_torn_frame_seek.cfs — seek target inside a deliberately torn last frame, expected: resolves to the nearest fully-checksummed frame per I1.

20.6 Pitfalls

Replaying from session start on every seek instead of the nearest keyframe defeats P8 entirely and must be caught by benchmarking that the keyframe path is actually exercised, not assumed from code review alone. Treating an I4 divergence as a new replay-crate bug in isolation is a common misdiagnosis — per 19.9's stable-ordering lesson, divergence is frequently a differ-side non-determinism surfacing downstream, not a replay bug at all. Assuming delta-chain application is idempotent across repeated seeks to the same target is false; the cursor must reset to the keyframe base every seek, never incrementally patch a retained mutable buffer, or repeated seeks silently diverge from a fresh reader's result. Live-tail replay that races the writer's in-flight frame by trusting raw end-of-file instead of the writer's last-advanced offset will read a torn frame as sealed and corrupt the reconstructed state.

20.7 Performance Concerns

Worst-case seek cost is bounded by the keyframe interval (2 min / 200 deltas, §8); benchmark the worst case explicitly — a target immediately before the next keyframe — not only the average case, since §4's p95 budget must hold there too. Index lookup cost (ADR-07's embedded SQLite page image) must be profiled separately from delta-apply cost so a regression in either is attributable, not lumped into one seek-latency number.

20.8 Edge Cases

A seek target before session start clamps to the first keyframe rather than erroring. A seek target after the last sealed frame of a Sealed session clamps to the final known state. A session that closed before its first keyframe threshold elapsed has zero keyframes and must still replay correctly from session start, per ADR-18's dual-threshold cadence.

20.9 Failure Analysis

Symptom: two readers replaying to the same sequence number produced different DebuggerVariable scope contents. Root cause: one reader consulted a stale index snapshot, built before a late-arriving Keyframe record was indexed, and so resolved the wrong nearest-keyframe pointer. Detection: the I4 golden-state fixture comparison caught the mismatch immediately. Recovery: index consumers must check index freshness (I6's rebuild trigger) against the live frame stream before trusting a keyframe pointer, not only at daemon startup.

20.10 Operational Notes

The seek-latency benchmark (benchmarks/replay_seek/) runs on every PR touching the replay or cfs-index crates; a regression past §4's 150 ms p95 budget blocks the merge, not merely a warning annotation.

21. Phase 9 — Cross-Tool Protocol Server

21.1 Objectives

Ship protocol-server, a local RPC surface (ADR-11, ADR-21) letting third-party tools discover, query, and subscribe to live or sealed sessions, honoring P7 (a session is useful before it is complete) and I10 (capability claims are always honored, never sniffed).

21.2 Detailed Implementation Steps

Implement rpc.rs: CBOR-framed request/response (ADR-03, ADR-09) over a Unix domain socket (ADR-08), reusing the negotiate/emit capability pattern (P10) — a connecting client declares a ClientCapabilities record before any other call. Implement subscribe.rs: a live-tail channel pushing newly sealed frames to subscribers, honoring P7's tolerance for an in-progress last frame by only forwarding checksum-validated frames (I1 extended to a new consumer). Implement session discovery against the daemon's session registry, a query surface (replay-at, delegating to Phase 8's ReplayCursor; get-metadata; list-records-by-kind, via the index, I6), and per-connection authorization scoped to the socket's filesystem permissions (ADR-08, rejecting cross-user connections per Threat Model row T8). Implement I10's dispatch-boundary rejection: a call for an operation the client never negotiated is rejected before dispatch, never silently ignored.

21.3 Deliverable

protocol-server crate (rpc.rs, subscribe.rs); a daemon-embedded server; a reference third-party client stub in examples/ demonstrating negotiate → subscribe → replay-at round trip.

21.4 Acceptance Criteria

Metadata-query round-trip latency p95 ≤ 20 ms on loopback socket; a newly sealed frame reaches a subscribed client within 100 ms p95 of its checksum being written; a client calling an operation outside its negotiated ClientCapabilities is rejected with a named capability-violation error against fixtures/p9_capability_violation.cfs, zero silent no-ops permitted (I10).

21.5 Conformance Fixtures

fixtures/p9_negotiate_subscribe_replay.cfs — a scripted negotiate → subscribe → replay-at sequence, expected: correctly ordered responses matching a golden transcript. fixtures/p9_cross_user_socket.cfs — a connection attempt from a different OS user, expected: rejected at the socket-permission layer (T8). fixtures/p9_capability_violation.cfs — a client calls query(sessionState, at:) without negotiating it, expected: rejected, capability_violation_total incremented. fixtures/p9_live_tail_race.cfs — a subscriber connects mid-write, expected: no torn-frame delivery.

21.6 Pitfalls

Exposing the RPC surface over TCP loopback "for convenience" reopens exactly the cross-user/cross-container attack surface ADR-08 chose Unix sockets to avoid. Delivering a live-tail frame before its checksum is verified violates the same seal-then-advance discipline (I1) the writer itself follows — subscribers must see only checksum-validated frames, never a raw tail read. Unbounded list-records-by-kind queries against the index (ADR-07) can starve the writer's own index access if not rate-limited or queued on a separate path, extending P1's critical-path rule to a query surface that didn't exist before this phase. Silently expanding a client's effective capabilities because repeated calls "seem to work" violates P10 outright — every served operation must trace to an explicit negotiated capability, not inferred tolerance.

21.7 Performance Concerns

The loopback latency budget (21.4) must hold under concurrent multi-client load — several IDE windows plus a CLI query at once — not only a single-client benchmark. Live-tail fan-out to N subscribers must be decoupled from the writer's frame-seal path via an async broadcast, never synchronous with it, or subscriber count becomes a hidden tax on §4's core write budget.

21.8 Edge Cases

A subscriber connected across a session rotation (§4's 24h/8GB threshold) must receive an explicit rotation-reason close event and a pointer to the successor session, never silent stream termination. A query against a nonexistent session id returns a named error, never a hang. Two clients negotiating different capability sets against the same session (one wants full DebuggerVariable trees, one wants metadata only) must be served independently with no shared mutable negotiation state between them.

21.9 Failure Analysis

Symptom: a subscriber's live-tail stream silently stopped after a session rotation. Root cause: the subscription was keyed by session id; rotation correctly closed the old subscription but no successor-notification path had been designed, so the client observed only silence. Detection: none — no telemetry existed for a subscription's close reason until a user reported it. Recovery: subscription-close events now carry an explicit reason code (rotated, sealed, error); subscription_closed_total{reason} added as a counter so this class is now detectable automatically.

21.10 Operational Notes

The protocol-server socket path and permission mode are logged at daemon startup; any third-party integration guide in docs/ documents the negotiate handshake explicitly, since P10 forbids a version-sniffing shortcut for new integrators.

22. Phase 10 — Export, Sharing & Encryption at Rest

22.1 Objectives

Ship the export crate: shareable, optionally recipient-encrypted session archives (ADR-14) that pass a mandatory pre-export redaction re-scan (P5, P9) and never co-locate decryption key material with the artifact (I11).

22.2 Detailed Implementation Steps

Implement pack.rs: an archive wrapping a sealed .cfs file or a materialized time-range sub-session plus a manifest (session metadata, CFS version, export-tool version). Implement the mandatory export-time redaction re-scan: even though P5 scrubbed at capture time, export re-runs the corpus-validated rule set (P9) against the full payload as a second gate, defending against rule-set drift between capture and export. Implement X25519 + ChaCha20-Poly1305 envelope encryption (ADR-14) for recipient-scoped exports, and I11's no-co-location check as a hard packaging abort — covering a co-located sidecar file, not only manifest-embedded key material. Implement partial time-range export by reusing Phase 8's ReplayCursor to materialize a self-contained sub-session rather than byte-slicing the frame stream. Implement I12's quarantine-isolation enforcement at export time: a quarantined record's digest is excluded from the exported blob store's index even when the exporting user has raw local access to the underlying store.

22.3 Deliverable

export crate (pack.rs); chronicle export CLI with --recipient <pubkey> and --redact-only modes; export manifest schema documented in docs/; I11's static no-co-location check wired into the packager's own test suite.

22.4 Acceptance Criteria

Export of a 4 GB sealed session completes in ≤ 90 s wall clock on reference hardware (throughput ≥ 45 MB/s, above §4's 40 MB/s scrubber floor); zero archives across fixtures/p10_* contain co-located key material (I11, 100% pass, static check); a 10-minute partial export from a 3-hour session replays standalone via Phase 8's cursor with no dangling references to excluded state.

22.5 Conformance Fixtures

fixtures/p10_full_export_roundtrip.cfs — export then decrypt-and-replay, expected: byte-identical reconstructed state to the source session. fixtures/ p10_key_colocation_reject.cfs — a manifest deliberately fed embedded key material, expected: packaging aborts before any artifact is emitted (I11). fixtures/ p10_partial_time_range.cfs — a 10-minute sub-export of a 3-hour session, expected: independently replayable, no dangling state references. fixtures/p10_quarantine_isolation.cfs — a session containing a quarantined record, expected: the exported shared-index has zero references to the quarantined digest (I12). fixtures/p10_torn_export.cfs — export killed mid-write, expected: the partial artifact is detected and rejected on next open, never treated as valid.

22.6 Pitfalls

Treating capture-time redaction as sufficient and skipping the export-time re-scan ignores that rule-set updates (P9) postdating capture leave an older session exposed to today's known-secret corpus unless re-scanned at export. Placing the decryption key in a "convenience" sidecar beside the archive technically satisfies "not embedded in the manifest" while violating I11's actual intent — the check must cover co-location, not only manifest content. Assuming partial time-range export can byte-slice the CFS frame stream directly breaks keyframe/delta-chain integrity (P8); a fresh self-contained session must be materialized via replay instead. Quarantined digests may already have entered the optional cross-session shared pool (Threat Model T2) before quarantine was applied, so isolation must be re-checked at export time, never assumed from capture-time state alone.

22.7 Performance Concerns

Export throughput is bounded by the slower of the redaction re-scan (§4's 40 MB/s/core floor) and envelope-encryption throughput; benchmark to confirm the scrubber, not the cipher, is actually the bottleneck rather than assuming it. Partial-export materialization via replay must scale with the requested range's size, not the full session's size — profile this explicitly, since a naive implementation could silently degrade to full-session replay cost.

22.8 Edge Cases

Export requested against a still-Recording (not yet Sealed) session must reject or force-seal-a-copy, never target a mutable original (I8's spirit extended to export). Export to a malformed or invalid recipient key is rejected before any redaction-scan work is wasted. Export of a session left with zero exportable content after redaction (everything quarantined) produces an explicit, valid, empty archive rather than a silent failure.

22.9 Failure Analysis

Symptom: an externally shared export was later found to contain a credential the capture-time scrubber had missed. Root cause: the redaction rule-set corpus (P9) had been updated after capture, but the export path was, at the time, skipping re-scan as an assumed "already scrubbed" optimization. Detection: none automated — a manual audit found it, which is itself the failure this phase closes. Recovery: export-time re-scan is now mandatory and non-skippable (22.2); redaction_scan_failures now fires on export-path scans as well as capture-path ones.

22.10 Operational Notes

Every export event is logged locally only (never remote, per P12) with recipient-key fingerprint, time range, and re-scan result; that log is itself an export-scanned artifact if a user chooses to share it, per P12's own rule applied recursively.

23. Phase 11 — Conformance Suite & Performance Hardening

23.1 Objectives

Close the loop P4 opened in Phase 0: assemble the full conformance harness across every fixture and phase, stand up the CFS-reader fuzz target as the primary fuzz surface, run an 8-hour soak, and gate every §4 budget in CI.

23.2 Detailed Implementation Steps

Implement conformance/harness: load every fixtures/p0_* through p10_* file, compare actual outcome to golden expectation, fail CI on any mismatch (P4's enforcement, begun in Phase 0, completed here). Implement fuzz/targets/cfs_reader (cargo-fuzz), the primary fuzz target per this phase's mandate, seeded from fuzz/corpus/ derived from the fixture corpus; implement fuzz/targets/index_rebuild and fuzz/targets/redaction_scan as secondary targets. Implement a fault-injection harness covering torn writes, disk-full/ENOSPC mid-frame, and a killed-mid-export process (extending Phase 10's torn-export fixture pattern), verifying I1 and I11 recovery under simulated failure, not only unit-tested happy paths. Implement the 8-hour soak: a scripted session running all three adapter types (IDE, terminal, DAP) continuously, asserting the §4 memory ceiling and zero queue-depth growth over the run. Wire performance-regression gating comparing every benchmarks/* result against a pinned baseline per PR, extending 20.10's seek-latency gate to every §4 row. Publish a documented third-party conformance vector subset for external CFS-reader implementers to self-verify against.

23.3 Deliverable

conformance/harness runner invoked via scripts/run-conformance.sh; fuzz/targets/ {cfs_reader,index_rebuild,redaction_scan}; an 8-hour soak script under benchmarks/; a published third-party conformance vector subset in conformance/golden/; a CI performance- regression gate covering every §4 row.

23.4 Acceptance Criteria

100% of fixtures/p0_* through p10_* pass with zero mismatches (P4, no exceptions); cfs_reader runs 24 CPU-hours with zero crashes, hangs, or sanitizer failures before exit; the 8-hour soak completes with RSS never exceeding 400 MB burst / 150 MB steady-state (§4) and zero unbounded queue growth; all 15 §4 constraint rows have a CI-enforced gate, verified by an explicit gate-to-constraint count (15 of 15, zero ungated).

23.5 Conformance Fixtures

fixtures/p11_full_corpus_manifest.cfs — a manifest fixture enumerating every prior fixture and its expected outcome, used to catch an accidentally deleted fixture. fixtures/ p11_torn_write_injection.cfs — a fault-injection driver killing the writer at 12 distinct byte offsets within a frame, expected: I1 recovery at every offset. fixtures/ p11_enospc_midframe.cfs — simulated ENOSPC during frame-payload write, expected: the writer aborts the frame cleanly and the next open shows the correct truncation point. fixtures/ p11_thirdparty_vector_01.cfs through _12.cfs — the published external conformance vector set. fixtures/p11_malformed_fuzz_regression_*.cfs — fuzz-discovered crashers, pinned permanently once fixed, never deleted, per P4.

23.6 Pitfalls

Treating "24 CPU-hours, zero crashes" as proof of absence of bugs mistakes a lower bound for a guarantee; pair fuzz hours with coverage-guided corpus review of which record kinds the fuzzer has actually reached. Running the 8-hour soak on idle hardware with a synthetic no-op loop instead of all three adapters under simulated developer activity proves nothing about real memory growth. Gating performance regressions against a baseline captured on noisy, shared CI hardware produces flaky thresholds that erode trust in the gate faster than no gate at all — the baseline needs pinned hardware or a statistically debounced multi-run capture. Publishing third-party conformance vectors before the format is genuinely frozen risks breaking an external implementer's trust in the compatibility promise (§27) before Chronicle has even shipped externally.

23.7 Performance Concerns

Fuzz-target mutation throughput must be profiled separately from bugs-found rate, since a slow harness wastes the 24-CPU-hour budget on fewer effective mutations. Soak-test memory sampling must run at a fine enough cadence (seconds, not hours) to catch a slow leak a coarse sample would miss entirely.

23.8 Edge Cases

A fixture that passes in isolation but fails only when run after another fixture in the same harness invocation indicates shared mutable state leaking between cases and must be isolated per fixture (fresh temp directory each run). A fuzz-discovered crash that reproduces only under a specific CPU architecture's alignment behavior. A performance regression visible only at p99, invisible to a p50-only dashboard.

23.9 Failure Analysis

Symptom: cfs_reader found zero crashes for weeks, then three in one day after a "minor" refactor. Root cause: the refactor changed an early-return bounds check in a way that silently disabled a validation path the fuzzer depended on to reach deeper code, so the target had stopped testing what the corpus review assumed. Detection: coverage-guided corpus review flagged reduced branch coverage in the same PR, before the crashes surfaced. Recovery: a coverage-delta CI check now flags any PR that reduces fuzz-target branch coverage without an explicit justification comment.

23.10 Operational Notes

Fuzz corpus and soak-test baselines are versioned artifacts under benchmarks/ and fuzz/corpus/, never regenerated fresh each run, making regression detection reproducible across CI runs and contributors — the same "tag explicitly, never infer" discipline as CFS format versioning (ADR-02, Phase 0's pitfall).

Structured logging fields (every daemon log line): session_id, sequence_no, capture_state (§8's state machine), component, event, severity — no free-text interpolation of record-payload content, so the log stream itself never becomes an un-scrubbed side channel around the scrubber (P5).

Dashboards: Capture Health (queue depth, frame-write latency percentiles, CPU-budget adherence — §4/§30 rows M1–M6); Format Integrity (digest mismatches, sequence gaps, sealed-mutation attempts — I1/I2/I7/I8); Redaction Posture (scan throughput, timeout rate, quarantine queue depth — I3/I5); Protocol Server Load (RPC latency, subscriber count, capability violations — §21).

Alerting philosophy: the "should be zero" telemetry (replay_state_divergence, quarantine_isolation_violations, export_key_colocation_checks_failed) pages at any nonzero value — these are correctness invariants (I4, I11, I12), not tunable SLO targets. Every other metric alerts on §4/§30 budget breach, debounced over a 5-minute window to avoid single-sample noise.

SLOs: capture overhead ≤ 2% CPU steady-state (M1) over a rolling 24h window; frame-write p95 ≤ 12 ms (M4) over a rolling 1h window; RTO ≤ 2 s daemon-crash-to-resumed-capture (M15), tracked per incident, never averaged away.

Incident response: any nonzero "should be zero" metric pages the on-call maintainer immediately; §4/§30 budget breaches open a tracked issue within one business day, not a page. The postmortem template (templates/postmortem.md) follows Beyer et al.'s blameless structure (§5); every postmortem links the triggering telemetry and the fixture added to prevent recurrence (P4 extended to incidents).

Named runbooks (docs/runbooks/): crash-recovery.md (I1 walkthrough), session-rotation.md (§4's 24h/8GB threshold operational steps), corrupt-session-triage.md (I2/P13 decision tree), redaction-rule-update.md (P9's corpus-validation gate procedure), export-incident.md (I11/T2 response steps), daemon-restart.md (RTO verification steps).

Backup/restore: sealed sessions are user-owned local files, not backed up by Chronicle itself; the conformance fixture corpus and fuzz corpus are treated as CI-critical artifacts, restorable from the last tagged release via scripts/release.sh-adjacent tooling.

Deployment topology: a single-host daemon (chroniclesd) plus an IDE extension plus optional protocol-server clients, all on one developer machine — no server-side fleet in scope through Phase 11 (§31 covers what changes if this assumption is ever relaxed).

Canary/rollback/migration: a new daemon build runs against the existing session directory in read-only canary mode before promotion to the default binary; rollback is a binary swap plus a CFS-version-compatibility check (§27), never a data migration, since P2's append-only rule means old sessions never need rewriting for a new daemon version.

27. Compatibility & Versioning

CFS format versioning: major.minor in the 2-byte format-version field (§8, ADR-02), SemVer-aligned (SemVer 2.0.0, §5). Minor bumps are additive-only (new RecordKind variants, new optional header fields); major bumps may change existing layout and require an explicit migration tool.

Forward-read rule: a reader built against CFS minor version N can open a file at minor version N+k (k≥0) within the same major version, skipping unknown RecordKind tags per the record-type registry below — unknown records are read as opaque length-prefixed blobs.

Backward-read rule: a reader built against minor version N+k can always open a file written at minor version N (older files never carry a field a newer reader doesn't already tolerate as absent/default).

Record-type registry: RecordKind tag values are allocated from a range reserved and frozen at Phase 0 (12.6's pitfall exists precisely to guard this); an unrecognized tag is skipped via its payload_len field without interpreting the payload, logged once per session open, never treated as corruption — distinct from a genuinely malformed frame (P13).

Adapter protocol versioning: AdapterCapabilities (P10) is itself versioned; a core-daemon upgrade that adds a capability flag never breaks an older adapter, since capabilities are additive-only by convention, mirroring the CFS minor-version rule.

API stability: protocol-server's RPC surface (ADR-11/ADR-21) follows the same additive-only discipline — a new query type is a new negotiated capability, never a breaking change to an existing one. The differ crate's diff() signature (19.10) is treated as equivalently frozen; any change is an ADR-02-adjacent compatibility-review event.

Migration tooling: chronicle migrate exists only for major-version bumps (none through Phase 11); it never runs implicitly, is always explicitly invoked, and always operates on a copy, never the sealed original (I8).

Deprecation: a deprecated RecordKind remains readable indefinitely (long-term readability commitment below) but stops being written after a documented deprecation window of at least two minor versions, announced in CHANGELOG.md.

Rolling-upgrade guarantee: a developer can upgrade the daemon and IDE extension independently, in either order, without losing capture — the negotiate handshake (P10) means an older extension against a newer daemon (or vice versa) degrades to the smaller common capability set, never crashes.

Long-term readability commitment: any CFS file sealed under a given major version remains readable by tooling for no less than 10 years from that major version's release, enforced by keeping at least one maintained reader implementation per major version in the conformance suite (§28) for the commitment's duration.

28. Testing & Verification Strategy

Unit: per-crate tests for header/frame encode-decode (cfs-core), chunk-boundary determinism (chunker, ADR-06), rule-set matching (scrubber, ADR-13) — each new RecordKind or layout change ships a fixture the same day per P4.

Integration: the Phase 0–11 fixture corpus (fixtures/p0_*–p11_*) runs end-to-end through conformance/harness (23.2); every phase's N.5 fixtures are integration tests, not documentation.

Property-based: write→read→replay round-trip (any valid record sequence reconstructs identically, I1/I4); dedupe correctness (two sessions with byte-identical content chunks always share one stored copy, I2/P6); diff symmetry (P11, 19.4's 100%-of-corpus assertion).

Differential: two independent CFS reader implementations (the primary Rust reader and a minimal reference reader built solely from the third-party conformance vectors, 23.2) must agree on reconstructed state for every fixture — a divergence here is a specification- clarity bug, not only an implementation bug.

Fuzzing: cfs_reader is the primary target (I1/I2/P13, 23.2); index_rebuild (I6) and redaction_scan (I3/I5/P9) are secondary targets; every crash becomes a permanent regression fixture (P4).

Chaos / fault injection: torn writes at 12 byte offsets (I1, p11_torn_write_injection.cfs), ENOSPC mid-frame (p11_enospc_midframe.cfs), killed-mid-export (I11, p10_torn_export.cfs), simulated clock-step during capture (I7).

Deterministic replay: I4's cross-reader golden-state comparison (Phase 8, 20.5) runs on every fixture touching replay, not sampled.

8-hour soak: continuous multi-adapter capture (23.2) asserting §4's memory ceiling and zero unbounded queue growth (P1/P3) — run before every major release, not only once at Phase 11 exit.

Conformance vectors for third-party readers: the published subset (23.3) is itself covered by CI to detect drift between the internal fixture corpus and the published external one.

Performance-regression gating: every benchmarks/* result is compared to a pinned baseline per PR (23.2), covering all 15 §4 rows (§30's M1–M15).

Every test class above ties back to a specific invariant (I1–I12) or a phase's N.5 fixture set — no test category in this strategy exists without a named correctness or performance claim it defends.

29. Build & Release Engineering

Reproducible builds: cargo build --locked against a pinned Cargo.lock (ADR-23) inside a pinned container image (Dockerfile), verified by comparing build-output digests across two independent build machines before a release is tagged.

Artifact signing: release binaries and the VS Code extension package (ADR-20) are signed with a maintainer-held key; signatures are verified by scripts/release.sh before upload, never trusted from a prior manual step.

SBOM: a software bill of materials is generated per release (cargo-cyclonedx or equivalent) and published alongside the release artifact, enabling the dependency-audit Threat Model mitigation (T10) to be checked against a specific release, not just HEAD.

Release channels: stable (tagged, signed, SBOM-published), nightly (unsigned, internal dogfooding only, never distributed externally) — matching the CFS version-freeze discipline, a nightly never changes a frozen minor version's on-disk layout.

CI/CD topology: PR pipeline runs unit + integration + clippy + the conformance harness (23.2) + the performance-regression gate (23.2); nightly additionally runs the fuzz targets for a bounded CPU-hour budget and the 8-hour soak; release additionally runs the full 24-CPU-hour fuzz budget (23.4) and cross-machine reproducible-build verification.

Version stamping: the daemon, CLI, and extension all embed the CFS format version (§27) and the build's git commit hash in --version output, so a bug report always carries enough information to reproduce the exact build.

Provenance/attestation: releases carry a SLSA-style build provenance attestation binding the signed artifact to the exact CI run and commit that produced it, checkable independently of trusting the release page.

Dependency auditing: cargo-audit and cargo-vet run in CI on every PR (T10's mitigation); a new transitive dependency with no vet record blocks merge until reviewed.

Marketplace publishing: the VS Code extension (ADR-20) publishes to the marketplace only from the release pipeline, never from a developer machine, closing the update-channel half of Threat Model row T6.

31. Scalability Analysis

Constant regardless of session length: per-frame write cost (M3–M5); single-query index lookup cost (O(log n) via the SQLite page image, ADR-07). Grows with session length: raw record-stream bytes (linear, bounded by rotation, M13); index size (linear but bounded to ≤2% of raw, M11); delta-chain length between keyframes (bounded by ADR-18's dual threshold, never unbounded).

Named bottlenecks in order of first appearance as session size grows: (1) delta-chain replay cost at the keyframe boundary (Phase 8, M10) — the first bottleneck a developer notices, as seek latency creeps toward the 150 ms budget near rotation size; (2) index rebuild time (I6) on a very large sealed session after a crash; (3) redaction scan throughput (M14) under an unusually terminal-output-heavy session; (4) cross-session shared blob-pool contention (Threat Model T2) once many sessions reference a common large vendored dependency's text.

Horizontal scaling: out of scope for a single-developer local tool through Phase 11 (§26's deployment topology) — there is no fleet to shard. The one horizontally-scalable-shaped component is the protocol server if a future team-dashboard consumer emerges (ADR-21's rejected-alternative note), tracked in the Deferred Features Register (§37), not built now.

Vertical scaling: raising the capture-agent memory ceiling (M12) linearly extends the burst-tolerant window (e.g., a larger terminal replay or test run) but does not change per-frame write latency, since the write path is CPU/syscall-bound, not memory-bound.

Sharding: not applicable to a per-developer local session file; the closest analogue is session rotation itself (M13) acting as a time-based shard boundary, chosen specifically so no single file's size becomes an unbounded liability (§4).

Coordination overhead: zero cross-process coordination on the write path (ADR-12's single-writer model) — the only coordination is protocol-server read concurrency (Phase 9), which is read-only and therefore lock-free against the writer by construction.

Practical ceiling: a single session is capped at 24h/8GB by design (M13); beyond that, Chronicle's answer is more sessions, not a bigger session — the lever beyond the ceiling is cross-session query (protocol server, index) rather than any attempt to make one file larger. A second lever, deferred, is a shared cross-developer index for team-scale queries, explicitly out of scope and tracked in §37.

32. Mental Models & First Principles

MM1 — A session is a log, not a database. Every feature (index, replay, diff, export) is a projection over an append-only stream, never a first-class store of its own. Predicts: any feature whose implementation requires rewriting history is architecturally wrong. Bug class avoided: mutable-index-as-truth bugs where the index and the log disagree and the index wins (it never should, I6). Resolved in §8, §27.

MM2 — Capture is a producer that must never wait on a consumer. The queue (P1/P3) is the one-way valve between "an event happened" and "an event is durable". Predicts: any design letting replay, export, or protocol-server load slow down capture is a regression, not a feature interaction. Bug class avoided: editor lag caused by the very tool built to diagnose editor lag. Resolved in Phase 1 (§13), §21.6.

MM3 — Identity is content, not location. A blob's digest (P6) is what it is, not where it sits. Predicts: two sessions can share storage safely without coordination, and a byte-for-byte identical file always dedupes, regardless of when or where it was captured. Bug class avoided: location-based cache-invalidation bugs content-addressing sidesteps entirely. Resolved in §8, Phase 2 (§14).

MM4 — A keyframe is a performance dial, never a correctness dial. Changing keyframe cadence must never change what replay produces (P8), only how fast it produces it. Bug class avoided: two readers disagreeing about state because they chose different keyframes (I4). Resolved in §8, Phase 8 (§20).

MM5 — Redaction is a gate, not a filter. Nothing crosses from capture to disk unscanned (P5); this is a hard ordering constraint, not a best-effort pass applied "eventually". Bug class avoided: a race where a secret reaches disk before the scrubber runs. Resolved in Phase 4 (§16), §24 (T1, T9).

MM6 — Fail loud beats fail quiet for a format whose entire job is being evidence. A parser that guesses at a malformed byte offset instead of naming it (P13) turns a debugging tool into another thing that needs debugging. Bug class avoided: silent truncation masquerading as a successful read. Resolved in §8, Phase 0 (§12).

MM7 — Capability negotiation beats version sniffing for any protocol with more than one implementer. An adapter declares what it can do (P10) rather than Chronicle guessing from a version string. Bug class avoided: an "if version >= X" branch matrix that silently breaks on the first host not fitting the assumed version-to-feature mapping. Resolved in §8's Adapter Contract, Phase 1 (§13), Phase 9 (§21).

MM8 — Diff must be provably symmetric, not just apparently symmetric. P11's round-trip assertion exists because "looks right on the fixtures tried" is not the same claim as "provably round-trips for any valid pair". Bug class avoided: an asymmetric diff that corrupts a replay-by-diff-chain only on inputs no one happened to test. Resolved in Phase 7 (§19).

34. Back-of-Envelope Capacity Model

  1. Raw keystroke-edit stream: 300 keystrokes/minute active typing, ~2 bytes/keystroke delta average (small EditDelta CBOR overhead) → 300 × 2 = 600 bytes/min → 36,000 bytes/hour ≈ 35 KB/hour — small relative to the 25 MB/hour ceiling (M7), confirming keystrokes are not the dominant raw-stream contributor.

  2. Buffer-save deltas: 20 saves/hour, average edit-since-last-save 4 KB → 20 × 4 KB = 80 KB/hour — still well under M7's ceiling, confirming terminal/build output (below) dominates raw growth, not editor activity.

  3. Terminal volume: a moderately chatty build/test loop producing 5 KB/s of terminal output for 10 minutes/hour of active session time → 5 KB/s × 600 s = 3 MB/hour — the dominant raw-stream contributor, consistent with M7's 25 MB/hour ceiling existing mostly to bound terminal-heavy sessions.

  4. Raw pre-dedupe total: 35 KB (keystrokes) + 80 KB (saves) + 3 MB (terminal) + ~1 MB/hour assumed debugger/VCS overhead ≈ 4.1 MB/hour typical, up to M7's 25 MB/hour ceiling for a terminal-output-heavy hour (repeated full test-suite runs).

  5. Post-dedupe, pre-compression: applying M9's ≥4:1 chunk-dedupe target to the 25 MB/hour worst case → 25 MB ÷ 4 = 6.25 MB/hour (repeated terminal banners and build output dedupe well).

  6. Post-compression session size: applying M9's ≥3:1 zstd ratio to the 6.25 MB residual → 6.25 MB ÷ 3 ≈ 2.08 MB/hour, comfortably under M8's 4 MB/hour target, leaving headroom for a worse-than-typical dedupe ratio.

  7. Index RAM footprint: 8 KiB average chunk size (§8) → a 4 MB/hour post-dedupe session over 24h (M13's ceiling) references ≈ 96 MB ÷ 8 KiB ≈ 12,000 unique chunks; at 32 bytes/digest (SHA-256 truncated reference, ADR-04) + ~24 bytes/index-entry overhead ≈ 56 bytes/entry → 12,000 × 56 bytes ≈ 672 KB — trivially within M11's ≤2%-of-raw-size ceiling at this scale.

  8. Keyframe cost: cadence of one Full snapshot per 2 minutes (§8) → 30 keyframes/hour; assume 15 open buffers averaging 8 KB each per keyframe → 15 × 8 KB = 120 KB/keyframe → 30 × 120 KB = 3.6 MB/hour of raw keyframe bytes before dedupe — a meaningful fraction of the pre-dedupe 25 MB ceiling, explaining why keyframes are chunked and deduped like any other blob (P6), never treated as an exempt special case.

  9. Replay seek cost: worst case is a target immediately before the next keyframe, i.e. up to 200 accumulated deltas (ADR-18's threshold) since the last one; at an assumed 0.5 ms/delta apply cost (structural diff apply, Phase 7/8) → 200 × 0.5 ms = 100 ms, comfortably under M10's 150 ms p95 budget with ~50 ms of margin for index-lookup overhead.

  10. 24-hour session ceiling check: 2.08 MB/hour (step 6, typical) × 24h ≈ 50 MB typical sealed size, or up to 25 MB/hour raw worst-case × 24h = 600 MB pre-dedupe → ÷12 combined ratio (M9's 4:1 × 3:1) = 50 MB worst-case post-compression too — both scenarios land far under M13's 8 GB size-based rotation trigger, confirming the 24h wall-clock threshold, not the 8 GB size threshold, is the binding rotation trigger for a typical developer session (only an unusually terminal-heavy session approaches the size trigger first).

36. Alternative Architectures (Roads Not Taken)

(a) Full deterministic syscall-level record/replay, Chronicle as a viewer atop it.

[app process]--syscalls-->[rr/Pernosco-style tracer]--trace-->[trace store]
                                                          |
                                                    [Chronicle viewer]
                                                    (queries trace via
                                                     its own index, no
                                                     independent capture)

Winning regime: post-mortem debugging of a crash where instruction-level determinism is the entire point. Real embodying system: rr / Pernosco (§33, §5's O'Callahan citation). Rejected here: overhead and platform-coupling (ptrace-based syscall interception) are incompatible with §4's ≤2% CPU / any-language-IDE goal (§1's non-goal boundary) — Chronicle targets tool-level developer questions (Ko & Myers, §5), not instruction-level ones.

(b) Screen recording plus OCR.

[screen capture]--video frames-->[OCR pass]--text-->[searchable index]

Winning regime: capturing a workflow with no programmatic access to the tool at all (a closed proprietary app with no extension API). Real embodying system: various screen-recording-plus-search tools in the QA/support-ticket space (no single canonical named project reaches reference-implementation status here). Rejected here: no structural fidelity (no BufferState, no EditDelta, no digest-addressable content, P6 inapplicable), OCR error rate makes redaction (P5) unreliable at the pixel level, and replay determinism (I4) is meaningless over lossy video.

(c) A git-commit-per-checkpoint model, no custom format.

[editor event]--debounced-->[git commit to a shadow branch]
                                        |
                                  [git log / git diff
                                   as the "replay" UI]

Winning regime: a team already fluent in git tooling wanting checkpoint-granularity history with zero new format to learn. Real embodying system: git itself (§33). Rejected here: commit granularity (seconds-to-minutes) cannot meet §4's 250 ms/512-event capture cadence; git has no first-class terminal-output, debugger-state, or cursor-position record kinds; and P2's append-only guarantee would fight git's mutable-ref/rebase-capable object model constantly.

(d) A cloud-streamed session with no local file.

[capture agent]--stream-->[cloud ingest]--store-->[cloud session store]
                                                          |
                                                   [any client, query
                                                    over network]

Winning regime: a team-wide, always-shareable, no-local-storage session model where cross-developer query (§31's deferred lever) is the primary goal, not local debugging speed. Real embodying system: no single reference implementation matches this shape precisely for developer-session capture; closest conceptually is a hosted logging/APM pipeline. Rejected here: violates P12 (telemetry never leaves the machine by default) outright as an architecture, not just a default; also reintroduces the T5/T8 shared-machine and unauthorized-read threat surface at cloud scale instead of local-socket scale.

38. Glossary

Frame — the atomic on-disk unit: magic, sequence number, record kind, payload, checksum (§8).

Record — the CBOR-encoded payload body carried by a frame; one of the RecordKind catalogue entries (§8).

Keyframe — a Full Snapshot record bounding replay cost (P8), written on a 2-minute or 200-delta cadence (ADR-18).

Delta snapshot — a Snapshot expressed as a prior snapshot digest plus a chain of EditDelta/state-change records (§8).

Content-defined chunking (CDC) — splitting a blob into variable-length chunks at content-determined boundaries (FastCDC gear hash, ADR-06) so identical sub-sequences dedupe regardless of surrounding-byte shifts.

Blob digest — the content-address (SHA-256, ADR-04) identifying a chunk; the only identity a blob has (P6).

Index footer — the CFS region mapping sequence↔offset, timestamp↔keyframe, digest↔ offset, and kind↔sequence-list, stored as an embedded SQLite page image (ADR-07).

Torn write — a frame left incomplete by a crash mid-write; detected via checksum mismatch on the trailing frame (I1).

Sealed session — a session whose Seal record and whole-file digest have been written, making it immutable (I8).

Replay cursor — the ReplayCursor object performing keyframe-plus-delta-chain state reconstruction at an arbitrary seek target (Phase 8).

Redaction rule — a pattern (regex or entropy-heuristic) in the scrubber's active rule set (P9, ADR-13) that triggers quarantine.

DAP — Debug Adapter Protocol; governs Chronicle's passive-observer debugger integration (ADR-10, §5).

PTY tap — the mechanism by which the terminal adapter observes a pseudo-terminal's input/output stream without interposing on it.

CFS — Chronicle Format Specification; the versioned, content-addressed, append-only on-disk session format (§8).

Seal-then-advance — the writer protocol of writing frame bytes, computing checksum, then only advancing the cursor (I1, Phase 0).

Quarantine — the state of a record that failed or timed out a redaction scan, held pending manual scrub rather than dropped or persisted raw (I5).

Capability negotiation — the AdapterCapabilities/ClientCapabilities handshake replacing version-sniffing (P10).

Coalescing — merging adjacent same-kind events (e.g., rapid cursor moves) under backpressure instead of blocking or dropping (P3).

Keyframe cadence — the dual threshold (time or delta-count) governing how often a Full snapshot is written (ADR-18).

Content address — an identifier derived solely from a byte sequence's digest, never from location (P6, MM3).

Dedupe ratio — raw bytes referenced ÷ unique bytes stored (§8, M9).

Snapshot — the reconstructable state of tracked buffers, debugger frame, and terminal cursor at a point in time; Full or Delta (§8).

Frame checksum — the CRC32C (ADR-19) validating a single frame's integrity, distinct from the whole-file seal digest.

Whole-file digest — the SHA-256 (ADR-04) over the entire sealed file, computed once at seal time (I8).

EditDelta — a record describing a buffer change relative to a declared base BufferState digest (I9).

BufferState — a full, self-contained snapshot of one tracked buffer's content.

VcsPosition — HEAD ref, branch name, and dirty-file digest set, captured as a VcsCheckpoint record.

TerminalChunk — a timestamped, stream-tagged (stdin/stdout) byte fragment (ADR-15).

Chunk store — the content-addressed blob storage layer, deduped via CDC (§8, Phase 2).

Capture scheduler — capture-sched's bounded queue and batcher enforcing P1/P3's never-block, coalesce-under-load discipline.

Scrubber — the redaction engine scanning records before persistence (P5, scrubber crate).

Differ — the differ crate computing symmetric structural diffs (P11, Myers 1986, ADR-16).

Replay engine — the replay crate's seek/reconstruct machinery (Phase 8).

Protocol server — the cross-tool local RPC surface (protocol-server crate, ADR-11).

Live-tail — subscribing to newly sealed frames of an in-progress session (P7, Phase 9).

Export packager — the export crate's archive-and-encrypt pipeline (Phase 10, ADR-14).

Envelope encryption — the X25519 + ChaCha20-Poly1305 recipient-scoped scheme used for exports (ADR-14).

Conformance fixture — a named .cfs file exercising a specific format or behavior guarantee, shipped the same day as the change it defends (P4).

Conformance harness — the runner comparing every fixture's actual outcome to its golden expectation, gating CI (Phase 11).

Third-party conformance vector — a published fixture subset letting an external CFS reader implementer self-verify (Phase 11).

Fault injection — deliberately simulated failures (torn write, ENOSPC, killed process) used to test recovery paths beyond unit-tested happy paths.

Soak test — an extended-duration run (8 hours) asserting no resource-growth regressions under continuous realistic load.

Rotation — starting a new session file upon reaching the 24h/8GB threshold (ADR-17).

RTO — recovery time objective; the daemon-crash-to-resumed-capture budget (§4, M15).

SBOM — software bill of materials; published per release (§29) for dependency audit.

Provenance attestation — a signed record binding a release artifact to its exact build and commit (§29).

Golden fixture / golden state — the recorded expected output a conformance test compares against (I4, §28).

Capability violation — a call for an operation outside a negotiated capability set, rejected before dispatch (I10).

Rolling upgrade — independently upgrading daemon and adapter without losing capture, guaranteed by additive-only capability evolution (§27).
