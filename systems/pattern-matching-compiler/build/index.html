⬜ Phase 0 — Repository, Deterministic Infrastructure & Correctness Kernel §12

Objectives

Establish the Cargo workspace, deterministic tooling baseline, telemetry architecture, and the correctness kernel (replay event log, arena allocator conventions, trampoline recursion primitive) that every later phase depends on. Introduces the constraint that no stage may use wall-clock time or unordered iteration (P1, ADR-20). Distributed compilation and incremental dependency-graph invalidation are explicitly out of scope for this single-host kernel — PhaseDeferred("§12") for both, registered in §35.

Deliverable

A reproducible workspace: cargo build --locked produces byte-identical artifact hashes across two clean-checkout CI runs; cli binary accepts --replay-seed and emits a replay event log for a no-op compilation.

Acceptance
  • Artifact hash identical across 3 consecutive CI reruns (0 divergence, I1).
  • Zero clippy::all warnings at deny level (ADR-19).
  • fixtures/replay/basic.json round-trips through replay::event_log with checksum match.
  • Startup time < 100 ms (§4) measured over 50 CLI invocations, p95.
Fixtures
  • fixtures/replay/basic.json — minimal one-event replay log; validates checksum-covered round trip (I10).
  • fixtures/logging/startup.snap — snapshot of structured startup log fields; catches accidental non-deterministic field ordering (P3).
  • fixtures/replay/corruption_case.bin — deliberately bit-flipped log; must be rejected with a checksum-mismatch diagnostic, not silently accepted (malformed case).
Pitfalls
  • Nondeterministic timestamps. Manifestation: artifact hash differs across reruns · Root cause: a stray SystemTime::now() call bypassing LogicalClock · Debug method: diff two CI run artifact hashes, bisect by crate · Signal: replay.checksum_mismatch_total > 0 · Recovery: replace with LogicalClock, add a clippy lint forbidding SystemTime outside telemetry.
  • Locale-sensitive formatting. Manifestation: diagnostic snapshot fails only on non-C-locale CI runners · Root cause: default number/date formatting reading LC_ALL · Debug method: rerun snapshot test with LC_ALL=C vs LC_ALL=de_DE.UTF-8 · Signal: snapshot diff limited to numeric separators · Recovery: force explicit formatting, never locale-default.
  • Unstable hash maps. Manifestation: replay divergence only under -j parallel test runs · Root cause: iterating a HashMap instead of an ordered IndexMap/BTreeMap in a telemetry-aggregation path · Debug method: recursion-depth/order gauge diff between two runs of the same fixture · Signal: matrix.row_order_digest mismatch (I1) even in Phase 0 scaffolding code · Recovery: replace with an order-preserving container workspace-wide.

⬜ Phase 1 — Lexer & Token Infrastructure §13

Objectives

Implement a UTF-8-aware, deterministic, span-tracked lexer producing a lossless (I11) token stream with trivia preservation, feeding the Phase 2 (§14) parser.

Deliverable

lexer::tokenize(&str) -> TokenStream producing a stable, hashable token stream for any input up to the 64 MB §4 file-size ceiling, with round-trip re-emission matching original bytes exactly for well-formed input.

Acceptance
  • 100% pass rate on the 3 named lexer fixtures below.
  • Token-stream hash identical across 10 repeated tokenizations of the same input (I1-adjacent determinism).
  • Round-trip re-emission byte-identical for well-formed input (I11), diff-tested against the original source.
  • Lexer throughput ≥ 200 MB/s on the benchmark corpus (feeds the M5 §28 target).
Fixtures
  • fixtures/lexer/malformed_utf8.txt — invalid byte sequences; expects U+FFFD substitution diagnostics, no panic.
  • fixtures/lexer/nested_patterns.txt — deeply nested constructor/tuple tokens; expects correct span nesting under the 4096 §4 branch-depth-adjacent token-nesting budget.
  • fixtures/lexer/trivia_spacing.txt — irregular whitespace/comment placement; expects trivia preserved and round-trip byte-identical.
Pitfalls
  • Unicode normalization drift. Manifestation: two visually identical identifiers hash differently · Root cause: NFC vs NFD normalization applied inconsistently · Debug method: compare identifier byte sequences directly in a failing fixture · Signal: types reports a spurious duplicate-binding diagnostic (I3-adjacent) · Recovery: lock lexer identifier handling to raw bytes, never normalize.
  • Span off-by-one errors. Manifestation: diagnostic underline points one column short · Root cause: byte-offset vs. codepoint-offset confusion in multi-byte UTF-8 sequences · Debug method: fixture with a known multi-byte character at a known column · Signal: I4 monotonic span assertion still passes (offsets increase) but is wrong by construction · Recovery: add a codepoint-boundary assertion, not just a monotonicity assertion.

⬜ Phase 2 — Parser & AST §14

Objectives

Implement a handwritten recursive-descent parser (ADR-07-equivalent choice, locked in ADR-07 of §9 as "handwritten recursive descent" for diagnostics quality) with deterministic error recovery, producing an arena-owned immutable AST.

Deliverable

parser::parse(TokenStream) -> (Ast, Vec<Diagnostic>) producing a lossless parse tree for well-formed input and a best-effort recovered tree plus diagnostics for malformed input, never a panic.

Acceptance
  • Parser roundtrip snapshots stable across 3 CI reruns (0 divergence, P1).
  • Malformed-input recovery coverage > 95% measured over a 200-case malformed-fixture corpus (i.e. < 5% of malformed inputs cause full parse abandonment rather than partial recovery).
  • All 3 named conformance fixtures below produce the expected diagnostic code and recovered AST shape.
Fixtures
  • fixtures/parser/missing_paren.pm — unterminated constructor pattern; expects a partial-tuple diagnostic and recovery at the next =>.
  • fixtures/parser/nested_or_pattern.pm — deeply nested OR-patterns; expects correct left-associative grouping and no recursion-depth panic (I13).
  • fixtures/parser/guard_chain.pm — chained guard expressions; expects guard spans attached to the correct enclosing pattern.
  • fixtures/parser/empty_tuple.pm — () pattern edge case; expects a zero-arity Tuple node, not a parse error.
Pitfalls
  • Recursive explosion. Manifestation: stack overflow on adversarially nested patterns · Root cause: native recursive descent without the Phase 0 trampoline bound · Debug method: fixture with 5000+ nested tuples, watch matrix.recursion_depth-equivalent parser gauge · Signal: process crash with no diagnostic emitted (violates P11) · Recovery: route deep constructor/tuple nesting through the bounded trampoline, cap at the 4096 §4 branch-depth soft limit with a diagnostic, not a crash.
  • Ambiguity resolution drift. Manifestation: the same OR-pattern parses differently across releases · Root cause: precedence-table change without a corresponding fixture update · Debug method: differential-parse the fixture corpus against the previous release binary · Signal: fixtures/parser/nested_or_pattern.pm snapshot diff · Recovery: pin precedence table behind ADR review, require a fixture for any precedence change.

⬜ Phase 3 — Type Resolution & Semantic Binding §15

Objectives

Resolve constructor identity, variant compatibility, wildcard typing, tuple/slice arity, and guard-binding semantics, closing pattern identity over resolved constructor IDs (I3) rather than source text.

Deliverable

types::resolve(&Ast, &Schema) -> (TypedPatternTree, Vec<Diagnostic>) producing a semantically-resolved pattern tree with every constructor reference bound to a stable ConstructorId.

Acceptance
  • Constructor resolution deterministic across 3 reruns (0 divergence, I3).
  • Semantic-mismatch diagnostics (unknown constructor, arity mismatch, OR-pattern binding-set mismatch) stable in snapshot form (P3).
  • fixtures/types/unknown_constructor.pm and fixtures/types/mismatched_or.pm produce the exact expected diagnostic codes.
  • Guard-purity analysis rejects 100% of a 20-case synthetic-impurity fixture corpus.
Fixtures
  • fixtures/types/unknown_constructor.pm — references an undeclared variant; expects a stable E-UNKNOWN-CTOR diagnostic.
  • fixtures/types/mismatched_or.pm — OR-pattern alternatives binding different variable sets; expects E-OR-BINDING-MISMATCH.
  • fixtures/types/duplicate_binding.pm — the same variable bound twice in one pattern; expects E-DUPLICATE-BINDING, not a silent shadow.
Pitfalls
  • Shadowed binding ambiguity. Manifestation: a nested pattern's binding silently shadows an outer one, producing a surprising guard-evaluation value · Root cause: symbol resolution scoping the inner binding without flagging the shadow · Debug method: fixture with a deliberately shadowed name, inspect resolved SymbolId chain · Signal: guard evaluates against the wrong binding in a differential test against a reference implementation · Recovery: emit an explicit shadow-warning diagnostic (non-fatal), document as intended behavior matching host-language scoping rules.

⬜ Phase 4 — Pattern Normalization §16

Objectives

Canonicalize all resolved patterns into the normalized pattern-ir form matrix decomposition requires: flattened OR-patterns, expanded implicit captures, normalized ranges, assigned constructor IDs carried forward from Phase 3.

Deliverable

pattern_ir::normalize(TypedPatternTree) -> PatternMatrix producing the canonical matrix form consumed unchanged by Phase 5 specialization.

Acceptance
  • Normalization idempotence: re-normalizing normalized IR produces a byte-identical digest in 100% of the 500-case regression corpus.
  • OR-pattern row expansion bounded: no single arm expands past 512 rows (enforced ceiling, feeding P5); exceeding it emits E-OR-EXPANSION-LIMIT rather than allocating unbounded rows.
  • fixtures/normalize/or_expansion.pm and fixtures/normalize/tuple_flatten.pm pass with exact expected row counts.
Fixtures
  • fixtures/normalize/or_expansion.pm — a 4-way nested OR-pattern; expects exactly 16 expanded rows (2^4).
  • fixtures/normalize/tuple_flatten.pm — nested tuple-of-tuple pattern; expects flattened column structure matching the ADT's true field arity.
  • fixtures/normalize/nested_or_guard.pm — OR-pattern with an attached guard; expects the guard duplicated correctly across every expanded row, not attached to only the first.
Pitfalls
  • Exponential OR expansion. Manifestation: normalization latency spikes on a legitimate-looking but deeply nested OR-pattern · Root cause: naive Cartesian expansion of nested ORs without a row-count ceiling · Debug method: pattern_ir.rows_generated metric spike correlated with one fixture · Signal: allocation-amplification metric exceeds the 1.8x §4 ceiling · Recovery: enforce the 512-row ceiling above, emit a diagnostic recommending restructuring rather than silently truncating.

⬜ Phase 5 — Pattern Matrix Compiler (Specialization) §17

Objectives

Implement Maranget-style matrix specialization and default-matrix construction: the core divide-and-conquer decomposition algorithm every downstream phase (exhaustiveness, redundancy, decision-tree) consumes. SIMD-width vectorized matching is explicitly out of scope for this scalar specialization engine — PhaseDeferred("§17"), registered in §35.

Deliverable

matrix_compiler::specialize(&PatternMatrix, ConstructorId) -> PatternMatrix and matrix_compiler::default_matrix(&PatternMatrix) -> PatternMatrix, both pure and cache-consistent, feeding Phase 6/7 analysis and Phase 8 decision-tree construction from the same specialization calls (no duplicated logic between analysis and codegen).

Acceptance
  • Decomposition correctness verified via replay: 100% of the 300-case fixture corpus produces a specialization sequence bit-identical to its recorded replay trace (I1).
  • Specialization cache hit rate ≥ 60% on the sparse_matrix.pm benchmark input (feeds M-series §28 targets).
  • Recursion depth never exceeds the 4096 §4 soft limit on any fixture; exceeding it degrades to a diagnostic, not a crash (I13).
Fixtures
  • fixtures/matrix/specialization_chain.pm — a 6-deep nested-constructor chain; expects a specific, recorded specialization-call sequence matching its replay trace.
  • fixtures/matrix/sparse_matrix.pm — a matrix with many wildcard-dominated columns; expects high cache-hit-rate specialization.
  • fixtures/matrix/empty_matrix.pm — a matrix with zero rows (unreachable scrutinee type); expects a well-defined Failure-terminal result, not a panic.
Pitfalls
  • Matrix explosion. Manifestation: memory usage spikes disproportionately to input pattern count · Root cause: specialization cache disabled or a cache key collision causing redundant sub-matrix materialization · Debug method: matrix.rows_materialized metric growth vs. expected O(patterns × constructor arity) bound · Signal: allocation-amplification exceeds the 1.8x §4 ceiling · Recovery: specialization throttling (reduce cache eviction aggressiveness, fall back to default-matrix-only decomposition for pathological inputs) — this is FM-1.
  • Recursion overflow. Manifestation: process abort on deeply nested constructor chains · Root cause: a code path bypassing the Phase 0 trampoline (e.g. an inlined fast path added for performance that forgot the bound) · Debug method: matrix.recursion_depth gauge spikes past 4096 immediately before the abort · Signal: no diagnostic emitted (P11 violation) · Recovery: route the fast path back through the trampoline, add a regression fixture at depth 4097.

⬜ Phase 6 — Exhaustiveness Analysis §18

Objectives

Implement the usefulness algorithm (Maranget 2007, §5 Papers) to detect missing match coverage and synthesize a human-readable missing-pattern witness for every gap. GADT-aware refinement typing and symbolic SAT-backed exhaustiveness are both explicitly out of scope for this constructor-space usefulness checker — PhaseDeferred("§18") for both, registered in §35.

Deliverable

exhaustiveness::check(&PatternMatrix) -> ExhaustivenessResult returning either Exhaustive or Missing(Vec<Witness>), gating whether Phase 8 decision-tree construction may proceed to codegen (P2).

Acceptance
  • Matches rustc/OCaml reference behavior (§5 Reference Implementations) on 100% of the 150-case differential fixture corpus (0 disagreements).
  • Usefulness recursion depth stays under 10.9M witness-node ceiling derived in §32 C4 for the 1 GB §4 exhaustiveness memory budget.
  • fixtures/exhaustiveness/non_exhaustive.pm produces the exact expected witness pattern string.
Fixtures
  • fixtures/exhaustiveness/non_exhaustive.pm — a match missing one variant; expects a witness naming that exact variant.
  • fixtures/exhaustiveness/recursive_variant.pm — a recursive ADT (e.g. a list-like constructor referencing itself); expects termination without infinite constructor-space enumeration.
  • fixtures/exhaustiveness/nested_slice.pm — nested slice patterns with rest-bindings; expects correct witness synthesis across variable-length constructor splits.
Pitfalls
  • Infinite constructor expansion. Manifestation: exhaustiveness check hangs on a recursive ADT · Root cause: constructor-space enumeration recursing into the same recursive variant without a visited-set bound · Debug method: exhaustiveness.recursion_depth metric climbing unbounded on recursive_variant.pm · Signal: memory approaches the 1 GB §4 ceiling before hang · Recovery: bound enumeration depth, treat depth-exceeded as "assume covered by wildcard" with a diagnostic note rather than hanging (documented conservative approximation).

⬜ Phase 7 — Redundancy Analysis §19

Objectives

Detect unreachable branches, shadowed patterns, and dead guards using the same usefulness foundation as Phase 6, maintaining the I2 agreement invariant between the two analyses.

Deliverable

redundancy::check(&PatternMatrix) -> Vec<RedundancyDiagnostic> identifying every row's reachability status, consumed by both the diagnostics engine (user-facing warnings) and Phase 8 (dead rows are excluded from decision-DAG construction as an optimization).

Acceptance
  • Zero false positives across the 120-case conformance suite (a false positive here means flagging a reachable row as dead — verified via differential execution against backend-bytecode for that exact row's discriminating input).
  • fixtures/redundancy/dead_branch.pm and fixtures/redundancy/shadowed_or.pm produce the exact expected redundant-row indices.
  • Guard-bearing rows are never reported as fully redundant (100% of a 30-case guard-fixture corpus).
Fixtures
  • fixtures/redundancy/dead_branch.pm — a row fully shadowed by an earlier wildcard; expects that row flagged dead.
  • fixtures/redundancy/shadowed_or.pm — one alternative of an OR-pattern shadowed by an earlier row while the other alternative remains reachable; expects only the shadowed alternative flagged, not the whole OR-pattern.
  • fixtures/redundancy/recursive_guard.pm — a guard referencing a recursively-bound capture; expects the row correctly excluded from dead-branch flagging (I5-consistent).
Pitfalls
  • Guard interaction bugs. Manifestation: a row with a guard is incorrectly flagged dead · Root cause: redundancy analysis treating a guarded row identically to an unguarded row during usefulness checking · Debug method: differential-execute the flagged row's discriminating input against backend-bytecode; if it actually executes, the flag is a false positive · Signal: fixtures/redundancy/recursive_guard.pm regression · Recovery: guard rows always contribute their pattern (guard-stripped) to the "still useful" set for later rows, never treated as fully covering.

⬜ Phase 8 — Decision Tree Generation & Optimization Pipeline §20

Objectives

Lower the analyzed, dead-row-pruned PatternMatrix into an acyclic decision DAG (I6) with dominance-based node merging, then apply semantics-preserving optimization passes (I12). Speculative branch-prediction feedback (profile-guided reordering fed back from production telemetry) is explicitly out of scope for this static pipeline — PhaseDeferred("§20"), registered in §35.

Deliverable

decision_tree::build(&PatternMatrix) -> Dag followed by optimizer::run(Dag) -> Dag, producing an optimized, acyclic decision DAG ready for Phase 9 dual-backend codegen, with a DOT-graph export for operator inspection (tools/dag_to_dot.rs).

Acceptance
  • Deterministic DAG hashes across 3 CI reruns (0 divergence, I1-adjacent).
  • Decision-tree generation throughput ≥ 50,000 nodes/sec (§4 M3 target), measured on the benchmarks/dag_generation.rs corpus.
  • Branch-count reduction measurable: optimized DAG has ≥ 15% fewer test nodes than the pre-optimization DAG on the redundant_tests.pm/branch_merge.pm fixtures.
  • Zero I12 semantic-drift violations across the 100-case optimizer differential-test corpus.
Fixtures
  • fixtures/decision-tree/deep_branch.pm — a wide, deep constructor space; expects a DAG within the 4096 §4 branch-depth soft limit.
  • fixtures/decision-tree/mergeable_tests.pm — two sibling branches with identical test sequences; expects dominance-based merging to collapse them into one shared sub-DAG.
  • fixtures/decision-tree/pathological_fanout.pm — an adversarially wide single-level fanout; expects bounded node count, not quadratic blowup.
  • fixtures/optimizer/redundant_tests.pm — a DAG with a provably-implied redundant test; expects dead-test elimination to remove it.
  • fixtures/optimizer/branch_merge.pm — mergeable equivalent branches; expects a measurable node-count reduction matching the 15% acceptance threshold.
Pitfalls
  • Cyclic DAG generation. Manifestation: DAG validation pass fails post-construction · Root cause: dominance-merging logic incorrectly reusing a node that is an ancestor of the node being merged, introducing a back-edge · Debug method: topological-sort failure output names the exact offending node pair · Signal: dag.cycle_detected_total (I6, FM-2) · Recovery: rebuild the DAG from the normalized IR (Phase 4) without the merging pass, bisect the merging heuristic against the fixture that triggered it.
  • Semantic drift after optimization. Manifestation: an optimized DAG accepts/rejects a different input set than its pre-optimization version · Root cause: guard hoisting moved a guard past a point where its captured bindings were not yet established · Debug method: I12 differential check between pre- and post-pass DAG on the fixture corpus · Signal: optimizer.semantic_drift_total > 0 · Recovery: disable the offending pass for the affected pattern shape, add a regression fixture, require binding-availability analysis before any future guard-hoisting change.

⬜ Phase 9 — Backend Code Generation, Runtime Hardening & Replay §21

Objectives

Emit two independent executable representations (C source, bytecode) from the same optimized DAG for differential testing, then finalize production hardening: fuzzing campaigns, deterministic replay validation, artifact signing, and telemetry export. JIT specialization and GPU dispatch generation are both explicitly out of scope for these two static backends — PhaseDeferred("§21") for both, registered in §35.

Deliverable

Two runnable, differentially-verified backend artifacts (backend-c C source, backend-bytecode bytecode blob) per compilation, plus a signed release binary passing a 72-hour continuous fuzz campaign with zero replay divergence.

Acceptance
  • Generated programs from both backends pass 100% of the conformance suite with identical accept/reject decisions (0 backend divergence, FM-5).
  • Fuzz campaign stable for 72h continuous run (0 crashes, 0 sanitizer violations) on lexer_fuzz.rs, parser_fuzz.rs, matrix_fuzz.rs, replay_fuzz.rs.
  • Replay divergence exactly 0 across the full fixture corpus (§4 hard requirement, I1/I10).
  • SBOM and Sigstore signature present and verifiable for every tagged release artifact.
Fixtures
  • fixtures/backend/c_backend.snap — canonical C-emitter output for a representative DAG; catches unintended emission-format drift.
  • fixtures/backend/bytecode_backend.snap — canonical bytecode-emitter output for the same DAG; must accept/reject identically to the C-backend snapshot's semantics.
  • fixtures/replay/replay_trace.bin — a full end-to-end compilation replay trace; must reproduce the identical final DAG hash on replay.
  • fixtures/replay/corruption_case.bin — a deliberately corrupted trace; must be rejected via checksum mismatch (I10), never silently replayed.
Pitfalls
  • Backend divergence. Manifestation: the same DAG accepts an input under backend-c but rejects it under backend-bytecode · Root cause: a subtle lowering bug in one emitter's jump-target computation (e.g. an off-by-one label offset) · Debug method: differential test harness pinpoints the exact discriminating input, then bisects which backend disagrees with the pre-codegen DAG's own semantics (via the runtime/conformance harness of §3) · Signal: backend.divergence_total (FM-5) · Recovery: backend isolation — disable the offending backend's release channel until the emitter bug is fixed and the differential suite is green.
  • Hidden nondeterminism. Manifestation: replay produces a different DAG hash on a fraction of reruns · Root cause: an unbounded HashMap iteration order surviving into the final release build despite Phase 0's lint gate (a new dependency introduced its own internal hashing) · Debug method: bisect the 72h fuzz corpus for the specific input triggering divergence, diff two replay traces byte-for-byte · Signal: replay.checksum_mismatch_total under concurrent execution specifically (not single-threaded reruns) · Recovery: audit new dependencies for hidden iteration-order nondeterminism, pin or replace.
