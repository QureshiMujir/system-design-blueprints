33. Hard Questions (Self-Examination)

  • Q1. If §17 specialization caching and §18 exhaustiveness witness generation disagree on which constructor space is "covered," which one is authoritative, and why does that not create a circular dependency between §17 and §19?
  • Q2. The §4 1 GB exhaustiveness ceiling and the §32 C4 witness-node derivation both assume 96 B/witness-node — what changes in §18's witness structure would invalidate that constant?
  • Q3. §20's dominance-based node merging and §21's dual-backend differential testing both exist to catch semantic drift — could a bug that both mechanisms would independently catch still ship, and what would that require of §12's replay logging?
  • Q4. §15's guard-purity check (I5) is static; §19's redundancy analysis treats guarded rows as never-fully-redundant — is there an input where a guard is provably pure and provably always-true, and does §19 need a special case or does §15 already prevent it?
  • Q5. §16's 512-row OR-expansion ceiling and §4's 1.8x allocation-amplification ceiling are independent budgets — construct an input that respects both individually but violates their product; does §17 or §32's C2 already account for this?
  • Q6. §21's 72-hour fuzz-stability gate and §4's zero-tolerance replay-divergence budget are both release gates — if the fuzz campaign relies on §12's replay infrastructure to reproduce a crash, what breaks the gate's own soundness if §12 has a latent nondeterminism bug?
  • Q7. §9's ADR-08 confines Tokio to the IO boundary; §17's parallel specialization is "permitted" across constructor branches — what synchronization primitive reconciles these without violating §12's P1 determinism requirement?
  • Q8. §18 differentially tests against rustc and OCaml reference behavior; §5's Reference Implementations section warns against copying OCaml's exit-jump numbering — does the harness in §26 need its own translation layer, and where would that layer's bugs surface?
  • Q9. §23's FM-9 (optimizer introduces unreachable success states) is caught by a reachability audit, while §20's I12 differential check is a separate mechanism — is FM-9 a subset of I12 violations, or can FM-9 occur while §20's differential check still passes?
  • Q10. §32's C3 concurrency-memory arithmetic assumes typical-case AST sizes for 128 concurrent compilations, while §4 sets the AST ceiling per-compilation at worst case — under what traffic pattern does §4's host RAM budget actually get exhausted despite both ceilings being respected?
  • Q11. §14's parser recovery synchronizes at => and | boundaries; §16's OR-pattern flattening assumes | always denotes an OR-pattern boundary within one arm — could a §14 recovery decision produce a token stream that §16 silently misinterprets rather than rejects?
  • Q12. §22's T11 (specialization cache poisoning) and §17's cache-key digest scheme are described as mutually exclusive by construction — what property of the digest function would need to fail for T11 to manifest, and does §9's ADR-05 serialization choice bound that risk?
  • Q13. §30's MM7 claims DAG merging never changes algorithm semantics, only sharing; §20's 20.6 pitfall list describes a cyclic-DAG failure from merging — is a cycle a violation of MM7's claim, or does MM7 only apply once §7's I6 acyclicity is independently established?
  • Q14. §29's horizontal-scaling claim rests on §7's I9 arena isolation per compilation unit, while §17's specialization cache is shared within one compilation — would sharing that cache across compilation units violate I9, and which §7 invariant would catch it first?
  • Q15. §28's M1/M2 latency targets and §32's C5 throughput-headroom arithmetic both assume a 10k-pattern reference workload — what would §4 and §28 each need to change if the reference workload shifted to 100k patterns?
  • Q16. §25's N-2 IR compatibility guarantee (I7) and §21's release-gate SBOM/signing process are independent controls — could a signed release still ship an IR schema change breaking N-2 compatibility, and which §27 CI stage should catch it?
  • Q17. §19's guard-interaction pitfall requires differential execution against backend-bytecode to catch a false positive, while §21 says backend divergence is itself caught by differential testing between the two backends — if backend-bytecode has the bug, does §19's method inherit it rather than catching the §19-level false positive?
  • Q18. §35 registers "vectorized matching" as deferred, anchored to §17; §28's M1 target is a latency budget, not a throughput-per-core budget — if vectorized matching were un-deferred, would it change the interpretation of §4's throughput row or only its achieved value?

30. Mental Models & First Principles

  • MM1 — Matrices Are Proofs of Coverage. The compressed insight: a PatternMatrix is not merely a data structure, it is a proof obligation — exhaustiveness is what happens when the matrix's specialization tree terminates with no unmatched constructor left · predicts: any bug in specialization (§17) will manifest as an exhaustiveness or redundancy disagreement (I2), never as an isolated local error · bug class avoided: treating exhaustiveness as a separate feature instead of a property of the matrix itself · applies in §17 and §18.
  • MM2 — Specialization Is Divide-and-Conquer on Constructors. Compressed insight: every matrix-compilation algorithm since Augustsson (1985) is structurally the same divide step — split by constructor, recurse, combine · predicts: any "novel" pattern-matching optimization is almost certainly a variant of specialization ordering or caching, not a new primitive · bug class avoided: reinventing a bespoke decomposition instead of reusing §17's specialize/ default_matrix pair · applies in §17 and §20.
  • MM3 — Usefulness Checking Is Exhaustiveness in Reverse. Compressed insight: "is this row reachable" (redundancy, §19) and "is anything unreached" (exhaustiveness, §18) are the same usefulness computation applied to complementary matrices · predicts: any algorithmic fix to one analysis without the mirrored fix to the other reintroduces I2 divergence · bug class avoided: patching exhaustiveness bugs without re-verifying redundancy on the same fixture · applies in §18 and §19.
  • MM4 — Decision Trees Trade Redundant Tests for Predictable Branches. Compressed insight: a decision DAG (§20) deliberately re-tests information already implied by an ancestor node when doing so improves branch predictability, not always minimizing test count · predicts: "fewest tests" is not the true optimization target — "fewest mispredicted branches under realistic input distribution" is · bug class avoided: an optimizer pass that minimizes node count but regresses measured latency · applies in §20 and §28.
  • MM5 — Determinism Is a Testing Multiplier. Compressed insight: every hour spent enforcing P1 determinism buys back many hours of flaky-test triage later, because a nondeterministic system cannot be bisected · predicts: the majority of "unreproducible" bug reports trace back to one of a small, enumerable set of nondeterminism sources (wall-clock, unordered hashing, uninitialized memory) · bug class avoided: chasing a "flaky" test instead of finding its determinism leak · applies in §12 and §21.
  • MM6 — Guards Are Escape Hatches That Break Static Reasoning. Compressed insight: every guard is a point where the compiler must stop reasoning statically and defer to runtime evaluation, which is why I5 purity exists — an impure guard breaks not just correctness but the analyzability of everything downstream · predicts: any feature request to "make guards smarter" (e.g. static guard evaluation) either requires proving purity first or is out of scope · bug class avoided: an optimizer treating a guard's result as statically knowable · applies in §15 and §19.
  • MM7 — A DAG Is a Tree With Sharing, Not a New Algorithm. Compressed insight: dominance- based merging (§20) does not change what the decision structure computes, only how much of it is physically duplicated in memory · predicts: any merging bug is necessarily an I12 semantic-preservation bug, never a "the algorithm changed" bug, because the algorithm by definition does not change · bug class avoided: debugging a merge failure as if it were a specialization-algorithm defect · applies in §20.
  • MM8 — Backend Divergence Is Always a Semantics Bug, Never a Codegen-Style Bug. Compressed insight: because both backends consume the identical optimized DAG, any accept/reject disagreement between them is necessarily a lowering bug in one emitter's control-flow encoding, not a difference in "what the DAG means" · predicts: backend-divergence triage should start at the label/jump-target computation, not at the DAG or the optimizer · bug class avoided: re-auditing the optimizer (§20) when the bug is actually in emit.rs or opcodes.rs (§21) · applies in §21.

5. Required Reading

Books

  • Compilers: Principles, Techniques, and Tools — Aho, Lam, Sethi & Ullman (2006), ch. 2, 6: frontend architecture and code-generation frameworks; applied in §13 and §14.
  • Modern Compiler Implementation in ML — Andrew W. Appel (1998), pattern-matching compilation sections: matrix-based compilation strategy; applied in §16 and §17.
  • Engineering a Compiler — Keith Cooper & Linda Torczon (2011), ch. 8–9 (IR, optimization): optimization-pipeline structuring; applied in §20.
  • Types and Programming Languages — Benjamin C. Pierce (2002), ch. 11 (ADTs, variants): algebraic type/constructor semantic modeling; applied in §11 and §15.
  • Advanced Compiler Design and Implementation — Steven Muchnick (1997), ch. 17 (code generation): backend emission strategy for two independent targets; applied in §21.
  • Crafting Interpreters — Robert Nystrom (2021), ch. 15, 24 (bytecode VM, dispatch loop): bytecode backend dispatch-loop design; applied in §21.
  • Programming Language Pragmatics — Michael L. Scott (2015), ch. 7 (semantic analysis): binding-time and semantic-tradeoff framing for guard evaluation; applied in §15.
  • The Garbage Collection Handbook — Jones, Hosking & Moss (2011), ch. 7 (region-based allocation): arena-allocation strategy for AST/IR nodes; applied in §12 and §13.

Papers

  • "Compiling Pattern Matching" — Lennart Augustsson, FPCA 1985: earliest systematic constructor-decomposition compilation strategy for ML-style patterns; applied in §17.
  • "Compiling Pattern Matching to Good Decision Trees" — Luc Maranget, ML Workshop (ICFP) 2008: canonical heuristic-driven decision-tree construction from pattern matrices; applied in §17 and §20.
  • "Warnings for Pattern Matching" — Luc Maranget, Journal of Functional Programming 17(3), 2007: usefulness-based exhaustiveness/redundancy algorithm sharing one witness construction; applied in §18 and §19.
  • "Optimizing Pattern Matching" — Fabrice Le Fessant & Luc Maranget, ICFP 2001: branch merging and constructor factoring in generated decision trees; applied in §20.
  • "ML Pattern Match Compilation and Partial Evaluation" — Peter Sestoft, in Partial Evaluation, LNCS 1110, 1996: specialization as a partial-evaluation instance; applied in §17.
  • "Efficient Compilation of Pattern Matching" — Philip Wadler, ch. 5 in Simon Peyton Jones's The Implementation of Functional Programming Languages, 1987: constructor-tree compilation with sharing; applied in §20.
  • "A Pattern Matching Compiler for Multiple Target Languages" — Pierre-Étienne Moreau, Christophe Ringeissen & Marian Vittek, CC 2003: automata-inspired, target-independent matching-compiler architecture; applied in §21.
  • "GADTs Meet Their Match" — Dimitrios Vytiniotis, Simon Peyton Jones, Tom Schrijvers & Martin Sulzmann, Haskell Symposium 2011: exhaustiveness/coverage under refinement typing; applied in §18.

Reference Implementations

  • rust-lang/rust — study compiler/rustc_mir_build/src/thir/pattern/usefulness.rs: usefulness-algorithm structure and witness generation; pitfall: do not copy its full type-checker coupling; applied in §18.
  • ocaml/ocaml — study typing/matching.ml: matrix specialization and exit-jump backend lowering; pitfall: do not copy its exit-point-numbering scheme verbatim, it assumes one target, this system has two; applied in §17 and §21.
  • ghc/ghc — study the pattern-match desugarer's guard-tree construction (GHC.HsToCore.Match): guard-tree flattening for nested guards; pitfall: GHC's laziness-aware order does not apply to this system's strict semantics; applied in §16.
  • scala/scala3 — study the pattern matcher's exhaustivity checker under sealed-trait closure: space-based exhaustiveness reasoning as an alternative to Maranget-style usefulness; applied in §18.
  • erlang/otp — study lib/compiler/src/v3_core.erl and BEAM pattern-matching lowering: guard-clause compilation into BEAM select instructions; pitfall: BEAM guards are a restricted subset, this system's guard purity invariant (I5) is stricter; applied in §15 and §20.
  • rust-fuzz/cargo-fuzz — study the fuzz/fuzz_targets/*.rs libFuzzer-harness directory convention: fuzz-target structuring and corpus-directory layout; pitfall: do not couple fuzz targets to internal crate versions, since the harness crate is a separate compilation unit from the library under test; applied in §21.

RFCs / Specifications

  • Rust RFC 2005 (Match Ergonomics) — pins down default binding-mode inference for nested reference patterns; applied in §14 and §15.
  • WebAssembly Core Specification, Control Instructions (br_table) — pins down jump-table dispatch semantics for the bytecode backend's jump-threading pass; applied in §20 and §21.
  • DWARF Debugging Information Format, Version 5, Line Number Program chapter — pins down span-to-debug-info encoding for mapping decision-DAG nodes back to source spans; applied in §21.
  • IETF RFC 8259 (The JavaScript Object Notation Data Interchange Format) — pins down the canonical JSON grammar used for the human-readable replay fixture envelope; applied in §12.

Glossary (§36) · 36 terms · site-wide glossary

Pattern Matrix
tabular row/column representation of a set of patterns used for specialization (§8.3, §17).
Constructor Space
the full reachable set of variants for a matched ADT type.
Usefulness
whether a matrix row can match some input not matched by any earlier row.
Exhaustiveness
whether every value of the scrutinee's type is covered by some row.
Redundancy
a row that is not useful given the rows above it; an unreachable branch.
Decision DAG
the acyclic branching graph produced by lowering an analyzed matrix (§20).
Specialization
constructor-focused matrix reduction producing a sub-matrix (§17).
Default Matrix
the fallback matrix of wildcard-only rows after specialization.
Guard
a conditional predicate attached to a pattern, evaluated at runtime (I5).
Wildcard
a match-any placeholder pattern.
Binding
a variable-capture pattern.
Replay Trace
a deterministic, checksum-covered event sequence (I10).
Arena Allocation
region-based memory strategy used for AST/IR node ownership (P4).
Span
source-location metadata attached to a token or diagnostic.
Canonicalization
the stable normalization process performed in Phase 4 (§16).
Snapshot Test
a stable serialized-output assertion (insta, ADR-12).
Differential Testing
comparing this system's output against a reference implementation.
IR
intermediate representation; here specifically pattern-ir's canonical form.
Branch Factoring
an optimizer pass merging equivalent test nodes (§20).
Constructor Arity
the number of fields a constructor variant carries.
Trampoline
a bounded, iterative substitute for native recursion enforcing I13.
Witness
a concrete example value demonstrating a missing or redundant match case.
OR-Pattern
a pattern expressing multiple alternative sub-patterns joined by |.
Dominance
a graph-theoretic relation used to identify mergeable DAG sub-structures.
Jump Threading
an optimizer pass eliminating indirection in generated control flow.
Guard Hoisting
moving a guard evaluation earlier without changing match outcome.
Dead-Test Elimination
removing a test whose result is already implied by an ancestor.
Backend Divergence
two codegen backends disagreeing on accept/reject for the same input.
Chaos Replay
deterministic replay combined with deliberate corruption injection.
SBOM
Software Bill of Materials; a CycloneDX manifest listing release dependencies.
Crash-Only Recovery
recovering solely via restart-and-replay, never partial in-place repair (P10).
Allocation Amplification
the ratio of in-memory representation size to raw input size.
N-2 Compatibility
the guarantee that a binary two minor versions newer can still decode older persisted data (I7).
Trivia
whitespace and comment tokens preserved separately from the significant token stream.
Constructor Splitting
decomposing a slice/range pattern into fixed- and variable-length sub-cases during specialization.
Row-Major Matrix
the specific in-memory layout chosen for cache-friendly column scans (§17.7).
