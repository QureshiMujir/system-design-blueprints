In one paragraph

A pattern matching compiler takes the match-style shapes a programmer writes (nested variants, tuples, slices, ranges, alternatives, guards) and lowers them into a branching graph with few tests (§1). On the way it proves that no input is left unhandled and no arm is dead (§1, §2), then emits the graph as C source and as bytecode (§3.2). It is a family of Rust crates plus a CLI and a CI conformance runner: a compiler backend component, not a language frontend, run by compiler, runtime, language-research and tooling engineers (§1). Its first principle is that every stage replays bit for bit from the same input and seed (P1, P7).

The problem, concretely

The obvious way to run a match is to try pattern 1, and if that fails try pattern 2, and so on (§34 Alt A). That backtracking interpreter shares no decomposition across alternatives, so its cost is exponential in the worst case, and it produces no graph that anything could check (§34 Alt A). It wins only for prototype DSLs with fewer than about 50 patterns, where simplicity and compile-time cost matter more than dispatch cost (§34 Alt A).

Speed is not the only problem:

  1. Silent holes. If a variant is not handled, the generated dispatch code falls through at runtime without warning (P2). The compiler must prove coverage before it emits code (P2, §2).
  2. Dead arms. An arm that can never run is dead code. The redundancy pass must find it and report it as a warning, without ever flagging a reachable arm (§1, §19.4, §19.9).
  3. Bugs nobody can reproduce. If a compiler stage reads the wall clock or iterates an unordered hash map, a reported bug cannot be reproduced by anyone but the reporter (P1, P7, MM5).
  4. Hostile input. A 64 MB source with pathological nesting, a crafted nested OR-pattern or a very deep constructor chain can cause unbounded work, exponential row expansion or stack exhaustion (T1, T6, T7).

The design answers each: decompose by constructor and reuse one decomposition everywhere (MM2, §17.3); treat coverage as a property of the table itself (MM1); make every stage replayable (P1, P7); and bound every stage's memory with explicit ceilings (P5, §4).

How it works, end to end

Follow the §8.3 match through the boxes of §3.1's diagram, here shortened to one column:

 source text (untrusted, <= 64 MB)   CLI / API
   -> Lexer          tokens          (§13)
   -> Parser         arena AST       (§14)
   -> Type Resolver  constructor IDs (§15)
   -> Normalizer     PatternMatrix   (§16, pattern-ir)
   -> Matrix Builder / Specializer   (§17)
        |-> Exhaustiveness (§18)  -> missing-pattern set
        |-> Redundancy     (§19)  -> dead-row set
   -> Decision Tree / DAG Compiler   (§20)   acyclic (I6)
   -> Optimization Pass Pipeline     (§20)
        |-> backend-c    |-> backend-bytecode   (§21, compared differentially)
   -> Runtime / Conformance / Replay Harness (§21, §26)
  1. cli loads config, starts telemetry, activates the replay seed and writes artifacts; it owns no network surface in the primary deployment (§3.2).
  2. lexer turns UTF-8 text into span-tracked tokens. Whitespace and comments are kept in a separate side table so the token stream stays dense (§3.2, §13.2).
  3. parser is recursive descent and builds an immutable arena-owned AST (ast). When a pattern is malformed, it resynchronizes at the next => or | so the other arms still parse (§3.2, §8.5).
  4. types gives every constructor a stable ID and checks arity. After this stage patterns are identified by constructor ID, not by source text (§3.2, §15, I3).
  5. pattern-ir flattens alternatives, makes implicit captures explicit and normalizes ranges. It is the last stage that touches surface syntax (§3.2, §16).
  6. matrix-compiler builds the table for the §8.3 match and splits it by constructor (§3.2, §17). Both analyzers consume the same snapshot of it (§3.2).
  7. exhaustiveness and redundancy read that snapshot. They must agree on the reachable constructor space; the blueprint calls a divergence a P1-class defect (I2, §3.2). Code generation does not proceed past a missing case (P2, §18.3).
  8. decision-tree lowers the analyzed matrix into an acyclic graph; optimizer rewrites it without changing its accept/reject set (§3.2, §20, I6, I12).
  9. backend-c and backend-bytecode emit from the same optimized graph, and the pair is the system's strongest defense against semantic drift (§3.2, §21).
  10. diagnostics, replay and telemetry run beside every stage. Diagnostics render in a deterministic order, replay records an event log, and telemetry emits spans and metrics (§1, P3, P6, P7).

The core ideas

The pattern matrix and specialization (§8.3, §17.2, MM2)

Write the arms as a table: one row per arm, one column per position being tested. That table is the pattern matrix. The blueprint's example (§8.3):

Row Constructor Field0 Guard Arm
0 Some 0 — A
1 Some x (binding) — B
2 None — — C

Specialization picks one constructor, keeps only the rows compatible with it and replaces its fields with new columns (§17.2). Specializing on Some gives { Field0: 0 -> A, Field0: x -> B } (§8.3). The default matrix is the fallback path (§17.2), and the blueprint's example gives it as { None -> C } (§8.3). MM2 says every matrix-compilation algorithm since Augustsson (1985) is structurally this same divide step: split by constructor, recurse, combine (MM2).

A toy version needs three rules: (1) pick a column and split by constructor; (2) recurse on each sub-matrix; (3) stop when no rows are left, which is a Failure result and not a crash (§17.5, §17.8), or when every row is a wildcard, which is an immediate match (§17.8). Real versions add three things. Slice and range patterns are split into fixed-length and variable-length cases (§17.2). Results are cached under (matrix_digest, constructor_id) (§17.2). Recursion runs through a bounded trampoline instead of native recursion (§17.2, I13). Row order decides which arm wins an ambiguous input, so it must not change (I1, §17.9).

The blueprint is not consistent on the default matrix. §17.2 defines it as the rows whose tested column is a wildcard, the glossary as the wildcard-only rows (§17.2, §36). §8.3 says it has constructor None excluded, yet gives it as { None -> C }, a row whose tested column is a constructor (§8.3). The blueprint does not reconcile the two.

Exhaustiveness and redundancy are one computation (§18.2, §19.2, MM1, MM3)

A row is useful if some input it matches is not matched by any earlier row (§18.2). Exhaustiveness asks whether anything in the whole constructor space is left uncovered, and returns either Exhaustive or Missing with a list of witnesses (§18.3). A witness is a concrete example value that shows the gap (§36). Redundancy asks the mirror question per row: a row is redundant if it is not useful against the rows above it (§19.2, MM3). Both reuse Phase 5's specialize and default_matrix calls rather than re-implementing decomposition (§17.3, §18.2).

The blueprint's own fixtures show both directions. non_exhaustive.pm is a match missing one variant and expects a witness naming that exact variant (§18.5). dead_branch.pm has a row fully shadowed by an earlier wildcard and expects that row flagged dead; shadowed_or.pm shadows one alternative of an OR-pattern and expects only that alternative flagged, not the whole OR-pattern (§19.5). Because the two analyses are the same usefulness computation applied to complementary matrices, a fix to one without the mirrored fix to the other reintroduces I2 divergence (MM3, I2).

Guards are escape hatches that break static reasoning (MM6). A guard is evaluated at runtime (§36), so the redundancy pass never marks a guarded row as fully redundant (§19.2), and guards must be pure so re-evaluating one during specialization is safe (I5, MM6).

Normalization and the OR-pattern cap (§16)

Before splitting, surface syntax is canonicalized. An OR-pattern becomes several rows that share one arm. A bare identifier becomes an explicit Binding, a range becomes a closed (lo, hi) interval, and elided fields get wildcards (§16.2). Normalizing already-normalized input must change nothing, checked by comparing digests (§16.2, §16.4).

Alternatives multiply: the fixture or_expansion.pm, a 4-way nested OR-pattern, expects exactly 16 expanded rows, 2 to the power 4 (§16.5). Naive expansion without a ceiling is exponential, so no single arm may expand past 512 rows; beyond that the compiler emits E-OR-EXPANSION-LIMIT instead of allocating (§16.6, §16.4, T6, P5). A guard on an OR-pattern is copied onto every expanded row, not just the first (§16.5).

The decision DAG and its optimizer (§20, MM4, MM7)

The analyzed matrix is lowered to a decision DAG (a branching graph where equal sub-branches are shared) whose nodes are Test, Guard, Bind, Success and Failure (§11, §20.2). Section §8.4 names the same states TestConstructor, TestLiteral, BindValue, EvaluateGuard, Fail and Match, and the blueprint does not map one list to the other (§8.4, §11). A DAG is a tree with sharing, not a new algorithm: merging changes how much is stored, never what is computed (MM7). Acyclicity is checked with a topological sort before the DAG is final (I6, §20.2).

The optimizer applies dead-test elimination, branch and constructor factoring, guard hoisting, constant folding and jump threading (§20.2). Each pass is checked against the pre-pass DAG, and a pass that changes the accept/reject set is a correctness bug (I12, §20.2). Passes build a new DAG rather than editing in place (§11). The fixture mergeable_tests.pm has two sibling branches with identical test sequences, and expects them to collapse into one shared sub-DAG (§20.5).

MM4 adds that "fewest tests" is not the true target; fewest mispredicted branches under a realistic input distribution is, so a DAG may deliberately re-test something an ancestor already implies (MM4). The phase gate is at least 15% fewer test nodes than the pre-optimization DAG on the redundant_tests.pm and branch_merge.pm fixtures (§20.4).

Determinism and replay (P1, P7, P10, I10, ADR-20)

Every stage must produce the same output from the same input and seed, so wall-clock reads and unordered-map iteration are forbidden inside stages (P1). Time comes from an injectable logical clock (ADR-20, §12.2). Each compilation appends events (timestamp, stage, payload_hash) to an append-only log covered end to end by a rolling checksum (§11, I10). Recovery is restart-and-replay of the whole compilation, never in-place repair (P10).

A Phase 0 fixture is a deliberately bit-flipped log that must be rejected with a checksum mismatch (§12.5). Determinism is a testing multiplier, because a nondeterministic system cannot be bisected (MM5).

Two backends, one graph (§3.2, §21, MM8)

Two independent emitters, backend-c and backend-bytecode, consume the same optimized DAG, and their accept/reject decisions must match on the whole conformance corpus (§21.2, §21.4). Because the input is identical, any disagreement is a lowering bug in one emitter's control flow, so triage starts at label and jump-target computation and not at the optimizer (MM8, FM-5). Exhaustiveness is checked differently: against rustc and OCaml reference behavior on a 150-case corpus (§18.4).

The trade-offs — where engineers disagree

Core runtime: one thread per compilation (ADR-07)

Chosen: a synchronous single-threaded core per compilation unit, because stages are CPU-bound and benefit from cache locality, not IO concurrency (ADR-07). Rejected: a pervasive async core. When the rejected choice is right: an IO-heavy incremental build server juggling thousands of small concurrent file reads (ADR-07). The blueprint contradicts itself: §3.2, §11 and §29 permit parallel specialization across constructor branches and cite ADR-08 for it, but ADR-08 only confines Tokio to the IO boundary, and ADR-07 locks a single-threaded core (§3.2, §11, §29, ADR-08). Q7 asks what reconciles them; the blueprint does not answer (§33).

Time source: a logical clock (ADR-20)

Chosen: an injectable logical clock in every stage, required for bit-for-bit replay (ADR-20, P1, I1). Rejected: direct SystemTime::now() calls. When the rejected choice is right: a stage that genuinely needs wall-clock time, such as release-artifact timestamping outside the replay boundary (ADR-20).

Serialization: postcard (ADR-05)

Chosen: postcard, for binary determinism, compact size and no float-formatting ambiguity (ADR-05). Rejected: JSON and bincode. When the rejected choice is right: a human-in-the-loop debugging workflow where JSON's readability outweighs its size; the design already uses JSON for the replay fixture envelope (ADR-05).

Language: Rust (ADR-01)

Chosen: Rust, for deterministic ownership, algebraic enums and mature fuzzing and profiling (ADR-01). Rejected: C++, Go, Java, OCaml and Zig (ADR-01). When the rejected choice is right: a team with a large existing OCaml compiler codebase and no Rust expertise, where OCaml's native pattern-match support outweighs tooling gaps (ADR-01).

Backpressure: bounded channels (ADR-21)

Chosen: bounded mpsc channels with credit-based scheduling, to prevent fuzz-induced or burst OOM (ADR-21, P8, T5). Rejected: unbounded channels. When the rejected choice is right: a strictly single-threaded batch tool with no producer or consumer channel at all (ADR-21).

Roads not taken (§34, §35)

Backtracking interpreter (§34 Alt A): try each pattern in turn. It wins for prototype DSLs with fewer than about 50 patterns, as in early Scheme syntax-rules-style interpreters. Rejected: the cost is exponential in the worst case and no graph exists for I6 to validate.

Regex-style automaton (§34 Alt B): a state machine over character classes. It wins for string and byte matching (regex-automata). Rejected: constructor matching needs typed field decomposition, and an automaton would discard the type information §15 depends on.

SAT/SMT-backed exhaustiveness (§34 Alt C): encode the matrix as a boolean formula for a solver. It wins for refinement-typed or dependently-typed languages where guard reasoning dominates. It is rejected for this scope because solver latency variance conflicts with the 250 ms p95 target (§34 Alt C). Alt C says it is tracked as the deferred GADT-aware refinement-typing feature, while §35 lists symbolic SAT-backed exhaustiveness as a separate row, un-deferred when witness generation proves insufficient for guard-heavy patterns at production scale (§34 Alt C, §35).

Interpreted decision table (§34 Alt D): execute table rows with a generic loop, never compiled. It wins for low-throughput rule engines where portability and hot reload matter more than speed. It is rejected because interpretive dispatch cannot meet the 50,000 nodes/sec target (§34 Alt D). That alternative cites the target as "§4 M3" (so do §20.4 and §35), but the M3 label is defined only in the §28 table; §4 has the same figure without a label (§4, §28).

Deferred features (§35): distributed compilation waits until the single-host limit of 128 concurrent compilations is regularly saturated; incremental invalidation until full-recompilation p99 latency dominates CI; JIT and GPU dispatch for a hot-loop or columnar-query-engine consumer; vectorized matching until SIMD-width tests dominate specialization latency in profiling (§35, §4).

What must never be false

  • I1: matrix row order is stable through specialization. Noticed by row-order digest assertions (matrix.row_order_digest, §7).
  • I2: exhaustiveness and redundancy agree on the reachable constructor space. Noticed by a reachable-set diff (exhaustiveness.divergence_total, §7).
  • I3: constructor IDs are deterministic. Noticed by an ID-assignment order digest (§7).
  • I4: source spans never regress. Noticed by a per-token monotonicity assertion (§7).
  • I5: guards cannot mutate compiler state. Noticed by static guard-effect analysis (§7).
  • I6: decision DAGs contain no cycles. Noticed by a topological-sort pass (dag.cycle_detected_total, §7).
  • I7: persisted IR stays readable for N-2 versions. Noticed by a version-envelope decode test matrix (§7).
  • I8: diagnostic order and format are deterministic. Noticed by a snapshot digest comparison (§7).
  • I9: every arena has one owning stage; cross-stage access is by index only. Noticed by an arena generation-tag assertion (§7).
  • I10: every replay log is checksum-covered end to end. Noticed by rolling checksum verification (replay.checksum_mismatch_total, §7).
  • I11: token streams round-trip losslessly, trivia included. Noticed by a re-emission diff (§7).
  • I12: optimization passes preserve the accept/reject set. Noticed by differential execution against the pre-pass DAG (optimizer.semantic_drift_total, §7).
  • I13: deep constructor recursion is trampolined, never native. Noticed by a recursion-depth gauge against the 4096 soft limit (matrix.recursion_depth, §7).

Every invariant maps to exactly one assertion in a deterministic simulator, conformance/runner.rs, and a new invariant needs a fixture designed to nearly violate it (§7).

What breaks in production

  • FM-1: matrix explosion. Memory spikes out of proportion to pattern count, up to OOM. Cause: the specialization cache is disabled, or a key collision forces repeated materialization (§23, §17.6). Detected by allocation telemetry against the 1.8x ceiling. Recovery: throttle specialization and fall back to default-matrix-only decomposition; tune cache eviction by hand (§23).
  • FM-2: a cycle in the DAG. Cause: dominance merging reused an ancestor node (§23, §20.6). Detected by the topological-sort pass (I6). Recovery: rebuild the DAG from the normalized IR without the merging pass; bisect the merge heuristic against the triggering fixture (§23).
  • FM-3: replay divergence. Cause: hidden nondeterminism such as unordered iteration or a wall-clock leak that survived into a release (§23, §21.6). Detected by a checksum mismatch on replay. Recovery: quarantine and reject the divergent trace; audit new dependencies for ordering nondeterminism (§23).
  • FM-5: backend mismatch. One emitter has a label or jump-offset bug (§23, §21.6). Detected by differential testing between the two backends (backend.divergence_total). Recovery: disable the release channel of the offending backend, then bisect the emitter change (§23).
  • FM-6: exhaustiveness false negative. A regression in the usefulness algorithm or witness builder (§23, §18.9). Detected by differential replay against rustc and OCaml. There is no automatic recovery by design, because the class blocks Phase 8 (P2); the manual fix is rolling back to the last differentially verified revision (§23).
  • FM-8: symbol-table contention or deadlock. A mutable symbol table is accessed concurrently during Phase 5 parallel specialization, seen as a latency spike or hang on types.resolution_latency_ms. The fix is structural: freeze the table as an immutable snapshot before normalization (P4, §23).
  • FM-9: the optimizer makes a success state unreachable. Guard hoisting or merging violates I12 (§23, §20.9). Detected by a reachability audit of Success node incoming paths before and after the pass. Recovery: reject the offending pass for that compilation; disable it via config until fixed (§23). Q9 asks whether FM-9 can occur while the I12 differential check still passes, and the blueprint leaves that open (§33).

Threats worth knowing (§22):

  • T1: an adversarial 64 MB source with pathological nesting; answered by bounded trampoline recursion and the recursion-depth gauge (I13).
  • T6: an OR-pattern crafted for exponential row expansion; answered by the 512-row cap (§16.4).
  • T10: compile latency leaking the shape of secret patterns in a multi-tenant CI service; answered by constant effort per compilation-unit size class, not per pattern shape.
  • T11: specialization-cache poisoning through a digest collision; a collision is treated as a correctness bug, not tolerated, and the cache is disabled for the affected key range (§17.8).

How it compares

  • rustc (thir::pattern) uses Maranget usefulness matrices and witness synthesis, and has one target and no cross-backend differential test. It decoupled its usefulness checker from the full type checker so exhaustiveness could be tested apart from borrow-checking; this design adopts that decoupling at the types crate boundary and differs by having two backends (§31, §15).
  • OCaml (matching.ml) threads numbered exit jumps through specialization instead of building a separate DAG. That suits a single native or bytecode target; this design needs an IR independent of either backend so that two backends can be compared (§31).
  • GHC interleaves guards with pattern tests in guard trees and covers closed types by space. That helps in a lazy language where guard order has observable effects; this design's strict, pure guards (I5) make interleaving unneeded complexity (§31).
  • Erlang/OTP (BEAM) performs no static exhaustiveness check and fails at runtime with function_clause. That fits a dynamically typed system with hot code reload, where new clauses can appear after the check; static exhaustiveness (P2) is incompatible with that model by design (§31).

Questions to test yourself

  1. If §17 specialization caching and §18 exhaustiveness witness generation disagree on which constructor space is "covered," which one is authoritative, and why does that not create a circular dependency between §17 and §19? — Hint: §3.2 and §18.2 on a shared matrix; MM1, MM3.
  2. §15's guard-purity check (I5) is static; §19's redundancy analysis treats guarded rows as never-fully-redundant — is there an input where a guard is provably pure and provably always-true, and does §19 need a special case or does §15 already prevent it? — Hint: §19.2 and MM6.
  3. §9's ADR-08 confines Tokio to the IO boundary; §17's parallel specialization is "permitted" across constructor branches — what synchronization primitive reconciles these without violating §12's P1 determinism requirement? — Hint: ADR-07, §3.2 and §29; FM-8 shows what goes wrong.
  4. §23's FM-9 (optimizer introduces unreachable success states) is caught by a reachability audit, while §20's I12 differential check is a separate mechanism — is FM-9 a subset of I12 violations, or can FM-9 occur while §20's differential check still passes? — Hint: §20.2 and the FM-9 row of §23.
  5. §30's MM7 claims DAG merging never changes algorithm semantics, only sharing; §20's 20.6 pitfall list describes a cyclic-DAG failure from merging — is a cycle a violation of MM7's claim, or does MM7 only apply once §7's I6 acyclicity is independently established? — Hint: I6 and FM-2.

If you only remember three things

A pattern matrix is a proof obligation, so exhaustiveness and redundancy are the same computation asked from two sides, and any fix to one needs the mirrored fix to the other (MM1, MM3, I2). The decision DAG is a tree with sharing, no optimizer pass may change its accept/reject set, and two backends emit from the same graph so that any disagreement points at a lowering bug in one emitter (MM7, I12, MM8). Every stage is replayable bit for bit, because a nondeterministic system cannot be bisected and a bug without a replay trace cannot be reproduced by anyone but its reporter (P1, P7, MM5).

Words used here

  • Pattern matrix: a table with one row per arm and one column per tested position (§8.3, §36).
  • Specialization: reducing the matrix to the rows compatible with one chosen constructor (§36).
  • Default matrix: the fallback matrix of wildcard-only rows after specialization (§36, §17.2).
  • Usefulness: whether a row can match some input that no earlier row matches (§36).
  • Exhaustiveness: whether every value of the matched type is covered by some row (§36).
  • Redundancy: a row that is not useful given the rows above it, so it can never run (§36).
  • Witness: a concrete example value showing a missing or redundant case (§36).
  • Guard: a condition attached to a pattern and evaluated at runtime; must be pure (§36, I5).
  • OR-pattern: several alternative patterns joined by | in one arm (§36).
  • Decision DAG: the acyclic branching graph produced by lowering an analyzed matrix (§36).
  • Trampoline: an iterative, depth-bounded replacement for native recursion (§36, I13).
  • Replay trace: a deterministic, checksum-covered record of one compilation's events (§36).
  • Differential testing: comparing this system's output against a reference implementation, or one backend against the other (§36, §26).
  • Arena: region-based memory where each node has one owner and is referenced by index (§36, P4).
