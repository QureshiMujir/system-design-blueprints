Project Number: 240

Project Name: Pattern Matching Compiler from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition. A pattern matching compiler is a batch/embeddable transformation pipeline that lowers declarative structural patterns (algebraic data type destructuring, tuples, slices, ranges, OR-patterns, guards) into a decision DAG with provable exhaustiveness and redundancy properties, then emits that DAG as executable dispatch code. It is a compiler backend component, not a language frontend: it consumes typed pattern ASTs and produces branch-minimal, cache-friendly dispatch artifacts, the same class of subsystem found inside rustc's thir::pattern usefulness checker, OCaml's matching.ml, and GHC's guard-tree desugarer.

Phase-0 deliverable — crates/services shipped:

  1. lexer — UTF-8 tokenizer with span tracking and trivia preservation.
  2. parser — recursive-descent parser with deterministic error recovery.
  3. ast — arena-owned immutable AST with stable node hashing.
  4. types — constructor/symbol resolution and semantic binding.
  5. pattern-ir — canonicalized, normalized pattern intermediate representation.
  6. matrix-compiler — specialization and default-matrix decomposition engine.
  7. exhaustiveness — usefulness-algorithm coverage checker.
  8. redundancy — dead-branch and shadowed-pattern detector.
  9. decision-tree — decision DAG construction and dominance analysis.
  10. optimizer — branch factoring, guard hoisting, dead-test elimination passes.
  11. backend-c / backend-bytecode — two independent codegen backends for differential testing.
  12. diagnostics — structured, span-carrying diagnostic rendering.
  13. replay — deterministic event log and checksum-verified replay.
  14. telemetry — tracing spans, metrics, structured log wrappers.
  15. cli — deterministic CLI/API entry point (config, replay activation, artifact emission).

System boundaries — provides: parsing, ADT-aware pattern normalization, matrix-based decomposition, exhaustiveness/redundancy analysis, decision-DAG optimization, two reference backends, conformance/fuzz/replay infrastructure. Delegates: the enclosing language's own type inference, borrow/lifetime checking, and full expression evaluation semantics remain the host compiler's responsibility — this system only owns pattern semantics. Does NOT provide: a general-purpose source-language frontend, a garbage collector, an SSA optimizer, a register allocator, a machine-code JIT, a distributed runtime, an IDE, or a debugger UI.

Non-goals: full language implementation; general expression optimization; native JIT compilation; multi-node distributed compilation (Phase 0–9 scope); GPU dispatch generation.

Deployment model: primary — embeddable static library, CLI compiler utility, CI conformance runner, benchmark binary, reusable Rust crate family. Secondary — language-server integration (LSP diagnostics passthrough), compiler-plugin embedding, rule-engine embedding.

Target operators: compiler engineers (deterministic lowering of pattern constructs), runtime engineers (predictable branching for dispatch-heavy interpreters), language researchers (decision-tree construction experimentation), tooling engineers (stable, replayable diagnostics for editor integrations).

What later phases unlock: Phase 4 (§16) normalization unlocks matrix decomposition; Phase 6 (§18) exhaustiveness unlocks compiler-grade missing-pattern diagnostics; Phase 8 (§20) decision-DAG optimization unlocks branch-count reductions measurable against Phase 5 (§17) baselines; Phase 9 (§21) backend generation unlocks differential testing across two independent code paths and production hardening (fuzzing, replay, signing).

Recommended language: Rust. Rationale: deterministic ownership semantics eliminate a whole class of aliasing bugs in arena-owned AST/IR graphs (ADR-01); algebraic enum types model PatternNode/DecisionNode variant spaces directly, matching the domain; mature profiling (perf, cargo-flamegraph) and fuzzing (cargo-fuzz) ecosystems suit a correctness-critical compiler component; predictable, GC-free ABI boundaries suit embeddability inside foreign-language runtimes. Rejected alternatives: C++ (higher undefined-behavior risk in arena/lifetime-heavy code — ADR-01), Go (weak algebraic modeling, no sum types, complicating PatternNode/DecisionNode representation), Java (GC pauses incompatible with the 250 ms p95 §4 latency budget and a mandatory runtime dependency for an embeddable library), OCaml (smaller operational tooling ecosystem for fuzzing/observability relative to Rust, despite excellent native pattern-match precedent), Zig (immature compiler-infrastructure ecosystem — no mature fuzzing/property-testing/tracing stack as of this writing).

Prerequisites: automata theory, compiler construction, parsing theory, graph algorithms, memory management and arena allocation, cache locality and branch prediction, concurrency, formal language theory, property-based testing, fuzzing, deterministic replay, profiling, IR design, serialization/versioning formats.

Estimated timeline: Phase 0 (§12) — 6–14 weeks (repository, deterministic infra, correctness kernel). Full production system (§12–§21 complete, hardened) — 8–14 months. Research extensions beyond scope (GADT-aware refinement typing, SAT-backed exhaustiveness, vectorized/GPU matching) — an additional 12–24 months, tracked in §35.

2. Why Build This

Pattern matching compilation is one of the highest-leverage subsystems in compiler engineering: it converts expressive declarative semantics (nested ADT destructuring, guards, OR-patterns) into efficient, predictable control flow, and it is one of the few compiler subsystems where correctness (exhaustiveness, no false redundancy) is formally checkable against the input's own type structure rather than against an external spec.

Historically, this subsystem shaped ML-family language design (SML, OCaml, Haskell), informed optimizing-compiler IR design (decision trees as a canonical dispatch IR), and underlies symbolic execution and theorem-proving front ends that need exhaustive case-space reasoning. It is architecturally adjacent to decision-DAG engines, bytecode VM dispatch loops, type checkers, SAT solvers, parser generators, rule engines, and relational query optimizers — all of which decompose a structured input space into disjoint, provably-covering cases.

Building it exercises: compiler frontend architecture (§13–§15), IR pipeline design (§16–§17), recursive matrix decomposition (§17), static analysis infrastructure (§18–§19), diagnostics engineering (§14, §18), optimization pass construction (§20), differential/benchmark methodology (§21, §26, §28), and replayable debugging (§21, §23).

What Mastery Looks Like

  • Can derive Maranget's matrix specialization algorithm from first principles and explain why row order must stay stable (I1) under Phase 5 (§17) specialization.
  • Can implement a usefulness-based exhaustiveness checker and prove it agrees with redundancy analysis on the same constructor space, per Phase 6 (§18) and Phase 7 (§19).
  • Can design a decision-DAG IR with dominance-based node merging and reason about its acyclicity invariant (I6) under Phase 8 (§20).
  • Can build two independent backends (§21) and use differential testing to catch semantic drift that neither backend's own test suite would catch alone.
  • Can instrument a multi-stage compiler pipeline with deterministic replay (§21, §23) such that every reported bug ships with a byte-identical reproduction trace.
  • Can quantify a compiler's resource budget (§4, §32) and defend every number with derivation rather than intuition.
  • Can distinguish a genuine algorithmic pitfall (matrix explosion, OR-pattern blowup) from an implementation bug using recursion-depth and allocation telemetry (§28, §29).

3.2 Subsystem Descriptions

CLI / API (§12). Deterministic entry point: configuration loading, telemetry init, replay-seed activation, benchmark integration, artifact emission. Trust boundary: accepts untrusted source paths and CLI flags; owns no network surface in the primary deployment.

Lexer (§13). Transforms UTF-8 source into a stable, span-tracked token stream. Concurrency boundary: single-threaded per compilation unit; arena-allocated tokens are immutable after lexing and shared with the parser by index, never by pointer.

Parser (§14). Recursive-descent parser producing an arena-owned immutable AST. Owns synchronization-set-based recovery so one malformed pattern does not abort the whole compilation unit. Persistence boundary: AST nodes are never independently serialized; only the downstream pattern-ir snapshot is.

Type Resolver (§15). Assigns constructor identity, variant compatibility, wildcard typing, and tuple/slice arity. This is the semantic binding boundary — after this stage, pattern identity is closed over resolved constructor IDs (I3), not source text.

Pattern Normalizer (§16). Canonicalizes user-facing syntax (flattens OR-patterns, expands implicit captures, normalizes ranges) into the PatternMatrix form matrix decomposition requires. This is the last stage that touches surface syntax.

Pattern Matrix Builder / Specializer (§17). Implements Maranget-style specialization and default-matrix construction. Concurrency boundary: matrices are immutable snapshots; parallel specialization across independent constructor branches is permitted (ADR-08).

Exhaustiveness Analyzer (§18) / Redundancy Analyzer (§19). Both consume the same PatternMatrix snapshot and must agree on reachable constructor space (I2) — this is the system's core correctness fork; divergence between them is a P1-class defect.

Decision Tree / DAG Compiler (§20). Lowers the analyzed matrix into an acyclic decision DAG (I6) with dominance-based node merging.

Optimization Pass Pipeline (§20). Branch factoring, constructor factoring, guard hoisting, dead-test elimination, constant folding, jump threading — all semantics-preserving rewrites over the DAG produced above.

Backend Layer (§21). Two independent backends (C source emitter, bytecode emitter) consuming the same optimized DAG — the protocol boundary between compiler and runtime. Differential testing between them is the system's strongest defense against semantic drift.

Runtime / Conformance / Replay Harness (§21, §26). Executes generated artifacts, captures telemetry, validates semantics against reference behavior (rustc/OCaml fixtures), and replays any compilation deterministically from its event log (§23).

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every compilation stage must be replayable bit-for-bit given the same input and seed · Tradeoff: forbids wall-clock timestamps and unordered hash-map iteration inside any stage · Operational: enforced by replay crate checksum verification (I1) · Violated: irreproducible bugs, unstable diagnostics ordering, benchmark drift across runs.
  • P2 — Exhaustiveness Is Mandatory. Rule: every reachable constructor space must be accounted for before code generation proceeds · Tradeoff: costs recursion depth and memory proportional to constructor arity · Operational: enforced by exhaustiveness gating decision-tree (I2) · Violated: generated dispatch code silently falls through on unhandled variants at runtime.
  • P3 — Stable Diagnostics. Rule: diagnostic ordering and formatting are deterministic across identical inputs · Tradeoff: forbids diagnostic collection via unordered sets · Operational: enforced by diagnostics snapshot tests (ADR-12) · Violated: flaky CI, unreviewable diagnostic diffs in PRs.
  • P4 — Explicit Ownership. Rule: every IR node has exactly one owning arena and is referenced elsewhere only by index · Tradeoff: indices must be validated, cannot rely on borrow-checker aliasing guarantees across arenas · Operational: enforced by ast and pattern-ir arena invariants (I9) · Violated: use-after-free-shaped logic bugs (stale index reuse) even in a memory-safe language.
  • P5 — Bounded Resource Usage. Rule: no stage may allocate memory unbounded in malformed input size · Tradeoff: requires explicit throttling logic (specialization caps, recursion budgets) that adds code paths with their own tests · Operational: enforced by the 1 GB §4 exhaustiveness ceiling and matrix-explosion throttling (FM-1) · Violated: single malformed file causes host-wide OOM.
  • P6 — Observability by Default. Rule: every major phase emits metrics, spans, and structured logs without opt-in configuration · Tradeoff: baseline tracing overhead on every compilation, even successful ones · Operational: enforced by telemetry wrappers wired into every crate boundary · Violated: postmortems reduce to guesswork; no forensic trail (§23).
  • P7 — Replayability First. Rule: every compilation artifact is deterministically replayable from its event log · Tradeoff: every stage must externalize enough state to reconstruct itself, increasing log volume · Operational: enforced by replay event-log checksums (I1, I10) · Violated: a reported bug cannot be reproduced by anyone but the original reporter.
  • P8 — Backpressure Everywhere. Rule: every queue and work-stealing scheduler has a bounded capacity with an explicit overflow policy · Tradeoff: bounded queues can reject work under burst load rather than buffering indefinitely · Operational: enforced by ADR-21 credit-based channel sizing · Violated: unbounded memory growth under fuzz-induced or legitimate burst load (T5).
  • P9 — Stable Wire Compatibility. Rule: serialized IR supports additive-only forward evolution for N-2 versions · Tradeoff: cannot remove or repurpose a serialized field once shipped, only deprecate · Operational: enforced by postcard-based versioned envelopes (ADR-05, I7) · Violated: a minor-version upgrade silently corrupts persisted snapshots.
  • P10 — Crash-Only Recovery. Rule: every subsystem recovers via restart-and-replay, never via in-place partial-state patching · Tradeoff: no incremental checkpoint/resume inside a single compilation, only whole-compilation replay · Operational: enforced by the replay harness and the RTO/RPO §4 budgets · Violated: divergent partially-recovered state that no one can audit.
  • P11 — Zero Silent Recovery. Rule: every recoverable failure emits telemetry even when execution continues · Tradeoff: adds an emit-on-recovery code path to every fallback branch · Operational: enforced by parser-recovery and specialization-throttle counters (§24) · Violated: silent degradation masks a growing failure rate until it becomes an outage.
  • P12 — Parse Once. Rule: source text is never re-lexed or re-parsed during optimization stages · Tradeoff: all later stages must carry forward enough span/identity metadata rather than re-deriving it from source · Operational: enforced by AST node identity stability (I4, I11) · Violated: quadratic-time re-parsing under repeated optimization passes and diagnostic spans that silently drift from the original source.
  • P13 — Fixture-Driven Correctness. Rule: every algorithmic change ships with a named fixtures/<area>/<name> regression case before merge · Tradeoff: fixture-authoring overhead on every bug fix, not just features · Operational: enforced by conformance-suite CI gating (ADR-14) · Violated: regressions reappear silently across releases (Appendix B risk column).

8. Domain Model — Pattern Matching Semantics & Matrix Representation

8.1 Pattern Categories

Supported pattern forms: wildcard, literal, constructor (ADT variant), tuple, slice, range, binding, OR-pattern, guarded-pattern.

8.2 Core Grammar (EBNF)

Pattern     ::= Wildcard | Literal | Constructor | Tuple | Slice
              | Range | Binding | OrPattern | GuardedPattern
Constructor ::= Ident "(" PatternList? ")"
Tuple       ::= "(" PatternList ")"
Slice       ::= "[" PatternList ("," "..")? "]"
Range       ::= Literal ".." Literal
OrPattern   ::= Pattern ("|" Pattern)+
GuardedPattern ::= Pattern "if" Guard
PatternList ::= Pattern ("," Pattern)*

8.3 Example Matrix (match value { Some(0) => A, Some(x) => B, None => C })

Row Constructor Field0 Guard Arm
0 Some 0 — A
1 Some x (binding) — B
2 None — — C

Specialization on Some yields the sub-matrix { Field0: 0 -> A, Field0: x -> B }; the default matrix (constructor None excluded) yields { None -> C }. This is the row-major representation matrix-compiler (§17) operates over.

8.4 Decision-Node State Space

State Meaning
TestConstructor evaluate variant tag against expected constructor ID
TestLiteral compare scrutinee against a literal value
BindValue store a capture into the arm's binding environment
EvaluateGuard execute a guard predicate (I5 purity-checked)
Fail fall through to the next specialization/default branch
Match emit terminal branch result (arm index)

8.5 Recovery Example

Malformed input Some((x, (unterminated tuple inside a constructor pattern) triggers: emit a partial-tuple diagnostic at the unterminated-paren span, then resynchronize the parser at the next => or | token boundary (§14 recovery, I4-consistent span emission) so the remaining match arms still parse.

12. Phase 0 — Repository, Deterministic Infrastructure & Correctness Kernel

12.1 Objectives

Establish the Cargo workspace, deterministic tooling baseline, telemetry architecture, and the correctness kernel (replay event log, arena allocator conventions, trampoline recursion primitive) that every later phase depends on. Introduces the constraint that no stage may use wall-clock time or unordered iteration (P1, ADR-20). Distributed compilation and incremental dependency-graph invalidation are explicitly out of scope for this single-host kernel — PhaseDeferred("§12") for both, registered in §35.

12.2 Detailed Implementation Steps

Touches Cargo.toml, rust-toolchain.toml, clippy.toml, rustfmt.toml, and every crate's skeleton (lexer, parser, ast, types, pattern-ir, matrix-compiler, exhaustiveness, redundancy, decision-tree, optimizer, backend-c, backend-bytecode, diagnostics, replay, telemetry, cli). Implements: workspace-wide lint gates (ADR-19), a LogicalClock abstraction replacing SystemTime::now() everywhere (ADR-20, P1), the replay::event_log append-only writer with rolling checksum (I10), the telemetry::spans OpenTelemetry-span initializer (ADR-10), a generic bounded-trampoline primitive in matrix-compiler::trampoline used by every later recursive algorithm to satisfy I13, CI matrix configuration (ADR-14), and insta-based snapshot-test scaffolding (ADR-12). Every subsequent phase's N.2 cites this trampoline primitive rather than re-implementing recursion. Theory anchor: P1, P4, ADR-19, ADR-20, I10, I13.

12.3 Deliverable

A reproducible workspace: cargo build --locked produces byte-identical artifact hashes across two clean-checkout CI runs; cli binary accepts --replay-seed and emits a replay event log for a no-op compilation.

12.4 Acceptance Criteria

  • Artifact hash identical across 3 consecutive CI reruns (0 divergence, I1).
  • Zero clippy::all warnings at deny level (ADR-19).
  • fixtures/replay/basic.json round-trips through replay::event_log with checksum match.
  • Startup time < 100 ms (§4) measured over 50 CLI invocations, p95.

12.5 Conformance Fixtures

  • fixtures/replay/basic.json — minimal one-event replay log; validates checksum-covered round trip (I10).
  • fixtures/logging/startup.snap — snapshot of structured startup log fields; catches accidental non-deterministic field ordering (P3).
  • fixtures/replay/corruption_case.bin — deliberately bit-flipped log; must be rejected with a checksum-mismatch diagnostic, not silently accepted (malformed case).

12.6 Pitfalls

  • Nondeterministic timestamps. Manifestation: artifact hash differs across reruns · Root cause: a stray SystemTime::now() call bypassing LogicalClock · Debug method: diff two CI run artifact hashes, bisect by crate · Signal: replay.checksum_mismatch_total > 0 · Recovery: replace with LogicalClock, add a clippy lint forbidding SystemTime outside telemetry.
  • Locale-sensitive formatting. Manifestation: diagnostic snapshot fails only on non-C-locale CI runners · Root cause: default number/date formatting reading LC_ALL · Debug method: rerun snapshot test with LC_ALL=C vs LC_ALL=de_DE.UTF-8 · Signal: snapshot diff limited to numeric separators · Recovery: force explicit formatting, never locale-default.
  • Unstable hash maps. Manifestation: replay divergence only under -j parallel test runs · Root cause: iterating a HashMap instead of an ordered IndexMap/BTreeMap in a telemetry-aggregation path · Debug method: recursion-depth/order gauge diff between two runs of the same fixture · Signal: matrix.row_order_digest mismatch (I1) even in Phase 0 scaffolding code · Recovery: replace with an order-preserving container workspace-wide.

12.7 Performance Concerns

Startup allocation pressure from eager crate initialization (mitigate: lazy-init telemetry exporters); tracing span overhead on every compilation, even trivial ones (mitigate: sampling disabled by default in CLI mode, always-on in CI conformance mode per P6/P11 tradeoff).

12.8 Edge Cases

Corrupted replay logs (truncated mid-event); partial CI artifact uploads (hash computed before upload completes); toolchain-pin drift between local dev and CI runner; workspace member added without registering in the lint-gate CI matrix.

12.9 Failure Analysis

Primary risk: nondeterministic builds undermining every downstream replay guarantee (P1). Detection: nightly artifact-hash diffing job comparing today's hash against yesterday's for an unchanged fixture corpus. Blast radius: every phase — Phase 0 nondeterminism poisons all downstream replay traces. Containment: CI gate blocks merge on any hash divergence. Recovery path: bisect via toolchain pin rollback (rust-toolchain.toml revert), re-verify hash stability before re-advancing the pin. Operator visibility: nightly hash-diff report posted to docs/failure-analysis/incident-template.md-based writeup.

12.10 Operational Notes

Metrics: build.artifact_hash, replay.checksum_mismatch_total, startup.latency_ms histogram. Tracing spans: phase0.init, replay.write_event. Structured-log fields: compiler_revision, replay_seed, build_hash. Deployment: CI matrix runs on Linux x86_64/ARM64 (§4 CPU target). Rollback: revert rust-toolchain.toml to last known-good pin. Migration/compatibility: none yet — this phase defines the baseline every later migration is measured against.

13.1 Objectives

13.2 Detailed Implementation Steps

14.4 Acceptance Criteria

14.6 Pitfalls

15.6 Pitfalls

  • Shadowed binding ambiguity. Manifestation: a nested pattern's binding silently shadows an outer one, producing a surprising guard-evaluation value · Root cause: symbol resolution scoping the inner binding without flagging the shadow · Debug method: fixture with a deliberately shadowed name, inspect resolved SymbolId chain · Signal: guard evaluates against the wrong binding in a differential test against a reference implementation · Recovery: emit an explicit shadow-warning diagnostic (non-fatal), document as intended behavior matching host-language scoping rules.

15.7 Performance Concerns

15.8 Edge Cases

Recursive ADTs (a constructor field whose type is the enclosing ADT itself — must not infinite loop during arity validation); duplicate bindings within one pattern; a wildcard shadowing a declared constructor name; a guard referencing a binding not yet in scope at guard-evaluation time.

15.9 Failure Analysis

Blast radius: propagates into Phase 5 specialization and Phase 6 exhaustiveness — a P1-severity class of bug since it corrupts I2 agreement downstream. Containment: types unit tests assert ConstructorId uniqueness per lexical scope before merging. Recovery path: algorithm rollback to the last known-good symbol-table revision, re-resolve from AST.

15.10 Operational Notes

16. Phase 4 — Pattern Normalization

16.1 Objectives

Canonicalize all resolved patterns into the normalized pattern-ir form matrix decomposition requires: flattened OR-patterns, expanded implicit captures, normalized ranges, assigned constructor IDs carried forward from Phase 3.

16.2 Detailed Implementation Steps

Touches crates/pattern-ir/src/lib.rs, normalize.rs, or_flatten.rs. Implements: OR-pattern flattening into multiple matrix rows sharing one arm (bounded by a row-count ceiling to contain exponential blowup, P5); canonical wildcard insertion for elided fields; implicit capture expansion (a bare identifier pattern becomes an explicit Binding node); range normalization to a canonical (lo, hi) closed-interval form; and an idempotence check (normalizing already-normalized IR is a no-op, verified via digest comparison) implementing GHC's guard-tree flattening strategy (Peyton Jones et al., §5 Reference Implementations) rather than a from-scratch design. Theory anchor: P5, I1, GHC guard-tree flattening (2011-era ghc reference).

16.3 Deliverable

pattern_ir::normalize(TypedPatternTree) -> PatternMatrix producing the canonical matrix form consumed unchanged by Phase 5 specialization.

16.4 Acceptance Criteria

  • Normalization idempotence: re-normalizing normalized IR produces a byte-identical digest in 100% of the 500-case regression corpus.
  • OR-pattern row expansion bounded: no single arm expands past 512 rows (enforced ceiling, feeding P5); exceeding it emits E-OR-EXPANSION-LIMIT rather than allocating unbounded rows.
  • fixtures/normalize/or_expansion.pm and fixtures/normalize/tuple_flatten.pm pass with exact expected row counts.

16.5 Conformance Fixtures

  • fixtures/normalize/or_expansion.pm — a 4-way nested OR-pattern; expects exactly 16 expanded rows (2^4).
  • fixtures/normalize/tuple_flatten.pm — nested tuple-of-tuple pattern; expects flattened column structure matching the ADT's true field arity.
  • fixtures/normalize/nested_or_guard.pm — OR-pattern with an attached guard; expects the guard duplicated correctly across every expanded row, not attached to only the first.

16.6 Pitfalls

  • Exponential OR expansion. Manifestation: normalization latency spikes on a legitimate-looking but deeply nested OR-pattern · Root cause: naive Cartesian expansion of nested ORs without a row-count ceiling · Debug method: pattern_ir.rows_generated metric spike correlated with one fixture · Signal: allocation-amplification metric exceeds the 1.8x §4 ceiling · Recovery: enforce the 512-row ceiling above, emit a diagnostic recommending restructuring rather than silently truncating.

16.7 Performance Concerns

Allocation amplification from row expansion (directly measured against the §4 1.8x ceiling); mitigate via a shared sub-pattern cache so structurally-identical expanded rows share underlying node allocations rather than duplicating them.

16.8 Edge Cases

Nested OR-patterns combined with nested guards (guard duplication correctness); an OR-pattern where every alternative is a wildcard (degenerate case, should normalize to a single wildcard row, not N identical rows); a range pattern with lo > hi (empty range, must be flagged, not silently unreachable without a diagnostic).

16.9 Failure Analysis

What breaks: canonicalization divergence across runs (the same input normalizes to structurally different matrices on two runs). Detection: the idempotence + digest check in 12.4/16.4 above, run continuously in CI against the regression corpus. Blast radius: every downstream phase (Phase 5–9) — a canonicalization bug invalidates specialization, exhaustiveness, and codegen simultaneously. Containment: normalization output is checksum-logged to the replay event log (P7) before Phase 5 consumes it, enabling exact bisection. Recovery path: revert to the last release's normalization pass, re-run the fixture corpus to confirm the regression is isolated to the new change.

16.10 Operational Notes

Metrics: pattern_ir.rows_generated, pattern_ir.normalization_latency_ms, pattern_ir.expansion_limit_hit_total. Tracing span: normalize (§3 diagram). Structured-log fields: arm_count, expanded_row_count. Deployment: linked into cli. Compatibility: PatternMatrix shape is internal; only the serialized replay-log record of its digest is wire-stable (I7).

17. Phase 5 — Pattern Matrix Compiler (Specialization)

17.1 Objectives

Implement Maranget-style matrix specialization and default-matrix construction: the core divide-and-conquer decomposition algorithm every downstream phase (exhaustiveness, redundancy, decision-tree) consumes. SIMD-width vectorized matching is explicitly out of scope for this scalar specialization engine — PhaseDeferred("§17"), registered in §35.

17.2 Detailed Implementation Steps

Touches crates/matrix-compiler/src/lib.rs, specialize.rs, default_matrix.rs, trampoline.rs. Implements: row-major PatternMatrix construction from the Phase 4 normalized IR; specialization on a chosen constructor (Maranget 2008, §5 Papers) producing a sub-matrix containing only rows compatible with that constructor, with fields substituted in; default matrix construction (rows where the tested column is a wildcard) for the fallback path; constructor-splitting for slice/range patterns (a slice pattern splits into fixed-length and variable-length sub-cases); specialization-result caching keyed on (matrix_digest, constructor_id) to avoid recomputing identical sub-problems (Sestoft 1996 partial-evaluation framing, §5 Papers); and recursion expressed via the Phase 0 bounded trampoline rather than native recursion, enforcing I13. Theory anchor: I1, I13, ADR-08, Maranget (2008), Sestoft (1996).

17.3 Deliverable

matrix_compiler::specialize(&PatternMatrix, ConstructorId) -> PatternMatrix and matrix_compiler::default_matrix(&PatternMatrix) -> PatternMatrix, both pure and cache-consistent, feeding Phase 6/7 analysis and Phase 8 decision-tree construction from the same specialization calls (no duplicated logic between analysis and codegen).

17.4 Acceptance Criteria

  • Decomposition correctness verified via replay: 100% of the 300-case fixture corpus produces a specialization sequence bit-identical to its recorded replay trace (I1).
  • Specialization cache hit rate ≥ 60% on the sparse_matrix.pm benchmark input (feeds M-series §28 targets).
  • Recursion depth never exceeds the 4096 §4 soft limit on any fixture; exceeding it degrades to a diagnostic, not a crash (I13).

17.5 Conformance Fixtures

  • fixtures/matrix/specialization_chain.pm — a 6-deep nested-constructor chain; expects a specific, recorded specialization-call sequence matching its replay trace.
  • fixtures/matrix/sparse_matrix.pm — a matrix with many wildcard-dominated columns; expects high cache-hit-rate specialization.
  • fixtures/matrix/empty_matrix.pm — a matrix with zero rows (unreachable scrutinee type); expects a well-defined Failure-terminal result, not a panic.

17.6 Pitfalls

  • Matrix explosion. Manifestation: memory usage spikes disproportionately to input pattern count · Root cause: specialization cache disabled or a cache key collision causing redundant sub-matrix materialization · Debug method: matrix.rows_materialized metric growth vs. expected O(patterns × constructor arity) bound · Signal: allocation-amplification exceeds the 1.8x §4 ceiling · Recovery: specialization throttling (reduce cache eviction aggressiveness, fall back to default-matrix-only decomposition for pathological inputs) — this is FM-1.
  • Recursion overflow. Manifestation: process abort on deeply nested constructor chains · Root cause: a code path bypassing the Phase 0 trampoline (e.g. an inlined fast path added for performance that forgot the bound) · Debug method: matrix.recursion_depth gauge spikes past 4096 immediately before the abort · Signal: no diagnostic emitted (P11 violation) · Recovery: route the fast path back through the trampoline, add a regression fixture at depth 4097.

17.7 Performance Concerns

Cache locality: row-major matrix layout keeps specialization column-scans sequential in memory; branch churn: constructor-splitting for slice patterns can fragment the branch predictor's history table under highly heterogeneous constructor distributions (mitigate: sort specialization order by constructor frequency, most-common-first).

17.8 Edge Cases

Empty-matrix semantics (zero rows after specialization — must terminate at Failure, not loop); a matrix where every row is a wildcard (immediate match, specialization is a no-op); specialization cache key collision between structurally-different matrices with the same digest (must be treated as a correctness bug, not tolerated as a rare cache miss).

17.9 Failure Analysis

What breaks: incorrect specialization ordering (rows processed out of source order, changing which arm "wins" for an ambiguous match). Detection: I1 row-order-digest assertion catches this immediately in CI; a differential test against rustc/OCaml reference behavior (§5 Reference Implementations) catches semantic ordering bugs that pass I1 but still disagree with reference semantics. Blast radius: every downstream consumer (exhaustiveness witness generation, decision-tree branch order) — an ordering bug is silent until a specific ambiguous-match input exposes it. Containment: specialization is pure and cache-checked; a detected ordering violation aborts the compilation rather than emitting a wrong-but-plausible DAG. Recovery path: abort and replay (P10), bisect via the recorded specialization-call sequence.

17.10 Operational Notes

Metrics: matrix.rows_materialized, matrix.cache_hit_rate, matrix.recursion_depth. Tracing span: specialize (§3 diagram). Structured-log fields: constructor_id, specialization_depth. Deployment: linked into cli. Compatibility: specialization algorithm internals are not wire-stable; only its replay-log trace format is (I7, ADR-05).

18. Phase 6 — Exhaustiveness Analysis

18.1 Objectives

Implement the usefulness algorithm (Maranget 2007, §5 Papers) to detect missing match coverage and synthesize a human-readable missing-pattern witness for every gap. GADT-aware refinement typing and symbolic SAT-backed exhaustiveness are both explicitly out of scope for this constructor-space usefulness checker — PhaseDeferred("§18") for both, registered in §35.

18.2 Detailed Implementation Steps

Touches crates/exhaustiveness/src/lib.rs, usefulness.rs, witness.rs. Implements: constructor-space enumeration per matched type (delegated schema boundary, §1); the usefulness recursion (a row is useful if some input it matches is not matched by any earlier row), expressed via the Phase 0 trampoline (I13) and reusing Phase 5's specialize/default_matrix calls directly rather than re-implementing decomposition (P4/P12-consistent, single source of decomposition truth); wildcard expansion synthesizing a concrete missing-pattern witness from an "uncovered" result (rustc usefulness.rs witness-generation structure, §5 Reference Implementations); and stable diagnostic rendering of the witness set via diagnostics. Theory anchor: I2, I13, P2, Maranget (2007).

18.3 Deliverable

exhaustiveness::check(&PatternMatrix) -> ExhaustivenessResult returning either Exhaustive or Missing(Vec<Witness>), gating whether Phase 8 decision-tree construction may proceed to codegen (P2).

18.4 Acceptance Criteria

  • Matches rustc/OCaml reference behavior (§5 Reference Implementations) on 100% of the 150-case differential fixture corpus (0 disagreements).
  • Usefulness recursion depth stays under 10.9M witness-node ceiling derived in §32 C4 for the 1 GB §4 exhaustiveness memory budget.
  • fixtures/exhaustiveness/non_exhaustive.pm produces the exact expected witness pattern string.

18.5 Conformance Fixtures

  • fixtures/exhaustiveness/non_exhaustive.pm — a match missing one variant; expects a witness naming that exact variant.
  • fixtures/exhaustiveness/recursive_variant.pm — a recursive ADT (e.g. a list-like constructor referencing itself); expects termination without infinite constructor-space enumeration.
  • fixtures/exhaustiveness/nested_slice.pm — nested slice patterns with rest-bindings; expects correct witness synthesis across variable-length constructor splits.

18.6 Pitfalls

  • Infinite constructor expansion. Manifestation: exhaustiveness check hangs on a recursive ADT · Root cause: constructor-space enumeration recursing into the same recursive variant without a visited-set bound · Debug method: exhaustiveness.recursion_depth metric climbing unbounded on recursive_variant.pm · Signal: memory approaches the 1 GB §4 ceiling before hang · Recovery: bound enumeration depth, treat depth-exceeded as "assume covered by wildcard" with a diagnostic note rather than hanging (documented conservative approximation).

18.7 Performance Concerns

Combinatorial growth in constructor-space enumeration for wide-arity constructors (mitigate: share Phase 5's specialization cache rather than re-enumerating); usefulness recursion reuses Phase 5's matrix decomposition, so its performance profile inherits Phase 5's cache-hit-rate characteristics directly.

18.8 Edge Cases

Nested slice patterns with both fixed-length and rest-binding sub-cases; a recursive ADT with no base case reachable from the current matrix (should report exhaustive-if-unreachable-is- assumed, with a diagnostic caveat); a constructor space larger than the 10.9M witness-node budget for a single degenerate input (must throttle with a diagnostic, not silently truncate the reported witness set).

18.9 Failure Analysis

What breaks: false negatives causing runtime-unreachable states (exhaustiveness reports "exhaustive" when a case is actually missing) — the single most severe correctness class in this system (I2 violation). Detection: continuous differential testing against rustc/OCaml reference behavior on every fixture-corpus change; any disagreement blocks merge. Blast radius: propagates directly into generated dispatch code that silently falls through on an unhandled variant at runtime — a P2 violation with no local containment once shipped. Containment: exhaustiveness gates Phase 8 codegen; nothing reaches a backend without a witness-set decision. Recovery path: algorithm rollback to the last differentially-verified usefulness-algorithm revision (this is FM-6, the highest-severity registered failure mode).

18.10 Operational Notes

Metrics: exhaustiveness.divergence_total (I2), exhaustiveness.recursion_depth, exhaustiveness.witness_count. Tracing span: part of the specialize→analysis fan-out (§3 diagram). Structured-log fields: missing_witness_count, constructor_space_size. Deployment: linked into cli. Compatibility: Witness rendering format is a diagnostic-output stability surface post-v1.0 (ADR-18) since tooling may parse it.

19. Phase 7 — Redundancy Analysis

19.1 Objectives

Detect unreachable branches, shadowed patterns, and dead guards using the same usefulness foundation as Phase 6, maintaining the I2 agreement invariant between the two analyses.

19.2 Detailed Implementation Steps

Touches crates/redundancy/src/lib.rs, dead_branch.rs. Implements: per-row usefulness checking (a row is redundant if it is not useful against the matrix of all earlier rows — the mirror image of Phase 6's whole-matrix usefulness check, per Maranget 2007, §5 Papers); guard-aware redundancy (a row with a guard is never marked fully redundant, since guard evaluation is a runtime decision — only guard-free shadowing is flagged, consistent with I5 guard purity meaning guards cannot be statically eliminated); dead-capture detection (a binding that is never referenced by its arm's guard or body — a lint-level diagnostic, not an error); and stable diagnostic ordering shared with Phase 6's diagnostics integration (P3). Theory anchor: I2, I5, P3, Maranget (2007).

19.3 Deliverable

redundancy::check(&PatternMatrix) -> Vec<RedundancyDiagnostic> identifying every row's reachability status, consumed by both the diagnostics engine (user-facing warnings) and Phase 8 (dead rows are excluded from decision-DAG construction as an optimization).

19.4 Acceptance Criteria

  • Zero false positives across the 120-case conformance suite (a false positive here means flagging a reachable row as dead — verified via differential execution against backend-bytecode for that exact row's discriminating input).
  • fixtures/redundancy/dead_branch.pm and fixtures/redundancy/shadowed_or.pm produce the exact expected redundant-row indices.
  • Guard-bearing rows are never reported as fully redundant (100% of a 30-case guard-fixture corpus).

19.5 Conformance Fixtures

  • fixtures/redundancy/dead_branch.pm — a row fully shadowed by an earlier wildcard; expects that row flagged dead.
  • fixtures/redundancy/shadowed_or.pm — one alternative of an OR-pattern shadowed by an earlier row while the other alternative remains reachable; expects only the shadowed alternative flagged, not the whole OR-pattern.
  • fixtures/redundancy/recursive_guard.pm — a guard referencing a recursively-bound capture; expects the row correctly excluded from dead-branch flagging (I5-consistent).

19.6 Pitfalls

  • Guard interaction bugs. Manifestation: a row with a guard is incorrectly flagged dead · Root cause: redundancy analysis treating a guarded row identically to an unguarded row during usefulness checking · Debug method: differential-execute the flagged row's discriminating input against backend-bytecode; if it actually executes, the flag is a false positive · Signal: fixtures/redundancy/recursive_guard.pm regression · Recovery: guard rows always contribute their pattern (guard-stripped) to the "still useful" set for later rows, never treated as fully covering.

19.7 Performance Concerns

Repeated usefulness computation: naively re-running Phase 6's whole-matrix algorithm once per row is O(n²) in row count (mitigate: share Phase 5's specialization cache across all n per-row checks within one redundancy pass, amortizing the shared sub-problem cost).

19.8 Edge Cases

Recursive guards (a guard referencing a binding from a recursively-matched constructor field); an OR-pattern where only some alternatives are shadowed; a dead-capture binding that is referenced only in an unreachable code path of the arm body (out of scope — this system only sees the pattern, not the arm body, per §1 system boundaries).

19.9 Failure Analysis

What breaks: incorrect dead-code diagnostics (a false positive causes a user to delete reachable code; a false negative leaves genuinely dead code silently in place — lower severity than a false negative since it is not a runtime-correctness bug, only a diagnostics-quality bug). Detection: the zero-false-positive conformance-suite gate in 19.4. Blast radius: user trust in diagnostics (P3) rather than runtime correctness — contained to the diagnostics output layer. Containment: redundancy diagnostics are advisory (warning severity), never block compilation the way exhaustiveness failures can. Recovery path: differential-execution verification against backend-bytecode before shipping any redundancy-algorithm change.

19.10 Operational Notes

Metrics: redundancy.dead_rows_total, redundancy.false_positive_suspected_total (raised by the differential-execution check in CI, not in production). Tracing span: shares the specialize→analysis fan-out span (§3 diagram) with Phase 6. Structured-log fields: redundant_row_count, dead_capture_count. Deployment: linked into cli. Compatibility: RedundancyDiagnostic codes are additive-only post-v1.0 (ADR-18).

20. Phase 8 — Decision Tree Generation & Optimization Pipeline

20.1 Objectives

Lower the analyzed, dead-row-pruned PatternMatrix into an acyclic decision DAG (I6) with dominance-based node merging, then apply semantics-preserving optimization passes (I12). Speculative branch-prediction feedback (profile-guided reordering fed back from production telemetry) is explicitly out of scope for this static pipeline — PhaseDeferred("§20"), registered in §35.

20.2 Detailed Implementation Steps

Touches crates/decision-tree/src/lib.rs, dag.rs, dominance.rs, and crates/optimizer/src/lib.rs, branch_factor.rs, guard_hoist.rs, dead_test.rs. Implements: DecisionNode DAG construction driven by Phase 5's specialization calls (Test, Guard, Bind, Success, Failure nodes per §11); dominance analysis to identify structurally equivalent sub-DAGs eligible for merging (Wadler 1987 constructor-tree sharing, §5 Papers); cycle-freedom validation via topological sort before the DAG is considered final (I6); then the optimizer pipeline — dead-test elimination (a test whose result is already implied by a dominating test), branch factoring / constructor factoring (merge equivalent test nodes across sibling branches, Le Fessant & Maranget 2001, §5 Papers), guard hoisting (move a guard evaluation as early as possible without changing which arm ultimately matches, respecting I5 purity so hoisting is safe), constant folding, and jump threading (informed by the WebAssembly br_table control-flow semantics, §5 RFCs). Every optimizer pass runs a differential check against the pre-pass DAG (I12) before being accepted. Theory anchor: I6, I12, P8 (bounded optimizer worklist), Wadler (1987), Le Fessant & Maranget (2001).

20.3 Deliverable

decision_tree::build(&PatternMatrix) -> Dag followed by optimizer::run(Dag) -> Dag, producing an optimized, acyclic decision DAG ready for Phase 9 dual-backend codegen, with a DOT-graph export for operator inspection (tools/dag_to_dot.rs).

20.4 Acceptance Criteria

  • Deterministic DAG hashes across 3 CI reruns (0 divergence, I1-adjacent).
  • Decision-tree generation throughput ≥ 50,000 nodes/sec (§4 M3 target), measured on the benchmarks/dag_generation.rs corpus.
  • Branch-count reduction measurable: optimized DAG has ≥ 15% fewer test nodes than the pre-optimization DAG on the redundant_tests.pm/branch_merge.pm fixtures.
  • Zero I12 semantic-drift violations across the 100-case optimizer differential-test corpus.

20.5 Conformance Fixtures

  • fixtures/decision-tree/deep_branch.pm — a wide, deep constructor space; expects a DAG within the 4096 §4 branch-depth soft limit.
  • fixtures/decision-tree/mergeable_tests.pm — two sibling branches with identical test sequences; expects dominance-based merging to collapse them into one shared sub-DAG.
  • fixtures/decision-tree/pathological_fanout.pm — an adversarially wide single-level fanout; expects bounded node count, not quadratic blowup.
  • fixtures/optimizer/redundant_tests.pm — a DAG with a provably-implied redundant test; expects dead-test elimination to remove it.
  • fixtures/optimizer/branch_merge.pm — mergeable equivalent branches; expects a measurable node-count reduction matching the 15% acceptance threshold.

20.6 Pitfalls

  • Cyclic DAG generation. Manifestation: DAG validation pass fails post-construction · Root cause: dominance-merging logic incorrectly reusing a node that is an ancestor of the node being merged, introducing a back-edge · Debug method: topological-sort failure output names the exact offending node pair · Signal: dag.cycle_detected_total (I6, FM-2) · Recovery: rebuild the DAG from the normalized IR (Phase 4) without the merging pass, bisect the merging heuristic against the fixture that triggered it.
  • Semantic drift after optimization. Manifestation: an optimized DAG accepts/rejects a different input set than its pre-optimization version · Root cause: guard hoisting moved a guard past a point where its captured bindings were not yet established · Debug method: I12 differential check between pre- and post-pass DAG on the fixture corpus · Signal: optimizer.semantic_drift_total > 0 · Recovery: disable the offending pass for the affected pattern shape, add a regression fixture, require binding-availability analysis before any future guard-hoisting change.

20.7 Performance Concerns

Branch misprediction from high node fanout in the generated dispatch loop (mitigate: frequency-sorted test ordering, consistent with Phase 5's constructor-frequency sort); node-fanout-driven cache pressure on the DAG arena during construction (mitigate: dominance analysis processes nodes in a single forward pass, avoiding repeated re-visitation).

20.8 Edge Cases

Pathological constructor distributions (one constructor with 10,000 variants, all others with 1); an optimizer pass that would merge two nodes with subtly different guard expressions (must not merge — guard identity, not just structural shape, determines mergeability); a DAG with a single Success node reachable from every path (degenerate always-match case).

20.9 Failure Analysis

What breaks: incorrect fallback edges (a Failure edge points to the wrong default branch after merging) or the optimizer introducing unreachable success states (a Success node no input can actually reach post-optimization — FM-9). Detection: I12 differential checking plus a reachability-audit pass counting every Success node's incoming path count before/after optimization. Blast radius: silently wrong runtime dispatch — high severity, contained only by the mandatory differential check gating pass acceptance. Containment: any pass failing its I12 check is rejected wholesale for that compilation (not partially applied). Recovery path: disable the specific pass via optimizer pass-list configuration, re-run with the reduced pipeline, file a fixture before re-enabling.

20.10 Operational Notes

Metrics: dag.nodes_total, dag.cycle_detected_total, optimizer.pass_latency_ms per pass, optimizer.semantic_drift_total, optimizer.branch_count_delta. Tracing spans: generate, optimize (§3 diagram). Structured-log fields: dag_node_count, optimizer_passes_applied. Deployment: linked into cli. Compatibility: DAG shape is internal; DOT-graph export format is an operator-tooling surface only, not a compatibility guarantee.

Blast radius: undermines every bug report filed against a release build, since reporters' replay traces stop reproducing the issue. Containment: replay verification runs on every CI merge, not just release candidates. 24. Operational Readiness

Metrics strategy. Every phase exports its own counters/gauges/histograms (enumerated per phase in N.10); system-wide aggregates exposed via Prometheus (ADR-11) include compile_latency_ms, matrix_rows_total, dag_nodes_total, replay_divergence_total, optimization_pass_latency_ms, and parser_recovery_total.

Tracing strategy. OpenTelemetry spans (ADR-10) follow the §3 pipeline diagram exactly: parse, normalize, specialize, generate, optimize — every span carries the compilation-unit ID for cross-request correlation in the 128-concurrent-compilation (§4) deployment.

Alerting philosophy. Page only on: deterministic divergence (I1/I10, any nonzero count is a page, per §4's zero-tolerance budget), persistent CI instability (FM-10 sustained past one business day), and replay corruption (FM-3/FM-4). Everything else — individual malformed-input diagnostics, single-fixture regressions — is a ticket, not a page (P11 requires telemetry, not necessarily an interrupt).

Backup strategy. Persist: replay traces (P7, fixtures/replay/ retention policy), benchmark baselines (benchmarks/ regression gate inputs), signed release artifacts (ADR-17). Retention bounded by the < 2.2x §4 storage-amplification budget.

Rolling-upgrade strategy. Support N-2 IR compatibility (I7): a compiler binary two minor versions newer than a persisted snapshot's writer must still decode it. Upgrade sequencing: deploy new binary, verify N-2 decode fixtures pass against production snapshot samples, then retire the oldest supported writer version.

25. Compatibility & Versioning

Wire compatibility. Serialized IR (pattern-ir, replay event logs) uses versioned envelopes (ADR-05, I7); every record carries a schema-version tag decoded before payload interpretation.

Schema evolution. Only additive evolution is permitted in stable records post-v1.0 (ADR-18): new optional fields default on read, no field is ever removed or repurposed within a major version.

API stability. Public crate APIs (lexer, parser, pattern-ir, matrix-compiler, exhaustiveness, redundancy, decision-tree, optimizer) stabilize after v1.0; pre-1.0, breaking changes require a BLUEPRINT_LOG.md entry but no deprecation window.

Deprecation policy. Minimum two minor releases of deprecation warning before removal of any stabilized API or DiagnosticCode/RedundancyDiagnostic variant, consistent with the additive-only serialization guarantee above.

26. Testing & Verification Strategy

Unit testing. Per-module deterministic validation (crates/*/tests/) against named fixtures — every fixture referenced in Phase N.5 sections above is a unit-test input.

Integration testing. Cross-stage pipeline execution (conformance/runner.rs) exercising lex → parse → resolve → normalize → specialize → analyze → generate → optimize → emit as one deterministic run per fixture.

Differential testing. Compare against rustc (rustc_mir_build::thir::pattern) and OCaml (typing/matching.ml) reference behavior (§5 Reference Implementations) for exhaustiveness (§18) and against each other's backend for backend-c/backend-bytecode (§21) — the system's two primary correctness oracles.

Property testing. proptest-generated randomized pattern matrices (ADR-12) targeting normalization idempotence (§16.4) and specialization row-order stability (I1).

Fuzzing. Coverage-guided cargo-fuzz (ADR-13) malformed-input fuzzing across lexer_fuzz.rs, parser_fuzz.rs, matrix_fuzz.rs, replay_fuzz.rs, gated at 72h continuous stability before release (§21.4).

Chaos testing. Replay corruption injection (fixtures/replay/corruption_case.bin-class inputs) verifying checksum-based rejection (I10) rather than silent corruption tolerance.

Deterministic replay. Hash-based artifact validation (I1) — every CI run re-derives the same artifact hash from the same fixture corpus, the foundation every other testing layer above depends on (P1).

27. Build & Release Engineering

Reproducible builds. Pin compiler toolchain (rust-toolchain.toml), dependency revisions (Cargo.lock, ADR-03), and linker versions in the CI image (ADR-16), enforced by the artifact- hash-diff gate (§12.4).

Artifact signing. Sigstore cosign signing plus SHA-256 manifests (ADR-17) for every tagged release binary.

SBOM generation. CycloneDX manifests generated per release, attached alongside the signed artifact (§21.2).

CI/CD topology. Stages: lint (ADR-19) → test (unit + integration) → fuzz smoke (short cargo-fuzz run, not the full 72h campaign) → replay validation (§26) → benchmark regression (§28) → release signing (ADR-17). Each stage gates the next; no stage is skippable for a release branch.

29. Scalability Analysis

Bottlenecks. OR-pattern explosion (§16, bounded to 512 rows/arm), usefulness recursion (§18, bounded by the 10.9M witness-node ceiling), DAG compaction under high fanout (§20).

Horizontal scaling. Parallelize independent compilation units across hosts (each compilation is self-contained per I9 arena isolation — no cross-unit shared mutable state); parallelize fuzz workers (§21) and benchmark runners (§28) independently, since neither requires cross-worker coordination.

Vertical scaling. Increase the specialization cache capacity (§17), arena pre-allocation sizes (§12, §13), and the number of parallel specialization threads permitted per compilation under ADR-08's Tokio-limited-to-boundary model (specialization itself is CPU-bound, so vertical scaling here means more cores per host, not more IO concurrency).

30. Mental Models & First Principles

  • MM1 — Matrices Are Proofs of Coverage. The compressed insight: a PatternMatrix is not merely a data structure, it is a proof obligation — exhaustiveness is what happens when the matrix's specialization tree terminates with no unmatched constructor left · predicts: any bug in specialization (§17) will manifest as an exhaustiveness or redundancy disagreement (I2), never as an isolated local error · bug class avoided: treating exhaustiveness as a separate feature instead of a property of the matrix itself · applies in §17 and §18.
  • MM2 — Specialization Is Divide-and-Conquer on Constructors. Compressed insight: every matrix-compilation algorithm since Augustsson (1985) is structurally the same divide step — split by constructor, recurse, combine · predicts: any "novel" pattern-matching optimization is almost certainly a variant of specialization ordering or caching, not a new primitive · bug class avoided: reinventing a bespoke decomposition instead of reusing §17's specialize/ default_matrix pair · applies in §17 and §20.
  • MM3 — Usefulness Checking Is Exhaustiveness in Reverse. Compressed insight: "is this row reachable" (redundancy, §19) and "is anything unreached" (exhaustiveness, §18) are the same usefulness computation applied to complementary matrices · predicts: any algorithmic fix to one analysis without the mirrored fix to the other reintroduces I2 divergence · bug class avoided: patching exhaustiveness bugs without re-verifying redundancy on the same fixture · applies in §18 and §19.
  • MM4 — Decision Trees Trade Redundant Tests for Predictable Branches. Compressed insight: a decision DAG (§20) deliberately re-tests information already implied by an ancestor node when doing so improves branch predictability, not always minimizing test count · predicts: "fewest tests" is not the true optimization target — "fewest mispredicted branches under realistic input distribution" is · bug class avoided: an optimizer pass that minimizes node count but regresses measured latency · applies in §20 and §28.
  • MM5 — Determinism Is a Testing Multiplier. Compressed insight: every hour spent enforcing P1 determinism buys back many hours of flaky-test triage later, because a nondeterministic system cannot be bisected · predicts: the majority of "unreproducible" bug reports trace back to one of a small, enumerable set of nondeterminism sources (wall-clock, unordered hashing, uninitialized memory) · bug class avoided: chasing a "flaky" test instead of finding its determinism leak · applies in §12 and §21.
  • MM6 — Guards Are Escape Hatches That Break Static Reasoning. Compressed insight: every guard is a point where the compiler must stop reasoning statically and defer to runtime evaluation, which is why I5 purity exists — an impure guard breaks not just correctness but the analyzability of everything downstream · predicts: any feature request to "make guards smarter" (e.g. static guard evaluation) either requires proving purity first or is out of scope · bug class avoided: an optimizer treating a guard's result as statically knowable · applies in §15 and §19.
  • MM7 — A DAG Is a Tree With Sharing, Not a New Algorithm. Compressed insight: dominance- based merging (§20) does not change what the decision structure computes, only how much of it is physically duplicated in memory · predicts: any merging bug is necessarily an I12 semantic-preservation bug, never a "the algorithm changed" bug, because the algorithm by definition does not change · bug class avoided: debugging a merge failure as if it were a specialization-algorithm defect · applies in §20.
  • MM8 — Backend Divergence Is Always a Semantics Bug, Never a Codegen-Style Bug. Compressed insight: because both backends consume the identical optimized DAG, any accept/reject disagreement between them is necessarily a lowering bug in one emitter's control-flow encoding, not a difference in "what the DAG means" · predicts: backend-divergence triage should start at the label/jump-target computation, not at the DAG or the optimizer · bug class avoided: re-auditing the optimizer (§20) when the bug is actually in emit.rs or opcodes.rs (§21) · applies in §21.

  • rustc — decoupled its usefulness checker from the full type checker in a 2021-era rewrite specifically so exhaustiveness could be tested independently of borrow-checking; this system adopts that decoupling directly (types crate boundary, §15) but wins narrowly in the single-target-compiler niche rustc itself occupies.
  • OCaml (matching.ml) — chose exit-jump numbering (each arm gets a numbered jump target threaded through specialization) rather than a separate DAG IR; wins when the target is always native/bytecode-adjacent and a dedicated DAG representation would be pure overhead — this system rejects that because dual-backend differential testing (§21) requires an IR-level representation independent of either target.
  • GHC — interleaves guards directly into its guard-tree representation rather than analyzing them as a separate pass; wins in a lazy-evaluation setting where guard-evaluation order has observable side effects on non-termination — this system's strict, guard-pure (I5) semantics make GHC's interleaving unnecessary complexity for this domain.
  • Erlang/OTP (BEAM) — skips static exhaustiveness entirely, relying on runtime function_clause errors; wins for a dynamically-typed, hot-code-reload production runtime where static exhaustiveness would be actively wrong (module reloading can add clauses) — this system's static exhaustiveness (P2) is incompatible with that operating model by design, not by oversight.

34. Alternative Architectures (Roads Not Taken)

Alt A — Backtracking Interpreter

scrutinee -> [try pattern 1] -fail-> [try pattern 2] -fail-> ... -fail-> [no match]
                 |match                  |match
                 v                      v
              [arm 1]                [arm 2]

Regime where it wins: prototype DSLs with fewer than ~50 patterns where implementation simplicity and compile-time cost matter more than dispatch-time cost. Real system: early Scheme syntax-rules-style tree-walking pattern interpreters. Rejected here because backtracking cost is exponential in the worst case (no shared decomposition across alternatives) and produces no artifact satisfying I6 (there is no DAG at all to validate).

Alt B — NFA/Regex-Style Automaton Compilation

[start] --char class--> [state 1] --char class--> [state 2] --> [accept]
                |already-seen-class
                v
           [shared state]

Regime where it wins: string/byte-oriented matching where the input space is characters, not typed constructors — regex/lexer-generator territory. Real system: rust-lang/regex (regex-automata), built on Thompson-construction NFA compilation. Rejected here because ADT constructor matching needs typed tuple/field decomposition (§8), not character-class transitions; forcing patterns through an automaton model would require encoding every constructor as a synthetic alphabet, discarding the type information §15 depends on.

Alt C — SAT/SMT-Backed Exhaustiveness

pattern matrix -> [encode as boolean formula] -> [SAT/SMT solver] -> SAT: witness
                                                                  -> UNSAT: exhaustive

Regime where it wins: refinement-typed or dependently-typed pattern systems where boolean guard reasoning dominates over constructor coverage — verification-oriented languages. Real system: Z3-backed verification tooling in the Prusti/Verus style for refinement-typed languages. Rejected for this system's Phase 0–9 scope because solver latency variance is incompatible with the 250 ms p95 §4 constraint; tracked instead as the deferred GADT-aware refinement-typing feature (PhaseDeferred("§18")) pending a use case that justifies the latency tradeoff.

Alt D — Interpreted Decision Table Without a Codegen Backend

[decision table row 1] -> test -> next row or arm
[decision table row 2] -> test -> next row or arm
   ... executed by a generic interpreter loop, never compiled ...

Regime where it wins: low-throughput rule engines where portability and hot-reload trump dispatch speed. Real system: interpreted-mode rule evaluation as used by Drools-style business rule engines. Rejected here because interpretive dispatch overhead cannot meet the 50,000 nodes/sec §4 M3 throughput target — this system compiles to two independent executable backends (§21) specifically to avoid paying interpretation cost on every dispatch.

36. Glossary

  • Pattern Matrix — tabular row/column representation of a set of patterns used for specialization (§8.3, §17).
  • Constructor Space — the full reachable set of variants for a matched ADT type.
  • Usefulness — whether a matrix row can match some input not matched by any earlier row.
  • Exhaustiveness — whether every value of the scrutinee's type is covered by some row.
  • Redundancy — a row that is not useful given the rows above it; an unreachable branch.
  • Decision DAG — the acyclic branching graph produced by lowering an analyzed matrix (§20).
  • Specialization — constructor-focused matrix reduction producing a sub-matrix (§17).
  • Default Matrix — the fallback matrix of wildcard-only rows after specialization.
  • Guard — a conditional predicate attached to a pattern, evaluated at runtime (I5).
  • Wildcard — a match-any placeholder pattern.
  • Binding — a variable-capture pattern.
  • Replay Trace — a deterministic, checksum-covered event sequence (I10).
  • Arena Allocation — region-based memory strategy used for AST/IR node ownership (P4).
  • Span — source-location metadata attached to a token or diagnostic.
  • Canonicalization — the stable normalization process performed in Phase 4 (§16).
  • Snapshot Test — a stable serialized-output assertion (insta, ADR-12).
  • Differential Testing — comparing this system's output against a reference implementation.
  • IR — intermediate representation; here specifically pattern-ir's canonical form.
