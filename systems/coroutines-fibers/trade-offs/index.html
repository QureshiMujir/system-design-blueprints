Decisions (§9) · 28 ADRs

ADR-01

Core language

Chosen

Rust 2024 + global_asm! per-arch assembly

Rejected

C; C++/Boost.Context; Zig

When the rejected choice is right

A team already deep in C/C++ with no Rust adoption path, needing Boost.Context's 15-year multi-arch coverage immediately.

Why: Ownership documents the aliasing contract at the unsafe boundary (§11, P10); ecosystem-native bridge to rank-129 (§23)

ADR-02

Coroutine model

Chosen

Stackful (register-level context switch)

Rejected

Stackless (compiler state machine, rank-129)

When the rejected choice is right

A workload that is overwhelmingly I/O-bound, single-depth, and never touches blocking FFI — stackless's near-zero per-task memory wins outright (rank-129's regime).

Why: Stackful calls arbitrary blocking/FFI code at any depth (P1); stackless needs Pin/Unpin and a bridge for blocking calls

ADR-03

Scheduling discipline

Chosen

Cooperative (explicit yield points)

Rejected

Preemptive (signal-based, Go-style)

When the rejected choice is right

A workload that cannot be trusted to yield voluntarily (multi-tenant, adversarial, or third-party code) — Go pays preemption's cost for exactly that regime.

Why: Preemption's async-signal-safe stack-rewriting cost is out of proportion to the benefit at this project's scale (P2)

ADR-04

Scheduler topology

Chosen

M:N work-stealing (Chase-Lev deque + global injector)

Rejected

1:1 (thread-per-coroutine); M:1 (single thread)

When the rejected choice is right

Concurrency count close to core count (M ≈ N) — 1:1 is simpler and work-stealing's overhead is not repaid.

Why: Only M:N scales past ~10k concurrent units without per-unit OS-thread cost while still using >1 core (P3)

ADR-05

Stack strategy (default)

Chosen

Fixed-size mmap'd stacks, 64 KiB

Rejected

Segmented stacks; growable/copying stacks

When the rejected choice is right

Per-coroutine memory is the binding constraint and depth is unpredictable — Go's copying stacks (§8) win there because Go's precise GC can relocate every pointer.

Why: Correct-by-construction, no pointer-relocation hazard; segmented/growable need a hot-path boundary check or precise-GC-style relocation Rust does not give for free (§15)

ADR-06

Overflow detection

Chosen

Guard page (mprotect(PROT_NONE)) + SIGSEGV handler

Rejected

Per-call stack-pointer canary check

When the rejected choice is right

A target with no MMU/page-fault mechanism (embedded, no-MMU microcontrollers) — canaries are the only option there.

Why: Guard pages cost nothing until faulted; canaries cost a check per call (P6)

ADR-07

API surface

Chosen

Asymmetric Coroutine<R,Y> + symmetric Fiber, one context-switch primitive

Rejected

Asymmetric-only (Lua-style)

When the rejected choice is right

A domain that is purely generator-shaped (iterator adapters) — Lua's asymmetric-only design is simpler and never needs Fiber's flexibility.

Why: Two genuinely different control-transfer shapes (generator vs. arbitrary graph) need two APIs (P4)

ADR-08

IPC primitive

Chosen

CSP channels (bounded + unbounded)

Rejected

Shared mutable state + locks only

When the rejected choice is right

Large data where copying through a channel dominates the workload — a shared Arc<RwLock<T>> wins for big-buffer producer/consumer.

Why: Channel-passing is the documented, auditable default (P7); locks-only reintroduces CSP's avoided races

ADR-09

Cancellation model

Chosen

Cooperative, observed at yield points

Rejected

Forced unwind from an arbitrary instruction

When the rejected choice is right

A host embedding an interpreter with its own safe-point mechanism (a bytecode VM) — that VM can force-terminate at its own safe points.

Why: Forced mid-instruction unwind corrupts invariants a coroutine's unwound callees held (P8)

ADR-10

Migration policy

Chosen

Opt-in migration; pinned by default

Rejected

Always-migratable (Go-runtime default)

When the rejected choice is right

No coroutine ever touches TLS or holds FFI-affine state — Go's always-migratable default wins on scheduler simplicity and steal-fairness.

Why: Rust's type system cannot enforce TLS/FFI-affinity safety the way Go's runtime convention does (P9)

ADR-11

Architecture coverage

Chosen

x86-64 SysV, x86-64 Windows, aarch64 AAPCS64, riscv64

Rejected

x86-64-only

When the rejected choice is right

A single known deployment architecture (an appliance) — narrowing to one arch halves the assembly-review and CI-matrix burden.

Why: Server and edge deployment both target aarch64 (Graviton, Apple Silicon CI); riscv64 is an emerging server/embedded target

ADR-12

Async-runtime interop

Chosen

A dedicated bridge crate into rank-129

Rejected

No interop (coroutines-only ecosystem)

When the rejected choice is right

An entirely coroutine-native greenfield service with no async I/O dependency — skipping the bridge removes a whole subsystem (§23) for zero loss.

Why: Most production Rust services already run an async runtime for I/O; an isolated coroutine ecosystem is unusable in an existing codebase

ADR-13

Licensing

Chosen

Apache-2.0 OR MIT dual license

Rejected

GPL-family

When the rejected choice is right

The project explicitly wants to force downstream modifications to stay open — GPL wins there, at the cost of the C-ABI embedder audience.

Why: Matches Rust-ecosystem default; permits proprietary embedding (P13's C-ABI audience)

ADR-14

Sync-primitive verification

Chosen

loom model-checking (Mutex/RwLock/Semaphore/WaitGroup)

Rejected

Manual stress-testing only

When the rejected choice is right

A state space too large for loom to explore in CI-budget time — not the case for these four primitives at TC ≤ 3 (§21).

Why: Loom exhaustively explores interleavings at small thread counts (I4, I11) that stress tests only sample probabilistically

ADR-15

Property/fuzz testing

Chosen

proptest + cargo-fuzz

Rejected

Hand-written edge-case tests only

When the rejected choice is right

An input space small enough to enumerate by hand (a 3-state enum) — exhaustive hand tests then dominate fuzzing's setup cost.

Why: Random op-sequence generation finds interleaving bugs hand tests miss by construction

ADR-16

Benchmarking

Chosen

criterion, CI regression-gated (M1–M12, §30)

Rejected

Ad hoc Instant::now() timing

When the rejected choice is right

The metric of interest is throughput over minutes, not nanosecond latency — coarser wall-clock timing is adequate and cheaper.

Why: Statistical outlier rejection and variance reporting are required to trust a ~10 ns measurement (P14)

ADR-17

Instrumentation

Chosen

tracing spans per spawn/yield/resume/cancel/drop

Rejected

log-crate flat line logging only

When the rejected choice is right

No span-aware collector is operationally supported, only greppable flat logs — log wins on zero-infrastructure cost.

Why: Per-coroutine spans reconstruct causal ordering across a million interleaved coroutines; flat lines cannot

ADR-18

CI hygiene

Chosen

clippy --deny warnings, rustfmt --check, cargo-deny, cargo-audit, Miri (non-asm crates)

Rejected

Best-effort/manual review only

When the rejected choice is right

A single-maintainer prototype with no consumers yet — the CI-matrix cost is not repaid until there are users to protect.

Why: I5's compile-time contracts and I14's panic-doc contract are only enforced if CI blocks on them

ADR-19

C ABI compatibility

Chosen

Binary-compatible with libtask's C surface where shapes overlap

Rejected

A bespoke, unrelated C ABI

When the rejected choice is right

No C embedder exists yet and the bespoke surface can be optimized purely for Rust internals without a compatibility tax.

Why: Existing C embedders (P13) port with minimal glue if shapes already line up

ADR-20

Default stack size

Chosen

64 KiB per coroutine

Rejected

8 KiB (Go's original default); 2 MiB (full OS-thread-sized)

When the rejected choice is right

Coroutine bodies are known shallow, non-recursive, and latency-insensitive to stack growth — 8 KiB then quadruples achievable coroutine count per GiB.

Why: 64 KiB covers deep-recursion Rust (which inlines less aggressively than Go) without paying multi-MiB-per-coroutine cost at 1M scale (§34)

ADR-21

Stack reuse

Chosen

Per-thread pool, fixed size classes (8/64/256 KiB, 1/4 MiB)

Rejected

Allocate-and-free every spawn

When the rejected choice is right

Coroutines are long-lived and rarely spawned/retired (a fixed worker-pool pattern) — the pool's memory overhead is not repaid there.

Why: mmap/munmap cost ~5 µs each (M3, §30); a pool amortizes to <100 ns on a hit (§34)

ADR-22

Determinism / replay

Chosen

Seeded PRNG + recorded op-log, bit-identical replay (I13)

Rejected

No replay support; live debugging only

When the rejected choice is right

A workload with no meaningful interleaving (strictly single-threaded use) — recording overhead has no offsetting debugging value.

Why: A scheduler-interleaving bug is often unreproducible live; replay turns a one-in-a-million race into a deterministic repro (P12)

ADR-23

Long-running-coroutine detection

Chosen

A consecutive-yield/no-progress counter emits a tracing warning past a threshold

Rejected

No detection; operator intuition only

When the rejected choice is right

An external watchdog/APM already provides equivalent starvation detection — the in-library counter becomes redundant instrumentation.

Why: A starving coroutine (P2's known failure mode) is otherwise invisible until a downstream timeout fires far from the root cause

ADR-24

Signal-handler safety

Chosen

The SIGSEGV handler touches only a pre-allocated, lock-free coroutine table (I9)

Rejected

A handler that allocates or takes a mutex for convenience

When the rejected choice is right

A platform whose fault semantics guarantee no page fault can occur inside the allocator or while holding the table lock — a theoretical static-heap embedded target; no hosted OS target we support qualifies today.

Why: A fault occurring inside malloc or while holding that mutex deadlocks a handler that itself needs either

ADR-25

Observability schema versioning

Chosen

Metric/span names frozen per major release under helios_<subsystem>_<noun>_<unit>

Rejected

Ad hoc renaming whenever convenient

When the rejected choice is right

An internal-only prototype with no external dashboards yet, where rapid metric-name iteration has no consumer to break.

Why: Dashboards (§26) built against a name break silently on rename

ADR-26

Coroutine-local storage

Chosen

Not provided; TLS remains the only per-context storage, with the documented migration hazard (T4)

Rejected

A first-class CoroutineLocal<T> analogous to TLS

When the rejected choice is right

A workload with pervasive implicit per-coroutine state (e.g., porting a codebase assuming thread-locals map 1:1 to logical tasks) — CLS removes a large refactor burden there.

Why: Correct CLS requires per-context storage swapped inside swap(), adding cost to the M1/M2 critical path for a feature most workloads route around via explicit state threading

ADR-27

Panic-message redaction

Chosen

Panicked telemetry never places the panic payload string in metric labels (only in the structured log body)

Rejected

Including the panic message directly as a metric label

When the rejected choice is right

A small, trusted, low-cardinality panic-message set (a fixed enum of internal panic reasons) where label cardinality is bounded by construction.

Why: Unbounded-cardinality panic strings as metric labels is a metrics-system cardinality-explosion risk

ADR-28

Dependency vendoring policy

Chosen

Dependencies pulled from crates.io via Cargo.lock, not vendored into the repo

Rejected

Full source vendoring of all dependencies

When the rejected choice is right

An air-gapped deployment environment with no crates.io network access at build time — vendoring or a private registry mirror is then required.

Why: Vendoring bloats the repo and duplicates cargo-audit's job of tracking upstream advisories

36. Alternative Architectures (Roads Not Taken)

Alternative A — Stackless compiler-transform coroutines only (no stackful runtime at all).

[async fn source] --(compiler)--> [generated state machine struct]
        |                                  |
        +-------- Future::poll -----------+---> executor (single stack, no swap())

Regime where it wins: workloads that are overwhelmingly I/O-bound, shallow-call-depth, and never touch blocking/recursive FFI. Real system: Rust's own async/await + any executor (the rank-129 blueprint's own domain). Rejected here because it cannot call arbitrary blocking or recursive FFI code without a bridge — exactly the capability §1/§2 identify as this project's reason to exist (ADR-02).

Alternative B — 1:1 OS-thread-per-coroutine (no user-level scheduler at all).

[coroutine 1] -> OS thread 1 (8 MiB stack, kernel-scheduled)
[coroutine 2] -> OS thread 2 (8 MiB stack, kernel-scheduled)
[coroutine N] -> OS thread N ...

Regime where it wins: low concurrency counts (thousands, not millions) where the engineering cost of a user-level scheduler is not repaid. Real system: traditional POSIX-threads-per-connection servers (e.g., pre-event-loop Apache MPM designs). Rejected here because per-thread stack cost (KiB–MiB range) and kernel-scheduling overhead do not scale to the 1M-coroutine target (M4, ADR-04).

Alternative C — Actor-model, no shared address space (Erlang/BEAM-style, per-process heap and GC).

[actor A: private heap] --msg--> [mailbox] --msg--> [actor B: private heap]
        (no shared memory ever; supervision tree manages restarts)

Regime where it wins: fault isolation is paramount and supervision-tree-style "let it crash" restart semantics are the primary reliability mechanism. Real system: Erlang/OTP, Elixir. Rejected here because helios coroutines share one address space by design — CSP channels (P7) are a convention, not an isolation boundary — and building a full per-actor-heap GC plus supervision tree is a fundamentally larger, different system than a coroutine library (explicit non-goal, §1).

Alternative D — Signal-based preemptive M:N scheduling (Go-style forced preemption).

worker thread --SIGURG--> [async preemption point injected into running goroutine's stack]
                                    |
                            forced yield, state saved, scheduler regains control

Regime where it wins: workloads with untrusted or adversarial cooperative code that cannot be trusted to yield voluntarily. Real system: the Go runtime post-1.14 (asynchronous preemption via signal-injected safe points). Rejected here because the engineering cost of async-signal-safe stack rewinding is disproportionate to the benefit at this project's scale, where cooperating code is assumed trusted (ADR-03, P2).
