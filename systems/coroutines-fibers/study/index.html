Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does this project default to 64 KiB stacks instead of Go's 8 KiB, and what would have to change in Rust's type system for it to safely adopt Go's growable-stack default instead? (§15, §9 ADR-05/ADR-20)
  2. Under what load pattern does M:N scheduling lose to a simple 1:1 model, and how does ADR-04's rejected-alternative column quantify that crossover? (§9 ADR-04, §31)
  3. Why is the guard page installed at the low address on every supported architecture, and what would have to be true of a hypothetical target for that to be wrong? (§8.3, §14.6)
  4. Trace mechanically what happens from the moment a coroutine's stack faults into its guard page to the moment Panicked(StackOverflow) is observable by the scheduler — name every subsystem involved. (§18, I3, I9)
  5. Why can the SIGSEGV handler not simply longjmp back to the scheduler, and what does it do instead? (§18.2, I9)
  6. What concrete Rust type-system feature would need to exist for growable/copying stacks to move from "gated, opt-in" to "the default," and why does Go not need that feature? (§15, §9 ADR-05, §33)
  7. What does Coroutine::resume() guarantee about "where control returns" that Fiber::switch_to() does not, and why can one API not simply be implemented in terms of the other despite sharing one context-switch primitive? (§16, §17, §9 ADR-07)
  8. Why does pinning default to on (opt-in migration) here while Go's goroutines default to always-migratable, and under what workload does each default actually cost more? (§9 ADR-10, §19.6)
  9. Walk through why a Mutex held across a channel.send() deadlocks, using the actual state-machine transitions. (§21.6, §8.4)
  10. What is the actual mechanism by which "half-stealing" reduces cross-core cache traffic versus stealing one task at a time, and which paper is it drawn from? (§19.2, §5 Chase & Lev 2005)
  11. Why is cancellation cooperative rather than forced, and what specific invariant would forced cancellation violate that cooperative cancellation does not? (§22, §9 ADR-09)
  12. Using §4 and §34's numbers, explain why the 1M-coroutine target is stated as "≤ 10 s spawn+drain" rather than a memory-only claim — what would a memory-only claim have missed? (§4, §34)
  13. Why does the async-bridge (§23) auto-pin conservatively on every yield rather than doing a precise stack walk, and what would the precise version need to detect that the conservative version does not? (§23.2, §37)
  14. Contrast the blast radius of a worker-thread panic (FM-8) with a stack-overflow panic (FM-1) — why does one restart a worker and the other only retire one coroutine? (§25, §8.4)
  15. Why is loom verification (ADR-14) run only at thread counts 2 and 3, and what argument justifies that this is sufficient rather than merely convenient? (§9 ADR-14, §21.4)
  16. What would have to change in this design to support cross-process coroutine migration, and why was that explicitly placed out of scope? (§1, §33)
  17. Why does the Deferred Features Register anchor segmented and growable stacks to §15 rather than to the Repository Layout's segmented.rs/growable.rs files directly? (§15, §37)
  18. Why does the Comparative Architecture Table include Project Loom despite it being JVM-hosted, not Rust — what load-bearing dimension makes the comparison valid anyway? (§33, §2)
  19. Using §30's M1/M2 and §34's derived per-core throughput ceiling, explain why context-switch latency, not coroutine count, is described as "the one defining property" in §4. (§4, §30, §34)
  20. Why does the C ABI (helios-c-abi) version independently from the Rust crate, and what specific compatibility guarantee would break if it did not? (§27, §9 ADR-19)
  21. Why does the C ABI redact panic-message strings from metric labels (ADR-27) while still logging them in full elsewhere — what failure mode does the split serve? (§26, §9 ADR-27)
  22. Why is coroutine-local storage explicitly not provided (ADR-26), and what does a caller do instead to get equivalent behavior? (§9 ADR-26, §25 T4/FM-5)
  23. I15 requires switch_to to check the target's state before switching; I2 requires an analogous check inside resume(). Are these the same invariant expressed twice, or two distinct ones — and why does each API need its own? (§16, §17, §7 I2/I15)

32. Mental Models & First Principles

  1. MM1 — A coroutine is a saved (SP, IP, registers) triple, not a thread. Predicts: switch cost is bounded by register-file size, not OS scheduling overhead. Bug class without it: assuming a coroutine switch costs ~1–2 µs (an OS thread's context-switch order of magnitude) instead of the actual ~10–60 ns (M1/M2), leading to unnecessary batching to "amortize" a cost that barely exists. Applied in §8.2, §13.
  2. MM2 — Cooperative scheduling means the coroutine, not the runtime, owns the safe point. Predicts: any code path with no yield is atomic with respect to every other coroutine on that worker. Bug class without it: adding defensive locking around code that cannot actually be preempted mid-computation (P2). Applied in §6 (P2), §19.
  3. MM3 — A guard page turns "undefined" into "detected." Predicts: overflow becomes a typed, attributable event (Panicked(StackOverflow)) rather than silent heap corruption. Bug class without it: treating stack overflow as an unrecoverable crash rather than a specific, recoverable, per-coroutine event. Applied in §18, I3.
  4. MM4 — Work-stealing is a load balancer with no coordinator. Predicts: throughput degrades gracefully, not catastrophically, under uneven load, because idle workers self-organize toward busy ones with no central scheduler. Bug class without it: manually pre-partitioning work "to balance load" when the scheduler already does this for free (§19, ADR-04). Applied in §19.
  5. MM5 — Pinning is a promise about identity, not a promise about speed. Predicts: a pinned coroutine may run slower under imbalance but never observes the wrong thread's TLS. Bug class without it: treating migratable: false as a performance knob to "optimize away," reintroducing TLS-affinity bugs (ADR-10). Applied in §19.6, P9.
  6. MM6 — A channel handoff is a rendezvous, not a mailbox. Predicts: a capacity-0 channel behaves as a direct control transfer with no buffer allocation at all. Bug class without it: assuming every send touches a buffer, missing why a parked-receiver handoff is faster than the buffered path (§20.2). Applied in §20.
  7. MM7 — Cancellation is a question the coroutine answers, not an order it obeys instantly. Predicts: cancellation latency is bounded by time-to-next-yield-point, never zero. Bug class without it: racing on the assumption that cancel() takes effect synchronously (§22, P8). Applied in §22.
  8. MM8 — The context-switch routine is the one place where "the compiler would have caught it" is false. Predicts: register-save bugs concentrate exactly here and nowhere else in the codebase, which is why the two-reviewer rule (I5) exists specifically for .s diffs and nowhere else. Bug class without it: applying normal Rust-safety confidence to assembly review, under-scrutinizing the one place that needs the most. Applied in §13, I5, P10.
  9. MM9 — A C-ABI handle is a capability, not a pointer. Predicts: the handle table (I17) can invalidate a handle without the C caller's copy becoming a dangling pointer that crashes on next use — it becomes a checked, rejected capability instead. Bug class without it: treating the handle as a raw pointer and skipping the invalidity check, reintroducing use-after-free at the FFI boundary. Applied in §10 (helios-c-abi), I17.
  10. MM10 — Determinism is recorded, not inferred. Predicts: a replay's fidelity depends entirely on what the op-log actually captured (I13) — any unseeded randomness silently escapes replay's guarantee. Bug class without it: assuming "the scheduler is deterministic" as a property of the algorithm alone, missing that an unseeded timer read or an OS-provided random value breaks it. Applied in §19, I13, FM-9 (§25).

5. Required Reading

Books

  • Knuth, D. The Art of Computer Programming, Vol. 1: Fundamental Algorithms, 3rd ed. Ch. 1.4.2 (Coroutines). Extract: the original formalization of a coroutine as a "generalized subroutine" with symmetric control transfer. Applied in §8 (Domain Model), §16 (Phase 4).
  • Tanenbaum, A.S. & Bos, H. Modern Operating Systems, 4th ed. Ch. 2 (Processes and Threads); Ch. 10 (Linux case study — signals, mmap). Extract: the thread/process scheduling vocabulary and the Linux signal-delivery model. Applied in §18 (Phase 6), §19 (Phase 7).
  • Silberschatz, A., Galvin, P., Gagne, G. Operating System Concepts, 10th ed. Ch. 4 (Threads & Concurrency). Extract: the 1:1 / N:1 / M:N threading-model taxonomy ADR-04 draws from directly. Applied in §19 (Phase 7), ADR-04 (§9).
  • Herlihy, M. & Shavit, N. The Art of Multiprocessor Programming, revised ed. Ch. 11 (Concurrent stacks/queues); Ch. 16 (Futures & scheduling). Extract: the correctness argument behind a lock-free work-stealing deque. Applied in §19 (Phase 7), ADR-04 (§9).
  • Hennessy, J. & Patterson, D. Computer Architecture: A Quantitative Approach, 6th ed. Ch. 2 (Memory hierarchy); ISA calling-convention appendix. Extract: the register-file/cache-line cost model behind I6 and M1. Applied in §8 (Domain Model), §30 (Performance Engineering).
  • Blandy, J., Orendorff, J., Tindall, L.F. Programming Rust, 2nd ed. Ch. 5 (References — the aliasing model); Ch. 21 (Foreign Functions). Extract: the safety-comment discipline behind P10 and helios-asm's FFI boundary. Applied in §11 (Core Schema & Types), §13 (Phase 1).
  • Butenhof, D.R. Programming with POSIX Threads. Addison-Wesley, 1997. Ch. 5 (Synchronization), Ch. 6 (Scheduling). Extract: the POSIX threading/scheduling model this project's Mutex/RwLock/Semaphore naming and semantics deliberately parallel. Applied in §21 (Phase 9), ADR-14 (§9).
  • Love, R. Linux Kernel Development, 3rd ed. Ch. 7 (Interrupts and Interrupt Handlers). Extract: the kernel-side discipline for code that must not allocate or block, directly analogous to the SIGSEGV handler's constraints. Applied in §18 (Phase 6), I9 (§7).

Papers

  • Conway, M.E. "Design of a Separable Transition-Diagram Compiler." CACM 6(7), 1963. Coined "coroutine." Applied in §2, §8.
  • Marlin, C.D. Coroutines: A Programming Methodology, a Language Design and an Implementation. LNCS 95, Springer, 1980. Grounds the symmetric-vs-asymmetric taxonomy. Applied in §8, §16–§17 (Phases 4–5), ADR-07 (§9).
  • de Moura, A.L. & Ierusalimschy, R. "Revisiting Coroutines." ACM TOPLAS 31(2), 2009. The full/semi/symmetric/asymmetric coroutine taxonomy; grounds Lua's design. Applied in §8, ADR-07 (§9), §17 (Phase 5).
  • Adya, A., Howell, J., Theimer, M., Bolosky, W.J., Douceur, J.R. "Cooperative Task Management Without Manual Stack Management." USENIX ATC, 2002. The Microsoft Research fibers-over-continuations design; direct ancestor of "fiber" terminology. Applied in §17 (Phase 5).
  • von Behren, R., Condit, J., Zhou, F., Necula, G.C., Brewer, E. "Capriccio: Scalable Threads for Internet Services." SOSP, 2003. Dynamic stack growth for user-level threads at scale. Applied in §15 (Phase 3), ADR-05 (§9).
  • Karsten, M. & Barghi, S. "User-Level Threading: Have Your Cake and Eat It Too." ACM SIGMETRICS, 2020 (libfibre). Measured M:N throughput vs. 1:1 and async models. Applied in §19 (Phase 7), §33 (Comparative Architecture).
  • Chase, D. & Lev, Y. "Dynamic Circular Work-Stealing Deque." SPAA, 2005. The lock-free work-stealing deque this project's scheduler implements. Applied in §19 (Phase 7), ADR-04 (§9).
  • Blumofe, R.D. & Leiserson, C.E. "Scheduling Multithreaded Computations by Work Stealing." JACM 46(5), 1999. The theoretical space/time bound for work-stealing schedulers. Applied in §19 (Phase 7), §31 (Scalability Analysis).
  • Hoare, C.A.R. "Communicating Sequential Processes." CACM 21(8), 1978. The CSP model behind the channel design. Applied in §20 (Phase 8), ADR-08 (§9).
  • Pressler, R., Rose, A. et al. JEP 444: Virtual Threads. OpenJDK, 2023. Production-scale stackful "virtual thread" design and its documented pinning limitations (JNI, synchronized). Applied in §17 (Phase 5), §22 (Phase 10), §33 (Comparative Architecture).
  • Bershad, B.N., Anderson, T.E., Lazowska, E.D., Levy, H.M. "Scheduler Activations: Effective Kernel Support for the User-Level Management of Parallelism." ACM TOCS 10(1), 1992. The kernel/user-level threading split that motivates why this project's scheduler lives entirely in userspace rather than requiring kernel cooperation. Applied in §19 (Phase 7), §9 ADR-04.
  • Ousterhout, J. "Why Threads Are a Bad Idea (for most purposes)." USENIX Winter Technical Conference invited talk, 1996. The classic argument for cooperative/event-driven concurrency over raw OS threads — the same argument this project's ADR-03 draws on for cooperative scheduling. Applied in §6 (P2), §9 ADR-03.

Reference Implementations

  • Go runtime — src/runtime/proc.go, src/runtime/stack.go. Lesson: the M:N scheduler and copying/growable-stack design. Pitfall not to copy: growable stacks require precise-GC pointer tracking to relocate; do not attempt them (§15, ADR-05) without an equivalent pointer-tracking story. Applied in §15 (Phase 3), §19 (Phase 7), §33.
  • Lua reference implementation — lstate.c, ldo.c (lua_resume/lua_yield). Lesson: the cleanest asymmetric-coroutine API surface. Pitfall not to copy: Lua's coroutines are single-threaded only — do not assume the API generalizes to an M:N scheduler without the scheduler layer. Applied in §16 (Phase 4), §33.
  • Boost.Context (boostorg/context, per-arch asm/*.S) + Boost.Coroutine2. Lesson: per-arch context-switch calling-convention handling. Pitfall not to copy: its API is a C++ template surface, not portable to a Rust FFI boundary as-is. Applied in §13 (Phase 1), ADR-01/ADR-19 (§9).
  • libtask (Russ Cox, 0intro/libtask, swtch.S, task.c). Lesson: the smallest legible production-grade stackful-coroutine reference. Pitfall not to copy: it ships no stack-overflow guard page — do not skip §18's guard-page work assuming libtask's simplicity suffices. Applied in §13 (Phase 1), ADR-19 (§9).
  • libdill/libmill (Martin Sústrik, sustrik/libdill). Lesson: CSP channel semantics (chmake/chsend/chrecv) over stackful coroutines in C. Pitfall not to copy: its channels default to unbuffered, unlike this project's bounded-buffered default (ADR-08) — do not conflate the two when porting fixtures. Applied in §20 (Phase 8).
  • may crate (Xudong-Huang/may). Lesson: Rust-specific stack-pool and generator-macro ergonomics. Pitfall not to copy: its stack-size-guessing heuristic is a documented source of its own overflow bugs — this project uses a fixed default (ADR-20) instead. Applied in §14 (Phase 2), ADR-20 (§9).
  • Tokio runtime — tokio/src/runtime/scheduler/multi_thread/. Lesson: a production Rust work-stealing scheduler's runqueue/injector/steal topology, directly comparable to this project's own (§19). Pitfall not to copy: Tokio's tasks are stackless futures, not stackful coroutines — its steal unit is a Future::poll call, not a full context switch; do not conflate the two cost models when benchmarking (§23.7). Applied in §19 (Phase 7), §9 ADR-12.
  • Erlang/OTP BEAM scheduler — erts/emulator/beam/erl_process.c. Lesson: a per-scheduler run-queue design with reduction-counting for fairness, the closest real-world analogue to a preemption-adjacent budget without full signal-based preemption. Pitfall not to copy: BEAM processes have per-process heaps and no shared mutable state at all — do not assume this project's shared-address-space coroutines get BEAM's isolation guarantees for free. Applied in §19 (Phase 7), §33 (Comparative Architecture).

RFCs / Specifications

  • System V Application Binary Interface, AMD64 Architecture Processor Supplement (x86-64 SysV ABI). Applied in §13 (Phase 1), §8.
  • Microsoft x64 Software Conventions (Windows x64 calling convention). Applied in §13 (Phase 1).
  • ARM Architecture Procedure Call Standard (AAPCS64). Applied in §13 (Phase 1), §8.

  • POSIX/Linux mmap(2), mprotect(2). The stack-mapping and guard-page primitives. Applied in §14 (Phase 2).

Glossary (§38) · 58 terms · site-wide glossary

AAPCS64
ARM's 64-bit Procedure Call Standard; defines aarch64 callee/caller-saved registers and argument passing.
Asymmetric coroutine
A parent/child control-transfer model; the child yields back to its resumer (Coroutine<R,Y>, §16).
Async-signal-safety
The restricted set of operations (per signal-safety(7)) safe to call inside a signal handler; excludes malloc.
Backpressure
A producer being slowed or blocked because a consumer/buffer cannot keep up; delegated to the caller for unbounded channels (ADR-08).
Blast radius
The scope of a fault's impact; this project's target is one coroutine or one worker, never the whole process (§4).
Boost.Context
The C++ reference library for per-architecture context switching (§5).
Bounded channel
A channel with a fixed ring-buffer capacity; blocks the sender when full (§20.2).
Callee-saved register
A register the called function must preserve across a call; the set saved by swap() (§8.2).
Caller-saved register
A register the caller must save itself if it needs the value preserved across a call.
Cache line
The unit of cache coherence transfer (typically 64 B); the size CoroutineHeader is bounded to (I6).
Cancellation token
A shared flag (Token, §11) observed at every yield point (I7).
Chase-Lev deque
A lock-free double-ended queue supporting owner-side LIFO pop and thief-side FIFO steal (§5, §19).
Context switch
The act of saving one execution context's registers/SP and loading another's (§8.2).
Coroutine
A suspendable, resumable unit of execution with its own stack (this project's stackful model, §8.1).
CSP
Communicating Sequential Processes (Hoare 1978); the channel-based IPC model (§20, ADR-08).
Fiber
A symmetric coroutine; transfers control to another named fiber with no implicit return (§17).
False sharing
Cache-line contention between unrelated data (e.g., a deque's top/bottom) placed too close in memory; avoided by explicit layout (§19.7, §20.7).
Guard page
A PROT_NONE-protected page at a stack's low address that converts overflow into a detectable fault (I3, §18).
Half-stealing
A work-stealing heuristic taking half of a victim's remaining queue per steal, amortizing the round-trip cost (§19.2, Chase & Lev 2005).
Injector (global injection queue)
The scheduler's shared queue for cross-thread spawns not yet claimed by any worker (§19).
libdill / libmill
Martin Sústrik's C CSP-over-stackful-coroutines libraries (§5).
libtask
Russ Cox's minimal production-grade stackful-coroutine reference library (§5).
Loom
A Rust concurrency model-checker exhaustively exploring thread interleavings at small thread counts (ADR-14).
M:N scheduling
Multiplexing M coroutines onto N OS threads (§8.4, ADR-04).
Migration
Moving a coroutine's execution from one OS worker thread to another (§19.6, ADR-10).
Op-log
The recorded sequence of scheduling decisions used to drive a deterministic replay (I13).
Parker/parking
The mechanism by which an idle worker or blocked coroutine suspends until woken (§19, §20).
Pinned / pinning
A coroutine restricted to its last-run worker thread; the default posture (P9, ADR-10).
Preemption
A forced context switch imposed by the runtime rather than requested by the coroutine (rejected by ADR-03; P2).
Project Loom
The JVM's virtual-threads project (JEP 444, §5, §33).
Red zone
The 128-byte region below rsp on x86-64 SysV a leaf function may use without adjusting the stack pointer (I5).
Rendezvous channel
A capacity-0 channel where every send must find a parked receiver or park itself (§20.8).
Replay harness
The (seed, op-log) mechanism reproducing a run bit-for-bit for offline debugging (I13, §28).
RwLock
A reader/writer lock; write-preferring by default in this project (§21.2).
Runqueue
A worker's local task queue (a Chase-Lev deque) (§19).
Semaphore
A counting synchronization primitive bounding concurrent permit holders (§21).
SIGSEGV
The POSIX signal delivered on an invalid memory access, including a guard-page fault (§18).
sigaltstack
The POSIX mechanism for running a signal handler on a separate stack from the faulting context (§18.2).
Stackful
A coroutine model where each unit owns a full, independent call stack (§8.1, ADR-02).
Stackless
A coroutine model compiled to a heap- or caller-allocated state machine with no independent stack (§8.1, ADR-02, rank-129).
Symmetric coroutine
A control-transfer model with no parent/child relationship; any unit may transfer to any other (Fiber, §17).
SysV ABI
The System V AMD64 calling convention used on Linux/macOS/BSD (§8.2, §5).
TLS (thread-local storage)
Per-OS-thread data (accessed via fs/gs on x86-64, tpidr_el0 on aarch64) not swapped by swap() (§8.2, T4/FM-5).
Trampoline
The synthetic-frame entry stub that starts a coroutine's entry function and calls coroutine_exit() on its return (§13.2).
Unbounded channel
A channel with no fixed capacity; send never blocks, backpressure delegated to the caller (§20.2).
WaitGroup
A counter-based primitive blocking until N done() calls match N add() calls (§21).
Work-stealing
A scheduling discipline where idle workers take tasks from busy peers' queues (§19, ADR-04).
Write-preferring
An RwLock fairness policy where a queued writer blocks new readers, avoiding writer starvation (§21.2).
Yield
A coroutine's voluntary suspension, returning control to its resumer or the scheduler (§16, §22).
Capability (handle)
A checked, revocable reference (as opposed to a raw pointer) — the model helios-c-abi handles follow (I17, MM9).
Cardinality (metric label)
The number of distinct values a metric label can take; unbounded cardinality (e.g., a raw panic string) degrades a metrics backend (T14, ADR-27).
Coroutine-local storage (CLS)
A hypothetical per-coroutine analogue to thread-local storage; explicitly not provided (ADR-26).
Handle table
The pre-allocated, lock-free table mapping opaque C-ABI handles to internal Rust state, and the sole enforcement point for I17.
Redaction
Withholding a value (e.g., a panic message) from a context where its unbounded cardinality would cause harm, while still recording it elsewhere (ADR-27).
Scheduler activations
A kernel/user-level threading design (Bershad et al. 1992, §5) in which the kernel notifies user-space of blocking events; contrasted with this project's fully userspace scheduler (§19).
Use-after-free
Dereferencing memory after it has been freed/retired; the defect class I1/I12/I17 exist specifically to make unrepresentable or detectable.
Vendoring
Committing a dependency's source directly into a repository rather than resolving it via a package registry at build time (ADR-28).
Zero-on-retire
The pool discipline of zeroing a stack's contents before returning it to the free list (I10, §14).
