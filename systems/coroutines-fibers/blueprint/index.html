131 — Coroutines / Green Threads / Fibers

Project Number: 131

Project Name: Coroutines / Green Threads / Fibers

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build helios: a stackful-coroutine (green-thread / fiber) runtime for Rust — a per-architecture assembly context-switch primitive, a stack-allocation subsystem (mmap'd fixed stacks now; segmented/growable deferred), an asymmetric Coroutine<R,Y> API and a symmetric Fiber API sharing one context-switch primitive, an M:N work-stealing scheduler multiplexing coroutines onto OS threads, CSP-style channels, coroutine-aware synchronization primitives, cooperative cancellation, guard-page stack-overflow detection, and a bridge into an external async/await runtime (rank-129) so a coroutine can await a future and a future can drive a coroutine to completion.

Phase-0 in-scope deliverable (numbered):

  1. helios — public facade crate: Coroutine<R,Y>, error types, crate-root re-exports.
  2. helios-asm — x86-64 SysV context-switch assembly + Rust FFI shim (other arches follow in Phase 1, §13).
  3. helios-stack — fixed-size mmap'd stack allocator with guard page.
  4. helios-scheduler — single-thread run loop (M:N arrives in Phase 7, §19).
  5. helios-channel — one bounded channel type.
  6. helios-cli — a debug CLI dumping live coroutine state.

System boundaries:

  • Provides: context switching; stack lifecycle (allocate / guard / retire); cooperative scheduling; cancellation; channels; sync primitives; one async-bridge direction pair.
  • Delegates: OS-thread creation to std::thread; async I/O polling to the external rank-129 runtime (not reimplemented here); non-stack heap allocation to the global allocator.
  • Does NOT provide: a garbage collector; a language-level compiler transform (this is a library — contrast rank-129's compiler-driven state machines); preemptive scheduling (P2, §6); a distributed/cross-process coroutine model.

Non-goals: a WASM compilation target (Deferred Features Register, §37); a JIT; a cross-language ABI beyond the C shim (helios-c-abi, §10).

Deployment model: a linked Rust library (optional cdylib for C embedders, ADR-19); no server component; runs inside the host process's address space.

Target users / operators: Rust systems engineers building high-concurrency services (proxies, connection poolers, simulation engines, request handlers) needing CPU-bound-friendly lightweight concurrency without adopting a whole-program async/await transform.

What later phases unlock: Phase 2 (§14) unlocks a bounded per-coroutine memory footprint at scale; Phase 7 (§19) unlocks horizontal scheduling across cores; Phase 11 (§23) unlocks interop with the existing async ecosystem.

Recommended language: Rust 2024 edition, per-architecture assembly emitted via global_asm!. Rationale: the ownership model documents the aliasing contract across the unsafe boundary (§11, P10); the ecosystem (tokio, rank-129) is Rust-native, so the bridge (§23) needs no cross-language FFI. Rejected languages: C — no borrow checker, and the context-switch boundary is exactly where use-after-free bugs concentrate, with no tool to contain them; C++ (Boost.Context) — mature (§9 ADR-01) but the explicit goal is a Rust-native primitive the Rust ecosystem can depend on without a C++ toolchain; Go — the goroutine model is excellent but is a language feature, not a library, and cannot be retrofitted onto an existing Rust codebase.

Prerequisites: calling-convention literacy (register classes, stack alignment, ABI argument passing); signal handling (sigaction, sigaltstack); virtual memory (mmap, mprotect, page-fault delivery); the async/await state-machine model (needed to build the bridge, §23).

Estimated timeline: Phase 0 in 1–2 weeks; the full system (Phases 0–11) in 5–6 months at one senior-engineer FTE.

Deferred features (full table in the Deferred Features Register, §37): segmented stacks PhaseDeferred("§15"); growable/copying stacks PhaseDeferred("§15"); signal-based preemption PhaseDeferred("§37"); TLS-aware migration PhaseDeferred("§37"); a WASM compilation target PhaseDeferred("§37"); OSS-Fuzz continuous fuzzing PhaseDeferred("§37"); NUMA-aware stack-pool placement PhaseDeferred("§37").

2. Why Build This

A coroutine runtime is the canonical system where the central insight — swap the stack pointer, save/restore the callee-saved registers, ret into the new stack's return address — is thirty lines of assembly, and the production-grade version is a multi-month systems project: an assembly routine correct across four ABIs; a stack allocator that survives "this coroutine needs more stack" without invalidating live pointers; an M:N scheduler that does not thrash cache lines under work-stealing; a cancellation discipline that survives cross-thread migration; a guard-page scheme that turns a wild stack write into a clean error instead of a corrupted heap; and an interoperability story with the async/await ecosystem the rest of the industry already standardized on.

It teaches, in one focused artifact, the full stack of "what a thread actually is": the ABI-level contract every OS scheduler, debugger, and unwinder relies on (§8); the memory-management tradeoffs behind every user-level threading system since coroutines were named (Conway 1963, §5); the scheduling theory (work-stealing, Blumofe & Leiserson 1999, §5) that underlies every modern task-parallel runtime, including the one already blueprinted at rank-129 and rank-128; and the hard boundary between "safe Rust" and "the thirty lines where safety is a comment, not a compiler guarantee" (P10, §11).

Architecturally it matters because it is the load-bearing counter-example to the industry's current default answer ("just use async/await"): async/await (rank-129) solves I/O-bound concurrency at near-zero memory cost but cannot call blocking or recursive-FFI code without "function coloring" spreading through the codebase; OS threads solve the calling-convention problem for free but cost 1 KiB–8 MiB of stack per unit and do not scale past low tens of thousands; stackful coroutines are the answer when a workload needs both "call arbitrary blocking code" and "spawn hundreds of thousands of units" — which is exactly the niche Go's goroutines, Java's Project Loom virtual threads, and Lua's coroutines each independently rediscovered.

The engineering muscles this builds: reading and implementing an ABI specification exactly (§13); reasoning about a lock-free work-stealing deque's memory-ordering guarantees (§19, Chase & Lev 2005); writing an async-signal-safe interrupt handler (§18); and building a deterministic replay harness for a genuinely nondeterministic concurrent system (I13, §7) — a technique that transfers directly to debugging any production scheduler, not just this one.

Cross-links to sibling systems: rank-129 (the async/await runtime this project bridges into, §23); rank-128 (the work-stealing task-parallel runtime whose Chase-Lev deque design this project's scheduler, §19, shares); Erlang/BEAM-style actor runtimes (a cross-link the Comparative Architecture Table, §33, makes explicit); Project Loom (the JVM's own stackful-coroutine answer to the same problem, also compared in §33).

Calibration value: a team that ships this correctly can be trusted with any systems-level concurrency primitive — the context switch (§13) is unforgiving in a way that punishes hand-waving immediately (a wrong register in the save/restore list corrupts silently until the specific code path that uses that register runs), which is precisely why it calibrates engineering judgment better than a higher-level abstraction would.

What Mastery Looks Like — after building this, an engineer can:

  • Write and review a per-architecture context-switch routine against its ABI specification from memory, and explain exactly which registers are callee-saved on x86-64 SysV, aarch64 AAPCS64, and RISC-V (Phase 1, §13).
  • Explain, with the actual numbers, why Go's stacks start at 2 KiB and grow, while this project's start at 64 KiB and do not (without opting into growable stacks) — and what type-system machinery Go's precise GC gives it that Rust does not (Phase 2–3, §14–§15).
  • Design a work-stealing scheduler's runqueue/injector/steal topology and reason about its cache-line traffic under contention (Phase 7, §19).
  • Write an async-signal-safe SIGSEGV handler and explain exactly which libc calls are forbidden inside it and why (Phase 6, §18).
  • Reason precisely about the difference between cooperative and preemptive scheduling, including the concrete failure mode each avoids and introduces (Phase 0 onward, P2/P3, §6).
  • Bridge two fundamentally different concurrency models (stackful coroutines and stackless async/await) without either one silently corrupting the other's invariants — in particular the Pin discipline across a suspension point (Phase 11, §23).
  • Build and use a deterministic replay harness to debug a concurrency bug that is not reliably reproducible live (Phase 0 onward, I13, §7).

Six boxes, six invariants they must jointly uphold. User code never touches raw stack pointers or registers — every unsafe operation is behind the facade (P10). helios (facade) owns the type-state (CoroutineResult<R,Y>, §11) and is the only crate without unsafe. helios-scheduler owns exactly the state machine in §8's state table and the work-stealing topology of ADR-04; it is the trust boundary between "logically running" and "physically on some OS thread." helios-stack / helios-asm / helios-overflow are peers, not a stack: helios-asm's swap() is called by the scheduler on every transition; helios-stack supplies the memory swap() transitions into; helios-overflow is a side-channel (the SIGSEGV path) that converts a fault inside memory helios-stack allocated into a scheduler-visible Panicked state — this is a concurrency boundary (a signal handler runs asynchronously with respect to the faulting coroutine) as well as a persistence-adjacent boundary (the guard page is a page-table entry, not heap state). helios-channel / helios-sync are the only queues/wait-lists in the diagram; every parked coroutine is on exactly one of their wait lists (I4). helios-cancel is a cross-cutting concern observed by every yield point in every box above it, not a separate pipeline stage. helios-async-bridge is the sole external interface, a protocol boundary to a different runtime's task model (rank-129); everything left of it is this project's; everything right of it is rank-129's, per §1's system boundary.

The crate-naming convention helios-* is normative and reused verbatim in the Repository Layout (§10) and Core Schema & Types (§11).

6. Design Principles

  1. P1 — Stackful primacy. A helios coroutine owns a full stack and may call arbitrary blocking/FFI code at any depth. Tradeoff: memory-per-coroutine (64 KiB default, ADR-20) vs. stackless's near-zero footprint. Operational implication: capacity planning is stack-count × stack-size (§34), not "however many tasks fit in one allocation." Violating it (e.g., trying to shrink stacks below the point recursive Rust code needs) reintroduces the exact overflow class §18 exists to catch.
  2. P2 — Cooperative, not preemptive, scheduling. No forced context switch; yield points are explicit. Tradeoff: a non-yielding coroutine monopolizes its worker. Operational implication: the yield-budget tracer (ADR-23) is mandatory, not optional, in production. Violating it (silently adding preemption) reintroduces the async-signal-safety hazard class P2 was written to avoid.
  3. P3 — M:N over 1:1. Coroutine count is decoupled from OS-thread count. Tradeoff: scheduler complexity (runqueue/injector/steal, §19) vs. thread-per-coroutine simplicity. Operational implication: the scheduler, not the OS, is the throughput bottleneck to profile. Violating it (falling back to 1:1) reintroduces the multi-KiB-to-MiB per-unit OS-thread cost this project exists to eliminate (§33).
  4. P4 — One context-switch primitive, two APIs. Coroutine (asymmetric) and Fiber (symmetric) share one assembly swap(). Tradeoff: API-surface duplication vs. a single audited primitive. Operational implication: every context-switch bugfix lands once, not twice. Violating it (a second hand-rolled switch routine) doubles the two-reviewer assembly-audit burden (ADR-07).
  5. P5 — Stacks are mmap'd, never malloc'd. Every stack is its own VM mapping with a trailing guard page. Tradeoff: an mmap syscall (~5 µs) per fresh allocation vs. heap-adjacency safety. Operational implication: the stack pool (ADR-21) exists specifically to amortize this cost. Violating it (malloc'd stacks) turns every overflow into silent heap corruption instead of a clean fault.
  6. P6 — Guard page over software canary. Rely on hardware page-fault trapping, not a per-call canary check, to catch overflow. Tradeoff: canaries catch overflow one write early but cost a check per frame; guard pages are free until faulted. Operational implication: overflow detection latency is "at the faulting instruction," not "at the next canary check." Violating it (canary-only) misses the single-huge-frame overflow class guard pages catch for free.
  7. P7 — CSP channels as the primary IPC. Coroutines communicate over channels by convention, not shared mutable state. Tradeoff: a channel-send/recv cost (M5, §30) vs. lock-free shared-state races. Operational implication: code review flags raw shared Mutex<T> used as an ad hoc channel. Violating it reintroduces exactly the races CSP (Hoare 1978, §5) was designed to make unrepresentable.
  8. P8 — Cancellation is cooperative, observed at yield points. No forced unwind from an arbitrary instruction. Tradeoff: a non-yielding coroutine is uncancellable until its next yield. Operational implication: the grace-period force-terminate (§22.6) is the escape hatch, not the default. Violating it (forced unwind) corrupts invariants a coroutine's unwound callees held mid-operation.
  9. P9 — Migration is opt-in; pinning is the default. A coroutine stays on its last-run worker unless explicitly marked migratable. Tradeoff: pinning forgoes some steal opportunities (§31) vs. migration risking TLS/FFI-affinity bugs. Operational implication: an FFI call that depends on thread-local state must run inside a pinned coroutine. Violating it (always-migratable default) reproduces the exact TLS-affinity bug class ADR-10 documents.
  10. P10 — Unsafe is boundary-scoped, and paired with a safety comment. Every unsafe block outside helios-asm/helios-stack is a defect (§10). Tradeoff: review velocity vs. auditability. Operational implication: #![forbid(unsafe_code)] on every crate except the two named. Violating it (unsafe leaking into helios-scheduler, say) removes the single audit boundary the whole safety argument depends on.
  11. P11 — No global mutable state. A Scheduler is a value; multiple coexist in one process. Tradeoff: callers thread a handle explicitly vs. singleton convenience. Operational implication: a test harness and the production app can each own an independent scheduler in the same process (useful for embedding, §33). Violating it (a process-global scheduler) collides two independently-configured subsystems the moment both exist.
  12. P12 — Determinism via the replay harness. A fixed scheduler seed plus a recorded op-log reproduces a run bit-for-bit (I13). Tradeoff: op-log recording overhead vs. debuggability. Operational implication: production incidents ship with a replayable op-log, not just a stack trace. Violating it (no replay support) makes a one-in-a-million interleaving bug effectively undebuggable.
  13. P13 — The C ABI is a first-class embedder surface. helios-c-abi is versioned and documented like the Rust API, binary-compatible with libtask's surface where shapes overlap (ADR-19). Tradeoff: maintaining a second, stability-locked surface. Operational implication: a C/C++ embedder's upgrade path is covered by the same Compatibility & Versioning policy (§27) as the Rust API. Violating it (Rust-only) forecloses exactly the embedder audience Boost.Context and libtask already serve.
  14. P14 — Performance targets are CI-gated, not aspirational. Every M# target (§30) has a criterion benchmark that fails the build on regression (ADR-16). Tradeoff: CI wall-clock time vs. undetected regressions. Operational implication: a context-switch regression is caught before merge, not after a customer's perf audit. Violating it (aspirational-only targets) is the exact failure mode that eroded confidence in early user-thread libraries industry-wide.

8. Domain Model

8.1 Stackful vs. stackless

A stackless coroutine (rank-129's model) is compiled to a state machine: local variables that live across a suspension point become struct fields; the "stack" is that struct, heap- or caller-allocated. A stackful coroutine (this project) keeps an ordinary call stack; suspension is a register-and-stack-pointer swap, not a compiler transform. Consequence (de Moura & Ierusalimschy 2009, §5): stackful coroutines can suspend from any call depth, including inside a blocking C FFI call; stackless coroutines can only suspend where the compiler inserted a suspension point, and a blocking call anywhere in that chain blocks the entire executor thread.

8.2 The context switch: registers, stack, SP, IP

A context switch is extern "C" fn swap(from: *mut Context, to: *const Context), called with from and to as ordinary ABI arguments. Effect: save the caller's callee-saved registers and current sp into *from; load sp and callee-saved registers from *to; ret — which pops the new stack's saved return address into ip, transferring control.

Arch/ABI Callee-saved (saved by swap) Caller-saved (not touched) Arg regs (1st two: from,to) Stack align at call
x86-64 SysV rbx, rbp, r12–r15, rsp rax, rcx, rdx, rsi, rdi, r8–r11, xmm0–15 rdi, rsi 16B (rsp ≡ 8 mod 16 at entry)
x86-64 Windows x64 rbx, rbp, rdi, rsi, r12–r15, rsp, xmm6–15 rax, rcx, rdx, r8–r11, xmm0–5 rcx, rdx 16B
aarch64 AAPCS64 x19–x30, sp, d8–d15 (low 64b of v8–v15) x0–x18, v0–v7, v16–v31 x0, x1 16B
riscv64 (LP64D) s0–s11, sp a0–a7, t0–t6, ra a0, a1 16B

Malformed input: a to context whose sp does not point into a live, guard-paged stack region (a use-after-retire) — swap() performs no validation (it cannot; it is a handful of instructions with no room for a check) so this class is prevented upstream by I1/I12's ownership discipline, not detected in the routine itself. Failure path: if prevention fails, the ret transfers control into freed or foreign memory — undefined behavior, not a clean fault; this is why I1/I12 are compile-time-enforced ownership invariants rather than runtime checks (§7).

8.4 The scheduler and M:N mapping

State table (coroutine lifecycle, referenced by I2, I4, I11):

From Event To
— Coroutine::new Ready
Ready scheduled onto a worker Running
Running yield_value / entry returns normally Yielded / Done
Running blocks on channel/mutex/cancel-wait Blocked
Running guard-page fault Panicked
Yielded resume() called again Running
Blocked wait condition satisfied, re-queued Ready
Done/Panicked (terminal) —

M:N mapping worked example: 4 OS worker threads (N=4), 12 coroutines (M=12) spawned at once onto the global injector. Each worker pops up to 3 from the injector into its local Chase-Lev deque. Worker 2's 3 coroutines each do a blocking channel recv in sequence (none ready) and park; worker 2's deque empties. Per ADR-04's steal policy, worker 2 becomes a thief: it picks a random peer (say worker 0), and takes half of worker 0's remaining local queue (the "half-stealing" heuristic, Chase & Lev 2005, §5) — if worker 0 has 3 local, worker 2 steals 1 (rounding down), leaving 2. This repeats until either all coroutines are Blocked/Done or queues are balanced within one task of each other.

before:  W0:[c1 c2 c3]  W1:[c4 c5 c6]  W2:[]        W3:[c10 c11 c12]
                                        ^ empty, W2 becomes a thief
steal:   W2 targets W0, takes floor(3/2)=1 from the queue's bottom (FIFO)
after:   W0:[c2 c3]     W1:[c4 c5 c6]  W2:[c1]      W3:[c10 c11 c12]

Malformed-input example: a coroutine that calls resume() on itself re-entrantly (from inside its own entry function, holding a handle to its own Coroutine) — detected because the header's state is already Running, not Ready/Yielded; resume() returns Err(InvalidState) per I2 rather than double-switching into the same stack.

Failure-path example: a worker thread panics (a genuine Rust panic, not a coroutine Panicked state) while holding a coroutine in Running. The scheduler's worker-loop wraps each swap() round-trip in catch_unwind; on an unwind, the coroutine is marked Panicked(HostPanic), its stack is queued for retirement (I12), and the worker thread restarts fresh (empty local deque, rejoins the injector pool) rather than the whole process aborting — bounding blast radius to the one coroutine and its worker's in-flight queue, matching the 0-blast-radius constraint in §4.

8.5 Worked lifecycle trace: spawn → yield → cancel → retire

The following trace ties §8.2–§8.4 together into one concrete sequence, cross-referencing the exact invariant or subsystem responsible at each step — the level of detail an on-call engineer reconstructs from tracing spans (§26) during an incident.

Step Event Subsystem Invariant / Ref
1 Coroutine::new(entry) helios-stack::pool allocates (or reuses) a 64 KiB stack + guard page I1, I3, §14
2 Trampoline frame written to the new stack helios-asm §13.2
3 Header constructed, state = Ready helios facade I2, §11

5 Entry runs; calls yield_value(v) helios-asm::swap switches back to resumer §16.2

7 CancelHandle::cancel() called externally helios-cancel::Token flag set I7, §22.2
8 Coroutine resume()d again scheduler transitions Yielded → Running I11
9 Next yield point observes the cancel flag yield_value/park check (I7) §22.2
10 Coroutine's own code runs Drop cleanup (e.g. releases a held Mutex, §21.6) Rust's ordinary drop discipline §22.5

Malformed-input variant of this trace: if step 7's cancel is signaled before step 3 completes (a cancel-handle obtained and fired against a coroutine still mid-construction) — the Token (§11) is constructed atomically with the header in step 3, so there is no window in which a handle exists but the token does not; the cancel is simply observed at the coroutine's very first yield point instead of a later one, with no special-case handling required.

Failure-path variant: if step 4's swap() call races against step 14's retire (a resume() called concurrently with a Drop, a caller-side logic bug since a Coroutine is not Sync and cannot legally be resumed from two threads at once) — Rust's !Sync bound on Coroutine<R,Y> (a compile-time property, not listed as a separate invariant because it is enforced by the type system rather than a runtime check) makes this scenario not compile for safe callers; the only way to reach it is through unsafe misuse of the type, which places the defect inside P10's audited boundary, not this trace's steady-state path.

11. Core Schema & Types

Signatures only, per the No-Code Rule (§4 of the standard). Ownership/mutation/concurrency/persistence/serialization/compatibility noted as terse annotations.

#[repr(C, align(64))]                              // I6: one cache line
struct CoroutineHeader {
    id: CoroutineId,                                // Copy; process-unique
    state: CoroutineState,                           // owned; mutated only by scheduler (I11)
    stack: StackHandle,                               // owned, !Clone (I1); freed in Drop (I12)
    saved_ctx: *mut asm::Context,                     // null iff Ready|Done (I2); no serialization
    migratable: bool,                                 // opt-in (P9, ADR-10); read by steal (I8)
    parent: Option<CoroutineId>,                      // asymmetric only; None for Fiber
    cancel: cancel::Token,                             // observed at every yield (I7)
}

enum CoroutineState { Ready, Running, Yielded, Blocked(WaitKind), Done, Panicked(PanicKind) } // I11 transition table, §8.4

enum CoroutineResult<R, Y> { Done(R), Yielded(Y), Panicked(PanicKind) }  // tagged union; not Clone (R may not be)

struct Coroutine<R, Y> { header: CoroutineHeader, _marker: PhantomData<(R, Y)> } // owned; Drop signals Cancel (§16.3)
// impl: fn new<F>(entry: F) -> Self; fn resume(&mut self) -> CoroutineResult<R, Y>; fn resume_with(&mut self, v: Y) -> CoroutineResult<R, Y>

fn yield_value<Y>(v: Y) -> Y   // callable only from inside a running coroutine; returns the resumer's next input
struct Fiber { header: CoroutineHeader }             // owned; no parent/child link (P4)
// impl: fn spawn<F>(f: F) -> Fiber; fn switch_to(&mut self, other: &mut Fiber) -> !  // never returns to caller directly

#[repr(C)]
struct Context { sp: usize, callee_saved: [usize; MAX_CALLEE_SAVED] } // helios-asm; per-arch width; no Rust Drop (asm-owned)

struct StackHandle { base: NonNull<u8>, size: usize, guard: GuardRegion, pool_class: SizeClass } // !Clone (I1); Drop → pool::retire (I10/I12)

struct GuardRegion { addr: NonNull<u8>, len: usize } // PROT_NONE for handle lifetime (I3); read-only after install

enum StackStrategy { Fixed, Segmented, Growable }    // Fixed is Phase-0 default; others PhaseDeferred("§15")
struct Scheduler { workers: Vec<Worker>, injector: Injector<TaskRef> } // value type (P11); multiple coexist

struct Worker { id: WorkerId, local: ChaseLevDeque<TaskRef>, parker: Parker } // one per OS thread (§19)

struct Stats { live: u64, parked: u64, stolen_total: u64, stack_bytes_used: u64 } // read-only snapshot; not serialized cross-version (§27)
struct Sender<T> { inner: Arc<ChannelInner<T>> }     // Clone; Send iff T: Send (§20)
struct Receiver<T> { inner: Arc<ChannelInner<T>> }   // not Clone (single-consumer default); §20.1

fn channel<T>(capacity: usize) -> (Sender<T>, Receiver<T>)  // capacity 0 == rendezvous; unbounded via Capacity::Unbounded (§20.2)

enum ChannelError { Closed, WouldBlock }              // recv/send Result error type
struct Mutex<T> { inner: RawMutex, data: UnsafeCell<T> }   // coroutine-aware wait queue (§21.1); std::sync::Mutex-incompatible (documented, §27)
struct RwLock<T> { inner: RawRwLock, data: UnsafeCell<T> } // write-preferring default (§21.2, ADR configurable at construction)
struct Semaphore { permits: AtomicUsize, waiters: WaitQueue }
struct WaitGroup { count: AtomicI64, waiters: WaitQueue }  // panics if count goes negative (§21.4)
struct Token { flag: Arc<AtomicBool> }                // Clone; observed at yield (I7)
struct CancelHandle { token: Token }                  // clonable; `.cancel()` sets the flag
fn cancel_handle(c: &Coroutine<impl Sized, impl Sized>) -> CancelHandle
// helios-async-bridge (§23); requires the rank-129 runtime present at the call site
async fn await_future<F: Future>(fut: F) -> F::Output      // coroutine-side: yields until fut resolves
fn block_on_coroutine<R, Y>(c: Coroutine<R, Y>) -> impl Future<Output = R> // async-side: drives a coroutine to Done

Serialization: no type in this schema derives Serialize/Deserialize — the runtime has no persistence layer (§1 scope boundary; §4 storage amplification: N/A). Compatibility: Stats and the C-ABI structs (helios.h) are the only cross-version-visible types; their field order is append-only per §27.

12. Phase 0 — Repo Skeleton & Correctness Kernel

12.1 Objectives

Stand up the workspace, CI skeleton, and a single smoke-test coroutine on the host's native arch only (x86-64 SysV or aarch64, whichever the CI runner is). No scheduler, no channels — just enough to prove Coroutine::new/resume() round-trips through one context switch. This phase exists per the standard's Phase-0 rule: repo skeleton + correctness kernel.

12.2 Detailed Implementation Steps

Lay out Cargo.toml workspace members per §10's tree. Implement helios-asm's native-arch swap() first (P4: the one shared primitive), gated behind #[cfg] for the host triple only — full arch matrix lands in Phase 1 (§13). Implement helios-stack::fixed with a single fixed-size mmap (no pool, no guard page yet — guard page lands with I3 in Phase 2, §14). Implement Coroutine::new/resume() in helios sufficient to run a Fn() -> R entry to completion (no yield support yet — Yielded arrives in Phase 4, §16). Wire Makefile targets: bootstrap, build, test, lint. Wire .github/workflows/ci.yml for build+test on the host triple. Write ADR-01, ADR-02, ADR-03, ADR-11, ADR-13 (§9) as standalone docs in docs/adr/.

Additionally, this phase fixes the helios_<subsystem>_<noun>_<unit-or-total> naming convention (§26) in a docs/architecture/overview.md stub, even though no metric is emitted yet — naming the convention before any code emits telemetry avoids a Phase-7 rename that would otherwise ripple through every dashboard built in the interim.

12.3 Deliverable

cargo test -p helios passes a single smoke test: Coroutine::new(|| 42).resume() returns Done(42).

12.4 Acceptance Criteria

  • Smoke test passes on 2 consecutive CI runs with 0 flakes.
  • cargo clippy --deny warnings clean (ADR-18 baseline).
  • Workspace builds in ≤ 60 s cold on CI.
  • Fixture smoke-return-value (§12.5) passes with the exact value 42.

12.5 Conformance Fixtures

Fixture Purpose Expected Output
smoke-return-value entry returns a plain value Done(42)
smoke-panic-propagate entry panics the panic propagates out of resume() (no coroutine-level catch yet — added in §16)
smoke-zero-sized-return entry returns () Done(())

12.6 Pitfalls

  • Shipping the context switch before the CI matrix exists — the arch-specific bug classes (§9.2's table) only surface once cross-arch CI runs, so building it "on faith" for one arch hides real defects.

  • cargo-deny failing on day one because the license manifest is incomplete — resolve before Phase 1, not deferred.

  • Forgetting that helios-asm's host-native-only gating in this phase must not leak into §11's public API shape — the facade's signature is arch-independent from day one even though only one arch is wired.

  • Treating Phase 0 as throwaway scaffolding tempts skipping the CODEOWNERS/CI wiring "for now" — but §13's two-reviewer rule depends on CODEOWNERS existing before the first .s file lands, so it is cheaper to wire correctly here than to retrofit under time pressure later.

12.7 Performance Concerns

No performance gate yet (M1–M12 arrive with helios-bench in §19/§30); however, the smoke test's resume() round-trip is timed informally to catch a >10× regression before Phase 1 sets the real budget.

12.8 Edge Cases

  • An entry closure that captures a !Send value — must compile (single-threaded Phase 0, no scheduler yet) but is flagged as a Phase-7 (§19) migration hazard in a code comment.

  • A zero-size stack request — rejected at construction with a documented panic (I14).

  • A workspace member crate with a name collision against a crates.io-published crate (unlikely but checked) — resolved by the helios- prefix convention (§10) being applied from this phase onward, never retrofitted.

12.9 Failure Analysis

A failure at this phase is exclusively "does not build" or "smoke test fails" — there is no production surface yet, so blast radius is limited to CI red. Detection: CI. Containment: N/A (no deployment). Recovery: fix and re-run; no rollback machinery needed this early.

12.10 Operational Notes

No telemetry yet — tracing integration begins in Phase 7 (§19, ADR-17). BUILD_PLAN.md is updated at the end of this phase with the actual vs. estimated timeline (§1).

13. Phase 1 — Context-Switch Assembly (All Architectures)

13.1 Objectives

Extend Phase 0's single-arch swap() to the full matrix: x86-64 SysV, x86-64 Windows, aarch64 AAPCS64, riscv64 (ADR-11). Land the entry trampoline so a coroutine's first resume correctly enters its entry function with its argument.

13.2 Detailed Implementation Steps

Per §8.2's register table, write one .s file per arch/ABI pair in helios-asm/asm/ (§10). Each routine: save the callee-saved set from §8.2's table into *from, load from *to, ret (I5: never touch the outgoing red zone on x86-64 SysV — the P6/ADR-06 guard-page work in Phase 2 is unrelated and does not substitute for this). Implement the trampoline (Marlin 1980, §5, on the symmetric/asymmetric split this trampoline must support both): the new stack is pre-populated with a synthetic frame whose return address points at coroutine_trampoline_fn; the trampoline reads the entry-fn pointer and argument from a fixed stack offset, calls it, and on return calls coroutine_exit() (switches back to parent, marks Done per I2). CODEOWNERS requires two reviewers on every diff touching asm/ (P4, I5).

This phase also fixes the CODEOWNERS rule requiring two reviewers on any diff touching helios-asm/asm/*.s (I5) — a governance artifact, not code, but one that must exist before the first cross-arch PR lands, since retrofitting a review gate after a defect has already merged defeats its purpose.

13.3 Deliverable

All four arch/ABI targets pass the cross-arch smoke test in CI (arch-matrix.yml, riscv64 via qemu-user).

13.4 Acceptance Criteria

  • Context-switch round-trip measured at ≤ 30 ns p50 on x86-64, ≤ 60 ns p50 on aarch64 (M1/M2, §30) via bench_ctx_switch (helios-bench).
  • All four fixtures in §13.5 pass on their native or emulated target.
  • Two-reviewer sign-off recorded on the assembly PR (I5 enforcement).

13.5 Conformance Fixtures

Fixture Purpose Expected Output
ctx-switch-roundtrip-x86_64 switch out and back, verify all callee-saved regs unchanged register snapshot equality
ctx-switch-roundtrip-aarch64 same, aarch64 register snapshot equality
ctx-switch-simd-alignment callee uses SSE/NEON after switch no fault (16-byte alignment held)
trampoline-arg-passthrough entry fn receives the exact argument written at construction argument equality

13.6 Pitfalls

  • Forgetting xmm6–15 on Windows x64 is a silent register-corruption bug that only surfaces when the consumer uses SIMD (§9.7's table, §8.2) — caught by ctx-switch-simd-alignment.

  • Misaligning the stack to other than 16 bytes is invisible until a callee does SIMD — same fixture catches it.

  • Touching the x86-64 SysV red zone (I5) on the outgoing stack is the single most subtle defect class; the two-reviewer rule (P4) exists specifically for this.

  • The frame pointer (rbp / x29) must stay consistent across the switch — an OS profiler unwinding via frame pointer gets confused pointing at a freed stack otherwise.

  • TLS registers (fs/gs, tpidr_el0) are never swapped by swap() — a coroutine that reads TLS observes the OS thread's TLS, not "its own"; this is the seed of the migration hazard formalized in ADR-10/P9.

  • Assuming the riscv64 qemu-user timing (§13.8) is representative of bare-metal riscv64 performance is a documented trap — qemu-user's instruction-emulation overhead swamps the actual swap() cost, which is exactly why M1/M2 gate only x86-64/aarch64.

13.7 Performance Concerns

The first switch on a fresh stack is I-cache-miss-dominated (cold trampoline code); warm switches amortize this. bench_ctx_switch reports both cold and warm p50/p99 separately so a regression in either is visible (M1/M2, §30).

13.8 Edge Cases

  • A to context representing a coroutine that has already run to Done — rejected upstream by I2's state check in resume() (§16), not inside swap() itself, since swap() has no room for validation logic (§8.2 malformed-input note).

  • riscv64 under qemu-user emulation reporting different timing characteristics than bare metal — arch-matrix.yml marks riscv64 timing as informational only, not gating (M1/M2 gate x86-64/aarch64 only).

  • A host CPU lacking the SIMD extensions the SIMD-alignment fixture (§13.5) assumes (e.g., an aarch64 target without NEON, vanishingly rare in practice) — the fixture is skipped, not failed, on a target reporting the extension absent.

13.9 Failure Analysis

A wrong callee-saved register in the save/restore list corrupts state silently until the specific code path using that register executes — often far from the switch site, making this the hardest class of bug in the whole project to localize by inspection alone; the fixture suite (§13.5) is the primary defense, not code review alone (though the two-reviewer rule is the secondary defense, I5).

13.10 Operational Notes

bench_ctx_switch results are archived to benchmarks/results/ per release (§29); a regression alert fires in perf.yml (ADR-16) if p50 exceeds M1/M2 by more than 10%.

14. Phase 2 — Stack Allocation: Fixed Stacks & Pool

14.1 Objectives

Replace Phase 0's bare mmap with the production allocator: guard page (I3), size-class pool (ADR-21), zero-on-retire (I10).

14.2 Detailed Implementation Steps

Implement helios_stack::guard::install: mmap the full size + guard_size region, then mprotect(base, guard_size, PROT_NONE) at the low address (stack grows downward on all four target arches, §8.2):

high address  +---------------------------+
              |  usable stack (64 KiB)    |   <- Coroutine's SP starts here
              |  stack grows downward  ↓  |
              |                           |
low address   +---------------------------+
              |  guard page (4 KiB)       |   PROT_NONE (I3)
              +---------------------------+
``` Implement `helios_stack::pool`: a per-thread free list keyed by `SizeClass` (8 KiB / 64 KiB / 256 KiB / 1 MiB / 4 MiB, ADR-21); `retire()` zeroes the region (I10) before returning it to the free list, or `munmap`s it if the class is at its configured cap. Default stack size 64 KiB (ADR-20, chosen over Go's 8 KiB default and a full 2 MiB thread-sized stack — the rationale in ADR-20's rejected-alternatives column applies directly here).

This phase also introduces the `Stats::stack_bytes_used` field (§11) as a live gauge, even though the scheduler consuming it (§19) does not exist yet — wiring the gauge here means Phase 7's dashboard work (§26) has real data from day one rather than a placeholder.

### 14.3 Deliverable

A coroutine spawned via the pool measurably reuses a retired stack (traced via `helios_stack_allocs_total` vs pool-hit counter) instead of issuing a fresh `mmap` on every spawn.

### 14.4 Acceptance Criteria

- Pool hit rate ≥ 95% under a steady-state 10,000-coroutine churn workload (§30 M8).
- Spawn latency ≤ 1 µs p50 on pool hit, ≤ 8 µs p99 on pool miss (M3, §4).
- 1,000,000 spawned 64 KiB stacks consume ≤ 100 GiB virtual address space and ≤ 4 GiB resident (§4, §34).
- Fixture `pool-no-leak` (§14.5) shows zero bytes of prior-occupant data in a reused stack.

### 14.5 Conformance Fixtures

| Fixture | Purpose | Expected Output |
|---|---|---|
| `guard-page-protection` | verify guard region is `PROT_NONE` post-install | mapping flags match I3 |
| `pool-no-leak` | write a sentinel, retire, reallocate, read | sentinel absent (I10) |
| `pool-size-class-rounding` | request 30 KiB | rounds up to 64 KiB class |
| `pool-cap-eviction` | exceed configured cap | excess stacks `munmap`'d, not retained |

### 14.6 Pitfalls

- Guard page on the wrong side (must be low address, since our four target arches all grow the stack downward, §8.2/§8.3) — a documented note covers the (unsupported) upward-growth case explicitly so no one "fixes" this incorrectly later.
- ASLR interaction: mmap address randomization can be disabled per-process; document that guard-page detection does not depend on address predictability (I3 is a protection-bit check, not an address check).
- The pool's stack-reuse is exactly where I10 lives — skipping the zero-on-retire step to save the ~100 ns cost (§30) is a cross-tenant confidentiality leak, not a performance nit.
- Large stacks (4 MiB class) cost ~1024 TLB entries each; document the cache-pressure tradeoff explicitly in the size-class docs so operators do not default every workload to the largest class.

- Sizing the pool's per-class cap too generously "to be safe" defeats the memory-ceiling guarantee in §4 — the cap exists specifically so a transient burst cannot permanently inflate resident memory; document the cap's tuning knobs rather than defaulting to unbounded.

### 14.7 Performance Concerns

`mmap`/`munmap` (~5 µs, M3 note) dominates pool-miss cost; pool-hit cost (<100 ns, ADR-21) is dominated by the zero-on-retire memset (I10) — sized against the size class, so the 4 MiB class's zero cost is measurably higher and documented as such.

### 14.8 Edge Cases

- A coroutine that requests a stack larger than the largest configured size class (4 MiB) — falls back to a direct one-off `mmap`, bypassing the pool entirely, and is flagged in tracing as a pool-bypass event (§19 instrumentation, ADR-17).
- Concurrent retire/allocate racing on the same per-thread pool — the pool is per-thread (single-writer) by construction in Phase 0–2; cross-thread pool sharing is out of scope until Phase 7's scheduler (§19) introduces multiple workers, at which point each worker owns its own pool instance (no cross-pool locking needed).

- A request for a stack size that is not a power-of-two multiple of the page size — rounded up to the nearest page boundary before size-class rounding (§14.6) applies, so the two roundings compose predictably rather than interacting unpredictably.

### 14.9 Failure Analysis

An `mmap` failure (ENOMEM, address-space exhaustion) surfaces as `Coroutine::new` returning `Err(SpawnFailed)` rather than panicking — the caller's responsibility to back off; detection via the `helios_stack_allocs_total` counter failing to increment alongside a spawn-error metric. Blast radius: the one failed spawn; existing coroutines are unaffected (§4's 0-blast-radius constraint).

### 14.10 Operational Notes

`Stats::stack_bytes_used` (§11) is scraped by the debug CLI (`helios-cli`, §10) for live memory-budget visibility; the runbook `docs/runbooks/stack-overflow.md` cross-references this phase's guard-page mechanics for on-call diagnosis once Phase 6 (§18) wires the SIGSEGV handler.

15. Phase 3 — Stack Growth: Segmented & Growable (Gated)

15.1 Objectives

Deliver the two deferred stack strategies from §8.3 behind explicit opt-in flags, without changing the Phase-2 fixed-stack default (ADR-05).

15.2 Detailed Implementation Steps

Segmented (von Behren et al. 2003 Capriccio, §5): on a guard-page fault, the handler (built in Phase 6, §18 — this phase's segmented path reuses that handler rather than duplicating it) allocates a new mmap'd segment, writes a back-segment pointer, and switches sp to the new segment's top; a compiler-emitted (here, assembly-stub-emitted, since Rust has no segmented-stack compiler support) boundary check on function entry detects a segment crossing on return. Growable (Go runtime src/runtime/stack.go, §5): on overflow, allocate a larger contiguous region, copy existing content, relocate every internal pointer — gated behind a sub-API (GrowableCoroutine) whose contract forbids any &local escaping into a heap structure, since Rust lacks Go's precise-GC pointer tracking (ADR-05's rationale column).

Because both strategies are feature-flagged (§15.10), this phase also adds a CI job variant that builds and runs the full fixture suite with each flag combination (--features segmented-stacks, --features growable-stacks, both, neither) — catching a flag-interaction defect before it reaches a user who enables both simultaneously.

15.3 Deliverable

Two opt-in coroutine constructors, Coroutine::new_segmented and Coroutine::new_growable, each passing their respective deep-recursion fixture.

15.4 Acceptance Criteria

  • Segmented: a 10-level deep recursive fixture that would overflow a 64 KiB fixed stack completes successfully, with ≤ 10% per-call overhead measured against a non-segmented baseline (§5's Capriccio-adjacent measurement, §15.5).
  • Growable: a fixture needing 3× the initial stack size relocates and completes with zero corrupted pointers (verified via a canary-pointer fixture, §15.5).
  • Both remain opt-in: the Phase-2 default-constructed Coroutine::new is provably unaffected (regression fixture from §14.5 re-run unchanged).

15.5 Conformance Fixtures

Fixture Purpose Expected Output
segmented-deep-recursion forces 3+ segment crossings completes, no overflow panic
segmented-overhead-bench per-call boundary-check cost ≤ 10% overhead vs. fixed-stack baseline
growable-relocation-canary plants a canary pointer, forces growth canary correctly relocated, no corruption
growable-pin-rejection attempts growable + Pin<&mut T> held across yield compile-time rejection (type-level, §17.6-adjacent)

15.6 Pitfalls

  • Segmented stacks' per-call boundary check is a permanent tax on every call in a segmented coroutine, not just the overflowing one — document this cost model clearly so users do not default to segmented "just in case."

  • Growable stacks' relocation step is the single trickiest piece in the whole deferred-feature set; the safety contract (no escaping stack references) is enforced by API shape, not by the borrow checker directly — a determined user can still violate it via unsafe, which is why this remains gated/deferred rather than promoted to default (ADR-05).

  • A coroutine using growable stacks that holds a Pin<&mut T> across a yield is UB if relocated mid-hold; growable-pin-rejection exists specifically to catch this at the API boundary.

  • Enabling both segmented-stacks and growable-stacks on the same coroutine simultaneously is not a supported configuration — the two strategies' overflow-handling paths are mutually exclusive by construction (§8.3's table lists them as alternatives, not composable layers).

15.7 Performance Concerns

Segmented: ~10% overhead is the number Go's own historical segmented-stack experiment (superseded by copying stacks in Go 1.3+, per the Go runtime reference, §5) reported for typical workloads — this project cites that as the expected order of magnitude, not a novel measurement claim.

15.8 Edge Cases

  • A segmented coroutine whose recursion depth oscillates across the segment boundary on every call (a "boundary-thrashing" pattern) — pathological but not incorrect; documented as a known perf cliff in docs/architecture/stack.md.

  • A growable coroutine that overflows during an in-progress relocation (re-entrant overflow) — explicitly out of scope for this deferred feature's first cut; flagged in the Deferred Features Register (§37) as a follow-up trigger.

  • A growable coroutine whose very first stack frame (before any user code runs) is already close to the initial region's capacity — treated identically to an ordinary mid-execution overflow; there is no separate "too small from the start" code path.

15.9 Failure Analysis

A relocation bug (a missed internal pointer) manifests as a use-after-free at an arbitrary later point — the hardest class of bug this deferred feature can introduce, which is precisely why ADR-05 keeps it gated behind an opt-in sub-API rather than the default path production coroutines take.

15.10 Operational Notes

Both features are feature-flagged at compile time (--features segmented-stacks, --features growable-stacks); disabled by default in the release build profile so the default helios dependency graph carries neither's complexity or risk (§27 Compatibility & Versioning).

16. Phase 4 — Asymmetric Coroutine API

16.1 Objectives

Deliver the full Coroutine<R,Y> surface: resume()/resume_with(), yield_value(), and Drop-triggered cancellation.

16.2 Detailed Implementation Steps

Implement the resume/yield state machine per §8.4's table and I2/I7: resume() switches to the coroutine's saved context (via helios-asm::swap, §13), runs until yield_value(v) or the entry returns; yield_value writes v into a parent-pointed slot and switches back (Knuth TAOCP 1.4.2, §5, the "generalized subroutine" model this API embodies literally). Drop for Coroutine signals Cancel (P8, I7) and blocks until the coroutine acknowledges at its next yield or completes — this is the structured-concurrency guarantee referenced in §1's non-goals discussion of what this project does provide despite not providing full actor-style supervision.

This phase also documents, in rustdoc directly on Coroutine<R,Y> (I14), the exact ordering guarantee between a resume_with(v) call and the corresponding yield_value return — namely that v is visible to the coroutine strictly after the switch, never before, which matters to any caller reasoning about happens-before ordering across the boundary.

16.3 Deliverable

A coroutine that yields ten times, observes ten distinct resume_with values, and returns is fully driven through every state in §8.4's table; Drop-cancellation on a Yielded coroutine is demonstrated.

16.4 Acceptance Criteria

  • The ten-yield fixture (§16.5) completes with exactly 10 Yielded results followed by 1 Done.
  • Drop-cancellation on a Yielded coroutine completes within the 10 ms grace period default (§22.6, cross-referenced here since Drop's cancellation path reuses Phase 10's cancellation discipline).
  • Zero uses of unsafe outside helios-asm/helios-stack in the helios crate itself (P10, verified by #![forbid(unsafe_code)] at helios's crate root).

16.5 Conformance Fixtures

Fixture Purpose Expected Output
ten-yield-roundtrip drive through 10 yield/resume cycles 10× Yielded, then Done
drop-cancels-yielded drop a Yielded coroutine Cancel observed, cleanup completes ≤ grace period
resume-wrong-state-rejected resume() on a Done coroutine Err(InvalidState) (I2)
yield-value-type-mismatch (compile-time) mismatched Y type at call site fails to compile

16.6 Pitfalls

  • A Yielded coroutine that never yields again hangs the Drop call indefinitely — the runbook (docs/runbooks/stuck-coroutine.md) documents the diagnostic (check helios_cancel_observed_total staying flat).

  • The R, Y generics produce one monomorphization per instantiation; size-conscious embedders should use the dyn-erased variant noted in §11's schema comments rather than assume zero code-size cost.

  • A Coroutine resumed with a value of the wrong logical meaning (not wrong type — Rust's type system catches type mismatches, per yield-value-type-mismatch) is a caller-logic bug the type system cannot catch; document clearly in rustdoc (I14).

  • Assuming Coroutine<R,Y> is Clone because the underlying stack could in principle be duplicated is wrong — StackHandle's !Clone bound (I1) makes this a compile error, not a runtime one, which is the point.

16.7 Performance Concerns

Each resume()/yield_value() pair is exactly one swap() round trip (§13's M1/M2 budget) plus the state-machine bookkeeping (I2/I11 checks) — bookkeeping is designed to stay inside the same cache line as the header (I6) so it does not add a second cache miss.

16.8 Edge Cases

  • yield_value called from a Fiber context by mistake (API misuse across §16/§17) — rejected at compile time since yield_value is only in scope inside a Coroutine's entry closure, not a Fiber's (P4's "two APIs, one primitive" split enforced at the type level here).

  • A panic inside the coroutine's entry function — caught by the trampoline (§13.2) and converted to Panicked(UserPanic), not propagated as a raw unwind across the context-switch boundary (unwinding across an arbitrary stack swap is undefined per the Rust unwind ABI).

  • A coroutine entry closure that itself constructs and immediately drops another Coroutine without ever resuming it — legal; the inner coroutine's stack is allocated and then retired (I12) without ever running, exercising the pool's allocate/retire path with zero swap() calls.

16.9 Failure Analysis

A stuck Drop (§16.6) blocks the dropping coroutine/thread, not other coroutines (I11's one-running-per-worker invariant means the blocked drop occupies its own call stack, not the scheduler) — but if the dropping context is itself a scheduler worker, that worker is unavailable until the drop resolves or times out; the grace-period mechanism (§22.6) is the actual bound.

16.10 Operational Notes

tracing spans (ADR-17) are emitted for every resume/yield/drop transition starting in this phase informally (full instrumentation lands with the scheduler in §19); span names follow helios.coroutine.{resume,yield,drop} verbatim for dashboard consistency (§26).

17. Phase 5 — Symmetric Fiber API

17.1 Objectives

Deliver Fiber::spawn/switch_to — arbitrary-graph control transfer with no parent/child relationship, sharing the Phase-1 context-switch primitive (P4, ADR-07).

17.2 Detailed Implementation Steps

Implement Fiber::spawn(f) using the same trampoline as Coroutine (§13.2) but with parent: None in the header (§11). Implement switch_to(&mut self, other: &mut Fiber): an unconditional swap() call with no implicit return path (de Moura & Ierusalimschy 2009's symmetric-coroutine taxonomy, §5, distinguishes this precisely from asymmetric resume/yield). Document the use cases this unlocks that Coroutine cannot: cooperative multitasking over an arbitrary task graph, continuation-passing-style implementations, and state-machine compilation targets (Marlin 1980, §5).

This phase also adds a Fiber::id() -> FiberId accessor (mirroring CoroutineId, §11) specifically so the runbook (§17.10) and any future graph-visualization tool (Deferred Features Register, §37) have a stable identity to key on when reconstructing a hung Fiber graph after the fact.

17.3 Deliverable

A three-fiber cycle (A → B → C → A) runs for a bounded number of hops and terminates cleanly via an explicit exit fiber.

17.4 Acceptance Criteria

  • The three-fiber cycle fixture (§17.5) completes exactly the configured hop count with no missed or duplicated switches.
  • switch_to a Done fiber returns Err(TargetDone) rather than switching into freed/retired memory (I12 enforcement extended to the symmetric API).
  • Context-switch cost for switch_to is within 5% of Coroutine::resume's M1/M2 budget (same underlying primitive, P4).

17.5 Conformance Fixtures

Fixture Purpose Expected Output
three-fiber-cycle A→B→C→A for N hops exactly N switches, clean exit
switch-to-done-rejected switch to an already-Done fiber Err(TargetDone)
fiber-vs-coroutine-cost-parity compare switch cost to Coroutine::resume within 5%

17.6 Pitfalls

  • A Fiber graph with cycles that never reach an exit fiber starves indefinitely — the runtime does not detect cycles (this is explicitly the application's responsibility, not a runtime invariant); document this clearly since it is the single biggest source of "why did my program hang" reports for symmetric-coroutine libraries generally (Project Loom's JEP 444, §5, notes an analogous class around unstructured continuation graphs).

  • switch_to has no implicit return — a caller expecting Coroutine-style "control comes back to me" semantics from Fiber has the wrong mental model; §32's Mental Models section addresses this confusion directly.

  • Building a Fiber graph with unbounded fan-out (every fiber can switch to every other) makes cycle-detection tooling infeasible after the fact — recommend graph topology be documented per application, not discovered empirically.

  • Confusing Fiber::spawn with Coroutine::new at a call site (both take an entry closure) is an easy copy-paste error; the type system catches the mixing of yield_value inside a Fiber body (§16.8) but not a developer reaching for the wrong constructor entirely — code review is the remaining defense.

17.7 Performance Concerns

Since switch_to shares swap() with resume(), there is no separate cost model — any regression here is caught by the same bench_ctx_switch gate (§13.4, M1/M2), not a duplicate benchmark.

17.8 Edge Cases

  • A Fiber that switch_tos itself — technically legal (a no-op round trip through swap()), documented as legal-but-useless rather than rejected, since rejecting it would require an extra check on every switch that the vast majority of correct call sites do not need.

  • Two fibers racing to switch_to the same third fiber concurrently from two different OS threads — undefined in Phase 5 (single-thread scheduler context, §12); becomes a real concern only once Phase 7's M:N scheduler (§19) is layered on, at which point pinning (P9) is the required mitigation for any Fiber graph shared across workers.

  • A Fiber graph where every fiber holds a strong reference to every other (an accidental reference cycle at the Rust ownership level, distinct from the control-flow cycle in §17.6) — a memory-leak concern orthogonal to the runtime-hang concern; Fiber handles use the same ownership discipline as Coroutine (I1/I12), so this is a caller-side Rc/Arc design question, not a runtime defect.

17.9 Failure Analysis

An unreachable-cycle hang (§17.6) is detected operationally via the same long-running-coroutine tracer as any other starvation case (ADR-23) — there is no Fiber-specific detection path, by design, to avoid a second detection mechanism doing the same job as the existing one.

17.10 Operational Notes

Fiber-graph topology is not introspectable by helios-cli in this phase (Deferred Features Register, §37, notes a graph-visualization tool as a candidate follow-up); operators debug Fiber hangs via the replay harness (I13) instead.

18. Phase 6 — Stack-Overflow Detection

18.1 Objectives

Convert a guard-page fault into a clean Panicked(StackOverflow) result instead of a process crash, via an async-signal-safe SIGSEGV handler (I9).

18.2 Detailed Implementation Steps

Register a SIGSEGV handler at scheduler startup via sigaction(SA_ONSTACK | SA_SIGINFO) (POSIX sigaction/sigaltstack, §5); each worker thread allocates a 16 KiB sigaltstack so the handler never runs on the faulting coroutine's (possibly exhausted) stack. On fault: read siginfo.si_addr; walk the per-thread coroutine table (pre-allocated, no locks, no allocation — I9) to find whose guard page (I3) contains the address. If found: patch the saved ucontext_t's instruction pointer to a "return-to-scheduler" stub, mark the header Panicked(StackOverflow), and return from the handler (the kernel resumes execution at the patched IP, since a signal handler cannot simply longjmp across a kernel signal frame — signal-safety(7), §5). If not found: re-raise/chain to any previously-installed handler.

guard-page write --> kernel delivers SIGSEGV (SA_ONSTACK) --> handler runs on sigaltstack
                                                                     |
                                     +-- si_addr in a known guard page? --+
                                     |                                    |
                                    yes                                  no
                                     |                                    |
                       patch ucontext IP to return-to-scheduler   re-raise / chain to
                       stub; mark Panicked(StackOverflow)         prior handler (§18.6)

This phase also wires the handler's fault-attribution table to be pre-sized at scheduler startup based on the worker's configured maximum coroutine count, rather than growing dynamically — a growing table would itself require an allocation the handler is forbidden from performing (I9), so the size must be fixed before any coroutine spawns.

18.3 Deliverable

A coroutine with unbounded recursion on a 64 KiB fixed stack (ADR-20) is converted to Panicked(StackOverflow); the host process survives and continues running other coroutines.

18.4 Acceptance Criteria

  • The unbounded-recursion fixture (§18.5) yields Panicked(StackOverflow) within 1 ms of the fault (handler dispatch + table walk + stub patch), verified against a 100-coroutine table.
  • Zero calls to malloc/free/printf inside the handler (I9), verified by the #[forbid(alloc)] custom lint (ADR-24).
  • The host process's other, unrelated coroutines continue running unaffected (0 blast radius, §4).

18.5 Conformance Fixtures

Fixture Purpose Expected Output
unbounded-recursion-overflow forces guard-page fault Panicked(StackOverflow), process survives
handler-no-alloc static analysis of handler module zero forbidden calls (I9)
fault-attribution-100-coroutines fault attribution correctness at scale correct coroutine identified among 100
unrelated-segfault-rechain a fault outside any guard page re-raised / chained to prior handler, not swallowed

18.6 Pitfalls

  • The handler must be async-signal-safe: only sigaction, sigaltstack, mmap/munmap/mprotect, pthread_kill are permitted; malloc/printf are not (signal-safety(7), §5, I9).

  • The alternative stack must be sized generously (16 KiB floor) — an under-sized altstack faulting inside the handler itself is unrecoverable.

  • The handler's interaction with other installed handlers (a profiler's own SIGSEGV hook, for instance) must chain correctly — the runtime documents that it installs last and chains to whatever was previously registered.

  • A coroutine that wraps its own body in catch_unwind does not catch a stack overflow — the signal-handling path operates below the unwind-table mechanism entirely; document this distinction clearly (I14).

  • The handler must be installed before any coroutine is spawned — an overflow before installation crashes the process with no recovery path.

  • Assuming the handler's 16 KiB altstack scales with the faulting coroutine's stack size is wrong — the altstack size is fixed and unrelated to the size of the stack that overflowed; it only needs to hold the handler's own (small, fixed) call depth.

18.7 Performance Concerns

The table walk is O(coroutines-on-this-thread), not O(all coroutines) — since guard pages are per-stack and the table is per-thread, this bounds worst-case handler latency even under the 1M-coroutine target (§4) as long as no single thread hosts an unreasonable fraction of them (the scheduler's steal-fairness invariant, §19, keeps this bounded in practice).

18.8 Edge Cases

  • Two coroutines on the same thread's table overflowing at nearly the same instant (vanishingly rare but possible under adversarial input) — signals are not re-entrant for the same signal number by default; the second fault is queued/masked per POSIX semantics and handled after the first returns.

  • macOS's signal-handling subtleties differ from Linux (documented separately in docs/architecture/overflow.md) — primarily around ucontext_t field layout; the port is arch/OS-specific code, isolated behind the same helios-overflow crate boundary.

  • A stack overflow occurring during the trampoline's synthetic-frame setup (before the coroutine has "really" started) — attributed correctly because the guard page exists from the moment helios-stack maps the region (Phase 2, §14), before the trampoline ever runs.

  • A fault whose address falls exactly on the guard page's boundary byte (the last byte before the guard begins) — attributed as a legitimate stack use, not an overflow, since the guard region's start address is the exclusive boundary by construction (§14.1).

18.9 Failure Analysis

If fault attribution fails (the address matches no known guard page though a helios-owned stack did overflow — a defect in the table, not in the concept), the fault re-raises as an ordinary uncaught SIGSEGV and the process crashes — this is the honest fallback: better to crash loudly than silently misattribute a fault to the wrong coroutine (which would corrupt that coroutine's state for no reason). Detection: a crash with no Panicked(StackOverflow) telemetry preceding it is the signature; the runbook docs/runbooks/stack-overflow.md walks the on-call engineer through checking table consistency.

18.10 Operational Notes

helios_stack_overflow_total counter increments on every successful attribution; a dashboard alert fires above a low absolute threshold (e.g. >0 in a service that should never legitimately overflow) since this is almost always an application bug (unbounded recursion), not expected steady-state behavior (§26).

19. Phase 7 — M:N Scheduler

19.1 Objectives

Multiplex M coroutines onto N OS worker threads via per-worker Chase-Lev deques, a global injector, and work-stealing (ADR-04); implement the full state machine of §8.4.

19.2 Detailed Implementation Steps

Implement Worker (§11) with a local Chase-Lev deque (Chase & Lev 2005, §5) — owner pops LIFO from the top, thieves steal FIFO from the bottom, minimizing false sharing between owner and stealer (Herlihy & Shavit's correctness argument, §5). Worker loop: pop local; if empty, drain the global injector; if still empty, steal half of a random peer's queue ("half-stealing" heuristic, Blumofe & Leiserson 1999's space bound, §5); if no work anywhere, park (§19.2's parker cooperates with helios_channel/helios_sync's wake paths, §20/§21). Enforce I8 (never steal a Pinned coroutine) by filtering the steal candidate on the migratable bit (§11) before removing it from the victim's deque. Enforce I11 (exactly one Running per worker) via the atomically-swapped Option<CoroutineId> slot.

This phase also introduces the per-worker Stats snapshot merge used by the fleet-wide dashboard (§26) — since each worker owns its own counters (no shared-state contention, per §19.7's cache-line reasoning), the merge is a read-only aggregation step run by the CLI/dashboard scraper, never by the workers themselves.

19.3 Deliverable

1,000,000 coroutines spawn and drain to completion on a 16-core host inside the M4 target window, with measured steal-fairness (every worker eventually serves work originated on every other).

19.4 Acceptance Criteria

  • 1M spawn+drain completes in ≤ 10 s on 16 cores (M4, §4/§30).
  • Cross-core work-steal latency ≤ 500 ns p50 (M7, §30).
  • Zero helios_steal_attempts_on_pinned_total events across the full fixture suite (I8).
  • helios_worker_running_count never exceeds 1 during a 1-hour soak (I11, §28).

19.5 Conformance Fixtures

Fixture Purpose Expected Output
stress-1M-spawn-drain full-scale throughput target ≤ 10 s, M4
steal-respects-pin pinned coroutine never stolen 0 violations (I8)
steal-fairness-16-workers work originating on any worker reaches all others fairness threshold met
unpark-race-regression double-check-after-park race no missed wakeup

19.6 Pitfalls

  • The unpark race — a remote signal observing a non-parked worker, followed by a park that misses the signal — is the canonical work-stealing deadlock; the protocol is double-check-after-park, and unpark-race-regression exists specifically to guard it under loom (ADR-14).

  • Migrating a coroutine holding a thread-local pointer is undefined (ADR-10, P9) — the type system catches obvious cases (a non-Send guard auto-pins, §21.6-adjacent) but not all; document the residual gap explicitly (I14).

  • A worker holding the only reference to a parked coroutine that itself is shut down stalls that coroutine indefinitely — the shutdown sequence (helios-scheduler::shutdown, §10) must drain parked coroutines onto surviving workers before a worker thread exits.

  • Per-call-site pinning overrides interact with steal fairness in non-obvious ways under heavy pin usage — the runbook documents the diagnostic for "why is my throughput uneven across cores."

  • Assuming work-stealing eliminates the need for any application-level load awareness is wrong under extreme skew (one coroutine doing 99% of the work) — stealing balances task count, not task duration; a single long-running task is not sub-divided by the scheduler.

19.7 Performance Concerns

The half-stealing heuristic minimizes cross-thread cache traffic versus stealing one task at a time (which would require a steal round-trip per stolen task); the Chase-Lev deque's top/bottom indices sit on separate cache lines specifically to avoid owner/thief false sharing (I6-adjacent reasoning, applied to the deque rather than the header).

19.8 Edge Cases

  • All N workers simultaneously idle with the injector also empty — every worker parks; a new spawn from an external thread must reliably unpark at least one worker (the unpark race in §19.6 is exactly this scenario under contention).

  • A coroutine that pins itself, then explicitly requests migration mid-execution — legal (opt-in flag is mutable at runtime, P9), but the switch only takes effect at the next yield point, not immediately, since a Running coroutine cannot be relocated mid-instruction (I11).

  • A worker thread that is asked to shut down while it is the only worker holding the sole reference to the global injector's remaining queue — the shutdown sequence (helios-scheduler::shutdown, §10) drains the injector to a surviving worker before the last worker exits, avoiding an orphaned queue.

19.9 Failure Analysis

A scheduler-level defect (I11 violation — two coroutines "running" on one worker) is treated as unrecoverable at the coroutine level; the affected worker's catch_unwind wrapper (§8.4's failure-path worked example) restarts the worker fresh rather than attempting fine-grained recovery, bounding blast radius to that worker's in-flight queue.

19.10 Operational Notes

Stats (§11) exposes live/parked/stolen_total/stack_bytes_used; helios-cli polls these for a live dashboard; tracing spans (helios.scheduler.{steal,park,unpark}, ADR-17) give causal traces across workers for postmortem analysis (§26).

20. Phase 8 — CSP Channels & Select

20.1 Objectives

Deliver bounded and unbounded CSP channels (Hoare 1978, §5; ADR-08) with a handoff fast path, plus a select! macro racing multiple channel operations.

20.2 Detailed Implementation Steps

Bounded channel: a ring buffer of capacity N plus a sender wait list and a receiver wait list (I4: each parked coroutine on exactly one). send: if the buffer has space and no receiver is parked, enqueue; if a receiver is parked, hand off directly (skip the ring buffer entirely — the perf-critical path, saving two atomic ops per pass); otherwise park the sender. recv is the mirror image. Unbounded: a linked list, send never blocks (backpressure explicitly delegated to the caller, per ADR-08's rejected-alternative note about large-payload channels). select!: evaluate each branch's non-blocking attempt first; if none succeed immediately, register the coroutine on every branch's wait list and park; on wake, identify the winning branch and de-register from all losing branches (the load-bearing step — a missed de-registration leaks a wait-list entry, directly threatening I4).

This phase also documents the exact ordering guarantee a select! provides when two branches become ready simultaneously (a tie): the implementation resolves ties by evaluation order (first-listed branch wins), a deterministic rule chosen specifically so the replay harness (I13) can reproduce a tied select! outcome bit-for-bit.

20.3 Deliverable

A producer/consumer benchmark sustaining 10M sends/sec on a single bounded-channel pair; a 1-producer/16-consumer fan-out fixture balancing load within a documented fairness bound.

20.4 Acceptance Criteria

  • Uncontended send/recv ≤ 100 ns p50 (M5, §4/§30).
  • 10M sends/sec sustained on one pair for 60 s with zero dropped messages (§20.5).
  • Fan-out fixture: no consumer receives less than 1/32 of the fair share over 1M messages.
  • Zero wait-list leaks after 10,000 select! races (§20.5's de-registration fixture).

20.5 Conformance Fixtures

Fixture Purpose Expected Output
bounded-throughput-10M sustained single-pair throughput ≥ 10M sends/sec, M5
fanout-16-consumer-fairness load balance across consumers within documented fairness bound
select-deregistration-no-leak 10,000 select races 0 wait-list leaks (I4)
closed-channel-recv-err recv on closed channel Err(Closed)
closed-channel-send-err send on closed channel Err(Closed)

20.6 Pitfalls

  • Skipping the handoff optimization (always going through the ring buffer even when a receiver is parked) pays two avoidable atomic ops per message — the perf-critical path documented in §20.2 exists specifically to avoid this.

  • A select!'s losing branches must be cleanly de-registered; failing to do so is a direct I4 violation (two "parked on" registrations for one logical wait).

  • A channel of T: Drop whose drop itself blocks (e.g., a T that internally awaits something) blocks the coroutine processing the channel close — document this interaction explicitly since it is easy to introduce accidentally.

  • A select! with all branches reading from the same channel is degenerate but legal — not rejected, since rejecting it would require cross-branch analysis most call sites do not need.

  • Assuming an unbounded channel is "safer" than a bounded one because it never blocks the sender is backwards — it trades a visible backpressure signal for an invisible memory-growth failure mode (T8, §24), which is strictly harder to diagnose in production.

20.7 Performance Concerns

The ring buffer's head/tail indices are on separate cache lines (anti-false-sharing, same reasoning as §19.7's deque); the handoff path's savings are largest exactly at the throughput target (§20.4) since it removes the ring buffer from the critical path entirely on the common "receiver already waiting" case.

20.8 Edge Cases

  • A bounded channel of capacity 0 (rendezvous channel) — every send must find a parked receiver or park itself; there is no buffer state to fall back to, making the handoff path mandatory rather than an optimization in this specific configuration.

  • An unbounded channel under a producer that never stops and a consumer that never runs — memory grows without bound; documented explicitly as the caller's responsibility (ADR-08), not a runtime-enforced backpressure.

  • A select! with zero branches (a degenerate macro invocation) — rejected at compile time by the macro's expansion, not a runtime edge case at all.

20.9 Failure Analysis

A wait-list leak (I4 violation) manifests as a slowly growing memory footprint and, eventually, spurious wakeups on stale registrations — detected via the helios_park_double_registration_total metric (§7) trending above zero; contained by the per-channel wait list being independent of other channels' (one leaking channel does not affect others).

20.10 Operational Notes

tracing spans helios.channel.{send,recv,select} (ADR-17) carry the channel's configured capacity as a field for dashboard grouping; the runbook documents diagnosing a fan-out fairness regression via per-consumer span counts (§26).

21. Phase 9 — Coroutine-Aware Sync Primitives

21.1 Objectives

Deliver Mutex<T>, RwLock<T>, Semaphore, WaitGroup — each parking the calling coroutine (not the OS thread) on contention, verified exhaustively by loom (ADR-14).

21.2 Detailed Implementation Steps

Mutex: a CAS-based fast path; on failure, append the coroutine to a wait queue and park; unlock pops the head and wakes it (the "unfair" pattern — a freshly arriving locker may win the CAS ahead of a queued waiter, who then re-races on wake). RwLock: reader count plus a writer queue; write-preferring by default (a queued writer blocks new readers) per POSIX convention, with a constructor flag for read-preferring (documented tradeoff: write-preferring avoids writer starvation at the cost of read-path latency under a queued writer). Semaphore: permit count plus wait queue, panics at construction if acquired permits would exceed capacity. WaitGroup: an atomic counter plus wait queue (add/done/wait, the Go sync.WaitGroup shape); panics if the count goes negative (more done calls than add). Every primitive's wait queue upholds I4 (one wait list per parked coroutine) and is exhaustively loom-checked per ADR-14, following the POSIX threading/scheduling model (Butenhof 1997, §5).

This phase also adds a RwLock::try_read()/try_write() non-blocking pair alongside the blocking read()/write(), since the select! macro (§20.6) needs a non-blocking attempt to race a lock acquisition against other branches the same way it already races channel operations.

21.3 Deliverable

All four primitives pass a 16-thread contention stress test and a loom exhaustive check at thread counts 2 and 3.

21.4 Acceptance Criteria

  • Uncontended Mutex acquire ≤ 50 ns p50 (M6, §4/§30).
  • loom reports zero invariant violations at TC 2 and TC 3 for all four primitives (I4 applied to each primitive's wait queue).
  • 16-thread stress test (§21.5) shows no lost wakeups over 10⁶ acquire/release cycles.
  • WaitGroup negative-count fixture panics deterministically, not silently.

21.5 Conformance Fixtures

Fixture Purpose Expected Output
mutex-16-thread-stress contention correctness at scale 0 lost wakeups over 10⁶ cycles
loom-mutex-tc2-tc3 exhaustive interleaving check 0 violations
rwlock-write-preferring-no-starve writer never starves under continuous readers writer acquires within bounded reader count
waitgroup-negative-count-panics done() exceeds add() deterministic panic
semaphore-over-capacity-rejected acquire > capacity at construction panic at construction

21.6 Pitfalls

  • A Mutex held across a channel.send() is the canonical deadlock pattern (holding a lock while parking on an unrelated wait list) — document prominently, since it is the single most common misuse pattern reported for coroutine-aware locks generally.

  • A coroutine that panics while holding a Mutex must release it via the same unwind-safety discipline as helios's trampoline (§13.2) — the lock is not "poisoned" the way std::sync::Mutex is (a documented, deliberate divergence, §27).

  • A MutexGuard held across a yield auto-pins the coroutine (non-Send guard) — the type-level enforcement referenced in §19.6; failing to understand this is a common source of "why won't my coroutine migrate" confusion.

  • Assuming Semaphore::acquire() and Mutex::lock() share an implementation because both park a coroutine is wrong — Semaphore tracks a count, Mutex tracks exclusive ownership with a poisoning-adjacent Drop discipline (§21.6); conflating the two in a code review is a common review-time error.

21.7 Performance Concerns

The "unfair" Mutex pattern (§21.2) trades worst-case fairness for uncontended-path speed; a fair variant handing the lock directly to the queue head is deferred (Deferred Features Register, §37) since it costs an extra handoff on the common uncontended case that dominates the M6 target.

21.8 Edge Cases

  • Two coroutines racing to acquire an uncontended Mutex at the exact same instant — resolved by the CAS; the loser parks per §21.2, no special-casing needed.

  • A RwLock read-preferring configuration under a workload with rare-but-latency-sensitive writes — documented as the wrong configuration choice for that workload; the constructor flag makes the tradeoff explicit rather than silently picking one.

  • A WaitGroup used with add() and done() calls from coroutines that are themselves migrated mid-sequence (P9) — legal, since the counter is a plain atomic with no thread-affinity requirement, unlike a MutexGuard (§21.6).

21.9 Failure Analysis

A lost-wakeup bug (a queued waiter that is never signaled) manifests as an indefinite hang on a specific primitive; loom's exhaustive TC2/TC3 check (§21.4) is the primary defense — a bug that survives loom but appears at higher thread counts is treated as a P0 and immediately gated by a targeted stress fixture addition.

21.10 Operational Notes

Stats-adjacent per-primitive counters (helios_mutex_contended_total, etc.) feed the dashboard describing lock contention hot spots; the runbook documents diagnosing the "Mutex held across channel send" deadlock pattern via a stalled-coroutine trace (§26).

22. Phase 10 — Cancellation Discipline

22.1 Objectives

Deliver cooperative cancellation (P8, ADR-09): a Cancel token observed at every yield point, with a bounded grace period for cleanup that itself yields.

22.2 Detailed Implementation Steps

Token (§11) wraps an Arc<AtomicBool>; CancelHandle::cancel() sets it. Every yield point (yield_value, park in channels/sync, §16/§20/§21) checks the flag before returning control to the coroutine (I7) — a single atomic load, negligible cost. On observing cancellation, the coroutine's next yield returns Err(Cancelled); the coroutine's own code decides whether to propagate or handle it — standard Rust Drop-based cleanup runs for any owned resources. Re-entrant cancellation during cleanup (a cleanup path that itself yields, observing a new cancellation) is bounded by a grace period (default 10 ms, §22.6): cleanup yields remain cancellable but "best-effort"; past the grace period, the coroutine is forcibly marked Panicked(CancelTimeout) rather than looping forever on cancelled-cleanup-yields-cancelled-again.

This phase also exposes CancelHandle::is_cancelled() -> bool as a non-blocking poll, distinct from the yield-point-only observation path (I7) — intended for use inside a long-running synchronous loop that cannot yield but can still check the flag between iterations, narrowing (without eliminating) the uncancellable-coroutine failure mode (§22.6).

22.3 Deliverable

A "cancel mid-channel-recv" fixture correctly unwinds; a "cancel while holding a Mutex" fixture releases the lock cleanly (cross-referencing §21.6's Mutex-Drop discipline).

22.4 Acceptance Criteria

  • Cancellation observed within 1 yield-point round trip (no more than one swap(), §13's M1/M2 budget, after the flag is set).
  • Grace-period force-termination triggers at exactly 10 ms ± 1 ms under the re-entrant-cleanup fixture (§22.5).
  • Zero held Mutex/RwLock guards remain locked after a cancelled coroutine completes cleanup (I7 combined with §21.6).

22.5 Conformance Fixtures

Fixture Purpose Expected Output

22.6 Pitfalls

  • A coroutine that never yields is uncancellable — a direct consequence of P2/P8's cooperative model; document the diagnostic (check helios_cancel_signaled_total incrementing with no matching helios_cancel_observed_total increase, §7 I7).

  • Cancellation cleanup that itself yields can be cancelled again — the re-entry policy (10 ms grace, force-terminate after) exists specifically to avoid an infinite "every cleanup yield gets cancelled before progress" pathology.

  • A cancellation observed during a recv returns Err(Cancelled) without affecting the channel itself — a common misunderstanding is assuming cancellation closes the channel, which it explicitly does not.

  • Assuming a Cancel signal implies the coroutine's Drop has already run is wrong — cancellation is observed, then the coroutine's own code chooses to unwind (§22.2); the Drop only runs once the coroutine's frames actually unwind, which can be several yield points later under the grace period.

22.7 Performance Concerns

The cancel-flag check is a single atomic load per yield point — negligible relative to the swap() cost it is bundled with (§13); the grace-period timer uses the same timer infrastructure as any timeout-based select! branch (§20), not a separate mechanism.

22.8 Edge Cases

  • A coroutine cancelled at the exact instant it would have returned normally (a race between "entry about to return" and "cancel observed") — resolved in favor of the normal return, since the entry function has already produced its result by the time any subsequent yield point would observe the flag.

  • Multiple CancelHandle clones signaling the same token concurrently — idempotent, since the underlying flag is a simple atomic set, not a counter.

  • A cancellation signaled against a CancelHandle whose coroutine has already reached Done before the signal arrives — a no-op; the flag is set on a token that no yield point will ever check again, and the handle's Drop does not error.

22.9 Failure Analysis

A coroutine that ignores cancellation past the grace period is force-terminated and marked Panicked(CancelTimeout) (I7's recovery column) — the blast radius is the one coroutine; its stack is retired through the normal Drop/I12 path once forced, not leaked.

22.10 Operational Notes

helios_cancel_observed_total/helios_cancel_signaled_total (I7) are the primary dashboard pair for cancellation health; a growing gap between them across the fleet is the leading indicator of an uncancellable-coroutine population building up (§26).

23. Phase 11 — Async-Runtime Bridge & Performance Hardening

23.1 Objectives

Deliver the bidirectional bridge into the rank-129 async runtime (ADR-12) and close out the release-hardening checklist: conformance-bucket pass rates, fuzz targets, and the 30-day stress canary.

23.2 Detailed Implementation Steps

await_future (coroutine → async direction, §11): constructs a oneshot channel, spawns a future on rank-129's executor that polls the awaited future and sends its result over the oneshot on completion, then yields the coroutine (reusing §16/§22's yield/cancel machinery) until the oneshot resolves. block_on_coroutine (async → coroutine direction): spawns the coroutine onto a helios scheduler and awaits its JoinHandle. Pin discipline (Project Loom JEP 444's documented pinning limitations, §5, are the closest real-world precedent for this exact hazard): a coroutine holding a Pin<&mut T> across a yield auto-pins to its worker (extending §19.6's TLS-pinning mechanism) since migration would invalidate Pin's no-move contract — detected via a stack-frame walk at yield time (conservative "pin on every yield" in this phase; a precise stack-inspecting variant is a documented follow-up, §37). Close hardening: run all conformance buckets (§23.5) to their committed pass rates, wire cargo-fuzz targets for scheduler+channel+cancel cross-primitive fuzzing (ADR-15), and start the 30-day stress canary (§28).

This phase also finalizes the docs/adr/ one-file-per-ADR split (§10) so the release-engineering pipeline (§29) can diff exactly which ADRs changed between releases — a prerequisite for the CHANGELOG.md generation step that accompanies every tagged release.

23.3 Deliverable

A coroutine awaits a tokio-family sleep future end-to-end via the bridge; a #[tokio::main] async fn block_ons a coroutine end-to-end; all conformance buckets pass at their committed rate.

23.4 Acceptance Criteria

  • await_future round-trip completes with the correct value in ≤ 3 scheduler round-trips of overhead beyond the underlying future's own latency.
  • All 8 conformance buckets (§23.5) at 100% pass rate except stress-1M (its own numeric target, ≤ 10 s, is the gate — §19.4).
  • 30-day stress canary completes with zero crashes and zero invariant-check failures (§7's deterministic simulator, run continuously).
  • cargo-fuzz targets run 24h with zero new crashes before a release is cut (§29).

23.6 Pitfalls

  • Mixing stackful and stackless coroutines without the pin discipline has been an open research problem for over a decade (de Moura & Ierusalimschy 2009's own discussion of coroutine/continuation interop hazards, §5) — this bridge is deliberately small and conservatively pinned rather than attempting a general solution.

  • A coroutine awaiting a future on a process with no rank-129 runtime present deadlocks — the bridge requires the runtime to be running; document this hard prerequisite prominently (I14).

  • A coroutine that awaits a future whose poll implementation recursively calls back into the same coroutine (a re-entrant poll) deadlocks; the runbook documents the diagnostic pattern (a block_on/await_future pair with no distinguishable "outer" caller).

  • The conservative "pin on every yield" approach (§23.2) over-pins relative to a precise stack-inspecting variant, costing some steal-fairness (§19) — an explicitly accepted tradeoff for this phase, revisited in the Deferred Features Register (§37).

  • Assuming the bridge's conservative pin-on-every-yield (§23.2) is free is wrong — it measurably reduces steal-fairness (§19) under a workload with many short-lived bridged awaits; the Deferred Features Register (§37) tracks the precise-stack-walk alternative specifically because this cost is real, not hypothetical.

23.7 Performance Concerns

The bridge's overhead (oneshot construction + spawn) is the dominant cost beyond the underlying future's own latency; bench_vs_go-style comparative benchmarking (Karsten & Barghi 2020's libfibre methodology, §5) is used to sanity-check this overhead against comparable M:N systems (§33).

23.8 Edge Cases

  • A cancelled coroutine mid-await_future — the oneshot's Drop cancels the spawned future on the rank-129 side, propagating cancellation across the bridge boundary rather than leaking a dangling future.

  • A block_on_coroutine call from inside a coroutine itself (nested bridging) — legal but discouraged; documented as a pattern that multiplies scheduling overhead without functional benefit.

  • A coroutine bridged via await_future whose future is itself backed by a helios channel recv (a channel-through-bridge round trip) — legal and exercised by the async-coro-bridge example (§10), though documented as adding one extra scheduling hop relative to a pure-helios channel operation.

23.9 Failure Analysis

A bridge deadlock (no rank-129 runtime present, §23.6) manifests as the awaiting coroutine parked forever with no wake source — detected via the same long-running-coroutine tracer as any other starvation (ADR-23); contained to the one coroutine, since the bridge's oneshot is per-call, not shared.

23.10 Operational Notes

tracing spans helios.bridge.{await,block_on} (ADR-17) carry a has_runtime: bool field so a missing-runtime deadlock is diagnosable from the very first span instead of only from the eventual hang; the 30-day stress canary's dashboard (§26) is the release gate this phase closes on.

26. Operational Readiness

  • Metrics. Every counter/gauge/histogram named in the Invariants (§7), Threat Model (§24), and Failure Modes (§25) tables is exported via a metrics-compatible facade; naming convention helios_<subsystem>_<noun>_<unit-or-total> (e.g. helios_stack_overflow_total, helios_worker_running_count). A per-release "metric census" diff (docs/performance/) flags any counter added or removed since the prior release, since a silently-dropped metric is itself an operational regression.
  • Tracing. tracing spans per ADR-17, named helios.<crate>.<verb> (e.g. helios.scheduler.steal, helios.channel.send, helios.bridge.await), each carrying coroutine_id/worker_id fields for cross-span correlation; a span's parent/child relationship reconstructs the causal chain across a coroutine's full lifetime (spawn → yields → cancel/done), which is the primary postmortem tool for FM-3/FM-4/FM-9-class bugs (§25).
  • Structured logging. Every Panicked variant logs exactly one structured event carrying the coroutine ID, panic kind, and (where applicable) the faulting address (§18) or the panic backtrace (FM-8, §25) — never a bare println!-style line, so the log line is machine-parseable by the same tooling that ingests the tracing spans.
  • Dashboards. One per subsystem (scheduler, stack pool, channels, sync, cancellation, bridge) plus one fleet-wide health rollup keyed on the FM-1..FM-12 signatures (§25); the rollup's top row is always the four "expected-zero" counters (helios_stack_overflow_total outside of intentional-overflow test traffic, helios_replay_divergence_total, helios_steal_attempts_on_pinned_total, helios_park_double_registration_total) so a correctness regression is visually distinct from a capacity one.
  • Alerting philosophy. Alert on rate-of-change for expected-zero counters rather than static thresholds, since these are correctness signals, not capacity signals; capacity-adjacent metrics (helios_injector_depth, pool hit rate) instead alert on sustained deviation from the M8/M9 targets (§30) over a rolling window, avoiding noisy single-sample flaps.
  • SLOs. p99 context-switch latency within 2× of M1/M2 (§30) sustained over any 5-minute window; zero FM-3/FM-4/FM-9 events per release; stack-pool hit rate (M8) not below 90% (a 5-point buffer under the 95% target) for more than 15 minutes continuously.
  • Incident response. The four runbooks in docs/runbooks/ (stack-overflow.md, stuck-coroutine.md, slow-spawn.md, migration-failed.md, §10) are the first-response references, each keyed to a specific FM-# class (§25) so an on-call engineer's first action is "open the runbook matching the firing alert's FM-# tag," not free-form investigation.
  • Backup/restore. N/A — no durable state (§4); the closest analogue is the I13 replay op-log, which is a debugging artifact, not a restore mechanism.
  • Deployment topology. A linked library inside the host process; no independent deployment unit, no separate lifecycle to manage beyond the host application's own.
  • Canary / rolling-upgrade / rollback / migration strategy. Governed entirely by the host application's own deployment process, since helios has no independent runtime to upgrade in place; a helios version bump is a host-application rebuild-and-redeploy, covered by §27's compatibility policy — the one helios-specific canary discipline is the 30-day stress-canary gate (§23.4/§28) that must be clean before any release is cut, independent of how the host later deploys that release.

27. Compatibility & Versioning

  • Wire compatibility. N/A at the coroutine layer — there is no network protocol in scope (§1); the bridge (§23) inherits rank-129's own wire compatibility where the bridged future itself does I/O.
  • Storage compatibility. N/A (§4, no persistence layer); no on-disk format exists to version.
  • API stability. SemVer on the helios facade crate; Coroutine<R,Y>/Fiber/Scheduler/channel/sync-primitive signatures (§11) are the stable surface a downstream crate depends on. Internal crates (helios-asm, helios-stack, helios-scheduler, helios-overflow) are 0.x and may break between minor versions of helios itself until the whole workspace reaches 1.0 — this is a deliberate, documented asymmetry: the facade is the contract, the internals are implementation detail even though they live in separate crates for compilation and audit-boundary reasons (P10).
  • C ABI (helios-c-abi, P13). Append-only struct layout, versioned independently via cbindgen-generated header comments; a breaking C-ABI change requires a major-version bump on helios-c-abi specifically, decoupled from the Rust crate's own version, so a C embedder pinned to helios-c-abi 1.x is unaffected by a helios 2.0 release that only touches the Rust-facing surface.
  • Migration. No in-place migration exists since there is no persisted state (§4); a version bump is a recompile, full stop — there is no "migrate the on-disk format" step to design for.
  • Deprecation policy. A deprecated API surface carries #[deprecated(note = "...")] for at least one minor version before removal, with the note naming the replacement API and the removal-target version.
  • Rolling-upgrade guarantees. Since helios has no independent process, "rolling upgrade" reduces entirely to the host application's own deployment discipline; the one helios-specific guarantee is that two different helios versions never need to interoperate within one process — exactly one version is linked per binary, by construction of how Cargo resolves a single semver-compatible version per dependency graph, so there is no cross-version wire/protocol compatibility matrix to maintain the way a networked service would need.
  • Feature-flag compatibility. The gated Phase-3 features (segmented-stacks, growable-stacks, §15) are additive Cargo features; disabling them never changes the default build's observable behavior, and enabling them never changes a program that does not opt into the corresponding constructors (new_segmented/new_growable) — feature flags are additive-only by policy, never behavior-altering-by-default.

28. Testing & Verification Strategy

  • Unit. Per-crate #[test] coverage on every public signature in §11; each crate's tests run in isolation with no cross-crate scheduling dependency.
  • Integration. conformance/runner.rs drives the fixtures named in every phase's N.5 table (§12.5 through §23.5) plus cross-phase fixtures that exercise more than one subsystem at once (e.g. a cancellation fixture that also holds a Mutex, §22.5/§21.6).
  • Property. proptest (ADR-15) generates random op sequences against the scheduler/channel/sync primitives, checking the invariants of §7 hold under arbitrary interleaving-adjacent inputs; loom (ADR-14) covers true interleaving exhaustively at small thread counts (TC 2/3, §21.4), while proptest covers larger, sampled input spaces loom cannot exhaust in CI-budget time.
  • Differential. bench_vs_go-style comparative measurement (§23.7) is diagnostic, not correctness-differential, since there is no reference oracle implementation to diff output against directly — the closest analogue is fixture-level agreement with documented reference-implementation behavior (e.g., matching libtask's trampoline argument-passing shape, §5, or Lua's asymmetric resume/yield contract, §16.2).
  • Fuzzing. cargo-fuzz targets for coroutine, scheduler, channel (§10), each seeded from the conformance corpora so a fuzz-found crash is immediately convertible into a named regression fixture.
  • Chaos. The 30-day stress canary (§23.4) injects churn (random spawn/cancel/migrate patterns) continuously against a long-lived process, the only test class in this strategy that runs on a timescale longer than a CI job.
  • Deterministic replay. I13's (seed, op-log) mechanism is the primary tool for turning a live production hang or an intermittent CI flake into a reproducible fixture — any flaky test in this suite is first triaged by attempting a replay before being dismissed as "flaky."
  • Soak. The 30-day canary, gated at zero crashes and zero invariant-check failures (§7's deterministic simulator running continuously against the canary's own workload).
  • Fault injection. The conformance adversarial/ corpus (malformed input, e.g. resume() on Done, §16.5) plus signal-handler fault-injection fixtures (§18.5) that synthetically trigger a guard-page fault rather than waiting for organic recursion depth.
  • Conformance. The eight buckets of §23.5, each with its own committed pass-rate gate.
  • Performance-regression gating. Every M# target (§30) has a criterion benchmark wired into perf.yml (ADR-16), failing the build on a >10% regression against the prior release's recorded baseline.

Every invariant in §7 maps to exactly one fixture or loom check; every phase's N.5 fixtures feed this strategy's integration layer directly — there is no separate, disconnected test suite maintained in parallel with the phase-level fixture tables.

29. Build & Release Engineering

  • Reproducible builds. Cargo.lock committed and CI-verified against a pinned toolchain (rust-toolchain.toml); the assembly .s files are checked into the repo (not codegen'd at build time) so a diff always shows the exact bytes shipped — no build-time code generation obscures what assembly actually ships (relevant directly to the I5/two-reviewer audit discipline, §13).
  • Artifact signing. Release tarballs and the cdylib artifact are signed via cosign (keyless, OIDC-based) before publication, so a downstream consumer can verify provenance without a long-lived signing key to manage.
  • SBOM. Generated via cargo-cyclonedx per release, covering the full dependency graph including helios-c-abi's C header, so a security audit of a helios-linking application has a complete bill of materials without re-deriving it from Cargo.lock by hand.
  • Release channels. stable (SemVer-tagged) and nightly (main-branch HEAD, informational only, explicitly not for production — the arch-matrix and loom gates still run on nightly but a nightly failure does not block stable).
  • CI/CD topology. ci.yml (build+test) → arch-matrix.yml (four-arch matrix, ADR-11) → loom.yml + miri.yml (verification) → perf.yml (regression gate, ADR-16) → fuzz.yml (24h fuzz window) → release.yml (only on a green run of every prior stage — the pipeline is a strict sequence, not a fan-out, so a release.yml run's green checkmark is a transitive guarantee about every earlier stage).
  • Version stamping. The helios crate version, git SHA, and build timestamp are embedded via built-crate-style codegen and exposed through Stats/the debug CLI (§11, §10), so an operator can answer "exactly which build is this" from a running process without consulting deployment records.
  • Provenance/attestation. SLSA-style build provenance attached to release artifacts, attesting the build happened in CI, from this exact commit, with this exact toolchain — closing the "was this artifact tampered with between CI and publication" gap.
  • Dependency auditing. cargo-audit (known-vulnerability database) and cargo-deny (license/duplicate-version policy) both gate release.yml (ADR-18); a new CVE against an existing dependency fails the next CI run automatically, not only at the next manual audit.

30. Performance Engineering

Benchmarking/profiling methodology: criterion (ADR-16) for all M# targets below, with perf/dtrace-based flamegraphs for allocation/lock/cache/syscall hot-path analysis on any regression investigation. Allocation analysis: the only steady-state allocation path is stack-pool miss (mmap, ADR-21) — everything else (context switch, channel handoff, mutex fast path) is allocation-free by construction (P5, P10). Lock analysis: the only true OS-level locks in the system are inside mmap/munmap's kernel path; every user-level "lock" (Mutex, RwLock, the Chase-Lev deque) is a lock-free or coroutine-parking construct, not an OS mutex. Cache analysis: I6 (one-cache-line header) and §19.7/§20.7's anti-false-sharing layout are the two structural decisions this section's numbers depend on. Syscall analysis: mmap/munmap (pool miss), sigaction/sigaltstack (once, at scheduler startup), and worker thread creation (clone/pthread_create, once per worker) are the only syscalls on any hot path — everything else is pure userspace. Tail-latency analysis: p99 numbers are tracked separately from p50 for every M# target below specifically because context-switch tail latency (a cold trampoline, an I-cache miss, §13.7) is where regressions hide.

31. Scalability Analysis

  • What stays constant (Big-O). Context-switch cost (M1/M2) is O(1) per switch, independent of coroutine count — the number of live coroutines never enters the swap() cost model (§8.2, §13).
  • What grows. Scheduler steal traffic grows with worker count N (more peers to contend for work from) and with load imbalance across workers; stack-pool memory grows O(live coroutines × stack size) (§34's capacity model formalizes this linearly).
  • Named bottlenecks, in order:
    1. Context-switch latency (M1/M2) — the hard floor beneath every other number in the system; nothing downstream can be faster than this.
    2. Stack-pool allocation rate under burst (M3's pool-miss path, ~5 µs mmap, §34 item 6) — the dominant cost the instant spawn rate exceeds pool-hit capacity (M8).
    3. Cross-core steal traffic (M7) — O(N²) worst-case contention in a naive all-to-all steal topology; mitigated to near-O(N) expected contention by random-victim selection (§19.2).
    4. Channel handoff contention on a single hot channel shared by many producers — a design-level bottleneck no scheduler change fixes; mitigated by sharding a hot channel into per-worker sub-channels at the application level (a documented pattern, not a helios-internal feature, since a general solution would need per-application knowledge of traffic shape).
  • Horizontal scaling. Adding OS worker threads, bounded by physical core count — beyond that ceiling, cache contention dominates and M1/M2 become the actual limiting factor, not thread count (§19.7's cache-line-layout reasoning explains why more threads past this point does not help).
  • Vertical scaling. Larger stacks (moving up the size-class ladder, ADR-21) trade per-coroutine memory for recursion-depth headroom — a vertical lever, not a horizontal one, and it does not touch throughput at all.
  • Sharding/partitioning. The per-thread stack pool (§14) is itself a partitioning strategy — no cross-thread pool coordination is needed by construction, which is precisely why the pool scales linearly with worker count rather than contending on a shared free list.
  • Coordination overhead. The global injector (§19) is the one shared-coordination point in the scheduler; its lock-free design (a variant of the Chase-Lev structure, §5) keeps this overhead sub-linear in worker count up to the core-count ceiling.
  • The practical ceiling and the levers beyond it. Physical core count bounds compute throughput; the M8/M9 targets (§30) bound pool/channel throughput. The lever beyond the ceiling is the M:N scheduler already sitting at its designed operating point (P3) — going further requires either NUMA-aware placement (deferred, §37, since cross-node steal traffic becomes the new dominant cost once single-node core counts are exhausted) or a fundamentally different topology (§36's Alternative Architectures explore this directly, notably Alternative D's preemptive model, which trades a different set of costs for the ability to run untrusted cooperative code at the same scale).

32. Mental Models & First Principles

  1. MM1 — A coroutine is a saved (SP, IP, registers) triple, not a thread. Predicts: switch cost is bounded by register-file size, not OS scheduling overhead. Bug class without it: assuming a coroutine switch costs ~1–2 µs (an OS thread's context-switch order of magnitude) instead of the actual ~10–60 ns (M1/M2), leading to unnecessary batching to "amortize" a cost that barely exists. Applied in §8.2, §13.
  2. MM2 — Cooperative scheduling means the coroutine, not the runtime, owns the safe point. Predicts: any code path with no yield is atomic with respect to every other coroutine on that worker. Bug class without it: adding defensive locking around code that cannot actually be preempted mid-computation (P2). Applied in §6 (P2), §19.
  3. MM3 — A guard page turns "undefined" into "detected." Predicts: overflow becomes a typed, attributable event (Panicked(StackOverflow)) rather than silent heap corruption. Bug class without it: treating stack overflow as an unrecoverable crash rather than a specific, recoverable, per-coroutine event. Applied in §18, I3.
  4. MM4 — Work-stealing is a load balancer with no coordinator. Predicts: throughput degrades gracefully, not catastrophically, under uneven load, because idle workers self-organize toward busy ones with no central scheduler. Bug class without it: manually pre-partitioning work "to balance load" when the scheduler already does this for free (§19, ADR-04). Applied in §19.
  5. MM5 — Pinning is a promise about identity, not a promise about speed. Predicts: a pinned coroutine may run slower under imbalance but never observes the wrong thread's TLS. Bug class without it: treating migratable: false as a performance knob to "optimize away," reintroducing TLS-affinity bugs (ADR-10). Applied in §19.6, P9.
  6. MM6 — A channel handoff is a rendezvous, not a mailbox. Predicts: a capacity-0 channel behaves as a direct control transfer with no buffer allocation at all. Bug class without it: assuming every send touches a buffer, missing why a parked-receiver handoff is faster than the buffered path (§20.2). Applied in §20.
  7. MM7 — Cancellation is a question the coroutine answers, not an order it obeys instantly. Predicts: cancellation latency is bounded by time-to-next-yield-point, never zero. Bug class without it: racing on the assumption that cancel() takes effect synchronously (§22, P8). Applied in §22.
  8. MM8 — The context-switch routine is the one place where "the compiler would have caught it" is false. Predicts: register-save bugs concentrate exactly here and nowhere else in the codebase, which is why the two-reviewer rule (I5) exists specifically for .s diffs and nowhere else. Bug class without it: applying normal Rust-safety confidence to assembly review, under-scrutinizing the one place that needs the most. Applied in §13, I5, P10.
  9. MM9 — A C-ABI handle is a capability, not a pointer. Predicts: the handle table (I17) can invalidate a handle without the C caller's copy becoming a dangling pointer that crashes on next use — it becomes a checked, rejected capability instead. Bug class without it: treating the handle as a raw pointer and skipping the invalidity check, reintroducing use-after-free at the FFI boundary. Applied in §10 (helios-c-abi), I17.
  10. MM10 — Determinism is recorded, not inferred. Predicts: a replay's fidelity depends entirely on what the op-log actually captured (I13) — any unseeded randomness silently escapes replay's guarantee. Bug class without it: assuming "the scheduler is deterministic" as a property of the algorithm alone, missing that an unseeded timer read or an OS-provided random value breaks it. Applied in §19, I13, FM-9 (§25).

Each system made one decision differently that defines its niche. Go goroutines chose copying/growable stacks backed by a precise GC — this is the one decision helios explicitly cannot copy (ADR-05) because Rust has no equivalent precise-pointer-relocation mechanism; Go wins decisively in the regime of unpredictable-depth, memory-constrained workloads where a 2 KiB initial stack matters. Lua coroutines chose a single-threaded, no-scheduler asymmetric-only model — the simplest possible correct implementation; Lua wins in the regime of embedding a scripting VM where the host application already provides its own concurrency and Lua coroutines are pure control-flow sugar, not a concurrency primitive. Java Project Loom chose to force pinning at specific JVM boundaries (JNI calls, synchronized blocks) rather than leaving it fully opt-in like helios's migratable flag — Loom wins in the regime of an existing, enormous ecosystem of blocking Java code that needs virtual threads to "just work" without every library author opting in explicitly. libdill/libmill chose unbuffered-by-default CSP channels and a typically single-threaded event loop — it wins in the regime of small, latency-sensitive network daemons (Sústrik's own libdill use cases) where the M:N scheduler's complexity is pure overhead relative to one thread's event loop.

34. Back-of-Envelope Capacity Model

  1. Max resident stacks per 4 GiB, worst case (every page touched). 4 GiB / 64 KiB = 65,536 stacks (§4).
  2. Max resident stacks per 4 GiB, typical case (3 of 16 pages touched, 4 KiB pages). 4 GiB / (3 × 4 KiB) = 4 GiB / 12 KiB ≈ 349,525 stacks — shows the 1M-coroutine target (M4) is a virtual-memory story, not a worst-case-physical-memory one.
  3. Virtual-address-space ceiling, 64 KiB stacks. 2⁴⁷ B (typical x86-64 48-bit user VA half) / 2¹⁶ B = 2³¹ ≈ 2.1 billion stacks, confirming §4's "~10⁹, address-space-bound" figure.
  4. Per-core context-switch throughput ceiling. 1 / 30 ns (M1) = 33.3 million switches/sec/core.
  5. 16-core aggregate switch ceiling (ideal, uncontended). 16 × 33.3M ≈ 533 million switches/sec.
  6. mmap-only cost if every one of 1M spawns were a pool miss. 1,000,000 × 5 µs = 5.0 s — nearly the entire M4 10 s budget, which is exactly why the ≥95% pool-hit target (M8) exists: at 95% hit rate only 50,000 calls miss, costing 0.25 s, leaving headroom for the remaining work.
  7. Channel bandwidth at the M9 throughput target, 64 B payload. 10,000,000 msgs/sec × 64 B = 640 MB/s per channel pair.
  8. Guard-page virtual-address overhead at 1M coroutines. 1,000,000 × 4 KiB = 4 GiB of VA reserved for guard pages alone (PROT_NONE, not physically resident, §14).
  9. Stack-zero cost per pool retire (I10), 64 KiB at ≈20 GB/s memset bandwidth. 65,536 B / 20×10⁹ B/s ≈ 3.3 µs — the dominant component of the "≤ 1 µs p50" pool-hit spawn target (M3), which is why that target is stated in microseconds rather than nanoseconds.
  10. Cross-core steal-attempt ceiling, 16 workers at 500 ns/steal (M7). 1/500 ns = 2M/sec per worker; 16 × 2M = 32 million steal attempts/sec aggregate ceiling, which is why the half-stealing heuristic (§19.2) — amortizing one round trip across multiple stolen tasks — matters more as worker count grows.

All ten numbers are derived directly from the System Constraints table (§4); none is asserted without the formula shown above it.

36. Alternative Architectures (Roads Not Taken)

Alternative A — Stackless compiler-transform coroutines only (no stackful runtime at all).

[async fn source] --(compiler)--> [generated state machine struct]
        |                                  |
        +-------- Future::poll -----------+---> executor (single stack, no swap())

Regime where it wins: workloads that are overwhelmingly I/O-bound, shallow-call-depth, and never touch blocking/recursive FFI. Real system: Rust's own async/await + any executor (the rank-129 blueprint's own domain). Rejected here because it cannot call arbitrary blocking or recursive FFI code without a bridge — exactly the capability §1/§2 identify as this project's reason to exist (ADR-02).

Alternative B — 1:1 OS-thread-per-coroutine (no user-level scheduler at all).

[coroutine 1] -> OS thread 1 (8 MiB stack, kernel-scheduled)
[coroutine 2] -> OS thread 2 (8 MiB stack, kernel-scheduled)
[coroutine N] -> OS thread N ...

Regime where it wins: low concurrency counts (thousands, not millions) where the engineering cost of a user-level scheduler is not repaid. Real system: traditional POSIX-threads-per-connection servers (e.g., pre-event-loop Apache MPM designs). Rejected here because per-thread stack cost (KiB–MiB range) and kernel-scheduling overhead do not scale to the 1M-coroutine target (M4, ADR-04).

Alternative C — Actor-model, no shared address space (Erlang/BEAM-style, per-process heap and GC).

[actor A: private heap] --msg--> [mailbox] --msg--> [actor B: private heap]
        (no shared memory ever; supervision tree manages restarts)

Regime where it wins: fault isolation is paramount and supervision-tree-style "let it crash" restart semantics are the primary reliability mechanism. Real system: Erlang/OTP, Elixir. Rejected here because helios coroutines share one address space by design — CSP channels (P7) are a convention, not an isolation boundary — and building a full per-actor-heap GC plus supervision tree is a fundamentally larger, different system than a coroutine library (explicit non-goal, §1).

Alternative D — Signal-based preemptive M:N scheduling (Go-style forced preemption).

worker thread --SIGURG--> [async preemption point injected into running goroutine's stack]
                                    |
                            forced yield, state saved, scheduler regains control

Regime where it wins: workloads with untrusted or adversarial cooperative code that cannot be trusted to yield voluntarily. Real system: the Go runtime post-1.14 (asynchronous preemption via signal-injected safe points). Rejected here because the engineering cost of async-signal-safe stack rewinding is disproportionate to the benefit at this project's scale, where cooperating code is assumed trusted (ADR-03, P2).

38. Glossary

  • AAPCS64. ARM's 64-bit Procedure Call Standard; defines aarch64 callee/caller-saved registers and argument passing.
  • Asymmetric coroutine. A parent/child control-transfer model; the child yields back to its resumer (Coroutine<R,Y>, §16).
  • Async-signal-safety. The restricted set of operations (per signal-safety(7)) safe to call inside a signal handler; excludes malloc.
  • Backpressure. A producer being slowed or blocked because a consumer/buffer cannot keep up; delegated to the caller for unbounded channels (ADR-08).
  • Blast radius. The scope of a fault's impact; this project's target is one coroutine or one worker, never the whole process (§4).
  • Boost.Context. The C++ reference library for per-architecture context switching (§5).
  • Bounded channel. A channel with a fixed ring-buffer capacity; blocks the sender when full (§20.2).
  • Callee-saved register. A register the called function must preserve across a call; the set saved by swap() (§8.2).
  • Caller-saved register. A register the caller must save itself if it needs the value preserved across a call.
  • Cache line. The unit of cache coherence transfer (typically 64 B); the size CoroutineHeader is bounded to (I6).
  • Cancellation token. A shared flag (Token, §11) observed at every yield point (I7).
  • Chase-Lev deque. A lock-free double-ended queue supporting owner-side LIFO pop and thief-side FIFO steal (§5, §19).
  • Context switch. The act of saving one execution context's registers/SP and loading another's (§8.2).
  • Coroutine. A suspendable, resumable unit of execution with its own stack (this project's stackful model, §8.1).
  • CSP. Communicating Sequential Processes (Hoare 1978); the channel-based IPC model (§20, ADR-08).
  • Fiber. A symmetric coroutine; transfers control to another named fiber with no implicit return (§17).
  • False sharing. Cache-line contention between unrelated data (e.g., a deque's top/bottom) placed too close in memory; avoided by explicit layout (§19.7, §20.7).
  • Guard page. A PROT_NONE-protected page at a stack's low address that converts overflow into a detectable fault (I3, §18).
  • Half-stealing. A work-stealing heuristic taking half of a victim's remaining queue per steal, amortizing the round-trip cost (§19.2, Chase & Lev 2005).
  • Injector (global injection queue). The scheduler's shared queue for cross-thread spawns not yet claimed by any worker (§19).
  • libdill / libmill. Martin Sústrik's C CSP-over-stackful-coroutines libraries (§5).
  • libtask. Russ Cox's minimal production-grade stackful-coroutine reference library (§5).
  • Loom. A Rust concurrency model-checker exhaustively exploring thread interleavings at small thread counts (ADR-14).
  • M:N scheduling. Multiplexing M coroutines onto N OS threads (§8.4, ADR-04).
  • Migration. Moving a coroutine's execution from one OS worker thread to another (§19.6, ADR-10).
  • Op-log. The recorded sequence of scheduling decisions used to drive a deterministic replay (I13).
  • Parker/parking. The mechanism by which an idle worker or blocked coroutine suspends until woken (§19, §20).
  • Pinned / pinning. A coroutine restricted to its last-run worker thread; the default posture (P9, ADR-10).
  • Preemption. A forced context switch imposed by the runtime rather than requested by the coroutine (rejected by ADR-03; P2).
  • Project Loom. The JVM's virtual-threads project (JEP 444, §5, §33).
  • Red zone. The 128-byte region below rsp on x86-64 SysV a leaf function may use without adjusting the stack pointer (I5).
  • Rendezvous channel. A capacity-0 channel where every send must find a parked receiver or park itself (§20.8).
  • Replay harness. The (seed, op-log) mechanism reproducing a run bit-for-bit for offline debugging (I13, §28).
  • RwLock. A reader/writer lock; write-preferring by default in this project (§21.2).
  • Runqueue. A worker's local task queue (a Chase-Lev deque) (§19).
  • Semaphore. A counting synchronization primitive bounding concurrent permit holders (§21).
  • SIGSEGV. The POSIX signal delivered on an invalid memory access, including a guard-page fault (§18).
  • sigaltstack. The POSIX mechanism for running a signal handler on a separate stack from the faulting context (§18.2).
  • Stackful. A coroutine model where each unit owns a full, independent call stack (§8.1, ADR-02).
  • Stackless. A coroutine model compiled to a heap- or caller-allocated state machine with no independent stack (§8.1, ADR-02, rank-129).
  • Symmetric coroutine. A control-transfer model with no parent/child relationship; any unit may transfer to any other (Fiber, §17).
  • SysV ABI. The System V AMD64 calling convention used on Linux/macOS/BSD (§8.2, §5).
  • TLS (thread-local storage). Per-OS-thread data (accessed via fs/gs on x86-64, tpidr_el0 on aarch64) not swapped by swap() (§8.2, T4/FM-5).
  • Trampoline. The synthetic-frame entry stub that starts a coroutine's entry function and calls coroutine_exit() on its return (§13.2).
  • Unbounded channel. A channel with no fixed capacity; send never blocks, backpressure delegated to the caller (§20.2).
  • WaitGroup. A counter-based primitive blocking until N done() calls match N add() calls (§21).
  • Work-stealing. A scheduling discipline where idle workers take tasks from busy peers' queues (§19, ADR-04).
  • Write-preferring. An RwLock fairness policy where a queued writer blocks new readers, avoiding writer starvation (§21.2).
  • Yield. A coroutine's voluntary suspension, returning control to its resumer or the scheduler (§16, §22).
  • Capability (handle). A checked, revocable reference (as opposed to a raw pointer) — the model helios-c-abi handles follow (I17, MM9).
  • Cardinality (metric label). The number of distinct values a metric label can take; unbounded cardinality (e.g., a raw panic string) degrades a metrics backend (T14, ADR-27).
  • Coroutine-local storage (CLS). A hypothetical per-coroutine analogue to thread-local storage; explicitly not provided (ADR-26).
  • Handle table. The pre-allocated, lock-free table mapping opaque C-ABI handles to internal Rust state, and the sole enforcement point for I17.
  • Redaction. Withholding a value (e.g., a panic message) from a context where its unbounded cardinality would cause harm, while still recording it elsewhere (ADR-27).
  • Scheduler activations. A kernel/user-level threading design (Bershad et al. 1992, §5) in which the kernel notifies user-space of blocking events; contrasted with this project's fully userspace scheduler (§19).
  • Use-after-free. Dereferencing memory after it has been freed/retired; the defect class I1/I12/I17 exist specifically to make unrepresentable or detectable.
  • Vendoring. Committing a dependency's source directly into a repository rather than resolving it via a package registry at build time (ADR-28).
  • Zero-on-retire. The pool discipline of zeroing a stack's contents before returning it to the free list (I10, §14).
