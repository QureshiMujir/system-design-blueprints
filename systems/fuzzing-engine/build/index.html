⬜ Phase 0 — Skeleton, Harness ABI, and CI §12

Objectives

Stand up the workspace skeleton, define the campaign-directory layout, implement the target harness ABI surface (ADR-18) so an example target can be linked and driven end to end even before instrumentation exists, and wire CI so every subsequent phase has a regression backstop.

Deliverable

A runnable fuzz-cli that can link either example harness, dispatch one input to it via the ABI, capture its exit status, and write a structured log line — with zero coverage feedback wired yet (that is Phase 1's job).

Acceptance
  • workspace builds reproducibly under the pinned toolchain
  • both example harnesses (libFuzzer-ABI, AFL-persistent-ABI) link and run one input successfully
  • CI passes on Linux x86_64
  • campaign-directory layout is created and resumable across a restart (I11 stub validated)
  • structured JSON log line emitted per dispatched input
Fixtures
  • conformance/phase0/libfuzzer_harness_ok — trivial libFuzzer-ABI target that always exits 0
  • conformance/phase0/afl_persistent_harness_ok — trivial AFL-persistent-ABI target that always exits 0
  • conformance/phase0/campaign_resume_after_restart — kills and restarts the CLI mid-campaign, asserts directory layout intact
  • conformance/phase0/concurrent_invocation_guard — launches two CLI instances against the same campaign directory, validates the second is rejected
Pitfalls
  • ABI mismatch: assuming the libFuzzer signature when the target actually exposes the AFL persistent-loop shape, causing a silent no-op dispatch.
  • Non-deterministic seed initialization at startup, breaking replay before replay tooling even exists (P6).
  • Treating the campaign directory as ephemeral instead of the durable state it is from day one (I11), forcing a painful retrofit later.
  • Hardcoding an assumption about which ABI mode a target uses instead of recording it explicitly in campaign configuration, so the ambiguity resurfaces on every resume.

⬜ Phase 1 — Coverage Instrumentation and the Shared Bitmap §13

Objectives

Wire the compiler's SanitizerCoverage output into a shared-memory bitmap the engine can read after each execution, implement the edge-encoding scheme (§8.1, P1), and establish collision monitoring (§8.2, CollAFL, Gan et al. 2018).

Deliverable

Instrumented example targets (compiled with SanitizerCoverage) that emit a valid, boundedly-collision-rate edge bitmap the engine can read and reset deterministically across repeated executions.

Acceptance
  • edge coverage is deterministic across repeated runs of the same input on a deterministic target (I2 corollary)
  • bitmap collision rate stays under 5% at the benchmark target's live-edge count (§4)
  • no bitmap writes observed outside the allocated shared-memory region across 10^6 executions
  • bitmap reset completes in under 10 microseconds
Fixtures
  • conformance/phase1/basic_edges — a target with a small, hand-countable set of branches, used to validate exact edge_id computation
  • conformance/phase1/collision_stress — a target with a deliberately high live-edge count to exercise CollAFL-style collision measurement
  • conformance/phase1/saturated_bitmap — a target designed to fill the bitmap near capacity, validating no overflow/corruption
  • conformance/phase1/zero_edge_target — a trivial no-op harness with no instrumented branches, validating the empty-bitmap case is not misreported as corruption
Pitfalls
  • Bitmap collision explosion from poor edge-hash entropy — silently undercounts coverage and stalls the is-interesting decision before Phase 3 even runs (§8.2).
  • Forgetting to reset the bitmap between forked children under the fork-server model built in Phase 2, contaminating coverage attribution (I2 dependency).
  • Shared-memory region size mismatch between the instrumented target's compiled expectation and the engine's runtime allocation, causing out-of-bounds writes.
  • Assuming instrumentation overhead is uniform across targets and skipping per-target overhead measurement, masking a pathological slowdown on one specific target family.

⬜ Phase 2 — The Fork Server and the Execution Loop §14

Objectives

Implement the fork-server protocol (§8.3, ADR-05) and the execution loop that dispatches inputs, enforces timeouts, and classifies exit status into ExitKind (I8), establishing the execs/second baseline the rest of the project is measured against (P2).

Deliverable

A stable fork-server-backed executor achieving the fork-mode execs/second target from §4 against the Phase 1 instrumented example targets, with unconditional timeout enforcement.

Acceptance
  • orphan-free shutdown across 10^4 dispatch cycles (no leaked zombie/child processes)
  • timeout enforcement validated against a deliberately hanging fixture — no campaign stall (I4)
  • fork-mode execs/second within the §4 target range (1k-5k/s) on the trivial parser fixture
  • ExitKind classification is exhaustive and never ambiguous across the full fixture suite (I8)
Fixtures
  • conformance/phase2/hanging_binary — an input that causes an infinite loop, validates I4
  • conformance/phase2/crashing_binary — a deliberate SIGSEGV target, validates Crash classification
  • conformance/phase2/fork_bomb_guard — a target that attempts to spawn excessive children, validates containment
  • conformance/phase2/handshake_desync — deliberately corrupts the control pipe to validate desync detection
  • conformance/phase2/resource_limit_exhaustion — a target sized to exhaust the configured fd/process-table limit, validating the limit is detected as a resource condition, not misclassified as target-caused
Pitfalls
  • Zombie process leakage from incomplete reaping under high-throughput dispatch.
  • Fork-server pipe desynchronization: a single dropped or malformed handshake byte silently hangs every subsequent dispatch (§8.3 step 3-4 boundary).
  • Treating a soft-timeout signal as sufficient — a target that masks or ignores SIGTERM requires hard-kill escalation (I4 requires unconditional enforcement, not best-effort).
  • Under-provisioning file-descriptor or process-table limits for the expected dispatch rate, causing spurious ExitKind::Oom-adjacent failures that are actually resource-limit misconfiguration, not target behavior.

⬜ Phase 3 — The Coverage-Feedback "Is-Interesting" Loop and the Corpus §15

Objectives

Close the loop: connect Phase 1's bitmap and Phase 2's executor to the is-interesting decision (§8.3, I1) and a persistent corpus/queue store (§8.6-8.7), so that a campaign can, for the first time, evolve.

Deliverable

An end-to-end loop: seed input → execute → extract coverage → is-interesting decision → corpus admission — demonstrably growing a queue and increasing cumulative edge coverage over a fixed run against the Phase 1 fixtures.

Acceptance
  • an input is added to the corpus iff it exercises a previously-unseen edge or hit-count bucket, validated against a fixture with known expected admissions (I1)
  • cumulative edge coverage strictly non-decreasing over a campaign run
  • favored-set recomputation produces a spanning set covering 100% of currently-known edges
  • campaign resumes from disk with an identical queue state after a forced restart (I11)
Fixtures
  • conformance/phase3/known_admission_sequence — a fixed sequence of inputs with a hand-computed expected admit/reject outcome per input
  • conformance/phase3/bucket_boundary — inputs designed to cross exactly one hit-count bucket boundary (§8.3 step 5)
  • conformance/phase3/resume_after_kill — validates queue-state identity across an unclean restart
  • conformance/phase3/redundant_coverage_pair — two independently-admitted inputs whose individual coverage overlaps entirely, validating both are retained at admission time (redundancy resolution deferred to favored-set computation, not blocked here)
Pitfalls
  • Off-by-one in the hit-count bucket boundaries (§8.3 step 5), causing systematic over- or under-admission relative to the AFL-validated bucket scheme.
  • Forgetting to merge the virgin map on keep, causing the same "new" edge to be re-admitted repeatedly (violates I1's "previously-unseen" semantics).
  • Losing lineage (parent_id) on admission, which silently breaks later minimization/triage traceability.
  • Recomputing the favored set on every single admission rather than periodically, silently reintroducing the same O(queue size)-per-admission cost the periodic-recomputation design was meant to avoid.

⬜ Phase 4 — The Mutation Engine (Deterministic + Havoc) §16

Objectives

Implement the deterministic mutation passes (bitflip, arithmetic, interesting-values) and the stochastic havoc stage (§8.4, P10, ADR-07), feeding mutated inputs back into the Phase 2/3 execution-and-feedback loop.

Deliverable

A mutation engine producing reproducible (seed-deterministic) deterministic-pass and havoc-stage mutations, driving measurable new-edge discovery on the Phase 1-3 fixtures beyond what the seed corpus alone covers.

Acceptance
  • deterministic replay of a mutation sequence given the same seed reproduces byte-identical mutated inputs (P6)
  • deterministic-pass exhaustively covers every offset for the fixture's input size within the ADR-08 gating rule
  • havoc-stage mutation cost stays under the §4 target (<10 microseconds per mutation, excluding I/O)
  • no buffer corruption or out-of-bounds mutation writes across 10^6 mutation calls
Fixtures
  • conformance/phase4/bitflip_exhaustive — small fixed-size input, validates every offset/width combination is exercised
  • conformance/phase4/havoc_seeded_replay — validates byte-identical mutation output across two runs with the same seed
  • conformance/phase4/overflow_guard — deliberately oversized/adversarial input, validates no mutator buffer overrun
  • conformance/phase4/boundary_wraparound — an input positioned at an exact byte/word wraparound boundary, validating deterministic wraparound behavior under arithmetic mutation
Pitfalls
  • Corpus bloat from havoc's block-insert primitive producing ever-larger inputs with no size discipline, directly taxing execs/second (P2).
  • Non-deterministic mutation output due to un-seeded or improperly-threaded PRNG state, silently breaking replay (P6) long before any crash-replay code exists to expose it.
  • Mutation starvation: an unbounded deterministic pass on a large seed consuming the entire energy budget before havoc ever runs.
  • Applying havoc's block-insert/delete primitives without bounds-checking against the target's declared maximum input size, producing inputs the harness silently truncates rather than genuinely tests.

⬜ Phase 5 — Splicing and Dictionary/Token Mutations §17

Objectives

Implement splicing (crossover between two corpus entries) and dictionary/token-based mutation (§8.4, ADR-09), giving the engine its first mechanism capable of defeating magic-byte and keyword guards that pure bitflip/havoc cannot climb (P11).

Deliverable

Splicing and dictionary/token mutation integrated into the Phase 4 mutation engine, demonstrated to discover coverage past a magic-byte guard fixture that the Phase 4 deterministic+havoc-only configuration fails to reach within a fixed exec budget.

Acceptance
  • splice mutation produces valid-length, byte-accounted-for crossover inputs with no out-of-bounds reads across source entries
  • dictionary mutation never introduces invalid UTF-8 into a target declared as requiring text input (I10)
  • the magic-byte-guard fixture (§17.5) is solved (new coverage past the guard) within a bounded exec budget when dictionary mutation is enabled, and not solved within the same budget when disabled — demonstrating P11 empirically
  • automatic token extraction produces at least one usable token on a fixture with a known comparison-embedded constant
Fixtures
  • conformance/phase5/magic_byte_guard — a target requiring an exact 4-byte magic value before reaching deeper code; the canonical P11 fixture
  • conformance/phase5/splice_crossover — two seed entries with known, disjoint coverage; validates the splice produces a plausible hybrid
  • conformance/phase5/dictionary_invalid_encoding — a token file containing a token that would produce invalid UTF-8 in a text-only target; validates the I10 fallback path
  • conformance/phase5/dual_magic_byte_guard — a target requiring two independent magic-byte guards to both hold; validates dictionary substitution composes across multiple mutation sites
Pitfalls
  • Splicing across two entries with incompatible structural assumptions (e.g., different record boundaries), producing inputs the target rejects trivially and that waste exec budget without discovery value.
  • Dictionary tokens becoming stale relative to the current target build (a magic value the target no longer checks), silently wasting mutation budget.
  • Over-reliance on dictionary mutation crowding out havoc's broader exploration — must remain one weighted option in the havoc stack, not a replacement (ADR-07's layering principle).
  • Auto-extracted tokens harvested from one code path being applied indiscriminately at mutation sites across the entire input, wasting substitution attempts where the token has no local relevance.

⬜ Phase 6 — The Power/Energy Schedule (AFLFast) and Seed Scheduling §18

Objectives

Replace the Phase 3 uniform-energy placeholder with the AFLFast Markov-chain-informed power schedule (§8.5, Böhme et al. 2016, P5), and implement favored-set-aware seed scheduling with queue aging (§8.7, ADR-11, ADR-12).

Deliverable

A scheduler that measurably shifts mutation trials toward low-frequency-path seeds relative to the Phase 3 uniform baseline, validated on a fixture with a deliberately rare branch.

Acceptance
  • a seed on a deliberately rare path receives strictly more mutation trials than a seed on a common path, holding queue size constant (P5 empirical validation)
  • no live queue entry is ever assigned zero energy across a full campaign run (I9)
  • favored-set recomputation produces a spanning set covering 100% of currently-known edges, matching the Phase 3 invariant under the new scheduler
  • queue-aging boost measurably increases selection frequency of a seed untouched beyond the configured threshold
Fixtures
  • conformance/phase6/rare_path_seed — a target with one branch reachable by only a small fraction of the seed corpus; validates AFLFast-style energy skew
  • conformance/phase6/zero_energy_guard — stress-tests the energy floor under an extreme hit-count skew
  • conformance/phase6/queue_aging — validates a long-untouched-but-favored seed regains scheduling priority
  • conformance/phase6/uniform_hit_count — every live path has an equally high hit count; validates the schedule degrades gracefully toward near-uniform energy rather than an ill-defined computation
Pitfalls
  • Scheduler bias collapse: an overly aggressive alpha exponent starves common-but-still-useful paths entirely, violating the spirit of I9 even while technically respecting the energy floor.
  • Recomputing the favored set too infrequently, letting the scheduler operate on a stale spanning set as the corpus grows.
  • Coupling energy accounting too tightly to wall-clock time rather than exec count, making the schedule's behavior throughput-dependent in a way that complicates reproducibility (P6 tension, resolved by keying on exec count).
  • Letting queue aging's boost compound without an upper bound, eventually inverting the schedule so stale seeds dominate over genuinely promising rare-path seeds.

⬜ Phase 7 — Crash Detection and Deduplication §19

Objectives

Implement crash classification from signal/exit-status and sanitizer-report parsing (§8.7, ADR-13), and deduplication via stack-hash and coverage-hash strategies (§8.8, ADR-14, I7).

Deliverable

A crash pipeline that classifies every non-Ok execution, deduplicates against prior crashes using the stack-hash/coverage-hash decision table, and persists a replayable artifact for each distinct crash group.

Acceptance
  • every sanitizer-flagged abort is classified as ExitKind::Crash, never as a benign non-zero exit (I12)
  • stack-hash dedup correctly merges two ASLR-shifted-but-identical crashes (relative-offset hashing validated)
  • crash-dedup accuracy meets the §4 target (≥95% precision, ≤3x recall inflation) on the benchmark suite
  • a saved crash artifact reproduces its recorded dedup key on replay ≥99% of the time on deterministic fixtures (I3)
Fixtures
  • conformance/phase7/asan_heap_overflow — a known ASan-detected heap-buffer-overflow target
  • conformance/phase7/ubsan_shift — a known UBSan-detected undefined-shift target
  • conformance/phase7/aslr_shifted_duplicate — the same crash captured under two different ASLR layouts; validates stack-hash relative-offset correctness
  • conformance/phase7/stripped_binary_fallback — a symbol-stripped target; validates the coverage-hash fallback path
  • conformance/phase7/multi_thread_race_report — a race-condition-detector sanitizer report spanning multiple threads; validates dedup handles a report shape beyond a single-frame stack-hash
Pitfalls
  • Hashing absolute stack addresses instead of relative offsets, causing every ASLR-shifted rerun of the same bug to false-split into a new crash group (violates the spirit of I7 by inflating apparent bug count).
  • Treating a sanitizer's non-abort warning output as a crash signal (over-classification) or missing a sanitizer abort buried in truncated stderr (under-classification, I12 violation).
  • Coverage-hash dedup silently merging two distinct root causes that happen to share a coverage signature — the documented, accepted risk of ADR-14's fallback, requiring the manual-review flag rather than silent merge.
  • Symbolizing every crash eagerly on the hot path rather than lazily on first triage access, needlessly taxing the crash-heavy phase of a campaign (e.g., early exploration against a fragile target).

⬜ Phase 8 — Corpus and Test-Case Minimization §20

Objectives

Implement corpus minimization (cmin) and test-case minimization (tmin) exactly per the §8.9 named-steps procedure, enforcing I6 (minimization never drops coverage) and preserving crash dedup keys under tmin.

Deliverable

A minimizer producing a reduced corpus with provably identical coverage union to the pre-minimization corpus, and a test-case minimizer that shrinks a crashing input while preserving its dedup key, both validated against fixtures with known expected outcomes.

Acceptance
  • cmin output's coverage union is byte-for-byte identical to the pre-minimization corpus's coverage union (I6, hard gate — abort minimization on any delta)
  • cmin completes within the §4 target (<5 minutes for 100k entries)
  • tmin-reduced crashing inputs reproduce the identical DedupKey as the original crash on replay
  • tmin reduces a synthetic large-crash fixture to within a known minimal expected size bound
Fixtures
  • conformance/phase8/cmin_redundant_corpus — a corpus with deliberate, known-redundant entries; validates exact expected reduction
  • conformance/phase8/tmin_known_minimal — a crash with a hand-verified minimal reproducer; validates tmin converges to it
  • conformance/phase8/cmin_coverage_delta_guard — a deliberately broken minimizer configuration; validates the I6 abort path triggers
  • conformance/phase8/tmin_dual_dependency — a crash requiring two non-adjacent byte ranges to both be present; validates tmin does not greedily delete one before discovering the dependency
Pitfalls
  • Over-minimization: a greedy set-cover implementation bug that drops an entry whose unique contribution wasn't correctly detected, silently violating I6 without tripping the delta assertion if the assertion itself is miscomputed.
  • tmin converging to a "minimal" input that reproduces a different crash than the original (dedup-key drift during reduction) — must re-validate the dedup key at every reduction step, not only at the end.
  • Running cmin synchronously on the hot campaign path instead of as an offline/periodic maintenance pass, stalling execs/second.
  • Running tmin's byte-normalization pass before the chunk-removal passes converge, wasting normalization effort on bytes that a later chunk-removal step would have deleted anyway.

⬜ Phase 9 — Persistent/In-Process Mode and Sanitizer Integration §21

Objectives

Implement the persistent/in-process execution mode (§8.3 contrast, ADR-05) to close the order-of-magnitude execs/second gap identified in §4/§34, and formalize sanitizer build-flag integration (ADR-17) as a first-class campaign configuration.

Deliverable

A persistent/in-process execution mode achieving the §4 target execs/second range (20k-100k/s on trivial parsers) with I5-enforced state cleanliness, and sanitizer integration available as a standard campaign configuration option.

Acceptance
  • persistent-mode execs/second on the trivial-parser fixture falls within the §4 target range and is at least a 10x improvement over the Phase 2 fork-mode baseline (§34-M1)
  • no state bleed detected across 10^5 persistent-mode iterations on a deterministic fixture (I5)
  • a deliberately state-leaking fixture triggers the fallback-to-fresh-fork recovery path within a bounded iteration window
  • sanitizer-enabled campaigns correctly classify every injected-bug fixture crash as ExitKind::Crash (I12, building on Phase 7)
Fixtures
  • conformance/phase9/persistent_stateful_leak — a target with deliberate global-state accumulation across calls, validates I5 leak detection and fallback
  • conformance/phase9/persistent_throughput_baseline — trivial parser, validates the execs/second target
  • conformance/phase9/sanitizer_enabled_known_bug — a target with an injected ASan-detectable bug, run once with and once without sanitizer flags, validating the detection-rate difference
  • conformance/phase9/time_dependent_target — a target whose behavior depends on wall-clock time; validates persistent mode's rapid iteration rate does not perturb it relative to fork-mode cadence
Pitfalls
  • Residual state leakage across persistent-mode iterations (heap fragmentation, static/global variable accumulation) silently corrupting coverage attribution for iteration N+1 based on iteration N's side effects — the canonical libFuzzer pitfall (§5 Reference Implementations).
  • File-descriptor accumulation across iterations exhausting the process's fd budget mid-campaign.
  • Assuming sanitizer overhead is negligible and defaulting it on for every campaign regardless of the execs/second budget, silently regressing throughput without operator awareness.
  • Setting the execution-recycling iteration cap too high in pursuit of maximum throughput, so leak accumulation before the mandatory fresh fork grows large enough to meaningfully skew coverage attribution for the last iterations before recycling.

⬜ Phase 10 — Structure-Aware/Grammar Fuzzing and Parallel Corpus Sync §22

Objectives

Add the structure-aware/grammar mutation hook (§8.4, ADR-10, Pham et al. 2019) for deeply-structured formats, and implement shared-directory parallel corpus synchronization (ADR-16) enabling multi-worker campaigns on a single node.

Deliverable

A structure-aware mutation hook demonstrated on a reference grammar fixture reaching coverage unreachable by byte-level mutation alone, plus N parallel local workers sharing one campaign directory with correctly deduplicated corpus and crash state across all workers.

Acceptance
  • the reference grammar plugin reaches a target coverage milestone within a bounded exec budget that byte-level-only mutation fails to reach in the same budget (mirrors the Phase 5 magic-byte empirical-validation pattern, now for structure)
  • corpus-sync latency across workers on a single node stays within the §4 target (<2 seconds)
  • no worker independently re-admits a coverage-hash-identical seed already present from a sibling worker as a spuriously "new" queue entry
  • a crash found by one worker is visible and correctly deduplicated by every other worker within the sync cadence window
Fixtures
  • conformance/phase10/grammar_reference_target — a structured-format fixture unreachable via byte mutation within a fixed budget, reachable via the grammar plugin
  • conformance/phase10/sync_dedup_race — two workers discovering the same coverage near-simultaneously; validates no duplicate admission
  • conformance/phase10/sync_crash_visibility — validates cross-worker crash-dedup propagation within the latency target
  • conformance/phase10/grammar_version_skew — a subset of workers running an older grammar-plugin version; validates malformed cross-version entries are rejected at sync time (T7)
Pitfalls
  • A grammar plugin that produces structurally invalid inputs the target rejects trivially, wasting exec budget without discovery value — the plugin interface must be validated against a "produces parseable output" fixture before being trusted.
  • Sync-induced duplicate admission: a race between two workers both locally deciding "new coverage" on the same edge before either has seen the other's sync update, transiently violating I1's "previously-unseen" framing until reconciliation catches up (acceptable only if bounded and self-correcting within the sync cadence).
  • Corpus-sync storms: a burst of simultaneous admissions across many workers overwhelming filesystem-watch-based sync, motivating the configurable poll-interval fallback.
  • Assuming every worker on a node has identical performance characteristics, so scheduler and sync-cadence tuning derived from one worker's behavior is silently miscalibrated for a heterogeneous-core node.

⬜ Phase 11 — Klees-et-al-Style Evaluation Harness, Chaos, and Perf Hardening §23

Objectives

Build the fuzz-eval evaluation harness implementing the Klees et al. 2018 methodology (bugs-over-trials with statistical significance) as the project's primary correctness/effectiveness gate, and harden the full system against chaos scenarios (crashing/hanging/OOMing targets, nondeterminism) and performance regression.

Deliverable

An evaluation harness that, run against the benchmark-target suite over N trials, reports deduplicated unique bugs found with a significance test, gates CI on both bug-finding effectiveness and execs/second non-regression, and a chaos-test suite demonstrating graceful handling of crashing/hanging/OOMing/nondeterministic targets.

Acceptance
  • the evaluation harness finds all known-injected bugs in the benchmark suite within a specified trial budget, with reported significance, on at least the same order of trials as comparable published methodology
  • execs/second on the Phase 9 persistent-mode benchmark shows no statistically meaningful regression across a CI run relative to the last tagged baseline
  • every chaos fixture (crashing/hanging/OOMing/nondeterministic target) is handled without campaign-wide stall, per I4/I8
  • a multi-day soak run resumes correctly across at least one forced mid-run restart with no queue or crash-artifact loss (I11)
Fixtures
  • conformance/phase11/lava_m_style_suite — the benchmark-target suite with known injected bugs
  • conformance/phase11/nondeterministic_target — a target with intentionally nondeterministic output, validating graceful degradation rather than corpus/crash corruption
  • conformance/phase11/chaos_combined — a single run combining crashing, hanging, and OOMing behavior across different queue entries in one campaign
  • conformance/phase11/soak_multi_day — a long-horizon run with a scheduled forced restart mid-campaign
  • conformance/phase11/harness_isolation_check — validates the evaluation harness's own trial-isolation setup does not itself introduce nondeterminism relative to a normal single-campaign run
Pitfalls
  • Reporting coverage percentage as the headline result instead of deduplicated unique bugs over trials — the exact methodological error Klees et al. 2018 was written to correct, and explicitly disallowed as a stand-alone metric by this project's own testing strategy (§28).
  • Insufficient trial count producing an evaluation result with no real statistical power, giving false confidence in either direction (a "no improvement" or "clear improvement" claim that doesn't survive a larger trial count).
  • Chaos fixtures that are too narrow (e.g., only testing hangs, never combining hang+crash+OOM in one campaign) missing interaction-effect bugs in the executor's classification logic.
  • Treating a single favorable evaluation run as sufficient evidence and skipping the differential-comparison mode against AFL++/libFuzzer, forfeiting the strongest available external validation of the bug-finding claim.
