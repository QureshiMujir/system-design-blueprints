CLI / campaign driver: not pictured as a box but wraps every component above; owns the campaign directory, starts/stops workers, and exposes replay/minimize/sync subcommands (§1, §10).

Target + coverage instrumentation: the compiler's SanitizerCoverage pass injects a call at every edge; the engine never rewrites the target's binary itself (ADR-02). This is the sole point where the fuzzer's fate depends on toolchain cooperation rather than its own code.

Shared coverage bitmap: an mmap'd byte array, one counter-ish slot per hashed edge, written by the target process and read by the engine after each execution (§8.1). It is the entire coverage signal — no call graphs, no data-flow, nothing else.

Fork server / in-process runner: the execution boundary. The fork server model spawns a stopped child once, then forks it repeatedly to avoid execve cost per input (AFL whitepaper); the in-process model instead calls the harness function directly in the fuzzer's address space (libFuzzer model), trading isolation for speed (§8.2, §33).

Execution loop: dispatches one input, arms a timeout, waits for exit/crash/timeout/OOM, and always leaves the bitmap and process state ready for the next execution — the untrusted target may misbehave, but the loop's own state may not become inconsistent (I5).

Coverage-feedback / is-interesting decision: the single deterministic gate that separates "this mutation mattered" from "discard" — new edge, or same edge with a new hit-count bucket, keeps the input (§8.3).

Corpus (queue) + on-disk store: durable record of every retained input plus its coverage signature, favored/energy metadata, and lineage — this is the evolving population the mutation engine draws from (§8.6).

Mutation engine: applies deterministic bitflip/arithmetic/interesting-value passes plus stochastic havoc, splicing, dictionary/token substitution, and optional structure-aware/grammar mutation (§8.4).

Power/energy scheduler: AFLFast's Markov-chain-informed schedule decides how many mutation trials a seed receives, favoring seeds that exercise low-frequency paths (§8.5, Böhme et al. 2016).

Crash detector + deduplicator: classifies a non-zero exit/signal/sanitizer abort, then dedups via coverage-hash or stack-hash so that one root cause yields one artifact, not thousands (§8.7).

Minimizer: two distinct passes — corpus minimization (drop redundant queue entries without losing coverage) and test-case minimization (shrink one crashing input while preserving the crash) (§8.8).

Sanitizer interface: ASan/UBSan/MSan compiled into the target turn silent memory corruption into a loud, immediately-detected abort — the crash detector's primary source of true positives (Serebryany et al. 2012).

8. Domain Model

8.1 Edge Coverage Encoding

Per the AFL scheme, each edge is identified by combining the current and previous instrumented location:

edge_id  = cur_loc XOR (prev_loc >> 1)
bitmap[edge_id mod MAP_SIZE] += 1   // saturating
prev_loc = cur_loc >> 1

MAP_SIZE is 65,536 (64 KiB) by default (§4). The >> 1 on prev_loc before storing avoids the map being dominated by same-edge-both-directions collisions (AFL whitepaper). This is the entirety of the coverage signal: no call stack, no data values, no path history beyond one hop.

8.2 Bitmap Collision Problem (CollAFL)

Because edge_id is hashed into a fixed 64 KiB space, two distinct real edges can collide into the same bitmap slot, undercounting true coverage and hiding new paths from the is-interesting decision (Gan et al. 2018, CollAFL). Collision probability grows with live-edge count (birthday-bound, quantified in §34). Mitigation: larger MAP_SIZE for large targets, or a collision-aware hash (CollAFL's approach) — recorded as ADR-08.

8.3 Fork-Server Protocol (sequence table)

Step Actor Action
1 Fuzzer spawn target under a stopped fork-server stub via execve, hold before main
2 Fork server (child) signal readiness on control pipe
3 Fuzzer write "go" token to control pipe with the next input already staged
4 Fork server fork() a fresh worker; worker execs the harness body on the staged input
5 Worker run to completion, exit/crash/signal
6 Fork server report worker exit status to fuzzer over status pipe
7 Fuzzer read bitmap, classify ExitKind, reset bitmap, go to step 3

Contrast — persistent/in-process model: steps 1-2 happen once; instead of forking per input, the harness loop calls the target function directly in-process (libFuzzer model) or the AFL persistent loop re-enters the same process N times before a fresh fork, trading isolation for a 10-100x execs/second gain (§34-M1). In-process execution requires I5 (clean child state) to hold across calls, not just across forks.

8.4 Is-Interesting Decision (named steps)

  1. Snapshot bitmap state before execution (all zero, per I2).
  2. Run the input; target writes edge hits into the bitmap.
  3. Diff bitmap against the campaign's cumulative "virgin map."
  4. If any never-seen edge index is now nonzero → new coverage, keep unconditionally.
  5. Else if a seen edge's hit count crosses into a new bucket (AFL uses log2-ish buckets: 1, 2, 3, 4-7, 8-15, 16-31, 32-127, 128+) → new edge-count bucket, keep.
  6. Else → discard input, no corpus mutation.
  7. On keep: merge bitmap into virgin map, create a QueueEntry, assign initial energy via §8.5.

8.5 Mutation Catalogue

Mutation Kind Mechanism When It Applies
Deterministic bitflip flip 1/2/4 consecutive bits at every offset early/exhaustive pass over small-to-medium seeds
Deterministic arithmetic add/subtract small integers to byte/word/dword at every offset targets near off-by-one and boundary conditions
Interesting values splice in known edge-case constants (0, -1, INT_MAX, etc.) targets integer-comparison guards
Havoc randomized stacked sequence of the above plus block insert/delete/duplicate bulk of the mutation budget after deterministic passes exhaust
Splicing crossover: combine byte ranges from two corpus entries escapes local optima the single-seed mutators cannot reach
Dictionary/token substitution insert known tokens (magic bytes, keywords, extracted comparisons) at mutation sites defeats magic-byte/keyword guards (P11)
Structure-aware/grammar mutate at the grammar-node level using an input model deeply-structured formats where byte-level mutation rarely produces valid structure (Pham et al. 2019, AFLSmart)

8.6 Power/Energy Schedule (AFLFast, equation)

AFLFast models the fuzzing process as a Markov chain over seeds, where a seed's transition/selection probability should be inversely related to how often its exercised path has already been hit. Energy assigned to seed s:

energy(s) ∝ 1 / hit_count(path(s))^alpha

with alpha a tunable exponent (AFLFast default favors low-frequency paths superlinearly). Seeds on paths hit rarely receive proportionally more mutation trials; seeds on paths hit often are throttled — this is what prevents the scheduler from re-exploring the same well-trodden region forever (Böhme et al. 2016; P5, I9).

8.7 Seed-Selection / Queue-Culling Model

  • Favored seeds: the smallest, fastest-executing seed covering each currently-known edge — a minimal spanning set, recomputed periodically (culling).
  • Non-favored seeds are still retained (I6 forbids dropping coverage) but receive lower scheduling priority, not zero (I9).
  • Queue aging: seeds untouched for a long duration receive an energy boost to prevent permanent starvation of rarely-revisited-but-still-favored seeds.

8.8 Crash Detection and Deduplication (decision table)

Signal Classification Dedup Key
Process exits 0 ExitKind::Ok n/a
Process killed by SIGSEGV/SIGABRT/SIGBUS/SIGFPE ExitKind::Crash stack-hash of unwound frames at fault
Sanitizer runtime prints an ASan/UBSan/MSan report and aborts ExitKind::Crash (sanitizer-flagged, I12) sanitizer report's bug-type + top frame, or coverage-hash fallback
Execution exceeds timeout ExitKind::Timeout input-hash (hangs are recorded, not stack-deduped)
Execution exceeds memory limit / OOM-killed ExitKind::Oom input-hash
Two crashes share a stack-hash merge into one crash group stack-hash
Two crashes share only a coverage-hash (stack unavailable/stripped) merge with lower confidence, flagged for manual review coverage-hash

Stack-hash dedup is precise when symbols are available but false-splits ASLR-shifted-but-identical crashes if addresses leak into the hash unfiltered (mitigation: hash relative offsets, not absolute addresses). Coverage-hash dedup is more robust to symbol stripping but false-merges distinct bugs that happen to share a coverage signature (I7).

8.9 Corpus and Test-Case Minimization (named steps — cmin/tmin)

cmin (corpus minimization): 1) compute the coverage bitmap for every queue entry; 2) run a greedy set-cover: repeatedly pick the entry covering the most currently-uncovered edges; 3) stop when the union equals the full corpus's coverage (I6 upper bound); 4) drop all unselected entries.

tmin (test-case minimization): 1) start from a crashing input; 2) attempt removing large chunks, replaying, keep the removal iff the crash (by dedup key) still reproduces; 3) repeat at decreasing chunk granularity down to single bytes; 4) attempt byte-value normalization (e.g., toward 0x00) on remaining bytes without losing the crash signature.

8.10 Input-to-State Correspondence (REDQUEEN, contrast)

Where dictionaries require a human or static-extraction step to know which tokens matter, REDQUEEN instruments comparison operations at runtime and directly captures the compared operand value, then patches that exact value into the mutated input at the corresponding offset (Aschermann et al. 2019). This is a lightweight, solver-free alternative to symbolic execution for defeating magic-byte/checksum guards (contrast §36) — noted as a natural Phase-10-adjacent extension, not a Phase-0-11 committed subsystem.

8.12 Malformed / Hard Examples

  • A bitmap collision (§8.2) makes two genuinely different edges look identical, hiding real new coverage from the is-interesting decision — symptom: coverage plateaus earlier than target complexity warrants.
  • A nondeterministic target (uninitialized memory, ASLR-sensitive pointer hashing in output, timing-dependent branches) pollutes feedback: the same input yields different bitmaps across runs, causing spurious corpus adds or spurious "unreproducible" crash flags (§24-T4).
  • A slow input (pathological O(n^2) parse, accidental sleep/IO) tanks execs/second campaign-wide if not isolated with a per-input timeout budget separate from the hang timeout.
  • A hang (infinite loop) must be caught by I4's watchdog; a hang that occurs only on 1-in-1000 runs of the same input due to nondeterminism is materially harder to triage than a deterministic hang.
  • A crash that will not reproduce — most commonly caused by ASLR/heap-layout drift, environment-variable differences, or genuine target nondeterminism; the replay sequence (§8.13) exists specifically to control for this.
  • A mutation that never reaches deeper code past a magic-byte check — the canonical case motivating dictionaries (P11) and REDQUEEN (§8.10).

8.13 Failure-Path Example — Replay Sequence

load crash metadata (input hash, build id, runtime flags, seed)
  -> verify target build hash matches recorded build id
  -> restore recorded runtime flags (sanitizer options, env)
  -> inject saved input bytes via the harness ABI
  -> observe exit classification
  -> compare dedup key (stack-hash or coverage-hash) to recorded key
  -> MATCH: replay success, artifact confirmed
  -> MISMATCH: flag flaky (§24-T4), re-run N times before quarantining as ground truth

8.14 Nondeterminism Detection Procedure

Nondeterministic targets (T4, §8.12) are diagnosed, not guessed at, via a fixed procedure: 1) select a candidate input (any admitted queue entry or any input flagged by a replay mismatch); 2) execute it N times (N configurable, default 10) under otherwise identical runtime conditions (same build_id, same env, ASLR held constant where the platform allows); 3) diff the resulting bitmaps pairwise across all N runs; 4) if any pair differs, the target is classified nondeterministic and tagged in campaign metadata; 5) once tagged, the is-interesting decision (§8.3) for that target widens its admission tolerance (a bitmap diff must persist across a repeat-check before being trusted as genuinely new coverage, not just admitted on a single observation) and the crash-dedup pipeline (§8.8) marks any crash from that target as flaky-checked rather than confirmed until it independently reproduces across the same N-run check. This procedure is the operational backbone of the nondeterminism-hunt runbook (§26).

8.15 Bitmap Saturation Response Procedure

When collision-rate telemetry (§13.10) crosses the §4 threshold, the response is a fixed, named sequence rather than an ad hoc tuning exercise: 1) confirm the breach is sustained (not a transient spike) over a rolling window; 2) snapshot the current bitmap density and live-edge estimate; 3) if the live-edge estimate materially exceeds the bitmap's designed capacity (§34's birthday-bound estimate), resize the bitmap upward (ADR-04's documented upsize path) and restart affected workers with the new size; 4) if resizing alone does not bring the collision rate back under threshold, recompile the target's instrumentation with CollAFL-style collision-aware hashing (§8.2, Gan et al. 2018) rather than continuing to grow the bitmap indefinitely; 5) re-baseline the campaign's virgin map after either change, since a bitmap-size or hash-function change invalidates prior coverage bookkeeping. This procedure backs the bitmap-saturation runbook (§26).
