Project Number: 229

Project Name: Fuzzing Engine (AFL/libFuzzer-like)

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Project 229 builds a from-scratch coverage-guided greybox fuzzing engine in Rust, in the tradition of AFL/AFL++ and libFuzzer. The engine's job is narrow and load-bearing: drive repeated execution of an instrumented target, harvest per-execution edge-coverage feedback from a shared bitmap, decide whether each mutated input is "interesting" (it touched a previously-unseen edge or edge-count bucket), retain interesting inputs in an evolving corpus, mutate corpus members to search for new coverage, and triage any crash the target raises into a deduplicated, reproducible artifact. It does not compile the target, does not inject coverage instrumentation itself, and does not diagnose the memory-safety violation inside a crash — those are delegated to the toolchain's SanitizerCoverage pass and to ASan/UBSan/MSan respectively. The engine is the search-and-feedback loop; the compiler and the sanitizer runtime are the sensors it reads. Coverage is the fitness function; execs/second is the throughput budget that fitness function gets evaluated against; the entire architecture downstream of this paragraph exists to maximize the product of the two.

Phase-0 deliverable (crate list):

  1. fuzz-core — shared ID types, error taxonomy, campaign-directory layout
  2. fuzz-coverage — bitmap model, edge encoding, is-interesting decision
  3. fuzz-executor — fork server, in-process runner, timeout/OOM handling
  4. fuzz-mutator — deterministic, havoc, splice, dictionary/token mutators
  5. fuzz-corpus — queue, favored-seed tracking, corpus store
  6. fuzz-schedule — power/energy schedule (AFLFast)
  7. fuzz-crash — crash detection, stack-hash/coverage-hash dedup
  8. fuzz-minimize — corpus minimization (cmin) and test-case minimization (tmin)
  9. fuzz-harness-abi — libFuzzer LLVMFuzzerTestOneInput / AFL persistent-loop compatible target ABI
  10. fuzz-cli — campaign driver, replay, minimize, sync subcommands
  11. fuzz-eval — Klees-et-al-style bugs-over-trials evaluation harness

Boundaries — Provides: the execution loop, the is-interesting decision, the mutation engine, corpus management and minimization, the power schedule, crash detection and dedup, persistent-mode driving, structure-aware mutation hooks. Delegates: compile-time coverage instrumentation to the compiler's SanitizerCoverage pass (__sanitizer_cov_trace_pc_guard, per the sanitizer runtime docs); crash root-causing to ASan/UBSan/MSan (Serebryany et al. 2012); process-isolation primitives to the OS. Does NOT provide: a symbolic/concolic execution engine — contrast SAGE (Godefroid, Levin & Molnar 2008) and KLEE (Cadar, Dunbar & Engler 2008), both of which solve path constraints precisely via an SMT/theorem-prover backend; this project never invokes a constraint solver. Also excluded: a static analyzer, a decompiler, a full grammar-authoring toolchain (grammar plugins are a mutator input, not a built subsystem), a distributed multi-machine cluster manager (a shared-directory corpus-sync primitive only).

Non-goals: not a whitebox/symbolic engine (SAGE/KLEE contrast above — path explosion and per-path solver cost make it non-competitive on execs/second, the master metric here); not a static analyzer; not a general dynamic-binary-instrumentation (DBI) framework; not a hypervisor-based kernel/VM fuzzer.

Fuzzing style: coverage-guided greybox fuzzing — the target is a black box for correctness but a grey box for feedback: cheap compile-time instrumentation exposes just enough signal (edge coverage) to direct search without symbolic reasoning (Manès et al. 2019, "The Art, Science, and Engineering of Fuzzing").

Deployment model: (a) a CLI fuzzer (fuzz-cli) owning a campaign directory; (b) a fork-server or in-process harness compiled against the target, exposing the libFuzzer LLVMFuzzerTestOneInput ABI or an AFL-style persistent loop; (c) an on-disk corpus directory (queue + crashes + metadata + stats) as the campaign's durable state. No network service, no daemon process beyond the fuzzer's own worker loop, no database — filesystem-first, single-node by default, corpus-sync-extensible for parallel runs.

Users/operators: security engineers running local or CI fuzzing campaigns against libraries and parsers; compiler/runtime engineers validating a toolchain; the operator runs the CLI, watches corpus growth and crash artifacts on a dashboard (§26), and uses the minimizer/replay tools during triage.

What later phases unlock: Phase 4-5 (mutation engine, dictionary) unlock discovery past shallow guards; Phase 6 (power schedule) unlocks efficient time allocation across a large corpus; Phase 9 (persistent mode + sanitizers) unlocks execs/second an order of magnitude above fork-per-input; Phase 10 (structure-aware + parallel sync) unlocks deep-format targets and multi-core scaling; Phase 11 (evaluation harness) unlocks a defensible, Klees-et-al-compliant claim of "found N unique bugs" rather than a coverage screenshot.

Rust + rationale: chosen for (1) memory safety in the orchestrator despite it constantly touching raw shared memory (the coverage bitmap) and supervising an adversarial, crash-prone child process; (2) zero-cost abstractions keep the hot per-execution path (bitmap touch, is-interesting check) allocation-free; (3) straightforward FFI to the C/C++ compiler-rt SanitizerCoverage runtime and to libFuzzer-ABI targets; (4) a mature systems ecosystem (libc/nix-style crates) for fork/exec/ptrace/mmap/signals. Rejected languages: C/C++ — matches AFL++/libFuzzer's own implementation language but reintroduces, inside the fuzzer's own orchestrator, the exact memory-corruption bug class the fuzzer exists to find in targets; Go — GC pauses tax the hot per-exec dispatch path directly, harming execs/second, the master metric (§4); Python — orders of magnitude too slow for per-exec dispatch at any interesting throughput.

Prerequisites: program instrumentation (SanitizerCoverage, edge encoding, bitmap collision math); POSIX process control (fork/exec/ptrace/signals, shared memory, pipes); mutation-strategy design (bitflip/arithmetic/havoc/splice/dictionary/grammar); basic statistics (trial counts, significance testing) for the Klees-et-al evaluation methodology.

Timeline: Phase 0 (skeleton + harness ABI + CI): 1-2 weeks. Phases 1-3 (instrumentation, fork server, coverage-feedback loop): 4-6 weeks. Phases 4-6 (mutation, dictionary/splicing, power schedule): 4-6 weeks. Phases 7-9 (crash dedup, minimization, persistent mode + sanitizers): 4-6 weeks. Phases 10-11 (structure-aware fuzzing, parallel sync, evaluation harness): 4-6 weeks. Total: roughly 4-6 months to a benchmark-validated, Klees-et-al-gated release.

Deferrals: PhaseDeferred("§10 Phase 10 — structure-aware/grammar fuzzing hardening") full context-free-grammar mutators beyond token dictionaries; PhaseDeferred("§10 Phase 10 — parallel corpus sync") multi-machine distributed fuzzing beyond a shared-directory sync primitive; PhaseDeferred("§36 Alternative Architectures — symbolic hybrid") concolic-assisted guard solving (REDQUEEN's input-to-state approach is adopted instead per §8/§32); PhaseDeferred("§31 Scalability Analysis — snapshot fuzzing") kernel/VM-snapshot execution for stateful targets.

2. Why Build This

coverage-guided search as evolutionary computation with a one-bit fitness signal · execs/second as the master engineering metric (fork-server and persistent-mode design exist solely to raise it) · compiler-instrumentation internals (SanitizerCoverage, edge encoding, bitmap-collision math per CollAFL) · the mutation-strategy design space (deterministic vs. stochastic havoc vs. structure-aware/grammar) · the AFLFast power-schedule/Markov-chain reasoning about seed energy allocation · crash triage and deduplication under noisy, sometimes-nondeterministic signals · rigorous empirical evaluation methodology for security tooling (Klees et al. 2018) — proving effectiveness instead of asserting it · the adjacent-technique contrast with symbolic/concolic execution (SAGE, KLEE) and why greybox mutation wins on throughput while losing on guard-precision · sanitizer integration as a force-multiplier on bug visibility, not just crash detection · corpus/test-case minimization as a distinct, coverage-preserving optimization problem.

What Mastery Looks Like

  • Can explain why "new edge → keep" alone turns random mutation into directed search, and trace that claim to the AFL whitepaper (Phase 3).
  • Can quantify the execs/second gap between fork() and persistent mode and justify the fork-server architecture from that number alone (Phase 2, Phase 9).
  • Can design a bitmap-collision experiment and reason about CollAFL-style false negatives in coverage feedback (Phase 1).
  • Can derive and implement AFLFast's power-schedule equation and demonstrate it shifts energy toward low-frequency-path seeds (Phase 6).
  • Can dedup two crashes correctly with both stack-hash and coverage-hash strategies and explain a failure mode specific to each (Phase 7).
  • Can run a Klees-et-al-compliant bug-finding evaluation with N trials and a significance test, and explain why a single coverage screenshot is not evidence (Phase 11).
  • Can explain, with a concrete example, why a 4-byte magic-value guard defeats naive mutation, and how a dictionary or REDQUEEN-style input-to-state correspondence solves it (Phase 5).
  • Can articulate why this project deliberately excludes symbolic execution and what throughput/precision trade-off that decision encodes (§36).

CLI / campaign driver: not pictured as a box but wraps every component above; owns the campaign directory, starts/stops workers, and exposes replay/minimize/sync subcommands (§1, §10).

Target + coverage instrumentation: the compiler's SanitizerCoverage pass injects a call at every edge; the engine never rewrites the target's binary itself (ADR-02). This is the sole point where the fuzzer's fate depends on toolchain cooperation rather than its own code.

Shared coverage bitmap: an mmap'd byte array, one counter-ish slot per hashed edge, written by the target process and read by the engine after each execution (§8.1). It is the entire coverage signal — no call graphs, no data-flow, nothing else.

Fork server / in-process runner: the execution boundary. The fork server model spawns a stopped child once, then forks it repeatedly to avoid execve cost per input (AFL whitepaper); the in-process model instead calls the harness function directly in the fuzzer's address space (libFuzzer model), trading isolation for speed (§8.2, §33).

Execution loop: dispatches one input, arms a timeout, waits for exit/crash/timeout/OOM, and always leaves the bitmap and process state ready for the next execution — the untrusted target may misbehave, but the loop's own state may not become inconsistent (I5).

Coverage-feedback / is-interesting decision: the single deterministic gate that separates "this mutation mattered" from "discard" — new edge, or same edge with a new hit-count bucket, keeps the input (§8.3).

Corpus (queue) + on-disk store: durable record of every retained input plus its coverage signature, favored/energy metadata, and lineage — this is the evolving population the mutation engine draws from (§8.6).

Mutation engine: applies deterministic bitflip/arithmetic/interesting-value passes plus stochastic havoc, splicing, dictionary/token substitution, and optional structure-aware/grammar mutation (§8.4).

Power/energy scheduler: AFLFast's Markov-chain-informed schedule decides how many mutation trials a seed receives, favoring seeds that exercise low-frequency paths (§8.5, Böhme et al. 2016).

Crash detector + deduplicator: classifies a non-zero exit/signal/sanitizer abort, then dedups via coverage-hash or stack-hash so that one root cause yields one artifact, not thousands (§8.7).

Minimizer: two distinct passes — corpus minimization (drop redundant queue entries without losing coverage) and test-case minimization (shrink one crashing input while preserving the crash) (§8.8).

Sanitizer interface: ASan/UBSan/MSan compiled into the target turn silent memory corruption into a loud, immediately-detected abort — the crash detector's primary source of true positives (Serebryany et al. 2012).

6. Design Principles

  • P1 — Coverage is the fitness function. An input is kept iff it exercises a new edge (or new hit-count bucket); this single greedy rule is what turns random mutation into directed search — the AFL insight (AFL whitepaper; §8.3).
  • P2 — Execs/second is the master metric. A fuzzer twice as fast finds twice as many bugs in the same wall-clock; the fork server and persistent mode exist solely to amortize process-startup cost (AFL whitepaper, libFuzzer docs; §4, §30).
  • P3 — Evaluation must follow Klees et al. Measure bugs found (deduplicated against ground truth) over many trials with statistical significance; never report a single coverage screenshot as evidence of effectiveness (Klees et al. 2018; §28).
  • P4 — The bitmap is reset, not accumulated, per execution. Coverage must be attributable to exactly one input; cross-execution bleed corrupts the is-interesting decision (I2).
  • P5 — Energy is not uniform. Seeds exercising low-frequency paths get more mutation trials; uniform scheduling wastes cycles on already-well-explored seeds (Böhme et al. 2016, AFLFast; §8.5).
  • P6 — A crash is worthless if it cannot be replayed. Every crash artifact carries its input bytes, the harness/target build identity, and enough runtime metadata to reproduce deterministically (I3, §8.7).
  • P7 — Deduplication trades precision against recall deliberately. Stack-hash and coverage-hash strategies each have a distinct false-merge and false-split failure mode; the choice is a stated ADR (ADR-15), not an accident.
  • P8 — Minimization must never reduce coverage. Corpus minimization (cmin) preserves the union of edges covered by the full corpus; test-case minimization (tmin) preserves the specific crash signature (§8.8, I6).
  • P9 — A hang is a first-class outcome, not an error. Timeout enforcement is unconditional; a hanging input must never block the campaign (I4).
  • P10 — Mutation strategy is layered, not monolithic. Deterministic passes, havoc, splicing, dictionary/token, and structure-aware mutation each cover a different part of the search space and are composed, not chosen exclusively (§8.4).
  • P11 — Magic bytes and checksums are solved by information, not brute force. A 4-byte guard is astronomically unlikely to be guessed randomly; dictionaries and REDQUEEN's input-to-state correspondence exist because pure havoc cannot climb that wall (Aschermann et al. 2019; §34).
  • P12 — The fork server's child state must be clean per execution. No cross-input contamination of file descriptors, heap state, or global variables; persistent mode's speed gain is void if it is not deterministic (I5).
  • P13 — Sanitizers turn silent corruption into loud, detectable failure. Coverage-guided fuzzing without a sanitizer finds far fewer true bugs, because most memory-safety violations are otherwise unobservable (Serebryany et al. 2012; §8.7).
  • P14 — Coverage plateaus; levers exist, but the plateau is expected, not a bug. Diminishing new-edge discovery over time is normal; the response is dictionaries, structure-aware mutation, or REDQUEEN-style techniques, not panic (§31, §32).

Debugging methodology: every invariant violation must be diagnosable from three artifacts alone — the saved input bytes, the structured event log entry naming the invariant ID, and the campaign's build/version metadata. Triage order: (1) reproduce with the exact saved input under the exact target build (I3); (2) if it fails to reproduce, suspect nondeterminism (§24-T4) or ASLR/environment drift before doubting the mutator; (3) only after reproduction, escalate to bitmap/coverage-hash inspection (I1, I2) or dedup logic (I7). Never "fix" an invariant violation by weakening the invariant — the correct response is always either a bug fix or a documented, ADR-recorded relaxation.

8. Domain Model

8.1 Edge Coverage Encoding

Per the AFL scheme, each edge is identified by combining the current and previous instrumented location:

edge_id  = cur_loc XOR (prev_loc >> 1)
bitmap[edge_id mod MAP_SIZE] += 1   // saturating
prev_loc = cur_loc >> 1

MAP_SIZE is 65,536 (64 KiB) by default (§4). The >> 1 on prev_loc before storing avoids the map being dominated by same-edge-both-directions collisions (AFL whitepaper). This is the entirety of the coverage signal: no call stack, no data values, no path history beyond one hop.

8.2 Bitmap Collision Problem (CollAFL)

Because edge_id is hashed into a fixed 64 KiB space, two distinct real edges can collide into the same bitmap slot, undercounting true coverage and hiding new paths from the is-interesting decision (Gan et al. 2018, CollAFL). Collision probability grows with live-edge count (birthday-bound, quantified in §34). Mitigation: larger MAP_SIZE for large targets, or a collision-aware hash (CollAFL's approach) — recorded as ADR-08.

8.3 Fork-Server Protocol (sequence table)

Step Actor Action
1 Fuzzer spawn target under a stopped fork-server stub via execve, hold before main
2 Fork server (child) signal readiness on control pipe
3 Fuzzer write "go" token to control pipe with the next input already staged
4 Fork server fork() a fresh worker; worker execs the harness body on the staged input
5 Worker run to completion, exit/crash/signal
6 Fork server report worker exit status to fuzzer over status pipe
7 Fuzzer read bitmap, classify ExitKind, reset bitmap, go to step 3

Contrast — persistent/in-process model: steps 1-2 happen once; instead of forking per input, the harness loop calls the target function directly in-process (libFuzzer model) or the AFL persistent loop re-enters the same process N times before a fresh fork, trading isolation for a 10-100x execs/second gain (§34-M1). In-process execution requires I5 (clean child state) to hold across calls, not just across forks.

8.4 Is-Interesting Decision (named steps)

  1. Snapshot bitmap state before execution (all zero, per I2).
  2. Run the input; target writes edge hits into the bitmap.
  3. Diff bitmap against the campaign's cumulative "virgin map."
  4. If any never-seen edge index is now nonzero → new coverage, keep unconditionally.
  5. Else if a seen edge's hit count crosses into a new bucket (AFL uses log2-ish buckets: 1, 2, 3, 4-7, 8-15, 16-31, 32-127, 128+) → new edge-count bucket, keep.
  6. Else → discard input, no corpus mutation.
  7. On keep: merge bitmap into virgin map, create a QueueEntry, assign initial energy via §8.5.

8.5 Mutation Catalogue

Mutation Kind Mechanism When It Applies
Deterministic bitflip flip 1/2/4 consecutive bits at every offset early/exhaustive pass over small-to-medium seeds
Deterministic arithmetic add/subtract small integers to byte/word/dword at every offset targets near off-by-one and boundary conditions
Interesting values splice in known edge-case constants (0, -1, INT_MAX, etc.) targets integer-comparison guards
Havoc randomized stacked sequence of the above plus block insert/delete/duplicate bulk of the mutation budget after deterministic passes exhaust
Splicing crossover: combine byte ranges from two corpus entries escapes local optima the single-seed mutators cannot reach
Dictionary/token substitution insert known tokens (magic bytes, keywords, extracted comparisons) at mutation sites defeats magic-byte/keyword guards (P11)
Structure-aware/grammar mutate at the grammar-node level using an input model deeply-structured formats where byte-level mutation rarely produces valid structure (Pham et al. 2019, AFLSmart)

8.6 Power/Energy Schedule (AFLFast, equation)

AFLFast models the fuzzing process as a Markov chain over seeds, where a seed's transition/selection probability should be inversely related to how often its exercised path has already been hit. Energy assigned to seed s:

energy(s) ∝ 1 / hit_count(path(s))^alpha

with alpha a tunable exponent (AFLFast default favors low-frequency paths superlinearly). Seeds on paths hit rarely receive proportionally more mutation trials; seeds on paths hit often are throttled — this is what prevents the scheduler from re-exploring the same well-trodden region forever (Böhme et al. 2016; P5, I9).

8.7 Seed-Selection / Queue-Culling Model

  • Favored seeds: the smallest, fastest-executing seed covering each currently-known edge — a minimal spanning set, recomputed periodically (culling).
  • Non-favored seeds are still retained (I6 forbids dropping coverage) but receive lower scheduling priority, not zero (I9).
  • Queue aging: seeds untouched for a long duration receive an energy boost to prevent permanent starvation of rarely-revisited-but-still-favored seeds.

8.8 Crash Detection and Deduplication (decision table)

Signal Classification Dedup Key
Process exits 0 ExitKind::Ok n/a
Process killed by SIGSEGV/SIGABRT/SIGBUS/SIGFPE ExitKind::Crash stack-hash of unwound frames at fault
Sanitizer runtime prints an ASan/UBSan/MSan report and aborts ExitKind::Crash (sanitizer-flagged, I12) sanitizer report's bug-type + top frame, or coverage-hash fallback
Execution exceeds timeout ExitKind::Timeout input-hash (hangs are recorded, not stack-deduped)
Execution exceeds memory limit / OOM-killed ExitKind::Oom input-hash
Two crashes share a stack-hash merge into one crash group stack-hash
Two crashes share only a coverage-hash (stack unavailable/stripped) merge with lower confidence, flagged for manual review coverage-hash

Stack-hash dedup is precise when symbols are available but false-splits ASLR-shifted-but-identical crashes if addresses leak into the hash unfiltered (mitigation: hash relative offsets, not absolute addresses). Coverage-hash dedup is more robust to symbol stripping but false-merges distinct bugs that happen to share a coverage signature (I7).

8.9 Corpus and Test-Case Minimization (named steps — cmin/tmin)

cmin (corpus minimization): 1) compute the coverage bitmap for every queue entry; 2) run a greedy set-cover: repeatedly pick the entry covering the most currently-uncovered edges; 3) stop when the union equals the full corpus's coverage (I6 upper bound); 4) drop all unselected entries.

tmin (test-case minimization): 1) start from a crashing input; 2) attempt removing large chunks, replaying, keep the removal iff the crash (by dedup key) still reproduces; 3) repeat at decreasing chunk granularity down to single bytes; 4) attempt byte-value normalization (e.g., toward 0x00) on remaining bytes without losing the crash signature.

8.10 Input-to-State Correspondence (REDQUEEN, contrast)

Where dictionaries require a human or static-extraction step to know which tokens matter, REDQUEEN instruments comparison operations at runtime and directly captures the compared operand value, then patches that exact value into the mutated input at the corresponding offset (Aschermann et al. 2019). This is a lightweight, solver-free alternative to symbolic execution for defeating magic-byte/checksum guards (contrast §36) — noted as a natural Phase-10-adjacent extension, not a Phase-0-11 committed subsystem.

8.12 Malformed / Hard Examples

  • A bitmap collision (§8.2) makes two genuinely different edges look identical, hiding real new coverage from the is-interesting decision — symptom: coverage plateaus earlier than target complexity warrants.
  • A nondeterministic target (uninitialized memory, ASLR-sensitive pointer hashing in output, timing-dependent branches) pollutes feedback: the same input yields different bitmaps across runs, causing spurious corpus adds or spurious "unreproducible" crash flags (§24-T4).
  • A slow input (pathological O(n^2) parse, accidental sleep/IO) tanks execs/second campaign-wide if not isolated with a per-input timeout budget separate from the hang timeout.
  • A hang (infinite loop) must be caught by I4's watchdog; a hang that occurs only on 1-in-1000 runs of the same input due to nondeterminism is materially harder to triage than a deterministic hang.
  • A crash that will not reproduce — most commonly caused by ASLR/heap-layout drift, environment-variable differences, or genuine target nondeterminism; the replay sequence (§8.13) exists specifically to control for this.
  • A mutation that never reaches deeper code past a magic-byte check — the canonical case motivating dictionaries (P11) and REDQUEEN (§8.10).

8.13 Failure-Path Example — Replay Sequence

load crash metadata (input hash, build id, runtime flags, seed)
  -> verify target build hash matches recorded build id
  -> restore recorded runtime flags (sanitizer options, env)
  -> inject saved input bytes via the harness ABI
  -> observe exit classification
  -> compare dedup key (stack-hash or coverage-hash) to recorded key
  -> MATCH: replay success, artifact confirmed
  -> MISMATCH: flag flaky (§24-T4), re-run N times before quarantining as ground truth

8.14 Nondeterminism Detection Procedure

Nondeterministic targets (T4, §8.12) are diagnosed, not guessed at, via a fixed procedure: 1) select a candidate input (any admitted queue entry or any input flagged by a replay mismatch); 2) execute it N times (N configurable, default 10) under otherwise identical runtime conditions (same build_id, same env, ASLR held constant where the platform allows); 3) diff the resulting bitmaps pairwise across all N runs; 4) if any pair differs, the target is classified nondeterministic and tagged in campaign metadata; 5) once tagged, the is-interesting decision (§8.3) for that target widens its admission tolerance (a bitmap diff must persist across a repeat-check before being trusted as genuinely new coverage, not just admitted on a single observation) and the crash-dedup pipeline (§8.8) marks any crash from that target as flaky-checked rather than confirmed until it independently reproduces across the same N-run check. This procedure is the operational backbone of the nondeterminism-hunt runbook (§26).

8.15 Bitmap Saturation Response Procedure

When collision-rate telemetry (§13.10) crosses the §4 threshold, the response is a fixed, named sequence rather than an ad hoc tuning exercise: 1) confirm the breach is sustained (not a transient spike) over a rolling window; 2) snapshot the current bitmap density and live-edge estimate; 3) if the live-edge estimate materially exceeds the bitmap's designed capacity (§34's birthday-bound estimate), resize the bitmap upward (ADR-04's documented upsize path) and restart affected workers with the new size; 4) if resizing alone does not bring the collision rate back under threshold, recompile the target's instrumentation with CollAFL-style collision-aware hashing (§8.2, Gan et al. 2018) rather than continuing to grow the bitmap indefinitely; 5) re-baseline the campaign's virgin map after either change, since a bitmap-size or hash-function change invalidates prior coverage bookkeeping. This procedure backs the bitmap-saturation runbook (§26).

12. Phase 0 — Skeleton, Harness ABI, and CI

12.1 Objectives

Stand up the workspace skeleton, define the campaign-directory layout, implement the target harness ABI surface (ADR-18) so an example target can be linked and driven end to end even before instrumentation exists, and wire CI so every subsequent phase has a regression backstop.

12.2 Detailed Implementation Steps

  • initialize the Rust workspace with the eleven crates from §1's Phase-0 deliverable list
  • define fuzz-core's ID types (InputId, CrashId, BuildId, Seed) per §11
  • define the campaign-directory layout on disk (queue/, crashes/, metadata/, stats file) per ADR-21
  • implement the Harness trait (§11) with a stub run_one that shells out to a linked example target
  • implement the AFL-persistent-loop-compatible and libFuzzer-LLVMFuzzerTestOneInput-compatible entrypoints (ADR-18)
  • build two trivial example targets under examples/: one libFuzzer-ABI, one AFL-persistent-ABI
  • implement the error taxonomy (FuzzError, §11) and structured JSON logging (ADR-22)
  • implement deterministic seed/PRNG initialization and persist it in campaign metadata (P6 prerequisite)
  • stand up CI (ci.yml) building the workspace and running unit tests on Linux x86_64
  • write BUILD_PLAN.md documenting the pinned toolchain (ADR-26 prerequisite)
  • implement campaign-directory resume/consistency check (I11 prerequisite) as a no-op stub validated by a fixture

12.3 Deliverable

A runnable fuzz-cli that can link either example harness, dispatch one input to it via the ABI, capture its exit status, and write a structured log line — with zero coverage feedback wired yet (that is Phase 1's job).

12.4 Acceptance Criteria

  • workspace builds reproducibly under the pinned toolchain
  • both example harnesses (libFuzzer-ABI, AFL-persistent-ABI) link and run one input successfully
  • CI passes on Linux x86_64
  • campaign-directory layout is created and resumable across a restart (I11 stub validated)
  • structured JSON log line emitted per dispatched input

12.5 Conformance Fixtures

  • conformance/phase0/libfuzzer_harness_ok — trivial libFuzzer-ABI target that always exits 0
  • conformance/phase0/afl_persistent_harness_ok — trivial AFL-persistent-ABI target that always exits 0
  • conformance/phase0/campaign_resume_after_restart — kills and restarts the CLI mid-campaign, asserts directory layout intact
  • conformance/phase0/concurrent_invocation_guard — launches two CLI instances against the same campaign directory, validates the second is rejected

12.6 Pitfalls

  • ABI mismatch: assuming the libFuzzer signature when the target actually exposes the AFL persistent-loop shape, causing a silent no-op dispatch.
  • Non-deterministic seed initialization at startup, breaking replay before replay tooling even exists (P6).
  • Treating the campaign directory as ephemeral instead of the durable state it is from day one (I11), forcing a painful retrofit later.
  • Hardcoding an assumption about which ABI mode a target uses instead of recording it explicitly in campaign configuration, so the ambiguity resurfaces on every resume.

12.7 Performance Concerns

  • JSON logging allocation overhead on the dispatch hot path — must be feature-gated or buffered from the start, since Phase 2-3 will make this path execute thousands of times per second.
  • Process-spawn overhead for the stub run_one is expected to be high in Phase 0 and is not yet a target for optimization (that begins in Phase 2).

12.8 Edge Cases

  • missing or malformed campaign-directory metadata on first run (must initialize cleanly, not crash)
  • a harness binary that is present but not executable
  • an example target that unexpectedly exits non-zero even on trivial input (must be classified, not ignored)
  • concurrent CLI invocations against the same campaign directory (must detect and reject, not silently corrupt shared state)

12.9 Failure Analysis

Primary failure mode at this phase is ABI ambiguity — the CLI dispatches to the wrong entrypoint shape and silently gets no signal back. Blast radius is total (nothing downstream works), but containment is cheap: an explicit ABI-detection/declaration step in campaign config, validated by the Phase 0.5 conformance fixtures before any coverage work begins.

12.10 Operational Notes

Emit a structured "campaign started" event containing toolchain version, ABI mode, and campaign-directory path on every startup — this becomes the anchor record every later runbook (§26) references first.

13. Phase 1 — Coverage Instrumentation and the Shared Bitmap

13.1 Objectives

Wire the compiler's SanitizerCoverage output into a shared-memory bitmap the engine can read after each execution, implement the edge-encoding scheme (§8.1, P1), and establish collision monitoring (§8.2, CollAFL, Gan et al. 2018).

13.2 Detailed Implementation Steps

  • implement the CoverageMap/Bitmap types (§11) backed by a mmap'd shared-memory region, 64 KiB default (ADR-04, I2)
  • implement the edge_id = cur_loc XOR (prev_loc >> 1) encoding exactly as in §8.1
  • provide the __sanitizer_cov_trace_pc_guard callback surface the target's SanitizerCoverage instrumentation calls into (ADR-02, the SanitizerCoverage interface spec)
  • implement Bitmap::reset and call it unconditionally before every execution (I2)
  • implement the virgin-map diff (diff_against_virgin) that Phase 3's is-interesting decision will consume
  • implement collision-rate telemetry: track observed edge_id collisions per campaign (P1, CollAFL)
  • implement bitmap-size configuration and a documented upsize path for high-edge-count targets (ADR-04)
  • add guard-page bounds checking around the shared bitmap region to catch out-of-bounds writes from a misbehaving target

13.3 Deliverable

Instrumented example targets (compiled with SanitizerCoverage) that emit a valid, boundedly-collision-rate edge bitmap the engine can read and reset deterministically across repeated executions.

13.4 Acceptance Criteria

  • edge coverage is deterministic across repeated runs of the same input on a deterministic target (I2 corollary)
  • bitmap collision rate stays under 5% at the benchmark target's live-edge count (§4)
  • no bitmap writes observed outside the allocated shared-memory region across 10^6 executions
  • bitmap reset completes in under 10 microseconds

13.5 Conformance Fixtures

  • conformance/phase1/basic_edges — a target with a small, hand-countable set of branches, used to validate exact edge_id computation
  • conformance/phase1/collision_stress — a target with a deliberately high live-edge count to exercise CollAFL-style collision measurement
  • conformance/phase1/saturated_bitmap — a target designed to fill the bitmap near capacity, validating no overflow/corruption
  • conformance/phase1/zero_edge_target — a trivial no-op harness with no instrumented branches, validating the empty-bitmap case is not misreported as corruption

13.6 Pitfalls

  • Bitmap collision explosion from poor edge-hash entropy — silently undercounts coverage and stalls the is-interesting decision before Phase 3 even runs (§8.2).
  • Forgetting to reset the bitmap between forked children under the fork-server model built in Phase 2, contaminating coverage attribution (I2 dependency).
  • Shared-memory region size mismatch between the instrumented target's compiled expectation and the engine's runtime allocation, causing out-of-bounds writes.
  • Assuming instrumentation overhead is uniform across targets and skipping per-target overhead measurement, masking a pathological slowdown on one specific target family.

13.7 Performance Concerns

  • Branch-predictor disruption from the instrumentation callback itself — measured and bounded against the ADR-02 rationale for compile-time instrumentation being the lowest-overhead option.
  • Cache-line contention on the shared bitmap under future multi-worker parallel fuzzing (Phase 10 concern, flagged early here).

13.8 Edge Cases

  • a target that forks internally without the coverage runtime re-initializing prev_loc correctly
  • edge IDs at the exact boundary of MAP_SIZE (index 0 and index MAP_SIZE-1)
  • a target compiled against a different SanitizerCoverage ABI version than the engine expects (ADR-02, §27 compatibility)
  • a target with zero instrumented edges (e.g., a trivial no-op harness), which must not be treated as a bitmap-corruption signal

13.9 Failure Analysis

Coverage corruption at this phase invalidates every downstream decision the scheduler (Phase 6) and the corpus (Phase 3) will ever make — a silent bitmap bug looks like a coverage plateau, not a crash, making it one of the hardest classes to diagnose late. Recovery is runtime quarantine: flag the target's instrumentation build as suspect and fall back to a smaller bitmap or a fresh recompile.

13.10 Operational Notes

Export bitmap density (fraction of slots ever set) and collision rate as first-class campaign metrics from this phase forward — both feed directly into the §26 coverage-plateau runbook.

14. Phase 2 — The Fork Server and the Execution Loop

14.1 Objectives

Implement the fork-server protocol (§8.3, ADR-05) and the execution loop that dispatches inputs, enforces timeouts, and classifies exit status into ExitKind (I8), establishing the execs/second baseline the rest of the project is measured against (P2).

14.2 Detailed Implementation Steps

  • implement the fork-server control/status pipe handshake exactly per the §8.3 sequence table
  • implement the stopped-child-then-repeated-fork execution pattern (ADR-05, AFL whitepaper)
  • implement per-execution timeout enforcement via a watchdog timer (I4)
  • implement hard-kill escalation for a child that ignores a soft-timeout signal
  • implement ExitKind classification (Ok/Crash/Timeout/Oom) from wait-status decoding (I8)
  • implement child-process reaping to avoid zombie accumulation
  • implement stdout/stderr capture per execution (needed later for sanitizer-report parsing in Phase 7)
  • implement per-exec metadata accounting (duration, bitmap pointer) feeding RunResult (§11)
  • implement execs/second telemetry as a live counter (P2)

14.3 Deliverable

A stable fork-server-backed executor achieving the fork-mode execs/second target from §4 against the Phase 1 instrumented example targets, with unconditional timeout enforcement.

14.4 Acceptance Criteria

  • orphan-free shutdown across 10^4 dispatch cycles (no leaked zombie/child processes)
  • timeout enforcement validated against a deliberately hanging fixture — no campaign stall (I4)
  • fork-mode execs/second within the §4 target range (1k-5k/s) on the trivial parser fixture
  • ExitKind classification is exhaustive and never ambiguous across the full fixture suite (I8)

14.5 Conformance Fixtures

  • conformance/phase2/hanging_binary — an input that causes an infinite loop, validates I4
  • conformance/phase2/crashing_binary — a deliberate SIGSEGV target, validates Crash classification
  • conformance/phase2/fork_bomb_guard — a target that attempts to spawn excessive children, validates containment
  • conformance/phase2/handshake_desync — deliberately corrupts the control pipe to validate desync detection
  • conformance/phase2/resource_limit_exhaustion — a target sized to exhaust the configured fd/process-table limit, validating the limit is detected as a resource condition, not misclassified as target-caused

14.6 Pitfalls

  • Zombie process leakage from incomplete reaping under high-throughput dispatch.
  • Fork-server pipe desynchronization: a single dropped or malformed handshake byte silently hangs every subsequent dispatch (§8.3 step 3-4 boundary).
  • Treating a soft-timeout signal as sufficient — a target that masks or ignores SIGTERM requires hard-kill escalation (I4 requires unconditional enforcement, not best-effort).
  • Under-provisioning file-descriptor or process-table limits for the expected dispatch rate, causing spurious ExitKind::Oom-adjacent failures that are actually resource-limit misconfiguration, not target behavior.

14.7 Performance Concerns

  • Fork overhead itself (page-table copy cost) is the dominant per-exec cost at this phase — quantified in §34-M1 and the reason Phase 9 introduces persistent mode.
  • Signal-dispatch latency for timeout enforcement must not itself become a bottleneck at high dispatch rates.

14.8 Edge Cases

  • child exits before completing the fork-server handshake (must not hang the parent indefinitely)
  • nested forks inside the target (must not leak coverage-map file descriptors into unexpected children)
  • a target that closes its own stdout/stderr, breaking capture assumptions
  • a target that changes its own process group or session, complicating signal delivery for timeout enforcement

14.9 Failure Analysis

Execution-supervisor failure halts campaign throughput entirely — this is the single point through which every input must pass, so a hang here is total, not partial. The watchdog (I4) and desync detection (§8.3) exist specifically to bound the blast radius of any one misbehaving input to that one execution.

14.10 Operational Notes

Mandatory live metrics from this phase: execs/second, timeout rate, and process-restart count — these three numbers are the first thing an operator checks when a campaign looks stalled (§26).

15. Phase 3 — The Coverage-Feedback "Is-Interesting" Loop and the Corpus

15.1 Objectives

Close the loop: connect Phase 1's bitmap and Phase 2's executor to the is-interesting decision (§8.3, I1) and a persistent corpus/queue store (§8.6-8.7), so that a campaign can, for the first time, evolve.

15.2 Detailed Implementation Steps

  • implement the is-interesting decision exactly per the §8.3 seven-step sequence (new edge / new hit-count bucket)
  • implement the virgin-map merge-on-keep step
  • implement QueueEntry creation and lineage tracking (parent_id) per §11
  • implement the on-disk corpus store layout (queue/ directory + sidecar metadata, ADR-21)
  • implement the favored-set computation (minimal spanning set over currently-known edges, §8.7)
  • implement initial (uniform, pre-AFLFast) energy assignment as a Phase-6 placeholder satisfying I9's non-zero floor
  • implement queue persistence and resume-from-disk (extends the Phase 0 campaign-resume stub, now with real content, I11)
  • wire seed loading: an initial corpus directory of user-supplied or auto-generated seeds

15.3 Deliverable

An end-to-end loop: seed input → execute → extract coverage → is-interesting decision → corpus admission — demonstrably growing a queue and increasing cumulative edge coverage over a fixed run against the Phase 1 fixtures.

15.4 Acceptance Criteria

  • an input is added to the corpus iff it exercises a previously-unseen edge or hit-count bucket, validated against a fixture with known expected admissions (I1)
  • cumulative edge coverage strictly non-decreasing over a campaign run
  • favored-set recomputation produces a spanning set covering 100% of currently-known edges
  • campaign resumes from disk with an identical queue state after a forced restart (I11)

15.5 Conformance Fixtures

  • conformance/phase3/known_admission_sequence — a fixed sequence of inputs with a hand-computed expected admit/reject outcome per input
  • conformance/phase3/bucket_boundary — inputs designed to cross exactly one hit-count bucket boundary (§8.3 step 5)
  • conformance/phase3/resume_after_kill — validates queue-state identity across an unclean restart
  • conformance/phase3/redundant_coverage_pair — two independently-admitted inputs whose individual coverage overlaps entirely, validating both are retained at admission time (redundancy resolution deferred to favored-set computation, not blocked here)

15.6 Pitfalls

  • Off-by-one in the hit-count bucket boundaries (§8.3 step 5), causing systematic over- or under-admission relative to the AFL-validated bucket scheme.
  • Forgetting to merge the virgin map on keep, causing the same "new" edge to be re-admitted repeatedly (violates I1's "previously-unseen" semantics).
  • Losing lineage (parent_id) on admission, which silently breaks later minimization/triage traceability.
  • Recomputing the favored set on every single admission rather than periodically, silently reintroducing the same O(queue size)-per-admission cost the periodic-recomputation design was meant to avoid.

15.7 Performance Concerns

  • The virgin-map diff must be a linear scan over the bitmap, not a per-bit branch-heavy comparison — at Phase 2's execs/second rates this is squarely on the hot path.
  • Queue-metadata write-to-disk cadence must be batched, not per-admission fsync, or corpus growth throttles execs/second.

15.8 Edge Cases

  • an input that is admitted, then immediately found to be functionally identical (byte-for-byte) to an existing queue entry (dedup by content hash, distinct from coverage dedup)
  • a campaign restarted with a corpus directory that was manually edited between runs
  • the very first input of a campaign (empty virgin map — every edge is "new")
  • two inputs admitted in rapid succession that each individually cover new edges but whose union covers no additional edge beyond either alone (both must still be retained independently, since favored-set computation, not admission, is where redundancy is later resolved)

15.9 Failure Analysis

A broken is-interesting decision does not crash anything — it silently produces a corpus that looks plausible but fails to grow coverage, which is why the fixed-sequence conformance fixture (§15.5) with hand-computed expected outcomes is mandatory rather than a "looks reasonable" spot check.

15.10 Operational Notes

Track and expose corpus size, cumulative edges covered, and time-since-last-new-coverage from this phase onward — the last of these becomes the primary plateau-detection signal used throughout §26 and §31.

16. Phase 4 — The Mutation Engine (Deterministic + Havoc)

16.1 Objectives

Implement the deterministic mutation passes (bitflip, arithmetic, interesting-values) and the stochastic havoc stage (§8.4, P10, ADR-07), feeding mutated inputs back into the Phase 2/3 execution-and-feedback loop.

16.2 Detailed Implementation Steps

  • implement bit-flip mutation at 1/2/4-consecutive-bit granularity at every offset (§8.4)
  • implement arithmetic mutation (add/subtract small integers) at byte/word/dword width at every offset
  • implement interesting-value substitution (0, -1, INT_MAX/MIN, and format-relevant boundary constants)
  • implement the havoc stage: a randomized stacked sequence of the deterministic primitives plus block insert/delete/duplicate (§8.4, ADR-08)
  • implement deterministic-vs-havoc gating: run the full deterministic pass only on new/small seeds, havoc-dominant thereafter (ADR-08)
  • implement mutation provenance tracking (which MutationKind produced a given QueueEntry, for later analysis)
  • implement seeded, reproducible PRNG threading through every stochastic mutation call (P6 prerequisite — mutations must be replayable)
  • implement mutation-energy accounting: consume energy budget per mutation trial against the Phase-3 placeholder scheduler

16.3 Deliverable

A mutation engine producing reproducible (seed-deterministic) deterministic-pass and havoc-stage mutations, driving measurable new-edge discovery on the Phase 1-3 fixtures beyond what the seed corpus alone covers.

16.4 Acceptance Criteria

  • deterministic replay of a mutation sequence given the same seed reproduces byte-identical mutated inputs (P6)
  • deterministic-pass exhaustively covers every offset for the fixture's input size within the ADR-08 gating rule
  • havoc-stage mutation cost stays under the §4 target (<10 microseconds per mutation, excluding I/O)
  • no buffer corruption or out-of-bounds mutation writes across 10^6 mutation calls

16.5 Conformance Fixtures

  • conformance/phase4/bitflip_exhaustive — small fixed-size input, validates every offset/width combination is exercised
  • conformance/phase4/havoc_seeded_replay — validates byte-identical mutation output across two runs with the same seed
  • conformance/phase4/overflow_guard — deliberately oversized/adversarial input, validates no mutator buffer overrun
  • conformance/phase4/boundary_wraparound — an input positioned at an exact byte/word wraparound boundary, validating deterministic wraparound behavior under arithmetic mutation

16.6 Pitfalls

  • Corpus bloat from havoc's block-insert primitive producing ever-larger inputs with no size discipline, directly taxing execs/second (P2).
  • Non-deterministic mutation output due to un-seeded or improperly-threaded PRNG state, silently breaking replay (P6) long before any crash-replay code exists to expose it.
  • Mutation starvation: an unbounded deterministic pass on a large seed consuming the entire energy budget before havoc ever runs.
  • Applying havoc's block-insert/delete primitives without bounds-checking against the target's declared maximum input size, producing inputs the harness silently truncates rather than genuinely tests.

16.7 Performance Concerns

  • Allocator churn from per-mutation buffer copies — the mutation engine sits directly on the hot path established in Phase 2's execs/second baseline.
  • Branch unpredictability in the havoc stage's randomized primitive selection; measured against the Phase 2 execs/second baseline to ensure mutation cost doesn't erode the fork-server throughput gain.

16.8 Edge Cases

  • zero-length seed input (deterministic pass has no offsets to iterate)
  • maximum-configured-length input (mutation must not silently truncate or panic)
  • an input at exactly the boundary where arithmetic mutation would wrap a byte/word (must wrap deterministically, not UB)
  • a seed whose mutation provenance chain has grown extremely deep (many generations of splice/havoc lineage), which must not degrade lookup cost for later triage

16.9 Failure Analysis

Mutation corruption — producing invalid or non-reproducible inputs — silently undermines the entire coverage-exploration premise (P1): the corpus keeps growing but the underlying search stops being directed. This is detected downstream as an unexplained drop in new-edge discovery rate, making the seeded-replay conformance fixture (§16.5) the primary early-warning check, run on every CI build rather than only when a plateau is already suspected.

16.10 Operational Notes

Track a mutation-effectiveness histogram (new-edges-found per MutationKind) from this phase forward — it becomes the primary input to Phase 6's power-schedule tuning and to the §31 plateau-lever analysis.

17. Phase 5 — Splicing and Dictionary/Token Mutations

17.1 Objectives

Implement splicing (crossover between two corpus entries) and dictionary/token-based mutation (§8.4, ADR-09), giving the engine its first mechanism capable of defeating magic-byte and keyword guards that pure bitflip/havoc cannot climb (P11).

17.2 Detailed Implementation Steps

  • implement splice mutation: select two queue entries, combine a byte range from each at a random split point (§8.4)
  • implement dictionary loading from a user-supplied token file (ADR-09)
  • implement automatic token extraction from comparison instructions observed at runtime, where available from the harness build (ADR-09 "auto-extracted" clause)
  • implement dictionary/token substitution mutation: insert a token at a mutation site, respecting I10's UTF-8-validity guard where the target requires text
  • implement token-application fallback: on invalid-encoding detection, drop the mutation and retry with raw bytes (I10)
  • wire splice and dictionary mutation into the havoc stage's stacked-primitive pool (§8.4 composition)
  • add a magic-byte-guard conformance fixture demonstrating pure-havoc failure and dictionary-assisted success (P11 empirical validation)

17.3 Deliverable

Splicing and dictionary/token mutation integrated into the Phase 4 mutation engine, demonstrated to discover coverage past a magic-byte guard fixture that the Phase 4 deterministic+havoc-only configuration fails to reach within a fixed exec budget.

17.4 Acceptance Criteria

  • splice mutation produces valid-length, byte-accounted-for crossover inputs with no out-of-bounds reads across source entries
  • dictionary mutation never introduces invalid UTF-8 into a target declared as requiring text input (I10)
  • the magic-byte-guard fixture (§17.5) is solved (new coverage past the guard) within a bounded exec budget when dictionary mutation is enabled, and not solved within the same budget when disabled — demonstrating P11 empirically
  • automatic token extraction produces at least one usable token on a fixture with a known comparison-embedded constant

17.5 Conformance Fixtures

  • conformance/phase5/magic_byte_guard — a target requiring an exact 4-byte magic value before reaching deeper code; the canonical P11 fixture
  • conformance/phase5/splice_crossover — two seed entries with known, disjoint coverage; validates the splice produces a plausible hybrid
  • conformance/phase5/dictionary_invalid_encoding — a token file containing a token that would produce invalid UTF-8 in a text-only target; validates the I10 fallback path
  • conformance/phase5/dual_magic_byte_guard — a target requiring two independent magic-byte guards to both hold; validates dictionary substitution composes across multiple mutation sites

17.6 Pitfalls

  • Splicing across two entries with incompatible structural assumptions (e.g., different record boundaries), producing inputs the target rejects trivially and that waste exec budget without discovery value.
  • Dictionary tokens becoming stale relative to the current target build (a magic value the target no longer checks), silently wasting mutation budget.
  • Over-reliance on dictionary mutation crowding out havoc's broader exploration — must remain one weighted option in the havoc stack, not a replacement (ADR-07's layering principle).
  • Auto-extracted tokens harvested from one code path being applied indiscriminately at mutation sites across the entire input, wasting substitution attempts where the token has no local relevance.

17.7 Performance Concerns

  • Splice's two-entry selection cost (choosing which pair to combine) must not become O(corpus size) per mutation call at large corpus sizes — informs Phase 6's scheduler-integrated selection.
  • Token-table lookup cost on the mutation hot path must stay in the same order of magnitude as the other §16 mutation primitives.

17.8 Edge Cases

  • splicing two entries of very different lengths (must not panic on split-point selection)
  • a dictionary containing zero-length or duplicate tokens
  • a magic-byte guard positioned at a non-zero, non-obvious offset (must still be reachable via dictionary substitution, not just prefix-anchored)
  • a target requiring two independent magic-byte guards to both hold simultaneously, testing whether dictionary substitution composes correctly across multiple mutation sites in one mutated input

17.9 Failure Analysis

If dictionary/splice mutation is broken but deterministic/havoc mutation still runs, the failure is invisible in aggregate execs/second and only shows up as a specific class of guarded coverage never being reached — exactly the magic-byte-guard fixture's purpose, and why it is a mandatory, not optional, Phase 5 gate.

17.10 Operational Notes

Extend the Phase 4 mutation-effectiveness histogram with per-MutationKind breakdown for Splice and Dictionary specifically — a near-zero discovery rate from Dictionary on a target known to have magic-byte guards is a direct signal of a broken token pipeline, not just an unlucky campaign.

18. Phase 6 — The Power/Energy Schedule (AFLFast) and Seed Scheduling

18.1 Objectives

Replace the Phase 3 uniform-energy placeholder with the AFLFast Markov-chain-informed power schedule (§8.5, Böhme et al. 2016, P5), and implement favored-set-aware seed scheduling with queue aging (§8.7, ADR-11, ADR-12).

18.2 Detailed Implementation Steps

  • implement per-path hit-count tracking keyed by coverage signature, feeding the energy(s) ∝ 1 / hit_count(path(s))^alpha equation (§8.5)
  • implement the energy-floor clamp guaranteeing I9 (no non-empty queue entry gets zero energy)
  • implement periodic favored-set recomputation (minimal spanning set over currently-known edges, §8.7)
  • implement queue aging: seeds untouched for a configurable duration receive an energy boost
  • implement scheduler selection (Scheduler::select_next) drawing from favored seeds with AFLFast-weighted probability
  • wire the Phase 4-5 mutation engine's energy consumption against the new per-seed energy budget instead of the flat placeholder
  • add power-schedule telemetry: energy distribution histogram across the live queue

18.3 Deliverable

A scheduler that measurably shifts mutation trials toward low-frequency-path seeds relative to the Phase 3 uniform baseline, validated on a fixture with a deliberately rare branch.

18.4 Acceptance Criteria

  • a seed on a deliberately rare path receives strictly more mutation trials than a seed on a common path, holding queue size constant (P5 empirical validation)
  • no live queue entry is ever assigned zero energy across a full campaign run (I9)
  • favored-set recomputation produces a spanning set covering 100% of currently-known edges, matching the Phase 3 invariant under the new scheduler
  • queue-aging boost measurably increases selection frequency of a seed untouched beyond the configured threshold

18.5 Conformance Fixtures

  • conformance/phase6/rare_path_seed — a target with one branch reachable by only a small fraction of the seed corpus; validates AFLFast-style energy skew
  • conformance/phase6/zero_energy_guard — stress-tests the energy floor under an extreme hit-count skew
  • conformance/phase6/queue_aging — validates a long-untouched-but-favored seed regains scheduling priority
  • conformance/phase6/uniform_hit_count — every live path has an equally high hit count; validates the schedule degrades gracefully toward near-uniform energy rather than an ill-defined computation

18.6 Pitfalls

  • Scheduler bias collapse: an overly aggressive alpha exponent starves common-but-still-useful paths entirely, violating the spirit of I9 even while technically respecting the energy floor.
  • Recomputing the favored set too infrequently, letting the scheduler operate on a stale spanning set as the corpus grows.
  • Coupling energy accounting too tightly to wall-clock time rather than exec count, making the schedule's behavior throughput-dependent in a way that complicates reproducibility (P6 tension, resolved by keying on exec count).
  • Letting queue aging's boost compound without an upper bound, eventually inverting the schedule so stale seeds dominate over genuinely promising rare-path seeds.

18.7 Performance Concerns

  • Per-path hit-count bookkeeping must not become a linear scan over the full queue on every scheduling decision — requires an indexed structure keyed by coverage signature.
  • Favored-set recomputation cost grows with queue size; must be amortized (periodic, not per-exec) per the Phase 3 precedent.

18.8 Edge Cases

  • a queue with only one entry (schedule must not divide by zero or otherwise degenerate)
  • a path whose hit count is so high the energy equation underflows toward the floor immediately
  • two seeds with identical coverage signatures but different sizes (favored-set tie-break must prefer the smaller/faster one, §8.7)
  • a scheduling round where every live path has an equally high hit count (the equation should degrade gracefully to near-uniform energy, not divide by an ill-defined value)

18.9 Failure Analysis

Scheduler collapse (all energy funneled to one seed, or effectively uniform despite AFLFast being enabled) directly reduces discovery velocity without any crash or error — detectable only via the energy-distribution histogram (§18.10), which is why that telemetry is mandatory rather than optional at this phase.

18.10 Operational Notes

Export the energy-distribution histogram and per-path hit-count skew as standing campaign metrics; a flattening of this histogram over time on a target known to have rare paths is an early plateau warning distinct from the raw new-edge-rate signal introduced in Phase 3.

19. Phase 7 — Crash Detection and Deduplication

19.1 Objectives

Implement crash classification from signal/exit-status and sanitizer-report parsing (§8.7, ADR-13), and deduplication via stack-hash and coverage-hash strategies (§8.8, ADR-14, I7).

19.2 Detailed Implementation Steps

  • implement signal-based crash classification (SIGSEGV/SIGABRT/SIGBUS/SIGFPE) into ExitKind::Crash (I8, I12)
  • implement ASan/UBSan/MSan report parsing from captured stderr (Serebryany et al. 2012, ADR-13)
  • implement stack unwinding at the fault point and stack-hash computation using relative offsets, not absolute addresses (§8.8 ASLR note)
  • implement coverage-hash computation as the dedup fallback for stripped/symbol-unavailable targets (ADR-14)
  • implement the crash-dedup decision table exactly per §8.8: signal/sanitizer classification, then stack-hash-primary/coverage-hash-fallback merge logic
  • implement Crash artifact persistence: input bytes, build_id, runtime_seed, dedup_key (§11, I3)
  • implement flaky-crash detection: replay a crash N times before treating a mismatch as ground truth (§8.13)
  • implement crash-group bookkeeping (CrashGroupId) so repeated dedup lookups are O(1) amortized

19.3 Deliverable

A crash pipeline that classifies every non-Ok execution, deduplicates against prior crashes using the stack-hash/coverage-hash decision table, and persists a replayable artifact for each distinct crash group.

19.4 Acceptance Criteria

  • every sanitizer-flagged abort is classified as ExitKind::Crash, never as a benign non-zero exit (I12)
  • stack-hash dedup correctly merges two ASLR-shifted-but-identical crashes (relative-offset hashing validated)
  • crash-dedup accuracy meets the §4 target (≥95% precision, ≤3x recall inflation) on the benchmark suite
  • a saved crash artifact reproduces its recorded dedup key on replay ≥99% of the time on deterministic fixtures (I3)

19.5 Conformance Fixtures

  • conformance/phase7/asan_heap_overflow — a known ASan-detected heap-buffer-overflow target
  • conformance/phase7/ubsan_shift — a known UBSan-detected undefined-shift target
  • conformance/phase7/aslr_shifted_duplicate — the same crash captured under two different ASLR layouts; validates stack-hash relative-offset correctness
  • conformance/phase7/stripped_binary_fallback — a symbol-stripped target; validates the coverage-hash fallback path
  • conformance/phase7/multi_thread_race_report — a race-condition-detector sanitizer report spanning multiple threads; validates dedup handles a report shape beyond a single-frame stack-hash

19.6 Pitfalls

  • Hashing absolute stack addresses instead of relative offsets, causing every ASLR-shifted rerun of the same bug to false-split into a new crash group (violates the spirit of I7 by inflating apparent bug count).
  • Treating a sanitizer's non-abort warning output as a crash signal (over-classification) or missing a sanitizer abort buried in truncated stderr (under-classification, I12 violation).
  • Coverage-hash dedup silently merging two distinct root causes that happen to share a coverage signature — the documented, accepted risk of ADR-14's fallback, requiring the manual-review flag rather than silent merge.
  • Symbolizing every crash eagerly on the hot path rather than lazily on first triage access, needlessly taxing the crash-heavy phase of a campaign (e.g., early exploration against a fragile target).

19.7 Performance Concerns

  • Stack unwinding cost per crash is acceptable to be relatively expensive (crashes are rare relative to total execs) but must not block the execution loop for non-crashing inputs.
  • Dedup-key lookup must be O(1) amortized (hash-indexed crash groups) even as the crash corpus grows into the thousands.

19.8 Edge Cases

  • a crash with a corrupted or truncated core/stderr capture (must not fail classification entirely — fall back to coverage-hash)
  • a crash that reproduces under replay but with a different, adjacent stack-hash due to compiler inlining variance across builds (build_id mismatch should be flagged, not silently accepted)
  • two genuinely distinct bugs that happen to crash at the identical top stack frame (stack-hash near-collision, requires the frame-count depth used in hashing to be tuned)
  • a crash whose sanitizer report spans multiple threads (a race-condition-detector report), where a single-frame stack-hash is insufficient to characterize the bug

19.9 Failure Analysis

Misclassified or over-merged crashes waste triage resources on the human end and, worse, can silently hide a distinct real bug behind an already-triaged one (I7). The mandatory manual-review flag on coverage-hash-fallback merges (§8.8) exists specifically to bound this risk rather than eliminate it outright, since perfect dedup without symbols is not achievable.

19.10 Operational Notes

Persist full replay context (build_id, runtime_seed, dedup_key, sanitizer report if any) with every crash artifact from this phase forward — this is the single most-referenced record in the §26 crash-repro-failure runbook.

20. Phase 8 — Corpus and Test-Case Minimization

20.1 Objectives

Implement corpus minimization (cmin) and test-case minimization (tmin) exactly per the §8.9 named-steps procedure, enforcing I6 (minimization never drops coverage) and preserving crash dedup keys under tmin.

20.2 Detailed Implementation Steps

  • implement per-queue-entry coverage bitmap capture as a minimization prerequisite (reuses Phase 1 bitmap machinery)
  • implement the greedy set-cover pass for cmin: repeatedly select the entry covering the most currently-uncovered edges (§8.9 step 2)
  • implement the coverage-union termination check and the pre/post coverage-delta assertion that enforces I6
  • implement tmin's iterative delta-reduction: large-chunk removal first, decreasing granularity down to single bytes, replay-validated against the recorded DedupKey at each step (§8.9)
  • implement tmin's byte-value normalization pass (toward 0x00) on remaining bytes without losing the crash signature
  • implement minimization-time telemetry against the §4 target (<5 minutes for 100k entries)
  • wire cmin as a periodic, not per-admission, campaign maintenance pass (performance-driven design choice)

20.3 Deliverable

A minimizer producing a reduced corpus with provably identical coverage union to the pre-minimization corpus, and a test-case minimizer that shrinks a crashing input while preserving its dedup key, both validated against fixtures with known expected outcomes.

20.4 Acceptance Criteria

  • cmin output's coverage union is byte-for-byte identical to the pre-minimization corpus's coverage union (I6, hard gate — abort minimization on any delta)
  • cmin completes within the §4 target (<5 minutes for 100k entries)
  • tmin-reduced crashing inputs reproduce the identical DedupKey as the original crash on replay
  • tmin reduces a synthetic large-crash fixture to within a known minimal expected size bound

20.5 Conformance Fixtures

  • conformance/phase8/cmin_redundant_corpus — a corpus with deliberate, known-redundant entries; validates exact expected reduction
  • conformance/phase8/tmin_known_minimal — a crash with a hand-verified minimal reproducer; validates tmin converges to it
  • conformance/phase8/cmin_coverage_delta_guard — a deliberately broken minimizer configuration; validates the I6 abort path triggers
  • conformance/phase8/tmin_dual_dependency — a crash requiring two non-adjacent byte ranges to both be present; validates tmin does not greedily delete one before discovering the dependency

20.6 Pitfalls

  • Over-minimization: a greedy set-cover implementation bug that drops an entry whose unique contribution wasn't correctly detected, silently violating I6 without tripping the delta assertion if the assertion itself is miscomputed.
  • tmin converging to a "minimal" input that reproduces a different crash than the original (dedup-key drift during reduction) — must re-validate the dedup key at every reduction step, not only at the end.
  • Running cmin synchronously on the hot campaign path instead of as an offline/periodic maintenance pass, stalling execs/second.
  • Running tmin's byte-normalization pass before the chunk-removal passes converge, wasting normalization effort on bytes that a later chunk-removal step would have deleted anyway.

20.7 Performance Concerns

  • Per-entry bitmap storage for the full corpus during cmin's set-cover computation is memory-intensive at scale (100k+ entries × 64 KiB bitmaps); requires compressed or streaming representation rather than naive in-memory retention.
  • tmin's replay-per-reduction-step cost means test-case minimization is inherently execs-per-second-bound in the same way the main campaign loop is.

20.8 Edge Cases

  • a corpus where every entry is uniquely necessary (cmin should reduce nothing, not force a spurious reduction)
  • a crash that stops reproducing partway through tmin's reduction (must halt and retain the last-known-reproducing state, not the fully-reduced-but-broken one)
  • a single-byte crashing input (tmin has no further granularity to reduce to)
  • a crash that requires two non-adjacent byte ranges to both be present (tmin's chunk-removal must not greedily delete one range before discovering the dependency on the other)

20.9 Failure Analysis

A minimization bug is uniquely dangerous because its failure mode (silently reduced coverage or a dedup-key-drifted "minimal" crash) looks identical to success until specifically checked — this is why the coverage-delta guard (I6) and per-step dedup-key re-validation (tmin) are hard gates with an abort path, not soft warnings.

20.10 Operational Notes

Log the pre/post corpus size and coverage-union size for every cmin run, and the pre/post input size plus dedup-key-stability confirmation for every tmin run — both feed the §26 operational dashboards as "minimization payoff" metrics.

21. Phase 9 — Persistent/In-Process Mode and Sanitizer Integration

21.1 Objectives

Implement the persistent/in-process execution mode (§8.3 contrast, ADR-05) to close the order-of-magnitude execs/second gap identified in §4/§34, and formalize sanitizer build-flag integration (ADR-17) as a first-class campaign configuration.

21.2 Detailed Implementation Steps

  • implement the AFL-persistent-loop entrypoint (repeated re-entry into the same process across N inputs before a fresh fork) per ADR-18
  • implement the libFuzzer-style in-process call path (direct function call within the fuzzer's own address space) per ADR-18
  • implement per-iteration state-reset hooks: allocator reset support, fd-cleanup hooks, global-state leak detection (I5)
  • implement a state-leak canary check that falls back to fresh-fork mode when persistent-mode contamination is detected (I5 recovery path)
  • implement sanitizer-flag wiring (ASan/UBSan/MSan) into the harness build configuration (ADR-17)
  • implement sanitizer-overhead measurement so operators can weigh execs/second cost against detection-coverage gain
  • implement execution recycling limits (max iterations per persistent-mode process lifetime before a mandatory fresh fork, bounding worst-case leak accumulation)

21.3 Deliverable

A persistent/in-process execution mode achieving the §4 target execs/second range (20k-100k/s on trivial parsers) with I5-enforced state cleanliness, and sanitizer integration available as a standard campaign configuration option.

21.4 Acceptance Criteria

  • persistent-mode execs/second on the trivial-parser fixture falls within the §4 target range and is at least a 10x improvement over the Phase 2 fork-mode baseline (§34-M1)
  • no state bleed detected across 10^5 persistent-mode iterations on a deterministic fixture (I5)
  • a deliberately state-leaking fixture triggers the fallback-to-fresh-fork recovery path within a bounded iteration window
  • sanitizer-enabled campaigns correctly classify every injected-bug fixture crash as ExitKind::Crash (I12, building on Phase 7)

21.5 Conformance Fixtures

  • conformance/phase9/persistent_stateful_leak — a target with deliberate global-state accumulation across calls, validates I5 leak detection and fallback
  • conformance/phase9/persistent_throughput_baseline — trivial parser, validates the execs/second target
  • conformance/phase9/sanitizer_enabled_known_bug — a target with an injected ASan-detectable bug, run once with and once without sanitizer flags, validating the detection-rate difference
  • conformance/phase9/time_dependent_target — a target whose behavior depends on wall-clock time; validates persistent mode's rapid iteration rate does not perturb it relative to fork-mode cadence

21.6 Pitfalls

  • Residual state leakage across persistent-mode iterations (heap fragmentation, static/global variable accumulation) silently corrupting coverage attribution for iteration N+1 based on iteration N's side effects — the canonical libFuzzer pitfall (§5 Reference Implementations).
  • File-descriptor accumulation across iterations exhausting the process's fd budget mid-campaign.
  • Assuming sanitizer overhead is negligible and defaulting it on for every campaign regardless of the execs/second budget, silently regressing throughput without operator awareness.
  • Setting the execution-recycling iteration cap too high in pursuit of maximum throughput, so leak accumulation before the mandatory fresh fork grows large enough to meaningfully skew coverage attribution for the last iterations before recycling.

21.7 Performance Concerns

  • Cache pollution across rapid persistent-mode iterations can offset some of the raw fork-avoidance gain; must be measured, not assumed, against the §34 back-of-envelope projection.
  • Allocator fragmentation accumulating over a long persistent-mode process lifetime, motivating the execution-recycling iteration cap.
  • Sanitizer runtime overhead (commonly 2x-10x depending on sanitizer) must be explicitly modeled in the operator-facing execs/second expectation, not hidden.

21.8 Edge Cases

  • a target that internally calls exit() mid-persistent-loop, terminating the whole process unexpectedly and requiring immediate fresh-fork recovery
  • a target whose global state is supposed to persist across calls by design (must be explicitly opted out of leak-detection false-positives)
  • sanitizer and persistent mode interacting badly (a sanitizer's own internal state assumptions conflicting with iteration reuse) — validated in sanitizer_enabled_known_bug under persistent mode specifically
  • a target whose behavior depends on wall-clock time (e.g., a cache with a time-based eviction policy), which persistent mode's rapid iteration rate can inadvertently perturb relative to fork mode's slower cadence

21.9 Failure Analysis

Persistent-mode corruption is the single highest-leverage failure mode in the entire system because it invalidates campaign data silently and at the highest execs/second rate — a leak that costs one wasted execution in fork mode costs thousands per second in persistent mode before it's noticed. This is why the state-leak canary (I5) has an automatic, not manual, recovery path.

21.10 Operational Notes

Track persistent-iteration stability (fraction of iterations completing without triggering the leak canary) as a standing metric; a downward trend is the leading indicator for the §26 bitmap-saturation and nondeterminism-hunt runbooks.

22. Phase 10 — Structure-Aware/Grammar Fuzzing and Parallel Corpus Sync

22.1 Objectives

Add the structure-aware/grammar mutation hook (§8.4, ADR-10, Pham et al. 2019) for deeply-structured formats, and implement shared-directory parallel corpus synchronization (ADR-16) enabling multi-worker campaigns on a single node.

22.2 Detailed Implementation Steps

  • implement the structure-aware mutation plugin interface (input-model-driven mutation at the grammar-node level, per ADR-10's opt-in-hook design)
  • provide one reference grammar plugin for a structured example format, demonstrating the hook without building a general CFG engine (ADR-10 boundary)
  • implement corpus-directory watching: detect new queue entries written by sibling workers sharing the campaign directory
  • implement cross-worker coverage-hash reconciliation so a seed discovered by worker A is recognized as non-novel by worker B without re-triggering false "new coverage" admission
  • implement sync-cadence configuration (poll interval vs. event-driven filesystem watch) balancing sync latency against filesystem load
  • implement distributed-dedup for crashes: a crash found by one worker must not be independently re-triaged as new by every other worker
  • extend the Phase 6 scheduler to treat synced-in entries with appropriately initialized (not zero) energy

22.3 Deliverable

A structure-aware mutation hook demonstrated on a reference grammar fixture reaching coverage unreachable by byte-level mutation alone, plus N parallel local workers sharing one campaign directory with correctly deduplicated corpus and crash state across all workers.

22.4 Acceptance Criteria

  • the reference grammar plugin reaches a target coverage milestone within a bounded exec budget that byte-level-only mutation fails to reach in the same budget (mirrors the Phase 5 magic-byte empirical-validation pattern, now for structure)
  • corpus-sync latency across workers on a single node stays within the §4 target (<2 seconds)
  • no worker independently re-admits a coverage-hash-identical seed already present from a sibling worker as a spuriously "new" queue entry
  • a crash found by one worker is visible and correctly deduplicated by every other worker within the sync cadence window

22.5 Conformance Fixtures

  • conformance/phase10/grammar_reference_target — a structured-format fixture unreachable via byte mutation within a fixed budget, reachable via the grammar plugin
  • conformance/phase10/sync_dedup_race — two workers discovering the same coverage near-simultaneously; validates no duplicate admission
  • conformance/phase10/sync_crash_visibility — validates cross-worker crash-dedup propagation within the latency target
  • conformance/phase10/grammar_version_skew — a subset of workers running an older grammar-plugin version; validates malformed cross-version entries are rejected at sync time (T7)

22.6 Pitfalls

  • A grammar plugin that produces structurally invalid inputs the target rejects trivially, wasting exec budget without discovery value — the plugin interface must be validated against a "produces parseable output" fixture before being trusted.
  • Sync-induced duplicate admission: a race between two workers both locally deciding "new coverage" on the same edge before either has seen the other's sync update, transiently violating I1's "previously-unseen" framing until reconciliation catches up (acceptable only if bounded and self-correcting within the sync cadence).
  • Corpus-sync storms: a burst of simultaneous admissions across many workers overwhelming filesystem-watch-based sync, motivating the configurable poll-interval fallback.
  • Assuming every worker on a node has identical performance characteristics, so scheduler and sync-cadence tuning derived from one worker's behavior is silently miscalibrated for a heterogeneous-core node.

22.7 Performance Concerns

  • Grammar-level mutation cost is typically higher per-mutation than byte-level havoc; must be weighted appropriately in the mutation-kind mix rather than displacing cheaper primitives entirely.
  • Filesystem-watch overhead scales with worker count; the poll-interval fallback exists specifically for node configurations beyond the point where event-driven watching pays off.

22.8 Edge Cases

  • a grammar plugin that is correct but extremely slow, silently tanking that worker's execs/second relative to its siblings
  • a sync event arriving for a crash artifact whose input file is only partially written (torn-write race) — must validate completeness before triage
  • more workers than cores, causing scheduling contention that masks itself as a sync-latency problem
  • a grammar plugin loaded by only a subset of workers (version skew across a rolling deployment), producing structurally inconsistent corpus entries across the shared directory

22.9 Failure Analysis

A broken sync path doesn't crash any individual worker — each worker's local loop remains healthy — but the campaign as a whole silently loses the multiplicative benefit of parallelism, degrading to N independent, redundant single-worker campaigns. This is specifically why cross-worker dedup visibility (§22.4) is a named acceptance gate, not an assumed side effect of "workers share a directory."

22.10 Operational Notes

Track per-worker execs/second alongside aggregate cluster execs/second and a sync-lag metric (time between a sibling's admission and local visibility) — divergence between per-worker and aggregate numbers is the primary signal for the §26 distributed-sync-issues runbook.

23. Phase 11 — Klees-et-al-Style Evaluation Harness, Chaos, and Perf Hardening

23.1 Objectives

Build the fuzz-eval evaluation harness implementing the Klees et al. 2018 methodology (bugs-over-trials with statistical significance) as the project's primary correctness/effectiveness gate, and harden the full system against chaos scenarios (crashing/hanging/OOMing targets, nondeterminism) and performance regression.

23.2 Detailed Implementation Steps

  • implement a benchmark-target suite with known/injected bugs (LAVA-M-style bug injection or equivalent hand-curated known-bug targets)
  • implement N-trial campaign execution against each benchmark target with independent seeds per trial
  • implement unique-bug-found aggregation across trials using the Phase 7 dedup machinery as ground truth
  • implement statistical significance reporting (e.g., a Mann-Whitney-style comparison between configurations) per Klees et al.'s stated methodology, explicitly rejecting single-run coverage-percentage comparisons as sufficient evidence
  • implement differential comparison hooks against AFL++/libFuzzer on shared targets (same benchmark suite, same trial count) as an optional cross-validation mode
  • implement chaos fixtures: crashing, hanging, and OOMing targets exercised specifically to validate I4/I8/graceful-degradation under adversity end to end
  • implement perf-regression gating on execs/second, wired into CI (eval.yml) as a required check
  • implement soak-test tooling for multi-day unattended campaign runs, validating I11 resume correctness over long horizons

23.3 Deliverable

An evaluation harness that, run against the benchmark-target suite over N trials, reports deduplicated unique bugs found with a significance test, gates CI on both bug-finding effectiveness and execs/second non-regression, and a chaos-test suite demonstrating graceful handling of crashing/hanging/OOMing/nondeterministic targets.

23.4 Acceptance Criteria

  • the evaluation harness finds all known-injected bugs in the benchmark suite within a specified trial budget, with reported significance, on at least the same order of trials as comparable published methodology
  • execs/second on the Phase 9 persistent-mode benchmark shows no statistically meaningful regression across a CI run relative to the last tagged baseline
  • every chaos fixture (crashing/hanging/OOMing/nondeterministic target) is handled without campaign-wide stall, per I4/I8
  • a multi-day soak run resumes correctly across at least one forced mid-run restart with no queue or crash-artifact loss (I11)

23.5 Conformance Fixtures

  • conformance/phase11/lava_m_style_suite — the benchmark-target suite with known injected bugs
  • conformance/phase11/nondeterministic_target — a target with intentionally nondeterministic output, validating graceful degradation rather than corpus/crash corruption
  • conformance/phase11/chaos_combined — a single run combining crashing, hanging, and OOMing behavior across different queue entries in one campaign
  • conformance/phase11/soak_multi_day — a long-horizon run with a scheduled forced restart mid-campaign
  • conformance/phase11/harness_isolation_check — validates the evaluation harness's own trial-isolation setup does not itself introduce nondeterminism relative to a normal single-campaign run

23.6 Pitfalls

  • Reporting coverage percentage as the headline result instead of deduplicated unique bugs over trials — the exact methodological error Klees et al. 2018 was written to correct, and explicitly disallowed as a stand-alone metric by this project's own testing strategy (§28).
  • Insufficient trial count producing an evaluation result with no real statistical power, giving false confidence in either direction (a "no improvement" or "clear improvement" claim that doesn't survive a larger trial count).
  • Chaos fixtures that are too narrow (e.g., only testing hangs, never combining hang+crash+OOM in one campaign) missing interaction-effect bugs in the executor's classification logic.
  • Treating a single favorable evaluation run as sufficient evidence and skipping the differential-comparison mode against AFL++/libFuzzer, forfeiting the strongest available external validation of the bug-finding claim.

23.7 Performance Concerns

  • The evaluation harness itself, run at full trial count against the full benchmark suite, is expected to be the single longest-running CI job in the project — must be scheduled appropriately (not on every commit) while the lighter perf-regression execs/second check remains fast enough for per-commit gating.
  • Soak-test resource consumption (multi-day runs) must be isolated from the fast CI path entirely.

23.8 Edge Cases

  • a benchmark target whose injected bug is only reachable via a magic-byte guard, indirectly re-validating Phase 5's dictionary mutation as load-bearing for the overall bug-finding claim
  • a trial that itself crashes the fuzzer's own harness process (must be classified as a fuzzer-side fault, distinct from a target-side crash, and not silently counted as a "bug found")
  • statistically ambiguous results (neither clearly significant nor clearly null) — must be reported as such, not rounded to a conclusion
  • a benchmark target that behaves differently under the evaluation harness's trial-isolation setup than it does in a normal single-campaign run, requiring the harness's isolation itself to be validated against the same nondeterminism-detection procedure (§8.14) used elsewhere

23.9 Failure Analysis

A weak or absent evaluation harness is a silent, project-level failure mode: every other phase can pass its own conformance fixtures while the system as a whole fails to find bugs competitively, and nothing in Phases 0-10 alone would detect that. This is why the evaluation harness — not coverage, not execs/second alone — is the project's terminal acceptance gate (§28, P3).

23.10 Operational Notes

Publish the evaluation harness's bugs-found-per-trial, significance results, and execs/second baseline as the release-gating dashboard (§26, §29); every tagged release must carry its evaluation-harness report as a release artifact, not just changelog prose.

26. Operational Readiness

Named metrics: execs/second, edges/coverage over time, corpus size, crashes found and unique-crashes found, time-since-last-new-coverage (plateau signal), bitmap saturation (density), hang rate, OOM rate, energy-distribution skew, sync lag. Tracing: lightweight span events per execution keyed by campaign/worker/exec-id (ADR-23), covering mutation → dispatch → execution → feedback → (optional) triage. Structured logging: JSON events only (ADR-22), one event per admission, crash, and phase-boundary transition. Dashboards: a campaign-health dashboard surfacing execs/second, coverage-over-time, and crash-rate as the three headline panels. Alerting philosophy: a stalled coverage plateau and a crashing fuzzer (the fuzzer's own process, not the target) are the two signals that matter most — everything else is diagnostic detail feeding into triage of one of those two. SLOs: campaign execs/second within 20% of the Phase 2/9 benchmark baseline; worker restart under 10 seconds (§4 RTO); crash-replay success ≥99% on deterministic targets (I3). Incident response: on a coverage-plateau alert, follow the coverage-plateau-triage runbook; on a crash-replay failure alert, follow crash-repro-failure; on inconsistent bitmap behavior across repeats, follow nondeterminism-hunt; on high collision-rate telemetry, follow bitmap-saturation; on multi-worker divergence, follow distributed-sync-issues. Named runbooks live under docs/runbooks/ (§10): coverage-plateau-triage.md, crash-repro-failure.md, nondeterminism-hunt.md, bitmap-saturation.md, distributed-sync-issues.md. Backup/restore: the corpus and crash directories are the entire durable state; backup is a filesystem-level copy of the campaign directory, restore is a copy-back plus the I11 consistency check on next startup. Deployment topology: single-node by default, N-worker shared-directory topology for parallel campaigns (§22); no external service dependency. Canary/rollback/migration: a new engine build is canaried against a held-out benchmark target before being promoted to drive a long-running production campaign; rollback is reverting to the last-tagged binary against the same campaign directory (corpus format is versioned, §27, so this is safe across minor releases).

27. Compatibility & Versioning

Harness/target ABI stability: the libFuzzer LLVMFuzzerTestOneInput and AFL persistent-loop ABIs (ADR-18) are treated as external, foreign-owned contracts — the engine tracks upstream changes but does not unilaterally break compatibility with either. Coverage-instrumentation interface: the SanitizerCoverage __sanitizer_cov_trace_pc_guard interface (§13) is versioned against the compiler toolchain; a target build's declared SanitizerCoverage ABI version is recorded in campaign metadata and checked against the engine's supported range at startup (mismatch is a hard error, not a silent best-effort attempt). Corpus format: the on-disk queue/sidecar-metadata format (ADR-21) is SemVer-versioned; a minor-version engine upgrade must read all prior minor-version corpora without migration; a major-version bump requires an explicit, documented migration step. Crash-artifact format: versioned identically to the corpus format, since crash artifacts are corpus entries with additional metadata (§11 Crash). Dictionary format: the token-file format (ADR-09) is a stable, documented text format independent of engine version, to remain interchangeable with AFL/AFL++-style dictionaries. API stability: the eleven-crate public API surface (§10) follows SemVer; the Harness, Mutator, Executor, and Scheduler traits (§11) are the primary extension points and receive the strongest stability guarantee, since third-party structure-aware plugins (§22) depend on them. Migration/deprecation: deprecated APIs are marked at least one minor version before removal, with a CHANGELOG.md entry and, where feasible, an automated migration note.

28. Testing & Verification Strategy

Unit tests cover the pure-function boundaries: edge-ID computation (§8.1), the is-interesting decision (§8.3, tied to I1), the power-schedule equation (§8.5, tied to I9), and the crash-dedup decision table (§8.8, tied to I7). Integration tests exercise full loop slices: mutation → execution → feedback → corpus admission (Phases 3-6), and execution → crash detection → dedup → artifact persistence (Phase 7). Property tests encode the invariants directly: an input is corpus-added iff it adds coverage (I1, §15.5); the bitmap resets fully between runs (I2, §13.4); a saved crash always reproduces (I3, §19.4); minimization preserves coverage (I6, §20.4); the fork-server child is deterministic given the same input on a deterministic target (I5, §21.4). The evaluation harness following Klees et al. (§23) — run against a suite of targets with known/injected bugs (LAVA-M-style), over N trials, reporting unique bugs found with statistical significance — is the primary named CI gate; coverage alone is never treated as a stand-alone success metric (P3, ADR-25). Differential testing compares bug-finding results against AFL++ and libFuzzer on shared benchmark targets (§23.2), validating the engine finds at least the bugs those established fuzzers find on the same suite. Self-fuzzing runs the engine's own input parsers (corpus-metadata reader, dictionary-file parser, replay-metadata deserializer) as fuzz targets (§10 fuzz/), tied to T10. Chaos testing exercises crashing, hanging, and OOMing targets in combination (§23.5 chaos_combined), tied to I4/I8. Deterministic replay testing validates §8.13's sequence end to end. Soak testing runs a multi-day campaign with a forced mid-run restart, tied to I11 (§23.4). Fault injection deliberately corrupts the fork-server handshake (§14.5 handshake_desync) and the shared bitmap (T1/T3) to validate detection and recovery paths. Perf-regression gating enforces execs/second non-regression on every tagged release (§23.6/§30), tied to P2.

Every test class above maps to a concrete phase gate: unit and property tests are a per-commit CI requirement from Phase 0 onward; differential and self-fuzzing tests become meaningful starting Phase 1 (once instrumentation exists to self-fuzz against); chaos and fault-injection tests are introduced incrementally as their corresponding subsystem lands (fork-server fault injection in Phase 2, persistent-mode chaos in Phase 9); and the full Klees-et-al evaluation harness, soak testing, and perf-regression gating are Phase 11's terminal acceptance bar, run on the release cadence described in §29 rather than per-commit.

29. Build & Release Engineering

Reproducible builds: a pinned Rust toolchain version and a committed lockfile produce bit-identical binaries across CI and release environments (ADR-26); this is a hard requirement because a crash artifact's build_id (§11 Crash) is only meaningful if the build it names is reproducible. Artifact signing: release binaries are signed (cosign-style signature) so a downloaded engine build's provenance is verifiable. SBOM: a software bill of materials is generated per release, feeding dependency-audit review (T9). Release channels: a stable channel tracking tagged releases and a nightly channel tracking main, with the evaluation harness (§23) gating promotion from nightly to stable, not just unit-test passage. CI/CD topology: ci.yml runs build + unit/property tests on every commit; eval.yml runs the Klees-et-al evaluation harness and the perf-regression gate on a slower cadence (nightly/pre-release, per §23.7); release.yml builds, signs, and publishes on tag push, attaching the evaluation-harness report (§23.10) as a release artifact. Version stamping: every binary embeds its build_id, toolchain version, and git commit hash, all of which are recorded into every campaign's metadata (§27). Provenance/attestation: release artifacts carry a signed build-provenance attestation linking the binary to the exact CI run and commit that produced it. Dependency auditing: cargo audit/cargo deny-equivalent checks run in CI and block release on any known-vulnerable or disallowed-license dependency (ADR-28, T9).

30. Performance Engineering

Methodology: execs/second is treated as the single dependent variable everything else is measured against (P2) — fork mode vs. persistent mode vs. a hypothetical future snapshot mode (§31, §36) are compared on this axis first; the coverage-bitmap update cost on the hot path (§13.7) is profiled independently of executor cost to isolate instrumentation overhead from process-supervision overhead; mutation cost per input (§16.7, §17.7) is profiled against the same execs/second baseline to ensure the mutation engine never becomes the bottleneck ahead of the executor; the number of syscalls per exec is minimized deliberately (batched fd handling, avoided redundant stat/open calls) since syscall overhead dominates at persistent-mode throughput levels; sanitizer overhead (§21.7) is measured and reported per-sanitizer rather than assumed; tail latency of slow inputs (a pathological O(n^2) parse) is tracked at p99/p999 separately from mean execs/second, since a small fraction of slow inputs can dominate wall-clock campaign time even at a healthy mean throughput.

31. Scalability Analysis

What stays constant: the bitmap size (fixed at configuration time, §4/ADR-04), the per-execution timeout enforcement cost (I4), and the ABI surface (§27). What grows: corpus size (linearly with campaign duration until minimization intervenes, §20), crash-artifact count (sub-linearly after dedup, §19), and per-path hit-count bookkeeping (bounded by live-path count, §18). Coverage discovery follows a saturating curve — diminishing returns as the bitmap fills and as the seed corpus already covers the target's shallow branches; new-edge discovery rate decays roughly as remaining-uncovered-edges shrinks, which is precisely the plateau behavior quantified in §4 and tracked as time_since_last_new_coverage (§15.10). Corpus growth is bounded in practice by periodic cmin (Phase 8), keeping steady-state queue size within the §4 target range rather than growing unboundedly with campaign duration. Parallel fuzzing scales sub-linearly with worker count because of corpus-sync overhead (§22) — each additional worker contributes new execs/second roughly linearly up to the point where sync-lag (M9) and shared-bitmap cache contention (§13.7) begin to dominate, after which additional workers yield diminishing unique-coverage contribution per worker. The deeper-bug problem: once shallow coverage saturates, further progress requires either better mutators (dictionary/structure-aware, Phases 5/10) or, past the mutation-only ceiling, techniques this project explicitly does not build (REDQUEEN-style input-to-state correspondence is noted as a natural extension in §8.10; full concolic/symbolic assistance is out of scope per §1/§36). Named bottlenecks: the shared-bitmap cache line under high worker-count contention (§13.7); the executor's per-exec syscall count at persistent-mode throughput (§30); corpus-sync latency at high worker counts (§22.7); crash-dedup lookup cost as the crash corpus grows (§19.7, mitigated by hash-indexed crash groups). Scaling across cores: near-linear up to the point where shared-bitmap contention and corpus-sync overhead begin to dominate (empirically in the tens-of-cores range on a single node, per §4's 32-core NUMA-awareness threshold). Scaling across machines: explicitly deferred (§1 PhaseDeferred, ADR-16) — the shared-directory sync primitive does not extend cleanly across a network filesystem at low latency, and a proper multi-machine design would require the RPC-based coordinator noted as the rejected alternative in ADR-16. Practical target-complexity ceiling: targets whose interesting behavior sits behind checksum/cryptographic guards or requires stateful multi-message protocol sequences exceed what byte/structure-level mutation can reach in reasonable time; the levers beyond that ceiling are dictionaries (cheap, already built), structure-aware/grammar fuzzing (built, Phase 10), REDQUEEN-style input-to-state correspondence (noted extension, §8.10), and ultimately symbolic/concolic assistance (explicitly out of scope, §36).

Memory scaling follows worker count linearly (§34's per-instance × parallel-instances calculation), not corpus size — the corpus itself is disk-resident, not memory-resident, by design (ADR-21's plain-files choice), so a campaign's memory footprint is dominated by the number of concurrently-running target instances and their individual heap ceilings, not by how large the on-disk queue has grown. This decouples the scalability story for compute (execs/second, worker count, sync overhead) from the scalability story for storage (corpus/crash-artifact volume), and each is monitored, tuned, and bottlenecked independently rather than treated as one combined resource-planning problem.

32. Mental Models & First Principles

  • MM1 — Coverage-guided fuzzing is evolutionary search where the fitness function is "did you reach somewhere new." That one bit of feedback is what separates it from dumb random testing and is the entire reason it works (AFL whitepaper; P1).
  • MM2 — Execs/second is the currency. Every architectural decision downstream of §3 is really a decision about running the target more times per second — the fork server, persistent mode, and even the choice of Rust over Python all reduce to this one number (P2, §34).
  • MM3 — A magic-byte or checksum guard is a wall random mutation cannot climb. Dictionaries, input-to-state correspondence (REDQUEEN), and concolic execution are all ways to guess the wall's password rather than brute-force it — they differ only in how they learn the password (P11, §8.10, §36).
  • MM4 — The bitmap is a lossy compression of "where has this program been." Its size and hash function are a deliberate trade of precision (perfect path tracking) for cost (a fixed 64 KiB scan), and every collision is a small, accepted lie the fuzzer tells itself about coverage (§8.2, CollAFL).
  • MM5 — A crash without a replay is not a bug, it's a rumor. The entire crash-triage subsystem exists because "it crashed once" carries zero engineering value until it can be reproduced on demand (P6, I3).
  • MM6 — Energy is a scarce resource being allocated under uncertainty about which seed is most promising. The power schedule is a bet, not a certainty, and AFLFast's contribution was making that bet quantitative instead of uniform (P5, §8.5).
  • MM7 — Minimization and mutation are opposite-direction operations over the same search space. Mutation expands a corpus outward looking for new coverage; minimization contracts it inward looking for the smallest representative set — and both must respect the same coverage-preservation contract to be trustworthy (I6, §8.9).
  • MM8 — A fuzzer is only as trustworthy as its own evaluation methodology. A fuzzer that "seems to find bugs" without an N-trial, dedup-against-ground-truth, statistically-significant evaluation is making an unfalsifiable claim — Klees et al.'s contribution was making fuzzing evaluation a science rather than a demo (P3, §28).
  • MM9 — Isolation and speed are in permanent tension. Fork-per-input isolates every execution completely at high cost; in-process/persistent mode shares an address space across executions at low cost but reintroduces the exact cross-contamination risk process isolation was preventing (§8.3, I5).
  • MM10 — Coverage plateaus are not failures, they are information. A flattening new-edge curve tells the operator precisely where to invest next — a dictionary, a grammar plugin, or accepting the target's current ceiling — rather than signaling anything is broken (P14, §31).
  • MM11 — Nondeterminism is a property of the target, not a bug in the fuzzer, until proven otherwise. A repeat-check (§8.14) exists because the fuzzer's own correctness cannot be judged from a single suspicious observation; the target must be interrogated deliberately before the fuzzer's own logic is blamed.
  • MM12 — Deduplication is a lossy compression of "how many distinct bugs exist," exactly as the bitmap is a lossy compression of "where has this program been." Both trade a small, bounded, monitored error rate for a tractable representation — the discipline is in knowing and measuring the error rate (T6, §8.8), not in pretending it is zero.
  • MM13 — Parallelism is not free coverage. Adding a worker adds raw execs/second linearly at first, but the unique-coverage contribution per additional worker decays as sync overhead grows (§22, §31, §34) — the naive assumption that N workers find N times the bugs of one worker is wrong past a modest worker count on a single node.

AFL++'s fork-server greybox model favors isolation and broad compatibility with arbitrary POSIX targets at a real but bounded per-exec cost, and its contribution to this project is the fork-server protocol (§8.3) and the AFLFast power schedule (§8.5) almost verbatim. libFuzzer's in-process model trades isolation for the largest single execs/second win available short of a symbolic engine, at the cost of requiring a well-behaved, state-resettable harness — this project adopts it as an opt-in persistent mode (Phase 9) rather than a default, precisely because that state-resettability requirement (I5) is not free. LibAFL's composable-components architecture (executor, feedback, corpus, mutator, scheduler as independently swappable traits) is this project's most direct structural ancestor (§11's trait boundaries mirror it deliberately) because it demonstrates that speed and modularity are not actually in tension if the trait boundaries are drawn at the right granularity. SAGE and KLEE represent the opposite end of the precision/throughput spectrum: by solving path constraints exactly via an SMT/theorem-prover backend, they can walk straight through a guard that would take a greybox fuzzer an astronomically long time to find by mutation (§34), but at a per-path cost that makes them uncompetitive on raw execs/second at scale — the reason this project stays greybox and treats symbolic assistance as a documented, rejected-for-now alternative (§36) rather than a core subsystem.

34. Back-of-Envelope Capacity Model

Execs/second, fork mode vs. persistent mode. Fork+exec cost ≈ 0.5-2 ms per the §4 constraint (dominated by page-table setup and dynamic-linker work). At 1 ms average: 1 / 0.001s = 1,000 execs/s, matching the low end of the M1 target. Persistent-mode per-iteration cost ≈ 5-20 µs (a direct function call plus a lightweight state-reset, no fork/execve syscall at all). At 10 µs average: 1 / 0.00001s = 100,000 execs/s, matching the high end of M2 — a ~100x order-of-magnitude gap, which is the single number that justifies building persistent mode at all (Phase 9, MM2).

Bitmap collision probability (birthday-style estimate). With a 64 KiB (65,536-slot) bitmap and k live edges hashed uniformly, the probability of at least one collision approximates the birthday bound: P(collision) ≈ 1 - exp(-k^2 / (2 * 65536)). At k = 1,000 live edges: k^2 / (2*65536) ≈ 1,000,000 / 131,072 ≈ 7.6, giving P ≈ 1 - e^-7.6 ≈ 99.95% — collisions are near-certain even at modest edge counts, which is precisely why CollAFL-style analysis (§8.2, Gan et al. 2018) matters and why the naive intuition "64 KiB is plenty of room for a few thousand edges" is wrong; the practical mitigation is that not every collision causes a missed discovery (only collisions between edges hit in the same execution), so the effective miss rate is lower than the raw collision probability, but the raw number motivates monitoring collision-rate telemetry (M4) rather than assuming safety.

Expected time to guess a 4-byte magic value by pure mutation. A 4-byte (32-bit) exact-match guard has 2^32 ≈ 4.29 billion possible values. Even at an optimistic 100,000 execs/second (persistent mode, M2) with every execution trying an independent random 4-byte value at the guard offset, expected time to hit it is 4.29e9 / 100,000 ≈ 42,900 seconds ≈ 11.9 hours for a single such guard, and this compounds multiplicatively with every additional independent guard in sequence — motivating dictionaries (P11) and REDQUEEN-style input-to-state correspondence (§8.10), either of which can solve the same guard in O(1) execs by directly observing or supplying the compared value instead of guessing it.

Corpus growth and minimization payoff. A campaign admitting roughly 1 new queue entry per 100-1,000 interesting-input checks (empirically typical greybox admission rate) over a 24-hour run at 50,000 execs/second average produces 50,000 * 86,400 / 500 ≈ 8.64 million / 500 ≈ 17,280 raw admissions before minimization; a set-cover cmin pass (§8.9) typically reduces such a corpus by 60-90%, yielding a steady-state queue in the low thousands — consistent with the §4 corpus-size target range.

Coverage-vs-time saturation curve shape. Modeling cumulative discovered edges as E(t) = E_max * (1 - e^(-t/τ)) (a standard saturating-exponential approximation), the new-edge rate dE/dt = (E_max/τ) * e^(-t/τ) decays exponentially — meaning each doubling of campaign duration yields a shrinking, not constant, absolute gain in new edges, which is exactly the plateau behavior operators observe and the reason time_since_last_new_coverage (not raw edge count) is the primary plateau-detection metric (§15.10, §26).

Parallel speedup with sync overhead. With N workers each achieving the single-worker execs/second baseline R, naive aggregate throughput is N*R, but effective unique-coverage discovery is reduced by sync overhead: approximating effective workers as N_eff = N / (1 + N*L/S) where L is per-worker sync latency contribution and S is the sync-cadence interval (§4, M9 target <2s), at small N (single-digit workers on one node) N_eff ≈ N (near-linear), but as N grows the denominator's N*L term grows with it, producing the sub-linear scaling described qualitatively in §31.

Memory per target × parallel instances. At the §4 per-instance ceiling of up to 2 GiB and a 32-worker single-node campaign: 32 * 2 GiB = 64 GiB peak — within the §4 vertical-scaling assumption of a 128-core/large-memory node, but a concrete number an operator must check before scaling worker count blindly upward on a constrained host.

  11. Crash-dedup's coverage-hash fallback (ADR-14) is explicitly flagged as capable of silently merging two distinct root causes (I7, T6) — why is a "manual review flag" considered sufficient mitigation rather than a stronger automated secondary signal? (§8.8, §19, T6)

  16. 36. Alternative Architectures (Roads Not Taken)

Pure black-box/dumb fuzzing (no instrumentation).

+-----------+     random input     +-----------------+
|  Mutator  |---------------------->|  Target (opaque) |
+-----------+                       +--------+---------+
                                              |
                                       exit/crash only
                                              v
                                     +------------------+
                                     | Crash Detector    |
                                     +------------------+

Winning regime: closed-source targets where no compile-time hook is possible and even binary-rewriting instrumentation is infeasible (e.g., heavily obfuscated or DRM-protected binaries). Real embodying system: the original Miller/Fredriksen/So 1990 "fuzz" utility-testing methodology, and many early network-protocol fuzzers. Why rejected here: with zero coverage feedback, the search is blind — it cannot distinguish "this mutation found something new" from "this mutation is redundant," making it dramatically less sample-efficient than greybox fuzzing at any interesting target size, and directly violating P1 (coverage as the fitness function).

Symbolic/concolic execution (SAGE/KLEE lineage).

Winning regime: targets dominated by a small number of hard, precisely-structured guards (checksums, magic values, parser state machines) where exact constraint solving reaches code greybox mutation would need astronomical time to reach (§34's magic-byte calculation). Why rejected here: path explosion (the number of distinct paths grows exponentially with branch count) and per-path solver cost make execs/second, this project's master metric (P2), orders of magnitude worse than greybox mutation at realistic target sizes — a deliberate, explicit non-goal stated in §1.

In-process (libFuzzer-style) vs. out-of-process (AFL fork-server-style).

Winning regime: in-process wins when the harness is well-behaved and resettable and maximum execs/second matters most (Phase 9's persistent mode adopts this for exactly that case); out-of-process wins when target crashes/hangs/state corruption must never be allowed to touch the fuzzer's own process, or when the target cannot be made safely resettable. Real embodying systems: libFuzzer (in-process), AFL/AFL++ (fork-server, out-of-process). Why the project keeps both rather than choosing one: this is the one "road not fully taken exclusively" — ADR-05 locks fork-server as the safe default while explicitly building persistent/in-process as an opt-in (Phase 9), rather than treating it as a rejected alternative outright, because the throughput case for it (§34) is too strong to discard.

Snapshot fuzzing (restore a memory snapshot per execution).

+----------------+   restore VM/process   +--------------------+
|  Saved Snapshot |----------------------->|  Target at exact    |
|  (memory image) |                        |  pre-fuzz state      |
+----------------+                        +----------+-----------+

        | restore for next exec                       v
        +---------------------------------- +--------------------+

Winning regime: heavily stateful targets (long-lived servers, kernel subsystems, targets with expensive one-time setup) where neither a fresh fork nor an in-process reset can cheaply reproduce the exact pre-fuzz state — snapshot restore can be faster than either because it skips both fork()'s page-table cost and the harness's own setup/state-reset cost. Real embodying pattern: kernel/VM-snapshot fuzzing approaches used in some syzkaller-adjacent and hypervisor-based fuzzing setups. Why rejected here (for now): implementing correct, fast memory-snapshot restore requires OS/hypervisor-level primitives well outside this project's Phase 0-11 scope (§1's boundaries — the project delegates process isolation to the OS rather than building a VM layer); recorded as PhaseDeferred("§31 Scalability Analysis — snapshot fuzzing") and ADR-19.

38. Glossary

  • Fuzzing — automated testing via feeding a target program unexpected or malformed input to trigger failures (Miller, Fredriksen & So 1990).
  • Coverage-guided greybox fuzzing — fuzzing that uses lightweight runtime feedback (edge coverage) to direct mutation, without full program analysis (Manès et al. 2019).
  • Black-box fuzzing — fuzzing with no visibility into target internals; input generation is uninformed by execution feedback.
  • Whitebox fuzzing — fuzzing informed by full program analysis, typically via symbolic execution (SAGE).
  • Concolic execution — hybrid concrete-plus-symbolic execution that collects path predicates during a real run (DART, SAGE).
  • Symbolic execution — execution over symbolic (unconstrained) input values, collecting logical path constraints solved by an SMT solver (KLEE).
  • Edge coverage — coverage tracked at the level of control-flow-graph edges (branch transitions), the AFL default granularity.
  • Block coverage — coverage tracked at the level of basic blocks, coarser than edge coverage.
  • Coverage bitmap — the shared-memory array recording which edges (or edge/hit-count buckets) have been observed (§8.1).
  • Bitmap collision — two distinct edges hashing to the same bitmap slot, undercounting true coverage (Gan et al. 2018, CollAFL).
  • prev_loc — the previous instrumented location, combined with the current location to compute an edge ID (§8.1).
  • Fork server — a persistent parent process that repeatedly forks fresh children to execute inputs, avoiding per-input execve cost (AFL whitepaper).
  • Persistent mode — repeated in-process re-entry into a target's entrypoint across many inputs without a fresh fork per input.
  • In-process fuzzing — executing the target directly within the fuzzer's own process/address space (libFuzzer model).
  • Snapshot fuzzing — restoring a saved memory/VM state per execution instead of forking or resetting in place (§36).
  • Corpus — the set of retained inputs a campaign has accumulated because they exercised new coverage.
  • Seed — an initial or retained input in the corpus; also, the PRNG seed controlling reproducible mutation (context-dependent usage, both used in this document).
  • Queue — the corpus represented as an orderable, schedulable collection of QueueEntry records.
  • Interesting input — an input whose execution produced new coverage (new edge or new hit-count bucket), and is therefore admitted to the corpus.
  • Mutation — a transformation applied to an input to produce a new candidate input.
  • Bitflip — a deterministic mutation flipping one or more consecutive bits at a given offset.
  • Havoc — a stochastic mutation stage applying a randomized stacked sequence of mutation primitives.
  • Splicing — a crossover mutation combining byte ranges from two distinct corpus entries.
  • Dictionary — a set of known tokens (magic bytes, keywords, extracted constants) available for substitution mutation.
  • Token — a single dictionary entry, a byte sequence with presumed semantic significance to the target.
  • Structure-aware fuzzing — mutation performed at the level of a parsed input model rather than raw bytes.
  • Grammar fuzzing — generation/mutation guided by a formal grammar describing valid input structure.
  • Power schedule — the policy assigning mutation-trial energy to each corpus entry.
  • Energy — the mutation-trial budget assigned to a given seed for a scheduling round.
  • AFLFast — the Markov-chain-informed power schedule favoring low-frequency-path seeds (Böhme et al. 2016).
  • Seed scheduling — the policy selecting which corpus entry to mutate next.
  • Favored seed — a seed selected as part of the minimal spanning set covering all currently-known edges.
  • Queue culling — periodic recomputation of the favored-seed spanning set.
  • Queue aging — an energy boost applied to seeds untouched for an extended duration, preventing starvation.
  • Crash — a target execution outcome classified as abnormal termination (signal or sanitizer abort).
  • Hang — an execution that fails to terminate within the configured timeout.
  • Timeout — the enforced maximum wall-clock duration for a single execution.
  • Crash deduplication — grouping crashes believed to share the same root cause into one artifact/group.
  • Stack hash — a dedup key computed from the unwound call stack at the point of failure, using relative offsets.
  • Coverage hash — a dedup key computed from the coverage signature of a crashing execution, used as a fallback when stack symbols are unavailable.
  • Minimization — reducing a corpus or a single input while preserving a defined property (coverage union or crash signature).
  • cmin — corpus minimization: reducing the corpus to a minimal subset preserving full coverage union (§8.9).
  • tmin — test-case minimization: reducing a single crashing input while preserving its crash signature (§8.9).
  • Sanitizer — a compiled-in runtime detector for a class of undefined/unsafe behavior (ASan, UBSan, MSan).
  • ASan — AddressSanitizer, a memory-safety-violation detector (Serebryany et al. 2012).
  • Input-to-state correspondence — directly capturing and reusing a runtime-compared value to defeat a guard, without a solver (REDQUEEN, Aschermann et al. 2019).
  • REDQUEEN — the specific input-to-state-correspondence technique and system (Aschermann et al. 2019).
  • Magic bytes — a fixed constant value a target checks for exact match before proceeding, a canonical hard-to-mutate-into guard.
  • Coverage plateau — a period of little-to-no new-edge discovery despite continued execution, signaling diminishing returns from the current mutation strategy.
  • Execs/second — the throughput metric counting target executions per second; this project's master performance metric.
  • Harness — the adapter code exposing a target's entrypoint to the fuzzer's execution ABI.
  • ABI (harness) — the calling-convention contract between the fuzzer and the target harness (e.g., LLVMFuzzerTestOneInput).
  • Campaign — one running instance of the fuzzer against one target, with its own corpus/crash/metadata directory.
  • Corpus sync — the mechanism by which multiple parallel workers share discovered coverage and crashes.
  • Evaluation harness — the Klees-et-al-style bugs-over-trials measurement subsystem used as the project's primary effectiveness gate (§23, §28).
  • Coverage-bitmap density — the fraction of bitmap slots ever set during a campaign, tracked as a saturation-warning signal distinct from the raw collision-rate estimate (§13.10, §8.15).
  • Favored set — the minimal spanning set of queue entries collectively covering every currently-known edge, recomputed periodically via queue culling (§8.7).
  • Queue culling entry (cross-reference) — see queue culling above; retained here as a glossary anchor since favored-set and queue-culling terminology are used interchangeably in §8.7 and the phase sections.
  • Corpus sync race — a transient condition where two parallel workers both locally decide a piece of coverage is new before either has observed the other's sync update; self-correcting within the sync cadence window (§22.6).
  • Trial (evaluation) — one independent, seeded run of a campaign against a benchmark target within the Klees-et-al evaluation harness, the unit over which bug-finding significance is computed (§23, §28).
