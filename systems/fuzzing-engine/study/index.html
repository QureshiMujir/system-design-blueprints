Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If the coverage bitmap is only a lossy 64 KiB hash of "edges seen," how confident can the project be that a long coverage plateau reflects target exhaustion rather than bitmap collision saturation? (§8.2, §31, §34)
  2. Why is stack-hash chosen as the primary crash-dedup key when it is strictly less robust to stripped binaries than coverage-hash — what does that ordering assume about the target population this project expects to fuzz? (§8.8, ADR-14)
  3. Given that persistent mode delivers a ~100x execs/second win (§34), why is it not simply the unconditional default rather than an opt-in Phase 9 feature? (§8.3, I5, ADR-05)
  4. The power schedule (§8.5) assigns energy based on a seed's path hit-count — but what happens when the coverage-hash itself used to key that hit-count is subject to the same collision risk discussed for the raw bitmap? (§8.2, §8.5, §18.6)
  5. If minimization (I6) guarantees the coverage union is preserved, does that guarantee say anything about whether the scheduling-relevant per-path hit-count distribution is preserved — and if not, could minimization silently undo Phase 6's scheduling work? (§18, §20)
  6. Why does the project treat "coverage alone is not a success metric" (P3) as a hard testing-strategy rule (§28) rather than merely a documentation caveat — what would go wrong operationally if coverage percentage were allowed as a stand-alone CI gate? (§23, §28, ADR-25)
  7. The dictionary/token mechanism (§8.4, ADR-09) and REDQUEEN's input-to-state correspondence (§8.10) both attack the same magic-byte-guard problem (§34) — why does this project build the former as a committed subsystem and leave the latter as a "noted extension" rather than building both to the same depth? (§1, §8.10, §17)
  8. Given that the fork-server protocol (§8.3) and the persistent-mode model (§8.3 contrast) are both "the execution model," why does ADR-05 lock fork-server as the default rather than persistent mode, when §34's math so strongly favors persistent mode on throughput alone? (§8.3, §21, ADR-05)
  9. If a nondeterministic target (T4) can poison the corpus by producing different bitmaps for the same input, how does the is-interesting decision (I1) avoid systematically over-admitting garbage from such a target, and is that failure mode fully distinguishable from genuine new-coverage discovery without a dedicated repeat-check? (§8.3, T4, §24)
  10. The evaluation harness (§23, §28) depends on a benchmark suite of known injected bugs to measure recall — what does that structurally miss about a fuzzer's ability to find genuinely unknown bug classes it was never benchmarked against? (§23, §28, §35 self-limitation)
  11. Crash-dedup's coverage-hash fallback (ADR-14) is explicitly flagged as capable of silently merging two distinct root causes (I7, T6) — why is a "manual review flag" considered sufficient mitigation rather than a stronger automated secondary signal? (§8.8, §19, T6)
  12. Structure-aware/grammar fuzzing (Phase 10, ADR-10) is scoped as an opt-in plugin hook rather than a built-in engine — does that design choice implicitly push the hardest, most target-specific engineering work (grammar authoring) onto the operator, and if so, is that consistent with the project's goal of being broadly useful out of the box? (§1, §22, ADR-10)
  13. Parallel corpus sync (§22) relies on a shared filesystem directory rather than a coordinator process — at what worker count does this become the dominant bottleneck described in §31, and is that threshold ever validated empirically rather than assumed? (§22, §31, M9)
  14. The threat model (§24, T1) treats a malicious target escaping the sandbox as a mitigated risk via namespace/seccomp isolation — but sandbox escapes are themselves a class of security bug; how does the project avoid a false sense of safety here given it explicitly does not build a full DBI/hypervisor isolation layer? (§1, §24-T1)
  15. §34's magic-byte guessing-time calculation assumes independent, uniformly random guesses per execution — does actual havoc/deterministic mutation behave close enough to that assumption for the calculation's conclusion (dictionaries are necessary) to hold, or could deterministic mutation's structured coverage of small values change the real-world number materially? (§8.4, §16, §34)
  16. If soak testing (§23, I11) validates resume-correctness across one forced restart, does that meaningfully bound the risk of corruption across the many restarts a real multi-week production campaign might experience, or is the test's coverage of this risk narrower than the acceptance criterion implies? (§23.4, §25-FM-2, I11)
  17. The project explicitly excludes symbolic/concolic execution (§1, §36) on throughput grounds, yet §8.10 and several Hard Questions above point back to REDQUEEN as a solver-free way to get some of symbolic execution's guard-solving benefit — at what point does accumulating enough of these "solver-free workarounds" start to functionally resemble the excluded approach, undermining the clean architectural boundary drawn in §1? (§1, §8.10, §36)
  18. The nondeterminism-detection procedure (§8.14) repeats an input N times (default 10) to classify a target as nondeterministic — what is the false-negative rate of that check against a target that is nondeterministic only rarely (e.g., a 1-in-1000 race), and does the §21 persistent-mode state-leak canary share the same blind spot for the same reason? (§8.14, §21.6, §24-T4)
  19. The bitmap-saturation response procedure (§8.15) resizes the bitmap or switches to collision-aware hashing after a sustained breach — but resizing invalidates the prior virgin map (§8.15 step 5), so does the campaign's apparent "coverage growth" before and after a resize remain a meaningful single time series, or does §26's plateau-detection dashboard need to treat a resize event as a discontinuity? (§8.15, §26, §31)
  20. §30's performance-engineering methodology treats execs/second as the single dependent variable, yet §28 insists coverage and execs/second alone are not sufficient success metrics — how does the project reconcile a performance-engineering discipline built around one master metric with an evaluation discipline that explicitly refuses to let that same metric stand in for effectiveness? (§28, §30, P2, P3)
  21. Favored-seed selection (§8.7) picks the smallest, fastest entry covering each edge — but Phase 6's power schedule (§8.5) separately weights energy by path hit-count; can these two seed-preference signals conflict (a favored seed on a high-hit-count path versus a non-favored seed on a rare path), and if so, which one wins in the current design? (§8.5, §8.7, §18)
  22. The threat model (§24, T8) documents fuzzing's dual-use nature as a policy note rather than a runtime control — given that the same engine that finds bugs for defenders finds them equally well for attackers, is a documentation-only mitigation for T8 consistent with how seriously the project treats every other threat-model row, which all carry a runtime detection/telemetry/recovery path? (§24-T8, §1)

32. Mental Models & First Principles

  • MM1 — Coverage-guided fuzzing is evolutionary search where the fitness function is "did you reach somewhere new." That one bit of feedback is what separates it from dumb random testing and is the entire reason it works (AFL whitepaper; P1).
  • MM2 — Execs/second is the currency. Every architectural decision downstream of §3 is really a decision about running the target more times per second — the fork server, persistent mode, and even the choice of Rust over Python all reduce to this one number (P2, §34).
  • MM3 — A magic-byte or checksum guard is a wall random mutation cannot climb. Dictionaries, input-to-state correspondence (REDQUEEN), and concolic execution are all ways to guess the wall's password rather than brute-force it — they differ only in how they learn the password (P11, §8.10, §36).
  • MM4 — The bitmap is a lossy compression of "where has this program been." Its size and hash function are a deliberate trade of precision (perfect path tracking) for cost (a fixed 64 KiB scan), and every collision is a small, accepted lie the fuzzer tells itself about coverage (§8.2, CollAFL).
  • MM5 — A crash without a replay is not a bug, it's a rumor. The entire crash-triage subsystem exists because "it crashed once" carries zero engineering value until it can be reproduced on demand (P6, I3).
  • MM6 — Energy is a scarce resource being allocated under uncertainty about which seed is most promising. The power schedule is a bet, not a certainty, and AFLFast's contribution was making that bet quantitative instead of uniform (P5, §8.5).
  • MM7 — Minimization and mutation are opposite-direction operations over the same search space. Mutation expands a corpus outward looking for new coverage; minimization contracts it inward looking for the smallest representative set — and both must respect the same coverage-preservation contract to be trustworthy (I6, §8.9).
  • MM8 — A fuzzer is only as trustworthy as its own evaluation methodology. A fuzzer that "seems to find bugs" without an N-trial, dedup-against-ground-truth, statistically-significant evaluation is making an unfalsifiable claim — Klees et al.'s contribution was making fuzzing evaluation a science rather than a demo (P3, §28).
  • MM9 — Isolation and speed are in permanent tension. Fork-per-input isolates every execution completely at high cost; in-process/persistent mode shares an address space across executions at low cost but reintroduces the exact cross-contamination risk process isolation was preventing (§8.3, I5).
  • MM10 — Coverage plateaus are not failures, they are information. A flattening new-edge curve tells the operator precisely where to invest next — a dictionary, a grammar plugin, or accepting the target's current ceiling — rather than signaling anything is broken (P14, §31).
  • MM11 — Nondeterminism is a property of the target, not a bug in the fuzzer, until proven otherwise. A repeat-check (§8.14) exists because the fuzzer's own correctness cannot be judged from a single suspicious observation; the target must be interrogated deliberately before the fuzzer's own logic is blamed.
  • MM12 — Deduplication is a lossy compression of "how many distinct bugs exist," exactly as the bitmap is a lossy compression of "where has this program been." Both trade a small, bounded, monitored error rate for a tractable representation — the discipline is in knowing and measuring the error rate (T6, §8.8), not in pretending it is zero.
  • MM13 — Parallelism is not free coverage. Adding a worker adds raw execs/second linearly at first, but the unique-coverage contribution per additional worker decays as sync overhead grows (§22, §31, §34) — the naive assumption that N workers find N times the bugs of one worker is wrong past a modest worker count on a single node.

Required reading (§5)

Books/Surveys

  • Manès et al. 2019, "The Art, Science, and Engineering of Fuzzing" (IEEE TSE) — the definitive survey; taxonomy of generation-vs-mutation, coverage-vs-directed. Applied in §1, §8, §32.
  • Zalewski, the AFL technical whitepaper ("afl-fuzz" documentation) — the founding design document for edge-bitmap coverage-guided fuzzing. Applied in §3, §8, Phase 1 (§13).
  • the libFuzzer documentation (LLVM project) — in-process fuzzing model and harness ABI. Applied in §1, §33, Phase 9 (§21).
  • Fioraldi et al. 2020, "AFL++: Combining Incremental Steps of Fuzzing Research" (WOOT) — consolidated modern greybox techniques (power schedules, CmpLog, custom mutators). Applied in §9, §33, Phase 6 (§18).
  • Böhme et al. 2016, "Coverage-based Greybox Fuzzing as Markov Chain" (CCS) — AFLFast, the power-schedule reference. Applied in §8, §32, Phase 6 (§18).
  • Böhme et al. 2017, "Directed Greybox Fuzzing" (CCS) — distance-guided scheduling, contrast to undirected AFLFast. Applied in §8, §31.
  • Klees et al. 2018, "Evaluating Fuzz Testing" (CCS) — the evaluation-methodology reference; must inform every benchmark/testing section. Applied in §28, §30, Phase 11 (§23).

Papers

  • Miller, Fredriksen & So 1990, "An Empirical Study of the Reliability of UNIX Utilities" (CACM) — the original fuzzing paper. Applied in §2, §32.
  • Böhme et al. 2016, "Coverage-based Greybox Fuzzing as Markov Chain" (CCS, AFLFast). Applied in §8, Phase 6 (§18).
  • Aschermann et al. 2019, "REDQUEEN" (NDSS) — input-to-state correspondence for guard-solving without a solver. Applied in §8, §32, Phase 5 (§17).
  • Gan et al. 2018, "CollAFL" (S&P) — coverage-bitmap collision analysis and mitigation. Applied in §8, §9-ADR-08, Phase 1 (§13).
  • Godefroid, Levin & Molnar 2008, "Automated Whitebox Fuzz Testing" (SAGE, NDSS) — concolic contrast. Applied in §1, §33, §36.
  • Godefroid et al. 2005, "DART" (PLDI) — directed automated random testing, concolic lineage. Applied in §36.
  • Cadar, Dunbar & Engler 2008, "KLEE" (OSDI) — symbolic execution engine, the precision-vs-throughput contrast case. Applied in §33, §36.
  • Serebryany et al. 2012, "AddressSanitizer" (USENIX ATC) — the sanitizer runtime the crash detector depends on. Applied in §3, §8, Phase 9 (§21).
  • Pham et al. 2019, "AFLSmart" — structure-aware fuzzing via input models. Applied in §8, Phase 10 (§22).
  • Klees et al. 2018, "Evaluating Fuzz Testing" (CCS). Applied in §28, §30.

Reference Implementations

  • AFL++ (src/afl-fuzz-*.c, afl-cc instrumentation, the fork server) — lesson: the fork server amortizes execve cost to near zero; pitfall: fork-server handshake desync silently hangs a campaign. Applied in Phase 2 (§14), Phase 9 (§21).
  • LLVM libFuzzer (compiler-rt/lib/fuzzer/) — lesson: in-process execution is dramatically faster but sacrifices isolation; pitfall: one target global-state leak poisons every subsequent run. Applied in Phase 9 (§21), §33.
  • honggfuzz — lesson: persistent-mode + hardware-assisted coverage (perf counters) as an AFL alternative; pitfall: platform-dependent counter availability. Applied in §33, Phase 9 (§21).
  • LibAFL (libafl/src/) — lesson: fuzzing components (executor, feedback, corpus, mutator, scheduler) are composable and independently testable, the most directly relevant architectural precedent; pitfall: over-abstraction can regress the hot-path exec cost if not benchmarked continuously. Applied in §9, §11, all of Phase 0-11.
  • SanitizerCoverage (__sanitizer_cov_trace_pc_guard interface) — lesson: this is the normative instrumentation contract, not something the fuzzer reimplements; pitfall: guard-table layout assumptions break across compiler versions without ABI versioning. Applied in §1, §8, §27.
  • OSS-Fuzz (published results/architecture) — lesson: continuous, always-on fuzzing integrated into a project's CI at scale finds regressions the moment they're introduced, validating the eval.yml perf/bug-regression gating model; pitfall: a purely continuous-integration posture without periodic long-horizon soak runs still misses slow-to-surface, low-probability bugs. Applied in §23, §29, §30.

RFCs / Specifications

  • the SanitizerCoverage interface specification (LLVM/compiler-rt docs) — normative instrumentation ABI. Applied in §11, §27, Phase 1 (§13).
  • the sanitizer runtime documentation (ASan/UBSan/MSan interface docs) — normative crash-signal contract. Applied in §8, §24, Phase 9 (§21).

Glossary (§38) · 60 terms · site-wide glossary

Fuzzing
automated testing via feeding a target program unexpected or malformed input to trigger failures (Miller, Fredriksen & So 1990).
Coverage-guided greybox fuzzing
fuzzing that uses lightweight runtime feedback (edge coverage) to direct mutation, without full program analysis (Manès et al. 2019).
Black-box fuzzing
fuzzing with no visibility into target internals; input generation is uninformed by execution feedback.
Whitebox fuzzing
fuzzing informed by full program analysis, typically via symbolic execution (SAGE).
Concolic execution
hybrid concrete-plus-symbolic execution that collects path predicates during a real run (DART, SAGE).
Symbolic execution
execution over symbolic (unconstrained) input values, collecting logical path constraints solved by an SMT solver (KLEE).
Edge coverage
coverage tracked at the level of control-flow-graph edges (branch transitions), the AFL default granularity.
Block coverage
coverage tracked at the level of basic blocks, coarser than edge coverage.
Coverage bitmap
the shared-memory array recording which edges (or edge/hit-count buckets) have been observed (§8.1).
Bitmap collision
two distinct edges hashing to the same bitmap slot, undercounting true coverage (Gan et al. 2018, CollAFL).
prev_loc
the previous instrumented location, combined with the current location to compute an edge ID (§8.1).
Fork server
a persistent parent process that repeatedly forks fresh children to execute inputs, avoiding per-input execve cost (AFL whitepaper).
Persistent mode
repeated in-process re-entry into a target's entrypoint across many inputs without a fresh fork per input.
In-process fuzzing
executing the target directly within the fuzzer's own process/address space (libFuzzer model).
Snapshot fuzzing
restoring a saved memory/VM state per execution instead of forking or resetting in place (§36).
Corpus
the set of retained inputs a campaign has accumulated because they exercised new coverage.
Seed
an initial or retained input in the corpus; also, the PRNG seed controlling reproducible mutation (context-dependent usage, both used in this document).
Queue
the corpus represented as an orderable, schedulable collection of QueueEntry records.
Interesting input
an input whose execution produced new coverage (new edge or new hit-count bucket), and is therefore admitted to the corpus.
Mutation
a transformation applied to an input to produce a new candidate input.
Bitflip
a deterministic mutation flipping one or more consecutive bits at a given offset.
Havoc
a stochastic mutation stage applying a randomized stacked sequence of mutation primitives.
Splicing
a crossover mutation combining byte ranges from two distinct corpus entries.
Dictionary
a set of known tokens (magic bytes, keywords, extracted constants) available for substitution mutation.
Token
a single dictionary entry, a byte sequence with presumed semantic significance to the target.
Structure-aware fuzzing
mutation performed at the level of a parsed input model rather than raw bytes.
Grammar fuzzing
generation/mutation guided by a formal grammar describing valid input structure.
Power schedule
the policy assigning mutation-trial energy to each corpus entry.
Energy
the mutation-trial budget assigned to a given seed for a scheduling round.
AFLFast
the Markov-chain-informed power schedule favoring low-frequency-path seeds (Böhme et al. 2016).
Seed scheduling
the policy selecting which corpus entry to mutate next.
Favored seed
a seed selected as part of the minimal spanning set covering all currently-known edges.
Queue culling
periodic recomputation of the favored-seed spanning set.
Queue aging
an energy boost applied to seeds untouched for an extended duration, preventing starvation.
Crash
a target execution outcome classified as abnormal termination (signal or sanitizer abort).
Hang
an execution that fails to terminate within the configured timeout.
Timeout
the enforced maximum wall-clock duration for a single execution.
Crash deduplication
grouping crashes believed to share the same root cause into one artifact/group.
Stack hash
a dedup key computed from the unwound call stack at the point of failure, using relative offsets.
Coverage hash
a dedup key computed from the coverage signature of a crashing execution, used as a fallback when stack symbols are unavailable.
Minimization
reducing a corpus or a single input while preserving a defined property (coverage union or crash signature).
cmin
corpus minimization: reducing the corpus to a minimal subset preserving full coverage union (§8.9).
tmin
test-case minimization: reducing a single crashing input while preserving its crash signature (§8.9).
Sanitizer
a compiled-in runtime detector for a class of undefined/unsafe behavior (ASan, UBSan, MSan).
ASan
AddressSanitizer, a memory-safety-violation detector (Serebryany et al. 2012).
Input-to-state correspondence
directly capturing and reusing a runtime-compared value to defeat a guard, without a solver (REDQUEEN, Aschermann et al. 2019).
REDQUEEN
the specific input-to-state-correspondence technique and system (Aschermann et al. 2019).
Magic bytes
a fixed constant value a target checks for exact match before proceeding, a canonical hard-to-mutate-into guard.
Coverage plateau
a period of little-to-no new-edge discovery despite continued execution, signaling diminishing returns from the current mutation strategy.
Execs/second
the throughput metric counting target executions per second; this project's master performance metric.
Harness
the adapter code exposing a target's entrypoint to the fuzzer's execution ABI.
ABI (harness)
the calling-convention contract between the fuzzer and the target harness (e.g., LLVMFuzzerTestOneInput).
Campaign
one running instance of the fuzzer against one target, with its own corpus/crash/metadata directory.
Corpus sync
the mechanism by which multiple parallel workers share discovered coverage and crashes.
Evaluation harness
the Klees-et-al-style bugs-over-trials measurement subsystem used as the project's primary effectiveness gate (§23, §28).
Coverage-bitmap density
the fraction of bitmap slots ever set during a campaign, tracked as a saturation-warning signal distinct from the raw collision-rate estimate (§13.10, §8.15).
Favored set
the minimal spanning set of queue entries collectively covering every currently-known edge, recomputed periodically via queue culling (§8.7).
Queue culling
entry (cross-reference) — see queue culling above; retained here as a glossary anchor since favored-set and queue-culling terminology are used interchangeably in §8.7 and the phase sections.
Corpus sync race
a transient condition where two parallel workers both locally decide a piece of coverage is new before either has observed the other's sync update; self-correcting within the sync cadence window (§22.6).
Trial (evaluation)
one independent, seeded run of a campaign against a benchmark target within the Klees-et-al evaluation harness, the unit over which bug-finding significance is computed (§23, §28).
