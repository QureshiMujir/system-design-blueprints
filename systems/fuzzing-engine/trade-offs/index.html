ADR-01

Implementation language

Chosen

Rust

Rejected

C/C++, Go

When the rejected choice is right

a from-scratch AFL-ABI-compatible drop-in replacement prioritizing max upstream-patch reuse (favors C)

Why: memory safety in the orchestrator; zero-cost hot path; no GC pause on exec loop

ADR-02

Coverage-instrumentation mechanism

Chosen

compile-time SanitizerCoverage

Rejected

binary rewriting, QEMU/emulation black-box

When the rejected choice is right

fuzzing closed-source binaries with no source access (QEMU mode wins)

Why: lowest overhead, LLVM-native, matches libFuzzer/AFL++ default

ADR-03

Coverage granularity

Chosen

edge coverage

Rejected

block coverage, path coverage, context-sensitive coverage

When the rejected choice is right

targets where path-sensitive state matters more than edge novelty and execs/sec budget is generous (path coverage wins)

Why: best empirically-validated cost/signal ratio (AFL whitepaper)

ADR-04

Bitmap design & collision handling

Chosen

fixed 64 KiB bitmap, CollAFL-style collision-aware hashing available as opt-in

Rejected

unbounded per-edge counters, perfect hashing

When the rejected choice is right

targets with >50k live edges where collision rate exceeds tolerance (larger map / CollAFL hashing wins)

Why: bounded memory, proven-good default size

ADR-05

Execution model

Chosen

fork server (default) with persistent/in-process opt-in

Rejected

pure fork+exec per input, full snapshot/VM-fork

When the rejected choice is right

targets requiring near-zero per-exec overhead on a trusted, stateless harness (persistent/in-process wins)

Why: fork server is the proven 10x+ win over naive fork+exec at moderate isolation cost

ADR-06

"Interesting" criterion

Chosen

new edge or new hit-count bucket

Rejected

new edge only (coarser), full path uniqueness (finer)

When the rejected choice is right

targets where hit-count noise from nondeterminism makes bucket-tracking counterproductive (new-edge-only wins)

Why: matches AFL's validated bucket scheme; balances sensitivity and queue bloat

ADR-07

Mutation strategy set

Chosen

layered: deterministic + havoc + splice + dictionary + structure-aware hook

Rejected

havoc-only, pure random

When the rejected choice is right

extremely time-constrained micro-campaigns where deterministic-pass overhead isn't worth it (havoc-only wins)

Why: layering matches empirically distinct discovery regimes (§8.4)

ADR-08

Deterministic-vs-havoc balance

Chosen

deterministic pass on new/small seeds only, havoc-dominant thereafter

Rejected

always run full deterministic pass, always skip deterministic pass

When the rejected choice is right

small, well-understood target formats where deterministic bitflip is cheap and highly effective (full deterministic wins)

Why: deterministic passes have high per-seed cost with diminishing returns on large corpora (AFL++ findings)

ADR-09

Dictionary/token support

Chosen

supported, auto-extracted from comparisons plus user-supplied file

Rejected

dictionary-free havoc only

When the rejected choice is right

targets with no meaningful token structure (e.g., raw arithmetic fuzzing) where dictionaries add noise

Why: large empirical win defeating magic-byte guards (P11)

ADR-10

Structure-aware/grammar fuzzing

Chosen

optional plugin hook, not a built-in grammar engine

Rejected

full built-in CFG grammar engine

When the rejected choice is right

a single flagship target format (e.g., one file format) where a bundled grammar pays for itself

Why: keeps core engine target-agnostic; grammar authoring is target-specific effort (Pham et al. 2019 pattern)

ADR-11

Power schedule

Chosen

AFLFast Markov-chain schedule (default)

Rejected

uniform round-robin schedule

When the rejected choice is right

extremely small, fully-covered corpora where scheduling variance doesn't matter

Why: proven throughput-to-bug-discovery win (Böhme et al. 2016)

ADR-12

Seed scheduling / queue culling

Chosen

favored-set spanning recomputed periodically + queue aging

Rejected

no culling, re-fuzz every seed equally forever

When the rejected choice is right

campaigns explicitly studying scheduling-fairness properties themselves

Why: prevents redundant re-exploration of already-well-covered seeds

ADR-13

Crash detection

Chosen

signal-based + sanitizer-abort parsing

Rejected

signal-based only

When the rejected choice is right

targets compiled without any sanitizer where the sanitizer-parsing path is simply inactive

Why: sanitizer aborts catch corruption with no visible signal otherwise (Serebryany et al. 2012)

ADR-14

Crash dedup

Chosen

stack-hash primary, coverage-hash fallback

Rejected

coverage-hash only, bug-oracle/AI-based clustering

When the rejected choice is right

fully stripped/obfuscated targets with no usable stack symbols (coverage-hash-only wins)

Why: stack-hash is precise when symbols exist; documented fallback covers stripped binaries

ADR-15

Minimization strategy

Chosen

greedy set-cover (cmin) + iterative delta-reduction (tmin)

Rejected

exhaustive minimal-cover search, no minimization

When the rejected choice is right

very small corpora where exhaustive minimization is cheap and exact-optimal matters

Why: greedy set-cover is near-optimal in practice at tractable cost

ADR-16

Parallel/distributed fuzzing

Chosen

shared-directory corpus sync across local workers

Rejected

full distributed cluster coordinator (RPC-based)

When the rejected choice is right

multi-machine fleets exceeding what filesystem sync can serve (RPC coordinator wins, deferred)

Why: matches Phase-0-11 scope; cluster orchestration explicitly deferred (§1)

ADR-17

Sanitizer integration

Chosen

ASan/UBSan/MSan via harness build flags

Rejected

no sanitizer support, custom in-house checker

When the rejected choice is right

targets where sanitizer runtime overhead makes execs/sec unacceptable for the campaign's time budget (no-sanitizer wins for a coverage-only pre-pass)

Why: reuse of the industry-standard, validated detectors (Serebryany et al. 2012)

ADR-18

Harness/target ABI

Chosen

Rejected

When the rejected choice is right

Why: maximizes reuse of the existing OSS-Fuzz/AFL++ target corpus

ADR-19

Snapshot fuzzing

Chosen

not implemented in Phase 0-11; documented as future direction

Rejected

When the rejected choice is right

heavily stateful kernel/service targets where fork/persistent-mode reset is insufficient (snapshot fuzzing wins)

Why: out of scope; stateful-target speed is a deferred concern (§1, §31)

ADR-20

Timeout/hang handling

Chosen

Rejected

no timeout (rely on target well-behavedness)

When the rejected choice is right

a fully trusted, pre-vetted target suite where hangs are structurally impossible (still not recommended; no realistic regime "wins" outright — even trusted-target CI pipelines with hard wall-clock caps retain a fallback watchdog)

ADR-21

36. Alternative Architectures (Roads Not Taken)

Pure black-box/dumb fuzzing (no instrumentation).

+-----------+     random input     +-----------------+
|  Mutator  |---------------------->|  Target (opaque) |
+-----------+                       +--------+---------+
                                              |
                                       exit/crash only
                                              v
                                     +------------------+
                                     | Crash Detector    |
                                     +------------------+

Winning regime: closed-source targets where no compile-time hook is possible and even binary-rewriting instrumentation is infeasible (e.g., heavily obfuscated or DRM-protected binaries). Real embodying system: the original Miller/Fredriksen/So 1990 "fuzz" utility-testing methodology, and many early network-protocol fuzzers. Why rejected here: with zero coverage feedback, the search is blind — it cannot distinguish "this mutation found something new" from "this mutation is redundant," making it dramatically less sample-efficient than greybox fuzzing at any interesting target size, and directly violating P1 (coverage as the fitness function).

Symbolic/concolic execution (SAGE/KLEE lineage).

+----------------+   collect path    +--------------------+
|  Concrete/     |------------------->|  Path Predicate    |
|  Symbolic Exec |                    |  Collector          |
+----------------+                    +----------+----------+
                                                  | negate one branch
                                                  v
                                       +--------------------+
                                       |  SMT Solver         |
                                       +----------+----------+
                                                  | new concrete input
                                                  v
                                       +--------------------+
                                       |  Re-execute Target  |
                                       +--------------------+

Winning regime: targets dominated by a small number of hard, precisely-structured guards (checksums, magic values, parser state machines) where exact constraint solving reaches code greybox mutation would need astronomical time to reach (§34's magic-byte calculation). Real embodying systems: SAGE (Godefroid, Levin & Molnar 2008), DART (Godefroid et al. 2005), KLEE (Cadar, Dunbar & Engler 2008). Why rejected here: path explosion (the number of distinct paths grows exponentially with branch count) and per-path solver cost make execs/second, this project's master metric (P2), orders of magnitude worse than greybox mutation at realistic target sizes — a deliberate, explicit non-goal stated in §1.

In-process (libFuzzer-style) vs. out-of-process (AFL fork-server-style).

In-process:                          Out-of-process (fork server):
+------------------+                 +------------------+     fork()    +------------+
| Fuzzer + Target   |                | Fuzzer            |-------------->| Target     |
| (same address     |                | (stable parent)    |               | (fresh     |
|  space, looped)   |                +------------------+               |  child)    |
+------------------+                                                    +------------+

Winning regime: in-process wins when the harness is well-behaved and resettable and maximum execs/second matters most (Phase 9's persistent mode adopts this for exactly that case); out-of-process wins when target crashes/hangs/state corruption must never be allowed to touch the fuzzer's own process, or when the target cannot be made safely resettable. Real embodying systems: libFuzzer (in-process), AFL/AFL++ (fork-server, out-of-process). Why the project keeps both rather than choosing one: this is the one "road not fully taken exclusively" — ADR-05 locks fork-server as the safe default while explicitly building persistent/in-process as an opt-in (Phase 9), rather than treating it as a rejected alternative outright, because the throughput case for it (§34) is too strong to discard.

Snapshot fuzzing (restore a memory snapshot per execution).

+----------------+   restore VM/process   +--------------------+
|  Saved Snapshot |----------------------->|  Target at exact    |
|  (memory image) |                        |  pre-fuzz state      |
+----------------+                        +----------+-----------+
        ^                                            | run one input
        | restore for next exec                       v
        +---------------------------------- +--------------------+
                                             |  Discard post-exec  |
                                             |  state, no fork     |
                                             +--------------------+

Winning regime: heavily stateful targets (long-lived servers, kernel subsystems, targets with expensive one-time setup) where neither a fresh fork nor an in-process reset can cheaply reproduce the exact pre-fuzz state — snapshot restore can be faster than either because it skips both fork()'s page-table cost and the harness's own setup/state-reset cost. Real embodying pattern: kernel/VM-snapshot fuzzing approaches used in some syzkaller-adjacent and hypervisor-based fuzzing setups. Why rejected here (for now): implementing correct, fast memory-snapshot restore requires OS/hypervisor-level primitives well outside this project's Phase 0-11 scope (§1's boundaries — the project delegates process isolation to the OS rather than building a VM layer); recorded as PhaseDeferred("§31 Scalability Analysis — snapshot fuzzing") and ADR-19.
