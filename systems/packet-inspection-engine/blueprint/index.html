218 — Packet Inspection Engine from Scratch

Project Number: 218

Project Name: Packet Inspection Engine from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition. A packet inspection engine is a userspace pipeline that classifies raw link-layer frames into flows, reconstructs ordered byte streams from those flows, decodes protocol grammars incrementally over the reconstructed streams, evaluates a rule runtime over the decoded events, and emits durable metadata plus telemetry — all under bounded memory, bounded latency, and deterministic replay. It is the packet-plane analogue of a query engine: ingress is the scan, flow/stream tracking is the join key, protocol parsing is projection, and the rule runtime is the filter predicate. Every stage must survive adversarial, malformed, and out-of-order input without unbounded resource growth.

Target: Linux-first userspace inspection platform, AF_PACKET baseline ingress with optional AF_XDP fast-path and eBPF pre-filtering, deployed passively (SPAN/TAP) or inline (bridge).

Phase 0 deliverable — numbered crate list (workspace members, §10 mirrors this exactly):

  1. pkt-capture — ingress abstraction over AF_PACKET / AF_XDP / PCAP replay.
  2. pkt-flow — flow key classification, flow table, eviction.
  3. pkt-stream — TCP stream reassembly.
  4. pkt-parser — incremental protocol decoders (HTTP/1.1, DNS, TLS ClientHello, PostgreSQL startup, Redis RESP, Kafka metadata).
  5. pkt-rule-engine — deterministic rule AST, compiler, Hyperscan-backed matcher.
  6. pkt-replay — WAL, segment rotation, deterministic replay scheduler.
  7. pkt-telemetry — metrics/tracing/log export.
  8. pkt-storage — RocksDB-backed metadata persistence.
  9. pkt-runtime — worker supervisor, lifecycle, shutdown orchestration.
  10. pkt-cli — operator command-line surface.
  11. pkt-observability — dashboards, health checks, profiling endpoints.
  12. pkt-bench — Criterion benchmark harness binary.
  13. pkt-fuzz — cargo-fuzz target aggregator.
  14. pkt-conformance — fixture-driven conformance runner.
  15. pkt-control-api — runtime configuration and rule-distribution API.

System boundary — provides: packet acquisition, packet normalization, flow tracking, TCP stream reconstruction, UDP session correlation, protocol parsing for the six listed grammars, inspection runtime, rule execution, metadata persistence, telemetry pipeline, replay infrastructure, observability infrastructure.

System boundary — delegates: kernel packet delivery (AF_PACKET/AF_XDP/NIC driver), TCP/IP correctness of the host stack, container/orchestration scheduling (Kubernetes), long-term telemetry storage (Prometheus/OTel backends), certificate trust decisions.

System boundary — does NOT provide: endpoint malware scanning, TLS interception via forged certificates, distributed policy orchestration, WAN routing, SDN control planes, Layer-7 load balancing, full packet-broker functionality. This is not a firewall appliance, not a full IDS/IPS replacement in Phase 0, not a generic SIEM, not a kernel module, not a TCP stack replacement.

Non-goals: GPU-accelerated regex scanning (PhaseDeferred("§17")), programmable WASM inspection runtime (PhaseDeferred("§16")), FPGA offload (PhaseDeferred("§20")), ML-assisted anomaly detection (PhaseDeferred("§19")), adaptive flow sampling (PhaseDeferred("§14")), QUIC deep stream decryption (PhaseDeferred("§16")), and distributed correlation across collectors (PhaseDeferred("§21")) — every one registered in §35 with the same anchor.

Deployment model: bare-metal Linux hosts, Kubernetes DaemonSets, security sensor appliances, edge network appliances, observability clusters, cloud traffic-mirror collectors. Supported modes: (1) passive SPAN/TAP analysis, (2) inline bridge inspection, (3) offline PCAP replay, (4) synthetic test-harness mode.

Target operators: network security teams, SRE/platform-observability teams, DFIR/SOC engineers (operators); protocol-parser developers, rule authors, performance engineers (developers); incident-response and release engineers, kernel-integration engineers (maintainers).

What later phases unlock: Phase 1 unlocks live traffic ingestion; Phase 2 unlocks stateful flow accounting; Phase 3 unlocks ordered byte streams (prerequisite for any protocol decode); Phase 4 unlocks protocol-level events; Phase 5 unlocks detection; Phase 6 unlocks forensic replay and crash recovery; Phase 7 unlocks production-grade debuggability; Phase 8 unlocks kernel fast-path acceleration; Phase 9 unlocks multi-tenant, multi-collector production rollout.

Recommended language: Rust. Rationale: deterministic ownership model eliminates use-after-free and double-free under hostile packet input (I1, I6); Send/Sync trait bounds make cross-worker packet ownership a compile-time property (P4); zero-cost abstractions keep the hot path allocation-bounded (P6); the async ecosystem (Tokio, ADR-07) gives structured concurrency for supervisor/telemetry without a hand-rolled reactor; cargo-fuzz and Hyperscan FFI are both mature.

Rejected languages:

Language Rejection Reason
C Unacceptable memory-corruption risk under malformed packet handling; no ownership checker.
C++ Allocator complexity and ownership ambiguity across worker-to-worker packet handoff.
Go GC pause jitter under sustained 8 Mpps packet pressure violates p99 latency budget (§4).
Java JVM startup cost and heap amplification violate the 10 s cold-start budget (§4).
Zig Networking/async ecosystem too immature for AF_XDP + Hyperscan FFI integration today.

Prerequisites: Linux networking internals, TCP/IP protocol stack, packet-capture systems, eBPF, AF_PACKET, AF_XDP, NUMA behavior, lock-free concurrency, async runtimes, parsers and finite-state machines, storage engines, observability systems, tracing infrastructure, cryptographic-protocol basics (TLS handshake shape, not crypto implementation), memory allocators, kernel/userspace boundaries, cache-locality optimization, distributed-systems fundamentals.

Estimated timeline: Phase 0 (repo bootstrap + runtime foundation): 6–14 weeks, covering packet ingress, stream tracking, TCP reassembly, parser framework, rule execution, telemetry. Full production platform (protocol hardening, replay determinism, high-scale observability, multi-tenant operation, eBPF integration, AF_XDP acceleration, rolling upgrades, distributed collectors): 6–12 months.

3.2 Box-by-Box Narrative

Control Plane (pkt-cli, pkt-control-api). Owns runtime configuration, parser registration, dynamic rule updates, policy synchronization, feature gating, health reporting, operational introspection. Never touches packet payload — this trust boundary (P4, I1) prevents administrative activity from injecting tail-latency amplification into the data plane.

Runtime Supervisor (pkt-runtime). Owns worker lifecycle, crash detection, queue-pressure management, NUMA placement enforcement (I11), telemetry aggregation, coordinated shutdown. Every worker failure propagates through a supervisor crash domain — crash-only semantics (P3).

RX Workers (pkt-capture). Acquire packets from AF_PACKET, AF_XDP, or replay sources. Perform timestamp normalization, framing validation, checksum-state extraction, RSS-aware sharding, ingress-queue assignment. This is the concurrency boundary where packet ownership is first assigned (I1).

Flow Engine (pkt-flow). Owns flow-key normalization, flow-table management, timeout handling, state transitions, memory accounting, eviction. Establishes deterministic single-owner semantics for every packet (I1) — the persistence boundary for flow-local state begins here.

Stream Reassembly (pkt-stream). Reconstructs ordered byte streams from fragmented/out-of-order TCP segments inside bounded buffers (I5); handles retransmission deduplication. Protocol boundary: downstream parsers never see raw segments, only ordered bytes.

Protocol Parsers (pkt-parser). Deterministic finite-state incremental decoders for HTTP/1.1, DNS, TLS ClientHello, PostgreSQL startup, Redis RESP, Kafka metadata. Fault-isolation boundary (P5, I6) — a parser panic quarantines one flow, never the process.

Rule Execution Runtime (pkt-rule-engine). Executes pattern matching, metadata filters, protocol predicates, threshold logic, behavioral rules. Allocation-bounded, deterministic under malformed traffic (I7) — the external interface where detections are produced.

Metadata Storage (pkt-storage). Persists flow summaries, parser outputs, alerts, runtime diagnostics, replay indexes. Raw packet persistence is optional — a separate, explicitly-enabled external interface into the PCAP archive.

Telemetry + Export Pipeline (pkt-telemetry). Exports Prometheus metrics, OpenTelemetry traces, structured logs, event streams, alert notifications, entirely asynchronously (P14) — an external interface that must never backpressure the data plane.

Persistence + Replay Layer (pkt-replay). WAL, PCAP archive, snapshot state. The durability boundary: every mutation the rule runtime and flow engine care about for forensic replay crosses this queue as an async append, never a synchronous write in the hot path.

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every packet-processing outcome must be bit-for-bit replayable from the WAL. · Tradeoff: forbids any wall-clock-seeded randomness or unordered concurrent writes to shared detection state. · Operational: replay-diff CI gate blocks merges that change match output for a fixed corpus. · Violated: alerts become irreproducible and postmortems cannot establish causality.
  • P2 — Backpressure Everywhere. Rule: every runtime queue is bounded and its bound is enforced at construction, not at insert time. · Tradeoff: bounded queues drop or stall under overload instead of degrading gracefully. · Operational: queue-depth gauges exported per stage (§19). · Violated: unbounded queues convert transient overload into catastrophic memory exhaustion (I5).
  • P3 — Crash-Only Worker Semantics. Rule: workers never attempt in-place recovery; they exit and the supervisor restarts them from durable state. · Tradeoff: every worker-local cache must be rebuildable from the flow table or WAL on restart. · Operational: supervisor restart budget is bounded by the RTO in §4. · Violated: ad-hoc in-process recovery paths accumulate untested edge cases and eventually corrupt shared state.
  • P4 — Explicit Ownership. Rule: every packet descriptor has exactly one owning subsystem at any instant, enforced by move semantics, not by convention. · Tradeoff: cross-worker handoff requires an explicit ownership-transfer API instead of shared mutable references. · Operational: duplicate-ownership counters alert (I1). · Violated: double frees, aliasing races, mutation ambiguity under concurrent access.
  • P5 — Parser Isolation. Rule: protocol parsers can mutate only flow-local parser state, never shared runtime state. · Tradeoff: cross-parser correlation (e.g. TLS-over-HTTP CONNECT) needs an explicit event bus, not shared memory. · Operational: parser panic isolates one flow (I6). · Violated: a single malformed frame can corrupt state shared across unrelated flows.
  • P6 — Allocation-Bounded Hot Paths. Rule: RX, flow-lookup, and rule-dispatch code paths issue zero heap allocations per packet in steady state. · Tradeoff: requires pre-sized pools and arena allocators instead of ergonomic Vec/Box usage. · Operational: allocator-churn counters gate performance CI (§28 M-series). · Violated: heap churn under load causes allocator lock contention and unpredictable tail latency.
  • P7 — Replayability First. Rule: every runtime decision that affects a detection outcome must be externally inspectable from the WAL, not just internally logged. · Tradeoff: adds a structured-record write to every state transition that matters for replay. · Operational: replay parity check in pkt-conformance (§26). · Violated: forensic replay silently diverges from the original decision path.
  • P8 — Stable Wire Compatibility. Rule: telemetry schemas are append-only; a field is never removed or repurposed. · Tradeoff: schema evolution requires deprecation windows instead of breaking renames. · Operational: schema-compat check in CI against the last two major versions (I8). · Violated: downstream telemetry consumers silently misparse a repurposed field.
  • P9 — Observability by Default. Rule: every subsystem emits metrics, traces, and structured events without an opt-in flag. · Tradeoff: baseline cardinality cost is paid even when a subsystem is quiet. · Operational: cardinality-guard alerts cap unexpected label explosion (§22 T-series). · Violated: an incident with no data plane visibility becomes undebuggable.
  • P10 — Fail Closed on Corruption. Rule: a parser or flow state detected as internally inconsistent terminates inspection for that flow rather than guessing. · Tradeoff: some malformed-but-benign traffic loses inspection coverage rather than risking a wrong verdict. · Operational: flow-quarantine counter and forced eviction (I6). · Violated: guessing past corrupted state produces false negatives that are worse than a dropped flow.
  • P11 — NUMA Locality Preservation. Rule: a packet's flow context, parser state, and rule evaluation stay on the NUMA node that received it; cross-node transfer requires an explicit, logged justification. · Tradeoff: imperfect RSS hashing can leave a node underutilized rather than rebalancing across nodes in the hot path. · Operational: cross-node-transfer counter is a first-class metric (§4). · Violated: silent cross-node memory traffic doubles flow-lookup latency under load.
  • P12 — Bounded State Lifetime. Rule: all flow and stream state carries an expiry, enforced by a timeout wheel, not by best-effort garbage collection. · Tradeoff: legitimate long-lived idle connections require an explicit keepalive-aware timeout class instead of a single global timeout. · Operational: eviction-rate dashboard (§19). · Violated: unbounded flow lifetime is the single largest driver of the memory ceilings in §4.
  • P13 — Protocol Parsing Must Be Incremental. Rule: a parser must be able to suspend at any byte boundary and resume later without re-scanning consumed bytes. · Tradeoff: parser state machines are more complex than a buffer-then-parse design. · Operational: partial-frame fixture coverage in pkt-conformance (§16.5). · Violated: buffer-then-parse designs cannot bound memory under slow-drip adversarial input.
  • P14 — Telemetry Must Not Stall the Data Plane. Rule: telemetry export runs on a separate async task set with its own bounded queue; a full telemetry queue drops telemetry, never packets. · Tradeoff: telemetry loss is possible under exporter outage. · Operational: telemetry-drop counter distinguishes this from packet drop (§22 T7). · Violated: a slow exporter becomes a data-plane bottleneck.
  • P15 — Versioned Persistence. Rule: every persisted record (WAL frame, snapshot, metadata row) carries an explicit schema version. · Tradeoff: every reader must carry a version-dispatch table instead of assuming one layout. · Operational: schema-version histogram exported per storage engine (I8). · Violated: a rolling upgrade silently corrupts records written by a mixed-version fleet.

8. Domain Model — Protocol & Flow Semantics

8.1 Packet Lifecycle

RX packet -> ingress normalization -> flow classification -> stream tracking
          -> protocol decode -> rule evaluation -> telemetry emission -> archival

Each arrow is a queue crossing (I5) and an ownership transfer point (I1, I4 in §11's PacketDescriptor).

8.2 Flow State Machine

State Description Transition Trigger
NEW First packet observed for this FlowKey. RX classification miss on flow table.
ACTIVE Packets actively processed. Any packet after NEW.
IDLE Timeout pending; no packets within the idle window. Idle-timeout wheel tick (P12).
EVICTING Cleanup in progress; no new packets accepted. Idle expiry, active-timeout expiry, or memory pressure.
CLOSED Finalized; flow summary persisted. FIN/RST sequence complete or eviction complete.

8.3 TCP Reassembly States

State Meaning
SYN_SEEN Connection initialization observed, handshake incomplete.
ESTABLISHED Bidirectional stream, reassembly active both directions.
HALF_CLOSED One direction closed (FIN seen), other still reassembling.
CLOSED Connection terminated cleanly.
RESET RST observed; buffers discarded per policy, not silently.

8.4 Parser Interface Contract

ParserInput {
    stream_fragment: &[u8];
    flow_ctx: FlowContextRef; }

ParserResult {
    consumed_bytes: usize;
    parser_state: ParserState;
    events: Vec<ParserEvent>;
    errors: Vec<ParserError>; }

consumed_bytes may be less than stream_fragment.len() — the unconsumed remainder is re-presented on the next call (P13). This contract is identical across all six protocol decoders in §16.

8.5 Rule Runtime Semantics

Rules operate over five event classes: packet metadata (flow tuple, timing), stream payloads (post-reassembly bytes), parser events (ParserEvent from §8.4), flow counters (byte/packet rates), and timing windows (sliding-window thresholds). A rule may reference at most one payload match, bounded metadata predicates, and one temporal-window predicate per clause (I12 budget enforcement depends on this bound being fixed at compile time, §17.2).

8.6 Example Flow (illustrative, non-normative)

Client SYN -> Server SYN/ACK -> Client ACK -> HTTP GET -> HTTP RESPONSE -> FIN

Generated artifacts: TCP session metadata (flow summary), one HTTP request ParserEvent, one response-latency metric sample, one flow summary record on CLOSED.

8.7 Malformed Cases (canonical, referenced by phase fixtures)

Overlapping TCP segments with conflicting payload bytes; invalid HTTP chunk-size fields; malformed DNS compression pointers forming a cycle; truncated TLS records mid-extension. Expected behavior in every case: parser isolation (I6), telemetry emission (P9), bounded failure — never an unbounded buffer, an infinite loop, or a process crash (P10).

11. Core Schema & Types

Signature-only, no bodies. Annotations: Own = ownership model, Mut = mutation surface, Conc = concurrency semantics, Pers = persistence, Ser = serialization, Compat = compatibility class.

struct PacketDescriptor {
    ingress_id: u64,
    rx_queue: u16,
    timestamp_ns: u64,
    packet_len: u32,
    capture_len: u32,
    flow_hash: u64,
    checksum_state: ChecksumState,
    payload_ref: PayloadRef, }
  • Own: single-owner (RX worker) until handed off to FlowContext; Mut: immutable after construction; Conc: Send, never Sync — no shared mutable aliasing; Pers: not persisted directly, summarized into flow/alert records; Ser: n/a (in-memory only); Compat: internal, no wire format.
struct FlowKey {
    src_ip: IpAddr,
    dst_ip: IpAddr,
    src_port: u16,
    dst_port: u16,
    protocol: L4Protocol,
    vlan_id: u16, }
  • Own: value type, copied freely; Mut: immutable, canonicalized once at construction (I1); Conc: Send + Sync, safe to hash concurrently; Pers: embedded in flow-summary records (§18); Ser: protobuf (ADR-05); Compat: append-only field additions only (P8).
struct FlowContext {
    key: FlowKey,
    state: FlowState,
    parser_state: ParserStateSlot,
    stream: Option<TcpReassemblyBuffer>,
    counters: FlowCounters,
    created_at_ns: u64,
    last_seen_ns: u64,
    memory_bytes: u32, }
  • Own: single-owner per shard worker (ADR-08); Mut: mutated only by the owning shard's worker thread; Conc: migration only during explicit rebalance, never concurrent (I1, P11); Pers: snapshotted at checkpoint boundaries (§18); Ser: protobuf; Compat: two-major-version readable (I8).
struct TcpReassemblyBuffer {
    next_expected_seq: u32,
    segments: SegmentTree,
    high_water_bytes: u32,
    gap_count: u16,
    overlap_count: u16, }
  • Own: owned by FlowContext.stream; Mut: mutated by the owning worker only; Conc: not shared; Pers: not persisted directly (rebuilt from WAL on recovery, P7); Ser: n/a; Compat: internal.
struct ParserEvent {
    parser_id: ParserId,
    timestamp_ns: u64,
    severity: Severity,
    metadata: EventMetadata,
    payload_refs: SmallVec<PayloadRef>, }
  • Own: constructed by a parser, moved into the rule-runtime input queue; Mut: immutable after construction; Conc: Send, single-consumer per flow; Pers: optionally persisted as parser-output record (§18); Ser: protobuf; Compat: append-only metadata fields (P8).
struct RuleMatch {
    rule_id: RuleId,
    flow_key: FlowKey,
    matched_at_ns: u64,
    evidence: MatchEvidence,
    rule_version: u32, }
  • Own: constructed by the rule scheduler; Mut: immutable; Conc: Send, fanned out to storage and telemetry concurrently; Pers: durable WAL append before async export (I4, I7); Ser: protobuf; Compat: two-major-version readable (I8).
struct TelemetryEnvelope {
    kind: TelemetryKind,
    payload: TelemetryPayload,
    emitted_at_ns: u64,
    trace_id: Option<TraceId>, }
  • Own: constructed at emission site, owned by the telemetry queue until exported; Mut: immutable; Conc: Send, MPSC into the async exporter (P14, ADR-22); Pers: not persisted by the engine itself (exported to Prometheus/OTel backends); Ser: OTel/Prometheus wire formats; Compat: append-only (P8).
struct ReplayFrame {
    frame_seq: u64,
    segment_id: SegmentId,
    schema_version: u16,
    body: ReplayFrameBody,
    checksum: u32, }
  • Own: owned by the WAL append engine until flushed; Mut: immutable once appended; Conc: Send, single-writer per segment (I4); Pers: the durability boundary itself; Ser: custom WAL framing (ADR-07 replay format); Compat: schema_version-dispatched reader (I8, P15).
struct WorkerHandle {
    worker_id: WorkerId,
    numa_node: NumaNodeId,
    kind: WorkerKind,
    shutdown: ShutdownToken, }
  • Own: owned by pkt-runtime supervisor; Mut: shutdown token is the only mutable field, written once; Conc: Send + Sync, shared read-only by health checks; Pers: not persisted; Ser: n/a; Compat: internal.
struct RuntimeError {
    class: ErrorClass,
    subsystem: SubsystemId,
    context: ErrorContext,
    retryable: bool, }
  • Own: value type, propagated up call stacks; Mut: immutable; Conc: Send + Sync; Pers: optionally logged as a structured event (§19); Ser: structured-log JSON; Compat: class enum is append-only (P8).
trait ProtocolParser {
    fn parser_id(&self) -> ParserId;
    fn feed(&mut self, input: ParserInput) -> ParserResult;
    fn reset(&mut self); }
  • Own: one instance per flow, owned by FlowContext.parser_state; Mut: feed/reset are the only mutation surface; Conc: never shared across flows (I6, P5); Pers: ParserState snapshot is part of the flow snapshot; Ser: parser-specific, versioned; Compat: adding a new ParserId variant is additive only.
trait RuleEvaluator {
    fn evaluate(&self, events: &[ParserEvent], ctx: &FlowCounters) -> Vec<RuleMatch>;
    fn budget_cost(&self) -> ExecutionBudget; }
  • Own: one instance per compiled rule, owned by the rule scheduler's dispatch table; Mut: immutable after compilation (hot-reload replaces the whole instance, §17.2); Conc: Send + Sync, invoked concurrently across flows; Pers: not persisted (rebuilt from rule source on load); Ser: n/a; Compat: budget_cost must be stable across a rule's version to preserve I12.

12. Phase 0 — Repository Bootstrap & Runtime Foundation

12.1 Objectives

  • Stand up the Cargo workspace, crate boundaries, and CI before any packet ever crosses the process (P3, ADR-02).
  • Establish the runtime-supervisor skeleton and worker-lifecycle contracts that every later phase builds workers against (P3, P4).
  • Establish tracing/metrics baselines so Phase 1 onward is observable from its first commit (P9).

  1. Create the Cargo workspace (Cargo.toml) with the fifteen member crates from §1 (ADR-02).

  3. Configure clippy deny-list (unwrap in non-test code, unbounded allocation lints) — ADR-25.
  4. Configure rustfmt stability profile pinned in rust-toolchain.toml.
  5. Implement tracing bootstrap in pkt-runtime::supervisor — span-per-worker (ADR-09).
  6. Implement the WorkerHandle (§11) lifecycle contract: spawn, health-check, shutdown-signal.
  7. Define the RuntimeSupervisor API: register worker, report health, request shutdown.
  8. Define configuration loading (ConfigLoader, TOML, ADR-24) with schema validation.
  9. Add a feature-gate registry keyed by string flags, resolved once at startup (P15-adjacent).
  10. Add structured shutdown orchestration: supervisor issues ShutdownToken, workers drain in a deterministic order (P3, I4 anticipates WAL flush ordering in §18).
  11. Add the metrics registry (pkt-telemetry::metrics) — Prometheus exposition (ADR-11).
  12. Add panic-hook installation that converts a worker panic into a RuntimeError (§11) instead of an unhandled abort.
  13. Add crash-reporting hooks feeding the supervisor's crash-domain counter (P3).
  14. Configure ci.yml: build, clippy, test, and doc-lint (I11) stages.
  15. Configure benchmark.yml running pkt-bench on a fixed runner class.
  16. Add cargo-audit dependency-audit tooling to CI (ADR-03).
  17. Add Syft SBOM generation to the release pipeline (ADR-18).
  18. Add reproducible-build configuration: cargo --locked, deterministic timestamps (ADR-20).
  19. Add build-metadata stamping (git SHA, build time, enabled features) into the binary.
  20. Configure release-artifact naming convention consumed by release.yml (§27).

12.3 Deliverable

A runnable runtime shell: pkt-runtime binary that starts, registers zero workers, exposes a Prometheus metrics endpoint, exposes a structured-log stream, and shuts down cleanly on SIGTERM. Config parsing accepts config/minimal.toml and rejects config/invalid-missing-runtime.toml with a diagnosable error.

12.4 Acceptance Criteria

  • Workspace compiles cleanly on the pinned toolchain; zero clippy warnings under the deny-list.
  • Cold start under 10 s (§4), measured from exec to metrics-endpoint-ready.
  • Graceful shutdown completes and exits 0 within 5 s with zero workers registered.
  • Metrics endpoint returns valid Prometheus exposition format (# HELP/# TYPE lines present).
  • fixtures/runtime/shutdown-sequence.json replay reproduces the same shutdown ordering twice.

12.5 Conformance Fixtures

  • fixtures/runtime/config-minimal.toml — smallest valid config, must load without warnings.
  • fixtures/runtime/config-invalid-missing-runtime.toml — malformed case, must reject with a named validation error, not a panic.
  • fixtures/runtime/shutdown-sequence.json — replay case, expected worker-shutdown order recorded.
  • fixtures/runtime/duplicate-worker-name.toml — malformed case, must reject at registration.

12.6 Pitfalls

  • Runtime shutdown deadlock. Manifestation: workers never terminate. Root cause: circular cancellation waits between two workers awaiting each other's ShutdownToken. Debugging: replay fixtures/runtime/shutdown-sequence.json under the deterministic simulator (§7) and diff the observed wait-graph. Signal: shutdown watchdog timer fires. Recovery: force-kill after a bounded grace period, alert.
  • Logger initialization race. Manifestation: missing startup logs. Root cause: a worker emits before tracing subscriber installation completes. Debugging: startup-order trace span review. Signal: gap in the span timeline before the first runtime.started event. Recovery: gate worker spawn on subscriber-ready signal.
  • Feature-gate drift. Manifestation: runtime inconsistency across nodes running the same binary. Root cause: feature flags resolved from environment rather than the versioned config (P15-adjacent). Signal: runtime.feature_gate telemetry diverges between nodes. Recovery: resolve gates exclusively from the loaded config snapshot, never ambient environment.

12.7 Performance Concerns

  • Startup allocation spikes from eager metrics-registry pre-sizing; batch registration instead.
  • Tracing-subscriber contention if spans are emitted from more threads than the writer can drain.
  • Lock-heavy metrics registries under high cardinality; pre-allocate label sets at startup (P6).

12.8 Edge Cases

  • Invalid UTF-8 in a config file must fail with a byte-offset diagnostic, not a panic.
  • Duplicate worker names at registration must be rejected deterministically, not last-write-wins.
  • Partial config reload (file truncated mid-write by an external tool) must not corrupt in-memory config state — validate the whole file before swapping.

12.9 Failure Analysis

Failure domain: runtime bootstrap. Containment: fail-fast startup — any config or crate-boundary violation aborts before any worker spawns, never a partial-degraded start. Blast radius: contained to the single process; no persisted state exists yet at this phase. Operator visibility: startup failures print a single structured diagnostic to stderr before the tracing subscriber is even up.

12.10 Operational Notes

Expose at startup: build SHA, runtime version, enabled feature gates, active-worker count (zero at this phase). Metric: runtime.startup.duration_ms. Trace span: runtime.bootstrap. Log field: build.sha. No migration concerns yet — this phase defines the schema version baseline (I8, P15) that every later persisted record inherits.

  13. Implement bounded ingress queues from RX ring to flow-classification stage (P2, I5).

13.3 Deliverable

A capture subsystem that ingests live AF_PACKET traffic or a PCAP replay file through the same PacketSource interface, producing a stream of owned PacketDescriptor values into the bounded ingress queue, with drop/truncation accounting visible via metrics.

13.4 Acceptance Criteria

  • Sustains 2,000,000 pps from replay input on the reference benchmark host without ring-full drops.
  • Packet-loss accounting matches kernel-reported drops within 0.1% on pcap/ipv4-basic.pcap.
  • Malformed frames in pcap/malformed-ethernet.pcap are isolated (rejected, counted) not crashed.

13.5 Conformance Fixtures

  • fixtures/capture/ipv4-basic.pcap — baseline well-formed traffic.
  • fixtures/capture/ipv6-fragments.pcap — IPv6 fragmentation reassembly precondition case.
  • fixtures/capture/truncated-frames.pcap — capture_len < packet_len regression case.
  • fixtures/capture/malformed-ethernet.pcap — malformed-frame rejection case.
  • fixtures/capture/replay-determinism.pcap — replayed twice, diffed for byte-identical output.

13.6 Pitfalls

  • RX ring starvation. Manifestation: RX worker stalls under burst. Root cause: descriptor pool exhausted because downstream flow classification is slower than ingress. Debugging: watch capture.pool.exhausted counter against flow.classify.latency. Signal: pool-exhaustion counter climbs while throughput flatlines. Recovery: bounded drop at the ring (I5), never block RX.
  • Packet-ownership leak. Manifestation: descriptor pool shrinks over time without corresponding frees. Root cause: a downstream stage holds a PayloadRef past flow eviction (violates P4). Debugging: pool high-water-mark trend versus active-flow count. Signal: pool exhaustion at steady-state traffic. Recovery: audit PayloadRef drop points; add a leak-detector fixture.
  • Timestamp inconsistency across RX queues. Manifestation: reordering artifacts blamed on reassembly that are actually ingress-timestamp skew. Root cause: per-queue clock reads without a shared monotonic base. Debugging: cross-queue timestamp-delta histogram. Signal: I3 violation counter nonzero. Recovery: single shared CLOCK_MONOTONIC read path (ADR-21).

13.7 Performance Concerns

  • Cache-line bouncing between RX worker and descriptor-pool allocator under high queue count.
  • Syscall amplification from small per-packet recvmmsg calls instead of batched drains (step 6).
  • Packet-copy amplification if payload_ref is deep-copied instead of referencing the mmap ring.

13.8 Edge Cases

  • Jumbo frames (>1500 B) exceeding the pre-sized descriptor payload region.
  • Invalid VLAN double-tagging (QinQ) beyond the parser's nesting bound.
  • Partial replay-file truncation mid-record — must stop cleanly, not read past EOF into garbage.

13.9 Failure Analysis

Ingress saturation triggers bounded drops at the ring boundary (I5), never unbounded queue growth. Detection: capture.queue.depth gauge crossing 90% of bound triggers an alert. Blast radius: contained to the affected RX queue/NUMA node; other queues continue (P11). Containment: RSS rebalancing is an operator action, not automatic mid-flight. Operator visibility: per-queue drop rate dashboard (§19).

13.10 Operational Notes

Metrics: capture.rx.packets, capture.rx.dropped, capture.rx.truncated, capture.queue.depth. Trace span: capture.rx.batch. Log fields: rx_queue, numa_node, drop_reason. Deployment: RX-queue-to-NUMA-node mapping is part of the DaemonSet node-affinity spec. Rollback: reverting this phase means reverting to no live ingress — replay-only mode remains available as a safe fallback.

14.4 Acceptance Criteria

  • Sustains 5,000,000 concurrent flows (§4) on the reference benchmark host without exceeding the 8 GB flow-table ceiling.
  • Flow-lookup latency p99 under 2 µs measured via pkt-bench on flows/eviction-pressure.json.
  • Emergency eviction under synthetic flood (flows/eviction-pressure.json) never exceeds the memory ceiling for more than one eviction-scoring tick.
  • NAT-rewrite fixture (flows/nat-rewrite.json) canonicalizes both pre- and post-NAT tuples to the same flow.

14.5 Conformance Fixtures

  • fixtures/flow/nat-rewrite.json — pre/post-NAT tuple canonicalization case.
  • fixtures/flow/fragmented-ipv4.json — fragment-before-first-packet ordering case.
  • fixtures/flow/eviction-pressure.json — synthetic flood exceeding capacity, expects bounded memory and forced eviction.
  • fixtures/flow/reused-tuple.json — a closed flow's tuple reused by a new connection within one timeout window.

14.6 Pitfalls

  • Hash flooding. Manifestation: one shard absorbs disproportionate load. Root cause: an attacker crafts tuples hashing to the same shard. Debugging: per-shard load histogram. Signal: shard-imbalance ratio exceeds 3× median. Recovery: keyed/salted hash rotated per deployment (not per packet, to preserve I1 determinism within one run).
  • Timeout-wheel drift. Manifestation: flows expire later than configured. Root cause: wheel tick driven by wall-clock reads that skip under scheduler pressure. Debugging: compare configured idle timeout against observed eviction latency in flows/eviction-pressure.json replay. Signal: flow.eviction.latency_p99 exceeds 2× the configured timeout. Recovery: drive the wheel from CLOCK_MONOTONIC ticks accounted independently of scheduler latency (ADR-21).
  • Flow leaks. Manifestation: flow count grows without bound despite steady traffic. Root cause: a reference cycle between FlowContext and a parser-held back-reference prevents eviction. Debugging: heap-profile diff before/after a synthetic idle period. Signal: flow count doesn't decay after traffic stops. Recovery: audit ownership graph (P4); add a leak-detector fixture.

14.7 Performance Concerns

  • Allocator churn on flow creation/eviction under high turnover; pool FlowContext slots (P6).
  • Hash collisions within a shard degrading lookup from O(1) toward O(n); bound bucket depth.
  • NUMA-remote accesses if a shard's memory arena isn't pinned to the shard's owning node (I10).

14.8 Edge Cases

  • Asymmetric routing: only one direction of a bidirectional flow observed by this sensor.
  • Partial TCP handshakes (SYN with no ACK) that never reach ESTABLISHED.
  • Reused 4-tuples within one timeout window creating ambiguous flow identity.

14.9 Failure Analysis

Flow exhaustion triggers emergency eviction (lowest-score-first) before rejecting new flow creation. Detection: flow.table.utilization gauge crossing 95%. Blast radius: contained to new flow admission; existing flows unaffected. Recovery path: eviction scoring runs synchronously on the admission path only when utilization is critical, otherwise on the timeout-wheel schedule. Operator visibility: eviction-rate and utilization dashboards (§19); forensic snapshot taken before emergency eviction (P7).

14.10 Operational Notes

Metrics: flow.table.size, flow.table.utilization, flow.eviction.rate, flow.lookup.latency_p99. Trace span: flow.classify. Log fields: shard_id, eviction_reason. Critical dashboards: flow count, eviction rate, timeout pressure (source-verbatim naming preserved for operator familiarity). Migration: flow-table schema version bump requires a drain-and-rehydrate from the last snapshot (I8).

15. Phase 3 — TCP Stream Reassembly

15.1 Objectives

  • Implement ordered byte-stream reconstruction from fragmented and out-of-order TCP segments (I2, RFC 793 §5).
  • Implement deterministic overlap-resolution policy and retransmission suppression.
  • Constraint introduced: reassembly buffer memory is capped per-stream (I9-adjacent) and in aggregate at the §4 ceiling.

15.2 Detailed Implementation Steps

  1. Implement sequence tracking (sequence.rs) — next_expected_seq with wraparound-safe comparison (Stevens 1994 ch. 17–21; applied per §5).
  2. Add overlap-handling policy (overlap.rs): first-write-wins, recorded deterministically for replay (P1, I2).
  3. Add out-of-order buffering via a bounded interval tree (SegmentTree in §11).
  4. Add retransmission suppression: byte ranges already delivered are dropped, not re-buffered.
  5. Add FIN/RST semantics matching the state machine in §8.3.
  6. Add partial-stream delivery: bytes up to a gap are handed to the parser immediately (P13).
  7. Add per-stream memory limits enforced at buffer-insert time, not after the fact (I5).
  8. Add stream-gap markers surfaced to the parser as an explicit ParserEvent field, not silence.
  9. Add parser-wakeup signaling when a gap closes and buffered bytes become contiguous.
  10. Add reassembly telemetry: gap count, overlap count, buffer occupancy per stream.
  11. Add buffer compaction: contiguous delivered ranges are freed immediately, not retained.
  12. Add stream aging tied into the flow's idle-timeout wheel (P12 reuse, no separate wheel).
  13. Add corruption detection: an internally inconsistent TcpReassemblyBuffer (e.g. negative gap) trips fail-closed quarantine (P10).
  14. Add replay verification comparing live reassembly output against WAL-recorded byte streams.
  15. Add deterministic segment-ordering: ties in sequence number broken by ingress timestamp, not arrival order into the buffer (P1).
  16. Add IPv4-fragmentation integration: fragments reassemble into one IP payload before TCP sequence tracking begins.
  17. Add flow-termination cleanup: reassembly buffer freed synchronously on flow CLOSED.
  18. Add stream checkpoints for pkt-replay snapshotting (§18, I13).
  19. Add high-water-mark alerts when a stream approaches its per-stream memory limit.
  20. Add malformed-TCP handling: invalid flag combinations (e.g. SYN+FIN) rejected deterministically.

15.3 Deliverable

A TCP stream-reconstruction runtime that, given out-of-order and retransmitted segments, delivers one ordered byte stream per direction to the parser layer, with bounded memory and a deterministic, replay-stable overlap policy.

15.4 Acceptance Criteria

  • streams/reordered-segments.pcap reassembles to the byte-identical stream as its known-good ordered baseline.
  • Overlap policy is deterministic: streams/overlapping-segments.pcap produces the same resolved bytes across 100 replay runs (I2, I7-adjacent).
  • Memory stays bounded under streams/overlapping-segments.pcap amplified 50× — no stream exceeds its configured per-stream cap.
  • streams/missing-fin.pcap ages out via the idle-timeout wheel within the configured window, not indefinitely.

15.5 Conformance Fixtures

  • fixtures/stream/reordered-segments.pcap — out-of-order delivery, expects correct reordering.
  • fixtures/stream/overlapping-segments.pcap — conflicting payload regions, expects deterministic first-write-wins resolution.
  • fixtures/stream/missing-fin.pcap — no clean close, expects idle-timeout aging.
  • fixtures/stream/sequence-wraparound.pcap — sequence number wraps past 2^32, expects correct wraparound comparison.

15.6 Pitfalls

  • Infinite buffering. Manifestation: a stream's buffer grows without bound. Root cause: a gap never closes because the missing segment was dropped upstream, and no per-stream cap is enforced. Debugging: buffer-occupancy trend on the stuck stream. Signal: high-water alert fires and stays latched. Recovery: enforce the per-stream cap at insert time (step 7), evict the stream on cap breach.
  • Overlap ambiguity. Manifestation: two replay runs of the same PCAP produce different reassembled bytes. Root cause: overlap resolution keyed on non-deterministic arrival order instead of sequence-plus-timestamp tie-break. Debugging: streams/overlapping-segments.pcap replayed twice, diffed. Signal: I2/I7 replay-mismatch counter nonzero. Recovery: apply step 15's deterministic tie-break unconditionally.
  • Parser starvation. Manifestation: a parser never receives bytes despite steady traffic. Root cause: partial-delivery logic (step 6) waits for full-stream completion instead of delivering up to the first gap. Debugging: compare bytes-delivered-to-parser against bytes-buffered. Signal: buffered-bytes grows while delivered-bytes flatlines. Recovery: verify the contiguous-prefix delivery path fires on every insert, not just on gap-close.

15.7 Performance Concerns

  • Interval-tree traversal cost for SegmentTree under heavy out-of-order arrival; bound tree depth.
  • Fragmentation-reassembly overhead for small-fragment attacks; cap fragment count per IP datagram.
  • Copy amplification if delivered bytes are copied to the parser instead of referenced (P6).

15.8 Edge Cases

  • Sequence-number wraparound mid-stream (2^32 boundary).
  • Duplicated-ACK storms that don't carry new sequence data — must not perturb reassembly state.
  • Simultaneous close (both sides FIN near-concurrently) — state machine must resolve deterministically.

15.9 Failure Analysis

A corrupted stream (I2 violation) triggers flow isolation: the stream is torn down, the flow is quarantined per P10, and a ParserEvent with an error severity is emitted so downstream telemetry sees the quarantine rather than silent data loss. Blast radius: one flow. Detection: corruption detector (step 13). Recovery: parser reset on the next new flow reusing the tuple, never on the corrupted one.

15.10 Operational Notes

Metrics: stream.reassembly.gaps, stream.reassembly.overlaps, stream.buffer.occupancy_bytes. Trace span: stream.reassemble. Log fields: flow_id, gap_count, overlap_count. Deployment: no separate rollout — this phase ships inside the same pkt-runtime binary as Phase 2. Migration: TcpReassemblyBuffer is never persisted directly (rebuilt from WAL on recovery, P7), so no schema migration path is needed for this type.

16.6 Pitfalls

  • Parser state leaks. Manifestation: FlowContext.memory_bytes grows across many flows using the same protocol. Root cause: a decoder retains a reference into a prior flow's buffer past reset.   • Unbounded recursion. Manifestation: DNS parser hangs or stack-overflows on crafted input. Root cause: compression-pointer chase without a hop limit (RFC 1035 §5 violation).   • UTF-8 validation cost on HTTP header values; validate lazily, only fields the rule runtime reads.

  • Parser-dispatch branching cost at high protocol diversity; keep the dispatch table a flat array indexed by a small ParserId, not a hash lookup.

16.8 Edge Cases

  • Chunked-transfer-encoding anomalies: zero-length final chunk arriving split across feed calls.

  • TLS record fragmentation spanning more than one reassembled stream chunk.

16.9 Failure Analysis

Detection: panic hook increments parser.fault.count tagged by ParserId. Postmortem guidance: the fuzz corpus that triggered the fault is auto-saved and becomes a new named conformance fixture (step 13 feedback loop).

16.10 Operational Notes

Deployment: new parsers are additive (new ParserId variant, P8) and can be feature-gated independently (Phase-0 feature-gate registry). Rollback: disabling a parser via feature gate is a config change, not a redeploy.

  • Catastrophic regex behavior. Manifestation: rule compilation or evaluation time explodes on a crafted pattern. Debugging: dependency-graph cycle detector output. Signal: compiler rejects with a named cycle diagnostic. Recovery: reject at compile time, never at runtime.
  • Hot-reload inconsistency. Manifestation: in-flight evaluations see a mix of old and new rule versions. Root cause: swap is not atomic — some worker threads observe the pointer swap before others. Debugging: version-tag mismatch counter across concurrent evaluations. Signal: rule.version.mismatch nonzero during a reload window. Recovery: swap via a single atomic pointer (P1, I7), never field-by-field mutation.

17.7 Performance Concerns

  • Hyperscan compiled-DFA memory footprint versus the §4 rule-runtime ceiling (2 GB); track per ruleset-version memory and cap active-signature count accordingly.
  • Cache pressure from large per-rule state (temporal-window buffers) evaluated across many flows concurrently; keep window state flow-local, not global.
  • Branch misprediction in the clause-dispatch loop at high rule-count; keep the AST-to-evaluator compile step flatten clauses into a dispatch table, not a nested match tree.

17.8 Edge Cases

  • Overlapping signatures matching the same payload region — must produce one RuleMatch per rule, not a merged/ambiguous result.
  • Replay-ordering drift: events replayed out of their original relative order must still produce the documented (possibly different) but deterministic result — flagged, not silently accepted.
  • Parser-timing races: a ParserEvent arriving after its flow was already quarantined by §16 must be dropped, not evaluated against a stale FlowContext.

17.9 Failure Analysis

A rule crash (evaluator panic) quarantines only the affected ruleset version, not the whole rule runtime — other rulesets (e.g. a canary version running in shadow mode) continue. Detection: evaluator panic hook increments rule.crash.count tagged by rule ID. Recovery path: automatic rollback to the last-known-good ruleset version (step 15); operator is paged with the offending rule ID and the triggering event for forensic replay (P7).

17.10 Operational Notes

Metrics: rule.latency_p95, rule.match_rate, rule.dropped_evaluations, rule.budget_exceeded. Trace span: rule.evaluate. Log fields: rule_id, ruleset_version, flow_id. Deployment: ruleset distribution flows through pkt-control-api (§1), never a direct file write to a running worker. Rollback: ADR-15's rollback support is the primary rollback mechanism; no redeploy needed for a bad ruleset.

18. Phase 6 — Persistence & Replay

18.1 Objectives

  • Implement the WAL append engine and deterministic replay subsystem (P1, P7, ADR-07 replay format).
  • Implement segment rotation, checksum verification, and snapshot checkpointing (I4, I13).
  • Constraint introduced: WAL write amplification under 1.5× (§4); replay recovery under 15 min.

18.2 Detailed Implementation Steps

  1. Define the ReplayFrame format (§11) — frame_seq, segment_id, schema_version, checksum (ADR-07, Kleppmann 2017 ch. 3 log-structured storage lesson per §5).
  2. Implement the WAL append engine (wal.rs) — single-writer-per-segment, strictly ordered (I4).
  3. Add segment rotation: a segment closes at a configured size/time bound, a new one opens atomically.
  4. Add the compression pipeline (zstd) sized against the >2× archive-compression target (§4).
  5. Add the replay index (index.rs) mapping logical replay offsets to segment/byte offsets.
  6. Add snapshot checkpoints (checkpoint.rs) — periodic, internally consistent (I13).
  7. Add corruption detection: per-frame checksum verified on read, not just on write.
  8. Add checksum verification at segment-open time before any frame in that segment is trusted.
  9. Add the replay scheduler (scheduler.rs) supporting both deterministic-timing replay and fast-forward replay modes.
  10. Add time-dilation support: replay can compress or expand inter-event gaps for stress testing.
  11. Add deterministic timing mode: replay reproduces original inter-event deltas exactly (P1).
  12. Add replay assertions: the deterministic simulator (§7) hooks its per-invariant assertions into this replay path.
  13. Add storage telemetry: WAL lag, segment count, compression ratio (P9).
  14. Add retention enforcement: segments older than the retention window are pruned, never silently.
  15. Add snapshot recovery: on crash, load the last consistent checkpoint (I13) then replay WAL frames after it.
  16. Add replay seek support: jump to a logical offset without replaying every frame from the start.
  17. Add partial-replay mode: replay a bounded window (e.g. one flow's frames) for targeted forensic debugging.
  18. Add replay metrics: replay.throughput, replay.lag.
  19. Add replay-drift detection: live-vs-replay match-count divergence trips an alert (I7-adjacent).
  20. Add WAL recovery tooling (pkt-cli subcommand) for offline segment inspection and repair.

18.3 Deliverable

A deterministic replay subsystem: durable WAL append with bounded write amplification, crash recovery from the last checkpoint plus WAL replay within the RTO budget, and a replay scheduler that reproduces identical RuleMatch output from a recorded event corpus.

18.4 Acceptance Criteria

  • Replay reproduces identical matches: replay/reordered-events.bin replayed twice yields the same RuleMatch sequence (I7, P1).
  • WAL recovery validated: crash-inject during a sustained-write test recovers within the 5 min RTO (§4) and the 60 s replay-index-load budget.
  • Corruption handling verified: replay/corrupted-segment.bin is quarantined (not trusted) and recovery proceeds from the prior consistent checkpoint.
  • WAL write amplification measured under 1.5× on the sustained-ingest benchmark (§4, §28 M-series).

18.5 Conformance Fixtures

  • fixtures/replay/corrupted-segment.bin — checksum-mismatched segment, expects quarantine not crash.
  • fixtures/replay/reordered-events.bin — replay-parity regression case.
  • fixtures/replay/partial-checkpoint.bin — checkpoint torn mid-write, expects fallback to prior checkpoint (I13).
  • fixtures/replay/mixed-version-segments.bin — segments spanning two schema versions, expects correct version-dispatched reads (I8).

18.6 Pitfalls

  • Replay timing drift. Manifestation: deterministic-timing replay diverges from recorded inter-event gaps. Root cause: the replay scheduler's clock source drifts under system load instead of following a virtual clock. Debugging: compare configured vs. observed inter-event deltas on replay/reordered-events.bin. Signal: drift-detection counter (step 19) nonzero. Recovery: drive deterministic-timing mode from a virtual clock, never wall-clock (ADR-21).
  • WAL corruption propagation. Manifestation: one corrupted segment blocks replay of all subsequent segments. Root cause: the replay index doesn't independently validate segment boundaries before sequential replay. Debugging: replay/corrupted-segment.bin inserted mid- sequence. Signal: replay halts entirely instead of quarantining one segment. Recovery: index- level segment validation (step 8) lets replay skip a quarantined segment and continue from the next valid one, flagging the gap.
  • Checkpoint inconsistency. Manifestation: recovery loads a checkpoint referencing a flow that was actually evicted before the checkpoint's logical timestamp (I13 violation). Root cause: checkpoint write isn't atomic with the flow-eviction path. Debugging: replay/partial-checkpoint.bin recovery trace. Signal: checkpoint-consistency-hash mismatch. Recovery: fall back to the prior checkpoint plus WAL replay (step 15).

18.7 Performance Concerns

  • fsync amplification if every frame syncs individually; batch fsync per segment-rotation boundary or a bounded time window, trading a small RPO increase (§4) for throughput.
  • Compression overhead on the hot append path; run zstd compression on a background task, never inline with the append (P14-adjacent pattern reused here).
  • Replay IO contention when replay and live ingest share the same storage device; separate volumes or explicit IO priority classes.

18.8 Edge Cases

  • Truncated WAL segments from a crash mid-write — must be detected and the partial tail discarded, not replayed as if complete.
  • Mixed-version snapshots during a rolling upgrade — the reader must dispatch on schema_version per record, not assume a uniform version across the file.
  • Clock skew between the writer and a downstream replay consumer — deterministic-timing mode must be self-contained, not dependent on wall-clock agreement.

18.9 Failure Analysis

Storage corruption triggers segment quarantine: the corrupted segment is isolated, replay continues from the next valid segment, and the quarantined segment is preserved (not deleted) for forensic analysis. Detection: per-frame checksum (step 7) and segment-open verification (step 8). Blast radius: bounded to the frames within the corrupted segment; checkpoint-based recovery bounds data loss to the RPO budget (§4).

18.10 Operational Notes

Metrics: wal.lag, wal.corruption_count, replay.throughput, replay.drift. Trace span: replay.scheduler.tick. Log fields: segment_id, frame_seq, schema_version. Deployment: WAL volumes are provisioned separately from the container's ephemeral storage. Migration: a schema_version bump ships with a reader that supports both the new and the prior two versions (I8) before any writer emits the new version.

19.6 Pitfalls

  • Telemetry storms. Manifestation: a burst of alerts overwhelms the exporter and the operator. Root cause: no rate-limiting or de-duplication on alert emission during a sustained incident. Debugging: alert-emission-rate trend during fixtures/telemetry/exporter-outage.json replay. Signal: alert volume exceeds a sane per-minute cap. Recovery: de-duplicate by alert class plus affected subsystem within a rolling window.
  • Recursive logging. Manifestation: the logging subsystem itself generates log lines about logging failures, looping. Root cause: the structured-logger's own error path logs through the same logger. Debugging: log-volume spike with no corresponding traffic increase. Signal: log lines tagged subsystem=telemetry dominate the stream. Recovery: the logger's internal error path writes to stderr directly, bypassing itself.
  • Metrics cardinality explosion. Manifestation: the metrics backend rejects writes or falls over. Root cause: a label (e.g. raw flow ID) is attached to a per-flow metric instead of being bucketed/sampled (P9 cardinality bound). Debugging: fixtures/telemetry/cardinality-attack.json. Signal: cardinality-guard alert (§19.2 step 6) fires. Recovery: cap label dimensionality at the metric-registration point (Phase 0 registry).

19.7 Performance Concerns

  • Exporter contention if metrics and traces share one export queue; separate queues per telemetry kind (P14).
  • Trace-sampling overhead at 100% sample rate under high match-rate rulesets; default to probabilistic sampling with a guaranteed-sample override for any flow that produced a RuleMatch.
  • Logging amplification: structured-log serialization cost per event; batch-serialize on the async telemetry task, never inline on the hot path.

19.8 Edge Cases

  • Exporter outages (OTel collector unreachable) — async buffering (P14) up to a bounded queue, then bounded drop with a telemetry.dropped counter, never blocking.
  • Malformed telemetry payloads generated by a buggy subsystem — the exporter validates before sending, quarantining the malformed envelope rather than corrupting the export stream.
  • Partial spans (a trace missing its terminal span because a worker crashed mid-request) — the tracing backend must show it as incomplete, not silently drop it.

19.9 Failure Analysis

Telemetry failures degrade asynchronously and never touch the data plane (P14): an exporter outage is absorbed by the bounded telemetry queue up to its cap, then telemetry (not packets) is dropped with a visible counter. Detection: exporter health check plus telemetry.dropped counter. Blast radius: observability gap during the outage window, no packet-processing impact. Recovery: async reconnect/backoff to the exporter; buffered-but-not-yet-dropped telemetry flushes on reconnect.

19.10 Operational Notes

Metrics: telemetry.exported, telemetry.dropped, telemetry.queue.depth. Trace span: telemetry.export. Log fields: exporter, envelope_kind. Mandatory dashboards (source-verbatim naming): packet throughput, flow counts, replay health, parser failures. Deployment: exporter endpoints are config-driven (pkt-control-api), rotatable without a restart.

20.1 Objectives

  1. Implement the AF_XDP socket abstraction (af_xdp.rs) with fill/completion/RX/TX ring management (Karlsson & Töpel 2018, applied per §5).

  5. Add the PacketSource implementation unifying AF_XDP behind the same trait as AF_PACKET/replay (§13.2 step 20 reuse).

  7. Add zero-copy frame recycling: completed TX/RX frames return to the fill ring without a copy (DPDK mempool lesson per §5).

  12. Add AF_XDP-specific telemetry: fill-ring/completion-ring occupancy, UMEM exhaustion counter.

  14. Add conformance fixtures replaying the same traffic through AF_PACKET and AF_XDP paths, asserting identical downstream output.
  15. Add capability detection at startup: kernel version, driver XDP mode surfaced to the operator before attach is attempted.
  16. Add an eBPF verifier-safety review checklist as a CI gate (bounded loops, verifier-passable map access patterns).
  17. Add an AF_XDP-path benchmark suite comparing pps/latency against the Phase-1 AF_PACKET baseline.
  18. Add graceful AF_XDP detach on shutdown, returning the NIC to a clean state for AF_PACKET fallback.
  19. Add a rollback path: an operator can force AF_PACKET-only mode via feature gate without a binary change.
  20. Add hardware-offload-aware checksum handling for NICs where AF_XDP bypasses normal checksum offload.

20.3 Deliverable

An AF_XDP fast-path ingress option, behind the same PacketSource abstraction as Phase 1, with automatic AF_PACKET fallback, full NUMA-aware worker placement across the entire pipeline, and telemetry proving zero-copy frame recycling is functioning.

20.4 Acceptance Criteria

  • AF_XDP path sustains the full 8,000,000 pps target (§4) on supported NICs, versus the 2,000,000 pps AF_PACKET baseline validated in Phase 1.
  • Fallback validated: disabling AF_XDP support (simulated unsupported driver) falls back to AF_PACKET within one restart cycle, logged, no operator intervention required.
  • Cross-node-transfer counter (I10) reads zero on a correctly NUMA-pinned deployment under the full-pipeline conformance fixture.

20.5 Conformance Fixtures

  • fixtures/xdp/af-xdp-vs-af-packet-parity.pcap — identical traffic through both paths, expects identical downstream output.
  • fixtures/xdp/driver-unsupported-fallback.json — simulated attach failure, expects logged fallback.
  • fixtures/xdp/numa-crossnode-audit.json — full-pipeline placement audit fixture.
  • fixtures/xdp/umem-exhaustion-pressure.pcap — sustained load near the UMEM ceiling.

20.6 Pitfalls

  • Busy-poll starvation. Manifestation: supervisor health checks stall under AF_XDP busy-poll mode. Root cause: the busy-poll loop monopolizes its core, starving the cooperative scheduler (xdp-tools lesson per §5). Debugging: health-check-latency trend under sustained AF_XDP load. Signal: health-check timeout counter rises. Recovery: default to interrupt-driven mode (step 13); busy-poll is opt-in with an explicit dedicated-core reservation.
  • UMEM frame leak. Manifestation: fill-ring occupancy trends toward zero under sustained traffic. Root cause: a completed frame isn't returned to the fill ring on an error path (P4 violation in the AF_XDP-specific code path). Debugging: fill-ring occupancy versus completion- ring rate. Signal: UMEM-exhaustion counter (step 12) climbs. Recovery: audit every AF_XDP error path for frame-return completeness; add a leak fixture.
  • Silent capability downgrade. Manifestation: operator believes AF_XDP is active but traffic is actually flowing through AF_PACKET fallback at 4× lower throughput. Root cause: fallback logging (step 6) was rate-limited into invisibility during a telemetry storm (§19.6 lesson reapplied). Debugging: capability-mode metric (step 15) reviewed directly, not inferred from logs. Recovery: expose current active path as a persistent gauge, not just a one-time log line.

20.7 Performance Concerns

  • eBPF pre-filter verifier constraints limit filter complexity; keep the in-kernel filter coarse, push fine-grained classification to userspace pkt-flow.
  • UMEM frame-pool sizing versus TLB pressure on large frame counts; size frames to hugepages where available.
  • Cross-node memory-pool partitioning (step 10) adds a startup-time allocation cost; amortized once at cold start, within the 10 s budget (§4).

20.8 Edge Cases

  • Driver reports native XDP support but silently falls back to generic (SKB-copy) mode under the hood — must be detected (step 15) and telemetered distinctly from true zero-copy mode.
  • NIC hot-unplug/replug during operation — AF_XDP socket must detach cleanly and the fallback path must engage without a process restart.
  • Mixed-mode fleet during rollout: some nodes on AF_XDP, some on AF_PACKET fallback — downstream aggregation must not assume uniform ingress path across the fleet.

20.9 Failure Analysis

An AF_XDP attach failure or runtime fault triggers immediate, logged fallback to AF_PACKET (step 6) — never a crash, never a silent throughput cliff. Detection: attach-failure exception path, UMEM-exhaustion counter, fill-ring stall detector. Blast radius: contained to the affected NIC/ NUMA node; other nodes in the fleet are unaffected. Operator visibility: active-path gauge (step 15) plus a fallback-event log with the specific failure reason.

20.10 Operational Notes

Metrics: xdp.fillring.occupancy, xdp.completionring.rate, xdp.umem.exhausted, capture.active_path (gauge: af_xdp | af_packet). Trace span: capture.xdp.rx.batch. Log fields: xdp_mode, fallback_reason. Deployment: AF_XDP requires a driver capability check baked into the DaemonSet node-affinity rules from Phase 1. Rollback: feature-gate to AF_PACKET-only, config change only.

Detection: per-tenant and fleet-wide SLO dashboards (step 18). Postmortem guidance: the version-inventory audit (step 19) plus per-tenant traces reconstruct exactly which tenants were on which version at the regression's onset.

24. Operational Readiness

Metrics strategy. Seven metric namespaces — ingress, flow, stream, parser, rule, replay, telemetry/runtime — each registered once at Phase 0 (§12.2 step 11) so cardinality is bounded from the start (P9). Every metric named in §12–§21's Operational Notes subsections must exist before that phase is considered exit-ready.

Tracing strategy. Every packet path is sampled probabilistically by default; any flow that produces a RuleMatch is guaranteed-sampled regardless of the probabilistic rate (§19.7), so a detection is always traceable end-to-end even under high-volume sampling.

Logging. Structured JSON logs are mandatory across every crate (ADR-09); the mandatory field set (subsystem, flow_id where applicable, timestamp_ns) is enforced by a CI lint, not convention.

Alerting philosophy. Alert on saturation (I5 queue bounds), correctness drift (I7 replay mismatch), replay mismatch (FM-5), and parser-crash rate (FM-3) — never on raw counters without a rate-of-change or threshold context, to avoid the telemetry-storm pitfall (§19.6).

Canary strategy. Deployments progress through four gates: (1) replay validation against a recorded corpus, (2) passive-mirror validation on live but non-decision traffic, (3) limited inline rollout to one canary tenant (§21.2 step 13), (4) fleet-wide production enablement gated by the go-live checklist (§21.2 step 20).

Runbooks. docs/runbooks/rx-saturation.md, docs/runbooks/flow-exhaustion.md, docs/runbooks/wal-corruption.md, and docs/runbooks/replay-drift.md map directly to FM-1, FM-2, FM-4, and FM-5 above — one runbook per failure class that has an established manual-recovery path.

25. Compatibility & Versioning

Wire compatibility. Telemetry schemas (TelemetryEnvelope, §11) are append-only (P8); a field is never removed or repurposed across any release. Consumers built against an older schema must continue to parse newer envelopes, ignoring unknown fields.

Storage compatibility. Persisted records (ReplayFrame, flow-summary rows in pkt-storage) remain backward-readable for two major versions (I8). A reader carries a schema_version-dispatch table (P15) rather than assuming a single layout.

Semantic versioning. MAJOR: storage or wire-format breaking change. MINOR: additive feature (new ParserId, new metric, new rule-AST clause type — all additive per P8). PATCH: behavior- preserving fixes only, never a schema change.

Rolling-upgrade compatibility. §21's version-skew window requires that a MINOR-version worker can always read a MAJOR-1-version worker's WAL frames and vice versa within the two-version window (I8); the schema-compatibility gate (§21.2 step 8) is a hard build/deploy block, not an advisory warning (FM-10 root cause if this regresses).

API compatibility. pkt-control-api's RBAC and rule-distribution surface follow the same additive-only discipline; a rule-DSL clause type is never removed, only deprecated with a multi-release warning window before removal in the next MAJOR.

26. Testing & Verification Strategy

Unit testing. Mandatory for parsers (§16), flow hashing (§14), and stream reconstruction (§15) — each crate's tests/*_conformance.rs binds directly to the named fixtures in that phase's N.5 subsection.

Integration testing. Covers replay pipelines (§18), telemetry exporters (§19), and the rule runtime (§17) end-to-end through pkt-conformance, which runs the deterministic simulator described in §7's closing paragraph — one assertion per invariant, replayed against a fixed fixture corpus under a mocked clock and mocked NUMA topology.

Fuzzing. Targets protocol parsers (§16.2 step 13), replay loaders (§18), and the rule compiler (§17) via cargo-fuzz (ADR-14). A 24-hour fuzz run with zero crashes and zero unbounded-memory findings is a Phase-4 exit criterion (§16.4).

Chaos testing. Injects packet loss, queue saturation, and replay corruption via pkt-conformance's fault-injection mode, validating that FM-1 through FM-11 (§23) each recover via their documented auto-recovery path, not just their manual-recovery path.

Replay-determinism gate. A dedicated CI stage (conformance.yml) replays a fixed event corpus against a fixed ruleset version twice and diffs RuleMatch output — any diff blocks the merge (I7). This is the single most load-bearing test in the suite, since P1 and P7 both depend on it holding.

Conformance harness. pkt-conformance is the executable form of this document's fixture tables — every fixtures/<area>/<name> referenced in §12–§21's N.5 subsections is a real file this harness loads and asserts against.

27. Build & Release Engineering

Reproducible builds. Every release artifact is deterministic (cargo --locked, stamped build metadata, ADR-20), signed, and version-stamped with the git SHA embedded at Phase 0 (§12.2 step 19).

Release channels. Nightly (every merge to main), stable (weekly cut, soak-tested), LTS (quarterly, backport-only) — ADR-19. Rolling upgrades (§21) always move fleet-wide only through stable or LTS, never nightly.

Supply-chain verification. SBOM generation via Syft is mandatory in the release pipeline (ADR-18); cargo-audit runs on every CI build (ADR-03), blocking merge on a known-vulnerable dependency, not just warning.

Packaging. OCI container images are the primary artifact (ADR-16), built via the pinned Dockerfile, tagged with the same build metadata as the binary itself.

CI pipeline stages. ci.yml (build/clippy/test/doc-lint), benchmark.yml (Criterion regression gate against §28's M-series targets), fuzz.yml (ADR-14 fuzz corpus run), conformance.yml (replay-determinism gate), security-audit.yml (SBOM + cargo-audit) — five independent gates, all required green before merge to main.

Rollback. Every release is rollback-capable to the immediately prior stable tag within the same RTO budget (§4) used for crash recovery, since a bad release is operationally treated as a correctness failure, not a separate incident class.

Benchmark strategy. pkt-bench (Criterion, ADR-12) covers packet ingress, flow lookup, stream reassembly, parser latency, and regex scanning — one benchmark suite per phase's N.7 Performance Concerns subsection, run against the fixtures in benchmarks/*.toml.

Profiling workflow. perf for CPU sampling, flamegraphs for call-stack visualization, heap profiling for allocator-churn hunting (P6 violations), lock profiling for contention hotspots (Gregg 2020, applied per §5) — all exposed via the profiling endpoints built in §19.2 steps 12–14.

29. Scalability Analysis

Horizontal scaling. Traffic partitions by RSS hash (intra-host, §13/§20), VLAN (inter-tenant boundary hint, §21), and tenant (explicit sub-budget carving, §21.2 step 2). Each partitioning dimension maps to a different scaling axis: RSS scales cores within a host, VLAN/tenant scales isolation guarantees, neither alone scales host count — that remains the deferred distributed- collector work (PhaseDeferred("§21"), §35).

Bottlenecks. Regex (Hyperscan DFA) memory is the first ceiling to hit as signature count grows past the §4 2 GB budget (§32 C5) — mitigated short-term by signature pruning, long-term by the deferred GPU-regex path (PhaseDeferred("§17")). Flow-table contention is the second ceiling, bounded by sharding (ADR-08) but re-emerging under adversarial hash-flooding (§14.6). Replay IO bandwidth is the third ceiling when replay and live ingest share a storage device (§18.7).

Metadata scaling. Metadata retention (pkt-storage) must support tiered archival: hot tier (RocksDB, recent flow summaries and alerts) feeding a cold tier (compressed PCAP/metadata archive, §4's >2× compression target) — the tiering boundary itself is a capacity-planning knob exposed via the per-tenant utilization telemetry built in §21.2 step 12.

Multi-tenant scaling ceiling. §21's per-tenant sub-budgets subdivide the global §4 ceilings linearly; the practical tenant-count ceiling is therefore flow_table_ceiling ÷ min_viable_tenant_ budget, which is a capacity-planning input to the go-live checklist (§21.2 step 20), not a fixed constant — it must be recomputed whenever §4's global ceilings change.

30. Mental Models & First Principles

  • MM1 — Ownership Is a Compile-Time Fact, Not a Runtime Convention. Explicit single-owner semantics (P4) let the compiler catch aliasing bugs before they reach production; predicts that any design where two subsystems "just agree" not to touch shared state will eventually be violated under load; the bug class it prevents is double-free/use-after-free-style races; applies in §14.
  • MM2 — Backpressure Converts Overload Into a Visible Signal. Bounding every queue makes overload observable (a saturated gauge) instead of a silent memory-growth curve; predicts that any unbounded queue in a design is a future incident, not a maybe; the bug class it prevents is an OOM-kill during a traffic spike; applies in §13.
  • MM3 — Determinism Is What Makes Postmortems Possible. If the same input can produce two different outputs, causality cannot be debugged backward from symptom to cause; predicts that any hidden nondeterminism (thread scheduling order, wall-clock reads) eventually surfaces as an unreproducible bug report; the bug class it prevents is "works on replay, didn't happen live"; applies in §18.
  • MM4 — Fault-Isolation Granularity Determines Blast Radius. The granularity at which faults are isolated (per-flow, not per-process) determines how much of the system one bad input can take down; predicts an adversary will eventually probe for exactly that boundary; the bug class it prevents is one malformed packet crashing the whole sensor; applies in §16.
  • MM5 — NUMA Locality Debt Compounds Silently. A single misplaced allocation early in the pipeline creates cross-node traffic that compounds at every downstream stage touching the same memory; predicts gradual p99 degradation as flow count grows, not a sudden cliff; the bug class it prevents is "it got slower over weeks with no code change" incidents; applies in §20.
  • MM6 — Every Constraint-Table Number Is a Promise to Another Section. §4's numbers are load-bearing citations, not documentation flavor — §28 and §32 must derive from them, not restate them; predicts that silent constraint drift between sections is a sign the design itself has drifted; the bug class it prevents is a capacity model that "passes review" but doesn't match the actual system; applies in §32.
  • MM7 — Hot-Reload Safety Is an Atomicity Problem, Not a Locking Problem. Swapping a whole versioned object atomically is simpler and safer than locking individual fields during a transition; predicts that any partial-update reload design eventually observes a torn read; the bug class it prevents is rule evaluation against half-old, half-new state; applies in §17.
  • MM8 — An Unrepresentative Canary Is Worse Than No Canary. A canary only catches regressions along the dimensions its traffic profile actually exercises; predicts that a rollout which "passed canary" can still regress fleet-wide on an untested traffic shape; the bug class it prevents is a canary-blind-spot production incident; applies in §21.

32. Back-of-Envelope Capacity Model

  • C1 — Packet Rate Ceiling. 10,000,000,000 bits/s ÷ (8 bits/byte × 104 B avg wire frame) = 12,019,230 pps theoretical ceiling; engineering target fixed at 8,000,000 pps (§4) = 66% of theoretical, leaving headroom for larger average frame sizes.
  • C2 — Flow Table Memory. 5,000,000 flows × 1,600 B/FlowContext (§11) = 8,000,000,000 B = 8 GB, exactly the §4 flow-table ceiling.
  • C3 — Reassembly Buffer Memory. 1,000,000 concurrent TCP streams × 16,384 B avg out-of-order window = 16,384,000,000 B ≈ 16 GB, matching the §4 reassembly-buffer ceiling.
  • C4 — RX Ring Memory. 8 NUMA-pinned RX rings × 512 MB UMEM region = 4,096 MB = 4 GB, matching the §4 RX-ring ceiling.
  • C5 — Rule Runtime Memory. 2,000 active signatures × ~1 MB average compiled Hyperscan DFA fragment = 2,000 MB = 2 GB, matching the §4 rule-runtime ceiling.
  • C6 — WAL Write Amplification. 512 B avg logical record + 32 B frame header + 4 B checksum = 548 B on-disk ÷ 512 B logical = 1.07×, inside the 1.5× §4 ceiling.
  • C7 — Replay Recovery Volume. 15 min RTO (§4) × 60 s/min × 8,000,000 pps sustained replay rate = 7,200,000,000 packets replayable inside the recovery budget.
  • C8 — Stream-to-Flow Ratio. 1,000,000 reassembly-concurrent streams ÷ 5,000,000 concurrent flows = 20%, matching the assumed TCP-with-reassembly fraction used to derive C3.
  • C9 — FD Budget Allocation. 65,536 max FDs (§4) − 4,096 replay reserve − 2,048 telemetry reserve = 59,392 FDs available for RX sockets and general runtime use.
  • C10 — Availability Downtime Budget. (1 − 0.9995) × 365.25 days × 24 h/day = 4.38 h/year permitted downtime at the 99.95% §4 availability target.

33. Hard Questions (Self-Examination)

  • Q1. If AF_XDP (§20) sustains 8,000,000 pps but the rule runtime (§17) budget is calibrated against the §4 p95 of 500 µs at that same rate, what happens to tail latency when a hot-reload (§17.4) coincides with a burst at the §4 20 Gbps ceiling — does the reload's atomic swap or the burst's queue pressure dominate the observed p99?
  • Q2. §14's eviction scoring and §21's tenant-aware eviction scoring both compete for the same emergency-eviction pass under §4's 8 GB flow-table ceiling — during a fleet mid-rollout (§21.9) with mixed old/new eviction-scoring code, which version's scoring function actually runs, and does I9 still hold?
  • Q3. §15's deterministic overlap tie-break depends on I3's monotonic-timestamp invariant, and §20's AF_XDP path plus §13's AF_PACKET fallback assign timestamps at different pipeline stages — can two frames of the same stream be timestamped by different paths during a §20.8 mixed-mode window, and does §15's tie-break remain deterministic?
  • Q4. §18's WAL is the source of truth for §17's replay-parity claim (I7), but §21's tenant-scoped replay (step 17) replays only a subset of frames — does replaying a tenant-scoped subset still satisfy I7's determinism claim if a threshold rule spans tenants?
  • Q5. §16's parser-timeout watchdog (step 15) force-resets a stuck parser, and §17.8 notes a ParserEvent arriving after its flow was quarantined must be dropped — if the watchdog fires mid-evaluation, does §17's execution-budget accounting (I12) get charged for work that will be discarded anyway?
  • Q6. §4 sets NUMA cross-node hot-path transfer at zero, but §21's per-tenant sub-budgets (step 2) are carved per-tenant, not per-node — could a tenant whose traffic lands disproportionately on one NUMA node exhaust that node's local slice while the global per-tenant budget still has headroom elsewhere, and would I10 detect this?
  • Q7. §19's telemetry queue is allowed to drop telemetry under backpressure (P14), but §22 treats a cardinality attack (T7) and an exporter outage (T8) as distinct threats — if both occur simultaneously, does the cardinality guard or the bounded-queue drop trip first, and does the resulting telemetry gap make T7's detection itself invisible?
  • Q8. §32's C7 sizes replay recovery volume against the sustained 8,000,000 pps rate from §4/C1, but §20 only reaches that rate on AF_XDP — during a fleet-wide fallback to AF_PACKET (capped at 2,000,000 pps per §13.4), does the §4 15-minute replay-recovery RTO still hold?
  • Q9. §17's rule-dependency-graph cycle detector (step 19) operates per ruleset, but §21 introduces per-tenant rule isolation (step 3) — if two tenants' rulesets both reference the same global (non-tenant-scoped) counter by mistake, does the cycle detector see the cross-tenant edge, or does isolation hide the bug until I7 replay-parity fails?
  • Q10. §13's malformed-frame rejection happens before flow classification, and §22 lists both T1 (malformed injection) and T11 (fragmentation exhaustion) at the same ingress stage — does rejecting a malformed frame early enough to satisfy T1 also correctly account it against T11's fragment-count cap, or can an attacker split one oversized malformed frame into fragments that each individually pass the T1 check?
  • Q11. §18's segment-quarantine recovery (FM-4) skips a corrupted segment and continues from the next valid one, but §15's stream checkpoints (step 18) may reference state written inside the quarantined segment — does skipping the segment violate I13's checkpoint-consistency invariant for any stream whose checkpoint falls inside the gap?
  • Q12. §30's MM7 and §21's rolling-upgrade coordination (step 6) both rely on atomic pointer swaps at different layers (ruleset vs. worker binary) — during a rolling upgrade that coincides with a §17 rule hot-reload, can the two swaps interleave such that a worker on the new binary evaluates an old ruleset pointer assuming the old binary's ExecutionBudget representation?
  • Q13. §28's M10 target and §29's RSS-hash scaling analysis both assume RSS distributes load evenly, but §14's hash-flooding pitfall shows an attacker can defeat this at the flow-table layer — if an attacker defeats RSS at the NIC level before §14 even sees the packet, does §20's per-NUMA UMEM sizing (C4) still hold, or does one node's UMEM region exhaust while others idle?
  • Q14. §26's replay-determinism CI gate and §17's Hyperscan hot-reload run on the same pipeline (§27) — if a ruleset change alters Hyperscan's compiled DFA and the determinism gate fails, how does an engineer distinguish "the ruleset is genuinely non-deterministic" from "Hyperscan produced a differently-ordered but equally valid DFA" without violating I7's black-box determinism promise?
  • Q15. §4's RPO of under 1 second is bounded by the WAL fsync interval, but §18's segment-rotation batching recommendation (§18.7) — if rotation is time-bounded at several seconds under low traffic, does the actual RPO silently drift past §4's stated budget, and would §28's M-series targets catch that gap?
  • Q16. §20's automatic AF_XDP-to-AF_PACKET fallback is described as never silent, but §20's own pitfall catalog (silent capability downgrade) documents exactly that failure mode occurring in practice — does §20's acceptance criteria actually test the telemetry visibility of a fallback event the way §19's observability platform would require, or only its functional correctness?
  • Q17. §31 favorably compares this blueprint's parser-isolation boundary (I6) against VPP's graph-node model, but §20's eBPF pre-filter runs before userspace flow classification, closer to VPP's in-kernel-graph philosophy than to this blueprint's per-flow philosophy — does the §20 pre-filter quietly reintroduce the fault-granularity mismatch §34 rejects VPP for?
  • Q18. §35 registers PhaseDeferred("§21") for distributed-collector correlation, but §21's correlation-hook interface (step 9) already ships to keep the wire format stable — if that wire format later proves wrong once the deferred feature is built, does the append-only compatibility guarantee (P8, I8) force the engine to carry a dead field forever, or is an interface-only stub exempt from P8?

Alt A — Kernel-Resident Detection (eBPF/XDP-Only Pipeline)

+--------------------------------------------------------+
|                    Kernel Space                        |
|  NIC -> XDP program -> eBPF maps (flow/counter state)  |
|                     -> verdict (PASS/DROP/REDIRECT)     |
+--------------------------------------------------------+
                         |
                         v (only aggregated counters/events)
+--------------------------------------------------------+
|                   Userspace (thin)                     |
|            Map reader -> metrics exporter               |
+--------------------------------------------------------+

Regime where it wins: pure L3/L4 flow accounting and DDoS mitigation at line rate with no L7 semantics required — a real system embodying this is Cilium (eBPF-based networking/ observability dataplane). Rejected here because the eBPF verifier's bounded-loop and bounded-map constraints cannot host arbitrarily deep TCP reassembly (I2) or incremental multi-protocol parser state machines (I6) — the moment L7 decode is required, the kernel-resident model runs out of room, forcing a userspace hop anyway, which this blueprint's architecture (§3) provides natively.

Alt B — DPDK-Native Full Userspace Vector Pipeline

+---------------------------------------------------------+
|         DPDK poll-mode driver, run-to-completion         |
|  RX burst -> [classify node] -> [protocol node] ->       |
|              [detect node] -> [TX/drop node]              |
|  (fixed graph, vectorized across a packet burst)          |
+---------------------------------------------------------+

Regime where it wins: pure packet forwarding/NAT/routing at line rate with lightweight per-packet classification and no deep stateful inspection — a real system embodying this is VPP (fd.io). Rejected here (§31) because batch/vector processing conflates fault-isolation granularity with processing-batch granularity: a malformed packet's fault blast radius becomes the whole batch, not one flow, violating I6's per-flow isolation requirement that this domain's adversarial-input threat model (§22) demands.

Alt C — Embedded Scripting Rule Runtime

+---------------------------------------------------------+
|   ParserEvent stream -> Scripting VM (Turing-complete)   |
|         -> analyst-authored event handlers                |
|         -> arbitrary correlation state, arbitrary I/O      |
+---------------------------------------------------------+

Regime where it wins: research/forensic environments where analysts need arbitrary custom correlation logic and expressiveness matters more than a provable cost bound — a real system embodying this is Zeek. Rejected here because it violates I12 (bounded execution budget) and I7 (deterministic replay) as hard invariants rather than soft goals: a Turing-complete rule runtime cannot statically prove its own worst-case cost, which is unacceptable for the inline-bridge deployment mode (§1) where a stalled rule blocks live traffic.

36. Glossary

  • Flow — bidirectional network tuple (FlowKey) tracked as one unit of state.
  • FlowKey — canonicalized 6-tuple (src/dst IP, src/dst port, protocol, VLAN) identifying a flow.
  • FlowContext — the mutable per-flow state: parser state, stream buffer, counters, timestamps.
  • RX Ring — packet receive queue, mmap-backed for AF_PACKET or UMEM-backed for AF_XDP.
  • WAL — write-ahead log; the durability boundary for replay and crash recovery.
  • Replay Drift — mismatch between live execution and replayed execution over the same input.
  • ParserEvent — normalized decode artifact emitted by a protocol parser.
  • Flow Eviction — forced removal of a flow's state, idle-timeout- or memory-pressure-driven.
  • NUMA — non-uniform memory access; cross-node memory reads carry a latency penalty.
  • RSS — receive-side scaling; NIC-level hash-based distribution of packets across RX queues.
  • AF_XDP — Linux high-performance zero-copy packet-socket interface.
  • AF_PACKET — Linux baseline raw-packet socket interface, the Phase-1 ingress path.
  • Span Port — switch port configured to mirror traffic for passive monitoring.
  • TAP — passive traffic-copy device, physically splits the signal for capture.
  • Stream Gap — missing byte range in a TCP reassembly buffer, awaiting retransmission.
  • Parser Isolation — the guarantee that one parser's fault cannot affect another flow's parser.
  • Queue Pressure — a bounded queue approaching, but not yet at, its saturation bound.
  • Hot Path — the latency-sensitive execution path from RX through rule evaluation.
  • Backpressure — upstream throttling signaled by a downstream stage's bounded queue.
  • Flow Table — the sharded registry of active FlowContext entries.
  • Segment Overlap — conflicting TCP payload regions covering the same sequence range.
  • Snapshot — a persisted, internally-consistent runtime checkpoint (I13).
  • Cardinality Explosion — unbounded growth in metric label-value combinations.
  • RuleMatch — a durable record of a successful detection produced by the rule runtime.
  • ExecutionBudget — the compile-time-bounded cost ceiling for one rule's evaluation (I12).
  • TelemetryEnvelope — the transport-neutral wrapper for a metrics/trace/log payload.
  • ReplayFrame — one durable, checksummed, versioned WAL record.
  • WorkerHandle — the supervisor's lifecycle handle for one managed worker thread.
  • ADR — Architectural Decision Record; a locked technology or design choice with rationale.
  • Invariant — a property the system must never violate, with a named enforcement point (§7).
  • Crash-Only Semantics — the discipline that workers never self-heal, only restart (P3).
  • UMEM — the AF_XDP user-memory region backing fill/completion/RX/TX rings.
  • eBPF — extended Berkeley Packet Filter; verified in-kernel bytecode used for the pre-filter.
  • DFA — deterministic finite automaton; Hyperscan's compiled multi-pattern match structure.
  • Fsync — the syscall that forces a write to durable storage before returning.
  • Segment Rotation — closing one WAL segment and opening a new one at a size/time bound.
  • Checkpoint — a periodic, internally consistent snapshot used to bound replay recovery time.
  • RTO — Recovery Time Objective; the maximum acceptable time to restore service after a fault.
  • RPO — Recovery Point Objective; the maximum acceptable data-loss window on failure.
  • SLO — Service Level Objective; an operator-facing latency/throughput/availability target.
  • Canary Rollout — a staged deployment to a small traffic subset before fleet-wide promotion.
  • Schema Version — the explicit version tag carried by every persisted record (P15).
  • Tenant Sub-Budget — a per-tenant carve-out of a global resource ceiling (§21).
  • Cross-Node Transfer — a hot-path memory access crossing a NUMA-node boundary (I10 violation).
  • Timeout Wheel — an O(1)-amortized data structure for scheduling flow/stream expiry.
  • Emergency Eviction — an out-of-schedule eviction pass triggered by memory-pressure crossing a critical threshold.
