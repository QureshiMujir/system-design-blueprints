Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does a single-token ring need ~150 vnodes to match the balance HRW gets for free, and what is the cost you pay for that match? (§8.3 vnode variance + §8.6 HRW argmax; ADR-09 vs P9.)
  2. Adding the (N+1)-th node moves at least K/(N+1) keys by pigeonhole. The ring moves ~K/N. Reconcile these two numbers and explain why a measured fraction_moved of 0.0 on an add is a bug, not a triumph. (§8.5 disruption math + INV-2; FM-2 over/under-migration.)
  3. A client computes a different owner for the same key than its peer. Enumerate every place determinism can break, from hash seed to BTreeMap construction, and state the telemetry that isolates which one failed. (INV-1 + FM-3; Operational Readiness ring_version/hash_seed metrics.)
  4. BoundedRing with c=1.0 gives perfect balance. Explain precisely why you would almost never deploy it, and what failure mode appears under a burst. (§8.10 + INV-5; FM-5 forwarding storm; MM5.)
  5. Why is jump hash unusable for a cluster where nodes fail arbitrarily, yet ideal for a CDN shard tier that only ever scales out? Walk through what removing bucket 3 of 10 does to the key map. (§8.8 ordinal constraint + INV-7; FM-6; P9.)
  6. Maglev fills its table to ±1 slot per backend only when M is prime and skip≠0. Explain the number-theoretic reason, and what observable symptom appears if someone sets M=65536. (§8.9 permutation fill + INV-8; T7 collision; ADR-18.)
  7. A reader holds an arc-swap snapshot across a slow call while 50 membership changes occur. Is its locate result wrong? Is it stale? What is the memory consequence, and how is each addressed? (P6 + INV-10; Phase 12 §24 stale-Arc pitfall; FM-8.)
  8. locate_n(key, 3) must return 3 distinct physical nodes in 3 distinct zones, but the cluster has only 2 zones. What does the walk do, and which invariant tells you it is correct rather than a fault-isolation bug? (§8.4 zone fallback + INV-4; INV-3 distinctness; Phase 4 §16.)
  9. WeightedRendezvous uses -w/ln(h01). Why this formula and not w × hash? What determinism hazard does ln() introduce across platforms, and how is it bounded? (§8.7 + ADR-15; Compatibility Guarantees determinism contract; MM8.)
  10. The ring stores tokens in a BTreeMap, but Performance Engineering says a sorted Vec is faster to read. Under exactly what workload does the Vec win, and what does it cost on the write path? (ADR-08 + Performance Engineering BTreeMap-vs-Vec table; Back-of-Envelope #7.)
  11. A node is removed and fraction_moved comes back at 0.45 instead of ~0.10. Give the most likely root cause, the debugging method, and the property test that would have caught it. (FM-2 + INV-2; Phase 13 §25 disruption property; §8.5.)
  12. Explain why this library separates placement from replication transport, and what breaks in a caller that assumes locate_n guarantees the replicas are actually in sync. (P8 + §1.2 non-goals; INV-3; Comparative Architecture Table Dynamo row.)
  13. An attacker controls keys on a public XxHash64-backed cache and pins load on one node. Walk the full attack and the two independent defenses, and explain why one defense holds even if the other is bypassed. (§3.2 trust boundary + T1/T2; P5; MM10; §8.10 bounded-load cap.)
  14. Maglev rebuilds its entire table on every backend change; the ring splices incrementally. Quantify the cost difference at n=64, V=150 and explain why Maglev accepts the worse number. (Back-of-Envelope #4/#8 + §8.9; MM6; Scalability membership-change table.)
  15. Why does the project ship a ModuloHash that it explicitly forbids in production, and what single deployment condition would actually make modulo the right choice? (§8.5 + ADR-19; P9; Comparative Architecture Table.)
  16. A 200-node HRW cluster sees locate p99 climb to 5 µs. Give the two structural fixes, the threshold at which each applies, and the correctness property the faster one must still satisfy. (§8.6–8.7 + ADR-16; Back-of-Envelope #5; Scalability HRW bottleneck row.)
  17. The arc-swap writer panics mid-clone. What state is the ring left in, who detects it, and how does a reader in flight survive? (Phase 12 §24 failure analysis + INV-10; P6; Operational Readiness.)
  18. Two different node names hash to the same u64 token. What happens on the ring, how is it detected, and why is the probability acceptable up to n=10k? (§8.11 token collision + CLRS birthday analysis; INV-9; Phase 3 §15 pitfalls.)
  19. Ketama-compat mode breaks the no_std guarantee and uses MD5. Justify why the library offers it anyway, and the exact compatibility it does vs does not promise. (Compatibility Guarantees ketama section + ADR-22; §5.4 ketama format; Comparative Architecture Table ketama row.)
  20. Bumping vnodes_per_unit_weight from 150 to 200 is a breaking change requiring a coordinated rollout, but bumping capacity_factor from 1.25 to 1.5 is safe to do live. Explain the difference in terms of what each change does to the token map. (Compatibility Guarantees migration table + §8.3; INV-11; ADR-09/ADR-13.)
  21. DisruptionReport and DistributionReport are both computed from a key sample. Why must the sample be ≥100k keys for the disruption property test, and what statistical artifact appears if it is too small? (P4/P12 + Phase 5 §17 pitfalls; Back-of-Envelope #11; §8.3.)
  22. A live ring under continuous membership churn shows writers starving readers (or vice versa). Which primitive is at fault, and what is the recommended replacement and why? (Phase 12 §24 RwLock-starvation pitfall + P6; ADR-20; Scalability arc-swap write-serialization row.)
  23. Explain why locate returning Option<NodeId> instead of panicking on an empty ring is a security property, not just an ergonomic one. (T8 panic-as-DoS + INV-1; §11 Placement contract; FM-9.)

Mental Models & First Principles

MM1 — The ring is a function of membership, never a stored artifact. Insight: every token, every owner, the entire BTreeMap is a pure deterministic function of (node set, weights, hasher seed, V); nothing is persisted. Predicts: a crash-restart that replays the node list rebuilds a bit-identical ring; two hosts with the same inputs agree without coordination. Bug class without it: persisting the ring to disk and restoring a stale token map after a membership change — silently routing to a removed node. Applied: §3.2 no-persistence invariant; INV-1; INV-9; Phase 12 §24 (rebuild = replay).

MM2 — Token gaps are exponential; balance is 1/sqrt(V). Insight: with V random tokens per node on a uniform ring, the arc each node owns is a sum of exponential gaps, so per-node load has variance ∝ 1/V and std-dev ∝ 1/sqrt(V). Predicts: doubling V cuts imbalance by ~1.41×, not 2×; past V≈150 returns diminish. Bug class without it: "fixing" a hot node by adding a handful of vnodes and being surprised it barely moved, or setting V=1000 and paying 6× memory for a ~2% gain. Applied: §8.3; Phase 3 §15 std-dev curve; ADR-09; Back-of-Envelope #2.

MM3 — HRW is argmax; the ring is successor — and that single difference is the whole disruption story. Insight: HRW assigns a key to the node maximizing hash(node,key), so removing a node only re-homes keys where it was the max (exactly its share); the ring assigns to the clockwise successor, so removing a node dumps its whole arc on one neighbor. Predicts: HRW hits the K/N minimum exactly with no vnode noise; the ring needs many vnodes to approximate it and a successor failure creates a transient hot neighbor. Bug class without it: expecting a single-token ring to balance like HRW, or expecting HRW removal to perturb unrelated keys. Applied: §8.5–8.6; Phase 7 §19; INV-2; INV-6.

MM4 — Minimal disruption has a hard floor: K/(N+1). Insight: by pigeonhole, adding the (N+1)-th node to K keys forces at least K/(N+1) keys onto it; no scheme beats this. Predicts: ring/HRW/jump/Maglev all asymptote to ~1/N moved; anything reporting less is a measurement bug, anything reporting ~(N-1)/N (modulo) is leaving the entire value of consistent hashing on the table. Bug class without it: celebrating a "0% moved" run (you compared a ring to itself) or accepting modulo's reshuffle as normal. Applied: §8.5; INV-2; Phase 5 §17; FM-2.

MM5 — Bounded load is a tail-latency lever, not a balance feature. Insight: the cap ceil(c·avg) does nothing for the average; it bounds the worst node, which under fan-out is what sets request p99 (Dean & Barroso). The cost is forwarding hops, which trade against the cap via c. Predicts: tightening c reduces peak load but raises forward-hop count and thus per-key latency; c=1.0 gives perfect balance at unbounded hops. Bug class without it: setting c=1.0 "for balance" and creating a forwarding storm (FM-5), or omitting the cap and letting one node saturate during a burst. Applied: §8.10; Phase 6 §18; INV-5; P10; Performance Engineering tail section.

MM6 — Maglev trades incremental updates for O(1) lookups and a prime modulus. Insight: Maglev precomputes a dense lookup[hash%M] table; lookup is one array read, but any membership change rebuilds the whole table (O(M)). The prime M with skip≠0 guarantees each backend's permutation visits all M slots, which is why the table fills and balances to ±1. Predicts: Maglev wins where reads vastly outnumber membership changes (L4 LB); a non-prime M or skip=0 silently under-fills and skews load. Bug class without it: choosing M=65536 (power of two) and getting uneven coverage, or rebuilding per-key instead of per-membership-change. Applied: §8.9; Phase 10 §22; INV-8; ADR-18.

MM7 — Jump hash is the cheapest consistent hash, and ordinality is the price. Insight: the Lamping-Veach recurrence needs no table and no node names — only a bucket count — because buckets are ordinals 0..n-1 and the recurrence is monotone in n. That same ordinality forbids removing a middle bucket without renumbering. Predicts: jump is unbeatable for tail-append shard growth and useless for arbitrary node failure or zone awareness. Bug class without it: removing bucket 3 of 10 and watching ~half the keys scatter (FM-6) because the ordinals shifted. Applied: §8.8; Phase 9 §21; INV-7; ADR-17.

MM8 — Determinism is a cross-host contract, not a single-process property. Insight: client-side routing with no coordinator only works if every client computes the same owner; that requires a seeded, architecture-independent hash and insertion-ordered (not HashMap-ordered) ring construction. Predicts: a per-host random seed, or HashMap iteration order leaking into token generation, produces split routing where two clients disagree and both miss the cache. Bug class without it: seeding XxHash64 from OS entropy per process — every host builds a different ring. Applied: INV-1; P3; FM-3; Phase 12 §24 epoch broadcast.

MM9 — Reads are lock-free because the writer publishes a whole new ring, atomically. Insight: arc-swap lets the writer build the next ring off to the side and swap a pointer; a reader's load() sees either the old ring or the new one in full, never a half-applied splice. Predicts: read latency is one atomic load regardless of write activity; a reader can never observe a token inserted before its node record exists. Bug class without it: mutating a shared BTreeMap under a read lock and exposing an intermediate state where locate returns a NodeId with no node (INV-10 violation). Applied: P6; INV-10; ADR-20; Phase 12 §24.

MM10 — A weak hash is an attacker's load-imbalance API. Insight: with a fixed, non-keyed hash, an adversary who controls keys can grind keys that land near one token and pin load on one node — the imbalance is chosen, not random. A keyed hash (SipHash) with a secret seed turns this into a PRF attack; bounded load caps the damage regardless. Predicts: a public, user-key-controlled service on XxHash64 is one crafted-key flood away from a hot node. Bug class without it: shipping XxHash64 as the default for a multi-tenant cache and treating the resulting hot spot as "bad luck". Applied: §3.2 trust boundary; P5; T1/T2 threats; ADR-06/ADR-07.

5.4 Specifications / Notes

Jump-hash reference pseudocode (Lamping & Veach §2):

int32_t JumpConsistentHash(uint64_t key, int32_t num_buckets) {
    int64_t b = -1, j = 0;
    while (j < num_buckets) { b = j; key = key*2862933555777941757ULL + 1; j = (b+1) * (double(1LL<<31) / double((key>>33)+1)); }
    return b;
}
  • Multiplier 2862933555777941757 is a Lehmer LCG constant — must match exactly for test-vector conformance.
  • Test vectors: key=0,n=1→0; key=1,n=1→0; key=0,n=2→0; key=1,n=2→0; key=2,n=2→1; key=3,n=2→0; etc. (Table 1 of paper).

Maglev table-build pseudocode (Eisenbud §3.4):

offset[b] = h1(name[b]) % M
skip[b]   = h1(name[b]) % (M-1) + 1          // skip != 0
// permutation[b][j] = (offset[b] + j*skip[b]) % M
// fill: for each j, each b claims next unfilled permutation slot
  • M must be prime; recommended M=65537 for n≤1000, M=655373 for larger clusters.
  • Post-fill invariant: each backend's slot count is floor(M/n) or ceil(M/n) — check within ±1.

Bounded-load (Mirrokni et al. §2): per-node current_load; threshold T = ceil(c·total/n); on locate, take clockwise successor if load < T else walk to next non-full; guarantee max_load ≤ ceil(c·avg), c=1.25 (<25% overhead).

Ketama format (libketama): label "<ip>:<port>-<replica>" (-0..-39); MD5 → 16 B → 4 tokens at byte offsets 0/4/8/12 (LE u32). chr-ring compat mode keeps the label + 4-token positions but hashes XxHash64 (structural compat, breaks wire compat).

Chi-square (Phase 1): B=256 buckets, S≥100k keys, expected S/B; χ² = Σ(obs−exp)²/exp; reject at p<0.01 (χ²₍₂₅₅₎ ≈ 310.5).

Glossary · 46 terms · site-wide glossary

arc-swap snapshot
ArcSwap<Arc<HashRing>> pattern; readers atomically load the current snapshot without a mutex; writers swap in a new Arc after mutation.
avalanche
Hash-quality property: flipping 1 input bit flips ~50% of output bits; tested via bit-sensitivity matrix.
balance
Property: load across nodes stays within a bounded ratio; measured by DistributionReport.peak_to_mean.
bounded load
Constraint: no node exceeds ceil(c * avg_load) for capacity factor c; enforced by BoundedRing.
capacity factor
Parameter c > 1.0 in BoundedRing; e.g., c=1.25 means max node load ≤ 125% of average.
chi-square uniformity
Statistical test applied to hash output buckets; p-value > 0.01 required; detects clustering bias.
churn
Repeated membership changes (adds + removes) in chr-sim; used to measure cumulative disruption over many operations.
clockwise
Direction of successor lookup on the [0, 2^64) ring; BTreeMap::range(token..).next() with wraparound to first().
consistent hashing
Scheme mapping keys to nodes via a shared ring; adding/removing a node moves only ~K/N keys (Karger et al., STOC 1997).
DistributionReport
chr-sim struct: per_node, peak_to_mean, gini, std_dev, max_load, min_load — one snapshot of load balance.
DisruptionReport
chr-sim struct: keys_total, keys_moved, fraction_moved, theoretical_minimum — quantifies migration cost of a membership change.
Gini coefficient
Load-inequality metric in [0,1]; 0 = perfectly balanced; computed in DistributionReport; target < 0.05 at V ≥ 150.
hash ring
The conceptual circular key-space [0, 2^64) onto which both node tokens and key hashes are mapped.
Hasher64
chr-core trait: fn hash_one(&self, bytes: &[u8]) -> u64; implemented by XxHash64 (default) and SipHasher64 (adversarial).
hot spot
Node(s) whose load significantly exceeds the mean; detected by chr-sim hot-spot detector when node_load > c * avg.
HRW
Highest Random Weight; synonym for rendezvous hashing; owner = argmax score(node, key) over all nodes.
jump consistent hash
Lamping-Veach algorithm; maps (key: u64, n: u32) -> u32 in O(ln n) time, O(1) memory; ordinal buckets 0..n-1 only.
key migration
The set of (key, old_node, new_node) triples produced when a membership change reassigns ownership.
ketama
The de-facto consistent-hashing implementation for memcached; chr-ring conformance vectors reproduce ketama's token placement.
Key
chr-core type: Key<'a>(pub &'a [u8]); arbitrary byte slice passed to Placement::locate.
load factor
Ratio node_load / avg_load; ideally ≈ 1.0; peak-to-mean captures the worst node.
lookup table
Maglev's Vec<i32> of length prime M; built via per-backend (offset, skip) permutation fill; O(1) lookup.
maglev
Eisenbud et al. (NSDI 2016) consistent hashing variant; lookup table of prime size M, permutation fill, near-perfect balance.
minimal disruption
Guarantee that removing one node remaps only its own keys (HRW) or ~K/N keys (ring/jump/maglev), not ~K*(n-1)/n as in modulo.
monotonicity
Property: adding a node never moves a key from one existing node to another; only moves keys from existing nodes to the new one.
NodeId
chr-core type: NodeId(pub u64); opaque stable identifier; a string name is interned to one u64 once.
ordinal bucket
Jump-hash constraint: buckets are numbered 0..n-1; add/remove only at the tail (n-1); no arbitrary removal.
peak-to-mean
max_load / avg_load; primary load-balance metric in DistributionReport; target < 1.10 at V ≥ 150.
permutation
Maglev per-backend sequence: entry[j] = (offset + j*skip) % M; each backend fills table slots in permutation order.
Placement
chr-core trait: add_node, remove_node, locate, locate_n; uniform API implemented by all four strategies.
PlacementError
chr-core enum: NoNodes, BadWeight, CapacityExceeded; returned by locate/locate_n on invalid state.
preference list
Ordered list of N distinct physical nodes for a key; PreferenceList { primary, replicas }; from locate_n.
rebalancing
Process of inserting/removing tokens from HashRing after a add_node/remove_node; incremental, O(V log V).
rendezvous hashing
Thaler & Ravishankar HRW; score(n,k) = hash(node_bytes ++ key); owner = argmax; O(n) per lookup unless skeleton variant.
replica
A secondary owner of a key; populated by locate_n; stored in PreferenceList.replicas.
replication factor
n in locate_n(key, n); number of distinct physical owners (primary + n-1 replicas).
ring version
Monotonically increasing u64 epoch incremented on every add_node/remove_node; used for cache invalidation + snapshot diffing.
score
Rendezvous: hash(concat(node_bytes, key_bytes)) -> u64; WeightedRendezvous: -weight / ln(hash_to_unit_f64(h)); higher wins.
SkeletonHrw
Hierarchical rendezvous variant in chr-rendezvous; fanout f tree reduces lookup from O(n) to O(log_f n).
spread
Number of distinct nodes a key can be assigned to across membership configurations; ideally ≤ replication factor + 1.
successor
The first clockwise token at or after hash(key) in the ring; BTreeMap::range(h..).next().unwrap_or(ring.first()).
token
A u64 position on the [0, 2^64) ring assigned to a VNode; token = hash(node_name ++ replica_idx).
virtual node (vnode)
VNode { token, node, replica_idx }; one of V * weight tokens placed for a physical node; reduces load variance to ~1/sqrt(V).
WeightedRendezvous
HRW variant in chr-rendezvous; score = -weight / ln(h01) where h01 = hash / 2^64; respects heterogeneous capacity.
Weight
chr-core type: Weight(pub u32); relative capacity; node gets vnodes_per_unit_weight * weight tokens.
zone/rack awareness
locate_n skips nodes sharing a ZoneId with an already-chosen replica; stored in HashRing.zones: HashMap<NodeId, ZoneId>.
