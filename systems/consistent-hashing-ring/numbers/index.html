Back-of-Envelope Capacity Model

All numbers derive from §4 System Constraints; formulas shown step by step.

1. Keys moved on one node add/remove (the core promise):

fraction_moved (consistent) = 1 / N        (arc geometry, §8.5)
fraction_moved (modulo)     = N / (N+1) ≈ 1 − 1/N
At N = 10:  consistent = 0.10 ;  modulo = 0.909  → 9.1× more cache churn
At K = 1e6 keys, N = 10:  consistent moves 1e5 keys ; modulo moves ~9.09e5 keys
→ This 9× gap is the entire reason the library exists (P1).

2. Ring load std-dev vs vnode count V:

std_dev(load) / mean ≈ 1 / sqrt(V)         (exponential-gap sum, §8.3)
V = 50   → 1/sqrt(50)  ≈ 0.141  (14.1%)
V = 150  → 1/sqrt(150) ≈ 0.0816 (8.2%)   ← default; peak-to-mean ≈ 1.10 at n=10
V = 500  → 1/sqrt(500) ≈ 0.0447 (4.5%)
→ Diminishing returns: 3.3× more memory (150→500) buys ~1.8× tighter balance (ADR-09).

3. Ring memory for n nodes at V vnodes:

§4: ~16 B/token (u64 token + NodeId u64) in the BTreeMap value path
tokens = n × V × avg_weight
n = 1000, V = 150, weight = 1 → 150,000 tokens × 16 B = 2.4 MB
n = 10,000, V = 150          → 1.5e6 tokens × 16 B = 24 MB  (matches §4 max-nodes row)
BTreeMap node overhead ~2× the raw bytes in practice → budget ~48 MB at n=10k.

4. Maglev table memory and balance:

§4: table = M × 4 B (Vec<i32>); M = 65537 prime
memory = 65537 × 4 B = 262,148 B ≈ 256 KB  (fixed, independent of backend count)
slots per backend = M / n ;  at n = 100 → 655.37 → each backend gets 655 or 656 (±1, INV-8)
disruption per backend change ≈ M/n slots / M = 1/n = 0.01 at n=100 (§8.9)
→ 256 KB fits L2; a 10× larger M (655373) = 2.56 MB spills to L3 (the balance/latency tradeoff, ADR-18).

5. HRW lookup cost vs node count:

locate = n hash calls × ~5 ns/hash (XxHash64, §4)
n = 10   →  50 ns       (≥ 5M locate/s, meets §4)
n = 200  →  1.0 µs      (~1M locate/s; still acceptable)
n = 1000 →  5.0 µs      (200k locate/s — below the 5M target → switch to SkeletonHrw)
SkeletonHrw fanout f=8: ~f × log_f(n) = 8 × log_8(1000) ≈ 8 × 3.3 ≈ 27 hashes ≈ 135 ns (≈ 37× fewer, ADR-16)

6. Jump-hash lookup cost:

iterations ≈ ln(num_buckets)            (Lamping-Veach, §8.8)
n = 1000  → ln(1000) ≈ 6.9 → ~7 LCG steps (paper bound; loop is monotone in jumps, ~log2 in practice ≤ 17)
each step: one wrapping mul + one float divide ≈ 2–3 ns → < 50 ns total (meets §4 jump latency)
memory = O(1): two i64 registers, no table → fits entirely in registers.

7. Ring lookup latency (BTreeMap successor):

§4: O(log(n·V)) with ~16 B/token
n = 8, V = 150  → 1200 tokens → log2(1200) ≈ 10.2 comparisons → L1-resident → < 100 ns
n = 1024, V=150 → 153,600 tokens → log2 ≈ 17.2 comparisons; tree spills L1 → cache-miss bound
→ At large nV the sorted-Vec layout (contiguous, ~3 cache lines) beats the scattered B-tree (ADR-08 alt).

8. Membership-change cost (incremental splice vs full rebuild):

incremental add: clone + V inserts × O(log(n·V))
n = 64, V = 150 → 150 × log2(9600) ≈ 150 × 13.2 ≈ 1980 ops → < 1 ms
full rebuild:    n·V × O(log(n·V)) = 9600 × 13.2 ≈ 1.27e5 ops → ~64× costlier
→ Phase 12 incremental splice (INV-9) is the lever that keeps writes off the read critical path.

9. Lock-free read throughput scaling:

single-core ring locate ≈ 5M/s (§4) ;  Maglev ≈ 33M/s
arc-swap load() ≈ 5 ns, lock-free → scales linearly with cores
32-core: ring ≈ 32 × 5M = 160M locate/s ;  Maglev ≈ 32 × 33M ≈ 1.06B/s
writes serialized on RwLock; pointer swap ≈ 10 ns; at 1 change/s write contention ≈ 10 ns/s → negligible.

10. Bounded-load forwarding overhead:

expected extra hops per key ≈ bounded by c (Mirrokni et al.); at c=1.25, < 5% of keys forward
each forward = one extra BTreeMap successor ≈ 50–100 ns
at 5% forward rate, n=20: amortized add ≈ 0.05 × 75 ns ≈ 3.75 ns/locate → < 2% latency tax
c=1.0 (perfect balance): forward rate → high (many keys hop), latency tax unbounded (FM-5).

11. Disruption-test corpus runtime (Phase 13 gate):

§4: 1M keys × 10 churn rounds
per round: 2 × 1M locate (before + after) at ring 5M/s → 2e6 / 5e6 = 0.4 s
10 rounds ≈ 4 s of locate work + owner-map diff (1M × 16 B ≈ 16 MB snapshot/round)
→ Property suite uses 10k keys (≈ 4 ms/round) for fast CI; 1M reserved for explicit bench gate.

12. SkeletonHrw memory overhead:

tree nodes ≈ n × (1 + 1/f + 1/f² + …) = n × f/(f−1)
f = 8 → n × 8/7 ≈ 1.143 n ;  at n = 1000 → ~1143 NodeId entries × 8 B ≈ 9.1 KB
vs flat HRW n × 8 B = 8 KB → ~14% memory overhead to convert O(n) lookups into O(log n) (ADR-16).
