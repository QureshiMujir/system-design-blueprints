402 — Consistent / Rendezvous Hashing Ring

Goal: Implement, from scratch in Rust, a key-placement library that maps keys to nodes so that adding or removing a node moves the minimum number of keys. It implements and compares the full placement-algorithm family behind one uniform Placement trait — a consistent hashing ring with virtual nodes, weighted placement, replication preference lists, and Consistent Hashing with Bounded Loads; rendezvous (HRW) hashing including weighted and skeleton-O(log n) variants; jump consistent hash; and Maglev lookup-table hashing — plus a simulation/analysis harness that measures load balance and disruption, and a lock-free-read concurrent embedding for a live sharded service. It answers "which node(s) own this key"; it is not the data store.

1. Goal

A from-scratch, production-quality Rust library answering "which node(s) own this key?" with minimal disruption across five placement strategies under one Placement trait: consistent-hashing ring (vnodes, weighted, preference lists, bounded load), rendezvous/HRW (weighted, skeleton O(log n)), jump (Lamping-Veach), Maglev (lookup-table), and a modulo baseline — plus a simulation harness that measures and compares them all.

1.1 Engineering Definition

The library resolves a single query family: locate(key) -> NodeId and locate_n(key, n) -> [NodeId; n]. Correctness requirements:

Property Requirement
Minimal disruption On one membership change, ~1/N keys remapped (ring/HRW/jump/maglev); never full reshuffle
Monotonicity Adding a node never moves a key away from its current owner to a third node
Determinism Same membership + same key -> same owner, always
Replication safety locate_n returns N DISTINCT physical nodes; no duplicates
Balance peak-to-mean < 1.1 at V >= 150 vnodes/unit (ring); near-1.0 for maglev

1.2 System Boundaries

IN scope: locate/locate_n with pluggable Hasher64 (XxHash64 default, SipHasher64 adversarial); strategies HashRing(+BoundedRing), Rendezvous, WeightedRendezvous, SkeletonHrw, JumpHash, Maglev, ModuloHash; zone/rack-aware preference walk; bounded-load cap ≤ ceil(c·avg) with clockwise forward; chr-sim cross-strategy Distribution/DisruptionReport; chring CLI (locate/add/remove/distribute/churn/compare/bench); thread-safe live ring (arc-swap lock-free reads).

NON-goals (explicit): data storage / replication transport / quorum / sloppy quorum (pair with 98 Sharding or 36 KV); cryptographic hash security (fast non-crypto hashes; SipHash is adversarial-resistant, not a security primitive); network membership / failure detection (72 Gossip / 40 Service Discovery); a hash-function library (61/87/88 — we consume Hasher64); ring persistence (rebuildable from membership).

2. Why Build This

2.1 Unique Systems Knowledge

  • Ring + vnodes: token-ring design, variance ~1/sqrt(V), weighted token generation.
  • Bounded load: the forwarding recurrence capping max load at c·avg with near-minimal extra movement.
  • HRW: removal re-homes only the node's own keys (argmax monotonicity); naive scan is O(n); SkeletonHrw → O(log n) via virtual hierarchy.
  • Jump hash: the PRNG recurrence (key,n)→bucket in O(ln n)/O(1), and why ordinal buckets limit it.
  • Maglev: (offset, skip) permutation fill → near-perfect balance; prime M → full coverage; O(1) lookup for connection affinity.
  • Disruption math: theoretical minimum 1/N; how vnode noise inflates it; how HRW/Maglev hit it exactly.

2.2 Historical / Architectural Significance

Dynamo (SOSP 2007) made vnodes + preference lists standard (Cassandra/Riak descend from it); ketama/libketama is the de-facto memcached ring (we validate against its vectors); Maglev (NSDI 2016) powers Google L4 LBs (O(1), connection-consistent); bounded loads (Mirrokni et al., SODA 2018) is the cap-and-forward hot-spot fix preserving minimal disruption. Every sharded system implements one of these or pays full-reshuffle cost (cache-invalidation storm, rebalance spike).

2.3 Engineering Muscles

Probability + balance analysis (std-dev ~1/sqrt(V), Gini, peak-to-mean); data layout (BTreeMap range successor, Vec<i32> maglev cache packing); hot-path optimization (zero-alloc inlined locate); lock-free-read concurrency (arc-swap snapshot, readers never block); property testing (add-then-remove returns keys to original owners); fuzzing (arbitrary keys/membership never panic).

2.4 Portfolio Cross-Links

98 Sharding (this is its placement oracle); 36 Distributed KV (routes GET/PUT to shard); 59 Distributed Cache (ketama-compatible ring); 66 Load Balancer (Maglev + bounded-load primitives); 72 Gossip (supplies add/remove events); 99 Anti-Entropy (walks token ranges; DisruptionReport quantifies churn); 88/61/87 Hash Functions (supply Hasher64 impls to compare).

2.5 Calibration Value

  • Balance vs disruption tradeoff — the fundamental tension: more vnodes -> better balance but slower ring build; maglev -> near-perfect balance + O(1) lookup but O(n*M) build cost
  • Strategy selection guide — teaches engineers which algorithm fits which constraint: jump for ordinal sharding with tail-add/remove; maglev for L4 LB connection affinity; HRW for perfect disruption minimality; ring for general-purpose with zone awareness; bounded-load for burst-prone workloads
  • The cost of getting it wrong — modulo baseline demonstrates full reshuffle: ~(N-1)/N fraction of keys remapped on any membership change vs ~1/N for consistent alternatives

2.6 What Mastery Looks Like

After building this, you can do the following — each competency cemented by a named phase:

  • Derive load variance from first principles and pick V. You can show why ring token gaps are exponentially distributed and balance std-dev scales as 1/sqrt(V), then choose vnodes_per_unit_weight from a measured curve rather than folklore (Phase 3 §15; §8.3).
  • Prove minimal disruption, not assert it. You can prove a single membership change moves ~K/N keys for the ring (arc geometry) and exactly the removed node's share for HRW (argmax monotonicity), and quantify the gap to the K/(N+1) pigeonhole bound (Phase 5 §17; Phase 7 §19; §8.5).
  • Build the Maglev table and explain every constant. You can implement the (offset, skip) permutation fill, prove a prime M with skip≠0 covers all slots, and bound disruption at ~1/n table entries per backend change (Phase 10 §22; §8.9).
  • Reproduce the jump-hash recurrence and state its limits. You can write the Lamping-Veach LCG from memory, match published vectors, and articulate exactly why ordinal-only buckets forbid arbitrary removal (Phase 9 §21; §8.8).
  • Cap tail load without wrecking disruption. You can implement bounded-load forwarding, prove max_load ≤ ceil(c·avg) terminates, and trade c against forwarding overhead (Phase 6 §18; §8.10; ADR-13).
  • Make placement lock-free and deterministic across hosts. You can build an arc-swap snapshot ring where readers never block writers, and guarantee bit-identical locate on every host/arch via seeded architecture-independent hashing (Phase 12 §24; §7 INV-1, INV-10).
  • Measure and compare strategies on one corpus. You can drive every strategy through one harness emitting peak-to-mean, Gini, and fraction_moved, and read the comparison table to select an algorithm by constraint (Phase 11 §23; §2.5; P9).
  • Debug a placement system in production. You can diagnose split routing (epoch/seed skew), over-migration (token-delta bug), and hot nodes (vnode/hash/weight) from telemetry alone (Failure Modes FM-2/FM-3; Operational Readiness runbooks).

3.2 Trust Boundary

  • Attacker-controlled keys/node names: crafted keys can pin one node under a fixed-seed XxHash64 → mitigate with SipHasher64 { k0, k1 } (random seed, externally unpredictable, still deterministic per seed).
  • Concurrency boundary: reads (locate/locate_n) lock-free over an arc-swap snapshot; writes (add/remove) serialized under RwLock — readers never block writers, writers never block readers.
  • No-persistence invariant: ring is fully derived from the node+weight list; crash-restart replays membership (no WAL/disk I/O).

3.3 Component Descriptions

chr-core — Placement + Hasher64. Defines the uniform Placement trait (all four strategies impl it) and Hasher64 (XxHash64 default, SipHasher64 keyed). NodeId(u64) opaque identity, Weight(u32) capacity, PlacementError {NoNodes,BadWeight,CapacityExceeded} (locate returns None, never panics). Zero deps beyond alloc; every strategy crate depends on it. (Types: §11.1.)

HashRing (chr-ring). BTreeMap<u64,NodeId> over [0,2⁶⁴); each node contributes V·weight tokens hash(name++replica_idx). locate = range(key_token..).next().or first(), O(log nV). Add/remove splice V·weight tokens incrementally. Invariant ring.len() == Σ weight_i·V (INV-11). Phases 2/3/5.

PreferenceList walk (chr-ring). locate_n walks clockwise dedup'ing physical nodes (and optionally zones via HashMap<NodeId,ZoneId>); first-N replicas span N distinct zones. Always distinct physical NodeIds (INV-3/INV-4). Phase 4.

BoundedRing (chr-ring). Wraps HashRing + per-node load counter; if successor ≥ ceil(c·avg) forward clockwise to next non-full node (c≈1.25; CapacityExceeded if all full). Guarantee max_load ≤ ceil(c·total/n) (INV-5). Phase 6.

Rendezvous / WeightedRendezvous / SkeletonHrw (chr-rendezvous). Flat HRW: score = hash(node++key), owner=argmax, ties by NodeId; removing X re-homes only X's keys (argmax monotone) — perfectly minimal but O(n). Weighted: -w/ln(h01) routes proportionally. Skeleton: fanout-f hierarchy → O(log_f n) (PhaseDeferred("§8.4") for n>10k tuning). Phases 7/8.

JumpHash (chr-alt). jump_hash(key,num_buckets)->u32, Lamping-Veach, O(ln n) time/O(1) memory. Ordinal buckets 0..n-1, tail-only add/remove. No NodeId — chr-cli adapter maps ordinals. Phase 9.

Maglev (chr-alt). Maglev { lookup: Vec<i32>, table_size }, prime M; per-backend offset=hash(b)%M, skip=hash2(b)%(M-1)+1 permutation-fill; lookup[hash(key)%M] O(1). Near-perfect balance, ~1/n disruption per backend change. Phase 10.

ModuloHash (chr-alt). hash(key)%n; O(1)/O(1)/zero-build baseline. ~(n-1)/n remapped per change — chr-sim baseline only, never production.

chr-sim — analysis harness. Drives any Placement over synthetic keys → DistributionReport (peak-to-mean/Gini/std-dev) + DisruptionReport (moved vs theoretical 1/N); churn simulator + hot-spot detector + cross-strategy Markdown table. Phase 11.

chr-cli — chring binary. Subcommands locate/add/remove/distribute/churn/compare/bench; --strategy ring|hrw|jump|maglev|bounded; --format json|table|csv; bench runs Criterion. Phases 12/13.

5.4 Specifications / Notes

Jump-hash reference pseudocode (Lamping & Veach §2):

int32_t JumpConsistentHash(uint64_t key, int32_t num_buckets) {
    int64_t b = -1, j = 0;
    while (j < num_buckets) { b = j; key = key*2862933555777941757ULL + 1; j = (b+1) * (double(1LL<<31) / double((key>>33)+1)); }
    return b;
}
  • Multiplier 2862933555777941757 is a Lehmer LCG constant — must match exactly for test-vector conformance.
  • Test vectors: key=0,n=1→0; key=1,n=1→0; key=0,n=2→0; key=1,n=2→0; key=2,n=2→1; key=3,n=2→0; etc. (Table 1 of paper).

Maglev table-build pseudocode (Eisenbud §3.4):

offset[b] = h1(name[b]) % M
skip[b]   = h1(name[b]) % (M-1) + 1          // skip != 0
// permutation[b][j] = (offset[b] + j*skip[b]) % M
// fill: for each j, each b claims next unfilled permutation slot
  • M must be prime; recommended M=65537 for n≤1000, M=655373 for larger clusters.
  • Post-fill invariant: each backend's slot count is floor(M/n) or ceil(M/n) — check within ±1.

Bounded-load (Mirrokni et al. §2): per-node current_load; threshold T = ceil(c·total/n); on locate, take clockwise successor if load < T else walk to next non-full; guarantee max_load ≤ ceil(c·avg), c=1.25 (<25% overhead).

Ketama format (libketama): label "<ip>:<port>-<replica>" (-0..-39); MD5 → 16 B → 4 tokens at byte offsets 0/4/8/12 (LE u32). chr-ring compat mode keeps the label + 4-token positions but hashes XxHash64 (structural compat, breaks wire compat).

Chi-square (Phase 1): B=256 buckets, S≥100k keys, expected S/B; χ² = Σ(obs−exp)²/exp; reject at p<0.01 (χ²₍₂₅₅₎ ≈ 310.5).

6. Design Principles

P1 — Minimal disruption is the whole point. Rule: one add/remove moves ~K/N keys, never ~all. Tradeoff: needs ring/HRW invariants; modulo is simpler but reshuffles ~(N-1)/N. Op: scale-out moves O(1/N) of cache/session keys — capacity-plannable. Violate → cache hit rates collapse, affinity breaks for ~all users.

P2 — One uniform Placement API. Rule: all strategies impl Placement; callers strategy-agnostic. Tradeoff: caps per-strategy ergonomics (jump has no NodeId — wrapped; ~1 ns). Op: swap Box<dyn Placement> at runtime, no router change. Violate → chr-sim/chr-cli can't dispatch uniformly.

P3 — Determinism across hosts and restarts. Rule: identical (membership, weights, seed) → same NodeId on every host/OS/arch. Tradeoff: forbids HashMap iteration order; needs seeded arch-independent hash. Op: coordinator-free client routing requires it. Violate → split-brain ownership, both clients miss (FM-3).

P4 — Balance is measured, not assumed. Rule: every strategy reports DistributionReport; balance claims are empirical. Tradeoff: chr-sim is a CI dep (1M-key run ~200 ms). Op: imbalance caught pre-prod; V=150 chosen empirically. Violate → over-provisioning on false claims, hidden hot spots.

P5 — Hashing is a dependency, not a feature. Rule: inject XxHash64 (~2 ns) or SipHasher64 (keyed, ~8 ns); strategies generic over H. Tradeoff: monomorphization +3–5 KB/combo. Op: user-key services use SipHash (T1). Violate → crafted keys pin all load on one vnode.

P6 — Lock-free reads on the hot path. Rule: locate/locate_n never lock; read an arc-swap snapshot. Tradeoff: writes swap the Arc, serialize on RwLock; reads pay one ~5 ns atomic. Op: a 15k-token rebuild happens off the critical path, snaps in atomically. Violate → p99 spikes under write contention.

P7 — Weighted capacity from day one. Rule: Weight(u32) first-class on add_node; default 1. Tradeoff: uniform clusters pay zero (fast path); weighted rings allocate V×weight tokens. Op: mixed HW gets proportional share, no manual partitioning. Violate → imbalance proportional to capacity ratio.

P8 — Replication is placement, not storage. Rule: locate_n returns N distinct physical NodeIds, no data transit; storage layer (98/36) consumes it. Tradeoff: can't verify replicas are synced — only that ownership is fault-isolated + deterministic. Op: RF change N=2→3 = call locate_n with new N, no migration implied. Violate → callers build replication on the wrong ownership set.

P9 — Right algorithm for the constraint. Select by constraint, not default; violate → jump with arbitrary removal corrupts mapping, Maglev with small M imbalances:

Constraint Algorithm Reason
Ordinal buckets, tail-only, O(1) mem JumpHash Lamping-Veach
O(1) lookup, connection consistency, LB Maglev lookup table, stable across churn
Perfect minimal disruption, arbitrary membership Rendezvous (HRW) argmax zero-extra-movement
Arbitrary membership + replication + zones HashRing (vnodes) preference-list walk (general case)
HashRing + load cap BoundedRing per-node counter, bounded load

P10 — Bounded load prevents hot spots. Rule: BoundedRing caps max_load ≤ ceil(c·avg) (c=1.25). Tradeoff: O(1) counters + a forward step; worst-case O(n) if all full. Op: failover surge spreads to next non-full node, capping it. Violate → single-node saturation ("thundering ring", FM-5).

P11 — Token-ring consistency: no dangling tokens. Rule: post-remove 0 tokens map to id; post-add exactly V×w. Tradeoff: remove scans for the node's vnodes O(V×w) (rare). Op: partial remove impossible (atomic arc-swap). Violate → locate returns a dead node, keys silently lost (INV-9).

P12 — Observability first: every metric computable. Rule: both reports computable from ring + sample, no external infra. Tradeoff: accuracy scales with sample (1M ≈ ±0.1%; 10k ~5 ms in CI). Op: capacity plans carry exact peak-to-mean predictions. Violate → config by intuition, prod surprises.

P13 — Separation of membership from routing. Rule: strategies know nothing of gossip/health; they take explicit add/remove. Tradeoff: caller supplies the membership source (gossip-72/SD-40/manual); no self-heal. Op: identical in test harness, CLI, and production. Violate → coupling to one failure detector makes the lib unusable elsewhere.

8. Domain Model — Placement Algorithms, Ring Geometry, Disruption Math

8.1 Placement Problem Statement

Objectives: ownership locate(k)->NodeId (deterministic, total); replication locate_n(k,N) (N distinct, preference-ordered); balance load ≈ K/n (min peak-to-mean/Gini/std-dev); minimal disruption (fewest keys move per change); monotonicity (surviving-node keys never move to another surviving node); spread (uniform, no hot shard). Metrics hierarchy: disruption fraction → peak-to-mean → Gini → std-dev, all on one corpus via chr-sim.

8.2 Ring Model — [0, 2⁶⁴) Token Circle

HashRing.ring: BTreeMap<u64, NodeId> over a circle wrapping at 2⁶⁴. token = hash(name ++ replica_idx_le). locate(key): t=hash(key); ring.range(t..).next().or_else(ring.first_key_value) (first token ≥ t, wrapping to min).

Worked — 3 nodes, 1 token each (N1=0x1A00, N2=0x5500, N3=0xCC00): "foo"→0x3F00 → first ≥ is 0x5500 → N2; "bar"→0xEE00 → wraps → 0x1A00 → N1.

8.3 Virtual Nodes — Load Smoothing

V tokens/node (default 150) cut load variance: token gaps are exponential, sum of V gaps → variance ∝ 1/V → std-dev ∝ 1/sqrt(V). Normalized std-dev / peak-to-mean (n=10): V=1 → ~1.0 / 3–10×; V=50 → ~0.14 / 1.3×; V=150 → ~0.08 / 1.1×; V=500 → ~0.045 / 1.05×. Weighted: Weight(w) → V·w tokens (hash(name ++ replica_idx), i∈0..V·w) = proportional load share.

8.4 Preference List Walk — Replication with Zone Awareness

Goal: locate_n(key, N=3) returns N distinct physical nodes for fault-isolated replication.

Algorithm (clockwise walk from key's primary token):

Iterate ring.range(key_token..).chain(ring.range(..)) (clockwise wrap). Per candidate token → physical node: skip if node ∈ seen_nodes; skip if zone(node) ∈ seen_zones AND unused zones remain (zone-aware mode); otherwise push to result, mark node+zone seen. Stop when result.len() == N or ring exhausted. Split: result[0] → primary, rest → replicas.

Step Condition Action
Visit token → node node already in result Skip (vnode of chosen physical node)
Visit token → node zone already covered AND unused zones remain Skip (rack-aware dedup)
Visit token → node node/zone both new Append to result; mark seen
result.len() == N — Return PreferenceList

Worked — 6 nodes / 3 zones, N=3, sorted tokens 0x10 N1(A), 0x20 N3(B), 0x30 N1(A)·skip, 0x40 N5(C), 0x50 N4(B)·skip, 0x60 N2(A)·skip, 0x70 N6(C)·skip. From key_token 0x05 → [N1, N3, N5] (one per zone) → PreferenceList { primary: N1, replicas: [N3, N5] }. If zones < N, fall back to node-distinct-only.

8.5 Disruption Math — Modulo vs Consistent Hashing

Modulo (hash(k)%n, n→n+1): a key stays iff hash(k)%n == hash(k)%(n+1), probability ≈ 1/(n+1) → fraction moved = n/(n+1) ≈ 1 − 1/n (near-total reshuffle).

Consistent hashing: adding node M between tokens A,B reassigns only keys in arc (A,B] (former owner of B → M); expected arc = 1/n of ring → fraction moved ≈ 1/n (the minimum). Theoretical floor: any K→n mapping must move ≥ K/(n+1) on add (pigeonhole); consistent hashing achieves it.

Before/after — adding N4 (3-node ring above): key 0x0500 moves N1→N4 (new token 0x0300); 0x2000/0x5800/0xDD00 stay on N1/N2/N3. Only the arc (0xCC00, 0x0300] (wrapping) moves to N4. DisruptionReport fields: §11.5.

8.6 HRW (Rendezvous) — Score Function and Top-N

score(node, key) = hash(node.0.to_le_bytes() ++ key); locate = argmax (ties by lower NodeId); locate_n(N) = partial-sort top-N.

Worked — 4 nodes, "session-xyz" with scores N1=0xF3.._0001, N4=0xD1.._0004, N2=0xA8.._0002, N3=0x55.._0003 → locate→N1, locate_n(2)→[N1, N4].

Disruption on remove(N1): only keys where N1 was argmax reassign (to next-highest score); fraction = load(N1)/K ≈ 1/n — perfectly minimal. Tradeoff: O(n) per lookup; SkeletonHrw for n > ~1000.

8.7 Weighted Rendezvous + Skeleton

WeightedRendezvous: h01 = hash_to_unit_f64(node,key) ∈ (0,1); score = -weight / h01.ln(). Higher weight → larger expected score → proportional keys; maximizing -w/ln(U) gives load ∝ w (Thaler-Ravishankar).

SkeletonHrw: fanout-f virtual hierarchy (f=8); score the f children of the winning parent per level, depth log_f(n) → O(f·log_f n) ≈ O(log n) vs flat O(n). Slight imbalance; fanout trades accuracy vs speed.

8.8 Jump Consistent Hash — Lamping-Veach

O(1) memory, O(ln n) time; the LCG recurrence is in §5.4. Worked trace — key=42, num_buckets=5: b walks −1→0 (j=1), →1 (j=3), →3 (j=4), exits when j=7>5 → bucket 3.

Constraint — ordinal buckets 0..n-1: add = increment n (append bucket n); remove = only the last bucket. No arbitrary middle removal, no non-contiguous ids. Use: stateless LB indexed 0..n-1 with tail-only append/trim.

8.9 Maglev Hashing — Lookup Table Construction

n backends, prime M (default 65537, M ≫ n). Per-backend: offset=hash(name)%M, skip=hash(name++"#")%(M-1)+1, perm(i,j)=(offset+j·skip)%M. Round-robin fill (illustrative):

lookup=[-1;M]; next=[0;n]; filled=0
while filled<M: for i in 0..n:
    c=perm(i,next[i]); while lookup[c]!=-1 { next[i]+=1; c=perm(i,next[i]) }
    lookup[c]=i; next[i]+=1; filled+=1; if filled==M break

Worked — M=7, 3 backends B0:(3,4), B1:(0,2), B2:(1,5): round 1 claims 3,0,1; round 2 (skipping taken) 4,2,6; round 3 fills 5 → [B1,B2,B1,B0,B0,B0,B2]; lookup[hash%7] O(1). Disruption per backend change: ~M/n slots → ≈ 1/n.

8.10 Bounded-Load Consistent Hashing

Capacity cap per node: max_load(node) <= ceil(c * avg_load) where c = capacity_factor (default 1.25), avg_load = total_keys / num_nodes.

BoundedRing forwarding (algorithm): Compute the clockwise successor as in plain HashRing::locate. If that node's load < ceil(c * avg), increment its counter and return it. Otherwise walk to the next distinct physical node clockwise and repeat. A circuit-breaker terminates the walk when all ring nodes have been visited once, returning PlacementError::CapacityExceeded. Signature: fn locate(&mut self, key: &[u8]) -> Result<NodeId, PlacementError> — &mut self because locate increments the load counter.

Guarantee: max_load ≤ ceil(c·total/n) — if all were full, total load would exceed c·total (contradiction). Disruption: ~c·(1/n), slightly above plain ring (some keys forward past their successor). c tradeoff: 1.0 = perfect balance / many hops; 1.25 = 25% over avg / rare forwarding; 2.0 = 2× avg / very rare.

8.11 Edge and Degenerate Cases

  • Single node (ring/HRW/bounded): locate→that node; locate_n(N>1)→[node] (no panic). All keys on one token (ring): bad hasher/degenerate keys, Gini→1.0. Remove last node: empty → None/NoNodes. Weight(0): BadWeight, node invisible. N > num_nodes: return all distinct, shorter list. Jump num_buckets=0: NoNodes. Maglev M<n: CapacityExceeded (M prime, ≫ n). Same-zone only: walk falls back to node-distinct. Token collision (~n²/2⁶⁴): PlacementError or last-write-wins by NodeId. Concurrent add+locate (BoundedRing): load is a per-epoch snapshot, stale ≤ one epoch; arc-swap keeps readers consistent.

11.1 chr-core — Shared Vocabulary

// hasher.rs — uniform 64-bit non-crypto hash; deterministic, avalanche (chi-square p>0.01)
pub trait Hasher64: Clone + Send + Sync { fn hash_one(&self, bytes: &[u8]) -> u64; }

// XxHash64: default; seed (default 0); >=10 GB/s on 64-B keys; token gen + hot-path locate
#[derive(Clone)] pub struct XxHash64 { seed: u64 }
impl XxHash64 { pub const fn new(seed: u64) -> Self; pub const fn default_seed() -> Self; }
impl Hasher64 for XxHash64 { /* xxh64 */ }

// SipHasher64: keyed SipHash-1-3; adversarial keys; ~1 GB/s; k0/k1 secret + stable for ring life
#[derive(Clone)] pub struct SipHasher64 { k0: u64, k1: u64 }
impl SipHasher64 { pub fn new(k0: u64, k1: u64) -> Self; }
impl Hasher64 for SipHasher64 { /* sip-1-3 */ }
// ids.rs
// NodeId: opaque, from hashed UTF-8 name; eq/ord by u64; one name -> one NodeId for ring life
#[derive(Copy, Clone, Eq, PartialEq, Ord, PartialOrd, Hash, Debug)] pub struct NodeId(pub u64);
impl NodeId { pub fn from_name<H: Hasher64>(name: &str, hasher: &H) -> Self; }

// Key: zero-copy byte slice; any length; hashed to u64 for positioning
#[derive(Copy, Clone, Debug)] pub struct Key<'a>(pub &'a [u8]);

// Weight: relative capacity; scales vnodes (ring) + score (WeightedRendezvous); default 1; 0 -> BadWeight
#[derive(Copy, Clone, Eq, PartialEq, Ord, PartialOrd, Debug)] pub struct Weight(pub u32);
impl Weight { pub const ONE: Self = Self(1); }

// ZoneId: fault-domain id for zone-aware preference lists
#[derive(Copy, Clone, Eq, PartialEq, Hash, Debug)] pub struct ZoneId(pub u64);
// placement.rs — uniform API for all strategies; &mut self mutates, &self reads (arc-swap-safe).
// Invariants: locate=None iff no nodes (INV-1); locate_n=min(n,distinct) distinct, primary first
// (INV-3); add+remove of same node restores prior locate; single add/remove moves <=ceil(K/N) (INV-2).
pub trait Placement {
    fn add_node(&mut self, node: NodeId, weight: Weight);
    fn remove_node(&mut self, node: NodeId);
    fn locate(&self, key: &[u8]) -> Option<NodeId>;
    fn locate_n(&self, key: &[u8], n: usize) -> Vec<NodeId>;
}
// error.rs — all fallible placement ops return PlacementError
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum PlacementError { NoNodes, BadWeight, CapacityExceeded }
impl core::fmt::Display for PlacementError { /* one-line per variant */ }
#[cfg(feature = "std")] impl std::error::Error for PlacementError {}

11.2 chr-ring — Consistent Hashing Ring

// vnode.rs — one virtual node; token = hash(name ++ replica_idx); BTreeMap key is the token
#[derive(Copy, Clone, Debug, Eq, PartialEq)]
pub struct VNode { pub token: u64, pub node: NodeId, pub replica_idx: u32 }
// ring.rs — consistent hashing ring; BTreeMap<u64,NodeId> O(log VN) successor via
// range(token..).next().or_else(first_key_value). add inserts V*weight tokens, remove deletes
// all of a node's tokens (both O(V log VN)). Not internally synced (wrap RwLock/arc-swap).
// Pure fn of membership+V+seed → serialize nodes/weights/zones, re-derive ring on load.
pub struct HashRing<H: Hasher64> {
    ring: BTreeMap<u64, NodeId>,          // token -> physical node
    vnodes_per_unit_weight: u32,          // V; typical 100–200
    hasher: H,
    nodes: HashMap<NodeId, Weight>,       // source of truth
    zones: HashMap<NodeId, ZoneId>,       // optional per-node zone
}
impl<H: Hasher64> HashRing<H> {
    pub fn new(hasher: H, vnodes_per_unit_weight: u32) -> Self;
    pub fn add_node_with_zone(&mut self, node: NodeId, weight: Weight, zone: Option<ZoneId>); // no-op if present
    pub fn remove_node(&mut self, node: NodeId);                 // no-op if absent
    pub fn locate(&self, key: &[u8]) -> Option<NodeId>;          // clockwise successor of hash(key)
    pub fn locate_n(&self, key: &[u8], n: usize) -> Vec<NodeId>; // N distinct, zone-skip if zones set
    pub fn tokens_for(&self, node: NodeId) -> Vec<u64>;          // sorted; for migration planner
}
impl<H: Hasher64> Placement for HashRing<H> { /* delegates */ }
// preference.rs — ordered distinct physical owners; primary = replicas[0]
#[derive(Debug, Clone)]
pub struct PreferenceList { pub primary: NodeId, pub replicas: Vec<NodeId> } // len = min(n, distinct)
// walk state: skip token if NodeId in seen_nodes OR zone in seen_zones
struct PreferenceWalk<'a> { seen_nodes: HashSet<NodeId>, seen_zones: HashSet<ZoneId>, ring: &'a HashRing<impl Hasher64> }
// bounded.rs — Consistent Hashing with Bounded Loads (Mirrokni et al.). max load <=
// ceil(c * total/num_nodes); forward clockwise to next non-full node on overflow. Load counters
// incremented on locate, resettable, not persisted; worst-case forward chain O(N), typical O(1).
pub struct BoundedRing<H: Hasher64> { ring: HashRing<H>, capacity_factor: f64, load: HashMap<NodeId, u64>, total_load: u64 }
impl<H: Hasher64> BoundedRing<H> {
    pub fn new(ring: HashRing<H>, capacity_factor: f64) -> Result<Self, PlacementError>; // c > 1.0; default 1.25
    pub fn capacity_ceiling(&self) -> u64;
    pub fn reset_counters(&mut self);                           // e.g. epoch boundary; no membership change
}
impl<H: Hasher64> Placement for BoundedRing<H> { /* locate forwards on overflow */ }

11.3 chr-rendezvous — HRW

// hrw.rs — Rendezvous (HRW); O(n) locate; perfectly minimal disruption. owner = argmax
// score(node,key)=hash(node_bytes ++ key_bytes); ties by NodeId ascending. locate_n = top-N, same pass.
pub struct Rendezvous<H: Hasher64> { nodes: Vec<(NodeId, Weight)>, hasher: H } // weights unused here (uniform)
impl<H: Hasher64> Rendezvous<H> { pub fn new(hasher: H) -> Self; pub fn score(&self, node: NodeId, key: &[u8]) -> u64; }
impl<H: Hasher64> Placement for Rendezvous<H> { /* argmax; top-N */ }
// weighted.rs — heterogeneous capacity: score = -weight / ln(h01), h01 = hash/u64::MAX in (0,1].
// Higher Weight wins proportionally; expected fraction at node i = weight_i / Σ weights.
pub struct WeightedRendezvous<H: Hasher64> { nodes: Vec<(NodeId, f64)>, hasher: H } // (id, weight_f64)
impl<H: Hasher64> Placement for WeightedRendezvous<H> { /* -w/ln(h01) argmax */ }
// skeleton.rs — hierarchical O(log_f n) HRW for large n; fanout-f virtual tree, HRW per level,
// leaf returns winner. Slight disruption increase vs flat HRW; still beats ring on removal.
pub struct SkeletonHrw<H: Hasher64> { fanout: usize, nodes: Vec<NodeId>, hasher: H } // f recommended 16–64
impl<H: Hasher64> Placement for SkeletonHrw<H> { /* tree descent; O(log_f n) */ }

11.4 chr-alt — Alternative Algorithms

// jump.rs — Lamping-Veach jump consistent hash; O(ln n) time, O(1) memory. Ordinal buckets
// 0..num_buckets-1; add/remove only at the tail (no arbitrary removal/zone/non-ordinal ids).
pub fn jump_hash(key: u64, num_buckets: u32) -> u32; // PRNG recurrence; return last valid b
// maglev.rs — lookup-table hashing (Eisenbud et al., NSDI 2016). lookup[hash%M] = backend idx;
// build: offset_i=hash(name,0)%M, skip_i=hash(name,1)%(M-1)+1, perm(j)=(offset+j*skip)%M, round-robin fill.
// Near-perfect balance (~1/n), O(1) lookup, ~1/M table change per backend change. M prime, M >> n (>=100n).
pub struct Maglev<H: Hasher64> { lookup: Vec<i32>, table_size: usize, nodes: Vec<NodeId>, hasher: H } // -1 = empty pre-fill
impl<H: Hasher64> Maglev<H> {
    pub fn new(hasher: H, table_size: usize) -> Result<Self, PlacementError>;
    pub fn rebuild(&mut self);                                  // after membership change; O(M)
}
impl<H: Hasher64> Placement for Maglev<H> { /* lookup[hash % M] */ }
// modulo.rs — naive baseline node = hash(key) % n; ~(n-1)/n remapped on any change. DisruptionReport only.
pub struct ModuloHash<H: Hasher64> { n: u32, nodes: Vec<NodeId>, hasher: H }
impl<H: Hasher64> Placement for ModuloHash<H> { /* nodes[hash % n] */ }

11.5 chr-sim — Reports

// distribution.rs — load over nodes after placing keys_total keys. peak_to_mean=max/mean;
// gini 0..1; std_dev of per-node loads. Ring V=150 target: peak_to_mean<1.10, std_dev/mean<0.05.
#[derive(Debug, Clone)]
pub struct DistributionReport { pub per_node: HashMap<NodeId, u64>, pub peak_to_mean: f64, pub gini: f64, pub std_dev: f64, pub max_load: u64, pub min_load: u64 }

pub struct DisruptionReport { pub keys_total: u64, pub keys_moved: u64, pub fraction_moved: f64, pub theoretical_minimum: f64 }
impl DisruptionReport { pub fn measure(before: &dyn Placement, after: &dyn Placement, keys: &[Vec<u8>]) -> Self; } // diff locate per key

1.2 Detailed Implementation Steps

Theory anchors: XxHash64/SipHasher64 realize P5 (hashing is a dependency) + ADR-06/ADR-07; the chi-square + avalanche gates apply Knuth §6.4 + the §5.4 chi-square spec and defend against T2 (weak-hash imbalance); deterministic token bytes establish INV-1 + P3.

4.2 Detailed Implementation Steps

chr-ring/src/preference.rs:

pub struct PreferenceList { pub primary: NodeId, pub replicas: Vec<NodeId> }

pub fn build_preference_list<H: Hasher64>(
    ring: &HashRing<H>, key: &[u8], n: usize, zone_aware: bool,
) -> PreferenceList

Algorithm:

  1. start_token = ring.hasher.hash_one(key).
  2. Iterate ring.ring.range(start_token..).chain(ring.ring.iter()) (clockwise wrap).
  3. Per candidate token → physical = *node_id; skip if seen_nodes.contains(physical).
  4. If zone_aware: fetch zone = ring.zones.get(physical); skip if seen_zones.contains(zone) AND seen_zones.len() < distinct_zones_in_ring.
  5. Insert into seen_nodes; if zone-aware insert zone into seen_zones; push to result.
  6. Stop when result.len() == n or ring exhausted.
  7. Split result[0] → primary, rest → replicas.

5.1 Objectives

5.2 Detailed Implementation Steps

Theory anchors: MigrationPlan + DisruptionReport quantify P1 (minimal disruption) against Karger (STOC 1997) and the §8.5 K/(N+1) pigeonhole bound; the near-minimal-movement property is INV-2; over-migration here is the gravest balance bug (FM-2).

chr-ring/src/migration.rs:

pub struct RangeMove { pub from: NodeId, pub to: NodeId, pub token_lo: u64, pub token_hi: u64 }
pub struct MigrationPlan { pub moves: Vec<RangeMove> }

pub fn plan_add<H: Hasher64>(before: &HashRing<H>, after: &HashRing<H>) -> MigrationPlan
pub fn plan_remove<H: Hasher64>(before: &HashRing<H>, after: &HashRing<H>) -> MigrationPlan

Algorithm for plan_add:

  1. Collect added node's new tokens (sorted).
  2. For each new token t: find before's successor at t (that node loses the key range (prev_t, t] to the new node).
  3. Emit RangeMove { from: old_successor, to: new_node, token_lo: prev_t+1, token_hi: t }.

Algorithm for plan_remove:

  1. Collect removed node's tokens (deterministically, same formula as add_node).
  2. For each removed token t: find after's successor at t (gains range (prev_t, t] from removed node).
  3. Emit RangeMove { from: removed_node, to: new_successor, token_lo: prev_t+1, token_hi: t }.

18. Phase 6 — Bounded-load consistent hashing (BoundedRing)

6.1 Objectives

6.2 Detailed Implementation Steps

Theory anchors: BoundedRing implements Mirrokni et al. (SODA 2018) verbatim (§5.4 algorithm statement) + P10 + ADR-13; the max_load ≤ ceil(c·avg) cap is INV-5; the bounded forwarding loop is the T5 / FM-5 non-termination defense; bounded load is the MM5 tail-latency lever.

File: chr-ring/src/bounded.rs

pub struct BoundedRing<H: Hasher64> {
    ring: HashRing<H>,
    capacity_factor: f64,               // c; default 1.25
    load: HashMap<NodeId, u64>,         // per-node assigned key count
    total_load: u64,

Key algorithms:

  • avg_load() → total_load / node_count; cap(node) → ceil(c * avg_load).

  • add_node delegates to inner HashRing, inserts load[new_node] = 0; remove_node drains load before removing (caller must re-route outstanding keys).
  • Thread-safe variant deferred to Phase 12 (arc-swap); here BoundedRing is Send but not Sync.

Forwarding invariant: the walk must terminate — cap is ceil(c*avg) and c>1, so there always exists at least one under-cap node when total assigned load < c * capacity; add a circuit-breaker (counter ≥ ring.len()) to return CapacityExceeded instead of looping.

File: chr-rendezvous/src/hrw.rs

pub struct Rendezvous<H: Hasher64> {
    nodes: Vec<(NodeId, Weight)>,
    hasher: H,
}

Score function (canonical):

score(node, key) = hasher.hash_one(node.0.to_le_bytes() ++ key)
  • Concatenate NodeId as 8-byte LE then key bytes → single hash_one call.
  • locate(key): iterate all nodes, compute score, track argmax; ties broken by NodeId ascending (lower id wins).

  • Weight field stored but unused in flat Rendezvous; reserved for Phase 8 WeightedRendezvous; document this explicitly.

Disruption property (key to the algorithm): when node Y is removed, score(Y, key) drops out of consideration; the new owner is the previous argmax among remaining nodes. Only keys where Y was the argmax change owner. Keys where another node had higher score are unaffected.

8.1 Objectives

8.2 Detailed Implementation Steps

Theory anchors: the -w/ln(h01) score is the Thaler & Ravishankar (1998) weighted maximizer + ADR-15; SkeletonHrw's fanout-f hierarchy realizes ADR-16's O(log_f n) goal; the equal-weight-matches-flat property guards P9 strategy equivalence; NaN-safety on ln(0) is a P3 determinism guard.

File: chr-rendezvous/src/weighted.rs

pub struct WeightedRendezvous<H: Hasher64> {
    nodes: Vec<(NodeId, f64)>,   // (id, weight as f64)
    hasher: H,
}

Score formula (Thaler & Ravishankar):

h01(node, key) = (hash_one(node ++ key) as f64) / u64::MAX as f64   // in (0,1]
score(node, key) = -(weight as f64) / h01.ln()                       // higher = better owner
  • Tie-break by NodeId ascending when scores equal (NaN-safe comparison: treat NaN as lowest).
  • add_node(node, Weight(w)): push (node, w as f64).
  • locate / locate_n: same argmax / top-N pattern as flat Rendezvous but using weighted score.
  • Guard: h01 == 0.0 → replace with f64::MIN_POSITIVE to avoid ln(0) = -inf → score +inf (always wins, wrong); use score = f64::MAX in that branch consistently so tie-break still applies.

    fanout: usize,           // f; typical 4–16
    hasher: H,
    // internal: Vec<Vec<NodeId>> tree levels built on construction
}

Algorithm (hierarchical):

  1. Build tree: root contains all n nodes split into ceil(n/f) groups; each level further subdivides until leaf groups have ≤ f nodes.
  2. locate(key): at each level, compute HRW score for the f group representatives (the group's canonical node or sub-group hash); descend into the winning group; continue until leaf; return argmax of leaf nodes.
  3. Level count = ceil(log_f(n)); total score computations = f * log_f(n) vs n for flat HRW.
  4. add_node/remove_node: rebuild the tree (O(n)); acceptable since membership changes are infrequent.
  5. locate_n: descend multiple branches when needed to collect N distinct nodes; at each branch-point, take the top-k sub-branches in score order.

22. Phase 10 — Maglev hashing

10.1 Objectives

  • Implement chr-alt/src/maglev.rs: Maglev<H: Hasher64> with build (lookup table construction) + O(1) lookup.
  • Table size M: prime, default 65537; configurable to any prime > n.

10.2 Detailed Implementation Steps

Theory anchors: the (offset, skip) permutation fill is Eisenbud et al. (NSDI 2016) §3.4 + ADR-18; the prime-M + skip≠0 full-coverage and ±1 balance guarantees are INV-8; backend-name collision producing equal (offset, skip) is the T7 defense; O(1) lookup realizes P9's load-balancer case.

File: chr-alt/src/maglev.rs

pub struct Maglev<H: Hasher64> {
    lookup: Vec<i32>,      // len = M; entry = backend index (-1 = empty during build)
    table_size: usize,     // prime M, default 65537
    backends: Vec<NodeId>, // ordered; index = backend id
    hasher: H,
}

Build algorithm (O(M) time, O(M + n) space):

  1. For each backend i: derive offset_i = hash("offset" ++ name_i) % M; skip_i = hash("skip" ++ name_i) % (M-1) + 1.
  2. Permutation perm[i][j] = (offset_i + j * skip_i) % M — generate lazily via counter, not stored.
  3. Fill loop: maintain next[i] = 0 cursor per backend; round-robin over backends; claim perm[i][next[i]]; advance until slot unclaimed; repeat until M slots filled.
  4. Invariant: exactly M slots filled; every slot 0..M claimed exactly once.

Lookup:

pub fn lookup(&self, key: &[u8]) -> Option<NodeId> {
    let idx = self.hasher.hash_one(key) as usize % self.table_size;
    self.backends.get(self.lookup[idx] as usize).copied()
}

Placement impl:

  • add_node / remove_node → rebuild table (O(M) rebuild; no incremental patch).
  • locate → self.lookup(key).
  • locate_n → unsupported natively; fall back to walk first n distinct backends in permutation order for primary; document limitation.

24. Phase 12 — Concurrency and production embedding

12.1 Objectives

  • Wrap any Placement impl in a lock-free-read snapshot using arc-swap; zero allocation on locate/locate_n hot path.

  • Tag each snapshot with a monotonic Epoch(u64); downstream routers can detect stale reads.
  • Expose LiveRing<P> integration API: resolve(key) -> Owner, resolve_n(key, n) -> PreferenceList, update(delta: MembershipDelta).

12.2 Detailed Implementation Steps

Theory anchors: LiveRing's arc-swap snapshot realizes P6 (lock-free reads) + ADR-20; the never-see-a-partial-membership-change guarantee is INV-10; monotonic Epoch + seeded hashing give cross-host determinism (INV-1 + P3 + FM-3); incremental token splice upholds INV-9 (no dangling tokens) + P11.

Adversarial Key Analysis

  • XxHash64 is not adversarially secure; a determined attacker who can observe hashes can construct colliding keys in O(1/ε) queries (birthday bound on 64-bit output).
  • SipHasher64 with a secret seed raises the bar to a PRF attack; practical resistance for most distributed-system threat models (attacker cannot enumerate tokens without the seed).
  • Recommendation: default XxHash64 for trusted-key workloads; expose --keyed-hash siphash flag in chring + the SipHasher64 constructor for untrusted-key paths.
  • Even with keyed hashing, BoundedRing provides a hard load cap regardless of key distribution: worst-case load ≤ ⌈c × avg⌉ for any key set.

Non-Threats (Explicit)

  • Cryptographic key secrecy — not in scope; use TLS/encryption at the transport layer.
  • Node identity forgery — this library consumes NodeId; caller is responsible for authentication.
  • Network partitions / node liveness — gossip (72) / service discovery (40); not modelled here.

FM-2: Over-Migration on Churn (S1 — gravest balance bug)

  • Symptom/cause: fraction_moved ≫ 1/N from a token insert/delete bug (full rebuild re-homes ~50% vs ~1/N). Detect: assert!(fraction_moved <= 1.5/N); pre/post owner-map diff. Auto: none (correctness bug) — pin prior ring version. Manual: diff token ranges, find wrongly-deleted tokens, roll back, patch. Forensic: DisruptionReport diff + BTreeMap before/after. Debug: replay on a clone with same seed; f ≫ 1/N → tokengen suspect. Long-term: Phase 13 property test fraction_moved ≤ 2/N.
  • Real incident: AWS DynamoDB us-east-1, 20 Sep 2015 (AWS public post-event summary): a brief network blip made a large storage-server fleet simultaneously re-request partition-assignment metadata; the metadata service was overwhelmed and retries cascaded. Lesson this blueprint encodes: a single perturbation must not trigger fleet-wide reassignment — minimal-disruption placement (P1, INV-2) bounds keys moved and change rate-limiting (T3) bounds perturbation rate.

FM-3: Split Routing / Non-Determinism (S1)

  • Symptom/cause: hosts compute different owners (data-not-found, stale, divergence) from seed skew, ring-version mismatch, or float non-determinism. Detect: cross-host determinism test (bit-identical locate on shared corpus). Recovery: broadcast canonical seed + epoch; clients compare epoch before routing (arc-swap gives one version atomically). Forensic: log (epoch, seed, node_count, result) per request, diff across hosts. Long-term: ring-version routing header; pinned ketama vectors (INV-1).

FM-4: Preference-List Duplicate or Same-Zone Replica (S3)

  • Symptom: locate_n returns < n distinct physical nodes; or all replicas in same rack.
  • Root cause: zone map not populated; clockwise-walk bug skipping zone check.
  • Detection: assert_eq!(result.iter().collect::<HashSet<_>>().len(), result.len()) after every locate_n.
  • Recovery: re-populate zones HashMap in HashRing; re-run locate_n; no data movement required.

FM-5: Bounded-Load Forwarding Storm (S2)

  • Symptom: locate() latency spikes; forward-chain length > 3; CapacityExceeded errors.
  • Root cause: capacity_factor c too tight (e.g. c=1.01) + burst traffic; all nodes near capacity.
  • Recovery: raise c (1.25 is the recommended default); add nodes to reduce avg load; BoundedRing terminates at ring.len() iterations → never loops.

FM-6: Jump-Hash Ordinal Mismatch (S3)

  • Symptom: key routed to wrong node after non-tail removal; stale cache hits.
  • Root cause: operator removed bucket 3 of 10 without shifting the mapping; JumpHash still assigns by ordinal index.
  • Recovery: use JumpHashAdapter (Vec<NodeId>); always remove from tail; rebuild adapter after change.

FM-7: Maglev Table Under-Fill (S4)

  • Symptom: one backend slot count = 0 in table; load entirely on remaining backends.
  • Root cause: (offset, skip) collision with another backend; prime M too small for backend count.
  • Detection: build-time assertion: all backends have slot_count > 0; min slot_count ≥ M/n - 2.
  • Recovery: choose larger prime M; rename colliding backend to produce distinct (offset, skip).

FM-8: Stale Ring Snapshot (S3)

  • Symptom: locate() returns a node removed seconds ago; requests routed to dead node.
  • Root cause: arc-swap reader holds pre-update snapshot; read-side sees previous Arc<HashRing>.
  • Recovery: arc-swap.load() is always the latest pointer after the write commits; no reader holds stale data beyond the current request span; ring-epoch header lets callers detect staleness.

FM-9: Empty Ring (S4)

  • Symptom: locate() returns None; service degraded. Recovery: caller treats None as "no capacity"; add ≥1 node.

FM-10: Token Collision (S3)

  • Symptom/cause: two distinct node names hash to the same u64 token (probability ~n²/2⁶⁴); the second insert overwrites the first → one node gets ~0 keys. Detect: ring.len() < Σ expected tokens after add; a node's vnode_count == 0 (INV-11). Recovery: detect at add_node via HashSet of tokens → PlacementError or last-write-wins by NodeId; switch hasher seed to break the collision. Forensic: dump (token, node) pairs for the colliding token. Acceptable up to n=10k (CLRS birthday bound).

Hash + Token Derivation: Normative Contract

Hash, seed, and derivation formulas are normative + versioned:

token(name, replica_idx) = hash(name_bytes ++ replica_idx_le)
score(node, key)         = hash(node_id_bytes ++ key_bytes)
maglev_offset(name) = hash(name)%M ;  maglev_skip(name) = hash(name ++ "skip")%(M-1)+1

Hot Paths + Cache Behavior

  • Ring locate: ring.range(token..).next() → O(log(n·V)) B-tree comparisons; V=150, n=8 → 1200 tokens, L1-resident; large V/n spills L1 (sorted-Vec alt below).
  • HRW score loop: sequential Vec<(NodeId,Weight)> scan, one hash_one/node; XxHash64 ~3 ns/hash → 8 nodes ≈ 24 ns; optional AVX2 4-way score mix ~2–3× for n>16.
  • Maglev locate: lookup[hash%M] single array index, one cache line (256 KB table fits L2); build O(M·n) cached after build.

Allocation + arc-swap

  • locate (all strategies): zero heap alloc, returns Option<NodeId> by value. locate_n(k,N): one small Vec<NodeId> (cap N; pre-allocated-buffer API is a future extension). Ring build: one BTreeMap + n·V inserts. Maglev build: one Vec<i32>[M] + freed-after per-backend permutation cursors.
  • ArcSwap::load() ≈ 5 ns atomic, no lock; readers see a consistent snapshot. Write path: RwLock<HashRing> → clone + mutate (incremental splice O(V), not O(nV)) → store(Arc::new(...)).

Mental Models & First Principles

MM1 — The ring is a function of membership, never a stored artifact. Insight: every token, every owner, the entire BTreeMap is a pure deterministic function of (node set, weights, hasher seed, V); nothing is persisted. Predicts: a crash-restart that replays the node list rebuilds a bit-identical ring; two hosts with the same inputs agree without coordination. Bug class without it: persisting the ring to disk and restoring a stale token map after a membership change — silently routing to a removed node. Applied: §3.2 no-persistence invariant; INV-1; INV-9; Phase 12 §24 (rebuild = replay).

MM2 — Token gaps are exponential; balance is 1/sqrt(V). Insight: with V random tokens per node on a uniform ring, the arc each node owns is a sum of exponential gaps, so per-node load has variance ∝ 1/V and std-dev ∝ 1/sqrt(V). Predicts: doubling V cuts imbalance by ~1.41×, not 2×; past V≈150 returns diminish. Bug class without it: "fixing" a hot node by adding a handful of vnodes and being surprised it barely moved, or setting V=1000 and paying 6× memory for a ~2% gain. Applied: §8.3; Phase 3 §15 std-dev curve; ADR-09; Back-of-Envelope #2.

MM3 — HRW is argmax; the ring is successor — and that single difference is the whole disruption story. Insight: HRW assigns a key to the node maximizing hash(node,key), so removing a node only re-homes keys where it was the max (exactly its share); the ring assigns to the clockwise successor, so removing a node dumps its whole arc on one neighbor. Predicts: HRW hits the K/N minimum exactly with no vnode noise; the ring needs many vnodes to approximate it and a successor failure creates a transient hot neighbor. Bug class without it: expecting a single-token ring to balance like HRW, or expecting HRW removal to perturb unrelated keys. Applied: §8.5–8.6; Phase 7 §19; INV-2; INV-6.

MM4 — Minimal disruption has a hard floor: K/(N+1). Insight: by pigeonhole, adding the (N+1)-th node to K keys forces at least K/(N+1) keys onto it; no scheme beats this. Predicts: ring/HRW/jump/Maglev all asymptote to ~1/N moved; anything reporting less is a measurement bug, anything reporting ~(N-1)/N (modulo) is leaving the entire value of consistent hashing on the table. Bug class without it: celebrating a "0% moved" run (you compared a ring to itself) or accepting modulo's reshuffle as normal. Applied: §8.5; INV-2; Phase 5 §17; FM-2.

MM5 — Bounded load is a tail-latency lever, not a balance feature. Insight: the cap ceil(c·avg) does nothing for the average; it bounds the worst node, which under fan-out is what sets request p99 (Dean & Barroso). The cost is forwarding hops, which trade against the cap via c. Predicts: tightening c reduces peak load but raises forward-hop count and thus per-key latency; c=1.0 gives perfect balance at unbounded hops. Bug class without it: setting c=1.0 "for balance" and creating a forwarding storm (FM-5), or omitting the cap and letting one node saturate during a burst. Applied: §8.10; Phase 6 §18; INV-5; P10; Performance Engineering tail section.

MM6 — Maglev trades incremental updates for O(1) lookups and a prime modulus. Insight: Maglev precomputes a dense lookup[hash%M] table; lookup is one array read, but any membership change rebuilds the whole table (O(M)). The prime M with skip≠0 guarantees each backend's permutation visits all M slots, which is why the table fills and balances to ±1. Predicts: Maglev wins where reads vastly outnumber membership changes (L4 LB); a non-prime M or skip=0 silently under-fills and skews load. Bug class without it: choosing M=65536 (power of two) and getting uneven coverage, or rebuilding per-key instead of per-membership-change. Applied: §8.9; Phase 10 §22; INV-8; ADR-18.

MM7 — Jump hash is the cheapest consistent hash, and ordinality is the price. Insight: the Lamping-Veach recurrence needs no table and no node names — only a bucket count — because buckets are ordinals 0..n-1 and the recurrence is monotone in n. That same ordinality forbids removing a middle bucket without renumbering. Predicts: jump is unbeatable for tail-append shard growth and useless for arbitrary node failure or zone awareness. Bug class without it: removing bucket 3 of 10 and watching ~half the keys scatter (FM-6) because the ordinals shifted. Applied: §8.8; Phase 9 §21; INV-7; ADR-17.

MM8 — Determinism is a cross-host contract, not a single-process property. Insight: client-side routing with no coordinator only works if every client computes the same owner; that requires a seeded, architecture-independent hash and insertion-ordered (not HashMap-ordered) ring construction. Predicts: a per-host random seed, or HashMap iteration order leaking into token generation, produces split routing where two clients disagree and both miss the cache. Bug class without it: seeding XxHash64 from OS entropy per process — every host builds a different ring. Applied: INV-1; P3; FM-3; Phase 12 §24 epoch broadcast.

MM9 — Reads are lock-free because the writer publishes a whole new ring, atomically. Insight: arc-swap lets the writer build the next ring off to the side and swap a pointer; a reader's load() sees either the old ring or the new one in full, never a half-applied splice. Predicts: read latency is one atomic load regardless of write activity; a reader can never observe a token inserted before its node record exists. Bug class without it: mutating a shared BTreeMap under a read lock and exposing an intermediate state where locate returns a NodeId with no node (INV-10 violation). Applied: P6; INV-10; ADR-20; Phase 12 §24.

MM10 — A weak hash is an attacker's load-imbalance API. Insight: with a fixed, non-keyed hash, an adversary who controls keys can grind keys that land near one token and pin load on one node — the imbalance is chosen, not random. A keyed hash (SipHash) with a secret seed turns this into a PRF attack; bounded load caps the damage regardless. Predicts: a public, user-key-controlled service on XxHash64 is one crafted-key flood away from a hot node. Bug class without it: shipping XxHash64 as the default for a multi-tenant cache and treating the resulting hot spot as "bad luck". Applied: §3.2 trust boundary; P5; T1/T2 threats; ADR-06/ADR-07.

Amazon Dynamo / DynamoDB: The system that made vnodes + preference lists production-standard (DeCandia et al., SOSP 2007). Its key differentiating decision is coupling placement to availability mechanisms — sloppy quorum and hinted handoff — so that an overloaded or failed successor is routed around at the data layer rather than capped at the placement layer. That wins for an always-writable store, but it conflates placement with replication transport; this library deliberately separates them (P8) so the same ring serves stores that make different durability choices.

Apache Cassandra (vnodes): Inherits Dynamo's ring but pushed the default vnode count to 256 and made the partitioner (Murmur3) and rack-awareness (snitch) first-class config. Its distinguishing decision is running placement inside a GC'd JVM, where a large ring rebuild can stall behind garbage collection — exactly the tail-latency hazard that motivates this library's zero-GC Rust + off-critical-path arc-swap rebuild (ADR-01, ADR-20). Cassandra wins when you want a batteries-included store with mature operational tooling and can absorb JVM tail latency.

Ketama / libketama (memcached): The de-facto consistent-hashing standard for memcached clients (RJ Ewing, 2007): a sorted ring array with 40 vnodes per server, 4 tokens extracted per MD5 digest, binary-searched on lookup. Its differentiating decisions — MD5 tokens and a global mutex around the lookup/rebuild — are exactly the two costs this library removes (XxHash64 at ~2 ns vs MD5 at ~50 ns; lock-free arc-swap reads). Ketama wins when wire compatibility with an existing memcached client fleet is mandatory, which is why this library offers a frozen ketama-compat mode (ADR-22) rather than reinventing the format.

Google Maglev: A fundamentally different placement model — a dense lookup table rather than a ring (Eisenbud et al., NSDI 2016). Its distinguishing decision is optimizing for the L4 load-balancer regime: O(1) per-packet lookup at line rate and connection consistency under backend churn, at the cost of an O(M) full-table rebuild on any membership change. Maglev wins where reads dominate membership changes by many orders of magnitude (every packet vs a backend change per minute) and weighting is not required; it loses where arbitrary weights or replication preference lists are needed.

Back-of-Envelope Capacity Model

All numbers derive from §4 System Constraints; formulas shown step by step.

1. Keys moved on one node add/remove (the core promise):

fraction_moved (consistent) = 1 / N        (arc geometry, §8.5)
fraction_moved (modulo)     = N / (N+1) ≈ 1 − 1/N
At N = 10:  consistent = 0.10 ;  modulo = 0.909  → 9.1× more cache churn
At K = 1e6 keys, N = 10:  consistent moves 1e5 keys ; modulo moves ~9.09e5 keys
→ This 9× gap is the entire reason the library exists (P1).

2. Ring load std-dev vs vnode count V:

std_dev(load) / mean ≈ 1 / sqrt(V)         (exponential-gap sum, §8.3)
V = 50   → 1/sqrt(50)  ≈ 0.141  (14.1%)
V = 150  → 1/sqrt(150) ≈ 0.0816 (8.2%)   ← default; peak-to-mean ≈ 1.10 at n=10
V = 500  → 1/sqrt(500) ≈ 0.0447 (4.5%)
→ Diminishing returns: 3.3× more memory (150→500) buys ~1.8× tighter balance (ADR-09).

3. Ring memory for n nodes at V vnodes:

§4: ~16 B/token (u64 token + NodeId u64) in the BTreeMap value path
tokens = n × V × avg_weight
n = 1000, V = 150, weight = 1 → 150,000 tokens × 16 B = 2.4 MB
n = 10,000, V = 150          → 1.5e6 tokens × 16 B = 24 MB  (matches §4 max-nodes row)
BTreeMap node overhead ~2× the raw bytes in practice → budget ~48 MB at n=10k.

4. Maglev table memory and balance:

§4: table = M × 4 B (Vec<i32>); M = 65537 prime
memory = 65537 × 4 B = 262,148 B ≈ 256 KB  (fixed, independent of backend count)
slots per backend = M / n ;  at n = 100 → 655.37 → each backend gets 655 or 656 (±1, INV-8)
disruption per backend change ≈ M/n slots / M = 1/n = 0.01 at n=100 (§8.9)
→ 256 KB fits L2; a 10× larger M (655373) = 2.56 MB spills to L3 (the balance/latency tradeoff, ADR-18).

5. HRW lookup cost vs node count:

locate = n hash calls × ~5 ns/hash (XxHash64, §4)
n = 10   →  50 ns       (≥ 5M locate/s, meets §4)
n = 200  →  1.0 µs      (~1M locate/s; still acceptable)
n = 1000 →  5.0 µs      (200k locate/s — below the 5M target → switch to SkeletonHrw)
SkeletonHrw fanout f=8: ~f × log_f(n) = 8 × log_8(1000) ≈ 8 × 3.3 ≈ 27 hashes ≈ 135 ns (≈ 37× fewer, ADR-16)

6. Jump-hash lookup cost:

iterations ≈ ln(num_buckets)            (Lamping-Veach, §8.8)
n = 1000  → ln(1000) ≈ 6.9 → ~7 LCG steps (paper bound; loop is monotone in jumps, ~log2 in practice ≤ 17)
each step: one wrapping mul + one float divide ≈ 2–3 ns → < 50 ns total (meets §4 jump latency)
memory = O(1): two i64 registers, no table → fits entirely in registers.

7. Ring lookup latency (BTreeMap successor):

§4: O(log(n·V)) with ~16 B/token
n = 8, V = 150  → 1200 tokens → log2(1200) ≈ 10.2 comparisons → L1-resident → < 100 ns
n = 1024, V=150 → 153,600 tokens → log2 ≈ 17.2 comparisons; tree spills L1 → cache-miss bound
→ At large nV the sorted-Vec layout (contiguous, ~3 cache lines) beats the scattered B-tree (ADR-08 alt).

8. Membership-change cost (incremental splice vs full rebuild):

incremental add: clone + V inserts × O(log(n·V))
n = 64, V = 150 → 150 × log2(9600) ≈ 150 × 13.2 ≈ 1980 ops → < 1 ms
full rebuild:    n·V × O(log(n·V)) = 9600 × 13.2 ≈ 1.27e5 ops → ~64× costlier
→ Phase 12 incremental splice (INV-9) is the lever that keeps writes off the read critical path.

9. Lock-free read throughput scaling:

single-core ring locate ≈ 5M/s (§4) ;  Maglev ≈ 33M/s
arc-swap load() ≈ 5 ns, lock-free → scales linearly with cores
32-core: ring ≈ 32 × 5M = 160M locate/s ;  Maglev ≈ 32 × 33M ≈ 1.06B/s
writes serialized on RwLock; pointer swap ≈ 10 ns; at 1 change/s write contention ≈ 10 ns/s → negligible.

10. Bounded-load forwarding overhead:

expected extra hops per key ≈ bounded by c (Mirrokni et al.); at c=1.25, < 5% of keys forward
each forward = one extra BTreeMap successor ≈ 50–100 ns
at 5% forward rate, n=20: amortized add ≈ 0.05 × 75 ns ≈ 3.75 ns/locate → < 2% latency tax
c=1.0 (perfect balance): forward rate → high (many keys hop), latency tax unbounded (FM-5).

11. Disruption-test corpus runtime (Phase 13 gate):

§4: 1M keys × 10 churn rounds
per round: 2 × 1M locate (before + after) at ring 5M/s → 2e6 / 5e6 = 0.4 s
10 rounds ≈ 4 s of locate work + owner-map diff (1M × 16 B ≈ 16 MB snapshot/round)
→ Property suite uses 10k keys (≈ 4 ms/round) for fast CI; 1M reserved for explicit bench gate.

12. SkeletonHrw memory overhead:

tree nodes ≈ n × (1 + 1/f + 1/f² + …) = n × f/(f−1)
f = 8 → n × 8/7 ≈ 1.143 n ;  at n = 1000 → ~1143 NodeId entries × 8 B ≈ 9.1 KB
vs flat HRW n × 8 B = 8 KB → ~14% memory overhead to convert O(n) lookups into O(log n) (ADR-16).

Hard Questions (Self-Examination)

Each question requires synthesizing ≥2 sections; the cited § shows where the primary answer lives, with a second pointer for the synthesis.

  1. Why does a single-token ring need ~150 vnodes to match the balance HRW gets for free, and what is the cost you pay for that match? (§8.3 vnode variance + §8.6 HRW argmax; ADR-09 vs P9.)
  2. Adding the (N+1)-th node moves at least K/(N+1) keys by pigeonhole. The ring moves ~K/N. Reconcile these two numbers and explain why a measured fraction_moved of 0.0 on an add is a bug, not a triumph. (§8.5 disruption math + INV-2; FM-2 over/under-migration.)
  3. A client computes a different owner for the same key than its peer. Enumerate every place determinism can break, from hash seed to BTreeMap construction, and state the telemetry that isolates which one failed. (INV-1 + FM-3; Operational Readiness ring_version/hash_seed metrics.)
  4. BoundedRing with c=1.0 gives perfect balance. Explain precisely why you would almost never deploy it, and what failure mode appears under a burst. (§8.10 + INV-5; FM-5 forwarding storm; MM5.)
  5. Why is jump hash unusable for a cluster where nodes fail arbitrarily, yet ideal for a CDN shard tier that only ever scales out? Walk through what removing bucket 3 of 10 does to the key map. (§8.8 ordinal constraint + INV-7; FM-6; P9.)
  6. Maglev fills its table to ±1 slot per backend only when M is prime and skip≠0. Explain the number-theoretic reason, and what observable symptom appears if someone sets M=65536. (§8.9 permutation fill + INV-8; T7 collision; ADR-18.)
  7. A reader holds an arc-swap snapshot across a slow call while 50 membership changes occur. Is its locate result wrong? Is it stale? What is the memory consequence, and how is each addressed? (P6 + INV-10; Phase 12 §24 stale-Arc pitfall; FM-8.)
  8. locate_n(key, 3) must return 3 distinct physical nodes in 3 distinct zones, but the cluster has only 2 zones. What does the walk do, and which invariant tells you it is correct rather than a fault-isolation bug? (§8.4 zone fallback + INV-4; INV-3 distinctness; Phase 4 §16.)
  9. WeightedRendezvous uses -w/ln(h01). Why this formula and not w × hash? What determinism hazard does ln() introduce across platforms, and how is it bounded? (§8.7 + ADR-15; Compatibility Guarantees determinism contract; MM8.)
  10. The ring stores tokens in a BTreeMap, but Performance Engineering says a sorted Vec is faster to read. Under exactly what workload does the Vec win, and what does it cost on the write path? (ADR-08 + Performance Engineering BTreeMap-vs-Vec table; Back-of-Envelope #7.)
  11. A node is removed and fraction_moved comes back at 0.45 instead of ~0.10. Give the most likely root cause, the debugging method, and the property test that would have caught it. (FM-2 + INV-2; Phase 13 §25 disruption property; §8.5.)
  12. Explain why this library separates placement from replication transport, and what breaks in a caller that assumes locate_n guarantees the replicas are actually in sync. (P8 + §1.2 non-goals; INV-3; Comparative Architecture Table Dynamo row.)
  13. An attacker controls keys on a public XxHash64-backed cache and pins load on one node. Walk the full attack and the two independent defenses, and explain why one defense holds even if the other is bypassed. (§3.2 trust boundary + T1/T2; P5; MM10; §8.10 bounded-load cap.)
  14. Maglev rebuilds its entire table on every backend change; the ring splices incrementally. Quantify the cost difference at n=64, V=150 and explain why Maglev accepts the worse number. (Back-of-Envelope #4/#8 + §8.9; MM6; Scalability membership-change table.)
  15. Why does the project ship a ModuloHash that it explicitly forbids in production, and what single deployment condition would actually make modulo the right choice? (§8.5 + ADR-19; P9; Comparative Architecture Table.)
  16. A 200-node HRW cluster sees locate p99 climb to 5 µs. Give the two structural fixes, the threshold at which each applies, and the correctness property the faster one must still satisfy. (§8.6–8.7 + ADR-16; Back-of-Envelope #5; Scalability HRW bottleneck row.)
  17. The arc-swap writer panics mid-clone. What state is the ring left in, who detects it, and how does a reader in flight survive? (Phase 12 §24 failure analysis + INV-10; P6; Operational Readiness.)
  18. Two different node names hash to the same u64 token. What happens on the ring, how is it detected, and why is the probability acceptable up to n=10k? (§8.11 token collision + CLRS birthday analysis; INV-9; Phase 3 §15 pitfalls.)
  19. Ketama-compat mode breaks the no_std guarantee and uses MD5. Justify why the library offers it anyway, and the exact compatibility it does vs does not promise. (Compatibility Guarantees ketama section + ADR-22; §5.4 ketama format; Comparative Architecture Table ketama row.)
  20. Bumping vnodes_per_unit_weight from 150 to 200 is a breaking change requiring a coordinated rollout, but bumping capacity_factor from 1.25 to 1.5 is safe to do live.   21. DisruptionReport and DistributionReport are both computed from a key sample. Why must the sample be ≥100k keys for the disruption property test, and what statistical artifact appears if it is too small? (P4/P12 + Phase 5 §17 pitfalls; Back-of-Envelope #11; §8.3.)

Alternative Architectures (Roads Not Taken)

Alternative 1 — Rendezvous (HRW) as the sole strategy, no ring

Show the original text diagram
        keys
          |
          v
   for each node n: score = hash(n || key)
          |
          v
     argmax over all nodes  → owner
   (top-N by score          → preference list)
   no token ring, no BTreeMap, no vnodes

Regime where it wins: Small clusters (n ≤ ~100) where perfectly minimal disruption matters more than lookup cost, and weighting/zone-awareness can be folded into the score. HRW removes a node and re-homes exactly that node's keys with zero vnode noise — strictly better disruption than a vnode ring, and O(1) membership updates (just push/pop the node list).

Real system that embodies it: Used widely in client libraries and CDNs for cache-server selection; the Thaler & Ravishankar (1998) construction underlies many "rendezvous hashing" implementations and is the model for the rendezvous Rust crate.

Why this blueprint rejected it as the only strategy: O(n) per lookup is fatal above a few hundred nodes (Back-of-Envelope #5), and SkeletonHrw recovers O(log n) only by reintroducing a tree and slight imbalance. The ring gives O(log nV) lookups with mature zone-aware preference walks (Dynamo lineage). This library keeps HRW as a first-class strategy (Phase 7–8) but does not make it the universal one (P9).

Alternative 2 — Maglev-style lookup table for everything

Show the original text diagram
        backends ──► build dense table[M] via (offset,skip) permutation fill
                               |
        key ──► hash(key) % M ─┴─► table[idx] = backend   (O(1) read)
        membership change ──► rebuild entire table (O(M))

Regime where it wins: Read-dominated, membership-stable workloads — L4/L7 load balancing where every packet is a lookup and backends change once a minute. O(1) lookup at line rate and connection consistency are exactly what a software LB needs, and ±1-slot balance beats a vnode ring without tuning V.

Real system that embodies it: Google Maglev (Eisenbud et al., NSDI 2016), which fronts Google's services at hardware line rate.

Why this blueprint rejected it as universal: O(M) rebuild on every membership change is unacceptable when membership churns rapidly, and the table has no native weighting and no replication preference list — locate_n is unnatural (§8.9, MM6). For a general key-placement library serving stateful stores with replication and heterogeneous capacity, the ring/HRW family is the right default; Maglev ships as the specialized strategy (Phase 10).

Alternative 3 — Centralized shard directory (lookup service)

Show the original text diagram
   clients ──► query ──► Directory service (authoritative key→node map)
                              |  (explicit assignment table, e.g. range or hash buckets)
                              v
                         returns owner(s); directory rebalances explicitly
   placement is data in a coordinator, not a function of membership

Regime where it wins: When assignment must be arbitrary and explicitly controllable — pinning a hot tenant to dedicated hardware, honoring data-residency constraints, or doing manual rebalancing the operator fully controls. A directory can encode any mapping, not just hash-derived ones, and supports range queries the hash family cannot.

Real system that embodies it: TiKV's Placement Driver (PD) maintains an explicit region→store map; Bigtable/HBase use a metadata table (META) to locate tablets/regions. The mapping is stored state, not a hash function.

Why this blueprint rejected it: A directory is a coordinator — a consistency, availability, and scaling problem in its own right (the exact thing client-side consistent hashing avoids, MM1/MM8). It needs caching, invalidation, and its own failure handling, and the directory's metadata storm is a real failure mode (the AWS DynamoDB 20-Sep-2015 incident cited in FM-2). This library's whole premise is coordinator-free placement derived from membership (§1, P3); the directory model is the opposite design and belongs to a different project (e.g. sharding/metadata services 98/36).
