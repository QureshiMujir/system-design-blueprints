Decisions (§9) · 27 ADRs

ADR-01

Implementation language

Chosen

Rust 2021, MSRV 1.78

Rejected

Go, C++, Python

When the rejected choice is right

Go wins when the placement library must live inside an existing Go service (Kubernetes ecosystem) and ~µs GC jitter is tolerable; Python wins for a one-off analysis notebook where dev speed beats throughput

Why: Zero-GC hot-path latency; enums model strategy set; Placement trait gives uniform API; memory-safe concurrent ring mutation

ADR-02

Workspace structure

Chosen

Six chr-* crates in one Cargo workspace

Rejected

Monolith crate; separate repos

When the rejected choice is right

A single monolith crate wins for a closed-source internal lib never published to crates.io, where the crate-split overhead (6 Cargo.tomls, version sync) buys nothing

Why: Separate compilation; chr-core shared without pulling in ring/sim deps; consumers pick only needed crates

ADR-03

no_std + alloc for cores

Chosen

chr-core, chr-ring, chr-rendezvous, chr-alt are no_std + alloc

Rejected

std everywhere

When the rejected choice is right

std everywhere wins when the only deployment target is a server binary: it unlocks std::collections::HashMap SIMD, thread-locals, and simpler error handling at zero portability cost

Why: Embeddable in kernel modules, WASM, embedded routers; chr-sim and chr-cli use std (file I/O, threading)

ADR-04

Uniform placement API

Chosen

Placement trait (add_node, remove_node, locate, locate_n)

Rejected

Per-algorithm bespoke APIs

When the rejected choice is right

Bespoke per-algorithm APIs win when only ONE algorithm ships (e.g. a pure-Maglev L4 LB): the trait's &[u8] erasure and Vec return forfeit Maglev's u32 ordinal fast path

Why: Single abstraction for chr-sim cross-strategy comparison; CLI and router code unchanged when switching algorithm

ADR-05

Hasher abstraction

Chosen

Hasher64 trait; default XxHash64; option SipHasher64

Rejected

Hard-coded xxHash; std::hash::Hasher; SHA-256

When the rejected choice is right

A hard-coded single hasher wins when binary size is paramount (embedded): monomorphizing every strategy over H multiplies code size; one fixed hash collapses it

Why: std::hash is 64-bit but not stable for cross-process consistency; SHA is cryptographic = too slow; trait allows user-supplied hashers

ADR-06

Default hash function

Chosen

XxHash64 (xxhash-rust crate)

Rejected

SipHash, FNV, CityHash, SHA

When the rejected choice is right

SipHash wins as the default in any multi-tenant service where keys are end-user-controlled (T1 hot-spotting); SHA wins when placement must be auditable/reproducible against an external crypto spec

Why: Fastest non-cryptographic 64-bit hash with excellent avalanche and chi-square uniformity; well-maintained

ADR-07

Adversarial-resistance option

Chosen

SipHasher64 (keyed, k0+k1)

Rejected

ChaCha-based, SHA

When the rejected choice is right

A full ChaCha/SHA keyed hash wins when the threat model includes an attacker who can submit ~2^32 probe keys and observe placement — SipHash-1-3's reduced rounds are then insufficient

Why: Protects against hash-flooding key injection without full cryptographic cost; opt-in

ADR-08

Ring backing structure

Chosen

BTreeMap<u64, NodeId>

Rejected

Sorted Vec<u64> + binary search; skip-list

When the rejected choice is right

A sorted Vec + partition_point wins for read-heavy, write-rare rings (n×V > 100k tokens): contiguous layout cuts cache misses ~3× vs scattered B-tree nodes (see Performance Engineering tradeoff table)

Why: BTreeMap::range gives O(log n) successor with wrap-around in two lines; Vec requires unsafe index arithmetic; B-tree cache-friendly for n ≤ 10k

ADR-09

vnode default count

Chosen

vnodes_per_unit_weight = 150

Rejected

100, 500, 1000

When the rejected choice is right

V=500+ wins when n is tiny (3–5 nodes) and balance is critical (each node is expensive), where 1/sqrt(V) gains still matter; V=40 (ketama default) wins for libketama wire compatibility

Why: 150 gives std-dev < 10% of mean for n ≥ 3; 500 adds marginal gain at 3× memory cost; 100 tested as too imbalanced for n < 5

ADR-10

vnode weighting scheme

Chosen

V * weight tokens; Weight(u32) relative capacity

Rejected

Fractional token sizes; floating-point weights

When the rejected choice is right

Float weights win in WeightedRendezvous (ADR-15), where capacity ratios are non-integer (e.g. 1.0 : 1.7) and no token multiplication is involved — there the float score is the mechanism

Why: Integer multiplication avoids float non-determinism across platforms; token count is the exact weight knob

ADR-11

Token generation

Chosen

hash(node_name.bytes ++ replica_idx.to_le_bytes())

Rejected

hash(node_name) + replica_idx; UUID tokens

When the rejected choice is right

hash(name) + i*stride wins for ketama-compat mode, which extracts 4 tokens from one MD5 digest per replica block — a structural requirement of the wire format, not a free choice

Why: XOR/addition produces clustered tokens; concatenated bytes feed through full hash avalanche; deterministic from name alone

ADR-12

Preference-list zone awareness

Chosen

Optional ZoneId per node; skip-same-zone walk

Rejected

Always zone-aware; separate "rack" abstraction

When the rejected choice is right

Always-on zone awareness wins in a fixed multi-AZ deployment where every node has a known AZ and accidental same-AZ replication is a correctness bug worth the mandatory ZoneId

Why: Optional keeps no_std and simple cases clean; zone-skip is a 2-line filter in the walk; matches Dynamo semantics

ADR-13

Bounded-load capacity factor default

Chosen

capacity_factor = 1.25

Rejected

1.1, 1.5, 2.0

When the rejected choice is right

c=1.1 wins when load is the scarce resource and a few extra forward hops are cheap (uniform stateless backends); c=2.0 wins when forwarding is expensive (stateful sessions) and mild imbalance is acceptable

Why: 25% headroom covers typical load spikes with < 5% forwarding overhead; matches Mirrokni et al. §4 experiments

ADR-14

HRW score mixing

Chosen

hasher.hash_one(node_id.to_le_bytes() ++ key)

Rejected

XOR of two separate hashes; HMAC

When the rejected choice is right

Two-hash XOR mixing (h(node) ^ h(key)) wins when node hashes can be precomputed once and keys stream in: it saves re-hashing the node bytes per key in a tight HRW scan

Why: Single-pass hash of concatenated bytes; no correlation between (node, key) pairs; matches Thaler-Ravishankar spec

ADR-15

WeightedRendezvous formula

Chosen

score = -weight / ln(hash_to_unit_f64(node, key))

Rejected

score = weight * hash; linear weight multiplier

When the rejected choice is right

The linear weight * hash heuristic wins when exact proportionality is not required and float determinism across platforms is paramount — it avoids ln(), whose last-bit reproducibility is fragile

Why: Thaler-Ravishankar proof: -w/ln(U) maximizer gives load ∝ w in expectation; linear multiplier does not

ADR-16

SkeletonHrw fanout

Chosen

Default fanout f = 8; configurable

Rejected

f=2 (binary tree), f=n (flat)

When the rejected choice is right

Flat HRW (f=n) wins for n ≤ 16 where tree-traversal overhead exceeds the linear scan (enforced in SkeletonHrw::new); f=2 wins when per-level score cost is high and you want the fewest candidates scored per level

Why: f=8 gives O(3 levels) for n=512; f=2 too deep; flat HRW is O(n) which we're trying to avoid

ADR-17

Jump hash inclusion

Chosen

Included as JumpHash in chr-alt; ordinal constraint documented

Rejected

Excluded (too limited)

When the rejected choice is right

Excluding jump wins for a library whose sole target is arbitrary-membership rings with zone-aware replication — jump's ordinal-only API then adds a footgun (FM-6) with no matching use case

Why: Jump is the reference O(1)-memory algorithm; useful for stateless LB; its ordinal limitation is a documented non-goal for the ring use case

ADR-18

Maglev table prime M

Chosen

Default M = 65537 (prime); configurable

Rejected

M=65536 (power of 2), M=1009

When the rejected choice is right

M=1009 (small prime) wins when memory is tight and backend count is small (n ≤ 10): a 4 KB table fits L1, and balance within ±1 slot is still guaranteed for M ≫ n

Why: Must be prime for permutation coverage; 65537 >> typical n (≤ 1000) giving < 0.002% disruption per backend change; power-of-2 not prime

ADR-19

ModuloHash role

Chosen

Included as ModuloHash in chr-alt; baseline-only, not production

Rejected

Excluded

When the rejected choice is right

Modulo wins in production when the backend set is fixed forever (never scales): with constant n it has zero disruption, O(1) lookup, O(1) memory and beats every consistent scheme on simplicity

Why: chr-sim needs a worst-case baseline to quantify consistent hashing's disruption advantage; clearly labeled non-production

ADR-20

Lock-free read concurrency

Chosen

arc-swap (ArcSwap<HashRing>) for reads; RwLock for write serialization

Rejected

RwLock-only; seqlock; epoch-based reclamation

When the rejected choice is right

A plain RwLock wins for a single-threaded or low-concurrency embedding where reader count is small: it avoids arc-swap's per-read Arc clone and the stale-snapshot retention risk (Phase 12 pitfall)

Why: RwLock read-lock contention at high read throughput; seqlock unsound in safe Rust; arc-swap gives atomic snapshot swap — readers see consistent ring, no stall

ADR-21

Simulation metrics

Chosen

peak-to-mean, Gini coefficient, std-dev, fraction_moved

Rejected

Only std-dev; only peak

When the rejected choice is right

Tracking only peak-to-mean wins for an SLA dashboard where the single operational question is "is any node over headroom?"; Gini/std-dev add analysis value but no alerting signal there

Why: Gini captures tail skew that std-dev misses; peak-to-mean is operationally meaningful (SLA headroom); fraction_moved directly compares disruption

ADR-22

Ketama compatibility

Chosen

chr-ring output matches libketama MD5-based ring for same node set

Rejected

Custom token scheme only

When the rejected choice is right

A custom token scheme wins for a greenfield cluster with no legacy memcached clients: it frees the design from MD5's ~50 ns/token cost and the 40-vnode/4-token-per-digest structural constraint

Why: libketama is the de-facto memcached standard; compatibility vectors in Phase 13 catch regressions; requires MD5 hash mode toggle

ADR-23

Differential oracles

Chosen

libketama ring vectors; published jump-hash vectors; Eisenbud Maglev test vectors

Rejected

Unit tests only

When the rejected choice is right

Unit-tests-only wins for a novel strategy with no published reference implementation to diff against (e.g. an in-house variant) — there is then no oracle, and property tests carry the correctness load

Why: Cross-implementation agreement catches subtle algorithm bugs not caught by property tests alone

ADR-24

Fuzzing

Chosen

cargo-fuzz / libFuzzer targets on locate, add_node/remove_node, jump_hash, Maglev build

Rejected

Manual testing only

When the rejected choice is right

Manual/example-based testing wins for a frozen, pure-function kernel (e.g. jump_hash alone) whose input space is small and fully covered by published vectors — fuzzing then adds CI cost without new coverage

Why: Placement correctness (no panic, monotonicity, bounded-load) must hold for all byte inputs; fuzzing finds edge cases in token arithmetic

ADR-25

Benchmarks

Chosen

criterion for locate throughput (ns/op), distribution quality (Gini), disruption fraction

Rejected

std::time; custom harness

When the rejected choice is right

Ad-hoc std::time wins for a quick local sanity check during development where Criterion's multi-second warmup + statistical run is too slow for the edit-measure loop

Why: Criterion gives statistically stable micro-benchmarks with regression detection; CI fails if locate regresses > 10%

ADR-26

Dependency policy

Chosen

Minimal: xxhash-rust, arc-swap, criterion (dev); no hashring crate

Rejected

Pull in hashring, consistent crates

When the rejected choice is right

Pulling a mature hashring crate wins for a product team that needs a ring today and has no learning or differentiation goal — reuse beats reimplementation when the ring is a means, not the end

Why: We build the ring from scratch (this is the project); third-party ring crates would defeat the purpose and add version-pinning risk

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alternative 1 — Rendezvous (HRW) as the sole strategy, no ring

        keys
          |
          v
   for each node n: score = hash(n || key)
          |
          v
     argmax over all nodes  → owner
   (top-N by score          → preference list)
   no token ring, no BTreeMap, no vnodes

Regime where it wins: Small clusters (n ≤ ~100) where perfectly minimal disruption matters more than lookup cost, and weighting/zone-awareness can be folded into the score. HRW removes a node and re-homes exactly that node's keys with zero vnode noise — strictly better disruption than a vnode ring, and O(1) membership updates (just push/pop the node list).

Real system that embodies it: Used widely in client libraries and CDNs for cache-server selection; the Thaler & Ravishankar (1998) construction underlies many "rendezvous hashing" implementations and is the model for the rendezvous Rust crate.

Why this blueprint rejected it as the only strategy: O(n) per lookup is fatal above a few hundred nodes (Back-of-Envelope #5), and SkeletonHrw recovers O(log n) only by reintroducing a tree and slight imbalance. The ring gives O(log nV) lookups with mature zone-aware preference walks (Dynamo lineage). This library keeps HRW as a first-class strategy (Phase 7–8) but does not make it the universal one (P9).

Alternative 2 — Maglev-style lookup table for everything

        backends ──► build dense table[M] via (offset,skip) permutation fill
                               |
        key ──► hash(key) % M ─┴─► table[idx] = backend   (O(1) read)
        membership change ──► rebuild entire table (O(M))

Regime where it wins: Read-dominated, membership-stable workloads — L4/L7 load balancing where every packet is a lookup and backends change once a minute. O(1) lookup at line rate and connection consistency are exactly what a software LB needs, and ±1-slot balance beats a vnode ring without tuning V.

Real system that embodies it: Google Maglev (Eisenbud et al., NSDI 2016), which fronts Google's services at hardware line rate.

Why this blueprint rejected it as universal: O(M) rebuild on every membership change is unacceptable when membership churns rapidly, and the table has no native weighting and no replication preference list — locate_n is unnatural (§8.9, MM6). For a general key-placement library serving stateful stores with replication and heterogeneous capacity, the ring/HRW family is the right default; Maglev ships as the specialized strategy (Phase 10).

Alternative 3 — Centralized shard directory (lookup service)

   clients ──► query ──► Directory service (authoritative key→node map)
                              |  (explicit assignment table, e.g. range or hash buckets)
                              v
                         returns owner(s); directory rebalances explicitly
   placement is data in a coordinator, not a function of membership

Regime where it wins: When assignment must be arbitrary and explicitly controllable — pinning a hot tenant to dedicated hardware, honoring data-residency constraints, or doing manual rebalancing the operator fully controls. A directory can encode any mapping, not just hash-derived ones, and supports range queries the hash family cannot.

Real system that embodies it: TiKV's Placement Driver (PD) maintains an explicit region→store map; Bigtable/HBase use a metadata table (META) to locate tablets/regions. The mapping is stored state, not a hash function.

Why this blueprint rejected it: A directory is a coordinator — a consistency, availability, and scaling problem in its own right (the exact thing client-side consistent hashing avoids, MM1/MM8). It needs caching, invalidation, and its own failure handling, and the directory's metadata storm is a real failure mode (the AWS DynamoDB 20-Sep-2015 incident cited in FM-2). This library's whole premise is coordinator-free placement derived from membership (§1, P3); the directory model is the opposite design and belongs to a different project (e.g. sharding/metadata services 98/36).
