In one paragraph

When data is spread over many servers, every request needs an answer to "which node owns this key?", and the answer should barely change when a node joins or leaves (§1, P1). This design is a Rust library that answers it with five strategies behind one Placement trait: a consistent hashing ring, rendezvous (HRW) hashing, jump hash, Maglev, and a modulo baseline (§1). A simulation harness measures and compares them all (§1). It is not the data store itself (§1.2). Its users are engineers building sharded caches, key-value stores and load balancers, who embed it as a library, a CLI or an in-process router (§1.3).

The problem, concretely

The obvious way to place keys is hash(key) % n. Say you run 10 cache nodes and add an 11th. A key stays put only when hash % 10 equals hash % 11, which happens with probability about 1/(n+1), so a fraction n/(n+1) of all keys move (§8.5). For N = 10 and K = 1,000,000 keys a consistent scheme moves about 100,000 keys and modulo about 909,000, roughly 9 times the cache churn: "the entire reason the library exists" (Capacity model item 1). Get it wrong and cache hit rates collapse and affinity breaks for nearly all users (P1).

Moving few keys is not enough. Four more problems show up once you try the cure:

  • Imbalance. With one point per node on the ring, Appendix B expects a peak-to-mean ratio above 2.0 for 10 nodes, while Phase 2 documents at least 1.5 and asserts only above 1.0; that naive phase exists to motivate the fix (Appendix B, §14).
  • Replicas on the same box. Replicas need distinct nodes, ideally distinct zones, or one rack failure takes all copies (I3, I4, T4).
  • Agreement without a coordinator. Clients route on their own, so they must all compute the same owner, or both miss the data (P3, FM-3, MM8).
  • Hostile keys. An attacker who controls keys can aim at one token and pin load on one node (T1).

How it works, end to end

The blueprint's overview diagram (§3.1), lightly shortened, drawn and coloured by role:

Follow one locate call and one membership change through the boxes:

  1. Caller and trait. A router calls locate, locate_n, add_node or remove_node on Placement, which chr-core defines for every strategy along with NodeId, Key, Weight and PlacementError (§3.3, §11, ADR-04, P2).
  2. Hasher. Key bytes become a 64-bit number through Hasher64: XxHash64 by default, keyed SipHasher64 for untrusted keys (§3.3, ADR-05, ADR-06, ADR-07, P5).
  3. Strategy. HashRing (chr-ring) keeps tokens in a BTreeMap<u64, NodeId> and finds the first token at or after the key's hash (§3.3, §8.2). Rendezvous (chr-rendezvous) scores every node (§8.6). In chr-alt, JumpHash needs no node names and Maglev answers with one table read (§3.3). ModuloHash is the baseline, never for production (§3.3, ADR-19).
  4. Replicas and caps. locate_n walks clockwise into a PreferenceList (§8.4). BoundedRing wraps HashRing with per-node load counters and forwards past full nodes (§3.3, §8.10).
  5. Membership. The library knows nothing about gossip; the caller says when to add or remove (P13, §1.2). A ring change touches only that node's tokens (§3.3, I11).
  6. Live embedding. LiveRing (Phase 12) builds the new ring off to the side and publishes it with ArcSwap::store, so readers see the old ring or the new one whole, and each snapshot has a larger epoch (§24, I10, I12, MM9). Nothing is persisted: restart replays the membership (§3.2, MM1).
  7. Measurement. chr-sim returns a DistributionReport and a DisruptionReport; chr-cli (chring) exposes locate/add/remove/distribute/churn/compare/bench (§3.3, §1.4).

The core ideas

The ring: the first token clockwise owns the key (§8.2, §8.5)

Picture the whole 64-bit hash space bent into a circle. Each node gets a point on the circle, a token, computed as hash(name ++ replica_idx) (§8.2). A key is hashed to a point and belongs to the first token at or after it, wrapping to the smallest token at the end (successor, §8.2).

The blueprint's trace has three nodes with tokens N1 = 0x1A00, N2 = 0x5500, N3 = 0xCC00 (§8.2):

Key Hash First token at or after it Owner
"foo" 0x3F00 0x5500 N2
"bar" 0xEE00 none, wrap to 0x1A00 N1

§8.5 says that adding a node M between tokens A and B reassigns only the keys in the arc (A, B], which used to belong to B. Under §8.2's rule only the part (A, M] changes owner, since keys after M still reach B first (§8.2, §8.5). The expected arc is about 1/n of the ring, so about 1/n of keys move, which the blueprint calls the minimum (§8.5). The floor comes from pigeonhole: any scheme must move at least K/(N+1) keys when the (N+1)-th node arrives, and a measured 0.0 on an add means the measurement is wrong (§8.5, MM4).

The blueprint's before/after example, adding N4 at token 0x0300, contradicts its own lookup rule. It prints "key 0x0500 moves N1→N4 (new token 0x0300); 0x2000/0x5800/0xDD00 stay on N1/N2/N3" and "Only the arc (0xCC00, 0x0300] (wrapping) moves to N4" (§8.5). Under §8.2's rule 0x0500 is above the new token and stays on N1, 0x2000 belongs to N2 and 0x5800 to N3, and 0xDD00 (N1's by wrap-around) lies inside the stated arc and moves to N4. Only the arc sentence agrees (§8.2, §8.5).

Virtual nodes and weights: smoothing the load (§8.3, I11)

With one token per node the arcs are very unequal. Giving each node V tokens, virtual nodes (vnodes), makes each node's share a sum of many gaps, and the relative spread falls as 1/sqrt(V) (§8.3). For n = 10 the blueprint gives std-dev/mean and peak-to-mean of about 1.0 and 3x to 10x at V = 1, 0.14 and 1.3x at V = 50, 0.08 and 1.1x at V = 150, and 0.045 and 1.05x at V = 500 (§8.3). Doubling V cuts imbalance by about 1.41x, not 2x, and returns diminish past V of about 150 (MM2). A node with Weight(w) gets V times w tokens, so a Weight(3) node at the default V = 150 gets exactly 450 tokens (§8.3, ADR-10, §15). The count is meant to be exact, since an off-by-one is a permanent imbalance (I11), yet Phase 3 also caps one node at 65,536 tokens, so a very large weight cannot get V times w (§15).

The preference list: walk clockwise, skip repeats (§8.4, I3, I4)

For locate_n(key, N), start at the key's token and walk clockwise. Skip a token whose node is already chosen. In zone-aware mode also skip a node whose zone is already used while unused zones remain. Stop at N nodes or when the ring is exhausted (§8.4).

The blueprint's trace: 6 nodes in 3 zones, N = 3, sorted tokens 0x10 N1(A), 0x20 N3(B), 0x30 N1(A) skipped, 0x40 N5(C), then 0x50 N4(B), 0x60 N2(A) and 0x70 N6(C) skipped. From key token 0x05 the result is [N1, N3, N5], one per zone (§8.4).

With fewer zones than N it falls back to distinct nodes only, and with fewer nodes than N it returns a shorter list (§8.4, I3). The length rule is stated two ways: I3 returns min(n, num_nodes) nodes and Phase 4 fills the rest from any zone when zones are fewer than N, while T4's invariant result.len() == min(n, distinct_zones) caps the list at the number of zones (I3, §16, T4).

Rendezvous hashing: the highest score wins (§8.6, §8.7)

Instead of a circle, score every node against the key, score = hash(node ++ key), and give the key to the highest one (rendezvous or HRW, highest random weight). Ties go to the lower NodeId (§8.6, I6). locate_n takes the top N scores (§8.6).

The blueprint's trace for key "session-xyz" has scores N1 = 0xF3.., N4 = 0xD1.., N2 = 0xA8.. and N3 = 0x55.., so locate gives N1 and locate_n(2) gives [N1, N4] (§8.6). If N1 is removed, only keys for which N1 was the highest move, each to its next-highest node; the moved fraction is N1's load divided by K, about 1/n, with no vnode noise (§8.6, MM3). The cost is that every lookup scores all n nodes (§8.6).

Weighted rendezvous uses score = -weight / ln(h01), where h01 is the hash scaled into (0, 1), so load follows weight (§8.7, ADR-15). SkeletonHrw arranges nodes in a tree with fanout f = 8 and scores only the children of the winning parent at each level, giving about O(f times log_f n) instead of O(n), at the price of slight imbalance (§8.7, ADR-16).

Bounded load: a cap and a forward step (§8.10, I5)

BoundedRing gives every node a cap of ceil(c * avg_load), with c = 1.25 by default, so no single node saturates (§8.10, ADR-13, P10). The steps: (1) find the clockwise successor as in HashRing::locate; (2) if its load is under the cap, increment its counter and return it; (3) otherwise move to the next distinct physical node clockwise and repeat; (4) once every node has been visited, return PlacementError::CapacityExceeded (§8.10, T5).

The guarantee is max_load <= ceil(c * total / n), since if every node were full the total would exceed c times the total, a contradiction (§8.10, I5). Smaller c balances better but forwards more: 1.0 is perfect balance with many hops, 1.25 forwards rarely, 2.0 very rarely (§8.10). The blueprint sees this as a tail-latency lever, not an average-balance feature (MM5, P10).

Two things disagree. §8.10 gives locate(&mut self) -> Result<NodeId, PlacementError> (it bumps a counter), but the shared trait has locate(&self) -> Option<NodeId> (§8.10, §11). The walk's bound is each node once (§8.10), ring.len() iterations (FM-5), or max_forward=2n (Performance Engineering).

Jump hash and Maglev: no ring at all (§8.8, §8.9)

Jump hash (Lamping-Veach) maps (key, num_buckets) to a bucket number using only a small random-number recurrence, so it needs O(1) memory and no node names (§8.8, MM7). The blueprint's trace for key 42 and 5 buckets says the running bucket b goes -1 to 0 (j = 1), to 1 (j = 3), to 3 (j = 4), and stops when j = 7 exceeds 5, giving bucket 3 (§8.8). That trace does not follow the §5.4 recurrence, which sets b to every j below the bucket count: after j = 4 the loop would run once more and end at b = 4 (§5.4, §8.8). The price of jump hash is ordinal buckets 0 to n-1: add or remove only at the tail. Removing bucket 3 of 10 shifts the ordinals and wrecks the mapping (§8.8, MM7, FM-6).

Maglev builds a lookup table of prime size M. Each backend has an offset and a skip, and visits slots (offset + j * skip) % M. Backends take turns claiming their next free slot until the table is full (§8.9). The blueprint's trace has M = 7 and backends B0 (3, 4), B1 (0, 2), B2 (1, 5) as (offset, skip). Round 1 claims slots 3, 0, 1; round 2, skipping taken slots, claims 4, 2, 6; round 3 fills slot 5, giving [B1, B2, B1, B0, B0, B0, B2]; a lookup is lookup[hash % 7] (§8.9). A prime M with skip != 0 makes every backend's sequence visit all slots, so the table always fills and each backend gets floor or ceiling of M/n slots (§8.9, I8, MM6). A backend change moves about M/n slots, about 1/n of keys (§8.9).

The trade-offs — where engineers disagree

One trait for every strategy (ADR-04)

Chosen: a single Placement trait with add_node, remove_node, locate and locate_n, so the harness can compare strategies and the CLI and router code do not change when you switch (§9). Rejected: a bespoke API per algorithm (§9). When the rejected choice is right: when only one algorithm ships, such as a pure-Maglev L4 balancer, because the trait's &[u8] erasure and Vec return give up Maglev's u32 ordinal fast path (§9).

Fast default hash, keyed hash as an option (ADR-06, ADR-07)

Chosen: XxHash64 as the default, the fastest non-cryptographic 64-bit hash with good uniformity, and an opt-in keyed SipHasher64 against hash-flooding (ADR-06, ADR-07, P5). Rejected: SipHash, FNV, CityHash or SHA as the default (ADR-06); a ChaCha-based or SHA keyed hash as the hardened option (ADR-07). When the rejected choice is right: SipHash should be the default in any multi-tenant service where keys are end-user-controlled (T1 hot-spotting), and SHA wins when placement must be auditable against an external crypto spec (ADR-06). A full ChaCha or SHA keyed hash wins when an attacker can submit about 2^32 probe keys and observe placement, as SipHash-1-3's reduced rounds then fall short (ADR-07).

An ordered tree for the ring (ADR-08)

Chosen: BTreeMap<u64, NodeId>, because range gives the successor with wrap-around in two lines and avoids unsafe index arithmetic (§9). Rejected: a sorted Vec with binary search, or a skip list (§9). When the rejected choice is right: a sorted Vec with partition_point wins for read-heavy, write-rare rings above 100k tokens, where contiguous memory cuts cache misses about 3 times (§9). The cost is that adding or removing a token shifts the array in O(n) (Performance Engineering).

150 virtual nodes per unit weight (ADR-09)

Chosen: vnodes_per_unit_weight = 150, which gives a standard deviation under 10% of the mean for n of 3 or more, while 500 adds little at 3 times the memory (§9). Rejected: 100, 500 or 1000 (§9). When the rejected choice is right: V = 500 or more wins when n is tiny (3 to 5 nodes) and balance is critical; V = 40, the ketama default, wins when you need libketama wire compatibility (§9).

A 25% load cap (ADR-13)

Chosen: capacity_factor = 1.25, enough headroom for typical spikes with under 5% forwarding overhead, matching Mirrokni et al. (§9, Capacity model item 10). Rejected: 1.1, 1.5 or 2.0 (§9). When the rejected choice is right: c = 1.1 wins when load is the scarce resource and extra hops are cheap (uniform stateless backends); c = 2.0 wins when forwarding is expensive (stateful sessions) and mild imbalance is acceptable (§9). Too tight a c, such as 1.01, is how FM-5 starts (FM-5).

Lock-free reads with arc-swap (ADR-20)

Chosen: ArcSwap<HashRing> for readers and a RwLock only to serialize writers, so readers never stall on a write and always see a consistent ring (§9, P6). Rejected: a plain RwLock, a seqlock, or epoch-based reclamation (§9). When the rejected choice is right: a plain RwLock wins for a single-threaded or low-concurrency embedding, because it skips the per-read Arc clone and the risk of a snapshot being kept alive (§9).

Roads not taken

Rendezvous as the only strategy (Alternative 1) wins for small clusters, up to about 100 nodes, where perfectly minimal disruption matters more than lookup cost; there a membership update is just a list push or pop. It lost as the sole strategy because O(n) lookup becomes fatal above a few hundred nodes, and SkeletonHrw only recovers speed by bringing back a tree (Alternative 1, Capacity model item 5).

A Maglev-style table for everything (Alternative 2) wins for read-dominated, membership-stable work such as L4 load balancing, where every packet is a lookup and backends change about once a minute. It lost because every membership change rebuilds the whole table, and it has no native weighting or replica list (Alternative 2, §8.9, MM6).

A central shard directory (Alternative 3) wins when assignment must be arbitrary and explicitly controlled, such as pinning a tenant to dedicated hardware or meeting data-residency rules, and it can answer range queries, as in TiKV's Placement Driver. It lost because a directory is a coordinator, which is exactly what client-side hashing avoids (Alternative 3, MM1, MM8).

Deferred features wait for triggers (Deferred register): skeleton fanout tuning past 10k HRW nodes (§8.4), seed rotation after a crafted-key hot spot (§1.2, T1), membership-change callbacks once a downstream system must react to exact moved ranges, and disk snapshots if rebuild-on-start is a measured bottleneck (§3.2).

What must never be false

The blueprint names these INV-1 to INV-12; they are written I1 to I12 here.

  • I1: the same nodes, weights and seed give the same owner on any host. Noticed by a differential test (two forks, 100k locates, 0 disagreements) and the epoch or membership hash logged at build.
  • I2: one add or remove moves at most w/(total_weight + w) of the keys. Noticed by fraction_moved <= theoretical_min + epsilon (epsilon at most 0.01) in each DisruptionReport.
  • I3, I4: locate_n(k, n) returns min(n, num_nodes) distinct nodes, in distinct zones when zones are at least n. Noticed by property tests, a debug assert and PreferenceList.zone_spread.
  • I5: no node's load exceeds ceil(c * total / n). Noticed by per-node load counters and peak_to_mean, warning at 0.9 times c.
  • I6: rendezvous ownership ignores node-list order; ties go to the lower NodeId. Noticed by a 100-shuffle property test and debug logs of (node, score).
  • I7: jump_hash(key, n) is always in [0, n). Noticed by exhaustive small-n tests and a debug assert with no release cost.
  • I8: after a Maglev build no slot is empty and each backend holds floor or ceiling of M/n slots. Noticed by a post-build scan and the chr-sim standard deviation (at most 1.0 slot).
  • I9, I11: every ring token maps to a live node (removal leaves zero tokens for that id), and add_node(id, Weight(w)) leaves exactly V times w tokens. Noticed by a post-remove scan, a 100-pair token-count property test, the rebuild logs and HashRing::vnode_count(id).
  • I10: an in-flight locate never sees a half-applied change. Noticed by an 8-reader, 2-writer stress test and an epoch counter per swap.
  • I12: the LiveRing epoch strictly increases with each published snapshot. Noticed by a 1000-operation property test and the epoch gauge.

What breaks in production

FM-1, a hot node (S2). Symptom: peak_to_mean above 1.5. Cause: too few vnodes (V under 50), a weak hash or skewed keys. Detection: chr-sim after every change, alerting above 1.3. Recovery: BoundedRing caps and forwards automatically; by hand, raise V from 100 to 200, switch to SipHasher64, or tune weights (FM-1).

FM-2, over-migration on churn (S1). Symptom: fraction_moved far above 1/N. Cause: a token insert or delete bug (a full rebuild re-homes about 50% instead of about 1/N) (FM-2). Detection: assert!(fraction_moved <= 1.5/N) and an owner-map diff before and after. Recovery: there is no automatic one; pin the prior ring version, diff token ranges, roll back and patch (FM-2). The blueprint cites the AWS DynamoDB 20 Sep 2015 incident, where a network blip made a fleet re-request partition metadata at once, as why one change must not trigger fleet-wide reassignment (FM-2, T3).

FM-3, split routing (S1). Symptom: hosts compute different owners for one key, so data looks missing. Causes: seed skew, a ring-version mismatch or float non-determinism. Detection: a cross-host determinism test and the ring_version and hash_seed metrics (FM-3, Operational Readiness). Recovery: broadcast the canonical seed and epoch; clients compare epochs before routing (FM-3, I1).

FM-5, a forwarding storm (S2). Symptom: locate latency spikes, forward chains longer than 3 and CapacityExceeded errors. Cause: c too tight, for example 1.01, plus a burst. Recovery: raise c (1.25 is the default) or add nodes; the walk always terminates (FM-5, T5).

FM-10, a token collision (S3). Symptom: one node gets almost no keys, because two names hashed to the same u64 token and the second insert overwrote the first. Detection: ring.len() below the expected token sum, or a vnode_count of 0. Recovery: detect at add_node and return a PlacementError or take last-write-wins by NodeId, or change the hasher seed. The probability is about n squared over 2^64 and the blueprint calls that acceptable up to n = 10k (FM-10, §8.11, I11).

Threats worth knowing:

  • T1, key hot-spotting from crafted keys that land near one token, is met by SipHasher64 with a secret seed plus the BoundedRing cap; detection is a peak_to_mean alert (T1, MM10).
  • T3, membership-churn amplification (rapid add and remove forcing mass migration), is bounded by caller rate limits and minimal disruption; detection is a fraction_moved spike (T3).
  • T5, a bounded-load forwarding loop, is stopped by bounding the walk by ring size; detection is forward-chain length, alerting above 3 hops (T5).

  • Chi-square. §4 says p above 0.05, Phase 1 says chi-square under 330 (p = 0.001), Appendix B and the glossary say p above 0.01, and T2 rejects below p = 0.01 (§4, §13, T2).
  • Jump cost. §4 says about 30 iterations at n = 1000, Phase 9 about 20, the capacity model about 7 (§4, §21, Capacity model item 6).
  • Speed. §4 puts 100 HRW nodes at 1 to 5 microseconds, yet Phase 13 wants at least 5M ops/s for 100 nodes; Maglev is under 20 ns in §4, 30 ns in M4 and 5 ns in Phase 10 (§4, §25, §22).
  • Timeline. §1.7 says about 3.5 months; Appendix B totals about 48 days (about 10 weeks relaxed, about 6 focused) (§1.7, Appendix B).

How it compares

  • Amazon Dynamo / DynamoDB made vnodes and preference lists standard, and ties placement to availability tricks (sloppy quorum, hinted handoff) so an overloaded node is routed around at the data layer. That suits an always-writable store; this design separates placement from replication (P8) so one ring can serve stores with different durability choices (Comparative table).
  • Apache Cassandra inherits the ring but defaults to 256 tokens, Murmur3 and rack-aware snitches, and runs it inside a garbage-collected JVM. That is right for a batteries-included store with mature tooling that can absorb JVM tail latency; this design uses zero-GC Rust and an off-path arc-swap rebuild (Comparative table, ADR-01, ADR-20).
  • Ketama / libketama uses a sorted array ring with 40 vnodes per server, MD5 tokens and a global mutex. That is right when wire compatibility with an existing memcached client fleet is mandatory, which is why this design offers a ketama-compatible mode (Comparative table, ADR-22).
  • Google Maglev uses a dense lookup table, O(1) per packet, with a full O(M) rebuild on any change. That is right where reads dominate membership changes by orders of magnitude and weighting is not needed, as in L4 load balancers (Comparative table, MM6).

Questions to test yourself

  1. Adding the (N+1)-th node moves at least K/(N+1) keys by pigeonhole. The ring moves ~K/N. Reconcile these two numbers and explain why a measured fraction_moved of 0.0 on an add is a bug, not a triumph. — Hint: §8.5 and MM4, then I2 and FM-2.
  2. BoundedRing with c=1.0 gives perfect balance. Explain precisely why you would almost never deploy it, and what failure mode appears under a burst. — Hint: §8.10, MM5 and FM-5.
  3. Maglev fills its table to ±1 slot per backend only when M is prime and skip≠0. Explain the number-theoretic reason, and what observable symptom appears if someone sets M=65536. — Hint: §8.9 with I8, then MM6 and ADR-18.
  4. A node is removed and fraction_moved comes back at 0.45 instead of ~0.10. Give the most likely root cause, the debugging method, and the property test that would have caught it. — Hint: FM-2 and I2, then Phase 13 in §25.
  5. A reader holds an arc-swap snapshot across a slow call while 50 membership changes occur. Is its locate result wrong? Is it stale? What is the memory consequence, and how is each addressed? — Hint: P6, I10, FM-8 and the Phase 12 pitfalls in §24.

If you only remember three things

The ring is a pure function of membership, never stored state, so every client that has the same nodes, weights and seed agrees without a coordinator (MM1, I1, P3). Any placement scheme must move at least K/(N+1) keys when a node is added, and the whole value of this family is staying near that floor where modulo moves nearly everything (MM4, §8.5). Pick the algorithm by constraint (jump for tail-only ordinal buckets, Maglev for O(1) load-balancer lookups, HRW for exact minimal disruption, the ring for zones and replicas) and measure balance instead of assuming it (P9, P4).

Words used here

  • Token: a 64-bit point on the ring assigned to a node; keys go to the first one at or after them (§8.2, Glossary).
  • Successor: the first token at or after a key's hash, wrapping around at the end (§8.2, Glossary).
  • Virtual node (vnode): one of many tokens a physical node owns, to even out load (§8.3, Glossary).
  • Preference list: the ordered, distinct nodes a key's replicas go to (§8.4, Glossary).
  • Rendezvous (HRW): give the key to the node with the highest hash(node ++ key) (§8.6, Glossary).
  • Peak-to-mean: the busiest node's load divided by the average, the main balance metric (Glossary).
  • Bounded load: a cap of ceil(c * avg) on every node, enforced by forwarding (§8.10, Glossary).
  • Jump hash: Lamping-Veach bucket choice with O(1) memory and ordinal buckets only (§8.8, Glossary).
  • Maglev: a prime-sized lookup table filled by per-backend permutations (§8.9, Glossary).
  • Epoch (ring version): a counter that rises with each published membership change (I12, Glossary).
