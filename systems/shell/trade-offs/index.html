ADR-01

Implementation language

Chosen

Rust 2021, MSRV 1.76

Rejected

C, Go, Zig

When the rejected choice is right

C wins when the team's sole expertise is C and zero build-toolchain risk is non-negotiable (e.g. bootstrapping in a minimal initramfs)

Why: ownership model makes FD/pointer lifetimes compile-checked without losing C-class perf (P14)

37. Alternative Architectures (Roads Not Taken)

AA-1 — Bytecode VM instead of tree-walking interpreter.

AST ──compile──▶ Bytecode ──▶ VM dispatch loop ──▶ effects
(this design skips the middle step: AST ──walk──▶ effects, §8.4)

Regime where it wins: scripts executed many times per second in a hot loop where compile-once/run-many amortizes the compilation cost (e.g., a templating engine calling the same shell function thousands of times). Real system: Tcl's tclsh compiles scripts to an internal bytecode representation before execution. Rejected because: this project's dominant cost is fork+exec latency (§4), not AST-walk dispatch overhead — a bytecode compiler adds a whole subsystem (compiler, verifier, VM) to shave a cost that isn't the bottleneck, and it complicates the arena-lifetime story (P10, MM5) since bytecode would need its own separate memory model.

AA-2 — posix_spawn/vfork instead of fork+execve.

this design: fork() [copy address space] → execve() in child
alternative: posix_spawn() [kernel-assisted, no full copy] → running child directly

Regime where it wins: workloads dominated by process-creation latency on a system where fork's copy-on-write setup (page-table duplication) is measurably expensive relative to execve — high-pipeline-fan-out scripts on memory-constrained hosts. Real system: dash uses vfork() as an optimization for the last command in certain simple pipelines. Rejected because: fork+execve gives the executor full control over the child's file descriptors and process-group state before the exec (§8.4 step 5, P7's job-control arbiter needs this window); vfork's shared-address-space window until execve is a correctness hazard for a design this dependent on precise FD/pgid setup.

AA-3 — readline-based instead of a custom line editor.

this design: crates/editor (custom termios+buffer+render, §20.2)
alternative: bind against GNU readline / libedit

Regime where it wins: a project whose interactive surface is a secondary concern and wants maximum keymap compatibility with existing .inputrc configuration with minimal engineering investment. Real system: bash binds directly to GNU readline (lib/readline/). Rejected because: this project's conformance harness requires PTY-level control over exact render output (ADR-05) and vi-mode parity testing that a third-party library's internals do not expose cleanly; P13 (separable line editor) requires an implementation this project fully controls.

AA-4 — A regular, LALR-friendly grammar instead of POSIX's irregular one.

this design: recursive descent over POSIX's grammar, irregular at
             here-docs / $() / quoting (§8.2, ADR-02)
alternative: a shell language designed from scratch to be table-parseable

Regime where it wins: designing a new shell language unconstrained by POSIX compatibility, where here-document and command-substitution syntax can be chosen to be regular from day one. Real system: rc (Plan 9, Duff 1990, §5 Required Reading) deliberately redesigned shell syntax to avoid these irregularities. Rejected because: this project's goal is POSIX conformance (P1, §1.1) — a cleaner grammar that isn't POSIX is a different project; every irregularity this design routes around (here-doc deferred read, $() reparse) is a POSIX section 2.10 requirement, not an implementation accident (MM7).
