Hard questions (§36)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why is the lexer a tagged state machine over five contexts rather than a single regular-expression tokenizer, and what real fixture would break the regex version first? (§8.1, §13.6)
  2. Trace exactly which of the eight expansion stages fires, and in what order, for ${var:-$(cmd)} where var is unset. (§8.3, §16.6)
  3. Why does the executor never serialize the AST across fork(), and what bug class would reappear if it did? (§8.4, P6, §17.2)
  4. Derive, from the System Constraints table, why a 10-stage pipeline's total fork+exec overhead must stay under roughly 4 ms — and what dominates that budget. (§4, §17.2, Back-of-Envelope Capacity Model row 3)
  5. Explain the exact sequence of tcsetpgrp calls and SIGTTOU self-ignoring that happens when a foreground pipeline is suspended with Ctrl-Z and later resumed with fg. (§8.5, §18.2)
  6. Why must both the parent and the child call setpgid after fork, and what race would appear if only the parent did? (I5, §8.5, §18.6)
  7. What specific POSIX section 2.11 contexts cause set -e to not abort the shell, and how does that table relate to the built-in "special vs. regular" distinction in Phase 3? (I9, §15.2, §17.6)
  8. Why is the AST arena-allocated per parse rather than reference-counted, and what does the Back-of-Envelope Capacity Model say about the cost difference? (§9, §11.3, Back-of-Envelope Capacity Model row 1)
  9. What makes a signal handler in this design "safe," and why would writing a log line inside one be a correctness bug rather than a style issue? (P8, I7, §18.2, §18.9)
  10. Compare this design's job-table reaping strategy to what waitid(P_PIDFD, ...) would change, and at what job count does that change start to matter? (§11.5, §18.2, Scalability Analysis, Back-of-Envelope Capacity Model row 6)
  11. Why is Mode::Enhanced a strictly additive, opt-in layer rather than a set of always-on convenience features, and what principle does that enforce? (P1, P2, §11.6, §23.1)
  12. Explain why history expansion (!!, !$) runs before quoting, and what user-facing surprise that ordering causes. (§21.2, §21.6)
  13. Why does restricted mode (osh -r) explicitly not count as a security boundary, and what threat does it actually mitigate? (I12, §7, Threat Model T5, §22.2)
  14. Derive the job-control practical ceiling from the reaper's per-job cost and the cold-start latency budget. (§4, §18, Back-of-Envelope Capacity Model row 6, Scalability Analysis)
  15. Contrast this design's recursive-descent parser with a Bison/LALR alternative: name the exact grammar irregularity that makes recursive descent the right call. (ADR-02, §8.2, §14, Alternative Architectures AA-4)
  16. Why does command substitution $(...) fork a real subshell rather than optimizing "no side effects" cases into the parent process? (§8.4, §16.2, P6)
  17. What is the concrete difference between a subshell (( ... )) and a function call in terms of process boundary, and why does conflating them cause bugs? (§17.6, §11.4)
  18. Why is $RANDOM seeded from /dev/urandom rather than a fixed seed, and how does that interact with the determinism principle (P12)? (§6, Threat Model T12, §19.9)
  19. Explain the two-phase relationship between Mode::Bash's always-additive AST/token variants and the SemVer policy's MAJOR-version trigger. (§11.1, §11.3, Compatibility & Versioning)
  20. Why does the design reject posix_spawn/vfork as the default execution primitive, and under what regime would that rejected choice actually win? (§9, §17.2, Alternative Architectures AA-2)

33. Mental Models & First Principles

MM1 — The lexer's job is to defer, not decide. Compressed insight: a token is a promise to interpret bytes a certain way given a context, not a final classification; "is if a keyword" is answered by the parser's command-start flag, not the lexer alone. Predicts: any shell bug where a keyword works "everywhere except..." is a context-sharing bug. Bug class without it: hardcoding reserved-word recognition purely lexically. Applied in §13 (Phase 1), §14.6.

MM2 — Expansion is a pipeline of pure functions over an ordered list, not a rewrite loop. Compressed insight: each of the 8 stages (§8.3) consumes the previous stage's output type, never re-visits an earlier stage's input. Predicts: any "double expansion" bug (a value expanded twice) is a stage-boundary violation. Bug class without it: naive "expand until fixed point" implementations that silently double-substitute attacker-controlled data (Threat Model T2). Applied in §16.

MM3 — A process group is a scheduling unit for signals, not for output. Compressed insight: tcsetpgrp decides who receives keyboard-generated signals, and is orthogonal to which process's stdout reaches the terminal (that's just inherited FDs, §8.4). Predicts: "backgrounded job stole my prompt" bugs are terminal-arbitration bugs, not FD-inheritance bugs. Bug class without it: conflating output correctness with signal correctness while debugging job control. Applied in §18, §8.5.

MM4 — A signal handler is not code, it is a wakeup. Compressed insight: the only async-signal-safe thing to do in a handler is note that something happened (P8); all actual work happens in the main loop after the fact. Predicts: any handler doing allocation/logging/locking is a latent heisenbug. Bug class without it: intermittent crashes only reproducible under signal load. Applied in §18.2, I7.

MM5 — An arena is a lifetime, not just an allocator. Compressed insight: bump-arena allocation (ADR-04) buys performance because it encodes "these nodes die together" as a type-level fact (I8), not merely because bumpalo::alloc is fast. Predicts: any attempt to keep an AST node alive past its script's execution needs an explicit re-architecture, not a workaround. Bug class without it: use-after-free attempts in languages without Rust's borrow checker (the historical C-shell bug class this design sidesteps). Applied in §11.3, Back-of-Envelope row 3.

MM6 — set -e is a contract about contexts, not a global flag. Compressed insight: POSIX section 2.11 lists exact syntactic positions where a non-zero status is "swallowed"; set -e is not "exit on any error," it is "exit on error, except in these named positions." Predicts: every "why didn't set -e catch this" bug reduces to identifying which swallow-context applies. Bug class without it: re-deriving the rules ad hoc per bug report instead of consulting one table. Applied in §17.6, I9.

MM7 — The grammar's irregularity is the spec, not a parser bug. Compressed insight: here-document deferred-read and command-substitution reparse are not implementation compromises — they are what POSIX section 2.10's grammar actually requires structurally (hence recursive descent over LALR, ADR-02, P4). Predicts: attempts to "clean up" the grammar into a regular one will silently break real scripts. Bug class without it: a from-scratch reimplementation that "simplifies" here-doc handling and breaks cat <<EOF | wc-class scripts. Applied in §14, §8.2.

MM8 — Determinism is a design choice, not a side effect of correctness. Compressed insight: $RANDOM's seed, set -o pipefail's exit-status rule, and LANG=C's collation are each an explicit decision to make a nondeterministic-feeling feature reproducible (P12), not merely "however the reference happened to behave." Predicts: any flaky CI test in this codebase traces to an unseeded or unpinned nondeterminism source. Bug class without it: unreproducible bug reports from users running an unpinned locale. Applied in §4, §19.9.

5. Required Reading

Books

  • Kernighan & Pike, The UNIX Programming Environment (Addison-Wesley, 1984), ch. 3, 5, 7 — the shell as a programming language; applied throughout Phase 4–5.
  • Stevens & Rago, Advanced Programming in the UNIX Environment (3rd ed., Addison-Wesley, 2013), ch. 8 (Process Control), 9 (Process Relationships), 10 (Signals), 18 (Terminal I/O) — the systems substrate; applied in Phase 5 (executor), Phase 6 (job control), Phase 8 (line editor).
  • Newham, Learning the bash Shell (3rd ed., O'Reilly, 2005) — built-ins, history, job control reference; applied in Phase 3 (built-ins) and Phase 9 (history).
  • Robbins, bash Cookbook (2nd ed., O'Reilly, 2017) — real-world idiom patterns; mined as a conformance-fixture source for Phase 4 and Phase 13 (validation).
  • Cooper, Advanced Bash-Scripting Guide (The Linux Documentation Project) — exhaustive reference for what real scripts write; fixture mine for Phase 13.
  • Aho, Lam, Sethi & Ullman, Compilers: Principles, Techniques, and Tools (2nd ed., Addison-Wesley, 2006) — recursive-descent and precedence-climbing background; applied in Phase 2 (parser) and Phase 7 (arithmetic engine).

Papers

  • Ritchie & Thompson, "The UNIX Time-Sharing System," CACM 17(7), 1974 — the process model the shell forks into; applied in Phase 5, Phase 6.
  • Bourne, "The UNIX Shell," Bell System Technical Journal, 1978 — the ancestor grammar and here-document design; applied in Phase 1 (lexer), Phase 2 (parser).
  • IEEE Std 1003.1-2017 (The Open Group / IEEE), Shell & Utilities volume, "Shell Command Language" — the specification itself; applied in every phase (§8, ADR-03).
  • POSIX 1003.1-2017 Rationale volume, section A.2 (Shell Command Language) — why the spec reads as it does; applied in Phase 4 (expansion order) and Phase 5 (set -e).
  • Korn, "KSH — An Extensible High Level Language," USENIX Summer Conference Proceedings, 1989 — the array/arithmetic extensions later standardized; applied in Phase 7 (arithmetic engine) and Phase 3 (built-ins, typeset/declare lineage).
  • Duff, "Rc — A Shell for Plan 9," USENIX Summer Conference Proceedings, 1990 — an alternative shell grammar without here-document/quoting irregularities; applied in Alternative Architectures (AA-1).
  • Free Software Foundation, Bash Reference Manual (current edition), §3–§6, §8 — the bash-extension surface gated on Mode::Bash; applied in Phase 1, Phase 3, Phase 4, Phase 8.
  • Wooledge, BashFAQ and Bash Pitfalls (greg's wiki) — curated real-user error corpus; applied as conformance-fixture seed in Phase 13 (validation) and N.6 Pitfalls throughout.

Reference Implementations

  • bash (parse.y, subst.c, execute_cmd.c, jobs.c, lib/readline/) — the most- read shell source; the bash-extension grammar reference; lesson: parse.y's Bison conflicts are the here-document/$() irregularities made visible; pitfall: do not copy its global-mutable-state style (P9, §8 diagram). Applied in Phase 1, 2, 5, 6, 8.
  • dash (src/parser.c, src/expand.c, src/jobs.c) — the smallest serious POSIX shell; lesson: read before bash — fewer extensions make the core algorithm legible; pitfall: dash's setjmp/longjmp control flow does not map to Rust — reimplement as Result-propagated control flow (§8.4). Applied in Phase 2, 4, 5.
  • busybox ash (shell/ash.c) — the embedded-systems POSIX shell; lesson: extreme binary-size and memory-footprint discipline (M7); pitfall: ash's combined lexer/parser is hard to test in isolation — keep osh's phases separated (§8 diagram). Applied in §4 (constraints) and Comparative Architecture Table.
  • mksh (lex.c, expr.c, eval.c, jobs.c) — the BSD/ksh lineage and array semantics that influenced ksh93; lesson: its arithmetic evaluator is a clean precedence-climbing reference; applied in Phase 7.
  • oil / oils (osh) (osh/word_parse.py, osh/cmd_parse.py, core/process.py) — an OSH-style bash-compatible front end with a lossless syntax tree; lesson: preserving source spans through the AST is what makes miette-quality diagnostics possible; applied in Phase 2 and Phase 10 (diagnostics). Pitfall: its Python implementation trades the performance this project needs (P14) — study the design, not the runtime.

RFCs / Specifications

  • IEEE Std 1003.1-2017, Shell & Utilities volume, chapter 2 ("Shell Command Language"): section 2.6 (word expansions, applied Phase 4), section 2.7 (redirection, applied Phase 5), section 2.10 (shell grammar, applied Phase 2), section 2.13 (pattern matching notation, applied Phase 4), section 2.14 (special built-in utilities, applied Phase 3).
  • The Open Group, Single UNIX Specification, Version 4 (SUSv4) — the superset SUSv4 conformance vocabulary used by the VSC test suite (Phase 12).
  • The Open Group, VSC: The Verification Suite for Commands — external conformance integration; applied in Phase 12.

Glossary (§39) · 49 terms · site-wide glossary

AST
abstract syntax tree; the parser's arena-allocated output (§11.3).
Arena allocation
bump-pointer allocation into one contiguous region, freed in bulk rather than per-object (ADR-04, P10).
Assignment word
a name=value token recognized before command-name resolution (§8.2).
bumpalo
the Rust arena-allocator crate backing the AST and word fragments (ADR-04, ADR-08).
Built-in (regular)
a shell-internal command without the special-built-in's set -e/assignment-persistence properties (§15.1).
Built-in (special)
one of POSIX's 15 built-ins with syntax-error-exits-shell and assignment-persistence semantics (POSIX section 2.14, §15.1).
Command substitution
$(...)/backtick expansion of a subshell's stdout into a word (§8.3 stage 4).
Compound command
if/for/case/while/until/brace-group/subshell (§8.2).
Controlling terminal
the TTY a process group can receive keyboard signals from; arbitrated by tcsetpgrp (§8.5).
Dot sourcing
the ./source special built-in, executing a file's commands in the current shell rather than a subshell (§15.2).
Extglob
bash extended glob patterns (?(...), *(...), +(...), @(...), !(...)), gated on Mode::Bash (§16.2).
Field splitting
IFS-driven division of expanded text into words (§8.3 stage 6).
FIFO
named pipe, used to materialize process substitution (§23.2).
fork
the syscall creating a child process by address-space copy (§8.4).
Glob
pathname expansion via POSIX pattern matching (§8.3 stage 7, §11 pattern crate).
Here-document
<</<<- redirection whose body is literal text up to a tag line (§8.1).
IFS
Internal Field Separator, the field-splitting delimiter set (§8.3 stage 6).
Job
one pipeline's process group plus its table bookkeeping (§11.5).
Job control
the subsystem arbitrating the controlling terminal between shell and children (§8.5, §18).
Lexical context
one of the five tagged states the lexer operates in (§8.1).
Monitor mode
set -o monitor / -m, enabling job-control notifications.
OTLP
OpenTelemetry Protocol, the tracing export format used when OSH_TRACE=1 (ADR-19).
Parameter expansion
${...}/$name substitution, 14 POSIX forms + 4 bash extensions (§8.3 stage 3, §11.2).
PATH hash table
the cached mapping from command name to resolved executable path (§11.4, ADR-07 sibling).
Pgid
process-group id; the pid of the group's leader process (§11.5).
Pipeline
a sequence of commands connected via |, each stage a separate process (§8.2).
POSIX
IEEE Std 1003.1-2017, the Shell & Utilities specification this project conforms to (§1.1, §5).
Quote removal
the final expansion stage stripping quoting metadata from surviving fields (§8.3 stage 8).
Reaper
the waitpid-loop component reconciling process exits into job-table state (§18.2, §11.5).
Recursive descent
a hand-written top-down parsing technique, one function per grammar non-terminal (ADR-02, §14.2).
Redirect
an I/O-operator + target-word AST node (Redirect, §11.3).
Restricted shell
osh -r, a least-privilege mode disabling cd/exec/output redirection/PATH changes (§22.2, I12).
Self-pipe trick
writing one byte from a signal handler to a pipe read by the main loop, for async-signal-safe dispatch (P8, §18.2).
setpgid
the syscall placing a process into a process group (§8.5, I5).
SIGCHLD
the signal delivered on a child's state change, driving the reaper (§18.2).
SIGTTOU
the signal sent to a background process group attempting terminal writes; self-ignored by the arbiter during its own tcsetpgrp call (§18.2, §18.6).
Subshell
a ( ... ) compound command, executed in a forked child (§8.2, §17.6).
tcsetpgrp
the syscall assigning the controlling terminal's foreground process group (§8.5, I6).
Token
the lexer's output unit: a Word, Operator, Reserved, IoNumber, or Newline/Eof (§11.1).
VSC

waitpid
the syscall retrieving a child's exit/stop status (§18.2).
Word

WordPart

ShellMode
the Posix/Bash/Enhanced mode enum gating extension surfaces (§11.6, P1, P2).
ShellFlags

xxHash
