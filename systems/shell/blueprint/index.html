79 — POSIX Shell

Project Number: 79

Project Name: POSIX Shell

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

1.1 Engineering definition

Build osh, a single static binary implementing a POSIX.1-2017 (IEEE Std 1003.1-2017, Shell & Utilities volume, "Shell Command Language") conformant command-language interpreter: contextual lexer (5 lexical contexts, §8.1), recursive-descent parser producing an arena-allocated AST (§8.2), a 7-step expansion pipeline executed in POSIX section 2.6 fixed order (§8.3), a fork/exec/pipeline executor with function-frame stack and set -e/-u/pipefail decision points (§8.4), a job-control nucleus arbitrating the controlling terminal via tcsetpgrp (§8.5), a built-ins library (15 POSIX-special + 19 POSIX-regular + 22 bash-gated), an arithmetic engine for $((...)), and an interactive line editor (vi/emacs) with programmable completion and history. osh runs interactively on a TTY, non-interactively via -c/script-file, and as a login/restricted shell.

1.2 Phase-0 deliverable — modules

  1. crates/sys — libc FFI boundary (fork, execve, waitpid, setpgid, tcsetpgrp, termios); the only crate containing unsafe.
  2. crates/lexer — tokenizer, 5 lexical contexts, here-doc capture, alias substitution.
  3. crates/parser — recursive-descent grammar (docs/grammar.ebnf), AST arena.
  4. crates/expand — brace/tilde/parameter/command/arithmetic/field-split/glob/quote.
  5. crates/exec — pipeline construction, redirection, function frames, flag decisions.
  6. crates/jobs — process-group table, foreground arbiter, reaper.
  7. crates/builtins — special + regular + bash-gated built-in commands.
  8. crates/editor — raw-mode line editor, vi/emacs keymaps, render loop.
  9. crates/history — append-only history store, !-expansion, reverse-i-search.
  10. crates/env — variable scope stack, PATH hash table, special parameters.
  11. crates/pattern — POSIX glob + bash extglob matcher.
  12. crates/arith — precedence-climbing arithmetic parser/evaluator.
  13. crates/osh — the binary: argv parsing, mode selection, REPL driver.
  14. conformance/runner — CLI that drives the above against fixture corpora.

1.3 System boundaries

  • Provides: POSIX-conformant parsing/expansion/execution; job control; interactive line editing; a curated, explicitly-gated bash-extension surface (Mode::Bash).
  • Delegates: process execution itself to the kernel (execve); terminal rendering to the host terminal emulator (the editor emits ANSI, does not implement one); DNS/network I/O (none — the shell has no network stack); filesystem semantics to the OS (glob, stat, chdir are thin wrappers, §8.3).
  • Does NOT provide: a general-purpose extension language (no embedded Tcl/Lua/JS, Design Principle P2); a package manager; a terminal multiplexer; sandboxing/capability confinement of executed programs (Threat Model T9); a GUI.

1.4 Non-goals

Training an ML model, designing a new shell language, competing with nushell's structured-data pipeline model (explicitly out of scope, referenced not built), Windows support (ADR-20), a WASM target (PhaseDeferred("Deferred Features Register")).

1.5 Deployment model & users

Single static binary (cargo zigbuild release matrix, ADR-20) installed as /usr/local/bin/osh or set as /etc/shells entry via chsh -s. Target users: engineers who need a portable, auditable POSIX shell; operators running it as a container entrypoint (ENTRYPOINT ["/usr/bin/osh"]); package maintainers building .deb/.rpm. No client-server topology — one process, one controlling terminal (or none, in -c/ script mode), one address space.

1.6 What later phases unlock

Phase 3 (built-ins) unlocks real scripts (cd, test, read). Phase 4 (expansion) unlocks parameter substitution and globbing used by virtually all real-world scripts. Phase 5 (executor) unlocks pipelines and set -e semantics. Phase 6 (jobs) unlocks interactive multitasking (Ctrl-Z, fg, bg). Phase 8 (editor) unlocks the interactive REPL. Phase 10 unlocks restricted/audit deployments. Phase 11 unlocks the opt-in zsh/fish-style convenience surface. Phase 12 unlocks external POSIX VSC-suite validation.

1.7 Recommended language + rationale

Rust, 2021 edition, MSRV 1.76 (ADR-01). Rationale: the interpreter's hot correctness surface is pointer/lifetime-heavy (arena-allocated AST nodes, process groups, FD ownership across fork, here-doc buffers) and Rust's ownership model makes every one of those surfaces a compile-time-checked contract instead of a valgrind session, while matching C's performance at the parser/expansion/completion hot paths (P14, ADR-01). Rejected: C (memory-safety cost proven repeatedly in bash/dash CVE history — no compile-time ownership check on FD/pointer lifetimes); Go (GC pauses unacceptable in a SIGWINCH-driven render loop; no safe raw-fork primitive without runtime.LockOSThread gymnastics); Python/Zig considered and rejected in ADR-01's long form (docs/adr/adr-01.md).

1.8 Prerequisites

Unix process model (fork, execve, waitpid, setpgid, tcsetpgrp, signal masks, FD inheritance); the POSIX shell as a programming language (parameter expansion, command substitution, here-documents, redirection, pipelines, traps); termios (VEOF/VINTR/ VERASE); intermediate Rust (lifetimes, traits, unsafe FFI). Reading bash/dash C source is required for Phases 1–2, 5–6 (§5).

1.9 Estimated timeline

Phase 0: 1 week. Full system (Phases 0–12): 14–16 weeks (≈ 4 months) at one senior engineer full-time; add 3–4 weeks if Phase 11 (enhanced mode) and Phase 12 (external VSC integration) are pursued rather than deferred.

2. Why Build This

  • Unique systems knowledge: the shell is the one userspace program that legitimately owns process groups, controlling-terminal arbitration, and a five-context lexer at once — no other common project teaches all three under one roof.
  • Architectural importance: every Unix engineer eventually debugs a divergence between the shell dialect they think they are writing and the one actually being parsed (unquoted-expansion word-splitting, pipefail-less silent pipeline failure, trap inheritance across subshells). Building the interpreter removes the mystery.
  • Engineering muscles built: context-sensitive lexing without regex; hand-written recursive descent with lookahead-free reserved-word disambiguation; async-signal-safe handler design (self-pipe trick); arena allocation discipline across fork boundaries; PTY-driven testing of an interactive surface.
  • Cross-links to portfolio siblings: the lexer/parser pairing parallels any compiler front-end project's tokenizer+parser split; the job-control state machine parallels process-supervisor projects (init systems, container runtimes) that also arbitrate signals and process groups; the arithmetic engine's precedence climber is the same technique used by any expression-evaluator project.
  • Calibration value: POSIX section 2 is a rare specification precise enough to gate byte-identical conformance, so this project calibrates "did I actually implement the spec" against ground truth rather than intuition — a discipline transferable to any standards-conformant systems project (wire protocols, file formats).

What Mastery Looks Like

  • Can explain, from first principles, why the shell lexer cannot be a single regex DFA (context-sensitivity at here-documents/$()/${} boundaries, applied in Phase 1).
  • Can trace exactly which of the seven POSIX section 2.6 expansion steps produces a given surprising result for any real-world word (applied in Phase 4).
  • Can explain the tcsetpgrp/SIGTTOU self-ignore dance well enough to debug a stuck background job in a live terminal (applied in Phase 6).
  • Can derive the set -e swallow-context rules from the spec text rather than memorizing bash's behavior, and name where the two diverge (applied in Phase 5).
  • Can justify, with real numbers, why the AST is bump-arena-allocated rather than Box-per-node (applied in Phase 2, quantified in the Back-of-Envelope Capacity Model).
  • Can redesign the executor around posix_spawn and state exactly what job-control capability is lost (Alternative Architectures).

Data flow is one-way and single-threaded: bytes → tokens → AST → expanded words → process tree; the executor's only side channels back are FDs, signals, and the shared Shell struct (§11.6). Trust boundary: script source bytes and the environment are the only untrusted inputs (Threat Model T1–T3); nothing crosses a network boundary. Concurrency boundary: none inside one osh process — it is single-threaded by design (ADR-10) — but fork() creates a process boundary at every pipeline stage, and SIGCHLD/SIGWINCH/SIGINT cross an async-signal boundary handled only via the self-pipe trick (§8.5, P8). Persistence boundary: the only durable state is the append-only history file; everything else (AST arena, job table, variable scope) is process-lifetime only. Every later section stays consistent with this diagram: the Repository Layout (§10) names one crate per box; the Core Schema (§11) types are the values that flow along each arrow.

6. Design Principles

P1 — POSIX is ground truth. Rule: every construct has a POSIX-conformant reference implementation; bash/zsh/fish extensions gate on ShellMode != Posix. Tradeoff: strict mode occasionally surprises bash users. Operational implication: the conformance suite (§22 analogue, Testing & Verification Strategy) enforces both modes. Violation: silent mode leakage makes the "strict" mode a lie — breaks Threat Model mitigation T2.

P2 — One interpreter, multiple modes; modes never leak into the core. Rule: the executor consults ShellMode only at the exact points POSIX/bash-extension text identifies (alias expansion, param forms, brace expansion, function syntax). Tradeoff: some duplication across mode branches. Violation: an untested mode interaction (Phase 2 pitfall on reserved-word aliasing).

P3 — The lexer is contextual, not regular. Rule: 5 lexical contexts (§8.1), a tagged state machine, never a single regex/DFA. Tradeoff: more code than a lexer generator. Violation: a regex lexer collapses on nested $()/here-docs by Phase 4 (N.6 of Phase 1).

P4 — The parser is recursive descent, not table-driven. Rule: hand-written functions matching POSIX section 2.10 productions one-to-one (§8.2 grammar). Tradeoff: no formal LALR conflict proof. Violation: Bison-style tables hide the here-document/$() irregularities that recursive descent makes explicit (P4, Alternative Architectures AA-1).

P5 — Expansion order is a sequence, never a merged pass. Rule: POSIX section 2.6's seven steps (brace/tilde/parameter/command/arithmetic/split/glob) plus quote removal run as eight ordered stages, never short-circuited. Violation: ${var:-$other} fixtures fail if $other is expanded before var's unset-check (Phase 4 N.6).

P6 — The executor never serializes the AST across fork. Rule: a child inherits the parent's arena via address-space copy; it never deserializes a wire form. Violation: half the "shell forgot function definitions after backgrounding" bug class (Phase 5 N.9).

P7 — Job control is owned by exactly one arbiter. Rule: one function calls tcsetpgrp; it is a small state machine over (controlling_tty, foreground_pgid, shell_pgid) (§8.5). Violation: two call sites racing on tcsetpgrp is the root cause of "stuck terminal" bug reports (Phase 6 N.9, FM-6).

P8 — Signal handlers are async-signal-safe at the boundary only. Rule: a handler writes one byte to a self-pipe; the main loop reads and dispatches (§8.5). Violation: any non-async-signal-safe call (allocation, printf) inside a handler is undefined behavior per POSIX and produces heisenbugs under load (Phase 6 N.6).

P9 — The lexer alone sees raw bytes. Rule: no other module decodes UTF-8 or normalizes multibyte input; downstream sees WordPart enums (§11.1). Violation: double decoding produces mojibake in completion candidates (Phase 9 N.8).

P10 — One arena per AST, one per running command's activations. Rule: AST nodes live in the script's bumpalo::Bump; open FDs/pending here-docs/expanded fields live in the command's arena (ADR-04, ADR-08). Violation: per-node heap boxing measured 3–5× allocator pressure in the parser benchmark (Back-of-Envelope Capacity Model, row 3).

P11 — No silent fallbacks; document every POSIX divergence. Rule: if set -e would abort but the spec swallows the status, the behavior is written to docs/posix-divergences.md, not silently absorbed (Phase 5 §13.6 analogue). Violation: undocumented divergence is the single largest source of "works in bash, not in osh" bug reports (Failure Modes FM-4).

P12 — Determinism is the default. Rule: set -o pipefail -e -u with LANG=C produces bit-identical output across runs given identical input/environment; $RANDOM is seeded from a documented, recoverable source. Violation: non-reproducible CI failures (Testing & Verification Strategy).

P13 — The line editor is a separable concern. Rule: the editor emits a Vec<u8> fed to the lexer exactly as a script would be (§3 diagram); replacing the editor never touches the executor. Violation: coupling editor state to executor state defeats the non-interactive/-c code-path reuse that Phase 0 establishes.

P14 — unsafe is fenced to one crate. Rule: all libc FFI lives in crates/sys; every other crate is zero-unsafe; every FFI call carries a safety comment naming the libc function and precondition (ADR-01, ADR-06). Violation: an unaudited unsafe block outside crates/sys fails CI's cargo geiger gate (Build & Release Engineering).

8. Domain Model, Protocol & Data Model

8.1 Lexical Contexts

Five contexts, a tagged state machine over (context, position) (P3):

Context Entered by Exited by Quoting rules
TopLevel session/script start EOF full: ', ", \, operators
HereDocBody <</<<- recognized line == tag (tabs stripped if <<-) none if tag was quoted; full expansion otherwise
CommandSubBody $( or ` matching ) / unescaped ` nested TopLevel scan; bracket-counted for $()
ParamExpansionBody ${ matching } small grammar per §8.3 form; may nest $()
ArithExpansionBody $(( matching )) arithmetic source bytes, one expansion round first

Transition table (excerpt — full table in docs/architecture/lexer.md):

state=TopLevel,  see '$(' → push CommandSubBody,   emit no token yet
state=TopLevel,  see '${' → push ParamExpansionBody
state=TopLevel,  see '<<' → capture tag, defer to HereDocBody after newline
state=CommandSubBody, see ')' at depth 0 → pop → TopLevel, emit CommandSub token
state=ParamExpansionBody, see '}' at depth 0 → pop → TopLevel, emit DollarBrace token
state=HereDocBody, line == tag → pop → TopLevel, attach body to pending Redirect

8.2 Grammar (EBNF, canonical form; full grammar in docs/grammar.ebnf)

Top-level productions (chunk 1 of 2):

program           = linebreak , [ complete_commands , linebreak ] ;
complete_commands = complete_command , { newline_list , complete_command } ;
complete_command  = and_or_list , { separator_op , and_or_list } , [ separator_op ] ;
and_or_list       = pipeline , { ( "&&" | "||" ) , linebreak , pipeline } ;
pipeline          = [ "!" ] , command , { "|" , linebreak , command } ;
command           = simple_command
                  | compound_command , [ redirect_list ]
                  | function_definition ;
compound_command  = brace_group | subshell | for_clause | case_clause
                  | if_clause   | while_clause | until_clause ;
brace_group       = "{" , compound_list , "}" ;
subshell          = "(" , compound_list , ")" ;
compound_list     = linebreak , term , [ separator ] ;
term              = and_or_list , { separator , and_or_list } ;
for_clause        = "for" , name , [ linebreak , "in" , { word } , sequential_sep ]
                  , do_group ;
case_clause       = "case" , word , linebreak , "in" , linebreak
                  , { case_item } , "esac" ;
case_item         = [ "(" ] , pattern , { "|" , pattern } , ")" , linebreak
                  , [ term ] , [ ";;" , linebreak ] ;
if_clause         = "if" , compound_list , "then" , compound_list
                  , { "elif" , compound_list , "then" , compound_list }
                  , [ "else" , compound_list ] , "fi" ;
while_clause      = "while" , compound_list , do_group ;
until_clause      = "until" , compound_list , do_group ;
do_group          = "do" , compound_list , "done" ;
function_definition = fname , "(" , ")" , linebreak , function_body ;
function_body     = compound_command , [ redirect_list ] ;

Word/redirection productions (chunk 2 of 2):

simple_command    = cmd_prefix , [ cmd_word , cmd_suffix ]
                  | cmd_name , cmd_suffix ;
cmd_prefix        = { io_redirect | assignment_word } ;
cmd_suffix        = { io_redirect | word } ;
io_redirect       = [ io_number ] , io_op , word ;
io_op             = "<" | "<&" | "<>" | ">" | ">&" | ">>" | ">|"
                  | "<<" | "<<-" | "<<<" ;
word              = { word_part } ;
word_part         = literal | single_quoted | double_quoted
                  | dollar_var | dollar_brace | command_sub
                  | arith_sub | tilde_prefix | backslash_escape ;
double_quoted     = '"' , { literal | dollar_var | dollar_brace
                  | command_sub | arith_sub | backslash_escape } , '"' ;
dollar_brace      = "${" , [ "!" ] , [ "#" ] , param_name , [ param_op ] , "}" ;
param_op          = ( ":-" | ":=" | ":?" | ":+" ) , word
                  | ( "#" | "##" | "%" | "%%" ) , pattern
                  | "/" , pattern , "/" , word
                  | ":" , offset , [ ":" , length ]
                  | "@" , transform_char ;
pattern           = { pattern_char } ;   (* POSIX section 2.13 notation, not regex *)

8.3 Expansion Pipeline — Ordered Sequence

Eight stages, strict order (I2, P5):

Stage Input Output POSIX cite
1 Brace WordParts expanded WordParts list (bash-gated) bash ext.
2 Tilde word head $HOME/getpwnam substitution section 2.6.1
3 Parameter ${...}/$name substituted bytes (unexpanded further) section 2.6.2
4 Command $()/backtick subshell stdout, trailing NL stripped section 2.6.3
5 Arithmetic $((...)) i64 decimal bytes section 2.6.4
6 Field split concatenated bytes Vec<Field> by IFS section 2.6.5
7 Pathname (glob) each field filesystem matches or unchanged section 2.6.6
8 Quote removal surviving fields final byte strings section 2.6.7

8.4 Execution Semantics — SimpleCommand Path

  1. Expand assignment prefixes (same 8-stage pipeline as a word).
  2. Empty command word after expansion → assignments persist in current shell (section 2.9.1); else scoped to subshell/built-in per I3.
  3. Function name match → new frame (§11.4), bind positionals, execute body.
  4. Built-in name match → dispatch via Builtin trait (§11.3).
  5. Else PATH lookup (hashed) → fork + execve.

8.6 Worked Examples

Well-formed: echo "$(cat file)" | grep -c foo && echo ok — pipeline of 2 stages; $(cat file) command-substitutes in a subshell before echo runs; && gates echo ok on the pipeline's exit status (rightmost non-zero if pipefail, else last stage, I3).

Malformed input: if true; then echo hi (missing fi) — parser detects EOF inside if_clause (§8.2), enters continuation mode (PS2) in interactive use, or exits status 2 with a miette-rendered "unexpected EOF, expected fi, opened at line 1" in script mode.

Failure path: cmd1 | cmd2 | cmd3 where cmd2 receives SIGSEGV — reaper (Phase 6) observes WIFSIGNALED, records Process.status = Signaled(11) for cmd2; overall pipeline status is cmd3's status unless pipefail, in which case it is 128+11=139 (the rightmost non-zero, per I3 and set -o pipefail), reported via $?.

12.9 Failure Analysis

A missing governance file (e.g. no SECURITY.md) blocks release-check but not build — the Makefile target isolates governance failures from build failures so CI signal stays specific. Blast radius of a Phase-0 regression: total (nothing later builds without this skeleton) — hence the smoke test is the one test that must never be skipped.

12.10 Operational Notes

make bootstrap is idempotent and safe to re-run; CI caches ~/.cargo keyed on Cargo.lock hash. No deployment yet — this phase produces a debug binary only.

13.10 Operational Notes

  • Reserved words are reserved only at command-start (for at a list head vs. as a command name) — the parser must consult the cursor's command-start flag, not infer it lexically (P3/P4 boundary).

14.9 Failure Analysis

A stack-overflow-class adversarial input is contained by the recursion-depth cap before it reaches the OS stack limit; detection is the cap's own counter, telemetry is a parse_depth_exceeded diagnostic, recovery is a clean parse-error return, never a panic.

17.3 Deliverable

Every AST construct executes correctly against conformance/corpora/exec/; a 100-line configure-style script (Required Reading, Cooper) runs to completion.

17.4 Acceptance Criteria

  • exec.* buckets: 100% match on exit status + stdout + stderr bytes, ≥ 300 cases.
  • exec.flags bucket covers all POSIX section 2.11 swallow contexts plus 8 documented bash deviations (I9).

17.5 Conformance Fixtures

  • corpora/exec/{simple,pipeline,redirect,heredoc,function}/*.in.
  • corpora/exec/flags/*.in — set -e/-u/pipefail cases.

17.6 Pitfalls

  • dup2 order is left-to-right in the redirect list — 2>&1 1>file ≠ 1>file 2>&1.
  • Large here-documents deadlock on a pipe write exceeding PIPE_BUF — materialize to a temp file above the threshold (§17.2).
  • set -e swallow rules are the most bug-prone area in any shell — consult the single decision table (I9), never re-derive ad hoc.

17.7 Performance Concerns

Pipeline fork+exec latency budget ≤ 400 µs/stage (§4); avoid AST re-walks per pipeline stage by resolving the command list once before forking.

17.8 Edge Cases

A pipeline whose middle stage is killed by a signal (§8.6 failure-path example, I3); set -u triggering inside a function's positional-parameter reference; a redirect whose target file cannot be created (permission denied — exit 1-class diagnostic, no crash).

17.9 Failure Analysis

An execve failure (ENOENT, EACCES) in the child reports via a dedicated exit-status convention (127 for not-found, 126 for not-executable, POSIX section 2.8.2) rather than an opaque non-zero; detection is the child's own error path, telemetry is the parent's waitpid status, recovery is normal shell continuation (I3).

17.10 Operational Notes

19.10 Operational Notes

Implement programmable tab-completion and the append-only history store with !-style expansion and reverse incremental search.

21.2 Detailed Implementation Steps

  • Implement crates/editor/src/completion.rs: a provider chain — command-name (PATH hash + aliases + functions + built-ins), file/directory, programmable (complete -F running user functions in a subshell with COMP_WORDS/COMP_CWORD/COMP_LINE/ COMP_POINT, appending to COMPREPLY), default (variables, users, hosts, git refs) (Bash Reference Manual §8 citation, §5).
  • Implement crates/history/src/store.rs: append-only ${HISTFILE:-~/.osh_history}, flock-serialized writes (I10), HISTSIZE-bounded load at session start.
  • Implement crates/history/src/expansion.rs: !!, !$, !N, !-N, !?str? — runs before quoting, gated on Mode::Bash and set -H (interactive default).
  • Implement Ctrl-R reverse incremental search: narrows on each keystroke; Esc accepts current match, Enter submits (I14 — search never mutates the store).
  • Wire completion.{command,file,programmable} and history.{expansion,fc,search} buckets; load a curated handful of real bash-completion scripts (git, cargo, kubectl) as an integration fixture.

21.3 Deliverable

Existing bash-completion scripts for git/cargo/kubectl load and complete correctly; history and fc built-ins operate on the in-memory store.

21.4 Acceptance Criteria

  • completion.{command,file,programmable} buckets: 100% candidate-set match, ≥ 60 cases.
  • history.{expansion,fc,search} buckets: 100% pass, all five !-forms covered.
  • The 3 curated real completion scripts complete correctly against ≥ 10 fixtures each.

21.5 Conformance Fixtures

  • corpora/completion/{command,file,programmable}/*.in.
  • corpora/history/{expansion,fc,search}/*.in.

21.6 Pitfalls

  • History expansion runs before quoting — a literal ! in interactive mode needs set +H, a frequent surprise (documented in docs/posix-divergences.md).
  • Concurrent shells writing history race; flock is the only portable cure (Solaris fcntl locking is finicky — tested Linux/macOS only, §5 scope note).
  • Ctrl-R in vi mode is a keymap binding, not a universal search trigger — the editor disambiguates by active mode.

21.7 Performance Concerns

Completion-candidate caching uses xxHash (ADR-07) keyed on the current word + PATH mtime; cache invalidates on PATH change or hash -r.

21.8 Edge Cases

A complete -F function that never sets COMPREPLY (empty candidate list, not an error); history file exceeding HISTSIZE (oldest entries dropped on load, not on write — the file itself stays append-only per ADR-17); a !?str? search with no match (no-op, diagnostic to stderr in interactive mode).

21.9 Failure Analysis

A malicious or buggy completion plugin can read the user's filesystem at user privilege but cannot escalate (Threat Model T5); containment is the subshell boundary — a plugin crash never takes down the parent shell.

21.10 Operational Notes

history -c clears the in-memory store without touching the file; HISTFILE rotation is an explicit operator action (documented, not automatic — §4 constraint on unbounded append-only growth).

22. Phase 10 — Restricted Shell, No-Exec Mode, Observability

22.1 Objectives

Implement least-privilege restricted mode (I12), static-analysis no-exec mode, opt-in OpenTelemetry tracing (ADR-19), and miette-based diagnostics (ADR-13).

22.2 Detailed Implementation Steps

  • Implement ShellFlags::RESTRICTED (osh -r/rosh) checks at every executor entry point (I12, not just the built-in dispatcher): disable cd; disable setting/unsetting PATH/ENV/BASH_ENV/SHELL; disable command names containing /; disable output redirection (>, >|, <>, >>); disable exec; disable command -p (ksh rsh rules + bash restricted.c superset, ADR-21). Document explicitly (Threat Model T5): restricted mode reduces accidents, not adversaries.
  • Implement osh -n (set -o noexec): parses and expands (surfacing $((...)) syntax errors) but replaces the executor's leaf execve calls with no-ops (P11 — no silent fallback, this is a documented mode, not a hidden shortcut).
  • Implement crates/osh tracing: OSH_TRACE=1 emits one OpenTelemetry span per parsed command, nested for compound commands; OTLP-over-HTTP exporter, default endpoint localhost:4318 (ADR-19 — opt-in, zero default overhead).
  • Implement miette-based diagnostics: source-span-carrying errors; multiline errors (e.g., a 30-line unclosed quote) show first/last line + an elision marker (ADR-13).

22.3 Deliverable

Restricted mode passes its conformance bucket; osh -n script.sh returns 0 on syntactically valid input, 2 on invalid, and executes zero leaves; OSH_TRACE=1 emits a coherent trace to a local OTLP collector.

22.4 Acceptance Criteria

  • restricted bucket: every restricted operation emits the documented diagnostic, 100% of ≥ 20 cases (I12).
  • noexec bucket: 100% of fixtures parse without executing a single leaf.
  • A tracing smoke test confirms span nesting matches the AST's compound-command nesting.

22.5 Conformance Fixtures

  • corpora/restricted/*.in — every restricted operation + expected diagnostic.
  • corpora/noexec/*.in — parse-only fixtures, execution-count asserted zero.

22.6 Pitfalls

  • Checking restrictions only in the built-in dispatcher misses direct executor paths (e.g., a redirect on a compound command) — checks belong at every entry point (I12).
  • No-exec mode must still run the expansion pipeline (to catch $((...)) syntax errors) — stubbing the whole pipeline produces false-negative "valid" scripts.
  • OSH_TRACE spans left always-on in a hot loop defeats the zero-overhead default — gate strictly on the env var check, not a runtime feature flag with residual cost.

22.7 Performance Concerns

Restricted-mode checks are O(1) flag tests per entry point — no measurable latency added to the executor's hot path (§4).

22.8 Edge Cases

osh -r invoked with PATH already containing a /-relative entry (rejected at lookup time, not at flag-set time); osh -n on a script containing an unterminated here-doc (parse error, exit 2, per §14.2); tracing enabled mid-session via export OSH_TRACE=1 (takes effect for subsequently parsed commands only).

22.9 Failure Analysis

A restricted-mode bypass attempt (Threat Model T5) is explicitly documented as not a security boundary — the failure mode here is user expectation mismatch, not privilege escalation; docs/threat-model/threat-model.md states this without qualification.

22.10 Operational Notes

docs/runbooks/triage.md documents reading an OSH_TRACE export to diagnose a slow interactive session; miette diagnostics are the primary operator-facing error surface from this phase forward.

23. Phase 11 — Enhanced Mode (Opt-In, Non-Portable)

23.1 Objectives

Ship the Mode::Enhanced convenience surface — zsh/fish-style features explicitly marked non-portable, gated behind Mode::Enhanced (P1, P2).

23.2 Detailed Implementation Steps

  • Implement zsh-style glob qualifiers (*(/) directories, *(.) regular files, *(N) no-error-on-no-match) as an extension to crates/pattern — PhaseDeferred("Deferred Features Register") until enough real-world fixtures justify the work (ADR-22 sibling decision).
  • Implement process substitution <(cmd)/>(cmd): lexer recognizes at word head, executor materializes a FIFO or /dev/fd/N link and substitutes its path.
  • Implement coprocesses (coproc { cmd; }): background execution exposing ${COPROC[0]}/${COPROC[1]} — requires a small extension to crates/exec/src/ pipeline.rs's pipe wiring; PhaseDeferred("Deferred Features Register").
  • Implement live syntax highlighting (fish-style): command names green if found in PATH, red otherwise; recomputed per keystroke in crates/editor/src/highlight.rs; PhaseDeferred("Deferred Features Register") until the editor (Phase 8) is stable.
  • Implement RPROMPT (zsh-style right-side prompt), tracking cursor position.

23.3 Deliverable

Mode::Enhanced builds and runs against a small curated fixture set; every PhaseDeferred call site is registered in the Deferred Features Register.

23.4 Acceptance Criteria

  • Process substitution: ≥ 10 fixtures pass byte-identical against a reference zsh/ bash (with xpg_echo-equivalent) run.
  • RPROMPT renders without corrupting the primary prompt's cursor tracking in ≥ 5 terminal-width fixtures.
  • Every enhanced-mode feature not yet implemented carries a PhaseDeferred(...) call site resolving to the Deferred Features Register.

23.5 Conformance Fixtures

  • corpora/enhanced/procsub/*.in.
  • corpora/enhanced/rprompt/*.expect (PTY-driven).

23.6 Pitfalls

  • Glob qualifiers are lexically adjacent to extglob syntax — a naive implementation double-parses @(...) as both extglob and a qualifier; disambiguate by mode.
  • Process substitution FIFOs leak if the consuming command never opens them — the executor must set a reaper timeout.
  • Coprocess pipe wiring interacting with the existing pipeline pipe-count assumption (§17.2, N-1 pipes for N commands) needs an explicit extra-pipe accounting path.

23.7 Performance Concerns

Live syntax highlighting recomputes on every keystroke — must stay within the same render-loop budget as Phase 8's diff-based redraw (§20.7) or it visibly lags.

23.8 Edge Cases

A process substitution used in a context that never reads it (<(cmd) passed to a program that ignores its argument — FIFO write blocks until reaped); RPROMPT on a terminal narrower than the combined PS1+RPROMPT width (truncate RPROMPT first).

23.9 Failure Analysis

A leaked process-substitution FIFO is a resource leak, not a correctness failure — detection is an lsof-visible orphaned FIFO; recovery is the reaper's timeout-based cleanup (Failure Modes & Recovery, FM-9).

23.10 Operational Notes

docs/enhanced-mode.md documents every enhanced feature as explicitly non-portable; scripts using Mode::Enhanced syntax must declare #!/usr/bin/env osh --enhanced.

27. Operational Readiness

Metrics: cold-start latency, parse rate, fork+exec latency per pipeline stage, job table size, history-lock contention count — all opt-in via OSH_TRACE=1 (§22.2, ADR-19). Tracing: OpenTelemetry spans nested per compound command, OTLP-over-HTTP, localhost:4318 default endpoint. Structured logging: miette-rendered diagnostics to stderr for interactive/script errors; no separate structured-log sink by default (a shell's "logs" are its stdout/stderr, by design). Dashboards: conformance-bucket pass rate over time (CI artifact trend), fuzz-crash corpus size, soak-test memory-growth curve. Alerting philosophy: CI-gated, not runtime-alerted — a shell process has no fleet-monitoring surface of its own; operators embedding osh in a fleet wire OSH_TRACE into their own collector. SLOs: M6 (cold start ≤50ms), M8 (conformance suite ≤10min) are the two CI-enforced SLOs; M9/M10 (soak/fuzz) gate Sealed, not every PR. Incident response: docs/runbooks/triage.md (general), orphaned-jobs.md (FM2), stuck-tty.md (FM6/FM7). Backup/restore: the only durable state is ~/.osh_history — operators back it up via their own dotfile-management tooling; osh itself performs no automatic backup (ADR-17 scope). Deployment topology: single static binary per host; no server component. Canary/rolling-upgrade: package-manager level (.deb/.rpm/Homebrew, ADR-20) — a new osh binary replaces the old atomically via the OS package manager; rollback is a package downgrade; migration: history- file format is stable across versions (ADR-17), so no migration step is required on upgrade.

28. Compatibility & Versioning

Wire/storage compatibility: the only "wire" format is the history file (append-only LF-delimited UTF-8, ADR-17) and conformance.report.json (schema_version field, §22.3) — both additive-only across minor versions. Schema evolution: TokenKind/AST node variants (§11.1, §11.3) may gain variants in a minor release; removing one is a major-version break. API stability: the normative traits (Lexer/Parser/Expander/Executor/JobControl/LineEditor — one per §3 diagram box) are the public contract for alternate implementations; a method signature change is major-version. Migration: none required for the history file across versions (stable format); a ShellFlags bit removal (§11.6) would require a migration note in CHANGELOG.md. Deprecation policy: a deprecated built-in or flag emits a miette warning for one full major version before removal. SemVer policy: MAJOR.MINOR.PATCH — PATCH: bugfix + new conformance fixtures; MINOR: new built-in/ADR-gated feature, additive AST/token variants; MAJOR: trait signature change, ShellFlags/VarFlags bit removal, history-format change. Rolling-upgrade guarantees: because osh is a single-process CLI (no server), "rolling upgrade" reduces to "each new interactive session picks up the newly installed binary" — no in-flight-session migration is needed or attempted.

  • Unit: per-crate (crates/*/tests/), one test per built-in (§15.3), per expansion form (§16.2), per arithmetic operator (§19.2).

32. Scalability Analysis

Stays constant: memory at idle (M7, O(1) in script size); per-token lexer allocation (O(1) amortized per byte, P9). Grows: AST arena size — O(n) in script line count (bounded by M1's 500ms/100K-line target); job table — O(j) in concurrent background jobs, bounded at ≥256 without degradation (§4); history file — O(t) unbounded over time (operator-managed rotation, §21.10). Named bottlenecks in order: (1) fork+execve latency per pipeline stage (≤400 µs budget, §4) — the dominant cost for any many-short-commands script; (2) glob matching on very large directories (M4's 50ms target, async-glob deferred per ADR-22); (3) completion-candidate generation on a huge PATH (mitigated by xxHash caching, ADR-07). Horizontal scaling: not applicable — one process per interactive session or script invocation; "scaling" means running more osh processes, each independent (no shared state, ADR-10's single-threaded-per-process design already implies process-level, not thread-level, parallelism for concurrent users). Vertical scaling: more CPU cores do not help a single-threaded interpreter directly, but do help many concurrent background jobs (each still forks its own process). Sharding/partitioning: not applicable — no persistent shared dataset. Coordination overhead: the only cross-process coordination is history-file flock (I10) — contention scales with concurrent interactive-shell count, mitigated by exponential backoff. Practical ceiling: the job table's O(1)-lookup design (§11.5) holds to ~10⁴ concurrent jobs before the waitpid(-1, ...) reaper loop itself becomes the bottleneck (Back-of-Envelope Capacity Model row 6); the lever beyond that ceiling is waitid(P_PIDFD, ...)-based targeted reaping (PhaseDeferred("Deferred Features Register")) rather than a broadcast waitpid(-1, ...).

33. Mental Models & First Principles

MM1 — The lexer's job is to defer, not decide. Compressed insight: a token is a promise to interpret bytes a certain way given a context, not a final classification; "is if a keyword" is answered by the parser's command-start flag, not the lexer alone. Predicts: any shell bug where a keyword works "everywhere except..." is a context-sharing bug. Bug class without it: hardcoding reserved-word recognition purely lexically. Applied in §13 (Phase 1), §14.6.

MM2 — Expansion is a pipeline of pure functions over an ordered list, not a rewrite loop. Compressed insight: each of the 8 stages (§8.3) consumes the previous stage's output type, never re-visits an earlier stage's input. Predicts: any "double expansion" bug (a value expanded twice) is a stage-boundary violation. Bug class without it: naive "expand until fixed point" implementations that silently double-substitute attacker-controlled data (Threat Model T2). Applied in §16.

MM3 — A process group is a scheduling unit for signals, not for output. Compressed insight: tcsetpgrp decides who receives keyboard-generated signals, and is orthogonal to which process's stdout reaches the terminal (that's just inherited FDs, §8.4). Predicts: "backgrounded job stole my prompt" bugs are terminal-arbitration bugs, not FD-inheritance bugs. Bug class without it: conflating output correctness with signal correctness while debugging job control. Applied in §18, §8.5.

MM4 — A signal handler is not code, it is a wakeup. Compressed insight: the only async-signal-safe thing to do in a handler is note that something happened (P8); all actual work happens in the main loop after the fact. Predicts: any handler doing allocation/logging/locking is a latent heisenbug. Bug class without it: intermittent crashes only reproducible under signal load. Applied in §18.2, I7.

MM5 — An arena is a lifetime, not just an allocator. Compressed insight: bump-arena allocation (ADR-04) buys performance because it encodes "these nodes die together" as a type-level fact (I8), not merely because bumpalo::alloc is fast. Predicts: any attempt to keep an AST node alive past its script's execution needs an explicit re-architecture, not a workaround. Bug class without it: use-after-free attempts in languages without Rust's borrow checker (the historical C-shell bug class this design sidesteps). Applied in §11.3, Back-of-Envelope row 3.

MM6 — set -e is a contract about contexts, not a global flag. Compressed insight: POSIX section 2.11 lists exact syntactic positions where a non-zero status is "swallowed"; set -e is not "exit on any error," it is "exit on error, except in these named positions." Predicts: every "why didn't set -e catch this" bug reduces to identifying which swallow-context applies. Bug class without it: re-deriving the rules ad hoc per bug report instead of consulting one table. Applied in §17.6, I9.

MM7 — The grammar's irregularity is the spec, not a parser bug. Compressed insight: here-document deferred-read and command-substitution reparse are not implementation compromises — they are what POSIX section 2.10's grammar actually requires structurally (hence recursive descent over LALR, ADR-02, P4). Predicts: attempts to "clean up" the grammar into a regular one will silently break real scripts. Bug class without it: a from-scratch reimplementation that "simplifies" here-doc handling and breaks cat <<EOF | wc-class scripts. Applied in §14, §8.2.

MM8 — Determinism is a design choice, not a side effect of correctness. Compressed insight: $RANDOM's seed, set -o pipefail's exit-status rule, and LANG=C's collation are each an explicit decision to make a nondeterministic-feeling feature reproducible (P12), not merely "however the reference happened to behave." Predicts: any flaky CI test in this codebase traces to an unseeded or unpinned nondeterminism source. Bug class without it: unreproducible bug reports from users running an unpinned locale. Applied in §4, §19.9.

That wins when a team is willing to rewrite scripts for a better day-to-day interactive experience and doesn't need POSIX portability.

35. Back-of-Envelope Capacity Model

  1. AST arena footprint for the M1 fixture — lines × nodes_per_line × bytes_per_node = 100,000 × 8 × 48 B ≈ 38.4 MB for the single largest parse in the conformance suite (§4 M1, §11.3). Stays well below a container's typical memory ceiling.
  2. Tokenizer time for a 10 MiB corpus — size ÷ throughput = 10 MiB ÷ 200 MiB/s = 50 ms (derives M5's throughput target from the corpus size assumption, §13.4).
  3. Pipeline syscall count, 10-stage pipeline — forks(10) + setpgid(10) + pipes(N-1=9) + dup2(≈2/stage×10=20) + execve(10) = 59 syscalls; at ~1–5 µs/syscall on the reference host, ≈ 60–300 µs raw syscall cost, leaving headroom under the ≤ 400 µs/stage budget (§4) for loader/dynamic-linking overhead in execve itself.
  4. Word-fragment allocation volume, a 5,000-line real-world script — lines × words_per_line(5) × fragments_per_word(3) = 5,000 × 5 × 3 = 75,000 fragments, confirming the stated 10⁴–10⁵ order of magnitude (ADR-08, §16.7).
  5. Job-table memory at the §4 concurrency floor — max_jobs(256) × (sizeof(Job)=96B + avg_processes(3)×sizeof(Process)=24B) = 256 × 168 B ≈ 43 KB, trivial against the 5 MiB idle budget (M7, §11.5).
  6. Reaper ceiling — job_count × waitpid_cost(≈2 µs); at 10,000 concurrent jobs, one SIGCHLD-triggered reap sweep costs ≈ 20 ms, starting to compete with the 50 ms cold-start budget (M6) — this derives the "~10⁴ jobs" practical ceiling stated in Scalability Analysis.
  7. History file annual growth, heavy user — avg_command_bytes(40) × commands_per_day(500) × days(365) ≈ 7.3 MB/year — justifies why history rotation is an explicit operator action (ADR-17, §21.10), not automatic.
  8. rc-file parse time at cold start — rcfile_lines(200) × per_line_parse_cost (500 ms ÷ 100,000 lines = 5 µs/line) = 200 × 5 µs = 1 ms, leaving ≈ 49 ms of the 50 ms cold-start budget (M6) for process init and PATH-hash construction (§12.7).
  9. Transient FD budget, 10-stage pipeline — ≤3 FDs × stage_count (§4) = 3 × 10 = 30 transient FDs momentarily open before both pipe ends close post-fork — well under a typical ulimit -n of 1024.
  10. Completion cache memory, typical PATH — binaries(2,000) × (name_bytes(12) + xxHash_entry_overhead(16)) = 2,000 × 28 B ≈ 56 KB (ADR-07, §21.7).

37. Alternative Architectures (Roads Not Taken)

AA-1 — Bytecode VM instead of tree-walking interpreter.

AST ──compile──▶ Bytecode ──▶ VM dispatch loop ──▶ effects
(this design skips the middle step: AST ──walk──▶ effects, §8.4)

Regime where it wins: scripts executed many times per second in a hot loop where compile-once/run-many amortizes the compilation cost (e.g., a templating engine calling the same shell function thousands of times). Real system: Tcl's tclsh compiles scripts to an internal bytecode representation before execution. Rejected because: this project's dominant cost is fork+exec latency (§4), not AST-walk dispatch overhead — a bytecode compiler adds a whole subsystem (compiler, verifier, VM) to shave a cost that isn't the bottleneck, and it complicates the arena-lifetime story (P10, MM5) since bytecode would need its own separate memory model.

AA-2 — posix_spawn/vfork instead of fork+execve.

this design: fork() [copy address space] → execve() in child
alternative: posix_spawn() [kernel-assisted, no full copy] → running child directly

Regime where it wins: workloads dominated by process-creation latency on a system where fork's copy-on-write setup (page-table duplication) is measurably expensive relative to execve — high-pipeline-fan-out scripts on memory-constrained hosts. Real system: dash uses vfork() as an optimization for the last command in certain simple pipelines. Rejected because: fork+execve gives the executor full control over the child's file descriptors and process-group state before the exec (§8.4 step 5, P7's job-control arbiter needs this window); vfork's shared-address-space window until execve is a correctness hazard for a design this dependent on precise FD/pgid setup.

AA-3 — readline-based instead of a custom line editor.

this design: crates/editor (custom termios+buffer+render, §20.2)
alternative: bind against GNU readline / libedit

Regime where it wins: a project whose interactive surface is a secondary concern and wants maximum keymap compatibility with existing .inputrc configuration with minimal engineering investment. Real system: bash binds directly to GNU readline (lib/readline/). Rejected because: this project's conformance harness requires PTY-level control over exact render output (ADR-05) and vi-mode parity testing that a third-party library's internals do not expose cleanly; P13 (separable line editor) requires an implementation this project fully controls.

AA-4 — A regular, LALR-friendly grammar instead of POSIX's irregular one.

this design: recursive descent over POSIX's grammar, irregular at
             here-docs / $() / quoting (§8.2, ADR-02)
alternative: a shell language designed from scratch to be table-parseable

Regime where it wins: designing a new shell language unconstrained by POSIX compatibility, where here-document and command-substitution syntax can be chosen to be regular from day one. Real system: rc (Plan 9, Duff 1990, §5 Required Reading) deliberately redesigned shell syntax to avoid these irregularities. Rejected because: this project's goal is POSIX conformance (P1, §1.1) — a cleaner grammar that isn't POSIX is a different project; every irregularity this design routes around (here-doc deferred read, $() reparse) is a POSIX section 2.10 requirement, not an implementation accident (MM7).

39. Glossary

  • AST — abstract syntax tree; the parser's arena-allocated output (§11.3).
  • Arena allocation — bump-pointer allocation into one contiguous region, freed in bulk rather than per-object (ADR-04, P10).
  • Assignment word — a name=value token recognized before command-name resolution (§8.2).
  • bumpalo — the Rust arena-allocator crate backing the AST and word fragments (ADR-04, ADR-08).
  • Built-in (regular) — a shell-internal command without the special-built-in's set -e/assignment-persistence properties (§15.1).
  • Built-in (special) — one of POSIX's 15 built-ins with syntax-error-exits-shell and assignment-persistence semantics (POSIX section 2.14, §15.1).
  • Command substitution — $(...)/backtick expansion of a subshell's stdout into a word (§8.3 stage 4).
  • Compound command — if/for/case/while/until/brace-group/subshell (§8.2).
  • Controlling terminal — the TTY a process group can receive keyboard signals from; arbitrated by tcsetpgrp (§8.5).
  • Dot sourcing — the ./source special built-in, executing a file's commands in the current shell rather than a subshell (§15.2).
  • Extglob — bash extended glob patterns (?(...), *(...), +(...), @(...), !(...)), gated on Mode::Bash (§16.2).
  • Field splitting — IFS-driven division of expanded text into words (§8.3 stage 6).
  • FIFO — named pipe, used to materialize process substitution (§23.2).
  • fork — the syscall creating a child process by address-space copy (§8.4).
  • Glob — pathname expansion via POSIX pattern matching (§8.3 stage 7, §11 pattern crate).
  • Here-document — <</<<- redirection whose body is literal text up to a tag line (§8.1).
  • IFS — Internal Field Separator, the field-splitting delimiter set (§8.3 stage 6).
  • Job — one pipeline's process group plus its table bookkeeping (§11.5).
  • Job control — the subsystem arbitrating the controlling terminal between shell and children (§8.5, §18).
  • Lexical context — one of the five tagged states the lexer operates in (§8.1).
  • Monitor mode — set -o monitor / -m, enabling job-control notifications.
  • OTLP — OpenTelemetry Protocol, the tracing export format used when OSH_TRACE=1 (ADR-19).
  • Parameter expansion — ${...}/$name substitution, 14 POSIX forms + 4 bash extensions (§8.3 stage 3, §11.2).
  • PATH hash table — the cached mapping from command name to resolved executable path (§11.4, ADR-07 sibling).
  • Pgid — process-group id; the pid of the group's leader process (§11.5).
  • Pipeline — a sequence of commands connected via |, each stage a separate process (§8.2).
  • POSIX — IEEE Std 1003.1-2017, the Shell & Utilities specification this project conforms to (§1.1, §5).
  • Quote removal — the final expansion stage stripping quoting metadata from surviving fields (§8.3 stage 8).
  • Reaper — the waitpid-loop component reconciling process exits into job-table state (§18.2, §11.5).
  • Recursive descent — a hand-written top-down parsing technique, one function per grammar non-terminal (ADR-02, §14.2).
  • Redirect — an I/O-operator + target-word AST node (Redirect, §11.3).
  • Restricted shell — osh -r, a least-privilege mode disabling cd/exec/output redirection/PATH changes (§22.2, I12).
  • Self-pipe trick — writing one byte from a signal handler to a pipe read by the main loop, for async-signal-safe dispatch (P8, §18.2).
  • setpgid — the syscall placing a process into a process group (§8.5, I5).
  • SIGCHLD — the signal delivered on a child's state change, driving the reaper (§18.2).
  • SIGTTOU — the signal sent to a background process group attempting terminal writes; self-ignored by the arbiter during its own tcsetpgrp call (§18.2, §18.6).
  • Subshell — a ( ... ) compound command, executed in a forked child (§8.2, §17.6).
  • tcsetpgrp — the syscall assigning the controlling terminal's foreground process group (§8.5, I6).
  • Token — the lexer's output unit: a Word, Operator, Reserved, IoNumber, or Newline/Eof (§11.1).
  • VSC — Verification Suite for Commands, the external POSIX conformance test suite integrated in Phase 12 (§24.2).
  • waitpid — the syscall retrieving a child's exit/stop status (§18.2).
  • Word — a sequence of WordParts retaining quoting context through expansion (§11.1).
  • WordPart — one lexical/quoting unit of a word (literal, quoted, substitution, etc.) (§11.1).
  • ShellMode — the Posix/Bash/Enhanced mode enum gating extension surfaces (§11.6, P1, P2).
  • ShellFlags — the bitflag set for set -e -u -o pipefail and related runtime options (§11.6).
  • xxHash — the non-cryptographic hash used for completion-cache keys (ADR-07).
  • ADR — Architecture Decision Record; one row per locked technology choice (§9).
  • Invariant — a system-wide correctness property enforced and telemetered per §7.
  • Principle — a numbered design rule (P1…P14) governing every later decision (§6).
