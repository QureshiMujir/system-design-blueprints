1. Goal & Scope

Append-only event-sourcing framework: durable log as system of record; aggregates rebuilt by deterministic replay; command handling w/ optimistic concurrency; checkpointed idempotent projections; snapshots; catch-up subscriptions; schema evolution via upcasting; sagas/process managers; CQRS query side. Embedded library first, optional single-binary server second.

1.1 What is built (precise terms)

  • Append-only event store + stream API — segmented log (monotonic per-stream version, global per-partition offset, fsync durability, scan-recover); append(stream, expected_version, events) -> AppendResult w/ optimistic-concurrency CAS + idempotent dedup-key retries (§3).
  • Aggregate repository + snapshots — load by replay (newest snapshot ≤ target + tail); command→events fold; pluggable Aggregate trait.
  • Projections / read models — checkpointed, idempotent, rebuildable from 0; pluggable store (KV/SQL).
  • Subscriptions — catch-up→live handoff; per-partition ordered; backpressure-aware dispatcher.
  • Upcaster pipeline — versioned payloads transformed lazily on read; chained vN→vN+1.
  • Sagas / process managers + CQRS query side — react→emit commands, persist state, timers, compensation; commands mutate via aggregates+log, queries from read models.

1.2 System boundaries

  • In scope: log durability, replay determinism, concurrency control, projection consistency, schema evolution, subscription delivery, saga orchestration, single-node correctness, optional multi-node partitioning (P12).
  • Out of scope (consumed): block storage/filesystem, OS page cache, TLS stack, external KV/SQL projection stores, cluster membership/consensus lib.

1.3 Explicit non-goals

  • Not a general-purpose database — no ad-hoc event query language, no payload secondary indexes, no SQL planner; queries hit read models only.
  • Not a message broker — no topic ACLs, consumer-group rebalancing, external pub/sub; subscriptions framework-internal.
  • Not a workflow engine UI — sagas are code, not a visual designer.
  • Not a CRDT / multi-master store — single writer per partition; conflicts resolved by optimistic concurrency, not merge.

1.4 Deployment model

  • Embedded library (primary) — links into a host owning command dispatch + projection hosting; one OS process owns the log dir.
  • Optional server (P12+) — single static binary exposing append/read/subscribe over a binary protocol; partitions shardable; one writer/partition.
  • Storage: dir of segment + snapshot + checkpoint files; no external dependency for core.

1.5 Target users

  • Operators — run host/server; manage disk; monitor lag/throughput; rebuild projections; backup/restore.
  • Developers — define aggregates/commands/events/projections/sagas; rely on replay determinism + schema evolution.
  • SRE / incident responders — explain/replay tooling, dashboards, runbooks for divergence/corruption.

1.6 Phase 0 deliverable (crates / modules)

14 crates (full file map in §10 + Appendix A): es-core (envelopes, ids, errors, traits); es-log (segments, offsets, fsync, recovery); es-store (EventStore, stream API, concurrency, idempotency); es-codec (serialization, content addressing, schema tags); es-snapshot (store, policy, load); es-aggregate (repository, command handling, fold); es-projection (checkpointed runtime, store trait, rebuild); es-subscribe (catch-up+live dispatch, backpressure, ordering); es-upcast (registry + lazy pipeline); es-saga (runtime, timers, command emit, compensation); es-query (CQRS read-model facade); es-obs (metrics, tracing, logging, explain/replay); es-server (optional: protocol, routing, multi-node); es-test (conformance harness, generators, faults, replay driver).

1.7 What later phases unlock

  • P5 snapshots → bounded load latency; P6 projections → CQRS read side; P7 subscriptions → live read-model updates + saga triggers; P8 upcasting → schema evolution w/o rewrites; P9 sagas → cross-aggregate workflows + compensation; P12 distribution → horizontal scale via partitioning + multi-node ordering.

1.8 Deferred features

Each gated behind a PhaseDeferred(...) marker resolving to a real heading; all catalogued in the Deferred Features Register (back-matter) w/ anchor, building phase, and un-defer trigger.

1.9 Timeline

  • Phase 0: 6–14 weeks (P1–P6 core path).
  • P7–P9: +4–6 weeks. P10–P11: +3–4 weeks. P12–P13: +4–8 weeks.

1.10 Recommended language

Rust. Deterministic destructors + explicit fsync control; zero-cost abstractions on hot paths; ADTs + exhaustive matching for envelopes/schema versions; ownership removes subscription/saga races; no GC tail; no_std core. Rejected: Go (GC p99; weak sum types); Java/C# (mature — Axon, EventStoreDB — but GC tail + JIT warmup harm recovery SLO); C++ (memory-unsafe across concurrent subscriptions).

1.11 Prerequisites

  • Storage / WAL — log-structured storage, segment compaction, fsync semantics, torn-write avoidance.
  • Concurrency — lock-free queues, single-writer discipline, backpressure, memory ordering.
  • Distributed systems — partitioning, ordering guarantees, exactly-once vs at-least-once, idempotency.
  • Serialization / schema evolution — fwd/back compatibility, upcasting, content addressing. Consistency — read-your-writes, eventual projection consistency, optimistic concurrency.

2. Why Build This

2.1 Unique knowledge

  • Log as source of truth — a fold over an immutable fact log; separates what happened (events) from current shape (projections).
  • Deterministic replay — same event sequence ⇒ byte-reproducible state/projections; side-effect-free apply.
  • CQRS — write model for invariants + concurrency, read models for queries; intentional divergence.
  • Idempotency — handlers tolerate redelivery; checkpointing turns at-least-once into exactly-once effect.
  • Exactly-once projection — atomic (apply effect, advance checkpoint), not network magic.

2.2 Historical / architectural significance

  • Lineage: WAL (System R, ARIES) → log-structured storage (LSM) → Kafka log → event sourcing (Fowler, Vernon) → durable execution (Temporal).
  • Reframes the database — log primary, tables derived caches; inverts the default model; underpins CDC, stream processing, audit systems.

2.3 Engineering muscles

  • Durable append-only storage + crash recovery; race-free concurrency; live schema evolution; consistency reasoning; idempotency design; replay/forensics tooling; perf under fsync.

2.4 Production concepts

  • Backpressure, checkpointing, optimistic concurrency, snapshotting cadence, projection rebuild ops, poison-event quarantine, rolling upgrade w/ schema change.

2.5 Cross-links

  • WAL / ARIES — durability + recovery mirror the log's fsync + scan-recover.
  • Kafka — partitioned ordered log; consumer offsets ≈ projection checkpoints.
  • CDC — projections ≈ in-process change-data-capture sinks.
  • Stream processing — projections + sagas ≈ stateful stream operators.
  • MVCC — expected-version concurrency ≈ optimistic MVCC validation.
  • Durable execution (Temporal) — sagas w/ timers/compensation ≈ durable workflows.

2.6 Calibration value

  • A correct event store exercises the full stack — disk durability, distributed ordering, app-level consistency. Replay determinism, exactly-once projections, and crash recovery under fault injection demonstrate end-to-end correctness reasoning.

2.7 What Mastery Looks Like

  • Design + verify a crash-safe append-only log: torn-write recovery, fsync-policy ↔ RPO arithmetic, dir-fsync ordering (Phase 1).
  • Build optimistic concurrency that survives 64-writer races with zero lost updates and explain the conflict-rate model (Phase 2).
  • Bound aggregate load latency by deriving snapshot interval from replay-tail math, never by guessing (Phase 5).
  • Turn at-least-once delivery into exactly-once effect via atomic checkpointing + idempotent apply, proven by crash injection (Phase 6).
  • Build catch-up→live delivery with bounded backpressure where a 10× slow consumer costs the writer ≤ 2% (Phase 7).
  • Evolve schemas on an immutable log with chained upcasters and a safe readers-before-producers rollout order (Phase 8).
  • Orchestrate cross-aggregate workflows with durable timers, exactly-once command emission, and reverse-order compensation (Phase 9).
  • Choose and defend a consistency mode (eventual / read-your-write / strong-from-aggregate) per query, quantitatively (Phase 10).

3.1 Command Side

CommandBus routes a command to its aggregate handler; repo loads state (snapshot ≤ head + replay tail), calls pure handle(cmd,&state) -> Result<Vec<Event>,DomainError>. Events append at expected_version = loaded_version; conflicts ⇒ VersionConflict. Owns invariants; never writes read models.

3.2 Event Store / Log

Wraps es-log w/ stream API + optimistic concurrency: validates expected_version under a per-partition writer lock, assigns next version + global offset, serializes envelopes, durably appends, returns AppendResult. Single mutation point; all else reads.

3.3 Append-Only Log (es-log)

Monotonically numbered segments; active appended, sealed immutable; each record length-prefixed w/ CRC, offset, stream id, version, ts, payload. fsync configurable. Recovery scans active segment, validates CRC, truncates at first torn record. No in-place mutation.

3.4 Stream Partitioning

partition = hash(stream_id) mod P (P fixed at init; reshardable in P12). Each partition = independent ordered log (own segments/offsets/writer). Cross-partition global order NOT provided — PhaseDeferred("Deferred Features Register"); per-partition order is total — the subscription-ordering unit.

3.5 Aggregate Repository

Folds events: state = fold(seed, apply), apply pure+total; w/ snapshots seeds from newest + folds tail. Exposes load/save; no cross-command cache by default — write-through cache is PhaseDeferred("Deferred Features Register").

3.6 Snapshot Store

State keyed (stream_id, version); taken when version - last_snapshot_version ≥ interval; load = newest ≤ target + replay (snapshot.version, target]; optimization only, never authoritative (INV-5).

3.7 Projection / Read-Model Builders

Consume ordered stream; apply each event idempotently to a read-model store; advance checkpoint atomically w/ effect. Rebuildable (drop model+checkpoint, replay from 0). Failures pause the projection, not the writer.

3.8 Subscription / Catch-up Dispatcher

Delivers per-partition-ordered events; a subscriber runs catch-up (offset → head) then live (tail); backpressure bounds a laggard. At-least-once ordered; exactly-once effect is the consumer's via checkpointing.

3.9 Saga / Process-Manager Runtime

Stateful consumer: reacts to events, persists saga state, emits commands to CommandBus, schedules timers/timeouts, compensates on failure. Event-sourced where possible (same replay/idempotency).

3.10 Upcaster Pipeline

On read each payload tagged (event_type, schema_version); registry chains v1→…→vCurrent so consumers see the latest shape. Lazy, pure, total; never rewrites bytes. Unknown future versions rejected; missing upcaster = startup error.

3.11 Read-Model Store (KV/SQL)

Pluggable backend (embedded KV default, SQL optional) holding projection outputs + checkpoints; atomic (mutation + checkpoint advance) per commit, or idempotent upsert keyed by offset.

3.12 External Interfaces

Embedded API (EventStore, repository, projection host); optional server (binary append/read/subscribe + routing); admin/replay tools (explain, replay, rebuild, verify).

6. Design Principles

Principle IDs P1…P15 (Pn ≡ §6.n below), referenced as "principle 6.n" throughout.

6.1 Events are immutable facts

Once appended, an event is never mutated/deleted in place. Tradeoff: storage grows w/o snapshots/archival; corrections are compensating events. Operational: trivial incremental backup; clean audit + replay. Violation: in-place edits destroy replay determinism + audit integrity.

6.2 The log is the source of truth

All state derives from log; read models + snapshots are disposable caches. Tradeoff: every query needs a projection; no ad-hoc raw-event queries. Operational: any read model rebuildable; DR = restore log + rebuild. Violation: authoritative projection creates undetectable drift.

6.3 Replay determinism

apply/handle pure: no clock/RNG/IO except injected, recorded ports. Tradeoff: time/random modeled as events or injected. Operational: enables differential testing + forensic replay. Violation: non-determinism diverges rebuilds.

6.4 Idempotent projections and handlers

Every consumer tolerates redelivery; effects keyed by offset/id. Tradeoff: defensive handlers (upsert, dedup). Operational: at-least-once ⇒ exactly-once effect. Violation: double-applied events corrupt read models.

6.5 Explicit versioning

Every payload carries (event_type, schema_version); upcasters bridge. Tradeoff: version bookkeeping + upcaster upkeep. Operational: rolling upgrades w/o log rewrites. Violation: silent drift ⇒ decode failures or misreads.

6.6 Backpressure on subscriptions

Dispatcher bounds per-consumer buffers; slow consumer slows only itself, never writer. Tradeoff: laggards fall further behind. Operational: prevents OOM + head-of-line collapse. Violation: unbounded buffering ⇒ OOM; writer-coupled-to-slowest ⇒ collapse.

6.7 Crash-only design

No clean-shutdown path needed; recovery-from-kill is the only path. Tradeoff: every write crash-consistent. Operational: kill = restart. Violation: persist-only-on-graceful-shutdown loses data on crash.

6.8 Optimistic concurrency, single writer per partition

Writers supply expected_version; conflicts rejected, not merged; one writer/partition serializes appends. Tradeoff: hot-stream contention ⇒ retries. Operational: no distributed locks within a partition. Violation: blind Any appends ⇒ lost updates.

6.9 Checkpoint atomicity (exactly-once effect)

Checkpoint advances atomically w/ effect (one txn or idempotent-by-offset upsert). Tradeoff: store must be transactional or idempotent. Operational: crash between effect + checkpoint is safe (idempotent replay). Violation: non-atomic ⇒ gaps or double-application.

6.10 Snapshots are optimizations, never truth

Load can always reconstruct from log alone. Tradeoff: tolerate snapshot staleness/version skew. Operational: corrupt snapshot ⇒ discard + replay, never loss. Violation: canonical snapshot hides divergence.

6.11 Total ordering is per-partition, not global

Ordering holds within a partition; cross-partition causal-at-best (deferred). Tradeoff: cross-partition sagas must not assume global order. Operational: linear writer scaling. Violation: global-sequence assumptions break when sharded.

6.12 Fail-stop on ambiguity

On undecodable events, missing upcasters, or checksum failure, stop the component loudly, never guess. Tradeoff: availability cost on poison. Operational: poison quarantined; operator decides. Violation: best-effort decode silently corrupts state.

6.13 Separation of write and read models (CQRS)

Commands never read projections for invariants; queries never touch write path. Tradeoff: read-your-write needs explicit handling. Operational: independent scaling per side. Violation: coupling reintroduces the monolithic-state problems ES avoids.

6.14 Bounded, observable resource use

Every buffer/queue/cache has a ceiling + a gauge. Tradeoff: tuning surface. Operational: predictable memory + early lag alerts. Violation: unbounded growth ⇒ OOM.

6.15 Deterministic file format w/ self-description

Every record/segment self-describing (magic, version, length, CRC); recovery never needs external metadata. Tradeoff: per-record overhead. Operational: any segment parseable standalone. Violation: out-of-band metadata loss ⇒ unreadable log.

8.12 Edge cases / malformed / failure paths

11.1 EventEnvelope

struct EventEnvelope { event_id, stream_id, stream_version, global_offset,
                       partition, event_type, schema_version, payload, metadata, recorded_at }
  • Ownership: store-owned on write; readers get Arc views. Mutation: immutable post-construction. Concurrency: Send + Sync. Persistence: serialized per §8.3 into active segment; payload via codec (ADR-05), header fixed binary. Compatibility: header versioned by record.version; new fields appended only.

11.2 EventMetadata

struct EventMetadata { correlation_id, causation_id, actor, source, content_type, trace_context, custom }
  • Mutation: immutable; built by the command layer. Persistence: codec-encoded, length-prefixed after payload. Compatibility: custom map ≤ 4 KB; unknown keys preserved on upcast.

11.3 StreamId

struct StreamId(String);  // "<category>-<instance>"
fn category(&self) -> &str; fn partition(&self, p_count: u16) -> u16;
  • Constraints: ≤ 255 bytes, ASCII, exactly one category-instance separator; value type, cheap clone.

11.4 ExpectedVersion

enum ExpectedVersion { Any, NoStream, StreamExists, Exact(u64) }
  • Semantics: NoStream ⇒ must not exist; Exact(v) ⇒ current==v; Any ⇒ no check (lint-warned); StreamExists ⇒ any existing. Mismatch → AppendError::VersionConflict{expected, actual}.

11.5 AppendResult

struct AppendResult { stream_version: u64, first_offset: u64, last_offset: u64, partition: u16 }
  • Contract: stream_version = last appended event's version; offsets dense, partition-scoped.

11.6 Aggregate trait

trait Aggregate {
  type Event; type Command; type Error;
  fn empty() -> Self;                               // seed state
  fn apply(&mut self, e: &Self::Event);             // pure, total fold step
  fn handle(&self, c: Self::Command)                // pure decision
        -> Result<Vec<Self::Event>, Self::Error>;
  fn category() -> &'static str;
}
  • Ownership: repository owns instances per load; not shared mutably. Mutation: only via apply; handle is &self. Persistence: state persisted only as a snapshot. Compatibility: apply handles all historical shapes.

11.7 Command

trait Command { fn target_stream(&self) -> StreamId; fn idempotency_key(&self) -> Option<Uuid>; }
  • Contract: idempotency_key enables dedup (INV-11 path); target_stream routes to partition.

11.8 EventStore interface

trait EventStore {
  fn append(&self, stream: &StreamId, expected: ExpectedVersion, events: &[RawEvent])
        -> Result<AppendResult, AppendError>;
  fn read_stream(&self, stream: &StreamId, from: u64, max: usize)
        -> Result<StreamSlice, ReadError>;
  fn read_all(&self, partition: u16, from_offset: u64, max: usize)
        -> Result<LogSlice, ReadError>;
  fn head(&self, stream: &StreamId) -> Result<Option<u64>, ReadError>;
}
  • Concurrency: &self (interior sync); store Send + Sync; appends serialized per partition, reads concurrent + lock-free where possible. Persistence: delegates to es-log. Compatibility: stable trait; additive methods only post-1.0.

12. Phase 1 — Event Store Core (Append-Only Log)

12.1 Objectives

  • Durable append-only log: segment files; dense per-partition offsets; configurable fsync; crash recovery (scan + truncate-to-last-valid); self-describing records (magic+len+crc+header, §8.3).
  • Append + sequential read iterators; no stream/concurrency semantics yet (P2).

12.2 Detailed Implementation Steps

  • Modules: segment.rs, writer.rs, reader.rs, recover.rs, fsync.rs, index.rs (Appendix A).
  • Segment layout: segment-<u64:010>.log; header [magic "ESSG"|format_ver u8|partition u16|base_offset u64|create_ts i64] + records (§8.3); roll at segment_bytes (default 256 MiB) or count cap. Self-describing per principle 6.15; append-only layout after paper P7 (LFS) + B4 Ch. 3.
  • Append: serialize into reusable buffer; write + policy fsync; update next_offset/active_file_pos; sparse-index per index_interval (default 4096) — design after R4 (Kafka OffsetIndex).
  • fsync policy: enum FsyncPolicy { PerBatch, GroupCommit{window_ms}, OsFlush }. Group-commit: commit thread coalesces appends, one fdatasync, signals waiters (after R4/paper P4 group commit; durability semantics per B4). Persist durable_offset distinct from appended_offset — the watermark enforcing INV-12.
  • Data structures: ActiveSegment{file, base_offset, next_offset, pos, sparse_index}; SegmentDir{sealed, active} (lock-free sealed reads, single writer per ADR-09). offset→(segment,pos) by binary search on base offsets + sparse index then linear scan; recovery walks last segment validating CRC (INV-7, S7) + offset density (INV-3), stops at first failure, truncates to last-valid — the redo-pass analogue of paper P1 (ARIES).
  • Durability: fdatasync on data; dir fsync per segment create/roll; O_APPEND atomic advance under single writer (INV-1; crash-only per principle 6.7).
  • Observability hooks: es_log_appends_total, es_log_bytes_written_total, es_log_fsync_total, es_log_fsync_seconds (histogram), es_log_recovery_truncated_bytes, es_log_durable_offset (gauge).
  • Test harness: LogHarness — append N, kill (truncate to arbitrary byte), reopen, assert recovery to last-valid + offset density; torn-write simulator.

12.3 Deliverable

  • es-log crate: open log dir, append raw record, read-by-offset/iterate, recover on open. CLI tools/es-verify reports record count, last offset, CRC failures.

12.4 Acceptance Criteria

  • Append ≥ 1M records/s w/ OsFlush, ≥ 200k/s w/ GroupCommit(10ms) on NVMe (≤ 512 B records).
  • Recovery of a 10 GB log ≤ 3 s (active-segment scan only).
  • Kill-and-recover (1000 iterations, random truncation): 100% recover to last valid record, zero offset gaps, zero false-valid reads; CRC verified on 100% of reads (corrupted byte → CorruptRecord{offset}).

12.5 Conformance Fixtures

  • append/basic_roundtrip.bin — N records, expected offsets/CRCs; clean_segment_roll.bin — crosses boundary (2 files).
  • malformed/torn_tail_partial_record.bin — record truncated mid-body; expected recovery offset.
  • malformed/crc_corrupt_mid.bin — flipped bit mid-segment; CorruptRecord{offset} (no truncation).
  • replay/sequential_scan.expected.json — ordered offsets for differential replay; regression/empty_segment_header_only.bin — header only, clean open, next_offset=base.

12.6 Pitfalls

  • write() success ≠ durable — fdatasync per policy + track durable_offset.
  • Retrying a failed fsync can falsely succeed: after an EIO the kernel may mark dirty pages clean, so the retry reports success on lost data — the PostgreSQL "fsyncgate" finding (2018; public pgsql-hackers/LWN record, Postgres now panics on fsync failure). Policy here: fsync error is fatal — crash + recover (principle 6.7), never retry-and-continue.
  • Missing dir fsync after segment create — new file may vanish on crash.
  • Recovery trusting file length over CRC-walk — accepts torn records; sparse-index must rebuild tail on truncation.

12.7 Performance Concerns

  • fsync governs throughput; group-commit amortizes it (tune window_ms vs RPO); CRC-32C via SSE4.2; buffer reuse + writev; mmap sealed reads for replay/rebuild.

12.8 Edge Cases

  • Record > segment_bytes → RecordTooLarge (oversized segment deferred).
  • Crash mid-segment-roll (active sealed, new uncreated) → recovery completes the roll.
  • Disk full mid-append → atomic fail (no partial ack); durable_offset unchanged. Zero-length payload valid; backward recorded_at skew allowed (ordering uses offset).

12.9 Failure Analysis

  • Torn tail write: CRC fails on last record → truncate to prior boundary → loss ≤ unsynced batch; detect via recovery_truncated_bytes.
  • Mid-segment bit-rot: CRC fails on read → CorruptRecord → restore segment from backup; no mid-file auto-truncate.
  • fsync lies (some SSDs): documented battery-backed-cache assumptions; RPO caveats in runbook. Partial dir entry: dir-fsync ordering yields consistent old-or-new state.

12.10 Operational Notes

  • Backup = incremental sealed segments + active w/ durable_offset; es-verify in CI + as health check. Monitor es_log_fsync_seconds p99 (alert > 50 ms); fsync↔RPO matrix in docs/runbooks/durability.md.

13. Phase 2 — Stream API + Optimistic Concurrency + Idempotent Appends

13.1 Objectives

  • Stream semantics over the raw log: per-stream monotonic version, expected-version CAS, idempotent retries via idempotency key; map streams to partitions, one writer/partition serializes appends.

13.2 Detailed Implementation Steps

  • Modules: store.rs, stream.rs, concurrency.rs, dedup.rs.
  • Stream version index: in-memory Map<StreamId,u64> rebuilt on startup by log scan (or persisted checkpoint) — the log is truth, the index a cache (principle 6.2); per-partition shard bounds lock scope.
  • Append flow: lock partition writer (ADR-09, principle 6.8); validate expected_version (INV-6 — optimistic validation after B1 Ch. 7); assign stream_version=current+1+i (INV-2), global_offset=next+i (INV-3); build records; delegate to es-log; update index + dedup; return AppendResult.
  • Idempotent appends: idempotency_key checks dedup cache (bounded LRU + persisted (stream,key)→AppendResult tail surviving restart); hit returns recorded result, no re-append (INV-11 — Idempotent Receiver after B6).
  • Data structures: PartitionWriter{lock, next_offset, log_handle}; StreamIndex{shards: [RwLock<HashMap<StreamId,u64>>; N]}; DedupCache{lru, persisted_tail}. Expected-version resolution (NoStream/Exact/StreamExists/Any); startup index = forward scan accumulating max version/stream + last offset/partition.
  • Synchronization: per-partition (not per-stream) writer lock bounds lock count at P; reads lock-free against ArcSwap snapshot; index rebuildable from log, checkpoint speeds startup.
  • Observability hooks: es_version_conflict_total, es_append_retry_total, es_dedup_hits_total, es_active_streams (gauge), es_partition_append_seconds (histogram).
  • Test harness: concurrent-append fuzz — N threads, one stream, Exact; assert one winner, losers VersionConflict, no gaps.

13.3 Deliverable

  • es-store exposing §11.8 EventStore w/ optimistic concurrency + idempotent append; startup index rebuild from es-log.

13.4 Acceptance Criteria

  • 64 concurrent writers, one stream: zero lost updates, dense versions, conflict rate matches a contention model.
  • Idempotent retry of an acked append returns the same AppendResult, appends nothing.
  • 100M-event startup index rebuild ≤ 30 s; NoStream to an existing stream → VersionConflict{expected:NoStream, actual:v}.

13.5 Conformance Fixtures

  • append/expected_version_matrix.json — ExpectedVersion × stream state → outcome; append/idempotent_retry.json — same key twice → one append, same result.
  • replay/version_density.expected.json — per-stream version sequence.
  • malformed/empty_batch.json → EmptyBatch.
  • regression/concurrent_conflict_trace.json — winner/loser set for a contention scenario.

13.6 Pitfalls

  • Per-stream OS locks → lock explosion; use per-partition (hash-keyed) locks.
  • Unpersisted dedup cache → duplicate appends after restart; index as count vs max on 0-based versions → off-by-one.
  • Holding writer lock across fsync (PerBatch) serializes disk; release-after-enqueue w/ group-commit. Any everywhere → silent lost updates (lint).

13.7 Performance Concerns

  • Hot-stream writer-lock contention; mitigate via stream-key sharding + client batching. Dedup lookups O(1); ArcSwap index snapshots avoid read locks for head().

13.8 Edge Cases

  • First event w/ Exact(0) vs NoStream — both valid for a fresh stream.
  • Idempotency-key reuse w/ different payload → IdempotencyKeyReused.
  • Partition hash collisions fine (streams share a partition; versions isolated); append spanning a segment roll keeps per-record atomicity (offsets may straddle files).

13.9 Failure Analysis

  • Index/log divergence after crash: rebuild index from log (truth) on startup → self-heals.
  • Lost dedup tail: worst case a retry double-appends; mitigate via persisted tail + bounded retry windows; detect via duplicate-detection projection.
  • Writer-lock poisoning: core is panic-free; poisoned lock aborts the process + crash-recovers.

13.10 Operational Notes

  • es_version_conflict_total rate is a contention SLI (high ⇒ hot-aggregate smell); index-checkpoint cadence trades startup vs runtime overhead; runbook "high conflict rate" → inspect aggregate boundaries / batching.

15. Phase 4 — Aggregate Repository (Load by Replay, Command Handling)

15.1 Objectives

  • Reconstruct aggregates by folding events; route commands; append w/ correct expected-version.
  • CommandBus ties command -> load -> handle -> append -> dispatch-notify.

15.2 Detailed Implementation Steps

  • Modules: repository.rs, command_bus.rs.
  • Load → handle → save: read_stream(from=0) → decode + upcast → fold via Agg::empty() + apply (track loaded_version) — pure fold per principle 6.3, determinism per INV-9 (the paper-P5 Calvin discipline: state from agreed log order); handle(cmd)? pure (reject DomainError, empty → no-op); append(stream, Exact(loaded_version)|NoStream, &events) under INV-6, on VersionConflict reload + re-handle (bounded retries, default 5) or surface.
  • CommandBus: command type → aggregate → repository; wraps load/handle/save; emits command.handle span; notifies es-subscribe (P7) of new offsets. Idempotency key from (command_id) so retries dedup at store (P2, INV-11). Aggregate-boundary discipline per B2 Ch. 6.
  • Data structures: Repository<A: Aggregate>{store, codec, upcaster, snapshot_store(opt)}; CommandBus{handlers: Map<CmdType,Box<dyn CommandHandler>>}. Load lock-free; save serialized by partition writer (P2); no aggregate cached mutably across commands; no persistence beyond the log (snapshots P5).
  • Observability hooks: es_command_total{type,outcome}, es_command_seconds, es_aggregate_replay_events (histogram), es_command_retry_total.
  • Test harness: given-when-then DSL (after B2); replay-determinism loads twice, asserts identical state hash (guards INV-9).

15.3 Deliverable

  • es-aggregate: Repository + CommandBus; example Order/BankAccount aggregates.

15.4 Acceptance Criteria

  • Load + handle + save round-trip correct for example aggregates (given-when-then suite green).
  • Concurrency: two commands racing one aggregate → one wins, the other retries + succeeds or returns conflict (no invariant violation).
  • Replay determinism: same stream loaded twice → identical state hash (1M streams sampled); command latency p95 ≤ 1 ms w/ snapshots (P5) for streams ≤ snapshot_interval tail.

15.5 Conformance Fixtures

  • aggregate/order_given_when_then.json — scenarios → expected events/errors.
  • replay/aggregate_state_hash.expected.json — per-stream folded-state hash.
  • malformed/command_on_closed_aggregate.json → DomainError.
  • regression/conflict_retry_succeeds.json — race resolved by reload; compat/aggregate_replay_after_upcast.json — old events upcast → same state (P8).

15.6 Pitfalls

  • Impure handle/apply (clock/RNG/IO) → non-deterministic replay (INV-9); forgetting to upcast on load → stale shapes.
  • Any on save → lost updates; caching mutable aggregate w/o invalidation → stale state.
  • Unbounded conflict-retry on a permanently hot aggregate → livelock; cap + surface.

15.7 Performance Concerns

  • Long streams w/o snapshots → O(history) replay per load (P5 bounds it); decode+upcast dominates; batch-read + reuse buffers; borrow in apply not clone.

15.8 Edge Cases

  • Command produces zero events (idempotent no-op) → default success, nothing appended.
  • Aggregate at terminal state → command → DomainError, not a panic.
  • Fresh-aggregate NoStream while concurrent creator wins → VersionConflict → reload shows existing.

15.9 Failure Analysis

  • Replay divergence (impurity): caught by differential replay test; fix impurity, rebuild affected projections.
  • Conflict storm: indicates aggregate too coarse; runbook advises boundary redesign.
  • Decode/upcast failure mid-replay: load fails loudly (poison) rather than producing partial state.

15.10 Operational Notes

  • es_aggregate_replay_events p99 high → snapshot interval too large (tune P5); idempotency keys recommended for all external commands; given-when-then suite is the domain-logic regression gate.

16. Phase 5 — Snapshots (Snapshot Store, Snapshot-on-Threshold, Load-from-Snapshot)

16.1 Objectives

  • Bound load latency for long streams: persist state at intervals; load = newest snapshot ≤ head + replay tail. Snapshots are pure optimizations (INV-5, principle 6.10); the log stays authoritative.

16.2 Detailed Implementation Steps

  • Modules: store.rs, policy.rs.
  • Snapshot store: files snapshots/<stream_id>/<version:020>.snap or KV keyed (stream_id,version); header [magic "ESSN"|format_ver|stream_ver u64|schema_ver u32|codec_id|crc] + blob, per ADR-25.
  • Policy + load: after save, if new_version - last_snapshot_version ≥ snapshot_interval, snapshot async (per-aggregate interval, never blocks command path) — snapshotter pattern after R2 (Axon AggregateSnapshotter). Load: load_latest(stream, head) respecting INV-5; if snap.schema_ver == agg_schema_ver seed from blob, from = snap.version+1; else from = 0; replay read_stream(from). Never authoritative (principle 6.10).
  • GC: retain newest K per stream (default 2); delete older (recomputable); crash-safe (delete after newer durable) — cleaning model after paper P7 (LFS segment cleaning).
  • Data structures / algorithms: SnapshotMeta{stream, version, schema_ver, path}; SnapshotPolicy{interval, retain_k}. Load-latest = max version ≤ target (directory listing or KV range scan); creation re-folds nothing.
  • Synchronization: write off command path (background); idempotent (overwrite same (stream,version) safe); file fsync'd before usable; corrupt on load → discard + full replay.
  • Observability hooks: es_snapshot_written_total, es_snapshot_load_hit_total/miss_total, es_snapshot_replay_tail_events (histogram), es_snapshot_corrupt_total.
  • Test harness: with-vs-without snapshot → identical hash; corrupt → full-replay fallback; schema-bump discards stale snapshots.

16.3 Deliverable

  • es-snapshot integrated into Repository::load; background snapshotter; GC.

16.4 Acceptance Criteria

  • State from snapshot+tail == full replay (byte-identical hash) for all fixtures.
  • Aggregate load p95 ≤ 1 ms for streams w/ ≥ 10k events (interval 256) vs O(history) without.
  • Corrupt/missing snapshot → transparent full replay, no error to caller; snapshot write never increases command p99 (off-path verified).

16.5 Conformance Fixtures

  • snapshot/snap_plus_tail_equals_replay.json — state hash equality; threshold_trigger.json — snapshot at the right version.
  • malformed/corrupt_snapshot.snap → discarded, full replay, correct state.
  • compat/old_schema_snapshot.snap → discarded on schema bump.
  • regression/gc_retains_k.json — only newest K remain.

16.6 Pitfalls

  • Snapshot version > stream head (INV-5) from racing the writer → read version under append consistency.
  • Treating snapshot as authoritative hides divergence; always allow log rebuild. Not invalidating on schema change → decode into wrong state.
  • Blocking command path on snapshot fsync → latency regression; GC deleting the only valid snapshot before a newer is durable → load slowdown (not loss).

16.7 Performance Concerns

  • Interval tuning: small → more writes + storage, large → longer load tail (default 256, tune by replay histogram); compress snapshots (zstd) for large states; snapshot only when interval crossed.

16.8 Edge Cases

  • Concurrent snapshot writes for one stream → idempotent overwrite; keep highest version.
  • Snapshot of a terminal/closed aggregate → allowed (load appends tail = none); version < interval → never snapshotted.
  • Snapshot store unavailable → degrade to full replay + alert (no command failure).

16.9 Failure Analysis

  • Snapshot corruption: CRC fails → discard → full replay (no loss); es_snapshot_corrupt_total alarm + disk health check.
  • Stale snapshot after apply bug fix: invalidate by bumping aggregate schema_ver → forces recompute.
  • Snapshot ahead of log (impossible if INV-5 enforced): detection asserts + discards; investigate writer/version path.

16.10 Operational Notes

  • Runbook "force snapshot rebuild" → delete snapshots dir; loads fall back to replay + re-snapshot. Snapshot storage counted in amplification budget (GC bounds it); monitor hit ratio (low ⇒ interval too large or churn).

17. Phase 6 — Projections / Read Models (Checkpointed, Idempotent, Rebuildable)

17.1 Objectives

  • Build queryable read models from the stream; idempotent apply; atomic checkpointing (INV-4); full rebuild from 0; decoupled from the write path (CQRS, principle 6.13).

17.2 Detailed Implementation Steps

  • Modules: runtime.rs, checkpoint.rs, store.rs (projection-store trait), rebuild.rs.
  • Projection trait: §11.10. Runtime pulls ordered events (from es-subscribe, P7; in P6 a direct catch-up reader), calls apply(store, event, checkpoint), commits. Checkpoint ≈ Kafka consumer offset (paper P4) ≈ Axon tracking token (R2).
  • Checkpoint atomicity: (a) transactional — apply + checkpoint.offset=N in one txn; (b) idempotent upsert — effect keyed by global_offset (ON CONFLICT DO NOTHING or last_offset row), checkpoint advanced after. Mode per store capability. Encodes principle 6.9 + INV-4; checkpoint/idempotency semantics per B5 Ch. 1–3; inline-vs-async tradeoff studied in R3 (Marten).
  • Projection-store trait: trait ProjectionStore { fn begin()->Txn; fn commit(Txn); fn read_checkpoint(name,partition)->u64; }; default embedded KV w/ atomic batch; SQL adapter via transaction.
  • Rebuild engine: drop namespace + checkpoint → stream from 0 → apply → advance; builds new version alongside old (blue/green) then switches reads. Rebuild-from-0 guaranteed by principle 6.2 + INV-9; coordination-free because per-offset idempotent apply is monotone (paper P2, CALM).
  • Data structures / algorithms: ProjectionRuntime{projection, store, checkpoint, filter}; RebuildJob{projection_name, from=0, target_head, progress}. At-least-once delivery + idempotent apply = exactly-once effect; startup resumes from read_checkpoint, skips applied offsets.
  • Synchronization: per-partition checkpoint per projection; projections independent; a slow one never blocks others or the writer (local backpressure). Checkpoint durable w/ effect; crash mid-apply re-applies idempotently from last durable checkpoint.
  • Observability hooks: es_projection_lag_events/_seconds (gauge), es_projection_applied_total, es_projection_redelivery_total, es_projection_rebuild_progress, es_projection_errors_total{name}.
  • Test harness: crash between effect and checkpoint → no gap/no double effect; rebuild-and-diff vs live; idempotency property.

17.3 Deliverable

  • es-projection: runtime + checkpoint store + rebuild engine; example read models (order summary, balance).

17.4 Acceptance Criteria

  • Crash between apply and checkpoint (1000 trials) → rebuilt model identical to fault-free run (INV-4); replaying the full log twice yields identical read model.
  • Rebuild of 100M events ≥ 500k events/s; byte-identical to incrementally-built.
  • Read-model lag p95 ≤ 200 ms under nominal load (P7 live subscription).

17.5 Conformance Fixtures

  • projection/balance_projection.json — events → state; idempotent_double_apply.json — apply×2 == apply×1.
  • replay/rebuild_equals_live.expected.json — diff must be empty.
  • malformed/poison_event_in_stream.json → projection pauses at offset, others unaffected.
  • regression/crash_between_apply_and_checkpoint.json — recovery correctness.

17.6 Pitfalls

  • Non-atomic checkpoint vs effect → gaps or double-apply (INV-4); advancing checkpoint before durable effect → loss on crash.
  • Non-idempotent apply (balance += x w/o offset guard) → double counting on redelivery.
  • Shared mutable read model across projections → coupling (one namespace each); coupling projection failure to the writer → availability loss.

17.7 Performance Concerns

  • Batch commits (N/transaction) amortize store fsync (bound to keep lag low); targeted updates over full-row rewrites; rebuilds read sealed segments via mmap, parallelize across partitions.

17.8 Edge Cases

  • Projection interested in a not-yet-existing category → idle, no error.
  • Event of unknown type → ignore (filter) or poison if it claimed interest.
  • Checkpoint store and read-model store distinct (no shared txn) → must use idempotent-by-offset mode.

17.9 Failure Analysis

  • Projection divergence: detect via periodic rebuild-and-diff (sampled) → rebuild. Causes: non-idempotent apply, non-atomic checkpoint, apply bug.
  • Checkpoint loss: rebuild from 0 (idempotent) → recovers; bounded by rebuild time.
  • Poison event: pause at offset, quarantine, operator fixes (upcaster/skip) → resume. Stuck projection (slow store): lag alarm → scale store or batch tuning.

17.10 Operational Notes

  • Runbook docs/runbooks/projection-rebuild.md: blue/green rebuild + switch + decommission old. Live projection-store hot migration w/o rebuild is PhaseDeferred("Deferred Features Register").
  • Lag dashboards per projection; alert on lag > 2 s or error rate > 0. Rebuild is an expected routine op (schema change, bug fix), not emergency-only.

18. Phase 7 — Subscriptions / Catch-up Dispatcher (Live + Catch-up, Backpressure, Ordering)

18.1 Objectives

  • Deliver per-partition-ordered events to consumers (projections, sagas) w/ a seamless catch-up -> live handoff, bounded backpressure, at-least-once ordering.

18.2 Detailed Implementation Steps

  • Modules: catchup.rs, live.rs, dispatcher.rs, backpressure.rs.
  • Catch-up: given from_offset, read partition log sequentially to head, delivering each event; track delivered offset. Catch-up→live model after R1 (EventStoreDB catch-up subscriptions); offset/checkpoint model after paper P4.
  • Live: store notifies dispatcher of new durable offsets (bounded MPSC + notify); dispatcher reads (last_delivered, new_durable] and fans out. Durable watermark, never raw append notify, is truth (INV-12; watermark discipline per B5).
  • Handoff: enter catch-up; at the head observed at subscribe time, atomically register for live + continue from next offset (no gap, no seam dup beyond at-least-once; ordering per INV-3).
  • Backpressure: per-consumer bounded queue (default 32 MiB). When full, dispatcher stops reading ahead for that consumer (its catch-up slows); never blocks writer or peers (principle 6.6; every bound gauged per principle 6.14).
  • Data structures / algorithms: Subscription{partition, position, sink, buffer_bound}; Dispatcher{partitions: [PartitionDispatch; P]}; PartitionDispatch{subscribers, durable_offset_rx}. Single reader/partition pushes to each bounded queue in offset order; ack advances position. Catch-up + live unified as "read position → min(head, position+budget)".
  • Synchronization: lock-free notify of durable offset; per-subscriber queues isolate slow consumers; ack via atomic position update. Subscription position is the consumer's checkpoint (projections persist it).
  • Observability hooks: es_subscription_lag_events, es_subscription_buffer_used, es_subscription_redelivery_total, es_dispatch_events_total, es_subscription_stalled_total.
  • Test harness: slow-consumer → writer + peers unaffected, lag bounded, no OOM; seam → no gap; ordering → offsets strictly increasing per partition.

18.3 Deliverable

  • es-subscribe: catch-up + live, backpressure, per-partition ordering; integrated into es-projection/es-saga.

18.4 Acceptance Criteria

  • Delivered offsets strictly increasing + dense per partition (INV-3 end-to-end).
  • Slow consumer (10x) reduces writer throughput ≤ 2%, no OOM; catch-up → live seam: zero gaps, redelivery ≤ 1 event (idempotency handles it).
  • 10k concurrent subscriptions within buffer budget; live lag p95 ≤ 200 ms.

18.5 Conformance Fixtures

  • subscribe/order_preserved.json — delivered == log sequence; catchup_to_live_seam.json — no gap at handoff.
  • subscribe/backpressure_slow_consumer.json — buffer bound respected, writer unaffected.
  • malformed/consumer_panics.json → subscription isolated, others continue.
  • regression/late_subscriber_from_checkpoint.json — resumes exactly from checkpoint.

18.6 Pitfalls

  • Coupling writer to the slowest consumer (synchronous fanout) → throughput collapse; unbounded per-consumer buffers → OOM.
  • Per-peer/per-consumer OS resources that scale with fan-out or fleet size creep toward hard OS limits unnoticed — the trigger of the AWS Kinesis US-East-1 outage (2020; public AWS postmortem: per-server thread count grew with the front-end fleet past the OS limit). Hence fixed budgets + gauges here (§4 FD budget, principle 6.14).
  • Gap/duplicate at catch-up/live seam from racy head snapshot → off-by-one delivery.
  • Delivering before durable (appended not durable) → consumers see events that vanish on crash; single global lock serializes unrelated streams.

18.7 Performance Concerns

  • Notify coalescing: signal once per group-commit to bound wakeups; per-partition single reader avoids contention; fanout copies cheap (Arc the envelope); catch-up via mmap.

18.8 Edge Cases

  • Subscribe w/ from > head → wait for new events (valid future position).
  • Consumer disconnects mid-delivery → position not advanced; resumes from last ack (at-least-once).
  • Live notification for an offset below the durable watermark (reorder) → dispatcher uses durable watermark, not raw notify, as truth.

18.9 Failure Analysis

  • Consumer crash: position checkpoint → resume; redelivery handled by idempotency (INV-4).
  • Dispatcher restart: rebuild from durable offsets + consumer checkpoints; no event skipped.
  • Backpressure deadlock: none — writer never waits on consumers; only the lagging consumer's own catch-up slows. Seam-gap bugs caught by ordering/density property test.

18.10 Operational Notes

  • es_subscription_lag_events per consumer is the primary lag SLI feeding the read-model-lag SLO; runbook "subscription stalled" → check consumer error rate, store latency, buffer saturation; backpressure thresholds tunable per consumer class.

19. Phase 8 — Schema Evolution / Upcasting Pipeline

19.1 Objectives

  • Evolve event schemas over a system's life w/o rewriting the log: lazy, chained, pure upcasters transform stored (type, vN) to the current shape on read (principle 6.5, INV-8).

19.2 Detailed Implementation Steps

  • Modules: registry.rs, pipeline.rs.
  • Registry: register(from=(type,vN), to=vN+1, upcaster); per-type chain v1→…→vCurrent — chain pattern after R2 (Axon upcasters). Startup: every observed/declared (type,version) has a path to current, else fail fast (INV-8).
  • Read integration: in es-codec decode → raw value tagged (type,ver); pipeline applies chain until ver == current; result handed to aggregate/projection. Pure + total per step (principle 6.5; resolution-rule reference S3/S4).
  • Change taxonomy: add optional field (default-fill); rename (map); split/merge; representation change; type rename = new type + migrator projection (not an upcaster). Forbidden: silently changing a field's meaning.
  • Data structures / algorithms: UpcastChain{steps}; UpcastRegistry{by_type: Map<String,UpcastChain>, current_version: Map<String,u32>}. Chain application = fold of upcasters; memoize compiled chains; detect unreachable versions at startup (graph reachability).
  • Synchronization: registry immutable after init (Arc); reads lock-free. No persistence — stored bytes unchanged; only interpretation evolves.
  • Observability hooks: es_upcast_apply_total{type,from,to}, es_missing_upcaster_total, es_upcast_seconds.
  • Test harness: cross-version replay — old fixtures upcast == native-current; missing-upcaster fails fast; chain-stability property.

19.3 Deliverable

  • es-upcast registry + pipeline integrated into read/decode; documented change taxonomy.

19.4 Acceptance Criteria

  • Old-version fixtures upcast to current produce byte-identical aggregate state vs events authored at current version.
  • Startup w/ a missing upcaster fails fast w/ MissingUpcaster{type,ver}; upcasting deterministic over 1M generated old events.
  • Adding an optional field requires only one vN→vN+1 upcaster; no log rewrite.

19.5 Conformance Fixtures

  • upcast/v1_to_current_chain.json — multi-step chain → expected current shape.
  • upcast/old_events_replay_equals_native.json — state equality cross-check.
  • malformed/missing_upcaster.json → startup fails fast.
  • malformed/upcaster_nondeterministic.json → property test catches.
  • regression/type_rename_via_migrator.json — new type + migrator projection path.

19.6 Pitfalls

  • Mutating stored bytes "to migrate" → breaks immutability + replay determinism + backups; non-total upcaster → poison on read.
  • Reusing a version number for incompatible change → ambiguous interpretation; forgetting to bump current_version → chain stops short.
  • Upcaster w/ side effects / clock → non-deterministic replay.

19.7 Performance Concerns

  • Upcasting on every read adds CPU; memoize compiled chains, keep steps cheap, share buffers. For very old common versions, an offline "rewrite to new stream" only as a deliberate logged migration — never silent mutation.

19.8 Edge Cases

  • Event already at current version → identity (no-op chain).
  • Future version (newer than code, after rollback) → reject UnknownVersion; do not guess.
  • Mixed-version producers during rolling upgrade → all readable via chains; removed field → upcaster drops it (downstream must not depend on it).

19.9 Failure Analysis

  • Missing upcaster in prod: startup fail-fast (caught in canary) → ship upcaster / rollback. Detection: es_missing_upcaster_total + startup check.
  • Buggy upcaster (wrong transform): differential replay vs golden catches; revert upcaster, rebuild projections.
  • Version skew on rollback: newer events unreadable by older code → block downgrade across a version that introduced new event versions.

19.10 Operational Notes

  • CI gate: any event-schema change must include an upcaster + cross-version fixture, else fail; rolling-upgrade runbook deploys upcaster-capable readers before producers emit new versions; change taxonomy documented in docs/adr + CONTRIBUTING.md.

20. Phase 9 — Sagas / Process Managers (React to Events, Emit Commands, Timeouts, Compensation)

20.1 Objectives

  • Coordinate multi-aggregate workflows: a saga reacts to events, persists its own state (event-sourced), emits commands, schedules timers/timeouts, compensates on failure.

20.2 Detailed Implementation Steps

  • Modules: runtime.rs, timers.rs, compensation.rs.
  • Saga trait: §11.12. Runtime subscribes (P7) to reacted-to events, folds saga state from saga events, calls react(state, event) -> Vec<SagaAction>, executes actions. Process Manager after B6; compensation model after paper P9 (Sagas).
  • Saga state: event-sourced into saga-<type>-<correlation_id> for replay/idempotency parity w/ aggregates (principle 6.3). Each reaction records a saga event (e.g. CommandEmitted) before emitting, for idempotent re-execution (principle 6.4).
  • Commands: Emit(cmd) routed back through CommandBus; idempotency key from (saga_id, triggering_offset, action_index) so redelivery never double-emits (INV-11; Idempotent Receiver after B6).
  • Timers: durable store (saga_id, timer_id, fire_at); timer wheel / min-heap fires TimerFired events; survive restart (rebuilt from store — crash-only per principle 6.7).
  • Compensation: on failure (permanent conflict, downstream reject), transition to Compensating, emit compensating commands in reverse causal order (paper P9); completion → Failed/Completed.
  • Data structures / algorithms: SagaRuntime{saga, state_store, timer_store, command_bus, subscription}; TimerWheel{heap, persistence}. Idempotent reaction — record intended actions as saga events keyed by triggering offset; replayed actions not re-emitted (CommandBus dedup by key).
  • Synchronization: one saga instance processes its events in order (per-correlation); independent sagas concurrent. Saga events + timers durable; reaction effects idempotent so at-least-once delivery is safe.
  • Observability hooks: es_saga_active, es_saga_commands_emitted_total, es_saga_timer_fired_total, es_saga_compensation_total, es_saga_stuck_total.
  • Test harness: crash mid-reaction → command emitted exactly once on recovery; timeout → compensation; per-correlation ordering preserved.

20.3 Deliverable

  • es-saga: runtime, durable timers, compensation; example inventory_saga (reserve→pay→ship + timeout compensation).

20.4 Acceptance Criteria

  • Crash between intent-record and command-emit (1000 trials) → command emitted exactly once after recovery.
  • Timeout fires reliably across restart (durable timers) within ± timer resolution; compensation runs in correct reverse order on induced failure, reaching a defined terminal state.
  • Saga reacts in per-correlation order; no double emission under redelivery.

20.5 Conformance Fixtures

  • saga/happy_path.json — events → emitted commands sequence.
  • saga/timeout_compensation.json — timer fires → compensating commands.
  • malformed/saga_command_permanent_conflict.json → compensation path.
  • regression/crash_between_intent_and_emit.json — exactly-once emission.
  • replay/timer_survives_restart.json — durable timer fires post-restart.

20.6 Pitfalls

  • Emitting commands w/o recording intent first → double emission; non-durable timers → missed timeouts (stuck sagas).
  • Saga reading not-yet-consistent projections → acts on stale state; prefer reacting to events. Compensation not idempotent → double rollback.
  • Unbounded saga state (never finishing) → stream growth; enforce terminal states + timeouts.

20.7 Performance Concerns

  • Timer wheel scalability for millions of timers (bucketed wheel + persistence batching); snapshot long-lived sagas (reuse P5); command fanout back-pressured through the CommandBus path.

20.8 Edge Cases

  • Duplicate triggering event (redelivery) → reaction idempotent via recorded intent.
  • Timer fires for an already-completed saga → ignored (terminal guard).
  • Out-of-order events across partitions (saga spans partitions) → tolerate causal-only order (principle 6.11); distributed coordination PhaseDeferred("Deferred Features Register"). Command targeting a closed aggregate → compensation or operator alert.

20.9 Failure Analysis

  • Stuck saga: no progress past a state → es_saga_stuck_total alarm + runbook (inspect awaited event/timer).
  • Double emission: broken intent-recording; differential replay catches; fix + dedup.
  • Lost timer: durable store + recovery rebuild; expected-vs-fired audit. Compensation failure: escalate to operator (Failed terminal + alert).

20.10 Operational Notes

  • Distributed/cross-node saga coordination is PhaseDeferred("Deferred Features Register"). Dashboards: active sagas by state, stuck count, compensation rate; runbook "saga stuck" → identify awaited trigger, replay missing event or operator-issue the command.

21. Phase 10 — CQRS Query Side + Read-Model Stores

21.1 Objectives

  • CQRS query side: a typed facade over read models, w/ explicit consistency (eventual default, read-your-write on request) and pluggable stores.

21.2 Detailed Implementation Steps

  • Modules: facade.rs + read-model-store adapters (shared w/ es-projection).
  • Query facade: query<Q: Query>(q) -> Q::Result dispatched to the read model backing that query. No access to write path or raw events for invariants (principle 6.13; CQRS per B3).
  • Consistency modes: (a) eventual (default) — read current read-model state; (b) read-your-write — caller passes AppendResult.last_offset; facade waits (bounded) until projection checkpoint ≥ it — well-defined because checkpoints are monotonic (INV-10); (c) strong-from-aggregate — load the aggregate directly (P4).
  • Read-model stores: embedded KV default (point/range), SQL adapter for relational queries; store choice per read model. Inline-transactional alternative studied in R3 (Marten) — rejected here to keep the write path store-agnostic.
  • Data structures / algorithms: QueryFacade{read_models, checkpoint_view}; ConsistencyToken(partition, offset). Read-your-write = notify on the projection checkpoint reaching the token offset, w/ timeout → fall back to eventual + flag staleness.
  • Synchronization: queries read-only + concurrent; no locks on write path. No new persistence; queries hit P6 projection stores.
  • Observability hooks: es_query_total{type}, es_query_seconds, es_query_staleness_seconds, es_read_your_write_wait_seconds, es_query_timeout_total.
  • Test harness: read-your-write — command, query w/ token, see own write; staleness bounded; load test for latency.

21.3 Deliverable

  • es-query facade w/ eventual + read-your-write + strong-from-aggregate modes; example queries over the example projections.

21.4 Acceptance Criteria

  • Read-your-write returns the caller's own write within bound (≤ lag bound + epsilon) or times out explicitly.
  • Eventual query latency p95 ≤ 1 ms (KV point read); no query path touches the write/log path for invariant decisions (architectural test).
  • Strong-from-aggregate returns up-to-date state (bypasses projection lag).

21.5 Conformance Fixtures

  • query/eventual_read.json — read-model state → query result.
  • query/read_your_write.json — token → sees own write.
  • query/staleness_bound.json — eventual lag within bound.
  • malformed/query_unknown_type.json → typed error.
  • regression/read_your_write_timeout.json — explicit timeout behavior.

21.6 Pitfalls

  • Using projections for command invariant checks → stale-read bugs; invariants belong to aggregates.
  • Read-your-write blocking indefinitely → caller hangs; always bound + fall back. Caching w/o invalidation on checkpoint advance → stale answers.
  • Mixing strong + eventual semantics implicitly → confusing; make mode explicit.

21.7 Performance Concerns

  • Read-your-write wait adds latency; use checkpoint-advance notifications (not polling), bound the wait to keep p99 predictable; choose store per query shape (KV point, SQL/columnar aggregates).

21.8 Edge Cases

  • Query for an entity whose creating event isn't projected yet (eventual) → not-found vs stale; document.
  • Read-your-write token for a different partition than the projection → resolve correct projection checkpoint.
  • Cross-read-model join → compose at the query layer (no cross-projection transactions).

21.9 Failure Analysis

  • Stale read complaints: distinguish acceptable eventual lag from a stuck projection (lag SLI).
  • Read-your-write timeouts: projection lag too high → scale/batch tuning; surface staleness rather than block.
  • Query store outage: queries fail fast + degrade; write path unaffected (CQRS isolation).

21.10 Operational Notes

  • SLOs: eventual lag + query latency published separately; runbook "users see stale data" → check projection lag, not write path; document consistency modes for application developers prominently.

Compatibility & Versioning

Governs storage-format/wire/schema/API/snapshot evolution. SemVer 2.0 (ADR-08/20).

Event schema evolution + upcasting contract

  • Stored bytes immutable forever (INV-1); evolution by interpretation, not rewrite. Every written (event_type, schema_version) retains a chain to current (INV-8); upcasters pure + total (principle 6.5).
  • Compatible (minor): add optional field (default-fill), widen a type, add an event_type — one vN→vN+1 upcaster, no rewrite (§8.6).
  • Breaking (handled): rename/split/merge via mapping upcaster; semantic change ⇒ new event_type + migrator. Never reuse a version or a type's meaning.
  • CI gate: any event-schema change must ship an upcaster + cross-version fixture or build fails (§19.10).

Serialization compatibility

  • Protobuf prod follows proto3 field-number discipline (ADR-05, S4): never reuse/renumber; new fields optional. Avro reader/writer resolution (S3); JSON (dev) tolerates unknown keys.
  • content_id canonical form stable across machines/endianness/languages (P3); equal events hash equally.

Read-model rebuild guarantees

  • Any read model rebuildable from 0 to byte-identical state (INV-4/9), independent of build path — foundation of restore + projection migration.
  • Read-model schemas change freely (disposable caches, principle 6.2); migration = rebuild, not in-place ALTER (hot migration PhaseDeferred("Deferred Features Register")).

API stability

  • es-core traits + types normative. Post-1.0: additive only (default methods, #[non_exhaustive] enums); removals/signature changes ⇒ major bump.
  • Server protocol (P12): length-prefixed binary + format_ver; additive frames; handshake negotiates version + refuses incompatible/downgrade-unsafe peers.

Snapshot-format versioning

  • Snapshot header carries format_ver, schema_ver, codec_id, CRC (ADR-25); uninterpretable snapshot discarded + replayed (principle 6.10) — format changes always safe, never data-loss.

Storage-format versioning

  • Segment header carries format_ver; record framing carries version (§8.3). New fields appended only; old readers fail-fast on unknown major formats (principle 6.15).

Deprecation policy

  • Deprecated types/fields kept readable (upcasters) ≥ 2 minor releases; CHANGELOG flags deprecation + the version-introducing release; removal only after the window at a major bump.

Semantic versioning + rolling-upgrade guarantees

  • MAJOR: breaking API/storage-major. MINOR: additive API, new event versions (+ upcasters). PATCH: fixes.
  • Rolling-upgrade: within a major line, mixed adjacent-minor instances interoperate given readers-before-producers ordering (§19.10). Downgrade: safe within a minor; crossing a version-introducing release is blocked (FM-10).

Scalability Analysis

Scaling unit = the partition: an independent ordered log + single writer (principle 6.8/6.11).

  • Stream partitioning / sharding: partition = hash(stream_id) mod P (§3.4); all events of a stream share one partition. P fixed at init; reshard via es-reshard (P12). Near-linear append scaling to P writers (share nothing).
  • Projection parallelism + metadata: projections run independently w/ per-partition checkpoints (§17.7); rebuild parallelizes across partitions; stream-version index sharded per partition, rebuildable from log (§13.2); ≥ 1M active streams via per-partition (not per-stream) locks (§4).
  • Subscription fan-out: per-partition single reader pushes to each bounded queue; Arc-shared envelopes make fanout cheap (§18.7); ≥ 10k subscriptions bounded by buffer budget (§4).
  • Storage growth: append-only ⇒ monotonic; bounded by snapshot GC (retain newest K, §16.2) + sealed-segment archival + amplification ≤ 1.4× (§4); crypto-shredding (TM-3) handles erasure w/o deletion.
  • Multi-writer coordination: none within a partition; cross-partition has no global order (principle 6.11) → no coordination overhead, a deliberate tradeoff for linear scale. Multi-writer/consensus replication PhaseDeferred("Deferred Features Register").
  • Bottlenecks (ranked): (1) fsync on hot partition (governor); (2) read-model store write throughput; (3) single-writer lock on a hot partition (FM-3); (4) subscription buffer memory at high fan-out; (5) rebuild throughput as recovery-time ceiling.
  • Scaling ceilings: per-partition append bounded by NVMe IOPS + fsync latency; per-node by FD budget (≤ 64 + 1/active-segment/partition, §4) + 256 MB core memory ceiling; cross-partition unbounded by adding partitions/nodes.
  • Horizontal vs vertical: vertical — faster NVMe + more cores raise per-partition append + replay/codec throughput (fsync stays governor). horizontal — add partitions/nodes for more writers (P12 StatefulSet, one owner/partition); linear append, no cross-partition global order (deferred). Hot-aggregate contention solved by boundary redesign, not nodes (FM-3).

Mental Models & First Principles

Compressed expert models (MM1–MM9). Each: the insight, what it predicts, the bug class written without it, and where this blueprint applies it.

  1. MM1 — The log is the database; every table is a cache. Current state = fold(apply, events); storing state is memoization, never truth. Predicts: any read model is reconstructible; DR = restore log + rebuild; "fixing data" = appending a compensating event. Bug class without it: dual-writes (store + log updated non-atomically) → undetectable drift. Applied: principle 6.2, §3.7, Phase 6 §17.2, Compatibility & Versioning (rebuild guarantees).
  2. MM2 — Durability is a watermark, not a boolean. write() returning is meaningless; there are two offsets (appended, durable) and only the second survives power loss. Predicts: consumers shown anything above the watermark act on data a crash can erase; recovery truncates the gap. Bug class: ghost deliveries — read models referencing events that no longer exist after restart. Applied: INV-12, Phase 1 §12.2, §18.8.
  3. MM3 — Exactly-once is an effect property, not a delivery property. Delivery is at-least-once everywhere (seam, crash, restart); only idempotent apply + atomic checkpoint makes effects exactly-once. Predicts: redelivery counters > 0 are healthy; a double effect always means broken idempotency, never bad luck. Bug class: balance += x without an offset guard → double counting (FM-6). Applied: principles 6.4/6.9, INV-4, Phase 6 §17.2.
  4. MM4 — An aggregate is a fold; a command is a pure decision. handle proposes events, apply folds them; neither touches clock/RNG/IO. Predicts: byte-identical replays, given-when-then testing, forensic reconstruction of any historical state. Bug class: impurity in apply → divergent rebuilds caught only by differential replay (INV-9). Applied: §11.6, principle 6.3, Phase 4 §15.2.
  5. MM5 — Schema evolution is reinterpretation, never rewriting. Bytes freeze at append; meaning evolves through pure upcaster chains at read. Predicts: readers-before-producers deploy order; rollback blocked across an introducing version. Bug class: in-place "migration" that corrupts replay determinism and every backup (FM-4/FM-10). Applied: principle 6.5, INV-8, Phase 8 §19.2.
  6. MM6 — Ordering is bought per partition; global order is a coordination bill. Predicts: linear writer scaling at P partitions; cross-partition workflows must tolerate causal-at-best order. Bug class: cross-stream sequence assumptions that silently break at reshard. Applied: principle 6.11, §3.4, §20.8, Scalability Analysis.
  7. MM7 — Backpressure is topology: a slow consumer may slow only itself. Predicts: bounded per-consumer queues; writer throughput invariant to fan-out health (M10). Bug class: synchronous fan-out or unbounded buffers → writer collapse or OOM. Applied: principle 6.6, Phase 7 §18.2, FM-1.
  8. MM8 — Contention is a modeling smell, not a locking problem. A hot stream's VersionConflict storm indicts the aggregate boundary, not the lock. Predicts: the conflict-rate SLI doubles as a domain-model health metric. Bug class: raising retry caps instead of splitting the aggregate → livelock (FM-3). Applied: principle 6.8, INV-6, Phase 2 §13.10.
  9. MM9 — Crash-only: recovery is the only startup path. If kill -9 is safe, every shutdown is. Predicts: rollback = stop + redeploy + recover; no correctness dependency on graceful drains. Bug class: state persisted only on clean shutdown → loss at power cut. Applied: principle 6.7, Phase 1 §12.2, Operational Readiness (rollback).

Alternative Architectures (Roads Not Taken)

Fundamentally different shapes for the same requirements. Each is real; each wins somewhere; each rejection is encoded in a decision above.

A1 — Event store inside an RDBMS (Marten shape)

clients ─▶ SQL txn ──▶ INSERT event rows            (Postgres WAL = durability)
                   └─▶ UPDATE read-model rows        (inline projection, same txn)
        global order = DB sequence · subscriptions = polling daemon on seq
  • Wins when: Postgres is already the operational center; write rates ≤ ~10k ev/s; transactional read-your-write outranks scale.
  • Real system: Marten (R3).
  • Rejected because: double-write amplification (event bytes + DB WAL + heap + indexes); B-tree insert ceiling vs append-only segments; sequence gaps under concurrent commits need daemon-side handling; and the project's pedagogy is owning fsync/recovery (Phase 1), which the DB hides. Costs encoded at ADR-09 and §4.

A2 — Brokered distributed log (Kafka shape)

producers ─▶ [ broker cluster: partitioned, ISR-replicated log ] ─▶ consumer groups
                       ▲ metadata/controller: KRaft                └─▶ Streams state stores
  • Wins when: many teams/languages share one firehose; PB-scale retention; ecosystem (Connect, Streams) matters more than per-aggregate semantics.
  • Real system: Apache Kafka (R4).
  • Rejected because: no expected-version CAS per logical stream — INV-6 cannot be enforced broker-side; ≥ 1M fine-grained streams (§4) do not map to topic/partition cardinality; broker + controller operations contradict the embedded-library deployment model (§1.4).

A3 — Quorum-replicated log (BookKeeper / clustered-EventStoreDB shape)

writer ─▶ partition leader ─▶ ║ replica A ║ replica B ║   ack on quorum (2/3)
durability = quorum across nodes (journal + RAM), not local fsync alone
  • Wins when: RPO must be 0 through whole-node loss; 99.99% availability; failover without restore is mandatory.
  • Real systems: Apache BookKeeper; EventStoreDB clusters (R1).
  • Rejected (for Phase 0) because: quorum RTT replaces fsync as the latency governor; membership, election, and re-replication machinery dwarf the single-node correctness kernel. Deliberately deferred — the Register's consensus-replication row (P12) un-defers it when the §4 availability target demands it.

A4 — Durable-execution platform (Temporal shape)

workflow code (deterministic) ◀──▶ Temporal service: per-workflow event history,
   replayed on every worker resume          task queues, durable timers
  • Wins when: long-running, human-timescale business workflows dominate; retries, timers, and versioned code paths as managed platform features beat owning the machinery.
  • Real system: Temporal (§2.2 lineage).
  • Rejected because: the log is hidden behind a service boundary — this project's deliverable is the log/store primitive; Phase 9 sagas provide in-process orchestration with the same replay model (paper P9) at zero extra infrastructure.

Glossary

  • Event — immutable fact record; once appended + synced, never mutated/deleted (INV-1); in an EventEnvelope.
  • Stream — ordered events for one aggregate, StreamId = "<category>-<instance>"; unit of optimistic concurrency.
  • Append-only log — system of record (es-log): O_APPEND segment files, never edited in place; source of all derived state (principle 6.2).
  • Segment — monotonically numbered log file; active appended, sealed immutable; rolled at size/count cap (§12.2).
  • Aggregate — consistency boundary; state = pure fold (apply) over its stream; enforces invariants in handle (§11.6).
  • Command — intent to change an aggregate; routed by target_stream; produces events via handle; may carry idempotency_key (§11.7).
  • Projection / read model — queryable view built by idempotent apply to a store w/ checkpoint; rebuildable from 0 (§11.10).
  • Snapshot — persisted aggregate state at (stream,version); bounds replay tail; never authoritative (principle 6.10, INV-5).
  • Upcaster — pure total vN→vN+1 transform applied lazily on read to current shape (§11.13, INV-8).
  • Saga / process manager — stateful event-sourced consumer: reacts to events, emits commands, schedules timers, runs compensation (§11.12).
  • CQRS — Command Query Responsibility Segregation: write side (aggregates + log) + read side (projections) diverge intentionally (principle 6.13).
  • Optimistic concurrency — append supplies expected_version; mismatch rejected as VersionConflict, not merged (INV-6).
  • Expected version — ExpectedVersion (Any/NoStream/StreamExists/Exact(v)) asserted at append (§11.4).
  • Idempotency — re-processing/redelivery causes no extra effect; offset/id-keyed handlers (principle 6.4).
  • Idempotency key — optional command id letting store dedup retries + return original AppendResult (§13.2, INV-11).
  • Checkpoint — consumer's (name, partition, offset); advanced atomically w/ its effect; monotonic (INV-4/10).
  • Catch-up subscription — reads historical events (offset→head) then hands to live tailing w/ no gap (§18.2).
  • Dispatcher — per-partition single reader delivering events in offset order w/ bounded backpressure (§3.8).
  • Backpressure — bounded per-consumer buffers; slow consumer slows only itself (principle 6.6).
  • Global offset — strictly-increasing dense per-partition position per record; basis of ordering + checkpoints (INV-3). Stream version: 0-based gapless per-stream sequence (INV-2).
  • Partition — independent ordered log + single writer; hash(stream_id) mod P; unit of scaling + total order (§3.4).
  • Replay — reconstruct state by re-applying events from a start point; deterministic given pure apply/handle (principle 6.3, INV-9). Rebuild = drop read model + checkpoint, replay from 0 to regenerate byte-identically (INV-4).
  • Crypto-shredding — GDPR erasure: destroy per-subject key ⇒ PII ciphertext unreadable forever, no record deletion (TM-3).
  • Durable offset — highest fsync-durable offset; consumers see only ≤ durable_offset (distinct from appended_offset) (INV-12).
  • Exactly-once (effect) — effect applied once via idempotent apply + atomic checkpointing over at-least-once delivery (§3.8; principle 6.9, INV-4).
  • Fsync policy — operator knob (PerBatch/GroupCommit/OsFlush) trading durability/RPO vs throughput (§12.2, §4).
  • Poison event — event no codec/upcaster can decode; quarantined so it pauses only its consumer (principle 6.12, FM-9).
  • Correlation id / causation id — metadata linking a workflow's events (correlation_id) + an event's cause (causation_id) (§8.2).
  • CRC-32C — Castagnoli per-record checksum, verified on every read for torn-write/bit-rot detection (ADR-27, INV-7).
  • AppendResult — successful-append outcome: stream_version + dense (first,last) offsets + partition (§11.5).
