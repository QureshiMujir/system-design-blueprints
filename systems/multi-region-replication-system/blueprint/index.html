Project Number: 202

Project Name: Multi-Region Replication System

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition: a replication substrate that transports strongly-ordered write-ahead-log (WAL) mutations from a source-region storage engine to N independent replica regions, preserving per-stream total order, exposing configurable consistency (linearizable-read-your-writes on the leader stream, bounded-staleness elsewhere), bounding recovery time and recovery point objectives, and making every replication decision deterministically replayable from durable log state. It is a transport and coordination layer, not a query engine: it moves already-serialized mutations and snapshots between storage engines that each remain responsible for their own on-disk format above the WAL boundary.

Phase-0 deliverable — twelve crates/services, one Cargo workspace member each:

  1. replication-core — shared IDs, error taxonomy, config loader, bounded-queue primitives, clock.
  2. replication-wal — segment format, fsync policy, replay cursor, corruption isolation.
  3. replication-transport — QUIC/TLS runtime, framing, retransmission, compression negotiation.
  4. replication-scheduler — inflight quotas, batching, backpressure, per-region fairness.
  5. replication-membership — epoch manager, Raft metadata plane, liveness, fencing tokens.
  6. replication-snapshot — manifest format, chunked transfer, restore, garbage collection.
  7. replication-observability — metrics registry, tracing exporters, structured audit log.
  8. replication-admin-api — topology/failover/audit HTTP API, isolated from the data path.
  9. replication-replay — ordered apply queue, idempotency validation, replay tracing.
  10. replication-cli — operator command-line surface over the admin API.
  11. replication-test-harness — deterministic simulator, one assertion per invariant (§7).
  12. replication-chaos-suite — fault injection, packet loss, corruption, region-isolation drills.

System boundaries:

Provides:

  • Ordered, durable, cross-region transport of WAL mutations and snapshots.
  • Region-aware scheduling, backpressure, and failover coordination.
  • Deterministic replay and conflict resolution for active-active streams.
  • Operator-facing topology, failover, and audit control plane.

Delegates:

  • Mutation encoding/decoding above the WAL frame boundary — owned by the storage-engine integrator.
  • Client-facing query/transaction semantics — owned by the storage engine, not this system.
  • Physical network transport below TLS/QUIC — owned by the OS network stack and NIC driver.

Does NOT provide:

  • SQL query engine, OLAP execution, or columnar analytics.
  • A full consensus database (this ships a metadata Raft plane, not a data-plane consensus store).
  • Distributed filesystem or object storage semantics.
  • Arbitrary workflow orchestration or multi-tenant billing.
  • A Kubernetes replacement — it runs on an orchestrator, it is not one.

Non-goals (explicit, revisited never inside this blueprint's scope): general-purpose OLTP query planning, cross-shard distributed SQL transactions, and building a competing object-store product.

Deployment model: one stateful cluster per geographic region, dedicated replication nodes with NVMe-backed WAL volumes, containerized (OCI) under Kubernetes or Nomad, TLS-secured east-west traffic, replication traffic on an isolated VLAN/subnet where the substrate permits, admin-plane traffic on a separate namespace so control-plane load never contends with the replication data path (see §6 P12, Isolation of Control Plane).

Target operators: (a) Operators run topology changes, regional failover, upgrade orchestration, recovery validation, and lag remediation; (b) Storage Engine Integrators map their mutation format onto WalEntry (§11), wire WAL append calls, and implement snapshot adapters; (c) Infrastructure Engineers own network tuning, capacity planning, and SLO compliance against §4.

Later phases unlock: active-active replication with programmable conflict resolvers (§20), dynamic shard migration, adaptive quorum routing, topology-aware traffic shaping, WAN-aware compression heuristics tuned per-link, and geo-fencing policies for data-residency compliance. Four capabilities are explicitly deferred out of Phase 0–9 scope — see §35 for the full register: PhaseDeferred("§20") (programmable conflict VM beyond deterministic built-ins), PhaseDeferred("§16") (adaptive replica placement), PhaseDeferred("§21") (Byzantine-fault-tolerant peer admission), and PhaseDeferred("§17") (cross-region snapshot deduplication).

Recommended language: Rust. Rationale — deterministic ownership eliminates a whole class of use-after-free/data-race bugs in the hot replay path (§18); no GC pause is compatible with the p99 apply-latency budget in §4; the async ecosystem (Tokio, quinn) covers QUIC transport and structured concurrency without hand-rolled event loops; the type system encodes wire-compatibility invariants (§6 P5) at compile time. Rejected: Go — GC pauses collide with the p99 < 150 ms budget under GC-stress workloads, and its weaker generics made the frame-codec type layer (§11) less safe at the time this ADR was locked (ADR-01); C++ — memory-safety burden is unacceptable for a network-facing parser surface that is also the fuzzing target (ADR-13); Java — GC pause and JIT warm-up variance conflict with the startup-recovery budget (§4).

Prerequisites: distributed-systems fundamentals, replication theory (leader/follower, quorum), WAL/durability semantics, TCP/QUIC internals and congestion control, Linux IO stack (io_uring, mmap, page cache), async runtimes, memory ordering and lock-free queues, Protobuf schema evolution, TLS 1.3 internals, consistency models (linearizability, causal, eventual), vector clocks, Raft fundamentals, OpenTelemetry-style observability, chaos engineering, and flamegraph-driven profiling.

Timeline: Phase 0 (§12) — 3 weeks to a runnable skeleton with health/metrics endpoints and CI green. Full system (Phases 0–9, §12–§21) — 10–14 months to production-grade completion including chaos validation (§21) and rolling-upgrade compatibility (§25).

2. Why Build This

Multi-region replication is the substrate underneath every distributed database, log-based message broker, globally-distributed cache, and metadata plane in production today. Building one from the WAL frame up — rather than reading about one — is the only way to internalize why replication lag, partial failure, and backpressure interact instead of composing cleanly. The system deliberately recreates the failure surface of Spanner, CockroachDB, TiKV, Kafka, etcd, and DynamoDB global tables at a scope a single engineer can actually finish, so every design tradeoff is felt, not assumed.

Core engineering lessons extracted phase by phase: WAL durability semantics and fsync economics (§13); deterministic replay under crash and reorder (§18); partial-failure containment across a WAN link with 350 ms RTT (§4, §14); snapshot correctness under interrupted transfer (§17); tail-latency amplification from retransmits and lock contention (§28); distributed flow control and backpressure propagation (§15); region-isolation and split-brain prevention (§16); quorum acknowledgment strategies (§7 I4); rolling-upgrade wire compatibility (§25); and failure-domain modeling for capacity planning (§29, §32).

Calibration value: completion materially improves the ability to debug distributed failures from partial evidence, review operational architecture for hidden coupling, reason about consistency guarantees precisely instead of colloquially, model performance from first principles (§30), and assess infrastructure reliability tradeoffs the way the Spanner and Kafka authoring teams do.

What Mastery Looks Like

  • Can explain why WAL-before-visibility (§6 P9) is the one rule that makes crash recovery compositional, and can point to the exact WAL Ordering Invariant (§7 I1) that enforces it — gained in Phase 1 (§13).
  • Can diagnose replication-lag incidents from replication_lag_seconds and queue-depth telemetry alone, without reading application logs — gained in Phase 3 (§15).
  • Can reason about epoch-fencing correctness well enough to prove a split-brain scenario is impossible under the Epoch Consistency Invariant (§7 I2) — gained in Phase 4 (§16).
  • Can design a resumable, chunked snapshot protocol that survives an interrupted WAN transfer without re-transferring completed chunks — gained in Phase 5 (§17).
  • Can distinguish genuine non-determinism from a replay bug using the deterministic-simulator methodology (§7 closing paragraph) — gained in Phase 6 (§18).
  • Can build an observability surface where a metric, a trace span, and a structured-log field always agree on names — gained in Phase 7 (§19).
  • Can implement a deterministic conflict resolver using vector clocks without introducing hidden divergence — gained in Phase 8 (§20).
  • Can design and read a chaos-suite forensic bundle well enough to reconstruct a failure timeline without live access to the cluster — gained in Phase 9 (§21).

3.2 Subsystem Descriptions

Admin Control Plane. Operator-facing HTTP/gRPC surface for topology changes, replication policy updates, failover initiation, audit retrieval, and compatibility validation. Logically isolated from the replication data path (§6 P12): a control-plane traffic spike must never starve WAL writes or transport sends. Trust boundary: mutual-TLS-authenticated operator identity; no anonymous access.

Cluster Membership Service. Owns cluster epochs, region metadata, peer liveness, topology generations, and capability negotiation, backed by a small Raft metadata log (ADR-19). Persistence boundary: metadata log is the only durable store for topology; membership changes serialize through epoch transitions (§7 I2) to prevent split-brain routing.

Replication Coordinator. Authoritative orchestrator for stream progression, ack aggregation, retry coordination, replay sequencing, and failover-state transitions. Concurrency boundary: one actor per StreamId, no cross-stream shared mutable state, so stream planners never contend on a global lock.

WAL Subsystem. Append-only persistence with deterministic segment ordering, checksum validation, fsync-policy enforcement, replay-cursor tracking, and single-segment corruption isolation. Persistence boundary: nothing is externally acknowledged before an fsync return (§6 P9, §7 I1/I3).

Replication Scheduler. Controls pacing, batching, congestion adaptation, retry windows, inflight quotas, and per-region fairness. Owns the credit-based backpressure queue (§6 P2, §7 I6) that is the system's only defense against unbounded memory growth under WAN stalls.

Snapshot Manager. Large-state synchronization via checkpointed, chunked, resumable snapshots with per-chunk checksum validation and garbage collection of superseded manifests. Persistence boundary: a snapshot is atomic-or-absent (§7 I5) — no partially-visible snapshot is ever exposed to a restore path.

Transport Runtime. Encrypted WAN transport: framing, retransmission, multiplexed replication streams, compression negotiation, connection recovery. Protocol boundary: QUIC/TLS 1.3 (ADR-06, ADR-17); this is the only subsystem that touches raw sockets.

Remote Replica Runtime. Receives ordered mutations, validates stream continuity, persists replicated WAL entries, coordinates replay application, tracks remote durability acknowledgments. Trust boundary: every inbound frame is checksum- and epoch-validated (§7 I2/I3) before it is queued.

Storage Engine Adapter. Delegation boundary — abstraction letting an independent storage engine consume replicated operations while preserving its own transactional semantics; this system never interprets the payload above the WAL frame.

Queue. The scheduler's inflight-quota queue and the transport's bounded send queue are the two load-bearing queues in the diagram; both reject writes past a configured capacity (§7 I6) rather than growing unboundedly.

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: all replication outcomes must be replayable from persisted WAL state alone · Tradeoff: forbids convenient non-deterministic scheduling shortcuts · Operational: replay tooling (§18) is the debugging entry point, not live cluster inspection · Violated: divergent replicas, unrecoverable replay drift, inconsistent failover outcomes.
  • P2 — Backpressure Everywhere. Rule: every queue, socket, scheduler, and WAL writer exposes bounded capacity (§7 I6) · Tradeoff: bounded queues reject work under overload instead of buffering it · Operational: queue-depth metrics are first-class dashboards (§19) · Violated: memory exhaustion, retry storms, tail-latency collapse.
  • P3 — Crash-Only Semantics. Rule: every subsystem recovers from SIGKILL without a graceful- shutdown path · Tradeoff: forbids relying on destructor-based cleanup for correctness · Operational: chaos suite (§21) kills processes mid-write as a first-class test · Violated: partial state corruption, operator-dependent manual recovery.
  • P4 — Observability By Default. Rule: every replication decision emits a metric, a structured-log field, and a trace span using one shared name · Tradeoff: instrumentation overhead on the hot path · Operational: name collisions between metric/log/span are a code-review blocker · Violated: un-debuggable lag, invisible corruption, opaque retries.
  • P5 — Stable Wire Compatibility. Rule: protocol evolution preserves rolling-upgrade interoperability across exactly one minor version skew (§25) · Tradeoff: new fields must be additive and ignorable by old readers · Operational: conformance/wire_compat.yaml gates every release · Violated: region partitioning during upgrade, upgrade deadlocks.
  • P6 — Explicit Ownership. Rule: every buffer, WAL segment, socket, and snapshot chunk has exactly one authoritative owner at any instant · Tradeoff: ownership handoff requires an explicit transfer API, not shared references · Operational: leak detectors in the test harness assert single ownership · Violated: use-after-free-class bugs, double-free-class corruption in Rust's terms a double-drop, torn snapshot state.
  • P7 — Bounded Resource Usage. Rule: an untrusted peer can never force unbounded allocation on this node · Tradeoff: legitimate large snapshots must be chunked rather than buffered whole · Operational: per-peer resource quotas surfaced in the admin API · Violated: single malicious or misbehaving peer exhausts node memory, denial of service to all other streams.
  • P8 — Replayability First. Rule: every replication state transition is reproducible by replaying persisted logs · Tradeoff: state transitions cannot depend on wall-clock reads that are not themselves logged · Operational: the differential-testing harness (§26) replays production traces against new builds · Violated: silent behavior drift across versions goes undetected.
  • P9 — WAL Before Visibility. Rule: no acknowledgment is externally visible before durable WAL fsync (§7 I1, §7 I3) · Tradeoff: fsync latency (§4, < 2 ms budget) sits directly on the critical path of every ack · Operational: ack-tracker code path has no branch that skips the fsync wait · Violated: acknowledged-but-lost writes, the single worst correctness failure this system can have.
  • P10 — Fail Closed. Rule: unknown protocol fields, malformed metadata, and incompatible epochs reject traffic rather than best-effort-accepting it · Tradeoff: a buggy peer is disconnected instead of tolerated, which can reduce availability during a bad rollout · Operational: peer-strike counter (§22) tracks rejection rate per peer · Violated: silent protocol corruption propagates into replica state.
  • P11 — Monotonic Epochs. Rule: topology epochs are strictly increasing, never reused (§7 I2) · Tradeoff: every topology change costs one epoch bump and a fencing round · Operational: epoch regression is an automatic P0 alert, not a warning · Violated: stale-leader writes, split-brain acceptance of two active coordinators.
  • P12 — Isolation of Control Plane. Rule: control-plane overload must never block replication progress · Tradeoff: admin API gets its own thread pool and connection budget, wasting some idle capacity · Operational: admin-plane queue depth is monitored separately from replication queue depth · Violated: an operator-triggered topology storm stalls the data path it was meant to fix.

8.3 Replication State Machine

State Description
INIT connection initialized, no capability negotiated yet
HANDSHAKE capability and protocol-version negotiation in progress
STREAMING active replication, frames flowing under scheduler control
BACKPRESSURED remote capacity exceeded, sender throttled by credit (§7 I10)

DEGRADED partial regional outage, stream alive but lag exceeds §4 budget
FAILED unrecoverable stream failure, awaiting operator or failover FSM action

8.4 Replication Sequence (nominal path)

Client Write -> WAL Append -> Checksum Validation -> Replication Scheduler
   -> Transport Send -> Remote WAL Persist -> Ack Aggregation
   -> Visibility Commit

8.5 Failure Path Example

Region-link interruption sequence: inflight window saturates (§7 I10) → scheduler transitions the affected streams to BACKPRESSURED → sustained saturation past the lag budget (§4) transitions to DEGRADED → if lag exceeds the snapshot-preferable threshold, the coordinator initiates SNAPSHOT_SYNC fallback rather than an unbounded WAL catch-up → snapshot completes, stream transitions to REPLAYING, then back to STREAMING once the replay cursor catches the live WAL tail.

8.6 Malformed Packet Handling

A malformed frame (bad magic, checksum mismatch, unparseable length) triggers, in order: checksum rejection at the transport layer (§7 I3) → peer-strike counter increment (§6 P10) → transport disconnect once the strike threshold is exceeded → structured audit log entry naming the peer, frame offset, and rejection reason, queryable via the admin audit API (§1 Admin Control Plane).

11. Core Schema & Types

Each type below is annotated: Own (ownership) · Mut (mutation) · Conc (concurrency) · Pers (persistence) · Ser (serialization) · Compat (compatibility).

struct WalEntry
    sequence: u64
    epoch: u64
    stream_id: u128
    txn_id: u128
    checksum: u32
    payload: Bytes
    timestamp_ns: u64

Own: single owner, the WAL segment writer, until fsync completes. Mut: immutable after persistence (§6 P1). Conc: read-shared across replay workers post-fsync. Pers: append-only durable record (§7 I1). Ser: Protobuf envelope, payload opaque (§8.2). Compat: additive fields only, epoch/ sequence never renumbered (ADR-05, §25).

struct ReplicationCursor
    stream_id: u128
    applied_sequence: u64
    last_ack_sequence: u64
    updated_at_ns: u64

Own: one cursor per StreamId, owned by the Replication Coordinator actor (§3.2). Mut: monotonic advance only (§7 I4). Conc: single-writer, read via snapshot clone. Pers: checkpointed alongside WAL segment boundaries. Ser: Protobuf. Compat: version-tagged for rolling upgrade (§25).

struct SnapshotManifest
    snapshot_id: u128
    region_id: u32
    wal_sequence_at_snapshot: u64
    chunk_count: u32
    chunk_checksums: Vec<u32>
    created_at_ns: u64

Own: Snapshot Manager, immutable once written (§7 I5). Mut: none post-creation; superseded manifests are garbage-collected, not edited. Conc: read-shared by all restore workers. Pers: rename-on-complete atomic write. Ser: Protobuf. Compat: chunk layout versioned independently of WAL format version.

struct PeerDescriptor
    replica_id: u128
    region_id: u32
    epoch: u64
    capabilities: u32
    address: SocketAddr

Own: Cluster Membership Service. Mut: replaced wholesale on capability renegotiation, never patched in place. Conc: read-shared, copy-on-write update. Pers: replicated via the metadata Raft log (ADR-19). Ser: Protobuf. Compat: capabilities bitset is additive-only.

struct SchedulerQuota
    stream_id: u128
    inflight_limit: u32
    inflight_used: u32
    credit_available: u64

Own: Replication Scheduler, one per stream. Mut: inflight_used/credit_available mutated under a per-stream atomic (§7 I10). Conc: single-writer, lock-free read. Pers: not persisted, rebuilt on restart from cursor state. Ser: n/a (in-memory only). Compat: n/a.

struct AckWatermark
    stream_id: u128
    quorum_sequence: u64
    replica_sequences: Vec<(u128, u64)>

Own: Replication Coordinator ack tracker. Mut: quorum_sequence advances monotonically only (§7 I4). Conc: single-writer per stream. Pers: checkpointed for RPO accounting (§4). Ser: Protobuf. Compat: replica_sequences length bounded by §4 max regional fanout.

struct TransportFrame
    magic: u32
    version: u8
    flags: u8
    epoch: u64
    stream_id: u128
    sequence: u64
    txn_id: u128
    payload_len: u32
    crc32: u32
    payload: Bytes

Own: Transport Runtime encoder/decoder, transient per-frame. Mut: immutable once constructed. Conc: decoded on the receiving connection's task, no cross-task sharing. Pers: not persisted, mirrors WalEntry for wire transfer (§8.2). Ser: fixed-header + opaque payload. Compat: version field gates decode path (ADR-05, §25).

struct ReplaySession
    stream_id: u128
    resume_sequence: u64
    idempotency_window: VecDeque<u64>
    started_at_ns: u64

Own: Replay Engine, one per active replay. Mut: idempotency_window slides forward, bounded size. Conc: single replay worker per stream (§3.2 concurrency boundary). Pers: resume_sequence checkpointed for crash recovery. Ser: n/a (rebuilt from WAL on restart). Compat: n/a.

struct FailureDomain
    region_id: u32
    rack_id: Option<u32>
    az_id: Option<u32>

Own: Cluster Membership Service, part of PeerDescriptor metadata. Mut: immutable after peer registration. Conc: read-shared. Pers: replicated via metadata Raft log. Ser: Protobuf. Compat: additive optional fields only.

struct ConflictRecord
    txn_id: u128
    vector_clock: BTreeMap<u128, u64>
    resolution: ConflictResolution
    resolved_at_ns: u64

Own: Conflict Resolution Framework (§20). Mut: written once at resolution time, immutable after. Conc: single resolver worker per stream. Pers: appended to the resolver audit log. Ser: Protobuf. Compat: resolution enum is append-only, never renumbered.

  • Stand up the Cargo workspace and all twelve crate boundaries from §1/§10 with CI green on day one.

  • Land the deterministic simulator skeleton (replication-test-harness) that every subsequent phase's invariant assertions (§7) plug into.
  • Constrain scope: no WAL, transport, or scheduler logic lands in this phase — only the substrate.

12.2 Detailed Implementation Steps

  • Initialize the Cargo workspace root and the twelve member crates listed in §10; wire workspace- level lint policy (clippy::all deny, unsafe_code deny outside replication-transport's zero-copy buffer module).
  • replication-core/src/ids.rs: newtype wrappers for RegionId, ReplicaId, StreamId, EpochId, WalSequence, SnapshotId, TransactionId (§8.1) — each a distinct type, no raw u64/u128 passed across module boundaries (ADR-01 rationale: type-system enforcement).
  • replication-core/src/error.rs: the error taxonomy of §11.1 as a single enum ReplicationError with one variant per row, each carrying structured context fields, not a string.
  • replication-core/src/clock.rs: a trait Clock abstraction (monotonic + wall) per ADR-20, with a real-time implementation and a virtual-time implementation for the simulator.
  • replication-core/src/queue.rs: the bounded-queue primitive that backs §7 I6 — a fixed-capacity MPSC ring with an explicit try_push that returns Err(QueueFull) rather than blocking.
  • replication-observability/src/metrics.rs and src/tracing.rs: metrics-registry and OTLP exporter scaffolding per ADR-11/ADR-10, wired to a /metrics HTTP endpoint from process start.
  • replication-test-harness/src/simulator.rs: virtual-clock event loop, deterministic seed control, the harness every phase's fixtures (§12.5 onward) execute against — implements the debugging methodology closed out in §7.
  • Add reproducible-build stamping (git SHA, build timestamp truncated to build-day, toolchain version) surfaced on the health endpoint, per ADR-14's reproducibility rationale.
  • Add configuration loader (TOML) with schema validation and a fail-closed default (§6 P10) on any unknown key.

12.3 Deliverable

A runnable runtime skeleton per node exposing a health endpoint, a Prometheus /metrics endpoint, structured JSON logs, and successful TOML config parsing — no replication logic yet, but every crate in §10 compiles, links, and passes its (currently trivial) integration test.

12.4 Acceptance Criteria

  • CI green across all twelve crates on every commit to main.
  • cargo clippy --workspace -- -D warnings passes with zero warnings.
  • Reproducible build: two clean builds from the same commit produce byte-identical stripped binaries (checksum match).
  • Runtime startup to health-endpoint-ready: < 2 seconds (feeds the §4 startup budget).
  • Simulator executes 10,000 deterministic ticks with zero wall-clock reads leaking into the virtual-time path (asserted by replication-test-harness).

12.5 Conformance Fixtures

  • fixtures/config/minimal.toml — smallest valid config, exercises default-fill behavior.
  • fixtures/config/malformed_missing_region.toml — missing required region_id key, must fail-closed with ProtocolViolation-class error, not panic.
  • fixtures/runtime/bootstrap_ok.json — golden startup trace for regression comparison.
  • fixtures/runtime/duplicate_replica_id.toml — two replicas configured with the same ReplicaId; must be rejected at config-validation time, not at first collision at runtime.

12.6 Pitfalls

  • Runtime global state leakage. Manifestation: tests pass individually, fail when run in parallel. Root cause: a static/OnceCell shared across test processes. Debugging method: run cargo test -- --test-threads=1 to confirm order-dependence, then grep for static. Signal: nondeterministic CI failures with no code change. Recovery: dependency injection of the Clock and metrics registry (§12.2) instead of process-global singletons.
  • Unbounded logging. Manifestation: disk exhaustion in a long-running soak test. Root cause: per-frame debug-level logs left enabled. Signal: disk-usage alert with no corresponding traffic spike. Recovery: sampling + log-level gating enforced at the macro layer, not per call site.
  • Tracing context loss across an async boundary. Manifestation: a trace span "disappears" between WAL append and transport send. Root cause: a spawned task not instrumented with the parent span (violates §6 P4). Debugging method: diff span IDs across the boundary in a captured trace. Recovery: tracing::Instrument applied at every tokio::spawn call site, enforced by a clippy lint in CI.

12.7 Performance Concerns

  • Logging macros must not heap-allocate on the hot path for the common (non-error) case — use the tracing crate's lazy-field evaluation, not pre-formatted strings.
  • Startup IO (config read, cert load) must be synchronous and off the async runtime's reactor thread to avoid blocking other tasks during the < 2 s startup window.
  • Parsed configuration is cached immutable after load; no per-request re-parse.

12.8 Edge Cases

  • Malformed TOML with a byte-order-mark prefix — parser must reject, not silently truncate.
  • Missing TLS certificate file at a configured path — fail-closed at startup, not at first connection attempt (P10).
  • Duplicate ReplicaId across two config files loaded via include — validation must span the fully-resolved config, not per-file.
  • Clock skew between the virtual-time simulator and any accidental real-time read — asserted by the harness as a hard test failure, never a warning.

12.9 Failure Analysis

Bootstrap failures terminate the process immediately with a structured diagnostic (error variant from §11.1, offending config key or file path, remediation hint) written to stderr before any logging subsystem is assumed ready — this must not itself depend on the logging subsystem it is diagnosing. Blast radius is contained to the single node; no bootstrap failure can propagate to peers because a node that fails to start never opens a listening socket.

12.10 Operational Notes

Metrics: runtime_build_info (gauge with git SHA label), runtime_startup_seconds (histogram). Tracing spans: runtime.bootstrap, runtime.config_load. Structured-log fields: build_sha, config_path, startup_phase. Deployment: container entrypoint runs config validation in a --check mode before the real process starts, so a bad rollout fails the readiness probe instead of crash-looping. Rollback: prior container image tag is always retained one release back (ADR-18).

13. Phase 1 — WAL Subsystem & Durability

13.1 Objectives

  • Implement the durable, append-only WAL (replication-wal) with deterministic segment ordering and replay, satisfying §7 I1 and §7 I3 from the first write.
  • Enforce §6 P9 (WAL Before Visibility): no code path may acknowledge a write before its fsync returns.
  • Land crash-recovery scanning that meets the < 90 s startup-recovery budget (§4) at 1M entries.
  • Establish the fsync-policy manager as a pluggable strategy (per-write vs. batched) without breaking the durability guarantee either way.

13.2 Detailed Implementation Steps

  • replication-wal/src/segment.rs: fixed-size segment file format — header (segment number, creation epoch), sequence of WalEntry frames (§11), footer checksum-of-checksums; segment rotation triggered at a configurable byte threshold.
  • replication-wal/src/fsync.rs: trait FsyncPolicy with PerWrite and BatchWindow(Duration) implementations; batched mode still blocks the acknowledging caller until its specific write's fsync completes (Kreps et al. 2011's batching insight, applied without weakening P9).
  • replication-wal/src/checksum.rs: CRC32 over each frame and a rolling checksum over the segment, enforcing §7 I3 before any frame is handed to a replay worker.
  • replication-wal/src/replay_cursor.rs: monotonic WalSequence cursor per stream (§11 ReplicationCursor), advanced only after a frame passes checksum validation (I1).
  • replication-wal/src/repair.rs: WAL repair tool that truncates a segment at the last valid frame boundary found by the crash-recovery scanner, per van Renesse and Schneider's ordered-topology reasoning (Chain Replication, applied in §7).
  • Add an mmap-backed read path for replay (page-cache-friendly, avoids a syscall per frame read) and a sequence allocator that hands out WalSequence values under a single-writer lock per stream (ADR-08).
  • Implement WAL retention policy (segment eligible for deletion only after the ack watermark, §11 AckWatermark, has passed its last frame) and segment-compaction metadata for the retention scan.
  • Add crash-recovery scanner: on startup, walk segments newest-to-oldest, verify checksums, and quarantine (not delete) the first segment that fails validation, per §7 I3 recovery column.

13.3 Deliverable

A persistent WAL crate supporting append, checksum-validated replay, and crash recovery, exercised end-to-end by replication-test-harness against a simulated power-failure (process killed mid-write, no fsync on the torn frame).

13.4 Acceptance Criteria

  • Survives 500 simulated power-failure injections (fixtures/wal/*) with zero silent corruption.
  • Replay is byte-identical and order-identical across 1M entries on ten repeated runs (§7 I7).
  • Corruption isolation confirmed: a corrupted frame quarantines exactly one segment, never more.
  • Startup recovery scan completes in < 90 s at 1M entries on the reference NVMe target (§4).
  • WAL fsync p99 < 2 ms under the PerWrite policy on the reference hardware profile (§4).

13.5 Conformance Fixtures

  • fixtures/wal/corrupted_crc.bin — single frame with a flipped bit; must quarantine and continue.
  • fixtures/wal/partial_tail.bin — segment truncated mid-frame (simulates a torn write); repair tool must truncate cleanly at the last complete frame.
  • fixtures/wal/replay_reference.bin — 1M-entry golden trace for deterministic-replay regression.
  • fixtures/wal/duplicate_sequence.bin — malformed input with a repeated WalSequence; must reject, not silently overwrite.

13.6 Pitfalls

  • Torn writes. Manifestation: a frame with a valid header but corrupted payload tail. Root cause: partial sector persistence on power loss mid-write. Debugging method: replay the crash-recovery scanner against the raw segment bytes offline. Signal: checksum failure exactly at the last frame written before the crash. Recovery: repair tool truncates at last-good frame.
  • Replay drift from hidden nondeterminism. Manifestation: two replay runs of the same input diverge. Root cause: a wall-clock read leaking into replay logic instead of using the logged timestamp_ns. Debugging method: differential replay under the simulator's virtual clock (§7 closing paragraph). Recovery: audit every replay code path for SystemTime::now() calls.
  • Excessive fsync frequency. Manifestation: throughput collapses under small-write workloads. Root cause: PerWrite policy with no batching under high concurrency. Signal: fsync-latency histogram p50 stays low but throughput metric craters. Recovery: switch to BatchWindow policy with a bounded window (still honoring P9 per-caller).
  • mmap eviction thrash. Manifestation: replay throughput drops under memory pressure. Root cause: page cache eviction of hot WAL segments under a competing memory consumer. Recovery: pin the active replay window's segment via madvise(MADV_WILLNEED).

13.7 Performance Concerns

  • Batch fsyncs under BatchWindow policy to amortize syscall cost without violating P9's per- caller durability wait.
  • Page-cache pressure from cold segment reads during replay — prefer sequential scan order.
  • mmap eviction behavior under concurrent replay workers competing for the same cache lines.
  • CRC32 computation should use a hardware-accelerated (SSE4.2/ARMv8 CRC) path to stay off the critical latency path at 1.5M ops/sec (§4).

13.8 Edge Cases

  • Disk full mid-append — must fail the append with a distinguishable error, not corrupt the segment header.
  • Checksum collision (extremely low probability but must degrade gracefully, not panic).
  • Segment truncation exactly at a frame boundary vs. mid-frame — repair logic must distinguish.
  • Sequence-allocator restart after crash — must resume from the last durably-written sequence, not from an in-memory counter that reset to zero.

13.9 Failure Analysis

Corruption detection quarantines the affected segment and halts replay progression for that stream only — other streams' segments are unaffected (§4 "WAL corruption tolerance: single-segment containment"). Operator visibility: quarantine event emits a P1 alert with the segment file path and byte offset. Postmortem guidance: correlate quarantine timestamp against disk SMART/power- event logs before assuming a software bug.

13.10 Operational Notes

Metrics: wal_fsync_latency_seconds (histogram), wal_segment_count (gauge), wal_replay_throughput_entries_per_sec (gauge), wal_quarantined_segments_total (counter). Tracing spans: wal.append, wal.fsync, wal.replay_scan. Structured-log fields: segment_id, wal_sequence, fsync_policy. Migration: WAL format version is stamped in the segment header (§11 TransportFrame mirrors this); a version bump requires a documented forward-read path in replication-wal/src/segment.rs.

14. Phase 2 — Transport Runtime

14.1 Objectives

  • Implement the encrypted, WAN-aware replication transport (replication-transport) over QUIC (ADR-06), meeting the p99 apply-latency budget under the §4 350 ms RTT assumption.
  • Provide multiplexed, per-stream flow so one slow StreamId cannot head-of-line-block another.
  • Implement mutual-TLS peer authentication (ADR-17) as the transport's trust boundary (§3.2).

14.2 Detailed Implementation Steps

  • replication-transport/src/quic.rs: integrate quinn (RFC 9000) as the QUIC runtime; one QUIC connection per peer, one QUIC stream per StreamId to get multiplexing without head-of-line blocking across streams.
  • replication-transport/src/frame.rs: encode/decode TransportFrame (§11) with the fixed header layout of §8.2; decoding rejects on bad magic or version before touching the payload (P10).
  • TLS mutual authentication via rustls (ADR-17, RFC 8446): peer certificate CN maps to a ReplicaId; unknown or expired certs are rejected at the handshake, never at first frame.
  • replication-transport/src/retransmit.rs: retransmission policy layered above QUIC's built-in loss recovery for application-level acknowledgment timeouts (distinct from QUIC packet ACKs).
  • Add congestion metrics export (RTT histogram, congestion-window gauge) sourced from quinn's connection stats API, per RFC 5681's congestion-control model (applied in §28).
  • replication-transport/src/compression.rs: negotiate Zstd compression per-connection during the QUIC handshake's application-layer capability exchange (ADR-06's WAN-efficiency rationale).
  • Implement bounded send queues per stream (§7 I6) — a full send queue is backpressure signaled to the scheduler (§15), not silently dropped.
  • Add heartbeat frames and peer-disconnect detection distinct from QUIC's idle-timeout, tuned tighter than the transport-layer default to catch a hung peer faster than 30 s.
  • Implement zero-copy buffer handling for the payload region (the one place unsafe is permitted in this codebase per §12.2's lint policy) to avoid a full-frame copy per send.

14.3 Deliverable

A bidirectional, multiplexed, encrypted replication channel between two nodes, exercised by the harness's simulated WAN link (configurable loss rate, RTT, and reorder).

14.4 Acceptance Criteria

  • Survives a 5% simulated packet-loss injection with zero corrupted frames delivered upstream.
  • Reconnects within 5 seconds of a simulated link flap (§4 RTO-adjacent budget for transport-level recovery, distinct from the cluster-wide 5-minute RTO).
  • Protocol compatibility validated against fixtures/transport/* across two adjacent minor versions (§25).
  • p99 frame round-trip under nominal 350 ms RTT stays within the §4 replication-lag budget.

14.5 Conformance Fixtures

  • fixtures/transport/invalid_frame.pb — malformed frame with a truncated payload length field.
  • fixtures/transport/compression_negotiation.pb — capability-exchange trace exercising both compression-enabled and compression-disabled negotiation outcomes.
  • fixtures/transport/replay_attack.pb — a previously-seen frame resent by a malicious peer; must be rejected as a duplicate at the idempotency layer, not double-applied.
  • fixtures/transport/mtls_expired_cert.pb — handshake attempt with an expired peer certificate.

14.6 Pitfalls

  • Head-of-line blocking across streams sharing one connection. Manifestation: one slow stream stalls unrelated streams. Root cause: falling back to a single QUIC stream for all traffic instead of one per StreamId. Recovery: verify per-stream QUIC stream allocation in code review.
  • Excessive retransmits under asymmetric loss. Manifestation: retransmit counter climbs while actual loss is low. Root cause: retransmit timeout tuned for LAN RTT, not the §4 350 ms WAN assumption. Recovery: RTT-adaptive timeout, not a fixed constant.
  • TLS renegotiation stalls. Manifestation: periodic latency spikes correlated with cert rotation. Root cause: renegotiation blocking the connection's send path. Recovery: rotate certificates via a new connection handshake, never mid-connection renegotiation.

14.7 Performance Concerns

  • Syscall batching for send/receive (sendmmsg/recvmmsg where available) to reduce per-frame syscall overhead at 1.5M ops/sec.
  • NIC queue pressure under burst traffic — monitor driver-level TX/RX ring drops, not just application-level metrics.
  • Packet coalescing to reduce small-frame overhead without violating the p50 apply-latency budget.

14.8 Edge Cases

  • Asymmetric MTU between regions — must fall back to a safe minimum, not assume path MTU discovery succeeds.
  • Clock skew between peers affecting heartbeat interpretation — heartbeats use monotonic intervals, never wall-clock deltas.
  • Duplicate frames from a retransmit racing a late original — idempotency window (§11 ReplaySession) absorbs these before they reach the WAL.

14.9 Failure Analysis

Transport failures degrade the affected stream's state (to BACKPRESSURED or DEGRADED, §8.3) but never threaten already-fsynced WAL durability — the transport layer sits entirely downstream of the durability boundary (§3.2). Blast radius is one peer connection; other peer connections on the same node are unaffected (separate QUIC connections, separate send queues).

14.10 Operational Notes

Metrics: transport_rtt_seconds (histogram), transport_retransmits_total (counter), transport_connection_churn_total (counter), transport_send_queue_depth (gauge). Tracing spans: transport.send, transport.receive, transport.handshake. Structured-log fields: peer_id, connection_id, compression_enabled. Rollback: protocol version negotiation (§25) means a transport rollback to the prior minor version is a config flag, not a redeploy.

15. Phase 3 — Replication Scheduler & Flow Control

15.1 Objectives

  • Implement replication pacing, batching, and credit-based backpressure (replication-scheduler), enforcing §7 I6 and §7 I10 across every stream.
  • Guarantee per-region fairness so one saturated region cannot starve another's inflight quota.
  • Keep p99 queue latency under the §4-derived 50 ms budget under nominal load.

15.2 Detailed Implementation Steps

  • replication-scheduler/src/quota.rs: implement SchedulerQuota (§11) as a per-stream credit ledger; credit is granted by the remote's ack rate and consumed by inflight sends (§7 I10).
  • replication-scheduler/src/batching.rs: adaptive batching — batch size grows under sustained low-latency acks and shrinks under rising RTT/retransmit signals from the transport layer (§14), balancing the p50/p99 latency tradeoff of §4.
  • replication-scheduler/src/backpressure.rs: propagate transport-layer send-queue-full signals (§14 I6) upstream to the WAL append path so producers see backpressure before memory grows (P2, Backpressure Everywhere).
  • Priority queues per stream class (interactive vs. bulk catch-up) with a starvation-prevention mechanism: no priority class may be starved for more than a bounded number of scheduling rounds (Kafka's ISR fairness reasoning, Kreps et al. 2011, applied here for regional fairness).
  • Per-region quotas layered above per-stream quotas so the §4 max-regional-fanout (32) ceiling is enforced at the scheduler, not left to transport-level congestion alone.
  • Add retry windows with exponential backoff bounded by a ceiling, distinct from QUIC's own loss- recovery retransmits — this is application-level retry after an explicit NACK or timeout.
  • Scheduler telemetry: per-stream queue depth, per-region aggregate inflight, credit-exhaustion events — feeding §19's dashboards directly.

15.3 Deliverable

An adaptive replication scheduler enforcing bounded queue memory and per-region fairness, validated against a simulated multi-region fanout with one artificially slow region.

15.4 Acceptance Criteria

  • Bounded queue memory: total scheduler memory footprint stays under the §4 32 GB node budget at 10,000 concurrent streams.
  • No starvation under load: every priority class receives at least one scheduling slot per 100 ms window (fixtures/scheduler/priority_starvation.json).
  • p99 queue latency < 50 ms under nominal load (§4-derived budget).
  • Credit-overdraft counter (§7 I10) stays at zero across a 1-hour soak test.

15.5 Conformance Fixtures

  • fixtures/scheduler/priority_starvation.json — bulk catch-up traffic saturating the queue while interactive traffic must still get slots.
  • fixtures/scheduler/backpressure.json — transport signals send-queue-full; scheduler must throttle the producer within one scheduling round.
  • fixtures/scheduler/region_slowdown.json — one region's ack rate drops 90%; other regions' fairness must be unaffected.
  • fixtures/scheduler/credit_overdraft_attempt.json — malformed internal state simulating an attempted overdraft; must be rejected by the credit-ledger assertion (§7 I10).

15.6 Pitfalls

  • Feedback oscillation in adaptive batching. Manifestation: batch size oscillates wildly instead of converging. Root cause: batching decision reacts to instantaneous RTT instead of a smoothed estimator (classic TCP-like control-loop bug, Stevens ch. 21). Recovery: exponentially-weighted moving average on the RTT signal before it feeds the batching decision.
  • Queue collapse under burst. Manifestation: queue depth spikes then the scheduler sheds an entire region's traffic at once. Root cause: admission control threshold too close to the hard capacity limit, no graduated backpressure. Recovery: graduated backpressure (soft threshold warns, hard threshold rejects) instead of one binary cutoff.
  • Retry amplification. Manifestation: retry traffic itself saturates the link during a partial outage. Root cause: retry backoff ceiling too low relative to the outage duration. Recovery: cap retry rate independent of backoff curve, feeding into the per-region quota.

15.7 Performance Concerns

  • Lock contention on the per-stream quota ledger under high stream count — use per-stream atomics, not a global mutex (ADR-08).
  • Atomic hotspotting on a shared aggregate counter across 10,000 streams — shard the aggregate across NUMA-local partial sums, reduce on read (§4 NUMA row).
  • Batching inefficiency at small message sizes — batch by byte budget, not just message count.

15.8 Edge Cases

  • Sudden regional slowdown mid-batch — in-flight batch must not block unrelated streams' credit replenishment.
  • Burst traffic exceeding instantaneous credit — must queue (bounded) rather than reject outright if capacity remains under the hard ceiling.
  • Queue exhaustion exactly at the admission boundary — must be deterministic (always reject at N, never off-by-one accept at N+1 under race).

15.9 Failure Analysis

Scheduler overload triggers admission control: new stream registration is rejected while existing streams continue draining under their existing credit, and the coordinator transitions the node to a degraded-admission state visible on the admin API. Blast radius is bounded to new-stream admission; already-admitted streams keep making progress at reduced batch size.

15.10 Operational Notes

Metrics: scheduler_queue_depth (gauge, per stream and per region), scheduler_credit_available (gauge), scheduler_starvation_events_total (counter). Tracing spans: scheduler.enqueue, scheduler.batch_flush. Structured-log fields: stream_id, region_id, batch_size. Operators inspect queue depth and lag progression via the admin API's topology-scoped dashboard (§19).

16. Phase 4 — Membership & Epoch Management

16.1 Objectives

  • Implement topology coordination (replication-membership) via a Raft metadata plane (ADR-19), enforcing §7 I2 (Epoch Consistency) and §7 I8 (Fencing Token) from first commit.
  • Guarantee split-brain prevention under simultaneous-failover conditions.
  • Keep metadata quorum latency compatible with the §4 32-region fanout ceiling.

16.2 Detailed Implementation Steps

  • replication-membership/src/raft_meta.rs: a small Raft group (Ongaro and Ousterhout 2014, applied here) carrying only topology metadata — region list, peer descriptors, current epoch — never replication data itself (kept distinct from the data-plane streams per §3.2).
  • replication-membership/src/epoch.rs: epoch transition protocol — a topology change proposes a new EpochId strictly greater than the current one (§7 I2, §6 P11); commit requires Raft-group majority before the new epoch is announced to peers.
  • replication-membership/src/fencing.rs: fencing tokens (§7 I8) issued alongside each epoch bump; a WAL append or ack carrying a superseded token is rejected at the WAL layer (§13), closing the loop between membership and durability.
  • replication-membership/src/liveness.rs: peer liveness probes distinct from transport heartbeats (§14) — liveness feeds failover decisions, heartbeats feed connection-health metrics only.
  • Region metadata replication through the Raft group so every node observes the same topology view within one Raft commit round, never via best-effort gossip (ADR-19's rationale over gossip).
  • Capability negotiation: peers exchange supported protocol/feature versions at registration, stored in PeerDescriptor.capabilities (§11), consulted before enabling any Phase 8+ feature.
  • Failover coordination: on liveness-probe timeout, the coordinator proposes a new epoch excluding the unreachable peer; the failover FSM (§3.2) drives the exclusion through fencing before any new writer is admitted for that stream.

16.3 Deliverable

A consistent membership subsystem where every node's view of the current epoch and region metadata converges within one Raft-commit round of any topology change, validated under simulated simultaneous-failover scenarios.

16.4 Acceptance Criteria

  • Split-brain prevention verified: fixtures/membership/split_brain.json produces exactly one active writer per stream across 1,000 randomized simultaneous-failover simulator runs.
  • Epoch monotonicity validated: no simulator run observes an epoch regression (§7 I2) across 10,000 topology-change events.
  • Metadata quorum commit latency stays under 200 ms at 32-region fanout (feeds §4's fanout ceiling).

16.5 Conformance Fixtures

  • fixtures/membership/stale_epoch.pb — a frame tagged with a superseded epoch; must be rejected with EpochMismatch (§11.1), never silently accepted.
  • fixtures/membership/split_brain.json — two candidate coordinators proposing epoch bumps simultaneously; exactly one must win the Raft-group majority.
  • fixtures/membership/fencing_replay.pb — a delayed append carrying a superseded fencing token (§7 I8), simulating network delay resurfacing stale traffic.
  • fixtures/membership/region_isolation.json — one region's Raft-group members become unreachable; cluster must degrade that region only, not the whole topology.

16.6 Pitfalls

  • Stale routing caches. Manifestation: a node routes to a peer that lost leadership one epoch ago. Root cause: routing cache not invalidated on epoch bump. Recovery: routing cache keyed by (RegionId, EpochId), never just RegionId.
  • Epoch rollback via a delayed message. Manifestation: an old epoch announcement arrives after a newer one due to network reordering. Root cause: epoch announcements not idempotent against reordering. Recovery: strictly-greater-than comparison at every consumer (§7 I2), never "most recently received."
  • Quorum fragmentation under regional partition. Manifestation: the metadata Raft group cannot reach majority during a multi-region partition. Root cause: Raft-group member placement not anti-affinity-aware across regions. Recovery: place Raft-group members across independent failure domains (§11 FailureDomain), never all in one region.

16.7 Performance Concerns

  • Metadata fanout cost grows with region count — batch topology-change notifications rather than one RPC per region per change.
  • Quorum commit latency is the metadata plane's tail-latency driver — keep the Raft group small (odd count, typically 3–5) independent of the 32-region data-plane fanout.

16.8 Edge Cases

  • Region isolation during an in-progress epoch transition — the isolated region must not observe a torn topology view (partially-applied change).
  • Simultaneous failover of two regions — fencing must resolve deterministically without a manual tie-break, per the Raft group's single-leader commit ordering.
  • Capability negotiation mismatch mid-rolling-upgrade — older peers must remain functional at their negotiated capability level, not be disconnected outright (§25).

16.9 Failure Analysis

Metadata-quorum loss (fewer than majority of the Raft group reachable) transitions the cluster into a read-only safety mode: no new epoch can be committed, but already-admitted streams continue under their last-known-good epoch until quorum is restored. Blast radius: topology changes are blocked cluster-wide; data-plane replication for already-fenced streams is unaffected.

16.10 Operational Notes

Metrics: membership_epoch (gauge), membership_election_latency_seconds (histogram), membership_peer_churn_total (counter). Tracing spans: membership.epoch_transition, membership.fencing_check. Structured-log fields: epoch_id, region_id, fencing_token. Deployment: Raft-group member count is fixed at cluster-bootstrap time; changing it requires a documented online membership-change procedure, never a config-only edit.

17. Phase 5 — Snapshot Engine

17.1 Objectives

  • Implement checkpointed, chunked, resumable snapshot synchronization (replication-snapshot), enforcing §7 I5 (Snapshot Atomicity) and §7 I9 (Snapshot/WAL Skew Bound).
  • Meet the §4 snapshot-restore-throughput budget (> 1 GB/sec) on the reference NVMe target.
  • Provide the fallback path the scheduler (§15) invokes when WAL catch-up would exceed the lag budget.

17.2 Detailed Implementation Steps

  • replication-snapshot/src/manifest.rs: SnapshotManifest (§11) written via rename-on-complete — the manifest file is written to a temp path and atomically renamed only after every chunk checksum (§11 chunk_checksums) validates, giving §7 I5 for free from the filesystem's atomic rename guarantee.
  • replication-snapshot/src/chunker.rs: chunked transfer with resumable offsets — a chunk index is tracked per in-progress transfer so an interrupted WAN transfer resumes from the last completed chunk, not from zero (Petrov's checkpointing chapter, applied here).
  • replication-snapshot/src/restore.rs: restore engine validates every chunk checksum before writing it into the target storage engine adapter (§3.2), and validates the assembled manifest's wal_sequence_at_snapshot against the local replay cursor before marking the restore usable (§7 I9).
  • replication-snapshot/src/gc.rs: garbage-collect superseded manifests only after confirming no in-progress restore references them — a manifest reference count, not a fixed retention timer.
  • Incremental delta snapshots: chunks unchanged since the prior snapshot are referenced, not re-transferred, bounding write amplification (§4's 3.5x ceiling, derivation in §32).
  • Snapshot throttling: chunk-transfer rate is subject to the same scheduler credit ledger (§15) as WAL streaming, so a snapshot transfer cannot starve concurrent WAL replication on the same link.
  • Restore verification: post-restore, replay a bounded WAL suffix (from wal_sequence_at_snapshot forward) and compare a content hash against a reference to catch a subtly-corrupted restore before the stream transitions out of SNAPSHOT_SYNC.

17.3 Deliverable

A snapshot synchronization subsystem supporting atomic checkpoint creation, resumable chunked transfer, and verified restore, exercised against a simulated mid-transfer WAN disconnect.

17.4 Acceptance Criteria

  • Restore correctness verified: 200 simulator runs of fixtures/snapshot/interrupted_transfer.json all resume and complete without re-transferring already-validated chunks.
  • Snapshot restore throughput > 1 GB/sec sustained on the reference NVMe target (§4).
  • Checksum validation complete: zero chunks accepted into a restore without a prior checksum pass.
  • Snapshot/WAL skew (§7 I9) never exceeds one segment across 10,000 simulated snapshot-then-catch-up cycles.

17.5 Conformance Fixtures

  • fixtures/snapshot/corrupted_chunk.bin — one chunk with a checksum mismatch; restore must reject that chunk and re-request it, not accept the manifest with a hole.
  • fixtures/snapshot/interrupted_transfer.json — WAN disconnect mid-transfer at a randomized chunk offset; resume must not re-fetch completed chunks.
  • fixtures/snapshot/manifest_wal_mismatch.pb — a manifest whose wal_sequence_at_snapshot is inconsistent with the local replay cursor by more than one segment; must trigger re-sync (§7 I9).
  • fixtures/snapshot/gc_race.json — a GC sweep racing an in-progress restore referencing the same manifest; GC must defer, never delete a referenced manifest.

17.6 Pitfalls

  • Stale snapshots used past their WAL-skew bound. Manifestation: replay after restore diverges from expected state. Root cause: restore accepted a manifest whose wal_sequence_at_snapshot had drifted beyond one segment from the local cursor. Recovery: enforce §7 I9's cross-check as a hard gate before exiting SNAPSHOT_SYNC.
  • Chunk ordering bugs in resumable transfer. Manifestation: restored state is subtly wrong but passes a naive checksum-per-chunk check. Root cause: chunks written out of order to the target adapter despite passing individual validation. Recovery: restore engine writes chunks in manifest order regardless of arrival order, buffering out-of-order chunks.
  • Snapshot/WAL mismatch after a fast-forward config change. Manifestation: a stream's WAL retention (§13) collects the segment a snapshot's manifest still points to. Recovery: retention policy must consult all live manifest references (§17.2 GC logic) before collecting a segment.

17.7 Performance Concerns

  • IO amplification from chunk-level checksumming — checksum incrementally during the streaming read/write, not as a separate full-chunk re-read pass.
  • Compression CPU cost (Zstd, ADR-06) on the snapshot path competes with the transport's own compression negotiation — share one compression context, do not double-compress.
  • Restore-path sequential-write pattern should match the target storage engine adapter's preferred write granularity to avoid read-modify-write amplification downstream.

17.8 Edge Cases

  • Disk full mid-restore — must fail cleanly with the partial restore state discoverable and resumable, not leave an ambiguous half-written target.
  • Partial restore interrupted twice in a row at different chunk offsets — resume logic must handle a resume-of-a-resume without re-validating already-confirmed chunks.
  • Snapshot divergence: two regions independently producing manifests with the same SnapshotId space but different content — SnapshotId generation must be collision-resistant (u128, §11).

17.9 Failure Analysis

A failed restore (checksum failure past retry budget, or WAL-skew violation) triggers quarantine of that manifest and a rollback to the prior known-good snapshot, with the affected stream held in SNAPSHOT_SYNC until a fresh manifest is available. Blast radius is the single stream undergoing restore; other streams on the same node are unaffected since restore runs in its own worker pool.

17.10 Operational Notes

Metrics: snapshot_age_seconds (gauge), snapshot_restore_throughput_bytes_per_sec (gauge), snapshot_chunk_retries_total (counter). Tracing spans: snapshot.chunk_transfer, snapshot.restore_verify. Structured-log fields: snapshot_id, chunk_index, manifest_state. Migration: manifest format version is independent of WAL format version (§13.10) so either can evolve without forcing a lockstep release.

18. Phase 6 — Replay Engine

18.1 Objectives

  • Implement deterministic mutation replay (replication-replay), the direct enforcement point for §7 I7 (Replay Determinism) and §7 I11 (Idempotent Replay).
  • Bound replay lag so a caught-up stream stays within the §4 replication-lag budget.
  • Provide the replay tracing that the differential-testing harness (§26) consumes.

18.2 Detailed Implementation Steps

  • replication-replay/src/apply_queue.rs: an ordered apply queue per stream — strictly sequenced by WalSequence (§7 I1), never reordered for throughput, because reordering would violate the determinism this whole phase exists to guarantee (P1, Determinism Over Convenience).
  • replication-replay/src/replay.rs: ReplaySession (§11) lifecycle — resume from a checkpointed resume_sequence, apply frames through the storage engine adapter (§3.2), advance the cursor only after the adapter confirms durable apply.
  • replication-replay/src/idempotency.rs: idempotency window (§11 ReplaySession.idempotency_window) — a bounded sliding window of recently-applied sequences; a duplicate within the window is a no-op (§7 I11), never a re-apply, protecting against transport-level retransmit duplicates (§14).
  • Transaction-boundary enforcement: a TransactionId (§8.1) spanning multiple WalEntry frames must apply atomically at the adapter boundary — partial-transaction replay is rejected, not best-effort applied.
  • Replay tracing: every apply emits a trace span parented to the original WAL-append span (from §13), preserving end-to-end correlation across the replication pipeline per §6 P4.
  • Deterministic scheduler hooks: the apply queue's worker-scheduling decisions are themselves deterministic given the same input order (Mattern 1989's causal-ordering reasoning extended to scheduling, not just data), so the simulator can reproduce a specific worker interleaving.
  • Replay worker pool sized per-stream (one worker per active StreamId replay, §3.2 concurrency boundary) to keep replay of one stream from serializing behind another's slow adapter calls.

18.3 Deliverable

A replay engine applying replicated WAL streams to the storage engine adapter with bounded lag and byte-for-byte deterministic output across repeated runs of the same input, validated by the differential-testing harness (§26).

18.4 Acceptance Criteria

  • Deterministic replay across 50 repeated runs of fixtures/replay/out_of_order.bin produces an identical resulting-state hash every time (§7 I7).
  • Replay lag stays bounded under 250 ms (§4) at sustained 1.5M ops/sec input rate.
  • Duplicate-apply counter (§7 I11 telemetry) stays at zero across a 1-hour soak with injected transport-level retransmits.
  • Transaction-boundary violations: zero partial-transaction applies across 10,000 simulated crash- mid-transaction injections.

18.5 Conformance Fixtures

  • fixtures/replay/duplicate_apply.json — a retransmitted frame with a sequence already inside the idempotency window; must be a no-op.
  • fixtures/replay/out_of_order.bin — frames arriving out of WalSequence order (simulating transport reordering); apply queue must re-sequence before applying, never apply out of order.
  • fixtures/replay/torn_transaction.bin — a crash injected mid-TransactionId; recovery must reject the partial transaction on resume, not apply half of it.
  • fixtures/replay/adapter_apply_failure.json — the storage engine adapter returns an error on apply; replay must halt that stream and surface the error, never skip the entry silently.

18.6 Pitfalls

  • Hidden nondeterminism from unordered collection iteration. Manifestation: replay hash differs between runs despite identical input. Root cause: a HashMap iteration order leaking into apply ordering somewhere in the adapter-facing code. Recovery: replace with an explicitly-ordered collection (BTreeMap/Vec) anywhere replay-order-sensitive state is iterated.
  • Duplicate application across a resume boundary. Manifestation: an entry is applied twice after a process restart. Root cause: resume_sequence checkpointed before the apply confirmed durable, not after. Recovery: checkpoint only after the adapter's apply-confirmation callback.
  • Transaction-boundary drift under partial replay. Manifestation: adapter state reflects half a logical transaction. Root cause: apply queue treating each WalEntry independently instead of grouping by TransactionId before handing off to the adapter. Recovery: buffer a transaction's full frame set before the first adapter call for that TransactionId.

18.7 Performance Concerns

  • Replay-queue contention when many streams' workers contend for a shared adapter connection pool — size the pool to the §4 max-concurrency budget, not unboundedly.
  • Cache locality: process frames for one stream on one worker consistently (avoid bouncing a stream's replay across cores) to keep the idempotency-window lookup cache-hot.
  • Transaction buffering adds latency proportional to transaction size — bound maximum transaction frame count to keep buffering latency inside the p99 budget.

18.8 Edge Cases

  • Replay interruption mid-transaction — must resume without re-requesting already-buffered frames that survived the interruption in memory-mapped WAL state.
  • Partial transaction replay after a stream migration between workers — the new worker must inherit the exact buffered-frame state, not restart the transaction from its first frame.
  • Idempotency-window overflow under a very large retransmit burst — window eviction must not evict an entry still within the resend-timeout horizon, or a legitimate duplicate could re-apply.

18.9 Failure Analysis

A replay-hash mismatch (§7 I7 violation) forces immediate halt of that stream's replay and a snapshot fallback (§17) rather than continued best-effort replay — continuing would compound the divergence. Operator visibility: mismatch emits a P0 alert naming the stream, the last-good sequence, and the divergent hash for forensic comparison against the reference trace.

18.10 Operational Notes

Metrics: replay_throughput_entries_per_sec (gauge), replay_apply_latency_seconds (histogram), replay_hash_mismatch_total (counter, should be permanently zero in a healthy cluster). Tracing spans: replay.apply, replay.transaction_buffer. Structured-log fields: stream_id, txn_id, resume_sequence. Deployment: replay-worker pool size is a runtime-tunable config, adjustable without a redeploy via the admin API.

19.1 Objectives

19.3 Deliverable

An operational telemetry stack where every replication decision from Phases 0–6 is visible via one consistent metric/span/log-field name, exercised by verifying end-to-end trace correlation across a simulated multi-hop replication path.

19.4 Acceptance Criteria

  • Traces correlate end-to-end: 100% of sampled traces in fixtures/observability/trace_sample.json show an unbroken span chain from WAL append through replay apply.
  • Dashboards expose replication health: lag, queue depth, and WAL durability visible without a custom query, per the default-dashboard list in §19.10.
  • Metric cardinality stays under 100,000 unique series per node at 10,000 concurrent streams.
  • Audit log write path never blocks a replication-critical-path call — verified by a fault-injected audit-sink outage causing zero replication throughput drop.

19.5 Conformance Fixtures

  • fixtures/observability/trace_sample.json — golden end-to-end trace for correlation regression.
  • fixtures/observability/metrics_reference.prom — golden Prometheus exposition snapshot for format regression testing.
  • fixtures/observability/high_cardinality_attack.json — a malformed peer sending frames engineered to blow up a per-peer label cardinality; must be capped, not accepted unbounded.
  • fixtures/observability/exporter_outage.json — OTLP exporter unreachable; spans must buffer bounded and drop-oldest, never block the traced code path.

19.6 Pitfalls

  • High-cardinality metrics from unbounded labels. Manifestation: Prometheus scrape latency balloons, memory grows unbounded on the metrics registry. Root cause: a label derived from an unbounded value (e.g. raw TransactionId) instead of a bounded one (StreamId bucket). Recovery: cardinality budget enforced at metric-registration time, not caught after the fact.
  • Trace amplification. Manifestation: exporter backpressure under high span-emission rate. Root cause: 1:1 span-per-frame at 1.5M ops/sec with no sampling. Recovery: head-based sampling at the correlation-ID level (sample whole transactions, not individual spans within one).

19.7 Performance Concerns

  • Telemetry overhead on the hot path — metric increment must be a lock-free atomic, never a mutex acquisition, at 1.5M ops/sec.
  • Exporter backpressure must degrade to sampling/dropping, never to blocking the instrumented call site (§6 P12 extended).

19.8 Edge Cases

  • Exporter outage during a cluster-wide incident — the moment observability matters most is exactly when its own backend is likeliest to be under load; buffering must not itself exhaust memory.
  • Log-sink saturation during a debug-level logging burst — sampling must kick in before disk fills, not after (contrast with §12.6's unbounded-logging pitfall, now handled systemically).

19.9 Failure Analysis

Observability degradation (exporter outage, metrics-registry pressure) must never halt replication — the isolation is structural: telemetry emission is fire-and-forget from the replication-critical code's perspective, with its own bounded buffer and drop policy. Detection: a "telemetry health" meta-metric (self-reporting) flags degraded observability without requiring the very telemetry that's degraded to diagnose it.

19.10 Operational Notes

Default dashboards: replication lag (per stream and per region), regional health (liveness, epoch currency), WAL durability (fsync latency, quarantine events). Metrics: observability_exporter_up (gauge), observability_dropped_spans_total (counter). Tracing spans: observability.export_batch. Structured-log fields: correlation_id, sample_decision.

20. Phase 8 — Conflict Resolution Framework

20.1 Objectives

  • Implement active-active conflict handling, unlocking the later-phase capability named in §1, enforcing §7 I12 (Conflict Resolution Determinism).
  • Provide a deterministic resolver API without exposing a general-purpose scripting surface (that capability is explicitly deferred, PhaseDeferred("§20"), register in §35).
  • Preserve replay compatibility (§7 I7) across conflict-resolved streams.

20.2 Detailed Implementation Steps

  • Vector-clock metadata (§11 ConflictRecord.vector_clock, Mattern 1989 applied) attached to every concurrently-writable mutation, distinguishing causally-ordered writes (no conflict) from concurrent writes (candidate conflict).
  • Conflict detector: compares vector clocks at apply time in the replay engine (§18); a detected concurrent pair is routed to the resolver instead of applied directly.
  • Deterministic resolver API: a small closed set of built-in resolution strategies (last-writer- wins by a deterministic tiebreak, deterministic merge for commutative payload types per Shapiro et al. 2011's CRDT reasoning) — no arbitrary user code executes here (P1, and the deferred programmable-VM boundary, §35).
  • Tombstone semantics: a deletion is represented as a first-class tombstone ConflictRecord variant so a concurrent write-after-delete resolves deterministically rather than resurrecting deleted state ambiguously.
  • Resolver audit logs: every resolution decision is written to the audit log (§19) with the losing/winning TransactionIds and the vector-clock comparison that produced the outcome.
  • Causal ordering validation: post-resolution, the resulting vector clock must dominate both inputs' clocks — a resolver that fails this check is a resolver bug caught before it reaches production data, not a data-correctness incident.

20.3 Deliverable

A conflict-aware replication mode where concurrent writes to the same key resolve identically on every replica, validated by replaying the same concurrent-write fixture against independently- running replica simulators and diffing resulting state.

20.4 Acceptance Criteria

  • Deterministic conflict outcomes: 500 randomized concurrent-write simulator runs against fixtures/conflicts/concurrent_update.json produce byte-identical resolved state on every replica.
  • Replay compatibility preserved: ConflictRecord entries replay identically under §7 I7's existing determinism harness with zero additional exceptions.
  • Causal-domination check passes on 100% of resolutions across the soak fixture set.

20.5 Conformance Fixtures

  • fixtures/conflicts/concurrent_update.json — two regions writing the same key with concurrent (non-causally-ordered) vector clocks.
  • fixtures/conflicts/vector_clock.pb — golden vector-clock comparison trace for regression.
  • fixtures/conflicts/tombstone_race.json — a delete concurrent with an update to the same key.
  • fixtures/conflicts/cyclic_causality.json — a malformed vector clock implying a causality cycle; must be rejected as ProtocolViolation, never resolved as if valid.

20.6 Pitfalls

  • Hidden divergence from floating-point or locale-dependent comparison. Manifestation: resolver produces different winners on different replicas despite "deterministic" logic. Root cause: a tiebreak comparison using a non-total-order key (e.g. locale-collated string compare). Recovery: tiebreak strictly on (vector_clock_hash, ReplicaId) — always a total order.
  • Resolver nondeterminism from iteration order. Manifestation: same as §18.6's hidden- nondeterminism pitfall, recurring here because the resolver iterates a set of concurrent writers. Recovery: sort candidates by ReplicaId before any resolution logic runs.

20.7 Performance Concerns

  • Vector-clock metadata expansion grows with regional fanout (§4, up to 32 regions) — bound clock size by pruning entries for regions that have causally stabilized past a watermark.
  • Conflict-detection comparison cost scales with concurrent-writer count per key — cache the comparison result for the lifetime of one apply batch.

20.8 Edge Cases

  • Cyclic causality from a corrupted vector clock — reject, do not attempt to "fix" it heuristically.
  • Clock skew inflating apparent concurrency (two causally-ordered writes misclassified as concurrent because of wall-clock-derived metadata) — vector clocks are logical, not wall-clock- derived, precisely to avoid this class of bug.
  • A resolver's tiebreak losing entry deleted by a concurrent tombstone before the resolution write lands — apply order at the adapter must be atomic per §18.2's transaction-boundary enforcement.

20.9 Failure Analysis

A resolver failure (causal-domination check fails, or an unrecognized ConflictRecord variant arrives from a newer minor version) quarantines the affected stream rather than guessing a resolution — an incorrect guess is strictly worse than a paused stream, per P1. Blast radius: one stream; unrelated keys and streams are unaffected.

20.10 Operational Notes

Audit every resolution decision (§20.2) — this is a hard operational requirement, not optional logging, because conflict resolution is the one place this system makes a data-visible choice on the operator's behalf. Metrics: conflict_resolutions_total (counter, by strategy), conflict_resolution_divergence_total (counter, §7 I12). Tracing spans: conflict.detect, conflict.resolve. Structured-log fields: winning_txn_id, losing_txn_id, strategy.

21. Phase 9 — Chaos & Recovery Automation

21.1 Objectives

  • Validate resilience under real failure classes using replication-chaos-suite, exercising every invariant in §7 under adversarial conditions rather than nominal ones.
  • Confirm the §4 RTO/RPO budgets hold under simultaneous, compounding failures, not just isolated single-fault injections.
  • Produce forensic bundles from every injected failure, closing the operational loop back to §19.

21.2 Detailed Implementation Steps

  • replication-chaos-suite/src/fault_injection.rs: a fault-injection API layered on the replication-test-harness simulator (§12) — packet loss, corruption, clock skew, and region isolation as composable, seeded, reproducible fault schedules (P1 extended to chaos testing itself: a chaos run must replay identically given the same seed).
  • replication-chaos-suite/src/scenarios.rs: named scenarios combining fault primitives — simultaneous region loss, repeated failover within one RTO window, WAL corruption during an active snapshot transfer — each mapped to an explicit acceptance threshold from §4.
  • Packet-loss and corruption injectors hook the transport (§14) and WAL (§13) layers directly rather than a network-namespace-level tc netem, so injection is deterministic and simulator- reproducible rather than best-effort.
  • Region-isolation tests exercise the membership layer's (§16) quorum-fragmentation handling under a full region-to-region partition, not just a single-peer liveness timeout.
  • Scheduler-overload tests push inflight quotas (§15) past the admission-control threshold deliberately, confirming graceful degradation rather than cascading failure.
  • Replay-interruption scenarios kill the replay worker pool (§18) mid-transaction at randomized points, confirming the torn-transaction recovery path (§18.6) holds under fuzzed timing, not just the one fixed fixture.
  • Every scenario run emits a forensic bundle: the fault schedule, the simulator seed, all emitted metrics/spans/logs for the run, and the resulting pass/fail against the scenario's §4-derived threshold — replayable offline without live cluster access.

21.3 Deliverable

An automated chaos-validation suite gating CI/CD (ADR-14) that runs the full scenario library on every release candidate and blocks promotion on any RTO/RPO or invariant violation.

21.4 Acceptance Criteria

  • Recovery SLOs achieved: RTO < 5 min and RPO < 5 s (§4) hold across all scenarios in fixtures/chaos/* at the 99th percentile over 100 runs per scenario.
  • No unrecoverable divergence: zero replay_hash_mismatch_total (§7 I7) increments across the entire scenario library.
  • Forensic bundle completeness: 100% of scenario runs produce a bundle sufficient to reconstruct the failure timeline without live cluster access (verified by a held-out reviewer replay).

21.5 Conformance Fixtures

  • fixtures/chaos/network_partition.yaml — full region-to-region partition scenario definition.
  • fixtures/chaos/corrupted_wal.yaml — WAL corruption injected mid-snapshot-transfer.
  • fixtures/chaos/repeated_failover.yaml — three failovers within one RTO window on the same region, testing epoch-bump churn (§16) under stress.
  • fixtures/chaos/replay_kill_mid_transaction.yaml — randomized-offset kill during transaction apply, seeded for reproducibility.

21.6 Pitfalls

  • Unrealistic chaos profiles. Manifestation: chaos suite passes but production incidents still surface novel failure modes. Root cause: fault schedules calibrated to convenient failure shapes instead of observed incident shapes (Beyer et al.'s postmortem-driven calibration, applied here). Recovery: feed real incident postmortems back into new named scenarios (§21.2), not just synthetic combinatorics.
  • Nondeterministic failure reproduction. Manifestation: a chaos-found bug cannot be reproduced on a second run. Root cause: fault injection using wall-clock timing instead of the simulator's deterministic seed and virtual clock. Recovery: audit every injector for a hidden real-time dependency, exactly the same audit discipline as §13.6's replay-drift pitfall.

21.7 Performance Concerns

  • Excessive instrumentation overhead during a chaos run can mask the very timing-sensitive bugs the run is meant to find — keep chaos-run instrumentation at the same overhead budget as production (§19.7), not a heavier debug-only mode.

21.8 Edge Cases

  • Simultaneous loss of two regions exceeding the metadata Raft group's fault tolerance — must degrade to the documented read-only safety mode (§16.9), not an undefined state.
  • Repeated failover exceeding the RTO window — must alert as an RTO-budget violation, not silently extend the effective RTO.

21.9 Failure Analysis

All chaos-suite failures generate replayable forensic bundles (§21.2) by construction — there is no failure mode in this phase that does not produce one, because the bundle generation is part of the scenario harness itself, not a best-effort afterthought. Postmortem guidance: a failing scenario's bundle is attached directly to the release-blocking CI check (§26) for reviewer replay.

21.10 Operational Notes

Integrate chaos tests into CI/CD gating (ADR-14): every release candidate runs the full scenario library before promotion to the canary channel (§25). Metrics: chaos_scenario_pass_rate (gauge, per scenario), chaos_forensic_bundle_size_bytes (histogram). Tracing spans: chaos.scenario_run. Structured-log fields: scenario_name, seed, outcome.

24. Operational Readiness

Metrics strategy: every subsystem's Operational Notes (§12.10–§21.10) register into the replication-observability registry (§19); core cluster-wide dashboards aggregate replication lag, WAL fsync latency, replay throughput, queue depth, snapshot transfer rate, peer RTT, and retransmit rate — the same seven signals an operator checks first in any replication incident.

Tracing strategy: correlation IDs propagate from WAL append (§13) through transport send (§14), replay apply (§18), and acknowledgment aggregation (§3.2 Replication Coordinator), per §6 P4 and §19's implementation. A broken span chain is itself a bug (§19.6 Trace Amplification) worth its own alert, not just a debugging inconvenience.

Alerting philosophy: alerts are categorized correctness (I1–I13 violations, P0 always), durability (fsync/checksum failures, P0), availability (quorum loss, region isolation, P1), latency (§4 budget breaches, P2 unless sustained past 15 minutes then P1), and capacity (queue depth/FD budget approaching ceiling, P2 escalating to P1 near the hard limit). Every P0/P1 alert names the invariant or budget row it violates, never a bare "something is wrong."

Deployment topology: minimum three metadata-plane Raft-group nodes (odd count for majority math), placed across independent failure domains (§11 FailureDomain) — never co-located in one rack or AZ, satisfying the anti-affinity requirement referenced in §16.6's quorum-fragmentation pitfall.

Rolling upgrade strategy: version-skew compatibility matrix (§25) validated in CI (§26) before any release reaches the canary channel (ADR-18); staged canaries run the full chaos scenario library (§21) against a mixed-version cluster before promotion to stable.

25. Compatibility & Versioning

Wire compatibility (§6 P5): new TransportFrame (§11) fields are additive only, with reserved field ranges left explicitly unused for one full minor version to guarantee an old reader safely ignores them; feature negotiation (§16.2 capability exchange) gates any behavior change on the field's presence, never on the peer's advertised version string alone.

Storage compatibility: WalEntry segment headers (§13.10) and SnapshotManifest (§11) each carry an independent format-version field, so a WAL format bump does not force a lockstep snapshot format bump, and vice versa — this decoupling is the direct payoff of ADR-05's schema-evolution rationale.

Semantic versioning:

Version Change Meaning
MAJOR incompatible wire protocol or storage format change; requires a full-cluster coordinated upgrade
MINOR backward-compatible feature addition; supports exactly one version of skew during rolling upgrade (§6 P5)
PATCH bug fixes only, no schema or protocol surface change

Version-skew compatibility matrix: every MINOR release documents which of the prior two MINOR versions it can run alongside during a rolling upgrade window, validated by conformance/wire_compat.yaml (§10) in CI before merge, not discovered in production.

26. Testing & Verification Strategy

Unit testing focuses on parsers (TransportFrame, WalEntry decode), checksums, and replay sequencing in isolation — the layer where a bug is cheapest to catch.

Integration testing spins up multi-region simulated clusters (replication-test-harness, §12) and validates failover, snapshot fallback, and conflict resolution end-to-end against the fixtures named throughout §12–§21.

Differential testing compares replay output across two runtime revisions on the same recorded WAL trace — the direct enforcement mechanism behind §7 I7 and the tool that catches the hidden- nondeterminism pitfalls named in §13.6, §18.6, and §20.6.

Property testing validates ordering invariants (§7 I1, I4) and idempotency (§7 I11) against randomized input generators rather than fixed examples, per ADR-12's rationale over example-only tests.

Fuzzing targets the transport frame parser, the WAL segment decoder, and the snapshot manifest parser (fuzz/fuzz_transport.rs, fuzz/fuzz_wal_decoder.rs, fuzz/fuzz_snapshot_manifest.rs, §10) via cargo-fuzz (ADR-13) — these three are the only parsers that consume untrusted, potentially adversarial bytes directly off the wire or disk.

Chaos testing (§21) injects packet loss, corruption, clock skew, and region isolation through the replication-chaos-suite, gating every release candidate in CI (ADR-14) before canary promotion.

27. Build & Release Engineering

Reproducible builds: pinned toolchain version (rust-toolchain.toml) and Cargo.lock committed, producing byte-identical stripped binaries across clean builds of the same commit (§12.4's acceptance criterion, ADR-14's reproducibility rationale extended here).

Artifact signing: Sigstore keyless signing on every release artifact, with provenance metadata (build environment, commit SHA, builder identity) attached per artifact, gating the canary channel.

SBOM generation: CycloneDX SBOM generated during CI for every release, feeding the dependency- auditing step below and the supply-chain mitigation named in T8 (§22).

Release channels: canary (every merge to main that passes CI and chaos gating), stable (canary soak for a documented minimum window with no P0/P1), LTS (a stable release designated for extended patch-only support, per ADR-18's staged blast-radius rationale).

Dependency auditing: cargo audit and license scanning run in CI on every dependency change; cargo vet (ADR-03) requires an explicit trust decision before an unaudited dependency version enters the build.

29. Scalability Analysis

Horizontal scaling is achieved via region fanout (up to the §4 32-region ceiling), shard/stream partitioning (one StreamId per source-partition-to-region pair, §8.1), and stream isolation (§3.2's actor-per-stream concurrency boundary) — adding regions or partitions adds streams, not contention on any existing stream's state.

Scaling bottlenecks, in the order they are expected to bite: metadata-plane quorum coordination (§16, commit latency grows with Raft-group round-trips, though the group itself stays small independent of region count); snapshot-transfer bandwidth (§17, shared with WAL streaming on the same link, mitigated by the scheduler's shared credit ledger, §15.2); and WAL fsync throughput (§13, the hard floor under any single node regardless of network capacity).

Metadata scaling mitigations: epoch caching at each node avoids a quorum round-trip for every read of the current topology, and compressed topology propagation (delta-encoded region-metadata updates rather than full-state re-broadcast) bounds the metadata-fanout cost named in §16.7 as the region-count-proportional cost driver.

30. Mental Models & First Principles

  • MM1 — Durability is a return value, not a promise. Compressed insight: an ack is only true once the fsync syscall has returned, never before · predicts: any "optimistic ack" shortcut will eventually lose an acknowledged write · bug class without it: acknowledged-but-lost writes on crash · applies in §13.
  • MM2 — Determinism is a property of the whole pipeline, not one function. Compressed insight: one hidden HashMap iteration or wall-clock read anywhere in the replay path breaks replay for the entire system · predicts: replay bugs cluster around collections and time reads · bug class without it: replay-hash mismatches with no obvious single cause · applies in §18.
  • MM3 — Backpressure must be structural, not advisory. Compressed insight: a queue that can grow unboundedly will, under exactly the WAN-stall condition this system exists to survive · predicts: any unbounded buffer becomes the first OOM under load · bug class without it: memory exhaustion during precisely the incident you were trying to ride out · applies in §15.
  • MM4 — An epoch is a fence, not a timestamp. Compressed insight: epochs order topology changes causally, they do not measure wall-clock time · predicts: comparing epochs across regions with clock skew is always safe, comparing timestamps is not · bug class without it: split-brain from timestamp-based leader-election logic · applies in §16.
  • MM5 — A snapshot is atomic or it does not exist. Compressed insight: there is no valid intermediate state between "no snapshot" and "complete, checksum-verified snapshot" · predicts: any partially-visible snapshot state is a bug, never an acceptable transient · bug class without it: restores from a half-written manifest · applies in §17.
  • MM6 — Observability that can block the system it observes is a liability, not a feature. Compressed insight: telemetry must degrade to sampling/dropping under its own backend's failure · predicts: an unbounded trace-export queue becomes a second incident during the first one · bug class without it: an exporter outage cascading into a replication outage · applies in §19.
  • MM7 — Conflict resolution is a data-visible decision, so it must be reproducible, not clever. Compressed insight: a resolver's cleverness is worthless if two replicas can compute different answers for the same input · predicts: any resolver using a non-total-order tiebreak will eventually diverge · bug class without it: silent, undetected replica divergence · applies in §20.
  • MM8 — Chaos testing must be as deterministic as the system it tests. Compressed insight: a chaos run that cannot be replayed from a seed is not a test, it is an anecdote · predicts: "flaky" chaos failures are almost always a hidden real-time dependency in the injector itself · bug class without it: unreproducible incident reports · applies in §21.

32. Back-of-Envelope Capacity Model

  • C1 — Node Throughput Ceiling. 25 Gbps ÷ 8 = 3.125 GB/s raw link capacity; at ~2 KB average frame size, 3.125 GB/s ÷ 2 KB = 1.56M frames/sec, rounded down to the 1.5M ops/sec §4 ceiling for headroom.
  • C2 — Startup Recovery Bound. 1,000,000 WAL entries ÷ 90 s = 11,111 entries/sec required scan rate, well under the WAL subsystem's ~500K entries/sec sequential-scan floor, leaving margin for checksum validation.
  • C3 — Node Memory Budget. 10,000 streams × 4,096 max inflight frames (§4) × 256 B queued-frame header = 10.5 GB queue memory + 16 GB WAL page-cache target + 4 GB scheduler overhead ≈ 30.5 GB, inside the 32 GB §4 ceiling.
  • C4 — Max Concurrent Streams. 65,536 FD budget ÷ 6 FDs per stream (one shared QUIC connection amortized plus ~5 file/socket handles) = 10,922, rounded down to the 10,000 §4 ceiling for admission-control headroom.
  • C5 — Write Amplification. 1.0x local WAL + 1.0x replicated remote WAL + 0.5x average snapshot-delta overhead during resync = 2.5x baseline, + 1.0x transient checksum-verification buffer during compaction = 3.5x, matching the §4 ceiling exactly.
  • C6 — Scheduler Credit Ledger Size. 10,000 streams × 128 B per SchedulerQuota (§11) = 1.28 MB, negligible against the 32 GB §4 ceiling, confirming the ledger is never the scaling bottleneck named in §29.
  • C7 — Snapshot Restore Time at Scale. 500 GB snapshot ÷ 1 GB/sec restore throughput (§4) = 500 s ≈ 8.3 min per full-state resync — inside the 5-minute RTO budget only when paired with incremental WAL catch-up (§17.2), never as a cold full restore alone.

34. Alternative Architectures (Roads Not Taken)

Alt A — Gossip-Based Membership (No Metadata Raft Plane)

   Node A <---gossip---> Node B
     ^                     ^
     |     gossip mesh      |
     v                     v
   Node C <---gossip---> Node D
   (no single authoritative epoch source;
    each node holds a locally-converged view)

Regime where it wins: very large node counts (thousands) where a small Raft group's commit latency (§16.7) would itself become the bottleneck, and where topology changes are rare enough that eventual-consistency convergence time is acceptable. Real system: Apache Cassandra's gossip-based ring membership. Why this blueprint rejected it: §7 I2 (Epoch Consistency) requires a single authoritative, strictly-increasing epoch source to prevent split-brain (§16.6); a gossip mesh gives only eventually-consistent membership views, which is exactly the property this system's fencing design (§7 I8) is built to avoid depending on.

Alt B — Synchronous Cross-Region Consensus (Spanner-Style Data Plane)

Client -> [Region A leader] --Paxos--> [Region B] --Paxos--> [Region C]
              (commit blocks on cross-region round trip, every write)

Regime where it wins: applications that cannot tolerate any replication lag or conflict semantics and can absorb per-write cross-region latency (hundreds of ms) as a business cost. Real system: Google Spanner (Corbett et al. 2012, §5, §31). Why this blueprint rejected it: the §4 p50 apply- latency budget (< 10 ms) is incompatible with a synchronous cross-region commit at 350 ms RTT; this system instead accepts bounded async lag (§4, < 250 ms) with a conflict-resolution framework (§20) for the active-active case, trading Spanner's zero-conflict guarantee for a much lower latency floor.

Alt C — Leaderless Quorum Replication (Dynamo-Style)

        Client write
       /     |      \
      v      v       v
  Replica1 Replica2 Replica3   (any W of N acks = success,
      \      |      /           no single ordered log)
       vector-clock reconciliation on read

Regime where it wins: workloads that value write availability over strict ordering, and where application-level conflict reconciliation on read is acceptable. Real system: Amazon Dynamo (DeCandia et al. 2007, §5, §31). Why this blueprint rejected it: §7 I1 (WAL Ordering) and the whole deterministic-replay design (§18, P1) require a single ordered log per stream; a leaderless quorum model has no such log, which would make §26's differential-testing methodology inapplicable and remove the deterministic-replay guarantee this blueprint is built around.

36. Glossary

  • WAL — write-ahead log; the durable append-only record every mutation passes through before visibility (§6 P9).
  • Epoch — monotonically increasing topology generation identifier (§7 I2, §11 EpochId).
  • Replay Drift — divergence between two replay runs of identical input; a §7 I7 violation.
  • Snapshot Manifest — immutable metadata describing a checkpoint's chunks and checksums (§11).
  • Inflight Window — the bounded outstanding-frame budget a stream is permitted (§11 SchedulerQuota).
  • Replica Watermark — the highest sequence a given replica has acknowledged (§11 AckWatermark).
  • Failover FSM — the state machine driving coordinator failover decisions (§3.2).
  • Stream Gap — a missing WalSequence detected during replay validation (§7 I1).
  • Tombstone — a first-class deletion marker used in conflict resolution (§20.2).
  • Quorum — the minimum acknowledgment set required to advance the ack watermark (§7 I4).
  • Backpressure — upstream rate-limiting signal propagated from a saturated downstream queue (§6 P2).
  • Split Brain — two coordinators simultaneously believing they hold write authority for the same stream; prevented by §7 I2/I8.
  • Replay Cursor — the per-stream marker of replay progression (§11 ReplicationCursor).
  • Checkpoint — a transactionally consistent snapshot instant (§7 I5).
  • Segment Rotation — WAL file rollover at a configured size threshold (§13.2).
  • Idempotency — the property that re-applying an already-applied entry is a no-op (§7 I11).
  • Corruption Quarantine — isolating a damaged WAL segment or snapshot chunk from further use (§13.9).
  • Capability Negotiation — peer feature/version discovery at connection registration (§16.2).
  • Degraded Mode — a stream state with reduced throughput but preserved correctness (§8.3).
  • Retry Amplification — a failure mode where retry traffic itself saturates a link (§15.6).
  • Fencing Token — a value invalidated on epoch bump that prevents a stale writer from acting (§7 I8).
  • Vector Clock — logical causality metadata used for conflict detection (§11 ConflictRecord, Mattern 1989).
  • ISR — in-sync replica set, the Kafka concept informing this system's lag-handling design (§5, §13).
  • RPO — recovery point objective, the maximum acceptable data loss window (§4).
  • RTO — recovery time objective, the maximum acceptable outage duration (§4).
  • Credit-Based Flow Control — a backpressure mechanism where senders spend explicitly granted credit rather than reacting to loss (§15.2).
  • Head-of-Line Blocking — one slow stream stalling unrelated streams sharing a transport connection (§14.6).
  • Zero-Copy Buffer — a payload-handling technique avoiding a full-frame memory copy per send (§14.2).
  • Causal Domination — the property that a resolved vector clock must be greater than or equal to both of its inputs (§20.2).
  • Forensic Bundle — the fault schedule, seed, and telemetry captured from one chaos-suite run (§21.2).
  • Admission Control — rejecting new work at a queue boundary once capacity is reached (§7 I6).
  • Anti-Affinity — placement policy preventing quorum members from sharing a failure domain (§24).
  • Version Skew — the state of two adjacent MINOR versions running simultaneously during a rolling upgrade (§25).
  • Rename-on-Complete — an atomic-write pattern using filesystem rename to guarantee no partial file is ever visible (§17.2).
  • Chunked Transfer — splitting a snapshot into independently checksummed, resumable segments (§17.2).
  • Peer Strike Counter — a per-peer counter of protocol violations gating disconnection (§14.6, §6 P10).
  • Correlation ID — the identifier carried across every span in one logical mutation's pipeline (§19.2).
  • Cardinality Budget — a cap on the number of unique label combinations a metric may emit (§19.6).
  • Deterministic Simulator — the virtual-clock test harness every invariant assertion runs against (§7 closing paragraph, §12).
  • Differential Testing — comparing replay output across runtime revisions on the same trace (§26).
  • Canary Channel — the first release channel a build reaches after CI and chaos gating (ADR-18, §27).
