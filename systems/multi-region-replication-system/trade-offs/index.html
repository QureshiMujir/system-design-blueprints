Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Gossip-Based Membership (No Metadata Raft Plane)

   Node A <---gossip---> Node B
     ^                     ^
     |     gossip mesh      |
     v                     v
   Node C <---gossip---> Node D
   (no single authoritative epoch source;
    each node holds a locally-converged view)

Regime where it wins: very large node counts (thousands) where a small Raft group's commit latency (§16.7) would itself become the bottleneck, and where topology changes are rare enough that eventual-consistency convergence time is acceptable. Real system: Apache Cassandra's gossip-based ring membership. Why this blueprint rejected it: §7 I2 (Epoch Consistency) requires a single authoritative, strictly-increasing epoch source to prevent split-brain (§16.6); a gossip mesh gives only eventually-consistent membership views, which is exactly the property this system's fencing design (§7 I8) is built to avoid depending on.

Alt B — Synchronous Cross-Region Consensus (Spanner-Style Data Plane)

Client -> [Region A leader] --Paxos--> [Region B] --Paxos--> [Region C]
              (commit blocks on cross-region round trip, every write)

Regime where it wins: applications that cannot tolerate any replication lag or conflict semantics and can absorb per-write cross-region latency (hundreds of ms) as a business cost. Real system: Google Spanner (Corbett et al. 2012, §5, §31). Why this blueprint rejected it: the §4 p50 apply- latency budget (< 10 ms) is incompatible with a synchronous cross-region commit at 350 ms RTT; this system instead accepts bounded async lag (§4, < 250 ms) with a conflict-resolution framework (§20) for the active-active case, trading Spanner's zero-conflict guarantee for a much lower latency floor.

Alt C — Leaderless Quorum Replication (Dynamo-Style)

        Client write
       /     |      \
      v      v       v
  Replica1 Replica2 Replica3   (any W of N acks = success,
      \      |      /           no single ordered log)
       vector-clock reconciliation on read

Regime where it wins: workloads that value write availability over strict ordering, and where application-level conflict reconciliation on read is acceptable. Real system: Amazon Dynamo (DeCandia et al. 2007, §5, §31). Why this blueprint rejected it: §7 I1 (WAL Ordering) and the whole deterministic-replay design (§18, P1) require a single ordered log per stream; a leaderless quorum model has no such log, which would make §26's differential-testing methodology inapplicable and remove the deterministic-replay guarantee this blueprint is built around.
