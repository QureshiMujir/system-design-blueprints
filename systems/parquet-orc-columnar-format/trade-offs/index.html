Decisions (§9) · 25 ADRs

A01

Implementation language

Chosen

Rust (stable channel)

Rejected

Java (parquet-mr), C++ (Arrow), Go

When the rejected choice is right

Java wins when the team already owns a JVM-based data platform and JNI integration overhead dominates; C++ wins for SIMD-heavy paths (Arrow Flight RPC) where Rust compile times and ecosystem maturity lag

Why: Safe slice indexing prevents OOB UB on hostile footers; newtypes prevent offset/value conflation; cargo-fuzz native; no GC pauses in scan loops

A02

Build system

Chosen

Cargo (workspace)

Rejected

Bazel, Buck, CMake

When the rejected choice is right

Bazel wins when the workspace is polyglot (Rust + Java oracle wrapper + Python test harness) and hermetic reproducibility across languages is a CI requirement

Why: Parquet-codec project is Rust-only; Cargo workspace manages 5 crates; Bazel overhead unwarranted

A03

Thrift decoding

Chosen

Hand-rolled compact-protocol decoder in shared::thrift_compact

Rejected

apache-thrift generated Rust, prost

When the rejected choice is right

Generated Thrift wins for multi-service RPC (many message types, versioned schemas, server + client both Rust) where hand-rolling 50+ structs is unmaintainable

Why: Generated Thrift adds build complexity + schema coupling; hand-rolled is 200 LOC and forward-compatible (skip unknown fields)

A04

Bit-packing / RLE

Chosen

Custom bit_reader/bit_writer in shared

Rejected

bitpacking crate, bitvec

When the rejected choice is right

bitpacking crate wins when the project is a general-purpose integer compression library that must handle multiple bit-ordering conventions and wants AVX-512 SIMD without hand-writing intrinsics

Why: Must control exact LSB-first layout matching Parquet spec; third-party crates have different bit ordering; performance-critical → inline

A05

Compression codec integration

Chosen

Trait abstraction Codec: compress + decompress; implementations from #397 project

Rejected

direct crate deps (snap, zstd, flate2, lz4)

When the rejected choice is right

Direct crate deps win for a standalone single-crate library that has no portfolio dependency and wants minimal build-graph complexity

Why: Avoids duplicate compression implementations across portfolio; #397 codec project is the authoritative implementation

A06

Async I/O model

Chosen

Synchronous Read + Seek / Write traits; async wrapper is caller responsibility

Rejected

tokio async, io_uring direct

When the rejected choice is right

Async-native wins when reading from object storage (S3/GCS) where network latency dominates and blocking a thread per row-group read burns the thread pool; io_uring wins on Linux for ultra-low-latency NVMe scans at ≥ 10 Gbit/s

Why: Codec is compute-bound, not I/O-bound in the hot path; async entanglement complicates embedding; callers wrap with spawn_blocking

A07

Protobuf decode (ORC)

Chosen

prost crate for ORC footer/postscript Protobuf

Rejected

hand-rolled, protobuf crate

When the rejected choice is right

Hand-rolled proto wins for a constrained no_std embedded environment where neither prost nor protobuf can be linked

Why: ORC footers use proto2; prost is lightweight, no runtime reflection; only ORC uses proto — justified for that crate

A08

CRC-32C

Chosen

crc32c crate (hardware-accelerated SSE4.2/ARM CRC)

Rejected

software fallback, crc crate

When the rejected choice is right

Software fallback wins on targets without SSE4.2/ARM CRC extension (e.g., RISC-V, WASM) where the hardware crate does not compile or silently falls back slower than a tuned software path

Why: DataPageV2 CRC field; hardware ~4 GB/s; software ~400 MB/s; justified for hot path

A09

Property-based testing

Chosen

proptest

Rejected

quickcheck, bolero

When the rejected choice is right

bolero wins when coverage-guided property testing (structure-aware fuzzing integrated with libFuzzer) is the primary mode and the team wants a single harness for both unit properties and fuzz

Why: proptest has shrinking + structured strategy support; well-maintained; encodes distribution invariants for encoding round-trips

Fuzzing

honggfuzz wins on targets where persistent-mode Linux perf hardware counters give sharper coverage feedback than SanitizerCoverage (e.g., very tight inner loops like RLEv2 decode)

A15

Conformance test corpus

Chosen

Generated from parquet-mr + Arrow Rust + manual edge cases

Rejected

Spark-generated files only

When the rejected choice is right

Spark-only corpus wins in a Spark-centric data platform where the only consumer is Spark and testing non-Spark edge cases is out of scope and too expensive to maintain

Why: Broader coverage; parquet-mr is authoritative for encodings; Arrow for statistics/indexes; manual for edge cases

A16

Row-group parallelism

Chosen

External (caller partitions row-groups across threads)

Rejected

internal rayon, internal thread pool

When the rejected choice is right

Internal rayon wins for a binary tool (not a library) where the caller never manages parallelism and a single scan(file, pred, proj) API must saturate available cores automatically

Why: No internal thread spawning (P9 design principle); callers use rayon::par_iter over row-group list

A17

Dictionary cache

Chosen

Per-column-chunk DictPage cached in ColumnChunkReader; evicted at column-chunk close

Rejected

global LRU cache

When the rejected choice is right

Global LRU wins for a server process reading many files simultaneously where the same 1,000-entry string dictionary repeats across row groups and cross-chunk dict sharing yields measurable memory savings

Why: LRU adds contention + complexity; per-chunk dict is lifetime-bound; simpler, correct, bounded

A18

Schema representation

Chosen

SchemaNode enum tree with max_rep/max_def precomputed

Rejected

flat SchemaElement list from Thrift

When the rejected choice is right

Flat list wins for a tiny embedded reader that must minimize code size and only supports flat (non-nested) schemas, avoiding the recursive enum machinery

Why: Flat Thrift schema requires DFS reconstruction at decode time; precomputed tree is faster and encodes Dremel invariants statically

A19

Statistics encoding

Chosen

Native Rust types + MinMaxStats<T> generic; binary min/max for BYTE_ARRAY

Rejected

raw Thrift Statistics bytes

When the rejected choice is right

Raw Thrift bytes win for a pass-through proxy that reads statistics from one file and re-emits them into another without interpreting them — typed decode + re-encode introduces unnecessary conversion risk

Why: Typed generics allow compiler-verified comparisons; avoids endian bugs in raw bytes

A20

Bloom filter hash

Chosen

XXHash-64 (double-hashing per Kirsch-Mitzenmacher)

Rejected

MurmurHash3, FNV

When the rejected choice is right

MurmurHash3 wins for a standalone Bloom filter library that prioritizes cross-language interoperability where XXHash is not available or consistent across SDKs

Why: Parquet spec mandates XXHash; double-hashing avoids multiple hash functions; xxhash-rust crate

A21

PageIndex (ColumnIndex/OffsetIndex)

Chosen

Parsed eagerly at open if present; stored in RowGroupReader

Rejected

lazy per-page

When the rejected choice is right

Lazy wins for streaming sources (no seek) or very wide tables (10k columns) where eager parse of all column indexes at open time exceeds the per-query memory budget

Why: Footer-adjacent; size ≪ data; eager parse enables predicate evaluation before any seek

A22

ORC vs Parquet separation

Chosen

Separate crates (orc_codec vs parquet_core); shared only via shared::

Rejected

unified crate with feature flags

When the rejected choice is right

Unified crate with feature flags wins for an embedded library with strict binary-size constraints where two crates double the metadata and the end user needs only one format

Why: Format models differ fundamentally (stripe vs row-group; Protobuf vs Thrift); separate crates with shared primitives is cleanest

Alternative Architectures (Roads Not Taken)

Fundamentally different ways to build a durable columnar codec for the same goal. Each: sketch, winning regime, the real system embodying it, why this blueprint rejected it.

A1 — Row-oriented page layout with a column metadata index. Values are stored row-major in pages; a side index maps each column to its byte offsets.

┌─────────────────────────────────────────────────────────┐
│  File Header                                            │
├─────────────────────────────────────────────────────────┤
│  Row Page 0: [col0_val, col1_val, col2_val, ...]        │
│  Row Page 1: [col0_val, col1_val, col2_val, ...]        │
│  ...                                                    │
├─────────────────────────────────────────────────────────┤
│  Column Offset Index: col_id → list of page offsets     │
│  Footer: schema + page index                            │
└─────────────────────────────────────────────────────────┘
  • Wins: write-heavy workloads with high row-update frequency (OLTP-style appends where every column of a row is written together) — row layout removes the column-fan-out write amplification of flushing 100 column chunks per row group.
  • Real system: PostgreSQL heap file format (row-oriented pages) with a separate BRIN index for column min/max metadata.
  • Rejected because: analytical queries project 2–5 of 100 columns; row layout reads all 100 columns' bytes to materialize 5 → 20× I/O amplification, versus 2–5% for columnar projection. P3 (Abadi et al., Column-Stores vs Row-Stores) is the authoritative quantification; the blueprint targets an OLAP-grade format, for which row layout is the wrong physical design.

A2 — Log-structured columnar format (LSM-style). Columns are written as immutable per-column SSTables at L0 and merged into sorted, larger SSTables by background compaction.

┌─────────────────────────────────────────────────────────┐
│  L0 SSTables (recent, uncompacted, small)               │
│    col_a_0.col, col_b_0.col, col_c_0.col               │
│  L1 SSTables (compacted, sorted within column)          │
│    col_a_1.col (sorted), col_b_1.col, ...               │
│  Bloom filter per SSTable + sparse index                 │
│  Manifest JSON: active SSTables per column              │
└─────────────────────────────────────────────────────────┘
Reads: merge-scan across levels; latest version wins.
Writes: append to L0; background compaction to L1+.
  • Wins: streaming ingestion with frequent small writes (IoT, CDC) where immutable append-only row groups would produce thousands of tiny files; LSM amortizes write cost through compaction and offers point-delete/upsert without rewriting whole row groups.
  • Real system: Apache Kudu (columnar LSM storage engine); Cassandra SSTables (row-oriented LSM, same write path).
  • Rejected because: LSM requires a compaction daemon, a manifest, multi-version concurrency, and a merge-read path — all well beyond "bytes-on-disk codec," and the blueprint explicitly non-goals the table-format and compaction layers (#214 Iceberg/Delta). A Parquet file from this codec managed by Iceberg achieves the same streaming-ingest + ACID result without embedding compaction in the codec.

A3 — Arrow IPC file format as the unified columnar format. The in-memory Arrow layout is written verbatim to disk; reads memory-map and zero-copy slice into buffers with no decode step.

┌──────────────────────────────────────────────────────────┐
│  Arrow IPC Magic: ARROW1                                 │
│  Schema message (FlatBuffers): field types + metadata    │
│  RecordBatch 0: buffers (validity, offsets, data)        │
│  RecordBatch 1: ...                                      │
│  Footer (FlatBuffers): RecordBatch offsets + schema; EOS │
└──────────────────────────────────────────────────────────┘
R/W memory-mapped; in-memory layout IS the file layout.
  • Wins: in-process or same-host columnar exchange at memory speed (shuffle between co-located processes, Python↔Rust IPC, shared-memory zero-copy); throughput is bounded by memcpy (~50 GB/s), not codec speed, because there is no encode/decode.
  • Real system: Apache Arrow IPC file format (.arrow); Apache Arrow Flight (Arrow IPC over gRPC).
  • Rejected because: Arrow IPC trades compression for zero-copy — a 100 GB Parquet file with ZSTD + DELTA_BINARY_PACKED is ~10 GB on disk, the Arrow IPC equivalent ~100 GB. For durable object-store lake storage that 10× drives storage cost and transfer time directly; the blueprint targets a bytes-on-disk codec requiring compression. Arrow IPC is the complementary in-memory layer (#395), not a substitute for Parquet at rest.

A4 — Avro with column reordering (row-columnar hybrid). Avro container blocks carry rows, with fields reordered at write time so each column's values are contiguous within a block.

┌──────────────────────────────────────────────────────────┐
│  Avro file header: schema (JSON), codec, sync marker     │
│  Block 0: N rows, Avro binary                            │
│    (reordered: all col0 values first, then col1, ...)    │
│  Sync marker; Block 1: ...                               │
│  No footer; schema in header only                        │
└──────────────────────────────────────────────────────────┘
Column reordering is a write-time convention, not a spec feature.
  • Wins: schema-registry-driven pipelines (Confluent Schema Registry, event streaming) where every producer/consumer is already Avro and adding Parquet writers means a second SDK; Avro's schema-in-header simplifies streaming deserialization without a footer read, and for narrow schemas (3–5 fields) the simplicity beats Parquet's optimization overhead.
  • Real system: Apache Avro container files (heavy in Kafka pipelines); Confluent Platform Avro serializer.
  • Rejected because: Avro has no native columnar storage — reordering is an unofficial convention readers cannot exploit without custom logic — and no statistics, page index, Bloom filter, or file-level predicate pushdown, so analytics over large files degrade to full scans. The blueprint targets OLAP I/O efficiency; Avro is the right format for streaming event encoding, not analytical storage.
