Back-of-Envelope Capacity Model

Numbers an expert computes from §4 (System Constraints) before designing; each is derived and names its §4 input. Variables: T = §4 decode throughput (PLAIN INT64, uncompressed) ≥ 2 GB/s/thread; T_z = §4 ZSTD L1 + RLE_DICTIONARY ≥ 400 MB/s/thread; RG = §4 row-group size = 128 MB uncompressed; P = §4 page buffer = 1 MB uncompressed; M = §4 memory per open reader ≤ 32 MB; F = §4 footer parse latency ≤ 2 ms / 1 MB footer.

  • C1 — Single-thread scan throughput (PLAIN INT64, uncompressed). Input: §4 T (≥ 2 GB/s) + INT64 width 8 B. rows/s = T / bytes_per_value = 2 GB/s ÷ 8 B = 250 M rows/s. A 1 B-row INT64 column takes ≈ 4 s on one thread; 8 threads (caller-partitioned, ADR-A16) → ≈ 0.5 s.
  • C2 — Single-thread scan throughput (ZSTD + RLE_DICTIONARY, INT64). Input: §4 T_z (≥ 400 MB/s) + 8 B width. rows/s = T_z ÷ 8 B = 400 MB/s ÷ 8 = 50 M rows/s. Compression is 5× slower per row than uncompressed → the codec, not the decode loop, is the bottleneck on compressed files.
  • C3 — Row groups per file for a 1 TB dataset. Input: §4 RG (128 MB). num_rg = file_size ÷ RG = 1 TB ÷ 128 MB = 8,192 row groups. Footer grows O(num_rg × num_columns); for 100 columns: 8,192 × 100 × ~200 B/column-chunk-metadata ≈ 164 MB (pathological — partition files first to keep the footer < 10 MB).
  • C4 — Footer parse budget for 10k row groups × 100 columns. Input: §4 F (≤ 2 ms / 1 MB). footer_bytes = 10,000 × 100 × 200 B = 200 MB; at a Thrift-compact field-ID decode rate ≈ 500 MB/s → 200 MB ÷ 500 MB/s = 400 ms, far over the 2 ms target. Conclusion: > ~500 row groups at 100 columns needs split-file partitioning; §4's 1 MB/2 ms budget is calibrated for ≤ ~50 row groups × 100 columns.
  • C5 — Memory for footer + schema at open. Input: §4 M (≤ 32 MB) + §4 max columns (1,000). schema_nodes ≈ 1,000 × 512 B = 512 KB; row_group_metadata ≈ num_rg × num_columns × 80 B; for 100 RG × 100 col = 800 KB. Total ≈ 512 KB + 800 KB + PageIndex ≈ 5 MB — well within the 32 MB M budget.
  • C6 — PageIndex memory per row group (100 columns × 128 pages). Input: §4 M + §4 page buffer P (1 MB → ~128 pages/128 MB RG). per_page_entry ≈ 2×min_max + 8 B null_count + 12 B PageLocation ≈ 60 B; 100 col × 128 pages × 60 B = 768 KB/RG; 10 row groups loaded → 7.68 MB, fits the 32 MB M budget.
  • C7 — Bloom filter memory budget. Input: §4 Bloom max size (128 KB/column chunk) + §4 FPP (1%). num_bytes = ceil(−n × ln(0.01) ÷ ln(2)²) = ceil(n × 9.585 bits ÷ 8). For n = 1 M (§4 dict cardinality threshold): ≈ 1.2 MB — exceeds the 128 KB cap, so Bloom is capped, raising FPP on high-cardinality columns; 100 columns × 128 KB = 12.8 MB worst case.
  • C8 — Effective FPP at the 128 KB cap for n = 1 M entries. Input: §4 Bloom max size (m = 128 KB × 8 = 1,048,576 bits) + 8 probes. FPP = (1 − e^(−k·n/m))^k; k·n/m = 8 × 10⁶ ÷ 1,048,576 ≈ 7.63; FPP = (1 − e^{−7.63})^8 ≈ 99.6% — near-useless. Conclusion: Bloom is effective only at ≤ ~100 K distinct values per row group; the design disables it for high-cardinality columns.
  • C9 — I/O savings from predicate pushdown at 1% selectivity. Input: §4 row-group skip ratio (≥ 95%) + §4 page skip ratio (≥ 80%). bytes_read = file_size × (1 − skip) = 1 TB × 0.05 = 50 GB (20× reduction vs full scan); add page-level skip on a sorted column: 50 GB × 0.20 = 10 GB effective I/O for a 1% point query.
  • C10 — Dict cardinality threshold vs page size. Input: §4 dict cardinality fallback (≤ 1 M or ≥ 50% of page) + §4 page buffer P (1 MB). At 1 M BYTE_ARRAY entries × (4 B length + 20 B) = 24 MB dict page — 24× over P. Conclusion: the threshold must enforce a byte cap too; the "≥ 50% of page" rule fires at P ÷ avg_value_size = 1 MB ÷ 24 B ≈ 43 K distinct 20-byte values, long before the 1 M entry count.
  • C11 — CRC-32C verification headroom. Input: §4 CRC rate (≈ 4 GB/s hardware) + §4 T (2 GB/s). crc_fraction_of_decode = T ÷ crc_rate = 2 GB/s ÷ 4 GB/s = 0.5 → CRC adds ≤ 50% to PLAIN decode time; on the ZSTD path T_z ÷ crc_rate = 400 MB/s ÷ 4 GB/s = 0.1 → ≤ 10% overhead (negligible).
  • C12 — File-descriptor pressure. Input: §4 FD usage (1 FD/open file, ADR-A06). A file-parallel scan over 1,000 Parquet files holds 1,000 FDs; Linux default ulimit -n = 1,024. Implication: operators must raise ulimit -n to ≥ 2 × num_files; no internal multi-FD pre-read is used (§4 thread model).
