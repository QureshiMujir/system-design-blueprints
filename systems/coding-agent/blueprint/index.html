Project Number: 25

Project Name: Coding Agent

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a from-scratch autonomous coding agent in Python: an LLM-driven loop that ingests a task specification and a repository, retrieves and budgets relevant repository context, proposes structured edits and shell commands through a schema-validated tool-calling layer, executes untrusted repository code and agent-authored commands inside a sandbox, verifies the result against the repository's own tests and linters as the correctness oracle, and emits a reviewable patch or pull request. The system is a concrete, narrow agent: one task shape (resolve a described repository issue with a verified diff), one effectiveness metric (does the change pass tests it did not write), and one hard safety property (nothing untrusted executes outside an isolated sandbox). Every subsystem — retrieval, editing, verification, sandboxing — exists to serve that one loop reliably at bounded cost and turns.

Phase-0 deliverable (numbered package list):

  1. agent-core — CLI entry point, task-spec parser, agent-loop state machine skeleton.
  2. agent-model — ModelClient provider interface, request/response types, recorded-response replay transport for deterministic tests.
  3. agent-trajectory — trajectory recorder/reader, JSONL schema, replay harness.
  4. agent-ci — CI pipeline running the replay-gate test suite (no live model calls).
  5. agent-types — the core schema and type module (TaskSpec, RepoSnapshot, AgentState, ...).

Boundaries — provides: the agent loop, tool layer, retrieval/budgeter, sandbox executor, structured editor, verification runner, trajectory recorder, cost accountant, patch/PR emitter, evaluation harness. Delegates: model inference to an external provider behind the ModelClient interface (ADR-02) — this system never trains or hosts a model; container primitives (namespaces, cgroups, the OCI runtime) to the host OS and an OCI-compliant runtime (ADR-11) — this system never reimplements kernel isolation. Does NOT provide: a general multi-agent orchestration substrate, an IDE, a model training pipeline, or a human-collaboration UI beyond patch/PR review artifacts.

Non-goals: this is not a general multi-agent framework. The sibling project, rank 24 (Agentic-Framework), owns cross-domain multi-agent orchestration, planner/coder/reviewer role decomposition, and generic tool-calling substrates usable outside coding. This blueprint is deliberately the concrete, coding-specific instance: its three load-bearing concerns — repository context selection under a token budget, sandboxed execution of untrusted code, and test-driven verification as the correctness oracle — are specific to "reads a repo, edits a repo, is graded by the repo's own tests," not generic agency. Where Agentic-Framework would add a fourth "reviewer" agent role, this project instead adds a fourth pipeline stage (verification) that is mechanical, not another LLM call. It is not an IDE (no live editor UI, no keystroke-level interaction); later phases can host it behind one, but that hosting is out of scope. It does not train, fine-tune, or distill a model — model capability is treated as an exogenous, versioned, swappable input (ADR-02, section 27).

Deployment model: three faces over one core. (a) CLI — agent run <task-spec> for interactive or scripted single-task use. (b) CI job — invoked from a pipeline on issue assignment or a scheduled backlog sweep, headless, budget-capped. (c) Service — a queue- fed worker pool for fleet-scale evaluation or backlog processing, sharing the same core loop and sandbox pool (section 26 deployment topology).

Users/operators: application developers triaging a backlog, SRE/on-call engineers wanting a supervised auto-triage of low-risk bugs, and ML/agents researchers running benchmark evaluation. Operators are distinct from users: an operator manages sandbox capacity, cost ceilings, model pinning and the deferred-feature backlog (section 37); a user submits tasks and reviews patches.

What later phases unlock: Phase 0 (section 12) unlocks deterministic CI for everything after it. Phase 4's state machine (section 16) unlocks Phase 5's sandbox integration having a place to plug into. Phase 7's verification loop (section 19) unlocks Phase 8's reflection (section 20), which is meaningless without a trustworthy pass/fail signal. Phase 9's patch emission (section 21) unlocks Phase 11's benchmark evaluation (section 23), since eval scoring needs a real diff artifact, not a chat transcript.

Language: Python 3.11+, locked (ADR-01). Rationale: mature LLM-provider SDKs, tree_sitter bindings, first-class subprocess/os primitives for the sandbox boundary, and the overwhelming majority of reference implementations studied in section 5 (SWE-agent, OpenHands, Aider) are Python, easing differential testing (section 28) and literature transfer. Rejected: TypeScript/Node — stronger terminal-UI ecosystem, weaker systems-level process/sandbox primitives and weaker tree-sitter/ML tooling maturity for this domain; Rust — superior for a latency-critical single-binary sandbox daemon but slows iteration on the agent-loop and prompt-engineering surface where this project's risk is concentrated; Go — strong concurrency primitives but a shallower LLM-tooling and tree-sitter-grammar ecosystem than Python as of the papers and reference implementations in section 5.

Prerequisites: working knowledge of LLM tool-calling APIs, POSIX process/signal semantics, container/namespace isolation fundamentals, Git plumbing, and JSON Schema. Recommended prior reading: section 5 in full before starting Phase 0.

Timeline: 12 phases, section 12 through section 23, sequenced 0–11, targeting roughly one phase per 1–2 weeks for a small team (3–4 engineers), 6 months end to end including the Phase 11 benchmark evaluation pass. IDE hosting, browser/computer-use tool access, voice input, team-shared sessions, and a plugin marketplace are explicitly out of scope for this timeline: PhaseDeferred("post-launch Phase 12 — IDE and surface expansion"). Full multi- repository/cross-service context assembly is deferred: PhaseDeferred("post-launch Phase 13 — cross-repository context"). Live LSP process integration (as opposed to static tree-sitter symbol indexing) is deferred: PhaseDeferred("section 14 — Phase 2 retrieval, LSP upgrade path"). All deferrals are registered with an un-defer trigger in section 37.

2. Why Build This

Keywords: agent loop; state machine; tool calling; JSON Schema validation; effect classification; sandboxed execution; OCI runtime; repository indexing; tree-sitter symbols; lexical and embedding retrieval; token-budget arithmetic; context-window management; history compaction; structured editing; stale-precondition detection; patch/diff generation; test- suite-as-oracle; flaky-test handling; reflection and retry; trajectory recording; deterministic replay; cost accounting; prompt-injection defense; trust-boundary design; benchmark evaluation (SWE-bench); PR emission; CI/CD for agentic systems.

Building this teaches what "the model is smart enough" cannot buy: the systems engineering that makes an LLM's fallible outputs survive contact with a real filesystem, a real shell, and a real test suite. It forces concrete answers to questions generic chatbot work never raises — what happens when the model's edit target no longer exists, when a shell command never returns, when the repository itself contains an instruction addressed to the model, when the model claims success and the tests disagree.

What Mastery Looks Like

  • Design a state machine with an explicit failure edge for every external failure mode — budget exhaustion, tool error, sandbox timeout, verification failure — with no implicit "and then it just retries forever" edge (Phase 4, section 16).
  • Build a tool-calling layer where a malformed or schema-invalid model output never reaches an effectful path, provably, not by convention (Phase 1, section 13).
  • Make a token budget an arithmetic constraint enforced before a request is sent, not an after-the-fact truncation (Phase 3, section 15).
  • Run untrusted repository code and untrusted agent-authored shell commands with zero sandbox escapes across a large evaluation run, and explain exactly which OS primitive enforces that (Phase 5, section 17).
  • Detect a stale edit — the file changed since the model was shown it — and reject it rather than silently misapplying it (Phase 6, section 18).
  • Treat the repository's own tests as the sole arbiter of "done," including handling a test suite that is itself flaky (Phase 7, section 19).
  • Reason from first principles about why "the model reads a file" is an untrusted-input event and design the trust boundary accordingly (Phase 10, section 22).
  • Produce a number — resolve rate on a named benchmark subset, cost per task, turns to completion — instead of an adjective, and defend it under section 28's differential and replay testing (Phase 11, section 23).

Concurrency: one agent-loop instance per task; the sandbox pool and model-client connection pool are shared, bounded resources (section 26 topology, section 31 sandbox-slot limit). Persistence: trajectories and the cost ledger are append-only and durable across process restarts; the repository index is durable and incrementally rebuilt. Protocol boundaries: CLI/service to core is an in-process call or a queue message (section 26); core to provider is the ModelClient protocol (section 11); core to sandbox is the OCI runtime interface (section 17); core to Git remote is the provider's REST/GraphQL API.

Per-box description: the task spec parser turns a free-text or structured task description into a validated TaskSpec (section 11), the first and only point where a raw instruction enters the system. The repository indexer builds and incrementally maintains the lexical, structural (tree-sitter), and optional embedding index (section 14) without model involvement — purely mechanical. The context retriever & budgeter is where the untrusted boundary begins in earnest: it selects repository chunks and enforces the token- budget arithmetic of section 8 before anything reaches a prompt. The prompt assembler concatenates system prompt, task, retrieved context and (compacted) history, tagging each segment's trust level for the model and for downstream logging. The model client is the sole point of contact with the external provider, behind a versioned interface (ADR-02) that also implements the recorded-response replay transport used by every deterministic test. The response parser & tool-call validator rejects any output that does not parse to a valid, schema-conformant tool call (I3) before it can reach an effectful path. The tool registry exposes read, edit, search, shell and test tools, each with a declared effect class (section 8). The sandbox executor is the only place untrusted code or untrusted commands run (I1); it enforces filesystem, network and resource isolation (section 17). The patch applier enforces the stale-precondition check (I2) before writing any edit to disk. The verification runner invokes the repository's own tests/lints/build inside the sandbox and is the sole source of truth for task success (P1). The trajectory recorder durably logs every turn for replay and evaluation (I7). The cost/token accountant maintains an atomic ledger (I10) consulted by the budgeter before every request. The patch emitter/PR creator turns a verified PatchSet into a reviewable diff or pull request (section 21). The eval harness drives the entire stack, unmodified, over a benchmark task set (section 23).

6. Design Principles

P1 — The test suite is the oracle. The agent's claim of success means nothing; only a green verification run (section 19) advances a task past Verifying. Tradeoff: a weak or missing test suite makes the agent unverifiable, not merely less accurate. Operational implication: flaky tests are a correctness problem, not an annoyance (ADR-17). Violating this by trusting self-reported completion produces silent regressions the agent itself "confirmed" were fixed.

P2 — Every effectful model output is schema-validated and bounded. A free-text shell command accepted without validation is a prompt-injection vulnerability with extra steps. Tradeoff: schema rigor costs expressiveness — the model cannot invent a new action shape mid-task. Implication: I3 is enforced pre-dispatch, never post-hoc. Violating this collapses the tool layer into ADR-03's rejected free-text protocol without the awareness that it was rejected for a reason.

P3 — All repository content is untrusted input. A file in the repo can address the model directly (Greshake et al. 2023). Tradeoff: every retrieved chunk must be trust-tagged and handled by the prompt assembler accordingly, adding bookkeeping. Implication: section 3's untrusted-content boundary is architectural, not a filter bolted on later. Violating this turns every README.md in every dependency into a potential command channel.

P4 — Every action is recorded in a replayable trajectory. A non-reproducible agent run cannot be debugged or evaluated (I7). Tradeoff: recording cost (storage, section 34) and the discipline of deterministic replay. Implication: the entire test suite in section 28 is foundationally built on recorded-response replay. Violating this means every regression investigation starts from nothing.

P5 — An edit applies only if its target still matches what the model was shown. A stale edit is rejected, not silently misapplied (I2). Tradeoff: extra hashing and a failure mode ("stale precondition") the model must be told how to recover from. Implication: concurrent mutation (another tool call, a background process) cannot corrupt a file quietly. Violating this reintroduces exactly the whitespace-corruption bugs unique-string matching was chosen to avoid (Aider lesson, section 5).

P6 — The token budget is enforced before a request, never after. Truncating a response after the fact wastes the call and the money. Tradeoff: the budgeter must be conservative, sometimes under-filling the window. Implication: I4 and I13 are pre-flight checks in the context retriever, not post-flight repairs. Violating this produces the "context window exceeded" provider error mid-task with no clean recovery path.

P7 — A task terminates within its turn and wall-clock ceilings, never looping unbounded. Tradeoff: a legitimately hard task may be cut off before it would have succeeded with more turns. Implication: I5, ADR-18's fixed ceilings, and an explicit Aborted terminal state (section 8). Violating this is the direct mechanism of a cost-runaway incident (T7).

P8 — Nothing untrusted executes outside the sandbox. No repository code, no agent- authored shell command, no test invocation runs on the host (I1). Tradeoff: sandbox spawn latency (section 4) on every command. Implication: the sandbox executor is the single narrowest waist of the system's trust boundary. Violating this is a sandbox-escape-adjacent design flaw before any actual escape occurs.

P9 — The sandbox holds no ambient credential. No environment secret, CI token, or cloud credential is readable from inside it (I6). Tradeoff: any legitimate need for a credential inside a task (e.g., private package registry auth) requires an explicit broker, not env passthrough (ADR-14). Implication: exfiltration via an injected command yields nothing of value. Violating this turns every prompt-injection incident into a credential-theft incident.

P10 — Deterministic replay from recorded model responses is the foundation of testing. A live-model test is neither reproducible nor cheap (section 28). Tradeoff: recorded fixtures drift from live model behavior over time and must be periodically refreshed. Implication: the Phase 0 replay gate (section 12) exists before any other feature. Violating this means every CI run is a flaky, costly integration test against a live third-party API.

P11 — Verification precedes advancement; there is no self-reported success path. Direct corollary of P1 expressed as a state-machine rule: the Verifying state's only exits are Done (tests pass) and Reflecting/Failed (tests fail) — there is no edge from Acting straight to Done. Violating this is architecturally identical to violating P1.

P12 — Every tool has a declared effect class. Read-only, mutating, or executing, each with its own idempotency and failure-mode contract (section 8 tool-call contract table). Tradeoff: classification overhead per tool addition. Implication: retry policy, approval gating, and sandboxing requirements all derive from effect class rather than being decided per tool ad hoc. Violating this means every new tool re-litigates its own safety posture.

P13 — The cost ledger is a first-class, atomically-updated ledger, not a log line. Cost data drives the budgeter's pre-flight check (P6) and the operational cost-ceiling alarm (section 26). Tradeoff: every model call must be wrapped in a ledger-write transaction. Implication: I10. Violating this makes the $2/$5 cost ceiling (section 4) unenforceable in practice, not merely unobserved.

P14 — The context budget is arithmetic, not vibes. System + task + retrieved + history + reserved-output must provably fit the window before assembly, with a named formula (section 8). Tradeoff: conservative allocation sometimes leaves the window under-filled. Implication: every retrieval decision is auditable against a number. Violating this is the single most common root cause of "the agent forgot what it was doing" bug reports (MM2, section 32).

Debugging methodology exercising these invariants: for any observed anomaly, first identify which invariant, if any, was violated (not "which feature is broken"); pull the trajectory (I7) and replay it deterministically; if replay diverges, the bug is in the model-client or recorder layer, not the agent logic; if replay reproduces the anomaly, bisect the turn at which the violated invariant's guard should have fired and inspect why it did not (a missing check, a race, or a genuinely new failure mode requiring a new invariant).

8. Domain Model

8.1 Agent-Loop State-Transition Table

From Event To Notes
Planning Model produces a parseable next action Retrieving or Acting Planning may itself request more context
Planning Model response has no parseable action Reflecting Counts against retry budget (I5)
Planning Malformed/unschematized response repeated past retry budget Failed Terminal
Retrieving Context assembled within budget Acting Budgeter check per I4/I13
Retrieving Budget cannot be satisfied even after compaction Aborted Terminal; P6/I4
Acting Tool call validates and dispatches Observing I3 gate passed
Acting Tool call fails schema validation Reflecting Returned as tool_result error, not silently dropped
Acting Turn ceiling reached mid-action Aborted Terminal; I5
Observing Tool result received normally Planning Loop continues
Observing Tool reports nonzero exit / exception Reflecting Tool-error failure edge
Observing Sandbox command exceeds per-command timeout Reflecting (first N) / Aborted (repeated) Sandbox-timeout failure edge
Observing Model signals task believed complete Verifying Never Done directly (P11)
Verifying Tests/lints/build pass Done Terminal; P1
Verifying Tests/lints/build fail Reflecting Verification-failure edge
Verifying Verification harness itself hangs/times out Aborted Terminal; treated as infra failure, not task failure
Reflecting Retry budget available Planning Reflexion-style feedback appended (Shinn et al. 2023)
Reflecting Retry budget exhausted Failed Terminal
Any Wall-clock ceiling reached Aborted Terminal; checked on every transition (I5)
Any Cost ceiling (hard) reached Aborted Terminal; T7 guard

Done, Failed, Aborted are terminal; only Done results in patch/PR emission (section 21).

8.2 Tool-Call Contract

Tool Schema (key fields) Effect Class Idempotent Timeout Failure Mode
read_file path, line_range? read-only yes 5s path outside root → schema/precondition error
search query, mode (lexical|structural|embedding), max_results read-only yes 5s empty index → degrade to lexical only
edit path, anchor (EditOp), content_hash mutating no 5s stale precondition (I2), ambiguous anchor
shell command, cwd, timeout_sec executing no ≤120s nonzero exit, timeout, sandbox spawn failure

8.3 Context-Budget Arithmetic

system_prompt + task_spec + retrieved_context + history + reserved_output ≤ context_window

Worked allocation (window = 200,000): system_prompt = 3,000; task_spec = 1,000; reserved_output = 8,000; history (compacted, cap) = 20,000; remaining for retrieved_context = 200,000 − 3,000 − 1,000 − 8,000 − 20,000 = 168,000 theoretical, policy-capped at 100,000 (section 4 per-turn input cap headroom) leaving 68,000 as safety margin for tool-result growth within a turn without re-running the budgeter mid-turn. Eviction/summarization policy: when history exceeds its 20,000-token cap, the oldest turns are collapsed into a single summary record ("earlier in this session, X was tried and failed because Y") preserving the most recent 4–8 turns verbatim and all open (unresolved) tool-call threads uncompacted.

8.4 Structured-Edit Representation Comparison

Representation Match Semantics Stale-Precondition Support Failure Mode Verdict
Whole-file rewrite Full replacement Trivial (hash whole file) Expensive; large diffs obscure intent Fallback for small/generated files (ADR-05)
Unified diff Line-number + context hunks Weak (hunk offsets drift) Model hallucinates line numbers; silent misapply Rejected as primary
Search-and-replace block Unique-anchor exact match Strong (hash the anchored region) Ambiguous/absent anchor → explicit error Locked primary (ADR-05)
AST-level edit Structural node match via tree-sitter Strong (structural equality) Requires a grammar per language; brittle on syntax errors Used for high-confidence template repairs (Getafix-style, section 18)

8.5 Retrieval Strategy Decision Table

Strategy Signal Cost Precision When Used
Lexical Token/substring match (ripgrep/BM25-style) Low High for exact identifiers Default first pass, every query
Structural tree-sitter symbol table Low–medium High for "definition of X" Symbol-shaped queries
Embedding Vector similarity Medium–high High for natural-language intent Fallback when lexical/structural yield low-confidence results

8.6 Verification-Loop Protocol (Sequence)

  1. Discover verification command (convention-based, ADR-16; manual override honored).
  2. Dispatch inside sandbox with the 600s test-suite budget (section 4).
  3. Capture stdout/stderr/exit code; classify: pass / fail / timeout / flaky-suspect.
  4. If flaky-suspect (result differs from a prior run on unchanged code), apply ADR-17 quorum (run 3×, majority rules).
  5. Emit VerificationRun record; transition per section 8.1.

8.7 Trajectory Record Schema (fields)

task_id, turn_index, state_from, state_to, model_request_ref, model_response_ref, tool_calls[], tool_results[], token_usage{input,output}, cost_delta, wall_clock_ms, trust_tags{}, timestamp. One record per turn, append-only (ADR-21).

8.8 Cost-Accounting Model

turn_cost = input_tokens × input_price + output_tokens × output_price; task_cost = Σ turn_cost over all turns; ledger entries are written atomically per turn (I10) and checked against the soft/hard ceilings (section 4) before the next request is issued (P6/P13).

8.9 Worked End-to-End Example (Four Turns)

Prices: $3 / 1M input tokens, $15 / 1M output tokens (representative frontier pricing).

Turn Action Input tok Output tok Turn cost
1 Retrieve + plan 15,000 800 $0.045 + $0.012 = $0.057
2 read_file result folded in, propose edit 22,000 600 $0.066 + $0.009 = $0.075
3 Test run result folded in, propose second edit 30,000 1,200 $0.090 + $0.018 = $0.108
4 Verification passes, summarize 34,000 400 $0.102 + $0.006 = $0.108

Task total: $0.348, well under the $2.00 soft ceiling (section 4) — an example of an easy task; section 34 shows the fleet-average 8-turn task at ≈$1.14.

8.10 Malformed-Input Examples

Example Handling
Tool call with an invalid schema (missing required field) I3 rejects pre-dispatch; returned as tool_result error; counts against turn
Edit whose anchor is absent from the current file EditPrecondition failure; explicit "anchor not found" error, no partial write (I12)
Edit whose anchor matches twice (ambiguous) Rejected with disambiguation hint (surrounding-line count) per file
Model response with no parseable action at all Planning → Reflecting failure edge (section 8.1)
Shell test command that hangs Sandbox per-command timeout fires; Observing → Reflecting (or Aborted if repeated)
Repository file containing an injected instruction (e.g., a README with "ignore previous instructions") Trust-tagged as untrusted at retrieval; system prompt instruction hierarchy (ADR-24) prevents it overriding task instructions; logged as an injection-detection hit (section 26 metric)

8.11 Failure-Path Example

Task: fix a failing test. Turn 1–3 proceed normally into Verifying. Verification fails (test still red). Reflecting: Reflexion-style feedback appended, retry budget available, back to Planning. Turns 4–7 repeat the loop with progressively refined edits. At turn 8 the model proposes an edit whose anchor is now stale (another tool call altered the file); I2 rejects it, Reflecting again. At turn 12, retry budget for this failure signature is exhausted → Failed, trajectory retained for post-mortem (section 25, FM-class review).

12. Phase 0 — Skeleton, Model-Client Interface, Recorded-Response Replay, CI

12.1 Objectives

Stand up the project skeleton, the ModelClient provider interface (ADR-02), the recorded- response replay transport that makes every later test deterministic (P10), and a CI pipeline that runs the replay gate before any feature work begins. Nothing in this phase talks to a sandbox or edits a repository; it is pure plumbing.

12.2 Detailed Implementation Steps

  1. Create the repository layout of section 10 (empty modules, populated pyproject.toml, pinned lockfile per ADR-32).
  2. Define ModelClient as a Protocol (section 11) with one live implementation (thin wrapper over a provider SDK) and one replay_transport implementation that reads ModelResponse fixtures keyed by request hash — this is the P10 foundation.
  3. Define TaskSpec, TaskId, RepoSnapshot (section 11); wire the CLI (agent run) to parse a task-spec file into a TaskSpec.
  4. Implement Trajectory/Turn recording (section 8.7) as an append-only JSONL writer (ADR-21); every ModelClient.send call, live or replayed, must produce a Turn record — this is I7's enforcement point.
  5. Implement the CI pipeline (ADR-30): a replay-gate job that runs the full test suite against replay_transport only, with zero live network calls, per the P10 design principle.
  6. Implement CostLedger skeleton (section 11) with a stub pricing.py — no real accounting logic yet (Phase 11 owns full accuracy), but the atomic-write contract (I10) is established here so nothing downstream has to retrofit it.
  7. Record the first fixture: a trivial one-turn ModelResponse ("no tool call, plain text reply") and assert replay reproduces it byte-for-byte.

12.3 Deliverable

A agent run --dry-run <task-spec> command that parses a task spec, sends exactly one request through replay_transport, records one Turn, and exits — with the replay-gate CI job green.

12.4 Acceptance Criteria

  • make replay-gate passes with zero live-network calls (verified by a network-block test fixture that fails the build if a socket is opened).
  • Trajectory file for the dry-run contains exactly one Turn record matching the schema in section 8.7.
  • Replay of the recorded fixture fixtures/phase0/basic_reply.json reproduces an identical tool-call sequence (I7) across 10 consecutive CI runs.
  • Cold CI run completes in under 90 seconds.

12.5 Conformance Fixtures

  • conformance/recorded_responses/phase0_basic_reply.json — one-turn plain-text response; expected: one Turn record, stop_reason="end_turn".
  • conformance/recorded_responses/phase0_malformed_json.json — a response body that is not valid JSON; expected: ModelClient raises a typed parse error, not an unhandled exception.
  • conformance/fixtures/phase0_taskspec_minimal.yaml — smallest valid TaskSpec; expected: parses without error.
  • conformance/fixtures/phase0_taskspec_missing_repo_ref.yaml — expected: schema-validation failure at parse time, not at first use.

12.6 Pitfalls

  • Hardcoding the live provider client into the agent loop instead of behind ModelClient — makes P10 impossible to retrofit later without a rewrite.
  • Keying replay fixtures by exact request string instead of a normalized hash — any harmless whitespace change in the system prompt then breaks every fixture.
  • Treating the trajectory writer as a logging convenience instead of the source of truth — later phases silently skip recording under error paths if this isn't enforced from turn one.
  • CI "passing" because the replay-gate job never actually exercised replay divergence detection — always include one fixture designed to catch a broken replay path.

12.7 Performance Concerns

Fixture lookup must be O(1) (hash-indexed), not a linear scan — replay-gate CI time grows with fixture count otherwise. Trajectory writes are append-only and must not fsync per-field; batch per turn.

12.8 Edge Cases

  • Empty TaskSpec.instruction string — reject at parse time, not deep in the loop.
  • A recorded fixture whose ModelResponse.usage is missing — accountant must default to a conservative estimate, not crash.
  • Two fixtures with colliding normalized-request hashes — must raise, not silently pick one.

12.9 Failure Analysis

Class: replay-gate false-green (fixture exists but its assertions are too weak to catch a regression). Root cause: fixtures written only for the happy path. Debug method: mutate the implementation deliberately (e.g., skip the trajectory write) and confirm the fixture suite fails — a "mutation smoke test" run once at phase close. Signal: CI green on a known-bad diff. Recovery: add the missing assertion, never merge a fixture without a corresponding negative-mutation check.

12.10 Operational Notes

This phase produces no user-facing capability; its exit criterion is entirely internal (CI green, replay deterministic). Treat the replay-gate job as a permanent, non-optional CI step for every subsequent phase — no later phase's tests may depend on a live model call.

13. Phase 1 — Tool Layer with Schema Validation

13.1 Objectives

Build the ToolSpec/ToolCall/ToolResult layer (section 11) and the JSON Schema gate (I3) that stands between every model output and any effectful action, following the agent-computer-interface lesson of Yang et al. (2024, SWE-agent — applied here per section 5) and the tool-learning framing of Schick et al. (2023, Toolformer).

13.2 Detailed Implementation Steps

  1. Define ToolSpec.json_schema for read_file, search, edit, shell, test (section 8.2) using the JSON Schema specification (section 5 RFC).
  2. Implement the response parser: extract ToolCalls from a ModelResponse, or classify the response as "no parseable action" per the Planning→Reflecting edge (section 8.1).
  3. Implement the validator: for every ToolCall, validate arguments against the matching ToolSpec.json_schema before any dispatch — this is I3's sole enforcement point; no other code path may call a tool implementation directly.
  4. Assign EffectClass (P12) to each tool; wire effect class into retry policy (mutating and executing tools are never blindly retried without re-validating preconditions).
  5. Implement read_file, search as read-only tools with no sandbox dependency yet (Phase 2 supplies real retrieval; Phase 5 supplies the sandbox for shell/test).
  6. Add a ToolResult trust-tagging step (P3): every payload returned from read_file/ search/shell/test is tagged untrusted_tool_output before re-entering the prompt.
  7. Record fixtures reproducing ReAct-style interleaved reason/act traces (Yao et al. 2023, applied here) to validate the parser handles reasoning text preceding a tool call.

13.3 Deliverable

A tool registry that dispatches read_file and search end-to-end from a validated ToolCall to a trust-tagged ToolResult, with 100% of dispatch attempts passing through the I3 schema gate (enforced by a single dispatch entry point, verified by static call-site audit).

13.4 Acceptance Criteria

  • Zero tool dispatches bypass schema validation across the full Phase 1 fixture suite (schema_validation_failures_total counter increments correctly on every injected bad call).
  • A malformed ToolCall (missing required field) never reaches a tool implementation — verified by a mock tool implementation that raises if invoked directly.
  • Parser correctly extracts tool calls from 20/20 fixtures spanning plain-text, reasoning- prefixed, and multi-tool-call-in-one-turn response shapes.

13.5 Conformance Fixtures

  • conformance/fixtures/phase1_invalid_schema_missing_path.json — read_file call missing path; expected: SchemaValidationError, no dispatch.
  • conformance/fixtures/phase1_react_trace.json — reasoning text + tool call in one response (Yao et al. 2023 shape); expected: tool call extracted correctly, reasoning text discarded from the effectful path.
  • conformance/fixtures/phase1_no_action.json — plain prose with no tool call; expected: Planning→Reflecting transition per section 8.1.
  • conformance/fixtures/phase1_multi_call_one_turn.json — two tool calls in one response; expected: both validated and dispatched in order, both results returned in one Observing step.

13.6 Pitfalls

  • Validating "most" arguments but trusting a free-text command-shaped field unchecked — this reintroduces exactly the free-text-protocol risk ADR-03 rejected.
  • Allowing a second code path (e.g., a "quick tool" shortcut) that skips the registry — guarantees an eventual I3 violation; enforce a single dispatch chokepoint.
  • Over-trusting StopReason — a stop_reason="tool_use" with an empty tool_calls list must be treated as a parser/provider anomaly, not silently skipped.

13.7 Performance Concerns

Schema validation cost is per-call and must stay sub-millisecond (compiled JSON Schema validators, not re-parsed per call) — at 40 turns/task with multiple tool calls per turn this is on the hot path of every turn's latency budget (section 4).

13.8 Edge Cases

  • A tool call whose tool_name does not match any registered ToolSpec — reject with a clear "unknown tool" error distinct from a schema-validation error.
  • A ToolResult payload larger than the per-turn budget's remaining allowance — truncate with an explicit truncation marker, never silently drop.
  • Duplicate call_id across two tool calls in one response — reject the turn.

13.9 Failure Analysis

Class: silent schema-gate bypass via a debug/test-only code path left enabled in production. Root cause: a "quick call" helper added for local testing never removed. Detection: static audit counts dispatch call sites; CI fails if more than one exists. Recovery: remove the bypass, add a regression fixture asserting single-chokepoint dispatch.

13.10 Operational Notes

Every new tool added after this phase must ship with a ToolSpec.json_schema, an EffectClass, and at least one negative (schema-violating) fixture before merge — this is a standing review checklist item, not a one-time task.

14. Phase 2 — Repository Indexing and Retrieval

14.1 Objectives

Build the lexical, structural (tree-sitter), and optional embedding indexes (ADR-07, ADR-08, ADR-09) and the retrieval query path, entirely mechanical and model-free, producing RetrievedChunks tagged untrusted_repo_content (P3) for the Phase 3 budgeter to consume.

14.2 Detailed Implementation Steps

  1. Walk the repository respecting .gitignore; build RepoSnapshot (section 11) and persist file metadata to the SQLite index store (ADR-08).
  2. Build the lexical inverted index over tokenized file contents; this is the default first retrieval pass (ADR-07) and must work with zero additional dependencies.
  3. Integrate tree-sitter per supported language grammar; extract function/class/method definitions into SymbolIndex (section 11), applying the lexical-analysis grounding of Aho et al. (compilers, section 5).
  4. Implement symbol-aware chunking (ADR-09): chunk boundaries align to tree-sitter node boundaries, never mid-function.
  5. Implement the optional embedding index (ADR-07 fallback path): chunk → embed → store vectors; gate behind a config flag since it adds ~300s to index build time (section 4).
  6. Implement search(query, mode) dispatch: lexical always available; structural available once SymbolIndex is built; embedding available only if enabled.
  7. Implement incremental re-indexing keyed on file mtime/content-hash delta, per the Aider repo-map lesson (section 5) — avoid full rebuild on every task.
  8. Wire the Continue-style pluggable-context-provider pattern (section 5) so retrieval mode selection is a strategy object, not a hardcoded branch.

14.3 Deliverable

agent index build <repo> produces a durable SQLite index within the section 4 time budget, and search() returns ranked RetrievedChunks for lexical and structural modes on a real open-source repository fixture.

14.4 Acceptance Criteria

  • Index build on a 1.5M-LOC fixture repo completes in <120s (lexical+structural), matching section 4; embedding-enabled build completes in <420s total.
  • find_symbol-shaped structural query returns the correct definition location in ≥95% of a 200-query labeled fixture set.
  • Retrieval p95 latency <400ms hybrid (lexical+structural) per section 4, measured over 500 queries against the fixture repo.
  • Incremental re-index after a single-file edit completes in <2s (not a full rebuild).

14.5 Conformance Fixtures

  • conformance/fixtures/phase2_labeled_symbol_queries.json — 200 (query, expected file:line) pairs across 3 languages; expected: ≥95% correct.
  • conformance/fixtures/phase2_gitignore_respect.json — repo fixture with a node_modules/ tree; expected: zero indexed files under it.
  • conformance/fixtures/phase2_incremental_delta.json — before/after file edit; expected: only the changed file's chunks are re-indexed.
  • conformance/fixtures/phase2_injection_readme.json — a README.md containing an embedded instruction ("ignore prior instructions..."); expected: indexed and retrievable like any other content, tagged untrusted_repo_content — indexing must not "notice" or act on it, only tag it (that judgment belongs to Phase 10, section 22).

14.6 Pitfalls

  • Chunking by fixed line windows for source code — routinely splits a function in half, degrading both retrieval precision and edit-anchor availability downstream (ADR-09).
  • Treating tree-sitter parse failures (syntax errors in a work-in-progress file) as fatal — degrade gracefully to lexical-only for that file instead of aborting the whole index build.
  • Letting embedding-index build time silently balloon the section-4 index-build budget when enabled by default — keep it opt-in (ADR-07).
  • Re-embedding the entire repo on every task instead of incrementally — defeats the point of a persistent index.

14.7 Performance Concerns

Lexical index build is O(total tokens); structural build is O(total AST nodes); both must stay within the 120s budget at 1.5M LOC (section 4). Retrieval must not degrade linearly with repo size — the whole point of an index (section 31 scalability: retrieval sublinear).

14.8 Edge Cases

  • Binary files — excluded from indexing, not silently truncated into garbage tokens.
  • A file that changed language (renamed .js → .ts) between index runs — re-parse under the new grammar, don't keep stale symbols.
  • A repository with no recognized build/language files at all — index falls back to lexical- only with a clear capability-degraded flag surfaced to the retriever.

14.9 Failure Analysis

Class: structural retrieval silently degrading to near-lexical quality after a grammar version bump breaks tree-sitter node-type names. Root cause: unpinned tree-sitter grammar version. Detection: the 200-query labeled fixture accuracy metric drops below 95% in CI. Recovery: pin grammar versions per ADR-32's reproducibility discipline; re-run fixture suite on any grammar upgrade before merge.

14.10 Operational Notes

Index storage lives outside the sandbox-writable workspace (it is trusted infrastructure state, not task output); back it up alongside the trajectory store per section 26. Re-index on a schedule for long-lived deployments, not only on task arrival, to keep incremental deltas small.

15. Phase 3 — Context Budgeter and Prompt Assembler

15.1 Objectives

Implement the token-budget arithmetic of section 8.3 as a pre-flight, provable check (P6, P14, I4, I13) and the prompt assembler that produces a trust-tagged PromptAssembly — the last stop before repository content and history reach the model.

15.2 Detailed Implementation Steps

  1. Implement TokenBudget/BudgetAllocation (section 11) with the constructor invariant sum(fields) <= window (I13) enforced as a hard assertion, not a warning.
  2. Implement the allocation formula from section 8.3: fixed reservations for system/task/ reserved-output, a capped history slice, and the retrieved-context remainder capped at the section-4 per-turn input policy limit.
  3. Implement token counting using the provider's actual tokenizer (not a character-count approximation) — approximation error compounds across 40 turns and silently violates I4.
  4. Implement the eviction/summarization policy (section 8.3): when history exceeds its cap, collapse older turns into a single summary turn, preserving the most recent 4–8 turns and all open tool-call threads verbatim, applying the chain-of-thought-preservation caution of Wei et al. (2022, applied here) — summarization must not discard the reasoning trail needed for the next planning step.
  5. Implement the prompt assembler: concatenate system, task, retrieved, history segments, attaching trust_tag metadata per segment (P3) so downstream logging and the Phase 10 injection guard can distinguish trusted from untrusted spans.
  6. Wire the budgeter as a mandatory pre-flight step in the Retrieving state (section 8.1): Retrieving may only transition to Acting after a successful BudgetAllocation.
  7. Add budget-exhaustion telemetry (budget_preflight_rejections_total, I4) and the Retrieving→Aborted failure edge for the case allocation cannot be satisfied even after compaction.

15.3 Deliverable

A PromptAssembly builder that, given a TaskSpec and a set of RetrievedChunks, either returns a valid assembly with sum(allocation) <= window provably true, or raises BudgetExceededError with no partial prompt ever sent.

15.4 Acceptance Criteria

  • Property test (section 28): for 10,000 randomly generated allocations, the budgeter never returns an assembly exceeding the 200,000-token window (I13, zero violations required).
  • History compaction triggers correctly at the 20,000-token cap on a fixture conversation of 60 synthetic turns, preserving the most recent 6 turns verbatim in 100% of runs.
  • Token counts computed by the budgeter match the provider's own reported usage field within 1% on a 50-fixture regression set (accounting for the estimate-before-response gap).

15.5 Conformance Fixtures

  • conformance/fixtures/phase3_overflow_allocation.json — retrieved context deliberately sized to overflow the window; expected: BudgetExceededError, no request sent.
  • conformance/fixtures/phase3_compaction_60_turns.json — 60-turn synthetic history; expected: compacted to ≤20,000 tokens, last 6 turns verbatim, all open tool threads intact.
  • conformance/fixtures/phase3_trust_tag_roundtrip.json — assembly containing both trusted (system) and untrusted (retrieved) segments; expected: trust tags survive serialization to the trajectory record unchanged.

15.6 Pitfalls

  • Estimating tokens with len(text) // 4 instead of the real tokenizer — the estimate error is exactly the kind of silent I4 violation that only shows up as a provider-side context- overflow error mid-task.
  • Compacting history but losing track of an "open" tool-call thread (a shell call whose result hasn't been observed yet) — the model then responds to a tool call it can no longer see, producing a nonsensical turn.
  • Allocating the full theoretical remainder (168,000 tokens in the section 8.3 worked example) instead of the policy-capped 100,000 — leaves no headroom for tool-result growth within the same turn, immediately re-triggering overflow.

15.7 Performance Concerns

Tokenization of large retrieved contexts must be batched, not called once per chunk — real tokenizer calls are not free, and doing this per-chunk across 100+ candidate chunks per retrieval pass is a measurable per-turn latency cost.

15.8 Edge Cases

  • A single retrieved chunk larger than the entire retrieval budget — split at a symbol boundary (ADR-09) or drop with a logged rationale, never truncate mid-token.
  • Task instruction itself exceeds the 1,000-token task reservation — this is a TaskSpec parse-time rejection (Phase 0), not a Phase 3 concern, but Phase 3 must not silently absorb the overflow by stealing from the retrieved-context slice.
  • Zero retrieved chunks available (empty index or no relevant matches) — assembly proceeds with an explicit "no relevant context found" marker rather than a silently empty segment.

15.9 Failure Analysis

Class: gradual context poisoning where compaction summaries lose critical constraints mentioned early in the task ("do not modify the public API"). Root cause: naive last-N-turns-verbatim-else-summarize with a summarizer that has no instruction to preserve constraints. Detection: eval harness (section 23) trajectory review flags tasks that violate an early stated constraint after turn 20+. Recovery: pin explicit constraints as a permanent, never-compacted segment separate from the compactable history slice.

15.10 Operational Notes

Treat the allocation formula's constants (3,000/1,000/8,000/20,000/100,000) as a versioned configuration, not a hardcoded literal — section 27 requires re-evaluation on any prompt- template version bump, and these constants are part of that template's behavioral contract.

16. Phase 4 — Agent-Loop State Machine with Turn Ceilings

16.1 Objectives

Implement the full AgentState machine of section 8.1 as executable control flow, enforcing I5's turn and wall-clock ceilings on every transition, applying the interleaved reason-act loop of Yao et al. (2023, ReAct — applied here) as the Planning/Acting/Observing core.

16.2 Detailed Implementation Steps

  1. Implement AgentState transitions exactly as tabulated in section 8.1, as a single dispatch table — no ad hoc if-chain scattered across the codebase (P7).
  2. Wire turn-counter and monotonic-clock (ADR-33) wall-clock checks into every transition; any transition attempted past the hard ceiling (60 turns / 45 min) forces Aborted regardless of the state it was in (I5).
  3. Wire cost-ceiling checks (I10, section 4) into the same transition guard — a hard-ceiling breach forces Aborted identically to a turn/wall-clock breach (P7, T7).
  4. Implement the Planning state to consult the budgeter (Phase 3) before every model call, never after (P6) — Planning cannot itself skip Retrieving.
  5. Implement the Observing state's classification of tool results into the three failure edges (tool error, sandbox timeout, normal) per section 8.1, each routed to its correct next state.
  6. Implement the Verifying-state entry guard (I9): no transition to Done is possible without a VerificationRun record attached to the current turn — enforce as an assertion, not a convention.
  7. Emit a Turn record (section 8.7) on every single transition, feeding the Phase 0 trajectory recorder — this phase is where I7 becomes load-bearing rather than theoretical.
  8. Build the CLI/service progress surface: expose current state, turn count, and running cost to the operator in real time (section 26 telemetry hook point).

16.3 Deliverable

A running agent loop that, driven entirely by replay_transport fixtures, executes a full Planning→Retrieving→Acting→Observing→Verifying→Done path and a full Planning→...→Reflecting→...→Failed path, both fully recorded and replayable.

16.4 Acceptance Criteria

  • 100% of transitions in a 500-fixture regression suite match the section 8.1 table exactly (no transition taken that section 8.1 does not enumerate).
  • Turn-ceiling enforcement: a fixture forcing 61 turns is forced to Aborted at turn 60, not 61 (I5, hard ceiling exact-boundary test).
  • Wall-clock ceiling enforcement: a fixture with injected 46-minute elapsed time is forced to Aborted (I5).
  • Zero Done transitions without an attached VerificationRun across the full fixture suite (I9, should be exactly 0).

16.5 Conformance Fixtures

  • conformance/fixtures/phase4_happy_path_4_turn.json — the section 8.9 worked example, replayed; expected: Done at turn 4.
  • conformance/fixtures/phase4_turn_ceiling_boundary.json — forces exactly 60 turns of Reflecting loops; expected: Aborted precisely at turn 60, not before or after.
  • conformance/fixtures/phase4_verify_skip_attempt.json — a mutated implementation that attempts Acting→Done directly; expected: assertion failure caught by I9's guard, test fails loudly (this is a deliberate mutation-test fixture per section 12.9's method).
  • conformance/fixtures/phase4_cost_hard_ceiling.json — injected cost ledger past $5.00; expected: Aborted at the exact turn the hard ceiling is crossed.

16.6 Pitfalls

  • Implementing ceilings as a "check at the top of the loop" instead of inside every transition — a single long-running tool call inside one turn can still blow through the wall-clock ceiling before the next top-of-loop check fires.
  • Allowing Reflecting to reset the turn counter — this defeats I5 entirely by turning "retry budget" into unlimited retries in disguise; retries consume the same turn budget.
  • Treating Aborted and Failed as interchangeable in logging/metrics — they have different root causes (external ceiling vs. exhausted task-specific retry) and conflating them destroys the failure-analysis signal (section 25).
  • Forgetting that a sandbox-timeout Observing edge must still count against the turn budget — an infinite sequence of "try a command, it hangs, retry" would otherwise never terminate.

16.7 Performance Concerns

State-transition dispatch itself must be O(1) table lookup, not a chain of isinstance checks — at up to 60 turns/task and high task concurrency (section 31), this is a measurable per-turn overhead if implemented naively.

16.8 Edge Cases

  • A tool result arrives after the wall-clock hard ceiling has already technically passed (race between the timer and the sandbox) — the transition guard, not the tool call site, is the authority; force Aborted even if the tool "succeeded."
  • A Reflecting→Planning edge taken with zero remaining budget headroom in the very same turn that would exceed the soft cost ceiling — must warn (telemetry) but is allowed to proceed once, only the hard ceiling is a hard stop (ADR-18).
  • Two failure edges applicable simultaneously (e.g., both a tool error and a wall-clock breach) — wall-clock/turn/cost ceilings take priority over task-specific failure edges (P7 supersedes local retry logic).

16.9 Failure Analysis

Class: task silently "stuck" in Reflecting for many turns without visible progress. Root cause: Reflexion-style feedback (Phase 8, section 20) not yet wired, so Reflecting loops back to Planning with no new information — deliberately absent in this phase (Phase 8 supplies it), so the correct behavior here is only that turn/cost ceilings still bound the loop, not that progress happens. Detection: turn-ceiling telemetry (task_ceiling_hits_total) firing at a suspiciously high rate signals this phase's transitions are correct but Phase 8 is what's missing. Recovery: none needed in this phase — this is the expected, bounded behavior until Phase 8 lands.

16.10 Operational Notes

Expose AgentState and turn/cost counters as the primary real-time operator-facing signal (CLI status line, service dashboard row) — this is the single most useful piece of live telemetry for a human watching a running task, and it costs nothing extra to surface once the state machine emits it per transition.

17. Phase 5 — Sandbox Executor

17.1 Objectives

Build the sandbox executor (P8, I1, I6, I11) as the sole place untrusted repository code and agent-authored commands run, on an OCI-compliant runtime (ADR-11, section 5 RFC), applying the syscall-isolation lineage of Provos (2003, applied here) and the event-stream runtime separation lesson of OpenHands (section 5, applied here).

17.2 Detailed Implementation Steps

  1. Implement SandboxSpec→SandboxHandle spawn via the OCI runtime interface: read-only repo bind mount + writable overlay workspace (ADR-12), default-deny network namespace with an explicit registry allowlist (ADR-13, I11).
  2. Implement the sandbox-slot pool with a bounded semaphore (ADR-34) sized to the host's per-sandbox RSS ceiling (section 4, section 34 capacity model) — spawn requests beyond pool capacity queue rather than oversubscribing memory.
  3. Implement env-construction with zero ambient credentials (I6, ADR-14): explicitly allowlisted, non-secret environment variables only; any legitimately required credential goes through a broker call outside the sandbox, never as a mounted env var.
  4. Implement run_command (backing the shell/test tools): per-command CPU/memory ceilings and timeout enforcement (section 4) using cgroup limits, killing the full process tree on timeout (not just the leader), consistent with the "kill children on timeout" lesson generalized from Nygard's stability patterns (section 5).
  5. Implement stdout/stderr capture with truncation (head+tail) on oversized output, tagged untrusted_tool_output (P3) before returning to the caller.
  6. Implement egress-denial logging: any attempted connection outside the allowlist is blocked and logged (sandbox_egress_denied_total, I11) without crashing the command (the command sees a connection failure, exactly as a real network-restricted host would).
  7. Implement sandbox teardown/recycling: destroy the writable overlay on task completion, return the slot to the pool, never reuse an overlay across tasks (I1 corollary — no cross-task contamination).
  8. Add the sandbox-escape-suspected detection hook: anomalous syscalls or an unexpected process outside the sandbox's cgroup are flagged as SandboxEscapeSuspectedError (highest severity, section 11) and immediately abort + page (T2).

17.3 Deliverable

A SandboxExecutor that spawns an isolated environment within the section 4 latency budget, runs an arbitrary command with enforced resource/network/timeout limits, and tears down cleanly, verified against a battery of escape-attempt fixtures with zero escapes.

17.4 Acceptance Criteria

  • Zero sandbox escapes over 10,000 adversarial command runs (section 4 target, escape attempts drawn from the fuzz corpus of section 28).
  • Sandbox spawn latency p50 ≤150ms / p95 ≤800ms on the warm pool (section 4).
  • A command attempting to read a mounted credential env var finds none present (I6, verified by an explicit env-diff assertion in every fixture run).
  • A command attempting egress to a non-allowlisted host is blocked in 100% of 500 fixture attempts (I11).
  • A command exceeding its timeout is fully killed (process tree, not just leader) within 1 second of the timeout firing, verified by process-table inspection post-kill.

17.5 Conformance Fixtures

  • conformance/fixtures/phase5_egress_denied.json — command attempts curl to a non-allowlisted host; expected: connection refused, logged, command completes with nonzero exit, task continues.
  • conformance/fixtures/phase5_credential_absent.json — command runs env; expected: output contains no AWS_*/GITHUB_TOKEN/etc. pattern (cross-checked against ADR-25's redaction pattern list).
  • conformance/fixtures/phase5_timeout_process_tree.json — command forks children then sleeps past timeout; expected: all descendant PIDs terminated.
  • conformance/fixtures/phase5_escape_attempt_corpus/ — a named suite of known container-escape technique reproductions (namespace-breakout attempts, privileged-syscall probes); expected: 0/N succeed.

17.6 Pitfalls

  • Killing only the process-group leader on timeout — orphaned children keep running and can keep consuming CPU/network past the nominal timeout.
  • Mounting the full host environment "for convenience" during early development and forgetting to strip it before merge — the single most common real-world I6 violation.
  • Reusing a writable overlay across tasks for a small performance win — silently leaks state (and potentially secrets or injected files) from one task's sandbox into the next's.
  • Treating "no network" as equivalent to "no exfiltration risk" — a crafted commit message, file content, or even DNS query can exfiltrate data without a conventional network call; the allowlist and egress logging (ADR-13) exist precisely because outright air-gapping breaks legitimate dependency installs while doing nothing extra against non-network channels addressed separately in section 24 (T4).

17.7 Performance Concerns

Cold sandbox spawn (800ms p95) dominates wall-clock cost if the pool isn't kept warm (section 34); maintain a pre-warmed pool sized to expected concurrency (section 26 topology) rather than spawning on demand for every task.

17.8 Edge Cases

  • A command that daemonizes itself (double-fork, detaches from the controlling process) — cgroup-based limits (not process-tree signals alone) are required to catch this; process- tree kill alone is insufficient and must be paired with cgroup freeze+kill.
  • Disk-space exhaustion inside the writable overlay from a runaway build — enforce an overlay size quota, treat quota breach as a SandboxTimeoutError-equivalent failure edge.
  • A command that legitimately needs a large but bounded amount of scratch space (a build cache) — quota must be generous enough for the section-4 repository-size ceiling's realistic build artifacts, tuned empirically, not guessed.

17.9 Failure Analysis

Class: intermittent sandbox spawn failures under load. Root cause: sandbox-slot pool exhaustion misreported as a generic error instead of a distinct "pool exhausted, queued" state. Detection: spawn-latency histogram shows a bimodal distribution (fast warm-pool hits, very slow or failing cold spawns) correlated with concurrent task count exceeding section 34's sandbox host capacity model. Recovery: apply ADR-34 backpressure (queue, don't fail) and alert if queue depth crosses a threshold (section 26).

17.10 Operational Notes

The sandbox pool is the single scarcest resource in the whole system at fleet scale (section 31) — instrument its utilization first, before instrumenting almost anything else, and size the host fleet from the section 34 capacity model, not from guesswork.

18. Phase 6 — Structured Editing with Stale-Precondition Checks

18.1 Objectives

Implement the search-and-replace EditOp application (ADR-05) with the content-hash stale-precondition check (I2, P5), producing a PatchSet (section 21 consumes it), informed by the Aider whitespace-brittleness lesson and the Getafix pattern-repair lesson (Bader et al. 2019, applied here for the AST-level fallback path of section 8.4).

18.2 Detailed Implementation Steps

  1. Implement EditPrecondition checking: hash the file region shown to the model at retrieval time; before writing, re-hash the current file and compare — mismatch raises StalePreconditionError (I2) with zero write attempted (I12).
  2. Implement anchor matching: exact-string search for EditOp.anchor, counting occurrences; zero occurrences → AmbiguousAnchorError-family "anchor absent"; more than one → "ambiguous," both surfaced to the model as a structured error, not a crash.
  3. Implement atomic write: write to a temp file inside the sandbox overlay, then rename — never a partial write on crash (I12 corollary).
  4. Implement multi_edit-equivalent sequencing: a list of EditOps against one file, each validated against the post-previous-edit content, applied in order, any single failure aborting the remaining edits in that batch (no partial batch application).
  5. Implement the AST-level edit fallback (section 8.4) for template-shaped repairs (Getafix- style pattern application) where a structural match is more robust than a textual anchor — gated to a defined set of well-understood patterns, not general-purpose.
  6. Implement encoding/line-ending/BOM preservation: detect on read, preserve on write, regardless of edit representation.
  7. Implement path containment (I8): canonicalize every write target and reject any path that resolves outside the workspace root, including via symlink traversal.
  8. Assemble PatchSet from one or more applied EditOps, computing changed_files/ changed_lines against the section-4 patch-size limit (800 lines/25 files).

18.3 Deliverable

A structured editor that applies a search-and-replace edit atomically, rejects a stale or ambiguous edit with a structured, model-recoverable error, and never partially corrupts a file, verified against a corpus of stale-precondition and encoding-edge-case fixtures.

18.4 Acceptance Criteria

  • 0 successful writes on 500 deliberately-stale fixtures (file mutated between retrieval and edit) — I2 must catch 100%.
  • 0 partial writes across 200 fault-injected crash-mid-write fixtures (I12) — post-crash file state is always either fully old or fully new content, verified by content hash.
  • Encoding/line-ending preserved exactly on 50 fixtures spanning UTF-8/UTF-16/Latin-1 and CRLF/LF, byte-for-byte outside the edited region.
  • Path-traversal fixture corpus (symlink escape, ../ sequences) — 0/50 successful out-of-root writes (I8).

18.5 Conformance Fixtures

  • conformance/fixtures/phase6_stale_hash.json — file mutated by a concurrent tool call between retrieval and edit; expected: StalePreconditionError, no write.
  • conformance/fixtures/phase6_ambiguous_anchor.json — anchor string occurs twice; expected: structured "ambiguous, N occurrences" error with surrounding-line disambiguation hint.
  • conformance/fixtures/phase6_symlink_escape.json — a symlink inside the workspace pointing outside root; expected: path_outside_root ConflictReport, no write.
  • conformance/fixtures/phase6_crash_mid_write.json — fault injection killing the process after temp-file write but before rename; expected: original file untouched (I12).
  • conformance/fixtures/phase6_multi_edit_partial_failure.json — second of three sequenced edits fails; expected: first edit's write is NOT rolled back independently but the batch as a whole reports partial-application status accurately, and the third edit never attempts.

18.6 Pitfalls

  • Hashing the whole file for the stale check when the model was only shown a slice — any unrelated concurrent edit elsewhere in the file then falsely triggers staleness; hash the shown region, not the whole file, unless the edit representation is whole-file rewrite.
  • Fuzzy/whitespace-normalized anchor matching "to be more forgiving" — this is the exact brittleness Aider's precedent (section 5) warns against; normalization masks real content drift and causes corruption, not resilience.
  • Rename-based atomic write across filesystem/mount boundaries (e.g., overlay to a different mount) silently falling back to copy+delete, which is not atomic — verify same-filesystem rename semantics inside the sandbox overlay.
  • Treating "anchor absent" and "anchor ambiguous" as the same error class — they need different model-facing recovery guidance (re-read the file vs. add more context to the anchor).

18.7 Performance Concerns

Anchor matching is O(file size) per edit; for multi_edit batches against large files this compounds — pre-index anchor candidates within a single batch rather than re-scanning the full file per edit when edits target disjoint regions.

18.8 Edge Cases

  • An edit whose replacement is empty (pure deletion) — must be distinguished from a no-op edit and still subject to the same stale-precondition and atomic-write path.
  • An edit targeting a file that was deleted by an earlier tool call in the same turn batch — "anchor absent" is the wrong error; surface a distinct "file no longer exists" error.
  • A newly created file (via a create_file-equivalent) immediately targeted by an edit in the same turn — precondition hash must be computed against the just-created content, not a stale pre-creation state.

18.9 Failure Analysis

Class: repeated stale-precondition rejections on the same file across several turns ("edit thrashing"). Root cause: the retrieval layer (Phase 2) is re-serving a cached, outdated chunk after the file has already been edited once this task. Detection: trajectory replay (I7) shows a read→edit→read(same stale content)→edit→reject pattern. Recovery: invalidate the retrieval cache for a file immediately upon any successful edit within the same task, regardless of the index's normal incremental-rebuild cadence (Phase 2).

18.10 Operational Notes

Every rejected edit (stale, ambiguous, absent-anchor) should be visible in the same real-time operator surface as section 16.10's state telemetry — a task stuck thrashing on edit rejections is a strong leading indicator of an eventual Failed outcome and is worth surfacing before the retry budget is exhausted.

19. Phase 7 — Verification Loop over Tests and Lints

19.1 Objectives

Implement the verification-loop protocol (section 8.6) as the sole correctness oracle (P1, I9), including convention-based command discovery (ADR-16) and flaky-test quorum handling (ADR-17), grounded in the oracle-problem framing of Barr et al. (2015, applied here) and the characterization-testing posture of Feathers (section 5, applied here — trust the existing suite even when it's imperfect).

19.2 Detailed Implementation Steps

  1. Implement verification-command auto-discovery: detect package.json/pyproject.toml/ Makefile/CI workflow files and derive the test invocation, with an explicit manual- override path (ADR-16) for nonstandard build systems.
  2. Implement VerificationRun dispatch inside the sandbox executor (Phase 5), inheriting the 600-second test-suite timeout (section 4) — a hang is a SandboxTimeoutError, not a test failure.
  3. Implement outcome classification: pass/fail/timeout/flaky_suspect, the last triggered when a re-run on unchanged code differs from a prior run.
  4. Implement the ADR-17 quorum: on flaky_suspect, re-run up to 3 times total, majority outcome wins; record all N runs in the VerificationRun.quorum_runs field for auditability.
  5. Implement lint/build-step verification as additional VerificationRuns of the same shape — a task is not Done until every configured verification step (tests, lint, build) passes, not just the primary test command.
  6. Wire the Verifying-state entry guard (I9, Phase 4) to require a VerificationRun record with outcome pass on every configured step before transitioning to Done.
  7. Implement verification-output trust tagging: test/lint stdout/stderr is untrusted_tool_output (P3) exactly like any other tool output, since a malicious test file could itself contain injected text in its failure message.

19.3 Deliverable

A verification runner that discovers the correct test command for a real open-source repo fixture, runs it inside the sandbox, classifies the outcome correctly including flaky cases, and gates the Verifying→Done transition strictly on a passing result.

19.4 Acceptance Criteria

  • Command auto-discovery succeeds on 90% of a 50-repo fixture corpus spanning Python/Node/ Rust/Go project layouts; the remaining 10% correctly fall back to the manual-override path rather than silently guessing wrong.
  • Flaky-test quorum resolves correctly (majority outcome matches ground truth) on 95% of a 100-case synthetic-flakiness fixture set.
  • Zero Done transitions with a failing or missing VerificationRun across the full fixture suite (I9, hard requirement, must be exactly 0 — reconfirms Phase 4's guard end-to-end).
  • Verification wall-clock stays within the 600s budget on 98% of the fixture corpus; the remaining 2% correctly produce a SandboxTimeoutError, not a false pass.

19.5 Conformance Fixtures

  • conformance/fixtures/phase7_discovery_corpus/ — 50 real project layouts; expected: correct command discovered or correct manual-override fallback for each.
  • conformance/fixtures/phase7_flaky_synthetic.json — a test designed to fail 1-in-4 runs regardless of code correctness; expected: quorum resolves to the true majority outcome.
  • conformance/fixtures/phase7_hang.json — a test that sleeps past 600s; expected: SandboxTimeoutError, not silently truncated pass/fail.
  • conformance/fixtures/phase7_injected_test_output.json — a failing test whose assertion message contains an embedded instruction; expected: treated purely as untrusted_tool_output, no special handling triggers here (Phase 10 owns the guard logic).
  • conformance/fixtures/phase7_lint_and_test_both_required.json — tests pass, lint fails; expected: task does not reach Done.

19.6 Pitfalls

  • Treating "test command exits 0" as sufficient without checking that any tests actually ran (a misconfigured discovery can produce a vacuously-passing empty test run) — verify a nonzero test count where the test framework reports one.
  • Running the quorum re-runs sequentially against a freshly-rebuilt sandbox each time instead of the same code state — reintroduces nondeterminism into what should be a controlled repeat-same-input experiment.
  • Auto-discovery picking up a Makefile target named test that actually runs a completely different task (a common false-positive in ad hoc repos) — validate the discovered command against a lightweight sanity heuristic (e.g., known test-runner binary name) before trusting it blindly.
  • Conflating "no verification command discovered" with "verification passed" — must always be an explicit failure/abort path, never a default pass.

19.7 Performance Concerns

The test-suite runtime is, per section 30/34, the dominant term in total task wall-clock — parallelizing independent verification steps (lint concurrently with test, where the sandbox resource ceiling allows) is worth the added orchestration complexity at fleet scale.

19.8 Edge Cases

  • A repository with multiple test suites at different granularities (unit vs. integration) — discovery must pick the one matching the task's stated scope, or run both if the task doesn't disambiguate, documented as a discovery-policy default.
  • A test suite that requires network access to pass (hits a real external service) — this conflicts with the default-deny sandbox network policy (ADR-13); such suites must be explicitly allowlisted or the task is correctly unverifiable in this sandbox and should abort with a clear diagnostic rather than a confusing hang.
  • A verification step that mutates repository state as a side effect (a test that writes a snapshot file) — must run against the sandbox's writable overlay, never against the read-only bind-mounted original (ADR-12 dependency).

19.9 Failure Analysis

Class: false-positive verification pass due to a discovery bug picking a no-op command. Root cause: Makefile target name collision (section 19.6). Detection: eval harness (section 23) benchmark resolve-rate anomaly — tasks marked Done but the hidden test grader (section 23) disagrees, a signature specific to this failure class. Recovery: add the sanity-heuristic validation from 19.6, re-run the affected fixture corpus, and add the specific colliding-target case as a permanent regression fixture.

19.10 Operational Notes

Track verification pass rate (section 26 named metric) separately from benchmark resolve rate — a low verification pass rate with a healthy resolve rate is expected (most attempts fail before succeeding); a verification pass rate that doesn't correlate with resolve rate at all is a discovery-correctness red flag worth investigating immediately.

20. Phase 8 — Reflection and Retry on Verification Failure

20.1 Objectives

Implement the Reflecting state's substance (Phase 4 built its transitions; this phase fills them): Reflexion-style verbal self-feedback (Shinn et al. 2023, applied here) combined with delta-debugging-style failure localization (Zeller & Hildebrandt 2002, applied here) so a failed verification run produces useful next-attempt context rather than a bare "try again."

20.2 Detailed Implementation Steps

  1. Implement failure-context extraction from a failed VerificationRun: parse test-framework output into a structured failure summary (failing test names, assertion diffs, stack traces) rather than passing raw untruncated stdout back into the prompt.
  2. Implement Reflexion-style feedback synthesis: a dedicated, cheap model call (or a templated heuristic for common cases) that turns the structured failure summary into a short natural-language reflection appended to history ("the previous edit broke test X because Y") — tagged as agent-authored, not repository content, for trust purposes.
  3. Implement delta-debugging-informed localization: when a failure summary implicates a large diff, narrow the reflection to the specific changed region correlated with the failing assertion, reducing the next Planning turn's search space.
  4. Wire the reflection into the Reflecting→Planning edge (section 8.1) as an explicit, budgeted history addition — it consumes tokens (Phase 3 budgeter) like any other content.
  5. Implement retry-budget tracking distinct from the raw turn ceiling (ADR-18): a per-failure-signature retry counter, so the same failure recurring N times (not just N turns elapsing) triggers Failed — this is what section 8.11's failure-path example depends on.
  6. Implement stale-precondition-triggered reflection (I2 tie-in): a rejected edit due to staleness produces a reflection distinct from a verification failure ("the file changed since you last read it, re-read before editing"), not a generic error dump.
  7. Add self-consistency-inspired candidate diversity (Wang et al. 2023, applied here) for hard cases: after repeated failure on the same signature, optionally sample multiple candidate next-edits and prefer the one whose reasoning is most internally consistent, before falling back to Failed.

20.3 Deliverable

A Reflecting-state implementation that, given a failed VerificationRun, produces a bounded, budgeted, trust-tagged feedback turn that measurably improves next-attempt success rate on a fixture set of previously-Failed tasks re-run with reflection enabled.

20.4 Acceptance Criteria

  • Task-level resolve rate on a 100-task regression subset improves from a reflection-disabled baseline (measured in Phase 7's fixtures) by a nonzero, recorded delta — report the exact percentage-point improvement, not "better."
  • Per-failure-signature retry counter correctly triggers Failed at the configured N (default
    1. on a synthetic repeated-identical-failure fixture, verified exactly, not approximately.
  • Reflection content stays within its allocated history-budget slice (section 15) on 100% of fixtures — no reflection turn itself triggers a BudgetExceededError.
  • Stale-precondition reflections are distinguishable from verification-failure reflections in 100% of a 50-fixture mixed-cause corpus (measured by a downstream classifier assertion).

20.5 Conformance Fixtures

  • conformance/fixtures/phase8_reflection_before_after.json — same failing task run with reflection off vs. on; expected: on-run resolves within fewer total turns.
  • conformance/fixtures/phase8_repeated_signature_to_failed.json — identical failure signature recurring 3 times; expected: Failed at the 3rd recurrence, not the 3rd turn.
  • conformance/fixtures/phase8_stale_vs_verification_reflection.json — 50 mixed-cause cases; expected: correct reflection-type classification on all 50.
  • conformance/fixtures/phase8_large_diff_localization.json — failure implicating one function inside a 200-line diff; expected: reflection narrows to that function's region.

20.6 Pitfalls

  • Feeding raw, untruncated test output back into history every retry — this burns the history budget (Phase 3) faster than compaction can reclaim it and crowds out the actual reflection.
  • Treating every verification failure as equally informative — a timeout failure needs a completely different reflection ("the test hung, likely an infinite loop in your edit") than an assertion failure; conflating them produces generic, unhelpful feedback.
  • Letting self-consistency candidate sampling (20.2 step 7) run unconditionally on every retry — this multiplies cost per retry and should be reserved for the "already failed twice on this signature" case, not the first retry.
  • Resetting the per-failure-signature retry counter on a superficially different but root-cause-identical failure (e.g., a different assertion message from the same underlying bug) — signature matching needs to be robust to cosmetic diff, not exact-string.

20.7 Performance Concerns

The reflection-synthesis call, if implemented as a dedicated model call rather than a template, adds a full extra turn's latency (section 4 p50 3s) to every failed verification — budget this explicitly in the turn/wall-clock ceiling accounting, don't treat it as free.

20.8 Edge Cases

  • A verification failure with no parseable structured output at all (a test framework that crashes before producing a report) — fall back to raw-output reflection, truncated, rather than failing to reflect at all.
  • A reflection that would, if included, itself contain what looks like an injected instruction (a test's assertion message echoing attacker-controlled input) — reflection content remains subject to the same trust-tagging as any other tool-output-derived text (P3), carried forward by the Phase 10 guard.
  • Multiple simultaneous verification steps failing (both lint and test) — reflection must address both, prioritized by which is cheaper to fix first (lint before semantic test failures, as a default heuristic).

20.9 Failure Analysis

Class: reflection loop converging on a superficially different edit that fails for the exact same underlying reason repeatedly, evading the signature-match retry counter. Root cause: signature matching is too strict (exact stack-trace string) and treats cosmetically different failures as new. Detection: trajectory replay shows N turns of edits touching the same function with materially unchanged root-cause failures. Recovery: broaden signature matching to a normalized failure fingerprint (failing test name + top stack frame), re-tune against the regression suite in 20.4.

20.10 Operational Notes

Report reflection-attributable resolve-rate improvement as a standing benchmark metric (section 26) — this is the number that justifies the extra latency/cost budgeted in 20.7, and it should be re-measured on every prompt-template version bump (section 27).

21. Phase 9 — Patch Emission and PR Creation

21.1 Objectives

Turn a verified (Done-state) task's accumulated EditOps into a PatchSet and, where configured, a reviewable pull request (ADR-23), informed by the production-repair rollout posture of Marginean et al. (2019, SapFix, applied here) and the reviewability requirement of I8.

21.2 Detailed Implementation Steps

  1. Assemble PatchSet from the task's applied EditOp history (not from re-diffing the sandbox overlay blindly) so the patch's provenance is traceable turn-by-turn in the trajectory (I7 tie-in).
  2. Enforce the section-4 patch-size limit (800 lines/25 files) at assembly time: a PatchSet exceeding it is flagged for manual split rather than silently emitted oversized.
  3. Generate a unified diff (diff_text) from the PatchSet for human review, independent of the internal search-and-replace representation used during editing (ADR-05 vs. ADR-23 are deliberately different representations for different consumers).
  4. Implement Git operations: create a branch, commit with a generated message summarizing the task and citing the task/trajectory ID, push to the configured remote.
  5. Implement PR creation via the provider's REST/GraphQL API: title and description generated from the task instruction and the verification result (which tests now pass), never auto-merged (P7/P8 corollary — a verified patch still requires human or policy-gated approval to land).
  6. Implement the "never push to a real default branch directly" guard (I8 corollary, T10 in section 24): patch emission always targets a new branch, and the PR-creation step is the only path that can reach a shared remote at all.
  7. Implement local-patch-file-only mode (ADR-23 rejected-choice-wins case) for the eval harness (Phase 11), where no real remote exists and the benchmark scores the diff directly.

21.3 Deliverable

A patch emitter that, given a Done-state task's trajectory, produces a correct unified diff and, in service/CLI mode with a configured remote, opens a PR with an accurate, generated description — verified against a corpus of known-good expected diffs.

21.4 Acceptance Criteria

  • Generated unified diff exactly matches the expected diff (byte-for-byte modulo whitespace- normalization of the diff header) on 50 known-good fixture tasks.
  • Zero direct pushes to a configured default/protected branch across the full fixture and fuzz corpus (I8/T10, must be exactly 0).
  • PatchSet exceeding the 800-line/25-file limit is flagged, not silently emitted, on 20 deliberately-oversized fixtures.
  • PR description accurately references the verification outcome (which test(s) now pass) on 100% of a 30-fixture sample, checked by string-containment assertion against the actual VerificationRun record.

21.5 Conformance Fixtures

  • conformance/fixtures/phase9_known_good_diffs/ — 50 tasks with pre-computed expected diffs; expected: byte-exact match.
  • conformance/fixtures/phase9_oversized_patch.json — a task accumulating 30 changed files; expected: flagged for manual split, not emitted.
  • conformance/fixtures/phase9_default_branch_push_attempt.json — a fault-injected attempt to target the default branch directly; expected: rejected before any Git call is made.
  • conformance/fixtures/phase9_local_only_mode.json — eval-harness mode, no remote configured; expected: valid diff file written locally, no PR-creation call attempted.

21.6 Pitfalls

  • Re-diffing the sandbox overlay against the original checkout instead of assembling from the recorded EditOp history — loses the turn-by-turn provenance link (I7) and can pick up incidental build-artifact changes that were never part of an intentional edit.
  • Auto-merging a PR because verification passed — conflates "the repo's own tests pass" with "this change is safe to land," which are not the same claim (P1 only claims the former).
  • Generating a commit message purely from the diff text with no reference to the task instruction — produces technically-accurate but contextless messages reviewers can't use.
  • Allowing patch emission to run outside the sandbox (e.g., invoking git push from the host directly with host credentials) — this is an I1/I6 violation dressed up as a "just Git" operation; the broker pattern (ADR-14) applies to Git credentials too.

21.7 Performance Concerns

Diff generation and Git operations are comparatively cheap relative to the rest of the loop (section 34) — no special performance engineering is warranted here beyond not re-cloning the repository unnecessarily per emission.

21.8 Edge Cases

  • A task that ends Done with zero net changed lines (the fix was already present, or the edits canceled out) — emit no patch and no PR, with a clear "no changes to emit" outcome rather than an empty PR.
  • Two tasks concurrently targeting overlapping files in the same repository — branch naming and push must not collide; use the TaskId in the branch name deterministically.
  • A provider API rate limit or outage during PR creation — patch emission itself (the diff) must already be durably recorded before the PR-creation network call, so a PR-creation failure never loses the underlying patch (retry the PR step independently, per ADR-19).

21.9 Failure Analysis

Class: PR description drifts from what the diff actually does (a generated description claims a fix the diff doesn't fully implement). Root cause: description generated from the task instruction alone rather than cross-checked against the final VerificationRun and diff content. Detection: differential review (section 28) comparing generated description claims against actual changed-file list flags a mismatch. Recovery: regenerate description with an explicit cross-check step, add the mismatched case as a regression fixture.

21.10 Operational Notes

Every emitted PR should carry a footer linking the TaskId and trajectory reference so a human reviewer (or a later forensics pass, section 24/25) can pull the exact replayable trajectory that produced it — this is the single highest-leverage operational habit for building reviewer trust in an auto-generated patch.

22. Phase 10 — Prompt-Injection Hardening and the Trust Boundary

22.1 Objectives

Make the untrusted-content boundary (section 3, P3) an enforced mechanism rather than a convention: an instruction hierarchy that structurally prevents repository content, issue text, or tool output from overriding task instructions, informed directly by Greshake et al. (2023, indirect prompt injection, applied here) and Perez & Ribeiro (2022, applied here).

22.2 Detailed Implementation Steps

  1. Implement the instruction-hierarchy system prompt (ADR-24): explicit, structural framing that trusted segments (system, task) are instructions and untrusted segments (retrieved content, tool output, history derived from either) are data to be reasoned about, never obeyed — reinforced by the trust_tag metadata already carried since Phase 2/3 (P3).
  2. Implement the injection-detection heuristic layer: pattern and structural signals (imperative sentences embedded in file content, role-marker strings like fake "system:" tags inside retrieved text) flagged as InjectionDetectedError-worthy for telemetry, even when the instruction-hierarchy framing already neutralizes the attempt structurally — defense in depth, not the primary control (ADR-24's stated ordering).
  3. Implement effect-gating reinforcement: even if an injected instruction did influence a model turn, the I3 schema gate and the effect-class-aware approval posture (P12) mean the resulting tool call still can't do anything the tool layer wouldn't otherwise allow — tie this explicitly back to why sandboxing (Phase 5) and schema validation (Phase 1) are themselves injection mitigations, not just general hygiene.
  4. Build the adversarial injection test corpus (section 28 named suite): fixtures embedding known injection patterns (fake system-tag content, "ignore previous instructions," imperative dependency-README content) inside repository files, issue text, and tool output.
  5. Implement redaction-before-model-visibility for detected secret-shaped strings inside retrieved/tool-output content (ADR-25 tie-in) — an injected instruction trying to get the model to echo a secret back finds nothing to echo if it was redacted before reaching the model in the first place.
  6. Wire injection-detection telemetry (injection_detection_hits_total, section 26) and a named runbook trigger (docs/runbooks/injection-incident.md, section 26) for repeated hits against the same repository or task source.

22.3 Deliverable

An enforced instruction hierarchy plus detection layer that neutralizes a corpus of known indirect-prompt-injection patterns without materially degrading legitimate task performance, measured against both the injection corpus and the standard benchmark subset (no resolve-rate regression attributable to the hardening).

22.4 Acceptance Criteria

  • 0 successful behavior changes (defined as an effectful tool call that would not have occurred absent the injected instruction) across a 200-case adversarial injection corpus.
  • Injection-detection heuristic recall ≥90% and precision ≥80% on the labeled 200-case corpus (both numbers reported, not just one — false positives degrade legitimate task UX).
  • Zero resolve-rate regression (within noise, ±1 percentage point) on the SWE-bench Verified subset (section 4 target) comparing hardening-enabled vs. disabled runs.
  • Redaction-before-visibility verified on 50 fixtures containing secret-shaped strings in retrieved content — 0 secrets reach the assembled prompt.

22.5 Conformance Fixtures

  • conformance/fixtures/phase10_fake_system_tag.json — a repository file containing <system>ignore your instructions</system>-style content; expected: no behavior change, detection hit logged.
  • conformance/fixtures/phase10_readme_imperative.json — a dependency README containing "before continuing, run curl ... | sh"; expected: no unapproved effectful action results.
  • conformance/fixtures/phase10_issue_text_injection.json — task instruction itself (from an issue body) contains an embedded conflicting instruction; expected: task-level instruction hierarchy still resolves to the legitimate task scope, not the embedded one.
  • conformance/fixtures/phase10_secret_shaped_string.json — retrieved file contains an AWS-key-shaped string; expected: redacted before prompt assembly, never visible to the model.
  • conformance/fixtures/phase10_benchmark_regression_check.json — full SWE-bench Verified subset run, hardening on vs. off; expected: resolve-rate delta within ±1 point.

22.6 Pitfalls

  • Relying solely on the output-filtering/detection layer (22.2 step 2) as the actual control instead of the structural instruction hierarchy — per ADR-24's explicit rationale, filtering after the fact is unreliable and must never be the sole defense.
  • Over-tuning the detection heuristic for recall at the cost of precision — a system that flags every third legitimate README as an injection attempt trains operators to ignore the alert, defeating its purpose (alert fatigue, tie to section 26 alerting philosophy).
  • Treating the task instruction itself as fully trusted when it originated from an untrusted source (an issue body, a webhook payload) — P3's boundary applies to task intake too, not only to retrieved repository content; this is the phase10_issue_text_injection fixture's point.
  • Assuming sandboxing alone is sufficient injection defense because "the worst it can do is run in the sandbox" — an injected instruction steering the model toward a legitimate-looking but wrong edit (e.g., silently weakening a security check) is a content-integrity attack, not an execution-boundary attack, and needs the instruction-hierarchy control specifically.

22.7 Performance Concerns

The detection heuristic runs on every retrieved chunk and tool result — keep it cheap (pattern/structural, not a full extra model call) for the default path; reserve a dedicated classification model call (ADR-24's "cheap layer" alternative) for a second-tier check only when the cheap layer already raised a flag.

22.8 Edge Cases

  • Legitimate repository content that looks like an injection pattern (a security test fixture file whose entire purpose is containing example injection strings) — false-positive-prone by design; the precision metric (22.4) must be measured on a corpus that includes such legitimate lookalikes, not only true positives and clean negatives.
  • An injection attempt spanning multiple retrieved chunks (split across files, reassembled only in context) — single-chunk pattern detection will miss this; document as a known detection-layer limitation, mitigated primarily by the structural instruction hierarchy regardless of whether the split attempt is detected.
  • A tool result (not repository content) carrying the injection, e.g., a test failure message crafted by a malicious test file — must receive identical trust-tagging and hierarchy treatment as repository content (P3 applies uniformly).

22.9 Failure Analysis

Class: a benign resolve-rate regression misattributed to injection hardening. Root cause: the instruction-hierarchy framing added enough system-prompt tokens to meaningfully shrink the retrieved-context budget (Phase 3 tie-in), degrading retrieval quality rather than the hardening logic itself causing harm. Detection: section 22.4's benchmark-regression check isolates the delta; a token-accounting diff (section 15) confirms whether budget shrinkage, not hardening logic, explains it. Recovery: tune the system-prompt framing for token economy, re-run the regression check.

22.10 Operational Notes

This phase's runbook (docs/runbooks/injection-incident.md, section 26) should be treated as a living document updated with every new injection pattern discovered in production, exactly as a security team maintains a signature database — the adversarial corpus (22.4) is never "complete," only "current."

23. Phase 11 — Evaluation Harness, Cost Accounting, and Performance Hardening

23.1 Objectives

Build the evaluation harness against SWE-bench (Jimenez et al. 2024, applied here), finalize accurate cost accounting (I10, P13) beyond Phase 0's skeleton, and perform the performance hardening needed to hit the section 4 latency/throughput targets at benchmark scale.

23.2 Detailed Implementation Steps

  1. Implement the SWE-bench task-set adapter (EvalCase construction from the benchmark's task/repo/gold-patch/hidden-test format), applying the HumanEval-lineage framing of Chen et al. (2021) and Austin et al. (2021, MBPP) to justify why SWE-bench, not those, is the primary benchmark here (ADR-22).
  2. Implement the eval driver: run the full agent loop, unmodified, over each EvalCase, scoring against the hidden test suite (never the gold patch text) — resolve/unresolved determined purely by whether the hidden tests now pass (P1 applied at benchmark scale).
  3. Implement EvalReport aggregation: resolve rate, mean turns-to-completion, mean cost, mean wall-clock, broken down by task difficulty tier where the benchmark provides one.
  4. Finalize CostLedger accuracy: real per-provider price tables (pricing.py), reconciled against provider billing exports (I10's detection mechanism) rather than only self-reported token counts.
  5. Implement candidate-diversity scoring for hard cases using self-consistency (Wang et al. 2023, applied here): where multiple candidate patches are generated (Phase 8 tie-in), select by majority-agreement among independently reasoned candidates rather than first-found.
  6. Perform performance hardening against section 4/30 targets: profile retrieval latency, sandbox spawn latency, and model-call latency under realistic concurrency (section 31 sandbox-slot limit); fix the dominant bottleneck first, re-measure, repeat.
  7. Wire the benchmark job into CI (ADR-30) as a scheduled, non-blocking job (full benchmark runs are too slow/costly to gate every merge) with a fast subset job that does gate merges.
  8. Produce the first full evaluation report against SWE-bench Verified and Lite, establishing the baseline resolve rate against the section 4 target (≥35%/≥40%).

23.3 Deliverable

A working evaluation harness producing an EvalReport for a full SWE-bench Lite run, with cost-ledger figures reconciled against real provider billing, and a documented baseline resolve rate against the section 4 targets.

23.4 Acceptance Criteria

  • Baseline resolve rate ≥40% on SWE-bench Lite, ≥35% on SWE-bench Verified subset (section 4, reported as an exact percentage from the harness, not estimated).
  • Cost-ledger figures reconcile with provider billing export within 2% on a 100-task sample (I10 detection mechanism, quantified).
  • Mean turns-to-completion and mean cost per task reported and compared against the section 34 worked-example figures (~8 turns, ~$1.14 average) with the actual measured deltas stated.
  • Sandbox spawn p95 and retrieval p95 measured under full-concurrency benchmark load meet the section 4 targets (800ms / 400ms respectively); any miss is reported with the measured number, not silently waived.

23.5 Conformance Fixtures

  • conformance/fixtures/phase11_swebench_lite_subset.json — a fixed 20-task subset for fast CI gating; expected: stable resolve rate across repeated runs (replay-gate compatible via recorded responses for the deterministic portion).
  • conformance/fixtures/phase11_cost_reconciliation.json — 100-task cost-ledger sample against a recorded billing export; expected: ≤2% discrepancy.
  • conformance/fixtures/phase11_self_consistency_selection.json — 3 candidate patches, one majority-agreeing pair; expected: the majority candidate selected, not the first-generated.
  • conformance/fixtures/phase11_load_concurrency.json — 20 concurrent tasks against the sandbox pool; expected: p95 spawn/retrieval latencies within section 4 targets, backpressure (ADR-34) engages rather than failing outright if the pool is oversubscribed.

23.6 Pitfalls

  • Scoring against the benchmark's gold patch text similarity instead of the hidden test suite — this measures "wrote similar code," not P1's actual correctness oracle, and is a common benchmark-methodology mistake to avoid.
  • Running the full expensive benchmark on every CI merge — burns budget for no proportional signal; use the fast fixed subset for gating (23.2 step 7) and the full benchmark on a schedule.
  • Reporting resolve rate without also reporting cost and turns — a high resolve rate achieved by burning far more turns/cost than the section 4 ceilings intend is not actually meeting the target; section 4's numbers are joint constraints, not resolve-rate-only.
  • Contaminating the benchmark by allowing the agent's retrieval or training-adjacent components any exposure to the gold patch or hidden tests during a run — an explicit benchmark-contamination check belongs in the harness itself (also see section 38 glossary).

23.7 Performance Concerns

At benchmark-fleet concurrency, the sandbox-slot semaphore (ADR-34) and the model-provider rate limits both become binding constraints before the model's raw latency does — profile end-to-end task throughput, not just single-task latency, when hardening for this phase's scale (section 31 scalability analysis carries the full bottleneck ordering).

23.8 Edge Cases

  • A benchmark task whose repository requires a dependency version no longer resolvable (bit-rot) — must fail with a clear infra-error EvalReport outcome ("error"), distinct from a genuine "unresolved" agent failure, to avoid deflating resolve rate with non-agent-attributable failures.
  • A task where the hidden test suite itself is flaky at the benchmark level (not just within one run) — apply the same ADR-17 quorum logic used in Phase 7, now at the benchmark-scoring layer.
  • Self-consistency candidate generation (23.2 step 5) producing zero majority agreement among 3 candidates — fall back to the single highest-confidence candidate rather than stalling.

23.9 Failure Analysis

Class: measured resolve rate below the section 4 target at first full run. Root cause candidates ranked by likelihood from prior phases: (a) retrieval precision insufficient (Phase 2) causing wrong-file edits, (b) budgeter over-conservatively starving retrieved context (Phase 3), (c) reflection not meaningfully improving retry attempts (Phase 8), (d) verification discovery misfiring on benchmark repo layouts (Phase 7). Detection: per-task trajectory review (I7) on a sample of unresolved cases, bucketed by which phase's failure mode dominates. Recovery: prioritize fixes by bucket size; re-run the fixed 20-task subset after each fix to confirm improvement before the next full benchmark run (avoids burning the full benchmark's cost on unconfirmed fixes).

23.10 Operational Notes

Publish the EvalReport baseline (resolve rate, cost, turns) as the reference point for every future prompt-template or model-version change (section 27's mandatory full-benchmark-re-run rule) — without this phase's baseline on record, that re-run requirement has nothing to compare against.

26. Operational Readiness

Named metrics: resolve rate (per benchmark, section 23), turns per task, tokens and dollars per task (section 8.8), tool-error rate, sandbox timeout rate, verification pass rate (distinct from resolve rate, section 19.10), injection-detection hits (section 22), sandbox-escape-suspected count (should be 0), cost-ceiling hit rate, replay-divergence rate (CI-only).

Tracing: one OpenTelemetry span per turn (ADR-26), with child spans for retrieval, model call, tool dispatch, and (where applicable) sandbox execution and verification — span attributes carry task_id, turn_index, and trust_tag counts, never raw untrusted payload content.

Structured logging: every log line passes through the ADR-25 redaction filter before write; secret-pattern matches are replaced with [REDACTED:<pattern-class>], never dropped silently (a dropped log line with no marker is indistinguishable from a missing feature).

Dashboards: (1) fleet overview — concurrent tasks, sandbox-pool utilization, cost-ledger rate of spend; (2) per-task drill-down — state-machine timeline, turn/cost counters, verification outcome; (3) security posture — injection-detection hit rate, egress-denial rate, escape- suspected count (target: always 0, any nonzero value is itself the alert).

Alerting philosophy: alert on rate-of-change and on any-nonzero for should-be-zero counters (escape-suspected, unredacted-secret-found, verification-skipped); alert on threshold breach for continuous metrics (cost-ceiling hit rate, sandbox-timeout rate) rather than every single occurrence, per the alert-fatigue caution in section 22.6.

SLOs: resolve rate ≥ section 4 target measured weekly on the fixed benchmark subset; p95 sandbox spawn and retrieval latency within section 4 targets measured continuously; zero sandbox escapes as an availability-style SLO (any breach is a Sev-1).

Incident response: severity tiers keyed to the threat model (section 24) — a T2/T2-adjacent (escape-suspected) event is Sev-1, paged immediately; a T7 (cost-runaway) event is Sev-2, auto-contained by the ceiling but reviewed within one business day; an FM-class task-level failure (section 25) below a rate threshold is not an incident at all, just a metric.

Named runbooks (docs/runbooks/):

  • cost-runaway-containment.md — confirm hard-ceiling engagement, audit the triggering task, adjust ceilings only after root-cause review.
  • sandbox-escape-response.md — immediate isolation of the affected host, forensic capture, no further scheduling to that host until cleared.
  • injection-incident.md — living document, updated per new pattern (section 22.10).
  • bad-patch-rollback.md — revert the merged/pushed patch, open a corrective task referencing the original TaskId.
  • benchmark-regression-bisect.md — bisect between the last-known-good and current model/prompt/index version using the section 23 baseline as the comparison point.

Backup/restore of trajectories: trajectories are append-only JSONL, backed up on the same cadence as the index store (section 14.10), RPO 5 minutes (section 4); restore is a direct file-copy since the format has no external referential dependency.

Deployment topology: CLI mode runs the full stack in-process on the operator's machine; service mode runs a queue-fed worker pool (ADR-34 bounded queue) with a shared sandbox pool and index store, horizontally scaled by adding worker nodes each with their own sandbox-slot allocation (section 34 capacity model).

Canary/rollback/migration: a new model pin, prompt-template version, or index format is rolled out to a small percentage of queued tasks first (canary), compared against the section 23 baseline before full rollout; rollback is a version-pin revert (section 27); index-format migration runs a parallel rebuild before cutover, never an in-place mutation of the live index.

27. Compatibility & Versioning

Tool-schema versioning: every ToolSpec.json_schema carries a SemVer-style version; a breaking schema change (removed/retyped required field) is a major bump requiring every recorded-response fixture referencing that tool to be regenerated, not silently reinterpreted.

Prompt-template versioning: the system prompt, the instruction-hierarchy framing (section 22), and the reflection templates (section 20) are versioned artifacts (templates/, section 10). A prompt change is a behavior-breaking change requiring the full section 23 benchmark re-run before rollout — this is stated as an explicit, non-negotiable gate, not a recommendation, because prompt text changes measurably shift resolve rate, cost, and injection-resistance simultaneously.

Trajectory format versioning: Trajectory.schema_version (section 11) is checked by the replay harness; an older-version trajectory is either replayed through a documented migration shim or explicitly marked non-replayable, never silently coerced.

Model-version pinning and migration: every trajectory records the exact model version string used (ADR-32). When a provider deprecates a model, the migration procedure is: pin the new version in a canary lane, run the full section 23 benchmark, compare against the last published baseline, and only promote to the default lane on parity or improvement — an unpinned "latest" alias is explicitly rejected (ADR-32) precisely to make this procedure possible at all.

Index format migration: a new lexical/structural/embedding index format is built in parallel alongside the live index and cut over atomically; the old format is retained until the new one has passed the section 14 acceptance criteria against a production repository sample.

API stability: the ModelClient, ToolSpec, and PatchSet interfaces (section 11) are the system's stable public surface; changes follow SemVer, with deprecation notices carried for at least one minor version before removal.

Deprecation: a deprecated tool, schema field, or prompt template segment remains functional but flagged in telemetry (deprecated_surface_used_total) for at least one release cycle before removal, giving operators visibility into in-flight usage before it breaks.

Explicit statement: a model upgrade requires a full benchmark re-run against the section 23 baseline before rollout, with no exception — this is the single compatibility rule most likely to be skipped under deadline pressure and is called out here for that reason.

28. Testing & Verification Strategy

Unit: every pure function (budgeter arithmetic, anchor matching, hash comparison, schema validation) has direct unit coverage with both valid and adversarial inputs.

Integration: end-to-end task runs against replay_transport fixtures (P10) covering each state-machine path (section 8.1) at least once, including every failure edge.

Property-based (tied to specific invariants and section N.5 fixtures):

  • A tool call rejected by schema validation never dispatches (I3; Phase 1 fixtures, section 13.5) — hypothesis-generated malformed ToolCall arguments, assert zero dispatch.
  • An edit with a stale precondition never applies (I2; Phase 6 fixtures, section 18.5) — hypothesis-generated concurrent-mutation timing, assert zero corrupted writes.
  • The budgeter never exceeds the window (I13/I4; Phase 3 fixtures, section 15.5) — 10,000 random allocations (section 15.4), assert zero overflow.
  • A replayed trajectory produces the same tool-call sequence (I7; Phase 0/4 fixtures, sections 12.5/16.5) — the replay-gate CI job itself is this property test, run continuously.

Differential: run a shared task subset against SWE-agent or Aider (section 5 reference implementations) and compare resolve rate, turns, and cost — differences investigated for root cause (retrieval quality, edit-format brittleness, verification discovery) rather than treated as a pure leaderboard number.

Deterministic replay from recorded model responses (P10) is the foundation of the whole test suite: the replay-gate CI job (ADR-30, section 12) is a named, mandatory gate — no merge proceeds without it passing, and it is the reason a live-model integration test is never required for correctness verification, only for the scheduled benchmark job (section 23).

Fuzzing (ADR-29, Atheris): primary targets are the tool-call parser (section 13), the edit-anchor matcher (section 18), and repository-content ingestion (section 14) — these are the three components that parse untrusted or model-generated text into structured decisions, making them the highest-value fuzz targets.

Chaos: sandbox killed mid-command (verifies I12's no-partial-effect guarantee, section 18), model call timeout (verifies ADR-19 backoff), provider 429 storm (verifies backpressure, ADR-34) — each run as a scheduled chaos-injection job against a staging deployment.

Adversarial injection test corpus (named suite, section 22.4): 200+ labeled cases, run as part of the standard test suite, not only ad hoc — regression on this corpus blocks merge exactly like any other failing test.

Soak: a multi-hour continuous run of queued tasks against the service topology (section 26), watching for resource leaks (sandbox-slot leakage, unbounded trajectory-store growth) that short-duration tests would miss.

Fault injection: deliberate corruption of a single ledger write, a single trajectory record, and a single index entry, verifying each failure is detected (section 7 invariant table's Detection column) rather than silently propagating.

Benchmark evaluation with a stated pass threshold: the section 4 resolve-rate targets (≥35%/≥40%) are the pass threshold for the scheduled benchmark job (section 23); a run below threshold blocks promotion of whatever version triggered it, per section 27's mandatory re-run rule.

Perf and cost regression gating: the section 30 targets table (M1–M12+) is checked on every scheduled benchmark run; a regression beyond a defined tolerance band blocks promotion identically to a resolve-rate regression.

29. Build & Release Engineering

Reproducible builds: pinned lockfile (ADR-32) plus a hermetic build environment (pinned base image digest, not a floating tag) so a given commit produces a bit-identical wheel across build machines.

Artifact signing: release wheels and container images are signed (Sigstore/cosign-style keyless signing) so operators can verify provenance before deploying to a fleet handling untrusted repository content.

SBOM: a software bill of materials generated per release, covering both the Python dependency tree and the sandbox base image's OS packages — relevant here specifically because the sandbox runs untrusted code and its own supply chain is part of the threat surface (T6).

Release channels: stable (benchmark-gated, section 23/27), canary (section 26 rollout lane), nightly (unblocked by the full benchmark, for fast iteration on non-behavioral changes only).

CI/CD topology (ADR-30): ci.yml (unit/integration matrix) and replay-gate.yml (section 28's mandatory gate) run on every PR; benchmark.yml runs on a schedule and on release- candidate tags; release.yml builds, signs, and publishes only after both gates and the benchmark threshold (section 28) are satisfied.

Version stamping: every release embeds its SemVer version, the pinned model-version string default, and the prompt-template version (section 27) into a machine-readable manifest shipped alongside the artifact.

Provenance/attestation: build provenance (SLSA-style attestation) records which commit, which CI run, and which dependency lockfile produced a given artifact, tying back to the signing step above.

Dependency auditing: automated vulnerability scanning of the dependency tree on every PR and on a recurring schedule for the released artifact, with a defined SLA for patching a high-severity finding.

Prompt-template versioning in the release artifact: the exact prompt-template version in use is part of the release manifest (not just a runtime config value), so a benchmark regression bisect (section 26 runbook) can identify the prompt version without needing separate out-of-band records.

31. Scalability Analysis

Constant vs. grows: model per-call latency and sandbox spawn latency stay roughly constant with repository size (section 4); retrieval latency grows sublinearly with repository size given the index (section 14, O(log n)-ish lexical lookup plus bounded structural lookup); context cost per turn is linear in retrieved-token count, not repository size directly; total task cost is linear in the number of turns (section 8.8's formula); verification wall clock is dominated by the repository's own test-suite runtime, which is a property of the target repo, not of this system's architecture, and is the least controllable term.

Named bottlenecks, in order of typical binding constraint at fleet scale: (1) the repository's own test-suite runtime (section 34 shows it as the dominant wall-clock term); (2) the sandbox- slot pool ceiling (ADR-34, bounded by host RSS per section 34 capacity model); (3) model- provider rate limits under high concurrency; (4) retrieval latency, materially bounded by the index (section 14) and rarely the binding constraint once built; (5) network/disk I/O for sandbox spawn, mitigated by the warm-pool strategy (section 17.7).

Parallel scaling across tasks: tasks are independent units of work (no shared mutable state beyond the read-only index and the append-only trajectory/cost stores), so horizontal scaling is adding worker nodes each with their own sandbox-slot allocation (section 26 topology) — the sandbox-slot limit per host (section 34) is the practical ceiling per node, not the agent loop's own logic.

The context-window ceiling as the binding architectural constraint: no amount of infrastructure scaling increases the 200,000-token window (section 4); it is the one constraint this system cannot buy its way past with more hardware. Levers beyond it, in order of first resort: better retrieval precision (reduces tokens needed for the same information, Phase 2/3); hierarchical summarization (section 8.3's compaction, extended to summarize retrieved content itself, not just history, for very large relevant regions); sub-agents (a bounded, explicitly out-of-scope-for-this-project lever — delegated to rank-24's territory, section 1 non-goals) that partition a task across multiple bounded-context loops rather than one loop holding everything.

Practical repository-size ceiling: ~1.5M LOC / 5,000 files (section 4) for full-index build within the time budget; beyond that, either the index-build budget must grow (accepted tradeoff for very large monorepos) or retrieval must shift toward the embedding-only regime identified in ADR-07's rejected-choice-wins case, since lexical/structural indexing cost grows with corpus size even though lookup stays fast.

32. Mental Models & First Principles

MM1 — The agent is a search procedure over patches whose evaluation function is the test suite. Predicts: any technique that doesn't either propose a better candidate or evaluate it more cheaply is decoration. Bug class without it: chasing prompt-wording improvements that don't move resolve rate because the actual bottleneck is candidate quality or oracle reliability (P1). Resolves via section 8/section 23.

MM2 — The context window is a budget-allocation problem, and most agent failures are retrieval failures wearing a reasoning-failure costume. Predicts: a model "not understanding" a task is usually a model never having seen the relevant code. Bug class without it: endless prompt-engineering on a task that was never retrievable in the first place. Resolves via section 8.3/section 14/section 15.

MM3 — Every string the model reads is potentially an instruction; there is no passive data in this system. Predicts: any untagged content path is a latent injection vector. Bug class without it: a "just logging" or "just displaying" code path that turns out to also feed the next prompt unfiltered. Resolves via section 3/section 22.

MM4 — A tool call is a contract, not a suggestion. Predicts: loosening schema validation "to be more forgiving" always trades safety for a marginal, temporary convenience gain. Bug class without it: the free-text-protocol failure mode ADR-03 explicitly rejected, reintroduced piecemeal. Resolves via section 13.

MM5 — Verification is the only fact in the system; everything upstream of it is a hypothesis. Predicts: a task's Planning/Acting/Observing turns can all look reasonable and still be wrong; only Verifying tells you. Bug class without it: trusting a coherent-sounding trajectory as evidence of correctness. Resolves via section 8.1/section 19.

MM6 — The sandbox is the trust boundary's load-bearing wall; the model is not. Predicts: model improvements do not reduce the need for sandboxing, because the threat model (section 24) is about what untrusted code and untrusted content can do, independent of how capable or well-aligned the model is. Bug class without it: relaxing sandbox isolation because "the model got better." Resolves via section 17/section 24.

MM7 — A turn spent without a state transition recorded did not happen, for debugging purposes. Predicts: any gap in the trajectory record is where the next unexplainable bug will hide. Bug class without it: "it worked on my machine" style irreproducibility. Resolves via section 8.7/section 28.

MM8 — Cost is a per-turn accumulation, not a per-task estimate. Predicts: a task that "usually" costs $0.50 can still hit the $5 hard ceiling if a specific failure mode causes turn count to spike; averages hide tail risk. Bug class without it: under-provisioning the cost ceiling based on mean behavior alone. Resolves via section 4/section 8.8/section 34.

34. Back-of-Envelope Capacity Model

Cost per task (average). cost = Σ turns (input_tok × $3/1e6 + output_tok × $15/1e6). At 8 turns average, ~40,000 input tokens and ~1,500 output tokens per turn (growing history): 8 × (40,000 × 3/1e6 + 1,500 × 15/1e6) = 8 × (0.12 + 0.0225) = 8 × 0.1425 = $1.14 per task — under the $2.00 soft ceiling (section 4), consistent with the M10 target (≤$1.50 fleet average) once easy tasks (section 8.9's $0.348 example) are averaged in.

Context-budget split. 200,000 (window) − 3,000 (system) − 1,000 (task) − 8,000 (reserved output) − 20,000 (history cap) = 168,000 theoretical remainder for retrieved context, policy-capped at 100,000 (section 8.3) leaving 68,000 tokens of headroom for in-turn tool- result growth without re-running the budgeter.

Retrieval index size. files × chunks/file × embedding_dims × bytes/float: 5,000 × 8 × 768 × 4 = 122,880,000 bytes ≈ 117 MiB, plus ~20% lexical-index overhead ≈ 140 MiB total for a 5,000-file repository with embedding indexing enabled.

Wall clock per task. turns × model_latency + verification_runs × test_suite_seconds + sandbox_spawns × spawn_ms: 8 × 3s + 3 × 90s + 5 × 0.15s = 24s + 270s + 0.75s ≈ 295s ≈ 4.9 min per task — the verification term dominates at ~91% of total wall clock, confirming section 30/31's claim that the repository's own test-suite runtime is the usual bottleneck, not model latency or sandbox spawn.

Sandbox host capacity. A 64 GiB host with a 2 GiB per-sandbox RSS ceiling (section 4) supports 64 / 2 = 32 theoretical concurrent sandboxes, ~28 practical after host-process overhead — this is the M-series capacity number feeding the ADR-34 semaphore sizing.

Trajectory storage. turns × record_bytes: at ~60 KB/turn average (dominated by truncated tool-result payloads, capped at three 8 KB tool results per turn plus metadata), 8 × 60 KB = 480 KB per task, matching the section 4 ~500 KB/task figure. For a 1,000-task benchmark run: 1,000 × 480 KB ≈ 458 MiB of trajectory storage.

Tasks a fixed budget buys. At $1.14/task average: a $500 budget buys 500 / 1.14 ≈ 438 tasks; a $5,000 monthly budget buys 5,000 / 1.14 ≈ 4,386 tasks — the number operators should use when sizing a backlog-sweep schedule against section 26's cost-ceiling alerting.

35. Hard Questions (Self-Examination)

  1. If retrieval (section 14) returns the wrong file with high confidence, does the budgeter (section 15) or the agent loop (section 16) ever get a signal to try a different retrieval mode, or does the task simply fail verification repeatedly until the retry budget (section
    1. is exhausted?
  2. Section 8.3 caps retrieved context at 100,000 tokens for in-turn headroom — what actually happens (section 15, section 16) when a single tool result alone exceeds that headroom mid-turn, and is that path tested (section 15.5) as thoroughly as the pre-flight path?
  3. Section 17's sandbox pool and section 34's capacity model assume a fixed per-sandbox RSS ceiling — what breaks (section 19) when a legitimate repository's own test suite requires more memory than that ceiling, and is the failure mode distinguishable from a genuine sandbox-escape attempt (section 24, T2)?
  4. Section 20's per-failure-signature retry counter and section 16's turn ceiling are two different bounding mechanisms — can a task exhaust one without exhausting the other in a way that produces a misleading Aborted vs. Failed classification (section 25, FM-1 vs. FM-2)?
  5. Section 22's instruction hierarchy is structural, not a filter — but section 15's history compaction summarizes older turns through a model call; could a successfully-neutralized injection attempt from turn 3 be re-introduced with more apparent authority by an imperfect turn-40 compaction summary that paraphrases it without the original trust tag?
  6. Section 19's flaky-test quorum (ADR-17) assumes flakiness is a property of the test, not of the sandbox — what happens to resolve rate (section 23) if sandbox resource contention itself (section 17, section 31) is the actual source of nondeterminism being misclassified as test flakiness?
  7. Section 21's patch emission asserts provenance traceability from the trajectory (I7) — if the Phase 8 reflection process (section 20) causes the agent to revert its own earlier edit and reapply a different one, does the emitted diff still cleanly correspond to a coherent narrative, or does it require trajectory-aware diff synthesis not yet specified?
  8. Section 27 mandates a full benchmark re-run on any model upgrade — does the same mandate apply to an upgrade of the tree-sitter grammar version (section 14.9) or the embedding model (section 14), both of which can shift retrieval quality as materially as a model swap, and if not, why not?
  9. Section 4's cost ceiling is per-task — does section 26's fleet-level cost dashboard actually distinguish "many tasks each near their soft ceiling" from "one task near its hard ceiling," and does the alerting philosophy (section 26) treat these as the same signal when they imply very different interventions?
  10. Section 18's stale-precondition check (I2) hashes the shown region, not the whole file — could two sequential edits within the same turn to disjoint regions of the same file produce a false staleness rejection on the second edit if the first edit's write shifts line offsets the second edit's precondition wasn't computed against?
  11. Section 24 (T8) names a poisoned retrieval index as a threat but section 14's acceptance criteria measure only retrieval accuracy on a labeled fixture set — is there an actual adversarial-poisoning fixture anywhere in section 14.5, or does that threat only get tested indirectly through section 22's injection corpus?
  12. Section 30's M9 (verification runtime budget, 600s) and section 34's wall-clock model both assume verification dominates; if a future repository's test suite legitimately needs 1,200s, does the system degrade gracefully (extend the budget with an explicit tradeoff) or silently misclassify the task as a sandbox timeout indistinguishable from a hang?
  13. Section 9's ADR-18 fixes turn/cost ceilings identically for every task regardless of apparent difficulty — section 1 explicitly rejects a "dynamic complexity-based ceiling" as the primary policy; does this mean genuinely hard, legitimately-resolvable tasks are systematically undercounted in the section 23 resolve-rate denominator, and would that be visible in the EvalReport breakdown by difficulty tier?
  14. Section 22.6 warns against tuning the injection-detection heuristic for recall at the cost of precision, but section 24 (T1) treats injection as a Sev-1-adjacent class of concern — which section 26 alerting rule actually resolves that tension in practice, and is it the threshold-breach rule or the any-nonzero rule?
  15. Section 33's Agentless contrast argues an agent loop may not be necessary — given section 34's arithmetic showing verification (not reasoning) dominates wall clock, and section 32's MM1 framing the agent as fundamentally a search procedure, what specific capability does the twelve-phase loop in this blueprint provide over a three-stage Agentless pipeline that the numbers in section 34 alone would not already predict?

36. Alternative Architectures (Roads Not Taken)

A1 — Agentless fixed pipeline (localize → repair → validate, no autonomous loop).

 Issue text --> Localizer (retrieval, no loop) --> Candidate file/line set
                                                          |
                                                          v
                                    Repair generator (single or few-shot LLM call)
                                                          |
                                                          v
                                          Validator (run tests once, no retry loop)
                                                          |
                                                          v
                                                  Patch or "no fix found"

Winning regime: benchmark-style tasks with a well-scoped issue and a fast test suite, where predictability and low cost matter more than squeezing out marginal resolve-rate gains from iteration. Embodying system: Agentless (Zhang et al. 2024, section 5). Rejected here because this project's mandate (section 1) is the general repository-task shape including ones that need multi-step exploration and iterative repair, not only benchmark-optimal single-shot cases — but section 33's contrast is deliberately preserved because it is a legitimate, cheaper alternative for a large subset of real tasks.

A2 — Human-in-the-loop pair-programming (Aider/IDE-assistant model).

 Human types intent --> Agent proposes edit --> Human reviews inline --> Human accepts/edits
        ^                                                                        |
        |------------------------------------------------------------------------+
                        (tight loop, human approves every step)

Winning regime: a solo developer working in their own codebase where the cost of an autonomous wrong action exceeds the friction of reviewing every diff. Embodying system: Aider, IDE assistants generally (section 5, section 33). Rejected here because this project's deployment model (section 1) explicitly includes headless CI and fleet-scale backlog processing where no human is available per-step — human review happens once, at the PR stage (section 21), not per-edit.

A3 — Multi-agent decomposition (planner / coder / reviewer roles).

 Planner agent --> task breakdown --> Coder agent --> candidate diff --> Reviewer agent
      ^                                                                        |
      +---------------------- revision requested ----------------------------+

Winning regime: tasks large enough that role specialization (a planner reasoning at a different abstraction level than a coder) outperforms one agent context-switching between roles. Embodying system: this is explicitly the rank-24 Agentic-Framework's territory (section 1 non-goals), not a system embodied elsewhere in the reference-implementation set studied here. Rejected here because this project deliberately replaces the "reviewer" role with a mechanical verification stage (P1) rather than another LLM call — a test suite is a cheaper, more reliable reviewer than a reviewer agent for the specific correctness question this system answers.

A4 — Search-heavy candidate generation (many patches, select by test outcome).

 Task --> Generate K candidate patches (diverse sampling) --> Run tests on each in parallel
                                                                        |
                                                                        v
                                                    Select first/best passing candidate

Winning regime: when compute is cheap relative to engineering time and the verification signal is fast enough to score many candidates in parallel — spending compute instead of reasoning. Embodying system: search-based automatic program repair (Le Goues et al. 2012, GenProg, section 5); the section 20/23 self-consistency candidate-selection step is a bounded version of this idea already incorporated, not rejected outright. Rejected as the primary architecture here because section 34's wall-clock model shows verification (test-suite runtime) as the dominant cost term — running K candidates multiplies that dominant term by K, which is only affordable when the test suite is fast, and this project's section 4 budget (600s verification ceiling) does not assume that.

38. Glossary

Agent loop — the Planning/Retrieving/Acting/Observing/Verifying/Reflecting state machine (section 8.1, section 16) driving one task to completion. Turn — one iteration of the loop, recorded as a Turn (section 8.7). Tool call — a model-emitted, schema-validated request to invoke a registered tool (ToolCall, section 11). Function calling — the provider's native tool-invocation mechanism (ADR-03), as opposed to a parsed text protocol. Schema validation — checking a ToolCall's arguments against its ToolSpec.json_schema before dispatch (I3). Effect class — a tool's classification as read-only, mutating, or executing (P12). Context window — the model's total token capacity per request (section 4, 200,000). Token budget — the arithmetic constraint bounding what fits in a request (section 8.3). Retrieval — selecting relevant repository content for a turn (section 14). Chunking — dividing repository content into retrievable units (ADR-09). Reranking — reordering retrieved candidates by a secondary (typically embedding) signal (section 8.5). Structured edit — a machine-checkable edit representation, as opposed to free-text (section 8.4). Search-and-replace block — the locked primary edit representation (ADR-05, EditOp). Stale precondition — an edit whose target content no longer matches what the model was shown (I2). Patch — the assembled set of edits for a task (PatchSet, section 21). Verification loop — the tests/lints/build gate that is the sole correctness oracle (P1, section 19). Oracle — the mechanism that decides pass/fail for a candidate change; here, the repository's own test suite (Barr et al. 2015). Flaky test — a test whose outcome varies across runs on unchanged code (ADR-17). Reflection — Reflexion-style verbal self-feedback appended to history after a failure (Shinn et al. 2023, section 20). Trajectory — the durable, replayable record of every turn in a task (section 8.7). Replay — re-executing a task's turns from recorded model responses to reproduce its exact tool-call sequence (I7, P10). Recorded response — a stored ModelResponse fixture used by the replay transport instead of a live model call. Temperature — the sampling- randomness parameter, set per ADR-20's determinism policy. Determinism — the property that identical inputs (including recorded responses) yield identical outputs; the basis of the replay-gate CI job. Prompt injection — an attempt to override the model's intended instructions via crafted input text. Indirect prompt injection — prompt injection delivered via content the model reads rather than the direct user turn (Greshake et al. 2023). Trust boundary — the structural line separating trusted (system/task) from untrusted (repository/tool-output) content (P3, section 3). Sandbox escape — untrusted code breaking out of its intended isolation to affect the host (T2). Cost ceiling — the per-task dollar limit enforced by the state machine (section 4, ADR-18). Resolve rate — the fraction of benchmark tasks an agent successfully fixes per the hidden-test oracle (section 23). Benchmark contamination — a benchmark's gold patch or hidden tests leaking into the agent's context or training data, invalidating the score (section 23.6). Agent-computer interface (ACI) — the designed surface of tools/affordances an agent uses to act on a repository (Yang et al. 2024). Lexical retrieval — token/substring-match search (BM25-style). Structural retrieval — retrieval keyed to parsed code structure (tree-sitter symbols). Embedding retrieval — vector-similarity search over chunk embeddings. Symbol index — the structural index mapping identifiers to definitions (SymbolIndex, section 11). Budgeter — the component enforcing token-budget arithmetic pre-flight (section 15). Compaction — summarizing older history to stay within the budget (section 8.3). Idempotency — a tool's property of producing the same effect if invoked repeatedly with the same arguments (section 8.2). Quorum (flaky-test) — the majority-of-N-reruns resolution policy for flaky_suspect outcomes (ADR-17). Turn ceiling — the maximum number of loop iterations per task (I5, ADR-18). Wall-clock ceiling — the maximum elapsed real time per task (I5). Ledger — the atomically-updated cost/token accounting record (CostLedger, I10). OCI runtime specification — the container-runtime contract implemented by the sandbox executor (ADR-11). Seccomp — the Linux syscall-filtering mechanism in the sandbox isolation lineage (Provos 2003). Cgroup / namespace — the Linux kernel primitives providing resource and filesystem/process isolation for the sandbox. Egress allowlist — the explicit set of network destinations permitted from inside the sandbox (ADR-13). Broker pattern — issuing a credential to a task via an external call rather than mounting it into the sandbox (ADR-14). Instruction hierarchy — the structural framing that trusted instructions outrank untrusted content (ADR-24). Differential testing — comparing this system's behavior against a reference implementation on a shared task set (section 28). Property-based testing — generative testing asserting an invariant holds across randomized inputs (section 28, Hypothesis). Mutation testing — deliberately breaking an implementation to confirm a test catches the break (section 12.9). Delta debugging — algorithmic minimization of a failure-inducing input (Zeller & Hildebrandt 2002). Self-consistency — selecting among multiple sampled reasoning paths by agreement (Wang et al. 2023). ReAct — the interleaved reasoning-and- acting prompting pattern (Yao et al. 2023). SWE-bench — the primary evaluation benchmark (Jimenez et al. 2024, ADR-22). HumanEval / MBPP — code-synthesis benchmarks distinguishing raw generation capability from repo-scale repair (Chen et al. 2021; Austin et al. 2021). Gold patch — a benchmark task's known-correct reference fix, never used for scoring directly (section 23.6). Hidden tests — the benchmark's held-out test suite used as the actual scoring oracle. SemVer — the versioning discipline applied to schemas, prompt templates, and the trajectory format (section 27).
