ADR-01

Language

Chosen

Python 3.11+

Rejected

TypeScript/Node; Rust; Go

When the rejected choice is right

Rust wins for a latency-critical, dependency-free sandbox daemon shipped as a single static binary

Why: LLM/tree-sitter ecosystem maturity, matches reference impls (section 5)

ADR-02

Model-provider abstraction

Chosen

Internal ModelClient protocol wrapping vendor SDKs

Rejected

Direct hardcoded SDK; LangChain; LiteLLM proxy

When the rejected choice is right

LiteLLM proxy wins when the org already runs a centralized multi-tenant LLM gateway for many non-agent apps

Why: Single interface point for retry/cost/replay

ADR-03

Tool-calling mechanism

Chosen

Native function-calling (provider tool-use API)

Rejected

Parsed text protocol (ReAct-style); Toolformer-style inline calls

When the rejected choice is right

A text protocol wins targeting a model with no native function-calling fine-tuning

Why: Reduces malformed-action rate (Yao et al. 2023)

ADR-04

Tool schema format

Chosen

JSON Schema

Rejected

Protobuf schema; ad hoc dict validation

When the rejected choice is right

Protobuf wins when the tool layer must interoperate with a protobuf-standardized RPC mesh

Why: Shared with provider tool-use APIs; mature validators

ADR-05

Edit representation

Chosen

Search-and-replace block, unique anchor

Rejected

Whole-file rewrite; unified diff; AST-level edit

When the rejected choice is right

Whole-file rewrite wins editing a small (<200-line) config/generated file

Why: Robust to hallucinated line numbers (Aider precedent)

ADR-06

Stale-edit detection

Chosen

Content-hash precondition (SHA-256 of shown region)

Rejected

mtime check; no check

When the rejected choice is right

mtime-only wins in a single-writer offline batch mode with measured hashing bottleneck

Why: mtime granularity/clock skew unreliable

ADR-07

Retrieval strategy

Chosen

Hybrid lexical + structural, optional embedding rerank

Rejected

Embedding-only; structural-only

When the rejected choice is right

Embedding-only wins on natural-language issue text against a 500K-file monorepo where grep is impractical

Why: Lexical is cheap/precise for identifiers; embeddings recover semantic queries

ADR-08

Index representation

Chosen

Rejected

When the rejected choice is right

36. Alternative Architectures (Roads Not Taken)

A1 — Agentless fixed pipeline (localize → repair → validate, no autonomous loop).

 Issue text --> Localizer (retrieval, no loop) --> Candidate file/line set
                                                          |
                                                          v
                                    Repair generator (single or few-shot LLM call)
                                                          |
                                                          v
                                          Validator (run tests once, no retry loop)
                                                          |
                                                          v
                                                  Patch or "no fix found"

Winning regime: benchmark-style tasks with a well-scoped issue and a fast test suite, where predictability and low cost matter more than squeezing out marginal resolve-rate gains from iteration. Embodying system: Agentless (Zhang et al. 2024, section 5). Rejected here because this project's mandate (section 1) is the general repository-task shape including ones that need multi-step exploration and iterative repair, not only benchmark-optimal single-shot cases — but section 33's contrast is deliberately preserved because it is a legitimate, cheaper alternative for a large subset of real tasks.

A2 — Human-in-the-loop pair-programming (Aider/IDE-assistant model).

 Human types intent --> Agent proposes edit --> Human reviews inline --> Human accepts/edits
        ^                                                                        |
        |------------------------------------------------------------------------+
                        (tight loop, human approves every step)

Winning regime: a solo developer working in their own codebase where the cost of an autonomous wrong action exceeds the friction of reviewing every diff. Embodying system: Aider, IDE assistants generally (section 5, section 33). Rejected here because this project's deployment model (section 1) explicitly includes headless CI and fleet-scale backlog processing where no human is available per-step — human review happens once, at the PR stage (section 21), not per-edit.

A3 — Multi-agent decomposition (planner / coder / reviewer roles).

 Planner agent --> task breakdown --> Coder agent --> candidate diff --> Reviewer agent
      ^                                                                        |
      +---------------------- revision requested ----------------------------+

Winning regime: tasks large enough that role specialization (a planner reasoning at a different abstraction level than a coder) outperforms one agent context-switching between roles. Embodying system: this is explicitly the rank-24 Agentic-Framework's territory (section 1 non-goals), not a system embodied elsewhere in the reference-implementation set studied here. Rejected here because this project deliberately replaces the "reviewer" role with a mechanical verification stage (P1) rather than another LLM call — a test suite is a cheaper, more reliable reviewer than a reviewer agent for the specific correctness question this system answers.

A4 — Search-heavy candidate generation (many patches, select by test outcome).

 Task --> Generate K candidate patches (diverse sampling) --> Run tests on each in parallel
                                                                        |
                                                                        v
                                                    Select first/best passing candidate

Winning regime: when compute is cheap relative to engineering time and the verification signal is fast enough to score many candidates in parallel — spending compute instead of reasoning. Embodying system: search-based automatic program repair (Le Goues et al. 2012, GenProg, section 5); the section 20/23 self-consistency candidate-selection step is a bounded version of this idea already incorporated, not rejected outright. Rejected as the primary architecture here because section 34's wall-clock model shows verification (test-suite runtime) as the dominant cost term — running K candidates multiplies that dominant term by K, which is only affordable when the test suite is fast, and this project's section 4 budget (600s verification ceiling) does not assume that.
