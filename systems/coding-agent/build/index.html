⬜ Phase 0 — Skeleton, Model-Client Interface, Recorded-Response Replay, CI §12

Objectives

Stand up the project skeleton, the ModelClient provider interface (ADR-02), the recorded- response replay transport that makes every later test deterministic (P10), and a CI pipeline that runs the replay gate before any feature work begins. Nothing in this phase talks to a sandbox or edits a repository; it is pure plumbing.

Deliverable

A agent run --dry-run <task-spec> command that parses a task spec, sends exactly one request through replay_transport, records one Turn, and exits — with the replay-gate CI job green.

Acceptance
  • make replay-gate passes with zero live-network calls (verified by a network-block test fixture that fails the build if a socket is opened).
  • Trajectory file for the dry-run contains exactly one Turn record matching the schema in section 8.7.
  • Replay of the recorded fixture fixtures/phase0/basic_reply.json reproduces an identical tool-call sequence (I7) across 10 consecutive CI runs.
  • Cold CI run completes in under 90 seconds.
Fixtures
  • conformance/recorded_responses/phase0_basic_reply.json — one-turn plain-text response; expected: one Turn record, stop_reason="end_turn".
  • conformance/recorded_responses/phase0_malformed_json.json — a response body that is not valid JSON; expected: ModelClient raises a typed parse error, not an unhandled exception.
  • conformance/fixtures/phase0_taskspec_minimal.yaml — smallest valid TaskSpec; expected: parses without error.
  • conformance/fixtures/phase0_taskspec_missing_repo_ref.yaml — expected: schema-validation failure at parse time, not at first use.
Pitfalls
  • Hardcoding the live provider client into the agent loop instead of behind ModelClient — makes P10 impossible to retrofit later without a rewrite.
  • Keying replay fixtures by exact request string instead of a normalized hash — any harmless whitespace change in the system prompt then breaks every fixture.
  • Treating the trajectory writer as a logging convenience instead of the source of truth — later phases silently skip recording under error paths if this isn't enforced from turn one.
  • CI "passing" because the replay-gate job never actually exercised replay divergence detection — always include one fixture designed to catch a broken replay path.

⬜ Phase 1 — Tool Layer with Schema Validation §13

Objectives

Build the ToolSpec/ToolCall/ToolResult layer (section 11) and the JSON Schema gate (I3) that stands between every model output and any effectful action, following the agent-computer-interface lesson of Yang et al. (2024, SWE-agent — applied here per section 5) and the tool-learning framing of Schick et al. (2023, Toolformer).

Deliverable

A tool registry that dispatches read_file and search end-to-end from a validated ToolCall to a trust-tagged ToolResult, with 100% of dispatch attempts passing through the I3 schema gate (enforced by a single dispatch entry point, verified by static call-site audit).

Acceptance
  • Zero tool dispatches bypass schema validation across the full Phase 1 fixture suite (schema_validation_failures_total counter increments correctly on every injected bad call).
  • A malformed ToolCall (missing required field) never reaches a tool implementation — verified by a mock tool implementation that raises if invoked directly.
  • Parser correctly extracts tool calls from 20/20 fixtures spanning plain-text, reasoning- prefixed, and multi-tool-call-in-one-turn response shapes.
Fixtures
  • conformance/fixtures/phase1_invalid_schema_missing_path.json — read_file call missing path; expected: SchemaValidationError, no dispatch.
  • conformance/fixtures/phase1_react_trace.json — reasoning text + tool call in one response (Yao et al. 2023 shape); expected: tool call extracted correctly, reasoning text discarded from the effectful path.
  • conformance/fixtures/phase1_no_action.json — plain prose with no tool call; expected: Planning→Reflecting transition per section 8.1.
  • conformance/fixtures/phase1_multi_call_one_turn.json — two tool calls in one response; expected: both validated and dispatched in order, both results returned in one Observing step.
Pitfalls
  • Validating "most" arguments but trusting a free-text command-shaped field unchecked — this reintroduces exactly the free-text-protocol risk ADR-03 rejected.
  • Allowing a second code path (e.g., a "quick tool" shortcut) that skips the registry — guarantees an eventual I3 violation; enforce a single dispatch chokepoint.
  • Over-trusting StopReason — a stop_reason="tool_use" with an empty tool_calls list must be treated as a parser/provider anomaly, not silently skipped.

⬜ Phase 2 — Repository Indexing and Retrieval §14

Objectives

Build the lexical, structural (tree-sitter), and optional embedding indexes (ADR-07, ADR-08, ADR-09) and the retrieval query path, entirely mechanical and model-free, producing RetrievedChunks tagged untrusted_repo_content (P3) for the Phase 3 budgeter to consume.

Deliverable

agent index build <repo> produces a durable SQLite index within the section 4 time budget, and search() returns ranked RetrievedChunks for lexical and structural modes on a real open-source repository fixture.

Acceptance
  • Index build on a 1.5M-LOC fixture repo completes in <120s (lexical+structural), matching section 4; embedding-enabled build completes in <420s total.
  • find_symbol-shaped structural query returns the correct definition location in ≥95% of a 200-query labeled fixture set.
  • Retrieval p95 latency <400ms hybrid (lexical+structural) per section 4, measured over 500 queries against the fixture repo.
  • Incremental re-index after a single-file edit completes in <2s (not a full rebuild).
Fixtures
  • conformance/fixtures/phase2_labeled_symbol_queries.json — 200 (query, expected file:line) pairs across 3 languages; expected: ≥95% correct.
  • conformance/fixtures/phase2_gitignore_respect.json — repo fixture with a node_modules/ tree; expected: zero indexed files under it.
  • conformance/fixtures/phase2_incremental_delta.json — before/after file edit; expected: only the changed file's chunks are re-indexed.
  • conformance/fixtures/phase2_injection_readme.json — a README.md containing an embedded instruction ("ignore prior instructions..."); expected: indexed and retrievable like any other content, tagged untrusted_repo_content — indexing must not "notice" or act on it, only tag it (that judgment belongs to Phase 10, section 22).
Pitfalls
  • Chunking by fixed line windows for source code — routinely splits a function in half, degrading both retrieval precision and edit-anchor availability downstream (ADR-09).
  • Treating tree-sitter parse failures (syntax errors in a work-in-progress file) as fatal — degrade gracefully to lexical-only for that file instead of aborting the whole index build.
  • Letting embedding-index build time silently balloon the section-4 index-build budget when enabled by default — keep it opt-in (ADR-07).
  • Re-embedding the entire repo on every task instead of incrementally — defeats the point of a persistent index.

⬜ Phase 3 — Context Budgeter and Prompt Assembler §15

Objectives

Implement the token-budget arithmetic of section 8.3 as a pre-flight, provable check (P6, P14, I4, I13) and the prompt assembler that produces a trust-tagged PromptAssembly — the last stop before repository content and history reach the model.

Deliverable

A PromptAssembly builder that, given a TaskSpec and a set of RetrievedChunks, either returns a valid assembly with sum(allocation) <= window provably true, or raises BudgetExceededError with no partial prompt ever sent.

Acceptance
  • Property test (section 28): for 10,000 randomly generated allocations, the budgeter never returns an assembly exceeding the 200,000-token window (I13, zero violations required).
  • History compaction triggers correctly at the 20,000-token cap on a fixture conversation of 60 synthetic turns, preserving the most recent 6 turns verbatim in 100% of runs.
  • Token counts computed by the budgeter match the provider's own reported usage field within 1% on a 50-fixture regression set (accounting for the estimate-before-response gap).
Fixtures
  • conformance/fixtures/phase3_overflow_allocation.json — retrieved context deliberately sized to overflow the window; expected: BudgetExceededError, no request sent.
  • conformance/fixtures/phase3_compaction_60_turns.json — 60-turn synthetic history; expected: compacted to ≤20,000 tokens, last 6 turns verbatim, all open tool threads intact.
  • conformance/fixtures/phase3_trust_tag_roundtrip.json — assembly containing both trusted (system) and untrusted (retrieved) segments; expected: trust tags survive serialization to the trajectory record unchanged.
Pitfalls
  • Estimating tokens with len(text) // 4 instead of the real tokenizer — the estimate error is exactly the kind of silent I4 violation that only shows up as a provider-side context- overflow error mid-task.
  • Compacting history but losing track of an "open" tool-call thread (a shell call whose result hasn't been observed yet) — the model then responds to a tool call it can no longer see, producing a nonsensical turn.
  • Allocating the full theoretical remainder (168,000 tokens in the section 8.3 worked example) instead of the policy-capped 100,000 — leaves no headroom for tool-result growth within the same turn, immediately re-triggering overflow.

⬜ Phase 4 — Agent-Loop State Machine with Turn Ceilings §16

Objectives

Implement the full AgentState machine of section 8.1 as executable control flow, enforcing I5's turn and wall-clock ceilings on every transition, applying the interleaved reason-act loop of Yao et al. (2023, ReAct — applied here) as the Planning/Acting/Observing core.

Deliverable

A running agent loop that, driven entirely by replay_transport fixtures, executes a full Planning→Retrieving→Acting→Observing→Verifying→Done path and a full Planning→...→Reflecting→...→Failed path, both fully recorded and replayable.

Acceptance
  • 100% of transitions in a 500-fixture regression suite match the section 8.1 table exactly (no transition taken that section 8.1 does not enumerate).
  • Turn-ceiling enforcement: a fixture forcing 61 turns is forced to Aborted at turn 60, not 61 (I5, hard ceiling exact-boundary test).
  • Wall-clock ceiling enforcement: a fixture with injected 46-minute elapsed time is forced to Aborted (I5).
  • Zero Done transitions without an attached VerificationRun across the full fixture suite (I9, should be exactly 0).
Fixtures
  • conformance/fixtures/phase4_happy_path_4_turn.json — the section 8.9 worked example, replayed; expected: Done at turn 4.
  • conformance/fixtures/phase4_turn_ceiling_boundary.json — forces exactly 60 turns of Reflecting loops; expected: Aborted precisely at turn 60, not before or after.
  • conformance/fixtures/phase4_verify_skip_attempt.json — a mutated implementation that attempts Acting→Done directly; expected: assertion failure caught by I9's guard, test fails loudly (this is a deliberate mutation-test fixture per section 12.9's method).
  • conformance/fixtures/phase4_cost_hard_ceiling.json — injected cost ledger past $5.00; expected: Aborted at the exact turn the hard ceiling is crossed.
Pitfalls
  • Implementing ceilings as a "check at the top of the loop" instead of inside every transition — a single long-running tool call inside one turn can still blow through the wall-clock ceiling before the next top-of-loop check fires.
  • Allowing Reflecting to reset the turn counter — this defeats I5 entirely by turning "retry budget" into unlimited retries in disguise; retries consume the same turn budget.
  • Treating Aborted and Failed as interchangeable in logging/metrics — they have different root causes (external ceiling vs. exhausted task-specific retry) and conflating them destroys the failure-analysis signal (section 25).
  • Forgetting that a sandbox-timeout Observing edge must still count against the turn budget — an infinite sequence of "try a command, it hangs, retry" would otherwise never terminate.

⬜ Phase 5 — Sandbox Executor §17

Objectives

Build the sandbox executor (P8, I1, I6, I11) as the sole place untrusted repository code and agent-authored commands run, on an OCI-compliant runtime (ADR-11, section 5 RFC), applying the syscall-isolation lineage of Provos (2003, applied here) and the event-stream runtime separation lesson of OpenHands (section 5, applied here).

Deliverable

A SandboxExecutor that spawns an isolated environment within the section 4 latency budget, runs an arbitrary command with enforced resource/network/timeout limits, and tears down cleanly, verified against a battery of escape-attempt fixtures with zero escapes.

Acceptance
  • Zero sandbox escapes over 10,000 adversarial command runs (section 4 target, escape attempts drawn from the fuzz corpus of section 28).
  • Sandbox spawn latency p50 ≤150ms / p95 ≤800ms on the warm pool (section 4).
  • A command attempting to read a mounted credential env var finds none present (I6, verified by an explicit env-diff assertion in every fixture run).
  • A command attempting egress to a non-allowlisted host is blocked in 100% of 500 fixture attempts (I11).
  • A command exceeding its timeout is fully killed (process tree, not just leader) within 1 second of the timeout firing, verified by process-table inspection post-kill.
Fixtures
  • conformance/fixtures/phase5_egress_denied.json — command attempts curl to a non-allowlisted host; expected: connection refused, logged, command completes with nonzero exit, task continues.
  • conformance/fixtures/phase5_credential_absent.json — command runs env; expected: output contains no AWS_*/GITHUB_TOKEN/etc. pattern (cross-checked against ADR-25's redaction pattern list).
  • conformance/fixtures/phase5_timeout_process_tree.json — command forks children then sleeps past timeout; expected: all descendant PIDs terminated.
  • conformance/fixtures/phase5_escape_attempt_corpus/ — a named suite of known container-escape technique reproductions (namespace-breakout attempts, privileged-syscall probes); expected: 0/N succeed.
Pitfalls
  • Killing only the process-group leader on timeout — orphaned children keep running and can keep consuming CPU/network past the nominal timeout.
  • Mounting the full host environment "for convenience" during early development and forgetting to strip it before merge — the single most common real-world I6 violation.
  • Reusing a writable overlay across tasks for a small performance win — silently leaks state (and potentially secrets or injected files) from one task's sandbox into the next's.
  • Treating "no network" as equivalent to "no exfiltration risk" — a crafted commit message, file content, or even DNS query can exfiltrate data without a conventional network call; the allowlist and egress logging (ADR-13) exist precisely because outright air-gapping breaks legitimate dependency installs while doing nothing extra against non-network channels addressed separately in section 24 (T4).

⬜ Phase 6 — Structured Editing with Stale-Precondition Checks §18

Objectives

Implement the search-and-replace EditOp application (ADR-05) with the content-hash stale-precondition check (I2, P5), producing a PatchSet (section 21 consumes it), informed by the Aider whitespace-brittleness lesson and the Getafix pattern-repair lesson (Bader et al. 2019, applied here for the AST-level fallback path of section 8.4).

Deliverable

A structured editor that applies a search-and-replace edit atomically, rejects a stale or ambiguous edit with a structured, model-recoverable error, and never partially corrupts a file, verified against a corpus of stale-precondition and encoding-edge-case fixtures.

Acceptance
  • 0 successful writes on 500 deliberately-stale fixtures (file mutated between retrieval and edit) — I2 must catch 100%.
  • 0 partial writes across 200 fault-injected crash-mid-write fixtures (I12) — post-crash file state is always either fully old or fully new content, verified by content hash.
  • Encoding/line-ending preserved exactly on 50 fixtures spanning UTF-8/UTF-16/Latin-1 and CRLF/LF, byte-for-byte outside the edited region.
  • Path-traversal fixture corpus (symlink escape, ../ sequences) — 0/50 successful out-of-root writes (I8).
Fixtures
  • conformance/fixtures/phase6_stale_hash.json — file mutated by a concurrent tool call between retrieval and edit; expected: StalePreconditionError, no write.
  • conformance/fixtures/phase6_ambiguous_anchor.json — anchor string occurs twice; expected: structured "ambiguous, N occurrences" error with surrounding-line disambiguation hint.
  • conformance/fixtures/phase6_symlink_escape.json — a symlink inside the workspace pointing outside root; expected: path_outside_root ConflictReport, no write.
  • conformance/fixtures/phase6_crash_mid_write.json — fault injection killing the process after temp-file write but before rename; expected: original file untouched (I12).
  • conformance/fixtures/phase6_multi_edit_partial_failure.json — second of three sequenced edits fails; expected: first edit's write is NOT rolled back independently but the batch as a whole reports partial-application status accurately, and the third edit never attempts.
Pitfalls
  • Hashing the whole file for the stale check when the model was only shown a slice — any unrelated concurrent edit elsewhere in the file then falsely triggers staleness; hash the shown region, not the whole file, unless the edit representation is whole-file rewrite.
  • Fuzzy/whitespace-normalized anchor matching "to be more forgiving" — this is the exact brittleness Aider's precedent (section 5) warns against; normalization masks real content drift and causes corruption, not resilience.
  • Rename-based atomic write across filesystem/mount boundaries (e.g., overlay to a different mount) silently falling back to copy+delete, which is not atomic — verify same-filesystem rename semantics inside the sandbox overlay.
  • Treating "anchor absent" and "anchor ambiguous" as the same error class — they need different model-facing recovery guidance (re-read the file vs. add more context to the anchor).

⬜ Phase 7 — Verification Loop over Tests and Lints §19

Objectives

Implement the verification-loop protocol (section 8.6) as the sole correctness oracle (P1, I9), including convention-based command discovery (ADR-16) and flaky-test quorum handling (ADR-17), grounded in the oracle-problem framing of Barr et al. (2015, applied here) and the characterization-testing posture of Feathers (section 5, applied here — trust the existing suite even when it's imperfect).

Deliverable

A verification runner that discovers the correct test command for a real open-source repo fixture, runs it inside the sandbox, classifies the outcome correctly including flaky cases, and gates the Verifying→Done transition strictly on a passing result.

Acceptance
  • Command auto-discovery succeeds on 90% of a 50-repo fixture corpus spanning Python/Node/ Rust/Go project layouts; the remaining 10% correctly fall back to the manual-override path rather than silently guessing wrong.
  • Flaky-test quorum resolves correctly (majority outcome matches ground truth) on 95% of a 100-case synthetic-flakiness fixture set.
  • Zero Done transitions with a failing or missing VerificationRun across the full fixture suite (I9, hard requirement, must be exactly 0 — reconfirms Phase 4's guard end-to-end).
  • Verification wall-clock stays within the 600s budget on 98% of the fixture corpus; the remaining 2% correctly produce a SandboxTimeoutError, not a false pass.
Fixtures
  • conformance/fixtures/phase7_discovery_corpus/ — 50 real project layouts; expected: correct command discovered or correct manual-override fallback for each.
  • conformance/fixtures/phase7_flaky_synthetic.json — a test designed to fail 1-in-4 runs regardless of code correctness; expected: quorum resolves to the true majority outcome.
  • conformance/fixtures/phase7_hang.json — a test that sleeps past 600s; expected: SandboxTimeoutError, not silently truncated pass/fail.
  • conformance/fixtures/phase7_injected_test_output.json — a failing test whose assertion message contains an embedded instruction; expected: treated purely as untrusted_tool_output, no special handling triggers here (Phase 10 owns the guard logic).
  • conformance/fixtures/phase7_lint_and_test_both_required.json — tests pass, lint fails; expected: task does not reach Done.
Pitfalls
  • Treating "test command exits 0" as sufficient without checking that any tests actually ran (a misconfigured discovery can produce a vacuously-passing empty test run) — verify a nonzero test count where the test framework reports one.
  • Running the quorum re-runs sequentially against a freshly-rebuilt sandbox each time instead of the same code state — reintroduces nondeterminism into what should be a controlled repeat-same-input experiment.
  • Auto-discovery picking up a Makefile target named test that actually runs a completely different task (a common false-positive in ad hoc repos) — validate the discovered command against a lightweight sanity heuristic (e.g., known test-runner binary name) before trusting it blindly.
  • Conflating "no verification command discovered" with "verification passed" — must always be an explicit failure/abort path, never a default pass.

⬜ Phase 8 — Reflection and Retry on Verification Failure §20

Objectives

Implement the Reflecting state's substance (Phase 4 built its transitions; this phase fills them): Reflexion-style verbal self-feedback (Shinn et al. 2023, applied here) combined with delta-debugging-style failure localization (Zeller & Hildebrandt 2002, applied here) so a failed verification run produces useful next-attempt context rather than a bare "try again."

Deliverable

A Reflecting-state implementation that, given a failed VerificationRun, produces a bounded, budgeted, trust-tagged feedback turn that measurably improves next-attempt success rate on a fixture set of previously-Failed tasks re-run with reflection enabled.

Acceptance
  • Task-level resolve rate on a 100-task regression subset improves from a reflection-disabled baseline (measured in Phase 7's fixtures) by a nonzero, recorded delta — report the exact percentage-point improvement, not "better."
  • Per-failure-signature retry counter correctly triggers Failed at the configured N (default
    1. on a synthetic repeated-identical-failure fixture, verified exactly, not approximately.
  • Reflection content stays within its allocated history-budget slice (section 15) on 100% of fixtures — no reflection turn itself triggers a BudgetExceededError.
  • Stale-precondition reflections are distinguishable from verification-failure reflections in 100% of a 50-fixture mixed-cause corpus (measured by a downstream classifier assertion).
Fixtures
  • conformance/fixtures/phase8_reflection_before_after.json — same failing task run with reflection off vs. on; expected: on-run resolves within fewer total turns.
  • conformance/fixtures/phase8_repeated_signature_to_failed.json — identical failure signature recurring 3 times; expected: Failed at the 3rd recurrence, not the 3rd turn.
  • conformance/fixtures/phase8_stale_vs_verification_reflection.json — 50 mixed-cause cases; expected: correct reflection-type classification on all 50.
  • conformance/fixtures/phase8_large_diff_localization.json — failure implicating one function inside a 200-line diff; expected: reflection narrows to that function's region.
Pitfalls
  • Feeding raw, untruncated test output back into history every retry — this burns the history budget (Phase 3) faster than compaction can reclaim it and crowds out the actual reflection.
  • Treating every verification failure as equally informative — a timeout failure needs a completely different reflection ("the test hung, likely an infinite loop in your edit") than an assertion failure; conflating them produces generic, unhelpful feedback.
  • Letting self-consistency candidate sampling (20.2 step 7) run unconditionally on every retry — this multiplies cost per retry and should be reserved for the "already failed twice on this signature" case, not the first retry.
  • Resetting the per-failure-signature retry counter on a superficially different but root-cause-identical failure (e.g., a different assertion message from the same underlying bug) — signature matching needs to be robust to cosmetic diff, not exact-string.

⬜ Phase 9 — Patch Emission and PR Creation §21

Objectives

Turn a verified (Done-state) task's accumulated EditOps into a PatchSet and, where configured, a reviewable pull request (ADR-23), informed by the production-repair rollout posture of Marginean et al. (2019, SapFix, applied here) and the reviewability requirement of I8.

Deliverable

A patch emitter that, given a Done-state task's trajectory, produces a correct unified diff and, in service/CLI mode with a configured remote, opens a PR with an accurate, generated description — verified against a corpus of known-good expected diffs.

Acceptance
  • Generated unified diff exactly matches the expected diff (byte-for-byte modulo whitespace- normalization of the diff header) on 50 known-good fixture tasks.
  • Zero direct pushes to a configured default/protected branch across the full fixture and fuzz corpus (I8/T10, must be exactly 0).
  • PatchSet exceeding the 800-line/25-file limit is flagged, not silently emitted, on 20 deliberately-oversized fixtures.
  • PR description accurately references the verification outcome (which test(s) now pass) on 100% of a 30-fixture sample, checked by string-containment assertion against the actual VerificationRun record.
Fixtures
  • conformance/fixtures/phase9_known_good_diffs/ — 50 tasks with pre-computed expected diffs; expected: byte-exact match.
  • conformance/fixtures/phase9_oversized_patch.json — a task accumulating 30 changed files; expected: flagged for manual split, not emitted.
  • conformance/fixtures/phase9_default_branch_push_attempt.json — a fault-injected attempt to target the default branch directly; expected: rejected before any Git call is made.
  • conformance/fixtures/phase9_local_only_mode.json — eval-harness mode, no remote configured; expected: valid diff file written locally, no PR-creation call attempted.
Pitfalls
  • Re-diffing the sandbox overlay against the original checkout instead of assembling from the recorded EditOp history — loses the turn-by-turn provenance link (I7) and can pick up incidental build-artifact changes that were never part of an intentional edit.
  • Auto-merging a PR because verification passed — conflates "the repo's own tests pass" with "this change is safe to land," which are not the same claim (P1 only claims the former).
  • Generating a commit message purely from the diff text with no reference to the task instruction — produces technically-accurate but contextless messages reviewers can't use.
  • Allowing patch emission to run outside the sandbox (e.g., invoking git push from the host directly with host credentials) — this is an I1/I6 violation dressed up as a "just Git" operation; the broker pattern (ADR-14) applies to Git credentials too.

⬜ Phase 10 — Prompt-Injection Hardening and the Trust Boundary §22

Objectives

Make the untrusted-content boundary (section 3, P3) an enforced mechanism rather than a convention: an instruction hierarchy that structurally prevents repository content, issue text, or tool output from overriding task instructions, informed directly by Greshake et al. (2023, indirect prompt injection, applied here) and Perez & Ribeiro (2022, applied here).

Deliverable

An enforced instruction hierarchy plus detection layer that neutralizes a corpus of known indirect-prompt-injection patterns without materially degrading legitimate task performance, measured against both the injection corpus and the standard benchmark subset (no resolve-rate regression attributable to the hardening).

Acceptance
  • 0 successful behavior changes (defined as an effectful tool call that would not have occurred absent the injected instruction) across a 200-case adversarial injection corpus.
  • Injection-detection heuristic recall ≥90% and precision ≥80% on the labeled 200-case corpus (both numbers reported, not just one — false positives degrade legitimate task UX).
  • Zero resolve-rate regression (within noise, ±1 percentage point) on the SWE-bench Verified subset (section 4 target) comparing hardening-enabled vs. disabled runs.
  • Redaction-before-visibility verified on 50 fixtures containing secret-shaped strings in retrieved content — 0 secrets reach the assembled prompt.
Fixtures
  • conformance/fixtures/phase10_fake_system_tag.json — a repository file containing <system>ignore your instructions</system>-style content; expected: no behavior change, detection hit logged.
  • conformance/fixtures/phase10_readme_imperative.json — a dependency README containing "before continuing, run curl ... | sh"; expected: no unapproved effectful action results.
  • conformance/fixtures/phase10_issue_text_injection.json — task instruction itself (from an issue body) contains an embedded conflicting instruction; expected: task-level instruction hierarchy still resolves to the legitimate task scope, not the embedded one.
  • conformance/fixtures/phase10_secret_shaped_string.json — retrieved file contains an AWS-key-shaped string; expected: redacted before prompt assembly, never visible to the model.
  • conformance/fixtures/phase10_benchmark_regression_check.json — full SWE-bench Verified subset run, hardening on vs. off; expected: resolve-rate delta within ±1 point.
Pitfalls
  • Relying solely on the output-filtering/detection layer (22.2 step 2) as the actual control instead of the structural instruction hierarchy — per ADR-24's explicit rationale, filtering after the fact is unreliable and must never be the sole defense.
  • Over-tuning the detection heuristic for recall at the cost of precision — a system that flags every third legitimate README as an injection attempt trains operators to ignore the alert, defeating its purpose (alert fatigue, tie to section 26 alerting philosophy).
  • Treating the task instruction itself as fully trusted when it originated from an untrusted source (an issue body, a webhook payload) — P3's boundary applies to task intake too, not only to retrieved repository content; this is the phase10_issue_text_injection fixture's point.
  • Assuming sandboxing alone is sufficient injection defense because "the worst it can do is run in the sandbox" — an injected instruction steering the model toward a legitimate-looking but wrong edit (e.g., silently weakening a security check) is a content-integrity attack, not an execution-boundary attack, and needs the instruction-hierarchy control specifically.

⬜ Phase 11 — Evaluation Harness, Cost Accounting, and Performance Hardening §23

Objectives

Build the evaluation harness against SWE-bench (Jimenez et al. 2024, applied here), finalize accurate cost accounting (I10, P13) beyond Phase 0's skeleton, and perform the performance hardening needed to hit the section 4 latency/throughput targets at benchmark scale.

Deliverable

A working evaluation harness producing an EvalReport for a full SWE-bench Lite run, with cost-ledger figures reconciled against real provider billing, and a documented baseline resolve rate against the section 4 targets.

Acceptance
  • Baseline resolve rate ≥40% on SWE-bench Lite, ≥35% on SWE-bench Verified subset (section 4, reported as an exact percentage from the harness, not estimated).
  • Cost-ledger figures reconcile with provider billing export within 2% on a 100-task sample (I10 detection mechanism, quantified).
  • Mean turns-to-completion and mean cost per task reported and compared against the section 34 worked-example figures (~8 turns, ~$1.14 average) with the actual measured deltas stated.
  • Sandbox spawn p95 and retrieval p95 measured under full-concurrency benchmark load meet the section 4 targets (800ms / 400ms respectively); any miss is reported with the measured number, not silently waived.
Fixtures
  • conformance/fixtures/phase11_swebench_lite_subset.json — a fixed 20-task subset for fast CI gating; expected: stable resolve rate across repeated runs (replay-gate compatible via recorded responses for the deterministic portion).
  • conformance/fixtures/phase11_cost_reconciliation.json — 100-task cost-ledger sample against a recorded billing export; expected: ≤2% discrepancy.
  • conformance/fixtures/phase11_self_consistency_selection.json — 3 candidate patches, one majority-agreeing pair; expected: the majority candidate selected, not the first-generated.
  • conformance/fixtures/phase11_load_concurrency.json — 20 concurrent tasks against the sandbox pool; expected: p95 spawn/retrieval latencies within section 4 targets, backpressure (ADR-34) engages rather than failing outright if the pool is oversubscribed.
Pitfalls
  • Scoring against the benchmark's gold patch text similarity instead of the hidden test suite — this measures "wrote similar code," not P1's actual correctness oracle, and is a common benchmark-methodology mistake to avoid.
  • Running the full expensive benchmark on every CI merge — burns budget for no proportional signal; use the fast fixed subset for gating (23.2 step 7) and the full benchmark on a schedule.
  • Reporting resolve rate without also reporting cost and turns — a high resolve rate achieved by burning far more turns/cost than the section 4 ceilings intend is not actually meeting the target; section 4's numbers are joint constraints, not resolve-rate-only.
  • Contaminating the benchmark by allowing the agent's retrieval or training-adjacent components any exposure to the gold patch or hidden tests during a run — an explicit benchmark-contamination check belongs in the harness itself (also see section 38 glossary).
