Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If retrieval (section 14) returns the wrong file with high confidence, does the budgeter (section 15) or the agent loop (section 16) ever get a signal to try a different retrieval mode, or does the task simply fail verification repeatedly until the retry budget (section 20) is exhausted?
  2. Section 8.3 caps retrieved context at 100,000 tokens for in-turn headroom — what actually happens (section 15, section 16) when a single tool result alone exceeds that headroom mid-turn, and is that path tested (section 15.5) as thoroughly as the pre-flight path?
  3. Section 17's sandbox pool and section 34's capacity model assume a fixed per-sandbox RSS ceiling — what breaks (section 19) when a legitimate repository's own test suite requires more memory than that ceiling, and is the failure mode distinguishable from a genuine sandbox-escape attempt (section 24, T2)?
  4. Section 20's per-failure-signature retry counter and section 16's turn ceiling are two different bounding mechanisms — can a task exhaust one without exhausting the other in a way that produces a misleading Aborted vs. Failed classification (section 25, FM-1 vs. FM-2)?
  5. Section 22's instruction hierarchy is structural, not a filter — but section 15's history compaction summarizes older turns through a model call; could a successfully-neutralized injection attempt from turn 3 be re-introduced with more apparent authority by an imperfect turn-40 compaction summary that paraphrases it without the original trust tag?
  6. Section 19's flaky-test quorum (ADR-17) assumes flakiness is a property of the test, not of the sandbox — what happens to resolve rate (section 23) if sandbox resource contention itself (section 17, section 31) is the actual source of nondeterminism being misclassified as test flakiness?
  7. Section 21's patch emission asserts provenance traceability from the trajectory (I7) — if the Phase 8 reflection process (section 20) causes the agent to revert its own earlier edit and reapply a different one, does the emitted diff still cleanly correspond to a coherent narrative, or does it require trajectory-aware diff synthesis not yet specified?
  8. Section 27 mandates a full benchmark re-run on any model upgrade — does the same mandate apply to an upgrade of the tree-sitter grammar version (section 14.9) or the embedding model (section 14), both of which can shift retrieval quality as materially as a model swap, and if not, why not?
  9. Section 4's cost ceiling is per-task — does section 26's fleet-level cost dashboard actually distinguish "many tasks each near their soft ceiling" from "one task near its hard ceiling," and does the alerting philosophy (section 26) treat these as the same signal when they imply very different interventions?
  10. Section 18's stale-precondition check (I2) hashes the shown region, not the whole file — could two sequential edits within the same turn to disjoint regions of the same file produce a false staleness rejection on the second edit if the first edit's write shifts line offsets the second edit's precondition wasn't computed against?
  11. Section 24 (T8) names a poisoned retrieval index as a threat but section 14's acceptance criteria measure only retrieval accuracy on a labeled fixture set — is there an actual adversarial-poisoning fixture anywhere in section 14.5, or does that threat only get tested indirectly through section 22's injection corpus?
  12. Section 30's M9 (verification runtime budget, 600s) and section 34's wall-clock model both assume verification dominates; if a future repository's test suite legitimately needs 1,200s, does the system degrade gracefully (extend the budget with an explicit tradeoff) or silently misclassify the task as a sandbox timeout indistinguishable from a hang?
  13. Section 9's ADR-18 fixes turn/cost ceilings identically for every task regardless of apparent difficulty — section 1 explicitly rejects a "dynamic complexity-based ceiling" as the primary policy; does this mean genuinely hard, legitimately-resolvable tasks are systematically undercounted in the section 23 resolve-rate denominator, and would that be visible in the EvalReport breakdown by difficulty tier?
  14. Section 22.6 warns against tuning the injection-detection heuristic for recall at the cost of precision, but section 24 (T1) treats injection as a Sev-1-adjacent class of concern — which section 26 alerting rule actually resolves that tension in practice, and is it the threshold-breach rule or the any-nonzero rule?
  15. Section 33's Agentless contrast argues an agent loop may not be necessary — given section 34's arithmetic showing verification (not reasoning) dominates wall clock, and section 32's MM1 framing the agent as fundamentally a search procedure, what specific capability does the twelve-phase loop in this blueprint provide over a three-stage Agentless pipeline that the numbers in section 34 alone would not already predict?

32. Mental Models & First Principles

MM1 — The agent is a search procedure over patches whose evaluation function is the test suite. Predicts: any technique that doesn't either propose a better candidate or evaluate it more cheaply is decoration. Bug class without it: chasing prompt-wording improvements that don't move resolve rate because the actual bottleneck is candidate quality or oracle reliability (P1). Resolves via section 8/section 23.

MM2 — The context window is a budget-allocation problem, and most agent failures are retrieval failures wearing a reasoning-failure costume. Predicts: a model "not understanding" a task is usually a model never having seen the relevant code. Bug class without it: endless prompt-engineering on a task that was never retrievable in the first place. Resolves via section 8.3/section 14/section 15.

MM3 — Every string the model reads is potentially an instruction; there is no passive data in this system. Predicts: any untagged content path is a latent injection vector. Bug class without it: a "just logging" or "just displaying" code path that turns out to also feed the next prompt unfiltered. Resolves via section 3/section 22.

MM4 — A tool call is a contract, not a suggestion. Predicts: loosening schema validation "to be more forgiving" always trades safety for a marginal, temporary convenience gain. Bug class without it: the free-text-protocol failure mode ADR-03 explicitly rejected, reintroduced piecemeal. Resolves via section 13.

MM5 — Verification is the only fact in the system; everything upstream of it is a hypothesis. Predicts: a task's Planning/Acting/Observing turns can all look reasonable and still be wrong; only Verifying tells you. Bug class without it: trusting a coherent-sounding trajectory as evidence of correctness. Resolves via section 8.1/section 19.

MM6 — The sandbox is the trust boundary's load-bearing wall; the model is not. Predicts: model improvements do not reduce the need for sandboxing, because the threat model (section 24) is about what untrusted code and untrusted content can do, independent of how capable or well-aligned the model is. Bug class without it: relaxing sandbox isolation because "the model got better." Resolves via section 17/section 24.

MM7 — A turn spent without a state transition recorded did not happen, for debugging purposes. Predicts: any gap in the trajectory record is where the next unexplainable bug will hide. Bug class without it: "it worked on my machine" style irreproducibility. Resolves via section 8.7/section 28.

MM8 — Cost is a per-turn accumulation, not a per-task estimate. Predicts: a task that "usually" costs $0.50 can still hit the $5 hard ceiling if a specific failure mode causes turn count to spike; averages hide tail risk. Bug class without it: under-provisioning the cost ceiling based on mean behavior alone. Resolves via section 4/section 8.8/section 34.

Required reading (§5)

Books

  • Kleppmann, Designing Data-Intensive Applications — ch. 3 (Storage and Retrieval: indexing structures) and ch. 9 (consistency/replication semantics for durable stores). Extract: index-structure tradeoffs for the lexical/structural index. Applied in section 14.
  • Arpaci-Dusseau & Arpaci-Dusseau, Operating Systems: Three Easy Pieces — chapters on process virtualization and CPU scheduling. Extract: what a namespace/cgroup actually isolates, and what it does not. Applied in section 17.
  • Zeller, Why Programs Fail — ch. on delta debugging. Extract: minimizing a failing input to its causal core, used for verification-failure localization. Applied in section 20.
  • Aho, Lam, Sethi, Ullman, Compilers: Principles, Techniques, and Tools — chapters on lexical analysis and syntax-directed translation. Extract: what an incremental parser (tree-sitter) is actually doing under the hood. Applied in section 14.
  • Feathers, Working Effectively with Legacy Code — ch. on characterization tests. Extract: treating an existing, possibly-inadequate test suite as ground truth anyway. Applied in section 19.
  • Nygard, Release It! — chapters on stability patterns (timeout, circuit breaker, bulkhead). Extract: bulkheading the sandbox pool and rate-limiting the provider client. Applied in section 17 and section 26.
  • Beyer et al. (Google), Site Reliability Engineering — ch. on postmortems and incident response. Extract: the blameless-postmortem template reused for section 26 runbooks. Applied in section 26.
  • Hunt & Thomas, The Pragmatic Programmer — ch. on "ubiquitous automation" and DRY. Extract: CI as a non-negotiable gate, reused for the Phase 0 replay-gate design. Applied in section 29.

Papers

  • Yao et al., ICLR 2023, "ReAct: Synergizing Reasoning and Acting in Language Models" — interleaved reasoning/action traces reduce hallucinated actions versus reasoning-only or acting-only prompting. Applied in section 16.
  • Schick et al., NeurIPS 2023, "Toolformer" — models can learn when and how to call a tool from demonstrations; motivates schema-first tool design over free-text tool invocation. Applied in section 13.
  • Shinn et al., NeurIPS 2023, "Reflexion" — verbal self-reflection on a failed attempt, fed back as context, improves next-attempt success without weight updates. Applied in section 20.
  • Wang et al., ICLR 2023, "Self-Consistency Improves Chain of Thought Reasoning" — sampling multiple reasoning paths and selecting by agreement outperforms single-sample decoding. Applied in section 23 (candidate patch selection in the eval harness).
  • Wei et al., NeurIPS 2022, "Chain-of-Thought Prompting Elicits Reasoning in Large Language Models" — explicit intermediate reasoning steps improve multi-step task performance. Applied in section 15 (prompt assembly).
  • Chen et al., 2021, "Evaluating Large Language Models Trained on Code" — introduces HumanEval; established functional-correctness-via-tests as the code-generation evaluation norm. Applied in section 23.
  • Austin et al., 2021, "Program Synthesis with Large Language Models" — introduces MBPP; a second synthesis-only benchmark distinguishing "can write code" from "can repair a real repo." Applied in section 23.
  • Jimenez et al., ICLR 2024, "SWE-bench: Can Language Models Resolve Real-World GitHub Issues?" — the primary benchmark for this project: real issues, real repos, hidden test- based grading. Applied in section 23.
  • Yang et al., NeurIPS 2024, "SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering" — the agent-computer interface (ACI) concept: tool ergonomics materially change resolve rate independent of the underlying model. Applied in section 13.
  • Wang et al., 2024, "OpenHands: An Open Platform for AI Software Developers as Generalist Agents" — event-stream runtime architecture separating agent, environment, and UI. Applied in section 17.
  • Zhang et al., 2024, "Agentless: Demystifying LLM-based Software Engineering Agents" — a fixed localize-repair-validate pipeline is competitive with agentic loops on SWE-bench at lower cost and higher predictability. Applied in section 36.
  • Le Goues et al., ICSE 2012 (GenProg) — search-based automatic program repair over a mutation space, scored by the test suite. Applied in section 36.
  • Monperrus, ACM CSUR 2018, automatic-repair bibliography — taxonomy of repair techniques and the recurring oracle problem across the field. Applied in section 21.
  • Bader et al., OOPSLA 2019, "Getafix" — pattern-based repair mined from historical fixes, informing template-driven edit generation. Applied in section 18.
  • Marginean et al., ICSE-SEIP 2019, "SapFix" — production-scale automated repair deployed at Facebook, informing the release/rollout posture for auto-generated patches. Applied in section 29.
  • Barr et al., 2015, "The Oracle Problem in Software Testing" (IEEE TSE) — a test suite is an imperfect oracle; frames why flaky/weak tests are a correctness risk, not a nuisance. Applied in section 19.
  • Zeller & Hildebrandt, 2002, IEEE TSE, delta debugging — algorithmic minimization of a failure-inducing input; the algorithmic basis for section 20's failure localization. Applied in section 20.
  • Greshake et al., 2023, "Not what you've signed up for: Compromising Real-World LLM- Integrated Applications with Indirect Prompt Injection" (AISec) — repository content, issue text, and tool output are viable injection vectors against an LLM agent. Applied in section 22.
  • Perez & Ribeiro, 2022, "Ignore Previous Prompt: Attack Techniques for Language Models" — catalog of prompt-override techniques informing the injection test corpus. Applied in section 22.
  • Provos, 2003 (seccomp/systrace lineage) — the systrace/seccomp approach to syscall-level sandboxing that underlies the sandbox executor's isolation guarantees. Applied in section 17.

Reference Implementations

  • SWE-agent — sweagent/agent/, sweagent/environment/swe_env.py. Lesson: a designed agent-computer interface materially reduces malformed actions. Pitfall: do not copy its early flat-file-only edit affordances uncritically — section 18's stale-precondition check is the fix. Applied in section 13.
  • OpenHands — openhands/runtime/, openhands/events/. Lesson: an event-stream architecture makes trajectory replay natural. Pitfall: do not couple runtime process lifecycle to UI session lifecycle — the sandbox must outlive/be independent of any frontend. Applied in section 17 and section 23.
  • Aider — aider/coders/, aider/repomap.py. Lesson: a tree-sitter-tag-based repo map is a cheap, effective structural retrieval signal. Pitfall: its search/replace format is brittle to whitespace drift — normalize before matching. Applied in section 14 and section 18.
  • Continue — core/context/, core/autocomplete/. Lesson: a pluggable context-provider interface generalizes across retrieval strategies cleanly. Pitfall: deep IDE coupling limits headless/CI use — keep the retriever IDE-agnostic. Applied in section 14.
  • GPT-Engineer — gpt_engineer/core/. Lesson: a simple linear plan-then-generate pipeline is a legitimate agentless baseline, useful for the section 36 contrast. Pitfall: no verification loop — it accepts generated code unconditionally, which this project's P1 explicitly forbids. Applied in section 36.
  • Cursor (documented published behavior; no inspectable source) — incremental diff application with inline accept/reject UX. Pitfall: proprietary — its sandboxing claims are unverifiable and must not be assumed equivalent to section 17's guarantees. Applied in section 21.

RFCs / Specifications

  • JSON Schema specification — the validation vocabulary used for every ToolSpec (I3). Applied in section 13.
  • The OCI runtime specification — the container runtime contract implemented by the sandbox executor (ADR-11). Applied in section 17.
  • The Language Server Protocol specification — the structural-analysis interface named as the deferred upgrade path from static tree-sitter indexing. Applied in section 14.
  • The OpenAI/Anthropic tool-calling schema conventions (published provider tool-use API documentation) — the native function-calling mechanism locked in ADR-03. Applied in section 13.
  • SemVer — the versioning discipline applied to tool schemas, prompt templates, and the trajectory format. Applied in section 27.

Glossary (§38) · 60 terms · site-wide glossary

Agent loop
the Planning/Retrieving/Acting/Observing/Verifying/Reflecting state machine (section 8.1, section 16) driving one task to completion.
Turn
one iteration of the loop, recorded as a Turn (section 8.7).
Tool call
a model-emitted, schema-validated request to invoke a registered tool (ToolCall, section 11).
Function calling
the provider's native tool-invocation mechanism (ADR-03), as opposed to a parsed text protocol.
Schema validation
checking a ToolCall's arguments against its ToolSpec.json_schema before dispatch (I3).
Effect class
a tool's classification as read-only, mutating, or executing (P12).
Context window
the model's total token capacity per request (section 4, 200,000).
Token budget
the arithmetic constraint bounding what fits in a request (section 8.3).
Retrieval
selecting relevant repository content for a turn (section 14).
Chunking
dividing repository content into retrievable units (ADR-09).
Reranking
reordering retrieved candidates by a secondary (typically embedding) signal (section 8.5).
Structured edit
a machine-checkable edit representation, as opposed to free-text (section 8.4).
Search-and-replace block
the locked primary edit representation (ADR-05, EditOp).
Stale precondition
an edit whose target content no longer matches what the model was shown (I2).
Patch
the assembled set of edits for a task (PatchSet, section 21).
Verification loop
the tests/lints/build gate that is the sole correctness oracle (P1, section 19).
Oracle
the mechanism that decides pass/fail for a candidate change; here, the repository's own test suite (Barr et al. 2015).
Flaky test
a test whose outcome varies across runs on unchanged code (ADR-17).
Reflection
Reflexion-style verbal self-feedback appended to history after a failure (Shinn et al. 2023, section 20).
Trajectory
the durable, replayable record of every turn in a task (section 8.7).
Replay
re-executing a task's turns from recorded model responses to reproduce its exact tool-call sequence (I7, P10).
Recorded response
a stored ModelResponse fixture used by the replay transport instead of a live model call.
Temperature
the sampling- randomness parameter, set per ADR-20's determinism policy.
Determinism
the property that identical inputs (including recorded responses) yield identical outputs; the basis of the replay-gate CI job.
Prompt injection
an attempt to override the model's intended instructions via crafted input text.
Indirect prompt injection
prompt injection delivered via content the model reads rather than the direct user turn (Greshake et al. 2023).
Trust boundary
the structural line separating trusted (system/task) from untrusted (repository/tool-output) content (P3, section 3).
Sandbox escape
untrusted code breaking out of its intended isolation to affect the host (T2).
Cost ceiling
the per-task dollar limit enforced by the state machine (section 4, ADR-18).
Resolve rate
the fraction of benchmark tasks an agent successfully fixes per the hidden-test oracle (section 23).
Benchmark contamination
a benchmark's gold patch or hidden tests leaking into the agent's context or training data, invalidating the score (section 23.6).
Agent-computer interface (ACI)
the designed surface of tools/affordances an agent uses to act on a repository (Yang et al. 2024).
Lexical retrieval
token/substring-match search (BM25-style).
Structural retrieval
retrieval keyed to parsed code structure (tree-sitter symbols).
Embedding retrieval
vector-similarity search over chunk embeddings.
Symbol index
the structural index mapping identifiers to definitions (SymbolIndex, section 11).
Budgeter
the component enforcing token-budget arithmetic pre-flight (section 15).
Compaction
summarizing older history to stay within the budget (section 8.3).
Idempotency
a tool's property of producing the same effect if invoked repeatedly with the same arguments (section 8.2).
Quorum (flaky-test)
the majority-of-N-reruns resolution policy for flaky_suspect outcomes (ADR-17).
Turn ceiling
the maximum number of loop iterations per task (I5, ADR-18).
Wall-clock ceiling
the maximum elapsed real time per task (I5).
Ledger
the atomically-updated cost/token accounting record (CostLedger, I10).
OCI runtime specification
the container-runtime contract implemented by the sandbox executor (ADR-11).
Seccomp
the Linux syscall-filtering mechanism in the sandbox isolation lineage (Provos 2003).
Cgroup / namespace
the Linux kernel primitives providing resource and filesystem/process isolation for the sandbox.
Egress allowlist
the explicit set of network destinations permitted from inside the sandbox (ADR-13).
Broker pattern
issuing a credential to a task via an external call rather than mounting it into the sandbox (ADR-14).
Instruction hierarchy
the structural framing that trusted instructions outrank untrusted content (ADR-24).
Differential testing
comparing this system's behavior against a reference implementation on a shared task set (section 28).
Property-based testing
generative testing asserting an invariant holds across randomized inputs (section 28, Hypothesis).
Mutation testing
deliberately breaking an implementation to confirm a test catches the break (section 12.9).
Delta debugging
algorithmic minimization of a failure-inducing input (Zeller & Hildebrandt 2002).
Self-consistency
selecting among multiple sampled reasoning paths by agreement (Wang et al. 2023).
ReAct
the interleaved reasoning-and- acting prompting pattern (Yao et al. 2023).
SWE-bench
the primary evaluation benchmark (Jimenez et al. 2024, ADR-22).
HumanEval / MBPP
code-synthesis benchmarks distinguishing raw generation capability from repo-scale repair (Chen et al. 2021; Austin et al. 2021).
Gold patch
a benchmark task's known-correct reference fix, never used for scoring directly (section 23.6).
Hidden tests
the benchmark's held-out test suite used as the actual scoring oracle.
SemVer
the versioning discipline applied to schemas, prompt templates, and the trajectory format (section 27). ---
