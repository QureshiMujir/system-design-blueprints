⬜ Phase 0 — Repository Bootstrap + Core Types §12

Objectives
  • Initialize ad-auction-rtb-engine Cargo workspace with all 11 crates.
  • Define rtb-core load-bearing types: Micros, Bid/Value/Price/Score, OpenRTB normalized objects, AuctionType, NoBidReason, ids, errors.
  • Enforce integer-money discipline (DP4): checked arithmetic, no float in money paths.
  • Establish CI: fmt, clippy, test, cargo-audit, cargo-deny, property-test scaffold.
Deliverable

Compilable workspace; all 11 crates build zero-warning; CI green; rtb-ctl --version prints version+git SHA; cargo test passes core-type tests.

Acceptance
  • Money types expose no floating-point arithmetic (enforced by absence of From<f64>/Mul<f64>).
  • Bid, Value, Price, Score are non-interchangeable (no cross-From).
  • Micros::checked_mul_ratio overflow returns MoneyError, never panics in release.
  • Zero unsafe in rtb-core except documented zerocopy derives.
  • cargo clippy -D warnings, cargo audit, cargo deny all pass.
  • 25+ unit tests pass.
Fixtures
  • conformance/fixtures/openrtb/valid_bidrequest.json — canonical ad call; decodes to normalized BidRequest.
  • conformance/fixtures/openrtb/missing_imp.json — no imp[]; expect InvalidRequest.
  • conformance/fixtures/openrtb/oversize.json — > size cap; expect reject.
  • conformance/fixtures/mechanisms/at_out_of_range.json — at=99; expect decode error.
Pitfalls
  • Float creeping into money via JSON: OpenRTB encodes bidfloor/price as JSON numbers (often decimals); parse as decimal-string → Micros (multiply by 1e6 with rounding rule), never f64. Root cause of non-reconciling charges.
  • Scale overflow in Score: bid(i64 micros) × pctr_scaled(1e9) × quality overflows i64; use i128. Manifests as negative scores / wrong winner.
  • Tie-break depending on map order: never derive winner from HashMap iteration; tie-break is an explicit total order (DP1/I6).
  • SmallVec inline size: too-small inline cap spills to heap on common N (fan-out 10–50); size inline arrays to the common case to honor DP14.

⬜ Phase 1 — Single-Unit Sealed-Bid Core (First-Price + Second-Price/Vickrey) §13

Objectives
  • Implement rtb-auction single-slot core: Scorer, Ranker, Allocator(1), ClearingPriceCalc.
  • Implement first_price (pay own bid) and second_price (Myerson single-unit threshold payment).
  • Establish determinism (I6) and run truthfulness (I1), IR (I2) property tests.
  • No reserves yet beyond pass-through bidfloor; no pacing/cap/predict (pCTR fixed = 1.0).
Deliverable

examples/single_auction.rs: feed a fixed bid set, run FirstPrice and SecondPrice, print winner + clearing price. proptest truthfulness/IR suites pass.

Acceptance
  • SecondPrice: winner pays second-highest effective bid clamped to reserve; price ≤ own bid always (10K random sets).
  • FirstPrice: winner pays own bid (≥ reserve).
  • Determinism: run_auction twice on identical input ⇒ identical digest() (I6).
  • Truthfulness property: for SecondPrice, no bid deviation strictly increases utility over truthful (proptest, 10K cases) (I1).
  • IR property: utility ≥ 0 for the winner in all cases (I2).
  • Single-auction compute < 1 µs for ≤ 16 bids (in-memory, criterion).
Fixtures
  • conformance/fixtures/mechanisms/first_price_basic.json (+ expected award).
  • conformance/fixtures/mechanisms/second_price_basic.json — pCTR-weighted threshold.
  • conformance/fixtures/mechanisms/second_price_single_bidder.json — one bid; pays reserve (or floor).
  • conformance/fixtures/mechanisms/tie_break.json — equal scores; deterministic winner.
  • conformance/fixtures/mechanisms/ir_clamp.json — threshold > bid scenario impossible; assert clamp invariant.
Pitfalls
  • Effective-bid vs stated-bid in second price: the second-highest score must be converted back to the winner's price units via winner's pCTR·quality, not the runner-up's. Wrong divisor breaks IR and truthfulness.
  • Reserve clamp ordering: clamp to reserve AFTER computing threshold; clamping the score instead misprices.
  • Tie-break instability: an unstable sort makes ties nondeterministic (I6 violation). Use stable sort + explicit total order.
  • Single-bidder second price: with no runner-up, score_2 = 0 ⇒ threshold 0 ⇒ price = reserve; forgetting reserve gives free impression.

⬜ Phase 2 — GSP Multi-Slot Ranking + eCPM Scoring §14

Objectives
  • Extend Allocator to k slots; rank top-k by score.
  • Implement gsp payment: slot-j winner pays min bid to hold slot j = score_{j+1}/(pctr_j×quality_j), floored at reserve.
  • Confirm GSP is NOT truthful (property test detects profitable deviation) and exhibits locally-envy-free equilibria.
  • Multi-slot allocation monotonicity (I3).
Deliverable

examples/single_auction.rs extended to Gsp{slots:2}; prints per-slot winners + prices. GSP property suites (monotonicity pass; non-truthfulness demonstrated) run.

Acceptance
  • k-slot allocation: top-k scores get slots 1..k in order.
  • Slot-j price = next-score / (own pCTR·quality), ≥ reserve, ≤ own bid (10K random sets).
  • Monotonicity (I3): raising a bid never demotes its slot (proptest sweep).
  • Determinism (I6): identical input ⇒ identical multi-slot digest().
  • Last-slot winner pays reserve when no next bidder.
Fixtures
  • conformance/fixtures/mechanisms/gsp_2slot.json
  • conformance/fixtures/mechanisms/gsp_3slot_with_reserve.json
  • conformance/fixtures/mechanisms/gsp_fewer_bids_than_slots.json — k < slots
  • conformance/fixtures/mechanisms/gsp_monotonicity_sweep.json
  • conformance/fixtures/mechanisms/gsp_last_slot_reserve.json
Pitfalls
  • Off-by-one in next-score indexing: slot-j pays score_{j+1}; the lowest filled slot pays reserve (next-score is 0). Off-by-one charges wrong amount.
  • pCTR divisor per slot: each slot uses its OWN winner's pCTR·quality; reusing slot-1's divisor for all slots misprices lower slots.
  • Slot-specific CTR (position bias): if θ_j position discount is enabled, scores must use position-adjusted CTR consistently in both ranking and payment; mixing adjusted/unadjusted breaks monotonicity.
  • Reserve per slot: reserves may differ per slot; apply the slot's reserve, not a global one.

⬜ Phase 3 — VCG Mechanism + Externality Payment §15

Objectives
  • Implement vcg multi-slot externality payment: each winner pays the total harm imposed on others.
  • Prove VCG truthfulness (I1) and IR (I2) by property test; contrast payments vs GSP.
  • Establish VCG ≤ GSP payment relationship (typical) and document exceptions.
Deliverable

examples/single_auction.rs supports Vcg{slots}; prints per-slot externality prices. VCG truthfulness + IR property suites pass; GSP/VCG comparison report.

Acceptance
  • VCG truthfulness (I1): no deviation strictly improves utility (proptest 10K, multi-slot).
  • VCG IR (I2): price_j ≤ bid_j, utility ≥ 0.
  • Single-slot VCG payment == single-slot second-price threshold (exact equality fixture).
  • Determinism (I6): identical input ⇒ identical digest().
  • VCG payment ≤ corresponding GSP payment in ≥ 95% of random comparison cases; document the rest.
Fixtures
  • conformance/fixtures/mechanisms/vcg_2slot.json
  • conformance/fixtures/mechanisms/vcg_3slot.json
  • conformance/fixtures/mechanisms/vcg_eq_second_price_single_slot.json
  • conformance/fixtures/mechanisms/vcg_vs_gsp_comparison.json
  • conformance/fixtures/mechanisms/vcg_truthfulness_sweep.json
Pitfalls
  • Externality must recompute the counterfactual allocation: welfare_without_j re-assigns others into all slots (they shift up); a naive "sum of others' current scores" is wrong and breaks truthfulness.
  • Slot count after removal: with j removed, lower bidders move up into freed slots; the counterfactual uses the same slot set.
  • Conversion to price units: externality is in score units; divide by pctr_j×q_j to get j's price. Forgetting this conflates value and price (DP13).
  • Reserve interaction: with reserves, VCG payment is max(externality-based, reserve); reserves change the counterfactual welfare (bidders below reserve don't count).

⬜ Phase 4 — Reserve Prices: Hard/Soft Floors + Myerson Optimal Reserve §16

Objectives
  • Implement rtb-reserve: hard floor (reject below), soft floor (first-price below / second-price above), publisher vs exchange floor (max), per-slot reserves.
  • Implement Myerson optimal monopoly reserve r* where φ(r*)=0.
  • Wire reserves into all mechanisms (I4: clearing ≥ reserve).
  • Per-impression dynamic floors from a value distribution.
Deliverable

run_auction honors hard/soft/publisher/exchange/dynamic floors across all four mechanisms. rtb-ctl reserve compute --dist uniform --max V prints r*. Reserve fixtures pass.

Acceptance
  • Hard floor: no winner clears below floor; all-below ⇒ BelowFloor no-bid (I4).
  • Soft floor: bid below soft floor pays first-price; at/above pays mechanism price (fixture-verified crossover).
  • effective_floor = max(...) correct across combinations.
  • Myerson r* for Uniform[0,V] equals V/2 within rounding; bisection converges < 30 iters.
  • Reserve respected in first/second/GSP/VCG (per-slot).
  • IR preserved after reserve clamp (I2) in all 10K random reserve fixtures.
Fixtures
  • conformance/fixtures/reserves/hard_floor_reject_all.json → BelowFloor
  • conformance/fixtures/reserves/hard_floor_one_above.json
  • conformance/fixtures/reserves/soft_floor_crossover.json
  • conformance/fixtures/reserves/publisher_vs_exchange_max.json
  • conformance/fixtures/reserves/myerson_uniform_half.json
  • conformance/fixtures/reserves/per_slot_reserves_gsp.json
Pitfalls
  • Hard vs soft confusion: hard rejects pre-auction; soft never rejects but changes payment. Mixing them double-penalizes or under-charges.
  • Reserve in score units vs price units: reserve is a price; compare against the bid's price-equivalent, and clamp the price, not the score.
  • Myerson regularity: φ must be monotone (regular distribution) for bisection; for irregular distributions, ironing is required (deferred; document PhaseDeferred("Deferred Features Register") for non-regular).
  • Dynamic floor staleness: ValueDist per segment must refresh; a stale distribution sets a wrong r*, suppressing or under-pricing.
  • Soft-floor + GSP/VCG: soft floors are a legacy second-price concept; define behavior for multi-slot (apply per slot or only slot-1) and document; default: soft applies only to single-slot second-price; reject soft+multi-slot config otherwise.

Objectives

Deliverable

examples/fanout_demo.rs + docker-compose.yml (rtbd + mock bidders): ad call fans out under tmax, runs the auction over received bids, returns BidResponse within budget. benchmarks/fanout_throughput.rs measures QPS + p99.

Acceptance

  • Late bids never enter the auction (I5): fanout.late_bid_admitted == 0 across fault sims.
  • Per-bidder timeout strictly < collection budget; slow bidder doesn't blow the budget.
  • Hedging reduces p99 by ≥ 20% vs no-hedge under a slow-tail bidder (criterion).
  • Circuit breaker trips after configured error rate; recovers via half-open probe.
  • All-timeout → BidResponse with nbr = NoBidsInTime.
Fixtures
  • conformance/fixtures/openrtb/valid_bidresponse.json
  • conformance/fixtures/openrtb/late_bid_dropped.json — bidder responds post-deadline; dropped
  • conformance/fixtures/openrtb/partial_result.json — 3 of 10 bidders respond; auction over 3
  • conformance/fixtures/openrtb/all_timeout_nobid.json — nbr=NoBidsInTime
  • conformance/fixtures/openrtb/circuit_open_skip.json — broken bidder skipped
Pitfalls
  • Deadline propagation drift: per-bidder timeout must be derived from the remaining budget at fan-out time, not the original tmax (parse already consumed some). Use the DeadlineClock start = recv_at.
  • Cancellation leaks: dropping a future must cancel the in-flight RPC; un-cancelled calls leak connections and CPU. Use scoped tasks + tonic deadlines.
  • Clock source on hot path: use monotonic Instant; SystemTime can jump and admit/late-drop incorrectly (I5).
  • Hedge amplification: hedging every bidder doubles load; hedge only the slow tail (after p95) and cap hedge fan-out.
  • Partial result + reserve: a partial set may all be below floor → BelowFloor, not NoBidsInTime; distinguish "no bids arrived" from "bids arrived but ineligible".

⬜ Phase 6 — Budget Management + Pacing Controller §18

Objectives
  • Implement rtb-pacing: campaign budget B over horizon T; target spend curve S*(t).
  • Implement three pacers: probabilistic throttling, dual/multiplicative shading, PID; selectable per campaign.
  • Track in-flight win reservations (I11); reconcile to KV; bound overspend ≤ 2% (I7).
  • Wire pacing admission/shading into the pre-auction filter.
Deliverable

examples/pacing_demo.rs: simulate a campaign; plot/print spend vs target across the horizon for each pacer. rtb-ctl pacing inspect --campaign C shows spend, μ/p_enter, in-flight. Pacing-stability sim passes.

Acceptance
  • Even-pacing: cumulative spend stays within ±5% of S*(t) over the horizon (sim).
  • Overspend bound (I7): final spend ≤ B·(1+0.02) across 10K sims with KV lag injected.
  • Dual pacer: under sustained over-demand, μ rises and spend rate → B/T (converges; no divergence).
  • PID: no sustained oscillation (amplitude decays); anti-windup prevents integral blowup after budget exhaustion.
  • In-flight (I11): a win without a billing confirm releases its reservation after confirm_timeout; no permanent leak; no double-count when confirm arrives.
  • Multi-campaign: contention on shared inventory does not cause any campaign to exceed its bound.
Fixtures
  • conformance/fixtures/pacing/even_curve_track.json
  • conformance/fixtures/pacing/asap_curve.json
  • conformance/fixtures/pacing/overspend_bound_kv_lag.json
  • conformance/fixtures/pacing/dual_convergence.json
  • conformance/fixtures/pacing/pid_oscillation_damped.json
  • conformance/fixtures/pacing/inflight_release_timeout.json
Pitfalls
  • Pacing on value vs price: shade the bid (price units) by 1/(1+μ), but the budget constraint is on spend (clearing price). The dual μ prices spend; ensure the LP/dual derivation uses realized price, not bid, when updating μ.
  • Controller instability (oscillation): too-high gains cause spend to overshoot/undershoot; tune η/Kp; smooth spend_rate with EWMA; sim sweep finds stable region.
  • Budget-depletion race: concurrent wins across nodes can collectively overspend in the KV-lag window; reservation + bound (I7) caps it; never assume zero lag.
  • In-flight double-count: counting both the reservation and the confirmed spend double-charges the controller; confirm moves in-flight → spent atomically.
  • Throttle determinism for replay: admission PRNG must be seeded deterministically (per campaign+auction) so replays reproduce admit/skip (DP1).
  • Horizon-end behavior: as t→T, S*(t)→B; avoid a spend cliff (dumping remaining budget) — clamp rate.

  • Targeting: ineligible campaigns never win (geo/device/category/daypart/blocklist fixtures).

Fixtures

Pitfalls
  • CMS must over-estimate, never under: use min across rows; under-counting (a buggy estimator) shows users too many ads (DP9/I8). Verify the one-sided property in tests.
  • Window bucketing granularity: too-coarse buckets cause early/late aging (a 24h cap with 1 bucket ages all at once); use sub-windows; document granularity/accuracy trade.
  • Concurrent-win race: increment-then-check vs check-then-increment matters; atomically record on win and re-evaluate; the auction-time check is advisory, the win-time check is authoritative.

  • Targeting before vs after fan-out: targeting narrows the eligible set pre-fan-out (don't waste bidder calls), but a bidder may still bid for an ineligible campaign — re-check eligibility at win.

Pitfalls
  • Property-test oracle wrong: the truthfulness check must compute utility correctly (value·win_indicator − price); a wrong utility formula false-passes or false-fails. Pin with hand-computed fixtures.
