Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived from the §4 System Constraints with the formula shown. Inputs are named with their §4 source.

C1 — Peak ingress request bandwidth. Inputs: Auctions/sec/node ≥ 100K (§4 M1); assume a typical OpenRTB JSON BidRequest ≈ 2 KB. Formula: QPS × req_size = 100,000 × 2 KB ≈ 200 MB/s ≈ 1.6 Gb/s ingress per node — already past 1 GbE, so 10 GbE NICs and simd-json in-place parsing (Phase 5) are mandatory, not optional.

C2 — Bidder fan-out egress bandwidth. Inputs: QPS 100K (§4 M1); fan-out degree 10–50 bidders (§4 M6); outbound request ≈ 2 KB. Formula: QPS × fanout × req_size = 100,000 × 30 (mid) × 2 KB ≈ 6 GB/s ≈ 48 Gb/s of bidder-facing traffic. Implication: fan-out egress is ~30× ingress; it dominates the NIC budget and forces connection pooling + co-location (§4 M20, "Network RTT < 20 ms").

C3 — Concurrent in-flight bidder calls. Inputs: QPS 100K (§4 M1); per-bidder timeout up to 90 ms ≈ 0.09 s (§4 M5); fan-out 30 (§4 M6). Formula (Little's law): in-flight = QPS × latency × fanout = 100,000 × 0.09 × 30 ≈ 270,000 concurrent outstanding RPCs per node. Implication: this far exceeds the FD budget below — connections must be multiplexed (HTTP/2, A08), not one socket per call.

C4 — File-descriptor pressure vs budget. Inputs: FD budget < 4096 (§4 M21); distinct bidders 10–50 (§4 M6). Formula: with HTTP/2 multiplexing, FDs ≈ pooled_conns_per_bidder × bidders + ingress_sockets ≈ (4 × 50) + ingress ≈ 200 + ingress, comfortably < 4096. Cross-check against C3: without multiplexing, 270K calls would need 270K FDs — 66× over budget — confirming A08's HTTP/2 choice is load-bearing, not stylistic.

C5 — Auction compute budget per call. Inputs: internal compute p99 < 5 ms (§4 M3); scoring throughput ≥ 5M bid-scores/sec/core (§4 M8); a few-hundred bids. Formula: scoring_time = bids / throughput = 300 / 5,000,000 ≈ 60 µs; well under the 5 ms compute ceiling, leaving headroom for ranking + clearing. Implication: compute is not the bottleneck (confirms MM1) — the 5 ms ceiling is generous slack against the 80–120 ms tmax (M2).

C6 — Per-call CPU vs throughput target. Inputs: Auctions/sec/node 100K (§4 M1); 1–2 cores auction compute (§4 M19). Formula: CPU budget per auction = cores / QPS = 2 / 100,000 = 20 µs/auction of pure compute. Cross-check against C5's 60 µs scoring for 300 bids: the steady-state average auction has far fewer bids (10–50, §4 M6), so ~10–20 µs is realistic — the 100K target is achievable on 2 cores only if there is zero per-call allocation (DP14, MM10).

C7 — pCTR inference cost per auction. Inputs: pCTR inference < 50 µs/bid (§4 M9); bids per auction ≈ 30 (§4 M6, fan-out mid). Formula: inference_per_auction = 50 µs × 30 = 1.5 ms. Implication: at face value pCTR inference exceeds the C6 CPU budget and rivals the C5 compute ceiling — so the < 50 µs must be a sparse dot-product (Phase 8) and inference is the dominant compute term, justifying in-process FTRL (A12) over any RPC model server.

C8 — Frequency-cap lookup load. Inputs: freq-cap lookup p99 < 100 µs (§4 M11); one lookup per eligible bid, ≈ 30/auction; QPS 100K (§4 M1). Formula: lookups/sec = QPS × bids = 100,000 × 30 = 3M lookups/s/node, each < 100 µs but O(1); at depth ≈ 4 CMS hashes that is 12M hash ops/s. Implication: must be lock-free sharded reads (A21), and the Bloom fast-path (Phase 7) matters for heavy-frequency users.

C9 — pCTR model memory footprint. Inputs: memory ceiling 8 GB, mostly static (§4 M10). Formula: a feature-hashed logistic model with 2^24 weights × 8 bytes ≈ 134 MB; comfortably within 8 GB alongside sketches and journal buffers. Implication: the model "fits L2" claim (§4 M9, "pCTR inference") refers to the hot weight working set, not the full table — design feature hashing so common features stay cache-resident (Phase 8).

C10 — Frequency-cap sketch memory. Inputs: memory ceiling 8 GB (§4 M10); freq-cap keys ~billions (Scalability Analysis). Formula: a CMS at width = 2^20, depth = 4, 4-byte counters = 2^20 × 4 × 4 ≈ 16 MB per campaign-group, bounding memory independent of user count. Implication: this is why probabilistic mode exists — exact (user,campaign) counters at billions of keys would blow the 8 GB ceiling; the sketch trades the C5/C8 one-sided error (MM5) for bounded RAM.

C11 — Journal write throughput. Inputs: QPS 100K (§4 M1); one AuctionRecord ≈ 1 KB length-prefixed protobuf. Formula: journal_write = QPS × rec_size = 100,000 × 1 KB ≈ 100 MB/s/node sequential. Implication: within a single NVMe's sequential write band, but only if fsync is batched off the auction task (Phase 9, MM10); a per-record fsync at 100K/s is physically impossible (M14 durability boundary).

C12 — Cluster node count for a target ad-call rate. Inputs: Auctions/sec/node 100K (§4 M1); Availability 99.95% (§4 M22). Formula: for a peak of, say, 2M ad calls/s, nodes = peak / per_node = 2,000,000 / 100,000 = 20 nodes, plus N+1 headroom for hedging/load-shed and drain during rolling upgrade → provision ~24. Implication: the system scales linearly (stateless nodes) until the shared KV plane (Scalability Analysis) becomes the coordination bottleneck.
