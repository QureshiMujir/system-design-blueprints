413 — Ad Auction / Real-Time Bidding Engine from Scratch

Project Number: 413 Project Name: Ad Auction / Real-Time Bidding Engine from Scratch Owner: Mujir Qureshi Document: FINAL_BLUEPRINT.md Status: specification — locked

1. Goal

Build a correctness-first, tail-latency-bounded ad auction / real-time bidding (RTB) engine — the server that, per ad impression, builds a BidRequest, fans out to N demand bidders under a hard time budget, runs a sealed-bid auction (first-price / second-price / GSP / VCG), applies reserve floors, ranks by expected value (eCPM), enforces budget pacing and frequency caps, settles a clearing price, and writes a billing-grade auction journal. Mechanism-design engine fused with a low-latency distributed-systems core. Correctness (mechanism truthfulness, monotonicity, IR, no over-delivery) first; observability second; maintainability third; performance fourth.

Core capability surface:

  • Auction mechanisms — first-price sealed-bid; second-price/Vickrey (single-unit, DSIC); Generalized Second-Price (GSP, multi-slot, rank-by-score, pay min-to-hold-position, NOT truthful); Vickrey-Clarke-Groves (VCG, multi-slot, DSIC, pay-the-externality). Selectable per-impression via auction_type.
  • Ranking & value — score = bid × pCTR × quality; eCPM = bid × pCTR × 1000; expected-value ranking; multi-slot allocation by descending score.
  • Reserve prices — hard floor (reject bid < floor); soft floor (legacy: first-price below, second-price above); publisher floor vs exchange floor (max); Myerson optimal monopoly reserve r* where φ(r*)=0; per-impression dynamic floors.
  • Budget pacing — campaign budget B over horizon T; even-pacing vs ASAP; (1) probabilistic throttling p_t; (2) bid-shading multiplier μ from Lagrangian dual of budget-constrained LP (primal-dual / online mirror descent / multiplicative-weights), shade bid = value/(1+μ); (3) PID on cumulative spend error.
  • Frequency capping — per (user, campaign) impression counts over sliding windows (e.g. 3/24h); exact bucketed TTL counters vs probabilistic (Count-Min Sketch, HyperLogLog, Bloom "already capped").
  • Latency-bounded fan-out — OpenRTB flow: build request → parallel fan-out → collect within tmax (80–120 ms) → drop late → auction over received → return winner + clearing price; deadline propagation, per-bidder timeouts, hedged requests, circuit breakers, partial-result auctions.
  • OpenRTB protocol — BidRequest / BidResponse; no-bid reasons (NBR); win/billing/loss notices (nurl/burl/lurl); clearing/settlement price.
  • Prediction — pCTR (online logistic regression, calibration); win-rate / bid-landscape P(win|bid) from censored win/loss data.
  • Auction journal — append-only, billing-reconcilable event log of every auction, bid, win, charge.
  • Deterministic simulation — auction fuzzing; mechanism property checks (truthfulness/IR/monotonicity); pacing-stability sims; replay.

System boundaries: a standalone auction server process (rtbd) + a bidder-side client library (rtb-client, also usable as a DSP-side bidder stub) + a CLI (rtb-ctl). NOT an ad-serving creative renderer, NOT an attribution/measurement pipeline, NOT a DMP, NOT an ML training platform (pCTR models trained offline; engine does online inference + light online updates only).

Explicit non-goals:

  • NOT a creative ad server / VAST player — rendering, viewability measurement → PhaseDeferred("Deferred Features Register").
  • NOT cross-device identity resolution / DMP — user graph is an opaque user_id → PhaseDeferred("Deferred Features Register").
  • NOT an offline ML training framework — model artifacts loaded from #123 recommender pipeline; engine does inference + online SGD only.
  • NOT header-bidding wrapper / Prebid.js client logic — server-side auction only.
  • NOT a billing/invoicing system — engine emits a reconcilable journal; downstream finance system (#411 ledger) settles money.
  • NOT floating-point money — amounts are integer micros (i64/u64); decimal display → #401.
  • NOT a generic RPC framework — bidder transport uses #155 gRPC patterns internally; not re-exported.

Deployment model: stateless auction nodes behind an L4/L7 load balancer; each node holds hot pacing/freq-cap/model state in-process backed by a distributed KV (#36); horizontally scaled by impression volume; co-located in the same region as exchange ad-call ingress for RTT budget. Linux, io_uring/epoll, async runtime (#129).

Target users: ad-exchange / SSP infra engineers, DSP bidder-platform engineers, auction-mechanism researchers needing a precise, testable reference.

2. Why Build This

Unique systems knowledge taught:

  • Mechanism design as executable code — DSIC, IR, revenue equivalence, Myerson optimal reserve, GSP vs VCG payment rules implemented and property-tested, not just derived on paper. Truthfulness becomes a checkable invariant.
  • Hard real-time auction budget — an auction that must return in ~100 ms whether or not bidders responded; deadline propagation, partial-result correctness, and tail-latency engineering as first-class concerns.
  • Online constrained optimization in the serving path — budget pacing as the Lagrangian dual of a budget-constrained LP solved online with primal-dual / mirror-descent / PID; stability of feedback controllers under noisy, bursty traffic.
  • Censored learning — win-rate / bid-landscape estimation P(win|bid) from one-sided observations (you only see whether you won, not others' bids); pCTR calibration so that bid×pCTR is a meaningful expected value.
  • Probabilistic counting at scale — frequency capping via Count-Min Sketch / HyperLogLog / Bloom; trading exactness for memory; quantifying error bounds against caps.
  • Billing-grade event journaling — append-only auction log that reconciles to charges; idempotent win-notice handling; exactly-once-ish billing under loss/retry.

Historical/architectural significance:

  • GSP — the auction that funded the modern web (Google AdWords, Overture); not truthful, but locally-envy-free equilibria explain observed bidding; Edelman-Ostrovsky-Schwarz 2007 / Varian 2007.
  • VCG — Facebook ad auction moved to VCG; theoretically truthful; payment = externality imposed on others; Vickrey 1961 / Clarke 1971 / Groves 1973.
  • Myerson optimal auction — 1981 Nobel-tier result: optimal mechanism = second-price with reserve set where virtual value crosses zero; the theoretical basis for reserve pricing.
  • OpenRTB — the IAB protocol standardizing programmatic exchange; the lingua franca of the $100B+ programmatic market.
  • Tail at Scale (Dean & Barroso 2013) — RTB is the canonical fan-out-under-deadline system; hedging, tied requests, and partial results are textbook applications.

Engineering muscles developed: mechanism implementation + property testing; deadline-bounded async fan-out; online optimization/control loops; censored statistical estimation; probabilistic data structures; append-only billing journals; deterministic simulation of economic systems.

Production concepts exercised: backpressure, circuit breaking, hedged requests, idempotent billing, spend-curve control, A/B-safe determinism, reconciliation.

Calibration value: fuses microeconomics with hard-real-time systems. Permanently raises the bar for: reasoning about incentives a system creates (not just outputs), engineering bounded-latency under partial failure, and proving economic invariants by simulation.

What Mastery Looks Like

  • Implement a truthful mechanism and prove it — build VCG/second-price as a monotone-allocation + threshold-payment pair and verify DSIC by property test, not algebra (Phase 1, Phase 3; I1).
  • Engineer a hard deadline that survives partial failure — return a valid BidResponse within tmax whether or not bidders answer, with deadline propagation, hedging, and a late-drop gate (Phase 5; I5, I10, DP2).
  • Solve a constrained optimization online in the serving path — derive the pacing multiplier μ as the Lagrangian dual of a budgeted LP and run it stably under bursty traffic with mirror-descent/PID (Phase 6; DP8, I7).
  • Estimate from one-sided observations — fit P(win|bid) from censored win/loss data and calibrate pCTR so bid×pCTR is a real expected value (Phase 8; I12, DP13).
  • Trade exactness for memory under a quantified bound — choose a Count-Min Sketch with one-sided error so frequency caps fail conservative, and state the breach bound (Phase 7; DP9, I8).
  • Build a billing-grade journal — append-only WAL with idempotent notice dedup that reconciles exactly-once to a ledger under loss/retry (Phase 9; DP12, I9).
  • Make an economic system reproducible — a pure deterministic mechanism core plus seeded simulation that replays any journaled auction bit-exactly (Phase 0, Phase 11; DP1, I6).
  • Reason about a design's incentives, not just its outputs — predict when GSP gaming, overspend races, or cap evasion appear and where each is contained (Phase 2, Phase 6, Phase 7; DP15).

Exchange Ad-Call Ingress — untrusted external boundary; an SSP/exchange (or our own SSP) sends an OpenRTB BidRequest per impression opportunity over HTTP/JSON or protobuf. L7 LB + anycast routes to the nearest region to preserve RTT budget. All input is hostile: size-bounded, schema-validated, rate-limited.

rtb-net (Ingress + Request Builder) — terminates HTTP; OpenRtbDecoder parses/validates the ad call (size caps, required fields, enum ranges); BidRequestBuilder normalizes into the internal BidRequest; TargetingFilter computes the eligible campaign set (geo/device/category/daypart/blocklists). On the response path it serializes BidResponse (seatbid) and emits nurl/burl/lurl. Trust boundary: everything downstream trusts the validated BidRequest.

rtb-fanout (Latency-Bounded Bidder Client) — owns the tmax deadline clock. Fans out the BidRequest to N eligible DSP bidders concurrently (async RPC, #155 patterns), each with a per-bidder timeout strictly less than the global budget. Drops late responses, hedges to a backup bidder when a primary is slow, and trips circuit breakers on bidders that error/time out repeatedly. The PartialResultGate guarantees the auction proceeds with whatever bids arrived before the deadline. Concurrency boundary: this is the only place that awaits external I/O on the hot path.

Pre-Auction Filters — each returned Bid must pass, in order: reserve floor (rtb-reserve), pacing admission/shading (rtb-pacing), frequency-cap eligibility (rtb-freqcap), creative/category eligibility, and scoring (rtb-predict supplies pCTR → score). A bid that fails any filter cannot win. This is a synchronous, allocation-light pipeline.

rtb-auction (Mechanism Engine) — the deterministic core. Scorer computes score = bid × pCTR × quality; Ranker sorts; Allocator assigns slots (single or multi); ClearingPriceCalc computes payment per the selected mechanism (first-price, second-price/Vickrey, GSP, VCG). Pure function of (eligible scored bids, mechanism, reserves, seed) → AuctionResult. No I/O, no clocks, no randomness except an explicit tie-break seed.

rtb-net Response — encodes the winner(s) and clearing price into a BidResponse; attaches nurl (win notice), burl (billing notice), lurl (loss notice) URLs the exchange will call.

rtb-pacing / rtb-freqcap state — on a confirmed win, spend is incremented (budget) and the impression is counted (freq-cap); the pacing controller (PID / dual update) recomputes the shading multiplier or throttle probability against the target spend curve. Persistence boundary: counters live in-process but are reconciled to the distributed KV.

rtb-journal (Append-Only Auction Log) — every auction writes an AuctionRecord (request id, eligible bids, winner, clearing price, mechanism, reserves), plus async WinNotice/BillingEvent records when notices fire. Append-only, billing-reconcilable; ReconcileCursor tracks settled vs unsettled. Durability boundary: local WAL → object store.

Shared State Plane — distributed KV (#36) holds authoritative budget counters, freq-cap sketches, and model artifacts shared across stateless auction nodes; metrics (#133) collect win/fill/eCPM/pacing/timeout series; model store serves pCTR/win-rate models. Trust boundary: internal, mutually-authenticated.

6. Design Principles

DP1 — Determinism in the mechanism core. rtb-auction MUST be a pure function of (eligible scored bids, mechanism, reserves, tie-break seed): bit-identical AuctionResult every time. No wall-clock, no thread-id, no hash-map iteration order, no float nondeterminism in payment math. Tradeoff: forces explicit seed threading. Operational: enables replay + property tests. Violation: two replays of the same auction disagree → billing disputes, untestable mechanism.

DP2 — The deadline is sacred. The engine MUST return a valid BidResponse (possibly no-bid) within tmax, regardless of bidder behavior. Every external await is deadline-bounded. Tradeoff: partial-result auctions may leave revenue on the table. Operational: tmax violations are paged. Violation: missing the budget = the exchange discards our response = 100% lost revenue for that call.

DP3 — A late bid can never win. Bids arriving after the collection deadline are dropped before the auction. Tradeoff: a slightly-late high bid is discarded. Operational: late-drop rate is a tracked metric. Violation: admitting a late bid makes the auction non-reproducible and can charge for an impression the exchange already cleared.

DP4 — Integer micros, never float, for money. All prices/bids/budgets are integer micros (i64/u64); payment arithmetic uses checked ops. Tradeoff: must manage currency scaling. Operational: overflow = explicit error, not silent wrap. Violation: float rounding produces non-reconciling charges and non-deterministic clearing prices.

DP5 — Truthfulness is an invariant, not a hope. For SecondPrice/VCG, the implementation MUST satisfy DSIC: a bidder's utility is maximized by bidding its true value. Enforced by Myerson-lemma structure (monotone allocation + threshold payment) and verified by property tests. Tradeoff: VCG is harder to compute than GSP. Violation: a non-truthful "second-price" misprices and breaks advertiser trust.

DP6 — Individual rationality (IR). No winner ever pays more than its bid; utility ≥ 0. Enforced in ClearingPriceCalc (price ≤ winning_bid). Violation: charging above bid is theft; advertisers churn; legal exposure.

DP7 — Allocation monotonicity. Raising one's bid weakly improves slot and weakly increases win probability; never demotes. Enforced by rank-by-score with deterministic tie-breaks. Violation: non-monotone allocation breaks the truthful payment rule (Myerson) and creates perverse incentives.

DP8 — Budgets are bounded, not exact. Spend may exceed B only by a bounded, quantified slack (in-flight wins + KV reconciliation lag), target ≤ 2%. Enforced by pacing admission + post-win reconciliation. Tradeoff: hard zero-overspend would require synchronous global locking (kills latency). Violation: unbounded overspend = advertiser overcharge, contractual breach.

DP9 — Frequency caps fail conservative. Probabilistic counters (CMS) overestimate, never underestimate, so caps are never under-enforced beyond a tiny bound. Enforced by choice of sketch with one-sided error. Tradeoff: occasional over-suppression (a user shown slightly fewer ads). Violation: under-counting shows users too many ads = user-experience and policy breach.

DP10 — Backpressure and load-shedding everywhere. Ingress admission, fan-out concurrency, journal write queue, KV reconciliation all bounded; on overload, shed whole auctions early (fast no-bid) rather than blow the budget. Violation: unbounded queues → latency cliff → mass tmax misses.

DP11 — Observability by default. Every auction emits structured outcome (mechanism, winner, clearing price, eligible count, late-drop, NBR); every subsystem emits latency histograms and counters. Violation: silent pacing drift / win-rate collapse / mechanism bug goes undetected until a revenue cliff.

DP12 — Billing is idempotent and reconcilable. Win/billing notices may be retried or lost; the journal dedups by (auction_id, bid_id); charges reconcile exactly-once against the ledger. Violation: double-charge or lost charge = revenue/financial integrity failure.

DP13 — Separate "value" from "bid". Internal value estimates (bid×pCTR) and externally-quoted bids/prices are distinct types; never conflate the advertiser's stated bid with our value estimate or with the clearing price. Violation: type confusion misprices auctions and corrupts pacing feedback.

DP14 — Bounded, mostly-static memory on the hot path. Bid collection uses per-request arenas; models/sketches are fixed-size; no unbounded per-auction allocation. Violation: alloc storms under load spike → GC-free-but-allocator-stall tail latency.

DP15 — Mechanism selection is explicit and logged. auction_type (first/second/GSP/VCG) and all reserves are recorded in the journal per auction. Violation: an unlogged mechanism switch makes outcomes irreproducible and unauditable.

Auction Mechanism Semantics

score_i      = bid_i × pCTR_i × quality_i           -- ranking key (all mechanisms)
eCPM_i       = bid_i × pCTR_i × 1000                 -- reported value-per-mille
rank: sort bids by score desc; deterministic tie-break by (score, bid, seat, bid_id)
Mechanism Allocation Payment (winner) Truthful? Notes
FirstPrice top score wins (1 slot) pays own bid (≥ reserve) No Bidder must shade; revenue = highest bid
SecondPrice / Vickrey top score wins (1 slot) pays 2nd-highest effective bid (= 2nd score / own pCTR·q), clamped to reserve, ≤ own bid Yes (DSIC) Threshold payment = Myerson payment for single unit
GSP (k slots) top-k by score get slots 1..k slot-j winner pays (score_{j+1}) / (pCTR_j · quality_j) (min bid to keep position j); floor at reserve No Locally-envy-free equilibrium; basis of search ads
VCG (k slots) top-k by score get slots 1..k each winner pays the externality: total score others would have gained had this bidder been absent, converted to its own price units Yes (DSIC) Pay harm imposed on others; ≤ GSP payment typically

Single-unit second-price payment (threshold form)

winner = argmax_i score_i
let s2 = max score among losers (0 if none)
threshold_bid = s2 / (pCTR_winner × quality_winner)   -- min bid winner needed to still win
price = max(threshold_bid, reserve)                    -- clamp to reserve
assert price ≤ bid_winner                              -- IR (I2)

GSP multi-slot payment

ranked = [b_1, ..., b_n] by score desc; slots = 1..k (k ≤ #slots, ≤ n)
next_score(j) = score_{j+1}, defined for each filled slot j = 1..k; next_score(k) := 0
price_j = max(next_score(j) / (pCTR_j × quality_j), reserve_j)   -- min bid to hold slot j

VCG externality payment

welfare_without_j(j)     = max total score achievable by others over all slots if j absent
welfare_with_j_excluded(j) = total score of others in the actual allocation (j removed)
externality_score(j)     = welfare_without_j(j) − welfare_with_j_excluded(j)   -- per winner j
price_j = max(externality_score(j) / (pCTR_j × quality_j), reserve_j)   -- score→price units; IR: price_j ≤ bid_j

Reserve / Floor Semantics

Floor type Rule
Hard floor bid < floor ⇒ bid rejected (cannot win); clearing price ≥ floor
Soft floor (legacy) bid < floor ⇒ pay first-price (= bid); bid ≥ floor ⇒ pay second-price; discourages low bids without rejecting
Publisher floor floor set by the publisher/SSP for the impression
Exchange floor floor set by the exchange; effective floor = max(publisher, exchange, dynamic)
Myerson optimal reserve r* reserve where virtual value crosses zero: φ(r*) = 0, with φ(v) = v − (1−F(v))/f(v); F = value distribution
Dynamic per-impression floor r* adjusted by context features (predicted value distribution per segment)

Worked Myerson example: if values are Uniform[0, V], F(v)=v/V, f(v)=1/V, then φ(v)=v−(V−v)=2v−V; φ(r*)=0 ⇒ r* = V/2. Optimal reserve is half the max value regardless of bidder count.

Budget Pacing Semantics

Campaign: budget B over horizon [0,T]; target spend curve S*(t) (even: S*(t)=B·t/T)
Observed cumulative spend S(t); error e(t) = S*(t) − S(t)
Method Update Bid effect
Probabilistic throttling enter auction with prob p_t; p_t ← clamp(p_t + k·e(t)/B, 0, 1) unshaded bid, admitted w.p. p_t
Dual / multiplicative pacing μ_{t+1} = max(0, μ_t + η·(spend_rate − B/T)) (mirror-descent / MW) shade bid_shaded = value / (1 + μ)
PID controller u(t) = Kp·e + Ki·∫e dt + Kd·de/dt; map u→p_t or μ throttle or shade

μ is the Lagrange multiplier on the budget constraint of the LP max Σ value·x s.t. Σ spend·x ≤ B, 0≤x≤1; at optimum, bid in opportunity-cost units value − μ·price, i.e. shade by 1/(1+μ). Anti-windup: clamp integral term; freeze on budget exhaustion.

Frequency-Cap Semantics

cap: ≤ C impressions per (user_id, campaign_id) per window W (sliding)
exact: bucketed counters keyed (user,campaign,window_bucket) with TTL = W
probabilistic: CountMinSketch[(user,campaign)] += 1 on win; estimate ≥ true (one-sided)
              HyperLogLog for distinct reach; Bloom "already capped" fast-path
admit if estimate(user,campaign) < C

Worked Examples

Single-unit second-price (with pCTR)

Bids: A(bid=2.00, pCTR=0.10, q=1) score=0.20; B(bid=3.00, pCTR=0.05, q=1) score=0.15
reserve = 0.50 (price units)
Winner = A (score 0.20 > 0.15)
threshold_bid = score_B / (pCTR_A × q_A) = 0.15 / 0.10 = 1.50
price = max(1.50, 0.50) = 1.50 ; assert 1.50 ≤ 2.00 ✓  (A pays 1.50)

GSP 2-slot

Ranked by score: b1(score .30, pCTR .10), b2(score .20, pCTR .08), b3(score .12)
slot1 price = score_b2 / pCTR_b1 = .20/.10 = 2.00
slot2 price = score_b3 / pCTR_b2 = .12/.08 = 1.50

Pacing shade

value = bid×pCTR = 0.20 ; μ = 0.25 ; bid_shaded_value = 0.20/(1+0.25) = 0.16
(spend rate above B/T ⇒ μ rose ⇒ bids shaded down ⇒ spend slows)

13.6 Pitfalls

  • Effective-bid vs stated-bid in second price: the second-highest score must be converted back to the winner's price units via winner's pCTR·quality, not the runner-up's. Wrong divisor breaks IR and truthfulness.
  • Reserve clamp ordering: clamp to reserve AFTER computing threshold; clamping the score instead misprices.
  • Tie-break instability: an unstable sort makes ties nondeterministic (I6 violation). Use stable sort + explicit total order.
  • Single-bidder second price: with no runner-up, score_2 = 0 ⇒ threshold 0 ⇒ price = reserve; forgetting reserve gives free impression.

  • Sort dominates for large N; for single-slot only the top-2 scores are needed → use a linear max/2nd-max scan (O(N)) instead of full sort when slots=1.

  • No allocation: operate over the arena-backed slice.

  • Off-by-one in next-score indexing: slot-j pays score_{j+1}; the lowest filled slot pays reserve (next-score is 0). Off-by-one charges wrong amount.

15. Phase 3 — VCG Mechanism + Externality Payment

15.1 Objectives

  • Implement vcg multi-slot externality payment: each winner pays the total harm imposed on others.

15.2 Detailed Implementation Steps

  • rtb-auction/src/vcg.rs (applies P5 Clarke/Groves pivot payment; DP5/I1):

  • clearing.rs: dispatch Vcg{slots}.
  • rtb-sim/src/props.rs: VCG truthfulness property (DSIC) — sweep one bidder's bid, assert truthful maximizes utility (I1); VCG IR (I2); GSP-vs-VCG comparison harness (per-auction payment deltas).

15.6 Pitfalls

  • Externality must recompute the counterfactual allocation: welfare_without_j re-assigns others into all slots (they shift up); a naive "sum of others' current scores" is wrong and breaks truthfulness.
  • Slot count after removal: with j removed, lower bidders move up into freed slots; the counterfactual uses the same slot set.
  • Conversion to price units: externality is in score units; divide by pctr_j×q_j to get j's price. Forgetting this conflates value and price (DP13).
  • Reserve interaction: with reserves, VCG payment is max(externality-based, reserve); reserves change the counterfactual welfare (bidders below reserve don't count).

15.7 Performance Concerns

  • Naive VCG is O(k) counterfactual re-rankings each O(N log N) → O(kN log N); for small k and pre-sorted bids, the counterfactual is a prefix shift → O(N) per winner via cumulative score sums. Implement the cumulative-sum optimization.
  • Precompute suffix-score sums once; each winner's externality is a suffix-sum difference.
  • No allocation beyond the awards SmallVec.

15.8 Edge Cases

  • Single winner, no others → externality 0 → price = reserve.
  • More slots than bidders → some slots empty; externalities computed over available bidders only.
  • All-equal bids → externalities equal; deterministic tie-break for slot assignment.
  • Position-discount enabled → suffix sums use position-adjusted scores.

15.9 Failure Analysis

  • Truthfulness fails: almost always the counterfactual welfare is computed without re-ranking others; the cumulative-sum form prevents this if derived correctly; add failing seed.
  • VCG > GSP unexpectedly: check reserve handling in counterfactual.
  • Single-slot inequivalence to second-price: divisor/clamp bug; exact fixture pins it.

19.6 Pitfalls

  • CMS must over-estimate, never under: use min across rows; under-counting (a buggy estimator) shows users too many ads (DP9/I8). Verify the one-sided property in tests.

  • Cap breach (I8 > 0.1%): sketch too small (width under-provisioned) or cross-node merge stalled; widen sketch; check merge cadence.

  • Targeting false-exclude: predicate index bug; differential test predicate index vs linear scan.

20.6 Pitfalls

  • Uncalibrated pCTR corrupts ranking: score = bid×pCTR×q requires calibrated pCTR; raw logistic scores can rank correctly but misprice eCPM and pacing (I12/DP13). Always calibrate before using in money math.
  • Censored data bias: win-rate fit on won auctions only is biased; you must model the censoring (you only see your wins). Use a likelihood that accounts for unobserved competing bids.

20.7 Performance Concerns

  • Logistic inference is a sparse dot-product + sigmoid; keep weights in a cache-friendly map; precompute feature indices.
  • Batched online updates off the hot path; never update under the auction lock.
  • Calibration lookup is O(log bins) (binary search) or O(1) with a lookup table.
  • Win-rate model evaluation O(1) per bid; cache per-segment landscape parameters.

20.8 Edge Cases

  • Cold start (no model) → default pCTR (segment prior); flagged; do not let pCTR=0 zero out all scores.

  • Calibration on too-few samples → widen bins or hold previous calibrator.
  • Win-rate at bid=0 → 0; at bid→∞ → 1; enforce monotonicity in bid.

20.9 Failure Analysis

  • Calibration drift (I12 metric rising): distribution shift; auto-recalibrate; if AUC also drops, roll back model version; runbook win-rate-collapse.md.
  • pCTR collapse to 0 (all no-bids): model load failure or feature pipeline break; fall back to prior; page.
  • Win-rate model over-predicts wins → over-bidding → overspend; cross-check with pacing.

  • Counting unconfirmed wins for spend/cap: charging pacing/cap at auction time over-counts (the exchange may not confirm). Count on confirmed billing notice; reconcile in-flight (I11) with a timeout. Conversely, never under-count confirmed wins.

  • Criterion warm-up too short: under-measures throughput; set warm-up ≥ 5 s.
  • Load-shed too late: shedding after the budget is blown is useless; shed whole auctions early when the admission queue exceeds a depth threshold (DP10).
  • Hot-path allocation regression: a stray Vec/Box per bid blows DP14; heaptrack-gate in CI.
  • Benchmark environment skew: mock-bidder latency must mirror production tail; otherwise fan-out benchmarks are optimistic.

24.7 Performance Concerns

  • Scoring inner loop: branch-free filter encoding; SoA for SIMD-friendly score compute; prefetch.
  • Top-k via bounded heap, not full sort, for multi-slot.
  • Journal enqueue is a bounded MPSC push; never fsync on the auction task.
  • Fan-out: single deadline timer; pooled connections; io_uring socket I/O.
  • Lock-free pacing/cap reads; model arc-swap.

24.8 Edge Cases

  • Burst 10× nominal QPS → load-shed engages; p99 of admitted auctions stays within budget; shed ones get fast no-bid.
  • Hot user (heavy frequency) → Bloom fast-path skips cap re-estimation.
  • One bidder degrades → circuit opens; QPS unaffected.
  • All campaigns paced to 0 → all no-bid (BudgetExhausted) cheaply.

24.9 Failure Analysis

  • Benchmark regression in CI (bench.yml > 5% vs baseline) → block merge; flamegraph the delta.
  • Soak memory growth → leak (arena not freed / unbounded queue); heaptrack localizes.
  • p99 breach under load → identify dominant phase (fan-out vs compute) from span timings; tune.

Documented industry incidents (mechanism-class failures this design guards against).

  • Google Ad Manager unified first-price auction (2019, publicly announced). Google migrated Ad Manager / AdX from a second-price auction with dynamic allocation and a "last look" advantage to a single unified first-price auction for display. The motivating failure class was opacity and inconsistent price computation across the stack — exactly the "Win-rate / fill-rate collapse" and mechanism-selection row above: when buyers cannot reason about the payment rule, bidding behavior (and revenue) shifts unpredictably. This design treats auction_type as explicit, per-auction, and journaled (DP15 — recorded in AuctionRecord), so a mechanism change is auditable rather than silent. See §8 mechanism table, Phase 2/Phase 3, and the "Bid shading exploit / mechanism gaming" Threat Model row.
  • Header bidding's rise as a response to dynamic allocation / "last look" (~2015–2017, widely documented in industry press). Publishers adopted client- and server-side header bidding to run a parallel auction before the ad-server's own auction, neutralizing the exchange's last-look advantage. This is the architectural pressure behind the "Roads Not Taken" client-side vs server-side header-bidding alternative (see Alternative Architectures), and is why this engine is a server-side auction (§1 non-goals) rather than a Prebid.js client wrapper.

These are the only two industry events cited because they are publicly and independently verifiable; no internal or unverifiable postmortems are asserted.

Partitioning strategy: stateless auction nodes scale horizontally; the shared state plane (KV) is the coordination bottleneck. Budget counters shard by campaign_id; freq-cap shards by user_id. Mental Models & First Principles

The compressed insights an RTB-engine expert holds. Each predicts behavior, names the bug class you write without it, and points to where this blueprint applies it.

MM1 — The auction is a deadline, not a computation. Insight: the system's job is to return on time, and the auction is whatever you can compute before the clock runs out — bids are an optional input. Predicts: p99 is dominated by bidder wait, not compute (§4: p50/p95/p99 = 12/60/95 ms vs compute p99 < 5 ms). Bug without it: you optimize scoring while a single slow bidder blows the whole budget. Applied: Phase 5 (gate.rs, DeadlineClock), DP2, I10.

MM2 — A truthful payment is a threshold, not a price you pick. Insight: in a DSIC mechanism the winner's payment is the minimum bid at which it would still have won — it is determined by the others, not chosen. Predicts: if you compute the second-price payment from the runner-up's score without dividing by the winner's pCTR·quality, you break both IR and truthfulness simultaneously. Bug without it: mispriced "second price" that fails the property test. Applied: Phase 1 (second_price.rs), DP5, I1/I2; the threshold = Myerson's lemma payment (B3).

MM3 — Score ranks, money is computed separately, and never the twain in the same units. Insight: score = bid×pCTR×q is a ranking key in abstract units; a payment is a price in money units; converting between them always means dividing by that bidder's pCTR·q. Predicts: VCG externalities and GSP slot prices are in score units until divided back. Bug without it: you charge a score as if it were money (DP13 violation), corrupting billing and pacing feedback. Applied: Phase 2/Phase 3 (gsp.rs, vcg.rs), DP13, §11 Value/Price/Score types.

MM4 — Pacing is a price on your own budget, set by feedback. Insight: the multiplier μ is the opportunity cost of spending a dollar now; you bid in units of value − μ·price, i.e. shade by 1/(1+μ), and μ rises exactly when you spend too fast. Predicts: under sustained over-demand μ climbs until spend rate → B/T; mis-tuned gain → oscillation. Bug without it: you treat pacing as a hard gate and either overspend in bursts or stall. Applied: Phase 6 (dual.rs), DP8, I7; theory P6/P7/P8, B4/B5.

MM5 — A probabilistic counter that errs one way is safe; one that errs both ways is a liability. Insight: a Count-Min Sketch only ever over-estimates, so a frequency cap built on it is at worst slightly conservative — never under-enforced. Predicts: the breach bound is one-sided (§4: ≤ 0.1% over cap, conservative); over-suppression is the failure you tune against, not under-counting. Bug without it: you pick a sketch with two-sided error and show users too many ads (a policy breach). Applied: Phase 7 (cms.rs), DP9, I8; theory P12, B8.

MM6 — You only ever see your own wins, so naive statistics are biased. Insight: win/loss data is censored — you never observe competitors' bids — so fitting a win-rate model on won auctions alone systematically misestimates. Predicts: a model that ignores censoring over-predicts win rate at high bids and corrupts suggested_bid. Bug without it: over-bidding → overspend, blamed wrongly on pacing. Applied: Phase 8 (winrate.rs), I12; theory P9.

MM7 — Determinism is a precondition for both replay and testing, and floats/maps quietly destroy it. Insight: a pure mechanism core that is a function of (bids, mechanism, reserves, seed) can be replayed bit-exactly and property-tested; any f64, HashMap iteration, or wall-clock read silently breaks this. Predicts: a replay digest mismatch always traces to an un-recorded or nondeterministic input. Bug without it: irreproducible billing disputes you cannot debug. Applied: Phase 0/Phase 11 (result.rs::digest, prng.rs), DP1, I6; A05/A20/A30.

MM8 — Count money on confirmation, not on the auction. Insight: a win is a claim; the charge is real only when the billing notice confirms, so spend/cap must move on confirmation and unconfirmed wins must be reserved-then-released. Predicts: counting at auction time over-counts (the exchange may not confirm) and double-counting reservation + confirm over-charges the controller. Bug without it: phantom overspend or leaked reservations. Applied: Phase 6/Phase 9 (inflight.rs, notice.rs), I11, DP12.

MM9 — Hedge the tail, never the body. Insight: a backup request cuts the tail of a fan-out, but hedging every call doubles load; you hedge only past p95. Predicts: blanket hedging at 100K QPS (§4) is self-inflicted DOS; targeted hedging cuts p99 with bounded extra load. Bug without it: a "latency fix" that collapses throughput. Applied: Phase 5 (hedge.rs), P11 Tail-at-Scale; §4 fan-out degree 10–50.

MM10 — The hot path must not allocate, lock, or fsync. Insight: GC-free does not mean stall-free — an allocator storm, a contended mutex, or an inline fsync each produce tail latency just as bad as a GC pause. Predicts: per-bid Box, a global counter Mutex, or fsync on the auction task each show up as a p99 cliff under load. Bug without it: you blame the language for a tail you built. Applied: Phase 12 (bumpalo arena, sharded atomics, MPSC journal enqueue), DP14, A21/A22; §4 memory ceiling 8 GB.

Google Ad Manager / AdX. It built a full-stack exchange-plus-DSP with a "banker" budget service (the lineage visible in RTBkit, R2) that centralizes pacing as a first-class service separate from the auction loop. Prebid Server. It is server-side header bidding: a thin, stateless orchestrator that fans out to external bidder adapters and returns the best bid to the publisher's ad server, with no internal mechanism design or pacing of its own. That wins for publishers who want vendor-neutral demand aggregation without owning an exchange. This blueprint rejected that shape as the whole system (it is a non-goal, §1) because the engineering interest here is the mechanism + pacing + journal core that Prebid delegates away — though Prebid's per-adapter timeout discipline directly informs Phase 5.

The Trade Desk (DSP). It sits on the demand side: it receives BidRequests and must answer within someone else's tmax, so its sophistication is in bid shading and cross-campaign budget optimization rather than running the auction. That wins for a buyer optimizing spend across many exchanges. This engine can host a DSP-side stub (rtb-client, §1) but is fundamentally the auctioneer; the win-rate/landscape model (Phase 8) is the one place its concerns overlap with a DSP's.

Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived from the §4 System Constraints with the formula shown. Inputs are named with their §4 source.

C1 — Peak ingress request bandwidth. Inputs: Auctions/sec/node ≥ 100K (§4 M1); assume a typical OpenRTB JSON BidRequest ≈ 2 KB. Formula: QPS × req_size = 100,000 × 2 KB ≈ 200 MB/s ≈ 1.6 Gb/s ingress per node — already past 1 GbE, so 10 GbE NICs and simd-json in-place parsing (Phase 5) are mandatory, not optional.

C2 — Bidder fan-out egress bandwidth. Inputs: QPS 100K (§4 M1); fan-out degree 10–50 bidders (§4 M6); outbound request ≈ 2 KB. Formula: QPS × fanout × req_size = 100,000 × 30 (mid) × 2 KB ≈ 6 GB/s ≈ 48 Gb/s of bidder-facing traffic. Implication: fan-out egress is ~30× ingress; it dominates the NIC budget and forces connection pooling + co-location (§4 M20, "Network RTT < 20 ms").

C3 — Concurrent in-flight bidder calls. Inputs: QPS 100K (§4 M1); per-bidder timeout up to 90 ms ≈ 0.09 s (§4 M5); fan-out 30 (§4 M6). Formula (Little's law): in-flight = QPS × latency × fanout = 100,000 × 0.09 × 30 ≈ 270,000 concurrent outstanding RPCs per node. Implication: this far exceeds the FD budget below — connections must be multiplexed (HTTP/2, A08), not one socket per call.

C4 — File-descriptor pressure vs budget. Inputs: FD budget < 4096 (§4 M21); distinct bidders 10–50 (§4 M6). Formula: with HTTP/2 multiplexing, FDs ≈ pooled_conns_per_bidder × bidders + ingress_sockets ≈ (4 × 50) + ingress ≈ 200 + ingress, comfortably < 4096. Cross-check against C3: without multiplexing, 270K calls would need 270K FDs — 66× over budget — confirming A08's HTTP/2 choice is load-bearing, not stylistic.

C5 — Auction compute budget per call. Inputs: internal compute p99 < 5 ms (§4 M3); scoring throughput ≥ 5M bid-scores/sec/core (§4 M8); a few-hundred bids. Formula: scoring_time = bids / throughput = 300 / 5,000,000 ≈ 60 µs; well under the 5 ms compute ceiling, leaving headroom for ranking + clearing. Implication: compute is not the bottleneck (confirms MM1) — the 5 ms ceiling is generous slack against the 80–120 ms tmax (M2).

C6 — Per-call CPU vs throughput target. Inputs: Auctions/sec/node 100K (§4 M1); 1–2 cores auction compute (§4 M19). Formula: CPU budget per auction = cores / QPS = 2 / 100,000 = 20 µs/auction of pure compute. Cross-check against C5's 60 µs scoring for 300 bids: the steady-state average auction has far fewer bids (10–50, §4 M6), so ~10–20 µs is realistic — the 100K target is achievable on 2 cores only if there is zero per-call allocation (DP14, MM10).

C7 — pCTR inference cost per auction. Inputs: pCTR inference < 50 µs/bid (§4 M9); bids per auction ≈ 30 (§4 M6, fan-out mid). Formula: inference_per_auction = 50 µs × 30 = 1.5 ms. Implication: at face value pCTR inference exceeds the C6 CPU budget and rivals the C5 compute ceiling — so the < 50 µs must be a sparse dot-product (Phase 8) and inference is the dominant compute term, justifying in-process FTRL (A12) over any RPC model server.

C8 — Frequency-cap lookup load. Inputs: freq-cap lookup p99 < 100 µs (§4 M11); one lookup per eligible bid, ≈ 30/auction; QPS 100K (§4 M1). Formula: lookups/sec = QPS × bids = 100,000 × 30 = 3M lookups/s/node, each < 100 µs but O(1); at depth ≈ 4 CMS hashes that is 12M hash ops/s. Implication: must be lock-free sharded reads (A21), and the Bloom fast-path (Phase 7) matters for heavy-frequency users.

C9 — pCTR model memory footprint. Inputs: memory ceiling 8 GB, mostly static (§4 M10). Formula: a feature-hashed logistic model with 2^24 weights × 8 bytes ≈ 134 MB; comfortably within 8 GB alongside sketches and journal buffers. Implication: the model "fits L2" claim (§4 M9, "pCTR inference") refers to the hot weight working set, not the full table — design feature hashing so common features stay cache-resident (Phase 8).

C10 — Frequency-cap sketch memory. Inputs: memory ceiling 8 GB (§4 M10); freq-cap keys ~billions (Scalability Analysis). Formula: a CMS at width = 2^20, depth = 4, 4-byte counters = 2^20 × 4 × 4 ≈ 16 MB per campaign-group, bounding memory independent of user count. Implication: this is why probabilistic mode exists — exact (user,campaign) counters at billions of keys would blow the 8 GB ceiling; the sketch trades the C5/C8 one-sided error (MM5) for bounded RAM.

C11 — Journal write throughput. Inputs: QPS 100K (§4 M1); one AuctionRecord ≈ 1 KB length-prefixed protobuf. Formula: journal_write = QPS × rec_size = 100,000 × 1 KB ≈ 100 MB/s/node sequential. Implication: within a single NVMe's sequential write band, but only if fsync is batched off the auction task (Phase 9, MM10); a per-record fsync at 100K/s is physically impossible (M14 durability boundary).

C12 — Cluster node count for a target ad-call rate. Inputs: Auctions/sec/node 100K (§4 M1); Availability 99.95% (§4 M22). Formula: for a peak of, say, 2M ad calls/s, nodes = peak / per_node = 2,000,000 / 100,000 = 20 nodes, plus N+1 headroom for hedging/load-shed and drain during rolling upgrade → provision ~24. Implication: the system scales linearly (stateless nodes) until the shared KV plane (Scalability Analysis) becomes the coordination bottleneck.

Alternative Architectures (Roads Not Taken)

Fundamentally different shapes for the same problem; each names the regime where it wins, the real system that embodies it, and why this blueprint rejected it.

ALT1 — Client-side header bidding (auction runs in the browser).

  Browser page
    ├── Prebid.js ──► Bidder A
    ├──         ──► Bidder B   (parallel, in the client)
    └──         ──► Bidder C
         │ best bid as keyword
         ▼
     Publisher ad server (final decision)

Regime where it wins: publishers who want full transparency and to neutralize the ad server's "last look" without trusting a server-side vendor; low integration cost per publisher. Real system: Prebid.js (client-side header bidding). Why rejected here: the auction, pacing, and journal — the entire engineering core of this blueprint (§1, Phase 2/6/9) — would move into untrusted client JavaScript with no deterministic core (DP1), no billing-grade journal (I9), and browser-bound latency. It also cannot enforce server-authoritative budgets/caps. Server-side is the explicit choice (§1 non-goals; see the header-bidding incident note in Failure Modes & Recovery).

ALT2 — Waterfall / daisy-chain mediation (sequential, not sealed-bid).

  Impression ─► Network 1 (floor $2)? ──no──► Network 2 (floor $1)? ──no──► Network 3 ...
                    │ yes                          │ yes
                    ▼                              ▼
                  serve                          serve

Regime where it wins: simple mobile mediation with a small fixed set of demand sources and no real-time bid signal; trivial to operate; no tmax fan-out machinery. Real system: classic mobile-SDK ad mediation waterfalls (pre-header-bidding). Why rejected here: a waterfall is sequential — it adds latency per tier and leaves money on the table (a lower tier may have bid higher), violating both the deadline model (MM1, DP2) and any notion of an efficient/truthful clearing (Phase 1–3). It cannot express GSP/VCG or a single sealed-bid clearing price.

ALT3 — Unified first-price exchange (one mechanism, no per-impression selection).

  Ad call ─► fan-out ─► collect bids ─► FIRST-PRICE clear (highest bid pays its bid) ─► response
                                          (no second/GSP/VCG path)

Regime where it wins: a dominant commercial exchange optimizing for buyer trust and operational simplicity, where transparency of the price rule beats mechanism flexibility — exactly Google Ad Manager's 2019 choice. Real system: Google Ad Manager / AdX unified first-price auction (2019). Why rejected here: this blueprint is a reference engine whose pedagogical and research value is precisely the selectable mechanism space (first/second/GSP/VCG) and their property-tested invariants (Phase 1–3, DP15, I1). Collapsing to one mechanism would delete the most instructive third of the system. The first-price path is still implemented — as one option among four.

ALT4 — Programmatic Guaranteed / PMP (reserved deals, not open auction).

  Impression ─► match against guaranteed/PMP deal (fixed price, priority) ?
                  │ matched                         │ no match
                  ▼                                 ▼
              serve at deal price            fall through to open auction (this engine)

Regime where it wins: premium inventory sold ahead of time at a negotiated fixed price with delivery guarantees; revenue predictability and brand-safety for publisher + buyer. Real system: programmatic guaranteed / private marketplace deals offered by Google Ad Manager, Magnite, PubMatic, OpenX. Why rejected as the core: guaranteed delivery is a forecasting and reservation problem (will I have enough impressions to honor the contract?), not a per-impression sealed-bid clearing problem — a different system with different invariants. This engine models the open-auction fall-through; PMP/guaranteed sits in front of it as priority inventory (a natural future extension, not this blueprint's core).
