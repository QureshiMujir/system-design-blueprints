Decisions (§9) · 30 ADRs

A01

Implementation language

Chosen

Rust (stable)

Rejected

Go, Java, C++, Python

When the rejected choice is right

Go wins when fan-out orchestration dominates and a looser p99 (header-bidding wrapper, ~250 ms budget) makes GC jitter irrelevant and team Go-fluency speeds delivery

Why: GC-free predictable p99 under tmax; strong types for mechanism correctness; portfolio consistency

A02

Build system

Chosen

cargo + make

Rejected

Bazel, CMake

When the rejected choice is right

Bazel wins in a giant polyglot monorepo with remote build caching where cargo's per-crate model can't share a cache across languages

Why: Standard Rust; reproducible via Cargo.lock

A03

Async runtime

Chosen

tokio (multi-thread, work-stealing)

Rejected

async-std, smol, custom (#129)

When the rejected choice is right

A custom thread-per-core runtime (#129, glommio-style) wins when you pin shards to cores and need zero cross-core work-stealing jitter for the very tightest p999

Why: Mature timers/select!/cancellation for deadline-bounded fan-out

A04

Money type

Chosen

integer Micros (i64/u64) newtype

Rejected

f64, Decimal, rust_decimal

When the rejected choice is right

rust_decimal wins at the display/invoicing boundary (#401) where arbitrary-precision human-readable currency, not hot-path arithmetic, is the requirement

Why: No float rounding; deterministic; reconcilable; display via #401

A05

Mechanism core purity

Chosen

pure, no_std-compatible, no clock/IO

Rejected

impure with ambient time

When the rejected choice is right

Ambient-time impurity wins for a throwaway exploratory prototype where replay/property-testing is not a goal and threading a seed everywhere is friction

Why: Determinism (DP1/I6); replay + property tests

A06

OpenRTB wire

Chosen

HTTP/JSON (simd-json) + protobuf (prost)

Rejected

XML, custom binary

When the rejected choice is right

A custom binary wire wins on a fully-owned closed exchange↔bidder link where you control both ends and can drop OpenRTB-compat for max bytes-on-wire efficiency

Why: OpenRTB 2.x is JSON; protobuf for high-QPS internal/OpenRTB 3.0

A07

Ingress HTTP server

Chosen

hyper (HTTP/1.1+2)

Rejected

actix-web, axum raw

When the rejected choice is right

axum/actix-web win when ingress is a feature-rich REST surface (auth middleware, routing, extractors) and the per-request size/timeout knobs of raw hyper are not load-bearing

Why: Low-level control of timeouts/keep-alive/size limits

A08

Bidder transport

Chosen

gRPC over HTTP/2 (tonic, patterns from #155)

Rejected

raw TCP, QUIC, REST

When the rejected choice is right

QUIC (RFC 9000) wins on lossy/high-RTT cross-region bidder links where HTTP/2 head-of-line blocking on a single TCP connection dominates the tail (RFC 9000 deferral, A08)

Why: Deadlines propagate natively; multiplexing; streaming bid responses

A09

Property/auction testing

Chosen

proptest + custom mechanism oracles

Rejected

quickcheck only

When the rejected choice is right

quickcheck alone suffices when you only need lightweight randomized checks without proptest's strategy DSL / structured shrinking machinery

Why: Shrinking; mechanism invariants (truthful/IR/monotone) as properties

A10

Simulation framework

Chosen

custom rtb-sim (seeded, deterministic)

Rejected

external sim, k6

When the rejected choice is right

k6/external load tools win for pure HTTP-throughput soak tests where you need ramp profiles and distributed load generation, not mechanism-property determinism

Why: Mechanism + pacing-stability + replay need full control

A11

Probabilistic counters

Chosen

custom CMS + HLL + Bloom (algorithms from #70)

Rejected

datasketches FFI

When the rejected choice is right

datasketches FFI wins for offline reach/analytics jobs where mergeability across heterogeneous producers and battle-tested estimators matter more than hot-path control

Why: Hot-path control; one-sided-error guarantees (DP9)

A12

pCTR model runtime

Chosen

in-process online logistic regression (FTRL-Proximal)

Rejected

TF-Serving, ONNX runtime

When the rejected choice is right

ONNX/TF-Serving wins when pCTR needs a deep model (DNN/GBDT) whose accuracy lift exceeds the RPC latency cost, e.g. a looser-budget DSP doing offline-scored candidates

Why: < 50 µs inference; online updates; no RPC on hot path

A13

Calibration

Chosen

isotonic regression + Platt scaling

Rejected

none

When the rejected choice is right

Skipping calibration wins only when pCTR is used purely for ranking (argmax) and never multiplied into money — i.e. no eCPM/pacing depends on it

Why: bid×pCTR must be calibrated (I12) for correct ranking/eCPM

A14

Distributed state

Chosen

KV client to #36 (budget, caps, models)

Rejected

etcd, Redis

When the rejected choice is right

Redis wins for a single-region small deployment needing sub-ms shared counters and rich data structures where #36's tunable-consistency model is overkill

Why: Portfolio KV; tunable consistency; async reconcile

A15

Journal storage

Chosen

Rejected

Kafka, DB

When the rejected choice is right

Kafka wins when many independent consumers (analytics, fraud, billing) must each replay the auction stream with their own offsets and a broker is already operated

Why: Billing-grade durability; replay; reconcilable; no broker dep on hot path

A16

Journal encoding

Rejected

When the rejected choice is right

CBOR (RFC 8949) wins when records carry dynamic/heterogeneous schemas without a fixed .proto, or human-debuggable self-describing encoding is needed (A16 deferral)

Why: Compact, schema-evolvable, fast decode for reconcile

A18

A19

Serialization (internal types)

Chosen

Rejected

When the rejected choice is right

serde everywhere wins for config/CLI/non-hot-path types where ergonomics and format-agnosticism beat the zero-copy win that only pays off on the auction hot path

Why: Zero-copy on hot path; serde only at JSON boundary

A20

Hashing (sketch/tie-break)

Chosen

fixed seeded hashers (ahash seeded, xxhash)

Rejected

When the rejected choice is right

DoS-resistant random RandomState wins for hash maps keyed on untrusted external input where collision-DoS resistance matters and determinism does not (no replay)

A21

Concurrency primitives

Chosen

Rejected

When the rejected choice is right

A global Mutex wins for cold-path state (admin config, segment index) updated rarely, where lock-free complexity buys nothing and a mutex is simpler to reason about

Alternative Architectures (Roads Not Taken)

Fundamentally different shapes for the same problem; each names the regime where it wins, the real system that embodies it, and why this blueprint rejected it.

ALT1 — Client-side header bidding (auction runs in the browser).

  Browser page
    ├── Prebid.js ──► Bidder A
    ├──         ──► Bidder B   (parallel, in the client)
    └──         ──► Bidder C
         │ best bid as keyword
         ▼
     Publisher ad server (final decision)

Regime where it wins: publishers who want full transparency and to neutralize the ad server's "last look" without trusting a server-side vendor; low integration cost per publisher. Real system: Prebid.js (client-side header bidding). Why rejected here: the auction, pacing, and journal — the entire engineering core of this blueprint (§1, Phase 2/6/9) — would move into untrusted client JavaScript with no deterministic core (DP1), no billing-grade journal (I9), and browser-bound latency. It also cannot enforce server-authoritative budgets/caps. Server-side is the explicit choice (§1 non-goals; see the header-bidding incident note in Failure Modes & Recovery).

ALT2 — Waterfall / daisy-chain mediation (sequential, not sealed-bid).

  Impression ─► Network 1 (floor $2)? ──no──► Network 2 (floor $1)? ──no──► Network 3 ...
                    │ yes                          │ yes
                    ▼                              ▼
                  serve                          serve

Regime where it wins: simple mobile mediation with a small fixed set of demand sources and no real-time bid signal; trivial to operate; no tmax fan-out machinery. Real system: classic mobile-SDK ad mediation waterfalls (pre-header-bidding). Why rejected here: a waterfall is sequential — it adds latency per tier and leaves money on the table (a lower tier may have bid higher), violating both the deadline model (MM1, DP2) and any notion of an efficient/truthful clearing (Phase 1–3). It cannot express GSP/VCG or a single sealed-bid clearing price.

ALT3 — Unified first-price exchange (one mechanism, no per-impression selection).

  Ad call ─► fan-out ─► collect bids ─► FIRST-PRICE clear (highest bid pays its bid) ─► response
                                          (no second/GSP/VCG path)

Regime where it wins: a dominant commercial exchange optimizing for buyer trust and operational simplicity, where transparency of the price rule beats mechanism flexibility — exactly Google Ad Manager's 2019 choice. Real system: Google Ad Manager / AdX unified first-price auction (2019). Why rejected here: this blueprint is a reference engine whose pedagogical and research value is precisely the selectable mechanism space (first/second/GSP/VCG) and their property-tested invariants (Phase 1–3, DP15, I1). Collapsing to one mechanism would delete the most instructive third of the system. The first-price path is still implemented — as one option among four.

ALT4 — Programmatic Guaranteed / PMP (reserved deals, not open auction).

  Impression ─► match against guaranteed/PMP deal (fixed price, priority) ?
                  │ matched                         │ no match
                  ▼                                 ▼
              serve at deal price            fall through to open auction (this engine)

Regime where it wins: premium inventory sold ahead of time at a negotiated fixed price with delivery guarantees; revenue predictability and brand-safety for publisher + buyer. Real system: programmatic guaranteed / private marketplace deals offered by Google Ad Manager, Magnite, PubMatic, OpenX. Why rejected as the core: guaranteed delivery is a forecasting and reservation problem (will I have enough impressions to honor the contract?), not a per-impression sealed-bid clearing problem — a different system with different invariants. This engine models the open-auction fall-through; PMP/guaranteed sits in front of it as priority inventory (a natural future extension, not this blueprint's core).
