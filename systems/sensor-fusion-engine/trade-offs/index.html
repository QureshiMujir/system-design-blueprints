Decisions (§9) · 30 ADRs

1

Core language

Chosen

Rust 2021, no_std core

Rejected

C++17, C, Zig

When the rejected choice is right

C when the toolchain must target a legacy RTOS without Rust support; C++17 when integrating into an existing ROS/Eigen codebase where FFI overhead exceeds GC pauses.

Why: Bounded latency (no GC), const generics, ownership prevents covariance aliasing, MCU-portable.

2

Linear algebra

Chosen

Own fixed-size Matrix<R,C> (const generics)

Rejected

nalgebra, ndarray, Eigen-FFI

When the rejected choice is right

nalgebra when state dim is dynamic (sliding-window MSCKF with variable clone count); Eigen-FFI when integrating with a Python/C++ toolchain for offline batch optimization.

Why: no_std + zero-alloc + compile-time dims + determinism control; deps add binary/build weight and float-contraction risk.

3

Float precision

Chosen

Type-parameterized Scalar (f64 host, f32 MCU)

Rejected

f64-only, f32-only

When the rejected choice is right

f64-only when the platform always has hardware f64 (high-end DSP, server INS) and mixed-precision testing cost exceeds value.

Why: Host accuracy vs MCU footprint; one code path, two instantiations.

4

FMA / contraction

Chosen

Disabled by default (-C target-feature explicit)

Rejected

allow contraction

When the rejected choice is right

Allow contraction when bit-exact replay across CPUs is not required and throughput is the primary constraint (e.g., offline batch processing).

Why: Determinism + reproducible replay; opt-in for perf.

5

Attitude representation

Chosen

Hamilton quaternion + 3-DOF error

Rejected

JPL quaternion, Euler, DCM-only

When the rejected choice is right

JPL quaternion in aerospace software that already uses JPL convention throughout (e.g., JPL/NASA ground-truth pipelines) to avoid sign-flip adapter bugs.

Why: Hamilton single-sourced; error-state avoids norm constraint.

Rejected

When the rejected choice is right

ENU-only in ground-robotics stacks (ROS convention) where all sensors, control, and visualization assume ENU and frame conversion overhead adds risk.

Why: Aerospace/INS convention; ENU via adapter flag.

Core filter

Chosen

Rejected

Why: Minimal attitude DOF, linearization validity, production-proven.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1: Factor Graph / Batch Smoother

IMU preintegration factors  →  ┌──────────────────────┐
GPS range/Doppler factors  →  │  Factor Graph        │
Visual landmark factors   →  │  iSAM2 / GTSAM       │  →  MAP estimate (full trajectory)
                              └──────────────────────┘
                                  Incremental Bayes tree update

Regime where it wins: Post-processing or sliding-window offline smoothing (AUV mapping, aerial survey) where the entire trajectory is needed at once, loop closure is mandatory, and compute is not hard-real-time. Can relinearize old factors when new information arrives.

Real system: GTSAM gtsam/navigation/ (IMU preintegration factors, Rao-Blackwellized states), iSAM2 incremental Bayes tree.

Why rejected: Non-causal (reads future measurements), O(window²) memory, cannot run hard-RT at IMU rate, requires a heap and dynamic graph structure incompatible with no_std. The ESKF online estimate is the input to any offline smoother — they are complementary, not competing.

Alt-2: Particle Filter / Sequential Monte Carlo

N particles (x_i, w_i)  →  motion model resample  →  measurement weight  →  reweight  →  resample
                                                              ↕
                                                  effective sample size check

Regime where it wins: Non-Gaussian, multi-modal posteriors — urban-canyon GPS (multiple hypotheses for position), kidnapped-robot recovery, highly nonlinear transitions. No Jacobian required; handles hard discontinuities.

Real system: Monte-Carlo Localization in ROS (amcl), FastSLAM. Also used in underwater acoustic positioning.

Why rejected: O(N × state-dim) memory and compute per step; N = 500–10,000 for adequate coverage in 15-DOF, yielding ~10× the UKF cost; no bounded worst-case compute; degeneracy under high-dimensional Gaussian process noise; the target platforms (Cortex-M4F) cannot support it. Gaussian assumption is valid for IMU + GNSS in open sky.

Alt-3: Complementary Filter (Attitude-only, No Position/Velocity)

IMU gyro  →  integrate  →  ┐
                           ├──(weighted blend)──→  attitude quaternion only
IMU accel + mag  →  tilt  →┘

Regime where it wins: Attitude-only applications (AHRS for gimbal, VR headset, handheld instrument) where memory < 2 KB, no position estimation needed, and a 30-line implementation is preferable to a full ESKF. Runs on Cortex-M0.

Real system: xioTechnologies Fusion (Madgwick), Mahony filter, STMicroelectronics MotionFX library.

Why rejected: No position or velocity; no principled covariance; no consistency monitoring; magnetometer disturbance handling is heuristic; no OOSM. Retained as Phase 4 baseline and DeadReckon fallback for exactly the cases where ESKF fails (no aiding, attitude-only suffices).

Alt-4: Tightly-Coupled INS/GNSS (Raw Pseudorange)

GNSS receiver  →  raw pseudoranges + Doppler  →  ┐
                                                  ├──  EKF/ESKF measurement update
IMU  →  strapdown predict  ────────────────────→  ┘
                 ↑  estimates receiver clock bias + drift, per-satellite geometry

Regime where it wins: High-precision navigation (surveying, precision agriculture, autonomous landing) where loosely-coupled solution quality is insufficient, GNSS signal is intermittent, or receiver-level integrity monitoring is required. Enables centimeter-level RTK fusion.

Real system: PX4 EKF2 (ecl tightly-coupled option), NovAtel SPAN, u-blox ADR (automotive dead-reckoning).

Why rejected: Requires access to raw GNSS pseudoranges (not available from NMEA/UBX NAV-PVT, the documented interface in §5.4); adds per-satellite states (4–12 clock/bias states) growing n to ~27+; satellite geometry and ionospheric modeling increase implementation complexity by an order of magnitude. Explicitly deferred per §1.3 ("loosely coupled" is the documented coupling level).
