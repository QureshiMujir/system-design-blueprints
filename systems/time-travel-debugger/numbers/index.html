Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from the § System Constraints table (§4). Formulas shown; no asserted-only numbers.

  1. Bytes per recorded minute (typical). From §4 trace growth 1–50 MB/s: 1 MB/s × 60 s = 60 MB/min (light) to 50 MB/s × 60 s = 3000 MB/min ≈ 3 GB/min (heavy). Confirms the §4 "50 MB – 3 GB per recorded minute" row.
  2. One-hour recording footprint. 60 MB/min × 60 min = 3.6 GB (light) to 3 GB/min × 60 = 180 GB (heavy). Implies retention/quota policy on .ttz artifacts (§ Scalability Analysis, storage growth) — heavy workloads cannot be kept indefinitely.
  3. Event-record cache budget. §4 caps supervisor RSS at ≤ 256 MB excl. checkpoints. A fixed-size TraceEvent decode record ≈ RegisterFile (16×8 + rip + rflags + 2 base = ~152 B) + tick(8) + kind(1) + small payload header (~16 B) ≈ 180 B. A 16 MB decode/ring budget holds 16 MB / 180 B ≈ 93,000 in-flight events — ample headroom inside the 256 MB ceiling.
  4. FD budget headroom. §4 caps total FDs at ≤ 64. Per §4 "1 perf fd/thread": with trace files (~4) + tracee (~1) + DAP socket (1), the perf-fd budget is 64 − 6 ≈ 58 → up to ~58 concurrent tracee threads can each hold a pinned counter before exhausting FDs (ties to P5 per-thread counters, §5.2).
  5. Checkpoint interval in wall-clock vs ticks. §4 default = every ~2–5 s of replay OR N = 2M ticks. If replay retires branches at, say, the count that fills 2M ticks in 2 s, that is 2,000,000 / 2 s = 1,000,000 ticks/s of replay — the cross-check that the two interval expressions are consistent at the low end.
  6. Seek latency = interval replay time. §4: seek latency = replay time from nearest checkpoint ≤ T. With a 2 s interval (item 5), worst-case seek ≈ 2 s; reverse-continue worst case = seek + replay-scan to last hit ≈ one full interval ≈ 2 s (§4 reverse-continue row). Halving the interval to 1 s halves worst-case seek but doubles checkpoint count.
  7. Checkpoint count for a 10-minute replay. 600 s / 2 s = 300 checkpoints at the default interval. With a logarithmic spread (MM8, §8.7) the retained count is far lower; this is the naive upper bound the eviction policy must cut.
  8. Checkpoint memory pressure. §4: COW checkpoint cost = pages dirtied since last checkpoint. For a tracee dirtying, e.g., 10 MB of writable working set per 2 s interval, 300 naive checkpoints would cost 10 MB × 300 = 3 GB — over any sane ceiling, which is exactly why Phase 8 mandates eviction + logarithmic spread (§ Failure Modes & Recovery, OOM row).
  9. Single-step stretch cost. §4 single-step rate 10k–500k steps/s. To cover a skid residual of, say, 300 branches (§3.4) at the slow end: 300 / 10,000 = 30 ms; at the fast end 300 / 500,000 = 0.6 ms. This is why P7 keeps the skid margin tight (§3.6) — every convergence pays it.
  10. Tick read amortization. §4 tick read < 1 µs via the mmapped counter page. At a sync point per syscall, a syscall-heavy workload doing 100k syscalls/s pays 100,000 × 1 µs = 100 ms/s ≈ 10% just in tick reads — bounding how cheap the read path must stay (P3, §3.7 rdpmc fast path).
  11. Divergence-check cost. With regs_hash (§3.2) the per-sync-point compare is O(1) (one u64 compare). At 100k sync points/s that is 100,000 comparisons/s — negligible CPU, so the §4 replay-overhead target (1.1×–1.8×) is dominated by injection and convergence, not by the divergence check (P2, §7.7).
  12. Blob spill threshold sizing. §4 trace I/O is dominated by syscall output bytes. With a 4 KB inline/blob threshold (§4.2), a read(fd, buf, 1 MB) spills 1 MB / 4 KB = 256 page-sized chunks to the blob store rather than bloating the event log — keeping event records L2-resident (§4 CPU/cache note, §4.7).
