299 — Time-Travel Debugger

Project Number: 299 Project Name: Time-Travel Debugger Owner: Mujir Qureshi Document: FINAL_BLUEPRINT.md Status: specification — locked

1. Goal

Build ttdb: a record-and-replay deterministic debugger for native Linux x86-64 processes (rr-style) supporting REVERSE EXECUTION. Record a process once; replay it deterministically infinitely; seek to any point in time; step and continue backward; query state at any tick.

Precise engineering statement. A process is deterministic given its nondeterministic inputs. ttdb records the small set of nondeterministic inputs — syscall results, signal-delivery points, thread-scheduling order, nondeterministic instructions (RDTSC/RDRAND/CPUID), and incoming shared-memory effects — into an append-only tick-indexed Trace. On replay the recorded process re-executes with real syscalls suppressed and recorded results injected; identical inputs ⇒ identical register/memory state. Async events (signals) are re-delivered at the exact same instruction using a hardware-counter Tick coordinate. COW-fork Checkpoints let a Session seek to any tick by restoring the nearest ≤ T checkpoint and replaying forward, which is also the substrate for reverse execution.

System boundaries.

  • IN: single-process (multi-thread) native ELF x86-64 Linux targets; ptrace-based supervision; perf_event_open retired-conditional-branch counting; trace persistence; forward + reverse debugging; DAP server.
  • OUT (non-goals): true-parallel multicore recording (PhaseDeferred("FINAL_BLUEPRINT §12.5")); cross-architecture portability beyond x86-64 (PhaseDeferred("FINAL_BLUEPRINT §12.3")); GPU/DMA device replay; kernel-mode / hypervisor recording; recording across exec of setuid binaries; recording sandboxed JIT that maps RWX and rewrites itself unboundedly (best-effort only); distributed multi-process record-replay; source-level expression evaluation beyond DWARF line/var lookup.
  • Contrast note (language-VM time-travel): a managed runtime can time-travel via event-sourcing + periodic state snapshots (deterministic command log + heap snapshot) instead of hardware counters — cheaper, coarser, in-VM only. ttdb targets the harder native case; §2 cross-links the contrast.

Deployment model. CLI binary ttdb + library libttdb. Three modes: ttdb record -- <prog args> → writes trace/ dir; ttdb replay trace/ → interactive REPL or DAP; ttdb dap trace/ → Debug Adapter Protocol server for editor frontends. Single host, single user, no network surface in core (DAP optional localhost socket). Linux ≥ 4.x, x86-64 with PMU (perf hardware retired-branch counter) and hardware debug registers DR0–DR3.

Target users. Systems engineers debugging nondeterministic native crashes (heisenbugs, data races, use-after-free); kernel/runtime developers; CI flaky-test forensics; security researchers doing reverse triage. Operators run it locally or on a CI worker; developers extend the DAP layer and trace format.

Phase 0 deliverable — numbered crate list.

  1. ttdb-core — shared types: Tick, RegisterFile, AddressSpace, TraceEvent, error enums, no I/O.
  2. ttdb-ptrace — nix-backed ptrace supervisor: attach/spawn, stop/cont, GETREGS/SETREGS, peek/poke, Tracee state machine.
  3. ttdb-perf — perf_event_open(2) FFI wrapper; retired-conditional-branch counter; Tick read; skid handling.
  4. ttdb-trace — append-only tick-indexed Trace/EventLog writer + reader; on-disk format; serialization.
  5. ttdb-record — Recorder: syscall interception (seccomp-BPF + PTRACE_SYSCALL), result+memory capture, scheduling serialization, signal/RDTSC trapping.
  6. ttdb-replay — Replayer: syscall suppression + injection, signal re-delivery at ticks, divergence detection.
  7. ttdb-checkpoint — Checkpoint engine: COW fork + memory-diff snapshots; ReplayTimeline seek.
  8. ttdb-debug — breakpoints (int3 sw / hw), single-step, reverse-step/continue, watchpoints, state query.
  9. ttdb-dap — Debug Adapter Protocol server with reverse-execution extensions.
  10. ttdb-cli — ttdb binary, arg parsing, REPL, subcommands.
  11. ttdb-testkit — fixtures, divergence harness, differential replay, deterministic test programs.

What later phases unlock. P1 supervisor → P2 record syscalls → P3 the Tick coordinate (the spine of everything) → P4 durable trace → P5 deterministic single-tracee scheduling → P6 async event capture → P7 the replay engine (first end-to-end record→replay) → P8 checkpoints + timeline (first seek) → P9 forward debugging → P10 reverse execution (the headline feature) → P11 watchpoints fwd/rev → P12 arbitrary-tick state reconstruction → P13 DAP → P14 persistence/portability/overhead tuning.

Deferred features. PhaseDeferred("FINAL_BLUEPRINT §12.5") true-parallel multicore recording (chunk-and-merge / hardware-transactional approaches). PhaseDeferred("FINAL_BLUEPRINT §12.3") perf-counter portability across microarchitectures (per-CPU skid calibration tables, Intel PT alternative). PhaseDeferred("FINAL_BLUEPRINT §6.6") full AVX-512/xsave extended-state capture and replay. PhaseDeferred("FINAL_BLUEPRINT §12.4") shared-memory inter-process race recording.

Estimated timeline. Phase 0 (crates 1–4 scaffold + P1–P3 spine): 8–12 weeks. Full P1–P14: 9–14 months for one engineer, ~5–7 months for a small team.

Recommended language: Rust. Rationale: ptrace via nix (typed ptrace::*); perf_event_open via direct libc::syscall FFI; memory-safe supervisor handling raw tracee bytes without UB; precise unsafe boundaries around FFI; zero-cost abstractions for the hot replay loop; no GC pauses to perturb tick counts.

  • Rejected C (rr's language): maximal control but no borrow checker; supervisor manipulates raw register/memory buffers where a single aliasing bug silently corrupts replay — Rust's ownership catches this class at compile time.
  • Rejected Python: an instruction-counting supervisor single-steps millions of instructions; interpreter overhead makes the final single-step stretch and divergence scans untenable.
  • Rejected Go: GC perturbs timing; the M:N goroutine scheduler fights ptrace, which requires the supervisor thread that issued PTRACE_ATTACH to be the one that calls waitpid and continues the tracee — Go can migrate goroutines across OS threads, breaking the ptrace owner-thread contract.

Prerequisites. OS internals: process model, virtual memory, COW fork, /proc. Linux ptrace + signal delivery semantics; seccomp-BPF; perf PMU counters + skid. x86-64: registers, RFLAGS.TF single-step, int3, debug registers DR0–DR7, RDTSC/RDRAND/CPUID. Concurrency: thread stop/run, race conditions. Binary formats: ELF, DWARF (for §12.9 var/line lookup). Debugger concepts: breakpoints, watchpoints, stack unwinding. Determinism + replay theory.

2. Why Build This

Unique systems knowledge taught. The deepest practical lesson in determinism as an engineering substrate: identifying the complete frontier of nondeterminism in a real OS/ISA and proving you have closed it (any miss ⇒ divergence). Hardware performance counters as a logical clock over instructions. ptrace as a kernel-mediated debugger substrate. COW snapshots as time-travel. Signal-delivery timing at instruction granularity.

Historical/architectural significance. Record-replay traces to ReVirt (full-VM, OSDI 2002) and "Debugging OS with Time-Traveling VMs" (ATC 2005). Mozilla rr (ATC 2017) made it deployable on commodity hardware by serializing threads onto one core and using retired-branch counters instead of VM-level logging — the architecture this project follows. Microsoft TTD/WinDbg and Pernosco extended it to omniscient/queryable debugging. Understanding rr's design is a rite of passage in systems debugging.

Engineering muscles developed. Reasoning about determinism boundaries; FFI safety around unsafe; precise instruction-level timing; building a state machine that must be bit-exact across two executions; divergence-as-a-first-class-signal debugging (the tool debugs itself); append-only log design; snapshot/restore engineering; protocol implementation (DAP).

Production engineering concepts exercised. Observability of an inherently invisible process; reproducibility (the entire point); resource bounding (trace growth, checkpoint memory); failure containment (a single nondeterminism miss must be detected, not silently wrong); compatibility (trace format must survive tool upgrades).

Cross-links to related projects.

  • Debugger (DWARF/breakpoints/unwinding) — ttdb is a debugger superset; reuse stack-unwinding + symbolication.
  • Profiler / Tracer — shares perf_event_open + ptrace + syscall interception; a tracer is record-only.
  • Deterministic replay engine / event-sourced store — same determinism theory; contrast native-counter vs command-log replay.
  • OS kernel — exercises the exact kernel interfaces (ptrace, signals, COW fork, seccomp) the kernel project implements.
  • VM / hypervisor — full-VM record-replay (ReVirt) is the heavyweight cousin; contrast device/DMA nondeterminism.

Calibration value. After this, "is this bug reproducible?" is a solved meta-question, and you carry a permanent mental model of every nondeterminism source in a Unix process — a model that sharpens all future systems debugging.

What mastery looks like. After building ttdb, the engineer can:

  • Enumerate the complete nondeterminism frontier of a Unix process (syscalls, signals, thread interleaving, nondeterministic instructions, address-space layout, vDSO) and prove closure by treating any escape as loud divergence — built in Phase 2, Phase 5, Phase 6, hardened in Phase 14.
  • Use a hardware performance counter as a logical clock over instructions, including the count-then-step two-stage convergence that defeats PMU skid — built in Phase 3.
  • Design an append-only, crash-only, versioned on-disk log that survives kill -9 mid-write and replays its valid prefix — built in Phase 4.
  • Turn copy-on-write fork into a time machine: bounded-memory checkpoints + replay-forward seeking that make random seek(T) and reverse execution cost one interval, not a full replay — built in Phase 8.
  • Implement reverse-continue / reverse-step / reverse-watch as pure functions of a trace (checkpoint + forward scan), never running a CPU backward — built in Phase 10 and Phase 11.
  • Reconstruct full program state (registers, memory, stack, DWARF-resolved variables) at any tick without re-recording — built in Phase 9 and Phase 12.
  • Bridge a forward-only protocol (DAP) onto a bidirectional timeline and reason about where its model leaks — built in Phase 13.
  • Debug a system that must be bit-exact across two executions, where divergence-as-signal is the primary debugging instrument (the tool debugs itself) — the discipline running through Phase 7 onward.

Recorder. Owns the tracee during recording. Spawns child, sets PTRACE_TRACEME+exec, installs seccomp-BPF filter to trap syscalls cheaply, drives the run loop, and at each nondeterminism point writes a TraceEvent tagged with the current Tick. Captures syscall return value plus every byte the kernel wrote into tracee memory (output buffers). Serializes all tracee threads onto one logical core so scheduling is a recordable sequence, not a true race.

Replayer. Re-spawns the same binary, drives an identical run loop, but at each syscall instead of letting the kernel execute it, it reads the recorded TraceEvent, writes the recorded memory effects back into the tracee, sets the recorded return register, and skips the instruction. Signals are re-delivered when the perf counter reaches the recorded Tick (then IP+regs match, then single-step the residual). Continuously compares observed regs/IP at known points against the trace; any mismatch = Diverged, surfaced immediately.

Tracee. The child process under ptrace. State machine {Running, AtSyscallEntry, AtSyscallExit, Stopped, Checkpointed, Diverged}. Inspected via PTRACE_GETREGS (registers) and process_vm_readv/PTRACE_PEEKDATA (memory). Controlled via PTRACE_CONT/PTRACE_SYSCALL/PTRACE_SINGLESTEP/PTRACE_SETREGS.

PerfCtr (ttdb-perf). Per-tracee-thread perf_event_open counting retired conditional branches (the unit that makes a deterministic, reproducible instruction clock; raw instruction count is less reliable across reps). Read to obtain the current Tick; programmed to interrupt (PMI) near a target tick so the supervisor can single-step the final stretch precisely (skid forces this two-stage approach).

Trace / EventLog (ttdb-trace). Append-only, tick-indexed, on-disk. Sequence of TraceEvents plus side-channel MmapData blobs (large memory captures stored out-of-line). Read sequentially during replay; binary-searchable by tick for seek. Versioned header; CRC per block; never mutated after write (crash-only).

Checkpoint Engine (ttdb-checkpoint). Periodically COW-forks the replaying tracee (or captures a memory diff) producing Checkpoint{tick, mem_snapshot, regs}. ReplayTimeline indexes checkpoints by tick; seek(T) = restore nearest checkpoint ≤ T, then replay forward to T. Substrate for fast random seek and all reverse operations.

Session / Debug Engine (ttdb-debug). Orchestrates replay + checkpoints into a debugger. Forward: int3/hardware breakpoints, single-step, stack unwinding, variable inspection via DWARF. Reverse: reverse-continue/step implemented as "restore an earlier checkpoint, replay forward recording breakpoint hits, stop at the last hit before current time." Watchpoints forward via DR0–DR3, reverse via replay scan. Answers "state at tick T" by seeking and reading regs/memory.

Target (DAP, ttdb-dap). Implements the Debug Adapter Protocol so editors drive ttdb. Standard requests (setBreakpoints, stackTrace, variables, continue, next, stepIn) plus reverse extensions (stepBack, reverseContinue, custom seekTick). Bridges DAP's forward-only worldview onto the timeline.

4. System Constraints

Constraint Target Notes
Recording overhead (CPU-bound workload) 1.2×–2× wall-clock rr-class; syscall-heavy workloads worse
Recording overhead (syscall-heavy) up to 3–5× each syscall = trap + memory capture
Replay overhead (no debugging) 1.1×–1.8× no real syscalls, but injection + divergence checks
Checkpoint interval (default) every ~2–5 s of replay OR every N=2M ticks tunable; memory-vs-seek-latency tradeoff
Checkpoint memory cost COW: pages dirtied since last; diff: changed pages only bounded by writable working set
Seek latency to arbitrary tick T = replay time from nearest checkpoint ≤ T bounded by checkpoint interval
reverse-continue latency = seek to prior checkpoint + replay-scan to last hit worst case = one full interval replay
reverse-step latency ≤ reverse-continue (target is one tick back) typically restore-nearest + short replay
Trace growth rate ~1–50 MB/s of recorded execution dominated by syscall output bytes + MmapData
Trace on-disk per recorded minute (typical) 50 MB – 3 GB workload dependent; large reads dominate
Supervisor memory ceiling ≤ 256 MB resident excl. tracee + checkpoints event ring buffers, indices
Single-step rate (final stretch) 10k–500k steps/s kernel round-trip bound; minimize stretch length
Concurrency model one tracee thread runnable at a time (record) serialization invariant, §7
Tick read latency < 1 µs read of mmapped perf counter page
Startup (record) < 50 ms to first instruction spawn + seccomp install + perf open
Shutdown flush + fsync trace; trace valid after kill -9 mid-record crash-only, §6
Recovery: partial trace replay up to last complete event truncate-on-torn-tail, §7
Availability local tool; no uptime SLO "available" = trace replays deterministically
FD budget ≤ 64 fds: trace files + 1 perf fd/thread + tracee
Divergence detection latency at next checkpointed/syscall point bounded by event spacing

CPU/cache: hot replay loop must keep TraceEvent decode in L2; event records fixed-size where possible. NUMA: pin supervisor + tracee to one node (single-core serialization already implies one CPU). No network RTT in core. RTO for a crashed replay session: re-seek from last good checkpoint, < interval seconds.

6. Design Principles

  1. Determinism over convenience. Every nondeterministic input must be recorded or eliminated; if a source is unhandled, replay must diverge loudly, never silently produce wrong state. Tradeoff: slower record (must trap more). Operational: divergence is a first-class alert. Violation: silent wrong replay = worse than no tool (engineers trust a lie).
  2. Divergence is detected, never tolerated. At every re-synchronization point (syscall, signal tick, checkpoint) compare observed vs recorded regs/IP. Tradeoff: extra compares cost replay time. Operational: a Diverged event names the exact tick + register that disagreed. Violation: undetected drift corrupts all downstream debugging.
  3. The Tick is the only clock. All temporal coordinates are (Tick, IP, regs), never wall-clock. Tradeoff: tied to a reproducible PMU counter (microarch-sensitive, §12.3). Operational: traces are portable only across identical-enough CPUs. Violation: wall-clock ordering is nonreproducible → replay impossible.
  4. Single runnable tracee thread during record. Serialize threads onto one core; record context-switch points as events. Tradeoff: no true parallelism in recorded run (slower for parallel workloads). Operational: scheduling becomes a deterministic, replayable sequence. Violation: true concurrent execution = unrecordable memory races (§12.4).
  5. Append-only, crash-only trace. The trace is written once, never mutated; a torn tail is truncated on read; no in-place edits. Tradeoff: storage grows monotonically. Operational: kill -9 mid-record still yields a replayable prefix. Violation: in-place mutation risks corrupting already-recorded history.
  6. Suppress, then inject (replay). On replay the tracee never performs real syscalls; the recorded result + memory effects are injected. Tradeoff: must perfectly model every syscall's memory side effects. Operational: replay is hermetic (no real I/O, safe to run anywhere). Violation: a real syscall during replay re-introduces nondeterminism.
  7. Two-stage convergence (count then step). Use the perf counter to get near a target tick, then single-step the residual to the exact instruction (skid means counters overshoot/undershoot). Tradeoff: single-step is slow → keep the residual short. Operational: bounded, predictable convergence. Violation: trusting the raw counter places async events one branch early/late → mismatch.
  8. Checkpoints are the time machine. Random seek and all reverse ops = restore nearest checkpoint ≤ T then replay forward. Tradeoff: checkpoint memory vs seek latency (tunable interval). Operational: reverse-continue cost is bounded by one interval. Violation: linear replay-from-start makes reverse ops unusably slow.
  9. Explicit ownership of the tracee. Exactly one supervisor thread owns ptrace control of a given tracee (the thread that attached). Tradeoff: no multi-threaded supervisor parallelism over one tracee. Operational: avoids ESRCH/owner-thread bugs. Violation: cross-thread ptrace calls fail unpredictably (the Go rejection rationale).
  10. Hermetic, reproducible replay environment. Replay re-creates the recorded address-space layout (disable ASLR / record mmap addresses); same binary, same env recorded. Tradeoff: must pin/record layout. Operational: addresses in the trace are meaningful across replays. Violation: ASLR variance shifts addresses → breakpoints/divergence break.
  11. Observability by default. Every event, tick, divergence, checkpoint, and seek emits structured telemetry. Tradeoff: log volume. Operational: the tool is debuggable. Violation: a determinism bug with no telemetry is undebuggable.
  12. Bounded resource usage. Trace growth, checkpoint memory, single-step stretch length all have ceilings + backpressure. Tradeoff: may pause record to flush. Operational: never OOM the host. Violation: unbounded MmapData captures fill the disk mid-record.
  13. Stable trace wire format. On-disk trace has a versioned, length-prefixed, CRC'd format with forward/backward compat rules (§ Compatibility & Versioning). Tradeoff: format ceremony. Operational: old traces replay on new ttdb. Violation: format drift orphans recorded traces.
  14. Minimal trusted FFI surface. All unsafe (ptrace, perf, /proc/mem) is confined to ttdb-ptrace/ttdb-perf with safe wrappers; the rest is safe Rust. Tradeoff: wrapper boilerplate. Operational: audit surface is small. Violation: scattered unsafe makes silent-corruption bugs hard to find.
  15. Record once, replay infinitely, never re-record to answer a question. All queries (state@T, reverse ops) operate on the existing trace. Tradeoff: trace must capture enough up front. Operational: deterministic, repeatable investigations. Violation: re-recording reintroduces nondeterminism and breaks reproducibility.

8. Domain Model

8.11 Timeline / event model

Recorded execution is a totally ordered sequence of instructions; the Tick (retired conditional-branch count) is a monotonic logical clock over that sequence. Nondeterminism enters only at discrete points; each becomes a TraceEvent anchored to a (Tick, IP, regs) coordinate. The timeline is the trace; "now" during replay is the current tick; seeking moves "now" along the timeline.

EBNF (logical trace structure):

Trace        = Header , { Block } , Footer ;
Header       = magic , version , arch , binary_id , aslr_flag , perf_event_cfg ;
Block        = block_len , crc32 , Event ;
Event        = tick , kind , RegSnapshot , Payload ;
kind         = "SyscallEntry" | "SyscallExit" | "Signal"
             | "Sched" | "RdtscRdrandCpuid" | "MmapData" ;
RegSnapshot  = gp_regs , rip , rflags , [ fp_state_ref ] ;   (* compact *)
Payload      = SyscallPayload | SignalPayload | SchedPayload
             | NondetInsnPayload | MmapRef ;
SyscallPayload    = nr , args[6] , retval , { MemWrite } ;
MemWrite          = addr , len , data_ref ;                  (* bytes kernel wrote *)
SignalPayload     = signo , siginfo , delivery_anchor ;
SchedPayload      = from_tid , to_tid ;
NondetInsnPayload = insn_kind , result_regs ;                (* RAX/RDX, etc. *)
MmapRef           = blob_id , addr , len ;                   (* large data out-of-line *)

8.12 Trace + tick + checkpoint schema (on-disk, lightweight)

  • Trace: directory trace/ = header.bin, events.log (append-only), blobs/ (MmapData payloads), checkpoints/ (snapshot images), index.bin (tick→file-offset, built lazily).
  • Tick: u64, retired conditional branches since record start for the current tracee thread; per-thread counters sequenced via Sched events.
  • Checkpoint: { tick:u64, regs:RegisterFile, mem:MemSnapshot, fd_table:FdSnapshot }; MemSnapshot = COW-fork pid (live) or page-set diff (persisted).

8.13 Worked example

Program: t = time(NULL); if (t & 1) A(); else B();

  • Record. At the time syscall: SyscallEntry(nr=201,...) then kernel returns 1000 into RAX → SyscallExit(nr=201, retval=1000, MemWrite none here). Tick at exit = e.g. 540. Program computes 1000 & 1 == 0 → branch to B() (this branch increments the tick). Recorder logs nothing more for the branch — it is deterministic given RAX=1000.
  • Replay. Re-run to the time syscall; at SyscallEntry, Replayer reads recorded SyscallExit, sets RAX=1000, advances RIP past the syscall instruction, does NOT enter the kernel. Program recomputes 1000 & 1 == 0 → branch to B(). Same branch, same tick progression. Observed regs at the next sync point match recorded ⇒ no divergence.
  • Counterfactual (bug). If time were not trapped, replay's real time() returns 2000; a value whose low bit flips to 1 routes to A() → branch differs → tick stream diverges → I1/I6 fire at the next compare with divergence{tick, reg=rip}.

Recorder            Tracee              Kernel            Trace
   | spawn+TRACEME --->|                                   |
   | install seccomp ->|                                   |
   | PTRACE_CONT ----->| run...                            |
   |                   |-- syscall -->| (SECCOMP_RET_TRACE)|
   |<-- ptrace stop (syscall-entry) --|                    |
   | read Tick, regs   |              |                    |
   | append SyscallEntry --------------------------------->|
   | PTRACE_SYSCALL -->| kernel executes syscall --------->|
   |<-- ptrace stop (syscall-exit) ---|                    |

   | append SyscallExit ---------------------------------->|
   | PTRACE_CONT ----->| run...                            |
   | (async signal pending) read Tick anchor               |
   | append Signal{tick,anchor} -------------------------->|
   | deliver signal via PTRACE_CONT(sig) ->|               |

8.15 Replay loop (sequence)

Replayer            Tracee                         Trace
   | re-spawn (ASLR off / recorded maps) ---------->|
   | read next Event ------------------------------>|
   |  case SyscallEntry: PTRACE_SYSCALL to entry    |
   |  read SyscallExit from trace ----------------->|
   |  write MemWrites into tracee (process_vm_writev)|
   |  SETREGS: RAX=retval, RIP past `syscall`        |
   |  (DO NOT enter kernel)                          |
   |  case Signal: program perf PMI to anchor.tick   |
   |   count-to-near, single-step residual to IP     |
   |   compare regs==anchor.regs (I10) else DIVERGE  |
   |   inject signal frame                           |
   | at each sync point: compare regs/IP vs trace    |
   |   mismatch -> emit `diverged`, STOP (I6)        |

8.16 Tracee state machine

        spawn                PTRACE_SYSCALL (entry)
[start] ----> (Running) --------------------------> (AtSyscallEntry)
                ^  |                                      |
   PTRACE_CONT  |  | signal/stop                          | PTRACE_SYSCALL
                |  v                                      v
            (Stopped) <----------------------------- (AtSyscallExit)
                |   \                                   /
   checkpoint   |    \  divergence (replay)            / done -> Running
                v     \--------------> (Diverged) <---/
          (Checkpointed)                  (terminal, replay only)

8.17 Malformed / divergence examples

  • Untrapped nondeterministic instruction. RDTSC not trapped; record sees TSC=X, replay's CPU returns Y → downstream branch differs → divergence at next compare. Fix: install trap (CR4.TSD trap-and-emulate, or rewrite) (I11).
  • Signal one branch late. Anchor recorded at tick T but replay delivers at T+1 (skid mishandled) → register state at delivery differs → I10 anchor mismatch. Fix: two-stage convergence (§ principle 7).
  • Shared-memory race (documented limitation). Two threads racing on a word without serialization order recorded → not reproducible at single-core granularity if the outcome depended on true parallelism. PhaseDeferred("§12.4"); surfaced as divergence, never silently wrong.
  • vDSO syscall bypass. clock_gettime via vDSO never traps ptrace → unrecorded nondeterminism. Fix (Phase 14): patch vDSO to force real syscall, or trap the underlying read. Until then: divergence on time-dependent branches.
  • Torn trace tail. Process killed mid-append → last block CRC fails → reader truncates to last good block (I9); replay covers the valid prefix.

11. Core Schema and Core Types

Lightweight signatures only (no implementation). Ownership / mutation / concurrency / persistence / serialization / compatibility annotated per type.

Tick — struct Tick(u64) retired-conditional-branch count.

  • Ownership: Copy value. Mutation: immutable; produced by PerfCounter. Concurrency: per-thread source; Send. Persistence: stored in every event (LE u64). Serialization: raw u64. Compatibility: width fixed at u64 forever (saturating beyond is a hard error, not a wrap).

RegisterFile — struct RegisterFile { gp:[u64;16], rip:u64, rflags:u64, fs_base:u64, gs_base:u64, fp_ref:Option<FpStateId> }.

  • Ownership: owned, Clone. Mutation: rebuilt from GETREGS / set via SETREGS. Concurrency: Send; not shared mutably. Persistence: compact snapshot in events + checkpoints. Serialization: fixed layout, version-tagged. Compatibility: new arch regs ⇒ new version + optional trailer (forward-compatible append).

AddressSpace — struct AddressSpace { regions:Vec<MemRegion>, aslr:bool }; MemRegion { base, len, prot, backing }.

  • Ownership: owned by Session. Mutation: updated on mmap/munmap events. Concurrency: single-owner. Persistence: snapshotted in checkpoints; maps recorded at start (I8). Serialization: region list. Compatibility: region flags extensible.

TraceEvent — struct TraceEvent { tick:Tick, kind:EventKind, regs:RegisterFile, payload:Payload }.

  • enum EventKind { SyscallEntry, SyscallExit, Signal, Sched, RdtscRdrandCpuid, MmapData }.
  • Ownership: owned, immutable once appended. Mutation: none post-append (I9). Concurrency: produced by owner thread only. Persistence: the core log record. Serialization: length-prefixed block, CRC32C. Compatibility: unknown future kinds skipped via length prefix (forward-compat read).

Payload — enum Payload { Syscall{nr:i64, args:[u64;6], ret:i64, mem:Vec<MemWrite>}, Signal{signo:i32, siginfo:[u8;128], anchor:Coord}, Sched{from:Tid,to:Tid}, NondetInsn{kind:InsnKind, out:RegDelta}, Mmap{blob:BlobId, addr:u64, len:u64} }.

  • MemWrite{addr:u64, len:u32, data:DataRef} — inline if small, blob if large. Coord{tick:Tick, rip:u64, regs_hash:u64}.
  • Ownership/mut/conc: as TraceEvent. Persistence: inline + blob store. Serialization: tagged union. Compatibility: per-variant trailer for added fields.

Checkpoint — struct Checkpoint { tick:Tick, regs:RegisterFile, mem:MemSnapshot, fds:FdSnapshot }; enum MemSnapshot { CowFork(Pid), PageDiff(Vec<PageImage>) }.

  • Ownership: owned by ReplayTimeline. Mutation: created, never edited. Concurrency: single-owner. Persistence: live (fork pid, volatile) or on-disk (PageDiff). Serialization: PageDiff persisted; CowFork is process-lifetime only. Compatibility: PageDiff format versioned.

Trace / EventLog — struct Trace { dir, header:Header, reader/writer, index:TickIndex, blobs:BlobStore }.

  • Methods (contracts): append(&mut self, ev) -> Result<()> (monotone tick, I3); read_at(&self, off) -> Result<TraceEvent>; seek_tick(&self, t:Tick) -> Result<Offset> (≤ t); truncate_torn(&mut self) (I9). Concurrency: single writer; many readers after seal. Persistence: directory of files. Compatibility: header carries format_version.

Recorder — struct Recorder { tracee:Tracee, perf:PerfCounter, trace:Trace, sched:Scheduler }.

  • run(&mut self) -> Result<()> drives §8.14. Owns the tracee (principle 9). Single thread. Not persisted.

Replayer — struct Replayer { tracee:Tracee, perf:PerfCounter, trace:Trace, pos:Offset }.

  • step_event(&mut self) -> Result<ReplayStop>; run_to(&mut self, t:Tick). Drives §8.15; emits divergence (I6). Single owner thread.

ReplayTimeline — struct ReplayTimeline { replayer:Replayer, checkpoints:BTreeMap<Tick,Checkpoint> }.

  • seek(&mut self, t:Tick) -> Result<()> (restore nearest ≤ t, replay forward); checkpoint_now(&mut self). Concurrency: single-owner.

Session — struct Session { timeline:ReplayTimeline, breakpoints, watchpoints, dwarf, now:Tick }.

  • Top-level debug orchestrator; continue/step/reverse_* map onto timeline. Owns debug state.

Tracee — struct Tracee { pid:Pid, state:TraceeState, owner:ThreadId }; enum TraceeState { Running, AtSyscallEntry, AtSyscallExit, Stopped, Checkpointed, Diverged }.

  • Ownership: exclusively by its owner thread (principle 9). Mutation: state advances per ptrace stop. Concurrency: !Sync across ptrace ops — enforced by owner-thread check.

Breakpoint — enum Breakpoint { Software{addr:u64, saved_byte:u8}, Hardware{addr:u64, drx:u8} }.

  • Ownership: Session. Mutation: install (write 0xCC / set DRx) / remove (restore). Persistence: not persisted (per-session). Concurrency: owner thread.

Watchpoint — struct Watchpoint { addr:u64, len:u8, kind:WatchKind, impl_:WatchImpl }; enum WatchKind{Write,ReadWrite,Exec}; enum WatchImpl{Hw(u8 /*drx*/), ReplayScan}.

  • Forward = Hw(DRx); reverse = ReplayScan over a replay window.

Target (DAP) — trait Target { fn capabilities(&self)->Capabilities; fn continue_(&mut self); fn step_back(&mut self); fn reverse_continue(&mut self); fn stack_trace(&self)->Vec<Frame>; fn read_vars(&self, frame)->Vec<Var>; fn seek_tick(&mut self, t:Tick); }.

  • Bridges Session to DAP; capabilities.supportsStepBack = true.

TtdbError — enum TtdbError { Ptrace(nix::Error), Perf(io::Error), TraceCorrupt{off:u64}, Diverged(Coord, RegMismatch), AnchorUnreachable(Coord), UntrappedNondet{ip:u64}, AspaceMismatch{region}, SchedSerialization, ... }.

  • Ownership: returned by value. Serialization: rendered in telemetry. Compatibility: non-exhaustive enum.

Phase 1 — ptrace supervisor

1.1 Objectives

Stand up ttdb-ptrace: spawn/attach a tracee, drive stop/continue, read+write registers and memory, decode waitpid status. Establish the Tracee state machine and the owner-thread ownership rule (principle 9). No recording yet — just deterministic control of one process.

1.2 Detailed Implementation Steps

Theory anchors: ADR-01 (Rust + owner-thread contract), ADR-03 (ptrace mechanism), ADR-06 (process_vm_readv bulk I/O), P9 (explicit tracee ownership), P14 (minimal trusted FFI surface), MM1 (the supervisor is a deterministic state machine over ptrace stops).

  • tracee.rs: spawn(cmd) -> Tracee via fork+PTRACE_TRACEME+execvp; parent waitpid for initial SIGTRAP-on-exec; set PTRACE_SETOPTIONS (TRACESYSGOOD, EXITKILL, TRACECLONE/FORK/VFORK for later threads).
  • wait.rs: decode WIFSTOPPED/WSTOPSIG, distinguish syscall-stop (SIGTRAP|0x80 via TRACESYSGOOD), group-stop, ptrace-event stops (PTRACE_EVENT_CLONE etc.).
  • regs_io.rs: getregs -> RegisterFile (PTRACE_GETREGS / GETREGSET NT_PRSTATUS), setregs; fpregs via GETFPREGS/NT_X86_XSTATE (full xsave deferred §6.6).
  • mem_io.rs: read_mem(addr,len) -> Vec<u8> and write_mem via process_vm_readv/writev with PTRACE_PEEK/POKE fallback for unmapped iovec edges.
  • lib.rs: cont(), single_step() (PTRACE_SINGLESTEP), syscall_step() (PTRACE_SYSCALL); owner-thread assertion on every call (debug_assert thread id == owner).
  • Wire ThreadId capture at attach; all ptrace ops route through one owner.

1.3 Deliverable

A Tracee that spawns /bin/true, single-steps N instructions, prints RIP/regs at each stop, and exits cleanly. CLI ttdb step --count N -- <prog> demo.

1.4 Acceptance Criteria

  • Spawn + step + cont + exit on 10 static test binaries, 0 leaked zombies.
  • GETREGS/SETREGS round-trips RIP modification (set RIP, confirm next step from new address).
  • read_mem/write_mem round-trips a 4 KB buffer at a known mapped address.
  • Owner-thread assertion fires (in a test) when ptrace is called off-owner.

1.5 Conformance Fixtures

  • progs/nop_loop — fixed instruction count; expected step count exact.
  • progs/static_hello — static-linked, predictable entry RIP.
  • fixtures/regs_roundtrip.json — set/get register pairs.
  • malformed: attach to already-exited pid → expect ESRCH mapped to TtdbError::Ptrace.

1.6 Pitfalls

  • PTRACE_TRACEME race: child may run before parent attaches → use the exec-SIGTRAP stop as the sync point; do not CONT before it. Detect via missing initial stop.
  • Syscall-stop vs SIGTRAP ambiguity: without TRACESYSGOOD you cannot tell a syscall stop from a real SIGTRAP → always set the option; signal = SIGTRAP|0x80.
  • process_vm_readv partial reads: short read at a page boundary → loop + fall back to PEEK; treat 0-length as fault, not EOF.
  • Thread leakage: forgetting EXITKILL leaves tracees alive after ttdb crashes → set EXITKILL at attach.

1.7 Performance Concerns

  • PEEK/POKE is one syscall per word (8 B) → always prefer process_vm_readv for buffers > 1 word. Cache RegisterFile per stop to avoid redundant GETREGS.
  • Owner-thread assertion compiled out in release; no hot-path cost.

1.8 Edge Cases

  • Tracee execs a different binary (PTRACE_EVENT_EXEC) → re-read maps. Tracee forks (deferred to P5 scheduling). Stopped tracee receiving a real signal while we expect a syscall stop → queue it (P6). Tracee exits during a step → handle WIFEXITED mid-loop.

1.9 Failure Analysis

  • Breaks: lost stop (CONT issued at wrong state) → tracee runs free → detected by unexpected WIFEXITED or hang on next waitpid (timeout watchdog). Blast radius: one session. Containment: kill tracee (EXITKILL backstop). Recovery: re-spawn. Postmortem: log every ptrace op + resulting wait status.

1.10 Operational Notes

  • Telemetry: ptrace_op{op,pid,result}, tracee_state{from,to}. Logging at TRACE for each stop. Deployment: needs CAP_SYS_PTRACE or ptrace_scope ≤ 1. Rollback: none (foundational). Compatibility: GETREGSET (NT_PRSTATUS) preferred over legacy GETREGS for future-arch.

Phase 2 — Syscall interception + recording

2.1 Objectives

Trap every syscall at entry and exit; capture nr, the 6 argument registers, the return value, and all bytes the kernel wrote into tracee memory (output buffers). Install a seccomp-BPF filter so cheap/ignorable syscalls do not pay the full trap cost. Produce in-memory TraceEvents (persisted in P4).

2.2 Detailed Implementation Steps

Theory anchors: ADR-04 (seccomp-BPF trap path), ADR-06 (process_vm_readv MemWrite capture), P1 (determinism over convenience), P6 (suppress-then-inject contract this captures the data for), I11 (no nondeterministic input escapes — syscall results are the largest such class), MM2 (a syscall's full effect = return register + every byte the kernel wrote); rr paper (ATC 2017) syscall-interception model.

  • seccomp.rs: build a cBPF program returning SECCOMP_RET_TRACE for syscalls of interest, SECCOMP_RET_ALLOW for always-deterministic ones; install with seccomp(SECCOMP_SET_MODE_FILTER, ..) in the child before exec (requires no_new_privs).
  • syscall.rs: on entry stop, read regs → nr=orig_rax, args = rdi,rsi,rdx,r10,r8,r9; classify syscall by an interception table (which args are out-pointers + length sources).
  • On exit stop: read retval=rax; for each out-pointer, read_mem(ptr, len) → MemWrite; length resolved per-syscall (e.g. read → min(retval, count); recvmsg → walk iovec; getdents → retval bytes).
  • Build the syscall interception table: map syscall nr → arg-out descriptor (pointer arg index, length source = arg index | retval | struct field). Cover the common set first (read/write/openat/mmap/stat/recv*/send*/poll/clock_gettime/getrandom/...).
  • Emit Payload::Syscall{nr,args,ret,mem} into the recorder's in-memory event buffer with current Tick placeholder (P3 fills real ticks).

2.3 Deliverable

ttdb record --dry -- <prog> prints a live stream of intercepted syscalls with captured output bytes, e.g. read(3, <8 bytes captured>, 4096) = 8. seccomp filter measurably skips uninteresting syscalls.

2.4 Acceptance Criteria

  • Correct arg/return decode for ≥ 40 syscalls vs strace -e raw differential.
  • read/recvmsg/getdents MemWrite byte-ranges exactly match what the program later observes (verified by a test program echoing the buffer).
  • seccomp filter reduces trap count on a getpid-loop microbench by ≥ 5×.

2.5 Conformance Fixtures

  • conformance/syscall/read_exact.* — read N bytes, assert captured == file contents.
  • conformance/syscall/recvmsg_iovec.* — scatter buffers; assert all segments captured.
  • conformance/syscall/getdents.* — directory listing bytes captured.
  • malformed: syscall with a bogus out-pointer (EFAULT) → retval=-EFAULT, zero MemWrite, no crash.

2.6 Pitfalls

  • Out-length comes from the return value, not the arg (read count is a ceiling) → using the arg length captures uninitialized bytes → divergence later. Resolve length from retval per the table.
  • Pointer args that are also in-args (e.g. ioctl) → must know direction per request code; default to capturing on exit only for known-output requests.
  • seccomp no_new_privs requirement → forgetting it makes seccomp() fail with EACCES.
  • mmap of files captured as data is wasteful → record mmap as MmapRef (region + backing), replay re-creates the mapping rather than logging bytes (real file content is reproducible if the file is part of the recorded inputs; otherwise capture lazily on first read).
  • vDSO syscalls (gettimeofday/clock_gettime fast path) never trap → flagged here, mitigated Phase 14 (vDSO patch). Until then they are a known divergence source.

2.7 Performance Concerns

  • Each intercepted syscall = 2 ptrace stops (entry+exit) + 1 process_vm_readv per out-buffer. Batch MemWrite reads into a single iovec where possible. The seccomp prefilter is the primary overhead lever (ADR 4).
  • Syscall classification table is a flat array indexed by nr → O(1), cache-resident.

2.8 Edge Cases

  • Restartable syscalls (ERESTARTSYS) re-enter → record both attempts; replay must re-issue identically. Signals interrupting a syscall → exit with -EINTR, captured as the real return. clone/fork syscalls → handled in P5. Large reads (> blob threshold) → spill MemWrite data to blob store (P4).

2.9 Failure Analysis

  • Breaks: wrong length in the interception table → captures too few/many bytes → silent at record, divergence at replay. Detection: differential vs strace + replay byte-compare. Blast radius: any program using that syscall. Containment: table is data, hot-fixable. Postmortem: dump nr + arg/len decode for the diverging syscall.

2.10 Operational Notes

  • Telemetry: syscall_intercepted{nr,ret,mem_bytes}, seccomp_skipped{nr}. Metrics: per-nr count + captured-byte histogram. Compatibility: interception table versioned with trace format (a new kernel syscall ⇒ table update ⇒ format minor bump). Rollback: unknown syscalls fall back to full PTRACE_SYSCALL trap (never silently allowed).

Phase 3 — Tick counting via perf_event_open + IP/regs coordinate

3.1 Objectives

Build ttdb-perf: open a per-thread retired-conditional-branch counter, read the current Tick, and define the canonical (Tick, IP, regs) coordinate. Implement two-stage convergence: count-to-near via PMI, then single-step the residual to land on an exact instruction. This is the temporal spine of the whole system (principle 3, 7).

3.2 Detailed Implementation Steps

Theory anchors: ADR-05 (retired-conditional-branch instruction clock), P3 (the Tick is the only clock), P7 (two-stage count-then-step convergence), I2 (tick monotonicity + reproducibility), MM3 (a hardware perf counter is a logical clock and skid is its quantization error); rr paper (ATC 2017) retired-branch coordinate; Intel SDM Vol 3B PMU/skid semantics.

  • sys.rs: perf_event_open FFI; perf_event_attr with type=PERF_TYPE_HARDWARE, config=PERF_COUNT_HW_BRANCH_INSTRUCTIONS (or a raw retired-conditional-branch event per microarch), exclude_kernel=1, exclude_hv=1, inherit=0, pinned to the tracee thread + CPU.
  • lib.rs: open(tracee_tid) -> PerfCounter; read() -> Tick via the mmapped counter page (rdpmc-style fast read) or read(2) fallback; reset().
  • skid.rs: program a sampling/overflow event to fire a PMI a safe margin before a target tick (target - skid_margin); on the PMI-induced stop, read() exact count, then PTRACE_SINGLESTEP until count == target AND at the desired IP (two-stage convergence).
  • Define Coord{tick, rip, regs_hash}; regs_hash = cheap hash of the GP register file for fast compare; full regs stored for divergence reports.
  • Calibrate skid_margin empirically per CPU at startup (run a known branch loop, measure overshoot distribution) → store in trace header (perf_event_cfg).

3.3 Deliverable

ttdb ticks -- <prog> runs a program and prints total retired branches; ttdb seektick T -- <prog> (record-then) lands the tracee on the exact instruction at tick T, printing RIP + regs, and re-landing identically across repeated runs.

3.4 Acceptance Criteria

  • Two recordings of the same deterministic program produce identical total tick counts (I2).
  • seektick T lands on the same RIP across ≥ 100 repetitions (reproducibility).
  • Two-stage convergence reaches the exact (tick, rip) with single-step residual ≤ calibrated skid margin (typically ≤ a few hundred branches).

3.5 Conformance Fixtures

  • progs/branch_count — fixed number of conditional branches; expected tick known.
  • progs/recursive_fib — deterministic, tick-rich; cross-run tick equality asserted.
  • fixtures/skid_calibration.json — recorded overshoot samples per CPU model.
  • malformed: PMU unavailable (cloud VM) → graceful TtdbError::Perf with remediation message.

3.6 Pitfalls

  • Counter skid / overcount: PMIs are imprecise; the counter overshoots the instruction that triggered overflow → never trust the raw count for exact placement; always single-step the residual (principle 7).
  • Counting kernel branches: forgetting exclude_kernel makes counts include syscall-handler branches → nonreproducible → set exclude_kernel/hv.
  • inherit on clone: a child thread inheriting the counter pollutes the parent's count → inherit=0, open a fresh counter per thread (ties into P5).
  • Microarch variance: retired-branch semantics differ across CPUs → trace records the exact event config; replay refuses on a mismatching CPU (or recalibrates) → portability is §12.3.
  • rdpmc vs read(): rdpmc needs the mmap page + correct multiplexing; if the event is multiplexed (scaled), the read is approximate → pin the event (not multiplexed) so the count is exact.

3.7 Performance Concerns

  • read() per stop is a syscall; the mmapped rdpmc fast path avoids it (< 100 ns). Single-step residual is the expensive part → keep skid_margin tight but safe. PMI delivery latency adds to seek time.

3.8 Edge Cases

  • Tight loops with no branches (rare) → tick does not advance → coordinate ambiguous → must also use IP + an instruction-count tiebreaker for such regions. Counter wrap (u64 retired branches) → effectively never, but saturate-to-error. Migration across CPUs mid-run → pinned affinity prevents it; detect and abort if it happens.

3.9 Failure Analysis

  • Breaks: skid_margin too small → single-step starts after the target → overshoot, cannot reach tick (would require running backward, impossible forward) → detected as anchor_unreachable. Recovery: restore an earlier checkpoint (P8) and re-converge. Postmortem: log (target, near-count, residual-steps, final-count, rip-trail).

3.10 Operational Notes

  • Telemetry: tick_read{value}, converge{target,near,residual,steps}, skid_margin{cpu,value}. Deployment: requires kernel.perf_event_paranoid ≤ 1 (script in scripts/setup_perf_paranoid.sh). Compatibility: perf_event_cfg in the header pins the event; a trace is replayable only on a CPU whose retired-branch semantics match (asserted at replay start).

Phase 4 — Trace log format + serialization

4.1 Objectives

Make the in-memory TraceEvent stream durable: define the on-disk Trace directory layout, an append-only CRC'd block format, the out-of-line blob store for large MmapData, a lazy tick→offset index, and torn-tail-tolerant reading (principles 5, 13; I3, I9).

4.2 Detailed Implementation Steps

Theory anchors: ADR-09 (append-only log + out-of-line blobs), ADR-10 (custom length-prefixed serialization), ADR-11 (CRC32C per block), P5 (append-only, crash-only trace), P13 (stable trace wire format), I3 (event ordering), I9 (append-only integrity), MM4 (a crash-only log is correct iff every torn tail truncates to a valid prefix).

  • format.rs: header (magic, format_version, arch, binary_id(hash), aslr_flag, perf_event_cfg, skid_margin); block = [len:u32][crc32c:u32][payload]; footer = [event_count][final_tick][trailer_crc] written on seal.
  • writer.rs: O_APPEND writer; serialize each TraceEvent to a block; CRC32C over payload; flush() + fsync() on checkpoint boundaries and at shutdown; reject out-of-order tick (I3).
  • reader.rs: sequential iterator decoding block-by-block; verify CRC; on a bad/short final block → truncate_torn() (logical truncation at last good offset, I9); seek_tick(t) uses index.rs.
  • index.rs: lazily build BTreeMap<Tick, Offset> (sample every K events) for seek_tick ≤ t; persisted as index.bin, rebuildable from the log.
  • blobs.rs: content-addressed blob store under blobs/; MemWrite/MmapData over a threshold (e.g. 4 KB) stored as a blob, referenced by data_ref/blob_id.
  • Versioning rules: read accepts format_version ≤ current with the same major; unknown event kinds skipped via length prefix.

4.3 Deliverable

A recording from P2/P3 now writes a real trace/ directory; tools/trace_dump re-reads and prints every event with ticks; tools/trace_stat reports size + per-kind histogram. Killing record mid-write yields a trace that trace_dump reads up to the last good block.

4.4 Acceptance Criteria

  • Write→read round-trip is byte-exact for ≥ 10k events incl. blobs.
  • seek_tick(t) returns the offset of the greatest event with tick ≤ t in O(log n).
  • A truncated trace (file cut mid-block) reads cleanly to the last valid block; trace_block_crc_fail telemetry emitted once.
  • Trace from format_version N reads on a build at version N+patch (forward-compat skip of an injected unknown kind).

4.5 Conformance Fixtures

  • conformance/trace_format/golden_v1.trace — frozen reference trace + expected dump.
  • conformance/trace_format/torn_tail.trace — deliberately truncated; expected last-good offset.
  • conformance/trace_format/unknown_kind.trace — synthetic future kind; expected skip.
  • fuzz/trace_parse.rs — random/garbage bytes must never panic; only TraceCorrupt.

4.6 Pitfalls

  • CRC over the wrong span (including the length field vs not) → silent mismatch → define CRC scope precisely (payload only) and test cross-build.
  • fsync cost on every event → batch fsync to checkpoint boundaries; document the durability window (events since last fsync may be lost on crash, but the prefix is always valid).
  • Blob orphaning: a referenced blob missing → TraceCorrupt; never delete blobs of a sealed trace.
  • Index drift: index built from a different log version → always derive index from the log; treat index.bin as a cache, rebuild on mismatch.
  • Endianness: fixed little-endian on-disk (x86-64); assert on read.

4.7 Performance Concerns

  • Append path: buffered writer, single write per block; fixed-size events keep decode branch-free. Reader keeps a decode buffer in L2. Blob threshold trades inline-locality vs log size. CRC32C uses the hardware instruction (SSE4.2) — confirm at build.

4.8 Edge Cases

  • Zero-event trace (program exits immediately) → valid header + empty footer. Single torn byte vs whole torn block → both truncate cleanly. Concurrent reader during record → reader stops at last fully-written block (no locking; append-only safety). Disk full mid-append → flush fails → record aborts with a valid prefix (principle 12).

4.9 Failure Analysis

  • Breaks: torn tail mis-detected as valid (CRC false-positive, 1/2^32) → replay diverges immediately at the bad event. Detection: divergence at event 0 of the bad region. Containment: divergence_bisect tool localizes. Recovery: truncate before the suspect block. Postmortem: dump raw bytes of the failing block.

4.10 Operational Notes

  • Telemetry: trace_append{bytes,kind}, trace_fsync{events}, trace_block_crc_fail{off}, blob_write{id,len}. Compatibility: format_version major/minor policy (§ Compatibility & Versioning). Backup: a trace directory is self-contained and copyable. Migration: a trace migrate tool upgrades old minor versions in place by re-framing (never mutating, writes a new copy).

Phase 5 — Deterministic single-tracee scheduling + context-switch recording

5.1 Objectives

Handle multithreaded tracees by enforcing the single-runnable-thread invariant (I5): at any instant exactly one tracee thread runs; all others are stopped. Record context-switch points as Sched events so replay re-creates the identical interleaving (principle 4). This converts true concurrency into a deterministic, replayable sequence.

5.2 Detailed Implementation Steps

Theory anchors: ADR-12 (single runnable tracee thread), P4 (single runnable tracee thread during record), I5 (single-tracee-thread serialization), MM5 (serialization converts a concurrency race into a recordable total order — the central tradeoff vs §12.4); CoreDet / Deterministic Process Groups (the serialization-vs-multicore rationale, papers §5 #11).

  • Catch thread/process creation: PTRACE_EVENT_CLONE/FORK/VFORK (set in P1 options) → register the new Tid, open a per-thread perf counter (P3), stop it immediately.
  • scheduler.rs: maintain a runnable set; pick exactly one thread to run (e.g. round-robin with a recorded quantum, or run-until-blocked). All others held at a ptrace stop.
  • Define switch points: a thread is switched out at (a) a blocking syscall, (b) quantum expiry (a tick budget via PMI), (c) a futex/lock wait, (d) voluntary yield. Emit Payload::Sched{from_tid,to_tid} at every switch with the current tick.
  • Tie scheduling to ticks: quantum = N branches; PMI fires → switch-out event recorded → next thread CONT'd. Per-thread tick counters; the global timeline orders events by (switch sequence, per-thread tick).
  • Handle thread exit (PTRACE_EVENT_EXIT), set_robust_list, TLS (fs_base/gs_base per thread in RegisterFile).

5.3 Deliverable

ttdb record correctly records a multithreaded test program (producer/consumer over a mutex); trace_dump shows interleaved Sched events; the recorded interleaving is fixed and reproducible.

5.4 Acceptance Criteria

  • A 4-thread program records with ≤ 1 runnable thread at all times (asserted via ptrace state probe in a test) (I5).
  • The recorded interleaving (sequence of Sched events) is identical across ≥ 20 recordings of a deterministic-after-serialization workload.
  • Thread create/exit events captured for all threads; no orphaned tracee threads on exit.

5.5 Conformance Fixtures

  • progs/mutex_pingpong — two threads alternating; expected Sched sequence golden.
  • progs/thread_spawn_storm — many short-lived threads; all create/exit events present.
  • conformance/signals/... reused later for signal+sched interaction.
  • malformed: a thread that never blocks (busy loop) → quantum PMI must force a switch (test the preemption path).

5.6 Pitfalls

  • Deadlock under serialization: if the only runnable thread blocks on a lock held by a stopped thread, naive scheduling deadlocks → the scheduler must detect "all runnable threads blocked" and run a blocked-on holder → requires modeling futex wait/wake (record futex syscalls and switch to the waker).
  • Quantum too large: a CPU-bound thread starves others (fine for determinism, bad for realism) but never breaks correctness; quantum too small = overhead. Tune via tick budget.
  • Per-thread counter inheritance: a cloned thread must get a fresh counter (inherit=0) or counts cross-contaminate (P3 pitfall recurs).
  • TID reuse: the kernel may reuse a TID after exit → key threads by (TID, generation) not TID alone.
  • vfork semantics: parent suspended until child execs/exits → model as a forced switch.

5.7 Performance Concerns

  • Serialization removes parallelism → recording a parallel workload runs at ~1-core speed (a stated cost, principle 4). Switch = stop one + cont another (2 ptrace ops). Minimize switches by running-until-blocked when fairness is not needed for the recorded semantics.

5.8 Edge Cases

  • Thread holding a lock gets switched out at quantum → other threads spin → recorded faithfully (spin branches counted). Signal targeting a specific thread vs process (P6 interaction). clone with CLONE_VM but not CLONE_THREAD (shared-mm process) → treated as a thread for scheduling but a process for fd semantics. Race on shared memory between switches → only visible at switch granularity → true sub-quantum races are the §12.4 limitation.

5.9 Failure Analysis

  • Breaks: a missed switch point (thread blocks in an unmodeled way) → deadlock or a thread running unrecorded → divergence at replay. Detection: replay reaches a Sched event but the wrong thread is runnable. Blast radius: the whole recording. Containment: scheduler logs the runnable set at each decision. Recovery: re-record with the switch point added. Postmortem: per-thread state timeline.

5.10 Operational Notes

  • Telemetry: sched_switch{from,to,tick,reason}, thread_create{tid}, thread_exit{tid}, sched_serialization_violation. Metrics: switches/sec, runnable-set size histogram. Compatibility: Sched event is a stable kind. Operational implication: recorded parallel programs are slower but deterministic — document for users debugging concurrency bugs (the intended use).

Phase 6 — Async signal capture anchored to ticks + nondeterministic-instruction trapping

6.1 Objectives

Close two remaining nondeterminism sources: (a) asynchronous signals — record the exact (Tick, IP, regs) anchor at which each signal was delivered so replay re-delivers at the identical instruction (I10); (b) nondeterministic instructions RDTSC/RDRAND/CPUID — trap and record their results so replay injects them (I11).

6.2 Detailed Implementation Steps

Theory anchors: P3 (the Tick coordinate locates the delivery point), P7 (two-stage convergence to the exact anchor), I10 (coordinate completeness — a full (Tick, IP, regs) triple), I11 (no nondeterministic instruction escapes), MM6 (an async event has no natural place in a deterministic re-run — the tick coordinate is the only thing that gives it one); rr paper (ATC 2017) signal-anchoring approach.

  • signals.rs: on a signal-delivery ptrace stop (PTRACE_GETSIGINFO), read the pending signo + siginfo; read the current Tick and regs → build Coord; record Payload::Signal{signo, siginfo, anchor}; then deliver via PTRACE_CONT(signo) (record) or defer to the anchored tick (replay, P7).
  • Distinguish synchronous (fault: SIGSEGV/SIGFPE/SIGTRAP from the program) from asynchronous (SIGINT/SIGTERM/SIGALRM/SIGCHLD) signals. Synchronous faults occur at a deterministic instruction → anchor is implicit (the faulting IP). Asynchronous signals can arrive anywhere → the tick anchor is essential.
  • nondet_insn.rs: trap RDTSC/RDTSCP via CR4.TSD (set TSD so RDTSC faults to the OS → ptrace sees SIGSEGV/illegal? — actually use PR_SET_TSC/prctl(PR_SET_TSC, PR_TSC_SIGSEGV) so RDTSC raises SIGSEGV, caught, emulated). Record Payload::NondetInsn{kind=Rdtsc, out=RegDelta{rax,rdx}}. CPUID: trap via arch_prctl/ARCH_SET_CPUID (PR_SET_TSC analogue, or CPUID faulting feature) → record EAX/EBX/ECX/EDX. RDRAND/RDSEED: no clean trap → option A: refuse (detect via static scan of the binary, warn); option B: binary-rewrite RDRAND → int3 + emulate (deferred, §6.6 stretch); record the produced value.
  • Decode the trapping instruction at the faulting RIP (length-decode x86-64) to advance RIP past it after emulation.

6.3 Deliverable

ttdb record captures a program that installs a SIGALRM handler and calls RDTSC; trace_dump shows Signal{SIGALRM,tick=...} and NondetInsn{Rdtsc,rax=...,rdx=...} events. The same RDTSC value is reproducible across replays (P7).

6.4 Acceptance Criteria

  • Async signal anchor (tick, rip) recorded for ≥ 5 signal types; the anchor is a complete coordinate (I10).
  • RDTSC and CPUID results recorded and, in P7, injected so a TSC-dependent branch takes the identical path across replays.
  • A program using RDRAND is detected (static scan) and either refused with a clear message or rewritten (if §6.6 enabled).

6.5 Conformance Fixtures

  • conformance/signals/sigalrm_anchor.* — handler increments a counter; anchor tick golden.
  • conformance/signals/sigsegv_fault.* — synchronous fault; faulting IP deterministic.
  • progs/rdtsc_branch — branches on TSC parity; replay path must match record path.
  • progs/cpuid_features — branches on CPUID leaf; injected leaf reproduces path.
  • malformed: signal delivered during a syscall (EINTR interaction) — anchor + EINTR both recorded.

6.6 Pitfalls

  • Signal one branch early/late: the anchor must be the delivery point (after the kernel would have delivered), captured precisely; mis-anchoring places the handler at the wrong instruction → divergence (the §8.17 example). PhaseDeferred("FINAL_BLUEPRINT §6.6") covers AVX-512/xsave extended-state capture and RDRAND binary rewrite as stretch items.
  • PR_SET_TSC granularity: traps all RDTSC (cost) but is the only portable user-space mechanism without a kernel module → accept the cost; RDTSC is rare in hot loops.
  • siginfo size/layout: siginfo_t is 128 B with union fields → capture the raw bytes, do not interpret structurally (forward-compat).
  • Signal queueing: real-time signals queue; standard signals coalesce → record each delivery the kernel actually performs, in order.
  • Re-entrancy: a signal during signal-handler execution → nested anchors; record the nesting via stack of anchors.
  • SIGKILL/SIGSTOP cannot be caught → SIGKILL ends recording (valid prefix); SIGSTOP handled as a group-stop, not a delivered signal.

6.7 Performance Concerns

  • Signal stops are rare → negligible steady-state cost. RDTSC trapping via PR_SET_TSC adds a fault per RDTSC → expensive only for RDTSC-heavy code (rare); benchmark and warn. Instruction-length decode is a small table lookup.

6.8 Edge Cases

  • Signal delivered exactly at a syscall boundary → order Signal before/after SyscallExit deterministically (I3 total order). Multiple signals pending → deliver in kernel order, each anchored. SIGTRAP from our own int3 breakpoints (P9) vs program SIGTRAP → distinguish by source (our breakpoint table). RDTSCP (also reads IA32_TSC_AUX into ECX) → record ECX too.

6.9 Failure Analysis

  • Breaks: an untrapped nondeterministic instruction (e.g. RDRAND missed by the scan) → record/replay produce different values → divergence (I11, untrapped_nondet_insn). Detection: divergence at the branch consuming the value; divergence_bisect localizes to the RIP. Blast radius: any run hitting that instruction. Containment: static scan at record start lists all such instructions. Recovery: add a trap/rewrite. Postmortem: disassemble around the diverging IP.

6.10 Operational Notes

  • Telemetry: signal_recorded{signo,tick}, nondet_insn{kind,ip}, untrapped_nondet_insn{ip}. Compatibility: Signal and RdtscRdrandCpuid are stable kinds; siginfo stored raw. Operational: record-start scan emits a warning listing RDRAND/CPUID sites so operators know coverage. Deployment: PR_SET_TSC needs no extra privilege.

Phase 7 — Replay engine

7.1 Objectives

The first end-to-end record→replay. Re-spawn the recorded binary and drive a replay loop that suppresses real syscalls and injects recorded results + memory effects, re-delivers signals at their tick anchors, replays nondeterministic-instruction results, and continuously detects divergence (principles 2, 6; I1, I6, I7). Determinism ⇒ identical regs/memory at every tick.

7.2 Detailed Implementation Steps

Theory anchors: P2 (divergence is detected, never tolerated), P6 (suppress, then inject), P10 (hermetic, reproducible replay environment), I1 (replay determinism), I6 (divergence ⇒ halt), I7 (syscall suppression), I8 (address-space stability), MM7 (replay is the same deterministic function as record run on injected inputs — equal inputs force equal state, so any inequality is a real bug); rr paper (ATC 2017) replay model.

  • run_loop.rs: re-spawn under ptrace with ASLR disabled (personality(ADDR_NO_RANDOMIZE)) and the recorded mmap layout enforced (I8); install the same seccomp filter; open the perf counter.
  • inject.rs: at a syscall-entry stop, read the next SyscallExit from the trace; write_mem each recorded MemWrite into the tracee; setregs with rax=retval and rip advanced past the syscall instruction; do not issue PTRACE_SYSCALL into the kernel (suppression, I7). For mmap/brk, perform the real mapping at the recorded address (memory layout must match) rather than injecting bytes.
  • signal_deliver.rs: for the next Signal event, program the perf PMI to the anchor tick − margin (P3), count-to-near, single-step the residual to anchor.rip, verify regs == anchor.regs (I10) else DIVERGE, then synthesize the signal delivery (PTRACE_CONT with the signal, or set up the signal frame).
  • Replay nondeterministic instructions: when the tracee reaches a recorded RDTSC/CPUID site (trap fires as in record), inject the recorded RegDelta instead of reading the hardware.
  • diverge.rs: at every sync point (each SyscallEntry, each signal anchor, each checkpoint in P8) compare observed (rip, regs_hash) against the recorded coordinate; on mismatch emit TtdbError::Diverged(coord, mismatch) and STOP (I6). Provide a full register diff in the report.

7.3 Deliverable

ttdb replay trace/ re-executes a recorded program to completion with no real I/O, producing identical final state; the §8.13 worked example (time() branch) replays the recorded branch. A deliberately corrupted trace (flipped retval) triggers an immediate, precise diverged report.

7.4 Acceptance Criteria

  • ≥ 30 deterministic test programs replay to completion with zero divergence and final regs matching the recorded final state (I1).
  • No real syscall executes during replay (verified: a write to stdout produces no output on replay; the recorded bytes are injected into the read-side instead) (I7).
  • Injecting a 1-bit change into any recorded retval causes a diverged report naming the exact tick + register (I6) within one sync interval.
  • Signal re-delivery lands at the recorded anchor.rip for all P6 signal fixtures (I10).

7.5 Conformance Fixtures

  • conformance/syscall/* replayed: each fixture's record then replay must match.
  • conformance/signals/* replayed: anchors hit exactly.
  • conformance/reverse/replay_determinism.* — record once, replay 100×, assert identical tick+reg stream.
  • malformed: corrupt_retval.trace, dropped_signal.trace, extra_event.trace → each yields a specific divergence/anchor error, never a silent wrong run.

7.6 Pitfalls

  • Forgetting to suppress a syscall → the tracee performs real I/O on replay → nondeterminism re-enters + side effects on the host → assert no PTRACE_SYSCALL into kernel during replay (I7 detection).
  • mmap address mismatch: replay mmap returns a different address than recorded → all subsequent pointers diverge → must MAP_FIXED at the recorded address or record and re-create the exact layout (I8).
  • Memory-effect modeling gaps: a syscall wrote to a buffer the interception table missed → replay leaves stale bytes → divergence when the program reads them → fix the table (P2), differential-test.
  • Signal frame construction: kernel builds a specific stack frame on delivery; if we deliver via PTRACE_CONT(sig) the kernel builds it for us → prefer that over hand-rolling the frame.
  • rip advance length: syscall is 2 bytes; advancing by the wrong length corrupts the next instruction → use a fixed +2 for syscall, decode for others.

7.7 Performance Concerns

  • Replay avoids real I/O but pays injection (write_mem per MemWrite) + per-sync-point compare + signal convergence single-steps. regs_hash makes the common compare O(1). Keep the divergence check on the fast path cheap (hash first, full diff only on mismatch). Replay overhead target 1.1×–1.8× (§4).

7.8 Edge Cases

  • Syscall that both reads and writes the same buffer → inject only the written region. Partial syscall (EINTR) replayed → inject the recorded -EINTR and re-issue path. Self-modifying code → the modified bytes are reproduced by replaying the writes that modified them (deterministic). Replay past recorded end (trace shorter than program) → stop at trace end; not an error. execve during replay → re-exec the recorded binary, reset maps.

7.9 Failure Analysis

  • Breaks: divergence — the central failure and the central feature. Detection: the compare at the next sync point. Blast radius: that replay session only (no host side effects, I7). Containment: STOP immediately (I6), never continue on wrong state. Recovery: divergence_bisect finds the first diverging event → usually points to a record-side gap (missing trap, wrong MemWrite length). Operator visibility: a diverged{tick,reg,exp,got} report + RIP disassembly. Postmortem: compare the recorded vs observed register file.

7.10 Operational Notes

  • Telemetry: replay_event{kind,tick}, inject{nr,mem_bytes}, diverged{...}, unexpected_real_syscall{nr}. Metrics: events replayed/sec, divergence count (should be 0). Compatibility: replay asserts header perf_event_cfg matches the host CPU (else refuse, §12.3). Operational: replay is safe to run anywhere (hermetic, I7) — no risk of re-triggering the recorded program's side effects (no real writes, network, etc.).

Phase 8 — Checkpoint / snapshot engine + ReplayTimeline

8.1 Objectives

Make seeking fast and enable reverse execution. Periodically snapshot the replaying tracee (COW fork for live, page-diff for persisted) into Checkpoint{tick,regs,mem,fds}; index checkpoints by tick in ReplayTimeline; implement seek(T) = restore nearest checkpoint ≤ T then replay forward to T (principle 8; I4).

8.2 Detailed Implementation Steps

Theory anchors: ADR-07 (COW fork + page-diff snapshots), ADR-08 (checkpoint + replay-forward, not undo log), P8 (checkpoints are the time machine), I4 (checkpoint consistency), MM8 (random access into a deterministic stream costs (distance to the nearest snapshot), so checkpoint spacing is the master latency knob); King/Dunlap/Chen ATC 2005 checkpoint+replay reverse algorithm.

  • cow_fork.rs: snapshot a live replay position by forking the replaying tracee under ptrace; the child is a frozen COW copy at that tick → store its pid + tick + regs as a Checkpoint{MemSnapshot::CowFork(pid)}. Restore = discard current tracee, adopt the fork (re-fork from it to keep the checkpoint reusable).
  • mem_diff.rs: for persisted checkpoints, capture changed pages since the last checkpoint via /proc/pid/clear_refs + soft-dirty PTE tracking (or full writable-region dump for the first) → MemSnapshot::PageDiff(Vec<PageImage>) written to checkpoints/.
  • timeline.rs: checkpoints: BTreeMap<Tick,Checkpoint>; checkpoint_now() triggered every interval (tick budget N or wall-time, §4); seek(T) = range(..=T).last() → restore → replayer.run_to(T); verify on arrival regs match the recorded coordinate at T (I4).
  • Checkpoint eviction: bound total checkpoint memory; keep a logarithmic spread (denser near "now") so any seek is within one interval; evict middling checkpoints under pressure.
  • Verify-on-restore: after restoring a checkpoint, single-step one event and confirm coordinate consistency (cheap I4 guard).

8.3 Deliverable

ttdb replay trace/ then seek <tick> lands at the exact tick state (regs + memory readable) in time bounded by the checkpoint interval, not by the distance from start. trace_stat reports checkpoint count + memory.

8.4 Acceptance Criteria

  • seek(T) to an arbitrary T completes in ≤ checkpoint-interval replay time (§4), independent of T's absolute value.
  • Restored state at T equals replay-from-start state at T for ≥ 50 random T (I4) — verified by comparing full register files and sampled memory.
  • Checkpoint memory stays within the configured ceiling under a long replay (eviction works).
  • COW-fork restore is reusable (seek to T, then seek to T' > T, then back to T) without re-replaying from start.

8.5 Conformance Fixtures

  • conformance/reverse/seek_random.* — record, seek to 50 random ticks, assert state matches a from-start replay.
  • conformance/reverse/checkpoint_verify.* — restore + 1-step verify for each checkpoint.
  • fixtures/checkpoint_interval.json — interval-vs-seek-latency measurements.
  • malformed: corrupt PageDiff → checkpoint_verify_fail, fall back to an earlier checkpoint.

8.6 Pitfalls

  • COW fork cost: forking a large-RSS tracee copies page tables (not pages) but is still O(mapped pages) → expensive for huge address spaces → tune interval; prefer page-diff for very large processes.
  • Soft-dirty reset races: clear_refs must bracket exactly one interval; a missed reset over-captures or under-captures pages → bracket precisely around checkpoint_now.
  • fd/state in a checkpoint: a checkpoint must also snapshot the logical fd table + signal mask (FdSnapshot) so a restored replay re-injects consistently → snapshot regs + mem + fds together.
  • Checkpoint of a diverged state: never checkpoint after divergence → checkpoint only verified-consistent positions.
  • Fork bomb of checkpoints: too many live COW forks exhaust pids/memory → cap live forks, spill older ones to PageDiff.

8.7 Performance Concerns

  • Interval is the master tradeoff: smaller = faster seek, more memory; larger = slower seek, less memory. Logarithmic checkpoint spread bounds worst-case seek to one interval while keeping memory sub-linear. Page-diff write is I/O; COW fork is memory. Measure both in benchmarks/seek_latency.

8.8 Edge Cases

  • Seek to tick 0 → restore initial state (a checkpoint at start). Seek to a tick between two checkpoints in a region with no branches (tick stalls) → use IP tiebreaker (P3 edge). Seek past trace end → clamp to last tick. Memory grows hugely between checkpoints (one syscall maps GBs) → checkpoint immediately after large mmap. Restore after the underlying binary changed on disk → binary_id mismatch → refuse.

8.9 Failure Analysis

  • Breaks: a checkpoint that does not faithfully restore (missed dirty page) → seek lands on subtly wrong state → divergence shortly after restore (I4 verify catches most). Detection: verify-on-restore + divergence within the interval. Blast radius: seeks into that interval. Containment: discard the bad checkpoint, fall back earlier (slower seek, still correct). Recovery: rebuild the checkpoint. Postmortem: diff restored vs replayed pages.

8.10 Operational Notes

  • Telemetry: checkpoint_create{tick,bytes,kind}, checkpoint_restore{tick,latency}, checkpoint_evict{tick}, checkpoint_verify_fail{tick}. Metrics: checkpoint memory, seek-latency histogram, checkpoints/replay. Compatibility: PageDiff format versioned with the trace. Operational: interval is operator-tunable (--checkpoint-interval); document the memory-vs-latency curve in docs/performance.

Phase 9 — Forward debugging

9.1 Objectives

Turn the replay+timeline into a usable forward debugger: software (int3) and hardware breakpoints, single-step, run-to-breakpoint, stack unwinding, and DWARF-backed line/variable inspection — all over the deterministic replay (not a live process).

9.2 Detailed Implementation Steps

Theory anchors: ADR-16 (int3 software + DRx hardware breakpoints), ADR-15 (DWARF via gimli), I1 (breakpoints must not perturb the deterministic tick stream), MM9 (a breakpoint is metadata layered over a deterministic replay, never part of the recorded execution — so its 0xCC must be invisible to the tick clock); Intel SDM Vol 3B (DR0–DR7, TF); DWARF v5 (.debug_line/.eh_frame).

  • breakpoint.rs: software breakpoint = save the byte at addr, write 0xCC; on SIGTRAP at addr+1, recognize via the breakpoint table, restore the byte, set RIP back, single-step over, re-arm. Hardware breakpoint = set DR0–DR3 + DR7 (exec condition) for ≤ 4 addresses.
  • step.rs: single-step via RFLAGS.TF (PTRACE_SINGLESTEP); continue = run replay until a breakpoint SIGTRAP or trace end; integrate with the divergence check (P7) on the same loop.
  • unwind.rs: stack unwinding via DWARF CFI (.eh_frame/.debug_frame) using gimli — walk frames from current (rip, rsp, rbp); produce Vec<Frame{pc, fp, sp, func}>.
  • dwarf.rs: map rip → (file, line) via .debug_line; resolve a variable name in a frame → location expression (DW_OP_*) → read the value from tracee memory/registers via state_query (P12 deepens this).
  • REPL commands in ttdb-cli: break <loc>, continue, step, next, bt (backtrace), print <var>, info regs.

9.3 Deliverable

ttdb replay trace/ REPL: set a breakpoint by function/line, continue to it, bt shows a correct call stack, print x shows a local variable's value — all reproducible because it runs over the recorded trace.

9.4 Acceptance Criteria

  • Breakpoint at a function entry is hit at the correct tick across ≥ 20 programs (sw + hw).
  • bt reconstructs ≥ 5 frames correctly for a recursive program (validated against gdb on the live program).
  • print reads correct values for int/pointer/struct locals at a breakpoint.
  • Breakpoint hits do not perturb the tick stream (breakpoint int3 is transparent to replay determinism — the 0xCC is removed before any tick-affecting execution).

9.5 Conformance Fixtures

  • conformance/reverse/breakpoint_hit.* — break at known address; expected hit tick.
  • progs/recursive_fib — backtrace depth golden.
  • progs/struct_locals — variable values at a line golden.
  • malformed: breakpoint at an unmapped address → clear error, not a crash; breakpoint in the middle of an instruction → reject.

9.6 Pitfalls

  • int3 perturbs ticks if left in place: the 0xCC must be removed and the original instruction executed for the program's branch behavior to match record → step-over-then-rearm; never let the trap byte alter control flow that affects ticks.
  • Breakpoint vs our nondet-insn traps / signal anchors: multiple SIGTRAP sources → a single dispatcher keyed by RIP + source table.
  • DWARF location expressions can reference CFA, registers, or memory → a partial DW_OP evaluator is needed; unsupported ops → "optimized out / unavailable", never a wrong value.
  • PIE/ASLR base: DWARF addresses are link-time; add the recorded load bias (I8) to get runtime addresses.
  • Inlined functions / optimized code: line tables can be non-monotonic → present best-effort, flag <optimized>.

9.7 Performance Concerns

  • continue to a far breakpoint replays many events → use breakpoints + the timeline (a hardware breakpoint avoids per-instruction stepping). Unwinding parses CFI lazily + caches per-function CFA rules. DWARF line lookup uses a sorted address table (binary search).

9.8 Edge Cases

  • Breakpoint at an address executed many times → hit each time (count + conditional breakpoints later). Recursive frame with no frame pointer → rely on CFI, not rbp-chaining. Breakpoint set after seeking backward (P10) → must be armed in the restored process. Self-modifying code at a breakpoint address → re-validate the saved byte. Tail calls → CFI must still unwind.

9.9 Failure Analysis

  • Breaks: a left-in int3 changes a branch → divergence (caught by P7) or a wrong backtrace from bad CFI. Detection: divergence, or backtrace mismatch vs gdb in tests. Blast radius: the debug session. Containment: breakpoint table is authoritative; assert no stray 0xCC before CONT. Recovery: clear all breakpoints, re-arm. Postmortem: dump the breakpoint table + bytes at each address.

9.10 Operational Notes

  • Telemetry: breakpoint_set{addr,kind}, breakpoint_hit{addr,tick}, unwind{frames}, dwarf_lookup{rip,file,line}. Compatibility: breakpoints are session state (not persisted). Operational: forward debugging is the familiar UX layer; the novelty (reverse) builds on it in P10. Document DWARF prerequisites (compile with -g, no strip).

Phase 10 — Reverse execution

10.1 Objectives

The headline feature. Implement reverse-continue (run backward to the most recent breakpoint hit before "now") and reverse-step (one source line / instruction backward), built on checkpoints + forward replay search (principle 8). The user perceives backward execution; the engine never actually runs the CPU backward.

10.2 Detailed Implementation Steps

Theory anchors: ADR-08 (checkpoint + replay-forward search), P8 (checkpoints are the time machine), P15 (record once, replay infinitely — reverse ops never re-record), I4 (checkpoint consistency under restore), MM8 (reverse cost = window distance to the nearest prior checkpoint), MM10 ("backward" is an illusion built from a forward scan plus a select-last — the CPU never runs in reverse); King/Dunlap/Chen ATC 2005 reverse-execution algorithm; gdb reverse.c UX.

  • reverse.rs reverse_continue(): let now = current tick. Restore the nearest checkpoint ≤ now (timeline.seek substrate). Replay forward from the checkpoint to now, recording every tick at which any armed breakpoint is hit (a hit list). The answer = the last hit with tick < now. Seek to that tick. If no hit in [checkpoint, now), step back to the previous checkpoint and repeat (expand the window backward) until a hit is found or tick 0 is reached.
  • reverse_step(): target = the instruction/line immediately before now. Restore nearest checkpoint ≤ now, replay forward to now − 1 instruction (or to the start of the previous source line via DWARF line boundaries), land there. For a single instruction: replay to now, note the penultimate (tick, rip), seek there.
  • Reverse-next (step over backward): combine reverse_step with breakpoint-on-return-address logic in reverse.
  • Window management: choose the search window using the checkpoint spread so a reverse-continue scans ≤ one interval typically; for a hit far back, expand window checkpoint-by-checkpoint.
  • Maintain a "current position" cursor (tick) in Session; all reverse/forward ops move it; breakpoints/watchpoints evaluated relative to it.

10.3 Deliverable

ttdb replay trace/ REPL: after running forward and hitting a fault, reverse-continue stops at the previous time the breakpoint condition held; reverse-step walks backward line by line. Demonstrated in examples/crash_repro (reverse from a SIGSEGV to the corrupting write).

10.4 Acceptance Criteria

  • reverse-continue from tick T to a breakpoint stops at the greatest hit tick < T (verified against a recorded list of all hits) for ≥ 20 programs.
  • reverse-step lands exactly one source line / instruction earlier, with correct regs (matches a from-start replay to that tick).
  • Latency bounded by the checkpoint interval for hits within one interval (§4); expands predictably for further hits.
  • Alternating forward/reverse navigation converges to consistent state at each stop (no drift; I4).

10.5 Conformance Fixtures

  • conformance/reverse/reverse_continue_lasthit.* — golden last-hit tick before a given now.
  • conformance/reverse/reverse_step_line.* — golden previous-line tick.
  • examples/crash_repro/ — record a UAF, reverse-continue to the free, then to the alloc.
  • malformed: reverse past tick 0 → stop at start with a clear "beginning of recording" message, not an error.

10.6 Pitfalls

  • Off-by-one at the boundary: reverse-continue must stop strictly before now (tick < now), else it returns the current position → define the comparison precisely and test the boundary.
  • Re-arming breakpoints in the restored process: after restoring a checkpoint the int3 bytes are gone (the checkpoint captured pre-breakpoint memory) → re-arm all breakpoints after every restore (P9 interaction).
  • Hit list cost: recording all hits in a window then picking the last is simpler and more robust than trying to stop at the right one during a single backward-feeling pass → prefer the scan-and-pick approach.
  • Conditional breakpoints in reverse: the condition must be evaluated at each candidate hit during the forward scan.
  • Window too small repeatedly: expanding one checkpoint at a time can be slow if hits are far back → exponentially expand the window for deep reverse-continue.

10.7 Performance Concerns

  • Reverse-continue = one (or a few) interval replays + breakpoint evaluation at each hit → dominated by replay speed (P7) and interval size (P8). Hardware breakpoints during the scan avoid per-instruction stepping. Cache the hit list for repeated reverse ops in the same window.

10.8 Edge Cases

  • Breakpoint hit exactly at a checkpoint boundary → include/exclude consistently. Reverse-continue with no breakpoints set → run to the start (or to the previous explicit stop). Reverse into a different thread's execution (the interleaving is fixed by Sched events) → cursor follows the recorded global order. Reverse across a signal anchor → the handler frame appears/disappears consistently. Reverse-step at the very first instruction → no-op with a message.

10.9 Failure Analysis

  • Breaks: returning the wrong hit (not the last before now) → user debugs the wrong event → detection via the golden last-hit fixtures + consistency check (forward to the returned tick must show the breakpoint condition true and no later hit < now). Blast radius: a single navigation. Containment: the hit list is recomputed deterministically from the trace. Recovery: re-scan. Postmortem: dump the hit list + chosen tick.

10.10 Operational Notes

  • Telemetry: reverse_continue{from,to,window,hits}, reverse_step{from,to}, window_expand{count}. Metrics: reverse-op latency histogram, window sizes. Compatibility: reverse ops are pure functions of the trace + breakpoints (no new persisted state). Operational: this is the feature users adopt the tool for — docs/runbooks includes a "reverse from a crash to root cause" walkthrough.

Phase 11 — Watchpoints (forward via hardware debug registers, reverse via replay scan)

11.1 Objectives

Data watchpoints: forward watchpoints via hardware debug registers DR0–DR3 (write/read-write/exec, 1/2/4/8-byte), and reverse watchpoints ("when did this memory last change before now?") via a replay scan over a window (principle 8). Answers the classic "who wrote this?" question both directions.

11.2 Detailed Implementation Steps

Theory anchors: ADR-17 (DR0–DR3 forward, replay-scan reverse), P8 (checkpoint substrate for the reverse scan), MM8 (reverse-watch cost = window distance to the nearest checkpoint), MM10 (reverse-watch is a forward write-scan plus select-last, not backward execution); Intel SDM Vol 3B (DR0–DR3 length/alignment + DR6 status).

  • watchpoint.rs forward: program DR0–DR3 with the target address; DR7 sets length + condition (RW bits) per register; on the debug-trap SIGTRAP, identify which DRx fired (DR6 status), report the watch hit at the current tick + RIP.
  • Reverse watchpoint: to find the last write to [addr,len) before now, restore the nearest checkpoint ≤ now, replay forward to now, and either (a) set a hardware write-watchpoint and collect all hit ticks then pick the last < now, or (b) for ranges > 4 watch slots, scan by reading [addr,len) at fine tick granularity and detect the value change (slower fallback).
  • ReplayScan impl in WatchImpl::ReplayScan: window-bounded forward replay collecting write events to the watched range; expand window backward as in reverse-continue (P10) if no write found.
  • Combine with DWARF: watch <var> resolves the variable's address + size, then arms the appropriate watch.
  • REPL: watch <expr>, rwatch, awatch, reverse-watch (last change before now).

11.3 Deliverable

watch globalCounter then continue stops when it changes (forward); reverse-watch globalCounter from a corrupted-value point jumps to the exact write that set the bad value (examples/crash_repro extended: find the corrupting store).

11.4 Acceptance Criteria

  • Forward hardware watchpoint fires at the exact tick of a write for ≥ 4 simultaneous watches (DR0–DR3).
  • Reverse-watch returns the greatest tick < now at which the watched range changed, validated against a recorded change list.
  • 1/2/4/8-byte watch lengths all detect correctly (alignment handled).
  • Reverse-watch latency bounded by the checkpoint interval for changes within one interval.

11.5 Conformance Fixtures

  • conformance/reverse/watch_write_tick.* — golden write tick (forward).
  • conformance/reverse/reverse_watch_lastchange.* — golden last-change tick before now.
  • progs/global_counter — single global mutated at known points.
  • malformed: unaligned 8-byte watch → either reject or split; watch on > 4 ranges → fall back to ReplayScan.

11.6 Pitfalls

  • DR slot exhaustion: only 4 hardware watchpoints → the 5th must use page-protection or replay-scan fallback → ReplayScan covers it (slower).
  • Watchpoint length/alignment: x86 hardware watch requires power-of-two length + alignment → split or reject misaligned ranges, do not silently watch the wrong bytes.
  • Reverse-watch over large ranges: a hardware watch covers ≤ 8 bytes; a struct/array reverse-watch needs ReplayScan or multiple slots → choose by size.
  • Stale debug registers across restore: like breakpoints, DRx must be re-programmed after a checkpoint restore (P8/P10 interaction).
  • Watch hit vs single-step trap: DR6 status bits disambiguate which DRx vs a TF single-step → read DR6 on every SIGTRAP.

11.7 Performance Concerns

  • Hardware watchpoints are free during normal execution (no per-instruction cost) — the preferred path. ReplayScan is O(window) replay + value reads → reserve for > 4 ranges or > 8 bytes. Cache change lists for repeated reverse-watch in a window.

11.8 Edge Cases

  • Watched memory unmapped mid-execution (munmap) → watch becomes inactive; report the unmap. Watch on a stack address that is reused across frames → fires for unrelated frames (document; combine with frame scoping). Multiple writes to the watched range in one instruction (e.g. rep movsb) → report once at that instruction's tick. Reverse-watch when the value was never different before now → "no change in recording" message.

11.9 Failure Analysis

  • Breaks: a missed write (ReplayScan granularity too coarse) → reverse-watch returns an earlier change, missing the real one → detection via the change-list fixture; mitigate by scanning at write-event granularity, not sampled. Blast radius: one query. Containment: deterministic re-scan. Recovery: re-run with finer granularity. Postmortem: dump the change list + chosen tick.

11.10 Operational Notes

  • Telemetry: watch_set{addr,len,kind,impl}, watch_hit{addr,tick}, reverse_watch{addr,from,to}. Metrics: watch-hit latency, ReplayScan fallback rate. Compatibility: watch is session state. Operational: reverse-watch is the second killer query ("what corrupted this?"); pair with reverse-continue in runbooks.

Phase 12 — State reconstruction and query at arbitrary tick

12.1 Objectives

Expose "show me the full program state at tick T" as a first-class query: registers, memory contents, call stack, source line, and resolved local/global variables at any T, by seeking (P8) and reading. Lay groundwork for an omniscient/queryable view (Pernosco-style north star) without re-recording (principle 15). Includes the deferred-scope notes for §12.3/§12.4/§12.5.

12.2 Detailed Implementation Steps

Theory anchors: P15 (record once, replay infinitely — all queries hit the existing trace), P8 (seek substrate), I1/I4 (queried state equals from-start replay state), MM8 (query latency = distance to the nearest checkpoint; the deep index amortizes it), MM7 (a queried state is just replay's deterministic output at tick t); Pernosco (post-hoc queryable-state north star, papers §5 #9); ODR/CASTOR (§12.5 multicore-deferral rationale, papers §5 #14/#15).

  • state_query.rs: state_at(t) -> ProgramState{regs, maps, stack:Vec<Frame>, line, vars:Vec<Var>} = timeline.seek(t) then GETREGS + unwind (P9) + DWARF resolve (P9). Cache recent states.
  • Memory query: read_mem_at(t, addr, len) = seek(t) + read_mem. Range/struct pretty-print via DWARF type info.
  • Variable lifetime: a variable's value over a tick interval = sample at line boundaries or watch its address (P11) — exposed as history <var> (list of (tick, value) where it changed).
  • Optional index build (trace index --deep): a post-hoc pass that records, per checkpoint interval, the set of memory regions touched + a coarse value timeline → accelerates repeated queries (the Pernosco-style DB; bounded, opt-in).
  • Deferred scope notes captured here:
    • PhaseDeferred("FINAL_BLUEPRINT §12.3") — perf-counter portability: per-microarch retired-branch calibration + Intel PT alternative; a trace currently replays only on matching CPUs.
    • PhaseDeferred("FINAL_BLUEPRINT §12.4") — shared-memory inter-process race recording: requires page-ownership tracking; single-tracee serialization does not capture true sub-quantum races.
    • PhaseDeferred("FINAL_BLUEPRINT §12.5") — true-parallel multicore recording: chunk-and-merge (CASTOR) or HTM approaches; current design serializes (principle 4).

12.3 Deliverable

ttdb replay trace/ REPL: state @ <tick> prints regs + backtrace + source line; history <var> prints every value the variable held with the tick of each change; mem @ <tick> <addr> <len> dumps memory at that point.

12.4 Acceptance Criteria

  • state_at(t) for ≥ 50 random t returns regs/memory identical to a from-start replay to t (I1/I4).
  • history <var> lists exactly the ticks at which the variable changed (validated against an instrumented reference).
  • Repeated queries to nearby ticks reuse cached/checkpointed state (latency drops on the second query in a region).
  • Deferred-scope items are documented with their §refs and detected (not silently wrong) when encountered (e.g. a multicore race surfaces as divergence, §12.4).

12.5 Conformance Fixtures

  • conformance/reverse/state_at_random.* — golden full-state at random ticks.
  • conformance/reverse/var_history.* — golden change list for a variable.
  • progs/data_race (in examples/) — documents the §12.4 limitation (recorded interleaving is one of many; true race not reproduced sub-quantum).
  • malformed: query at a tick beyond trace end → clamp + message; query for an out-of-scope variable → "not in scope at this tick".

12.6 Pitfalls

  • Variable scope vs tick: a local is only live in part of its function → resolving it outside its PC range gives garbage → gate variable resolution on the DWARF lexical-block PC range at tick t.
  • Optimized-away values: report <optimized out>, never a stale register guess.
  • Query thrash: random-access queries far apart each pay a full seek → encourage locality; the deep index amortizes.
  • Memory aliasing across seeks: ensure each seek fully restores (P8 verify) before reading, else stale pages leak into the answer.
  • Deferred-scope confusion: users may expect multicore reproduction → the §12.4 limitation must be surfaced in docs + at record time (warn if true multithread parallelism was serialized).

12.7 Performance Concerns

  • Each state_at is a seek (bounded by interval) + unwind + DWARF resolve. Caching a window of states makes scrubbing (UI timeline drag) smooth. The deep index trades a one-time post-hoc pass for fast repeated queries. Variable history over a long range = a windowed replay-scan (P11 substrate).

12.8 Edge Cases

  • Tick in a region with no checkpoints nearby (after eviction) → slower seek, still correct. Variable that is a register at one tick and spilled to stack at another (DWARF location lists) → resolve per-tick location. Querying state inside a signal handler → the handler frame is present (P6 anchor). Querying across a thread switch → state is that of the runnable thread at t (Sched-ordered). Huge memory dump request → stream + cap.

12.9 Failure Analysis

  • Breaks: wrong variable value from mis-evaluated DWARF location → user draws wrong conclusions → detection via var_history golden + cross-check against gdb on the live program. Blast radius: a query's correctness. Containment: location evaluation is conservative (unavailable beats wrong). Recovery: fix the DW_OP evaluator. Postmortem: dump the location expression + register/memory inputs.

12.10 Operational Notes

  • Telemetry: state_query{tick,latency}, var_resolve{name,tick,available}, deep_index_build{intervals,bytes}. Metrics: query latency, cache hit rate. Compatibility: the deep index is a derived artifact (rebuildable, versioned). Operational: history + state @ tick power the "what was the program doing at the moment of failure?" workflow; deferred-scope limitations are documented prominently.

Phase 13 — DAP server with reverse-execution extensions

13.1 Objectives

Expose ttdb to editors via the Debug Adapter Protocol so users debug visually, including reverse operations. Implement the standard request/response/event flow plus supportsStepBack and a custom seekTick, mapping DAP's forward-oriented model onto the timeline (the Target trait, §11).

13.2 Detailed Implementation Steps

Theory anchors: ADR-18 (DAP + reverse extensions), P11 (observability by default — tick exposed as a custom body field), MM10 (the timeline is bidirectional; DAP's forward-only model is bridged, and the leaks are documented in §13.6); DAP spec (supportsStepBack); the Target trait (§11) abstraction from gdb target.c.

  • protocol.rs: DAP message framing (Content-Length header + JSON body over stdio or a localhost socket); request/response/event structs for initialize, launch/attach, setBreakpoints, setFunctionBreakpoints, setDataBreakpoints (watchpoints), threads, stackTrace, scopes, variables, continue, next, stepIn, stepOut, pause, disconnect.
  • Reverse extensions: advertise supportsStepBack=true, supportsRestartFrame, supportsDataBreakpoints in the initialize response; implement stepBack (→ reverse-step, P10), reverseContinue (→ reverse-continue, P10), and a custom request ttdb/seekTick (→ timeline.seek, P8).
  • handlers.rs: translate DAP requests to Target calls (Session methods); emit stopped events (reason: breakpoint/step/data breakpoint/entry) with the current tick exposed as a custom body field; output events relay recorded program stdout (from the trace, not real I/O).
  • reverse_ext.rs: a custom timeline view — expose total ticks + current tick so a frontend can render a scrubber; handle ttdb/seekTick for timeline drag.
  • Map DAP variablesReference to frames/scopes resolved via P12 state_at(current_tick).

13.3 Deliverable

A VS Code (or any DAP client) session attaches to ttdb dap trace/, sets breakpoints, steps forward and backward (Step Back button), inspects variables, and scrubs the timeline via seekTick. Recorded program output appears in the debug console.

13.4 Acceptance Criteria

  • A DAP client completes initialize → setBreakpoints → configurationDone → stopped → stackTrace → variables → continue without protocol errors (validated against the DAP test harness / a reference client).
  • stepBack and reverseContinue produce correct stops matching the REPL reverse ops (P10) at the same ticks.
  • setDataBreakpoints arms a watchpoint that fires (P11) and reports via a stopped(reason:data breakpoint) event.
  • ttdb/seekTick repositions the session and refreshes stack/variables consistently.

13.5 Conformance Fixtures

  • conformance/... DAP request/response golden transcripts (dap_initialize.json, dap_stepback.json).
  • fuzz/dap_protocol.rs — malformed DAP messages must never panic; respond with an error response.
  • progs/struct_locals driven via DAP variables — golden variable tree.
  • malformed: a request before initialize → DAP error response, not a crash; oversized Content-Length → bounded, rejected.

13.6 Pitfalls

  • DAP assumes forward-only: there is no native "current time" → expose tick via custom body fields + ttdb/seekTick; frontends without reverse support still work forward-only.
  • variablesReference lifetime: references are valid only for the current stop → invalidate them on any navigation (forward, reverse, seek) to avoid reading stale state.
  • Threads in DAP vs serialized scheduling: present recorded threads; "running" is the Sched-current thread at the cursor → map carefully so the UI thread list matches the timeline.
  • Output ordering: relayed program output must be ordered by tick, not by when the DAP server reads it.
  • Blocking the protocol loop: a long seek/reverse-continue must not stall the DAP loop → run navigation on the owner thread, send progress events; keep protocol I/O responsive.

13.7 Performance Concerns

  • DAP variables expansion triggers state queries (P12) → cache per-stop. Timeline scrubbing fires many seekTicks → debounce + reuse checkpoints. JSON encode/decode is off the hot replay path. Keep the protocol socket non-blocking.

13.8 Edge Cases

  • Client disconnects mid-navigation → abort cleanly, keep the trace intact. restartFrame → re-seek to that frame's entry tick. Conditional/log breakpoints from DAP → evaluate the condition during replay. Multi-thread stackTrace for a non-current thread → seek/reconstruct that thread's last position. terminate vs disconnect semantics → both leave the (immutable) trace usable.

13.9 Failure Analysis

  • Breaks: a protocol desync (wrong seq/response) hangs the frontend → detection via the DAP harness + a watchdog on pending requests. Blast radius: the editor session (trace unaffected). Containment: strict request/response correlation by seq. Recovery: client reconnects to the same trace. Postmortem: log the full DAP transcript.

13.10 Operational Notes

  • Telemetry: dap_request{command,seq}, dap_response{command,success}, dap_event{event}. Compatibility: DAP version + advertised capabilities documented; ttdb/* custom requests namespaced. Operational: docs/runbooks includes editor setup (launch.json with "type":"ttdb"); the DAP server is the primary end-user surface; localhost-only socket by default (no remote exposure).

Phase 14 — Recording persistence / portability + overhead tuning

14.1 Objectives

Make traces portable and recording efficient: package a trace as a self-contained, movable artifact (incl. the binary + needed mmap-backing files + metadata); add the syscall-buffer optimization (rr-style) to cut recording overhead; mitigate vDSO bypass; and tune toward the §4 overhead targets. Final hardening pass.

14.2 Detailed Implementation Steps

Theory anchors: P1 (determinism over convenience — buffered syscalls must not leak nondeterminism), P12 (bounded resource usage), P13 (stable, portable trace format), I1 (any buffering/vDSO gap surfaces as divergence, never silent), MM2 (the syscallbuf still captures the full return + memory effect, just without a ptrace stop), MM3 (the CPU-compat gate exists because the Tick clock is microarch-specific); rr paper (ATC 2017) syscallbuf optimization.

  • Trace packaging: ttdb pack trace/ -> trace.ttz bundles header.bin, events.log, blobs/, checkpoints/ (optional), the recorded binary + its shared libraries + any file-backed mmaps referenced (content-addressed) + CPU/microarch metadata; ttdb unpack restores a replayable directory on a compatible host.
  • vDSO mitigation: at record start, patch the tracee's vDSO (gettimeofday/clock_gettime/getcpu/time) to trap into a real syscall (overwrite the vDSO entry with a syscall stub or int3) so these fast-path calls become recordable (closes the §8.17 vDSO divergence source).
  • Syscall buffer (overhead optimization): inject a small in-tracee buffer + a patched libc/syscall site so batched, deterministic syscalls record into shared memory without a ptrace stop each, flushed periodically (rr's syscallbuf). This is the main lever to reach 1.2×–2× (ADR-referenced, previously deferred from P2).
  • Portability metadata + replay gate: record CPU model, microcode, retired-branch event config; on replay assert compatibility or attempt recalibration (PhaseDeferred §12.3 for cross-microarch).
  • Overhead tuning pass: profile record + replay (flamegraphs), reduce ptrace round-trips, batch MemWrite reads, right-size checkpoint interval; meet §4 targets in benchmarks/overhead.

14.3 Deliverable

ttdb pack/unpack move a recording between machines and it replays; a vDSO-heavy program (frequent clock_gettime) now records + replays deterministically; recording overhead on the benchmark suite meets the §4 envelope.

14.4 Acceptance Criteria

  • A packed trace replays on a second compatible host with zero divergence; on an incompatible CPU it refuses with a clear message (not a silent wrong replay).
  • vDSO-fast-path syscalls are captured (a clock_gettime loop replays deterministically; previously diverged).
  • Recording overhead ≤ 2× on CPU-bound benchmarks and ≤ 5× on syscall-heavy benchmarks after the syscall buffer (§4).
  • Replay overhead ≤ 1.8× (§4).

14.5 Conformance Fixtures

  • conformance/trace_format/packed_roundtrip.ttz — pack→move→unpack→replay golden.
  • progs/vdso_clock — clock_gettime loop; deterministic replay after the vDSO patch.
  • benchmarks/overhead/* — record/replay overhead-ratio gates wired into bench.yml.
  • malformed: packed trace with a missing referenced library → clear "missing backing object" error; incompatible-CPU trace → refusal.

14.6 Pitfalls

  • Syscall buffer breaks determinism if mis-scoped: only deterministic, side-effect-contained syscalls may be buffered; anything that can be interrupted/signal-affected must still trap → conservative buffering list.
  • vDSO patch fragility: vDSO layout varies by kernel → detect the symbols dynamically (parse the vDSO ELF) before patching; fall back to "warn + treat as nondet" if unknown.
  • Packaging file-backed mmaps: a memory-mapped file that changes between record and replay → content-address + bundle it; refuse if a referenced file is absent and not bundled.
  • Microarch portability illusion: a trace may appear to replay on a different CPU then diverge deep in → gate strictly on the recorded event config; recalibration is a deferred research item (§12.3).
  • Overhead regressions: a refactor silently doubles ptrace round-trips → the bench.yml gate must fail the build on overhead regression.

14.7 Performance Concerns

  • The syscall buffer is the dominant overhead win (eliminates 2 ptrace stops per buffered syscall). Packaging is I/O-bound and offline (not on the hot path). vDSO patching adds a syscall per former-fast-path call (cost, but correctness-required). Final flamegraph-driven tuning targets ptrace round-trips, process_vm_readv batching, and checkpoint cadence.

14.8 Edge Cases

  • Packed trace > available disk on the target → stream-unpack or refuse early. Binary uses absolute paths to data files → bundle or record content. Kernel newer/older than recorded (syscall numbering stable, but new syscalls) → replay refuses on unknown event kinds (forward-compat skip only for trace kinds, not syscalls). Buffered syscall interrupted by a signal mid-batch → fall back to trapped recording for that call.

14.9 Failure Analysis

  • Breaks: a buffered syscall that should have trapped → unrecorded nondeterminism → divergence on replay (I1). Detection: divergence + the buffering list audit. Blast radius: programs using that syscall pattern. Containment: conservative buffer list; easy to shrink. Recovery: remove the syscall from the buffer list, re-record. Postmortem: which buffered call preceded the divergence.

14.10 Operational Notes

  • Telemetry: pack{bytes,objects}, vdso_patch{symbols}, syscallbuf_flush{count}, overhead-ratio metrics. Compatibility: packed-trace format versioned; CPU-compatibility gate explicit. Operational: ttdb pack enables "attach the trace to the bug report" workflows (CI flaky-test forensics — a failing CI run uploads trace.ttz, a developer replays it locally). This closes the loop on the primary use case.

Operational Readiness

  • Metrics. Record: overhead ratio, syscalls intercepted/sec, trace growth B/s, seccomp-skip rate. Replay: events/sec, divergence count (must be 0), seek/reverse latency histograms. Resources: supervisor RSS, checkpoint memory, fd count. Exported via the metrics facade; optional Prometheus textfile.
  • Tracing. tracing spans around record loop iteration, replay event, seek, reverse-continue, checkpoint create/restore; span fields carry tick + kind. JSON output for machine ingestion.
  • Structured logging. Every event/divergence/anchor/checkpoint logs structured fields (tick, rip, reg). TRACE level dumps each ptrace op + wait status (for supervisor-hang forensics).
  • Dashboards. (1) Recording health: overhead, growth, intercept rate. (2) Replay health: events/sec, divergence (alarm if > 0), seek latency. (3) Resources: RSS, checkpoint memory, fds.

  • Incident response. Divergence → divergence_bisect → identify first bad event → classify (record gap vs trace corruption) → fix table / re-record. Runbooks: divergence.md, trace_corruption.md, perf_counter.md.
  • Backup / restore. A trace directory (or packed .ttz) is the backup unit; copyable, self-contained (after pack). Restore testing: packed_roundtrip fixture in CI replays a moved trace.
  • Deployment topology. Single host (record + replay co-located) or split (record on a CI worker, replay on a developer machine via pack/unpack). No clustering.
  • Canary / rolling upgrade / rollback. New ttdb versions must replay old traces (compat gate); a canary replays a golden trace corpus before rollout; rollback = previous binary (traces unaffected, immutable). Migration: trace migrate for minor-version traces.
  • Compatibility strategy. See § Compatibility & Versioning; the trace format and CPU-compat gate are the load-bearing contracts.

Compatibility & Versioning

  • Wire/file compatibility. Trace = versioned header (format_version = MAJOR.MINOR). Same MAJOR ⇒ readable; unknown future event kinds are length-prefixed and skippable (forward-compat read). MINOR bump = additive (new kinds/fields). MAJOR bump = breaking; trace migrate provided for one MAJOR back.
  • Storage compatibility. Blob store + PageDiff + checkpoint formats each carry a version; derived artifacts (index.bin, deep index) are rebuildable and never a compatibility constraint.
  • Schema evolution. New syscall coverage = interception-table version (MINOR). New register state (e.g. future arch) = RegisterFile trailer (additive). Per-Payload-variant trailers allow added fields.
  • API stability. ttdb-core types and the Target trait are the normative API; SemVer on the library crates. The DAP custom requests (ttdb/*) are namespaced and versioned in initialize.
  • CPU compatibility. A trace records its retired-branch event config + CPU/microcode; replay asserts a match. Cross-microarch replay is gated (refuse) until §12.3 calibration lands. This is an explicit, non-silent boundary.
  • Migration / deprecation. Deprecated event kinds remain readable for one MAJOR. Deprecation announced in CHANGELOG.md; a trace recorded on version N replays on N..N+1 minor and the next MAJOR with migration.
  • Rolling-upgrade guarantee. New ttdb replays all in-MAJOR older traces; CI gates this with a golden-trace corpus across versions.

Testing & Verification Strategy

  • Unit. Per-crate: Tick arithmetic, register encode/decode, trace block round-trip, seccomp filter build, DWARF location eval, breakpoint arm/disarm.
  • Integration. End-to-end record→replay on the progs/ corpus; seek/reverse/watch flows; DAP request/response transcripts.
  • Differential. Replay vs a from-start replay (must match at every tick). Where rr is available, differential record/replay of the same program (behavioral cross-check). Backtraces/variable values vs gdb on the live program.
  • Property. Random deterministic programs: record→replay yields identical tick+reg streams (I1). Seek to random ticks equals from-start replay (I4). Reverse-continue returns the greatest hit < now (P10 property).
  • Fuzzing. trace_parse (torn/garbage traces never panic), syscall_decode (arg/return decoding), dap_protocol (malformed DAP). CI budget per target; libFuzzer corpora committed.
  • Chaos / fault injection. Kill record mid-write (torn tail recovery); corrupt random trace bytes (CRC detection); inject an untrapped nondet insn (divergence fires); drop/duplicate a trace event (divergence/anchor error).
  • Deterministic replay. The core acceptance: a recorded trace replays bit-identically N times (I1) — gated in CI.
  • Soak. Long recordings (minutes of execution) → trace growth + checkpoint eviction behave; replay the whole thing without divergence or OOM.
  • Conformance. The conformance/ buckets (syscall, signals, reverse, trace_format) with golden outputs; version-compat traces across format versions.
  • Performance regression. bench.yml gates overhead ratio + seek latency; fails the build on regression beyond a threshold.

Scalability Analysis

  • Bottlenecks. Record: ptrace stop rate (syscall-heavy workloads) and trace I/O bandwidth. Replay: event decode + injection + divergence checks. Reverse: checkpoint interval (replay distance per op).
  • Scaling ceilings. Single-core serialization caps recordable parallelism (principle 4) — a 32-thread program records at ~1-core speed. Trace size scales with recorded I/O volume (GB/min possible). Checkpoint memory scales with writable working set × checkpoint count.
  • Horizontal scaling. None within a session (a trace is one process). "Scale-out" is operational: record on many CI workers in parallel, each producing an independent .ttz; replay distributed across developer machines.
  • Vertical scaling. Faster CPU + more RAM → smaller checkpoint interval (faster seek) + faster single-step. Faster disk → higher trace growth tolerance.
  • Sharding / partitioning. The trace can be partitioned by tick range for parallel analysis (deep index build, Phase 12) but replay itself is inherently sequential within a window.
  • Replication / coordination. None (single host, no consensus). The only coordination is owner-thread ↔ UI channel.
  • Network fanout. None in core; DAP is point-to-point localhost.
  • Scheduler saturation. Record scheduler handles thread-switch decisions; switch rate scales with quantum (tunable) — not a true scaling limit, a determinism/overhead knob.
  • Storage growth. Monotonic per recording; bounded by pack compression + checkpoint eviction; operators set quotas/retention on .ttz artifacts.
  • Metadata scaling. Tick index + checkpoint map are O(events / sampling), kept small; the deep index is opt-in and bounded per interval.

Mental Models & First Principles

The compressed models an expert holds about deterministic record/replay. Each: the insight, what it predicts, the bug class you ship without it, and the § where this blueprint applies it. All cited §/Phase references resolve.

  • MM1 — The supervisor is a state machine clocked by ptrace stops. Insight: ttdb makes no progress between waitpid returns; every stop is a transition with a defined action. Predicts: a CONT issued in the wrong state desynchronizes the whole run. Bug without it: "lost stop" hangs and free-running tracees. Applied in: §8.16 (the state-transition table), Phase 1 (§1.2, owner-thread + state machine), § Failure Modes & Recovery (Supervisor hang).
  • MM2 — A syscall's full effect is (return register + every byte the kernel wrote). Insight: replay needs not just the return value but the exact output-buffer bytes, sized by the result, not the argument. Predicts: using the arg length captures uninitialized bytes that diverge later. Bug without it: silent record-side gaps surfacing as far-downstream divergence. Applied in: §8.11 (MemWrite schema), Phase 2 (§2.2, §2.6 out-length pitfall), Phase 7 (§7.2 injection).
  • MM3 — A hardware perf counter is a logical clock; skid is its quantization error. Insight: retired conditional branches order instructions, but the overflow interrupt fires near not at the triggering instruction. Predicts: you can count to a neighborhood but must single-step the residual to land exactly. Bug without it: async events placed one branch early/late → divergence at delivery. Applied in: §6 P7 (two-stage convergence), Phase 3 (§3.2, §3.6), §4 (skid margin constraint).
  • MM4 — A crash-only log is correct iff every torn tail truncates to a valid prefix. Insight: durability is not "never lose data" but "what survives is always replayable." Predicts: with per-block CRC + length prefix, a kill -9 mid-append costs only the in-flight block. Bug without it: a half-written final record read as valid → immediate replay divergence. Applied in: §6 P5, Phase 4 (§4.2, §4.6), I9.
  • MM5 — Serialization turns a race into a recordable total order. Insight: running ≤1 tracee thread at a time makes the interleaving a sequence of Sched events instead of a non-deterministic memory race. Predicts: recorded parallel programs are slower but reproducible; true sub-quantum races are not captured. Bug without it: "it reproduced once and never again." Applied in: §6 P4, Phase 5 (§5.2, §5.7), I5, the §12.4 deferral.
  • MM6 — An async event has no natural place in a deterministic re-run; the tick coordinate is the only thing that gives it one. Insight: a signal can arrive at any instruction during record, so replay must be told the exact (Tick, IP, regs) to re-deliver it. Predicts: a coordinate missing any of the three cannot be re-found. Bug without it: the handler runs at the wrong instruction. Applied in: Phase 6 (§6.2), I10, §8.17 (signal-one-branch-late example).
  • MM7 — Replay is the same deterministic function as record, run on injected inputs; equal inputs force equal state. Insight: given identical nondeterministic inputs, the CPU is a pure function — so any observed inequality is a real missing input, never noise. Predicts: divergence is always actionable; it points at a record-side gap. Bug without it: tolerating "small" divergence and trusting corrupt state. Applied in: §6 P2/P6, Phase 7 (§7.2, §7.9), I1/I6.
  • MM8 — Random access into a deterministic stream costs (distance to the nearest snapshot). Insight: you cannot seek a replay directly; you restore a checkpoint ≤ T and replay forward. Predicts: checkpoint spacing is the single knob trading memory for seek/reverse latency; a logarithmic spread bounds any seek to one interval. Bug without it: linear replay-from-start makes reverse ops unusable. Applied in: §6 P8, Phase 8 (§8.2, §8.7), Phase 10 (§10.2), Phase 12 (§12.7), §4 (seek-latency constraint).
  • MM9 — A breakpoint is metadata over a deterministic replay, never part of the recorded execution. Insight: the 0xCC must be invisible to the tick clock — removed and the original instruction executed before any tick-affecting control flow. Predicts: a left-in trap byte changes a branch and diverges. Bug without it: breakpoints silently corrupt the replay they sit on. Applied in: Phase 9 (§9.2, §9.6), I1.
  • MM10 — "Backward" is an illusion built from a forward scan plus a select-last. Insight: reverse-continue / reverse-step / reverse-watch all = restore a prior checkpoint, replay forward collecting hits, and pick the last one before "now"; the CPU never runs in reverse. Predicts: off-by-one at the tick < now boundary returns the current position. Bug without it: the user debugs the wrong event. Applied in: Phase 10 (§10.2, §10.6), Phase 11 (§11.2), Phase 13 (§13.2 DAP bridge).

Mozilla rr. The one decision: rr optimizes recording overhead with an in-tracee syscallbuf that batches deterministic syscalls into shared memory without a ptrace stop each — the lever ttdb defers to Phase 14 (§14.2). Wins where low default-on recording overhead on commodity Linux x86-64 is paramount; it is the system ttdb most directly follows (papers §5 #5).

GDB record-full. The one decision: it records a per-instruction undo log rather than periodic checkpoints, so it can step exactly one instruction backward with zero replay. Wins for very short executions where exact instruction-granular reverse with no checkpoint/replay latency matters more than memory — the regime named in ADR-08 "When the Rejected Choice Wins". ttdb rejects it as the primary model because the undo log grows unbounded with execution length (§ Reference Implementations #6).

Microsoft WinDbg TTD. The one decision: it records by instrumenting/emulating every instruction instead of trapping only nondeterministic inputs, capturing a complete instruction stream. Wins on Windows (where ptrace + retired-branch-counter semantics are unavailable) and when a full per-instruction trace is wanted regardless of overhead (papers §5 #8). ttdb rejects whole-instruction instrumentation for the lighter input-only recording model (ADR-05, ADR-03).

Pernosco. The one decision: it separates recording from analysis — it builds a queryable state/dataflow database from a recording once, then answers every query (including reverse) from the DB rather than re-replaying. Wins for repeated omniscient queries over the same recording (dataflow "where did this value come from?"). ttdb adopts a bounded, opt-in slice of this as the Phase 12 deep index (§12.2) but keeps replay-on-demand as the default (papers §5 #9).

Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from the § System Constraints table (§4). Formulas shown; no asserted-only numbers.

  1. Bytes per recorded minute (typical). From §4 trace growth 1–50 MB/s: 1 MB/s × 60 s = 60 MB/min (light) to 50 MB/s × 60 s = 3000 MB/min ≈ 3 GB/min (heavy). Confirms the §4 "50 MB – 3 GB per recorded minute" row.
  2. One-hour recording footprint. 60 MB/min × 60 min = 3.6 GB (light) to 3 GB/min × 60 = 180 GB (heavy). Implies retention/quota policy on .ttz artifacts (§ Scalability Analysis, storage growth) — heavy workloads cannot be kept indefinitely.
  3. Event-record cache budget. §4 caps supervisor RSS at ≤ 256 MB excl. checkpoints. A fixed-size TraceEvent decode record ≈ RegisterFile (16×8 + rip + rflags + 2 base = ~152 B) + tick(8) + kind(1) + small payload header (~16 B) ≈ 180 B. A 16 MB decode/ring budget holds 16 MB / 180 B ≈ 93,000 in-flight events — ample headroom inside the 256 MB ceiling.
  4. FD budget headroom. §4 caps total FDs at ≤ 64. Per §4 "1 perf fd/thread": with trace files (~4) + tracee (~1) + DAP socket (1), the perf-fd budget is 64 − 6 ≈ 58 → up to ~58 concurrent tracee threads can each hold a pinned counter before exhausting FDs (ties to P5 per-thread counters, §5.2).
  5. Checkpoint interval in wall-clock vs ticks. §4 default = every ~2–5 s of replay OR N = 2M ticks. If replay retires branches at, say, the count that fills 2M ticks in 2 s, that is 2,000,000 / 2 s = 1,000,000 ticks/s of replay — the cross-check that the two interval expressions are consistent at the low end.
  6. Seek latency = interval replay time. §4: seek latency = replay time from nearest checkpoint ≤ T. With a 2 s interval (item 5), worst-case seek ≈ 2 s; reverse-continue worst case = seek + replay-scan to last hit ≈ one full interval ≈ 2 s (§4 reverse-continue row). Halving the interval to 1 s halves worst-case seek but doubles checkpoint count.
  7. Checkpoint count for a 10-minute replay. 600 s / 2 s = 300 checkpoints at the default interval. With a logarithmic spread (MM8, §8.7) the retained count is far lower; this is the naive upper bound the eviction policy must cut.
  8. Checkpoint memory pressure. §4: COW checkpoint cost = pages dirtied since last checkpoint. For a tracee dirtying, e.g., 10 MB of writable working set per 2 s interval, 300 naive checkpoints would cost 10 MB × 300 = 3 GB — over any sane ceiling, which is exactly why Phase 8 mandates eviction + logarithmic spread (§ Failure Modes & Recovery, OOM row).
  9. Single-step stretch cost. §4 single-step rate 10k–500k steps/s. To cover a skid residual of, say, 300 branches (§3.4) at the slow end: 300 / 10,000 = 30 ms; at the fast end 300 / 500,000 = 0.6 ms. This is why P7 keeps the skid margin tight (§3.6) — every convergence pays it.
  10. Tick read amortization. §4 tick read < 1 µs via the mmapped counter page. At a sync point per syscall, a syscall-heavy workload doing 100k syscalls/s pays 100,000 × 1 µs = 100 ms/s ≈ 10% just in tick reads — bounding how cheap the read path must stay (P3, §3.7 rdpmc fast path).
  11. Divergence-check cost. With regs_hash (§3.2) the per-sync-point compare is O(1) (one u64 compare). At 100k sync points/s that is 100,000 comparisons/s — negligible CPU, so the §4 replay-overhead target (1.1×–1.8×) is dominated by injection and convergence, not by the divergence check (P2, §7.7).
  12. Blob spill threshold sizing. §4 trace I/O is dominated by syscall output bytes. With a 4 KB inline/blob threshold (§4.2), a read(fd, buf, 1 MB) spills 1 MB / 4 KB = 256 page-sized chunks to the blob store rather than bloating the event log — keeping event records L2-resident (§4 CPU/cache note, §4.7).

Alternative Architectures (Roads Not Taken)

Three fundamentally different architectures for the same goal (process time-travel debugging), not parameter tweaks. Each: sketch, winning regime, the real system embodying it, why rejected here.

A. Full-VM record/replay (log at the virtual-hardware boundary).

   +-----------------------------+
   |        Guest OS + app       |
   |  (the program under study)  |
   +--------------+--------------+
                  | all device I/O, interrupts, DMA
   +--------------v--------------+
   |       Hypervisor / VMM      |
   |  logs every nondeterministic|
   |  input at the HW boundary   |
   +--------------+--------------+
                  v
            VM event log  --> deterministic whole-VM replay

Winning regime: whole-system bugs — kernel, drivers, cross-process and device/DMA nondeterminism — where process scope is too narrow. Real system: ReVirt (OSDI 2002) and "Debugging OS with Time-Traveling VMs" (ATC 2005) (papers §5 #6/#7). Why rejected: heavyweight (record the whole VM), and the project's goal is the harder process-level native case at low overhead; device/DMA replay is an explicit non-goal (§1). Lifting to VM scope would discard the retired-branch-counter approach (§6 P3) that makes commodity recording cheap.

B. In-process interposition (LD_PRELOAD / library-level record).

   +-------------------------------+
   |        app process            |
   |  +-------------------------+  |
   |  | interposed libc shims   |  |  record syscall args/results
   |  | (LD_PRELOAD) + emulator |  |  into an in-process buffer
   |  +-------------------------+  |
   +-------------------------------+
        no separate supervisor; no ptrace

Winning regime: cooperative targets where you only need library-call-level record with near-zero overhead and no privilege to ptrace. Real system: Jockey (AADEBUG 2005) (papers §5 #13). Why rejected: interposition cannot see register/signal state or trap nondeterministic instructions, and a hostile/statically-linked target bypasses the shims; ptrace gives the control LD_PRELOAD cannot (§ADR-03, § Reference Implementations #9). It is listed as ADR-03's "When the Rejected Choice Wins" regime.

C. True-multicore record with page-ownership / output-determinism.

   core0   core1   core2   core3      (threads run in PARALLEL)
     |       |       |       |
     +---+---+---+---+---+---+
         | page-ownership / version log
         v
   parallel-replay log  --> reproduces a *consistent* parallel run

Winning regime: bugs that only manifest under genuine parallelism, where single-core serialization (§6 P4) perturbs the bug away. Real systems: CASTOR (ASPLOS 2017, page-ownership) and ODR (SOSP 2009, output-determinism) (papers §5 #14/#15). Why rejected (here, for now): an order of magnitude more complex (page-ownership tracking or relaxed output-determinism semantics) and not needed for the single-process scope this blueprint targets; deferred as PhaseDeferred("FINAL_BLUEPRINT §12.5") and named in ADR-12's "When the Rejected Choice Wins". The serialized design detects (never silently mis-replays) such races as divergence (§12.4).

Glossary

  • Tick — retired-conditional-branch count; the monotonic logical clock over executed instructions; the temporal coordinate axis.
  • Coordinate — (Tick, IP, regs) triple uniquely locating an execution point for async re-delivery and seek.
  • Trace / EventLog — append-only, tick-indexed, on-disk record of all nondeterministic inputs.
  • TraceEvent — one recorded nondeterminism point: SyscallEntry/Exit, Signal, Sched, RdtscRdrandCpuid, MmapData.
  • MemWrite — bytes the kernel wrote into tracee memory during a syscall, captured for injection.
  • Checkpoint — a saved tracee state (regs + memory snapshot + fds) at a tick; the time-machine substrate.
  • MemSnapshot — checkpoint memory as a live COW fork (CowFork) or persisted page-diff (PageDiff).
  • ReplayTimeline — checkpoints indexed by tick + seek(T) (restore nearest ≤ T, replay forward).
  • Recorder — the record-side driver; intercepts and logs nondeterministic inputs.
  • Replayer — the replay-side driver; suppresses real syscalls, injects recorded results, detects divergence.
  • Session — top-level debug orchestrator over a ReplayTimeline (breakpoints, watchpoints, cursor).
  • Tracee — the process under ptrace; state machine {Running, AtSyscallEntry, AtSyscallExit, Stopped, Checkpointed, Diverged}.
  • Divergence — observed replay state ≠ recorded state; a fatal, first-class signal (never tolerated).
  • Suppress + inject — replay never runs a real syscall; it writes the recorded effects + return value instead.
  • Two-stage convergence — count-to-near via the perf counter, then single-step the residual to an exact instruction.
  • Skid — PMU counter imprecision; the overflow fires near (not exactly at) the triggering instruction.
  • Skid margin — calibrated safety distance before a target tick at which the PMI is programmed.
  • PMI — Performance Monitoring Interrupt; fires when a perf counter overflows.
  • Serialization (scheduling) — running ≤ 1 tracee thread at a time so the interleaving is deterministic + recordable.
  • Sched event — a recorded context-switch point (from_tid → to_tid).
  • Anchor — the recorded coordinate at which an async signal (or nondet insn) was delivered.
  • Reverse-continue — run backward to the most recent breakpoint hit before now (via checkpoint + forward scan).
  • Reverse-step — move one instruction/source-line backward.
  • Reverse-watch — find the last time a memory range changed before now.
  • Watchpoint — a data breakpoint: forward via DR0–DR3, reverse via replay scan.
  • Breakpoint — int3 (software) or DRx (hardware) execution stop.
  • int3 — the 0xCC single-byte breakpoint instruction.
  • Debug registers (DR0–DR7) — x86 hardware breakpoint/watchpoint registers.
  • RFLAGS.TF — the Trap Flag enabling single-step.
  • seccomp-BPF — kernel syscall filter; SECCOMP_RET_TRACE traps selected syscalls cheaply.
  • process_vm_readv/writev — bulk tracee memory I/O syscalls.
  • vDSO — kernel-mapped fast-path syscall page (gettimeofday/clock_gettime) that bypasses ptrace unless patched.
  • COW fork — copy-on-write process duplication used for cheap memory snapshots.
  • soft-dirty PTE — kernel page-table bit tracking pages written since the last clear_refs, used for page-diff checkpoints.
  • RDTSC / RDRAND / CPUID — nondeterministic x86 instructions that must be trapped + recorded.
  • DAP — Debug Adapter Protocol; the editor-facing debug protocol; supportsStepBack enables reverse ops.
  • DWARF — debug-info format for line/variable/frame description.
  • CFI — Call Frame Information (DWARF) used for stack unwinding.
  • Hermetic replay — replay with no real I/O or host side effects.
  • Trace format version — MAJOR.MINOR contract governing trace readability across ttdb versions.
  • Divergence bisect — tooling to find the first diverging event between recorded and replayed runs.
  • Owner thread — the single supervisor thread permitted to issue ptrace ops on a given tracee.
