⬜ Phase 1 — ptrace supervisor

Objectives

Stand up ttdb-ptrace: spawn/attach a tracee, drive stop/continue, read+write registers and memory, decode waitpid status. Establish the Tracee state machine and the owner-thread ownership rule (principle 9). No recording yet — just deterministic control of one process.

Deliverable

A Tracee that spawns /bin/true, single-steps N instructions, prints RIP/regs at each stop, and exits cleanly. CLI ttdb step --count N -- <prog> demo.

Acceptance
  • Spawn + step + cont + exit on 10 static test binaries, 0 leaked zombies.
  • GETREGS/SETREGS round-trips RIP modification (set RIP, confirm next step from new address).
  • read_mem/write_mem round-trips a 4 KB buffer at a known mapped address.
  • Owner-thread assertion fires (in a test) when ptrace is called off-owner.
Fixtures
  • progs/nop_loop — fixed instruction count; expected step count exact.
  • progs/static_hello — static-linked, predictable entry RIP.
  • fixtures/regs_roundtrip.json — set/get register pairs.
  • malformed: attach to already-exited pid → expect ESRCH mapped to TtdbError::Ptrace.
Pitfalls
  • PTRACE_TRACEME race: child may run before parent attaches → use the exec-SIGTRAP stop as the sync point; do not CONT before it. Detect via missing initial stop.
  • Syscall-stop vs SIGTRAP ambiguity: without TRACESYSGOOD you cannot tell a syscall stop from a real SIGTRAP → always set the option; signal = SIGTRAP|0x80.
  • process_vm_readv partial reads: short read at a page boundary → loop + fall back to PEEK; treat 0-length as fault, not EOF.
  • Thread leakage: forgetting EXITKILL leaves tracees alive after ttdb crashes → set EXITKILL at attach.

⬜ Phase 2 — Syscall interception + recording

Objectives

Trap every syscall at entry and exit; capture nr, the 6 argument registers, the return value, and all bytes the kernel wrote into tracee memory (output buffers). Install a seccomp-BPF filter so cheap/ignorable syscalls do not pay the full trap cost. Produce in-memory TraceEvents (persisted in P4).

Deliverable

ttdb record --dry -- <prog> prints a live stream of intercepted syscalls with captured output bytes, e.g. read(3, <8 bytes captured>, 4096) = 8. seccomp filter measurably skips uninteresting syscalls.

Acceptance
  • Correct arg/return decode for ≥ 40 syscalls vs strace -e raw differential.
  • read/recvmsg/getdents MemWrite byte-ranges exactly match what the program later observes (verified by a test program echoing the buffer).
  • seccomp filter reduces trap count on a getpid-loop microbench by ≥ 5×.
Fixtures
  • conformance/syscall/read_exact.* — read N bytes, assert captured == file contents.
  • conformance/syscall/recvmsg_iovec.* — scatter buffers; assert all segments captured.
  • conformance/syscall/getdents.* — directory listing bytes captured.
  • malformed: syscall with a bogus out-pointer (EFAULT) → retval=-EFAULT, zero MemWrite, no crash.
Pitfalls
  • Out-length comes from the return value, not the arg (read count is a ceiling) → using the arg length captures uninitialized bytes → divergence later. Resolve length from retval per the table.
  • Pointer args that are also in-args (e.g. ioctl) → must know direction per request code; default to capturing on exit only for known-output requests.
  • seccomp no_new_privs requirement → forgetting it makes seccomp() fail with EACCES.
  • mmap of files captured as data is wasteful → record mmap as MmapRef (region + backing), replay re-creates the mapping rather than logging bytes (real file content is reproducible if the file is part of the recorded inputs; otherwise capture lazily on first read).
  • vDSO syscalls (gettimeofday/clock_gettime fast path) never trap → flagged here, mitigated Phase 14 (vDSO patch). Until then they are a known divergence source.

⬜ Phase 3 — Tick counting via perf_event_open + IP/regs coordinate

Objectives

Build ttdb-perf: open a per-thread retired-conditional-branch counter, read the current Tick, and define the canonical (Tick, IP, regs) coordinate. Implement two-stage convergence: count-to-near via PMI, then single-step the residual to land on an exact instruction. This is the temporal spine of the whole system (principle 3, 7).

Deliverable

ttdb ticks -- <prog> runs a program and prints total retired branches; ttdb seektick T -- <prog> (record-then) lands the tracee on the exact instruction at tick T, printing RIP + regs, and re-landing identically across repeated runs.

Acceptance
  • Two recordings of the same deterministic program produce identical total tick counts (I2).
  • seektick T lands on the same RIP across ≥ 100 repetitions (reproducibility).
  • Two-stage convergence reaches the exact (tick, rip) with single-step residual ≤ calibrated skid margin (typically ≤ a few hundred branches).
Fixtures
  • progs/branch_count — fixed number of conditional branches; expected tick known.
  • progs/recursive_fib — deterministic, tick-rich; cross-run tick equality asserted.
  • fixtures/skid_calibration.json — recorded overshoot samples per CPU model.
  • malformed: PMU unavailable (cloud VM) → graceful TtdbError::Perf with remediation message.
Pitfalls
  • Counter skid / overcount: PMIs are imprecise; the counter overshoots the instruction that triggered overflow → never trust the raw count for exact placement; always single-step the residual (principle 7).
  • Counting kernel branches: forgetting exclude_kernel makes counts include syscall-handler branches → nonreproducible → set exclude_kernel/hv.
  • inherit on clone: a child thread inheriting the counter pollutes the parent's count → inherit=0, open a fresh counter per thread (ties into P5).
  • Microarch variance: retired-branch semantics differ across CPUs → trace records the exact event config; replay refuses on a mismatching CPU (or recalibrates) → portability is §12.3.
  • rdpmc vs read(): rdpmc needs the mmap page + correct multiplexing; if the event is multiplexed (scaled), the read is approximate → pin the event (not multiplexed) so the count is exact.

⬜ Phase 4 — Trace log format + serialization

Objectives

Make the in-memory TraceEvent stream durable: define the on-disk Trace directory layout, an append-only CRC'd block format, the out-of-line blob store for large MmapData, a lazy tick→offset index, and torn-tail-tolerant reading (principles 5, 13; I3, I9).

Deliverable

A recording from P2/P3 now writes a real trace/ directory; tools/trace_dump re-reads and prints every event with ticks; tools/trace_stat reports size + per-kind histogram. Killing record mid-write yields a trace that trace_dump reads up to the last good block.

Acceptance
  • Write→read round-trip is byte-exact for ≥ 10k events incl. blobs.
  • seek_tick(t) returns the offset of the greatest event with tick ≤ t in O(log n).
  • A truncated trace (file cut mid-block) reads cleanly to the last valid block; trace_block_crc_fail telemetry emitted once.
  • Trace from format_version N reads on a build at version N+patch (forward-compat skip of an injected unknown kind).
Fixtures
  • conformance/trace_format/golden_v1.trace — frozen reference trace + expected dump.
  • conformance/trace_format/torn_tail.trace — deliberately truncated; expected last-good offset.
  • conformance/trace_format/unknown_kind.trace — synthetic future kind; expected skip.
  • fuzz/trace_parse.rs — random/garbage bytes must never panic; only TraceCorrupt.
Pitfalls
  • CRC over the wrong span (including the length field vs not) → silent mismatch → define CRC scope precisely (payload only) and test cross-build.
  • fsync cost on every event → batch fsync to checkpoint boundaries; document the durability window (events since last fsync may be lost on crash, but the prefix is always valid).
  • Blob orphaning: a referenced blob missing → TraceCorrupt; never delete blobs of a sealed trace.
  • Index drift: index built from a different log version → always derive index from the log; treat index.bin as a cache, rebuild on mismatch.
  • Endianness: fixed little-endian on-disk (x86-64); assert on read.

⬜ Phase 5 — Deterministic single-tracee scheduling + context-switch recording

Objectives

Handle multithreaded tracees by enforcing the single-runnable-thread invariant (I5): at any instant exactly one tracee thread runs; all others are stopped. Record context-switch points as Sched events so replay re-creates the identical interleaving (principle 4). This converts true concurrency into a deterministic, replayable sequence.

Deliverable

ttdb record correctly records a multithreaded test program (producer/consumer over a mutex); trace_dump shows interleaved Sched events; the recorded interleaving is fixed and reproducible.

Acceptance
  • A 4-thread program records with ≤ 1 runnable thread at all times (asserted via ptrace state probe in a test) (I5).
  • The recorded interleaving (sequence of Sched events) is identical across ≥ 20 recordings of a deterministic-after-serialization workload.
  • Thread create/exit events captured for all threads; no orphaned tracee threads on exit.
Fixtures
  • progs/mutex_pingpong — two threads alternating; expected Sched sequence golden.
  • progs/thread_spawn_storm — many short-lived threads; all create/exit events present.
  • conformance/signals/... reused later for signal+sched interaction.
  • malformed: a thread that never blocks (busy loop) → quantum PMI must force a switch (test the preemption path).
Pitfalls
  • Deadlock under serialization: if the only runnable thread blocks on a lock held by a stopped thread, naive scheduling deadlocks → the scheduler must detect "all runnable threads blocked" and run a blocked-on holder → requires modeling futex wait/wake (record futex syscalls and switch to the waker).
  • Quantum too large: a CPU-bound thread starves others (fine for determinism, bad for realism) but never breaks correctness; quantum too small = overhead. Tune via tick budget.
  • Per-thread counter inheritance: a cloned thread must get a fresh counter (inherit=0) or counts cross-contaminate (P3 pitfall recurs).
  • TID reuse: the kernel may reuse a TID after exit → key threads by (TID, generation) not TID alone.
  • vfork semantics: parent suspended until child execs/exits → model as a forced switch.

⬜ Phase 6 — Async signal capture anchored to ticks + nondeterministic-instruction trapping

Objectives

Close two remaining nondeterminism sources: (a) asynchronous signals — record the exact (Tick, IP, regs) anchor at which each signal was delivered so replay re-delivers at the identical instruction (I10); (b) nondeterministic instructions RDTSC/RDRAND/CPUID — trap and record their results so replay injects them (I11).

Deliverable

ttdb record captures a program that installs a SIGALRM handler and calls RDTSC; trace_dump shows Signal{SIGALRM,tick=...} and NondetInsn{Rdtsc,rax=...,rdx=...} events. The same RDTSC value is reproducible across replays (P7).

Acceptance
  • Async signal anchor (tick, rip) recorded for ≥ 5 signal types; the anchor is a complete coordinate (I10).
  • RDTSC and CPUID results recorded and, in P7, injected so a TSC-dependent branch takes the identical path across replays.
  • A program using RDRAND is detected (static scan) and either refused with a clear message or rewritten (if §6.6 enabled).
Fixtures
  • conformance/signals/sigalrm_anchor.* — handler increments a counter; anchor tick golden.
  • conformance/signals/sigsegv_fault.* — synchronous fault; faulting IP deterministic.
  • progs/rdtsc_branch — branches on TSC parity; replay path must match record path.
  • progs/cpuid_features — branches on CPUID leaf; injected leaf reproduces path.
  • malformed: signal delivered during a syscall (EINTR interaction) — anchor + EINTR both recorded.
Pitfalls
  • Signal one branch early/late: the anchor must be the delivery point (after the kernel would have delivered), captured precisely; mis-anchoring places the handler at the wrong instruction → divergence (the §8.17 example). PhaseDeferred("FINAL_BLUEPRINT §6.6") covers AVX-512/xsave extended-state capture and RDRAND binary rewrite as stretch items.
  • PR_SET_TSC granularity: traps all RDTSC (cost) but is the only portable user-space mechanism without a kernel module → accept the cost; RDTSC is rare in hot loops.
  • siginfo size/layout: siginfo_t is 128 B with union fields → capture the raw bytes, do not interpret structurally (forward-compat).
  • Signal queueing: real-time signals queue; standard signals coalesce → record each delivery the kernel actually performs, in order.
  • Re-entrancy: a signal during signal-handler execution → nested anchors; record the nesting via stack of anchors.
  • SIGKILL/SIGSTOP cannot be caught → SIGKILL ends recording (valid prefix); SIGSTOP handled as a group-stop, not a delivered signal.

⬜ Phase 7 — Replay engine

Objectives

The first end-to-end record→replay. Re-spawn the recorded binary and drive a replay loop that suppresses real syscalls and injects recorded results + memory effects, re-delivers signals at their tick anchors, replays nondeterministic-instruction results, and continuously detects divergence (principles 2, 6; I1, I6, I7). Determinism ⇒ identical regs/memory at every tick.

Deliverable

ttdb replay trace/ re-executes a recorded program to completion with no real I/O, producing identical final state; the §8.13 worked example (time() branch) replays the recorded branch. A deliberately corrupted trace (flipped retval) triggers an immediate, precise diverged report.

Acceptance
  • ≥ 30 deterministic test programs replay to completion with zero divergence and final regs matching the recorded final state (I1).
  • No real syscall executes during replay (verified: a write to stdout produces no output on replay; the recorded bytes are injected into the read-side instead) (I7).
  • Injecting a 1-bit change into any recorded retval causes a diverged report naming the exact tick + register (I6) within one sync interval.
  • Signal re-delivery lands at the recorded anchor.rip for all P6 signal fixtures (I10).
Fixtures
  • conformance/syscall/* replayed: each fixture's record then replay must match.
  • conformance/signals/* replayed: anchors hit exactly.
  • conformance/reverse/replay_determinism.* — record once, replay 100×, assert identical tick+reg stream.
  • malformed: corrupt_retval.trace, dropped_signal.trace, extra_event.trace → each yields a specific divergence/anchor error, never a silent wrong run.
Pitfalls
  • Forgetting to suppress a syscall → the tracee performs real I/O on replay → nondeterminism re-enters + side effects on the host → assert no PTRACE_SYSCALL into kernel during replay (I7 detection).
  • mmap address mismatch: replay mmap returns a different address than recorded → all subsequent pointers diverge → must MAP_FIXED at the recorded address or record and re-create the exact layout (I8).
  • Memory-effect modeling gaps: a syscall wrote to a buffer the interception table missed → replay leaves stale bytes → divergence when the program reads them → fix the table (P2), differential-test.
  • Signal frame construction: kernel builds a specific stack frame on delivery; if we deliver via PTRACE_CONT(sig) the kernel builds it for us → prefer that over hand-rolling the frame.
  • rip advance length: syscall is 2 bytes; advancing by the wrong length corrupts the next instruction → use a fixed +2 for syscall, decode for others.

⬜ Phase 8 — Checkpoint / snapshot engine + ReplayTimeline

Objectives

Make seeking fast and enable reverse execution. Periodically snapshot the replaying tracee (COW fork for live, page-diff for persisted) into Checkpoint{tick,regs,mem,fds}; index checkpoints by tick in ReplayTimeline; implement seek(T) = restore nearest checkpoint ≤ T then replay forward to T (principle 8; I4).

Deliverable

ttdb replay trace/ then seek <tick> lands at the exact tick state (regs + memory readable) in time bounded by the checkpoint interval, not by the distance from start. trace_stat reports checkpoint count + memory.

Acceptance
  • seek(T) to an arbitrary T completes in ≤ checkpoint-interval replay time (§4), independent of T's absolute value.
  • Restored state at T equals replay-from-start state at T for ≥ 50 random T (I4) — verified by comparing full register files and sampled memory.
  • Checkpoint memory stays within the configured ceiling under a long replay (eviction works).
  • COW-fork restore is reusable (seek to T, then seek to T' > T, then back to T) without re-replaying from start.
Fixtures
  • conformance/reverse/seek_random.* — record, seek to 50 random ticks, assert state matches a from-start replay.
  • conformance/reverse/checkpoint_verify.* — restore + 1-step verify for each checkpoint.
  • fixtures/checkpoint_interval.json — interval-vs-seek-latency measurements.
  • malformed: corrupt PageDiff → checkpoint_verify_fail, fall back to an earlier checkpoint.
Pitfalls
  • COW fork cost: forking a large-RSS tracee copies page tables (not pages) but is still O(mapped pages) → expensive for huge address spaces → tune interval; prefer page-diff for very large processes.
  • Soft-dirty reset races: clear_refs must bracket exactly one interval; a missed reset over-captures or under-captures pages → bracket precisely around checkpoint_now.
  • fd/state in a checkpoint: a checkpoint must also snapshot the logical fd table + signal mask (FdSnapshot) so a restored replay re-injects consistently → snapshot regs + mem + fds together.
  • Checkpoint of a diverged state: never checkpoint after divergence → checkpoint only verified-consistent positions.
  • Fork bomb of checkpoints: too many live COW forks exhaust pids/memory → cap live forks, spill older ones to PageDiff.

⬜ Phase 9 — Forward debugging

Objectives

Turn the replay+timeline into a usable forward debugger: software (int3) and hardware breakpoints, single-step, run-to-breakpoint, stack unwinding, and DWARF-backed line/variable inspection — all over the deterministic replay (not a live process).

Deliverable

ttdb replay trace/ REPL: set a breakpoint by function/line, continue to it, bt shows a correct call stack, print x shows a local variable's value — all reproducible because it runs over the recorded trace.

Acceptance
  • Breakpoint at a function entry is hit at the correct tick across ≥ 20 programs (sw + hw).
  • bt reconstructs ≥ 5 frames correctly for a recursive program (validated against gdb on the live program).
  • print reads correct values for int/pointer/struct locals at a breakpoint.
  • Breakpoint hits do not perturb the tick stream (breakpoint int3 is transparent to replay determinism — the 0xCC is removed before any tick-affecting execution).
Fixtures
  • conformance/reverse/breakpoint_hit.* — break at known address; expected hit tick.
  • progs/recursive_fib — backtrace depth golden.
  • progs/struct_locals — variable values at a line golden.
  • malformed: breakpoint at an unmapped address → clear error, not a crash; breakpoint in the middle of an instruction → reject.
Pitfalls
  • int3 perturbs ticks if left in place: the 0xCC must be removed and the original instruction executed for the program's branch behavior to match record → step-over-then-rearm; never let the trap byte alter control flow that affects ticks.
  • Breakpoint vs our nondet-insn traps / signal anchors: multiple SIGTRAP sources → a single dispatcher keyed by RIP + source table.
  • DWARF location expressions can reference CFA, registers, or memory → a partial DW_OP evaluator is needed; unsupported ops → "optimized out / unavailable", never a wrong value.
  • PIE/ASLR base: DWARF addresses are link-time; add the recorded load bias (I8) to get runtime addresses.
  • Inlined functions / optimized code: line tables can be non-monotonic → present best-effort, flag <optimized>.

⬜ Phase 10 — Reverse execution

Objectives

The headline feature. Implement reverse-continue (run backward to the most recent breakpoint hit before "now") and reverse-step (one source line / instruction backward), built on checkpoints + forward replay search (principle 8). The user perceives backward execution; the engine never actually runs the CPU backward.

Deliverable

ttdb replay trace/ REPL: after running forward and hitting a fault, reverse-continue stops at the previous time the breakpoint condition held; reverse-step walks backward line by line. Demonstrated in examples/crash_repro (reverse from a SIGSEGV to the corrupting write).

Acceptance
  • reverse-continue from tick T to a breakpoint stops at the greatest hit tick < T (verified against a recorded list of all hits) for ≥ 20 programs.
  • reverse-step lands exactly one source line / instruction earlier, with correct regs (matches a from-start replay to that tick).
  • Latency bounded by the checkpoint interval for hits within one interval (§4); expands predictably for further hits.
  • Alternating forward/reverse navigation converges to consistent state at each stop (no drift; I4).
Fixtures
  • conformance/reverse/reverse_continue_lasthit.* — golden last-hit tick before a given now.
  • conformance/reverse/reverse_step_line.* — golden previous-line tick.
  • examples/crash_repro/ — record a UAF, reverse-continue to the free, then to the alloc.
  • malformed: reverse past tick 0 → stop at start with a clear "beginning of recording" message, not an error.
Pitfalls
  • Off-by-one at the boundary: reverse-continue must stop strictly before now (tick < now), else it returns the current position → define the comparison precisely and test the boundary.
  • Re-arming breakpoints in the restored process: after restoring a checkpoint the int3 bytes are gone (the checkpoint captured pre-breakpoint memory) → re-arm all breakpoints after every restore (P9 interaction).
  • Hit list cost: recording all hits in a window then picking the last is simpler and more robust than trying to stop at the right one during a single backward-feeling pass → prefer the scan-and-pick approach.
  • Conditional breakpoints in reverse: the condition must be evaluated at each candidate hit during the forward scan.
  • Window too small repeatedly: expanding one checkpoint at a time can be slow if hits are far back → exponentially expand the window for deep reverse-continue.

⬜ Phase 11 — Watchpoints (forward via hardware debug registers, reverse via replay scan)

Objectives

Data watchpoints: forward watchpoints via hardware debug registers DR0–DR3 (write/read-write/exec, 1/2/4/8-byte), and reverse watchpoints ("when did this memory last change before now?") via a replay scan over a window (principle 8). Answers the classic "who wrote this?" question both directions.

Deliverable

watch globalCounter then continue stops when it changes (forward); reverse-watch globalCounter from a corrupted-value point jumps to the exact write that set the bad value (examples/crash_repro extended: find the corrupting store).

Acceptance
  • Forward hardware watchpoint fires at the exact tick of a write for ≥ 4 simultaneous watches (DR0–DR3).
  • Reverse-watch returns the greatest tick < now at which the watched range changed, validated against a recorded change list.
  • 1/2/4/8-byte watch lengths all detect correctly (alignment handled).
  • Reverse-watch latency bounded by the checkpoint interval for changes within one interval.
Fixtures
  • conformance/reverse/watch_write_tick.* — golden write tick (forward).
  • conformance/reverse/reverse_watch_lastchange.* — golden last-change tick before now.
  • progs/global_counter — single global mutated at known points.
  • malformed: unaligned 8-byte watch → either reject or split; watch on > 4 ranges → fall back to ReplayScan.
Pitfalls
  • DR slot exhaustion: only 4 hardware watchpoints → the 5th must use page-protection or replay-scan fallback → ReplayScan covers it (slower).
  • Watchpoint length/alignment: x86 hardware watch requires power-of-two length + alignment → split or reject misaligned ranges, do not silently watch the wrong bytes.
  • Reverse-watch over large ranges: a hardware watch covers ≤ 8 bytes; a struct/array reverse-watch needs ReplayScan or multiple slots → choose by size.
  • Stale debug registers across restore: like breakpoints, DRx must be re-programmed after a checkpoint restore (P8/P10 interaction).
  • Watch hit vs single-step trap: DR6 status bits disambiguate which DRx vs a TF single-step → read DR6 on every SIGTRAP.

⬜ Phase 12 — State reconstruction and query at arbitrary tick

Objectives

Expose "show me the full program state at tick T" as a first-class query: registers, memory contents, call stack, source line, and resolved local/global variables at any T, by seeking (P8) and reading. Lay groundwork for an omniscient/queryable view (Pernosco-style north star) without re-recording (principle 15). Includes the deferred-scope notes for §12.3/§12.4/§12.5.

Deliverable

ttdb replay trace/ REPL: state @ <tick> prints regs + backtrace + source line; history <var> prints every value the variable held with the tick of each change; mem @ <tick> <addr> <len> dumps memory at that point.

Acceptance
  • state_at(t) for ≥ 50 random t returns regs/memory identical to a from-start replay to t (I1/I4).
  • history <var> lists exactly the ticks at which the variable changed (validated against an instrumented reference).
  • Repeated queries to nearby ticks reuse cached/checkpointed state (latency drops on the second query in a region).
  • Deferred-scope items are documented with their §refs and detected (not silently wrong) when encountered (e.g. a multicore race surfaces as divergence, §12.4).
Fixtures
  • conformance/reverse/state_at_random.* — golden full-state at random ticks.
  • conformance/reverse/var_history.* — golden change list for a variable.
  • progs/data_race (in examples/) — documents the §12.4 limitation (recorded interleaving is one of many; true race not reproduced sub-quantum).
  • malformed: query at a tick beyond trace end → clamp + message; query for an out-of-scope variable → "not in scope at this tick".
Pitfalls
  • Variable scope vs tick: a local is only live in part of its function → resolving it outside its PC range gives garbage → gate variable resolution on the DWARF lexical-block PC range at tick t.
  • Optimized-away values: report <optimized out>, never a stale register guess.
  • Query thrash: random-access queries far apart each pay a full seek → encourage locality; the deep index amortizes.
  • Memory aliasing across seeks: ensure each seek fully restores (P8 verify) before reading, else stale pages leak into the answer.
  • Deferred-scope confusion: users may expect multicore reproduction → the §12.4 limitation must be surfaced in docs + at record time (warn if true multithread parallelism was serialized).

⬜ Phase 13 — DAP server with reverse-execution extensions

Objectives

Expose ttdb to editors via the Debug Adapter Protocol so users debug visually, including reverse operations. Implement the standard request/response/event flow plus supportsStepBack and a custom seekTick, mapping DAP's forward-oriented model onto the timeline (the Target trait, §11).

Deliverable

A VS Code (or any DAP client) session attaches to ttdb dap trace/, sets breakpoints, steps forward and backward (Step Back button), inspects variables, and scrubs the timeline via seekTick. Recorded program output appears in the debug console.

Acceptance
  • A DAP client completes initialize → setBreakpoints → configurationDone → stopped → stackTrace → variables → continue without protocol errors (validated against the DAP test harness / a reference client).
  • stepBack and reverseContinue produce correct stops matching the REPL reverse ops (P10) at the same ticks.
  • setDataBreakpoints arms a watchpoint that fires (P11) and reports via a stopped(reason:data breakpoint) event.
  • ttdb/seekTick repositions the session and refreshes stack/variables consistently.
Fixtures
  • conformance/... DAP request/response golden transcripts (dap_initialize.json, dap_stepback.json).
  • fuzz/dap_protocol.rs — malformed DAP messages must never panic; respond with an error response.
  • progs/struct_locals driven via DAP variables — golden variable tree.
  • malformed: a request before initialize → DAP error response, not a crash; oversized Content-Length → bounded, rejected.
Pitfalls
  • DAP assumes forward-only: there is no native "current time" → expose tick via custom body fields + ttdb/seekTick; frontends without reverse support still work forward-only.
  • variablesReference lifetime: references are valid only for the current stop → invalidate them on any navigation (forward, reverse, seek) to avoid reading stale state.
  • Threads in DAP vs serialized scheduling: present recorded threads; "running" is the Sched-current thread at the cursor → map carefully so the UI thread list matches the timeline.
  • Output ordering: relayed program output must be ordered by tick, not by when the DAP server reads it.
  • Blocking the protocol loop: a long seek/reverse-continue must not stall the DAP loop → run navigation on the owner thread, send progress events; keep protocol I/O responsive.

⬜ Phase 14 — Recording persistence / portability + overhead tuning

Objectives

Make traces portable and recording efficient: package a trace as a self-contained, movable artifact (incl. the binary + needed mmap-backing files + metadata); add the syscall-buffer optimization (rr-style) to cut recording overhead; mitigate vDSO bypass; and tune toward the §4 overhead targets. Final hardening pass.

Deliverable

ttdb pack/unpack move a recording between machines and it replays; a vDSO-heavy program (frequent clock_gettime) now records + replays deterministically; recording overhead on the benchmark suite meets the §4 envelope.

Acceptance
  • A packed trace replays on a second compatible host with zero divergence; on an incompatible CPU it refuses with a clear message (not a silent wrong replay).
  • vDSO-fast-path syscalls are captured (a clock_gettime loop replays deterministically; previously diverged).
  • Recording overhead ≤ 2× on CPU-bound benchmarks and ≤ 5× on syscall-heavy benchmarks after the syscall buffer (§4).
  • Replay overhead ≤ 1.8× (§4).
Fixtures
  • conformance/trace_format/packed_roundtrip.ttz — pack→move→unpack→replay golden.
  • progs/vdso_clock — clock_gettime loop; deterministic replay after the vDSO patch.
  • benchmarks/overhead/* — record/replay overhead-ratio gates wired into bench.yml.
  • malformed: packed trace with a missing referenced library → clear "missing backing object" error; incompatible-CPU trace → refusal.
Pitfalls
  • Syscall buffer breaks determinism if mis-scoped: only deterministic, side-effect-contained syscalls may be buffered; anything that can be interrupted/signal-affected must still trap → conservative buffering list.
  • vDSO patch fragility: vDSO layout varies by kernel → detect the symbols dynamically (parse the vDSO ELF) before patching; fall back to "warn + treat as nondet" if unknown.
  • Packaging file-backed mmaps: a memory-mapped file that changes between record and replay → content-address + bundle it; refuse if a referenced file is absent and not bundled.
  • Microarch portability illusion: a trace may appear to replay on a different CPU then diverge deep in → gate strictly on the recorded event config; recalibration is a deferred research item (§12.3).
  • Overhead regressions: a refactor silently doubles ptrace round-trips → the bench.yml gate must fail the build on overhead regression.
