Project Number: 160

Project Name: Email Server (SMTP + IMAP)

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a production-grade email server in Rust implementing SMTP as a receiving MTA and authenticated submission agent (RFC 5321, RFC 6409 port 587), an SMTP outbound relay with durable queueing and retry/backoff, and an IMAP4rev2 access server (RFC 9051) with push (IDLE), incremental sync (CONDSTORE/QRESYNC RFC 7162), backed by a Maildir-format message store with a SQLite metadata index, SASL authentication (RFC 4422), and an anti-abuse pipeline (SPF RFC 7208, DKIM RFC 6376, DMARC RFC 7489, Sieve RFC 5228, greylisting, rate limiting) — engineered so no single malformed message, misbehaving client, or crash mid-write can corrupt another user's mailbox or turn the server into an open relay.

Phase-0 deliverable — numbered list of crates (see §10 for full tree):

  1. em-core — envelope/message/mailbox/user types shared by every crate.
  2. em-msgparse — RFC 5322 + MIME (RFC 2045-2049) message parser.
  3. em-smtp-server — SMTP receiver state machine (EHLO/MAIL/RCPT/DATA, pipelining).
  4. em-verifier — deterministic protocol-invariant simulator (one assertion per I#, §7).

System boundaries:

  • Provides: SMTP receive (25) + submission (587) + LMTP local delivery; SMTP outbound relay with DNS MX lookup, STARTTLS, DKIM signing; IMAP4rev2 access (SELECT/FETCH/SEARCH/STORE/IDLE/CONDSTORE/QRESYNC); Maildir storage; SASL (PLAIN/LOGIN/CRAM-MD5/SCRAM-SHA-256/OAUTHBEARER); SPF/DKIM/DMARC verify + DKIM sign; Sieve filtering; DSN bounce generation; greylisting + per-IP/per-user rate limiting.
  • Delegates: DNS resolution to the operator's recursive/authoritative resolver (this project does not implement a DNS server — MX/SPF/DKIM/DMARC records are read via standard TXT/MX lookups; see Authoritative-DNS project #162; this is a permanent architectural boundary, P13, not a deferred feature); TLS certificate issuance (ACME/Let's Encrypt) is operator-provided, not built; anti-virus scanning delegates to an external clamd daemon via a milter-style hook, PhaseDeferred("§38") (in-process AV is the deferred alternative).
  • Does NOT provide: POP3 (RFC 1939 — smaller surface than IMAP, deferred, PhaseDeferred("§38")), mailing-list management (Mailman-class), webmail UI, CalDAV/CardDAV, JMAP (RFC 8620/8621), ARC (RFC 8617) forwarder re-signing.

Non-goals: real-time chat transport, X.400 gatewaying, UUCP.

Deployment model: one binary per role (smtpd, imapd, outboundd) sharing the Maildir volume and SQLite index over NFS-unsafe-avoiding local disk (each role pinned to the host that owns the volume in Phase 0; sharded multi-host mailbox placement is PhaseDeferred("§38")); systemd units; containers with named volumes.

Target users/operators: SRE / mail-infra teams operating a multi-tenant mail platform for 10³–10⁶ mailboxes; the calibration domain is "email infrastructure engineer," the same competency Postfix, Exim, Dovecot, and Cyrus maintainers hold.

Later phases unlock (see §12+): authenticated submission and SASL (Phase 3), mailbox access (Phase 5), push/incremental sync (Phase 6), outbound relay economics (Phase 7), cryptographic trust (Phase 8-9), server-side automation (Phase 10), failure notification (Phase 11), abuse resistance (Phase 12).

Recommended language: Rust 1.78+ MSRV. Rationale: memory safety eliminates the dominant CVE class in C-based mail servers — stack/heap overflows in header and MIME parsers (CVE-2020-12100 Dovecot stack overflow from deeply nested MIME; CVE-2017-7504 Sendmail header-parsing memory corruption; the 1988 Morris Worm's sendmail debug-command buffer overflow); tokio's async runtime fits the many-thousand-concurrent-connection SMTP/IMAP workload (IDLE sessions sit open for hours); rustls removes the OpenSSL CVE surface entirely (Heartbleed, CVE-2014-0160, would not exist in this stack). Rejected languages: C — the historic failure mode itself (see above CVEs); Go — GC pauses degrade p99 latency under heavy IMAP IDLE fan-out and weaker control over zero-copy wire buffers costs throughput at the SMTP DATA hot path; Java — JVM footprint and GC pause tail latency are a poor fit for constrained mail-relay VMs and for the many-thousand-idle-connection memory budget (§4).

Prerequisites: SMTP/IMAP protocol state machines, RFC 5322/MIME parsing, async I/O, cryptographic message signing (DKIM), DNS record semantics (MX/TXT/SPF/DMARC), TLS handshake mechanics, SASL challenge-response.

Estimated timeline: Phase 0 in 2 weeks; full system (Phases 0–12) in 11 months.

Every deferred feature is flagged PhaseDeferred("§38") inline and registered in the Deferred Features Register, §38: POP3, ARC forwarder re-signing, JMAP, mdbox/sdbox storage, LDAP auth backend, CalDAV/CardDAV, mailing-list manager, MTA-STS/TLS-RPT, sharded multi-host mailbox placement, external clamd AV integration.

2. Why Build This

Unique systems knowledge: this is the only project in the portfolio that forces simultaneous mastery of two independently-evolved, fifty-year-accreted protocol families (SMTP's message-transfer state machine and IMAP's stateful mailbox-access state machine) sharing one storage substrate under crash-safety and multi-writer concurrency constraints. RFC 5321 (SMTP) is ~60 pages, RFC 5322 (message format) ~40, RFC 3501/9051 (IMAP4rev1/rev2) ~110, RFC 6376 (DKIM) ~60, RFC 7208 (SPF) ~50, RFC 7489 (DMARC) ~40 — and each of thirty adjacent RFCs adds another 20-100. No other project in this portfolio has this much load-bearing, already-standardized surface area to get exactly right, because interoperability is graded by every mail client and MTA on the public Internet, not by an internal test suite.

Why it matters architecturally/historically: email predates almost every other distributed system in this portfolio and its production shape — Postfix's master+ daemon-per-role split, Exim's router+transport pipeline, Dovecot's pluggable storage backends, Cyrus's single-process-per-mailbox atomicity model, OpenSMTPD's privilege-separated processes — is a direct historical response to the 1988 Morris Worm (a single sendmail process, running as root, with a debug command reachable pre-auth). Every later distributed system that separates "parse untrusted input" from "hold privilege" (seccomp sandboxes, gVisor, microservice ingress) is re-deriving a lesson email learned in 1988.

Engineering muscles built: protocol state-machine design under adversarial input (§8); crash-safe file-system storage without a database (Maildir atomic rename, §8, §16); cryptographic verification pipelines with layered, sometimes-conflicting trust signals (SPF passes via a forwarder, DKIM fails after re-signing, DMARC says quarantine — Phase 9); durable work queues with exponential backoff and poison- message isolation (Phase 7); a DSL runtime embedded in a trust boundary (Sieve, Phase 10) with loop-detection as a first-class correctness property.

Cross-links to sibling systems: VPN-WireGuard (#156) shares the "many long-lived encrypted sessions, minimal per-session memory" scaling shape as IMAP IDLE; BGP-Router (#157) shares the "durable routing/retry table with backoff" shape as the outbound queue; gRPC-Framework (#155) is the admin-API analogue of this project's operator CLI; Authoritative-DNS (#162) is the upstream dependency for MX/SPF/DKIM/DMARC record resolution (§1).

Calibration value: an engineer who has built this system can debug production email delivery incidents (bounces, DKIM failures, IMAP sync bugs, blacklisting) with the same first-principles confidence a Postfix or Dovecot core maintainer holds, because they built the state machine, not just configured it.

What Mastery Looks Like (after finishing, the reader can):

  • Trace any SMTP transcript byte-for-byte through the receiver state machine and name which state, which invariant (§7), and which RFC section governs the next legal transition — built in Phase 2.
  • Explain why Maildir's tmp/ → new/ rename is the entire crash-safety argument and reproduce the argument for any other atomic-rename storage design — built in Phase 4.
  • Diagnose an IMAP client stuck in full-resync mode from a UIDVALIDITY bump and explain the CONDSTORE/QRESYNC delta protocol that avoids it — built in Phase 6.
  • Compute, from first principles, why a queue's exponential-backoff ceiling is set where it is and what breaks if it is set differently — built in Phase 7.
  • Explain why a DKIM signature can validly fail after a legitimate forward and what ARC does about it (and why this blueprint defers ARC) — built in Phase 8.
  • Distinguish SPF/DKIM/DMARC's three independent, sometimes-contradictory trust signals and resolve them into one delivery decision — built in Phase 9.
  • Design a sandboxed DSL runtime (Sieve) with loop detection as a structural invariant, not a bolted-on check — built in Phase 10.
  • Defend, with a threat model and quantified rate limits, why this design cannot become an open relay or a backscatter source — built in Phase 12.

smtp_recv: the untrusted-input trust boundary — every byte from an unauthenticated remote MTA is parsed here before anything else touches it; owns the EHLO/MAIL/RCPT/DATA state machine (§8, P1, I1). smtp_submit: identical wire protocol, but SASL-authenticated (port 587, RFC 6409) — the trust boundary moves from "any TCP peer" to "any authenticated user," so relay policy differs (ADR-14). anti_abuse pipeline: a milter-style ordered chain — SPF, then DKIM, then DMARC alignment, then greylist/rate-limit — each stage can defer (4xx), reject (5xx), or annotate and continue; order is fixed because DMARC alignment needs both SPF and DKIM results (§8, I11). local_delivery: LMTP-like; runs Sieve (Phase 10) before the message ever touches Maildir, checks quota (P10), and is the only writer path into a user's Maildir for inbound mail. mailbox_store: the persistence boundary — Maildir owns durability via atomic rename (P2, I3); SQLite owns the queryable index (UIDs, MODSEQ) that Maildir's filesystem layout cannot answer efficiently (§8). imap_server: the read/write access boundary for MUAs; sessions subscribe to per-mailbox change notification for IDLE (I9); POP3 access is out of scope for Phase 0-12 (PhaseDeferred("§38")). outbound_queue: the persistence + concurrency boundary for anything not locally deliverable — four durable directories (active/deferred/hold/bounce) mirror Postfix's queue model (ADR-10); a crash must never lose a queued message (I4). smtp_outbound: the client-side SMTP state machine — resolves MX (delegated to the operator's resolver, §1), opportunistically STARTTLS, signs DKIM on egress (Phase 8) before sending. bounce_processor: generates RFC 3464 DSNs on permanent (5xx) failure or retry-budget exhaustion; verifies SPF before bouncing to avoid backscatter (T7, FM-7).

6. Design Principles

  1. P1 — SMTP is push, IMAP is pull; they share storage, never state. Rule: no in-process shared mutable session state crosses the SMTP/IMAP boundary — only the Maildir + SQLite index (§3) is shared. Tradeoff: an extra persistence round-trip for cross-protocol notification (IDLE wake-up, I9). Operational implication: either subsystem restarts independently. Violated: a shared-memory shortcut couples restart/crash domains and reintroduces the coupling Postfix/Dovecot's split avoids (§2).
  2. P2 — Illegal protocol states are unrepresentable in the type system. Rule: SmtpState/ImapState enums encode exactly the legal transitions (§8, §11); no boolean flags simulate a state machine. Tradeoff: more enum variants to plumb through match arms. Operational implication: a compiler error, not a runtime bug, when a phase is unhandled. Violated: boolean-flag state (as in historical sendmail) admits combinations the protocol forbids — the exact CVE-2019-19515 class of bug.
  3. P3 — The untrusted-input parser never holds privilege. Rule: em-msgparse and the SMTP command parser run before authentication and before any privileged file write (§3 trust boundary). Tradeoff: two-phase parse (syntax, then semantic) costs one extra pass. Operational implication: a parser crash cannot escalate. Violated: parsing with privilege already granted is the 1988 Morris Worm's exact shape (§2).
  4. P4 — Maildir writes are atomic via tmp/ → new/ rename; nothing else is durable. Rule: every delivery path writes to tmp/, fsyncs, then rename(2)s (§8, I3). Tradeoff: one extra fsync per message vs. an in-place write. Operational implication: crash recovery is "GC orphaned tmp/ files," not "replay a WAL." Violated: in-place mailbox mutation (mbox-style) corrupts under a concurrent writer or a mid-write crash.
  5. P5 — SASL mechanism negotiation is pluggable, not hardcoded. Rule: em-sasl exposes one SaslMechanism trait; PLAIN/LOGIN/CRAM-MD5/ SCRAM-SHA-256/OAUTHBEARER are implementations, not special-cased branches (§11, ADR-06/07). Tradeoff: one more trait-object indirection per auth attempt. Operational implication: adding GSSAPI later is additive, not a rewrite. Violated: hardcoded mechanism dispatch blocks OAuth-only providers (Gmail/Microsoft) without a rewrite.
  6. P6 — SPF, DKIM, and DMARC are evaluated in a fixed order because DMARC depends on both. Rule: SPF → DKIM → DMARC-alignment, never reordered (§8, I11). Tradeoff: DMARC's per-message cost includes both upstream checks even when one alone would suffice for a coarse decision. Operational implication: alignment failures are always attributable to a specific upstream check in logs. Violated: evaluating DMARC before its inputs exist yields a meaningless verdict.
  7. P7 — The outbound queue never drops a message; it defers, bounces, or holds. Rule: every outbound message is in exactly one of active/deferred/hold/bounce at all times (§8, I4); exponential backoff caps at 5 days (§4) before a bounce is generated. Tradeoff: disk usage for long-deferred mail. Operational implication: mailq-equivalent introspection always accounts for 100% of accepted mail. Violated: dropping on transient failure silently loses mail — the "black hole" failure mode §2 explicitly rejects.
  8. P8 — DKIM signs on egress with Ed25519 by default, RSA-2048 for compatibility. Rule: signing key type is per-domain configurable but Ed25519 is the shipped default (ADR-08, RFC 8463). Tradeoff: some older receivers lack Ed25519 verification support (rare in 2026). Operational implication: signing latency is ~500 µs vs. RSA's ~5 ms (§4, M5). Violated: RSA-only signing costs 10× CPU at volume (§31).
  9. P9 — Sieve execution is sandboxed with a hard iteration/redirect cap. Rule: the Sieve VM (§8, Phase 10) enforces a Received:-header count cap (50) and a bytecode step budget per message. Tradeoff: pathological but legitimate scripts (long forwarding chains) may hit the cap. Operational implication: a runaway script cannot become a mail-loop DoS (T8). Violated: unbounded redirect execution is a documented incident class (T8, FM-9).
  10. P10 — Per-user quota is enforced at the write path, not the read path. Rule: local_delivery and IMAP COPY/APPEND check quota before the Maildir write commits (§11, I6). Tradeoff: an extra index lookup per write. Operational implication: quota cannot be bypassed via IMAP-side copy operations (a documented pitfall, §22 Phase 12 N.6). Violated: read-path-only enforcement lets COPY multiply messages past quota.
  11. P11 — TLS is opportunistic on 25, mandatory on 587/993. Rule: STARTTLS is advertised but not required for relay-to-relay SMTP (interop with the installed base); submission (587) and IMAP-over-TLS (993) require it (§4, ADR-03, RFC 8314). Tradeoff: unauthenticated relay SMTP can still be plaintext if the peer refuses STARTTLS. Operational implication: TLS posture is auditable per-port. Violated: mandatory TLS on 25 breaks interop with legacy MTAs still on the public Internet.
  12. P12 — Every conformance fixture is a named, versioned file, never an inline ad hoc string. Rule: N.5 fixtures live under conformance/ fixtures/ with a stable name (§10). Tradeoff: more repository surface area. Operational implication: a regression always has a reproducible, diffable fixture (§29 Testing & Verification Strategy). Violated: inline test strings can't be shared across differential runs against Postfix/Dovecot (§5 Reference Implementations).
  13. P13 — The DNS resolver is a pluggable dependency, never embedded. Rule: em-dns wraps the operator's resolver via a trait (§11); this project never runs its own authoritative or recursive resolver (§1). Tradeoff: an extra network hop per MX/TXT lookup vs. an embedded zone cache. Operational implication: DNS outages are a separately operable failure domain (FM-6). Violated: embedding DNS duplicates Authoritative-DNS (#162) and couples two independently-scaled systems.

I1 An SmtpSession only accepts commands legal in its current SmtpState (§8, §11). I10 SPF, DKIM, then DMARC-alignment are evaluated in that fixed order for every inbound message (P6). I13 This server relays outbound mail only for authenticated, permitted senders/recipients (never anonymous-to-anonymous). I14 The SQLite mailbox index and the Maildir filesystem tree agree on message existence after any successful operation (no orphan on either side). Divergence between index and filesystem is silent data loss or a phantom message. em-mailbox-idx write-through commit ordering periodic reconciliation sweep (em-cli mailbox fsck) index_maildir_divergence_total fsck rebuilds index from Maildir (source of truth)

Debugging methodology: em-verifier is a deterministic simulator that drives every state machine (SmtpState, IMAP session state, queue state, Sieve VM) through generated and replayed transcripts, asserting each I# after every step; a violation aborts the run with the failing transcript prefix attached, making every invariant breach reproducible offline (§29 Testing & Verification Strategy).

8. Domain Model / Protocol / Data Model

8.1 SMTP command grammar (section 4.1 of RFC 5321, EBNF excerpt)

command     = ehlo / helo / mail / rcpt / data / rset / vrfy / noop / quit
            / starttls / auth ;
ehlo        = "EHLO" SP domain CRLF ;
mail        = "MAIL FROM:" reverse-path [SP mail-params] CRLF ;
rcpt        = "RCPT TO:" forward-path [SP rcpt-params] CRLF ;
mail-params = esmtp-param *(SP esmtp-param) ;
esmtp-param = esmtp-keyword ["=" esmtp-value] ;   (* SIZE, BODY=8BITMIME, AUTH *)
data        = "DATA" CRLF ;
reverse-path= "<" [mailbox] ">" ;
forward-path= "<" mailbox ">" ;
mailbox     = local-part "@" domain ;

8.2 SMTP session state machine

From Event To Guard
Connected EHLO/HELO valid Greeted domain syntactically valid
Greeted STARTTLS (if advertised) TlsNegotiating → Greeted (TLS) not already TLS

S: 250-PIPELINING

S: 250-STARTTLS

S: 250 OK

S: 354 End data with <CR><LF>.<CR><LF>

Malformed-input example: RCPT TO:<bob@example.com (missing closing >) → parser rejects at grammar level (§8.1), server replies 501 5.5.4 syntax error in parameters, session remains in MailFrom (I1) — no partial RCPT is accumulated.

Failure-path example: client disconnects mid-InData after 40% of body bytes → em-smtp-server discards the partial buffer (never reaches I2's durable-write gate), no tmp/ file is ever created, no bounce is generated (nothing was accepted) — see FM-4.

8.3 RFC 5322 message + MIME model

Message  := Headers CRLF Body
Headers  := 1*(Field-Name ":" [FWS] Field-Body CRLF *( WSP Field-Body CRLF ))
Body     := *OCTET                          ; opaque unless MIME
MIME     := Content-Type ";" boundary=B
            "--"B CRLF Part *( "--"B CRLF Part ) "--"B"--"
Part     := Headers CRLF Body

Header folding: a continuation line begins with SPACE/TAB (section 2.2.3 of RFC 5322); encoded-words (RFC 2047) decode non-ASCII header text: =?UTF-8?Q?...?=. Malformed-input example: an unterminated MIME boundary — the parser closes the last part at end-of-message and flags mime_truncated=true rather than erroring (permissive "trustworthy" parsing per section 1.2 of RFC 5322 tolerance guidance), consistent with P3 (parser never panics on malformed input).

8.4 Maildir storage model

  • Mailbox/
    • tmp/<uniq>.host (in-progress write; not yet visible)
    • new/<uniq>.host:2, (delivered, unread)
    • cur/<uniq>.host:2,S (seen; trailing flags: S=Seen R=Replied
  • T=Trashed F=Flagged D=Draft)

<uniq> = <epoch-sec>.M<µs>P<pid>.<hostname> (I3). Write path: create in tmp/, write body, fsync, rename(2) into new/ (P4, I2) — POSIX guarantees rename is atomic within one filesystem. A crash before rename leaves an inert tmp/ file, cleaned after 36h (Maildir convention, FM-1).

8.5 IMAP command grammar (excerpt, sections 6/7 of RFC 9051)

command      = tag SP (login / select / fetch / store / search / idle) CRLF ;
select       = "SELECT" SP mailbox ;
fetch        = "FETCH" SP sequence-set SP fetch-att ;
fetch-att    = "UID" / "FLAGS" / "BODY" ["[" section "]"] / "ENVELOPE" ;
store        = "STORE" SP sequence-set SP store-att-flags ;
search       = "SEARCH" SP search-key *(SP search-key) ;
idle         = "IDLE" ;                      (* RFC 2177 *)

8.6 IMAP session state machine

From Event To
NotAuthenticated LOGIN/AUTHENTICATE success Authenticated
Authenticated SELECT/EXAMINE Selected(mailbox)
Selected CLOSE/UNSELECT Authenticated
Selected IDLE IdleSelected (untagged pushes until DONE)
any LOGOUT Closed

Worked example:

* OK IMAP4rev2 Server ready
A001 LOGIN alice secret
A001 OK LOGIN completed
A002 SELECT INBOX
* 23 EXISTS
* OK [UIDVALIDITY 1] UIDs valid
* OK [UIDNEXT 24] Predicted next UID
A002 OK [READ-WRITE] SELECT completed
A003 FETCH 1:23 (UID FLAGS)
* 1 FETCH (UID 1 FLAGS (\Seen))
A003 OK FETCH completed

Malformed-input example: FETCH abc (UID) (non-numeric sequence-set) → A004 BAD invalid sequence set per section 7.1 of RFC 9051, session state unchanged (I1 analogue for IMAP).

Failure-path example: server crashes mid-STORE; on restart, MODSEQ (I8) is recomputed from the last durable Maildir flag-rename, so the client's next FETCH CHANGEDSINCE sees a consistent (possibly slightly stale, never corrupt) view — see FM-2.

8.7 Anti-abuse pipeline data model

VerifyResult { spf: SpfResult, dkim: Vec<DkimResult>, dmarc: DmarcVerdict }
SpfResult    ∈ {Pass, Fail, SoftFail, Neutral, None, TempError, PermError}
DkimResult   { selector, domain, valid: bool, canon: (Header, Body) }
DmarcVerdict { policy: {None, Quarantine, Reject}, aligned: bool }

Worked example: a message forwarded through a mailing list — original DKIM signature valid=false (headers modified by list software adding List-Id:), but SPF Pass for the forwarder's IP is not aligned with the original From: domain, so DMARC alignment fails on both checks; policy Quarantine → message delivered to the recipient's Spam mailbox, not rejected (I10, Phase 9 N.8).

13.3 Deliverable

  • Folded headers with trailing whitespace before the fold are indistinguishable from a new field to a naive line-splitter — root cause: splitting on bare \n instead of checking the next line's leading whitespace; debugging: diff against the 1,000-message corpus.

13.10 Operational Notes

  • A buggy client sends a literal .\r\n mid-message without escaping — the server correctly ends DATA per spec; root cause is the client's bug, not the server's, but the failure mode looks like message truncation; debugging: compare against the escaping requirement in section 4.5.2 of RFC 5321.

14.9 Failure Analysis

Implement quota accounting (P10, I6) updated in the same transaction as the index write.

16.5 Conformance Fixtures

  • Two deliveries on the same epoch-second collide without the microsecond+PID+hostname disambiguators — always include all three (Maildir spec convention, I3).
  • Flag updates via rename (cur/…:2, → cur/…:2,S) racing a concurrent reader can present a moment where two filenames exist for one logical message; the index (not the filesystem listing) is the momentary source of truth for readers.

16.9 Failure Analysis

Index/filesystem divergence (FM-2) is detected by the periodic reconciliation sweep, not silently ignored; blast radius is one mailbox; containment is per-mailbox fsck, not a global lock; forensic artifact is the pre-repair divergence log entry retained for 30 days.

18. Phase 6 — IMAP IDLE / CONDSTORE / QRESYNC

18.1 Objectives

Implement push notification (RFC 2177 IDLE) and incremental resync (RFC 7162 CONDSTORE/QRESYNC), closing I8 (MODSEQ monotonicity) and I9 (no missed notification) fully.

18.2 Detailed Implementation Steps

Implement per-mailbox subscriber fan-out (§3 concurrency boundary): each Selected/IdleSelected session registers with the mailbox's notification list; on any committed index change (new delivery, flag STORE, EXPUNGE), the change is multiplexed to every subscriber before the next client command is accepted anywhere (I9). Implement MODSEQ (I8): a per-mailbox counter in em-mailbox-idx incremented transactionally with every flag/existence change (section 3.1 of RFC 7162); implement CHANGEDSINCE/ UNCHANGEDSINCE conditional STORE (an IMAP CAS, section 3.6 of RFC 7162) and SEARCH MODSEQ. Implement QRESYNC's SELECT parameter (last known UIDVALIDITY + MODSEQ + UID set) returning only the delta: new UIDs, flag changes since MODSEQ, and vanished UIDs (section 3.2.10 of RFC 7162) — this is the entire value proposition over a full-mailbox re-enumeration (P1 mental model, MM3 forward reference). Persist MODSEQ counters durably so a server restart doesn't reset them (I8 survives crash).

18.3 Deliverable

em-imap-server supporting IDLE with live push, CONDSTORE incremental FETCH, and QRESYNC-accelerated reconnect, verified against Dovecot (ADR-11) for push-latency parity.

18.4 Acceptance Criteria

Push (new mail → client EXISTS notification) latency ≤ 100 ms p99 (§4); zero imap_modseq_regression_total (I8) across a 10,000-mutation fuzz run including a mid-run server restart; QRESYNC reconnect after a simulated 60 s network drop returns exactly the delta (no full re-enumeration) in the qresync_after_drop.txt fixture (§18.5).

18.5 Conformance Fixtures

conformance/buckets/imap_idle_condstore/idle_push_latency.txt — new delivery while a session is IDLE, expected: EXISTS push ≤ 100 ms. .../modseq_restart.txt — server restart mid-mutation-sequence, expected: MODSEQ resumes above its pre-restart high-water mark, never regresses. .../qresync_after_drop.txt — reconnect with a stale UIDVALIDITY+MODSEQ+ UID-set, expected: exactly the new/changed/vanished delta returned.

18.6 Pitfalls

  • IDLE connections sit open for hours; per-session resource use must stay near the 100 KB budget (§4) — a naive implementation that buffers all history per subscriber leaks memory over a long IDLE.
  • CONDSTORE state persisted only in memory is lost on restart, silently breaking every client's incremental-sync assumption — MODSEQ must be durable (I8).
  • A network drop during IDLE without QRESYNC support forces full re-enumeration; without the UID-set-aware vanished-list logic, a naive QRESYNC implementation returns "everything changed," defeating its purpose.

18.7 Performance Concerns

Idle-session memory: ~100 KB/session (§4); 100,000 concurrent IDLE sessions ⇒ 10 GB, a chained constraint verified in §35 Capacity Model. Notification fan-out must be O(subscribers-to-this-mailbox), not O(all-sessions-on-server) — a per-mailbox subscriber list, not a global scan, keeps push latency flat as the server scales (§32 Scalability Analysis).

18.8 Edge Cases

A client that sends IDLE then immediately disconnects without DONE (TCP keepalive detects and reaps, §22 N.6 forward reference); a MODSEQ overflow at u64::MAX (astronomically distant, documented but not actively mitigated); QRESYNC parameters referencing a UIDVALIDITY that no longer matches (server forces full resync, correctly, rather than serving a mismatched delta).

18.9 Failure Analysis

A missed IDLE notification (I9 violation) manifests as "client doesn't see new mail until next poll" — a silent correctness bug, not a crash; detection: the subscriber-ack fixture in em-verifier; recovery is QRESYNC-style catch-up on the client's next SELECT even if the live push was missed, bounding the damage to "delayed," never "lost."

18.10 Operational Notes

Emit idle_sessions_active, idle_push_latency_seconds (histogram), imap_modseq_regression_total (I8, must stay 0). Deployment: IDLE sessions must be drained gracefully (send a final push, then close) during rolling upgrade, not abruptly reset, per the 30 s drain budget (§4).

em-queue::Scheduler driving em-smtp-client::deliver against a live remote MX (verified against a containerized Postfix receiver, ADR-11), correctly partitioning messages across active/deferred/hold/bounce.

19.4 Acceptance Criteria

Zero queue_reconcile_mismatch_total (I4) across a 10,000-message injected-failure fuzz run (mixing 4xx/5xx/timeout responses); retry backoff reaches the 5-day ceiling exactly at attempt 15 for a 2×-doubling schedule starting at 15 min (§4); per-message delivery latency 50–500 ms p50 against a local containerized MX (§4).

19.5 Conformance Fixtures

conformance/buckets/queue_bounce/deferred_backoff.txt — a recipient MX returning 421 repeatedly, expected: deferred with correctly doubling backoff, bounce generated exactly at the 5-day ceiling (I5). .../poison_message.txt — a recipient address crafted to trigger a parser edge case in the client FSM, expected: moved to hold/, never silently dropped (I4). .../reconcile_sweep.txt — an injected queue-state inconsistency, expected: detected and repaired by the reconciliation sweep.

19.6 Pitfalls

  • DNS resolution failures must retry with backoff, not immediately bounce — a transient resolver hiccup is not a permanent failure (P13).
  • TLS failures on outbound: falling back to plaintext silently is a downgrade-attack surface (T5) — default to hard-fail unless the operator explicitly opts into fallback per destination domain.
  • A crash between "MX responded 250" and "remove from active/" would double-send on restart if not made idempotent — the removal must be the durable commit point, checked before any retry.

19.7 Performance Concerns

Per-domain worker pools (§3) avoid head-of-line blocking one slow destination behind a fast one; queue-depth-based backpressure (RED- inspired, §5 paper #3) throttles new enqueues before the deferred queue grows unbounded (P7). DNS lookups are the dominant per-message outbound latency component (§4); cache MX answers for their TTL.

19.8 Edge Cases

A recipient domain with zero MX records but a valid A record (section 5.1 of RFC 5321, implicit MX fallback); a destination that accepts the TCP connection but never speaks SMTP (timeout, not immediate failure); multiple recipients on one message where some succeed and some 5xx (partial success — a per-recipient DSN, not an all-or-nothing bounce).

19.9 Failure Analysis

A queue-reconciliation mismatch (FM-3) — a message in zero or two directories — is caught by the periodic sweep (I4); blast radius is one message, not the whole queue; recovery moves the ambiguous entry to hold/ for operator resolution rather than guessing.

19.10 Operational Notes

Emit queue_depth{state}, queue_retry_ceiling_hits_total (I5), queue_reconcile_mismatch_total (I4). Operator CLI (em-cli mailq, em-cli queue flush, em-cli queue hold) mirrors Postfix's mailq/postqueue -f/postsuper -h mental model (§5 Reference Implementations #1) for operator familiarity.

20. Phase 8 — DKIM Signing & Verification

20.1 Objectives

Implement em-dkim: RFC 6376 signing on egress and verification on ingress, closing I11 (canonicalization fidelity), per ADR-08 and the Allman et al. CEAS 2005 DKIM paper (§5 paper #2).

20.2 Detailed Implementation Steps

Implement signing: canonicalize headers + body per the declared c= tag (simple or relaxed, section 3.4 of RFC 6376); compute the body hash (bh=); sign the canonical header block (including the signature-placeholder header itself excluded from its own hash, avoiding the recursive-hash trap) with Ed25519 by default or RSA-2048 (ADR-08, P8); insert the DKIM-Signature: header with h= listing exactly the signed headers (From, To, Subject, Date, Message-ID, Content-Type, MIME-Version — never headers a forwarder adds later, like Received:). Implement verification: parse the DKIM-Signature: header, fetch the public key from DNS (<selector>._domainkey.<domain> TXT record, via the delegated em-dns, P13), recompute the canonical hash with the declared canonicalization (I11 — never assume a different mode than what's declared), verify the signature. Support multiple signatures per message (different selectors/ domains) — verification passes if any one is valid.

20.3 Deliverable

em-dkim::sign and em-dkim::verify passing 100% of the RFC 6376 test vectors, wired into smtp_outbound (sign) and the anti_abuse pipeline (verify, I10 ordering).

20.4 Acceptance Criteria

100% pass on RFC 6376 official test vectors; Ed25519 sign latency ≤ 1 ms p99 (§4 M5); verify latency ≤ 5 ms p99 including a cached DNS lookup (§4 M6); zero dkim_canon_mismatch_total (I11) across a 1,000-message fuzz run mixing simple/relaxed canonicalization.

20.5 Conformance Fixtures

conformance/buckets/dkim/rfc6376_test_vectors.json — official RFC 6376 Appendix test vectors, expected: 100% pass. .../relaxed_forwarder.eml — a message re-canonicalized by a simulated forwarder (whitespace collapsed), expected: relaxed/relaxed signature still verifies; simple/ simple fails (correctly, per canonicalization semantics). .../multi_sig.eml — two DKIM-Signature headers, one broken, expected: verification passes via the valid one.

20.6 Pitfalls

  • Canonicalization mismatch between signer and verifier (signer used relaxed, a bug assumes simple) silently fails verification for every message from that domain — always read the c= tag, never hardcode (I11).
  • The signature header itself must be excluded from its own hash computation — including it is a recursive-hash bug that breaks every signature.
  • A mailing list or forwarder that modifies headers (adds List-Id:) invalidates the original signature — this is correct DKIM behavior, not a bug, but is frequently mis-diagnosed as one (§25 Threat Model T12 notes the operational confusion).

20.7 Performance Concerns

Ed25519 sign ~500 µs vs. RSA-2048 ~5 ms (§4 M5) — at 10,000 msg/s egress, Ed25519 costs ~5% CPU vs. RSA's ~50% (§31 Performance Engineering). DNS lookup for verification is the dominant verify-path cost; cache the public key per (domain, selector) respecting the DNS TTL.

20.8 Edge Cases

A DNS TXT record split across multiple strings (section 3.6.2.2 of RFC 6376 concatenation rule); a revoked key (empty p= tag) — must fail closed, not treat as absent; a signature with an l= body-length limit (section 8.2 of RFC 6376 deprecates this — verify but flag as suspicious, never silently truncate trust).

20.9 Failure Analysis

A canonicalization bug (I11) causes false-negative verification for an entire sending domain — detection: the RFC 6376 test-vector suite catches it pre-merge; blast radius in production would be legitimate mail flagged as DKIM-fail, feeding into DMARC's quarantine/reject decision (Phase 9) — this is why I11 is a hard invariant, not a best-effort check.

20.10 Operational Notes

Emit dkim_sign_duration_seconds, dkim_verify_result_total{valid}. Key rotation runbook (§27): publish new selector, wait for DNS TTL, switch signing, then retire the old selector — skipping the TTL wait breaks verification for in-flight mail (a documented operational pitfall, §26).

21. Phase 9 — SPF + DMARC

21.1 Objectives

Implement em-spf (RFC 7208) and em-dmarc (RFC 7489), closing I10 (fixed SPF→DKIM→DMARC evaluation order, P6).

21.2 Detailed Implementation Steps

Implement SPF: fetch the TXT v=spf1 record for the MAIL FROM domain via em-dns; walk mechanisms (a, mx, ip4, ip6, include, all) per section 5 of RFC 7208, matching against the SMTP source IP; cap total DNS-lookup- causing mechanisms at 10 (section 4.6.4 of RFC 7208 — a spec-mandated limit, mitigating T13 SPF-recursion-amplification); produce one of Pass/Fail/SoftFail/Neutral/None/TempError/PermError. Implement DMARC: fetch TXT _dmarc.<domain>; parse p= policy; check alignment (From: header domain vs. the SPF-authenticated domain and/or the DKIM-signing domain, strict or relaxed per section 3.1.1 of RFC 7489); apply policy — reject (550), quarantine (deliver to Spam), or none (deliver to INBOX) — only after both SPF (Phase 9 same-phase dependency) and DKIM (Phase 8) results exist, enforcing I10's fixed order at the anti_abuse dispatcher (§3).

21.3 Deliverable

em-spf::check and em-dmarc::evaluate composed into the anti_abuse pipeline (§3), producing a VerifyResult (§8.7) that gates local delivery routing (INBOX vs. Spam vs. reject).

21.4 Acceptance Criteria

100% pass on spf_dmarc conformance bucket; SPF check ≤ 50 ms p99 (§4 M7); zero dmarc_evaluated_out_of_order_total (I10) across a 1,000-message fuzz run; SPF lookup count capped at exactly 10 for a crafted include: chain of 15 (section 4.6.4 of RFC 7208 fixture, §21.5).

21.5 Conformance Fixtures

conformance/buckets/spf_dmarc/spf_include_chain_15.txt — an SPF record with 15 chained include: mechanisms, expected: evaluation halts with PermError at the 10th lookup (T13 mitigation). .../dmarc_forwarder.eml — the worked example from §8.7 (SPF fails via forwarder, DKIM fails via re-signing, DMARC quarantines), expected: delivered to Spam, not rejected. .../dmarc_reject_unaligned.eml — a spoofed From: with no aligned SPF/ DKIM and p=reject, expected: 550 5.7.1 before DATA completes.

21.6 Pitfalls

  • SPF's redirect= modifier can itself trigger unbounded additional lookups if not counted toward the same 10-lookup cap — a documented amplification vector (T13, "SPF redirect bombing").
  • DMARC alignment mode (aspf=s|r, adkim=s|r) defaults differ by publisher intent — strict requires exact domain match, relaxed allows organizational-domain match; misreading the published mode causes false alignment failures.
  • DNS TempError (resolver timeout) must not be treated as SPF Fail — section 2.6.1 of RFC 7208 requires distinct handling (typically accept-and-defer, not reject) to avoid rejecting legitimate mail during a DNS blip.

21.7 Performance Concerns

SPF/DMARC checks are DNS-bound (§4 M7, ~5-50 ms); cache SPF/DMARC TXT answers per their DNS TTL to keep steady-state latency near the low end. At 1,000 msg/s inbound, the combined SPF+DKIM+DMARC pipeline costs ~20 ms/ message serialized — parallelizing the independent SPF and DKIM lookups (both needed before DMARC) halves this critical path.

21.8 Edge Cases

A domain publishing no SPF record (None result, not Fail); a DMARC record with pct= sampling (only a percentage of failing mail gets the strict policy — the rest gets monitored-but-delivered); a From: header with a different domain than any RFC 5322 addr-spec seen elsewhere in the message (the exact alignment check DMARC exists to make precise).

21.9 Failure Analysis

An out-of-order DMARC evaluation (I10 violation) produces a meaningless verdict (T14, "DMARC policy bypass" if it silently defaults to pass); detection: the order assertion in em-verifier; containment: the anti_abuse dispatcher is the single call site for pipeline order, never invoked piecemeal elsewhere in the codebase.

21.10 Operational Notes

Emit spf_result_total{result}, dmarc_policy_applied_total{policy}. DMARC aggregate reporting (RUA) generation is PhaseDeferred("§38") — out of scope for Phase 0-12; incoming RUA reports (if the operator's domain is a report recipient) are rate-limited to avoid the flooding pitfall noted in §26.

22. Phase 10 — Sieve Filter Runtime

22.1 Objectives

Implement em-sieve: a compiler + sandboxed bytecode VM for RFC 5228 server-side filtering, closing I12 (bounded execution, P9).

22.2 Detailed Implementation Steps

Implement the Sieve grammar subset (section 8 of RFC 5228): if/elsif/else, header/address/envelope tests, and the action set keep, discard, redirect, fileinto, reject, vacation (§11.4 SieveAction). Compile scripts to bytecode ahead of execution (ADR-09 — never interpret the source text per-message). Enforce I12 at the VM level: a Received:- header count check (cap 50, mitigating T8/FM-9 mail-loop DoS) and a bytecode step budget evaluated before any redirect/vacation action is permitted to execute; a script that exceeds either budget aborts to the default Keep action (P9). Run Sieve at local_delivery time (Phase 4's downstream consumer), before the message reaches Maildir, so fileinto can target the final mailbox directly.

22.3 Deliverable

em-sieve::compile and em-sieve::VM::run executing user scripts against delivered messages, verified against Dovecot's Pigeonhole Sieve implementation behavior (ADR-11 differential).

22.4 Acceptance Criteria

100% pass on the sieve conformance bucket; per-message Sieve evaluation ≤ 1 ms p99 (§4 M8); zero sieve_budget_exceeded_total false-positives against a corpus of 500 legitimate real-world Sieve scripts; a crafted 50+Received:-header redirect-loop fixture is refused within I12's cap (§22.5).

22.5 Conformance Fixtures

conformance/buckets/sieve/redirect_loop_51.eml — a message with 51 Received: headers hitting a redirect action, expected: refused with "loop detected," I12. .../vacation_storm.txt — a vacation auto-reply responding to a mailing-list message, expected: suppressed (do not auto-reply to List-Id:-tagged mail, a documented pitfall §22.6). .../fileinto_missing_folder.txt — fileinto "NoSuchFolder", expected: compile-time or runtime error surfaced to the user's "Filter Errors" folder, not a silent drop.

22.6 Pitfalls

  • A user's redirect chain can loop through another user's Sieve script that redirects back — I12's Received:-header count is the structural defense, not a per-user check (which can't see the other user's script).
  • vacation auto-replies responding to a mailing list create a storm (list replies to the auto-reply, auto-reply fires again) — suppress vacation for messages carrying List-Id:/Precedence: bulk.
  • A syntactically valid but semantically broken script (fileinto to a nonexistent folder) must not silently drop mail — route to a well-known fallback folder and surface the compile/runtime error.

22.7 Performance Concerns

Bytecode compilation happens once per script edit, not per message (ADR-09) — the per-message cost is VM execution only, budgeted at ≤ 1 ms (§4 M8). The Received:-header count check must be O(1) (a maintained counter from parsing, §13), not an O(n) header re-scan per action.

22.8 Edge Cases

An empty Sieve script (implicit keep); a script referencing an unsupported extension (compile error, not silent ignore); a reject action combined with a fileinto (RFC 5228 semantics: mutually exclusive per section 4.1 of RFC 5228 — reject discards, so ordering in the script matters); Unicode in header :contains comparisons (case-folding per section 2.7.3 of RFC 5228 comparator rules).

22.9 Failure Analysis

An I12 budget-bypass bug would let a malicious or buggy script cause the mail-loop DoS class the design specifically defends against (T8); blast radius would be the recipient's mailbox flooding, potentially cascading to other users if redirects fan out; detection: the loop-fixture in em-verifier; containment: budget check precedes action execution, not merely logged after the fact.

22.10 Operational Notes

Emit sieve_scripts_compiled_total, sieve_eval_duration_seconds, sieve_budget_exceeded_total (I12). Compile errors surface to the user via whatever management interface the operator provides (out of this project's scope, §1 non-goals — webmail UI); this project only guarantees the error is captured and queryable via em-cli.

23. Phase 11 — Bounce Processing (DSN)

23.1 Objectives

Implement em-bounce: RFC 3464 DSN generation on permanent failure or retry-budget exhaustion (I5), avoiding the backscatter failure mode (T7).

23.2 Detailed Implementation Steps

Implement DsnReport (§11.4) construction: multipart/report; report-type=delivery-status per section 2 of RFC 3464, with a human-readable part, a message/delivery-status part (Reporting-MTA, Original-Recipient, Final-Recipient, Action, Status per RFC 3463's enhanced status codes), and the original message (or headers-only, per size policy) as message/rfc822. Set Return-Path: <> on the DSN itself (the standard signal "do not bounce this bounce," preventing double-bounce loops). Before generating a DSN for an inbound-rejected message, verify SPF for the claimed sender (I10's SPF result, Phase 9) — never bounce to a domain whose SPF fails for the connecting IP, the structural defense against backscatter (T7, FM-7). A DSN that itself cannot be delivered is a double-bounce: hold for postmaster review, never retried indefinitely.

23.3 Deliverable

em-bounce::generate producing a valid RFC 3464 DSN for every permanently failed or retry-exhausted QueueEntry (Phase 7), verified byte-for-byte against the RFC 3464 grammar.

23.4 Acceptance Criteria

100% pass on the queue_bounce DSN-format conformance fixtures; zero backscatter DSNs generated across a 1,000-message fuzz run of forged- sender rejections (T7, SPF-gated); double-bounce messages are held, not retried, within 1 delivery attempt (§23.5).

23.5 Conformance Fixtures

conformance/buckets/queue_bounce/dsn_format.eml — a generated DSN, expected: parses as valid multipart/report per section 2 of RFC 3464. .../backscatter_spf_fail.txt — a rejected message with a forged sender whose SPF fails, expected: no DSN sent to the forged address (T7). .../double_bounce.txt — a DSN that itself bounces, expected: held for postmaster, not retried.

23.6 Pitfalls

  • Bouncing without an SPF check on the claimed sender is the exact backscatter mechanism that gets legitimate mail systems blacklisted (T7) — this check is structural, not optional/configurable.
  • Forgetting Return-Path: <> on the DSN itself creates a bounce-of-a- bounce loop the moment the DSN also fails to deliver.
  • Including the full original message body in every DSN (rather than headers-only past a size threshold) can itself create oversized-message rejections downstream — cap DSN body-inclusion size.

23.7 Performance Concerns

DSN generation is off the hot path (triggered only on failure, not per successful delivery) — no per-message latency budget applies (§4 notes N/A for this phase, consistent with the original scoping). Double-bounce detection must be O(1) (a flag on the message, not a content scan).

23.8 Edge Cases

A message with multiple recipients where some succeed and some permanently fail — generate a per-recipient DSN, not an all-or-nothing bounce (§19.8 cross-reference). A DSN for a message that itself had no valid Return-Path (already a bounce) — recognize and route to postmaster directly rather than attempting normal DSN generation.

23.9 Failure Analysis

A missing SPF-gate-before-bounce bug (T7) causes backscatter, the single most reputationally damaging failure mode for an MTA (alongside open relay, T1); detection: the fuzz fixture asserting zero DSNs to SPF-failing forged senders; recovery: BATV (Bounce Address Tag Validation, tagging outgoing envelope-from so incoming bounces without a valid tag are rejected) is PhaseDeferred("§38") as a defense-in-depth addition beyond the SPF gate.

23.10 Operational Notes

Emit dsn_generated_total{reason}, double_bounce_total (should stay near 0; a sustained nonzero rate indicates a backscatter incident, T7, §27 runbook). DSN templates live under templates/ (§10) for operator customization of the human-readable portion only — the message/delivery-status machine part is never operator-customizable (interop requirement).

24. Phase 12 — Anti-Abuse, Conformance & Fuzzing

24.1 Objectives

Close the remaining anti-abuse surface (greylisting, per-IP/per-user rate limiting, I13's relay-policy hardening) and stand up the full differential

  • fuzz + 30-day soak canary gating GA (§4's defining property).

24.2 Detailed Implementation Steps

Implement greylisting (ADR-15, E. Harris 2003, §5): on first contact from an unseen (source IP, sender, recipient) triplet, reply 450 temporary deferral; legitimate MTAs retry per RFC 5321's mandated retry behavior, most spam engines do not — accept on retry after a configurable minimum delay (typically minutes). Implement per-IP and per-user rate limiting (ADR-17) via a Bloom-filter-backed approximate token bucket (B. Bloom 1970, §5 paper #4) — O(1) memory per bucket, bounded false-positive rate tuned below an operationally acceptable threshold. Harden I13's relay check with the rate-limit and greylist results feeding into the RCPT-time decision (ADR-19). Stand up the full conformance/ suite across every bucket from Phases 1-11, the Postfix/Dovecot differential harness (ADR-11), the em-fuzz targets (msgparse, SMTP command parser, IMAP command parser, Sieve compiler) running continuously in CI, and the 30-day fuzz soak canary gating GA sign-off.

24.3 Deliverable

Full anti-abuse pipeline (greylist + rate-limit + SPF/DKIM/DMARC from Phase 9) composed at the anti_abuse boundary (§3); green differential suite against Postfix + Dovecot; 24h continuous fuzz run with zero panics as the GA gate (M15 forward reference).

24.4 Acceptance Criteria

Greylisting correctly defers 100% of first-contact triplets and accepts 100% of legitimate retries after the configured delay in the greylist_retry.txt fixture; rate limiter false-positive rate ≤ 0.1% at the configured Bloom-filter size (§24.5); zero panics across a 24h continuous fuzz run (M15) and zero invariant violations across the 30-day soak canary before GA sign-off.

24.5 Conformance Fixtures

conformance/buckets/smtp_extensions/greylist_retry.txt — a first-contact triplet followed by a correctly-timed retry, expected: 450 then 250. .../rate_limit_burst.txt — 10,000 connection attempts from one IP in 60 s, expected: rate-limited past the configured threshold with 421, not accepted. interop_postfix/full_differential.txt and interop_dovecot/full_differential.txt — the complete SMTP/IMAP command surface run against both oracles, expected: byte-identical behavior on every documented RFC-mandated response.

24.6 Pitfalls

  • Greylisting delays all first-contact mail, including legitimate one-off senders (e.g., a password-reset email from a service the user has never received mail from) — mitigate with an allowlist for high-reputation sending infrastructure (documented operator tuning, not a code-level exception).
  • A Bloom-filter rate limiter's false-positive rate grows unbounded if the filter is undersized relative to actual distinct-IP cardinality — size it from the Capacity Model (§35), not a fixed guess.
  • Differential testing against Postfix/Dovecot can pass while both diverge from the RFC in the same (widely-tolerated) way — the RFC test vectors (§5, §20.5) remain the ground truth, differential testing is a complement, not a replacement.

24.7 Performance Concerns

Greylisting's (IP, sender, recipient) triplet cache must support O(1) lookup at connection time — a hash-indexed cache, evicted on a rolling window (not unbounded growth). Rate-limit checks happen before any protocol parsing to shed load as early as possible (defense-in-depth ordering ahead of I13's RCPT-time check).

24.8 Edge Cases

A legitimate sender behind a load-balanced outbound MTA pool where retries come from a different source IP (greylisting's IP-based triplet incorrectly treats this as a new first-contact) — documented limitation, mitigated by allowlisting known multi-IP senders. A single user triggering rate limits via many legitimate simultaneous IMAP client devices (phone + laptop + tablet) — per-user limits must account for realistic multi-device concurrency (§4).

24.9 Failure Analysis

A rate-limiter or greylist bug that's too aggressive silently drops legitimate mail (a false-positive failure mode, distinct from but as damaging as an open relay); detection: delivery-success-rate dashboards alarm on an unexpected drop (§27); recovery: an emergency allowlist override via em-cli bypasses greylist/rate-limit for a specified sender without a redeploy.

24.10 Operational Notes

Emit greylist_deferred_total, greylist_accepted_after_retry_total, ratelimit_denied_total{scope}. GA sign-off checklist (§27 Operational Readiness) requires: 24h fuzz clean, 30-day soak clean, full differential green (M14), all M1-M15 performance targets met (§31).

Metrics (Prometheus text exposition, ADR-21): per-crate counters/ histograms named throughout the Phase Plan (§12+) — smtp_*, imap_*, maildir_*, queue_*, dkim_*, spf_*, dmarc_*, sieve_*, ratelimit_*, greylist_*. Tracing: tracing spans (ADR-20) per session, per delivery attempt, per Sieve execution, exported as structured JSON for SIEM ingestion. Structured logging: every log line carries session_id, queue_id (where applicable), and the invariant/ADR token relevant to the event.

Dashboards: (1) SMTP accept-rate + latency percentiles; (2) IMAP command-rate + latency percentiles; (3) queue depth by state (active/deferred/hold/bounce, I4); (4) anti-abuse verdict distribution (SPF/DKIM/DMARC/greylist/rate-limit); (5) disk usage (Maildir + queue volumes, FM-10 precursor); (6) TLS handshake version/failure distribution.

Alerting philosophy: alert on rate-of-change and ratio anomalies (relay_denied_total/relay_permitted_total ratio, T1; DMARC-fail ratio, T14/T15) rather than raw counts, since raw counts scale with traffic. Page on: queue-depth sustained growth (FM-3 precursor), disk-usage threshold breach (FM-10), cert-expiry countdown (FM-8), sustained double-bounce rate (FM-12).

Incident response: named runbooks (below) are the first response action; every runbook ends with a forensics-retention step matching its Failure Modes row (§26).

Runbooks (named, cross-referencing §26 FM rows):

  • Queue backed up (FM-3): em-cli mailq, inspect destination responsiveness, em-cli queue flush, em-cli queue hold for triage.
  • IMAP IDLE clients disconnecting (FM-5): check NAT/keepalive timers, adjust per-user concurrent connection limits.
  • DKIM failures (T12, T2): verify DKIM-Signature header, check DNS record, rotate keys per §27 rotation procedure.

Deployment topology: one binary per role (smtpd, imapd, outboundd, §1) behind a load balancer for SMTP/IMAP ports; Maildir + SQLite index on host-local disk in Phase 0-12 (sharded multi-host placement PhaseDeferred("§38")).

Canary/rolling-upgrade/rollback: canary one instance at low traffic weight; monitor SLO burn rate for 1h before proceeding; rollback is a binary redeploy (no schema migration in the common case — see §28 for when one is required); IMAP IDLE sessions drain gracefully within the 30 s budget (§4) before instance termination.

28. Compatibility & Versioning

Wire compatibility: SMTP/IMAP protocol behavior follows the RFCs exactly (§5); this project's own extensions (none beyond standard RFCs) are not introduced, keeping wire compatibility with every conforming client/MTA indefinitely.

Storage compatibility: Maildir format is the de facto standard (§8.4) — externally compatible with any Maildir-aware tool. The SQLite index schema is versioned (schema_version row, ADR-05); a schema migration ships as a versioned, forward-only migration script run at startup, with a pre-migration backup snapshot taken automatically.

API stability: the operator CLI (em-cli) and config schema (em-config, ADR-16) follow SemVer; a MAJOR bump is required to remove or change the meaning of any config key or CLI subcommand.

Migration policy: index-schema migrations are additive-preferred (new nullable columns) to avoid a rewrite of the entire index; a breaking migration (rare) requires a documented downtime window and is gated by a MAJOR version bump.

Deprecation policy: a deprecated config key or CLI flag emits a structured warning for ≥ 2 MINOR releases before removal in the next MAJOR release.

Rolling-upgrade guarantees: SmtpState/ImapState enum additions are backward compatible for in-flight connections (§14.10, §17.10) because no connection spans a deploy in this architecture; the queue's on-disk QueueEntry format (§11.4) is versioned so a mixed-version queue directory during a rolling upgrade never misparses an entry written by the other version.

29. Testing & Verification Strategy

Unit tests: per-crate, colocated with source; every parser (em- msgparse, SMTP/IMAP command parsers, em-sieve compiler) carries a unit suite covering its EBNF grammar (§8.1, §8.5) exhaustively.

Integration tests: conformance/ buckets (§10) exercise full session lifecycles against live crate compositions.

Property-based testing: Envelope/Message/MailboxIndexRow round-trip properties (parse→serialize→parse is identity) checked via generated inputs.

Differential testing: the Postfix + Dovecot oracle (ADR-11) runs the full documented RFC-mandated response surface and diffs behavior (interop_postfix/, interop_dovecot/ buckets, §24).

Fuzzing: em-fuzz targets per untrusted-input parser (msgparse, SMTP command parser, IMAP command parser, Sieve compiler); continuous 24h run gates every release (ADR-12, M15); a 30-day soak canary gates GA.

Chaos / fault injection: em-verifier's deterministic simulator (§7) injects crashes mid-write (FM-1 fixture), network drops mid-IDLE (§18.5 QRESYNC fixture), and DNS timeouts (FM-6 fixture) to exercise recovery paths without waiting for production incidents.

Deterministic replay: every em-verifier transcript is a byte-exact input log; a violation aborts with the failing prefix attached (§7), making every invariant breach reproducible offline by any engineer, any time.

Soak testing: the 30-day fuzz canary (ADR-12) processes synthetic mail at scale, asserting zero invariant violations and zero panics across the full duration — this is the GA gate (§24.10).

Conformance: named fixture buckets (§10, P12) map 1:1 to phases; every phase's N.5 (Conformance Fixtures) is a row in this suite.

Performance-regression gating: em-bench criterion benchmarks run in CI against the M-table (§31) baselines; a regression beyond a configured tolerance fails the build.

Traceability to System Invariants: every I# (§7) has at least one dedicated em-verifier assertion and at least one fixture exercising it (cross-referenced throughout §12+'s N.5 sections).

30. Build & Release Engineering

Reproducible builds: pinned Cargo.lock, pinned MSRV (Rust 1.78+, ADR-01), and a Dockerfile (§10) multi-stage build producing a byte-identical artifact for a given lockfile + toolchain version.

Artifact signing: release binaries are signed (minisign or cosign-style) so operators can verify provenance before deployment.

SBOM: generated per release via cargo-cyclonedx (or equivalent), covering every crate dependency (§10's 22-crate workspace) for downstream dependency-auditing.

Release channels: stable (SemVer-tagged), nightly (main-branch build, fuzz-gated only, not soak-gated) — operators choose per their risk tolerance.

CI/CD topology (ADR-22): GitHub Actions for build/test/lint/short- fuzz on every PR; a self-hosted runner for the 24h continuous fuzz gate and the 30-day soak canary (hosted CI cannot provide multi-day-lived runners).

Version stamping: every binary embeds its SemVer + git SHA + build timestamp, queryable via em-cli version.

Provenance/attestation: CI produces a signed build-provenance attestation (SLSA-style) linking the released artifact to its exact source commit and build environment.

Dependency auditing: cargo audit runs on every PR against the RustSec advisory database; a new advisory affecting a workspace dependency fails CI until triaged.

31. Performance Engineering

Benchmarking/profiling methodology: em-bench (criterion) benchmarks the hot paths — message parse (§13), SMTP command dispatch (§14), Maildir insert (§16), IMAP FETCH (§17), DKIM sign/verify (§20) — against the M-table below, gated in CI (§29). perf record identifies hot syscalls; bpftrace traces kernel-side fsync/rename latency; tracing spans provide application-level flame graphs.

Allocation analysis: header parsing uses Bytes-sliced zero-copy views (§13.7) rather than per-field copies; SMTP pipelining uses a single cursor-based buffer rather than per-command reallocation (§14.7).

Lock contention: SmtpState/ImapState are single-owner per connection (P1, §11) — no cross-connection locks on the hot path; the mailbox index's single-writer commit path (I14) is the one serialization point per mailbox, sized to stay off the critical path for read-heavy IMAP workloads.

Cache/syscall analysis: Maildir delivery costs 1 file create + N write syscalls + 1 fsync + 1 rename (§16.7); IMAP FETCH of metadata-only attributes never touches the Maildir file, only the SQLite index (§17.7) — this split is the primary lever keeping FETCH fast.

Tail-latency analysis: p99 budgets are set 5x the p50 target throughout the M-table (reflecting DNS/TLS/disk tail variance); the DKIM/SPF/DMARC pipeline's p99 is dominated by uncached DNS lookups (M6, M7) — caching per TTL is the primary tail-latency lever.

32. Scalability Analysis

What stays constant: per-connection memory (§4, ~100 KB IDLE session); per-message parse/dispatch cost (O(message size), §13, §14); DKIM sign/verify cost per message (O(1) relative to mailbox size, §20).

What grows (with Big-O): mailbox SELECT/SEARCH cost grows with mailbox size — O(n) for a full-text SEARCH without an index (§17.7, M4); O(log n) or better for UID/MODSEQ-indexed operations via SQLite's B-tree (§16, ADR-05). Queue reconciliation sweep cost grows O(queue depth) (§19.9). IDLE notification fan-out grows O(subscribers to one mailbox), not O(total server sessions) — the mailbox-scoped subscriber list (§3, I9) is what keeps this from becoming a global bottleneck as the server scales to more users.

Named bottlenecks in order: (1) disk I/O for Maildir delivery + index commit (§16.7, the dominant per-message cost at scale); (2) cryptographic cost of TLS handshake + DKIM sign/verify at high connection/ message churn (§20.7); (3) DNS lookup latency for SPF/DKIM/DMARC/MX resolution, mitigated by TTL-respecting caching (§21.7); (4) single-host Maildir volume capacity ceiling (§4's 10 GB/user default quota × user count).

Horizontal scaling: SMTP/IMAP roles scale horizontally behind a load balancer (stateless per-connection routing, since state lives in Maildir

  • SQLite, not in-process, P1); the outbound queue's per-domain worker pools (§19.7) scale by adding workers, bounded by DNS/network resources of the sending host, not by the queue design itself.

Sharding/partitioning: mailbox placement is single-host in Phase 0-12 (PhaseDeferred("§38") for sharded multi-host placement); the practical ceiling before sharding is required is the single host's disk capacity and IOPS budget (§35 Capacity Model derives the exact number).

Coordination overhead: none across SMTP/IMAP roles (P1 — no shared mutable state); within one mailbox, the single-writer index-commit path (I14) is the sole coordination point, and it is scoped per-mailbox, not per-server, so overhead doesn't grow with unrelated-mailbox traffic.

Practical ceiling and levers beyond it: a single host reaches its ceiling at the disk-IOPS-bound Maildir insert rate (§35); the lever beyond it is sharded multi-host mailbox placement (deferred, §38), which trades the current zero-coordination-overhead property for a mailbox-to-host routing layer — a fundamentally different tradeoff, covered as Alternative Architecture Roads Not Taken #2 (§37).

33. Mental Models & First Principles

  1. MM1 — SMTP is push, IMAP is pull; a mailbox is a shared inbox two independent protocols write/read against, never a shared process. Predicts: crash-domain independence between receive and access paths. Bug class without it: a shared-memory shortcut couples restart/crash domains, so an IMAP bug can take down mail receipt. Applied in §3, §11.2 (P1).
  2. MM2 — A Maildir rename is a state transition, not a file operation. Predicts: crash safety comes entirely from filesystem atomicity (rename(2)), not application-level locking. Bug class without it: in-place mutation (mbox-style) corrupts under a concurrent writer or a mid-write crash. Applied in §8.4, Phase 4 (§16), I2/I3.
  3. MM3 — UID is identity; sequence number is position. Never confuse the two. Predicts: correct handling of EXPUNGE-caused sequence-number shifts. Bug class without it: client-side cache corruption the moment any message is deleted. Applied in §8.6, §17 (I7).
  4. MM4 — MODSEQ is a Lamport-clock-like monotonic counter for one mailbox's mutation history. Predicts: CONDSTORE/QRESYNC's entire correctness argument reduces to "never let this counter go backward or skip." Bug class without it: incremental sync silently returns stale or wrong deltas after a restart. Applied in §18 (I8).
  5. MM5 — SPF/DKIM/DMARC are three independent witnesses; DMARC is the judge that needs both testimonies before it rules. Predicts: evaluation order is part of correctness, not an implementation detail. Bug class without it: a meaningless DMARC verdict computed before its inputs exist. Applied in §8.7, §21 (I10, P6).
  6. MM6 — A queue entry's state-machine position, not the message content, is what you're debugging when mail seems "stuck." Predicts: operators should read queue state first, grep logs second. Bug class without it: reconciliation bugs go unnoticed because nobody is watching the state distribution. Applied in §19, §26 (I4, FM-3).
  7. MM7 — A DSL embedded inside a trust boundary needs a budget, not just a sandbox. Predicts: loop/redirect storms require a structural execution cap, not merely restricted capabilities. Bug class without it: a capability-safe but unbounded script still causes a mail-loop DoS. Applied in §22 (I12, T8, FM-9).
  8. MM8 — Backscatter is what happens when you trust the envelope sender enough to talk back to it. Predicts: any auto-response system (bounce, vacation) needs a trust check before replying, symmetric to the trust check on receiving. Bug class without it: reputational blacklisting incidents from bouncing to forged senders. Applied in §23, §25 (T7, FM-7).

Postfix made the master+ multi-daemon-per-role split its one distinguishing decision — every stage (smtpd, cleanup, qmgr, local, smtp) is a separate process communicating over Unix-domain sockets. Dovecot made pluggable storage backends (Maildir/mbox/mdbox) plus a separate index layer (dovecot.index) its distinguishing decision — accelerating SEARCH/FETCH beyond what raw Maildir directory scans can do. That wins when IMAP read performance at very large mailbox sizes matters more than storage-format simplicity — this design borrows the "separate index" idea (SQLite, ADR-05) but keeps Maildir as the sole storage format rather than also supporting mdbox.

Cyrus IMAP made single-process-per-mailbox-operation atomicity its distinguishing decision, trading a proprietary binary index format (cyrus.index/cyrus.cache) for extremely tight consistency guarantees. That wins in regimes demanding the strongest possible consistency per mailbox operation — at the cost of a documented history of format-version migration pain (§5 Reference Implementations #5) this design avoids via a versioned, schema-evolvable SQLite index (ADR-05, §28).

35. Back-of-Envelope Capacity Model

  1. Inbound sustained bandwidth = per-core throughput × avg message size = 10,000 msg/s (M9, §4) × 10 KB = 100 MB/s sustained inbound bandwidth per core at the receive path.
  2. IDLE session memory footprint = concurrent IDLE sessions × per-session memory = 100,000 (§4 max concurrency) × 100 KB (§4) = 10 GB resident memory for a fully-loaded IDLE fleet (chained directly from §4's two rows).
  3. FD budget = concurrent connections × (1 connection FD + ~1 open Maildir handle) = 100,000 × 2 ≈ 200,000 FDs, matching the ulimit -n 200,000 constraint in §4.
  4. Total mailbox storage ceiling = user count × per-user quota = 10⁶ users (§1 target scale) × 10 GB (§4 default quota) = 10 PB aggregate storage ceiling at the upper end of the target user range.
  5. SQLite index footprint = user count × avg messages/user × per-row index size = 10⁶ × 10,000 msgs × 200 B (§4 storage amplification row) = 2 TB aggregate index size — small relative to the 10 PB of message bodies, confirming the index is not the storage bottleneck.
  6. Worst-case deferred-queue depth = deferred fraction × inbound rate × backoff ceiling = assume 1% of 10,000 msg/s deferred at steady state × 5-day ceiling (§4, I5) = 100 msg/s × 432,000 s = 43.2M messages; at 10 KB avg, that's 432 GB of deferred-queue disk footprint to provision for.
  7. DKIM signing CPU cost at volume = throughput × sign latency = 10,000 msg/s (M9) × 500 µs (M5, Ed25519) = 5 CPU-core-seconds per second, i.e. 5 dedicated cores' worth of signing work at full receive-path throughput — matching the "~5% CPU with Ed25519" figure in §20.7 on a ~100-core fleet.
  8. Ingress anti-abuse CPU cost = throughput × combined SPF+DKIM+DMARC latency = 1,000 msg/s (a conservative ingress-verification-rate assumption) × 20 ms (§21.7, chained from M6+M7) = 20 CPU-core- seconds per second.
  9. Greylist triplet cache size = inbound rate × distinct-sender fraction × retention window = 10,000 msg/s × 10% distinct-first- contact assumption × 14,400 s (4h retention) = 14.4M active triplets to size the Bloom filter/cache for (ADR-17 input).
  10. 1M-mailbox SELECT feasibility = confirms M13's 1 s p50 target: a 1M-row SQLite index scan at ~10⁶ rows/sec sequential B-tree scan rate (conservative NVMe-backed estimate) ≈ 1 s, matching M13 without requiring a full-text index for basic EXISTS/UIDVALIDITY metadata.

37. Alternative Architectures (Roads Not Taken)

Alt 1 — Unified single-process daemon (no SMTP/IMAP split).

        ┌─────────────────────────────────────┐
        │   single process: SMTP + IMAP +      │
        │   Maildir + index, one address space │
        └─────────────────────────────────────┘

Regime where it wins: small-to-medium single-host deployments valuing atomic operational simplicity (one process to start/stop/monitor) over independently scaling or restarting SMTP vs. IMAP. Real system: Cyrus IMAP's historical single-process-per-mailbox-operation design taken to its logical extreme. Rejected because it violates P1 (MM1) — a bug or crash in the IMAP command parser would take down mail receipt too, exactly the coupling this design's trust-boundary separation (§3) exists to prevent.

Alt 2 — Transactional-database-backed mailbox store.

   smtp/imap servers ──► RDBMS (e.g. ESE/Postgres) ──► shared storage
                          (messages as rows/blobs, not files)

Regime where it wins: deployments needing strong cross-message transactional guarantees and location-transparent multi-host access without relying on shared-filesystem semantics. Real system: Microsoft Exchange Server's ESE-based store. Rejected because it trades away Maildir's simple, dependency-free crash-safety argument (P4, MM2) for a heavyweight database dependency, and couples storage scaling to the database's scaling story rather than the filesystem's (ADR-04's rationale).

Alt 3 — Content-addressed immutable blob store.

   message bytes ──► SHA-256 ──► content-addressed blob store
                                  (dedup across users; flags external)

Regime where it wins: archival/compliance-focused deployments valuing deduplication and immutable audit trails over low-latency flag mutation. Real system: Perkeep (formerly Camlistore, Brad Fitzpatrick's personal content-addressable storage system). Rejected because content-addressing adds a hash-index lookup indirection to every read, and IMAP's frequent small mutations (flag changes, STORE, §18) fit awkwardly against a storage model optimized for immutability — Maildir's rename-based flag mutation (§8.4) is a better fit for email's actual mostly-immutable-body/ frequently-mutated-metadata access pattern.

Alt 4 — Pure relay/smarthost (no local IMAP storage at all).

   inbound SMTP ──► anti-abuse pipeline ──► outbound SMTP (forward only)

Regime where it wins: pure relay/smarthost deployments with no local mailbox-hosting requirement — every message is received and immediately forwarded, never stored for IMAP access. Real system: OpenSMTPD configured purely as a relay with no local delivery table. Rejected because this project's explicit mission (§1) includes IMAP mailbox access as a first-class deliverable, not merely SMTP transport — a pure-relay design abandons half the problem statement §2 exists to teach.

39. Glossary

  • ACL: Access Control List governing shared-mailbox permissions (deferred beyond default single-owner mailboxes, §38).
  • ADR: Architecture Decision Record — this document's §9 table format.
  • ARC: Authenticated Received Chain (RFC 8617), preserves auth results across forwarders; deferred, §38.
  • BATV: Bounce Address Tag Validation — tags outgoing envelope-from to reject invalid-tag bounces; deferred, §38.
  • Bytecode budget: the per-Sieve-script execution-step cap enforced by I12.
  • CONDSTORE: IMAP extension (RFC 7162) providing MODSEQ-based conditional fetch/store.
  • DATA: the SMTP command beginning message-body transfer (section 4.1.1.4 of RFC 5321).
  • DKIM: DomainKeys Identified Mail (RFC 6376) — cryptographic message signing.
  • DMARC: Domain-based Message Authentication, Reporting, and Conformance (RFC 7489).
  • DSN: Delivery Status Notification (RFC 3464) — the bounce message format.
  • EHLO: Extended HELO — the ESMTP session-opening command advertising capabilities.
  • Envelope: the SMTP-level sender/recipient pair, distinct from message header From:/To:.
  • ESMTP: Extended SMTP, the extensible successor to plain SMTP.
  • fsck (mailbox): the em-cli mailbox fsck reconciliation sweep enforcing I14.
  • Greylisting: temporary-deferral spam mitigation exploiting the retry-tolerance gap between legitimate MTAs and spam engines (ADR-15).
  • HELO: the original (non-extended) SMTP greeting command.
  • IDLE: IMAP push-notification extension (RFC 2177).
  • IMAP: Internet Message Access Protocol (RFC 3501/9051).
  • JMAP: JSON Meta Application Protocol (RFC 8620/8621) — deferred, §38.
  • LMTP: Local Mail Transport Protocol — the local-delivery-oriented SMTP variant used by local_delivery.
  • Maildir: per-message-file mailbox storage format with tmp/new/cur atomicity (§8.4).
  • mbox: legacy single-file mailbox format lacking Maildir's atomicity (ADR-04 rejected alternative).
  • mdbox/sdbox: Dovecot's improved storage formats — deferred, §38.
  • MIME: Multipurpose Internet Mail Extensions (RFC 2045-2049).
  • MODSEQ: per-mailbox monotonic modification sequence number (I8, RFC 7162).
  • MTA: Mail Transfer Agent — an SMTP relay/receiver.
  • MUA: Mail User Agent — the end-user email client.
  • MX record: DNS record type identifying a domain's mail exchanger.
  • OAUTHBEARER: OAuth 2.0 bearer-token SASL mechanism (RFC 7628).
  • PIPELINING: SMTP extension (RFC 2920) allowing multiple commands per round-trip.
  • POP3: Post Office Protocol v3 (RFC 1939) — deferred, §38.
  • QRESYNC: IMAP quick-resync extension (RFC 7162) built atop CONDSTORE.
  • QueueEntry: the durable per-message record tracked through active/deferred/hold/bounce (§11.4, I4).
  • RCPT TO: the SMTP recipient-designation command.
  • Relay policy: the RCPT-time decision of whether to accept a message for onward delivery (I13).
  • rustls: the pure-Rust TLS implementation used in this design (ADR-03).
  • SASL: Simple Authentication and Security Layer (RFC 4422).
  • SCRAM: Salted Challenge Response Authentication Mechanism (RFC 5802).
  • Sieve: server-side mail-filtering language (RFC 5228).
  • SMTP: Simple Mail Transfer Protocol (RFC 5321).
  • SmtpState: the type-encoded SMTP session state machine (§11.2, P2).
  • SPF: Sender Policy Framework (RFC 7208).
  • STARTTLS: opportunistic in-band TLS upgrade for SMTP/IMAP.
  • Submission: authenticated SMTP on port 587 (RFC 6409), distinct trust boundary from port 25.
  • tokio: the async runtime this design is built on (ADR-02).
  • UID: stable IMAP message identifier, never reassigned within a UIDVALIDITY epoch (I7).
  • UIDVALIDITY: the epoch counter that, when bumped, signals clients to discard cached UIDs.
  • VerifyResult: the composed SPF/DKIM/DMARC outcome type (§8.7, §11.4).
