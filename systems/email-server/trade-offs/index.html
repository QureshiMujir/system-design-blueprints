Decisions (§9) · 22 ADRs

ADR-01

Language

Chosen

Rust 1.78+ MSRV

Rejected

C, Go, Java

When the rejected choice is right

Go wins when team Rust experience is near-zero and time-to-first-prototype dominates over long-run CVE risk

Why: Memory safety removes the dominant mail-server CVE class (§1)

ADR-02

Async runtime

Chosen

tokio

Rejected

async-std, glommio, raw epoll

When the rejected choice is right

glommio wins on a single-NUMA-node io_uring-only deployment optimizing p99 tail latency above all else

Why: Ecosystem maturity, rustls/hyper integration, work-stealing scheduler fits many-thousand-conn workload

ADR-03

TLS

Chosen

rustls

Rejected

OpenSSL (via FFI), native-tls

When the rejected choice is right

OpenSSL wins when FIPS-140 certified crypto modules are a hard compliance requirement

Why: Pure-Rust removes Heartbleed-class CVE surface (P11)

ADR-04

Storage format

Chosen

Maildir

Rejected

mbox, mdbox/sdbox

When the rejected choice is right

mbox wins for single-user, single-writer archival where inode count must be minimized

Why: Atomic rename crash-safety, no locking for concurrent readers (P4)

ADR-05

Mailbox metadata index

Chosen

SQLite (embedded)

Rejected

Berkeley DB, PostgreSQL (separate process), flat files

When the rejected choice is right

PostgreSQL wins at a scale needing cross-host shared index (multi-host mailbox placement, §38)

Why: Embedded, transactional, queryable for UID/MODSEQ without a separate DB process

ADR-06

Default SASL mechanisms

Chosen

PLAIN + LOGIN + SCRAM-SHA-256 + OAUTHBEARER

Rejected

CRAM-MD5-only, GSSAPI-only

When the rejected choice is right

GSSAPI wins inside a Kerberos-SSO enterprise intranet deployment

Why: Covers modern MUAs and OAuth-only providers (Gmail/Microsoft) day one

ADR-07

OAUTHBEARER support

Chosen

Included at Phase 3

Rejected

Deferred to stretch

When the rejected choice is right

Deferring wins for an air-gapped deployment with no external OAuth IdP reachable

Why: Gmail/Microsoft require it for interop; deferring blocks a large user segment

ADR-08

DKIM signing key

Chosen

Ed25519 default, RSA-2048 optional

Rejected

RSA-2048-only

When the rejected choice is right

RSA-2048 wins against legacy receivers that reject Ed25519 DKIM (a shrinking but nonzero population in 2026)

Why: 8× smaller signature, ~10× faster sign (P8, RFC 8463)

ADR-09

Sieve runtime

Chosen

Custom bytecode VM (em-sieve)

Rejected

Embed an existing scripting engine (Lua/WASM)

When the rejected choice is right

WASM wins if the product needs user-extensible filters beyond RFC 5228's action set

Why: Sandboxed, RFC-5228-scoped, no general-purpose escape surface (P9)

ADR-10

Outbound queue layout

Chosen

Four durable directories (active/deferred/hold/bounce), Postfix-style

Rejected

Single flat queue with a status column

When the rejected choice is right

A single-status-column queue wins when the queue backend is already a transactional DB (removes directory-scan cost)

Why: Crash-safe via filesystem semantics; matches operator mental model from Postfix (§5)

ADR-11

Differential test oracle

Chosen

Postfix + Dovecot (spawned in CI containers)

Rejected

No external oracle; spec-only tests

When the rejected choice is right

Spec-only wins when CI cannot run privileged containers (constrained CI runners)

Why: Catches interop bugs a spec reading misses (§5 Reference Implementations)

ADR-12

Fuzz canary duration

Chosen

24h continuous per release + 30-day soak pre-GA

Rejected

Fuzz-on-commit only (no continuous canary)

When the rejected choice is right

Commit-only fuzzing wins under tight CI budget with no soak infrastructure

Why: Catches slow-accumulating corruption (Maildir tmp/ leak class, §26)

ADR-13

Message parser tolerance

Chosen

Permissive ("trustworthy") parse, per section 1.2 of RFC 5322

Rejected

Strict RFC-only rejection

When the rejected choice is right

Strict rejection wins in a closed, fully-controlled internal-only mail system with no external senders

Why: Real-world mail from 50 years of MUAs is not always strict; rejecting loses legitimate mail

ADR-14

Submission (587) relay policy

Chosen

SASL-authenticated senders only

Rejected

Same relay policy as port 25

When the rejected choice is right

Same-policy wins only if 587 is firewalled to an already-trusted internal network (rare in practice)

Why: Distinct trust boundary (P1, I13); authenticated users get outbound relay

ADR-15

Greylisting

Chosen

Enabled by default, per-domain override

Rejected

Disabled by default

When the rejected choice is right

Disabled-by-default wins for latency-sensitive transactional-mail-only deployments where first-attempt delivery latency matters more than spam reduction

Why: Cheap, effective first-pass spam filter with near-zero false-positive on legitimate MTAs (E. Harris 2003, §5)

ADR-16

Configuration language

Chosen

Static declarative config (TOML), no embedded expression language

Rejected

Exim-style string-expansion config

When the rejected choice is right

An expression language wins for operators needing dynamic per-message routing logic beyond static rules

Why: String-expansion has been a repeated CVE source (CVE-2019-19515-class)

ADR-17

Rate limiting

Chosen

Token bucket per-IP + per-user (Bloom-filter-backed approximate counters, B. Bloom 1970)

Rejected

Exact sliding-window counters in SQLite

When the rejected choice is right

Exact counters win when false-positive rate-limit denials are legally/contractually unacceptable

Why: O(1) memory, no DB write per connection attempt (§5)

ADR-18

Bounce format

Chosen

RFC 3464 DSN, multipart/report

Rejected

Plain-text bounce message

When the rejected choice is right

Plain-text wins for a closed internal system where only humans read bounces

Why: Machine-parseable by sending MTAs' bounce-handling logic

ADR-19

Anti-relay check point

Chosen

RCPT-time (before DATA)

Rejected

DATA-time (after body received)

When the rejected choice is right

DATA-time wins if relay policy needs body content (e.g., size-based rules) to decide

Why: Rejects abuse before wasting bandwidth on the body (I13)

ADR-20

Logging format

Chosen

Structured JSON via tracing

Rejected

Plain-text log lines

When the rejected choice is right

Plain-text wins for a single-operator deployment with no log-aggregation pipeline

Why: Machine-parseable for SIEM/alerting pipelines (§27 Operational Readiness)

ADR-21

Metrics export

Chosen

Prometheus text exposition

Rejected

StatsD push

When the rejected choice is right

StatsD wins in a push-based, high-cardinality-tag environment already standardized on StatsD

CI/CD

Chosen

GitHub Actions + self-hosted runner for privileged fuzz/soak jobs

Rejected

Fully-hosted CI only

37. Alternative Architectures (Roads Not Taken)

Alt 1 — Unified single-process daemon (no SMTP/IMAP split).

        ┌─────────────────────────────────────┐
        │   single process: SMTP + IMAP +      │
        │   Maildir + index, one address space │
        └─────────────────────────────────────┘

Regime where it wins: small-to-medium single-host deployments valuing atomic operational simplicity (one process to start/stop/monitor) over independently scaling or restarting SMTP vs. IMAP. Real system: Cyrus IMAP's historical single-process-per-mailbox-operation design taken to its logical extreme. Rejected because it violates P1 (MM1) — a bug or crash in the IMAP command parser would take down mail receipt too, exactly the coupling this design's trust-boundary separation (§3) exists to prevent.

Alt 2 — Transactional-database-backed mailbox store.

   smtp/imap servers ──► RDBMS (e.g. ESE/Postgres) ──► shared storage
                          (messages as rows/blobs, not files)

Regime where it wins: deployments needing strong cross-message transactional guarantees and location-transparent multi-host access without relying on shared-filesystem semantics. Real system: Microsoft Exchange Server's ESE-based store. Rejected because it trades away Maildir's simple, dependency-free crash-safety argument (P4, MM2) for a heavyweight database dependency, and couples storage scaling to the database's scaling story rather than the filesystem's (ADR-04's rationale).

Alt 3 — Content-addressed immutable blob store.

   message bytes ──► SHA-256 ──► content-addressed blob store
                                  (dedup across users; flags external)

Regime where it wins: archival/compliance-focused deployments valuing deduplication and immutable audit trails over low-latency flag mutation. Real system: Perkeep (formerly Camlistore, Brad Fitzpatrick's personal content-addressable storage system). Rejected because content-addressing adds a hash-index lookup indirection to every read, and IMAP's frequent small mutations (flag changes, STORE, §18) fit awkwardly against a storage model optimized for immutability — Maildir's rename-based flag mutation (§8.4) is a better fit for email's actual mostly-immutable-body/ frequently-mutated-metadata access pattern.

Alt 4 — Pure relay/smarthost (no local IMAP storage at all).

   inbound SMTP ──► anti-abuse pipeline ──► outbound SMTP (forward only)

Regime where it wins: pure relay/smarthost deployments with no local mailbox-hosting requirement — every message is received and immediately forwarded, never stored for IMAP access. Real system: OpenSMTPD configured purely as a relay with no local delivery table. Rejected because this project's explicit mission (§1) includes IMAP mailbox access as a first-class deliverable, not merely SMTP transport — a pure-relay design abandons half the problem statement §2 exists to teach.
