⬜ Phase 0 — Skeleton, History Store, Append-Only Event Log & CI §12

Objectives

Stand up workflow-core types (§11), a Postgres PersistenceStore (ADR-06), a minimal append transaction enforcing gapless monotonic EventId (I2), and a CI skeleton with the replay-compatibility gate stubbed for later phases to fill.

Deliverable

cargo run --bin history-svc-skeleton accepts a StartWorkflowExecution call (stubbed transport acceptable), writes WorkflowExecutionStarted as event_id=1, and GetWorkflowExecutionHistory returns it byte-identical after a process restart.

Acceptance

Append of event_id=1 for a fresh execution completes in <20 ms p99 on local Postgres; a duplicate append at event_id=1 is rejected (I2); CI green for 3 consecutive runs; conformance/fixtures/phase0_single_event.json exists and round-trips byte-identical.

Fixtures

phase0_single_event.json — single WorkflowExecutionStarted history, expects exact byte-for-byte round trip. phase0_duplicate_event_id.json — malformed, expects rejection. phase0_gapped_event_id.json — malformed (event_id jumps 1→3), expects rejection (I2). This phase seeds the recorded-history replay corpus that becomes the single most important fixture family by Phase 11 (§28).

Pitfalls
  • Using a global Postgres sequence instead of a per-execution counter for event_id — breaks I2's per-execution gaplessness; manifestation: replay cursor desyncs; debug: compare executions.next_event_id against max(history_events.event_id); recovery: migrate to a per-execution counter.
  • Missing unique constraint on (shard_id, namespace, workflow_id, run_id, event_id) — silently permits I2 violations under concurrent writers; signal: history_append_gap_total stays zero because nothing is checking; recovery: add the constraint, audit existing rows.
  • Modeling WorkflowExecution as mutable-in-place rather than event-derived — breaks P2; manifestation: executions row diverges from the event log after a crash; recovery: rebuild executions from history_events.

⬜ Phase 1 — The Deterministic Replay Runtime And Command/Event Correlation §13

Objectives

Build WfCtx and WfExecutor (§8.2, §8.3), the #[workflow] proc-macro determinism lint (P1, P4's first layer), and the command/event comparator (I1).

Deliverable

fn hello(ctx, name) -> String calling ctx.timer(1s) then returning a formatted string, replayed twice (live, then from a serialized History) with byte-identical command sequences, verified by workflow-conformance's new replay-diff runner.

Acceptance

Replay-diff runner reports 0 mismatches across ≥5 seed fixtures; the lint fails compilation for a workflow module with a direct SystemTime::now() call (phase1_lint_reject_now.rs); WfExecutor replays a 100-event history in <10 ms (feeds §34's per-event replay-cost assumption).

Fixtures

phase1_replay_basic.json — 12-event recorded history with its expected command sequence enumerated. phase1_replay_reordered_activities.json — malformed, two activities swapped, expects NonDeterminismError. phase1_lint_reject_now.rs, phase1_lint_reject_hashmap_iter.rs — compile-time fixtures. phase1_replay_basic.json is the seed of the recorded-history replay corpus central to Phase 11.

Pitfalls
  • Implementing "deterministic" join via tokio::join! because it's stable today — diverges after a tokio version bump since stability isn't contractual (P6); debug: diff command sequences across two tokio versions in CI.
  • Comparator checking only command_type, not attributes — lets a wrong-activity-under-right-type slip through; recovery: add attribute-hash comparison.
  • Waker registry keyed only by CommandType, not (CommandType, seq) — two concurrent activities resolve to the wrong waker; recovery: add seq to the key.
  • Determinism violation from HashMap iteration inside a workflow's own retry-tracking — surfaces only under load, not single-threaded dev testing; debug: fuzz with randomized HashMap seeds across replay attempts (feeds Phase 11 fuzzing); recovery: BTreeMap per §8.3.

⬜ Phase 2 — Workflow Task Dispatch And The Matching Service §14

Objectives

Introduce workflow-matching-svc with in-memory task-queue rings (ADR-10), long-poll dispatch (ADR-11), the task-token scheme (§8.11) fencing I3, and full shard hashing with leased ownership fencing (P5, I9, ADR-07) now that history splits from a single process into a routable, sharded service.

Deliverable

Independent history-svc and matching-svc processes plus a worker binary polling matching, replaying via WfExecutor, and completing end-to-end over gRPC — demonstrated on examples/order-fulfillment (activities still stubbed instant-complete).

Acceptance

p50 workflow-task dispatch latency <15 ms on a local 3-process setup (M3, non-sticky); a duplicate RespondWorkflowTaskCompleted with a stale token is rejected in 100% of 1,000 trials (I3); zero cross-queue delivery across a 2-queue, 2-worker-pool test; killing one of two history processes reassigns its shards to the survivor within 10 s with zero duplicate writes across the handoff (I9).

Fixtures

phase2_duplicate_token.json; phase2_wrong_queue_delivery.json — asserts task-for-A never reaches a poller-on-B; phase2_long_poll_timeout.json — clean timeout, no connection leak; phase2_shard_fencing_stale_writer.json — a killed-then-recovered old owner attempts a write after losing its lease, expects rejection via range_id mismatch (I9).

Pitfalls
  • Trusting a client-supplied queue name without namespace-scoping it — cross-namespace task leakage (feeds T4); recovery: namespace-scope every queue key.
  • Task tokens without an HMAC — forgeable, any caller can complete any task (T3); recovery: sign before this phase's demo is called done.
  • Expecting matching-svc to survive a restart with tasks intact — it can't (P2 applies to queue contents too); recovery: history's re-schedule-on-no-poller fallback, documented as expected, not a bug.
  • Omitting the range_id guard on any single write path "just this once" — the one unfenced write path is exactly where split-brain corruption enters; recovery: audit every UPDATE/INSERT against history_events/executions/timers for the guard, no exceptions (P5, I9).

⬜ Phase 3 — Activity Execution With At-Least-Once Delivery §15

Objectives

Introduce ActivityTask dispatch through a second matching queue type, at-least-once delivery (P3, ADR-14), and activity_info persistence (I8).

Deliverable

examples/order-fulfillment's charge activity runs in a genuinely separate OS process with a simulated 2-second delay, while the workflow process correctly suspends and resumes around it.

Acceptance

An activity worker killed mid-execution yields exactly one eventual ActivityTaskCompleted after redelivery (fixture-verified, not just "it retried"); I7 holds under a close-vs-dispatch race with zero dispatches to the closed execution across 500 trials.

Fixtures

phase3_worker_crash_midactivity.json — kills the worker post-ActivityTaskStarted, pre-completion, expects redelivery and a single terminal event (I8). phase3_dispatch_to_closed_execution.json — race fixture, expects zero deliveries (I7). phase3_unknown_scheduled_id.json — malformed, ActivityTaskCompleted references an absent activity_id, expects rejection (§8.14).

Pitfalls
  • Running the activity synchronously inline in the workflow process (the natural first shortcut) — breaks the crash-recovery model entirely (P3); must be caught in review.
  • Not persisting activity_info before matching-queue insertion — a crash between "decided to schedule" and "recorded" loses duplicate-scheduling detection on recovery; recovery: same transaction as the ActivityTaskScheduled append.
  • Two workers both picking up a redelivered task after a timeout that was just slow, not dead — this is the expected duplicate-activity-execution class (P3), not a bug; document prominently.

⬜ Phase 4 — Timeouts, Retries And Heartbeating §16

Objectives

Implement the full TimeoutSpec (schedule-to-start, start-to-close, schedule-to-close, heartbeat — ADR-15), RetryPolicy (ADR-16), and heartbeat-driven resumable activities (§8.7).

Deliverable

An activity failing on attempts 1–3, succeeding on attempt 4, with exponential backoff visible in the resulting History timeline; a long-running activity heartbeating every 6 s against a 30 s heartbeat_timeout that survives past its (much longer) start_to_close_timeout, demonstrating the two timeouts are independent.

Acceptance

Retry backoff intervals match backoff_coefficient within 5% across 20 trials; a fixture with start_to_close=300s, heartbeat_timeout=5s, and a worker that stops heartbeating at t=10s times out at ~t=15s, not t=300s; activity_id remains stable across all retry attempts in 100% of fixture runs.

Fixtures

phase4_retry_backoff_4_attempts.json; phase4_heartbeat_independent_timeout.json; phase4_non_retryable_error_no_retry.json — asserts an error in non_retryable_errors short-circuits retry; phase4_schedule_to_close_caps_total_retry_time.json.

Pitfalls
  • Resetting activity_id on retry — breaks history audit continuity and I8's per-attempt-group bookkeeping; the attempt counter is separate from identity, never conflate them.
  • Heartbeat-deadline reset racing a genuine ActivityTaskTimedOut append — a heartbeat arriving 1 ms after the timeout append must be rejected, not resurrect a timed-out activity; fixture-verified.
  • Computing backoff without jitter — synchronized retry storms across executions that failed at the same moment; recovery: jitter per Nygard's stability-pattern guidance (§5).

⬜ Phase 5 — Durable Timers §17

Objectives

Promote the Phase 0 timer table into a first-class shard-owned timer service (§8.7) meeting the §4 precision/skew bound (I5, P7).

Deliverable

10,000 workflows each start a 1-hour timer over a 60-second start window; all fire within the ±150 ms p99 skew bound of §4, verified by a benchmarks/ load-test harness.

Acceptance

p99 timer skew ≤150 ms across the 10,000-timer load test; zero early fires across 1,000,000 fuzzed timer-fire events; a canceled timer never fires across 10,000 cancel-then-wait trials.

Fixtures

phase5_10k_timer_load.json (load-test descriptor); phase5_early_fire_stress.json — fuzzed clock-skew injection, expects zero early fires; phase5_timer_cancel_race.json — cancel racing fire, expects deterministic resolution per §8.2's ordering rule.

Pitfalls
  • A shared deadline across many executions ("everyone times out at midnight") saturating the reaper — the canonical timer-storm failure mode; mitigated by jitter plus the timer-storm-mitigation.md runbook (§26).
  • Polling with a too-coarse interval to save CPU — directly inflates skew past the §4 bound; 100 ms is a hard constraint, not a tuning knob, absent a §4 revision.
  • Deleting the timer row before confirming the TimerFired append committed — a crash in between loses the timer entirely, violating I5; recovery: single transaction, never split.

⬜ Phase 6 — Signals And Queries §18

Objectives

Implement SignalWorkflowExecution and QueryWorkflow (§8.8), buffered-signal ordering (I10), and query-must-not-mutate enforcement (P10, I11).

Deliverable

A workflow waiting on an "approve" signal for up to 24 hours (timer/signal race via Phase 1's deterministic select) exposing a status query returning "pending"/"approved" without ever appending an event when queried.

Acceptance

10,000 signals sent within 1 second while the workflow is mid-task are all delivered, in send order, with zero loss (I10); a query handler attempting ctx.activity(...) is rejected with QueryMutationError in 100% of trials; SignalWithStart against a non-existent workflow starts it and delivers the signal atomically across ≥1,000 concurrent-race trials with zero lost signals.

Fixtures

phase6_10k_signal_burst.json; phase6_query_mutation_attempt.json — expects rejection; phase6_signal_before_start_race.json; phase6_signal_to_closed_execution.json — malformed, expects ExecutionClosedError, not buffering (§8.14).

Pitfalls
  • Applying signals to history immediately while a task is Started — races with the in-flight task's own decisions; mitigation is buffer-then-merge (I10), not immediate application.
  • Letting query handlers read mutable statics or call activities "just this once" — the query-must-not-mutate rule (P10) has no exceptions; enforce structurally via a distinct read-only WfCtx type, not convention.
  • Losing a signal sent in the gap between "not found" and "just started" — the race SignalWithStart exists to close; a naive two-call client pattern loses signals under load.

⬜ Phase 7 — Cancellation And Termination Semantics §19

Objectives

Implement cooperative cancellation (RequestCancelWorkflowExecution, ctx.is_cancelled(), ADR-17) and administrative termination, completing the execution state machine (§8.6).

Deliverable

A workflow that, on observing cancellation, cancels its in-flight activity, runs a short cleanup activity, then completes as Canceled — contrasted with an administrative Terminate against a separate, unresponsive workflow that closes immediately with no cleanup.

Acceptance

ctx.is_cancelled() returns true within one workflow task of a RequestCancel append in 100% of trials; Terminate closes an execution in <50 ms regardless of workflow-code state; an activity ignoring its cancel flag runs to its normal terminal state (documents ADR-17's cooperative-only guarantee) rather than being force-killed.

Fixtures

phase7_cooperative_cancel_with_cleanup.json; phase7_terminate_bypasses_workflow_code.json; phase7_activity_ignores_cancel_flag.json — asserts normal completion under the cooperative-only contract.

Pitfalls
  • Implementing Terminate by trying to signal the workflow first — defeats its purpose as the "this workflow is hung" escape hatch; Terminate must never depend on workflow code responding.
  • Assuming activity cancellation is forceful — it is not (ADR-17); an activity that never checks its cancel flag runs to completion.
  • Racing a cancel-observed cleanup activity against a concurrent normal-path activity completing — needs the same deterministic-ordering discipline as any concurrent command (P6).

⬜ Phase 8 — Child Workflows And Continue-As-New §20

Objectives

Implement ChildWorkflowRef (§8.9), ctx.child::<W>(), parent-child cancellation policies, and continue-as-new (ctx.continue_as_new, I6, P8).

Deliverable

A parent workflow starting 5 children in parallel via deterministic join, waiting for all, aggregating results; a separate "infinite" workflow processing one item per minute that continues-as-new every 1,000 iterations, run long enough to show history staying bounded across many runs.

Acceptance

Parent-cancel with RequestCancel policy delivers a cancel request to all 5 open children within one workflow task; continue-as-new's new-run history never exceeds 1,000 events at any iteration boundary across a 10,000-iteration soak; WorkflowId continuity holds across ≥50 continue-as-new hops in a single fixture chain (I6).

Fixtures

phase8_five_children_parallel_join.json; phase8_parent_cancel_propagation_terminate_policy.json; phase8_continue_as_new_history_bound.json — asserts event count resets at each hop; phase8_continue_as_new_workflow_id_continuity.json.

Pitfalls
  • Treating continue-as-new like a function call and executing code after it — the run terminates at that command (P8); a lint should flag unreachable code following ctx.continue_as_new.
  • Child-completion events not carrying enough for the parent to resume across its own continue-as-new — documented limitation: a child started before a continue-as-new cannot be awaited across that boundary; parents must drain children first.
  • Unbounded history growth from a loop that never continues-as-new — the canonical failure named in the phase arc; mitigation is the SDK's soft-warn threshold plus documentation, since the split point is an application decision the engine cannot force.

⬜ Phase 9 — Versioning And Patching For Safe Code Change §21

Objectives

Implement ctx.patched(change_id) (§8.10, P11, I13), marker-based version branching, and the operational discipline for safely retiring old branches (§27).

Deliverable

Version 1 (charge→ship) and version 2 (if ctx.patched("add-validation") { validate() } inserted) running concurrently against the same worker fleet: pre-v2 in-flight executions take the old path on every replay, new executions take the new path, both complete correctly.

Acceptance

0 NonDeterminismErrors across 200 pre-v2 in-flight executions replayed post-deploy; 100% of new-start executions take the v2 path; workflowctl patches status add-validation correctly reports 0 remaining pre-v2 open executions once drained, verified against visibility ground truth.

Fixtures

phase9_patch_old_execution_takes_old_path.json; phase9_patch_new_execution_takes_new_path.json; phase9_patch_removed_early_breaks_replay.json — deliberately-malformed, simulates premature guard removal, expects NonDeterminismError.

Pitfalls
  • Removing a patched() guard before all pre-deploy executions have drained — the single most damaging versioning mistake (§27); the CLI drain-check is mandatory process, not optional.
  • Moving a patched() call to a different code position between deploys without removing it — changes its position in command/event correlation and can itself cause NonDeterminismError.
  • Treating change_id strings as disposable — a typo across a deploy creates an unrelated second marker instead of matching the intended one; change_ids are part of the public compatibility surface (§27).

⬜ Phase 10 — Sticky Caching, Visibility Indexing And Multi-Tenant Namespaces §22

Objectives

Implement sticky execution caching with build-id-bound invalidation (P12, I12, ADR-12), the visibility indexer (I14, ADR-21, ADR-24), and namespace/quota enforcement (P13, ADR-22, ADR-23).

Deliverable

A workflow with 100 events of history showing <10 ms decision latency on sticky vs. >50 ms on forced fallback; workflowctl list --namespace acme --state Running --type OrderFulfillment --start 1d returning correct results within the §4 visibility-lag bound; a namespace with max_starts_per_second=10 correctly rejecting its 11th start within the same second.

Acceptance

Sticky-cache hit ratio ≥90% (§4) in a steady-state 1,000-workflow soak; visibility index lag p99 ≤2 s (§4); namespace quota rejection rate equals exactly the excess over the configured limit across 10 trials at 2× the configured rate; a worker deploy bumping build_id results in 100% cache eviction for that worker's prior entries (I12).

Fixtures

phase10_sticky_hit_latency.json; phase10_sticky_fallback_on_timeout.json; phase10_build_id_invalidation.json; phase10_visibility_lag_bound.json; phase10_namespace_quota_rejection.json; phase10_cross_namespace_isolation.json — asserts a namespace-A query never returns namespace-B executions.

Pitfalls
  • Binding sticky-cache validity to wall-clock time or deploy timestamp instead of build_id — a redeploy with an unchanged build_id (a real CI misconfiguration) silently keeps stale caches alive; CI must fail a release that doesn't bump build_id (P12).
  • Computing visibility synchronously in the append path "for simplicity" — reintroduces exactly the coupling ADR-24 rejected, turning visibility into a durability risk instead of an eventually-consistent view.
  • Enforcing quotas only at history/matching, after the request already consumed shared capacity — must be enforced at the frontend (P13), or one tenant still starves others despite the quota existing.
  • Sticky-cache staleness surviving a partial worker restart (process restarts but an old executor instance lingers in a thread pool) — named explicitly in the phase-arc brief; mitigation: key the cache by build_id plus a per-process-start nonce, not build_id alone.

⬜ Phase 11 — Conformance Replay Corpus, Chaos And Perf Hardening §23

Objectives

Assemble the recorded-history replay corpus as a permanent CI gate (§28), run the full chaos suite, and hit the §4/§30 performance targets, producing a release-candidate build.

Deliverable

A green replay-gate.yml run against a ≥50-history corpus, a 12-hour chaos soak with zero correctness violations logged, a perf report meeting every §4/§30 target, and a signed, SemVer-tagged release candidate.

Acceptance

0 replay mismatches across the full corpus; 0 duplicate-completion events, 0 lost workflows, 0 double-decisions across the 12-hour chaos soak; p99 workflow-task dispatch latency ≤250 ms sustained at 500 starts/sec for the soak's final 2 hours (M5); fuzz targets run ≥1,000,000 iterations each with 0 crashes.

Fixtures

phase11_full_corpus_manifest.json — enumerates every fixture from Phases 0–10 plus new production-shape recordings; phase11_chaos_12h_soak.json — soak descriptor with fault-injection schedule; phase11_perf_targets.json — machine-checkable §4/§30 thresholds consumed by the perf harness.

Pitfalls
  • Treating the replay corpus as a one-time Phase 11 artifact rather than a permanently-growing CI gate — every production incident from this point forward should add a corpus entry, or the corpus stops earning its keep.
  • Running chaos tests only against happy-path shapes already covered by earlier fixtures — chaos value comes from combining fault injection with each phase's N.8 edge cases (e.g., killing a worker specifically during sticky-cache staleness, not just any random moment).
  • Declaring performance targets met from a single clean run rather than a sustained soak's tail — tail-latency regressions (Dean & Barroso 2013) hide in short benchmarks and appear only under sustained load.
