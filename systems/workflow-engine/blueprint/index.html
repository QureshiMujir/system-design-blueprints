Project Number: 163

Project Name: Workflow / Durable Execution Engine

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

This blueprint specifies a from-scratch, Temporal-class durable execution engine in Rust: application programmers author workflow control flow as ordinary imperative async code, and the engine makes that control flow durable across process crashes, worker redeployments, and multi-year executions via event-sourced deterministic replay (Schneider 1990). Every observable decision a workflow function makes — start an activity, start a timer, spawn a child workflow, signal, complete — is recorded as a HistoryEvent in an append-only per-execution History (I2); recovery is not snapshot restoration, it is re-executing the workflow function from the start against that History, with already-recorded results replayed rather than re-performed (P1). The engine is a cluster of a stateless frontend, a sharded history service, and a matching service, backed by a persistence layer (ADR-06), fronted by a client/starter API and paired with an embedded worker SDK hosting the deterministic replay runtime (§3).

Phase-0 deliverable — crates:

  1. workflow-core — HistoryEvent/EventType/Command/CommandType/WorkflowExecution types; no I/O.
  2. workflow-persistence — PersistenceStore trait plus Postgres implementation (events, executions, timers, activity_info, visibility tables).
  3. workflow-history-svc — shard ownership, mutable-state cache, transactional history append, timer-loop skeleton.
  4. workflow-matching-svc — in-memory task-queue rings, long-poll gRPC endpoints.
  5. workflow-frontend-svc — gRPC gateway, authn/authz, rate limiting, request routing.
  6. workflow-sdk-core — WfCtx, WfExecutor (deterministic replay runtime), #[workflow]/#[activity] proc-macros.
  7. workflow-sdk-worker — poller loops, sticky cache, activity task handler.
  8. workflow-cli — workflowctl for start/signal/query/list/reset.
  9. workflow-conformance — replay-corpus harness, fixture runner (scaffolded Phase 0, load-bearing by Phase 11).

Boundaries. Provides: history/event log, workflow and activity task queues and dispatch, deterministic replay runtime, durable timers, signals/queries, child workflows/continue-as-new, versioning/patching, sticky caching, visibility, namespaces/quotas. Delegates: business-logic execution to activity implementations (arbitrary Rust calling real systems), transport security to mTLS/JWT at the frontend (RFC 7519), cross-cluster replication (PhaseDeferred("Comparative Architecture")), UI to CLI plus OpenTelemetry. Does not provide: a declarative-DSL runtime (ADR-04), a general-purpose message queue (task queues exist solely to move WorkflowTask/ActivityTask between matching and workers), compensating-transaction orchestration as a primary abstraction.

Non-goals. Not a DAG batch scheduler like Apache Airflow — Airflow schedules independent tasks per DAG run with no in-workflow control flow or replay; here the workflow function is a single continuously-executing logical thread of control (§36). Not a general queue. Not a saga coordinator: sibling blueprint #97 Saga / Workflow Coordinator specifies compensating-transaction orchestration across services (Garcia-Molina & Salem 1987) as its primary model; this blueprint's load-bearing concerns are the determinism contract (P1, §8), history-versus-code compatibility (§27), and exactly-once effect semantics layered on at-least-once delivery (P3, I8) — not compensation. A workflow here can implement saga-style compensation as ordinary activity calls in a try/catch shape, but that is an application pattern, not an engine primitive.

Deployment model. A service cluster (frontend, history, matching — independently scalable, §3.1) backed by a persistence layer, plus an embedded worker SDK that customer processes link against and run alongside business logic. Operators run the cluster; application teams embed the SDK.

Users/operators. Workflow authors (#[workflow]/#[activity] authors), cluster operators (SRE running history/matching/frontend and Postgres), and visibility consumers (dashboards, support tooling).

What later phases unlock. Phase 1 (replay runtime) unlocks any workflow logic. Phase 2 (matching) unlocks horizontal worker scaling. Phase 3 (activities) unlocks real side-effecting work. Phases 4–5 (timeouts/retries, timers) unlock production reliability. Phase 6 (signals/queries) unlocks external interaction. Phase 7 (cancellation) unlocks safe teardown. Phase 8 (child workflows/continue-as-new) unlocks composition and unbounded-duration workflows. Phase 9 (versioning) unlocks safe rolling deploys. Phase 10 (sticky/visibility/namespaces) unlocks multi-tenant production operation. Phase 11 (conformance/chaos/perf) unlocks a release candidate.

Rust + rationale. No GC pauses in the latency-sensitive history-append and matching hot paths; the ownership system statically prevents a workflow-context handle from being smuggled into a spawned OS thread (a determinism hazard, P1); tokio drives server-side I/O concurrency while workflow code runs on a wholly separate, non-tokio, single-threaded executor (ADR-02) — Rust's !Send markers enforce this boundary at compile time. Rejected: Go (Temporal's own implementation language — avoided here specifically to get compile-time determinism enforcement Go's simpler type system can't provide); Java (GC pause tail latency antagonizes the p99 dispatch targets of §4); Erlang/Elixir (strong actor-supervision fit, weaker 2026-era ecosystem maturity for this persistence/protobuf/gRPC stack).

Prerequisites. Working async Rust (Send/Sync, Future, pinning), Postgres transactions and row locking, gRPC/protobuf, the event-sourcing/CQRS pattern family (Fowler articles; Kleppmann DDIA ch. 11).

Timeline. Phase 0 ~3 weeks; Phases 1–3 ~3 weeks each (Phase 1, the replay runtime, is the long pole); Phases 4–9 ~2 weeks each; Phase 10 ~3 weeks; Phase 11 ~4 weeks (conformance corpus + chaos). ~30 weeks single-engineer full-time.

Deferrals. PhaseDeferred("Comparative Architecture") — multi-region active-active replication. PhaseDeferred("Alternative Architectures (Roads Not Taken)") — a declarative-DSL authoring mode. PhaseDeferred("Compatibility & Versioning") — cross-cluster namespace migration. PhaseDeferred("Operational Readiness") — a web UI beyond CLI + OpenTelemetry.

2. Why Build This

  • Durable execution as a distributed-systems primitive, not an API to consume.
  • Event sourcing / CQRS applied to control flow, not just data (Fowler; Young; Kleppmann DDIA ch. 11).
  • Deterministic replay as a from-scratch discipline (Schneider 1990), not inherited from a framework.
  • Exactly-once effect semantics layered on at-least-once delivery (Helland 2007).
  • Shard ownership, leader election, fencing tokens at cluster scale (Ongaro & Ousterhout 2014).
  • Sticky caching and cache-invalidation-on-deploy as a real production hazard.
  • Versioning long-running in-flight state against evolving code (Barga et al. 2004).
  • A from-scratch Rust systems build spanning proc-macros, a custom executor, sharded storage, and a matching service.

What Mastery Looks Like

  • You can explain why a workflow's HashMap iteration order is a correctness bug, not a style nit (Phase 1, §8 determinism contract).
  • You can design a task-token scheme that survives shard reassignment without forgery (Phase 2, ADR-07).
  • You can reason about why activities need four separate timeouts, not one (Phase 4, §8 timeout model).
  • You can implement continue-as-new and explain, with §34's arithmetic, why unbounded history is a Big-O correctness bomb, not merely an efficiency concern (Phase 8, §31).
  • You can write a patched() guard and reason about which in-flight histories break if it is removed early (Phase 9, §27).
  • You can distinguish sticky-cache staleness from a genuine determinism violation during a production incident (Phase 10, FM-6).
  • You can run a replay-compatibility CI gate against a corpus of recorded histories and explain why it is the industry-standard regression test for this system class (Phase 11, §28).

Client/starter SDK. Tenant-facing entry point (trust boundary A); issues StartWorkflow, SignalWorkflowExecution, QueryWorkflow, RequestCancelWorkflowExecution, ListWorkflowExecutions. Never touches history directly.

Frontend service. Stateless gRPC gateway; authn/authz, per-namespace rate limiting (ADR-23), routes each RPC to history or matching by shard/queue lookup. The sole crossing of protocol boundary 1.

History service. Sharded (§3.2); owns the event log and denormalized mutable execution state per execution; runs the timer service as a per-shard poll loop; the only writer of its owned shards (trust boundary B, fenced by range_id, P5/I9).

Matching service. Holds in-memory workflow-task and activity-task queues; long-polls from workers; stateless with respect to durable data — durable truth always lives in history (P2).

Persistence layer. Postgres tables for events, executions, timers, activity_info, visibility (ADR-06); the sole persistence boundary (boundary 2) — every durability guarantee in this document reduces to a transaction committed here.

Worker SDK. Embedded in tenant processes; hosts the deterministic replay runtime (WfExecutor, concurrency boundary D — single-threaded, non-tokio) for workflow-task handling, plus an activity-task handler that runs arbitrary (trust boundary C, untrusted relative to the cluster) tenant code with real tokio concurrency; maintains the sticky cache (build-id bound, P12).

Visibility indexer. Consumes committed history/execution-state changes asynchronously and denormalizes into the visibility store (I14); never a write path for control decisions.

3.1 Why Three Services, Not One

Ship as a monolith through Phase 5; split when matching's long-poll bookkeeping load and history's transactional-write load start contending for the same process's resources — not before. In steady state: frontend scales horizontally without coordination; history scales by adding shards and processes, bounded by lease coordination overhead (§31); matching scales by adding queue-serving replicas per task queue.

3.2 Sharding Strategy

Hash (namespace, workflow_id) into a fixed shard count (512 at GA, ADR-07). Each shard has exactly one owning history process at a time, elected via a lease with a monotonic range_id fencing token (Ongaro & Ousterhout 2014's term-based reasoning applied to storage writes). Ownership is required because history append must be linearized per workflow, timer firing must not double-fire, and the in-memory mutable-state cache needs a single home.

3.3 Data Flow For One Workflow Task

A worker long-polls a workflow-task queue on matching. When history schedules a task (because a triggering event was appended), matching hands it to a waiting poller. The worker fetches history (sticky cache, or full fetch from history service), replays, emits new commands, calls RespondWorkflowTaskCompleted. History validates commands against current state (I1), appends events transactionally, schedules follow-on work (timers, activity tasks, child-workflow starts), and notifies matching to enqueue the resulting activity tasks. This round trip is one workflow task; most workflows are a sequence of these separated by activity execution or timer waits.

6. Design Principles

P1 — Workflow code is a pure function of its history. Any wall-clock read, RNG call, non-deterministic map iteration, or direct network/file I/O performed outside WfCtx is a determinism violation; the SDK supplies a durable substitute for each (ctx.now(), ctx.random(), ctx.activity(), sorted iteration). Tradeoff: authors give up "plain Rust" for a constrained dialect. Operational implication: a compile-time lint (Phase 1) plus a runtime command/event comparator (I1) are both required — the lint alone misses nondeterminism hidden behind trait objects. Violating it: replay silently diverges from the original run until the comparator trips NonDeterminismError.

P2 — The history is the system of record; the in-memory workflow object is a discardable cache. No state is durable unless appended as a HistoryEvent and committed. Tradeoff: every meaningful decision costs at least one durable write. Operational implication: sticky cache (Phase 7) is an optimization, never a correctness path. Violating it: a crashed worker loses decisions never durably recorded, and recovery replays a shorter, wrong history.

P3 — Activities are at-least-once; exactly-once effect is a cooperative contract. The engine guarantees at-least-once dispatch and exactly-once durable recording of a completion, but cannot prevent an activity function from running twice against the outside world (Helland 2007). Tradeoff: idempotency work is pushed onto activity authors. Operational implication: the SDK offers an idempotency-key helper but cannot enforce its use. Violating it: undetectable duplicate side effects (FM-7).

P4 — Determinism enforcement is layered: lint, runtime comparator, conformance corpus. No single layer suffices (Schneider 1990). Tradeoff: three mechanisms cost more than one. Operational implication: the Phase 11 replay corpus is a release gate. Violating it: a lint-only strategy ships production nondeterminism.

P5 — A shard is the unit of ownership, exclusive at every instant. Exactly one history process may mutate a shard's executions at a time, enforced by a monotonic fencing token (range_id, Ongaro & Ousterhout 2014). Tradeoff: reassignment causes brief unavailability for affected executions. Operational implication: every write needs a WHERE range_id = $lease guard. Violating it: silent split-brain corruption (I9, FM-4).

P6 — Commands and events correlate by emission order, not value alone. The Nth command a run emits must correspond to the Nth matching-type history event. Tradeoff: reordering independently-deterministic operations via a non-deterministic combinator is still unsafe. Operational implication: the SDK provides deterministic select/join combinators that poll in declaration order. Violating it: two individually-fine activities mismatch on replay if issued via ordering-nondeterministic concurrency.

P7 — Timers fire at-least-once and never before their deadline. Poll interval trades latency for shard load. Tradeoff: a 100 ms interval bounds skew but runs the shard timer loop continuously. Operational implication: timer storms (shared deadlines) need jitter smoothing. Violating it: an early-fired timer lets a workflow race ahead of a business deadline.

P8 — Continue-as-new is return plus start, not a function call. It terminates the current run's history and starts a fresh run under the same WorkflowId with a new RunId; nothing after the call executes. Tradeoff: state to carry forward must be passed explicitly as the new run's input. Operational implication: unbounded logical lifetimes are supported by design, bounded runs are not optional. Violating it (treating it as a call): dead code after continue-as-new, invisible until an incident.

P9 — A completed activity's result is durable before the workflow task consuming it is dispatched. Tradeoff: adds a serialization point to the completion path. Operational implication: without this order a crash can strand a workflow expecting an unrecorded result. Violating it: breaks I4, stranding replay.

P10 — Queries must not mutate history. Query handlers may read workflow-local state but may not call any command-emitting primitive. Tradeoff: query handlers are more restricted than signal handlers. Operational implication: query dispatch runs against a read-only WfCtx view. Violating it: a "read" silently changes future replay behavior (I11).

P11 — Versioning branches on a recorded marker, not on deploy time. ctx.patched(change_id) records MarkerRecorded on first evaluation per run; replay returns the recorded branch regardless of currently-deployed code. Tradeoff: change_ids are permanent forks until every pre-change history has drained. Operational implication: removing a guard is only safe after a visibility query confirms zero open executions predate the version (§27). Violating it: NonDeterminismError storms across every pre-deploy in-flight execution.

P12 — Sticky cache validity is bound to worker build identity. A build-id mismatch invalidates the cache unconditionally. Tradeoff: every deploy must mint a new build id or stale caches persist silently. Operational implication: CI must fail a release that doesn't bump build id. Violating it: sticky cache poisoning (FM-6).

P13 — Namespaces are the unit of isolation, quota, and blast radius. Executions, task queues, and visibility records are namespace-scoped; cross-namespace reads are a distinct, audited operation. Tradeoff: some conveniences (global search) need an explicit admin path. Operational implication: NamespaceQuota is enforced at the frontend before reaching history/matching. Violating it: one unbounded tenant starves shared shard/matching capacity (T6).

P14 — Payloads are opaque bytes to the engine. History storage, replay, and visibility indexing operate on Payload (bytes plus a content-type tag) without deserializing into application types except at the SDK boundary. Tradeoff: search attributes must be explicitly promoted by the workflow author. Operational implication: encryption-at-rest (T7) is transparent to persistence because it never parses payload contents. Violating it: an engine that inspects payloads for convenience becomes a processor of arbitrary tenant PII, needlessly expanding the threat surface.

I3 A workflow task is processed by exactly one worker at a time, fenced by task token + run id concurrent replay corrupts sequencing task-token validation on RespondWorkflowTaskCompleted (Phase 2) stale/duplicate token rejected duplicate_task_completion_total second response rejected; task retried from current state
I4 A completed activity's result is recorded before its workflow task is dispatched P9 transactional append ordering (Phase 3) causal-predecessor check on WorkflowTaskScheduled activity_result_ordering_violation_total reorder at append; reject out-of-order scheduling
I5 A durable timer fires at least once, never before its deadline P7 shard timer-poll loop (Phase 5) fire_time <= now() guard on read timer_skew_ms histogram late fire tolerated within skew bound; early fire caught by fixture
I6 Continue-as-new preserves WorkflowId while resetting the history (RunId) P8; callers must find "the workflow" across runs ContinueAsNew handling (Phase 8) WorkflowId continuity check on ContinuedAsNew continue_as_new_total none if held; visibility loses continuity otherwise
I7 No activity is dispatched for an execution that has already closed avoids wasted work and visibility corruption matching dispatch check vs. mutable state (Phase 3) execution-state lookup before delivery dispatch_to_closed_execution_total drop task, log, alert if nonzero
I8 Every ActivityTaskScheduled has exactly one terminal event activity-info bookkeeping needs a single terminal transition activity-info state machine (Phase 4) double-terminal write rejected activity_double_terminal_total reject second write; first wins
I9 A shard has at most one owner at any instant, fenced by a monotonic token P5 lease table + range_id check on every write (Phase 6) write rejected on stale range_id fencing_rejection_total rejected owner releases and re-acquires lease
I10 Signals during an in-flight workflow task are buffered and applied in arrival order before the next task lost/reordered signals corrupt logic silently buffered_events table + task-completion transaction (Phase 6) buffered-event count reconciliation buffered_signal_count replay buffered events in recorded order
I11 Query handlers never emit commands; a query never advances history P10 read-only WfCtx view for query dispatch (Phase 6) attempted command emission raises QueryMutationError query_mutation_attempt_total reject query response; log for audit
I12 Sticky cache entries invalidate whenever worker build id changes P12 worker cache admission check (Phase 7) build-id mismatch on sticky pickup sticky_cache_invalidation_total fall back to full replay
I13 A recorded version marker is immutable for the life of its run P11 MarkerRecorded append semantics (Phase 9) re-evaluation returns cached marker, never "current" version version_marker_total by change_id none — read of durable state
I14 Visibility never shows state more advanced than the last committed event prevents acting on data ahead of durable truth indexer consumes only committed events (Phase 10) lag metric vs. append timestamp visibility_lag_ms indexer replays from checkpoint cursor

Debugging methodology. For a suspected violation, pull the full History for the affected (namespace, workflow_id, run_id), replay it offline against the exact worker build id recorded in its events, and diff the resulting command sequence against the persisted event sequence. This single offline-replay-and-diff procedure exercises I1, I2, I4, I6, I8, I10, and I13 simultaneously, because each is expressed as an assertion somewhere along that path.

8.7 Timer And Heartbeat Models

A durable timer is a row (shard_id, fire_time, workflow_id, run_id, timer_id); the owning shard's poll loop (100 ms interval, I5/P7) converts an expired row into TimerFired plus WorkflowTaskScheduled, transactionally. Heartbeats: an activity worker sends heartbeat_details at 20% of heartbeat_timeout; the server resets the heartbeat deadline on receipt and persists heartbeat_details in activity_info so a retried attempt resumes from the last checkpoint rather than from scratch; a missed heartbeat_timeout produces ActivityTaskTimedOut{timeout_type: Heartbeat}.

8.8 Signal And Query Semantics

Signals are async and durable: WorkflowExecutionSignaled is appended and dispatched to the registered SignalChannel; signals arriving while a workflow task is in flight are buffered (I10) and applied in arrival order before the next task. Queries are synchronous and side-effect-free (P10, I11): no event is appended; the handler runs against a read-only WfCtx view of current (or sticky-cached) state; the query-must-not-mutate rule is enforced by disallowing every command-emitting primitive inside a registered query handler.

8.9 Child-Workflow And Continue-As-New Linkage

ChildWorkflowRef carries the child's (namespace, workflow_id, run_id) and the parent's initiating event id; a parent-child cancellation policy (ABANDON / REQUEST_CANCEL / TERMINATE) governs propagation on parent cancellation. Continue-as-new links two runs by a one-way back-pointer only: the old run's WorkflowExecutionContinuedAsNew carries new_run_id; the new run's WorkflowExecutionStarted carries continued_from_run_id. A run's own history never spans a continue-as-new boundary (I6).

8.14 Malformed-Input And Failure-Path Examples

  • Replay command mismatch: replay emits ScheduleActivity("ship") where history's next event is ActivityTaskScheduled{type:"charge"} → NonDeterminismError, task failed (I1).
  • Activity result for unknown scheduled id: RespondActivityTaskCompleted references an activity_id absent from activity_info → rejected at the persistence boundary, corruption alarm raised.
  • History gap: append encounters a requested event_id that skips ahead of next_event_id → rejected (I2); shard recovery pauses pending manual repair.
  • Duplicate event id: append targets an already-used event_id → rejected at the unique-key constraint (I2).
  • Signal to closed execution: SignalWorkflowExecution targets a closed execution → rejected with ExecutionClosedError, not buffered (contrast with I10, which only applies to open executions).
  • Failure-path example: a workflow task fails determinism (I1) → WorkflowTaskFailed → retried up to 5 attempts → still fails → execution flagged task-failure-stuck → operator uses ResetWorkflowExecution to roll back to the last known-good event and resumes from there (§27).

  • Implementing "deterministic" join via tokio::join! because it's stable today — diverges after a tokio version bump since stability isn't contractual (P6); debug: diff command sequences across two tokio versions in CI.

13.7 Performance Concerns

13.8 Edge Cases

A workflow emitting zero commands before completing; a workflow whose only command is CompleteWorkflowExecution; replay against a history ending mid-command (server crashed pre-terminal-append) — executor must resume live-mode cleanly.

13.9 Failure Analysis

Workflow code panics — caught at the executor boundary, surfaced as WorkflowTaskFailed, never crashes the worker process. Comparator false positives from non-canonical attribute serialization (e.g. map key order in Payload) — fix: canonicalize serialization before comparison (ADR-08).

13.10 Operational Notes

14. Phase 2 — Workflow Task Dispatch And The Matching Service

14.1 Objectives

Introduce workflow-matching-svc with in-memory task-queue rings (ADR-10), long-poll dispatch (ADR-11), the task-token scheme (§8.11) fencing I3, and full shard hashing with leased ownership fencing (P5, I9, ADR-07) now that history splits from a single process into a routable, sharded service.

14.2 Detailed Implementation Steps

  1. Implement shard hashing: hash(namespace, workflow_id) mod 512 (ADR-07); a shards lease table (from Phase 0's schema) tracks owner_host, owner_lease, and a monotonic range_id fencing token per shard.
  2. Every history write includes WHERE range_id = $current_lease_range (P5); a stale writer's conditional update fails, closing the split-brain hole named in I9.
  3. Define TaskQueue, WorkflowTaskToken (§11); implement HMAC signing/verification per §8.11.
  4. Build matching-svc: per-queue in-memory ring of pending WorkflowTask handles; long-poll gRPC endpoint blocking until a task is available or timeout.
  5. History service calls matching's internal enqueue RPC when scheduling a decision, rather than dispatching directly (protocol boundary, §3); frontend routes each request to the correct shard owner via the hash from step 1.
  6. Implement RespondWorkflowTaskCompleted: validate task_token (I3), reject stale/duplicate tokens, hand commands to Phase 0/1's append path.
  7. Split the single binary into three processes (frontend stub, history, matching) over real gRPC; run ≥2 history processes to exercise shard ownership handoff.
  8. Basic worker poller in workflow-sdk-worker: long-poll matching, invoke Phase 1's WfExecutor, respond.

14.3 Deliverable

Independent history-svc and matching-svc processes plus a worker binary polling matching, replaying via WfExecutor, and completing end-to-end over gRPC — demonstrated on examples/order-fulfillment (activities still stubbed instant-complete).

14.4 Acceptance Criteria

p50 workflow-task dispatch latency <15 ms on a local 3-process setup (M3, non-sticky); a duplicate RespondWorkflowTaskCompleted with a stale token is rejected in 100% of 1,000 trials (I3); zero cross-queue delivery across a 2-queue, 2-worker-pool test; killing one of two history processes reassigns its shards to the survivor within 10 s with zero duplicate writes across the handoff (I9).

14.5 Conformance Fixtures

phase2_duplicate_token.json; phase2_wrong_queue_delivery.json — asserts task-for-A never reaches a poller-on-B; phase2_long_poll_timeout.json — clean timeout, no connection leak; phase2_shard_fencing_stale_writer.json — a killed-then-recovered old owner attempts a write after losing its lease, expects rejection via range_id mismatch (I9).

14.6 Pitfalls

  • Trusting a client-supplied queue name without namespace-scoping it — cross-namespace task leakage (feeds T4); recovery: namespace-scope every queue key.
  • Task tokens without an HMAC — forgeable, any caller can complete any task (T3); recovery: sign before this phase's demo is called done.
  • Expecting matching-svc to survive a restart with tasks intact — it can't (P2 applies to queue contents too); recovery: history's re-schedule-on-no-poller fallback, documented as expected, not a bug.
  • Omitting the range_id guard on any single write path "just this once" — the one unfenced write path is exactly where split-brain corruption enters; recovery: audit every UPDATE/INSERT against history_events/executions/timers for the guard, no exceptions (P5, I9).

14.7 Performance Concerns

Long-poll connection count scales with worker-pool size; benchmark ring-buffer contention under 1,000 concurrent long-polls (feeds §30's task-matching latency methodology); shard-lease renewal traffic must stay a small fraction of append traffic even at 512 shards.

14.8 Edge Cases

A worker polls a queue with zero registered workflow types; two workers race to poll the same task (must be exclusive, I3); a queue with pending tasks but zero pollers for >30 s (feeds §4's backlog bound); a shard whose owner is network-partitioned from Postgres but still alive (must let its lease lapse rather than continue believing it owns the shard).

14.9 Failure Analysis

matching-svc crash — in-flight long-polls drop, but history's WorkflowTaskScheduled append already persisted; matching-svc needs a startup reconciliation pass requesting any scheduled-but-undelivered tasks from history. A history process that loses Postgres connectivity must release its shards (no lease renewal) rather than continue serving stale reads.

14.10 Operational Notes

Expose task_queue_backlog_age and fencing_rejection_total from this phase forward — the former is the earliest warning of matching falling behind, the latter the earliest warning of a lease-handoff bug.

16.1 Objectives

Implement the full TimeoutSpec (schedule-to-start, start-to-close, schedule-to-close, heartbeat — ADR-15), RetryPolicy (ADR-16), and heartbeat-driven resumable activities (§8.7).

16.2 Detailed Implementation Steps

  1. Add per-timeout deadline tracking to activity_info (ADR-15's four-timeout model); a per-shard reaper scans for elapsed deadlines and appends ActivityTaskTimedOut with the specific timeout_type, preserving I8's single-terminal-event guarantee.
  2. Implement RetryPolicy evaluation on ActivityTaskFailed/TimedOut (ADR-16): exponential backoff with jitter (Nygard's stability-pattern guidance, §5), respecting max_attempts and non_retryable_errors; re-schedule keeps the same activity_id, increments attempt (§8.5).
  3. Implement the heartbeat RPC: the activity worker calls RecordActivityTaskHeartbeat periodically; the server resets the heartbeat deadline and persists heartbeat_details (§8.7), the durable-substitute mechanism P3 requires for resumable, at-least-once activities.
  4. Extend the Phase 3 activity-worker handler to heartbeat automatically at 20% of heartbeat_timeout (§4) for long-running activities.
  5. Add workflow-execution-timeout and workflow-task-timeout as execution-level and task-level reaper-driven deadlines, mirroring the activity reaper.

16.3 Deliverable

An activity failing on attempts 1–3, succeeding on attempt 4, with exponential backoff visible in the resulting History timeline; a long-running activity heartbeating every 6 s against a 30 s heartbeat_timeout that survives past its (much longer) start_to_close_timeout, demonstrating the two timeouts are independent.

16.4 Acceptance Criteria

Retry backoff intervals match backoff_coefficient within 5% across 20 trials; a fixture with start_to_close=300s, heartbeat_timeout=5s, and a worker that stops heartbeating at t=10s times out at ~t=15s, not t=300s; activity_id remains stable across all retry attempts in 100% of fixture runs.

16.5 Conformance Fixtures

phase4_retry_backoff_4_attempts.json; phase4_heartbeat_independent_timeout.json; phase4_non_retryable_error_no_retry.json — asserts an error in non_retryable_errors short-circuits retry; phase4_schedule_to_close_caps_total_retry_time.json.

16.6 Pitfalls

  • Resetting activity_id on retry — breaks history audit continuity and I8's per-attempt-group bookkeeping; the attempt counter is separate from identity, never conflate them.
  • Heartbeat-deadline reset racing a genuine ActivityTaskTimedOut append — a heartbeat arriving 1 ms after the timeout append must be rejected, not resurrect a timed-out activity; fixture-verified.
  • Computing backoff without jitter — synchronized retry storms across executions that failed at the same moment; recovery: jitter per Nygard's stability-pattern guidance (§5).

16.7 Performance Concerns

The reaper scan must not become an unbounded table scan as open executions approach the §4 ceiling (2,000,000); index activity_info by deadline per shard, mirroring the timer table's indexing.

16.8 Edge Cases

heartbeat_timeout longer than start_to_close_timeout (heartbeat becomes a no-op safety net, must not error); a retry that would exceed schedule_to_close_timeout mid-backoff must fail immediately rather than waiting out a backoff it can't complete before the cap.

16.9 Failure Analysis

Reaper falls behind under load (many elapsed deadlines queue up) — must not block new activity scheduling; partition reaper work per shard so one hot shard's backlog doesn't starve others.

16.10 Operational Notes

activity_retry_rate and activity_timeout_rate per activity_type are the two metrics operators check first when a downstream dependency degrades — wire them from this phase.

17. Phase 5 — Durable Timers

17.1 Objectives

Promote the Phase 0 timer table into a first-class shard-owned timer service (§8.7) meeting the §4 precision/skew bound (I5, P7).

17.2 Detailed Implementation Steps

  1. Implement the per-shard timer poll loop (100 ms interval) reading timers WHERE shard_id = ? AND fire_time <= now() ORDER BY fire_time LIMIT N.
  2. On each expired timer, transactionally append TimerFired + WorkflowTaskScheduled and delete the timer row (same transaction as Phase 0's append primitive).
  3. Implement ctx.timer(duration) in WfCtx: emits StartTimer, suspends the workflow future, registers a waker keyed by (TimerFired, timer_id) per Phase 1's registry pattern.
  4. Add jitter to poll-loop batch selection when more than N timers share a fire_time bucket, smoothing timer-storm risk (P7).
  5. Add TimerCanceled handling for workflows that start then cancel a timer before it fires.

17.3 Deliverable

10,000 workflows each start a 1-hour timer over a 60-second start window; all fire within the ±150 ms p99 skew bound of §4, verified by a benchmarks/ load-test harness.

17.4 Acceptance Criteria

p99 timer skew ≤150 ms across the 10,000-timer load test; zero early fires across 1,000,000 fuzzed timer-fire events; a canceled timer never fires across 10,000 cancel-then-wait trials.

17.5 Conformance Fixtures

phase5_10k_timer_load.json (load-test descriptor); phase5_early_fire_stress.json — fuzzed clock-skew injection, expects zero early fires; phase5_timer_cancel_race.json — cancel racing fire, expects deterministic resolution per §8.2's ordering rule.

17.6 Pitfalls

  • A shared deadline across many executions ("everyone times out at midnight") saturating the reaper — the canonical timer-storm failure mode; mitigated by jitter plus the timer-storm-mitigation.md runbook (§26).
  • Polling with a too-coarse interval to save CPU — directly inflates skew past the §4 bound; 100 ms is a hard constraint, not a tuning knob, absent a §4 revision.
  • Deleting the timer row before confirming the TimerFired append committed — a crash in between loses the timer entirely, violating I5; recovery: single transaction, never split.

17.7 Performance Concerns

The (shard_id, fire_time) index must stay a tight B-tree scan even at the §4 ceiling of 2,000,000 open executions each potentially holding a timer.

17.8 Edge Cases

A timer with duration=0 must fire without racing ahead of the WorkflowTaskCompleted that created it; a workflow starting 1,000 timers in a single task (bulk-insert path, not 1,000 transactions).

17.9 Failure Analysis

Shard reassignment mid-poll-cycle — the new owner resumes scanning fire_time <= now() with no assumption about the old owner's in-flight batch, since ownership transfer (P5) invalidates any in-progress scan the instant the lease is fenced.

17.10 Operational Notes

Alert on now() - min(fire_time) exceeding 60 s for any shard (starvation signal) — the primary input to timer-storm-mitigation.md.

18.9 Failure Analysis

18.10 Operational Notes

ctx.is_cancelled() returns true within one workflow task of a RequestCancel append in 100% of trials; Terminate closes an execution in <50 ms regardless of workflow-code state; an activity ignoring its cancel flag runs to its normal terminal state (documents ADR-17's cooperative-only guarantee) rather than being force-killed.

19.5 Conformance Fixtures

phase7_cooperative_cancel_with_cleanup.json; phase7_terminate_bypasses_workflow_code.json; phase7_activity_ignores_cancel_flag.json — asserts normal completion under the cooperative-only contract.

19.6 Pitfalls

  • Implementing Terminate by trying to signal the workflow first — defeats its purpose as the "this workflow is hung" escape hatch; Terminate must never depend on workflow code responding.
  • Assuming activity cancellation is forceful — it is not (ADR-17); an activity that never checks its cancel flag runs to completion.
  • Racing a cancel-observed cleanup activity against a concurrent normal-path activity completing — needs the same deterministic-ordering discipline as any concurrent command (P6).

19.7 Performance Concerns

Terminate's bypass path must not contend with normal shard append throughput even under a burst of administrative terminations (e.g. incident response terminating thousands of stuck executions at once).

19.8 Edge Cases

RequestCancel against an already-closed execution is a no-op, not an error; a workflow that ignores cancellation and completes normally anyway is valid — cooperative cancellation is advisory.

19.9 Failure Analysis

An incident requiring mass Terminate across thousands of executions must not require per-execution round trips; workflowctl terminate --batch (§10) issues bulk terminate, exercised in this phase's chaos-adjacent testing.

19.10 Operational Notes

Distinguish Canceled from Terminated prominently in visibility and dashboards — one ran cleanup, one didn't, with very different downstream-reconciliation implications.

20. Phase 8 — Child Workflows And Continue-As-New

20.1 Objectives

Implement ChildWorkflowRef (§8.9), ctx.child::<W>(), parent-child cancellation policies, and continue-as-new (ctx.continue_as_new, I6, P8).

20.2 Detailed Implementation Steps

  1. Implement StartChildWorkflowExecution plus ChildWorkflowExecutionStarted/Completed/Failed/Canceled events (§8.1).
  2. Implement ctx.child::<W>(input, opts): emits the start command, suspends, registers a waker for the child's terminal event, propagating result/failure to the parent future.
  3. Implement parent-child cancellation propagation per ChildCancellationPolicy (Abandon/RequestCancel/Terminate) — on parent cancel/terminate, apply the chosen policy to open children.
  4. Implement ctx.continue_as_new(input): emits ContinueAsNewWorkflowExecution, terminates the current run (I6), starts a new run under the same WorkflowId with a continued_from_run_id back-pointer (§8.9).
  5. Add an SDK-level history-size advisory (soft warn at 10,240 events / 10 MiB per §4), feeding the continue-as-new triggering discipline of ADR-19.

20.3 Deliverable

A parent workflow starting 5 children in parallel via deterministic join, waiting for all, aggregating results; a separate "infinite" workflow processing one item per minute that continues-as-new every 1,000 iterations, run long enough to show history staying bounded across many runs.

20.4 Acceptance Criteria

Parent-cancel with RequestCancel policy delivers a cancel request to all 5 open children within one workflow task; continue-as-new's new-run history never exceeds 1,000 events at any iteration boundary across a 10,000-iteration soak; WorkflowId continuity holds across ≥50 continue-as-new hops in a single fixture chain (I6).

20.5 Conformance Fixtures

phase8_five_children_parallel_join.json; phase8_parent_cancel_propagation_terminate_policy.json; phase8_continue_as_new_history_bound.json — asserts event count resets at each hop; phase8_continue_as_new_workflow_id_continuity.json.

20.6 Pitfalls

  • Treating continue-as-new like a function call and executing code after it — the run terminates at that command (P8); a lint should flag unreachable code following ctx.continue_as_new.
  • Child-completion events not carrying enough for the parent to resume across its own continue-as-new — documented limitation: a child started before a continue-as-new cannot be awaited across that boundary; parents must drain children first.
  • Unbounded history growth from a loop that never continues-as-new — the canonical failure named in the phase arc; mitigation is the SDK's soft-warn threshold plus documentation, since the split point is an application decision the engine cannot force.

20.7 Performance Concerns

Child-workflow start adds a cross-execution write (parent's Started event plus the child's own WorkflowExecutionStarted); benchmark fan-out of 100 children from one parent workflow task.

20.8 Edge Cases

Continue-as-new called with zero prior activities (immediate re-loop); a child that itself continues-as-new while the parent awaits it (the parent's wait must resolve against the child's final run); a parent terminated while children are under an Abandon policy (children continue independently, by design).

20.9 Failure Analysis

A child's terminal event fails to propagate to the parent due to a lost notification — the parent workflow task never wakes; detection: a completion-propagation lag metric; recovery: history must re-check for unpropagated child completions on the parent's next scheduled task rather than rely solely on push notification.

20.10 Operational Notes

Surface history_length and the 10,240-event soft-warn threshold in visibility so operators can proactively find continue-as-new candidates before the hard cap (§25, §31).

21. Phase 9 — Versioning And Patching For Safe Code Change

21.1 Objectives

Implement ctx.patched(change_id) (§8.10, P11, I13), marker-based version branching, and the operational discipline for safely retiring old branches (§27).

21.2 Detailed Implementation Steps

  1. Implement ctx.patched(change_id) -> bool: on first evaluation per run, checks the replayed-so-far history for an existing MarkerRecorded{change_id}; if absent (live/new execution), records a new marker at the latest version and returns true; if present, returns the recorded value deterministically (I13).
  2. Implement optional deprecate_patch(change_id) tooling signal (not engine-enforced) marking a path as now unconditional, aiding drain confirmation.
  3. Add workflowctl patches status <change_id> (visibility-backed) reporting open-execution counts predating a given deploy, supporting §8.10 step 4's drain confirmation.
  4. Extend the Phase 1 replay comparator to treat version-marker mismatches as a distinct NonDeterminismError subtype for clearer diagnostics.
  5. Document the rollout runbook: deploy behind patched(), monitor drain via the CLI helper, remove the guard only at zero pre-deploy open executions.

21.3 Deliverable

Version 1 (charge→ship) and version 2 (if ctx.patched("add-validation") { validate() } inserted) running concurrently against the same worker fleet: pre-v2 in-flight executions take the old path on every replay, new executions take the new path, both complete correctly.

21.4 Acceptance Criteria

0 NonDeterminismErrors across 200 pre-v2 in-flight executions replayed post-deploy; 100% of new-start executions take the v2 path; workflowctl patches status add-validation correctly reports 0 remaining pre-v2 open executions once drained, verified against visibility ground truth.

21.5 Conformance Fixtures

phase9_patch_old_execution_takes_old_path.json; phase9_patch_new_execution_takes_new_path.json; phase9_patch_removed_early_breaks_replay.json — deliberately-malformed, simulates premature guard removal, expects NonDeterminismError.

21.6 Pitfalls

  • Removing a patched() guard before all pre-deploy executions have drained — the single most damaging versioning mistake (§27); the CLI drain-check is mandatory process, not optional.
  • Moving a patched() call to a different code position between deploys without removing it — changes its position in command/event correlation and can itself cause NonDeterminismError.
  • Treating change_id strings as disposable — a typo across a deploy creates an unrelated second marker instead of matching the intended one; change_ids are part of the public compatibility surface (§27).

21.7 Performance Concerns

MarkerRecorded events accumulate in history like any other event and count toward the §4 size ceiling; workflows with many patch points over their lifetime should budget for this in continue-as-new threshold planning.

21.8 Edge Cases

patched() called inside a loop with a per-iteration change_id (anti-pattern, unbounded distinct markers); two patched() calls with the same change_id in different code paths of the same run must resolve to the same recorded version.

21.9 Failure Analysis

A bad deploy removes a guard while pre-deploy executions are still open — mass NonDeterminismError across every affected execution simultaneously (FM-9's defining scenario); recovery is docs/runbooks/bad-deploy-rollback-inflight.md (§26): roll back the binary, let affected executions drain against the rolled-back code, re-attempt guard removal only after confirmed drain.

21.10 Operational Notes

version_marker_total by change_id (I13 telemetry) answers "is it safe to remove this guard yet" — wire it directly to the drain-confirmation CLI helper.

22. Phase 10 — Sticky Caching, Visibility Indexing And Multi-Tenant Namespaces

22.1 Objectives

Implement sticky execution caching with build-id-bound invalidation (P12, I12, ADR-12), the visibility indexer (I14, ADR-21, ADR-24), and namespace/quota enforcement (P13, ADR-22, ADR-23).

22.2 Detailed Implementation Steps

  1. Worker advertises a per-process sticky task-queue name and a build_id (reproducible build fingerprint, ADR-33) at registration.
  2. On WorkflowTaskCompleted, the worker requests subsequent tasks be routed to its sticky queue; the next task for that queue includes only events since last_started_event_id (§3.3).
  3. Implement sticky-timeout fallback: if the sticky worker doesn't respond within a bounded window, the server routes the next task to the normal queue, forcing full replay.
  4. Implement the worker-side LRU StickyCacheEntry (§11) with build-id-keyed invalidation (I12); a mismatch triggers unconditional eviction.
  5. Build the visibility indexer as an async consumer of committed history/execution-state changes (ADR-24), denormalizing into the visibility table (§8.12, ADR-21) with a checkpoint cursor for restart recovery.
  6. Implement NamespaceQuota enforcement at the frontend (P13, ADR-23): token-bucket rate limiting on starts/second, hard caps on open-execution count and history size per namespace.

22.3 Deliverable

A workflow with 100 events of history showing <10 ms decision latency on sticky vs. >50 ms on forced fallback; workflowctl list --namespace acme --state Running --type OrderFulfillment --start 1d returning correct results within the §4 visibility-lag bound; a namespace with max_starts_per_second=10 correctly rejecting its 11th start within the same second.

22.4 Acceptance Criteria

Sticky-cache hit ratio ≥90% (§4) in a steady-state 1,000-workflow soak; visibility index lag p99 ≤2 s (§4); namespace quota rejection rate equals exactly the excess over the configured limit across 10 trials at 2× the configured rate; a worker deploy bumping build_id results in 100% cache eviction for that worker's prior entries (I12).

22.5 Conformance Fixtures

phase10_sticky_hit_latency.json; phase10_sticky_fallback_on_timeout.json; phase10_build_id_invalidation.json; phase10_visibility_lag_bound.json; phase10_namespace_quota_rejection.json; phase10_cross_namespace_isolation.json — asserts a namespace-A query never returns namespace-B executions.

22.6 Pitfalls

  • Binding sticky-cache validity to wall-clock time or deploy timestamp instead of build_id — a redeploy with an unchanged build_id (a real CI misconfiguration) silently keeps stale caches alive; CI must fail a release that doesn't bump build_id (P12).
  • Computing visibility synchronously in the append path "for simplicity" — reintroduces exactly the coupling ADR-24 rejected, turning visibility into a durability risk instead of an eventually-consistent view.
  • Enforcing quotas only at history/matching, after the request already consumed shared capacity — must be enforced at the frontend (P13), or one tenant still starves others despite the quota existing.
  • Sticky-cache staleness surviving a partial worker restart (process restarts but an old executor instance lingers in a thread pool) — named explicitly in the phase-arc brief; mitigation: key the cache by build_id plus a per-process-start nonce, not build_id alone.

22.7 Performance Concerns

The visibility indexer must keep pace with peak append rate (~9,000 writes/s per §34) without falling permanently behind; sticky-cache LRU eviction under memory pressure must favor recency over size, so hot workflows aren't evicted ahead of cold ones.

22.8 Edge Cases

A worker configured with zero sticky-cache capacity (every task falls back — must degrade gracefully, not error); a namespace deleted while executions are still open (must reject, or require explicit force+drain, never silently orphan running executions); a visibility query spanning a continue-as-new boundary (must show continuity via continued_from_run_id).

22.9 Failure Analysis

The visibility indexer crashes and restarts from a stale checkpoint — must replay only the gap via idempotent upsert keyed by execution identity, never double-count. A namespace's quota configuration becomes corrupted (e.g. max_starts_per_second=0 by operator error) — must fail closed (reject all starts) with a loud alert, never fail open.

22.10 Operational Notes

Dashboard the four numbers operators check constantly from this phase forward: sticky-cache hit rate, visibility lag, per-namespace quota utilization, and fencing-rejection rate — together they describe whether the multi-tenant cluster is healthy.

23.1 Objectives

The chaos soak surfaces a correctness violation late in its 12-hour window — must be reproducible from the fault-injection schedule alone (a deterministic seed for the fault scheduler, distinct from the determinism required of the workflows under test). 26. Operational Readiness

Named metrics: workflow_task_dispatch_latency_ms (p50/p95/p99, M3–M5), workflow_task_backlog_count, replay_duration_ms (histogram by history-length bucket), sticky_cache_hit_rate, determinism_violation_total (I1), activity_retry_rate, activity_timeout_rate, timer_skew_ms, open_execution_count (per namespace and cluster-wide), fencing_rejection_total (I9), visibility_lag_ms (I14), task_queue_backlog_age.

Tracing spans that survive the async hops: every RPC carries a W3C traceparent header; task tokens additionally embed a trace-context fragment so a span survives the gap between ActivityTaskScheduled and its eventual ActivityTaskStarted on a different process, potentially minutes or hours later — the defining tracing challenge here versus a typical request/response service.

Structured logging: JSON via the tracing crate (ADR-25); every line carries namespace, workflow_id, run_id, and event_id where applicable, for direct correlation with the History.

Dashboards: (1) determinism-violation dashboard, keyed by workflow_type and build_id — the single most important one; (2) sticky-cache health (hit/invalidation/eviction rate); (3) timer health (skew, backlog, batch-size histogram); (4) namespace quota utilization; (5) shard ownership (fencing rejections, lease-renewal latency).

Alerting philosophy: alert on invariant-adjacent signals (the I1–I14 telemetry columns), not symptoms alone — e.g. alert on determinism_violation_total > 0 for any single execution (it should never be nonzero in steady state), rather than only aggregate error rate, since one silent determinism violation can outweigh a visible spike of retryable failures.

SLOs: 99.9% monthly availability (§4); p99 dispatch latency ≤250 ms sticky; zero tolerance for determinism-violation-caused data loss — a correctness SLO, not a latency one; any occurrence is sev-2 minimum.

Incident response: a determinism-violation spike immediately following a deploy is a stop-the-line event — halt further rollout rather than waiting for the alert to self-clear.

Named runbooks under docs/runbooks/: determinism-violation-triage.md (offline replay-and-diff, §7); stuck-execution-recovery.md (draining buffered signals, ResetWorkflowExecution); history-size-remediation.md (patching toward more aggressive continue-as-new); bad-deploy-rollback-inflight.md (the versioning-regression response, FM-9); timer-storm-mitigation.md (jitter application, shard rebalancing).

Backup/restore: continuous Postgres WAL archiving plus periodic base backups; restore drills validate that a restored history_events table replays identically against the same worker build_id used at backup time — tying recovery directly to the determinism contract, not only to Postgres's own consistency guarantees.

Deployment topology: history sharded across N processes behind a lease coordinator; matching horizontally scaled per task queue; frontend horizontally scaled behind a load balancer; workers deployed independently by tenant teams, each pinned to a build_id.

Canary/rolling-upgrade/rollback/migration: canary a new worker build against a small percentage of new workflow starts first (in-flight executions are the risk, not new ones); roll the server tier stateless-first (frontend, matching), history last, one shard-owning process at a time, relying on I9's fencing to make handoff safe; rollback simply redeploys the previous build_id — no data migration needed since sticky cache invalidates cleanly (P12); persistence-schema migrations stay additive-only during any rolling-upgrade window (§27).

Rolling out worker code while executions are mid-flight is the defining operational hazard of this system. Every other concern in this section is secondary to getting that one transition right, because a mid-flight rollout is exactly the scenario the determinism contract (P1) and versioning discipline (P11, §21, §27) exist to make safe, and exactly the scenario every FM-9-class incident actually occurs in.

27. Compatibility & Versioning

The history-versus-code compatibility contract is the centerpiece here: a History recorded against SDK/workflow-code build B1 must remain replayable against any later build B2 that has not declared an announced, guarded, or major-version compatibility break against it — a stronger promise than typical API backward compatibility, because the "client" of this contract is not a caller but the workflow's own past self.

The patch/version-marker mechanism (§8.10, §21 recap): ctx.patched(change_id) records MarkerRecorded on first evaluation; replay reads the recorded marker rather than re-evaluating "current" behavior (I13, P11) — the sole sanctioned mechanism for introducing a change that must coexist with in-flight histories.

Replay-breaking vs. safe changes:

Change Safe / Breaking Why
Adding a new #[activity] function Safe doesn't alter existing command sequences
Adding a new EventType variant Safe, additive-only old workers tolerate unknown variants if the enum is non-exhaustive (ADR-08)
Changing an activity's input type without a version guard Breaking changes serialized Payload bytes an in-flight replay expects
Reordering two ctx.activity() calls Breaking violates P6's emission-order correlation
Adding a new branch behind ctx.patched() Safe I13 guarantees replay sees the recorded branch
Removing a ctx.patched() guard Breaking until drained pre-deploy in-flight executions have no recorded marker and still need the old path
Changing RetryPolicy defaults for new activities only Safe doesn't touch already-scheduled activity_info rows
Changing EventAttributes wire encoding (ADR-08) Breaking unless versioned changes byte-level comparison in the determinism checker (§8.3)
Renaming a registered workflow/activity type string Breaking in-flight histories reference the old name; requires dual-registration during a drain window

Payload serialization evolution: Payload carries a content_type tag (§11); evolving an application's serialized shape should follow the same additive-field discipline recommended for the engine's own Protocol Buffers messages — an application-level responsibility the engine can recommend but not enforce.

Event-type addition rules and unknown-event handling: new EventType variants are additive-only after GA; a worker on an older SDK build encountering an unknown event type during replay must fail closed with a distinct UnknownEventTypeError — never silently skip it, which would desynchronize the replay cursor — for immediate operator diagnosis.

API stability: the frontend gRPC surface follows SemVer 2.0.0 (ADR-32); a major bump is required for any breaking RPC change; minor/patch stay additive-only.

Persistence schema migration: changes to history_events/executions/timers/activity_info during a rolling upgrade must be additive-only (new nullable columns) until every cluster process runs the new binary; destructive migrations are a separate, later, fully-drained step.

Deprecation: a deprecated patched() change_id or activity type is marked in docs/adr/ with a target drain-complete date, tracked via workflowctl patches status (§21).

SemVer 2.0.0 discipline: SDK crate versions follow SemVer; a major bump signals a possible replay-compatibility break and triggers a mandatory replay-gate run against the full historical corpus (§28) before release.

Rolling-upgrade guarantees: at every point during a rolling upgrade, I1–I14 continue to hold for any single execution even when different workers in the fleet run different (compatible) builds simultaneously — precisely what "additive-only" plus "guard-then-drain" jointly buy.

28. Testing & Verification Strategy

Unit: per-crate logic (RetryPolicy backoff math, task-token HMAC round trip, EventAttributes serialization) — fast, no Postgres.

Integration: multi-process (frontend+history+matching+worker) scenarios against real local Postgres, covering each phase's N.3 deliverable.

Property-based: (1) replaying any recorded history reproduces its command sequence exactly (I1, the central property); (2) an activity executed twice with the same idempotency key produces one effect (P3, tested against the SDK's idempotency-key helper); (3) a timer never fires early (I5); (4) history event ids are gapless and monotonic under concurrent append attempts (I2).

Differential: run a shared scenario set against this engine and against Temporal's documented semantics (§5), comparing observable behavior (state-machine transitions, timeout behavior) — behavioral parity on load-bearing semantics, not byte-for-byte wire compatibility.

Replay-compatibility testing against a corpus of recorded production histories, as a named CI gate, is the industry-standard practice for this system class and is specified here as non-optional: replay-gate.yml (§10, §23) replays every corpus entry on every PR touching workflow-sdk-core/workflow-core, failing the build on any command-sequence mismatch — the single test most likely to have caught real-world durable-execution incidents in the reference implementations (§5).

Fuzzing: fuzz/fuzz_targets/history_deserialize.rs, payload_decode.rs, task_token_parse.rs (ADR-29); scheduled via fuzz.yml; any crash triaged against §24 (T1, T3).

Chaos: kill a worker mid-workflow-task (FM-1); partition the persistence layer (FM-4, FM-10); inject clock skew (I5's early-fire guarantee); inject duplicate task delivery (I3, P3). Run as the Phase 11 12-hour soak, then nightly via chaos-nightly.yml.

Deterministic replay: every conformance fixture is, by construction, a deterministic-replay test; fixture-based tests pin historically-significant shapes (including ones that previously caused an incident) rather than purely random ones.

Soak: 12-hour minimum (Phase 11), extended multi-day before major releases, watching for tail-latency drift (Dean & Barroso 2013) and slow sticky-cache memory growth.

Fault injection: compounds chaos-style single faults into combined scenarios (e.g. worker kill during a sticky-cache-staleness window), per §23.6's warning against shallow chaos coverage.

Conformance: the full corpus run (§23) is a release gate — necessary but not sufficient; perf-regression gating and the chaos soak must also pass.

Perf-regression gating: every M-series target in §30 has a benchmarks/ counterpart; CI compares each PR's results against the previous release's baseline, failing on regression past a 10% default tolerance.

Each category ties back to specific invariants (I1–I14) and to the N.5 fixtures introduced by the phase that first needed that guarantee — testing strategy here is the direct operationalization of §7's invariant table, not a bolt-on.

29. Build & Release Engineering

Reproducible builds: pinned Cargo.lock (ADR-33), locked toolchain via rust-toolchain.toml, --locked CI builds; a given commit plus toolchain version must always produce a bit-identical build_id fingerprint, since sticky-cache correctness (P12) depends on build_id faithfully proxying code identity.

Artifact signing: release binaries and container images are signed as part of release.yml; signatures verified by deployment tooling before rollout.

SBOM: generated per release, attached to the GitHub release and container image, covering every crate dependency (T10).

Release channels: stable (SemVer-tagged, passed the full §28 gate) and canary (passed unit+integration but not the full chaos soak — internal early adopters only).

CI/CD topology: ci.yml (every PR) → replay-gate.yml (corpus replay, gates merge to main) → nightly chaos-nightly.yml/fuzz.yml (gate the next release cut) → release.yml (main-only, requires all prior gates green within a bounded freshness window).

Version stamping: build_id embeds the git commit hash and toolchain version; SDK crate versions follow SemVer 2.0.0 (ADR-32) independently, since build_id bumps more frequently than semver-meaningful releases do.

Provenance/attestation: release.yml produces a provenance attestation binding the artifact hash to the exact CI run, commit, and build environment.

Dependency auditing: cargo audit runs on every PR and nightly against the published advisory database; a new advisory against a locked dependency fails the nightly build even with no code change.

30. Performance Engineering

Profiling/benchmark methodology: (1) history-append path — end-to-end transaction latency under increasing concurrent-append load, isolating Postgres commit latency from serialization cost; (2) replay cost as a function of history length — benchmark WfExecutor at 100/1,000/10,000/51,200-event histories, fitting the linear model used in §34; (3) allocation — profile the hot poll loop for per-event allocation (target: zero on the steady-state path); (4) lock contention on shard state — mutable-state-cache lock hold time under concurrent workflow-task and query dispatch to the same execution; (5) task-matching latency — long-poll-to-dispatch latency under varying queue depth and poller count; (6) tail latency — always report p99 and p99.9, per Dean & Barroso 2013's warning that fan-out amplifies tail behavior.

31. Scalability Analysis

What stays constant: per-append transaction cost (bounded by a single shard's row-set, independent of cluster size); per-timer-fire cost; task-token size/verification cost.

What grows, with Big-O: replay cost is O(n) in history length per execution — precisely why continue-as-new exists (§8.9, §20): without it, per-decision latency grows unboundedly over a workflow's logical lifetime. Persistence QPS grows O(starts/sec × events/execution) (§34), bounded above by M1/M2. Storage grows O(executions/day × history bytes × retention) (§34) — linear, requiring active archival policy (history-size-remediation.md) rather than being self-limiting. Sharding by workflow_id keeps per-shard state O(open executions on that shard), so total cluster capacity grows roughly linearly with shard count up to the coordination-overhead bottleneck below.

Named bottlenecks, in order: (1) history-append transaction throughput per shard — the earliest ceiling, mitigated by adding shards, not by optimizing one shard further; (2) shard-lease coordination overhead (§3.2), growing with shard count; (3) matching-service long-poll connection count, growing with worker-pool size, mitigated by horizontal matching replicas per queue; (4) visibility-indexer throughput, which must track append rate or lag grows unboundedly (I14 risk); (5) Postgres itself as a single logical database — the ultimate ceiling absent a move to a sharded storage engine (ADR-06).

Horizontal scaling: frontend scales trivially (stateless); history scales by adding shards up to the point where lease-coordination overhead starts eating into throughput gains — the practical ceiling named below, not raw shard count.

Coordination overhead of shard ownership: every lease renewal and reassignment (P5, I9) consumes coordinator capacity independent of workflow traffic; at very high shard counts this overhead itself becomes the bottleneck before persistence QPS does.

Practical ceilings and the levers beyond them: ~2,000,000 concurrent open executions per cluster at 512 shards (§4) is the practical ceiling for this architecture before shard-count growth's coordination overhead outweighs its benefit — the lever beyond it is horizontal cluster partitioning by namespace (ADR-22's dedicated-cluster alternative), not further shard growth within one cluster. The practical single-execution history-length ceiling is the §4 hard cap (51,200 events / 50 MiB) — the lever beyond it is application-level continue-as-new discipline (§20), not an engine-side change.

32. Mental Models & First Principles

MM1 — Durable execution is state-machine replication applied to application code. If execution is a deterministic function of an ordered log, crash recovery is just replay (Schneider 1990). Predicts: any two processes consuming the same history reach the same state. Bug class without it: bespoke checkpoint/resume logic per workflow instead of recovery-for-free. Resolving: §8, §13.

MM2 — The history is a program's memoized past; every non-deterministic call outside the SDK is a hole in that memo. Predicts: any call not routed through WfCtx is a replay bug waiting to happen. Bug class: intermittent, production-only nondeterminism. Resolving: §8.3, §6 (P1).

MM3 — A shard is a mini single-writer database; the cluster is many of those glued by routing, not one big database. Predicts: throughput scales by adding shards, not by making one shard faster past a point. Bug class: vertically scaling Postgres indefinitely, or forgetting fencing when adding shards. Resolving: §3.2, ADR-07, §31.

MM4 — At-least-once delivery plus idempotent effects is the only distributed "exactly-once" that exists (Helland 2007). Predicts: any activity author assuming the engine prevents duplicate side effects will eventually double-charge someone. Bug class: FM-7. Resolving: §6 (P3), §25 (FM-7).

MM5 — Continue-as-new is a return, not a call; logical lifetime and run lifetime are different axes. Predicts: code after continue_as_new is dead code. Bug class: developers writing cleanup expecting it to execute post-call. Resolving: §8.9, §20 (P8).

MM6 — A version marker is a permanent fork until proven otherwise by an empty query. Predicts: removing a patched() guard is only safe after measurement, never after a calendar date. Bug class: FM-9 versioning regressions. Resolving: §21, §27.

MM7 — Sticky cache is a hint, never a source of truth; treat every hit as a possibly-wrong guess the system can unwind. Predicts: correctness never depends on cache freshness, only latency does. Bug class: FM-6, and the temptation to skip the fallback path "because it's rare." Resolving: §22 (P12).

MM8 — Replay cost is linear in history length, so unboundedness anywhere in history is unboundedness in latency everywhere downstream. Predicts: any workflow shape without a periodic reset accumulates a hidden O(n) tax that eventually dominates. Bug class: FM-8, "why did this workflow get slow after a year." Resolving: §31, §34.

MM9 — A query is a true read only if the type system, not the author's intent, forbids mutation. Predicts: a query that "shouldn't" mutate but isn't structurally prevented from doing so eventually will. Bug class: subtle history corruption from a command-emitting query handler. Resolving: §8.8, P10, I11.

Temporal keeps the author's mental model at "just write code," pushing all replay complexity into the SDK's deterministic executor; it wins wherever teams need unrestricted control flow (dynamic loops, recursion, computed branching) and accept the determinism-lint discipline this blueprint inherits wholesale.

Azure Durable Functions builds atop an existing serverless platform rather than a bespoke cluster, trading a from-scratch history/matching/persistence stack for tight integration with an already-operated platform; it wins for shops fully committed to Azure Functions wanting durable orchestration without standing up a new service tier.

Netflix Conductor chose a declarative task graph with no in-workflow replay at all — each task is a stateless call against an externally-tracked graph position; it wins when most "workflows" are simple linear or branching pipelines where a full determinism/replay engine is more machinery than the problem needs.

Apache Airflow chose a fresh-process-per-task DAG scheduler with no continuation state inside a run — no replay, no determinism constraint, at the cost of no in-workflow control flow; it wins for schedule-driven batch/ETL where each task is naturally idempotent and independently retriable.

AWS Step Functions chose a declarative state machine (ASL) with no general-purpose language inside a state at all; it wins when visual/audit-friendly, statically analyzable definitions matter more than expressiveness and AWS-native integrations cover most of the workflow's needs.

Restate chose a simplified journal-based model narrowing the determinism contract's surface relative to Temporal's; it wins for request/response-adjacent durable handlers wanting durability without Temporal's full orchestration-oriented API surface.

34. Back-of-Envelope Capacity Model

  1. Average event bytes ≈ 250 B (protobuf-encoded HistoryEvent with typical small inline payload references, ADR-08/ADR-09).
  2. History bytes at the soft-warn threshold = 10,240 events × 250 B ≈ 2.56 MB — well under the 10 MiB soft-warn byte threshold (§4), confirming event count, not bytes, is the commonly binding constraint for typical small-payload workflows; the byte cap binds only for activity-heavy workflows with larger results.
  3. History bytes at the hard cap = 51,200 events × 250 B ≈ 12.8 MB — still under the 50 MiB hard byte cap, reinforcing point 2.
  4. Replay time at the hard cap = 51,200 events × ~50 µs/event (Phase 1 baseline, §13.7) ≈ 2.56 s — matches M7's ≤2.6 s target exactly, showing the target was derived from, not asserted independently of, the per-event cost.
  5. Persistence write QPS = workflow starts/sec (M1, 500/s) × average events per execution (~18, per the §8.13 worked example's shape) ≈ 9,000 writes/sec — matches §4's ~9,000 row-writes/s figure.
  6. Storage growth per day = executions/day (500/s × 86,400 s ≈ 43.2M) × average history bytes/execution (18 × 250 B = 4.5 KB) ≈ 194.4 GB/day at fully sustained M1 throughput; §4's steady-state figure is stated as the same order of magnitude, since real traffic rarely sustains the M1 ceiling continuously.
  7. 30-day hot-retention footprint = 194.4 GB/day × 30 days ≈ 5.8 TB, the sizing input for history-size-remediation.md's archival-policy trigger.
  8. Sticky-cache memory = cached executions (~100,000, the practical hot working set at ≥90% hit ratio, M8) × in-memory ReplayState size (~50 KB, waker registry + replayed local state) ≈ 5 GB across the fleet — small relative to typical worker fleet memory, confirming P12's design is affordable at scale.
  9. Timer index size = open timers (≤2,000,000, §4 ceiling) × entry bytes (~100 B: shard_id+fire_time+ids) ≈ 200 MB — trivial for Postgres index memory.
  10. Timer-storm fire-rate spike = if 10,000 executions share one fire_time bucket and the poll loop drains LIMIT 1,000 per 100 ms cycle, draining takes ~10 cycles ≈ 1 s — a visible but bounded spike, which is exactly why P7's jitter mitigation exists rather than being optional.
  11. Task-queue backlog memory = backlog bound (100,000 tasks, §4) × task-handle size (~500 B, metadata only, not full history) ≈ 50 MB — confirms the in-memory ring design (ADR-10) is safe at the specified bound.

35. Hard Questions (Self-Examination)

  1. If a read replica lags the primary, how do you guarantee a query (§8.8) never observes state ahead of committed truth without breaking I14's guarantee? (§8, §27)
  2. Why does continue-as-new reset the history rather than compacting/pruning old events in place? (§8.9, §31)
  3. Where exactly does the "exactly-once effect" claim in §1's non-goals stop being true, and what discipline closes that gap? (§6, §25 FM-7)
  4. During a rolling upgrade with two different build_ids simultaneously sticky-serving one namespace, does I12 still hold per-execution, and how would you prove it? (§22, §27)
  5. Why is the timer poll interval a hard 100 ms constraint (§4) rather than adaptive — what would adaptivity break? (§17, I5)
  6. If two different but semantically-equivalent Payload byte sequences represent "the same" activity input, how does that interact with the comparator's canonical-serialization requirement? (§9, §13)
  7. What specific replay failure does moving a ctx.patched() call one line earlier in otherwise-identical code produce? (§8.10, §21)
  8. Why does "fail closed" strictly dominate "fail open" for a corrupted namespace quota, given fail-closed's own availability cost? (§22, §26)
  9. Under what conditions does sticky caching stop sufficiently mitigating O(n) replay cost and continue-as-new become mandatory rather than advisory? (§20, §31, §34)
  10. Why does child-completion propagation rely on history-service re-checking rather than solely push notification — what does push-only miss, tied to I4's ordering guarantee? (§8, §20)
  11. Does the threat model's task-token mitigation (§24 T3) cover a captured-off-the-wire valid token from a killed worker, or only outright forgery? (§24, §8.11)
  12. What property makes eventual consistency acceptable for visibility (I14, ADR-24) but unacceptable for shard-lease fencing (I9)? (§7, §9)
  13. If a Phase 11 fuzz crash reveals a shape the corpus should already have caught (§23.6), what does that imply about corpus coverage versus corpus size? (§23, §28)
  14. Given Schneider 1990 requires identical inputs applied in identical order, what is the precise argument that a HistoryEvent sequence is sufficient "input" when ctx.random() injects apparent randomness? (§6 P1, §8.3)
  15. Why does Terminate bypass workflow code entirely rather than attempt a bounded cooperative cancellation first — what operational scenario demands zero code involvement? (§19, §26)
  16. Child workflows under an Abandon policy (§20) spawn independently-tracked units much like Airflow's fresh-process tasks (§33) — where precisely is the line between "still one durable execution's control flow" and "independent task orchestration"? (§20, §33, §36)
  17. What feedback loop exists between §20's continue-as-new guidance and §34's capacity numbers actually holding in production, given both average-events-per-execution and start-rate are shaped by team adoption of that guidance? (§20, §34)
  18. ADR-06 rejects FoundationDB except "when ordered multi-key transactions across shards are required" — does any feature in this blueprint actually need a cross-shard multi-key transaction, or is that rejection criterion currently vacuous? (§9, §31)

36. Alternative Architectures (Roads Not Taken)

36.1 Declarative State-Machine / DSL

StateMachine (ASL JSON, no general-purpose code):
  ChargeCustomer(Task) -> Wait3Days(Wait) -> CheckCancelled(Choice)
    --Yes--> End
    --No---> SendFollowup(Task) -> WaitForReply(Wait/Callback)
             -> Escalate(Task) -> End
Interpreter walks the static graph directly; no user "code" replays.

Winning regime: statically expressible graphs with no dynamically-computed branching, where visual/audit tooling outweighs expressiveness. Embodying system: AWS Step Functions (ASL). Rejected here because this blueprint's target workloads need arbitrary control flow (dynamic loops, recursive child-workflow patterns, computed branching, ADR-04) that a static graph cannot express without Task-state escape hatches calling out to more compute anyway — the determinism/replay engineering this blueprint centers on (§1) is exactly what this alternative sidesteps, at the cost of the expressiveness this blueprint's authors need.

36.2 State-Snapshot Checkpointing

Orchestrator continuation serialized as an opaque blob per await point:
  Checkpoint_1 = serialize(continuation after call_activity("charge"))
  Checkpoint_2 = serialize(continuation after create_timer(3d))
Recovery: deserialize the LATEST blob, resume directly — no replay.

Winning regime: platforms whose language runtime can serialize a paused continuation directly, where avoiding replay's O(n) cost matters more than a full audit history. Embodying system: Azure Durable Functions / Durable Task Framework (Netherite). Rejected here because continuation serialization couples tightly to a runtime's internal representation (fragile across upgrades, a harder compatibility problem than §27's additive-event-type discipline), discards the audit trail event-sourcing provides for free (§8, Fowler), and is impractical to build safely atop Rust's ownership model for an arbitrary paused Future (ADR-03).

36.3 External DAG Scheduler

DAG (Python, parsed by a scheduler, never executed durably):
  charge_task >> wait_sensor >> [cancel_check] >> followup_task
Each task = a fresh, independent process/pod invocation.
No in-run control flow; branching lives in DAG structure, not code.

Winning regime: schedule-driven batch/ETL where each task is naturally idempotent and independently retriable, and "workflow" means a graph of largely-independent jobs, not one continuously-executing logical thread. Embodying system: Apache Airflow. Rejected here because no durable in-process control flow exists — a workflow needing local variables across a wait, a runtime-computed branch, or recursion must push that state into an external database the author manages by hand, reconstituting the "cron jobs plus a status table" anti-pattern this blueprint exists to collapse; Airflow's own DAG-file-as-privileged-code CVE history (§5) is a pitfall avoided here by keeping workflow code off the control plane (trust boundary C, §3).

36.4 Durable-Actor Model

Grain/Virtual-Actor "OrderActor#42":
  state: { charged: bool, shipped: bool }   <- durable per-actor state
  method ProcessOrder(): mutates state, persists after each call
No execution history log; CURRENT state is the durable unit.
Recovery = reload latest state, not replay a decision sequence.

Winning regime: many independent, addressable stateful entities handling short request/response method calls, where per-entity concurrency, not long-lived multi-step control flow, is the scaling axis and "how did we get here" matters less than current state. Embodying systems: Microsoft Orleans (Bernstein, Bykov et al. 2014); Restate's durable-handler model shares this lineage while layering journal-based replay on top. Rejected here because current-state-only actor models lose the step-by-step audit history this blueprint's event-sourcing provides by construction (§8.1), and don't express a long-running, multi-step control flow spanning days-to-months with complex waiting/timeout/signal semantics (§8.6–§8.9) as cleanly as one continuously-replayed function — exactly this blueprint's primary target (§1).

38. Glossary

  • Activity: a unit of side-effecting work invoked by a workflow; idempotent by convention, not by engine guarantee (P3).
  • Activity task: a unit dispatched to an activity worker for execution; at-least-once delivery (ADR-14).
  • At-least-once: the delivery guarantee for activities — dispatched one or more times, never zero (P3, Helland 2007).
  • Build id: a reproducible fingerprint identifying a worker binary version; sticky-cache validity is bound to it (P12, I12).
  • Child workflow: a workflow started by another workflow as a sub-execution, linked via ChildWorkflowRef (§8.9).
  • Command: a workflow's emitted intent during a workflow task, translated into one or more history events on acceptance (§8.2).
  • Command/event correlation: the ordered matching of emitted commands to recorded history events that makes replay verifiable (P6, I1).
  • Continue-as-new: terminate the current run and start a new run under the same WorkflowId with a new RunId, bounding history (P8, I6).
  • Determinism: the property that workflow code, given the same history, always produces the same commands in the same order (P1).
  • Determinism violation: a replay producing a command that mismatches the recorded history event at that position (I1).
  • Deterministic replay: re-executing a workflow function against its history to reconstruct in-memory state without side effects (§8.2).
  • Durable execution: making ordinary control flow survive crashes and restarts via event-sourced replay (§1).
  • Event sourcing: modeling state as a sequence of immutable events rather than mutable current state (Fowler; Kleppmann DDIA ch. 11).
  • Exactly-once effect: the (cooperative, not engine-guaranteed) property that an idempotent activity produces one durable real-world effect despite at-least-once delivery (P3).
  • Execution: an instance of a workflow, identified by (namespace, workflow_id, run_id).
  • Fencing token: a monotonic identifier (range_id) preventing a stale shard owner from corrupting state (P5, I9).
  • Heartbeat: a periodic liveness signal from an activity, resetting its heartbeat deadline and persisting resumable progress (§8.7).
  • History: the ordered, append-only sequence of events defining a workflow execution — the system of record (P2, I2).
  • History event: one entry in a History; the atomic unit of durable truth (§8.1).
  • History service: the sharded server component owning durable state mutation for workflow executions (§3).
  • Idempotency key: an application-supplied token letting a duplicated activity invocation be recognized and deduplicated by the downstream system (P3).
  • Long poll: a blocking RPC pattern used by matching to hand off tasks to waiting workers (ADR-11).
  • Marker: a special history event recording SDK-internal information (side effects, version stamps) (§8.1).
  • Matching service: the server component routing tasks to workers via task queues (§3).
  • Namespace: a tenant boundary for isolation, quota, and retention configuration (P13).
  • Non-determinism error: the error raised when replay's emitted command mismatches its corresponding history event (I1).
  • Patch: the code branch introduced behind a ctx.patched() guard (§8.10).
  • Payload: the opaque, content-typed byte wrapper the engine never deserializes into application types (P14).
  • Query: a synchronous, side-effect-free read of workflow state (P10, I11).
  • Query-must-not-mutate: the rule that query handlers may never emit commands (P10, I11).
  • Replay: re-executing a workflow function against its recorded history (§8.2).
  • Replay compatibility: the guarantee that a history recorded against one code build remains replayable against a later, compatible build (§27).
  • Replay divergence: the condition where replay's command sequence differs from the originally recorded one (I1).
  • Run id: an identifier for a specific execution attempt; new on retry or continue-as-new.
  • Schedule-to-close timeout: the maximum total time an activity may take across all retries (§8.7, ADR-15).
  • Schedule-to-start timeout: the maximum time an activity task may wait in queue before a worker starts it (§8.7, ADR-15).
  • Shard: a slice of workflow executions owned by exactly one history process at a time (§3.2, P5).
  • Side effect: a workflow operation whose result is recorded once via a marker and replayed thereafter (§8.1).
  • Signal: an asynchronous, durable event sent to a running workflow, becoming part of its history (§8.8, I10).
  • Sticky cache: the worker-side, build-id-bound cache of replayed workflow state (§22, P12).
  • Sticky execution: routing subsequent workflow tasks for an execution to the same worker that last touched it (§3.3, ADR-12).
  • Task queue: a named channel matching tasks to workers (§11).
  • Task token: an opaque, HMAC-signed handle a worker returns to complete a task (§8.11).
  • Version marker: the recorded result of a ctx.patched() evaluation, immutable for the life of its run (I13).
  • Visibility store: the denormalized, eventually-consistent index supporting workflow listing and search (§8.12, I14).
  • Workflow: a long-lived, durable, deterministic function from input to output, expressed as user code (§1).
  • Workflow id: the caller-chosen, durable external identity for a workflow, stable across runs.
  • Workflow task: a unit dispatched to a workflow worker for replay and decision emission (§8.4).
  • Worker: a process that polls task queues and executes workflow or activity code (§3).
