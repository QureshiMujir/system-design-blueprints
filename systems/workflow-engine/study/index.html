32. Mental Models & First Principles

MM1 — Durable execution is state-machine replication applied to application code. If execution is a deterministic function of an ordered log, crash recovery is just replay (Schneider 1990). Predicts: any two processes consuming the same history reach the same state. Bug class without it: bespoke checkpoint/resume logic per workflow instead of recovery-for-free. Resolving: §8, §13.

MM2 — The history is a program's memoized past; every non-deterministic call outside the SDK is a hole in that memo. Predicts: any call not routed through WfCtx is a replay bug waiting to happen. Bug class: intermittent, production-only nondeterminism. Resolving: §8.3, §6 (P1).

MM3 — A shard is a mini single-writer database; the cluster is many of those glued by routing, not one big database. Predicts: throughput scales by adding shards, not by making one shard faster past a point. Bug class: vertically scaling Postgres indefinitely, or forgetting fencing when adding shards. Resolving: §3.2, ADR-07, §31.

MM4 — At-least-once delivery plus idempotent effects is the only distributed "exactly-once" that exists (Helland 2007). Predicts: any activity author assuming the engine prevents duplicate side effects will eventually double-charge someone. Bug class: FM-7. Resolving: §6 (P3), §25 (FM-7).

MM5 — Continue-as-new is a return, not a call; logical lifetime and run lifetime are different axes. Predicts: code after continue_as_new is dead code. Bug class: developers writing cleanup expecting it to execute post-call. Resolving: §8.9, §20 (P8).

MM6 — A version marker is a permanent fork until proven otherwise by an empty query. Predicts: removing a patched() guard is only safe after measurement, never after a calendar date. Bug class: FM-9 versioning regressions. Resolving: §21, §27.

MM7 — Sticky cache is a hint, never a source of truth; treat every hit as a possibly-wrong guess the system can unwind. Predicts: correctness never depends on cache freshness, only latency does. Bug class: FM-6, and the temptation to skip the fallback path "because it's rare." Resolving: §22 (P12).

MM8 — Replay cost is linear in history length, so unboundedness anywhere in history is unboundedness in latency everywhere downstream. Predicts: any workflow shape without a periodic reset accumulates a hidden O(n) tax that eventually dominates. Bug class: FM-8, "why did this workflow get slow after a year." Resolving: §31, §34.

MM9 — A query is a true read only if the type system, not the author's intent, forbids mutation. Predicts: a query that "shouldn't" mutate but isn't structurally prevented from doing so eventually will. Bug class: subtle history corruption from a command-emitting query handler. Resolving: §8.8, P10, I11.

5. Required Reading

Books

  • Kleppmann, Designing Data-Intensive Applications, Ch. 11 "Stream Processing" (event sourcing, CQRS, state/streams/immutability). Extract: history-as-log-of-truth, current state as derived view. Applied in §8.
  • Kleppmann, Designing Data-Intensive Applications, Ch. 9 "Consistency and Consensus" (linearizability, fencing tokens, leader election). Extract: the fencing-token pattern for shard ownership. Applied in Phase 6, ADR-07.
  • Richardson, Microservices Patterns, Ch. 4 "Managing Transactions with Sagas". Extract: compensation-based transaction model, contrasted against this blueprint's replay model. Applied in §1.
  • Newman, Building Microservices, 2nd ed., Ch. 6 "Workflow". Extract: orchestration-vs-choreography vocabulary. Applied in §33.
  • **Nygard, Release It!, 2nd ed., Stability Patterns chapter (Timeout, Circuit Breaker, Bulkhead)**. Extract: timeout taxonomy and backpressure discipline. Applied in Phase 4.
  • Fowler, martinfowler.com, "Event Sourcing" (article). Extract: history as source of truth, projections as derived views. Applied in §8.
  • Young, published CQRS work ("CQRS Documents" and related articles). Extract: command/query separation, the query-must-not-mutate rule. Applied in §8 (query semantics).

Papers

  • Helland, "Life Beyond Distributed Transactions," CIDR 2007. No cross-service ACID; idempotent, at-least-once effects are the achievable contract. Applied in §1, P3.
  • Garcia-Molina & Salem, SIGMOD 1987 (Sagas). Compensation-based long-lived transactions; the contrast model for the rank-97 sibling. Applied in §1.
  • Lamport, "Time, Clocks, and the Ordering of Events in a Distributed System," CACM 1978. Logical vs. wall-clock time; motivates ctx.now(). Applied in §8, P1.
  • Chandy & Lamport, "Distributed Snapshots," ACM TOCS 1985. Consistent-cut reasoning; informs shard-recovery correctness. Applied in Phase 6.
  • Schneider, "Implementing Fault-Tolerant Services Using the State Machine Approach," ACM Computing Surveys 1990. The central citation: replay determinism as state-machine replication. Applied in §6 (P1, P4), §8.
  • Birman & Joseph, "Exploiting Virtual Synchrony in Distributed Systems," 1987. Ordered, agreed delivery; informs signal-buffering and sticky-cache consistency reasoning. Applied in Phase 6, Phase 7.
  • Ongaro & Ousterhout, "In Search of an Understandable Consensus Algorithm (Raft)," USENIX ATC 2014. Leader terms and fencing; the model for shard-lease ownership. Applied in Phase 6, ADR-07.
  • Corbett et al., "Spanner: Google's Globally-Distributed Database," OSDI 2012. External consistency and commit-wait; informs the RPO=0 / consistency-model discussion. Applied in §4, §27.
  • Bernstein, Bykov et al., "Orleans: Distributed Virtual Actors for Programmability and Scalability," Microsoft Research TR 2014. The durable-actor alternative model. Applied in §33, §36.
  • Barga et al., "Persistent Applications via Automatic Recovery," 2004 (recovery guarantees for workflows). Applied in §8 (execution state machine), §27.
  • Dean & Barroso, "The Tail at Scale," CACM 2013. Tail-latency amplification under fan-out; informs dispatch-latency targets. Applied in §30.
  • Kreps, Narkhede, Rao, "Kafka: a Distributed Messaging System for Log Processing," NetDB 2011. Log-as-source-of-truth at scale. Applied in §9 (ADR-08, ADR-10).
  • Kreps, "The Log: What Every Software Engineer Should Know About Real-Time Data's Unifying Abstraction," LinkedIn Engineering 2013 (article). Applied in §2, §8.

Reference Implementations

  • Temporal, service/history/. Shard ownership, mutable-state cache, transactional append. Lesson: fencing tokens are load-bearing, not defensive. Pitfall not to copy: coupling activity execution into the history service (kills independent scaling). Applied in Phase 6.
  • Temporal, service/matching/. In-memory task-queue rings, long-poll matching. Lesson: matching can be stateless because durable truth lives in history. Pitfall: do not persist queue state — it recreates a second source of truth. Applied in Phase 2.
  • Temporal, common/persistence/. Storage-engine abstraction over the event/execution/timer schema. Lesson: keep the persistence trait narrow so alternate backends (Cassandra, FoundationDB) are swappable. Applied in Phase 0, ADR-06.
  • Cadence (Uber, 2017 open source; Temporal's predecessor). Lesson: sticky execution is essential, not optional — without it replay cost crushes the server. Pitfall: signal buffering that isn't transactional with task completion loses signals. Applied in Phase 7, Phase 6.
  • Apache Airflow (DAG-scheduler contrast). Lesson: a fresh-process-per-task model sidesteps determinism entirely, at the cost of in-workflow control flow. Pitfall not to copy: DAG-file-as-code loaded and executed on the control plane (a real CVE history — CVE-2020-17511, CVE-2022-40189 — of privileged code execution). Applied in §33, §36.
  • Restate. A newer durable-execution system with a cleaner journal/service model. Lesson: worth studying for its simplified take on the replay contract. Applied in §33.

Glossary (§38) · 49 terms · site-wide glossary

Activity
: a unit of side-effecting work invoked by a workflow; idempotent by convention, not by engine guarantee (P3).
Activity task
: a unit dispatched to an activity worker for execution; at-least-once delivery (ADR-14).
At-least-once
: the delivery guarantee for activities — dispatched one or more times, never zero (P3, Helland 2007).
Build id
: a reproducible fingerprint identifying a worker binary version; sticky-cache validity is bound to it (P12, I12).
Child workflow
: a workflow started by another workflow as a sub-execution, linked via ChildWorkflowRef (§8.9).
Command
: a workflow's emitted intent during a workflow task, translated into one or more history events on acceptance (§8.2).
Command/event correlation
: the ordered matching of emitted commands to recorded history events that makes replay verifiable (P6, I1).
Continue-as-new
: terminate the current run and start a new run under the same WorkflowId with a new RunId, bounding history (P8, I6).
Determinism
: the property that workflow code, given the same history, always produces the same commands in the same order (P1).
Determinism violation
: a replay producing a command that mismatches the recorded history event at that position (I1).
Deterministic replay
: re-executing a workflow function against its history to reconstruct in-memory state without side effects (§8.2).
Durable execution
: making ordinary control flow survive crashes and restarts via event-sourced replay (§1).
Event sourcing
: modeling state as a sequence of immutable events rather than mutable current state (Fowler; Kleppmann DDIA ch. 11).
Exactly-once effect
: the (cooperative, not engine-guaranteed) property that an idempotent activity produces one durable real-world effect despite at-least-once delivery (P3).
Execution
: an instance of a workflow, identified by (namespace, workflow_id, run_id).
Fencing token
: a monotonic identifier (range_id) preventing a stale shard owner from corrupting state (P5, I9).
Heartbeat
: a periodic liveness signal from an activity, resetting its heartbeat deadline and persisting resumable progress (§8.7).
History
: the ordered, append-only sequence of events defining a workflow execution — the system of record (P2, I2).
History event
: one entry in a History; the atomic unit of durable truth (§8.1).
History service
: the sharded server component owning durable state mutation for workflow executions (§3).
Idempotency key
: an application-supplied token letting a duplicated activity invocation be recognized and deduplicated by the downstream system (P3).
Long poll
: a blocking RPC pattern used by matching to hand off tasks to waiting workers (ADR-11).
Marker
: a special history event recording SDK-internal information (side effects, version stamps) (§8.1).
Matching service
: the server component routing tasks to workers via task queues (§3).
Namespace
: a tenant boundary for isolation, quota, and retention configuration (P13).
Non-determinism error
: the error raised when replay's emitted command mismatches its corresponding history event (I1).
Patch
: the code branch introduced behind a ctx.patched() guard (§8.10).
Payload
: the opaque, content-typed byte wrapper the engine never deserializes into application types (P14).
Query
: a synchronous, side-effect-free read of workflow state (P10, I11).
Query-must-not-mutate
: the rule that query handlers may never emit commands (P10, I11).
Replay
: re-executing a workflow function against its recorded history (§8.2).
Replay compatibility
: the guarantee that a history recorded against one code build remains replayable against a later, compatible build (§27).
Replay divergence
: the condition where replay's command sequence differs from the originally recorded one (I1).
Run id
: an identifier for a specific execution attempt; new on retry or continue-as-new.
Schedule-to-close timeout
: the maximum total time an activity may take across all retries (§8.7, ADR-15).
Schedule-to-start timeout
: the maximum time an activity task may wait in queue before a worker starts it (§8.7, ADR-15).
Shard
: a slice of workflow executions owned by exactly one history process at a time (§3.2, P5).
Side effect
: a workflow operation whose result is recorded once via a marker and replayed thereafter (§8.1).
Signal
: an asynchronous, durable event sent to a running workflow, becoming part of its history (§8.8, I10).
Sticky cache
: the worker-side, build-id-bound cache of replayed workflow state (§22, P12).
Sticky execution
: routing subsequent workflow tasks for an execution to the same worker that last touched it (§3.3, ADR-12).
Task queue
: a named channel matching tasks to workers (§11).
Task token
: an opaque, HMAC-signed handle a worker returns to complete a task (§8.11).
Version marker
: the recorded result of a ctx.patched() evaluation, immutable for the life of its run (I13).
Visibility store
: the denormalized, eventually-consistent index supporting workflow listing and search (§8.12, I14).
Workflow
: a long-lived, durable, deterministic function from input to output, expressed as user code (§1).
Workflow id
: the caller-chosen, durable external identity for a workflow, stable across runs.
Workflow task
: a unit dispatched to a workflow worker for replay and decision emission (§8.4).
Worker
: a process that polls task queues and executes workflow or activity code (§3).
