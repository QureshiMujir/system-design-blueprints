Client/starter SDK. Tenant-facing entry point (trust boundary A); issues StartWorkflow, SignalWorkflowExecution, QueryWorkflow, RequestCancelWorkflowExecution, ListWorkflowExecutions. Never touches history directly.

Frontend service. Stateless gRPC gateway; authn/authz, per-namespace rate limiting (ADR-23), routes each RPC to history or matching by shard/queue lookup. The sole crossing of protocol boundary 1.

History service. Sharded (§3.2); owns the event log and denormalized mutable execution state per execution; runs the timer service as a per-shard poll loop; the only writer of its owned shards (trust boundary B, fenced by range_id, P5/I9).

Matching service. Holds in-memory workflow-task and activity-task queues; long-polls from workers; stateless with respect to durable data — durable truth always lives in history (P2).

Persistence layer. Postgres tables for events, executions, timers, activity_info, visibility (ADR-06); the sole persistence boundary (boundary 2) — every durability guarantee in this document reduces to a transaction committed here.

Worker SDK. Embedded in tenant processes; hosts the deterministic replay runtime (WfExecutor, concurrency boundary D — single-threaded, non-tokio) for workflow-task handling, plus an activity-task handler that runs arbitrary (trust boundary C, untrusted relative to the cluster) tenant code with real tokio concurrency; maintains the sticky cache (build-id bound, P12).

Visibility indexer. Consumes committed history/execution-state changes asynchronously and denormalizes into the visibility store (I14); never a write path for control decisions.

3.1 Why Three Services, Not One

Ship as a monolith through Phase 5; split when matching's long-poll bookkeeping load and history's transactional-write load start contending for the same process's resources — not before. In steady state: frontend scales horizontally without coordination; history scales by adding shards and processes, bounded by lease coordination overhead (§31); matching scales by adding queue-serving replicas per task queue.

3.2 Sharding Strategy

Hash (namespace, workflow_id) into a fixed shard count (512 at GA, ADR-07). Each shard has exactly one owning history process at a time, elected via a lease with a monotonic range_id fencing token (Ongaro & Ousterhout 2014's term-based reasoning applied to storage writes). Ownership is required because history append must be linearized per workflow, timer firing must not double-fire, and the in-memory mutable-state cache needs a single home.

3.3 Data Flow For One Workflow Task

A worker long-polls a workflow-task queue on matching. When history schedules a task (because a triggering event was appended), matching hands it to a waiting poller. The worker fetches history (sticky cache, or full fetch from history service), replays, emits new commands, calls RespondWorkflowTaskCompleted. History validates commands against current state (I1), appends events transactionally, schedules follow-on work (timers, activity tasks, child-workflow starts), and notifies matching to enqueue the resulting activity tasks. This round trip is one workflow task; most workflows are a sequence of these separated by activity execution or timer waits.

8.7 Timer And Heartbeat Models

A durable timer is a row (shard_id, fire_time, workflow_id, run_id, timer_id); the owning shard's poll loop (100 ms interval, I5/P7) converts an expired row into TimerFired plus WorkflowTaskScheduled, transactionally. Heartbeats: an activity worker sends heartbeat_details at 20% of heartbeat_timeout; the server resets the heartbeat deadline on receipt and persists heartbeat_details in activity_info so a retried attempt resumes from the last checkpoint rather than from scratch; a missed heartbeat_timeout produces ActivityTaskTimedOut{timeout_type: Heartbeat}.

8.8 Signal And Query Semantics

Signals are async and durable: WorkflowExecutionSignaled is appended and dispatched to the registered SignalChannel; signals arriving while a workflow task is in flight are buffered (I10) and applied in arrival order before the next task. Queries are synchronous and side-effect-free (P10, I11): no event is appended; the handler runs against a read-only WfCtx view of current (or sticky-cached) state; the query-must-not-mutate rule is enforced by disallowing every command-emitting primitive inside a registered query handler.

8.9 Child-Workflow And Continue-As-New Linkage

ChildWorkflowRef carries the child's (namespace, workflow_id, run_id) and the parent's initiating event id; a parent-child cancellation policy (ABANDON / REQUEST_CANCEL / TERMINATE) governs propagation on parent cancellation. Continue-as-new links two runs by a one-way back-pointer only: the old run's WorkflowExecutionContinuedAsNew carries new_run_id; the new run's WorkflowExecutionStarted carries continued_from_run_id. A run's own history never spans a continue-as-new boundary (I6).

8.14 Malformed-Input And Failure-Path Examples

  • Replay command mismatch: replay emits ScheduleActivity("ship") where history's next event is ActivityTaskScheduled{type:"charge"} → NonDeterminismError, task failed (I1).
  • Activity result for unknown scheduled id: RespondActivityTaskCompleted references an activity_id absent from activity_info → rejected at the persistence boundary, corruption alarm raised.
  • History gap: append encounters a requested event_id that skips ahead of next_event_id → rejected (I2); shard recovery pauses pending manual repair.
  • Duplicate event id: append targets an already-used event_id → rejected at the unique-key constraint (I2).
  • Signal to closed execution: SignalWorkflowExecution targets a closed execution → rejected with ExecutionClosedError, not buffered (contrast with I10, which only applies to open executions).
  • Failure-path example: a workflow task fails determinism (I1) → WorkflowTaskFailed → retried up to 5 attempts → still fails → execution flagged task-failure-stuck → operator uses ResetWorkflowExecution to roll back to the last known-good event and resumes from there (§27).
