⬜ Phase 0 — Skeleton: Complex type, naïve DFT oracle, bench harness, conformance scaffold §12

Objectives
  • Stand up the Cargo workspace (ADR-2) and the fft-core + simd + conformance skeleton.
  • Define Complex<T>, the Float trait (f32/f64), Direction/Normalization/Layout, error type, machine probe.
  • Ship the trusted naïve O(N²) DFT oracle — the truth every later phase diffs against.
  • Establish the bench + conformance scaffolding (flop model, error-bound checker) reused everywhere.
Deliverable
  • cargo run -p bench --bin probe prints cache sizes, ISA, vreg count, FMA-peak estimate.
  • cargo test runs the oracle on hand-computed cases (δ→flat, constant→DC) and the Complex unit tests.
Acceptance
  • Oracle reproduces hand-computed 8-point cases (§8.5) exactly (to ε).
  • Oracle round-trip ‖idft(dft(x))−x‖/‖x‖ ≤ c·N·ε on 10³ random vectors (naïve bound).
  • Complex arithmetic + alignment pass Miri (no UB); probe correct on CI x86-64 and aarch64.
Fixtures
  • dft/oracle_{delta,constant,ramp,random}.json — inputs + expected + tolerance.
  • numerics/complex_mul_assoc.json — complex arithmetic sanity.
  • golden/probe_{x86,aarch64}.json — expected Machine per CI arch.
Pitfalls
  • Exponent-sign convention: forward is e^{−2πi…} (Direction::Forward=-1) — flipping it conjugates everything; pin it once (I7, ADR-11).
  • 3-mul complex multiply tempts here — rejected (ADR-19); worse FP error, harder to vectorize.
  • Aligned alloc must be paired with aligned free → wrap exclusively in AlignedArena.
  • Oracle must use a stable summation order so its own result is reproducible (it is the reference).

⬜ Phase 1 — Radix-2 DIT + bit-reversal (recursive, correctness-first) §13

Objectives
  • Implement a recursive radix-2 DIT FFT for power-of-2 N (clarity over speed).
  • Implement the bit-reversal permutation and prove it is a bijection (I3).
  • First green diff against the oracle — the correctness anchor for the whole power-of-2 family.
Deliverable
  • A correct (if unoptimized) power-of-2 FFT; examples/fft_basic transforms a vector and prints the spectrum.
Acceptance
  • Matches oracle within c·log₂N·ε·‖x‖ for all power-of-2 N ≤ 2¹⁶ (I2).
  • Bit-reversal bijection test passes for all N ≤ 2²⁰ (histogram of targets all-ones, I3).
  • Round-trip ‖IFFT(FFT(x))−x‖/‖x‖ ≤ c·log₂N·ε (I5).
Fixtures
  • dft/radix2_pow2_sweep.json — every power-of-2 size vs oracle.
  • dft/bitreverse_{8,16,1024}.json — known bit-reversal mappings.
  • numerics/roundtrip_pow2.json — forward∘inverse identity.
Pitfalls
  • Off-by-one in bit-reversal (reversing b vs b−1 bits) → silently wrong order; the bijection + oracle tests catch it.
  • DIT requires bit-reversed input (or bit-reversed output if you reorder after) — mixing the two scrambles results.
  • Twiddle sign again (−2πi) — assert one length-4 case by hand.
  • Recursion base case (N=1 returns the input; N=2 is a single butterfly with w=1).

⬜ Phase 2 — Twiddle generation + caching, and radix-2 DIF §14

Objectives
  • Build the twiddle crate: generate W_N^k tables (direct-trig + recurrence), cache them, prove correctness (I7).
  • Implement radix-2 DIF (natural input, bit-reversed output) — the transpose of DIT.
  • Remove per-butterfly trig (the P1 bottleneck) by precomputing tables once per N.
Deliverable
  • Twiddle cache; both DIT and DIF correct vs oracle; a measurable speedup over P1 from cached twiddles.
Acceptance
  • Twiddle table vs direct (cos,−sin) reference: max error ≤ c·ε (direct), bounded drift (recurrence) (I7).
  • DIF matches oracle within bound; DIF∘(bit-reverse) == DIT result.
  • Twiddle cache hit avoids regeneration (hit-rate counter > 0 on repeated transforms).
Fixtures
  • numerics/twiddle_table_{64,4096}.json — table vs direct-trig reference.
  • numerics/twiddle_recurrence_drift.json — recurrence error stays bounded.
  • dft/radix2_dif_sweep.json — DIF vs oracle.
Pitfalls
  • Recurrence twiddle drift: naïve W^{k+1}=W^k·W accumulates ~O(k)·ε error → ruins accuracy for large N unless re-seeded (I7).
  • Storing only the first half (0..N/2) requires sign-flip logic for the second half — test the boundary.
  • DIF vs DIT confusion: DIF needs bit-reversal after, DIT before; mislabeling scrambles output ordering.
  • Cache key must include dtype (f32 and f64 tables differ).

⬜ Phase 3 — Iterative in-place FFT + accuracy bounds §15

Objectives
  • Replace recursion with the iterative in-place radix-2 FFT (the standard production form): bit-reverse once, then log₂N stages of butterflies with stride-doubling.
  • Establish and assert the formal accuracy bounds (~c·log₂N·ε·‖x‖) — the project's numerical contract and selling point.
  • Make the transform allocation-free given pre-generated twiddles (toward I14).
Deliverable
  • Iterative in-place radix-2 FFT; accuracy/Parseval/round-trip bounds asserted across sizes; zero steady-state alloc.
Acceptance
  • Measured RMS error vs oracle ≤ c·log₂N·ε·‖x‖ for all power-of-2 N ≤ 2²⁰ (I2) — and demonstrably lower than the naïve DFT's ~N·ε (the selling point, logged side-by-side).
  • Parseval residual ≤ c·log₂N·ε·E (I8).
  • Zero allocations inside the transform (I14, alloc-counter test).
  • Iterative form ≥ 5× faster than the P1 recursive form (no call overhead, cached twiddles).
Fixtures
  • numerics/accuracy_bound_sweep.json — measured error vs c·log₂N·ε per size (incl. naïve comparison).
  • numerics/parseval_sweep.json — energy preservation.
  • numerics/alloc_free_execute.json — alloc-count assertion.
Pitfalls
  • Stride/index arithmetic in the stage loop is the classic bug nest → derive tw index (j·N/len) carefully; the oracle diff catches errors.
  • In-place butterflies must read both operands before writing either (read a,b, then write a',b').
  • Accumulation order changes bits vs the recursive form → that is expected (different plan); assert bounds, not equality (I4).
  • Forgetting twiddle stride per stage (N/len) → wrong twiddles, plausible-but-wrong output.

⬜ Phase 4 — Radix-4 and split-radix (flop reduction) §16

Objectives
  • Implement radix-4 butterflies (4 points/stage; ±i multiplies are free) — fewer twiddle multiplies, fewer stages (log₄N).
  • Implement split-radix (radix-2/4 hybrid) — the lowest known flop count for power-of-2 (~4N log₂N real ops vs radix-2's ~5N log₂N).
  • Demonstrate the flop reduction as a measurable speedup with unchanged accuracy.
Deliverable
  • Radix-4 and split-radix transforms correct vs oracle; flop-count and timing comparison vs radix-2.
Acceptance
  • Both match the oracle within c·log₂N·ε·‖x‖ (accuracy unchanged from radix-2, I2).
  • Split-radix performs measurably fewer real flops and runs faster than radix-2 for N ≥ 256 (flop model + timing confirm).
  • Radix-4 produces identical-within-bound results to radix-2 for power-of-4 sizes.
Fixtures
  • dft/radix4_pow4_sweep.json — radix-4 vs oracle (power-of-4 sizes).
  • dft/split_radix_sweep.json — split-radix vs oracle (power-of-2).
  • numerics/split_radix_flopcount.json — measured flop count ≈ 4N log₂N.
Pitfalls
  • ±i multiply: implement as (re,im)→(∓im,±re), not a complex multiply — getting the sign/swap wrong is a subtle correctness bug.
  • Split-radix's irregular (L-shaped) recursion is index-error-prone → derive the X[4k+1]/X[4k+3] indices carefully; oracle diff is the net.
  • The W^{3k} table must match the W^k convention (same sign) — a separate table, same generator (I7).
  • Output ordering for split-radix differs from radix-2 → handle the permutation consistently.

⬜ Phase 5 — Mixed-radix for composite N §17

Objectives
  • Implement general Cooley–Tukey for composite N = N₁·N₂ (the four-step / index-decomposition view, §8.7).
  • Provide hand-written small-prime codelets (radix-3, 5, 7, 8) as the building blocks.
  • Support any composite N (e.g. 6, 12, 360, 1000, 44100) — the bulk of real-world sizes.
Deliverable
  • FFT of arbitrary composite N correct vs oracle; examples/fft_basic works for non-power-of-2 sizes.
Acceptance
  • Matches oracle within bound for composite N ∈ {6,9,12,15,60,360,1000,1024·3, 44100, 48000} (I2).
  • Factorization is correct (product of factors == N) and balanced.
  • Small-prime codelets (r3/r5/r7) match oracle exactly for their base sizes.
Fixtures
  • dft/mixedradix_composite.json — a spread of composite sizes vs oracle.
  • dft/codelet_{r3,r5,r7,r8}.json — base-size codelet correctness.
  • numerics/factor_correctness.json — factorization product == N.
Pitfalls
  • The inter-stage twiddle multiply is easy to misplace or mis-index (W_N^{n₂k₁}) → the classic mixed-radix bug; derive against the oracle.
  • Data layout: the four-step view requires viewing the 1-D array as an N₁×N₂ matrix (row/column reads) → strided access; get the transpose right.
  • Small-prime codelet twiddle constants (e.g. radix-3 uses cos(2π/3)=−0.5, sin(2π/3)=√3/2) must carry the right sign for the forward convention.
  • Unbalanced factorization (e.g. N = large_prime · 2) → falls to Bluestein/Rader (P6); detect and route.

⬜ Phase 6 — Bluestein (chirp-z) + Rader (prime / arbitrary N) §18

Objectives
  • Implement Bluestein's chirp-z transform: FFT of any N via a power-of-2 convolution (§8.8) — eliminates the "unsupported size" case.
  • Implement Rader's algorithm for prime N via a length-(N−1) cyclic convolution + primitive root.
  • Bound the prime-size performance cliff (constant-factor, not asymptotic).
Deliverable
  • FFT of any N (including large primes like 1009, 65537) correct vs oracle.
Acceptance
  • Matches oracle within bound for prime N ∈ {3,5,7,13,17,1009,65537} and awkward N ∈ {2·1009, 1000003} (I2, I10).
  • Bluestein result == direct DFT within bound for arbitrary N (the convolution identity holds, I10).
  • Prime-N (Bluestein) within ~3–6× of the nearest power-of-2 FFT (cliff bounded, §4).
Fixtures
  • prime/bluestein_sweep.json — many prime + arbitrary sizes vs oracle.
  • prime/rader_prime.json — Rader path for primes vs oracle.
  • prime/primitive_root.json — primitive-root correctness for small primes.
  • numerics/bluestein_chirp_accuracy.json — chirp accuracy (the n²/2 exponent risks precision loss).
Pitfalls
  • Chirp exponent n²/2: for large N, n² overflows or loses precision in the exponent → compute W_N^{(n² mod 2N)/2} (reduce mod 2N) to keep the angle accurate (I7).
  • Bluestein accuracy is worse than direct Cooley–Tukey (extra transforms + chirp multiplies) → document the error inflation; still within O(log M)·ε.
  • Rader needs N prime (a primitive root exists); for prime powers use a different (Winograd/PFA) route or Bluestein — detect.
  • Padding M must be ≥ 2N−1 (else circular convolution wraps and corrupts) — and a power of 2 for the inner FFT.
  • DC term in Rader is handled separately — forgetting it drops X[0].

⬜ Phase 7 — Real-input RFFT / IRFFT (Hermitian symmetry) §19

Objectives
  • Implement RFFT (real → N/2+1 complex Hermitian) and IRFFT (Hermitian → real), exploiting X[N−k]=conj(X[k]) for ~2× speed and ½ memory (§8.6, I6).
  • Implement the "two real FFTs from one complex FFT" trick.
  • Define and validate the Hermitian / halfcomplex storage contract.
Deliverable
  • RFFT/IRFFT for even and odd N; examples/rfft_spectrum computes a real signal's spectrum.
Acceptance
  • RFFT output is exactly Hermitian (X[N−k]=conj(X[k]), X[0].im=X[N/2].im=0) — verified by reconstruction (I6).
  • RFFT matches the first N/2+1 bins of the full c2c FFT within bound (I2).
  • IRFFT∘RFFT = identity within c·log₂N·ε (I5).
  • RFFT ≈ 1.7–2× faster and ½ memory vs c2c of the same N (§4).
Fixtures
  • real/rfft_even_odd.json — RFFT vs c2c (even and odd N).
  • real/hermitian_symmetry.json — output symmetry check (I6).
  • real/irfft_roundtrip.json — IRFFT∘RFFT identity.
  • real/two_real_trick.json — two-signal separation correctness.
Pitfalls
  • The unscramble pass twiddle indexing is subtle (it mixes X[k] and conj(X[N/2−k])) → derive carefully; the c2c comparison catches errors.
  • X[0] (DC) and X[N/2] (Nyquist) are purely real — a packing that stores their imaginary parts as nonzero is a bug (I6).
  • Odd N has no Nyquist bin → the layout differs; handle separately.
  • Halfcomplex layout ordering (re's ascending, im's descending) is easy to get backwards → pin the contract, test.

⬜ Phase 8 — Inverse + normalization conventions + FFT convolution §20

Objectives
  • Make the inverse FFT (IFFT) and normalization conventions (None/1/N/1/√N) explicit and configurable (§8.1, I5, ADR-11).
  • Implement FFT-based convolution (linear & circular) and streaming overlap-add / overlap-save (§8.9).
  • Wire the bignum-multiplication hook for #370 (the FFT-convolution consumer).
Deliverable
  • IFFT with all normalization conventions; linear/circular convolution; overlap-add/save; the bignum hook.
Acceptance
  • IFFT∘FFT = identity within c·log₂N·ε under each normalization convention; double-normalization guarded (I5).
  • fft_conv matches a direct O(N·M) convolution within bound.
  • overlap-add and overlap-save produce identical results to a single large convolution.
  • bignum hook: FFT-multiply of two integer arrays matches schoolbook multiply for sizes within the f64 precision limit.
Fixtures
  • numerics/normalization_{none,oneovern,unitary}.json — round-trip per convention.
  • convolution/linear_vs_direct.json — FFT conv vs direct.
  • convolution/overlap_add_save_equiv.json — streaming == single conv.
  • convolution/bignum_multiply.json — FFT multiply vs schoolbook (bounded sizes).
Pitfalls
  • Normalization applied twice (once in IFFT, once by the caller) → the guard + the convention id (I5) prevent it.
  • Linear vs circular: insufficient zero-padding silently gives circular (wrap-around) results → the consumer must pad; document loudly.
  • overlap-save discards the wrap-corrupted block prefix; overlap-add sums tails — mixing the two corrupts output.
  • bignum: f64 has 53 mantissa bits → products exceeding ~2⁵³ lose precision in the carry step → cap digit size or use NTT (deferred); a silent precision bug otherwise (docs/failure-analysis/bignum-precision.md).

⬜ Phase 9 — Multi-dimensional FFT (2D / 3D, row-column) §21

Objectives
  • Implement 2D and 3D FFT via the row-column method: batched 1-D FFTs along each axis (§ box multidim).
  • Support real-input 2D RFFT (for images / codecs / #173).
  • Parallelize the independent rows/columns across threads (I11) and add a transpose-for-locality option.
Deliverable
  • 2D/3D c2c and 2D real FFT; examples/fft2d_image transforms an image-shaped array.
Acceptance
  • 2D/3D FFT matches a 2D/3D naïve DFT oracle within bound (I2).
  • Row-column == direct multi-dim DFT (separability holds).
  • Threaded multi-dim is a disjoint cover (I11, TSan clean) and deterministic per thread count (I4).
  • 2D RFFT exploits Hermitian symmetry (≈ ½ memory along the real axis, I6).
Fixtures
  • multidim/fft2d_vs_oracle.json — 2D FFT vs 2D oracle.
  • multidim/fft3d_vs_oracle.json — 3D.
  • multidim/rfft2d.json — 2D real FFT symmetry.
  • multidim/threaded_determinism.json — same result at 1/2/4/8 threads.
Pitfalls
  • Strided column-axis FFTs thrash cache → transpose first (the row-column performance crux).
  • Mixing the axis order (which axis is contiguous) → wrong layout, plausible-but-wrong output; pin the convention (row-major: last axis contiguous).
  • 2D RFFT: which axis carries the Hermitian symmetry must be documented (usually the last/contiguous one).
  • Thread oversubscription if a batched 1-D plan is itself threaded (it should not be inside a parallel multi-dim region).

⬜ Phase 10 — The planner (estimate / measure, codelet selection, wisdom) §22

Objectives
  • Build the FFTW-style planner: factor N → a plan tree of codelets; choose via ESTIMATE (cost model) or MEASURE (timing); persist wisdom (I9, P5).
  • This is what turns the codelet zoo (P1–P9) into one coherent "best plan for this N on this machine" engine.
Deliverable
  • A planner that picks (and persists) good plans across all sizes; examples/plan_inspect + wisdom_io show plan trees and wisdom round-trip; tools/plan_inspector.
Acceptance
  • ESTIMATE plans in < 1 ms; MEASURE within the budget (§4); wisdom hit re-plans in < 100 µs (§4).
  • MEASURE chooses a plan within ~10 % of the best hand-tuned plan for common sizes.
  • Plan determinism: same (N,dir,layout,flags,ISA,dtype) → same plan tree hash (I9); wisdom round-trips losslessly.
  • A plan chosen by the planner passes the accuracy bound (I2) for its N.
Fixtures
  • golden/plan_tree_hash.json — deterministic plan-tree hashes per (N,flags,ISA) (I9).
  • golden/wisdom_roundtrip.json — export→import == identity.
  • numerics/planner_vs_handtuned.json — measured plan within tolerance of best-known.
Pitfalls
  • Cost-model miscalibration → ESTIMATE picks a poor plan (correct but slow) → MEASURE/wisdom is the safety valve; recalibrate constants per ISA.
  • Wisdom keyed on too little (omitting ISA or dtype) → a plan measured on one machine reused wrongly on another → the key must include ISA + dtype (I9).
  • MEASURE non-determinism (timing noise) → pin threads, median-of-k, stable tie-break (prefer the canonical plan on ties, I4).
  • Wisdom file corruption / version mismatch → validate on import (WisdomCorrupt error), fall back to planning (wisdom-corruption.md).
  • Combinatorial explosion of candidates in PATIENT → bound the search depth.

⬜ Phase 11 — SIMD butterfly codelets + FFTW-compatible C ABI §23

Objectives
  • Implement vectorized butterfly codelets (AVX2/FMA, with a scalar fallback) for radix-2/4/split-radix and the small-prime kernels — the performance heart (§ box simd).
  • Expose an FFTW-compatible C ABI (fftw_plan_dft_*-style + native pfft_*) — drop-in linkable.
Deliverable
  • SIMD codelets ≥ 2× the scalar form; libpfft.so/.a + pfft.h; examples/pfft_from_c.c links and runs.
Acceptance
  • SIMD codelets match the scalar fallback (and oracle) within bound (I2); no register spill (disasm/perf verified, P4).
  • A C program calling pfft_plan_dft_1d + pfft_execute gets identical results to the Rust facade.
  • f32 ≈ 2× f64 throughput (SIMD width exploited, §4).
  • No unwinding across the FFI boundary (C integration test, I12).
Fixtures
  • dft/simd_vs_scalar.json — vectorized codelets vs scalar (within bound).
  • numerics/no_register_spill.json — disasm assertion (no inner-loop spills).
  • abi/c_integration.json — a C program's result == Rust facade.
  • badargs/cabi_param_positions.json — bad-arg → error/null plan (I12).
Pitfalls
  • Complex interleave: AoS [re,im,re,im] needs shuffles to do SIMD complex multiply → planar (SoA) inside codelets (ADR-23) reduces shuffles; convert at edges. Getting the shuffle masks wrong is a subtle correctness bug.
  • Register spill from too-wide butterflies → the #1 perf cliff (like #349's micro-kernel); verify in asm (P4).
  • Unaligned load/store on user buffers (the C caller may pass unaligned data) → handle a misaligned head/tail or copy into aligned scratch.
  • Panic across FFI = UB → catch_unwind everywhere (I12).
  • FFTW symbol collision if both libs are linked → namespace under pfft_*, make fftw_* aliases opt-in.

⬜ Phase 12 — Performance hardening (the long pole) §24

Objectives
  • Close to ≥ 60 % of the 5N·log₂N flop ceiling across the full size sweep; bound the prime-N cliff.
  • Levers: bit-reversal/transpose cache optimization, codelet tuning, twiddle-layout, small-N specialization, AVX-512/NEON codelets (gated), prefetch.
Deliverable
  • GFLOP/s sweep meeting §4 across N ∈ [16, 2²⁴] (pow2, composite, prime); AVX-512 path measurable on a capable CPU.
Acceptance
  • ≥ 60 % flop ceiling (pow2, f64, 1 thread) sustained across the sweep.
  • Small-N codelets beat the general path below threshold.
  • Prime-N cliff bounded to ~3–6× (§4); AVX-512 ≈ 2× AVX2 where available.
  • No accuracy regression (re-diff oracle, I2).
Fixtures
  • golden/gflops_sweep_full.json — per-size flop-fraction floor (pow2/composite/prime).
  • dft/small_n_codelets.json — small-N specialization correctness + crossover.
  • ISA-specific golden hashes; bench/pow2_vs_prime curve.
Pitfalls
  • Bit-reversal cache misses dominate large-N FFTs → a blocked permutation is the key win; measure miss rates.
  • AVX-512 downclocking can make it slower than AVX2 for bandwidth-bound (large-N) FFTs → measure, don't assume (like #349).
  • Small-N overhead (the general machinery) → branch to specialized codelets early.
  • On-the-fly twiddles trade bandwidth for trig flops → the right choice is size- and ISA-dependent; measure.
  • NEON has 32 registers → a different butterfly width optimum than AVX2's 16.

⬜ Phase 13 — Conformance, differential, fuzzing, benchmarks §25

Objectives
  • Lock correctness and performance with a full conformance suite.
  • Components: differential vs the O(N²) oracle, numerical error-bound + Parseval + round-trip assertions, an FFTW differential harness, codelet/permutation/Bluestein fuzzing, and a reproducible GFLOP/s report.
Deliverable
  • make conformance green; make bench emits a report; make fuzz runs N iterations clean.
Acceptance
  • 100 % differential pass within bounds across the full case space (I2).
  • FFTW differential agrees within bound for all tested sizes.
  • Fuzz clean ≥ 10⁷ iterations (extended 30-day runs deferred).
  • Determinism hashes stable; bench meets all §4 constraints; coverage of all transform types (c2c/r2c/c2r/2d/3d/conv).
Fixtures
  • Full conformance/ corpora: dft/, real/, prime/, multidim/, numerics/, convolution/, badargs/, golden/.
  • Structured inputs (impulses, sinusoids at exact bins, chirps, random) with known spectra.
Pitfalls
  • Tolerance too tight (false fails on legit rounding) or too loose (misses bugs) → derive from theory (Higham §24, c·log₂N·ε).
  • Fuzz corpus not exercising prime/awkward N or non-vlen-multiple sizes → bias the generator toward edges.
  • Determinism hash breaks legitimately when the planner changes → version the golden set with the numeric contract (I4/I9).
  • FFTW differential masking a shared-convention bug (both use the same sign) → keep the independent oracle as the primary truth.
  • Bench noise (turbo, noisy neighbors) → pin + median.
