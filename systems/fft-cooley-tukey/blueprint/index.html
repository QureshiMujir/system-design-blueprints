369 — FFT / Cooley–Tukey

Goal: Implement, from scratch in Rust, a general-purpose, production-grade Fast Fourier Transform library: the Cooley–Tukey divide-and-conquer family (radix-2/4 DIT+DIF, split-radix, mixed-radix for composite N) plus Bluestein (chirp-z) and Rader for prime/arbitrary N, a Hermitian-symmetry real-input RFFT/IRFFT, multi-dimensional (2D/3D row-column) transforms, FFT-based convolution (overlap-add/save) and a hook for FFT-based bignum multiplication, behind an FFTW-style planner (estimate vs measure, codelet selection, persisted wisdom) with SIMD butterfly codelets, runtime ISA dispatch, configurable normalization conventions, and a FFTW-compatible C ABI. Crates: fft-core / radix / twiddle / mixedradix / bluestein / real / multidim / planner / convolution / simd / cabi / bench / conformance. It is a standalone numerical FFT engine modeling the FFTW / PocketFFT / KISS-FFT / MKL-FFT family — not a DSP/audio library (#174, a sibling/consumer), not a general linear-algebra runtime (#349, a sibling), not a DCT/codec (#173/#380, related). Correctness is validated by differential tests against a naïve O(N²) DFT oracle within proven error bounds, by a round-trip (FFT∘IFFT) identity, by Parseval/energy and bit-reversal-bijection checks, and by an FFTW differential harness; performance by a 5N·log₂N-flop roofline / fraction-of-peak benchmark harness.

1. Goal

1.1 Engineering Definition

Build a from-scratch FFT runtime: complex type + naïve DFT oracle → radix-2 DIT (bit-reversal) → twiddle generation/caching + radix-2 DIF → iterative in-place + error bounds → radix-4 / split-radix (flop reduction) → mixed-radix (composite N) → Bluestein + Rader (prime/arbitrary N) → real-input RFFT/IRFFT → inverse + normalization + FFT convolution → multi-dimensional → an FFTW-style planner (estimate/measure + wisdom) → SIMD codelets + C ABI. Numerics are IEEE-754 f32/f64 complex (Complex<f32>/Complex<f64>).

1.2 System Boundaries

  • In scope: the DFT X[k]=Σₙ x[n]·W_N^{nk}, W_N=e^{−2πi/N}; radix-2/4 DIT+DIF butterflies; bit-reversal permutation; twiddle generation (direct-trig vs recurrence) + caching; split-radix (lowest flops); mixed-radix for composite N (factor into small codelets); Bluestein chirp-z + Rader for prime N; RFFT/IRFFT (Hermitian packing, two-real / half-complex tricks); IFFT + normalization conventions (1/N, 1/√N, unnormalized — configurable); 2D/3D row-column FFT; FFT convolution (overlap-add / overlap-save); planner (estimate/measure, codelet plan, wisdom persistence, in-place vs out-of-place, alignment); SIMD butterfly codelets (AVX2/FMA + scalar fallback, AVX-512/NEON gated); FFTW-compatible C ABI.
  • Out of scope (non-goals): DSP/audio framework (filters, oscillators, effects) → #174 (a sibling/consumer, see §2.7); general dense linear algebra → #349; DCT/codecs → #173 image / #380 video (related transforms, cross-linked, §2.5); GPU FFT → PhaseDeferred("§39"); Number-Theoretic Transform (NTT, exact integer convolution) → PhaseDeferred("§11.12") (briefly modeled, deferred); distributed/multi-node FFT → PhaseDeferred("§39"); fixed-point/integer FFT → PhaseDeferred("§39").

1.3 Deployment Model

Shipped as (a) a Rust library crate (fft facade re-exporting the workspace), (b) a cdylib/staticlib exposing an FFTW-compatible C ABI (fftw_plan_dft_1d-style + a leaner pfft_* native ABI) drop-in linkable by C/C++/Fortran callers, (c) a CLI fftc for micro-benchmarks, conformance runs, plan inspection, wisdom import/export, and a machine probe (cache sizes, SIMD width). Single process, shared-memory threads only. Wisdom persists to a file (~/.pfft-wisdom) or an explicit path.

1.4 Target Users

FFT-library implementers; engineers who must understand why an O(N log N) transform beats O(N²) by 1000× at N=2²⁰, why twiddle precision and accumulation order set the error floor, and why a planner exists at all; downstream portfolio projects (#370 bignum reuses the convolution kernel for fast multiplication; #174 DSP could relink onto this engine; #173/#380 codecs share transform-decomposition intuition).

1.9 Recommended Language & Rationale

Rust. (a) Portfolio numerical default (#349 BLAS, #181 SIMD — both Rust) → ABI/tooling/bench-methodology reuse; (b) core::arch::x86_64/aarch64 intrinsics give bit-exact control over FMA/load/store/shuffle for the butterfly codelets with no compiler-autovectorization lottery; (c) safe Complex<T> value types with a documented unsafe seam confined to the SIMD codelets and the in-place permutation; (d) #![no_std]-capable kernel crates (codelets depend only on core); (e) extern "C" yields a clean FFTW-compatible ABI with stable #[repr(C)] plan handles. Rejected: C (FFTW/PocketFFT/KISS-FFT's language — we read it for semantics and codelet shapes; no borrow checker for the harness, manual aligned-alloc/plan-lifetime bugs); Fortran (historic FFTPACK; semantics oracle, not impl language); C++ (template-heavy expression metaprogramming — FFTW's genfft is OCaml-generated C; we write explicit Rust codelets, ABI instability); Python/NumPy (calls into FFTW/PocketFFT, defeating "from scratch"; ~100× too slow for the kernel).

1.10 Prerequisites

Computer arithmetic (IEEE-754, rounding, FMA, catastrophic cancellation, error accumulation); complex arithmetic & Euler's formula; the DFT and its properties (linearity, shift, convolution theorem, Parseval); divide-and-conquer recurrences (T(N)=2T(N/2)+O(N)); number theory for Rader (primitive roots, modular inverse) and mixed-radix (CRT / coprime-factor view); CPU microarchitecture (cache hierarchy, vector width, FMA latency×throughput); SIMD (AVX2/FMA lane/shuffle semantics). Helpful: prior #349 (BLAS — blocking/SIMD/accuracy discipline), #181 (SIMD), #370 (bignum, the convolution consumer).

2. Why Build This

2.1 Unique Knowledge Taught

  • The divide-and-conquer that changed computing. How Cooley–Tukey turns O(N²) into O(N log N) by recursively splitting the DFT into even/odd (or radix-r) sub-DFTs combined by twiddle-weighted butterflies — the canonical "fast algorithm."
  • Why accuracy improves with the fast algorithm. Naïve DFT error grows ~O(N)·ε·‖x‖; FFT error grows ~O(log N)·ε·‖x‖ because each value passes through only log₂N butterfly stages, not N additions — a selling point, not just a speedup.
  • The planner mindset (FFTW). Why there is no single best FFT: the optimal decomposition of N into codelets depends on cache, ISA, and N's factorization → measure candidate plans, persist wisdom.
  • Number theory meets signal processing. Bluestein re-expresses any DFT as a convolution (computable by a power-of-2 FFT); Rader maps a prime-N DFT to a length-(N−1) cyclic convolution via a primitive root — algorithms that make "FFT of any N" tractable.
  • Mechanical sympathy for transforms. Bit-reversal cache behavior, twiddle table residence, register-resident butterfly tiles, real-input symmetry exploitation — the same roofline discipline as GEMM, on a different kernel.

2.2 Why It Matters

Among the most important numerical algorithms of the 20th century (Cooley–Tukey 1965; idea traces to Gauss 1805). Substrate of signal processing, audio/image/video codecs (via the related DCT), spectral PDE solvers, large-integer/polynomial multiplication, and convolution across scientific computing and ML. FFTW won the 1999 Wilkinson Prize. Understanding the Cooley–Tukey family — and the planner that tames it — is understanding how a 1000× algorithmic speedup becomes usable, accurate, portable software.

2.3 Engineering Muscles

Recurrence-based algorithm design; numerical error reasoning (forward/backward error of a transform); cache-aware data layout (bit-reversal, twiddle tables); SIMD codelet authoring; runtime ISA dispatch; a planner (cost model + measurement + persisted state); differential testing against a trusted O(N²) oracle and a reference (FFTW); benchmark methodology resistant to noise; a stable C ABI mirroring an entrenched de-facto standard.

2.4 Production Concepts Exercised

Roofline/flop-model analysis (5N·log₂N flops); register/cache blocking of butterflies; twiddle prec/precompute tradeoffs; codelet selection & plan caching (FFTW wisdom); runtime CPU-feature dispatch; reproducible benchmarking; a SemVer-versioned numerical contract (assert error bounds, not bits across plans); FFTW-compatible ABI + wisdom-file format compatibility.

3.2 Box Narratives

  • Public API / fft facade. Two-step like FFTW: plan(shape,dir,norm,layout,flags)->Plan, then plan.execute(in,out) (allocation-free, reusable). Validates shape/alignment/aliasing/normalization; selects f32/f64. Thin, no arithmetic; delegates to the planner. RFFT/IRFFT, 2D/3D, convolution are typed entry points over 1-D plans.
  • cabi ABI. #[repr(C)] opaque fftw_plan-style handle + fns mirroring FFTW (fftw_plan_dft_1d/_r2c/_c2r/_2d, fftw_execute, fftw_destroy_plan, fftw_import/export_wisdom); leaner native pfft_* also exposed. Never panics across the boundary (catch_unwind→error). Plan lifetime caller-owned.
  • planner. The brain. Factors N (trial division → prime/prime-power factors); builds a plan tree mapping each factor to a codelet (radix-2/4/split-radix leaf, mixed-radix node, Bluestein/Rader for awkward factors). ESTIMATE = static cost model (flop+memory+codelet costs); MEASURE times candidate sub-plans, keeps the fastest. Wisdom persists choices keyed by (N,dir,layout,ISA,dtype) → re-plan instant. Owns in-place/out-of-place + alignment.
  • twiddle. Generates W_N^k=e^{−2πik/N} tables. direct trig ((cos,−sin) per index — most accurate, O(N) trig) vs recurrence (W^{k+1}=W^k·W — cheap, error ~O(k)·ε → mitigated by periodic re-seed). Cached per (N,dtype) in a OnceLock registry, 64-B aligned. Split-radix adds W^{3k} tables.
  • radix. The power-of-2 core. Radix-2 DIT (bit-reversed in → natural out) and DIF (natural in → bit-reversed out) butterflies; radix-4 (fewer twiddle mults). The bit-reversal permutation (a true bijection, I3) reorders in place. Holds the canonical scalar butterflies the SIMD codelets must match.
  • mixedradix. General Cooley–Tukey for composite N=N₁·N₂: view x as N₁×N₂, FFT one dim, twiddle-multiply, FFT the other (four-step / Stockham). Split-radix (radix-2/4 hybrid) hits the lowest known flop count (~4N log₂N real ops) for power-of-2. Small primes (3,5,7) use hand codelets.
  • bluestein. For prime/awkward N where Cooley–Tukey stalls: Bluestein's chirp-z re-expresses X[k] as a convolution of x[n]·W_N^{n²/2} with a chirp kernel, done by a power-of-2 FFT of length ≥ 2N−1 → FFT of any N in O(N log N). Rader maps a prime-N DFT (minus DC) to a length-(N−1) cyclic convolution via a primitive root of N.
  • real. Real input → Hermitian-symmetric output (X[N−k]=conj(X[k])) → only N/2+1 outputs independent. RFFT: pack length-N real as length-N/2 complex, complex FFT, unscramble (the "two reals at once" trick) → ~2× speed, ½ memory. IRFFT inverts it. Layout in §8.6.
  • multidim. 2D/3D via row-column: FFT every row, then column (then page in 3D), each a batched 1-D plan. For images/codecs/PDEs. Transpose-for-locality is tunable (Phase 9).
  • convolution. Linear/circular via the convolution theorem conv(a,b)=IFFT(FFT(a)·FFT(b)). Overlap-add/save stream long signals against a fixed kernel in blocks (FIR filtering, the DSP path; also the bignum multiply primitive, §8.9).
  • simd. Cplx<f32|f64> vector type over __m256/__m256d (+ scalar fallback). Vectorized radix-2/4/split-radix butterflies process multiple complex points/instruction; shuffles handle re/im interleave. Dispatch picks the widest ISA once (cached fn ptrs). Owns 64-B aligned alloc + scratch arena.
  • fft-core. The vocabulary: Complex<T> (#[repr(C)] interleaved), Plan/Transform handles, Direction{Forward,Inverse}, Normalization{None,OneOverN,Unitary}, Layout{InPlace,OutOfPlace}, error type, machine constants. No arithmetic kernels.
  • bench. Probes cache/SIMD width; runs GFLOP/s sweeps using the 5N·log₂N flop model; emits roofline + fraction-of-peak; statistically robust (warmup, median-of-k, pinned). Compares power-of-2 vs prime-N performance (the cliff).
  • conformance. The naïve O(N²) DFT oracle (the trusted truth), a differential harness, numerical error-bound assertions (~c·log₂N·ε·‖x‖), round-trip/Parseval/bit-reversal-bijection checks, an FFTW differential harness (optional, not a build dep), and codelet/permutation fuzzing.

3.3 Boundaries

  • Trust boundary: the C ABI (untrusted N, pointers, alignment, flags from C callers → validated, never trusted). Internally, the SIMD codelets trust that the planner produced correctly-sized, aligned scratch and twiddle tables — that invariant is the seam between safe and unsafe.
  • Concurrency boundary: in batched/multi-dim transforms, independent rows/columns/signals are partitioned across threads; each owns disjoint output and private scratch → no data races by construction. A single 1-D power-of-2 transform is sequential (stage-by-stage data dependence).
  • Numerical boundary: accumulation order and twiddle-table values depend on the chosen plan (radix, ordering) → documented, not bit-identical to the naïve oracle nor across different plans for the same N. We assert error bounds, not bit-equality (except in a forced deterministic mode).

3.4 Data-flow walk — one out-of-place c2c forward FFT, N composite

  1. Caller invokes plan(N, Forward, OneOverN, OutOfPlace, MEASURE).
  2. planner validates N>0, checks wisdom for (N,dir,layout,ISA,dtype); on hit → reuse plan tree; on miss → continue.
  3. factor(N) → e.g. N = 2^a · 3 · 5; build a plan tree: radix-2/4 leaves for the 2^a part, hand codelets for 3 and 5, mixed-radix nodes combining them (I-invariant: factor product = N).
  4. MEASURE mode times two candidate orderings; keep the faster; record in wisdom (I9: same N+flags+ISA → same plan).
  5. twiddle tables for each sub-size generated/fetched (direct-trig by default; I7 table-correctness).
  6. plan.execute(in, out): allocation-free; runs the tree — bit-reversal/permutation (I3 bijection), staged butterflies via simd codelets (I-accum-order), twiddle multiplies, mixed-radix recombination.
  7. Normalization applied per OneOverN (I5): forward unnormalized here unless chosen; (the 1/N lives on whichever of fwd/inv the convention dictates).
  8. Optional PlanTrace emitted (N, factors, dir, layout, ISA, codelets, plan_ns, exec_ns, GFLOP/s, accum_order_id).

4.1 Worked flop-count & accuracy derivation (reference)

To make targets concrete (Haswell-class core, f64, N=2²⁰):

  • Naïve DFT: N² complex MACs ≈ 8·N² real flops = 8·(2²⁰)² ≈ 7.0×10¹³ flops → seconds.
  • Radix-2 FFT: log₂N stages × N/2 butterflies; one radix-2 butterfly = 1 complex mul + 2 complex add ≈ 10 real flops → ~5N·log₂N ≈ 5·2²⁰·20 ≈ 1.0×10⁸ flops → ~milliseconds. Speedup ≈ 7×10⁵.
  • Split-radix: ~4N·log₂N real flops → ~20 % fewer than radix-2.
  • Accuracy: worst-case forward error bound (Higham): ‖fl(FFT(x)) − FFT(x)‖₂ / ‖FFT(x)‖₂ ≤ η·log₂N with η ≈ μ·ε (μ a small constant from per-butterfly rounding + twiddle error). Naïve DFT bound is ~N·ε. At N=2²⁰: FFT ≈ 20·ε vs naïve ≈ 10⁶·ε — a ~5×10⁴× accuracy advantage. This bound is asserted by the conformance suite (§4 accuracy targets), parameterized by N.
  • Bluestein padding: for N, pick M = next power of 2 ≥ 2N−1 → up to ~4× the work of an M-sized FFT; the prime-N constraint above follows.

6. Design Principles

The canonical principle IDs P1…P14; referenced as §6.N (= principle PN) throughout.

  • P1 — Correctness before speed; the naïve DFT oracle is sacred. Every transform is first proven against the O(N²) Σ x[n]·W_N^{nk} reference within an error bound. Violation: tuning before a green oracle → fast wrong spectra that fuzzing finds only by luck.
  • P2 — Plan once, execute many; planning and execution are separate. A Plan is built (possibly expensively) once and executed repeatedly, allocation-free, on conforming buffers (FFTW model). Violation: re-planning per call → planning cost dominates; or alloc in execute → jitter, no real-time use.
  • P3 — One twiddle convention, generated once, cached. W_N^k = e^{−2πik/N} (forward sign −); tables precomputed per (N, dtype), shared, 64-B aligned. Violation: recomputing trig per butterfly → trig dominates; mixing sign conventions → conjugated/wrong output.
  • P4 — Keep the butterfly tile in registers; stream data through stages. A radix-r butterfly's accumulators live in vector registers; data streams stage-by-stage. Violation: register spill in the codelet → the perf cliff; measured GFLOP/s collapses.
  • P5 — Derive codelet/plan choices from a cost model + measurement, not folklore. The planner (ESTIMATE cost model, MEASURE timing, wisdom) chooses radix/ordering. Violation: hardcoded "always radix-2" → slow on composite/prime N and on other CPUs.
  • P6 — unsafe is confined to SIMD codelets and the in-place permutation; everything else is checked. A documented seam with explicit alignment/size preconditions. Violation: unsafe leaking upward → unauditable memory bugs in index arithmetic.
  • P7 — Assert error bounds, not bits; numerical behavior is a versioned contract. Accumulation order and twiddle values depend on the plan; we promise ~c·log₂N·ε bounds and a forced-deterministic mode, not bit-equality across plans/ISAs. Violation: promising bit-reproducibility → broken by every planner change.
  • P8 — Exploit structure: real input, symmetry, in-place. RFFT uses Hermitian symmetry (½ work); DIT/DIF run in place (O(1) extra memory). Violation: always doing full complex out-of-place → 2× memory, 2× work, worse cache behavior.
  • P9 — Make arbitrary N a first-class citizen. Mixed-radix for composite N, Bluestein/Rader for prime/awkward N — no size is unsupported, the cliff is bounded. Violation: power-of-2-only → unusable for real signal lengths (44100, 48000, image dims).
  • P10 — Runtime ISA dispatch, resolved once. Detect AVX2/AVX-512/NEON at init; cache codelet fn pointers. Violation: per-call cpuid → branch overhead; illegal-instruction crashes on older CPUs.
  • P11 — Bounded, streaming memory. Scratch is O(N) (Bluestein O(M)), reused across execute calls; never O(N²). Violation: materializing intermediate arrays per stage → allocator churn, OOM on large N.
  • P12 — Bit-reversal / permutation is a proven bijection. Index permutations are tested as exact permutations (no value lost or duplicated). Violation: an off-by-one in bit-reversal → silently wrong output that looks plausible.
  • P13 — Observability by default. Every plan/execute can emit which codelets/ISA, factorization, twiddle strategy, plan vs exec time, GFLOP/s. Violation: opaque transforms → unprofilable regressions, unexplained accuracy drift.
  • P14 — Parameter validation at the boundary. Bad N, misaligned/aliased buffers, illegal flag combos → typed error before any compute (and before plan execution). Violation: trusting C-caller args → OOB read/write, UB; executing a plan on a wrong-size buffer → corruption.

8. Domain Model — The Discrete Fourier Transform

8.1 The DFT and its inverse

The forward DFT and inverse (IDFT) of a length-N complex sequence:

Forward:  X[k] = Σ_{n=0}^{N-1} x[n]·W_N^{nk},     k = 0..N-1,   W_N = e^{-2πi/N}   (the "twiddle factor")
Inverse:  x[n] = (1/N) Σ_{k=0}^{N-1} X[k]·W_N^{-nk}

W_N is a primitive N-th root of unity: W_N^N = 1, W_N^{k+N/2} = -W_N^k (the symmetry the radix-2 split exploits), W_N^{2k} = W_{N/2}^k (the periodicity that makes recursion work). Naïve evaluation is O(N²). The normalization 1/N is a convention (ADR-15): it may sit on the inverse (default), be split as 1/√N on both (unitary), or be omitted (caller scales).

8.2 Cooley–Tukey: the even/odd split (radix-2 DIT)

Split the sum into even- and odd-indexed terms:

X[k]      = Σ_even x[2m]·W_N^{2mk} + Σ_odd x[2m+1]·W_N^{(2m+1)k}
          = E[k] + W_N^k · O[k]          where E,O are length-N/2 DFTs of evens/odds
X[k+N/2]  = E[k] − W_N^k · O[k]          (using W_N^{k+N/2} = −W_N^k)

This is the radix-2 decimation-in-time (DIT) butterfly. Recurse → T(N) = 2T(N/2) + O(N) = O(N log N). DIT takes bit-reversed input, natural output. DIF (decimation-in-frequency) splits the output instead → natural input, bit-reversed output. The two are transposes of each other's flow graph.

8.3 The butterfly (the atomic operation)

A radix-2 butterfly combines two complex values a, b with a twiddle w:

        a ──────●──────────► a' = a + w·b
                 \   ╱
                  \ ╱
                   X
                  ╱ \
                 ╱   \
        b ──[w]─●──────────► b' = a − w·b

Cost: 1 complex multiply (w·b) + 2 complex add/sub = ~10 real flops. A radix-4 butterfly combines 4 points with 3 twiddles, eliminating some multiplies (±i multiplies are free swaps/negations). Split-radix mixes radix-2 and radix-4 to minimize total multiplies.

8.4 Bit-reversal permutation

DIT needs input in bit-reversed index order: index n (b-bit) maps to the integer formed by reversing its bits. Example for N=8 (3 bits):

n :  0   1   2   3   4   5   6   7      (binary: 000 001 010 011 100 101 110 111)
br:  0   4   2   6   1   5   3   7      (reversed: 000 100 010 110 001 101 011 111)

It is an involution (br(br(n))=n) and a bijection (I3). Done in place by swapping x[n] ↔ x[br(n)] for n < br(n). Cache-unfriendly (scattered access) → a known perf concern (Phase 3 pitfalls); cache-oblivious / blocked variants exist.

8.5 Worked 8-point radix-2 DIT (the canonical example)

N=8, twiddles W_8^k = e^{-2πik/8}: W^0=1, W^1=(√2/2)(1−i), W^2=−i, W^3=(√2/2)(−1−i).

Input x[0..7] → bit-reverse → [x0 x4 x2 x6 x1 x5 x3 x7]

Stage 1 (length-2 DFTs, W^0 only):     4 butterflies, pairs (0,4)(2,6)(1,5)(3,7), w=1
Stage 2 (length-4 DFTs, W_4 = {1,-i}): 2 groups of 2 butterflies, twiddles {W^0, W^2=-i}
Stage 3 (length-8 DFT, W_8):           1 group of 4 butterflies, twiddles {W^0,W^1,W^2,W^3}
                                       → natural-order output X[0..7]

Sanity: x = [1,1,1,1,1,1,1,1] ⇒ X = [8,0,0,0,0,0,0,0]   (DC only).
        x = δ[0] = [1,0,...,0]  ⇒ X = [1,1,1,1,1,1,1,1]  (flat).

3 stages = log₂8; 4 butterflies/stage = N/2; total 12 butterflies ≈ (N/2)log₂N.

8.6 Real-input FFT (RFFT) & Hermitian packing

For real x, X[N−k] = conj(X[k]) → outputs X[0..N/2] (that's N/2+1 complex values) fully determine the spectrum; X[0] and X[N/2] are real (I6). Packing/"halfcomplex" layout (the RFFT I/O contract):

Complex out (length N/2+1):  X[0], X[1], …, X[N/2]      (X[0].im = X[N/2].im = 0)
Halfcomplex (length N, real array):  r0, r1, …, r_{N/2}, i_{(N/2)-1}, …, i_1   (re's ascending, im's descending)

Algorithm: pack length-N real → length-N/2 complex (even→re, odd→im), run a complex N/2 FFT, then unscramble with one pass of butterflies using W_N → ~2× faster, ½ memory. IRFFT reverses it. The "two real FFTs from one complex FFT" trick handles two real signals at once.

8.7 Mixed-radix & split-radix (composite N)

For N = N₁·N₂ (Cooley–Tukey general / four-step): index n = N₂·n₁ + n₂, k = N₁·k₂ + k₁:

1. N₁ DFTs of length N₂  (along one dim)
2. multiply by twiddles W_N^{n₂·k₁}        ("twiddle multiply" between the two stages)
3. N₂ DFTs of length N₁  (along the other dim)

Small factors {2,3,4,5,7,8} get hand-written codelets (straight-line, register-resident). Split-radix (for power-of-2): recursively X[2k] via a radix-2 split and X[4k±1] via a radix-4 split → fewest multiplies (~4N log N). State machine: factor N → tree of (radix-r leaf | mixed-radix node).

8.8 Bluestein (chirp-z) & Rader (prime N)

Bluestein — works for any N: using nk = (n² + k² − (k−n)²)/2,

X[k] = W_N^{k²/2} · Σ_n [ x[n]·W_N^{n²/2} ] · W_N^{-(k-n)²/2}
     = (chirp) · convolution( a[n]=x[n]·W_N^{n²/2} ,  b[m]=W_N^{-m²/2} )

The convolution is computed by zero-padding to M = next-pow2 ≥ 2N−1 and using a power-of-2 FFT (I10). Rader — for prime N: the multiplicative group mod N is cyclic with a primitive root g; reindexing by powers of g turns the N−1 non-DC outputs into a length-(N−1) cyclic convolution, itself done by FFT (or recursively by Bluestein/Rader). DC term X[0]=Σx[n] handled separately.

8.9 FFT convolution & bignum multiplication (the consumers)

Convolution theorem: conv(a,b) = IFFT(FFT(a) ⊙ FFT(b)) (⊙ = pointwise). Linear conv needs zero-padding to length ≥ len(a)+len(b)−1 (else circular wrap-around). Overlap-add / overlap-save stream a long signal against a fixed kernel in blocks (FIR filtering — the #174 DSP consumer's path). Big-integer multiplication (#370 consumer): represent integers as polynomials (digits = coefficients), multiply via FFT convolution, carry-propagate → Schönhage–Strassen-style O(n log n) multiply. Precision note: floating-point FFT convolution risks rounding errors in the carry step for huge integers → an exact NTT (modular integer transform) is the robust alternative (deferred, §11.12).

11. Core Schema and Core Types

Normative signatures. Lightweight only — no codelet bodies (CRITICAL RULE 10).

11.1 Complex scalar trait

pub trait Float: Copy + Send + Sync { /* f32 | f64 */
    const EPS: Self; const PI: Self; const ZERO: Self; const ONE: Self;
    fn mul_add(self, b: Self, c: Self) -> Self;     // FMA
    fn sin_cos(self) -> (Self, Self);               // for direct-trig twiddles
}
#[repr(C)] pub struct Complex<T: Float> { pub re: T, pub im: T }   // interleaved, C `_Complex`-compatible
impl<T: Float> Complex<T> { fn mul(self, o:Self)->Self; fn conj(self)->Self; fn add(self,o:Self)->Self; fn scale(self,s:T)->Self; }

Ownership: Copy, no heap. Concurrency: Send+Sync. Serialization: #[repr(C)] matches C _Complex (ADR-5). Complex mul = 4 real mul + 2 add (ADR-19; 3-mul rejected).

11.2 Direction / Normalization / Layout

#[repr(i32)] pub enum Direction { Forward = -1, Inverse = 1 }   // sign of the exponent
pub enum Normalization { None, OneOverN, Unitary /* 1/√N */ }
pub enum Layout { InPlace, OutOfPlace }

ABI: Direction integer values are the exponent sign (FFTW convention FFTW_FORWARD=-1). Compatibility: integer values frozen (I9, SemVer-major to change).

11.3 Plan & Transform handles

pub struct Plan<T: Float> {            // built once, executed many (ADR-6)
    n: usize, dir: Direction, norm: Normalization, layout: Layout,
    tree: PlanTree,                    // codelet decomposition
    twiddles: Arc<TwiddleSet<T>>,      // shared, cached
    scratch: AlignedArena<Complex<T>>, // owned, reused; no alloc in execute (I14)
    isa: Isa, plan_hash: u64,
}
impl<T: Float> Plan<T> {
    fn execute(&self, input: &[Complex<T>], output: &mut [Complex<T>]) -> Result<(), FftError>; // I1,I14
    fn execute_inplace(&self, data: &mut [Complex<T>]) -> Result<(), FftError>;
}

Ownership: Plan owns its scratch; twiddles shared via Arc. Mutation: execute is &self (no plan mutation; scratch via interior UnsafeCell with a documented single-thread-per-execute contract). Concurrency: a Plan is Send; concurrent execute on the same plan requires external sync (or clone the plan). Persistence: the plan tree is serializable as wisdom (§11.9).

11.4 Plan tree (the decomposition)

pub enum PlanTree {
    Radix2Dit { stages: u32 }, Radix2Dif { stages: u32 }, Radix4 { stages: u32 },
    SplitRadix { n: usize },
    MixedRadix { n1: usize, n2: usize, inner: Box<(PlanTree, PlanTree)>, twiddle_id: u64 },
    Codelet { radix: u8 },                       // hand kernels r3/r5/r7/r8
    Bluestein { n: usize, m: usize /*≥2n-1, pow2*/, inner: Box<PlanTree> },
    Rader { p: usize, g: usize /*primitive root*/, inner: Box<PlanTree> },
    Real { half: Box<PlanTree> },                // RFFT/IRFFT wrapper
}

The product of leaf sizes = N (I-factorization). MixedRadix/Bluestein/Rader carry their inner plans. twiddle_id keys the shared twiddle table.

11.5 Twiddle set & cache

pub struct TwiddleSet<T: Float> { tables: HashMap<TwiddleKey, AlignedVec<Complex<T>>> }
struct TwiddleKey { n: usize, kind: TwiddleKind }     // Forward / SplitRadix-W3 / Chirp
pub enum TwiddleKind { Dft, SplitRadixW3, Chirp { m: usize } }
fn gen_trig<T>(n: usize) -> AlignedVec<Complex<T>>;   // W[k]=(cos(-2πk/n), sin(-2πk/n)), direct (I7)

Ownership: cached in a process-wide OnceLock registry, shared Arc. Generation: direct-trig (accurate) default; recurrence opt-in (ADR-7). Alignment: 64-B (I15). LRU-evictable to bound memory.

11.6 SIMD complex & codelet function type

pub struct Cplx<T> { /* vector of complex: AoS or planar re/im per ADR-23 */ }
type Butterfly<T> = unsafe fn(data: *mut Complex<T>, n: usize, stride: usize, tw: *const Complex<T>);
struct CodeletSet<T> { r2_dit: Butterfly<T>, r2_dif: Butterfly<T>, r4: Butterfly<T>, sr: Butterfly<T>, /* r3/r5/r7/r8 */ }

Selected once by ISA dispatch; stored as fn pointers (ADR-4). The single unsafe surface alongside the in-place permutation (I3/I15).

11.7 Planner API

11.12 NTT note (deferred)

A Number-Theoretic Transform replaces e^{−2πik/N} with a primitive root of unity in ℤ/pℤ (a prime modulus), giving exact integer convolution (no rounding) — the robust path for huge-integer multiplication (#370). Modeled here for completeness; implementation gated PhaseDeferred("§11.12"). Same Cooley–Tukey butterfly structure; arithmetic is modular instead of complex.

  • golden/probe_{x86,aarch64}.json — expected Machine per CI arch.

12.6 Pitfalls

  • Exponent-sign convention: forward is e^{−2πi…} (Direction::Forward=-1) — flipping it conjugates everything; pin it once (I7, ADR-11).
  • 3-mul complex multiply tempts here — rejected (ADR-19); worse FP error, harder to vectorize.
  • Aligned alloc must be paired with aligned free → wrap exclusively in AlignedArena.
  • Oracle must use a stable summation order so its own result is reproducible (it is the reference).

12.7 Performance Concerns

  • N/A for the oracle (it is O(N²), the "0×" baseline) — but record its time to quantify later speedup (typically 10³–10⁶×).
  • Establish measurement methodology (warmup, median-of-k, pinned) now; reused by every bench.

12.8 Edge Cases

  • N=0 → param error; N=1 → identity; one NaN/±Inf element → propagates (I13).

12.9 Failure Analysis

  • If the oracle is wrong, every later test is wrong. Mitigation: hand-computed fixtures + an independent one-off cross-check vs NumPy/FFTW (documented, not a build dep).

13. Phase 1 — Radix-2 DIT + bit-reversal (recursive, correctness-first)

13.1 Objectives

  • Implement a recursive radix-2 DIT FFT for power-of-2 N (clarity over speed).
  • Implement the bit-reversal permutation and prove it is a bijection (I3).
  • First green diff against the oracle — the correctness anchor for the whole power-of-2 family.

13.2 Detailed Implementation Steps

  • radix::butterfly — the scalar radix-2 butterfly (a, b, w) → (a + w·b, a − w·b) (§8.3; complex mul = 4-real-mul form per ADR-19). Applies the Cooley–Tukey 1965 even/odd identity (§5.2 paper 1).
  • radix::radix2_dit — recursive: split even/odd, recurse on halves, combine with butterflies + twiddles (§8.2; CLRS ch.30, §5.1 book 3). Twiddles computed inline via sin_cos for now (cached in P2 per ADR-07).
  • radix::bitreverse — compute br(n) (bit-reverse of a b-bit index); in-place swap loop for n < br(n) (§8.4); a bit_reverse_permute(data) proven a bijection (I3).
  • A driver: recursive_fft(x, dir) -> X wiring split→recurse→combine, applying normalization (I5; correctness-before-speed per P1, §6).
  • conformance::differential — generate random complex vectors of sizes {2,4,8,…,2¹⁶}, diff vs the naïve oracle within bound (I2; oracle is sacred per P1).

13.3 Deliverable

  • A correct (if unoptimized) power-of-2 FFT; examples/fft_basic transforms a vector and prints the spectrum.

13.4 Acceptance Criteria

  • Matches oracle within c·log₂N·ε·‖x‖ for all power-of-2 N ≤ 2¹⁶ (I2).
  • Bit-reversal bijection test passes for all N ≤ 2²⁰ (histogram of targets all-ones, I3).
  • Round-trip ‖IFFT(FFT(x))−x‖/‖x‖ ≤ c·log₂N·ε (I5).

13.5 Conformance Fixtures

  • dft/radix2_pow2_sweep.json — every power-of-2 size vs oracle.
  • dft/bitreverse_{8,16,1024}.json — known bit-reversal mappings.
  • numerics/roundtrip_pow2.json — forward∘inverse identity.

13.6 Pitfalls

  • Off-by-one in bit-reversal (reversing b vs b−1 bits) → silently wrong order; the bijection + oracle tests catch it.
  • DIT requires bit-reversed input (or bit-reversed output if you reorder after) — mixing the two scrambles results.
  • Twiddle sign again (−2πi) — assert one length-4 case by hand.
  • Recursion base case (N=1 returns the input; N=2 is a single butterfly with w=1).

13.7 Performance Concerns

  • Recursion + per-call sin_cos is slow (function-call overhead, repeated trig) — expected; this phase is correctness, not speed. Record its GFLOP/s as the "recursive baseline."
  • Bit-reversal's scattered memory access is already a visible cost → flagged for P3.

13.8 Edge Cases

  • N=1 (identity), N=2 (one butterfly); non-power-of-2 N → reject here (mixed-radix is P5).
  • Subnormal inputs; NaN/Inf propagation (I13).

13.9 Failure Analysis

  • A wrong butterfly or permutation produces a plausible-but-wrong spectrum → caught only by the oracle diff + bijection check. Add a regression fixture for any escape.
  • Blast radius: every power-of-2 path builds on this butterfly.

13.10 Operational Notes

  • PlanTrace (stub) records codelets=["radix2_dit_recursive"].
  • Document the input-ordering contract (bit-reversed in / natural out for DIT).

14. Phase 2 — Twiddle generation + caching, and radix-2 DIF

14.1 Objectives

  • Build the twiddle crate: generate W_N^k tables (direct-trig + recurrence), cache them, prove correctness (I7).
  • Implement radix-2 DIF (natural input, bit-reversed output) — the transpose of DIT.
  • Remove per-butterfly trig (the P1 bottleneck) by precomputing tables once per N.

14.2 Detailed Implementation Steps

  • twiddle::gen_trig — W[k] = (cos(−2πk/N), sin(−2πk/N)) for k = 0..N/2 (exploit W^{k+N/2}=−W^k); direct sin_cos (I7, ADR-7).
  • twiddle::gen_recurrence — W^{k+1} = W^k · W^1 with periodic re-seed from a direct value every √N steps to bound drift; opt-in.
  • twiddle::cache — process-wide OnceLock registry keyed by TwiddleKey{n,kind}; Arc<AlignedVec<Complex<T>>>; LRU eviction.
  • radix::radix2_dif — output-split formulation: combine first (with twiddles), then recurse → natural in / bit-reversed out (§8.2).
  • Wire recursive DIT/DIF to fetch twiddles from the cache instead of computing inline.

14.3 Deliverable

  • Twiddle cache; both DIT and DIF correct vs oracle; a measurable speedup over P1 from cached twiddles.

14.4 Acceptance Criteria

  • Twiddle table vs direct (cos,−sin) reference: max error ≤ c·ε (direct), bounded drift (recurrence) (I7).
  • DIF matches oracle within bound; DIF∘(bit-reverse) == DIT result.
  • Twiddle cache hit avoids regeneration (hit-rate counter > 0 on repeated transforms).

14.5 Conformance Fixtures

  • numerics/twiddle_table_{64,4096}.json — table vs direct-trig reference.
  • numerics/twiddle_recurrence_drift.json — recurrence error stays bounded.
  • dft/radix2_dif_sweep.json — DIF vs oracle.

14.6 Pitfalls

  • Recurrence twiddle drift: naïve W^{k+1}=W^k·W accumulates ~O(k)·ε error → ruins accuracy for large N unless re-seeded (I7).
  • Storing only the first half (0..N/2) requires sign-flip logic for the second half — test the boundary.
  • DIF vs DIT confusion: DIF needs bit-reversal after, DIT before; mislabeling scrambles output ordering.
  • Cache key must include dtype (f32 and f64 tables differ).

14.7 Performance Concerns

  • Direct-trig generation is O(N) sin_cos calls (one-time, amortized over many executes); recurrence is O(N) mul (cheaper but less accurate) — the documented accuracy/speed knob (ADR-7).
  • Twiddle table residence in cache (the table is streamed each stage) — flagged for P12 layout work.

14.8 Edge Cases

  • N=1/N=2 (trivial tables); very large N table memory (LRU evicts).
  • f32 twiddle precision noticeably worse than f64 — document the per-dtype error floor.

14.9 Failure Analysis

  • A wrong twiddle table corrupts every transform of that size → caught by the table-correctness assert (I7) before any FFT diff.
  • Recurrence drift manifests as accuracy slowly worsening with N → the drift fixture + error-bound check catch it.

14.10 Operational Notes

  • PlanTrace.twiddle records "direct_trig" | "recurrence".
  • tools/twiddle_dump prints a table for inspection.
  • Document the twiddle strategy + per-dtype error floor in docs/performance/twiddle-strategy.md.

15. Phase 3 — Iterative in-place FFT + accuracy bounds

15.1 Objectives

  • Replace recursion with the iterative in-place radix-2 FFT (the standard production form): bit-reverse once, then log₂N stages of butterflies with stride-doubling.
  • Establish and assert the formal accuracy bounds (~c·log₂N·ε·‖x‖) — the project's numerical contract and selling point.
  • Make the transform allocation-free given pre-generated twiddles (toward I14).

15.2 Detailed Implementation Steps

  • radix::radix2_dit (iterative): first bit_reverse_permute(x), then log₂N stages. At stage s the sub-DFT length is len = 2^s with half = len/2; the array is partitioned into N/len contiguous groups, and within each group the half butterflies pair element j with element j+half using twiddle tw[j·N/len] (§8.2/8.4). Stage/group/position indexing is the structure; no inner loop is transcribed here (NO-CODE, §4).
  • In-place: butterflies write back to the same array; O(1) extra memory beyond twiddles (ADR-12, P8).
  • conformance::errorbounds extended: per-size measured RMS error vs oracle, assert ≤ c·log₂N·ε·‖x‖ (Higham §24); also forward-only and round-trip bounds.
  • conformance::parseval — assert Σ|x|² ≈ (1/N)Σ|X|² within bound (I8).
  • Alloc guard test: custom global allocator counts allocations inside the transform → must be 0 (I14).

15.3 Deliverable

  • Iterative in-place radix-2 FFT; accuracy/Parseval/round-trip bounds asserted across sizes; zero steady-state alloc.

15.4 Acceptance Criteria

  • Measured RMS error vs oracle ≤ c·log₂N·ε·‖x‖ for all power-of-2 N ≤ 2²⁰ (I2) — and demonstrably lower than the naïve DFT's ~N·ε (the selling point, logged side-by-side).
  • Parseval residual ≤ c·log₂N·ε·E (I8).
  • Zero allocations inside the transform (I14, alloc-counter test).
  • Iterative form ≥ 5× faster than the P1 recursive form (no call overhead, cached twiddles).

15.5 Conformance Fixtures

  • numerics/accuracy_bound_sweep.json — measured error vs c·log₂N·ε per size (incl. naïve comparison).
  • numerics/parseval_sweep.json — energy preservation.
  • numerics/alloc_free_execute.json — alloc-count assertion.

15.6 Pitfalls

  • Stride/index arithmetic in the stage loop is the classic bug nest → derive tw index (j·N/len) carefully; the oracle diff catches errors.
  • In-place butterflies must read both operands before writing either (read a,b, then write a',b').
  • Accumulation order changes bits vs the recursive form → that is expected (different plan); assert bounds, not equality (I4).
  • Forgetting twiddle stride per stage (N/len) → wrong twiddles, plausible-but-wrong output.

15.7 Performance Concerns

  • Bit-reversal's scattered access is now the dominant non-compute cost for large N → measure; blocked/cache-oblivious bit-reversal is a P12 lever.
  • The inner butterfly loop should be branch-free and stride-regular → sets up SIMD vectorization (P11).
  • Twiddle table streamed each stage → cache residence matters (the table is O(N)).

15.8 Edge Cases

  • N=1/N=2; the last stage (single group spanning the whole array); subnormals accumulating across stages.
  • NaN/Inf propagation across all stages (I13).

15.9 Failure Analysis

  • A subtle stage-loop bug can pass for small N and fail for large N (the index math diverges) → the full power-of-2 sweep + accuracy bound is the net.
  • Accuracy drift (e.g. from a bad twiddle stride) → the accuracy-bound fixture flags it; runbook accuracy-regression.md.
  • Blast radius: this iterative kernel is the basis for mixed-radix, RFFT, convolution, and the SIMD codelets.

15.10 Operational Notes

  • PlanTrace.accum_order_id distinguishes the iterative order (I4); PFFT_DETERMINISTIC pins it (ADR-25).
  • Document the accuracy bound + the naïve-vs-FFT error comparison in docs/performance/ and the README (the headline numerical result).
  • The bit-reversal cache behavior documented in docs/performance/bitreverse-cache.md.

16. Phase 4 — Radix-4 and split-radix (flop reduction)

16.1 Objectives

  • Implement radix-4 butterflies (4 points/stage; ±i multiplies are free) — fewer twiddle multiplies, fewer stages (log₄N).
  • Implement split-radix (radix-2/4 hybrid) — the lowest known flop count for power-of-2 (~4N log₂N real ops vs radix-2's ~5N log₂N).
  • Demonstrate the flop reduction as a measurable speedup with unchanged accuracy.

16.2 Detailed Implementation Steps

  • radix::radix4 — radix-4 butterfly: combine 4 inputs with twiddles {W^0, W^k, W^{2k}, W^{3k}}; multiply by ±i via real/imag swap + sign (no FP multiply) (§8.3; hand-written straight-line codelet per ADR-08).
  • mixedradix::split_radix — the L-shaped recursion: X[2k] from a length-N/2 DFT of x[n]+x[n+N/2]; X[4k+1], X[4k+3] from length-N/4 DFTs of twiddle-weighted differences (§8.7; Duhamel & Hollmann 1984, §5.2 paper 6). Needs the W^{3k} table (TwiddleKind::SplitRadixW3, §11.5; I7).
  • Scalar implementations first (oracle-verified, I2); SIMD codelets deferred to P11 (PhaseDeferred("§16.2")).
  • Register the codelets in CodeletSet (§11.6) for the planner to select (P10, §22; ADR-09).
  • bench adds a flop-count comparison (radix-2 vs radix-4 vs split-radix) and a speedup measurement (Johnson & Frigo 2007 record count, §5.2 paper 12).

16.3 Deliverable

  • Radix-4 and split-radix transforms correct vs oracle; flop-count and timing comparison vs radix-2.

16.4 Acceptance Criteria

  • Both match the oracle within c·log₂N·ε·‖x‖ (accuracy unchanged from radix-2, I2).
  • Split-radix performs measurably fewer real flops and runs faster than radix-2 for N ≥ 256 (flop model + timing confirm).
  • Radix-4 produces identical-within-bound results to radix-2 for power-of-4 sizes.

16.5 Conformance Fixtures

  • dft/radix4_pow4_sweep.json — radix-4 vs oracle (power-of-4 sizes).
  • dft/split_radix_sweep.json — split-radix vs oracle (power-of-2).
  • numerics/split_radix_flopcount.json — measured flop count ≈ 4N log₂N.

16.6 Pitfalls

  • ±i multiply: implement as (re,im)→(∓im,±re), not a complex multiply — getting the sign/swap wrong is a subtle correctness bug.
  • Split-radix's irregular (L-shaped) recursion is index-error-prone → derive the X[4k+1]/X[4k+3] indices carefully; oracle diff is the net.
  • The W^{3k} table must match the W^k convention (same sign) — a separate table, same generator (I7).
  • Output ordering for split-radix differs from radix-2 → handle the permutation consistently.

16.7 Performance Concerns

  • Radix-4 halves the number of stages → fewer passes over memory (better than radix-2 even at equal flops, due to memory traffic).
  • Split-radix's irregular structure can hurt SIMD regularity → a known tension (radix-4/8 is often faster in practice than split-radix once vectorized) — measure, document (P11/P12).
  • More twiddle tables (W^{3k}) → more cache pressure.

16.8 Edge Cases

  • N a power of 2 but not 4 (radix-4 needs one radix-2 stage, or split-radix) — handle the mixed last stage.
  • Small N (N<16) where higher-radix overhead exceeds benefit → fall back to radix-2 or a direct codelet.

16.9 Failure Analysis

  • A split-radix index bug fails subtly (some output bins wrong) → the full sweep + per-bin diff catches it.
  • Blast radius: split-radix becomes the default power-of-2 leaf the planner picks → high test priority.

16.10 Operational Notes

  • PlanTrace.codelets distinguishes radix2/radix4/split_radix.
  • Document the flop counts and the "split-radix vs vectorized-radix-4" tradeoff in docs/performance/.
  • The planner (P10) chooses among these per N + ISA.

17. Phase 5 — Mixed-radix for composite N

17.1 Objectives

  • Implement general Cooley–Tukey for composite N = N₁·N₂ (the four-step / index-decomposition view, §8.7).
  • Provide hand-written small-prime codelets (radix-3, 5, 7, 8) as the building blocks.
  • Support any composite N (e.g. 6, 12, 360, 1000, 44100) — the bulk of real-world sizes.

17.2 Detailed Implementation Steps

  • mixedradix::factor — trial-division factorization of N into prime powers (§11.7); chooses a balanced N₁·N₂ split.
  • mixedradix::cooley_tukey — the three-step recombination: N₁ DFTs of length N₂, twiddle multiply (W_N^{n₂k₁}), N₂ DFTs of length N₁ (§8.7). Recurse on sub-sizes.
  • mixedradix::codelets::{r3,r5,r7,r8} — straight-line hand kernels (the radix-3/5/7 butterflies use specific twiddle constants; radix-8 is two radix-4 + twiddles).
  • Twiddle tables for the inter-stage multiply (TwiddleKind::Dft at size N) cached.
  • The plan tree (§11.4) now has MixedRadix nodes wrapping Codelet/Radix* leaves.

17.3 Deliverable

  • FFT of arbitrary composite N correct vs oracle; examples/fft_basic works for non-power-of-2 sizes.

17.4 Acceptance Criteria

  • Matches oracle within bound for composite N ∈ {6,9,12,15,60,360,1000,1024·3, 44100, 48000} (I2).
  • Factorization is correct (product of factors == N) and balanced.
  • Small-prime codelets (r3/r5/r7) match oracle exactly for their base sizes.

17.5 Conformance Fixtures

  • dft/mixedradix_composite.json — a spread of composite sizes vs oracle.
  • dft/codelet_{r3,r5,r7,r8}.json — base-size codelet correctness.
  • numerics/factor_correctness.json — factorization product == N.

17.6 Pitfalls

  • The inter-stage twiddle multiply is easy to misplace or mis-index (W_N^{n₂k₁}) → the classic mixed-radix bug; derive against the oracle.
  • Data layout: the four-step view requires viewing the 1-D array as an N₁×N₂ matrix (row/column reads) → strided access; get the transpose right.
  • Small-prime codelet twiddle constants (e.g. radix-3 uses cos(2π/3)=−0.5, sin(2π/3)=√3/2) must carry the right sign for the forward convention.
  • Unbalanced factorization (e.g. N = large_prime · 2) → falls to Bluestein/Rader (P6); detect and route.

17.7 Performance Concerns

  • Mixed-radix is less regular than pure radix-2 → typically a lower fraction of peak; the small-prime codelets are the hot leaves (optimize them).
  • The transpose/strided access between stages hurts cache → blocking (the four-step's purpose) and a transpose pass help (P9/P12).
  • Twiddle multiply adds N complex mults per level.

17.8 Edge Cases

  • N with a large prime factor → must route to Bluestein/Rader (P6), not loop forever in mixed-radix.
  • N square-free vs prime-power; N = 2·prime; very composite N (highly factorable, e.g. 5040).

17.9 Failure Analysis

  • A twiddle-multiply index bug produces wrong-but-plausible spectra for composite N while power-of-2 stays correct → composite-size fixtures are essential.
  • Blast radius: composite N is the common case; RFFT of odd N and many real signal lengths route through here.

17.10 Operational Notes

  • PlanTrace.factors records the factorization; codelets lists the leaves.
  • The planner (P10) chooses the N₁·N₂ split (cost-model or measured).
  • Document the mixed-radix decomposition + codelet constants in docs/performance/.

18. Phase 6 — Bluestein (chirp-z) + Rader (prime / arbitrary N)

18.1 Objectives

  • Implement Bluestein's chirp-z transform: FFT of any N via a power-of-2 convolution (§8.8) — eliminates the "unsupported size" case.
  • Implement Rader's algorithm for prime N via a length-(N−1) cyclic convolution + primitive root.
  • Bound the prime-size performance cliff (constant-factor, not asymptotic).

18.2 Detailed Implementation Steps

  • bluestein::chirpz — build chirp a[n]=x[n]·W_N^{n²/2} and kernel b[m]=W_N^{−m²/2}; pad to M = next_pow2(2N−1); convolve via a power-of-2 FFT (reuse P3/P4); multiply by the output chirp W_N^{k²/2} (§8.8, I10).
  • bluestein::primitive_root — find a primitive root g of prime p (smallest generator of (ℤ/pℤ)*).
  • bluestein::modinv — modular inverse (extended Euclid) for the Rader reindexing.
  • bluestein::rader — reindex non-DC inputs/outputs by powers of g/g⁻¹ → length-(N−1) cyclic convolution (done by FFT, possibly recursive Bluestein if N−1 is awkward); add DC term X[0]=Σx[n] (§8.8).
  • Plan tree gains Bluestein{n,m,inner} and Rader{p,g,inner} nodes; the planner routes prime/awkward factors here.

18.3 Deliverable

  • FFT of any N (including large primes like 1009, 65537) correct vs oracle.

18.4 Acceptance Criteria

  • Matches oracle within bound for prime N ∈ {3,5,7,13,17,1009,65537} and awkward N ∈ {2·1009, 1000003} (I2, I10).
  • Bluestein result == direct DFT within bound for arbitrary N (the convolution identity holds, I10).
  • Prime-N (Bluestein) within ~3–6× of the nearest power-of-2 FFT (cliff bounded, §4).

18.5 Conformance Fixtures

  • prime/bluestein_sweep.json — many prime + arbitrary sizes vs oracle.
  • prime/rader_prime.json — Rader path for primes vs oracle.
  • prime/primitive_root.json — primitive-root correctness for small primes.
  • numerics/bluestein_chirp_accuracy.json — chirp accuracy (the n²/2 exponent risks precision loss).

18.6 Pitfalls

  • Chirp exponent n²/2: for large N, n² overflows or loses precision in the exponent → compute W_N^{(n² mod 2N)/2} (reduce mod 2N) to keep the angle accurate (I7).
  • Bluestein accuracy is worse than direct Cooley–Tukey (extra transforms + chirp multiplies) → document the error inflation; still within O(log M)·ε.
  • Rader needs N prime (a primitive root exists); for prime powers use a different (Winograd/PFA) route or Bluestein — detect.
  • Padding M must be ≥ 2N−1 (else circular convolution wraps and corrupts) — and a power of 2 for the inner FFT.
  • DC term in Rader is handled separately — forgetting it drops X[0].

18.7 Performance Concerns

  • Bluestein does ~3 FFTs of size M ≥ 2N−1 → constant-factor ~3–6× overhead vs an equal-size pow2 FFT; the kernel b FFT is precomputable in the plan (amortized).
  • Rader is efficient when N−1 is highly composite; if N−1 is itself prime, recursion/Bluestein inside → measure.
  • Chirp/kernel buffers add O(M) memory.

18.8 Edge Cases

  • N=2 or tiny primes (direct codelet cheaper than Bluestein — route to a small codelet).
  • 2N−1 itself prime (M = next pow2 still fine); very large N where M exceeds memory → resource cap error (I12).
  • N−1 with a large prime factor (Rader recursion depth).

18.9 Failure Analysis

  • A chirp-exponent precision bug shows as accuracy degrading with N for primes only → the chirp-accuracy fixture + per-size bound catch it.
  • A wrong primitive root scrambles Rader output entirely → the primitive-root fixture + oracle diff.
  • Blast radius: any non-smooth N; the planner's fallback path → must be rock-solid (runbook prime-size-cliff.md).

18.10 Operational Notes

  • PlanTrace.codelets shows bluestein(M=…) / rader(p,g=…).
  • Document the prime-size cliff + Bluestein overhead in docs/failure-analysis/prime-cliff.md.
  • The planner prefers mixed-radix when N is composite; Bluestein/Rader only for prime/awkward factors.

19. Phase 7 — Real-input RFFT / IRFFT (Hermitian symmetry)

19.1 Objectives

  • Implement RFFT (real → N/2+1 complex Hermitian) and IRFFT (Hermitian → real), exploiting X[N−k]=conj(X[k]) for ~2× speed and ½ memory (§8.6, I6).
  • Implement the "two real FFTs from one complex FFT" trick.
  • Define and validate the Hermitian / halfcomplex storage contract.

19.2 Detailed Implementation Steps

  • real::rfft — pack length-N real as length-N/2 complex (even→re, odd→im), run a complex N/2 FFT (any P3–P6 plan), then unscramble with one butterfly pass using W_N to recover X[0..N/2] (§8.6; Sorensen et al. 1987, §5.2 paper 8; exploit-structure per P8, §6).
  • real::irfft — the inverse: re-scramble Hermitian input, complex N/2 IFFT, unpack to real (round-trip within bound, I5).
  • real::hermitian_pack — the N/2+1-complex and halfcomplex layouts (§8.6) + conversions; symmetry X[N−k]=conj(X[k]) by construction (I6, ADR-13).
  • real::two_real_trick — transform two real signals via one complex FFT (z = a + i·b, separate by symmetry; Press et al. ch.12, §5.1 book 5).
  • Handle odd N (no Nyquist bin X[N/2]) via the mixed-radix RFFT route (§17).

19.3 Deliverable

  • RFFT/IRFFT for even and odd N; examples/rfft_spectrum computes a real signal's spectrum.

19.4 Acceptance Criteria

  • RFFT output is exactly Hermitian (X[N−k]=conj(X[k]), X[0].im=X[N/2].im=0) — verified by reconstruction (I6).
  • RFFT matches the first N/2+1 bins of the full c2c FFT within bound (I2).
  • IRFFT∘RFFT = identity within c·log₂N·ε (I5).
  • RFFT ≈ 1.7–2× faster and ½ memory vs c2c of the same N (§4).

19.5 Conformance Fixtures

  • real/rfft_even_odd.json — RFFT vs c2c (even and odd N).
  • real/hermitian_symmetry.json — output symmetry check (I6).
  • real/irfft_roundtrip.json — IRFFT∘RFFT identity.
  • real/two_real_trick.json — two-signal separation correctness.

19.6 Pitfalls

  • The unscramble pass twiddle indexing is subtle (it mixes X[k] and conj(X[N/2−k])) → derive carefully; the c2c comparison catches errors.
  • X[0] (DC) and X[N/2] (Nyquist) are purely real — a packing that stores their imaginary parts as nonzero is a bug (I6).
  • Odd N has no Nyquist bin → the layout differs; handle separately.
  • Halfcomplex layout ordering (re's ascending, im's descending) is easy to get backwards → pin the contract, test.

19.7 Performance Concerns

  • RFFT's ½ memory improves cache behavior on top of the ½ flops → often more than 2× faster in practice.
  • The unscramble pass is O(N) extra work (one butterfly sweep) — cheap relative to the N/2 FFT.
  • IRFFT shares the machinery; ensure the scramble pass is equally tight.

19.8 Edge Cases

  • N odd (no Nyquist), N=1 (trivial real), N=2.
  • Real input with ±Inf/NaN → propagates (I13); the symmetry still holds structurally.

19.9 Failure Analysis

  • A packing/unscramble bug shows as the reconstructed spectrum violating Hermitian symmetry → the symmetry fixture (I6) is the precise net.
  • Blast radius: RFFT is the path real-world consumers (DSP #174, codecs) use most → high priority.

19.10 Operational Notes

  • PlanTrace.codelets shows the Real{half} wrapper + the inner plan.
  • Document the Hermitian/halfcomplex layout in the README and docs/ (it is a public I/O contract).
  • The N/2+1 output-length convention is part of the API contract (Compatibility Guarantees).

20.1 Objectives

20.5 Conformance Fixtures

  • numerics/normalization_{none,oneovern,unitary}.json — round-trip per convention.
  • convolution/linear_vs_direct.json — FFT conv vs direct.
  • convolution/overlap_add_save_equiv.json — streaming == single conv.
  • convolution/bignum_multiply.json — FFT multiply vs schoolbook (bounded sizes).

20.6 Pitfalls

  • Normalization applied twice (once in IFFT, once by the caller) → the guard + the convention id (I5) prevent it.
  • Linear vs circular: insufficient zero-padding silently gives circular (wrap-around) results → the consumer must pad; document loudly.
  • overlap-save discards the wrap-corrupted block prefix; overlap-add sums tails — mixing the two corrupts output.
  • bignum: f64 has 53 mantissa bits → products exceeding ~2⁵³ lose precision in the carry step → cap digit size or use NTT (deferred); a silent precision bug otherwise (docs/failure-analysis/bignum-precision.md).

20.7 Performance Concerns

  • Convolution cost is dominated by the FFTs → reuse plans; precompute the fixed-kernel FFT once (overlap-add/save).
  • Block size in overlap methods trades FFT efficiency vs latency → tunable (the #291 real-time consumer cares).
  • For real signals, use RFFT convolution (½ the work).

20.8 Edge Cases

  • N=1 IFFT; zero-length convolution; kernel longer than the block; circular conv of equal-length inputs.
  • Convolution of signals with ±Inf/NaN; bignum carry overflow at the precision boundary.

20.9 Failure Analysis

  • A normalization-convention bug shows as round-trip off by a constant factor → the per-convention fixtures pinpoint it.
  • A bignum precision overrun produces wrong digits silently for huge inputs → the bounded-size fixture + documented limit; recommend NTT (deferred).
  • Blast radius: convolution feeds DSP (#174) and bignum (#370) — both consumers.

20.10 Operational Notes

  • PlanTrace.norm / norm_convention_id (I5).
  • Document each normalization convention + the convolution padding rules in the README (public contract).
  • The bignum hook + NTT-deferral noted in docs/ and cross-linked to #370.

21. Phase 9 — Multi-dimensional FFT (2D / 3D, row-column)

21.1 Objectives

  • Implement 2D and 3D FFT via the row-column method: batched 1-D FFTs along each axis (§ box multidim).
  • Support real-input 2D RFFT (for images / codecs / #173).
  • Parallelize the independent rows/columns across threads (I11) and add a transpose-for-locality option.

21.2 Detailed Implementation Steps

  • multidim::fft2d — FFT every row (a batched 1-D plan), then every column; 3D adds the third (page) axis.
  • multidim::row_column — the batched-1-D driver (reuse 1-D plans; iterate along strided axes).
  • multidim::transpose — optional cache-friendly transpose between axes (so the column pass is contiguous) — the standard trick to avoid strided FFTs.
  • threading::partition — split rows/columns across the pool; disjoint cover (I11).
  • 2D RFFT: RFFT along one axis (Hermitian), c2c along the others.

21.3 Deliverable

  • 2D/3D c2c and 2D real FFT; examples/fft2d_image transforms an image-shaped array.

21.4 Acceptance Criteria

  • 2D/3D FFT matches a 2D/3D naïve DFT oracle within bound (I2).
  • Row-column == direct multi-dim DFT (separability holds).
  • Threaded multi-dim is a disjoint cover (I11, TSan clean) and deterministic per thread count (I4).
  • 2D RFFT exploits Hermitian symmetry (≈ ½ memory along the real axis, I6).

21.5 Conformance Fixtures

  • multidim/fft2d_vs_oracle.json — 2D FFT vs 2D oracle.
  • multidim/fft3d_vs_oracle.json — 3D.
  • multidim/rfft2d.json — 2D real FFT symmetry.
  • multidim/threaded_determinism.json — same result at 1/2/4/8 threads.

21.6 Pitfalls

  • Strided column-axis FFTs thrash cache → transpose first (the row-column performance crux).
  • Mixing the axis order (which axis is contiguous) → wrong layout, plausible-but-wrong output; pin the convention (row-major: last axis contiguous).
  • 2D RFFT: which axis carries the Hermitian symmetry must be documented (usually the last/contiguous one).
  • Thread oversubscription if a batched 1-D plan is itself threaded (it should not be inside a parallel multi-dim region).

21.7 Performance Concerns

  • The transpose dominates non-FFT time for large arrays → blocked/cache-oblivious transpose (a P12 lever).
  • Memory bandwidth caps multi-dim scaling once aggregate traffic saturates the bus (like #349 GEMM).
  • Batched 1-D plans amortize twiddle generation across many rows.

21.8 Edge Cases

  • Non-square 2D (rows ≠ cols); a 1×N or N×1 "2D" (degenerates to 1-D); 3D with a unit dimension.
  • Prime dimensions (each axis routes through Bluestein/Rader); very large images (memory).

21.9 Failure Analysis

  • An axis-ordering or transpose bug shows as a transposed/scrambled 2D spectrum → the 2D oracle diff catches it.
  • Blast radius: image/video codecs (#173/#380) and PDE consumers depend on multi-dim correctness.

21.10 Operational Notes

  • PlanTrace records the per-axis 1-D plans + transpose strategy.
  • Document the axis/layout convention (which axis is contiguous, where Hermitian symmetry lives) — a public contract.
  • Threading policy: parallelize across rows/cols, single-threaded inner 1-D FFT.

22. Phase 10 — The planner (estimate / measure, codelet selection, wisdom)

22.1 Objectives

  • Build the FFTW-style planner: factor N → a plan tree of codelets; choose via ESTIMATE (cost model) or MEASURE (timing); persist wisdom (I9, P5).
  • This is what turns the codelet zoo (P1–P9) into one coherent "best plan for this N on this machine" engine.

22.2 Detailed Implementation Steps

  • planner::factor_plan — factor N (trial division), enumerate candidate decompositions (which radix, which N₁·N₂ split, when to use Bluestein/Rader).
  • planner::cost_model — ESTIMATE: static cost = Σ codelet_flops + memory_traffic·bytes_cost with per-codelet constants from the probe (§11.7).
  • planner::measure — MEASURE/PATIENT: time candidate sub-plans (warmup + median-of-k), keep the fastest; PATIENT explores more candidates.
  • planner::plan_tree — build the chosen PlanTree (§11.4); compute plan_hash (I9).
  • planner::wisdom — persist (WisdomKey → PlanTree) to a file; import/export_wisdom (§11.9); FFTW-format interop documented.
  • planner::select — the top-level plan_c2c/r2c/... entry points; wisdom lookup → reuse, else plan + record.

22.3 Deliverable

  • A planner that picks (and persists) good plans across all sizes; examples/plan_inspect + wisdom_io show plan trees and wisdom round-trip; tools/plan_inspector.

22.4 Acceptance Criteria

  • ESTIMATE plans in < 1 ms; MEASURE within the budget (§4); wisdom hit re-plans in < 100 µs (§4).
  • MEASURE chooses a plan within ~10 % of the best hand-tuned plan for common sizes.
  • Plan determinism: same (N,dir,layout,flags,ISA,dtype) → same plan tree hash (I9); wisdom round-trips losslessly.
  • A plan chosen by the planner passes the accuracy bound (I2) for its N.

22.5 Conformance Fixtures

  • golden/plan_tree_hash.json — deterministic plan-tree hashes per (N,flags,ISA) (I9).
  • golden/wisdom_roundtrip.json — export→import == identity.
  • numerics/planner_vs_handtuned.json — measured plan within tolerance of best-known.

22.6 Pitfalls

  • Cost-model miscalibration → ESTIMATE picks a poor plan (correct but slow) → MEASURE/wisdom is the safety valve; recalibrate constants per ISA.
  • Wisdom keyed on too little (omitting ISA or dtype) → a plan measured on one machine reused wrongly on another → the key must include ISA + dtype (I9).
  • MEASURE non-determinism (timing noise) → pin threads, median-of-k, stable tie-break (prefer the canonical plan on ties, I4).
  • Wisdom file corruption / version mismatch → validate on import (WisdomCorrupt error), fall back to planning (wisdom-corruption.md).
  • Combinatorial explosion of candidates in PATIENT → bound the search depth.

22.7 Performance Concerns

  • Planning cost is amortized by wisdom → the common (warm) path is a lookup; only the first plan of a size pays MEASURE.
  • The cost model must be cheap (it runs over many candidates) — closed-form per-codelet costs, no execution.
  • Wisdom I/O is off the hot path (load at startup, save on demand).

22.8 Edge Cases

  • N=1 (trivial plan, no search); prime N (the candidate set is Bluestein vs Rader); highly composite N (many splits → bound the search).
  • Empty/missing wisdom file (plan fresh); stale wisdom for a now-unavailable ISA (re-plan).

22.9 Failure Analysis

  • A wisdom key/format bug causes a wrong plan reuse → wrong-machine slowdown or (if a size mismatch slips through) a correctness issue → the round-trip + key fixtures + I1 buffer check guard it.
  • Blast radius: every transform goes through the planner → highest-leverage component (and the most FFTW-like).

22.10 Operational Notes

  • PlanTrace.plan_hash + plan_ns (ESTIMATE vs MEASURE) + the chosen codelets.
  • Wisdom file path configurable (PFFT_WISDOM); fftc wisdom export/import CLI; tools/wisdom_dump.
  • Document the estimate/measure/patient semantics + wisdom format + FFTW-interop in docs/.

23. Phase 11 — SIMD butterfly codelets + FFTW-compatible C ABI

23.1 Objectives

  • Implement vectorized butterfly codelets (AVX2/FMA, with a scalar fallback) for radix-2/4/split-radix and the small-prime kernels — the performance heart (§ box simd).
  • Expose an FFTW-compatible C ABI (fftw_plan_dft_*-style + native pfft_*) — drop-in linkable.

23.2 Detailed Implementation Steps

  • simd::cplx — Cplx<T> vector complex (planar re/im internally per ADR-23 to minimize shuffles); load/store/fma/shuffle wrappers over __m256/__m256d.
  • simd::x86_avx2 — vectorized radix-2/4/split-radix butterflies processing vlen complex points per instruction; the interleave/deinterleave shuffles for AoS↔planar at the edges.
  • simd::scalar_fb — scalar fallback with identical semantics (the correctness reference for the codelets).
  • AVX-512 (zmm, wider) and NEON codelets behind dispatch — PhaseDeferred("§16.2") sites turned real on those ISAs in P12.
  • Register vectorized codelets in CodeletSet (§11.6) via ISA dispatch (ADR-4).
  • cabi crate extern "C" fns: pfft_plan_dft_1d/_r2c/_c2r/_2d, pfft_execute, pfft_destroy_plan, pfft_import/export_wisdom; #[repr(C)] opaque plan handle; map flags ↔ PlanFlags; catch_unwind at every boundary (I12). An FFTW-symbol shim (fftw_* aliases) is optional.

23.3 Deliverable

  • SIMD codelets ≥ 2× the scalar form; libpfft.so/.a + pfft.h; examples/pfft_from_c.c links and runs.

23.4 Acceptance Criteria

  • SIMD codelets match the scalar fallback (and oracle) within bound (I2); no register spill (disasm/perf verified, P4).
  • A C program calling pfft_plan_dft_1d + pfft_execute gets identical results to the Rust facade.
  • f32 ≈ 2× f64 throughput (SIMD width exploited, §4).
  • No unwinding across the FFI boundary (C integration test, I12).

23.5 Conformance Fixtures

  • dft/simd_vs_scalar.json — vectorized codelets vs scalar (within bound).
  • numerics/no_register_spill.json — disasm assertion (no inner-loop spills).
  • abi/c_integration.json — a C program's result == Rust facade.
  • badargs/cabi_param_positions.json — bad-arg → error/null plan (I12).

23.6 Pitfalls

  • Complex interleave: AoS [re,im,re,im] needs shuffles to do SIMD complex multiply → planar (SoA) inside codelets (ADR-23) reduces shuffles; convert at edges. Getting the shuffle masks wrong is a subtle correctness bug.
  • Register spill from too-wide butterflies → the #1 perf cliff (like #349's micro-kernel); verify in asm (P4).
  • Unaligned load/store on user buffers (the C caller may pass unaligned data) → handle a misaligned head/tail or copy into aligned scratch.
  • Panic across FFI = UB → catch_unwind everywhere (I12).
  • FFTW symbol collision if both libs are linked → namespace under pfft_*, make fftw_* aliases opt-in.

23.7 Performance Concerns

  • The vectorized butterfly is where peak fraction is won/lost → independent accumulator chains hide FMA latency (like GEMM).
  • Shuffle overhead for complex multiply caps the complex peak below the real FMA peak → document.
  • ABI marshalling is negligible vs compute.

23.8 Edge Cases

  • N not a multiple of vlen (scalar tail); misaligned C buffers; null pointers (validate, I12).
  • Mixed f32/f64 calls; reentrancy from a Fortran caller.

23.9 Failure Analysis

  • A shuffle-mask bug fails subtly (some lanes wrong) → the SIMD-vs-scalar fixture is the precise net.
  • An FFI enum/flag mismatch produces wrong results in someone else's program → the pinned-header + C integration test (highest severity).
  • Panic-across-FFI → crash → catch_unwind + CI test.
  • Blast radius: SIMD codelets underlie all hot-path performance; the ABI is the external contract.

23.10 Operational Notes

  • PlanTrace.isa + the selected codelet names; tools/plan_inspector dumps the codelet + disasm.
  • Document the register budget (butterfly-budget.md) and the FFTW-compat ABI surface.
  • SONAME + symbol versioning for ABI stability; pfft.h is the pinned header.

24. Phase 12 — Performance hardening (the long pole)

24.1 Objectives

  • Close to ≥ 60 % of the 5N·log₂N flop ceiling across the full size sweep; bound the prime-N cliff.
  • Levers: bit-reversal/transpose cache optimization, codelet tuning, twiddle-layout, small-N specialization, AVX-512/NEON codelets (gated), prefetch.

24.2 Detailed Implementation Steps

  • Blocked / cache-oblivious bit-reversal and multi-dim transpose (the dominant non-compute costs; Hennessy & Patterson ch.2, §5.1 book 8; mechanical-sympathy per P4, §6).
  • Twiddle-table layout for streaming access (group twiddles by stage; consider on-the-fly for large N to save bandwidth — the ADR-07 bandwidth/accuracy knob; Bailey 1989 four/six-step, §5.2 paper 9).
  • Specialized small-N codelets (fully unrolled straight-line FFTs for N ≤ 64) — the leaves of every mixed-radix plan (ADR-08; Frigo PLDI 1999, §5.2 paper 3).
  • Implement AVX-512 (wider butterflies) and NEON codelets behind dispatch (turn PhaseDeferred("§16.2") sites real; ADR-04 dispatch; Agner Fog tables, §5.1 book 9).
  • Prefetch tuning in the stage loop and the packing/transpose passes; keep the butterfly tile register-resident (P4, P4; no spill, I-perf).
  • Recalibrate the planner's cost-model constants per ISA from measured codelet costs (ADR-09; feeds §22 cost model).

24.3 Deliverable

  • GFLOP/s sweep meeting §4 across N ∈ [16, 2²⁴] (pow2, composite, prime); AVX-512 path measurable on a capable CPU.

24.4 Acceptance Criteria

  • ≥ 60 % flop ceiling (pow2, f64, 1 thread) sustained across the sweep.
  • Small-N codelets beat the general path below threshold.
  • Prime-N cliff bounded to ~3–6× (§4); AVX-512 ≈ 2× AVX2 where available.
  • No accuracy regression (re-diff oracle, I2).

24.5 Conformance Fixtures

  • golden/gflops_sweep_full.json — per-size flop-fraction floor (pow2/composite/prime).
  • dft/small_n_codelets.json — small-N specialization correctness + crossover.
  • ISA-specific golden hashes; bench/pow2_vs_prime curve.

24.6 Pitfalls

  • Bit-reversal cache misses dominate large-N FFTs → a blocked permutation is the key win; measure miss rates.
  • AVX-512 downclocking can make it slower than AVX2 for bandwidth-bound (large-N) FFTs → measure, don't assume (like #349).
  • Small-N overhead (the general machinery) → branch to specialized codelets early.
  • On-the-fly twiddles trade bandwidth for trig flops → the right choice is size- and ISA-dependent; measure.
  • NEON has 32 registers → a different butterfly width optimum than AVX2's 16.

24.7 Performance Concerns

  • The whole phase is performance: roofline + flamegraph + perf counters (L1/L2/L3 miss, dTLB, FMA-port util, IPC).
  • The bit-reversal-miss-rate and transpose-cost curves are the canonical tuning artifacts.
  • Document each win/regression in docs/performance/.

24.8 Edge Cases

  • Frequency scaling / turbo variance (pin the governor in bench); thermal throttling on long runs; mixed sizes in one workload; cache-resident vs out-of-cache N (the crossover where bit-reversal cost explodes).

24.9 Failure Analysis

  • A "win" on one CPU can regress another → CI bench matrix across ISAs; regressions block release.
  • A perf-only change must not alter accuracy → re-run the accuracy sweep after every tuning change (runbook perf-regression.md).

24.10 Operational Notes

  • Bench-gate thresholds per ISA; PFFT_ISA/PFFT_TWIDDLE overrides for experiments.
  • Record flop-fraction history in CHANGELOG (the numeric/perf contract).
  • New-ISA codelet procedure in docs/runbooks/new-isa-codelet.md.

25.1 Objectives

  • Lock correctness and performance with a full conformance suite.
  • Components: differential vs the O(N²) oracle, numerical error-bound + Parseval + round-trip assertions, an FFTW differential harness, codelet/permutation/Bluestein fuzzing, and a reproducible GFLOP/s report.

25.2 Detailed Implementation Steps

  • differential — generate {dtype × N (pow2/composite/prime) × dir × layout × norm × 1d/2d/3d × real/complex}, run the runtime vs the oracle, assert the error bound (I2).

  • fuzz — cargo-fuzz targets: random N (incl. primes/awkward), bit-reversal/permutation bijection (I3), Bluestein chirp, RFFT round-trip, plan/wisdom round-trip; ASAN/Miri.
  • Determinism — golden hashes per (N, plan, ISA) (I4) and plan-tree hashes (I9).

25.3 Deliverable

  • make conformance green; make bench emits a report; make fuzz runs N iterations clean.

25.4 Acceptance Criteria

  • 100 % differential pass within bounds across the full case space (I2).
  • FFTW differential agrees within bound for all tested sizes.
  • Fuzz clean ≥ 10⁷ iterations (extended 30-day runs deferred).
  • Determinism hashes stable; bench meets all §4 constraints; coverage of all transform types (c2c/r2c/c2r/2d/3d/conv).

25.5 Conformance Fixtures

  • Full conformance/ corpora: dft/, real/, prime/, multidim/, numerics/, convolution/, badargs/, golden/.
  • Structured inputs (impulses, sinusoids at exact bins, chirps, random) with known spectra.

25.6 Pitfalls

  • Tolerance too tight (false fails on legit rounding) or too loose (misses bugs) → derive from theory (Higham §24, c·log₂N·ε).
  • Fuzz corpus not exercising prime/awkward N or non-vlen-multiple sizes → bias the generator toward edges.
  • Determinism hash breaks legitimately when the planner changes → version the golden set with the numeric contract (I4/I9).
  • FFTW differential masking a shared-convention bug (both use the same sign) → keep the independent oracle as the primary truth.
  • Bench noise (turbo, noisy neighbors) → pin + median.

25.7 Performance Concerns

  • Bench is the perf gate; exclude measurement overhead (warmup, steady-state windows); plan once, time execute.

25.8 Edge Cases

  • N=1, primes, prime powers, highly-composite N; extreme dynamic range (energy in one bin); NaN/Inf propagation; subnormals; max sizes (memory limits); Bluestein where 2N−1 is itself prime.

25.9 Failure Analysis

  • A conformance gap = a shippable bug. Differential + error-bounds + FFTW-diff are the safety net; any escape → add a regression fixture (the suite only grows).

25.10 Operational Notes

  • CI runs differential + short fuzz + bench gate per PR; nightly long fuzz + full sweep + FFTW-diff.
  • Reports archived. This phase defines "Phase-0 done" for the future coding contract.

29. Compatibility Guarantees

  • C ABI: pfft_* function signatures and the #[repr(C)] plan handle are frozen — changing them is SemVer-major. SONAME tracks ABI. Optional fftw_* aliases follow FFTW's signatures.
  • Numeric behavior: error bounds are the contract, not bit-reproducibility across plans/ISAs/thread counts. A change altering results within-bounds is a minor version + CHANGELOG entry (P7, ADR-31). Bit-reproducible deterministic mode (PFFT_DETERMINISTIC) is itself a stable contract.
  • Normalization convention: the chosen Normalization is part of the plan's contract; the default (forward unnormalized, inverse 1/N) is stable and documented (ADR-11, I5).
  • RFFT / Hermitian layout: the N/2+1-complex and halfcomplex storage layouts are a frozen I/O contract (§8.6).
  • Wisdom format: our wisdom is versioned; an incompatible format is rejected (WisdomCorrupt) and re-planned, never silently mis-applied. FFTW-format interop is documented best-effort (read-only import), not a hard guarantee.
  • API (Rust): SemVer; #[non_exhaustive] on FftError/Isa/Normalization so additions are non-breaking.
  • Direction enum values: Forward=-1/Inverse=1 (FFTW convention) frozen.
  • Deprecation: one minor-version warning cycle before removal.
  • Size support: any N ≥ 1 is supported permanently (mixed-radix/Bluestein/Rader); adding a faster path for a size is not a breaking change.

  • Unit: per-codelet vs hand-computed values (8-point §8.5, radix-3/5 base sizes); bit-reversal mappings; twiddle tables vs direct-trig; Hermitian packing round-trip.
  • Differential: every transform vs the naïve O(N²) oracle across the full case space (the backbone, P1/P13, I2).
  • FFTW differential: vs reference FFTW corpora (generated, non-dependency) — a second independent oracle.
  • Property (proptest): randomized N/strides/inputs; invariants (bit-reversal bijection I3, Parseval I8, linearity, shift theorem, RFFT Hermitian symmetry I6, round-trip I5).
  • Numerical error-bound: measured error ≤ c·log₂N·ε·‖x‖ × safety factor, parameterized by N (Higham §24) — and the naïve-vs-FFT comparison (the selling point).

33. Scalability Analysis

  • Single 1-D FFT: inherently sequential (each stage depends on the previous) → does not thread well; scaling comes from batching (many independent 1-D FFTs) and multi-dim (independent rows/cols).
  • Batched / multi-dim scaling: near-linear to physical cores for many independent transforms; SMT gives little (FP units shared); falls off when bandwidth-bound (the transpose/bit-reversal traffic saturates the bus).
  • Problem-size scaling: O(N log N) compute vs O(N) data → larger in-cache N is more efficient; once N exceeds cache, bandwidth (bit-reversal + twiddle streaming) caps throughput → the four-step/six-step (Bailey) and blocked transpose are the levers.
  • Prime-N scaling: Bluestein adds a constant factor (~3–6×) and O(M) memory; not asymptotically worse, but a real per-size cost (the bounded cliff).
  • Twiddle-table scaling: O(N) per cached size → LRU-evict to bound memory; on-the-fly generation trades bandwidth for trig flops at very large N.
  • NUMA: remote-memory access on large multi-dim transforms kills scaling on multi-socket → first-touch + per-node scratch (deferred §39, documented).
  • What does NOT scale here (by design): distributed/multi-node FFT (deferred §39 — that would wrap this as the per-rank local kernel, mirroring #351's relation to #349); GPU FFT (deferred §39).
  • Coordination overhead: negligible for the library itself (no metadata service); the planner's cost is amortized by wisdom.

34. Mental Models & First Principles

The compressed insights an FFT expert carries. Each: the model, what it predicts, the bug class you write without it, and where this blueprint applies it.

  • MM1 — The FFT is divide-and-conquer on the DFT's algebraic structure; the twiddle factor is the merge step. The DFT matrix factors into sparse stage matrices; each Cooley–Tukey split is "solve two half-size DFTs, then merge with a diagonal of twiddles." Predicts: every variant (radix-r, mixed-radix, split-radix) is just a different factoring of the same matrix, so they all compute the same X to within rounding. Bug class without it: treating radix-4/split-radix as "a different transform" and expecting different results, instead of asserting one shared oracle bound. Applied: §8.2, §8.7, Phase 1 (§13), Phase 4 (§16).
  • MM2 — W_N^{k+N/2} = −W_N^k is the whole speedup. The half-period antisymmetry of the roots of unity lets one twiddle multiply serve two outputs (the butterfly's a±w·b). Predicts: the flop count is ~(N/2)·log₂N butterflies because each stage reuses every twiddle product twice; lose the symmetry and you're back to O(N²). Bug class: computing w·b twice (once per output) — correct but throws away the constant factor that makes it an FFT. Applied: §8.1–8.3, Phase 1 (§13.2).
  • MM3 — Accuracy improves with the fast algorithm because error counts stages, not terms. Each value passes through log₂N butterfly roundings, vs N additions in the naïve DFT → forward error ~c·log₂N·ε·‖x‖ vs ~N·ε·‖x‖. Predicts: the FFT is both faster and more accurate; accuracy degrades only logarithmically with N. Bug class: setting a fixed absolute tolerance independent of N (false fails at large N, missed bugs at small N) instead of an N-parameterized bound. Applied: §4.1, I2, Phase 3 (§15.2), Phase 13 (§25).
  • MM4 — There is no single best FFT; the optimal plan is a function of (N's factorization, cache, ISA). The best decomposition trades flops against memory traffic against codelet quality, all machine-dependent — hence the planner. Predicts: a hardcoded "always radix-2" loses to a measured plan on composite/prime N and on other CPUs; wisdom must key on ISA+dtype. Bug class: baking one decomposition in, or keying wisdom on N alone → a plan measured on one machine misapplied on another. Applied: §3.2 (planner), ADR-09/ADR-17, Phase 10 (§22).
  • MM5 — Plan once, execute many; the plan owns all the memory. Planning is amortized over thousands of executes; execute must be allocation-free and re-entrant on its own scratch. Predicts: steady-state latency is jitter-free only if no allocation/planning happens per call (I14); real-time use depends on it. Bug class: allocating scratch or re-planning inside execute → latency spikes, no real-time guarantee. Applied: ADR-06, I14, §11.3, Phase 10 (§22).
  • MM6 — Bit-reversal is a permutation, and permutations are bijections — prove it, don't eyeball it. DIT requires the input in bit-reversed order; the permutation must hit every index exactly once. Predicts: an off-by-one (reversing b vs b−1 bits) yields a plausible-but-wrong spectrum that no magnitude check catches — only a bijection test (histogram all-ones) and the oracle diff do. Bug class: silent index corruption that passes casual inspection. Applied: §8.4, I3, Phase 1 (§13.6), Phase 13 (§25).
  • MM7 — Any DFT is a convolution in disguise (Bluestein), and any convolution is a DFT (the convolution theorem). Bluestein turns a length-N DFT into a length-≥(2N−1) convolution computable by a power-of-2 FFT; the convolution theorem turns conv into FFT·FFT. Predicts: no size is unsupported — the prime-N "cliff" is a bounded constant factor (~3–6×), not an asymptotic wall; and fast multiplication/filtering ride on the same kernel. Bug class: declaring prime sizes unsupported, or padding insufficiently and getting silent circular wrap-around. Applied: §8.8, §8.9, I10, Phase 6 (§18), Phase 8 (§20).
  • MM8 — Real input has Hermitian symmetry, so half the spectrum is free. X[N−k]=conj(X[k]) → only N/2+1 outputs are independent; pack two reals into one complex FFT. Predicts: RFFT is ~2× faster and ½ memory; X[0] and X[N/2] are purely real. Bug class: storing nonzero imaginary parts for DC/Nyquist, or running reals through full c2c and paying 2× for nothing. Applied: §8.6, I6, ADR-13, Phase 7 (§19).
  • MM9 — A multi-dimensional FFT is separable: transform along each axis independently. 2D/3D = batched 1-D FFTs per axis (row-column). Predicts: the bottleneck is the transpose/strided access between axes, not the FFTs; blocking the transpose is the lever. Bug class: doing strided column FFTs without a transpose (cache thrash), or mixing up which axis is contiguous (transposed spectrum). Applied: §3.2 (multidim), Phase 9 (§21), §33 (Scalability).
  • MM10 — The butterfly tile lives in registers; data streams past it. Peak fraction is won when accumulators + twiddles fit the vector register file and independent chains hide FMA latency; lost the instant the codelet spills. Predicts: a butterfly too wide for the register file falls off a performance cliff (visible in disasm as spills) — the same failure mode as a GEMM micro-kernel. Bug class: widening a codelet past the register budget and silently regressing throughput. Applied: P4 (P4), §11.6, Phase 11 (§23.6), Phase 12 (§24).

FFTW3 — the system this design most directly models: its one decisive choice is the code generator (genfft, an OCaml program that emits provably-good straight-line codelets for each base size). That wins decisively once you must support dozens of radices across several ISAs — a scale where hand-writing codelets (our choice, ADR-08) becomes unmaintainable. We accept the smaller hand-written codelet set in exchange for readable, debuggable, dependency-free Rust; FFTW's niche is "maximum size/ISA coverage at any maintenance cost," and it owns that niche.

Intel MKL DFTI — its decisive choice is vertical integration with the microarchitecture: hand-tuned AVX-512 kernels, cache/NUMA heuristics, and a descriptor API co-designed with Intel silicon. That wins on Intel server CPUs where the last 20% of peak matters and the binary will only ever run on Intel. We forgo vendor-locked tuning for portability and openness; MKL's niche is "absolute peak on Intel hardware," unbeatable there and irrelevant off it.

NVIDIA cuFFT — its decisive choice is Stockham auto-sort, out-of-place, massively data-parallel on GPU SMs: it avoids the bit-reversal permutation entirely (paying a second buffer) because scattered writes are catastrophic on a GPU but extra bandwidth is cheap. That wins when N is large and the data already lives in GPU memory (deep learning, large spectral simulations). We are a CPU engine with in-place support (ADR-12); cuFFT's niche is GPU-resident batched transforms, deferred here (§40 GPU FFT).

PocketFFT — the closest readable model for our scope and NumPy/SciPy's actual backend. Its decisive choice is pragmatic compactness: a single header, mixed-radix + Bluestein covering every N, no planner and no persistent wisdom — it plans cheaply per call. That wins as a default library backend where simplicity, portability, and "works for any N out of the box" beat the last increment of speed. We add a planner + wisdom + SIMD codelets + a C ABI; PocketFFT's niche is "the sensible default everyone links," which is exactly why NumPy chose it.

36. Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived from the System Constraints (§4): ε = 2⁻⁵³ (f64), complex = 16 B (two f64), cache line 64 B, L1d 32 KB, L2 256 KB–1 MB, AVX2 = 4 f64 lanes, flop model 5N·log₂N.

  • C1 — Flop count (radix-2), N = 2²⁰: flops = 5·N·log₂N = 5 · 2²⁰ · 20 ≈ 1.05×10⁸ flops. At a 50 GFLOP/s sustained single-core f64 rate (≈60% of a ~85 GFLOP/s peak, §4): t ≈ 1.05×10⁸ / 5×10¹⁰ ≈ 2.1 ms. (Derives the "milliseconds" headline vs the naïve "seconds.")
  • C2 — Naïve-DFT flop count, same N: flops ≈ 8·N² = 8·(2²⁰)² ≈ 7.0×10¹³. Speedup = 8N² / (5N·log₂N) = 1.6N/log₂N = 1.6·2²⁰/20 ≈ 8.4×10⁴×. (Quantifies §4.1's "~10⁵× speedup".)
  • C3 — Split-radix flop count, same N: flops ≈ 4·N·log₂N ≈ 8.4×10⁷ → ~20% fewer than radix-2's 5N·log₂N; expected speedup ~1.2× modulo memory traffic (§4 split-radix row).
  • C4 — Twiddle-table bytes for size N: bytes = N · 16 (one complex per index; half-table + symmetry ≈ (N/2)·16). At N = 2²⁰: ≈ 16 MB full / ≈ 8 MB half — far exceeds L2 (256 KB–1 MB) → the table streams from L3/RAM each stage (§32 twiddle residence). Split-radix adds the W^{3k} table: ×1.5 (§4 twiddle row).
  • C5 — Cache-blocking threshold (largest N kept in L2): N_L2 = L2 / 16. For L2 = 512 KB: N_L2 = 524288/16 = 32768 = 2¹⁵. Above 2¹⁵ a single transform's data spills L2 → bandwidth-bound regime begins; below it, compute-bound (§33 problem-size scaling).
  • C6 — In-L1 small-codelet ceiling: N_L1 = L1d / 16 = 32768/16 = 2048 = 2¹¹. Fully-unrolled small-N codelets (Phase 12, §24.2) target N ≤ 64 so the working set (64·16 = 1 KB) sits comfortably in L1 with room for twiddles + registers.
  • C7 — Memory traffic, out-of-place, one pass: traffic = 2·N·16 B (read input + write output) = 32·N B. At N = 2²⁰: ≈ 32 MB moved minimum; bit-reversal/transpose add scattered re-reads, inflating effective traffic — the dominant non-compute cost (§24.6). In-place halves the buffer footprint (ADR-12) but keeps the scattered bit-reversal traffic.
  • C8 — Roofline crossover (arithmetic intensity): AI = flops/bytes = 5N·log₂N / (32·N) = (5/32)·log₂N ≈ 0.156·log₂N flop/B. At N=2²⁰: AI ≈ 3.1 flop/B. Against a ~10 GB/s·core effective bandwidth and ~50 GFLOP/s compute, the machine balance is ~5 flop/B → FFT at this N is bandwidth-bound (AI 3.1 < 5), confirming C5/C7 and §33.
  • C9 — Numerical RMS error bound, N = 2²⁰: ‖err‖/‖X‖ ≲ c·log₂N·ε = c·20·2⁻⁵³ ≈ c·2.2×10⁻¹⁵ (c≈O(1), Higham §24). vs naïve ≈ N·ε = 2²⁰·2⁻⁵³ ≈ 1.2×10⁻¹⁰ → FFT is ~5×10⁴× more accurate (I2, §4.1). (Derives the accuracy target, not just asserts it.)
  • C10 — Bluestein overhead for prime N: for prime N, pad to M = next_pow2(2N−1) → M ∈ [2N, 4N). Work ≈ 3 FFTs of size M ≈ 3·5·M·log₂M. Ratio to a size-N pow2 FFT ≈ 3·(M/N)·(log₂M/log₂N) ∈ ~[3, 6]× → the bounded cliff (§4 prime-N row, §18.7).
  • C11 — Wisdom re-plan vs cold MEASURE: cold MEASURE times ~k candidates × median-of-m runs ≈ k·m·exec_time (10 ms–seconds, §4); a wisdom hit is a hashmap lookup + tree rebuild < 100 µs (§4). Break-even: wisdom pays off after the first reuse of any (N,dir,layout,ISA,dtype) key (§22.7).
  • C12 — Batched throughput ceiling (multi-dim/many transforms): B independent size-N transforms across P cores ≈ B·5N·log₂N / (P·rate) until aggregate traffic B·32·N / time saturates ~P·10 GB/s; beyond that, bandwidth caps scaling (§33 batched scaling, like #349 GEMM).

  1. Why is the FFT both faster and more accurate than the naïve DFT, and how do you encode that in a test? Synthesize §8.1 (conventions) + I5 (§7) + §20.2/20.6 (normalization step + double-normalize guard): the scale is one explicit step keyed to Normalization; the guard + norm_convention_id prevent the caller-plus-IFFT double scale.
  8. Why is a single 1-D FFT hard to thread, and where does parallelism actually come from? Synthesize §3.3 (concurrency boundary) + §33 (scalability) + I11 + §21.10: each stage depends on the previous (sequential); parallelism comes from batching and multi-dim row/column independence (disjoint cover, I11).
  9. What makes bit-reversal the performance villain at large N, and what's the lever? Synthesize §8.4 + C5/C7 (§36) + §24.6 (pitfalls) + §32 (cache artifacts): scattered access blows the cache once N exceeds L2 (N>L2/16); blocked/cache-oblivious permutation is the win.
  10. How does Rader reduce a prime-N DFT to a convolution, and what number-theoretic object makes it work? Synthesize §8.8 (Rader) + §18.2 (primitive_root/modinv) + I10: a primitive root g of N reindexes the N−1 non-DC outputs into a length-(N−1) cyclic convolution; DC is handled separately.
  11. Why does the complex multiply use the 4-mul form, not the 3-mul Karatsuba form — and when would you flip? Synthesize ADR-19 + §11.1 + the ADR-19 "when rejected wins" cell (§9): 4-mul has better FP error and pipelines better on FP hardware; 3-mul wins only where multiplies dominate and adds are free (fixed-point/integer transforms).
  12. How does RFFT achieve ~2× speed and ½ memory, and which two output bins are special? Synthesize §8.6 + I6 + MM8 (§34) + §19.2: pack reals into a half-size complex FFT + one unscramble pass; X[0] (DC) and X[N/2] (Nyquist) are purely real and must store zero imaginary parts.

Synthesize I1 + I12 + I13 (§7) + §23.6/§26 (threat model): wrong length/alignment → validated to a typed error/null plan before compute; NaN → propagated per IEEE-754, never "cleaned."

Synthesize §24.6 (downclock pitfall) + §4 (bandwidth-bound) + §24.9/§28 (CI bench matrix): AVX-512 downclocking + bandwidth-bound large N; per-ISA bench gates block regressions at merge.

38. Alternative Architectures (Roads Not Taken)

Fundamentally different designs for the same "compute the DFT" mission — not parameter tweaks. Each: sketch, winning regime, real system, why rejected here.

ALT-1 — Naïve O(N²) DFT (dense matrix–vector).

x[0..N-1] ──► [ W matrix, N×N, W[k,n]=e^{-2πikn/N} ] ──► X[0..N-1]
              one GEMV: X = W·x        (no divide-and-conquer)

Wins when: N is tiny (≤ ~16–32) where O(N²) ≤ the FFT's constant-factor overhead, or as the oracle (trusted truth). Also when only a few output bins are needed (→ Goertzel, a one-bin special case). Real system: used internally by every FFT library as the small-N base case and the test oracle (our conformance::oracle, §25.2; ADR-20). Why rejected as the engine: O(N²) is catastrophic at scale (C2: 8.4×10⁴× slower at N=2²⁰) and less accurate (N·ε vs log₂N·ε, MM3) — it is our reference, not our product.

ALT-2 — Recursive radix-2 (function-call tree) vs the iterative bit-reversed form we chose.

 RECURSIVE (call tree)                 ITERATIVE (chosen, Phase 3)
   fft(N)                                 step A: bit_reverse_permute(data)
   ├── fft(N/2) on evens                  step B: log₂N stages, stride-doubling
   │     └── ... down to N=1                      each stage = N/2 butterflies
   └── fft(N/2) on odds                           sweeping the whole array
         └── ...                          ──────────────────────────────────
   merge ◄── twiddle-weighted             one flat array, no recursion,
   butterflies up the tree                no call overhead, O(1) extra memory

Wins when: clarity/teaching matters more than speed (the recursion is the Cooley–Tukey proof), or for a one-off where call overhead is irrelevant. Real system: CLRS ch.30's RECURSIVE-FFT (pedagogical, §5.1 book 3); we build it first in Phase 1 (§13) precisely to anchor correctness. Why rejected as the production form: per-call overhead + poor cache behavior + repeated trig; the iterative in-place form (Phase 3, §15) is ≥5× faster and allocation-free (I14) — so recursion is the teaching path, the iterative kernel is the shipping path.

ALT-3 — Prime-Factor Algorithm (PFA / Good–Thomas) instead of mixed-radix Cooley–Tukey for composite N.

N = N1·N2 with gcd(N1,N2)=1  ──► CRT index map ──► N1×N2 grid
   ──► N2 DFTs of length N1, then N1 DFTs of length N2  (NO twiddle multiply between them)

Wins when: N factors into coprime parts (e.g. 1008 = 16·9·7) — PFA eliminates the inter-stage twiddle multiply entirely (the CRT reindex absorbs it), saving those flops; classic on fixed coprime sizes. Real system: FFTW includes a PFA/Good–Thomas step; Winograd's WFTA builds on it; FFTPACK-era radix-3/5/7 kernels combine with it. Why rejected as the default: it only applies to coprime factors and needs the more intricate CRT index machinery; general mixed-radix Cooley–Tukey (Phase 5, §17) handles all composite N (including prime powers like 2^a) with one uniform twiddle-multiply step — PFA is a deferred optimization for coprime N, not the base mechanism.

ALT-4 — Cache-oblivious recursive (Stockham auto-sort), out-of-place, no explicit bit-reversal.

Stockham: each stage reads from buffer A in one order, writes buffer B in the
   "self-sorting" order ──► after log2(N) stages the data is naturally ordered.
   Ping-pong A↔B every stage; the bit-reversal permutation never appears.

Wins when: scattered writes are catastrophic but bandwidth is cheap — i.e. GPUs and vector machines, where avoiding the irregular bit-reversal permutation is worth a second buffer; also large out-of-cache N where the auto-sort's regular access beats a separate scattered permutation pass. Real system: NVIDIA cuFFT and most GPU FFTs use Stockham auto-sort out-of-place; Bailey's vector-computer FFTs (§5.2 paper 9, 11) too. Why rejected as the default: it mandates out-of-place (two buffers, 2× memory) and forgoes the in-place selling point (ADR-12, MM10); on a CPU with in-place support the explicit blocked bit-reversal (Phase 12, §24) is competitive while keeping O(1) extra memory. We keep Stockham in view for the deferred GPU path (§40) and large-N out-of-place plans.

40. Glossary

  • DFT Discrete Fourier Transform: X[k]=Σ x[n]·W_N^{nk}. IDFT the inverse.
  • FFT Fast Fourier Transform: any O(N log N) DFT algorithm.
  • Cooley–Tukey the divide-and-conquer FFT (recursive even/odd or radix-r split).
  • Twiddle factor W_N^k = e^{−2πik/N}, a power of the primitive N-th root of unity.
  • Butterfly the atomic combine (a,b,w) → (a+w·b, a−w·b).
  • Radix-2 / radix-4 FFT splitting into 2 / 4 sub-DFTs per stage.
  • DIT (decimation-in-time) split the input (bit-reversed in, natural out).
  • DIF (decimation-in-frequency) split the output (natural in, bit-reversed out).
  • Bit-reversal permutation reordering index n to its bit-reversed value; an involution and bijection.
  • Split-radix radix-2/4 hybrid; lowest known flop count (~4N log₂N) for power-of-2.
  • Mixed-radix Cooley–Tukey for composite N via factor decomposition.
  • Codelet a small straight-line (often hand-written/SIMD) FFT kernel for a base size.
  • Bluestein / chirp-z FFT of arbitrary N via a power-of-2 convolution.
  • Rader's algorithm prime-N DFT via a length-(N−1) cyclic convolution + primitive root.
  • Primitive root a generator of the multiplicative group (ℤ/pℤ)*.
  • RFFT / IRFFT real-input FFT exploiting Hermitian symmetry / its inverse.
  • Hermitian symmetry X[N−k]=conj(X[k]) for real input → N/2+1 independent outputs.
  • Halfcomplex layout packed real array storing the N/2+1 complex outputs.
  • Normalization convention placement of the 1/N (or 1/√N) scale factor.
  • Convolution theorem conv(a,b)=IFFT(FFT(a)·FFT(b)).
  • Overlap-add / overlap-save block methods for streaming long-signal convolution.
  • Parseval's theorem energy preservation: Σ|x|² = (1/N)Σ|X|².
  • Planner the component choosing/persisting the best plan (FFTW-style).
  • Plan / execute the two-step API: build a Plan once, execute it many times.
  • Wisdom persisted measured-plan choices keyed by (N, dir, layout, ISA, dtype).
  • Estimate / measure / patient plan modes: cost-model / timed / exhaustive.
  • Plan tree the recursive codelet decomposition of N.
  • Four-step / six-step FFT cache/large-N formulation viewing the data as a 2-D array.
  • Row-column method multi-dim FFT as batched 1-D FFTs along each axis.
  • Flop model 5N·log₂N the standard radix-2 real-flop count (the roofline x-reference).
  • NTT Number-Theoretic Transform: exact integer DFT over ℤ/pℤ (deferred).
  • ISA dispatch runtime selection of the widest available instruction set.
  • u (unit roundoff) / ε 2⁻²⁴ (f32) / 2⁻⁵³ (f64).
  • FMA fused multiply-add, single rounding.
  • YMM/ZMM 256-/512-bit vector registers.
  • Oracle the naïve O(N²) DFT reference (the trusted truth).
