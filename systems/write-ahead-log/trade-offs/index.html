Decisions (§9) · 22 ADRs

ADR-01

Implementation language

Chosen

Rust

Rejected

C, C++, Go, Java

When the rejected choice is right

C wins for a codebase that must link directly into an existing C storage engine with no FFI boundary tolerance

Why: #[repr(C)] byte-exact structs, no GC jitter in force() timing (§4)

ADR-02

LSN representation

Chosen

Absolute byte offset into the logical (multi-segment) log

Rejected

Monotonic opaque counter, decoupled from physical offset

When the rejected choice is right

Opaque counter wins when segment sizes vary unpredictably or the log is not one continuous byte stream (e.g., RocksDB's per-file sequence numbers)

Why: O(1) seek to any LSN without a separate index (P11)

ADR-03

Corruption detection granularity

Chosen

Per-record CRC-32C

Rejected

Whole-segment checksum, no checksum

When the rejected choice is right

Whole-segment checksum wins when segments are written once, atomically, by a single process with no partial-write exposure, e.g. a cold snapshot dump

Why: Torn-write isolation to exactly one record (P7)

ADR-04

Durability barrier syscall

Chosen

fdatasync (fallback fsync)

Rejected

O_DIRECT + write-through (FUA)

When the rejected choice is right

O_DIRECT+FUA wins on NVMe deployments accepting page-cache bypass for the lowest tail latency

Why: Portability across common filesystems (POSIX.1-2017)

ADR-05

Commit batching policy

Chosen

Time+size-bounded group commit (≤2 ms / ≤8 MiB, §4)

Rejected

Immediate per-transaction force()

When the rejected choice is right

Immediate force() wins for a single-writer workload with no concurrent committers to batch with

Why: Throughput under concurrent commit load (P9)

ADR-06

Segment sizing model

Chosen

Fixed-size (16 MiB) rotating segment files

Rejected

Single unbounded growing file

When the rejected choice is right

Single growing file wins for an embedded, single-connection deployment prioritizing simplicity, matching SQLite's regime

Why: Bounded, atomic-rename-friendly rotation and retention (P11/P12)

ADR-07

Segment naming scheme

Chosen

Monotonic zero-padded decimal segment ID

Rejected

Content-hash-based naming

When the rejected choice is right

Content-hash naming wins for a content-addressed archival store deduplicating identical segment bytes

Why: Lexical sort order equals chronological order

ADR-08

Checkpoint style

Chosen

Fuzzy checkpoint (DPT/TT snapshot, no flush-all)

Rejected

Sharp (consistent) checkpoint

When the rejected choice is right

Sharp checkpoint wins for a small in-memory dataset where flush-all cost is negligible

Why: Avoids an I/O stall at checkpoint time (P10, Mohan et al. 1992)

ADR-09

Recovery algorithm family

Chosen

ARIES three-pass (Analysis/Redo/Undo)

Rejected

Two-pass redo-only under a no-steal/no-undo buffer policy

When the rejected choice is right

No-steal wins when the buffer pool always fits the entire dirty working set, eliminating eviction pressure

Why: Supports early eviction of uncommitted (dirty) pages

ADR-10

Undo mechanism

Chosen

Compensation Log Records with UndoNextLSN chaining

Rejected

Plain undo re-execution without CLRs

When the rejected choice is right

Plain re-execution wins only in a system with a proof obligation of zero crashes during rollback — not a real crash-recovery target, but a stated regime such as an in-memory test harness with no crash injection

Why: Idempotent rollback under repeated crash-during-undo (P3)

ADR-11

Buffer-page write policy

Chosen

Steal, no-force

Rejected

Force policy (flush all dirty pages at commit)

When the rejected choice is right

Force policy wins in a design with no separate log at all (shadow paging), where the page write is the only durability mechanism

Why: Decouples commit latency from data-page I/O (P5, Härder & Reuter 1983)

ADR-12

Log record content model

Chosen

Physiological (physical PageId + logical operation description)

Rejected

Pure physical (full before/after page images) or pure logical (operation-only, no page anchor)

When the rejected choice is right

Pure physical page images win when operations are too structurally complex to redo deterministically from a logical description alone (e.g., a full B-tree page split)

Why: Balances redo/undo cost against record size (P6, Mohan et al. 1992)

ADR-13

Page-to-log linkage

Chosen

Embedded pageLSN header field on every page

Rejected

External side-table tracking last-applied LSN per page

When the rejected choice is right

External side-table wins when the page format is fixed and foreign, unable to accommodate a header field

Why: O(1) redo-skip check per page without an auxiliary lookup (I6)

ADR-14

Dirty Page Table persistence

Chosen

Snapshot embedded in each checkpoint record

Rejected

Full-log rescan from the start on every recovery

When the rejected choice is right

Full rescan wins for a tiny log where checkpoint bookkeeping overhead exceeds the scan time it would save

Why: Bounds Analysis-pass scan length (P10)

ADR-15

Transaction Table persistence

Chosen

Snapshot embedded in checkpoint, refined during Analysis

Rejected

Pure derivation from BEGIN/COMMIT/ABORT records with no checkpoint hint

When the rejected choice is right

Pure derivation wins for workloads with very few, very long-lived transactions where snapshot churn outweighs its benefit

Why: Bounds Analysis-pass start point (I5)

ADR-16

Segment retention policy

Chosen

Retain until checkpointed AND acknowledged by every attached replica

Rejected

Fixed segment-count ring-buffer retention

When the rejected choice is right

Fixed-count retention wins for a standalone deployment with no replicas, where bounding disk usage matters more than replay-from-log catch-up

Why: Prevents a replica from needing an already-deleted segment (P12)

ADR-17

Replication transport granularity

Chosen

Streaming, record-granularity log shipping

Rejected

Periodic whole-closed-segment file shipping

When the rejected choice is right

File-based shipping wins for a disaster-recovery-only replica that tolerates minutes of lag and needs a simpler transport

Why: Minimizes replica lag against §28's measurable target

ADR-18

Crate/module layout

Chosen

6-crate workspace (wal-core/writer/reader/recovery/replicate/bench)

Rejected

Single monolithic crate

When the rejected choice is right

Monolithic crate wins for a quick prototype with no reuse or API-boundary goal

Why: Enforces module boundary = terminology boundary (§10)

ADR-19

Writer concurrency model

Chosen

Single dedicated writer thread draining an MPSC intake queue

Rejected

N threads writing directly under a mutexed file handle

When the rejected choice is right

Direct mutexed writes win only at very low concurrency (≤2 writers), where batching gains are negligible relative to queue latency

Why: Group commit batching (ADR-05) requires one serialization point (P4)

ADR-20

Torn-write recovery policy

Chosen

Truncate-and-continue at the first corrupt/incomplete record

Rejected

Fail hard, require manual intervention on any CRC mismatch

When the rejected choice is right

Fail-hard wins for a regulatory audit log required to flag every suspected-corrupt byte range rather than silently truncate it

Why: Matches the physical reality of an interrupted write (P8), matching PostgreSQL/SQLite end-of-log behavior

Test strategy

Property-based (proptest-style) + example fixtures

Rejected

Example-based tests only

When the rejected choice is right

Example-only wins for a small, stable format surface with no ongoing change

Why: Finds LSN-arithmetic and segment-rollover boundary bugs examples miss (§26)

Fixture format

Chosen

JSON scenario files under fixtures/

Rejected

Inline Rust assert! only

When the rejected choice is right

Inline asserts win for a closed, single-language suite with no cross-tool sharing plan

Why: Enables cross-language conformance re-use (§26)

Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Shadow Paging (No Log At All)

Page Table v1 --commit--> Page Table v2 (new root, old pages untouched)
     |                          |
  [old pages]              [new pages]   (atomic root pointer swap = commit)

Wins when: updates are infrequent and whole-page-copy-on-write overhead is acceptable — no log manager needed at all, since the old page table root is always a consistent prior state (Lampson & Sturgis 1979). Real system: early System R prototypes used shadow paging before switching to logging. Rejected here: shadow paging fragments data physically (updated pages move), destroys locality, and cannot express fine-grained (sub-page) concurrent updates the way physiological logging can (ARIES's namesake "fine-granularity locking" goal, Mohan et al. 1992) — the entire point of this project is studying WAL-based recovery, so removing the log erases the subject.

Force-at-Commit, No Redo Capability

Commit(T) --> flush ALL of T's dirty pages to disk --> ack Commit(T)

Wins when: transactions touch very few pages and synchronous flush latency is tolerable — no redo pass is ever needed because every committed page is already durable at ack time (Härder & Reuter 1983's "force" policy). Real system: some embedded key-value stores default to force-on-commit for simplicity. Rejected here: commit latency becomes proportional to dirty-page count and disk seek cost rather than to one force() call (defeats §4's commit-latency targets); it also forecloses the group-commit amortization (P9) this project exists to demonstrate.

Log-Structured Storage (No Separate Data Pages)

Append-only log  ==  the data store itself (no separate "page" to redo against)
   segment1 -> segment2 -> segment3 -> ... -> compaction merges old segments

Wins when: write throughput dominates over read/update-in-place cost, and periodic compaction can absorb the cost of never updating in place (Rosenblum & Ousterhout 1992). Real system: log-structured merge-tree engines (RocksDB, LevelDB, §31) apply this at the storage-engine level; the original LFS paper applied it at the filesystem level. Rejected here: this project's entire subject is the WAL-plus-separate-pages architecture (ARIES) and its redo/undo mechanics — a log-structured store has no in-place page to undo against, eliminating exactly the recovery mechanism (Phase 8) under study.

Consensus-Replicated Log (Raft/Paxos Instead of Async Streaming)

Writer --propose(record)--> [Peer1] [Peer2] [Peer3]  (quorum ack before commit)
                                  \____ committed once (N/2)+1 peers durable ____/

Wins when: the log itself must survive the total loss of the primary machine, not just crash-and-restart (etcd's raft WAL, §31). Real system: etcd, and any Raft/Paxos- backed replicated log. Rejected here: this project's replication (Phase 9, ADR-17) is deliberately asynchronous and single-primary — adding quorum-based commit would require a full consensus implementation, a different and larger project than "build a WAL," and is explicitly deferred (PhaseDeferred("§21")).
