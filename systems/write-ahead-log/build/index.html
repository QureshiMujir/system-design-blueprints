✅ Phase 0 — Repo Skeleton & Correctness Kernel §12

Objectives

Stand up the 6-crate workspace (§10); land Lsn/TxnId/PageId/WalError; land the RecordHeader/RecordType/LogRecord shapes (§11) with no I/O yet; wire CI to run cargo test --workspace on every commit (§27).

Deliverable

Compiling 6-crate workspace; wal-core exports Lsn, TxnId, PageId, WalError, RecordHeader, RecordType, LogRecord; CI green on an empty test suite.

Acceptance

cargo build --workspace exits 0; cargo test --workspace exits 0 with ≥1 placeholder test per crate (6 tests minimum); CI pipeline definition present and green on the initial commit.

Fixtures

None yet — no wire format or I/O exists to fix behavior against. fixtures/ directory created empty with a .gitkeep.

Pitfalls

Defining Lsn as a bare u64 without a newtype (loses P4's compile-time monotonicity-adjacent type safety downstream). Letting RecordType variants carry payload fields directly instead of keeping payload opaque bytes in LogRecord (pre-empts ADR-12's physiological encoding decision before Phase 1 makes it).

✅ Phase 1 — Record & Page Layout §13

Objectives

Implement real binary encode/decode for RecordHeader/LogRecord (§8.1, §11); implement the fixed-size page layout (§8.2); implement the CRC-32C computation over header+payload (P7, ADR-03).

Deliverable

Working LogRecord encode/decode with CRC, and a Page layout struct, both usable by wal-writer (Phase 2) and wal-reader (Phase 5) without further format changes.

Acceptance

fixtures/update_commit_roundtrip.json passes: decode(encode(record)) == record for all three record types in the fixture (3/3 exact matches); a single-bit flip in any encoded record's payload is detected by the CRC check in 100% of 1,000 randomized trials (feeds Phase 5's crc_bitflip_detection.json).

Fixtures

fixtures/update_commit_roundtrip.json (encode/decode equality); a new fixtures/payload_length_boundary.json (max 8 KiB payload per §4, one-byte-over rejected at construction, per I13).

Pitfalls

Computing the CRC over the payload only, forgetting the header (silently weakens P7's guarantee — a corrupted lsn/txn_id field would go undetected). Using a variable-width integer encoding for payload_len "to save bytes," which breaks the fixed 32 B RecordHeader size assumption (§4) that later segment-offset arithmetic (Phase 4) depends on.

✅ Phase 2 — Append-Only Writer & Durability Barrier §14

Objectives

Implement wal-writer's single-writer append path (ADR-19) and the force() durability barrier (P1, ADR-04) using fdatasync with an fsync fallback; establish the crash model (bytes not yet forced do not survive a simulated or real crash).

Deliverable

Working DurableWriter with real force() semantics and single-writer enforcement, usable directly (pre-batching) by every later phase.

Acceptance

Crash-variant fixture passes: records appended-but-not-forced before a simulated crash are absent after a Phase 1 decode-based replay (0 of N−K survive); records forced before the crash are all present (K of K); fdatasync is confirmed to be the syscall invoked (not a silent no-op) via a test-only I/O-tracing hook.

Fixtures

Crash variant of fixtures/update_commit_roundtrip.json; a new fixtures/post_commit_write_rejected.json (I14: Update after Commit for the same TxnId is rejected, not silently applied).

Pitfalls

Calling force() implicitly inside append() (defeats the entire point of testing the pre-force crash window — P9's later group-commit batching becomes impossible if every append force-writes). Assuming fsync and fdatasync are interchangeable in timing cost — fdatasync skips metadata (e.g., mtime) not needed for data integrity and is measurably cheaper (ADR-04); conflating them defeats §28's latency targets.

✅ Phase 3 — Group Commit & Batching §15

Objectives

Implement the MPSC intake queue and time/size-bounded batching (P9, ADR-05, ADR-19) that turns N concurrent commits into one force() call per batch window.

Deliverable

Working group-commit path demonstrating amortized force() cost under concurrent load, without changing single-writer append semantics from Phase 2.

Acceptance

fixtures/group_commit_batching.json passes: force() call count ≤ 5 for 50 concurrent commits (§28 M9 target ratio); each caller's completion signal fires only after a force() covering its LSN (I2, 0 premature-signal violations in 1,000 trials).

Fixtures

fixtures/group_commit_batching.json; a new fixtures/batch_window_boundary.json (exactly-2ms and exactly-8MiB boundary conditions each independently trigger a flush).

Pitfalls

Signaling completion to all queued callers after a batch's force(), including ones whose record was enqueued after the batch closed (violates I2 — a caller could be told "durable" for a record not yet forced). Using a wall-clock sleep for the 2 ms window in a way that is not mockable/accelerable in tests (makes the fixture suite slow and defeats P14's determinism goal for recovery-adjacent testing).

✅ Phase 4 — Segment Files, Rotation & Naming §16

Objectives

Implement fixed-size (16 MiB, §4) segment file rotation (ADR-06), monotonic zero-padded decimal naming (ADR-07), and the LSN-to-(segment, offset) addressing function that makes P11's "one logical log" abstraction real.

Deliverable

Working segment rotation with continuous LSN addressing across file boundaries, transparent to every crate written before this phase.

Acceptance

fixtures/segment_rotation_boundary.json passes: LSN sequence has zero gaps across a rotation event (I1 holds across the boundary); segment files are named seg-000001.wal, seg-000002.wal, ... with no reused IDs across 100 simulated rotations; LSN-to-segment lookup returns the correct file for 100% of randomly sampled LSNs spanning 5 segments.

Fixtures

fixtures/segment_rotation_boundary.json; a new fixtures/lsn_segment_lookup_roundtrip.json (every LSN in a 5-segment log maps to exactly one (segment, offset) pair, and decoding at that offset yields a record whose header LSN matches).

Pitfalls

Rotating mid-record (splitting a single LogRecord's bytes across two segment files) — this project's fixed segment size (§4) is chosen specifically so this never happens by construction (a rotation check runs before, not during, an append); getting that check's boundary condition wrong reintroduces exactly this bug. Reusing a segment ID after a failed rotation attempt (must always increment, even on retry, to preserve P11's naming-boundary-not-logical-boundary guarantee).

✅ Phase 5 — Reader, CRC & Torn-Write Detection §17

Objectives

Implement wal-reader's sequential multi-segment scanner (§11 SegmentScanner); implement CRC validation and the truncate-at-first-bad-record policy (P7/P8, ADR-03, ADR-20).

Deliverable

Working SegmentScanner that reliably finds the true end of a possibly-torn log across an arbitrary number of segment files, usable by wal-recovery (Phase 7) without any recovery-specific logic of its own.

Acceptance

fixtures/torn_write_tail_truncation.json passes: scanner reports last_valid_lsn equal to the last record before the injected truncation in 100% of 200 randomized truncation-point trials; fixtures/crc_bitflip_detection.json passes: a single-bit flip anywhere in a record's header or payload is detected in 100% of 1,000 randomized trials (matches Phase 1's CRC guarantee, now exercised end-to-end through real files).

Fixtures

fixtures/torn_write_tail_truncation.json; fixtures/crc_bitflip_detection.json; a new fixtures/multi_segment_clean_traversal.json (5-segment log with no corruption scans end-to-end with zero false-positive truncations).

Pitfalls

Treating a clean end-of-segment (correct trailer, no more bytes) as a torn write — this would truncate a perfectly healthy multi-segment log at the first segment boundary, a severe correctness bug distinct from, but easily confused with, genuine torn-write handling. Attempting to "skip" a bad record's declared length and resume scanning after it (explicitly rejected by P8 — the declared length itself may be the corrupted field).

✅ Phase 6 — Checkpointing (Fuzzy Checkpoint, DPT/TT) §18

Objectives

Implement fuzzy checkpointing (ADR-08, P10): periodically snapshot the in-memory Dirty Page Table and Transaction Table into a CHECKPOINT_BEGIN/CHECKPOINT_END record pair, without flushing any dirty pages.

Deliverable

Working fuzzy checkpoint mechanism producing a CheckpointPayload that Phase 7's Analysis pass can consume as its scan-start hint, without ever pausing the writer for a flush-all.

Acceptance

fixtures/checkpoint_dpt_tt_snapshot.json passes: checkpoint completion adds ≤ 10 ms of writer-thread latency (no flush-all stall, per ADR-08) in 100 trials; snapshot DPT/TT entries match the live tables' state as of begin_checkpoint_lsn with zero mismatches (I10 holds).

Fixtures

fixtures/checkpoint_dpt_tt_snapshot.json; a new fixtures/checkpoint_interval_ trigger.json (both the 64 MiB and 60 s triggers independently fire a checkpoint).

Pitfalls

Snapshotting the DPT/TT after CHECKPOINT_BEGIN's LSN is assigned but reading values that have since advanced past it (violates I10 — the snapshot must be consistent as of the begin LSN, not as of whenever the copy loop happens to run). Blocking new Update/Commit records while the snapshot copy is in progress (defeats the entire "fuzzy" premise — ADR-08 was chosen specifically to avoid any such stall).

✅ Phase 7 — ARIES Recovery: Analysis Pass §19

Objectives

Implement the Analysis pass (§8.5): starting from the last completed checkpoint's begin_checkpoint_lsn, scan forward to the end of the log (using Phase 5's SegmentScanner) and rebuild the true Dirty Page Table and Transaction Table as of the crash point.

Deliverable

Working Analysis pass producing a DPT/TT consumed directly by Phase 8's Redo and Undo passes, correct whether or not a checkpoint exists.

Acceptance

fixtures/analysis_pass_differential.json passes: checkpoint-hinted Analysis and full-scan-from-zero Analysis produce byte-identical DPT/TT snapshots across 20 randomized workload/crash-point combinations (I5, 0 mismatches); Analysis completes within §4's recovery-throughput budget (≥150 MB/s of log scanned, feeding §28 M6).

Fixtures

fixtures/analysis_pass_differential.json; a new fixtures/analysis_no_checkpoint_ fallback.json (log with zero completed checkpoints still analyzes correctly from Lsn(0)).

Pitfalls

Using the checkpoint's embedded DPT rec_lsn values as final, without letting subsequent Update records in the scanned range lower them further — a page dirtied again after the checkpoint but before an even-earlier still-unwritten update would get the wrong (too-late) rec_lsn, corrupting Phase 8's redo start point. Forgetting that a CLR record (from a previous, still-incomplete undo before the crash) must also update the TT entry's undo_next_lsn during Analysis — treating CLRs as if they were ordinary Updates loses the undo-progress bookkeeping needed by §8.7's resume-from-crash-during-undo scenario.

✅ Phase 8 — ARIES Recovery: Redo & Undo Passes §20

Objectives

Implement the Redo pass (repeating history, P2) and the Undo pass (CLR-based rollback of losers, P3) using Phase 7's Analysis-pass output, completing the three-pass ARIES pipeline (Mohan et al. 1992, Lomet & Tuttle 1995).

Deliverable

Complete three-pass ARIES recovery pipeline (wal-recovery): Analysis (Phase 7) → Redo → Undo, restoring a crashed log to a consistent, fully-recovered state with all losers rolled back.

Acceptance

fixtures/redo_pass_idempotency.json passes: running Redo twice in a row on the same post-Analysis state produces zero additional page mutations the second time (I6, idempotent by construction); fixtures/crash_during_undo_recovery.json passes: across 50 randomized "crash again during undo" trials, no single Update is ever undone more than once (I8, 0 double-undo violations); full pipeline meets §4's RTO target (≤5 s per 1 GiB of unckpointed log, §28 M7).

Fixtures

fixtures/redo_pass_idempotency.json; fixtures/undo_pass_clr_chain.json; fixtures/crash_during_undo_recovery.json.

Pitfalls

Running Undo before Redo completes (violates P2 — undo logic assumes the page already reflects full physical history, including the loser's own updates, before rolling any of them back). Computing a CLR's undo_next_lsn from the original transaction's prev_lsn chain after some entries have already been undone in a prior, crashed attempt — must instead resume from the TT entry's current undo_next_lsn (as rebuilt by Analysis, §19.6), not restart the chain from the transaction's last_lsn.

✅ Phase 9 — Log Shipping, Retention & Performance Harness §21

Objectives

Implement wal-replicate's streaming log-shipping sender/receiver (ADR-17) and the retention gate (P12, I11) that blocks segment deletion until every attached replica has acknowledged past the relevant LSN; wire wal-bench to gate the full §28 M1– M12 target set in CI.

Deliverable

End-to-end pipeline: local durability (Phases 0–6) → recovery (Phases 7–8) → replication + retention (this phase), with wal-bench gating every release against §28's targets.

Acceptance

fixtures/replication_lag_retention_gate.json passes: retention blocks 100% of attempted deletions for segments still needed by a lagging consumer, across the §4 replica-lag budget (≤5 segments); fixtures/recovery_determinism_replay.json passes: 0 divergences across 100 replay runs (I12); wal-bench meets or exceeds every §28 M1–M12 target on the CI reference hardware profile.

Fixtures

fixtures/replication_lag_retention_gate.json; fixtures/recovery_determinism_replay.json.

Pitfalls

Shipping unforced (buffered-but-not-yet-force()-ed) records to a replica "to reduce lag" — this violates I2 for the replication path exactly as it would for a local commit ack, and can leave a replica believing it has data the primary itself would lose on its own crash. Gating retention only on checkpoint completion and forgetting the replica-ack half of the condition (ADR-16) — reintroduces the exact premature-deletion hazard P12 exists to prevent.
