3. Architectural Overview

   Transaction API (host engine, out of scope)
              |
              v  UPDATE/COMMIT/ABORT intents
     +--------+---------+
     |      wal-core     |   Lsn, TxnId, PageId, RecordHeader, RecordType, WalError
     +--------+---------+
              |
              v  append(record) -> Lsn
     +--------+---------+        group-commit queue (MPSC, ADR-19)
     |     wal-writer     |----------------------------------------+
     |  (single writer     |                                        |
     |   thread, P4)        |<--- batches --- force() barrier -----+
     +--------+---------+        (fsync/fdatasync, P9, ADR-04)
              |
              v  append to active segment, rotate at size limit
     +--------+---------+
     |   Segment Files    |  seg-000001.wal ... seg-NNNNNN.wal  (ADR-06/07)
     +--------+---------+
              |
   +----------+-----------+---------------------------+
   |                      |                           |
   v                      v                           v
+--+--------+     +-------+--------+          +-------+---------+
| wal-reader |     |  wal-recovery   |          |  wal-replicate    |
| CRC check, |---->| Analysis/Redo/  |          |  log-shipping to  |
| torn-write |     |  Undo, DPT/TT,  |          |  standby (P12)    |
| detection  |     |  Checkpoint     |          +-------------------+
+------------+     +-----------------+

Boxes: wal-core owns identifier types and the wire-format constants; it performs no I/O (§11). wal-writer is the only crate holding the append cursor — a single dedicated thread drains an MPSC intake queue, batches pending commit records (group commit, P9), and issues the one force() barrier per batch (P1, ADR-04/05). Segment files are the physical persistence boundary: bytes before the last forced offset survive a crash, bytes after do not (Phase 2 §14). wal-reader owns sequential scanning and CRC/length validation (P7, I4, I13); it never interprets RecordType payloads semantically (P13) — that is wal-recovery's job. wal-recovery owns the Dirty Page Table, Transaction Table, and the three-pass ARIES pipeline (§8, Phase 6–8); it is the trust boundary for "what the log means." wal-replicate is the only component with network I/O authority; it streams forced records to a standby and gates local segment retention on replica acknowledgment (P12, Phase 9 §21). Concurrency boundary: exactly one thread ever appends (ADR-19); readers/recovery/ replication read a strictly append-only, already-forced byte range (I9). Persistence boundary: force() is the line between "survives a crash" and "does not" (I2, I3).

8. Domain Model / Protocol / Data Model

8.1 Log Wire Grammar (EBNF)

LogFile        ::= Segment+
Segment        ::= SegmentHeader Record* SegmentTrailer?
SegmentHeader  ::= Magic Version SegmentId FirstLsn
Record         ::= RecordHeader Payload Crc32
RecordHeader   ::= Lsn PrevLsn TxnId RecordType PayloadLen
RecordType     ::= "BEGIN" | "UPDATE" | "COMMIT" | "ABORT"
                 | "CLR" | "CHECKPOINT_BEGIN" | "CHECKPOINT_END"
Payload        ::= UpdatePayload | ClrPayload | CheckpointPayload | Bytes
UpdatePayload  ::= PageId Offset BeforeLen AfterLen BeforeImage AfterImage
ClrPayload     ::= PageId UndoNextLsn Offset AfterLen AfterImage
CheckpointPayload ::= DptEntries TtEntries

8.2 Page Layout (Fixed-Size Slotted Page)

Field Size Purpose
page_id 8 B Physical page identity
page_lsn 8 B LSN of the last applied update — the redo-skip check (I6)
slot_count 2 B Number of occupied slots
free_space_ptr 2 B Offset to first free byte
slot_directory 4 B × slot_count Slot offset/length pairs
page_checksum 4 B CRC over the page, verified on read (independent of P7's record CRC)

8.3 Transaction and Page State Tables

Transaction State Event Next State Log Write
(none) begin() Active BEGIN
Active update() Active UPDATE
Active commit() Committed COMMIT
Active abort() Aborting none yet — undo begins
Aborting undo pass writes CLRs Aborting CLR × N
Aborting undo pass exhausts prevLSN chain Aborted none — terminal, implicit
Page State (recovery-relevant) Meaning
pageLSN < record.lsn Update not yet reflected — redo applies (I6)
pageLSN >= record.lsn Update already reflected — redo skips (I6)
Not present in Dirty Page Table Clean since last checkpoint, or never touched

8.4 Worked Example — Single Update-Commit Round

t0 transaction T7 begins: writer assigns lsn=100, logs BEGIN{T7}. t1 T7 updates page P3: writer assigns lsn=101, logs UPDATE{T7,P3,prevLsn=100}, page P3's in-memory pageLSN is set to 101 (not yet flushed, P5). t2 T7 commits: writer assigns lsn=102, logs COMMIT{T7,prevLsn=101}, batches this record into the current group-commit window (P9). t3 the batch's force() completes, covering LSNs 100–102; the commit is acknowledged to the caller only now (I2). Page P3's data bytes may be flushed to disk at any later time, or never before the next crash — either is safe because the log already durably describes how to redo it (P2/P5).

8.5 Worked Example — ARIES Recovery After a Mid-Transaction Crash

Log (post-crash) contains, in order: CHECKPOINT_BEGIN(lsn=200, dpt={}, tt={}), CHECKPOINT_END(lsn=201), BEGIN{T9}(lsn=210), UPDATE{T9,P5}(lsn=211), BEGIN{T10}(lsn=220), UPDATE{T10,P6}(lsn=221), COMMIT{T9}(lsn=230) — then the process crashes before T10 commits or aborts. Analysis (starts at lsn=200 per I5): scans forward, rebuilds Transaction Table (T9→Committed, T10→Active-at-crash, i.e. a loser) and Dirty Page Table (P5→recLSN 211, P6→recLSN 221). Redo: starts at min(recLSN)=211, reapplies lsn=211 to P5 and lsn=221 to P6 if their on-disk pageLSN is behind (I6, P2) — including T10's update, per "repeating history." Undo: T10 is a loser; its only update (lsn=221) is undone, writing CLR{undo of 221, UndoNextLsn=None}(lsn=240) — T10 is now Aborted. T9 needed no undo (already committed).

8.6 Malformed-Input Example

Reader encounters a record header claiming payload_len=4096 but only 900 bytes remain before the segment's declared end-of-written-data marker (a torn write mid record, mirroring a crash during wal-writer's in-progress append). Per P7/P8: the CRC check cannot even run (insufficient bytes to read the claimed payload), so the reader stops at the last fully-read, CRC-valid record's offset and reports that as the log's true end — the partial bytes are neither an error nor repaired, they are simply outside the recovered log (I4/I13).

8.7 Failure-Path Example — Crash During Undo

Undo pass is midway through rolling back loser T10 (§8.5): it has written CLR(lsn=240) for T10's update at lsn=221, but the process crashes before writing T10's implicit "fully aborted" bookkeeping. On restart, Analysis re-scans from the last checkpoint and finds T10 in the Transaction Table with UndoNextLsn already advanced past lsn=221 (because the CLR at lsn=240 is itself in the log). Undo resumes from UndoNextLsn, which — since T10 had only one update — is now None; no further undo work happens, and T10 is Aborted. The CLR already applied is never re-applied (I8) — this is P3's idempotency guarantee exercised for real.
