69 — Write-Ahead Log (WAL) from Scratch

Project Number: 69

Project Name: Write-Ahead Log (WAL) from Scratch

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from first principles, a durable write-ahead log substrate for a transactional storage engine: a physiological record/page format with monotonic Log Sequence Numbers (LSNs), a single-writer append path with group commit and an fsync/fdatasync durability barrier, CRC-guarded records with torn-write detection, rotating segment files with a retention/truncation policy, ARIES-style fuzzy checkpointing, and a full three-pass ARIES recovery pipeline (Analysis, Redo, Undo) with Compensation Log Records (CLRs), plus a log-shipping path for streaming a replica. The deliverable is a six-crate Rust workspace reproducing, at teaching scale, the mechanism shared by PostgreSQL's xlog, SQLite's wal.c, RocksDB's log writer/reader, and etcd's raft wal package: an append-only, crash-recoverable record stream that is the single source of truth data pages are rebuilt from.

Phase-0 Deliverable (crates)

  1. wal-core — Lsn/TxnId/PageId identifiers, RecordHeader, RecordType, WalError, wire-format constants.
  2. wal-writer — single-writer append path, group-commit batching, segment rotation, force() durability barrier.
  3. wal-reader — sequential segment scan, CRC validation, torn-write tail detection.
  4. wal-recovery — ARIES Analysis/Redo/Undo passes, Dirty Page Table, Transaction Table, checkpoint record encode/decode.
  5. wal-replicate — log-shipping sender/receiver skeleton, retention-gate hook.
  6. wal-bench — performance harness driving the §28 M1–M12 targets.

Non-Goals

Not a production storage engine; not a query processor; no buffer-pool eviction policy beyond the minimum needed to exercise steal/no-force (P5); no B-tree or hash-index structural logging beyond a generic UPDATE record; no Byzantine fault tolerance — only crash-stop failures (I3, ADR-06 analog absent here since this project has no distributed consensus in scope).

Deployment Model

Statically linked Rust library (wal-core/wal-writer/wal-reader/wal-recovery) embedded in a host storage engine process; wal-replicate runs as an optional secondary thread pushing/pulling records over a plain TCP stream to a standby process running the same crates. No daemon, no external dependency beyond the local filesystem.

Target Users

Storage-engine and database-internals engineers studying durability mechanics: WAL protocol enforcement, group-commit throughput tradeoffs, checkpoint design, and ARIES recovery; implementers deciding whether to hand-roll a WAL or embed an existing one.

Language + Rationale

Rust (stable channel). Rationale: #[repr(C)] structs give byte-exact control over the wire format (§8/§11) without a foreign build toolchain; ownership makes the single-writer discipline (ADR-19) a compile-time property, not a runtime lock convention; no GC pauses to distort force() latency measurements (§28). Rejected: C (manual serialization bugs are exactly the CRC/length mismatches §7 I4/I13 exist to catch — Rust's type system prevents the common subset at compile time); Go (GC pauses confound the p99 durability-latency targets in §4); Java (same GC concern, plus no direct control over fsync/fdatasync selection without JNI).

Prerequisites

Buffer management and the steal/no-steal, force/no-force taxonomy; two-phase locking or an equivalent concurrency-control scheme (assumed, not built here); binary serialization and checksums; POSIX file I/O durability semantics (fsync vs fdatasync); basic ARIES vocabulary (LSN, CLR, DPT, TT) — even if only from a textbook skim before starting.

2. Why Build This

The WAL is the single mechanism every ACID storage engine leans on to reconcile two conflicting demands: commit latency must be low (one force(), not a full page flush) and crash recovery must be exact (no committed write lost, no uncommitted write kept). ARIES (Mohan, Haderle, Lindsay, Pirahesh & Schwarz, 1992, ACM TODS) is the paper that made "steal, no-force" buffer management provably safe via physiological logging, LSNs, and Compensation Log Records — and it is the design PostgreSQL's xlog, most of MySQL/InnoDB's redo log, and every teaching database textbook's recovery chapter descend from. Building a WAL from scratch converts "the log is the source of truth" from a slogan into a reproduced fact: you watch a crash mid-checkpoint, mid-redo, and mid-undo each resolve correctly because the log format and the recovery passes were built to make that true.

Cross-links: PostgreSQL's xlog.c/xlogrecovery.c (§31) is ARIES-derived physical WAL with a fuzzy checkpoint; SQLite's wal.c (§31) inverts the usual segment-rotation model into a single growing file reset by checkpoint; RocksDB's log_writer.cc (§31) is a WAL for a log-structured-merge engine, not a page store — comparing its record framing to this project's physiological records is a direct lesson in "logical vs physical" logging tradeoffs (P6); etcd's wal package (§31) shows the same append-CRC-segment-rotate skeleton reused for a Raft log instead of a data-page log. Calibration value: an engineer who has built this project can read any of those four codebases' recovery path and recognize every structure by name.

What Mastery Looks Like

  • Can explain, from the record format alone (§8, §11), why a page write happening before its log record is forced would make crash recovery unsound (P1, I3, Phase 2 §14).
  • Can trace a single UPDATE→COMMIT round through group commit and name the exact force() call that makes the commit durable (Phase 3 §15).
  • Can explain why ARIES redoes updates for transactions that will later be undone ("repeating history") rather than skipping them (P2, Phase 8 §20).
  • Can explain why undo actions are themselves logged as CLRs with an UndoNextLSN, and what specific crash scenario breaks without that pointer (P3, I8, Phase 8 §20).
  • Can read a fuzzy checkpoint's embedded Dirty Page Table and Transaction Table and state exactly where the Analysis pass must start scanning (Phase 6 §18, Phase 7 §19).
  • Can point to the exact CRC field that turns an interrupted write from silent corruption into a detected, truncatable tail (P7, P8, Phase 5 §17).
  • Can run the recovery fixture suite and predict, before looking, which injected crash point produces a redo-only recovery vs. one requiring undo (Phase 9 §21, §26).

Boxes: wal-core owns identifier types and the wire-format constants; it performs no I/O (§11). wal-writer is the only crate holding the append cursor — a single dedicated thread drains an MPSC intake queue, batches pending commit records (group commit, P9), and issues the one force() barrier per batch (P1, ADR-04/05). Segment files are the physical persistence boundary: bytes before the last forced offset survive a crash, bytes after do not (Phase 2 §14). wal-reader owns sequential scanning and CRC/length validation (P7, I4, I13); it never interprets RecordType payloads semantically (P13) — that is wal-recovery's job. wal-recovery owns the Dirty Page Table, Transaction Table, and the three-pass ARIES pipeline (§8, Phase 6–8); it is the trust boundary for "what the log means." wal-replicate is the only component with network I/O authority; it streams forced records to a standby and gates local segment retention on replica acknowledgment (P12, Phase 9 §21). Concurrency boundary: exactly one thread ever appends (ADR-19); readers/recovery/ replication read a strictly append-only, already-forced byte range (I9). Persistence boundary: force() is the line between "survives a crash" and "does not" (I2, I3).

6. Design Principles

  • P1 — Log Precedes Data (the WAL Rule). Rule: the log record for a page modification is forced to durable storage before that page's modified bytes are written to durable storage (Härder & Reuter 1983). Tradeoff: an extra force() call gates every flush-worthy commit boundary. Operational implication: the buffer manager's flush path must query the writer's last-forced LSN before evicting a dirty page. Violation consequence: a flushed page could reflect an update whose log record never survives a crash — recovery cannot redo what it never sees, and the page is now permanently inconsistent (breaks I3).
  • P2 — Repeating History (Redo Everything Since the Checkpoint). Rule: the redo pass reapplies every logged update whose LSN is not yet reflected in the target page, regardless of whether the owning transaction will later be undone (Mohan et al. 1992). Tradeoff: redoes work for "loser" transactions that undo removes moments later. Operational implication: redo must run to completion before undo starts. Violation consequence: skipping redo for a presumed-losing transaction leaves pages in a state inconsistent with the log's physical history, and undo's CLRs (which assume a fully-redone starting state) become incorrect (breaks I6).
  • P3 — Idempotent Undo via Compensation Log Records. Rule: every undo action is itself written as a CLR carrying an UndoNextLSN pointing to the next record to undo, so a crash during rollback never re-executes an already-undone action. Tradeoff: rollback of a long transaction generates as much log volume as its forward path. Operational implication: undo never "just re-runs the inverse operation" — it logs the inverse, then applies it. Violation consequence: repeated crash during rollback could re-undo the same update indefinitely — a livelock, not merely a bug (breaks I8).
  • P4 — Monotonic LSN Assignment. Rule: LSNs are assigned in strictly increasing order matching physical append order; no record is ever assigned an LSN out of sequence. Tradeoff: LSN assignment must funnel through one serialization point (ADR-19). Operational implication: any concurrent-writer design must still present a single logical assignment point to the log. Violation consequence: redo/undo direction assumptions (both rely on LSN order) collapse, and recovery becomes undefined (breaks I1).
  • P5 — No-Force at Commit, Compensated by Redo Capability. Rule: a transaction's commit record's own bytes must be forced before commit is acknowledged; its dirty data pages need not be flushed at commit time. Tradeoff: recovery must be able to redo committed-but-unflushed pages from the log (P2). Operational implication: the buffer manager may defer data-page writes indefinitely past commit. Violation consequence: without P2's redo guarantee, no-force is simply data loss on crash — the two principles are a matched pair, not independent choices.
  • P6 — Physiological Logging. Rule: log records name the target page physically (a PageId) but describe the operation logically (e.g., "insert at slot S") rather than storing full before/after page images (Mohan et al. 1992). Tradeoff: redo/undo logic must understand each operation type, not blindly copy bytes. Operational implication: adding a new operation type means adding a new redo/undo handler, not just a new payload shape. Violation consequence: full-page-image logging for every small update blows the §4 payload-size ceiling and multiplies I/O for no benefit.
  • P7 — Checksums Bound Corruption to One Record. Rule: every record carries a CRC over its own header+payload; a corruption check never needs to inspect neighboring records to decide validity. Tradeoff: extra bytes and compute per record. Violation consequence: without a per-record boundary, a torn write mid-record could be parsed as a differently-shaped but internally-consistent record, corrupting recovery silently instead of being caught (breaks I4).
  • P8 — Truncate, Never Repair, a Torn Tail. Rule: on detecting a corrupt or incomplete record during a recovery scan, treat everything from that byte offset onward as never-written and stop scanning — never attempt to reconstruct or skip past it. Tradeoff: a record that was actually fine but tripped a false-positive CRC check is lost along with everything after it. Violation consequence: any "smart" attempt to skip a bad record and resume scanning risks reading a wrong LSN/length field and silently misinterpreting the rest of the log.
  • P9 — Group Commit Amortizes the force() Cost. Rule: commit records from concurrently-committing transactions are batched into a single force() call bounded by a time/size window (§4). Tradeoff: the fastest committer in a batch waits up to the batching window's duration. Operational implication: commit latency has a floor equal to the batching window under load, not equal to raw force() latency. Violation consequence: one force() per transaction serializes all commits behind disk force latency, capping throughput at 1 / force_latency (see §28 M1 vs. M9).
  • P10 — Checkpoints Bound, Never Eliminate, Recovery Time. Rule: a checkpoint records enough state (Dirty Page Table, Transaction Table, begin_checkpoint LSN) to start the Analysis pass there instead of at the log's start; it never itself performs a flush-all of dirty pages (fuzzy checkpoint, ADR-08). Tradeoff: recovery still scans from the checkpoint forward, never instantly. Violation consequence: a sharp (flush-all) checkpoint reintroduces the I/O stall this design specifically avoids, and under load can itself miss its interval target (§4).
  • P11 — Segment Rotation Is a Naming Boundary, Not a Logical One. Rule: an LSN's meaning (byte offset, ordering) is independent of which segment file currently holds it; the segment sequence is treated as one logical, unbounded append log. Tradeoff: requires an LSN-to-(segment, offset) addressing function everywhere. Violation consequence: recovery or replication logic that assumes "one physical file is the whole log" breaks the first time the log outgrows one segment.
  • P12 — Retention Waits for the Slowest Consumer. Rule: a segment is eligible for deletion/reuse only once it is both covered by a completed checkpoint and acknowledged by every attached log-shipping consumer. Tradeoff: disk usage grows with the slowest replica's lag (§4's replica-lag budget). Violation consequence: premature deletion strands a lagging replica permanently — it can no longer catch up by streaming and needs an out-of-band base backup (FM-9).
  • P13 — Separation of Log-Writing from Log-Interpretation. Rule: wal-writer and wal-reader understand only the record wire format (§8/§11); no crate outside wal-recovery interprets RecordType payloads semantically. Tradeoff: an extra indirection layer between "append/read bytes" and "understand bytes." Violation consequence: recovery logic scattered across crates becomes untestable in isolation and breaks the terminology lock this document enforces (§10).
  • P14 — Deterministic Recovery Is a Pure Function of the Log. Rule: given the same on-disk log bytes and the same checkpoint, ARIES recovery must produce the same final page states and the same set of aborted "loser" transactions on every run. Tradeoff: no recovery-time heuristics may depend on wall-clock time or any state outside the log itself. Violation consequence: non-deterministic recovery cannot be fixture-replayed (§26) and every safety claim in §7 becomes unfalsifiable.

8.4 Worked Example — Single Update-Commit Round

t0 transaction T7 begins: writer assigns lsn=100, logs BEGIN{T7}. t1 T7 updates page P3: writer assigns lsn=101, logs UPDATE{T7,P3,prevLsn=100}, page P3's in-memory pageLSN is set to 101 (not yet flushed, P5). t2 T7 commits: writer assigns lsn=102, logs COMMIT{T7,prevLsn=101}, batches this record into the current group-commit window (P9). t3 the batch's force() completes, covering LSNs 100–102; the commit is acknowledged to the caller only now (I2). Page P3's data bytes may be flushed to disk at any later time, or never before the next crash — either is safe because the log already durably describes how to redo it (P2/P5).

8.5 Worked Example — ARIES Recovery After a Mid-Transaction Crash

Log (post-crash) contains, in order: CHECKPOINT_BEGIN(lsn=200, dpt={}, tt={}), CHECKPOINT_END(lsn=201), BEGIN{T9}(lsn=210), UPDATE{T9,P5}(lsn=211), BEGIN{T10}(lsn=220), UPDATE{T10,P6}(lsn=221), COMMIT{T9}(lsn=230) — then the process crashes before T10 commits or aborts. Analysis (starts at lsn=200 per I5): scans forward, rebuilds Transaction Table (T9→Committed, T10→Active-at-crash, i.e. a loser) and Dirty Page Table (P5→recLSN 211, P6→recLSN 221). Redo: starts at min(recLSN)=211, reapplies lsn=211 to P5 and lsn=221 to P6 if their on-disk pageLSN is behind (I6, P2) — including T10's update, per "repeating history." Undo: T10 is a loser; its only update (lsn=221) is undone, writing CLR{undo of 221, UndoNextLsn=None}(lsn=240) — T10 is now Aborted. T9 needed no undo (already committed).

8.6 Malformed-Input Example

Reader encounters a record header claiming payload_len=4096 but only 900 bytes remain before the segment's declared end-of-written-data marker (a torn write mid record, mirroring a crash during wal-writer's in-progress append). Per P7/P8: the CRC check cannot even run (insufficient bytes to read the claimed payload), so the reader stops at the last fully-read, CRC-valid record's offset and reports that as the log's true end — the partial bytes are neither an error nor repaired, they are simply outside the recovered log (I4/I13).

8.7 Failure-Path Example — Crash During Undo

Undo pass is midway through rolling back loser T10 (§8.5): it has written CLR(lsn=240) for T10's update at lsn=221, but the process crashes before writing T10's implicit "fully aborted" bookkeeping. On restart, Analysis re-scans from the last checkpoint and finds T10 in the Transaction Table with UndoNextLsn already advanced past lsn=221 (because the CLR at lsn=240 is itself in the log). Undo resumes from UndoNextLsn, which — since T10 had only one update — is now None; no further undo work happens, and T10 is Aborted. The CLR already applied is never re-applied (I8) — this is P3's idempotency guarantee exercised for real.

11. Core Schema & Types

struct Lsn(u64);                       // Copy, Eq, Ord — strictly monotonic (I1)
struct TxnId(u64);                     // Copy, Eq, Hash
struct PageId(u64);                    // Copy, Eq, Hash

struct RecordHeader {                  // 32 B fixed (§4)
    lsn: Lsn,
    prev_lsn: Lsn,                     // per-transaction backward chain (§8.5)
    txn_id: TxnId,
    record_type: RecordType,
    payload_len: u32,                  // must equal serialized payload bytes (I13)
}

enum RecordType {
    Begin,
    Update { page_id: PageId },
    Commit,
    Abort,
    Clr { undo_next_lsn: Option<Lsn> }, // I8: strictly backward or None
    CheckpointBegin,
    CheckpointEnd,
}

struct LogRecord {                     // ADR-12 physiological layout
    header: RecordHeader,
    payload: Vec<u8>,                  // opaque to wal-writer/wal-reader (P13)
    crc32: u32,                        // over header+payload (P7)
}
struct DirtyPageTableEntry { page_id: PageId, rec_lsn: Lsn }   // §8.3
struct TransactionTableEntry {
    txn_id: TxnId,
    status: TxnStatus,                 // Active | Committed | Aborting
    last_lsn: Lsn,
    undo_next_lsn: Option<Lsn>,        // I8
}
enum TxnStatus { Active, Committed, Aborting }

struct CheckpointPayload {             // ADR-08 fuzzy checkpoint
    begin_checkpoint_lsn: Lsn,         // I10
    dirty_page_table: Vec<DirtyPageTableEntry>,
    transaction_table: Vec<TransactionTableEntry>,
}

enum WalError {
    CrcMismatch { at_lsn: Lsn },
    LengthMismatch { at_lsn: Lsn, declared: u32, actual: u32 },
    LsnOutOfOrder { expected_min: Lsn, got: Lsn },
    PostCommitWrite { txn_id: TxnId },
    ForceFailed,
    SegmentNotFound { segment_id: u64 },
}
trait DurableWriter {                  // owned exclusively by wal-writer (ADR-19)
    fn append(&mut self, r: LogRecord) -> Lsn;
    fn force(&mut self) -> Result<Lsn, WalError>;   // durability barrier (P1/ADR-04)
}

trait SegmentScanner {                 // owned by wal-reader (P13)
    fn next_record(&mut self) -> Result<Option<LogRecord>, WalError>;
    fn last_valid_lsn(&self) -> Lsn;   // torn-write tail boundary (P8)
}

trait RetentionGate {                  // owned by wal-replicate (P12)
    fn min_required_lsn(&self) -> Lsn; // slowest consumer's watermark
    fn segment_eligible_for_deletion(&self, segment_id: u64) -> bool;
}

Ownership: DurableWriter is instantiated exactly once per process, behind the single writer thread (ADR-19, I1). Concurrency: SegmentScanner/wal-recovery read only bytes already covered by a force() call (I2); no reader ever races the writer's in-flight append. Serialization: LogRecord uses a stable, versioned tag-based encoding (ADR-03/ADR-22); wire format is not yet SemVer-stable pre-1.0 (§25).

15. Phase 3 — Group Commit & Batching

15.1 Objectives

Implement the MPSC intake queue and time/size-bounded batching (P9, ADR-05, ADR-19) that turns N concurrent commits into one force() call per batch window.

15.2 Detailed Implementation Steps

  1. Implement an MPSC channel feeding the single writer thread (ADR-19) — callers' append/commit calls enqueue and block on a per-call completion signal.
  2. Implement the batching loop: drain the queue until either the 2 ms window (§4) elapses or 8 MiB of buffered bytes accumulates (ADR-05), whichever first.
  3. Call force() (Phase 2) exactly once per batch; on success, signal completion to every caller whose record's LSN is ≤ the batch's max forced LSN (I2).
  4. Ensure LSN assignment (P4) still happens per-append, not per-batch — batching affects when force() runs, never how LSNs are ordered.
  5. Write fixtures/group_commit_batching.json: N=50 concurrent committers, assert a single-digit force() call count (≪ 50) and 50/50 correct completion signals.

15.3 Deliverable

Working group-commit path demonstrating amortized force() cost under concurrent load, without changing single-writer append semantics from Phase 2.

15.4 Acceptance Criteria

fixtures/group_commit_batching.json passes: force() call count ≤ 5 for 50 concurrent commits (§28 M9 target ratio); each caller's completion signal fires only after a force() covering its LSN (I2, 0 premature-signal violations in 1,000 trials).

15.5 Conformance Fixtures

fixtures/group_commit_batching.json; a new fixtures/batch_window_boundary.json (exactly-2ms and exactly-8MiB boundary conditions each independently trigger a flush).

15.6 Pitfalls

Signaling completion to all queued callers after a batch's force(), including ones whose record was enqueued after the batch closed (violates I2 — a caller could be told "durable" for a record not yet forced). Using a wall-clock sleep for the 2 ms window in a way that is not mockable/accelerable in tests (makes the fixture suite slow and defeats P14's determinism goal for recovery-adjacent testing).

15.7 Performance Concerns

This phase is the direct implementation of §4's group-commit-window constraint and the primary driver of the p50/p99 commit-latency targets (§28 M1/M2) — the batching window is the single largest latency-vs-throughput knob in the whole system (§29).

15.8 Edge Cases

A single very large record (near the 8 KiB payload ceiling, §4) arriving alone must still flush promptly (size-bound trigger) rather than waiting the full 2 ms for company. A batch that fills to exactly 8 MiB from many tiny records must close on the size bound even if the 2 ms window has not elapsed.

15.9 Failure Analysis

A force() failure (WalError::ForceFailed, Phase 2) during a batch must fail every caller in that batch, not just the one that "caused" it — there is no way to partially force a batch; this is enforced as a batch-wide result, never a per-caller one.

15.10 Operational Notes

Expose batch_size_bytes and batch_fill_reason ({time_bound, size_bound}) as histograms from this phase onward — operators use the ratio of size_bound to time_bound fills to judge whether the batching window is well-tuned for current load (§24 dashboards).

16. Phase 4 — Segment Files, Rotation & Naming

16.1 Objectives

Implement fixed-size (16 MiB, §4) segment file rotation (ADR-06), monotonic zero-padded decimal naming (ADR-07), and the LSN-to-(segment, offset) addressing function that makes P11's "one logical log" abstraction real.

16.2 Detailed Implementation Steps

  1. Implement SegmentHeader encode/decode (§8.1): magic bytes, format version, segment_id, first_lsn.
  2. Implement rotation: when the active segment would exceed 16 MiB on the next append, close it (write trailer), open seg-{id+1:06}.wal (ADR-07), continue appending without any gap in LSN sequence (P4/P11).
  3. Implement the LSN-to-(segment, offset) lookup: given an Lsn, compute which segment file holds it and the byte offset within that file — needed by both wal-reader (Phase 5) and wal-replicate (Phase 9).
  4. Ensure rotation itself never blocks an in-flight force() — the trailer write for the old segment and the header write for the new segment are ordered, but neither delays a caller's completion signal beyond the batching window (P9).
  5. Write fixtures/segment_rotation_boundary.json: append records until rotation triggers mid-batch, assert LSN continuity across the segment boundary and correct file naming.

16.3 Deliverable

Working segment rotation with continuous LSN addressing across file boundaries, transparent to every crate written before this phase.

16.4 Acceptance Criteria

fixtures/segment_rotation_boundary.json passes: LSN sequence has zero gaps across a rotation event (I1 holds across the boundary); segment files are named seg-000001.wal, seg-000002.wal, ... with no reused IDs across 100 simulated rotations; LSN-to-segment lookup returns the correct file for 100% of randomly sampled LSNs spanning 5 segments.

16.5 Conformance Fixtures

fixtures/segment_rotation_boundary.json; a new fixtures/lsn_segment_lookup_roundtrip.json (every LSN in a 5-segment log maps to exactly one (segment, offset) pair, and decoding at that offset yields a record whose header LSN matches).

16.6 Pitfalls

Rotating mid-record (splitting a single LogRecord's bytes across two segment files) — this project's fixed segment size (§4) is chosen specifically so this never happens by construction (a rotation check runs before, not during, an append); getting that check's boundary condition wrong reintroduces exactly this bug. Reusing a segment ID after a failed rotation attempt (must always increment, even on retry, to preserve P11's naming-boundary-not-logical-boundary guarantee).

16.7 Performance Concerns

Segment rotation (trailer + new header write) adds a small, bounded, infrequent latency spike (once per 16 MiB written, §4) — tracked separately from the steady-state per-batch force() cost in §28's M9 so rotation events don't get averaged away in p50/p99 reporting.

16.8 Edge Cases

A rotation triggered by the very last record of a batch must still complete the current batch's force() against the old segment before any record is appended to the new one — otherwise a crash between rotation and force could lose records the caller believes are durable. An empty segment (rotated into but crashed before any append) must be recognized by recovery as contributing zero records, not as corrupt.

16.9 Failure Analysis

A crash during segment rotation, after the old segment's trailer is written but before the new segment's header is written, is resolved at recovery time by treating "segment file physically absent" identically to "segment file present but zero valid records" (§8.6's torn-write handling, generalized to whole-file granularity) — no special-cased rotation-crash logic is needed because P8's truncate-tail rule already covers it.

16.10 Operational Notes

Expose active_segment_id and segments_on_disk as gauges from this phase onward — the primary signal feeding §24's disk-usage dashboard and the retention logic introduced in Phase 9 (§21).

17. Phase 5 — Reader, CRC & Torn-Write Detection

17.1 Objectives

Implement wal-reader's sequential multi-segment scanner (§11 SegmentScanner); implement CRC validation and the truncate-at-first-bad-record policy (P7/P8, ADR-03, ADR-20).

17.2 Detailed Implementation Steps

  1. Implement SegmentScanner::next_record: reads a RecordHeader, validates payload_len bounds before reading the payload (defends against the malformed length seen in §8.6), then validates the CRC (P7).
  2. On any validation failure — insufficient bytes, length mismatch (I13), or CRC mismatch (I4) — implement the truncate-tail policy (P8/ADR-20): stop scanning, record last_valid_lsn as the prior record's LSN.
  3. Implement multi-segment traversal: when one segment's declared end is reached cleanly (trailer present, no partial record), advance to the next segment file in ID order (P11) — this is not a "torn write," it is a normal boundary.
  4. Distinguish, in the returned status, "clean segment boundary, continue" from "torn tail, stop entirely" — the two must never be confused (a torn write in segment 3 must not be masked by segment 4 existing).
  5. Write fixtures/torn_write_tail_truncation.json and fixtures/crc_bitflip_detection.json: inject a truncated record and a bit-flipped record respectively; assert the scanner stops at the correct last_valid_lsn in both cases.

17.3 Deliverable

Working SegmentScanner that reliably finds the true end of a possibly-torn log across an arbitrary number of segment files, usable by wal-recovery (Phase 7) without any recovery-specific logic of its own.

17.4 Acceptance Criteria

fixtures/torn_write_tail_truncation.json passes: scanner reports last_valid_lsn equal to the last record before the injected truncation in 100% of 200 randomized truncation-point trials; fixtures/crc_bitflip_detection.json passes: a single-bit flip anywhere in a record's header or payload is detected in 100% of 1,000 randomized trials (matches Phase 1's CRC guarantee, now exercised end-to-end through real files).

17.5 Conformance Fixtures

fixtures/torn_write_tail_truncation.json; fixtures/crc_bitflip_detection.json; a new fixtures/multi_segment_clean_traversal.json (5-segment log with no corruption scans end-to-end with zero false-positive truncations).

17.6 Pitfalls

Treating a clean end-of-segment (correct trailer, no more bytes) as a torn write — this would truncate a perfectly healthy multi-segment log at the first segment boundary, a severe correctness bug distinct from, but easily confused with, genuine torn-write handling. Attempting to "skip" a bad record's declared length and resume scanning after it (explicitly rejected by P8 — the declared length itself may be the corrupted field).

17.7 Performance Concerns

Sequential scan throughput must meet §4's 150 MB/s recovery-scan target (§28 M6); CRC computation (Phase 1) is the dominant per-record cost here, identical in nature to the writer-side cost measured in Phase 1 but now on the critical path of recovery time rather than commit time.

17.8 Edge Cases

A log containing exactly zero records (fresh, never-written) must scan to last_valid_lsn = Lsn(0) (or an explicit "empty" sentinel) without error. A segment file that is fully present but entirely zero-filled (e.g., pre-allocated but never written) must be detected as "zero valid records here," not as a CRC failure on garbage — a zero-length read before any header bytes exist is distinguishable from a corrupt header.

17.9 Failure Analysis

A CRC mismatch on the first record of a segment (as opposed to mid-segment) is handled identically to any other position — P8 makes no special case for segment-boundary-adjacent corruption, which is precisely what keeps this phase's logic simple and matches ADR-20's stated policy.

17.10 Operational Notes

Expose last_valid_lsn and torn_write_detected_total from every scan invocation — operators watch torn_write_detected_total as an early signal of a misbehaving storage device (FM-3), distinct from an expected clean shutdown's absence of any torn tail.

18. Phase 6 — Checkpointing (Fuzzy Checkpoint, DPT/TT)

18.1 Objectives

Implement fuzzy checkpointing (ADR-08, P10): periodically snapshot the in-memory Dirty Page Table and Transaction Table into a CHECKPOINT_BEGIN/CHECKPOINT_END record pair, without flushing any dirty pages.

18.2 Detailed Implementation Steps

  1. Implement in-memory DirtyPageTable/TransactionTable (§11) maintained incrementally as the writer processes Update/Begin/Commit/Abort records (feeds Phase 7's Analysis pass with a live structure to snapshot, not just a recovery-time-only concept).
  2. Implement checkpoint triggering per §4 (every 64 MiB written or 60 s, whichever first) — a background timer/counter, not blocking the writer thread (P9's batching discipline still applies to the checkpoint records themselves).
  3. Implement CHECKPOINT_BEGIN: log the current begin_checkpoint_lsn before copying the DPT/TT snapshot (I10 — snapshot LSNs must be ≥ this value).
  4. Implement CHECKPOINT_END: log the completed CheckpointPayload (§11) once the snapshot copy is done — the pair brackets a period during which the DPT/TT may still be changing (hence "fuzzy," per Mohan et al. 1992).
  5. Write fixtures/checkpoint_dpt_tt_snapshot.json: run a mixed workload, trigger a checkpoint, assert the snapshot's DPT/TT matches the writer's live state at begin_checkpoint_lsn (not at CHECKPOINT_END's later LSN).

18.3 Deliverable

Working fuzzy checkpoint mechanism producing a CheckpointPayload that Phase 7's Analysis pass can consume as its scan-start hint, without ever pausing the writer for a flush-all.

18.4 Acceptance Criteria

fixtures/checkpoint_dpt_tt_snapshot.json passes: checkpoint completion adds ≤ 10 ms of writer-thread latency (no flush-all stall, per ADR-08) in 100 trials; snapshot DPT/TT entries match the live tables' state as of begin_checkpoint_lsn with zero mismatches (I10 holds).

18.5 Conformance Fixtures

fixtures/checkpoint_dpt_tt_snapshot.json; a new fixtures/checkpoint_interval_ trigger.json (both the 64 MiB and 60 s triggers independently fire a checkpoint).

18.6 Pitfalls

Snapshotting the DPT/TT after CHECKPOINT_BEGIN's LSN is assigned but reading values that have since advanced past it (violates I10 — the snapshot must be consistent as of the begin LSN, not as of whenever the copy loop happens to run). Blocking new Update/Commit records while the snapshot copy is in progress (defeats the entire "fuzzy" premise — ADR-08 was chosen specifically to avoid any such stall).

18.7 Performance Concerns

Checkpoint frequency is a direct tradeoff against Phase 7's Analysis-pass scan length (§29): more frequent checkpoints shrink recovery time (§4's RTO target, §28 M7) at the cost of steady-state writer overhead measured here as checkpoint latency.

18.8 Edge Cases

A checkpoint triggered while the Transaction Table is empty (no active transactions) must still produce a valid, if trivially small, CheckpointPayload — an empty DPT/TT is not an error. Two checkpoint triggers firing back-to-back (interval elapsed exactly when the byte-count threshold also elapsed) must not produce two overlapping CHECKPOINT_BEGIN/CHECKPOINT_END pairs — only one checkpoint runs at a time.

18.9 Failure Analysis

A crash between CHECKPOINT_BEGIN and CHECKPOINT_END (the snapshot copy never completes) is handled by Phase 7's Analysis pass simply ignoring the incomplete pair and falling back to the previous completed checkpoint (or LSN 0 if none exists) — no special-cased "half checkpoint" recovery logic is needed.

18.10 Operational Notes

Expose checkpoint_count, checkpoint_latency_seconds, and log_bytes_since_ checkpoint from this phase onward — the last of these is the primary signal operators watch to confirm checkpoints are actually bounding recovery time as intended (§24, §29).

19. Phase 7 — ARIES Recovery: Analysis Pass

19.1 Objectives

Implement the Analysis pass (§8.5): starting from the last completed checkpoint's begin_checkpoint_lsn, scan forward to the end of the log (using Phase 5's SegmentScanner) and rebuild the true Dirty Page Table and Transaction Table as of the crash point.

19.2 Detailed Implementation Steps

  1. Locate the last completed CHECKPOINT_BEGIN/CHECKPOINT_END pair (Phase 6); initialize working DPT/TT from its CheckpointPayload — falls back to empty tables starting at Lsn(0) if none exists (mirrors §18.9).
  2. Scan forward via SegmentScanner::next_record (Phase 5) from begin_checkpoint_lsn: for each Begin, add a TT entry; for each Update, add/ refresh a DPT entry (rec_lsn = first LSN that dirtied the page since checkpoint) and refresh the TT entry's last_lsn; for each Commit, mark TT entry Committed; for each Abort, mark TT entry Aborting.
  3. Stop scanning at SegmentScanner's last_valid_lsn (Phase 5's torn-write boundary) — Analysis never scans past what the reader considers the log's true end (P8, applied here).
  4. At scan end, every TT entry still Active is a loser needing full undo; every TT entry Aborting is a loser needing undo resumed from its undo_next_lsn.
  5. Write fixtures/analysis_pass_differential.json: run Analysis with a checkpoint hint vs. a full scan from Lsn(0) on the same log; assert the resulting DPT/TT are identical (I5).

19.3 Deliverable

Working Analysis pass producing a DPT/TT consumed directly by Phase 8's Redo and Undo passes, correct whether or not a checkpoint exists.

19.4 Acceptance Criteria

fixtures/analysis_pass_differential.json passes: checkpoint-hinted Analysis and full-scan-from-zero Analysis produce byte-identical DPT/TT snapshots across 20 randomized workload/crash-point combinations (I5, 0 mismatches); Analysis completes within §4's recovery-throughput budget (≥150 MB/s of log scanned, feeding §28 M6).

19.5 Conformance Fixtures

fixtures/analysis_pass_differential.json; a new fixtures/analysis_no_checkpoint_ fallback.json (log with zero completed checkpoints still analyzes correctly from Lsn(0)).

19.6 Pitfalls

Using the checkpoint's embedded DPT rec_lsn values as final, without letting subsequent Update records in the scanned range lower them further — a page dirtied again after the checkpoint but before an even-earlier still-unwritten update would get the wrong (too-late) rec_lsn, corrupting Phase 8's redo start point. Forgetting that a CLR record (from a previous, still-incomplete undo before the crash) must also update the TT entry's undo_next_lsn during Analysis — treating CLRs as if they were ordinary Updates loses the undo-progress bookkeeping needed by §8.7's resume-from-crash-during-undo scenario.

19.7 Performance Concerns

Analysis-pass scan length is bounded by the checkpoint interval (Phase 6, §4) — this is the single lever operators have over recovery time (§29's named bottleneck #1); Analysis itself does no redo/undo I/O, so its cost is pure sequential scan throughput (§28 M6).

19.8 Edge Cases

A Begin record for a TxnId that already appears Committed in the checkpoint's TT snapshot (the transaction committed, then somehow a stale Begin for the same ID appears later — should never happen given monotonic TxnId allocation, but Analysis must reject or flag it rather than silently overwrite the Committed status). A page that appears in the checkpoint's DPT snapshot but receives no further Update records before the crash must retain its checkpoint-supplied rec_lsn unchanged.

19.9 Failure Analysis

A crash during the Analysis pass itself (recovery is interrupted by another crash) is resolved by restarting Analysis from scratch — Analysis is read-only with respect to the log (it writes nothing) and idempotent by construction (P14), so re-running it from the same checkpoint always reaches the same result.

19.10 Operational Notes

Expose analysis_scan_bytes and analysis_duration_seconds per recovery run — the first-reported metrics of any recovery event, letting operators estimate total RTO (§4) before Redo/Undo (Phase 8) even begin.

20. Phase 8 — ARIES Recovery: Redo & Undo Passes

20.1 Objectives

Implement the Redo pass (repeating history, P2) and the Undo pass (CLR-based rollback of losers, P3) using Phase 7's Analysis-pass output, completing the three-pass ARIES pipeline (Mohan et al. 1992, Lomet & Tuttle 1995).

20.2 Detailed Implementation Steps

  1. Implement Redo: start scanning at min(rec_lsn) across the Dirty Page Table (Phase 7); for each Update/Clr record with lsn > page.pageLSN, reapply it and set page.pageLSN = lsn (I6); skip records with lsn <= page.pageLSN — this is the literal redo-skip check from §8.2/§11.
  2. Redo applies to every dirty page's updates regardless of the owning transaction's eventual fate (P2) — Redo has no concept of "loser," only of "unapplied."
  3. After Redo completes, implement Undo: for each TT entry that is Active or Aborting (a loser, per §19.2), walk its prev_lsn/undo_next_lsn chain backward from last_lsn, generating one CLR per undone Update (P3, ADR-10).
  4. Each CLR's undo_next_lsn is set to the next record still needing undo in that transaction's chain (or None if this was the last) — I8's strictly-backward guarantee, enforced at construction.
  5. Write fixtures/redo_pass_idempotency.json and fixtures/undo_pass_clr_chain.json plus fixtures/crash_during_undo_recovery.json (re-crash mid-undo, restart recovery, assert no update is undone twice — §8.7).

20.3 Deliverable

Complete three-pass ARIES recovery pipeline (wal-recovery): Analysis (Phase 7) → Redo → Undo, restoring a crashed log to a consistent, fully-recovered state with all losers rolled back.

20.4 Acceptance Criteria

fixtures/redo_pass_idempotency.json passes: running Redo twice in a row on the same post-Analysis state produces zero additional page mutations the second time (I6, idempotent by construction); fixtures/crash_during_undo_recovery.json passes: across 50 randomized "crash again during undo" trials, no single Update is ever undone more than once (I8, 0 double-undo violations); full pipeline meets §4's RTO target (≤5 s per 1 GiB of unckpointed log, §28 M7).

20.5 Conformance Fixtures

fixtures/redo_pass_idempotency.json; fixtures/undo_pass_clr_chain.json; fixtures/crash_during_undo_recovery.json.

20.6 Pitfalls

Running Undo before Redo completes (violates P2 — undo logic assumes the page already reflects full physical history, including the loser's own updates, before rolling any of them back). Computing a CLR's undo_next_lsn from the original transaction's prev_lsn chain after some entries have already been undone in a prior, crashed attempt — must instead resume from the TT entry's current undo_next_lsn (as rebuilt by Analysis, §19.6), not restart the chain from the transaction's last_lsn.

20.7 Performance Concerns

Redo pass I/O-bound cost dominates recovery time for a large unckpointed log (§29's named bottleneck #1, direct consequence of Phase 6's checkpoint-interval choice); Undo pass cost scales with the number and size of loser transactions specifically, independent of total log size — a log with zero active transactions at crash time has a near-zero-cost Undo pass regardless of Redo's cost.

20.8 Edge Cases

A loser transaction with zero Update records (crashed immediately after Begin, before any write) requires no CLRs at all — Undo marks it Aborted with an empty undo chain, not an error. A page appearing in the DPT with rec_lsn set but which turns out to need zero redo (its on-disk pageLSN already caught up, e.g. from an earlier partial flush) is a normal, expected I6 skip — not a warning-worthy condition.

20.9 Failure Analysis

A crash during Redo (before Undo begins) is resolved by restarting the entire recovery pipeline from Analysis — Redo is idempotent (I6, redo-skip check) so re-running it from the same checkpoint reapplies only what is still needed and is safe to repeat any number of times, matching §19.9's identical reasoning for Analysis.

20.10 Operational Notes

Expose redo_apply_count, redo_skip_count, undo_clr_count, and losers_recovered per recovery run — the last two are the operationally interesting numbers post- incident (how much rollback work happened, how many transactions were lost), feeding §24's post-recovery incident report.

21. Phase 9 — Log Shipping, Retention & Performance Harness

21.1 Objectives

Implement wal-replicate's streaming log-shipping sender/receiver (ADR-17) and the retention gate (P12, I11) that blocks segment deletion until every attached replica has acknowledged past the relevant LSN; wire wal-bench to gate the full §28 M1– M12 target set in CI.

21.2 Detailed Implementation Steps

  1. Implement the sender: streams forced records (never unforced ones — I2 applies to replication acks exactly as it does to local commit acks) to a connected receiver over a plain TCP stream, record-by-record.
  2. Implement the receiver: applies incoming records to its own local segment files (Phase 4) using the same DurableWriter append path as a primary — a replica is structurally just another instance of this project's writer, fed remotely instead of locally.
  3. Implement RetentionGate (§11): tracks each attached consumer's last-acknowledged LSN; segment_eligible_for_deletion returns true only if the segment's highest LSN is ≤ every consumer's ack watermark and ≤ the last completed checkpoint's begin_checkpoint_lsn (ADR-16, I11/P12 combined).
  4. Implement wal-bench: drives fixed-throughput append/commit workloads against the full pipeline (Phases 2–8), measuring every §28 M# target, with and without an attached replica.
  5. Write fixtures/replication_lag_retention_gate.json (a deliberately lagging receiver blocks retention until it catches up) and fixtures/recovery_determinism_replay.json (same log + checkpoint replayed 100 times yields identical final page states, I12).

21.3 Deliverable

End-to-end pipeline: local durability (Phases 0–6) → recovery (Phases 7–8) → replication + retention (this phase), with wal-bench gating every release against §28's targets.

21.4 Acceptance Criteria

fixtures/replication_lag_retention_gate.json passes: retention blocks 100% of attempted deletions for segments still needed by a lagging consumer, across the §4 replica-lag budget (≤5 segments); fixtures/recovery_determinism_replay.json passes: 0 divergences across 100 replay runs (I12); wal-bench meets or exceeds every §28 M1–M12 target on the CI reference hardware profile.

21.5 Conformance Fixtures

fixtures/replication_lag_retention_gate.json; fixtures/recovery_determinism_replay.json.

21.6 Pitfalls

Shipping unforced (buffered-but-not-yet-force()-ed) records to a replica "to reduce lag" — this violates I2 for the replication path exactly as it would for a local commit ack, and can leave a replica believing it has data the primary itself would lose on its own crash. Gating retention only on checkpoint completion and forgetting the replica-ack half of the condition (ADR-16) — reintroduces the exact premature-deletion hazard P12 exists to prevent.

21.7 Performance Concerns

Replication adds network round-trip latency to the ack path only if the design requires replica confirmation before local commit acknowledgment — this project's default (ADR-17) ships asynchronously, so replication lag affects retention (§4's lag budget) but not local commit latency (§28 M1/M2 remain unaffected by replica health, by design).

21.8 Edge Cases

A receiver that disconnects mid-stream must be treated as "lagging," not "gone" — retention still respects its last-known ack watermark until an explicit detach/timeout policy removes it from the consumer set (avoiding silent data loss for a replica that reconnects later). wal-bench run with zero attached replicas must still execute the full local pipeline's fixture suite — replication is additive, never a prerequisite for local correctness.

21.9 Failure Analysis

A receiver applying a record with an Lsn lower than its own last-applied Lsn (possible after a receiver-side restart re-establishing a stream mid-segment) is handled as an idempotent no-op — the receiver's own DurableWriter instance rejects or skips already-applied LSNs rather than double-appending, reusing I1's monotonicity check as a dedup mechanism.

21.10 Operational Notes

Expose replica_ack_lsn (per consumer), replica_lag_bytes, and retention_blocked_segments from this phase onward — the primary dashboard triad for diagnosing FM-9 (stranded replica) before it happens, not just after (§24).

Structured logging: every force() call, every checkpoint, and every recovery pass emits a structured (JSON) event with lsn_range, duration_ms, and outcome — satisfies the traceability needed to reconstruct a timeline for any FM-1..FM-10 incident.

Dashboards: (1) commit-latency percentile trend vs. §4/§28 targets; (2) disk-usage trend (segments_on_disk, log_bytes_since_checkpoint) for capacity planning; (3) replica-lag triad (replica_ack_lsn, replica_lag_bytes, retention_blocked_ segments) for FM-9 early warning; (4) recovery-event timeline (Analysis/Redo/Undo durations) for post-incident review.

SLOs: p99 commit latency within §4 targets; zero I1/I4/I8/I12 violation events (hard SLOs, any breach is release-blocking per §27); RTO ≤ §4's budget per GiB of unckpointed log.

Runbooks: FM-3 storage-hardware investigation procedure; FM-9 base-backup restore procedure (explicitly the only path once triggered — no safe automated recovery); FM-7 checkpoint-interval tuning procedure.

Backup/restore: a consistent backup is a closed set of segment files plus the checkpoint covering them; restore = copy segments + run Analysis/Redo/Undo from the included checkpoint (identical mechanism to ordinary crash recovery, §8.5).

Deployment topology: single writer process per WAL instance; zero or more wal-replicate receivers per writer (§21) — no multi-writer topology exists (PhaseDeferred("§16")).

Canary/rollback/migration: wal-bench regression gate (§21/§27) is this project's canary signal; rollback = redeploy the previous binary against the same on-disk format (no format change without a version bump, §25).

25. Compatibility & Versioning

Wire format: RecordHeader/RecordType/LogRecord encoding (§8.1, §11) is tag-based with an explicit format-version constant introduced in Phase 1 (§13.10); pre-1.0, adding a RecordType variant or changing RecordHeader's fixed 32 B layout is a breaking change. Storage format: segment file layout (SegmentHeader, fixed 16 MiB sizing, ADR-06) is fixed for a given format version; no in-place segment upgrade mechanism exists — a format change requires a full checkpoint-and-restart migration. API stability: DurableWriter/SegmentScanner/RetentionGate trait signatures (§11) are the only cross-crate contracts considered stable within this repo; internal fields of wal-writer's batching state are private. SemVer: workspace crates version together (single release train, ADR-18's 6-crate layout versioned as one unit pre-1.0). Deprecation: none yet — no released 1.0. Rolling-upgrade guarantees: a replica (wal-replicate receiver) running the same format version as its primary can stream indefinitely; a format-version mismatch between primary and replica is rejected at connection time, not silently tolerated — mixed-version rolling upgrades are out of scope pre-1.0.

29. Scalability Analysis

Constant regardless of log size: per-record header size (32 B, §4); CRC computation cost per record (O(record size), independent of log length); DurableWriter's in-memory batching-window state.

Grows with log size (Big-O): Analysis-pass scan length is O(bytes since last checkpoint); Redo-pass work is O(dirty pages since checkpoint × average update size); segment count is O(total log bytes / 16 MiB).

Named bottlenecks, in order: (1) Analysis+Redo scan throughput (§19.7/§20.7) — the first ceiling hit as unckpointed log volume grows past §4's RTO budget; (2) single- writer serialization point (ADR-19) — all appends funnel through one thread, capping total throughput at that thread's sequential I/O bandwidth regardless of concurrent caller count; (3) checkpoint latency (§18.7) — grows slowly with DPT/TT size, but is a real (if small, §4's ≤10 ms target) writer-thread stall each time it fires.

Horizontal scaling: not applicable to a single logical WAL (this design is inherently single-writer-per-log by construction, ADR-19) — horizontal scale-out is a different-log concern (sharding data across independent WAL instances, each single- writer), out of scope here (PhaseDeferred("§16")'s multi-writer successor would need it).

Vertical scaling: force() latency (the dominant per-batch cost, §15.7) benefits directly from faster storage media (NVMe vs. SATA SSD); this is the primary vertical lever before the single-writer bottleneck (#2 above) becomes the binding constraint.

Sharding: not modeled — a real deployment shards by key range or hash across independent WAL instances, each with its own single writer and its own recovery scope; out of scope for this single-writer design (PhaseDeferred("§16")).

Practical ceiling and levers: ceiling is one writer thread's sequential I/O bandwidth (§4's 200 MB/s target) and the checkpoint-interval-bounded RTO; levers beyond it are (a) shorten the checkpoint interval to shrink bottleneck #1 at the cost of more frequent bottleneck #3 stalls, (b) move to a sharded multi-writer design (addresses bottleneck #2, PhaseDeferred("§16")), (c) faster storage media (addresses the vertical-scaling lever directly).

30. Mental Models & First Principles

  • MM1 — "The log is the truth; the page is a cache of it." Compressed insight: a data page's on-disk bytes are only ever a performance optimization over replaying the log — the log alone is sufficient to reconstruct any page (P1/P2). Predicts: any design that can lose a page but not the log recovers fully; any design that can lose log bytes but keep the page cannot be trusted. Bug class without it: flushing pages "for safety" ahead of their log records (FM-1). Resolving §: §6 (P1), §7 (I3).

  • MM2 — "Durability is a property of bytes on disk, not of code having run." Compressed insight: force() completing is the only event that matters for durability — everything before it is provisional regardless of how much code executed. Predicts: any "we already applied it in memory" reasoning about durability is a category error. Bug class without it: acknowledging a commit before its force() completes (I2 violation). Resolving §: §6 (P1/P9), §14.

  • MM3 — "Redo doesn't ask who wins; undo does." Compressed insight: repeating history (P2) applies every update uniformly, deferring the winner/loser question entirely to the Undo pass — this separation is what makes Redo simple and idempotent. Predicts: any recovery design trying to skip redoing "probably-losing" transactions has conflated two separate questions. Bug class without it: pages left in a state inconsistent with the log's physical history (I6 violation). Resolving §: §6 (P2), §20.

  • MM4 — "Undo must be as durable as the thing it's undoing." Compressed insight: because undo can itself be interrupted by a crash, an undo action must be logged (CLR) with the same durability discipline as a forward update, or rollback isn't actually crash-safe. Predicts: any "just re-run the inverse operation" rollback scheme is unsafe under crash-during-rollback. Bug class without it: undo livelock across repeated crashes (FM-5). Resolving §: §6 (P3), §7 (I8), §20.

  • MM5 — "A checkpoint is a hint, not a commitment." Compressed insight: a fuzzy checkpoint only shortens where Analysis starts scanning — it never claims the snapshotted pages are actually flushed (P10). Predicts: any code path that treats "checkpoint completed" as "data is now safe without the log" is wrong. Bug class without it: deleting log segments based on checkpoint completion alone, ignoring replica acknowledgment (P12 violation, FM-9). Resolving §: §6 (P10/P12), §18.

  • MM6 — "Corruption detection and corruption repair are different problems, and this system only solves the first." Compressed insight: a CRC tells you a record is wrong; it never tells you what the record should have been (P7/P8). Predicts: any "smart recovery" that tries to reconstruct a corrupted record's likely original content is solving a problem this design deliberately declines to solve. Bug class without it: skip-and-resume-scanning logic that silently misinterprets subsequent bytes (explicitly rejected, §17.6). Resolving §: §6 (P7/P8), §17.

  • MM7 — "One writer, many readers, is not a limitation — it's what makes ordering free." Compressed insight: LSN monotonicity (P4/I1) is trivial to guarantee with a single serialization point, and everything downstream (redo order, undo order, segment addressing) depends on that ordering being unconditionally true. Predicts: any attempt to parallelize the writer without a new ordering mechanism reintroduces exactly the bugs P4 exists to prevent. Bug class without it: LSN races corrupting redo/undo direction. Resolving §: §6 (P4), §29 (bottleneck #2).

  • MM8 — "Replication is just another reader with a stricter retention contract." Compressed insight: a log-shipping receiver is structurally the same DurableWriter append path as the primary, fed remotely — the only new concept is that retention now has to wait for it too (P12). Predicts: replication bugs are almost always retention-gate bugs, not streaming-protocol bugs. Bug class without it: premature segment deletion stranding a replica (FM-9). Resolving §: §6 (P12), §21.

32. Back-of-Envelope Capacity Model

  1. Record overhead per update (physiological, small payload): 32 B header (§4) + ~40 B typical payload (page id, offset, before/after lengths, small before/after images) + 4 B CRC = ≈ 76 B/update record — well under the 8 KiB ceiling.
  2. Records per transaction (typical OLTP txn, 5 updates): 1 Begin + 5 Update + 1 Commit = 7 records × ≈76 B avg = ≈ 532 B/txn logged.
  3. Segment lifetime at steady 200 MB/s (§4 M3) sustained write: 16 MiB segment ÷ 200 MB/s = ≈ 84 ms/segment at peak throughput — informs how aggressively retention (§21) must track replica acks under sustained load.
  4. Checkpoint interval in records, at 64 MiB trigger (§4) and ≈76 B/record: 64 MiB ÷ 76 B ≈ ≈ 883,000 records between checkpoints at steady small-record load — directly bounds Analysis-pass scan length (§29 bottleneck #1).
  5. Recovery time for a full checkpoint interval, at M6's 150 MB/s scan floor: 64 MiB ÷ 150 MB/s ≈ ≈ 448 ms Analysis+Redo scan time — well under §4's RTO budget (5 s/GiB), confirming the checkpoint interval is conservatively sized.
  6. Group-commit amortization at 50 concurrent committers (§15.4): worst case 1 force() per 2 ms window regardless of committer count ⇒ at 500 commits/sec aggregate demand, ≤ 1 force() per ≥ 40 requests/force() — exceeds M9's ≤1-per-10 target with margin.
  7. Dirty Page Table memory footprint at §4's 100,000-page ceiling: 100,000 × (8 B page_id + 8 B rec_lsn) = 1.6 MB — negligible relative to any modern process's memory budget.
  8. Transaction Table memory footprint at §4's 10,000-txn ceiling: 10,000 × (8 B txn_id + 1 B status + 8 B last_lsn + 9 B Option<Lsn>) ≈ ≈ 260 KB — similarly negligible.
  9. Undo work for a single large loser transaction (10,000 updates): 10,000 CLRs × ≈76 B/record ≈ ≈ 760 KB of additional log volume generated purely by rolling back one transaction — the concrete cost P3's idempotency guarantee is paid for.
  10. Replica catch-up time after a 5-segment (80 MiB, §4's lag budget) gap, at M11's healthy-network streaming rate: assuming streaming throughput matches local append throughput (200 MB/s, M3) once caught up to steady state, 80 MiB ÷ 200 MB/s ≈ ≈ 400 ms to fully catch up from the maximum tolerated lag — well inside a typical retention-gate patience window.
  11. Segments on disk at steady state with a 5-segment replica-lag budget (§4): 1 active + up to 5 pending-replica-ack + 1 pending-checkpoint ≈ ≈ 7 segments × 16 MiB = 112 MiB typical disk footprint before older segments become eligible for deletion (P12).
  12. CRC compute cost at M3's 200 MB/s target, illustrative CRC-32C throughput ≈2 GB/s per core (hardware-accelerated): 200 MB/s ÷ 2 GB/s ≈ 10% of one core dedicated to checksumming at peak throughput — informs M5's ≤5%-of-append-cost target as achievable with hardware CRC instructions, tighter without them.

34. Alternative Architectures (Roads Not Taken)

34.1 Shadow Paging (No Log At All)

Page Table v1 --commit--> Page Table v2 (new root, old pages untouched)
     |                          |
  [old pages]              [new pages]   (atomic root pointer swap = commit)

Wins when: updates are infrequent and whole-page-copy-on-write overhead is acceptable — no log manager needed at all, since the old page table root is always a consistent prior state (Lampson & Sturgis 1979). Real system: early System R prototypes used shadow paging before switching to logging. Rejected here: shadow paging fragments data physically (updated pages move), destroys locality, and cannot express fine-grained (sub-page) concurrent updates the way physiological logging can (ARIES's namesake "fine-granularity locking" goal, Mohan et al. 1992) — the entire point of this project is studying WAL-based recovery, so removing the log erases the subject.

34.2 Force-at-Commit, No Redo Capability

Commit(T) --> flush ALL of T's dirty pages to disk --> ack Commit(T)

Wins when: transactions touch very few pages and synchronous flush latency is tolerable — no redo pass is ever needed because every committed page is already durable at ack time (Härder & Reuter 1983's "force" policy). Real system: some embedded key-value stores default to force-on-commit for simplicity. Rejected here: commit latency becomes proportional to dirty-page count and disk seek cost rather than to one force() call (defeats §4's commit-latency targets); it also forecloses the group-commit amortization (P9) this project exists to demonstrate.

34.3 Log-Structured Storage (No Separate Data Pages)

Append-only log  ==  the data store itself (no separate "page" to redo against)
   segment1 -> segment2 -> segment3 -> ... -> compaction merges old segments

Wins when: write throughput dominates over read/update-in-place cost, and periodic compaction can absorb the cost of never updating in place (Rosenblum & Ousterhout 1992). Real system: log-structured merge-tree engines (RocksDB, LevelDB, §31) apply this at the storage-engine level; the original LFS paper applied it at the filesystem level. Rejected here: this project's entire subject is the WAL-plus-separate-pages architecture (ARIES) and its redo/undo mechanics — a log-structured store has no in-place page to undo against, eliminating exactly the recovery mechanism (Phase 8) under study.

34.4 Consensus-Replicated Log (Raft/Paxos Instead of Async Streaming)

Writer --propose(record)--> [Peer1] [Peer2] [Peer3]  (quorum ack before commit)
                                  \____ committed once (N/2)+1 peers durable ____/

Wins when: the log itself must survive the total loss of the primary machine, not just crash-and-restart (etcd's raft WAL, §31). Real system: etcd, and any Raft/Paxos- backed replicated log. Rejected here: this project's replication (Phase 9, ADR-17) is deliberately asynchronous and single-primary — adding quorum-based commit would require a full consensus implementation, a different and larger project than "build a WAL," and is explicitly deferred (PhaseDeferred("§21")).

36. Glossary

ARIES — Algorithm for Recovery and Isolation Exploiting Semantics; the three-pass (Analysis/Redo/Undo) recovery method this project implements (Mohan et al. 1992).

Analysis pass — the ARIES pass that rebuilds the Dirty Page Table and Transaction Table from a checkpoint forward to the log's true end (§8.5, Phase 7).

CLR (Compensation Log Record) — a log record describing an undo action, carrying an UndoNextLSN so rollback is idempotent under repeated crashes (P3).

Checkpoint — a periodic snapshot of recovery-relevant state used to bound Analysis-pass scan length (P10).

CRC-32C — the cyclic redundancy check variant used for per-record corruption detection in this project (ADR-03).

Dirty Page Table (DPT) — the table of pages modified but not yet flushed since their earliest unflushed update, keyed by rec_lsn (§8.3).

fdatasync — the POSIX syscall flushing a file's data (and only the metadata needed to read it back) to durable storage; this project's default durability barrier (ADR-04, POSIX.1-2017).

fsync — the POSIX syscall flushing a file's data and all metadata to durable storage; used as a fallback when fdatasync is unavailable (ADR-04).

Force / force() — this project's durability barrier abstraction wrapping fdatasync/fsync (P1).

Fuzzy checkpoint — a checkpoint that snapshots bookkeeping state without flushing dirty pages, avoiding an I/O stall (ADR-08).

Group commit — batching multiple transactions' commit records into a single force() call (P9).

LSN (Log Sequence Number) — the strictly monotonic identifier assigned to every log record in append order (P4, I1).

LSM tree (Log-Structured Merge tree) — an alternative storage architecture with no in-place page to redo/undo against, contrasted in §34.

Loser transaction — a transaction active or aborting at crash time, requiring undo during recovery (§8.3).

No-force policy — the policy that a committed transaction's dirty pages need not be flushed at commit time, relying on redo capability instead (P5).

No-steal policy — the (rejected, ADR-09) policy that uncommitted pages are never evicted from the buffer pool before commit, eliminating the need for undo.

pageLSN — the LSN of the last update applied to a given data page, used for the redo-skip check (I6, ADR-13).

Payload — the record-type-specific bytes following a RecordHeader (§11).

Physiological logging — logging that names a page physically but describes the operation logically, rather than storing full page images (P6, ADR-12).

Redo pass — the ARIES pass that reapplies every logged update not yet reflected in its target page, regardless of the owning transaction's eventual fate (P2).

RecordHeader — the fixed 32-byte structure prefixing every log record's payload (§11).

RecordType — the tag distinguishing Begin/Update/Commit/Abort/Clr/ CheckpointBegin/CheckpointEnd records (§11).

Repeating history — the principle that redo reapplies all logged updates uniformly, deferring winner/loser distinction to undo (P2, MM3).

Retention gate — the mechanism blocking segment deletion until covered by both a checkpoint and every replica's acknowledgment (P12, ADR-16).

Segment (file) — a fixed-size (16 MiB) chunk of the logical, unbounded log (ADR-06, P11).

Shadow paging — an alternative, log-free recovery architecture using copy-on-write page tables, contrasted in §34.

SegmentHeader — the magic/version/ID/first-LSN header at the start of every segment file (§8.1).

Single-writer discipline — the rule that exactly one thread ever appends to the log, enabling group commit and LSN ordering without locking (ADR-19, P4).

Steal policy — the policy that the buffer pool may evict uncommitted (dirty) pages before their owning transaction commits, requiring undo capability (ADR-09/11).

Torn write — a partially-completed physical write, typically from a crash mid-write, detected via CRC/length mismatch (P7, §8.6).

Transaction Table (TT) — the table of transactions active (or aborting) at a given point, tracking last_lsn and undo_next_lsn (§8.3).

Truncate-tail policy — the rule that a torn/corrupt tail is dropped, never repaired or partially skipped (P8).

Undo pass — the ARIES pass that rolls back every loser transaction's updates via CLRs, in strict reverse-LSN order (P3, I7).

UndoNextLSN — the field in a CLR (or Transaction Table entry) pointing to the next record still needing undo, guaranteeing idempotent rollback (I8).

WAL protocol / WAL rule — the rule that a log record must be durable before the data it describes is written to durable storage (Härder & Reuter 1983, P1).
