In one paragraph

A write-ahead log is an append-only file in which a database records what it is about to do before doing it, so that after a crash it can rebuild exactly the committed state (§1, §2). This design is a six-crate Rust library that a storage engine embeds: records carry increasing sequence numbers and checksums, one writer thread batches commits behind a single disk-flush call, the log is cut into 16 MiB files, periodic snapshots shorten recovery, and a three-pass recovery procedure (ARIES) restores consistency (§1, §3, §4). An optional second thread streams the log to a standby copy. It is a teaching-scale reproduction of the mechanism in PostgreSQL, SQLite, RocksDB and etcd, not a production engine (§1, §31).

The problem, concretely

Take the blueprint's example: transaction T7 updates page P3 and commits (§8.4). The database keeps changed pages in memory and may write them to disk before the transaction commits (steal) or long after (no-force) (ADR-11, §36). A crash in between can leave an uncommitted change on disk, which needs undo, or lose a committed one, which needs redo (ADR-09, P5). Commit must be fast (one force(), not a full page flush), and recovery exact: no committed write lost, no uncommitted write kept (§2).

The obvious fix is to write every changed page to disk before telling the caller "done". That makes commit time proportional to the number of dirty pages and to disk seek cost, and it rules out sharing one flush among many committers (§34.2, P9). The other obvious fix is to swap whole page tables atomically (shadow paging); the old root is always a consistent state, but updated pages move, locality is lost, and fine-grained concurrent updates cannot be expressed (§34.1).

The blueprint's answer is to write a small description of each change to a log first, and make only that log durable at commit. The pages can reach disk later, or never before a crash, because the log can rebuild them (§8.4, P5). That raises new problems the rest of the design solves: a crash can cut a log record in half (§8.6), rollback must survive a crash in the middle of it (§8.7), and an old log segment may be deleted only once every standby has acknowledged it (P12).

How it works, end to end

Follow one transaction through the boxes of §3's diagram:

   Transaction API (host engine, out of scope)
              |  UPDATE/COMMIT/ABORT intents
     +--------+---------+
     |      wal-core     |   Lsn, TxnId, PageId, RecordHeader, RecordType, WalError
     +--------+---------+
              |  append(record) -> Lsn
     +--------+---------+        group-commit queue (MPSC, ADR-19)
     |     wal-writer     |  single writer thread; force() barrier (fsync/fdatasync)
     +--------+---------+
              |  append to active segment, rotate at size limit
     +--------+---------+
     |   Segment Files    |  seg-000001.wal ... seg-NNNNNN.wal  (ADR-06/07)
     +--------+---------+
              |
   +----------+-----------+---------------------------+
   v                      v                           v
 wal-reader            wal-recovery               wal-replicate
 CRC check,   ------>  Analysis/Redo/Undo,        log-shipping to standby
 torn-write            DPT/TT, Checkpoint
 detection
  1. A transaction (call it txn 7) begins and updates one page. The host engine sends intents to wal-core, which only defines the shared types: Lsn, TxnId, PageId, RecordHeader, RecordType, WalError. It does no I/O (§3, §11).
  2. wal-writer is the only crate that appends. One thread drains a queue, assigns each record the next log sequence number (LSN), and writes the bytes. Exactly one thread ever appends (§3, ADR-19, I1). In the blueprint's trace, the begin record gets LSN 100, the update 101 and the commit 102 (§8.4).
  3. The commit record joins a batch. When the batch is full or its time window ends, the writer makes one force() call (the blueprint's name for the durability barrier over fdatasync, falling back to fsync). Only after that call returns is the commit acknowledged (§8.4, I2, ADR-04, ADR-05).
  4. The bytes live in Segment Files: fixed 16 MiB files named seg-000001.wal and so on. The writer rotates to the next file when one fills, and an LSN means the same thing across the boundary (§3, ADR-06, ADR-07, P11).
  5. After a crash, wal-reader scans the segments in order, checks each record's checksum, and stops at the first record that is incomplete or wrong. It never interprets what a record means (§3, P7, P8, P13).
  6. wal-recovery takes the reader's valid prefix and runs Analysis, Redo and Undo, using a table of dirty pages and a table of transactions. A checkpoint record tells it where to start (§3, §8.5).
  7. wal-replicate streams forced records to a standby over plain TCP. The standby applies them through the same DurableWriter append path, and the primary keeps old segments until the standby has acknowledged them (§3, §21.2, P12, ADR-17).

wal-bench is the harness that measures the §28 targets M1 to M12 (§1). The buffer pool belongs to the host engine, not this design, except that its flush path must ask for the last-forced LSN (§1, P1, I3).

The core ideas

The WAL rule: log first, then data (P1, I2, I3, §8.4)

The rule: a record describing a page change must be on durable storage before that page's changed bytes are. Two checks enforce it. The writer acknowledges a commit only after the force() that covers it (I2). The buffer flush path refuses to write a page whose pageLSN (the LSN of the last update applied to it) is newer than the writer's last-forced LSN (I3).

Tiny trace from the blueprint: txn 7 gets LSNs 100, 101, 102. The batch's force() covers 100 to 102, and only then does the caller hear "committed". Page 3 may be written to disk at any later time, or not before the next crash; either is safe because the log already says how to redo it (§8.4, P5). If the order were reversed, a page could show an update whose record never survived, and recovery cannot redo what it never sees (P1). Mental model: durability is a property of bytes on disk, not of code having run (MM2).

Records, LSNs and checksums (§8.1, §8.2, ADR-02, ADR-03, ADR-12)

Every record is a 32-byte header, a payload, and a 4-byte CRC-32C checksum computed over header and payload (§4, §8.1, §32 item 1, P7, ADR-03). The header holds the LSN, the previous LSN of the same transaction, the transaction id, the record type and the payload length (§8.1). The LSN is an absolute byte offset into the logical log; ADR-02's stated reason is an O(1) seek to any LSN without a separate index (ADR-02, P11). The record type is one of begin, update, commit, abort, compensation (CLR), and the two checkpoint markers (§8.1).

The payload is physiological: it names the target page physically but describes the change logically ("insert at slot S") instead of storing whole page images (P6, ADR-12). The transaction's chain of previous-LSN links is how undo walks backward (§8.3, I7). Each data page also carries its own page_lsn, which recovery compares against a record's LSN to decide whether to apply it (§8.2, ADR-13, I6).

Torn writes: detect, then truncate (§8.6, P7, P8, ADR-20, I4, I13)

A crash in the middle of an append leaves a torn write: a record cut short. Trace from the blueprint: a header claims payload_len = 4096 but only 900 bytes remain. The reader cannot even run the checksum, so it stops at the last fully-read valid record and reports that offset as the true end of the log. The partial bytes are neither an error nor repaired; they are simply outside the log (§8.6).

The reader never skips a bad record and resumes, because a damaged length or LSN field could make the rest of the log parse as something it is not (P8, MM6). The cost is accepted: a good record that trips a false CRC alarm is lost along with everything after it (P8). A clean segment boundary (trailer present, no partial record) is a normal event and must not be confused with a torn tail (§17.2, §33 item 22).

Group commit: one flush for many committers (P9, ADR-05, ADR-19, §4)

A force() is the expensive step, so the single writer thread collects commit records from many callers and flushes once. The batch closes when 2 ms have passed or 8 MiB is buffered, whichever comes first (§4, ADR-05, §15.2). Each caller blocks until a force() covering its LSN has finished (§15.2, I2).

With one flush per transaction, throughput is capped at 1 divided by the flush latency (P9). With 50 concurrent committers the Phase 3 test expects at most 5 flushes in total (§15.4). The price is that the fastest committer in a batch waits up to the batching window (P9). The queue-into-one- thread shape also gives LSN ordering for free (MM7, P4).

Fuzzy checkpoints: a hint, not a flush (ADR-08, P10, I10, §18)

Without a checkpoint, Analysis starts at LSN 0 (§19.2). A checkpoint writes down enough state to start later: the Dirty Page Table (DPT: pages changed in memory but not yet flushed, each with the first LSN that dirtied it) and the Transaction Table (TT: transactions active or aborting) (§36, §18.1). It is fuzzy because it does not flush any pages, so there is no I/O stall (ADR-08, P10).

Three steps: (1) log CHECKPOINT_BEGIN and note its LSN; (2) copy the DPT and TT while the system keeps running; (3) log CHECKPOINT_END with the copied payload (§18.2). The snapshot must match the live tables as of the begin LSN, not the end LSN (§18.2), and Analysis starts scanning at the begin LSN (§19.1); why is hard question 6 (§33 item 6, I10). If a crash cuts the begin/end pair, recovery falls back to the previous checkpoint, or to LSN 0 if there is none (T5, §18.9). A checkpoint is a hint that shortens Analysis; it never claims pages are flushed (MM5).

ARIES recovery and compensation records (§8.5, §8.7, P2, P3, I5 to I8, ADR-10)

Three passes, run in order (ADR-09, §19, §20, P2):

  1. Analysis scans forward from the last checkpoint to the log's true end and rebuilds the TT and DPT as of the crash (§19.1, I5).
  2. Redo starts at the smallest first-dirtied LSN in the DPT and reapplies an update only if the record's LSN is greater than the page's on-disk pageLSN (§20.2, I6). It does this for every transaction, including ones that will be undone ("repeating history") (P2, MM3).
  3. Undo rolls back each unfinished transaction ("loser") in strict reverse-LSN order, writing a compensation log record (CLR) for each step. A CLR carries an UndoNextLSN pointing to the next record still needing undo (I7, P3, §20.2).

The blueprint's worked example (§8.5), with page and transaction numbers spelled out:

LSN Record After Analysis
200, 201 checkpoint begin and end, empty tables start scanning at 200
210, 211 txn 9 begins, updates page 5 page 5 dirty since 211
220, 221 txn 10 begins, updates page 6 page 6 dirty since 221
230 txn 9 commits txn 9 committed
(crash) txn 10 never finished txn 10 is a loser

Redo starts at 211 and reapplies 211 and 221 where the page on disk is behind, including txn 10's update. Undo reverses LSN 221 and writes one compensation record (LSN 240) whose next-undo pointer is empty, so txn 10 is aborted. Txn 9 needs no undo (§8.5).

Because undo is itself logged, a crash during rollback is safe (§8.7, P3). In the §8.7 trace the CLR at LSN 240 is in the log when the crash hits; Analysis finds txn 10's UndoNextLSN already past LSN 221, so nothing is left to undo and the update is never reversed twice. The pointer must go strictly backward, never forward or to itself, or rollback could loop forever (I8, P3). The cost: rolling back a transaction writes as much log as its forward path did (P3).

The trade-offs — where engineers disagree

Durability barrier: fdatasync (ADR-04)

Chosen: fdatasync (fallback fsync), portable across common filesystems. Rejected: O_DIRECT plus write-through (FUA). When the rejected choice is right: on NVMe deployments that accept bypassing the page cache for the lowest tail latency.

Commit batching: group commit with a window (ADR-05)

Chosen: batches bounded by 2 ms and 8 MiB, for throughput under concurrent commit load (P9). Rejected: an immediate force() per transaction. When the rejected choice is right: a single-writer workload with no concurrent committers to batch with.

Checkpoint style: fuzzy (ADR-08)

Chosen: snapshot the tables without flushing pages, avoiding an I/O stall (P10, Mohan et al. 1992). Rejected: a sharp (consistent) checkpoint. When the rejected choice is right: a small in-memory dataset where the cost of flushing everything is negligible.

Buffer policy: steal, no-force (ADR-11, ADR-09)

Chosen: the buffer pool may evict uncommitted pages (steal) and need not flush a transaction's pages at commit (no-force), which decouples commit latency from data-page I/O (P5, Härder & Reuter 1983). That is why recovery needs both redo and undo (ADR-09). Rejected: flush all dirty pages at commit (force); and, for recovery, a two-pass redo-only scheme under no-steal. When the rejected choice is right: force wins in a design with no separate log at all, such as shadow paging, where the page write is the only durability mechanism (ADR-11); no-steal wins when the buffer pool always fits the entire dirty working set, so no eviction pressure exists (ADR-09).

Undo mechanism: compensation records (ADR-10)

Chosen: CLRs with UndoNextLSN chaining, for idempotent rollback under repeated crash-during-undo (P3). Rejected: plain undo re-execution without CLRs. When the rejected choice is right: only where there is a proof obligation of zero crashes during rollback, such as an in-memory test harness with no crash injection; the blueprint calls this not a real crash-recovery target.

Writer concurrency: one thread, one queue (ADR-19)

Chosen: a single dedicated writer thread draining an MPSC queue, because group commit needs one serialization point (P4) and it makes LSN order unconditional (MM7). Rejected: N threads writing under a mutexed file handle. When the rejected choice is right: at very low concurrency (two writers or fewer), where batching gains are negligible relative to queue latency. The cost of the choice: total throughput is capped at one thread's sequential I/O bandwidth (§29 bottleneck 2).

Torn tail: truncate and continue (ADR-20)

Chosen: stop at the first corrupt or incomplete record and treat everything after it as never written (P8), matching the physical reality of an interrupted write. Rejected: fail hard and require manual intervention on any CRC mismatch. When the rejected choice is right: a regulatory audit log that must flag every suspected-corrupt byte range rather than silently truncate.

Retention: wait for the slowest consumer (ADR-16)

Chosen: keep a segment until it is both covered by a checkpoint and acknowledged by every attached replica (P12, I11). Rejected: a fixed segment-count ring buffer. When the rejected choice is right: a standalone deployment with no replicas, where bounding disk usage matters more than catch-up from the log.

Roads not taken (§34, §35)

Shadow paging replaces the log with copy-on-write page tables and an atomic root swap. It wins when updates are infrequent and whole-page copying is acceptable (early System R). It is rejected because pages move, locality is lost, and sub-page concurrent updates cannot be expressed (§34).

Force-at-commit with no redo flushes all of a transaction's dirty pages before acknowledging. It wins when transactions touch very few pages and synchronous flush latency is tolerable. It is rejected because commit latency tracks dirty-page count and group commit is lost (§34, P9).

Log-structured storage makes the log the data store, with compaction merging old segments. It wins when write throughput dominates and compaction can absorb the cost (RocksDB, LevelDB). It is rejected because it has no in-place page to undo against, which is the subject here (§34, §31).

A consensus-replicated log (Raft or Paxos) acknowledges a commit once a quorum of peers has it durable. It wins when the log must survive total loss of the primary machine, as in etcd. It is rejected because replication here is deliberately asynchronous and single-primary, and quorum commit is a different and larger project (§34, ADR-17).

The deferred register (§35) parks six features, each with an un-defer trigger: block-device backend and at-rest encryption, multi-writer sharded WAL (when single-writer throughput binds), parallel checkpointing, logical row-level decoding, consensus-based replica leader election, and object-storage tiering of cold segments (§35).

What must never be false

  • I1 — LSNs strictly increase in append order. Noticed by an LSN-monotonicity fixture and the counter lsn_out_of_order_total; recovery is to halt the writer and audit.
  • I2 — a record is forced before any dependent acknowledgment is sent. A log-order fixture and force_before_ack_violations; the blueprint treats a hit as a specification bug.
  • I3 — no page is flushed with a pageLSN newer than the last-forced LSN. A flush-gate fixture and page_flush_ahead_of_log_total; if hit, see FM-2.
  • I4 — a record's CRC matches or it and everything after it is excluded from recovery. An injected-bit-flip reader fixture and crc_mismatch_total; the tail is truncated.
  • I5 — Analysis from a checkpoint yields the same tables a full scan from LSN 0 would. A differential fixture and analysis_dpt_mismatch_total; fall back to a diagnostic full rescan.
  • I6 — Redo applies an update iff its LSN exceeds the page's on-disk pageLSN. A redo idempotency fixture and the redo_skip_count / redo_apply_count pair.
  • I7 — Undo rolls back each loser in strict reverse-LSN order. An undo-order fixture and undo_order_violations; see FM-4.
  • I8 — a CLR's UndoNextLSN points strictly backward. A repeated-crash-during-undo fixture and undo_livelock_detected_total; see FM-5.
  • I9 — the log is append-only; the writer's API has no update method (type-level, no telemetry).
  • I10 — a checkpoint's begin LSN is at or before every LSN in its snapshot. A checkpoint LSN-order fixture and checkpoint_lsn_order_violations; see FM-6.
  • I11 — no segment is deleted while an attached consumer has not acknowledged past it. A lagging-replica fixture and premature_segment_deletion_total; see FM-9.
  • I12 — recovery on a fixed log and checkpoint always ends in the same page states. A differential replay fixture and recovery_nondeterminism_detected_total.
  • I13 — payload_len equals the real payload size. A length-mismatch fixture and length_mismatch_total; the tail is truncated.
  • I14 — no update or abort follows a transaction's commit record. A post-commit-write fixture and post_commit_write_rejected_total; rejected at the API layer.

What breaks in production

  • FM-1 and FM-2 — committed data missing, or a page showing an update with no log record. Root cause: the WAL rule was broken, a page flushed before its record was forced (P1, I3). Detection: the flush-gate fixture, or a data-loss report. Recovery: none automatic, since it is a specification violation; fix the code and audit pageLSN against the last-forced LSN at flush.
  • FM-3 — repeated torn-write detections on a healthy shutdown path. Root cause: the storage device is silently corrupting writes, or a writer bug not using force() properly. Detection: a rate alert on torn_write_detected_total. Recovery: manual; investigate the storage hardware, check the writer's force-before-rotate ordering (§16.9), audit segment by segment with CRCs.
  • FM-5 — the same update undone more than once across repeated crashes. Root cause: I8 was violated, so a CLR's pointer did not move strictly backward, or Analysis rebuilt it wrongly. Detection: the repeated-crash-during-undo fixture. Recovery: none automatic; release-blocking, fixed by auditing CLR construction (§20.6).
  • FM-7 — recovery takes longer than the budget. Root cause: checkpoint interval too long for the write volume, or scan throughput regressed. Detection: the wal-bench RTO check (§28 M7). Recovery: shorten the interval and investigate the regression (§29 bottleneck 1).
  • FM-9 — a replica can never catch up. Root cause: retention deleted a segment the replica still needed, breaking I11 and P12. Detection: premature_segment_deletion_total above zero. Recovery: not possible by streaming; restore the replica from an out-of-band base backup, then resume streaming.
  • FM-10 — two recoveries of the same crashed log end in different states. Root cause: I12 broken, for example a wall-clock read leaked in (P14). Detection: the recovery-determinism replay fixture (§21). Recovery: none automatic; release-blocking, found by auditing recovery's inputs.

Threats a reader should know (§22):

  • T2 — a torn write mid-record from power loss; answered by CRC plus truncate-tail (P7, P8), watched by torn_write_detected_total.
  • T5 — a crash in the middle of a checkpoint's begin/end window; Analysis detects the incomplete pair and falls back to the previous checkpoint or LSN 0.
  • T7 — a batch's force() fails partway (disk full); every caller in the batch gets WalError::ForceFailed and may retry (§15.9).
  • T9 — a buggy retention gate deletes a segment a replica needs; no automatic recovery (FM-9), prevented by I11.
  • T10 — a forged record with a valid CRC; explicitly out of scope, since CRC guards against accidental corruption, not an adversary (§22).

How it compares

  • PostgreSQL xlog made the same core choices: ARIES-derived redo-then-undo, fuzzy checkpoints and 16 MiB segments, with CRC-32 where this design uses CRC-32C (§31). It fits a general-purpose relational engine that needs fine-grained locking and partial rollback (§31).
  • SQLite wal.c logs whole changed pages ("frames") into one growing file that a checkpoint resets, with no undo pass. That suits an embedded single-process database (§31, P12).
  • RocksDB's log writer records logical key/value operations and replays them into an in-memory table, with no undo pass because an LSM tree has no in-place update to reverse (§31). That fits wherever the storage engine is itself log-structured (§31, §34.3).
  • etcd's raft WAL uses the same append, checksum, rotate skeleton for a consensus log, with CRCs chained across records and truncation after a Raft snapshot. It makes replicated commands durable, not data pages (§31).

Questions to test yourself

  1. Why must a page's modified bytes never reach durable storage before the log record describing that modification is forced, and what exactly breaks if the order is reversed? — Hint: P1 in §6, I3 in §7, and the trace in §8.4.
  2. Why is an undo action itself logged as a Compensation Log Record instead of simply being re-executed from the original update's inverse? — Hint: P3, I8 and the crash-during-undo example in §8.7.
  3. Why does the Analysis pass need to start from a checkpoint's begin_checkpoint_lsn rather than its CHECKPOINT_END LSN? — Hint: I10 and the snapshot timing in §18.
  4. Why is single-writer serialization (ADR-19) not simply a performance limitation to be "fixed" with more writer threads, and what specific guarantee depends on it? — Hint: P4, MM7 and bottleneck 2 in §29.
  5. Why does this project treat "torn write" and "clean segment boundary" as fundamentally different signals that must never be confused, even though both involve "no more valid bytes here"? — Hint: the scanner's two outcomes in §17 and I4.

If you only remember three things

The log is the truth and the pages are a cache of it, so a commit is durable the instant its record's force() returns, and never before (MM1, MM2, I2). One writer thread, one flush per batch, and per-record checksums give ordering, throughput and a clean "true end of log" without locks or guesswork (ADR-19, ADR-05, P7, P8). Recovery repeats all history first and then undoes the losers through logged compensation records, which is what lets it survive a crash in the middle of rollback (P2, P3, MM3, MM4).

Words used here

  • WAL rule — a change's log record must be durable before the changed page is written (P1).
  • LSN (log sequence number) — the increasing identifier of each record, here a byte offset (I1, ADR-02).
  • Group commit — batching many transactions' commit records into one force() (P9).
  • Torn write — a record cut short by a crash, caught by length or checksum (P7, §8.6).
  • pageLSN — the LSN of the last update applied to a page; the redo-skip test (I6, ADR-13).
  • Dirty Page Table (DPT) — pages changed in memory and not yet flushed, with their first-dirtied LSN (§8.3).
  • Fuzzy checkpoint — a snapshot of the two tables that flushes no pages (ADR-08).
  • Repeating history — redo reapplies every logged update, winner or loser, and leaves the choice to undo (P2, MM3).
  • CLR (compensation log record) — a logged undo step carrying UndoNextLSN (P3).
