Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1 — Blakley Hyperplane Geometry

Secret embedded as coordinate in Z_p^t vector space.
Each share = one hyperplane equation a_i · x = b_i (t unknowns).
Reconstruct = solve linear system of t hyperplane equations.

The secret is a specific coordinate of the unique intersection point of t hyperplanes in t-dimensional projective space over Z_p. Each share is a hyperplane (a vector of t field elements + a constant), making shares O(t) times larger than Shamir shares. Reconstruction is Gaussian elimination.

Regime where it wins: Geometric secret sharing and visual cryptography schemes (where shares are 2D pixel arrays and reconstruction is overlay) descend from Blakley's geometry. When the secret encoding is naturally geometric (images, spatial data), Blakley's representation maps directly. Also wins in theoretical analysis where orthogonality of hyperplanes provides useful algebraic structure for extension.

Real system embodying it: Blakley's original 1979 paper ("Safeguarding cryptographic keys," AFIPS 1979). Visual secret sharing (Naor & Shamir 1995) extends this for printed image shares.

Why rejected here: Share size is O(t) field elements vs. O(1) for Shamir (§4.1 share vector memory). Reconstruction requires full Gaussian elimination (O(t^3)) vs. O(t^2) Lagrange. No verifiability extensions as mature as Feldman/Pedersen. No production Rust ecosystem.

Alt-2 — Additive / Replicated Secret Sharing

Secret s split as: s = s_1 + s_2 + ... + s_n  (additive)
or:
Each party holds shares for every subset of size n-t (replicated).
Reconstruction: sum the additive shares.

In additive secret sharing, the secret is literally split into n random field elements summing to s. Any single share reveals nothing (one degree of freedom), but reconstruction requires ALL n shares — this is n-of-n, not t-of-n. Replicated secret sharing assigns to each party a bundle of shares indexed by all (n-t+1)-size subsets, achieving t-of-n but with exponentially many shares.

Regime where it wins: Additive secret sharing is the bedrock of MPC protocols (BGW, SPDZ) because it is linear — parties can add their shares to compute the additive secret sharing of a sum without interaction. This linearity enables generic circuit evaluation. Additive sharing wins when the goal is not just key custody but computation ON the secret (e.g., threshold AES, threshold PRFs). Replicated sharing wins for very small n (n ≤ 4) where the exponential share count is tolerable and zero-communication reconstruction is needed.

Real system embodying it: SPDZ (Damgård et al., CRYPTO 2012) uses additive sharing over rings for authenticated MPC. MP-SPDZ (github.com/data61/MP-SPDZ) is the production implementation. BGW protocol (Ben-Or, Goldwasser, Wigderson 1988) uses replicated sharing for information-theoretic MPC.

Why rejected here: Additive sharing is n-of-n — any party absence blocks reconstruction. This violates the t-of-n fault-tolerance requirement stated in §1.1. Replicated sharing is exponential in n; at n=20 it produces C(20,11) ≈ 167,960 shares per party — completely impractical. The goal here is key custody, not generic computation.

Alt-3 — Threshold Encryption Without Reconstruction (ElGamal / ECIES Variant)

Public key Y = g^s. Ciphertext C = (rY, m XOR H(rg)).
Decryption share: D_i = r * share_i * g (partial decryption).
Aggregate: combine t D_i via Lagrange to recover rY; XOR with H(rY).

Threshold decryption distributes ElGamal or ECIES decryption across t parties. No party reconstructs the secret key s; instead, each contributes a partial decryption share D_i = r·Y_i = r·g^{share_i}. The aggregator combines t partial decryptions via Lagrange interpolation in the group exponent to recover rY, then derives the symmetric key.

Regime where it wins: When the use case is encryption/decryption rather than signing. Threshold decryption is appropriate for escrow systems (recover data only with t parties), distributed PKI (no single CA holds the root key), and threshold wallets where transaction approval is by decryption of a blinded message. It wins over FROST/BLS when the protocol needs to protect ciphertexts, not produce signatures.

Real system embodying it: Tlock (threshold time-lock encryption, drand.love); threshold El Gamal in Helios voting (Benaloh 2009); PVSS schemes used in randomness beacons. The Pedersen DKG paper (P10) originally described threshold decryption as the primary use case.

Why rejected here: This project's deliverable is threshold signing (§1.1 out-of-scope: threshold decryption). Adding a decryption path would require an ElGamal ciphertext type, a partial decryption type, and a new verification equation — doubling the protocol surface without contributing to the learning objectives (§2.1).
