Back-of-Envelope Capacity Model

All numbers derived step-by-step from §4.1 System Constraints.

C1 — Per-share size. From §4.1: ShareId = 4 bytes, Scalar = 32 bytes. Per share: 4 + 32 = 36 bytes.

C2 — Share vector for n=255. n=255 shares × 36 bytes = 9,180 bytes ≈ 9 KB. Fits in L1 cache on any modern CPU.

C3 — Dealer polynomial memory. From §4.1: Polynomial memory = t × 32 bytes. At t=128 (practical maximum): 128 × 32 = 4,096 bytes = 4 KB. Zeroized after split; peak heap is one allocation.

C4 — Feldman commitment vector (broadcast size per DKG dealer). From §4.1: Commitment vector = t × 32 bytes (EC points compressed). At t=50: 50 × 32 = 1,600 bytes per dealer broadcast. At n=100 dealers: 100 × 1,600 = 160 KB total commitment material per DKG session per party.

C5 — DKG per-party message size. From §4.1: DKG per-party message size ≈ n × 128 bytes at n=255. Formula: n_peers × (32 bytes share + 32 bytes blinding + 33 bytes commitment_point_each + overhead) ≈ n × 128. At n=50: 50 × 128 = 6,400 bytes ≈ 6 KB per party per DKG round. Total DKG traffic per party: O(n) broadcast + O(n) unicast ≈ 2 × n × 128 bytes.

C6 — DKG total wire traffic (n=50, t=26). Total unicast messages: n × (n-1) = 50 × 49 = 2,450 messages × 128 bytes = 313 KB. Total broadcast: n × commitment_size = 50 × 1,600 = 80 KB. Grand total: ~393 KB for a 50-party DKG. Fits in a single HTTP/2 batch with no fragmentation concern.

C7 — Shamir split CPU: Horner evaluation. From §4.1 and §8.6.2: Horner cost = O(n × t) field multiplications. From §4.1: Shamir split latency (p50) < 1 ms at t=10, n=20. Field mul ≈ 10–50 ns (from §4.2 benchmark targets). At t=10, n=20: 200 field muls × 50 ns = 10 µs. At t=100, n=200: 20,000 × 50 ns = 1 ms — matches §4.1 budget.

C8 — Shamir reconstruct CPU: Lagrange. From §8.6.1: O(t²) field muls + t inversions. With batch inversion (Montgomery trick): O(3(t-1)) muls + 1 inv. At t=10: ~30 muls + 1 inv ≈ 30 × 50 ns + 500 ns = 2 µs. At t=128: 384 × 50 ns + 500 ns ≈ 20 µs. Well within the < 1 ms budget.

C9 — Feldman VSS verify per share. From §4.1: Feldman VSS verify (p50) < 5 ms at t=10. Verify cost: O(t) scalar muls (EC). From §4.1: scalar mul ≈ 60–200 µs. At t=10: 10 × 200 µs = 2 ms (without Pippenger batch). With batch multiscalar mul: ≈ 0.5 ms — matches budget.

C10 — FROST nonce commitment round (n=100). From §4.1: FROST round 1 per party < 10 ms. Each party: 2 scalar muls (D_i, E_i) = 2 × 200 µs = 400 µs. Binding factor: hash O(n) bytes per signer = 100 × 100 bytes = 10 KB hashed ≈ 0.1 ms. Group nonce: 100 scalar muls + 100 point adds ≈ 100 × 200 µs = 20 ms at aggregator (matches < 20 ms target in §4.1 for this step).

C11 — Proactive refresh bandwidth (n=50, t=26). Refresh mirrors DKG: O(n²) unicast messages. At n=50: 2,450 unicast × (32 bytes delta share + 1,600 bytes commitment) ≈ 2,450 × 1,632 = 4 MB total bandwidth per epoch. At one refresh per day (86,400 s), average bandwidth = 4 MB / 86,400 s ≈ 46 bytes/s — negligible for any transport.

C12 — Storage per key share. From §4.3: Storage per key share ≈ 100 bytes (KeyShare serialized). From §11.5: KeyShare = 4 (id) + 32 (secret_share) + 33 (public_share) + 33 (group_public) + 8 (params) + 8 (epoch) + AEAD tag (16) = 134 bytes. Matches §4.3 estimate. At n=255 parties, total key material cluster = 255 × 134 = 34 KB — trivial.
