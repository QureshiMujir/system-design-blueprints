In one paragraph

A distributed job queue lets application code hand off units of background work: a durable broker stores each job, defers or schedules it, hands it to one of many worker processes, retries failures with bounded backoff and dead-letters what keeps failing (§1). This design is a Go broker (cmd/jobqd) plus a producer/worker SDK (pkg/jobq) over Redis or Postgres, in the same class as Sidekiq, SQS, Celery and Faktory — a work-distribution primitive, not a log like Kafka (§1, §31). The one property that cannot be tuned away: the broker never loses an acknowledged job and never silently exceeds its stated at-least-once contract (§4, I1). Backend engineers embed it in a Go service; platform/SRE teams operate one shared multi-tenant broker (§1).

The problem, concretely

The first naive answer — a shared database table that every worker polls, with no broker process — is the blueprint's Alternative 2: it wins only in the simplest, low-volume deployments (under 100/s), because the polling interval breaks the reserve-latency target and there is no natural place to enforce fairness between tenants without logic duplicated in every consumer (§34, I9). The second naive answer — import a queue library without reading it — is where the incidents come from: mistuned visibility timeouts, undocumented exactly-once claims and unread dead-letter sets are, per the blueprint, the majority of on-call queue incidents (§2).

Now the hard case (§8.3): worker A reserves the job charge (idempotency key order-9182), charges the card, and its host is SIGKILLed before Ack. A worker holding a lease might already be dead, so the system must treat every lease as possibly stale at expiry (MM1) and hand the job out again — the charge handler runs twice. At-least-once is a consequence of the network being asynchronous and lossy, not a marketing choice, and the blueprint forbids even claiming exactly-once (§2, I5); the correctness burden moves to idempotent handlers or an idempotency layer (MM2, §8.7). On a shared broker, one tenant's high-priority flood can also starve another's low-priority work indefinitely (P11). The design answers with explicit leases, an idempotency-key path, bounded backoff, a dead-letter set and per-tenant fair scheduling (§1).

How it works, end to end

Follow one job through the boxes of §3's diagram:

  1. Producer SDK (pkg/jobq.Client) encodes the typed Job through the registered codec (ADR-11), attaches an idempotency key and W3C trace context, and calls the broker over gRPC (§3, §8.1). Bad input is rejected before any network call: a queue name outside [a-z0-9_-]{1,64} or a payload over the 1 MiB hard ceiling fails at the SDK boundary, and both errors come back together in one errors.Join (§8.4, I14).
  2. Frontend gRPC and Operator HTTP (internal/api/grpc, internal/api/http) are the only network entry points; both delegate to the same Engine so the logic exists once (§3).
  3. Engine (internal/broker/engine.go) validates again, because a raw gRPC producer can bypass the SDK check (§17.6); it applies middleware, generates the ULID and calls exactly one Storage method per operation, never touching adapter internals (P3, §17.2). A repeated idempotency key returns the existing ID with no error and no second write (I8, §17.5).
  4. Storage adapter (internal/storage/{redis,postgres,inmem,stub}) implements the full 13-method Storage interface and reports its Capabilities instead of narrowing the contract to the weakest adapter (§11, §14, P3): Lua scripts on Redis (§15.2), a FOR UPDATE SKIP LOCKED CTE on Postgres (§16.2).
  5. Scheduler (internal/broker/scheduler.go, elected through internal/leader) is the one single-writer part: exactly one leader promotes delayed jobs, sweeps expired leases and fires cron ticks (§3, P4, I4). Phase 0 elects it with an advisory lock; Raft is the registered deferral (ADR-12, §35).
  6. Worker process (pkg/workerpool) makes a Reserve call that blocks up to a deadline waiting for a job (long-poll), runs the handler in a bounded pool, and starts a heartbeat goroutine per job that renews the lease every LeaseDuration/3 (§3, §18.2, I2). The handler returns one of Ack | Retry | DeadLetter | Drop (§11); on SIGTERM the worker stops new pulls, finishes in-flight work up to drain_timeout, and keeps renewing leases while it drains (P10, I10).

Every primitive along that path emits a Prometheus metric and an OpenTelemetry span keyed by job_id, so an incident is debuggable from the operator surface alone (P9, I11).

The core ideas

A job's life is a six-state machine (§8.2)

Every job is in exactly one of PENDING, DELAYED, LEASED, COMPLETED, DEAD_LETTERED or CANCELED, and the engine's State type mirrors that diagram exactly (§8.2, §11). The transitions, in plain words:

From Event To
DELAYED the scheduler promotes it once ScheduledAt is reached PENDING
PENDING a worker reserves it LEASED
LEASED the worker acks COMPLETED
LEASED the worker returns retry (after backoff), or the lease expires and the sweep reclaims it PENDING, Attempt+1
LEASED dead-letter (including retry exhaustion at MaxAttempts, I7) DEAD_LETTERED
LEASED cancel CANCELED

SQS calls the reservation a visibility timeout and Faktory calls terminal failure bury; this project says lease and DEAD_LETTERED throughout (§8.2). Once a job is acked the record is gone — you cannot replay a completed job the way you replay a Kafka offset (MM3).

A lease is a bet with an expiry clock, granted atomically (§8.2, MM1, P13)

A reservation hands the worker a Lease{JobID, WorkerID, Token, IssuedAt, ExpiresAt}; the token is opaque, and every Storage method that accepts it compares it by exact match and never parses it (§11, T6). The default lease is 30 s, renewable up to 24 h (ADR-15, §4), and the worker's heartbeat renews it every LeaseDuration/3 to leave headroom for clock skew and network delay (§18.2, §18.6). Trace the blueprint's own worked example (§8.3):

  1. The producer enqueues charge with idempotency key order-9182; the broker persists it and returns the ID.
  2. Worker A reserves it; LeaseExpiresAt = now + 30 s.
  3. Worker A's host is SIGKILLed after charging the card, before Ack.
  4. The sweep reclaims it at LeaseExpiresAt; the job returns to PENDING with Attempt = 2.
  5. Worker B reserves it and re-runs the handler; the handler's own idempotency table, keyed by order-9182, sees the charge already happened and returns success without charging again.
  6. Worker B acks; state → COMPLETED. This sequence is the idempotency_double_run conformance fixture (§26).

Two invariants sit behind this: a lease never silently expires while its worker still runs (I2), and no two workers hold a valid lease on one job at once (I3). One way to break I2 is to stop the heartbeat goroutine before the handler goroutine has exited — a long handler then loses its lease exactly at LeaseDuration (§18.6).

I3 holds because every multi-step primitive — reserve, promote, sweep — is one Lua script on Redis or one statement on Postgres, never a client-side read-modify-write (P13). On Redis one queue's keys are hash-tagged {<queue>} onto one cluster slot, blocking reserve uses BLMPOP across the band keys, and WATCH/MULTI/EXEC is not enough (§15.2, §15.6); a crash between BLMPOP and the lease write is impossible because reserve.lua does both (§15.8). On Postgres, READ COMMITTED plus SKIP LOCKED suffices, SERIALIZABLE is unnecessary, LISTEN/NOTIFY payloads coalesce and drop under load (§16.6), and lock_timeout = 1s stops a stuck handler holding a row lock indefinitely (§16.4). Durability is delegated to Redis AOF everysec and Postgres WAL rather than reimplemented (§1, §15.7, §24).

At-least-once plus a bounded idempotency window (§8.7, ADR-14)

A caller-supplied string that makes repeated enqueues within a window resolve to one job (idempotency key) is stored as idem:<key> → job_id with a TTL equal to the dedup window — 24 h by default, configurable per tenant (§8.7, §4). A second Enqueue with the same key returns the existing job ID without a new write (I8), and the window survives completion, so a late producer retry after the job finished still gets the same ID (§8.7). The caller supplies the key because the caller controls the semantics (ADR-14). It is a poor man's exactly-once, bounded by a window: after the window expires the behaviour silently reverts to at-least-once (MM6). The window must expire — an index that never expires is an unbounded-memory bug disguised as a correctness feature (P12, FM-10). And a CI grep check forbids claiming exactly-once in code, docs and UI (I5, T1).

Retry with full jitter, then a dead-letter set (P5, ADR-13, ADR-16)

The default policy is exponential backoff with full jitter: delay = uniform(0, min(cap, base·2^attempt)) with base = 1 s, cap = 12 h and max_attempts = 25 (P5, ADR-13); Phase 7 checks drawn delays against the formula within 5% over 10,000 samples at a fixed seed (§19.4). A policy returns a negative delay to signal dead-letter at attempt exhaustion (§11, §19.2). The blueprint counts exhaustion two ways without reconciling them: I7 says retry attempts never exceed MaxAttempts and §36 defines Attempt as the reservation count, yet §19.4 says a MaxAttempts=25 job dead-letters "on the 26th failure, never the 25th or 27th", and the §19.5 exhaustion fixture fails a job 26 times.

Exhausted work goes to a durable, inspectable set, never a log line (dead-letter): it keeps the full attempt history (I6), is bounded, paginated and requeueable (P6), and is retained 30 days before archiving (ADR-16). A dead-letter handler chain — metric, webhook, audit log — runs without blocking the transition (§19.2). It is a forensic ledger, not a graveyard: the operator's next action is almost always "fix and replay" (MM7).

Priority bands with a starvation cap, plus per-tenant quotas (§8.6, I13, P11)

Each job sits in one of ten priority bands, 0–9 with a default of 5, and Reserve scans band 9 down to 0 (§8.1, §8.6). A per-(queue, tenant) counter tracks consecutive same-band reservations; at 100 (configurable) the scan restarts at band 5, bounding worst-case low-priority starvation to 100 × avg_handler_duration (§20.2, I13). §8.6 calls it a per-tenant counter and §20.8 says the cap is band-scoped, not tenant-request-scoped; the blueprint does not reconcile the scopes. Proof: a 100,001-reservation trace (§15.4), and ≥ 1 low-priority reservation per 100 high-priority ones in a 3-tenant skewed-load scenario (§20.4). Bands are per queue, so a noisy tenant sharing a queue with a quiet one needs a second mechanism: an optional per-tenant MaxConcurrentLeases quota, checked at Reserve in the same atomic storage operation as the lease grant, never check-then-act (§20.2, §20.6), and answered with an ErrBackpressure-class rejection (§20.4). Fairness is a scheduling problem, not a queue-depth problem (MM4).

One scheduler leader, many reservers (P4, I4, I12)

Delay-promotion, sweep and cron ticks run under exactly one elected leader (I4); reservation stays many-writer, serialized by the storage adapter (P4). Phase 0 elects with a Postgres session-scoped lock (advisory lock, pg_try_advisory_lock): of two brokers trying at the same tick, exactly one succeeds and the loser retries next tick (§16.2, §16.8, ADR-12). The cost is an availability window: if the leader crashes mid-tick, the lock's session TTL expires and a new leader is elected within one TTL period (MM8, §19.9). A tick straddling that handover could fire twice, so each tick enqueues under cron:<name>:<bucket> — a truncated timestamp, one minute by default — and the dedup index absorbs the duplicate (I12, §36). The blueprint's derivation: 1 s / 60 s ≈ 1.7% raw double-fire probability per handover, 0% observed with the key; the gate is 0 double-enqueues across 10 simulated handovers (§32 item 8, §19.4). Electing by timestamp comparison is a classic split-brain generator (T4, §19.6).

The trade-offs — where engineers disagree

Language: Go (ADR-01)

Chosen: Go 1.22+, because the goroutine model fits the worker pool — one goroutine per in-flight lease — context gives cancellation propagation for free, and the closest prior art (asynq) is Go (ADR-01, §1). Rejected: Rust, Java. When the rejected choice is right: Rust wins when the handler ecosystem is Rust-native and GC pauses are unacceptable at sub-ms tails (ADR-01).

Default store: Redis 7 (ADR-03)

Chosen: Redis 7, for throughput at §4's ceiling (ADR-03). Rejected: Postgres-only, Kafka. When the rejected choice is right: Postgres wins when the operator already runs it and cannot add another stateful service (ADR-03). The Postgres adapter is still built as a full adapter that passes every applicable conformance bucket (§16.3).

Leader election: advisory lock now, Raft later (ADR-12)

Chosen: an advisory lock in Phase 0, with Raft as the deferred upgrade, because there is no extra cluster to operate at Phase 0 (ADR-12, §35). Rejected: etcd, ZooKeeper, Consul. When the rejected choice is right: etcd or ZooKeeper win once more than one coordination service already exists in the deployment (ADR-12).

Retry policy: exponential full jitter (ADR-13)

Chosen: full jitter, base 1 s, cap 12 h, max 25 attempts — rationale: the AWS Architecture Blog result and its uniform spread (ADR-13). Rejected: linear, fixed, decorrelated jitter. When the rejected choice is right: fixed delay wins for handlers with a known, narrow recovery window, e.g. a 5 s cache refresh (ADR-13). The blueprint separately warns against reaching for decorrelated jitter without measuring (§19.6).

Idempotency: an application-supplied key (ADR-14)

Chosen: the caller supplies the key and gets a 24 h dedup window, because the caller controls the semantics (ADR-14). Rejected: a server-generated key, a content hash. When the rejected choice is right: a content hash wins when the caller cannot supply a stable key but payload identity is sufficient (ADR-14).

Roads not taken (§34, §35)

A log-based replay queue (Kafka-shaped). Wins when multiple independent consumers must replay the same stream at their own offsets (fan-out, reprocessing, event sourcing). Rejected because a log has no native "this consumer took ownership of this record" primitive, and offset commits as a proxy for ack give no per-record retry or dead-letter semantics (§34, §31).

A stateless shared-table polling queue. Wins where a broker process is operationally unwelcome and volume is under 100/s (early Celery database backends, Django-Q). Rejected because polling latency violates the reserve p99 target and there is no natural place for per-tenant fairness (§34, I9).

An actor-supervision-tree queue (BEAM/OTP-shaped, Oban). Wins on a runtime with cheap preemptive process isolation and built-in supervision. Rejected because Go has no native let-it-crash semantics; reimplementing OTP's runtime in Go is a worse trade than explicit panic recovery (§34, §18.2).

The deferred register. Multi-broker sharding (un-deferred once single-shard throughput exceeds the 100k enqueue/s ceiling), Raft leader election (once the rank-37 Raft library hits v1.0), a hosted multi-tenant control plane, and SDK-layer payload encryption at rest (§35).

What must never be false

  • I1 — every acked job was durably persisted before Ack succeeded; ack/positive bucket, jobq_ack_total (§7).
  • I2 — a lease never silently expires while its worker still runs; a gap in jobq_lease_renew_total is the tell (§7).
  • I3 — no two workers hold a valid lease on one job at once; jobq_reserve_conflict_total must stay 0 (§7).
  • I4 — at most one scheduler leader promotes, sweeps or ticks; the jobq_scheduler_leader leader-count gauge (§7).
  • I5 — the broker never claims exactly-once in code, docs or UI; a grep -i "exactly.once" check fails CI (§7).
  • I6 — a dead-lettered job always carries its full attempt history; dead_letter/list bucket, jobq_deadletter_total (§7).
  • I7 — retry attempts never exceed MaxAttempts; retry/exhaustion bucket, jobq_retry_attempt histogram (§7).
  • I8 — an idempotency key resolves to exactly one job ID within its window; idempotency/dedup, jobq_idem_conflict_total (§7).
  • I9 — reserve p99 on an idle queue stays under 50 ms; benchmark gate M4, jobq_reserve_latency_seconds (§7, §28).
  • I10 — graceful shutdown never drops an in-flight job; shutdown/no_drop, jobq_shutdown_dropped_total must stay 0 (§7).
  • I11 — every state transition emits a trace span keyed by job_id; span count is compared with transition count (§7).
  • I12 — a cron tick never double-enqueues across a leader handover; cron/idempotent, jobq_cron_dup_total must stay 0 (§7).
  • I13 — priority-band starvation is bounded by the configured skip count; reserve/priority, jobq_band_skip_total (§7).
  • I14 — a payload never exceeds the configured maximum size; enqueue/negative, jobq_oversized_rejected_total (§7).

Each invariant has exactly one assertion in a deterministic simulator that drives the engine against the inmem adapter on a virtual clock with injected crash-mid-handler, lease-loss and leader-handover events, so a broken invariant fails one named test (§7, §26).

What breaks in production

  • FM-1 — a poison message. A handler bug only one payload triggers crashes every worker that touches it; the retry count on one job_id spikes. The broker dead-letters it at MaxAttempts (I7); the operator inspects the payload, patches the handler and requeues (I6, §23).
  • FM-2 — a broker process crashes. OOM, an escaped panic or host failure; health checks fail and jobq_engine_op_duration_seconds shows a gap. Clients reconnect to the next replica within the RTO of < 5 s; nothing manual is normally required (§23, §4).
  • FM-4 — the storage layer crashes mid-write. A disk failure or a kill during a Lua script or CTE; the adapter health check fails. One script or statement per primitive means no partial write (P13), so RPO is 0 for acked jobs; the operator restores from replica or AOF (§23, §4).
  • FM-5 — a lease leak. Jobs sit LEASED forever because the sweep is disabled or the scheduler leader is down; jobq_scheduler_leader == 0 sustained is the alert. Failover re-elects and the sweep resumes; otherwise the operator triggers a sweep from the CLI (§23).
  • FM-6 — a dead-letter flood. An upstream dependency outage makes handlers fail en masse; jobq_deadletter_total spikes. The dead-letter handler chain still fires its metric and webhook; the operator pauses the queue and requeues in bulk once the dependency recovers (§23).
  • FM-7 — a cron tick fires twice across a leader handover. A handover lands in a tick window without idempotency; jobq_cron_dup_total rises above 0 (I12). The cron:<name>:<bucket> key absorbs the duplicate; the cron-tick plus leader-handover timeline is the forensic view (§23).
  • FM-8 — one tenant is starved. A quota misconfiguration or a missing starvation cap; jobq_tenant_reserve_rejected_total sits at 100% for one tenant. The starvation cap forces the band-scan reset (I13) and the operator adjusts the quota (§23, §20.9).
  • FM-10 — the idempotency index grows without bound. The dedup window was set to never expire; a storage memory-growth alert fires. TTL enforcement at the storage layer (P12, ADR-14) is the automatic guard; the operator sets a finite window (§23).

Threats a reader should know (§22): T1 — docs claiming exactly-once, encouraging skipped dedup logic; a CI grep forbids the phrase (I5). T3 — a Resque-style implicit lease timeout that loses jobs on slow handlers; answered by explicit leases plus renewal (P2, I2). T4 — split-brain double-scheduling from timestamp-comparison election; answered by the advisory lock or Raft, detected by the leader-count gauge above 1 (I4). T5 — an enqueue flood from a compromised producer; answered by backpressure (P7) and rate limiting, detected on jobq_queue_depth. T6 — a forged or guessed lease token; answered by a large opaque token compared by exact match, counted by jobq_lease_token_mismatch_total.

How it compares

  • AWS SQS made the queue fully managed and opaque, trading operator visibility for zero operational burden; it wins whenever a team has no appetite to run broker infrastructure. Its visibility timeout is this project's lease; its FIFO mode is effectively-once per window (§31).
  • RabbitMQ made routing — exchanges and bindings — a first-class, flexible concept, with ack/nack delivery and quorum-queue replication; it wins when complex fan-out/fan-in routing topologies matter more than raw throughput (§31).
  • Apache Kafka keeps the log after consumption so consumers replay at their own offsets; it wins when consumers need independent offsets or reprocessable data — the case this project does not target, since a log has no native per-record ownership primitive (§31, §34).
  • Temporal makes the workflow itself durable through deterministic replay, giving exactly-once workflow execution; it wins when a "job" is really a multi-day saga with compensating actions rather than a single unit of work (§31).

Questions to test yourself

  1. Why does the broker never claim exactly-once, and what specific network failure mode makes that claim false regardless of implementation cleverness? (§7 I5, §22 T1) — Hint: start from §2's "delivery-semantics fault line" and the SIGKILL step of §8.3.
  2. Trace the full sequence of state changes when a worker host is SIGKILLed mid-handler holding a Redis lease — name every component involved. (§8.3, §18.9) — Hint: §8.3's six steps and the lease-sweep in §3's scheduler box carry the trace.
  3. Why does the scheduler need a single leader (I4) but the worker pool does not, and what invariant would break if reservation itself required a leader? (§7, §3) — Hint: P4 in §6 names what serializes reservation instead of a leader.
  4. What would break if the lease-renewal heartbeat fired at LeaseDuration instead of LeaseDuration/3, and which two sections independently protect against that mistake? (§18.6, §4) — Hint: read the §18.6 pitfalls alongside the §4 default-lease row.
  5. Trace a cron tick that straddles a leader handover through the collision-probability derivation — what makes the observed double-enqueue rate zero despite a nonzero raw probability? (§19, §32) — Hint: §32 item 8 gives the ratio; I12 in §7 names the mechanism.

If you only remember three things

A lease is a bet with an expiry clock, so any job may be delivered twice, and an idempotent handler or an idempotency layer is what makes that harmless (MM1, MM2). Every multi-step operation is one Lua script or one SQL statement at the storage layer, which is what keeps two workers from holding a valid lease on the same job (P13, I3). Exactly one leader schedules while many workers reserve, retries are capped with full jitter, and what finally fails lands in a dead-letter set you can requeue from (P4, P5, MM7).

Words used here

  • Lease — the explicit, renewable reservation record (JobID, WorkerID, Token, ExpiresAt) a worker holds instead of an implicit visibility timeout (§36).
  • Heartbeat — the periodic lease-renewal call a worker makes while it holds a lease (§36).
  • Sweep — the scheduler action that reclaims jobs whose lease has expired (§36).
  • Long-poll — a Reserve call that blocks up to a deadline waiting for an available job (§36).
  • At-least-once — a job may run more than once but never zero times (§36).
