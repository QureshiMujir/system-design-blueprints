Project Number: 38

Project Name: Distributed Job Queue

Owner: Mujir Qureshi

1. Goal & Scope

Build a distributed, horizontally-scalable job queue — a durable broker plus a worker-pool protocol — that lets application code enqueue units of background work, defers or schedules them, delivers each at-least-once with an idempotency-key path to effectively-once, retries failures with bounded exponential backoff, dead-letters exhausted work, enforces per-tenant fairness, and exposes every internal state to an operator. The design class is Sidekiq / AWS SQS / Celery / Faktory; the queue is a work-distribution primitive, not a log (contrast Kafka, §31).

Phase-0 deliverable — numbered modules:

  1. pkg/jobq — producer/consumer SDK: Job, Client, Worker, Handler, Result.
  2. internal/codec — protobuf + CBOR wire encoders (ADR-11).
  3. internal/storage — Storage interface plus redis, postgres, inmem, stub adapters.
  4. internal/broker — engine (enqueue/reserve/ack/retry/cancel), lease accounting, scheduler.
  5. pkg/workerpool — bounded-concurrency handler pool with lease-renewal heartbeat.
  6. internal/leader — advisory-lock leader election (Raft upgrade deferred, §35).
  7. internal/api/grpc, internal/api/http — frontend and operator surfaces.
  8. conformance/runner — deterministic pass/fail/deferred harness per storage adapter.

System boundaries.

  • Provides: durable enqueue, at-least-once delivery, visibility-timeout leases, retry with backoff, dead-letter, priority bands, delayed/cron jobs, per-tenant fair scheduling, horizontal broker/worker scaling, full observability.
  • Delegates: durable storage engine correctness to Redis/Postgres themselves (the queue does not reimplement WAL or replication); TLS termination to the deployment's ingress; authentication identity to an external IdP (the queue only checks bearer tokens/mTLS certs).
  • Does NOT provide: exactly-once delivery (impossible over an unreliable network, I5), ordered cross-partition delivery, a general stream/replay log (that is Kafka's job, §31), a UI for end users (only for operators).

Non-goals. Competing with Kafka's log-and-replay model; supporting non-idempotent side-effecting handlers without an application-level idempotency story; single-digit-millisecond enqueue latency at the 10 Gbps tier (this is a queue, not an in-memory ring buffer).

Deployment model. One or more broker processes (cmd/jobqd) fronting a shared storage backend (Redis or Postgres), one or more worker processes embedding pkg/jobq.Worker, horizontally scaled independently. Phase 0 runs a single broker shard; Phase-deferred multi-shard routing is PhaseDeferred("§29").

Target users/operators. Backend engineers embedding background work into a Go service; platform/SRE teams operating a shared multi-tenant broker; the on-call engineer diagnosing a stuck queue at 3 a.m. from the operator HTTP API alone.

What later phases unlock. Multi-shard consistent hashing (§29, §35), Raft-based scheduler leader election replacing the advisory lock (§35), a hosted multi-tenant control plane (§35).

Language. Go 1.22+. Rationale: goroutines map directly onto the worker-pool concurrency model (one goroutine per in-flight lease, cheap enough at 10k-per-process scale, §4); the context package gives cancellation-propagation for free, which the lease-cancel path (§13 Phase 1 companion, internal/broker/engine.go) depends on; the closest prior art (asynq) is Go, so operational idioms transfer. Rejected: Rust (superior memory control, but the worker-handler ecosystem this queue targets is overwhelmingly Go/Python/Ruby, and Rust's async-runtime fragmentation — Tokio vs async-std — would leak into the public Handler trait); Java (JVM warm-up and GC pause tails directly fight the p99-latency invariant I9; also a heavier operational footprint per worker host than Go's static binaries).

Prerequisites. At-least-once vs exactly-once semantics; Redis list/sorted-set/Lua scripting; Postgres MVCC and SELECT … FOR UPDATE SKIP LOCKED; exponential backoff with jitter; leader election via advisory lock or consensus; Prometheus/OpenTelemetry conventions.

Estimated timeline. Phase 0 (repo skeleton + correctness kernel): 1 week. Phases 1–4 (types, storage abstraction, Redis + Postgres adapters): 3 weeks. Phases 5–9 (engine, worker pool, retry/scheduler, fairness, operator surfaces): 5–7 weeks. Full system (Phases 0–9): 10–12 weeks; multi-shard + Raft (deferred, §35): additional 6–8 weeks, out of Phase-0 scope.

Deferred features are flagged inline with a PhaseDeferred(anchor) marker and consolidated in the Deferred Features Register (§35): multi-broker sharding PhaseDeferred("§29"), Raft leader election PhaseDeferred("§20.2"), hosted multi-tenant control plane PhaseDeferred("§35"), SDK-layer payload encryption at rest PhaseDeferred("§22").

2. Why Build This

  • Silent-cost domain. Every production system imports a queue without reading its source; mistuned visibility timeouts, undocumented exactly-once claims, and unread dead-letter sets are the majority of on-call queue incidents. Building one from scratch forces every implicit assumption into writing.
  • Teaches the delivery-semantics fault line. At-least-once vs exactly-once is not a marketing choice — it is a consequence of the network being asynchronous and lossy (I5, Kreps NetDB 2011, Treat's "You Cannot Have Exactly-Once Delivery"). A job queue is the cleanest place to internalize this because the failure is directly observable (duplicate side effects).
  • Teaches lease-based coordination. Visibility timeouts/leases are the same primitive as Chubby's session leases (Burrows OSDI 2006) and Raft's leader lease (Ongaro & Ousterhout
    1. — a job queue is the smallest system where this pattern can be built and broken safely.
  • Teaches fairness under contention. Multi-tenant priority scheduling with starvation control is the same problem operating-system schedulers solve; building it here transfers directly to rank-37 (Raft) and rank-40 (Service Discovery) scheduling logic.
  • Cross-links. Rank 59 (Distributed Cache) reuses this queue for warm-up jobs. Rank 40 (Service Discovery) reuses it for heartbeat-driven registration retries. Rank 37 (Raft) supplies the Phase-deferred leader-election upgrade (§20.2, §35). Rank 27 (Kafka Messaging) is the log-shaped sibling this project explicitly is not (§31).
  • Calibration value. A correct queue is falsifiable in a way most "backend CRUD" work is not: the conformance suite (Phase 9, §21; harness, §26) either proves at-least-once and lease-expiry hold under fault injection, or it does not.

What Mastery Looks Like

  • Can state, from memory, why exactly-once delivery is impossible over an asynchronous network and defend it against a marketing claim — built in Phase 1 (§13), tested in §26.
  • Can design a lease-renewal heartbeat that survives clock skew and crash-mid-handler without losing or duplicating a job beyond the documented at-least-once contract — Phase 6 (§18).
  • Can implement SELECT … FOR UPDATE SKIP LOCKED correctly and explain why LISTEN/NOTIFY alone is not a substitute — Phase 4 (§16).
  • Can design starvation-bounded priority scheduling across untrusted tenants — Phase 8 (§20).
  • Can reason about the CAP-theorem tradeoff a broker makes on failover and write the corresponding invariant table (§7) and threat model (§22) entries.
  • Can defend every ADR's rejected alternative with a concrete regime where it would win instead (§9 ADR 6th column) rather than reciting the locked choice as obviously correct.

Producer SDK — encodes a typed Job through the registered codec (ADR-11), attaches an idempotency key and trace context, and calls the frontend over gRPC (ADR-02). Frontend gRPC / Operator HTTP — the only network entry points; both delegate to the same Engine so business logic exists once. Engine — validates, dispatches middleware, and calls exactly one Storage method per operation (P3); it never touches adapter internals. Storage Adapter — pluggable persistence (P3, ADR-03/04/05); each adapter implements the full Storage interface (§11) and reports its Capabilities. Scheduler — single leader (P4, I4) that promotes delayed jobs, sweeps expired leases, and fires cron ticks; leader election is an advisory lock in Phase 0, Raft in the deferred upgrade (§20.2). Worker Process — pulls via long-poll Reserve, runs handlers in a bounded pool, renews the lease heartbeat (P2, I2), and drains gracefully on SIGTERM (P10). All later sections keep every name in this diagram identical to the Repository Layout (§10) and Core Schema & Types (§11) — the terminology lock.

6. Design Principles

  1. At-least-once by default; idempotency is the application's contract (P1). The broker never claims exactly-once. Tradeoff: applications must supply idempotency keys or idempotent handlers. Operational implication: the SDK docstrings and operator UI repeat this in plain language. Violating it (claiming exactly-once) misleads operators into skipping dedup logic and causes double side effects (§22 T1).
  2. Visibility timeouts are leases, and leases are explicit (P2). Every reservation carries lease_expires_at; workers renew on a heartbeat (I2). Tradeoff: renewal traffic scales with in-flight count. Operational implication: lease state is inspectable from the operator UI. Violating it (implicit timeouts, Resque-style) silently drops in-flight work on slow handlers.
  3. Storage is pluggable but not lowest-common-denominator (P3). Storage is a Go interface (§11); adapters expose Capabilities() rather than narrowing the contract. Tradeoff: the engine must branch on capability gaps. Violating it collapses every adapter to the weakest one's feature set.
  4. Single-leader for the scheduler; multi-leader for workers (P4). Delay-promotion, sweep, and cron ticks run under one elected leader (I4); reservation is many-writer, serialized by the storage adapter. Violating it (timestamp-comparison election) produces split-brain double-scheduling (§22 T4).
  5. Retries are exponential with full jitter, and capped (P5). delay = uniform(0, min(cap, base·2^attempt)), base=1s, cap=12h, max_attempts=25 (ADR-13). Tradeoff: custom policies are pluggable but the default is non-negotiable without an ADR. Violating it (unbounded retry) starves the queue on a permanently-broken handler.
  6. Dead-letter is durable and inspectable, never a log line (P6). The dead-letter set is bounded, paginated, requeueable, and carries full retry history (ADR-16). Violating it loses the operator's only forensic trail for exhausted work.
  7. Backpressure is explicit (P7). Producers may opt into ErrBackpressure at a depth threshold (Nygard ch. 5); silent unbounded buffering past the threshold is forbidden absent an explicit operator opt-out. Violating it turns a transient outage into an unbounded queue.
  8. The wire format is typed (P8). Submit[T] encodes through a registered codec (ADR-11); interface{} in the SDK without justification is rejected in review. Violating it pushes runtime type errors into production handlers.
  9. Observability is not opt-in (P9). Every broker primitive emits a Prometheus metric and an OTel span keyed by job_id (I11). Violating it makes an incident undebuggable from the operator surface alone.
  10. Graceful shutdown drains (P10). SIGTERM stops new pulls, finishes in-flight up to drain_timeout, renews leases throughout the drain. Violating it drops in-flight jobs on every deploy.
  11. Fairness is per-tenant, bounded, and auditable (P11). A starvation cap (§19) prevents one tenant's high-priority flood from starving another tenant's low-priority work indefinitely. Violating it turns a shared broker into a noisy-neighbor incident generator.
  12. Idempotency windows expire (P12). The dedup index (ADR-14) has a TTL; an index that never expires leaks memory until the process dies. Violating it is an unbounded-memory bug disguised as a correctness feature.
  13. Every cross-adapter primitive is atomic at the storage layer (P13). Multi-step operations (reserve, promote, sweep) are one Lua script (Redis) or one statement (Postgres) — never client-side read-modify-write. Violating it reintroduces the races the adapter exists to prevent (I3).

8.2 State machine (delivery semantics)

Show the original text diagram
PENDING --reserve--> LEASED --ack-------------> COMPLETED
   ^                    │  \--retry(backoff)---> PENDING (attempt++)
   │                    │  \--dead-letter------> DEAD_LETTERED
DELAYED --promote-------┘   \--lease-expiry-----> PENDING (sweep, attempt++)
   (scheduled_at reached)     \--cancel----------> CANCELED

Terminology: SQS calls the lease a visibility timeout; Faktory calls the terminal-failure transition bury; this project names the primitive lease (vocabulary rationale below, I2) and the terminal-failure state DEAD_LETTERED to match ADR-16.

8.3 Worked example — at-least-once double delivery

  1. Producer calls Enqueue(Job{Type:"charge", IdempotencyKey:"order-9182"}). Broker persists, returns ID 01J...Z.
  2. Worker A reserves it; LeaseExpiresAt = now+30s.
  3. Worker A's host is SIGKILLed mid-handler (after charging the card, before Ack).
  4. Sweep reclaims at LeaseExpiresAt; job returns to PENDING, Attempt=2.
  5. Worker B reserves and re-runs the handler. The handler's own idempotency table (keyed by order-9182) recognizes the charge already happened and returns success without a second charge.
  6. Worker B calls Ack. State → COMPLETED. This sequence is exactly the idempotency_double_run conformance fixture (§26).

8.4 Malformed-input example

Enqueue(Job{Queue:"My Queue!", Payload: 2MiB}) — rejected at the SDK boundary before any network call: Queue fails [a-z0-9_-]{1,64} (space and ! are illegal), and Payload exceeds the 1 MiB hard ceiling (§4). The broker never sees a partial write; ErrInvalidQueue and ErrPayloadTooLarge are both returned in one errors.Join so the caller sees every violation at once. Fixture: conformance/fixtures/negative/enqueue_malformed.json.

8.5 Failure-path example — storage adapter outage

Redis becomes unreachable mid-Reserve. The circuit breaker (Phase 3, §15.10) opens after 5 consecutive failures within 2 s; Capabilities() reports Degraded=true; the engine returns ErrStorageUnavailable to new Enqueue/Reserve calls while in-flight leases already held by workers remain valid (no data loss, I1) until the breaker half-opens and probes recovery. Fixture: conformance/fixtures/negative/storage_outage_reserve.json.

8.6 Priority and fairness model

Bands 0–9, reserve scans band 9 → 0. A per-tenant skip counter (I13) forces the scan to restart at band 5 after 100 consecutive same-band reservations, bounding worst-case starvation of a low-priority tenant to 100 × avg_handler_duration.

8.7 Idempotency key and dedup window

idem:<key> → job_id, TTL = dedup window (24 h default, ADR-14). A second Enqueue with the same key returns the existing job_id without a new write (I8). The window survives completion so a late producer retry after the job finished still returns the same ID (Vogels 2009, eventual convergence of the dedup view).

11. Core Schema & Types

Signatures only, per the No-Code Rule (§4 of the standard). Every type below appears on disk in the named file; ownership/mutation/concurrency/persistence/serialization notes are inline.

// pkg/jobq/job.go — immutable once enqueued except broker-owned fields below.
type Job struct {
  ID string                 // owner: broker; set once at Enqueue; immutable after
  Queue, Type string         // owner: producer; immutable
  Payload []byte             // owner: producer; opaque to broker; ≤ MaxPayloadSize
  PayloadCodec string        // owner: producer; selects Encoder (ADR-11)
  Priority uint8             // owner: producer; read by reserve band-scan (I13)
  ScheduledAt, Deadline time.Time
  MaxAttempts, Attempt uint8 // Attempt: owner broker, incremented per reservation
  RetryStrategy string       // selects RetryPolicy by name
  LeaseDuration time.Duration
  IdempotencyKey, Tenant string
  EnqueuedAt, LeaseExpiresAt, CompletedAt time.Time // owner: broker
  LastError string
  TraceID, SpanID string
}

// Capabilities: adapter self-report, read by engine per Enqueue/Reserve dispatch (P3).
type Capabilities struct {
  SupportsDelay, SupportsPriority, SupportsCron bool
  SupportsIdempotency, SupportsLeaseRenewal bool
  MaxQueueDepth uint64
  MaxJobSizeBytes int
  ConsistencyModel string // "strong" | "eventual"
  Degraded bool
}

// Outcome: handler return discriminant. Concurrency: read-only after construction.
type Outcome int
const ( OutcomeAck Outcome = iota; OutcomeRetry; OutcomeDeadLetter; OutcomeDrop )

type Result struct {
  Outcome Outcome
  Err error
  RetryIn time.Duration // honoured iff Outcome==OutcomeRetry; zero → policy decides
  Attribute map[string]string
}

// Handler: user-implemented. Concurrency: invoked from a bounded pool goroutine (§17).
type Handler interface { Handle(ctx context.Context, j *Job) Result }
type HandlerFunc func(ctx context.Context, j *Job) Result // adapts a func to Handler

// Client: producer SDK, safe for concurrent use.
type Client interface {
  Enqueue(ctx context.Context, j Job) (id string, err error)
  Schedule(ctx context.Context, j Job, when time.Time) (id string, err error)
  Periodic(ctx context.Context, queue, jobType, cronSpec string, payload []byte) error
  Cancel(ctx context.Context, id string) (CancelResult, error)
  Close() error
}

// Worker: consumer SDK. Not safe for concurrent Run calls on the same instance.
type Worker interface {
  Register(jobType string, h Handler)
  Run(ctx context.Context) error
  Shutdown(ctx context.Context) error // graceful drain, honours P10
}
// internal/broker/lease.go — broker-owned; never constructed by producers/workers directly.
type Lease struct {
  JobID, WorkerID, Token string // Token: opaque, compared by exact match (§22 T6)
  IssuedAt, ExpiresAt time.Time
}

// internal/broker/engine.go — State: canonical, mirrors §8.2's diagram exactly.
type State int
const (
  StatePending State = iota; StateDelayed; StateLeased
  StateCompleted; StateDeadLettered; StateCanceled
)

// internal/storage/adapter.go — the contract every adapter implements (P3).
type Storage interface {
  Enqueue(ctx context.Context, j *jobq.Job) (id string, conflict bool, err error)
  Reserve(ctx context.Context, queue, workerID string, lease, wait time.Duration) (*jobq.Job, *Lease, error)
  Ack(ctx context.Context, jobID, leaseTok string) error
  RenewLease(ctx context.Context, jobID, leaseTok string, ext time.Duration) (time.Time, error)
  Retry(ctx context.Context, jobID, leaseTok string, after time.Duration, lastErr string) error
  DeadLetter(ctx context.Context, jobID, leaseTok, reason string) error
  Cancel(ctx context.Context, jobID string) (State, error)
  Peek(ctx context.Context, queue string, limit int) ([]*jobq.Job, error)
  PromoteDelayed(ctx context.Context, queue string, now time.Time, batch int) (int, error)
  SweepLeases(ctx context.Context, now time.Time, batch int) (int, error)
  Stats(ctx context.Context, queue string) (Stats, error)
  Capabilities() jobq.Capabilities
  Close() error
}

type RetryPolicy interface {
  NextDelay(attempt uint8) (delay time.Duration) // negative signals dead-letter
}

type LeaderElection interface {
  Campaign(ctx context.Context, role string) (token string, err error)
  Resign(ctx context.Context, role, token string) error
  Renew(ctx context.Context, role, token string) error
}

// internal/middleware/chain.go — both producer- and worker-side chains implement this.
type Middleware interface { Apply(next Handler) Handler }

// internal/codec/codec.go — ADR-11.
type Encoder interface {
  Encode(v any) (data []byte, codecName string, err error)
  Decode(codecName string, data []byte, v any) error
}

  • Calling time.Now() inside the codec — the codec must be deterministic; time is caller-supplied (breaks the round-trip property test's reproducibility).

  • A Job with Payload == nil vs Payload == []byte{} — the codec treats both as zero-length, never as an encoding error.

  • A codec name in PayloadCodec that no registered Encoder recognizes — Decode returns ErrCapabilityNotSupported, not a panic.

13.9 Failure Analysis

A codec bug that silently drops a field is the worst-case failure here: it is invisible until a downstream consumer misbehaves. 13.10 Operational Notes

internal/proto/gen/ is committed, not generated at build time, so a broker and a producer on different commits can still interoperate as long as both regenerate before their next deploy; docs/adr/ADR-11.md documents the codec-version compatibility table referenced in §25.

15. Phase 3 — Redis Adapter (Lua-Scripted Primitives)

16. Phase 4 — Postgres Adapter (SKIP LOCKED)

16.1 Objectives

Implement Storage against Postgres 14+ using SELECT … FOR UPDATE SKIP LOCKED for reservation (ADR-04, Petrov ch. 5), avoiding both LISTEN/NOTIFY reliability gaps and SERIALIZABLE overhead.

16.2 Detailed Implementation Steps

  • Schema: jobs, leases, dead_letters tables; index on (queue, priority DESC, scheduled_at ASC) for the reserve query; partial index on idempotency_key WHERE idempotency_key IS NOT NULL for I8.
  • Reserve as one WITH … FOR UPDATE SKIP LOCKED CTE followed by an UPDATE … RETURNING (signature only, §11; no runnable SQL body committed to this document per the No-Code Rule — the query shape is documented in docs/adr/ADR-04.md).
  • Promotion and sweep as scheduled statements guarded by a Postgres advisory lock (pg_try_advisory_lock) so exactly one broker instance runs them (I4, P4).
  • Embedded SQL migrations under internal/storage/postgres/migrations/, applied by cmd/jobqd at start unless --skip-migrate.

16.3 Deliverable

The Postgres adapter passes every applicable conformance bucket; a migration test walks every schema version forward to head and back to initial without data loss.

16.4 Acceptance Criteria

  • 10,000 enqueue/s sustained (§28 M5); 5,000 dequeue/s sustained (§28 M8).
  • lock_timeout = 1s enforced by the adapter's connection-pool init, preventing a stuck handler from holding a row lock indefinitely (§17.6 pitfall).
  • Migration round-trip test: every version 1..N and back to 0, 0 data-integrity failures.

16.6 Pitfalls

  • Reaching for LISTEN/NOTIFY for reservation — NOTIFY payloads coalesce and drop under load; the reserve loop must poll with backoff and rely on SKIP LOCKED for correctness, not notification delivery (§5 book 4).
  • Omitting lock_timeout — a handler that holds a transaction open indefinitely poisons the queue for every other reserver on that row's neighbors in the index.

  • Two brokers both attempt pg_try_advisory_lock at the exact same tick — exactly one succeeds by Postgres's own lock semantics; the loser retries next tick (I4).
  • A migration applied against a database already at head — cmd/jobqd detects the current version and no-ops, never re-applies.

16.9 Failure Analysis

Postgres connection pool exhaustion: detected via jobq_pg_pool_wait_seconds histogram; contained to new reserve/enqueue calls; recovery is pool resize or read-replica offload for Peek/Stats (never for Reserve, which must hit the primary).

17. Phase 5 — Broker Engine (Enqueue / Reserve / Ack / Retry / Cancel)

17.1 Objectives

Build the business-logic layer between the public API and the Storage adapter (§3): request validation, capability dispatch, middleware invocation, and the single call site per operation that keeps the adapter opaque to the engine (P3, P13).

17.2 Detailed Implementation Steps

  • internal/broker/engine.go: Enqueue validates queue/type charset and payload size (I14), applies producer middleware, generates the ULID (§13), sets EnqueuedAt, calls Storage.Enqueue; on idempotency conflict (I8) returns the existing ID without an error.
  • Reserve accepts a long-poll deadline, dispatches to the adapter, applies worker-side middleware (trace-context propagation, I11), returns (*Job, *Lease).
  • Ack/RenewLease/Retry/Cancel each verify the lease token against the adapter's stored value before mutating state (I3); Cancel on a leased job invalidates the token so the worker's next call observes ErrLeaseExpired.
  • Every method emits one Prometheus counter and one OTel span (P9, I11).

17.3 Deliverable

The engine compiles against all four adapters, has unit tests against stub (interface-only, no I/O), and is wired into the gRPC frontend (internal/api/grpc).

17.4 Acceptance Criteria

  • 100% of engine unit tests pass against stub with 0 adapter-internal imports (enforced by tools/ifacecheck, §14.4).
  • Every engine method emits exactly one span per call, verified by tracing/correlation conformance bucket (I11).
  • Cancel on an in-flight lease propagates within one RenewLease cycle (≤ LeaseDuration/3, ADR-15).

18. Phase 6 — Worker Pool, Lease Heartbeats, Graceful Shutdown

18.1 Objectives

Implement the bounded worker pool (pkg/workerpool), the lease-renewal heartbeat (P2, I2), and graceful SIGTERM drain (P10) — the pattern Cox-Buday ch. 4–5 (§5) formalizes as pipeline-with-cancellation.

18.2 Detailed Implementation Steps

  • pkg/workerpool: MaxConcurrency bound per process (§4 ceiling, 10,000), per-handler-type concurrency caps configurable independently.
  • Reservation loop pulls at the rate the pool can absorb (backpressure applied internally, not just at the producer side, P7); on pull, starts a per-job heartbeat goroutine that renews the lease every LeaseDuration/3 (ADR-15 rationale: headroom for clock skew and network delay).
  • Middleware chain: tracing, structured logging, metrics, panic recovery, deadline-from-context — standard set applied to every handler invocation (P9).
  • Panic recovery converts a handler panic into Result{Outcome: OutcomeRetry, Err: recovered} and logs the stack trace at ERROR — panics are retryable, not terminal (§22 T8).
  • Graceful shutdown: on SIGTERM, stop new Reserve calls, wait up to drain_timeout for in-flight handlers, keep renewing leases throughout the wait (I10), then close the storage client.

18.3 Deliverable

cmd/jobq-worker runs registered handlers end-to-end; examples/hello demonstrates the full loop with zero external dependencies (ADR-05 in-memory adapter).

18.4 Acceptance Criteria

  • SIGTERM drains 1,000 in-flight jobs with 0 drops (§28 M11, I10).
  • Lease-renewal heartbeat fires at exactly LeaseDuration/3 ± 5% jitter under load, verified by a 10,000-lease soak test.
  • A handler panic never terminates the worker process; the process survives 1,000 injected panics in a fuzz loop.

18.6 Pitfalls

  • Renewing on a fixed schedule that does not divide LeaseDuration evenly — use /3 to leave headroom for clock skew (Kleppmann ch. 8, §5 book 1).
  • Treating panics as terminal — they are retryable; the next attempt succeeds once the triggering bug is fixed and redeployed.
  • Stopping the heartbeat goroutine before the handler's goroutine actually exits — long-running handlers lose their lease exactly at LeaseDuration if the heartbeat stops early.

18.7 Performance Concerns

10,000 concurrent leases means 10,000 heartbeat goroutines per worker process at the ceiling (§4); each renewal is one round trip to storage — batching renewals (grouping heartbeats due in the same 100 ms window into one adapter call) is required to hold the FD/syscall budget.

18.8 Edge Cases

  • drain_timeout shorter than the longest in-flight handler's remaining runtime — the worker logs a WARN and force-cancels via ctx cancellation at drain_timeout, converting the outcome to OutcomeRetry rather than silently dropping (I10, no partial-and-lost state).
  • Two heartbeats for the same lease racing due to goroutine scheduling jitter — the adapter's renew.lua/CTE is idempotent on the same token, so a duplicate renewal is a no-op, not a double-extension bug.

18.9 Failure Analysis

A worker host OOM-kills mid-drain: in-flight leases are not renewed after the kill; sweep reclaims them at their natural LeaseExpiresAt (§8.3 worked example applies unchanged); blast radius is bounded to that host's in-flight set, at-least-once (I1) still holds.

18.10 Operational Notes

jobq_worker_inflight gauge and jobq_worker_drain_seconds histogram are the deploy-time dashboard panels; a rolling deploy's runbook (docs/runbooks/worker-rolling-deploy.md) requires drain_timeout ≥ p99.9 handler duration measured over the prior 7 days.

19. Phase 7 — Retry Policy, Dead-Letter, Scheduler & Cron

19.1 Objectives

Implement the default backoff policy (ADR-13), dead-letter routing (ADR-16), and the single-leader scheduler that promotes delayed jobs and fires cron ticks (P4, I4, I12).

19.2 Detailed Implementation Steps

  • internal/broker/retry.go: RetryPolicy implementations; default ExponentialJitterPolicy{Base:1s, Cap:12h, Max:25} per ADR-13; NextDelay returns a negative duration to signal dead-letter at attempt exhaustion (I7).
  • internal/broker/deadletter.go: dead-letter routing after MaxAttempts; carries full attempt history (I6); a dead-letter handler chain (mirrors middleware, §18) runs for side effects (metric emission, webhook, audit log) without blocking the state transition.
  • internal/broker/scheduler.go: single leader via internal/leader (advisory lock in Phase 0, Raft deferred §20.2); on tick, promotes delayed jobs (PromoteDelayed, batched) and fires cron specs (robfig/cron/v3, ADR-06) with idempotency key cron:<name>:<bucket> so a leader handover mid-tick cannot double-enqueue (I12).
  • Cron spec grammar: POSIX crontab(5) 5-field plus optional 6th seconds field (§5 RFCs/Specifications).

19.3 Deliverable

The scheduler runs as a single elected leader; cron ticks and delay-promotion are observable via jobq_scheduler_leader and jobq_cron_tick_total; a dead-lettered job is inspectable via the operator surfaces built in Phase 9 (§21).

19.4 Acceptance Criteria

  • 0 double-enqueues across 10 simulated leader-handover events during a cron tick window (§28 M7, I12).
  • Retry-delay distribution matches the full-jitter formula within a 5% tolerance over 10,000 samples at a fixed seed.
  • A job at MaxAttempts=25 dead-letters on the 26th failure, never the 25th or 27th (I7).

19.6 Pitfalls

  • Cron leader election by timestamp comparison instead of an advisory lock/lease — a classic split-brain generator (§5 book 2, Kleppmann ch. 9).
  • Cron without the cron:<name>:<bucket> idempotency key — a leader change at the wrong instant double-enqueues (I12).
  • Reaching for "decorrelated jitter" without measuring — full jitter is the correct default for this workload (AWS Architecture Blog, ADR-13); a custom policy is opt-in, not default.

19.7 Performance Concerns

Delay-set promotion and lease sweep are both batched operations; an unbounded batch size risks a single scheduler tick blocking the storage adapter for other operations — batch size is tunable and defaults to 1,000 per tick.

19.8 Edge Cases

  • Clock skew between the scheduler leader and the storage server — cron bucket resolution (default: minute) must exceed the assumed skew bound (§4 NTP assumption, < 1 s) by a wide margin to avoid bucket-boundary double-fires.
  • A dead-letter handler chain entry that itself panics — recovered and logged, never blocks the dead-letter transition itself (transition happens first, side effects after).

19.9 Failure Analysis

Scheduler leader crashes mid-tick: the advisory lock's session TTL expires, a new leader is elected within one TTL period, delay-promotion and cron resume; the idempotency key (I12) absorbs any tick that straddles the handover.

19.10 Operational Notes

20. Phase 8 — Priority, Delay Queues & Fair Multi-Tenant Scheduling

20.1 Objectives

Implement priority bands with starvation control (I13) and per-tenant fairness (P11) so a shared broker cannot let one tenant starve another.

20.2 Detailed Implementation Steps

  • Band-scan reserve logic (§8.6): scans band 9→0; a per-(queue,tenant) counter tracks consecutive same-band reservations; at 100 (configurable), the scan is forced to restart at band 5, bounding worst-case low-priority starvation to 100 × avg_handler_duration (I13).
  • Per-tenant quota: an optional MaxConcurrentLeases per tenant, enforced at Reserve time by checking the tenant's current leased count before granting a new one — this is the multi-tenant fairness primitive (P11) distinct from priority bands (which are per-queue, not per-tenant).
  • PhaseDeferred("§20.2"): the leader-election upgrade from advisory lock to Raft (rank-37 dependency) is not built here; the advisory-lock leader from Phase 7 remains the Phase-0 mechanism. This subsection number is the deferral's registered anchor (§35).
  • Delay-set promotion tuning: per-tenant delay-set keys so one tenant's delayed-job backlog cannot delay another tenant's promotion batch (extends §19's batching to be tenant-fair).

20.3 Deliverable

A multi-tenant conformance scenario (3 tenants, skewed priority distributions) demonstrates bounded starvation and quota enforcement, with metrics broken out per tenant.

20.4 Acceptance Criteria

  • Low-priority tenant in a 3-tenant skewed-load scenario receives ≥ 1 reservation per 100 high-priority reservations (I13 bound verified empirically).
  • A tenant at its MaxConcurrentLeases quota receives ErrBackpressure-class rejection on further Reserve attempts, not silent queuing past the quota.
  • 0 cross-tenant lease leakage: a tenant's Reserve never returns another tenant's job (verified by 100,000-reservation fuzz run with tenant-tagged synthetic jobs).

20.6 Pitfalls

  • Implementing fairness only at the priority-band level and assuming it covers multi-tenancy — priority is per-queue; a noisy tenant sharing a queue with a quiet one needs the separate per-tenant quota (P11), not just band rotation.
  • Quota enforcement that races with concurrent Reserve calls from the same tenant — the quota check and the lease grant must be one atomic storage-layer operation (P13), not a check-then-act pair.

20.7 Performance Concerns

Per-tenant quota tracking adds one counter read/write per Reserve; at the 50,000 dequeue/s ceiling (§4) this must stay within the existing Lua-script/CTE atomicity unit rather than adding a second round trip.

20.8 Edge Cases

  • A tenant with zero jobs currently reserving from a queue shared with a saturated tenant — the starvation-cap reset (I13) must trigger even when the "starved" tenant has not attempted a reservation yet, since the cap is band-scoped, not tenant-request-scoped.
  • Tenant quota reconfigured downward while the tenant already holds more leases than the new quota — existing leases are honored to natural completion/expiry; only new reservations are blocked.

20.9 Failure Analysis

A misconfigured quota of 0 for an active tenant silently starves that tenant entirely; detection is a per-tenant jobq_tenant_reserve_rejected_total metric with alerting on a sustained 100% rejection rate; recovery is an operator config change, no restart required.

20.10 Operational Notes

Per-tenant dashboards in ops/grafana/ break out jobq_reserve_total, jobq_tenant_reserve_rejected_total, and band-skip counts by tenant label; docs/runbooks/tenant-starvation.md is the on-call playbook.

Incident response: named runbooks in docs/runbooks/ for every alert defined above (redis-adapter-degraded, postgres-adapter-lock-timeout, scheduler-no-leader, tenant-starvation, worker-rolling-deploy, engine-high-latency). Deployment topology: broker daemons behind a load balancer, workers as an independently-scaled fleet, storage as a managed or self-hosted cluster. 25. Compatibility & Versioning

Wire compatibility. Protobuf field numbers (ADR-02) are never reused or renumbered; internal/proto/jobq.proto follows additive-only evolution within a major version. Storage compatibility. Postgres migrations (§16.2) are forward-only within a major version; downgrades require the paired down-migration, tested in the migration round-trip fixture (§16.5). API stability. pkg/jobq public types (§11) are stable across the v1 series; a breaking change requires a v2 import path. Deprecation policy. A deprecated field/method is marked in its docstring with the removal-eligible version and remains functional for at least 2 minor releases. SemVer. MAJOR.MINOR.PATCH; MAJOR breaks wire/API compatibility, MINOR adds capability-gated features, PATCH is bug-fix only. Rolling-upgrade guarantee. A broker N and N+1 (same major version) interoperate with workers on either version for the duration of a rolling deploy — verified by the encoding/roundtrip conformance bucket run cross-version in CI (§26).

29. Scalability Analysis

Constant regardless of scale: per-job engine logic (§17), codec cost (§13), lease-token comparison cost (O(1)). Grows with load: in-flight lease count (Little's Law, §32), idempotency index size (§32), dead-letter storage (§32) — all linear in throughput. Named bottlenecks, in order: (1) single Redis/Postgres shard's write throughput ceiling (§4); (2) single scheduler leader's promote/sweep/cron batch size (§19.7); (3) per-broker-process FD/connection budget (§4, §18.7). Horizontal scaling. Worker fleet scales linearly and independently of the broker (stateless beyond in-flight leases). Broker scaling beyond one shard requires consistent-hashing partitioning across queue names — PhaseDeferred("§29"), registered §35 — because the current single-shard design (§3) assumes one authoritative pending/delayed/leased set per queue. Vertical scaling. Redis/Postgres shard sizing follows the capacity model (§32); a single well-provisioned Redis instance holds the line to roughly 100k enqueue/s and 50k dequeue/s (§4) before horizontal sharding becomes necessary. Sharding/partitioning. Deferred design: consistent hashing on queue name, each shard owning 1/N of keyspace, hash-tag co-location (§15.2) extended per-shard. Coordination overhead. Multi-shard cross-queue operator views (list-all-queues) fan out and merge — O(N) shard calls per such view, acceptable because it is operator-path, not producer/worker-path (§21.7). Practical ceiling. Single-shard Redis: ~100k enqueue/s (§4, M1); beyond that, the lever is horizontal sharding (§35), not vertical Redis scaling, because Redis's single-threaded command loop is the ultimate ceiling regardless of host size.

30. Mental Models & First Principles

  1. MM1 — A lease is a bet with an expiry clock, not a proof of liveness. Predicts: a worker holding a lease might already be dead; the system must act as if every lease could be stale at expiry. Bug class without it: treating lease possession as a liveness guarantee, causing double-processing to be "surprising" instead of expected (§18.9, §8.3).
  2. MM2 — At-least-once shifts the correctness burden downstream, it does not eliminate it. Predicts: every handler must be idempotent or the system must supply an idempotency layer. Bug class without it: assuming the broker "handles" duplicates when only the application can (§7 I1, §8.7).
  3. MM3 — A queue is a work-distribution primitive with amnesia; a log is a replay primitive with memory. Predicts: once a job is acked, the record is gone — you cannot "replay" a completed job the way you replay a Kafka offset. Bug class without it: expecting queue semantics from a log or vice versa (§2, §31).
  4. MM4 — Fairness is a scheduling problem, not a queue-depth problem. Predicts: a deep queue for one tenant does not by itself starve another tenant if the scheduler enforces per-tenant bounds. Bug class without it: throttling globally instead of per-tenant, punishing quiet tenants for a noisy one (§8.6, §20).
  5. MM5 — Backpressure is a contract the caller opts into, not a physical law the broker enforces unconditionally. Predicts: an operator who never enables Backpressure: true has consciously chosen unbounded buffering. Bug class without it: assuming the broker always protects itself, then being surprised by unbounded growth (§6 P7, §22 T5).
  6. MM6 — An idempotency key is a poor man's exactly-once, bounded by a window. Predicts: after the dedup window expires, the "exactly-once" property silently reverts to at-least-once. Bug class without it: assuming permanent dedup and never re-checking after a long producer-side retry delay (§8.7, §32).
  7. MM7 — A dead-letter queue is a forensic ledger, not a graveyard. Predicts: every dead-lettered job must be requeueable with its history intact, because the operator's next action is almost always "fix and replay." Bug class without it: treating dead-letter as a terminal log line with no path back (§6 P6, §23 FM-1).
  8. MM8 — Leader election converts a distributed problem into a single-writer problem, at the cost of an availability window during handover. Predicts: the scheduler is unavailable for at most one lock-TTL period during a leader crash — a bounded, known cost, not an open-ended outage. Bug class without it: expecting zero-downtime scheduling without accounting for the handover window (§7 I4, §19.9).

AWS SQS made queue management fully managed and opaque, trading operator visibility (no Lua scripts, no schema to inspect) for zero operational burden — SQS wins whenever a team has no appetite to run broker infrastructure at all. Temporal made the workflow itself durable via deterministic replay, solving long-running multi-step orchestration that a plain job queue cannot express without significant application-level state machinery — it wins whenever a "job" is really a multi-day saga with compensating actions, not a single unit of work.

32. Back-of-Envelope Capacity Model

  1. Steady-state in-flight leases (Little's Law): L = λ × W = 50,000 jobs/s (§4 dequeue ceiling) × 30 s (§4 default lease) = 1,500,000 concurrent leases at saturation → requires ≥150 worker processes at the 10,000-lease-per-process ceiling (§4).
  2. Redis ingress bandwidth: 100,000 enqueue/s (§4) × 1 KiB typical payload (well under the 256 KiB default cap, §4) = 100 MB/s sustained ingress.
  3. Leased-set memory: 1,500,000 in-flight leases (#1) × ~150 bytes/zset-member (job_id + worker_id + token) ≈ 225 MB resident in Redis's leased zset.
  4. Dead-letter growth rate: 0.1% assumed terminal-failure rate × 100,000 enqueue/s (§4) = 100 dead-letters/s × 2 KB/record × 2,592,000 s (30-day retention, ADR-16) ≈ 518 GB worst-case archival storage.
  5. Idempotency index worst case: 100,000 enqueue/s (§4) × 86,400 s (24 h dedup window, ADR-14) × 64 bytes/entry ≈ 553 GB if every job carried a unique key — sizes the ceiling operators must plan for even though real-world key adoption is a fraction of this.
  6. Postgres table growth: 10,000 enqueue/s (§4 Postgres ceiling) × 200 bytes/row × 86,400 s/day ≈ 173 GB/day raw growth before autovacuum reclaims completed rows.
  7. FD budget rationale: 10,000 leases/process (§4) would be 10,000+ FDs at 1:1, but heartbeat batching (§18.7) multiplexes renewals onto ~10 pooled connections, holding the actual ceiling at 12,000 FDs (§4) rather than 10,010+.
  8. Cron bucket-collision probability: skew_bound / bucket_width = 1 s (§4 clock-skew assumption) / 60 s (default cron bucket) ≈ 1.7% raw double-fire probability per handover event, reduced to an observed 0% after the I12 idempotency key absorbs it (§19.4, §28 M7).

34. Alternative Architectures (Roads Not Taken)

Alternative 1 — Log-based replay queue (Kafka-shaped).

Show the original text diagram
Producer --append--> [ partitioned append-only log ] --offset read--> Consumer group
                          (retained N days, replayable)

Regime where it wins: multiple independent consumers need to replay the same stream at their own offsets (fan-out, reprocessing, event sourcing). Real embodiment: Apache Kafka (Kreps et al., NetDB 2011). Rejected here because this project needs work-distribution with acknowledgement and lease-based retry (I1–I3) — a log has no native "this consumer took ownership of this record" primitive; bolting one on (consumer-group offset commit as a proxy for ack) does not give per-record retry/dead-letter semantics without significant extra machinery (§2, §31).

Alternative 2 — Stateless shared-table polling queue.

Show the original text diagram
[ Workers ] --poll every N ms--> [ shared DB table, no broker process ] <--enqueue-- [ Producers ]

Regime where it wins: the simplest possible deployments where a dedicated broker process is operationally unwelcome and job volume is low (< 100/s). Real embodiment: early Celery database-backend configurations, Django-Q. Rejected here because polling-interval latency and the lack of a long-poll/blocking primitive directly violate the reserve p99 target (I9, §4), and there is no natural place to enforce per-tenant fairness (§20) without significant application-side logic duplicated across every consumer.

Alternative 3 — Actor-supervision-tree queue (BEAM/OTP-shaped).

  • Supervisor
    • ├── Producer actor
    • ├── Queue actor (owns all state, message-passing only)
    • └── Worker actor pool (linked, restart-on-crash)

Regime where it wins: a runtime with cheap preemptive process isolation and built-in supervision (crash containment is free) — long-running, deeply stateful job graphs benefit from per-job actor isolation. Real embodiment: Oban (Elixir, on BEAM). Rejected here because Go's goroutine model has no native supervision-tree/let-it-crash semantics (ADR-01) — replicating BEAM's isolation guarantees in Go would require reimplementing much of OTP's runtime behavior, which is a worse tradeoff than accepting Go's shared-memory-with-explicit-panic-recovery model (§18.4) for this project's target ecosystem.

36. Glossary

Ack — worker signal that a job completed successfully; broker moves state to COMPLETED. ADR — Architecture Decision Record; this document's ADR table is §9. Advisory lock — Postgres session-scoped lock used for Phase-0 leader election (ADR-12). At-least-once — delivery guarantee where a job may run more than once but never zero times (I1). Attempt — broker-incremented counter of reservation count for a job. Backpressure — explicit signal (ErrBackpressure) that a producer's enqueue was rejected due to queue depth (P7). Band — one of ten priority levels (0–9) scanned by the reserve loop (§8.6). Broker — the process (cmd/jobqd) hosting the Engine, Scheduler, and Storage adapter. Capabilities — an adapter's self-reported feature/limit set (§11). Circuit breaker — a client-side failure-detection wrapper that opens after consecutive storage failures (§15.10). Cold start — the time from broker process launch to readiness (§4, M9). Conformance bucket — a named group of positive/negative fixtures verifying one capability (§26). Cron bucket — the truncated-timestamp unit (default: minute) used to key a cron idempotency key (§19.2). Dead-letter — terminal state for a job that exhausted MaxAttempts (ADR-16, I6). Dedup window — the TTL over which an idempotency key resolves to the same job ID (§8.7). Delay set — the storage structure holding jobs whose ScheduledAt is in the future (§8.1). Drain timeout — the maximum wait during graceful shutdown for in-flight handlers to finish (P10). Engine — the business-logic layer between the API and the Storage adapter (§17). Full jitter — a backoff formula, uniform(0, min(cap, base·2^attempt)) (ADR-13). Handler — user-supplied callback invoked per reserved job. Heartbeat — the periodic lease-renewal call made by a worker holding an active lease (§18.2). Idempotency key — caller-supplied string deduplicating enqueue calls within a window (§8.7). Lease — the explicit, renewable reservation record (JobID, WorkerID, Token, ExpiresAt) this project uses instead of an implicit visibility timeout (§8.2, MM1). Leader election — the mechanism ensuring exactly one scheduler instance promotes/sweeps/ticks (I4). Long-poll — a Reserve call that blocks up to a deadline waiting for an available job. Middleware — a wrapper applied to a Handler for cross-cutting concerns (tracing, metrics, recovery). Payload — the opaque application bytes carried by a Job. Priority — the band (0–9) determining reserve-scan order (§8.6). Promote — the scheduler action moving a delayed job into the immediate queue once ready (§8.1). Reserve — the operation by which a worker takes ownership of the next eligible job. RTO — Recovery Time Objective; the target time to restore service after a failure (§4). RPO — Recovery Point Objective; the target maximum acceptable data loss window (§4). SKIP LOCKED — the Postgres row-locking clause enabling concurrent, non-blocking reservation (§16.2). Starvation cap — the consecutive-same-band reservation limit that forces a scan-restart at a lower band (I13). Storage adapter — the pluggable persistence implementation of the Storage interface (§11). Sweep — the scheduler action reclaiming jobs whose lease has expired (§8.1). Tenant — the multi-tenant scoping label used for fairness quotas (§20). ULID — Universally Unique Lexicographically-sortable Identifier, this project's job-ID format (§13). Visibility timeout — the SQS term for what this project calls a lease (§8.2 terminology note). Worker — the process running registered Handlers against reserved jobs. Worker pool — the bounded-concurrency goroutine pool executing handlers (§18). Zset — Redis sorted set, used for delayed/leased/dead-letter/done ordering by score (§15.2).
