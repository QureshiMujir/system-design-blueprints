⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the full repository shape (§10) and the deterministic correctness kernel: the State enum, the invariant simulator harness, and enough CI wiring that a broken invariant fails a named test on every push.

Deliverable

A cloned repo where make bootstrap && make test runs green on everything except the intentionally-failing invariant stubs, whose failure messages name I1–I14 (P9 applied: even a stub failure is observable, not silent).

Acceptance
  • make lint reports 0 findings across internal/, pkg/, cmd/.
  • Exactly 14 named-failing tests in the invariant simulator, one per I1–I14 — not 13, not 15.
  • docker-compose up brings up redis, postgres, and jobqd within 10 s.

Pitfalls
  • Treating the empty-dir README.md stubs as throwaway — a later session reads them to decide what belongs there (§22 T9, documentation-drift class).
  • Skipping the SECURITY.md PGP placeholder because "we don't have one yet" — the placeholder is the documented mechanism for not having one yet.
  • Letting the invariant stubs silently t.Skip() instead of t.Fatal() — this defeats the correctness-kernel's entire purpose (P9).

⬜ Phase 1 — Core Job Types & Wire Encoding §13

Objectives

Lock the Job schema (§8.1, §11) and the codec layer (ADR-11) so every later phase encodes and decodes identically.

Deliverable

Every Job field round-trips through all three codecs; internal/proto/gen/ contains committed generated code; the ULID generator produces monotonically-sortable IDs under concurrent calls within the same millisecond.

Acceptance
  • 100% field coverage in the round-trip property test (all 20 Job fields, 3 codecs = 60 assertions, 0 failures).
  • ULID monotonicity property test: 10,000 concurrent NewID() calls within one millisecond produce a strictly increasing sequence.
  • Oversized payload (> 1 MiB, §4) rejected at encode time with ErrPayloadTooLarge, not at the broker.
Fixtures
Filename Purpose Expected Output
conformance/fixtures/positive/encoding_roundtrip.json all fields, 3 codecs Pass
conformance/fixtures/negative/enqueue_malformed.json bad queue name + oversized payload (§8.4) Fail, both errors joined
conformance/fixtures/positive/ulid_monotonic.json 10k concurrent IDs strictly increasing
Pitfalls
  • Calling time.Now() inside the codec — the codec must be deterministic; time is caller-supplied (breaks the round-trip property test's reproducibility).
  • Normalizing time.Time zero values inconsistently across codecs — the codec normalizes zero to "absent" on the wire uniformly.
  • Reaching for encoding/gob because it is in the standard library — gob is not cross-version stable; ADR-11 forbids it for payloads.

⬜ Phase 2 — Storage Adapter Abstraction & Conformance Baseline §14

Objectives

Lock the Storage interface (§11, P3) and prove the conformance harness is sensitive by running it against a stub that fails everything.

Deliverable

The Storage interface compiles with zero adapters implementing it beyond stub; the conformance runner against stub fails 100% of positive buckets and passes 100% of negative buckets — proving the harness discriminates correctly before any real adapter exists.

Acceptance
  • stub adapter: 0/24 positive buckets pass (§26 lists 24), 100% of applicable negative buckets pass.
  • Interface has exactly 13 methods (§11); a go vet custom analyzer (tools/ifacecheck) fails CI if any adapter's method set drifts from the interface.

conformance/fixtures/negative/stub_capability_gap.json every method against stub ErrCapabilityNotSupported

⬜ Phase 3 — Redis Adapter (Lua-Scripted Primitives) §15

Objectives

Implement Storage against Redis 7 with every multi-step primitive as one atomic Lua script (P13, ADR-03), matching asynq's atomicity pattern (§5 ref-impl 2).

Deliverable

The Redis adapter passes every applicable conformance bucket (§26); benchmark results committed to benchmarks/results/redis.md against the §4/§28 throughput and latency targets.

Acceptance
  • 100,000 enqueue/s sustained over 60 s (§28 M1); p99 enqueue latency < 10 ms (§28 M2).
  • reserve/priority fixture: starvation cap at 100 same-band reservations (I13) verified by a 100,001-reservation trace.
  • Cluster-mode fixture: a queue whose name contains { or } is rejected at Enqueue with ErrInvalidQueue (prevents cross-slot Lua failures).
Fixtures
Filename Purpose Expected Output
conformance/fixtures/positive/redis_reserve_priority.json band-scan + starvation cap matches I13
conformance/fixtures/negative/redis_oversized_lua_payload.json payload > configured limit redis.error_reply, no partial hash write

Pitfalls
  • Mixing keys without the {queue} hash tag — cross-slot Lua errors under cluster mode; the broker rejects illegal queue names at the SDK boundary instead of discovering this at runtime.
  • Assuming WATCH/MULTI/EXEC suffices for the multi-step primitives — Lua is the only server-side-atomic choice available here (P13).
  • Forgetting the payload-size guard inside the Lua script itself — a client-side-only check can be bypassed by a non-SDK producer; the guard must live in enqueue.lua.

⬜ Phase 4 — Postgres Adapter (SKIP LOCKED) §16

Objectives

Implement Storage against Postgres 14+ using SELECT … FOR UPDATE SKIP LOCKED for reservation (ADR-04, Petrov ch. 5), avoiding both LISTEN/NOTIFY reliability gaps and SERIALIZABLE overhead.

Deliverable

The Postgres adapter passes every applicable conformance bucket; a migration test walks every schema version forward to head and back to initial without data loss.

Acceptance
  • 10,000 enqueue/s sustained (§28 M5); 5,000 dequeue/s sustained (§28 M8).
  • lock_timeout = 1s enforced by the adapter's connection-pool init, preventing a stuck handler from holding a row lock indefinitely (§17.6 pitfall).
  • Migration round-trip test: every version 1..N and back to 0, 0 data-integrity failures.
Fixtures
Filename Purpose Expected Output
conformance/fixtures/positive/pg_skip_locked_concurrency.json 50 concurrent reservers, 1 row each no duplicate reservation (I3)
conformance/fixtures/negative/pg_lock_timeout.json handler holds row past lock_timeout reservation released, error logged
conformance/fixtures/positive/pg_migration_roundtrip.json forward/back through all versions 0 integrity failures
Pitfalls
  • Reaching for LISTEN/NOTIFY for reservation — NOTIFY payloads coalesce and drop under load; the reserve loop must poll with backoff and rely on SKIP LOCKED for correctness, not notification delivery (§5 book 4).
  • Omitting lock_timeout — a handler that holds a transaction open indefinitely poisons the queue for every other reserver on that row's neighbors in the index.
  • Reaching for SERIALIZABLE isolation — unnecessary; READ COMMITTED plus FOR UPDATE SKIP LOCKED is sufficient and materially cheaper (Petrov ch. 5).

⬜ Phase 5 — Broker Engine (Enqueue / Reserve / Ack / Retry / Cancel) §17

Objectives

Build the business-logic layer between the public API and the Storage adapter (§3): request validation, capability dispatch, middleware invocation, and the single call site per operation that keeps the adapter opaque to the engine (P3, P13).

Deliverable

The engine compiles against all four adapters, has unit tests against stub (interface-only, no I/O), and is wired into the gRPC frontend (internal/api/grpc).

Acceptance
  • 100% of engine unit tests pass against stub with 0 adapter-internal imports (enforced by tools/ifacecheck, §14.4).
  • Every engine method emits exactly one span per call, verified by tracing/correlation conformance bucket (I11).
  • Cancel on an in-flight lease propagates within one RenewLease cycle (≤ LeaseDuration/3, ADR-15).

⬜ Phase 6 — Worker Pool, Lease Heartbeats, Graceful Shutdown §18

Objectives

Implement the bounded worker pool (pkg/workerpool), the lease-renewal heartbeat (P2, I2), and graceful SIGTERM drain (P10) — the pattern Cox-Buday ch. 4–5 (§5) formalizes as pipeline-with-cancellation.

Deliverable

cmd/jobq-worker runs registered handlers end-to-end; examples/hello demonstrates the full loop with zero external dependencies (ADR-05 in-memory adapter).

Acceptance
  • SIGTERM drains 1,000 in-flight jobs with 0 drops (§28 M11, I10).
  • Lease-renewal heartbeat fires at exactly LeaseDuration/3 ± 5% jitter under load, verified by a 10,000-lease soak test.
  • A handler panic never terminates the worker process; the process survives 1,000 injected panics in a fuzz loop.
Fixtures
Filename Purpose Expected Output
conformance/fixtures/positive/shutdown_drain.json SIGTERM with 1k in-flight 0 dropped (I10)
conformance/fixtures/negative/handler_panic_recovery.json handler panics OutcomeRetry, process alive
conformance/fixtures/positive/heartbeat_cadence.json 10k leases, renewal timing within LeaseDuration/3 ± 5%
Pitfalls
  • Renewing on a fixed schedule that does not divide LeaseDuration evenly — use /3 to leave headroom for clock skew (Kleppmann ch. 8, §5 book 1).
  • Treating panics as terminal — they are retryable; the next attempt succeeds once the triggering bug is fixed and redeployed.
  • Stopping the heartbeat goroutine before the handler's goroutine actually exits — long-running handlers lose their lease exactly at LeaseDuration if the heartbeat stops early.

⬜ Phase 7 — Retry Policy, Dead-Letter, Scheduler & Cron §19

Objectives

Implement the default backoff policy (ADR-13), dead-letter routing (ADR-16), and the single-leader scheduler that promotes delayed jobs and fires cron ticks (P4, I4, I12).

Deliverable

The scheduler runs as a single elected leader; cron ticks and delay-promotion are observable via jobq_scheduler_leader and jobq_cron_tick_total; a dead-lettered job is inspectable via the operator surfaces built in Phase 9 (§21).

Acceptance
  • 0 double-enqueues across 10 simulated leader-handover events during a cron tick window (§28 M7, I12).
  • Retry-delay distribution matches the full-jitter formula within a 5% tolerance over 10,000 samples at a fixed seed.
  • A job at MaxAttempts=25 dead-letters on the 26th failure, never the 25th or 27th (I7).
Fixtures
Filename Purpose Expected Output
conformance/fixtures/positive/retry_policy_distribution.json 10k samples, fixed seed matches full-jitter formula ±5%
conformance/fixtures/positive/retry_exhaustion.json job fails 26 times dead-lettered with full history (I6, I7)
conformance/fixtures/negative/cron_leader_handover.json 10 handovers mid-tick 0 duplicate enqueues (I12)
Pitfalls
  • Cron leader election by timestamp comparison instead of an advisory lock/lease — a classic split-brain generator (§5 book 2, Kleppmann ch. 9).
  • Cron without the cron:<name>:<bucket> idempotency key — a leader change at the wrong instant double-enqueues (I12).
  • Reaching for "decorrelated jitter" without measuring — full jitter is the correct default for this workload (AWS Architecture Blog, ADR-13); a custom policy is opt-in, not default.

⬜ Phase 8 — Priority, Delay Queues & Fair Multi-Tenant Scheduling §20

Objectives

Implement priority bands with starvation control (I13) and per-tenant fairness (P11) so a shared broker cannot let one tenant starve another.

Deliverable

A multi-tenant conformance scenario (3 tenants, skewed priority distributions) demonstrates bounded starvation and quota enforcement, with metrics broken out per tenant.

Acceptance
  • Low-priority tenant in a 3-tenant skewed-load scenario receives ≥ 1 reservation per 100 high-priority reservations (I13 bound verified empirically).
  • A tenant at its MaxConcurrentLeases quota receives ErrBackpressure-class rejection on further Reserve attempts, not silent queuing past the quota.
  • 0 cross-tenant lease leakage: a tenant's Reserve never returns another tenant's job (verified by 100,000-reservation fuzz run with tenant-tagged synthetic jobs).
Fixtures
Filename Purpose Expected Output
conformance/fixtures/positive/fairness_starvation_bound.json 3-tenant skewed load low-priority tenant served within bound (I13)
conformance/fixtures/negative/tenant_quota_exceeded.json tenant at quota reserves again rejected, quota-specific error
conformance/fixtures/negative/cross_tenant_leak.json 100k reservations, tenant-tagged 0 leaks
Pitfalls
  • Implementing fairness only at the priority-band level and assuming it covers multi-tenancy — priority is per-queue; a noisy tenant sharing a queue with a quiet one needs the separate per-tenant quota (P11), not just band rotation.
  • Quota enforcement that races with concurrent Reserve calls from the same tenant — the quota check and the lease grant must be one atomic storage-layer operation (P13), not a check-then-act pair.

⬜ Phase 9 — Operator Surfaces, Observability & Conformance Suite §21

Objectives

Ship the operator HTTP API, web UI, and CLI (all delegating to the Phase-5 engine, never duplicating business logic), and close out the conformance suite (§26) to full Pass/Deferred coverage for every Phase-0 surface.

Deliverable

An end-to-end test walks enqueue → peek → retry → ack through the HTTP API, the CLI, and the UI against all three adapters; the Phase-0 conformance report is 100% Pass for every bucket the Phase-0 surface promises and Deferred (with a blueprint_ref) for everything else.

Acceptance
  • 24/24 conformance buckets (§26) report Pass or Deferred with a resolving anchor — 0 silent skips (the runner asserts on this, not a human checklist).
  • Every HTTP endpoint has a corresponding UI view and CLI subcommand — 1:1:1 coverage verified by a generated coverage table in docs/operator-guide.md.
  • Trace ID present on 100% of sampled spans from Enqueue to Ack in a 1,000-job soak run (I11).
