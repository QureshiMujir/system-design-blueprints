In one paragraph

A service-discovery system is a phone book for running programs: a workload says "I am web, on this address and port", and other programs ask who is currently alive and healthy under that name. This design is a Consul-class system, one agent binary (discoveryd) per node that registers workloads, probes their health, keeps a strongly consistent catalog replicated by Raft, answers over DNS and an HTTP API with long-poll watches, spreads cluster membership by gossip, and forwards reads across datacenters (§1). Its defining property: the catalog is linearizable within one datacenter, and everything else (membership, DNS answers, the ACL cache) is a view of it with bounded staleness (§4). Each agent runs in server or client role (§3, ADR-02).

The problem, concretely

You run a web service on a changing set of machines. The first fix is DNS with a record per machine. That fails in three ways the blueprint names: DNS has coarse TTL granularity, carries no metadata, and has no health-awareness (§2). The second fix is for every client to poll an HTTP endpoint asking "has the list changed?". That fails at scale as a thundering herd (§2, P3). The blueprint's answer splits the problem in two. Catalog writes, the list of what is registered, go through consensus (Raft) (P2). Membership, whether a node is reachable, is a probabilistic judgement that is allowed to be eventually consistent, so it rides gossip (P2, MM3). Clients never talk to the cluster directly; they talk to a local agent, which gives the cluster a queueing and access-control boundary (P1).

How it works, end to end

Follow one registration, PUT /v1/agent/service/register {"Name":"web","Port":8080} (§8.8), through the boxes of §3. The diagram below is a trimmed copy of §3's.

   Clients (CLI, sidecar libs, k8s)   -- HTTP API + blocking queries / DNS (UDP+TCP, A/AAAA/SRV)
        |
   discoveryd (one binary per node, -server or -client role)
     HTTP API | DNS Server | KV Front | Sidecar Bridge
                    |
         Catalog / Registry  (nodes, services, instances, checks, monotonic index, watch waiters, ACL cache)
            |                              |
     Health Check Engine           Gossip / Membership (SWIM + Lifeguard)
            |                              |
         Replicated Log (Raft)  <-  Embedded KV shares this log
                    ^
                    | WAN gossip + cross-DC forwarding  ->  other datacenters
  1. Local agent first. The workload talks to its own node's agent, over the HTTP API (internal/httpapi) or the Unix-socket sidecar bridge (internal/sidecar). The agent forwards register, deregister and health updates into the cluster (§3, P1).
  2. Access check. The HTTP handler validates the ACL token (internal/acl). Every read and write path takes a token, including DNS and gossip control operations (§8.8, I4).
  3. Write through consensus. The request becomes a log entry of kind RegisterService (one of the nine kinds in §8.6) carrying a request UUID, and goes through internal/raft, the thin adapter over the workspace Raft library. Writes are leader-serialized (§3, ADR-07).
  4. Apply to the catalog. internal/catalog upserts the Node, Service and Instance under one lock acquisition and assigns the next index; the §8.8 example gets index 42 (I1).
  5. Wake the watchers. Only after the index is committed does the catalog notify the web channel (I2). A parked GET .../health/service/web?index=41 wakes and returns index 42 (§8.8).
  6. Health decides visibility. internal/checks probes the instance asynchronously, one goroutine per check, never blocking the apply path (§3, I5). dig web.service.dc1.discovery. SRV returns the instance once its first check reaches passing (§8.8, I3). DNS lives in internal/dns.
  7. Membership and other datacenters. internal/gossip tells the cluster which nodes are alive. internal/federation forwards ?dc= reads to other datacenters (§3, §21).

The KV store (internal/kv) is an extra door onto the same log, not a second system (ADR-08, §3). Monotonic clocks drive every interval; the wall clock is for display only (ADR-20).

The core ideas

The catalog is a log-fed state machine with one index (§8.6, I1, I6, I11)

Every change is a log entry: a kind (register node, register service, update check, KV put, revoke ACL token and so on, §8.6), a 16-byte request UUID, a payload, and a CRC for corruption checks (§8.6). Applying an entry follows three rules. First, the apply step reads no wall clock; each transition is a pure function of (state, entry), so replaying the log reproduces the state (I11, P9). Second, a repeated request UUID is a no-op, so a client retry after a timeout cannot register twice (I6, P12). Third, the catalog keeps a single global, monotonic counter, the index, never one per row (I1). The index is a logical clock: it orders events and measures no time (MM2). Raft has its own log index, distinct from this one (§8.6). The KV store uses the same single counter (P14).

A toy trace from §8.8: a waiter is parked at index 41; the web registration is applied and assigned index 42. The same entry delivered again is a no-op, dropped by its request UUID (I6). TTL-style checks need a clock, so an outside timer injects a "deadline passed" event as ordinary input (P9). One wrinkle: §8.6 attributes the protobuf payload encoding to ADR-04, but ADR-04 in §9 is the HTTP framework and router choice; no ADR row in §9 covers serialization.

Blocking queries: a subscription with a receipt (§8.5, I2, I7, MM5)

A client asks "tell me when the list changes from index 41". The server follows five steps (§8.5):

  1. Snapshot the current index. If it is already above 41, answer at once.
  2. Otherwise register a waiter on the service's notification channel (I7).
  3. Block for min(wait, 10m), with a floor of 100 ms so bursts coalesce.
  4. On notify (after I2's ordering) or timeout, re-snapshot under the lock and return (index, data). A timeout returns the same index unchanged.
  5. Set X-Consul-Index and two sibling headers on every response, blocking or not.

The index is the receipt: after a restart a client resumes by sending its last index, so no server-side session is needed (MM5). Coalescing means one notification fans out to all waiters on the same table, bounded to one fan-out per table transition (I7). Notify must follow commit, or a waiter wakes before the data is visible (I2). If the Raft leader dies while a query is parked on index 100, the waiter is not cancelled, because it is agent-local; if no write arrives it gets index 100 back, never an error (§8.10).

Health as a small state machine with hysteresis (§8.2, I5, I9, I13)

Health is one of passing, warning, critical, with no "unknown" outside a registration grace period (P4). Transitions need several consecutive observations (hysteresis), which stops flapping:

From Event To
passing N consecutive failures (N ≥ FailuresBeforeCritical) critical
passing one warning-class result (HTTP 429/503 only) warning
warning N consecutive successes (N ≥ SuccessBeforePassing) passing
critical N consecutive successes passing
critical continuous critical for DeregisterCriticalServiceAfter deregistered

(§8.2.) A TTL check, which the client must refresh before a deadline, only goes critical after a grace of at least TTL/2, to tolerate clock skew (I9). The auto-deregister timer counts continuous critical time, and one passing observation resets it (I13). Probes run asynchronously and never block the apply path (I5); the HTTP mapping is 2xx passing, 429/503 warning, anything else critical (§16.2).

Two replication planes: Raft for the catalog, gossip for membership (P2, MM3, MM4, §8.7)

Catalog writes need one agreed order, so they use Raft. "Is node X reachable?" is a probabilistic judgement, so it rides gossip, an epidemic protocol where nodes ping each other and piggyback updates on those messages (P2, §8.7). The system is therefore CP for the catalog and AP for membership at once, and "is it CP or AP?" has no single answer without naming the subsystem (MM4).

The gossip failure detector (SWIM, with the Lifeguard extension) has a suspicion state between alive and dead, since no detector is both accurate and fast on an asynchronous network (P11, MM3). Vanilla SWIM's worst-case suspicion timeout is 3 × the 1 s LAN probe interval, 3 s, so the 500 ms convergence target depends on Lifeguard's dynamic timeouts (§34.10, ADR-06). The adapter is the only code that maps a gossip NodeID to a catalog Node.ID (§8.7). A failed node has all its instances marked critical, and duplicate join events are a no-op (§18.2, I6, I8).

DNS as a read-only, filtered view (§8.3, §8.4, I3, P5)

A query like web.service.dc1.discovery. parses as service, datacenter, domain; the datacenter defaults to the local one and the domain is configuration, never a literal (§8.3). Answers are built from the catalog (§8.4):

Record Comes from
A / AAAA Instance.Address, else Node.Address
SRV priority 0, weight from the instance's passing/warning weights, port from Instance.Port
TXT (opt-in) Instance.Meta

Every answer is filtered: critical instances never appear, and warning ones appear only on opt-in (I3). DNS is read-only and returns the freshest local snapshot rather than a consensus-confirmed read, so a write path built on DNS would break I3 (P5). An oversized UDP answer is truncated with the TC flag so the resolver re-queries over TCP, and a degenerate EDNS0 buffer of 0 falls back to the 512-byte legacy limit (§8.9, §15.2).

Federation forwards reads; it never merges (§21, MM6, I12)

A query with ?dc=remote is forwarded by the local leader to the remote leader, and the response is returned verbatim with the remote datacenter's own index. Indexes are datacenter-local and never merged (§21). Merging would need one linearizable order across separate failure domains (MM6). If the remote datacenter is unreachable the answer is a hard 503 dc_unreachable, never a silent fallback to another datacenter (I12, P7). The cost is a latency floor set by the speed of light: a federated read is about one local lookup, one round trip of 30–150 ms, and one remote lookup, 32–152 ms (§34.11). Caching "to fix" that would quietly bring back the staleness this design avoids (MM6).

The trade-offs — where engineers disagree

Replicated log: Raft (ADR-07)

Chosen: Raft, via the workspace's Raft crate, reusing an implementation built to be understandable (§9). Rejected: Multi-Paxos; manual primary-backup. When the rejected choice is right: Multi-Paxos for leaderless multi-region writes (Spanner-style placement); manual failover at a 2-node edge site where Raft's odd-quorum rule is awkward (§9). The price of the choice: extra servers add fault tolerance, not write throughput (§31).

Membership: SWIM + Lifeguard gossip (ADR-06)

Chosen: gossip via the workspace's Gossip-Protocol crate, for O(1) per-node bandwidth and no single point of failure (§9). Rejected: full all-to-all heartbeats; a central heartbeat server. When the rejected choice is right: all-to-all below about 20 nodes, where O(n²) cost is negligible and instant convergence beats gossip's probabilistic delay (§9).

KV store shares the catalog's Raft log (ADR-08)

Chosen: embed the Distributed-KV-Store crate on one shared log, for one source of truth and one ACL surface (§9, P14). Rejected: a separate KV cluster; no KV at all. When the rejected choice is right: a separate KV cluster, once unrelated config write volume swamps catalog write latency (§9). The visible cost is FM6: KV latency rising under catalog load because both share one leader (§25).

One binary, two roles (ADR-02)

Chosen: a single binary run as server or client, giving one operational artifact (§9, §3). Rejected: separate server and client binaries; sidecar-only. When the rejected choice is right: separate binaries, where policy forbids client hosts from ever holding quorum-signing keys (§9).

Bounded everything (ADR-21)

Chosen: bounded worker pools and bounded channels everywhere, for a predictable memory ceiling under load spikes (§9, P13). Rejected: unbounded goroutine-per-request. When the rejected choice is right: a bursty, low-QPS internal tool where simplicity outweighs a rare OOM risk (§9). The blueprint treats this as correctness, not tuning: an unbounded queue fails catastrophically at the worst moment (MM7).

Encrypt the LAN too (ADR-17)

Chosen: AES-GCM keyring rotation on gossip plus mTLS on Raft RPC, as defence in depth for multi-tenant safety (§9, T5, T7). Rejected: unencrypted LAN traffic with perimeter isolation only. When the rejected choice is right: inside a single-tenant VPC, where the AES-GCM CPU cost on every gossip packet is not worth paying (§9).

Storage: a B+tree log and snapshot file (ADR-05)

Chosen: a Bolt-style single-file B+tree log plus snapshot, for simple crash recovery and no cgo (§9). Rejected: RocksDB/LSM via cgo; flat files. When the rejected choice is right: RocksDB past about 50K sustained writes per second with large values, where B+tree page splits dominate (§9).

Roads not taken

etcd as the discovery backend (§36 Alternative A): clients watch a key prefix and interpret keys as endpoints themselves. It wins for a shop already running etcd under Kubernetes that wants one fewer moving part. It is rejected because every client would reimplement the health enum (P4) and the DNS-style lookup (P5).

Kubernetes-native discovery (§36 Alternative B): Endpoints/EndpointSlice plus CoreDNS fall out of the scheduler's reconciliation loop. It wins for a fleet that already runs a Kubernetes control plane. It is rejected because the target users include bare-metal and VM fleets with no such control plane (§1).

Pure-gossip AP catalog (§36 Alternative C): no Raft, each agent holds its own eventually consistent copy, as in Eureka. It wins for a client-heavy, write-light fleet that prefers a stale list to a refused read. It is rejected because it violates P2 and cannot give linearizable register/deregister (§7 I1, I6).

ZooKeeper-style ephemeral znodes (§36 Alternative D): registration as one use of a generic coordination primitive. It wins when the main need is locks, leader election and config, with registration a side use. It is rejected because SRV-style records, health semantics (P4) and DNS (P5) must be built on top, and one-shot watches push reconnection state onto every client (§8.5, MM5).

The deferred register (§37): script checks, KV sessions and locks, /v1/txn, prepared queries, the full Connect mesh and an operator web UI are postponed, each with an explicit trigger, and MM8 calls that a decision, not an omission. Script checks are held back because arbitrary command execution is a threat (T10), and the feature stays out until a sandboxed exec runtime design is approved (§37).

What must never be false

  • I1: the catalog index is global and strictly increasing. A unit test asserts it; gauge catalog_index_current (§7).
  • I2: notify fires only after the index increment is committed. Caught by race-detector CI runs; catalog_notify_lag_seconds (§7).
  • I3: DNS never returns a critical instance, and warning only on opt-in. Fixture dns/health-filter; dns_answers_by_status_total (§7).
  • I4: every read and write path evaluates an ACL token, including DNS and gossip control. Fixture acl/coverage; acl_checks_total{path} (§7).
  • I5: health probes never block the apply path. Goroutine count compared with apply latency; check_probe_goroutines (§7).
  • I6: a retried or replayed mutation applies once, deduped by request UUID. Replay fixture catalog/dup-apply; catalog_dup_applies_total (§7).
  • I7: watch coalescing is one fan-out per table transition. A 10K-waiter load test; watch_waiters_gauge, and past the cap it sheds with a 503 (§7).
  • I8: gossip membership is eventually consistent, while catalog membership after Raft apply is linearizable within one datacenter. Fixture gossip/idempotent-apply; gossip_events_applied_total (§7).
  • I9: a TTL check gets a grace of at least TTL/2 before going critical. Fixture checks/ttl-grace; check_ttl_grace_triggers_total (§7).
  • I10: KV sessions and locks, once built, must use a monotonic lock-delay and avoid split-brain locks. The feature is deferred, so the detector is a design-review gate (§7, §37).
  • I11: the apply path reads no wall clock. A deterministic-replay harness (§28); apply_nondeterminism_alerts (§7).
  • I12: federation never silently reroutes to a different datacenter. Fixture federation/unreachable-dc; federation_forward_errors_total (§7).
  • I13: auto-deregistration counts continuous critical time, and a pass resets it. Fixture checks/hysteresis-reset; check_dereg_counter_resets_total (§7).

What breaks in production

All from §25.

  • FM1: leader loss. Symptom: writes stall briefly. Cause: leader crash or partition. Detection: raft_leader_changes_total. Recovery: automatic election within the RTO of under 500 ms (§4); tune the heartbeat/election-timeout ratio long term.
  • FM2: gossip false-positive storm. Symptom: many nodes turn critical at once. Cause: a GC pause or network blip triggers mass suspicion. Detection: a spike in gossip_suspect_to_dead_total. Recovery: Lifeguard-style dynamic timeout backoff (§18.9); widen the probe timeout, and tune GOGC and gossip timeout together. P8 names the same GC-to-false-suspicion chain.
  • FM3: watch fan-out storm. Symptom: a CPU spike on every notify. Cause: a coalescing bug, an I7 violation. Detection: watch_waiters_gauge against notification count. Recovery: none automatic; restart the agent, and the fixture watch/coalesce-10.yaml guards it in CI.
  • FM6: KV and catalog write contention. Symptom: KV latency rises under catalog load. Cause: the shared single-leader log (ADR-08). Detection: correlating kv_write_latency_seconds with catalog_write_latency_seconds. Recovery: rate-limit the noisy KV client; consider a KV-priority lane if chronic (§37 escape hatch).
  • FM8: federation partition. Symptom: ?dc=remote calls error. Cause: the WAN link is down. Detection: federation_forward_errors_total. Recovery: none automatic by design, since I12 says fail loud; repair the network and alert on sustained dc_unreachable.
  • FM9: check-engine goroutine leak. Symptom: memory grows over days. Cause: a probe goroutine that does not exit when its check is deregistered. Detection: check_probe_goroutines trending up. Recovery: restart the agent, and add a leak regression fixture.
  • FM10: snapshot growth runaway. Symptom: disk use exceeds the 3× amplification budget (§4). Cause: a snapshot interval too long for the write rate. Detection: the storage-amplification-ratio metric. Recovery: force an out-of-band snapshot; tune the interval dynamically (§34.8).

Threats a reader should know (§24): T3 DNS cache poisoning by spoofed UDP answers, handled structurally because DNS has no write path (P5). T4 DNS amplification, where small forged-source queries reflect large SRV answers at a victim, answered by response-size rate limiting and EDNS0 buffer caps. T9 stale authorization after token revocation, answered by event-driven cache invalidation (I4) with a forced flush as recovery. T10 remote code execution through script checks, avoided by not building the feature yet (§37). T14 a long-poll flood, answered by bounded pools (ADR-21, P13), the 10K ceiling (§4) and a 503 shed.

How it compares

  • Consul is the closest analog. It also uses Raft plus SWIM+Lifeguard, with a blocking-query watch (§33). This design bundles KV and catalog under one log; Consul's separation wins where unrelated app config writes swamp catalog latency (§33, §37).
  • etcd runs every operation, membership included, through Raft and watches by gRPC stream with revisions (§33). That wins in Kubernetes-scale control planes where one linearizable source of truth is worth the leader-serialization cost this design avoids for gossip (§33).
  • ZooKeeper gives ephemeral znodes with a client-held session and one-shot watches (§33). It wins when the need is generic coordination (locks, elections, config) rather than a registry, at the cost of building registry semantics yourself (§33, §36 Alternative D).
  • Eureka is AP: stale reads during a partition and a self-preservation mode (§33). It wins when serving a slightly stale list beats refusing reads, the opposite of P2 (§33, §36 Alternative C).
  • CoreDNS is a pluggable DNS middleware chain that fronts etcd, Kubernetes or files (§33). It wins when one DNS server fronts several backends, at the cost of the tight DNS-to-catalog integration this design uses for I3's health filtering (§33, §15).

Questions to test yourself

  1. Why is DNS forbidden as a write path (P5), and what specific invariant (not just "bad practice") would a DNS-UPDATE-style mutation violate? — Hint: §6 P5, §7 I3 and §8.4.
  2. Gossip and Raft both "replicate" something — precisely what does each replicate, and why would merging them into one mechanism break P2? — Hint: §6 P2, §18.2 and §33.
  3. Why is the catalog index global rather than per-table or per-row, and what specific blocking-query behavior breaks if you shard it? — Hint: §7 I1, §13.2 and §13.6.
  4. Why does a TTL check need a grace period at all — what physical phenomenon does TTL/2 actually bound, and what happens at exactly zero grace? — Hint: §7 I9, §16.2 and §16.8.
  5. Why does auto-deregistration require continuous critical duration rather than a simple counter of critical observations, and what specific flapping scenario does the distinction prevent? — Hint: §7 I13, §8.2 and §16.9.

If you only remember three things

The catalog is one Raft-ordered log with one global index, applied deterministically and idempotently, so every watch, DNS answer and replay can be explained from that order (I1, I6, I11, MM2). Consistency is chosen per subsystem: strong for the catalog, probabilistic gossip for membership, and a read-only, health-filtered view for DNS (P2, MM4, I3). Failures are made loud and bounded, with an unreachable datacenter returning an error, every queue capped and every deferred feature carrying a trigger (I12, ADR-21, MM8).

Words used here

  • Agent: the discoveryd process on one node, in server or client role (§1).
  • Catalog: the Raft-replicated map of nodes, services, instances and checks (§7, §13).
  • Instance: one addressable copy of a service on one node (§11.1).
  • Index: the global, monotonic counter that orders catalog changes; a logical clock, not a time (I1).
  • Blocking query: a long-poll HTTP request parked on an index until something changes (§8.5).
  • Coalescing: fanning a single notification out to every waiter on the same table (I7).
  • Raft: the consensus protocol that gives the catalog and KV one agreed log (ADR-07).
  • Gossip: spreading membership news by nodes pinging each other and piggybacking updates (§8.7).
  • Suspicion: the in-between state before a node is declared dead, which bounds false positives (P11).
  • Hysteresis: requiring several consecutive results before a health state changes (§8.2).
  • SRV record: a DNS record carrying priority, weight, port and target (§8.4).
  • Federation: forwarding reads to another datacenter without merging state (§21, MM6).
  • Idempotent apply: applying the same request twice has the effect of applying it once (I6).
  • Backpressure: bounding queues and pools so overload sheds work instead of exhausting memory (P13).
