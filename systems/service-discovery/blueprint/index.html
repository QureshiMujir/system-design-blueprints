1. Goal & Scope

Service Discovery (project 181) is a Consul-class distributed service-registry and discovery system: a per-node agent (discoveryd) through which workloads register and deregister; a health-check engine that probes them via TTL, HTTP, TCP, and gRPC checks; a strongly-consistent catalog of nodes, services, instances, and checks replicated via Raft; a DNS interface (RFC 1035 / 2782 / 6891) and an HTTP API with blocking-query watches that resolve that catalog; a SWIM+Lifeguard gossip layer that disseminates cluster membership; and a federation layer that forwards reads across datacenters. It is not a load balancer, not a service-mesh data-plane proxy, not a general-purpose document/relational database (the embedded KV is a flat namespace, not a query engine), and not a DNS resolver cache.

Phase-0 deliverable — numbered module list (built end to end by §12, Phase 0):

  1. internal/catalog — in-memory + Raft-replicated catalog: nodes, services, instances, checks, the monotonic index, watch waiters.
  2. internal/httpapi — register / deregister / list / health / KV / blocking-query HTTP surface.
  3. internal/dns — UDP + TCP DNS server (A / AAAA / SRV) resolving from the catalog.
  4. internal/checks — TTL / HTTP / TCP / gRPC health-check engine.
  5. internal/kv — embedded KV adapter sharing the catalog's Raft log.
  6. internal/gossip — thin adapter over the workspace's SWIM+Lifeguard gossip library.
  7. internal/raft — thin adapter over the workspace's Raft library.
  8. internal/acl — token / policy / namespace evaluation.
  9. internal/federation — WAN gossip pool + cross-datacenter forwarding.
  10. internal/sidecar — Unix-socket local-registration bridge.
  11. internal/connect — mTLS mesh stretch surface (CA, intentions, proxy scaffolding; implementation deferred, see §22, §37).
  12. cmd/discoveryd, cmd/discoveryctl, cmd/conformance — the agent binary, the CLI client, the conformance-fixture runner.

System boundaries.

  • Provides: registration, health checking, catalog replication, DNS/HTTP resolution, blocking-query watches, an embedded KV, gossip membership, ACLs, federation, a sidecar bridge.
  • Delegates: consensus internals to the workspace Raft crate (ADR-07, Raft project rank 39); gossip failure-detector internals to the workspace gossip crate (ADR-06, Gossip-Protocol project rank 74); mTLS certificate issuance internals to the workspace TLS crate (ADR-17, TLS-SSL-Handshake project rank 50, consumed in §22).
  • Does NOT provide: request proxying/load balancing (clients resolve, then connect directly or via their own proxy); a production service-mesh data plane (§22 ships CA + intentions scaffolding only); a query engine over the KV; DNSSEC signing (no verifiable authority chain is modeled).

Non-goals: a Kubernetes CRD/operator integration; a hosted multi-tenant SaaS control plane (only licensed for via ADR-22, never built here); a general pub/sub bus (watches are catalog-scoped only, §8.5).

Deployment model: one static Go binary (discoveryd) per node, run in -server or -client role; servers form one Raft quorum per datacenter; clients forward register/ deregister/health traffic to a local or nearby server.

Target users/operators: platform/infra engineers running 10–10,000 service instances across one or more datacenters; on-call engineers debugging registration, health, or DNS incidents under the runbooks in §26.

What later phases unlock: §18 (gossip) decouples membership from the Raft leader's serialization point, unlocking horizontal scale past a single-leader write ceiling; §21 (federation) unlocks multi-region deployment; §22 (Connect) unlocks a zero-trust mTLS data plane atop the existing catalog.

Recommended language + rationale: Go 1.22+ (ADR-01). Rejected: Rust — memory-safety win, but a smaller pool of the workspace's existing gossip/Raft/KV crates (all Go) and slower iteration on HTTP/DNS stdlib surfaces; Java/Kotlin — JVM heap and cold-start overhead conflict with the "<1 s cold-start" constraint (§4); C++ — manual memory management raises defect rate on a large concurrent codebase without a compensating performance need at this scale (§34).

Prerequisites: Go modules, context.Context cancellation, golang.org/x/sync primitives; DNS wire format (RFC 1035), SRV (RFC 2782), EDNS0 (RFC 6891); TCP/UDP/HTTP1.1 framing; the gRPC health-checking protocol; gossip/SWIM and Raft at a working-knowledge level (both are consumed as libraries here, not re-derived — ADR-06/ADR-07).

Estimated timeline: Phase 0 in 1 week (§12); the full system (Phases 0–11) in roughly 16 weeks (~4 months) at one FTE per §40's per-phase durations, plus a 30-day fuzz-soak buffer (M12, §30) before a hardened release.

Deferred features (flagged PhaseDeferred("§N"), registered in the Deferred Features Register, §37): script/alias checks (§16); KV sessions/locks (§17); /v1/txn (§14); prepared queries, EDNS0 client-subnet, and DNS-over-HTTPS (§15); the full Connect mesh data plane (§22); full multi-tenant namespace isolation (§19); snapshot-to-S3 and an operator web UI (§26).

2. Why Build This

  • Unique systems knowledge. The exact place DNS-only discovery fails (TTL granularity, zero metadata, no health-awareness) and where HTTP-polling fails at scale (thundering herd) — both are visible only once you have implemented blocking queries yourself (§8.5).
  • Architectural importance. Service discovery sits at the intersection of four hard subfields — consensus (catalog writes, §13), failure detection (gossip + health checks, §16/§18), naming (DNS, §15), and access control (ACLs, §19) — few systems force correct composition of all four.
  • Historical context. Consul (2014) proved bundling KV + catalog + DNS + gossip into one agent beats point solutions (ZooKeeper for coordination, a separate DNS-based discovery tool, separate config management) on operational simplicity; Kubernetes later proved the opposite axis — decompose into Endpoints/EndpointSlice + CoreDNS + etcd — wins once a control plane already exists (§36 alternative D).
  • Engineering muscles built. Bounded concurrency (goroutine-per-check ceilings, §16), lock discipline under one catalog mutex (§13), byte-for-byte wire-protocol correctness (RFC 1035, §15), operator-facing error design (§26).
  • Cross-links to sibling systems (by name): consumes the Raft project (rank 39) as its replicated log (ADR-07), the Gossip-Protocol project (rank 74) as its membership layer (ADR-06), the Distributed-KV-Store project (rank 38) as its embedded KV (ADR-08), and the TLS-SSL-Handshake project (rank 50) as its Connect CA (ADR-17) — the portfolio's clearest exercise in composing previously built primitives rather than re-deriving them.
  • Calibration value. After this build, Consul's, etcd's, or ZooKeeper's source maps directly onto a decision you already made and defended.

What Mastery Looks Like

  • Explain, unprompted, why the catalog index is global rather than per-row (§13; I1).
  • Derive the memory/bandwidth cost of a target-scale cluster from first principles (§34).
  • Defend, with a rejected-alternative argument, why gossip governs membership while Raft governs the catalog (§18; ADR-06, ADR-07).
  • Debug a "watch never fires" incident by naming which of I1/I2/I7 is violated (§13, §20).
  • Design the ACL token-revocation path without a stale-cache window (§19; I4).
  • Explain federation's latency floor as cross-DC RTT, not code inefficiency (§21; §34.11).
  • Pick the right one of the four Alternative Architectures (§36) for a given regime.

  • Operators/Clients: CLI (discoveryctl), sidecar libraries, Kubernetes controllers, an optional web UI (deferred, §26) — never talk to the cluster directly, always through a local agent (P1).
  • HTTP API: register/deregister/list/health/KV/blocking-query surface; the only write path into the catalog (P5); §14.
  • DNS Server: read-only resolver over the catalog; UDP+TCP on port 8600; §15.
  • KV Front: HTTP surface over the embedded KV; shares the catalog's Raft log (ADR-08); §17.
  • Sidecar Bridge: Unix-socket local registration path, filesystem-permission auth boundary; §22.
  • Catalog/Registry: the single source of truth — nodes, services, instances, checks, the global monotonic index (I1), watch waiters (I7); §13.
  • Health Check Engine: one goroutine per check; asynchronous, never blocks the apply path (I5); §16.
  • Gossip/Membership: SWIM+Lifeguard failure detection and membership dissemination, eventually consistent (P2); §18.
  • Replicated Log (Raft): linearizable catalog and KV writes; leader-serialized apply path; §8.6, §13.
  • Embedded KV: flat key-value namespace for operator/application configuration, replicated through the same log as the catalog (ADR-08); §17.
  • Federation: WAN gossip pool tracking remote datacenters' server addresses, plus a thin cross-DC forwarding RPC; reads only, never replicates state; §21.

The agent is one binary; role (-server/-client) is chosen at startup. A client-role node registers local workloads with its own agent over the HTTP API or the sidecar socket; the local agent forwards register/deregister/health updates into the cluster.

6. Design Principles

  1. P1 — Local agent first. The data path is workload → local agent → cluster; workloads never speak to the cluster directly. Tradeoff: one extra local hop. Operational implication: agent must be as available as the workload itself. Violating it: bypassing to the cluster removes the ACL/queueing boundary and reintroduces thundering-herd polling.
  2. P2 — Strong consistency for the catalog, eventual for membership. Catalog writes go through Raft; membership rides gossip. Tradeoff: two different staleness models in one system. Operational implication: never treat a gossip-suspected node as catalog-authoritative without a confirming health check. Violating it: blurs CP and AP guarantees, breaking §35's consistency answers.
  3. P3 — Blocking queries are the watch primitive. No callbacks, no push, no WebSocket; a monotonic index plus long polling. Tradeoff: higher per-connection FD cost than push. Operational implication: coalescing (I7) is mandatory, not optional. Violating it: reintroduces client-side polling and its thundering herd.
  4. P4 — Health is opinionated. A service is passing, warning, or critical; no "unknown" outside an explicit registration grace period. Tradeoff: less expressive than free-form status strings. Operational implication: DNS/HTTP consumers get a closed enum to switch on. Violating it: ambiguous states leak into client logic.
  5. P5 — DNS is read-only and lossy. Writes go through the HTTP API only; DNS returns the freshest local snapshot, not a consensus-confirmed read. Tradeoff: DNS answers can be microseconds stale. Operational implication: never build a write path on top of DNS. Violating it: breaks I3 and confuses operators about durability.
  6. P6 — ACLs are not an afterthought. Every read and write path takes a token, validated against a cluster-replicated cache. Tradeoff: a cache-invalidation problem on every write path. Operational implication: token revocation must be a first-class Raft-replicated event (I4). Violating it: creates an unauditable write path.
  7. P7 — Federation is a first-class operating mode. Cross-DC forwarding is a property of the agent, not a bolt-on sidecar. Tradeoff: every server must carry WAN gossip state. Operational implication: an unreachable DC is a hard error, never a silent fallback (I12). Violating it: hides partitions as data-loss-shaped bugs.
  8. P8 — The agent must run forever. No allocations on hot paths after warmup; no blocking I/O in the gossip loop; watch coalescing prevents fan-out storms. Tradeoff: more upfront design work per hot path. Operational implication: profile every phase (§30). Violating it: GC pressure turns into missed gossip deadlines and false suspicions.
  9. P9 — Determinism for the catalog log. Every state transition is reproducible from the log; no clocks in the apply path (I11). Tradeoff: harder to express TTL-style logic (must be driven by an external timer feeding a deterministic event, not a clock read inside apply). Operational implication: replay-based debugging works. Violating it: two replicas can diverge on replay.
  10. P10 — Operator empathy. Every error carries a code, a one-line cause, and a runbook pointer; discoveryctl validate checks config without starting the agent. Tradeoff: more error-taxonomy upkeep. Operational implication: incident triage time drops. Violating it: on-call debugging degrades to log-archaeology.
  11. P11 — Failure detection is probabilistic, not binary. A suspicion state exists (Das/Gupta/Motivala 2002) between "alive" and "dead" to bound false-positive rate. Tradeoff: slower worst-case detection than an instant binary flip. Operational implication: convergence-time SLOs (§4) are a function of the suspicion timeout, not just RTT. Violating it (removing suspicion) inflates false-positive churn under GC pauses or transient packet loss.
  12. P12 — Every write path is idempotent. The catalog treats a duplicate apply (retried register, replayed Raft entry) as a no-op keyed by request UUID. Tradeoff: an extra dedup-key column per mutation. Operational implication: safe client-side retry without double-registration. Violating it: retries after a timeout silently duplicate state.
  13. P13 — Backpressure over unbounded queues. Check-engine goroutines, watch fan-out buffers, and the HTTP accept queue are all explicitly bounded. Tradeoff: a saturated agent starts rejecting instead of queueing forever. Operational implication: a predictable memory ceiling under load spikes (§4). Violating it: unbounded goroutines convert a load spike into an OOM kill.
  14. P14 — One numbering authority for the log. The catalog and the KV are one Raft log with one monotonic index (ADR-08); there is no second index counter anywhere in the system. Tradeoff: KV and catalog throughput compete for the same leader. Violating it (a second index) breaks blocking-query coalescing across catalog and KV reads.

8. Domain Model / Protocol / Data Model

8.1 Catalog Entity Model

Entities (types defined in full in §11.1): Node 1—N Instance (a node hosts many service instances); Service 1—N Instance (a service name has many instances across nodes); Instance 1—N Check (an instance carries zero or more checks); Check has exactly one CheckStatus. Every entity carries CreateIndex/ModifyIndex (I1) and is addressed by a stable ID, never a mutable name, to keep DNS names decoupled from primary keys.

8.2 Check Status State Machine

State Event Next State Condition
(none) register with check critical (or passing if SuccessBeforePassing=0) initial grace applies (I9)
passing N consecutive failures critical N ≥ FailuresBeforeCritical
passing 1 warning-class probe result warning HTTP 429/503 only (§16.3)
warning N consecutive successes passing N ≥ SuccessBeforePassing
warning N consecutive failures critical N ≥ FailuresBeforeCritical
critical N consecutive successes passing N ≥ SuccessBeforePassing
critical continuous critical ≥ DeregisterCriticalServiceAfter (deregistered) I13; counter resets on any success

8.3 DNS Query Grammar (EBNF)

question    = service-q | node-q | prepared-q ;
service-q   = [ tag "." ] service "." "service" "." [ dc "." ] domain ;
node-q      = node "." "node" "." [ dc "." ] domain ;
prepared-q  = query-name "." "query" "." [ dc "." ] domain ;  (* deferred, §15 *)
dc          = label ;
domain      = label , { "." , label } ;
label       = ALPHA , { ALPHA | DIGIT | "-" } ;

dc defaults to the agent's local datacenter; domain defaults to discovery. and is never hard-coded (§16.6 Pitfalls references this same rule for the check-domain string).

8.4 DNS Response Composition

Record Source field Filter applied
A / AAAA Instance.Address (or Node.Address if unset) I3
SRV priority=0, weight from Weights.{Passing,Warning}, port=Instance.Port, target=Node.Node I3
TXT (metadata, opt-in) Instance.Meta I3

8.5 HTTP Blocking-Query Protocol (sequence)

  1. Client issues GET .../health/service/web?index=41&wait=5m.
  2. Handler snapshots current index; if current > 41, responds immediately (§14.2).
  3. Else the handler registers a waiter on the service's notification channel (I7) and blocks on min(wait, 10m), floored at 100 ms to coalesce bursts (§20.2).
  4. On notify (after I2's ordering) or timeout, the handler re-snapshots under the lock and returns (index, data); a timeout returns the same index unchanged.
  5. X-Consul-Index, X-Consul-LastContact, X-Consul-KnownLeader are set on every response, blocking or not (§14.2).

8.6 Raft Log Entry Wire Layout

RaftLogEntry {
  term        uint64          // Raft term (opaque to the catalog, ADR-07)
  index       uint64          // Raft log index (distinct from catalog.Index, I1)
  kind        uint8           // 0=RegisterNode 1=DeregisterNode 2=RegisterService
                               // 3=DeregisterService 4=RegisterCheck 5=UpdateCheck
                               // 6=KVPut 7=KVDelete 8=ACLTokenRevoke
  request_id  [16]byte        // UUID, dedup key (I6, P12)
  payload     []byte          // kind-specific, protobuf-encoded (ADR-04 serialization)
  crc32       uint32          // corruption check on read
}

8.7 Gossip Message Envelope (SWIM, LAN pool)

GossipEnvelope {
  msg_type    uint8   // 0=Ping 1=IndirectPing 2=Ack 3=Suspect 4=Alive 5=Dead 6=UserMsg
  seq         uint32  // per-sender sequence, dup suppression
  from        NodeID  // gossip-layer identity, NOT the catalog Node.ID
  piggyback   []byte  // infection-style disseminated updates (Das/Gupta/Motivala §2)
}

NodeID is a gossip-layer identity distinct from catalog.Node.ID; the adapter (internal/gossip/adapter.go, §18.1) is the only code that maps between the two.

8.8 Worked Example: Service Registration End to End

PUT /v1/agent/service/register {"Name":"web","Port":8080} → HTTP handler validates ACL token (I4) → builds a RegisterRequest (§11.2) → catalog ApplyRegisterService upserts Node, Service, Instance under one lock acquisition, assigns index 42 (I1) → notifies the web service channel (I2 ordering) → a blocking GET .../health/service/web?index=41 wakes within the coalescing window (§20.2) and returns index 42 with the new instance → dig web.service.dc1.discovery. SRV returns the instance once its first check reaches passing (I3).

8.9 Malformed Input Examples

Input Issue Expected Handling
DNS question ..service.dc1.discovery empty label FORMERR, no panic
PUT /v1/agent/service/register {"Port":"abc"} non-numeric port 400 with error code EINVALIDPORT

8.10 Failure-Path Example: Leader Loss Mid-Blocking-Query

A blocking query is parked on index 100 when the Raft leader crashes. The waiter's context is not canceled (it is agent-local, not leader-bound). A new leader is elected within the RTO (§4); the next write on the new leader bumps the index past 100 and the local catalog (now following the new leader's replicated stream) notifies the parked waiter normally. If no write occurs before wait expires, the client receives the unchanged index 100 — never an error — matching P5's "lossy but never wrong" contract.

13. Phase 1 — Catalog & In-Memory Registry (Week 2)

13.1 Objectives

  • Implement the in-memory catalog (§11.1) with the global monotonic index (I1) and watch waiters (I7).
  • Ship a local-only registration path (no gossip/Raft wiring yet — that lands in §18).

13.2 Detailed Implementation Steps

  • catalog.go: a struct guarded by one sync.RWMutex (P9, I11 — no clock reads inside the lock); reads take RLock, writes take Lock.
  • index.go: nextIndex() increments a uint64 under the write lock (I1); never reset except on wipe.
  • apply.go: ApplyRegisterService upserts Node→Service→Instance→Checks in one lock acquisition (ADR-07 apply-path discipline), assigns one index to the whole batch, dedups by RegisterRequest.RequestID (I6, P12).
  • watch.go: one notification channel per table (services, checks, kv), not per row — implements I7; Stop() every time.Timer in a deferred call to avoid leaks (§13.6).
  • snapshot.go: periodic encode of the full catalog for Raft snapshotting (wired fully in §18; stubbed here as an in-memory copy).

13.3 Deliverable

internal/catalog/*.go implements §11.1's primitives end to end, single-process, no network yet; a Go API a test harness can call directly.

13.4 Acceptance Criteria

  • A unit test registers 1,000 services and runs 1,000 concurrent blocking waiters; measured p99 wake latency < 10 ms (§4), recorded in benchmarks/results/.
  • go test -race ./internal/catalog/... passes with zero races.
  • Index strictly increases across 10,000 sequential applies (fixture catalog/index-monotonic.yaml).

13.5 Conformance Fixtures

  • catalog/register-basic.yaml — register → visible within one notification cycle (I2).
  • catalog/index-nonzero.yaml — every list response carries Meta.Index > 0.
  • catalog/dup-apply.yaml — replay the same RequestID twice → single resulting instance (I6).
  • catalog/index-monotonic.yaml — 10K applies, index never decreases or repeats.

13.6 Pitfalls

  • Per-row notification channels balloon goroutine count under load — use one table-level channel plus a fan-out step (I7).
  • Notifying before the index increment lets a waiter observe stale state — order must be increment-then-notify (I2).
  • time.NewTimer without Stop() leaks timers under high fan-out — always defer Stop().

13.7 Performance Concerns

  • Single sync.RWMutex is correctness-first, not throughput-optimal; per-row locking or an STM is an explicit non-goal until §30 benchmarks show contention (do not pre-optimize — P8's "no allocations" is about the hot read path, not premature sharding).
  • Snapshot encode must not hold the write lock for the full encode duration — copy under lock, encode outside it.

13.8 Edge Cases

  • Registering an instance whose Node does not yet exist — must upsert the Node implicitly in the same apply, not error.
  • A blocking query with wait exceeding the 10-minute ceiling — clamp, do not error.
  • Concurrent register + deregister of the same Instance.ID — last-writer-by-index wins; no lost update (verified by catalog/dup-apply.yaml's sibling race fixture).

13.9 Failure Analysis

  • Symptom: watchers never wake. Root cause: I2 violated (notify before increment) or a goroutine leak exhausted the scheduler. Detection: watch_waiters_gauge growing unboundedly. Recovery: restart the agent (single-process state only at this phase); root-cause via the deterministic replay harness (§28).

13.10 Operational Notes

  • Metrics: catalog_index_current, watch_waiters_gauge, catalog_dup_applies_total (ADR-10).
  • No persistence yet at this phase — a restart loses all state; this is explicitly acceptable pre-§18 and documented in BUILD_PLAN.md.

15. Phase 3 — DNS Interface (Week 4)

15.1 Objectives

  • Ship the UDP+TCP DNS server (port 8600 default) answering the §8.3 grammar over the catalog.
  • Guarantee I3 (never return critical instances) at the wire level.

15.2 Detailed Implementation Steps

  • server.go: dual UDP/TCP listeners via miekg/dns (ADR-03); TCP is mandatory, not optional — resolvers fall back to it for large responses (RFC 1035 section 4.2.2).
  • handler.go: routes by the §8.3 EBNF; datacenter defaults to local DC, domain defaults to discovery. from Config.Domain (§11.4) — never a literal string in code (P5, §16.6 cross-reference to the same anti-hard-coding rule for checks).
  • records.go: A/AAAA from Instance.Address (fallback Node.Address); SRV priority/weight/port/target per §8.4; filters by CheckStatus per I3.
  • edns0.go: honors client buffer size (RFC 6891); truncates cleanly and sets TC when the response would overflow, letting the resolver re-query over TCP.
  • No response caching in the DNS server itself — the catalog is already the cache (P5); caching, if any, is the resolver's job.
  • prepared.go stubs prepared queries as PhaseDeferred("§15") (registered §37); EDNS0 client-subnet (RFC 7871) and DoH transport (RFC 8484) are likewise PhaseDeferred("§15").

15.3 Deliverable

dig @127.0.0.1 -p 8600 web.service.dc1.discovery. SRV returns every passing instance of web; A/AAAA queries resolve correctly; TCP fallback works for oversized answers.

15.4 Acceptance Criteria

  • DNS A-record p99 over UDP < 5 ms at 1,000 registered instances (§4, M6).
  • 0 critical instances ever appear in a SRV/A/AAAA answer across 10,000 fixture runs (fixture dns/health-filter.yaml).
  • EDNS0 buffer-size compliance verified against 3 buffer sizes (512/1232/4096) in dns/edns0-truncation.yaml.

15.5 Conformance Fixtures

  • dns/health-filter.yaml — mixed passing/warning/critical instances → only passing (+warning if opted in) returned (I3).
  • dns/srv-health-filter.yaml — SRV weight matches Weights.Passing/Weights.Warning.
  • dns/edns0-truncation.yaml — oversized answer sets TC, TCP retry succeeds.
  • dns/malformed-question.yaml — empty label → FORMERR, no panic (§8.9).

15.6 Pitfalls

  • Returning unhealthy instances — the single most important DNS invariant (I3); treat any regression here as a release blocker.
  • Hard-coding the domain string — discovery. is the default, but every test must use a configurable domain (P5).
  • Forgetting TCP — large SRV sets truncate on UDP; skipping TCP breaks real resolvers.

15.7 Performance Concerns

  • miekg/dns message parsing allocates per query; pool dns.Msg buffers to hold the <5 ms p99 target under sustained load (§4).
  • Avoid a DNS-server-side cache (P5) — it would reintroduce a second staleness clock independent of the catalog's index, breaking I3's freshness guarantee.

15.8 Edge Cases

  • Query for a service with zero registered instances — NXDOMAIN, not an empty-but-NOERROR answer that some resolvers cache differently.
  • IPv6-only instance queried via an A (not AAAA) record — return empty answer, not a synthesized/mapped address.
  • EDNS0 buffer size of 0 — degenerate; fall back to the legacy 512-byte limit (§8.9).

15.9 Failure Analysis

  • Symptom: resolvers report intermittent SERVFAIL. Root cause: a panic in a malformed-question path not caught by DNS-equivalent recovery middleware. Detection: DNS server crash-loop metric. Recovery: per-query panic recovery wrapping handler.go; add the triggering question to dns/malformed-question.yaml.

15.10 Operational Notes

  • Metrics: dns_queries_total{qtype,rcode}, dns_answer_latency_seconds (ADR-10).
  • dig-based smoke test is part of make compose-up's health gate.

16. Phase 4 — Health Check Engine (Week 5)

16.1 Objectives

  • Ship the four Phase-0 check kinds (TTL, HTTP, TCP, gRPC) as an asynchronous engine (I5) that never blocks the catalog apply path.
  • Implement hysteresis (I9, I13) to prevent flapping and premature deregistration.

16.2 Detailed Implementation Steps

  • engine.go: one goroutine per check; TTL checks run a deadline timer, HTTP/TCP/gRPC run an interval timer that fires the probe (P8: bounded by check_max_concurrent, default 50, ADR-21's backpressure discipline).
  • ttl.go: PUT /v1/agent/check/{pass,warn,fail}/<id> resets the deadline; on expiry the check transitions to critical only after the I9 grace (≥ TTL/2, default TTL 30 s).
  • http.go: 2xx→passing; 429/503→warning; else→critical; TLS settings honored; operator headers win over defaults on merge.
  • tcp.go: connect success→passing, failure→critical; no warning state exists for TCP (binary reachability signal only).
  • grpc.go: grpc.health.v1.Health/Check; SERVING→passing, else→critical with the error text in Check.Output.
  • status.go: hysteresis counters per §8.2's state table (I9, I13); auto-deregister after DeregisterCriticalServiceAfter of continuous critical (I13 — one passing observation resets the counter).

16.3 Deliverable

A workload registers an HTTP check; the engine polls every 10 s and the catalog reflects passing→warning→critical transitions per §8.2 within one probe interval.

16.4 Acceptance Criteria

  • TTL check missing its deadline transitions to critical within TTL + grace, never earlier (fixture checks/ttl-deadline.yaml).
  • HTTP/TCP/gRPC checks each cover their §8.2 transition table in a fixture with 100% branch coverage of status.go.
  • check_max_concurrent ceiling (50) is enforced under a 200-check load test — no more than 50 in-flight probes observed (check_probe_goroutines metric ≤ 50).

16.5 Conformance Fixtures

  • checks/ttl-deadline.yaml — no pass call before deadline → critical after grace (I9).
  • checks/hysteresis-reset.yaml — one passing observation resets the dereg counter (I13).
  • checks/passing-only-filter.yaml — HealthReader excludes warning/critical when passingOnly=true.
  • checks/grpc-not-serving.yaml — NOT_SERVING → critical with populated Output.

16.6 Pitfalls

  • Running probes inline with the API request — probes must run on dedicated goroutines (I5); this is the single most common regression in this subsystem.
  • Holding the catalog lock during a probe — probes write asynchronously via ApplyCheckUpdate, never inline with the lock held.
  • Hard-coding TTL/2 instead of reading Config-driven grace — clock skew tolerance must be operator-tunable (mirrors §15.6's domain-hard-coding pitfall).
  • Script checks (CheckScript) and alias checks (CheckAlias) are PhaseDeferred("§16") (registered §37) — do not accidentally wire their execution paths this phase; the enum values exist, the engine dispatch does not.

16.7 Performance Concerns

  • 50 concurrent probes × ~200 ms average HTTP probe duration bounds sustainable check throughput at ≈ 250 checks/sec/agent (§34.12) — surface this ceiling to operators configuring check intervals.
  • gRPC health-check dialing should reuse a connection pool per target, not dial fresh per probe (amortizes TLS handshake cost, relevant once ADR-17's mTLS lands).

16.8 Edge Cases

  • A check whose Interval is shorter than its own Timeout — reject at registration with EINVALIDCHECK, do not silently overlap probes.
  • Clock skew between the agent and a TTL-updating client — the I9 grace absorbs typical NTP drift; document the assumed bound (±5 s) in docs/operator-guide.md.
  • Probe goroutine panics — must be recovered per-probe, must not crash the engine or leave the check stuck in its last-known status.

16.9 Failure Analysis

  • Symptom: a service flaps passing↔critical every few seconds. Root cause: hysteresis misconfigured (FailuresBeforeCritical=1) or a genuinely flaky dependency. Detection: check_status_transitions_total rate. Recovery: raise the threshold; if genuine, this is a signal for the operator, not a bug — document in the runbook (§26).

16.10 Operational Notes

  • Metrics: check_status{check_id} (gauge, 0/1/2), check_probe_goroutines, check_status_transitions_total (ADR-10).
  • Runbook docs/runbooks/runbook-node-failure.md covers "all checks on a node go critical simultaneously" (correlate with gossip suspicion, §18).

17. Phase 5 — Embedded KV Store (Week 6)

17.1 Objectives

  • Wire the embedded KV (Distributed-KV-Store crate, ADR-08) sharing the catalog's Raft log and index (P14 — one numbering authority).
  • Implement CAS semantics per the HAT tradeoffs (Bailis et al. 2014).

17.2 Detailed Implementation Steps

  • adapter.go: thin wrapper translating KV interface calls (§11.5) into the same RaftLogEntry stream as catalog writes (kind 6/7 in §8.6) — one apply path, one index (ADR-08, P14).
  • CAS write: PUT /v1/kv/:key?cas=N succeeds only if KVPair.ModifyIndex == N; anchors to the HAT paper's read-committed-CAS pattern (§5 Papers, Bailis 2014).
  • Recursive ops: ?recurse on GET returns all keys under a prefix; on DELETE removes them atomically in one apply (one index bump, not N).
  • Sessions/locks (sessions.go) are PhaseDeferred("§17") (registered §37) — the file exists with type stubs (KVPair.Session field, §11.3) but no lock-acquisition logic ships this phase.

17.3 Deliverable

KV CRUD (GET/PUT/DELETE/prefix-list) works against the single-node agent; blocking KV reads coalesce on the same index as blocking catalog reads.

17.4 Acceptance Criteria

  • KV write throughput ≥ 10,000 ops/sec on a single leader (§4, M4), recorded in benchmarks/results/.
  • A CAS write with a stale ModifyIndex returns (false, _, nil) and performs zero mutation (fixture kv/cas-mismatch.yaml).
  • A recursive delete of 1,000 keys is observed as exactly one index increment.

17.5 Conformance Fixtures

  • kv/cas-mismatch.yaml — stale CAS → no-op, false returned.
  • kv/recursive-delete-atomic.yaml — prefix delete is one index bump, not N.
  • kv/blocking-coalesce.yaml — a KV blocking read and a catalog blocking read on the same index wake in the same notification cycle.

17.6 Pitfalls

  • Treating the KV as a separate service with its own index counter — it shares the catalog's Raft log; a second counter breaks P14 and blocking-query coalescing.
  • Building session/lock logic ahead of schedule — PhaseDeferred("§17") (registered §37) exists precisely because lock-delay semantics (I10) need a dedicated design review first.

17.7 Performance Concerns

  • Recursive delete over a large prefix must not hold the write lock for an unbounded scan — batch the scan under a read lock, then apply the delete set in one write-lock acquisition.
  • CAS retries under contention should back off (exponential, capped) rather than hot-loop against the leader.

17.8 Edge Cases

  • PUT with cas=0 on a key that does not yet exist — succeeds (create-if-absent semantics, matching Chubby-style CAS conventions, Burrows 2006).
  • A key containing / used both as a leaf and as a prefix elsewhere — must not silently merge two logical namespaces; document the flat-namespace contract.
  • ?recurse on a prefix matching zero keys — returns an empty list, not 404.

17.9 Failure Analysis

  • Symptom: KV writes stall under catalog write load. Root cause: single-leader contention (§4's throughput ceilings are additive across catalog+KV, ADR-08's known tradeoff). Detection: kv_write_latency_seconds vs. catalog_write_latency_seconds correlation. Recovery: none at this phase (documented tradeoff); §37 tracks a separate-cluster escape hatch if this becomes binding.

17.10 Operational Notes

  • Metrics: kv_ops_total{op}, kv_cas_conflicts_total (ADR-10).
  • Backup/restore of the KV rides the same snapshot mechanism as the catalog (§26).

18. Phase 6 — Multi-Node Gossip Membership (Weeks 7–8)

18.1 Objectives

  • Turn the standalone agent into a cluster: wire SWIM+Lifeguard membership (ADR-06, Das/Gupta/Motivala 2002) and translate gossip events into catalog operations (I8).

18.2 Detailed Implementation Steps

  • adapter.go: translates gossip events into catalog applies — MemberJoin→ ApplyRegisterNode, MemberLeave→ApplyDeregisterNode, MemberSuspect→annotate node meta _suspect=true, MemberFailed→mark all instances on the node critical (ties to I8 and P11's suspicion-state principle; theory: Gupta/Chandra/Goldszmidt 2001 PODC).
  • LAN pool: 1 s probe / 100 ms gossip interval (§4); WAN pool (federation-facing, scaffolded here, wired fully in §21): 30 s probe / 200 ms gossip interval.
  • Every gossip event apply is idempotent (I6) — duplicate MemberJoin deliveries are a no-op, since gossip can and does deliver duplicates.
  • Clean shutdown routes through the gossip leave path (MemberLeave broadcast before process exit) — converges in milliseconds versus a hard-kill's full probe-interval cost.

18.3 Deliverable

A three-node docker-compose cluster converges to a stable membership view; killing one node is reflected in /v1/health/node/<n> as critical within the convergence budget.

18.4 Acceptance Criteria

  • Convergence after a single node loss < 500 ms in a 3-node cluster (§4, M7).
  • Killing one node reflects as critical in /v1/health/node/<n> within 5 s (fixture gossip/node-failure-convergence.yaml).
  • Duplicate MemberJoin events applied twice produce exactly one Node row (I6).

18.5 Conformance Fixtures

  • gossip/node-failure-convergence.yaml — kill one of three nodes, assert convergence timing.
  • gossip/idempotent-apply.yaml — replay a MemberJoin event, assert no duplicate row.
  • gossip/clean-leave-vs-hard-kill.yaml — compares leave-path timing to kill -9 timing.

18.6 Pitfalls

  • Not idempotently applying member events — gossip delivers duplicates by design (I6).
  • Treating gossip as a Raft substitute — catalog state replicates through Raft only; gossip carries membership exclusively (P2).
  • Skipping the gossip-leave path on shutdown — a hard kill costs a full probe interval before the cluster notices (§18.2).

18.7 Performance Concerns

  • Gossip bandwidth per node stays O(log n) via SWIM's fanout design, not O(n) — verify this scaling empirically at 100/1,000-node simulated fleets (§31).
  • Suspicion-timeout tuning (Lifeguard-style dynamic shrinking, per the memberlist reference implementation, §5) trades false-positive rate against convergence speed — document the chosen operating point.

18.8 Edge Cases

  • A node that flaps join/leave rapidly (container restart loop) — must not destabilize the whole gossip pool's suspicion state for unrelated nodes.
  • Network partition splitting the LAN pool in half — each half converges internally; reconciliation on heal must not create duplicate Node rows (I6 again).
  • Clock skew between nodes — gossip protocol periods are locally timed (I11-adjacent: no cross-node clock dependency in the protocol itself).

18.9 Failure Analysis

  • Symptom: nodes marked critical that are actually healthy (false positive). Root cause: probe timeout too aggressive for the actual network RTT (§4). Detection: gossip_suspect_to_dead_total rate spike correlated with GC pause metrics. Recovery: widen the probe timeout; this is the exact failure mode P11/Lifeguard's suspicion state exists to bound.

18.10 Operational Notes

  • Metrics: gossip_members_total{status}, gossip_suspect_to_dead_total (ADR-10).
  • Runbook docs/runbooks/runbook-node-failure.md walks the convergence timeline an on-call engineer should expect to see.

19. Phase 7 — ACLs, Tokens & Policies (Week 9)

19.1 Objectives

  • Ship token/policy/namespace evaluation (P6) enforced on every read and write path (I4), including DNS's default token and gossip control operations.

19.2 Detailed Implementation Steps

  • token.go: every Token (§11.4) carries a UUID AccessorID (logged on every request, P10), a policy list, an optional namespace. The bootstrap token (global-management) is minted by the leader on first start (ADR-07's leader-only write discipline extended to ACL bootstrap).

19.4 Acceptance Criteria

  • 100% ACL coverage across catalog, KV, DNS-default-token, and gossip control paths, verified by fixture acl/coverage.yaml (I4) — zero unchecked paths.
  • Token revocation propagates to every agent's local cache within 1 Raft-commit round trip (bounded by §4's RTO), verified in acl/revocation-propagation.yaml.
  • Deny-overrides correctly resolve a conflicting allow+deny policy pair in acl/deny-override.yaml.

19.5 Conformance Fixtures

  • acl/coverage.yaml — enumerates every HTTP/DNS/gossip-control path, asserts a token check fires on each (I4).
  • acl/deny-override.yaml — conflicting policies resolve to deny.
  • acl/revocation-propagation.yaml — revoke → next request on every agent gets 403.

19.6 Pitfalls

  • Bypassing the cache on hot paths — every request validates; the cache exists so validation stays local and microsecond-scale, not to skip validation.
  • Letting an expired-but-not-yet-evicted token authenticate — cache TTL is conservative (default 30 s) but revocation (I4) is event-driven, not TTL-dependent, for correctness.
  • Forgetting DNS/gossip-control ACL coverage — HTTP-only ACL plumbing is the most common regression in this subsystem.

19.7 Performance Concerns

  • Token cache lookup must stay off the catalog's write lock — a slow ACL check must never become a catalog-apply bottleneck (I5-adjacent discipline extended to ACLs).
  • Policy-rule matching (prefix trees) should be O(prefix length), not O(policy count) — benchmark at 10,000 policies.

19.8 Edge Cases

  • A token whose only policy is revoked mid-request — the in-flight request completes under its cached decision; the next request is denied (documented eventual-denial window, bounded by cache TTL).
  • Bootstrap called twice — second call fails cleanly with EALREADYBOOTSTRAPPED, does not mint a second root token.
  • A policy referencing a namespace that does not exist — treated as matching nothing (deny by default), not an error.

19.9 Failure Analysis

  • Symptom: a revoked token still authenticates on one agent. Root cause: that agent missed the Raft-committed revocation entry (partition or lag). Detection: acl_cache_staleness_seconds per agent. Recovery: force cache flush via discoveryctl acl cache-flush; root-cause via Raft replication lag metrics.

19.10 Operational Notes

  • Metrics: acl_checks_total{path,result}, acl_cache_staleness_seconds (ADR-10).
  • Runbook docs/runbooks/runbook-acl-lockout.md covers "operator locked themselves out" recovery via the bootstrap token's break-glass procedure.

20. Phase 8 — Watches, Coalescing & Long-Poll Hardening (Week 10)

20.1 Objectives

  • Deepen the Phase-1 watch primitive (§13.3) to production hardness: per-service, per-key, catalog-wide, and event-stream watch types, all sharing I7's coalescing discipline.

20.2 Detailed Implementation Steps

  • Watch types: per-service (/v1/health/service/<svc>?index=N), per-key (/v1/kv/<key>?index=N), catalog-wide (/v1/catalog/services?index=N), and an agent event stream (local-only, not Raft-replicated).
  • Coalescing: when N requests block on the same table, one notification fans out to all N — the coalesce buffer is per-table-per-agent and does not survive an agent restart (I7; theory anchor: this is the server-side analogue of etcd's single-gRPC-stream watch multiplexing, §5 Reference Implementations).
  • Long-poll deadline default 5 minutes, server-side cap configurable, to avoid exceeding common reverse-proxy timeouts (documented operator knob, §26).
  • Re-snapshot under the lock after the wake signal, never reuse a pre-wake snapshot — prevents returning stale data on wake.

20.3 Deliverable

A discoveryctl watch CLI streams catalog changes in real time; a load test sustains 10,000 concurrent blocking queries.

20.4 Acceptance Criteria

  • 10,000 concurrent blocking queries sustained with p99 wake latency < 10 ms after notify (§4), recorded in benchmarks/results/.
  • Coalescing verified: 10 simultaneous waiters on one service receive exactly 1 underlying notification event (fixture watch/coalesce-10.yaml).
  • Zero stale-snapshot-on-wake occurrences across 1,000 fixture runs.

20.5 Conformance Fixtures

  • watch/coalesce-10.yaml — 10 waiters, 1 notification, all wake with identical data.
  • watch/stale-snapshot-regression.yaml — regression guard for the re-snapshot-after-wake rule.
  • watch/10k-load.yaml — sustained 10K-waiter load test with latency histogram output.

20.6 Pitfalls

  • Long-poll deadlines exceeding reverse-proxy timeouts — default 5 minutes, but document and expose the server-side cap explicitly (§26).
  • Returning a stale snapshot on wake — always re-snapshot under the lock post-wake.
  • Per-request goroutines with no ceiling under 10K-waiter load — apply ADR-21's bounded pool here as well, not just to write paths.

20.7 Performance Concerns

  • Coalescing turns O(waiters) wakeups into O(1) per table transition — verify this scaling holds at 10K waiters, not just the 1K tested in §13.
  • Memory per parked waiter (context + response channel) must stay small enough that 10,000 waiters fit comfortably under the §4 memory ceiling.

20.8 Edge Cases

  • A waiter whose context is canceled mid-block (client disconnect) — must be released promptly, not linger until the next notification.
  • Two different watch types (service + catalog-wide) both fire on the same underlying mutation — must not double-count in watch_waiters_gauge.
  • An agent restart with waiters in flight — clients receive a clean connection reset, not a hung connection.

20.9 Failure Analysis

  • Symptom: watch_waiters_gauge grows without bound. Root cause: a coalescing bug parking new waiters on an already-fired (but not cleared) notification channel. Detection: gauge growth uncorrelated with actual client count. Recovery: restart to clear parked state; root-cause via the deterministic replay harness (§28), same methodology as §13.9.

20.10 Operational Notes

  • Metrics: watch_waiters_gauge (already introduced §13.10, now dashboarded, ADR-10), watch_notifications_total{table}.
  • discoveryctl watch is the primary on-call tool for "is this service actually updating" triage.

21. Phase 9 — Federation (Weeks 11–12)

21.1 Objectives

  • Ship cross-datacenter forwarding: a WAN gossip pool tracking remote DCs' server addresses, plus a thin forwarding RPC (P7 — federation is first-class).

21.2 Detailed Implementation Steps

  • wan_gossip.go: servers across DCs join a WAN gossip pool (30 s probe / 200 ms gossip interval, §4) separate from the LAN pool (different port, different key, ADR-17). Membership is eventual; a partition shows up as a missing DC, never a corrupted local catalog (I8 extended across DCs).
  • forward.go: a query with ?dc=remote is forwarded by the local leader to the remote leader; the response is returned verbatim carrying the remote agent's own index (federation reads never merge indexes across DCs — indexes are DC-local, I1 scoped per DC).
  • An unreachable DC returns a hard 503 dc_unreachable error — the agent never silently falls back to a different DC (I12, P7).
  • Federation forwards reads only; it does not replicate state — confusing the two is the #1 conceptual error in this phase (distinguishes federation from Raft replication, ADR-07).

21.3 Deliverable

A two-DC docker-compose cluster; discoveryctl catalog services -dc=dc2 returns the remote catalog; a simulated WAN partition returns a clear, bounded-time error.

21.4 Acceptance Criteria

  • Cross-DC forwarded read latency ≈ local lookup + one WAN round trip, matching the §34.11 derivation (30–150 ms), verified in federation/latency-budget.yaml.
  • A simulated WAN link drop returns 503 dc_unreachable within 5 s (fixture federation/unreachable-dc.yaml, I12).
  • Zero silent-DC-substitution occurrences across 500 fixture runs.

21.5 Conformance Fixtures

  • federation/unreachable-dc.yaml — drop the WAN link, assert the hard error and timing.
  • federation/latency-budget.yaml — asserts forwarded-read latency stays within the derived §34.11 bound.
  • federation/index-non-merge.yaml — asserts a forwarded response's index is the remote DC's own, never merged with the local DC's index.

21.6 Pitfalls

  • Letting clients silently fall back to the wrong DC — an unreachable DC is always an error, never a quiet substitution (I12).
  • Confusing federation with replication — federation forwards reads; the catalog itself is never replicated across DCs by this layer.
  • Reusing the LAN gossip key for WAN — must be a distinct key (ADR-17); a shared key collapses two trust boundaries into one.

21.7 Performance Concerns

  • Cross-DC RTT (30–150 ms, §4) dominates forwarded-read latency; do not attempt to "optimize" this — it is a physical floor (§34.11), not a code inefficiency, and no amount of local-side batching removes it.
  • WAN gossip's slower probe/gossip cadence (§4) trades convergence speed for lower cross-DC bandwidth — do not tune it to LAN speeds without re-deriving the bandwidth cost (§34.4's formula applies at WAN scale too, with WAN's larger fanout multiplier).

21.8 Edge Cases

  • A DC that becomes reachable again mid-forward — the in-flight request should still complete against a consistent snapshot, not race a reconnect.
  • ?dc= referencing the local DC explicitly — must be a no-op local read, not routed through the forwarding RPC unnecessarily.
  • Two DCs both believing they are unreachable from each other but each individually healthy (asymmetric partition) — each must independently report dc_unreachable rather than one side silently succeeding.

21.9 Failure Analysis

  • Symptom: forwarded reads hang past the 5 s error budget. Root cause: the forwarding RPC has no client-side deadline. Detection: federation_forward_duration_seconds p99 vs. the 5 s SLO. Recovery: enforce a hard context deadline on every forward call; this is a release-blocking defect class, not a tuning issue.

21.10 Operational Notes

  • Metrics: federation_forward_errors_total{dc}, federation_forward_duration_seconds (ADR-10).
  • Federation status surfaced in discoveryctl members -wan for on-call triage.

22. Phase 10 — Sidecar Bridge & Connect Mesh Scaffolding (Weeks 13–14)

22.1 Objectives

  • Ship the Unix-socket sidecar registration bridge (ADR-16 socket-only auth boundary).
  • Land the Connect mTLS mesh directory layout and type scaffolding; implementation is PhaseDeferred("§22") (registered §37).

22.2 Detailed Implementation Steps

  • socket.go: exposes /var/run/discoveryd.sock; local applications register over the socket without a token — filesystem permissions on the socket are the auth boundary (ADR-16, mirrors consul.sock semantics per the Consul reference implementation, §5).
  • bridge.go: forwards socket-received register/deregister calls into the same Registrar interface (§11.5) as the HTTP path — no parallel code path, no drift.
  • connect/ca.go, connect/intentions.go, connect/proxy.go: files exist with type stubs (an SVID descriptor type, an intention-rule type) but no CA issuance, no intention evaluation, no proxy logic ships this phase — each call site carries PhaseDeferred("§22") (registered §37; ADR-17 names the TLS-SSL-Handshake project, rank 50, as the eventual CA implementation source).
  • Document the platform matrix: Unix-socket auth is Linux/macOS-native; Windows named pipes are a distinct, unbuilt code path (noted, not implemented).

22.3 Deliverable

A workload registers via the Unix socket and is visible in the cluster within one notification cycle; a docker-compose example demonstrates the sidecar pattern end-to-end; the connect/ directory compiles with stub types only.

22.4 Acceptance Criteria

  • Socket-registered workload appears in /v1/catalog/service/<name> within one notification cycle (reuses I2's ordering guarantee), verified in sidecar/socket-register.yaml.
  • Socket file permissions default to 0700, owner-only, verified in sidecar/socket-permissions.yaml.
  • connect/ package compiles (go build ./internal/connect/...) with zero runnable CA/intention logic — a grep -rn PhaseDeferred internal/connect/ count of ≥ 3 hits confirms the scaffolding-only state.

22.5 Conformance Fixtures

  • sidecar/socket-register.yaml — register over the socket, assert catalog visibility.
  • sidecar/socket-permissions.yaml — asserts 0700 default, rejects a world-writable socket configuration at startup.
  • sidecar/bridge-no-duplicate-path.yaml — asserts the socket path and HTTP path share one Registrar implementation, not two.

22.6 Pitfalls

  • Auth via socket permissions alone is fine on Linux, but Unix sockets behave differently on macOS/Windows — document the platform matrix rather than assuming parity.
  • Connect CA rotation is non-trivial — plan the rotation runbook before issuing a first certificate, even though issuance itself is deferred (§37); designing the rotation story after the fact is the #1 real-world Connect-category incident cause.
  • Building a second registration code path for the socket instead of reusing Registrar — creates silent drift between socket and HTTP semantics.

22.7 Performance Concerns

  • Unix-domain-socket I/O has lower per-call overhead than TCP loopback — expect the socket path's registration latency to be strictly ≤ the HTTP path's.
  • Stub connect/ types must not be imported into any hot path — a stub struct with an unused import can still add binary size/startup cost; keep the scaffolding inert.

22.8 Edge Cases

  • Socket file left over from a crashed previous instance — startup must remove and recreate it, not fail to bind.
  • A registration request over the socket carrying an ACL token — must be rejected or ignored consistently (socket path is no-token by design, ADR-16); document which.
  • Multiple workloads on one host racing to register via the same socket — serialized correctly by the shared Registrar's existing locking (§13.2), no new lock needed.

22.9 Failure Analysis

  • Symptom: sidecar registrations silently stop working after an agent restart. Root cause: the socket file was not recreated (stale inode reference from clients). Detection: sidecar_socket_reconnects_total. Recovery: agent restart procedure recreates the socket atomically (rename-into-place); documented in the operator guide (§26).

22.10 Operational Notes

  • Metrics: sidecar_registrations_total, sidecar_socket_reconnects_total (ADR-10).
  • examples/sidecar-bridge/ in the repo tree (§10) is the canonical end-to-end demo referenced from docs/operator-guide.md.

26. Operational Readiness

  • Metrics: every counter/gauge/histogram introduced in §12–§23 (ADR-10) is Prometheus-scraped at /metrics; naming convention <subsystem>_<noun>_<unit>.
  • Tracing: OpenTelemetry spans per HTTP route, per DNS query, per Raft apply, per gossip probe cycle (ADR-10); trace IDs thread through RequestID (§14.2).
  • Structured logging: JSON via log/slog (ADR-11); every line carries role, datacenter, version (§12.10); token values are redacted per T8's mitigation.
  • Dashboards: one per subsystem (catalog, DNS, checks, gossip, ACL, federation), each keyed to the metrics introduced in that subsystem's phase.
  • Alerting philosophy: alert on invariant violations (I1–I13's detection columns) and SLO burn (§4/§30 M-targets), not on raw resource usage alone — a healthy-looking CPU graph with a broken invariant is still an incident.
  • SLOs: derived directly from §4's constraints table and §30's M-table; error budget policy: two consecutive M-target breaches in CI block release (§23.4).
  • Incident response: severity classes map to the Threat Model (§24) and Failure Modes (§25) tables; every FM-class has a named runbook or a documented "no manual recovery needed" entry.
  • Named runbooks: docs/runbooks/runbook-node-failure.md (§18.10), runbook-leader-loss.md (FM1), runbook-acl-lockout.md (FM5, §19.10).
  • Backup/restore: catalog and KV share one Raft snapshot mechanism (§8.6, §17.10); restore replays the snapshot then the log tail; RPO 0 for committed entries (§4). Snapshot-to-S3 is deferred (§37).
  • Deployment topology: one Raft quorum (3 or 5 servers) per datacenter; clients scale independently; WAN gossip connects quorums across datacenters (§21).
  • Canary / rolling upgrade: roll servers one at a time, never more than a minority at once (preserves quorum, ADR-07); clients roll freely since they hold no replicated state.
  • Rollback: a server rollback to the immediately prior minor version is supported if the compatibility table (§27) shows no breaking change between the two versions; otherwise rollback requires a snapshot restore to the pre-upgrade snapshot.
  • Migration: schema-evolution additions (§27) roll forward without a maintenance window; breaking changes require the documented major-version migration procedure in docs/operator-guide.md.
  • Operator web UI: deferred (§37) — CLI (discoveryctl) plus the metrics/tracing surface above is the Phase-0 operational interface.

27. Compatibility & Versioning

  • Wire compatibility: HTTP JSON payloads are field-additive only (§11 annotation tables); removing or renaming a field is a breaking change requiring a major-version bump (SemVer, extending ADR-19's reproducibility discipline to the wire contract).
  • DNS wire compatibility: RFC 1035/2782/6891 compliance is a permanent contract; the discovery. default domain is configurable but the grammar (§8.3) itself is not versioned independently of the RFCs it implements.
  • Storage compatibility: the Raft log entry format (§8.6) carries a kind byte reserved for forward extension; new kinds are additive; removing a kind requires a major version and a documented migration.
  • Schema evolution: CheckDefinition, Node, Service, Instance (§11.1–11.2) accept new optional fields with safe zero-value defaults across minor versions; required-field additions are a major-version event.
  • API stability: /v1/* routes are stable within a major version; a /v2/* prefix is reserved for any breaking HTTP redesign, never an in-place /v1/* change.
  • Deprecation policy: a deprecated field/route is marked in docs/api-reference.md and emits a Deprecation response header for at least one minor-version cycle before removal.
  • SemVer policy: MAJOR.MINOR.PATCH; MAJOR = breaking wire/storage/API change; MINOR = additive fields/routes/checks; PATCH = bug fixes with no contract change.
  • Rolling-upgrade guarantees: a mixed-version cluster (N and N+1 minor) must interoperate for the duration of a rolling upgrade — the Raft log format and gossip envelope (§8.6, §8.7) are versioned fields precisely to make this checkable in CI (a mixed-version conformance run, tracked alongside §28's suite).
  • Client SDK compatibility: api/client/* (§10) follows the same MAJOR.MINOR.PATCH contract as the server; a SDK MINOR bump never requires a server MAJOR bump.

28. Testing & Verification Strategy

  • Unit: go test table-driven (ADR-13) per package; 100% branch coverage target on catalog/apply.go, checks/status.go (§16.4), acl/rules.go.
  • Integration: testcontainers-go spins a real multi-agent cluster for gossip (§18.5), federation (§21.5), and ACL (§19.5) fixtures.
  • Property-based: the catalog's index monotonicity (I1) and idempotent-apply (I6) properties are checked via randomized apply sequences, not just fixed fixtures.
  • Differential: DNS answers are differentially compared against a reference miekg/dns-based oracle for a corpus of question shapes (§15.5).
  • Fuzzing: Go native fuzzing (ADR-14) on the DNS and HTTP parsers (fuzz/, §23.2), gated in CI at 24 hours, soaked at 30 days on a scheduled job (M12).
  • Chaos / fault injection: kill-one-node (§18.4), WAN-partition (§21.4), and leader-loss-mid-blocking-query (§8.10) scenarios are first-class conformance fixtures, not manual game days only.
  • Deterministic replay: the conformance/runner (§7's debugging methodology) drives the catalog's apply path from a recorded event log and asserts I1/I2/I6/I11 on every apply — the primary tool for root-causing FM3/FM4 (§25).
  • Soak: the 30-day fuzz soak (M12) and a 7-day sustained-load run at the §4 target scale (10K services / 100K instances) are both scheduled, not CI-blocking, jobs.
  • Conformance: every phase's N.5 fixtures (§12.5–§23.5) are the authoritative acceptance surface; make conformance runs the full suite and fails the build on any fail count greater than zero.
  • Performance-regression gating: §30's M-table is enforced in CI with a 10% tolerance band (§23.4); every target is traceable back to a §4 constraint and a §34 derivation.
  • Tie-back to invariants: every row of §7's invariant table names its enforcement point and detection signal; the conformance fixtures in §12.5–§23.5 are the executable form of that table.

29. Build & Release Engineering

  • Reproducible builds: pinned go.sum, -trimpath, deterministic build flags (ADR-19); a rebuild from the same commit produces a byte-identical binary.
  • Artifact signing: release binaries are signed (cosign-compatible) as part of the goreleaser pipeline (ADR-18); signatures are verified in the release CI job.
  • SBOM: a software bill of materials is generated per release (go.sum-derived) and published alongside the binary.
  • Release channels: latest (tag-driven stable), edge (main-branch nightly, not for production).
  • CI/CD topology: ci.yml (build/vet/lint/test/race) → conformance.yml (full fixture suite) → security.yml (govulncheck/gosec/dependency review) → release.yml (tag-driven goreleaser), each gating the next (§10, §12.2).
  • Version stamping: internal/version/version.go embeds the git commit, build timestamp, and Go toolchain version at link time; exposed via /v1/agent/self.
  • Provenance/attestation: the release pipeline emits SLSA-style provenance metadata alongside the signed binary and SBOM.
  • Dependency auditing: govulncheck runs on every PR and nightly; a new transitive dependency requires an ADR entry (the "dependency budget" discipline folded into ADR-01's rationale).
  • Build matrix: linux/amd64, linux/arm64, darwin/arm64; Windows is unsupported for the server role (Unix-socket sidecar dependency, §22.6) and client-only supported, documented in the platform matrix.
  • Container publishing: the distroless image (ADR-16) is published to a container registry alongside the raw binary, both signed identically.

30. Performance Engineering

Benchmarking/profiling methodology: every M-target below is measured on a pinned-CPU host — thermal throttling and noisy-neighbor CI runners invalidate a run (§23.6); pprof CPU and heap profiles are captured on every scheduled soak run; telemetry export is disabled during a benchmark run so its own hot-path cost does not skew the number (§23.6).

  • Allocation analysis: the catalog's blocking-query path (§8.5) is the primary allocation-sensitivity target — a parked waiter's context + channel must stay small enough that 10,000 waiters fit the §4 memory ceiling (§20.7).
  • Lock-contention analysis: the single sync.RWMutex (§13.2) is profiled under the M2/M4 write-throughput benchmarks; per-row locking is an explicit non-goal until contention is measured, not assumed (§13.7).
  • Cache analysis: the ACL token cache (§19.7) and the DNS dns.Msg buffer pool (§15.7) are the two structures profiled for cache-hit-rate impact on tail latency.
  • Syscall analysis: DNS UDP recv/send and HTTP accept-loop syscalls are profiled under M6/M10 load to confirm the worker-pool sizing (ADR-21) matches observed syscall cost.
  • Tail-latency analysis: every latency M-target below is a p99, not an average — p50/p99 divergence beyond 10× at target scale is itself a regression signal, even when the p99 nominally still passes.

31. Scalability Analysis

  • Constant regardless of scale: per-request handler CPU cost (O(1) per HTTP/DNS request, excluding catalog size); ACL cache lookup (O(prefix length), §19.7).
  • Grows with scale, and its Big-O: catalog memory — O(instances) (§34.1); gossip bandwidth per node — O(log n) via SWIM's fanout design, not O(n) (§18.7); Raft log growth between snapshots — O(write rate × time) (§34.7); watch-waiter memory — O(concurrent waiters), bounded by the 10K fan-out ceiling (§4).
  • Bottlenecks, in order of first-to-bind: (1) the single Raft leader's write serialization (M2/M4 ceiling, shared across catalog+KV per ADR-08, FM6); (2) the check engine's 50-probe concurrency ceiling (§34.12); (3) DNS single-threaded parse cost before horizontal fan-out (§15.7); (4) cross-DC RTT floor for federation (§34.11, not addressable by code).
  • Horizontal scaling: client-role agents scale linearly with workload count (no shared state); server-role agents scale by Raft quorum size (3→5→7), trading write latency for fault tolerance (ADR-07); gossip scales sub-linearly in bandwidth (§18.7), but the convergence time target (§4) still requires re-derivation past roughly 1,000 nodes.
  • Vertical scaling: CPU sizing scales from 2 vCPU (baseline) to 8 vCPU at the 100K-instance Phase-0 target (§4); beyond that, sharding (below) replaces vertical scaling as the primary lever.
  • Sharding/partitioning: not built in Phase-0; the natural shard boundary is the datacenter (each DC is an independent Raft quorum + gossip pool, §21) — a significantly-past-target-scale deployment shards by adding datacenters rather than by splitting one DC's catalog, since the catalog itself has no intra-DC partitioning primitive.
  • Coordination overhead: grows with quorum size (Raft, O(quorum) RPC fanout per write) and with WAN pool size (gossip, O(log n) per federation-facing server, §21.2); ACL cache invalidation is O(1) per revocation (event-driven, not O(agents) polling).
  • Practical ceiling and levers beyond it: the Phase-0 target (10K services / 100K instances, single DC) is the practical ceiling for one Raft quorum at the M2/M4 throughput targets; the lever beyond it is federation (§21) — split the fleet across datacenters rather than growing one quorum's write load, since Raft write throughput does not scale with quorum size (more servers add fault tolerance, not throughput, ADR-07).

32. Mental Models & First Principles

  • MM1 — A service instance is a claim, not a fact. Insight: the catalog holds what an agent last reported, not ground truth. Predicts: DNS/HTTP answers can be stale by up to one notification cycle even when "correct." Bug class without it: clients assume a passing instance is reachable right now and skip retry logic. Resolving §: §8.5, §15.6 (I3).
  • MM2 — The index is a logical clock, not a timestamp. Insight: catalog.Index orders events; it does not measure elapsed time (Lamport 1978). Predicts: two agents can disagree on wall-clock time yet agree perfectly on event order. Bug class without it: engineers derive a staleness duration from an index delta, which is meaningless without a separate timestamp. Resolving §: §7 (I1, I11), §13.2.
  • MM3 — Suspicion is a probability, not a verdict. Insight: SWIM's suspect state exists because no failure detector is both accurate and fast in an asynchronous network (Chandra & Toueg 1996). Predicts: some false positives are mathematically unavoidable at any fixed timeout. Bug class without it: engineers chase a "fix" for every false positive instead of tuning the probability/latency tradeoff. Resolving §: §18.9 (P11).
  • MM4 — Consistency is a per-subsystem choice, not a system-wide constant. Insight: this system is CP for the catalog and AP for membership simultaneously (P2). Predicts: "is this system CP or AP" has no single correct answer without naming the subsystem. Bug class without it: engineers apply catalog reasoning to membership data, or vice versa, and are surprised by the mismatch. Resolving §: §6 (P2), §33.
  • MM5 — A blocking query is a subscription with a receipt, not a socket. Insight: the index is the receipt — resuming a watch after a restart means replaying the last known index, no session state required server-side. Predicts: watch clients can be stateless across reconnects. Bug class without it: engineers build session-affinity infrastructure for watches that do not need it. Resolving §: §8.5, §20.2.
  • MM6 — Federation is a WAN-shaped RPC, not a bigger cluster. Insight: cross-DC reads forward, they do not merge, because merging would require one linearizable order across physically separated failure domains. Predicts: federation latency is bounded below by speed-of-light RTT, not by any software optimization (§34.11). Bug class without it: engineers "optimize" federation latency with caching that silently reintroduces the staleness federation was designed to avoid. Resolving §: §21.2 (I12), §36.
  • MM7 — Backpressure is a correctness property, not a performance one. Insight: an unbounded queue does not fail slowly, it fails catastrophically (OOM) at exactly the worst moment (P13). Predicts: a system with no explicit bounds anywhere has an implicit bound equal to available memory, discovered in production. Bug class without it: engineers treat ADR-21-style bounding as an optimization to defer, not a correctness requirement to ship on day one. Resolving §: §9 (ADR-21), §20.7.
  • MM8 — A deferred feature is a decision, not an omission. Insight: every PhaseDeferred entry (§37) carries an explicit un-defer trigger — the absence of script checks, for instance, is a security decision (T10), not an oversight. Predicts: a future session reading this blueprint can distinguish "not built yet, intentionally" from "forgot to build." Bug class without it: a maintainer builds a deferred feature ad hoc, without revisiting the design review the deferral was waiting on. Resolving §: §37.

Consul (HashiCorp, 2014) is the closest real analog — the decision this blueprint departs from is bundling the KV and catalog under one Raft log rather than treating KV as a fully separate subsystem with its own ACL surface; the niche where Consul's own separation would win is a deployment where KV write volume from unrelated app config genuinely swamps catalog latency (§37 tracks this as an escape hatch, not a default).

etcd chose linearizable reads through Raft for every operation, including membership, rather than layering an eventually-consistent gossip membership plane on top; that wins in Kubernetes-scale control planes where one linearizable source of truth for both config and membership is worth the leader-serialization cost this design explicitly avoids for gossip (§18).

ZooKeeper chose ephemeral znodes plus a client-held session as the registry primitive instead of a purpose-built catalog schema; that wins when the coordination need is generic (locks, leader election, configuration) rather than specifically service-registry-shaped, at the cost of building your own registry semantics on top of a lower-level primitive (§36 Alternative D).

Eureka chose AP over CP for the catalog itself, accepting stale reads during a partition in exchange for local-agent-only availability (self-preservation mode); that wins in a deployment that would rather serve a slightly stale service list than reject any read during a partition — the opposite of this design's P2 choice to keep the catalog linearizable (§36 Alternative C).

CoreDNS chose a pluggable middleware chain over a fixed DNS server, decoupling the DNS layer from any single backend; that wins when the same DNS server must front multiple discovery backends (etcd, Kubernetes, files) rather than one purpose-built catalog, at the cost of the tight DNS-to-catalog integration (§15) this design relies on for I3's health-filtering guarantee.

34. Back-of-Envelope Capacity Model

34.1 Catalog Memory Footprint at Target Scale

100,000 instances × 1 KiB/instance (§4) = 100,000 KiB ≈ 97.7 MiB.

34.2 Total Agent Memory Ceiling Check

97.7 MiB (§34.1) + 128 MiB baseline (§4) ≈ 226 MiB, comfortably under a 512 MiB container limit — roughly 2× headroom for GC.

34.3 Catalog Write Bandwidth

5,000 registrations/sec (§4, M2) × ~300 bytes/JSON registration ≈ 1.5 MB/sec sustained ingest on the Raft leader's apply path.

34.4 Gossip Bandwidth per Node (LAN)

fanout 3 × ~200 bytes/message ÷ 1 s probe interval × ~3 indirect probes (§4, ADR-06) ≈ 1.8 KB/sec/node steady state, staying near-constant per node as cluster size grows because SWIM's fanout is O(log n), not O(n) (§18.7).

34.5 FD Usage at Target Blocking-Query Fan-Out

10,000 HTTP connections (§4, M10) + ~1,000 gossip peer FDs (one per active peer probe at a 1,000-node cluster) = ~11,000 FDs, above the 4,096 Phase-0 default — large deployments must raise the agent's ulimit accordingly.

34.6 DNS UDP Throughput Ceiling

A <5 ms p99 (§4, M6) implies roughly 200 qps per serial goroutine; with an 8-goroutine pool (matching the 8 vCPU ceiling, §4), practical ceiling ≈ 1,600 qps before horizontal scale-out is required.

34.7 Raft Log Growth Rate

5,000 registrations/sec × ~300 bytes/entry (§4, same inputs as §34.3) = 1.5 MB/sec log growth between snapshots — the log grows at exactly the catalog's write-ingest rate since every write is one log entry.

34.8 Snapshot-Interval Bound

To keep storage amplification ≤ 3× (§4) — i.e. the log must not exceed 2× live-data size, live data ≈ 97.7 MiB (§34.1) — the log must snapshot before exceeding ≈ 195.4 MiB; at 1.5 MB/sec (§34.7) that is a ~130 s worst-case window, so a 30–60 s snapshot interval is chosen with comfortable margin.

34.9 ACL Token Cache Footprint

10,000 active distinct tokens (a generous fleet estimate) × ~200 bytes/entry (UUID + policy refs) = 2 MB, negligible against the 512 MiB ceiling (§34.2).

34.10 Convergence Time Budget

Vanilla SWIM's worst-case suspicion timeout is 3× the 1 s LAN probe interval (§4) = 3 s; meeting the 500 ms convergence target (§4, M5/M7) therefore requires Lifeguard's dynamic-timeout shrinking under low false-positive-rate conditions (§18.9) — the target is a requirement for Lifeguard, not achievable with SWIM alone (ADR-06).

34.11 Cross-DC Forwarding Latency Budget

Typical cross-DC RTT is 30–150 ms (§4); a federated read's total latency ≈ local lookup (<1 ms) + one round trip (30–150 ms) + remote lookup (<1 ms) ≈ 32–152 ms, which is why federation is explicitly excluded from the single-DC p99 targets in §4.

34.12 Check-Engine Throughput Ceiling

50 concurrent probes (§4, check_max_concurrent) × ~200 ms average HTTP probe duration ⇒ sustainable check throughput ≈ 250 checks/sec/agent before probes start queueing past their configured interval — this bounds the maximum check-interval density an operator may configure per agent (§16.7).

36. Alternative Architectures (Roads Not Taken)

Alternative A — etcd-centric pull-based discovery. No dedicated catalog schema; clients watch a KV prefix directly and interpret keys as endpoints themselves.

Client --watch--> etcd cluster (KV, Raft)
Client's own code interprets keys as service endpoints
No dedicated Node/Service/Instance schema; no DNS; no health engine

Regime where it wins: a shop already running etcd as its Kubernetes backing store that wants one fewer moving part — every service publishes its own health as a lease-backed key, and clients watch a prefix directly. Real system: etcd, used directly as a discovery backend (the pattern several etcd-adjacent tools use, distinct from a purpose-built Consul-style catalog). Rejection reason: pushes the catalog schema, health semantics, and DNS resolution entirely into application code — every client reimplements P4's health-state enum and P5's DNS-equivalent lookup, the exact duplicated-effort problem this blueprint's bundled agent avoids (§2).

Alternative B — Kubernetes-native control-loop discovery. Discovery as a side effect of the scheduler's own reconciliation loop (Endpoints/EndpointSlice + CoreDNS) rather than a dedicated gossip+Raft agent.

kube-apiserver (etcd-backed) --watch--> Endpoint controller
                                        --writes--> EndpointSlice
CoreDNS --watches EndpointSlice--> answers cluster DNS
kubelet --readiness probe--> reports Pod status to apiserver

Regime where it wins: a fleet that already runs a Kubernetes control plane and wants discovery as a side effect of existing reconciliation, not a second system. Real system: Kubernetes (kube-apiserver + kubelet + CoreDNS). Rejection reason: requires a full control plane (apiserver, scheduler, controller-manager) as a prerequisite — this blueprint's target users (§1) include bare-metal/VM fleets with no Kubernetes control plane at all; adopting this alternative would mean building Kubernetes, not a service-discovery system.

Alternative C — pure-gossip AP catalog, no Raft. Every agent holds its own eventually-consistent registry copy; no leader, no quorum; self-preservation mode on suspected partition.

Agent A <--gossip--> Agent B <--gossip--> Agent C
Each agent holds its own eventually-consistent registry copy
No leader, no quorum; self-preservation mode on suspected partition

Regime where it wins: a deployment that would rather serve a stale-but-available service list during a partition than reject any read (AP over CP) — typically a client-heavy, write-light fleet where read availability during a network event matters more than register/deregister precision. Real system: Netflix Eureka. Rejection reason: violates P2 — this blueprint's users need linearizable catalog writes (register/deregister must not silently diverge across replicas, §7 I1/I6), which a pure-gossip catalog cannot provide without layering a consensus mechanism back on top, at which point it is no longer "pure gossip."

Alternative D — ZooKeeper-style ephemeral-znode coordination primitive. Service registration as one more use of a generic coordination primitive rather than a purpose-built registry.

ZK ensemble (ZAB-replicated tree)
Service instance --creates--> ephemeral znode /services/web/instance-1
Client --one-shot watch--> /services/web  (re-registers watch after each fire)

Regime where it wins: a system whose primary need is generic coordination (locks, leader election, config) that treats service registration as one more use of that primitive. Real system: Apache ZooKeeper, with the Curator ServiceDiscovery recipe as the registry-shaped layer on top. Rejection reason: znodes are a generic primitive — SRV-style weighted records, health-state semantics (P4), and DNS resolution (P5) all have to be built as a layer on top rather than being first-class, and one-shot (not persistent) watches (§5 Reference Implementations' ZooKeeper pitfall) push reconnection-state management onto every client, which this blueprint's index-based blocking query (§8.5, §32 MM5) avoids by design.

38. Glossary

  • Agent — the discoveryd binary running on one node, in server or client role (§1).
  • Catalog — the cluster-wide, Raft-replicated map of nodes, services, instances, checks (§7, §13).
  • Instance — a single addressable copy of a service on a single node (§11.1).
  • Check — a probe producing a passing/warning/critical status (§11.2, §8.2).
  • Index — the monotonic uint64 ordering catalog mutations (I1, §13.2).
  • Datacenter (DC) — a failure-domain unit; one Raft quorum per DC (§4, §21).
  • Federation — cross-DC forwarding of catalog reads (§21).
  • Blocking query — a long-poll HTTP request parked on a monotonic index (§8.5).
  • Coalescing — fanning one notification out to all waiters on the same table (I7, §20.2).
  • Gossip — SWIM+Lifeguard-based membership dissemination (§18, ADR-06).
  • LAN pool — the gossip pool within one datacenter (§18.2).
  • WAN pool — the gossip pool spanning datacenters (§21.2).
  • Suspicion — SWIM's intermediate state between alive and dead (P11, §18.2).
  • Raft — the consensus algorithm replicating the catalog/KV log (ADR-07, §8.6).
  • Leader — the single Raft node serializing writes for a quorum (§4, ADR-07).
  • RTO — recovery time objective; bounded by ~3× the heartbeat interval here (§4).
  • RPO — recovery point objective; 0 for committed Raft entries (§4).
  • Snapshot — a point-in-time encode of the full catalog for Raft compaction (§13.2, §8.6).
  • ACL — access control list; token/policy/namespace evaluation on every path (§19, I4).
  • Token — a bearer credential with an AccessorID and policy list (§11.4).
  • Policy — a named rules document merged by union with deny-overrides (§19.2).
  • Namespace — a label scoping tokens/instances; isolation itself is deferred (§19, §37).
  • Sidecar bridge — the Unix-socket local-registration path (§22, ADR-16).
  • Connect — the mTLS service-mesh stretch layer; scaffolding only in Phase-0 (§22, §37).
  • SVID — a SPIFFE-style verifiable identity issued by Connect (deferred, §22).
  • Intention — an allow/deny rule between two services in Connect (deferred, §22).
  • KV — the embedded flat key-value namespace sharing the catalog's Raft log (§17, ADR-08).
  • CAS — compare-and-swap; a conditional KV write keyed on ModifyIndex (§17.2).
  • EDNS0 — the DNS extension mechanism for larger UDP buffer sizes (RFC 6891, §15.3).
  • SRV record — a DNS record carrying priority/weight/port/target (RFC 2782, §8.4).
  • TTL check — a check driven by a client-refreshed deadline, not an active probe (§16.2).
  • Hysteresis — the success/failure counter thresholds preventing check flapping (§8.2, I9).
  • Auto-deregistration — removing an instance after continuous critical duration (I13).
  • Watch waiter — a parked blocking-query goroutine registered on a notification channel (§13.2, §20).
  • Notification channel — the per-table channel a waiter blocks on (I7, §13.2).
  • Dedup key — the RequestID UUID making an apply idempotent (I6, P12).
  • Apply path — the code path turning a RaftLogEntry into a catalog mutation (§8.6, §13.2).
  • FSM — the finite-state machine the Raft crate drives via the apply path (ADR-07, §11.5).
  • Wire compatibility — the contract keeping HTTP/DNS payloads additive-only across versions (§27).
  • M-table — the quantified performance-targets table (M1–M12, §30).
  • Conformance fixture — a named YAML test case with an expected result (§7, phase N.5 sections).
  • PhaseDeferred — the marker anchoring an out-of-scope feature to a real heading and the Register (§37).
  • Backpressure — bounding queues/pools so overload sheds instead of OOMing (P13, ADR-21).
  • Self-preservation mode — Eureka's AP-favoring behavior under suspected partition (§33, §36 Alternative C).
  • Ephemeral znode — ZooKeeper's session-bound coordination primitive (§33, §36 Alternative D).
