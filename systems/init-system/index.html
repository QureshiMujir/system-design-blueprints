Box notes. is-parser is pure data-in/data-out: no process is ever touched here (P1). is-graph is the single source of truth for ordering and requirement edges; it is rebuilt, never mutated in place, on every daemon-reload (I11). is-txn is the trust boundary between "what the admin/CLI asked for" and "what the kernel will be told to do" — every activation and every shutdown passes through it (I6, I13). is-activate is the concurrency boundary: it fans out into parallel batches bounded only by DAG readiness (P9). is-supervisor and is-cgroup are the persistence boundary for process/resource state (survives until the process exits). is-reap is PID 1's only consumer of SIGCHLD; every other subsystem learns of a child's exit through it, never independently. is-journal is the observability boundary — the only durable record once a process's stdout/stderr closes. The control bus (is-bus, driving is-cli) is the external interface: a Unix-domain socket trust boundary gated by filesystem permissions (ADR-07).

8. Domain Model

8.1 Unit / service model

A unit is (name, kind) — the pair, not the name alone, is the identity key (foo.service and foo.socket are distinct units). Nine kinds ship in Phase-0 scope: Service, Socket, Timer, Path, Target, Slice, Scope, Device, Mount.

[Unit]
Description=Example web service
Requires=network.target
After=network.target local-fs.target
OnFailure=alert.service

[Service]
ExecStart=/usr/bin/webd --port=8080
Restart=on-failure
RestartSec=200ms
StartLimitBurst=5
StartLimitIntervalSec=10s
MemoryMax=256M
CPUWeight=100

[Install]
WantedBy=multi-user.target

Directives resolve into a typed UnitConfig (§11). Unknown keys are warned, not fatal — forward compatibility with future directives (P1). Drop-in files (foo.service.d/*.conf) layer over the base file; later drop-ins override earlier directive values, set-valued directives (After=, Wants=) accumulate.

8.2 Dependency ordering DAG

Two edge classes, deliberately not conflated:

  • Requirement edges (Requires, Wants, BindsTo, Conflicts) — determine whether a unit activates and what happens if a peer fails.
  • Ordering edges (After, Before) — determine when, relative to peers.
Relation Class Semantics
Requires=B requirement A fails if B fails or is stopped
Wants=B requirement (weak) A starts regardless of B's outcome
BindsTo=B requirement (strong) A is stopped if B stops, even post-facto
Conflicts=B requirement (negative) A and B are never both Active
After=B ordering A activates only once B has reached a terminal state
Before=B ordering (inverse of After) —

A unit graph is validated in two independent passes: cycle detection on the ordering subgraph alone (Tarjan SCC, I1), and a requirement-consistency pass (Conflicts= co-occurring with Requires= on the same target is a load error). After= naming a non-existent unit is a warning (I1's cycle check does not apply to edges into nonexistent nodes); Requires= naming a non-existent unit is an error at transaction-build time (I4).

8.3 Service supervision state machine

            ┌──────────┐   activate()    ┌────────────┐   fork+exec ok   ┌────────┐
            │ Inactive │ ───────────────▶ │ Activating │ ────────────────▶ │ Active │
            └────┬─────┘                 └─────┬──────┘                  └───┬────┘
                 │▲                             │ timeout / exec fail        │
                 ││                             ▼                            │ SIGTERM/stop()
                 ││                        ┌────────┐    Restart= policy      ▼
                 │└────────────────────────┤ Failed │◀───────────────┌─────────────┐
                 │      reset-failed       └───┬────┘   exit code    │ Deactivating │
                 │                             │ StartLimitBurst     └──────┬───────┘
                 │                             ▼ exceeded                  │ exit ok
                 │                        ┌────────────┐                   │
                 └────────────────────────┤ Maintenance│◀──────────────────┘
                          admin action    └────────────┘
State Meaning Entered from Exits to
Inactive no process, not requested boot, Deactivating Activating
Activating fork/exec issued, awaiting readiness Inactive Active, Failed
Active running (or RemainAfterExit=yes exited cleanly) Activating Deactivating, Failed
Deactivating SIGTERM sent, awaiting exit Active Inactive, Failed
Failed exited abnormally or dependency failed (I4) Activating, Active, Deactivating Activating (restart), Maintenance
Maintenance StartLimitBurst exceeded; requires operator reset Failed Inactive (via is-ctl reset-failed)

Every (state, event) pair not shown above is an explicit no-op or error arm (P7) — e.g. a SIGCHLD for a PID no longer tracked (already reaped as an orphan) is logged and dropped, never panics (I10).

8.4 Worked example — activation of a 3-unit chain

Units: local-fs.target (no deps) ← After= ← db.service (Requires=local-fs.target) ← After= ← web.service (Requires=db.service). Transaction for target web.service: transitive closure = {local-fs.target, db.service, web.service}. Topological sort of the ordering subgraph yields batch 1 = {local-fs.target}, batch 2 = {db.service} (its only After= dep, local-fs.target, is now terminal), batch 3 = {web.service}. Each batch activates in parallel internally (trivial here, one unit each); is-verifier asserts I6 (order is a valid topological sort) after replay.

8.5 Malformed-input example

[Unit]
After=db.service
[Service]
ExecStart=/usr/bin/web
Restart=alwyas

Two defects: (1) Restart=alwyas is a typo — is-parser rejects the value (not the key) against the closed enum RestartPolicy, producing ParseError::InvalidEnumValue { key: "Restart", value: "alwyas", unit: "web.service" }, and the unit load fails closed (does not silently default to no). (2) After= with no matching Requires=/Wants= is legal but produces only an ordering constraint with no activation trigger — web.service will never auto-activate unless something else Wants=s it; is-verifier's lint pass flags this as OrderingWithoutActivation (a warning, not a load error).

8.6 Failure-path example

db.service is Requires=d by web.service and fails during Activating (ExecStart binary missing, ENOENT). Per I4, web.service cannot become Active while db.service is not Active: is-txn marks web.service Failed without ever issuing its fork+exec (no Activating state is entered for a unit whose hard requirement is already known-failed at batch-schedule time, §16 Phase 4 N.2). db.service's OnFailure=alert.service (if declared) is activated as a new, independent transaction. The operator sees both units in Failed via is-ctl status, with db.service's journal entry carrying the ENOENT detail and web.service's carrying FailedDependency{unit:"db.service"}.
