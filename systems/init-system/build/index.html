⬜ Phase 0 — Repo Skeleton & Correctness Kernel §12

Objectives

Stand up the Cargo workspace (§10), CI matrix (ADR-13), and the correctness kernel: is-core's types (§11), a minimal is-verifier capable of running one trivial invariant assertion, and a QEMU boot smoke test that boots a stub init to a single target with no real units. No dependency graph, no supervision yet — this phase proves the toolchain, not the domain logic.

Deliverable

cargo build --workspace succeeds; CI green on both ci.yml and qemu-boot.yml; the QEMU image boots the stub init to the hardcoded log line and shuts down cleanly under a test harness invocation.

Acceptance

Cold cargo build --all-targets completes in < 100 s on the reference CI runner (4 vCPU); QEMU boot-to-log-line completes in < 5 s wall clock; zero compiler warnings with #![deny(warnings)] on is-core.

Fixtures

conformance/buckets/parser/ seeded with stub.target (a zero-directive Target unit) — purpose: prove the workspace round-trips a trivial unit through is-core types; expected output: Unit { kind: Target, state: Inactive, .. }.

Pitfalls
  • Running the QEMU test init as the host's actual PID 1 (never — always inside a disposable VM/container, per the isolation note carried from the original draft).
  • Forgetting #![no_std]-adjacent discipline creep: PID 1 links libc but must not assume a fully-populated /proc//sys at the instant it starts (ADR-14).

⬜ Phase 1 — Unit-File Parser & Config Model §13

Objectives

Implement is-parser: the key=value INI-like grammar (ADR-02), section gating ([Unit], [Service], [Install]), drop-in layering, and the closed-enum validation demonstrated in §8.5. Output is UnitConfig (§11) — data only, per P1.

Deliverable

is-parser::parse_unit(path) -> Result<UnitConfig, InitError> plus the drop-in resolver, both covered by the parser conformance bucket.

Acceptance

Parses 500 synthetic unit files in < 50 ms single-core (§4's 10,000 files/sec reference class); 100% of the parser conformance bucket's 40 fixtures pass; zero panics across a 10-minute cargo fuzz run parse_unit corpus run (ADR-12).

Fixtures

fixtures/parser/multiline-continuation.service — purpose: verify backslash continuation; expected: single merged ExecStart= value. fixtures/parser/ bad-enum.service — purpose: §8.5's malformed-Restart-value case; expected: ParseError::InvalidEnumValue. fixtures/parser/dropin-override.service{,.d/ 10-override.conf} — purpose: verify drop-in layering order; expected: the .d/ value wins for scalars, both values present for After=.

Pitfalls
  • Expanding ${FOO} at parse time instead of activation time (I11-adjacent bug: a daemon-reload would re-resolve against the init's environment, not the eventual service's).
  • Treating an unknown key as fatal — breaks forward compatibility (P1); must warn and continue.
  • Non-deterministic drop-in application order from an unsorted directory read (violates P13; always sort the glob results).

⬜ Phase 2 — Dependency Graph & Ordering §14

Objectives

Implement is-graph: build the two-class edge model (§8.2) from a set of parsed units, run cycle detection on the ordering subgraph (I1), and run the requirement-consistency pass (Conflicts=+Requires= co-occurrence, §8.2).

Deliverable

is-graph::build(units) -> Result<Graph, InitError> and is-graph::detect_cycles(&Graph) -> Vec<Vec<UnitName>>, covered by the graph conformance bucket, plus a tools/graph-visualize CLI emitting Graphviz DOT for operator debugging.

Acceptance

Builds a 500-node graph in < 30 ms (§4's reference class); the graph bucket's 25 fixtures (including 5 deliberately cyclic) all classify correctly; is-verifier asserts I1 on every fixture with zero false negatives across a 1-hour fuzz run.

Fixtures

fixtures/graph/simple-cycle.units (A.After=B, B.After=A) — expected: GraphCycle{members:[A,B]}. fixtures/graph/conflicts-requires.units — expected: load rejection citing the co-occurrence rule. fixtures/graph/dangling-after.units — expected: successful build with a recorded warning, not an error.

Pitfalls
  • Running cycle detection over the combined (ordering + requirement) graph instead of the ordering subgraph alone — a Requires=-only relationship between two units with no ordering constraint is not a deadlock and must not be flagged (§8.2's explicit design note).
  • Treating After=-to-missing-unit as an error, which needlessly breaks unit files written for a superset deployment (some optional units absent).

⬜ Phase 3 — Transaction Engine §15

Objectives

Implement is-txn: given a validated Graph (§14) and a requested target unit, compute the transitive closure of units to activate, snapshot their current states, and produce an ordered batch plan (I6) — the trust boundary between "what was requested" and "what will be told to the kernel" (P3).

Deliverable

is-txn::plan(&Graph, &UnitName) -> Result<Transaction, InitError> and is-txn::commit(Transaction) -> ActivationReport, covered by the txn conformance bucket.

Acceptance

Plans a 500-unit transitive closure + batch sort in < 50 ms (§4); the txn bucket's 20 fixtures pass, including 3 asserting idempotent re-start produces zero new fork calls (P11); is-verifier replay confirms I6 on every recorded transaction in the fixture corpus with zero reorder violations.

Fixtures

fixtures/txn/three-unit-chain.units — the §8.4 worked example; expected batch plan [[local-fs.target],[db.service],[web.service]]. fixtures/txn/ already-active-skip.units — expected: re-planning a fully-Active target produces an empty batch list.

Pitfalls
  • Computing batches by walking the live unit-state table during the sort instead of the snapshot — reintroduces exactly the race I6 exists to prevent (a unit transitioning Failed mid-sort must not silently reorder the plan already handed to the caller).
  • Forgetting Conflicts= at plan time: activating a target while a conflicting unit is Active must stop the conflicting unit as part of the same transaction, not a follow-up one (else a window exists where both are transiently Active).

⬜ Phase 4 — Parallel Activation Engine §16

Objectives

Implement is-activate: execute one transaction batch (round) in parallel, respecting the concurrency ceiling (§4), and report per-unit readiness back to is-txn so the next round can be released (P9's "maximal safe parallelism" made concrete).

Deliverable

is-activate::activate(Round) -> ActivationReport returning per-unit terminal state and timing, covered by the activate conformance bucket.

Acceptance

Full 500-unit transitive activation completes in ≤ 5 s p50 (§4's boot budget, excluding the ≤ 1.2 s parse+graph+plan overhead already budgeted upstream); a unit stuck in Activating past TimeoutStartSec transitions to Failed within 100 ms of the deadline; the activate bucket's 18 fixtures pass including 4 timeout-triggering cases.

Fixtures

fixtures/activate/parallel-independent.units — 20 units with no edges between them; expected: single round, all Active. fixtures/activate/slow-start- timeout.units — an ExecStart= pointing at sleep 999; expected: Failed with ActivationTimeout after TimeoutStartSec.

Pitfalls
  • Releasing the next round before every unit in the current round has reached a terminal state — reintroduces the exact race I6/P4 exist to prevent (a "mostly done" round is not a done round).
  • A blocking cgroup-creation syscall issued directly on the reactor thread stalls every other unit's spawn in the same round (ADR-05's rationale made concrete; route through the blocking thread pool).

⬜ Phase 5 — Process Supervision & State Machine §17

Objectives

Implement is-supervisor: own the per-unit SupervisorRecord (§11), perform the actual fork/clone3+exec, and enforce Restart= policy with exponential backoff and the StartLimitBurst circuit breaker (I8).

Deliverable

is-supervisor::spawn(&UnitConfig, &CgroupPath) -> Result<Pid, InitError> plus the restart-policy state machine, covered by the supervisor conformance bucket.

Acceptance

Fork+exec completes in < 5 ms p99 (§4); a flapping unit (Restart=always, immediate-exit ExecStart=) reaches Maintenance within StartLimitBurst × RestartSec (default: 5 × 100 ms = 500 ms, matching §34's derived restart-storm ceiling) and never exceeds it; the supervisor bucket's 22 fixtures pass.

Fixtures

fixtures/supervisor/flap-loop.service (Restart=always, ExecStart=/bin/false) — expected: Maintenance within 500 ms, exactly StartLimitBurst restart attempts logged. fixtures/supervisor/remain-after-exit.service — expected: Active after clean exit, no restart attempted.

Pitfalls
  • Writing the SupervisorRecord after clone3 returns instead of before — reopens the I2 race this phase exists to close.
  • Resetting the StartLimitBurst window counter with a separate read-then-reset instead of an atomic compare-and-swap (the historical systemd race cited in ADR discussion, §9 ADR-04's lineage note) — under concurrent restart storms this undercounts and lets a flapping unit escape the circuit breaker.
  • Forgetting setsid(): a SIGINT in the controlling terminal (if any) kills the child alongside the init.

⬜ Phase 6 — PID 1 Signal Handling & Orphan Reaping §18

Objectives

Implement is-reap: the sole SIGCHLD consumer for the whole process, driven by signalfd (P5, MM5), including orphan reaping (processes reparented to PID 1 whose original parent exited) and the bounded-drain backpressure discipline (ADR-20).

Deliverable

The is-reap signalfd loop integrated into the main reactor, covered by the supervisor bucket's reap-specific fixtures (shared bucket with Phase 5, since reaping and restart policy are tested end-to-end together).

Acceptance

Reap latency (exit → supervisor state update) is p99 ≤ 5 ms (§4); a synthetic SIGCHLD-storm test (500 children exiting within 10 ms) produces zero lost exits and zero zombies remaining after the storm settles, verified via /proc/<pid>/task zombie-state scan.

Fixtures

fixtures/supervisor/sigchld-storm.units — 500 short-lived processes spawned simultaneously; expected: all reaped, zero zombies, reap-batch histogram shows at least one 256-capped iteration. fixtures/supervisor/orphan-reap.units — a process that double-forks and lets its immediate parent exit; expected: the grandchild is reparented to the test init and reaped as an orphan (logged, no restart attempted).

Pitfalls
  • Using a traditional sigaction handler instead of signalfd — reintroduces signal coalescing, the exact bug class P5/MM5 exist to eliminate.
  • Reaping without the WNOHANG flag — blocks the reactor thread if no child has actually exited yet (a logic bug distinct from, but easily confused with, the storm-throttling concern).
  • Treating an orphan reap as an error condition — it is expected, routine behavior for PID 1 and must not be logged above debug/info priority.

⬜ Phase 7 — cgroups v2 Resource Control §19

Objectives

Implement is-cgroup: create a per-unit cgroup, write declared resource limits before the unit's first process exists (I12), and enter the cgroup atomically via clone3(CLONE_INTO_CGROUP) (P8, MM4).

Deliverable

is-cgroup::create_and_enter(&CgroupPath, &Limits) -> Result<(), InitError> plus the teardown hook, covered by the cgroup conformance bucket.

Acceptance

Create+enter completes in ≤ 5 ms p99 (§4); a unit exceeding memory.max is OOM-killed within the cgroup scope only (verified: sibling cgroups' processes unaffected) in the cgroup bucket's OOM fixture; zero cgroup_late_limit_total events (I12) across the fixture corpus.

Fixtures

fixtures/cgroup/memory-oom.service (MemoryMax=16M, a memory-bomb ExecStart=) — expected: memory.events's oom_kill count increments, sibling unit's cgroup shows zero OOM events. fixtures/cgroup/no-delegation. service — parent cgroup missing subtree_control entries — expected: load error surfaced before spawn is attempted, not a silent unconstrained run.

Pitfalls
  • Writing limits after fork() and adding the PID to cgroup.procs afterward — the TOCTOU race MM4 names explicitly: the child can allocate before the limit lands.
  • Forgetting parent-cgroup delegation bootstrap — child cgroup creation succeeds but limits silently have no effect (§35's OOM-not-enforced runbook, §26, traces to exactly this).
  • Cgroup path collisions between a slice and a same-named service (namespaced by the .slice/.service suffix convention, never bare names).

⬜ Phase 8 — Socket & Bus Activation §20

Objectives

Implement is-socket (lazy service startup via listening-socket ownership, P10, MM6) and is-bus (the Unix-domain control bus D-Bus-adjacent protocol, ADR-07, carrying is-ctl's start/stop/status/daemon-reload operations).

Deliverable

is-socket::activate_on_connection(&SocketUnit) -> Result<OwnedFd, InitError> and the is-bus request/response loop, covered by the socket-act conformance bucket.

Acceptance

Cold socket-activation latency (connection arrival → service Active) is ≤ 50 ms p50 (§4); a service crash mid-connection does not drop the listening socket (verified: a second connection attempt within 1 s succeeds and re-activates the service); the socket-act bucket's 15 fixtures pass; bus command round-trip latency ≤ 50 ms p50 (§4's control-bus RTT budget plus processing overhead).

Fixtures

fixtures/socket-act/cold-start.socket+service — a ListenStream=-only socket with Accept=no; expected: connection triggers service spawn with LISTEN_FDS=1 correctly set in the child's environment. fixtures/socket-act/ crash-mid-connection.service — service SIGKILLs itself immediately after accept; expected: listening socket survives, next connection re-activates.

Pitfalls
  • Letting the service's own FD-inheritance discipline (normally: close all FDs except stdio, per §17's spawn path) accidentally close the inherited listening FD — requires an explicit O_CLOEXEC-clearing exception for FD 3..N+2 only (a carefully scoped exception to an otherwise strict default-deny FD policy).
  • A bus client issuing malformed frames that desync the framing parser — must fail that one connection, never destabilize the bus listener itself.

⬜ Phase 9 — Targets & Boot Sequencing §21

Objectives

Implement is-target: the runlevel-equivalent synchronization-point unit kind (Target), boot-sequence composition (multi-user.target, graphical.target, etc.), and the default-target selection mechanism.

Deliverable

is-target's target-unit handling integrated into is-graph/is-txn, plus is-ctl isolate, covered by the target conformance bucket.

Acceptance

Default-target boot (20-unit reference multi-user.target closure) completes within the §4 boot-time budget; is-ctl isolate rescue.target correctly deactivates every unit outside the rescue closure within the default DefaultTimeoutStopSec (10 s, §4); the target bucket's 12 fixtures pass.

Fixtures

fixtures/target/multi-user-closure.units — a 20-unit reference boot graph; expected batch plan matches a recorded golden trace. fixtures/target/isolate- rescue.units — expected: every non-rescue unit transitions to Deactivating then Inactive within the timeout budget.

Pitfalls
  • Giving a Target unit an ExecStart= (a modeling error — targets are pure synchronization points, MM1; if a caller needs a process, that belongs in a Service unit Wants=d by the target).
  • Implementing isolate as a special-cased code path instead of a transaction that both activates and deactivates — duplicates the ordering logic already proven correct in §15/§16 and risks divergent bugs between "boot" and "isolate."

⬜ Phase 10 — Journald-Style Logging §22

Objectives

Implement is-journal: per-unit structured log capture from stdout/stderr, stored in a crash-consistent binary indexed format (I9, ADR-06, P12).

Deliverable

is-journal::append(JournalEntry) -> Result<(), InitError> plus the journalctl-equivalent is-ctl logs <unit> query path, covered by the journal conformance bucket.

Acceptance

Sustained write throughput ≥ 100,000 entries/sec, burst ≥ 250,000/sec (§4); journal_fsync_lag_seconds never exceeds 5 s (I9) across a 1-hour soak; corruption-recovery fixture recovers 100% of entries preceding a simulated mid-write crash and correctly discards the torn final record.

Fixtures

fixtures/journal/crash-mid-write.bin — a segment file with a deliberately truncated final record — expected: recovery discards exactly that record, retains all prior entries intact. fixtures/journal/high-priority-sync.service — emits a crit-priority entry — expected: fsync observed synchronously before append returns, not batched.

Pitfalls
  • Batching all priorities identically — a crit entry sitting in an unfsynced buffer defeats the entire point of structured crash-forensics logging (I9's distinction exists specifically to prevent this).
  • An unbounded index growth without periodic compaction — left as an operational rotation policy (§26), not a Phase-10 correctness bug, but must be documented so it isn't mistaken for a leak.

⬜ Phase 11 — Graceful Shutdown & System Transitions §23

Objectives

Implement is-shutdown: reboot/poweroff/kexec transitions driven by the same transaction machinery as activation, run in reverse dependency order (I13, P14).

Deliverable

is-shutdown's reverse-transaction builder plus the escalation timer, covered by the shutdown conformance bucket.

Acceptance

A 20-unit reference shutdown completes within the aggregate TimeoutStopSec budget for the longest-timeout unit on the critical path, not the sum of all units' timeouts (parallel escalation, mirroring §16's parallel activation); the shutdown bucket's 14 fixtures pass, including 2 asserting SIGKILL-escalation timing to within 100 ms of the configured timeout.

Fixtures

fixtures/shutdown/reverse-order.units — the §8.4 three-unit chain in reverse; expected stop order [web.service, db.service, local-fs.target], exactly inverted from the activation order. fixtures/shutdown/hung-stop.service (ExecStop= ignores SIGTERM) — expected: SIGKILL issued exactly at TimeoutStopSec, not before and not more than 100 ms after.

Pitfalls
  • Implementing shutdown as an unconditional "SIGTERM everyone, sleep, SIGKILL survivors" loop with no dependency awareness — violates I13/P14 by letting a dependency (e.g. a database) be torn down before its dependents have finished flushing to it.
  • Failing to bound the total shutdown wall-clock time — a chain of units each individually within their own TimeoutStopSec but serialized unnecessarily can blow past an operator's expected reboot time; batches must escalate in parallel per round, mirroring §16.
