1. Goal & Scope

Build, from scratch in Rust, a PID-1-capable init system in the systemd / launchd / runit / OpenRC tradition: a declarative unit model, a dependency-ordered activation engine, per-process supervision with restart policies, cgroups-v2 resource control, socket- and bus-activation, target-based boot sequencing, journald-style structured logging, and dependency-order-inverted graceful shutdown. The system is the first userspace process the kernel executes (PID 1) and the last to exit; every other userspace process is, transitively, its child or its orphan.

Phase-0 deliverable — numbered modules:

  1. is-core — unit/service domain types, IDs, error taxonomy.
  2. is-parser — unit-file lexer/parser + drop-in layering.
  3. is-graph — dependency DAG construction + cycle detection.
  4. is-verifier — deterministic simulator, one assertion per invariant (§7).
  5. is-cli (stub) — is-ctl status against a fixture graph, no live PID 1 yet.

System boundaries.

  • Provides: unit parsing/validation, dependency-ordered parallel activation, process supervision + restart policy, cgroups-v2 membership and limits, socket/bus activation, timers, path units, targets, structured logging, graceful shutdown, a control bus + CLI.
  • Delegates: kernel scheduling itself (CFS/cgroup weights only, not a scheduler reimplementation), filesystem mounting mechanics beyond mount(2) invocation, network stack, container image management, MAC policy engines (SELinux/AppArmor — hooks only, ADR-16).
  • Does NOT provide: a container runtime (ADR-15), a package manager, a configuration-management layer, a distributed coordination service (this is a single-host PID 1, not a cluster init).

Non-goals: multi-host orchestration, arbitrary shell-script execution as the primary activation mechanism (sysvinit's model — rejected, §36), GUI session management beyond minimal seat hand-off.

Deployment model: compiled as a static (musl) binary, /sbin/init, invoked by the kernel with PID 1; a companion is-cli binary talks to it over a Unix-domain control socket. Target hosts: bare-metal and VM Linux hosts, kernel ≥ 5.8 (cgroups v2 default-mounted), single init instance per host plus optional per-user instances (Phase 9 target scope).

Target users/operators: distribution integrators packaging /sbin/init; on-call engineers debugging boot/service failures; embedded-systems teams needing a small, auditable PID 1.

Later phases unlock: socket activation (Phase 8) unlocks lazy service startup; targets (Phase 9) unlock runlevel-equivalent boot profiles; the journal (Phase 10) unlocks queryable structured logs; graceful shutdown (Phase 11) unlocks safe reboot/kexec/poweroff transitions.

Language: Rust 1.78+ (ADR-01). Rationale: memory safety in the single most privileged process on the host — a use-after-free or data race in PID 1 is a kernel panic, not a crash-and-restart. Rejected: C (no memory-safety guarantee at this privilege level; the historical incumbent, systemd, absorbs a steady CVE stream from exactly this class of bug), C++ (same class of bug, plus larger unsafe-surface from implicit conversions), Go (GC pauses are unacceptable inside SIGCHLD-latency-critical paths, I5).

Prerequisites (systems knowledge required): POSIX process model (fork/exec/wait, process groups, sessions), Linux signals and signalfd(2), cgroups v2 (Documentation/admin-guide/cgroup-v2.rst), Unix-domain sockets and FD passing (SCM_RIGHTS), graph algorithms (topological sort, Tarjan SCC), state-machine design, epoll-based event loops.

Estimated timeline: Phase 0 — 2 weeks. Full system (Phases 0–11) — 7–9 months for a small team (2–3 engineers) working from this specification.

Deferred features (full table: Deferred Features Register, §37):

  • cgroups v1 dual-hierarchy support — PhaseDeferred("§19").
  • Bundled OCI container runtime — PhaseDeferred("§9").
  • Embedded SELinux/AppArmor policy engine — PhaseDeferred("§24").
  • Transient unit creation via the control bus (systemd-run equivalent) — PhaseDeferred("§20").
  • Multi-seat session manager (logind-equivalent) — PhaseDeferred("§21").
  • Automated 30-day soak/fuzz canary pipeline — PhaseDeferred("§29").
  • IPv6/dual-stack socket-activation matrix beyond a single ListenStream= — PhaseDeferred("§20").

2. Why Build This

An init system is the canonical example of infrastructure whose architectural decisions echo for decades: it is the only process the kernel starts unconditionally, the eventual parent of every orphan, and the single point where "is the system up" gets defined. The unique systems knowledge it teaches: dependency-graph correctness under live mutation (daemon-reload while units are mid-activation), signal-safe programming as PID 1 (a lost SIGCHLD here is not a bug, it is a slow leak of the entire PID space), and resource isolation as a first-class scheduling concern (cgroups v2), not an afterthought bolted onto rlimit.

It matters architecturally because it is the one place where "declarative configuration" and "imperative process control" must be reconciled without either side losing: the unit graph is data (parsed, validated, diffed), but the thing it describes is a tree of live, signal-delivering, resource-consuming OS processes. It matters historically because the industry has now run three full architectural generations in public — sysvinit's shell scripts, upstart's event-driven jobs, systemd's transactional unit graph — and each generation's failure mode is a lesson: implicit ordering (sysvinit), non-deterministic convergence (upstart), and (systemd's own steady lesson) the cost of a single process owning too much surface area (exactly why this blueprint's ADR-15/ADR-16 draw hard scope lines).

The engineering muscles it builds: writing async, signal-driven Rust with no tolerance for a stalled reactor thread; treating a directed graph as the primary data structure of a systems project; and reasoning about a state machine that must be total (every (state, event) pair defined, P7) because "undefined behavior" in PID 1 is "undefined behavior for the whole host."

Cross-links to sibling systems: the dependency-graph engine (§14 Phase 2) is the same topological-sort-plus-cycle-detection discipline used by a Build System blueprint's task graph and a Job Scheduler blueprint's DAG scheduling; the cgroup resource-control work (§19 Phase 7) is a direct prerequisite for a Container Runtime blueprint's isolation layer; the journal (§22 Phase 10) shares its structured-log design space with a Distributed Tracing Collector blueprint.

Calibration value: an init system forces correct handling of exactly the primitives (signals, process groups, cgroups) that most application-level Rust never touches, and forces a team to build a deterministic simulator (is-verifier, §7) as a first-class deliverable rather than an afterthought — a discipline transferable to any concurrent systems project.

What Mastery Looks Like

  • Can explain, from memory, why signalfd and not sigaction is mandatory for reliable SIGCHLD handling in a process supervising hundreds of children — Phase 6 (§18).
  • Can design a unit-file format's drop-in layering (foo.service.d/*.conf) without breaking daemon-reload atomicity — Phase 1 (§13).
  • Can compute, on paper, whether a given dependency graph is safely activatable in parallel and identify the critical-path chain — Phase 2 and Phase 4 (§14, §16).
  • Can design a restart-policy state machine with exponential backoff and a flap-detection circuit breaker (StartLimitBurst) that provably terminates — Phase 5 (§17).
  • Can implement clone3(CLONE_INTO_CGROUP)-based atomic cgroup entry and explain why the alternative (fork, then write cgroup.procs) is a TOCTOU race — Phase 7 (§19).
  • Can design a socket-activation protocol (LISTEN_FDS, FD-passing) that survives a service crash without losing in-flight connections — Phase 8 (§20).
  • Can build a crash-consistent structured log store with a documented fsync/durability contract — Phase 10 (§22).
  • Can design a shutdown sequence that is the activation engine run backward under the same transactional guarantees, not a separate ad hoc code path — Phase 11 (§23).

Box notes. is-parser is pure data-in/data-out: no process is ever touched here (P1). is-graph is the single source of truth for ordering and requirement edges; it is rebuilt, never mutated in place, on every daemon-reload (I11). is-txn is the trust boundary between "what the admin/CLI asked for" and "what the kernel will be told to do" — every activation and every shutdown passes through it (I6, I13). is-activate is the concurrency boundary: it fans out into parallel batches bounded only by DAG readiness (P9). is-supervisor and is-cgroup are the persistence boundary for process/resource state (survives until the process exits). is-reap is PID 1's only consumer of SIGCHLD; every other subsystem learns of a child's exit through it, never independently. is-journal is the observability boundary — the only durable record once a process's stdout/stderr closes. The control bus (is-bus, driving is-cli) is the external interface: a Unix-domain socket trust boundary gated by filesystem permissions (ADR-07).

6. Design Principles

P1. Declarative units only. Units are pure data — no unit ever embeds executable control-flow logic beyond a command line and a handful of typed directives. Tradeoff: less expressive than an arbitrary shell script. Operational implication: a unit can be statically validated before any process runs. Violation cost: hidden, unauditable ordering dependencies (sysvinit's actual failure mode, §36).

P2. Single unified cgroup hierarchy (v2-only). One tree is the one truth about resource membership (ADR-03). Tradeoff: no v1 dual-hierarchy compatibility. Operational implication: one accounting model to reason about in incident response. Violation cost: split-brain resource accounting across controllers (cgroups v1's actual, documented failure mode).

P3. Transaction-before-execution. Every activation is planned as an atomic job set (§15 Phase 3) before any process is spawned. Tradeoff: adds a planning-phase latency (bounded by §4's graph-build constraint). Operational implication: activation either fully applies its plan or is rejected up front. Violation cost: partially-applied activation, inconsistent unit states (I11).

P4. Topological, not retry-based, activation. Deterministic order from a DAG sort (ADR-04), never "keep retrying until it converges" (Upstart's model). Tradeoff: requires precise dependency declarations from unit authors. Operational implication: boot order is reproducible across reboots (P13). Violation cost: nondeterministic boot races.

P5. SIGCHLD is sacred. Every child exit is observed exactly once; never lost, never silently coalesced away (I5). Tradeoff: mandates signalfd plus a bounded-drain event loop (ADR-20), not a naive signal handler. Operational implication: zombie count is always explainable. Violation cost: zombie accumulation, eventual PID-space exhaustion.

P6. PID 1 never exits to a bug. Every panic is caught, logged, and degrades a single unit to Failed — it never propagates to terminate the process (I10). Tradeoff: defensive catch_unwind wrapping at every per-unit callback boundary. Operational implication: a bug in one unit's handling never takes down the host. Violation cost: PID 1 exit ⇒ kernel panic.

P7. State machines are total functions. Every (state, event) pair has a defined transition, including explicit "ignore" and "error" arms — no unhandled combination (§8 Domain Model). Tradeoff: verbose transition tables. Operational implication: out-of-order event delivery (e.g. SIGCHLD racing a supervisor record write) has defined behavior. Violation cost: undefined behavior under unusual event ordering.

P8. Resource limits are a cgroup property, never an ad-hoc rlimit-only control. Every resource ceiling routes through the delegated cgroup hierarchy uniformly (I12). Tradeoff: requires subtree-delegation bookkeeping at every level. Operational implication: one place to inspect resource state per unit. Violation cost: escaped resource usage, OOM-killer selecting the wrong victim.

P9. Maximal safe parallelism. Activation batches are the finest-grained parallel groups the DAG allows — never serialize two units with no ordering edge between them. Tradeoff: scheduler complexity; many concurrent forks/execs to track. Operational implication: boot time approaches the critical-path length, not the total unit count. Violation cost: needlessly slow boot.

P10. Socket activation decouples startup cost from availability. A unit's listening socket exists before its process does (ADR entries under §9). Tradeoff: extra FD-passing plumbing (LISTEN_FDS). Operational implication: a cold service can be "available" (accepting connections) before it has forked. Violation cost: connection-refused windows during cold start, or thundering-herd effects at boot.

P11. Control-plane operations are idempotent where possible. daemon-reload, start, stop are safe to repeat without side effects beyond the first call. Tradeoff: extra state comparison before acting. Operational implication: a retried CLI command from a flaky script never double-starts a unit. Violation cost: duplicate cgroups, double-start races.

P12. Logs are structured at the point of capture. The journal captures key-value fields from the first byte written, not raw text later parsed (§22 Phase 10). Tradeoff: capture-side overhead versus a plain append log. Operational implication: every log query is a structured query, not a regex. Violation cost: unqueryable logs, forensic blindness during an incident.

P13. Determinism through sorted iteration. Every graph traversal iterates over a canonically ordered (BTreeSet/BTreeMap) structure, never an unordered hash iteration order. Tradeoff: forgoes a faster unordered-hash hot path. Operational implication: the same unit graph produces the same activation order on every reboot. Violation cost: unreproducible boot-order bugs.

P14. Graceful shutdown mirrors startup, inverted. Shutdown runs the reverse dependency order through the same transaction machinery as activation (§23 Phase 11), not a separate ad hoc "kill everything" path. Tradeoff: shutdown is not "just SIGTERM everything" — it is itself a planned transaction. Operational implication: dependents always finish before their dependencies are torn down. Violation cost: services losing a dependency (e.g. a database) mid-flush.

8. Domain Model

8.1 Unit / service model

A unit is (name, kind) — the pair, not the name alone, is the identity key (foo.service and foo.socket are distinct units). Nine kinds ship in Phase-0 scope: Service, Socket, Timer, Path, Target, Slice, Scope, Device, Mount.

[Unit]
Description=Example web service
Requires=network.target
After=network.target local-fs.target
OnFailure=alert.service

[Service]
ExecStart=/usr/bin/webd --port=8080
Restart=on-failure
RestartSec=200ms
StartLimitBurst=5
StartLimitIntervalSec=10s
MemoryMax=256M
CPUWeight=100

[Install]
WantedBy=multi-user.target

Directives resolve into a typed UnitConfig (§11). Unknown keys are warned, not fatal — forward compatibility with future directives (P1). Drop-in files (foo.service.d/*.conf) layer over the base file; later drop-ins override earlier directive values, set-valued directives (After=, Wants=) accumulate.

8.2 Dependency ordering DAG

Two edge classes, deliberately not conflated:

  • Requirement edges (Requires, Wants, BindsTo, Conflicts) — determine whether a unit activates and what happens if a peer fails.
  • Ordering edges (After, Before) — determine when, relative to peers.
Relation Class Semantics
Requires=B requirement A fails if B fails or is stopped
Wants=B requirement (weak) A starts regardless of B's outcome
BindsTo=B requirement (strong) A is stopped if B stops, even post-facto
Conflicts=B requirement (negative) A and B are never both Active
After=B ordering A activates only once B has reached a terminal state
Before=B ordering (inverse of After) —

A unit graph is validated in two independent passes: cycle detection on the ordering subgraph alone (Tarjan SCC, I1), and a requirement-consistency pass (Conflicts= co-occurring with Requires= on the same target is a load error). After= naming a non-existent unit is a warning (I1's cycle check does not apply to edges into nonexistent nodes); Requires= naming a non-existent unit is an error at transaction-build time (I4).

8.4 Worked example — activation of a 3-unit chain

Units: local-fs.target (no deps) ← After= ← db.service (Requires=local-fs.target) ← After= ← web.service (Requires=db.service). Transaction for target web.service: transitive closure = {local-fs.target, db.service, web.service}. Topological sort of the ordering subgraph yields batch 1 = {local-fs.target}, batch 2 = {db.service} (its only After= dep, local-fs.target, is now terminal), batch 3 = {web.service}. Each batch activates in parallel internally (trivial here, one unit each); is-verifier asserts I6 (order is a valid topological sort) after replay.

8.5 Malformed-input example

[Unit]
After=db.service
[Service]
ExecStart=/usr/bin/web
Restart=alwyas

Two defects: (1) Restart=alwyas is a typo — is-parser rejects the value (not the key) against the closed enum RestartPolicy, producing ParseError::InvalidEnumValue { key: "Restart", value: "alwyas", unit: "web.service" }, and the unit load fails closed (does not silently default to no). (2) After= with no matching Requires=/Wants= is legal but produces only an ordering constraint with no activation trigger — web.service will never auto-activate unless something else Wants=s it; is-verifier's lint pass flags this as OrderingWithoutActivation (a warning, not a load error).

8.6 Failure-path example

db.service is Requires=d by web.service and fails during Activating (ExecStart binary missing, ENOENT). Per I4, web.service cannot become Active while db.service is not Active: is-txn marks web.service Failed without ever issuing its fork+exec (no Activating state is entered for a unit whose hard requirement is already known-failed at batch-schedule time, §16 Phase 4 N.2). db.service's OnFailure=alert.service (if declared) is activated as a new, independent transaction. The operator sees both units in Failed via is-ctl status, with db.service's journal entry carrying the ENOENT detail and web.service's carrying FailedDependency{unit:"db.service"}.

12. Phase 0 — Repo Skeleton & Correctness Kernel

12.1 Objectives

Stand up the Cargo workspace (§10), CI matrix (ADR-13), and the correctness kernel: is-core's types (§11), a minimal is-verifier capable of running one trivial invariant assertion, and a QEMU boot smoke test that boots a stub init to a single target with no real units. No dependency graph, no supervision yet — this phase proves the toolchain, not the domain logic.

12.2 Detailed Implementation Steps

Scaffold crates/is-core with Unit, UnitKind, UnitState, Dependencies, InitError exactly as declared in §11 (terminology lock, P13's BTreeSet choice applies from day one). Wire Makefile targets (build, test, fuzz, bench). Author .github/workflows/qemu-boot.yml: builds the static musl binary (ADR-14), boots it under QEMU as PID 1 in a disposable initramfs, and asserts the process reaches a hardcoded "boot complete" log line without panicking (I10's earliest possible test). Author is-verifier's harness skeleton: a Simulator struct owning a mock CLOCK_MONOTONIC (ADR-19) and a mock process table, with one registered assertion (a stand-in for I10: "the simulated PID 1 never unwinds past catch_unwind").

12.3 Deliverable

cargo build --workspace succeeds; CI green on both ci.yml and qemu-boot.yml; the QEMU image boots the stub init to the hardcoded log line and shuts down cleanly under a test harness invocation.

12.4 Acceptance Criteria

Cold cargo build --all-targets completes in < 100 s on the reference CI runner (4 vCPU); QEMU boot-to-log-line completes in < 5 s wall clock; zero compiler warnings with #![deny(warnings)] on is-core.

12.5 Conformance Fixtures

conformance/buckets/parser/ seeded with stub.target (a zero-directive Target unit) — purpose: prove the workspace round-trips a trivial unit through is-core types; expected output: Unit { kind: Target, state: Inactive, .. }.

12.6 Pitfalls

  • Running the QEMU test init as the host's actual PID 1 (never — always inside a disposable VM/container, per the isolation note carried from the original draft).
  • Forgetting #![no_std]-adjacent discipline creep: PID 1 links libc but must not assume a fully-populated /proc//sys at the instant it starts (ADR-14).

12.7 Performance Concerns

None load-bearing yet — this phase's only performance constraint is the build-time ceiling in 12.4; no runtime hot path exists.

12.8 Edge Cases

QEMU image boot failure due to a missing initramfs entry (CI must fail loudly, not hang); a workspace crate compiled with a stale Cargo.lock (locked by ADR-18 from day one, not deferred to a later phase).

12.9 Failure Analysis

A red qemu-boot.yml run blocks merge (branch protection); a hung QEMU boot (no log line within timeout) is treated as a boot failure, not a slow pass — CI kills the VM at a fixed wall-clock ceiling and reports failure, never "flaky, retry".

12.10 Operational Notes

No operator-facing surface yet. The only "deployment" is the CI-produced QEMU image artifact, retained for 30 days as a build-provenance record (feeding ADR-18's reproducibility discipline forward).

13. Phase 1 — Unit-File Parser & Config Model

13.1 Objectives

Implement is-parser: the key=value INI-like grammar (ADR-02), section gating ([Unit], [Service], [Install]), drop-in layering, and the closed-enum validation demonstrated in §8.5. Output is UnitConfig (§11) — data only, per P1.

13.2 Detailed Implementation Steps

Lexer tokenizes lines into (section, key, value) triples; a continuation (trailing \) merges the next physical line before tokenizing (a stateful lexer, not a stateless line-splitter). Section gating rejects a [Service]-only key (e.g. ExecStart=) appearing under [Unit] as a load error, citing P1's "validated before any process runs" discipline. Enum-valued directives (Restart=, kind-specific directives) parse against a closed Rust enum (RestartPolicy, §11) — an unrecognized value is InitError::ParseError (§8.5's malformed-input example), never a silent default. Drop-in resolution: for each base unit, glob foo.service.d/*.conf in lexical (BTreeSet-sorted, P13) order and apply as an ordered patch — scalar directives overwrite, set-valued directives (After=, Wants=) accumulate via BTreeSet::extend. Environment variable expansion (${FOO}) is deferred to is-supervisor's spawn step (§17), never performed here — this is the ADR-09-adjacent "parse ≠ activation-time" boundary (I11 depends on this separation holding).

13.3 Deliverable

is-parser::parse_unit(path) -> Result<UnitConfig, InitError> plus the drop-in resolver, both covered by the parser conformance bucket.

13.4 Acceptance Criteria

Parses 500 synthetic unit files in < 50 ms single-core (§4's 10,000 files/sec reference class); 100% of the parser conformance bucket's 40 fixtures pass; zero panics across a 10-minute cargo fuzz run parse_unit corpus run (ADR-12).

13.5 Conformance Fixtures

fixtures/parser/multiline-continuation.service — purpose: verify backslash continuation; expected: single merged ExecStart= value. fixtures/parser/ bad-enum.service — purpose: §8.5's malformed-Restart-value case; expected: ParseError::InvalidEnumValue. fixtures/parser/dropin-override.service{,.d/ 10-override.conf} — purpose: verify drop-in layering order; expected: the .d/ value wins for scalars, both values present for After=.

13.6 Pitfalls

  • Expanding ${FOO} at parse time instead of activation time (I11-adjacent bug: a daemon-reload would re-resolve against the init's environment, not the eventual service's).
  • Treating an unknown key as fatal — breaks forward compatibility (P1); must warn and continue.
  • Non-deterministic drop-in application order from an unsorted directory read (violates P13; always sort the glob results).

13.7 Performance Concerns

Parsing allocates one String per value; a 500-unit boot set should stay under 5 MB transient allocation. Drop-in glob resolution is O(units × dropins), bounded in practice by directory size, not unit count.

13.8 Edge Cases

Empty unit file (all-defaults UnitConfig); a unit file that is a symlink to /dev/null (systemd's "masked unit" convention — treated as Inactive, never-activatable, without a load error); a drop-in directory that exists but contains zero .conf files (no-op, not an error); a unit file exceeding a 64 KiB size ceiling (rejected — a load error, not a silent truncation).

13.9 Failure Analysis

A parser bug that silently accepts malformed input produces a wrong-but-valid UnitConfig, which propagates undetected into is-graph; the debug-build is-verifier re-parses every fixture in the corpus on every CI run and diffs against a golden UnitConfig snapshot to catch drift (ties to I11's "validate before touching state" discipline one layer up).

13.10 Operational Notes

Parse errors surface to journalctl-equivalent output tagged with the offending file path and line number (not just "unit failed to load"); is-ctl daemon-reload reports a per-file error list, never a single opaque "reload failed."

14. Phase 2 — Dependency Graph & Ordering

14.1 Objectives

Implement is-graph: build the two-class edge model (§8.2) from a set of parsed units, run cycle detection on the ordering subgraph (I1), and run the requirement-consistency pass (Conflicts=+Requires= co-occurrence, §8.2).

14.2 Detailed Implementation Steps

Build an adjacency representation keyed by UnitName with two edge sets per node (ordering, requirement), iterating input units in BTreeSet order (P13). Cycle detection: Tarjan's strongly-connected-components algorithm restricted to the ordering subgraph alone (After/Before edges) — any SCC of size > 1 is InitError::GraphCycle (I1), named for the ADR-04 decision to prefer a single deterministic pass over Upstart's retry model. After=/Before= targeting a unit absent from the loaded set is a warning (recorded, surfaced via is-ctl, never a load error — distinguishing it from Requires= on a missing unit, which is a load-time error caught here before it can reach I4 territory at transaction-build time). Requirement-consistency pass: for every unit, if Conflicts= and Requires= name the same target, reject the unit's load (a configuration error, not a runtime one) — this is the one place is-graph produces user-facing static analysis beyond pure structure.

14.3 Deliverable

is-graph::build(units) -> Result<Graph, InitError> and is-graph::detect_cycles(&Graph) -> Vec<Vec<UnitName>>, covered by the graph conformance bucket, plus a tools/graph-visualize CLI emitting Graphviz DOT for operator debugging.

14.4 Acceptance Criteria

Builds a 500-node graph in < 30 ms (§4's reference class); the graph bucket's 25 fixtures (including 5 deliberately cyclic) all classify correctly; is-verifier asserts I1 on every fixture with zero false negatives across a 1-hour fuzz run.

14.5 Conformance Fixtures

fixtures/graph/simple-cycle.units (A.After=B, B.After=A) — expected: GraphCycle{members:[A,B]}. fixtures/graph/conflicts-requires.units — expected: load rejection citing the co-occurrence rule. fixtures/graph/dangling-after.units — expected: successful build with a recorded warning, not an error.

14.6 Pitfalls

  • Running cycle detection over the combined (ordering + requirement) graph instead of the ordering subgraph alone — a Requires=-only relationship between two units with no ordering constraint is not a deadlock and must not be flagged (§8.2's explicit design note).
  • Treating After=-to-missing-unit as an error, which needlessly breaks unit files written for a superset deployment (some optional units absent).

14.7 Performance Concerns

Tarjan SCC is O(V+E); the dominant real cost at scale is edge-set construction from BTreeSet inputs (O(E log E)) — acceptable against the 100 µs/node budget (§4) up to the 500-node reference class; the 8,192-unit hard ceiling is documented as degraded-mode only (§34 Capacity Model item 5).

14.8 Edge Cases

A self-referential After= on its own unit (degenerate 1-cycle, caught by the same SCC pass); a unit graph with zero edges (all-parallel, valid); a BindsTo=+Conflicts= combination on the same target (not rejected here — deferred to runtime, since BindsTo= is a requirement-strength distinction, not a static contradiction).

14.9 Failure Analysis

A missed cycle (a bug in the SCC implementation) manifests as an infinite wait at activation time (§16 Phase 4) — is-verifier's fuzz corpus specifically targets graphs with multi-node cycles of varying SCC shapes (chains-into-cycles, disjoint cycles) to defend against implementation-specific SCC bugs.

14.10 Operational Notes

is-ctl list-dependencies <unit> renders the resolved edge sets for operator inspection; a rejected daemon-reload due to a newly introduced cycle reports the exact SCC membership list, not just "cycle detected."

15. Phase 3 — Transaction Engine

15.1 Objectives

Implement is-txn: given a validated Graph (§14) and a requested target unit, compute the transitive closure of units to activate, snapshot their current states, and produce an ordered batch plan (I6) — the trust boundary between "what was requested" and "what will be told to the kernel" (P3).

15.2 Detailed Implementation Steps

Transitive closure: BFS over Requires+Wants edges from the target, collecting the activation set (§8.4's worked example is this algorithm's canonical trace). Batch computation: topological sort of the ordering subgraph restricted to the activation set, grouped into rounds where round k contains every unit whose After= dependencies are already in round < k (or absent from the set entirely) — this is I6's "valid topological sort" requirement made concrete. State snapshot: is-txn takes an Arc-shared read snapshot of every unit's current UnitState before planning begins (P3's "before execution" — a unit that fails mid-plan-computation via a concurrent event does not retroactively invalidate an already-committed plan; it is picked up by the next transaction). Commit: for each batch in order, hand the round to is-activate (§16) and block on that round's readiness signal before releasing the next round — this sequential round boundary is what parallel activation composes with, not around. A unit already Active at snapshot time is skipped (idempotent re-activation, P11).

15.3 Deliverable

is-txn::plan(&Graph, &UnitName) -> Result<Transaction, InitError> and is-txn::commit(Transaction) -> ActivationReport, covered by the txn conformance bucket.

15.4 Acceptance Criteria

Plans a 500-unit transitive closure + batch sort in < 50 ms (§4); the txn bucket's 20 fixtures pass, including 3 asserting idempotent re-start produces zero new fork calls (P11); is-verifier replay confirms I6 on every recorded transaction in the fixture corpus with zero reorder violations.

15.5 Conformance Fixtures

fixtures/txn/three-unit-chain.units — the §8.4 worked example; expected batch plan [[local-fs.target],[db.service],[web.service]]. fixtures/txn/ already-active-skip.units — expected: re-planning a fully-Active target produces an empty batch list.

15.6 Pitfalls

  • Computing batches by walking the live unit-state table during the sort instead of the snapshot — reintroduces exactly the race I6 exists to prevent (a unit transitioning Failed mid-sort must not silently reorder the plan already handed to the caller).
  • Forgetting Conflicts= at plan time: activating a target while a conflicting unit is Active must stop the conflicting unit as part of the same transaction, not a follow-up one (else a window exists where both are transiently Active).

15.7 Performance Concerns

BFS closure is O(V+E); batch grouping is a second O(V+E) pass over the restricted subgraph. The dominant cost at scale is the Arc snapshot clone of unit states — mitigated by snapshotting only the UnitState enum (a Copy type), not the full Unit struct.

15.8 Edge Cases

A target with an empty transitive closure (already fully satisfied); a transaction whose closure includes a unit currently Deactivating (must wait for terminal state before re-activating, not race the two transitions); a daemon-reload arriving mid-commit (I11: the in-flight transaction completes against its already-snapshotted graph; the new graph takes effect for the next transaction only).

15.9 Failure Analysis

A unit's Requires= target fails mid-batch: is-txn marks the dependent Failed without issuing its fork+exec (I4, §8.6's failure-path example) and continues the rest of the batch — one failure does not abort sibling units with no requirement relationship to the failure.

15.10 Operational Notes

is-ctl status --transaction shows the last N committed transactions with their batch structure, timestamps, and per-unit outcome — the primary debugging surface for "why didn't X start" incidents (feeds the Runbook in §26).

16. Phase 4 — Parallel Activation Engine

16.1 Objectives

Implement is-activate: execute one transaction batch (round) in parallel, respecting the concurrency ceiling (§4), and report per-unit readiness back to is-txn so the next round can be released (P9's "maximal safe parallelism" made concrete).

16.2 Detailed Implementation Steps

For a given round, fan out one supervised spawn attempt per unit concurrently (bounded by the epoll reactor's single-threaded event loop, ADR-05 — "concurrent" here means "interleaved via non-blocking I/O," not OS-thread-parallel; the blocking thread pool handles only the cgroup-creation syscalls that cannot be made non-blocking). Each unit's spawn transitions it Inactive → Activating (§8.3) and starts a per-unit TimeoutStartSec timer (default 90 s) on the monotonic clock (ADR-19). A unit's round is "ready" once it reaches Active or Failed; is-activate reports round completion to is-txn only once every unit in the round is ready — a round does not release early. A unit whose Requires= dependency already failed at round-schedule time (I4) is marked Failed without ever entering Activating (§8.6).

16.3 Deliverable

is-activate::activate(Round) -> ActivationReport returning per-unit terminal state and timing, covered by the activate conformance bucket.

16.4 Acceptance Criteria

Full 500-unit transitive activation completes in ≤ 5 s p50 (§4's boot budget, excluding the ≤ 1.2 s parse+graph+plan overhead already budgeted upstream); a unit stuck in Activating past TimeoutStartSec transitions to Failed within 100 ms of the deadline; the activate bucket's 18 fixtures pass including 4 timeout-triggering cases.

16.5 Conformance Fixtures

fixtures/activate/parallel-independent.units — 20 units with no edges between them; expected: single round, all Active. fixtures/activate/slow-start- timeout.units — an ExecStart= pointing at sleep 999; expected: Failed with ActivationTimeout after TimeoutStartSec.

16.6 Pitfalls

  • Releasing the next round before every unit in the current round has reached a terminal state — reintroduces the exact race I6/P4 exist to prevent (a "mostly done" round is not a done round).
  • A blocking cgroup-creation syscall issued directly on the reactor thread stalls every other unit's spawn in the same round (ADR-05's rationale made concrete; route through the blocking thread pool).

16.7 Performance Concerns

Fork+exec latency (§4: < 5 ms) dominates per-unit activation cost; the round-boundary synchronization overhead must stay sub-millisecond relative to that, or parallelism gains are erased by coordination cost (§34 Capacity Model item 7 quantifies the equivalent cgroup-serialization cost this phase's parallelism specifically avoids).

16.8 Edge Cases

Two units in the same round racing to create a shared parent slice cgroup (resolved by is-cgroup's idempotent mkdir-or-check-exists semantics, not by is-activate serializing them); a round containing a single unit (degenerate case, no parallelism benefit but same code path); a unit whose ExecStart= binary is missing (ENOENT at execve — immediate Failed, no timeout wait needed).

16.9 Failure Analysis

A round with one persistently timing-out unit does not block sibling units in the same round (each unit's timeout is independent) but does delay the next round if a sibling After=-depends on the timing-out unit's terminal state — this is expected backpressure, not a bug, and is surfaced via is-ctl status showing the blocking unit explicitly.

16.10 Operational Notes

Round timing (start, per-unit terminal state, wall-clock span) is logged to the journal (§22) with round_id correlation, enabling post-boot analysis of which round dominated total boot time (feeds §30 Performance Engineering's boot-timing breakdown).

17. Phase 5 — Process Supervision & State Machine

17.1 Objectives

Implement is-supervisor: own the per-unit SupervisorRecord (§11), perform the actual fork/clone3+exec, and enforce Restart= policy with exponential backoff and the StartLimitBurst circuit breaker (I8).

17.2 Detailed Implementation Steps

Before calling clone3, write the SupervisorRecord (unit name, a uniquifier, zeroed PID) into a lookup table keyed by the uniquifier — then call clone3(CLONE_INTO_CGROUP), and on return, patch the record with the real PID (I2's ordering requirement, closing the race described in MM5/§8.6-adjacent reasoning: a child that segfaults before the record is patched is still attributable because the uniquifier, not the PID, is the initial lookup key). setsid() is called before exec so the child owns its own session (P1's process-group hygiene, Kerrisk ch. 34 applied). On exit, consult Restart= (§11's RestartPolicy enum) against the exit disposition (code 0, nonzero, signal, watchdog-timeout, "abnormal"); on a restart-eligible exit, apply exponential backoff (RestartSec= doubled each attempt, ceiling RestartMaxIntervalSec) and increment the StartLimitBurst window counter (atomic, time-windowed against CLOCK_MONOTONIC, ADR-19) — exceeding the burst within StartLimitIntervalSec transitions the unit to Maintenance (§8.3), never straight back to Activating (I8). RemainAfterExit=yes lets a oneshot unit's clean exit be treated as entering Active rather than Inactive.

17.3 Deliverable

is-supervisor::spawn(&UnitConfig, &CgroupPath) -> Result<Pid, InitError> plus the restart-policy state machine, covered by the supervisor conformance bucket.

17.4 Acceptance Criteria

Fork+exec completes in < 5 ms p99 (§4); a flapping unit (Restart=always, immediate-exit ExecStart=) reaches Maintenance within StartLimitBurst × RestartSec (default: 5 × 100 ms = 500 ms, matching §34's derived restart-storm ceiling) and never exceeds it; the supervisor bucket's 22 fixtures pass.

17.5 Conformance Fixtures

fixtures/supervisor/flap-loop.service (Restart=always, ExecStart=/bin/false) — expected: Maintenance within 500 ms, exactly StartLimitBurst restart attempts logged. fixtures/supervisor/remain-after-exit.service — expected: Active after clean exit, no restart attempted.

17.6 Pitfalls

  • Writing the SupervisorRecord after clone3 returns instead of before — reopens the I2 race this phase exists to close.
  • Resetting the StartLimitBurst window counter with a separate read-then-reset instead of an atomic compare-and-swap (the historical systemd race cited in ADR discussion, §9 ADR-04's lineage note) — under concurrent restart storms this undercounts and lets a flapping unit escape the circuit breaker.
  • Forgetting setsid(): a SIGINT in the controlling terminal (if any) kills the child alongside the init.

17.7 Performance Concerns

clone3 + execve is the dominant per-unit cost (§4's 5 ms budget); the backoff-window counter update must be a single atomic operation to avoid lock contention under a restart storm (I5-adjacent: this is the supervisor's analog of the SIGCHLD-storm concern).

17.8 Edge Cases

A unit that execs successfully but the binary immediately SIGSEGVs before any observable output (attributable via the I2 uniquifier mechanism, not the PID); a restart attempt racing a concurrent daemon-reload that removes the unit entirely (the in-flight restart completes against the pre-reload config, per I11); clock adjustment (NTP step) during a backoff window — immune, because backoff timing uses CLOCK_MONOTONIC (ADR-19), not wall-clock time.

17.9 Failure Analysis

A misconfigured Restart=always on an immediately-failing service is the single most common operator-facing incident class (Failure Modes §25, FM-4); the circuit breaker (I8) bounds its blast radius to StartLimitBurst restarts before Maintenance, at which point is-ctl status surfaces the unit as needing reset-failed, not silently retrying forever.

17.10 Operational Notes

Every restart attempt, backoff interval, and burst-counter state is logged with unit, attempt_n, next_backoff_ms fields (P12); is-ctl reset-failed <unit> clears the window counter and transitions Maintenance → Inactive, the only operator-initiated escape from that state.

18. Phase 6 — PID 1 Signal Handling & Orphan Reaping

18.1 Objectives

Implement is-reap: the sole SIGCHLD consumer for the whole process, driven by signalfd (P5, MM5), including orphan reaping (processes reparented to PID 1 whose original parent exited) and the bounded-drain backpressure discipline (ADR-20).

18.2 Detailed Implementation Steps

Register SIGCHLD for delivery via signalfd(2) and block it from default disposition/sigaction; add the resulting FD to the same epoll instance used by sockets, timers, and the control bus (single reactor, ADR-05, ADR-08). On a readable event, read struct signalfd_siginfo records in a loop, capped at 256 per iteration (ADR-20) — after 256, yield to the rest of the event loop and resume on the next epoll wake, preventing a SIGCHLD storm from starving socket and timer processing (§34 Capacity Model item 1 quantifies the resulting throughput ceiling). For each siginfo, call waitpid(pid, &status, WNOHANG) to reap and retrieve the real exit status (signalfd tells you that something happened, waitpid tells you what — MM5). Look up the reaped PID against the SupervisorRecord table (I2); a hit routes to is-supervisor's restart-policy logic (§17); a miss is classified as an orphan — reparented to PID 1 by the kernel when its original parent exited — and is simply logged and dropped (no restart policy applies to unknown children, P7's explicit "ignore" arm).

18.3 Deliverable

The is-reap signalfd loop integrated into the main reactor, covered by the supervisor bucket's reap-specific fixtures (shared bucket with Phase 5, since reaping and restart policy are tested end-to-end together).

18.4 Acceptance Criteria

Reap latency (exit → supervisor state update) is p99 ≤ 5 ms (§4); a synthetic SIGCHLD-storm test (500 children exiting within 10 ms) produces zero lost exits and zero zombies remaining after the storm settles, verified via /proc/<pid>/task zombie-state scan.

18.5 Conformance Fixtures

fixtures/supervisor/sigchld-storm.units — 500 short-lived processes spawned simultaneously; expected: all reaped, zero zombies, reap-batch histogram shows at least one 256-capped iteration. fixtures/supervisor/orphan-reap.units — a process that double-forks and lets its immediate parent exit; expected: the grandchild is reparented to the test init and reaped as an orphan (logged, no restart attempted).

18.6 Pitfalls

  • Using a traditional sigaction handler instead of signalfd — reintroduces signal coalescing, the exact bug class P5/MM5 exist to eliminate.
  • Reaping without the WNOHANG flag — blocks the reactor thread if no child has actually exited yet (a logic bug distinct from, but easily confused with, the storm-throttling concern).
  • Treating an orphan reap as an error condition — it is expected, routine behavior for PID 1 and must not be logged above debug/info priority.

18.7 Performance Concerns

The 256-event cap (ADR-20) trades worst-case per-storm reap latency for event-loop fairness; §34 Capacity Model item 1 shows the theoretical ceiling this bound imposes is far above realistic fork/exit rates, so it is not the system's actual bottleneck under normal load.

18.8 Edge Cases

Two children exiting in the same kernel timeslice, coalesced into a single SIGCHLD delivery — handled correctly because the drain loop always calls waitpid(WNOHANG) to exhaustion regardless of signal count (I5's core guarantee, independent of how many signalfd events actually arrived); a child that is stopped (SIGSTOP) rather than exited — waitpid's WUNTRACED is deliberately not set, since PID 1 does not job-control its children, only reaps true exits.

18.9 Failure Analysis

A lost SIGCHLD (I5 violation) would manifest as zombie accumulation; as a structural backstop beyond the primary signalfd path, a periodic 5-second waitpid(-1, WNOHANG) sweep runs regardless of signal delivery, so even a hypothetical signalfd registration bug degrades to "5-second reap latency," not "unbounded zombie growth" (belt-and-suspenders decision documented against I5).

18.10 Operational Notes

reap_batch_size (histogram) and orphan_reap_total (counter) are the primary telemetry for this subsystem; a sustained non-zero orphan_reap_total rate is a signal that some supervised service is failing to reap its own grandchildren, surfaced as a runbook trigger (§26).

19. Phase 7 — cgroups v2 Resource Control

19.1 Objectives

Implement is-cgroup: create a per-unit cgroup, write declared resource limits before the unit's first process exists (I12), and enter the cgroup atomically via clone3(CLONE_INTO_CGROUP) (P8, MM4).

19.2 Detailed Implementation Steps

Cgroup path convention: /sys/fs/cgroup/<slice>.slice/<unit>.service/ (mirrors the Repository Layout / Core Schema naming, §10/§11's CgroupPath). Before spawning, verify the parent cgroup has delegated the needed controllers via cgroup.subtree_control (write +memory +cpu +io +pids if absent and the init owns the parent, per Tejun Heo's cgroup-v2 documentation, §5 applied here); write memory.max, cpu.weight, io.weight from the unit's UnitConfig (§11) into the newly created cgroup directory. Only after every limit file write succeeds does is-supervisor (§17) issue clone3(CLONE_INTO_CGROUP) targeting this cgroup's FD — the ordering is enforced by is-cgroup::create_and_enter's single entry point, which is-supervisor calls rather than sequencing the two steps itself (I12 is structurally guaranteed by API shape, not by caller discipline alone). Teardown: on the unit's last process exiting (confirmed via cgroup.events's populated field reaching 0), rmdir the cgroup unless Delegate=yes (I3) — a Delegate=yes unit owns its own subtree and is responsible for its own sub-cgroup cleanup.

19.3 Deliverable

is-cgroup::create_and_enter(&CgroupPath, &Limits) -> Result<(), InitError> plus the teardown hook, covered by the cgroup conformance bucket.

19.4 Acceptance Criteria

Create+enter completes in ≤ 5 ms p99 (§4); a unit exceeding memory.max is OOM-killed within the cgroup scope only (verified: sibling cgroups' processes unaffected) in the cgroup bucket's OOM fixture; zero cgroup_late_limit_total events (I12) across the fixture corpus.

19.5 Conformance Fixtures

fixtures/cgroup/memory-oom.service (MemoryMax=16M, a memory-bomb ExecStart=) — expected: memory.events's oom_kill count increments, sibling unit's cgroup shows zero OOM events. fixtures/cgroup/no-delegation. service — parent cgroup missing subtree_control entries — expected: load error surfaced before spawn is attempted, not a silent unconstrained run.

19.6 Pitfalls

  • Writing limits after fork() and adding the PID to cgroup.procs afterward — the TOCTOU race MM4 names explicitly: the child can allocate before the limit lands.
  • Forgetting parent-cgroup delegation bootstrap — child cgroup creation succeeds but limits silently have no effect (§35's OOM-not-enforced runbook, §26, traces to exactly this).
  • Cgroup path collisions between a slice and a same-named service (namespaced by the .slice/.service suffix convention, never bare names).

19.7 Performance Concerns

Cgroup filesystem writes are syscalls against cgroupfs, not in-memory operations — batched where possible (all limit files written before the single clone3 call, not interleaved with other unit's spawns); §34 Capacity Model item 7 quantifies why this phase's per-unit cost must be parallelized across a batch (§16 Phase 4) rather than serialized.

19.8 Edge Cases

A unit with no declared limits at all (cgroup still created, for accounting/ process-tracking purposes, but no limit files written — inherits parent defaults); nested slices (parent.slice/child.slice/unit.service) requiring delegation at every level, not just the leaf; a cgroup rmdir racing a just-reparented orphan process momentarily still resident (retried with backoff, not treated as a hard failure).

19.9 Failure Analysis

A cgroup leak (I3 violation — a directory left behind after its unit's last process exits) accumulates /sys/fs/cgroup/ nodes indefinitely; a periodic reconciliation scan (parallel to is-reap's zombie backstop, §18.9) compares the on-disk cgroup tree against the known-units set and rmdirs anything orphaned past a grace period, emitting cgroup_orphan_count.

19.10 Operational Notes

is-ctl status <unit> --cgroup surfaces memory.current, memory.max, cpu.weight, and memory.events's oom_kill count directly from cgroupfs — the primary diagnostic path for the OOM runbook (§26).

20. Phase 8 — Socket & Bus Activation

20.1 Objectives

Implement is-socket (lazy service startup via listening-socket ownership, P10, MM6) and is-bus (the Unix-domain control bus D-Bus-adjacent protocol, ADR-07, carrying is-ctl's start/stop/status/daemon-reload operations).

20.2 Detailed Implementation Steps

A Socket unit (ListenStream=) creates its listening socket at boot time — before its associated Service unit exists as a process — and registers the FD with the main epoll reactor. On an incoming connection event, is-socket dups the listening FD (I7's "retained FD" requirement — the init keeps the original, the spawned service inherits the duplicate) and activates the associated service unit with LISTEN_FDS=1 in its environment and the socket FD placed at file descriptor 3 (the systemd-documented convention, §5 Required Reading applied). The service accepts the connection itself once running; the init's retained duplicate means a service crash mid-connection does not lose the listening socket (I7) — is-socket simply re-activates the service on the next connection event. is-bus implements a minimal D-Bus-like framing (message type, path, method name, body) over a Unix-domain socket at a well-known path (/run/is-bus.sock, mode 0660, group-gated per ADR-07); is-cli's is-ctl binary is the sole reference client. Each bus method call is validated against a capability check (calling UID/GID against an allow-list) before being routed to is-txn/is-supervisor.

20.3 Deliverable

is-socket::activate_on_connection(&SocketUnit) -> Result<OwnedFd, InitError> and the is-bus request/response loop, covered by the socket-act conformance bucket.

20.4 Acceptance Criteria

Cold socket-activation latency (connection arrival → service Active) is ≤ 50 ms p50 (§4); a service crash mid-connection does not drop the listening socket (verified: a second connection attempt within 1 s succeeds and re-activates the service); the socket-act bucket's 15 fixtures pass; bus command round-trip latency ≤ 50 ms p50 (§4's control-bus RTT budget plus processing overhead).

20.5 Conformance Fixtures

fixtures/socket-act/cold-start.socket+service — a ListenStream=-only socket with Accept=no; expected: connection triggers service spawn with LISTEN_FDS=1 correctly set in the child's environment. fixtures/socket-act/ crash-mid-connection.service — service SIGKILLs itself immediately after accept; expected: listening socket survives, next connection re-activates.

20.6 Pitfalls

  • Letting the service's own FD-inheritance discipline (normally: close all FDs except stdio, per §17's spawn path) accidentally close the inherited listening FD — requires an explicit O_CLOEXEC-clearing exception for FD 3..N+2 only (a carefully scoped exception to an otherwise strict default-deny FD policy).
  • A bus client issuing malformed frames that desync the framing parser — must fail that one connection, never destabilize the bus listener itself.

20.7 Performance Concerns

Socket-activation latency is dominated by the same fork+exec cost as any other unit spawn (§17.7); the FD-duplication step itself is a single syscall, negligible against that baseline.

20.8 Edge Cases

A connection arriving while the associated service is already Activating from a previous connection (queued by the kernel's listen backlog, not double-spawned — is-socket checks unit state before triggering a second activation); a bus client that disconnects mid-request (the in-flight request is abandoned, not retried on the server side); IPv6/dual-stack sockets beyond a single ListenStream= (out of Phase-8 scope — PhaseDeferred("§20"), §37).

20.9 Failure Analysis

A leaked listening socket (service exits without properly registering, and is-socket's retained duplicate is itself somehow lost — a defensive-only scenario) is detected by is-verifier's socket-activation fixture asserting I7 after every simulated service-crash event; recovery is the init re-creating the listener from the unit's ListenStream= spec if ever found missing.

20.10 Operational Notes

is-ctl list-sockets shows every socket unit's bind address, backlog depth, and whether its associated service is currently Active (warm) or not (cold, awaiting next connection) — directly informs capacity planning for lazily-activated services.

21. Phase 9 — Targets & Boot Sequencing

21.1 Objectives

Implement is-target: the runlevel-equivalent synchronization-point unit kind (Target), boot-sequence composition (multi-user.target, graphical.target, etc.), and the default-target selection mechanism.

21.2 Detailed Implementation Steps

A Target unit has no ExecStart= and no process of its own — it exists purely as a Wants=/Requires= aggregation point in the dependency graph (MM1: "a unit is a promise, not a process," made concrete). The boot sequence is expressed as a chain of targets: basic.target (Wants= core filesystem and early-boot units) → multi-user.target (Wants= basic.target plus all user-facing services, After=basic.target) → optionally graphical.target (Wants=multi-user.target, adds a display-manager service). PID 1's boot sequence is simply "compute and commit a transaction (§15) for the configured default target" — no separate boot-specific code path exists (P3 applies uniformly to boot and to a later isolate request). is-ctl isolate <target> issues a transaction that both activates the new target's closure and deactivates any currently-Active unit not in that closure (a "switch runlevel" operation), reusing the same transitive-closure-plus-batch machinery as any other transaction.

21.3 Deliverable

is-target's target-unit handling integrated into is-graph/is-txn, plus is-ctl isolate, covered by the target conformance bucket.

21.4 Acceptance Criteria

Default-target boot (20-unit reference multi-user.target closure) completes within the §4 boot-time budget; is-ctl isolate rescue.target correctly deactivates every unit outside the rescue closure within the default DefaultTimeoutStopSec (10 s, §4); the target bucket's 12 fixtures pass.

21.5 Conformance Fixtures

fixtures/target/multi-user-closure.units — a 20-unit reference boot graph; expected batch plan matches a recorded golden trace. fixtures/target/isolate- rescue.units — expected: every non-rescue unit transitions to Deactivating then Inactive within the timeout budget.

21.6 Pitfalls

  • Giving a Target unit an ExecStart= (a modeling error — targets are pure synchronization points, MM1; if a caller needs a process, that belongs in a Service unit Wants=d by the target).
  • Implementing isolate as a special-cased code path instead of a transaction that both activates and deactivates — duplicates the ordering logic already proven correct in §15/§16 and risks divergent bugs between "boot" and "isolate."

21.7 Performance Concerns

Target aggregation adds no runtime cost beyond ordinary graph edges — the multi-user.target closure computation is identical in cost profile to any other transitive-closure BFS (§15.7).

21.8 Edge Cases

A default target that itself is missing or fails to load (falls back to rescue.target, a minimal single-shell target, logged as a boot-time degradation, not a silent failure); a target cycle (a.target Wants=b.target, b.target Wants=a.target with no other units) — caught by the same I1 cycle check as any other unit, since targets participate in the ordinary graph.

21.9 Failure Analysis

A unit that is Required= by the boot-critical-path target and fails during boot halts forward progress on that path (I4); is-ctl status --boot surfaces the exact stalled unit and its failure reason, distinguishing a boot-blocking failure from a merely Wants=-level failure that boot proceeds past.

21.10 Operational Notes

/etc/is-init/default.target (a symlink, mirroring the systemd convention) sets the default boot target; changing it takes effect on next boot only, never retroactively re-triggering the current session's target (an explicit isolate is required for that).

22. Phase 10 — Journald-Style Logging

22.1 Objectives

Implement is-journal: per-unit structured log capture from stdout/stderr, stored in a crash-consistent binary indexed format (I9, ADR-06, P12).

22.2 Detailed Implementation Steps

Every supervised process's stdout/stderr are redirected to a pipe owned by is-journal rather than inherited directly (P12: structured capture from the first byte, not a later best-effort scrape). Each captured line is wrapped into a JournalEntry (§11: unit, ts_realtime [CLOCK_REALTIME, ADR-19], a priority guessed from stream (stdout → info, stderr → err) unless the process uses the structured sd_notify-adjacent logging protocol to set an explicit priority) and appended to a length-prefixed binary segment file with a separate sparse index (unit name + timestamp → byte offset), enabling journalctl-equivalent filtered queries without a full scan. Durability: a background task calls fsync on the active segment at least every FlushIntervalSec (default 5 s, I9's ceiling) and immediately (synchronous, O_DSYNC) for any entry at crit priority or above, trading throughput for guaranteed durability exactly where it matters. Corruption recovery: on startup, if the index's last recorded offset does not match the segment file's actual tail (a crash mid-write), is-journal re-scans the raw segment forward from the last known-good offset and rebuilds the index tail, discarding only the torn/partial final record.

22.3 Deliverable

is-journal::append(JournalEntry) -> Result<(), InitError> plus the journalctl-equivalent is-ctl logs <unit> query path, covered by the journal conformance bucket.

22.4 Acceptance Criteria

Sustained write throughput ≥ 100,000 entries/sec, burst ≥ 250,000/sec (§4); journal_fsync_lag_seconds never exceeds 5 s (I9) across a 1-hour soak; corruption-recovery fixture recovers 100% of entries preceding a simulated mid-write crash and correctly discards the torn final record.

22.5 Conformance Fixtures

fixtures/journal/crash-mid-write.bin — a segment file with a deliberately truncated final record — expected: recovery discards exactly that record, retains all prior entries intact. fixtures/journal/high-priority-sync.service — emits a crit-priority entry — expected: fsync observed synchronously before append returns, not batched.

22.6 Pitfalls

  • Batching all priorities identically — a crit entry sitting in an unfsynced buffer defeats the entire point of structured crash-forensics logging (I9's distinction exists specifically to prevent this).
  • An unbounded index growth without periodic compaction — left as an operational rotation policy (§26), not a Phase-10 correctness bug, but must be documented so it isn't mistaken for a leak.

22.7 Performance Concerns

zstd compression per segment-batch keeps storage amplification at ≤ 1.3× raw bytes (§4); compression is applied only to sealed (rotated) segments, never the actively-written one, so it never sits on the append hot path.

22.8 Edge Cases

A unit producing output faster than 250,000 entries/sec burst capacity (entries queue in a bounded buffer; once full, is-journal drops the oldest queued entry and increments a journal_drop_total counter — an explicit, measured degradation, never an unbounded memory grow); a unit with no output at all (no journal entries, not an error); binary (non-UTF-8) output on stdout (stored as a base64-encoded field value, not silently mangled).

22.9 Failure Analysis

A journal corruption event (detected via the index/segment-tail mismatch, 22.2) triggers the recovery scan automatically on next is-journal startup — no operator action required for the common case; a segment file corrupted beyond the recoverable tail (mid-file, not just the final record) is quarantined and flagged via is-ctl status --journal for manual forensic inspection rather than silently discarded in bulk.

22.10 Operational Notes

is-ctl logs <unit> --since <time> --priority <p> is the primary operator query surface; journal rotation policy (segment size/age ceilings) and vacuum commands are documented in §26/§27, not re-derived per-deployment.

23. Phase 11 — Graceful Shutdown & System Transitions

23.1 Objectives

Implement is-shutdown: reboot/poweroff/kexec transitions driven by the same transaction machinery as activation, run in reverse dependency order (I13, P14).

23.2 Detailed Implementation Steps

A shutdown request (is-ctl poweroff, or a signal from the kernel on a power-button event) triggers is-shutdown to build a transaction (P3, §15's is-txn machinery reused, not reimplemented) targeting "deactivate everything" — computed as the reverse-edge transitive closure over every currently-Active unit, batched by the inverse of the ordering subgraph used at activation (a unit that was After= another at startup is now stopped before it, per I13, since its dependency must remain available until the dependent has finished). Each unit in a shutdown batch receives SIGTERM first; is-shutdown waits up to that unit's TimeoutStopSec (default from §4's 10 s budget) for a clean exit, then escalates to SIGKILL for stragglers — this per-unit timeout-then-escalate logic is identical in shape to the activation timeout logic in §16, reused rather than reimplemented. Once every unit is Inactive, PID 1 itself performs the final kernel transition (reboot(RB_AUTOBOOT) / reboot(RB_POWER_OFF) / kexec_load+reboot (RB_KEXEC)), the one point in the system where PID 1's own process, not a supervised child, is the actor.

23.3 Deliverable

is-shutdown's reverse-transaction builder plus the escalation timer, covered by the shutdown conformance bucket.

23.4 Acceptance Criteria

A 20-unit reference shutdown completes within the aggregate TimeoutStopSec budget for the longest-timeout unit on the critical path, not the sum of all units' timeouts (parallel escalation, mirroring §16's parallel activation); the shutdown bucket's 14 fixtures pass, including 2 asserting SIGKILL-escalation timing to within 100 ms of the configured timeout.

23.5 Conformance Fixtures

fixtures/shutdown/reverse-order.units — the §8.4 three-unit chain in reverse; expected stop order [web.service, db.service, local-fs.target], exactly inverted from the activation order. fixtures/shutdown/hung-stop.service (ExecStop= ignores SIGTERM) — expected: SIGKILL issued exactly at TimeoutStopSec, not before and not more than 100 ms after.

23.6 Pitfalls

  • Implementing shutdown as an unconditional "SIGTERM everyone, sleep, SIGKILL survivors" loop with no dependency awareness — violates I13/P14 by letting a dependency (e.g. a database) be torn down before its dependents have finished flushing to it.
  • Failing to bound the total shutdown wall-clock time — a chain of units each individually within their own TimeoutStopSec but serialized unnecessarily can blow past an operator's expected reboot time; batches must escalate in parallel per round, mirroring §16.

23.7 Performance Concerns

Shutdown wall-clock time is bounded by the longest per-unit TimeoutStopSec on the critical path through the reverse graph, not the unit count — the same parallel-batch reasoning as boot (§16.7), applied in reverse.

23.8 Edge Cases

A unit already Failed at shutdown-request time (skipped — nothing to stop); a shutdown request arriving while a daemon-reload (I11) or another transaction is mid-commit (queued behind the in-flight transaction's completion, never interleaved with it, preserving I6/I13 for both); a kexec target image that fails to load (falls back to a normal reboot(RB_AUTOBOOT), logged as a degradation, not a silent no-op).

23.9 Failure Analysis

A unit that never responds to SIGTERM and resists SIGKILL (a kernel-stuck process, e.g. blocked on uninterruptible I/O) is the one shutdown scenario this design cannot fully bound — is-shutdown proceeds with the rest of the transaction and logs the stuck PID explicitly rather than hanging the entire reboot indefinitely, trading "a fully clean shutdown" for "a bounded, forensic one" (documented tradeoff, not a silent gap).

23.10 Operational Notes

is-ctl status --shutdown (available up until the final kernel transition) shows in-flight stop batches and any escalated-to-SIGKILL units; the journal (§22) captures the full shutdown sequence up until the moment the journal process itself is torn down, at which point the kernel console becomes the sole remaining log target (mirroring ADR-09's early-boot symmetry).

26. Operational Readiness

Metrics. Every counter/gauge/histogram named in §7 (Invariants), §24 (Threat Model), and §25 (Failure Modes) is exposed via the Prometheus textfile exporter (ADR-10). Tracing. Each transaction (§15) carries a txn_id propagated through every log line and metric label touching its batches, enabling end-to-end boot/reload/shutdown tracing without a separate tracing library. Structured logging. All init-internal diagnostics (distinct from per-unit journal entries, §22) follow the same JournalEntry schema (§11), queryable identically. Dashboards. A reference Grafana dashboard (checked into docs/performance/) plots boot-time-by-round (§16.10), restart-rate-by-unit (§17.10), and journal-fsync-lag (I9) as the three primary always-on panels. Alerting philosophy. Alert on invariant violations (any invariant_violation metric > 0) and on the Failure Modes table's detection signals directly — never on a derived "looks unhealthy" heuristic; every alert names the exact I#/FM-# it corresponds to. SLOs: boot-to-default-target p99 ≤ 3.5 s (§4); zero invariant violations per host-day; journal-fsync-lag p99 ≤ 5 s. Incident response: the runbooks below are the first response artifact; each maps directly to a Failure Modes row. Named runbooks (full text in docs/runbooks/):

  • Service won't start — maps to FM-1/FM-2; check is-ctl status, is-ctl logs, is-ctl cat <unit>, verify ExecStart= path and dependencies.
  • Zombie processes accumulating — maps to FM-3; check reap_batch_size, identify the reactor-starving event source.
  • OOM in a cgroup — maps to FM-4/FM-5; check memory.events, verify subtree_control delegation, raise MemoryMax= or fix the leak.
  • cgroup limits not enforced — maps to FM-5; verify parent delegation, re-run daemon-reload.

Backup/restore: unit-file directories are backed up via ordinary filesystem snapshotting (no init-specific backup mechanism — units are declarative text, §8.1); the journal's binary store is backed up as a directory of immutable sealed segments plus the one active segment. Deployment topology: one PID 1 instance per host, optional per-user is-init --user instances sharing the same crate but a distinct control-bus socket path ($XDG_RUNTIME_DIR/ is-bus.sock). Canary/rolling-upgrade/rollback: a new PID 1 binary is staged alongside the running one and takes effect only on next reboot (PID 1 cannot be hot-swapped mid-session without kexec-based re-exec, which is documented as an advanced, opt-in operational procedure, not a default rollout mechanism); rollback is "boot the previous kernel/initramfs image," identical in shape to a kernel rollback.

27. Compatibility & Versioning

Wire compatibility (control bus): the is-bus message framing (§20.2) is versioned per SemVer (ADR-17); a 2-major-version compatibility window means is-ctl from version N can talk to an is-bus from N-1 or N-2. Storage compatibility (journal): the binary segment format (§22.2, ADR-06) embeds a format-version byte in its header; is-journal refuses to append to a segment from a newer major format than it understands, and reads (but does not write) segments from the prior major format during a migration window. Schema evolution (unit files): new directives are additive-only within a minor version (P1's "unknown key is a warning, not fatal" discipline, §13.2, is the mechanism that makes this safe); a directive removal requires a major-version bump and a documented deprecation cycle. API stability: the is-core types (§11) are the one surface every other crate depends on; a breaking change there requires bumping every dependent crate's major version in lockstep (a workspace-wide version, not per-crate independent versioning). Migration: is-ctl migrate-units --from systemd (a Phase-13-and-beyond tooling concern, not part of the 8–14 phase count above, documented here for completeness) reads existing systemd.unit(5)-format files directly, since ADR-02 chose format compatibility specifically to make this migration path near-zero-cost. Deprecation policy: any deprecated directive or bus method logs a deprecated_usage_total{name} metric for two full minor versions before removal in the next major version. Rolling-upgrade guarantees: because PID 1 itself cannot be hot-swapped (§26), "rolling upgrade" in this system means per-host reboot-at-a-time, coordinated by tooling outside this project's scope (a fleet orchestrator), not by is-init itself.

28. Testing & Verification Strategy

Unit tests: per-crate, covering pure functions (is-parser::parse_unit, is-graph::detect_cycles) directly. Integration tests: conformance buckets (§10's conformance/buckets/) exercise crate boundaries end-to-end (e.g. parse → graph → transaction → activation) against named fixtures. Property-based testing: proptest (ADR-11) generates random valid unit graphs and asserts I1/I4/I6 hold after every generated transaction. Differential testing: the differential-systemd bucket runs a curated unit set through both this project and a reference systemd instance (in a container), diffing activation order and final unit states — divergences are either fixed or documented as an ADR (§9's ADR-04 lineage note is one such documented divergence). Fuzzing: cargo-fuzz targets parse_unit and the transaction-replay path (ADR-12, crates/is-fuzz/), run continuously in CI and for a 24-hour soak before any release tag. Chaos/fault injection: is-verifier's simulator (§7) injects out-of-order SIGCHLD delivery, mid-transaction daemon-reloads, and simulated OOM events, asserting every I# after each. Deterministic replay: every recorded transaction log (§15.10) can be replayed byte-for-byte against is-verifier's mock clock/process-table, making a production incident reproducible offline. Soak testing: a 30-day continuous-fuzz canary (Phase 13+/deferred automation, PhaseDeferred("§29"), §37) runs the full parser+ transaction+supervisor stack under synthetic churn. Performance-regression gating: every M# target in §30 is checked in CI against the criterion benchmark suite (is-bench); a regression beyond 10% of the recorded baseline fails the build. Every fixture in every bucket is tied back to at least one I# invariant or one phase's N.5 (Conformance Fixtures) entry — no fixture exists without a named correctness or performance claim it defends.

29. Build & Release Engineering

Reproducible builds: a locked Cargo.lock (ADR-18), pinned Rust toolchain version (rust-toolchain.toml), and deterministic build timestamps (SOURCE_ DATE_EPOCH) make the PID 1 binary bit-for-bit reproducible from source. Artifact signing: release binaries are signed (minisign or equivalent) and the signature published alongside the SHA-256 checksum. SBOM: a CycloneDX-format software bill of materials is generated per release from the cargo-vet-audited dependency graph (ADR-22), listing every crate and its license (cross-checked against ADR-21). Release channels: stable (SemVer-tagged, 2-major-version compat window per ADR-17) and nightly (main-branch CI builds, no compat guarantee). CI/CD topology: GitHub Actions matrix (ADR-13) runs unit+integration+property+differential tests on every PR; the QEMU-boot smoke test (§12) gates merge to main; the 24-hour fuzz soak and the criterion benchmark suite run on a nightly schedule, not per-PR (cost/latency tradeoff). Version stamping: the compiled binary embeds its exact git commit SHA and build timestamp, queryable via is-ctl version. Provenance/attestation: CI produces a SLSA-style provenance attestation binding the released binary to the exact source commit and build environment. Dependency auditing: cargo audit (CVE database) and cargo vet (manual review attestation, ADR-22) both gate every release; a finding in either blocks the release until resolved or explicitly (and visibly) waived with a documented reason.

30. Performance Engineering

Benchmarking/profiling methodology: criterion (is-bench) micro-benchmarks each hot path (parse, graph-build, transaction-plan, cgroup-create) in isolation; perf record/flamegraph profiling runs against the QEMU-boot smoke test to attribute wall-clock boot time to specific phases (§16.10's round-timing telemetry is the production-facing analog of this same methodology). Allocation analysis: is-parser and is-graph are profiled under valgrind --tool=massif to bound transient allocation during a 500-unit boot (§13.7's 5 MB ceiling). Lock contention: the single-reactor design (ADR-05) eliminates most lock contention by construction; the one shared structure requiring synchronization — the StartLimitBurst window counter (§17.7) — is analyzed specifically for atomic-CAS contention under a synthetic restart-storm benchmark. Cache/syscall analysis: strace -c profiling of the boot sequence quantifies syscall count per unit activation (fork, execve, the cgroupfs writes) against the §4 latency budgets. Tail- latency analysis: every p99 target below is measured, not just p50 — tail latency in the restart path (I8) and the cgroup-create path (I12) are the two hottest tail-latency risks, both directly load-bearing for boot-time SLOs.

31. Scalability Analysis

What stays constant: per-unit fork+exec cost (M5), per-unit cgroup create+enter cost (M7), and control-bus RTT (§4) — none of these scale with total unit count. What grows: dependency-graph build/sort cost, O(V log V) dominated by the sort step (§14.7); transitive-closure computation, O(V+E); journal index size, linear in total logged entries. Named bottlenecks in order: (1) graph rebuild on daemon-reload at high unit count (§34 Capacity Model item 5 shows this is the first constraint to bite past the 500-unit reference class); (2) cgroup creation latency if ever serialized instead of batch-parallelized (§34 item 7, structurally avoided by §16's design, but the named risk if that design regresses); (3) FD budget for socket-heavy deployments (§34 item 3) before raw unit count becomes the limiting factor. Horizontal scaling: does not apply — PID 1 is inherently single-host; the unit of horizontal scale is hosts, not units-per-init, coordinated by tooling outside this project's scope (§27). Vertical scaling: more CPU cores widen the practical parallel-activation batch size (§16) but do not change the graph-build critical path, which is single-threaded by design (ADR-05). Sharding/partitioning: targets (§21) are the natural partition boundary for operators — a host running only basic.target plus a narrow service set never approaches the 500-unit reference class regardless of the full unit catalog's size. Coordination overhead: the round-boundary synchronization in §16 is the one point where parallelism pays a coordination cost; it is sub-millisecond relative to fork+exec cost (§16.7) and does not become the bottleneck at any scale documented here. Practical ceiling: ~2,048 units (§4's soft cap) before graph-rebuild latency on daemon-reload becomes operator-visible; the lever beyond it is reducing daemon-reload frequency (batching config changes) or, architecturally, partitioning the host into multiple init-managed scopes (deferred — see the microkernel-style Alternative Architecture, §36, rejected for this project but a real lever at a different scale regime).

32. Mental Models & First Principles

MM1 — "A unit is a promise, not a process." Predicts: units can be Active with no associated PID (targets, slices, RemainAfterExit= services). Bug class without it: assuming every unit has a meaningfully-set pid field. Applies in §11 (Core Schema, UnitState) and §21 Phase 9 (Target units).

MM2 — "The graph is data, the transaction is a plan, activation is execution — three distinct phases, never conflated." Predicts: validation errors surface before any process touches the kernel. Bug class without it: parse/graph errors that only surface at runtime because validation was skipped under time pressure. Applies in §8 Domain Model and §15 Phase 3.

MM3 — "PID 1 is an event loop wearing a supervisor costume." Predicts: everything routes through one epoll reactor; a blocking call anywhere stalls every subsystem, not just its caller. Bug class without it: spawning a blocking syscall directly on the reactor thread and wondering why unrelated units stop progressing. Applies in §17 Phase 5 and §18 Phase 6.

MM4 — "A cgroup is a lease, not a label." Predicts: cgroup membership must be established atomically with process creation, never applied after the fact. Bug class without it: a TOCTOU window where the new process allocates memory before its limit lands. Applies in §19 Phase 7, I12.

MM5 — "Signals are doorbells, not messages." Predicts: SIGCHLD tells you that something happened, never what — you always re-scan with waitpid. Bug class without it: trying to correlate one specific signal delivery to one specific child, which breaks the instant two children exit close together. Applies in §18 Phase 6, I5.

MM6 — "A socket unit is a promise redeemed lazily." Predicts: connection accept can precede process existence; a socket unit is "available" before it has forked anything. Bug class without it: assuming a socket-activated, Accept=no unit behaves like a live server the instant it reports Active. Applies in §20 Phase 8.

MM7 — "Restart policy is a control loop with a spring, not a switch." Predicts: naive immediate-restart-forever policies oscillate under a persistent failure. Bug class without it: no circuit breaker, so a bad deploy pins a CPU core indefinitely. Applies in §17 Phase 5, I8.

MM8 — "Boot order is a partial order, not a sequence." Predicts: two units with no path between them in the DAG have no guaranteed relative order and must never be written to depend on one existing anyway. Bug class without it: implicit ordering assumptions inherited from directory/alphabetical scan order (sysvinit's actual, historical failure mode). Applies in §14 Phase 2 and §36 Alternative Architectures.

34. Back-of-Envelope Capacity Model

  1. SIGCHLD-storm reactor ceiling = batch_size × loop_hz = 256 events/iteration (ADR-20) × ~5,000 Hz idle-loop rate (≈200 µs/epoll_wait cycle) ≈ 1,280,000 reaps/sec theoretical ceiling — real fork/waitpid overhead caps actual exit rate far below this, so the reactor itself is never the bottleneck (§18.7).
  2. Unit-graph RAM at max scale = 8,192 units × ~1.2 KiB per Unit+ Dependencies struct ≈ 9.8 MiB, plus 8,192 × ~200 B supervisor records ≈ 1.6 MiB — well within the 32 MiB PID 1 ceiling (§4) with headroom for journal write buffers.
  3. Socket-unit FD ceiling = hard_nofile ÷ fds_per_socket_unit = 4,096 ÷ 3 ≈ 1,365 concurrently listening socket units before FD exhaustion — below the 2,048 soft unit cap, meaning socket-heavy deployments hit the FD ceiling before the unit-count ceiling (the real practical limit for that workload shape, §31).
  4. Boot-time journal burst bandwidth = units × avg_line_bytes ÷ throughput = 2,048 × 200 B ÷ 100,000 entries/sec ≈ 4.1 ms to drain a full-boot logging burst — negligible against the 1.2 s p50 boot target (§4).
  5. Dependency-graph build time at the hard ceiling = nodes × per-node cost = 8,192 × 100 µs ≈ 819 ms — this alone would blow the 1.2 s p50 boot budget, which is exactly why §4's 500-node reference class, not 8,192, backs the p50 target; 8,192 is documented as a degraded-mode ceiling only.
  6. Journal storage growth at sustained max throughput = throughput × entry_size × amplification × seconds/day = 100,000 × 200 B × 1.3 × 86,400 ≈ 2.25 TB/day — the reason journal rotation/vacuuming policy (§26, §27) is mandatory, not optional, for any host run near this ceiling indefinitely.
  7. cgroup fan-out cost if serialized = units × per-unit cgroup latency = 8,192 × 5 ms ≈ 41 s of serialized cgroup setup — the concrete number motivating §16 Phase 4's decision to parallelize cgroup creation across a batch rather than the process-spawn step alone.
  8. Restart-storm blast-radius bound = burst × restart_latency = StartLimitBurst(5) × 80 ms p50 ≈ 400 ms of churn before a flapping unit enters Maintenance (I8) — bounding the CPU-pinning blast radius of a single bad deploy to under half a second before the circuit breaker trips.

36. Alternative Architectures (Roads Not Taken)

1. Retry-until-stable, event-driven (no static DAG).

 udev event ──▶ [job queue] ──▶ try-start job ──▶ fail? requeue with delay
                                        │
                                        └─ succeed ──▶ emit "started" event

Regime where it wins: hardware-event-driven boot (hot-plug devices arriving in unpredictable order) where a static dependency declaration is impossible to write correctly in advance. Real system: Upstart. Rejected here because a static service graph (this project's actual workload) has no such unpredictability, and retry-until-stable trades away the determinism P4/P13 depend on for no corresponding benefit in this regime.

2. Dependency-free, supervision-only.

 /service/*/  ──▶ [runsvdir scans dir] ──▶ [runsv per entry, independent]

Regime where it wins: a minimal embedded image with a handful of services and no meaningful ordering requirements. Real system: runit. Rejected here because this project's target scope (hundreds of units, complex Requires=/After= graphs) needs exactly the ordering expressiveness this model omits.

3. Continuous reconciliation loop (desired-state vs. actual-state, not one-shot activation).

 ┌────────────┐   diff    ┌───────────┐   converge   ┌──────────────┐
 │ desired-state ├────────▶│ controller ├─────────────▶│ actual state │
 │   (units)     │◀────────┤   loop     │◀─────────────┤ (processes)  │
 └────────────┘  re-diff  └───────────┘   observe     └──────────────┘

Regime where it wins: containerized/cloud-native fleets where "keep converging toward desired state forever" is the right model because the desired state itself changes continuously (a kubelet-style control loop). Real system: Kubernetes' kubelet reconciling pod specs. Rejected here because a continuous reconciliation loop's inherent latency (poll-diff-converge cycles) is unsuitable for PID 1's boot-critical path (§4's sub-2-second p95 boot target), where one-shot transactional activation (§15) is both simpler to reason about and faster.

4. Micro-kernel-style init split into cooperating minimal daemons, no single privileged supervisor.

 [tiny root task] ──spawns──▶ [name-service daemon]
        │                            │
        └──spawns──▶ [supervisor daemon] ◀──queries── [policy daemon]

Regime where it wins: high-assurance, security-certified systems where minimizing the trusted computing base of any single component is the overriding goal, even at the cost of more inter-process coordination. Real system: seL4-based deployments following the root-task minimalism pattern. Rejected here because it fragments the single coherent unit graph and control-bus UX operators expect (§3's architectural overview), trading a unified operational model for a smaller-but-more-numerous trust boundary set — the wrong tradeoff for a general-purpose Linux distribution's init.

38. Glossary

  • Activation — the process of transitioning a unit from Inactive toward Active (§8.3).
  • After= / Before= — ordering relations between units (§8.2).
  • Backoff — the exponentially-increasing delay between restart attempts (§17.2).
  • BindsTo= — a strong requirement relation; the dependent stops if the dependency stops (§8.2).
  • Batch (round) — the set of units activated in parallel within one step of the topological sort (§15.2).
  • Bus (control bus) — the Unix-domain-socket protocol carrying operator commands (§20).
  • cgroup — a Linux control group; the resource-isolation and process-tracking primitive (§19).
  • cgroups v2 — the unified single-hierarchy cgroup model (ADR-03).
  • Conflicts= — a negative requirement; two conflicting units are never both Active (§8.2).
  • Controller (cgroup) — a resource-accounting/limiting subsystem (memory, cpu, io, pids) (§19.2).
  • Delegate= — a unit directive letting a service manage its own cgroup subtree (§19.2).
  • Drop-in — a layered unit-file config override (foo.service.d/*.conf) (§8.1).
  • Ephemeral (orphan) — a process reparented to PID 1 whose original parent exited (§18.2).
  • ExecStart= — the unit-file directive declaring the command to run (§8.1).
  • FD (file descriptor) — the kernel handle for an open resource; central to socket activation's FD-passing protocol (§20).
  • Fork+exec — the POSIX process-creation idiom clone3 (or fork) followed by execve (§17.2).
  • Isolate — an operation switching the active target, deactivating everything outside the new target's closure (§21.2).
  • Journal — the structured, crash-consistent log store (§22).
  • LISTEN_FDS — the environment variable protocol communicating inherited socket FD count to an activated service (§20.2).
  • Maintenance — the unit state entered after StartLimitBurst is exceeded, requiring operator reset (§8.3).
  • MemoryHigh= / MemoryMax= — the cgroup memory throttle threshold and hard limit, respectively (§19.2).
  • OnCalendar= — a cron-like timer specification (a Timer-unit directive, deferred detail beyond Phase 9's target scope).
  • Once semantics (idempotency) — the property that repeating a control-plane operation has no additional side effect (P11).
  • Orphan reaping — waitpid-ing a process whose original parent already exited (§18.2).
  • PID 1 — the first userspace process; the init; the ancestor of every other userspace process (§1).
  • Process group / session — the POSIX grouping mechanisms setsid() establishes for signal-delivery isolation (§17.2).
  • Reap — calling wait/waitpid on an exited child to release its zombie slot (§18).
  • Requires= — a strong requirement relation; the dependent fails if the dependency fails (§8.2).
  • RestartPolicy — the closed enum governing post-exit restart behavior (§11).
  • RestartSec= — the base backoff interval before a restart attempt (§17.2).
  • Round — see Batch.
  • Signalfd — the Linux facility delivering signals as readable file descriptor events instead of interrupting execution (§18.2).
  • SIGCHLD — the signal delivered to a parent on a child's state change (§18).
  • Slice — a cgroup-grouping unit kind aggregating related units' cgroups (§10, §19.2).
  • Socket activation — lazily starting a service upon a connection to its pre-created listening socket (§20).
  • StartLimitBurst / StartLimitIntervalSec — the circuit-breaker parameters bounding restart attempts within a time window (I8).
  • Target — a synchronization-point unit kind with no process of its own (§21.2).
  • Transaction — a planned, atomic set of activation/deactivation batches (§15).
  • UnitConfig — the parsed, typed representation of a unit file's directives (§11).
  • UnitName — the (name, kind) identity pair for a unit (§8.1).
  • UnitState — the six-state supervision FSM (§8.3).
  • Watchdog (WatchdogSec=) — a per-service heartbeat timeout enforcing liveness beyond mere process existence (§17.2).
  • Zombie — an exited process still occupying a process-table slot pending its parent's reap (§18).
