3. Architectural Overview

+------------------------------------------------------------+
|                 Surface Syntax Parser                      |
|        (lexer, recursive-descent, CST -> surface AST)      |
+------------------------------|-------------------------------+
                               v
+------------------------------------------------------------+
|              Elaborator  (UNTRUSTED, dtc-elab)              |
|  implicit-arg insertion | metavariables | HO unification    |
|  pattern-match elaboration -> case tree | inductive decls    |
+------------------------------|-------------------------------+
                               v   fully-elaborated core term
================================================================  <- de Bruijn criterion
                               v      (trust boundary)
+------------------------------------------------------------+
|                Trusted Kernel  (TRUSTED, dtc-kernel)         |
|  bidirectional checker (infer/check) | conversion checker    |
|  universe checker | inductive/eliminator well-formedness     |
+---------------+----------------------------+------------------+
                v                            v
+----------------------+        +--------------------------+
|   NbE Evaluator        |        |  Global Env / Signature |
|  eval: Term -> Value    |<------>|  decls, inductives,      |
|  quote: Value -> Normal|        |  eliminators, universes  |
+----------------------+        +--------------------------+
                ^
                | strict-positivity + eliminator generation
+------------------------------------------------------------+
|            Inductive-Definition Processor (dtc-inductive)    |
+------------------------------------------------------------+

Surface Syntax Parser. Converts UTF-8 source text into a surface AST; performs no semantic resolution, so a syntactically valid but meaningless program still parses (name resolution and elaboration happen downstream).

Elaborator. The untrusted heart of the system: inserts implicit arguments, allocates metavariables, generates and solves higher-order pattern-unification constraints (Miller 1991), and elaborates surface pattern matches into eliminator applications. Its output is a fully-elaborated core term with zero unsolved metavariables (I8).

Trusted Kernel. The trust boundary. Only the kernel may declare a term well-typed. It independently re-derives the type of every elaborator-produced term via the bidirectional infer/check judgements (§8), invoking the conversion checker whenever the typing rules require a definitional-equality check, and invoking the universe checker whenever a universe-formation rule applies.

NbE Evaluator. Computes definitional equality by evaluating core terms into a semantic domain of values with closures (eval) and reading values back into canonical beta-normal, eta-long syntax (quote). This is the engine both the kernel's conversion checker and the REPL's #eval command invoke.

Inductive-Definition Processor. Validates strict positivity of a proposed inductive declaration before it is registered in the global signature, and mechanically generates its eliminator/recursor and computation (iota) rules.

Global Env / Signature. The append-only registry of accepted declarations, inductive definitions, and generated eliminators that both the kernel and the NbE evaluator consult to resolve global references.

8. Domain Model

8.1 Core Syntax Grammar

Term  ::= Var(Ix)
        | Global(Name)
        | Lam(Name, Term)
        | App(Term, Term)
        | Pi(Name, Term, Term)
        | Sigma(Name, Term, Term)
        | Pair(Term, Term)
        | Proj1(Term) | Proj2(Term)
        | U(Lvl)
        | Ind(Name)              // inductive type former
        | Ctor(Name, [Term])     // constructor application
        | Elim(Name, Term, Motive, [Method], Term)  // eliminator application
        | Meta(MetaVar)          // elaborator-only, never in kernel input
        | Let(Name, Term, Term, Term)

Ix is a de Bruijn index (counts binders inward, term-local). Lvl is a universe level. Meta never occurs in a term handed to the kernel (I8).

8.2 Typing Judgements

Γ ⊢ t ⇒ A (infer: t synthesizes type A), Γ ⊢ t ⇐ A (check: t is checked against A), Γ ⊢ A ≡ B (definitional equality / conversion), Γ ⊢ (context well-formedness).

8.3 Typing Rules (selected, inference-rule form)

Rule Premises Conclusion
Var (x : A) ∈ Γ Γ ⊢ x ⇒ A
U-Formation Γ ⊢ Γ ⊢ Uᵢ ⇒ U_(i+1)
Pi-Formation Γ ⊢ A ⇐ Uᵢ and Γ, x:A ⊢ B ⇐ Uⱼ Γ ⊢ Π(x:A).B ⇒ U_(max i j)
Pi-Intro (Lam) Γ, x:A ⊢ t ⇐ B Γ ⊢ λx.t ⇐ Π(x:A).B
Pi-Elim (App) Γ ⊢ f ⇒ Π(x:A).B and Γ ⊢ a ⇐ A Γ ⊢ f a ⇒ B[a/x]
Sigma-Formation Γ ⊢ A ⇐ Uᵢ and Γ, x:A ⊢ B ⇐ Uⱼ Γ ⊢ Σ(x:A).B ⇒ U_(max i j)
Sigma-Intro (Pair) Γ ⊢ a ⇐ A and Γ ⊢ b ⇐ B[a/x] Γ ⊢ (a,b) ⇐ Σ(x:A).B
Sigma-Elim (Proj) Γ ⊢ p ⇒ Σ(x:A).B Γ ⊢ p.1 ⇒ A; Γ ⊢ p.2 ⇒ B[p.1/x]
Conversion Γ ⊢ t ⇒ A, Γ ⊢ A ≡ B, Γ ⊢ B ⇐ Uᵢ Γ ⊢ t ⇐ B
Cumulativity Γ ⊢ A ⇐ Uᵢ and i ≤ j Γ ⊢ A ⇐ Uⱼ

The Conversion rule is the one that ties typing to definitional equality: it is the reason a dependent checker must evaluate, not just parse, to decide typing.

8.4 Normalization by Evaluation — Named Steps

  1. eval(Term, Env) -> Value: recursively evaluate a term under an environment of values, building VLam/VPi/VSigma/VPair/VU/VNeutral values; a Lam becomes a VLam closing over its Env (a Closure), never substituting under the binder.
  2. apply(Value, Value) -> Value: eliminates a VLam by evaluating its body in the closure's environment extended with the argument (beta), or builds a VNeutral NApp if the head is neutral (stuck).
  3. quote(Value, Lvl) -> Term (readback): turns a value back into normal-form syntax at a given binder depth, eta-expanding VLam/VPair/VPi-typed neutrals so the result is eta-long as well as beta-normal.

Worked example: normalize (λx. x) y. eval produces apply(VLam(cl), VNeutral(NVar y)); applying the closure evaluates the body x in an environment where x ↦ VNeutral(NVar y), yielding VNeutral(NVar y). quote at depth 0 reads this back as the term y. Two syntactically different terms, (λx.x) y and y, both quote to y: they are definitionally equal.

8.5 Definitional Equality / Conversion Checking — Named Steps

  1. eval both sides in the current environment.
  2. quote both resulting values back to normal form (or, more efficiently, compare values structurally without a full quote — conv(Value, Value, Lvl) -> bool, which eta-expands functions/pairs on the fly rather than materializing the normal form; this is the algorithm actually implemented, §13/§15).
  3. Compare up to alpha (de Bruijn indices already make alpha-equivalence syntactic equality) and eta (function/pair eta handled by expansion during comparison, not as a separate rule).

Worked equal example: Γ ⊢ (λx. x) y ≡ y : A. Both sides evaluate to VNeutral(NVar y); conv returns true.

Worked rejection example: Γ ⊢ Π(x:Nat).Nat ≡ Σ(x:Nat).Nat. Both sides are already values in normal form; conv compares head constructors first (VPi vs VSigma) and rejects immediately — different head constructors can never be definitionally equal.

8.7 Bidirectional Typing — Infer vs. Check

Syntactic form Judgement Why
Var, Global infer type is looked up, never guessed
App infer function's type is inferred, then argument is checked against its domain
Proj1/Proj2 infer pair's type is inferred, projection type follows structurally
U(Lvl) infer its type is mechanically U(Lvl+1)
Lam check the domain type is not otherwise recoverable from a bare lambda
Pair check which Sigma it inhabits is not otherwise recoverable
Meta/hole check (elaborator-only) expected type seeds the metavariable's type
Let infer (bound term inferred, body checked/inferred in extended context) mixes both modes

8.8 Metavariables and Higher-Order Pattern Unification — Named Steps

  1. Meta creation: elaborating an implicit argument or a hole allocates a fresh MetaVar with a recorded expected type and the ambient context (spine of bound variables it may depend on).
  2. Constraint generation: each unification obligation Γ ⊢ t ≟ u becomes a Constraint::Equality entry; rigid-rigid constraints decompose structurally (matching head constructors and recursing on subterms).
  3. Flex-rigid: a constraint ?m spine ≟ t where the spine is a list of distinct bound variables (a Miller pattern, Miller 1991) solves by abstracting t over the spine and assigning ?m := λspine. t, after an occurs-check that ?m does not appear in t.
  4. Flex-flex / non-pattern spines: postponed to a deferred-constraint queue, retried as other metas resolve.
  5. Spine pruning: eliminates dependencies a meta's solution provably cannot use, shrinking future pattern-unification obligations.

Worked example: elaborating id x where id : (A:Type) -> A -> A and x : Nat. The elaborator inserts an implicit metavariable for A, producing id ?m x; checking x against ?m under the applied function's domain generates the constraint ?m ≟ Nat (a trivial pattern, empty spine), which solves immediately: ?m := Nat.

8.9 Inductive Families — Named Steps

  1. Declare: name, parameters, indices, a list of constructors each with argument types possibly recursively mentioning name.
  2. Strict-positivity scan: for every constructor argument type, name may occur only in strictly-positive position (never to the left of a function arrow an odd number of times, i.e. never in a position that would make name an argument to itself negatively) — see the negative-occurrence rejection example below.
  3. Eliminator generation: mechanically build a motive parameter (a family over the inductive), one method parameter per constructor (typed using the motive applied to that constructor's recursive subterms), and the resulting eliminator's type.
  4. Computation (iota) rule generation: for eliminator applied to a constructor application, the computation rule reduces it to the corresponding method applied to the constructor's arguments (and their recursive eliminations).

8.10 Dependent Pattern-Match Elaboration

  1. Build a case tree from surface match clauses, splitting on the first scrutinee whose constructors are not yet distinguished.
  2. Coverage check: at each split, confirm every constructor of the scrutinee's inductive type has a clause (or is provably impossible by unification of indices).
  3. Termination check: confirm each recursive call is on a structurally smaller argument (or defer via PhaseDeferred to size-change termination, §22).
  4. Elaborate the checked case tree into nested eliminator applications against the generated recursor (§8.9).

8.11 End-to-End Worked Example — Length-Indexed Vector append

Vec : (A : Type) -> Nat -> Type
  nil  : Vec A zero
  cons : (n:Nat) -> A -> Vec A n -> Vec A (succ n)

append : (A:Type) -> (n m : Nat) -> Vec A n -> Vec A m -> Vec A (plus n m)
append A n m nil         ys = ys
append A n m (cons k x xs) ys = cons (plus k m) x (append A k m xs ys)

Elaboration: append's surface match splits on the fourth explicit argument (Vec A n); coverage requires both nil and cons clauses (present); the recursive call append A k m xs ys is structurally smaller in the fourth argument (xs vs. cons k x xs), satisfying termination. The elaborated core term is a single Elim(Vec, ..., motive=λn._.Vec A (plus n m), methods=[ys; λk x xs ih. cons (plus k m) x ih], scrutinee). The kernel independently infers this eliminator's type and checks it convertible to the declared return type Vec A (plus n m) — this is where the plus n m vs. plus (succ k) m index computation is settled by NbE, not by syntax.

8.12 Malformed / Hard Examples

  • Universe-inconsistent: Type_i : Type_i — rejected by I3 (Girard's paradox).
  • Non-positive inductive: Bad : Type with mk : ((Bad -> Nat) -> Bad) -> Bad — Bad occurs negatively (to the left of one function arrow, an odd number of times, inside the outer argument type) — rejected by I4.
  • Non-covering match: a Vec match with only a nil clause — rejected by I5 (coverage).
  • Non-terminating recursion: loop : Nat -> Nat; loop n = loop n with no decreasing argument — rejected by I5 (termination).
  • Unification failure: ?m ≟ f x where f x is not a Miller pattern (a non-variable spine) and no rigid structure lets the constraint decompose — postponed, then reported as UnificationFailure if never solved by end of elaboration.
  • Ill-typed kernel input: App(Lam(...), ...) where the argument's inferred type does not convert to the lambda's expected domain — rejected by the Pi-Elim rule's premise failing, independent of whatever the elaborator believed.

8.13 Failure-Path Example

Given f : Nat -> Nat := λx. x true (applying a Nat to a Bool literal): inference of x yields Nat; Nat is not a Pi type, so Pi-Elim's premise Γ ⊢ f ⇒ Π(x:A).B fails at the head — the kernel rejects with a structured NotAFunctionType diagnostic carrying the inferred head type and the source span, before any conversion check is attempted.
