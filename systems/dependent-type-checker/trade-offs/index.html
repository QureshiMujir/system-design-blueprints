ADR-01

Implementation language

Chosen

Rust

Rejected

Haskell, OCaml, C++

When the rejected choice is right

a pure research prototype valuing terseness over auditability (OCaml wins there)

Why: ownership-enforced trust boundary, no GC noise in cost model

ADR-02

Variable representation

Chosen

de Bruijn indices (syntax) + de Bruijn levels (semantic values)

Rejected

named vars, locally-nameless

When the rejected choice is right

a pedagogical checker prioritizing readable error messages over performance (named vars win there)

Why: indices avoid alpha-renaming bugs; levels make NbE closures well-defined without shifting

ADR-03

Evaluation strategy

Chosen

NbE (eval to values, quote back)

Rejected

naive substitution, an abstract reduction machine

When the rejected choice is right

a checker for a terminating-by-construction total language with tiny terms (naive substitution is adequate at that scale)

Why: avoids substitution's exponential blowup; canonical normal forms make conversion decidable

ADR-04

Value representation

Chosen

closures over an environment

Rejected

full substitution at each step

When the rejected choice is right

an interpreter for a language with no binders under evaluation (substitution is fine there)

Why: O(1) binder capture instead of O(n) substitution per reduction

ADR-05

Conversion algorithm

Chosen

NbE-based value comparison with eta-expansion-on-demand

Rejected

untyped reduction to normal form, typed conversion

When the rejected choice is right

a system needing normal forms as first-class artifacts for display (materializing them wins there)

Why: avoids materializing full normal forms for large terms; terminates by construction on well-typed input

ADR-06

Universe handling

Chosen

predicative, cumulative Type_0 : Type_1 : ...

Rejected

impredicative Prop, full universe polymorphism

When the rejected choice is right

a system targeting classical-logic proof irrelevance at scale (impredicative Prop wins there — deferred, §37)

Why: simplest paradox-free hierarchy sufficient for Phase 0 scope

ADR-07

Kernel/elaborator split

Chosen

separate trusted kernel crate re-checking all elaborator output

Rejected

single integrated checker (Agda-style)

When the rejected choice is right

a small closed research prototype where the same person owns both and formal audit is unnecessary (integrated wins there)

Why: de Bruijn criterion: bugs in a large elaborator become rejections, not unsoundness

ADR-08

Kernel size target

Chosen

≤ 3,000 LOC, audited

Rejected

no explicit size budget

When the rejected choice is right

a kernel that must support many theory extensions natively (Coq's larger kernel wins there)

Why: keeps the "small trusted base" claim falsifiable and reviewable

ADR-09

Metavariable/unification design

Chosen

Miller higher-order pattern unification with postponement

Rejected

full higher-order unification (undecidable in general), first-order-only unification

When the rejected choice is right

a system needing full unification for e.g. an equation compiler with non-pattern metas as a common case (postponement queue depth wins there instead)

Why: pattern unification is decidable and covers the overwhelming majority of real implicit-argument cases

ADR-10

Implicit-argument strategy

Chosen

eager insertion at application sites with metavariable placeholders

Rejected

fully explicit surface syntax, elaboration-time-only insertion without metas

When the rejected choice is right

a minimal teaching core valuing explicitness over ergonomics (fully explicit wins there)

Why: matches surface ergonomics of Agda/Lean while keeping insertion mechanical

ADR-11

Inductive-type mechanism

Rejected

When the rejected choice is right

a metatheoretically minimal core valuing a tiny rule count over ergonomics (W-types win there)

Why: matches how real systems (Lean, Agda, Coq) present inductives; avoids W-type encoding overhead in every proof

ADR-12

Positivity-checking method

ADR-16

Surface-syntax design

Chosen

Rejected

ADR-17

Normal-form caching/memoization

Chosen

Rejected

When the rejected choice is right

a system where signatures never change during a checking session and memory is unconstrained (unconditional caching wins there)

Why: bounds repeated conversion cost while keeping the cache key sound (P11)

ADR-18

De-Bruijn-criterion adherence

Chosen

kernel API exposes no "trusted load" or "skip re-check" entrypoint

Rejected

an escape hatch for "known-good" cached terms

When the rejected choice is right

A non-foundational dependently-typed language used only for programming, never for proving — where logical soundness is not a goal and a trusted-load fast path buys startup latency (early-Idris Type:Type-style pragmatism) — this is the one place the project holds a hard line; no real regime should reintroduce a bypass

Why: any bypass is an alternate trust path and defeats the criterion (I7)

ADR-19

Caching soundness argument

Chosen

cache key includes context fingerprint + universe assignment + signature version

Rejected

cache key on term structure only

When the rejected choice is right

a closed-term-only cache with no free variables and a frozen signature (term-only key is sound there)

Why: a term's normal form depends on more than its own syntax; omitting context/signature from the key is unsound (T5)

Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Conversion via Untyped Reduction to Normal Form (instead of NbE)

Term -> [untyped beta/iota reduction to normal form] -> compare syntactically (mod alpha)

Winning regime: a system where terms are guaranteed small and shallow by construction (no deep eliminator nesting), where materializing full normal forms is cheap. Real embodying system: early Coq kernel generations and simpler pedagogical checkers using plain reduction-to-normal-form rather than NbE. Why rejected here: untyped reduction to full normal form is harder to reason about for termination (no closure-based sharing argument, §34) and does not naturally support the eta-expansion-on-demand optimization NbE's value-level comparison gets for free (§15, §30) — this project needs the performance headroom for the eliminator-heavy Phase 8-10 workloads.

No-Separate-Kernel Design (Agda-style)

Surface -> Elaborator+Checker (single trust boundary, no independent re-check)

Winning regime: a long-lived, extensively-tested single implementation where the elaborator's own correctness has been validated over years by a large user base (substituting empirical confidence for structural guarantee). Real embodying system: Agda. Why rejected here: this project explicitly wants the de Bruijn criterion's structural soundness argument (P1, I1) rather than relying on accumulated empirical confidence, and a from-scratch project has none of that accumulated confidence to lean on yet.

Eliminator-Only / W-Type-Based Core (no native pattern matching)

Core = { Pi, Sigma, U, W (well-founded trees) }  // all inductives encoded via W-types
Surface pattern matches -> encode into W-elimination, no native Ctor/Ind/Elim forms

Winning regime: a metatheoretically minimal core valuing a small, uniform rule count over ergonomics — useful for metatheory papers proving properties about "the" core calculus. Real embodying system: this is the Coq-vs-Agda axis in miniature — Coq's kernel is closer to a small-rule-count core with inductives as a schema on top, while richer native-inductive-family systems (Agda) trade rule-count minimality for ergonomics. Why rejected here: W-type encoding of Vec-style indexed families is substantially more awkward to elaborate and to generate readable diagnostics for than native inductive families (ADR-11), and this project's god-bar target explicitly includes a real Vec/append worked example (§8.11) that benefits from native inductives' directness.

Proof-Assistant-with-Tactics Architecture (checking as one service under an interactive tactic engine)

+----------------------------------------------------+
|         Interactive Tactic Engine / REPL             |
|   (proof state, tactic combinators, backtracking)    |
+---------------------|--------------------------------+
                       v
              [ this project's kernel+elaborator, as one checking service ]

Winning regime: an interactive theorem-proving workflow where most user effort is spent inside partial proof states, not authoring complete terms up front. Real embodying system: Coq (Ltac/Ltac2), Lean 4's tactic framework. Why rejected here: Phase 0's scope is explicitly a batch checker (§1) — tactics are PhaseDeferred("Phase 13 — tactic engine") precisely because a tactic engine is a large, separable concern that should sit on top of a stable checked-term-producing core, not be built concurrently with it.
