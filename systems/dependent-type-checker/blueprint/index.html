239 — Dependent Type Checker

Project Number: 239

Project Name: Dependent Type Checker

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Dependent Type Checker (project 239) builds, from scratch in Rust, a dependently-typed language front end and a small trusted kernel implementing a Martin-Löf-style dependent type theory extended with a Calculus-of-Constructions-flavored universe hierarchy (the theory is stated precisely below). The system is split, by design, into two trust domains: a large, complex, untrusted elaborator that turns human-writable surface syntax into a fully-elaborated core term (resolving implicit arguments, allocating metavariables, solving higher-order pattern-unification constraints), and a small, simple, trusted kernel that independently re-checks every core term the elaborator produces against the primitive typing rules of the theory (Pi/Sigma formation, universe formation, inductive-family formation, the conversion rule) — the de Bruijn criterion. Definitional equality, the load-bearing judgement of any dependent checker, is decided by normalization by evaluation (NbE): terms are evaluated into a semantic domain of values with closures, then read back ("quoted") into canonical beta-normal, eta-long normal forms; two terms are definitionally equal iff their normal forms are alpha-equivalent. The system boundary stops at a checked, fully-elaborated core term plus its inferred/checked type — it does not lower to any intermediate representation for execution, does not generate native code, and does not provide an optimizing runtime for checked programs (the only execution the system performs is the same NbE evaluator used for conversion, invoked interactively for a REPL's #eval).

Phase-0 deliverable, as a numbered crate list:

  1. dtc-syntax — surface syntax AST and parser.
  2. dtc-core — core term representation (Term/Value/Neutral/Normal).
  3. dtc-nbe — the NbE evaluator (eval and quote).
  4. dtc-kernel — trusted kernel: bidirectional type checker, conversion checker, universe checker.
  5. dtc-elab — untrusted elaborator: metavariables, higher-order unification, implicit inference.
  6. dtc-inductive — inductive-family processor: strict-positivity checking, eliminator generation.
  7. dtc-pattern — pattern-match elaboration, coverage checking, termination checking.
  8. dtc-diagnostics — structured type-error reporting.
  9. dtc-cli — REPL / batch checker CLI.
  10. dtc-conformance — differential/conformance test harness.

Boundaries. Provides: surface parsing, elaboration (implicit-argument insertion, metavariables, unification), a trusted kernel, NbE-based conversion checking, universe consistency checking, inductive families with positivity checking and eliminator generation, dependent pattern matching with coverage/termination checking, and a checked core term plus its type as the final artifact. Delegates / does NOT provide: no native code generation, no optimizing execution runtime for checked programs, no tactic language or proof automation in Phase 0, no SMT integration, no IDE beyond a batch CLI/REPL. The boundary stops before code generation: this project type-checks and elaborates, it does not compile.

Non-goals — the Type-Checker-42 contrast, stated explicitly: Type Checker (project 42) checks a simply-typed / Hindley-Milner language, where types and terms are different syntactic categories and type checking never requires evaluating the program under check; there is no universe hierarchy, no conversion checker, and no kernel/elaborator trust split, because a single checker suffices when types do not depend on values. This project adds three things a simply-typed checker structurally does not need: (1) definitional equality via NbE, because dependent types can contain terms (e.g. Vec A n), so checking type equality requires evaluating those terms, not just comparing syntax; (2) universe consistency checking, because types-of-types form an infinite hierarchy that must itself be checked for paradox (Girard's paradox, the Type : Type inconsistency); (3) a trusted-kernel/untrusted-elaborator split, because implicit-argument inference and higher-order unification are complex enough that the elaborator must be allowed to be wrong, provided a small independent kernel re-verifies every result (the de Bruijn criterion). This project is also not a full proof assistant with a tactic language in Phase 0 (PhaseDeferred("Phase 13 — tactic engine")), not a compiler backend, and not general theorem-proving automation (no SMT, no proof search).

Type theory, stated precisely: a Martin-Löf-style intensional dependent type theory with a predicative, cumulative universe hierarchy Type_0 : Type_1 : Type_2 : ... (no impredicative Prop in Phase 0 — PhaseDeferred("Phase 12 — impredicative Prop / proof-irrelevant universe")), Pi types (dependent functions), Sigma types (dependent pairs), and one native inductive-family mechanism (native inductive declarations, not a W-type or eliminator-only encoding — ADR-14). This sits closest to the Martin-Löf / Agda-Lean core (Martin-Löf 1984; Nordström, Petersson & Smith) rather than the impredicative-Prop-plus-CIC theory of Coq, though the universe-formation and Pi/Sigma-formation rules follow the Coquand-Huet 1988 presentation structurally.

Deployment model: a library (dtc-kernel, dtc-elab as Cargo crates usable independently) plus a REPL/checker CLI (dtc-cli) that type-checks a module and reports an accept/reject verdict with structured diagnostics. Users/operators: language implementers, PL researchers studying dependent-type-theory implementation, and contributors validating conformance against Agda/Lean via the differential harness (§28, Phase 11). Later phases this unlocks: pattern-match compilation as a reusable component, eliminator generation as a reusable component, and a differential conformance harness — a foundation a later, separate project (a tactic engine, an extraction pipeline) could build on, though those are explicitly out of scope here.

Rust, and rationale: ownership discipline lets the kernel/elaborator trust boundary be enforced structurally (core terms are constructed only through kernel-owned smart constructors, so "constructed outside the trust boundary" is a compile error, not a convention); no GC pauses to confound the eval/quote cost model central to NbE performance reasoning (§30); a mature arena/enum ecosystem fits the Term/Value sum types directly; strong pattern matching fits inference-rule-shaped code; robust fuzzing (cargo-fuzz) targets the parser and term deserializer. Rejected: Haskell (laziness obscures the eval/quote cost model this project depends on reasoning about precisely); OCaml (closest structural fit, but a less mature arena/interning and fuzzing ecosystem — the "would also work" alternative); C++ (no ownership-checked trust boundary, and undefined-behavior risk is unacceptable in a soundness-critical kernel).

Prerequisites: lambda calculus (untyped and simply-typed), type theory (through dependent types), operational semantics (small-step and big-step), de Bruijn indexing.

Timeline: Phase 0-2 (skeleton, NbE for a simply-typed core, kernel bidirectional core) ~10 weeks; Phase 3-4 (conversion checking, universes) ~6 weeks; Phase 5 (Sigma, full dependent core) ~4 weeks; Phase 6-7 (elaborator, metavariables, implicits) ~10 weeks; Phase 8-10 (inductive families, eliminators, pattern matching) ~12 weeks; Phase 11 (de-Bruijn re-check, differential harness, perf hardening) ~4 weeks. Total ~46 weeks to a conformance-gated v1.

Deferrals: PhaseDeferred("Phase 12 — impredicative Prop / proof-irrelevant universe"), PhaseDeferred("Phase 13 — tactic engine"), PhaseDeferred("Phase 14 — SMT-backed proof automation"), PhaseDeferred("Phase 15 — sized types / codata"), PhaseDeferred("Phase 16 — extraction to a compiled backend").

2. Why Build This

  • decidable definitional equality as an evaluation problem, not a syntactic one
  • the trusted-kernel / untrusted-elaborator split as the central trust architecture of every real proof assistant (the de Bruijn criterion)
  • normalization by evaluation as a general technique beyond type theory (partial evaluation, staged compilation, glued evaluation)
  • universe hierarchies and paradox avoidance (Girard's paradox, Type : Type)
  • higher-order pattern unification (Miller patterns) as the workhorse of practical elaboration
  • strict positivity and termination checking as the two conditions that keep a logic consistent (no proof of False via non-termination)
  • bidirectional type checking as a general infer/check discipline used far outside dependent types
  • inductive families and eliminator/recursor generation as the mechanism underlying "proof by induction" made executable

What Mastery Looks Like

  • can explain, from evaluation cost first, why NbE with closures beats naive substitution for conversion checking (tied to Phase 1 — NbE, §13)
  • can write the Pi/Sigma/universe typing rules and the conversion rule from memory and explain why the conversion rule is what makes typing depend on evaluation (tied to Phase 2 — kernel, §14)
  • can explain why cumulative universes need cumulativity, not just formation, to avoid re-stating every definition per level (tied to Phase 4 — universes, §16)
  • can trace a higher-order pattern-unification solve step by step for a real implicit-argument example (tied to Phase 6-7 — elaborator/implicits, §18-19)
  • can state strict positivity precisely enough to classify a real inductive declaration as accepted or rejected (tied to Phase 8 — inductive families, §20)
  • can explain the de Bruijn criterion and why it makes an elaborator bug a rejected term rather than a false proof (tied to Phase 11 — differential harness, §23)
  • can design a coverage checker that proves a case tree exhaustive without executing the program (tied to Phase 10 — pattern matching, §22)

Surface Syntax Parser. Converts UTF-8 source text into a surface AST; performs no semantic resolution, so a syntactically valid but meaningless program still parses (name resolution and elaboration happen downstream).

Elaborator. The untrusted heart of the system: inserts implicit arguments, allocates metavariables, generates and solves higher-order pattern-unification constraints (Miller 1991), and elaborates surface pattern matches into eliminator applications. Its output is a fully-elaborated core term with zero unsolved metavariables (I8).

Trusted Kernel. The trust boundary. Only the kernel may declare a term well-typed. It independently re-derives the type of every elaborator-produced term via the bidirectional infer/check judgements (§8), invoking the conversion checker whenever the typing rules require a definitional-equality check, and invoking the universe checker whenever a universe-formation rule applies.

NbE Evaluator. Computes definitional equality by evaluating core terms into a semantic domain of values with closures (eval) and reading values back into canonical beta-normal, eta-long syntax (quote). This is the engine both the kernel's conversion checker and the REPL's #eval command invoke.

Inductive-Definition Processor. Validates strict positivity of a proposed inductive declaration before it is registered in the global signature, and mechanically generates its eliminator/recursor and computation (iota) rules.

Global Env / Signature. The append-only registry of accepted declarations, inductive definitions, and generated eliminators that both the kernel and the NbE evaluator consult to resolve global references.

Type-checking throughput ≥ 2,000 top-level definitions/second on the conformance corpus (small definitions, warm signature)

Conversion-check latency (worst case) bounded by a reduction-fuel ceiling of 1,000,000 reduction steps; exceeding it is a rejected-term error, never a hang (I2)

Metavariable/unification scale ≤ 5,000 live metavariables per module; ≤ 50,000 constraint-queue entries
Kernel size (trusted LOC) ≤ 3,000 LOC across dtc-kernel + dtc-nbe combined — the entire trust boundary, audited line-by-line
Universe-level depth practical ceiling of 32 explicit surface levels; internal Lvl representation unbounded (u32)
Inductive-definition complexity ≤ 64 constructors per inductive, ≤ 32 parameters + indices, ≤ 16 recursive occurrences per constructor argument
Memory per checked module < 50 MB for a 10,000-definition module (core terms + normal-form cache)
Decidability guarantee conversion checking terminates on every well-typed term (Abel, Öhman & Vezzosi 2018); ill-scoped input is rejected before conversion is invoked
Error-reporting latency p95 < 2 ms from rejection point to structured diagnostic emission
RTO (CLI/service crash) < 5 s restart; no persistent mutable state to recover in Phase 0 (stateless batch checker)

CPU assumptions: x86_64 baseline, AVX2 optional, single-threaded kernel/elaboration path in Phase 0 (parallel module elaboration is a later-phase concern, not required for the god bar here). Decidability is a correctness guarantee, not a performance one: the fuel ceiling exists precisely because conversion-check cost is not elementarily bounded in general (§31).

6. Design Principles

P1. The kernel is small and trusted; the elaborator is large and untrusted — every term the elaborator produces is re-checked by the kernel, so an elaborator bug is a failed check, not an unsound proof (the de Bruijn criterion, I1).

P2. Definitional equality is decided by normalization, not ad hoc syntactic rules — NbE gives a canonical normal form, and conversion is comparing normal forms, which is what makes type checking decidable (Abel, Öhman & Vezzosi 2018, §8).

P3. Type checking is bidirectional — some terms synthesize their type (infer) and some are checked against an expected type (check); the infer/check split is what makes elaboration tractable (§8 bidirectional table).

P4. Variables are de Bruijn indices in the core term syntax and de Bruijn levels in the semantic value domain — indices count binders inward from a term's own root, levels count binders outward from the empty context, and this split is what makes NbE's closures well-defined (ADR-02).

P5. Universes are checked, not assumed — every type has a level, and every declaration's level is validated against Girard's-paradox avoidance before acceptance (I3).

P6. Positivity is checked, not assumed — every inductive declaration's constructor argument types are scanned for negative self-occurrence before the declaration is admitted (I4).

P7. Pattern matches are checked for coverage and termination before elaboration into eliminator applications — an unchecked match is not part of the theory (I5).

P8. The elaborator may postpone, guess, and backtrack; the kernel may never do any of these — the kernel's algorithm is fully deterministic and total on well-formed input (P1 corollary).

P9. A fully-elaborated core term handed to the kernel contains zero unsolved metavariables — metavariables are elaboration-local (I8).

P10. Normal forms are canonical (beta-normal, eta-long) — two terms are definitionally equal iff their normal forms are alpha-equivalent, with no separate eta-rule needed at comparison time (I6).

P11. Caching or memoizing a normal form is sound only if the cache key includes every input that could change the result (context, universe assignment) — an unsound cache is a soundness bug, not a performance bug (ADR-19, T5).

P12. Every rejection carries a structured reason (universe inconsistency / non-positive / non-covering / non-terminating / unification failure / kernel type mismatch) — "type error" alone is never an acceptable diagnostic.

P13. Surface syntax may change between releases; the core theory (the kernel's typing rules) is the stability anchor (§27).

P14. The differential oracle (checking the same definitions against Agda/Lean) is not a nice-to-have test — for a proof checker, silent unsoundness is the primary risk, and only an independent oracle catches it (§28, §32 MM3).

8. Domain Model

8.1 Core Syntax Grammar

Term  ::= Var(Ix)
        | Global(Name)
        | Lam(Name, Term)
        | App(Term, Term)
        | Pi(Name, Term, Term)
        | Sigma(Name, Term, Term)
        | Pair(Term, Term)
        | Proj1(Term) | Proj2(Term)
        | U(Lvl)
        | Ind(Name)              // inductive type former
        | Ctor(Name, [Term])     // constructor application
        | Elim(Name, Term, Motive, [Method], Term)  // eliminator application
        | Meta(MetaVar)          // elaborator-only, never in kernel input
        | Let(Name, Term, Term, Term)

Ix is a de Bruijn index (counts binders inward, term-local). Lvl is a universe level. Meta never occurs in a term handed to the kernel (I8).

8.2 Typing Judgements

Γ ⊢ t ⇒ A (infer: t synthesizes type A), Γ ⊢ t ⇐ A (check: t is checked against A), Γ ⊢ A ≡ B (definitional equality / conversion), Γ ⊢ (context well-formedness).

8.3 Typing Rules (selected, inference-rule form)

Rule Premises Conclusion
Var (x : A) ∈ Γ Γ ⊢ x ⇒ A
U-Formation Γ ⊢ Γ ⊢ Uᵢ ⇒ U_(i+1)
Pi-Formation Γ ⊢ A ⇐ Uᵢ and Γ, x:A ⊢ B ⇐ Uⱼ Γ ⊢ Π(x:A).B ⇒ U_(max i j)
Pi-Intro (Lam) Γ, x:A ⊢ t ⇐ B Γ ⊢ λx.t ⇐ Π(x:A).B
Pi-Elim (App) Γ ⊢ f ⇒ Π(x:A).B and Γ ⊢ a ⇐ A Γ ⊢ f a ⇒ B[a/x]
Sigma-Formation Γ ⊢ A ⇐ Uᵢ and Γ, x:A ⊢ B ⇐ Uⱼ Γ ⊢ Σ(x:A).B ⇒ U_(max i j)
Sigma-Intro (Pair) Γ ⊢ a ⇐ A and Γ ⊢ b ⇐ B[a/x] Γ ⊢ (a,b) ⇐ Σ(x:A).B
Sigma-Elim (Proj) Γ ⊢ p ⇒ Σ(x:A).B Γ ⊢ p.1 ⇒ A; Γ ⊢ p.2 ⇒ B[p.1/x]
Conversion Γ ⊢ t ⇒ A, Γ ⊢ A ≡ B, Γ ⊢ B ⇐ Uᵢ Γ ⊢ t ⇐ B

The Conversion rule is the one that ties typing to definitional equality: it is the reason a dependent checker must evaluate, not just parse, to decide typing.

8.4 Normalization by Evaluation — Named Steps

  1. eval(Term, Env) -> Value: recursively evaluate a term under an environment of values, building VLam/VPi/VSigma/VPair/VU/VNeutral values; a Lam becomes a VLam closing over its Env (a Closure), never substituting under the binder.
  2. apply(Value, Value) -> Value: eliminates a VLam by evaluating its body in the closure's environment extended with the argument (beta), or builds a VNeutral NApp if the head is neutral (stuck).
  3. quote(Value, Lvl) -> Term (readback): turns a value back into normal-form syntax at a given binder depth, eta-expanding VLam/VPair/VPi-typed neutrals so the result is eta-long as well as beta-normal.

Worked example: normalize (λx. x) y. eval produces apply(VLam(cl), VNeutral(NVar y)); applying the closure evaluates the body x in an environment where x ↦ VNeutral(NVar y), yielding VNeutral(NVar y). quote at depth 0 reads this back as the term y. Two syntactically different terms, (λx.x) y and y, both quote to y: they are definitionally equal.

8.5 Definitional Equality / Conversion Checking — Named Steps

  1. eval both sides in the current environment.
  2. quote both resulting values back to normal form (or, more efficiently, compare values structurally without a full quote — conv(Value, Value, Lvl) -> bool, which eta-expands functions/pairs on the fly rather than materializing the normal form; this is the algorithm actually implemented, §13/§15).
  3. Compare up to alpha (de Bruijn indices already make alpha-equivalence syntactic equality) and eta (function/pair eta handled by expansion during comparison, not as a separate rule).

Worked equal example: Γ ⊢ (λx. x) y ≡ y : A. Both sides evaluate to VNeutral(NVar y); conv returns true.

Worked rejection example: Γ ⊢ Π(x:Nat).Nat ≡ Σ(x:Nat).Nat. Both sides are already values in normal form; conv compares head constructors first (VPi vs VSigma) and rejects immediately — different head constructors can never be definitionally equal.

8.8 Metavariables and Higher-Order Pattern Unification — Named Steps

  1. Meta creation: elaborating an implicit argument or a hole allocates a fresh MetaVar with a recorded expected type and the ambient context (spine of bound variables it may depend on).
  2. Constraint generation: each unification obligation Γ ⊢ t ≟ u becomes a Constraint::Equality entry; rigid-rigid constraints decompose structurally (matching head constructors and recursing on subterms).
  3. Flex-rigid: a constraint ?m spine ≟ t where the spine is a list of distinct bound variables (a Miller pattern, Miller 1991) solves by abstracting t over the spine and assigning ?m := λspine. t, after an occurs-check that ?m does not appear in t.
  4. Flex-flex / non-pattern spines: postponed to a deferred-constraint queue, retried as other metas resolve.
  5. Spine pruning: eliminates dependencies a meta's solution provably cannot use, shrinking future pattern-unification obligations.

Worked example: elaborating id x where id : (A:Type) -> A -> A and x : Nat. The elaborator inserts an implicit metavariable for A, producing id ?m x; checking x against ?m under the applied function's domain generates the constraint ?m ≟ Nat (a trivial pattern, empty spine), which solves immediately: ?m := Nat.

8.9 Inductive Families — Named Steps

  1. Declare: name, parameters, indices, a list of constructors each with argument types possibly recursively mentioning name.
  2. Strict-positivity scan: for every constructor argument type, name may occur only in strictly-positive position (never to the left of a function arrow an odd number of times, i.e. never in a position that would make name an argument to itself negatively) — see the negative-occurrence rejection example below.
  3. Eliminator generation: mechanically build a motive parameter (a family over the inductive), one method parameter per constructor (typed using the motive applied to that constructor's recursive subterms), and the resulting eliminator's type.
  4. Computation (iota) rule generation: for eliminator applied to a constructor application, the computation rule reduces it to the corresponding method applied to the constructor's arguments (and their recursive eliminations).

8.10 Dependent Pattern-Match Elaboration

  1. Build a case tree from surface match clauses, splitting on the first scrutinee whose constructors are not yet distinguished.
  2. Coverage check: at each split, confirm every constructor of the scrutinee's inductive type has a clause (or is provably impossible by unification of indices).
  3. Termination check: confirm each recursive call is on a structurally smaller argument (or defer via PhaseDeferred to size-change termination, §22).
  4. Elaborate the checked case tree into nested eliminator applications against the generated recursor (§8.9).

8.11 End-to-End Worked Example — Length-Indexed Vector append

Vec : (A : Type) -> Nat -> Type
  nil  : Vec A zero
  cons : (n:Nat) -> A -> Vec A n -> Vec A (succ n)

append : (A:Type) -> (n m : Nat) -> Vec A n -> Vec A m -> Vec A (plus n m)
append A n m nil         ys = ys
append A n m (cons k x xs) ys = cons (plus k m) x (append A k m xs ys)

Elaboration: append's surface match splits on the fourth explicit argument (Vec A n); coverage requires both nil and cons clauses (present); the recursive call append A k m xs ys is structurally smaller in the fourth argument (xs vs. cons k x xs), satisfying termination. The elaborated core term is a single Elim(Vec, ..., motive=λn._.Vec A (plus n m), methods=[ys; λk x xs ih. cons (plus k m) x ih], scrutinee). The kernel independently infers this eliminator's type and checks it convertible to the declared return type Vec A (plus n m) — this is where the plus n m vs. plus (succ k) m index computation is settled by NbE, not by syntax.

8.12 Malformed / Hard Examples

  • Universe-inconsistent: Type_i : Type_i — rejected by I3 (Girard's paradox).
  • Non-positive inductive: Bad : Type with mk : ((Bad -> Nat) -> Bad) -> Bad — Bad occurs negatively (to the left of one function arrow, an odd number of times, inside the outer argument type) — rejected by I4.
  • Non-covering match: a Vec match with only a nil clause — rejected by I5 (coverage).
  • Non-terminating recursion: loop : Nat -> Nat; loop n = loop n with no decreasing argument — rejected by I5 (termination).
  • Unification failure: ?m ≟ f x where f x is not a Miller pattern (a non-variable spine) and no rigid structure lets the constraint decompose — postponed, then reported as UnificationFailure if never solved by end of elaboration.
  • Ill-typed kernel input: App(Lam(...), ...) where the argument's inferred type does not convert to the lambda's expected domain — rejected by the Pi-Elim rule's premise failing, independent of whatever the elaborator believed.

8.13 Failure-Path Example

Given f : Nat -> Nat := λx. x true (applying a Nat to a Bool literal): inference of x yields Nat; Nat is not a Pi type, so Pi-Elim's premise Γ ⊢ f ⇒ Π(x:A).B fails at the head — the kernel rejects with a structured NotAFunctionType diagnostic carrying the inferred head type and the source span, before any conversion check is attempted.

12. Phase 0 — Skeleton, Core-Term Representation, Parser, CI

12.1 Objectives

Stand up the repository skeleton, the Term core-syntax representation, a recursive-descent parser for the surface grammar (§8.1's simply-typed subset only — Pi/lambda/application/universe, no Sigma/inductives yet), and a CI pipeline that gates every subsequent phase.

12.2 Detailed Implementation Steps

Term is defined exactly as in §11, with de Bruijn indices from the start (ADR-02) so no later phase has to retrofit indexing; the parser produces a named surface AST first, then a separate name-resolution pass converts names to Ix (P4). CI wires cargo test, cargo clippy --deny warnings, and rustfmt --check as hard gates per P13's stability discipline.

12.3 Deliverable

dtc-syntax (lexer, parser, surface AST, name resolver) and dtc-core (the Term enum, arena-backed construction, de Bruijn scope-checked smart constructors per I10) compiling and passing a parser-only fixture set; CI green.

12.4 Acceptance Criteria

  • 100% of conformance/well-typed/phase0-parse/*.dep fixtures parse to an identical, deterministic AST hash across three repeated runs.
  • Every constructed Term::Var(Ix) passes the I10 scope-check smart constructor; zero scope_violation panics across the fixture set.
  • CI wall-clock < 10 minutes.

12.5 Conformance Fixtures

parser/valid-lambda.dep, parser/valid-pi.dep, parser/malformed-unicode.dep, parser/unclosed-pi.dep, core/debruijn-roundtrip.dep (parse, pretty-print, re-parse, compare AST).

12.6 Pitfalls

  • Name resolution silently shadowing an outer binder instead of reporting it (I10- adjacent: an incorrectly shifted index looks well-scoped but references the wrong binder).
  • Parser accepting a term whose pretty-printer cannot round-trip it (asymmetry between parse and print grammars).
  • Deterministic-AST-hash fixture passing locally but failing in CI due to locale-dependent Unicode normalization in the lexer.

12.7 Performance Concerns

Token allocation churn in the lexer; recursive-descent stack depth on deeply nested Pi/Lam chains (bounded by a parser recursion-depth ceiling, not the kernel's fuel ceiling — these are distinct budgets).

12.8 Edge Cases

Empty source file; a single top-level universe literal with no declarations; a comment-only file; a file containing only whitespace and BOM.

12.9 Failure Analysis

Most severe Phase-0 risk: the parser accepts a structurally invalid tree (e.g. an Ix that does not yet correspond to any binder) that later phases silently tolerate. Containment: I10's scope-check smart constructor makes this a hard construction-time panic, not a downstream type error, so Phase 0 fixtures catch it immediately rather than surfacing confusingly in Phase 2's kernel.

12.10 Operational Notes

Emit parse-latency histograms and token-throughput counters from the start (ADR-22); these become the baseline §30 performance targets are measured against.

13. Phase 1 — NbE Evaluator (eval + quote) for a Simply-Typed Core

13.1 Objectives

Implement dtc-nbe's eval and quote (§8.4) for the Phase-0 simply-typed subset (no dependent Pi yet — domain and codomain types are non-dependent), establishing the Value/Neutral/Closure/Env representation that every later phase builds on.

13.2 Detailed Implementation Steps

Value and Closure are built exactly per §11 and ADR-04 (closures over an environment, not substitution); eval follows the named steps in §8.4.1-2, quote follows §8.4.3, applying P2 (normalization decides equality, not ad hoc rules) and P10 (canonical beta-normal, eta-long forms) as the governing principles; ADR-03 locks NbE over naive substitution specifically to avoid the exponential blowup demonstrated in §34's capacity model.

13.3 Deliverable

A working eval/quote round trip for the simply-typed subset, with a property test (I6-driven) proving quote(eval(t)) is idempotent under re-quoting.

13.4 Acceptance Criteria

  • quote(eval(t, [])) == quote(eval(quote(eval(t, [])), [])) for 100% of the conformance/well-typed/phase1-nbe/*.dep corpus (idempotence, I6).
  • Beta-reduction fixtures ((λx.x) y, (λx.λy.x) a b) normalize to their expected hand-computed normal forms exactly.
  • Normalization throughput ≥ the §4 NbE-cost target on the benchmark corpus.

13.5 Conformance Fixtures

nbe/beta-simple.dep, nbe/nested-application.dep, nbe/deep-spine.dep (a 200-deep application chain), nbe/eta-function.dep (checks eta-expansion of a bare neutral function value during quote).

13.6 Pitfalls

  • Closures capturing the wrong environment slice under nested binders (an off-by-one in Env indexing that only manifests on doubly-nested lambdas).
  • quote producing a beta-normal but not eta-long form for a neutral function-typed variable, silently violating I6 without tripping any existing test.
  • Stack overflow on deep spines instead of a controlled fuel-exhaustion error (this phase predates the kernel's fuel ceiling — Phase 1 must still bound recursion depth independently).
  • Memoizing eval results keyed only on the Term pointer, not on Env contents, producing silently wrong values when the same sub-term is evaluated under two different environments (an early instance of the ADR-19 caching-soundness trap).

13.7 Performance Concerns

Allocation storms from boxing every Value variant; environment-vector cloning on closure creation (mitigated by Env sharing via reference-counting rather than deep clone, revisited under ADR-19 once caching is introduced in Phase 3).

13.8 Edge Cases

Zero-argument application (a type error caught upstream, but eval must not panic on malformed spines during fuzzing); a closure whose body never references its bound variable (constant function); a term with no free variables at all (fully closed).

13.9 Failure Analysis

Symptom: p99 normalization latency spikes on deep spines. Detection: per-term reduction-step counters compared against the §4 fuel budget (introduced fully in Phase 2, stubbed here). Recovery: isolate the offending fixture, add it to the regression corpus, and re-benchmark after the closure-representation fix.

13.10 Operational Notes

Track normalization-step counts and closure-allocation counts per eval call; this telemetry becomes the input to the conversion-latency dashboards built out in Phase 3 (§26).

14. Phase 2 — Trusted Kernel: Bidirectional Checking for Pi and Lambda

14.1 Objectives

Implement dtc-kernel's infer/check (§8.2-8.3, §8.7) for Var, App, Lam, Pi, and U, establishing the kernel crate as the sole authority able to accept a Decl (P1, I1).

14.2 Detailed Implementation Steps

Bidirectional dispatch follows §8.7's table exactly: Var/App/U infer, Lam checks; the Pi-Elim rule (§8.3) drives App's infer case, and the Pi-Intro rule drives Lam's check case. Every rule application is a direct transcription of §8.3's inference-rule table — no rule is approximated or special-cased outside that table (P3, P8). The kernel crate exposes no API that accepts a Term without running these rules (I7, ADR-18).

14.3 Deliverable

A kernel that accepts every well-typed Phase-0/1 fixture and rejects every ill-typed one with a structured TypeError (§11), using Phase 1's eval/quote for any conversion obligation the Pi-Elim substitution introduces.

14.4 Acceptance Criteria

  • 100% of conformance/well-typed/phase2-kernel/*.dep accepted; 100% of conformance/ill-typed/phase2-kernel/*.dep rejected with the exact expected TypeError variant (P12).
  • Zero instances of the kernel accepting a term that Phase 1's quote cannot re-derive the same normal form for (an early I1-style self-consistency check, ahead of the full differential harness in Phase 11).

14.5 Conformance Fixtures

typing/identity.dep ((A:Type) -> A -> A), typing/app-mismatch.dep (applying a Nat to a Nat, expecting NotAFunctionType), typing/pi-formation.dep.

14.6 Pitfalls

  • Context corruption across nested Lam checks (an inner check mutating a context slot the outer check still needs) — caught by making Context extension immutable-append only (§11).
  • The kernel silently accepting a term because a TypeError path returns Ok on an unhandled Term variant by default instead of exhaustively matching (Rust's exhaustive match on the Term enum is the structural guard here, not a runtime check).
  • Substitution in the Pi-Elim rule (B[a/x]) implemented via naive term substitution instead of NbE-based evaluation, reintroducing exactly the cost/soundness problem ADR-03/ADR-05 exist to avoid.

14.7 Performance Concerns

Repeated re-evaluation of the same sub-term across nested infer calls (no memoization yet — deferred to Phase 3, ADR-19); context-vector growth on deeply nested lambdas.

14.8 Edge Cases

A Lam with no body reference to its bound variable; App where the argument itself is a Lam (higher-order but still simply-typed); checking a term against a Pi whose domain is itself a Pi (higher-rank in the simply-typed sense).

14.9 Failure Analysis

Kernel soundness failures at this phase are the first real instance of the worst-case risk named in T1: an accepted ill-typed term. Response: any conformance-fixture mismatch here halts Phase 2 sign-off — this phase's acceptance criteria are treated as a soundness gate, not a normal test-pass bar.

14.10 Operational Notes

Expose typecheck latency per top-level declaration from this phase onward; this is the first real data point for the §4 throughput targets.

15. Phase 3 — Definitional Equality / Conversion Checking via NbE

15.1 Objectives

Generalize Phase 1's eval/quote into the full conversion checker conv(Value, Value, Lvl) -> ConvResult that the Conversion typing rule (§8.3) invokes, and wire it into the Phase 2 kernel as the mechanism for every definitional-equality obligation.

15.2 Detailed Implementation Steps

conv implements §8.5's named steps directly: structural comparison of values with on-demand eta-expansion, short-circuiting on head-constructor mismatch (the §8.5 worked rejection example) before recursing into subterms; a reduction-fuel counter (I2) bounds worst-case cost per ADR-05's decidability argument (Abel, Öhman & Vezzosi 2018).

15.3 Deliverable

A conversion checker satisfying I2 (bounded termination), I6 (canonical quote output), and I9 (equivalence-relation properties), with the Conversion typing rule now fully operative in the kernel.

15.4 Acceptance Criteria

  • conv returns Equal for 100% of conformance/conversion-pairs/equal/*.dep and NotEqual for 100% of conformance/conversion-pairs/unequal/*.dep.
  • Property tests confirm reflexivity, symmetry, and transitivity (I9) across ≥ 10,000 generated term pairs with zero violations.
  • Fuel-exhaustion path exercised by a synthetic pathological fixture and confirmed to reject with NonTermination, never hang (I2).

15.5 Conformance Fixtures

conversion-pairs/equal/beta-eta.dep (the §8.5 worked-equal example), conversion- pairs/unequal/pi-vs-sigma-head.dep (the §8.5 worked-rejection example, added ahead of Sigma's own Phase 5 landing as a head-constructor-mismatch fixture using a placeholder tag), conversion-pairs/fuel-exhaustion.dep.

15.6 Pitfalls

  • Asymmetric conv implementation (checking a against b takes a different code path than b against a), silently violating I9's symmetry without any single-fixture test catching it — only the property-test suite catches this class.
  • Eta-expansion applied inconsistently between the two sides being compared, causing a false NotEqual on genuinely equal terms.
  • Fuel counter shared incorrectly across independent conv calls in a batch check, causing an unrelated later declaration to spuriously fail with NonTermination.

15.7 Performance Concerns

This phase introduces the central performance risk of the whole system (§31): worst-case conversion cost is not elementarily bounded. Mitigations locked here: eta-expansion on-demand rather than eager (avoids expanding terms that never need it), and the ADR-19 cache-key design specified now even though caching itself lands as an optimization pass later.

15.8 Edge Cases

Comparing a term against itself (must always be Equal in O(depth), not O(full re-evaluation) — an easy self-check optimization); comparing two neutrals with different spine lengths (immediate NotEqual, no recursion needed).

15.9 Failure Analysis

Primary risk: hidden asymmetry or non-transitivity in conv (I9 violation), which would silently make the Conversion typing rule unsound in one direction. Detection: the property-test suite (§28) is the only defense here — example-based tests cannot practically enumerate the counterexample space. Recovery: block release; this is treated identically to a T5-class soundness threat.

15.10 Operational Notes

Track conversion-check latency distribution (p50/p95/p99) and fuel-exhaustion counts as first-class dashboards from this phase forward (§26); a rising fuel-exhaustion rate on real fixtures — as opposed to synthetic pathological ones — is itself an alert condition.

16. Phase 4 — Universe Hierarchy and Consistency Checking

16.1 Objectives

Implement the universe checker: U-Formation, Pi/Sigma-Formation's max i j rule (Sigma lands fully in Phase 5, but the level-arithmetic machinery is built here), and cumulativity (§8.6), enforcing I3 (no Type_i : Type_i) and I11 (level monotonicity under substitution).

16.2 Detailed Implementation Steps

Lvl is a u32 per §11; universe-formation and cumulativity are implemented exactly per the §8.3/§8.6 rule tables — P5 ("universes are checked, not assumed") governs every code path here. Girard's-paradox avoidance is enforced structurally: the U-Formation rule's conclusion level is always strictly the premise's successor, so no recursive well-formedness check can ever produce Uᵢ : Uᵢ (I3 is a corollary of the rule's shape, not a separate runtime check, though a runtime assertion is kept as a defense-in-depth measure per T2).

16.3 Deliverable

A universe checker integrated into the Phase 2 kernel's formation rules, with cumulativity available as an explicit coercion the Conversion-adjacent subsumption rule can invoke.

16.4 Acceptance Criteria

  • 100% of conformance/universe-inconsistency/*.dep rejected with UniverseInconsistency.
  • Cumulativity fixtures (A : Type_0 used where Type_3 is expected) accepted; the reverse (using a Type_3 term where Type_0 is strictly required with no cumulativity path) rejected.
  • I11 property test: substituting a level-i term into a context expecting level j ≥ i never decreases the surrounding type's computed level, across ≥ 5,000 generated cases.

16.5 Conformance Fixtures

universe-inconsistency/type-in-type.dep, universe/cumulativity-up.dep, universe/cumulativity-reject-down.dep, universe/max-formation.dep.

16.6 Pitfalls

  • An off-by-one in the U-Formation successor computation that only manifests at level ≥ 2, hiding behind a Phase-2-era test suite that only ever exercised Type_0/ Type_1.
  • Cumulativity implemented as silent level-coercion everywhere, accidentally admitting a case the formation rules should have rejected (over-eager subsumption masking a real inconsistency, T2's central concern).
  • Level arithmetic overflow on deeply nested universe-polymorphic-looking surface code, even though full universe polymorphism is deferred (§37) — the internal u32 must still not silently wrap.

16.7 Performance Concerns

Universe-level checks are cheap (integer comparisons) relative to conversion checking; the risk is not per-check cost but accumulated bookkeeping across large signatures — see §34's universe-level-arithmetic capacity numbers.

16.8 Edge Cases

A declaration whose type mentions no universe explicitly (level must still be inferred, never defaulted silently to 0 without justification); a chain of let-bound universe-polymorphic-looking aliases that must still resolve to concrete levels in Phase 0's non-polymorphic universe model.

16.9 Failure Analysis

A universe-inconsistency slipping through here is precisely T2: it would let Girard's paradox construct a term of every type, including a proof of False, entirely independent of any inductive-family machinery. Detection: the dedicated universe-inconsistency conformance corpus plus the differential oracle (§28, Phase 11) cross-checking against Agda/Lean's own universe checkers on shared fixtures.

16.10 Operational Notes

Track universe-level-depth histograms per module; a module regularly touching levels near the §4 practical ceiling (32) is a signal to revisit whether universe polymorphism should be un-deferred (§37's trigger condition).

17. Phase 5 — Sigma Types and the Full Dependent Core

17.1 Objectives

Add Sigma/Pair/Proj1/Proj2 to the kernel's bidirectional rules (§8.3, §8.7) and generalize Phase 2's Pi-only dependent substitution machinery to the full dependent core — this is the phase where "types can contain terms" (MM1) becomes true throughout the checker, not just in Pi domains.

17.2 Detailed Implementation Steps

Sigma-Formation/Intro/Elim are transcribed directly from §8.3's rule table; Proj1/ Proj2 infer (§8.7), following the same infer/check discipline P3 established for Pi. Because B[p.1/x] in Sigma-Elim's second projection rule requires substituting an arbitrary inferred term (not just a bound variable) into a type, this phase is the first real stress test of NbE-based substitution-avoidance (ADR-04): the substitution is performed by evaluating B in an environment extended with eval(p.1), never by syntactic term substitution.

17.3 Deliverable

A kernel accepting the full Pi+Sigma+universe dependent core, with conversion checking (Phase 3) generalized to compare VSigma/VPair values.

17.4 Acceptance Criteria

  • 100% of conformance/well-typed/phase5-sigma/*.dep accepted, including a fixture whose second projection's type genuinely depends on the first projection's value (e.g. a dependent pair (n : Nat) × Vec Bool n-shaped fixture using a placeholder inductive stand-in, since Vec itself lands in Phase 8).
  • Eta-for-pairs fixtures ((p.1, p.2) ≡ p) accepted by conv (extending I6's eta-long guarantee to VPair).

17.5 Conformance Fixtures

sigma/dependent-pair.dep, sigma/proj-substitution.dep, sigma/eta-pair.dep, conversion-pairs/equal/pair-eta.dep.

17.6 Pitfalls

  • Proj2's type computed using the syntactic first component instead of its evaluated value, producing a type that fails to convert against the expected one even though the term is genuinely well-typed (a substitution-strategy bug, not a theory bug).
  • Eta-for-pairs implemented asymmetrically from eta-for-functions, creating two subtly different code paths in conv that must both independently satisfy I9.
  • Confusing Sigma's dependent second component with a non-dependent product type during elaboration (a surface-syntax ambiguity that must be resolved before reaching the kernel, not inside it).

17.7 Performance Concerns

Every Proj1 evaluation performed as part of computing Proj2's type doubles the evaluation work along projection chains; this is the first place a "recompute vs. cache the projection's evaluated value" tradeoff (ADR-19-adjacent) becomes visible.

17.8 Edge Cases

A Sigma whose second component type does not actually depend on the first (degenerate to a non-dependent pair — must still type-check identically to the dependent case, no special-casing allowed per P8's "no special-casing outside the rule table"); nested Sigmas three levels deep.

17.9 Failure Analysis

Risk class: an unsound projection-substitution shortcut that happens to pass the initial fixture set because those fixtures' second components don't actually use the first component's value. Mitigation: §28's fixture design mandates at least one genuinely-dependent-on-value fixture per new type former, not just structurally- dependent-in-syntax ones.

17.10 Operational Notes

Extend the Phase 3 conversion-latency dashboards to break down by head-constructor kind (Pi vs. Sigma vs. neutral), since Sigma-heavy fixtures are expected to shift the latency distribution.

18. Phase 6 — The Elaborator: Metavariables and Pattern Unification

18.1 Objectives

Stand up dtc-elab: metavariable allocation, constraint generation, and Miller higher-order pattern unification (§8.8, Miller 1991), establishing the untrusted side of the trust boundary (P1, ADR-07) as a real component for the first time.

18.2 Detailed Implementation Steps

Follows §8.8's five named steps exactly: meta creation with recorded expected type and spine (step 1), rigid-rigid structural decomposition (step 2), flex-rigid pattern solving with occurs-check (step 3, ADR-09), flex-flex postponement to a deferred queue (step 4), and spine pruning (step 5). Every solved meta's assignment is recorded but never trusted directly — I8 requires the finalization pass (Phase 7) to substitute all metas away before any kernel handoff, so this phase deliberately does not yet wire dtc-elab's output into dtc-kernel.

18.3 Deliverable

A standalone constraint solver that, given a set of Constraint::Equality obligations generated from a hand-written test harness (not yet real surface syntax — that is Phase 7's implicit-insertion front end), solves all Miller-pattern cases and correctly postpones non-pattern cases.

18.4 Acceptance Criteria

  • 100% of conformance unification fixtures classified as Miller patterns solve to the expected assignment.
  • 100% of non-pattern fixtures postpone rather than incorrectly "solving" via an unsound heuristic.
  • Occurs-check fixtures (?m ≟ f ?m) rejected as UnificationFailure, never accidentally producing a cyclic assignment.

18.5 Conformance Fixtures

elaboration/pattern-solve.dep, elaboration/flex-flex-postpone.dep, elaboration/occurs-check-reject.dep, elaboration/spine-pruning.dep.

18.6 Pitfalls

  • A "nearly a pattern" spine (repeated variables, e.g. ?m x x) incorrectly accepted as a Miller pattern, producing an assignment that is not actually the most general solution (Miller patterns require distinct bound variables in the spine).
  • Postponed flex-flex constraints never retried because the retry trigger (another meta resolving) is not wired to re-scan the deferred queue, causing silent unification starvation that only manifests as a much later UnsolvedMetavariable with no actionable diagnostic.
  • Occurs-check implemented shallowly (checks the immediate constraint but not a meta that transitively depends on itself through two other metas' assignments).

18.7 Performance Concerns

Constraint-queue scanning cost on retry (naive full-queue rescans on every meta solve are O(n²) in the number of live metas); the §4 metavariable-scale target (≤ 50,000 queue entries) is the ceiling this phase's data structures must stay efficient under.

18.8 Edge Cases

A metavariable with an empty spine (a "closed" meta, trivially either solved or stuck); a constraint that is simultaneously a valid pattern in one direction and not in the other (asymmetric flex-rigid vs. rigid-flex framing) — the solver must normalize which side is "flex" consistently.

18.9 Failure Analysis

Risk class: a metavariable-assignment bug (T6) that leaks an incorrect or unsolved constraint forward. Containment: because this phase's output never reaches the kernel directly (I8's finalization gate is Phase 7), any bug here manifests as an elaboration- level rejection or an incorrect-but-still-kernel-checked term — the kernel's independent re-derivation (I1) is the actual backstop, not this phase's own correctness alone.

18.10 Operational Notes

Emit constraint-queue depth and postponement-count metrics; a queue that never drains (monotonically growing postponed count) is an elaboration-health alert condition distinct from any single fixture failure.

19. Phase 7 — Implicit-Argument Inference

19.1 Objectives

Wire real surface syntax through implicit-argument insertion (§8.8's worked id x example) and the elaboration finalization pass that enforces I8 (zero unsolved metas at kernel handoff), completing the untrusted-elaborator-to-trusted-kernel pipeline for the Pi/Sigma/universe core.

19.2 Detailed Implementation Steps

Implicit insertion follows ADR-10 (eager insertion at application sites): every application to a Pi-typed head with a leading implicit-marked binder gets a fresh metavariable inserted automatically, then unified against the argument's inferred type per Phase 6's solver. The finalization pass (P9, I8) walks the fully-constrained term and substitutes every solved meta, rejecting with UnsolvedMetavariable (P12) if any remain — this is the first point in the pipeline where a Term is guaranteed Meta-free before it is passed to dtc-kernel.

19.3 Deliverable

An end-to-end path from surface syntax with implicit arguments to a kernel-checked core term, exercising the full §8.8 worked example (id x inferring A := Nat) as a real integration fixture rather than a hand-built constraint set.

19.4 Acceptance Criteria

  • 100% of conformance/well-typed/phase7-implicits/*.dep elaborate to a Meta-free term that the Phase 2/5 kernel independently accepts (I1 exercised end-to-end for the first time).
  • 100% of fixtures with a genuinely unsolvable implicit reject with UnsolvedMetavariable, never silently defaulting an implicit to an arbitrary guess.
  • p95 elaboration latency meets the §4 target (< 5 ms per definition, ≤ 10 metas).

19.5 Conformance Fixtures

elaboration/implicit-simple.dep (the id x example), elaboration/implicit- ambiguous.dep (an implicit that cannot be determined from any argument, expecting rejection), elaboration/implicit-chain.dep (three nested implicit-taking functions).

19.6 Pitfalls

  • Implicit insertion order interacting badly with left-to-right argument checking, causing a later explicit argument's type to be needed before an earlier implicit is solved (a genuine dependency-ordering problem, not just an implementation detail — requires the deferred-constraint queue from Phase 6, not a simple single-pass insert).
  • The finalization pass substituting solved metas in the wrong order (a meta solved in terms of another still-unsolved meta), producing a term that still structurally contains Meta despite the pass believing it is done — directly threatens I8.
  • An ambiguous implicit silently resolved to whichever solution the solver happened to find first, instead of being detected as genuinely ambiguous and rejected.

19.7 Performance Concerns

Elaboration latency is dominated by constraint-solving retries (Phase 6) triggered by insertion order; this phase's benchmark corpus is the first to meaningfully exercise the §4 elaboration-latency target under realistic implicit-argument density.

19.8 Edge Cases

A function with all-implicit arguments and no explicit ones (nothing to unify against without an expected-type propagated from context); an implicit argument whose expected type is itself dependent on an earlier explicit argument's value.

19.9 Failure Analysis

Primary risk: I8 violation (a meta-containing term reaching the kernel). Detection: the finalization pass's own meta-scan (§7) is the direct enforcement; as defense-in-depth, dtc-kernel's Term construction path has no Meta variant reachable from its public API at all (a compile-time guarantee via crate-boundary type design, not just a runtime check) — this is the concrete mechanism behind ADR-07's split.

19.10 Operational Notes

Track metavariables-solved vs. metavariables-postponed-to-failure ratios per module; this ratio, tracked over the conformance corpus, becomes a §26 operational metric for elaborator health going forward.

20. Phase 8 — Inductive Families with Strict-Positivity Checking

20.1 Objectives

Implement dtc-inductive's declaration processing and the strict-positivity scan (§8.9 steps 1-2), gating every inductive declaration behind I4 before it is registered in the trusted Signature.

20.2 Detailed Implementation Steps

The positivity scan walks each constructor's argument types counting sign-flips across function arrows relative to the inductive's own name (P6); an even number of arrow- crossings (including zero) is positive, an odd number is negative, transcribing the standard strict-positivity criterion (Coquand-Huet-adjacent, also used by Coq/Agda — §33) rather than any semantic/model-based method (ADR-12). The scan runs entirely before kernel registration — the kernel itself never sees a rejected inductive.

20.3 Deliverable

A processor that accepts Nat, Bool, and Vec (the §8.11 worked example's dependencies) and rejects the §8.12 non-positive Bad example, registering accepted inductives into the Signature with their constructors typed against the declared parameters/indices.

20.4 Acceptance Criteria

  • 100% of conformance/well-typed/phase8-inductive/*.dep (including Nat, Bool, Vec) accepted.
  • 100% of conformance/non-positive/*.dep rejected with NonStrictlyPositive, each carrying the specific constructor and argument position where negativity was detected (P12).
  • Parameter/index arity mismatches between a constructor's declared type and the inductive's signature rejected before positivity is even checked (a prior well-formedness gate).

20.5 Conformance Fixtures

inductive/nat.dep, inductive/vec.dep, non-positive/bad-negative-occurrence.dep (the §8.12 example), non-positive/mutual-negative.dep (negativity introduced through a second, mutually referenced inductive).

20.6 Pitfalls

  • The positivity scan counting arrow-crossings correctly for a direct self-reference but missing an indirect one mediated through an alias or a let-bound type synonym.
  • A constructor argument whose type is itself a Pi returning the inductive type (strictly positive) being misclassified as negative by a scan that treats any occurrence to the left of any arrow as negative rather than counting crossings correctly.
  • Parameters (uniform across all constructors) confused with indices (varying per constructor) in the arity check, silently accepting a malformed Vec-like declaration with an inconsistent parameter count.

20.7 Performance Concerns

Positivity scanning cost is linear in constructor-argument-type size and bounded by the §4 inductive-complexity ceiling (≤ 64 constructors, ≤ 32 params+indices); no NbE evaluation is required for the scan itself (it is purely syntactic per ADR-12), keeping this phase cheap relative to conversion checking.

20.8 Edge Cases

An inductive with zero constructors (an empty type, e.g. False-shaped — must still be accepted as a valid, if uninhabited, declaration); a constructor with zero arguments (a nullary constructor, e.g. zero/nil); an inductive that is a parameter of another inductive's constructor (nested, non-recursive occurrence — always positive).

20.9 Failure Analysis

A non-positive inductive slipping through is T3: it admits a term that can be used to build a non-terminating recursor application, which in turn is usable to prove False. Detection: the dedicated non-positive conformance corpus, expanded during Phase 11's fuzzing pass (§28) to generate structurally-varied negative-occurrence patterns beyond the hand-written fixtures.

20.10 Operational Notes

Track positivity-scan rejection counts and reasons; a spike in a specific rejection subtype (e.g. mutual-negative) across real user-authored fixtures is a signal that the scan's diagnostic quality, not its correctness, needs attention.

21. Phase 9 — Eliminator/Recursor Generation and Computation Rules

21.1 Objectives

Mechanically generate, for every accepted inductive, its eliminator (motive + one method per constructor) and the iota (computation) rules that let the kernel reduce an eliminator applied to a constructor application (§8.9 steps 3-4).

21.2 Detailed Implementation Steps

Eliminator generation is a mechanical transcription from the inductive's constructor list: the motive parameter's type is Π(indices).Ind(params, indices) -> Uᵢ; each method parameter's type mirrors its constructor's argument types, with every recursive argument (an occurrence of the inductive itself, licensed by I4's positivity check) additionally requiring an "induction hypothesis" argument of the motive applied to that recursive argument. Iota rules are registered as reduction rules the NbE evaluator's apply/eval (§8.4 step 2) recognizes on an Elim head applied to a Ctor value, extending Phase 1's evaluator rather than replacing it.

21.3 Deliverable

Generated eliminators for Nat (Nat-elim), Bool (Bool-elim), and Vec (Vec-elim), each with kernel-verified formation and NbE-verified computation rules matching the standard Martin-Löf presentation (Nordström-Petersson-Smith).

21.4 Acceptance Criteria

  • Nat-elim/Bool-elim/Vec-elim's generated types independently pass the Phase 2/5 kernel's formation rules (I1 exercised on generated, not hand-written, terms for the first time).
  • Iota-rule fixtures (Nat-elim P pz ps zero ≡ pz, Nat-elim P pz ps (succ n) ≡ ps n (Nat-elim P pz ps n)) hold under conv (Phase 3).
  • 100% of conformance/well-typed/phase9-eliminators/*.dep accepted.

21.5 Conformance Fixtures

eliminator/nat-elim-zero.dep, eliminator/nat-elim-succ.dep, eliminator/vec-elim-nil.dep, eliminator/vec-elim-cons.dep.

21.6 Pitfalls

  • An induction-hypothesis argument's type built against the syntactic recursive occurrence instead of the motive applied to that occurrence, producing an eliminator that type-checks in simple cases but is subtly too weak for genuinely dependent motives (an easy-to-miss generalization gap).
  • Iota rules registered as ordinary let-style unfoldings instead of as reduction rules the NbE evaluator's apply recognizes structurally, causing conversion checks involving eliminators to fail to reduce and spuriously reject equal terms.
  • Off-by-one in method-parameter ordering when a constructor has multiple recursive occurrences of the same inductive (each needs its own induction hypothesis, in the same order as the constructor's own argument list).

21.7 Performance Concerns

Every eliminator application on a large constructor argument (e.g. a Vec of length 1,000) triggers that many nested iota-rule reductions during evaluation; this is a direct instance of the §31 definitional-equality-blowup risk and is the first place a real, non-synthetic fixture can exercise it.

21.8 Edge Cases

An inductive with no recursive constructor arguments at all (e.g. Bool: its eliminator needs no induction hypotheses, only motive-typed method results); a constructor with two recursive arguments of the same inductive (needs two independent induction hypotheses); an eliminator applied to a neutral (non-constructor) scrutinee (must produce a well-typed neutral NElim, not attempt reduction).

21.9 Failure Analysis

A wrong induction-hypothesis type is a subtle instance of T1 (an elaborator/generator bug the kernel might or might not catch, depending on whether the weakness is exercised by a given fixture) — the kernel's independent re-derivation of the generated eliminator's formation rule is the real defense, which is exactly why 21.4's acceptance criterion insists the generated eliminator itself passes kernel formation, not just its uses.

21.10 Operational Notes

Track per-inductive eliminator-generation time and generated-eliminator size (method count × average method-type size); this feeds the §34 capacity model's memory-per- checked-term estimate for inductive-heavy modules.

22. Phase 10 — Dependent Pattern Matching with Coverage and Termination Checking

22.1 Objectives

Implement dtc-pattern's case-tree construction, coverage checking, and structural termination checking (§8.10), completing elaboration of surface match syntax into nested eliminator applications against Phase 9's generated recursors — the §8.11 vector append example becomes a real, checked end-to-end fixture in this phase.

22.2 Detailed Implementation Steps

Case-tree construction and coverage checking follow McBride & McKinna 2004's "view from the left" discipline (P7): splitting on a scrutinee is only valid when every constructor of its inductive type is represented by a clause or is index-unifiably impossible; termination checking uses structural recursion (ADR-13) — a recursive call is accepted only if some argument position is a strict sub-term (by constructor depth) of the corresponding argument in the enclosing definition, exactly as exercised by append's xs vs. cons k x xs relationship (§8.11).

22.3 Deliverable

A pattern-match elaborator producing coverage-checked, termination-checked case trees, lowered into Elim applications the Phase 9 eliminators and Phase 2/5 kernel accept — with append itself as the flagship accepted fixture and the §8.12 non-covering/ non-terminating examples as the flagship rejected fixtures.

22.4 Acceptance Criteria

  • append (§8.11) elaborates and kernel-checks successfully, including the plus n m vs. plus (succ k) m index computation settling by NbE (I1, I2 exercised together on a realistic dependently-typed program for the first time).
  • 100% of conformance/non-covering/*.dep rejected with NonCovering, naming the missing constructor(s) (P12).
  • 100% of structurally-non-terminating fixtures rejected with NonTerminating, naming the argument position that failed to decrease.

22.5 Conformance Fixtures

pattern/vec-append.dep (the §8.11 flagship), non-covering/vec-missing-cons.dep (the §8.12 example), pattern/non-terminating-loop.dep (the §8.12 example), pattern/nested-match.dep (a match nested inside another match's method body).

22.6 Pitfalls

  • Index unification during "impossible clause" detection incorrectly deciding a genuinely reachable clause is impossible (a false-positive coverage gap that rejects a valid program), versus the opposite and more dangerous direction: deciding an actually-reachable clause is impossible and silently dropping it from the case tree (a coverage hole, T4).
  • Structural termination checking rejecting a genuinely terminating but not directly structurally-decreasing recursion (e.g. recursion through an accumulator or a helper function one level removed) — a completeness gap rather than a soundness one, but one that materially affects the ADR-13 rejected-alternative trigger condition (size-change termination, §37).
  • Nested matches accumulating coverage obligations incorrectly across levels, so an inner match's coverage is checked against the wrong ambient set of already-excluded constructors from the outer match.

22.7 Performance Concerns

Case-tree construction cost grows with the product of scrutinee count and constructor count per scrutinee; coverage checking's index-unification step reuses the Phase 6 unifier, so its cost is bounded by the same metavariable-scale ceilings (§4) even though pattern variables, not metavariables, are what is being unified here.

22.8 Edge Cases

A match with a single catch-all variable pattern (trivially covering, no splitting needed); a match on an inductive with zero constructors (a match with zero clauses is itself covering — the "absurd pattern" case); mutually recursive pattern-matching definitions (termination must be checked across the mutual group, not per-definition in isolation).

22.9 Failure Analysis

A coverage hole (T4) is the most dangerous failure class in this phase: it produces a partial function silently treated as total, which downstream can be applied to the missing case and reduce to a neutral NElim that never reduces further — not an immediate crash, but a soundness-adjacent gap that only the differential oracle (§28, Phase 11) reliably surfaces against Agda/Lean's own coverage checkers on shared fixtures.

22.10 Operational Notes

Track coverage-check and termination-check rejection counts and case-tree depth histograms; a definition whose case tree depth approaches the practical module-size ceiling (§31) is a signal worth surfacing to module authors before it becomes a performance problem.

23. Phase 11 — De-Bruijn-Criterion Re-Check, Differential Conformance Harness, and Performance Hardening

23.1 Objectives

Close the loop on I1 with an explicit, always-on kernel re-check of every elaborator output (not just as a test-suite property but as a production code path), stand up the differential conformance harness against Agda/Lean (§28), and perform the performance hardening pass (§30) needed to hit the full §4 constraint table under the accumulated load of Phases 0-10's feature set.

23.2 Detailed Implementation Steps

The re-check path is architecturally trivial by this phase — dtc-cli simply always calls dtc-kernel::check on dtc-elab's output, never on the elaborator's own belief about the term's type (P1, P8) — but this phase adds the fault-injection variant named in §7's invariant methodology: a deliberately mutated elaborator build that skips a subset of unification checks, run against the full conformance corpus to confirm the kernel's independent re-derivation actually catches every resulting ill-typed term (I1's detection path exercised under adversarial conditions, not just clean ones). Differential testing invokes Agda and/or Lean as external oracles on a shared definition corpus, comparing accept/reject verdicts (not internal representations). Performance hardening applies ADR-19's caching design (deferred until now precisely because caching correctness depends on every prior phase's context/signature shape being stable) and glued/lazy evaluation techniques from Kovács's smalltt (§5, §30).

23.3 Deliverable

A hardened dtc-cli meeting every §4 target under the full feature set, a differential-harness CI job comparing verdicts against Agda/Lean on a shared corpus, and a fault-injection test confirming I1's detection path fires correctly.

23.4 Acceptance Criteria

  • 100% verdict agreement with the Agda/Lean oracle across the shared differential corpus (≥ 500 definitions spanning well-typed and every rejected category from §8.12).
  • The fault-injected mutated-elaborator build produces zero silently-accepted ill-typed terms — every one is caught by the kernel re-check (I1 verified under adversarial conditions).
  • Full §4 constraint table met on the benchmark corpus, with conversion-check p99 latency specifically re-verified under the caching optimization (P11/ADR-19 — the optimization must not regress I9's equivalence-relation properties).

23.5 Conformance Fixtures

differential/shared-corpus/*.dep (mirrored against Agda/Lean equivalents), fault-injection/mutated-elaborator-skip-occurs-check.dep, fault-injection/mutated-elaborator-skip-positivity.dep, performance/cache-soundness-regression.dep (a fixture specifically designed to catch an ADR-19 cache-key omission).

23.6 Pitfalls

  • The differential harness comparing against a different theory variant of Agda/Lean (e.g. one with --type-in-type or a different universe policy enabled) than this project implements, producing spurious verdict mismatches that are theory-policy differences, not real bugs — the harness must pin oracle configuration explicitly.
  • Fault injection that is too easy to catch (skipping an entire check phase) giving false confidence, when the real risk (per T5, T6) is a subtler partial-correctness bug — the fault-injection corpus must include narrow, realistic mutations, not just wholesale check removal.
  • Performance-hardening's caching layer introducing exactly the ADR-19 soundness gap it was designed to avoid, if a later contributor extends the cache key set incompletely when a new context-affecting feature (e.g. a future universe-polymorphism extension) lands after this phase.

23.7 Performance Concerns

This phase is where the §30/§34 performance-engineering methodology is fully applied: glued evaluation (deferring unfolding of global definitions during conversion checking until forced), memoization keyed per ADR-19, and re-verification that these optimizations hold the §4 latency targets under the full Phase 0-10 feature set rather than under any single phase's narrower benchmark corpus.

23.8 Edge Cases

A differential-corpus definition that is valid in this project's theory but has no direct Agda/Lean equivalent (e.g. exercising a Phase-0-specific syntax choice) — must be excluded from the differential comparison explicitly, not silently skipped without record; a fault-injection run that happens to produce a term that is accidentally still well-typed despite the injected bug (the mutation didn't matter for that specific fixture) — must be distinguished from a genuine catch in the harness's reporting.

23.9 Failure Analysis

This phase's entire purpose is to be the backstop for every soundness risk enumerated in §24: any T1-T6-class bug that survived Phases 0-10 undetected is the target this phase's differential and fault-injection harnesses are built to catch before release. A failure to catch an injected fault here is treated as a blocking release issue, not a test flake.

23.10 Operational Notes

The differential-harness and fault-injection jobs become permanent CI gates (§29), not one-time Phase-11 activities; their pass/fail history is the primary soundness- confidence signal referenced in every subsequent release's changelog (§27).

26. Operational Readiness

Named metrics: definitions checked (count, rate), conversion-check time distribution (p50/p95/p99, per head-constructor kind, per §17.10), NbE normalization cost (steps per eval/quote call), metavariables solved vs. postponed vs. failed (§18.10, §19.10), universe-level depth histograms (§16.10), kernel re-check pass rate (should be exactly 100% outside fault injection, I1), and rejected-term reasons broken down by TypeError variant (P12).

Tracing: an elaboration trace — the sequence of implicit insertions, metavariable allocations, constraint solves/postponements, and the final kernel re-check verdict for a single declaration — is the key debugging artifact of the whole system; every declaration checked emits one, correlated by a per-declaration trace ID (ADR-22, tracing spans).

Structured logging follows ADR-15's diagnostic schema; every log line touching a rejection carries the TypeError variant as a structured field, never only free text.

Dashboards: throughput and latency against the §4 targets; rejection-reason distribution over time; fuel-exhaustion and coverage/termination/positivity-rejection rates; the differential-harness and fault-injection pass/fail history (§23.10).

Alerting philosophy: a kernel accepting an ill-typed term — found by the differential oracle or by the fault-injection harness failing to catch an injected bug — is a page-immediately soundness event (T1, T5, T6), on par with data corruption in a database, not a normal bug-tracker item. Latency-target misses and elevated rejection-reason rates are ticket-worthy, not page-worthy.

SLOs: kernel re-check pass rate = 100% (I1, hard SLO, any deviation outside fault injection pages); differential-harness verdict agreement ≥ 99.5% (allowing for theory-policy-difference exclusions per §23.8); p95 elaboration and conversion-check latency within §4 targets, tracked as a soft SLO with a ticket, not a page, on breach.

Named runbooks under docs/runbooks/: soundness-bug-response.md (the T1/T5/T6 page-immediately procedure), conversion-nontermination-triage.md (FM-2), universe- inconsistency.md (FM-3), elaboration-failure-debug.md (FM-6/FM-7, using the elaboration trace artifact above).

Backup/restore: Phase 0 is a stateless batch checker (no persistent mutable state to back up); the conformance/differential corpus and the trusted-kernel LOC budget are the artifacts under version control that matter operationally, both covered by ordinary repository backup.

Deployment topology: a single-binary CLI/library, no distributed components in Phase 0; canary/rollback is release-level (a new version is canaried against the differential corpus before promotion, and rollback is reverting to the prior signed release, ADR-26). Migration concerns are covered in §27.

27. Compatibility & Versioning

Core-term format versioning: dtc-core's serialized Term format (used only by dtc-conformance fixtures in Phase 0, not by any production persistence layer) carries an explicit schema-version tag; a version bump requires a migration adapter or an explicit breaking-change note.

Type-theory version: the set of typing rules the kernel implements (§8.3) is versioned as part of the crate's SemVer major component — adding impredicative Prop or universe polymorphism (§37) is a major-version change by definition, since it changes what the kernel accepts.

Surface-syntax stability: surface syntax (ADR-16) may evolve on a minor-version cadence; the elaborator's job is precisely to insulate the stable core theory from surface-syntax churn (P13).

Elaborator API stability: dtc-elab's public API (constraint types, metavariable handles) is explicitly not covered by the same stability guarantee as dtc-kernel's — the untrusted side is allowed to change faster, since no external soundness property depends on its interface shape (only on its output being independently re-checked).

Backward compatibility of accepted programs: a program accepted by version N must still be accepted by version N+1 within the same major version (no silent tightening of the theory on a minor bump); a major-version theory change (e.g. un-deferring impredicative Prop) may require migration but must not retroactively invalidate existing accepted programs without an explicit deprecation notice.

Deprecation: surface-syntax deprecations get one minor-version warning period before removal; core-theory deprecations (removing a rule) are major-version-only and require an entry in CHANGELOG.md naming the affected conformance fixtures.

28. Testing & Verification Strategy

Unit testing covers each named algorithm step in §8 in isolation (e.g. eval on a single beta-redex, one step of the positivity scan). Integration testing covers cross-component paths (surface syntax through elaboration through kernel acceptance).

Property testing, the defining properties: subject reduction — a well-typed term stays well-typed under reduction (property-tested by reducing accepted terms one step and re-checking, tied to I1/I2); type preservation and progress — every well-typed non-value term can step, and stepping preserves type (tied to §14, §15); conversion is an equivalence relation — reflexive, symmetric, transitive (I9, tied to §15); every elaborated term passes the kernel re-check (I1, tied to §19, §23); normalization is confluent and terminating on well-typed terms (I2, I6, tied to §13, §15).

The conformance corpus (§10 conformance/) of well-typed programs (all must be accepted) and ill-typed programs (all must be rejected with the specific expected TypeError variant) is a named CI gate (conformance-gate), failing the build on any single mismatch.

Differential testing against Agda and/or Lean on a shared definition corpus (§23) is a second, independently-required CI gate (differential-gate): same accept/reject verdict is the bar, not internal representation agreement.

Fuzzing targets the parser and the term deserializer as primary targets (T7, T8, ADR-24); a secondary fuzz mode generates random well-typed terms (by construction, via a typed term generator rather than free-form fuzzing) and checks kernel acceptance plus conversion reflexivity (I9) on the result.

Chaos/fault-injection: the mutated-elaborator fault-injection harness (§23) is this project's chaos-testing analogue — instead of injecting infrastructure failures, it injects specific soundness-relevant algorithmic faults and confirms the kernel catches them.

Deterministic replay: every elaboration trace (§26) is replayable — re-running the recorded metavariable-solve sequence against the same input must reproduce the same final term, a determinism property tested directly.

Soak testing: a 24-hour continuous run of the differential harness against a growing shared corpus, watching for latency drift or memory growth (§4's memory-per-module target) rather than for correctness regressions (those are caught by the gates above).

Fault injection and perf-regression gating: conversion-check p99 latency (§4, §30) is tracked per commit; a regression past the target threshold fails the perf-regression-gate CI stage, tied specifically to I2's decidability guarantee not degrading in practice even though it holds in theory.

Every property/fixture above is tied to a specific invariant (I#) and to the phase (§N.5) that introduced its fixture corpus, per the table embedded across §12-23.

29. Build & Release Engineering

Reproducible builds: pinned Rust toolchain version and a committed Cargo.lock (ADR-27), deterministic build flags, verified by rebuilding twice and comparing binary hashes as a release-gate check.

Artifact signing: releases are signed (Sigstore or equivalent, ADR-26) with an attached SBOM; signature verification is documented as a prerequisite for any downstream consumer embedding dtc-kernel as a library dependency.

Release channels: a stable channel gated by both the conformance and differential CI gates (§28), and a nightly channel gated only by the conformance gate (for faster iteration on non-kernel crates like dtc-cli or dtc-diagnostics).

CI/CD topology: lint (clippy --deny warnings, rustfmt --check) → unit tests → conformance-gate → differential-gate → fuzz-smoke (a bounded-time fuzz run, not the full continuous corpus) → perf-regression-gate → release packaging and signing.

Version stamping: every built artifact embeds the Git commit, the theory-rule-set version (§27), and the differential-oracle version it was last verified against.

Provenance/attestation: build provenance (SLSA-style attestation) is attached to signed releases, recording which CI run produced the artifact and which gates it passed.

Dependency auditing: cargo-deny runs in CI on every PR touching Cargo.toml, with a stricter policy (near-zero tolerance for new transitive dependencies) applied specifically to dtc-kernel/dtc-nbe's dependency graph, keeping the trusted kernel's dependency set minimal per I12 and ADR-08's LOC-budget spirit.

30. Performance Engineering

Methodology: the dominant performance decision in this whole system is NbE with closures versus naive substitution (ADR-03, ADR-04) — every other optimization is secondary to getting this right, because a naive-substitution conversion checker is exponential in the worst case regardless of any other tuning (§34). Conversion-check cost is the other central concern: eta-expansion-on-demand rather than eager (§15), sharing/memoization of normal forms with a soundness-audited cache key (ADR-19, P11), and glued/lazy evaluation (deferring global-definition unfolding until forced, as Lean 4 and Kovács's smalltt do — §23, §33) are the three levers applied, in that order, as performance needs surface phase by phase. Allocation is managed via arena-style construction for Term/Value variants; tail behavior on deep terms (long application spines, deep Vec-style recursive structures) is specifically benchmarked rather than assumed, given §21's observation that eliminator applications on large structures trigger proportionally many iota-rule reductions.

31. Scalability Analysis

What stays constant by design: the trusted kernel's size (I12, ADR-08's 3,000-LOC target) does not grow with module size or feature usage — this is a deliberate architectural invariant, not an emergent property. What grows with module size: elaboration time (roughly linear in declaration count, super-linear in metavariable interaction density — §18's O(n²) queue-rescan risk); NbE normalization cost (linear in term size under sharing via closures, but the underlying conversion-checking problem is not elementarily bounded in the worst case — say this precisely: conversion checking's worst-case cost is bounded only by the fuel ceiling, and pathological terms exist for which cost grows non-elementarily in term size before hitting that ceiling, exactly the decidability-vs-practical-cost distinction Abel et al. 2018 make explicit; the practical bound this project relies on is that real dependently-typed programs (as opposed to adversarially constructed ones) exhibit polynomial-in-practice behavior, which is why M10's real-fixture fuel-exhaustion target is 0 while the theoretical worst case remains unbounded-but-decidable).

Named bottlenecks: global-symbol lookup in the signature under large module counts (mitigated by content-addressed lookup, not a linear scan); the constraint-queue rescan cost in the elaborator (§18.7); repeated re-evaluation of shared sub-terms across independent conversion checks absent caching (mitigated by ADR-19).

The definitional-equality blow-up is the central scaling risk (§21.7, §34): deeply nested eliminator applications on large recursive structures can force proportionally many iota-rule reductions per conversion check. Mitigations: glued/lazy evaluation (unfold global definitions only when a comparison actually forces them), memoization with a soundness-audited cache key (ADR-19), and — as a last resort within Phase 0's scope — the fuel ceiling converting a would-be hang into a bounded, diagnosable rejection rather than unbounded resource consumption.

Practical module-size ceiling: ~10,000 definitions per module at the §4 memory target; beyond that, the levers are module partitioning (checking modules independently against a frozen upstream signature, not re-elaborating dependencies) and the caching layer's hit-rate improving with repeated-definition density — both deferred-scope concerns beyond Phase 0's single-module-at-a-time model but named here as the scaling path.

32. Mental Models & First Principles

MM1. In a dependent type checker, types and terms are the same syntactic category, so type checking must run the program — definitional equality is evaluation, which is why NbE is the engine of the whole system, not an optimization applied to it.

MM2. The kernel/elaborator split (the de Bruijn criterion) means you only have to trust a small checker — the clever, buggy elaborator can produce anything, and the worst it does is fail the check, never admit a false proof.

MM3. A dependent type checker is a proof checker, so a soundness bug does not crash — it silently accepts a proof of False, which is why the differential oracle matters more than any crash test (§23, §28).

MM4. Bidirectional typing exists because dependent types make "just infer everything" intractable and "just check everything against an annotation" unusably verbose — the infer/check split is the pragmatic middle that lets each syntactic form use whichever mode actually has enough information.

MM5. Universes are not bureaucracy — they exist because "the type of all types" is paradoxical (Girard), and a hierarchy with a strict successor rule is the simplest fix that still lets Type itself be a first-class type at some level.

MM6. Strict positivity and termination checking are the same idea applied to two different places: both exist to guarantee that recursion — over data (positivity) or over control flow (termination) — cannot be used to manufacture a value of an empty type, which is what "the logic is consistent" actually means operationally.

MM7. A metavariable is a promise, not a value — the elaborator's entire unification machinery exists to keep that promise before the kernel ever sees the term, because the kernel's grammar has no way to represent an unkept one.

MM8. Caching a normal form is caching an answer to a question that includes its context — forgetting that (omitting context/signature from the cache key) turns a performance optimization into a soundness bug, which is why ADR-19 treats the cache key as a correctness artifact, not a tuning parameter.

34. Back-of-Envelope Capacity Model

Kernel size. Target ≤ 3,000 LOC (§4, ADR-08) across dtc-kernel + dtc-nbe. Basis: Lean 4's kernel is reported in the low thousands of LOC; a Pi/Sigma/universe/inductive core with bidirectional checking, a conversion checker, and eliminator well-formedness checking is comparable in rule count, so 3,000 LOC is a realistic ceiling for an auditable trusted base of this scope, not an arbitrary round number.

NbE cost with vs. without sharing. For a term of size N with a beta-redex depth of d, naive substitution re-copies the substituted subterm at every reduction step: cost is O(N × k^d) in the worst case where k is the branching factor of substitution sites (the textbook exponential-blowup example is repeated self-application, e.g. Church-numeral- style doubling terms). With closures (ADR-04), each apply step is O(1) to build the new closure (no copying, only an environment-pointer extension); total cost across d reduction steps is O(N + d), linear rather than exponential — this is the concrete arithmetic behind ADR-03/ADR-05's rejection of naive substitution.

Conversion-check cost, common vs. pathological. Common case (real fixtures, §31): O(term size) per comparison, dominated by a single eval+structural-compare pass, sub-millisecond for the ≤ 200-node terms in the §4 p50 target. Pathological case: a term whose evaluation forces unfolding of k nested global definitions, each itself unfolding m sub-definitions, gives O(m^k) unfoldings absent glued evaluation — the fuel ceiling (1,000,000 steps) is the concrete number bounding this before it is classified as NonTermination rather than left unbounded.

Metavariable count, typical elaboration. A definition with p implicit-argument-taking function calls, each introducing on average 1-2 metavariables, yields roughly 1.5p live metas per definition; at the §4 target of ≤ 10 metas per definition, this bounds p to roughly 6-7 implicit-taking calls per definition in the typical case the elaboration- latency target (M5) is benchmarked against.

Memory per checked term. Each Term/Value node is roughly 48-64 bytes (a tagged union with boxed children, per §11's representation) on a 64-bit target; a 10,000- definition module averaging 50 nodes per definition is 500,000 nodes × ~56 bytes ≈ 28 MB for core terms alone, leaving headroom under the §4 50 MB target for normal-form cache entries and signature bookkeeping.

Universe-level arithmetic. With a practical ceiling of 32 explicit levels (§4) and a u32 internal representation, level-comparison cost is O(1) per check; the max i j computation in Pi/Sigma-formation is a single integer max, so universe bookkeeping is never the dominant cost anywhere in the system — it exists in this capacity model only to confirm it is not a bottleneck, in contrast to conversion checking.

Conformance-corpus check time. At the M1 throughput target (≥ 2,000 definitions/sec) and a 500-definition differential corpus (§23.4), full corpus checking takes ≤ 0.25 seconds of pure checking time; the M12 target of < 5 minutes wall-clock for the differential-harness run is therefore dominated by invoking the external Agda/Lean oracles, not by this project's own checker — a deliberate acknowledgment that the oracle round-trip, not the kernel, is the differential-gate's bottleneck.

35. Hard Questions (Self-Examination)

  1. If the elaborator and kernel disagree on whether a term type-checks, which one is "right," and how would you know without a third opinion? (§23, §28 — the differential oracle is the only independent third opinion available.)
  2. What stops someone from adding a "fast path" that skips the kernel re-check for "obviously fine" elaborator output? (§7 I7, §9 ADR-18 — the kernel API surface has no such entrypoint by construction.)
  3. Why is conversion checking allowed to be expensive in the worst case but never allowed to not terminate? (§4, §31, §34 — decidability is the guarantee; bounded worst-case cost is not, and the fuel ceiling converts unboundedness into a diagnosable rejection.)
  4. Could a bug in the positivity checker itself (not the inductive it's checking) be worse than a non-positive inductive slipping through undetected? (§20, §24 T3 — both are soundness bugs; the checker's own correctness is exactly as load-bearing as the property it enforces.)
  5. Why does universe cumulativity need to be a rule, not just "level inference always picks the maximum needed level"? (§8.6, §16 — without an explicit cumulativity rule, a term proven at level i could not be reused where level j > i is expected without re-elaborating it.)
  6. If the elaborator postpones a flex-flex constraint indefinitely, is that a bug or correct behavior? (§18 — correct behavior if it never becomes solvable and is reported as UnificationFailure; a bug only if the retry trigger fails to fire when it should become solvable.)
  7. Why is a coverage-checking false positive (rejecting a valid program) less dangerous than a false negative (accepting an invalid one), and does that asymmetry justify being conservative? (§22.6, §24 T4 — yes: a false positive is a usability bug, a false negative is a soundness bug; the design should bias toward rejecting when uncertain.)
  8. What would have to be true of a "clever" NbE optimization for it to be provably safe to add without re-running the full property-test suite? (§30, §34 — it would need to preserve I6/I9 by construction, which in practice means re-running the property suite is cheaper than proving safety abstractly.)
  9. Does the 3,000-LOC kernel budget (ADR-08) actually make the system more trustworthy, or just more auditable — are those the same thing? (§4, §24 T9 — auditable is a precondition for trustworthy, not a substitute; the budget is a proxy metric.)
  10. If the differential oracle (Agda/Lean) itself has a bug on a shared fixture, how would the harness distinguish "our bug" from "their bug"? (§23.6, §28 — it can't, by verdict comparison alone; a third independent check or manual proof would be needed, which is an acknowledged limit of the differential-testing approach.)
  11. Why does the elaborator need an occurs-check at all if the kernel will catch any resulting ill-typed term anyway? (§18, §24 T6 — a cyclic metavariable assignment can make the elaborator itself loop or produce an ill-formed (not just ill-typed) term the kernel's grammar cannot even represent, which is a different failure class than a caught type error.)
  12. Is structural termination checking (ADR-13) too conservative for real programs, and if so, what is the actual trigger for un-deferring size-change termination? (§22.6, §37 — the trigger is a measured rejection rate on real, hand-written fixtures that are termination-obviously-fine but structurally non-obvious.)
  13. Why does caching a normal form require including the signature version in the cache key, not just the term and context? (§9 ADR-19, §32 MM8 — a later declaration can change what a global reference unfolds to, so the same term/context pair can have a different normal form under a different signature.)
  14. What's the actual difference between "the kernel rejected a term" and "the kernel crashed while checking a term," and why does the fuel ceiling exist specifically to prevent the second from masquerading as neither? (§4, §7 I2 — a crash is undiagnosable; a bounded rejection with a specific reason code is always diagnosable, which is the entire point of the fuel mechanism.)
  15. If Phase 11's fault-injection harness passes (catches every injected bug), does that prove the kernel is sound, or only that it catches the specific bugs injected? (§23.6, §35.10-adjacent — only the latter; fault injection is evidence, not proof, which is why the differential oracle and property tests remain necessary complements, not redundant with fault injection.)
  16. Why is a Meta-free precondition (I8) enforced by both a runtime scan and a type-level exclusion from the kernel's API, rather than either alone? (§19.9 — the runtime scan catches ordinary bugs cheaply; the type-level exclusion is the structural backstop if the scan itself has a bug.)
  17. Given that inductive families and eliminator generation both land in Phase 8-9, could a bug in eliminator generation ever be indistinguishable from a bug in the positivity checker, from the outside? (§20-21 — yes in principle (both manifest as "this inductive behaves wrong"), which is why §21.4 requires the generated eliminator itself to independently pass kernel formation, isolating which component actually failed.)

36. Alternative Architectures (Roads Not Taken)

36.1 Conversion via Untyped Reduction to Normal Form (instead of NbE)

Term -> [untyped beta/iota reduction to normal form] -> compare syntactically (mod alpha)

Winning regime: a system where terms are guaranteed small and shallow by construction (no deep eliminator nesting), where materializing full normal forms is cheap. Real embodying system: early Coq kernel generations and simpler pedagogical checkers using plain reduction-to-normal-form rather than NbE. Why rejected here: untyped reduction to full normal form is harder to reason about for termination (no closure-based sharing argument, §34) and does not naturally support the eta-expansion-on-demand optimization NbE's value-level comparison gets for free (§15, §30) — this project needs the performance headroom for the eliminator-heavy Phase 8-10 workloads.

36.2 No-Separate-Kernel Design (Agda-style)

Surface -> Elaborator+Checker (single trust boundary, no independent re-check)

Winning regime: a long-lived, extensively-tested single implementation where the elaborator's own correctness has been validated over years by a large user base (substituting empirical confidence for structural guarantee). Real embodying system: Agda. Why rejected here: this project explicitly wants the de Bruijn criterion's structural soundness argument (P1, I1) rather than relying on accumulated empirical confidence, and a from-scratch project has none of that accumulated confidence to lean on yet.

36.3 Eliminator-Only / W-Type-Based Core (no native pattern matching)

Core = { Pi, Sigma, U, W (well-founded trees) }  // all inductives encoded via W-types
Surface pattern matches -> encode into W-elimination, no native Ctor/Ind/Elim forms

Winning regime: a metatheoretically minimal core valuing a small, uniform rule count over ergonomics — useful for metatheory papers proving properties about "the" core calculus. Real embodying system: this is the Coq-vs-Agda axis in miniature — Coq's kernel is closer to a small-rule-count core with inductives as a schema on top, while richer native-inductive-family systems (Agda) trade rule-count minimality for ergonomics. Why rejected here: W-type encoding of Vec-style indexed families is substantially more awkward to elaborate and to generate readable diagnostics for than native inductive families (ADR-11), and this project's god-bar target explicitly includes a real Vec/append worked example (§8.11) that benefits from native inductives' directness.

36.4 Proof-Assistant-with-Tactics Architecture (checking as one service under an interactive tactic engine)

+----------------------------------------------------+
|         Interactive Tactic Engine / REPL             |
|   (proof state, tactic combinators, backtracking)    |
+---------------------|--------------------------------+
                       v
              [ this project's kernel+elaborator, as one checking service ]

Winning regime: an interactive theorem-proving workflow where most user effort is spent inside partial proof states, not authoring complete terms up front. Real embodying system: Coq (Ltac/Ltac2), Lean 4's tactic framework. Why rejected here: Phase 0's scope is explicitly a batch checker (§1) — tactics are PhaseDeferred("Phase 13 — tactic engine") precisely because a tactic engine is a large, separable concern that should sit on top of a stable checked-term-producing core, not be built concurrently with it.

38. Glossary

Dependent type — a type that can mention (depend on) a term, e.g. Vec A n where n is a term. Pi type — the type of dependent functions, Π(x:A).B. Sigma type — the type of dependent pairs, Σ(x:A).B. Universe — a type whose elements are themselves types (Type_i). Universe hierarchy — the indexed family Type_0 : Type_1 : ... avoiding self-reference. Predicative — a universe hierarchy where each level's formation rule only quantifies over strictly smaller levels. Impredicative — a universe (commonly Prop) that may quantify over itself without paradox, due to proof irrelevance. Cumulativity — the rule that a term typed at level i is also typed at any level j ≥ i. Type-in-Type — the inconsistent rule Type : Type, the source of Girard's paradox. Inductive family — an inductively defined type indexed by other types/terms, e.g. Vec A n. Constructor — a primitive term-former for an inductive type. Eliminator (recursor) — the mechanically generated function that consumes an inductive value via one method per constructor. Strict positivity — the condition that an inductive type never occurs in a negative (contravariant) position in its own constructors' argument types. Definitional equality — equality of terms decided by computation/normalization, independent of any explicit proof term. Propositional equality — equality expressed as a term of an identity type, requiring an explicit proof. Conversion — the act of checking definitional equality, invoked by the Conversion typing rule. Normalization — reducing a term to a canonical form. Normal form — a term with no further reductions available. Beta reduction — the computation rule (λx.t) a ⟶ t[a/x]. Eta expansion — the rule identifying a function/pair with its fully-applied/projected expansion. Normalization by evaluation (NbE) — deciding normal forms by evaluating into a semantic domain and reading back, rather than by syntactic rewriting. Closure — a value pairing a term with the environment it should be evaluated in. Neutral term — a stuck computation headed by a variable or an unresolved elimination. Quote (readback) — converting a semantic value back into normal-form syntax. De Bruijn index — a variable representation counting binders inward from the term's own root. De Bruijn level — a variable representation counting binders outward from the empty context. Bidirectional typing — the discipline splitting typing into infer (synthesize a type) and check (verify against an expected type) judgements. Infer — the typing mode that synthesizes a term's type. Check — the typing mode that verifies a term against a given expected type. Elaboration — the process of turning surface syntax into a fully-elaborated core term. Metavariable — a placeholder standing for a not-yet-solved term, allocated during elaboration. Unification — the process of solving equality constraints between terms, possibly containing metavariables. Higher-order pattern unification — a decidable fragment of unification where metavariables are applied only to spines of distinct bound variables (Miller patterns). Implicit argument — a function argument the elaborator infers rather than the user writing explicitly. Coverage — the property that a pattern match handles every possible constructor case. Termination checking — verifying that a recursive definition cannot loop forever. Subject reduction — the property that a well-typed term remains well-typed after reduction. Progress — the property that a well-typed non-value term can always take a reduction step. Preservation — the property that reduction preserves typing (a synonym used alongside subject reduction). The de Bruijn criterion — the design rule that a small, independently-checkable kernel must re-verify anything a larger, untrusted component produces. Trusted kernel — the small component whose correctness the whole system's soundness depends on. Untrusted elaborator — the larger component whose bugs are caught, not assumed away, by the trusted kernel. Girard's paradox — the inconsistency that results from an impredicative Type : Type rule, allowing construction of a paradoxical term inhabiting every type. Signature (global environment) — the append-only registry of accepted declarations and inductive definitions. Spine — a list of arguments/eliminations applied in sequence to a neutral head. Fuel (reduction budget) — a bounded counter limiting reduction steps to convert a would-be non-termination into a diagnosable rejection. Occurs check — the check preventing a metavariable from being solved in terms of a term that contains itself. Case tree — the elaborated decision structure produced from a surface pattern match, prior to lowering into eliminator applications. Iota rule (computation rule) — the reduction rule specifying how an eliminator applied to a constructor reduces to the corresponding method.
