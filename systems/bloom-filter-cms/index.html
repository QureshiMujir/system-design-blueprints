In one paragraph

pdsr is a Rust library of probabilistic data structures, small summaries that answer "have I seen this?", "how often?", "how many different ones?" and "what is the median?" with a known error bound instead of an exact answer (§1, MM1). It covers three families, set membership (Bloom, cuckoo and xor filters), frequency estimation (Count-Min Sketch) and cardinality and quantiles (HyperLogLog, t-digest, KLL), behind one stable, checksummed file format shared by Rust, Python, JavaScript and C (§1, P4). The library does no I/O, so whoever embeds it in a cache, a storage engine or an analytics job owns every byte it touches (§4, §2). The goal is to own the hashes, the math and the format (§2).

The problem, concretely

Systems at the bottom of the stack have to decide something about "a billion or a trillion items" while spending only a single-digit number of bits on each (§2). The blueprint's lead example is an LSM-tree storage engine (a database that keeps sorted files on disk). A Bloom filter attached to each file turns "this key may not be here" into "this key is definitely not here, do not read the disk" (§2). At a 1% error rate the filter costs 9.59 bits per item (§36 item 1).

The first naive route is to take a library and trust that its error bound matches the paper. §2 lists how that goes wrong in practice: counting filters whose counters overflow silently and start returning false negatives, HyperLogLog implementations that pick the wrong low-count correction and underestimate, Count-Min Sketches that share one seed across all rows and lose their independence guarantee, and cuckoo filters that loop forever when no slot is free (§2). The design answers each with a rule: saturation is observable (P12, I8), the HLL correction is always on (I10), row seeds are engineered to be independent (P3), and failure is a typed error, never a fallback (P6).

The second naive route is a plain Bloom filter, which has a speed problem. It touches about 7 separate cache lines per lookup at 1% error (§36 item 2). At roughly 80 ns per memory miss that is a worst case of 7 x 80 = 560 ns (§36 item 3), against a target of 10 ns median for a design that touches one line (§4). A third trap is treating the error rate as a constant: it rises with load, so fpr() reports the real rate from the bit population instead of the design rate (MM2, P14, §14.2).

How it works, end to end

Follow one insert and one later contains through the boxes of §3's diagram, drawn here and coloured by role:

  1. Bindings. pdsr-py, pdsr-wasm, pdsr-cffi and pdsr-cli own marshalling and ownership only, and the algorithms live once in core (§3, P9). A bad argument raises a typed error and never corrupts a sketch (§26).
  2. Construction. bloom::Classic::sized_for(n, f) takes the quality target and computes the parameters itself (P1). For n = 10,000 and f = 0.01 it computes m = 95,851 bits and k = 7 (§8).
  3. Insert. The Hasher in hash/xxhash3.rs hashes b"alice" once into 128 bits (§8, §14.2, ADR-02). hash/combinator.rs turns that into 7 bit indices (§8, §13.2). Those 7 bits are set (§8).
  4. Lookup. contains(b"alice") is true only if all 7 bits are set. For a never-inserted key like b"mallory" it is true only if all 7 happen to be set by other items, with probability about f (§8).
  5. The other families. cuckoo/, quotient/ and xor/ do membership, cms/ frequency, hll/ cardinality and quantile/ quantiles; each implements at least one trait, and Mergeable where the algebra allows it (§3, §10).
  6. Serialize. serde/frame.rs writes PDSR | v=1 | kind | flags | body_len | body | crc32c (§8).
  7. Reload. from_bytes verifies the CRC first, then rebuilds a bit-identical filter (§8, I4, I5, I13).
  8. Verify. conformance/runner.rs writes conformance.report.json, and a Pass-to-Fail regression blocks merge (§10, §30).

The core ideas

A Bloom filter: a bit array and k probes (§8, §14, I1, I2)

A Bloom filter is an array of m bits plus a rule that maps each item to k positions. Insert sets those k bits, and lookup asks whether all k are set (§14.2). It can say "yes" wrongly, but it never says "no" for an inserted item (I1). The blueprint sizes it with m = ⌈−n·ln f / (ln 2)²⌉ and k = round((m/n)·ln 2) (§2, §14.2). The "false positive rate" fpr actually reached is about (1−e^(−kn/m))^k, which is why it rises quickly past the design item count (MM2).

n (items) f (target) m (bits) k bits per item
1,000 0.01 9,586 7 9.59
10,000 0.01 95,851 7 9.59
1,000,000 0.01 9,585,059 7 9.59
1,000,000 0.001 14,377,588 10 14.38
1,000,000 0.0001 19,170,117 13 19.17

All rows are from §36's sizing table. Two rules keep the filter honest. The fpr() call reads the actual bit population, so a filter past its design size reports the higher real rate (P14, §14.2). Two filters merge by bitwise OR only when (m, k, hasher, seed) all match (§14.2, I7).

The counting Bloom variant replaces each bit with a small saturating counter so that items can be deleted (§14.2). One slot with a 4-bit counter behaves like this (§8):

Slot value Operation Next Note
0 insert 1 slot now occupied
1 to 14 insert +1 normal
15 insert 15 saturated (I8) and permanently set
15 delete 15 cannot un-saturate, so a false-negative risk is documented
0 delete 0 underflow is a no-op

Delete is not the inverse of insert: insert twice, delete once, and the item still reports present (§14.6, §8).

Many hashes from one: double hashing and independent seeds (§13, P3, ADR-03, I3)

A filter with k = 7 needs 7 indices per item. Double hashing (Kirsch-Mitzenmacher) hashes once and builds the i-th index as (h1 + i·h2) mod m, where h1 and h2 are the high and low 64 bits of one 128-bit hash (§13.2, §13.6, §11.1), which saves k−2 hash calls (ADR-03). h2 is forced odd on every call so that it is never 0 and, for a power-of-two m, the walk can reach every position (§13.6, §13.8, §11.1).

The independence of the rows is what the error bound is built on, so it is engineered and not assumed. The two seeds come from the sketch's salt through a key-derivation function, in the form blake3(seed‖i), and not from seed ^ i or seed + i, which ADR-23 rejects outside a throwaway demo (P3, ADR-23). The blueprint calls seeds[i] = seed ^ i a known-bad pattern for Count-Min rows, because correlated rows destroy the multiplied-out confidence while every unit test still passes (§19.6, MM3).

Blocked Bloom: spend bits, buy cache locality (§15, ADR-04, MM4)

At these sizes memory access time dominates, not arithmetic (MM4). The blocked Bloom filter picks one 64-byte block (one cache line) from the hash, then sets and tests k_per_block bits (typically 8) inside that block only (§15.2, ADR-04). The price is accuracy and space. The target error rate is inflated by about 10% relative, and the filter needs about 16.4 bits per item at f = 0.01, against 9.59 for the classical one (§15.1, §36 sizing tables). The payoff is a 2 to 3 times throughput gain (MM4). A subtle failure is uneven block occupancy, where one hot block has a high local error rate while the overall fpr() looks fine. A block_max_load() diagnostic exists for this (§15.8, §15.9).

Count-Min Sketch and conservative update (§19, ADR-07)

A Count-Min Sketch (CMS) is a table of d rows by w counters. To add an item, hash it once, derive d column positions with the combinator, and add the count to one counter per row, using a saturating add (§19.2). To estimate, read the same d counters and return the minimum (§19.1, §19.2). The size comes from the accuracy you want: w = ⌈e/eps⌉ and d = ⌈ln(1/delta)⌉. For eps = 0.001 and delta = 0.001 that is w = 2,719 and d = 7, a table of 2,719 x 7 x 4 bytes, about 76 KiB (§36 item 9).

Conservative update is the default. It first finds the row-minimum, then raises only the cells equal to that minimum, to min + count. That reduces overestimation but loses exact additive merging, so a CMS-CU merge is a per-cell max and only approximate (§19.2, P5, FM-8). Two companions find the most frequent items. Misra-Gries keeps at most k counters, and when a new key arrives with no free counter it decrements them all (§20.2). Top-k pairs a CMS-CU with a size-k min-heap (§20.2).

HyperLogLog: counting distinct items from leading zeros (§21, I9, I10)

HyperLogLog (HLL) counts distinct items in memory that does not grow with the count. Each item hashes to 64 bits. The first p bits pick one of 2^p registers, and the register keeps the largest leading-zero count (plus one) seen in the remaining bits (§21.2). The estimate is a harmonic mean over the registers, with a small-range correction that is always on (§21.2, I10). Without that correction the blueprint says the sketch badly underestimates when the count is below about m/2.5 (§21.6, I10). The precision p is limited to [4, 18] with a default of 14 (I9, ADR-08). The standard error is 1.04/√m, for example 0.8125% at p = 14, which uses 2^14 registers (§36 item 7, §36 HLL table). HLL++ keeps a short explicit list while few items have been seen (sparse), then switches to the register array (dense), and uses published bias-correction tables copied verbatim (§21.2, §21.6). Merging two HLLs takes the register-wise maximum, and only when (p, hasher, seed) match (§21.2).

Mergeability and the on-disk frame (§23, P4, P5, I5, I7)

A sketch is mergeable only if its algebra allows it, and under stated parameter equality (P5, MM8). Bloom merges by OR, CMS by element-wise sum, HLL by register-max, KLL and t-digest are mergeable, and Greenwald-Khanna is not, so its merge returns a typed error (§33, §22.2, FM-11). Merging unequal sketches returns Error::Incompatible (I7).

Every sketch is saved in the same frame, all fields little-endian (§23.2):

Field Size Content
magic 4 B PDSR
version 1 B 1
kind 1 B which sketch
flags 2 B sub-type, for example CMS vs CMS-CU
body_len 8 B length of the body
body body_len per-sketch layout
crc32c 4 B CRC over every earlier byte

A reader bounds every length and verifies the CRC before trusting any body field (§23.2, I5, I6). The failures are named: BadMagic, UnsupportedVersion, Truncated, TooLarge and Corrupt, and none allocates before validation (§8). Same seed plus same insert order gives bit-identical bytes (I13, P7).

The trade-offs — where engineers disagree

Default hash: xxhash3 (ADR-02)

Chosen: xxhash3 at 128 bits, the fastest non-cryptographic option with documented avalanche (§9). Rejected: wyhash, murmur3, SipHash and Blake3 (§9). When the rejected choice is right: wyhash for keys of 8 bytes or less, and SipHash under adversarial inputs (§9). The rubric lists xxhash3 near 5 GB/s on 64-byte input and SipHash-1-3 near 1 GB/s, with xxhash3 vulnerable to adversarial input and SipHash resistant, so SipHash is the opt-in keyed path (§36, T5).

Deriving k indices: Kirsch-Mitzenmacher (ADR-03)

Chosen: double hashing, which saves k−2 hash calls at no false-positive cost (§9). Rejected: k independent hashes, or enhanced double hashing (§9). When the rejected choice is right: true independent hashing, if a future adversary model defeats double hashing (§9).

Blocked-Bloom block size: 64 bytes (ADR-04)

Chosen: 64 bytes, one cache line on x86 and aarch64 (§9). Rejected: blocks of 32, 128 or 256 bytes (§9). When the rejected choice is right: 128 bytes on POWER9 or future CPUs with 128-byte lines (§9).

Xor and fuse construction retries: 256 seeds (ADR-06)

Chosen: retry construction with a new seed up to 256 times, then return a typed error (§9, §4). More than 8 retries is empirically rare, and 256 is the safety net (§9, §18.2). Rejected: a cap of 8 or 32, or unbounded retries (§9). When the rejected choice is right: unbounded retry for offline batch builds where failure is not acceptable (§9). A failure never returns a partial filter (§8).

Default frequency sketch: CMS with conservative update (ADR-07)

Chosen: CMS-CU, which dominates the vanilla CMS for the same (w, d) (§9). Rejected: vanilla CMS and count-sketch (§9). When the rejected choice is right: vanilla CMS when exact linear mergeability is required (§9). That is the price named in FM-8 (§27).

Compatibility target: answer-parity, not byte-parity (ADR-20)

Chosen: assert that answers agree with Apache DataSketches within each error bound, and own the file format (§9, §38 A2). Rejected: a byte-compatible format, or no cross-check (§9). When the rejected choice is right: byte-compatibility, if drop-in replacement of DataSketches is the goal (§9). Matching its bytes would tie every sketch to its evolving format and forbid the CRC32C trailer and the KM seed design (§38 A2).

Roads not taken (§38, §39)

A server that owns the sketches (A1, the RedisBloom shape) wins when many processes and languages must share sketches over the network and persist them with an existing datastore. It loses here because a network hop would dominate a 10 ns blocked-Bloom lookup (§38, §36 item 4).

A byte-compatible DataSketches clone (A2) wins when you must replace it in a pipeline without re-serializing existing sketches. It loses here because the library wants its own CRC trailer and seed design (§38, ADR-20).

A generic monoid framework (A3, the Algebird shape) wins for compositional stream processing in Spark-like pipelines. It loses here because one trait erases the per-sketch merge preconditions that Mergeable makes typed errors (§38, P5, I7).

A single-family library (A4, the Guava shape) wins when an application needs exactly one well-tested Bloom filter. It loses here because the project's aim is to teach the full surface (§38, §2).

Deferred features (§39) each wait for a trigger: JVM bindings for DataSketches dogfooding, a constant-time contains if the timing side channel T10 enters scope, rotating sketches for time windows, a gRPC federation layer for cross-node shipping, GPU sketches above one billion batched lookups, and streaming xor construction if the 5x construction-memory peak blocks a large build (§39).

What must never be false

  • I1: an inserted item always reports present in Bloom, blocked, scalable and partitioned filters. Noticed by insert-then-contains over a corpus; counter pdsr_bloom_inserts_total (§7).
  • I2: real error rate is at most 1.5 times the documented rate at the design item count. Noticed by conformance fpr bands per (n, f); gauge pdsr_bloom_fpr_estimate (§7).
  • I3: the k hash indices do not correlate across rows. Noticed by a property test of row correlation under a fixed seed (§7).
  • I4: on-disk bytes are little-endian and identical across hosts and languages. Noticed by cross-language round-trip conformance (§7).
  • I5: a file body is trusted only after its CRC32C verifies. Noticed by a fuzz target on the deserializer (§7).
  • I6: loading never allocates more than a bound derived from body_len. Noticed by fuzzing and a max-allocation assertion (§7).
  • I7: two sketches merge only if their structural parameters are equal. Noticed by a property test that a mismatched merge errors (§7).
  • I8: a counter at its maximum stays there and is observable. Noticed by a soak test, an is_saturated() query and a pdsr_*_saturated gauge (§7).
  • I9: an HLL has exactly 2^p registers with p in [4, 18]. Noticed by a unit test on the bounds (§7).
  • I10: HLL never underestimates at low counts. Noticed by conformance at n = 1, 10 and 100; gauge pdsr_hll_cardinality_estimate (§7).
  • I11 and I12: a cuckoo fingerprint of 0 is reserved as the empty marker, and xor and fuse filters never change after construction. Noticed by a zero-fingerprint unit test and by the type having no insert (§7).
  • I13: same seed and same insertion order give bit-identical bytes. Noticed by a determinism conformance check (§7).
  • I14: a sizing request over the memory cap returns a typed error, not an allocation. Noticed by a unit test at n = u64::MAX (§7).

What breaks in production

The blueprint labels failure modes F1 to F13 in §27. This explainer writes them FM-1 to FM-13.

FM-1: error rate above design after overload. Symptom: the fpr() diagnostic reports more than the target. Cause: sustained insertion past the design item count (§14.9, MM2). A classical Bloom has no in-place resize, so recovery is a fresh sized_for at the new load, or compact() for a scalable filter (§14.9, §27). False negatives never appear, since I1 holds regardless of load (§14.9).

FM-2: counting-Bloom saturation. Symptom: false negatives (§27). Cause: a counter reached its maximum and stopped counting, a cliff rather than a slope (§8, MM6). Detection: is_saturated() (§27). Recovery: a wider counter (8 or 16 bits) or a lower load (ADR-21, §27).

FM-4: cuckoo Error::Full. Symptom: an insert fails. Cause: 500 evictions failed to find a slot, which can come from a pathological insert order (ADR-05, T7). The filter stays consistent and earlier items stay queryable (§8). Recovery: resize or raise MAX_KICKS, and the caller decides (§27).

FM-6: xor or fuse construction failure. Symptom: from_iter returns an error after 256 seeds. Cause: peeling found no valid order, as with an adversarial set (§27, T8). No partial filter is returned (§8). Recovery: a different input order or a smaller block length (§27).

FM-7: CMS counter saturation. Symptom: estimates freeze for the keys that share a saturated cell, hidden for months if unobserved (§19.9, P12). Cause: a counter stuck at u32::MAX (§19.6, §27). Detection: is_saturated(). Recovery: widen to u64 or rotate the sketch (§27, I8).

FM-8: CMS-CU merge is only approximate. Symptom: a merged result differs from a sketch built over the combined stream, within a band (§19.5). Cause: the conservative update breaks additivity (§19.2). It is documented in the Mergeable impl, and exact merging means using vanilla CMS (§27, P5).

FM-10: wrong t-digest quantiles after a naive merge. Symptom: quantile drift against what is expected, though each shard alone is correct (§37). Cause: a naive merge or concatenation (§27, §37). Recovery: compact() re-sorts and re-merges the centroids (§22.2, §27).

Threats worth knowing (§26):

  • T2, unbounded allocation from a fake body_len, is stopped by length-checking every allocation against the file size and the memory cap (I6).
  • T5, an adversary choosing keys to inflate error, is met by the opt-in SipHash13 keyed constructor; the default hashes are vulnerable (§36 hash rubric, §13.2).
  • T6, resource exhaustion with a request like sized_for(u64::MAX, 1e-30), is met by the memory cap and a typed error (I14, §4).
  • T10, a timing side channel that leaks filter contents, is documented and not fixed. The constant-time contains is deferred (§26, §39).

Where the blueprint disagrees with itself, both sides are given and left unresolved:

  • The 1M-item Bloom size. §4 and §36 item 1 say about 1.17 MiB, and item 1 says this matches the sizing table, which lists 1170.0 KiB for the same row (§4, §36 item 1, §36 sizing table).
  • HLL p = 14 memory. §4 and §36 item 6 count 6-bit registers (12 KiB packed), while §23.2 stores registers: 2^p B and the §36 table lists 16384 bytes (§4, §23.2, §36).
  • What goes wrong without the HLL correction. I10 and §21.9 say about 50% underestimate for n below m/2.5, while §21.6 says the estimate is 0, as §37 question 10 also assumes (I10, §21.9, §21.6, §37).
  • When p must exceed 14. §36 item 8 derives p ≥ 14 for 1% error from 1.04/√(2^p), and the §36 HLL table gives 0.8125% at p = 14, yet §33 and item 8 say 600 million distinct items needs p ≥ 16, and ADR-08 picks p = 16 to 18 above 600 million (§33, §36 item 8, §36 HLL table, ADR-08).
  • Cuckoo space. §36 item 11 gives about 12.6 bits of fingerprint and 33.7 bits per item in total, against Bloom's 9.59 as the space cost of delete support, while the note under the cuckoo table calls 33.7 bits per item close to the Bloom equivalent for f ≈ 0.0024 (§36 item 11, §36 cuckoo table).
  • Xor against cuckoo. §36 item 12 and §18.1 call xor8 tighter-fpr than cuckoo, with xor8 at f ≈ 0.0039, while ADR-05 gives cuckoo f ≈ 0.0024 (§36 item 12, §18.1, ADR-05).

How it compares

  • RedisBloom lives inside Redis as a server-side module, so its sketches are reachable over the network and saved with the database. That is right when you already run Redis and want sketches without a separate service, a niche pdsr does not target (§35).
  • Google Guava BloomFilter chose immutability and JVM-native serialization, with one well-tested Bloom filter. That is right for a JVM application that needs exactly that with no configuration, since it deliberately ships no cuckoo, CMS or HLL (§35).
  • Apache DataSketches chose rigorously analysed sketch families and a portable binary format. That is right for large analytics systems where answer-parity across Java, C++ and Python is the requirement, which is why pdsr checks parity against it and does not compete on it (§35, ADR-20).
  • Cassandra Bloom filters chose per-SSTable, on-disk filters tuned to one job: skipping a disk read. That is right inside a storage engine where the filter sits next to the data block, a pattern pdsr shows in examples/lsm-block-filter.rs and does not embed (§35).

Building it — the phase plan

There are 14 phases, 0 to 13, with week labels from Appendix B (§42). Build card: blueprints/build-cards/Bloom-Filter-CMS.md. The critical path puts classical Bloom, classical CMS, HLL and the on-disk format ahead of xor and quantiles (§42).

§1 describes a 2-to-3-week "Phase-0 drop" that ships the hash layer, classical Bloom, CMS, HLL, the format, the PyO3 binding and the conformance suite, while §12's Phase 0 (week 1) is scaffolding and a smoke test (§1, §12, §42). Both are stated, unresolved.

Questions to test yourself

  1. Why does the blocked Bloom use more bits per item than the classical Bloom yet ship as the recommended filter? — Hint: §15, MM4 and the two sizing tables in §36.
  2. Why is seeds[i] = seed ^ i catastrophic for CMS but the analogous KM h2 for Bloom is fine? — Hint: P3, §13.6 and §19.6.
  3. Why is CMS-CU the default frequency sketch despite not being exactly mergeable, and when would you override the default? — Hint: ADR-07, §19.2 and FM-8.
  4. The HLL estimate is 0 for a stream of 50 distinct items at p=14. What is broken? — Hint: §21.6 and I10.
  5. Why does the on-disk format put the CRC32C in a trailer rather than a header, and what would break if a reader trusted body fields before the trailer? — Hint: §23.2, I5 and T3.

If you only remember three things

Every answer is an estimate whose error depends on load, size and hash independence, so the sizing math belongs to the library and the real rate is always reported (P1, P14, MM2, MM3). Anything that could silently go wrong, such as a saturated counter, a full cuckoo table or a failed xor build, is a visible flag or a typed error and never a quiet fallback (P6, P12, I8). A sketch merges only when its algebra and parameters allow it, and every byte loaded from disk is hostile until its length and CRC check out (P5, I7, I5, MM7).

Words used here

  • fpr: the chance a membership filter says "present" for something never inserted (§40).
  • False negative: saying "absent" for an item that was inserted; Bloom variants never do, apart from counter saturation (I1, I8).
  • Bloom filter: a bit array plus k probes per item, sized for a target error rate (§14.2, §40).
  • Cache line: the 64-byte chunk the CPU fetches at once; blocked Bloom confines each item to one (§15.1).
  • Double hashing: building k indices from two hash halves as h1 + i·h2 (§40, ADR-03).
  • Saturation: a counter stuck at its maximum, which stops counting (I8, MM6).
  • CMS (Count-Min Sketch): d rows by w counters, estimated by the row minimum (§19.1, §40).
  • Conservative update: raise only the minimum cells; less overestimate, approximate merge (§40, §19.2).
  • Register: an HLL slot that stores a leading-zero count; there are 2^p of them (§40).
  • Small-range correction: the HLL fix that stops underestimating at low counts (I10, §40).
  • Mergeable: the trait that exists only where combining two sketches is algebraically valid (§40, P5).
  • Frame: the on-disk envelope of magic, version, kind, flags, length, body and CRC (§40, §23.2).
