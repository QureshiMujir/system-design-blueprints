70 — Bloom Filter + Count-Min Sketch

Project Number: 70

Project Name: Bloom Filter + Count-Min Sketch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a single Rust library, pdsr (probabilistic data structures, Rust), that implements the three families of probabilistic data structures that production systems actually deploy and that are usable from Rust, Python, JavaScript, and any C-ABI host through one stable on-disk format.

  • Family one — approximate set membership: classical Bloom (Bloom 1970), counting Bloom, scalable Bloom (Almeida et al. 2007), partitioned Bloom (Kirsch and Mitzenmacher), blocked Bloom (Putze et al. 2007), cuckoo filter (Fan et al. 2014), quotient filter, vacuum filter, xor filter (Graf and Lemire 2019), binary fuse filter.
  • Family two — frequency estimation: classical Count-Min Sketch (Cormode and Muthukrishnan 2005), CMS with conservative update, count-sketch (Charikar et al. 2002), AMS sketch, Misra-Gries heavy-hitter, CMS+top-k augmentation.
  • Family three — cardinality and quantiles: HyperLogLog (Flajolet et al. 2007), HLL++ (Heule et al. 2013), t-digest, KLL sketch, q-digest, Greenwald-Khanna sketch.

In scope. The hash primitive layer (locked choice + documented independence story); the math (capacity calculators that round-trip with the configured false-positive rate); the on-disk format (version field, stable layout, cross-language fixtures); the merge / union / intersection / difference operators where the algebra defines them; PyO3, WASM, and C-ABI bindings; a CLI; a conformance suite gating release.

Out of scope. Learned indexes; RSA-accumulator variants; every literature variant without a deployed citation; GPU sketches, mmap-update-in-place sketches, gRPC federation (all Deferred — see Deferred Features Register). The tight focus is the only reason the timeline is 8–12 weeks rather than 8–12 quarters.

Estimated time. 8–12 weeks for the full plan; 2–3 weeks for a Phase-0 drop that ships the hash primitive layer, the classical Bloom filter, the classical Count-Min Sketch, HyperLogLog, the stable on-disk serialization format, the PyO3 binding, and the conformance suite.

Recommended language. Rust 1.75+ for the core. PyO3 for Python. wasm-bindgen for JavaScript. cbindgen-generated pdsr.h for the C-ABI. Java is a JNI shim around the C-ABI (Deferred). The CLI is a thin Rust binary (pdsr-cli) wrapping the library.

Prerequisites. A working memory model for hash-based data structures (what a "hash collision" is and why birthday bounds matter); enough Rust to read unsafe, MaybeUninit, repr(C), and #[inline(always)]; comfort with bit manipulation (leading_zeros, trailing_zeros, popcount, rotate ops); probability at the level of "I can evaluate (1 − 1/m)^(kn) and explain why it is the false-positive rate of a Bloom filter."

2. Why Build This

Probabilistic data structures live at the bottom of every system that has to make a decision about a billion or a trillion items in a single-digit number of bits each. Cache admission policies use them (W-TinyLFU in Caffeine). LSM-tree storage engines embed them in every block (an SSTable Bloom filter turns "this key may not be here" into "this key is definitely not here, do not read the disk"). Distributed key-value stores use them for read-repair anti-entropy (Cassandra, Riak). Rate limiters use them for heavy-hitter detection (which keys are responsible for the top 1% of traffic). Streaming analytics platforms use them for cardinality counting and quantile estimation (Druid's HLL columns; ClickHouse's quantileTDigest).

The problem is that almost every team that ships these in production does so by reaching for an off-the-shelf library and trusting that the false-positive bound matches the paper, that the merge operator is associative and commutative, that the on-disk format is stable across language runtimes, and that the hash function the author chose is independent enough not to undermine the math. Sometimes the trust is well-placed; very often it is not. There is a long history of subtle bugs in this surface area: counting Bloom filters that overflow their counters silently and start returning false negatives; HyperLogLog implementations that pick the wrong small-range correction and underestimate cardinality at low n; CMS implementations that share a single seed across all hash rows and lose their independence guarantee; cuckoo filter implementations that do not handle the "no slot available after N evictions" failure mode and instead loop forever or panic.

The teams that own their probabilistic data structures from the hash primitive up are the teams who can debug those failures in their own source. This project is the smallest library that still teaches the full surface. It owns the hash primitives, the math, the on-disk format, and the merge operators. By the end of the phase plan you can open src/bloom/blocked.rs and read the SIMD'd Putze et al. 2007 algorithm; src/cms/conservative.rs and read the Estan and Varghese 2002 conservative-update rule; src/hll/plus.rs and read HLL++ with the sparse / dense representations and the bias-correction tables at exactly the precisions Heule et al. 2013 specify.

What Mastery Looks Like

  • You can derive the Bloom sizing closed-form m = ⌈−n·ln f / (ln 2)²⌉, k = round((m/n)·ln 2) from first principles and explain why violating it inflates fpr — Phase 2 (§14).
  • You can explain why the Kirsch-Mitzenmacher combinator costs no fpr and where its h2-odd requirement matters — Phase 1 (§13) and §6 P3.
  • You can predict the blocked-Bloom ~10% relative fpr penalty and the ~2–3× throughput win from cache-line locality before measuring — Phase 3 (§15).
  • You can state, for any pair of sketches, whether they are mergeable and under what parameter-equality precondition the algebra holds — §6 P5, §7 I7, Phase 7 (§19).
  • You can read a .pdsr file's frame header by hand and verify its CRC32C — Phase 11 (§23).
  • You can name the small-range correction that stops HLL underestimating at low n and quantify the ~50% error without it — Phase 9 (§21).
  • You can decide xor-vs-cuckoo-vs-Bloom for a static-vs-mutable, space-vs-throughput workload and justify it against the capacity model — Back-of-Envelope Capacity Model.

Bindings. PyO3, WASM, and C-ABI shims. They own marshalling and ownership semantics only; the algorithms live exactly once in core. Java is a JNI shim around the C-ABI, Deferred.

Public Rust API. The user-facing surface: one module per sketch family, each concrete sketch a type that implements at least one of the four sketch traits and (where the algebra holds) Mergeable.

Sketch traits. ApproxMembership, FrequencyEstimator, Cardinality, Quantile, Mergeable. Every concrete sketch implements at least one. Benchmarks and conformance code program against the traits, not the concrete types.

Serialization. Owned by the core, not by each sketch. Sketches expose a single Serialize/Deserialize pair; the format carries magic + version + CRC32C trailer and is little-endian regardless of host. The on-disk bytes are stable across language runtimes.

Hash primitive layer. The only place that chooses a hash function. Sketches accept a Hasher type parameter so benchmarks and conformance can swap hashes without touching sketch code. The double-hashing combinator and SIMD batch path live here.

6. Design Principles

Each principle: the rule, the tradeoff, and how violating it breaks the system. Enforced at the type level where possible, by code review where not.

  • P1 — Math is owned by the library, not the caller. Every sketch has a constructor taking the quality budget (fpr, relative error, confidence) and computing parameters; plus a "by-parameters" constructor for advanced users. Tradeoff: two constructors per type. Violation: callers guess (m, k), ship a filter whose real fpr is 10× the intended one, and discover it in production.
  • P2 — One hash family per sketch type. xxhash3 default; wyhash alt for ≤8-byte keys; murmur3-128 legacy only; SipHash opt-in adversarial. Tradeoff: less hashing flexibility. Violation: mixing hashes across rows breaks independence and inflates fpr/overestimate.
  • P3 — Independence is engineered, not assumed. k independent hashes via the Kirsch-Mitzenmacher combinator with two seeds derived from the sketch salt through a KDF, not from i/i+1. Tradeoff: a KDF call at construction. Violation: correlated rows collapse the d-fold confidence and the empirical error blows past the bound.
  • P4 — The on-disk format is the contract. Every sketch has a stable encoding: magic, version, length-prefixed body, CRC32C trailer, little-endian regardless of host, no pointers. Tradeoff: explicit (de)serialization per sketch. Violation: a big-endian host silently writes incompatible files; a missing CRC lets a corrupt body return garbage.
  • P5 — Mergeability is explicit. A sketch is Mergeable iff the algebra makes it so, under stated parameter equality. Tradeoff: some sketches (GK) refuse merge. Violation: merging incompatible sketches silently yields a wrong answer no one can detect.
  • P6 — No silent fallbacks. Cuckoo full after MAX_KICKS, counting-Bloom counter overflow, xor construction failure after MAX_TRIES → typed error. Tradeoff: callers handle errors. Violation: "best-effort" success masks a filter that is now lying.
  • P7 — Determinism is the default. Same seed + same insertion sequence → bit-identical on-disk bytes, even where order matters (cuckoo eviction, xor rejection) because the seed governs the random walk. Tradeoff: no wall-clock or thread-id entropy. Violation: non-reproducible fixtures make cross-language conformance impossible.
  • P8 — The capacity calculator is part of the API. sized_for(items, fpr) and capacity_for(memory, fpr) are public; the math is documented with a citation per closed-form. Tradeoff: maintained sizing module. Violation: users size by guessing and over- or under-provision by an order of magnitude.
  • P9 — Bindings do not re-implement. PyO3/WASM/C-FFI are shims; algorithms live once. Tradeoff: marshalling boilerplate. Violation: a Python-side sizing reimplementation drifts from Rust and produces incompatible filters.
  • P10 — Benchmarks before optimisation. Every primitive ships a Criterion benchmark; SIMD/prefetch/batched lookups land only against a baseline. Tradeoff: benchmark maintenance. Violation: "optimisations" regress throughput undetected.
  • P11 — Untrusted bytes are validated before use. Deserialization bounds every read, caps every allocation against body_len, checks magic+version, and verifies CRC32C before trusting any field. Tradeoff: a validation pass on load. Violation: a malformed .pdsr file overflows a buffer or allocates petabytes.
  • P12 — Saturation is observable, never silent. Counting Bloom and CMS counters saturate at MAX and expose is_saturated(). Tradeoff: a diagnostic per counter type. Violation: a saturated counter turns into a false negative / frozen estimate that hides for months.
  • P13 — Static and mutable filters are different types. Xor / binary-fuse are immutable after from_iter; they expose no insert. Tradeoff: two construction idioms. Violation: a caller mutating a peeled xor filter corrupts the fingerprint invariants.
  • P14 — Document the load-vs-fpr curve, do not hide it. The published fpr is at the design n; the API surfaces the actual fpr at the current load. Tradeoff: an extra diagnostic. Violation: users trust the design fpr at 2× overload where real fpr is ~4×.

8. Domain Model / Protocol / Data Model

The domain object is a sketch: a fixed-size (or bounded-growth) summary of a stream of items, supporting a probabilistic query. The shared protocol is construct → mutate* → query* → (merge)* → serialize.

Worked example — classical Bloom round-trip. Construct Bloom::sized_for(n=10_000, f=0.01) → computes m = 95_851 bits, k = 7. Insert b"alice": hash to h: u128, derive 7 indices via KM, set those 7 bits. contains(b"alice") → all 7 bits set → true. contains(b"mallory") (never inserted) → true only if all 7 happen to collide (prob ≈ f). serialize() → PDSR | v=1 | kind=Bloom | flags | body_len | body(m,k,seed,items,hasher_kind,bits) | crc32c. from_bytes verifies CRC, reads fields, reconstructs a bit-identical filter (I4, I13).

State-transition table — counting Bloom slot (4-bit counter, saturating):

Current Op Next Note
0 insert 1 slot now occupied
c (0<c<15) insert c+1 normal
15 insert 15 saturated (I8); slot now permanently set
c (0<c≤15) delete c−1 unless saturated path was hit
15 delete 15 cannot un-saturate; false-negative risk documented
0 delete 0 underflow no-op

Malformed input handling. Empty item b"" is valid (hashes normally). A 4 KiB item is valid (single hash call). On the wire: a .pdsr file with bad magic → Error::BadMagic; unknown version → Error::UnsupportedVersion; body_len exceeding the file → Error::Truncated; body_len exceeding the memory cap → Error::TooLarge; CRC mismatch → Error::Corrupt (I5, I6). None of these allocate before validation.

Failure path. Cuckoo insert that cannot place a fingerprint after 500 kicks → Error::Full; the filter is left consistent (the in-flight fingerprint is held, not lost into a half-evicted bucket) and prior items remain queryable (§17.5). Xor construction that cannot peel after 256 seeds → Error::ConstructionFailed; no partial filter is returned (P6, I12).

/// Kirsch-Mitzenmacher double-hashing: k indices in [0,m) via h_i=(h1+i*h2) mod m.

pub struct KmIter { /* h1, h2 (forced odd), i, k, m */ }

The combinator forces h2 odd so the walk visits every residue mod a power-of-two m. The high 64 bits of the 128-bit hash are h1, the low 64 bits are h2 (§13.2).

Use the 128-bit xxhash3 variant exclusively (high 64 = h1, low 64 = h2). wyhash seed quality matters: derive the pair (seed, seed ^ 0xa076_1d64_78bd_642f). 13.7 Performance Concerns

  • The SIMD batch path is a net win only at k≥4 hash draws per item (§11.1) — below that, the per-call overhead of setting up vector registers exceeds the scalar cost; gate it behind a k-threshold, not a blanket feature flag.
  • wyhash's advantage over xxhash3 is inputs ≤ 8 bytes only (§5 rubric, §36) — do not default to it for the general-purpose path.
  • The KM combinator's mod m step is a 64-bit division unless m is a power of two; profile whether the sizing module should round m up to 2^⌈log2 m⌉ to replace mod with a mask (a tradeoff against exact-fpr sizing, P8) — Deferred if the division cost is not observed above 2% of insert time.

13.8 Edge Cases

  • Zero-length input (b""): all four hash families must accept it (used by Bloom's empty- item test, §14.5).
  • k=0 or k=1 requested from a caller: KmIter must not divide by zero and must still terminate.
  • h2 == 0 before forcing odd (a real seed can produce this): the odd-forcing step must run unconditionally, not only when a check trips.
  • SipHash keyed path with an attacker-supplied key (not seed): document that per-key isolation is opt-in and not automatic (P2).

14.6 Pitfalls

Small n (n<100) gives k>30; cap k at 32 and document the fpr drift. The fpr() diagnostic must read the bit population, so a filter past design n reports a higher fpr — the right answer. Counting-Bloom delete is not the inverse of insert: insert-twice delete-once still reports present (P14, §8 state table).

14.7 Performance Concerns

  • Classical Bloom touches k (≈7 at fpr 0.01) independent cache lines per op — the dominant cost is k memory accesses, not the hash computation (§36 #3); this motivates blocked Bloom (§15) but is the correct baseline here.
  • fpr() recomputation by full bit-population scan is O(m) — cache it and invalidate on insert, or fpr() becomes an accidental O(n) hot path if called per-lookup.
  • Counting-Bloom 4-bit packing (bitvec) trades ~2× memory savings against non-word- aligned counter access — benchmark against the u8/u16 opt-in (ADR-21) before defaulting broadly.

14.8 Edge Cases

  • n < 100: sizing yields k > 32 — cap k at 32 and document the resulting fpr drift (§14.6).
  • Insert past design n (overload): fpr() correctly reports the higher actual rate (P14) rather than the stale design value.
  • Counting Bloom: insert×2, delete×1 on the same item still reports present (state table §8) — not a bug, a documented non-inverse.
  • Merge attempt between two Blooms with equal m,k but different hasher types: rejected (I7) even though the bit arithmetic would "work" — hasher identity is part of the equality check.

14.9 Failure Analysis

What breaks (F1, §27): empirical fpr drifts above the 1.5× band after sustained overload. Detection: fpr() diagnostic (P14) or the conformance suite's fpr-band check. Blast radius: false positives inflate at the calling system's boundary (e.g. more unnecessary disk reads in an LSM use, §2) — never false negatives (I1 holds regardless of load). Containment: the caller's own SLOs catch elevated miss/read-amplification before data-correctness is at risk (I1 is unconditional). Recovery: resize via a fresh sized_for at the new load, or call compact() if using scalable Bloom (§16); classical Bloom has no in-place resize — this is why scalable Bloom (§16) exists. Operator visibility: pdsr_bloom_fpr_estimate gauge (§14.10).

14.10 Operational Notes

pdsr_bloom_inserts_total, pdsr_bloom_lookups_total{result}, pdsr_bloom_fpr_estimate; counting exposes is_saturated(). conformance bloom.classic/bloom.counting Pass and round-trip identity confirmed are the exit criteria; a regression here blocks every later phase since classical Bloom is the conformance ground truth (§30 critical path, Appendix B).

15. Phase 3 — Blocked Bloom filter (Week 2)

15.1 Objectives

Trade ~10% relative fpr for 2–3× throughput by keeping every probe in one 64-byte cache line (ADR-04). The recommended variant for cache admission and DB block filters.

15.2 Detailed Implementation Steps

Putze-Sanders-Singler 2007 (ADR-04, 64-byte block). Refines I2 at a documented higher band. Touches Block (#[repr(C, align(64))], 8×u64) and BlockedBloom (§11.3); impl ApproxMembership, impl Mergeable. One base hash selects the block; k_per_block (typically 8) hashes within set bits. Set per-block bits with one 512-bit OR (AVX-512), one 256-bit OR (AVX2), or two 128-bit ORs (NEON); contains precomputes the mask, tests with a vptest-equivalent. Sizing ≈ (1 − exp(−k_per_block / bits_per_block_per_item))^k_per_block in sizing.rs::blocked_size_for. Merge is bitwise OR over the block array iff (n_blocks,k_per_block,hasher,seed) agree. Optional prefetch_read_data before bit ops (§4 M1 target).

15.3 Deliverable

src/bloom/blocked.rs; benches/bloom_blocked.rs with committed baseline.

15.4 Acceptance Criteria

conformance bloom.blocked Pass at the documented ~10%-inflated band; M1 (≥100M lookups/s) met on reference HW (§4); prefetch A/B shows the documented lift.

15.6 Pitfalls

64-byte block is a hard requirement on x86_64/aarch64; gate the SIMD path with #[cfg(target_arch)], document POWER9/RISC-V line sizes (ADR-04 6th column). Base-hash low-bit avalanche must be uniform across blocks — xxhash3 has none, early Murmur variants do.

15.7 Performance Concerns

  • The entire phase is a cache-locality bet (MM4, §34): one 64 B line vs k≈7 lines. Below ~100 M lookups/s, first check memory bandwidth (§36 #5: 100 M × 64 B = 6.4 GB/s, well under DDR5 ~40 GB/s) before suspecting hash cost.
  • prefetch_read_data only helps a cold-cache workload; a hot-resident filter (small n) sees no lift and the prefetch instruction is pure overhead — feature-gate it behind a size heuristic.
  • AVX-512 downclocking on some Intel SKUs can make the 512-bit OR path slower than AVX2 despite doing "more work per instruction" — benchmark per-target, do not assume wider is faster (ADR-04 6th column).

15.8 Edge Cases

  • n_blocks == 1 (tiny filter): base-hash selection is a no-op; behaves like k_per_block classical Bloom in one block — verify sizing does not divide by zero.
  • Non-uniform base-hash distribution concentrates items in few blocks, locally saturating them well before global load suggests — block_max_load() (§15.10) catches this before the aggregate fpr diagnostic would.
  • Cross-arch merge: merging a filter built with AVX-512 bit-set order and one built on NEON — safe only because the merge operates on logical bits, not SIMD register layout (I4 independence from host).

15.9 Failure Analysis

What breaks: uneven block occupancy silently produces regional fpr far above the documented ~10%-inflated band even while the aggregate fpr() looks fine. Detection: block_max_load() diagnostic (§15.10) surfaces the worst block, not just the average. Blast radius: localized to items hashing into the hot block(s) — not a whole-filter failure, which makes it easy to miss without per-block instrumentation. Containment: cap k_per_block growth and alert on block_max_load() past a threshold. Recovery: rebuild with a different seed (P7) or a wider n_blocks. Operator visibility: block_max_load() exported alongside the standard Bloom metrics (§14.10).

15.10 Operational Notes

block_max_load() diagnostic; reuses bloom metrics (§14.10). Conformance Pass and the M1 benchmark target hit are the exit criteria — a benchmark regression >10% blocks merge (bench.yml, P10) before the phase is considered shippable.

16. Phase 4 — Scalable and partitioned Bloom (Week 3)

16.1 Objectives

Ship a Bloom that grows past its design n without losing the fpr target (scalable) and a partitioned reformulation that is computationally cleaner.

16.2 Detailed Implementation Steps

Almeida 2007 (scalable); Kirsch-Mitzenmacher partitioning (P3/ADR-03). Maintains I2 under overload. Touches ScalableBloom, PartitionedBloom (§11.3); both ApproxMembership; scalable exposes chain_length() and compact(). When the active filter hits design capacity, append a larger, tighter filter; lookups query each in turn, true iff any is true. compact() rebuilds a single classical Bloom from the union on opt-in. Partitioned: slice m into k disjoint partitions of m/k; the k-th hash maps into partition k. Algebraically equivalent to classical; each hash maps into a smaller index space.

  • Scalable Bloom's per-lookup cost is O(chain_length) classical-Bloom lookups — at 100× overload with r=2, that is ~7 sub-filter queries per contains; document the degraded latency budget explicitly rather than let callers discover it in a profiler.
  • Partitioned Bloom's k disjoint partitions are individually smaller than the classical single array, which can each fit in one cache line at moderate n — a partial win toward blocked Bloom's cache-locality argument (MM4) without the ~10% fpr inflation, at the cost of uneven-load risk (§16.6).

  • Partitioned Bloom with k not dividing m evenly: the sizing module rounds partitions up and documents the resulting small fpr slack, never silently truncates.

16.9 Failure Analysis

Blast radius: latency-only (correctness holds — I1/I2 still enforced per sub-filter) but every contains call pays the full chain cost. Containment: alert on chain_length(); schedule periodic compact() during low-traffic windows. Recovery: compact() rebuilds to a single classical Bloom at the current fpr. Operator visibility: chain_length() exported per instance.

17. Phase 5 — Cuckoo, vacuum, and quotient filters (Week 3–4)

17.1 Objectives

Ship three delete-capable membership filters that beat classical Bloom on space or speed at typical fpr: quotient (native delete + sort-merge), cuckoo (fingerprint + eviction), and vacuum (a smaller-fingerprint cuckoo variant).

17.2 Detailed Implementation Steps

Quotient. Pagh-Pagh-Rao 2005 (§5); Bonomi 2006 precursor (§5). Adds delete support Bloom lacks. Touches Quotient (§11.3); ApproxMembership; Mergeable via sort-merge; delete. Each slot stores remainder bits (9–12) plus three metadata bits (is_occupied, is_continuation, is_shifted); 12–15 bits/slot; table is 2^q slots. Insert locates the run for the slot, shifts remainders within the run to insert in sorted order, updates metadata; delete reverses it; merge sort-merges two slot arrays in O(2N), following the Pagh paper line for line.

Cuckoo / vacuum. Fan et al. 2014 (cuckoo, ADR-05); Wang et al. 2019 (vacuum). Enforces I11 (zero-fingerprint marker) and the bounded-failure budget (§4). Touches CuckooFilter, Bucket, VacuumFilter (§11.3); ApproxMembership; delete; insert returns Result<(), Error::Full>. A bucket is 4 fingerprints of 12 bits packed as [u16;4], 8-byte aligned. Addressing: b0 = h(item) mod n_buckets; b1 = b0 XOR (h(fingerprint) mod n_buckets) so the alternate bucket derives from the fingerprint alone (enables eviction without rehashing). Insert tries b0 then b1; on failure, evict: pick a current bucket, repeatedly kick a random resident fingerprint and re-home it to its alternate bucket up to max_kicks (500, ADR-05); if still no slot, Error::Full (P6). Vacuum uses the same layout with fp_bits=8 and a smarter eviction heuristic at load 0.95: ~30% smaller than cuckoo at the cost of higher fpr. Eviction uses a per-instance xorshift seeded from the salt (P7).

17.3 Deliverable

src/quotient/quotient.rs; src/cuckoo/{cuckoo,vacuum}.rs.

17.4 Acceptance Criteria

conformance quotient Pass at ~10^-3 with 11-bit remainders across load 50/75/90%; conformance cuckoo.basic and cuckoo.vacuum Pass at load 0.95 (f≈0.0024 for cuckoo, ADR-05); delete semantics verified for all three (post-delete contains returns false); the Error::Full failure path leaves prior items queryable.

17.6 Pitfalls

The quotient sliding window during insert is the easy place to introduce a bug that works at low load and breaks above 75% — run conformance at 50/75/90%. Cuckoo: fp == 0 is the empty marker; map a real zero fingerprint to a fixed non-zero value (1) and document the slight fpr inflation (I11). A deterministic RNG breaks the eviction symmetry analysis — use a per-instance xorshift seeded from the salt. max_kicks=500 matches the paper; 50 produces premature Error::Full above 90% load (ADR-05).

17.7 Performance Concerns

  • Quotient merge is O(2N) sort-merge — cheaper asymptotically than rebuilding, but touches every slot of both inputs; for small, frequent merges the fixed cost can dominate — batch merges where possible.
  • Cuckoo eviction cost is bounded but not free: at load 0.95, expected kicks per insert rises sharply (the paper's own curve) — instrument avg_kicks_per_insert alongside load_factor() to catch approach-to-Full before it happens.
  • Vacuum's 8-bit fingerprint halves the false-positive resistance per lookup compared to cuckoo's 12-bit, but its bucket layout is otherwise identical, so throughput is comparable — the space/fpr tradeoff is the only axis that moves (ADR-05 6th column).

17.8 Edge Cases

  • Quotient table at exactly 2^q slots filled (100% load): documented as unsupported — the sizing calculator refuses to size at ≥95% target load.
  • Cuckoo insert of an item already present (duplicate insert): both fingerprints are stored (no de-duplication) — contains still returns true; delete only removes one copy, matching multiset semantics, not set semantics — document this explicitly since it differs from Bloom-family semantics.
  • Cuckoo eviction cycle (a kicked fingerprint returns to a bucket it was already evicted from): max_kicks bounds the cycle length; the hard cap guarantees termination regardless of the RNG's period.
  • Vacuum at load exactly 0.95: the sizing calculator's own boundary — verify no off-by-one admits load 0.951.

17.9 Failure Analysis

What breaks (F4/F5, §27): cuckoo Error::Full after MAX_KICKS, or quotient slot-shift overflow above 90% load. Detection: typed error return from insert in both cases — never a silent failure (P6). Blast radius: the specific insert fails; the filter remains internally consistent and all prior items stay queryable (§8 failure-path guarantee) — not a whole-filter corruption. Containment: caller-level backoff (resize, or route new inserts to a fresh filter instance). Recovery: resize (larger n_buckets/2^q) or raise MAX_KICKS (with the tradeoff noted in ADR-05's 6th column: lower load needed for the paper's guarantees at higher kick bounds). Operator visibility: load_factor() (cuckoo/vacuum) and the quotient slot-occupancy diagnostic, both exported before the typed error is ever hit in practice.

17.10 Operational Notes

90% load. Cuckoo/vacuum: typed Error::Full; load_factor(). All three conformance buckets passing at their documented load points, with delete and failure-path behavior verified, are the exit criteria.

18. Phase 6 — Xor and binary fuse filters (Week 4)

18.1 Objectives

Ship static membership filters — built once from a finite set, queried many times, never modified — faster, smaller, and tighter-fpr than cuckoo.

18.2 Detailed Implementation Steps

Graf-Lemire 2019 (xor, §5); Dietzfelbinger-Walzer 2019 and Lemire 2022 (binary fuse, §5). Enforces I12, P13, and the construction-retry budget (ADR-06). Touches Xor8, Xor16, BinaryFuse8, BinaryFuse16 (§11.3); built via from_iter, query only contains — no insert. Construction is the peeling algorithm: place each item at three candidate slots (xor8) such that one slot is uniquely occupied; build a DAG; topologically sort; assign fingerprints by xor of the three slots. On peeling failure (no order exists), retry with a new seed; ≤8 retries empirically at load 0.81, 256 is the cap (ADR-06). Lookup computes three indices and the fingerprint from one hash and checks the xor of the three stored fingerprints. Binary fuse partitions slots into segments so the three indices fall in three consecutive segments, halving cache misses at the cost of more complex construction; ship both 8- and 16-bit widths.

src/xor/{xor8,xor16,binary_fuse}.rs; benches/xor.rs.

18.4 Acceptance Criteria

conformance xor.xor8/xor16/binary_fuse_8 Pass (fpr ≈ 0.0039 for xor8, ≈0.000015 for xor16, ≤1.5× band); construction-failure retry path succeeds on next seed with no partial filter ever returned; BinaryFuse8 shows fewer cache misses than Xor8 in the throughput benchmark.

The peeling DAG uses 3–5× the final filter size during construction — document the peak (§4) and offer streaming construction (Deferred). The fingerprint width and the mod choice interact; use the published constants verbatim and cite the line numbers.

18.7 Performance Concerns

  • Construction is the expensive side (peeling DAG, topological sort) — amortize it: xor/ fuse filters exist because lookup must be fast on a filter built once (§2), so construction cost is explicitly traded away, not optimized (§34 MM5).
  • Binary fuse's segment layout is the whole performance argument over plain xor: three indices in three consecutive segments instead of three arbitrary slots turns 3 potential cache misses into ~1–2 (§36 #12) — verify this empirically per target, since segment size interacts with L1/L2 size differently across microarchitectures.
  • Construction memory peak (3–5×) can itself thrash cache during the build, slowing construction further at large n — acceptable because construction is offline/batch (§2), never on the hot query path.

18.8 Edge Cases

  • Duplicate items in the input set to from_iter: peeling must treat the input as a set (not a multiset) — document dedup as a caller contract rather than silently dropping duplicates inside the algorithm.
  • Input set size 0 or 1: peeling trivially succeeds (or is a degenerate one-slot filter) — verify no divide-by-zero in the segment-length calculation.
  • Seed exhaustion (all 256 retries fail): documented as Error::ConstructionFailed (P6) — expected to be exceptionally rare (§5) but must never panic or loop.
  • A contains query for an item never in the built set: returns true only at the documented fpr — since there is no insert, there is no way to "add" and hide this from the fpr statistics (unlike a mutable filter under overload).

18.9 Failure Analysis

What breaks (F6, §27): construction fails to find a peeling order after MAX_TRIES (256) seeds. Detection: typed Error::ConstructionFailed returned from from_iter — never a partial or corrupt filter (P6, I12). Blast radius: the specific build attempt fails; because xor/fuse are offline-construction filters (§2), this is caught before any filter reaches production traffic, not a live-traffic incident. Containment: none needed at runtime — the caller's build pipeline fails closed. Recovery: retry with a different input order or a smaller block_length/segment size; escalate to the classical or blocked Bloom (mutable alternative) if the input set structurally defeats peeling (extremely rare per the literature). Operator visibility: construction attempt count exposed for diagnostics (§18.10).

18.10 Operational Notes

19. Phase 7 — Count-Min Sketch, conservative update, count-sketch, and AMS (Week 5)

19.1 Objectives

Ship frequency estimation two ways: Count-Min Sketch (d rows × w counters, min-across-rows estimate) with its conservative-update variant (default, ADR-07), and signed-counter count-sketch with its AMS F2-moment application.

19.2 Detailed Implementation Steps

CMS. Cormode-Muthukrishnan 2005 (§5); Estan-Varghese 2002 (CU, ADR-07). Independence of rows enforced by P3/I3/ADR-23. Touches Cms, CmsCu (§11.4); impl FrequencyEstimator; impl Mergeable for Cms (element-wise sum), CMS-CU merge is per-cell max (approximate, P5). Sizing: w = ⌈e/eps⌉, d = ⌈ln(1/delta)⌉; at (eps=0.001, delta=0.001) → w=2719, d=7 (§36 #9). Insert hashes once, derives d columns via the combinator (§13.2), saturating_adds count to each row's column; estimate reads the same d cells and returns the minimum. Conservative update: find the row-minimum first, then increment only the cells equal to that minimum to min+count — reduces overestimation but loses exact additive mergeability (P5). Row seeds via chained KDF blake3(seed‖i) (ADR-23, P3).

Count-sketch / AMS. Charikar et al. 2002 (§5); Alon-Matias-Szegedy 1996 (AMS/F2, §5). Touches CountSketch, AmsSketch (§11.4); FrequencyEstimator; variance_estimate(). Each row derives a sign hash from its seed; the sign bit is the high bit of the row hash. Insert adds +count or −count accordingly; the estimate is the median across rows of sign·counter (more robust than CMS's min on signed streams). AMS estimates F_2 = Σ f_i² as median_j (Σ sign_j·counter_j)² — a thin wrapper over count-sketch.

19.6 Pitfalls

Row seeds must be independent — seeds[i] = seed ^ i is a known-bad antipattern; use the chained KDF and document it (ADR-23). High variance for low-frequency items in count-sketch — expose variance_estimate() and recommend larger d. Sign hash must be independent of the column hash, or the estimator biases.

19.7 Performance Concerns

  • CMS-CU's conservative update requires a full row-min scan before the increment pass — two passes over d cells per insert instead of one; at M4's target (≥50M inserts/s) this doubles the per-insert memory touches versus vanilla CMS, the direct cost of CU's tighter estimates (ADR-07 6th column).
  • d rows scattered across d independent cache lines per insert/estimate is the CMS-family analogue of classical Bloom's cache-locality cost (§34 MM4) — a blocked-CMS variant is a plausible future optimization, currently out of scope (§1).
  • Count-sketch's median-of-d estimate requires a small sort/selection per query — negligible at typical d≈7-11 but worth avoiding in a per-item hot loop (batch estimates where possible).

19.8 Edge Cases

  • eps/delta requested so small that w·d exceeds the memory cap (§4, I14): sizing returns a typed error rather than allocating (mirrors Bloom's §14.8 discipline).
  • CMS-CU merge of two sketches with different (w,d): rejected (I7) — CMS-CU's approximate mergeability (P5) only applies under exact parameter equality, same as vanilla CMS.
  • Negative-then-positive updates to the same key in count-sketch: the signed estimator must converge to the correct net frequency, not accumulate sign-cancellation error unboundedly.
  • A key that never appears in the stream: CMS returns 0 or a small positive artifact of hash collisions (never negative) — count-sketch, being signed, can return a small negative estimate for an absent key, which callers must not mistake for "confirmed absent" (there is no exact-absence guarantee, unlike Bloom's I1).

19.9 Failure Analysis

What breaks (F7/F8, §27): a CMS counter saturates at u32::MAX under a high-multiplicity stream, or a caller relies on CMS-CU's merge as if it were exact. Detection: is_saturated() (I8) for the counter case; the Mergeable impl's documented approximation (P5) is the defense for the merge case — this is a design-time/code-review control, not a runtime one. Blast radius: saturation degrades every subsequent estimate through that cell (frozen minimum) — bounded to the affected key(s) sharing that cell, not the whole sketch. Containment: alert on is_saturated() gauges; document CMS-CU merge semantics prominently in the type's doc comment (P5). Recovery: widen the counter type (u32→u64) or rotate the sketch (time-windowed CMS, Deferred, §39); for the merge case, switch to vanilla CMS when exact federation is required (ADR-07 6th column). Operator visibility: pdsr_cms_estimate_total, is_saturated() gauge.

Misra-Gries underestimates proportionally to k; expose underflow_bound() and recommend larger k. heavy_hitters(phi) must return a superset of the true heavy hitters (no false negatives at the threshold).

20.7 Performance Concerns

  • Misra-Gries's "decrement all counters" step on eviction is O(k) — at large k (thousands of tracked keys) this dominates insert cost; the Karp reformulation typically amortizes this with a lazy/deferred decrement — document which strategy is implemented and its amortized cost.
  • CMS top-k's min-heap push/pop is O(log k) per candidate promotion — rare in steady state (most inserts do not beat the heap minimum) but a worst-case adversarial input (monotonically increasing frequencies) forces a promotion on every insert; this is a real single-threaded tail-latency risk worth a synthetic worst-case benchmark.

20.8 Edge Cases

  • k=1 Misra-Gries: degenerates to "track the single most frequent item seen so far, evicting on any tie-breaking decrement" — verify no off-by-one in the eviction condition.
  • Ties at the heap minimum in CMS top-k: document the tie-break rule (e.g. keep the incumbent) so behavior is deterministic (P7) across identical replay input.
  • A stream with >k items of exactly equal true frequency: neither algorithm can distinguish which subset is "the" top-k — both return a valid but non-unique superset/ estimate, which is the documented limitation, not a bug.

20.9 Failure Analysis

What breaks: heavy_hitters(phi) fails to include a true heavy hitter (a false negative), which would violate the documented superset guarantee. Detection: the conformance recall fixture (§20.5) is the mechanical check; recall dropping below 0.95/0.99 in production monitoring (via periodic ground-truth sampling) is the operational check. Blast radius: limited to downstream consumers of heavy_hitters (e.g. a rate limiter, §25 examples) that under-detect a hot key. Containment: Misra-Gries's underflow_bound() bounds the worst case analytically — a caller can pre-compute the maximum possible miss before trusting the result. Recovery: increase k (both algorithms) or switch from Misra-Gries to CMS top-k for tighter recall at the cost of the underlying CMS memory (ADR-07 6th column). Operator visibility: underflow_bound(); top-k reuses CMS metrics (§19.10).

20.10 Operational Notes

underflow_bound(); top-k reuses CMS metrics. Both buckets Passing at the documented recall are the exit criteria; a production heavy-hitter regression (e.g. a rate limiter missing an abusive key) should first check underflow_bound() before assuming a code defect.

21. Phase 9 — HyperLogLog and HLL++ (Weeks 6–7)

21.1 Objectives

Ship cardinality estimation: classical HLL and HLL++ with sparse/dense representations and bias correction.

21.2 Detailed Implementation Steps

Flajolet et al. 2007 (HLL, §5); Heule et al. 2013 (HLL++, ADR-08). Enforces I9, I10. Touches Hll, HllPlus (§11.4); impl Cardinality; impl Mergeable (register-max); is_dense(). Each item hashes to 64 bits; the leading p bits select one of 2^p registers; the leading-zero count of the remaining bits (plus one) is stored in the register (max wins). Cardinality is the harmonic-mean estimator with the paper's alpha_p constant, the small-range correction at low cardinality (always on, I10), and the large-range correction near 2^64. HLL++: below a precision-dependent threshold, store an explicit (register, value) list (sparse); above it, switch to the dense register array. Bias-correction tables shipped verbatim from the Heule appendix in bias_tables.rs. Merge is element-wise register-max iff (p,hasher,seed) agree; sparse merges promote to dense past the threshold.

21.3 Deliverable

src/hll/{classic,plus,bias_tables}.rs; benches/hll.rs.

21.4 Acceptance Criteria

conformance hll.classic and hll.plus Pass (accuracy within 1.04/√(2^p) + floor across streams 10^3–10^7 at p∈{4,8,12,14,16,18}); n=1,10,100 fixtures confirm no small-range underestimate (I10); sparse→dense crossing is continuous; DataSketches parity (ADR-20) holds within each bound; M6/M7/M8 met.

21.5 Conformance Fixtures

Fixture Purpose Expected
streams 10^3…10^7 at p∈{4,8,12,14,16,18} accuracy within 1.04/√(2^p) + floor
n = 1, 10, 100 I10 small-range accurate (no underestimate)
sparse→dense crossing transition correctness estimate continuous across switch
DataSketches HLL on same input ADR-20 parity answers agree within each bound

21.6 Pitfalls

The small-range correction is the silent killer: without it HLL estimates 0 for n < ~m/2.5 (I10). alpha_p for p=4 is not simply 0.673 — Heule's tables are normative; transcribe them, do not derive them.

21.7 Performance Concerns

  • HLL insert is O(1) — one hash, one register update — and is memory-bandwidth-trivial (§36 #6: 16 KiB total footprint at p=14) — the M6 target (≥100M inserts/s) is realistically instruction-issue-bound, not memory-bound, unlike the Bloom family.
  • Sparse representation trades insert simplicity for query cost: cardinality() on a sparse HLL++ must scan the explicit list rather than the dense array — cheap while the list is small, which is precisely while it is sparse.
  • The bias-correction table lookup (bias_tables.rs) is a small fixed-size binary search or interpolation — negligible cost, but verify it is not accidentally a linear scan at the estimate hot path.

21.8 Edge Cases

  • p at the boundary (4 or 18, I9): both ends produce valid but extreme relative-error figures (26% at p=4, 0.2% at p=18, §36) — the constructor validates the range but does not second-guess an operator's choice.
  • Two HLLs merged where one is sparse and one is dense: merge promotes the result to dense (§21.2) — never silently drops the sparse side's precision.
  • Cardinality estimate requested on an empty (freshly constructed) HLL: must return 0 without invoking the harmonic-mean formula on all-zero registers in a way that divides by zero — the small-range correction path (I10) handles n=0 as its lowest case.
  • Hash collisions at extremely high cardinality (approaching 2^64 distinct 64-bit hash outputs): the large-range correction (§21.2) is the documented defense; below the practical cardinalities this library targets (§4), it is a documented boundary, not an active concern.

21.9 Failure Analysis

What breaks (F9, §27; prevented by design): without the small-range correction, cardinality is underestimated by ~50% for n < m/2.5. Detection: the conformance fixture at n=1,10,100 (§21.5) is the mechanical gate; in production, an HLL reporting near-zero cardinality against a known-nonzero stream is the operational signal. Blast radius: none in the shipped design — I10 makes the correction unconditional, so this failure mode is closed by construction, not by monitoring. Containment: n/a (always on). Recovery: n/a — this section documents why the invariant exists, for the reader who might otherwise "optimize away" the correction as a rarely-hit branch. Operator visibility: pdsr_hll_cardinality_estimate remains monotonically sane across the sparse→dense transition, which is itself a regression signal if violated.

21.10 Operational Notes

pdsr_hll_inserts_total, pdsr_hll_cardinality_estimate, is_dense(). Both conformance buckets Passing, cross-language parity holding, and M6/M7/M8 met are the exit criteria; sparse→dense transition and bias-correction accuracy are re-verified any time bias_tables.rs changes (a Heule-table transcription error is a silent-accuracy regression, not a crash).

22. Phase 10 — t-digest, KLL, q-digest, GK (Weeks 7–8)

22.1 Objectives

Ship quantile estimation: t-digest (default), KLL (mergeable), q-digest (legacy), GK (fixed-order).

22.2 Detailed Implementation Steps

Dunning 2019 (t-digest, ADR-09 K2); Karnin-Lang-Liberty 2016 (KLL, ADR-10 k=200); Shrivastava 2004 (q-digest); Greenwald-Khanna 2001 (GK). Touches TDigest, Kll, QDigest, Gk (§11.4); impl Quantile; Mergeable for t-digest and KLL; GK merge returns a typed error (not associative, P5). t-digest: bounded-centroid sketch using the K2 scale function k(q); centroids near the tails are smaller, near the median larger; centroid count bounded by ~delta/k_2(q); compact() re-sorts and re-merges. KLL: a hierarchy of compactor levels each of capacity k; a full level halves itself by random-coin compaction and promotes survivors; quantile via cumulative-weight scan; mergeable. q-digest: a binary tree over the value domain with approximate node counts, compressed by collapsing under-counted nodes; shipped for legacy compatibility (KLL dominates new use). GK: a list of (value, rank, delta) tuples; merges are not associative; useful for exact-quantile-from- sorted-stream with fixed input order. Each random walk is seeded from the sketch salt (P7), one xorshift per KLL level.

22.3 Deliverable

src/quantile/{tdigest,kll,qdigest,gk}.rs; benches/tdigest.rs.

22.4 Acceptance Criteria

conformance quantile.{tdigest,kll,qdigest,gk} Pass (q∈{.01,.1,.5,.9,.99,.999} within band on uniform/exponential/lognormal/mixture, 1M values); M9/M10 met; two-halves-merge-vs- single-pass within band for t-digest and KLL; GK merge attempt returns a typed error (non-associativity, P5).

22.5 Conformance Fixtures

Fixture Purpose Expected
uniform/exponential/lognormal/mixture, 1M values accuracy q∈{.01,.1,.5,.9,.99,.999} within band
two-halves merge vs single pass (KLL, t-digest) merge within band
GK merge attempt non-associativity returns typed error

22.6 Pitfalls

t-digest compression after merge is order-dependent — sort and re-merge centroids before querying (compact()). KLL random-coin compaction needs a per-level RNG to avoid biased compaction across levels.

22.7 Performance Concerns

  • t-digest's compact() is an O(centroid_count · log centroid_count) sort — cheap at the target ~100-800 centroids (§36) but must not run on every insert; batch it (on merge, on query if dirty) rather than eagerly.
  • KLL's level-compaction is amortized O(1) per insert across the hierarchy but has a worst-case burst when many levels fill simultaneously — benchmark the tail, not just the mean insert latency, for M9.
  • q-digest's binary tree over the value domain scales with the domain size, not just the sample count — for a wide-range value domain (e.g. full u64 latencies), tree depth can dominate; this is the documented reason KLL is preferred for new use (§22.2).

22.8 Edge Cases

  • All-identical input values: every quantile sketch must return that exact value at every quantile, not divide-by-zero or degenerate on zero-variance input.
  • Extreme skew (all mass at q=0.001 of the range): t-digest's K2 scale function is specifically designed to keep tail accuracy under this — the conformance fixture set (§22.5) includes a mixture distribution to catch a regression here.
  • GK merge attempted anyway (caller error): the typed error (P5) must fire deterministically, never silently return a wrong-but-plausible merged summary.
  • KLL query before any insert (empty sketch): quantile()/rank() on zero samples must return a documented sentinel or error, not panic.

22.9 Failure Analysis

What breaks (F10/F11, §27): a t-digest reports wrong quantiles after a naive (non- compact()) merge, or a caller attempts a GK merge expecting associativity. Detection: quantile drift versus an expected/ground-truth value (production-side sampling) or the merge-order-dependence conformance fixture (§22.5) mechanically. Blast radius: t-digest — bounded to the merged sketch's future queries until compact() runs; GK — the merge attempt fails closed (typed error), so there is no silent-wrong-answer blast radius for GK specifically. Containment: t-digest merges always call compact() internally before being queried, or expose is_dirty() so callers cannot forget. Recovery: compact() re-sorts and re-merges centroids (t-digest); switch to KLL for distributed merge scenarios (P5, §37 Q12). Operator visibility: centroid_count(), level_count(), tree_depth().

22.10 Operational Notes

centroid_count(), level_count(), tree_depth(). All four quantile conformance buckets Passing is the exit criterion; a t-digest accuracy regression should first check whether compact() runs before every query (§22.9) before suspecting the K2 scale function itself.

23. Phase 11 — On-disk serialization (Week 8)

23.1 Objectives

Ship the contract that makes the library usable across language runtimes: a stable, versioned, CRC-protected on-disk format.

23.2 Detailed Implementation Steps

CRC-32C/Castagnoli (RFC 3385, ADR-11); P4, P11. Enforces I4, I5, I6. Touches Frame (§11.5); Serialize/Deserialize per sketch; serde::{frame,magic,crc32c}. Frame layout (every field little-endian) is fixed at magic(4B)/version(1B)/kind(1B)/flags(2B)/ body_len(8B LE)/body(body_len B)/crc32c(4B LE) — see the diagram below.

+--------+---------+------+-------+-----------+--------------+----------+
| magic  | version | kind | flags | body_len  | body         | crc32c   |
| 4 B    | 1 B     | 1 B  | 2 B   | 8 B (LE)  | body_len B   | 4 B (LE) |
+--------+---------+------+-------+-----------+--------------+----------+

magic = b"PDSR", version = 1, kind is the SketchKind discriminant, flags encode sub-type (CMS-CU vs CMS, HLL sparse vs dense). crc32c is the Castagnoli CRC over magic‖version‖kind‖flags‖body_len‖body. Per-sketch body layouts are documented in docs/api/on-disk-format.md (e.g. Bloom: m:u64 | k:u32 | seed:u128 | items:u64 | hasher_kind:u8 | bits:⌈m/8⌉B; CMS: w:u32 | d:u32 | seeds:16×u128 | items:u64 | hasher_kind:u8 | counters:w·d·4B; HLL dense: p:u8 | seed:u128 | hasher_kind:u8 | registers:2^p B). Every length field is bounds-checked on read (I6); the CRC is verified before any body field is trusted (I5). Hardware CRC via the crc32c crate (_mm_crc32_u64/__crc32cx).

23.3 Deliverable

src/serde/*; docs/api/on-disk-format.md; the fixture corpus.

23.4 Acceptance Criteria

conformance serde.frame Pass; round-trip identity (bit-identical bytes, I4/I13) across 50 sketches spanning all kinds and varied params; the fuzz target finds no crashes over the CI run window; pdsr-cli inspect works against every fixture.

23.5 Conformance Fixtures

Fixture Purpose Expected
50 sketches across all kinds at varied params round-trip bit-identical bytes (I4/I13)
empty Bloom (zero-length body) edge case valid; CRC still applies
flipped byte in body I5 Error::Corrupt
body_len > file I6 Error::Truncated, no alloc

23.6 Pitfalls

Endianness — every multi-byte field uses to_le_bytes/from_le_bytes; never rely on platform behaviour. Field order is normative; reordering breaks every existing file. Zero-length bodies are valid and still CRC-checked.

23.7 Performance Concerns

  • Hardware CRC32C (_mm_crc32_u64/__crc32cx) is essentially free versus a software CRC table lookup — verify the build actually selects the hardware path per target (#[cfg(target_feature)]) rather than silently falling back, or the ADR-11 rationale (hardware acceleration) is not actually realized.
  • Deserialization is bounds-checked before every allocation (I6) — this adds a fixed small overhead per field versus an unchecked read, which is the deliberate P11 tradeoff; the §4 startup budget (≤2 ms for a 1.17 MiB Bloom) already accounts for it.
  • Large-body sketches (e.g. a 76 KiB CMS table) deserialize in one bounded allocation, not incrementally — verify this does not spike allocator contention when many sketches load concurrently at process start.

23.8 Edge Cases

  • Zero-length body (an empty/degenerate sketch): valid per §23.6, and the CRC still covers the zero-length body plus header.
  • body_len exactly at the memory cap boundary (§4, I14): the boundary itself must be accepted, one byte over must be rejected — an off-by-one here is a real, testable bug class.
  • A file truncated mid-body (valid header, short body): Error::Truncated (I6) before any attempt to read past the actual byte count.
  • A file with a valid CRC over a well-formed but semantically wrong body (e.g. a kind-byte corruption that still parses): the CRC is computed over all bytes including kind, so a kind corruption is itself CRC-detected — verify no field is excluded from the checksum.

23.9 Failure Analysis

What breaks (F12, §27; T1–T4, §26): a corrupt or truncated .pdsr file is loaded. Detection: CRC32C mismatch (Error::Corrupt), magic mismatch (Error::BadMagic), version mismatch (Error::UnsupportedVersion), or length mismatch (Error::Truncated) — one of the four typed errors fires before any body field is trusted (I5, I6). Blast radius: the single file/load attempt fails closed; no partial or garbage sketch is ever returned to the caller (P6, P11). Containment: none needed beyond the typed error — the deserializer itself is the containment boundary (trust boundary 2, §26). Recovery: caller re-fetches or rebuilds the sketch from its source stream (RTO is bounded by stream replay, not by the library, §4). Operator visibility: pdsr-cli inspect <file> surfaces the frame header for triage even on a body that fails CRC (header fields are checked incrementally, so a corrupt body does not prevent inspecting the header itself).

23.10 Operational Notes

pdsr-cli inspect <file> prints the frame header and body summary. Round-trip identity for all 50 fixtures and CRC/bounds checks verified under fuzzing are the exit criteria. A format-version bump (§29) is the operational trigger for pdsr-cli convert.

26. Threat Model

Trust boundaries. (1) Library API — any caller is untrusted; the library does no I/O, so the caller controls every byte that reaches a sketch (FD budget 0, §4). (2) On-disk file — .pdsr files are untrusted bytes; the deserializer must not overflow on a malformed header, must not allocate unbounded on a malformed body_len, must not crash on a truncated body, and must verify CRC32C before trusting any field (I5, I6, P11). (3) Binding boundary — PyO3/WASM/C-ABI shims own marshalling; bad arguments raise typed errors, never corrupt the sketch.

33. Scalability Analysis

  • Single-sketch memory scaling. Bloom is O(n·ln(1/f)) bits; HLL is O(2^p) bytes independent of n; CMS is O((1/eps)·ln(1/delta)) counters independent of n. The cardinality and frequency sketches are the ones that scale sublinearly — that is the entire point.
  • Throughput scaling. Per-sketch operations are single-threaded and bound by memory bandwidth (blocked Bloom: one cache line/op; classical Bloom: k independent lines/op). The concurrency model is single-writer many-reader (§4); horizontal scale is achieved by sharding the stream and merging sketches (P5), not by locking a shared sketch.
  • Distributed scaling. Mergeable sketches (Bloom OR, CMS sum, HLL register-max, KLL, t-digest) compose across shards: each shard maintains a local sketch; a coordinator merges. Merge cost is O(sketch_size), independent of stream length — the property that makes the federation pattern (Deferred) cheap.
  • The non-scaling cases. Scalable Bloom's lookup cost grows with chain length under overload (mitigate with compact()); GK is not associatively mergeable (use KLL); CMS-CU merge is approximate (use vanilla CMS for exact). These are the boundaries of the linear story.
  • Bottleneck at extreme cardinality. For >600M distinct items, HLL needs p≥16 (64 KiB); for >2.4B, p=18 (256 KiB). Beyond that, register memory is the limiter and HLL++ sparse no longer helps (the sketch is dense). The capacity model below derives these thresholds.

34. Mental Models & First Principles

  • MM1 — A sketch is lossy compression with a known error distribution, not a database. Predicts that every query has a bound, not an answer. Without it you treat estimate() as exact and ship a billing system that over-charges by the overestimate. Applied §19, §21, §32.
  • MM2 — The fpr is a function of load, not a constant. f ≈ (1−e^(−kn/m))^k rises super-linearly past design n. Predicts the ~4× fpr at 2× overload. Without it you trust the design fpr and silently degrade. Applied §14 (P14, I2).
  • MM3 — Hash independence is the load-bearing assumption. The d/k-fold confidence is a product of per-row independence; correlate the rows and the product collapses. Without it (e.g. seed^i) the empirical error blows past the bound while every unit test passes. Applied §13, §19 (P3, I3).
  • MM4 — Cache-line locality beats algorithmic constant factors at these sizes. A blocked Bloom touches one line; a classical Bloom touches k lines. Predicts the 2–3× throughput win for a ~10% fpr cost. Without it you optimise instruction count and miss the memory wall. Applied §15 (§4 latency budget).
  • MM5 — Static and streaming filters are different problems. A set known in advance can be peeled (xor: ~1.23 bytes/item at fpr 0.0039); a mutable filter cannot. Predicts xor wins on read-only sets, cuckoo/Bloom win when you must insert later. Without it you reach for Bloom when xor would halve the memory. Applied §18 (P13, I12).
  • MM6 — Saturation is a phase change, not a gradual drift. A counter at MAX stops counting; the filter's guarantee silently inverts (counting Bloom starts producing false negatives). Predicts a cliff, not a slope. Without it you watch averages and miss the cliff. Applied §19 (I8, P12).
  • MM7 — The on-disk format is a wire protocol, so treat every loaded byte as hostile. Predicts the deserializer's failure modes (overflow, over-allocation, garbage) before they happen. Without it a single flipped byte returns a confidently wrong answer. Applied §23, §26 (I5, I6, P11).
  • MM8 — Mergeability is an algebraic property of the sketch, not a feature you add. Bloom is a monoid under OR only with equal (m,k,seed); HLL under register-max; GK under nothing. Predicts exactly which sketches federate. Without it you ship a merge that is silently wrong. Applied §33, §22 (P5, I7).

RedisBloom made the decision to live inside Redis as a server-side module, so its sketches are network-addressable and persisted with the database. That wins when you already run Redis and want sketches without a separate service — the niche pdsr does not target (it is a library, FD budget 0).

Google Guava BloomFilter chose immutability and JVM-native serialization with a single, well-tested Bloom implementation. That wins for JVM applications that need exactly one Bloom filter with zero configuration — it deliberately ships no cuckoo/CMS/HLL, which pdsr does.

Apache DataSketches chose mathematically rigorous, cross-language sketch families with published error theorems and a portable binary format. That wins for large-scale analytics (Druid, Pinot) where answer-parity across Java/C++/Python is the requirement — which is exactly why pdsr asserts parity against it (ADR-20) rather than competing on it.

Cassandra Bloom filters chose per-SSTable, on-disk Bloom filters tuned to one job: skip a disk read. That wins inside an LSM engine where the filter lives next to the data block — the pattern pdsr demonstrates in examples/lsm-block-filter.rs rather than embedding.

36. Back-of-Envelope Capacity Model

Each number is derived from the §4 System Constraints table; the formula is shown.

  1. Bloom bits per item at fpr 0.01. bits/item = −ln f / (ln 2)² = −ln(0.01)/0.4805 = 4.605/0.4805 ≈ 9.59. → A 1M-item Bloom at fpr 0.01 needs 9.59e6 bits ≈ 1.17 MiB (matches §4 memory row and the sizing table below).
  2. Optimal k. k = (m/n)·ln 2 = 9.59 × 0.693 ≈ 6.65 → round to 7. → 7 cache-line touches per classical-Bloom op, the basis for M3 vs M1.
  3. Classical Bloom lookup latency floor. k independent lines × ~80 ns DRAM miss = 7 × 80 ≈ 560 ns worst case, ~350 ns p99 with partial cache residency (§4 latency row).
  4. Blocked Bloom lookup latency. One cache line: ~10 ns warm (L1/L2), one DRAM miss ~80–120 ns cold. → p50 ≤ 10 ns, p99 ≤ 120 ns (§4), and the ~2–3× throughput win over M3 that yields M1 = 100 M ops/s.
  5. Blocked Bloom throughput sanity. At 100 M lookups/s and one cache line/op, memory traffic = 100e6 × 64 B = 6.4 GB/s — well inside DDR5 bandwidth (~40 GB/s), so the limiter is issue width / branch resolution, not bandwidth (confirms M1 is achievable).
  6. HLL p=14 memory. 2^14 registers × 6 bits = 98_304 bits = 12 KiB packed, ≤ 16 KiB with overhead (§4 / M8).
  7. HLL p=14 standard error. 1.04/√(2^14) = 1.04/128 ≈ 0.008125 → ≤ 1.25% (M7).
  8. HLL precision for a target cardinality. Error 1% needs 1.04/√(2^p) ≤ 0.01 → 2^p ≥ 10816 → p ≥ 14; for sustained sub-1% at 600M distinct, p≥16 (64 KiB) per §33.
  9. CMS dimensions at (eps=0.001, delta=0.001). w = ⌈e/eps⌉ = ⌈2.718/0.001⌉ = 2719; d = ⌈ln(1/delta)⌉ = ⌈6.908⌉ = 7. → table = w·d·4 B = 2719×7×4 ≈ 76 KiB (the sizing table below).
  10. CMS-CU insert cost. d row updates per insert = 7 cache touches; at M4 = 50 M inserts/s that is 50e6 × 7 × 4 B ≈ 1.4 GB/s write traffic — inside bandwidth, so the limiter is the conservative-update min-scan, not memory.
  11. Cuckoo bits per item. bucket 4 × 12-bit fp / load 0.95 = 48 bits / 4 / 0.95 ≈ 12.6 bits/item of fingerprint, ~33.7 bits/item total with bucket overhead (the sizing table below) — vs Bloom's 9.59 at comparable fpr, the space cost of delete support.
  12. Xor8 bits per item. 1.23 × 8 bits ≈ 9.84 bits/item at fpr ≈ 0.0039 — smaller than cuckoo at a tighter fpr, the reason xor wins for static sets (MM5), but with the 5× construction-memory peak (§4) that bounds offline build size.

38. Alternative Architectures (Roads Not Taken)

A1 — Server-side sketch service (the RedisBloom shape).

Show the original text diagram
[clients] --network--> [sketch server: owns sketches + persistence]

Wins when sketches must be shared across many processes/languages over the network and persisted with an existing datastore. Embodied by RedisBloom. Rejected: pdsr is a library with FD budget 0 (§4); a network hop would dominate the 10 ns blocked-Bloom lookup and defeat the entire latency story (§36 #4). The federation layer is the controlled, Deferred concession to this regime.

A2 — Byte-compatible drop-in for Apache DataSketches.

Show the original text diagram
[DataSketches .bin] <--same wire format--> [pdsr]

Wins when the goal is to replace DataSketches in a pipeline without re-serializing existing sketches. Embodied by Apache DataSketches' portable format. Rejected (ADR-20): matching their byte layout would couple every pdsr sketch to their evolving format and forbid the CRC32C trailer and KM-seed design we want; we assert answer-parity instead and own our format (P4).

A3 — Generic monoid framework over a Sketch trait (the Algebird shape).

trait Monoid { fn zero(); fn combine(a,b); }  // every sketch is just a Monoid instance

Wins for compositional stream-processing where sketches flow through generic aggregate/reduce combinators (Spark/Scalding). Embodied by Twitter Algebird. Rejected for the core: forcing every sketch into one monoid trait erases the per-algebra preconditions (Bloom needs equal (m,k,seed); GK has no monoid) that pdsr makes explicit and type-checked (P5, I7). We expose Mergeable per-type instead, keeping the typed mismatch error.

A4 — Single-family library (the Guava shape).

[one Bloom implementation, zero configuration]

Wins when an application needs exactly one well-tested Bloom filter and nothing else. Embodied by Google Guava BloomFilter. Rejected: the project's pedagogical and portfolio goal (§2) is to own the full surface — cuckoo, xor, CMS, HLL, quantiles — which a single-family library cannot teach.

40. Glossary

  • fpr — false-positive rate; probability a membership filter reports contains(x)==true for an un-inserted x.
  • false negative — reporting contains==false for an inserted item; Bloom variants never do this (I1) except via counter saturation in counting Bloom (I8).
  • load factor — for cuckoo/quotient/xor filters, ratio of inserted items to total slots.
  • bits/item — total filter size in bits divided by inserted items; the space-efficiency metric.
  • k — number of hash functions / bit-probes per item in a Bloom filter.
  • m — Bloom bit-array length in bits.
  • MAX_KICKS — cuckoo eviction bound; evictions tried before declaring Error::Full.
  • MAX_TRIES — xor/fuse construction seed-retry bound (256, ADR-06).
  • eps, delta — CMS/count-sketch parameters: eps additive error relative to stream length, delta failure probability.
  • w, d — CMS table dimensions: w columns (width), d rows (depth).
  • conservative update — CMS-CU rule incrementing only the minimum cells (Estan-Varghese).
  • count-sketch — signed-counter frequency sketch using a sign hash; estimate is the median.
  • AMS — Alon-Matias-Szegedy F2 (second frequency moment) estimator.
  • heavy hitter — an item whose frequency exceeds a threshold phi of the stream.
  • Misra-Gries — bounded-counter heavy-hitter algorithm.
  • p — HLL precision; m = 2^p registers.
  • register — HLL slot storing a leading-zero count.
  • harmonic-mean estimator — HLL's cardinality formula over register values.
  • small-range correction — HLL adjustment preventing underestimation at low n (I10).
  • bias correction — HLL++ empirical correction tables (Heule 2013).
  • sparse / dense — HLL++ representations below / above a precision-dependent threshold.
  • cardinality — number of distinct items in a stream.
  • quantile — value below which a given fraction of the data falls.
  • rank — number of items ≤ a given value.
  • centroid — t-digest cluster of weighted samples.
  • K2 — t-digest scale function k(q) = (delta/2π)·arcsin(2q−1).
  • KLL compactor — a KLL level performing random-coin halving when full.
  • q-digest — binary-tree quantile sketch over a value domain.
  • GK — Greenwald-Khanna quantile summary; not associatively mergeable.
  • fingerprint — cuckoo/xor/fuse per-item identifier (8–16 bits).
  • peeling — xor/fuse construction; topological sort assigning fingerprints to slots.
  • blocked Bloom — Putze 2007 variant confining all probes to one cache line.
  • scalable Bloom — Almeida 2007 chain of geometrically growing, tightening Blooms.
  • partitioned Bloom — Bloom with k disjoint bit partitions, one per hash.
  • quotient filter — Pagh 2005 hash-table filter with native delete and sort-merge.
  • cuckoo filter — Fan 2014 fingerprint filter with two candidate buckets and eviction.
  • vacuum filter — Wang 2019 cuckoo variant; smaller fingerprints, smarter eviction.
  • xor filter — Graf-Lemire 2019 static membership filter built by peeling.
  • binary fuse filter — Lemire 2022 segmented xor filter with better cache locality.
  • Kirsch-Mitzenmacher — double-hashing combinator h_i = h1 + i·h2.
  • avalanche — degree to which a hash spreads input bit changes across the output.
  • CRC32C — Castagnoli CRC32; the on-disk trailer (ADR-11).
  • frame — the on-disk envelope: magic, version, kind, flags, body_len, body, CRC.
  • magic — the 4-byte PDSR file signature.
  • Mergeable — the trait implemented exactly where the sketch algebra admits a merge.
  • monoid — an algebra with an associative combine and an identity; the merge abstraction.
  • W-TinyLFU — Window TinyLFU cache admission policy using a Bloom front-door.
  • SSTable — sorted-string-table; LSM-tree on-disk segment with per-block Bloom filters.
  • PhaseDeferred — the anchor marking work recorded in the Deferred Features Register.
