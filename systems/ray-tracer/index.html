In one paragraph

This is a design for an offline renderer written in Rust: you give it a 3D scene file, it fires virtual light rays through the scene, and it writes out an image. Instead of flattening triangles onto the screen (the rasterizer approach), it estimates how much light reaches each pixel by averaging many random light paths (Monte Carlo path tracing). It trades minutes to hours of render time for physical accuracy (§1). It ships as a command-line renderer and as embeddable libraries (§1), with a design-target render time under 15 minutes for a Cornell-box-class scene at 1920×1080 (§4). Technical artists, render-farm operators and CI jobs run it (§1).

The problem, concretely

A rasterizer decides visibility by projecting each triangle onto the screen and testing against a depth buffer, in one deterministic pass (§1). That is fast, but it cannot produce the things that make an image look physical: soft shadows, light bouncing off a red wall onto a white floor, glossy reflections. The blueprint's own cheap alternative, a Whitted-style recursive ray tracer that traces only a hard shadow ray plus mirror and refraction rays, gives "zero soft shadows, zero GI" (§36). So the design takes on the harder job: estimate the rendering equation (the integral of all incoming light at a point) by random sampling (§1, §8).

Random sampling creates three new problems, and the blueprint's structure answers each.

First, speed. Every sample needs many ray-versus-geometry tests. The blueprint's baseline is a linear scan of every triangle: a 400×300, one-sample-per-pixel render of a 70,000-triangle bunny must finish in under 30 s that way (§14.4). Behind a spatial index it must finish in under 0.5 s, at least a 60× speedup (§15.4, M3 in §30). The second problem is noise: an image built from few random samples is grainy, so the design spends effort on smarter sampling (§2, MM1). The third is that bugs are invisible. A material whose sample_f and pdf disagree looks "moodier", like an art choice, when it is simply darker (P2), so correctness is proven against numbers, never a screenshot (P4, MM4).

How it works, end to end

Follow one pixel through the boxes of §3 (diagram adapted from §3), in pipeline-table order (§8).

scene file -> [Scene Loader] -> [Geometry Store] -> [BVH Builder (SAH)]  (read-only after)
[Tile Scheduler] --tiles (work-steal)--> per-tile worker thread:
    [Camera / Ray Generator] <- [Sampler]
      -> [BVH Traverser] -> [Integrator: path tracer] (BSDF, Light sampling, Texture)
      -> per-pixel atomic accumulate
[Film / Framebuffer Accumulator] -> [Progressive Preview emitter] -> disk/socket
      -> [Tone Mapper] -> [Denoiser Seam (trait)] -> [Output Writer] -> PPM / PNG / OpenEXR
  1. Load the scene (raytracer-io, raytracer-core). The scene loader parses a custom JSON wrapper plus glTF 2.0 meshes and materials into a Scene. It runs once, single-threaded, and is the only untrusted-input boundary (§3, §24). The result is the Geometry Store, immutable after load, so every thread can read it without locks (§3, P6).
  2. Build the BVH (raytracer-accel). A bounding volume hierarchy (a tree of boxes around groups of triangles) is built once with the surface-area heuristic and packed into a flat array of 32-byte BvhNodes (§3, §8, §15.2). Nothing mutates it afterwards (P6).
  3. Schedule tiles (raytracer-render). The Tile Scheduler cuts the film into 16×16 tiles and hands them to a rayon work-stealing pool. One tile belongs to one thread at a time (§3, §4, ADR-19, I13).
  4. Generate a camera ray (raytracer-render, raytracer-sampling). The Camera maps a film position plus lens position to a world-space Ray; the Sampler, owned by one thread and never shared, supplies the random numbers (§3, P12).
  5. Traverse the BVH (raytracer-accel). The traverser walks the tree and returns the nearest hit as a SurfaceInteraction; it holds no state about the tree, so threads share it freely (§3, §15.2).
  6. Integrate (raytracer-render, with raytracer-bsdf, raytracer-lights, raytracer-texture). The path tracer asks the material how light scatters here, samples a light, and decides whether to continue the path (§3, §8). These three crates are in §10's layout but not in §1's seven-crate Phase-0 list, though §12.1 stands up the §10 workspace.
  7. Accumulate (raytracer-render). The sample goes into the pixel's sum, sum-of-squares and count, using atomic adds, never locks (§3, P14, I13).
  8. Tone map and write (raytracer-render, raytracer-io). The film holds linear radiance. A pure function turns it into a display image once, then the denoiser seam (a no-op trait in Phases 0 to 11) and the writer produce PPM, PNG or OpenEXR (§3, P10, ADR-21).

The core ideas

Path tracing is an average of f/p (§8, §16)

The Monte Carlo estimator averages f(X)/p(X) over N random samples drawn from density p; it is unbiased as long as p(x) > 0 wherever f(x) ≠ 0, and its variance falls as 1/N (§8):

⟨F⟩ = (1/N) Σ_{k=1..N} f(X_k) / p(X_k)
Var[⟨F⟩] = (1/N) Var[f(X)/p(X)]

Choosing p roughly proportional to f (importance sampling) shrinks the variance. For a matte (Lambertian) surface the blueprint uses the cosine-weighted hemisphere density p(ω) = cosθ / π (§8). The key discipline: every sampling routine must return the density it actually used, and a separate pdf method must agree with it (P2, I2). Image quality questions then reduce to variance questions (MM1).

The blueprint's own two-bounce trace (§8, "Worked numeric example"):

Step What happens Number
1 Camera ray hits Lambertian floor, albedo ρ = 0.8; f·cosθ/pdf = ρ throughput 0.8
2 Bounce ray hits a wall, ρ = 0.5, no emission; sample an area light (radiance 10, pdf_solid_angle 2.0, cosθ_l 0.9) direct term ≈ 0.716
3 Scale that by the throughput so far ≈ 0.573 added to the pixel
4 The BSDF-sampled continuation carries throughput 0.8 × 0.5 into depth 2 0.4; Russian roulette (RR) not yet engaged

Each bounce also offsets the ray origin along the geometric normal by a scale-aware epsilon, not a fixed constant, or shadow rays hit their own triangle ("shadow acne") (P5, P7, I11, §16.2, §8).

BVH with the surface-area heuristic (§8, §15, ADR-03, ADR-04)

A BVH makes finding a ray's nearest hit take roughly O(log N) steps instead of scanning every triangle (§31). The only question is where to split each box. The surface-area heuristic (SAH) scores a split from each child's surface area and triangle count (§38, §8):

cost(split) = K_T + (SA(L)/SA(N)) · N_L · K_I + (SA(R)/SA(N)) · N_R · K_I

The blueprint's worked example: N = 100 triangles, SA(N) = 24 m², K_T = 1.0, K_I = 1.2. Split A (SA(L) 10 m², 40 triangles; SA(R) 16 m², 60) costs 69.0. Split B (12 m², 50; 13 m², 50) costs 63.5, so B wins (§8). The build bins triangle centroids into 12 to 16 buckets per axis, scores each bucket boundary, and keeps the cheapest split (§15.2). The traversal uses an explicit stack, visits the nearer child first, and keeps a running t_max to prune (§15.2).

Two safety rules matter. If all centroids coincide, SAH cost is flat, so the builder falls back to an index-median split to keep depth O(log N) (I10, §8, §15.2). And because a silently wrong BVH corrupts everything downstream, debug builds cross-check it against a linear scan (P11, I3, I4).

Next-event estimation and multiple importance sampling (§8, §19, §20)

Next-event estimation (NEE) samples a point on a light directly at every non-specular bounce and traces a shadow ray to it (§3, §19.2); with it, a 64-spp Cornell box matches a 1024-spp BSDF-only reference within 2% RMSE (§19.4). Multiple importance sampling (MIS) uses both light and BSDF sampling and blends them with weights that sum to one (I6, §8). On a glossy surface under a small light, MIS at 128 spp must reach ≤ 5% RMSE where BSDF-only sampling exceeds 20% (§20.4):

Balance heuristic:  w_s(x) = p_s(x) / Σ_i p_i(x)
Power heuristic:    w_s(x) = p_s(x)² / Σ_i p_i(x)²      (β = 2)

The light-sampled contribution is weighted by mis(light_pdf, bsdf_pdf), where bsdf_pdf comes from the BSDF's own pdf method; the BSDF-sampled one, if it hits a light, is weighted by mis(bsdf_pdf, light_pdf), with light_pdf from the hit light's pdf_li (§20.2, P9). Never re-derive a PDF in the weighting code: that is the commonest source of energy loss or gain (P9). A specular bounce has no light-sampling competitor, so its BSDF weight is 1, and Phase 7's temporary skip-emission rule is removed once MIS lands (§19.2, §20.2).

Russian roulette keeps paths short without bias (§8, P8, I8)

Without it, samples are wasted on paths that can't matter (P8). Russian roulette continues a path with probability q, scaling its throughput by 1/q on survival, and ends it otherwise (§8). It stays unbiased only if q depends on accumulated past throughput, not the path's own future contribution (§8). Here q follows the throughput's maximum channel from depth 3 on (§16.2, §4, ADR-14); the depth cap still applies: default 8, hard cap 64 (§4, §16.2).

Microfacet materials: rough metal and glass (§8, §18)

A microfacet model treats a rough surface as a crowd of tiny mirrors. The BRDF is built from a distribution of facet orientations D, a masking-shadowing term G, and a Fresnel term F (§8):

f(ω_o, ω_i) = D(h) G(ω_o, ω_i) F(ω_o · h) / (4 cosθ_o cosθ_i)
D_GGX(h) = α² / (π ((n·h)²(α² − 1) + 1)²)
F_schlick(θ) = F0 + (1 − F0)(1 − cosθ)^5

Sampling uses visible-normal sampling (Heitz 2014): pick a half-vector h visible from ω_o, reflect to get ω_i, and convert the density with the reflection Jacobian so that pdf matches exactly (§8, §18.2). Below a minimum roughness the BSDF is treated as a delta and flagged specular, so the integrator skips light sampling at that bounce (§18.2). Glass picks reflection or refraction by Fresnel and forces reflection on total internal reflection (§18.2). Energy is checked by the white-furnace test: in a uniform glowing environment the object must converge to exactly the source radiance (I1, P4). Tolerances differ: I1 flags a white-furnace RMSE above 0.5% (§7), while Phase 6 accepts 1% for GGX metal and 1.5% for glass (§18.4).

Tiles and the film: parallelism without locks (§3, §6, §13)

A tile is the unit of work, parallelism and failure isolation (P14). Workers share only the read-only BVH and Geometry Store (P6) and the film, whose per-pixel sum, sum_sq and count are updated by atomic add (§3, §13.2, I13); the sampler is per thread (P12). Running sums keep film memory constant in sample count (§31), and their variance feeds the per-tile convergence check (§13.2, §4).

The trade-offs — where engineers disagree

Acceleration structure: BVH (ADR-03)

Chosen: a BVH, for the best general-purpose build and traversal balance on triangle soups of varying density. Rejected: kd-tree, uniform grid, octree. When the rejected choice is right: a kd-tree for static architectural scenes dominated by axis-aligned geometry; a grid for uniform-density point clouds; an octree for sparse volumetric data.

BVH build: binned SAH, front-to-back (ADR-04)

Chosen: binned SAH with front-to-back traversal, for an O(N) cost evaluation at near-optimal tree quality. Rejected: full unbinned SAH, median split. When the rejected choice is right: full SAH for scenes under 10k triangles where its O(N²) cost is cheap; median split under a hard real-time build-time budget.

Integrator: unidirectional path tracing plus MIS (ADR-06)

Chosen: the simplest integrator that reaches production image quality for the target scene class. Rejected: bidirectional path tracing, Metropolis light transport, photon mapping. When the rejected choice is right: bidirectional for caustic-dominated specular-diffuse-specular scenes; Metropolis for keyhole or hard-to-sample scenes; photon mapping for fast biased previews. §36 treats the caustic gap as an accepted §1 non-goal.

Bias policy: unbiased by default (ADR-07)

Chosen: unbiased by default; biased modes (firefly clamping, denoising) are opt-in and labelled in the render metadata, preserving P3 and P4. Rejected: an always-biased fast preview as the default. When the rejected choice is right: a fully biased fast-preview mode for interactive walkthroughs where correctness is secondary to frame time.

MIS weighting: power heuristic (ADR-13)

Chosen: the power heuristic (β = 2), for empirically lower variance in the target scene class. Rejected: the balance heuristic. When the rejected choice is right: when its strict "within 4× of optimal" theoretical bound matters more than empirical noise. Either way the weights must sum to one (I6, §35 question 3).

Denoising: define the seam, ship no model (ADR-21)

Chosen: a seam trait with a no-op implementation and no trained model, keeping the correctness baseline undiluted by a default bias (P3). Rejected: a bundled bilateral filter as the default. When the rejected choice is right: when a zero-dependency "good enough" denoise is required and edge-smudging bias is acceptable.

Reproducibility: pinned toolchain, no FMA contraction (ADR-26)

Chosen: a pinned toolchain, disabled FMA contraction (fused multiply-add rounding) and a fixed thread count, so a seeded render is bit-exact (I9). Rejected: unpinned toolchain, FMA allowed, variable thread count. When the rejected choice is right: when only visual, not bit-exact, parity is needed across a heterogeneous render farm, trading reproducibility for a modest speed gain. A changed thread count, math library or sample ordering also breaks it (§27).

Roads not taken

Whitted-style recursive ray tracing (§36): hard shadows plus mirror and refraction rays, no noise, no global illumination. It wins for real-time-adjacent previews where a fast but incomplete image beats a slow, correct, noisy one; §1 requires soft shadows and GI, so it loses.

Bidirectional path tracing and Metropolis light transport (§36, ADR-06): connect camera and light subpaths, or mutate high-contribution paths. They win for caustics through glass and light through a keyhole, but roughly triple integrator complexity for a gain §36 calls a §1 non-goal; un-defer when MIS cannot resolve a needed caustic within the SPP budget (§37).

Photon mapping (§36, ADR-07): trace photons from lights, then gather them near camera hits. It wins for fast caustic previews where a small documented bias is acceptable; unbiased-by-default would force a separate, labelled biased mode and a second transport algorithm.

GPU wavefront path tracer (§36): per-stage kernels over thousands of in-flight paths, winning on raw GPU throughput. Rejected per the §1 non-goal: the CPU tile-per-thread design is simpler and enough offline; un-defer when the §31 single-machine ceiling binds a named workload (§37).

What must never be false

  • I1: a white-furnace scene converges to exactly the source radiance, never brighter. Noticed when white-furnace RMSE exceeds 0.5%; the per-material energy-ratio metric runs in conformance CI (§7).
  • I2: each BSDF sample's returned PDF matches the analytic density of the routine that made it. Noticed by a chi-square test per BSDF; each per-BSDF test report is a CI artifact (§7, §28).
  • I3, I4: the BVH never misses a ray that geometrically hits, and never reports a hit that does not exist. Noticed by a debug-build differential test against a linear scan; the metric is a mismatch count per build (§7).
  • I5: no NaN or infinity reaches the film. A per-sample guard counts them in nan_sample_count; the bad sample is discarded and the path logged (§7, §26).
  • I6: MIS weights across strategies sum to one. A property test sums them; debug builds assert it (§7).
  • I7: variance falls as 1/N. A soak-test regression compares measured slope with theory; the metric is convergence_rate; a violation points at correlated RNG seeding (§7, §26).
  • I8: Russian roulette's p and 1/p compensation preserve the expectation. A unit test compares RR-terminated with full-depth renders on a synthetic scene (§7).
  • I9: a fixed seed, scene and thread count give a bit-identical or tolerance-bounded image. The seeded-replay fixture pixel-diffs against a stored reference (§7).
  • I10: BVH build never degrades to O(N²) traversal, even for coincident or degenerate geometry. Noticed by a build-depth and leaf-size assertion; metrics max_leaf_primitive_count and build_depth (§7).
  • I11: an offset shadow or continuation ray never self-hits at t≈0. Noticed by an acne-pattern detector in the conformance renderer and a self-hit rejection counter (§7).
  • I12: texture sampling never reads outside the mip chain. A bounds-check assertion in debug builds; recovery clamps the level to [0, max_level] (§7).
  • I13: film accumulation is race-free. Noticed by a loom-style race-detector test in CI (§7, §28).

What breaks in production

  • FM-1: fireflies. Isolated very bright pixels, from rare samples with large contribution. A per-tile variance-spike detector flags them. There is no automatic recovery in unbiased mode; an operator may enable the clamped firefly mode, which is biased and labelled (ADR-07), and re-render. The forensic step is to inspect the logged path and PDF trace (§25).
  • FM-2: shadow acne. Speckled banding on lit surfaces, because the ray offset was not scale-aware (violating P7). The I11 acne detector catches it; the fix is a relative epsilon and a re-render (§25, §8 failure-path example).
  • FM-3: energy loss or gain. The white-furnace test fails; causes are an unnormalized BSDF, a wrong Smith G or a missing sampling Jacobian. Conformance CI blocks the build, and the recovery is a term-by-term bisect of the BSDF (§25, I1).
  • FM-4: NaN propagation. A tile goes black or saturated white from a divide-by-zero or a zero-length normal. The I5 guard discards the sample and the tile continues; nan_sample_count and logged ray and hit data support the investigation (§25).
  • FM-5: BVH degeneration. Build or traversal time spikes because coincident bounds defeat the SAH split. The I10 build-depth assertion fires and the builder falls back to a median split automatically; build_depth and bvh_node_count are the metrics (§25).
  • FM-6: non-determinism. The replay test fails, from per-thread RNG seeded by thread id or from FMA-contraction variance. The I9 seeded-replay CI detects it; there is no automatic recovery. An operator pins the toolchain and thread count and re-seeds correctly (§25, ADR-26).
  • FM-7: MIS double-counting. Subtle over-brightening at direct light, from a weight-sum violation. The weight-sum property test detects it; the remedy is auditing PDF reuse (§25, P9).
  • FM-8: texture cache thrash. Performance regresses with no code change because the working set exceeds the 512 MB ceiling. The texture_cache_hit_rate metric drops; LRU eviction is the expected behaviour, and the manual fix is a bigger cache or smaller textures (§25, §4).

Threats a reader should know (§24): T1, a crafted glTF accessor causing an out-of-bounds read (bounds validation at load, cargo-fuzz, typed RenderError::GltfImport); T2, a scene asking for an unreasonable resolution or triangle count (hard ceiling, pre-flight size estimate); T4, a buffer URI containing ../ (paths canonicalized and confined to the asset root); T7, degenerate bounds crafted to defeat SAH (bounded-depth median-split fallback); T10, untrusted plugin materials (no dynamic plugin loading in Phases 0 to 11).

How it compares

  • pbrt-v4 made the rendering math and the BVH the teaching centre of a book and codebase, with spectral rendering by default and an optional GPU path. It is slower than the fastest renderers, which suits its education and reference niche, and is why this blueprint leans on it for required reading (§33, §5).
  • Embree is a kernel library, not an integrator: wide BVH4/BVH8 trees with hand-tuned SIMD, CPU only. That is right for studios that want the best CPU traversal without adopting a shading and light-transport stack, the opposite of this blueprint's all-in-one design (§33).
  • Mitsuba 3 made differentiability central, so every BSDF, integrator and sampler supports automatic differentiation. It suits inverse-rendering research, where this blueprint's non-differentiable design (ADR-11) is a deliberate simplification (§33).
  • Blender Cycles made GPU wavefront execution central, splitting the integrator into per-stage kernels over large batches of path state. It fits interactive and production viewports, at the memory-access complexity this CPU tile-per-thread design avoids (§33, §36).

If the BVH cross-check (I3, I4) never fires in CI, does that prove the BVH is correct, or only that the fuzz/random-ray corpus hasn't found the counterexample yet — and how does the §28 differential test against Mitsuba 3 change that answer? (§15, §28) — Hint: P11 and MM3 in §32, plus the differential-testing paragraph of §28.
  2. Under what circumstances does Russian roulette (P8, I8) increase variance rather than decrease it, and how does the depth-3 floor (ADR-14) address that? (§6, §9) — Hint: P8's "violating it" sentence and §16.2 step 3.
  3. Why must the geometric normal and shading normal (P5) remain distinct even after Phase 9's normal mapping introduces a third "perturbed" normal, and which invariant (I11) would break if they were merged? (§6, §21) — Hint: P5, P7 and the §21.4 criterion about shadow rays.
  4. What is the relationship between the §30 M1 rays/second target and the §34 total-ray-count derivation — does hitting M1 in isolation guarantee hitting the M2 wall-clock target, or what else must also hold? (§30, §34) — Hint: §34 items 1, 2 and 8.
  5. Why does I2 (BSDF PDF consistency) need a chi-square test rather than a simple equality assertion, given that §11 defines sample_f and pdf as two separate trait methods that could trivially disagree? (§7, §11) — Hint: I2 in §7 and the §28 property-test paragraph.

If you only remember three things

A path tracer is an average of random samples, so every image-quality question is a variance question, and every sampling trick must leave the expected answer untouched (MM1, MM2, P3). The BVH is read-only after it is built and the tile is the unit of parallel work, so the renderer scales across cores without locks (P6, P14, MM8). Correctness is proven against numbers, such as the white-furnace test and brute-force BVH checks, never by looking at a picture (P4, P11, MM4).

Words used here

  • Radiance: light flux per unit projected area per unit solid angle; the quantity the renderer estimates.
  • Monte Carlo estimator: an average of f(X)/p(X) over random samples that converges to the true integral.
  • Importance sampling: drawing samples more often where the integrand is large, to cut variance.
  • BSDF: the function describing how a surface scatters light, reflection and transmission.
  • BVH: a tree of bounding boxes that lets a ray skip most of the scene.
  • SAH: the cost model that picks BVH split positions from child surface area and triangle count.
  • Next-event estimation: sampling a light directly at each non-specular bounce.
  • MIS: blending several sampling strategies with weights that sum to one.
  • Russian roulette: random path termination that stays unbiased through 1/p scaling.
  • White-furnace test: a uniform glowing environment used to check that a material conserves energy.
  • Shadow acne: speckle caused by a ray hitting its own surface because its origin was not offset enough.
