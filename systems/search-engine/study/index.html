Hard questions (§34)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does a BMW pruning bug manifest as missing results rather than a crash, and which two invariants jointly make that failure mode detectable in CI before production? (§7 I4/I6, §17.5)
  2. Why must the term dictionary be built from sorted input, and what breaks — concretely — if a delta-flush race allows unsorted input through? (§7 I7, §14.2)
  3. Trace exactly why a stemmed field can never safely serve as its own highlight source, using both the analyser-ownership principle and the highlighter's implementation split. (§6 P8, §19.2)
  4. Why does immutability (P6) make the real-time delta layer's read-path lock-free, and what would have to change in §11.5's trait if segments were mutable in place? (§6 P6, §11.5, §18.2)
  5. Derive why RRF needs no per-corpus tuning while weighted-sum does, using both the fusion formulas and the score-distribution argument. (§20.2–20.3, §32)
  6. Why is the FST's O(prefix-length) lookup insufficient by itself to make wildcard queries fast, and what additional technique closes the gap? (§6 P4, §17.8)
  7. Using the capacity model, explain why doubling the corpus size does not double query latency in the presence of BMW, but would without it. (§33 C5, §17.5)
  8. Why is a CRC computed over compressed bytes rather than decompressed postings, and what corruption class would escape detection under the alternative? (§7 I3, §15.6)
  9. Trace the full failure path of a crash during flush_block() from the segment lifecycle state machine through to what a subsequent query actually sees. (§8.4, §8.7, §18.9)
  10. Why does the coordinator set per-shard top_k to 2× the global value, and what precisely goes wrong at 1×? (§21.2, §21.6)
  11. Explain why P2 (one trait, two storage layers) is a correctness requirement and not merely a code-cleanliness preference, using a concrete real-time-visibility bug it prevents. (§6 P2, §18.7)
  12. Why is BM25F's tf' formula a generalization of BM25's tf rather than an unrelated scoring function, and what does it degenerate to at a single field with weight=1? (§17.2, §5 Robertson & Zaragoza)
  13. Using the scalability analysis and the ADR table, argue for or against choosing level-based merge over tiered merge for a write-heavy, rarely-queried log-archival deployment. (§9 ADR-05, §30)
  14. Why does a fuzzy query's Levenshtein-automaton term expansion need a hard cap, and what threat class does the cap defend against beyond raw performance? (§17.7, §23 T2)
  15. Explain why the hybrid fusion path pipelines sparse and dense retrieval concurrently rather than sequentially, quantifying the latency cost of getting this wrong. (§20.2, §4 network RTT constraint)
  16. Why is "no silent fallback" (P10) compatible with hybrid search's automatic sparse-only degradation (§20.9) — are these in tension, and how is the apparent contradiction resolved? (§6 P10, §20.9)
  17. Derive the FD-budget capacity number and explain what operational symptom appears first if the tiered merge policy's segment-count ceiling is misconfigured upward without raising the FD budget. (§33 C7, §24 FM4)
  18. Why does the blueprint reject Raft-based coordination for Phase 0, and under what concrete growth condition (named in the scalability analysis) does that rejection reverse? (§9 ADR-22, §30, §35)

31. Mental Models & First Principles

  • MM1 — A posting list is a compressed integer stream, not a list of documents. Predicts: every design decision (block size, codec choice, skip list) is an integer-compression problem wearing a search-engine costume. Bug class without it: treating postings as objects and adding per-document overhead that destroys the compression ratio (§33 C1). Applies at §15, §8.2.

  • MM2 — The searcher is a merge over sorted streams, not a database query. Predicts: document-at-a-time execution with cost-ordered iterators (§17.2) is the natural shape, not an afterthought optimization. Bug class without it: writing a naive nested-loop join instead of a merge, turning O(N log K) into O(N·K). Applies at §17.2, §17.3.

  • MM3 — A block-max statistic is a promise, and promises must be provably true. Predicts: any early-termination scheme is only as safe as its bound is tight and correct (I4). Bug class without it: shipping a "usually right" pruning heuristic that silently drops true top-k members (P13). Applies at §17.5, §7 I4/I6.

  • MM4 — Analysis is a pure function fixed at two points in time that must agree. Predicts: any asymmetry between index-time and query-time analysis manifests as "my exact query doesn't match" — the single most common production search bug. Bug class without it: re-tuning the query-time analyser without re-indexing, or vice versa. Applies at §13, I2, §8.5.

  • MM5 — Immutability is what makes concurrency free. Predicts: because segments never mutate (P6), readers need no locks against writers — the entire read-path concurrency story is "take a refcounted snapshot" (I8). Bug class without it: adding a mutex to "fix" a race that immutability would have prevented structurally. Applies at §18, §7 I1/I8.

  • MM6 — The merge policy is a scheduling problem, not a storage problem. Predicts: its parameters trade write amplification against read fan-out along one dial (tiered vs. level vs. none, §35), and getting it wrong looks like a performance bug but is actually a scheduling mis-tune. Bug class without it: chasing a "slow disk" hypothesis instead of retuning TieredMergePolicy (FM4). Applies at §18.4, ADR-05.

  • MM7 — Score-safety and speed are not the same axis. Predicts: an early-termination strategy can be arbitrarily fast and still wrong (or arbitrarily safe and still slow); the two properties must be evaluated independently, never traded against each other silently. Bug class without it: accepting a speedup PR without checking I6 first. Applies at §17.5, P13.

  • MM8 — Rank fusion is order statistics, not score arithmetic. Predicts: RRF's rank-based formula is robust exactly because it throws away the score magnitudes that differ incommensurably between BM25 and cosine similarity (§20.2); weighted-sum tries to keep the magnitudes and pays for it in normalization fragility. Bug class without it: tuning α per corpus forever instead of reaching for RRF first. Applies at §20.2–20.3, ADR-09.

Chs. 1–6: inverted index construction, term-at-a-time vs. document-at-a-time scoring, BM25 derivation — applied in §14, §17. Chs. 7–11: query expansion, language models, probabilistic retrieval — applied in §16 rewriter and §20 hybrid fusion. Chs. 18–21: web crawling, link analysis, clustering — background only, informs §32 comparative row on Google.
  • Büttcher, Clarke, Cormack, 2010. Information Retrieval: Implementing and Evaluating Search Engines, MIT Press. Ch. 5 (index compression), ch. 6 (query processing and pruning), ch. 8 (evaluation) — applied in §15 (codec selection) and §17 (WAND/BMW).
  • Witten, Moffat, Bell, 1999. Managing Gigabytes, 2nd ed., Morgan Kaufmann. Ch. 3 (inverted files), ch. 5 (compression codes) — applied in §15 (FOR/PFOR/varbyte lineage) and §33 (capacity arithmetic).

Reference Implementations

  • Apache Lucene (org.apache.lucene.codecs.lucene99.*, search.BooleanScorer, search.BM25Similarity, index.TieredMergePolicy). Lesson: block-size-128 + FST + tiered merge is a two-decade-converged local optimum — applied in §14, §15, §18. Pitfall: do not copy Java's GC assumptions into a manual-memory design; the block layout transfers, the allocation pattern does not.
  • Tantivy (tantivy/src/postings/, src/query/, src/indexer/). Lesson: closest existing Rust reference; segment layout and trait-object dispatch transfer cleanly — applied in §11, §18. Pitfall: Tantivy's single-writer-lock model is simpler than our concurrent-delta design; do not copy the lock granularity.
  • PISA (pisa/include/pisa/codec/simdbp.hpp, wand_data.hpp). Lesson: the reference for compressed-list query latency at billion-scale and for BlockMax-WAND — applied in §15.4, §17.5. Pitfall: PISA assumes a static, batch-built index; do not copy its assumption of no concurrent writers into §18's real-time delta layer.
  • Xapian (xapian-core/backends/glass/). Lesson: a mature, non-Java reference for posting-list chunking and a from-scratch B-tree-backed term list — applied in §14.5 (term-dictionary alternatives) and §35 (alternative architecture discussion). Pitfall: Glass's B-tree trades FST's compactness for update-friendliness; understand the trade before rejecting it (ADR-02).
  • Vespa (searchcore/src/vespa/searchcore/proton/, searchlib/.../queryeval/). Lesson: the right reference for federation and cross-shard aggregation — applied in §19, §21. Pitfall: Vespa's content-node model assumes a config-driven cluster controller; our Phase-0 coordinator is deliberately simpler (ADR-22 defers Raft membership).
  • Elasticsearch (server/src/main/java/org/elasticsearch/search/). Lesson: the reference for the JSON query-DSL layered atop a Lucene core, and for scatter-gather partial-failure semantics — applied in §21.4 (partial-failure tolerance).

Glossary (§37) · 51 terms · site-wide glossary

Analyser
the pipeline (CharFilter → Tokenizer → TokenFilter chain) that turns raw text into a token stream; owns all text handling per P8.
ASCII folding
a token filter mapping Latin-extended characters to their ASCII base form (e.g. é→e).
avgdl
average document length across a field, a BM25 statistic that must roll forward correctly across merges (§17.2).
Block-Max-WAND (BMW)
WAND extended with per-block maximum-score statistics, enabling whole-block skipping during top-k retrieval (§17.5).
BM25
the default probabilistic ranking function; scores term frequency saturated against document length normalization (§17.2, §5).
BM25F
BM25 generalized to weight multiple fields with per-field k1/b (§17.2).
Block-max score
the true upper bound on any document's score within one posting block; the safety property WAND/BMW pruning depends on (I4).
BLOCK_SIZE
the fixed number of documents per posting-list block, 128 by default (P5).
BTreeMap memtable
the in-memory sorted map backing the delta layer before flush (§18.2).
Codec
a block-level integer compression scheme (varbyte/FOR/PFOR/simd-bp128/Elias-Fano), §15.
Conjunction
a boolean AND query, executed by advancing all sub-iterators to agreement (§17.2).
Coordinator
the stateless component that authenticates, routes, and scatter-gathers requests across shards (§3, §21).
CRC32C
the checksum computed over each posting block's compressed bytes, detecting corruption (I3).
Decompounding
splitting a compound word (e.g. German) into searchable constituent stems (§13.2).
Delta layer
the in-memory, WAL-backed structure holding documents not yet flushed to a segment (§18.2).
Disjunction
a boolean OR query, executed via a min-heap over candidate doc-ids (§17.2).
DocId
a u32, shard-local document identifier (§11.1).
Document-at-a-time execution
the query-execution model advancing all posting iterators for one candidate document before moving to the next (§17.2).
Doc-values
a per-field, per-document columnar side-storage used for aggregations and sorting (§8.3).
Elias-Fano encoding
a compact encoding for monotonic integer sequences, used for dense document-store side indexes (§15.2).
Fan-out
the number of shards a coordinator request is scattered to (§21.2).
FieldId
a u16 identifier for a schema field (§11.1).
FOR (Frame-Of-Reference)
a block codec storing (min, [delta], bit_width) (§15.2).
FST (finite-state transducer)
the term-dictionary data structure mapping terms to posting offsets in O(prefix-length) (P4, ADR-02).
Fuzzy query
a query matching terms within a bounded edit distance, resolved via a Levenshtein automaton intersected with the FST (§17.7).
Hybrid retrieval
combining sparse (BM25) and dense (embedding) retrieval results, typically via RRF (§20).
IndexOptions
the per-field indexing granularity (docs / docs+freqs / +positions / +offsets), §11.2.
IndexReader / IndexWriter
the read-only and mutating traits over a shard's index (§11.9).
Inverted index
the core data structure mapping terms to the documents (and positions) containing them.
PFOR (Patched Frame-Of-Reference)
FOR with an exception side-list for outlier values (§15.2, ADR-04).
Posting
one (doc_id, term_freq, positions?, offsets?) entry in a term's posting list (§11.4).
Posting list
the ordered sequence of postings for one term, stored as compressed blocks (§8.2).
RRF (Reciprocal Rank Fusion)
a rank-based fusion formula summing 1/(k+rank) across result lists, robust to score-scale mismatch (§20.2, §5).
Scatter-gather
the coordinator pattern of fanning a request out to all shards and merging their responses (§21.2).
Schema
the named, typed field definitions for a shard's documents (§11.2).
Score-safety
the property that an early-termination strategy never drops a true top-k member (P13, I6).
Segment
an immutable, on-disk unit of the index (§8.3, P6).
SegmentId
a u32 identifier for a segment (§11.1).
Skip list
a sparse (doc_id, block_offset) index over a long posting list, enabling block-granularity seeks (§14.2).
Snapshot
a versioned, refcounted view of the segment list pinned for a request's lifetime (I8, §11.9).
Snowball
a stemming-algorithm bytecode format/interpreter supporting 20+ languages (§13.2, ADR-14).
Stemming
reducing a token to a common root form (e.g. running→run), §13.2.
Stopword
a language-specific, frequently occurring word dropped from the token stream by default (§13.2).
Term dictionary
see FST.
TermId
a u32 interned identifier for a unique term (§11.1).
Tiered merge policy
the LSM-style merge scheduler folding small segments into larger ones on size/count/age triggers (P7, ADR-05, §18.2).
Tombstone
a bitmap entry marking a document as deleted without removing its bytes until merge time (P6, I12).
Top-k collector
the bounded min-heap tracking the current best-scoring documents during search (§17.2).
UAX-29 / UAX-15
Unicode Standard Annexes for text segmentation and normalization forms respectively (§5).
WAL (Write-Ahead Log)
the durability mechanism recording writes before they are acknowledged, replayed on crash recovery (I10, I11, §18.2).
WAND (Weak AND)
the original score-safe top-k pruning algorithm generalized by BMW (§17.5, §5 Broder).
