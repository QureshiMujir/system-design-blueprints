Project Number: 80

Project Name: Search Engine

1. Goal & Scope

Build a Lucene-class inverted-index search engine, single-shard core plus a thin scatter-gather coordinator, in Rust: document ingestion → multi-language analysis → compressed on-disk posting lists in immutable segments → real-time visibility via an in-memory delta layer → Lucene-syntax query parsing → BM25/BM25F ranking with WAND/Block-Max-WAND early termination → aggregations and snippet highlighting → sparse+dense hybrid fusion. Conformance is measured against recorded Lucene baselines and the MS-MARCO / TREC retrieval tasks — not against opinion.

Phase-0 deliverable (numbered modules, one crate each unless noted):

  1. core — DocId/TermId/FieldId/SegmentId, Schema, Document, error types (§11).
  2. analyser — tokenizer/normaliser/stemmer pipeline (Phase 1, §13).
  3. codec — varbyte/FOR/PFOR/simd-bp128/Elias-Fano block codecs (Phase 3, §15).
  4. postings — posting-list writer/reader, block-skip-list (Phase 2, §14).
  5. dictionary — FST term dictionary (Phase 2, §14).
  6. query — lexer/parser/rewriter for the Lucene-style grammar (Phase 4, §16).
  7. search — iterators, BM25/BM25F scorers, WAND/BMW, top-k collector (Phase 5, §17).
  8. segment + delta — immutable segments, tiered merge policy, WAL (Phase 6, §18).
  9. aggregations + highlight — term/histogram/percentile aggs, unified highlighter (Phase 7, §19).
  10. hybrid — RRF/weighted-sum fusion, dense adapter (Phase 8, §20).
  11. coordinator + server — HTTP/gRPC, scatter-gather, replication (Phase 9, §21).
  12. conformance — CLI runner against recorded golden vectors (all phases).

System boundaries.

  • Provides: single-process shard engine; ingestion API; Lucene-syntax query API; BM25/BM25F ranking; real-time (≤1 s refresh) visibility; aggregations; highlighting; multi-shard scatter-gather with replica fail-over; sparse+dense hybrid fusion via an external vector service.
  • Delegates: dense-vector storage/ANN search to a Vector-Database service (Ranking 47); embedding computation to an Embedding-Similarity-Search service (Ranking 48); durable WAL framing conventions to the pattern documented in LSM-Tree-Storage (Ranking 70, referenced not vendored).
  • Does NOT provide: learning-to-rank model training; a distributed transaction coordinator; multi-datacenter replication; Raft-based shard membership; 2-D geo queries; per-tenant quota enforcement. All six are deferred features — see the Deferred Features Register (§36).

Non-goals: dialect-complete analysis for every world language (targets English, simplified and traditional Chinese, Japanese, Korean, Hindi, Arabic, German, French, Spanish, Russian only); exactly-once cross-shard transactions; a query planner that reorders relational joins (this is a document retrieval engine, not an OLAP engine).

Deployment model: one binary (searchd) per shard; a shard is a process with its own segment directory, delta layer, and WAL; shards are horizontally independent and speak to each other only through the coordinator's scatter-gather RPCs (§3). Operators run N shards behind one coordinator process (co-located for Phase 0; separable later).

Target users/operators: platform teams embedding full-text + hybrid search into an application backend; SRE/on-call staff running the shard fleet; ML engineers wiring in dense reranking.

What later phases unlock: Phase 8 (hybrid fusion) unlocks neural reranking; Phase 9 (coordinator) unlocks horizontal scale-out; Phase 10 (observability) unlocks a supportable production deployment. Stretch surfaces (learning-to-rank, multi-tenant quotas, Raft coordination, geo queries) are deferred and tracked in the Deferred Features Register (§36).

Recommended language: Rust 1.78+. Rationale: ownership-driven memory safety for posting-list buffers that are otherwise a classic C/C++ use-after-free/overflow surface; zero-cost trait dispatch for the PostingListReader/Scorer/Codec abstraction (§11); first-class SIMD via core::arch and std::simd for the codec hot path (§15); a mature async ecosystem (tokio) for the server boundary (§21) without forcing async onto the synchronous search hot path. Rejected: Java — Lucene already owns that niche and studying it as a reference is more valuable than re-deriving it (ADR-01); C++ — equal codec performance, weaker memory-safety guarantees for a project whose core asset is a hand-rolled binary format; Go — GC pauses are incompatible with p99 query-latency targets (§4).

Prerequisites: Information Retrieval to the level of Manning/Raghavan/Schütze chs. 1–11; Rust to the level of Box<dyn Trait>, lifetimes, unsafe discipline, SIMD intrinsics; Unicode (NFC/NFKC, UAX-29 segmentation); linear algebra sufficient to reason about cosine similarity for the hybrid path (§20).

Estimated timeline: Phase 0 in 1 week; the full 11-phase plan (§12–§22) in 14 weeks (~3.5 months) to a conformant single-shard-plus-coordinator system; hardening to the M9/M10 soak and fuzz gates (§29) adds 4–6 weeks beyond that.

2. Why Build This

  • The unique systems knowledge: the only way to internalize why a tokenizer mismatch between index-time and query-time analysis silently breaks exact-match search, why a posting-list codec that is fast but wrong on one block in a million is worse than a slow-but-correct one, why BM25's average-document-length statistic must roll forward correctly across a segment merge, and why a query parser's escaping rules are observable behavior rather than documented behavior, is to build the analyser, the codec, the merge policy, and the parser yourself.
  • Why it matters architecturally: search is the substrate under nearly every information surface ever shipped (web search, e-commerce, log search, code search, RAG retrieval); the inverted index + block-max early termination pattern here recurs, structurally unchanged, from 1998 web search (Brin & Page) through 2024 hybrid RAG stacks.
  • Why it matters historically: BM25 (Robertson & Zaragoza) has resisted twenty years of learned-ranking attempts to fully dislodge it as a first-stage retriever; understanding why is a calibration exercise in when a 1970s-lineage probabilistic model still wins.
  • Engineering muscles built: binary-format design under a correctness-first mandate (§6 P1); SIMD-accelerated decode loops with a byte-identical reference fallback; LSM-style merge-policy reasoning (shared muscle with LSM-Tree-Storage, Ranking 70); document-at-a-time query execution with score-safe pruning (WAND/BMW); scatter-gather distributed-systems reasoning under partial failure.
  • Cross-links to sibling systems: LSM-Tree-Storage (Ranking 70) — the merge-policy and WAL patterns transfer directly (§18); Vector-Database (Ranking 47) — the dense half of hybrid fusion (§20); Embedding-Similarity-Search (Ranking 48) — the reranking half (§20); Distributed-Cache (Ranking 61) — the replication pattern reused at §21.5.
  • Calibration value: a reader who can explain, from this document alone, why Lucene's block size is 128, why FST beats a hash map for the term dictionary, and why WAND needs block-max statistics to be safe, has calibrated principal-engineer judgment about the entire IR literature — not just this codebase.

What Mastery Looks Like:

  • Derive the FOR/PFOR/simd-bp128 bit-width choice for a given posting-list distribution without looking it up (cemented in Phase 3, §15).
  • Explain, precisely, why the searcher must never branch on segment-vs-delta storage layer (Phase 6, §18; Principle P2).
  • Reproduce the BM25 IDF derivation and state exactly which term it omits relative to classic probabilistic relevance (Phase 5, §17; Required Reading, §5).
  • Design a score-safe early-termination strategy from first principles and explain why block-max statistics — not just whole-list max — are required for it to be safe (Phase 5, §17).
  • Diagnose, from a production dashboard alone, whether a query-latency regression is a decode, merge, or intersection-cost problem (Phase 10, §22; Operational Readiness §25).
  • Redesign the storage layer as LSM-tiered vs. size-tiered vs. append-only-log and state exactly which read/write/space trade each makes (Alternative Architectures, §35).
  • Explain why RRF outperforms naive score-normalization fusion without retuning per corpus (Phase 8, §20; Required Reading §5).

Box-by-box. HTTP/gRPC frontend terminates untrusted client connections, deserializes requests, and is the only component that sees raw client bytes (trust boundary 1, §23). Coordinator is the only component aware of shard topology; it owns request fan-out and partial-failure merging (§21.3) and is stateless across requests. Shard engine is the unit of correctness: analyser and query parser are pure functions over text with no shared mutable state; indexer and searcher are the only components that touch the inverted index, and they do so through one shared trait boundary (PostingListReader, §11.5) so the searcher never branches on which storage layer served a posting. Inverted index is the immutable artifact boundary — nothing downstream mutates a posting once written (Principle P6). Aggregations/highlight run alongside the searcher as read-only observers of the same scored-document stream. Hybrid fusion adapter is the only component that crosses a service boundary to another blueprint's system (delegation, §1). Storage layer is the persistence boundary: segment files are rename-into-place atomic; the WAL is the crash-recovery source of truth for anything not yet in a segment (§18.6, I11).

Three load-bearing properties, referenced throughout: (1) the data path is one-way — documents flow down into the segment store, queries flow down into the searcher, posting lists are the immutable interface between them; (2) every backend (analyser, scorer, codec, merge policy) presents the same trait-bound interface (§11) and the searcher never branches on backend identity; (3) every cross-cutting resource (memory pool, Unicode tables, term dictionary, page cache) is owned by exactly one module and reached everywhere else only via a trait call, never a direct reach-across.

6. Design Principles

  1. P1 — Correctness is the ground truth. Every codec has a scalar reference path that is the conformance baseline; SIMD-accelerated paths must be bit-identical to it. Tradeoff: the reference path is kept even after the fast path ships (double maintenance). Violate it and a "fast" decoder that is wrong on one block in a million silently corrupts rankings — worse than a slow correct one.
  2. P2 — One engine, two storage layers, one trait. The immutable-segment layer and the in-memory delta layer both implement PostingListReader (§11.5); the searcher never branches on which layer served a posting. Tradeoff: the trait must be conservative enough to fit both. Violate it and real-time visibility logic leaks into the scorer, becoming untestable in isolation.
  3. P3 — Analysis is the document's property, not the searcher's. A document is analysed once at index time; the query is analysed at query time with the same analyser configuration per field. Tradeoff: changing an analyser requires re-indexing. Violate it and the user's exact query never matches the document (§7 I2, §16.2).
  4. P4 — The term dictionary is a finite-state transducer. FST gives O(prefix-length) lookup and 5–10× size reduction vs. a hash map (ADR-02). Tradeoff: FST construction requires sorted input, forcing a sort at flush time. Violate it (plain hash map) and term-dictionary memory blows past §4's 2.5 GB ceiling at 50 M terms.
  5. P5 — Posting lists are blocks of integers, no per-document headers. Fixed BLOCK_SIZE=128 blocks (doc-id delta + tf + optional positions + block-max stat), tail block for the remainder. Tradeoff: block granularity bounds skip precision. Violate it and per-document overhead dominates at scale (§33 C1).
  6. P6 — Segments are immutable. Updates are delete-tombstone + insert; GC happens at merge time. Tradeoff: deleted documents cost disk until the next merge. Violate it (in-place mutation) and concurrent readers lose the free consistent-snapshot property (I8).
  7. P7 — The merge policy owns time, not the indexer. Indexer flushes; a separate module decides when to fold, on explicit triggers (size/count/age) and explicit budgets (CPU/IO/fan-in). Tradeoff: merge scheduling adds a coordination layer. Violate it and indexing throughput and read amplification couple in an untunable way (§18.4).
  8. P8 — Strings are owned by the analyser. No other module decodes UTF-8 or normalizes Unicode; downstream sees TermId (interned u32) and analyser-owned byte slices. Tradeoff: every new text-touching feature must route through the analyser. Violate it and Unicode bugs (Turkish dotless-I, ZWJ sequences) surface in three different modules instead of one.
  9. P9 — Determinism is the default. Same documents, same order ⇒ byte-identical segments; merge policy and scorer are deterministic given the same inputs; stochastic components (learned reranking) are seeded. Tradeoff: some optimizations (unordered parallel merge) are foreclosed. Violate it and conformance fixtures (§14.5 et al.) become flaky.
  10. P10 — No silent fallbacks. A codec that cannot decode a block (bad CRC, unsupported version) raises; the caller decides. Tradeoff: no automatic "just serve something" degradation. Violate it and throughput predictability — the search-tier SLO — is destroyed by hidden slow paths.
  11. P11 — Memory pool per query, one global term-dictionary cache. Per-query allocations live in a query-scoped arena freed at end-of-query; no per-posting malloc/free on the hot path. Tradeoff: arena sizing must be tuned per workload. Violate it and allocator contention becomes the dominant cost at high QPS (§17.7).
  12. P12 — One shard is a unit of work; replicas are for availability, not sharding. The router treats replicas as interchangeable reads; only the primary accepts writes. Tradeoff: replica reads can lag (§21.5). Violate it (writes to any replica) and you have reinvented a conflict-resolution problem this engine explicitly does not solve.
  13. P13 — Score-safety before speed. Any early-termination strategy (WAND, BMW, MaxScore) must be provably score-safe (never drops a true top-k member) before it is allowed to ship; speed gains beyond that are free upside, never a justification to relax safety. Violate it and top-k results become silently incomplete (§17.5, I6).
  14. P14 — Every backend is swappable through one trait, never a call-site if. Analyser, Codec, Scorer, MergePolicy all present trait-bound interfaces (§11); the search/index hot path contains zero match backend_kind {} dispatch outside the trait impl itself. Violate it and adding a new codec requires touching every call site instead of one impl block.
  15. P15 — Observability is a first-class output, not an afterthought. Every phase ships named metrics/traces before it ships an optimization (§22, §25). Violate it and a production latency regression becomes undiagnosable from the dashboard alone.

These principles are enforced at the type level where possible (P2, P4, P8, P14 via trait boundaries), by conformance fixtures where not (P1, P9, P13).

8. Domain Model / Protocol / Data Model

8.1 Query grammar (EBNF)

query          = disjunction ;
disjunction    = conjunction , { "OR" , conjunction } ;
conjunction    = factor , { [ "AND" ] , factor } ;
factor         = [ "NOT" | "+" | "-" ] , clause ;
clause         = group | term-clause | phrase-clause | field-clause | range-clause ;
group          = "(" , disjunction , ")" ;
field-clause   = ident , ":" , clause ;
term-clause    = term , [ "~" , integer ] , [ "^" , float ] ;
phrase-clause  = '"' , { term } , '"' , [ "~" , integer ] , [ "^" , float ] ;
range-clause   = ( "[" | "{" ) , (range-value | "*") , "TO" , (range-value | "*") ,
                  ( "]" | "}" ) , [ "^" , float ] ;
range-value    = integer | float | date | keyword ;
term           = unicode-word | escaped-unicode-word ;

Operator precedence: NOT > AND > OR; parentheses override. Bare juxtaposition (foo bar) is a disjunction (Lucene-compatible default, ADR-08).

8.2 Posting-list wire/storage layout

posting list:
  [block 0][block 1] ... [block N-1][tail]
each block (fixed 128 docs, except tail):
  header:    doc_count:u8 | codec_id:u8 | bit_width:u8 | flags:u8
  doc_ids:   delta-encoded, codec-compressed (§15)
  tfs:       codec-compressed
  positions: offset into separate .pos stream (only if field has positions)
  block_max_doc_id: u32
  block_max_score:  f32   (I4)
  crc32c:           u32   (I3)
tail:
  varbyte-encoded remainder, no block-max fields

8.5 Worked example — query rewrite

Input: title:"quick brown"~2 AND status:active. Lex → [FIELD(title) COLON PHRASE("quick","brown") TILDE 2 AND FIELD(status) COLON TERM(active)]. Parse → Query::Boolean{ must: [Phrase{field:title, terms:["quick","brown"], slop:2}, Term{field:status, term:"active"}], should: [], must_not: [], minimum_should_match: 1 }. Rewrite applies the title field's analyser (stemming off, lowercase on) to "quick"/"brown" and the status field's keyword analyser (exact, no stemming) to "active" — this is where P3 is enforced: if status were accidentally stemmed, "active" could rewrite to "activ" and never match a keyword-indexed "active" value.

8.6 Malformed-input example

Input: title:"unterminated phrase AND x:1. Lexer reaches EOF inside the phrase quote. Parser raises SearchError::QueryParse{ col: 38, msg: "unterminated phrase literal" }. The HTTP layer maps this to 400 Bad Request with the column echoed in the response body so a client can underline the offending character. Conformance fixture: conformance/corpora/query/malformed-001.json (§16.5).

8.7 Failure-path example

Indexing thread crashes mid-flush_block() after writing 96 of 128 doc-id deltas but before the CRC is written. On restart, segment::reader opens the .post file, encounters a block whose trailing CRC bytes are absent (Building-state temp file, never renamed into place per I1), and the previous committed segment (still Live) is used for search unaffected. The partial _tmp file is garbage-collected on next flush attempt. No corrupt bytes ever reach a Live segment because commit is a single atomic rename (§8.4 Committing → Live), not an in-place write.

14.1 Objectives

15. Phase 3 — Posting-List Codecs (Weeks 4–5)

15.1 Objectives

Ship the codec library — varbyte, FOR, PFOR, simd-bp128, Elias-Fano — and the per-block dispatcher that picks one, with a scalar reference path that every SIMD path must match bit-for-bit (P1).

15.2 Detailed Implementation Steps

  • Varbyte: 7-bit groups + continuation bit; 1 byte per value < 128; dominant on tail blocks (Witten/Moffat/Bell, §5). Reference/fallback path for all bit widths.
  • FOR (Frame-Of-Reference): block → (min, [value−min], bit_width), bit_width = ceil(log2(max−min+1)) (Anh & Moffat, §5, ADR-04 territory). Degenerate bit_width=0 (all-equal block) is a named edge case (§15.8).
  • PFOR (Patched FOR): pick bit_width covering ~90% of values; remaining 10% stored as (index, value) exception side-list (ADR-04). Threshold tuned to the BM25 posting-list distribution; documented as workload-sensitive.
  • simd-bp128 (Lemire & Boytsov, §5): SIMD-shuffle bit-packing of 128-integer blocks; one pack/unpack routine per bit width 1..32, runtime-dispatched; ~5 GiB/s decode on AVX2 (M5, §29), ~2 GiB/s on NEON (M6, §29) — anchors ADR-03.
  • Elias-Fano: monotonic-sequence encoding in N·(2+⌈log2(U/N)⌉) bits via a rank-select bit-vector; used for the dense document-store side index; O(1) decode per element.
  • Dispatcher (codec::pick_codec): selects per-block by statistics — tail (<32 values) → Varbyte; degenerate range → FOR bit_width 0; low outlier fraction (<10%) + SIMD-eligible bit width → SimdBp128; low outlier fraction otherwise → PFOR; else FOR. Selection is itself a conformance-fixture-gated decision table, not free-form heuristic drift (I6-adjacent: dispatcher choice must match a recorded baseline).
  • Endianness: all on-disk integers little-endian (I3-adjacent correctness requirement); no host-endian leakage.

17. Phase 5 — Search Execution (Weeks 7–8)

17.1 Objectives

Land the document-at-a-time executor: conjunction/disjunction/phrase/proximity/fuzzy/range/wildcard iterators, BM25/BM25F scoring, WAND/Block-Max-WAND early termination (P13), the top-k collector.

17.2 Detailed Implementation Steps

  • Execution model: document-at-a-time (P13) — advance each posting iterator to the next candidate, evaluate the boolean predicate, score if accepted, push to the top-k heap (§11.6, §11.5).
  • Conjunction (must): sort sub-iterators by cost() (§11.5) ascending so the cheapest (shortest posting list) drives candidate generation; each candidate is confirmed via advance() on the remaining iterators — a mismatch aborts the candidate (Croft/Metzler/Strohman ch. 5, §5).
  • Disjunction (should): min-heap of iterators ordered by current doc-id; naive form is O(N log K) across K terms; top-k disjunction uses Block-Max-WAND instead (§17.5).
  • Phrase/proximity (§17.4): after conjunction, positions arrays are walked in lockstep per candidate; slop-0 requires pos_i+1 == pos_{i+1}, slop-k requires pos_i+1 ≤ pos_{i+1} ≤ pos_i+1+k.
  • BlockMax-WAND (§17.5): pivot selection finds the smallest doc-id whose prefix-sum of per-term max-scores exceeds the current top-k threshold (Broder 2003 WAND, extended by Mallia et al. 2017 with per-block max, ADR-07); a block whose block-max sum is still below threshold is skipped whole (I4's block-max bound is what makes this safe, P13).
  • BM25/BM25F (§17.6): default k1=1.2, b=0.75, both per-field tunable; BM25F field-weights tf'(t,D) = Σ_f weight_f · tf(t,D,f) / B_f in place of raw tf (Robertson & Zaragoza, §5, ADR-06).
  • Fuzzy (§17.7): precompile a Levenshtein automaton (known finite-state shape for k∈{1,2}, DP fallback for k>2) and intersect with the FST (§14) term dictionary; result set becomes an inner disjunction; capped at 1,024 intersected terms (Lucene-matching default, documented warning on cap hit).
  • Wildcard/regexp (§17.8): compile pattern, extract a literal prefix to seek the FST (avoids O(vocab) worst case); regexp compiles via regex-automata to a DFA intersected with the FST.
  • Range (§17.9): 1-D BKD-tree for numeric/date ranges (Lucene-standard approach); 2-D BKD for geo bounding-box is PhaseDeferred("§17.9") (§36).
  • Top-k collector: bounded min-heap of (score, doc_id), push replaces the minimum when a higher-scoring candidate arrives once at capacity.

17.6 Pitfalls

  • Float comparison in the top-k heap — use a total-order float wrapper; never let NaN poison comparisons.

17.9 Failure Analysis

18. Phase 6 — Segments, Merge Policy, Real-Time Index (Weeks 9–10)

18.1 Objectives

Land the persistent index: immutable segments (P6), the LSM-style tiered merge policy (P7, ADR-05), the in-memory delta layer with WAL, and the snapshot semantics (I8) that keep the index queryable while writes are in flight.

18.2 Detailed Implementation Steps

  • Segment file set per §8.3 (.terms .post .pos .skip .docv .doc .del .meta); files append-only at write time, rename-into-place at commit (§8.4 Building→Committing→Live, enforcing I1).
  • segment::writer finalizes each field writer, renames temp files to final names, writes the manifest — this atomic rename is the entire durability contract for I1.
  • segment::reader mmaps segment files at open, parses the manifest, builds per-field FST handles (§14), precomputes per-field avgdl and BM25 statistics (§17.6) so search-time work is pure traversal.
  • Tiered merge policy (TieredMergePolicy-alike, ADR-05, Kleppmann ch. 3, §5): parameters max_segments_per_tier=10, max_segment_size=5 GB, floor_segment_size=2 MB, merge_factor=10; policy returns merge specs, a separate merge thread executes them out-of-band (P7) — the searcher keeps querying pre-merge segments until the merge commits (§8.4 Merging→Retired).
  • Tombstones: deletes are bitmap entries in .del (I12); every posting iterator filters at the iterator boundary; GC of tombstoned documents happens only at merge time, when the merged segment writes only live documents.
  • Delta layer: writes go to the WAL (durability, I11) then the in-memory memtable (BTreeMap<term, Vec<Posting>>); on commit the memtable sorts (I7 precondition), writes as a new segment, WAL rotates; on crash the WAL replays in strict sequence order (I10) against an empty memtable.
  • Real-time visibility: a search request sees all committed segments plus in-flight delta writes past the refresh boundary (default 1 s); the delta-layer reader implements the same PostingListReader trait (P2) — the searcher never branches on layer.
  • Snapshot (§11.9) pins a segment-list version at request start (I8); refresh increments the version; a long-running query holding an old snapshot blocks GC of the segments it references until release.

  • Crash test: kill the process mid-write, restart, replay WAL — zero data loss past the last committed commit() call (I11, RPO=0 per §4).

18.6 Pitfalls

  • rename-into-place atomicity is filesystem-specific — works on ext4/xfs/apfs, unreliable on overlayfs; document supported filesystems explicitly.
  • Merge-policy parameters are workload-coupled — ship the §18.2 defaults but expose them in EngineConfig.
  • WAL fsync is the write-throughput bottleneck — group commits across submitters, fsync ∈ {none, batch, always}, default batch with a 5 ms group window.
  • Tombstone bitmaps grow with deletes — a segment above 30% deleted-fraction is a merge candidate even below the size threshold.

18.7 Performance Concerns

Merge I/O competes with query read I/O for the same NVMe bandwidth — the merge thread's IO budget is capped (§4 storage-amplification constraint) so a large merge cannot starve concurrent queries; mmap page-fault cost on cold segments is amortized by warming the FST + first block on segment open.

18.8 Edge Cases

A crash during Committing (rename in progress) — the pre-rename temp file is simply orphaned and GC'd, the prior Live segment remains authoritative (§8.7 worked failure path); a merge selecting a segment that a concurrent second merge attempt also selects (I13 prevents this); clock skew affecting created_at/last_merged_at ordering in the merge policy's age trigger.

18.9 Failure Analysis

A WAL corruption (partial record at crash boundary) is detected by a per-record checksum; replay stops at the last valid record (I10) and the corrupted tail is discarded — this bounds data loss to at most the unfsync'd tail, never earlier committed data (I11). Forensic artifact: the discarded tail bytes are archived to notes/ for offline analysis, never silently dropped.

18.10 Operational Notes

19. Phase 7 — Aggregations & Highlighting (Week 11)

19.1 Objectives

Land term/numeric-histogram/date-histogram/percentile aggregations and unified/plain snippet highlighting, both running as read-only observers alongside the top-k collector (§3 box description).

19.2 Detailed Implementation Steps

  • Aggregation framework: an Aggregation is a Collector that runs alongside search::collector (§17), observing each scored document and updating per-bucket statistics — no separate scan of the posting lists.
  • Term aggregation: per-shard HashMap<TermId, u64> count, coordinator merges per-shard maps with top-N selection (§21); min_doc_count and size (top-N) are configurable; a documented bucket_overflow flag fires when cardinality exceeds the in-memory cap (§19.6 pitfall).
  • Histogram/date-histogram: bucket index = (value − origin) / interval; dense buckets use a Vec<u64>, sparse buckets fall back to HashMap<i64,u64>; date-histogram interval arithmetic uses calendar-aware libraries (months/weeks), never raw millisecond division.
  • Percentile: t-digest (Dunning, §5) online quantile estimation; per-shard digests merged at the coordinator (§21); HDR-histogram offered as an opt-in for bounded-range fields.
  • Highlighting — unified highlighter (default): re-analyse the field at query time with the same analyser as index time (P3, I2), match tokens against the query's MatchSet, score sentences by matching-token weight, emit top-N snippets with <em> markup. Plain highlighter (cheap alternative): operates on stored-field bytes with simple position-list intersection — documented as unusable on stemmed fields (§13.6 pitfall cross-reference).

20. Phase 8 — Hybrid Sparse + Dense Fusion (Week 12)

20.1 Objectives

Ship the hybrid retrieval path: BM25 (sparse) and dense-vector (delegated, §1) results combined via RRF or weighted-sum (ADR-09), with an optional neural-reranker hook on the merged top-k.

20.2 Detailed Implementation Steps

  • Dense adapter: thin client to the Vector-Database service (Ranking 47, delegation per §1) behind a DenseRetriever trait (P14); implementations: LocalHnswRetriever (dev), RemoteVectorDbClient (production), MockRetriever (tests).
  • RRF fusion (Cormack, Clarke, Buettcher 2009, §5): RRF(d) = Σ_l 1/(k + rank_l(d)), k=60 standard default; rank-based, robust to score-scale mismatch between BM25 and cosine similarity, no per-corpus tuning required (anchors ADR-09).
  • Weighted-sum fusion: score(d) = α·score_bm25(d) + (1−α)·score_dense(d) with both inputs min-max normalized first (score-scale mismatch is otherwise fatal, §20.6 pitfall); α=0.5 reasonable default, tunable per corpus.
  • Sparse and dense retrieval run concurrently (pipelined, not sequential) — the dense path's latency dominates end-to-end hybrid latency, so overlapping it with sparse retrieval is required to hit M12's target (§29).
  • Neural reranker: cross-encoder over the merged top-k, calling into the Embedding-Similarity-Search service (Ranking 48, delegation per §1); adds 50–200 ms at top-k=100 — documented as a high-precision, latency-costly opt-in, capped to top-k ≤ 100 by default.

21. Phase 9 — HTTP/gRPC Server, Coordinator, Scatter-Gather (Week 13)

21.1 Objectives

Ship the network surface (axum HTTP + tonic gRPC, ADR-10), the coordinator that routes requests to shards, the scatter-gather merger, and partial-failure tolerance across shard replicas (P12).

21.2 Detailed Implementation Steps

  • HTTP endpoints: POST /v1/index, POST /v1/index/bulk (NDJSON), POST /v1/search, POST /v1/aggregations, POST /v1/highlight, GET /v1/admin/segments, POST /v1/admin/merge, GET /v1/admin/snapshots, GET /healthz, GET /readyz, GET /metrics. gRPC mirrors the same surface via docs/api/search.proto (§10).
  • Coordinator: validates + authenticates, parses and rewrites the query (§16), selects target shards (default: scatter to all), issues parallel fan-out RPCs, gathers and merges responses.
  • Scatter-gather: fan out SearchRequest to all shard clients concurrently; per-shard top_k is set to 2 × global_top_k (documented tradeoff, §21.6 pitfall) so the merged top-k is correct; merge combines per-shard SearchResponses by score; a shard timeout or error is recorded as a partial failure, not a whole-request failure, unless every shard fails (§21.4).
  • Partial-failure tolerance: if some but not all shards fail, return the partial result with a partial_failures field naming the failed shard ids — the search-tier SLO is "available results", not "all-or-nothing" (P12).
  • Replication (P12): a shard has one primary + N replicas; writes go to the primary, which appends to its WAL and forwards records to replicas (pattern shared with Distributed-Cache, Ranking 61, §5); replicas catch up asynchronously; reads default to the primary, falling back to replicas on primary failure (RTO ≤ 5 s, §4).

  • Per-shard top-k must be ≥ global top-k or the merged top-k is silently wrong — default 2 × global_top_k, document the multiplier as a tunable tradeoff (memory vs. correctness margin).
  • Partial-failure tolerance is easy to get subtly wrong — test extensively with chaos-style random shard timeouts and connection resets, not just clean kills.
  • Replication lag means a just-committed write may not be visible on a replica for up to the refresh boundary (§18.7) — default read-after-write consistency to "primary read" for write-heavy workloads.

21.9 Failure Analysis

Total scatter-gather failure (all shards down) is a P0 outage — detection is the partial_failures count equaling shard count; containment is the coordinator's circuit breaker rejecting new requests fast (fail-fast) rather than queuing behind a dead cluster; recovery is shard-by-shard restart with WAL replay (§18.9).

25. Operational Readiness

Metrics, tracing, structured logging: the single catalog in §22.2, exported over /metrics (Prometheus, ADR-19) and OpenTelemetry (ADR-18); structured logs (JSON lines) at DEBUG (document/query bodies, redacted per T7) and INFO (metadata only).

Dashboards: one Grafana dashboard (ops/grafana/, §10) graphing QPS, p99 latency, decode throughput, segment count per tier, BMW skip ratio — generated from the §22.2 metric names, never hand-duplicated.

Alerting philosophy: alert on symptom (p99 latency, error rate, replica lag), never on cause alone (e.g. "merge running" is not itself alertable — merge count trending past the tier ceiling is, per FM4); every alert links to the runbook that resolves it (§10 docs/runbooks/).

SLOs: 99.9% query availability per shard-month (§4); p99 query latency ≤ 50 ms (M3, §29); indexing throughput ≥ 100,000 docs/sec sustained (M1, §29). Breach of any SLO pages on-call per the error-budget policy (28 days rolling window, standard SRE practice).

Incident response: docs/runbooks/triage.md (§22.2) is the first ten minutes; severity is classified by blast radius (FM1–FM3 are single-segment/single-query-class; FM6 is whole-coordinator) using the Failure Modes table (§24) as the triage lookup.

Named runbooks (§10): triage.md, slow-queries.md, ingestion-lag.md, shard-rebalance.md — each references the exact metric names in §22.2, never an ad hoc metric.

Backup/restore: segment files are the backup unit (immutable, P6) — a backup is a point-in-time copy of a shard's segment directory plus its WAL tail; restore is: stop shard, copy segment directory + WAL into place, start shard (WAL replay, §18.9, reconstructs any unflushed delta state).

Deployment topology: one searchd process per shard replica; coordinator co-located with shard 0 in Phase 0, separable to its own process/host once shard count grows (§30).

Canary / rolling-upgrade / rollback / migration strategy: new binary version deployed to one replica first (canary); the coordinator's health check gates traffic shift; rollback is redeploying the prior binary version against the same segment/WAL format (compatibility guaranteed within a major version, §26); a storage-format migration (major version bump) requires an offline re-index or a documented online migration tool (PhaseDeferred("§26"), tracked in §36).

26. Compatibility & Versioning

Wire compatibility: HTTP/gRPC API follows SemVer; additive fields (new optional SearchRequest/SearchResponse members, §11.8) are minor-version changes; removing or repurposing a field is a major-version change requiring a documented migration window.

Storage compatibility: <seg>.meta (§8.3) carries an explicit schema-version integer; a new BlockCodec variant (§11.4) or a SegmentMeta field removal is a storage-format-breaking change gated behind a manifest version bump; segment::reader refuses to open a manifest version newer than it understands (fail loud, P10) rather than guessing.

Schema evolution: adding a Field to a live Schema (§11.2) is backward-compatible (documents missing the new field are simply absent from it); changing an existing field's FieldType requires re-indexing that field (no in-place type coercion — silent coercion is a correctness risk P1 forbids).

API stability: the OpenAPI/proto definitions (docs/api/, §10) are the versioned contract; a deprecated endpoint is marked in OpenAPI with a sunset date and continues to function for at least one major version cycle.

Migration policy: a storage-format-breaking change ships with either (a) an offline re-index tool, or (b) a documented online migration path that reads the old format and writes the new one segment-by-segment during otherwise-idle merge cycles.

Deprecation policy: minimum one minor-version-cycle deprecation warning (structured log + response header) before removal; breaking changes only at major-version boundaries.

SemVer policy: MAJOR.MINOR.PATCH — MAJOR for storage-format or wire-breaking changes, MINOR for additive API/feature changes, PATCH for bug fixes with no format/API change.

Rolling-upgrade guarantees: a shard running version N and a shard running version N+1 (same major) can coexist during a rolling upgrade because segment format is unchanged within a major version; the coordinator does not require all shards to be on the same minor version to serve correct scatter-gather results.

Unit tests: per-crate (§10), one test module per source file; cover every Codec (§15), every tokenizer/stemmer (§13), the parser grammar (§16.4).

Integration tests: tests/integration/ per crate — segment stress test (§18.4), crash-replay (§18.5), scatter-gather (§21.4), replica fail-over (§21.4).

29. Performance Engineering

Methodology: every target below is measured on the §4 reference hardware, gated in CI via benchmarks/ (§10), and re-run on every release candidate. Profiling uses perf (Linux) for cache-miss and syscall analysis, valgrind --tool=massif for allocation profiling, and flamegraphs generated from perf record for lock-contention and tail-latency triage.

Allocation analysis: the query arena (P11) is instrumented to report high-water-mark per query shape; a regression in arena high-water-mark for a fixed query shape is itself a CI-gated signal independent of latency (catches allocation regressions before they manifest as latency ones).

Lock/contention analysis: the only lock on the query hot path is the merge-lock set (I13); its hold time is measured via perf lock and must stay under 100 µs p99 to avoid stalling concurrent merges without stalling queries (queries never take this lock — only the merge scheduler does).

Cache/syscall analysis: posting-block decode is profiled for L1/L2 miss rate (target: <5% L2 miss rate at steady-state QPS, §15.7); io_uring/mmap page-fault rate is tracked per shard to catch cold-cache regressions after a deploy.

Tail-latency analysis: p99/p99.9 are tracked separately from p50/p95 (§4); the dominant tail contributor is identified per release via trace sampling (§22.2) — historically either GC-equivalent allocator pauses (mitigated by P11's arena model) or merge-induced I/O contention (§18.7).

30. Scalability Analysis

Constant regardless of scale: per-query CPU cost for a fixed result-set size (O(1) in corpus size once BMW pruning is engaged, §17.5); FST point-lookup cost (O(prefix length), independent of vocabulary size, P4); per-document analyser cost (independent of corpus size, P3).

Grows with scale, and its Big-O: posting-list length grows O(corpus size) per common term, driving decode cost linearly absent pruning (§15); FST size grows roughly O(vocabulary size) (sub-linear in corpus size past a point, since vocabulary growth flattens, Heaps' Law); merge I/O grows O(corpus size · log(corpus size / floor_segment_size)) under the tiered policy (§18.4); term-dictionary memory grows O(vocabulary size) (M13's 2.5 GB ceiling at 50M terms, §33).

Named bottlenecks, in order: (1) posting-list decode throughput (§4's defining read-path property) — mitigated by codec choice (§15) and BMW pruning (§17.5); (2) merge I/O contention with query I/O on the same NVMe (§18.7) — mitigated by IO budget capping; (3) coordinator fan-out network RTT (§4) — mitigated by same-AZ shard placement; (4) term-dictionary memory at very large vocabularies (multi-hundred-million terms) — mitigated by sharding (below).

Horizontal scaling: add shards; each shard is an independent unit of work (P12) — the coordinator's scatter-gather fan-out cost grows O(shard count) in RPC overhead but each shard's individual query cost stays constant (assuming even document distribution). Sharding key is typically hash-of-external_id for even distribution, or a semantic key (e.g. tenant id) when per-tenant isolation matters (§36 multi-tenant deferral).

Vertical scaling: more RAM increases the page-cache hit rate for posting-block reads (diminishing returns past working-set size); more cores increases per-shard query concurrency (§4's 512 in-flight ceiling) up to the point where merge-thread and query-thread CPU contend.

Sharding/partitioning: single-shard ceiling is ~1B postings / ~5TB (§4); beyond that, split by hash-of-document or by a semantic partition key; re-sharding is an offline or online-migration operation (§26) — Raft-based dynamic membership is not automatic in Phase 0; it is deferred (§36).

Coordination overhead: grows with shard count (RPC fan-out) and with replica count (WAL forwarding, §18.2); the practical ceiling for the Phase-0 single-leader-plus-replicas design is tens of shards before coordination overhead (not per-shard query cost) dominates total latency — beyond that, the lever is Raft-based membership and hierarchical fan-out (both deferred, §36; explored as regime shifts in §35).

Practical ceiling and the levers beyond it: at corpus sizes beyond a few hundred billion postings across a fleet, the levers are (a) hierarchical scatter-gather (coordinator-of-coordinators) to bound fan-out width, (b) tiered hot/warm/cold segment placement — PhaseDeferred("§30") — to bound working-set memory pressure, (c) learned-sparse or dense-only retrieval for the coldest tiers to trade recall for a smaller index footprint.

31. Mental Models & First Principles

  • MM1 — A posting list is a compressed integer stream, not a list of documents. Predicts: every design decision (block size, codec choice, skip list) is an integer-compression problem wearing a search-engine costume. Bug class without it: treating postings as objects and adding per-document overhead that destroys the compression ratio (§33 C1). Applies at §15, §8.2.

  • MM2 — The searcher is a merge over sorted streams, not a database query. Predicts: document-at-a-time execution with cost-ordered iterators (§17.2) is the natural shape, not an afterthought optimization. Bug class without it: writing a naive nested-loop join instead of a merge, turning O(N log K) into O(N·K). Applies at §17.2, §17.3.

  • MM3 — A block-max statistic is a promise, and promises must be provably true. Predicts: any early-termination scheme is only as safe as its bound is tight and correct (I4). Bug class without it: shipping a "usually right" pruning heuristic that silently drops true top-k members (P13). Applies at §17.5, §7 I4/I6.

  • MM4 — Analysis is a pure function fixed at two points in time that must agree. Predicts: any asymmetry between index-time and query-time analysis manifests as "my exact query doesn't match" — the single most common production search bug. Bug class without it: re-tuning the query-time analyser without re-indexing, or vice versa. Applies at §13, I2, §8.5.

  • MM5 — Immutability is what makes concurrency free. Predicts: because segments never mutate (P6), readers need no locks against writers — the entire read-path concurrency story is "take a refcounted snapshot" (I8). Bug class without it: adding a mutex to "fix" a race that immutability would have prevented structurally. Applies at §18, §7 I1/I8.

  • MM6 — The merge policy is a scheduling problem, not a storage problem. Predicts: its parameters trade write amplification against read fan-out along one dial (tiered vs. level vs. none, §35), and getting it wrong looks like a performance bug but is actually a scheduling mis-tune. Bug class without it: chasing a "slow disk" hypothesis instead of retuning TieredMergePolicy (FM4). Applies at §18.4, ADR-05.

  • MM7 — Score-safety and speed are not the same axis. Predicts: an early-termination strategy can be arbitrarily fast and still wrong (or arbitrarily safe and still slow); the two properties must be evaluated independently, never traded against each other silently. Bug class without it: accepting a speedup PR without checking I6 first. Applies at §17.5, P13.

  • MM8 — Rank fusion is order statistics, not score arithmetic. Predicts: RRF's rank-based formula is robust exactly because it throws away the score magnitudes that differ incommensurably between BM25 and cosine similarity (§20.2); weighted-sum tries to keep the magnitudes and pays for it in normalization fragility. Bug class without it: tuning α per corpus forever instead of reaching for RRF first. Applies at §20.2–20.3, ADR-09.

33. Back-of-Envelope Capacity Model

All numbers derived from §4 (System Constraints); formula shown for each.

  • C1 — Postings-bytes at the single-shard ceiling. bytes = postings × (4B/compression_ratio + tf_bytes). At the §4 ceiling of 1B postings, compression ratio ≥6× (§4) gives doc-id cost ≤0.67 B; PFOR-packed tf adds ~1 B ⇒ ≤1.67 B/posting ⇒ ≤1.67 GB doc-id+tf bytes per shard (positions, when enabled, roughly double this for positional fields — §8.2's separate .pos stream is exactly why non-positional queries never pay it).
  • C2 — Term-dictionary memory (FST). bytes = terms × bytes_per_term_FST. M13/§4 budget ≤2.5 GB at 50M terms ⇒ ≤50 B/term average FST cost — consistent with ADR-02's claimed 5–10× reduction vs. a ~250–500 B flat sorted-string entry.
  • C3 — Indexing ingest bandwidth. bandwidth = docs/sec × avg_doc_bytes. M1's 100,000 docs/sec at the assumed 1 KB/doc (5 fields) ⇒ 100 MB/s raw text ingest — against the §4 NVMe sequential-write floor of ≥2 GB/s, this leaves a 20× margin for simultaneous WAL + segment writes.
  • C4 — Per-shard query-CPU ceiling. queries/core/sec = 1000 ms / cpu_ms_per_query. §4's ≤4 core-ms/query budget ⇒ 250 queries/core/sec; × 8 cores (§4 reference hardware) ⇒ ~2,000 q/s theoretical per-shard ceiling before contention — cross-checked against M4 (5,000 QPS ÷ 4 shards = 1,250/shard), leaving headroom for coordination overhead (§30).
  • C5 — Decode-bound query latency contribution. latency = bytes_decoded / decode_throughput. A term at 1% selectivity in a 1B-posting shard has df≈10M ⇒ ≈78,125 blocks; at M7's 70% BMW skip ratio, ≈23,437 blocks are actually decoded ⇒ ≈6 MB of doc-id+tf bytes; at M5's 5 GiB/s AVX2 decode ⇒ ≈1.1 ms — comfortably inside the §4 p50 budget of 8 ms, leaving room for intersection, scoring, and network.
  • C6 — WAL batch-fsync sizing. batch_bytes = (docs/sec × fsync_window_sec) × avg_record_bytes. At 100,000 docs/sec (M1) and the §18.6 5 ms group-commit window ⇒ 500 docs/batch; at ~200 B/record (analyzed tokens + doc-id) ⇒ ≈100 KB/batch — well inside NVMe's ≥2 GB/s sequential write floor, so fsync=batch (ADR default, §18.6) never becomes the bottleneck at this throughput.
  • C7 — FD budget vs. concurrently open segment sets. max_open_sets = fd_budget / files_per_segment. §4's 4,096-FD ceiling ÷ 8 files/segment (§8.3) ⇒ ≈512 concurrently open segment file-sets — comfortably above the tiered policy's steady-state segment count (§18.2's max_segments_per_tier = 10 × a handful of tiers).
  • C8 — Storage-amplification headroom. transient_overhead = live_bytes × (amplification_ceiling − 1). At §4's ≤1.3× ceiling, a 1 TB live corpus has a transient merge overhead ceiling of ≈300 GB — both must fit inside the §4 5 TB segment-bytes ceiling, leaving a ~3.5× growth margin before re-sharding (§30) becomes necessary.

35. Alternative Architectures (Roads Not Taken)

35.1 Signature-file retrieval

doc → hash each term into an m-bit Bloom-style signature
      → OR all term-signatures into one per-doc bitmap
query → build query signature, AND against every doc signature
      → candidates = docs whose bitmap AND == query signature (false positives verified)

Regime it wins: very high update rates with weak precision requirements, where building/ maintaining an inverted index's sorted structures is too costly relative to a flat bitmap scan (historically: early-1990s bibliographic retrieval on constrained hardware). Real system: early signature-file IR systems predating the inverted-index consensus (surveyed in Zobel & Moffat 2006, §5). Why rejected: false-positive verification cost grows with corpus size and signature density, and there is no efficient way to do ranked (BM25-style) retrieval from a bitmap — it answers "does it match" cheaply but not "how well does it match," which is this project's core requirement (ADR-06).

35.2 Suffix-array / n-gram substring index

corpus text → concatenate → build suffix array (or trigram posting index)
query substring → binary search suffix array for range containing query
                → (or) trigram-decompose query, intersect trigram posting lists

Regime it wins: arbitrary substring / regex search over source code or unstructured text where tokenization boundaries are the wrong unit (e.g. searching for foo_bar( across a codebase). Real system: grep-style code-search engines (e.g. Google Code Search's trigram index; ripgrep's literal-substring optimizations). Why rejected: substring indexes do not naturally support relevance ranking (BM25 needs term statistics, not substring positions), and suffix-array construction/memory cost scales with total corpus character count rather than token count — wrong shape for a document-relevance search engine (ADR-06, ADR-02).

35.3 Dense-only (embedding) retrieval, no sparse index

doc → embedding model → dense vector → ANN index (HNSW/IVF)
query → embedding model → dense vector → k-NN search → ranked results

Regime it wins: semantic/paraphrase-heavy retrieval where exact term overlap is a poor relevance signal (e.g. conversational RAG over loosely-worded natural-language questions). Real system: the Vector-Database (Ranking 47) this project delegates to, and the DPR line of research (Karpukhin et al. 2020, §5). Why rejected as the sole retrieval path: dense-only retrieval loses exact-match precision (a user searching a legal document for a specific defined term wants that term, not a semantically similar one), has weaker interpretability for relevance debugging than BM25's transparent term-weight arithmetic, and requires an embedding model in the critical serving path — this project's ADR-23 keeps hybrid (sparse and dense) rather than replacing sparse outright, precisely to keep BM25's exact-match guarantee as the floor.

37. Glossary

  • Analyser — the pipeline (CharFilter → Tokenizer → TokenFilter chain) that turns raw text into a token stream; owns all text handling per P8.
  • ASCII folding — a token filter mapping Latin-extended characters to their ASCII base form (e.g. é→e).
  • avgdl — average document length across a field, a BM25 statistic that must roll forward correctly across merges (§17.2).
  • Block-Max-WAND (BMW) — WAND extended with per-block maximum-score statistics, enabling whole-block skipping during top-k retrieval (§17.5).
  • BM25 — the default probabilistic ranking function; scores term frequency saturated against document length normalization (§17.2, §5).
  • BM25F — BM25 generalized to weight multiple fields with per-field k1/b (§17.2).
  • Block-max score — the true upper bound on any document's score within one posting block; the safety property WAND/BMW pruning depends on (I4).
  • BLOCK_SIZE — the fixed number of documents per posting-list block, 128 by default (P5).
  • BTreeMap memtable — the in-memory sorted map backing the delta layer before flush (§18.2).
  • Codec — a block-level integer compression scheme (varbyte/FOR/PFOR/simd-bp128/Elias-Fano), §15.
  • Conjunction — a boolean AND query, executed by advancing all sub-iterators to agreement (§17.2).
  • Coordinator — the stateless component that authenticates, routes, and scatter-gathers requests across shards (§3, §21).
  • CRC32C — the checksum computed over each posting block's compressed bytes, detecting corruption (I3).
  • Decompounding — splitting a compound word (e.g. German) into searchable constituent stems (§13.2).
  • Delta layer — the in-memory, WAL-backed structure holding documents not yet flushed to a segment (§18.2).
  • Disjunction — a boolean OR query, executed via a min-heap over candidate doc-ids (§17.2).
  • DocId — a u32, shard-local document identifier (§11.1).
  • Document-at-a-time execution — the query-execution model advancing all posting iterators for one candidate document before moving to the next (§17.2).
  • Doc-values — a per-field, per-document columnar side-storage used for aggregations and sorting (§8.3).
  • Elias-Fano encoding — a compact encoding for monotonic integer sequences, used for dense document-store side indexes (§15.2).
  • Fan-out — the number of shards a coordinator request is scattered to (§21.2).
  • FieldId — a u16 identifier for a schema field (§11.1).
  • FOR (Frame-Of-Reference) — a block codec storing (min, [delta], bit_width) (§15.2).
  • FST (finite-state transducer) — the term-dictionary data structure mapping terms to posting offsets in O(prefix-length) (P4, ADR-02).
  • Fuzzy query — a query matching terms within a bounded edit distance, resolved via a Levenshtein automaton intersected with the FST (§17.7).
  • Hybrid retrieval — combining sparse (BM25) and dense (embedding) retrieval results, typically via RRF (§20).
  • IndexOptions — the per-field indexing granularity (docs / docs+freqs / +positions / +offsets), §11.2.
  • IndexReader / IndexWriter — the read-only and mutating traits over a shard's index (§11.9).
  • Inverted index — the core data structure mapping terms to the documents (and positions) containing them.
  • PFOR (Patched Frame-Of-Reference) — FOR with an exception side-list for outlier values (§15.2, ADR-04).
  • Posting — one (doc_id, term_freq, positions?, offsets?) entry in a term's posting list (§11.4).
  • Posting list — the ordered sequence of postings for one term, stored as compressed blocks (§8.2).
  • RRF (Reciprocal Rank Fusion) — a rank-based fusion formula summing 1/(k+rank) across result lists, robust to score-scale mismatch (§20.2, §5).
  • Scatter-gather — the coordinator pattern of fanning a request out to all shards and merging their responses (§21.2).
  • Schema — the named, typed field definitions for a shard's documents (§11.2).
  • Score-safety — the property that an early-termination strategy never drops a true top-k member (P13, I6).
  • Segment — an immutable, on-disk unit of the index (§8.3, P6).
  • SegmentId — a u32 identifier for a segment (§11.1).
  • Skip list — a sparse (doc_id, block_offset) index over a long posting list, enabling block-granularity seeks (§14.2).
  • Snapshot — a versioned, refcounted view of the segment list pinned for a request's lifetime (I8, §11.9).
  • Snowball — a stemming-algorithm bytecode format/interpreter supporting 20+ languages (§13.2, ADR-14).
  • Stemming — reducing a token to a common root form (e.g. running→run), §13.2.
  • Stopword — a language-specific, frequently occurring word dropped from the token stream by default (§13.2).
  • Term dictionary — see FST.
  • TermId — a u32 interned identifier for a unique term (§11.1).
  • Tiered merge policy — the LSM-style merge scheduler folding small segments into larger ones on size/count/age triggers (P7, ADR-05, §18.2).
  • Tombstone — a bitmap entry marking a document as deleted without removing its bytes until merge time (P6, I12).
  • Top-k collector — the bounded min-heap tracking the current best-scoring documents during search (§17.2).
  • UAX-29 / UAX-15 — Unicode Standard Annexes for text segmentation and normalization forms respectively (§5).
  • WAL (Write-Ahead Log) — the durability mechanism recording writes before they are acknowledged, replayed on crash recovery (I10, I11, §18.2).
  • WAND (Weak AND) — the original score-safe top-k pruning algorithm generalized by BMW (§17.5, §5 Broder).
