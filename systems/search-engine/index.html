In one paragraph

A Lucene-class full-text search engine in Rust: a single-shard core plus a thin scatter-gather coordinator (§1). Documents are analysed into normalised words and stored as compressed posting lists — for every word, the sorted list of documents containing it — inside immutable segments (§1). Lucene-syntax queries are ranked with BM25/BM25F, with WAND and Block-Max-WAND early termination (§1, §17). New documents become visible within a 1 s refresh through an in-memory delta layer; aggregations, highlighting and hybrid sparse-plus-dense fusion complete it (§1). Conformance is measured against recorded Lucene baselines and MS-MARCO / TREC (§1). One searchd binary runs one shard; platform teams embed it in application backends and SREs run the shard fleet (§1).

The problem, concretely

The blueprint names the failures you only understand by building the pieces yourself (§2): a tokenizer mismatch between index-time and query-time analysis silently breaks exact-match search; a posting-list codec that is fast but wrong on one block in a million is worse than a slow correct one; BM25's average-document-length statistic must roll forward correctly across a segment merge; and a query parser's escaping rules are observable behaviour, not documented behaviour.

Each obvious shortcut fails in a way the blueprint spells out:

  • Store each posting as an object with its own header. Per-document overhead then dominates at scale and destroys the compression ratio; the fix is to treat a posting list as "a compressed integer stream, not a list of documents" (P5, §31 MM1, §33 C1).
  • Keep the term dictionary in a plain hash map. Term-dictionary memory blows past §4's 2.5 GB ceiling at 50 M terms (P4).
  • Answer a multi-word query with a nested loop. That turns an O(N log K) merge over sorted streams into O(N·K) (§31 MM2).
  • Prune with a "usually right" heuristic. It silently drops true top-k members (§31 MM3, P13).
  • Analyse the query differently from the document. In the blueprint's worked example, a status keyword field accidentally stemmed at query time turns active into activ, which never matches the indexed active (§8.5, P3).

How it works, end to end

The blueprint's diagram places a frontend and a coordinator above independent shard processes, each with a one-way data path down to storage (§3). Lightly adapted:

 HTTP / gRPC frontend (§21)  — the only component that sees raw client bytes
          │
 Coordinator (§21) — auth, quota, query plan, shard routing
          │  scatter-gather
 Shard engine (one searchd process):
   Analyser (§13) ──► Indexer / delta (§18) ──┐
   Query parser (§16) ──► Searcher (§17) ─────┤──► Inverted index (§14–§15):
                                              │    posting lists, skip lists, FST, doc-values
   Aggregations · Highlight engine (§19) · Hybrid fusion adapter (§20) ──► Vector-DB / Embed
          │
 Storage: segment files (.terms .post .pos .skip .docv .doc .del .meta), WAL,
          page cache + io_uring (Linux) / mmap (BSD/macOS)

The crates are server and coordinator for the top two boxes; analyser, query, search, segment + delta, postings, dictionary and codec inside the shard; aggregations, highlight and hybrid for the side paths (§1).

Indexing one document. The server frontend receives it (§21.2). Inside the shard, the analyser turns each field's text into tokens with positions (§13). The delta layer writes the document to the WAL first (durability, I11) and then to an in-memory memtable; on commit the memtable is sorted (the I7 precondition) and written by segment::writer as a new segment, and the WAL rotates (§18.2). A segment is a directory of files: the FST term dictionary, the posting-list blocks, positions, a skip list, doc-values, stored fields, a tombstone bitmap and a JSON manifest (§8.3). The commit is a rename into place (§18.2, I1). A tiered merge policy later folds small segments together on a separate merge thread (§18.2, P7, ADR-05).

Answering one query. The coordinator validates and authenticates the request and fans it out to all shards, with per-shard top_k set to twice the global value so the merged top-k is correct (§21.2). The blueprint places parsing in two spots: §21.2 has the coordinator parse and rewrite the query, while §3's diagram draws the query parser inside each shard engine (§21.2, §3). Either way the query rewriter applies each field's own analyser to the query terms — the same pipeline used at index time (I2, §8.5). The search executor walks the posting iterators document-at-a-time, scores with BM25, and uses Block-Max-WAND to skip blocks that cannot reach the top-k threshold (§17.2, ADR-07). Every request runs against a Snapshot that pins the segment list at request start, so concurrent merges never change what it sees (I8, §18.2). Back at the coordinator, a shard timeout or error is recorded in partial_failures rather than failing the request, unless every shard fails (§21.2).

The core ideas

Posting lists are blocks of compressed integers (§8.2, §15)

Each posting list is a run of fixed 128-document blocks plus a varbyte tail for the remainder (§8.2, P5). A block holds a small header, delta-encoded and codec-compressed document ids, the compressed term frequencies, an offset into the separate .pos positions stream, the block's maximum document id, its maximum score, and a CRC-32C (§8.2). A dispatcher picks the codec per block from its statistics: fewer than 32 values → varbyte; low outlier fraction and a SIMD-eligible bit width → simd-bp128; low outlier fraction otherwise → PFOR; else FOR (§15.2). FOR stores (min, [value − min], bit_width) with bit_width = ceil(log2(max − min + 1)); PFOR picks a bit width covering about 90% of the values and stores the rest as (index, value) exceptions, so one outlier does not inflate the whole block (§15.2, ADR-04). The hot codec, simd-bp128, decodes at about 5 GiB/s on AVX2 against about 1 GiB/s for varbyte (ADR-03). The compression target is at least 6× versus raw u32 document ids (§4).

The blueprint's block layout and its types disagree on detail: §8.2's header names one codec and one bit width, while §11.4's PostingBlock has separate doc-id and frequency codecs (§8.2, §11.4).

The term dictionary is a finite-state transducer (ADR-02, §14)

The dictionary that maps a term to its posting-list offset, document frequency and collection frequency is an FST (finite-state transducer) rather than a hash map or a sorted-string table (§14.2, ADR-02). Lookup cost is proportional to the term's prefix length, and prefix iteration feeds wildcard queries (§14.2). It must be built from strictly sorted, deduplicated input, which forces a sort at flush time (I7, P4). The memory budget is ≤ 2.5 GB resident for 50 M terms, which §33 works out as ≤ 50 B per term (§4, §33 C2).

The blueprint is not consistent about what the FST's 5–10× size reduction is measured against. P4 says "vs. a hash map" (P4); §33 C2 says it is against a ~250–500 B flat sorted-string entry (§33 C2); and the Phase 2 acceptance test asks for an FST at most 1/5 the size of "an equivalent sorted flat term list" (§14.4).

Score-safe early termination with Block-Max-WAND (§17, ADR-07, MM3)

Each block carries an upper bound on the score of any document inside it (I4). WAND picks a pivot — the smallest document id whose prefix-sum of per-term maximum scores exceeds the current top-k threshold — and Block-Max-WAND skips whole any block whose block-max sum is still below that threshold (§17.2). What makes this safe rather than merely fast is I6: the pruned pass must return the same top-k set as an exhaustive disjunction, checked by a differential test on every conformance query (I6). The blueprint treats safety and speed as separate checks — "score-safety and speed are not the same axis" (§31 MM7).

The capacity model's trace shows the effect (§33 C5):

  1. A term at 1% selectivity in a 1 B-posting shard has df ≈ 10 M, ≈ 78,125 blocks.
  2. At M7's 70% skip ratio, ≈ 23,437 blocks are decoded — ≈ 6 MB of doc-id + tf bytes.
  3. At M5's 5 GiB/s that is ≈ 1.1 ms, inside the 8 ms p50 budget.

Analysis is a pure function fixed at two points in time (§8.5, I2, MM4)

A document is analysed once at index time, and the query is analysed at query time with the same analyser configuration per field (P3). The query::rewriter loads the analyser by a field-name key shared with segment::writer (I2). In §8.5's example, title:"quick brown"~2 AND status:active is rewritten with the title analyser (stemming off, lowercase on) and the status keyword analyser (exact, no stemming); stemming status by mistake would make the query term activ (§8.5). The blueprint calls the resulting "my exact query doesn't match" the single most common production search bug (§31 MM4). The price is that changing an analyser requires re-indexing (P3).

Immutable segments make reads lock-free (§8.4, I1, I8, MM5)

A segment moves through Building → Committing → Live → Merging → Retired → Deleted (§8.4). The blueprint's failure trace (§8.7):

  1. The indexing thread crashes mid-flush_block(), after 96 of 128 doc-id deltas but before the CRC.
  2. On restart the partial file is a Building-state temp file that was never renamed into place, so the previous Live segment serves searches unaffected.
  3. The _tmp file is garbage-collected on the next flush attempt.

Because a Live segment never changes (I1), readers need no locks; they take a refcounted snapshot (I8, §31 MM5). Updates are a delete tombstone plus an insert; tombstones are checked by every posting iterator and garbage-collected only at merge time (P6, I12, §18.2).

Hybrid retrieval fuses ranks, not scores (§20, ADR-09, MM8)

Dense-vector search is delegated to a separate Vector-Database service (§1, §20.2). The engine fuses its results with BM25 by reciprocal rank fusion: RRF(d) = Σ_l 1/(k + rank_l(d)), with k = 60 the standard default (§20.2). Because it uses positions, not scores, it is robust to the scale mismatch between BM25 scores and cosine similarities and needs no per-corpus tuning (§20.2, ADR-09). The secondary weighted sum, α·score_bm25 + (1−α)·score_dense, needs both inputs min-max normalised first and α tuned per corpus (§20.2, §31 MM8). The acceptance bars are a higher MRR@10 than either sparse-only or dense-only (§20.4) and at least +10% MRR@10 over BM25-only (M12).

The trade-offs — where engineers disagree

Language: Rust, not Java (ADR-01)

Chosen: Rust 1.78+, for ownership-driven memory safety in hand-rolled binary codecs and zero-cost trait dispatch (ADR-01); §1 adds that posting-list buffers are otherwise a classic C/C++ use-after-free/overflow surface (§1). Rejected: Java (Lucene's language), C++, Go (ADR-01); §1 rejects Go because GC pauses are incompatible with the p99 targets (§1). When the rejected choice is right: Java, when the team already owns a JVM operational stack and wants to extend Lucene directly rather than clean-room it (ADR-01).

Term dictionary: FST (ADR-02)

Chosen: a finite-state transducer, for O(prefix) lookup and a 5–10× size reduction (ADR-02). Rejected: a hash map, or a sorted-string table such as Xapian's Glass-style B-tree (ADR-02). When the rejected choice is right: a hash map when terms are few (under 100k) and update frequency matters more than memory density, because FST rebuild cost amortises poorly for tiny, frequently updated dictionaries (ADR-02).

Hot codec: SIMD bit-packing (ADR-03)

Chosen: simd-bp128 (AVX2/NEON) with a scalar fallback — about 5 GiB/s decode on AVX2 versus about 1 GiB/s for varbyte (ADR-03). Rejected: pure varbyte, pure Elias-Fano everywhere (ADR-03). When the rejected choice is right: varbyte on the tail block of fewer than 32 values, where SIMD lane setup overhead exceeds the gain (ADR-03).

Merge policy: tiered, not levelled (ADR-05)

Chosen: a tiered, LSM-style policy that amortises merge cost and bounds read fan-out for a read-heavy SLO (ADR-05). Rejected: level-based (RocksDB-style) merging, or no merging at all (ADR-05). When the rejected choice is right: level-based for write-heavy, rarely read workloads such as cold log archival, where read fan-out matters less than write amplification (ADR-05). The policy "is a scheduling problem, not a storage problem" (§31 MM6).

Early termination: WAND and Block-Max-WAND (ADR-07)

Chosen: the strongest score-safe pruning for top-k below 1,000 (ADR-07). Rejected: MaxScore, exhaustive disjunction (ADR-07). When the rejected choice is right: MaxScore at very large k (above 1,000), where Block-Max-WAND's per-block bookkeeping costs more than its pruning saves (ADR-07).

Fusion: reciprocal rank fusion first (ADR-09)

Chosen: RRF as primary and weighted sum as secondary — rank-based, robust to score-scale mismatch, no per-corpus tuning (ADR-09). Rejected: weighted sum only, a learned fusion model (ADR-09). When the rejected choice is right: weighted sum when both score distributions are well calibrated and a validation set exists to tune α (ADR-09).

Coordination: single leader plus replicas, Raft later (ADR-22)

Chosen: single leader plus replicas for Phase 0, with Raft evaluated later, because Raft adds a coordination subsystem that single-digit shard counts do not need (ADR-22). Rejected: Raft-based membership from day one (ADR-22). When the rejected choice is right: once shard count and membership churn are high enough that manual primary/replica configuration becomes an operational burden (ADR-22).

Roads not taken (§35)

Signature files — one Bloom-style bitmap per document, ANDed against a query signature — win for very high update rates with weak precision needs, historically early-1990s bibliographic retrieval on constrained hardware. They are rejected because false-positive verification cost grows with the corpus, and a bitmap answers "does it match" but not "how well does it match", which BM25 ranking needs (§35.1).

Suffix-array or n-gram substring indexes win for arbitrary substring and regex search over source code, where token boundaries are the wrong unit. They are rejected because they carry no term statistics for relevance ranking and their cost scales with character count rather than token count (§35.2).

Dense-only embedding retrieval wins for paraphrase-heavy retrieval such as conversational RAG. It is rejected as the sole path because it loses exact-match precision, is harder to debug than BM25's term weights, and puts an embedding model in the serving path; hybrid keeps BM25's exact-match guarantee as the floor (§35.3, ADR-23).

What must never be false

  • I1 — a committed segment file is never mutated in place; noticed by a conformance re-read with CRC check, segment_mutation_detected_total.
  • I2 — index-time and query-time analysis of a field use the identical pipeline; noticed by fixture analyser-parity.jsonl, analyser_config_mismatch_total.
  • I3 — every posting block's CRC-32C matches its compressed bytes; checked on every block read, crc_mismatch_total{segment}.
  • I4 — a block's max score is a true upper bound on every document inside it; a fixture asserts no document scores above its block max, bmw_bound_violation_total.
  • I5 — a segment's doc_count equals its live, non-tombstoned documents; fixture doc-count-check.jsonl, doc_count_mismatch_total.
  • I6 — an early-terminated top-k equals the exhaustive top-k for every conformance query; differential BMW-vs-naive test, topk_mismatch_total.
  • I7 — the FST is built from strictly sorted, deduplicated terms; build-time assertion and fixture fst-sorted.bin, fst_build_order_violation_total.
  • I8 — a snapshot taken at request start sees a fixed segment list for the whole request; fixture snapshot-stability.jsonl, snapshot_version_drift_total.
  • I9 — per-query memory stays within the query arena's ceiling; high-water-mark assertion in a load test, query_arena_exhausted_total.
  • I10 — WAL records replay in exactly the order they were appended; crash-replay fixture, wal_replay_order_violation_total.
  • I11 — no committed write is lost across a crash (fsync before ack); a crash-injection test kills the process mid-write, wal_fsync_failures_total.
  • I12 — a deleted document is never returned, even from an unmerged segment; fixture tombstone-visibility.jsonl, tombstoned_doc_returned_total.
  • I13 — the merge policy never selects an in-flight segment for a second merge; merge-scheduler assertion, concurrent_merge_conflict_total.
  • I14 — every PhaseDeferred(...) call site has a matching register row; CI lint make lint-deferred, deferred_unregistered_total.

What breaks in production

  • FM-1 — segment corruption. Query errors on one segment while others are fine; caused by disk bit-rot, a buggy codec write path, or a crash outside the rename boundary. A CRC mismatch at open (I3) quarantines the segment and the remaining Live segments keep serving; the manual fix is a restore from backup or a re-index of the affected range.
  • FM-2 — WAL truncation. After a crash, replay stops early and recent writes are missing; caused by a full disk during fsync or a crash mid-append. A per-record checksum failure stops replay at the last valid record (I10), the tail is discarded and archived, and the documents are re-ingested from the source of truth.
  • FM-3 — Block-Max-WAND drops true results. Top-k results are silently incomplete because a block-max statistic was computed wrongly at index time. The differential fixture (I6) catches it in CI and a production canary compares BMW with naive evaluation; recovery disables BMW for the segment and falls back to exhaustive disjunction, then re-indexes it.
  • FM-4 — merge-policy thrash. Read latency degrades and segment count grows, visible as segment_count{tier} trending past max_segments_per_tier. It is a configuration problem, not auto-recoverable: the operator retunes TieredMergePolicy and triggers /v1/admin/merge; chasing a "slow disk" is the wrong lead (§31 MM6).
  • FM-5 — analyser mismatch. Exact-match queries return zero results after an analyser change without a re-index, or after per-field drift between writer and rewriter. The parity fixture (I2) catches it before production; the only cure is re-indexing the affected fields.
  • FM-7 — replica divergence. Stale reads from a lagging replica under high write load, when WAL forwarding falls behind. A replica-lag metric crosses its threshold and the router prefers the primary automatically.
  • FM-9 — the dense-retrieval service is down. Hybrid search degrades to sparse-only; dense_retriever_latency_seconds spikes and hybrid_degraded_total increments, and responses carry hybrid_degraded: true (§20.9).
  • FM-11 — fsync-induced write stall. Indexing throughput drops sharply because fsync=always was chosen for a workload that needs batch, or disk latency spiked; visible as index_throughput_docs_per_sec falling in step with WAL fsync latency. The operator switches the policy to batch (§18.6).

Threats a reader should know (§23): T1 malformed segment bytes, for example restored from an untrusted backup, answered by bounded reads, strict manifest validation and per-block CRCs; T2 adversarial query strings (deep nesting, huge wildcard expansion), answered by an 8 KB length cap, a 1,024-term wildcard-expansion cap, a fuzzy edit-distance cap of 2 and a recursion-depth cap; T3 adversarial documents such as a gigabyte token, answered by a 1 MB per-document cap, a 1 M per-field token cap and a 1 s analyser timeout; T5 request floods, answered by per-API-key concurrency limits and a queue-depth cap that returns HTTP 503; T12 a misbehaving vector service, answered by bounds-checking every returned document id before fusion.

How it compares

  • Apache Lucene / Elasticsearch is the two-decade-converged reference for 128-document blocks, FST dictionaries and tiered merging; Elasticsearch adds a JSON DSL and cluster coordination on top. It wins where a JVM operational profile is acceptable and the organisation wants a proven cluster-management layer rather than building one (§32).
  • Google's 1998 web search made PageRank the primary ranking signal atop an inverted index. It wins in the open-web link-graph regime, where authority signals matter more than term matching — a regime this blueprint's scope excludes (§32).
  • Tantivy is the closest Rust-native reference, with a simpler single-writer-lock model. It wins when a team wants an embeddable Rust search library instead of operating a standalone service (§32).
  • PISA is the research reference for compressed-list query latency and Block-Max-WAND at billion-document scale. It wins for static, offline-built corpora where real-time visibility is irrelevant — the assumption this design's delta layer rejects (§32).

Questions to test yourself

  1. Why does a BMW pruning bug manifest as missing results rather than a crash, and which two invariants jointly make that failure mode detectable in CI before production? — Hint: §7 I4/I6 and §17.5.
  2. Why must the term dictionary be built from sorted input, and what breaks — concretely — if a delta-flush race allows unsorted input through? — Hint: §7 I7 and §14.2.
  3. Why does immutability (P6) make the real-time delta layer's read-path lock-free, and what would have to change in §11.5's trait if segments were mutable in place? — Hint: P6, §11.5 and §18.2.
  4. Why is a CRC computed over compressed bytes rather than decompressed postings, and what corruption class would escape detection under the alternative? — Hint: §7 I3 and §15.6.
  5. Using the capacity model, explain why doubling the corpus size does not double query latency in the presence of BMW, but would without it. — Hint: §33 C5 and §17.5.

If you only remember three things

A posting list is a compressed integer stream, so block size, codec and skip structure are integer-compression decisions (§31 MM1). Early termination is acceptable only because an invariant requires the pruned top-k to equal the exhaustive one, and that is checked separately from speed (I6, §31 MM7). The same analyser must run at index time and at query time, and immutable segments are what let readers run without locks (P3, §31 MM5).

Words used here

  • Inverted index — for every term, the list of documents containing it.
  • Posting / posting list — one (document, frequency, positions) entry, and the sorted list of them for a term.
  • Segment — an immutable directory of index files written at commit and later merged.
  • Delta layer — the in-memory index of documents not yet in a segment, visible within the 1 s refresh.
  • Analyser — the tokenise, normalise and stem pipeline applied to text at index and query time.
  • FST — finite-state transducer; the compact term dictionary mapping a term to its posting list.
  • Codec — the integer-compression scheme for a block of document ids and frequencies.
  • BM25 / BM25F — the default relevance score, and its multi-field generalisation.
  • WAND / Block-Max-WAND — top-k early termination using per-term and per-block score upper bounds.
  • Score-safety — the guarantee that pruning never drops a true top-k member.
  • Snapshot — a pinned, refcounted view of the segment list for one request.
  • Tombstone — a deletion bit checked by every iterator so deleted documents never surface.
  • Tiered merge policy — the scheduler deciding which segments to combine, trading write cost for read fan-out.
  • Scatter-gather — the coordinator fanning a query out to shards and merging their partial results.
  • RRF — reciprocal rank fusion; combining rankings by position rather than by score.
