Decisions (§9) · 24 ADRs

ADR-01

Core implementation language

Chosen

Rust 1.78+

Rejected

Java (Lucene's language), C++, Go

When the rejected choice is right

Java wins when the team already owns a JVM operational stack and wants to extend Lucene directly rather than clean-room it

Why: ownership-driven memory safety for hand-rolled binary codecs + zero-cost trait dispatch (§1, P14)

ADR-02

Term dictionary structure

Chosen

FST (finite-state transducer)

Rejected

hash map, sorted-string table (Xapian Glass-style B-tree)

When the rejected choice is right

a hash map wins when terms are few (<100k) and update-frequency dominates over memory density — FST rebuild cost is amortized poorly for tiny, frequently-updated dictionaries

Why: O(prefix) lookup + 5–10× size reduction (P4, §5 Zobel & Moffat)

ADR-03

Posting-list hot codec

Chosen

simd-bp128 (AVX2/NEON) with scalar fallback

Rejected

pure varbyte, pure Elias-Fano everywhere

When the rejected choice is right

varbyte wins on the tail block (<32 values) where SIMD lane setup overhead exceeds the gain

Why: ~5 GiB/s decode on AVX2 vs. ~1 GiB/s varbyte (Lemire & Boytsov)

ADR-04

Outlier handling in dense blocks

Chosen

PFOR (patched FOR)

Rejected

plain FOR, re-bucketing by exact max

When the rejected choice is right

plain FOR wins when the block has near-zero variance (e.g. sequential doc-ids with no gaps) — patch overhead isn't worth it

Why: PFOR keeps 90% of values at a tight bit-width and patches the rest, avoiding one-outlier-inflates-everything

ADR-05

Merge policy

Chosen

tiered (LSM-style, TieredMergePolicy-alike)

Rejected

level-based (RocksDB-style), no-merge (append-only)

When the rejected choice is right

level-based wins for write-heavy, read-rarely workloads (e.g. cold log archival) where read fan-out matters less than write amplification

Why: amortizes merge cost, bounds read fan-out for our read-heavy SLO (§4)

ADR-06

Default ranking function

Chosen

BM25 (BM25F for multi-field)

Rejected

TF-IDF, learned dense-only ranking

When the rejected choice is right

learned dense-only wins when a large labeled relevance-judgment set exists and latency budget accommodates a reranker (§20)

Why: strongest unsupervised first-stage retriever, 40+ years of validation (Robertson & Zaragoza)

ADR-07

Top-k early termination

Chosen

WAND + Block-Max-WAND

Rejected

MaxScore, exhaustive disjunction

When the rejected choice is right

MaxScore wins at very large k (>1000) where BMW's per-block bookkeeping overhead exceeds its pruning benefit

Why: strongest score-safe pruning for top-k<1000 (Mallia et al. 2017)

ADR-08

Query syntax

Chosen

Lucene-classic grammar (§8.1)

Rejected

JSON query DSL only, SQL-like

When the rejected choice is right

a JSON-only DSL wins for programmatic query builders that never expose a raw string to end users (no parser ambiguity risk)

Why: every existing search client already targets Lucene syntax; JSON DSL layered on top later, not instead

ADR-09

Sparse+dense fusion

Chosen

RRF primary, weighted-sum secondary

Rejected

weighted-sum only, learned fusion model

When the rejected choice is right

weighted-sum wins when both score distributions are well-calibrated and a validation set exists to tune α (§20.3)

Why: RRF is rank-based, robust to score-scale mismatch, needs no per-corpus tuning (Cormack et al. 2009)

ADR-10

gRPC framework

Chosen

tonic

Rejected

grpc-rs, raw prost + hyper

When the rejected choice is right

raw prost+hyper wins when a team wants zero-framework control over wire framing for an unusual transport

Why: native tokio integration, active maintenance, matches server async story

ADR-11

Python bindings

Chosen

PyO3

Rejected

cffi, gRPC-only Python client

When the rejected choice is right

gRPC-only wins when Python and Rust must run in separate processes/containers (e.g. security isolation)

Why: ergonomic in-process bindings for notebook workflows without an RPC hop

ADR-12

Async runtime

Chosen

tokio, spawn_blocking for the sync hot path

Rejected

async-std, fully-async search path

When the rejected choice is right

a fully-async search path wins if per-query work becomes dominated by network I/O rather than CPU (not the case here, §4)

Why: single-runtime discipline; the search hot path is intentionally synchronous (P11) to keep arena allocation deterministic

ADR-13

License

Chosen

Apache-2.0 (engine), ELv2 reserved for hosted control plane

Rejected

pure MIT, pure AGPL

When the rejected choice is right

AGPL wins for a project that wants to force downstream contribution back, at the cost of enterprise adoption friction

Why: permissive core encourages embedding; ELv2 protects a future hosted offering

ADR-14

Stemmer family

Chosen

Snowball default, Hunspell for compounding languages

Rejected

Porter-only, ICU-only

When the rejected choice is right

Porter-only wins for English-only deployments that want to avoid the Snowball-VM dependency entirely

Why: Snowball covers 20+ languages at a small footprint; Hunspell handles productive compounding (German/Hungarian/Finnish/Turkish)

ADR-15

Non-cryptographic hashing (delta layer)

Chosen

xxhash3

Rejected

FNV-1a, SipHash

When the rejected choice is right

SipHash wins when the hash table is exposed to adversarial key insertion (DoS via hash-flooding) — not our threat model for internal term ids

Why: fastest widely-used 64-bit hash with acceptable collision behavior for an in-memory term-id map

ADR-16

Async I/O for posting-list reads (Linux)

Chosen

io_uring, mmap fallback

Rejected

plain pread, mmap-only everywhere

When the rejected choice is right

mmap-only wins on macOS/BSD (no io_uring) and is the correct default there (ADR-17)

Why: io_uring batches many small posting-block reads without thread-pool overhead

ADR-17

Default read path

Chosen

mmap

Rejected

io_uring-always, pread-always

When the rejected choice is right

io_uring-always wins under concurrent write-heavy + high-QPS-read workloads on Linux, hence it is opt-in not default

Why: simplest correct default for read-heavy workloads across all platforms

ADR-18

Distributed tracing

Chosen

OpenTelemetry

Rejected

vendor-specific SDK (e.g. Datadog-only)

When the rejected choice is right

a vendor-specific SDK wins when the org has already standardized on one vendor's proprietary richer feature set

Why: vendor-neutral, exports to any OTLP-compatible backend

ADR-19

Metrics

Chosen

Prometheus (pull-based)

Rejected

StatsD (push), vendor-hosted-only metrics

When the rejected choice is right

push-based StatsD wins in environments where the scrape target is unreachable (e.g. serverless, ephemeral containers)

Why: pull-based scraping matches the on-call runbook tooling already assumed in §25

ADR-20

Build system

Chosen

Cargo (Phase 0), Bazel evaluated Phase 2+

Rejected

Bazel from day one

When the rejected choice is right

Bazel wins once the Python frontend + multiple language SDKs make a monorepo build graph necessary (deferred, §36)

Why: Cargo is the lower-friction Phase-0 default for a single-language workspace

ADR-21

Learning-to-rank reranker

Chosen

deferred to Phase-1+ stretch

Rejected

ship LTR in Phase 0

When the rejected choice is right

shipping LTR in Phase 0 wins only if a labeled relevance-judgment corpus already exists at project start (rare)

Why: Phase-0 focus is a correct BM25/BM25F baseline; LTR needs labeled data that does not exist yet

ADR-22

Cluster coordination

Chosen

single-leader + replicas (Phase 0), Raft evaluated later

Rejected

Raft-based membership from day one

When the rejected choice is right

Raft wins once shard count and membership churn are high enough that manual primary/replica config becomes an operational burden

Why: Raft adds a coordination subsystem the Phase-0 scope does not need at single-digit shard counts

ADR-23

Hybrid retrieval status

Chosen

first-class (adapter to Vector-DB rank 47)

Rejected

out of scope entirely

When the rejected choice is right

out-of-scope wins for a pure keyword-search product with no ML infrastructure investment planned

Why: hybrid search is now a baseline expectation for production retrieval systems

ADR-24

Conformance ground truth

Chosen

recorded Lucene baselines + MS-MARCO + TREC

Rejected

invented synthetic fixtures only

When the rejected choice is right

synthetic-only fixtures win for exercising a specific internal edge case (e.g. bit_width=0) where no external baseline exists — used as a supplement, never a replacement

Why: real, externally-verifiable baselines catch regressions synthetic fixtures cannot (they encode Lucene's actual quirks)

Roads not taken (§35)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Signature-file retrieval

doc → hash each term into an m-bit Bloom-style signature
      → OR all term-signatures into one per-doc bitmap
query → build query signature, AND against every doc signature
      → candidates = docs whose bitmap AND == query signature (false positives verified)

Regime it wins: very high update rates with weak precision requirements, where building/ maintaining an inverted index's sorted structures is too costly relative to a flat bitmap scan (historically: early-1990s bibliographic retrieval on constrained hardware). Real system: early signature-file IR systems predating the inverted-index consensus (surveyed in Zobel & Moffat 2006, §5). Why rejected: false-positive verification cost grows with corpus size and signature density, and there is no efficient way to do ranked (BM25-style) retrieval from a bitmap — it answers "does it match" cheaply but not "how well does it match," which is this project's core requirement (ADR-06).

Suffix-array / n-gram substring index

corpus text → concatenate → build suffix array (or trigram posting index)
query substring → binary search suffix array for range containing query
                → (or) trigram-decompose query, intersect trigram posting lists

Regime it wins: arbitrary substring / regex search over source code or unstructured text where tokenization boundaries are the wrong unit (e.g. searching for foo_bar( across a codebase). Real system: grep-style code-search engines (e.g. Google Code Search's trigram index; ripgrep's literal-substring optimizations). Why rejected: substring indexes do not naturally support relevance ranking (BM25 needs term statistics, not substring positions), and suffix-array construction/memory cost scales with total corpus character count rather than token count — wrong shape for a document-relevance search engine (ADR-06, ADR-02).

Dense-only (embedding) retrieval, no sparse index

doc → embedding model → dense vector → ANN index (HNSW/IVF)
query → embedding model → dense vector → k-NN search → ranked results

Regime it wins: semantic/paraphrase-heavy retrieval where exact term overlap is a poor relevance signal (e.g. conversational RAG over loosely-worded natural-language questions). Real system: the Vector-Database (Ranking 47) this project delegates to, and the DPR line of research (Karpukhin et al. 2020, §5). Why rejected as the sole retrieval path: dense-only retrieval loses exact-match precision (a user searching a legal document for a specific defined term wants that term, not a semantically similar one), has weaker interpretability for relevance debugging than BM25's transparent term-weight arithmetic, and requires an embedding model in the critical serving path — this project's ADR-23 keeps hybrid (sparse and dense) rather than replacing sparse outright, precisely to keep BM25's exact-match guarantee as the floor.
