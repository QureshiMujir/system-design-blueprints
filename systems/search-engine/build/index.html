✅ Phase 0 — Skeleton, Governance, "Hello Index" (Week 1) §12

Objectives

Stand up the repository (§10) at production-scaffold quality; land governance files; land CI; prove end-to-end plumbing with a minimal in-memory index and a single-term query, with zero codec or analyser correctness work yet (that is Phase 1+).

Deliverable

Cloning the repo and running make bootstrap && make build && make test returns zero on all three; searchctl indexes a 100-document fixture and returns the expected top-1 document for an exact single-term query.

Acceptance
  • make test passes with ≥1 test exercising the 100-document smoke corpus (conformance/corpora/e2e/smoke-100.jsonl).
  • Runtime Docker image ≤ 80 MB (docker images check in CI).
  • ADR files for ADR-01, ADR-02, ADR-05, ADR-08, ADR-10, ADR-13 committed under docs/adr/.
  • make lint-deferred (I14) passes with zero unregistered PhaseDeferred call sites.
Fixtures
Fixture Purpose Expected Output
smoke-100.jsonl 100-doc corpus, single field top-1 doc-id matches recorded fixture
smoke-empty.jsonl 0-document corpus empty SearchResponse, total=0, no panic
smoke-malformed.jsonl 1 line invalid JSON among 100 IndexWriter::add_document returns Err, remaining 99 succeed
Pitfalls
  • Starting the FOR/PFOR codec (Phase 3) before CI is green — resist; Phase 0 is plumbing only.
  • Misconfigured Cargo.toml resolver causing feature-unification surprises across crates — pin resolver = "2" explicitly (ADR-01).
  • Docker image bloat from a single-stage build — multi-stage is mandatory, verify with docker history.

✅ Phase 1 — Analyser Pipeline (Weeks 2–3) §13

Objectives

Bit-identical token streams vs. reference analysers (Lucene StandardAnalyzer, ICU, Snowball) across every fixture; land the CharFilter → Tokenizer → TokenFilter pipeline for all 11 supported languages (§1).

Deliverable
pub struct Token<'a> { pub text: std::borrow::Cow<'a, str>, pub start_byte: u32, pub end_byte: u32,
    pub position: u32, pub position_increment: u32, pub type_: TokenType }
pub enum TokenType { Word, Numeric, Punctuation, Cjk, Hangul, Indic, Synonym, Compound, Stem }
pub trait Stemmer: Send + Sync { fn stem<'a>(&self, token: &'a str) -> std::borrow::Cow<'a, str>; }

crates/analyser/ ships the full pipeline; python/search_engine/analyser.py exposes analyse(text, analyser_name) for notebook use (ADR-11).

Acceptance
  • Analyser conformance suite green (byte/position/type-for-type match) for English, German, French, Spanish, Russian, simplified Chinese (n-gram only), Indic — 4,096/4,096 fixtures pass (conformance/corpora/tokenizer/, bucket analyser.standard + analyser.stemmer).
  • Zero-allocation hot path past the input string for the standard tokenizer (verified via benchmarks/ allocator instrumentation, ≤1 allocation per 64 tokens).
Fixtures
Fixture Purpose Expected Output
standard.jsonl mixed-script, apostrophe, numeric, emoji/ZWJ cases token-for-token match vs. recorded Lucene 9.x baseline
stemmer-{en,de,fr,es,ru}.jsonl Snowball reference vectors stems identical to Snowball test suite
cjk.jsonl n-gram segmentation overlapping-bigram output matches recorded baseline
indic.jsonl grapheme + virama cases matches ICU CLDR reference
Pitfalls
  • Whitespace/apostrophe divergence between UAX-29 and Lucene's StandardTokenizer — pick Lucene-compat as default, document the divergence (do not silently diverge from user expectation).
  • Locale-aware lowercasing traps: Turkish dotted/dotless I, German ß→ss, Greek final sigma — use ICU, never a hand-rolled lowercase table.
  • Stemming is destructive: a stemmed field must not double as the highlight source — ship a _stemmed sub-field for retrieval and _raw for highlighting (feeds §19.5).
  • Synonym expansion at query time is costlier than index time but is the correct default (lists evolve, re-index is expensive) — ship both modes.

✅ Phase 2 — Posting Lists & Term Dictionary (Weeks 3–4) §14

Objectives

Land the in-memory posting-list representation, the on-disk block layout (§8.2), the block-skip list, and the FST term dictionary (P4, ADR-02) that maps terms to posting-list offsets.

Deliverable
pub struct InMemoryPostingList { pub term: String, pub field: FieldId, pub postings: Vec<Posting>,

crates/postings/ ships PostingListReader/Writer + skip-list; crates/dictionary/ ships FST builder/reader. Both round-trip a 1M-posting fixture byte-identically.

Acceptance
  • Round-trip test: write 1,000,000 postings, read back — byte-identical and posting-identical (conformance/corpora/postings/roundtrip-1m.bin).
  • FST size ≤ 1/5 of an equivalent sorted flat term list for a 1M-term vocabulary (ADR-02 claim, verified in benchmarks/).
  • Skip-list intersection benchmark shows ≥ 3× speedup over no-skip-list at df ≥ 100,000 (two-term AND, benchmarks/posting_intersection.rs).
Fixtures
Fixture Purpose Expected Output
roundtrip-1m.bin 1M-posting write+read byte-identical recovery
skip-boundary.bin df ∈ {0,1,127,128,129,1023,1024,1025,1_000_000} correct block/skip behavior at every boundary

Pitfalls
  • Off-by-one in the skip list is the dominant bug class — test the full boundary set in §14.5.
  • CRC must cover compressed block bytes, not decompressed postings (a codec bug corrupting the compression itself must still be caught) — see I3.
  • BufWriter defaults to an 8 KB buffer; bump to 64 KB for posting-list writes to avoid the small-write tax (§17 perf).
  • FST builder requires sorted input; an in-place delta-flush sort has a memory-overhead spike at flush time — budget for it (§33 C3 sizing).

✅ Phase 3 — Posting-List Codecs (Weeks 4–5) §15

Objectives

Ship the codec library — varbyte, FOR, PFOR, simd-bp128, Elias-Fano — and the per-block dispatcher that picks one, with a scalar reference path that every SIMD path must match bit-for-bit (P1).

Deliverable
pub trait Codec: Send + Sync { fn encode(&self, values: &[u32], out: &mut Vec<u8>);
    fn decode(&self, bytes: &[u8], n: usize, out: &mut Vec<u32>); fn name(&self) -> &str; }

crates/codec/ ships all six codecs behind this trait (P14) with round-trip tests across 1M-value fixtures per codec; benchmarks/codec_throughput.rs reports ints/sec by (codec, bit_width).

Acceptance
  • Every codec round-trips 1,000,000 fixture values byte-identically for its designed input distribution (conformance/corpora/codecs/{varbyte,for,pfor,simdbp128}.bin).
  • simd-bp128 decode throughput ≥ 5 GiB/s on AVX2 (M5), ≥ 2 GiB/s on NEON (M6) — gated in CI (§29).
  • Dispatcher's codec choice matches a recorded baseline for representative posting-list shapes (conformance bucket codec.dispatch), zero mismatches.
Fixtures
Fixture Purpose Expected Output
varbyte.bin 1M small-integer values round-trip byte-identical
for.bin 1M dense-range values round-trip byte-identical
pfor.bin 1M values, 10% outliers round-trip byte-identical, exception count matches
simdbp128.bin 1M values, AVX2 required round-trip byte-identical, scalar-path parity
dispatch-baseline.json representative posting-list shapes dispatcher choice matches recorded baseline
Pitfalls
  • Endianness leakage from host to disk — the silent killer across platforms; enforce little-endian explicitly in every codec's byte-level operations.
  • bit_width=0 (all-equal block) must not divide-by-zero in the decoder — an explicit degenerate path is required (§15.8).
  • AVX2 unaligned loads cost ~10% on Skylake-class CPUs — align block starts to 32 bytes where the allocator permits.
  • PFOR's 10% exception threshold is tuned for BM25-shaped posting-list distributions and may need retuning for other workloads — document it as a configuration knob, not a constant.

Acceptance

  • Malformed-input fixtures (§16.5) all produce QueryParse with the exact expected column, never a panic.

Fixtures
Fixture Purpose Expected Output
ast-parity-512.json 512 representative queries AST matches recorded baseline exactly

Pitfalls
  • Whitespace inside a phrase vs. between clauses — lex phrase contents without operator recognition.
  • * collides between prefix-wildcard (term*) and unbounded range marker ([1 TO *]) — resolved by parse-context (a value position expects the range form).
  • +/- prefixes bind at operator level, tighter than AND/OR — document the precedence explicitly (§8.1 EBNF is normative).
  • Believing the Lucene syntax is fully specified from documentation alone — edge cases (unbalanced quotes, escaped colons, leading whitespace in parens) are observed Lucene behavior; fixtures must be recorded against an actual Lucene runtime, not inferred (§27 Lucene parity).

✅ Phase 5 — Search Execution (Weeks 7–8) §17

Objectives

Land the document-at-a-time executor: conjunction/disjunction/phrase/proximity/fuzzy/range/wildcard iterators, BM25/BM25F scoring, WAND/Block-Max-WAND early termination (P13), the top-k collector.

Deliverable
pub trait PhraseMatcher: Send { fn matches(&mut self, doc: DocId) -> bool;
    fn matches_count(&mut self, doc: DocId) -> u32; }

crates/search/ ships all iterators, both scorers, the BMW top-k path, and the collector, all behind the PostingListReader/Scorer traits (§11.5, §11.6, P14).

Acceptance
  • BM25 scores match a recorded Lucene baseline within 1e-5 relative tolerance on 1,000 MS-MARCO subset queries (conformance/corpora/scorer/bm25.jsonl, bucket scorer.bm25).
  • BMW throughput ≥ 30% faster than naive disjunction on a 1M-document corpus at top-10 (benchmarks/bm25_topk.rs).
  • BMW skip ratio ≥ 70% blocks skipped on the MS-MARCO subset (M7, §29).
  • Every conformance query's BMW top-k set is identical to the exhaustive-disjunction top-k set (I6, zero mismatches).
Fixtures
Fixture Purpose Expected Output
bm25.jsonl 1,000 MS-MARCO queries scores within 1e-5 of Lucene baseline
bmw-vs-naive.jsonl differential top-k check identical top-k sets (I6)
phrase-slop-0-1-2.jsonl phrase/proximity at 3 slop values matches recorded Lucene baseline
fuzzy-cap-hit.jsonl fuzzy query exceeding 1,024-term cap documented warning emitted, capped result returned
Pitfalls
  • Float comparison in the top-k heap — use a total-order float wrapper; never let NaN poison comparisons.
  • BMW correctness depends on block-max being a true upper bound — compute and verify at index time (I4); any drift is a correctness bug, not a performance regression.
  • Phrase queries with slop > 0 are subtle around tied positions — test against a recorded Lucene baseline at slop {0,1,2}.
  • Fuzzy queries can blow up the candidate term set — the 1,024-term cap with a documented warning is mandatory, not optional.

⬜ Phase 6 — Segments, Merge Policy, Real-Time Index (Weeks 9–10) §18

Objectives

Land the persistent index: immutable segments (P6), the LSM-style tiered merge policy (P7, ADR-05), the in-memory delta layer with WAL, and the snapshot semantics (I8) that keep the index queryable while writes are in flight.

Deliverable
pub struct TieredMergePolicy { pub max_segments_per_tier: u32, pub max_segment_size: u64,
    pub floor_segment_size: u64, pub merge_factor: u32 }
pub trait MergePolicy: Send + Sync { fn select(&self, segments: &[SegmentMeta]) -> Vec<MergeSpec>; }
pub struct Snapshot { pub version: u64, pub segments: Vec<SegmentReader>, pub delta: DeltaReaderHandle }

crates/segment/ + crates/delta/ ship the full mechanism; both pass a 100k-document stress test and a crash-replay test (§18.5).

Acceptance
  • 100k-document stress test (batches of 1,000): zero OOM, every commit produces a queryable segment, merge policy keeps segment count ≤ max_segments_per_tier per tier throughout.
  • Crash test: kill the process mid-write, restart, replay WAL — zero data loss past the last committed commit() call (I11, RPO=0 per §4).
  • Storage amplification at steady state ≤ 1.3× live-document bytes (§4 constraint, verified post-merge).
Fixtures
Fixture Purpose Expected Output
stress-100k.jsonl 100k docs in 1k batches no OOM, bounded segment count per tier
crash-mid-write.sh kill -9 mid-flush_block WAL replay recovers to last commit, zero loss
tombstone-visibility.jsonl delete then immediate query deleted doc never returned (I12)
snapshot-stability.jsonl query holds snapshot across a concurrent merge consistent view throughout (I8)
Pitfalls
  • rename-into-place atomicity is filesystem-specific — works on ext4/xfs/apfs, unreliable on overlayfs; document supported filesystems explicitly.
  • Merge-policy parameters are workload-coupled — ship the §18.2 defaults but expose them in EngineConfig.
  • WAL fsync is the write-throughput bottleneck — group commits across submitters, fsync ∈ {none, batch, always}, default batch with a 5 ms group window.
  • Tombstone bitmaps grow with deletes — a segment above 30% deleted-fraction is a merge candidate even below the size threshold.

⬜ Phase 8 — Hybrid Sparse + Dense Fusion (Week 12) §20

Objectives

Ship the hybrid retrieval path: BM25 (sparse) and dense-vector (delegated, §1) results combined via RRF or weighted-sum (ADR-09), with an optional neural-reranker hook on the merged top-k.

Deliverable
pub trait DenseRetriever: Send + Sync { fn retrieve(&self, query_vector: &[f32], k: u32) -> Vec<(DocId, f32)>; }
pub trait Reranker: Send + Sync { fn rerank(&self, query: &str, candidates: &[Document]) -> Vec<f32>; }

crates/hybrid/ ships RRF, weighted-sum, the dense adapter, and the neural-rerank hook.

Acceptance
  • RRF fusion (sparse + dense) on the MS-MARCO subset yields higher MRR@10 than either sparse-only or dense-only retrieval alone (benchmarks/results/<host>/hybrid.json).
  • Hybrid (BM25 + dense + RRF) MRR@10 improvement over BM25-only ≥ +10% (M12, §29).
  • Dense + sparse retrieval overlap measurably reduces end-to-end latency vs. sequential execution (benchmark comparison, both paths timed).
Fixtures
Fixture Purpose Expected Output
hybrid-msmarco.jsonl MS-MARCO subset, RRF fusion MRR@10 ≥ +10% vs. BM25-only
rrf-vs-weighted.jsonl same query set, both fusion modes both outperform single-signal, RRF requires no tuning
dense-adapter-mock.jsonl MockRetriever contract test fixed vectors return deterministic scores
Pitfalls
  • Score-scale differences between BM25 and cosine similarity are large — weighted-sum without normalization produces nonsense rankings; always normalize per-list first.
  • The dense path's latency dominates hybrid latency — pipeline sparse and dense retrieval in parallel, never sequentially.
  • The reranker is the most expensive stage — cap top-k to 100 by default and document the latency/precision tradeoff explicitly.

⬜ Phase 9 — HTTP/gRPC Server, Coordinator, Scatter-Gather (Week 13) §21

Objectives

Ship the network surface (axum HTTP + tonic gRPC, ADR-10), the coordinator that routes requests to shards, the scatter-gather merger, and partial-failure tolerance across shard replicas (P12).

Deliverable
pub async fn scatter_gather(req: SearchRequest, shards: &[ShardClient],
    timeout: std::time::Duration) -> Result<SearchResponse>;

crates/server/ ships HTTP + gRPC; crates/coordinator/ ships the router + scatter-gather.

Acceptance
  • Integration test: 4 shards, 1M documents, 1,000 queries — p99 latency < 50 ms (M3, §4, §29).
  • Partial-failure test: 1 of 4 shards killed mid-benchmark — responses continue with partial_failures populated, zero request-level failures while ≥1 shard is healthy.
  • Replica fail-over test: primary killed — reads continue from a replica within RTO ≤ 5 s (§4).
Fixtures
Fixture Purpose Expected Output
scatter-gather-4shard.jsonl 4-shard fan-out, 1M docs p99 < 50 ms, correct merged top-k
partial-failure-1of4.sh kill one shard mid-load partial_failures populated, request succeeds
replica-failover.sh kill primary reads resume from replica within RTO
openapi-examples.json every OpenAPI example request response validates against schema
Pitfalls
  • Per-shard top-k must be ≥ global top-k or the merged top-k is silently wrong — default 2 × global_top_k, document the multiplier as a tunable tradeoff (memory vs. correctness margin).
  • Partial-failure tolerance is easy to get subtly wrong — test extensively with chaos-style random shard timeouts and connection resets, not just clean kills.
  • Replication lag means a just-committed write may not be visible on a replica for up to the refresh boundary (§18.7) — default read-after-write consistency to "primary read" for write-heavy workloads.
