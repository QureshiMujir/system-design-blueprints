34. Back-of-Envelope Capacity Model

  1. Snapshot payload bytes. 5,000 nodes (§4 latency-budget reference size) × 6 avg fields/node × 24 avg bytes/field (CBOR-encoded) = 5,000 × 6 × 24 = 720,000 bytes ≈ 703 KB per keyframe — the number the p50/p95/p99 serialize-latency budget (§4) is benchmarked against. At the 20,000-node truncation cap: 20,000 × 6 × 24 = 2,880,000 bytes ≈ 2.75 MB, the worst case before TruncationMarker intervenes.

  2. Transport bandwidth. Steady state: one delta message every 16 ms (60/s) averaging 2 KB = 60 × 2 KB = 120 KB/s = 0.96 Mbps — comfortably under the 2 Mbps sustained cap (§4), leaving headroom for periodic full keyframes (~703 KB every K commits, amortized).

  3. Ring-buffer memory. 50,000 events (§4 capacity) × 160 bytes/event (§4 average) = 8,000,000 bytes ≈ 7.63 MiB — consistent with the declared 8 MB byte cap (§4); the capacity and byte-cap numbers were chosen to match at this average event size.

  4. Time-scrub seek cost. Keyframe interval K commits, each delta apply ≈ 0.1 ms, worst case K−1 deltas applied = (K−1) × 0.1 ms. For the ≤ 120 ms p95 budget (§4) to hold, K−1 ≤ 1,200, i.e. K ≤ ~1,200 at this assumption; the reference implementation (§19.2) uses K = 200, giving a worst-case seek cost of 199 × 0.1 ms ≈ 20 ms, well within budget with margin for slower deltas.

  5. Serialization CPU per commit. ~20 nodes touched per commit (typical dirty subtree) × ~20 ns/node (a delta touches far fewer nodes than a full snapshot) = 20 × 20 ns = 400 ns — far under the ≤ 0.5 ms (500,000 ns) per-commit budget (§4/M2), leaving ~99.9% of that budget as margin for hook-call overhead itself.

  6. Dependency-graph memory. 500 edges (§4/M11 query-ceiling reference) × 48 bytes/edge (two NodeId-scale references plus a clock and a kind tag) = 24,000 bytes ≈ 23 KiB for a typical session — trivial relative to the 40 MB memory ceiling (§4/M12), confirming the dependency graph is not the dominant memory consumer at typical scale, though §31 names it as the first structure to grow unbounded over a very long session since, unlike the other buffers here, it carries no cap.

  7. Redaction throughput headroom. At the ≥ 50,000 fields/s target (§4/M9) against a typical 5,000-node × 6-field snapshot = 30,000 fields, a full-snapshot redaction pass costs 30,000 / 50,000 = 0.6 s worst case — why redaction is applied incrementally on deltas in steady state (§22.2) rather than re-scanning a full snapshot on every message; the 0.6 s figure is the ceiling for the keyframe case only, amortized against the K-commit interval between keyframes (0.6 s / 200 ≈ 3 ms of amortized redaction cost per commit-equivalent).
