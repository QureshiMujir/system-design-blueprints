1 — Live Runtime State Inspector

Project Number: 1

Project Name: Live Runtime State Inspector

1. Goal & Scope

The Live Runtime State Inspector (LRSI) is a development-time instrumentation and inspection system for JavaScript/TypeScript runtimes. It attaches to a running target — a browser tab or a Node.js process — via a set of instrumentation hooks installed in the target's own realm, walks the live component/module tree, the reactive signal/effect/subscription graph, in-flight async work, and a bounded history of runtime events, serializes all of it into a versioned, cycle-safe snapshot schema, and streams it over a reconnect-tolerant transport to a separate inspector backend and UI client. The UI presents this as a queryable, time-scrubbing surface: the developer can search the live tree, replay the last N commits, inspect why a given effect re-ran, and follow an async task from dispatch to settlement — all without modifying the target's build pipeline.

Phase-0 deliverable — packages (pnpm workspace):

  1. @lrsi/hooks — instrumentation hook registration API, installed in the target realm; the only package with a hard near-zero-overhead budget (see §4).
  2. @lrsi/serializer — cycle-safe, bounded snapshot serializer; produces StateSnapshot.
  3. @lrsi/eventlog — monotonic ring-buffer event log, keyed by LogicalClock.
  4. @lrsi/transport — WebSocket wire protocol, CBOR encoding, reconnect-across-hot-reload.
  5. @lrsi/backend — session manager, query-engine host, redaction-filter application point.
  6. @lrsi/query — QuerySpec compiler and evaluator over snapshots and event streams.
  7. @lrsi/replay — time-scrub projector; keyframe + delta replay.
  8. @lrsi/ui — inspector UI client (tree view, dependency-graph view, scrubber, event log).
  9. @lrsi/redact — RedactionRule engine, applied pre-transport.
  10. @lrsi/telemetry — opt-in operational telemetry (OpenTelemetry-based).
  11. @lrsi/adapter-react — first runtime adapter (Phase 1).
  12. @lrsi/bridge — remote-target bridge (Phase 10).
  13. @lrsi/conformance — conformance suite and fixture corpus (Phase 11).

Boundaries. Provides: the instrumentation-hook contract, the state-snapshot schema and its serializer, dependency-graph capture, a bounded event log, a reconnect-tolerant transport, a query engine, time-scrub replay, redaction, and a remote-target bridge. Delegates: breakpoint/step debugging to the editor's own Debug Adapter Protocol tooling; wire-level browser introspection to the Chrome DevTools Protocol / V8 Inspector Protocol where the target is V8-hosted; pixel-level replay to the browser itself. Does NOT provide: production APM (no long-term metrics warehouse, no alerting SaaS), a general-purpose debugger replacing DAP (no breakpoints, no stepping, no register/stack inspection), a session-replay/video product, or a source-map decompiler.

Non-goals (explicit). Not a production APM. Not a general-purpose debugger replacing DAP. Not a state-mutation tool — LRSI observes; it never writes into the target's live state (Principle P1). Not a multi-language inspector — V8-hosted JS/TS only for the life of this blueprint.

Deployment model. Three surfaces: (a) a dev dependency (@lrsi/hooks + adapter installed in the target app during development, tree-shaken to nothing in production builds per ADR-17); (b) a browser-hosted UI served by @lrsi/backend with an optional thin browser-extension shell that proxies CDP-adjacent context for tab discovery; (c) a remote-target bridge (@lrsi/bridge, Phase 10) for Node.js or remote-browser targets reachable only over a network boundary.

Users/operators. Primary: the developer instrumenting their own app. Secondary: a teammate attached read-only to a shared remote target (Phase 10). Tertiary: the CI conformance harness, non-interactive, driving fixture apps.

What later phases unlock. Phase 4 unlocks visual component/module tree navigation. Phase 5 unlocks the reactive dependency graph — the actual "why did this re-run" question. Phase 6 unlocks historical event correlation. Phase 7 unlocks time-travel over captured commits. Phase 8 unlocks async-causality tracking. Phase 9 unlocks ad hoc querying and saved views for recurring investigations. Phase 10 unlocks safely attaching to a deployed remote target. Phase 11 locks conformance and performance budgets for a 1.0 release.

TypeScript, and why. The target runtimes are themselves JS/TS; a shared type system across the hook contract, the wire protocol, and the UI client removes a translation boundary that is a chronic source of bugs in prior art (react-devtools-shared's own bridge layer duplicates types across its backend/frontend split). Strict mode; no any at the hook boundary. Rejected: Rust/WASM for the hooks — cannot safely monkey-patch a running JS heap from outside the JS realm, and FFI overhead defeats the near-zero-cost requirement of Invariant I1. Go for the backend — no shared type surface with the hook contract, forcing a schema-translation layer (ADR-01). Python for tooling — acceptable for conformance scripts, wrong for anything on the hot instrumentation path.

Prerequisites. Node.js current LTS; a V8-hosted target (Phase 1 scope; other engines are PhaseDeferred, see §37); Chrome 120+ for the optional extension shell.

Timeline. Expressed as Phase 0 through Phase 11, unit-of-work ordered, not calendar-dated — this document specifies engineering scope, not a shipping calendar.

Deferrals. PhaseDeferred("§20 Phase 8 — Async/In-Flight Work Tracking") — cross-runtime async causality (work spanning worker threads or a second engine). PhaseDeferred("§22 Phase 10 — Remote-Target Bridge + Redaction") — target-side pre-serialization redaction, as opposed to the backend-side filter shipped in Phase 10. PhaseDeferred("§13 Phase 1 — Instrumentation Contract + First Runtime Adapter") — multi-session collaborative attach (concurrent UI clients on one session with live cursors), and non-V8 engine adapters (SpiderMonkey, JSC). PhaseDeferred("§14 Phase 2 — Cycle-Safe Bounded Serialization") — a compiler-transform instrumentation mode as an alternative to runtime monkey-patching (see §36). PhaseDeferred("§19 Phase 7 — Time-Scrub Replay Projection") — persistent cross-session recordings retained beyond a single attach.

2. Why Build This

  • Framework dev tools are siloed: React DevTools, Vue DevTools, Redux DevTools each understand one runtime's internals and nothing else.
  • "Why did this re-run" is the single most expensive question in reactive UI debugging, and no general tool answers it structurally — engineers grep console logs instead.
  • Time-travel exists (Elm, Redux DevTools) but only for architectures that are already pure and serializable; most real apps are not.
  • Async causality — which fetch caused which render — is invisible without manual instrumentation.
  • Production-build name-mangling and tree-shaken dev tools leave engineers blind exactly when an incident is live.
  • The Chrome DevTools Protocol proves a session-oriented, versioned, reconnect-tolerant wire protocol for runtime introspection is buildable and durable — LRSI generalizes that model above the framework layer instead of below it.
  • Observing a system changes it (the observer effect); most ad hoc debugging aids ignore this and quietly corrupt the timing behavior they're trying to explain.

What Mastery Looks Like

  • Writing an instrumentation hook that is provably a no-op when uninstalled, with a bundle-diff test proving dead-code elimination (Phase 0 / Phase 11).
  • Designing a serializer that terminates on any cyclic object graph without an unbounded stack or an unbounded payload (Phase 2).
  • Building a transport that survives a hot-reload disconnect without losing session identity or double-counting events (Phase 3).
  • Modeling a fine-grained reactive dependency graph well enough to answer "why did this effect re-run" as a structural query, not a log grep (Phase 5, Phase 9).
  • Building a time-scrub projector that reconstructs historical state from keyframes and deltas without re-executing any target-side code (Phase 7).
  • Tracing an async task from dispatch to settlement across event-loop turns without corrupting the causal order (Phase 8).
  • Bridging to a remote, untrusted-network target safely, with redaction enforced before the trust boundary, not after (Phase 10).
  • Proving all of the above holds under a synthetic render storm and a fuzzed wire decoder before calling it 1.0 (Phase 11).

Instrumentation Hooks install into the target's own realm at attach time and are the only component with a hard zero-overhead-when-detached requirement (I1); they call into the framework adapter (Phase 1) and forward raw mount/update/unmount/edge/event notifications.

Snapshot Serializer walks the live object graph reachable from tracked roots, applies cycle detection and truncation, and produces a StateSnapshot — the single artifact everything downstream operates on.

Dependency Graph Tracker observes signal reads, effect registrations, and subscription edges as they are established or torn down, and emits DependencyEdge records independent of the snapshot tree.

Redaction Filter applies RedactionRules to a snapshot or event before it leaves trust boundary A; this is the only point downstream code may assume secrets have already been stripped.

Event Ring Buffer stores EventRecords in a fixed-capacity, LogicalClock-ordered buffer inside the target process, so a hot-reload or crash doesn't require replaying history from zero.

Transport is a WebSocket connection carrying CBOR-encoded TransportMessages, with a bounded send-queue and an explicit reconnect/resume handshake that survives a hot-reload disconnect.

Session Manager owns the per-attach state machine (§8.6), routes messages to the query engine and replay projector, and is the only component permitted to change session state.

Query Engine compiles and evaluates QuerySpec predicates/projections over the current snapshot and the event log, without ever falling back to string-matching serialized JSON (P10).

Time-Scrub / Replay Projector reconstructs any historical ScrubCursor position from the nearest keyframe plus delta application, without re-invoking any target-side code (I9).

UI Client renders the tree, the dependency graph, the event log, and the scrubber; it holds no direct reference to the target and communicates exclusively over the wire protocol.

Telemetry emits OpenTelemetry spans/metrics from the backend and transport only — never from the hooks, preserving the zero-overhead boundary (ADR-19).

6. Design Principles

P1 — Never change program semantics. The inspector must never change the semantics of the program it observes. Tradeoff: LRSI cannot live-patch application data as a debugging shortcut. Operational implication: engineers reproduce bugs via inputs, not live state edits. Violating this turns the inspector into an uncontrolled production mutator and voids I9.

P2 — Bounded-by-construction. No unbounded structure — every buffer (ring buffer, snapshot cache, id table) has a documented eviction policy declared at definition time. Violating this converts a long session into a slow memory leak in the target process.

P3 — Serialization is lossy by declaration, never silent. Every truncation emits a TruncationMarker. Violating this makes the UI lie about what it's showing.

P4 — Zero cost when detached. Hooks installed but the session Detached cost effectively nothing. Violating this means merely installing LRSI as a dev dependency taxes every developer's machine, defeating adoption.

P5 — The wire is the contract, not the runtime internals. UI and backend never assume in-process access to the target. Violating this collapses the trust and protocol boundaries that make the remote bridge (Phase 10) possible.

P6 — Attach is reversible. Every install() has a matching uninstall() restoring pre-attach state. Violating this causes hot-reload node-id orphaning and leaked listeners.

P7 — Logical time, not wall time, orders causality. The event log and dependency graph use LogicalClock. Violating this corrupts causal ordering the instant a remote bridge introduces clock skew.

P8 — A cycle is not an error. Cyclic graphs (store referencing a component referencing the store) are expected and must serialize to a finite payload every time. Violating this crashes the serializer on the first real reactive store it meets.

P9 — Redaction happens before the trust boundary, not after. A redacted field is filtered before it is placed on the wire. Violating this means a secret is one client bug away from disclosure.

P10 — Query the graph, don't grep the tree. The query engine operates over the dependency graph and event log as first-class structures. Violating this reduces the "why did this re-run" question back to manual log archaeology — the exact problem this project exists to solve.

P11 — Degrade visibly, never silently. A Degraded session state is always user-visible. Violating this lets the UI show stale data as if it were live, which is worse than showing nothing.

P12 — One hook contract, many adapters. Framework-specific concepts never leak into the wire schema. Violating this couples the UI to a single framework's internals, defeating the framework-agnostic design.

P13 — Every invariant has a detection method. An invariant without a runtime check (§7) is a belief, not an invariant. Violating this means regressions ship silently.

P14 — The inspector must be debuggable using itself. Dogfooding forces the schema and performance budget to hold under LRSI's own development. Violating this means the tool's authors never feel the pain their users feel.

Methodology. A release candidate is exercised by: attaching to a fixture app under a synthetic render storm (I11, I14); forcing a hot reload mid-snapshot (I6, I12); injecting a cyclic store (I3); instrumenting a getter with a side effect (I13); then running the full conformance suite (§28), confirming every detection signal fires and every recovery path engages before the candidate is declared green.

8.2 Instrumentation Contract

Hook Call When Ordering Guarantee
onMount(node) first materialization of a tracked node happens-before any onUpdate for that node
onUpdate(node, prevRef) a value/shape change commits ordered by LogicalClock; never reordered relative to onMount/onUnmount for the same node
onUnmount(node) node is removed happens-after all onUpdate calls for that node
onDependencyEdge(from, to, kind) a signal/effect/subscription edge is (dis)established may interleave with onUpdate; always tagged with the triggering commit's clock
onAsyncTaskStart / onAsyncTaskEnd an async boundary is crossed matched pair, single writer per task id
onEvent(record) a discrete event occurs (dispatch, render, effect run) append-only, monotonic clock

8.3 Dependency Graph Model

Nodes are signals, effects, and subscriptions. Edges are DependencyEdge { from, to, kind } where kind ∈ { reads, writes, subscribes, triggers }. The graph is captured independently of the snapshot tree so that "what depends on this" is a graph traversal, not a tree search (P10).

8.7 Time-Scrub Projection Model

A keyframe is captured every K commits (K derived in §34). ScrubCursor = { keyframeId, deltasApplied }. Seeking forward from the cursor applies subsequent deltas in order; seeking to an earlier point replays from the nearest prior keyframe forward (deltas are not assumed invertible unless the adapter declares them so).

8.8 Worked Example — Serializing a Cyclic Reactive Store

Store S has a computed signal derived whose value structurally embeds a back-reference to S itself (a common pattern: a store exposing self for chaining). The serializer visits S, assigns it nodeId = N1, walks into derived, and on encountering the embedded reference to S again, recognizes N1 in the visited-WeakMap and emits { typeTag: "ref", cycleRef: { target: "N1" } } instead of recursing. The resulting payload is finite regardless of how many times S references itself, satisfying I3.

8.9 Malformed-Input Examples

  • An EventBatch containing an out-of-order LogicalClock value — quarantined per I4, session flagged Degraded until the source stream is confirmed sane.
  • A Snapshot referencing a NodeId absent from the id table (orphaned after a hot reload) — treated as a newly-mounted node; the orphan is flagged, never silently merged into stale state.
  • A TransportMessage carrying a truncated CBOR frame — the decoder rejects the frame and requests retransmission rather than attempting partial decode.

8.10 Failure-Path Example

A hot reload occurs mid-snapshot-serialization. The partial payload is discarded (never partially applied); the adapter is reinstalled; a fresh keyframe is requested; the UI shows a Degraded badge until the new keyframe arrives and the session returns to Attached.

11. Core Schema & Types

// SessionId — owner: SessionManager; immutable once issued; not persisted across Detached.
type SessionId = string & { readonly __brand: "SessionId" };

// NodeId — owner: serializer's WeakRef table; stable within a session; not compatible across
// session boundaries; serializable as an opaque string.
type NodeId = string & { readonly __brand: "NodeId" };

// LogicalClock — owner: hooks (issued at source); monotonic per session; compared, never added.
type LogicalClock = number & { readonly __brand: "LogicalClock" };

// StateSnapshot — owner: serializer; produced per keyframe; immutable once emitted;
// serializes via CBOR (ADR-05); versioned by `ussVersion` (see §27).
interface StateSnapshot {
  readonly sessionId: SessionId;
  readonly clock: LogicalClock;
  readonly roots: readonly NodeId[];
  readonly nodes: ReadonlyMap<NodeId, SnapshotNodeRecord>; // see §8.1 field table
  readonly ussVersion: string;
}
// SerializedValue — tagged union; owner: serializer; immutable; produced per primitive node.
type SerializedValue =
  | { tag: "string"; v: string }
  | { tag: "number"; v: number }
  | { tag: "boolean"; v: boolean }
  | { tag: "bigint"; v: string }   // decimal string form, CBOR bignum on the wire
  | { tag: "null" }
  | { tag: "undefined" }
  | { tag: "native"; kind: string; summary: string }; // Date, Map, Set, Promise, RegExp, etc.

// TruncationMarker — owner: serializer; attached to a node exceeding depth/breadth caps (§4).
interface TruncationMarker {
  readonly reason: "depth" | "breadth" | "node-cap" | "byte-cap";
  readonly limit: number;
}

// CycleRef — owner: serializer; emitted in place of re-descending into a visited node (I3).
interface CycleRef {
  readonly target: NodeId;
}
// DependencyEdge — owner: Dependency Graph Tracker; append-only within a session.
interface DependencyEdge {
  readonly from: NodeId;
  readonly to: NodeId;
  readonly kind: "reads" | "writes" | "subscribes" | "triggers";
  readonly clock: LogicalClock;
}

// EffectRecord — owner: Dependency Graph Tracker; mutation: append/retire only, never edited.
interface EffectRecord {
  readonly nodeId: NodeId;
  readonly lastRunClock: LogicalClock;
  readonly dependsOn: readonly NodeId[];
  readonly disposed: boolean;
}

// AsyncTaskRecord — owner: async-tracking hook (Phase 8); concurrency: single writer per task.
interface AsyncTaskRecord {
  readonly taskId: string;
  readonly startClock: LogicalClock;
  readonly endClock: LogicalClock | null;
  readonly causedBy: NodeId | null;
  readonly status: "pending" | "settled" | "rejected";
}
// EventRecord — owner: hooks; append-only; see §8.4 for the full field table.
interface EventRecord {
  readonly eventId: string;
  readonly clock: LogicalClock;
  readonly kind: "dispatch" | "render" | "effect-run" | "subscription-fire" | "async-boundary";
  readonly subjectNodeId: NodeId;
  readonly payloadSummary: SerializedValue | null;
  readonly sourceAdapter: string;
  readonly sizeBytes: number;
}

// RingBuffer<T> — owner: @lrsi/eventlog; mutation: push-with-eviction only (ADR-10);
// concurrency: single-writer (hooks), multi-reader snapshot view.
interface RingBuffer<T> {
  readonly capacity: number;
  readonly byteCapacity: number;
  push(item: T): void;                 // may evict oldest non-keyframe entry
  snapshotRange(from: LogicalClock, to: LogicalClock): readonly T[];
}
// TransportMessage — owner: @lrsi/transport; wire-serializable via CBOR; versioned (§27).
type TransportMessage =
  | { type: "Hello"; protocolVersion: string; capabilities: readonly string[] }
  | { type: "AttachRequest"; targetId: string }
  | { type: "AttachAck"; sessionId: SessionId; snapshot: StateSnapshot }
  | { type: "Detach"; sessionId: SessionId }
  | { type: "Snapshot"; snapshot: StateSnapshot }
  | { type: "SnapshotDelta"; sessionId: SessionId; patch: readonly DeltaOp[] }
  | { type: "EventBatch"; sessionId: SessionId; events: readonly EventRecord[] }
  | { type: "Heartbeat"; sessionId: SessionId }
  | { type: "Query"; sessionId: SessionId; spec: QuerySpec }
  | { type: "QueryResult"; sessionId: SessionId; result: unknown }
  | { type: "RedactionPolicyUpdate"; rules: readonly RedactionRule[] }
  | { type: "Error"; code: string; message: string };

// DeltaOp — owner: @lrsi/serializer diff step; used by SnapshotDelta and by @lrsi/replay.
type DeltaOp =
  | { op: "add"; path: string; node: SnapshotNodeRecord }
  | { op: "replace"; path: string; node: SnapshotNodeRecord }
  | { op: "remove"; path: string };
// Subscription — owner: @lrsi/backend session; mutation: created/torn down by client request.
interface Subscription {
  readonly id: string;
  readonly sessionId: SessionId;
  readonly spec: QuerySpec;
  readonly active: boolean;
}

// RedactionRule — owner: @lrsi/redact; evaluated pre-transport (I5); serializable, versioned.
interface RedactionRule {
  readonly pathPattern: string;   // glob-like path matcher, see §8.2 path format
  readonly reason: "secret-heuristic" | "user-declared" | "policy";
}

// ScrubCursor — owner: @lrsi/replay; mutation: advanced only by seek operations.
interface ScrubCursor {
  readonly sessionId: SessionId;
  readonly keyframeId: string;
  readonly deltasApplied: number;
}
// QuerySpec — owner: @lrsi/query; compiled, not string-interpreted (P10); immutable once built.
interface QuerySpec {
  readonly select: "nodes" | "edges" | "events";
  readonly predicate: QueryPredicate;
  readonly project?: readonly string[];
}

type QueryPredicate =
  | { kind: "pathMatches"; pattern: string }
  | { kind: "typeIs"; typeTag: string }
  | { kind: "and"; of: readonly QueryPredicate[] }
  | { kind: "or"; of: readonly QueryPredicate[] };

// InstrumentationHooks — owner: framework adapter; installed/uninstalled per §8.2 contract.
interface InstrumentationHooks {
  readonly adapterId: string;
  install(ctx: unknown): void;     // idempotent (P6)
  uninstall(): void;               // must fully restore pre-attach state (I6)
  onMount(node: NodeId): void;
  onUpdate(node: NodeId, prevRef: NodeId | null): void;
  onUnmount(node: NodeId): void;
  onDependencyEdge(edge: DependencyEdge): void;
  onEvent(record: EventRecord): void;
}

// Error types — owner: shared; serializable across the wire boundary.
type LrsiErrorCode =
  | "ATTACH_TIMEOUT" | "PROTOCOL_MISMATCH" | "REDACTION_VIOLATION"
  | "RING_BUFFER_OVERFLOW" | "REPLAY_NONDETERMINISM" | "RESUME_TOKEN_INVALID";
interface LrsiError { readonly code: LrsiErrorCode; readonly message: string; }

  3. Implement fiber traversal → onMount/onUpdate/onUnmount calls, respecting the happens-before ordering in §8.2.
  4. Implement onDependencyEdge emission for useState/useReducer/useEffect dependency arrays — a first, coarse dependency graph, refined in Phase 5 (§17).
  5. Implement install()/uninstall() idempotency per P6; write the uninstall-cleanliness conformance fixture (I6).
  6. Add the ADR-17 production-strip guard around every adapter install call site; verify via scripts/bundle-diff.ts.

13.3 Deliverable

@lrsi/adapter-react attaches to a running React 18 app, emits mount/update/unmount/edge events conforming to §8.2, and fully uninstalls on request.

13.4 Acceptance Criteria

  • Overhead per commit ≤ 0.5 ms (§4) measured on examples/react-counter at 60 renders/s.
  • Zero-cost-when-detached: CPU delta between "hooks loaded, not attached" and "hooks absent" is < 0.1% over a 60-second idle profile.
  • uninstall() leaves zero listeners/globals per adapter-uninstall-cleanliness.spec.ts.
  • Detection succeeds on 5 named fixture apps: CRA, Vite+React, Next.js app router, Next.js pages router, Remix.

13.5 Conformance Fixtures

  • conformance/fixtures/phase1-react-detect-cra.json — expects {detected:true, version:"18.x"}.
  • conformance/fixtures/phase1-react-mount-order.json — asserts onMount happens-before onUpdate for a freshly mounted counter.
  • conformance/fixtures/phase1-react-uninstall-cleanliness.json — attach, interact, detach; asserts zero residual listeners via a listener census.
  • conformance/fixtures/phase1-malformed-no-react.json — a plain DOM page; expects {detected:false}, not a thrown error.

13.6 Pitfalls

  • Assuming __REACT_DEVTOOLS_GLOBAL_HOOK__ is always present — many production and some dev builds omit it; the DOM-walk fallback is not optional.
  • Coupling onUpdate payloads to React's internal memoizedState shape — leaks a framework-specific concept into the wire schema, violating P12.
  • Forgetting that uninstall() must also detach from __REACT_DEVTOOLS_GLOBAL_HOOK__ if LRSI registered as a renderer listener there — a common source of I6 violations.
  • Hot-reload orphaning fiber-derived NodeIds: a component's fiber identity can change across a Fast Refresh boundary even though the developer perceives "the same component" — addressed structurally in Phase 3, but the adapter must tag orphan candidates now.

13.7 Performance Concerns

Fiber traversal on a commit is O(nodes in the committed subtree); the adapter must never walk the full tree on every update — only the dirty subtree the renderer already identifies — or the overhead budget (§4) is unreachable on any nontrivial app.

13.8 Edge Cases

  • Suspense boundaries and lazily-loaded components mounting asynchronously — onMount ordering must still hold per-node even though tree-wide ordering is not total.
  • A component that throws during render — the adapter must not itself throw; it emits a best-effort partial event and continues.
  • Portals rendering into a DOM node outside the root — must still resolve to a NodeId under the correct logical root, not silently dropped.

13.9 Failure Analysis

The dominant Phase-1 failure mode is a React minor-version internal shape change breaking fiber-field access; detected by the adapter's version-dispatch table failing to match, surfaced as a Degraded session with a PROTOCOL_MISMATCH-adjacent warning rather than a silent crash; recovery is a per-version dispatch-table patch release.

13.10 Operational Notes

Adapter releases are versioned independently of the core packages (§27); a new React minor version triggers a same-week compatibility check per the Required Reading discipline around framework internals drift.

14. Phase 2 — Cycle-Safe Bounded Serialization

14.1 Objectives

  • Extend @lrsi/serializer to handle cyclic object graphs without unbounded recursion or payload growth (I3, ADR-06).
  • Enforce the node-count and memory ceilings from §4.
  • Guarantee getter/proxy-trap safety during traversal (I13).

14.2 Detailed Implementation Steps

  1. Introduce a visited-WeakMap<object, NodeId> walked before recursing into any container (ADR-06); on a hit, emit CycleRef instead of descending (I3).
  2. Replace the Phase-0 strong id table with the WeakRef/FinalizationRegistry model from ADR-07/I2; verify via a heap-snapshot diff test.
  3. Access all object properties via Reflect.get with a re-entrancy guard flag; never invoke a property's setter or trigger a Proxy set trap during a read-only walk (I13; informed by the Crafting Interpreters GC-chapter ownership discipline, §5).
  4. Implement the node-count cap (20,000, §4) and byte-cap truncation, emitting TruncationMarker{reason:"node-cap"|"byte-cap"} (P3/I10).
  5. Add the native-type serializer registry (Date, Map, Set, Promise, RegExp) producing stable SerializedValue{tag:"native"} summaries (ADR-05).
  6. Benchmark against the §4 p50/p95/p99 serialize-latency targets on a 5,000-node synthetic fixture; gate CI on regression beyond p99.

14.3 Deliverable

A serializer that terminates in bounded time and bounded payload size on any object graph, including deliberately pathological cyclic and getter-laden fixtures.

14.4 Acceptance Criteria

  • serializer-cycle.spec.ts: a self-referencing store serializes to a payload ≤ 2 KB regardless of reference depth.
  • Serialize latency on the 5,000-node fixture: p50 ≤ 4 ms, p95 ≤ 16 ms, p99 ≤ 40 ms (§4), measured via benchmarks/serializer.bench.ts.
  • Memory ceiling: heap-snapshot diff shows ≤ 40 MB attributable to LRSI structures after 100 consecutive snapshots of the 5,000-node fixture.
  • Zero side-effecting getter invocations recorded in phase2-getter-side-effect.json (I13).

14.5 Conformance Fixtures

  • conformance/fixtures/phase2-cyclic-self-ref.json — store referencing itself; expects a CycleRef node and a finite payload.
  • conformance/fixtures/phase2-cyclic-mutual.json — two objects referencing each other; expects both directions resolved without infinite recursion.
  • conformance/fixtures/phase2-getter-side-effect.json — a getter incrementing a counter on access; asserts the counter is untouched after serialization (I13).
  • conformance/fixtures/phase2-node-cap-overflow.json — a 25,000-node flat array; expects truncation at the 20,000-node cap with TruncationMarker{reason:"node-cap"}.
  • conformance/fixtures/phase2-malformed-proxy-trap-throw.json — a Proxy whose get trap throws; expects the node marked opaque, not a serializer crash.

14.6 Pitfalls

  • Using a strong Map<object, NodeId> "temporarily for simplicity" — silently reintroduces I2 violations and is easy to forget to remove.
  • Detecting cycles only on plain-object identity while ignoring array/Map/Set containers, which are also legitimately cyclic in reactive stores.
  • Assuming Reflect.get never triggers a side effect — it does invoke the getter (that's the point); the re-entrancy guard must catch mutation attempts from within the getter, not the read itself.
  • Truncating "at random" once a limit is hit rather than deterministically — breadth-first vs. depth-first order matters for reproducible fixtures.

14.7 Performance Concerns

Cycle detection via WeakMap lookups adds a constant-factor overhead per visited node; profile against the p50/p95/p99 budget specifically, not aggregate throughput alone — p99 tail latency is what a developer notices as UI jank during a snapshot refresh.

14.8 Edge Cases

  • A cycle of length 1 (self-reference) versus length 1,000 (a long chain looping back) — both must resolve in comparable time, since cycle-detection cost is per-visit, not per-cycle-length.
  • A getter returning a different object identity on each call — the serializer cannot rely on structural equality across two reads of "the same" property; each read is authoritative for that walk only.
  • A WeakRef target collected by GC between snapshot construction and delta computation — the diff engine treats this as a removal, not an error.

14.9 Failure Analysis

The dominant Phase-2 failure class is a getter with an undocumented side effect (a lazy-initialization pattern) silently corrupting target state during inspection; detected via the getter_side_effect_suspected telemetry signal (I13) firing in the field; recovery is marking the offending path opaque via a RedactionRule-adjacent allow-list override, tracked as an FM-class incident (§25).

14.10 Operational Notes

The node-count and byte-cap constants (§4) are configuration, not code; an operator attaching to an unusually large app can raise the cap locally, trading serialize latency for completeness, with the tradeoff surfaced in the UI as a warning banner (P11).

15. Phase 3 — Transport + Reconnect Across Hot Reload

15.1 Objectives

  • Implement @lrsi/transport: WebSocket (RFC 6455) framing, CBOR (RFC 8949) encoding, per the §11 TransportMessage union.
  • Implement the reconnect/resume handshake (ADR-09) surviving a hot-reload disconnect without losing SessionId (I12).
  • Implement the session lifecycle state machine (§8.6) in SessionManager.

15.2 Detailed Implementation Steps

  1. Implement the wire codec: TransportMessage → CBOR bytes → WebSocket binary frame, and the inverse decode path, rejecting truncated frames per the §8.9 malformed-input example.
  2. Implement the bounded send-queue with drop-oldest-event backpressure (ADR-27, I14); verify enqueue never awaits inside the hook write path.
  3. Implement the session state machine (§8.6) exactly as tabulated, including every failure edge; add an illegal-transition guard raising lrsi.session.illegal_transition (I7).
  4. Implement the resumption token: issued on AttachAck, presented on ReconnectResume; validated for session identity and staleness window (ADR-09, I12).
  5. Simulate a hot-reload disconnect in a fixture harness (kill and restart the hook's WebSocket client mid-EventBatch) and verify resume within the §4 budget (≤ 2 s p95).
  6. Re-establish "enabled subscription" state on reconnect — the CDP lesson from ChromeDevTools/devtools-protocol (§5) — i.e. re-arm whatever was active pre-disconnect rather than assuming the backend remembers it for free.

15.3 Deliverable

A transport that survives repeated hot-reload cycles in a live development loop without the UI losing session continuity or double-counting events.

15.4 Acceptance Criteria

  • Reconnect-after-hot-reload p95 ≤ 2 s across 50 simulated reload cycles (conformance/fixtures/phase3-hot-reload-cycle.json).
  • Zero duplicate EventRecords observed at the UI after a reconnect, verified by eventId uniqueness assertion.
  • Illegal state transitions (e.g. Detached → Attached directly) rejected 100% of the time in session-state-machine.spec.ts.
  • Sustained bandwidth ≤ 2 Mbps and message rate ≤ 120 msg/s under the Phase-1 fixture's steady-state load (§4).

15.5 Conformance Fixtures

  • conformance/fixtures/phase3-hot-reload-cycle.json — 50 simulated disconnect/reconnect cycles; expects session continuity and the §4 latency budget.
  • conformance/fixtures/phase3-resume-token-expired.json — a resumption token presented past its staleness window; expects fallback to a fresh session, not a hang.
  • conformance/fixtures/phase3-malformed-truncated-frame.json — a CBOR frame truncated mid-message; expects a retransmit request, not a decode crash.
  • conformance/fixtures/phase3-illegal-transition.json — a direct Detached→Attached message; expects rejection and a forced Detached.

15.6 Pitfalls

  • Treating "reconnect" as "recreate the session" by default — the single biggest UX regression this phase exists to prevent (ADR-09).
  • Forgetting that a resumption token is a bearer credential across a reconnect and must never be logged or included in telemetry payloads.
  • Allowing the send-queue to grow unbounded "just during reconnect, temporarily" — reintroduces I14/ADR-27 violations exactly when the target is already stressed.
  • Assuming WebSocket message ordering is preserved across a reconnect — a new socket is a new ordering domain; the resume handshake must explicitly re-sequence, not assume continuity.

15.7 Performance Concerns

The reconnect handshake must not become a second bottleneck: token validation and re-arming subscriptions must complete within the ≤ 2 s budget even while the send-queue simultaneously replays buffered events from the outage window.

15.8 Edge Cases

  • Two rapid hot reloads in succession (before the first reconnect completes) — the second disconnect must not corrupt the first reconnect's in-flight token exchange.
  • A reconnect where the target process itself restarted (not just a module hot-reload) — the resumption token is necessarily invalid (new process, new LogicalClock origin) and must fall back to a fresh session, not a silent stale resume.
  • Backend restart while the target stays alive — the target's send-queue must buffer and retry rather than drop immediately.

15.9 Failure Analysis

The dominant Phase-3 failure mode is resumption-token validation racing a concurrent second disconnect, producing a false "invalid token" fallback more often than the true expiry case; detected via lrsi.transport.resume_success_rate dropping below a healthy baseline; recovery is serializing token validation per session rather than allowing concurrent validation attempts.

15.10 Operational Notes

lrsi.transport.resume_success_rate is the single most useful dashboard metric during active development (§26); a sustained drop indicates either a token-window misconfiguration or a genuine process-restart pattern in the target that should be investigated, not silenced.

17. Phase 5 — Reactive Dependency Graph

17.1 Objectives

  • Extend the Dependency Graph Tracker to capture fine-grained signal/effect/subscription edges (§8.3), beyond the coarse Phase-1 hook-dependency-array capture.
  • Ship a graph view in @lrsi/ui answering "what does this depend on" and "what depends on this" as structural traversals (P10), informed by Meyerovich & Bodik 2010 and the Carniato/Solid.js fine-grained-reactivity lineage (§5).
  • Extend @lrsi/adapter-react to model useEffect/useMemo dependency arrays as first-class DependencyEdges, not just re-render triggers.

17.2 Detailed Implementation Steps

  1. Emit DependencyEdge{kind:"reads"} whenever a hook or signal read is observed during a render/computation pass, and kind:"writes" on the corresponding update (§8.3).
  2. Emit DependencyEdge{kind:"subscribes"} when an effect registers against a signal/store, and kind:"triggers" when that registration causes a re-run, tagged with the triggering commit's LogicalClock per §8.2.
  3. Build the EffectRecord table (§11): dependsOn populated from the accumulated reads edges for that effect's last run.
  4. Implement graph-view rendering: a layered-DAG node/edge layout with a "trace to root" traversal (P10).
  5. Implement "why did this re-run": given a NodeId and a LogicalClock, walk backward along triggers edges to the originating writes edge — a direct structural answer to the Ko & Myers Whyline-class question (§5), applied here rather than via natural-language query.
  6. Guard the edge-tracking hot path against the §4 budget (≤ 50 ns per signal read) — this phase is the first to seriously stress that specific budget line.

17.3 Deliverable

A dependency graph view answering "why did this re-run" as a structural backward traversal, built on DependencyEdge/EffectRecord data captured with bounded per-read overhead.

17.4 Acceptance Criteria

  • Per-signal-read overhead ≤ 50 ns total (§4), measured via benchmarks/dependency-edge.bench.ts against an uninstrumented ~5 ns baseline.
  • "Why did this re-run" resolves to a correct originating writes edge in 100% of the phase5-causal-chain-* fixtures.
  • Graph view renders a 500-edge dependency graph in ≤ 100 ms.
  • EffectRecord.dependsOn matches the adapter's own internal dependency-array contents exactly, verified differentially (§28) against React DevTools' own hook inspection where available.

17.5 Conformance Fixtures

  • conformance/fixtures/phase5-causal-chain-single-hop.json — one write directly triggers one effect; expects a 1-edge backward trace.
  • conformance/fixtures/phase5-causal-chain-multi-hop.json — a write triggers an effect that writes a second signal triggering a second effect; expects a correctly ordered 2-hop trace.
  • conformance/fixtures/phase5-diamond-dependency.json — two effects both depending on one signal, feeding a third — expects both incoming edges represented, no edge lost to a naive tree assumption.
  • conformance/fixtures/phase5-malformed-disposed-effect-edge.json — an edge reported for an already-disposed effect; expects the edge rejected and logged, not silently attached.

17.6 Pitfalls

  • Modeling the dependency graph as a tree because the snapshot tree already exists — a real reactive graph has diamonds and must be modeled as a DAG from the start; retrofitting this after building tree-shaped storage is expensive.
  • Recording reads edges unconditionally on every render pass, including reads inside an already-memoized branch that didn't actually re-execute — inflates the edge count and corrupts causal traces.
  • Ignoring the overhead budget until "graph view looks done", then discovering the per-read cost is 10x over budget — must be measured from the first edge-emission commit, not retrofitted.
  • Treating EffectRecord.disposed as advisory — a disposed effect must never accept new edges (see the malformed-input fixture above); I6-class cleanup discipline applies here too.

17.7 Performance Concerns

This phase directly stresses the tightest budget line in §4 (≤ 50 ns per signal read); a single unnecessary allocation per read (e.g. constructing a new edge object even when the edge already exists) blows the budget at any nontrivial signal-read frequency — de-duplicate before allocating.

17.8 Edge Cases

  • A signal read inside a conditionally-executed branch that is sometimes skipped — the edge set for that effect must reflect only the branches actually taken on its last run, matching real fine-grained reactivity semantics (Carniato/Solid, §5), not a static over-approximation.
  • An effect that both reads and writes the same signal (a self-referential update pattern) — must not appear as an infinite triggers loop in the causal trace; the trace terminates at the first previously-visited edge, mirroring I3's cycle-safety at the graph level.
  • A dependency edge established during a render that is later discarded (an aborted render pass in a concurrent-rendering framework) — must not be committed to the graph.

17.9 Failure Analysis

The dominant Phase-5 failure mode is an edge leak from effects that never call their cleanup function, causing EffectRecord.dependsOn sets to grow unbounded over a long session; detected via a periodic sanity check comparing live effect count against the adapter's own bookkeeping; recovery is flagging the session Degraded and prompting a targeted heap inspection.

17.10 Operational Notes

The "why did this re-run" trace is the single most-demoed feature of this blueprint (§2); its correctness is verified continuously via the differential test against React DevTools' own hook inspection (§28), not just LRSI's own fixtures, since a subtle drift here is otherwise invisible until a user distrusts the answer.

18.1 Objectives

  • Implement @lrsi/eventlog's production RingBuffer<EventRecord> with the eviction policy locked in ADR-10.

  • Ship an event-log UI view correlating events against the tree and graph views by LogicalClock.

18.2 Detailed Implementation Steps

  1. Implement RingBuffer.push with drop-oldest-non-keyframe eviction (ADR-10), preserving periodic keyframe entries needed by the Phase-7 replay projector.
  2. Enforce byte-cap accounting via EventRecord.sizeBytes (§8.4), rejecting/truncating oversized payloadSummary fields before they enter the buffer, per I8.
  3. Implement the monotonic LogicalClock ordering check (I4) at the point of push; quarantine and flag Degraded on an out-of-order record rather than silently reordering.
  4. Wire W3C User Timing / Performance Timeline-style correlation (§5) between EventRecords and the browser's own performance marks, where available, as an optional enrichment only — never a dependency for core ordering, which stays on LogicalClock (P7/I4).
  5. Implement the event-log UI view: a scrolling, filterable list keyed by eventId (§8.4), with jump-to-node and jump-to-graph-edge affordances.
  6. Run the render-storm soak test (§28): a fixture app issuing 10,000 events/s for 60 seconds; verify the buffer stays within its byte cap and the drop rate is reported accurately.

18.3 Deliverable

A bounded, monotonically-ordered event log surviving a sustained render storm without unbounded memory growth, with a UI view correlating events to tree and graph state.

18.4 Acceptance Criteria

  • Ring buffer never exceeds 50,000 events or 8 MB (§4) under the render-storm soak fixture, verified continuously, not just at test end.
  • lrsi.eventlog.drop_rate accurately reflects the actual eviction count within 1% under the soak test.
  • Out-of-order LogicalClock values are quarantined 100% of the time in eventlog-ordering.spec.ts, never silently reordered.
  • Event-log UI view renders 1,000 visible events with jump-to-node navigation in ≤ 100 ms.

18.5 Conformance Fixtures

  • conformance/fixtures/phase6-render-storm-60s.json — 10,000 events/s for 60s; expects bounded memory and an accurate drop-rate report.
  • conformance/fixtures/phase6-out-of-order-clock.json — a deliberately shuffled event batch; expects quarantine and a Degraded flag.
  • conformance/fixtures/phase6-oversized-payload.json — an event whose payloadSummary exceeds the byte cap; expects truncation with a marker, not buffer corruption.
  • conformance/fixtures/phase6-keyframe-preservation.json — a storm that would otherwise evict a keyframe entry; expects the keyframe preserved per ADR-10, non-keyframe entries evicted first.

18.6 Pitfalls

  • Implementing eviction as strict FIFO without the keyframe-preserving exception — breaks Phase 7's replay projector, which depends on keyframes surviving eviction.
  • Computing sizeBytes after insertion rather than before — allows a single oversized event to transiently blow the byte cap before correction.
  • Treating the render-storm soak test as a "nice to have" perf test rather than a correctness test — I11 is a correctness invariant, not a performance target.
  • Correlating events to browser Performance Timeline marks as the primary ordering mechanism instead of LogicalClock — violates P7 the moment a non-browser (Node.js) target is attached.

18.7 Performance Concerns

RingBuffer.push must be O(1) amortized; any eviction strategy requiring an O(n) scan to find the next evictable non-keyframe entry will not survive the render-storm soak test's throughput requirement.

18.8 Edge Cases

  • A storm where every single event happens to be a keyframe (pathological adapter misconfiguration) — the keyframe-preservation exception must not degrade into "never evicts anything"; a hard byte-cap fallback (drop-oldest-keyframe-too) must exist as a last resort, itself telemetry-flagged as anomalous.
  • A single event whose declared sizeBytes is deliberately wrong (adversarial or buggy adapter) — the buffer must not trust the declared size blindly for critical accounting; a periodic real-size audit catches drift.
  • Session duration exceeding the 4-hour cap (§4) — the buffer transitions to snapshot-only mode per SessionManager, not an unbounded continuation.

18.9 Failure Analysis

The dominant Phase-6 failure mode is keyframe starvation under a storm skewed heavily toward keyframe-tagged events, degrading replay fidelity; detected via a keyframe-density telemetry gauge falling outside its expected band; recovery is the hard byte-cap fallback (§18.8) plus an operator alert to investigate the adapter's keyframe-tagging logic.

18.10 Operational Notes

lrsi.eventlog.bytes_used and lrsi.eventlog.drop_rate are the two metrics operators watch during a live debugging session under load; both are surfaced directly in the UI status bar, not just in telemetry, per P11 (degrade visibly).

19. Phase 7 — Time-Scrub Replay Projection

19.1 Objectives

  • Implement @lrsi/replay's keyframe + delta projector (ADR-11) satisfying the §4 seek-latency budget.
  • Ship the scrubber UI: seek to any point in the retained event/snapshot history without re-executing target-side code (I9).
  • Contrast explicitly against full deterministic record/replay (O'Callahan et al. 2017, Microsoft TTD) and pure-model replay (the Elm Architecture) per §5/§36.

19.2 Detailed Implementation Steps

  1. Define the keyframe interval K (derived in §34) balancing snapshot-storage cost against seek latency; store keyframes as full StateSnapshots, deltas as DeltaOp[] sequences between them.
  2. Implement ScrubCursor seek: locate the nearest keyframe at or before the target LogicalClock, then apply deltas forward to the exact target point (§8.7).
  3. Enforce I9 structurally: @lrsi/replay has no reference to the live target connection; it operates purely over retained StateSnapshot/DeltaOp data, making target-side re-execution architecturally impossible, not just policy-forbidden.
  4. Implement the scrubber UI (§8.7): a timeline control with keyframe tick marks, hover preview, and play/pause/step controls at 1x/2x/4x speed.
  5. Implement replay-determinism verification: replay the same cursor position twice and assert byte-identical projected state (§28 property test).
  6. Handle the Phase-6 keyframe-eviction interaction (ADR-10): a scrub target whose keyframe has been evicted (session exceeded retention) must degrade gracefully to "earliest available" rather than erroring.

19.3 Deliverable

A scrubber that seeks to any retained point in session history within the §4 latency budget, provably without invoking any target-side code.

19.4 Acceptance Criteria

  • Seek latency within the last 5 keyframes, p95 ≤ 120 ms (§4), measured via benchmarks/replay.bench.ts.
  • Replay-determinism property test: 100 repeated seeks to the same cursor produce byte-identical StateSnapshot projections.
  • Zero onEvent/hook invocations recorded during any replay operation (lrsi.replay.side_effect_attempts === 0, I9).
  • Seeking to an evicted keyframe degrades to "earliest available" with an explicit UI notice, never an error dialog.

19.5 Conformance Fixtures

  • conformance/fixtures/phase7-seek-recent-keyframe.json — seek within the last 5 keyframes; expects the §4 latency budget met.
  • conformance/fixtures/phase7-seek-evicted-keyframe.json — seek to a point whose keyframe was evicted; expects graceful "earliest available" fallback.
  • conformance/fixtures/phase7-replay-determinism.json — 100 repeated seeks; expects byte-identical projections.
  • conformance/fixtures/phase7-malformed-out-of-range-cursor.json — a ScrubCursor referencing a clock value beyond the current session's range; expects a clamped, in-range result, not an out-of-bounds error.

19.6 Pitfalls

  • Implementing "replay" as literally reconnecting to the target and asking it to reproduce state — exactly the I9 violation this phase exists to prevent; replay must be a pure projection over retained data.
  • Choosing K (the keyframe interval) purely to minimize storage without checking the resulting seek latency against the §4 budget — the two are in direct tension and must be tuned together (§34).
  • Assuming deltas are invertible by default — most adapters do not declare reversible deltas; backward seeks must replay forward from a keyframe unless invertibility is explicitly declared.
  • Allowing the scrubber UI to trigger a live query (@lrsi/query) against the current live state while displaying a historical cursor position — silently conflates "then" and "now"; the UI is either live-following or scrub-mode, never both against different data sources at once.

19.7 Performance Concerns

Seek latency is dominated by delta-application count since the last keyframe; K must be tuned so the worst-case delta-application chain (K−1 deltas) stays within the ≤ 120 ms p95 budget even for a snapshot near the §4 node-count ceiling (20,000 nodes).

19.8 Edge Cases

  • A seek target that falls exactly on a keyframe boundary — must apply zero deltas, not off-by-one apply the adjacent keyframe's first delta.
  • A session with irregular keyframe spacing (e.g. because §18.8's hard byte-cap fallback evicted an expected keyframe) — the seek algorithm must locate the actual nearest keyframe, not assume uniform spacing.
  • Rapid successive scrub operations (a user dragging the scrubber quickly) — must debounce/cancel superseded seek computations rather than completing every intermediate seek in order.

19.9 Failure Analysis

The dominant Phase-7 failure mode is delta-application drift: a delta sequence that, when replayed, produces a projection subtly different from what the live snapshot actually was at that point (e.g. a missed edge case in diff construction); detected via the replay-determinism property test combined with periodic live/replay cross-checks at the current cursor; recovery is treating any detected drift as a release-blocking correctness bug, not a cosmetic one, since it undermines the entire time-travel premise.

19.10 Operational Notes

Keyframe interval K is a tunable operational parameter (§26), not a hardcoded constant; operators debugging an unusually large app may need a denser keyframe schedule at the cost of storage, with the tradeoff visible in the same UI warning-banner pattern used elsewhere (P11).

  • Matched-pair enforcement: an orphaned pending task past the 4-hour session cap is flagged, not silently dropped nor left pending forever.
  • Opt-in overhead, when enabled, stays within a separately-declared budget of ≤ 5% additional CPU (distinct from the §4 baseline 2%), explicitly labeled as an opt-in cost in the UI.
  • Async-task Gantt view renders 200 concurrent in-flight tasks in ≤ 100 ms.

20.5 Conformance Fixtures

  • conformance/fixtures/phase8-causal-async-fetch.json — a signal write dispatches a fetch; expects causedBy correctly set.
  • conformance/fixtures/phase8-causal-async-chained.json — a fetch's .then dispatches a second async task; expects the causal chain preserved across the boundary.
  • conformance/fixtures/phase8-orphaned-pending-task.json — a task that never settles within session duration; expects the flagged-orphan behavior, not silent loss.
  • conformance/fixtures/phase8-malformed-mismatched-end.json — an onAsyncTaskEnd for a taskId with no matching onAsyncTaskStart; expects rejection and a logged anomaly, not a crash.

20.6 Pitfalls

  • Enabling async tracking by default "since it's useful" — contradicts the documented opt-in overhead risk (§5) and the general P4 discipline.
  • Attributing causedBy via a best-guess heuristic (e.g. "most recent write") instead of actual causal-context capture — produces plausible-looking but wrong answers, worse than no answer.
  • Treating every microtask as a trackable "async task" — explodes cardinality past anything the UI or ring buffer (§4/§18) can usefully display; only boundary-crossing work (fetch, timers, explicit async functions) should be tracked, not every promise tick.
  • Assuming async tasks always settle — an abandoned fetch (component unmounted mid-request) is common and must resolve to a defined status, not remain pending indefinitely without a flag.

20.7 Performance Concerns

The opt-in overhead budget (≤ 5% additional CPU) must be measured on a task-dispatch-heavy fixture, not an idle one — async_hooks-class instrumentation cost scales with dispatch rate, not wall-clock session length.

20.8 Edge Cases

  • A task that starts before attach and settles after — its causedBy is necessarily unknown (no context was captured pre-attach); must resolve to null, not a fabricated guess.
  • Two async tasks racing to settle in the same microtask flush — ordering by LogicalClock must remain stable and match the true settlement order, not queue-iteration order.
  • A worker-thread-originated task (out of scope for causal correlation per the Phase-8 PhaseDeferred note in §1/§37) — must be visibly marked "cross-runtime, not correlated" rather than silently omitted.

20.9 Failure Analysis

The dominant Phase-8 failure mode is causal misattribution under high dispatch concurrency (two overlapping writes racing to be recorded as the "active" context when a task dispatches); detected via a differential check against a fixture with a known-unique dispatch context per task; recovery is tightening the context-capture window to be synchronous with dispatch, never inferred after the fact.

20.10 Operational Notes

The opt-in flag and its declared overhead cost are surfaced in the UI's session-info panel at all times when active, per P11 — an operator must never discover async tracking was silently taxing their app.

21. Phase 9 — Query Engine + Saved Views

21.1 Objectives

  • Implement @lrsi/query's QuerySpec compiler/evaluator (ADR-12) over nodes, edges, and events.
  • Ship saved views: named, persisted QuerySpecs recallable across a session (cross-session persistence is PhaseDeferred, §37).
  • Directly answer the Sillito et al. FSE 2006 question taxonomy (§5) — structure, relationship, and history questions — as first-class query shapes.

21.2 Detailed Implementation Steps

  1. Implement the QueryPredicate evaluator (§11): pathMatches, typeIs, and, or, compiled to a direct tree/graph walk, never a string-search fallback (P10).
  2. Extend QuerySpec.select (§11) to cover nodes, edges, and events uniformly, so one query shape answers "what nodes", "what depends on what", and "what happened" without three separate UIs.
  3. Implement the SavedViewSync message (§8.5): persist a named QuerySpec to the backend's session-scoped store; recall by name.
  4. Implement a query builder UI: a structured (not free-text) form driven by the QueryPredicate union, preventing the string-grep fallback P10 forbids.
  5. Wire the "why did this re-run" trace (Phase 5) and the causal async chain (Phase 8) as pre-built saved-view templates (ADR-12) shipped with the product, demonstrating the query engine is the same substrate behind both.
  6. Benchmark query evaluation against the §4 node/edge/event counts to ensure interactive-feeling latency (target: ≤ 16 ms for the default 5,000-node/500-edge/50,000-event ceilings).

21.3 Deliverable

A structured query engine and saved-view mechanism answering structure/relationship/history questions (§5) as compiled predicate evaluations, with the Phase 5/8 causal traces re-expressed as saved-view templates.

21.4 Acceptance Criteria

  • Query evaluation over the full §4 ceiling (5,000 nodes / 500 edges / 50,000 events) completes in ≤ 16 ms.
  • Saved views persist and recall correctly across a Reconnecting→Attached cycle within the same SessionId (I12-consistent).
  • Zero string-search fallback paths exist in @lrsi/query — verified by a lint rule forbidding .includes/.match against serialized JSON blobs in that package.
  • The "why did this re-run" and causal-async saved-view templates produce results identical to the Phase 5/8 bespoke implementations, verified differentially.

21.5 Conformance Fixtures

  • conformance/fixtures/phase9-query-path-match.json — a pathMatches query against a known fixture tree; expects the exact matching node set.
  • conformance/fixtures/phase9-query-and-or-compound.json — a compound and/or predicate; expects correct boolean combination.
  • conformance/fixtures/phase9-saved-view-recall.json — save, disconnect/reconnect, recall; expects identical QuerySpec and identical result set.
  • conformance/fixtures/phase9-malformed-empty-predicate.json — a QuerySpec with an empty and: []; expects a defined result (vacuous true) rather than undefined behavior.

21.6 Pitfalls

  • Allowing a "quick" string-search shortcut into the query evaluator "just for this one query type" — the exact P10 regression this phase exists to prevent; once one string-search path exists, more accrete.
  • Building saved views as a UI-only feature (localStorage) instead of a backend-persisted, session-scoped construct — breaks recall across a reconnect (I12) and diverges from the wire-protocol model (P5).
  • Treating and: [] / or: [] as an error instead of a defined vacuous case — undefined edge-case behavior in a query language is a correctness bug waiting to surface in a saved view.
  • Letting the query builder UI expose the full QueryPredicate union's power in a way that lets a user construct a predicate more expensive than the §4 ceiling was benchmarked against — needs a compiled-cost estimate, not just a raw pass-through.

21.7 Performance Concerns

Predicate compilation (not just evaluation) must itself be cheap — a query built once and evaluated on every incoming SnapshotDelta (a "live saved view") amortizes compilation cost across many evaluations, so lazy per-evaluation compilation would violate the 16 ms target under live-updating saved views.

21.8 Edge Cases

  • A saved view referencing a typeTag value that no longer exists in a later schema version (ADR-25/§27 compatibility concern) — must degrade to "no matches" with a version-mismatch notice, not a crash.
  • A query against events scoped to a time range that spans an eviction boundary (§18) — must return the available subset with an explicit "partial — some events evicted" marker, never silently present a complete-looking but truncated result.
  • Two saved views with the same user-chosen name — must be disambiguated (e.g. by id, with name as a display label only), never silently overwritten.

21.9 Failure Analysis

The dominant Phase-9 failure mode is a saved view silently returning stale results after a schema evolution (§27) changes what a typeTag or path shape means; detected via a saved-view schema-version tag mismatch check run at recall time; recovery is surfacing the mismatch explicitly and offering a re-save rather than silently returning a wrong or empty result.

21.10 Operational Notes

The built-in saved-view templates (why-did-this-re-run, causal-async-chain) are versioned alongside the wire protocol (§27), since they are effectively part of the product surface, not just examples.

22. Phase 10 — Remote-Target Bridge + Redaction

22.1 Objectives

  • Implement @lrsi/bridge: a relay process enabling attach to a Node.js or remote-browser target across a network boundary (ADR-15).
  • Implement the backend-side RedactionRule enforcement point (ADR-16) as the mandatory pre-transport filter for any remote attach.
  • Address T1/T2-class threats (§24) that only become real once a target crosses a network trust boundary.

22.2 Detailed Implementation Steps

  1. Implement @lrsi/bridge as a mutual-TLS relay: the remote target's hooks connect outbound to the bridge (never an inbound-listening inspector port, per ADR-15/T1), and the local backend connects to the bridge as a separate authenticated leg.
  2. Enforce RedactionRule application at the backend before any Snapshot/EventBatch crosses from bridge to local UI (I5), with a default rule set matching the secret-heuristic (password|token|secret|apiKey-class path patterns).
  3. Implement RedactionPolicyUpdate handling (I5): an operator can extend the default rules; changes take effect on the next serialized payload, never retroactively "unredacting" already-sent data.
  4. Implement bridge authentication and session binding (ADR-15): a remote attach requires an explicit, out-of-band-provisioned credential — no anonymous remote attach path exists.
  5. Implement the T4 (denial-of-service by snapshot amplification) mitigation: a remote target's declared node/event counts are rate- and size-capped independently of the local-attach §4 ceilings, since a compromised or buggy remote target is a more adversarial position than a local one.
  6. Run a redaction-throughput benchmark against the §4 target (≥ 50,000 fields/s) using the default rule set on the 20,000-node ceiling fixture.

22.3 Deliverable

A remote-target bridge that never exposes an inbound inspector port, enforces redaction before any payload leaves the bridge, and authenticates every remote attach.

22.4 Acceptance Criteria

  • Zero inbound listening ports opened by @lrsi/bridge on the target side — verified by a network-scan conformance check (phase10-no-inbound-port.json).
  • Redaction throughput ≥ 50,000 fields/s (§4) on the 20,000-node ceiling fixture with the default rule set.
  • 100% of default-rule-matching paths (password, token, secret, apiKey) are absent from captured wire traffic in phase10-redaction-wire-capture.json.
  • An unauthenticated remote attach attempt is rejected 100% of the time in phase10-unauthenticated-attach.json.

22.5 Conformance Fixtures

  • conformance/fixtures/phase10-no-inbound-port.json — network scan of a running bridge-attached target; expects zero inbound listening ports.
  • conformance/fixtures/phase10-redaction-wire-capture.json — a fixture store containing secret-heuristic-matching fields; expects zero occurrences on the wire.
  • conformance/fixtures/phase10-unauthenticated-attach.json — an attach attempt without a valid credential; expects rejection, not a degraded-but-connected state.
  • conformance/fixtures/phase10-malformed-oversized-remote-snapshot.json — a remote target declaring a node count far beyond the independent remote-target cap; expects rejection/ truncation, not amplification passed through to the local UI.

22.6 Pitfalls

  • Allowing the bridge to listen for inbound connections "for simplicity in early testing" and never removing it before a remote-capable release — precisely the T1 threat this phase exists to close.
  • Implementing redaction only in the UI layer for the remote-bridge case "since it's already implemented there" — the trust boundary for a remote target is materially different (network, not process) and requires the backend-side enforcement point, never a UI-only check (I5, ADR-16).
  • Treating the remote target's self-reported node/event counts as trustworthy for the local §4 ceilings — a compromised or buggy remote target can amplify past the local budget unless independently capped (T4).
  • Reusing the local-session resumption-token model unmodified for the remote case — ADR-09's local reconnect model assumes a trusted token; the remote bridge needs its own credential model, not a copy-paste.

22.7 Performance Concerns

Mutual-TLS handshake and redaction-filter application both add latency to the remote attach path; the RTO budget (§4, ≤ 5 s) must account for both, not just the transport-level reconnect time already budgeted in Phase 3.

22.8 Edge Cases

  • A remote target on a high-latency network link (e.g. a distant data-center) — the reconnect/resume budget (§4) may need a remote-specific relaxation, explicitly declared, not silently missed and reported as a false failure.
  • A redaction rule added mid-session that would have redacted a field already sent in an earlier Snapshot — must not attempt retroactive redaction of already-transmitted data (I5 governs future payloads only); the UI surfaces this limitation explicitly.
  • A bridge process restart while both legs (target and backend) are connected — both legs must independently detect the drop and re-authenticate, not assume the other leg will re-establish the pairing for them.

22.9 Failure Analysis

The dominant Phase-10 failure mode is a redaction-rule gap discovered after the fact (a secret shape not matching any default heuristic); detected via an operator-reported incident or a periodic red-team-style scan of a fixture using known secret shapes; recovery is a rule-set patch release plus an audit of any prior session's transmitted data for exposure, tracked as a T2/FM-class incident (§24/§25).

22.10 Operational Notes

Remote-bridge deployments are the one surface with a named runbook (docs/runbooks/remote-bridge-incident.md, §26) since a redaction gap here is a genuine security incident, not merely a bug, and needs an incident-response path distinct from ordinary defect triage.

23. Phase 11 — Conformance Suite + Perf Hardening

23.1 Objectives

  • Complete @lrsi/conformance: the full fixture corpus spanning Phases 0–10, run as a single CI-gated suite.
  • Verify every §4 budget line under the actual conformance corpus, not synthetic micro-benchmarks alone.
  • Complete the ADR-17 production-build stripping proof and lock 1.0 compatibility guarantees (§27).

23.2 Detailed Implementation Steps

  1. Assemble the full conformance corpus (ADR-21): every phase0–phase10 fixture file referenced in this document's N.5 sections, plus cross-phase integration fixtures (e.g. a hot-reload cycle occurring mid-time-scrub-replay).
  2. Wire the perf-regression gate: any §4 budget line regressing beyond its declared threshold across two consecutive CI runs blocks merge (ADR-22-adjacent discipline).
  3. Complete the ADR-17 bundle-diff proof: a production build of a fixture app instrumented with @lrsi/hooks must byte-for-byte match the same build without LRSI present, modulo the DCE guard itself (I1 verified mechanically, not by inspection).
  4. Run the full fuzz corpus (ADR-22) against the wire decoder and SerializedValue deserializer for a fixed CI time budget per run, tracking crash/hang discoveries as release blockers.
  5. Run the differential test suite (§28) against React DevTools' hook inspection and, where feasible, Redux DevTools' action log, on the same fixture apps, to catch semantic drift accumulated across Phases 1–9.
  6. Execute the full §7 invariant-exercising methodology (render storm + hot-reload-mid-snapshot + cyclic store + side-effecting getter) as a named CI job (conformance/runner/release-gate.ts) that must pass before any 1.0-track release tag.

23.3 Deliverable

A single CI-gated conformance suite covering every phase's fixtures, every §4 performance budget, the ADR-17 stripping proof, and the full §7 invariant-exercising methodology, as the release gate for 1.0.

23.4 Acceptance Criteria

  • 100% of named fixtures across phase0–phase10 (this document's N.5 sections) pass in the release-gate CI job.
  • Zero §4 budget-line regressions beyond declared threshold across two consecutive runs.
  • ADR-17 bundle-diff proof passes: production build with LRSI present is byte-identical to without, modulo the DCE guard.
  • Fuzz corpus runs for ≥ 30 CPU-minutes per CI run with zero new crash/hang discoveries before a 1.0 tag.

23.5 Conformance Fixtures

  • conformance/fixtures/phase11-cross-phase-hotreload-during-replay.json — a hot reload occurring while a time-scrub replay is in progress; expects the replay to complete against its already-retained data undisturbed (I9 holds independent of live-connection state).
  • conformance/fixtures/phase11-differential-react-devtools.json — a fixture app inspected simultaneously by LRSI and React DevTools; expects matching hook-state reports.
  • conformance/fixtures/phase11-bundle-diff-proof.json — paired production builds (with/without LRSI); expects byte-identical output modulo the DCE guard.
  • conformance/fixtures/phase11-fuzz-regression-corpus.json — a curated corpus of previously-discovered fuzz-crash inputs; expects all now pass (regression-lock).

23.6 Pitfalls

  • Treating the conformance suite as "done" once it's green once, rather than as a continuously-enforced release gate — a suite that isn't CI-blocking degrades to documentation within a few releases.
  • Fuzzing only the wire decoder and skipping the SerializedValue deserializer (or vice versa) — ADR-22 names both explicitly because they are independently reachable from an adversarial input (a malicious remote target, per Phase 10).
  • Declaring the ADR-17 stripping proof "verified" via manual bundle inspection instead of an automated byte-diff — manual inspection does not scale and drifts silently as bundler config evolves.
  • Running the differential tests against a single React version — framework-internals drift (Phase 1's dominant failure mode) means the differential corpus must span the supported version range, not just the latest.

23.7 Performance Concerns

The full conformance suite's own runtime must itself stay within a CI-practical budget (target: under 15 minutes wall-clock for the fast lane, fuzzing run separately/nightly at the 30-CPU-minute budget) or it will be disabled under release pressure — a release gate too slow to run gets bypassed, which is worse than no gate.

23.8 Edge Cases

  • A fixture that passes in isolation but fails only in the full cross-phase integration run (e.g. an interaction between Phase 6 eviction and Phase 9 saved-view recall) — exactly why §23.2 step 1 explicitly calls for cross-phase fixtures, not just per-phase fixtures re-run together.
  • A flaky fixture (nondeterministic timing-dependent failure) — must be quarantined and root-caused, never silenced with a retry-until-green loop, which would mask a real I4/I9-class ordering bug.
  • A perf-regression gate false-positive caused by CI runner variance rather than a real regression — mitigated by running each benchmark multiple times and gating on a statistical threshold, not a single sample.

23.9 Failure Analysis

The dominant Phase-11 failure mode is a cross-phase interaction bug invisible to any single phase's fixture set (e.g. redaction rules from Phase 10 not applying correctly to saved-view results from Phase 9); detected only by the explicit cross-phase integration fixtures introduced in this phase; recovery is treating any such discovery as evidence the per-phase fixture corpus was incomplete, and adding a permanent regression fixture, not just a one-off patch.

23.10 Operational Notes

Post-1.0, this suite becomes the compatibility gate referenced throughout §27: no wire-protocol or hook-contract change ships without the full conformance suite passing against both the current and previous supported major version's fixtures.

Incident response: a redaction gap (FM-8) or a realized T-class threat triggers the security incident path (docs/runbooks/security-incident.md), distinct from ordinary defect triage (docs/runbooks/defect-triage.md).

Named runbooks (docs/runbooks/): remote-bridge-incident.md (§22.10), security-incident.md, defect-triage.md, perf-regression.md, replay-drift.md (FM-9).

Backup/restore: session state itself is not backed up — ephemeral by design (P2); the conformance fixture corpus and the ADR/threat-model documentation are the durable artifacts, protected by the repository's own remote redundancy.

Deployment topology: a local-loopback backend for the dev-dependency model; a single @lrsi/bridge instance per remote target for Phase 10, never multi-tenant across targets, which bounds the T7/T8 blast radius.

Canary/rollback/migration: a new @lrsi/hooks version is canaried against the full conformance fixture corpus before publish; a wire-protocol version bump follows the §27 capability-negotiation path so an old UI client degrades gracefully against a new backend rather than failing hard.

27. Compatibility & Versioning

Wire-protocol versioning and capability negotiation. Hello.protocolVersion is negotiated at connect time; a major-version mismatch between UI and backend rejects with PROTOCOL_MISMATCH rather than attempting a best-effort connection — the LSP/DAP capability-negotiation precedent (§5). Hello.capabilities lists optional features (async-task-tracking, remote-bridge-support) so peers on the same major version can still differ on optional feature availability.

Snapshot schema evolution. StateSnapshot.ussVersion is independent of the wire-protocol version. Additive fields on SnapshotNodeRecord are backward-compatible; removing or repurposing a field is a major bump requiring the dual-version support window below.

Instrumentation-hook API stability across runtime versions. InstrumentationHooks (§11) is stable across a major version; a framework-internal breaking change (e.g. a React internal restructuring) is absorbed by the adapter's own version-dispatch table (§13.9), never by breaking the hook contract itself.

Extension↔backend compatibility. The optional browser-extension shell (ADR-14) negotiates its own minimal capability set against the backend independently of the full UI client, since it ships on the browser's own update cadence, not the project's release cadence.

Migration. A major wire-protocol or schema bump ships with both the new and immediately-prior major version supported simultaneously for at least one full minor-release cycle before the prior version is dropped.

Deprecation. A deprecated message type or field is recorded in docs/adr/ and continues to be accepted (not just emitted) for the duration of the compatibility window.

SemVer. Patch = fixes with no schema/protocol change. Minor = additive, backward-compatible field/message additions. Major = any breaking wire-protocol, schema, or hook-contract change.

Rolling-upgrade guarantees. A backend can be upgraded independently of an already-attached UI client mid-session only within the same major version; a major-version backend upgrade forces a fresh attach, never a silent mid-session renegotiation.

28. Testing & Verification Strategy

Unit. Per-package Vitest suites (ADR-21), ≥ 80% line coverage on @lrsi/serializer, @lrsi/eventlog, and @lrsi/query.

Integration. The @lrsi/conformance runner drives real fixture apps end-to-end through attach→snapshot→query→detach.

Property. Serialize→deserialize→re-serialize is stable (I3, I10; phase2-* fixtures). Cyclic graphs always terminate (I3; phase2-cyclic-*). Snapshots hold no strong references, verified via a weak-ref/GC-pressure test (I2; the Phase-2 heap-snapshot diff).

Differential. Against React DevTools' own hook-inspection output on a fixture app (I13; phase5/phase11 differential fixtures) — any drift is a Phase-11 release blocker (§23.9).

Fuzzing. The snapshot deserializer and the wire decoder are the primary targets (ADR-22; I3, I13, T5), run nightly at a 30-CPU-minute budget (§23.7), regression-locked via phase11-fuzz-regression-corpus.json.

Chaos. Simulated backend crash mid-session (RTO target, §4/§26); simulated bridge-leg drop (FM-11).

Deterministic replay. The replay-determinism property test (I9; phase7-replay-determinism.json) runs on every CI pass, not just at release time.

Soak. The render-storm soak test (I11; phase6-render-storm-60s.json) runs nightly, not just once per phase.

Fault injection. Transport drop mid-message (I12, I4; phase3-hot-reload-cycle.json); hot reload mid-snapshot (§8.10; phase11-cross-phase-hotreload-during-replay.json).

Conformance vectors for third-party runtime adapters. The adapter-contract test suite (§13.2 step 1) is published as a reusable conformance package so a future non-React adapter (deferred, §37) can be verified against the same InstrumentationHooks ordering guarantees without bespoke test-writing.

Perf-regression gating. The §23.2 step 2 gate, enforced in CI, is the mechanism keeping every §4/§30 budget line honest release over release.

29. Build & Release Engineering

Reproducible builds. Deterministic esbuild output (ADR-26), pinned lockfile, no embedded build timestamps; a rebuild of the same commit produces a byte-identical artifact, verified in CI.

Artifact signing. Published npm packages carry provenance attestation; the standalone bridge binary is code-signed per target platform.

SBOM. A software bill of materials is generated per release and published alongside the release artifact.

Release channels. latest (stable, SemVer-tagged), next (pre-release, changesets-driven), and canary (built from every merge to main, for internal dogfooding per P14) ahead of any tagged release.

CI/CD topology. GitHub Actions matrix (ADR-23): lint → typecheck → unit → conformance → perf-gate → (on tag) build → sign → publish.

Version stamping. Every artifact embeds its git commit SHA and the wire-protocol/schema versions it implements, queryable at runtime for support and debugging.

Provenance/attestation. Build provenance (workflow run, commit, runner) is attached to every published package so a supply-chain audit can trace an artifact back to reviewed source.

Dependency auditing. Automated scanning (ADR-23) on every dependency bump; a flagged vulnerability blocks merge until triaged.

Extension-store publishing. The optional browser-extension shell (ADR-14) is published through the Chrome Web Store / Firefox Add-ons review pipelines independently of the npm release cadence.

Production build proves instrumentation was stripped. The ADR-17 bundle-diff proof (§23.2 step 3) is re-run as part of the release gate itself — a release cannot publish without this proof passing.

31. Scalability Analysis

What stays constant. Per-node serialize overhead (O(1) marginal per node given the WeakMap cycle check); per-message transport framing overhead.

What grows. Total serialize latency O(nodes) up to the truncation cap; event-log memory O(events) up to the ring-buffer cap; dependency-graph memory O(edges), currently uncapped at 1.0 scope.

Named bottlenecks, in order. (1) Dependency-graph edge count — unlike the event log's ring buffer, no eviction policy exists yet, making it the first structure to grow unbounded in a very long session. (2) Query evaluation's lack of an index — every query is a full walk, fine at the §4 ceiling, a real bottleneck beyond it. (3) Serialize latency at the node-count ceiling, since truncation is a hard cliff, not a graceful degradation curve.

Scaling strategies. Raise the node/event/edge caps deliberately, with the operator-visible cost tradeoff (P11), rather than silently. A future indexed query engine would address bottleneck 2 without a schema change, since QuerySpec is already structurally query-planner-friendly (ADR-12 rationale).

Coordination overhead. None within a single session (single-target, single-backend model); the remote bridge (Phase 10) introduces the only cross-process coordination, bounded to two legs (target↔bridge, bridge↔backend), never a distributed-consensus problem.

Practical ceiling and the levers beyond it. The §4 node/event/edge ceilings as configured; beyond them, serialize latency and query evaluation both degrade in ways that stay visible (P11) but degrade nonetheless — the lever beyond the ceiling is architectural (an indexed query engine, a graph-eviction policy), not a config bump.

32. Mental Models & First Principles

MM1 — An inspector is a serializer with a scheduling problem. The hard part is not reading state but reading it without becoming part of it. Predicts overhead budgets dominate the design more than feature completeness. Without it: unbounded instrumentation cost creeps into the target's own timing behavior. Resolved in §4 and §14 (I13).

MM2 — A snapshot is a lossy compression of a live heap, and the loss must be declared, not discovered. Predicts every truncation needs a marker. Without it: a developer trusts a truncated view as complete and misdiagnoses a bug. Resolved in §8.1 (P3, I10).

MM3 — Causality needs its own clock, because wall time lies the moment two processes are involved. Predicts any cross-process feature needs LogicalClock discipline from day one. Without it: reordered events under clock skew produce an impossible-looking causal trace. Resolved in §15 and §22 (P7, I4).

MM4 — A cycle is not a bug in the data, it's a bug in your assumption that data is a tree. Predicts any tree-first serializer/graph model needs an expensive retrofit. Without it: a crash or infinite loop the first time a real reactive store is inspected. Resolved in §14 and §17 (I3).

MM5 — Reconnection is a protocol, not an event handler. Predicts that treating "the socket reconnected" as sufficient will silently break session continuity. Without it: duplicate or missing events after every hot reload. Resolved in §15 (I12, ADR-09).

MM6 — Query power and query cost are the same knob. Expose one without bounding the other and you've built a denial-of-service generator, not a feature. Predicts any sufficiently expressive query language needs an explicit cost model before it ships. Without it: a saved view silently hangs the backend. Resolved in §21 (T12, FM-10).

MM7 — Time travel over an impure system is a projection over recorded history, not a rewind of the system itself. Predicts any live-target callback from the replay path is architecturally wrong, not just risky. Without it: replay accidentally re-triggers real side effects. Resolved in §19 and §36 (I9).

MM8 — Redaction is a property of the pipe, not the display. Predicts any redaction implemented downstream of the trust boundary is a compliance liability waiting to be discovered. Without it: a secret "not shown in the UI" sitting in a network capture. Resolved in §22 (P9, I5).

MM9 — Every buffer is a promise about memory, and an undocumented eviction policy is a broken promise waiting for a demo. Predicts any new stateful buffer added later must declare its eviction policy at the same commit that introduces it. Without it: a slow memory leak that only surfaces after hours of live use, exactly when a demo or incident is happening. Resolved in §18 and §31 (P2).

React DevTools chose a single-global-hook renderer-registration model, winning at zero-setup convenience for the common case of one React root, but losing the moment two renderer instances or a non-DevTools-aware embed exist — LRSI's rejection of that coupling (ADR-04) buys multi-tool coexistence at the cost of a slightly heavier detection step.

Vue DevTools chose a plugin-registration API that decouples the UI from Vue's own reactivity-proxy internals more than React DevTools decouples from fiber internals, winning wherever the reactivity implementation itself changes across versions — the niche is version resilience within one framework, not cross-framework generality.

Redux DevTools chose to only ever inspect state reachable through a pure-reducer action log, winning completely at deterministic time-travel because the substrate makes it trivially safe — the niche is any architecture that is already Redux-shaped; it cannot generalize to arbitrary mutable reactive stores, the gap LRSI's keyframe+delta model (ADR-11) exists to fill.

Chrome DevTools Protocol / V8 Inspector chose to live inside the engine itself rather than the framework layer, winning at true remote-target support and engine-level truth that no framework-level tool can match — the niche is anything below the framework, precisely why LRSI delegates to it (§1 boundaries) rather than reimplementing it.

rr / Pernosco chose full deterministic OS-level record/replay, winning at total fidelity — literally reversible execution — at the cost of an overhead profile and platform coupling (ptrace, kernel support) that cannot run inside a JS realm being inspected from outside; the niche is a fully-controlled native process where recording cost is acceptable, which motivated LRSI's rejection of this approach for its own time-travel design (ADR-11, §36).

34. Back-of-Envelope Capacity Model

  1. Snapshot payload bytes. 5,000 nodes (§4 latency-budget reference size) × 6 avg fields/node × 24 avg bytes/field (CBOR-encoded) = 5,000 × 6 × 24 = 720,000 bytes ≈ 703 KB per keyframe — the number the p50/p95/p99 serialize-latency budget (§4) is benchmarked against. At the 20,000-node truncation cap: 20,000 × 6 × 24 = 2,880,000 bytes ≈ 2.75 MB, the worst case before TruncationMarker intervenes.

  2. Transport bandwidth. Steady state: one delta message every 16 ms (60/s) averaging 2 KB = 60 × 2 KB = 120 KB/s = 0.96 Mbps — comfortably under the 2 Mbps sustained cap (§4), leaving headroom for periodic full keyframes (~703 KB every K commits, amortized).

  3. Ring-buffer memory. 50,000 events (§4 capacity) × 160 bytes/event (§4 average) = 8,000,000 bytes ≈ 7.63 MiB — consistent with the declared 8 MB byte cap (§4); the capacity and byte-cap numbers were chosen to match at this average event size.

  4. Time-scrub seek cost. Keyframe interval K commits, each delta apply ≈ 0.1 ms, worst case K−1 deltas applied = (K−1) × 0.1 ms. For the ≤ 120 ms p95 budget (§4) to hold, K−1 ≤ 1,200, i.e. K ≤ ~1,200 at this assumption; the reference implementation (§19.2) uses K = 200, giving a worst-case seek cost of 199 × 0.1 ms ≈ 20 ms, well within budget with margin for slower deltas.

  5. Serialization CPU per commit. ~20 nodes touched per commit (typical dirty subtree) × ~20 ns/node (a delta touches far fewer nodes than a full snapshot) = 20 × 20 ns = 400 ns — far under the ≤ 0.5 ms (500,000 ns) per-commit budget (§4/M2), leaving ~99.9% of that budget as margin for hook-call overhead itself.

  6. Dependency-graph memory. 500 edges (§4/M11 query-ceiling reference) × 48 bytes/edge (two NodeId-scale references plus a clock and a kind tag) = 24,000 bytes ≈ 23 KiB for a typical session — trivial relative to the 40 MB memory ceiling (§4/M12), confirming the dependency graph is not the dominant memory consumer at typical scale, though §31 names it as the first structure to grow unbounded over a very long session since, unlike the other buffers here, it carries no cap.

  7. Redaction throughput headroom. At the ≥ 50,000 fields/s target (§4/M9) against a typical 5,000-node × 6-field snapshot = 30,000 fields, a full-snapshot redaction pass costs 30,000 / 50,000 = 0.6 s worst case — why redaction is applied incrementally on deltas in steady state (§22.2) rather than re-scanning a full snapshot on every message; the 0.6 s figure is the ceiling for the keyframe case only, amortized against the K-commit interval between keyframes (0.6 s / 200 ≈ 3 ms of amortized redaction cost per commit-equivalent).

35. Hard Questions (Self-Examination)

  1. If the dependency graph (§17, §31) has no eviction policy while the event log (§18) does, what stops a multi-hour session from exhausting target-process memory even though every other buffer is bounded — and does the 4-hour session cap (§8.6) actually save you, or just delay the failure? (§17, §31)

  2. I9 says replay never re-executes target-side code, and §19.2 says the replay projector holds no reference to the live target connection at all. When a saved view (§21) is evaluated against a historical ScrubCursor, is that a distinct query path from the live-attached one, and does §11's schema actually distinguish the two cases anywhere? (§19, §21, §11)

  3. The redaction filter (§22) runs at the backend, downstream of the target's serializer, while I13's getter-guard runs inside the serializer, upstream of redaction. Could a getter that is itself a secret accessor be materialized (T10) before the backend gets a chance to filter it — and does that mean the target-side pre-filter deferral (§37) needs un-deferring before Phase 10 ships safely? (§14, §22, §37)

  4. §15's reconnect model assumes a locally-issued resumption token is trustworthy; §22 says the remote-bridge case needs "its own credential model, not a copy-paste." Where is that boundary actually enforced — one shared SessionManager path, or two genuinely separate ones — without becoming exactly the copy-paste ADR-09 warns against? (§15, §22, ADR-09)

  5. M3 sets a 50 ns budget per signal read, and §17.7 says a single unnecessary allocation blows it. Given DependencyEdge (§11) is declared immutable, how does the tracker avoid allocating a fresh edge object per read without violating that immutability or reintroducing a mutable-shared-state hazard P2/I2 forbid elsewhere? (§11, §17, §30)

  6. §18's ring buffer preserves keyframes under eviction, but §18.8 admits a storm could make "every event a keyframe," and the fallback evicts keyframes too. What actually happens to an in-progress scrub session (§19) when the keyframe it's anchored to is evicted by that fallback mid-session? (§18, §19)

  7. ADR-04 locks runtime monkey-patching over a compiler transform partly on zero-build-step grounds. For a target whose bundler LRSI genuinely cannot hook into post-hoc, is there a real migration path to a future compiler-transform adapter that doesn't re-derive the entire InstrumentationHooks contract, or does §1's deferral quietly assume a rewrite? (ADR-04, §36, §1)

  8. §20's async tracking is opt-in due to overhead risk, but §8.4's EventRecord.kind already includes "async-boundary" with no opt-in gate mentioned in §8. Does enabling async tracking retroactively change the meaning of events already in the ring buffer, or does the event log need a per-event capability marker to avoid an inconsistent read across the toggle? (§8, §18, §20)

  9. §27 says a schema-version-mismatched saved view degrades to "no matches," and §21.8 says an eviction-spanning query degrades to "partial." If both occur at once, does the UI have one consistent way to say "incomplete and possibly stale," or do the two warning paths collide? (§21, §27)

  10. T12's mitigation is a compiled-cost estimate plus a hard evaluation cap, but §21.7 says predicate compilation must be cheap enough for a live-updating saved view evaluated on every delta. Is the cost estimate computed once at compile time (cheap, possibly wrong for data-dependent cost) or dynamically per evaluation (accurate, but reintroducing the overhead §21.7 forbids)? (§21, T12, §30)

  11. §26 says session state is "not backed up — ephemeral by design," yet §22.9's redaction-gap forensics require a "wire-capture archive... retained only as long as policy allows." Doesn't a forensic wire-capture archive directly contradict "ephemeral by design," and where is the actual retention policy specified as a real, versioned rule rather than a placeholder? (§25, §26, §29)

  12. §17.8 says a dependency edge from an aborted concurrent-render pass "must not be committed to the graph." How does the tracker know a pass was aborted before committing edges it already emitted, given onDependencyEdge (§8.2) is append-only and may interleave with onUpdate — is a transactional/rollback mechanism implied that isn't in the §11 signatures? (§8, §11, §17)

  13. §31 names the dependency graph as the top bottleneck precisely because it's uncapped, while every other buffer here has an explicit eviction policy (P2). Why doesn't Phase 5 apply the same ring-buffer discipline Phase 6 applies to events — a technical blocker, or a genuine scope gap? (§17, §18, §31)

  14. §19.6 forbids assuming deltas are invertible "unless the adapter declares them so," and no adapter through Phase 11 ever declares invertibility. Does that make every backward seek in the shipped product a forward-replay-from-an-earlier-keyframe illusion rather than true reverse playback, and is that disclosed to the user anywhere, per P11? (§13, §19)

  15. T9's mitigation for session hijack is a short token staleness window, but ADR-09's rationale is that hot reload disconnects "every few seconds." Is the staleness window actually tuned to survive a realistic hot-reload gap while staying short enough to bound the T9 window, or are these two numeric requirements never reconciled against each other? (ADR-09, T9, I12)

  16. §33 credits Redux DevTools with "full" time-travel specifically because reducers are pure, and §17/I9 build LRSI's replay model around the opposite (impure-target) assumption. Does the query engine (§21) ever offer a Redux-DevTools-equivalent full-fidelity mode for a sub-store that happens to be pure, or does the general impure-target model uniformly degrade even a pure sub-store to lossy keyframe+delta replay? (§19, §21, §33)

  17. §22.8 says a mid-session redaction rule "must not attempt retroactive redaction of already-transmitted data," yet §22.9's failure analysis calls for "an audit of any prior session's transmitted data for exposure." If retroactive redaction is architecturally impossible, what does that audit accomplish beyond confirming the exposure already happened — is there a purge mechanism elsewhere it's meant to trigger? (§22, §25, §26)

  18. MM7 frames keyframe+delta replay as a philosophical commitment (never re-execute the observed system), while §36 frames the rejection of full record/replay as an engineering-feasibility argument (can't ptrace a JS heap). If a future engine-level hook made full in-realm replay feasible, would P1 still forbid it, or was feasibility the only real blocking constraint all along? (MM7, §36, P1)

36. Alternative Architectures (Roads Not Taken)

A — Compiler-Transform Instrumentation

Source (.tsx) → [Babel/SWC LRSI Plugin] → Instrumented Bundle
                        │
                        ▼
              inserted onMount/onUpdate/onEvent
              calls at every state-touching AST node
                        │
                        ▼
              Bundle ships with hooks already baked in,
              no runtime monkey-patch needed

Winning regime: build systems where a custom bundler or non-standard component model makes runtime monkey-patching unreachable. Real embodying systems: Svelte's own compiler (rewrites reactive assignments at build time) and Solid's JSX compiler transform. Rejected because it couples LRSI to a specific build tool per target, breaking the zero-build-step deployment model (§1, ADR-04), and fails silently for any dynamically-loaded or eval'd code the transform never saw.

B — CDP-Only, No In-Process Agent

Target (V8) ⇄ [V8 Inspector Protocol] ⇄ [LRSI Backend as CDP client]
                                              │
                                              ▼
                                        UI Client
        (no @lrsi/hooks in the target realm at all)

Winning regime: introspecting engine-level primitives (heap, call stack, breakpoints) without touching the app's own code. Real embodying system: Chrome DevTools itself. Rejected because CDP exposes engine concepts (objects, scopes, heap), not framework concepts (components, signals, effects); reconstructing a dependency graph purely from CDP-level object graphs would mean re-implementing framework-internals knowledge at the protocol-consumer layer instead of inside an adapter (ADR-04) — strictly harder and less maintainable.

C — Full Deterministic Record/Replay

Target Process (recorded via OS-level trace, a la rr)
        │  full instruction/syscall trace
        ▼
  [Recording Store] ── pure viewer ──▶ [LRSI UI]
   (no live attach; replay only, bit-accurate)

Winning regime: a single, fully-controlled native process where total reversibility matters more than live interactivity. Real embodying system: rr / Pernosco (O'Callahan et al., USENIX ATC 2017) and Microsoft Time Travel Debugging. Rejected because it requires OS/kernel-level trace capture that cannot observe a JS heap from outside its own realm without unacceptable overhead and platform coupling, and it answers "what did the CPU do" rather than "what did the reactive graph do."

D — Log-Only Exporter, No Live Attach

Target → [Event Exporter] → OTel Collector → External Trace Viewer
   (fire-and-forget spans/events; no session, no attach, no scrub)

Winning regime: production observability where live attach is explicitly undesirable and historical trend analysis matters more than a single debugging session. Real embodying system: standard OpenTelemetry-instrumented production monitoring stacks. Rejected because this is precisely the production-APM non-goal from §1 — it answers "what happened in aggregate," not "why did this specific re-run happen right now," and has no notion of a live, queryable, time-scrubbing session at all.

38. Glossary

  • Adapter — a per-runtime implementation of InstrumentationHooks (e.g. @lrsi/adapter-react).
  • Attach — connecting a session to a running target and beginning snapshot/event capture.
  • AttachAck — the wire message confirming a successful attach with an initial keyframe.
  • Async task — a tracked unit of async work with a start/end boundary (Phase 8).
  • Backpressure — the mechanism bounding queue growth when producers outpace consumers.
  • Bridge — the remote-target relay process (@lrsi/bridge) enabling attach across a network boundary.
  • CBOR — Concise Binary Object Representation (RFC 8949), the wire payload encoding.
  • Conformance suite — the fixture-driven test corpus (@lrsi/conformance) gating releases.
  • CycleRef — a schema marker replacing a re-visited node reference during serialization.
  • Degraded — a session state indicating impaired but not lost connectivity.
  • Delta / DeltaOp — a single structural change applied to reconstruct a snapshot from a keyframe.
  • Dependency edge — a typed link (reads/writes/subscribes/triggers) in the reactive graph.
  • Detach — ending a session and reverting the target to its pre-attach state.
  • Effect — a reactive computation that re-runs when its dependencies change.
  • EffectRecord — the schema type tracking an effect's last-run dependencies and disposal state.
  • Event ring buffer — the bounded, LogicalClock-ordered store of EventRecords.
  • Eviction policy — the documented rule governing what a bounded buffer discards when full.
  • Fiber — React's internal unit of work; adapter-internal, never exposed in the wire schema.
  • Hot reload — a development-time module replacement that disconnects and reconnects the transport without restarting the target process.
  • Instrumentation hook — a call the target's own runtime makes into LRSI at a defined lifecycle point.
  • Keyframe — a full StateSnapshot captured periodically as a replay anchor point.
  • Logical clock — a monotonic, per-session ordering value independent of wall-clock time.
  • Node identity (NodeId) — the stable identifier assigned to a tracked live object within a session.
  • Observer effect — the phenomenon where the act of inspecting a system changes its behavior.
  • Query engine — the component compiling and evaluating QuerySpec predicates over snapshots and events.
  • QuerySpec — a typed predicate/projection request against nodes, edges, or events.
  • Redaction rule — a path-pattern rule stripping a field before it crosses the trust boundary.
  • Reference model — the strategy (weak vs. strong) governing how snapshots hold onto live objects.
  • Reconnect / resume — re-establishing a dropped transport connection under the same SessionId.
  • Resumption token — the credential presented to resume a session after a transport drop.
  • Ring buffer — a fixed-capacity, oldest-evicted-first data structure.
  • Saved view — a named, persisted QuerySpec recallable within a session.
  • Scrub cursor — the current position within a session's replay timeline.
  • Serializer — the component walking a live object graph into a StateSnapshot.
  • Session — the bounded lifetime of one attach-to-detach relationship between a target and the backend.
  • Session manager — the backend component owning the session lifecycle state machine.
  • Signal — a fine-grained reactive primitive whose reads/writes are individually tracked.
  • Snapshot (StateSnapshot) — a versioned, cycle-safe serialization of live target state at a point in logical time.
  • Structured clone — the HTML-spec algorithm for deep-copying values, whose cycle/type limitations motivate LRSI's own serializer design.
  • Subscription — a registered interest in future state changes matching a QuerySpec.
  • Time scrub — navigating to an arbitrary historical point in a session's retained data.
  • Transport — the WebSocket-based wire connection carrying TransportMessages.
  • Trust boundary — a point in the architecture across which data crosses from one security domain to another.
  • Truncation marker — a schema field declaring that a subtree was deliberately cut short.
  • Weak reference — a reference that does not prevent garbage collection of its target.
