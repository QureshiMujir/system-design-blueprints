⬜ Phase 0 — Skeleton + Snapshot Serializer + CI §12

Objectives
  • Stand up the pnpm monorepo skeleton for every package listed in §1.
  • Implement a first-cut @lrsi/serializer capable of walking a plain (acyclic) object graph into a StateSnapshot.
  • Stand up CI (ADR-23) running lint, typecheck, and unit tests on every push.
  • Establish the production-build stripping guard (ADR-17) before any hook code exists, so the discipline is baked in from commit one.
Deliverable

A buildable monorepo; @lrsi/serializer serializes an acyclic fixture object into a StateSnapshot matching §8.1; CI green on every PR.

Acceptance
  • serializer.spec.ts passes on 3 fixture object graphs of depth 1, 5, and 12 nodes.
  • Depth-cap truncation fires at exactly the configured limit (default depth 32) and emits TruncationMarker{reason:"depth"}.
  • CI pipeline completes in under 4 minutes on the reference fixture set.
  • Zero any types in @lrsi/hooks and @lrsi/serializer public exports (typecheck gate).
Fixtures
  • conformance/fixtures/phase0-acyclic-shallow.json — depth-1 object, expects a 1-node StateSnapshot.
  • conformance/fixtures/phase0-acyclic-deep.json — depth-40 nested object, expects TruncationMarker{reason:"depth"} at node 32.
  • conformance/fixtures/phase0-malformed-empty-root.json — an empty root object, expects a StateSnapshot with zero children, not an error.
Pitfalls
  • Treating TruncationMarker as an error path instead of an expected, declared outcome (P3).
  • Letting the CI unit-test harness silently skip the bundle-diff placeholder — it must fail loudly once Phase 11 wires real content in.
  • Introducing a utility dependency (e.g. lodash) into @lrsi/hooks at scaffold time "temporarily" — violates ADR-03 and is expensive to remove once call sites multiply.
  • Hand-rolling depth counting without a shared constant, causing depth-cap drift between the serializer and its tests.

⬜ Phase 1 — Instrumentation Contract + First Runtime Adapter §13

Objectives
  • Lock the InstrumentationHooks interface (§11) as the stable contract every future adapter implements.
  • Ship @lrsi/adapter-react, the first concrete adapter, hooking into a running React tree.
  • Prove P4 (zero cost when detached) with a measured micro-benchmark, not an assertion.
Deliverable

@lrsi/adapter-react attaches to a running React 18 app, emits mount/update/unmount/edge events conforming to §8.2, and fully uninstalls on request.

Acceptance
  • Overhead per commit ≤ 0.5 ms (§4) measured on examples/react-counter at 60 renders/s.
  • Zero-cost-when-detached: CPU delta between "hooks loaded, not attached" and "hooks absent" is < 0.1% over a 60-second idle profile.
  • uninstall() leaves zero listeners/globals per adapter-uninstall-cleanliness.spec.ts.
  • Detection succeeds on 5 named fixture apps: CRA, Vite+React, Next.js app router, Next.js pages router, Remix.
Fixtures
  • conformance/fixtures/phase1-react-detect-cra.json — expects {detected:true, version:"18.x"}.
  • conformance/fixtures/phase1-react-mount-order.json — asserts onMount happens-before onUpdate for a freshly mounted counter.
  • conformance/fixtures/phase1-react-uninstall-cleanliness.json — attach, interact, detach; asserts zero residual listeners via a listener census.
  • conformance/fixtures/phase1-malformed-no-react.json — a plain DOM page; expects {detected:false}, not a thrown error.
Pitfalls
  • Assuming __REACT_DEVTOOLS_GLOBAL_HOOK__ is always present — many production and some dev builds omit it; the DOM-walk fallback is not optional.
  • Coupling onUpdate payloads to React's internal memoizedState shape — leaks a framework-specific concept into the wire schema, violating P12.
  • Forgetting that uninstall() must also detach from __REACT_DEVTOOLS_GLOBAL_HOOK__ if LRSI registered as a renderer listener there — a common source of I6 violations.
  • Hot-reload orphaning fiber-derived NodeIds: a component's fiber identity can change across a Fast Refresh boundary even though the developer perceives "the same component" — addressed structurally in Phase 3, but the adapter must tag orphan candidates now.

⬜ Phase 2 — Cycle-Safe Bounded Serialization §14

Objectives
  • Extend @lrsi/serializer to handle cyclic object graphs without unbounded recursion or payload growth (I3, ADR-06).
  • Enforce the node-count and memory ceilings from §4.
  • Guarantee getter/proxy-trap safety during traversal (I13).
Deliverable

A serializer that terminates in bounded time and bounded payload size on any object graph, including deliberately pathological cyclic and getter-laden fixtures.

Acceptance
  • serializer-cycle.spec.ts: a self-referencing store serializes to a payload ≤ 2 KB regardless of reference depth.
  • Serialize latency on the 5,000-node fixture: p50 ≤ 4 ms, p95 ≤ 16 ms, p99 ≤ 40 ms (§4), measured via benchmarks/serializer.bench.ts.
  • Memory ceiling: heap-snapshot diff shows ≤ 40 MB attributable to LRSI structures after 100 consecutive snapshots of the 5,000-node fixture.
  • Zero side-effecting getter invocations recorded in phase2-getter-side-effect.json (I13).
Fixtures
  • conformance/fixtures/phase2-cyclic-self-ref.json — store referencing itself; expects a CycleRef node and a finite payload.
  • conformance/fixtures/phase2-cyclic-mutual.json — two objects referencing each other; expects both directions resolved without infinite recursion.
  • conformance/fixtures/phase2-getter-side-effect.json — a getter incrementing a counter on access; asserts the counter is untouched after serialization (I13).
  • conformance/fixtures/phase2-node-cap-overflow.json — a 25,000-node flat array; expects truncation at the 20,000-node cap with TruncationMarker{reason:"node-cap"}.
  • conformance/fixtures/phase2-malformed-proxy-trap-throw.json — a Proxy whose get trap throws; expects the node marked opaque, not a serializer crash.
Pitfalls
  • Using a strong Map<object, NodeId> "temporarily for simplicity" — silently reintroduces I2 violations and is easy to forget to remove.
  • Detecting cycles only on plain-object identity while ignoring array/Map/Set containers, which are also legitimately cyclic in reactive stores.
  • Assuming Reflect.get never triggers a side effect — it does invoke the getter (that's the point); the re-entrancy guard must catch mutation attempts from within the getter, not the read itself.
  • Truncating "at random" once a limit is hit rather than deterministically — breadth-first vs. depth-first order matters for reproducible fixtures.

⬜ Phase 3 — Transport + Reconnect Across Hot Reload §15

Objectives
  • Implement @lrsi/transport: WebSocket (RFC 6455) framing, CBOR (RFC 8949) encoding, per the §11 TransportMessage union.
  • Implement the reconnect/resume handshake (ADR-09) surviving a hot-reload disconnect without losing SessionId (I12).
  • Implement the session lifecycle state machine (§8.6) in SessionManager.
Deliverable

A transport that survives repeated hot-reload cycles in a live development loop without the UI losing session continuity or double-counting events.

Acceptance
  • Reconnect-after-hot-reload p95 ≤ 2 s across 50 simulated reload cycles (conformance/fixtures/phase3-hot-reload-cycle.json).
  • Zero duplicate EventRecords observed at the UI after a reconnect, verified by eventId uniqueness assertion.
  • Illegal state transitions (e.g. Detached → Attached directly) rejected 100% of the time in session-state-machine.spec.ts.
  • Sustained bandwidth ≤ 2 Mbps and message rate ≤ 120 msg/s under the Phase-1 fixture's steady-state load (§4).
Fixtures
  • conformance/fixtures/phase3-hot-reload-cycle.json — 50 simulated disconnect/reconnect cycles; expects session continuity and the §4 latency budget.
  • conformance/fixtures/phase3-resume-token-expired.json — a resumption token presented past its staleness window; expects fallback to a fresh session, not a hang.
  • conformance/fixtures/phase3-malformed-truncated-frame.json — a CBOR frame truncated mid-message; expects a retransmit request, not a decode crash.
  • conformance/fixtures/phase3-illegal-transition.json — a direct Detached→Attached message; expects rejection and a forced Detached.
Pitfalls
  • Treating "reconnect" as "recreate the session" by default — the single biggest UX regression this phase exists to prevent (ADR-09).
  • Forgetting that a resumption token is a bearer credential across a reconnect and must never be logged or included in telemetry payloads.
  • Allowing the send-queue to grow unbounded "just during reconnect, temporarily" — reintroduces I14/ADR-27 violations exactly when the target is already stressed.
  • Assuming WebSocket message ordering is preserved across a reconnect — a new socket is a new ordering domain; the resume handshake must explicitly re-sequence, not assume continuity.

⬜ Phase 4 — Component/Module Tree View §16

Objectives
  • Ship the first UI surface in @lrsi/ui: a virtualized tree view rendering the live StateSnapshot tree.
  • Implement search/filter over node paths and type tags.
  • Wire live SnapshotDelta application to the rendered tree with diff highlighting.
Deliverable

A tree view that renders a 5,000-node snapshot, updates live via SnapshotDelta, and lets a developer search/filter/jump to any node, including truncated and cyclic nodes.

Acceptance
  • Initial render of a 5,000-node snapshot completes in ≤ 50 ms (aligned to the serialize p95 budget, §4).
  • Search-as-you-type over 5,000 nodes returns results in ≤ 16 ms per keystroke (one frame budget).
  • Diff highlight clears after exactly 2 consecutive settled frames, verified in tree-view-diff-highlight.spec.ts.
  • CycleRef jump-to-target navigates correctly in 100% of phase2-cyclic-* fixtures replayed through the UI.
Fixtures
  • conformance/fixtures/phase4-tree-render-5000.json — 5,000-node snapshot; expects render within budget.
  • conformance/fixtures/phase4-search-fuzzy-path.json — a search query matching 40 of 5,000 nodes; expects the correct result set.
  • conformance/fixtures/phase4-truncated-node-display.json — a TruncationMarker node; expects the "N more" affordance, not silent omission.
  • conformance/fixtures/phase4-malformed-delta-unknown-path.json — a SnapshotDelta referencing a path not present in the current tree; expects a graceful re-request of a fresh keyframe, not a UI crash.
Pitfalls
  • Rendering the full unvirtualized tree "for simplicity" during early development and never circling back — silently breaks the render-latency criterion under any real fixture size.
  • Treating CycleRef as an error state in the UI layer, contradicting P8 at the presentation layer even though the schema already handles it correctly.
  • Applying SnapshotDelta operations out of order (e.g. a remove before its preceding add completes) — must apply strictly in received order.
  • Search implemented as live re-serialization of visible nodes to strings and substring-matching — violates P10 and does not scale.

⬜ Phase 5 — Reactive Dependency Graph §17

Objectives
  • Extend the Dependency Graph Tracker to capture fine-grained signal/effect/subscription edges (§8.3), beyond the coarse Phase-1 hook-dependency-array capture.
  • Ship a graph view in @lrsi/ui answering "what does this depend on" and "what depends on this" as structural traversals (P10), informed by Meyerovich & Bodik 2010 and the Carniato/Solid.js fine-grained-reactivity lineage (§5).
  • Extend @lrsi/adapter-react to model useEffect/useMemo dependency arrays as first-class DependencyEdges, not just re-render triggers.
Deliverable

A dependency graph view answering "why did this re-run" as a structural backward traversal, built on DependencyEdge/EffectRecord data captured with bounded per-read overhead.

Acceptance
  • Per-signal-read overhead ≤ 50 ns total (§4), measured via benchmarks/dependency-edge.bench.ts against an uninstrumented ~5 ns baseline.
  • "Why did this re-run" resolves to a correct originating writes edge in 100% of the phase5-causal-chain-* fixtures.
  • Graph view renders a 500-edge dependency graph in ≤ 100 ms.
  • EffectRecord.dependsOn matches the adapter's own internal dependency-array contents exactly, verified differentially (§28) against React DevTools' own hook inspection where available.
Fixtures
  • conformance/fixtures/phase5-causal-chain-single-hop.json — one write directly triggers one effect; expects a 1-edge backward trace.
  • conformance/fixtures/phase5-causal-chain-multi-hop.json — a write triggers an effect that writes a second signal triggering a second effect; expects a correctly ordered 2-hop trace.
  • conformance/fixtures/phase5-diamond-dependency.json — two effects both depending on one signal, feeding a third — expects both incoming edges represented, no edge lost to a naive tree assumption.
  • conformance/fixtures/phase5-malformed-disposed-effect-edge.json — an edge reported for an already-disposed effect; expects the edge rejected and logged, not silently attached.
Pitfalls
  • Modeling the dependency graph as a tree because the snapshot tree already exists — a real reactive graph has diamonds and must be modeled as a DAG from the start; retrofitting this after building tree-shaped storage is expensive.
  • Recording reads edges unconditionally on every render pass, including reads inside an already-memoized branch that didn't actually re-execute — inflates the edge count and corrupts causal traces.
  • Ignoring the overhead budget until "graph view looks done", then discovering the per-read cost is 10x over budget — must be measured from the first edge-emission commit, not retrofitted.
  • Treating EffectRecord.disposed as advisory — a disposed effect must never accept new edges (see the malformed-input fixture above); I6-class cleanup discipline applies here too.

⬜ Phase 6 — Event Ring-Buffer Log §18

Objectives
  • Implement @lrsi/eventlog's production RingBuffer<EventRecord> with the eviction policy locked in ADR-10.
  • Enforce the §4 capacity (50,000 events / 8 MB) and the I8/I11 boundedness invariants under a synthetic render storm.
  • Ship an event-log UI view correlating events against the tree and graph views by LogicalClock.
Deliverable

A bounded, monotonically-ordered event log surviving a sustained render storm without unbounded memory growth, with a UI view correlating events to tree and graph state.

Acceptance
  • Ring buffer never exceeds 50,000 events or 8 MB (§4) under the render-storm soak fixture, verified continuously, not just at test end.
  • lrsi.eventlog.drop_rate accurately reflects the actual eviction count within 1% under the soak test.
  • Out-of-order LogicalClock values are quarantined 100% of the time in eventlog-ordering.spec.ts, never silently reordered.
  • Event-log UI view renders 1,000 visible events with jump-to-node navigation in ≤ 100 ms.
Fixtures
  • conformance/fixtures/phase6-render-storm-60s.json — 10,000 events/s for 60s; expects bounded memory and an accurate drop-rate report.
  • conformance/fixtures/phase6-out-of-order-clock.json — a deliberately shuffled event batch; expects quarantine and a Degraded flag.
  • conformance/fixtures/phase6-oversized-payload.json — an event whose payloadSummary exceeds the byte cap; expects truncation with a marker, not buffer corruption.
  • conformance/fixtures/phase6-keyframe-preservation.json — a storm that would otherwise evict a keyframe entry; expects the keyframe preserved per ADR-10, non-keyframe entries evicted first.
Pitfalls
  • Implementing eviction as strict FIFO without the keyframe-preserving exception — breaks Phase 7's replay projector, which depends on keyframes surviving eviction.
  • Computing sizeBytes after insertion rather than before — allows a single oversized event to transiently blow the byte cap before correction.
  • Treating the render-storm soak test as a "nice to have" perf test rather than a correctness test — I11 is a correctness invariant, not a performance target.
  • Correlating events to browser Performance Timeline marks as the primary ordering mechanism instead of LogicalClock — violates P7 the moment a non-browser (Node.js) target is attached.

⬜ Phase 7 — Time-Scrub Replay Projection §19

Objectives
  • Implement @lrsi/replay's keyframe + delta projector (ADR-11) satisfying the §4 seek-latency budget.
  • Ship the scrubber UI: seek to any point in the retained event/snapshot history without re-executing target-side code (I9).
  • Contrast explicitly against full deterministic record/replay (O'Callahan et al. 2017, Microsoft TTD) and pure-model replay (the Elm Architecture) per §5/§36.
Deliverable

A scrubber that seeks to any retained point in session history within the §4 latency budget, provably without invoking any target-side code.

Acceptance
  • Seek latency within the last 5 keyframes, p95 ≤ 120 ms (§4), measured via benchmarks/replay.bench.ts.
  • Replay-determinism property test: 100 repeated seeks to the same cursor produce byte-identical StateSnapshot projections.
  • Zero onEvent/hook invocations recorded during any replay operation (lrsi.replay.side_effect_attempts === 0, I9).
  • Seeking to an evicted keyframe degrades to "earliest available" with an explicit UI notice, never an error dialog.
Fixtures
  • conformance/fixtures/phase7-seek-recent-keyframe.json — seek within the last 5 keyframes; expects the §4 latency budget met.
  • conformance/fixtures/phase7-seek-evicted-keyframe.json — seek to a point whose keyframe was evicted; expects graceful "earliest available" fallback.
  • conformance/fixtures/phase7-replay-determinism.json — 100 repeated seeks; expects byte-identical projections.
  • conformance/fixtures/phase7-malformed-out-of-range-cursor.json — a ScrubCursor referencing a clock value beyond the current session's range; expects a clamped, in-range result, not an out-of-bounds error.
Pitfalls
  • Implementing "replay" as literally reconnecting to the target and asking it to reproduce state — exactly the I9 violation this phase exists to prevent; replay must be a pure projection over retained data.
  • Choosing K (the keyframe interval) purely to minimize storage without checking the resulting seek latency against the §4 budget — the two are in direct tension and must be tuned together (§34).
  • Assuming deltas are invertible by default — most adapters do not declare reversible deltas; backward seeks must replay forward from a keyframe unless invertibility is explicitly declared.
  • Allowing the scrubber UI to trigger a live query (@lrsi/query) against the current live state while displaying a historical cursor position — silently conflates "then" and "now"; the UI is either live-following or scrub-mode, never both against different data sources at once.

⬜ Phase 8 — Async/In-Flight Work Tracking §20

Objectives
  • Track async task lifecycles (AsyncTaskRecord, §11) from dispatch to settlement, informed by Node.js async_hooks (§5).
  • Correlate async tasks back to the NodeId/DependencyEdge that caused them (causedBy).
  • Ship an async-task UI view (a Gantt-style in-flight list) distinct from the event log.
Deliverable

An async-task tracker correlating dispatch → settlement with a causal link back to the triggering node, visualized as an in-flight Gantt view, opt-in and clearly bounded in overhead.

Acceptance
  • causedBy correctly attributes 100% of phase8-causal-async-* fixtures to the originating NodeId.
  • Matched-pair enforcement: an orphaned pending task past the 4-hour session cap is flagged, not silently dropped nor left pending forever.
  • Opt-in overhead, when enabled, stays within a separately-declared budget of ≤ 5% additional CPU (distinct from the §4 baseline 2%), explicitly labeled as an opt-in cost in the UI.
  • Async-task Gantt view renders 200 concurrent in-flight tasks in ≤ 100 ms.
Fixtures
  • conformance/fixtures/phase8-causal-async-fetch.json — a signal write dispatches a fetch; expects causedBy correctly set.
  • conformance/fixtures/phase8-causal-async-chained.json — a fetch's .then dispatches a second async task; expects the causal chain preserved across the boundary.
  • conformance/fixtures/phase8-orphaned-pending-task.json — a task that never settles within session duration; expects the flagged-orphan behavior, not silent loss.
  • conformance/fixtures/phase8-malformed-mismatched-end.json — an onAsyncTaskEnd for a taskId with no matching onAsyncTaskStart; expects rejection and a logged anomaly, not a crash.
Pitfalls
  • Enabling async tracking by default "since it's useful" — contradicts the documented opt-in overhead risk (§5) and the general P4 discipline.
  • Attributing causedBy via a best-guess heuristic (e.g. "most recent write") instead of actual causal-context capture — produces plausible-looking but wrong answers, worse than no answer.
  • Treating every microtask as a trackable "async task" — explodes cardinality past anything the UI or ring buffer (§4/§18) can usefully display; only boundary-crossing work (fetch, timers, explicit async functions) should be tracked, not every promise tick.
  • Assuming async tasks always settle — an abandoned fetch (component unmounted mid-request) is common and must resolve to a defined status, not remain pending indefinitely without a flag.

⬜ Phase 9 — Query Engine + Saved Views §21

Objectives
  • Implement @lrsi/query's QuerySpec compiler/evaluator (ADR-12) over nodes, edges, and events.
  • Ship saved views: named, persisted QuerySpecs recallable across a session (cross-session persistence is PhaseDeferred, §37).
  • Directly answer the Sillito et al. FSE 2006 question taxonomy (§5) — structure, relationship, and history questions — as first-class query shapes.
Deliverable

A structured query engine and saved-view mechanism answering structure/relationship/history questions (§5) as compiled predicate evaluations, with the Phase 5/8 causal traces re-expressed as saved-view templates.

Acceptance
  • Query evaluation over the full §4 ceiling (5,000 nodes / 500 edges / 50,000 events) completes in ≤ 16 ms.
  • Saved views persist and recall correctly across a Reconnecting→Attached cycle within the same SessionId (I12-consistent).
  • Zero string-search fallback paths exist in @lrsi/query — verified by a lint rule forbidding .includes/.match against serialized JSON blobs in that package.
  • The "why did this re-run" and causal-async saved-view templates produce results identical to the Phase 5/8 bespoke implementations, verified differentially.
Fixtures
  • conformance/fixtures/phase9-query-path-match.json — a pathMatches query against a known fixture tree; expects the exact matching node set.
  • conformance/fixtures/phase9-query-and-or-compound.json — a compound and/or predicate; expects correct boolean combination.
  • conformance/fixtures/phase9-saved-view-recall.json — save, disconnect/reconnect, recall; expects identical QuerySpec and identical result set.
  • conformance/fixtures/phase9-malformed-empty-predicate.json — a QuerySpec with an empty and: []; expects a defined result (vacuous true) rather than undefined behavior.
Pitfalls
  • Allowing a "quick" string-search shortcut into the query evaluator "just for this one query type" — the exact P10 regression this phase exists to prevent; once one string-search path exists, more accrete.
  • Building saved views as a UI-only feature (localStorage) instead of a backend-persisted, session-scoped construct — breaks recall across a reconnect (I12) and diverges from the wire-protocol model (P5).
  • Treating and: [] / or: [] as an error instead of a defined vacuous case — undefined edge-case behavior in a query language is a correctness bug waiting to surface in a saved view.
  • Letting the query builder UI expose the full QueryPredicate union's power in a way that lets a user construct a predicate more expensive than the §4 ceiling was benchmarked against — needs a compiled-cost estimate, not just a raw pass-through.

⬜ Phase 10 — Remote-Target Bridge + Redaction §22

Objectives
  • Implement @lrsi/bridge: a relay process enabling attach to a Node.js or remote-browser target across a network boundary (ADR-15).
  • Implement the backend-side RedactionRule enforcement point (ADR-16) as the mandatory pre-transport filter for any remote attach.
  • Address T1/T2-class threats (§24) that only become real once a target crosses a network trust boundary.
Deliverable

A remote-target bridge that never exposes an inbound inspector port, enforces redaction before any payload leaves the bridge, and authenticates every remote attach.

Acceptance
  • Zero inbound listening ports opened by @lrsi/bridge on the target side — verified by a network-scan conformance check (phase10-no-inbound-port.json).
  • Redaction throughput ≥ 50,000 fields/s (§4) on the 20,000-node ceiling fixture with the default rule set.
  • 100% of default-rule-matching paths (password, token, secret, apiKey) are absent from captured wire traffic in phase10-redaction-wire-capture.json.
  • An unauthenticated remote attach attempt is rejected 100% of the time in phase10-unauthenticated-attach.json.
Fixtures
  • conformance/fixtures/phase10-no-inbound-port.json — network scan of a running bridge-attached target; expects zero inbound listening ports.
  • conformance/fixtures/phase10-redaction-wire-capture.json — a fixture store containing secret-heuristic-matching fields; expects zero occurrences on the wire.
  • conformance/fixtures/phase10-unauthenticated-attach.json — an attach attempt without a valid credential; expects rejection, not a degraded-but-connected state.
  • conformance/fixtures/phase10-malformed-oversized-remote-snapshot.json — a remote target declaring a node count far beyond the independent remote-target cap; expects rejection/ truncation, not amplification passed through to the local UI.
Pitfalls
  • Allowing the bridge to listen for inbound connections "for simplicity in early testing" and never removing it before a remote-capable release — precisely the T1 threat this phase exists to close.
  • Implementing redaction only in the UI layer for the remote-bridge case "since it's already implemented there" — the trust boundary for a remote target is materially different (network, not process) and requires the backend-side enforcement point, never a UI-only check (I5, ADR-16).
  • Treating the remote target's self-reported node/event counts as trustworthy for the local §4 ceilings — a compromised or buggy remote target can amplify past the local budget unless independently capped (T4).
  • Reusing the local-session resumption-token model unmodified for the remote case — ADR-09's local reconnect model assumes a trusted token; the remote bridge needs its own credential model, not a copy-paste.

⬜ Phase 11 — Conformance Suite + Perf Hardening §23

Objectives
  • Complete @lrsi/conformance: the full fixture corpus spanning Phases 0–10, run as a single CI-gated suite.
  • Verify every §4 budget line under the actual conformance corpus, not synthetic micro-benchmarks alone.
  • Complete the ADR-17 production-build stripping proof and lock 1.0 compatibility guarantees (§27).
Deliverable

A single CI-gated conformance suite covering every phase's fixtures, every §4 performance budget, the ADR-17 stripping proof, and the full §7 invariant-exercising methodology, as the release gate for 1.0.

Acceptance
  • 100% of named fixtures across phase0–phase10 (this document's N.5 sections) pass in the release-gate CI job.
  • Zero §4 budget-line regressions beyond declared threshold across two consecutive runs.
  • ADR-17 bundle-diff proof passes: production build with LRSI present is byte-identical to without, modulo the DCE guard.
  • Fuzz corpus runs for ≥ 30 CPU-minutes per CI run with zero new crash/hang discoveries before a 1.0 tag.
Fixtures
  • conformance/fixtures/phase11-cross-phase-hotreload-during-replay.json — a hot reload occurring while a time-scrub replay is in progress; expects the replay to complete against its already-retained data undisturbed (I9 holds independent of live-connection state).
  • conformance/fixtures/phase11-differential-react-devtools.json — a fixture app inspected simultaneously by LRSI and React DevTools; expects matching hook-state reports.
  • conformance/fixtures/phase11-bundle-diff-proof.json — paired production builds (with/without LRSI); expects byte-identical output modulo the DCE guard.
  • conformance/fixtures/phase11-fuzz-regression-corpus.json — a curated corpus of previously-discovered fuzz-crash inputs; expects all now pass (regression-lock).
Pitfalls
  • Treating the conformance suite as "done" once it's green once, rather than as a continuously-enforced release gate — a suite that isn't CI-blocking degrades to documentation within a few releases.
  • Fuzzing only the wire decoder and skipping the SerializedValue deserializer (or vice versa) — ADR-22 names both explicitly because they are independently reachable from an adversarial input (a malicious remote target, per Phase 10).
  • Declaring the ADR-17 stripping proof "verified" via manual bundle inspection instead of an automated byte-diff — manual inspection does not scale and drifts silently as bundler config evolves.
  • Running the differential tests against a single React version — framework-internals drift (Phase 1's dominant failure mode) means the differential corpus must span the supported version range, not just the latest.
