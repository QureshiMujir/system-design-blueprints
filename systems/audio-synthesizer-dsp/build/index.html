⬜ Phase 0 — Skeleton, Buffer/Block Contract, Offline Renderer & CI §12

Objectives
  • Establish the audiolib.core types (SampleRate, BlockSize, AudioBuffer, ChannelLayout, RenderContext) per §11.
  • Establish the block-processing contract (P7) and prove it with a passthrough node.
  • Stand up the offline renderer (audiolib.render.offline) as the first non-RT render path.
  • Stand up CI (ADR-23): lint, unit tests, allocation-tracing harness stub (I1).
Deliverable

A package importable as audiolib; an OfflineRenderer that renders N seconds of silence (passthrough) to a valid WAV file; a green CI pipeline.

Acceptance
  • OfflineRenderer renders 1.0000 s at 48000 Hz to silence_1s_48k.wav, byte-for-byte matching a golden fixture (I13 baseline).
  • Allocation-tracing fixture reports 0 allocations across 1000 consecutive PassthroughNode. process() calls (I1).
  • CI green on a clean checkout; lint zero-warnings.
  • Render is bit-exact across two consecutive runs on the same machine (ADR-26).
Fixtures
  • silence_1s_48k.wav — 1 s digital silence, 48 kHz/stereo/float32; expected: all samples exactly 0.0.
  • passthrough_impulse.wav — single-sample impulse at t=0; expected: impulse reproduced unchanged (identity contract).
  • render_determinism_regression.json — SHA-256 of five consecutive renders of the same 1 s patch; expected: all five hashes identical, tolerance: exact.
  • malformed_wav_header.bin — a WAV file with a truncated RIFF header; expected: WavParseError raised, no crash (T1 preview).
Pitfalls
  • Treating AudioBuffer as interleaved by accident (ADR-02 mandates planar) — breaks every downstream node's channel indexing silently.
  • Sizing the arena to the default block size instead of the ceiling block size (§4) — works in dev, xruns the first time a host requests the max block size.
  • Letting the offline renderer diverge informally from the RT renderer instead of sharing the literal compiled kernel (P14) — the two silently drift apart later.
  • A trivially-passing numeric-regression CI job because no real fixture exists yet — must be a tracked failing placeholder, not a skip.

⬜ Phase 1 — Naive Oscillators & the Measured Aliasing Baseline §13

Objectives
  • Implement naive sine/saw/square/triangle oscillators (audiolib.osc.naive) with no antialiasing (deliberately, as a measurement baseline).
  • Build the spectral measurement fixture that will quantify the aliasing floor for every later oscillator phase (§4 target).
  • Extend CI's numeric-regression job with the first real fixture.
Deliverable

Naive oscillators for all five waveforms; a measured, recorded aliasing baseline across the full pitch range, establishing the "before" state that Phase 2 must improve on by ≥60 dB (§4 floor of -80 dBFS versus this baseline's typical -20 to -40 dBFS).

Acceptance
  • Measured alias energy for a naive sawtooth at A3 (220 Hz) matches the §8 worked calculation (-40.8 dB at 23800 Hz) within 0.5 dB.
  • alias_baseline.json contains one entry per MIDI note 21-108 with measured worst-harmonic dBFS.
  • THD+N of the naive sine oscillator (no discontinuity, so no aliasing) is ≤ -90 dB, confirming the measurement pipeline itself is not the source of noise (P10 sanity check).
Fixtures
  • naive_saw_a3.wav — naive sawtooth at 220 Hz, 1 s, 48 kHz; expected spectrum matches §8 worked example within 0.5 dB.
  • naive_square_c4.wav — naive square at 261.63 Hz; expected: alias components at odd harmonics above Nyquist.
  • alias_baseline.json — per-note worst-harmonic dBFS table; regression tolerance: none (this is the baseline, not a gate).
  • naive_sine_thd.wav — pure sine at 1 kHz; expected THD+N ≤ -90 dB (measurement-pipeline sanity).
Pitfalls
  • Measuring alias energy with a rectangular (unwindowed) FFT window, which itself introduces spectral leakage indistinguishable from aliasing — use a Hann window (§28).
  • Confusing the fundamental's own harmonic rolloff (1/k amplitude, expected) with true aliasing (frequency folding, the actual defect) — the worked example in §8 disambiguates the two.
  • Forgetting that naive triangle (via leaky integration of naive square) inherits the square's aliasing, not a separate lesser defect.

⬜ Phase 2 — Band-Limited Oscillators (PolyBLEP / minBLEP) §14

Objectives
  • Replace naive discontinuities with PolyBLEP correction (default, ADR-05) and add minBLEP as an opt-in higher-fidelity path for hard-sync/FM-heavy patches.
  • Meet the §4 aliasing floor (≤ -80 dBFS) across the full MIDI pitch range.
  • Extend the differential-test suite to compare measured spectra against the Phase 1 baseline.
Deliverable

audiolib.osc.polyblep and audiolib.osc.minblep, both RT-safe (zero allocation after graph-commit), each passing the aliasing-floor gate across MIDI notes 21-108.

Acceptance
  • 100% of MIDI notes 21-108: measured worst-harmonic alias energy ≤ -80 dBFS for PolyBLEP saw and square (§4).
  • minBLEP path measured floor ≤ -90 dBFS on the same sweep (Brandt 2001's stated improvement over PolyBLEP).
  • CPU cost delta vs. naive oscillator (Phase 1): PolyBLEP ≤1.3×, minBLEP ≤3× (M-series target, §30).
  • Zero allocations measured on the RT path for both oscillator types (I1, allocation-tracing harness).
Fixtures
  • polyblep_saw_sweep.json — per-note alias energy, PolyBLEP saw, notes 21-108; tolerance: every entry ≤ -80 dBFS.
  • minblep_hardsync_c4.wav — hard-synced oscillator pair at C4 with minBLEP correction; expected: no audible zipper at the sync discontinuity, alias floor ≤ -90 dBFS.
  • polyblep_vs_naive_regression.json — paired comparison per note; tolerance: ≥40 dB improvement every entry.
Pitfalls
  • Applying poly_blep at the wrong phase-wrap boundary (off-by-one-sample) — silently reintroduces most of the aliasing while looking "corrected" on a casual listen.
  • minBLEP table precomputed at the wrong sample rate (tables are fs-dependent) — must be recomputed on sample-rate change, not cached globally across streams.
  • Applying BLEP correction twice (once per discontinuity type, accidentally on every sample) — distorts the waveform's DC/amplitude, not just its band-limiting.
  • Assuming PolyBLEP fixes triangle-wave aliasing — triangle is (leaky-integrated) square, so the correction must be applied to the square stage before integration, not after.

⬜ Phase 3 — Envelopes & Parameter Smoothing §15

Objectives
  • Implement the ADSR state machine (audiolib.env.adsr) per the §8 segment equations.
  • Implement SmoothedParam (audiolib.env.smoothing) as the mandatory path for every non- sample-accurate parameter change (P3, ADR-09).
  • Establish the zipper-noise differential test that gates every future node exposing a runtime parameter.
Deliverable

EnvelopeParams/EnvelopeStage driving per-voice amplitude/filter-cutoff envelopes; SmoothedParam available to every node exposing a runtime-changeable parameter, both zero- allocation on the RT path.

Acceptance
  • Envelope output continuity: max sample-to-sample delta at any stage transition ≤ the theoretical single-sample slope bound, verified across 100% of a NoteOn/NoteOff fuzz corpus (I7-adjacent).
  • Zipper-noise test: a step parameter change through SmoothedParam (tau=20 ms) produces no spectral component >-60 dBFS at the step-repetition frequency, versus a raw (unsmoothed) jump which must measurably fail the same test (regression contrast, P10).
  • Release-to-Idle transition reaches exactly 0.0 (not just "small") within release_samples × 1.2, confirmed against envelope_release_zero.json.
  • Zero RT-path allocations across a full ADSR cycle (I1).
Fixtures
  • adsr_full_cycle_c4.wav — a single note through Attack/Decay/Sustain/Release at defined parameters; expected level trace matches §8 equations within 1e-4 relative tolerance.
  • envelope_early_release.wav — NoteOff arriving mid-Attack; expected: smooth transition into Release from the current level, not a jump to sustain first (§8 decision, documented).
  • zipper_noise_stepped_cutoff.wav — raw step change to filter cutoff (unsmoothed control case); expected: FAILS the -60 dBFS zipper gate, proving the test detects the defect it's meant to catch.
  • smoothed_cutoff_sweep.wav — same change routed through SmoothedParam; expected: PASSES the same gate.
Pitfalls
  • Resetting envelope state to exactly 0 on retrigger instead of ramping down from the current level first — produces an audible click on rapid retriggers (a documented, deliberate choice point per §8; this blueprint locks "ramp from current level").
  • Choosing tau_ms too large (>100 ms) — smoothing itself becomes audible as "filter lag," feeling unresponsive; too small (<2 ms) barely helps zipper noise at all.
  • Applying the exponential release formula with a tau_R in samples rather than seconds-times- fs, silently changing perceived release time when sample rate changes (I8-adjacent).
  • Sharing one SmoothedParam instance across multiple voices when the parameter is meant to be per-voice — causes cross-voice zipper artifacts under polyphony.

⬜ Phase 4 — Biquad & State-Variable Filters with Stability Proofs §16

Objectives
  • Implement direct-form biquads (audiolib.filters.biquad) using the RBJ cookbook formulas (Bristow-Johnson; §8) for low-pass, high-pass, band-pass, notch, peaking, and shelving.
  • Implement the TPT/zero-delay-feedback state-variable filter (audiolib.filters.svf_tpt, Zavalishin 2012) for every modulatable filter use (ADR-06).
  • Produce a machine-checked stability proof (pole-magnitude sweep) covering the full exposed parameter range for both filter types (P4, I2).
Deliverable

BiquadCoeffs/FilterState and the TPT SVF, both RT-safe, both differentially validated against scipy.signal, both carrying a machine-checked stability proof across their full parameter range.

Acceptance
  • Biquad magnitude response matches scipy.signal.freqz within 0.1 dB across 100 (cutoff, Q) grid points spanning 20 Hz-20 kHz and Q in [0.5, 10] (P10).
  • TPT SVF pole magnitude |pole| < 1.0 for 100% of a grid of cutoff in (0, 0.4999·fs) × resonance in [0, 1) (I2, §4).
  • CPU cost per filter-sample: biquad ≤5 ns, TPT SVF ≤8 ns on reference hardware (M-series, §30).
  • Denormal-tail fixture: CPU-per-block does not exceed 1.5× nominal cost during a 10 s silent decay tail with FTZ/DAZ enabled (I6).
Fixtures
  • biquad_lpf_1khz_q0707.json — coefficients from the §8 worked example; expected values within 1e-5.
  • filter_freqz_differential.json — measured vs. analytic magnitude response, 100 grid points; tolerance: 0.1 dB.
  • svf_pole_sweep.json — pole magnitude per (cutoff, resonance) grid point; tolerance: all entries <1.0.
  • denormal_tail_reverb_input.wav — a decaying sine feeding into a filter's feedback path; expected: no CPU spike after amplitude drops below denormal range.
  • svf_self_oscillation_boundary.wav — resonance swept to the documented clamp boundary; expected: bounded output amplitude, no runaway growth.
Pitfalls
  • Computing biquad coefficients in float32 near very low cutoffs (sub-100 Hz) — coefficients cluster near 1.0, losing precision (§8); mitigate with float64 coefficient computation (ADR-02).
  • Modulating a direct-form biquad's coefficients per-sample — computationally expensive and introduces transients; this is exactly why TPT SVF exists for modulated use (ADR-06) — do not retrofit smooth modulation onto biquads instead.
  • Filter self-oscillation at extreme Q/resonance producing a musically "correct" but system- dangerous sine at full amplitude — must be bounded by P12's clamp, not left to the limiter alone.
  • Forgetting to pre-warm filter state (feeding silence before audible input) — causes an audible transient/overshoot at note start from zero initial state.

⬜ Phase 5 — Signal Graph & Topological Scheduling §17

Objectives
  • Implement Graph/Node/Port/Connection (§11) and the topological-sort scheduler (audiolib.graph.scheduler, ADR-04).
  • Enforce graph acyclicity except through an explicit unit-delay node (P5, I3).
  • Prove the block-processing contract (P7/I8) holds across arbitrary graphs and arbitrary block sizes.
Deliverable

A committable, validated Graph with a precomputed topological order, an RT-safe scheduler iterating it per block, and a proven block-size-invariance guarantee.

Acceptance
  • 100% of a fuzz corpus of randomly generated cyclic graphs (without an explicit delay node) are rejected at commit with GraphCycleError, zero false negatives (I3).
  • Block-size-invariance test: an 11-node reference patch rendered at 64/128/256/512/1024-sample blocks produces output identical within 1e-6 RMS difference across all five (I8).
  • Graph commit-to-snapshot-swap latency ≤1 audio block at the default block size (P13 latency budget).
  • Scheduler iterates a 4096-node graph (§4 ceiling) within the per-block deadline at the default block size, measured on reference hardware (M-series, §30).
Fixtures
  • cyclic_graph_no_delay.json — a patch graph with an undeclared cycle; expected: GraphCycleError at commit.
  • cyclic_graph_with_delay.json — the same topology but routed through an explicit unit-delay node; expected: commit succeeds.
  • block_size_invariance_reference_patch.json — an 11-node patch (oscillator, envelope, filter, delay, mixer); expected: identical output across all five supported block sizes within tolerance.
  • graph_4096_node_stress.json — a synthetic graph at the node-count ceiling; expected: scheduler completes within the per-block deadline.
Pitfalls
  • Recomputing topo_order on the audio thread instead of only at commit time — reintroduces allocation/compute risk into the RT path (violates P1).
  • A cycle detector that misses a cycle spanning both audio-rate and mod-rate connections (two different ConnectionTypes forming one logical cycle) — must validate the union of both edge kinds, not each independently.
  • Mutating a live (already-swapped) graph's node list in place from the control thread — violates P9 and can race with the RT thread mid-block.
  • Treating the unit-delay node as "free" — it still consumes a static buffer slot and must be counted against the node-count ceiling (§4).

  • Enforce the click-free voice-stealing guarantee (P8, I5) with a differential waveform-continuity test.
  • Size the static voice array to the §4 memory-per-voice and max-polyphony budgets (I14).
Deliverable

A polyphonic voice pool with proven click-free stealing under sustained note pressure, its static memory footprint verified against the §4/I14 budget.

Acceptance
  • Voice-steal waveform-continuity test: 0 discontinuities exceeding the slope bound across a fuzz corpus of 10,000 randomly-timed steal events (I5).
  • Static Voice array memory: ≤4096 bytes/voice × configured polyphony, verified by build-time size assertion (I14, §4).
  • Same-note NoteOn (legato reuse) never allocates a new voice when an exact match exists, verified by allocator unit tests (ADR-08).
  • 64-voice dense-chord stress test (dense_chord_64voice.wav) sustains 0 xruns over a 10-minute render at the default block size (§4 dropout budget).
Fixtures
  • voice_steal_fuzz_corpus.json — 10,000 randomly-timed NoteOn events against a fixed 8-voice pool; expected: 0 continuity violations at steal boundaries.
  • dense_chord_64voice.wav — a sustained 64-note chord at max default polyphony; expected: 0 xruns, CPU within the per-voice budget × 64 (§4).
  • legato_same_note_reuse.json — repeated NoteOn for an already-playing note; expected: voice count never exceeds the number of distinct notes played.
  • voice_memory_static_assertion.json — build-time size check output; expected: ≤4096 bytes/voice.
Pitfalls
  • Stealing "the quietest" instead of "the oldest" without updating ADR-08's documented rationale — a silent policy drift that breaks the predictability guarantee the ADR argues for.
  • Applying the fast-release ramp only to amplitude and forgetting the filter's key-tracked state — a voice can click at steal time if its filter state jumps discontinuously even while amplitude ramps smoothly.
  • Sizing the voice array to the default polyphony (64) instead of the configurable ceiling (256) when the ceiling is exposed as a runtime option — causes an allocation (violating P1) if a user raises polyphony after stream-open instead of at stream-open.
  • Voice age counter (age_samples) overflowing on a very long-running stream — must use a wide enough integer or a wraparound-safe comparison.

A bounded-cost modulation matrix routing named sources to named destinations through SmoothedParam, and a sample-accurate automation event queue integrated with the block scheduler.

  • Modulation-matrix route evaluation cost stays within the per-voice CPU budget (§4) at the maximum route ceiling, measured under 64-voice polyphony (M-series, §30).
  • A patch exceeding the route ceiling is rejected at commit with a typed error, 0 silent truncations across a fuzz corpus of over-budget patches.
  • LFO-to-audio-rate-destination routing (e.g. LFO modulating oscillator pitch at audio rate) measured alias energy still meets the §4 -80 dBFS floor (P2 applies even to modulation sources).
Fixtures
  • sample_accurate_automation.json — a filter-cutoff ParamEvent scheduled at sample 137 within a 256-sample block; expected: cutoff change measurable exactly at sample 137, not sample 0 or
  • mod_matrix_route_ceiling_fuzz.json — patches with route counts at, just under, and just over the ceiling; expected: accept/accept/reject respectively.
  • lfo_audio_rate_alias_check.wav — an LFO routed to oscillator pitch at an audio-rate depth; expected: alias floor ≤ -80 dBFS (§4).
  • mod_matrix_cpu_budget_64voice.json — measured route-evaluation CPU at max route ceiling, 64 voices; expected: within per-voice budget.
Pitfalls
  • Evaluating the modulation matrix per-sample instead of per-block (control-rate, ADR-10) — wastes CPU disproportionate to the (typically slow-moving) modulation sources' actual bandwidth.

  • Allowing an LFO's own rate to exceed what its destination's SmoothedParam time constant can track — produces an unintentionally attenuated or distorted modulation depth.
  • Treating route-ceiling rejection as a soft warning instead of a hard commit failure — silently drops user-authored routes, breaking the "what you patched is what plays" contract.

⬜ Phase 8 — Delay-Based Effects & FDN Reverb §20

Objectives
  • Implement DelayLine (audiolib.fx.delay) with feedback and modulated (interpolated) read position, for delay/chorus/flanger use.
  • Implement the feedback delay network reverb (audiolib.fx.fdn_reverb, ADR-07) with an orthogonal feedback matrix (Jot & Chaigne 1991), replacing the plain Schroeder comb/allpass topology as the locked choice.
  • Prove the FDN's stability condition (I9) via eigenvalue analysis of the feedback matrix.
Deliverable

DelayLine, FdnMatrix, and the FDN reverb node, plus chorus/flanger, all RT-safe and stability- proven per I9.

Acceptance
  • FDN feedback matrix spectral radius ≤1.0 for 100% of the exposed size/decay parameter grid (I9).
  • Reverb tail measured RT60 (decay time to -60 dB) matches the configured decay parameter within 10% across a grid of room-size settings, verified against reverb_rt60_measurement.json.
  • Modulated delay (chorus) alias/artifact energy from interpolation stays below -70 dBFS relative to the wet signal, verified against chorus_interpolation_artifact.wav.
  • 0 RT-path allocations across a 10-minute continuous reverb-tail render (I1).
Fixtures
  • reverb_impulse_response.wav — FDN reverb's response to a unit impulse; expected: RT60 within 10% of configured decay, no runaway growth (I9).
  • reverb_rt60_measurement.json — measured RT60 per room-size/decay setting; tolerance: 10%.
  • chorus_interpolation_artifact.wav — modulated delay at typical chorus rate/depth; expected: artifact energy ≤ -70 dBFS relative to wet signal.
  • fdn_matrix_eigenvalue_sweep.json — spectral radius per parameter grid point; tolerance: all entries ≤1.0.
Pitfalls
  • Choosing delay-line lengths that share common factors — causes audible resonant coloration (comb-filtering artifacts) rather than a smooth diffuse tail; delay lengths should be mutually-prime-adjacent per classic Schroeder/Freeverb-lineage tuning wisdom (Moorer 1979).
  • Letting a user-exposed "feedback" or "decay" parameter map directly to a raw matrix gain above the I9-proven-stable range — violates P12; must clamp before it ever reaches the matrix.
  • Denormals in the reverb's damping-filter feedback path during a long quiet tail — exactly the scenario P6/I6 targets; must be verified specifically here, not assumed covered by Phase 4's generic filter test.
  • Linear interpolation in the modulated delay line introduces its own (mild) high-frequency attenuation — documented as an accepted artifact (ADR-13-adjacent tradeoff), not a bug to chase away.

⬜ Phase 9 — Nonlinear Effects & Oversampling §21

Objectives
  • Implement waveshaping/tube-model distortion (audiolib.fx.distortion, Zölzer ch. 5) as the library's nonlinear-processing node family.
  • Implement polyphase oversampling (audiolib.fx.oversampler) as the antialiasing strategy for nonlinear nodes, whose harmonic generation is not analytically band-limitable the way oscillator discontinuities are (contrast with ADR-05's BLEP approach).
  • Quantify the oversampling factor's cost/alias-suppression tradeoff against the §4 floor.
Deliverable

A distortion/waveshaping node family with a measured, tunable oversampling factor meeting the §4 aliasing floor, plus a nonlinear diode-ladder filter option.

Acceptance
  • At 4x oversampling, measured alias energy from the distortion node stays ≤ -80 dBFS across MIDI notes 21-108 (§4 floor), verified against distortion_alias_by_oversampling.json.
  • At 1x (no oversampling), the same measurement must show a clearly worse floor (documenting the oversampling factor's necessity, P10 contrast methodology as in Phase 1/2).
  • DC-offset removal reduces measured DC component to ≤ -80 dBFS in the output, verified against distortion_dc_offset_regression.wav.
  • Diode-ladder filter's stability proof (pole/state-boundedness argument analogous to I2) covers its full exposed drive/resonance range.
Fixtures
  • distortion_alias_by_oversampling.json — measured alias energy at 1x/2x/4x oversampling per MIDI note; tolerance: 4x entries all ≤ -80 dBFS.
  • distortion_dc_offset_regression.wav — sustained-drive distortion output; expected: DC component ≤ -80 dBFS after high-pass removal.
  • ladder_filter_stability_sweep.json — diode-ladder filter output boundedness across its drive/resonance grid; tolerance: no unbounded growth at any grid point.
  • oversampling_cpu_cost.json — measured CPU cost at each oversampling factor; used to populate the §30 M-series entries for this phase.
Pitfalls
  • Assuming oversampling alone fixes all nonlinear-node aliasing without also verifying the anti-imaging low-pass filter's own quality — a cheap low-pass can reintroduce artifacts the oversampling was meant to remove.
  • DC offset accumulating silently through an asymmetric waveshaper and then compounding through a downstream feedback path (e.g. into the Phase 8 reverb) — must be caught at the distortion node's own output, not assumed to be filtered out later.
  • Running the diode-ladder filter's nonlinearity at the base sample rate without its own oversampling — a nonlinear filter aliases by the same mechanism as a waveshaper and needs the same treatment (this phase's ADR-05-adjacent lesson generalizes).
  • Treating oversampling factor as a free knob without accounting its added latency against the P13 budget — a 4x oversampled node's upsample/downsample filters add real, cumulative delay.

⬜ Phase 10 — MIDI Input & Real-Time Device Streaming §22

Objectives
  • Implement a strict MIDI 1.0 Detailed Specification-conformant parser (audiolib.midi.parser, ADR-11) including running status, plus a MIDI 2.0/UMP adapter (audiolib.midi.ump).
  • Implement the PortAudio callback stream binding (audiolib.io.stream, ADR-12) closing the loop from a physical device through to the graph built in Phases 0-9.
  • Enforce I11 (no NoteEvent from a malformed message) and I12 (legal stream-lifecycle transitions only).
Deliverable

End-to-end operation: a physical MIDI keyboard driving the polyphonic engine built in Phases 0-9, streaming through a real PortAudio device, with a fuzz-hardened parser and a guarded stream lifecycle.

Acceptance
  • Keyboard-to-sound latency ≤10 ms at the default block size (128 samples @48kHz), measured end-to-end (device-in to device-out), consistent with the §4 RT deadline budget.
  • MIDI parser fuzz corpus (§28): 100% of malformed inputs rejected without producing a spurious NoteEvent (I11), 0 crashes.
  • Stream lifecycle: 100% of a fuzz corpus of device-error injections (disconnect, buffer-size change mid-stream) result in a legal FSM transition, never an illegal state (I12).
  • RTO: stream recovers and resumes audio within 2 s of a simulated device error (§4, §26).
Fixtures
  • midi_running_status_valid.bin — a valid running-status Note On sequence; expected: correct NoteEvent sequence produced.
  • midi_malformed_corpus/ — a fuzz-generated set of malformed MIDI byte sequences (truncated messages, invalid status bytes, out-of-range pitch bend); expected: 0 spurious NoteEvents, 0 crashes (I11).
  • device_error_injection_fuzz.json — simulated device disconnects/buffer-size changes at random points; expected: 100% legal FSM transitions (I12).
  • keyboard_to_sound_latency.json — measured end-to-end latency across block-size configurations; tolerance: ≤10 ms at default block size.
Pitfalls
  • Losing running status across a non-MIDI byte (e.g. an active-sensing byte) interleaved in the stream — the MIDI 1.0 Detailed Specification defines exactly which bytes reset running status; getting this wrong causes intermittent stuck/ghost notes (a documented historical bug class).
  • MIDI clock drift relative to the audio sample clock — MIDI timestamps come from a different time source (OS scheduler wake time) than the audio callback's sample counter; naive 1:1 mapping accumulates drift over a long session.
  • Treating a device buffer-size change mid-stream as fatal instead of a legal FSM transition needing re-sizing of the (already-ceiling-sized, per Phase 0) arena — must not require a reallocation (P1).
  • A velocity-0 Note On (MIDI convention for Note Off) mishandled as a zero-velocity Note On instead of a Note Off — produces a stuck voice.

⬜ Phase 11 — Conformance Suite, Numeric-Regression Gating & Perf Hardening §23

Objectives
  • Consolidate every phase's differential/property/fuzz fixtures into a single gated conformance suite (conformance/, ADR-21/22/23).
  • Close the loop on I1 (zero-allocation) and I13 (offline/RT parity) as release-blocking, not just phase-local, gates.
  • Perf-harden the compiled kernel (SIMD-friendly reformulation, cache-locality pass) against the M-series targets (§30) established across Phases 1-9.
Deliverable

A release-gated conformance suite covering every invariant (I1-I14) and every phase's fixtures, a perf-hardened compiled kernel meeting all M-series targets, and a nightly soak/fault-injection pipeline.

Acceptance
  • 100% of aggregated N.5 fixtures pass in a single CI run; 0 regressions against any phase's recorded numeric baseline (I13, P10, P14).
  • Real-time-safety verification pass: 0 allocations across a 10-minute stress-patch render at max polyphony with all effect types active (I1).
  • Post-perf-hardening measurements meet or exceed 100% of the M-series targets (§30) — no target left un-met at release.
  • 24-hour soak test: 0 xruns, 0 NaN/Inf detections, denormal-flush count consistent with expected idle-tail behavior only (§4 dropout budget, I6, I10).
Fixtures
  • full_conformance_suite_manifest.json — the aggregated list of every N.5 fixture across Phases 0-10, tagged by invariant; expected: 100% pass.
  • rt_safety_stress_patch.json — max-polyphony, all-effects-active patch definition; expected: 0 allocations across a 10-minute render (I1).
  • perf_hardening_before_after.json — M-series measurements pre/post optimization; expected: 100% of targets met post-optimization.
  • soak_24h_regression.json — xrun/NaN/denormal counters across a 24-hour render; expected: 0 xruns, 0 NaN detections.
Pitfalls
  • Treating the conformance suite's aggregation as purely mechanical (concatenating fixture lists) without re-verifying that cross-phase interactions (e.g. Phase 9's distortion after Phase 8's reverb, per §21.9) are represented — the suite must include full-chain patches, not only per-node fixtures.
  • Applying a perf optimization (e.g. a SIMD reformulation of the TPT SVF) without re-running Phase 4's differential test against scipy.signal — a "faster" filter that quietly changes its numeric behavior violates P10/P14.
  • Letting the soak test's duration be shortened "to save CI time" — denormal creep and slow numeric drift are specifically the classes of bug that only manifest over long runs (§4 dropout budget is stated in 24-hour terms for this reason).
  • Gating only on mean-case perf numbers instead of tail latency (deadline-miss distribution) — a rare but real deadline miss is an xrun, and xruns are budgeted at near-zero (§4), not "rare enough on average."
