Project Name: Audio Synthesizer / DSP Library

1. Goal & Scope

This blueprint specifies a from-scratch, real-time-capable audio synthesis and digital signal processing (DSP) library in Python: band-limited oscillators (BLIT/minBLEP/PolyBLEP), ADSR envelopes with sample-accurate parameter smoothing, biquad and topology-preserving-transform (TPT) state-variable filters, a modular signal-graph engine that a scheduler evaluates block-at-a-time in topological order, polyphonic voice management with an explicit stealing policy, a fixed effects family (delay, FDN reverb, chorus, distortion) plus band-limited nonlinear processing via oversampling, MIDI 1.0/UMP input parsing, a sample-accurate parameter-automation and modulation-matrix system, and WAV/RIFF file plus PortAudio-callback stream I/O. The library is usable both as an offline renderer (deterministic, non-real-time, throughput-bound) and as the DSP core behind a real-time engine driven by a host audio callback (PortAudio/JACK/ALSA/CoreAudio contract); in the real-time path the callback thread performs zero heap allocation, takes no locks, and blocks on nothing — every buffer it needs was reserved before the stream opened. The three load-bearing engineering concerns threading every phase are: numerical correctness (aliasing suppressed by construction, filter poles proven inside the unit circle across the parameter range, denormals excluded from feedback paths), real-time safety (no allocation/lock/GC/syscall on the audio thread), and the block-processing/latency tradeoff (smaller blocks cut latency but shrink the real-time deadline and raise per-callback overhead).

Phase-0 deliverable, as packages:

  1. audiolib.core — SampleRate/BlockSize/AudioBuffer/ChannelLayout/RenderContext types and the block-processing contract.
  2. audiolib.rt — lock-free ring buffer, arena allocator, allocation-guard, compiled real-time kernel dispatch shim.
  3. audiolib.render — OfflineRenderer, RenderStats, deterministic non-RT render loop.
  4. audiolib.io — WAV/RIFF reader/writer, PortAudio stream binding stub.
  5. CI scaffold: lint + unit tests + allocation-tracing harness stub, benchmarks/ stub.

Boundaries. Provides: synthesis/DSP math, the graph engine, voice management, MIDI parsing, file I/O. Delegates: device I/O to PortAudio (a thin binding over its callback contract), FFT/BLAS primitives to NumPy/SciPy, plug-in hosting to nothing (not built). Does not provide: a DAW UI, a sequencer/timeline, a plug-in host, audio codec decoding (MP3/AAC/OGG — WAV only), network audio transport.

Non-goals. Not a DAW; not a plug-in host (VST3/CLAP are named target ABI surfaces for a future export shim, not built here); not a general audio editor; not a codec library.

Deployment model. (a) library — imported by a Python process; (b) offline renderer — batch process rendering a patch plus an automation timeline to a WAV file, throughput-bound, non-RT; (c) real-time engine — a long-lived process whose audio thread runs the callback contract, fed by MIDI/automation from a control thread via lock-free queues.

Users/operators. DSP engineers building instruments/effects; researchers needing a numerically-verifiable synthesis testbed; downstream authors of a plug-in shim or a game-audio integration (cross-ref: PROJECT 172 Game-Engine-Core consumes the offline-render and streaming APIs).

What later phases unlock. Phase 5 (graph) unlocks arbitrary patchable topologies; Phase 6 (voices) unlocks polyphony; Phase 7 (modulation) unlocks expressive automation; Phase 9 (oversampling) unlocks alias-free nonlinear effects; Phase 11 unlocks a numerically-gated release.

Python + numeric-core strategy. Python is chosen for the graph-construction/control layer (dynamic, fast to iterate, rich ecosystem — NumPy/SciPy for reference numerics, pytest for property/differential testing) while the sample-rate-critical inner loop is compiled ahead of time via a nopython-mode JIT kernel (or a Cython extension) into a real-time-safe function operating on pre-allocated NumPy buffers with no Python object creation, no reference-counting churn in the hot path, and no GIL reacquisition mid-block. This hybrid — Python for topology, compiled kernel for the sample loop — mirrors FAUST-generates-C++ and Csound's compiled-opcode model. Rejected: pure Python per-sample loops (interpreter overhead dwarfs the arithmetic and every attribute access risks allocation); pure C/C++ (the correct choice for a production plug-in binary, but rejected here to keep the numeric layer NumPy-interoperable and the prototyping loop fast); pure Rust (same rejection rationale — memory-safety benefits noted, not adopted); NumPy vectorization with no compiled kernel (acceptable in the offline renderer, unusable on the audio thread because block-at- a-time ufunc calls allocate temporaries per operation).

Prerequisites. Sampling theory and the Nyquist–Shannon criterion; complex analysis (poles/ zeros, the unit circle); the z-transform and transfer-function algebra; linear time-invariant (LTI) system theory; phase-accumulator trigonometry.

Timeline. Twelve phases (0–11), sequential, each gated by its own §N.4 acceptance criteria before the next opens; 2–4 weeks per phase for a single engineer part-time, compressible for a dedicated team.

2. Why Build This

  • Real-time systems discipline transfers beyond audio: zero-allocation hot paths, lock-free handoff, deadline-bound scheduling.
  • DSP mathematics is compact and testable: transfer functions, poles/zeros, and measured spectra give ground truth most domains lack.
  • Aliasing and filter stability are correctness bugs, not taste — training the instinct to prove bounds instead of eyeballing waveforms.
  • The Python-hybrid numeric-core pattern (interpreted topology + compiled kernel) generalizes to any latency-critical system embedded in a dynamic-language host.
  • Polyphonic voice management and modulation routing are a compact combinatorial-scheduling problem worth mastering independent of audio.
  • MIDI, WAV/RIFF, and the PortAudio callback contract are stable, well-specified interop surfaces — a rare chance to build against real specs instead of ad hoc formats.
  • The reference literature (Zavalishin, Smith, Zölzer, Bristow-Johnson) is unusually rigorous for an applied-engineering domain; reading it end to end is itself the payoff.

What Mastery Looks Like

  • Deriving and defending a biquad's pole locations analytically before ever running it (Phase 4).
  • Explaining, with a spectrum plot, why a naive sawtooth aliases and why PolyBLEP fixes it (Phase 2).
  • Reasoning correctly about a scheduler's topological-sort validity on an arbitrary patch graph (Phase 5).
  • Defending a voice-stealing policy's audible tradeoffs under CPU pressure (Phase 6).
  • Tracing a zipper-noise bug to an unsmoothed block-rate parameter update (Phase 7).
  • Proving zero audio-thread allocation with an instrumented allocator (Phase 0 and Phase 11).
  • Bounding a reverb's FDN stability via its feedback matrix's eigenvalues (Phase 8).
  • Quantifying oversampling's cost/alias-suppression tradeoff for a nonlinear waveshaper (Phase 9).

MIDI Parser: strict MIDI 1.0/UMP byte-stream parser (ADR-11) running on a control thread; turns raw bytes into NoteEvent/ParamEvent records pushed through the SPSC queue. Preset/Patch Loader: persistence boundary — reads/writes patch files and WAV assets, never touches the audio thread directly (ADR-17). Automation Editor: produces a ParamEvent stream ahead of render time; feeds the same queue as live MIDI. Offline Renderer: a separate, non-RT execution path sharing the compiled kernel with the RT path (P14/I13); bypasses the device entirely, writing WAV directly. SPSC ring buffers: the sole concurrency boundary between control and audio threads (P9); fixed capacity, backpressure policy per ADR-27. Audio Callback: the real-time boundary; everything below the "REAL-TIME BOUNDARY" line executes with zero allocation, no locks, no blocking syscalls (P1, I1). Block Scheduler: splits each callback's block at the sample offsets where queued events become due (§8 block-processing contract). Voice Allocator/Stealer: assigns incoming NoteEvents to Voice slots per the decision table in §8; enforces the click-free stealing guarantee (P8, I5). Signal Graph: the topologically-sorted DAG of Nodes (§8 interface table); per-voice subgraphs plus a global bus. Modulation Matrix: routes named sources to named destinations at a bounded route count (ADR-10). Global Effects Chain: post-mixdown delay/FDN-reverb/chorus/distortion, each RT-safe. Telemetry: a non-RT consumer thread draining the lock-free metrics/log queue (ADR-18/19/20), feeding dashboards (§26) without ever touching the RT thread's timing.

6. Design Principles

P1 — Zero-Allocation Audio Thread. The callback allocates nothing, locks nothing, waits for nothing. Tradeoff: every buffer is reserved at stream-open, sized for the worst case (max polyphony × max block size). Operational implication: every new node/voice/effect type must pre-declare its static memory footprint. Violation: a single dynamic append inside the callback risks a malloc-triggered page fault mid-block — an xrun.

P2 — Band-Limited by Construction. Every oscillator's discontinuity is corrected (BLIT/ minBLEP/PolyBLEP) before it reaches the graph. Tradeoff: correction costs a few extra flops per sample versus naive generation. Violation: naive saw/square aliases audibly, invisibly on a scope but obvious on a spectrogram — aliasing is not a quality issue, it is correctness.

P3 — Sample-Accurate or Explicitly Smoothed. Every parameter change either lands on an exact sample index or runs through a smoothing filter with a stated time constant. Tradeoff: smoothing adds latency-to-full-effect. Violation: a raw block-rate jump is a click, and a click is a bug.

P4 — Poles Proven, Not Assumed. Every filter design carries an explicit stability argument (pole-magnitude bound) valid across its full exposed parameter range, not just nominal settings. Tradeoff: TPT/SVF formulations cost more multiplies than direct-form biquads. Violation: a biquad computed near a Nyquist-adjacent cutoff in float32 can push a pole outside the unit circle silently.

P5 — The Graph is Acyclic Except Through an Explicit Delay. Feedback in the signal graph is legal only through a unit-delay node that breaks the same-block dependency cycle. Tradeoff: sample-accurate zero-delay feedback needs an implicit solver (TPT) or an explicit one-sample delay. Violation: an undeclared cycle makes topological sort undefined; the scheduler hangs or silently drops a node.

P6 — Denormals Never Reach a Feedback Path. Flush-to-zero/DAZ is enabled at stream-open and reverb/delay tails are monitored for denormal-range values. Tradeoff: FTZ changes bit-exact behavior at the noise floor (acceptable — below the aliasing/THD floor). Violation: an unflushed denormal in an IIR feedback loop can cost 100× the normal CPU on x86, silently degrading an idle reverb tail.

P7 — Block Processing is a Contract, Not an Implementation Detail. Every node produces identical output regardless of the host's block size, subject to its declared smoothing/latency parameters. Tradeoff: some algorithms (partitioned effects) must be written block-size-invariant deliberately. Violation: a node assuming a fixed block size silently corrupts output when the host changes buffer size mid-stream.

P8 — Voice Stealing Never Leaves a Discontinuity. A stolen voice is force-released over a fixed short ramp before reallocation, never truncated mid-waveform. Tradeoff: a few milliseconds of released-voice overlap CPU cost. Violation: an abrupt voice cutoff is an audible click on every dense chord.

P9 — Real-Time and Non-Real-Time Never Share Mutable State Directly. All cross-thread communication goes through lock-free SPSC queues or atomic pointer swaps of immutable snapshots. Tradeoff: control-thread changes are visible to the audio thread one block late. Violation: a shared mutable structure read on the audio thread while the control thread mutates it is a data race and a potential crash-class bug.

P10 — Numerical Correctness is Verified Against a Reference, Never by Ear. Every filter/ oscillator/effect ships a differential test against scipy.signal or an analytic formula with a stated tolerance. Tradeoff: building the reference harness costs real up-front engineering time. Violation: "it sounds fine" is not a regression gate — a subtle coefficient bug can pass casual listening and fail a decade later at an extreme parameter.

P11 — The Compiled Kernel is the Only Code That Runs on the Audio Thread. Python object code (graph construction, control logic) never executes in the callback; only the precompiled kernel does. Tradeoff: any new DSP algorithm must be written in the constrained subset the JIT/Cython can compile in nopython mode. Violation: falling back to interpreted object mode silently reintroduces the GIL and allocation the whole architecture exists to avoid.

P12 — Every Exposed Parameter is a Stability Claim. A filter's resonance, a reverb's feedback: each is bounded to the range where the P4 stability proof holds. Tradeoff: aggressive users lose access to true self-oscillation unless a separate, deliberate mode is provided. Violation: exposing raw feedback coefficients above the proven-stable range invites user-triggered blowups indistinguishable from a bug report.

P13 — Latency is a Budget, Not a Constant. Every added block of buffering (oversampling, partitioned processing, smoothing) is accounted against the declared latency budget (§4). Tradeoff: lower latency shrinks headroom for expensive per-block work. Violation: adding a lookahead stage without updating the latency budget breaks every downstream latency-compensation assumption.

P14 — Offline and Real-Time Renders Must Agree Within Tolerance. The offline renderer and the real-time engine share the same compiled kernel and must produce bit-exact or tolerance-bounded identical output for the same patch and event stream. Tradeoff: the offline renderer forgoes naive-NumPy-only vectorization speed to keep kernel parity. Violation: divergence between offline and real-time renders means the render used for mastering doesn't match what the live engine actually plays.

Debugging methodology. Every invariant above is exercised by a dedicated property or differential test in §28, wired to the phase's N.5 fixtures. 8. Domain Model

Sampling and the Nyquist criterion.

fs >= 2 * f_max                         (Nyquist–Shannon)
f_alias = min_k | f_true - k * fs |     (aliasing condition, k integer, result folded into [0, fs/2])

The z-transform and transfer functions (Oppenheim & Schafer ch. 2, 5).

X(z) = sum_{n=-inf}^{inf} x[n] * z^-n
H(z) = Y(z) / X(z) = (b0 + b1 z^-1 + b2 z^-2) / (1 + a1 z^-1 + a2 z^-2)
stable  <=>  all poles (roots of denominator) satisfy |z| < 1

Biquad coefficients (Bristow-Johnson Audio EQ Cookbook; low-pass shown, other types by the same reference table — high-pass, band-pass, notch, peaking, shelving each substitute the b/a numerator form for the same alpha/omega machinery).

omega0 = 2*pi*f0/fs ;  alpha = sin(omega0) / (2*Q)
LPF:  b0=(1-cos(omega0))/2, b1=1-cos(omega0), b2=b0
      a0=1+alpha,           a1=-2*cos(omega0), a2=1-alpha
normalize: b_i /= a0 ,  a_i /= a0   (applied in §16, ADR-06)

TPT / trapezoidal-integrator state-variable filter (Zavalishin 2012; Smith CCRMA TPT notes).

g  = tan(pi * fc / fs) ;  k = 1 / Q
v3 = x - ic2
v1 = (ic1 + g*v3) / (1 + g*(g+k))
v2 = ic2 + g*v1
ic1' = 2*v1 - ic1 ;  ic2' = 2*v2 - ic2
outputs: LP = v2 ,  BP = v1 ,  HP = x - k*v1 - v2

ADSR envelope segment equations.

Attack  (linear):    level[n] = level[n-1] + 1/N_A                      until level >= 1
Decay   (exp, tau_D): level[n] = sustain + (level[n-1]-sustain)*exp(-1/(tau_D*fs))
Sustain:             level[n] = sustain                                 while gate held
Release (exp, tau_R): level[n] = level[n-1] * exp(-1/(tau_R*fs))        until level < eps

Band-limited oscillator construction.

BLIT[n]   = (M/N) * sin(pi*M*n/N) / (M*sin(pi*n/N)) ,  M = 2*floor(fs/(2*f0)) + 1   (Stilson & Smith 1996)
Saw       = leaky_integrate(BLIT)
PolyBLEP correction, applied at the discontinuity, t in phase units, dt = phase increment:
  t < dt:        +=  t/dt + t/dt - (t/dt)^2 - 1
  t > 1-dt:      +=  ((t-1)/dt)^2 + (t-1)/dt + (t-1)/dt + 1
minBLEP: naive discontinuity convolved with a precomputed band-limited step residual (Brandt 2001)

FM/PM index and sidebands (Chowning 1973).

y[n] = A * sin(2*pi*fc*n/fs + I * sin(2*pi*fm*n/fs))
sideband amplitude at fc +/- k*fm  =  J_k(I)     (Bessel function of the first kind, order k)

FDN reverb stability condition (Jot & Chaigne 1991).

y[n] = A * x[n - m]          (per-line feedback through delay vector m)
stable  <=>  spectral_radius(A) <= 1     (enforced by an orthogonal/unitary A, gain-scaled < 1)

Parameter smoothing time constant.

y[n] = y[n-1] + (target - y[n-1]) / N_smooth ,   N_smooth ~= tau_ms * fs / 1000   (tau ~ 5-30 ms)

Node/graph interface (signatures in §11). Every node exposes process(ctx, inputs) -> outputs, static_size() -> bytes, reset(). process is called exactly once per block per node, in topological order; static_size is queried once at graph-commit time (P1); reset never allocates.

Block-processing contract. (1) a node's output for a given absolute sample range is independent of how that range was sliced into blocks (P7/I8); (2) internal phase/state persists across block boundaries; (3) a node never reads beyond the current block's declared inputs; (4) latency introduced by a node is declared and additive into the global budget (P13).

Voice-allocation and stealing policy (decision table).

Pool State Event Action Resulting Voice Count
≥1 voice Idle NoteOn assign Idle voice, start Attack active += 1
all voices busy, none matches note NoteOn steal oldest voice (ADR-08), force fast-release ramp (P8), reassign after ramp active unchanged (steal, not add)
a voice already plays this MIDI note NoteOn (same note) reuse that voice (legato fast path) active unchanged
voice in Release, level < epsilon (background) transition to Idle, return to free list active -= 1
NoteOff for a playing note NoteOff trigger Release on the matching voice active unchanged until Release completes
NoteOff for a note with no matching voice NoteOff no-op, log active unchanged

Modulation-matrix routing model. Sources: LFO1, LFO2, EnvelopeN, Velocity, ModWheel, Aftertouch. Destinations: oscillator pitch, filter cutoff, amplitude, pan. Each ModRoute is (source, destination, depth); the matrix is bounded to a fixed route ceiling per voice (§4 graph node ceiling divided across per-voice budget) so CPU cost is statically known (ADR-10).

Parameter-automation event record. ParamEvent { param_id, target_value, sample_index, curve_type }; curve_type in { step, linear, exponential-smoothed } (§11).

Worked example — biquad coefficients, cutoff 1000 Hz, Q=0.707, fs=48000 Hz (ADR-06, applied §16): omega0 = 2*pi*1000/48000 = 0.130900 rad; cos(omega0)=0.991445, sin(omega0)=0.130537; alpha = 0.130537/(2*0.707) = 0.092322; unnormalized b0=0.0042775, b1=0.008555, b2=0.0042775, a0=1.092322, a1=-1.98289, a2=0.907678; normalized by a0: b0=0.0039166, b1=0.0078332, b2=0.0039166, a1=-1.815483, a2=0.830958.

Worked example — aliasing from a naive sawtooth at f0=220 Hz, fs=48000 Hz (applied §13/§14): Nyquist = 24000 Hz; naive saw contains harmonics at k*220 Hz for all k with amplitude ~1/k; harmonics alias once k*220 > 24000, i.e. k > 109.09, so k>=110 folds. For k=110: true frequency 24200 Hz aliases to |24200-48000| = 23800 Hz at amplitude 20*log10(1/110) = -40.8 dB relative to the fundamental — already far above the -80 dBFS floor (§4), and the infinite sum over k>=110 accumulates further energy, demonstrating naive generation structurally violates the aliasing floor and motivating band-limited construction (P2).

Malformed-input examples (applied §22, §24, §28): MIDI running status — a Note On status byte followed by status-omitted data bytes for subsequent messages must retain the last status per the MIDI 1.0 Detailed Specification; a stream lacking an initial status byte is rejected (I11). Out-of-range pitch bend — a 14-bit value outside [0, 16383] is clamped and logged, never passed through raw. NaN in a feedback loop — a zero-Q biquad division or an ill-conditioned FDN matrix edit is caught by the isfinite guard (I10) before it poisons state.

Failure-path example. A patch commit introduces a cycle without an explicit delay node: the graph validator raises GraphCycleError at commit time, before the audio thread ever observes it; the previous valid graph snapshot remains active (the atomic snapshot swap never occurs, P9); the operator sees a rejected-commit log entry, not a runtime crash (I3).

13. Phase 1 — Naive Oscillators & the Measured Aliasing Baseline

13.1 Objectives

  • Implement naive sine/saw/square/triangle oscillators (audiolib.osc.naive) with no antialiasing (deliberately, as a measurement baseline).
  • Build the spectral measurement fixture that will quantify the aliasing floor for every later oscillator phase (§4 target).
  • Extend CI's numeric-regression job with the first real fixture.

13.2 Detailed Implementation Steps

  1. Implement phase-accumulator oscillators per §8 (naive, no BLEP correction), matching the Oscillator type (§11).
  2. Implement a spectral-measurement utility (via scipy.signal/librosa, non-RT, conformance/ only per ADR-01/ADR-21) computing per-harmonic dBFS relative to the fundamental.
  3. Render the worked-example case from §8 (naive sawtooth, f0=220 Hz, fs=48000 Hz) and confirm the predicted -40.8 dB alias component at 23800 Hz appears in the measured spectrum (P10).
  4. Sweep the full MIDI pitch range (notes 21-108) recording measured alias energy per note into alias_baseline.json — this is the number every later phase must beat.
  5. Wire the sweep into CI as a numeric-regression job (ADR-23) that fails if a future commit regresses band-limited oscillators back toward this baseline.

13.3 Deliverable

Naive oscillators for all five waveforms; a measured, recorded aliasing baseline across the full pitch range, establishing the "before" state that Phase 2 must improve on by ≥60 dB (§4 floor of -80 dBFS versus this baseline's typical -20 to -40 dBFS).

13.4 Acceptance Criteria

  • Measured alias energy for a naive sawtooth at A3 (220 Hz) matches the §8 worked calculation (-40.8 dB at 23800 Hz) within 0.5 dB.
  • alias_baseline.json contains one entry per MIDI note 21-108 with measured worst-harmonic dBFS.
  • THD+N of the naive sine oscillator (no discontinuity, so no aliasing) is ≤ -90 dB, confirming the measurement pipeline itself is not the source of noise (P10 sanity check).

13.5 Conformance Fixtures

  • naive_saw_a3.wav — naive sawtooth at 220 Hz, 1 s, 48 kHz; expected spectrum matches §8 worked example within 0.5 dB.
  • naive_square_c4.wav — naive square at 261.63 Hz; expected: alias components at odd harmonics above Nyquist.
  • alias_baseline.json — per-note worst-harmonic dBFS table; regression tolerance: none (this is the baseline, not a gate).
  • naive_sine_thd.wav — pure sine at 1 kHz; expected THD+N ≤ -90 dB (measurement-pipeline sanity).

13.6 Pitfalls

  • Measuring alias energy with a rectangular (unwindowed) FFT window, which itself introduces spectral leakage indistinguishable from aliasing — use a Hann window (§28).
  • Confusing the fundamental's own harmonic rolloff (1/k amplitude, expected) with true aliasing (frequency folding, the actual defect) — the worked example in §8 disambiguates the two.
  • Forgetting that naive triangle (via leaky integration of naive square) inherits the square's aliasing, not a separate lesser defect.

13.7 Performance Concerns

  • The naive oscillators are cheap (a handful of flops); this phase's cost is entirely in the offline measurement pipeline, which is explicitly non-RT and excluded from §4 budgets.

13.8 Edge Cases

  • f0 = 0 Hz (DC): oscillator must not divide by zero computing phase increment.
  • f0 above Nyquist (a MIDI note whose fundamental itself exceeds fs/2): must not crash; documented as an invalid-range input the graph should reject upstream (deferred validation to Phase 5).
  • Noise oscillator: "aliasing" is not meaningful (broadband already); the fixture set excludes it from the per-note sweep.

13.9 Failure Analysis

alias_baseline.json shows implausibly good numbers (e.g. -70 dB) for a naive oscillator: root cause, likely the measurement window is clipping the harmonic content (FFT size too small relative to fundamental period); debug method, re-run with a longer FFT and cross-check against the §8 closed-form prediction; detection signal, measured value contradicts the analytic worked example; recovery, fix the FFT sizing in the measurement utility, not the oscillator.

13.10 Operational Notes

  • alias_baseline.json is committed to conformance/ permanently — it is the historical control group future phases are measured against, not something to delete once Phase 2 lands.

14. Phase 2 — Band-Limited Oscillators (PolyBLEP / minBLEP)

14.1 Objectives

  • Replace naive discontinuities with PolyBLEP correction (default, ADR-05) and add minBLEP as an opt-in higher-fidelity path for hard-sync/FM-heavy patches.
  • Meet the §4 aliasing floor (≤ -80 dBFS) across the full MIDI pitch range.
  • Extend the differential-test suite to compare measured spectra against the Phase 1 baseline.

14.2 Detailed Implementation Steps

  1. Implement poly_blep(t, dt) per the §8 closed-form correction, applied at each oscillator's discontinuity (saw wrap, square up/down transition) per P2.
  2. Implement BLIT-based band-limited generation (Stilson & Smith 1996) as the reference the leaky-integrated sawtooth derives from (§8).
  3. Implement minBLEP (Brandt 2001): precompute the band-limited step residual table at graph-commit time (non-RT), convolve it into the naive discontinuity on the RT path using only pre-allocated buffers (P1).
  4. Re-run the Phase 1 pitch sweep with PolyBLEP and with minBLEP active; record both into alias_polyblep.json / alias_minblep.json.
  5. Add a differential test asserting every measured value in alias_polyblep.json is ≤ -80 dBFS and improves on the matching alias_baseline.json entry by ≥40 dB (I2-adjacent numeric gate, P10).

14.3 Deliverable

audiolib.osc.polyblep and audiolib.osc.minblep, both RT-safe (zero allocation after graph-commit), each passing the aliasing-floor gate across MIDI notes 21-108.

14.4 Acceptance Criteria

  • 100% of MIDI notes 21-108: measured worst-harmonic alias energy ≤ -80 dBFS for PolyBLEP saw and square (§4).
  • minBLEP path measured floor ≤ -90 dBFS on the same sweep (Brandt 2001's stated improvement over PolyBLEP).
  • CPU cost delta vs. naive oscillator (Phase 1): PolyBLEP ≤1.3×, minBLEP ≤3× (M-series target, §30).
  • Zero allocations measured on the RT path for both oscillator types (I1, allocation-tracing harness).

14.5 Conformance Fixtures

  • polyblep_saw_sweep.json — per-note alias energy, PolyBLEP saw, notes 21-108; tolerance: every entry ≤ -80 dBFS.
  • minblep_hardsync_c4.wav — hard-synced oscillator pair at C4 with minBLEP correction; expected: no audible zipper at the sync discontinuity, alias floor ≤ -90 dBFS.
  • polyblep_vs_naive_regression.json — paired comparison per note; tolerance: ≥40 dB improvement every entry.

14.6 Pitfalls

  • Applying poly_blep at the wrong phase-wrap boundary (off-by-one-sample) — silently reintroduces most of the aliasing while looking "corrected" on a casual listen.
  • minBLEP table precomputed at the wrong sample rate (tables are fs-dependent) — must be recomputed on sample-rate change, not cached globally across streams.
  • Applying BLEP correction twice (once per discontinuity type, accidentally on every sample) — distorts the waveform's DC/amplitude, not just its band-limiting.
  • Assuming PolyBLEP fixes triangle-wave aliasing — triangle is (leaky-integrated) square, so the correction must be applied to the square stage before integration, not after.

14.7 Performance Concerns

  • minBLEP's convolution-with-residual-table cost must stay within the per-voice CPU budget (§4, M-series §30); benchmark before enabling as default for all patches.
  • Table lookups (minBLEP residual, BLIT sinc) risk cache misses at high voice counts — keep tables small enough to stay resident (§4 memory-per-voice, I14).

14.8 Edge Cases

  • Extremely low fundamentals (sub-20 Hz, e.g. LFO-rate "oscillators" reused as audio sources): dt (phase increment) becomes very small, and PolyBLEP's correction window shrinks correspondingly — verify no divide-by-dt instability.
  • Hard sync at a ratio producing a discontinuity faster than one sample period — minBLEP table lookup index must clamp, not overflow.

14.9 Failure Analysis

A specific high note (e.g. MIDI 108) fails the -80 dBFS gate while lower notes pass: root cause, dt approaches 0.5 (phase increment near the block's Nyquist-relative limit) where PolyBLEP's polynomial approximation degrades; debug method, compare against the BLIT reference at the same pitch; detection signal, polyblep_saw_sweep.json entry for note 108 fails its threshold; recovery, fall back to minBLEP or reduce the maximum playable fundamental for PolyBLEP-only patches, documented as a known tradeoff (ADR-05).

14.10 Operational Notes

  • The Phase 1 naive oscillators remain in the codebase permanently as the control group for alias_baseline.json regression comparisons (§13.10) — never deleted once Phase 2 lands.

15. Phase 3 — Envelopes & Parameter Smoothing

15.1 Objectives

  • Implement the ADSR state machine (audiolib.env.adsr) per the §8 segment equations.
  • Implement SmoothedParam (audiolib.env.smoothing) as the mandatory path for every non- sample-accurate parameter change (P3, ADR-09).
  • Establish the zipper-noise differential test that gates every future node exposing a runtime parameter.

15.2 Detailed Implementation Steps

  1. Implement the EnvelopeStage state machine per §8: Idle -> Attack -> Decay -> Sustain -> Release -> Idle, using the exponential decay/release equations (linear attack, per §8).
  2. Implement SmoothedParam.next() per the one-pole exponential update in §8, with smoothing_samples derived from a configurable tau_ms (typical 5-30 ms, ADR-09).
  3. Wire EnvelopeParams as an immutable per-voice-type config (§11), loaded at patch-commit, never mutated on the RT thread mid-note.
  4. Implement the zipper-noise differential test: apply a step change to a smoothed parameter, measure the output derivative's discontinuity against a dB tolerance (I7).
  5. Implement the envelope-continuity property test: assert level[n] is continuous (no jump exceeding one sample's maximum possible slope) across every stage transition, including NoteOff arriving mid-Attack or mid-Decay (§8 malformed/edge transition).

15.3 Deliverable

EnvelopeParams/EnvelopeStage driving per-voice amplitude/filter-cutoff envelopes; SmoothedParam available to every node exposing a runtime-changeable parameter, both zero- allocation on the RT path.

15.4 Acceptance Criteria

  • Envelope output continuity: max sample-to-sample delta at any stage transition ≤ the theoretical single-sample slope bound, verified across 100% of a NoteOn/NoteOff fuzz corpus (I7-adjacent).
  • Zipper-noise test: a step parameter change through SmoothedParam (tau=20 ms) produces no spectral component >-60 dBFS at the step-repetition frequency, versus a raw (unsmoothed) jump which must measurably fail the same test (regression contrast, P10).
  • Release-to-Idle transition reaches exactly 0.0 (not just "small") within release_samples × 1.2, confirmed against envelope_release_zero.json.
  • Zero RT-path allocations across a full ADSR cycle (I1).

15.5 Conformance Fixtures

  • adsr_full_cycle_c4.wav — a single note through Attack/Decay/Sustain/Release at defined parameters; expected level trace matches §8 equations within 1e-4 relative tolerance.
  • envelope_early_release.wav — NoteOff arriving mid-Attack; expected: smooth transition into Release from the current level, not a jump to sustain first (§8 decision, documented).
  • zipper_noise_stepped_cutoff.wav — raw step change to filter cutoff (unsmoothed control case); expected: FAILS the -60 dBFS zipper gate, proving the test detects the defect it's meant to catch.
  • smoothed_cutoff_sweep.wav — same change routed through SmoothedParam; expected: PASSES the same gate.

15.6 Pitfalls

  • Resetting envelope state to exactly 0 on retrigger instead of ramping down from the current level first — produces an audible click on rapid retriggers (a documented, deliberate choice point per §8; this blueprint locks "ramp from current level").
  • Choosing tau_ms too large (>100 ms) — smoothing itself becomes audible as "filter lag," feeling unresponsive; too small (<2 ms) barely helps zipper noise at all.
  • Applying the exponential release formula with a tau_R in samples rather than seconds-times- fs, silently changing perceived release time when sample rate changes (I8-adjacent).
  • Sharing one SmoothedParam instance across multiple voices when the parameter is meant to be per-voice — causes cross-voice zipper artifacts under polyphony.

15.7 Performance Concerns

  • SmoothedParam.next() runs once per sample per exposed parameter per voice; at 64-voice polyphony with several smoothed parameters per voice this must stay within the per-voice CPU budget (§4) — benchmark against M-series targets (§30).

15.8 Edge Cases

  • sustain_level set to 0: Decay must reach silence and the voice must still respond to NoteOff correctly (transitions straight toward Release's already-zero level).
  • Extremely fast attack (attack_samples = 1): must not divide by zero or produce a single-sample discontinuity exceeding I7's slope bound.
  • Parameter target changed twice within one smoothing window: SmoothedParam.set() must simply retarget, not stack or double-apply the exponential curve.

15.9 Failure Analysis

A patch exhibits an audible click exactly at Decay-to-Sustain transitions under heavy modulation: root cause, the Decay segment's exponential formula asymptotically approaches but never exactly equals sustain_level, and a naive equality check on the transition condition never fires, leaving the envelope stuck fractionally above sustain; debug method, replace equality with an epsilon-bounded comparison and re-run adsr_full_cycle_c4.wav; detection signal, envelope continuity property test flags a non-monotonic tail; recovery, patch the comparison, add a regression fixture for the specific parameter combination that exposed it.

15.10 Operational Notes

  • SmoothedParam becomes the mandatory contract (P3) for every subsequent phase's exposed parameters — Phase 4 onward must not introduce a new unsmoothed runtime parameter without an explicit, documented exception.

16.1 Objectives

  • Implement direct-form biquads (audiolib.filters.biquad) using the RBJ cookbook formulas (Bristow-Johnson; §8) for low-pass, high-pass, band-pass, notch, peaking, and shelving.
  • Implement the TPT/zero-delay-feedback state-variable filter (audiolib.filters.svf_tpt, Zavalishin 2012) for every modulatable filter use (ADR-06).
  • Produce a machine-checked stability proof (pole-magnitude sweep) covering the full exposed parameter range for both filter types (P4, I2).

16.2 Detailed Implementation Steps

  1. Implement biquad_coeffs() per the §8 cookbook formulas, validated against the §8 worked example (cutoff 1000 Hz, Q=0.707, fs=48000 Hz) to 1e-5 tolerance.
  2. Implement the TPT SVF per §8's trapezoidal-integrator equations, exposing LP/BP/HP outputs simultaneously from one state pair (ic1, ic2).
  3. Implement a differential test against scipy.signal.freqz: for a grid of (cutoff, Q) pairs, compare the biquad's measured magnitude response to the analytic transfer function within a stated dB tolerance (P10, ADR-21).
  4. Implement the pole-magnitude sweep (I2): for every (cutoff, resonance) pair on a fine grid across the full exposed range, compute pole locations and assert |pole| < 1.0.
  5. Implement resonance clamping (P12) at the boundary where self-oscillation becomes numerically marginal, per Zavalishin's stated safe range for the TPT SVF.
  6. Implement denormal handling (P6/ADR-13): enable FTZ/DAZ at stream-open; add the denormal-tail test fixture feeding a decaying filter through a long silent period.

16.3 Deliverable

BiquadCoeffs/FilterState and the TPT SVF, both RT-safe, both differentially validated against scipy.signal, both carrying a machine-checked stability proof across their full parameter range.

16.4 Acceptance Criteria

  • Biquad magnitude response matches scipy.signal.freqz within 0.1 dB across 100 (cutoff, Q) grid points spanning 20 Hz-20 kHz and Q in [0.5, 10] (P10).
  • TPT SVF pole magnitude |pole| < 1.0 for 100% of a grid of cutoff in (0, 0.4999·fs) × resonance in [0, 1) (I2, §4).
  • CPU cost per filter-sample: biquad ≤5 ns, TPT SVF ≤8 ns on reference hardware (M-series, §30).
  • Denormal-tail fixture: CPU-per-block does not exceed 1.5× nominal cost during a 10 s silent decay tail with FTZ/DAZ enabled (I6).

16.5 Conformance Fixtures

  • biquad_lpf_1khz_q0707.json — coefficients from the §8 worked example; expected values within 1e-5.
  • filter_freqz_differential.json — measured vs. analytic magnitude response, 100 grid points; tolerance: 0.1 dB.
  • svf_pole_sweep.json — pole magnitude per (cutoff, resonance) grid point; tolerance: all entries <1.0.
  • denormal_tail_reverb_input.wav — a decaying sine feeding into a filter's feedback path; expected: no CPU spike after amplitude drops below denormal range.
  • svf_self_oscillation_boundary.wav — resonance swept to the documented clamp boundary; expected: bounded output amplitude, no runaway growth.

16.6 Pitfalls

  • Computing biquad coefficients in float32 near very low cutoffs (sub-100 Hz) — coefficients cluster near 1.0, losing precision (§8); mitigate with float64 coefficient computation (ADR-02).
  • Modulating a direct-form biquad's coefficients per-sample — computationally expensive and introduces transients; this is exactly why TPT SVF exists for modulated use (ADR-06) — do not retrofit smooth modulation onto biquads instead.
  • Filter self-oscillation at extreme Q/resonance producing a musically "correct" but system- dangerous sine at full amplitude — must be bounded by P12's clamp, not left to the limiter alone.
  • Forgetting to pre-warm filter state (feeding silence before audible input) — causes an audible transient/overshoot at note start from zero initial state.

16.7 Performance Concerns

  • Filters run once per voice per sample at 64-voice polyphony — the dominant per-voice CPU cost alongside oscillators (§4 CPU-budget-per-voice); SIMD-friendly reformulation is deferred to Phase 11 perf hardening.
  • Coefficient recomputation (on cutoff/resonance change) is more expensive than per-sample processing — recompute at control rate (block-rate), not per-sample, unless modulation demands otherwise (P13 latency/cost tradeoff).

16.8 Edge Cases

  • Cutoff requested above 0.4999·fs (near-Nyquist): must clamp, not let tan() in the TPT formulation approach its pole at π/2.
  • Q or resonance requested at exactly the stability boundary: I2's sweep must include the boundary point itself, not just interior samples.
  • A filter with zero input for an extended period (silence): I6's denormal guard must engage before CPU cost rises, not after.

16.9 Failure Analysis

A biquad passes the differential test at coarse Q values but fails at Q=10 near 8 kHz cutoff: root cause, float32 coefficient precision loss compounds at high-Q/high-frequency combinations; debug method, recompute the same coefficients in float64 and compare; detection signal, filter_freqz_differential.json shows a magnitude-response tolerance breach isolated to that grid region; recovery, promote coefficient computation to float64 for the affected range (ADR-02), re-run the full grid.

16.10 Operational Notes

  • The pole-magnitude sweep (svf_pole_sweep.json) is re-run on every commit touching filters/ (ADR-23 numeric-regression gate) — it is the single highest-value automated check in this phase given P4's centrality.

17. Phase 5 — Signal Graph & Topological Scheduling

17.1 Objectives

  • Implement Graph/Node/Port/Connection (§11) and the topological-sort scheduler (audiolib.graph.scheduler, ADR-04).
  • Enforce graph acyclicity except through an explicit unit-delay node (P5, I3).
  • Prove the block-processing contract (P7/I8) holds across arbitrary graphs and arbitrary block sizes.

17.2 Detailed Implementation Steps

  1. Implement Graph.validate_acyclic() (I3): a DFS-based cycle detector run at patch-commit time, raising GraphCycleError before any snapshot swap to the audio thread (P9).
  2. Implement the topological-sort scheduler (ADR-04, referencing SuperCollider's UGen calc-rate dispatch as the model for audio-vs-mod rate separation, §5 ref-impl 1): compute topo_order once per commit, iterate it once per block on the RT thread.
  3. Implement the explicit unit-delay node as the sole legal feedback-breaking primitive (P5); graphs requiring true zero-delay feedback instead route through a TPT-style implicit solver node (documented exception, cross-ref Phase 4).
  4. Implement the block-size-invariance property test (I8): render the same patch at each supported block size (§4) and assert output matches within tolerance regardless of slicing.
  5. Implement the atomic graph-snapshot swap (P9, ADR-15): the control thread builds a new Graph, validates it, and swaps an atomic pointer the audio thread reads at the next block boundary — never mutating the live graph in place.

17.3 Deliverable

A committable, validated Graph with a precomputed topological order, an RT-safe scheduler iterating it per block, and a proven block-size-invariance guarantee.

17.4 Acceptance Criteria

  • 100% of a fuzz corpus of randomly generated cyclic graphs (without an explicit delay node) are rejected at commit with GraphCycleError, zero false negatives (I3).
  • Block-size-invariance test: an 11-node reference patch rendered at 64/128/256/512/1024-sample blocks produces output identical within 1e-6 RMS difference across all five (I8).
  • Graph commit-to-snapshot-swap latency ≤1 audio block at the default block size (P13 latency budget).
  • Scheduler iterates a 4096-node graph (§4 ceiling) within the per-block deadline at the default block size, measured on reference hardware (M-series, §30).

17.5 Conformance Fixtures

  • cyclic_graph_no_delay.json — a patch graph with an undeclared cycle; expected: GraphCycleError at commit.
  • cyclic_graph_with_delay.json — the same topology but routed through an explicit unit-delay node; expected: commit succeeds.
  • block_size_invariance_reference_patch.json — an 11-node patch (oscillator, envelope, filter, delay, mixer); expected: identical output across all five supported block sizes within tolerance.
  • graph_4096_node_stress.json — a synthetic graph at the node-count ceiling; expected: scheduler completes within the per-block deadline.

17.6 Pitfalls

  • Recomputing topo_order on the audio thread instead of only at commit time — reintroduces allocation/compute risk into the RT path (violates P1).
  • A cycle detector that misses a cycle spanning both audio-rate and mod-rate connections (two different ConnectionTypes forming one logical cycle) — must validate the union of both edge kinds, not each independently.
  • Mutating a live (already-swapped) graph's node list in place from the control thread — violates P9 and can race with the RT thread mid-block.
  • Treating the unit-delay node as "free" — it still consumes a static buffer slot and must be counted against the node-count ceiling (§4).

17.7 Performance Concerns

  • Topological sort cost is amortized (once per commit, not per block, ADR-04) — but commit frequency under a "live-patching" workflow (frequent graph edits) must stay off the RT thread's critical path entirely (P9).
  • Cache locality of nodes/topo_order iteration matters at high node counts (§4 ceiling) — contiguous array-of-structs layout preferred over a pointer-chasing dict for the hot iteration (deferred detailed tuning to Phase 11).

17.8 Edge Cases

  • An empty graph (no nodes): scheduler must produce silence, not raise.
  • A graph with exactly one node (the output sink) and no sources: must render silence, not divide-by-zero on an empty topo_order.
  • A disconnected subgraph (nodes with no path to the output sink): must still be scheduled (for side effects like telemetry) but its output must not leak into the mix uninvited — documented as a validation warning, not an error.

17.9 Failure Analysis

A patch with a delay-based feedback loop (delay + filter + sum-back) intermittently produces runaway output only under certain block sizes: root cause, the unit-delay node's declared latency (exactly one block versus one sample) was mismatched against what the topology assumed, letting a same-block read-before-write race occur at particular slicing boundaries; debug method, reproduce under the offline renderer at the failing block size (P10), trace RenderStats per node; detection signal, block_size_invariance_reference_patch.json fails only at block size 64; recovery, correct the unit-delay node's declared latency semantics (one sample, not one block) and re-run I8's sweep.

17.10 Operational Notes

  • Every subsequent phase's new node types (filters already built in Phase 4, voices/effects/ modulation still to come) must be added to block_size_invariance_reference_patch.json's coverage before that phase closes, keeping I8 a living, growing gate.

18.2 Detailed Implementation Steps

  1. Implement the static Voice array (struct-of-arrays layout, ADR-15) sized at stream-open to the configured max polyphony (§4 default 64, ceiling 256).
  2. Implement VoiceAllocator.allocate()/.steal()/.release() per the §8 decision table: free-voice-first, oldest-first stealing, same-note reuse.
  3. Implement the mandatory fast-release ramp (P8): a stolen voice's envelope is force-transitioned into a short (e.g. 5-10 ms) Release before reallocation, never truncated to zero directly.
  4. Implement the waveform-continuity differential test (I5): compare the sample-level output around a steal event against a reference expected ramp shape, asserting no discontinuity exceeding the single-sample slope bound (cross-ref Phase 3's I7 methodology).
  5. Implement per-voice key-tracking (filter cutoff scaled by note frequency) and per-voice LFU phase, per Pirkle's voice-management structuring (§5 ref-impl 4).

18.3 Deliverable

A polyphonic voice pool with proven click-free stealing under sustained note pressure, its static memory footprint verified against the §4/I14 budget.

18.4 Acceptance Criteria

  • Voice-steal waveform-continuity test: 0 discontinuities exceeding the slope bound across a fuzz corpus of 10,000 randomly-timed steal events (I5).
  • Static Voice array memory: ≤4096 bytes/voice × configured polyphony, verified by build-time size assertion (I14, §4).
  • Same-note NoteOn (legato reuse) never allocates a new voice when an exact match exists, verified by allocator unit tests (ADR-08).
  • 64-voice dense-chord stress test (dense_chord_64voice.wav) sustains 0 xruns over a 10-minute render at the default block size (§4 dropout budget).

18.5 Conformance Fixtures

  • voice_steal_fuzz_corpus.json — 10,000 randomly-timed NoteOn events against a fixed 8-voice pool; expected: 0 continuity violations at steal boundaries.
  • dense_chord_64voice.wav — a sustained 64-note chord at max default polyphony; expected: 0 xruns, CPU within the per-voice budget × 64 (§4).
  • legato_same_note_reuse.json — repeated NoteOn for an already-playing note; expected: voice count never exceeds the number of distinct notes played.
  • voice_memory_static_assertion.json — build-time size check output; expected: ≤4096 bytes/voice.

18.6 Pitfalls

  • Stealing "the quietest" instead of "the oldest" without updating ADR-08's documented rationale — a silent policy drift that breaks the predictability guarantee the ADR argues for.
  • Applying the fast-release ramp only to amplitude and forgetting the filter's key-tracked state — a voice can click at steal time if its filter state jumps discontinuously even while amplitude ramps smoothly.
  • Sizing the voice array to the default polyphony (64) instead of the configurable ceiling (256) when the ceiling is exposed as a runtime option — causes an allocation (violating P1) if a user raises polyphony after stream-open instead of at stream-open.
  • Voice age counter (age_samples) overflowing on a very long-running stream — must use a wide enough integer or a wraparound-safe comparison.

18.7 Performance Concerns

  • Voice allocation/stealing decisions must be O(1) or O(log N) (age-ordered free list or heap), never a full O(N) scan per NoteOn at high polyphony, to stay within the per-block scheduling overhead budget (§4).
  • Per-voice CPU cost (oscillator + filter + envelope, Phases 1-4 combined) must be re-measured under full 64-voice polyphony, not just single-voice, to catch cache-pressure effects invisible at N=1 (§30 M-series).

18.8 Edge Cases

  • All voices simultaneously receive NoteOff at the same sample (chord release): every voice's Release must start on the same sample index, not staggered by scheduling artifacts.
  • A steal request arrives for a voice that is itself already mid-steal (double-steal, §8 FSM failure edge): must no-op and log, not double-apply the fast-release ramp.
  • Max-polyphony configured to 1 (monophonic mode): allocator must degrade gracefully to single-voice behavior without special-casing bugs.

18.9 Failure Analysis

Dense chords occasionally produce an audible click despite the fast-release ramp passing its isolated unit test: root cause, two steals happening in the same block target voices whose ramps overlap the same output samples, and the summed ramp-out plus ramp-in transient exceeds the per-sample slope bound only in combination; debug method, reproduce with the exact NoteOn/NoteOff timing from the failing take under the offline renderer, inspect summed output around the steal boundary; detection signal, dense_chord_64voice.wav's spectral analysis shows an unexpected transient not present in the single-steal fixture; recovery, stagger simultaneous steals across consecutive samples within the block, or extend the ramp length, re-run I5's fuzz corpus.

18.10 Operational Notes

  • voice_steal_fuzz_corpus.json grows every time a new steal-adjacent bug is found (§18.9 pattern) — treat it as a living regression corpus, not a fixed-size fixture.

19.7 Performance Concerns

  • Route evaluation cost scales with voices × routes_per_voice; at 64 voices and a route ceiling sized to the graph-node budget (§4), this must be profiled distinctly from oscillator/filter cost (§30 M-series breakdown).

19.8 Edge Cases

  • Two ParamEvents targeting the same ParamId within the same block: must apply in sample_index order, not commit-order or arrival-order.
  • A modulation route whose depth is set to exactly 0: must still be evaluated (for consistency of CPU-cost accounting) but must produce no measurable effect on the destination.
  • An LFO with a rate of 0 Hz (effectively DC modulation): must not divide by zero in its phase increment computation (cross-ref Phase 1 edge case).

19.9 Failure Analysis

A patch with a fast LFO modulating filter cutoff produces audible zipper noise despite routing through SmoothedParam: root cause, the modulation matrix evaluates at block-rate (once per block) and the LFO's rate is fast enough that its value changes significantly between evaluations, so the block-rate-sampled target itself is the discontinuity, not the smoother; debug method, compare a block-rate-evaluated trace against a hypothetical per-sample-evaluated trace at the same LFO rate; detection signal, lfo_audio_rate_alias_check.wav's zipper-noise measurement (Phase 3 methodology) fails at LFO rates above a measured threshold; recovery, document the block-rate modulation bandwidth limit explicitly (a P13-style budget) and recommend audio-rate routing (bullet 19.2.2) for LFO rates exceeding it.

  • The modulation-matrix route ceiling and per-voice CPU budget must be re-validated every time a new destination type is added in a later phase (effects parameters in Phase 8/9) — treat §4's graph-node ceiling as the single source of truth, not a per-phase local assumption.

20. Phase 8 — Delay-Based Effects & FDN Reverb

20.1 Objectives

  • Implement DelayLine (audiolib.fx.delay) with feedback and modulated (interpolated) read position, for delay/chorus/flanger use.
  • Implement the feedback delay network reverb (audiolib.fx.fdn_reverb, ADR-07) with an orthogonal feedback matrix (Jot & Chaigne 1991), replacing the plain Schroeder comb/allpass topology as the locked choice.
  • Prove the FDN's stability condition (I9) via eigenvalue analysis of the feedback matrix.

20.2 Detailed Implementation Steps

  1. Implement DelayLine as a static ring buffer (ADR-15) with linear-interpolated fractional-delay reads for modulation (chorus/vibrato use), citing Zölzer ch. 4 for the interpolation-artifact tradeoff (§5).
  2. Implement FdnMatrix construction (§8): build an orthogonal/unitary matrix (e.g. a Hadamard-derived construction) scaled by a per-line gain <1, per Jot & Chaigne 1991's stability condition.
  3. Implement the FDN reverb node combining N delay lines through the feedback matrix, with per-line damping filters (citing Moorer 1979's practical refinements over the plain Schroeder topology, §5).
  4. Implement the eigenvalue-magnitude unit test (I9): compute the feedback matrix's spectral radius and assert ≤1.0 across every exposed size-decay parameter combination.
  5. Implement chorus/flanger (audiolib.fx.chorus) as a modulated DelayLine (LFO-driven read position, reusing Phase 2's band-limited LFO where its rate risks folding into audible modulation artifacts, cross-ref Phase 7).

20.3 Deliverable

DelayLine, FdnMatrix, and the FDN reverb node, plus chorus/flanger, all RT-safe and stability- proven per I9.

20.4 Acceptance Criteria

  • FDN feedback matrix spectral radius ≤1.0 for 100% of the exposed size/decay parameter grid (I9).
  • Reverb tail measured RT60 (decay time to -60 dB) matches the configured decay parameter within 10% across a grid of room-size settings, verified against reverb_rt60_measurement.json.
  • Modulated delay (chorus) alias/artifact energy from interpolation stays below -70 dBFS relative to the wet signal, verified against chorus_interpolation_artifact.wav.
  • 0 RT-path allocations across a 10-minute continuous reverb-tail render (I1).

20.5 Conformance Fixtures

  • reverb_impulse_response.wav — FDN reverb's response to a unit impulse; expected: RT60 within 10% of configured decay, no runaway growth (I9).
  • reverb_rt60_measurement.json — measured RT60 per room-size/decay setting; tolerance: 10%.
  • chorus_interpolation_artifact.wav — modulated delay at typical chorus rate/depth; expected: artifact energy ≤ -70 dBFS relative to wet signal.
  • fdn_matrix_eigenvalue_sweep.json — spectral radius per parameter grid point; tolerance: all entries ≤1.0.

20.6 Pitfalls

  • Choosing delay-line lengths that share common factors — causes audible resonant coloration (comb-filtering artifacts) rather than a smooth diffuse tail; delay lengths should be mutually-prime-adjacent per classic Schroeder/Freeverb-lineage tuning wisdom (Moorer 1979).
  • Letting a user-exposed "feedback" or "decay" parameter map directly to a raw matrix gain above the I9-proven-stable range — violates P12; must clamp before it ever reaches the matrix.
  • Denormals in the reverb's damping-filter feedback path during a long quiet tail — exactly the scenario P6/I6 targets; must be verified specifically here, not assumed covered by Phase 4's generic filter test.
  • Linear interpolation in the modulated delay line introduces its own (mild) high-frequency attenuation — documented as an accepted artifact (ADR-13-adjacent tradeoff), not a bug to chase away.

20.7 Performance Concerns

  • The reverb is typically the single most expensive node in a patch's effects chain (many multiply-accumulates per sample across N delay lines) — must be profiled explicitly and budgeted separately from per-voice costs in §30's M-series (it runs on the global bus, not per-voice).
  • Fractional-delay interpolation cost multiplies by the number of modulated taps (chorus voices) — bound the maximum chorus voice count against the global-bus CPU budget.

20.8 Edge Cases

  • Reverb decay parameter set to produce a spectral radius approaching exactly 1.0 (the stability boundary): I9's sweep must include this boundary point, not just safely-interior values.
  • Delay time modulated to sweep through zero or negative effective delay (LFO depth exceeding base delay time): must clamp the read position, never wrap negative into undefined buffer indices.
  • FDN reverb receiving a NaN-poisoned input from an upstream node: I10's finite-value guard must catch it before it enters the feedback matrix, not after it has already propagated through N delay lines.

20.9 Failure Analysis

A reverb tail that should decay smoothly instead exhibits a slowly growing metallic ringing at a specific room-size setting: root cause, the feedback matrix's per-line gain scaling was computed from the decay parameter using a formula that, at that specific size/decay combination, pushed the effective spectral radius fractionally above 1.0 due to a rounding step in gain computation (missed by the coarse original test grid); debug method, compute the matrix's eigenvalues directly at the failing setting and compare against the I9 threshold; detection signal, RT60 measurement diverges upward over a long render instead of converging; recovery, tighten the gain-computation formula's safety margin and add the specific failing setting to fdn_matrix_eigenvalue_sweep.json as a permanent regression point.

20.10 Operational Notes

  • Reverb parameters (docs/runbooks/) should ship a documented safe range separate from the raw matrix-gain internals, so patch authors never need to reason about spectral radii directly — the clamp (P12) is the interface.

21.1 Objectives

  • Implement waveshaping/tube-model distortion (audiolib.fx.distortion, Zölzer ch. 5) as the library's nonlinear-processing node family.
  • Implement polyphase oversampling (audiolib.fx.oversampler) as the antialiasing strategy for nonlinear nodes, whose harmonic generation is not analytically band-limitable the way oscillator discontinuities are (contrast with ADR-05's BLEP approach).

  4. Implement DC-offset detection/removal (a high-pass at ~5 Hz in the output chain) addressing the nonlinearity's tendency to introduce a DC component (a named pitfall class, §21.6).
  5. Implement the diode-ladder nonlinear filter (audiolib.filters.ladder, Yeh/Abel/Smith 2010) as an additional nonlinear-filter option, distinct from the linear TPT SVF (Phase 4), carrying its own (separately proven) stability argument.

21.3 Deliverable

A distortion/waveshaping node family with a measured, tunable oversampling factor meeting the §4 aliasing floor, plus a nonlinear diode-ladder filter option.

21.4 Acceptance Criteria

  • At 4x oversampling, measured alias energy from the distortion node stays ≤ -80 dBFS across MIDI notes 21-108 (§4 floor), verified against distortion_alias_by_oversampling.json.
  • At 1x (no oversampling), the same measurement must show a clearly worse floor (documenting the oversampling factor's necessity, P10 contrast methodology as in Phase 1/2).
  • DC-offset removal reduces measured DC component to ≤ -80 dBFS in the output, verified against distortion_dc_offset_regression.wav.
  • Diode-ladder filter's stability proof (pole/state-boundedness argument analogous to I2) covers its full exposed drive/resonance range.

21.5 Conformance Fixtures

  • distortion_alias_by_oversampling.json — measured alias energy at 1x/2x/4x oversampling per MIDI note; tolerance: 4x entries all ≤ -80 dBFS.
  • distortion_dc_offset_regression.wav — sustained-drive distortion output; expected: DC component ≤ -80 dBFS after high-pass removal.
  • ladder_filter_stability_sweep.json — diode-ladder filter output boundedness across its drive/resonance grid; tolerance: no unbounded growth at any grid point.
  • oversampling_cpu_cost.json — measured CPU cost at each oversampling factor; used to populate the §30 M-series entries for this phase.

21.6 Pitfalls

  • Assuming oversampling alone fixes all nonlinear-node aliasing without also verifying the anti-imaging low-pass filter's own quality — a cheap low-pass can reintroduce artifacts the oversampling was meant to remove.
  • DC offset accumulating silently through an asymmetric waveshaper and then compounding through a downstream feedback path (e.g. into the Phase 8 reverb) — must be caught at the distortion node's own output, not assumed to be filtered out later.
  • Running the diode-ladder filter's nonlinearity at the base sample rate without its own oversampling — a nonlinear filter aliases by the same mechanism as a waveshaper and needs the same treatment (this phase's ADR-05-adjacent lesson generalizes).
  • Treating oversampling factor as a free knob without accounting its added latency against the P13 budget — a 4x oversampled node's upsample/downsample filters add real, cumulative delay.

21.7 Performance Concerns

  • Oversampling multiplies the nonlinear node's sample-rate-dependent cost by the factor (2x/4x) plus the polyphase filter cost — must be measured and budgeted distinctly per §4/§30, not assumed proportional to the naive factor alone.
  • The diode-ladder filter's nonlinear per-sample cost is higher than the linear TPT SVF (Phase 4) — patches must budget accordingly under polyphony.

21.8 Edge Cases

  • Drive parameter at 0 (no distortion): output must equal input exactly (bypass-equivalent), not a near-zero-but-not-exact residual.
  • Extremely high drive (hard clipping regime): DC-offset removal and oversampling must both remain effective, not degrade disproportionately at the extreme.
  • Diode-ladder filter resonance at its documented stability boundary: analogous to Phase 4's I2 boundary-inclusive sweep requirement.

21.9 Failure Analysis

The distortion node passes its alias-floor gate in isolation but fails when placed after the Phase 8 reverb in a chained patch: root cause, the reverb's own slight high-frequency coloration (damping filter) interacts with the distortion's oversampling anti-imaging filter's passband edge, revealing a previously-masked residual alias component; debug method, reproduce the exact chain order under the offline renderer and measure the alias spectrum after each stage individually (P10); detection signal, a full-chain regression fixture fails where each node's isolated fixture passes; recovery, tighten the anti-imaging filter's stopband attenuation or raise the oversampling factor for chained-nonlinear-after-reverb patches, document as a known interaction in docs/failure-analysis/.

21.10 Operational Notes

  • distortion_alias_by_oversampling.json's 1x/2x/4x comparison is retained permanently (like Phase 1/2's baseline pattern) as the historical justification for defaulting to a nonzero oversampling factor.

23.6 Pitfalls

  • Treating the conformance suite's aggregation as purely mechanical (concatenating fixture lists) without re-verifying that cross-phase interactions (e.g. Phase 9's distortion after Phase 8's reverb, per §21.9) are represented — the suite must include full-chain patches, not only per-node fixtures.
  • Applying a perf optimization (e.g. a SIMD reformulation of the TPT SVF) without re-running Phase 4's differential test against scipy.signal — a "faster" filter that quietly changes its numeric behavior violates P10/P14.
  • Letting the soak test's duration be shortened "to save CI time" — denormal creep and slow numeric drift are specifically the classes of bug that only manifest over long runs (§4 dropout budget is stated in 24-hour terms for this reason).
  • Gating only on mean-case perf numbers instead of tail latency (deadline-miss distribution) — a rare but real deadline miss is an xrun, and xruns are budgeted at near-zero (§4), not "rare enough on average."

23.7 Performance Concerns

  • This phase's own profiling methodology (§30) must itself be RT-safe to run against the actual compiled kernel path, not a debug-instrumented stand-in that changes the timing characteristics being measured.
  • SIMD reformulation opportunities differ per node type (oscillators/filters are more amenable than the inherently serial IIR feedback in the reverb) — budget optimization effort by measured cost contribution (§13.1-style breakdown), not uniformly.

23.8 Edge Cases

  • A fixture that passed in isolation throughout Phases 0-10 but fails only in the full-chain conformance suite: treated as a release blocker, not a "known issue," per I13's release-gating intent.
  • A perf optimization that improves mean-case cost but worsens tail latency (e.g. an occasional cache-miss-prone code path): must fail the M-series gate on the tail-latency metric even if the mean-case metric improves.

23.9 Failure Analysis

The full conformance suite intermittently fails only in CI, never locally: root cause, CI's shared runner has less consistent cache/CPU-frequency behavior than local development hardware, exposing a tail-latency-sensitive M-series target that was marginal all along; debug method, re-run the specific failing fixture under a CPU-pinned, frequency-locked CI configuration to separate environmental noise from a real regression; detection signal, perf_hardening_before_after.json's tail-latency entries show high run-to-run variance; recovery, either tighten the implementation's margin against the target or adjust CI's runner configuration to match the documented reference hardware (§30), never silently loosen the M-series target itself.

23.10 Operational Notes

  • This phase's output — the conformance suite plus the perf-hardened kernel — is the release artifact gate referenced throughout §26 (operational readiness) and §29 (build/release engineering): nothing ships without it passing.

26. Operational Readiness

Named metrics (telemetry, ADR-20): xrun_count, deadline_miss_rate, cpu_per_block, output_peak_dbfs/output_rms_dbfs, active_voices, filter_pole_margin, denormal_flush_count, nan_detected_count, graph_validation_failures, voice_steal_click_score, render_parity_max_delta. All updated via atomic increments on the RT thread (ADR-20), drained by a non-RT exporter.

Tracing occurs exclusively outside the audio thread (ADR-19): the RT thread emits lightweight counters/timestamps into the lock-free telemetry queue; a non-RT consumer thread constructs spans from those records for dashboards.

Structured logging uses the lock-free handoff (ADR-18): the audio thread never calls a logger directly; it writes fixed-size records consumed by a non-RT logging bridge.

Dashboards: xrun rate over time, CPU-per-block distribution (mean and tail/p99.9), active-voice count, denormal-flush rate, NaN-detection rate — each tied to an §4/§30 target.

Alerting philosophy: alert on tail-latency and rare-event counters (xrun, NaN, graph-validation failure), not on mean-case CPU, since the RT-safety guarantees (§7) are worst-case claims, not average-case ones.

SLOs: xrun rate <1 per 10⁶ blocks (§4); 0 NaN detections per release; RTO <2 s per stream error (§4).

Incident response: an xrun burst or NaN-detection spike pages the on-call engineer, who first reproduces under the offline renderer (P10) before touching the live stream.

Named runbooks (docs/runbooks/): xrun-diagnosis.md, nan-outbreak.md, latency-tuning.md (§22.10).

Backup/restore of presets: patch/preset files are versioned artifacts (§27) backed up via standard filesystem/version-control mechanisms; restore is a file-copy operation, no database migration required.

Deployment topology: a single long-lived process per audio stream instance; the offline renderer runs as a stateless batch job, horizontally scalable across independent render requests.

Canary/rollback/migration: a new release is canaried against the full conformance suite (§23) before promotion; rollback is a version pin revert (ADR-25); patch/preset migration follows §27's compatibility policy.

27. Compatibility & Versioning

Preset/patch file format is versioned independently of the library (a format_version field); graph serialization evolves additively (new node types/fields ignored by older readers rather than breaking them). Node parameter-set evolution follows an additive-only policy within a major version — removing or renarrowing a parameter's range is a breaking (major-version) change. Parameter semantics are sample-rate-independent (durations/rates expressed in seconds/Hz, converted to samples internally per §8), so a patch renders equivalently across supported sample rates (§4) subject to the numeric-tolerance bounds of ADR-26. Render reproducibility across versions and platforms follows ADR-26: bit-exact within a single build/platform, tolerance-bounded across differing BLAS/compiler versions, documented per release. Plug-in ABI stability is not yet applicable (the export shim is deferred, §37) but is a named future compatibility surface. API stability follows SemVer (ADR-25): breaking changes only at a major version, with a documented migration guide and a deprecation window (minimum one minor version) before removal. Rolling- upgrade guarantees: the offline renderer supports side-by-side version installs (stateless batch jobs); the real-time engine does not support hot-upgrading a running stream — a version change requires a stream restart within the RTO budget (§4/§26).

28. Testing & Verification Strategy

Unit tests: per-node behavior in isolation (ADR-21), covering the state machines in §8 (envelope, voice, stream lifecycles).

Integration tests: full-chain patches spanning multiple node families (cross-ref §23.6's full-chain conformance requirement).

Property tests (Hypothesis, ADR-21): a filter's measured magnitude response matches its analytic transfer function within a stated dB tolerance (I2, ties to §16 fixtures); a band-limited oscillator's alias energy stays below the §4 floor across the full pitch range (I2-adjacent, ties to §14 fixtures); envelope output is continuous across every stage transition (I7, ties to §15 fixtures); the graph scheduler's topological order is a valid topological sort for any acyclic input graph (I3, ties to §17 fixtures).

Differential tests: against scipy.signal for filters (I2, §16); against a reference render for full patches (I13, §23).

Fuzzing (ADR-22): the preset/patch loader (T2, §37), the MIDI parser (I11, §22), the WAV/RIFF parser (T1, §12).

Chaos/fault injection: device dropout, buffer-size change mid-stream (I12, §22).

Deterministic offline replay: bit-exact or tolerance-bounded comparison of repeated renders of the same patch/event stream (ADR-26, I13, §12).

Soak testing: a multi-hour render checking for drift and denormal creep (I6, §23).

Real-time-safety verification: an allocation-tracing pass proving no allocation occurs on the audio thread across a stress patch (I1, §23).

Perf-regression gating: the M-series targets (§30) checked on every PR (ADR-23), tail-latency included, not mean-case only (§23.6).

Every test class above ties back to a specific invariant (I1-I14) and to the originating phase's N.5 fixtures, per the aggregation performed in §23.

31. Scalability Analysis

Constant vs. growing (Big-O): per-voice CPU cost is O(1) per sample, independent of total polyphony; total voice CPU is O(V) in voice count V; graph traversal is O(N) in node count N per block (topological order precomputed, ADR-04); delay-line/reverb memory is O(D) in max delay samples D (per §34's derivation); oversampling cost is O(K) in the oversampling factor K per nonlinear node, plus the polyphase filter's own O(1)-per-output-sample cost.

Named bottlenecks, in order: (1) per-voice oscillator+filter+envelope cost at high polyphony (dominant, §13.1-style breakdown carried into §30's M2); (2) the global reverb's serial IIR feedback cost (M8), which resists the same SIMD treatment as independent per-voice oscillators; (3) modulation-matrix route evaluation at the route ceiling (§19.7); (4) oversampling-driven nonlinear-effect cost (M9).

Scaling across cores: the audio callback itself resists multi-core scaling by construction (ADR-14) — a single RT thread owns the block's deadline, and splitting DSP work across cores mid-block reintroduces the synchronization P9 exists to avoid. Scaling beyond one core's budget (§4) requires either raising the block size (trading latency for headroom, P13) or partitioning independent voice groups across multiple RT threads (ADR-14's noted rejected-alternative-wins case), each with its own deadline and its own lock-free handoff — not shared-state parallelism within one callback.

Block-size-vs-latency tradeoff curve: 64 samples -> 1.333 ms deadline, highest overhead-to- work ratio, lowest latency; 128 -> 2.667 ms, the locked default (ADR-03); 256 -> 5.333 ms; 512 -> 10.667 ms, lowest overhead-to-work ratio, highest latency. Each doubling roughly halves per-block scheduling overhead's relative cost while doubling worst-case latency.

Practical polyphony ceiling and levers beyond it: the default 64-voice polyphony is bounded by M2's per-voice budget at the default block size; the levers to raise it are (a) increasing block size (P13 tradeoff), (b) reducing per-voice DSP cost via the Phase 11 perf-hardening pass (§23), or (c) the ADR-14 multi-RT-thread partitioning strategy — each a documented, deliberate tradeoff, not a free scaling dimension.

32. Mental Models & First Principles

MM1 — Every synthesis technique is a bandwidth-management problem. You are always deciding where the energy above Nyquist goes: suppressed by construction (BLIT/PolyBLEP, P2), pushed above the audible range by oversampling (Phase 9), or allowed to fold back as measurable, budgeted aliasing (§4 floor). Without this model you write oscillators that "sound fine" until a high note exposes silent, uncontrolled folding. Resolved in §8, §14, §21.

MM2 — A filter is a feedback system, so every exposed parameter is a stability claim. Cutoff and resonance are not just tone knobs; they are coordinates in a stability region you must prove, not assume (P4). Without this model you ship a filter that works at demo settings and blows up at a user's extreme setting. Resolved in §7 (I2), §16.

MM3 — Real-time is a worst-case contract, not an average-case one. A callback that meets its deadline 999,999 times out of 1,000,000 still has an xrun budget violation if that one miss happens (§4 SLO). Without this model you optimize mean CPU and ship tail-latency regressions. Resolved in §23, §30.

MM4 — The control/audio thread boundary is the one true concurrency boundary. Everything else in the system can be reasoned about sequentially once you accept that only the SPSC queues and atomic snapshot swaps cross it (P9). Without this model you introduce a shared-mutable-state bug that is a segfault waiting for the right race. Resolved in §3, §6 (P9), §17.

MM5 — A click is always a discontinuity, and a discontinuity always has a named cause. Zipper noise (unsmoothed parameter), voice-stealing clicks (truncated envelope), aliasing (uncorrected discontinuity) are the same underlying bug class wearing different clothes. Without this model you chase each click as a one-off instead of routing every new parameter/event through the existing smoothing/ramping contracts. Resolved in §6 (P3, P8), §15, §18.

MM6 — Block processing is a scheduling artifact, not a synthesis concept. The math (§8) is defined per-sample; blocks exist only to amortize call overhead. A node that leaks block-size dependence into its output is confusing an implementation detail for a contract. Resolved in §8, §17.

MM7 — Reproducibility is the only trustworthy form of correctness at scale. "It sounds right" does not scale past a handful of manual listens; a differential test against a closed-form or reference implementation does (P10). Without this model, regressions hide until a user with extreme settings finds them. Resolved in §7 (I13), §28.

MM8 — Every deferred feature is a scope boundary, not a missing feature. Naming what this library does not do (convolution reverb, plug-in hosting, wavetable synthesis) is as load-bearing as naming what it does — it prevents scope creep from silently violating the real-time/numerical-correctness contracts the built features were held to. Resolved in §1, §37.

MM9 — Latency and CPU headroom are the same budget viewed from two ends. Every microsecond spent processing shrinks the deadline's remaining margin (§4); every sample of added buffering (oversampling, smoothing, lookahead) shrinks the latency budget instead (P13). A design decision that ignores one while optimizing the other is only half-reasoned. Resolved in §4, §30, §34.

SuperCollider decided to split language (sclang) from the real-time audio server (scsynth) entirely, communicating over OSC — this blueprint's Python-control/compiled-kernel split is a lighter-weight descendant of the same idea, without a second process. Csound decided to keep DSP algorithms as a large, stable library of opcodes accumulated over decades rather than a small orthogonal primitive set — its niche wins when breadth of battle-tested, idiomatic algorithms matters more than a clean, minimal core (this blueprint deliberately chose the opposite: a small, provably-correct primitive set).

FAUST decided to compile the entire signal-processing graph ahead of time into a specialized kernel rather than keep it dynamically patchable at runtime — its niche wins when the patch is fixed for the product's lifetime (an embedded effects pedal, a fixed plugin) and maximum throughput matters more than runtime flexibility (ADR-04 rejected this for the opposite reason).

JUCE's juce_dsp decided to expose DSP as composable C++ template building blocks the host application assembles at compile time, rather than owning a runtime graph/scheduler itself — its niche wins when the host already has its own audio-thread architecture and just needs well-tested primitive building blocks (filters, oversampling) rather than a full engine.

34. Back-of-Envelope Capacity Model

  1. RT deadline, block 64 @48kHz: 64 / 48000 = 0.001333 s = 1.333 ms = 1333 µs (§4).
  2. RT deadline, block 128 @48kHz: 128 / 48000 = 0.002667 s = 2.667 ms = 2667 µs (§4, default).
  3. RT deadline, block 512 @48kHz: 512 / 48000 = 0.010667 s = 10.667 ms = 10667 µs (§4).
  4. Max polyphony from per-voice budget: with a 70% headroom target at block 128 (0.7 * 2667 µs = 1867 µs available for voices), and a measured per-voice cost of ~29 µs/block (M2), 1867 / 29 ≈ 64 voices — matching the §4 default polyphony exactly by construction.
  5. Delay-line memory, 1 s max delay, stereo, 100 instances: 1 s * 48000 Hz * 4 bytes (float32) * 2 channels * 100 instances = 38,400,000 bytes ≈ 36.6 MiB.
  6. Oversampling cost, 4x factor, base per-sample cost c: total cost ≈ 4c for the upsampled nonlinearity evaluation, plus the polyphase anti-imaging filter's own cost (a fixed multi-tap FIR/IIR stage per direction, independent of the nonlinearity itself) — so total node cost is 4c + 2*f where f is one polyphase filter stage's cost (up + down).
  7. FFT cost per block, if a spectral node existed (deferred, §37): N log2(N) butterflies for an N-point FFT; at N=1024, 1024 * 10 = 10240 butterfly operations per transform, times a per-butterfly cost, times two (forward+inverse) for an analysis/resynthesis round trip — this blueprint defers spectral nodes precisely because this cost does not fit the per-block RT budget at small block sizes (§37 anchor).
  8. Alias energy, naive sawtooth at 220 Hz (repeated from §8's worked example, chained here for completeness): Nyquist 24000 Hz; harmonics alias once k > 24000/220 = 109.09, i.e. k>=110; at k=110, amplitude 20*log10(1/110) = -40.8 dB — 39.2 dB above the -80 dBFS floor (§4), demonstrating naive generation's structural violation before summing the remaining infinite tail of aliased harmonics (which only adds more energy).
  9. Total memory per voice: oscillator state (~16 bytes) + filter state (~16 bytes) + envelope state (~16 bytes) + bookkeeping (note, age, flags, ~16 bytes) ≈ 64 bytes of active state, comfortably inside the ≤4096-byte budget (I14, §4), leaving headroom for per-voice modulation- route storage and future per-voice effect sends.
  10. Total voice-array memory at max polyphony ceiling (256 voices): 256 * 4096 bytes = 1,048,576 bytes = 1 MiB — the worst-case static allocation the arena must reserve at stream-open regardless of the configured default (§4, ADR-15).

36. Alternative Architectures (Roads Not Taken)

Sample-at-a-time processing instead of block processing.

for each sample n:
    for each node in topo_order:
        node.process_one(ctx, n)   // one sample in, one sample out
    output[n] = mix(...)

Winning regime: feedback-heavy topologies needing true zero-delay per-sample feedback without an implicit solver (e.g. certain analog-modeled circuits). Real embodying system: SuperCollider's UGen graph, which partly supports per-sample audio-rate calculation for exactly this reason. Rejected here because per-sample Python-level dispatch (even into a compiled kernel) multiplies call overhead by the sample count instead of the block count, and this blueprint's TPT/SVF approach (Phase 4) already solves the zero-delay-feedback problem within block processing without paying that overhead (ADR-04, ADR-06).

A compiled DSP-language approach, à la FAUST, compiling the graph to a specialized kernel.

patch.dsp  --[FAUST compiler]-->  specialized_kernel.cpp  --[C++ compiler]-->  kernel.so
                                          (one static topology, maximum throughput)

Winning regime: a fixed-topology product (an embedded effects pedal, a single-purpose plugin) where the patch never changes after build time and maximum throughput matters more than runtime patchability. Real embodying system: FAUST itself, and products built by compiling FAUST programs to embedded targets. Rejected here (ADR-04) because this blueprint's explicit goal is a runtime-patchable graph (a modular-synth-like authoring experience), which a whole-graph ahead-of-time compilation model structurally forecloses.

Wavetable/sample-playback synthesis instead of computed band-limited synthesis (PhaseDeferred, anchor "36. Alternative Architectures (Roads Not Taken)").

table[0..N-1]  (one or more cycles, band-limited per octave/mip-level)
read position += phase_increment ; output = interpolate(table, read position)

Winning regime: reproducing specific, complex, non-parametric timbres (real instrument samples, captured analog waveforms) cheaply at playback time. Real embodying system: most commercial samplers and many hardware/software synths' "wavetable" oscillator banks. Rejected here because this blueprint's goal is a from-scratch computed-synthesis library whose correctness is provable from first principles (Moore 1977's table-lookup-noise analysis is exactly the kind of tradeoff this blueprint's computed BLIT/PolyBLEP/minBLEP approach was chosen to avoid needing).

Physical-modeling/waveguide synthesis as the primary engine (PhaseDeferred, anchor "36. Alternative Architectures (Roads Not Taken)").

[excitation] -> [delay line (string/tube)] -> [loss filter] -> feedback -> [pickup/output]
                (Karplus-Strong / digital waveguide topology)

Winning regime: physically-inspired instruments (plucked strings, wind instruments) where the delay-line-plus-loss-filter topology directly models the physical system, per Karplus & Strong 1983 and Smith & Angell 1982. Real embodying system: waveguide synthesizers and much of the physical-modeling literature built on this pair of papers. Rejected here as the primary engine because this blueprint's scope centers on the oscillator/filter/envelope/effects-graph model common to subtractive/FM/effects-processing work; a waveguide engine is a fundamentally different signal-flow primitive (a delay line is the instrument, not an effect on one) that would double the domain-model surface (§8) rather than extend it.

38. Glossary

Nyquist frequency — half the sample rate; the highest frequency representable without aliasing. Aliasing — a frequency above Nyquist folding back into the audible band as a false, lower frequency. Band-limited — a signal containing no energy above Nyquist by construction. BLIT — band-limited impulse train, a closed-form antialiased pulse generator (Stilson & Smith 1996). minBLEP — minimum-phase band-limited step correction via table convolution (Brandt 2001). PolyBLEP — polynomial band-limited step approximation applied at a waveform discontinuity. Biquad — a two-pole, two-zero IIR filter section. Pole — a root of a transfer function's denominator; governs feedback/resonance and stability. Zero — a root of a transfer function's numerator; shapes the frequency response's nulls. Unit circle — the |z|=1 boundary in the z-plane; poles inside it are stable. Transfer function — H(z) = Y(z)/X(z), the frequency-domain description of an LTI system. TPT integrator — topology-preserving-transform (trapezoidal) integrator used to build zero-delay-feedback filters (Zavalishin 2012). State-variable filter (SVF) — a filter topology exposing low-pass/band- pass/high-pass simultaneously from shared integrator state. Resonance / Q — the parameter controlling a filter's peak sharpness near cutoff; at extremes, self-oscillation. ADSR — Attack-Decay-Sustain-Release envelope. Zipper noise — audible stepping artifacts from an unsmoothed, block-rate parameter change. Voice stealing — reallocating an already-sounding voice to a new note when the polyphony ceiling is reached. Modulation matrix — a bounded source×destination×depth routing table for modulation signals. Sample-accurate automation — a parameter change applied at an exact sample index rather than quantized to a block boundary. Block rate vs. control rate — the frequency at which audio-rate processing (per sample) versus modulation/control processing (per block) occurs. Denormal — a floating-point value so close to zero it loses normalized precision, historically costly on some CPUs. DC offset — an unwanted constant (0 Hz) component in a signal, often from an asymmetric nonlinearity. Over- sampling — processing a signal at a higher internal rate to push aliasing above the eventual output Nyquist before downsampling. FDN reverb — feedback delay network reverb, N delay lines coupled through a stability-proven feedback matrix (Jot & Chaigne 1991). Schroeder allpass — an allpass filter section used in classic reverb topologies (Schroeder 1962). Comb filter — a delay-with-feedback structure producing evenly-spaced frequency-response notches/peaks. Impulse response — a system's output when driven by a unit impulse; fully characterizes an LTI system. THD+N — total harmonic distortion plus noise, a measured signal-purity metric. Xrun — a buffer underrun/overrun in the audio callback, audible as a click or dropout. Real-time safety — the property that a code path never allocates, locks, or blocks unpredictably. RMS — root-mean-square, a signal-level measure. dBFS — decibels relative to full scale, the digital audio level unit. SPSC — single-producer single-consumer, a lock-free queue discipline. Arena allocator — a pre-reserved memory pool sized once, never grown at runtime. FTZ/DAZ — flush-to-zero / denormals-are-zero, CPU flags forcing denormal values to zero in hardware. RIFF — the container format WAV files use (Resource Interchange File Format). Running status — a MIDI 1.0 optimization omitting a repeated status byte across consecutive same-type messages. UMP — Universal MIDI Packet, the MIDI 2.0 wire format. Legato — reusing an already-sounding voice for a new note rather than retriggering, for a smooth pitch transition. Key tracking — scaling a filter's cutoff by the played note's frequency. Spectral radius — the largest eigenvalue magnitude of a matrix; governs feedback- system stability. Bessel function — the special function giving FM synthesis's sideband amplitudes (Chowning 1973). Waveshaping — a nonlinear, memoryless transfer function applied to a signal for distortion/timbre shaping. Diode-ladder filter — a nonlinear filter topology modeling analog diode-ladder circuits (Yeh, Abel & Smith 2010). Polyphase filter — an efficient multirate filter structure used in up/downsampling. Topological sort — an ordering of a DAG's nodes such that every edge points from earlier to later in the order. Node protocol — the structural interface (process/static_size/reset) every graph node implements. RTO — recovery time objective, the target maximum time to restore service after a failure. SLO — service-level objective, a quantified reliability target. Latency budget — the total accounted delay a system may introduce, allocated across its buffering/processing stages.
