Decisions (§9) · 25 ADRs

A01

Implementation language

Chosen

Rust (stable)

Rejected

Zig (TigerBeetle native), C, Go

When the rejected choice is right

Zig wins when the entire team already owns the TigerBeetle codebase and zero-FFI interop with the reference implementation is required; C wins when binary footprint and toolchain portability across exotic embedded targets outweigh safety concerns

Why: Safety + u128 native + portfolio consistency + zerocopy/io_uring ecosystem

A02

Build system

Chosen

cargo + make

Rejected

Bazel, CMake

When the rejected choice is right

Bazel wins in a monorepo where ledger crates must co-build with C++/Java/Go services and incremental build caching across languages justifies the setup cost

Why: Standard Rust toolchain; reproducible via Cargo.lock

A03

Dependency policy

Chosen

Minimal; zero transitive unsafe outside zerocopy/bytemuck/io-uring

Rejected

Tokio full runtime, serde

When the rejected choice is right

serde wins for non-state-machine crates (CLI output, config parsing) where human ergonomics and schema evolution matter more than determinism constraints

Why: Determinism requires controlled deps; serde excluded from state machine (non-deterministic derive)

A04

Record serialization

Chosen

zerocopy safe transmute; #[repr(C, packed)]

Rejected

bincode, prost, serde

When the rejected choice is right

prost wins when the wire format must evolve over time with optional fields and schema registry compatibility (e.g., a multi-version fleet where record layout changes between releases)

Why: Fixed 128-byte layout; zero-copy cast; no serialization overhead in hot path

A05

Async I/O

Chosen

io-uring crate (tokio-uring feature)

Rejected

epoll/mio, io_uring raw syscalls

When the rejected choice is right

epoll/mio wins on kernels < 5.10 or in containers without CAP_SYS_ADMIN, where io_uring SQPOLL is unavailable and portability across Linux distros matters more than peak I/O throughput

Why: Submission ring reduces syscall count; fixed-buffer registered I/O

A06

State machine thread model

Chosen

Single-threaded synchronous

Rejected

Rayon, async executor

When the rejected choice is right

A multi-threaded executor wins for a general-purpose OLTP engine where transactions are independent and horizontal CPU scaling is preferred over determinism (e.g., TiKV region-sharded raftstore)

Why: Determinism requires serial execution; no concurrent mutation of state

A07

WAL format

Chosen

Custom: 512-byte sectors, CRC32C header per sector

Rejected

SQLite WAL, Kafka log format

When the rejected choice is right

SQLite WAL wins when embedding a proven WAL within an existing SQLite-based stack where integration cost and code ownership size outweigh the customization benefits

Why: Full control; sector-aligned; torn-write detectable

A08

LSM implementation

Chosen

Custom ledger-lsm (fixed 128-byte records)

Rejected

RocksDB, sled, LevelDB

When the rejected choice is right

RocksDB wins when the value schema is variable-length and evolves frequently, or when operational familiarity and tuning tooling (Advisor, BlobDB) are more valuable than write-amplification reduction

Why: Variable-record LSMs are heavier; fixed-record enables O(1) lookup without block parsing

A09

Consensus protocol

Chosen

VSR (Viewstamped Replication Revisited)

Rejected

Raft, Multi-Paxos, EPaxos

When the rejected choice is right

Raft wins when the team is integrating with an existing Raft-based ecosystem (etcd, CockroachDB), shared libraries exist, and the cleaner Raft log-compaction API reduces integration risk

Why: VSR has cleaner state-transfer; matches TigerBeetle architecture; Raft log truncation semantics differ

A10

Network transport

Chosen

TCP (internal replica); UDP (client)

Rejected

QUIC, gRPC

When the rejected choice is right

QUIC wins when clients are on mobile/WAN with high packet loss, where connection migration and 0-RTT reconnect reduce tail latency more than UDP's framing simplicity saves overhead

Why: TCP for ordered replica messages; UDP for low-overhead client batches (client handles loss)

A11

Integer type for amounts

Chosen

u128 (native Rust)

Rejected

i128, u64, Decimal, f64

When the rejected choice is right

Decimal wins when the application must display human-readable currency values with configurable precision and round-half-up semantics required by financial regulations — in that case, a fixed-point decimal layer (project #401) is the right location

Why: u128 prevents negative-amount abuse; 128-bit range exceeds world GDP in satoshis

A12

Clock source

Chosen

CLOCK_MONOTONIC_RAW for relative; primary assigns timestamp

Rejected

CLOCK_REALTIME, NTP direct

When the rejected choice is right

CLOCK_REALTIME + TrueTime wins in a globally distributed multi-cluster deployment (Spanner-style) where externally consistent read timestamps across clusters require bounded clock uncertainty

Why: Monotonic prevents backward jumps in state machine; primary serializes timestamps

A13

Checksum algorithm

Chosen

CRC32C (hardware-accelerated)

Rejected

SHA256, xxHash, Adler32

When the rejected choice is right

SHA256 wins when the integrity check must double as a cryptographic commitment (e.g., regulatory audit trail where tamper-evidence against privileged insiders is required, not just bit-flip detection)

Why: Hardware CRC32C (SSE4.2/ARM CRC) is ~10 GB/s; sufficient for sector-level integrity

A14

Block cache policy

Chosen

Fixed-size LRU, static allocation

Rejected

mmap + OS page cache, dynamic cache

When the rejected choice is right

mmap + OS page cache wins on a read-heavy analytics workload on a dedicated machine where the OS can adaptively allocate all free RAM to cache across multiple files and workloads are not latency-sensitive

Why: O_DIRECT bypasses OS cache; static LRU prevents memory surprises

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alternative 1 — Append-Only Event Log (Kafka-style)

Client ──► Kafka Topic (transfers) ──► Consumer Group ──► Materialized Views
                                              │
                                       balance-service-1 (ledger A)
                                       balance-service-2 (ledger B)
                                              │
                                       PostgreSQL / RocksDB (per-service)

Regime where it wins: read-heavy analytics ledgers where the history of all events is more valuable than the current balance, event replay for audits is frequent, and throughput > correctness isolation is acceptable. Systems that embody this: Apache Kafka + Flink for financial event streaming at companies like Uber (Kafka-based money movement audit logs, as described in their engineering blog).

Why rejected here: the double-entry invariant (I1) requires atomic debit + credit in a single commit. In the event-log model, the two halves of a transfer are separate events; enforcing Σdebits == Σcredits requires a coordinator that scans all consumer offsets — introducing exactly the distributed coordination complexity we are avoiding. The ordering guarantee requires a distributed lock or consensus at the Kafka partition level, reverting to VSR-equivalent complexity with more moving parts.

Alternative 2 — Multi-Version Concurrency Control (MVCC) Row Store

Client ──► SQL Layer ──► MVCC Transaction Manager
                              │
                    ┌─────────┴──────────┐
              Account Table (MVCC)   Transfer Table (MVCC)
                    │                         │
              WAL (Postgres-style)     WAL (Postgres-style)

Regime where it wins: general-purpose financial platforms where the application requires arbitrary SELECT queries, schema evolution (ALTER TABLE), and rich reporting (aggregations by code:u16, range scans on timestamp). CockroachDB and PostgreSQL embody this; Stripe's core billing engine is believed to be PostgreSQL-backed.

Why rejected here: MVCC stores multiple versions of each row, multiplying storage for a write-heavy ledger. Garbage collection of old versions introduces latency jitter incompatible with the p999 < 20 ms target (§4). The lock-free concurrency model in MVCC requires version chains to be traversed on every read, adding O(V) overhead per lookup where V is version count — opposite of the O(1) fixed-record LSM design. Most critically, the double-entry invariant is enforced at the application layer in SQL via triggers or application code, not as a storage primitive.

Alternative 3 — Shared-Disk Cluster (Oracle RAC-style)

                   Shared NVMe-oF / SAN
                          │
           ┌──────────────┼──────────────┐
      Node 1 (R/W)   Node 2 (R/W)   Node 3 (R/W)
           └──────────────┴──────────────┘
                   Distributed Lock Manager

Regime where it wins: workloads where read scaling across many nodes is critical and the storage budget allows a high-end SAN. Oracle RAC is the canonical embodiment; it is used by banks and payment processors that cannot migrate away from Oracle SQL semantics. Wins when cross-node read throughput > write throughput and the organization already operates a SAN fabric.

Why rejected here: the distributed lock manager (DLM) becomes a bottleneck for write-heavy workloads — acquiring a lock on an account record before mutation serializes access back to a single node. For financial ledgers where writes are the critical path (every payment is a write), the DLM overhead exceeds the benefit of shared storage. This blueprint eliminates the problem by making each replica a full copy and using consensus (VSR) for write ordering, avoiding any shared mutable state.

Alternative 4 — Pure In-Memory with Replication (Redis Sentinel-style)

Client ──► Redis Primary (all state in RAM) ──► Sentinel ──► Replicas (async)
                                                               (no fsync)

Regime where it wins: extreme low-latency trading systems where sub-100 µs commit latency is required and the business can tolerate eventual loss of recent transactions on power failure (acceptable for ephemeral order books but not settlement). Redis Cluster with AOF persistence is the canonical embodiment; used by fintech companies for rate limiting and real-time balance caches (not authoritative ledgers).

Why rejected here: async replication means acknowledged writes can be lost on primary failure — RPO > 0. This violates the RPO = 0 requirement (§4) which is non-negotiable for an authoritative financial ledger. Upgrading to synchronous replication eliminates the latency advantage. Storing 1 × 10⁹ accounts × 128 bytes = 128 GB in RAM per replica also exceeds the §4 6 GB static memory ceiling by 21×. This design trades safety for speed in a way incompatible with financial auditability.
