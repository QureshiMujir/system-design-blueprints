411 — Double-Entry Ledger / Transaction Processing Engine (TigerBeetle-style) from Scratch

Project Number: 411 Project Name: Double-Entry Ledger / Transaction Processing Engine (TigerBeetle-style) from Scratch Owner: Mujir Qureshi Document: FINAL_BLUEPRINT.md Status: specification — locked

1. Goal

Build a crash-safe, deterministic, high-throughput double-entry financial accounting engine — peer class to TigerBeetle. Fixed-schema state machine; NOT a general-purpose OLTP DB (see #100). Correctness-first, observability-second, maintainability-third, performance-fourth.

Core capability surface:

  • Account records — 128-byte fixed-size; id:u128, ledger:u32, code:u16, flags:u16, pending/posted debit/credit balances (each u128), user_data:u128, timestamp:u64.
  • Transfer records — 128-byte fixed-size; id:u128, debit_account_id:u128, credit_account_id:u128, amount:u128, pending_id:u128, ledger:u32, code:u16, flags:u16, timestamp:u64.
  • Double-entry invariant — every posted transfer increments debit_acct.debits_posted += amount AND credit_acct.credits_posted += amount; Σdebits == Σcredits per (ledger) always.
  • Balance constraints via flags — debits_must_not_exceed_credits (asset/overdraft guard), credits_must_not_exceed_debits (liability guard); enforced atomically before commit.
  • Two-phase transfers — pending → posted/voided/expired; debits_pending/credits_pending reserve; post/void resolves; timeout auto-voids.
  • Linked atomic chains — linked flag chains a sequence; all succeed or all fail atomically; per-event result code.
  • Idempotent creates — client-assigned u128 IDs; re-create with existing ID returns prior result exactly (no duplicate insert).
  • Deterministic state machine — same ordered input → bit-identical state on every replica; required for VSR consensus replication.
  • WAL durability — append-only WAL + fsync; recovery replays from last checkpoint.
  • LSM object store — accounts + transfers in LSM-forest; key = id; value = fixed 128-byte record.
  • VSR consensus — Viewstamped Replication Revisited (Liskov & Cowling 2012); views/primary/prepare/commit/view-change/state-transfer.
  • Client protocol — request batching (~8 KiB messages); pipelining; session registration; backpressure.
  • Deterministic simulation testing (VOPR) — fault-injecting simulator over randomized histories; checks all invariants.

System boundaries: a standalone replicated database process (ledgerd) + a client library (ledger-client) + a CLI (ledger-ctl). NOT an ORM, NOT a SQL layer, NOT a general key-value store.

Explicit non-goals:

  • NOT floating-point amounts — integer u128 only; decimal/fixed-point display layer → see project #401 → PhaseDeferred("FINAL_BLUEPRINT §11").
  • NOT multi-ledger cross-currency settlement — currency conversion logic → PhaseDeferred("FINAL_BLUEPRINT §24").
  • NOT SQL/relational query — no SELECT, no joins, no arbitrary predicates.
  • NOT multi-tenant auth/authz — operator-level access only; fine-grained RBAC → PhaseDeferred("FINAL_BLUEPRINT §24").
  • NOT a generic consensus library — VSR implementation is internal only; public Raft/Paxos library = separate project.
  • NOT NTP/clock discipline — clock sync = project #394; this engine reads cluster time, never disciplines it.

Deployment model: 3-replica cluster (primary + 2 backups) on bare metal or VMs with dedicated NVMe; single-threaded deterministic execution per replica; io_uring-based I/O on Linux.

Target users: financial platform engineers, payment processors, ledger infrastructure owners who need auditability and crash-safety at the storage layer.

Phase 0 deliverable — numbered crates/modules:

  1. ledger-core/ — record layout, enums, error types, balance arithmetic.
  2. ledger-state/ — deterministic state machine: account/transfer CRUD + constraint enforcement.
  3. ledger-wal/ — append-only WAL, fsync discipline, checksum per sector, recovery.
  4. ledger-lsm/ — LSM-forest object store + indexes.
  5. ledger-vsr/ — VSR consensus: prepare/commit/view-change/state-transfer.
  6. ledger-net/ — client protocol: session, batching, pipelining, backpressure.
  7. ledger-sim/ — VOPR deterministic simulator: fault injection, history generation, invariant checker.
  8. ledger-ctl/ — CLI: cluster admin, account/transfer inspection, WAL dump.

What later phases unlock: P3 unlocks balance constraint enforcement; P4 unlocks two-phase transfers; P5 unlocks linked chains; P6 unlocks WAL crash safety; P8 unlocks LSM persistence; P9 unlocks VSR replication; P11 unlocks VOPR simulation.

Estimated timeline: Phase 0 (P0–P3, single-node) = 8–10 weeks; full P0–P12 including VSR + VOPR = 5–7 months.

2. Why Build This

Unique systems knowledge taught:

  • Double-entry invariant enforcement at storage level — balance accounting as a first-class DB primitive, not application logic; audit trail as structural property.
  • Fixed-size deterministic records — 128-byte layout enables O(1) lookup, cache-line alignment, and bit-identical replica state without serialization ambiguity.
  • Two-phase transfer state machine — pending reservation prevents double-spend; void/post/timeout transitions must be atomic and idempotent.
  • Linked atomic chains — batched multi-transfer atomicity without distributed transactions; rollback-on-failure semantics implemented purely in the state machine.
  • VSR replication mechanics — Viewstamped Replication Revisited is the cleanest expression of primary-backup consensus with a clean view-change protocol; building it from scratch teaches quorum mechanics, prepare/commit separation, and state transfer.
  • Deterministic simulation (VOPR) — FoundationDB / TigerBeetle hallmark; running thousands of randomized fault histories against a reference model and checking invariants is more effective than any unit test suite.
  • WAL + LSM interaction — crash recovery: replay WAL from checkpoint into LSM; torn-write detection; superblock management.
  • Static allocation discipline — zero heap allocation after startup; bounded memory; arena allocators; why this matters for tail latency and GC-free operation.

Historical/architectural significance:

  • TigerBeetle — first production database designed from the ground up as a financial state machine; introduced VOPR deterministic simulation; Zig implementation.
  • Double-entry bookkeeping — invented ~1494 (Pacioli); every accounting system from QuickBooks to Stripe Ledger uses the same invariant.
  • VSR — Liskov & Cowling 2012 re-derivation is the cleanest consensus protocol paper; more readable than Raft, stronger invariants than Multi-Paxos.
  • FoundationDB deterministic simulation — formal verification via randomized testing; influenced TigerBeetle VOPR.

Engineering muscles developed: record-layout design; checked integer arithmetic; consensus protocol implementation; WAL/LSM interaction; fault-injecting test harness; invariant-driven correctness.

Production concepts exercised: crash-only semantics; fsync discipline; quorum availability; rolling upgrades; financial audit compliance.

Cross-links:

  • #69 WAL — WAL subsystem; this project extends with per-sector checksums + superblock checkpoints.
  • #68 LSM Storage Engine — LSM-forest object store backend; compaction, bloom filters.
  • #100 Generic OLTP — contrast: fixed schema vs flexible; deterministic vs concurrent.
  • #394 NTP/PTP — cluster timestamps sourced from clock; engine reads but never disciplines.
  • #401 Decimal Arithmetic — u128 integer amounts flow into that project's decimal layer for display.
  • Consensus projects — VSR vs Raft ADR is a key learning; same quorum math, different view-change model.

Calibration value: financial systems demand zero tolerance for logical bugs (double-spend, balance divergence). This permanently raises an engineer's bar for invariant enforcement, crash-safety, and deterministic testing.

Client Layer — ledger-client encodes events into 8 KiB batch frames; handles request/response correlation via session sequence numbers. ledger-ctl is the operator CLI. FFI headers expose a C ABI for non-Rust clients. All clients register sessions; sessions carry monotonic sequence numbers for exactly-once delivery.

ledger-net — decodes UDP/TCP frames into typed Vec<Event> batches; demultiplexes responses to waiting sessions; enforces per-session sliding-window backpressure; validates frame CRC32C before dispatch to state machine.

ledger-state — single-threaded deterministic core; processes one Vec<Event> batch per call; mutates AccountStore, TransferStore, PendingIndex, DedupIndex; enforces all invariants. Only place state changes occur. Bit-identical output given identical ordered input.

ledger-wal — append-only log of PrepareMessage payloads; fsynced before acknowledgement; per-512-byte-sector CRC32C checksums; torn-write detection on open; superblock records checkpoint LSN + WAL offset; recovery replays from checkpoint LSN forward.

ledger-lsm — four LSM trees: accounts, transfers, pending, dedup; fixed 128-byte values; O_DIRECT block I/O; tiered compaction; bloom filters per SSTable; static block cache (4 GB); manifest log for metadata durability.

ledger-vsr — VSR normal mode (prepare/prepare-ok/commit); view-change (start-view-change/do-view-change/start-view); state-transfer (request-start-view/send-state chunks). Drives StateMachine::execute_batch() deterministically; primary sequences batches into numbered PrepareMessages; backups apply identical sequence.

NVMe / Block Device — dedicated partition; O_DIRECT + io_uring; pre-allocated WAL zone + LSM zone; no filesystem cache in critical path; zone boundaries enforced at startup.

6. Design Principles

P1 — Determinism over convenience. The state machine MUST produce bit-identical output given identical ordered input on every replica. Reject any non-deterministic operation (random, system time in state, pointer hashing). Violation: replica divergence detected by state checksum mismatch → consensus failure.

P2 — Crash-only semantics. No graceful shutdown path for the state machine; crash = truncate uncommitted WAL tail; restart = replay WAL from checkpoint. Violation: unsynced state write causes undetectable data loss.

P3 — Integer arithmetic only, no floats. All amounts are u128; all arithmetic uses checked_add/checked_sub; overflow = CreateTransferError::Overflow. Violation: float rounding creates balance discrepancies; illegal in financial accounting.

P4 — Invariants enforced before commit, not after. Balance constraints, pending-fund conservation, and double-entry balance are checked atomically in execute_batch before WAL append. Post-commit fixup is not an option. Violation: partial commit of a linked chain leaves ledger in inconsistent state.

P5 — Static allocation; zero heap after startup. Memory pools, slab allocators, and fixed-size ring buffers allocated at init(); no malloc/Box::new in the hot path. Violation: heap fragmentation causes unbounded tail latency; GC pauses in a GC-free language = allocator stalls.

P6 — Exactly-once creates via client-assigned IDs. u128 IDs are assigned by the client; re-create with existing ID is a no-op returning the prior result. Violation: duplicate inserts double-count balances; idempotency guard must be the first check.

P7 — WAL is the source of truth; LSM is a derived index. LSM state can always be reconstructed by replaying the WAL from a checkpoint. Never treat LSM as authoritative unless WAL confirms. Violation: LSM corruption without WAL diverges replica state.

P8 — Sequential I/O over random I/O. WAL appends are always sequential; LSM compaction reorganizes data into sequential runs. Random reads hit the block cache. Violation: random WAL writes destroy throughput on spinning or NVMe QD=1 devices.

P9 — Backpressure everywhere. Client sliding windows; internal batch queues; compaction rate limiter; network send buffers. Violation: unbounded queues cause OOM; drop-head vs. block-on-full must be explicit per queue.

P10 — Observability by default. Every state transition emits structured log events; every WAL/LSM I/O emits latency histograms; every VSR round emits phase metrics. Violation: silent divergence or latency regression goes undetected.

P11 — No undefined behavior in the critical path. All record parsing uses zerocopy or explicit bytemuck safe transmutes; all integer ops use checked variants; no unsafe in ledger-state. Violation: UB in state machine = non-deterministic replica behavior.

P12 — Idempotent WAL recovery. Replaying the same WAL segment N times produces the same state as replaying once. Violation: double-replay inflates balances; recovery must track applied LSN.

P13 — Linked chain atomicity is all-or-nothing. If any event in a linked chain fails, all preceding events in the chain are rolled back before WAL append. The chain commits as a unit or not at all. Violation: partial chain commit violates the double-entry invariant.

8. Domain Model / Protocol

Record Layout (EBNF / bit-level)

Account  ::= id:u128 | debits_pending:u128 | debits_posted:u128
           | credits_pending:u128 | credits_posted:u128
           | user_data:u128 | reserved:u32 | ledger:u32
           | code:u16 | flags:u16 | timestamp:u64
           -- total: 128 bytes

Transfer ::= id:u128 | debit_account_id:u128 | credit_account_id:u128
           | amount:u128 | pending_id:u128 | user_data:u128
           | timeout:u32 | ledger:u32 | code:u16 | flags:u16
           | timestamp:u64
           -- total: 128 bytes

All fields little-endian. timestamp = cluster time (nanoseconds since epoch, assigned by primary). reserved = must be zero (future-proofing). flags = bitmask (see below).

Account Flags Bitmask

Bit Name Semantics
0 linked This event is chained to the next in the batch
1 debits_must_not_exceed_credits Enforce debit ≤ credit at all times (asset)
2 credits_must_not_exceed_debits Enforce credit ≤ debit at all times (liability)
3–15 reserved Must be zero

Transfer Flags Bitmask

Bit Name Semantics
0 linked Chain to next event; all-or-nothing
1 pending Two-phase: reserve funds, do not post
2 post_pending_transfer Resolve a prior pending transfer (post)
3 void_pending_transfer Resolve a prior pending transfer (void)
4 balancing_debit Reduce debits_must_not_exceed_credits violation risk
5 balancing_credit Reduce credits_must_not_exceed_debits violation risk
6–15 reserved Must be zero

Transfer State Machine

                  create(pending=1)
                  ────────────────►  PENDING
                                     │        │           │
               post_pending          │        │ void_pending│  timeout expires
               ────────────►  POSTED │        └───────────► VOIDED
                                     │
                                     └───────────────────► EXPIRED
                                          (auto-void by TimeoutSweep)

State transitions:

Current State Event Next State Preconditions
— create_transfer(pending=0) POSTED (immediate) Accounts exist; ledgers match; amounts valid; balance constraints pass
— create_transfer(pending=1) PENDING Same as above + timeout > 0
PENDING create_transfer(post_pending=1, pending_id=X) POSTED pending_id exists and is PENDING; amount ≤ pending.amount
PENDING create_transfer(void_pending=1, pending_id=X) VOIDED pending_id exists and is PENDING
PENDING cluster_time ≥ pending.timestamp + pending.timeout EXPIRED Auto-applied by TimeoutSweep before each batch

Balance Arithmetic (per posted transfer)

debit_account.debits_pending  -= amount   (if resolving pending)
debit_account.debits_posted   += amount
credit_account.credits_pending -= amount  (if resolving pending)
credit_account.credits_posted  += amount

All ops: checked_add / checked_sub; overflow → CreateTransferError::Overflow.

Linked Chain Semantics

batch = [T1(linked=1), T2(linked=1), T3(linked=0)]
  → T1, T2, T3 form one atomic chain
  → If T2 fails: T1 rolled back in memory; no WAL append for chain
  → Result codes: T1=linked_event_failed, T2=<actual error>, T3=linked_event_failed

Chain detection: scan batch left-to-right; linked flag on event N means N and N+1 are in the same chain; chain ends at first event with linked=0 or last event.

Idempotency Protocol

create_account(id=X):
  1. DedupIndex.lookup(X)
  2. If found: return stored result (no mutation)
  3. If not found: execute, store result in DedupIndex, return result

DedupIndex is an in-memory hash map (backed by LSM dedup tree for durability). Key = u128 ID. Value = CreateAccountResult or CreateTransferResult enum.

Client Protocol (Frame Format)

Frame ::= magic:u32(0x0A_5CA1AB) | checksum:u32 | client_id:u128
        | request_id:u64 | operation:u8 | reserved:u8 | batch_size:u16
        | payload: [Event; batch_size]   -- each Event = 128 bytes

Operations: CREATE_ACCOUNTS=0, CREATE_TRANSFERS=1, LOOKUP_ACCOUNTS=2, LOOKUP_TRANSFERS=3.

Response frame: same header structure; payload = array of result codes (one per input event, u32 each).

Worked Examples

Normal transfer (T-account view)

Transfer: debit_account=A (asset), credit_account=B (liability), amount=100
Before: A.debits_posted=0, B.credits_posted=0
After:  A.debits_posted=100, B.credits_posted=100
Trial balance: Σdebits=100, Σcredits=100 ✓

Two-phase transfer

1. create_transfer(pending=1, amount=50) → PENDING
   A.debits_pending+=50, B.credits_pending+=50
2. create_transfer(post_pending=1, pending_id=P, amount=50) → POSTED
   A.debits_pending-=50, A.debits_posted+=50
   B.credits_pending-=50, B.credits_posted+=50

Balance constraint violation (malformed)

Account A: flags=debits_must_not_exceed_credits, credits_posted=100, debits_posted=90
Transfer: amount=20 to debit A → debits_posted would become 110 > credits_posted=100
Result: CreateTransferError::DebitAccountExceedsCredits (no mutation)

Linked chain partial failure

Batch: [T1(amount=10, linked=1), T2(amount=999999, linked=0)]
T1 valid. T2 violates balance constraint.
Result: T1=linked_event_failed, T2=DebitAccountExceedsCredits
WAL: no append. State: unchanged.

Malformed transfer (zero amount)

Transfer: amount=0
Result: CreateTransferError::AmountMustNotBeZero

  debits_posted:    u128,  // Settled debits
  credits_pending:  u128,  // Reserved by pending transfers (credit side)

  reserved:         u32,   // Must be zero

16.6 Pitfalls

  • O_DIRECT alignment: pwrite buffers must be sector_size-aligned; use aligned_alloc or posix_memalign; Rust Vec is NOT guaranteed aligned to sector boundaries.
  • Double superblock write: superblock update is not atomic for >1 sector; use ping-pong (write to A, validate, write to B); read newest valid on open.
  • fsync vs fdatasync: use fsync for WAL (metadata + data); fdatasync is insufficient for new files where size metadata must be durable.
  • LSN gap on recovery: if WAL has a gap (missing sector), treat everything after gap as potentially corrupt; truncate to gap start.
  • Recovery replay idempotency: StateMachine::execute_batch during replay must not re-register dedup entries twice; replay path passes is_recovery=true flag to skip dedup write.

16.7 Performance Concerns

  • O_DIRECT with small (512 B) sectors: consider grouping multiple prepares into a single 4 KB write; reduces pwrite call overhead.
  • io_uring for WAL: submit multiple sector writes in a single io_uring_enter; reduces syscall count from N to 1 per batch.
  • fsync batching: batch multiple prepares before a single fsync if VSR pipeline depth > 1; trades latency for throughput.

16.8 Edge Cases

  • WAL file exactly at pre-allocated limit: wrap to start of log zone (circular WAL); requires checkpoint to be current before wrap.
  • Multiple recovery attempts: recovery is idempotent; LSN dedup prevents double-apply.
  • Concurrent write and crash: if crash during multi-sector payload write, only complete sectors are valid; partial final payload detected by CRC failure.

16.9 Failure Analysis

  • WAL corruption beyond torn write: multiple bad sectors = catastrophic; recover from replica via state transfer. Operator action: ledger-ctl replica recover --from-peer.
  • fsync returns EIO: NVMe hardware failure; halt replica immediately; alert operator.
  • Superblock unreadable (both copies corrupt): cold WAL from replica; state transfer from healthy peer.

  • tracing::warn! on torn write with LSN range discarded.

21.7 Performance Concerns

  • LSM flush (all 4 trees): 1M records × 4 trees × 128 bytes = 512 MB; sequential write; ~2–3 s on NVMe 200 MB/s write.
  • Superblock write: 2 × 4096-byte fsync = negligible.
  • Recovery replay: 1 GB WAL at 500 MB/s = 2 s read + state machine apply.

21.8 Edge Cases

  • Checkpoint triggered when memtable is empty: skip memtable flush; superblock still updated with new checkpoint_lsn.
  • Second checkpoint before first completes: serialize checkpoints via Mutex<CheckpointState>; reject concurrent checkpoint.
  • WAL zone full before checkpoint completes: impose write stall on state machine until checkpoint frees space.

21.9 Failure Analysis

  • Both superblock copies corrupt: manual recovery from replica via state transfer; no local recovery possible.
  • LSM SST missing after checkpoint: manifest log records SST additions; on open, verify each SST file exists; missing file = state transfer required.

21.10 Operational Notes

  • metrics::histogram!("checkpoint.duration_ms"), metrics::gauge!("checkpoint.wal_delta_mb").
  • tracing::info! on each checkpoint with checkpoint_lsn, state_hash, duration.
  • Alert: checkpoint duration > 10 s (I/O saturation likely).

22. Phase 10 — io_uring Integration

22.1 Objectives

  • Replace pread/pwrite/fsync syscalls with io_uring submission ring.
  • Register fixed buffers for WAL and LSM I/O.
  • Batch multiple I/O operations into single io_uring_enter call.
  • Measure throughput improvement vs. baseline syscall approach.

22.2 Detailed Implementation Steps

  • ledger-lsm/src/io.rs: IoRing { ring: IoUring, fixed_bufs: RegisteredBuffers }; submit_read(fd, buf, offset), submit_write(fd, buf, offset), wait_all(). (ADR-A05 io_uring crate; Linux io_uring man page; Design Principle P5 static buffer registration)
  • ledger-wal/src/append_log.rs: replace pwrite + fsync with io_uring linked SQEs (IOSQE_IO_LINK): write SQE linked to fsync SQE; single io_uring_enter. (ADR-A05; POSIX io_uring_enter(2); Design Principle P8 sequential I/O)
  • Register fixed WAL buffer (4 MB) and LSM read buffer pool (64 × 4 KB) at startup. (Design Principle P5 zero heap after startup; §4 memory ceiling 6 GB)
  • io_uring CQE processing: poll completion queue after io_uring_enter; map completions back to pending operations via user_data tag. (Linux io_uring CQE lifecycle docs)
  • io_uring flags: IORING_SETUP_SQPOLL for kernel-side polling (zero-syscall after registration); evaluate latency vs. CPU trade-off. (ADR-A05; §4 CPU: 1 core state machine + 2–4 I/O threads)
  • Benchmark: compare io_uring vs. pwrite+fsync for WAL append rate and LSM read rate. (ADR-A22 criterion; §24 benchmark targets)

22.3 Deliverable

WAL append + fsync via io_uring linked SQEs. LSM block reads via io_uring. Benchmark showing ≥ 20% throughput improvement vs. syscall baseline.

22.4 Acceptance Criteria

  • WAL append correctness unchanged (all P4 conformance fixtures pass).
  • LSM read correctness unchanged (all P5 conformance fixtures pass).
  • WAL append + fsync throughput ≥ 600 MB/s (vs. 500 MB/s baseline).
  • No io_uring setup errors on Linux 5.10+.
  • IORING_SETUP_SQPOLL: evaluate; disable if CPU overhead exceeds throughput gain.

22.5 Conformance Fixtures

  • Reuse all WAL and LSM fixtures from P4/P5; verify identical outputs.

22.6 Pitfalls

  • io_uring registered buffer alignment: fixed buffers must be page-aligned (4096 bytes); use mmap(MAP_ANONYMOUS | MAP_LOCKED).
  • Completion order: io_uring CQEs may arrive out of submission order; use user_data tags to match completions to pending ops.
  • IORING_SETUP_SQPOLL requires CAP_SYS_NICE: may not be available in containers; fallback to non-SQPOLL mode.
  • Linked SQE failure: if write SQE fails, linked fsync is cancelled; check both CQEs; handle partial failure.

22.7 Performance Concerns

  • Submission ring size: 256–1024 SQEs; tune to batch size.
  • Kernel-side polling (SQPOLL): reduces syscalls to zero after registration; CPU cost: 1 kernel thread busy-polling.
  • For latency-sensitive paths (WAL fsync): prefer non-SQPOLL + single io_uring_enter per fsync round.

22.8 Edge Cases

  • io_uring not supported (kernel < 5.6): detect at startup; fall back to pread/pwrite; log warning.
  • Ring full: all 256 SQEs in use; block submission until CQEs arrive.

22.9 Failure Analysis

  • io_uring_enter returns ENOMEM: ring buffers exhausted; reduce concurrent I/O; increase ring size.
  • Kernel BUG in io_uring: known issues in kernels < 5.15; enforce minimum kernel version check at startup.

22.10 Operational Notes

  • metrics::histogram!("io_uring.wal_write_latency_us"), metrics::histogram!("io_uring.lsm_read_latency_us").
  • tracing::debug! on ring full events.
  • Enable io_uring only on Linux 5.10+; compile-time feature gate #[cfg(target_os = "linux")].

Bottlenecks at scale: (1) NVMe write bandwidth (WAL + LSM compaction competing); (2) VSR round-trip latency becomes dominant above 500 K tps; (3) LSM bloom filter memory grows O(N accounts); static allocation limits this.

Mental Models & First Principles

MM1 — The state machine is a pure function. Expert insight: execute_batch(events, timestamp) → results is a total, deterministic function; given identical inputs on any replica it produces bit-identical outputs and bit-identical next state. What it predicts: any non-determinism source (system clock, pointer hash, thread scheduling) will cause replica divergence. Bug class without it: calling SystemTime::now() inside execute_batch produces states that agree most of the time but diverge under any timing difference — the invariant I4 violation appears only under load. Applied in: Phase 1 (§13 StateMachine, digest()), Design Principle P1, and Phase 11 (§23 VOPR reference model comparison).

MM2 — The WAL is the truth; everything else is a cache. Expert insight: the LSM, in-memory HashMaps, and block cache are all derived indices over the WAL. If there is ever a conflict, the WAL wins. What it predicts: you can always rebuild the entire LSM from a WAL replay; you cannot rebuild the WAL from the LSM. Bug class without it: writing to LSM first and treating the WAL as a secondary record leads to undetectable data loss on power failure before the WAL write completes. Applied in: Design Principle P7, Phase 4 (§16 RecoveryReplay), Phase 9 (§21 checkpoint ordering — LSM flush must precede superblock write).

MM3 — fsync is a fence, not a write. Expert insight: pwrite writes to the OS page cache; fsync flushes the page cache to the storage device's on-disk buffer; on NVMe with power-loss protection, fsync guarantees persistence. Without power-loss protection, fsync returns after the volatile DRAM cache is flushed — not after the flash medium. What it predicts: consumer NVMe drives without power-loss capacitors can lose data even after fsync. Bug class without it: treating pwrite return as a durability guarantee causes silent data loss on power failure. Applied in: Phase 4 (§16 AppendLog::fsync, WAL write discipline), Phase 6 (§18 primary fsync before prepare-ok), §4 (RPO = 0 guarantee).

MM4 — Quorum is the unit of durability, not the individual node. Expert insight: in a 3-replica VSR cluster (f=1), a write is durable when f+1 = 2 replicas have fsynced it — because at least one of those 2 replicas will survive any single failure. What it predicts: a replica that has fsynced a prepare but not yet received CommitMessage can safely be the log carrier after a view-change. Bug class without it: waiting for all 3 replicas to fsync before committing turns a single slow disk into a latency bottleneck, while waiting for only 1 (the primary) violates durability. Applied in: Phase 6 (§18 QuorumTracker, f+1 threshold), §4 (Availability 99.99%, RPO = 0).

MM5 — Client-assigned IDs make idempotency free. Expert insight: if the client owns the ID namespace, re-submitting the same operation with the same ID is unconditionally idempotent — the server looks up the stored result and returns it. The server never needs distributed locking, compare-and-swap, or sequence coordination to provide exactly-once semantics. What it predicts: any re-submission with a matching ID is safe; the only risk is a bug in the DedupIndex (not checking ID before validation). Bug class without it: server-assigned IDs require the client to remember whether a prior request succeeded, leading to duplicate inserts on retry. Applied in: Phase 1 (§13 IdempotencyGuard, DedupIndex), Design Principle P6, System Invariant I7.

MM6 — Static allocation eliminates tail latency from allocators. Expert insight: every malloc call can trigger a page fault, a lock on the allocator, or a compaction. In a latency-sensitive single-threaded loop, a 10 ms GC pause — or even a 50 µs allocator stall — violates p999 targets. Pre-allocating all memory at startup bounds every operation to the pre-allocated pools. What it predicts: any Box::new or Vec::push without pre-allocated capacity in the hot path will show up in the tail latency flamegraph. Bug class without it: passing the average case while failing p999 SLOs under load. Applied in: Design Principle P5, Phase 12 (§24 heaptrack audit), §4 (p999 < 20 ms, memory ceiling 6 GB static).

MM7 — A linked chain is a mini-transaction, not a loop. Expert insight: linked chains achieve multi-transfer atomicity entirely within the single-threaded state machine by speculative application to a StateDelta and conditional commit — no locks, no WAL rollback record, no undo log. This works because the state machine is the only writer. What it predicts: the chain must be evaluated entirely in memory before any WAL append; WAL append is the commit point. Bug class without it: appending WAL entries for each event in the chain independently then trying to "undo" on failure violates the crash-safety model because a partial WAL is unrecoverable. Applied in: Phase 3 (§15 LinkedChainEval, StateDelta), Design Principle P13, System Invariant I8.

MM8 — The LSM bloom filter is a probabilistic bail-out, not a lookup. Expert insight: a bloom filter does not return the value — it returns "definitely absent" or "possibly present". A false positive causes an unnecessary disk read (one extra SST probe); a false negative is impossible by construction. Sizing the bloom filter correctly (k=7 hashes, ≤ 1% FPR) means 99% of absent-key lookups skip the disk entirely. What it predicts: without a bloom filter, every absent-key lookup requires touching every SST level, turning O(1) point lookups into O(L) disk reads. Bug class without it: a cache-cold lookup for a non-existent transfer ID reads every SST file, collapsing throughput under any skewed key distribution. Applied in: Phase 5 (§17 BloomFilter k=7, 1% FPR target), §4 (FD budget < 512 per replica).

Back-of-Envelope Capacity Model

All numbers derived step-by-step from §4 System Constraints.

1. Record storage — accounts. From §4: max accounts per node = 1 × 10⁹; record size = 128 bytes (§11). 1 × 10⁹ accounts × 128 bytes/account = 128 GB — matches §4 "128 GB storage" annotation.

2. Record storage — transfers. From §4: max transfers per node = 1 × 10¹⁰; record size = 128 bytes. 1 × 10¹⁰ transfers × 128 bytes/transfer = 1.28 TB — matches §4 "1.28 TB storage" annotation.

3. Batch size → events per message. From §4: batch size = 8 KiB per message; record size = 128 bytes. 8,192 bytes ÷ 128 bytes/event = 64 events/message — but §4 notes "~2,048 events @ 128 bytes". Reconciliation: 8 KiB frame header is small (≈ 32 bytes); effective payload ≈ 8,160 bytes → 8,160 ÷ 128 = ~63.75, rounded to 64. The §4 "~2,048" figure refers to the maximum batch the client auto-splits at (§20.2: "> 2048 events"); the network frame carries up to ~64 events. Throughput target: 200 K transfers/sec ÷ 64 events/frame = 3,125 frames/sec into the state machine under VSR.

4. Throughput → WAL write rate (3-replica VSR). From §4: 3-replica throughput target = 200 K transfers/sec; each PrepareMessage payload = 1 transfer × 128 bytes + VSR header overhead (~100 bytes) ≈ 228 bytes. 200,000 prepares/sec × 228 bytes/prepare = 45.6 MB/sec WAL write rate — well within §4 WAL append target (≥ 500 MB/s); WAL is not the bottleneck at 200 K tps.

5. Throughput → fsync rate. From §4: p50 commit latency < 1 ms. Without batching: 1 fsync per prepare × 200,000 prepares/sec = 200,000 fsyncs/sec — catastrophic. With pipeline depth = 32 (§4 "Batch pipeline depth"): 200,000 ÷ 32 = 6,250 fsyncs/sec; at 1 ms fsync latency, 1,000 ms/sec ÷ 1 ms/fsync = 1,000 fsyncs/sec max on a single thread. Therefore: pipeline depth must be ≥ 200,000 ÷ 1,000 = 200 to sustain 200 K tps with 1 ms fsync. The §4 "32 in-flight prepares" is a conservative starting point; tuning upward is expected during Phase 12.

6. Memory — LSM block cache. From §4: 4 GB static block cache; block size = 4 KB (§17). 4 GB ÷ 4 KB/block = 1,048,576 blocks cached. Hot account set: 64 K hot accounts × 128 bytes = 8 MB — fits entirely in cache. Full 1 × 10⁹ accounts: 128 GB >> 4 GB cache; cold accounts require disk reads. Bloom filter check prevents most unnecessary cold reads.

7. Memory — pending index upper bound. From §4: memory ceiling = 6 GB static; record size = 128 bytes. Maximum pending transfers: (6 GB - 4 GB cache - ~1 GB other) × 1 / 128 bytes = 1 GB ÷ 128 bytes ≈ 8 × 10⁶ pending transfers resident in memory. §17 pitfall: "1 M pending transfers = 128 MB" — budget is comfortable.

8. WAL zone capacity → time to fill. From §4: WAL zone = 256 GB; WAL write rate at 200 K tps ≈ 45.6 MB/sec (derived above). 256 GB ÷ 45.6 MB/sec ≈ 5,754 sec ≈ 96 minutes before WAL wraps. §21 checkpoints every 60 s or at 50% WAL fill (~128 GB ÷ 45.6 MB/sec ≈ 48 min). 60-second trigger fires first — WAL never approaches 50% fill at sustained 200 K tps.

9. Network bandwidth — replica-to-replica. From §4: 3-replica; each PrepareMessage ≈ 228 bytes; 200 K prepares/sec; primary sends to 2 backups. 228 bytes × 200,000/sec × 2 = 91.2 MB/sec outbound on primary — requires a 1 Gbps NIC; typical NVMe servers have 10–25 Gbps; headroom is ample.

10. File descriptor budget. From §4: FD budget < 512 per replica. WAL: 1 FD. LSM per tree: memtable + up to ~10 SSTables per level × 3 levels × 4 trees = ~120 SST FDs. Sockets: replica-to-replica TCP = 2 FDs; client connections = up to ~100 FDs (bounded by session limit). Total: 1 + 120 + 2 + 100 ≈ 223 FDs — within §4's 512 FD budget with margin for compaction temp files.

11. Startup recovery time. From §4: startup time < 5 s; WAL write rate at 200 K tps = 45.6 MB/sec; checkpoint every 60 s. WAL delta since last checkpoint: 45.6 MB/sec × 60 sec = 2.74 GB. NVMe read rate (WAL replay): §16 target ≥ 500 MB/s. 2.74 GB ÷ 500 MB/sec = 5.48 sec — marginally over §4 target. Mitigation: increase checkpoint frequency to 30 s → 45.6 × 30 = 1.37 GB ÷ 500 MB/sec = 2.7 sec recovery. §21 pipeline note: if state machine apply is the bottleneck (not disk read), parallelize WAL decode from state machine apply.

12. Write amplification — LSM. From §4: write amplification ≤ 1.5×. Fixed-record LSM with 3 levels: L0 → L1 merge = 1 rewrite; L1 → L2 merge overlaps ~10 L1 files per 1 L2 file (size ratio). With fixed 128-byte records and size-tiered compaction, measured write amplification for sequential key inserts is typically 1.1–1.3×. Bloom filters reduce read amplification; write amplification is dominated by the L0→L1 merge ratio, bounded by the level size ratio set in Level::max_bytes.

Alternative Architectures

Alternative 1 — Append-Only Event Log (Kafka-style)

Client ──► Kafka Topic (transfers) ──► Consumer Group ──► Materialized Views
                                              │
                                       balance-service-1 (ledger A)
                                       balance-service-2 (ledger B)
                                              │
                                       PostgreSQL / RocksDB (per-service)

Regime where it wins: read-heavy analytics ledgers where the history of all events is more valuable than the current balance, event replay for audits is frequent, and throughput > correctness isolation is acceptable. Systems that embody this: Apache Kafka + Flink for financial event streaming at companies like Uber (Kafka-based money movement audit logs, as described in their engineering blog).

Why rejected here: the double-entry invariant (I1) requires atomic debit + credit in a single commit. In the event-log model, the two halves of a transfer are separate events; enforcing Σdebits == Σcredits requires a coordinator that scans all consumer offsets — introducing exactly the distributed coordination complexity we are avoiding. The ordering guarantee requires a distributed lock or consensus at the Kafka partition level, reverting to VSR-equivalent complexity with more moving parts.

Alternative 2 — Multi-Version Concurrency Control (MVCC) Row Store

Client ──► SQL Layer ──► MVCC Transaction Manager
                              │
                    ┌─────────┴──────────┐
              Account Table (MVCC)   Transfer Table (MVCC)
                    │                         │
              WAL (Postgres-style)     WAL (Postgres-style)

Regime where it wins: general-purpose financial platforms where the application requires arbitrary SELECT queries, schema evolution (ALTER TABLE), and rich reporting (aggregations by code:u16, range scans on timestamp). CockroachDB and PostgreSQL embody this; Stripe's core billing engine is believed to be PostgreSQL-backed.

Why rejected here: MVCC stores multiple versions of each row, multiplying storage for a write-heavy ledger. Garbage collection of old versions introduces latency jitter incompatible with the p999 < 20 ms target (§4). The lock-free concurrency model in MVCC requires version chains to be traversed on every read, adding O(V) overhead per lookup where V is version count — opposite of the O(1) fixed-record LSM design. Most critically, the double-entry invariant is enforced at the application layer in SQL via triggers or application code, not as a storage primitive.

Alternative 3 — Shared-Disk Cluster (Oracle RAC-style)

                   Shared NVMe-oF / SAN
                          │
           ┌──────────────┼──────────────┐
      Node 1 (R/W)   Node 2 (R/W)   Node 3 (R/W)
           └──────────────┴──────────────┘
                   Distributed Lock Manager

Regime where it wins: workloads where read scaling across many nodes is critical and the storage budget allows a high-end SAN. Oracle RAC is the canonical embodiment; it is used by banks and payment processors that cannot migrate away from Oracle SQL semantics. Wins when cross-node read throughput > write throughput and the organization already operates a SAN fabric.

Why rejected here: the distributed lock manager (DLM) becomes a bottleneck for write-heavy workloads — acquiring a lock on an account record before mutation serializes access back to a single node. For financial ledgers where writes are the critical path (every payment is a write), the DLM overhead exceeds the benefit of shared storage. This blueprint eliminates the problem by making each replica a full copy and using consensus (VSR) for write ordering, avoiding any shared mutable state.

Alternative 4 — Pure In-Memory with Replication (Redis Sentinel-style)

Client ──► Redis Primary (all state in RAM) ──► Sentinel ──► Replicas (async)
                                                               (no fsync)

Regime where it wins: extreme low-latency trading systems where sub-100 µs commit latency is required and the business can tolerate eventual loss of recent transactions on power failure (acceptable for ephemeral order books but not settlement). Redis Cluster with AOF persistence is the canonical embodiment; used by fintech companies for rate limiting and real-time balance caches (not authoritative ledgers).

Why rejected here: async replication means acknowledged writes can be lost on primary failure — RPO > 0. This violates the RPO = 0 requirement (§4) which is non-negotiable for an authoritative financial ledger. Upgrading to synchronous replication eliminates the latency advantage. Storing 1 × 10⁹ accounts × 128 bytes = 128 GB in RAM per replica also exceeds the §4 6 GB static memory ceiling by 21×. This design trades safety for speed in a way incompatible with financial auditability.
