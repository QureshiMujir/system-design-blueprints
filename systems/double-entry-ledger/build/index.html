⬜ Phase 0 — Repository Bootstrap + Record Layout §12

Objectives
  • Initialize double-entry-ledger Cargo workspace with all 7 crates.
  • Define all #[repr(C, packed)] record types with zerocopy traits.
  • Implement and verify 128-byte size/alignment invariants.
  • Establish CI pipeline: fmt, clippy, test, cargo-audit, cargo-deny.
  • Produce ledger-ctl skeleton with version/help output.
Deliverable

Compilable Cargo workspace; all 7 crates build with zero warnings; CI green. ledger-ctl --version prints version string. cargo test passes all record layout tests.

Acceptance
  • size_of::<Account>() == 128 (compile-time assert).
  • size_of::<Transfer>() == 128 (compile-time assert).
  • Zero unsafe in ledger-core.
  • cargo clippy -- -D warnings passes.
  • cargo audit passes (no known vulnerabilities).
  • cargo test 100% pass rate on 20+ unit tests.
  • CI pipeline green on first PR.
Fixtures
  • conformance/fixtures/accounts/valid_account.json — canonical 128-byte account creation payload.
  • conformance/fixtures/malformed/reserved_field_nonzero.json — reserved field set; expected ReservedField error.
  • conformance/fixtures/malformed/zero_id.json — id=0; expected IdMustNotBeZero.
  • conformance/fixtures/malformed/overflow_amount.json — amount = u128::MAX; expected Overflow.
Pitfalls
  • Packed struct alignment: #[repr(C, packed)] makes fields unaligned; never take &account.field reference — use zerocopy read_unaligned or ptr::read_unaligned. UB otherwise.
  • static_assert at wrong crate level: assert inside #[cfg(test)] only runs in test mode; use const _: () = assert!(...) at module level.
  • bitflags! vs raw u16: bitflags! macro prevents unknown-bit errors only if .from_bits_truncate is used; use .from_bits() (returns None on unknown bits) in validation path.
  • Cargo workspace resolver v1 vs v2: resolver = "2" required for no_std feature unification; forgetting it causes feature leakage across crates.

⬜ Phase 1 — Deterministic State Machine (Single-Node, In-Memory) §13

Objectives
  • Implement StateMachine::execute_batch with full account/transfer create and lookup operations.
  • Enforce all field-level validations (reserved fields, zero amounts, mismatched ledgers).
  • Implement IdempotencyGuard (DedupIndex) for exactly-once create semantics.
  • No WAL, no LSM yet — all state in-memory HashMaps.
  • Produce a runnable binary that processes event batches and returns result codes.
Deliverable

cargo run --bin ledger-ctl accounts create --id <uuid> creates account and returns result JSON. cargo run --bin ledger-ctl transfers create ... creates transfer. cargo test passes 50+ state machine tests.

Acceptance
  • All 30+ CreateAccountError variants tested with a fixture.
  • All 30+ CreateTransferError variants tested with a fixture.
  • Idempotency: second create with same ID returns None error and prior account/transfer unchanged.
  • execute_batch with 2048 events processes in < 10 ms (in-memory; no I/O).
  • digest() produces identical hash for identical ordered inserts on two separate StateMachine instances.
  • Zero heap allocations in execute_batch beyond pre-allocated result Vec.
Fixtures
  • conformance/fixtures/accounts/create_valid.json + expected_result.json
  • conformance/fixtures/accounts/create_idempotent.json — same ID twice; second result = Exists code
  • conformance/fixtures/transfers/create_valid_immediate.json — immediate (non-pending) transfer
  • conformance/fixtures/transfers/mismatched_ledger.json — debit/credit on different ledgers
  • conformance/fixtures/transfers/balance_constraint_violation.json — overdraft attempt
Pitfalls
  • Dedup check must precede all other validation: if an ID was previously rejected, the dedup index stores the error; re-submitting must return the stored error without re-validating.
  • Mutable borrow of two accounts simultaneously: Rust borrow checker prevents &mut account_a and &mut account_b simultaneously from the same HashMap; use get + clone → mutate → re-insert pattern or split into entry API.
  • Timestamp assignment: timestamp is assigned by the caller (VSR primary); StateMachine must not call SystemTime::now() internally (non-deterministic).
  • Zero-amount check before account lookup: avoids wasted lookup for obviously invalid transfers.

⬜ Phase 2 — Balance Constraints + Two-Phase Transfers §14

Objectives
  • Implement PhaseResolver for pending → posted/voided/expired transitions.
  • Implement TimeoutSweep for auto-void of expired pending transfers.
  • Enforce pending-fund conservation invariant (I3).
  • Implement partial post (post amount ≤ pending amount).
Deliverable

Two-phase transfer demo: examples/two_phase_payment.rs runs create-pending → post-pending in memory; prints before/after balances.

Acceptance
  • Pending funds conserved: (debit.debits_pending + debit.debits_posted) increases by exactly amount on pending create.
  • Post-pending: debits_pending decreases and debits_posted increases by exact amount.
  • Void-pending: debits_pending and credits_pending decrease; posted unchanged.
  • Partial post: remaining reserved amount released.
  • Auto-void at timeout: VOPR advances cluster time; pending transfer voided; balances restored.
  • PendingTransferAlreadyPosted and PendingTransferAlreadyVoided errors returned on double-resolve.
Fixtures
  • conformance/fixtures/two_phase/pending_post_full.json
  • conformance/fixtures/two_phase/pending_post_partial.json
  • conformance/fixtures/two_phase/pending_void.json
  • conformance/fixtures/two_phase/pending_timeout.json
  • conformance/fixtures/two_phase/double_post.json — expected PendingTransferAlreadyPosted
Pitfalls
  • Timeout unit mismatch: timeout field is seconds; cluster_time is nanoseconds; conversion: pending.timestamp + (pending.timeout as u64 * 1_000_000_000) ≤ cluster_time.
  • Partial post balance math: total released = pending.amount - transfer.amount; must credit back to both pending accounts.
  • PendingIndex out of sync with TransferStore: on void/post, remove from PendingIndex AND update TransferStore state; doing only one leaves ghost entries.
  • TimeoutSweep modifying PendingIndex during iteration: collect IDs first; then apply voids in second pass.

⬜ Phase 3 — Linked Atomic Chains §15

Objectives
  • Implement LinkedChainEval for all-or-nothing batch atomicity.
  • Implement in-memory rollback on chain failure (no WAL yet).
  • Produce per-event result codes: LinkedEventFailed, LinkedEventChainOpen, actual error.
  • Verify via VOPR: inject failure at each position in N-length chain; verify rollback.
Deliverable

conformance/fixtures/linked_chains/ pass. VOPR enabled for chain tests: generate random chains with injected failures; verify rollback.

Acceptance
  • N-event chain fails at position K: events 0..K-1 = LinkedEventFailed; event K = actual error; events K+1..N = LinkedEventChainOpen.
  • Successful chain: all events = None (success).
  • Mixed batch (chain A succeeds, chain B fails): chain A committed; chain B rolled back; independent chains do not interfere.
  • StateMachine::digest() after failed chain = identical to digest before batch.
Fixtures
  • conformance/fixtures/linked_chains/two_event_success.json
  • conformance/fixtures/linked_chains/two_event_fail_at_1.json
  • conformance/fixtures/linked_chains/five_event_fail_at_3.json
  • conformance/fixtures/linked_chains/mixed_chains.json
  • conformance/fixtures/linked_chains/single_event_linked.json — single event with linked=1 is an open chain; LinkedEventChainOpen error
Pitfalls
  • linked=1 on last event in batch: chain never closed; all events = LinkedEventChainOpen. Must detect and error before execution.
  • StateDelta must snapshot balances before chain starts: if rollback needed, must restore exact prior values; copy-on-write pattern.
  • Dedup interaction: if chain fails after some events were dedup-registered, dedup entries must also be rolled back.
  • Nested chains: not supported; linked flag connects adjacent events only; no nesting. Validate: chains are flat sequences.

⬜ Phase 4 — Write-Ahead Log + Crash Recovery §16

Objectives
  • Implement AppendLog with sector-aligned writes, per-sector CRC32C, fsync discipline.
  • Implement TornWriteDetector for recovery.
  • Implement Superblock with checkpoint LSN tracking.
  • Implement RecoveryReplay: replay WAL from checkpoint LSN into state machine.
  • Achieve zero data loss for committed operations after process restart.
Deliverable

Process can crash mid-operation; restart replays WAL; state identical to pre-crash committed state. ledger-ctl wal dump outputs sector log. Benchmark: WAL append + fsync latency measured.

Acceptance
  • Crash after fsync returns: all fsynced operations present after recovery.
  • Crash before fsync: uncommitted operations absent after recovery; no partial state.
  • Torn write at last sector: TornWriteDetector identifies and truncates; no panic.
  • Recovery produces identical StateMachine::digest() as pre-crash state.
  • WAL append throughput ≥ 500 MB/s (sequential NVMe).
  • p99 fsync latency < 1 ms on dedicated NVMe.
Fixtures
  • conformance/fixtures/wal/clean_recovery.bin — valid WAL; expect identical post-recovery state
  • conformance/fixtures/wal/torn_last_sector.bin — last sector corrupt CRC; expect truncation to prior LSN
  • conformance/fixtures/wal/partial_payload.bin — sector truncated mid-payload; expect skip + truncation
  • conformance/fixtures/wal/empty_wal.bin — fresh start; expect empty state machine
Pitfalls
  • O_DIRECT alignment: pwrite buffers must be sector_size-aligned; use aligned_alloc or posix_memalign; Rust Vec is NOT guaranteed aligned to sector boundaries.
  • Double superblock write: superblock update is not atomic for >1 sector; use ping-pong (write to A, validate, write to B); read newest valid on open.
  • fsync vs fdatasync: use fsync for WAL (metadata + data); fdatasync is insufficient for new files where size metadata must be durable.
  • LSN gap on recovery: if WAL has a gap (missing sector), treat everything after gap as potentially corrupt; truncate to gap start.
  • Recovery replay idempotency: StateMachine::execute_batch during replay must not re-register dedup entries twice; replay path passes is_recovery=true flag to skip dedup write.

⬜ Phase 5 — LSM-Forest Object Store §17

Objectives
  • Implement ledger-lsm: fixed-record LSM with 4 trees (accounts, transfers, pending, dedup).
  • Implement memtable (sorted BTreeMap<u128, [u8;128]>) → L0 SSTable flush.
  • Implement tiered compaction (L0→L1→L2); manifest log; bloom filters.
  • Replace in-memory HashMaps in ledger-state with LSM-backed stores.
  • Achieve O(1) point lookups (bloom filter + binary search in SST).
Deliverable

Full persistence: accounts and transfers survive process restart via WAL replay into LSM. LSM inspection via ledger-ctl. Benchmark: point lookup latency vs. dataset size.

Acceptance
  • Point lookup: O(1) with bloom filter hit; measured ≤ 5 µs p99 after warm cache.
  • Bloom filter false positive rate ≤ 1% (measured via cargo test -- bloom_false_positive).
  • Compaction produces no missing records (verified by full scan before/after compaction).
  • Manifest log survives crash; no orphaned SST files on recovery.
  • LSM write amplification ≤ 1.5× at steady-state insert workload.
  • Forest::get_account returns identical account to HashMap implementation for same input (differential test).
Fixtures
  • conformance/fixtures/lsm/insert_and_lookup.bin — 10K accounts; verify all lookups succeed
  • conformance/fixtures/lsm/compaction_correctness.bin — pre/post compaction; all records present
  • conformance/fixtures/lsm/bloom_false_positive.bin — 1M absent keys; FP count ≤ 10K (1%)
  • conformance/fixtures/lsm/manifest_recovery.bin — crash mid-compaction; manifest replay; no orphans
Pitfalls
  • O_DIRECT SST reads must be sector-aligned: SST block offset must align to block_size; round down during read; adjust pointer into block.
  • Bloom filter size for small tables: minimum bit array prevents degenerate FP rates for 1-record tables; clamp to min 64 bytes.
  • Compaction deletes old SSTs before manifest commit: if crash between delete and manifest update, phantom SST references; always commit manifest BEFORE deleting files.
  • Memtable unbounded growth: flush trigger at memtable.len() > MEMTABLE_MAX (e.g., 65536 records); back-pressure on inserts if L0 has too many tables (compaction lagging).
  • Key collisions between trees: each tree has its own file namespace; never share an SST between trees.

⬜ Phase 6 — VSR Consensus: Normal Mode §18

Objectives
  • Implement VSR normal mode: primary sequences operations; backups apply in order.
  • Implement PrepareMessage / PrepareOkMessage / CommitMessage flow.
  • Implement quorum tracking: f+1 prepare-oks required before commit.
  • Integrate with WAL: fsync on prepare; commit on quorum.
  • 3-replica cluster processes client batches with VSR-ordered durability.
Deliverable

3-replica cluster accepts client batches; all 3 replicas have identical state after each commit. ledger-ctl cluster status shows view, op_number, commit_number per replica.

Acceptance
  • All 3 replicas apply identical operations in identical order (verified by digest() comparison after 10K ops).
  • Client receives response only after quorum fsync (no response before f+1 prepare-oks).
  • Throughput ≥ 100 K transfers/sec (3-replica, in-process, NVMe).
  • p99 commit latency < 5 ms (3-replica, same-host loopback).
  • CommitMessage gap (backup missed a prepare): backup detects gap by op_number discontinuity; requests retransmit.
Fixtures
  • conformance/fixtures/vsr/normal_mode_10ops.bin — 10 prepare/commit cycles; verify all ops committed
  • conformance/fixtures/vsr/out_of_order_prepare.bin — backup receives op 5 before op 4; expect stash + apply in order
  • conformance/fixtures/vsr/commit_without_prepare_ok.bin — commit arrives without prior prepare-ok; backup applies if op already in log
Pitfalls
  • Op number gaps: backup must buffer prepares received out of order; apply strictly in order.
  • Primary sends CommitMessage without waiting for all backups: CommitMessage announces commit_number; backups apply up to it; only primary knows quorum was reached.
  • View mismatch: if backup's view != message.view, discard or trigger view-change check.
  • Client response before quorum: primary must wait for f+1 PrepareOkMessage before responding to client; avoid premature ack.

⬜ Phase 7 — VSR View-Change + State Transfer §19

Objectives
  • Implement VSR view-change protocol: StartViewChangeMessage / DoViewChangeMessage / StartViewMessage.
  • Implement state transfer: RequestStartViewMessage / StateTransferChunk flow.
  • Handle primary failure: backups elect new primary within RTO < 30 s.
  • Recovering replica receives full state from current primary; resumes normal mode.
Deliverable

Kill primary process; cluster elects new primary within 5 s; new primary serves client requests; old primary restarts and receives state transfer; all 3 replicas converge.

Acceptance
  • RTO (primary failure to new primary serving): < 30 s (target < 5 s in same-DC).
  • View-change triggered: (view+1) mod cluster_size becomes new primary.
  • Recovering replica converges to primary state within 60 s for 1 GB WAL delta.
  • State transfer chunk checksum verification: any corrupt chunk triggers re-request.
  • After recovery: digest() of recovering replica == digest() of primary.
  • No committed operations lost during view-change (VSR safety guarantee).
Fixtures
  • conformance/fixtures/vsr/primary_failure_view_change.bin — simulate primary stop; verify view-change messages and new primary election
  • conformance/fixtures/vsr/state_transfer_1000ops.bin — recovering replica misses 1000 ops; receives state transfer; verifies digest match
  • conformance/fixtures/vsr/split_network.bin — partition: 2 of 3 replicas proceed; 1 isolated; verify isolated replica halts and recovers on reconnect
Pitfalls
  • View-change timer race: two backups trigger view-change simultaneously; both send StartViewChangeMessage(view+1); harmless — first f+1 collection wins; higher-view messages ignored.
  • Log truncation by new primary: new primary may have shorter log than a backup; backup must accept StartViewMessage and truncate its log accordingly.
  • State transfer during active writes: primary must not compact or delete WAL segments being transferred; hold compaction lock during state transfer.
  • Heartbeat storm: on primary recovery, suppress initial heartbeats until state is current; stale heartbeats with old view cause unnecessary view-change triggers.

⬜ Phase 9 — Checkpoints + Superblock Management §21

Objectives
  • Implement periodic LSM checkpoint: flush all memtables; write superblock with checkpoint_lsn + state_hash.
  • Implement WAL truncation up to checkpoint: circular WAL zone management.
  • Reduce recovery time: replay only WAL delta since last checkpoint.
  • Implement dual-superblock (ping-pong) atomic writes.
Deliverable

Checkpoint demo: 1M transfers → checkpoint → kill process → restart → digest() match. Recovery time < 5 s (WAL delta < 1 GB).

Acceptance
  • Superblock write atomic: crash during ping-pong leaves one valid copy; open always finds valid superblock.
  • WAL sectors before checkpoint_lsn reclaimed: WAL file never grows beyond pre-allocated zone.
  • Recovery time < 5 s for WAL delta ≤ 256 MB (measured via criterion benchmark).
  • state_hash in superblock matches StateMachine::digest() post-recovery.
  • Checkpoint overhead < 100 ms for 1M accounts + 1M transfers (measured).
Fixtures
  • conformance/fixtures/checkpoint/full_checkpoint.bin — checkpoint sequence; verify superblock content
  • conformance/fixtures/checkpoint/crash_during_superblock_write.bin — kill mid-write; verify recovery uses valid copy
  • conformance/fixtures/checkpoint/wal_zone_wraparound.bin — WAL reaches end of zone; verify reclaim and continued appends
Pitfalls
  • LSM flush before superblock write: must fsync all SSTs before writing superblock; superblock records LSM state that must be durable.
  • WAL reclaim races with recovery: if crash occurs just after reclaim marker is written but before new superblock is committed, recovery may try to replay from a reclaimed LSN; validate superblock before using checkpoint_lsn.
  • Checkpoint blocking client requests: checkpoint runs on a background thread; WAL appends must not be blocked; use a brief WAL flush lock only during superblock write.

⬜ Phase 10 — io_uring Integration §22

Objectives
  • Replace pread/pwrite/fsync syscalls with io_uring submission ring.
  • Register fixed buffers for WAL and LSM I/O.
  • Batch multiple I/O operations into single io_uring_enter call.
  • Measure throughput improvement vs. baseline syscall approach.
Deliverable

WAL append + fsync via io_uring linked SQEs. LSM block reads via io_uring. Benchmark showing ≥ 20% throughput improvement vs. syscall baseline.

Acceptance
  • WAL append correctness unchanged (all P4 conformance fixtures pass).
  • LSM read correctness unchanged (all P5 conformance fixtures pass).
  • WAL append + fsync throughput ≥ 600 MB/s (vs. 500 MB/s baseline).
  • No io_uring setup errors on Linux 5.10+.
  • IORING_SETUP_SQPOLL: evaluate; disable if CPU overhead exceeds throughput gain.
Fixtures
  • Reuse all WAL and LSM fixtures from P4/P5; verify identical outputs.
Pitfalls
  • io_uring registered buffer alignment: fixed buffers must be page-aligned (4096 bytes); use mmap(MAP_ANONYMOUS | MAP_LOCKED).
  • Completion order: io_uring CQEs may arrive out of submission order; use user_data tags to match completions to pending ops.
  • IORING_SETUP_SQPOLL requires CAP_SYS_NICE: may not be available in containers; fallback to non-SQPOLL mode.
  • Linked SQE failure: if write SQE fails, linked fsync is cancelled; check both CQEs; handle partial failure.
