Client Layer — ledger-client encodes events into 8 KiB batch frames; handles request/response correlation via session sequence numbers. ledger-ctl is the operator CLI. FFI headers expose a C ABI for non-Rust clients. All clients register sessions; sessions carry monotonic sequence numbers for exactly-once delivery.

ledger-net — decodes UDP/TCP frames into typed Vec<Event> batches; demultiplexes responses to waiting sessions; enforces per-session sliding-window backpressure; validates frame CRC32C before dispatch to state machine.

ledger-state — single-threaded deterministic core; processes one Vec<Event> batch per call; mutates AccountStore, TransferStore, PendingIndex, DedupIndex; enforces all invariants. Only place state changes occur. Bit-identical output given identical ordered input.

ledger-wal — append-only log of PrepareMessage payloads; fsynced before acknowledgement; per-512-byte-sector CRC32C checksums; torn-write detection on open; superblock records checkpoint LSN + WAL offset; recovery replays from checkpoint LSN forward.

ledger-lsm — four LSM trees: accounts, transfers, pending, dedup; fixed 128-byte values; O_DIRECT block I/O; tiered compaction; bloom filters per SSTable; static block cache (4 GB); manifest log for metadata durability.

ledger-vsr — VSR normal mode (prepare/prepare-ok/commit); view-change (start-view-change/do-view-change/start-view); state-transfer (request-start-view/send-state chunks). Drives StateMachine::execute_batch() deterministically; primary sequences batches into numbered PrepareMessages; backups apply identical sequence.

NVMe / Block Device — dedicated partition; O_DIRECT + io_uring; pre-allocated WAL zone + LSM zone; no filesystem cache in critical path; zone boundaries enforced at startup.

8. Domain Model / Protocol

Record Layout (EBNF / bit-level)

Account  ::= id:u128 | debits_pending:u128 | debits_posted:u128
           | credits_pending:u128 | credits_posted:u128
           | user_data:u128 | reserved:u32 | ledger:u32
           | code:u16 | flags:u16 | timestamp:u64
           -- total: 128 bytes

Transfer ::= id:u128 | debit_account_id:u128 | credit_account_id:u128
           | amount:u128 | pending_id:u128 | user_data:u128
           | timeout:u32 | ledger:u32 | code:u16 | flags:u16
           | timestamp:u64
           -- total: 128 bytes

All fields little-endian. timestamp = cluster time (nanoseconds since epoch, assigned by primary). reserved = must be zero (future-proofing). flags = bitmask (see below).

Account Flags Bitmask

Bit Name Semantics
0 linked This event is chained to the next in the batch
1 debits_must_not_exceed_credits Enforce debit ≤ credit at all times (asset)
2 credits_must_not_exceed_debits Enforce credit ≤ debit at all times (liability)
3–15 reserved Must be zero

Transfer Flags Bitmask

Bit Name Semantics
0 linked Chain to next event; all-or-nothing
1 pending Two-phase: reserve funds, do not post
2 post_pending_transfer Resolve a prior pending transfer (post)
3 void_pending_transfer Resolve a prior pending transfer (void)
4 balancing_debit Reduce debits_must_not_exceed_credits violation risk
5 balancing_credit Reduce credits_must_not_exceed_debits violation risk
6–15 reserved Must be zero

Transfer State Machine

                  create(pending=1)
                  ────────────────►  PENDING
                                     │        │           │
               post_pending          │        │ void_pending│  timeout expires
               ────────────►  POSTED │        └───────────► VOIDED
                                     │
                                     └───────────────────► EXPIRED
                                          (auto-void by TimeoutSweep)

State transitions:

Current State Event Next State Preconditions
— create_transfer(pending=0) POSTED (immediate) Accounts exist; ledgers match; amounts valid; balance constraints pass
— create_transfer(pending=1) PENDING Same as above + timeout > 0
PENDING create_transfer(post_pending=1, pending_id=X) POSTED pending_id exists and is PENDING; amount ≤ pending.amount
PENDING create_transfer(void_pending=1, pending_id=X) VOIDED pending_id exists and is PENDING
PENDING cluster_time ≥ pending.timestamp + pending.timeout EXPIRED Auto-applied by TimeoutSweep before each batch

Balance Arithmetic (per posted transfer)

debit_account.debits_pending  -= amount   (if resolving pending)
debit_account.debits_posted   += amount
credit_account.credits_pending -= amount  (if resolving pending)
credit_account.credits_posted  += amount

All ops: checked_add / checked_sub; overflow → CreateTransferError::Overflow.

Linked Chain Semantics

batch = [T1(linked=1), T2(linked=1), T3(linked=0)]
  → T1, T2, T3 form one atomic chain
  → If T2 fails: T1 rolled back in memory; no WAL append for chain
  → Result codes: T1=linked_event_failed, T2=<actual error>, T3=linked_event_failed

Chain detection: scan batch left-to-right; linked flag on event N means N and N+1 are in the same chain; chain ends at first event with linked=0 or last event.

Idempotency Protocol

create_account(id=X):
  1. DedupIndex.lookup(X)
  2. If found: return stored result (no mutation)
  3. If not found: execute, store result in DedupIndex, return result

DedupIndex is an in-memory hash map (backed by LSM dedup tree for durability). Key = u128 ID. Value = CreateAccountResult or CreateTransferResult enum.

Client Protocol (Frame Format)

Frame ::= magic:u32(0x0A_5CA1AB) | checksum:u32 | client_id:u128
        | request_id:u64 | operation:u8 | reserved:u8 | batch_size:u16
        | payload: [Event; batch_size]   -- each Event = 128 bytes

Operations: CREATE_ACCOUNTS=0, CREATE_TRANSFERS=1, LOOKUP_ACCOUNTS=2, LOOKUP_TRANSFERS=3.

Response frame: same header structure; payload = array of result codes (one per input event, u32 each).

Worked Examples

Normal transfer (T-account view)

Transfer: debit_account=A (asset), credit_account=B (liability), amount=100
Before: A.debits_posted=0, B.credits_posted=0
After:  A.debits_posted=100, B.credits_posted=100
Trial balance: Σdebits=100, Σcredits=100 ✓

Two-phase transfer

1. create_transfer(pending=1, amount=50) → PENDING
   A.debits_pending+=50, B.credits_pending+=50
2. create_transfer(post_pending=1, pending_id=P, amount=50) → POSTED
   A.debits_pending-=50, A.debits_posted+=50
   B.credits_pending-=50, B.credits_posted+=50

Balance constraint violation (malformed)

Account A: flags=debits_must_not_exceed_credits, credits_posted=100, debits_posted=90
Transfer: amount=20 to debit A → debits_posted would become 110 > credits_posted=100
Result: CreateTransferError::DebitAccountExceedsCredits (no mutation)

Linked chain partial failure

Batch: [T1(amount=10, linked=1), T2(amount=999999, linked=0)]
T1 valid. T2 violates balance constraint.
Result: T1=linked_event_failed, T2=DebitAccountExceedsCredits
WAL: no append. State: unchanged.

Malformed transfer (zero amount)

Transfer: amount=0
Result: CreateTransferError::AmountMustNotBeZero
