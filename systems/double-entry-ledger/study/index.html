Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. The §4 System Constraints table specifies RPO = 0. Walk through exactly what happens to a client's transfer batch if the primary crashes after AppendLog::fsync returns on the primary but before any backup has received the PrepareMessage. Does the RPO = 0 guarantee hold? Which invariants (§7) and VSR mechanism (§19) are responsible?
  2. A replica diverges: vsr.state_hash_mismatch fires (I4). You check the WAL (§16) and find no corruption. Propose three root causes, each in a different section of this blueprint, and describe which VOPR fault type (§23) would reproduce each.
  3. You must sustain 200 K transfers/sec (§4) with p99 commit latency < 5 ms on a 3-replica cluster. Using the Back-of-Envelope Capacity Model, calculate the maximum fsync pipeline depth required and explain how the WAL design (§16) and VSR normal mode (§18) interact to achieve it.
  4. A client submits a linked chain of 5 transfers (§15). Transfer T3 fails with ExceedsCredits. Trace the exact result codes returned for T1–T5, explain which data structures (§11 StateDelta) are modified and which are not, and verify that StateMachine::digest() (§13) is unchanged after this batch.
  5. The bloom filter for the transfers LSM tree (§17) is sized for 1% false positive rate. At 1 × 10¹⁰ transfers (§4), compute the bit array size in GB. Then explain how the FD budget constraint (§4, < 512 FDs) and static memory ceiling (§4, 6 GB) interact to cap the number of open SSTables, and what compaction policy (§17) prevents unbounded FD growth.
  6. Design Principle P7 says "WAL is the source of truth; LSM is a derived index." Yet Phase 9 (§21) writes the superblock — which records checkpoint_lsn and lsm_root_hash — AFTER lsm.flush_all(). Why must LSM flush precede superblock write? What failure scenario (§21 pitfalls) occurs if the order is reversed, and which invariant (§7) is violated?
  7. Contrast ADR-A09 (VSR) with Raft as implemented in etcd (R3). Specifically: how do log truncation semantics differ during view-change (§19), and why does VSR's approach simplify StateTransferMgr (§19) compared to Raft's log compaction + snapshot mechanism?
  8. A pending transfer has timeout = 60 (seconds) and timestamp = T. The TimeoutSweep (§14) runs at cluster time T + 61,000,000,000 ns. It auto-voids the transfer. Now a client submits post_pending(pending_id = X) in the same batch, after the sweep. What error code is returned, and why must the sweep run at the start of execute_batch rather than the end? Which design principles (§6) mandate this ordering?
  9. The VOPR simulator (§23) uses xoshiro256** seeded PRNG. A bug is found at seed=42, step=500. Describe the exact steps to reproduce, isolate, and add a regression fixture. Which modules (ledger-sim) are involved, and how does the VOPR seed → deterministic replay property (Design Principle P1) enable this without mocking?
  10. The SlidingWindow per-client backpressure (§20) has window_size = 32. A client is producing 10,000 transfers/sec. The primary is under heavy compaction (§17) and execute_batch latency rises from 100 µs to 5 ms. Walk through what happens to client throughput, in-flight request count, and the net.in_flight_requests metric (Operational Readiness). Does the system deadlock? Identify the relevant pitfall in §20.
  11. You must add a new 128-byte record type Adjustment to support regulatory reversals (not in current scope). Identify every section of this blueprint that must change: record layout (§11), state machine (§13), WAL (§16), LSM (§17), client protocol (§8), VOPR (§23), and compatibility guarantees. Which compatibility guarantee in the Compatibility section is the hardest constraint?
  12. The §4 constraint specifies < 5 s startup time. The Back-of-Envelope Capacity Model (this section) shows that at 200 K tps, the WAL delta since last checkpoint can approach 2.74 GB. Identify the two optimization levers in Phase 9 (§21) and Phase 10 (§22) that reduce recovery time, and explain the trade-off each makes against write amplification or CPU usage.
  13. Explain why ADR-A06 (single-threaded state machine) is both the source of the system's throughput ceiling and its freedom from locking. Then explain what would need to change in §13, §15, §17, and §23 if you were to introduce a second writer thread for a different ledger namespace — and why this would compromise Design Principle P1.
  14. The Threat Model identifies "non-deterministic divergence" as a threat vector mitigated by Design Principle P1. Given the state machine calls cluster_time: u64 (set by the VSR primary). Describe exactly how the primary serializes the timestamp into the PrepareMessage (§18), how the backup applies it (§18), and why this preserves determinism even if the two replicas have different CLOCK_MONOTONIC_RAW values.
  15. The IdempotencyGuard (§13, I7) stores results in DedupIndex, which is backed by the dedup LSM tree (§17) for durability. During WAL recovery (§16), RecoveryReplay replays PrepareMessages. If is_recovery=true skips DedupIndex writes (§16 pitfall), how does the system ensure idempotency for subsequent client re-submissions after recovery? Which invariant and which Design Principle define the correct behavior? ---

Mental Models & First Principles

MM1 — The state machine is a pure function. Expert insight: execute_batch(events, timestamp) → results is a total, deterministic function; given identical inputs on any replica it produces bit-identical outputs and bit-identical next state. What it predicts: any non-determinism source (system clock, pointer hash, thread scheduling) will cause replica divergence. Bug class without it: calling SystemTime::now() inside execute_batch produces states that agree most of the time but diverge under any timing difference — the invariant I4 violation appears only under load. Applied in: Phase 1 (§13 StateMachine, digest()), Design Principle P1, and Phase 11 (§23 VOPR reference model comparison).

MM2 — The WAL is the truth; everything else is a cache. Expert insight: the LSM, in-memory HashMaps, and block cache are all derived indices over the WAL. If there is ever a conflict, the WAL wins. What it predicts: you can always rebuild the entire LSM from a WAL replay; you cannot rebuild the WAL from the LSM. Bug class without it: writing to LSM first and treating the WAL as a secondary record leads to undetectable data loss on power failure before the WAL write completes. Applied in: Design Principle P7, Phase 4 (§16 RecoveryReplay), Phase 9 (§21 checkpoint ordering — LSM flush must precede superblock write).

MM3 — fsync is a fence, not a write. Expert insight: pwrite writes to the OS page cache; fsync flushes the page cache to the storage device's on-disk buffer; on NVMe with power-loss protection, fsync guarantees persistence. Without power-loss protection, fsync returns after the volatile DRAM cache is flushed — not after the flash medium. What it predicts: consumer NVMe drives without power-loss capacitors can lose data even after fsync. Bug class without it: treating pwrite return as a durability guarantee causes silent data loss on power failure. Applied in: Phase 4 (§16 AppendLog::fsync, WAL write discipline), Phase 6 (§18 primary fsync before prepare-ok), §4 (RPO = 0 guarantee).

MM4 — Quorum is the unit of durability, not the individual node. Expert insight: in a 3-replica VSR cluster (f=1), a write is durable when f+1 = 2 replicas have fsynced it — because at least one of those 2 replicas will survive any single failure. What it predicts: a replica that has fsynced a prepare but not yet received CommitMessage can safely be the log carrier after a view-change. Bug class without it: waiting for all 3 replicas to fsync before committing turns a single slow disk into a latency bottleneck, while waiting for only 1 (the primary) violates durability. Applied in: Phase 6 (§18 QuorumTracker, f+1 threshold), §4 (Availability 99.99%, RPO = 0).

MM5 — Client-assigned IDs make idempotency free. Expert insight: if the client owns the ID namespace, re-submitting the same operation with the same ID is unconditionally idempotent — the server looks up the stored result and returns it. The server never needs distributed locking, compare-and-swap, or sequence coordination to provide exactly-once semantics. What it predicts: any re-submission with a matching ID is safe; the only risk is a bug in the DedupIndex (not checking ID before validation). Bug class without it: server-assigned IDs require the client to remember whether a prior request succeeded, leading to duplicate inserts on retry. Applied in: Phase 1 (§13 IdempotencyGuard, DedupIndex), Design Principle P6, System Invariant I7.

MM6 — Static allocation eliminates tail latency from allocators. Expert insight: every malloc call can trigger a page fault, a lock on the allocator, or a compaction. In a latency-sensitive single-threaded loop, a 10 ms GC pause — or even a 50 µs allocator stall — violates p999 targets. Pre-allocating all memory at startup bounds every operation to the pre-allocated pools. What it predicts: any Box::new or Vec::push without pre-allocated capacity in the hot path will show up in the tail latency flamegraph. Bug class without it: passing the average case while failing p999 SLOs under load. Applied in: Design Principle P5, Phase 12 (§24 heaptrack audit), §4 (p999 < 20 ms, memory ceiling 6 GB static).

MM7 — A linked chain is a mini-transaction, not a loop. Expert insight: linked chains achieve multi-transfer atomicity entirely within the single-threaded state machine by speculative application to a StateDelta and conditional commit — no locks, no WAL rollback record, no undo log. This works because the state machine is the only writer. What it predicts: the chain must be evaluated entirely in memory before any WAL append; WAL append is the commit point. Bug class without it: appending WAL entries for each event in the chain independently then trying to "undo" on failure violates the crash-safety model because a partial WAL is unrecoverable. Applied in: Phase 3 (§15 LinkedChainEval, StateDelta), Design Principle P13, System Invariant I8.

MM8 — The LSM bloom filter is a probabilistic bail-out, not a lookup. Expert insight: a bloom filter does not return the value — it returns "definitely absent" or "possibly present". A false positive causes an unnecessary disk read (one extra SST probe); a false negative is impossible by construction. Sizing the bloom filter correctly (k=7 hashes, ≤ 1% FPR) means 99% of absent-key lookups skip the disk entirely. What it predicts: without a bloom filter, every absent-key lookup requires touching every SST level, turning O(1) point lookups into O(L) disk reads. Bug class without it: a cache-cold lookup for a non-existent transfer ID reads every SST file, collapsing throughput under any skewed key distribution. Applied in: Phase 5 (§17 BloomFilter k=7, 1% FPR target), §4 (FD budget < 512 per replica).

Glossary · 44 terms · site-wide glossary

Double-Entry
Accounting invariant: every monetary transaction has equal debit and credit entries; Σdebits == Σcredits per ledger always
Debit
A left-side T-account entry; increases asset accounts; decreases liability accounts
Credit
A right-side T-account entry; increases liability accounts; decreases asset accounts
Ledger
Namespace for double-entry balance; identified by ledger:u32; trial balance holds within a ledger
Account
A 128-byte record holding balance state; identified by id:u128
Transfer
A 128-byte record encoding a debit/credit movement between two accounts
Pending Transfer
A two-phase transfer in PENDING state; reserves funds without posting them
Post Pending
Second phase of a two-phase transfer; moves reserved funds to posted balances
Void Pending
Cancels a PENDING transfer; releases reserved funds
Timeout (pending)
Auto-void of a PENDING transfer when cluster_time >= timestamp + timeout
Linked Chain
A sequence of transfers in a single batch all-or-nothing; any failure rolls back the entire chain
Idempotency Guard
DedupIndex: maps event id to prior result; re-create with existing ID returns prior result
WAL
Write-Ahead Log: append-only durability log fsynced before state mutation
LSN
Log Sequence Number: monotonic u64 identifying a WAL position
Superblock
Durable metadata record (dual-copy ping-pong) containing checkpoint_lsn and state_hash
Checkpoint
Durable point in WAL/LSM where WAL can be truncated; recovery replays from here
LSM
Log-Structured Merge-Tree: sorted-run storage engine; fixed-record variant used here
SSTable
Sorted String Table: immutable on-disk sorted file of (key, value) records
Bloom Filter
Probabilistic data structure for fast negative lookups in SST
VSR
Viewstamped Replication: primary-backup consensus protocol (Liskov & Cowling 2012)
View
VSR epoch; incremented on primary failure via view-change
Op Number
VSR operation sequence number; assigned by primary; monotonically increasing
Commit Number
VSR highest committed op; operations up to this are applied to state machine
Prepare
VSR message from primary to backups: "execute this operation at op_number N"
Prepare-Ok
VSR acknowledgement from backup: "I have fsynced prepare N"
Commit
VSR message from primary to backups: "ops up to N are committed; apply them"
View-Change
VSR protocol for electing a new primary after the current primary fails
State Transfer
VSR protocol for a recovering replica to receive full state from the primary
VOPR
TigerBeetle's deterministic simulation framework; fault-injecting randomized history tester
Deterministic State Machine
State machine where identical ordered inputs always produce identical outputs and state
Trial Balance
Accounting check: Σdebits == Σcredits across all accounts in a ledger; must always hold
O_DIRECT
Linux I/O flag bypassing page cache; required for predictable WAL/LSM latency
io_uring
Linux async I/O submission ring; reduces per-operation syscall overhead
f
VSR failure tolerance: cluster of 2f+1 replicas tolerates f failures; f=1 for 3 replicas
Quorum
f+1 replicas agreeing for prepare-ok; 2f+1 replicas for view-change
CRC32C
Castagnoli CRC; hardware-accelerated on x86_64 (SSE4.2) and ARM (CRC extension)
Torn Write
Partial sector write (e.g. power loss mid-write); detected by CRC32C on last sector
Sector
512-byte or 4096-byte disk unit; WAL writes are sector-aligned
Batch
Multiple events submitted in a single client request; processed atomically per execute_batch
Session
Client registration with the server; tracks sequence numbers for exactly-once delivery
Pipeline Depth
Number of in-flight VSR prepares; trade: higher depth = higher throughput, higher latency variance
SLO
Service Level Objective: quantified correctness/availability/latency target
RTO
Recovery Time Objective: maximum acceptable downtime after a failure
RPO
Recovery Point Objective: maximum acceptable data loss after a failure; 0 for this system
