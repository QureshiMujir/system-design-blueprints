4. System Constraints

Hard, measurable bounds on the process model + sandbox. All targets: Linux x86-64 primary backend, release build, on a 2-core warm machine, kernel >= 5.10 (seccomp KILL_PROCESS, memfd seals, unprivileged userns assumed enabled). Targets are SLOs; the security invariants (C-SEC-*) are NON-negotiable and gate the build.

4.1 Trust boundary (the overriding constraint)

  • The browser/broker process is the TCB; everything across the TRUST BOUNDARY (renderer/GPU/network/utility) is fully untrusted, possibly attacker-controlled.
  • C-SEC-1 — never trust child input. Every Message, BrokerRequest, Handle, length, offset, and FD count arriving from a child is adversarial: bounds-checked, type-validated, capability-checked before any privileged action. No path/string/index from a child is dereferenced unvalidated.
  • C-SEC-2 — defense in depth = two independent layers. A renderer's OS access is DENIED by seccomp and brokered+validated against its CapabilitySet. A single layer's bug must not yield escape.
  • C-SEC-3 — deny by default. Unlisted syscall → Errno/Kill; unlisted resource → Denied. New capability requires explicit grant.
  • C-SEC-4 — zero ambient privilege in a sandboxed child (see 4.4).
  • C-SEC-5 — blast radius bounded by CapabilitySet. A compromised renderer gains only its own grants; broker re-validation prevents escalation across the boundary.

4.3 Process-count + reuse constraints

  • C-13 — process ceiling. Hard cap MAX_RENDERER_PROCS (default 64, configurable; derived from RAM via total_ram / C-8 ceiling). At cap, ProcessReusePolicy transitions ProcessPerSiteInstance → ReuseExistingForSite → LimitReached.
  • C-14 — reuse threshold. Reuse kicks in at >= 80% of the cap; a new SiteInstance whose SiteId already has a host reuses it; same-BrowsingInstance script-related instances always coalesce to one process.
  • C-15 — process-per-site-instance is the invariant below threshold; reuse never merges two distinct SiteIds in different BrowsingInstances (would breach site isolation → forbidden).
  • C-16 — FD budget per process. Each child runs under RLIMIT_NOFILE <= 256 (renderer) / 1024 (network); the browser sizes its own fd table for MAX_RENDERER_PROCS x (1 pipe + brokered FDs) with headroom. FD exhaustion → graceful SpawnFailed, never browser abort.

4.5 Availability + blast-radius constraints

  • C-AV-1 — child death != browser death. A renderer crash (SIGSEGV, seccomp SIGSYS, OOM-kill, IPC disconnect) NEVER takes down the browser or any other renderer. Detected via SIGCHLD/exit/IPC-EOF; surfaced as "sad tab".
  • C-AV-2 — no shared mutable state across the boundary except explicitly via sbx-shm buffers with seals; a child cannot corrupt browser memory.
  • C-AV-3 — bounded restart. RestartPolicy::Restart { max, window_secs } (default max 3 / 60 s) caps restart storms; exceeding → Never/ReloadTab, no busy-loop.
  • C-AV-4 — malformed input is non-fatal. A malformed Message/BrokerRequest from a child yields SbxError/connection teardown, never a panic/UB in the TCB (enforced by IPC fuzzing, P13).

4.6 Platform, portability + scope constraints

  • Linux primary: hard dependency on seccomp-bpf, unprivileged user namespaces, pivot_root, memfd_create + seals, SCM_RIGHTS. Degradation: if unprivileged userns disabled (kernel.unprivileged_userns_clone=0), spawn fails closed with actionable error — never silently runs unsandboxed.
  • macOS (Seatbelt) / Windows (job object + restricted token / AppContainer): Sandbox backend stubs behind PhaseDeferred — must compile, must Err(SbxError::Sandbox) at apply, must not pretend to confine.
  • MSRV 1.78, edition 2021; unsafe confined to syscall wrappers (clone/seccomp/SCM_RIGHTS/mmap), each with a documented safety contract; no unsafe in policy/validation logic.
  • NON-GOALS (constraints by exclusion): no real layout/JS engine (renderer is a minimal untrusted stand-in); no network stack; not a general container runtime or hypervisor. The renderer must NOT acquire rendering/network/file capability beyond test fixtures.

4.7 Determinism + testability constraints

  • Sandbox policies + capability profiles are declarative + static per ProcessType → reproducible, auditable, snapshot-testable.
  • Spawn/IPC/broker paths expose injectable clocks + counters → all C-1..C-12 targets are CI-asserted regressions, not aspirations.
  • The red-team harness (sbx attack, P13) is a release gate: every forbidden syscall/file/socket attempt MUST be denied or kill the child; a single bypass fails the build.

Back-of-Envelope Capacity Model

The six numbers a principal engineer computes before designing this system. Each is derived step-by-step from the §4 System Constraints table (C-1 through C-16). No number is asserted without derivation.

BOE-1 — Renderer private RSS per process (the memory floor)

Derivation from C-8 (per-renderer private RSS target: 2–4 MB for the minimal stand-in) and B2 (COW page semantics):

shared_pages = zygote image ≈ 30–60 MB (runtime + libs + warmed data, shared RO)
private_pages = touched-on-write pages per renderer ≈ 2–4 MB (C-8)
total_renderer_RSS = shared_pages (counted once) + N × private_pages
=> For N=20 renderers: 60 MB + 20 × 3 MB = 120 MB aggregate
=> Per-renderer marginal cost = 3 MB private (not 60 MB full image)
RLIMIT_AS for renderer = 512 MB (C-8 ceiling; headroom for growth)

This is why the zygote fork is the memory-scaling lever: 20 renderers cost 120 MB, not 20 × 63 MB = 1.26 GB.

BOE-2 — Renderer process count ceiling (memory-bounded)

Derivation from C-7 (total process budget) and BOE-1:

RAM budget (desktop) = 4 GB (reference machine, C-AV)
browser process RSS ≈ 60 MB (runtime + host registry + route tables)
renderer per-process marginal private = 3 MB (BOE-1)
available_for_renderers = 4096 MB − 60 MB = 4036 MB
renderer_count_ceiling = floor(4036 / 3) ≈ 1345 renderers
BUT: hard process cap C-7 = max_renderers = 2 × logical_cores, clamp [16, 256]
=> For 8-core machine: cap = min(16, 256) = 16 ... max(2×8=16, 256) = 16
=> Practical bound = process cap (16–256), NOT memory (1345)
=> Memory binds first only with a real engine (50–150 MB/renderer): 4036/100 = 40 renderers

BOE-3 — IPC message throughput (the router bottleneck)

Derivation from C-3 (IPC throughput target: ≥1 GB/s per pipe for 64 KB payloads; ≥200k small msgs/s aggregate) and C-2 (p50 round-trip < 20 µs):

small message (64 B payload + 24 B header = 88 B):
  sendmsg + recvmsg ≈ 2 syscalls at ~2 µs/syscall = 4 µs minimum
  => max single-pipe rate = 1 / 4 µs = 250k msg/s  [matches ≥200k aggregate target, C-3]
large message (64 KB payload):
  socket copy = 64 KB / memory bandwidth (≈50 GB/s DRAM) ≈ 1.3 µs copy
  + sendmsg overhead ≈ 2 µs
  => per-message ≈ 3.3 µs → ~300k msgs/s → ~300k × 64 KB = 19 GB/s theoretical
  BUT: socket buffer (default 128 KB–256 KB) limits in-flight data
  => bulk transfers move to ShmRing (zero-copy, SPSC, ≥5 GB/s target C-4)

BOE-4 — fd table budget in the browser process

Derivation from C-7 (max 256 renderers) and ADR-23 (one UDS pipe per process via RouteId mux):

fds per child = 1 (MessagePipe) + 1 (IPC with broker) = ~2
fds for 256 renderers = 256 × 2 = 512
+ GPU process: 1 fd
+ NET process: 1 fd
+ standard fds (stdin/stdout/stderr) = 3
+ internal pipes (reaper self-pipe, signal fd) ≈ 4
total ≈ 512 + 2 + 3 + 4 = ~521 fds in browser process
RLIMIT_NOFILE for browser = 4096 (C-16; headroom)
=> fd table headroom = 4096 − 521 = 3575 free slots
=> RouteId mux keeps this O(processes), not O(frames); critical for 10k+ tabs/site

BOE-5 — Zygote spawn latency (the fork bottleneck)

Derivation from C-5 (spawn latency target: zygote fork < 10 ms p50, < 20 ms p99) and B2 (COW fault cost):

fork(2) syscall overhead (Linux, 64-bit) ≈ 0.1–0.5 ms
COW page table copy (for 60 MB zygote image) ≈ 60 MB / 4 KB pages = 15360 PTEs
  PTE copy overhead ≈ 15360 × 20 ns/PTE ≈ 0.3 ms
post-fork seccomp seal (install BPF program) ≈ 0.1–0.5 ms
handshake (Hello/HelloAck RTT over loopback UDS) ≈ 0.1 ms
total p50 ≈ 0.5 + 0.3 + 0.3 + 0.1 = 1.2 ms  [well inside 10 ms target]
p99 headroom: +kernel scheduling jitter + COW fault burst on first dirty write
  ≈ 1.2 ms + 5 ms = 6.2 ms  [inside 20 ms p99 target]

BOE-6 — Broker request rate (the policy throughput)

Derivation from C-6 (broker request rate target: ≥10k requests/s under load) and ADR-20 (O(1) CapabilitySet lookup):

PolicyEngine: per-request = ProcessId → CapabilitySet lookup (HashMap) + op validation
  HashMap lookup ≈ 50–100 ns (L2/L3 cache hit on small map)
  op validation ≈ 50 ns (enum match + capability contains check)
  UDS round-trip (send request, recv FD) ≈ 4 µs (2 syscalls × 2 µs)
  => per-request wall time ≈ 4.1 µs → max rate ≈ 240k requests/s single-threaded
  => well above 10k/s target; bottleneck is UDS syscall cost, not PolicyEngine logic
capacity at 256 renderers, each issuing 40 broker requests/s:
  total = 256 × 40 = 10,240 requests/s ≈ at target; PolicyEngine never the bottleneck
