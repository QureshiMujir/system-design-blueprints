Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does the seccomp filter's arch-check instruction have to be FIRST, not anywhere in the BPF program? If it is not first, can an attacker reach syscalls that pass the filter by using a different ABI? Explain using the x32 example. Resolves: §17 Phase 5 (cBPF ordering), ADR-13, §7 INV-2, §5.4 struct seccomp_data.
  2. The broker validates every BrokerRequest, but what prevents a compromised renderer from impersonating a different renderer (e.g., the GPU process) to request GPU-level capabilities? Trace the exact validation path. Resolves: §19 Phase 7 (PolicyEngine per-ProcessId validation), §20 Phase 8 (CapabilitySet per ProcessId), §7 INV-11, ADR-20.
  3. If F_SEAL_WRITE is applied to a SharedBuffer before it is passed to the renderer, what exactly prevents the renderer from (a) resizing it, (b) writing to it, (c) remapping it writable? Reference the kernel mechanism and the ShmRing header position. Resolves: §14 Phase 2 (memfd seals), §11.3 (SharedBuffer sealing), ADR-09, memfd_create(2) §5.4.
  4. Why is ProcessReusePolicy::LimitReached an isolation regression, and what exactly is the blast-radius consequence of coalescing two different sites into one renderer? What metric is emitted? Resolves: §21 Phase 9 (ProcessReusePolicy), Scalability Analysis (security-vs-resource tension), §20 Phase 8 (CapabilitySet scope), Operational Readiness.
  5. A renderer in a PID namespace sees itself as PID 1. What happens when it calls fork(2) without the fork syscall being in the seccomp allow-list, and what happens if fork is in the allow-list? Connect the PID namespace semantics to the zygote design decision. Resolves: §17 Phase 5 (seccomp baseline renderer policy), §18 Phase 6 (zygote owns the fork path, renderers do not), ADR-12, §5.4 pid_namespaces(7).
  6. Why does pivot_root provide stronger isolation than chroot, and under what specific conditions can a chroot jail be escaped? Which exact sequences break chroot and why do they fail with pivot_root in a mount namespace? Resolves: §16 Phase 4 (pivot_root design), ADR-16, B5 (chroot pitfalls), §5.4 pivot_root(2).
  7. The ShmRing is SPSC with Acquire/Release ordering on the head and tail atomics. What breaks if you use Relaxed ordering? Give a concrete example of the memory reordering that would corrupt data. Resolves: §14 Phase 2 (ShmRing implementation), §11.3 (ShmRing ring semantics), §7 INV-4 (no-race on ring head/tail).
  8. Explain why a BrowsingInstance group of SiteInstances may share a process even if they are different sites (eTLD+1). When does site isolation override the BrowsingInstance grouping? Resolves: §21 Phase 9 (BrowsingInstance grouping rule), P1 (Reis et al. 2019 — BrowsingInstance + OOPIF), ADR-18.
  9. If PR_SET_NO_NEW_PRIVS is set, and the renderer calls execve to re-exec itself as a SUID binary, what privilege does it obtain? Trace through no_new_privs semantics step by step. Resolves: §16 Phase 4 (no_new_privs ordering), §17 Phase 5 (install ordering), ADR-14, §5.4 prctl(2), MM9.
  10. The MessageHeader.num_handles field is validated against the SCM_RIGHTS fd count on recv. What are the two failure modes (mismatch in each direction) and what resource leak or security consequence does each create if not handled? Resolves: §11.2 (wire format, num_handles reconciliation), §14 Phase 2 (Handle recv validation), §7 INV-3, ADR-06.
  11. A renderer is killed with SIGKILL from outside the sandbox. Walk through all three crash-detection paths (SIGCHLD, IPC-disconnect, exit-watcher). Which fires first? Can any of them fail to fire? What if the browser process is also under memory pressure during the kill? Resolves: §23 Phase 11 (CrashHandler, three detection paths), §7 INV-6 (crash detected ≥1 path), Operational Readiness (SIGCHLD reaping).
  12. The SeccompFilter compiles SyscallRule[] to a cBPF program. If there are 200 allow-listed syscalls, approximately how many cBPF instructions does the emitted program contain, and does program length affect filter installation? What is the kernel's cBPF program-length limit? Resolves: §17 Phase 5 (cBPF compilation algorithm), §11.4 (SeccompFilter), ADR-11, §5.4 bpf(2) classic-BPF section.
  13. Why does the RouteId mux keep the browser process's fd count at O(processes) rather than O(frames)? What would the fd count be if there were one socket per RenderFrame, and at what point would that hit the process fd table limit? Resolves: Scalability Analysis (IPC fan-out), Back-of-Envelope Capacity Model BOE-4, ADR-23, §22 Phase 10 (router design).
  14. The zygote must warm COW pages before forking renderers. What exactly should it do to maximize page sharing — which pages SHOULD be pre-faulted and which MUST NOT be pre-faulted? Explain in terms of heap allocation, code pages, and thread-local state. Resolves: §18 Phase 6 (ForkServer COW warm pages), Back-of-Envelope Capacity Model BOE-1/BOE-5, B2 (COW semantics), ADR-17.
  15. If the PSL snapshot bundled in sbx-site/data/public_suffix_list.dat is six months old, and a new public suffix is added to the real PSL in the meantime, what is the security consequence? Is this better or worse than using a live DNS lookup? Resolves: §21 Phase 9 (PSL bundled snapshot rationale), ADR-19, P1 (site isolation cost data — stale PSL tradeoff), MM6.
  16. The PolicyEngine is described as an O(1) capability lookup. Walk through the exact data structure and the lookup algorithm. What is the CapabilitySet containment check and what happens if the check has a false-positive — i.e., it grants a capability the process should not have? Resolves: §20 Phase 8 (PolicyEngine, CapabilitySet), §11.6 (sbx-broker types), §7 INV-10, ADR-20, Back-of-Envelope Capacity Model BOE-6.
  17. What is the SECCOMP_FILTER_FLAG_TSYNC flag and should sbx-266 use it? What happens if a multi-threaded renderer is allowed to install a seccomp filter without TSYNC? Resolves: §17 Phase 5 (seccomp install), §5.4 seccomp(2), ADR-11/ADR-14.
  18. A renderer is in a NET namespace with no routable interface. The seccomp filter allows socket(AF_INET, ...). What happens when the renderer calls socket(AF_INET, SOCK_STREAM, 0) — does it succeed? If it does, can it connect() to the internet? Trace through the namespace and broker layers. Resolves: §16 Phase 4 (NET namespace isolation), §17 Phase 5 (seccomp allows socket but namespace denies connectivity), §19 Phase 7 (broker ConnectSocket validation), §6 P5, MM3.
  19. What is the BrokerOp OpenFile validation path for a request with a path containing ../etc/passwd? Trace from the renderer's request through PolicyEngine to the file system, step by step. Resolves: §19 Phase 7 (FileBroker path canonicalization, symlink prevention), P11 (Garfinkel TOCTOU), §7 INV-11, ADR-06.
  20. Why does ShmRing use a power-of-two capacity with bitmask indexing rather than modulo? In a SPSC ring, can the producer and consumer ever both be at the same index simultaneously? Prove it cannot happen. Resolves: §14 Phase 2 (ShmRing SPSC correctness), §11.3 (ring semantics), §7 INV-4.
  21. The sbx attack harness must verify that a forbidden syscall results in KillProcess. But KillProcess kills the child — how does the harness observe and assert the kill without itself crashing? Explain the test architecture. Resolves: §25 Phase 13 (attack harness architecture), §23 Phase 11 (crash detection), §7 INV-1/INV-2, ADR-26.
  22. Explain the difference between a SiteInstance and a BrowsingInstance. Can a single BrowsingInstance contain SiteInstances from different registrable domains? What is the consequence for process assignment? Resolves: §21 Phase 9 (SiteInstance/BrowsingInstance design), P2 (Chromium Site Isolation Design — BrowsingInstance scripting semantics), ADR-18.
  23. If the broker process itself crashes (e.g., due to a bug in PolicyEngine), what happens to all live renderers? Are they killed? Do they stall? Is the crash cascading? Describe the recovery path. Resolves: §23 Phase 11 (crash isolation — browser IS the broker; renderer crashes ≠ browser crashes), §7 INV-6, Failure Modes F1/F5.
  24. Why is SOCK_SEQPACKET used instead of SOCK_STREAM for MessagePipe? What would break about the framing and handle-passing protocol if SOCK_STREAM were used instead? Resolves: §13 Phase 1 (SOCK_SEQPACKET boundary semantics), §14 Phase 2 (SCM_RIGHTS atomicity requirement), §11.2 (wire format), ADR-05.
  25. The ProcessReusePolicy::LimitReached path puts two different sites in one renderer. How does the two-layer (seccomp + broker) defense-in-depth continue to hold in this degraded state, even though site isolation is weakened? Resolves: §21 Phase 9 (LimitReached reuse), Scalability Analysis (security-vs-resource tension), §20 Phase 8 (CapabilitySet still applies per-ProcessId), MM3, MM7.

Mental Models & First Principles

The compressed insights a senior sandbox engineer holds before designing any system in this space. Each predicts a class of bugs you write without it; each resolves to a concrete section of this blueprint.

# Mental Model What It Predicts Bug Class Without It Applied In
MM1 A rendered web page is fully attacker-controlled code. The renderer process does not run "code you trusted" — it runs arbitrary JavaScript, native compiled code from a plugin, and parses untrusted network data. Threat model must start at "renderer is already compromised". Every design decision that says "but the renderer wouldn't do that" is wrong. Insufficient confinement justified by "we trust the content." §1.2, Threat Model T1, §6 P1
MM2 A Handle IS an authority; a path is a capability claim. Passing an FD via SCM_RIGHTS transfers a kernel-enforced capability — the receiving process can use whatever the FD refers to, regardless of filesystem namespace or credentials. Passing a path is passing a claim that must be verified, and the object can change between verification and use (TOCTOU). Any system that passes paths instead of FDs is TOCTOU-vulnerable. Broker validates a path at request time, but renderer opens it after the broker's check. §14 Phase 2, §19 Phase 7, ADR-06, P11
MM3 Defense-in-depth means one layer's bug does not yield escape. Two independent layers (seccomp filter AND broker policy) means an attacker must compromise both simultaneously. The seccomp filter blocks syscall-level primitives; the broker denies access to resources. A filter bypass that reaches the broker finds another deny; a broker logic bug that grants a resource finds seccomp has already blocked the syscall used to exploit it. Designing one strong layer gives false confidence. The invariant is "AND", not "OR". A seccomp filter bug in a single-layer design is a complete sandbox escape. §1.2, §6 P2, §7 INV-1, §17 Phase 5, §19 Phase 7
MM4 The seccomp filter is an allowlist, not a denylist. The BPF program's default action is KillProcess. Every syscall the renderer legitimately needs must be explicitly listed. A new kernel syscall is denied by default — not silently permitted. The arch-check must be the first instruction or the entire allowlist is bypassed via the x32/ia32 ABI. Forgetting one of these properties opens a bypass. A filter that blocks "bad" syscalls but allows the rest: the attacker finds a new syscall not on the denylist. §17 Phase 5, ADR-12, ADR-13, §7 INV-2
MM5 COW fork is a memory snapshot, not a copy. When the zygote forks a renderer, the child shares the parent's physical pages (marked read-only in the MMU). A write in the child triggers a page fault that copies only the touched page. The "cheap" renderer spawn is cheap because most of the process image (runtime, libraries, pre-warmed caches) is never written and therefore never copied. RSS growth per renderer equals the private dirty pages only. Assuming "fork is free regardless" leads to over-spawning and unexpected RSS growth. Forking a renderer that immediately writes a large buffer blows out COW savings; the zygote's value comes only from pre-warming the RO working set. §18 Phase 6, Back-of-Envelope Capacity Model BOE-1, B2 ch.9, ADR-17
MM6 Site isolation principal = eTLD+1, not full origin. The security principal is the registrable domain (scheme + eTLD+1 via the public suffix list), not the full origin (scheme+host+port). Two subdomains of the same eTLD+1 (e.g., a.example.com and b.example.com) are the same site and may share a process without Spectre risk — they can already read each other's cookies. Two domains on the same TLD but different eTLD+1 (e.g., a.github.io and b.github.io) are DIFFERENT sites and must be isolated, because github.io is a public suffix. Using naive "last two labels" as the site key misgroups a.co.uk and b.co.uk as the same site — a cross-site isolation bug. A naive label-counter without the PSL puts a.co.uk and b.co.uk in the same process, enabling cross-origin data leakage via Spectre. §21 Phase 9, ADR-18, ADR-19, P1, P9
MM7 The broker's job is to be the only path to the OS. A renderer in an empty NET namespace with pivot_root and full cap-drop cannot open(), connect(), or mmap() device memory directly — not because the broker says no, but because the kernel says the syscall would fail or is blocked by seccomp. The broker then validates the intent ("I need to read this file") against the renderer's CapabilitySet and returns only a pre-opened FD. This is object-capability security: authority is carried in the FD, not in the name. Thinking the broker is a "firewall" that blocks bad calls misses that the kernel already blocks them — the broker adds semantic validation on top. If the seccomp layer is misconfigured to allow open(2), the broker becomes the sole defense; if the broker is misconfigured, the seccomp layer becomes the sole defense. One can fail; both cannot simultaneously. §19 Phase 7, §20 Phase 8, §6 P3, MM3
MM8 Crash isolation = blast radius = CapabilitySet. A renderer crash (or full compromise) can cause at most what its CapabilitySet permits. If the CapabilitySet is {ReadFile(allowlist)}, the worst the attacker can do is read files on that allowlist. No capabilities that were not granted can be exercised. The browser process and sibling renderers are structurally unaffected — they hold separate address spaces and the broker validates against each caller's own ProcessId. Without explicit blast-radius reasoning, "compromise" is an unbounded bad outcome. A broker that does not isolate per-ProcessId allows a compromised renderer to impersonate another renderer and request its capabilities. §23 Phase 11, §20 Phase 8, §7 INV-14, Threat Model T1, P12
MM9 PR_SET_NO_NEW_PRIVS is a one-way ratchet, not a filter. Once set, the process can never gain privilege via exec (SUID binaries become non-SUID, file capabilities are dropped). This is a precondition for unprivileged seccomp installation. The seccomp filter is then a capability over the syscall ABI; no_new_privs ensures that exec of a privileged binary does not escape the filter. The combination means the child is permanently capability-bounded regardless of what it execs. Assuming the seccomp filter alone is sufficient: if no_new_privs is absent, the filter survives exec but a SUID binary exec'd from inside the renderer would gain privilege before the filter acts on its syscalls. A renderer that can exec a SUID binary and escalate privilege; the filter is in place but the SUID gains privilege before the filter's syscall rules take effect on the elevated context. §17 Phase 5, §16 Phase 4, ADR-14, prctl(2), §7 INV-1
MM10 A hardware-enforced process boundary is a fundamentally stronger isolation primitive than a software-enforced one. The MMU page-table boundary between two processes is enforced by silicon the attacker cannot reprogram from user space; a software fault-isolation boundary (a WASM sandbox, a V8 isolate, an in-process interpreter) is enforced by code the same runtime executes, and a bug in that runtime (a JIT miscompile, a bounds-check elision) collapses the boundary from inside. This is why the design is multi-process rather than in-process-sandboxed. A single-process "sandbox" built from a memory-safe interpreter or a software fault-isolation scheme is not equivalent to an OS process boundary — it inherits every bug in its own enforcement layer. Treating a WASM/JS sandbox as sufficient confinement for fully-untrusted code and skipping the OS-level process boundary, then discovering a JIT or bounds-check bug breaks the "sandbox" with no second layer to catch it. §1.2, Alt-B (In-process Sandboxing — rejection rationale), P9 (Spectre — same-address-space isolation is unsafe), §6 P5

Glossary · 53 terms · site-wide glossary

browser process
The single privileged orchestrator (sbx-browser::BrowserProcess, ProcessType::Browser, ProcessRole::Privileged). The TCB. Owns ProcessHost, launcher, brokers, site policy, crash handler, IPC router. Never untrusted input executes here unsandboxed.
renderer process
Fully untrusted child (sbx-renderer::RendererProcess, ProcessType::Renderer, ProcessRole::Sandboxed). Confined by seccomp-bpf + namespaces; holds only its CapabilitySet; reaches OS resources only via the broker. A minimal stand-in here — not a web engine.
GPU process
Child (ProcessType::Gpu) with a relaxed sandbox (needs device/driver access); holds a GpuChannel capability. Isolates the graphics driver attack surface from the browser.
network process
Child (ProcessType::Network) holding ConnectSocket capabilities; the only child permitted (brokered) network egress, since renderers run in a NET namespace with no network.
utility process
Child (ProcessType::Utility) for one-off untrusted work (parsing, decoding) with a minimal CapabilitySet; short-lived, tightest sandbox.
broker
A privileged service in the browser (sbx-broker: FileBroker/SocketBroker/ResourceBroker, Broker trait) that performs OS operations a sandboxed child cannot, after PolicyEngine validation. Returns a brokered FD via SCM_RIGHTS, never a path.
sandbox
OS-level confinement of a child (sbx-sandbox: Sandbox trait, LinuxSandbox, Policy). Combines namespaces + pivot_root + rlimits + cap drop + no_new_privs + seccomp-bpf.
seccomp-bpf
Kernel syscall-filtering mechanism: a classic-BPF program (SeccompFilter) attached to a process that the kernel runs on every syscall, returning a disposition. Installed via prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER) after no_new_privs.
syscall filter
The SeccompFilter cBPF program compiled from SyscallPolicy (Vec<SyscallRule>); per-syscall nr matched, optional ArgFilter, then a Disposition. One of the two defense layers.
disposition
sbx-sandbox::Disposition — the verdict for a filtered syscall: Allow, Errno(i32), Trap (→ SIGSYS), KillProcess, Log. Maps to SECCOMP_RET_ALLOW/ERRNO/TRAP/KILL_PROCESS/LOG.
seccomp_data
The kernel struct the cBPF program reads: { nr: i32, arch: u32, instruction_pointer: u64, args: [u64; 6] }. arch MUST be checked first to reject non-AUDIT_ARCH_* ABIs (blocks the x32/ia32 syscall-number bypass).
namespace
Linux kernel isolation of a global resource (sbx-sandbox::Namespaces, clone flags). Six used: user (maps child to fake root, enables the rest unprivileged), pid (hides other processes), net (removes all network → forces brokering), mnt (private mounts for pivot_root), ipc (isolates SysV IPC), uts (isolates hostname).
pivot_root
pivot_root(2) syscall that swaps the child's root mount to a minimal, mostly read-only rootfs (Policy::root); strips access to the real filesystem tree. Done inside the mnt namespace.
no_new_privs
prctl(PR_SET_NO_NEW_PRIVS, 1) — irrevocably bars the process (and descendants) from gaining privileges via setuid/setgid/fcaps. Prerequisite for an unprivileged process to install a seccomp filter.
rlimit
Per-process resource ceiling (Policy::rlimits → Rlimits): RLIMIT_AS/NOFILE/NPROC/CPU/CORE etc. Caps blast radius (memory/FD/fork exhaustion) and disables core dumps.
capability
sbx-core::Capability — a single least-privilege grant a child may exercise (OpenFile{path_glob,mode}, ConnectSocket{host,port}, SharedMemory{max_bytes}, ReadClipboard, GpuChannel). Distinct from a Linux POSIX capability (which is dropped).
CapabilitySet
sbx-core::CapabilitySet — the per-process set of granted Capabilitys. The PolicyEngine validates every BrokerRequest against the caller's set; it is the precise statement of a compromised child's reach.
least privilege
Design rule: each ProcessType gets the minimum CapabilitySet to function (renderer minimal; network/GPU relaxed). Narrows what a sandbox escape can do.
deny by default
Broker + seccomp posture: any syscall/resource not explicitly allowed is denied (Errno/KillProcess / BrokerResponse::Denied). New code fails closed, not open.
zygote
sbx-zygote::Zygote — a pre-forked, pre-sandboxed template process holding warmed read-only pages; renderers spawn as cheap COW forks from it instead of fresh execs.
fork server
sbx-zygote::ForkServer — services ForkRequest{process_type, policy, channel} over a socket by fork()ing the zygote and sealing the child's seccomp policy before untrusted work runs.
copy-on-write (COW)
Kernel page-sharing after fork(): child and zygote share identical pages read-only until written. Makes zygote spawn fast and memory-cheap (shared runtime/libs).
IPC
Inter-process communication (sbx-ipc). All cross-process traffic over UNIX domain sockets; the only sanctioned channel across the trust boundary; carries Messages, FDs (SCM_RIGHTS), and shared-memory handles.
message pipe
sbx-ipc::MessagePipe — a bidirectional UDS-backed channel (pair() = socketpair); the transport for Message{header, payload, handles}.
Mojo
The Chromium typed-IPC system this layer is modeled on: typed Interfaces bound to message-pipe endpoints with request/response + async. sbx-ipc is "Mojo-like."
Interface
sbx-ipc::Interface trait — a typed request/response contract bound to an Endpoint; gives compile-time-shaped messages instead of raw bytes.
Endpoint
sbx-ipc::Endpoint<T: Interface> — a typed end of a message pipe carrying interface T; the RouteId-addressed binding point.
SCM_RIGHTS
UNIX-socket ancillary message (unix(7)) that duplicates an open FD into the receiver. The capability-passing primitive: the broker passes an opened FD, never a path → eliminates path-reinterpretation TOCTOU.
handle passing
Moving an OS handle across a process boundary via SCM_RIGHTS as a sbx-ipc::Handle (owned FD with close-on-drop). MessageHeader::num_handles declares count; receiver takes ownership.
shared memory
sbx-shm — large/zero-copy data shared between processes via a memfd FD passed over IPC, then mmaped (SharedBuffer, Mapping). Avoids byte-copying big payloads through the socket.
memfd
Anonymous file from memfd_create(2) backing a SharedBuffer; supports seals; the FD is the shareable handle.
seal
fcntl F_SEAL_* flag on a memfd (F_SEAL_WRITE/SHRINK/GROW/SEAL) making the region immutable/fixed-size, so an untrusted peer cannot resize or rewrite shared memory underneath the broker.
ShmRing
sbx-shm::ShmRing — a single-producer single-consumer ring buffer over a SharedBuffer for streaming large transfers without per-message IPC overhead.
site isolation
The policy that each site runs in its own process (sbx-site), so a compromised renderer cannot read another site's data in-process.
SiteInstance
sbx-site::SiteInstance{id, site: SiteId, browsing_instance} — a specific site within a specific BrowsingInstance; the principal for process assignment + capability grants.
BrowsingInstance
sbx-site::BrowsingInstance{id, instances} — a group of SiteInstances that may script each other (e.g., via window references) and therefore may share a process.
eTLD+1
"Effective top-level domain plus one label" — the registrable domain (e.g. foo.co.uk); the site key together with scheme. Computed via the public suffix list.
registrable domain
Synonym for eTLD+1: the highest domain a single party can register; the unit of same-site grouping.
public suffix list
The dataset of effective TLDs (co.uk, github.io, …) used by SiteIsolationPolicy::site_for to derive eTLD+1 correctly; without it, attacker-controlled subdomains could be mis-grouped.
process-per-site-instance
ProcessReusePolicy::ProcessPerSiteInstance — the default: one process per SiteInstance, subject to a process-count limit.
process reuse
sbx-site::ProcessReusePolicy (ReuseExistingForSite, LimitReached) — when the process limit/memory pressure is hit, reuse an existing same-site process rather than spawn anew.
RouteId
sbx-core::RouteId(u32) — multiplexing key in MessageHeader::route; lets many frames/interfaces share one MessagePipe. The sbx-browser router dispatches by RouteId.
trust boundary
The line between the privileged browser/broker and the untrusted children (drawn in the architecture diagram). Everything crossing it (IPC messages, brokered FDs) is treated as hostile and validated.
TCB (Trusted Computing Base)
The code that must be correct for the security model to hold: the browser process + brokers + PolicyEngine + sandbox setup. Minimized + memory-safe (Rust) by design; renderers are explicitly outside it.
defense in depth
Two independent confinement layers — the seccomp syscall filter AND the broker policy — so a single layer's bug does not yield escape.
blast radius
The maximal damage from a compromised child: exactly its CapabilitySet, since the broker re-validates every request. Bounded, not zero.
sad tab
The user-visible signal (sbx-crash) that a renderer died; the browser + other renderers stay alive (renderer crash ≠ browser crash).
minidump
sbx-crash::Minidump — a minimal crash artifact (pid, signal, registers-ish, maps snapshot) captured on child death for post-mortem; not a full core dump.
restart policy
sbx-crash::RestartPolicy (Never, Restart{max, window_secs}, ReloadTab) governing whether/how a dead child is respawned; rate-limited to avoid crash loops.
sandbox escape
An exploit that breaks a child out of its OS confinement (seccomp/namespaces). The seccomp arch check, deny-by-default policy, and minimal kernel surface are the mitigations the red-team harness attacks.
privilege escalation
A compromised child gaining rights beyond its CapabilitySet (e.g., tricking the broker). Prevented by per-ProcessId capability validation on every BrokerRequest.
confused deputy
An attack where the renderer induces the privileged broker to misuse its authority on the renderer's behalf. Countered by validating each BrokerOp against the caller's CapabilitySet (caller identity bound to the connection, not asserted in the message).
brokered resource
An OS resource (file/socket/shm) the renderer cannot obtain directly; the broker opens it after policy validation and passes back only the resulting Handle via SCM_RIGHTS.
