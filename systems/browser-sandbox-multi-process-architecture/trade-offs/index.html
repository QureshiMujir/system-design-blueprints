Each card is one row of the blueprint's decision table: what was locked in, what was rejected, and — the column that matters most — the situation in which the rejected choice is the right one.

Decisions (§9) · 29 ADRs

01

Implementation language [TCB]

Chosen

Rust, edition 2021, MSRV 1.78

Rejected

C/C++ (Chromium's language); Go; any GC scripting lang

When the rejected choice is right

C/C++ wins when the codebase is already a multi-million-line C++ engine (Chromium itself) and the incremental security gain of Rust is outweighed by interop friction; C wins in resource-constrained embedded systems where std Rust is unavailable and the sandbox perimeter is hardware-enforced anyway.

Why: Broker is the TCB parsing fully-untrusted renderer input → memory safety eliminates Chromium's dominant sandbox-CVE class (UAF/OOB in the broker). Need raw fork/clone/seccomp/namespace control with safe handle wrappers. C/C++ reintroduces the exact attack surface we remove. Go's runtime + M:N scheduler fights single-threaded clone/seccomp/unshare ordering; GC + thread-per-filter friction.

02

Code organization

Chosen

Cargo workspace, 12 members sbx-*

Rejected

one monolith crate; one crate per binary

When the rejected choice is right

A single crate wins for a small prototype or a component that will always be used as a whole — when crate-boundary compile overhead and version management cost outweigh the layering benefit. One-crate-per-binary wins when each binary is genuinely unrelated and sharing types has negative value.

Why: Crate boundaries enforce the layering invariant: sbx-core is OS-free; sbx-ipc/sbx-shm/sbx-sandbox/sbx-broker are independently testable + fuzzable; the dependency DAG is the architecture. Monolith blurs the trust boundary in the type system.

03

OS target priority [TCB]

Chosen

Linux primary; Sandbox trait abstracts backend

Rejected

cross-platform from day 1; Linux-only with no trait

When the rejected choice is right

Cross-platform from day 1 wins when the deployment target is an existing multi-OS product (e.g., a shipped browser or IDE plugin) where macOS/Windows usage volume exceeds Linux; the Sandbox trait abstraction is then the right design but must be fleshed out in all backends immediately.

Why: Confinement primitives (seccomp-bpf, namespaces, pivot_root) are Linux-specific; chasing 3 OSes dilutes depth. The Sandbox trait + LinuxSandbox lets macOS (Seatbelt) / Windows (job object + restricted token + AppContainer) ship as PhaseDeferred stubs without API churn.

04

macOS / Windows backends

Chosen

PhaseDeferred stubs behind Sandbox

Rejected

full parity now; #[cfg] forks everywhere

When the rejected choice is right

Full parity now wins when the primary users are on macOS or Windows (consumer browser distribution) and shipping a non-functional stub creates a worse user experience than shipping a weaker but working sandbox. #[cfg] forks win in a tiny two-platform tool where the abstraction overhead exceeds the sharing benefit.

Why: Keeps one confinement contract; defers OS-specific work without leaking platform cfg into callers. Stubs return SbxError::Sandbox (fail-closed), never silently un-sandboxed.

05

IPC transport [TCB]

Chosen

UNIX domain socket (socketpair) per pipe + SCM_RIGHTS

Rejected

anonymous pipes; shared-memory-only; D-Bus / a message bus

When the rejected choice is right

Anonymous pipes win when FD transfer is never needed and message sizes are small and one-directional (logging, streaming stdout). A message bus (D-Bus, systemd socket activation) wins in a desktop-integration context where services must be discoverable, activated on demand, and share a well-known namespace. Shared-memory-only wins when throughput dominates and a separate control channel is already established.

Why: UDS gives bidirectional framed datagrams and ancillary FD passing in one primitive — the capability-transfer mechanism the broker needs. Pipes can't pass FDs. Shm-only lacks a control channel + handshake. A bus adds a third trusted daemon inside the trust boundary.

06

Handle passing [TCB]

Chosen

SCM_RIGHTS FD duplication, wrapped in Handle

Rejected

path strings in messages; pidfd_getfd; /proc/pid/fd

When the rejected choice is right

Path strings win when the peer process is trusted (same privilege level, no adversarial input) and the path is stable enough that re-opening it on the peer side is safe — for example, inter-trusted-service IPC in a same-UID microservice mesh where TOCTOU risk is not in scope. pidfd_getfd wins when transferring fds into a process you did not fork and cannot send a socket message to (post-hoc fd injection during debugging or tooling).

Why: Passing an FD is passing a capability (broker opens a file, sends only the FD — never a path the renderer could re-derive or TOCTOU). Handle owns the fd, closes on drop, moves on send. Path-in-message would reopen the confused-deputy hole brokering exists to close.

07

IPC typing layer

Chosen

Mojo-like Interface + Endpoint<T> over Message{header,payload,handles}

Rejected

raw bytes ad hoc; gRPC; protobuf-over-socket; Cap'n Proto

When the rejected choice is right

gRPC wins in a multi-language, multi-service microservice environment where schema evolution, cross-language stubs, and load balancing are priorities — the toolchain cost is amortized. Cap'n Proto wins for zero-copy RPC where message parsing latency dominates. Raw bytes win in ultra-constrained embedded systems where any framework is overhead.

Why: Typed request/response + async with a hand-rolled compact wire format = no codegen toolchain, no large transitive dep tree in the TCB, full control of the parser we fuzz. gRPC/protobuf pull HTTP/2 + heavy deps into the broker. Models Mojo/IPDL directly.

08

Wire serialization

Chosen

Hand-written framing over seccomp_data-style fixed header + length-prefixed payload

Rejected

serde + bincode; protobuf; JSON

When the rejected choice is right

serde + bincode wins for trusted inter-service IPC in the same trust domain where developer velocity outweighs minimal TCB size and the serializer does not parse adversarial input. protobuf/JSON win when the protocol must be stable across major version changes, readable by external tools, or consumed by multiple language ecosystems.

Why: The deserializer sits on the trust boundary; a small, audited, fuzzed parser beats a large generic one. Fixed MessageHeader{route,kind,req_id,num_handles}; num_handles validated against received SCM_RIGHTS count (mismatch → drop + close).

09

Shared memory [TCB]

Chosen

memfd_create + F_SEAL_* (SEAL_SHRINK/GROW/WRITE), SharedBuffer/Mapping/ShmRing

Rejected

POSIX shm_open; mmap of a tmpfs file; SysV shm

When the rejected choice is right

POSIX shm_open wins when the communicating processes are unrelated (no common ancestor to forward an FD) and must discover the shared segment by name in a controlled namespace. SysV shm wins in legacy codebases or when communicating with non-Linux systems that do not support memfd.

Why: memfd has no filesystem name → nothing for a sandboxed renderer to reopen; passed as an FD via SCM_RIGHTS. Seals make a producer-frozen buffer immutable so the broker can map RO without a renderer racing the size/content (defeats shm TOCTOU). POSIX/SysV shm need a namespace path + leak across the boundary.

10

Large transfer path

Chosen

ShmRing SPSC ring over a sealed SharedBuffer

Rejected

copy every payload through the socket; one memfd per message

When the rejected choice is right

Per-message copy through the socket wins when message sizes are small (< 4 KB) and frequency is low — the socket copy is a single sendmsg, cheaper than allocating + sealing a memfd. One memfd per message wins for irregular, bursty large transfers where a persistent ring adds coordination overhead and wasted ring space.

Why: Bulk/zero-copy frames bypass the socket copy; control + small msgs stay on the typed pipe. SPSC needs no lock; head/tail are the only shared mutable words, bounded + validated each read.

11

seccomp-bpf builder [TCB]

Chosen

Hand-built cBPF builder in SeccompFilter (compiles SyscallRule[])

Rejected

libseccomp (C lib); seccompiler crate

When the rejected choice is right

libseccomp wins when the policy is complex, multi-arch, and the team has limited BPF expertise — the C library's abstraction + portability outweighs the dependency cost for a non-Rust-TCB system. seccompiler wins when a Rust-native cBPF compiler is preferred but the arch-check + ordering requirements are met by the crate's API, avoiding the maintenance burden of a hand-rolled emitter.

Why: Owning the cBPF emitter removes a C dependency from the TCB, guarantees the arch-check-first instruction ordering, and lets the red-team harness assert the exact emitted program. libseccomp is C (memory-unsafety) + abstracts away ordering we must control; seccompiler is reasonable but we want a fully-audited, dependency-light filter we can prove.

12

seccomp default disposition [TCB]

Chosen

Deny by default: unlisted syscall → KillProcess; explicit Allow/Errno/Trap/Log per rule

Rejected

allowlist-by-exception over a permissive base; Errno default

When the rejected choice is right

Errno default wins for development environments where killing the process on every new syscall blocks iteration — Errno surfaces breakage in test logs without crashing; Trap (SIGSYS) wins when the sandbox must intercept forbidden calls for telemetry or forwarding to the broker without terminating the child (user-notify design). Permissive base wins only in controlled environments where a first-pass audit is preferred before tightening.

Why: Allowlist closes the whole syscall ABI; an unknown/new syscall is denied, not silently permitted. KillProcess (not Trap) for the renderer baseline so a forbidden call is fatal + observable, not catchable.

13

seccomp arch handling [TCB]

Chosen

Check seccomp_data.arch first; allow only the expected AUDIT_ARCH_*; deny x32/ia32

Rejected

trust the syscall nr alone

When the rejected choice is right

Trusting the syscall number alone is acceptable only on a host kernel configured with no compat ABI support (CONFIG_X86_X32_ABI=n, CONFIG_IA32_EMULATION=n) — where only one ABI is possible, the arch check is redundant (but still best practice to future-proof).

Why: Syscall numbers differ per ABI; without an arch gate, an attacker re-enters via the x32 or i386 compat ABI to invoke a number that maps to an allowed name on the native ABI. First BPF instruction rejects any non-native arch.

14

seccomp install ordering [TCB]

Chosen

PR_SET_NO_NEW_PRIVS before installing the filter

Rejected

rely on privilege; install filter first

When the rejected choice is right

Installing without no_new_privs wins only when the process holds CAP_SYS_ADMIN (e.g., a privileged container-setup tool) and the use of no_new_privs would block legitimate privilege transitions elsewhere in the lifecycle — a constrained operational scenario where the process needs to gain privilege after filter install.

Why: no_new_privs lets an unprivileged process load a filter and blocks setuid/fcaps from regaining privilege through the filter; required precondition for unprivileged seccomp.

15

Privilege model for namespaces [TCB]

Chosen

Unprivileged user namespace maps child→fake root, enabling pid/net/mnt/ipc/uts ns

Rejected

SUID/setuid helper binary; CAP-granted launcher; no namespaces

When the rejected choice is right

SUID helper wins on enterprise Linux kernels where /proc/sys/kernel/unprivileged_userns_clone is locked to 0 by policy (common in RHEL/CentOS hardening profiles) — user namespaces are disabled system-wide, making a setuid helper the only available path. CAP-granted launcher wins in container runtimes that already run as root or with elevated caps.

Why: No SUID bit, no real root, no fcaps to audit — the user ns grants the appearance of root inside the child only, which is enough to unshare the rest. Removes an entire privileged-helper attack surface present in older Chromium SUID-sandbox designs.

16

Filesystem confinement [TCB]

Chosen

pivot_root to a minimal, mostly-RO rootfs in a mount ns

Rejected

chroot; bind-mount allowlist only

When the rejected choice is right

chroot wins in environments where mount namespaces are unavailable (old kernels, restricted container configs) and the threat model does not include a local-root attacker who can chroot-escape; it remains usable as a path-namespace limiter in those contexts. Bind-mount allowlist wins in container environments where the full OS filesystem is already trusted and only selective path isolation is needed.

Why: pivot_root detaches the old root so it cannot be re-reached; chroot is escapable (chroot-then-../fd tricks, no detach of old root). Renderer sees a minimal tree; everything real comes via the broker.

17

Renderer spawn path

Chosen

sbx-zygote fork server (warm COW template)

Rejected

fresh clone+exec per renderer; thread pool

When the rejected choice is right

Fresh clone+exec wins when spawn frequency is low (< 1/s), memory overhead per renderer is acceptable, or the process image changes frequently (e.g., A/B binary experiments) making the COW template stale. Thread pool wins when the workload is trusted (no sandbox needed) and concurrency overhead dominates spawn cost.

Why: Fork from a pre-warmed, pre-sandboxed zygote shares read-only pages COW → spawn is a cheap fork, not a cold exec + relink. Each forked child seals/tightens its seccomp policy before touching untrusted work. Target spawn latency dominated by fork, not image load.

18

Site granularity [TCB]

Chosen

Process-per-site-instance (site = scheme + eTLD+1)

Rejected

process-per-tab; process-per-origin; single process

When the rejected choice is right

Process-per-tab wins on memory-constrained devices (mobile browsers) where per-site isolation is too expensive and the primary threat is renderer crashes rather than cross-site data exfiltration. Single process wins for a headless/server-side rendering tool with no cross-origin content and where parallelism, not isolation, is the objective.

Why: The web security principal is the site (registrable domain), and same-BrowsingInstance SiteInstances can script each other so must share a process; per-origin over-fragments + breaks scripting; per-tab ignores cross-tab same-site scripting. Subject to a process-count limit + ProcessReusePolicy.

19

Site derivation source

Chosen

Bundled public suffix list (PSL) → eTLD+1

Rejected

hardcoded TLD table; live DNS/registry lookup; naive last-2-labels

When the rejected choice is right

Live DNS/registry lookup wins in a trusted enterprise intranet browser where the TLD namespace is internal and controlled — a live lookup against the internal DNS is more accurate than a stale PSL snapshot for internal domains. Hardcoded table wins in an embedded browser with no update mechanism and a known-fixed TLD set.

Why: eTLD+1 (a.co.uk ≠ b.co.uk) requires the PSL; naive label-counting mis-groups multi-label suffixes → cross-site sharing = isolation bug. Bundled snapshot = deterministic, offline, audit-pinned; no network in the policy path.

20

Resource access model [TCB]

Chosen

Capability-based brokering: PolicyEngine validates each BrokerRequest vs the caller's CapabilitySet

Rejected

static path allowlist in the renderer; per-syscall ACL only

When the rejected choice is right

Static path allowlist wins in a trusted-peer setup where both sides are in the same trust domain and the broker's validation overhead exceeds the benefit (e.g., a local developer tool sandbox where the content is first-party and the threat model excludes malicious content). Per-syscall ACL only wins where there is no broker process and the confinement model is seccomp-only (as in a container runtime that does not implement FD brokering).

Why: Capabilities are least-privilege, per-ProcessId, principal = SiteInstance; the broker is the single validation point and returns only a brokered FD. A renderer-side allowlist is inside the untrusted process = worthless. Two independent layers (seccomp and broker) = defense in depth.

21

Fail mode of the sandbox [TCB]

Chosen

Fail-closed: any setup error (ns/seccomp/pivot_root/cap-drop) aborts the child before untrusted code runs

Rejected

best-effort / continue degraded

When the rejected choice is right

Best-effort / degraded wins in a development environment or a tool whose primary value is running the task (not security), where an occasional sandbox setup failure on unusual host configurations should not block the work. Applicable when the sandbox is defense-in-depth on top of other isolation layers (e.g., a VM).

Why: A partially-applied sandbox is worse than none — it looks confined but isn't. Policy::apply returns Err → launcher never hands the child a renderer task; child exits. No "untrusted code with a half-built filter" state exists.

22

Capability dropping [TCB]

Chosen

Drop all capabilities (bounding set + ambient) + no_new_privs in every child

Rejected

drop a curated subset; keep CAP_NET for net process

When the rejected choice is right

Dropping a curated subset wins when one specific child type has a legitimate need for a narrow capability that the broker cannot proxy — e.g., a GPU process in a system that does not have a DRM/GPU brokering path and requires CAP_SYS_RAWIO for device init. The subset is still least-privilege; the question is whether "zero caps" or "minimal caps" is achievable given the system's broker completeness.

Why: Children need zero kernel capabilities (all privileged ops are brokered); dropping everything removes the privilege-escalation target entirely. The network process gets network access via the broker, not CAP_NET_*.

23

IPC multiplexing

Chosen

RouteId-keyed router in sbx-browser over one pipe per child

Rejected

one socket per frame; port-style demux daemon

When the rejected choice is right

One socket per frame wins when frames are long-lived, large, and independently closeable — a streaming media pipeline where each stream has its own flow control. A port-style demux daemon wins in a microkernel architecture where routing is itself a security domain boundary (capability-based routing through a trusted server).

Why: Many RenderFrames multiplex over a single message pipe per process via RouteId in the header — bounds FD count + connection state in the broker, matches Mojo routing.

24

Crash artifact

Chosen

Minidump (pid, signal, register-ish snapshot, maps) via SIGCHLD/exit/IPC-disconnect watch

Rejected

core dumps to disk; full ptrace dumper; no capture

When the rejected choice is right

Full core dumps win in an internal development or security research environment where the process is trusted, memory contents are not sensitive, and a full dump enables postmortem debugging in a debugger. Full ptrace dumper wins when registers + stack traces from all threads are needed for production crash analytics (Breakpad/Crashpad pattern). No capture wins in an ultra-constrained embedded system where disk space precludes artifacts.

Why: A minimal in-process artifact is enough to triage; full core dumps of a sandboxed child leak memory + are heavy. Renderer death is detected ≥1 of three ways; browser stays up, shows sad tab, applies RestartPolicy. Blast radius = that renderer's CapabilitySet.

25

Low-level syscall surface

Chosen

nix + libc (thin, audited usage)

Rejected

only libc (unsafe everywhere); caps/syscallz/nsroots frameworks

When the rejected choice is right

libc-only wins for one-off scripts or tools that need a single syscall and where adding nix as a dependency is disproportionate. Heavyweight frameworks (nsroots, etc.) win for teams without deep Linux kernel expertise who need a higher-level API that handles edge cases, even at the cost of control over ordering — acceptable when the TCB is small and the framework is well-audited.

Why: nix gives safe wrappers over clone/socketpair/sendmsg/mmap/prctl; libc for raw constants + syscalls nix doesn't cover. Avoid heavyweight sandbox frameworks that hide the ordering this design must control.

26

Security testing

Chosen

cargo-fuzz on the IPC Message deserializer + the red-team attack subcommand

Rejected

manual testing only; no fuzzing

When the rejected choice is right

Manual testing only wins for rapid prototyping where the security boundary is not yet defined and the investment in fuzz infrastructure is premature; acceptable as a temporary state before the TCB surfaces are stabilized. Applicable in a completely closed-source, physically-isolated system where the threat model excludes external attackers.

Why: Fuzzing proves a malformed Message from an untrusted renderer never crashes/UB-s the broker (TCB liveness). The red-team harness (sbx attack) asserts forbidden syscalls/files/sockets are denied or kill the child — the security "done" gate (Phase 13).

27

CI

Chosen

GitHub Actions; a privileged Linux runner for namespace/seccomp tests

Rejected

unprivileged runner only; no CI for sandbox

When the rejected choice is right

Unprivileged runner only wins for projects where the sandbox test suite can be fully mocked or skipped — accepting that namespace/seccomp integration tests will only run locally. Acceptable for open-source contributors who lack privileged CI budget. No CI for sandbox tests is a recognized tech-debt posture for early-stage projects where CI infrastructure setup is deferred.

Why: Sandbox + namespace tests need an unrestricted kernel surface (user-ns enabled, no host seccomp masking ours); a privileged self-hosted/--privileged runner gates these. Unit/fuzz/build run on standard runners.

28

Dependency policy [TCB]

Chosen

Minimal, audited tree; cargo-deny + cargo-audit in CI; no unvetted transitive deps in the TCB

Rejected

pull crates freely

When the rejected choice is right

Pulling crates freely wins in a non-security-critical application binary or in a rapid-prototype phase where developer velocity is the priority and the TCB boundary has not been finalized — e.g., a UI layer or a test harness binary where a CVE in a dep is low-impact.

Why: Every dep in the broker is attack surface; license + advisory + duplicate checks gate merges. Justifies the hand-rolled IPC/seccomp/serialization choices above.

29

Licensing

Chosen

MIT OR Apache-2.0

Rejected

GPL; proprietary

When the rejected choice is right

GPL wins when the project is intended as a copyleft component that must remain open — when protecting downstream openness is more important than broad commercial adoption. Proprietary wins for a commercial product where the sandbox is a competitive differentiator and the organization can accept the maintenance burden of a closed-source release.

Why: Rust-ecosystem standard dual license; permissive, patent-grant via Apache-2.0.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-A: Full Syscall Emulation (gVisor-style sentry)

+---------------------------+
|  Renderer (untrusted)     |
|  syscall: open("x")       |
+------ PTRACE / KVM -------+
|  SENTRY (Go userspace     |  <- intercepts ALL syscalls
|  kernel emulation)        |  <- implements Linux ABI in Go
+------ host kernel ---------+
|  Host kernel              |
|  (tiny exposed surface)   |
+---------------------------+

Regime where it wins: When the threat model includes kernel exploits from a compromised renderer — i.e., a sophisticated attacker who can exploit a kernel vulnerability reachable through the syscall ABI. The sentry's virtualization approach means the host kernel sees only a handful of hypervisor/PTRACE calls, dramatically reducing the attack surface compared to 400+ seccomp-filtered syscalls. gVisor is used in Google Cloud Run and Cloud Functions where multi-tenant workloads require container isolation stronger than seccomp alone.

Real system embodying it: gVisor (runsc, Google, open-source 2018).

Why sbx-266 rejected it: 2–10× syscall overhead (every renderer syscall traps into the sentry) is unacceptable for a browser that calls read/write/mmap millions of times per second during rendering. The sentry's Go runtime is incompatible with direct fork/seccomp/namespace patterns, requiring a completely different process model. The threat model (compromised web renderer, not kernel exploit specialist) does not require kernel-exploit-level isolation. seccomp + broker defense-in-depth is sufficient for the renderer threat model and avoids the 2–10× overhead.

Alt-B: In-process Sandboxing (NaCl / WebAssembly / SFI-style)

+--------------------------------------------------+
|  Browser process                                 |
|  +--------------------------------------------+  |
|  |  Renderer (in-process sandbox)             |  |
|  |  WASM / SFI / NaCl: software fault isolation|  |
|  |  address space partitioned by SW checks    |  |
|  +--------------------------------------------+  |
|  IPC: function calls / shared memory           |  |
+--------------------------------------------------+

Regime where it wins: When spawn latency, IPC latency, or inter-renderer shared state make process-level isolation too expensive — e.g., real-time collaborative editing tools or game engines where cross-component latency must be microseconds. WebAssembly sandboxing (WASM + Wasmtime or V8 WASM) is O(ns) for cross-sandbox calls vs O(µs) for UDS IPC; for workloads where 100k sandbox crossings per second are required, in-process SFI wins.

Real system embodying it: Google Native Client (NaCl, 2008); WebAssembly (W3C, 2019+); Lucet/Wasmtime (Fastly, Bytecode Alliance).

Why sbx-266 rejected it: In-process isolation cannot provide true address-space separation — a Spectre-class speculative read can cross the software-enforced boundary regardless of software checks, because the CPU speculatively executes outside the checked bounds. After Spectre/Meltdown (2018, P9), in-process isolation for cross-origin web content is architecturally broken; the fix is process-level separation. NaCl was retired from Chrome in 2019 precisely because WASM + process isolation is more correct. sbx-266 exists to implement the correct model.

Alt-C: Language-Runtime Isolation (Deno/QuickJS-in-subprocess style)

+----------------------------------------------------------+
|  Browser process                                         |
|  sbx-browser: hosts multiple renderer "isolates"        |
|  +------------------------+ +-------------------------+  |
|  |  Renderer isolate A    | |  Renderer isolate B     |  |
|  |  Deno/V8 isolate;      | |  (same process)         |  |
|  |  no OS process boundary| |                         |  |
|  +------------------------+ +-------------------------+  |
|  IPC: in-process message passing (no UDS)               |
+----------------------------------------------------------+

Regime where it wins: When the renderer runs a scripting language (JavaScript/TypeScript) whose runtime provides strong in-language isolation guarantees — e.g., Deno isolates, Cloudflare Workers (V8 isolates per request). Each V8 isolate has its own heap and cannot access another's memory via the V8 API. For workloads where the entire renderer is a managed language runtime with no native code execution, language-level isolation is cheap (microseconds) and effectively correct (assuming a correct V8). Cloudflare Workers serves millions of isolates per machine this way.

Real system embodying it: Deno (Ryan Dahl, 2018); Cloudflare Workers (V8 isolates, 2017); Node.js VM module.

Why sbx-266 rejected it: sbx-266's renderer is explicitly a general-purpose process, not a language sandbox. The renderer runs native C/Rust code (layout engine, image decoder, media) with arbitrary syscall access. A language runtime cannot sandbox native code — a JIT-compiled escape or a native plugin would bypass the isolate boundary. More fundamentally, this architecture requires trust in the language runtime's isolation (V8 is the dominant browser CVE class), whereas sbx-266 requires trust only in the kernel and the TCB — a much smaller and more auditable set.

Alt-D: Microkernel / Capability OS (seL4-style process model)

+--------------------------------------------------------------+
|  Browser "application"                                       |
|  +---------------------+   +----------------------------+   |
|  |  Renderer server    |   |  File server (FS cap)      |   |
|  |  holds only IPC cap |   |  validates file access cap |   |
|  +---------------------+   +----------------------------+   |
|  seL4 / MINIX3: all IPC via capability endpoint calls       |
|  kernel = 10,000 lines, formally verified                   |
+--------------------------------------------------------------+

Regime where it wins: When formal verification of the entire isolation stack is required — safety-critical or high-assurance environments (avionics, medical devices, military systems) where a CVE in the OS kernel is an unacceptable risk. seL4 is formally verified (no implementation bugs at the kernel level), the microkernel has a minimal attack surface (10k lines), and the capability model is enforced by hardware. The DARPA HACMS project used seL4 for unmanned vehicle isolation with this rationale.

Real system embodying it: seL4 (CSIRO/Data61, 2009); MINIX3; Genode OS framework.

Why sbx-266 rejected it: Linux is the deployment target — no existing Linux process can run on seL4 without a complete port. The Chromium browser codebase, the GPU drivers, and the userland libraries sbx-266 depends on do not run on seL4. Even if they did, the engineering cost of a microkernel port for a browser sandbox exceeds the security gain over the existing two-layer (seccomp + broker) model for the web-browser threat model. sbx-266 achieves a practically sound security posture on a commodity OS (Linux) — the security bar of seL4 is warranted for embedded safety-critical systems, not for a desktop browser where the development velocity on Linux dominates.
