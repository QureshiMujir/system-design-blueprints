Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does the Ready-drain order place "send messages to peers" after "persist WAL" but before "apply to state machine"? What invariant would break if messages were sent before the WAL was fsynced? (Phase 4 §16 S10 drain order; §7 Invariants I11 and I12)
  2. A follower is 20,000 log entries behind the leader and the WAL has been GC'd past the follower's apply_index. Walk through every step the leader takes to bring the follower back to parity, and identify the two conditions that must hold simultaneously when the follower replaces its state machine. (Phase 7 §19 S3–S4; §7 Invariants I3 and I4)
  3. A client puts key /config/db/host at revision 10, then immediately calls get /config/db/host on a follower. The follower returns KeyNotFound. Is this a linearizability violation? If yes, what mechanism prevents it; if no, explain why not, and what the follower should return instead. (Phase 6 §18 ReadIndex path; §6 Design Principle P1; §7 Invariant I8)
  4. Lease L is granted with TTL=5s on leader A. At T+3s leader A crashes. New leader B wins election at T+4s. B has no checkpoint entry in the log. When does B expire the keys bound to L? (Phase 10 §22 S7–S8 checkpoint; §8.5 lease lifecycle; §7 Invariant I6)
  5. A watch is registered with start_revision=50. The compact_revision advances to 75 while the watch syncer is replaying events from rev 50 to the current apply_index of 80. What happens to the watch, and what must the client do to recover? (Phase 9 §21 S8 and S11; Phase 13 §25 S3; §7 Invariant I7)
  6. The treeIndex shows key /x has three generations. Describe the exact sequence of Put/Delete/Put/Delete/Put operations that would produce exactly three generations, and state what create_revision and version the final KeyValue must have. (§8.1 MVCC revision model; Phase 2 §14 S1 key_index.rs)
  7. A 3-node cluster performs a membership change to add a 4th node. The leader proposes the ConfChange entry. At what point does the quorum requirement change, and what is the quorum size during the joint-consensus phase vs after C_new is committed? (Phase 7 §19 S6–S9 joint_conf.rs; §8.2 Raft state machine role table; §7 Invariant I8)
  8. The ReadIndex heartbeat rate under full 50k read load without batching would require 100,000 heartbeat messages per second (see Back-of-Envelope §7). Explain the exact mechanism that makes 50k linearizable reads per second achievable without 100k heartbeats, and what the failure mode is if the batch window is too large. (Phase 6 §18 S2 read_only.rs; Back-of-Envelope §7; §4 read latency p99 < 5 ms; Scalability Analysis)
  9. A TxnRequest arrives with compare:[version("/lock")=0], success:[put("/lock","node-1",lease=L)], failure:[get("/lock")]. The compare evaluates against the committed state at the moment of apply, not at the moment of proposal. Why is this correct? Under what race condition would evaluating at proposal time yield a wrong result? (Phase 8 §20 S4 comparison evaluation; §7 Invariant I5; Phase 6 §18 linearizability; §8.3 TxnRequest grammar)
  10. After a compaction to revision 500, the backend "key" bucket must have all entries with encode_rev(r) where r.main ≤ 500 deleted. The treeIndex must have all revisions ≤ 500 pruned from generations. But each generation must keep at least the last revision ≤ 500 if the key was live at that revision. Why? What would a read at revision 500 return if you deleted all revisions ≤ 500 unconditionally? (Phase 13 §25 S1 compaction algorithm; §8.1 generation model; Phase 3 §15 S7 historical read)
  11. gRPC watch streams use HTTP/2 flow control as a backpressure signal. Explain the path from a slow gRPC client's TCP window filling to the watch engine's try_send() failing. Name the two places in the system where backpressure is enforced and the failure mode at each. (Phase 9 §21 S6–S7 fan_out.rs; §6 Design Principle P4; Scalability Analysis watch row; HTTP/2 RFC 9113)
  12. The config layer resolver issues 4 parallel MVCC reads. Why must all 4 reads use the same ReadTx pinned to a single revision? What inconsistency would result if each read used a fresh ReadTx that could see a different revision? (Phase 11 §23 S10 resolver.rs; §8.6 layered config resolution; §7 Invariant I10; Phase 3 §15 S7 historical read)
  13. dcs-schema validates values at proposal time (before the Raft log entry is created) rather than at apply time (after the entry is committed). Explain the tradeoff: what is gained, what is lost, and under what scenario does a schema update break clients that were previously valid? (Phase 11 §23 S1 and S12; §6 Design Principle P6; §7 Invariant I9; Failure Modes schema validation regression row)
  14. The RevokeLease proposal atomically deletes all keys bound to lease L in a single main revision. Why must this be a Raft log entry and not a direct call to the MVCC store? What divergence would occur across replicas if the leader fired the delete directly? (§7 Invariant I6; §6 Design Principle P8; Phase 10 §22 S4 RevokeLease apply; §8.5 lease lifecycle)
  15. WAL repair.rs truncates at the first CRC error in the last segment. If the truncated entries were below the committed index stored in HardState, this implies data loss. Prove that this scenario cannot occur if Invariants I11 and I12 are both upheld, and describe what component would first detect the inconsistency if they were both violated simultaneously. (Phase 1 §13 S5 repair.rs; §7 Invariants I11 and I12; Phase 4 §16 S10; Failure Modes WAL corruption row)
  16. The Scalability Analysis states writes do not scale horizontally. A user proposes sharding the keyspace across two DCS clusters, each owning half the key range. What new problems does this introduce for transactions, watches, and the layered config resolver, and which of this blueprint's design principles would need to be relaxed? (Scalability Analysis; §8.3 TxnRequest grammar; Phase 9 §21 watch; Phase 11 §23 resolver; §6 Design Principles P1–P2)
  17. Describe the complete sequence of events when a client's watch channel fills (1024 events) due to a slow gRPC connection. Trace the path from the watch engine's try_send() failure through the fan_out.rs cancel logic to the client receiving the cancellation and deciding what to do next. (Phase 9 §21 S6–S7 and S11; §8.4 watch event model; Failure Modes watch missed events row)
  18. The benchmark target for put_throughput is ≥ 10,000 ops/s with 512 B values. The Back-of-Envelope model shows the WAL write bandwidth is 6.12 MB/s. What is the minimum NVMe throughput required to sustain this target at p99 write latency < 10 ms, and which Scalability Analysis mitigation is the primary lever for exceeding this target? (Back-of-Envelope §2 WAL write bandwidth; §4 write latency p99; Scalability Analysis write throughput row; Phase 1 §13 S7 fsync policy)
  19. A 5-node cluster loses nodes 4 and 5 simultaneously (quorum = 3). Node 3 was a follower 500 entries behind. Can the remaining 3-node cluster (nodes 1, 2, 3) continue to commit new entries immediately? What must node 3 do before it can vote in a new election? (Phase 5 §17 S5 become_leader; §7 Invariant I8; Phase 7 §19 S10 learner catchup; §4 failure budget)
  20. The porcupine linearizability checker in Phase 13 verifies that the recorded operation history is linearizable. What does a porcupine "fail" result mean in terms of the ReadIndex protocol, and which combination of two bugs — one in dcs-raft and one in dcs-server — could together produce a linearizability violation that passes all unit and integration tests? (Phase 13 §25 S6 checker.py; Phase 6 §18 pitfalls no-op pre-read; Phase 4 §16 S10 drain order; §7 Invariant I4)

Mental Models & First Principles

MM1 — The apply loop is the only reality. The expert's insight: dcs-mvcc's treeIndex and backend exist only as the materialized output of the Raft log; every byte of cluster state can be re-derived by replaying the log from the beginning. What this predicts: any "shortcut" write outside the log produces a replica that diverges silently. Bug class you write without it: calling mvcc.put() directly in a maintenance handler, bypassing the proposal path, so that only one node sees the change — violating I5. Where this blueprint applies it: §7 System Invariants I5; Phase 2 (§14) S6 put logic; Phase 4 (§16) apply loop.

MM2 — ReadIndex buys linearizability at the cost of one heartbeat RTT. The expert's insight: a linearizable read does not require writing to the log; it only requires confirming you are still the leader (quorum heartbeat) and that the state machine has caught up to the commit index at the time of the request. What this predicts: read latency is bounded by heartbeat RTT, not disk. Bug class you write without it: serving reads from the state machine before the no-op of the current term has committed — returning stale data that pre-dates the current leadership. Where this blueprint applies it: Phase 6 (§18) read_only.rs; §8.2 ReadIndex flow; Scalability Analysis read throughput row.

MM3 — MVCC generations are key lifecycles, not time-series. The expert's insight: a generation starts with a Put on a non-existent key (or the first Put after a tombstone) and ends with the next tombstone. The version field counts Puts within a generation, not across the key's entire history. What this predicts: a client seeing version=1 after a delete+re-put is seeing a new generation, not evidence the key is new to the store. Bug class you write without it: conflating "version=0" (tombstone) with "key has never existed", so get --rev=<tombstone_rev> returns KeyNotFound instead of the tombstone KV. Where this blueprint applies it: §8.1 generation model; Phase 2 (§14) S1 key_index.rs; Phase 3 (§15) S7 historical read.

MM4 — Lease expiry is a consensus event, not a local timer. The expert's insight: the leader's wall clock fires the expiry proposal; but the deletion of bound keys is committed through the Raft log. This means two things: (1) an isolated leader that cannot commit the proposal cannot expire the keys — the cluster is safer than the leader's clock; (2) a new leader must read the last checkpointed remaining_ttl or it will reset all TTLs, giving keys an unintended extension. What this predicts: without checkpointing, a leader failover extends every lease by up to its full granted_ttl. Bug class you write without it: firing direct mvcc.delete() from the expiry timer without a log entry — so replicas never see the delete; I6 violated. Where this blueprint applies it: §7 Invariant I6; §8.5 lease lifecycle; Phase 10 (§22) S3–S8.

MM5 — Compaction windows must be coordinated with watch resumability. The expert's insight: compaction discards history below compact_revision; a watcher that reconnects with a start_revision below compact_revision cannot replay missed events and must re-list the keyspace. If compaction races ahead of watch syncer hand-off, the syncer will try to read events from a revision that no longer exists. What this predicts: a compaction triggered concurrently with a watch registration at an old revision can produce a gap: syncer reads history up to T1, compaction removes T0–T1, live fan-out starts at T2 > T1. Bug class you write without it: allowing the syncer to start replaying events after the compaction has removed the underlying revisions — resulting in the watch engine emitting a Compacted error for a watcher that should have been valid. Where this blueprint applies it: §7 Invariant I7; Phase 9 (§21) S8 syncer; Phase 13 (§25) S3 watch coordination.

MM6 — The Ready-drain order is a hardware durability contract. The expert's insight: entries must reach durable storage (WAL fsync) before messages are sent to peers, and messages must be sent before committed entries are applied to the state machine. Inverting any step can produce a node that has committed an entry to the state machine but has no durable record of the corresponding Raft term/vote — making it vulnerable to electing a leader in a prior term whose log dominates an entry the crashed node had already applied. What this predicts: wrong drain order → data loss after a crash that cannot be detected until revision-audit finds divergence. Bug class you write without it: calling store.apply(op) before wal.sync() — so a crash between apply and sync produces an applied entry not in any log replica. Where this blueprint applies it: §7 Invariant I11; I12; Phase 4 (§16) S10 Ready drain order block.

MM7 — Backpressure must live at the channel boundary, not the consumer. The expert's insight: in an async system, the only safe place to enforce slow-consumer policy is at the try_send() call that hands off to the slow consumer's channel. Blocking at the producer (apply loop) to wait for a slow watcher propagates the slowness upstream into the consensus path — the apply loop stalls, commit index stops advancing, and the entire cluster slows. What this predicts: unbounded channels or blocking sends cause a single slow client to degrade cluster-wide write throughput. Bug class you write without it: using channel.send().await (blocking) instead of try_send() in fan_out.rs — so a client running at 10 events/s forces the apply loop to process at 10 entries/s. Where this blueprint applies it: §6 Design Principle P4; §7 Invariant (implicit); Phase 9 (§21) S6–S7.

MM8 — Joint consensus requires two quorums during transition. The expert's insight: during a membership change, the cluster temporarily holds two configurations (C_old and C_new) and requires a majority of both for any commit. This prevents any single old or new majority from making unilateral decisions during the transition window. What this predicts: if a transition is initiated when the new member is not yet caught up, a joint-consensus commit requires a quorum of C_old (the majority that includes the slow node) — potentially blocking commits. Bug class you write without it: applying C_new immediately on the ConfChange log entry without waiting for C_old+C_new joint commit — allowing a split-brain where C_old majority and C_new majority elect different leaders simultaneously. Where this blueprint applies it: §7 Invariant I8; Phase 7 (§19) S6–S9; §8.2 Raft state machine.

Glossary · 49 terms · site-wide glossary

linearizability
Strongest single-object consistency model; every op appears to take effect atomically at a point between invocation and response; reads never observe stale committed writes
sequential consistency
Weaker than linearizability; all ops ordered; does not require real-time ordering
Raft
Consensus algorithm (Ongaro 2014); leader-based; log replication; safety via quorum
term
Raft epoch; monotonically increasing; reset to higher term on any valid message
log index
1-based position of a LogEntry in the Raft log; unique within term
quorum
Majority: ⌊N/2⌋ + 1; required for commit and election
leader
Raft role that accepts proposals and drives replication
follower
Raft role that replicates log from leader
candidate
Raft role actively seeking votes to become leader
ReadIndex
Linearizable read technique; leader records commitIndex at read time; broadcasts heartbeat; waits for apply; reads from state machine
lease-read
Clock-based read technique; leader holds lease valid for election_timeout; avoids heartbeat per read; requires bounded clock skew
MVCC
Multi-Version Concurrency Control; keep all revisions of a key; reads at any revision without blocking writes
revision (main)
Global monotonically increasing txn counter; bumps once per committed txn
revision (sub)
Index of an op within a multi-op txn; 0-based
mod_revision
main revision at which a key was last modified
create_revision
main revision at which a key was first created (in current generation)
version
Count of Puts to a key since create_revision; 1 on first put; 0 on tombstone
TreeIndex
In-memory BTreeMap mapping Key → KeyIndex; tracks all generations and revisions
generation
One lifecycle of a key (create → delete); multiple generations if key recreated
tombstone
MVCC record with version=0; marks key deletion at mod_revision
compaction
Discarding MVCC history at/below compact_revision; reclaims backend space
defragmentation
Rebuilding backend file to reclaim pages freed by compaction
snapshot
Serialized state-machine + treeIndex at a specific (term, index); used for fast follower catch-up
InstallSnapshot
Raft RPC: leader sends snapshot to lagging follower
watch
Client registration to receive Events for a key/prefix/range from start_revision
watcher fan-out
Distributing a batch of Events to all matching registered watchers
event
A single mutation notification: {EventType, KeyValue, prev_kv?}
prev_kv
Previous KeyValue before the mutation; optionally included in Event
resumable watch
Reconnecting watch that provides start_revision to replay missed events
compacted-revision error
DcsError::Compacted returned when start_revision < compact_revision
lease
Time-bounded object with TTL; keys attached to a lease are deleted on expiry or revoke
grant
Create a new lease with specified TTL
keepalive
Reset lease remaining_ttl to granted_ttl
revoke
Immediately expire a lease; delete all bound keys
ephemeral key
A key bound to a lease; automatically deleted when lease expires
transaction
Atomic multi-key operation: evaluate compare predicates; apply success or failure ops; one main revision
compare-and-swap (CAS)
Txn pattern: compare version/value/lease against expected; create/update only if match
joint consensus
Raft membership change protocol; quorum requires majority of both C_old and C_new during transition
membership change
Adding or removing nodes from the Raft cluster via ConfChange log entries
key range
Interval [key, range_end) used in range requests, watch registrations, RBAC grants
range_end
Exclusive upper bound in a key range; empty = single key; prefix_end(key) = prefix scan
prefix
All keys sharing a common byte prefix; range_end = prefix_end(prefix)
RBAC
Role-Based Access Control; permissions scoped to key ranges; enforced at dcs-api boundary
config layering
Precedence-ordered inheritance: Default < Env < Service < Instance
schema validation
Type + constraint checking of value bytes against ConfigSchema before proposal
watch fragmentation
Splitting a large Event batch into multiple WatchResponse messages
backpressure
Bounded channel depth forces slow consumers to be cancelled rather than stalling producers
ResponseHeader
Metadata on every response: cluster_id, member_id, revision, raft_term
group commit
Batching multiple Raft entries into one WAL fsync to amortize fsync latency
