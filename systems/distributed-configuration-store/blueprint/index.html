1. Goal

Attribute Value
What Strongly-consistent, linearizable distributed config store: hierarchical MVCC key-value space replicated by Raft; clients put/get/range/delete/txn; watch prefixes for change streams; leases for ephemeral/TTL keys; historical revision reads; atomic multi-key transactions with compare predicates

dcs-api: gRPC/HTTP2 boundary. Authenticates requests against RBAC policy; routes KV ops as Raft proposals to leader; routes Watch requests to the watch engine; routes Lease RPCs to dcs-lease; exposes Maintenance (compact/defrag/status). Applies rate limiting and request size caps before any proposal.

dcs-server (node): Orchestrates the apply loop: drains committed entries from dcs-raft's Ready batch, applies each to dcs-mvcc in log order, then notifies dcs-watch. Drives the ReadIndex path: receives a linearizable read request, sends a ReadIndex message to Raft, waits for apply index ≥ read index, then reads from dcs-mvcc. Runs the compactor (background) and snapshotter (on demand or log threshold).

dcs-raft: Self-contained consensus module with no IO dependencies. Exposes a tick() + step(msg) + ready() interface. Internally transitions Role{Follower, Candidate, Leader}, maintains the log (in memory + WAL-backed), tracks term/vote/commit/apply indexes. Emits a Ready batch: entries to persist, messages to send to peers, committed entries ready to apply.

dcs-mvcc: The authoritative state machine. treeIndex maps Key → KeyIndex (generations of Revisions). Backend is a B-tree-like bucket store. Each write increments the global Revision. Supports point reads, range reads, historical reads, tombstones. Exports a Watchable interface that the apply loop calls after each committed entry to generate events.

dcs-watch: Watch engine manages a registry of WatchId → WatchRequest. On apply, dcs-server calls the watch engine with a batch of Events; the engine matches events to watchers by key/prefix/range, filters (no-put, no-delete, prevKV), enqueues on per-watcher channels. Backpressure: slow watcher channel fills → cancels watcher with SLOW_WATCHER error. Fragmentation: large event batches split into ≤ N events per WatchResponse.

dcs-lease: Manages LeaseId → Lease{granted_ttl, remaining_ttl, keys[]}. Leader runs an expiry ticker: each heartbeat interval, decrement remaining_ttl; expired leases trigger a RevokeLease txn through the log (deletes all bound keys atomically). KeepAlive renews remaining_ttl. Lease state checkpointed to survive leader change.

dcs-schema: Validates value bytes against a registered ConfigSchema on each Put/Txn. Resolves the layered config model: a read for (service=S, env=E, instance=I) merges keys from Default → Env → Service → Instance layers using the Layer enum precedence. Exposes an atomic effective-config snapshot.

dcs-wal: Segmented append-only log files. Each segment is a sequence of framed records: [length:u32][CRC32:u32][payload]. On startup, replays all segments to recover HardState + log entries. Supports snapshot file format (separate .snap files). Segments are created on rotation threshold; old segments pruned after snapshot.

6. Design Principles

P1 — Linearizability by Default. Every read and write on any key path returns a value consistent with a real-time total order. Tradeoff: higher read latency than eventual-consistent stores. Violation: stale follower reads silently return outdated config causing misconfigured services.

P2 — Consensus-Serialized Writes Only. No state-machine mutation outside the Raft apply loop. Tradeoff: write throughput bounded by quorum RTT. Violation: direct writes to dcs-mvcc bypass ordering → MVCC invariant broken.

P3 — MVCC Never Loses History Within the Retention Window. Revision compaction is explicit and coordinated. Tradeoff: disk amplification grows without periodic compaction. Violation: compacting a revision still referenced by an active watcher → watch returns wrong events.

P4 — Backpressure Everywhere. Every async channel has a bounded capacity; slow consumers are cancelled, not stalled. Tradeoff: aggressive watchers may be force-cancelled. Violation: unbounded watch channel → apply loop blocks → cluster-wide write stall.

P5 — Crash-Only Semantics. No graceful degradation path that compromises durability. On any unrecoverable error, dcsd exits; systemd/supervisor restarts it; WAL replay recovers state. Violation: swallowing fsync errors → committed entries lost on crash.

P6 — Schema Validation at Proposal Time. Values are validated against registered schemas before entering the Raft log. Tradeoff: slightly higher write latency. Violation: invalid values in the log can be applied but never corrected without compaction.

P7 — Layered Config Resolution is Read-Only. Layer inheritance is a query-time computation; it never writes merged keys back to the store. Tradeoff: every read incurs merge cost (cached). Violation: writing merged keys introduces fan-out invalidation complexity.

P8 — Lease Expiry Through the Log. Lease TTL expiry fires a RevokeLease proposal; the delete of bound keys is atomic via the Raft log. Tradeoff: expiry latency ≤ 1 heartbeat interval beyond TTL. Violation: direct ephemeral-key deletion without log entry → divergence across replicas.

P9 — Monotonic Global Revision. The global Revision.main counter is strictly monotonically increasing, never reset by leadership change. Tradeoff: revision space must be 64-bit. Violation: revision wrap or reset → historical reads return wrong data.

P10 — Observability by Default. Every significant event (proposal, apply, leader change, compaction, watcher cancel) emits a structured log line and a metric counter/histogram. Tradeoff: minor overhead per operation. Violation: silent failures make production incidents undiagnosable.

P11 — Explicit Membership Changes. Node adds/removes go through joint-consensus ConfChange entries; no implicit rebalancing. Tradeoff: operator must drive membership explicitly. Violation: split-brain if membership diverges across a partition.

P12 — Stable Wire Compatibility. Proto message schemas are additive-only; no field removals or renumbering after v1.0. Tradeoff: accumulated deprecated fields. Violation: field renumber breaks rolling upgrades.

P13 — Bounded Resource Usage. Watch channel depth, lease count, max key/value sizes, WAL segment count, snapshot count — all hard-capped with explicit error returns, never silently grown. Violation: unbounded growth → OOM on the apply node.

8. Domain Model

8.1 MVCC Revision Model

Revision { main: i64, sub: i64 }
  main — global txn counter; increments once per committed txn
  sub  — index within a multi-op txn; [0..n-1]

KeyValue {
  key             : Key         // bytes
  create_revision : i64         // main at first Put
  mod_revision    : i64         // main at last Put/Delete
  version         : i64         // count of Puts since create (0 if tombstone)
  value           : Vec<u8>
  lease           : i64         // 0 = no lease
}

Generation model (treeIndex):

KeyIndex { key, modified: Revision, generations: Vec<Generation> }
Generation { created: Revision, version: i64, revs: Vec<Revision> }
  - new Put on non-existent key  → new Generation; created = current rev; version = 1
  - subsequent Put               → append rev to current Generation; version++
  - Delete                       → append tombstone rev; start next Generation on next Put
  - compaction below rev R       → prune revs where rev.main < R from generations

Example key lifecycle (main revisions 1–5):

rev=1: PUT /config/db/host = "db1"   → gen[0]={created:1, revs:[1]}         version=1
rev=2: PUT /config/db/host = "db2"   → gen[0]={created:1, revs:[1,2]}       version=2
rev=3: DEL /config/db/host           → gen[0]={created:1, revs:[1,2,3†]}     version=0  (†=tombstone)
rev=4: PUT /config/db/host = "db3"   → gen[1]={created:4, revs:[4]}          version=1
rev=5: GET at rev=2                  → walks gen[0].revs, finds rev=2 → "db2"

8.2 Raft State Machine

Role transition table:

Current Role  │ Event                              │ Next Role
──────────────┼────────────────────────────────────┼───────────────
Follower      │ election_timeout, no heartbeat     │ Candidate
Candidate     │ receives quorum votes              │ Leader
Candidate     │ discovers higher term              │ Follower
Candidate     │ election timeout (split vote)      │ Candidate (new term)
Leader        │ discovers higher term              │ Follower
Leader        │ receives AppendResp quorum         │ stays Leader; advances commit
Follower      │ receives valid AppendEntries       │ stays Follower; resets timeout

Log invariants (Log Matching Property):

  • If two entries at same index have same term → identical content
  • If entry is committed → all preceding entries committed

ReadIndex flow (linearizable read, no log write):

1. Client → Leader: RangeRequest with linearizable flag
2. Leader sends ReadIndex heartbeat to quorum (confirms still leader)
3. Leader records readIndex = commitIndex at time of request
4. Leader waits: applyIndex ≥ readIndex
5. Leader reads from dcs-mvcc at applyIndex
6. Returns result with ResponseHeader.revision = applyIndex

8.3 TxnRequest Grammar (EBNF)

TxnRequest   ::= "compare" ":" Compare* "success" ":" Op* "failure" ":" Op*
Compare      ::= CompareTarget "(" Key ")" CompareResult value
CompareTarget::= "version" | "create" | "mod" | "value" | "lease"
CompareResult::= "=" | "!=" | "<" | ">"
Op           ::= RangeOp | PutOp | DeleteOp | TxnOp
RangeOp      ::= "get" "(" Key ["," RangeEnd] ")"
PutOp        ::= "put" "(" Key "," Value ["," LeaseId] ")"
DeleteOp     ::= "delete" "(" Key ["," RangeEnd] ")"
TxnOp        ::= TxnRequest            // nested; bounded depth = 3

Worked Txn Example (CAS: update only if version=3):

compare: [version("/cfg/x") = 3]
success: [put("/cfg/x", "new-val")]
failure: [get("/cfg/x")]
→ atomic; entire txn is one log entry at main rev R

Malformed Txn Examples:

compare: [value("/cfg/x") > "abc"]   // INVALID: value compare with ">" is rejected
compare nesting depth = 4            // INVALID: exceeds depth limit
put key_size = 2 MB                  // INVALID: exceeds 1 MB key cap → ValidationFailed

8.4 Watch Event Model

WatchRequest  { key, range_end, start_revision, prev_kv: bool, filters: WatchFilters }
WatchResponse { watch_id: WatchId, events: Vec<Event>, compact_revision: i64, header }
Event         { ty: Put|Delete, kv: KeyValue, prev_kv: Option<KeyValue> }
WatchFilters  { no_put: bool, no_delete: bool }

Watch lifecycle sequence:

Client                         dcs-api / dcs-watch
  │──── WatchCreate(req) ────────────────────────────────▶│
  │◀─── WatchCreated(watch_id) ──────────────────────────│
  │                              [key events from apply] │
  │◀─── WatchResponse(events) ───────────────────────────│ (repeated)
  │──── WatchCancel(watch_id) ───────────────────────────▶│
  │◀─── WatchCancelled(watch_id) ────────────────────────│

Compacted-revision error path:

Client requests start_revision=50; compact_revision=100
→ WatchResponse { compact_revision=100, events=[], canceled=true }
→ Client must: List(key/prefix) at revision≥100; re-Watch from response.header.revision

8.5 Lease Lifecycle

States: { Absent → Granted → Active → Expired | Revoked }
  grant(ttl)        → LeaseId; remaining_ttl = ttl
  keepalive(id)     → remaining_ttl reset to granted_ttl (if id valid)
  attach(id, key)   → Lease.keys.push(key)
  detach(id, key)   → Lease.keys.remove(key)
  expiry ticker     → each heartbeat: remaining_ttl -= heartbeat_interval
                    → remaining_ttl ≤ 0 → propose RevokeLease(id)
  revoke(id)        → propose RevokeLease(id) immediately
  RevokeLease apply → txn: delete all keys in Lease.keys

Leader change / checkpoint:

Leader A checkpoints Lease{id, remaining_ttl} into log entry (LeaseCheckpoint)
Leader B wins election → reads checkpointed remaining_ttl; continues countdown
Without checkpoint: Leader B resets all TTLs → ephemeral keys live too long (false positive availability)

8.6 Layered Config Resolution

Layer precedence (low → high): Default < Env < Service < Instance
Resolution(service=S, env=E, instance=I, key=K):
  candidates = [
    get(key="/default/K"),
    get(key="/env/{E}/K"),
    get(key="/service/{S}/K"),
    get(key="/instance/{I}/K")
  ]
  result = last non-nil candidate (highest layer wins)

Worked Example:

/default/db/pool_size    = "5"
/env/prod/db/pool_size   = "20"
/service/api/db/pool_size = (not set)
/instance/api-1/db/pool_size = "10"
→ Resolution(service=api, env=prod, instance=api-1, key=db/pool_size) = "10"  (Instance wins)

20.1 Objectives

Step File Action
S1 TxnRequest encoding serialize TxnRequest → protobuf bytes → Raft EntryKind::Normal payload (ADR-A07 prost; §8.3 TxnRequest grammar; etcd v3 API proto)

S4 Comparison evaluation for each Compare: read KeyValue for key; match target (version/create/mod/value/lease) against expected; AND all results (Herlihy & Wing 1990 atomicity; I10)
S5 Op application PutOp → put(key, value, lease); RangeOp → range(key, range_end) included in response; DeleteOp → delete_range; TxnOp → recurse (depth-check) (§8.3 TxnRequest grammar; I5)

Mental Models & First Principles

MM1 — The apply loop is the only reality. The expert's insight: dcs-mvcc's treeIndex and backend exist only as the materialized output of the Raft log; every byte of cluster state can be re-derived by replaying the log from the beginning. What this predicts: any "shortcut" write outside the log produces a replica that diverges silently. Bug class you write without it: calling mvcc.put() directly in a maintenance handler, bypassing the proposal path, so that only one node sees the change — violating I5. Where this blueprint applies it: §7 System Invariants I5; Phase 2 (§14) S6 put logic; Phase 4 (§16) apply loop.

MM2 — ReadIndex buys linearizability at the cost of one heartbeat RTT. The expert's insight: a linearizable read does not require writing to the log; it only requires confirming you are still the leader (quorum heartbeat) and that the state machine has caught up to the commit index at the time of the request. What this predicts: read latency is bounded by heartbeat RTT, not disk. Bug class you write without it: serving reads from the state machine before the no-op of the current term has committed — returning stale data that pre-dates the current leadership. Where this blueprint applies it: Phase 6 (§18) read_only.rs; §8.2 ReadIndex flow; Scalability Analysis read throughput row.

MM3 — MVCC generations are key lifecycles, not time-series. The expert's insight: a generation starts with a Put on a non-existent key (or the first Put after a tombstone) and ends with the next tombstone. The version field counts Puts within a generation, not across the key's entire history. What this predicts: a client seeing version=1 after a delete+re-put is seeing a new generation, not evidence the key is new to the store. Bug class you write without it: conflating "version=0" (tombstone) with "key has never existed", so get --rev=<tombstone_rev> returns KeyNotFound instead of the tombstone KV. Where this blueprint applies it: §8.1 generation model; Phase 2 (§14) S1 key_index.rs; Phase 3 (§15) S7 historical read.

MM4 — Lease expiry is a consensus event, not a local timer. The expert's insight: the leader's wall clock fires the expiry proposal; but the deletion of bound keys is committed through the Raft log. This means two things: (1) an isolated leader that cannot commit the proposal cannot expire the keys — the cluster is safer than the leader's clock; (2) a new leader must read the last checkpointed remaining_ttl or it will reset all TTLs, giving keys an unintended extension. What this predicts: without checkpointing, a leader failover extends every lease by up to its full granted_ttl. Bug class you write without it: firing direct mvcc.delete() from the expiry timer without a log entry — so replicas never see the delete; I6 violated. Where this blueprint applies it: §7 Invariant I6; §8.5 lease lifecycle; Phase 10 (§22) S3–S8.

MM5 — Compaction windows must be coordinated with watch resumability. The expert's insight: compaction discards history below compact_revision; a watcher that reconnects with a start_revision below compact_revision cannot replay missed events and must re-list the keyspace. If compaction races ahead of watch syncer hand-off, the syncer will try to read events from a revision that no longer exists. What this predicts: a compaction triggered concurrently with a watch registration at an old revision can produce a gap: syncer reads history up to T1, compaction removes T0–T1, live fan-out starts at T2 > T1. Bug class you write without it: allowing the syncer to start replaying events after the compaction has removed the underlying revisions — resulting in the watch engine emitting a Compacted error for a watcher that should have been valid. Where this blueprint applies it: §7 Invariant I7; Phase 9 (§21) S8 syncer; Phase 13 (§25) S3 watch coordination.

MM6 — The Ready-drain order is a hardware durability contract. The expert's insight: entries must reach durable storage (WAL fsync) before messages are sent to peers, and messages must be sent before committed entries are applied to the state machine. Inverting any step can produce a node that has committed an entry to the state machine but has no durable record of the corresponding Raft term/vote — making it vulnerable to electing a leader in a prior term whose log dominates an entry the crashed node had already applied. What this predicts: wrong drain order → data loss after a crash that cannot be detected until revision-audit finds divergence. Bug class you write without it: calling store.apply(op) before wal.sync() — so a crash between apply and sync produces an applied entry not in any log replica. Where this blueprint applies it: §7 Invariant I11; I12; Phase 4 (§16) S10 Ready drain order block.

MM7 — Backpressure must live at the channel boundary, not the consumer. The expert's insight: in an async system, the only safe place to enforce slow-consumer policy is at the try_send() call that hands off to the slow consumer's channel. Blocking at the producer (apply loop) to wait for a slow watcher propagates the slowness upstream into the consensus path — the apply loop stalls, commit index stops advancing, and the entire cluster slows. What this predicts: unbounded channels or blocking sends cause a single slow client to degrade cluster-wide write throughput. Bug class you write without it: using channel.send().await (blocking) instead of try_send() in fan_out.rs — so a client running at 10 events/s forces the apply loop to process at 10 entries/s. Where this blueprint applies it: §6 Design Principle P4; §7 Invariant (implicit); Phase 9 (§21) S6–S7.

MM8 — Joint consensus requires two quorums during transition. The expert's insight: during a membership change, the cluster temporarily holds two configurations (C_old and C_new) and requires a majority of both for any commit. This prevents any single old or new majority from making unilateral decisions during the transition window. What this predicts: if a transition is initiated when the new member is not yet caught up, a joint-consensus commit requires a quorum of C_old (the majority that includes the slow node) — potentially blocking commits. Bug class you write without it: applying C_new immediately on the ConfChange log entry without waiting for C_old+C_new joint commit — allowing a split-brain where C_old majority and C_new majority elect different leaders simultaneously. Where this blueprint applies it: §7 Invariant I8; Phase 7 (§19) S6–S9; §8.2 Raft state machine.

etcd v3: The direct normative model for this blueprint's wire format and MVCC semantics. etcd's key design decision that differs from DCS is language choice (Go + GC). The GC produces periodic p99 spikes on the apply loop under sustained high-throughput — reported in etcd performance analyses at > 5 ms p99 under GC pressure. etcd's niche: production Kubernetes; best-in-class tooling, operability, and client ecosystem; the right choice unless GC latency is a hard constraint.

ZooKeeper 3.x: Chose ZAB over Raft for leader election semantics (ZAB's "recovery phase" differs from Raft's term-based election) and models data as a tree of znodes rather than a flat key space. The one-shot watch (auto-removed after first event, must re-register) simplifies the server but forces clients into a register-check-register loop that can miss events during re-registration. ZooKeeper's niche: Kafka metadata coordination (until KRaft migration), Hadoop NameNode HA — situations where the existing ZK client ecosystem and per-node ZAB ordering guarantees match the workload.

Consul (KV + sessions): Chose HTTP long-polling over gRPC streaming, making watch semantics stateless on the server side (no per-client channel state) but requiring the client to re-poll on every event — higher per-watch overhead at scale. Sessions are health-check-driven (not just TTL), enabling service-mesh integration where node health directly drives key expiry. Consul's niche: service discovery + KV in a single agent; natively multi-datacenter via WAN gossip; the right choice when both service mesh and configuration storage are needed and gRPC is not available.

TiKV (PD meta-server): Uses Multi-Raft (one Raft group per key range region) to achieve horizontal scale beyond a single Raft group's throughput ceiling. The per-region sharding means there is no global revision counter — TiKV uses MVCC timestamps from the centralized TSO (timestamp oracle) instead. TiKV's niche: datasets that exceed a single node's storage (TBs of key-value data) where horizontal sharding is required; its complexity (region splitting, region scheduling, TSO) far exceeds what a configuration store needs.

Back-of-Envelope Capacity Model

All numbers are derived from §4 System Constraints. Formulas are shown step by step.

1. Write bandwidth (network, leader → followers):

Write throughput × payload = bandwidth per follower
10,000 ops/s × 512 B (value) + ~100 B (KV overhead + proto framing)
= 10,000 × 612 B = 6.12 MB/s per follower
3-node cluster: leader sends to 2 followers → 2 × 6.12 = 12.24 MB/s outbound from leader

2. WAL write bandwidth (disk, per node):

Same entries persisted to WAL before sending (I11)
10,000 ops/s × 612 B = 6.12 MB/s sequential write
At 64 MB segment size: new segment every 64 / 6.12 ≈ 10.5 s
WAL segment count before snapshot: snapshot at 10,000 entries → 1 s at 10k ops/s → 1 segment/snapshot

3. treeIndex memory (for 10M keys):

§4: Memory (treeIndex) ≤ 512 MB for 10M keys
Per-key estimate: KeyIndex = Key(avg 50 B) + modified Revision (16 B) + Vec<Generation> (1 generation × ~64 B) ≈ 130 B
BTreeMap node overhead: ~40 B per entry (pointers, balance)
10M × (130 + 40) = 10M × 170 B = 1.7 GB  ← exceeds 512 MB
→ In practice etcd uses a more compact encoding; DCS must use Bytes (reference-counted) for Key and pool small Vecs
→ Budget forces average key ≤ 50 B; average 1 live generation; otherwise prefix-shard TreeIndex

4. Backend on-disk size:

§4: Max keyspace 8 GB per node
10M keys × 512 B value avg = 5.12 GB values
+ treeIndex metadata in backend "meta" bucket: ~170 B × 10M = 1.7 GB
Total ≈ 6.82 GB → within 8 GB ceiling with 1.18 GB headroom for compaction overhead

5. Watch fan-out channel memory:

§4: Max concurrent watchers = 10,000; channel depth = 1024 events (Phase 9 S7)
Per WatchResponse: header (48 B) + Event{KV(~200 B), prev_kv(~200 B)} × 1 event ≈ 450 B
Worst-case: all 10,000 channels full: 10,000 × 1,024 × 450 B = 4.61 GB
→ Budget forces channel depth << 1024 for large-KV workloads, or per-channel memory cap
→ At 200 B avg event: 10,000 × 1,024 × 200 = 2.05 GB — borderline; enforce watcher memory cap

6. File descriptors per node:

§4: FDs per node ≤ 512
WAL segments: §4 WAL segment size 64 MB; snapshot trigger at 100 MB WAL → ~2 open segments + 1 current = 3
Backend: 1 file (B-tree)
Peer gRPC connections: 2 peers × ~5 connections each = 10
Client gRPC connections: gRPC max streams 1,000 per connection; typical 5–20 connections → 20 FDs
Misc (stdout, stderr, metrics socket, etc.): ~10
Total: 3 + 1 + 10 + 20 + 10 = 44 FDs  ← well within 512 ceiling
→ The FD budget is comfortable; ceiling mainly protects against watch stream leak (10k watchers each needing one stream object but not one FD)

7. ReadIndex heartbeat rate under full read load:

§4: Read throughput ≥ 50,000 ops/s (linearizable)
Each ReadIndex triggers heartbeats to 2 followers (3-node)
Without batching: 50,000 × 2 = 100,000 heartbeat messages/s ← unsustainable
With batching per heartbeat interval (default 100 ms): 50,000 reads / (1/0.1) = 5,000 reads per heartbeat batch
→ Must batch ReadIndex requests per heartbeat interval to achieve 50k ops/s (§18 Phase 6 S2; Scalability Analysis)

8. Lease expiry ticker cost:

§4: Max leases 65,536; heartbeat_interval default = 100 ms (1/10 of election_timeout = 1 s)
Naive O(leases) per tick: 65,536 checks × 10 ticks/s = 655,360 operations/s
With min-heap (Phase 10 S3 note): only expired leases popped; O(expired × log N) per tick
At steady-state (low expiry rate): O(log 65536) = 16 comparisons/tick → negligible

9. Snapshot size estimate:

treeIndex (512 MB worst case) + backend (8 GB max) + LeaseManager state (65536 × Lease ≈ 65536 × 64 B = 4 MB) + SchemaRegistry (negligible)
= 512 MB + 8 GB + 4 MB ≈ 8.5 GB uncompressed
zstd level 1 compression ratio on typical config data ≈ 3–5×
→ snapshot ≈ 1.7–2.8 GB → §4 startup warm (< 3 s) requires 1.7 GB / 3 s ≈ 570 MB/s read throughput (NVMe capable)

10. WAL replay time on cold start:

§4: Startup cold < 10 s; WAL replay at 500 MB/s (Phase 1 S9 acceptance criterion)
Entries between last snapshot and crash: at 10k ops/s × 10k entries per snapshot trigger = 10k entries max
10k entries × 612 B each = 6.12 MB → replay in 6.12 / 500 ≈ 12 ms → negligible
Full cold replay (no snapshot, 8 GB WAL): 8 GB / 500 MB/s = 16 s → exceeds 10 s ceiling
→ Confirms: snapshot is mandatory; cold start without snapshot fails the §4 constraint

11. Compaction backend delete cost:

§4: Compaction latency < 500 ms
After 1h at 10k ops/s: 36M entries to delete from backend "key" bucket
At 1000 entries per WriteTx batch (Phase 13 S1 note): 36,000 transactions
At 1 ms per WriteTx (in-memory B-tree): 36 s → far exceeds 500 ms
→ Requires batching > 10k entries per WriteTx, or async compaction spread over multiple ticks
→ Backend must support range-delete (delete all keys below encoded_rev threshold in one pass)

Alternative Architectures

Alternative 1 — Log-Structured State Machine with LSM Backend

clients
  |
  v
API layer (gRPC)
  |
  v
Raft log  ──────────────────────────────────────┐
  |                                             |
  v (apply)                                     v (WAL segments)
LSM store (RocksDB)                         RocksDB WAL
  - key → latest value (CF: kv)
  - (key, rev) → value (CF: history)
  - compact old CFs via RocksDB compaction
  |
  v
Watch engine (reads from RocksDB snapshots)

Regime where this wins: Keyspace exceeds available memory (100 GB+ of key-value data) and write amplification from RocksDB's compaction is acceptable. LSM write throughput scales with disk bandwidth rather than with the size of the in-memory index. If the average key size is large (> 4 KB values, millions of keys), the B-tree treeIndex approach exhausts memory; LSM keeps hot data in block cache and offloads cold data to disk transparently.

Real system that embodies it: TiKV uses RocksDB per Raft region as its storage engine. etcd historically evaluated RocksDB before choosing bbolt; chose bbolt for its simpler single-writer semantics and absence of compaction write amplification in the small-dataset regime.

Why this blueprint rejected it: DCS targets a config store with ≤ 10M keys at ≤ 512 MB index. A custom B-tree (inspired by bbolt) gives zero external C dependencies (ADR-A05), deterministic latency without LSM compaction stalls, and simpler crash recovery semantics. Portfolio project 67 (B-Tree) is the direct reference; using RocksDB would eliminate that learning objective. LSM compaction pauses would violate the p99 write latency < 10 ms target unpredictably.

Alternative 2 — Multi-Raft Sharded Architecture

clients
  |
  v
Routing layer (key → region)
  /                \
 v                  v
Region 1           Region 2
Raft group         Raft group
(keys /a–/m)       (keys /n–/z)
 |                  |
 v                  v
Local MVCC         Local MVCC
store              store

Regime where this wins: Write throughput must exceed a single Raft group's ceiling (typically 50–100k ops/s on a 3-node cluster). When the config store serves millions of microservices generating continuous write load (key churn from service deployments), a single Raft log becomes the bottleneck. Horizontal sharding lets N Raft groups each carry 1/N of the write load, scaling linearly with group count.

Real system that embodies it: TiKV's Placement Driver (PD) coordinates Multi-Raft regions. Google Chubby explored but deliberately rejected sharding — their insight was that Chubby's load is dominated by reads (lease renewal), not writes, so a single leader suffices.

Why this blueprint rejected it: Cross-shard transactions (a TxnRequest spanning two regions) require distributed 2PC, making Phase 8 (§20) an order of magnitude more complex. Cross-shard watches require a fan-out broker. The layered config resolver (Phase 11, §23) issues 4 reads per resolve; with two shards it could hit both, requiring a scatter-gather layer. DCS targets configuration storage (not OLTP), where the write load stays comfortably below 10k ops/s (§4). Complexity is the wrong tradeoff at this scale.

Alternative 3 — Gossip-Based Eventually-Consistent Config Store

node-1 ──── gossip ──── node-2
  |                       |
  └──────── gossip ────── node-3

Each node:
  - local in-memory KV (eventual)
  - CRDTs for conflict resolution (LWW or vector clocks)
  - watch: local notification, no global ordering
  - no Raft; no leader; no quorum writes

Regime where this wins: Global geo-distribution where network partitions between datacenters are expected to last hours (not milliseconds), and the config values are idempotent (e.g., feature flags that can be stale for seconds). Gossip-based stores survive indefinite partitions; a linearizable Raft cluster unavailable during a partition refuses writes. High availability across regions without accepting quorum write latency (100+ ms WAN RTT) is the primary driver.

Real system that embodies it: Consul (cross-datacenter replication via gossip; eventual for cross-DC reads) and Serf. Dynamo-style stores (Cassandra, Riak) use gossip + eventual consistency for similar reasons.

Why this blueprint rejected it: The entire §1 Goal states "strongly-consistent, linearizable" as a hard requirement. Config stores that can serve stale values cause misconfigured services that are difficult to diagnose (§6 Design Principle P1 explicitly names this failure mode). The portfolio also requires building consensus, MVCC, and watch semantics — gossip provides none of those learning objectives.
