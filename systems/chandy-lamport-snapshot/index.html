In one paragraph

Chandy–Lamport is a way to photograph a running distributed program without stopping it: each process records its own state, and every message still in flight on a channel is recorded too, so the pieces add up to one consistent global state (§1.1). This blueprint builds it from scratch in Rust as a single-binary, single-host reference implementation. The processes are simulated, and a seeded scheduler makes every run exactly reproducible (§1.4, §3.2 cl-sim). Its users are engineers, students and reviewers who study the algorithm; it is a teaching and portfolio artifact, not a service (§1.4, §1.5). Each snapshot is then checked for consistency and searched for termination, deadlock and conservation (§1.1).

The problem, concretely

Several processes pass messages over channels, and you want one picture of "the whole system right now". There is no global clock, so each process can only record itself at its own moment (Glossary, "Reachable state"; §1.1). Record carelessly and messages in transit are lost from the picture, which breaks the conservation sum (P6, I6). The blueprint's own failure trace (§8.11) has one token in a three-process ring. The marker overtakes the token, so the receiver records its state before the token arrives, and the token is then recorded neither in a process nor on the channel. The snapshot totals 0 tokens where the system holds 1 (§8.11). That sum is exactly the kind of check the design uses as its end-to-end oracle (MM7, I6).

The brute-force fix is to freeze everything, collect state, and resume. The blueprint rejects this: the pause grows with process count and state size, and in its example a 1 ms pause at 64 processes running 500,000 steps per second eliminates 500 simulation steps (Alternative Architectures, ALT-1). Freezing also violates the non-blocking principle (P2). So the target is three things at once: a cut with no effect before its cause (P1, I1), no application pause (P2), and a way to capture messages in transit without a global clock (P6). The one price is that every channel must deliver in order (P1, P3).

How it works, end to end

Follow one snapshot through the boxes of §3.1, drawn smaller and coloured by role:

  1. Setup (cl-cli). It parses the topology, application type, seed, initiator and trigger step, then hands a RunConfig to the simulator. It holds no business logic (§3.2 cl-cli, §4.9).
  2. Application traffic (cl-app, cl-process). A token ring or a bank-transfer computation runs through the AppHandler trait; cl-process logs every send, receive and internal step as an Event (§3.2 cl-app, cl-process).
  3. Channels and delivery (cl-channel, cl-transport). Each channel is a directed queue (VecDeque) between exactly two processes; cl-transport is only a registry that routes a dequeued message to its receiver (§3.2 cl-channel, cl-transport).
  4. The scheduler (cl-sim). Each step picks a deliverable channel with a seeded generator, delivers its head message, and appends an Event with a vector clock to the EventLog (§3.2 cl-sim, §8.13). It also injects the snapshot initiation at a chosen step (§3.2 cl-sim).
  5. The protocol (cl-snapshot). It applies the marker-sending and marker-receiving rules per (process, SnapshotId) (§3.2 cl-snapshot, §8.2).
  6. Assembly (cl-recorder). It keeps a pending set of processes; when the last one signals completion it assembles and seals the GlobalSnapshot exactly once (§8.22, I5).
  7. Checks (cl-verify, cl-detect). cl-verify checks the cut against the event history; cl-detect evaluates termination, deadlock and conservation on the snapshot alone (§3.2, §8.8).

cl-core holds the shared types and depends on nothing in the workspace (§3.2 cl-core, §4.3).

The core ideas

The marker rules: record once, then flood (§8.2, P4, P5)

A marker is a message that carries only a snapshot id and no application data (P4). The initiator records its own state, then puts a marker on every outgoing channel before any further application message (§8.2.1, §3.2). A process that sees its first marker for a snapshot records its state, marks the arrival channel as empty (nothing in flight on it), starts recording every other incoming channel, and sends markers on all outgoing channels (§8.2.1). Any later marker for the same snapshot only closes recording on the channel it arrived on (§8.2.1). The local state is written exactly once per snapshot (P5, I3). The blueprint's ring trace (§8.10), with the three processes numbered 0, 1, 2 (§8.10 gives them a P prefix):

Step What happens (§8.10)
1 Process 0 holds the one token and queues it on channel c01 toward process 1
2 Process 0 initiates: records token=0, queues its marker on c01, behind the token
3 c01 delivers the token first (FIFO), so process 1 holds it; then the marker: process 1 records token=1, c01 is Done and empty, marker goes out on c12
4 Process 2 gets its first marker: records token=0, c12 is Done, marker goes out on c20
5 Process 0 gets the marker on c20: Done on all channels, so it is complete

Result: states 0, 1, 0, all channel lists empty, total 1, conservation holds (§8.10). Steps 3 and 6 of §8.10 also have process 1 recording or closing a channel c20, but §8.10's own channel list defines c20 as the channel from process 2 into process 0, and step 4 corrects itself mid-line ("actually c01 not incoming to P2"). The blueprint does not resolve this. The initiator's incoming channels are also stated three ways: Done (Phase 6 §6.1), NotStarted (Phase 6 step 2, §3.2), and Recording at once (a later Phase 6 bullet, §8.2.1).

The channel window: two timestamps, not one (§8.2, MM3, P6, I4)

The recorded state of a channel is the set of messages sent before the sender's cut point and received after the receiver's cut point (P6). Concretely: the window opens at the receiver's first marker, and closes when that channel's own marker arrives (MM3, I4). Different incoming channels of one process close at different times, so a single "recording started" flag per process is a bug (MM3). In the §8.10 trace nothing arrives inside any window, so every channel list is empty, and the token appears in the recorded state of process 1 instead (§8.10).

FIFO is the proof, not a convenience (P3, MM8, §8.11)

The consistency theorem assumes order-preserving channels (P3, MM8). The §8.11 trace shows why: if the marker overtakes the token on c01, process 1 records token=0, closes c01 as empty, and only then receives the token, which is in no recorded place. The total is 0, not 1 (§8.11). cl-verify reports a CutInconsistency for it, and this is the Phase 14 negative test (§8.11, P3). Each channel carries a per-channel sequence number, and a delivery whose number is not the expected next one is rejected (§8.3, §8.4, I2).

A consistent cut and how it is verified (MM1, §8.6, I1, P12)

A consistent cut is a set of events that is closed under "happened before": if an event is in it, every event that causally precedes it is in it too (MM1). The blueprint's predicate: for every receive in the cut, the matching send is in the cut or the message is in the channel state (§8.6, I1). For process P, the cut position is the index of its first-marker receipt (§8.6). Vector clocks decide "before": clock a is below clock b iff every component of a is at most b's and at least one is smaller (§8.6). Verification is a separate pass after the snapshot, never an inline assertion, so the protocol pays no verification cost and the checker can run again on stored artifacts (P12).

Stable properties and conservation (P8, MM5, MM7, §8.8, §8.14)

A stable property is one that, once true, stays true (P8, MM5). Termination (all idle and all channels empty), deadlock (a cycle in the wait-for graph) and conservation are stable; momentary idleness and transient load are not (P8, §8.8). So a stable property found in a consistent snapshot holds in every state reachable from it (P8, I7), and the StableProperty enum contains only those three (P8). Conservation is the end-to-end oracle (MM7): process-state sum plus channel-state sum must equal the initial amount (I6, §8.14). For the token ring that is one sum over tokens plus in-flight tokens (§8.14).

Determinism and concurrent snapshots (P9, MM4, P10, MM6, §8.7, §8.13)

Each simulator step picks a non-empty channel with a seeded generator and delivers its head, so seed determines schedule, events, snapshot and verdict (§8.13, P9, I9). That turns an unreproducible interleaving bug into a replayable seed (MM4). Several snapshots can run at once because all recording state is stored per SnapshotId, and a marker only touches its own snapshot's record (§8.7, P10, I8). MM6 calls this instance isolation by an opaque key, the way Raft uses term+index and Paxos a ballot number.

The trade-offs — where engineers disagree

Concurrency model: a single-threaded simulator (ADR-04)

Chosen: one deterministic thread in cl-sim, with optional threads in cl-transport guarded by Mutex queues, because testing needs controlled interleavings and an async scheduler would hide races (ADR-04). Rejected: tokio async, rayon. When the rejected choice is right: Tokio when cl-transport runs over real networks, where event-driven I/O beats thread-per-channel above 100 real processes; Rayon for CPU-bound parallel verification of independent snapshots (ADR-04).

Random numbers: a seeded ChaCha8 generator (ADR-07)

Chosen: rand_chacha::ChaCha8Rng seeded from --seed u64, reproducible across platforms (ADR-07). Rejected: SmallRng, StdRng, OS entropy. When the rejected choice is right: OS entropy in a production real-transport setting where an attacker must not predict delivery order; SmallRng when memory on embedded targets is the hard limit (ADR-07). The blueprint is inconsistent here: P9 and I9 name SmallRng as the generator, while ADR-07 and §8.13 choose ChaCha8Rng.

Channel queue: a plain VecDeque with sequence numbers (ADR-08)

Chosen: VecDeque<(u32, Message)> with a monotone seq_no, giving O(1) push and pop and a hook for deliberately breaking FIFO in negative tests (ADR-08). Rejected: ring buffer, lock-free queue. When the rejected choice is right: a lock-free queue such as crossbeam-queue::ArrayQueue, once cl-transport uses real OS threads and lock contention on the Mutex<VecDeque> becomes measurable above 1 M msg/s per channel (ADR-08).

Per-snapshot state: one record per SnapshotId (ADR-09)

Chosen: HashMap<SnapshotId, PerSnapshotRecord> per process, supporting concurrent snapshots and enforcing isolation by key (ADR-09, §8.7). Rejected: a single global recording state. When the rejected choice is right: when only one snapshot at a time is ever needed, such as termination detection alone, and the per-id maps cost too much memory on small nodes (ADR-09). The container type disagrees across sections: P10, I8 and HQ6 say BTreeMap, ADR-09 and §8.7 say HashMap, while P9 and I9 call for BTreeMap only in cl-sim and cl-verify.

Assembling the result: a blocking collector (ADR-11)

Chosen: the recorder waits for every process's completion event and then seals the snapshot, because the simulated environment delivers reliably and blocking is simpler (ADR-11, §8.22). Rejected: distributed two-phase commit, gossip. When the rejected choice is right: gossip in wide-area systems where one central recorder is a latency bottleneck; two-phase commit when assembly must be transactional and a failed assembler must not leave a partial snapshot visible (ADR-11).

Detecting stable properties: post-hoc on the snapshot (ADR-12)

Chosen: DFS cycle search for deadlock, a sum check for conservation, and idle-and-empty for termination, all run on the snapshot, so detection never interferes with the running computation (ADR-12). Rejected: Dijkstra–Scholten, token-based detection. When the rejected choice is right: Dijkstra–Scholten when a full snapshot is too expensive for a real diffusing computation; token-based when event rates are so high that post-hoc latency is unacceptable (ADR-12).

Checking the cut: a causal check over the event log (ADR-13)

Chosen: for each receive in the cut assert the matching send is in the cut or in channel state, cross-checked with vector clocks, with no re-execution (ADR-13). Rejected: replay, model checking. When the rejected choice is right: replay when the verifier must also confirm application invariants a static snapshot cannot show; TLA+ model checking during algorithm design, to explore small state spaces exhaustively (ADR-13).

Roads not taken

Stop-the-world snapshot (Alternative Architectures, ALT-1): a coordinator freezes everyone and collects state, with no markers and no channel recording. It wins for small fixed topologies (n of 8 or fewer) where a pause is acceptable, such as a once-a-minute embedded diagnostic. It is rejected because it violates P2 and its pause grows with process count.

Causal-delivery snapshot (ALT-2): if channels already deliver in causal order, no channel recording is needed. It wins in systems that already run causal broadcast, such as causal key-value stores. It is rejected here because it needs vector clocks on every application message and the project targets plain FIFO, so it would also break P4.

External orchestrator (ALT-3): a separate process pauses, reads and resumes each process over RPC. It wins for legacy systems that cannot join a protocol but expose a management API, and CRIU and VM snapshots work this way. It is rejected for its central point of failure and pauses.

Durable-log epochs (ALT-4): put an epoch record in an append-only log and store offsets. It wins when the system already runs on Kafka-style logs, where checkpoint cost is one offset per channel. It is rejected because it removes the channel-recording problem the project exists to teach.

Lai-Yang for non-FIFO channels: the P1 tradeoff table says it removes the FIFO precondition at the cost of extra state piggybacked on every message; the Deferred Features Register lists it as a later feature (5 to 8 days estimated) and §1.3 gates it on Phase 11. The Deferred Features Register also parks real TCP transport, persistence and recovery (§1.8).

What must never be false

  • I1 consistent cut: every receive in the cut has its send in the cut or in channel state. Noticed by cl-verify comparing vector clocks; counter snapshot_consistency_failures_total (§7).
  • I2 FIFO: per channel, receives follow send order and markers obey it. Noticed by a sequence check on each dequeue (ChannelError::OutOfOrder); channel_ooo_deliveries_total must stay zero outside the negative test (§7).
  • I3 marker-once: a process's local state is written once per snapshot. Noticed by a debug-assert (silent skip plus counter in release); snapshot_local_state_records_total must equal 1 (§7).
  • I4 channel recording: a channel's list is exactly the messages received after the first marker and before that channel's marker. cl-verify cross-checks it against the history; snapshot_channel_msgs_recorded_total (§7).
  • I5 completeness: the snapshot is assembled only when every channel is Done. assemble() returns Err(Incomplete) otherwise; gauge snapshot_processes_complete (§7).
  • I6 conservation: process sums plus channel sums equal the initial amount. check_conservation reports a delta; gauge snapshot_conservation_delta must be 0 (§7).
  • I7 stable-property soundness: a detected stable property holds in every later reachable state. Noticed by the Phase 12 test that runs 100 more steps and expects no new events; false_positive_detections_total should always be 0 (§7).
  • I8 concurrent-snapshot non-interference: one snapshot's record never changes another's. Noticed by the Phase 11 two-snapshot test; diverging completion times in snapshot_completion_time_ms are the warning sign (§7).
  • I9 reproducibility: same seed, topology and logic give identical history, snapshot and verdict. Noticed by running a seed twice and comparing hashes in CI (§7).
  • I10 liveness: under reliable FIFO delivery every started snapshot terminates. Noticed by the Phase 14 liveness test (1000 seeds, up to 16 processes) and the snapshot_termination_steps histogram (§7).
  • I11 completion monotonicity: status only moves forward (NotStarted, Recording, Done) and the pending set only shrinks (P11, §7 summary table). The §7 detail section stops at I10, so the blueprint lists no detection or telemetry row for I11, and P11 itself says "Enforced by I5".
  • I12 verification independence: cl-verify never touches protocol state (P12, §7 summary table). Enforced by the crate dependency graph (P12), with no detection row in §7.

What breaks in production

The blueprint's failure table (Failure Modes & Recovery) names classes but gives them no FM-numbers, so they are cited by name. The design is a single-host simulator (§1.4), so "production" here means a run that goes wrong.

  • FIFO violation. Symptom: fifo_violation_count above zero and cl-verify rejects the cut. Root cause: a cl-transport bug or a test injection. Detection: the sequence-number check in cl-channel on every delivery. Recovery: abort the affected SnapshotId, fix the transport, rerun (T3, I2).
  • Snapshot never completes. Symptom: snapshot_completion_timeout fires and no GlobalSnapshot exists. Root cause: a missing channel, an unreachable process, or a lost message. Detection: a per-SnapshotId watchdog plus a per-process marker-received bitmap. Recovery: none automatic, because completeness is safety-critical; correct the topology and re-initiate (I5, I10, T10).
  • Inconsistent cut. Symptom: cl-verify returns Inconsistent. Root cause: a FIFO violation, a marker-rule bug, or concurrent interference. Detection: the vector-clock check against the event history. Recovery: none automatic; replay the same seed and debug the recording state machine (I1).
  • Conservation violated. Symptom: the token or money sum is off. Root cause: a recording miss, double recording, or an AppState clone taken at the wrong moment. Detection: the cl-detect sum. Recovery: find the process or channel with the wrong count, starting at channel recording (I4, I6).
  • Duplicate recording. Symptom: a process's state recorded twice. Root cause: the first-marker path ran twice (I3). Detection: a dedup check on the status transition and duplicate_marker_count. Recovery: the second call is a no-op with a warning; inspect the transition log (T4).
  • Concurrent snapshot interference. Symptom: one snapshot's channel state holds another's markers. Root cause: a SnapshotId not threaded through the recording state. Detection: a per-SnapshotId isolation check in cl-verify. Recovery: rerun with a single snapshot to find the filtering gap (I8).
  • Stable-property false positive. Symptom: cl-detect reports Terminated or Deadlocked on a running app. Root cause: a stale or inconsistent snapshot. Detection and recovery: cl-verify must pass before cl-detect runs; recapture and re-verify (I7, P8).
  • Scheduler seed not reproducible. Symptom: one seed gives two outputs. Root cause: a non-determinism leak such as OS time or thread scheduling. Detection: run the seed twice and diff. Recovery: audit for hidden sources; the long-term fix is a ban on unseeded randomness or time in cl-sim (I9).

Threats worth knowing (Threat Model): T3 an out-of-order marker from a buggy transport, caught by sequence numbers and the Phase 14 negative test; T4 a duplicate Marker(SnapshotId), handled by a per-(process, SnapshotId, channel) dedup map that makes the second marker a no-op; T5 a colliding SnapshotId; since the id includes the initiator, only a reused seq can collide, and the second initiation is rejected at registry insert; T6 flooding the system with concurrent snapshots, capped by a hard limit on in-flight SnapshotIds (the example cap is 64); T10 a topology missing incoming channels so no snapshot completes, answered by a topology validator and a completion watchdog.

Places where the blueprint's own numbers disagree, left unresolved:

  • §4.1 gives worst-case in-flight memory as ~66 MB from "64 × 4032 × 256 B", while C3 gives ~1.06 GB from the 1,024 queue cap. HQ9 asks the reader to reconcile them.
  • §4.1 says an event is ~128 bytes with its vector clock, and also says a vector clock alone is 512 bytes at n=64; C6 uses 533 bytes per event.
  • C7 estimates cl-verify at ~320 ms for 1 M events and says the 50 ms target needs the log pruned to 50K events (~16 ms). M8 and Phase 10 state "< 50 ms" for a 1,000-event log instead.
  • C2 counts a 17-byte marker, while the §8.3 wire layout also has a 4-byte per-channel seq_no field that C2's byte breakdown leaves out.
  • C8 uses a ring diameter of n/2, while §4.1 bounds marker flood depth at "≤ n for ring".
  • Termination bounds differ: §4.1 says ≤ 2 × diameter steps, I10 says O(diameter × max_channel_depth) and tests n_processes * n_channels * 10, P7 says O(d + max_channel_delay) and tests n_processes * n_channels * max_delay_steps.
  • T1 allows n up to 1,024 and T2 a 64 KB payload with a queue cap of 1 M messages, while §4.1 uses at most 256 processes, 256-byte payloads and a 1,024 cap.

How it compares

  • Apache Flink barriers (Carbone et al. 2015) inject barriers from a central JobManager into a dataflow; aligned barriers make an operator buffer input until all upstream barriers arrive, so they partly block. That is fine for large-state production streaming with exactly-once sinks, where the buffering cost is small beside state serialization (Comparative Architecture).
  • Kafka Streams epoch checkpointing treats durable topic partitions as the channels, so committed offsets mark the channel-state boundary and in-flight messages need no capture. That is fine for Kafka-to-Kafka pipelines where replay from an offset is always available (Comparative Architecture).
  • Spark Streaming RDD checkpointing avoids channel recording by recomputing state from lineage on a driver-set timer. That is fine for micro-batch analytics where state can be re-derived from inputs (Comparative Architecture).
  • Naiad / Timely Dataflow tracks progress with pointstamps, so a checkpoint at a consistent frontier needs no in-flight capture. That is fine for iterative computations where a coarse global snapshot would stall waiting for slow loops (Comparative Architecture).
  • This design is fully decentralized, non-blocking and supports concurrent snapshots, but has no restore path and no exactly-once story, since it is a simulated study (Comparative Architecture, §1.3).

Questions to test yourself

  1. If a process P receives two markers for the same SnapshotId on two different incoming channels simultaneously (in the single-threaded simulator), what is the exact sequence of state transitions in cl-snapshot, and what guarantees that the recorded local state is identical regardless of which marker is processed first? — Hint: the per-channel table in §8.2.1 and the marker-once rule P5.
  2. Describe the exact failure scenario where a correct FIFO channel implementation can still produce an inconsistent cut. (Hint: the bug is not in cl-channel.) Which phase gate catches it, and what does the cl-verify evidence payload report? — Hint: I3's debugging line and the Failure Modes & Recovery row on duplicate recording.
  3. Phase 11 introduces concurrent snapshots. Explain why the existing single-snapshot cl-snapshot implementation produces corrupted cuts when two snapshots run simultaneously, and why the SnapshotId-keyed BTreeMap per process (§8.7) is sufficient — not merely necessary — to prevent interference. — Hint: P10's violation consequence and MM6. (§8.7 itself shows a HashMap; see the ADR-09 note above.)
  4. The Capacity Model (C3) shows worst-case channel-state RAM of ~1 GB for n=64, fully connected, max queue depth 1024, and 256-byte payloads. The §4.1 target says "≤ 66 MB for fully connected n=64." Reconcile these two numbers: under what realistic conditions is the 66 MB figure achievable, and what configuration reduces worst-case to near-typical? — Hint: §4.1's queue cap row, §4.4's assumptions and the C3 and C4 formulas.
  5. A process P is the initiator of snapshot s. After initiating, P sends three application messages on channel c before the marker reaches c's receiver. How many of those three messages appear in GlobalSnapshot.channel_states[c], and what does this mean for the consistency of the cut? Trace through the marker-receiving rule at the receiver. — Hint: the marker-sending rule in §3.2 (cl-snapshot) and the queue order in Phase 6's deliverable.

If you only remember three things

A snapshot is only consistent if every message is either inside a process's recorded state or on a channel's recorded list, and the marker rules plus ordered channels guarantee exactly that (P1, P3, P6). Markers carry no data, so nothing waits and the application never pauses (P2, P4). Verify the cut afterwards with vector clocks, and run everything under a seeded scheduler so any bug is a replayable seed (P12, P9, MM4).

Words used here

  • Snapshot / global state: one process-by-process record of the system plus every message in transit (§1.1).
  • Channel: a one-way, reliable, in-order queue between two processes (§3.2 cl-channel).
  • Marker: a data-free control message that says "snapshot s starts here" on a channel (P4).
  • Initiator: the process that starts a snapshot; any process may (Glossary, "Initiator").
  • Consistent cut: a snapshot boundary with no effect recorded without its cause (MM1, I1).
  • Channel state: the in-flight messages recorded for one channel (P6, I4).
  • FIFO: first sent, first delivered, per channel; the correctness precondition (P3, I2).
  • Vector clock: one counter per process, used to tell "before" from "concurrent" (§8.6).
  • Stable property: a fact that, once true, stays true, like termination or deadlock (P8).
  • Conservation: a quantity such as total tokens or money that the app never changes (I6, §8.14).
  • Wait-for graph: who is blocked on whom; a cycle means deadlock (§8.19, §8.8).
  • SnapshotId: initiator plus sequence number, naming one snapshot instance (§8.1, I8).
  • Seed: the number that fixes the scheduler's choices so a run can be replayed (I9, §8.13).
