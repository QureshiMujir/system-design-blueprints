3.2 Subsystem Descriptions

cl-core — zero-I/O vocabulary crate; the root of the workspace dependency DAG. Defines every shared type: ProcessId(u32), ChannelId{from,to}, SnapshotId{initiator,seq}, Message enum (App(AppPayload) | Marker(SnapshotId)), ProcessState, RecordStatus (NotStarted | Recording | Done), SnapshotState, GlobalSnapshot, Event (Send | Receive | Internal), Cut (per-process frontier), VectorClock (Map<ProcessId,u64>), DeliverySchedule, StableProperty. All other crates import cl-core; cl-core imports nothing from the workspace. A type change in cl-core is a cross-cutting breaking change — treat as a published API boundary.

cl-channel — directed, reliable, FIFO message queue between exactly two processes. Internal state: a VecDeque<Message> preserving send order. Interface: enqueue(msg) on send side; dequeue() -> Option<Message> on receive side; drain_recorded() -> Vec<AppPayload> for snapshot channel-state extraction. The FIFO invariant (I2) is the structural precondition for Chandy-Lamport correctness: a marker must not arrive before messages sent before it on the same channel. cl-channel enforces this by construction — order is determined by insertion order in the deque. No concurrency internally; cl-sim drives all dequeue calls.

cl-process — models one logical process: holds AppState (application-defined), a map of outgoing ChannelIds to cl-channel references, a map of incoming ChannelIds, and a per-snapshot HashMap<SnapshotId, ProcessState>. Exposes: send(channel_id, msg) (enqueues into the channel, logs a Send event), on_receive(channel_id, msg, handler) (dispatches to the AppHandler trait, logs a Receive event), internal_transition(handler) (application step, logs Internal event). Snapshot logic is injected by cl-snapshot calling into the process; the process does not implement the protocol itself. Application logic is provided by an AppHandler trait impl (supplied by cl-app). Process boundaries are the trust boundary: no process reads another's AppState directly.

cl-transport — passive registry that maps ChannelId to a (sender-process, receiver-process, channel) triple. Used by cl-process.send to locate the channel and by cl-sim.deliver to route a dequeued message to the receiving process. In the simulated backend, cl-transport holds no message buffers; messages reside in cl-channel's deque. Interface: register(channel_id, sender, receiver), send(channel_id, msg) (delegates to cl-channel.enqueue), deliver(channel_id) -> Option<DeliveryToken> (dequeues one message, returns a token cl-sim uses to call cl-process.on_receive). No persistence; no acknowledgement; no retransmit.

cl-app — two concrete distributed computations implementing the AppHandler trait: (1) TokenRingApp — a fixed number of tokens circulate around a ring; total tokens across all processes plus all channels is the conservation invariant; (2) BankTransferApp — processes send money amounts on channels; total money across all process balances plus all in-flight transfers is conserved. Both apps provide an invariant_value(state: &AppState) -> u64 method that cl-detect uses for conservation checking (I6). Data flow: cl-app state is embedded in AppState; cl-process snapshots it as part of SnapshotState at first-marker time; cl-detect sums all process and channel contributions.

cl-sim — seeded deterministic scheduler. Maintains a pending-delivery set: for each channel with non-empty queue, the next deliverable (channel_id, head_index) pair. Each step: apply a deterministic selection function (seeded PRNG or round-robin) to choose a channel; call transport.deliver(channel_id); append the resulting Event (with updated VectorClock) to the EventLog. Reproducibility invariant (I9): same seed → same event sequence → same snapshot state → same verifier verdict. cl-sim serializes all process steps: no real parallelism; all interleaving is under cl-sim's control. cl-sim also supports: inject_snapshot_initiation(pid, snapshot_id, step) to trigger a snapshot at a scheduled step; violate_fifo_at(channel_id, step) for the Phase 14 negative test (reorders two adjacent messages on a channel). cl-sim must not depend on cl-snapshot (avoids coupling scheduling to protocol).

cl-snapshot — implements the Chandy-Lamport protocol as rule applications invoked by cl-process's message dispatch and by an external initiation call. Manages a HashMap<(ProcessId, SnapshotId), PerProcessSnapshotState> where PerProcessSnapshotState contains: local_state_recorded: bool, channel_status: HashMap<ChannelId, RecordStatus>, recorded_msgs: HashMap<ChannelId, Vec<AppPayload>>. Rules: (a) initiate(pid, snapshot_id, process) — if not already started, record process local state, set all incoming channels to NotStarted, set all outgoing channels to Recording, send Marker(snapshot_id) on all outgoing channels before any further app message; (b) on_marker(pid, snapshot_id, from_channel, process, recorder) — if first marker for this snapshot: record local state, mark from_channel Done (empty), set all other incoming channels to Recording, send Marker on all outgoing; else: stop recording from_channel (Done), move its recorded list to SnapshotState; call recorder.maybe_complete(pid, snapshot_id). This is the most semantics-dense crate; the state machine is the core contribution.

cl-recorder — collects SnapshotState contributions from processes as they finish (receive marker on every incoming channel). Holds a HashMap<SnapshotId, SnapshotAccumulator> where SnapshotAccumulator tracks: which processes have submitted, the assembled GlobalSnapshot under construction. Interface: submit(snapshot_id, pid, state: SnapshotState) — adds process's local state + recorded channel messages; is_complete(snapshot_id) -> bool — all P processes have submitted and all C channels have RecordStatus::Done; assemble(snapshot_id) -> GlobalSnapshot — final immutable snapshot. Completion detection is O(P*C) check; acceptable at simulation scale. Concurrency: protected by a Mutex in multi-snapshot scenarios (Phase 11).

cl-verify — takes a completed GlobalSnapshot and the VectorClock-annotated EventLog from cl-sim and mechanically checks the consistent-cut invariant (I1). Algorithm: (a) reconstruct the Cut — per-process event-count at the time of each process's first-marker recording; (b) for every Receive event in the cut, find the matching Send event using Message identity; (c) assert the Send event is also in the cut (its VectorClock ≤ the Cut frontier at the sender) OR the message appears in the snapshot's channel-state list; (d) assert no message sent after the cut (sender's clock > cut frontier) appears in any process's received set before the cut. Returns VerifyResult::Consistent or VerifyResult::Violated { evidence: Vec<CausalViolation> }. The verifier is the mechanized proof; it must pass on all valid runs and must return Violated on FIFO-violation injections.

cl-detect — evaluates stable properties over a completed GlobalSnapshot without re-running the simulation. Three detectors: (a) Termination — all process AppStates report idle (via AppHandler::is_idle) AND all channel states are empty Vec; (b) Deadlock — construct WaitForGraph from AppStates (via AppHandler::wait_for edges); run DFS cycle detection; return the cycle if found; (c) Conservation — for each conserved quantity (tokens, money), sum AppHandler::invariant_value over all process states plus sum AppPayload values over all channel states; compare to initial value; report delta if non-zero. Returns Vec<StablePropertyResult>. The soundness argument (P8, I7): stable properties are monotone — once true, remain true; a consistent snapshot (I1) captures a reachable state; therefore a stable property true in the snapshot is true in the current execution.

cl-cli — top-level entry point. Parses arguments: --processes N, --topology [ring|full|custom], --app [token-ring|bank-transfer], --seed U64, --initiate PID@STEP, --output [text|json]. Subcommands: run (execute simulation, print event log), snapshot (run + trigger snapshot + print GlobalSnapshot), detect (snapshot + run cl-detect, print StablePropertyResult), verify (snapshot + run cl-verify, print VerifyResult + evidence). No business logic in cl-cli; all calls delegate to the other crates. Depends on all 10 other crates.

8.2 Process State Machine

Each process P, per snapshot s, tracks RecordStatus for every incoming channel.

Show the original text diagram
State labels: NS=NotStarted, REC=Recording, DONE=Done
Transitions per channel c ∈ incoming(P):

  GLOBAL process-recording phase for (P, s):
    IDLE ──[first Marker(s) on any c']──> ACTIVE
    ACTIVE ──[Marker(s) on c]──> DONE_c   (channel c finishes)
    ACTIVE ──[App msg on c while REC]──> ACTIVE (enqueue to channel_msgs[c])
    DONE_all_channels ──> SNAPSHOT_COMPLETE(P, s)

Per-channel RecordStatus state machine:
  NS ──[first Marker(s) received by P on any channel]──> REC (start recording c unless c was marker channel)
  NS ──[Marker(s) arrives on THIS channel AND it is the first marker]──> DONE (channel c is empty: no in-flight)
  REC ──[App msg received on c]──> REC (append msg to SnapshotState.channel_msgs[c])
  REC ──[Marker(s) arrives on c]──> DONE
  DONE ──[]──> DONE (terminal; no messages from c accepted into recording)

8.2.1 Full per-process phase table

Trigger Pre-condition Action Post-state
initiate(P, s) P is initiator Record local_state; send Marker(s) on all outgoing channels All incoming channels: NS→REC (none have arrived yet)
Receive(Marker(s), c) — first for s P has no entry for s Record local_state; set channel_msgs[c]=[]; set RecordStatus[c]=DONE; set all other incoming RecordStatus=REC; send Marker(s) on all outgoing P enters ACTIVE
Receive(App(m), c) RecordStatus[c]==REC Append m to SnapshotState.channel_msgs[c] ACTIVE (unchanged)
Receive(App(m), c) RecordStatus[c]==DONE Deliver to app only; not recorded ACTIVE or COMPLETE
Receive(App(m), c) RecordStatus[c]==NS Deliver to app only IDLE
Receive(Marker(s), c) — subsequent RecordStatus[c]==REC Set RecordStatus[c]=DONE ACTIVE or COMPLETE if all channels DONE
All channels DONE All RecordStatus==DONE Notify cl-recorder; snapshot complete for P COMPLETE

8.3 Message Grammar (EBNF)

channel-stream  ::= message*
message         ::= app-message | marker-message
app-message     ::= APP_TAG payload-bytes
marker-message  ::= MARKER_TAG snapshot-id
snapshot-id     ::= uint32 uint64       (* initiator.id, seq *)
payload-bytes   ::= length-prefixed-bytes
APP_TAG         ::= 0x01
MARKER_TAG      ::= 0x02

Wire layout (little-endian, fixed header):

Bytes  0     : tag (u8)         — 0x01=App, 0x02=Marker
Bytes  1–4   : sender ProcessId (u32)
Bytes  5–8   : seq_no (u32)     — per-channel monotone send counter (FIFO proof)
--- App message ---
Bytes  9–12  : payload_len (u32)
Bytes 13..   : payload (opaque)
--- Marker message ---
Bytes  9–12  : initiator ProcessId (u32)
Bytes 13–20  : snapshot seq (u64)

FIFO invariant (I2): seq_no must be exactly prev_seq_no + 1 on delivery; out-of-order detected and rejected.

8.4 Channel Model

Channel(c: ChannelId):
  queue: VecDeque<(seq_no: u32, msg: Message)>  — ordered, reliable
  next_send: u32                                 — monotone counter
  next_recv: u32                                 — expected seq_no

send(m):    enqueue (next_send++, m)
deliver():  pop front if non-empty; assert seq_no == next_recv++

Invariant I2 enforcement: if delivered seq_no != next_recv, channel is corrupt — panic in simulator, emit error in real transport.

8.5 Snapshot Assembly Model

GlobalSnapshot:
  snapshot_id   : SnapshotId
  process_states: BTreeMap<ProcessId, AppState>        — state at first marker per process
  channel_states: BTreeMap<ChannelId, Vec<AppPayload>> — in-flight pre-snapshot messages
  completed_at  : EventIndex                           — simulator time when last process finished

Assembly sequence:
  1. Each process P contributes: (P, SnapshotState.local_state_at_first_marker)
  2. Each channel c contributes: (c, SnapshotState.channel_msgs[c])
  3. Recorder waits for all |processes| completion events before sealing GlobalSnapshot
  4. Sealed snapshot is immutable; hash-stamped for integrity

8.6 Vector Clock Attachment and Cut Derivation

Each Event carries a VectorClock snapshot at time of occurrence:

Event { kind: EventKind, vc: VectorClock, process: ProcessId, channel: Option<ChannelId> }
EventKind ::= Send(ChannelId, Message) | Receive(ChannelId, Message) | Internal

Cut derivation from event history:

Cut[P] = index of last event included in snapshot for process P
       = index of the FIRST marker receipt event for P (for snapshot s)

Cut consistency predicate (I1):

∀ Receive(c, m) ∈ cut:  ∃ Send(c, m) ∈ cut  OR  m ∈ channel_states[c]
∀ Send(c, m) ∉ cut AND Send(c, m) happened-before cut[receiver]:  m ∈ channel_states[c]

VectorClock happened-before: vc_a < vc_b iff ∀p: vc_a[p] <= vc_b[p] and ∃p: vc_a[p] < vc_b[p].

8.7 Concurrent Snapshot Isolation

Per-process runtime recording map keyed by SnapshotId:

ProcessState.recordings: HashMap<SnapshotId, PerSnapshotRecord>
PerSnapshotRecord:
  local_state     : AppState                          — captured at first marker
  channel_status  : HashMap<ChannelId, RecordStatus>
  channel_msgs    : HashMap<ChannelId, Vec<AppPayload>>

Isolation invariant (I8): operations on recordings[s1] never access recordings[s2] for s1 ≠ s2. Markers carry their SnapshotId; dispatch is keyed strictly by id.

8.8 Stable-Property Detection Model

Property Snapshot predicate Detection logic
Terminated All processes idle AND all channel states empty ∀P: state[P].idle == true AND ∀c: channel_states[c].is_empty()
Deadlocked Wait-for cycle in snapshot Build wait-for graph from process_states; DFS cycle detect
Conserved(f) f(process_states, channel_states) == initial_value Sum tokens/money across all states + in-flight msgs

Stable-property soundness (I7): property true in consistent snapshot remains true in real execution — because the snapshot is reachable and the property is monotone-true.

8.9 Event History and Trace Layout

Trace file format (binary, append-only, per-run):

TraceHeader: magic(4B) | version(u8) | process_count(u32) | seed(u64)
TraceRecord: timestamp(u64) | process_id(u32) | event_tag(u8) | vc_bytes(variable) | payload(variable)
event_tag: 0x10=Send, 0x11=Receive, 0x12=Internal, 0x20=MarkerSend, 0x21=MarkerReceive,

8.10 Worked Example — Correct Snapshot

Show the original text diagram
Topology: P0 → P1 → P2 → P0 (ring); 1 token starts at P0

Initial states: P0={token=1}, P1={token=0}, P2={token=0}
Channels: c01=(P0→P1), c12=(P1→P2), c20=(P2→P0); all empty

Step 1: P0 sends token to P1 via c01: App(token) enqueued on c01
Step 2: P0 initiates snapshot s0 = {initiator=P0, seq=0}
        → P0 records local_state={token=0} (already sent token)
        → P0 sends Marker(s0) on all outgoing: c01 (after the token)
Step 3: c01 delivers App(token) to P1 first (FIFO): P1.token=1
        c01 delivers Marker(s0) to P1:
        → First marker for P1: record local_state={token=1}
        → channel c01 was marker channel: RecordStatus[c01]=DONE, msgs=[]
        → Start recording c20 (only other incoming): RecordStatus[c20]=REC
        → P1 sends Marker(s0) on c12
Step 4: c12 delivers Marker(s0) to P2:
        → First marker for P2: record local_state={token=0}
        → RecordStatus[c12]=DONE, msgs=[]
        → Start recording c01 (P2 has no other incoming in this ring; actually c01 not incoming to P2)
        → P2 sends Marker(s0) on c20
Step 5: c20 delivers Marker(s0) to P0:
        → RecordStatus[c20] at P0: P0 is initiator, was already in ACTIVE with all outgoing sent
        → P0 marks RecordStatus[c20]=DONE; all channels DONE → P0 complete
Step 6: c20 delivers Marker(s0) to P1 (P1 was recording c20):
        → RecordStatus[c20]=DONE; all channels DONE → P1 complete
        → channel_msgs[c20]=[] (no app msgs arrived on c20 during recording window)

GlobalSnapshot s0:
  process_states: {P0: {token=0}, P1: {token=1}, P2: {token=0}}
  channel_states: {c01: [], c12: [], c20: []}
  total tokens = 0+1+0 + 0+0+0 = 1 ✓ conservation holds
  consistency: token was in-flight on c01 before snapshot; but P1 recorded its state AFTER receiving it
               → token appears in P1.local_state, not in channel_states → cut is consistent (I1 satisfied)

8.11 Failure-Path Example — FIFO Violation

Show the original text diagram
Suppose channel c01 delivers Marker(s0) BEFORE the App(token) it preceded (FIFO broken):

Step A: c01 delivers Marker(s0) to P1 first (out of order)
        → P1 records local_state={token=0} (token not yet arrived)
        → RecordStatus[c01]=DONE; channel_msgs[c01]=[]
Step B: c01 delivers App(token) to P1: P1.token=1 (after snapshot recorded)
        → not in recording window (c01 is DONE); not in channel_states

Result in GlobalSnapshot s0:
  process_states: {P0: {token=0}, P1: {token=0}, P2: {token=0}}
  channel_states: all empty
  total tokens = 0 ≠ 1  → conservation violated; snapshot is NOT consistent

cl-verify detects: a Send(c01, App(token)) appears before P0's cut index,
  but Receive(c01, App(token)) appears after P1's cut index,
  and App(token) is absent from channel_states[c01] → I1 violated.
cl-verify emits: CutInconsistency { channel: c01, missing_msg: token }

This is the Phase 14 negative test: FIFO-violation mode in cl-sim triggers exactly this path.

8.12 Edge Cases

Edge case Description Expected behavior
Initiator receives its own marker via loopback Ring topology: P0 sends marker on c_N0; receives it from c_N0 Treat as a subsequent-marker event; RecordStatus[c_N0]=DONE; msgs recorded in window
Process with no incoming channels Source node; never receives a marker Snapshot complete immediately after initiation (zero channels to record)
Process with no outgoing channels Sink node; receives markers; never sends Correctly receives all markers; sends no outgoing markers; finishes when all incoming DONE
Empty channel at snapshot No messages in flight on c at snapshot time channel_states[c] = [] (valid, not error)
Concurrent snapshots, overlapping marker windows P mid-recording s1 when s2 marker arrives Dispatch by SnapshotId; s1 and s2 recording maps are independent (I8)
Very late initiator Snapshot s initiated after most messages already delivered Small or empty channel states; valid consistent cut
Duplicate marker delivery Same (SnapshotId, channel) marker delivered twice (transport bug) seq_no check catches duplicate; discard; log error
Zero-process system n=0 GlobalSnapshot trivially complete; empty maps; no error
Single-process system n=1, no channels Snapshot = just local_state; channel_states={}; trivially consistent
Snapshot initiated simultaneously by two processes s_A={P0,1} and s_B={P1,1} both start concurrently Two independent recordings; both complete; both consistent (I8, I10)

8.13 Scheduling Semantics (cl-sim)

DeliverySchedule: Vec<(ChannelId, send_index: u32)>
  — generated from seed via seeded PRNG (ChaCha8Rng)
  — each step: select a non-empty channel uniformly at random (weighted or unweighted)
  — deliver its head message (FIFO respected: always head of queue)
  — interleaved with process internal steps and snapshot initiations
  — snapshot initiation injected at configurable step offsets (or random from seed)
  — event log records chosen steps for full reproducibility (I9)

Invariant: scheduler never skips past a channel's head (FIFO preserved by construction).

8.14 AppState and Conservation Invariant

AppState (token ring):    { tokens: u32 }
AppState (bank transfer): { balance: i64 }

Conservation check:
  token ring:    Σ process_states[P].tokens + Σ |channel_states[c]| * token_value == N_tokens_initial
  bank transfer: Σ process_states[P].balance + Σ channel_states[c].iter().sum() == total_initial

cl-detect evaluates this over GlobalSnapshot without re-running any process logic.

8.19 Wait-For Graph Model (Deadlock Detection)

WaitForGraph:
  Nodes: ProcessId ∈ GlobalSnapshot.process_states
  Edges: (Pi, Pj) iff state[Pi].waiting_for == Some(Pj) (blocked on message from Pj)
  Cycle: Pi → Pj → Pk → Pi  ⟹ deadlock detected (I7: stable if cut is consistent)

Derived from process_states:
  Each AppState exposes: fn blocked_waiting_for(&self) -> Option<ProcessId>
  cl-detect builds adjacency list; runs DFS; collects back-edges as deadlock cycles
  Outputs: DeadlockReport { cycles: Vec<Vec<ProcessId>> }

8.21 Transport Delivery Semantics

cl-transport delivery contract (simulated mode):
  1. Scheduler calls: transport.deliver_next(channel_id) -> Option<Message>
  2. Transport pops head of channel_id.queue (FIFO)
  3. Calls target_process.on_receive(channel_id, message)
  4. on_receive dispatches:
       Message::App(p)    -> app_handler(p); Event::Receive logged
       Message::Marker(s) -> cl-snapshot.handle_marker(process, s, channel_id)
  5. All side effects (state mutations, marker sends) complete before scheduler
     selects the next delivery step (single-threaded sim: no interleaving within a step)

Real transport (cl-transport network backend, future):
  - TCP streams per channel; seq_no header enforces FIFO at receiver
  - Out-of-order: buffer and re-order up to MAX_REORDER_BUFFER (default 64 msgs)
  - Loss: not modelled (reliable delivery is a precondition of Chandy-Lamport; P3/P7)

8.22 Snapshot Completion Detection

completion_detector for snapshot s:
  pending: BTreeSet<ProcessId>  — initialized to all processes at initiation
  on process P signals COMPLETE for s:
    pending.remove(P)
    if pending.is_empty():
      recorder.assemble_and_seal(s)
      emit Event { tag: SnapshotComplete, snapshot_id: s }

Invariant I5: recorder.assemble_and_seal called exactly once per s.
Race-free in simulator: single-threaded; in multi-threaded transport, guarded by Mutex<CompletionDetector>.
