4.2 Failure Budget and Recovery Behavior

Failure class Budget / enforced behavior
Inconsistent cut detected by cl-verify Hard error: simulation halts; seed + event log + violated events printed for reproduction; CI test fails
Conservation violation detected by cl-detect Hard error: token/money delta and offending process/channel states reported; CI test fails
Channel queue overflow (> 1024 messages) panic! in debug builds; configurable: drop-with-log or error-return in release
Snapshot non-termination cl-sim step budget: max 10 M steps per run; exceeded → error with seed + completion status
FIFO-violation negative test (intentional injection) cl-verify must return Violated; test fails if it returns Consistent (false negative)
Concurrent snapshot interference (I8 violation) Phase 11 property test: any cross-SnapshotId state contamination = test failure with seed
Seed non-reproducibility Phase 14: run same seed twice; diff event histories must be empty bytes
Marker-once violation (I3: second recording attempt) cl-snapshot must return error or no-op; test asserts local state is recorded only once per (pid, snapshot_id)
Recorder double-submit (same pid, same snapshot_id) cl-recorder returns Err(DuplicateSubmit); test asserts accumulator state unchanged

4.8 Error Handling Philosophy

Layer Error handling strategy
cl-core No fallible operations; all types are value types
cl-channel dequeue returns Option<Message>; empty queue is not an error
cl-process send returns Result<(), ChannelError>; channel not found = hard error
cl-snapshot initiate returns Result<(), SnapshotError::AlreadyStarted>; on_marker returns Result<RecordStatus, ...>
cl-recorder submit returns Result<(), RecorderError::DuplicateSubmit | UnknownSnapshot>
cl-verify Returns VerifyResult; never panics; evidence collected exhaustively
cl-detect Returns Vec<StablePropertyResult>; never panics; partial results on incomplete snapshot input
cl-sim Step-budget exceeded → Err(SimError::StepBudgetExceeded { seed, step }); FIFO violation (intentional) → logged event
cl-cli Maps all internal errors to non-zero exit codes; human-readable or JSON error output

Back-of-Envelope Capacity Model

All numbers derived step-by-step from the System Constraints table (§4.1). Formula shown for each.

C1 — Total directed channels for fully-connected topology:

Formula: channels = n × (n − 1)
n = 64 processes → channels = 64 × 63 = 4,032
n = 256 processes → channels = 256 × 255 = 65,280

C2 — Marker control overhead per snapshot (fully connected, n=64):

Formula: marker_msgs = channels = n × (n − 1)
Each Marker message: 1 byte tag + 4 bytes sender + 8 bytes SnapshotId seq + 4 bytes initiator = 17 bytes wire size
Total marker bytes: 4,032 × 17 = ~68 KB per snapshot
At 100 snapshots/s: 6.8 MB/s control traffic — negligible vs. any modern network

C3 — In-flight message RAM at snapshot time (worst case, n=64 fully connected):

Formula: channel_state_RAM = channels × queue_depth_cap × msg_size
channels = 4,032; queue_depth_cap = 1,024; msg_size = 256 bytes (max, §4.1)
worst case: 4,032 × 1,024 × 256 = ~1.06 GB

C4 — Typical GlobalSnapshot RAM (ring topology, n=64, 8-byte payloads):

Formula: snapshot_RAM = n × process_state_size + channels × avg_inflight × msg_size
Ring: channels = n = 64; avg_inflight = 1 token; msg_size = 8 bytes; process_state_size = 64 bytes
snapshot_RAM = 64 × 64 + 64 × 1 × 8 = 4,096 + 512 = ~4.6 KB per snapshot (trivial)

C5 — VectorClock size per event (n=64):

Formula: vc_bytes = n × 8 bytes (one u64 per process)
n = 64 → vc_bytes = 512 bytes per event
n = 256 → vc_bytes = 2,048 bytes per event

C6 — Event log RAM for 1M events (n=64):

Formula: log_RAM = events × (vc_bytes + event_overhead)
event_overhead = 1 byte tag + 4 bytes process_id + 8 bytes channel_id + 8 bytes seq = ~21 bytes
total per event: 512 + 21 = 533 bytes
1M events × 533 bytes = ~533 MB  → prune event log aggressively; target ≤ 256 MB with delta encoding

C7 — cl-verify runtime estimate (1M events, 64 channels, 1,024 in-flight per channel):

Formula: verify_ops = E × n + C × M   (VectorClock comparison per event + channel-state scan)
E = 1M; n = 64; C = 64; M = 1,024
verify_ops = 1M × 64 + 64 × 1,024 = 64M + 65K ≈ 64M comparisons
At ~200M u64 comparisons/s per core: 64M / 200M = ~320 ms (§4.1 target ≤ 50 ms requires pruning)
With event-log pruning to 50K active events: 50K × 64 = 3.2M ops → ~16 ms ✓

C8 — Marker flood steps to completion (ring, n=64):

Formula: flood_steps = diameter × avg_channel_depth_in_steps
Ring diameter = n/2 = 32 hops; each hop = 1 delivery step
flood_steps ≈ 32 steps (ideal); at 500K steps/s → 64 µs to complete snapshot flood ✓

C9 — cl-detect deadlock (wait-for graph DFS, n=256):

Formula: dfs_ops = O(P + W) where W = wait-for edges ≤ P = 256
ops ≤ 512; at 100M ops/s → < 1 µs  (§4.1 target ≤ 10 ms: comfortable margin)

C10 — Concurrent snapshot memory overhead (n=64, s=4 simultaneous snapshots):

Formula: concurrent_state_RAM = s × n × in_degree × RecordStatus_size
in_degree = n-1 = 63 (fully connected); RecordStatus size = 32 bytes (enum + Vec pointer)
concurrent_state_RAM = 4 × 64 × 63 × 32 = ~516 KB  (per §4.1 target: acceptable)

C11 — Binary startup time estimate:

Formula: startup_time = heap_init + topology_setup + cli_parse
heap_init: ~1 ms for 64 Arc<Mutex<FifoChannel>> allocations
topology_setup: n × n channel registrations at O(1) HashMap inserts = ~0.1 ms for n=64
cli_parse: clap overhead ~2 ms
Total: ~3 ms → well within §4.1 target of ≤ 50 ms ✓

C12 — File descriptor budget:

Formula: FDs = stdout(1) + stderr(1) + log_file(1) + trace_file(2: trace.bin + trace.idx) = 5
No sockets; no mmap; budget = 5 FDs well within §4.1 limit of 10 ✓
