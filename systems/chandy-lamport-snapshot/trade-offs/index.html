Decisions (§9) · 28 ADRs

ADR-01

Implementation language

Chosen

Rust (stable, 2021 edition)

Rejected

Go, C++, Java, Python

When the rejected choice is right

Go wins for rapid prototyping and team familiarity when algorithm correctness is secondary to deployment speed; Java wins in large enterprise shops where JVM expertise dominates and GC pauses are acceptable

Why: Memory safety without GC; explicit ownership maps to FIFO queue invariants; no data-race UB; ecosystem for deterministic testing

ADR-02

Build system

Chosen

Cargo workspace (Cargo.toml at root, 11 member crates)

Rejected

Bazel, Buck2, Make

When the rejected choice is right

Bazel wins in polyglot monorepos with Java/Python/Go co-located with Rust, where remote caching and cross-language dependency graphs matter; Buck2 wins when Meta-style build hermeticity is a hard requirement

Why: Native Rust; workspace unifies lockfile; per-crate isolation matches architectural boundaries

ADR-03

Dependency policy

Chosen

Minimal: serde, bincode/postcard, rand/rand_chacha, clap, tracing, criterion; no async runtime in core crates

Rejected

tokio, async-std, heavy framework deps

When the rejected choice is right

Tokio wins the moment cl-transport evolves to real TCP: async I/O eliminates per-connection thread overhead and enables thousands of simulated nodes on one host without OS-thread exhaustion

Why: Core algorithm is synchronous and deterministic; async adds non-determinism; test surface stays small

ADR-04

Async/concurrency model

Chosen

Single-threaded deterministic simulation in cl-sim; optional multi-thread in cl-transport with std::sync::Mutex-guarded queues

Rejected

tokio async, rayon

When the rejected choice is right

Tokio async wins when cl-transport runs over real networks: event-driven I/O multiplexing outperforms thread-per-channel at n > 100 real processes; Rayon wins for CPU-bound parallel verification of independent snapshots

Why: Chandy-Lamport correctness testing requires controlled interleavings; async scheduler would hide race conditions from tests

ADR-05

Serialization (wire + trace)

Chosen

postcard (no-std compatible, compact binary, serde-derived) for wire; bincode for trace files

Rejected

JSON, protobuf, MessagePack, capnproto

When the rejected choice is right

Protobuf wins when cross-language consumers exist (Python analysis scripts, Go dashboard); capnproto wins for zero-copy deserialization of very large GlobalSnapshot payloads at n > 1000 processes

Why: postcard: minimal overhead, no schema registry; bincode: fast append-only trace; both serde-derived so no separate schema maintenance

ADR-06

Trace/event storage

Chosen

Append-only binary file trace.bin + index trace.idx; one per run

Rejected

SQLite, Parquet, in-memory only

When the rejected choice is right

SQLite wins when trace-level queries (e.g., "find all markers for SnapshotId X across processes") become a development workflow; Parquet wins for offline analytics over millions of events with columnar aggregation

Why: O(1) random access via index for verifier; append-only avoids corruption on partial runs; human-readable JSON export optional

ADR-07

Deterministic RNG

Chosen

rand_chacha::ChaCha8Rng seeded from CLI --seed u64

Rejected

SmallRng, StdRng, OS entropy

When the rejected choice is right

OS entropy (getrandom) wins in production real-transport scenarios where an attacker must not predict delivery ordering; SmallRng wins when memory footprint on embedded targets is a hard constraint

Why: ChaCha8: reproducible across platforms, seed-exportable, cryptographically independent streams per scheduler component (I9)

ADR-08

Channel FIFO implementation

Chosen

std::collections::VecDeque<(u32, Message)> with monotone seq_no

Rejected

ring buffer, lock-free queue

When the rejected choice is right

Lock-free queue (e.g., crossbeam-queue::ArrayQueue) wins when cl-transport runs on real OS threads and lock contention on Mutex<VecDeque> becomes measurable under high message throughput (> 1 M msg/s per channel)

Why: VecDeque: O(1) push/pop; seq_no enables explicit FIFO-violation injection for negative tests (Phase 14)

ADR-09

SnapshotId keying

Chosen

HashMap<SnapshotId, PerSnapshotRecord> per process

Rejected

single global recording state

When the rejected choice is right

Single global state wins when only one snapshot at a time is ever needed (simpler protocol for termination detection only) and memory overhead from per-SnapshotId maps matters on resource-constrained nodes

Why: Supports concurrent snapshots (P10); isolation by key enforces I8; negligible overhead for typical concurrency level

ADR-10

Vector clock storage

Chosen

BTreeMap<ProcessId, u64> (sorted for deterministic serialization)

Rejected

array indexed by ProcessId, HashMap

When the rejected choice is right

Fixed-size array [u64; MAX_PROCS] wins when n is known at compile time and O(1) indexed access and minimal heap allocation outweigh the serialization-order flexibility of BTreeMap (e.g., embedded systems with n ≤ 32 fixed)

Why: BTreeMap: deterministic iteration order → consistent serialization → stable test snapshots; small n makes BTreeMap overhead negligible

ADR-11

GlobalSnapshot assembly

Chosen

Blocking collection: recorder waits for all `

Rejected

processes

When the rejected choice is right

distributed two-phase commit, gossip

Why: ` completion events, then seals

ADR-12

Stable-property detection algorithm

Chosen

DFS cycle detection (wait-for graph) for deadlock; sum-check for conservation; idle-and-empty for termination

Rejected

Dijkstra–Scholten, token-based

When the rejected choice is right

Dijkstra–Scholten wins for diffusing-computation termination in real distributed systems where taking a full snapshot is too expensive; token-based termination wins in systems with very high event rates where post-hoc analysis latency is unacceptable

Why: Snapshot-based detection is O(n+e) post-hoc; no algorithm interference with running computation; simpler than online detectors

ADR-13

Consistency verification strategy

Chosen

Causal check: for each Receive in cut, assert Send in cut or in channel_states; vector-clock cross-check

Rejected

Replay, model checking

When the rejected choice is right

Replay wins when the verifier must also confirm application-level invariants that cannot be extracted from a static GlobalSnapshot alone; TLA+ model checking wins during algorithm design to exhaustively explore small state spaces

Why: Post-hoc over event log + VectorClocks; no re-execution needed; linear in event count; deterministic outcome (I1)

ADR-14

Logging

Chosen

tracing crate with tracing-subscriber (structured JSON output)

Rejected

log crate, println!

When the rejected choice is right

The log crate wins for library crates that must remain compatible with consumers using non-tracing logging frameworks; structured stdout wins for embedded or constrained targets where tracing-subscriber's overhead is prohibitive

Why: Structured spans per phase/process; filterable by SnapshotId or ProcessId; compatible with tracing-test for test assertions

ADR-15

Metrics

Chosen

metrics crate (facade) with in-process recorder for tests; optional Prometheus exporter for cl-cli

Rejected

OpenTelemetry SDK, statsd

When the rejected choice is right

OpenTelemetry SDK wins when the deployment already runs an OTel collector and traces + metrics must correlate via context propagation; statsd wins in legacy infrastructure already instrumented with Graphite/statsd pipelines

Why: Facade pattern: core crates emit metrics without depending on an exporter; test harness captures metrics without network

ADR-16

Unit testing

Chosen

cargo test; each crate's tests/ directory; property-based tests via proptest

Rejected

QuickCheck, custom harness

When the rejected choice is right

QuickCheck wins for simpler projects where proptest's strategy DSL is overkill; a custom harness wins when test fixtures must be generated from a formal spec (e.g., TLA+ counterexamples exported to Rust test cases)

Why: proptest generates diverse AppPayloads, schedules, and process counts; proptest integrates with Cargo natively

ADR-17

Fuzz testing

Chosen

cargo-fuzz (libFuzzer) targeting cl-channel, cl-snapshot marker dispatch, cl-verify

Rejected

AFL++, honggfuzz

When the rejected choice is right

AFL++ wins when corpus sharing across multiple fuzzer instances on a cluster is needed; honggfuzz wins for hardware-performance-counter guided fuzzing on Linux x86 for coverage-dense code

Why: cargo-fuzz is idiomatic Rust; targets: malformed wire bytes, out-of-order seq_no, duplicate markers

ADR-18

Integration / conformance testing

Chosen

Golden-file tests: fixed seed → serialized GlobalSnapshot JSON diffed against committed expected output

Rejected

random oracle, differential

When the rejected choice is right

Differential testing against a reference implementation wins when there is an independent correct implementation to compare against (e.g., a verified Coq/TLA+ model); random oracle wins when a ground-truth specification exists but no second implementation

Why: Reproducibility (I9) makes golden files exact; seed-locked conformance suite in tests/conformance/

ADR-19

Benchmarking

Chosen

criterion microbenchmarks in benches/; wall-time for: per-message deliver, full-ring snapshot at n=8/32/128

Rejected

custom timers, perf, hyperfine

When the rejected choice is right

perf + flamegraph wins for identifying root-cause bottlenecks at the CPU instruction level; hyperfine wins for end-to-end CLI latency comparisons that span process startup time

Why: Criterion: stable statistical estimates; HTML reports; CI regression gate via cargo bench --message-format=json

ADR-20

CI/CD

Chosen

GitHub Actions: cargo fmt --check, cargo clippy -- -D warnings, cargo test, cargo bench (regression check), cargo fuzz (10s smoke), cargo audit

Rejected

Jenkins, CircleCI, Buildkite

When the rejected choice is right

Jenkins wins in enterprises with on-prem artifact registries, LDAP auth gates, and compliance-audited pipelines that GitHub Actions cannot satisfy; Buildkite wins for large monorepos needing agent-level parallelism and custom hardware

Why: Standard Rust CI idioms; cargo audit catches supply-chain issues; fuzz smoke in CI catches quick regressions

ADR-21

Packaging / distribution

Chosen

Cargo workspace; cargo install from source; no Docker required for core; optional Dockerfile for cl-cli demo

Rejected

pre-built binaries, npm wrapper

When the rejected choice is right

Pre-built binaries win when the target audience includes systems engineers who do not have Rust installed; Docker wins for regulated environments where supply-chain verification requires image signing and SBOM attestation

Why: Pure Rust; no runtime deps; source install is idiomatic; Docker for demo keeps environment reproducible for evaluators

ADR-22

Licensing

Chosen

MIT OR Apache-2.0 (SPDX dual license)

Rejected

GPL, BSL, proprietary

When the rejected choice is right

GPL wins when the goal is to compel downstream users to open-source their modifications (copyleft effect); BSL (Business Source License) wins for commercial products that need to prevent cloud-provider re-hosting while eventually open-sourcing after a time window

Why: Rust ecosystem norm; compatible with all dependency licenses in use; permissive for portfolio and educational use

ADR-23

AppState trait design

Chosen

trait AppState: Clone + Debug + Serialize + DeserializeOwned in cl-core

Rejected

concrete struct, dynamic dispatch (dyn)

When the rejected choice is right

Dynamic dispatch (dyn AppHandler) wins when the set of application types is not known at compile time and the binary must support user-supplied plugins loaded at runtime; concrete struct wins for a fixed single-application system where generics add boilerplate without benefit

Why: Generic monomorphization eliminates virtual dispatch overhead; bounds enable serialization and snapshot assembly without reflection

ADR-24

Error handling

Chosen

thiserror-derived error enums per crate; anyhow only in cl-cli binary

Rejected

Box<dyn Error>, panic, string errors

When the rejected choice is right

Box<dyn Error> wins in prototype code where defining error enums per crate is premature; panic-on-error wins in embedded no_std contexts where unwinding is disabled and the only recovery is a watchdog reset

Why: thiserror: typed, matchable errors in library crates; anyhow: ergonomic context chaining in CLI only; no unwrap in library code

ADR-25

Snapshot record format (human-readable export)

Chosen

JSON (via serde_json) export from GlobalSnapshot for cl-cli snapshot --output json

Rejected

YAML, TOML, custom

When the rejected choice is right

YAML wins when the snapshot output must be human-edited and re-fed into tooling (e.g., manual injection of a corrected cut for debugging); TOML wins for configuration-style snapshots with clear key-value semantics

Why: JSON: universally parseable; suitable for pipeline to external tools; not the primary storage format (postcard for wire, bincode for trace)

ADR-26

Process communication in simulator

Chosen

In-process function calls through shared Arc<Mutex<ChannelQueue>>; no OS threads per process

Rejected

OS threads, green threads, actor framework

When the rejected choice is right

OS threads win when each process must run user-level code that blocks (e.g., a real database query) — in-process function calls cannot parallelize blocking work; actor frameworks (Actix, Lunatic) win for production deployments needing message-driven concurrency with supervision trees

Why: Simulator controls delivery order externally; shared queue under mutex gives deterministic, non-parallel delivery; no scheduler nondeterminism

ADR-27

FIFO-violation injection (negative tests)

Chosen

cl-sim exposes inject_reorder(channel, msg_a, msg_b) to swap two consecutive messages; guarded behind #[cfg(test)] feature flag

Rejected

separate negative-test binary, manual manipulation

When the rejected choice is right

Separate negative-test binary wins when the injection mechanism is complex enough to risk polluting the production code path; manual manipulation wins for one-off exploratory testing where a programmatic injection API would take longer to build than the investigation

Why: Compile-time gated: never active in production builds; enables Phase 14 negative conformance tests without shipping a footgun

ADR-28

Reproducibility guarantee scope

Chosen

Seed → same DeliverySchedule → same Event log → same GlobalSnapshot → same verifier verdict, on any platform with same Rust std/rand versions

Rejected

cross-version, cross-OS float stability

When the rejected choice is right

Cross-version reproducibility wins for long-lived correctness archives where snapshots taken years apart must still verify; hardware-specific reproducibility (tied to a specific CPU model) wins in safety-critical embedded systems where the execution environment is fully controlled

Why: ChaCha8 is platform-independent; no floats in scheduling; BTreeMap iteration is deterministic; lockfile pins versions (I9)

Alternative Architectures (Roads Not Taken)

ALT-1 — Coordinated Blocking Snapshot (Stop-the-World)

Show the original text diagram
Architecture:
  Coordinator ─── FREEZE ──> all processes (broadcast, synchronous)
  Each process: records local state + drains channel queues
  All processes ─── STATE ──> Coordinator
  Coordinator assembles GlobalSnapshot
  Coordinator ─── RESUME ──> all processes

Regime where it wins: small fixed-topology systems (n ≤ 8) where the blocking pause is acceptable (e.g., an embedded controller taking a diagnostic snapshot once per minute) and implementation simplicity is paramount. No channel recording needed; no marker protocol; trivially correct.

Real system embodying it: database LOCK TABLES + FLUSH TABLES WITH READ LOCK (MySQL/MariaDB) for a consistent backup; Linux SIGSTOP sent to all processes in a container group for a cold checkpoint with CRIU.

Why rejected: violates P2 (non-blocking). The pause duration grows linearly with the number of processes and the time to serialize their states. For a token-ring with 64 processes running at 500,000 steps/s, a 1 ms pause eliminates 500 simulation steps — the entire purpose of the deterministic simulator. More fundamentally: the blocking snapshot cannot be used to study the algorithm being implemented, which is the non-blocking variant.

ALT-2 — Vector-Clock Causal Snapshot (Causal-Delivery-Based)

Architecture:
  All channels deliver messages in causal order (not just FIFO, but causal)
  Snapshot initiator broadcasts: SNAP(s, initiator_vc)
  Each process records state when it causally delivers SNAP(s, ...)
  No channel recording needed: causal delivery guarantees no pre-snapshot
  message arrives after the snapshot boundary

Regime where it wins: systems that already implement causal broadcast (e.g., causal-consistency distributed databases using vector-clock-stamped reads/writes). The causal-delivery guarantee subsumes FIFO and eliminates the need for channel recording entirely — the consistent cut is automatic at the delivery boundary.

Real system embodying it: Bayou (Terry et al. 1994) and causal key-value stores that propagate vector-clock-stamped updates. The "snapshot" in a causal KV store is the state visible after applying all updates causally before a given vector timestamp.

Why rejected: causal delivery is strictly stronger than FIFO delivery and requires piggybacking vector clocks on every application message. This doubles the message overhead and couples every channel to a global vector clock. The goal of this project is to implement Chandy-Lamport precisely as specified (FIFO only), not a stronger-guarantee variant. P4 (markers carry no state) would also be violated — application messages would carry causal metadata.

ALT-3 — Externally-Coordinated Checkpoint (Orchestrator Model)

Show the original text diagram
Architecture:
  External orchestrator (separate process/service) ──pause(P)──> each process Pi
  Orchestrator waits for acknowledgement from each Pi
  Orchestrator reads process state via RPC: snapshot_state(Pi) → AppState
  Orchestrator reads channel state via RPC: drain_channel(c) → Vec<Message>
  Orchestrator assembles GlobalSnapshot
  Orchestrator ──resume(P)──> each process Pi

Regime where it wins: legacy systems that cannot be modified to participate in a distributed protocol but expose a management API (pause/inspect/resume). Operational checkpointing of a running microservice deployment where injecting a marker protocol is impractical. Kubernetes ephemeral container snapshots with CRIU follow this pattern.

Real system embodying it: CRIU (Checkpoint/Restore in Userspace) for Linux processes; VMware vSphere live VM snapshots (hypervisor pauses VM, takes memory snapshot, resumes).

Why rejected: introduces a central coordinator SPOF; pauses all processes simultaneously (same issue as ALT-1 but adds network round-trips); requires a management API that cl-process does not expose; and most importantly: this is not the Chandy-Lamport algorithm. The educational and portfolio value of this project is specifically implementing the decentralized, non-blocking marker-flooding protocol.

ALT-4 — Epoch-Based Log-Truncation Checkpoint (Log-Structured)

Architecture:
  All process communication goes through an append-only log (Kafka-style)
  Epoch boundary record injected into every channel's log at checkpoint time
  Each process reads up to the epoch boundary, records state
  No in-flight messages: the log is durable; replay from offset covers them
  GlobalSnapshot = {per-process AppState at epoch boundary, per-channel offset}

Regime where it wins: systems already built on a durable ordered log (Kafka topics, DynamoDB Streams, Kinesis). The log serves simultaneously as the channel, the channel-state recording mechanism, and the recovery source. Checkpoint cost is O(1) per channel (record an offset), not O(in-flight messages). This is the exact model of Kafka Streams checkpointing and, at larger scale, Apache Flink with Kafka sources.

Real system embodying it: Kafka Streams state-store checkpointing; Apache Samza checkpoint protocol; AWS Kinesis Analytics checkpoint API.

Why rejected: requires a durable ordered log as the channel substrate, which eliminates the in-memory FIFO channel abstraction (cl-channel) and the entire cl-transport layer. The educational goal is to implement the channel-recording mechanism that makes non-blocking snapshots work without a durable log — the "hard part" of Chandy-Lamport. Using a log sidesteps the core algorithmic challenge.
