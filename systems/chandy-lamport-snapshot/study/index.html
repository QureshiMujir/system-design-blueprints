Mental Models & First Principles

MM1 — A Consistent Cut Is a Down-Set of the Happens-Before Relation

The compressed insight: a consistent cut C is a subset of events that is causally closed — if event e is in C and e' → e (e' happened-before e), then e' is also in C. This is exactly the definition of a down-set (order ideal) in a partial order.

What it predicts: the Chandy-Lamport marker rules automatically produce a down-set. The sender records state before emitting the marker; the marker travels through the FIFO channel; the receiver records state on first marker receipt. Everything sent before the sender's recording boundary that is not yet received appears in channel state — closing the down-set.

Bug class you write without it: failing to capture a message in channel state because you stop recording too early (before the channel's own marker arrives). The resulting cut is no longer a down-set — a Receive is in the cut whose matching Send is not, violating I1.

Applied in: §6 P1, §7 I1, §8.6 (Cut derivation), Phase 10 (cl-verify algorithm).

MM2 — Markers Are Logical Barriers, Not Data

The compressed insight: a Marker message carries only a snapshot identifier and has zero application payload (P4). Its sole job is to delineate "before" from "after" on a single directed FIFO channel. All state capture is local to the receiving process.

What it predicts: because markers carry no state, the sending process does not need to wait for state assembly before forwarding. This decoupling is what makes P2 (non-blocking) possible: the marker travels independently of the state it logically separates.

Bug class you write without it: adding a payload to the Marker variant (e.g., piggybacking the sender's local state "for convenience"). This creates a dependency: the marker cannot be sent until the state is serialized, introducing latency and potentially reordering the marker relative to later application messages on the channel.

Applied in: §6 P4, §9 ADR-28 (wire format — Marker has no payload field), §11.2 (Message enum), Phase 6.

MM3 — Channel Recording Window Is Defined by Two Timestamps, Not One

The compressed insight: channel state for channel c = {messages received after the receiver's first-marker event AND before c's own marker arrives}. Both boundaries matter independently. The window opens at the receiver's first-marker time (not when recording starts globally) and closes when c's specific marker arrives (not when any marker arrives).

What it predicts: in a partially-connected graph, different incoming channels at the same process have different recording windows because their markers arrive at different times. The window for channel c1 may close long before the window for c2.

Bug class you write without it: using a single global "recording started" flag per process instead of per-channel RecordStatus. You either over-record (include messages that arrived before the window opened on some channels) or under-record (close all channels when the first marker from any channel arrives).

Applied in: §6 P6, §7 I4, §8.2 (per-channel RecordStatus state machine), Phase 8.

MM4 — Seeded Deterministic Scheduler Is the Correctness Amplifier

The compressed insight: any concurrent protocol bug is a heisenbug without reproducibility. A seeded scheduler transforms a distributed algorithm with exponentially many interleavings into a function: seed → unique interleaving → unique snapshot → unique verdict. Every failure has a fingerprint (the seed) that exactly reproduces it.

What it predicts: the conformance suite runs 10,000+ seeds cheaply because each run is a pure function with no external non-determinism. Any failing seed is a regression fixture at zero additional cost.

Bug class you write without it: using a HashMap (non-deterministic iteration order), wall-clock time, or OS-scheduled threads inside the simulator. A real bug passes 9,999 seeds, fails on seed 4213, and you cannot reproduce it.

Applied in: §6 P9, §7 I9, §8.13 (scheduling semantics), §9 ADR-07/ADR-10, Phase 4 (cl-sim), Phase 14 (conformance harness).

MM5 — Stable Properties Are Monotone-True: Detection Is Sound by Construction

The compressed insight: a stable property Φ satisfies: Φ(S) ∧ S → S' ⟹ Φ(S'). Once true, it cannot become false. Therefore if a consistent snapshot (a reachable state) satisfies Φ, then Φ holds in all future reachable states. The detection is not approximate — it is exact.

What it predicts: cl-detect never produces false positives by construction, not by testing. The type system enforces that only genuinely stable predicates are represented in the StableProperty enum. Adding a non-stable predicate (e.g., "currently idle") to the enum is a design error, not a runtime risk.

Bug class you write without it: detecting "quiescence" (momentary idleness) rather than "termination" (permanent idleness with empty channels). A quiescence detector reports the system terminated when all processes are transiently idle between bursts, causing operators to kill a live system.

Applied in: §6 P8, §7 I7, §8.8 (stable-property detection model), Phase 12 (cl-detect), Phase 12 soundness test.

MM6 — SnapshotId Keying Is the General Principle: Instance Isolation by Opaque Token

The compressed insight: every per-snapshot recording state is keyed by SnapshotId. This is an instance of a universal pattern in distributed protocols: scope mutable state to an opaque identifier that distinguishes concurrent instances of the same protocol. Raft uses term+index, Paxos uses ballot number, TCP uses (src,dst,src_port,dst_port).

What it predicts: adding a second snapshot (Phase 11) costs only a HashMap key lookup, not a protocol redesign. Any cross-SnapshotId state access is structurally impossible when the key is always required.

Bug class you write without it: using a single-instance recording state. Two concurrent snapshots (s1, s2) share the RecordStatus map; a marker for s2 closes a channel window in s1 prematurely; both snapshots fail cl-verify.

Applied in: §6 P10, §7 I8, §8.7 (concurrent snapshot isolation), §9 ADR-09, Phase 11.

MM7 — Conservation Is the End-to-End Correctness Oracle

The compressed insight: if the sum of tokens (or money) across all process states plus all channel states equals the initial count, then no messages were double-counted, dropped, or fabricated by the snapshot protocol. Conservation is a single number that aggregates the correctness of every recording window across every channel.

What it predicts: any violation of I1, I2, I4, or I5 that affects an application message will manifest as a non-zero conservation delta. You do not need to inspect individual channels to diagnose most bugs — the delta tells you immediately that something is wrong and approximately how much was lost or duplicated.

Bug class you write without it: writing a verifier that only checks vector-clock relationships but ignores message payload values. Such a verifier can return "Consistent" on a snapshot that dropped a token if the causal ordering of events happens to be preserved by accident.

Applied in: §6 P6, §7 I6, §8.14 (AppState conservation invariant), Phase 13 (cl-detect conservation), Phase 14 conformance.

MM8 — The FIFO Precondition Is Not Defensive Programming — It Is the Proof

The compressed insight: the consistent-cut theorem in Chandy & Lamport 1985 (Theorem 1) has FIFO as a hypothesis, not a convenience. Without FIFO, the marker-receiving rule produces a cut that is not necessarily a down-set. The negative test (Phase 14) demonstrates this empirically: one FIFO violation → cl-verify reports Violated.

What it predicts: any transport layer that reorders messages within a channel, even rarely, invalidates all snapshot guarantees. There is no "probably consistent" — either FIFO holds or the cut may be inconsistent.

Bug class you write without it: implementing cl-transport with a priority queue that gives markers slightly higher delivery priority than app messages "for performance." A marker overtakes the app message sent before it; the receiver records state without that message; it is absent from both process state and channel state; conservation fails.

Applied in: §6 P3, §7 I2, §8.4 (channel model FIFO proof), Phase 2 (cl-channel FIFO enforcement), Phase 14 negative test.

Glossary · 44 terms · site-wide glossary

AppPayload
Opaque application-level value (token, transfer amount) carried by Message::App(AppPayload); treated as a blob by the protocol layer; interpreted only by cl-app handlers.
AppState
Per-process application state frozen at the first-marker instant; stored as the process contribution to GlobalSnapshot::process_states; cloned via clone_for_snapshot().
Asynchronous barrier snapshotting
Flink's descendant (Carbone et al., 2015): barrier control messages flood a dataflow DAG analogously to markers; the same consistent-cut guarantee applies to streaming checkpoints. Cross-reference: portfolio #105.
Causal consistency
Synonym for the consistent-cut property stated in causal terms: if e2 causally depends on e1 (e1 → e2) and e2 is in the cut, then e1 must also be in the cut.
Channel state
Vec<AppPayload> recorded for a directed channel in a GlobalSnapshot; precisely the messages sent before the sender's snapshot instant but received after the receiver's snapshot instant; managed by cl-recorder.
Chandy-Lamport algorithm
Distributed snapshot protocol (ACM TOCS, 1985): an initiator records its own state and floods marker messages; each process records state on first marker and buffers in-flight messages per channel until that channel's marker arrives; produces a consistent cut without halting computation.
Checkpoint
A persisted GlobalSnapshot enabling rollback-recovery; the algorithm produces the in-memory consistent cut; durability is a deployment concern above cl-recorder.
Completion detection
Mechanism in cl-recorder::completion: declares GlobalSnapshot fully assembled when every process has RecordStatus::Done on every incoming channel.
Concurrent snapshots
Two or more snapshot instances with distinct SnapshotIds running simultaneously; recording state keyed by SnapshotId; fully independent; non-interference enforced by I8 and Phase 11.
Conservation invariant
Application-level quantity preserved under any valid execution (total tokens, total account balances); cl-detect::conservation asserts sum(process_states) + sum(channel_states) == initial_value over a snapshot (I6).
Consistent cut
A Cut (per-process event-count frontier) that is causally closed: for every Receive in the cut, the matching Send is also in the cut, or the message appears as channel state. Proved for every Chandy-Lamport snapshot by cl-verify (I1).
Consistent global state
The global system state corresponding to a consistent cut; a GlobalSnapshot produced by the algorithm; reachable even though no physical instant at which all processes simultaneously occupy it need exist.
Cut
Map<ProcessId, u64> mapping each process to an event-count frontier; events at index ≤ frontier are "inside" the cut; used by cl-verify::cut to partition EventHistory and check causal closure.
Deadlock detection
cl-detect::deadlock stable-property check: construct a wait-for graph from the snapshot (edge Pi → Pj = Pi waiting for Pj); DFS cycle detection; a cycle implies deadlock, which is stable once true.
DeliverySchedule
cl-sim::schedule::DeliverySchedule: deterministically seeded ordered sequence of (ChannelId, message_index) steps; fully determines message delivery interleaving for a simulated run.
Deterministic scheduler
cl-sim::Simulator: given a fixed seed, generates an identical DeliverySchedule and thus identical EventHistory and identical snapshot on every execution (P9, I9).
Distributed snapshot
A GlobalSnapshot of a running distributed system captured without halting computation; Chandy-Lamport is the canonical algorithm; the result is a consistent global state.
Event
enum { Send(ChannelId, Message), Receive(ChannelId, Message), Internal } — atomic unit of run history; logged per process in cl-sim::history::EventHistory; ground truth for cl-verify cut construction and causal closure.
Event history
Ordered append-only log of (ProcessId, Event) pairs maintained by cl-sim::history; per-process subsequence queryable; used by cl-verify to reconstruct the happens-before relation.
FIFO channel
Directed, reliable, order-preserving channel: messages enqueued in send order and dequeued in that order; cl-channel::FifoChannel enforces this. Without FIFO a marker can be overtaken by an app message, breaking the recording boundary (P3, I2).
Flooding
Marker propagation strategy: every process receiving its first Marker(s) immediately sends Marker(s) on every outgoing channel; guarantees all reachable processes eventually participate in the snapshot.
GlobalSnapshot
{ snapshot_id, process_states: Map<ProcessId, AppState>, channel_states: Map<ChannelId, Vec<AppPayload>> } — complete output of one snapshot instance; assembled by cl-recorder; input to cl-verify and cl-detect.
Happens-before (→)
Lamport's 1978 partial order: e1 → e2 if same-process program order, or e1 = send(m) and e2 = recv(m), or transitively. A consistent cut is a down-set of →.
In-flight message
AppPayload sent before the sender's snapshot instant but received after the receiver's snapshot instant; not part of any process state; captured as channel state by cl-recorder.
Initiator
The process Pi calling cl-snapshot::initiate(Pi, sid); records own state first; sends Marker(s) on all outgoing channels; identified by SnapshotId::initiator. Any process may initiate.
Interleaving
A particular ordering of message-delivery events across channels in a concurrent run; cl-sim controls interleavings via DeliverySchedule; Phase 14 fuzzes many interleavings to confirm invariant soundness.
Lai-Yang variant
Distributed snapshot algorithm for non-FIFO channels: piggybacks color information on every application message; referenced as contrast in the FIFO-violation negative test; not implemented in this project.
Lamport clock
Scalar logical timestamp (CACM, 1978); sufficient for total event ordering; insufficient alone for causal direction between arbitrary events; cl-verify uses vector clocks instead.
Local state
AppState of a single process frozen at its first-marker instant for a given SnapshotId; the per-process contribution to GlobalSnapshot::process_states; governed by I3 (recorded exactly once per snapshot).
Marker
Message::Marker(SnapshotId) — lightweight control message carrying only a snapshot identifier; no application payload; sole purpose is to delineate pre-snapshot from post-snapshot app messages on a channel (P4).
Marker-receiving rule
On first Marker(s) at Pj from channel c: record own state; mark c as empty; start recording all other incoming channels; send Marker(s) on all outgoing. On subsequent Marker(s) from c: stop recording c. Implemented in cl-snapshot::receive.
Marker-sending rule
On initiation or first-marker receipt: before sending any further app message, send Marker(s) on every outgoing channel; ensures marker arrives before all post-snapshot app messages. Implemented in cl-snapshot::initiate and cl-snapshot::receive.
Non-blocking
Characteristic of Chandy-Lamport: processes continue sending, receiving, and executing application logic during snapshot recording; no synchronization barrier halts computation (P2).
ProcessState
Runtime struct { local: AppState, recording: Map<ChannelId, RecordStatus>, recorded: SnapshotState } — tracks both application state and per-channel snapshot bookkeeping; distinguished from the snapshot's AppState contribution.
RecordStatus
enum { NotStarted, Recording, Done } — per-(SnapshotId, ChannelId) recording state at a receiving process; drives the channel-recording state machine in cl-snapshot::receive.
Reachable state
A global state reachable from the initial configuration by some valid execution sequence; the Chandy-Lamport consistency theorem: every consistent snapshot corresponds to a reachable state even without a global clock.
Reliable delivery
Channel guarantee: every sent message is eventually delivered exactly once in send order; enforced by cl-channel and cl-sim; required for snapshot liveness (I10).
Snapshot ID
SnapshotId { initiator: ProcessId, seq: u64 } — unique identifier for one snapshot instance; keys all per-snapshot recording state in cl-snapshot and cl-recorder; enables concurrent independent snapshots (I8).
SnapshotState
{ local_state_at_first_marker: AppState, channel_msgs: Map<ChannelId, Vec<AppPayload>> } — per-process recording accumulator: frozen local state plus growing in-flight message list per incoming channel.
Stable property
Predicate P on global state such that P(s) true and s → s' implies P(s'); once true, stays true; detecting P over a consistent snapshot is sound (P8, I7). Examples: Terminated, Deadlocked, Conserved.
Termination detection
cl-detect::termination: all process_states report idle AND all channel_states are empty in the snapshot; if true in a consistent snapshot, termination is permanent.
Token ring
cl-app::token_ring distributed computation: N tokens circulate among P processes; sum(process_states) + sum(channel_states) == initial token count; a conservation invariant testable by cl-detect::conservation.
Vector clock
Map<ProcessId, u64> logical timestamp advanced on send/receive per Fidge/Mattern rules; used by cl-verify::causal to reconstruct happens-before and certify causal closure of the recorded cut.
Wait-for graph
Directed graph in cl-detect::deadlock: node per process, edge Pi → Pj if Pi is blocked waiting for Pj; cycle implies deadlock; detected via iterative DFS over GlobalSnapshot.
