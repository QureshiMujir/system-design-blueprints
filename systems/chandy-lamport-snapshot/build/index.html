⬜ Phase 1 — core types: process, channel, message, marker

Objectives
  • Define the complete shared vocabulary for the entire protocol in cl-core; all other crates depend on this crate, nothing else.
  • Lock the canonical type names exactly as in the spine: ProcessId, ChannelId, SnapshotId, Message, AppPayload, ProcessState, RecordStatus, SnapshotState, GlobalSnapshot, Event, Cut, VectorClock, DeliverySchedule, StableProperty.
  • Zero I/O, zero async, zero protocol logic; pure data definitions and their invariant-preserving constructors.
  • Enforce #![no_std]-compatible design where feasible; all heap use is explicit alloc.
  • Derive Clone, Debug, PartialEq, Eq, Hash, serde::Serialize/Deserialize on every exported type.
Deliverable
  • cl-core compiles, all types serialize/deserialize round-trip, cargo test -p cl-core passes.
  • No protocol or I/O code present; library is a pure data crate.
  • cargo doc -p cl-core generates complete docs with zero warnings.

Pitfalls
  • from == to in ChannelId: self-loop channels are undefined in Chandy-Lamport; add a debug_assert! in the constructor.
  • HashMap nondeterminism: using HashMap instead of BTreeMap breaks reproducibility (I9, P9); entire snapshot assembly becomes seed-dependent in unpredictable ways.
  • RecordStatus state duplication: storing accumulated messages outside the variant leads to out-of-sync states on clone; keep the Vec inside the variant.
  • AppState opaque bytes: downstream crates that cast AppState bytes without a version tag will silently misparse after schema drift; add a schema_version: u8 prefix in AppState.
  • Missing SnapshotId equality / clock overflow: if SnapshotId lacks Eq/Hash, BTreeMap<SnapshotId, _> lookups compile but panic — derive both; guard VectorClock::increment with checked_add against theoretical u64 overflow.

⬜ Phase 2 — FIFO channel abstraction

Objectives
  • Implement cl-channel: a directed, reliable, order-preserving unidirectional channel between two processes.
  • Guarantee: a message enqueued before another is dequeued before it — the FIFO precondition that Chandy-Lamport depends on (P3, I2).
  • Channel carries both Message::App and Message::Marker in the same ordered queue; markers never overtake app messages.
  • Expose explicit enqueue / dequeue / peek interface; no async, no threads — delivery is driven externally by cl-sim.
  • Track per-channel statistics (enqueue count, dequeue count, current depth) for observability.
Deliverable
  • cl-channel compiles against cl-core.
  • FifoChannel enqueue/dequeue maintains FIFO order across 10,000-message stress test.
  • Stats counters match enqueue/dequeue counts after any sequence.
  • cargo test -p cl-channel passes; drain returns messages in correct order.

Pitfalls
  • Marker overtaking: if Message::Marker is given priority delivery outside FifoChannel (e.g., via a side queue), FIFO (I2) is broken; markers MUST enter the same queue as app messages — no priority queue, no side channel.
  • Sequence number reuse after drain: if next_seq resets after drain, simulator indices collide; next_seq is monotone for the channel's lifetime.
  • VecDeque front/back confusion: push_back + pop_front = FIFO; push_back + pop_back = LIFO and silently wrong; add an assertion: pop_front.
  • Double-dequeue / stats drift: a test helper calling dequeue twice on a length-1 queue must get Empty, not a panic, on the second call; and since drain bypasses dequeue, stats must be updated inside drain too, or they silently underscore true throughput.
  • Channel self-loop construction: prevented by ChannelId::new (Phase 1); FifoChannel::new re-asserts in debug mode.

⬜ Phase 3 — process model

Pitfalls
  • State recorded after first app message post-marker: if on_receive processes an app message before taking local_state snapshot, the cut is incorrect. Mitigation: snapshot AppState synchronously before any handler runs in same tick.
  • Outgoing marker delayed past app messages: if the process sends app messages before flooding markers, downstream processes may see app messages before the marker, violating FIFO delineation. Rule: marker injection must precede any further app sends in the tick.
  • channel_status initialized lazily: channels not yet in the map default to NotStarted; if all_incoming is stale (topology change), some channels never enter Recording. Mitigation: all_incoming slice must be authoritative topology at time of snapshot initiation.
  • Concurrent snapshot state collision: keying ProcessRecordingState by SnapshotId only — if HashMap uses default hasher and SnapshotId equality is wrong (e.g., only seq compared), distinct snapshots from same initiator collide. Use (initiator, seq) equality.
  • Marker sent on a channel not yet established: if outgoing channel set changes between initiation and first-marker receipt, send to a dropped channel panics. Guard with channel_exists(out_c).
  • Re-entrant on_marker during marker sending: if marker-send triggers immediate receipt at the same process (loopback), re-entrancy corrupts ProcessRecordingState. Ensure markers_sent = true is set before sending.

⬜ Phase 10 — Consistency Verification

Objectives
  • Implement cl-verify: prove a GlobalSnapshot is a consistent cut per I1 and P1. Causal closure check: every message receive in the cut has its matching send in the cut, or the message is captured as channel (in-flight) state; anti-violation check: no message sent strictly after the cut boundary is received before the cut.
  • Attach VectorClock to each Event in the run history (EventLog) during simulation; use those clocks to establish happens-before order across processes. Scope covers App messages only — Marker messages are control messages, excluded from causal-closure checks.
  • Output VerificationResult — Consistent or Inconsistent(Vec<CutViolation>); cl-verify is entirely read-only over GlobalSnapshot + EventLog (zero mutation of snapshot state).
  • Dependency: Phase 9 (GlobalSnapshot assembled); Phase 4 (EventLog with vector-clock annotation from cl-sim). Verification is the correctness oracle for the entire cl-snapshot protocol — if cl-verify reports Consistent, I1 and P1 hold for that snapshot.

⬜ Phase 12 — Stable-Property Detection

Objectives
  • Implement cl-detect: evaluate StableProperty variants over a GlobalSnapshot (I7, P8) — Terminated (all processes idle AND all channels empty: necessary and sufficient for real termination after the cut), Deadlocked (a wait-for cycle exists: sufficient for real deadlock, and stable once true), and Conserved(invariant) (a user-supplied invariant holds over process states plus in-flight channel messages).
  • Soundness guarantee (I7, P8): a stable property true in a consistent snapshot remains true in the actual execution after the cut; completeness note: detection is sound (true positive = real property) but not complete (a stable property may hold in the real system without holding in a given snapshot taken before it became stable). Termination detection requires a consistent snapshot specifically — an inconsistent snapshot could report false termination.
  • Wait-for graph captures only direct blocking relationships; transitive deadlock (p waits for q waits for r) is resolved by DFS cycle detection, not manual transitive closure. Constraint: detection is entirely read-only over GlobalSnapshot — no mutation, no I/O.
  • Dependency: Phase 9 (GlobalSnapshot assembled and verified consistent by Phase 10).
Deliverable
