1. Goal

1.1 What Is Built

A from-scratch Rust implementation of the Chandy-Lamport distributed snapshot algorithm (ACM TOCS 1985). The system records a consistent global state — each process's local state at the snapshot boundary plus the messages in flight on every directed FIFO channel — while the underlying computation continues running without pause. Snapshot recording is triggered by a designated initiator process, which floods marker messages through the topology; each process responds according to the marker-sending rule (on initiation) and the marker-receiving rule (on receiving its first marker per snapshot). The resulting GlobalSnapshot is passed to: (a) cl-verify, which proves the captured cut is causally consistent using vector-clock annotation of the event history; (b) cl-detect, which checks stable properties (termination, deadlock, conservation). The implementation runs inside a deterministic seeded simulator (cl-sim) that serializes all message deliveries, making any interleaving exactly reproducible.

1.3 Non-Goals

  • No real network transport; cl-transport is an in-memory simulated routing layer throughout all primary phases.
  • No on-disk persistence; snapshots live in memory for the duration of a simulation run.
  • No Lai-Yang non-FIFO extension. PhaseDeferred("Phase 11")
  • No distributed recovery from a captured checkpoint (restore and re-execute). PhaseDeferred("Phase 14")
  • No multi-host deployment or container orchestration. PhaseDeferred("Phase 14")
  • No GUI, web dashboard, or metrics endpoint.
  • No dynamic topology change (process addition/removal) while a snapshot is in progress.
  • No Byzantine or crash-fault tolerance; the model assumes reliable FIFO delivery throughout.
  • No encryption, authentication, or authorization on the transport.
  • No integration with external consensus libraries (Raft, Paxos bindings).

1.4 Intended Deployment Model

Single-binary, single-host, multi-threaded Rust executable. Processes are modeled as in-process entities; all message delivery is serialized by cl-sim. The binary is fully self-contained: no external services, no databases, no network stack, no configuration files beyond CLI flags. The CLI (cl-cli) configures topology (process count, channel graph), application type (token ring / bank transfer), scheduler seed, snapshot initiator identity, and snapshot trigger timing, then runs the simulation and reports results (GlobalSnapshot, consistency verdict, stable-property results) to stdout or a structured JSON output file.

Primary use: a correctness-demonstrating reference implementation and portfolio artifact. Secondary use: a teaching tool for studying specific interleavings by reproducing seeds.

1.10 Language Rationale — Rust (Locked)

The algorithm is a concurrent message-passing protocol whose correctness hinges on FIFO channel ordering and precise marker handling across many processes running simultaneously; reasoning about it demands a model where message delivery, marker rules, and channel recording are explicit and where runs are deterministically replayable for testing. Rust gives exhaustive enums for the message/marker/event taxonomy, channels and async tasks for the process model with Send/Sync-checked concurrency, and a deterministic scheduler for reproducible interleavings. The core types, FIFO channels, process model, snapshot protocol, recorder, simulator, and stable-property detectors are all Rust.

Specific Rust features that map directly to algorithm concerns:

Algorithm concern Rust feature
Message taxonomy (App Marker) must be exhaustive
RecordStatus per channel must not be confused across SnapshotIds HashMap<(SnapshotId, ChannelId), RecordStatus> — type-level keying
FIFO channel ownership: one sender, one receiver Rust's ownership model; VecDeque<Message> in channel struct; no shared write path
Concurrent snapshot state must not alias Arc<Mutex<ProcessState>> per process; borrow checker prevents data races

VectorClock arithmetic must be exact [u64; MAX_PROCS] or HashMap<ProcessId, u64>; no floats

2.2 Unique Systems Knowledge This Teaches

  • Causal consistency operationalized: cl-verify forces the implementer to mechanize the happens-before relation over a concrete event log, not merely recite the definition.
  • FIFO as correctness precondition: the negative test (deliberate FIFO violation → cl-verify returns Violated) makes the precondition visceral and empirically verifiable, not just theoretical.
  • Non-blocking two-phase protocol: the marker-sending and marker-receiving rules encode a logical two-phase protocol interleaved with application traffic — the same pattern as two-phase commit but asynchronous and non-blocking.
  • Distributed state assembly from local observations: each process contributes only its own snapshot; cl-recorder assembles the global view — a composability pattern used in gossip protocols, monitoring aggregators, and consensus state transfer.
  • Stable-property soundness argument: constructing the formal argument that a stable property true at a consistent cut holds in all future reachable states solidifies the engineer's ability to reason about safety in distributed systems.
  • Deterministic simulation testing: cl-sim's seeded scheduler is the same architecture as FoundationDB's deterministic simulator, TigerBeetle's VOPR, and the Antithesis platform — one of the highest-leverage testing techniques for distributed systems.
  • Conservation invariant over distributed state: summing a quantity across process states plus channel states to verify conservation is a technique used in distributed ledgers, stream processors, and distributed databases.
  • Concurrent protocol instances: Phase 11's per-SnapshotId isolation teaches the general technique of scoping protocol state to an instance key — used in Raft log replication, Paxos ballots, and distributed transaction IDs.

3.2 Subsystem Descriptions

cl-core — zero-I/O vocabulary crate; the root of the workspace dependency DAG. Defines every shared type: ProcessId(u32), ChannelId{from,to}, SnapshotId{initiator,seq}, Message enum (App(AppPayload) | Marker(SnapshotId)), ProcessState, RecordStatus (NotStarted | Recording | Done), SnapshotState, GlobalSnapshot, Event (Send | Receive | Internal), Cut (per-process frontier), VectorClock (Map<ProcessId,u64>), DeliverySchedule, StableProperty. All other crates import cl-core; cl-core imports nothing from the workspace. A type change in cl-core is a cross-cutting breaking change — treat as a published API boundary.

cl-channel — directed, reliable, FIFO message queue between exactly two processes. Internal state: a VecDeque<Message> preserving send order. Interface: enqueue(msg) on send side; dequeue() -> Option<Message> on receive side; drain_recorded() -> Vec<AppPayload> for snapshot channel-state extraction. The FIFO invariant (I2) is the structural precondition for Chandy-Lamport correctness: a marker must not arrive before messages sent before it on the same channel. cl-channel enforces this by construction — order is determined by insertion order in the deque. No concurrency internally; cl-sim drives all dequeue calls.

cl-process — models one logical process: holds AppState (application-defined), a map of outgoing ChannelIds to cl-channel references, a map of incoming ChannelIds, and a per-snapshot HashMap<SnapshotId, ProcessState>. Exposes: send(channel_id, msg) (enqueues into the channel, logs a Send event), on_receive(channel_id, msg, handler) (dispatches to the AppHandler trait, logs a Receive event), internal_transition(handler) (application step, logs Internal event). Snapshot logic is injected by cl-snapshot calling into the process; the process does not implement the protocol itself. Application logic is provided by an AppHandler trait impl (supplied by cl-app). Process boundaries are the trust boundary: no process reads another's AppState directly.

cl-transport — passive registry that maps ChannelId to a (sender-process, receiver-process, channel) triple. Used by cl-process.send to locate the channel and by cl-sim.deliver to route a dequeued message to the receiving process. In the simulated backend, cl-transport holds no message buffers; messages reside in cl-channel's deque. Interface: register(channel_id, sender, receiver), send(channel_id, msg) (delegates to cl-channel.enqueue), deliver(channel_id) -> Option<DeliveryToken> (dequeues one message, returns a token cl-sim uses to call cl-process.on_receive). No persistence; no acknowledgement; no retransmit.

cl-app — two concrete distributed computations implementing the AppHandler trait: (1) TokenRingApp — a fixed number of tokens circulate around a ring; total tokens across all processes plus all channels is the conservation invariant; (2) BankTransferApp — processes send money amounts on channels; total money across all process balances plus all in-flight transfers is conserved. Both apps provide an invariant_value(state: &AppState) -> u64 method that cl-detect uses for conservation checking (I6). Data flow: cl-app state is embedded in AppState; cl-process snapshots it as part of SnapshotState at first-marker time; cl-detect sums all process and channel contributions.

cl-sim — seeded deterministic scheduler. Maintains a pending-delivery set: for each channel with non-empty queue, the next deliverable (channel_id, head_index) pair. Each step: apply a deterministic selection function (seeded PRNG or round-robin) to choose a channel; call transport.deliver(channel_id); append the resulting Event (with updated VectorClock) to the EventLog. Reproducibility invariant (I9): same seed → same event sequence → same snapshot state → same verifier verdict. cl-sim serializes all process steps: no real parallelism; all interleaving is under cl-sim's control. cl-sim also supports: inject_snapshot_initiation(pid, snapshot_id, step) to trigger a snapshot at a scheduled step; violate_fifo_at(channel_id, step) for the Phase 14 negative test (reorders two adjacent messages on a channel). cl-sim must not depend on cl-snapshot (avoids coupling scheduling to protocol).

cl-snapshot — implements the Chandy-Lamport protocol as rule applications invoked by cl-process's message dispatch and by an external initiation call. Manages a HashMap<(ProcessId, SnapshotId), PerProcessSnapshotState> where PerProcessSnapshotState contains: local_state_recorded: bool, channel_status: HashMap<ChannelId, RecordStatus>, recorded_msgs: HashMap<ChannelId, Vec<AppPayload>>. Rules: (a) initiate(pid, snapshot_id, process) — if not already started, record process local state, set all incoming channels to NotStarted, set all outgoing channels to Recording, send Marker(snapshot_id) on all outgoing channels before any further app message; (b) on_marker(pid, snapshot_id, from_channel, process, recorder) — if first marker for this snapshot: record local state, mark from_channel Done (empty), set all other incoming channels to Recording, send Marker on all outgoing; else: stop recording from_channel (Done), move its recorded list to SnapshotState; call recorder.maybe_complete(pid, snapshot_id). This is the most semantics-dense crate; the state machine is the core contribution.

cl-recorder — collects SnapshotState contributions from processes as they finish (receive marker on every incoming channel). Holds a HashMap<SnapshotId, SnapshotAccumulator> where SnapshotAccumulator tracks: which processes have submitted, the assembled GlobalSnapshot under construction. Interface: submit(snapshot_id, pid, state: SnapshotState) — adds process's local state + recorded channel messages; is_complete(snapshot_id) -> bool — all P processes have submitted and all C channels have RecordStatus::Done; assemble(snapshot_id) -> GlobalSnapshot — final immutable snapshot. Completion detection is O(P*C) check; acceptable at simulation scale. Concurrency: protected by a Mutex in multi-snapshot scenarios (Phase 11).

cl-verify — takes a completed GlobalSnapshot and the VectorClock-annotated EventLog from cl-sim and mechanically checks the consistent-cut invariant (I1). Algorithm: (a) reconstruct the Cut — per-process event-count at the time of each process's first-marker recording; (b) for every Receive event in the cut, find the matching Send event using Message identity; (c) assert the Send event is also in the cut (its VectorClock ≤ the Cut frontier at the sender) OR the message appears in the snapshot's channel-state list; (d) assert no message sent after the cut (sender's clock > cut frontier) appears in any process's received set before the cut. Returns VerifyResult::Consistent or VerifyResult::Violated { evidence: Vec<CausalViolation> }. The verifier is the mechanized proof; it must pass on all valid runs and must return Violated on FIFO-violation injections.

cl-detect — evaluates stable properties over a completed GlobalSnapshot without re-running the simulation. Three detectors: (a) Termination — all process AppStates report idle (via AppHandler::is_idle) AND all channel states are empty Vec; (b) Deadlock — construct WaitForGraph from AppStates (via AppHandler::wait_for edges); run DFS cycle detection; return the cycle if found; (c) Conservation — for each conserved quantity (tokens, money), sum AppHandler::invariant_value over all process states plus sum AppPayload values over all channel states; compare to initial value; report delta if non-zero. Returns Vec<StablePropertyResult>. The soundness argument (P8, I7): stable properties are monotone — once true, remain true; a consistent snapshot (I1) captures a reachable state; therefore a stable property true in the snapshot is true in the current execution.

cl-cli — top-level entry point. Parses arguments: --processes N, --topology [ring|full|custom], --app [token-ring|bank-transfer], --seed U64, --initiate PID@STEP, --output [text|json]. Subcommands: run (execute simulation, print event log), snapshot (run + trigger snapshot + print GlobalSnapshot), detect (snapshot + run cl-detect, print StablePropertyResult), verify (snapshot + run cl-verify, print VerifyResult + evidence). No business logic in cl-cli; all calls delegate to the other crates. Depends on all 10 other crates.

6. Design Principles

P1. The Snapshot Is a Consistent Cut

Statement. The recorded global state corresponds to a reachable state of the system: causally closed — if a receive event is in the cut, its matching send is in the cut or the message is captured as channel state.

Formal grounding. For every message m, send(m) →* receive(m) in the happens-before partial order (Lamport 1978). The Chandy-Lamport marker rules enforce this: a process records local state at the first marker, capturing all effects of sends issued before the marker. Channel recording captures the asymmetric window where sender has snapshotted but receiver has not yet.

Tradeoff table.

Option Consistency Overhead Notes
Consistent cut (Chandy-Lamport) Causally closed Zero app pause Requires FIFO channels (P3)
Stop-the-world freeze Simultaneously consistent Full pause Not scalable; violates P2
Non-FIFO snapshot (Lai-Yang) Causally closed Extra piggyback state on every message FIFO precondition removed; more complex recording rule

Operational implication. cl-verify attaches VectorClock to every Event; validates for each Receive in the cut that sender's clock at send-time ≤ receiver's clock at first-marker time.

Violation consequence. Inconsistent cut → stable-property verdicts are unsound; deadlock reported on a live system or termination missed; GlobalSnapshot unusable for checkpointing.

Cross-references. Enforced by I1; verified in Phase 10 (cl-verify); proven correct in Chandy & Lamport 1985 Section 3.

P2. Non-Blocking

Statement. Processes never pause application-level computation to participate in a snapshot; snapshot actions are side-effects of normal message processing.

Formal grounding. The algorithm's "concurrent" nature is explicit in the original paper: the global state is recorded "while the underlying computation executes." The only snapshot-visible actions are (a) recording local state on first marker and (b) appending to channel_msgs while recording — both O(1) per message.

Tradeoff table.

Option App pause Consistency Complexity
Non-blocking (Chandy-Lamport) None Consistent cut Channel recording required
Stop-the-world Full Trivially consistent No channel recording needed
Two-phase coordinator Partial (per-phase) Consistent Coordinator SPOF; deadlock risk

Operational implication. cl-process event loop: receive message → dispatch app handler → check snapshot recording state → continue. No snapshot wait point anywhere in the loop.

Violation consequence. Any blocking on snapshot coordination creates deadlock risk within the protocol itself — precisely what the algorithm was designed to avoid.

Cross-references. P2 is why P6 (channel recording) exists; violated by any implementation that piggybacks state on markers (see P4).

P3. FIFO Channels Are Required

Statement. Every channel delivers messages in send order; a marker never overtakes an earlier application message on the same channel.

Formal grounding. The consistent-cut proof in Chandy & Lamport 1985 (Theorem 1) relies on FIFO: if message m is sent before marker on channel c, m arrives before marker at the receiver; therefore the receiver is still recording when m arrives and captures m in channel state. Without FIFO, m could arrive after the marker — silently dropped from the snapshot.

Counterexample (P3 violation).

Sender records state (sends Marker on c).
Earlier app message m is delayed; Marker arrives at receiver first.
Receiver stops recording c.
m arrives after recording stopped — not in channel state, not in process state.
Conservation violated: delta = value(m) ≠ 0.

Operational implication. cl-channel: strict enqueue/dequeue FIFO; sequence numbers assert ordering; cl-transport: may delay messages but never reorder within a channel.

Violation test. Phase 14 negative test: inject deliberate out-of-order delivery on one channel; run snapshot; cl-verify must report inconsistent cut and conservation delta ≠ 0.

Cross-references. I2 enforces FIFO at runtime; P5 (Lai-Yang paper) shows the non-FIFO alternative; cl-channel is the enforcement point.

P4. Markers Delineate, They Do Not Carry State

Statement. A Marker(SnapshotId) carries only the snapshot identifier; it signals the boundary on its channel and nothing more.

Formal grounding. The paper defines markers as "special messages" with no data payload. State capture is entirely local (each process records its own state on first-marker receipt) and channel-local (the receiver accumulates in-flight messages). Coupling state to the marker would require the sender to wait for state assembly before forwarding, breaking P2.

Enforcement. Message::Marker(SnapshotId) — no other fields; reviewed as a type-level invariant; any PR adding fields to the Marker variant is rejected.

Violation consequence. Piggybacking state on markers: (a) forces sender to pause until state assembled (breaks P2); (b) creates ordering dependency on state size (breaks P3 if state assembly delays marker relative to earlier app messages); (c) multiplies network traffic proportionally to state size.

Cross-references. P4 and P2 are co-dependent; P4 is what makes P2 possible; violations also risk I3 (marker-once) if state-carrying markers are forwarded conditionally.

P5. Record-on-First-Marker

Statement. A process records its local state exactly once per SnapshotId — at the moment of its first incoming marker (or at initiation).

Formal grounding. The paper rule: "On receiving a marker for the first time on any channel, process q records its local state." Subsequent markers close channel recording windows but do not update the recorded local state. The cut component for q is fixed at the moment of first-marker receipt.

State machine.

Show the original text diagram
Per (process, SnapshotId):
  INITIAL → (first marker or initiate) → RECORDED_LOCAL_STATE
  RECORDED_LOCAL_STATE → (each subsequent marker closes a channel) → ... → ALL_CHANNELS_DONE

Operational implication. cl-snapshot checks per_snapshot_state.get(sid).local_state.is_some() before recording; if Some, skip and only close the channel's recording window.

Violation consequence. Double-recording advances the cut component for that process past its causal position — a received message may predate the sender's now-later recorded state, creating an inconsistent cut (I1 violation).

Cross-references. I3 is the runtime invariant enforcing P5; cl-snapshot is the enforcement crate.

P6. Channel State Is the In-Flight Set

Statement. The recorded state of channel c is exactly the set of application messages sent before the sender's cut point but received after the receiver's cut point.

Formal grounding. The paper defines: "The state of channel c = {m : send(m) precedes pi recording state AND receive(m) does not precede pj recording state}". This is the set of messages in transit when the snapshot was taken.

Recording-window diagram.

Sender's timeline:   |---pre-snapshot sends---|[RECORD]|---post-snapshot sends---|
Receiver's timeline: |---receives----|[FIRST MARKER]|---channel recording---|[MARKER arrives: stop]
                                                       ^^^^^^^^^^^^^^^^^^^^
                                                       These are channel state for c

Tradeoff. Buffer size for channel recording = number of in-flight messages at snapshot time; bounded per session but theoretically unbounded; in cl-app the token-ring has at most 1 in-flight token per channel.

Violation consequence. Over-counting (including post-snapshot messages): double-counts tokens/money (conservation violation I6). Under-counting (missing pre-snapshot messages): loses tokens/money (conservation violation I6). Both break I1.

Cross-references. I4 is the runtime invariant; cl-verify validates recording window boundaries in Phase 10.

P7. Termination Is Guaranteed

Statement. Under reliable FIFO delivery and finite processes, every initiated snapshot terminates in bounded event steps.

Formal grounding. Proof by induction on graph diameter d: initiator sends marker on all outgoing channels (step 1); each recipient forwards on all outgoing channels (step 2...); by step d every process has received at least one marker. Reliable delivery ensures each channel delivers its marker in finite time. I5 (completeness) follows from finitely many channels and reliable delivery.

Complexity. Marker messages: O(e) for e directed edges. Event steps to completion: O(d + max_channel_delay), where d = diameter.

Operational implication. cl-sim: never drop markers (only delay). Phase 14 liveness test: 1000 random seeds, all snapshots complete within n_processes * n_channels * max_delay_steps steps.

Dependency table.

Precondition If violated Effect
Reliable delivery Marker dropped RecordStatus stays Recording forever; I10 fails
FIFO ordering Marker overtaken Channel state incomplete; I2, I4 fail
Finite processes Infinite graph Marker flood never terminates

Cross-references. I10 is the runtime invariant; P7 is why cl-transport in sim mode never drops messages.

P8. Stable-Property Soundness

Statement. A stable property (monotone: P true → P stays true) detected in the consistent snapshot is true in the real execution at the cut point onward.

Formal grounding. Chandy & Lamport 1985 Theorem 2: if S is a consistent snapshot and Φ is stable and Φ(S) holds, then Φ holds in all reachable states from S. Proof: S is a reachable state; stable Φ cannot become false once true; therefore Φ holds everywhere reachable from S.

Stable vs. non-stable properties.

Property Stable? Detectable? Notes
Termination (all idle, all channels empty) Yes Yes Once terminated, stays terminated
Deadlock (wait-for cycle with no resource release) Yes Yes Deadlocked processes cannot self-undeadlock
Conservation (sum constant) Yes Yes Sum never changes by application invariant
Momentary idleness No No A process may receive a new message next step
Transient high load No No Load fluctuates

Operational implication. cl-detect's StableProperty enum is closed: only Terminated, Deadlocked, Conserved(invariant). Attempting to detect a non-stable property via this path is a type error by design.

Violation consequence. False positive: system declared terminated/deadlocked while still running → operator kills live system. False negative: missed detection → system hangs undetected.

Cross-references. I7 is the runtime invariant; Phase 12 tests validate stable-property soundness by continuing the run after a positive detection.

P9. Determinism for Testing

Statement. Every run is driven by a seeded scheduler (cl-sim); any interleaving and its resulting snapshot are exactly reproducible from the seed.

Formal grounding. cl-sim's DeliverySchedule is a pure function of the PRNG seed + initial topology. The Event history is a pure function of the DeliverySchedule + process logic. cl-verify's verdict is a pure function of the Event history.

Determinism sources to control.

Source of non-determinism Mitigation
HashMap iteration order Use BTreeMap in cl-sim and cl-verify
Thread scheduling cl-sim is single-threaded; no async in the core sim loop
System time All "time" is logical event count; no wall-clock reads
External I/O None in cl-core, cl-sim, cl-snapshot, cl-verify
PRNG choice rand::SeedableRng with explicit seed type (e.g., SmallRng)

Operational implication. cl-cli run --seed <u64> replays any scenario exactly. Every failing test emits seed=<u64> to stderr. CI stores seeds of all known-failing interleavings.

Violation consequence. Non-determinism makes any concurrent-protocol bug a heisenbug — found once, unreproducible, impossible to regression-test. P9 is what makes Chandy-Lamport correctness testable in practice.

Cross-references. I9 is the runtime invariant; Phase 14 fuzz tests validate 1000+ seeds produce consistent cuts.

P10. Concurrent Snapshots Are Independent

Statement. Multiple snapshot instances identified by distinct SnapshotIds run concurrently without interfering; recording state for one snapshot never corrupts another's state or cut component.

Formal grounding. Each SnapshotId induces an independent flooding wave. A process's local state at first-marker time is recorded separately per SnapshotId. Channel recording windows for distinct SnapshotIds are independent sequences of received messages — interleaved in delivery time but separated by their respective marker boundaries.

State layout.

ProcessState.per_snapshot: BTreeMap<SnapshotId, SnapshotState>
  SnapshotState {
    local_state_at_first_marker: AppState,  // recorded once per SnapshotId
    channel_msgs: BTreeMap<ChannelId, (RecordStatus, Vec<AppPayload>)>
  }

Tradeoff. Memory usage scales as O(concurrent_snapshots × state_size × n_channels). In cl-sim, bounded and small. Production deployments should bound concurrent snapshots (e.g., max 4) via a semaphore in cl-snapshot.

Violation consequence. Shared recording state: one snapshot's marker closes another's channel window prematurely; recorded channel_msgs[c] for SnapshotId s2 contains messages from s1's window; both cuts fail I1 verification.

Violation test. Phase 11: initiate two snapshots simultaneously from different processes; both must pass cl-verify independently; interleavings explored over 100 seeds.

Cross-references. I8 is the runtime invariant; cl-snapshot is the enforcement crate; Phase 11 is the test phase.

P11. Completion Detection Is Monotone

Statement. A process's completion state for a given snapshot only ever moves forward — NotStarted → Recording → Done per channel, and pending only ever shrinks toward empty at the recorder. No transition ever reverses, and no completed channel or process is ever re-added to a pending set.

Formal grounding. RecordStatus (§8.2) is a three-state lattice with Done as the unique maximal element; CompletionDetector::mark_done (§11.10) only removes from pending, never inserts. Monotonicity is what makes is_complete() a safe one-shot check: once true, it is true forever for that SnapshotId, so cl-recorder never needs to re-poll or roll back an assembly decision.

Tradeoff table.

Option Correctness Complexity Notes
Monotone RecordStatus/pending (locked) Trivial to prove assemble_snapshot fires exactly once (I5) O(1) transition checks No retry path if a marker is lost — pairs with T10/RB-01 timeout handling
Retractable status (allow Done → Recording) Requires re-deriving completion each poll Higher — must re-validate invariants on every retraction Would let a duplicate/stale marker "un-complete" a channel — direct violation of I3

Operational implication. Any code path that would set a channel back to NotStarted or Recording after Done, or re-insert a process into pending after mark_done, is a bug by construction — the type should make it unrepresentable (RecordStatus::Done carries no further transition in the match arms, §8.2).

Violation consequence. A non-monotone implementation can double-assemble a GlobalSnapshot (violates I5) or reopen a channel-recording window after in-flight messages were already sealed, silently corrupting channel_states.

Cross-references. Enforced by I5; implemented in §8.2 (RecordStatus state machine) and §11.10 (CompletionDetector); exercised in Phase 9 (single snapshot) and Phase 11 (concurrent snapshots, one monotone tracker per SnapshotId).

P12. Verification Is a Separate, Mechanized Pass — Not an Inline Assertion

Statement. Consistent-cut correctness (I1) is never asserted inline during protocol execution; it is checked after the fact by cl-verify, a dedicated pass over the completed GlobalSnapshot and the VectorClock-annotated event history.

Formal grounding. Chandy & Lamport's original proof is a post-hoc argument about the algorithm's output, not a runtime guard the algorithm itself executes. Mirroring that structure, cl-snapshot runs the marker rules with zero knowledge of cl-verify; the two crates are dependency-ordered (§4.3: cl-recorder does not depend on cl-verify) so an inline check is structurally impossible even if attempted.

Operational implication. This separation means: (a) the protocol's hot path pays zero verification overhead — markers flood at wire speed; (b) cl-verify can be run zero, one, or many times against the same recorded artifacts (GlobalSnapshot + EventLog) without re-executing the simulation, which is exactly what the Phase 14 conformance harness and cl-cli verify --replay (Testing & Verification Strategy) depend on; (c) a verification bug can never mask itself by also corrupting the thing it's checking, because the checker never touches protocol state.

Violation consequence. Inlining causal checks into cl-snapshot would couple the marker-receiving rule to cl-verify's internal representation (Cut, VectorClock comparison), forcing every protocol change to also touch the verifier, and would make it impossible to run verification as an independent, replayable audit step — exactly the workflow Testing & Verification Strategy's deterministic replay testing relies on.

Cross-references. Enforced structurally by the crate dependency graph (§4.3, ADR-11); the check itself is I1, run in Phase 10 (cl-verify) against artifacts from Phase 9 (cl-recorder) and Phase 4 (cl-sim event log).

Detailed Invariant Specifications

I1 — Consistent Cut

  • Statement. For every receive event r = Receive(c, m) in the cut, either (a) the matching send s = Send(c, m) is also in the cut, or (b) m appears in GlobalSnapshot.channel_states[c]. No effect precedes its cause across the cut boundary.
  • Why it matters. Foundation of all stable-property detection; without causal closure, any property verdict is unsound.
  • Where enforced. cl-verify verify_cut(history: &[Event], snapshot: &GlobalSnapshot) -> Result<(), CutViolation>; VectorClock attached to every Event in cl-core.
  • Detection. For each Receive(c, m) in cut: find matching Send(c, m) in history; check sender's VectorClock[sender] at send-time ≤ receiver's VectorClock[sender] at first-marker time. Fail if not.
  • Telemetry. snapshot_consistency_failures_total{snapshot_id} counter; log the offending (send-event, receive-event) pair with their vector clocks.
  • Recovery. No automatic repair; discard the snapshot; initiate a new snapshot.
  • Debugging. Dump full Event history with per-event VectorClock; locate receive whose send has a higher clock component than the receiver's first-marker clock; trace to recording-window boundary error (likely I4 or I3 violation upstream).

I2 — FIFO Preservation

  • Statement. For every channel c = (from, to), if Send(c, m1) precedes Send(c, m2) in the event history, then Receive(c, m1) precedes Receive(c, m2); markers obey the same ordering.
  • Why it matters. The consistent-cut proof (P1, P3) depends on markers never overtaking earlier app messages.
  • Where enforced. cl-channel: per-channel send-sequence counter + receive-sequence assertion; cl-transport: delivery queue is FIFO per channel in cl-sim.
  • Detection. cl-channel asserts recv_seq == expected_seq on each dequeue; mismatch → ChannelError::OutOfOrder { channel_id, expected, got }.
  • Telemetry. channel_ooo_deliveries_total{channel_id} — must be zero in all runs except the Phase 14 negative test.
  • Recovery. Reject the out-of-order delivery; surface error; simulator marks the run as invalid (for the negative test, this is the expected outcome).
  • Debugging. Compare send-event sequence vs. receive-event sequence for the channel in the Event history; the position of the inversion identifies the delivery that broke order.

I3 — Marker-Once

  • Statement. For each process p and SnapshotId s, per_snapshot_state[s].local_state is written exactly once — at the first-marker event for s.
  • Why it matters. Double-recording advances the process cut component, breaking I1.
  • Where enforced. cl-snapshot: if per_snapshot_state[s].local_state.is_some() { skip recording } guard; debug-assert panics on second write attempt.
  • Detection. Debug build: assert!(per_snapshot_state[s].local_state.is_none(), "double-record for sid={s} at pid={p}"). Release build: skip silently, emit counter.
  • Telemetry. snapshot_local_state_records_total{process_id, snapshot_id} — must equal 1 at snapshot completion; >1 is a bug.
  • Recovery. Idempotent guard prevents corruption; but the snapshot must be discarded if double-record was not caught, as the local state may be inconsistent.
  • Debugging. Grep Event history for all first-marker events for (p, s); more than one indicates the initiator path and the receiver path are both recording, pointing to a missing is_initiator guard.

I4 — Channel-Recording Correctness

  • Statement. GlobalSnapshot.channel_states[c] = {app messages m received on c after receiver's first-marker time AND before c's own marker arrives}.
  • Why it matters. Gap (under-count) loses in-flight value; over-count (includes post-snapshot messages) double-counts; both break I6 and I1.
  • Where enforced. cl-snapshot: accumulate in channel_msgs[c] only while RecordStatus[c] == Recording; set Done on Marker(s) from c.
  • Detection. cl-verify cross-references recorded channel_msgs against Event history: every recorded message must have a Send event with sender's VectorClock[sender] ≤ sender's first-marker clock, AND a Receive event with receiver's VectorClock[receiver] ≥ receiver's first-marker clock.
  • Telemetry. snapshot_channel_msgs_recorded_total{channel_id, snapshot_id} gauge; mismatch between recorded count and expected count from Event history is a bug metric.
  • Recovery. No repair; discard snapshot; reinitiate.
  • Debugging. Diff the set of Receive(c, *) events between receiver's first-marker time and c's marker arrival against channel_states[c]; any element in the diff is a recording-window boundary error.

I5 — Completeness

  • Statement. GlobalSnapshot is assembled only after every process has RecordStatus == Done for all incoming channels for SnapshotId s.
  • Why it matters. Premature assembly produces a partial snapshot with missing process states or channel states; all downstream detectors give wrong results.
  • Where enforced. cl-recorder: assemble() returns Err(Incomplete) unless all (process, channel) RecordStatus entries are Done.
  • Detection. cl-recorder polls or awaits a CompletionSignal from each process; assemble() is callable only from the AllDone state.
  • Telemetry. snapshot_processes_complete{snapshot_id} gauge (increments as each process completes); snapshot_completion_time_ms histogram.
  • Recovery. Wait; I10 guarantees completion under reliable delivery. Timeout + reinitiate if a process is stuck.
  • Debugging. Identify which (process, channel) pairs have RecordStatus != Done; trace whether their markers were enqueued in cl-transport; a missing enqueue means the sending process never received its first marker.

I6 — Conservation

  • Statement. For a conserved quantity Q: sum(GlobalSnapshot.process_states[p].Q for all p) + sum(len(GlobalSnapshot.channel_states[c]) * unit_value for all c) == initial_Q.
  • Why it matters. Conservation violations expose snapshot correctness bugs; they are the primary oracle for cl-app tests.
  • Where enforced. cl-detect check_conservation(snapshot: &GlobalSnapshot, inv: &ConservationInvariant) -> Result<(), ConservationViolation>.
  • Detection. actual = sum_process_states + sum_channel_states; expected = initial_value; delta = actual - expected; fail if delta != 0.
  • Telemetry. snapshot_conservation_delta{application, snapshot_id} gauge — must be 0; histogram of delta values over fuzz runs.
  • Recovery. Delta ≠ 0 indicates I1 or I4 violation upstream; discard snapshot; run cl-verify to locate the cause.
  • Debugging. Dump per-process state quantities and per-channel message lists; compute partial sums to locate the process or channel contributing the delta.

I7 — Stable-Property Soundness

  • Statement. If cl-detect reports StableProperty::Terminated (or Deadlocked, or Conserved) for snapshot s, the same property holds in the real execution at all states reachable from s.
  • Why it matters. False-positive termination/deadlock detection causes operators to kill live systems; false-negative misses real deadlocks.
  • Where enforced. cl-detect: StableProperty enum is closed; only monotone predicates enumerated; type-level enforcement.
  • Detection. Phase 12 test: after cl-detect reports Terminated, run cl-sim for 100 more steps — no new events should be generated; any event is a soundness violation.
  • Telemetry. stable_property_detections_total{property, snapshot_id}; false_positive_detections_total (should always be 0 by construction).
  • Recovery. Soundness is a design-time guarantee; runtime recovery = re-run cl-verify to confirm the snapshot is consistent before trusting cl-detect output.
  • Debugging. If a detection is suspect: confirm I1 holds for the snapshot (cl-verify); confirm the property definition is genuinely stable (not just transiently true); add a continuation-run test.

I8 — Concurrent-Snapshot Non-Interference

  • Statement. For distinct SnapshotIds s1 and s2, per_snapshot_state[s1] and per_snapshot_state[s2] are fully independent; a marker for s1 does not affect recording state for s2 and vice versa.
  • Why it matters. Cross-contamination produces mixed cuts that belong to neither snapshot; both cl-verify checks fail.
  • Where enforced. cl-snapshot: BTreeMap<SnapshotId, SnapshotState> per process; every recording-state lookup is keyed by SnapshotId.
  • Detection. Phase 11 test: two concurrent snapshots, both pass cl-verify; any state sharing causes at least one to fail.
  • Telemetry. snapshot_active_count gauge; per-snapshot snapshot_completion_time_ms histogram; diverging completion times for concurrent snapshots indicate interference.
  • Recovery. Structural: per-SnapshotId keying prevents runtime contamination; if detected, indicates a code-level merge of state maps (review required).
  • Debugging. If one snapshot fails only when another is concurrent: trace which SnapshotId wrote to the failing snapshot's channel_msgs; grep cl-snapshot for any access to channel_msgs without a SnapshotId key lookup.

I9 — Reproducibility

  • Statement. Given the same scheduler seed, initial topology, and process logic, the Event history, GlobalSnapshot, and cl-verify verdict are bit-for-bit identical across runs.
  • Why it matters. Reproducibility is the foundation of testing a concurrent protocol; without it, any correctness bug is a heisenbug.
  • Where enforced. cl-sim: deterministic PRNG (seeded SmallRng); DeliverySchedule is a pure function; BTreeMap (not HashMap) everywhere in cl-sim and cl-verify to eliminate iteration-order non-determinism.
  • Detection. Property-based test: run same seed twice; hash Event logs; assert equal. Run in CI on every PR.
  • Telemetry. simulation_seed logged at INFO level at run start; simulation_events_total counter for cross-run comparison.
  • Recovery. If non-determinism detected: audit for HashMap usage, wall-clock reads, or unordered iteration in cl-sim, cl-snapshot, cl-recorder.
  • Debugging. Enable RUST_LOG=cl_sim=trace; diff two runs' event logs line-by-line; the first divergence points to the non-determinism source.

I10 — Liveness / Termination

  • Statement. Under reliable FIFO delivery and finite processes, every initiated snapshot terminates in O(diameter × max_channel_depth) event steps.
  • Why it matters. Without termination, GlobalSnapshot is never assembled; stable-property detection never runs; checkpointing never completes.
  • Where enforced. cl-sim: no message drops; cl-transport: delivery is deterministic and complete; P7 is the design-level guarantee.
  • Detection. Phase 14 liveness test: for 1000 random seeds and topologies up to 16 processes, every snapshot completes; test fails with seed logged if any snapshot does not complete within bound = n_processes * n_channels * 10 steps.
  • Telemetry. snapshot_termination_steps{snapshot_id} histogram; p99 latency alert.
  • Recovery. Production: marker retransmit timer (exponential backoff) in cl-transport; simulation: assert no dropped markers; liveness failure in tests = delivery bug in cl-transport.
  • Debugging. Find which (process, channel) RecordStatus pair is stuck in Recording; trace backwards to whether that channel's marker was ever enqueued in cl-transport; a missing enqueue means the flooding process never received its first marker on an incoming channel — trace the flooding wave from the initiator.

8.2 Process State Machine

Each process P, per snapshot s, tracks RecordStatus for every incoming channel.

State labels: NS=NotStarted, REC=Recording, DONE=Done
Transitions per channel c ∈ incoming(P):

  GLOBAL process-recording phase for (P, s):
    IDLE ──[first Marker(s) on any c']──> ACTIVE
    ACTIVE ──[Marker(s) on c]──> DONE_c   (channel c finishes)
    ACTIVE ──[App msg on c while REC]──> ACTIVE (enqueue to channel_msgs[c])

Per-channel RecordStatus state machine:
  NS ──[first Marker(s) received by P on any channel]──> REC (start recording c unless c was marker channel)
  NS ──[Marker(s) arrives on THIS channel AND it is the first marker]──> DONE (channel c is empty: no in-flight)
  REC ──[App msg received on c]──> REC (append msg to SnapshotState.channel_msgs[c])
  REC ──[Marker(s) arrives on c]──> DONE
  DONE ──[]──> DONE (terminal; no messages from c accepted into recording)

8.3 Message Grammar (EBNF)

channel-stream  ::= message*
message         ::= app-message | marker-message
app-message     ::= APP_TAG payload-bytes
marker-message  ::= MARKER_TAG snapshot-id
snapshot-id     ::= uint32 uint64       (* initiator.id, seq *)
payload-bytes   ::= length-prefixed-bytes
APP_TAG         ::= 0x01
MARKER_TAG      ::= 0x02

Wire layout (little-endian, fixed header):

Bytes  0     : tag (u8)         — 0x01=App, 0x02=Marker
Bytes  1–4   : sender ProcessId (u32)
Bytes  5–8   : seq_no (u32)     — per-channel monotone send counter (FIFO proof)
--- App message ---
Bytes  9–12  : payload_len (u32)
Bytes 13..   : payload (opaque)
--- Marker message ---
Bytes  9–12  : initiator ProcessId (u32)
Bytes 13–20  : snapshot seq (u64)

FIFO invariant (I2): seq_no must be exactly prev_seq_no + 1 on delivery; out-of-order detected and rejected.

8.4 Channel Model

Channel(c: ChannelId):
  queue: VecDeque<(seq_no: u32, msg: Message)>  — ordered, reliable
  next_send: u32                                 — monotone counter
  next_recv: u32                                 — expected seq_no

send(m):    enqueue (next_send++, m)
deliver():  pop front if non-empty; assert seq_no == next_recv++

Invariant I2 enforcement: if delivered seq_no != next_recv, channel is corrupt — panic in simulator, emit error in real transport.

8.5 Snapshot Assembly Model

GlobalSnapshot:
  snapshot_id   : SnapshotId
  process_states: BTreeMap<ProcessId, AppState>        — state at first marker per process
  channel_states: BTreeMap<ChannelId, Vec<AppPayload>> — in-flight pre-snapshot messages
  completed_at  : EventIndex                           — simulator time when last process finished

Assembly sequence:
  1. Each process P contributes: (P, SnapshotState.local_state_at_first_marker)
  2. Each channel c contributes: (c, SnapshotState.channel_msgs[c])
  3. Recorder waits for all |processes| completion events before sealing GlobalSnapshot
  4. Sealed snapshot is immutable; hash-stamped for integrity

8.6 Vector Clock Attachment and Cut Derivation

Each Event carries a VectorClock snapshot at time of occurrence:

Event { kind: EventKind, vc: VectorClock, process: ProcessId, channel: Option<ChannelId> }
EventKind ::= Send(ChannelId, Message) | Receive(ChannelId, Message) | Internal

Cut derivation from event history:

Cut[P] = index of last event included in snapshot for process P
       = index of the FIRST marker receipt event for P (for snapshot s)

Cut consistency predicate (I1):

∀ Receive(c, m) ∈ cut:  ∃ Send(c, m) ∈ cut  OR  m ∈ channel_states[c]
∀ Send(c, m) ∉ cut AND Send(c, m) happened-before cut[receiver]:  m ∈ channel_states[c]

VectorClock happened-before: vc_a < vc_b iff ∀p: vc_a[p] <= vc_b[p] and ∃p: vc_a[p] < vc_b[p].

8.7 Concurrent Snapshot Isolation

Per-process runtime recording map keyed by SnapshotId:

ProcessState.recordings: HashMap<SnapshotId, PerSnapshotRecord>
PerSnapshotRecord:
  local_state     : AppState                          — captured at first marker
  channel_status  : HashMap<ChannelId, RecordStatus>
  channel_msgs    : HashMap<ChannelId, Vec<AppPayload>>

Isolation invariant (I8): operations on recordings[s1] never access recordings[s2] for s1 ≠ s2. Markers carry their SnapshotId; dispatch is keyed strictly by id.

Suppose channel c01 delivers Marker(s0) BEFORE the App(token) it preceded (FIFO broken):

Step A: c01 delivers Marker(s0) to P1 first (out of order)
        → P1 records local_state={token=0} (token not yet arrived)
        → RecordStatus[c01]=DONE; channel_msgs[c01]=[]
Step B: c01 delivers App(token) to P1: P1.token=1 (after snapshot recorded)
        → not in recording window (c01 is DONE); not in channel_states

Result in GlobalSnapshot s0:
  process_states: {P0: {token=0}, P1: {token=0}, P2: {token=0}}
  channel_states: all empty
  total tokens = 0 ≠ 1  → conservation violated; snapshot is NOT consistent

cl-verify detects: a Send(c01, App(token)) appears before P0's cut index,
  but Receive(c01, App(token)) appears after P1's cut index,
  and App(token) is absent from channel_states[c01] → I1 violated.
cl-verify emits: CutInconsistency { channel: c01, missing_msg: token }

This is the Phase 14 negative test: FIFO-violation mode in cl-sim triggers exactly this path.

8.13 Scheduling Semantics (cl-sim)

DeliverySchedule: Vec<(ChannelId, send_index: u32)>
  — generated from seed via seeded PRNG (ChaCha8Rng)
  — each step: select a non-empty channel uniformly at random (weighted or unweighted)
  — deliver its head message (FIFO respected: always head of queue)
  — interleaved with process internal steps and snapshot initiations
  — snapshot initiation injected at configurable step offsets (or random from seed)
  — event log records chosen steps for full reproducibility (I9)

Invariant: scheduler never skips past a channel's head (FIFO preserved by construction).

8.14 AppState and Conservation Invariant

AppState (token ring):    { tokens: u32 }
AppState (bank transfer): { balance: i64 }

Conservation check:
  token ring:    Σ process_states[P].tokens + Σ |channel_states[c]| * token_value == N_tokens_initial
  bank transfer: Σ process_states[P].balance + Σ channel_states[c].iter().sum() == total_initial

cl-detect evaluates this over GlobalSnapshot without re-running any process logic.

8.21 Transport Delivery Semantics

cl-transport delivery contract (simulated mode):
  1. Scheduler calls: transport.deliver_next(channel_id) -> Option<Message>
  2. Transport pops head of channel_id.queue (FIFO)
  3. Calls target_process.on_receive(channel_id, message)
  4. on_receive dispatches:
       Message::App(p)    -> app_handler(p); Event::Receive logged
       Message::Marker(s) -> cl-snapshot.handle_marker(process, s, channel_id)
  5. All side effects (state mutations, marker sends) complete before scheduler
     selects the next delivery step (single-threaded sim: no interleaving within a step)

Real transport (cl-transport network backend, future):
  - TCP streams per channel; seq_no header enforces FIFO at receiver
  - Out-of-order: buffer and re-order up to MAX_REORDER_BUFFER (default 64 msgs)
  - Loss: not modelled (reliable delivery is a precondition of Chandy-Lamport; P3/P7)

8.22 Snapshot Completion Detection

completion_detector for snapshot s:
  pending: BTreeSet<ProcessId>  — initialized to all processes at initiation
  on process P signals COMPLETE for s:
    pending.remove(P)
    if pending.is_empty():
      recorder.assemble_and_seal(s)
      emit Event { tag: SnapshotComplete, snapshot_id: s }

Invariant I5: recorder.assemble_and_seal called exactly once per s.
Race-free in simulator: single-threaded; in multi-threaded transport, guarded by Mutex<CompletionDetector>.

Phase 2 — FIFO channel abstraction

2.1 Objectives

  • Implement cl-channel: a directed, reliable, order-preserving unidirectional channel between two processes.
  • Guarantee: a message enqueued before another is dequeued before it — the FIFO precondition that Chandy-Lamport depends on (P3, I2).

  • Expose explicit enqueue / dequeue / peek interface; no async, no threads — delivery is driven externally by cl-sim.
  • Track per-channel statistics (enqueue count, dequeue count, current depth) for observability.

    pub fn send_marker(&mut self, to: ProcessId, sid: SnapshotId) -> Result<(), ProcessError>;
    pub fn receive(&mut self, channel: ChannelId, msg: Message) -> Result<(), ProcessError>;
    pub fn internal_step(&mut self) -> Result<(), ProcessError>;
    pub fn state(&self) -> &AppState;
    pub fn clock(&self) -> &VectorClock;
    pub fn log(&self) -> &EventLog;
    pub fn incoming_channels(&self) -> impl Iterator<Item = ChannelId> + '_;
    pub fn outgoing_channels(&self) -> impl Iterator<Item = ChannelId> + '_;
}
  • FifoChannelHandle is a *mut FifoChannel or an index into a channel arena; owned by the simulator (Phase 4); Process borrows a handle, does not own the channel.
  • send calls clock.increment(self.id) (VectorClock arithmetic underpins I1's causal-closure check), creates EventRecord, appends to log, then calls channel.enqueue(Message::App(payload)); send_marker follows the same clock-increment path but enqueues Message::Marker(sid) with no app callback — markers are events too.
  • receive dispatches: Message::App → clock.merge(incoming_clock); clock.increment(self.id); app.on_receive(...); Message::Marker → clock update only, then returns ReceiveOutcome::Marker(SnapshotId) for the caller (cl-sim or cl-snapshot) to dispatch — receive itself never invokes snapshot logic (clean separation preserves P2 non-blocking).
  • internal_step calls app.on_internal, increments clock, logs Event::Internal; EventLog::append grows an unbounded Vec<EventRecord> — no eviction in Phase 3 (pruning deferred to Phase 14, I9 reproducibility requires the full log until then).

AppState typed wrapper (pub struct AppState { pub raw: Vec<u8>, pub schema_version: u8 }): application logic in cl-app interprets raw; cl-process treats it as opaque bytes.

Process state machine (no snapshot) — all transitions synchronous, no blocking, no async: Idle ──internal_step──> Idle; Idle ──send(to,msg)──> Idle (channel enqueued); Idle ──receive(c,App)──> Idle (app callback fired); Idle ──receive(c,Marker)──> Idle (returns SnapshotId to caller).

3.6 Pitfalls

  • Snapshot logic leaking into cl-process: tempting to add marker-handling here; resist — returns ReceiveOutcome::Marker and stops; cl-snapshot does the state transition (P2 boundary discipline).

Phase 4 — transport + deterministic simulator

4.1 Objectives

  • Implement cl-transport: delivers Message values over cl-channel FIFO queues; pluggable backend (simulated or future real-network).
  • Implement cl-sim: seeded, deterministic scheduler that picks which pending channel to drain next; controls all delivery ordering; no hidden concurrency.
  • Event-history log: every Send, Receive, Internal event appended in causal order; consumed by cl-verify and cl-detect.
  • Constraint introduced: all non-simulator phases MUST deliver messages only through cl-transport; direct queue manipulation forbidden outside cl-channel.

4.2 Detailed Implementation Steps

cl-transport/src/lib.rs

  • Transport struct: holds references to all cl-channel::FifoChannel instances indexed by ChannelId.
  • fn deliver(&mut self, cid: ChannelId) -> Option<Message> — dequeues front of channel cid; returns None if empty; appends Event::Receive(cid, msg) to history.
  • fn send(&mut self, cid: ChannelId, msg: Message) — enqueues to channel cid; appends Event::Send(cid, msg) to history.
  • fn pending(&self) -> Vec<ChannelId> — returns all channels with at least one queued message; used by simulator to pick next step.
  • EventHistory: Vec<(u64, Event)> with monotonic step counter; snapshot-able; serializable to JSONL for replay.

cl-sim/src/lib.rs

  • DeliverySchedule seed-based construction: Rng from rand::SeedableRng (e.g. SmallRng::seed_from_u64).
  • Simulator struct: holds Transport, registered cl-process::Process instances, step counter, event log.
  • fn step(&mut self) -> SimResult — calls transport.pending(), selects index via rng.gen_range(0..pending.len()), delivers that channel, dispatches to receiving process's on_receive, logs event; returns Stepped(cid) or Idle.
  • fn run_until(&mut self, predicate: fn(&Simulator)->bool, max_steps: u64) — drives step() until predicate true or step budget exhausted.
  • fn run_steps(&mut self, n: u64) — exactly n steps.
  • Scheduler is single-threaded; "concurrency" comes from interleaving deliveries, not OS threads; this is the P9 (determinism) guarantee.
  • fn replay(&mut self, history: &EventHistory) — replays recorded delivery order exactly; used for regression.

Observability hooks

  • Each step() emits a trace line: STEP {n} deliver {from}→{to} msg={:?}.
  • EventHistory written to events.jsonl on flush(); format: {"step":N,"event":"Receive","channel":{"from":0,"to":1},"msg":"..."}.

Phase 6 — snapshot initiation + marker-sending rule

6.1 Objectives

  • Implement cl-snapshot::initiate(pid, sid, transport, process): the initiator records its own local state immediately, then sends Message::Marker(sid) on every outgoing channel before any further app message.
  • Enforce the marker-sending rule: after initiate, no app message from the initiator is delivered on any outgoing channel until all markers are enqueued (atomically from the transport's perspective within a single step).
  • Introduce SnapshotState and RecordStatus per process per SnapshotId; initiator's own channels transition to RecordStatus::Done (no need to record own outgoing channels in the CL protocol).
  • Constraint: cl-snapshot holds no application logic; it calls cl-process state-capture and cl-transport send.

6.2 Detailed Implementation Steps

cl-snapshot/src/lib.rs

  • SnapshotCoordinator: per-process struct; holds Map<SnapshotId, ProcessSnapshotRecord>.
  • ProcessSnapshotRecord: { local_state: Option<AppState>, channel_records: Map<ChannelId, RecordStatus>, recorded_msgs: Map<ChannelId, Vec<AppPayload>>, initiated: bool }.
  • fn initiate(pid: ProcessId, sid: SnapshotId, proc: &mut Process, transport: &mut Transport):
    1. Capture local_state = proc.capture_state() — atomic w.r.t. step boundary.
    2. Set initiated = true; mark all incoming channels for pid as RecordStatus::NotStarted (will transition when marker arrives — but for the initiator, own outgoing channels have no pre-snapshot messages after the marker; incoming channel recording handled in Phase 7).
    3. For each outgoing channel c from pid: call transport.send(c, Message::Marker(sid)).
    4. Append Event::Internal (snapshot-initiation) to history.
  • fn capture_state(proc: &Process) -> AppState — delegates to ProcessHandler::snapshot_state(&self) -> AppState.
  • Initiator's own RecordStatus for incoming channels: set to Recording immediately (I3: first-marker rule — the initiator treats its own initiation as seeing its "own" marker).

cl-process/src/lib.rs additions

  • ProcessHandler trait gains: fn snapshot_state(&self) -> AppState — returns serializable local state.
  • Process::capture_state_at_boundary() — callable only from within a Simulator::step() to enforce step atomicity.

Marker-sending atomicity

  • All markers for a given initiate call are enqueued to cl-transport within the same step() invocation, before the step returns; no interleaving delivery can happen between marker enqueues within one step (single-threaded scheduler guarantees this).
  • Post-initiate, the initiator's outgoing app messages are still sent via transport.send; they are enqueued after all markers; FIFO ensures markers are delivered before later app messages on each channel (P3).

cl-snapshot/src/rules.rs

  • fn marker_sending_rule(pid: ProcessId, sid: SnapshotId, outgoing: &[ChannelId], transport: &mut Transport) — enumerates outgoing channels, sends Marker(sid) on each; returns count of markers sent.
  • Called by initiate; also called by Phase 7 (first-marker receipt triggers re-flood).

7.6 Pitfalls

  • State recorded after first app message post-marker: if on_receive processes an app message before taking local_state snapshot, the cut is incorrect. Mitigation: snapshot AppState synchronously before any handler runs in same tick.
  • Outgoing marker delayed past app messages: if the process sends app messages before flooding markers, downstream processes may see app messages before the marker, violating FIFO delineation. Rule: marker injection must precede any further app sends in the tick.
  • channel_status initialized lazily: channels not yet in the map default to NotStarted; if all_incoming is stale (topology change), some channels never enter Recording. Mitigation: all_incoming slice must be authoritative topology at time of snapshot initiation.
  • Concurrent snapshot state collision: keying ProcessRecordingState by SnapshotId only — if HashMap uses default hasher and SnapshotId equality is wrong (e.g., only seq compared), distinct snapshots from same initiator collide. Use (initiator, seq) equality.
  • Marker sent on a channel not yet established: if outgoing channel set changes between initiation and first-marker receipt, send to a dropped channel panics. Guard with channel_exists(out_c).
  • Re-entrant on_marker during marker sending: if marker-send triggers immediate receipt at the same process (loopback), re-entrancy corrupts ProcessRecordingState. Ensure markers_sent = true is set before sending.

7.7 Performance Concerns

  • HashMap<SnapshotId, ProcessRecordingState> lookup: O(1) expected; SnapshotId hash must be cheap (two u32/u64 fields).
  • all_incoming.iter() for status transition: O(in-degree); typical in-degree ≤ 8; no concern.
  • Marker flood: |outgoing| sends per first marker; batch into a single Vec before dispatching to cl-transport to avoid per-send lock acquisition.
  • Clone of AppState: snapshot records a deep clone; application state must implement Clone efficiently (prefer Arc<_> for large state blobs).
  • Event log append: amortized O(1) with Vec; pre-allocate 64-entry capacity per process.

7.8 Edge Cases

  • Process with zero incoming channels: never receives a marker; it only initiates. handle_first_marker never called — handled in Phase 9 completion detection.
  • Process with zero outgoing channels: handle_first_marker sends no markers; downstream processes never receive markers from it (fine; they receive from other paths).
  • Marker from a channel not in the known topology: return Err(UnknownChannel) — do not crash.
  • AppState clone mid-application-transition: if AppState is in a partially updated state when the marker arrives, the snapshot captures an inconsistent app state. Application must provide snapshot_local_state() which returns a linearizable snapshot (e.g., locks a mutex briefly, then releases).
  • First marker arrives before process learns it is a snapshot participant: coordinator must lazily initialize ProcessRecordingState on first marker arrival.

Phase 10 — Consistency Verification

10.1 Objectives

  • Implement cl-verify: prove a GlobalSnapshot is a consistent cut per I1 and P1. Causal closure check: every message receive in the cut has its matching send in the cut, or the message is captured as channel (in-flight) state; anti-violation check: no message sent strictly after the cut boundary is received before the cut.
  • Attach VectorClock to each Event in the run history (EventLog) during simulation; use those clocks to establish happens-before order across processes. Scope covers App messages only — Marker messages are control messages, excluded from causal-closure checks.
  • Output VerificationResult — Consistent or Inconsistent(Vec<CutViolation>); cl-verify is entirely read-only over GlobalSnapshot + EventLog (zero mutation of snapshot state).
  • Dependency: Phase 9 (GlobalSnapshot assembled); Phase 4 (EventLog with vector-clock annotation from cl-sim). Verification is the correctness oracle for the entire cl-snapshot protocol — if cl-verify reports Consistent, I1 and P1 hold for that snapshot.

10.2 Detailed Implementation Steps

Module layout (cl-verify/src/): lib.rs — public API verify(), VerificationResult, CutViolation; cut.rs — Cut derivation, cut_index(log, pid) -> usize; causal.rs — message matching via HashMap<(ChannelId, SeqNo), EventRef>; clock.rs — VectorClock attachment pass over EventLog; report.rs — VerificationReport (summary + per-violation detail).

Types (cl-core/cl-verify): CutViolation { channel, payload, send_vc, recv_vc, kind: ViolationKind }; ViolationKind { ReceiveWithoutMatchingSend, PostCutSendReceivedInCut }; VerificationResult { Consistent, Inconsistent(Vec<CutViolation>) }; VerificationReport { result, cut_frontier: Cut, events_checked: usize, elapsed_us: u64 }.

VectorClock attachment (clock.rs, I1 groundwork): input is the raw EventLog (ordered by simulator delivery step, no clocks yet); algorithm keeps per-process vc: [u64; N] — on Send(c,m) at p: increment vc[p], attach clone; on Receive(c,m) at q from p: merge vc = max(vc, sender_vc_at_send), increment vc[q], attach clone; on Internal at p: increment vc[p]. Output is AnnotatedLog: Vec<(ProcessId, Event, VectorClock)>; called once before verify(), idempotent if the log already has clocks.

Cut derivation (cut.rs): cut_index(log, pid) -> EventIdx is the index of the first Receive(_, Marker(sid)) or Internal(Initiate(sid)) event at pid; Cut: HashMap<ProcessId, EventIdx> is the frontier (C[p] = local event count at snapshot moment); in_cut(event_idx, pid, cut) -> bool is event_idx <= cut[pid]; cut_vc(pid, annotated_log, cut) -> VectorClock is the clock attached to the event at cut[pid].

Message matching (causal.rs): index all Send(c, App(payload, seq)) events as HashMap<(ChannelId, SeqNo), &AnnotatedEvent> — AppPayload carries a seq: u64 field (monotonic per channel, added in Phase 4) to guarantee unique match keys; for each Receive(c, App(payload, seq)) event at q in the cut, look up (c, seq) in the send index.

Core algorithm — verify(snapshot, annotated_log, cut) -> VerificationResult (implements I1's consistent-cut predicate, P1):

  1. For each Receive(c, App(p, seq)) event e at q where in_cut(e.idx, q, cut): a. Look up matching Send(c, App(p, seq)) event s at sender r. b. If in_cut(s.idx, r, cut) → consistent for this message (send also in cut). c. Else if payload appears in snapshot.channel_states[c] → in-flight; consistent. d. Else → append CutViolation { kind: ReceiveWithoutMatchingSend, ... }.
  2. For each Send(c, App(p, seq)) event s at r where !in_cut(s.idx, r, cut) (sent after cut): a. Locate matching Receive(c, App(p, seq)) event e at q. b. If in_cut(e.idx, q, cut) → append CutViolation { kind: PostCutSendReceivedInCut, ... }.
  3. Return Consistent iff violations list is empty; else Inconsistent(violations).
  4. Marker messages (Message::Marker) are excluded from causal-closure checks in both steps.

11.1 Objectives

11.2 Detailed Implementation Steps

State refactoring in cl-process/cl-snapshot (I8 isolation): Phase 9's single-snapshot ProcessState { local: AppState, recording: Map<ChannelId, RecordStatus>, recorded: SnapshotState } becomes ProcessState { local: AppState, snapshots: HashMap<SnapshotId, PerSnapshotState> } where PerSnapshotState { recording: HashMap<ChannelId, RecordStatus>, recorded: SnapshotState } — one full recording record per concurrently active SnapshotId.

cl-snapshot protocol changes (P10, I8): initiate(pid, sid) asserts pid.snapshots does not already contain sid, inserts a fresh PerSnapshotState, clones pid.local into pss.recorded.local_state_at_first_marker, sends Marker(sid) on every outgoing channel (unchanged from Phase 6), and marks all incoming channels NotStarted for sid. on_receive(Marker(sid), c, p) looks up entry = p.snapshots.entry(sid).or_insert_with(PerSnapshotState::default): if this is the first marker for sid at p (all channels NotStarted), clone p.local into entry.recorded.local_state_at_first_marker, set entry.recording[c] = Done, set all other incoming channels to Recording, and send Marker(sid) on all outgoing; otherwise just set entry.recording[c] = Done — with no access to any p.snapshots[other_sid] in either branch. record_app_message(msg, c, p) (on every Receive(c, App(msg))) appends msg to pss.recorded.channel_msgs[c] for every (sid, pss) in p.snapshots where pss.recording[c] == Recording — a single incoming message may be appended to multiple PerSnapshotState entries, and iteration order over p.snapshots is immaterial since each entry is independent.

Completion detection refactoring (cl-recorder): RecorderState { snapshots: HashMap<SnapshotId, AssemblyState> } where AssemblyState { per_process: HashMap<ProcessId, Option<SnapshotState>>, status: AssemblyStatus { InProgress, Complete(GlobalSnapshot) } }; notify_process_done(sid, pid, state) sets per_process[pid] = Some(state), is_complete(sid) is true when all entries are Some, and on completion the recorder assembles GlobalSnapshot(sid), transitions to Complete, and emits it — each sid completes independently and cl-cli prints results as they arrive.

Simulator extension (cl-sim/src/concurrent_gen.rs): concurrent_snapshot_schedule(n_snapshots, offset_steps, seed) -> DeliverySchedule injects n_snapshots initiation events at delivery steps 0, offset_steps, 2×offset_steps, … — offset_steps = 0 means all initiated at the same step, offset_steps = N staggers them, and offset_steps = u64::MAX (no second snapshot) preserves single-snapshot behavior as a regression check.

cl-cli snapshot --concurrent N --offset K --seed S: runs the simulation, initiates N snapshots at offset K, and reports all GlobalSnapshot outputs; --list-active prints currently in-progress SnapshotIds at each scheduler step (debug mode).

Phase 12 — Stable-Property Detection

12.1 Objectives

  • Implement cl-detect: evaluate StableProperty variants over a GlobalSnapshot (I7, P8) — Terminated (all processes idle AND all channels empty: necessary and sufficient for real termination after the cut), Deadlocked (a wait-for cycle exists: sufficient for real deadlock, and stable once true), and Conserved(invariant) (a user-supplied invariant holds over process states plus in-flight channel messages).
  • Soundness guarantee (I7, P8): a stable property true in a consistent snapshot remains true in the actual execution after the cut; completeness note: detection is sound (true positive = real property) but not complete (a stable property may hold in the real system without holding in a given snapshot taken before it became stable). Termination detection requires a consistent snapshot specifically — an inconsistent snapshot could report false termination.
  • Wait-for graph captures only direct blocking relationships; transitive deadlock (p waits for q waits for r) is resolved by DFS cycle detection, not manual transitive closure. Constraint: detection is entirely read-only over GlobalSnapshot — no mutation, no I/O.
  • Dependency: Phase 9 (GlobalSnapshot assembled and verified consistent by Phase 10).

12.2 Detailed Implementation Steps

Module layout (cl-detect/src/): lib.rs — detect_all(), detect_one(), DetectionResult, StableProperty; termination.rs — detect_termination(snapshot) -> DetectionResult; deadlock.rs — detect_deadlock(snapshot) -> DetectionResult, WaitForGraph; conservation.rs — ConservationInvariant trait, TokenConservation, MoneyConservation; report.rs — DetectionReport (per-property result + elapsed_us).

Core types: StableProperty { Terminated, Deadlocked, Conserved(Box<dyn ConservationInvariant + Send + Sync>) }; DetectionResult { Holds, DoesNotHold, Inconclusive { reason: String } }; ConservationInvariant trait with fn check(&self, snapshot: &GlobalSnapshot) -> DetectionResult and fn name(&self) -> &'static str; DetectionReport { property, result, elapsed_us: u64 }.

Termination (termination.rs, I7/P8): detect_termination(snapshot) -> DetectionResult returns Holds iff condition A (∀ pid: process_states[pid].is_idle()) AND condition B (∀ cid: channel_states[cid].is_empty()), else DoesNotHold. is_idle() is an AppState method (token ring: tokens_held == 0 && no_pending_send; bank: no_pending_transfer); condition B is mandatory — idle processes with non-empty channels is NOT terminated.

Deadlock (deadlock.rs, P8): build wait-for graph G=(V,E) with V = {ProcessId} and edge p → q where process_states[p].wait_for() == Some(q) (an AppState method returning Some(q) iff definitively blocked awaiting q); self-loops (p → p) excluded from E and logged as AppBug. Iterative DFS with a [White, Gray, Black] color array detects cycles in O(V+E); WaitForGraph { nodes, edges, cycles } is exposed for diagnostics, and the result is Holds (deadlocked) iff cycles is non-empty.

Conservation (conservation.rs, I6): TokenConservation { initial_tokens: u64 } sums process_states[p].token_count() over all p plus channel_states[c].len() over all c (each in-flight message is one token) and compares to initial_tokens; MoneyConservation { initial_total: i64 } sums process_states[p].balance() plus msg.amount() over all in-flight messages and compares to initial_total — both return Holds if equal, DoesNotHold { found, expected } otherwise, using checked_add throughout (integer-only, no floating point).

AppState trait additions (cl-core/cl-app): fn is_idle(&self) -> bool, fn wait_for(&self) -> Option<ProcessId> (None if not blocked), fn token_count(&self) -> u64 (0 if not token-ring), fn balance(&self) -> i64 (0 if not bank).

detect_all(snapshot, properties) -> Vec<DetectionReport>: runs all requested detectors — each is independent and can run without sequencing — returning one DetectionReport per property.

Integration in cl-cli: cl-cli detect --property terminated|deadlocked|conserved=tokens|conserved=money --snapshot <file>, with --all running all three detectors; prints per-property result and exits with the code shown in the table below.

12.7 Performance Concerns

  • Wait-for graph DFS: O(V + E), at most n_processes nodes and n_processes² edges, < 1 ms for n ≤ 1000; conservation sum is O(n_processes + n_channels), a single linear pass with no allocation beyond the accumulator.
  • In-flight message sum iterates channel_states.values() once, avoiding an intermediate Vec; ConservationInvariant trait-object dispatch is one virtual call per check(), negligible overhead.
  • Snapshot deserialization dominates for large snapshots (> 10k channel-state messages) — deserialize once and share Arc<GlobalSnapshot>; avoid per-call heap allocation in WaitForGraph by reusing the node-color array via vec![White; n].
  • detect_all parallelism: termination, deadlock, and conservation checks are independent, so rayon::join applies; for n > 100 processes, early-exit the termination check on the first non-idle process or non-empty channel rather than a full scan.
  • AppState::is_idle and AppState::wait_for must be O(1) by contract; slow implementations break the latency SLA.

12.8 Edge Cases

  • Single-process system: no channels; termination = is_idle(p0) only; deadlock impossible (no wait-for edges); conservation trivial (no channel state to sum). Snapshot with zero processes: all three detectors return Holds trivially (degenerate case; do not assert on empty process set).
  • All processes idle but one channel non-empty: Terminated: DoesNotHold; conservation may still hold since messages are still in-flight. Partial wait-for graph (some wait_for() return None): acyclic sub-graph, DoesNotHold unless a cycle exists among the Some entries.
  • wait_for returns a ProcessId not in the snapshot: log warning UnknownWaitTarget, treat as no edge (not deadlock evidence). Multiple disjoint wait-for cycles: detect_deadlock reports all cycles in WaitForGraph::cycles with Holds and the full cycle list.
  • token_count() returns u64::MAX, or balances go negative (debt transfers): checked_add can overflow/underflow u64/i64 — use a u128/i128 accumulator as fallback, returning Inconclusive { reason: "overflow in conservation sum" } only if that still fails.
  • Conservation check on concurrent-snapshot output: each GlobalSnapshot checked independently; totals differ only if snapshots capture different in-flight sets (both correct if consistent). Deadlock check on a terminated system: Terminated: Holds and Deadlocked: DoesNotHold both expected — termination implies no blocking waits.

  • Metrics: cl_detection_result_total{property, result} counter (Holds on termination or deadlock triggers alert), cl_detection_duration_us{property} histogram (termination p99 < 1 ms, deadlock p99 < 2 ms), cl_wait_for_graph_edges{snapshot_id} gauge (> n_processes² edges is a bug), cl_conservation_delta{property, snapshot_id} gauge (0 = holds, non-zero = violation magnitude).

Tracing Strategy

  • Span per snapshot lifecycle: snapshot.initiate → snapshot.marker_sent (per channel) → snapshot.first_marker_received (per process) → snapshot.channel_done (per channel) → snapshot.complete.
  • Span per cl-sim delivery step: sim.deliver { channel_id, msg_type, step }.
  • Span per cl-verify run: verify.check_cut { snapshot_id, n_processes, n_channels, result }.
  • Span per cl-detect evaluation: detect.evaluate { snapshot_id, property, result }.
  • Trace context: propagate SnapshotId and seed as baggage across all spans.
  • Backend: tracing crate with tracing-subscriber; OTLP exporter for real deployments; in-memory ring for simulator runs.

Structured Logging

  • Format: JSON lines with fields { ts, level, crate, snapshot_id, process_id, channel_id, event, msg }.

Alerting Philosophy

  • Alert on invariant breach immediately (FIFO violation, inconsistent cut, conservation failure): these are always bugs, never noise.

Incident Response

  1. Triage: identify snapshot_id from alert; pull structured log for that snapshot_id.
  2. Isolate: determine failure class from symptoms table (Failure Modes section); check fifo_violation_count first.
  3. Reproduce: extract seed from log; re-run cl-cli run --seed <seed> --snapshot; confirm determinism (I9).
  4. Root cause: attach cl-sim event history and GlobalSnapshot dump to incident ticket.
  5. Mitigate: abort affected SnapshotId; if live system, gate further snapshots until fix deployed.
  6. Post-mortem: add failing seed as regression fixture; extend Phase 14 conformance suite.

Backup and Trace Management

  • GlobalSnapshot files: length-prefixed, CRC32-protected binary blobs; retain last 100 snapshots per run; purge older on startup.
  • Event history logs: retained for the duration of the simulation run; flushed to disk at snapshot completion; compressed (zstd) for archival.
  • Seed registry: persist seed to run mapping in a flat file (seeds.log) for regression reproducibility.
  • No distributed persistence required (simulator is single-process); backup = copying the output directory.

Deployment Topology

  • cl-cli is a single binary; no daemon; invoked as a CLI tool or in CI pipelines.
  • For real-network backend (future): cl-transport wraps a gRPC or TCP channel; each process node runs as an OS process; cl-cli acts as orchestrator.
  • Simulator mode (primary): all processes run in a single OS process under cl-sim's scheduler; no network required.

Canary, Rolling Upgrade, Rollback

  • Canary: run new binary against a fixed seed set; compare GlobalSnapshot output and cl-verify verdict with known-good baseline before promoting.
  • Rolling upgrade (multi-process real-network mode): upgrade one process node at a time; snapshot compatibility must hold (see Compatibility & Versioning); in-flight snapshots quiesced before node restart.
  • Rollback: revert binary; re-run from last known-good seed; GlobalSnapshot files from old version are compatible if schema version unchanged.
  • Migration: schema version bump requires a migration step; never silently drop fields.

Mental Models & First Principles

MM1 — A Consistent Cut Is a Down-Set of the Happens-Before Relation

The compressed insight: a consistent cut C is a subset of events that is causally closed — if event e is in C and e' → e (e' happened-before e), then e' is also in C. This is exactly the definition of a down-set (order ideal) in a partial order.

What it predicts: the Chandy-Lamport marker rules automatically produce a down-set. The sender records state before emitting the marker; the marker travels through the FIFO channel; the receiver records state on first marker receipt. Everything sent before the sender's recording boundary that is not yet received appears in channel state — closing the down-set.

Bug class you write without it: failing to capture a message in channel state because you stop recording too early (before the channel's own marker arrives). The resulting cut is no longer a down-set — a Receive is in the cut whose matching Send is not, violating I1.

Applied in: §6 P1, §7 I1, §8.6 (Cut derivation), Phase 10 (cl-verify algorithm).

MM2 — Markers Are Logical Barriers, Not Data

The compressed insight: a Marker message carries only a snapshot identifier and has zero application payload (P4). Its sole job is to delineate "before" from "after" on a single directed FIFO channel. All state capture is local to the receiving process.

What it predicts: because markers carry no state, the sending process does not need to wait for state assembly before forwarding. This decoupling is what makes P2 (non-blocking) possible: the marker travels independently of the state it logically separates.

Bug class you write without it: adding a payload to the Marker variant (e.g., piggybacking the sender's local state "for convenience"). This creates a dependency: the marker cannot be sent until the state is serialized, introducing latency and potentially reordering the marker relative to later application messages on the channel.

Applied in: §6 P4, §9 ADR-28 (wire format — Marker has no payload field), §11.2 (Message enum), Phase 6.

MM3 — Channel Recording Window Is Defined by Two Timestamps, Not One

The compressed insight: channel state for channel c = {messages received after the receiver's first-marker event AND before c's own marker arrives}. Both boundaries matter independently. The window opens at the receiver's first-marker time (not when recording starts globally) and closes when c's specific marker arrives (not when any marker arrives).

What it predicts: in a partially-connected graph, different incoming channels at the same process have different recording windows because their markers arrive at different times. The window for channel c1 may close long before the window for c2.

Bug class you write without it: using a single global "recording started" flag per process instead of per-channel RecordStatus. You either over-record (include messages that arrived before the window opened on some channels) or under-record (close all channels when the first marker from any channel arrives).

Applied in: §6 P6, §7 I4, §8.2 (per-channel RecordStatus state machine), Phase 8.

MM4 — Seeded Deterministic Scheduler Is the Correctness Amplifier

The compressed insight: any concurrent protocol bug is a heisenbug without reproducibility. A seeded scheduler transforms a distributed algorithm with exponentially many interleavings into a function: seed → unique interleaving → unique snapshot → unique verdict. Every failure has a fingerprint (the seed) that exactly reproduces it.

What it predicts: the conformance suite runs 10,000+ seeds cheaply because each run is a pure function with no external non-determinism. Any failing seed is a regression fixture at zero additional cost.

Bug class you write without it: using a HashMap (non-deterministic iteration order), wall-clock time, or OS-scheduled threads inside the simulator. A real bug passes 9,999 seeds, fails on seed 4213, and you cannot reproduce it.

Applied in: §6 P9, §7 I9, §8.13 (scheduling semantics), §9 ADR-07/ADR-10, Phase 4 (cl-sim), Phase 14 (conformance harness).

MM5 — Stable Properties Are Monotone-True: Detection Is Sound by Construction

The compressed insight: a stable property Φ satisfies: Φ(S) ∧ S → S' ⟹ Φ(S'). Once true, it cannot become false. Therefore if a consistent snapshot (a reachable state) satisfies Φ, then Φ holds in all future reachable states. The detection is not approximate — it is exact.

What it predicts: cl-detect never produces false positives by construction, not by testing. The type system enforces that only genuinely stable predicates are represented in the StableProperty enum. Adding a non-stable predicate (e.g., "currently idle") to the enum is a design error, not a runtime risk.

Bug class you write without it: detecting "quiescence" (momentary idleness) rather than "termination" (permanent idleness with empty channels). A quiescence detector reports the system terminated when all processes are transiently idle between bursts, causing operators to kill a live system.

Applied in: §6 P8, §7 I7, §8.8 (stable-property detection model), Phase 12 (cl-detect), Phase 12 soundness test.

MM6 — SnapshotId Keying Is the General Principle: Instance Isolation by Opaque Token

The compressed insight: every per-snapshot recording state is keyed by SnapshotId. This is an instance of a universal pattern in distributed protocols: scope mutable state to an opaque identifier that distinguishes concurrent instances of the same protocol. Raft uses term+index, Paxos uses ballot number, TCP uses (src,dst,src_port,dst_port).

What it predicts: adding a second snapshot (Phase 11) costs only a HashMap key lookup, not a protocol redesign. Any cross-SnapshotId state access is structurally impossible when the key is always required.

Bug class you write without it: using a single-instance recording state. Two concurrent snapshots (s1, s2) share the RecordStatus map; a marker for s2 closes a channel window in s1 prematurely; both snapshots fail cl-verify.

Applied in: §6 P10, §7 I8, §8.7 (concurrent snapshot isolation), §9 ADR-09, Phase 11.

MM7 — Conservation Is the End-to-End Correctness Oracle

The compressed insight: if the sum of tokens (or money) across all process states plus all channel states equals the initial count, then no messages were double-counted, dropped, or fabricated by the snapshot protocol. Conservation is a single number that aggregates the correctness of every recording window across every channel.

What it predicts: any violation of I1, I2, I4, or I5 that affects an application message will manifest as a non-zero conservation delta. You do not need to inspect individual channels to diagnose most bugs — the delta tells you immediately that something is wrong and approximately how much was lost or duplicated.

Bug class you write without it: writing a verifier that only checks vector-clock relationships but ignores message payload values. Such a verifier can return "Consistent" on a snapshot that dropped a token if the causal ordering of events happens to be preserved by accident.

Applied in: §6 P6, §7 I6, §8.14 (AppState conservation invariant), Phase 13 (cl-detect conservation), Phase 14 conformance.

MM8 — The FIFO Precondition Is Not Defensive Programming — It Is the Proof

The compressed insight: the consistent-cut theorem in Chandy & Lamport 1985 (Theorem 1) has FIFO as a hypothesis, not a convenience. Without FIFO, the marker-receiving rule produces a cut that is not necessarily a down-set. The negative test (Phase 14) demonstrates this empirically: one FIFO violation → cl-verify reports Violated.

What it predicts: any transport layer that reorders messages within a channel, even rarely, invalidates all snapshot guarantees. There is no "probably consistent" — either FIFO holds or the cut may be inconsistent.

Bug class you write without it: implementing cl-transport with a priority queue that gives markers slightly higher delivery priority than app messages "for performance." A marker overtakes the app message sent before it; the receiver records state without that message; it is absent from both process state and channel state; conservation fails.

Applied in: §6 P3, §7 I2, §8.4 (channel model FIFO proof), Phase 2 (cl-channel FIFO enforcement), Phase 14 negative test.

Apache Flink Asynchronous Barrier Snapshotting (Carbone et al. 2015): The one decision Flink made differently is the aligned barrier model: operators buffer incoming messages that arrive after a barrier from one upstream but before barriers from all other upstreams, trading throughput for simplicity. Unaligned barriers (Flink 1.11+) removed this trade-off but add complexity by including buffered messages in operator state. Flink's niche: high-throughput stateful stream processing at enterprise scale with exactly-once guarantees to external sinks.

Kafka Streams epoch-based checkpointing: Kafka's key difference is that the channel model is already durable — Kafka topics are the channels, and partition offsets serve as the channel-state boundary. There is no need to capture in-flight messages because they are already persisted in the log. This wins when the input sources are Kafka topics (extremely common) because checkpoint cost is just a metadata commit, not state serialization. The niche: Kafka-native applications where the entire data pipeline is Kafka-to-Kafka and replay from offset is always available.

Apache Spark Streaming RDD checkpointing: Spark chose to avoid the channel-recording problem entirely by representing computation as lineage — an RDD's state can always be recomputed by replaying its parent transformations from the last materialized checkpoint. This wins for batch-oriented workloads with expensive-to-materialize transformations where lineage recomputation is cheaper than snapshotting large operator state. The niche: analytics pipelines with bounded latency requirements where micro-batch processing (not continuous streaming) is acceptable and state is naturally re-derivable from inputs.

Naiad / Timely Dataflow (Murray et al. 2013): Naiad's key difference is the pointstamp progress-tracking system, which provides a finer-grained notion of consistent frontier than a single global snapshot epoch. Progress is tracked per (timestamp, edge) pair, allowing the system to know exactly which timestamps have been fully processed across all operators. Checkpointing at a consistent frontier means no in-flight message capture is needed because the frontier guarantees all messages at that timestamp have been delivered. This wins for iterative computations (graph algorithms, machine learning iterations) where a coarse global snapshot would unnecessarily stall the entire computation to wait for slow iterative loops to converge.

Alternative Architectures (Roads Not Taken)

ALT-1 — Coordinated Blocking Snapshot (Stop-the-World)

Show the original text diagram
Architecture:
  Coordinator ─── FREEZE ──> all processes (broadcast, synchronous)
  Each process: records local state + drains channel queues
  All processes ─── STATE ──> Coordinator
  Coordinator assembles GlobalSnapshot
  Coordinator ─── RESUME ──> all processes

Regime where it wins: small fixed-topology systems (n ≤ 8) where the blocking pause is acceptable (e.g., an embedded controller taking a diagnostic snapshot once per minute) and implementation simplicity is paramount. No channel recording needed; no marker protocol; trivially correct.

Real system embodying it: database LOCK TABLES + FLUSH TABLES WITH READ LOCK (MySQL/MariaDB) for a consistent backup; Linux SIGSTOP sent to all processes in a container group for a cold checkpoint with CRIU.

Why rejected: violates P2 (non-blocking). The pause duration grows linearly with the number of processes and the time to serialize their states. For a token-ring with 64 processes running at 500,000 steps/s, a 1 ms pause eliminates 500 simulation steps — the entire purpose of the deterministic simulator. More fundamentally: the blocking snapshot cannot be used to study the algorithm being implemented, which is the non-blocking variant.

ALT-2 — Vector-Clock Causal Snapshot (Causal-Delivery-Based)

Architecture:
  All channels deliver messages in causal order (not just FIFO, but causal)
  Snapshot initiator broadcasts: SNAP(s, initiator_vc)
  Each process records state when it causally delivers SNAP(s, ...)
  No channel recording needed: causal delivery guarantees no pre-snapshot
  message arrives after the snapshot boundary

Regime where it wins: systems that already implement causal broadcast (e.g., causal-consistency distributed databases using vector-clock-stamped reads/writes). The causal-delivery guarantee subsumes FIFO and eliminates the need for channel recording entirely — the consistent cut is automatic at the delivery boundary.

Real system embodying it: Bayou (Terry et al. 1994) and causal key-value stores that propagate vector-clock-stamped updates. The "snapshot" in a causal KV store is the state visible after applying all updates causally before a given vector timestamp.

Why rejected: causal delivery is strictly stronger than FIFO delivery and requires piggybacking vector clocks on every application message. This doubles the message overhead and couples every channel to a global vector clock. The goal of this project is to implement Chandy-Lamport precisely as specified (FIFO only), not a stronger-guarantee variant. P4 (markers carry no state) would also be violated — application messages would carry causal metadata.

ALT-3 — Externally-Coordinated Checkpoint (Orchestrator Model)

Show the original text diagram
Architecture:
  External orchestrator (separate process/service) ──pause(P)──> each process Pi
  Orchestrator waits for acknowledgement from each Pi
  Orchestrator reads process state via RPC: snapshot_state(Pi) → AppState
  Orchestrator reads channel state via RPC: drain_channel(c) → Vec<Message>
  Orchestrator assembles GlobalSnapshot
  Orchestrator ──resume(P)──> each process Pi

Regime where it wins: legacy systems that cannot be modified to participate in a distributed protocol but expose a management API (pause/inspect/resume). Operational checkpointing of a running microservice deployment where injecting a marker protocol is impractical. Kubernetes ephemeral container snapshots with CRIU follow this pattern.

Real system embodying it: CRIU (Checkpoint/Restore in Userspace) for Linux processes; VMware vSphere live VM snapshots (hypervisor pauses VM, takes memory snapshot, resumes).

Why rejected: introduces a central coordinator SPOF; pauses all processes simultaneously (same issue as ALT-1 but adds network round-trips); requires a management API that cl-process does not expose; and most importantly: this is not the Chandy-Lamport algorithm. The educational and portfolio value of this project is specifically implementing the decentralized, non-blocking marker-flooding protocol.

ALT-4 — Epoch-Based Log-Truncation Checkpoint (Log-Structured)

Architecture:
  All process communication goes through an append-only log (Kafka-style)
  Epoch boundary record injected into every channel's log at checkpoint time
  Each process reads up to the epoch boundary, records state
  No in-flight messages: the log is durable; replay from offset covers them
  GlobalSnapshot = {per-process AppState at epoch boundary, per-channel offset}

Regime where it wins: systems already built on a durable ordered log (Kafka topics, DynamoDB Streams, Kinesis). The log serves simultaneously as the channel, the channel-state recording mechanism, and the recovery source. Checkpoint cost is O(1) per channel (record an offset), not O(in-flight messages). This is the exact model of Kafka Streams checkpointing and, at larger scale, Apache Flink with Kafka sources.

Real system embodying it: Kafka Streams state-store checkpointing; Apache Samza checkpoint protocol; AWS Kinesis Analytics checkpoint API.

Why rejected: requires a durable ordered log as the channel substrate, which eliminates the in-memory FIFO channel abstraction (cl-channel) and the entire cl-transport layer. The educational goal is to implement the channel-recording mechanism that makes non-blocking snapshots work without a durable log — the "hard part" of Chandy-Lamport. Using a log sidesteps the core algorithmic challenge.

Chandy-Lamport algorithm Distributed snapshot protocol (ACM TOCS, 1985): an initiator records its own state and floods marker messages; each process records state on first marker and buffers in-flight messages per channel until that channel's marker arrives; produces a consistent cut without halting computation.
Checkpoint A persisted GlobalSnapshot enabling rollback-recovery; the algorithm produces the in-memory consistent cut; durability is a deployment concern above cl-recorder.
Completion detection Mechanism in cl-recorder::completion: declares GlobalSnapshot fully assembled when every process has RecordStatus::Done on every incoming channel.
Concurrent snapshots Two or more snapshot instances with distinct SnapshotIds running simultaneously; recording state keyed by SnapshotId; fully independent; non-interference enforced by I8 and Phase 11.
Conservation invariant Application-level quantity preserved under any valid execution (total tokens, total account balances); cl-detect::conservation asserts sum(process_states) + sum(channel_states) == initial_value over a snapshot (I6).
Consistent cut A Cut (per-process event-count frontier) that is causally closed: for every Receive in the cut, the matching Send is also in the cut, or the message appears as channel state. Proved for every Chandy-Lamport snapshot by cl-verify (I1).
Consistent global state The global system state corresponding to a consistent cut; a GlobalSnapshot produced by the algorithm; reachable even though no physical instant at which all processes simultaneously occupy it need exist.
Cut Map<ProcessId, u64> mapping each process to an event-count frontier; events at index ≤ frontier are "inside" the cut; used by cl-verify::cut to partition EventHistory and check causal closure.
Deadlock detection cl-detect::deadlock stable-property check: construct a wait-for graph from the snapshot (edge Pi → Pj = Pi waiting for Pj); DFS cycle detection; a cycle implies deadlock, which is stable once true.
DeliverySchedule cl-sim::schedule::DeliverySchedule: deterministically seeded ordered sequence of (ChannelId, message_index) steps; fully determines message delivery interleaving for a simulated run.
Deterministic scheduler cl-sim::Simulator: given a fixed seed, generates an identical DeliverySchedule and thus identical EventHistory and identical snapshot on every execution (P9, I9).
Distributed snapshot A GlobalSnapshot of a running distributed system captured without halting computation; Chandy-Lamport is the canonical algorithm; the result is a consistent global state.
Event enum { Send(ChannelId, Message), Receive(ChannelId, Message), Internal } — atomic unit of run history; logged per process in cl-sim::history::EventHistory; ground truth for cl-verify cut construction and causal closure.
Event history Ordered append-only log of (ProcessId, Event) pairs maintained by cl-sim::history; per-process subsequence queryable; used by cl-verify to reconstruct the happens-before relation.
FIFO channel Directed, reliable, order-preserving channel: messages enqueued in send order and dequeued in that order; cl-channel::FifoChannel enforces this. Without FIFO a marker can be overtaken by an app message, breaking the recording boundary (P3, I2).
Flooding Marker propagation strategy: every process receiving its first Marker(s) immediately sends Marker(s) on every outgoing channel; guarantees all reachable processes eventually participate in the snapshot.
GlobalSnapshot { snapshot_id, process_states: Map<ProcessId, AppState>, channel_states: Map<ChannelId, Vec<AppPayload>> } — complete output of one snapshot instance; assembled by cl-recorder; input to cl-verify and cl-detect.
Happens-before (→) Lamport's 1978 partial order: e1 → e2 if same-process program order, or e1 = send(m) and e2 = recv(m), or transitively. A consistent cut is a down-set of →.
In-flight message AppPayload sent before the sender's snapshot instant but received after the receiver's snapshot instant; not part of any process state; captured as channel state by cl-recorder.
Initiator The process Pi calling cl-snapshot::initiate(Pi, sid); records own state first; sends Marker(s) on all outgoing channels; identified by SnapshotId::initiator. Any process may initiate.
Interleaving A particular ordering of message-delivery events across channels in a concurrent run; cl-sim controls interleavings via DeliverySchedule; Phase 14 fuzzes many interleavings to confirm invariant soundness.
Lai-Yang variant Distributed snapshot algorithm for non-FIFO channels: piggybacks color information on every application message; referenced as contrast in the FIFO-violation negative test; not implemented in this project.
Lamport clock Scalar logical timestamp (CACM, 1978); sufficient for total event ordering; insufficient alone for causal direction between arbitrary events; cl-verify uses vector clocks instead.
Local state AppState of a single process frozen at its first-marker instant for a given SnapshotId; the per-process contribution to GlobalSnapshot::process_states; governed by I3 (recorded exactly once per snapshot).
Marker Message::Marker(SnapshotId) — lightweight control message carrying only a snapshot identifier; no application payload; sole purpose is to delineate pre-snapshot from post-snapshot app messages on a channel (P4).
Marker-receiving rule On first Marker(s) at Pj from channel c: record own state; mark c as empty; start recording all other incoming channels; send Marker(s) on all outgoing. On subsequent Marker(s) from c: stop recording c. Implemented in cl-snapshot::receive.
Marker-sending rule On initiation or first-marker receipt: before sending any further app message, send Marker(s) on every outgoing channel; ensures marker arrives before all post-snapshot app messages. Implemented in cl-snapshot::initiate and cl-snapshot::receive.
Non-blocking Characteristic of Chandy-Lamport: processes continue sending, receiving, and executing application logic during snapshot recording; no synchronization barrier halts computation (P2).
ProcessState Runtime struct { local: AppState, recording: Map<ChannelId, RecordStatus>, recorded: SnapshotState } — tracks both application state and per-channel snapshot bookkeeping; distinguished from the snapshot's AppState contribution.
RecordStatus enum { NotStarted, Recording, Done } — per-(SnapshotId, ChannelId) recording state at a receiving process; drives the channel-recording state machine in cl-snapshot::receive.
Reachable state A global state reachable from the initial configuration by some valid execution sequence; the Chandy-Lamport consistency theorem: every consistent snapshot corresponds to a reachable state even without a global clock.
Reliable delivery Channel guarantee: every sent message is eventually delivered exactly once in send order; enforced by cl-channel and cl-sim; required for snapshot liveness (I10).
Snapshot ID SnapshotId { initiator: ProcessId, seq: u64 } — unique identifier for one snapshot instance; keys all per-snapshot recording state in cl-snapshot and cl-recorder; enables concurrent independent snapshots (I8).
SnapshotState { local_state_at_first_marker: AppState, channel_msgs: Map<ChannelId, Vec<AppPayload>> } — per-process recording accumulator: frozen local state plus growing in-flight message list per incoming channel.
Stable property Predicate P on global state such that P(s) true and s → s' implies P(s'); once true, stays true; detecting P over a consistent snapshot is sound (P8, I7). Examples: Terminated, Deadlocked, Conserved.
Termination detection cl-detect::termination: all process_states report idle AND all channel_states are empty in the snapshot; if true in a consistent snapshot, termination is permanent.
Token ring cl-app::token_ring distributed computation: N tokens circulate among P processes; sum(process_states) + sum(channel_states) == initial token count; a conservation invariant testable by cl-detect::conservation.
Vector clock Map<ProcessId, u64> logical timestamp advanced on send/receive per Fidge/Mattern rules; used by cl-verify::causal to reconstruct happens-before and certify causal closure of the recorded cut.
Wait-for graph Directed graph in cl-detect::deadlock: node per process, edge Pi → Pj if Pi is blocked waiting for Pj; cycle implies deadlock; detected via iterative DFS over GlobalSnapshot.
