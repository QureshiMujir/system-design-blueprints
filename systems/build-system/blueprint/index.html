Project Name: Build System (Bazel-like)

1. Goal & Scope

Build a hermetic, content-addressed, incrementally-correct, Bazel-like build system: a Starlark-configured target/action dependency graph, a demand-driven memoised evaluator (Skyframe-style) that derives the minimal rebuild set on every source change, a sandboxed local executor, a BLAKE3 content-addressed store (CAS) with local + remote tiers, an action cache keyed by a canonical hash of an action's declared inputs (never mtime, never paths), a REAPI-speaking remote-execution client, a persistent-worker subsystem for warm-process reuse, and a Datalog-flavoured query language over the target/action graphs. The contract: identical declared inputs on any machine produce byte-identical outputs (I2, I5); a change to one source file rebuilds only the closure of actions whose declared inputs changed (I6); a cache hit is re-validated against content before being trusted (I9, ADR-14).

Phase-0 deliverable (numbered, one crate per line; full tree in §10):

  1. core-types — Label, Digest, Artifact, Action, ActionKey, Provider, Configuration signatures (§11).
  2. starlark-vm — the deterministic Starlark interpreter (§13).
  3. loader — BUILD-file + MODULE.bzl loading, label resolution, workspace (§14).
  4. skyframe — the demand-driven graph evaluator (§17).
  5. cas — local content-addressed store, BLAKE3 digesting (§18, Phase-0 subset).
  6. executor — unsandboxed subprocess path only in Phase 0; sandbox lands §19.
  7. action-cache — in-memory map in Phase 0; RocksDB + double-keying lands §20.
  8. build-cli + buildd — thin client and daemon skeleton (§12).

System boundaries — provides: hermetic action execution, content-addressed caching (local + remote), incremental rebuild via dirty propagation with early cutoff, a Starlark-like configuration language, a query language over the graph, remote/distributed execution via REAPI, cross-host reproducibility verification. Delegates: the actual compiler/linker/toolchain binaries (declared, not implemented); container orchestration for remote workers (Kubernetes/Nomad — out of scope); source control (git — out of scope); artifact hosting beyond the CAS wire protocol. Does NOT provide: a package registry/dependency-resolution service beyond file-system MODULE.bzl overrides (PhaseDeferred("§14.2")); a distributed multi-region scheduler (PhaseDeferred("§31")); IDE language-server integration (PhaseDeferred("§37")).

Non-goals: a general-purpose task runner (no arbitrary-script execution outside declared actions); a CI/CD pipeline scheduler; a bundled language package manager (rules are pluggable, Phase 0 ships only genrule/filegroup).

Deployment model: one long-lived daemon (buildd) per developer workstation or CI runner, holding the Skyframe graph in memory, backed by RocksDB for cold-start persistence (I11); remote execution and remote cache are optional network services reached over gRPC/TLS. Target users/operators: platform/build-infrastructure engineers standing up the system; individual engineers invoking build/query/test; on-call staff diagnosing stale-cache or non-determinism incidents via the runbooks (§26).

Later phases unlock: cross-compilation and fat binaries (§16), elastic remote execution (§21), warm-process compiler reuse (§21), whole-graph queries at scale (§22), profiling-grade throughput (§23). Recommended language: Rust (2021 edition) — no GC pause in the hot Skyframe-restart loop, Send-checked concurrency for the parallel evaluator, a mature async ecosystem (tokio, tonic) for the gRPC surfaces, and Buck2's production migration from C++ to Rust is a direct existence proof (ADR-01). Rejected: Java (Bazel's own choice) — JVM warm-up and GC pauses measurably hurt cold-build p50 (§4); C++ — the memory-safety burden on a security-sensitive sandboxed-execution surface is unacceptable without a decade of hardening; Go — GC and the absence of a true zero-cost async/ownership model make the CAS hot path (§30, M6) harder to hit.

Prerequisites: Linux namespaces (namespaces(7), unshare(2), mount(2), seccomp(2)), a working model of content-addressed storage (Merkle trees, Git-style object stores), async Rust (the tokio task model), gRPC/protobuf, and the Build Systems à la Carte taxonomy (§5) before starting §17. Estimated timeline: Phase 0 in 2 weeks; the full 12-phase plan (§12–§23) in 7–9 months to a cross-host-reproducible, remotely-executable, query-capable system.

Deferred features (registered once in §37): bzlmod registry resolution PhaseDeferred("§14.2"); FUSE-lazy materialisation PhaseDeferred("§18.5"); configuration trimming PhaseDeferred("§16.4"); dynamic/monadic deps PhaseDeferred("§13.6"); Windows sandbox PhaseDeferred("§19.2"); distributed multi-region scheduler PhaseDeferred("§31").

2. Why Build This

  • The canonical whiteboard-vs-production gap. A topological sort is a page of pseudocode; a trustworthy incremental cache across a moving compiler, moving OS, moving hardware is a multi-year discipline. This is the smallest system that still contains the full production surface.
  • Teaches the "suspending scheduler + verifying trace" design point (Mokhov, Mitchell, Peyton Jones, ICFP 2018) — the exact axis separating make from shake from bazel from nix; without living inside one implementation the taxonomy stays abstract.
  • Teaches cache correctness as a first-class discipline, not an afterthought: the action-key derivation (§20.2), the double-keying defence (§20.6, ADR-14), and the early-cutoff optimisation (§17.4, I6) are the actual load-bearing engineering behind every production build system's headline speed claim.
  • Teaches hermetic sandboxing from primitives — namespaces, seccomp, sandbox-exec — not from a wrapper library (§19); the same muscle builds container runtimes, CI isolation, and multi-tenant execution platforms generally.
  • Cross-links (by name): the Incremental Build Graph Engine project shares the Skyframe/DICE/Salsa demand-driven evaluator shape (§17); the Artifact Build Cache Server project shares the CAS + action-cache wire protocol (§18, §20); the OCI Image Builder project shares the sandboxed, hermetic execution model (§19).
  • Historically: Make (1976) → Google's internal Blaze (2000s) → open-sourced Bazel (2015) → Buck2's Rust rewrite (2023) → Nix's independent purely-functional lineage (Dolstra, 2006). Understanding why each successor exists is understanding the failure modes of its predecessor.
  • Calibration value: an engineer who has implemented the action-key derivation, the double-keyed cache, and the cross-host determinism oracle has felt, first-hand, how easy it is to believe a build is hermetic while it silently is not — the single most expensive class of incident in build infrastructure.

What Mastery Looks Like — after finishing this blueprint, the reader can:

  • Explain, DAG in hand, why a "suspending scheduler with verifying traces" subsumes both make and shake, and derive Skyframe's restart mechanism from first principles (§17, Phase 5).
  • Derive an action key by hand for a two-input compile action and predict, without running it, whether a one-character source change changes the key (§20.2, Phase 8).
  • Explain why a remote-cache hit must be re-validated against CAS content before trust, and name the specific poisoning attack this defeats (§20.6, T1, Phase 8).
  • Stand up a Linux sandbox from unshare/pivot_root/seccomp primitives and enumerate every leak it must close (§19.1–19.3, Phase 7).
  • Reason about the exec-vs-host-vs-target configuration triad and predict cross-compilation behaviour for a fat binary (§16.3–16.4, Phase 4).
  • Diagnose a stale-cache incident using the digest-mismatch telemetry path end to end (§25, FM-1).
  • Compute, from the System Constraints table alone, the RAM and FD budget a 100k-target workspace needs (§34).

  • CLI: thin client, no graph state; talks to buildd over a Unix domain socket; commands map 1:1 to daemon RPCs (§12).
  • Loader: parses MODULE.bzl + BUILD files via the Starlark VM, resolves Labels to Targets, produces immutable Package values (§13, §14).
  • Analysis: runs each target's rule impl_fn, emitting Providers and Actions; the ConfiguredTarget is the analysis output (§15).
  • Configuration: resolves platforms/toolchains, applies transitions on dep edges, computes the content-hashed ConfigurationId (§16).
  • Skyframe graph engine: demand-driven, memoised, restart-based evaluator; the one graph engine every phase's "what is the value of X" question goes through (P6, §17).
  • Watcher: inotify/FSEvents/kqueue source-change events, coalesced and fed to the graph as FileKey invalidations (§22.1).
  • Action graph: the DAG of Actions keyed by ActionKey; constructed lazily as the evaluator restarts on missing deps (§17.3).
  • Local/Remote/Worker executors: interchangeable behind the ExecutionEngine trait; the graph never branches on which executor ran an action (P2, §19, §21).
  • Action Cache: (ActionKey → ActionResult) with the double-keyed poisoning defence; local RocksDB tier + remote REAPI tier (§20).
  • Content-Addressed Store: BLAKE3-digested objects, Merkle-tree directories, local + remote tiers, mark-and-sweep GC (§18).

Five load-bearing properties, referenced throughout: First, the data path is one-way — loader → analysis → graph → executor → CAS, never reversed. Second, executors are interchangeable and the graph is executor-agnostic (P2). Third, every cross-cut (CAS, action cache, digest function, Starlark VM, watcher) is owned by exactly one crate and reached only via a trait (P6). Fourth, the cache is content-keyed and content-validated — a hit is re-digested before being trusted (I9). Fifth, hermeticity is structural, not conventional — every action's sandbox exposes only declared inputs/tools/env (P1, I1).

6. Design Principles

  1. P1 — Hermeticity is the default. Every action runs in a sandbox exposing only its declared inputs, tools, and environment. Tradeoff: rules that need ambient state (network, $HOME) must declare it explicitly, adding friction. Operationally: the hermeticity probe suite (§24.1) is the regression gate. Violating it: an action silently reads host state, producing a build that is right on one machine and wrong on the next.
  2. P2 — The action graph is executor-agnostic. No phase branches on which ExecutionEngine ran an action. Tradeoff: the Action type must be a superset every executor can consume, costing some per-executor optimisation opportunity. Operationally: local/remote/worker executors are swappable via one flag. Violating it: executor-specific fields leak into the graph, and dynamic executor selection (§21) breaks.
  3. P3 — Content-addressed everything. Every file has a BLAKE3 digest; the action key, the cache lookup, and materialisation are all digest operations. Tradeoff: digesting large trees costs CPU on every analysis pass (amortised via the digest cache, §22.2). Operationally: cache hit rate is the primary throughput lever. Violating it: a path- or mtime-keyed cache degrades to make's known failure mode (FM-1).
  4. P4 — Incremental correctness outranks availability. A build that returns a stale output is strictly worse than a build that errors. Tradeoff: the system fails loudly (aborts) rather than degrading gracefully when a digest cannot be verified. Operationally: I9 is a hard gate, not a warning. Violating it: silent staleness, the single most expensive class of build-system incident.
  5. P5 — Bazel-like, not Bazel. Borrow the architecture (Skyframe, Starlark, action graph, REAPI); reject the accumulated legacy (no --legacy_* flags, no deprecated WORKSPACE file — MODULE.bzl/bzlmod only). Tradeoff: less ecosystem-rule compatibility on day one. Operationally: a smaller, auditable surface. Violating it: re-accumulating the same decade of legacy flags this project exists to avoid.
  6. P6 — One graph engine. Every "what is the value of X" question — loading, configuration, action results — goes through the same SkyFunction → SkyValue interface (§17). Tradeoff: one engine must be generic enough for heterogeneous key types, costing some type-erasure overhead. Operationally: one invalidation path, one scheduler, one profiling surface. Violating it: a second ad hoc graph for "just configuration" duplicates the dirty-propagation logic and reintroduces I6 bugs.
  7. P7 — The action key is the contract. A change that does not change the ActionKey must not change the output; a change that does may. Tradeoff: the key derivation (§20.2) must canonicalise every field precisely, which is exacting engineering. Operationally: action.replay and action.divergence conformance buckets enforce both directions. Violating it: non-deterministic actions silently poison every downstream cache consumer.
  8. P8 — Sandbox via namespaces, not chroot. Linux: user/mount/PID/network/IPC/UTS namespaces, no setuid binary, no privileged daemon. macOS: sandbox-exec. Tradeoff: the macOS sandbox is structurally weaker (documented gap, §19.6). Operationally: no root requirement simplifies CI deployment. Violating it (e.g. falling back to chroot) reintroduces a privilege-escalation surface (T3).
  9. P9 — Remote execution is optional and observable. No --remote_executor flag means local-only; cache and execution are decoupled (--remote_cache without --remote_executor is the common case). Tradeoff: added configuration surface. Operationally: a remote failure is recorded, never silently swallowed (P14). Violating it: an opaque remote dependency where none was asked for.
  10. P10 — BLAKE3 with a rollable digest-function tag. Every stored Digest carries a 1-byte function tag (ADR-07). Tradeoff: 1 extra byte per digest, permanently. Operationally: a future hash break is a migration, not a rewrite. Violating it (a bare hash with no tag) forces a flag-day migration industry-wide precedent shows is routinely botched.
  11. P11 — The daemon owns the graph. buildd holds the Skyframe graph in memory; the CLI is a stateless client (§12). Tradeoff: a daemon lifecycle (start/stop/crash-restart) to manage. Operationally: warm builds skip the cold-start reload entirely. Violating it: every invocation pays the full graph-reconstruction cost (§4 cold-start row).
  12. P12 — The persistent worker is a contract, not a hack. Workers implement the documented Bazel worker protocol (§21.1); the pool bounds multiplexing and kills drifted workers (I13). Tradeoff: workers are not fully hermetic between requests. Operationally: a worker blacklist backstops the tradeoff. Violating it: a leaky worker silently returns different outputs for identical inputs.
  13. P13 — Query is a language, not a flag. query/cquery/aquery parse a documented Datalog-flavoured grammar (§22.3) to an AST, then walk the graph. Tradeoff: a real parser + evaluator to build and fuzz. Operationally: composable expressions (deps(...) except tests(...)) instead of a combinatorial flag explosion. Violating it: an ad hoc string-matching query layer that cannot compose.
  14. P14 — No silent fallbacks. A remote-cache failure is recorded and (per flag) falls back to local, but the failure is always observable; a sandbox that cannot be created fails the build, it does not run unsandboxed. Tradeoff: stricter default behaviour can surprise a first-time operator. Operationally: cache.miss.remote_error and sandbox.create_failed are always-emitted metrics. Violating it: a build that "just works" by quietly dropping a guarantee it advertised.

Debugging methodology: a deterministic single-threaded simulator (skyframe::sim) replays a recorded event log (source edits + build requests) with one assertion per invariant above attached to every SkyNode transition; a fixture that trips an assertion is committed to conformance/corpora/incrementality/ as a regression case.

8. Domain Model

8.1 Target & Action Graph Model

The build has two nested graphs. The target graph (Label → Target → ConfiguredTarget) is produced by loading and analysis (§14, §15); the action graph (ActionKey → Action) is produced as a side effect of analysis and evaluated by Skyframe (§17). A Target's lifecycle:

State Meaning Produced By Next States
Unloaded Label referenced, package not yet read — Loaded, LoadFailed
Loaded Package frozen, Target exists, rule not yet run loader (§14) Configured
Configured Paired with a ConfigurationId; toolchains resolved config (§16) Analyzed
Analyzed impl_fn ran; Providers + Actions emitted rules::analyse (§15) (terminal for the target; its Actions each have their own lifecycle below)
LoadFailed / AnalysisFailed typed error, propagated to dependents any of the above terminal

An Action's execution lifecycle (independent of its owning target):

State Meaning Transition Trigger Next States
Pending enqueued, inputs not yet materialised action-graph construction CacheCheck
CacheCheck looking up ActionKey in local then remote action cache §20 lookup Cached, Dispatched
Cached result found and content-revalidated (I4) cache hit Done
Dispatched sent to Local, Remote, or Worker executor (P2) cache miss Executing
Executing subprocess/RPC/worker request in flight executor accepted Success, Failed, TimedOut
Success outputs digested, uploaded to CAS, cache updated executor return 0 Done
Failed non-zero exit or executor error executor return ≠ 0 terminal (build fails unless target marked best-effort)
TimedOut exceeded Action.timeout, killed SIGTERM→SIGKILL timer Failed
Done outputs available in CAS + workspace Success or Cached terminal

8.2 Content-Addressed Cache Keys

The ActionKey is the BLAKE3 digest of a canonical encoding of an ActionKeyInput:

Field Type Canonicalisation Rule
salt u32 algorithm-revision counter, bumped only via ADR (ADR-04)
domain_separator 16 bytes fixed literal "BUILD-SYSTEM/ACT", defeats cross-key extension attacks
mnemonic string verbatim, e.g. "CcCompile"
command_argv string list verbatim order (order is semantically significant)
env map sorted by key, fixed-width encoding, no floats
inputs_tree_digest Digest BLAKE3 of the canonical Merkle-tree serialisation of declared inputs
tools_tree_digest Digest same, over the declared tool set
output_paths string list sorted lexicographically
platform_properties map sorted by key
timeout_ms u64 fixed-width, milliseconds

Derivation procedure, in order: (1) build the Merkle tree over inputs and digest its canonical serialisation; (2) same for tools; (3) canonicalise env as a sorted map; (4) sort output_paths lexicographically; (5) canonicalise platform_properties; (6) feed salt, domain_separator, and every field above — each preceded by a zero-byte separator — into a BLAKE3 hasher; (7) the finalised 32-byte output, tagged with DigestFunction, is the ActionKey. Every field is canonicalised before hashing so that two Action values that are semantically equal (same effective inputs, different construction order) always hash identically (I3, I12's sibling guarantee for actions).

8.3 Incremental Rebuild State Machine

A SkyNode's invalidation lifecycle (I6, I10):

From Event To Notes

Dirty evaluator revisits node (recompute) requests all deps again (I10)
Dirty recomputed value equals cached value Clean early cutoff — propagation halts (I6)

8.4 Worked Example: Compile-and-Link, Cold Then Warm

Two actions: CcCompile(hello.c → hello.o) then CcLink(hello.o → hello).

Cold build. hello.c digests to d_src=0x71a2…. CcCompile's ActionKeyInput combines d_src, the gcc tool digest, argv, and env into ActionKey_compile=0x4f9c…. Cache lookup: miss (first build). Executor runs; hello.o digests to d_obj=0x88e1…; the result is stored under ActionKey_compile. CcLink's key folds in d_obj: ActionKey_link=0x2b7d…. Miss; executor runs; hello digests to d_bin=0x0c35…; stored under ActionKey_link.

Warm rebuild, no source change. Both keys recompute identically (0x4f9c…, 0x2b7d… — same inputs, same canonical encoding). Both are Cached; total work: two RocksDB reads, zero subprocesses (M2).

One-line change to hello.c. d_src changes to 0x9931…. ActionKey_compile changes (a different inputs_tree_digest) to 0x77e0… — miss, CcCompile re-executes. Suppose the new hello.o happens to digest to the same d_obj=0x88e1… (e.g. a comment-only source edit that does not change codegen). Then ActionKey_link — which only depends on d_obj, not on hello.c's digest — is unchanged: CcLink is a cache hit. This is the early-cutoff optimisation (I6) made concrete: the rebuild touched one action, not two.

8.5 Malformed Input Handling

  • A BUILD file with a syntax error (Stmt::While — while loops are not part of Starlark) yields EvalError::WhileNotAllowed { span }; the loader aborts that package's load with a typed LoadError, other packages are unaffected.
  • A REAPI WorkResponse with request_id matching no in-flight request is logged (worker.protocol.unmatched_response) and dropped; the corresponding WorkRequest is retried on a fresh worker after a 5 s timeout.
  • An ActionKeyInput encoding that produces a digest not matching a previously-recorded fixture in conformance/corpora/action_key/ fails that conformance case immediately (regression, not a runtime path).
  • A Directory proto (Merkle tree node) with entries not sorted by name is rejected at materialisation time with CasError::UnsortedTree — a malformed tree is never partially trusted.

8.6 Failure-Path Example

A compromised remote cache returns ActionResult { outputs: [{path: "hello.o", digest: 0xdead…}] } for ActionKey_compile=0x4f9c…, where 0xdead… does not exist in the remote CAS (or exists but is attacker content). The engine's cache-hit path (§20.5) attempts to fetch 0xdead…; the CAS FindMissingBlobs call reports it missing (or, if present, the content-revalidation in I4 recomputes its digest post-fetch and finds a mismatch against the declared 0xdead…, which cannot happen for correctly-addressed content but can happen if the cache lied about the digest of real bytes it returned). Either branch trips cache.poison.detected (I9), the entry is rejected, and the engine falls back to executing CcCompile locally — the build completes correctly, slower, with the incident logged for T1.

12. Phase 0 — Foundations: Repo Skeleton & Correctness Kernel

12.1 Objectives

Stand up the repository (§10), the Cargo workspace, CI skeleton, and a minimal correctness kernel: Label/Digest/Artifact (§11.1–11.2), a stub loader recognising exactly one rule (genrule, no Starlark yet), an unsandboxed local executor, and an in-memory action cache — enough to build one file end to end and validate the pipeline shape before any component is built out fully.

12.2 Detailed Implementation Steps

Land the Cargo workspace with core-types, loader (stub), executor (subprocess-only), action-cache (in-memory HashMap). Implement Label::parse/canonical and Digest::of_bytes/of_file (P3, P10, §11.1). The loader recognises genrule via a hard-coded match — full Starlark evaluation is Phase 1 (§13); this is a deliberate, documented scope cut, not a shortcut around P5. The executor runs argv via tokio::process::Command (ADR-10) with no sandbox — the gap is flagged prominently for §19 and asserted-on in examples/hello/README.md. Wire tracing spans (ADR-17) around load → analyze → execute from commit one. Land the seven fuzz-target stubs (ADR-19) compiling but not yet exercising real subjects; land cargo-deny/clippy --deny warnings/rustfmt (ADR-20) as CI gates.

12.3 Deliverable

build //hello:greeting runs end to end: build-cli → buildd (UDS RPC) → loader → executor → filesystem write (no CAS yet — Phase 0 writes directly to the workspace), asserting the output file exists with the expected bytes.

12.4 Acceptance Criteria

make bootstrap && make build && make test all exit 0; conformance bucket smoke.genrule reports Pass with exactly 1 case; cargo-deny check clean; all seven fuzz targets run 60 s each with zero crashes and zero panics (ADR-19); every workspace crate compiles under cargo check --workspace in under 90 s on the reference host.

12.5 Conformance Fixtures

corpora/smoke/hello_genrule.jsonl — expects output bytes "hello\n". corpora/adversarial /starlark/empty.bin — empty input, parser must not panic. corpora/adversarial/starlark /oversize.bin — 1 MiB of 'a', parser must reject with a typed error, not OOM.

12.6 Pitfalls

The temptation to build the Starlark interpreter before the workspace skeleton is strong; resisting it is what keeps CI green from commit one (P5's discipline starts here). cargo-deny flags missing license fields on day one — add ADR-20's dual license to every crate's manifest before the first push. clippy --deny warnings surfaces pedantic-by-default lints; pin the policy in clippy.toml, don't fight it ad hoc. The unsandboxed smoke test is easy to mistake for "already hermetic" — document the gap where a new contributor will read it (examples/hello/BUILD's header comment).

12.7 Performance Concerns

None load-bearing yet; the only budget is CI wall-clock (make test under 30 s on the reference host) so the workspace stays fast to iterate on through Phase 1–2.

12.8 Edge Cases

A BUILD file naming an unknown rule returns LoadError::UnknownRule(name) (a typed error, never a panic) — this is intentional: Phase 0 is the skeleton, not the engine. An empty BUILD file loads to an empty Package. A zero-byte source file digests to Digest::empty() (§11.1) without special-casing.

12.9 Failure Analysis

A compile error in core-types blocks every downstream crate transitively; CI runs cargo check --workspace before any test to fail fast rather than burning CI minutes on crates that cannot build. A genrule whose command exits non-zero surfaces the captured stderr verbatim to the CLI (no swallowing).

12.10 Operational Notes

tracing spans load, analyze (stub-only in Phase 0), and execute exist from commit one specifically so that later phases only add spans and never retrofit instrumentation onto code that shipped without it — a deliberate operational-readiness investment this early (§26).

13. Phase 1 — Starlark Interpreter

13.1 Objectives

Implement the deterministic Starlark dialect (ADR-02, P5) used by every BUILD file and .bzl module from Phase 2 onward: a tree-walking evaluator over a parsed AST producing frozen, immutable values, with zero I/O, zero clock, zero randomness by construction.

13.2 Detailed Implementation Steps

Implement the lexer/parser producing an Ast (Nystrom, Crafting Interpreters, §5.1), rejecting while and lambda at parse time per the Starlark spec (§5.4 RFC). Implement eval_module as a tree-walking evaluator (P6's discipline of "no ad hoc side channel" applies here too: the only side effect is constructing values). Implement the freeze pass: walk the value graph in topological order, convert MutList/MutDict to FrozenList/FrozenDict, intern equal frozen values (CSE), and compute a stable hash per frozen value consumed later by ActionKeyInput canonicalisation (§8.2, I3). Implement Span-carrying diagnostics for every EvalError variant (§11's terseness principle applies to error types too — no untyped strings). Implement the standard library subset (len, range, sorted, string methods) with no networked or filesystem-reading builtin, ever (P1's determinism guarantee starts in this crate, before any sandbox exists).

13.3 Deliverable

starlark_vm::eval_module(src) accepts every fixture in conformance/corpora/starlark/ and returns a FrozenModule; a 10 KB BUILD file evaluates deterministically on repeated runs.

13.4 Acceptance Criteria

100% of corpora/starlark/ fixtures pass (arithmetic, string ops, list/dict/set, default-arg functions, recursion rejection, load() resolution, freeze semantics); a 10 KB BUILD file evaluates in < 5 ms on the reference host (M-perf gate for Phase 1); fuzz target starlark_parse runs 1 hour clean seeded from corpora/adversarial/starlark/.

13.5 Conformance Fixtures

corpora/starlark/eval/recursion_reject.jsonl — a mutually-recursive def pair, expects EvalError::Recursion. corpora/starlark/eval/freeze_mutation.jsonl — a post-freeze mutation attempt, expects EvalError::Frozen (I8). corpora/starlark/eval/overflow_2e63.jsonl — integer literal 2**63, expects a parse-time rejection.

13.6 Pitfalls

The Starlark spec changes slowly; pin the version in docs/adr/002-starlark.md and re-pin via ADR on upgrade. Integer overflow at 2**63 is a frequent fixture gap — enforce the bound at both parse time (literals) and runtime (arithmetic). A naive freeze pass via Rc<RefCell<...>> blows the stack on deeply nested structures; use an explicit work-queue instead of recursion. load() cycles are a real hazard the loader (§14) must detect and report with the full chain. Dynamic/monadic dependencies (Mitchell, "Shake Before Building", 2012) are explicitly out of scope here — PhaseDeferred("§13.6"), registered in §37.

13.7 Performance Concerns

The tree-walking evaluator is ~3× slower than a future bytecode VM; acceptable through Phase 0–1 given the 5 ms/10 KB target (§13.4) — a bytecode VM is deferred, not required, until profiling (§23) shows it as the bottleneck.

13.8 Edge Cases

A load() cycle (a.bzl loads b.bzl loads a.bzl); a function with both *args and **kwargs and a default-arg collision; a string method call on a frozen value (must succeed — freezing blocks mutation, not method calls); an empty module (zero statements).

13.9 Failure Analysis

EvalError::Frozen { span } — write to a frozen value (I8); blast radius is the one statement, not the module (the diagnostic pinpoints the exact assignment). EvalError ::Recursion { span, call_chain } — full chain reported so a developer does not have to bisect. EvalError::Fail { span, msg } — user-invoked fail(), surfaced verbatim.

13.10 Operational Notes

Every Diag (parse or eval error) renders a Rust-style caret diagnostic; buildd streams these over the BEP-JSON sink (§26) so a CI log shows the same diagnostic a local terminal would.

14. Phase 2 — BUILD Loading, Label Resolution & Workspace

14.1 Objectives

Produce a Workspace value that resolves Label references to frozen Target values by recursively walking BUILD files through the real Starlark VM (§13), replacing Phase 0's hard-coded genrule-only loader.

14.2 Detailed Implementation Steps

Implement workspace::resolve() rooted at the directory containing MODULE.bzl, resolving module dependencies eagerly against the local file system only — the full bzlmod registry resolution is PhaseDeferred("§14.2") (registered §37). For every directory containing a BUILD/BUILD.bazel file: parse via starlark_vm::eval_module (§13.2), evaluate in an environment exposing the native rule functions and load(); each rule invocation registers a Target into the package's BTreeMap; freeze the Package after evaluation (I8's discipline extends to packages, not just values). Implement Label::parse for all five canonical forms (§11.1: @repo//pkg:name, shorthand, current-repo, current-package, bare name); canonicalise relative forms to fully-qualified before storage (P3 — labels are never re-derived from strings downstream). Implement Visibility checking deferred to analysis time (Phase 3, §15), not load time — a load-time check would block harmless reads (query, §22). Add native rules filegroup, alias, test_suite alongside Phase 0's genrule (ADR-02's Starlark foundation now bears real weight).

14.3 Deliverable

loader::load_workspace(root) returns a Workspace; every BUILD file under examples/ (§10) parses and loads cleanly through the real Starlark VM.

14.4 Acceptance Criteria

100% of conformance/corpora/loader/ fixtures pass; a load() cycle is detected and reports the full chain (not just the two adjacent files); Label::parse round-trips all 5 canonical forms with 0 ambiguous-resolution cases across the fixture set; loading a 500-package synthetic workspace completes in ≤ 2 s on the reference host.

14.5 Conformance Fixtures

corpora/loader/cycle_ab.jsonl — a.bzl ↔ b.bzl load cycle, expects LoadError::Cycle with the 2-element chain. corpora/loader/duplicate_target.jsonl — two rules named :x in one package, expects LoadError::DuplicateTarget. corpora/loader/labels/relative_forms .jsonl — all 5 canonical forms resolving to the same fully-qualified Label.

14.6 Pitfalls

glob(["src/**/*.rs"]) must be deterministic — sorted by lexicographic path (P3); a non-deterministic glob is a cache-busting bug that will not surface until a second machine builds the same target. Visibility enforced at load time (instead of analysis time) blocks harmless reads like query — keep it at analysis (§15.4). Symlinks in the source tree must canonicalise consistently: resolve via canonicalize, store both the symlink path and the real path, and digest over the real path's content only.

14.7 Performance Concerns

Package loading is embarrassingly parallel across directories with no shared mutable state (P6's "no ad hoc side channel" rule applies); parallelise via tokio tasks bounded by the directory count, not a fixed thread pool, to avoid starving Phase-1's evaluator on large workspaces.

14.8 Edge Cases

A BUILD file with zero targets (valid, empty Package); a load() referencing a label that does not exist — not an error at parse time, only at use time when a rule attribute dereferences it (§8.5); a package re-loaded after a file-watch event (§22) produces a new Package value, GC'd once no live Target refers to the old one.

14.9 Failure Analysis

LoadError::Cycle { chain } — full path reported; blast radius is every package downstream of any node in the cycle, all marked LoadFailed (§8.1). LoadError::Visibility { from, to } surfaces both labels so the fix (adding a package_group entry) is a one-line diff.

14.10 Operational Notes

Loader errors carry the originating BUILD file path and line (via the Starlark Span, §13); buildd's BEP-JSON stream tags each error with the PackageKey (§11.6) so a CI dashboard can group failures by owning team's directory.

15. Phase 3 — Rules, Providers & DepSets

15.1 Objectives

Lift the loader's Target values to ConfiguredTarget values by running each target's rule impl_fn in an analysis context, producing Providers and emitting Actions as a side effect — the transition from "what the developer wrote" to "what will actually build."

15.2 Detailed Implementation Steps

Implement the ctx object (Starlark-side surface: ctx.label, ctx.attr.*, ctx.actions.run/write/symlink, ctx.runfiles) exposing Rust-side builtins that record Action values (§11.2) into a per-ConfiguredTarget buffer (P6: the analysis phase is the only place Actions are constructed). Implement the native Provider types (DefaultInfo, FilesToRunProvider, OutputGroupInfo, §11.5) and custom provider(...) declaration, with provider IDs hashed at module-load time (two same-named providers declared in two modules are two distinct types — no accidental aliasing). Implement DepSet<T> (§11.5) as the sole container for transitive provider fields (ADR-15's Datalog query language later walks these trees directly); construction is O(direct + #transitive), flatten is lazy via to_list(). Implement duplicate-output detection in the action-graph builder (I7): two Actions claiming the same output Artifact is a hard analysis error, not a runtime race. Ship the aspect infrastructure (propagation along declared attribute edges) as scaffolding; specific aspects (proto_aspect, coverage_aspect) are Phase 1+ rule-crate work, not Phase 3 itself.

15.3 Deliverable

rules::analyse(target, configuration) -> ConfiguredTarget; the genrule rule emits one Action and a DefaultInfo provider consumable by an rdep.

15.4 Acceptance Criteria

Every fixture in conformance/corpora/rules/ produces a byte-stable provider snapshot; a rule that emits two actions with the same output path fails analysis with AnalysisError ::DuplicateOutput in 100% of the fixture's 12 adversarial cases (I7); DepSet::to_list() on a 10,000-node transitive set completes in ≤ 50 ms.

15.5 Conformance Fixtures

corpora/rules/genrule_snapshot.jsonl — the exact Action + DefaultInfo for a reference genrule. corpora/rules/provider_isolation.jsonl — two modules declaring provider(fields=["x"]) under the same name, expects two distinct ProviderIds. corpora/rules/duplicate_output.jsonl — two rules in one target claiming out.txt.

15.6 Pitfalls

A rule reading ctx.attr.x.providers[MyProvider] on a dep that never emitted MyProvider must raise a typed AnalysisError, not a Starlark KeyError (P1's "no silent surprises" extends to error typing). A DepSet constructed with itself as a transitive element is a cycle — the constructor must check, not defer to a later stack overflow. A rule mutating its inputs is impossible by construction (providers are frozen, I8) — but a rule re-reading ctx.attr.x expecting freshness across two calls is a real confusion to document in docs/architecture/overview.md.

15.7 Performance Concerns

DepSet flattening is the hot path for large cc_library dep chains; lazy flatten (only on to_list()) keeps analysis itself O(direct + transitive-count) instead of O(total transitive elements) per target (Kleppmann's tree-structured-merge lesson, §5.1, applied here).

15.8 Edge Cases

A rule that emits zero actions (a pure filegroup); a rule whose impl_fn raises Starlark fail() mid-analysis (the whole ConfiguredTarget is AnalysisFailed, dependents see a typed propagated error, not a partial result); an aspect that reaches a target with no matching propagate-attr (returns an empty provider set, not an error).

15.9 Failure Analysis

AnalysisError::DuplicateOutput { path, owners } names both owning Actions so the fix is immediate. A cyclic DepSet construction raises AnalysisError::DepSetCycle before any flatten is attempted — caught at construction, never at read time.

15.10 Operational Notes

Provider snapshots are content-addressed (BLAKE3 of the canonical Provider encoding) so aquery's (§22) action-graph diff view can show "this target's providers changed" without a full structural diff.

16. Phase 4 — Configurations, Platforms & Transitions

16.1 Objectives

Introduce the Configuration value (§11.5) and the transition machinery that lets one target be analysed multiple times under different platforms/flags — the foundation for cross-compilation and fat binaries.

16.2 Detailed Implementation Steps

Implement Configuration as a frozen, content-hashed bundle (platform, cpu, os, CompilationMode, flags) with ConfigurationId the BLAKE3 digest of its canonical encoding (I12 — structural equality, not allocation-order equality). Implement platform() and toolchain() rule registration and a deterministic toolchain resolver: highest-scoring match for (exec_compatible_with, target_compatible_with), ties broken by declaration order (no non-determinism from hash-map iteration, P3's discipline). Implement Transition (§11.5) for host and exec flavours, plus custom Starlark-declared transitions producing a new Configuration from a parent; a split transition produces multiple output configurations per dep edge, keying the analysis result by (label, configuration, split_id) — the fat-binary case. Cap transition chain depth at 16 (ADR-24's structural-hash discipline still needs a termination bound); report the full chain on overflow, matching §13's load()-cycle diagnostic style.

16.3 Deliverable

config::resolve_toolchains(target, platform) -> Toolchains; config::transition(cfg, transition) -> Configuration; a fixture demonstrating one target analysed under two ConfigurationIds (host + exec) simultaneously.

16.4 Acceptance Criteria

conformance/corpora/config/ fixtures cover host transitions, exec transitions, split transitions, and platform-constraint matching, 100% pass; two Configuration values built with fields inserted in different orders hash to the same ConfigurationId in every one of 50 randomised-order fixture reconstructions (I12); a transition chain exceeding depth 16 reports the full chain, not a stack overflow.

16.5 Conformance Fixtures

corpora/config/split_fat_binary.jsonl — one cc_binary target analysed for x86_64 + arm64 simultaneously via a split transition. corpora/config/depth_overflow.jsonl — 17 chained transitions, expects a reported chain, not a crash. corpora/config/id_stability .jsonl — same fields, different construction order, same ConfigurationId.

16.6 Pitfalls

A transition depending on a previously-applied transition can produce a configuration explosion — the depth cap (§16.2) exists specifically for this. Two configurations differing only in fields no rule reads must still hash to the same id unless configuration trimming is implemented; Phase 4 ships without trimming (PhaseDeferred("§16.4"), registered §37) — document this so a reviewer does not assume trimming exists yet. The exec configuration is not the host configuration: host is the platform buildd runs on; exec is the platform an action actually runs on (which may be a remote worker, §21) — conflating the two is a documented Bazel-era bug class (§5.3, BuildXL paper).

16.7 Performance Concerns

Without configuration trimming, a workspace with many independent flag axes multiplies ConfigurationId cardinality faster than necessary; the M4 query-latency target (§30) degrades gracefully but is the first thing to profile if trimming becomes necessary.

16.8 Edge Cases

A split transition on a target with zero matching toolchains (analysis error, not a silent empty result); a custom transition that returns a Configuration identical to its parent (must still be tracked at a distinct ConfigurationId only if content actually differs — identical content collapses to the same id by I12, which is correct, not a bug); a toolchain declaration with a constraint set matching multiple registered toolchains equally (broken by declaration order, deterministically).

16.9 Failure Analysis

ConfigError::NoMatchingToolchain { target, platform } names both; blast radius is the one ConfiguredTargetKey, not the whole build. ConfigError::TransitionDepthExceeded { chain } reports the full transition chain for bisection.

16.10 Operational Notes

cquery's --output modes (§22) surface ConfigurationId alongside each configured target so an operator debugging "why did this rebuild under a new configuration" can diff two ids' canonical field dumps directly.

17. Phase 5 — Skyframe Graph & Action Graph Construction

17.1 Objectives

Ship the load-bearing phase: a demand-driven, memoised, restart-based graph evaluator (Skyframe-style, ADR-03) over which every later phase's "what is the value of X" question is asked, plus the ActionGraph DAG it constructs as a side effect of evaluating ConfiguredTargetKeys.

17.2 Detailed Implementation Steps

Implement SkyFunction::compute (§11.6) for every SkyKey variant; a function that needs a dependency not yet computed calls env.request(k) and returns Restart([k]) — the engine schedules the dependency and re-enqueues the requesting key (Mokhov et al.'s "suspending scheduler," §5.2, applied directly). Implement the parallel evaluator: independent keys run concurrently on the tokio pool (ADR-10); a cycle detector raises SkyError::Cycle with the full chain the moment a key transitively depends on itself. Implement reverse-dependency tracking (rev_deps) so a FileKey invalidation (§22) can propagate upward; implement the early-cutoff check (I6): a Dirty node recomputes and, if its new value equals the cached one, halts propagation instead of marking NeedsRebuild. Construct the ActionGraph (§11.2's Action, keyed by ActionKey) lazily — an Action's inputs that are themselves generated artifacts register a dep edge to the owning ActionKey, with duplicate-output detection (I7) at construction. Cap restart count per key at 1024; a function that keeps requesting new deps past that bound is declared buggy and reported, not looped forever.

17.3 Deliverable

skyframe::Engine evaluates a root SkyKey with parallel execution; action_graph ::ActionGraph is constructed from every ConfiguredTarget reachable from a build's root targets; a byte-stable snapshot fixture proves the DAG topology is deterministic across hosts.

17.4 Acceptance Criteria

The engine sustains ≥ 1e6 trivial (no-op) SkyKey evaluations/second on the reference host (§4); a 10,000-target synthetic workspace cold-evaluates in < 30 s, warm-evaluates in < 1 s (§4); every fixture in conformance/corpora/action_graph/ produces a byte-identical DAG snapshot across Linux and macOS runners; a deliberately cyclic fixture raises SkyError::Cycle with the exact chain in 100% of 20 adversarial cases.

17.5 Conformance Fixtures

corpora/action_graph/cycle_self.jsonl — a ConfiguredTargetKey depending transitively on itself, expects SkyError::Cycle with the full path. corpora/action_graph/restart_loop.jsonl — a pathological function requesting 1025 distinct deps, expects SkyError ::TooManyRestarts. corpora/action_graph/snapshot_10k.jsonl — the byte-stable DAG for a 10,000-target synthetic workspace.

17.6 Pitfalls

A SkyFunction reading non-keyed state (a global, a thread-local) breaks incrementality silently — forbidden at the trait level; SkyEnv is the only legitimate side channel (I10, P6). A function that caches an intermediate value from an earlier dep without re-requesting it on every run produces stale values on incremental builds — the restart pattern requires requesting every dep every run, with no exceptions. Parallel evaluation of independent keys can deadlock if a key transitively depends on itself without the cycle detector catching it first — test the detector against the restart scheduler directly, not just against a static graph.

17.7 Performance Concerns

The critical-path-unaware naive scheduler (enqueue every ready key in arbitrary order) is acceptable for Phase 5's correctness bar; the critical-path-aware priority scheduler is deferred to §23 (Phase 11) once profiling shows where it matters (M8's restart-count target of ≤ 2 mean restarts/key is the interim gate).

17.8 Edge Cases

A ConfiguredTargetKey whose impl_fn itself triggers a load of a not-yet-loaded package (a legitimate cross-phase dependency, handled by the same Restart mechanism uniformly); an Action whose declared inputs include an artifact from a different configuration (a host-transition dependency, §16); a restart loop capped at exactly 1024 (the 1025th request is the trigger for SkyError::TooManyRestarts).

17.9 Failure Analysis

SkyError::Cycle { chain } — blast radius is every key in the cycle plus every rev-dep of any of them, all marked Failed, never silently dropped. SkyError::ComputeFailed { key, source } wraps the underlying typed error (a LoadError, AnalysisError, etc.) so the failure's true root cause is never erased by the graph layer.

17.10 Operational Notes

Every SkyFunction::compute call is a tracing span tagged with its SkyKey variant; aquery --output=graph (§22) renders the ActionGraph as DOT directly from this instrumentation, giving an operator a debuggable picture without a separate export step.

18. Phase 6 — Content-Addressed Store

18.1 Objectives

Ship the CAS (§11.4): the BLAKE3 digest function, the local object store and RocksDB index, the Merkle-tree encoding for directories, the remote REAPI-backed tier, materialisation strategies, and mark-and-sweep GC — the substrate every later cache and executor phase reads from and writes to.

18.2 Detailed Implementation Steps

Implement Digest::of_file (§11.1) with two paths: read(2) + BufReader for files under 4 MiB, mmap + BLAKE3 tree mode above that threshold (ADR-21) — the system's only unsafe block outside #![forbid(unsafe_code)]'s exceptions, carrying its own ADR per P10's discipline. Implement the local store layout: objects/<aa>/<bb>/<digest> two-level shard (ADR-08), write-then-fsync-then-rename for atomicity, small blobs (< 1 KiB) inlined in RocksDB to avoid per-file inode overhead. Implement Tree/FileNode/DirectoryNode (§11.4) with entries sorted by name and a deterministic canonical serialisation — the REAPI Directory message adopted as-is (§5.4 RFC). Implement the remote tier: FindMissingBlobs, BatchUpdateBlobs, BatchReadBlobs, ByteStream streaming for large blobs, over tonic/prost (ADR-11) with TLS. Implement materialisation as hardlink-with-copy-on-write-detection (ADR-22): after action completion, check (dev, inode) against the CAS object; a mismatch means the link broke and the output must not be re-uploaded under the original digest. Implement mark-and-sweep GC on a 24-hour schedule: mark every action-cache output digest, every live Skyframe artifact digest, and every materialised workspace file's digest; sweep anything unmarked whose last_used_at exceeds 7 days (I14 — never sweep a digest a live entry still references).

18.3 Deliverable

cas::LocalCas and cas::RemoteCas both implement CasStore (§11.4); Tree round-trips through the REAPI Directory proto; the materialiser hardlinks when possible and falls back to copy; GC runs unattended on schedule.

18.4 Acceptance Criteria

BLAKE3 digest throughput on a 1 GiB local file via the mmap path is ≥ 3 GiB/s on AVX2-capable reference hardware (M6, §4); every fixture in conformance/corpora/cas/ produces byte-stable digests across Linux and macOS; a GC sweep in a 24-hour soak test deletes 0 digests referenced by a live action-cache entry across 10,000 synthetic sweep cycles (I14); FindMissingBlobs for a 1,000-digest batch completes in ≤ 1 round trip.

18.5 Conformance Fixtures

corpora/cas/digest/large_file_mmap.jsonl — a 1 GiB fixture asserting mmap-path and read(2)-path digests are identical. corpora/cas/tree/unsorted_reject.jsonl — a Directory proto with out-of-order entries, expects CasError::UnsortedTree (§8.5). corpora/cas /gc_live_reference.jsonl — a digest referenced by an in-flight materialisation, expects the GC sweep to skip it.

18.6 Pitfalls

A link(2) across filesystems silently fails to ENOENT on some kernels — detect and fall back to copy rather than surfacing a confusing error. A blob whose stored size does not match its content is corruption; detect via re-digesting a sampled 1% of reads rather than paying the cost on every read. A directory with more than 65k entries overflows the kernel readdir buffer on ext4 — the materialiser must walk in chunks. BLAKE3's tree mode produces a different digest from sequential mode for identical content if the internal chunk size differs — pin the chunk size at BLAKE3's default and never change it (ADR-07's rollable tag exists precisely so a chunk-size change becomes a new DigestFunction variant, not a silent corruption). FUSE-lazy materialisation is explicitly out of scope here — PhaseDeferred("§18.5"), registered §37.

18.7 Performance Concerns

The mmap path is restricted to local-filesystem CAS only — mmap over NFS/FUSE/sshfs has unpredictable lazy-fault semantics (Dolstra's thesis chapter 5 on store correctness applies the same caution to network-backed stores). The two-level directory shard (ADR-08) keeps per-directory entry counts low enough that readdir stays fast even at CAS sizes past 10M objects.

18.8 Edge Cases

A symlink whose target resolves outside the tree it belongs to (a hermeticity violation caught at materialisation, not digest time); a 0-byte file (Digest::empty(), no special mmap path); a directory containing another directory with an identical name-and-digest pair at two tree positions (legal — Merkle trees dedupe by digest, not path).

18.9 Failure Analysis

A partial write (power loss between put and fsync) leaves a tmp/<random> orphan, never a corrupted final object — the rename is the only visibility point, so a crash mid-write is invisible to every reader. CasError::SizeMismatch { expected, actual } on read triggers an immediate re-fetch from the remote tier rather than serving corrupted bytes.

18.10 Operational Notes

GC sweep results (bytes freed, objects swept, objects skipped-as-live) are logged as one structured event per run and exposed as cas.gc.swept_bytes/cas.gc.skipped_live metrics (§26); a sweep that skips an anomalously high fraction of "live" objects is the leading indicator of an I14 bug and pages on-call per the stale-cache runbook (§26).

19. Phase 7 — Local Sandboxed Execution

19.1 Objectives

Replace Phase 0's unsandboxed subprocess executor with a real hermetic sandbox on Linux and macOS: an action's view of the filesystem, environment, and network is exactly its declared inputs/tools/env, nothing else (P1, I1).

19.2 Detailed Implementation Steps

Implement the Linux sandbox via unshare(2) (user, mount, PID, network, IPC, UTS namespaces) + pivot_root(2) (mount a tmpfs root first, then pivot — ordering matters, §19.6) + bind mounts: read-only /sandbox/inputs, read-write /sandbox/outputs, read-only /sandbox/tools; no network namespace veth by default (only lo); a seccomp filter rejecting mount, unshare, clone(CLONE_NEWNET), kexec_load; a cgroup bounding CPU, memory, and PID count (Tanenbaum & Bos, §5.1, applied directly — no privileged daemon, no setuid binary, per ADR-05). Implement the macOS sandbox via sandbox-exec with a per-action-generated policy restricting file-read*/file-write* to the declared paths and denying network by default. Implement the fixed sandbox environment (PATH, HOME=/sandbox /home, TMPDIR, LC_ALL=C, LANG=C, TZ=UTC, §19.3's table) plus the action's declared env only — no variable is ever forwarded from buildd's own process. Implement the action lifecycle (§8.1's Executing state, in order): materialise inputs, create empty output dirs, construct the sandbox, set env/cwd/ulimit/cgroup, fork+exec, wait and capture stdout/stderr, digest and upload declared outputs, build ActionResult, insert into the action cache (§20), tear down.

19.3 Deliverable

executor::LocalExecutor::execute(action, inputs) -> ActionResult; the Linux sandbox passes every hermeticity probe in conformance/corpora/sandbox/; the (smaller) macOS probe set passes; every action's stdout/stderr is captured and uploaded as a CAS blob.

19.4 Acceptance Criteria

Sandbox construction overhead is < 5 ms on Linux, < 20 ms on macOS (§4); 100% of the seven hermeticity probes (§19.5) fail in exactly the documented way (a probe that succeeds at leaking is the test failure, not the pass condition); a timed-out action is killed with SIGTERM then SIGKILL after 5 s, with 0 partial outputs uploaded.

19.5 Conformance Fixtures

corpora/sandbox/network_leak.jsonl — curl https://example.com, expects ENETUNREACH. corpora/sandbox/home_leak.jsonl — read $HOME/.bashrc, expects failure (empty sandbox $HOME). corpora/sandbox/path_leak.jsonl — exec a binary outside the declared tool set, expects ENOENT. corpora/sandbox/tmp_persistence.jsonl — write /tmp/leaked, then a fresh sandbox asserts it does not exist.

19.6 Pitfalls

pivot_root requires the new root to already be a mount — mount the tmpfs first, then pivot, or the syscall fails outright. setresuid inside a user namespace fails on some kernels if the seccomp filter is applied before namespace creation — order matters, and getting it backwards produces a cryptic EPERM far from its root cause. The macOS sandbox can be bypassed by a binary that re-execs itself outside the policy (the policy is per-process) — mitigate by refusing to run setuid binaries found in the input set, not by trying to patch the policy language. LC_ALL=C breaks tools reading UTF-8 filenames; allow an explicit opt-out via execution_requirements["locale"] rather than a global relaxation.

19.7 Performance Concerns

Materialisation via hardlink runs at native link(2) syscall throughput (typically 100,000+/s on ext4); a cross-filesystem CAS forces the copy fallback (§18.6) which is markedly slower — keep the CAS and the workspace on the same filesystem in the default deployment topology (§26).

19.8 Edge Cases

A long-running action exceeding its declared Action.timeout (§11.2); an action whose declared inputs include a directory with a broken symlink inside it (rejected at materialisation, not silently skipped); a sandbox construction failure on a kernel missing a required namespace flag (the build fails loudly per P14 — it never silently runs unsandboxed).

19.9 Failure Analysis

A sandbox-creation failure surfaces ExecError::SandboxUnavailable { reason } and fails the specific action, not the whole daemon; blast radius is bounded to that action's dependents. A killed (SIGKILL) action's partial output directory is discarded entirely before the next attempt — no partial-write contamination across retries.

19.10 Operational Notes

Every sandbox teardown emits sandbox.lifecycle.duration_ms broken down by phase (materialise/construct/execute/teardown); the sandbox-failure runbook (§26) walks an operator from a SandboxUnavailable alert to the specific missing kernel feature.

20. Phase 8 — Action Cache & Cache Correctness

20.1 Objectives

Ship the action cache: the layered local/remote lookup, the ActionKey derivation procedure (§8.2), and the double-keyed poisoning defence (ADR-14, I9) — the component whose correctness this entire blueprint is organised around (P7).

20.2 Detailed Implementation Steps

Implement LocalActionCache (RocksDB-backed) and RemoteActionCache (REAPI ActionCache client), composed by a LayeredActionCache: lookup checks local then remote; update writes local synchronously and remote in the background. Implement ActionKey::derive exactly per §8.2's canonicalisation procedure — every field sorted/fixed-width/domain-separated before hashing, salted per ADR-04 so an algorithm revision invalidates old entries without deleting them (they age out via §18's GC). Implement the double-keying defence (ADR-14): store (ActionKey, result_digest) pairs; on lookup, recompute result_digest from the fetched ActionResult and reject on mismatch, emitting cache.poison.detected (I9) — this is the single check every remote-cache trust decision in the system reduces to. Implement partial-hit handling: a cache hit whose declared output digest is not fetchable from CAS falls back to execution rather than failing the build outright.

20.3 Deliverable

LocalActionCache and RemoteActionCache both satisfy the ActionCache trait (§11.3); make repro-check runs a full build twice and asserts every action is a cache hit the second time.

20.4 Acceptance Criteria

Action-cache lookup latency is p50 ≤ 40 µs, p99 ≤ 100 µs warm/local (M7, §4); every fixture in conformance/corpora/action_cache/ — including the poison pair (§20.5) — passes; a full two-run repro-check on the reference 100-target workspace shows 100% cache-hit rate on the second run with 0 subprocess executions.

20.5 Conformance Fixtures

corpora/action_cache/poison_pair.jsonl — a hand-curated (key, result) plus a (key, result_with_one_byte_changed); the cache must hit the first and reject the second with cache.poison.detected (I9). corpora/action_cache/mtime_insensitivity.jsonl — two actions identical except source mtime, expects the same ActionKey (I3). corpora/action_cache /salt_bump.jsonl — an entry stored under salt=0, looked up under salt=1, expects a miss, not a stale hit.

20.6 Pitfalls

Including mtime anywhere in ActionKeyInput is the canonical stale-cache bug (§29 in the original literature's framing) — the action becomes uncacheable across machines the instant clocks disagree; use content digests exclusively, with mtime only as a fast pre-check before re-digesting (§22.2), never as part of the key itself. Failing to canonicalise env as a sorted map produces different keys for semantically-equal actions. A command_argv element with an embedded \0 or \n confuses some remote services — reject such arguments at the rule level (§15), before an Action is ever constructed. output_paths must be the declared outputs, never the observed ones — a rule writing to an undeclared path is a hermeticity bug (§19), not a key-derivation bug.

20.7 Performance Concerns

The local RocksDB tier is on every action's hot path; the layered cache's local-first lookup order (§20.2) means a warm local build never touches the network even when a remote tier is configured — this is the primary reason M2's 500 ms warm-build target is achievable at all.

20.8 Edge Cases

A cache entry whose ActionResult outputs reference a CAS digest that has since been garbage-collected (I14 should prevent this; if it happens anyway, it is treated identically to a poisoning detection — reject and re-execute, then investigate as a GC bug, not a cache bug). A remote cache that returns NOT_FOUND (a legitimate miss) versus one that returns an empty ActionResult (a poisoning attempt or a server bug — rejected identically, logged distinctly).

20.9 Failure Analysis

cache.poison.detected is a Sev-1-class signal (T1, §24); a single occurrence pages on-call per the stale-cache runbook (§26) even though the immediate build recovers by falling back to execution — the build is fine, the cache's trustworthiness is the incident. A salt bump that was not deliberate (accidentally touching the encoding without an ADR) manifests as a mass cache-miss event, distinguishable from an attack by its blast radius (everything misses, nothing is individually poisoned).

20.10 Operational Notes

cache.hit.rate (windowed, 5-minute) is the headline dashboard metric (§26); a sustained drop is the leading indicator of either a salt bump, a non-deterministic action newly introduced (§8.4's early-cutoff failure mode), or a remote-cache outage — the runbook disambiguates the three in order.

21. Phase 9 — Remote Execution & Persistent Workers

21.1 Objectives

Ship the REAPI remote-execution client and the persistent-worker subsystem: an action declared requires-remote=1 dispatches to a remote worker fleet; a worker-eligible action runs in a long-lived process pool amortising interpreter/compiler startup across requests.

21.2 Detailed Implementation Steps

Implement the REAPI client (tonic/prost, ADR-06, ADR-11) against the four services: Capabilities (discover server support before assuming BatchUpdateBlobs exists, §5.3's NativeLink lesson), ContentAddressableStorage, ActionCache, Execution (Execute/WaitExecution, a long-running Operation the client polls or streams). Implement retry policy (§21's BuildXL-paper-informed model, §5.2): network/scheduler errors retried with exponential backoff (50 ms → 30 s cap, 5 attempts); action failures (non-zero exit) are never retried automatically — a flaky re-run-until-green is itself a determinism bug (P4); internal server errors retry twice, then fall back to local execution only if --remote_local_fallback is explicitly set (P14 — no silent fallback). Implement the persistent-worker protocol (§5.4 RFC): length-prefixed WorkRequest/WorkResponse protobufs over the worker's stdin/stdout; a WorkerPool keyed by (mnemonic, binary_digest, args_digest, platform); multiplex-capable workers handle concurrent request_ids, others serialise. Implement worker isolation bounds (I13, P12): kill any worker exceeding 1 hour lifetime or 4 GiB memory; blacklist a worker whose output fails the action cache's content-revalidation (§20) on an otherwise-identical input — the signal that a worker's internal state has leaked between requests.

21.3 Deliverable

executor::RemoteExecutor::execute(...) and executor::WorkerExecutor::execute(...) both satisfy ExecutionEngine (§11.6); an integration test runs against NativeLink (§5.3) in docker-compose and asserts a cold cross-machine build produces byte-identical output to the local-executor path.

21.4 Acceptance Criteria

Remote-cache single-stream throughput on a 1 GiB blob is ≥ 200 MiB/s (M5, §4); RBE round-trip for a trivial cache-miss action is ≤ 250 ms p50 to a local REAPI server (M10); FindMissingBlobs batches up to 1,000 digests per round trip (§21.2); a worker exceeding 4 GiB memory is killed and removed from the pool in 100% of 200 synthetic overflow fixtures (I13); local, remote, and worker execution of the same Action produce byte-identical ActionResult.output_files digests in the cross-engine determinism fixture set.

21.5 Conformance Fixtures

corpora/remote/reapi_replay.jsonl — serialised REAPI request/response pairs replayed byte-for-byte. corpora/worker/protocol_trace.jsonl — a captured WorkRequest/WorkResponse exchange for replay. corpora/remote/capability_gate.jsonl — a server lacking BatchUpdateBlobs, expects the client to fall back to ByteStream after checking Capabilities first.

21.6 Pitfalls

The REAPI's Action/Command messages have a different schema from this system's internal Action (§11.2) — the conversion layer is a real translation, not a cast, and must be fixture-tested for byte-identical encoding on stable inputs. A worker that buffers stdout writes deadlocks the protocol — workers must flush after every response (a documented requirement of the protocol, not an implementation detail). A worker whose binary digest changes mid-build (e.g. the compiler itself was rebuilt) invalidates the entire pool for that key; draining stale workers must not orphan their in-flight requests. A server responding NOT_FOUND on GetActionResult is a legitimate miss; one responding with an empty ActionResult is a poisoning attempt or a bug (§20.6) — reject and log identically to the local-cache poisoning path (ADR-14).

21.7 Performance Concerns

RBE batching — checking 1,000 digests in one FindMissingBlobs round trip instead of 1,000 separate calls — is the single highest-leverage remote-execution optimisation available before any server-side change; implement it before touching worker pooling.

21.8 Edge Cases

A remote executor that accepts an Execute call then never completes it (network partition mid-flight) — WaitExecution's deadline triggers the retry policy, not an indefinite hang. A worker request whose declared inputs include a file the CAS has since garbage-collected (I14 should prevent this; if seen, treated as a cache-layer bug, not a worker bug). Two actions differing only in --target=x86_64 vs --target=arm64 route to two distinct workers via the args_digest component of WorkerKey.

21.9 Failure Analysis

RemoteError::CapabilityMismatch { needed, supported } fails fast before any wasted upload, rather than discovering the gap mid-transfer. A blacklisted worker's pending requests are redispatched to a freshly spawned worker of the same key, never silently dropped — blast radius is one retry's added latency, not a build failure.

21.10 Operational Notes

remote.execute.p50/p99, worker.pool.blacklist_count, and worker.pool.active_count are the three headline remote-execution dashboard metrics (§26); the remote-cache-miss runbook walks from a p99 latency alert to a Capabilities mismatch as the most common root cause.

22. Phase 10 — Query Language & Incrementality Engine

22.1 Objectives

Ship the Datalog-flavoured query language (query/cquery/aquery, ADR-15) over the target/configured-target/action graphs, and the file-watcher-driven incrementality engine that turns a one-byte source edit into the minimal rebuild closure (P4, I6).

22.2 Detailed Implementation Steps

Implement the query grammar (§5.4 RFC's Datalog-flavoured spec): deps, rdeps, allpaths, somepath, kind, attr, labels, filter, composed via union/intersect/ except; parse to an AST, evaluate via a graph walker (P13 — a language, not a string-matching hack). Distinguish query (unconfigured target graph, post-§14), cquery (configured graph, post-§16 — selects collapse, transitions expand), and aquery (action graph, post-§17 — output is Action descriptions). Implement the file watcher via notify (ADR-16: inotify/FSEvents/kqueue behind one trait), coalescing events within a 50 ms window and dispatching FileKey invalidations into Skyframe (§17). Implement the digest cache (§8.2's sibling for source files): keyed by (path, dev, inode, mtime, size), value is the BLAKE3 digest; on a Modify event, a matching (dev, inode, mtime, size) tuple validates the cached digest without re-reading the file — the fast path that makes touch-without-content -change cheap. Implement the change-pruning walk: every changed FileKey enqueues Dirty; each dequeued Dirty node recomputes, and if the new value equals the old, halts (I6's early-cutoff, concretely implemented here) — otherwise marks NeedsRebuild and propagates to rev_deps.

22.3 Deliverable

query::parse(s) -> QueryExpr and query::eval(expr, &workspace) -> TargetSet; the CLI surfaces build query, cquery, aquery; watcher::Watcher emits coalesced events the Skyframe engine consumes end to end.

22.4 Acceptance Criteria

query 'deps(//...)' over a 10,000-target workspace completes in ≤ 1 s (M4, §4); every fixture in conformance/corpora/query/ and conformance/corpora/incrementality/ passes; a one-file source change in a 10,000-target synthetic workspace triggers rebuild of at most the recorded direct-plus-transitive-rdep closure — 0 over-rebuild cases across 500 randomised-edit fixtures (incrementality.minimal_closure, I6).

22.5 Conformance Fixtures

corpora/query/eval/rdeps_10k.jsonl — rdeps(//..., //x:y) over a 10,000-target synthetic graph, target set matched exactly. corpora/incrementality/single_file_closure.jsonl — one source edit, expects the exact recorded rebuild set, not a superset. corpora/incrementality /digest_cache/touch_no_change.jsonl — a touch with unchanged content, expects 0 re-digests beyond the (mtime, size) check.

22.6 Pitfalls

deps(//x:y, 1) counts dep edges, not target levels — a target depending on itself via an alias is a frequent off-by-one fixture gap. rdeps(//..., //x:y) over a 100k-target workspace is the slow case if the reverse-dep index is recomputed per query instead of maintained incrementally in Skyframe (§17) — cache it, don't rebuild it. inotify's default watch limit (/proc/sys/fs/inotify/max_user_watches, typically 8192 on stock distributions) is exceeded by a 100k-file workspace — buildd startup must raise it and fail loudly (P14) if it cannot, rather than silently missing events. FSEvents on macOS coalesces with a default ~1 s delay; register with the no-defer flag to keep incrementality latency inside M3's budget.

22.7 Performance Concerns

Pre-computing the reverse-dep index once per loaded workspace, rather than per query, is the difference between rdeps being usable at 100k-target scale and not; this is the single highest-leverage optimisation in this phase.

22.8 Edge Cases

A query reaching into a not-yet-loaded package triggers a load as a side effect (intentional, can be slow — documented, not a bug); a symlink whose target changes is not a content change to the symlink itself — the watcher tracks symlink identity separately from target content; a file modified by a process outside buildd entirely (e.g. a manual sed -i) is still picked up correctly by the next build via the watcher.

22.9 Failure Analysis

A watcher that silently drops events past the inotify limit is the single worst failure mode in this phase — it manifests as "I changed the file and nothing rebuilt," indistinguishable from a genuine I6 bug without the watcher's own health metric (§22.10). A query AST that fails to parse returns a typed QueryError with the offending token span, matching the Starlark diagnostic style (§13.10) for consistency.

22.10 Operational Notes

watcher.events.dropped (should be permanently 0; a non-zero value is the leading indicator of the inotify-limit failure mode above) and skyframe.cutoff.count vs skyframe.rebuild.count (the ratio is the direct evidence early cutoff is doing its job) are the two dashboard metrics unique to this phase (§26).

23. Phase 11 — Performance & Hermeticity Hardening

23.1 Objectives

Take the system from correct to fast and from probabilistically-hermetic to audited-hermetic: critical-path-aware scheduling, lock-free CAS reads, streaming action output, RBE batching, plus the cross-host byte-identical oracle and the long-running fuzz canary that together are the release gate.

23.2 Detailed Implementation Steps

Implement the critical-path-aware Skyframe scheduler (§17.7's deferred item): prioritise SkyKeys on the longest-duration dependency chain to a root, replacing the naive enqueue-in-arbitrary-order scheduler. Implement a lock-free, read-mostly CAS index structure for the hot lookup path (an evmap-style structure trading slower writes for lock-free reads — Kleppmann's read/write tradeoff framing, §5.1, applied to this specific hot path); gate any staleness risk behind the content-revalidation already required by I9. Implement action-result streaming: a long-running action's stdout is written to a temporary file as produced and finalised with one rename, never buffered fully in memory (a verbose 100 MiB compile log must never live in RAM at once). Implement RBE request batching across concurrently in-flight actions (§21.7's deferred item, now built). Implement the hermeticity probe suite (§19's seven probes, §24.1) as an automated, scheduled audit; implement the cross-host byte-identical oracle (I2, I5): build a curated fixture set (a trivial genrule, a rust_library, a cc_library with a pinned random seed) on both Linux and macOS runners in CI and assert every output digest matches. Implement the 30-day fuzz canary across all seven targets (ADR-19) on dedicated hardware, reporting new crashes/panics/stuck-states/coverage delta.

23.3 Deliverable

Benchmarks M1–M12 (§30) meet target on the reference host; the cross-host oracle is green for 14 consecutive days; the fuzz canary log is published under docs/architecture/ per run.

23.4 Acceptance Criteria

The critical-path scheduler reduces mean Skyframe restarts/key to ≤ 2 (M8, matching §4's constraint); CAS lookup under the lock-free index sustains ≥ 500,000 reads/s with 0 observed stale reads across a 24-hour soak with concurrent writers; the cross-host oracle shows 0 divergences across 3 fixture classes for 14 consecutive days; the 30-day fuzz canary reports 0 crashes, 0 panics across all seven targets (M12).

23.5 Conformance Fixtures

corpora/cross_host/genrule_trivial.jsonl, corpora/cross_host/rust_library.jsonl, corpora/cross_host/cc_library_pinned_seed.jsonl — the three byte-identical-across-hosts classes. corpora/sandbox/hermeticity_full_suite.jsonl — the complete seven-probe automated run (§19.5, now scheduled rather than ad hoc).

23.6 Pitfalls

A naive parallel scheduler that fills the run queue with low-priority keys starves the critical path — the priority queue from §23.2 is not an optimisation, it is the fix for a real pathology observable in the pre-Phase-11 scheduler. mmap on NFS/FUSE/sshfs has surprising lazy-fault semantics (§18.7's caution repeated because Phase 11's profiling work is exactly where someone is tempted to relax the local-fs-only restriction under throughput pressure — don't). evmap-style reads see eventually-consistent writes; on rapid invalidate-then-rebuild sequences a stale read is a real risk, caught only by I9's content-revalidation — verify that path is exercised by the soak test, not assumed.

23.7 Performance Concerns

This entire phase is the performance-concerns phase; the specific numbers are gated in §30's M# table and are the actual CI release gate, not aspirational targets.

23.8 Edge Cases

A cc_library embedding __DATE__/__TIME__ C macros (patched via the default toolchain's -D__DATE__=""); a test reading /proc/cpuinfo or /dev/random (fundamentally non-hermetic — documented at the rule level, marked no-cache=1, never silently cached); a divergence fixture where two hosts produce different digests (committed to corpora/cross_host/divergences/ with an ADR, per T-class incident handling, §24).

23.9 Failure Analysis

A cross-host divergence is a hard release-gate failure, not a warning — it blocks Sealed status (§29) until root-caused and either fixed or explicitly ADR'd as an accepted platform difference. A fuzz-canary crash blocks the next release; a panic opens an issue; a stuck state (no progress in 60 s) opens an issue — the three are triaged distinctly (§29).

23.10 Operational Notes

The 30-day fuzz canary's log and the cross-host oracle's daily report are both published to the same operational dashboard (§26) an on-call engineer checks before approving any release — this phase is where "correct" becomes "provably correct, continuously."

Dashboards: one per phase's headline metric (cache hit rate; restart/cutoff ratio; remote p99; worker blacklist count), plus one incident-response dashboard combining all Sev-1 signals (cache.poison.detected, hermeticity.probe.result=fail, crosshost.divergence). Alerting philosophy: page on any cache.poison.detected or hermeticity-probe failure immediately (T1, T3); page on cache.hit.rate sustained below 80% for 15 minutes (leading indicator of FM-1/FM-2/FM-7); ticket (not page) on worker.pool.blacklist_count increments. SLOs: warm build p99 ≤ 1 s; incremental rebuild p99 ≤ 8 s (§4); cache-hit rate ≥ 95% on an unchanged re-build. Incident response: the runbooks in docs/runbooks/ (stale-cache.md, non-determinism.md, sandbox-failure.md, remote-cache-miss.md) are the first read for on-call, each keyed to a specific FM-# or T#. Backup/restore: the RocksDB-backed Skyframe graph and action cache are periodically snapshotted; a restore replaces buildd's data directory and triggers a cold-start integrity check (I11). Deployment topology: one buildd per workstation/CI runner; remote cache and remote execution are shared network services behind a load balancer, independently scalable. Canary/rollback: a new buildd release runs the full conformance suite (§28) plus a 24-hour shadow build against production traffic before promotion; rollback is a binary swap plus a cold-start reload (≤ 8 s, §4).

27. Compatibility & Versioning

Wire compatibility: the REAPI v2 protocol (ADR-06) is versioned upstream; this system tracks it via Capabilities negotiation (§21.2), never assuming a fixed server version. Storage compatibility: RocksDB column-family schemas are versioned; a schema change ships behind a migration that runs on cold start, gated by a schema-version key in the index. Action-key compatibility: the Salt (§11.2, ADR-04) is the sole compatibility boundary for the action cache — bumping it is a breaking change to every existing entry, handled by aging out rather than migrating (§20.6). API stability: the Starlark-side ctx.* surface (§15.2) is the public rule-author API; additive changes (new ctx.actions.* method) are non-breaking; removing or changing an existing method's signature requires a documented deprecation cycle in CHANGELOG.md. Deprecation policy: a deprecated native rule or ctx method emits a starlark.deprecation_warning for two minor releases before removal. SemVer policy: the CLI/daemon RPC protocol and the REAPI client follow SemVer; a MAJOR bump is required for any wire-incompatible change. Rolling-upgrade guarantees: a buildd of version N+1 can read a RocksDB store written by version N within the same MAJOR version; cross-MAJOR upgrades require a documented migration path in docs/architecture/.

28. Testing & Verification Strategy

Unit: per-crate, standard cargo test, one test module per source file (§10). Property: ActionKeyInput canonicalisation is property-tested for permutation-invariance (any field reordering during construction yields the same key, I3/I12's shared discipline). Differential: local vs remote vs worker execution of the same Action must produce byte-identical ActionResult digests (§21.4) — the cross-engine determinism oracle. Fuzzing: seven cargo-fuzz targets (ADR-19) seeded from corpora/adversarial/, escalating to a 30-day canary in Phase 11 (§23). Chaos: a fault-injection harness kills buildd mid-RocksDB-write to exercise FM-5's recovery path; a network-partition harness exercises FM-7's retry policy. Deterministic replay: the Skyframe simulator (§7's debugging methodology, skyframe::sim) replays recorded event logs with one assertion per invariant (I1–I14). Soak: a 24-hour soak on a 10,000-target workspace with randomised source edits targets zero stale-cache events (M11, §30). Conformance: the 21-bucket suite (§17.4, §18.4, §19.4, §20.4, §21.4, §22.4, §23.4 collectively) is the system's ground truth, byte-exact, no fuzzy comparisons — a bucket regression (Pass → Fail) blocks merge. Performance-regression gating: every M# target in §30 is a CI gate via criterion per-host baselines (ADR-18), not an aspirational number. Every fixture ties back to the System Invariants (§7) and to each phase's N.5 Conformance Fixtures.

29. Build & Release Engineering

Reproducible builds: the system builds itself with itself (§23's dogfooding extends to release engineering) — Stage 0 (cargo build), Stage 1 (build //buildd:buildd under the Stage-0 binary), Stage 2 (the Stage-1 binary rebuilds itself); Stage-1-vs-Stage-2 byte-identical output is the strongest reproducibility test available and gates Sealed status. Artifact signing: release binaries are signed; the signature is verifiable against a published key. SBOM: generated per release from the Cargo.lock dependency graph. Release channels: stable (tagged, signed) and nightly (unsigned, from main post-conformance). CI/CD topology: ci.yml (unit + integration), conformance.yml (§28's 21-bucket suite), fuzz.yml (1-hour smoke per target), hermeticity.yml (§19.5's probe suite, Linux + macOS), reproducibility.yml (daily cross-host oracle, §23). Version stamping: the release binary embeds its own build's ActionKey chain root — the tool that attests to its own provenance using its own mechanism. Provenance/attestation: an in-toto attestation chain is generated from the release build's own action graph (PhaseDeferred("§37") — SLSA-3 is a stretch target, not a Phase 0–11 requirement). Dependency auditing: cargo-deny (license + advisory + duplicate-version checks, ADR-20) runs on every push; a new advisory against a pinned dependency opens an issue automatically.

30. Performance Engineering

Methodology: criterion (ADR-18) with per-host baselines under benchmarks/results/ (§10) — a build that takes 20 s on a workstation and 90 s on a small CI instance is compared only against its own host's baseline, never cross-host. Profiling: a flamegraph recipe (tools/flamegraph.sh, §10) is the standard first step for any M# regression. Allocation/ lock/cache/syscall analysis: the lock-free CAS index (§23.2) and the mmap digest path (§18.2, ADR-21) are the two allocation/syscall-sensitive hot paths profiled every release. Tail-latency analysis: p99, not just p50, is gated for every latency-shaped M# target below — a system that is fast on average and occasionally catastrophic is not fast.

31. Scalability Analysis

Stays constant: action-cache lookup latency (O(1) RocksDB point read, independent of workspace size, M7); CAS digest throughput per file (independent of workspace size, M6). Grows: buildd resident memory (O(target count) for the Skyframe graph, §34 C2); cold-start time (O(RocksDB size), §4); rdeps query latency absent a maintained reverse-dep index (O(graph size) if recomputed per query, O(1) amortised if maintained incrementally, §22.7). Named bottlenecks, in order: (1) the reverse-dep index maintenance cost at scale (§22.7) — the first thing to profile past ~50,000 targets; (2) ConfigurationId cardinality without trimming (PhaseDeferred("§16.4"), §16.7) — the second, once cross-compilation flag axes multiply; (3) single-daemon memory ceiling (§4's 4 GiB row) — the third, requiring graph sharding beyond ~200,000 targets. Horizontal scaling: the remote-cache and remote-execution tiers scale independently and horizontally (stateless REAPI servers behind a load balancer); the Skyframe graph itself does not shard in Phase 0–11 — PhaseDeferred("§31"), a distributed multi-region scheduler, registered §37. Vertical scaling: more cores directly reduces cold-build wall-clock (M1) up to the critical-path length (§23.2); beyond that, additional cores are idle. Coordination overhead: remote execution's RTT budget (§4) is the practical floor on any single action's latency, regardless of local core count. Practical ceiling: ~200,000 targets per single buildd graph before the memory ceiling (§4) forces sharding; the lever beyond it is the deferred distributed scheduler (PhaseDeferred("§31")).

32. Mental Models & First Principles

  • MM1 — A build is a memoized pure function. Treat the whole system as memoizing f(declared inputs) → outputs. Predicts: two calls with equal declared inputs must return equal outputs, full stop. Bug class without it: engineers reach for "clean and rebuild" instead of trusting the cache, because they never internalised what "equal inputs" even means. Applies in §8.2, §20.
  • MM2 — The graph is discovered, not built. Skyframe's restart model means evaluation of one node can discover it needs another, mid-computation. Predicts why a "topological sort first" design breaks under dynamically-discovered dependencies. Bug class without it: assuming the whole DAG can be computed before any evaluation starts. Applies in §17.
  • MM3 — A cache hit is a claim, not a fact. Trust is derived from re-verified content, never from the cache's authority. Predicts the existence of double-keying and content-revalidation. Bug class without it: silently trusting a compromised or merely buggy cache server. Applies in §20.6, T1.
  • MM4 — Hermeticity is a boundary you draw, not a property you hope for. The sandbox is an explicit, enumerable boundary (namespaces, mounts, env). Predicts exactly which leaks (network, $HOME, /tmp, PATH) must be closed one at a time. Bug class without it: believing "no obvious side effects" is the same as hermetic. Applies in §19.
  • MM5 — Early cutoff turns "changed" into "possibly changed." Dirty does not mean different — it means "must be checked." Predicts a minimal rebuild set even when many nodes are marked dirty simultaneously. Bug class without it: over-rebuilding on every source edit because every dirty node is treated as needing full re-execution. Applies in §17.4 (I6), §8.3.
  • MM6 — The action key IS the cache contract. What fields enter ActionKeyInput defines exactly what "the same build" means. Predicts the tradeoff: adding a field trades hit rate for correctness; removing one trades correctness for hit rate. Bug class without it: ad hoc field additions/removals with no understanding of which side of the tradeoff moved. Applies in §8.2, §20.2, ADR-04.
  • MM7 — Configuration is a value, not a flag soup. Content-hashing Configuration (I12) means two constructions with equal effective fields always agree, regardless of build order. Predicts that fat binaries and cross-compilation fall out of split transitions for free. Bug class without it: a string-concatenated flag cache that misses on harmless reordering. Applies in §16.
  • MM8 — A distributed cache is a slower, less trustworthy local cache, not a different kind of thing. Apply the identical validation discipline to the remote tier, with a network RTT budget layered on top. Predicts REAPI's content-addressed, capability-negotiated design. Bug class without it: treating "the cache is remote" as license to skip the validation the local tier requires. Applies in §21, §4.

34. Back-of-Envelope Capacity Model

  • C1 — Skyframe node count, 100k-target workspace. ≈5 SkyNodes per target (package, target, configured-target, action, artifact) × 100,000 targets = 500,000 nodes.
  • C2 — buildd resident memory. 500,000 nodes (C1) × ~4 KB average per-node overhead (key + value + dep list + SmallVec slack) ≈ 2.0 GiB, chained directly against §4's ≤ 4 GiB ceiling — leaving headroom for DepSet interning and RocksDB write buffers.
  • C3 — CAS storage footprint. 100,000 targets × ~50 KB average output size = 5 GB logical; × 1.3 storage-amplification ceiling (§4, ADR-08) ≈ 6.5 GB physical CAS size.
  • C4 — Sandbox FD budget. ~10 FDs per sandboxed action (namespaces + bind mounts) × 256 max concurrent local actions (§4) = 2,560 FDs, well inside the 65,536 ulimit (§4).
  • C5 — Cold-build wall-clock at scale. 100,000 targets × 3 actions/target average = 300,000 actions ÷ 1,600 actions/min (M1's per-minute basis, §4/§30) ≈ 187 minutes (≈ 3.1 hours) for a fully cold build at this scale — the number that makes M2/M3's cache-hit and incremental targets the actual product, not cold build speed.
  • C6 — Cold-start digesting cost. 100,000 source files × ~20 KB average = 2 GB total ÷ 3 GiB/s per core (M6, §4) ≈ 0.67 s single-core, parallelisable across cores near-linearly.
  • C7 — inotify watch count. 100,000 files ÷ ~20 files per directory (directory-level watching) ≈ 5,000 watches — under a raised max_user_watches (§22.6) though over the stock-distribution default of 8,192 is not guaranteed once file count multiplies by 2×.
  • C8 — Remote-cache bandwidth, worst case. 1,600 actions/min (M1 basis) × ~1 MB average input-tree size ÷ 60 s = ≈ 26.7 MB/s, well under M5's 200 MiB/s single-stream ceiling (§4, §30) — confirming remote cache is not the cold-build bottleneck at this scale.
  • C9 — Worker-pool memory (separate budget from buildd itself). 50 concurrent persistent workers × ~200 MB average resident compiler process = 10 GB — deliberately outside buildd's own 4 GiB ceiling (C2), motivating a separate host/cgroup budget for the worker pool in production topology (§26).

36. Alternative Architectures (Roads Not Taken)

A1 — Static topological build (Make-style).

sources ──► [static DAG, computed once] ──► topo-sort ──► execute in order

Regime where it wins: a small, fully-static dependency set known entirely before any evaluation starts (an embedded firmware repo with a hand-maintained Makefile). Real system: GNU Make, Ninja (§33). Rejected because: breaks the moment a rule's dependencies are themselves discovered during evaluation (generated headers, dynamic codegen) — exactly the case Mokhov et al. (§5.2) and Mitchell's monadic-deps paper (§5.2) identify as requiring a suspending scheduler (ADR-03).

A2 — Purely functional derivation model (Nix-style), no separate action cache.

inputs ──► derivation (content-hashed spec) ──► store path IS the cache key

Regime where it wins: whole-system reproducible deployment where "the same store path" across machines is the primary guarantee needed (NixOS). Real system: Nix (Dolstra, §5.1). Rejected because: derivation-per-output granularity is coarser than an action-key-per- compile-step (§8.2) — a large multi-language monorepo needs finer incremental rebuilds than one hash per whole-package derivation provides.

A3 — Centralised build-as-a-service (no local daemon, thin client only).

CLI ──(every request)──► always-on central service ──► owns graph, cache, execution

Regime where it wins: a single organisation's global monorepo at extreme scale, where a centrally-operated service amortises graph state across every engineer (Google's internal Blaze/Forge model, documented in the Bazel engineering blog posts, §5.2). Rejected because: requires an always-connected central service, materially worsening the offline/laptop developer experience this system's local buildd (P11, ADR-09) is designed to preserve, and demands an operational investment not justified below Google's scale.

A4 — Flat compiler-invocation cache, no target/action graph (ccache/sccache-style).

compiler invocation ──► hash(args+preprocessed source) ──► cached object file

Regime where it wins: a single-language, single-toolchain project with a simple, mostly linear dependency structure, where wrapping the compiler invocation directly is sufficient (ccache, sccache, §5.3-adjacent). Rejected because: no target/action graph means no query language (§22), no cross-language incremental-rebuild closure (§8.3), and no notion of "the minimal rebuild set" across a large multi-language monorepo — the exact capability this entire blueprint exists to provide.

38. Glossary

  • Action — a unit of executable work with fully declared inputs, tools, outputs, command, and environment (§11.2).
  • ActionKey — the BLAKE3 digest of an action's canonical ActionKeyInput encoding; the cache lookup key (§8.2).
  • ActionResult — the stored outcome of an executed action: exit code, output digests, execution metadata (§11.3).
  • Artifact — a named file or tree in the build graph: source, generated, or symlink (§11.2).
  • BUILD file — the per-package Starlark file declaring targets.
  • buildd — the long-lived daemon holding the Skyframe graph in memory (§12, ADR-09).
  • CAS (Content-Addressed Store) — the digest-keyed object store, local and remote tiers (§18).
  • Configuration — a frozen, content-hashed bundle of platform, compilation mode, and flags (§11.5).
  • ConfiguredTarget — a Target paired with a Configuration, post-analysis (§11.5).
  • cquery — query over the configured-target graph (§22.2).
  • DepSet — a tree-shaped, deduplicated, lazily-flattened transitive-set container (§11.5).
  • Determinism — the property that identical declared inputs always produce identical outputs (I2).
  • Digest — a tagged content hash (function + size + hash bytes) (§11.1).
  • Domain separator — a fixed literal prefix mixed into a hash to prevent cross-context collision/extension attacks (§8.2).
  • Double-keying — storing (ActionKey, result_digest) pairs and rejecting on mismatch (ADR-14, I9).
  • Early cutoff — halting dirty-propagation when a recomputed value equals its prior value (I6).
  • ExecutionEngine — the trait unifying local, remote, and worker executors (§11.6, P2).
  • Hermeticity — the guarantee that an action sees only its declared inputs/tools/env (P1, I1).
  • Label — a fully-qualified target identifier, @repo//pkg:name (§11.1).
  • Loader — the component resolving BUILD files and labels into Package/Target values (§14).
  • Materialisation — making CAS content available on a working filesystem (hardlink, copy, or FUSE-lazy) (§18.2).
  • Merkle tree — the recursive, digest-linked encoding of a directory's contents (§11.4).
  • Mnemonic — a short human-readable action-type label (e.g. "CcCompile") (§11.2).
  • MODULE.bzl — the workspace-root file declaring module name, version, and dependencies (§14.2).
  • Persistent worker — a long-lived process handling multiple action requests via a length-prefixed protocol (§21).
  • Platform — a named tuple of constraint values (os, cpu, …) (§16.2).
  • Provider — a typed bag of values a rule emits for its dependents to consume (§11.5).
  • Query language — the Datalog-flavoured expression language over the graphs (§22.2, ADR-15).
  • REAPI — the Remote Execution API v2 protocol (§5.4, ADR-06).
  • Reverse dependency (rev-dep) — the inverse edge from a SkyKey to every key that depends on it, used for invalidation propagation (§17.2).
  • Rule — a named, Starlark-implemented transformation from attributes to providers and actions (§11.2, §15).
  • Salt — the algorithm-revision counter mixed into ActionKeyInput (§11.2, ADR-04).
  • Sandbox — the namespace/sandbox-exec-enforced execution boundary (§19).
  • SkyFunction — the trait computing a SkyValue for a given SkyKey (§11.6).
  • SkyKey — the tagged union identifying any cacheable unit of graph state (§11.6).
  • SkyNode — the stored state (value, deps, lifecycle state, version) for one SkyKey (§11.6).
  • Skyframe — this system's demand-driven, memoised, restart-based graph evaluator (§17, ADR-03).
  • Starlark — the deterministic BUILD-file DSL (§13, ADR-02).
  • Target — a rule instantiation with concrete attribute values, pre-analysis (§11.2).
  • Toolchain — a registered, platform-matched implementation of a toolchain type (§16.2).
  • Transition — a function rewriting Configuration across a dependency edge (§11.5, §16.2).
  • Visibility — the per-target access-control attribute checked at analysis time (§14.4).
  • Watcher — the inotify/FSEvents/kqueue-backed source-change event source (§22.2).
  • Worker pool — the keyed collection of persistent-worker processes (§21.2).
