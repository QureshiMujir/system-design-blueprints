Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  2. If ActionKeyInput included mtime, which specific invariant breaks first, and what symptom would an operator see? (§8.2, I3, FM-1)
  3. Why must a cache hit be re-digested even though the ActionKey lookup already succeeded? (§20.2, §20.6, I9)
  4. Under what conditions does the early-cutoff optimisation (I6) fail to fire even though it theoretically could, and what does that cost in rebuild time? (§17.4, §8.3, §22)
  5. Why is the exec configuration not the same as the host configuration, and what cross-compilation bug results from conflating them? (§16.2, §16.6)
  6. What specific property of DepSet (§11.5) makes rdeps queries tractable at 100,000-target scale, and what happens to query latency if that property is violated? (§15.2, §22.7)
  7. Why does the double-keying defence (ADR-14) require re-computing result_digest on every hit rather than trusting a previously-verified entry? (§20.6, T1, MM3)
  8. What is the actual difference between a legitimate cache miss (NOT_FOUND) and a poisoning attempt at the wire-protocol level, and how does the client tell them apart? (§21.6, §20.6)
  9. Why does the persistent-worker pool key on binary_digest rather than just mnemonic, and what failure mode does omitting it produce? (§21.2, I13, FM-8)
  10. Given the System Constraints table (§4) alone, derive the expected buildd memory footprint at 100,000 targets and show the arithmetic. (§4, §34 C1/C2)
  11. Why is configuration trimming deferred rather than shipped in Phase 4, and what specific metric would justify building it? (§16.4, §31, §37)
  12. What is the precise difference between a Dirty SkyNode and a NeedsRebuild one, and why does conflating them break the early-cutoff guarantee? (§8.3, I6)
  13. Why must every SkyFunction re-request all its dependencies on every invocation, even ones it already read successfully earlier in the same evaluation? (I10, §17.6)
  14. Trace what happens, step by step, when a remote executor accepts an Execute call and then the network partitions before WaitExecution completes. (§21.2, §21.8, FM-7)
  15. Why does the sandbox mount /tmp fresh per action instead of once per buildd process lifetime? (§19.2, §19.5, T2)
  16. What would have to be true of a workspace for the Make-style static-DAG alternative (§36 A1) to be the correct choice instead of a rejected one? (§36, ADR-03)
  17. Why does BLAKE3's tree-mode chunk size need to be pinned permanently rather than tunable per deployment? (§18.6, ADR-07)
  18. Derive, from the Capacity Model (§34), why remote-cache bandwidth is not expected to be the cold-build bottleneck at 100,000-target scale, and name what is. (§34 C5/C8, §30)
  19. Why does trusting a persistent worker's output without the action cache's content-revalidation path fail in exactly the same shape as trusting an unverified remote-cache hit — what single principle covers both? (§20.6, §21.2, MM3)
  20. What specific telemetry distinguishes an inotify watch-limit failure (FM-9) from a genuine early-cutoff bug, given that both present as "my change didn't rebuild"? (§22.9, §22.10, FM-9)

32. Mental Models & First Principles

  • MM1 — A build is a memoized pure function. Treat the whole system as memoizing f(declared inputs) → outputs. Predicts: two calls with equal declared inputs must return equal outputs, full stop. Bug class without it: engineers reach for "clean and rebuild" instead of trusting the cache, because they never internalised what "equal inputs" even means. Applies in §8.2, §20.
  • MM2 — The graph is discovered, not built. Skyframe's restart model means evaluation of one node can discover it needs another, mid-computation. Predicts why a "topological sort first" design breaks under dynamically-discovered dependencies. Bug class without it: assuming the whole DAG can be computed before any evaluation starts. Applies in §17.
  • MM3 — A cache hit is a claim, not a fact. Trust is derived from re-verified content, never from the cache's authority. Predicts the existence of double-keying and content-revalidation. Bug class without it: silently trusting a compromised or merely buggy cache server. Applies in §20.6, T1.
  • MM4 — Hermeticity is a boundary you draw, not a property you hope for. The sandbox is an explicit, enumerable boundary (namespaces, mounts, env). Predicts exactly which leaks (network, $HOME, /tmp, PATH) must be closed one at a time. Bug class without it: believing "no obvious side effects" is the same as hermetic. Applies in §19.
  • MM5 — Early cutoff turns "changed" into "possibly changed." Dirty does not mean different — it means "must be checked." Predicts a minimal rebuild set even when many nodes are marked dirty simultaneously. Bug class without it: over-rebuilding on every source edit because every dirty node is treated as needing full re-execution. Applies in §17.4 (I6), §8.3.
  • MM6 — The action key IS the cache contract. What fields enter ActionKeyInput defines exactly what "the same build" means. Predicts the tradeoff: adding a field trades hit rate for correctness; removing one trades correctness for hit rate. Bug class without it: ad hoc field additions/removals with no understanding of which side of the tradeoff moved. Applies in §8.2, §20.2, ADR-04.
  • MM7 — Configuration is a value, not a flag soup. Content-hashing Configuration (I12) means two constructions with equal effective fields always agree, regardless of build order. Predicts that fat binaries and cross-compilation fall out of split transitions for free. Bug class without it: a string-concatenated flag cache that misses on harmless reordering. Applies in §16.
  • MM8 — A distributed cache is a slower, less trustworthy local cache, not a different kind of thing. Apply the identical validation discipline to the remote tier, with a network RTT budget layered on top. Predicts REAPI's content-addressed, capability-negotiated design. Bug class without it: treating "the cache is remote" as license to skip the validation the local tier requires. Applies in §21, §4.

5. Required Reading

5.1 Books

  • Steve Klabnik, Carol Nichols — The Rust Programming Language, 2nd ed. Ch. on ownership, traits, and async/await. Applied in §11 (Core Schema & Types) and §12 (Phase 0 crate skeleton).
  • Robert Nystrom — Crafting Interpreters (2021). The tree-walking-interpreter and AST chapters. Applied in §13 (Starlark VM, Phase 1).
  • Martin Kleppmann — Designing Data-Intensive Applications (2017). Chapters on hashing, replication, and consistency models. Applied in §18 (Content-Addressed Store, Phase 6) and §20 (Action Cache, Phase 8).
  • Andrew S. Tanenbaum, Herbert Bos — Modern Operating Systems, 4th ed. Chapters on processes, namespaces, and scheduling. Applied in §19 (Local Sandboxed Execution, Phase 7).
  • Robert Love — Linux System Programming, 2nd ed. Chapters on namespaces, seccomp, mount semantics. Applied in §19 (Phase 7).
  • Eelco Dolstra — The Purely Functional Software Deployment Model, PhD thesis (2006), Utrecht University. Chapters 5–6, the Nix store and derivation model. Applied in §18 (Phase 6) and ADR-07.

5.2 Papers

  • Mokhov, Mitchell, Peyton Jones — "Build Systems à la Carte", ICFP 2018. Applied in §17 (Skyframe Graph, Phase 5) and ADR-03.
  • Neil Mitchell — "Shake Before Building", ICFP 2012. Monadic/dynamic dependencies. Applied in §37 (Deferred Features Register — dynamic deps).
  • Galen Hunt et al. (Microsoft) — "BuildXL: Distributed Build System for Heterogeneous Workloads" (2019). Cache-validity and speculative-execution model. Applied in §21 (Remote Execution & Persistent Workers, Phase 9).
  • Aumasson, Neves, O'Connor, Wilcox-O'Hearn — "BLAKE3: One Function, Fast Everywhere" (2020). Tree-mode parallelism, keyed-hash mode. Applied in §18 (Phase 6) and ADR-07.
  • Bazel Engineering — "Skyframe: A new evaluation framework for Bazel" (Bazel Blog, 2017). Applied in §17 (Phase 5).
  • Bazel Engineering — "Build in the Cloud" (Google Engineering Blog, 2016). Applied in §21 (Phase 9).
  • Bazel Engineering — "Reproducible builds via hermetic toolchains" (Bazel Blog, 2019). Applied in §19 (Phase 7) and §24 (Threat Model).
  • Niko Matsakis et al. — "Salsa: a generic framework for on-demand, incrementalized computation" (salsa-rs project docs/talks). Applied in §17 (Phase 5) and §22 (Incrementality Engine, Phase 10).

5.3 Reference Implementations

  • Bazel (bazelbuild/bazel) — src/main/java/.../skyframe/, analysis/, actions/, remote/. Lesson: the Skyframe restart model. Pitfall: do not copy the JVM per-node object overhead. Applied in §17.
  • Buck2 (facebook/buck2) — app/buck2_action_impl/, dice/dice/src/. Lesson: a Rust-native incremental engine (DICE) at production scale. Pitfall: do not copy its async cancellation complexity wholesale in Phase 0. Applied in §17, ADR-01.
  • Pants v2 (pantsbuild/pants) — src/rust/engine/. Lesson: a Rust executor beneath a scripting front-end. Pitfall: the FFI boundary has a real per-call cost; batch across it. Applied in §12, §19.
  • Nix (NixOS/nix) — src/libstore/. Lesson: the content-addressed store layout and GC. Pitfall: do not copy the single-writer daemon-lock contention. Applied in §18.
  • NativeLink (TraceMachina/nativelink) — the REAPI server reference used in CI. Lesson: the scheduler/worker split. Pitfall: do not assume every REAPI server implements BatchUpdateBlobs; check Capabilities first. Applied in §21.

5.4 RFCs / Specifications

  • Remote Execution API v2 (bazelbuild/remote-apis) — the normative gRPC contract for ContentAddressableStorage, ActionCache, Execution, Capabilities. Applied in §21.
  • Starlark language specification (bazelbuild/starlark) — the deterministic-dialect contract. Applied in §13.
  • Bazel Persistent Worker Protocol — WorkRequest/WorkResponse framing. Applied in §21.
  • Build Event Protocol (BEP) — the build-observability event stream. Applied in §26 (Operational Readiness).

Glossary (§38) · 44 terms · site-wide glossary

Action
a unit of executable work with fully declared inputs, tools, outputs, command, and environment (§11.2).
ActionKey
the BLAKE3 digest of an action's canonical ActionKeyInput encoding; the cache lookup key (§8.2).
ActionResult
the stored outcome of an executed action: exit code, output digests, execution metadata (§11.3).
Artifact
a named file or tree in the build graph: source, generated, or symlink (§11.2).
BUILD file
the per-package Starlark file declaring targets.
buildd
the long-lived daemon holding the Skyframe graph in memory (§12, ADR-09).
CAS (Content-Addressed Store)
the digest-keyed object store, local and remote tiers (§18).
Configuration
a frozen, content-hashed bundle of platform, compilation mode, and flags (§11.5).
ConfiguredTarget
a Target paired with a Configuration, post-analysis (§11.5).
cquery
query over the configured-target graph (§22.2).
DepSet
a tree-shaped, deduplicated, lazily-flattened transitive-set container (§11.5).
Determinism
the property that identical declared inputs always produce identical outputs (I2).
Digest
a tagged content hash (function + size + hash bytes) (§11.1).
Domain separator
a fixed literal prefix mixed into a hash to prevent cross-context collision/extension attacks (§8.2).
Double-keying
storing (ActionKey, result_digest) pairs and rejecting on mismatch (ADR-14, I9).
Early cutoff
halting dirty-propagation when a recomputed value equals its prior value (I6).
ExecutionEngine
the trait unifying local, remote, and worker executors (§11.6, P2).
Hermeticity
the guarantee that an action sees only its declared inputs/tools/env (P1, I1).
Label
a fully-qualified target identifier, @repo//pkg:name (§11.1).
Loader
the component resolving BUILD files and labels into Package/Target values (§14).
Materialisation
making CAS content available on a working filesystem (hardlink, copy, or FUSE-lazy) (§18.2).
Merkle tree
the recursive, digest-linked encoding of a directory's contents (§11.4).
Mnemonic
a short human-readable action-type label (e.g. "CcCompile") (§11.2).
MODULE.bzl
the workspace-root file declaring module name, version, and dependencies (§14.2).
Persistent worker
a long-lived process handling multiple action requests via a length-prefixed protocol (§21).
Platform
a named tuple of constraint values (os, cpu, …) (§16.2).
Provider
a typed bag of values a rule emits for its dependents to consume (§11.5).
Query language
the Datalog-flavoured expression language over the graphs (§22.2, ADR-15).
REAPI
the Remote Execution API v2 protocol (§5.4, ADR-06).
Reverse dependency (rev-dep)
the inverse edge from a SkyKey to every key that depends on it, used for invalidation propagation (§17.2).
Rule
a named, Starlark-implemented transformation from attributes to providers and actions (§11.2, §15).
Salt
the algorithm-revision counter mixed into ActionKeyInput (§11.2, ADR-04).
Sandbox
the namespace/sandbox-exec-enforced execution boundary (§19).
SkyFunction
the trait computing a SkyValue for a given SkyKey (§11.6).
SkyKey
the tagged union identifying any cacheable unit of graph state (§11.6).
SkyNode
the stored state (value, deps, lifecycle state, version) for one SkyKey (§11.6).
Skyframe
this system's demand-driven, memoised, restart-based graph evaluator (§17, ADR-03).
Starlark
the deterministic BUILD-file DSL (§13, ADR-02).
Target
a rule instantiation with concrete attribute values, pre-analysis (§11.2).
Toolchain
a registered, platform-matched implementation of a toolchain type (§16.2).
Transition
a function rewriting Configuration across a dependency edge (§11.5, §16.2).
Visibility
the per-target access-control attribute checked at analysis time (§14.4).
Watcher
the inotify/FSEvents/kqueue-backed source-change event source (§22.2).
Worker pool
the keyed collection of persistent-worker processes (§21.2).
