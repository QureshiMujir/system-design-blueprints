Decisions (§9) · 24 ADRs

ADR-01

Core implementation language

Chosen

Rust 2021

Rejected

Java, C++, Go

When the rejected choice is right

Java wins when an org already runs a JVM-only toolchain fleet and has dedicated GC-tuning staff (Bazel's own context at Google)

Why: No GC pause in the Skyframe restart hot loop; Send-checked concurrency; Buck2's C++→Rust migration is an existence proof

ADR-02

BUILD-file DSL

Chosen

Starlark

Rejected

Python, YAML, custom DSL

When the rejected choice is right

A general scripting DSL (Python) wins for a single-org tool with no cross-host reproducibility requirement

Why: Only deterministic DSL with a real spec and 3 independent implementations; Python's I/O/clock/random break determinism

ADR-03

Graph engine shape

Chosen

Skyframe-style, suspending scheduler + verifying trace

Rejected

Static topo-sort (Make-style), constructive-trace-only

When the rejected choice is right

Static topo-sort wins for a small, fully-static dependency set known before any evaluation (a 20-target embedded firmware repo)

Why: Rule deps can be discovered during evaluation (Mokhov et al. 2018); topo-sort breaks the moment deps are dynamic

ADR-04

Action key derivation

Chosen

Salted structured hash (canonical CBOR)

Rejected

Plain content hash, no salt

When the rejected choice is right

A plain unsalted hash wins when the key algorithm is provably final and a migration path is never needed (rare in practice)

Why: The salt is the only roll-forward knob against an unforeseen key-algorithm bug

ADR-05

Local sandbox mechanism

Chosen

Linux user/mount/PID/net/IPC/UTS namespaces + bind mounts; macOS sandbox-exec

Rejected

chroot, Docker-per-action, bubblewrap

When the rejected choice is right

Docker-per-action wins when the org already standardises on container images as the toolchain distribution unit

Why: No root requirement, no daemon; namespaces are the primitive bubblewrap itself wraps

ADR-06

Remote execution protocol

Chosen

REAPI v2 over gRPC

Rejected

Custom RPC protocol

When the rejected choice is right

A custom protocol wins for a closed single-vendor deployment optimising for a workload REAPI's model does not fit (e.g. GPU-scheduling-aware batching)

Why: Only protocol with multiple independent server implementations (BuildBuddy, BuildBarn, NativeLink, EngFlow)

ADR-07

Digest function

Chosen

BLAKE3-256, with a 1-byte digest-function tag

Rejected

SHA-256, untagged hash

When the rejected choice is right

SHA-256 wins where FIPS 140 certification is a hard compliance requirement and BLAKE3 has not been certified

Why: 6× faster on large files via tree mode, SIMD-accelerated; the tag allows migration without a flag day

ADR-08

Local CAS layout

Chosen

Object-per-file, two-level shard (objects/<aa>/<bb>/<digest>) + RocksDB index

Rejected

Single flat key-value store for blobs

When the rejected choice is right

A single flat KV store wins when the median object size is under 1 KiB and per-file inode overhead dominates (config-only workspaces)

Why: Matches git/Nix convention; ext4/APFS/xfs all handle the shard depth; large blobs avoid RocksDB's value-size sweet spot

ADR-09

Daemon architecture

Chosen

Persistent buildd holding the graph in memory

Rejected

Stateless CLI, full reload every invocation

When the rejected choice is right

A stateless CLI wins for a CI runner that starts fresh per job and never benefits from a warm cache anyway

Why: Cold reload costs seconds; engineers expect build to feel like grep

ADR-10

Async runtime

Chosen

tokio (multi-threaded)

Rejected

async-std, OS threads only

When the rejected choice is right

Plain OS threads win for a single-digit-concurrency embedded deployment where async's complexity buys nothing

Why: Canonical Rust async runtime; tonic and notify integrate natively

ADR-11

RPC framework

Chosen

tonic + prost

Rejected

Hand-rolled protobuf/HTTP2

When the rejected choice is right

A hand-rolled stack wins only when gRPC itself is rejected for a lighter wire protocol (not the case here, given ADR-06)

Why: Canonical Rust gRPC stack; matches the REAPI's gRPC requirement directly

ADR-12

Graph + action-cache persistence

Chosen

RocksDB, distinct column families

Rejected

SQLite, LMDB

When the rejected choice is right

SQLite wins when the deployment needs a single portable file an operator can inspect with generic tools

Why: Canonical embedded KV store at this write volume; column families isolate graph/cache/index without separate files

ADR-13

Persistent worker protocol

Chosen

Bazel WorkRequest/WorkResponse (length-prefixed protobuf over stdio)

Rejected

Custom IPC (Unix socket, shared memory)

When the rejected choice is right

Shared-memory IPC wins when worker request/response payloads are multi-GiB and the stdio copy becomes the bottleneck

Why: Documented, multiple compatible implementations already exist (rules_scala's worker)

ADR-14

Action-cache poisoning defence

Chosen

Double-keying: store (ActionKey, result_digest), reject on mismatch

Rejected

Single-keyed cache trusting the stored result

When the rejected choice is right

A single-keyed cache is acceptable only inside a fully trusted, single-tenant, network-isolated cache deployment

Why: A compromised or buggy remote cache must never silently serve wrong bytes (I9)

ADR-15

Query language

Chosen

Datalog-flavoured (deps, rdeps, kind, attr, …)

Rejected

SQL-like query language

When the rejected choice is right

SQL wins for ad hoc analytics over a build-metadata warehouse export, not for interactive graph queries

Why: Matches Bazel's documented, already-learned grammar; composes via union/intersect/except

ADR-16

File-system watcher

Chosen

notify crate (multi-backend: inotify/FSEvents/kqueue)

Rejected

Hand-rolled per-OS watchers

When the rejected choice is right

A hand-rolled watcher wins when a platform-specific feature (e.g. macOS FSEventStreamCreateFlagFileEvents per-file granularity) is load-bearing and notify does not expose it

Why: Already unifies the three backends behind one trait; avoids three maintenance surfaces

ADR-17

Tracing

Chosen

tracing + tracing-subscriber, per-action spans

Rejected

Ad hoc println!/log-file logging

When the rejected choice is right

Plain logging wins for a throwaway prototype where structured export has no downstream consumer

Why: Structured spans export to OpenTelemetry; per-action timing is required for §30

ADR-18

Benchmarking

Chosen

criterion, per-host baselines

Rejected

Manual timing loops

When the rejected choice is right

Manual timing wins for a one-off exploratory profiling session, not for CI-gated regressions

Why: Statistical-significance reporting is the correct default for regression gating (§30)

ADR-19

Fuzzing

Chosen

cargo-fuzz, OSS-Fuzz onboarding once stable

Rejected

No fuzzing

When the rejected choice is right

Skipping fuzzing is acceptable only for a prototype never exposed to untrusted BUILD files or network input

Why: The Starlark parser and the REAPI decoder are the two highest-value untrusted-input surfaces

ADR-20

License

Chosen

Apache-2.0 OR MIT (runtime); ELv2 (hosted RBE control plane only)

Rejected

GPL/AGPL

When the rejected choice is right

AGPL wins when the project's strategic goal is preventing closed-source hosted forks above all else

Why: Matches Rust ecosystem norm; keeps embedding unencumbered; ELv2 gates only the optional hosted offering

ADR-21

mmap-based digesting

Chosen

mmap + BLAKE3 tree mode for files ≥ 4 MiB

Rejected

Always read(2) into a buffer

When the rejected choice is right

Plain read(2) wins on network filesystems (NFS/FUSE) where mmap's lazy-fault semantics are unpredictable

Why: Bandwidth-bound read(2) loses to mmap+SIMD on multi-GiB files (M6)

ADR-22

Materialisation strategy

Chosen

Hardlink with copy-on-write detection (Phase 0); FUSE-lazy deferred

Rejected

Always-copy; always-FUSE

When the rejected choice is right

Always-copy wins on a filesystem without hardlink support (some overlay/network filesystems) or when writability of copies must never leak into the CAS

Why: Hardlink is near-free on same-filesystem CAS; copy-on-write detection catches the one correctness hazard

ADR-23

Windows sandbox

Chosen

Deferred to Phase-1: job objects + AppContainer, documented weaker isolation

Rejected

Skip Windows entirely

When the rejected choice is right

Skipping Windows entirely wins for an organisation with a 100% Linux/macOS engineering fleet

Why: Linux + macOS cover Phase 0–11's conformance and hermeticity gates; Windows demand is real but not blocking

ADR-24

Configuration representation

Chosen

Content-hashed Configuration struct → ConfigurationId

Rejected

Flag-string concatenation as the cache key

When the rejected choice is right

Flag-string concatenation wins for a two-flag toy system where a real hash adds only overhead

Why: Structural equality (I12) survives flag-order changes and additive fields; string concatenation does not

36. Alternative Architectures (Roads Not Taken)

A1 — Static topological build (Make-style).

sources ──► [static DAG, computed once] ──► topo-sort ──► execute in order

Regime where it wins: a small, fully-static dependency set known entirely before any evaluation starts (an embedded firmware repo with a hand-maintained Makefile). Real system: GNU Make, Ninja (§33). Rejected because: breaks the moment a rule's dependencies are themselves discovered during evaluation (generated headers, dynamic codegen) — exactly the case Mokhov et al. (§5.2) and Mitchell's monadic-deps paper (§5.2) identify as requiring a suspending scheduler (ADR-03).

A2 — Purely functional derivation model (Nix-style), no separate action cache.

inputs ──► derivation (content-hashed spec) ──► store path IS the cache key

Regime where it wins: whole-system reproducible deployment where "the same store path" across machines is the primary guarantee needed (NixOS). Real system: Nix (Dolstra, §5.1). Rejected because: derivation-per-output granularity is coarser than an action-key-per- compile-step (§8.2) — a large multi-language monorepo needs finer incremental rebuilds than one hash per whole-package derivation provides.

A3 — Centralised build-as-a-service (no local daemon, thin client only).

CLI ──(every request)──► always-on central service ──► owns graph, cache, execution

Regime where it wins: a single organisation's global monorepo at extreme scale, where a centrally-operated service amortises graph state across every engineer (Google's internal Blaze/Forge model, documented in the Bazel engineering blog posts, §5.2). Rejected because: requires an always-connected central service, materially worsening the offline/laptop developer experience this system's local buildd (P11, ADR-09) is designed to preserve, and demands an operational investment not justified below Google's scale.

A4 — Flat compiler-invocation cache, no target/action graph (ccache/sccache-style).

compiler invocation ──► hash(args+preprocessed source) ──► cached object file

Regime where it wins: a single-language, single-toolchain project with a simple, mostly linear dependency structure, where wrapping the compiler invocation directly is sufficient (ccache, sccache, §5.3-adjacent). Rejected because: no target/action graph means no query language (§22), no cross-language incremental-rebuild closure (§8.3), and no notion of "the minimal rebuild set" across a large multi-language monorepo — the exact capability this entire blueprint exists to provide.
