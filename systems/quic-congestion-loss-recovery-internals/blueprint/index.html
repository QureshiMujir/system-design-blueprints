224 — QUIC Congestion + Loss Recovery Internals from Scratch

Project Number: 224

Project Name: QUIC Congestion + Loss Recovery Internals from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

1.1 Engineering Definition

Build, from scratch, an RFC-9002-conformant QUIC congestion-control and loss-recovery subsystem: packet-number-space tracking, an ACK-range processing engine, RTT estimation, packet/time-threshold loss detection, PTO scheduling and backoff, pluggable congestion control (Reno, CUBIC, a BBR-ready interface), token-bucket pacing, ECN validation, persistent-congestion handling, delivery-rate/bandwidth estimation, a deterministic network simulator, and a replay-driven observability pipeline. The system is a transport-core subsystem, not a full protocol stack.

1.2 Phase 0 Deliverable — Crates

  1. quic-recovery-core — shared types, invariant kernel, monotonic clock/timer abstractions.
  2. quic-packet-space — packet number spaces, send-history slab, ACK-eligibility state.
  3. quic-ack-engine — ACK-range decoding, implied-loss extraction, duplicate detection.
  4. quic-rtt — RTT sampling, smoothing, ACK-delay correction.
  5. quic-loss-detector — packet/time-threshold loss, PTO timer, persistent congestion.
  6. quic-congestion — CongestionController trait, Reno, CUBIC, bandwidth estimator.
  7. quic-pacer — token-bucket pacing scheduler, burst limiter.
  8. quic-telemetry — metrics registry, tracing spans, structured log fields.
  9. quic-sim — deterministic network simulator, fault injection.
  10. quic-replay — append-only replay log, deterministic re-execution.
  11. quic-conformance — RFC 9002 vector runner.
  12. quic-cli — operator inspection and replay-diff CLI.

1.3 System Boundaries

Provides:

  • Packet tracking, ACK processing, RTT/PTO/cwnd/pacing state machines.
  • ECN validation, persistent-congestion detection.
  • Send-budget accounting, deterministic replay, simulator integration.

Delegates:

  • Packet encryption and framing — to the caller's QUIC stack.
  • Socket IO (sendmmsg/recvmmsg, GSO/GRO) — to the embedding runtime.
  • Stream scheduling policy — to the application layer.

Does NOT provide: TLS 1.3 handshake, HTTP/3 semantics, stream multiplexing/prioritization, connection migration orchestration, kernel-bypass NIC drivers, multipath scheduling (see Deferred Features Register).

1.4 Non-Goals

  • Not a full QUIC implementation.
  • Not a TLS library.
  • Not an HTTP/3 server.
  • Not a kernel module.
  • Not a userspace network stack.
  • Not a general-purpose event loop (embeds into one, ADR-07).

1.5 Deployment Model

  • Primary targets: Linux x86_64/ARM64, containerized, embedded as a library inside QUIC servers/clients, RPC runtimes, proxies, edge/CDN transport.
  • Secondary targets: BSD, macOS — development environments only, not a production commitment.
  • Transport assumptions: UDP userspace sockets, epoll/io_uring integration, a monotonic clock source, and PMTU discovery handled upstream of this subsystem.

1.6 Target Operators & Users

  • Operators: CDN operators, infra networking teams, RPC-runtime SRE.
  • Developers: QUIC implementers, distributed-systems engineers, transport researchers.
  • Researchers: congestion-control experimentation, pacing dynamics, RTT/BDP analysis, packet-loss simulation.

1.7 What Later Phases Unlock

Phase 5 (§17) unlocks pluggable CC experimentation and the BBR interface; Phase 6 (§18) unlocks adaptive pacing under RTT variance; Phase 7 (§19) unlocks ECN-adaptive congestion heuristics; Phase 8 (§20) unlocks fault-injected regression suites and replay-driven postmortems; Phase 9 (§21) unlocks production rollout, soak testing, and delivery-rate-based bandwidth estimation ahead of a future BBR/multipath phase.

1.8 Recommended Language

Rust. Rationale: deterministic ownership for packet-metadata lifetime (no double-free of send-history entries), zero-cost enum modeling for DeliveryState/CongestionState, no GC-pause amplification of PTO timing, mature tracing/fuzzing ecosystem, safe concurrent access to shared inflight counters without a GC.

Rejected alternatives:

Language Rejection Reason
C manual packet-metadata lifetime management risks use-after-free in the ACK path
C++ allocator/ownership complexity compounds under async cancellation
Go GC pause variability corrupts PTO/pacing timing determinism
Java heap overhead and scheduler mismatch versus per-packet metadata cost budget

1.9 Prerequisites

  • TCP congestion-control theory (Jacobson 1988).
  • RFC 9000 and RFC 9002, read in full before Phase 0.
  • RTT estimation theory, including retransmission ambiguity (Karn's algorithm).
  • UDP networking internals, epoll/io_uring event-loop models.
  • Lock-free/low-lock concurrent data-structure design.
  • Binary protocol design and wire-format schema evolution.
  • Performance profiling (flamegraphs, cache-miss analysis).
  • Deterministic replay/simulation system design.

1.10 Estimated Timeline

Phase 0: 10 weeks. Full implementation (Phases 0–9): 8–12 months. Stabilization (soak testing, fuzz corpus maturity, production rollout hardening): additional 3–5 months.

1.11 Non-Functional Requirements Summary

  • Correctness: RFC 9002 conformance is non-negotiable (P9); every hot-path optimization is gated on the conformance suite (§21, §26).
  • Observability: every state transition is telemetry-visible by default (P10); an incident must be diagnosable from metrics/traces/replay alone, never from adding ad hoc logging under fire.
  • Maintainability: pluggable congestion control (P11) and additive-only schema evolution (§25) keep the system extensible without core-crate churn.
  • Performance: the §4 budgets are floors, not aspirations — every phase gate in §28 reuses them unchanged.
  • Security: fail-closed on invariant violation (P8) is the default security posture against both bugs and adversarial peers (§22).

2. Why Build This

2.1 Educational Value

Teaches: modern transport design, practical congestion algorithms (Reno/CUBIC/BBR-shaped interfaces), timer-wheel design, ACK-range compression, tail-loss handling, bandwidth estimation, packet-metadata lifecycle management, transport observability. Forces reasoning about timing uncertainty, packet reordering, delayed ACKs, ACK compression, burst amplification, persistent congestion, timer drift, and replayability — problems that do not appear in request/response systems.

2.2 Historical Importance

Loss recovery and congestion control are QUIC's operational heart: userspace transport innovation (RFC 9000/9002 vs. kernel TCP) accelerated congestion-control experimentation (CUBIC → BBR → BBRv2) at a pace kernel TCP stacks could not match. Building this from scratch exposes why TCP evolved slowly (kernel upgrade cycles), why pacing matters (burst amplification at the bottleneck queue), why RTT estimation is fragile (ACK delay, retransmission ambiguity — Karn's algorithm), and why ACK behavior dominates achievable throughput.

2.3 Engineering Muscles Developed

Packet-level reasoning, distributed timing analysis, lock minimization on hot ACK/send paths, observability-first engineering, protocol-invariant reasoning, replay-based debugging, memory budgeting under a 250k-connection ceiling (§4), transport-correctness validation against RFC vectors.

2.5 Calibration Value

Demonstrates: transport engineering, systems debugging under nondeterminism, performance analysis, event-loop design, low-level networking, observability architecture, deterministic replay-system design. Permanently improves intuition for queueing, bandwidth-delay product, packet-loss dynamics, transport fairness, timer instability, pacing collapse, and backpressure.

What Mastery Looks Like

  • Can derive PTO and persistent-congestion behavior from RFC 9002 formulas by hand and defend every constant — gained in §16 (Phase 4).
  • Can explain why a given ACK trace implies a specific set of lost packets without running code — gained in §14 (Phase 2).
  • Can diagnose a live cwnd collapse from cwnd_bytes/congestion_events_total telemetry alone — gained in §17 (Phase 5).
  • Can distinguish scheduler jitter from genuine pacing-token starvation using pacing_debt_ns histograms — gained in §18 (Phase 6).
  • Can reason about ECN false-congestion signals from a middlebox without disabling ECN globally — gained in §19 (Phase 7).
  • Can reproduce a production incident deterministically from a replay log and a fixed seed — gained in §20 (Phase 8).
  • Can defend every ADR-## choice against a named rejected alternative and the regime where it would win — gained across §9 and §34.

2.6 What This Project Deliberately Is Not

  • Not a TLS library, not an HTTP/3 server, not a full QUIC stack (§1.3) — those are the caller's responsibility.
  • Not a kernel module or NIC driver — hardware/kernel pacing offload is explicitly deferred (§35, PhaseDeferred("§18")).
  • Not a multi-algorithm research playground in v1 — BBR is deferred (§35, PhaseDeferred("§17")) until delivery-rate determinism is solved.
  • Not a general-purpose event loop — it embeds into one (Tokio, ADR-07), it does not provide one.

3.2 Subsystem Descriptions

Application Layer — consumes send capacity, receives delivery notifications; never mutates congestion state directly.

Transport Integration API — the sole crossing point between protocol code and recovery internals; exposes packet registration, ACK notification, pacing availability, retransmission eligibility (I2, P3).

Packet Assembly Layer — packet-number assignment, encryption-space separation, immutable per-packet metadata snapshots (SentPacket, §11) consumed later by loss detection.

Congestion + Recovery Core — the decision engine: RTT update, PTO scheduling, cwnd transitions, ACK processing, loss declaration, ECN state, pacing decisions. Single-threaded per connection (ADR-08) — this is the concurrency boundary that makes replay deterministic.

Send Budget Engine — authoritative source for "may I send now": inflight bytes vs. cwnd, pacing-token balance (P2, P3).

Runtime Event Scheduler — timer wheel (ADR-23) driving PTO/pacing wakeups; jitter is measured, not assumed away.

UDP Socket Layer — batched syscalls (ADR-06), ECN codepoint marking, GSO segmentation; the external interface to the kernel network stack.

Telemetry/Replay path — every state transition emits a structured, replay-log-serializable event (P6); this is the persistence boundary.

Simulation path — quic-sim drives the same Transport Integration API as production, injecting deterministic loss/delay/reorder/duplication/ECN faults (Phase 8, §20).

3.3 Explicit Boundaries

  • Trust boundary: the Transport Integration API — everything below it trusts only validated, RFC-conformant data; everything above it is caller-controlled, untrusted input.
  • Concurrency boundary: the Congestion + Recovery Core is single-writer per connection (ADR-08); no lock is held across the ACK/loss/pacing decision path.
  • Persistence boundary: the Telemetry Path — nothing before it is durable, everything after it (the replay log, §20) is.
  • Protocol boundary: the Packet Assembly Layer — RFC 9000/9002 wire semantics live below it; algorithmic decisions (which packets to send, when) live above it.
  • External interface: the UDP Socket Layer — the only point where this subsystem touches the kernel network stack directly.

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every recovery decision is a pure function of (state, event, clock reading) and is replay-log serializable · Tradeoff: forbids ad hoc randomness or wall-clock reads in hot paths · Operational: replay checksum must match across re-execution · Violated: postmortems become guesswork, simulations stop being trustworthy.
  • P2 — Backpressure Everywhere. Rule: transmission eligibility is always bounded by min(cwnd headroom, pacing tokens) · Tradeoff: adds a check on every send-path call · Operational: poll_tx_budget() must be consulted before every packet build · Violated: burst collapse, queue explosion, unfairness against co-existing flows.
  • P3 — Single Source of Truth for Inflight State. Rule: inflight-byte accounting lives only in the Send Budget Engine, never duplicated · Tradeoff: every subsystem needing inflight data calls through one API · Operational: inflight_delta_total telemetry must sum to zero over a closed connection · Violated: negative inflight counts, cwnd corruption, retransmission instability.
  • P4 — Monotonic Timing Only. Rule: wall-clock reads are forbidden inside recovery/pacing/PTO logic · Tradeoff: requires a dedicated clock abstraction (ADR-20) threaded through every timer call · Operational: NTP step corrections must never perturb PTO · Violated: PTO instability, replay divergence across machines.
  • P5 — Explicit Ownership. Rule: SentPacket metadata has exactly one owner (the send-history slab) for its entire lifetime · Tradeoff: ACK processing must mutate through a handle, not a copy · Operational: slab entry lifecycle is auditable end to end · Violated: double-free risk, stale ACK references, memory leaks under long-lived connections.
  • P6 — Replayability First. Rule: every state transition emits a replay-safe, versioned event before it is considered committed · Tradeoff: adds serialization cost to every hot-path transition · Operational: replay-log append precedes externally observable effects · Violated: impossible debugging, nondeterministic simulation runs.
  • P7 — Bounded Memory Growth. Rule: packet-tracking structures have a hard per-connection ceiling (§4) regardless of peer behavior · Tradeoff: pathological peers get fail-fast, not best-effort accommodation · Operational: slab exhaustion is a metered, alertable event · Violated: attacker-driven memory exhaustion, unbounded metadata amplification.
  • P8 — Fail Closed on Invariant Violations. Rule: any invariant (§7) breach terminates the connection rather than continuing in an unknown state · Tradeoff: sacrifices availability of one connection for correctness of the fleet · Operational: termination reason is always attributable to an invariant ID · Violated: silent congestion-state divergence, corrupted accounting propagating undetected.
  • P9 — Protocol Correctness Before Optimization. Rule: RFC 9002 conformance gates every optimization; a faster but non-conformant path is rejected · Tradeoff: some throughput left on the table until conformance is proven · Operational: conformance suite (quic-conformance) runs before any performance PR merges · Violated: interop breakage with real QUIC peers.
  • P10 — Structured Telemetry by Default. Rule: every state transition emits a structured event with a fixed schema, not free-text logs · Tradeoff: schema evolution requires versioning discipline (§25) · Operational: dashboards and alerts key off stable metric names (§24) · Violated: unqueryable incidents, dashboard rot on refactor.
  • P11 — Pluggable Congestion Control Behind One Trait. Rule: Reno, CUBIC, and future BBR all implement CongestionController (§11) with no algorithm-specific leakage into the core · Tradeoff: the trait surface must anticipate delivery-rate-based algorithms even before BBR ships · Operational: swapping algorithms is a config change, not a core-crate change · Violated: algorithm-specific hacks metastasize into quic-recovery-core.
  • P12 — Pacing Is Not Optional. Rule: every congestion controller reports a pacing rate; the pacer is never bypassed · Tradeoff: adds one indirection to every send decision · Operational: idle-restart repacing must re-derive rate from current cwnd/RTT, not resume stale tokens · Violated: microburst-induced queue drops at the bottleneck.
  • P13 — ECN Signals Are Advisory, Never Authoritative. Rule: a CE mark contributes to a congestion decision but never bypasses cwnd/pacing accounting directly · Tradeoff: requires a validation state machine (§19) rather than trusting the network · Operational: ECN can be disabled per-path without touching core recovery logic · Violated: middlebox ECN-mangling causes false or missed congestion response.
  • P14 — Bandwidth Estimates Are Observational, Never Load-Bearing (Until §21). Rule: the delivery-rate estimator (§17) informs pacing_rate() but never overrides cwnd-derived send eligibility while Reno/CUBIC are active · Tradeoff: leaves some achievable throughput on the table versus a full BBR-style rate-based sender · Operational: bandwidth_estimate_bps is dashboarded but not alerted on until §21's confidence groundwork lands · Violated: an unvalidated bandwidth estimate silently becomes the de facto congestion controller through the back door.

8. Domain Model — QUIC Packet Number Spaces, RTT, and Loss State Machines

8.1 Packet Number Spaces

Space Purpose
Initial handshake bootstrap, discarded once Handshake keys install
Handshake TLS progression, discarded once Application keys confirm
Application steady-state traffic, lives for the connection lifetime

Each space independently tracks: largest_acked, its own send-history slab region, its own loss-detection timer, and its own ACK-range state (I1, I8).

8.2 RTT Model

Core variables: latest_rtt, smoothed_rtt, rttvar, min_rtt, max_ack_delay.

Update sequence (RFC 9002 §5): (1) reject sample if ambiguous retransmission (I3) — (2) compute raw sample from send-time to ACK-receive-time — (3) adjusted_rtt = max(latest_rtt - min(ack_delay, max_ack_delay), min_rtt) — (4) update min_rtt = min(min_rtt, latest_rtt) — (5) rttvar = 3/4·rttvar + 1/4·|smoothed_rtt - adjusted_rtt| — (6) smoothed_rtt = 7/8·smoothed_rtt + 1/8·adjusted_rtt — (7) recompute PTO = smoothed_rtt + max(4·rttvar, kGranularity) + max_ack_delay, kGranularity = 1 ms.

8.3 Loss Detection State Machine

SENT ---ack-eligible frame acked---> ACKED
SENT ---packet or time threshold---> LOST
SENT ---no ACK before PTO fires----> PTO_PENDING
PTO_PENDING ---probe response acked--> ACKED
PTO_PENDING ---still unacked, rearm--> PTO_PENDING

Loss declared on: packet threshold (kPacketThreshold = 3 higher-numbered packets acked), time threshold (kTimeThreshold = 9/8 × max(latest_rtt, smoothed_rtt)), or persistent-congestion detection (I9).

8.4 Congestion States

SLOW_START --loss or ECN CE--> RECOVERY
SLOW_START --cwnd >= ssthresh--> CONGESTION_AVOIDANCE
CONGESTION_AVOIDANCE --loss/CE--> RECOVERY
RECOVERY --one RTT elapsed, no new loss--> CONGESTION_AVOIDANCE
RECOVERY --persistent congestion (I9)--> PERSISTENT_CONGESTION
PERSISTENT_CONGESTION --successful send at min cwnd--> SLOW_START

8.5 ACK Processing Worked Example

Sent packet numbers: 100 101 102 103 104 105. Received ACK ranges: [105-103], [101-100]. Packet 102 is not covered by any range and lies below largest_acked (105) by more than kPacketThreshold's implied gap once packet 105 is acked three-higher — it is an implied loss. Recovery consequences: inflight reduction by bytes_sent(102), a congestion event dispatched to the active CongestionController, and pacing-rate recalculation from the new cwnd (§17, §18).

8.6 Persistent Congestion Duration

RFC 9002's persistent-congestion duration formula: pc_duration = (smoothed_rtt + max(4·rttvar, kGranularity) + max_ack_delay) × kPersistentCongestionThreshold, with kPersistentCongestionThreshold a small integer constant. A run of consecutive PTO-triggered probes spanning at least pc_duration with zero intervening ACKs on that packet-number space triggers I9. Boundary conditions the fixtures in §16.5 and §19.5 must cover:

  • Exactly one probe short of pc_duration — must not trigger.
  • Exactly at pc_duration — must trigger.
  • The window spanning a packet-number-space discard (Initial→Handshake) — must not falsely combine probes from two spaces (I15).

struct SentPacket
  packet_number: u64
  packet_space: PacketSpaceId
  sent_time: Instant
  ack_eliciting: bool
  bytes_sent: u32
  inflight: bool
  retransmittable_frames: FrameSet
  delivery_state: DeliveryState
  ecn_marking: EcnCodepoint

Ownership: owned exclusively by the send-history slab (P5); mutation: immutable after insertion except delivery_state; concurrency: single-writer per connection actor (ADR-08); persistence: replay-log serializable (postcard, ADR-05); serialization: derive(Serialize), versioned via non_exhaustive; compatibility: new fields must be additive, see §25.

enum DeliveryState = Sent | Acked | Lost | PtoPending

Ownership: field of SentPacket; mutation: single-writer, exhaustive transition table (I14); concurrency: no shared mutability; persistence: logged on every transition; serialization: fixed discriminant order (compatibility-locked); compatibility: new variants require a schema-major bump.

enum CongestionState = SlowStart | CongestionAvoidance | Recovery | PersistentCongestion

Ownership: owned by the active CongestionController instance; mutation: driven only by on_packet_acked/on_packet_lost; concurrency: single-writer; persistence: replay-logged on transition; serialization: stable discriminant order; compatibility: additive-only.

trait RttEstimator
  fn update(sample: Duration, ack_delay: Duration);
  fn pto_base() -> Duration;
  fn smoothed_rtt() -> Duration;
  fn rttvar() -> Duration;
  fn min_rtt() -> Duration;

Ownership: one instance per connection, owned by quic-rtt; mutation: update() is the sole mutator; concurrency: single-writer; persistence: samples logged, estimator state reconstructable by replay; serialization: not wire-serialized, replay-derivable instead; compatibility: trait is additive-extend only (default-method rule).

trait CongestionController
  fn on_packet_sent(bytes: u32, pn: u64);
  fn on_packet_acked(bytes: u32, pn: u64, rtt: Duration);
  fn on_packet_lost(bytes: u32, pn: u64);
  fn on_ecn_ce(pn: u64);
  fn cwnd() -> u64;
  fn pacing_rate() -> u64;
  fn state() -> CongestionState;

Ownership: boxed trait object selected at connection start (P11); mutation: through the four on_* hooks only; concurrency: single-writer per connection; persistence: cwnd/state changes replay-logged; serialization: none (behavioral trait); compatibility: new hooks default to no-op for existing implementers.

struct AckRange
  start: u64
  end: u64

Invariant: start <= end, ranges non-overlapping and strictly descending across a frame (I4); ownership: owned by the decoded ACK frame, dropped after processing; mutation: immutable; concurrency: none (transient); persistence: not persisted, only its effects are; serialization: wire-decoded from RFC 9000 ACK frame varints; compatibility: wire format is RFC-locked, not evolvable by this project.

struct PacketSpaceId(u8)   // Initial = 0, Handshake = 1, Application = 2

Ownership: value type, copied freely; mutation: immutable; concurrency: safe to share; persistence: replay-logged alongside every packet event; serialization: single byte; compatibility: closed set, RFC-defined.

struct TokenBucket
  capacity_bytes: u32
  tokens_bytes: u32
  refill_rate_bps: u64
  last_refill: Instant

Ownership: one per connection, owned by quic-pacer; mutation: refilled/drained on every send decision (P12); concurrency: single-writer; persistence: debt (capacity_bytes - tokens_bytes) replay-logged for pacing_debt_ns derivation; serialization: not wire-relevant; compatibility: internal, free to evolve.

struct ReplayEvent

  connection_epoch: u32
  ts_monotonic_ns: u64
  kind: EventKind
  payload: EventPayload

Ownership: owned by quic-replay append pipeline; mutation: append-only, never mutated post-write (I12); concurrency: single-writer queue per connection, fan-in on flush; persistence: the durable unit of §20; serialization: postcard-framed (ADR-05); compatibility: EventKind/EventPayload are additive-only enums, schema versioned major.minor.schema (§25).

  • Allocator locality: slab entries cache-line aligned to the §4 ≤ 64 B/entry budget.

  • Replay serialization amplification bounded by §4's ≤ 1.35× target.

  • Clock rollback: must be detected and rejected, never silently accepted (P4).

  • CI running on a host without invariant TSC (ARM64 secondary target, §4 CPU assumptions).
  • Workspace built with a mismatched rust-toolchain.toml pin, breaking ADR-19 reproducibility.

  • Containment: bounded to the one connection's replay window.
  • Forensics: starts from the last matching checksum, not the whole log.

  • Packet-metadata leaks: manifestation — memory growth over long-lived connections; root cause — slab entries not reclaimed after ACK+drain window; debugging — packet_history_entries trend over connection lifetime; recovery — bounded reclamation sweep tied to largest_acked watermark.

13.7 Performance Concerns

  • Slab traversal locality: sequential scan order matters more than hashmap's O(1) lookup at this scale (ADR-27).
  • ACK-range scan cost bounded by §4's 32-packet reordering assumption.
  • Branch prediction during ACK-range iteration: sorted-descending order, per I4, is branch-predictor-friendly.
  • Reclamation-sweep cost must stay off the hot insert path — amortize it over the connection's ACK cadence.

13.8 Edge Cases

  • ACK of an unknown or already-discarded packet number.
  • Reordered ACK ranges arriving before in-order ones.
  • Duplicated ACK frames.
  • Handshake-space discard while PTO-pending packets remain.
  • Packet-number-space confusion: an Application ACK referencing an Initial-space packet number — must be rejected, not silently accepted.
  • Slab entry reused before its prior occupant's replay event has flushed.

13.9 Failure Analysis

  • Symptom: corrupted send history feeds incorrect loss declarations into §16.
  • Blast radius: spurious loss propagates into §17's cwnd accounting, causing collapse; replay divergence follows (P6 violated).
  • Detection: the I1/I13/I14 assertion trio.
  • Containment: connection-scoped termination (P8).
  • Operator visibility: pn_monotonicity_violation_total and delivery_state_conflict_total counters.

13.10 Operational Notes

  • Metrics: packet_history_entries, ack_duplicate_total, inflight_bytes, slab_occupancy_ratio.
  • Tracing spans: packet_space.register, packet_space.discard.
  • Structured-log fields: packet_space_id, packet_number.
  • Migration: SentPacket schema changes are additive-only (§11); a schema-major bump is required to remove a field.

14. Phase 2 — ACK Range Processing Engine

14.1 Objectives

Implement the ACK-frame decode and implied-loss extraction pipeline that turns wire-level ACK ranges into DeliveryState transitions, per the worked example in §8.5.

14.2 Detailed Implementation Steps

Implement quic-ack-engine (lib.rs, ack.rs, range.rs). Decode AckRange lists per RFC 9000 §13 wire format, validating strict-descending non-overlapping order (I4) before any state mutation. Extract implied losses: any unacked packet below largest_acked covered by neither range and separated by ≥ kPacketThreshold (RFC 9002, §16) higher-numbered acked packets is provisionally marked lost, handed to §16's threshold logic for final declaration. Anchor: quic-go's ACK-processing structure (P3 — single source of truth for the resulting inflight delta) informs the range-scan design; msquic's vtable pattern is deliberately not used here since range decode has no pluggable variants.

14.3 Deliverable

An ACK-processing engine that, given a wire-format ACK frame and the current send history, emits a deterministic set of {newly-acked, provisionally-lost, duplicate} packet numbers plus the inflight-byte delta.

14.4 Acceptance Criteria

Zero false-positive duplicate-ACK detections across 1M synthetic frames. Implied-loss extraction matches RFC 9002 vectors in fixtures/ack-engine/overlapping_ack_ranges.json bit-for-bit. ACK processing latency stays under the §4 budgets (p50 < 5 µs, p99 < 40 µs) on a warm 65,536-entry slab.

14.5 Conformance Fixtures

  • fixtures/ack-engine/malformed_ack_ranges.bin — non-descending ranges, must reject per I4.
  • fixtures/ack-engine/ack_flood_replay.bin — high-rate duplicate-ACK replay, tests idempotency.
  • fixtures/ack-engine/implied_loss_vector.json — RFC 9002-style implied-loss conformance vector.
  • fixtures/ack-engine/reordered_ranges.bin — reordered-arrival regression case.

14.6 Pitfalls

  • ACK compression: manifestation — a burst of coalesced ACKs looks like a sudden large cwnd-worthy event; root cause — network-path buffering delays ACK delivery, then releases many at once; debugging — inter-ACK-arrival histogram; recovery — feed ACK-compression detection into §17's cwnd-growth gating, not the ACK engine itself.
  • Off-by-one range boundaries: manifestation — one extra or missing packet marked acked; root cause — inclusive/exclusive range-boundary confusion; debugging — property test against exhaustive small ranges; recovery — single canonical inclusive-inclusive convention, enforced at decode.
  • ACK-of-never-sent packet number: manifestation — engine dereferences a nonexistent slab slot; root cause — missing existence check before state mutation; debugging — fuzz target ack_parser (fuzz/fuzz_targets/ack_parser.rs); recovery — reject frame, connection error (I4).

14.7 Performance Concerns

  • Range-scan cost dominates p99 (§4).
  • Branch-predictor-friendly descending iteration (I4).
  • Avoiding allocation on the hot decode path: a fixed-capacity stack buffer up to the §4 32-packet reordering assumption, spilling to heap only beyond it.
  • Duplicate-detection lookup cost must stay sub-microsecond — index by packet number range, not linear scan of prior frames.

14.8 Edge Cases

  • Empty ACK-range list (ACK-only-of-nothing, malformed).
  • Single-packet range at u64::MAX.
  • ACK referencing packets from a just-discarded space (§13.8).
  • Adversarial range list crafted to maximize scan cost, mitigated by the §4 32-packet-reordering-derived scan bound.
  • ACK-delay field saturation feeding into §15.
  • A frame containing only duplicate ranges of an already-fully-acked prefix.

14.9 Failure Analysis

  • Symptom: a broken ACK engine mis-declares loss, causing spurious retransmission storms downstream in §16.
  • Alternate symptom: under-declaration causes silent throughput collapse as the peer waits on packets already lost.
  • Detection: malformed_ack_total spike or an I4 assertion trip.
  • Blast radius: single connection, contained by P8's fail-closed termination.
  • Forensics: replay the decoded range sequence against the send-history snapshot at the time of decode.

14.10 Operational Notes

  • Metrics: ack_ranges_processed_total, ack_duplicate_total (shared counter with §13), implied_loss_extracted_total, malformed_ack_total.
  • Tracing spans: ack_engine.decode, ack_engine.extract_loss.
  • Structured-log fields: largest_acked, range_count.
  • Rollback: ACK wire-format handling is RFC-locked (§25), never versioned independently of the QUIC version it serves.

15.5 Conformance Fixtures

  • fixtures/rtt/delayed_ack_trace.bin — delayed-ACK replay validating ACK-delay correction.

  • ACK-delay abuse: manifestation — perceived RTT inflates, PTO grows unnecessarily conservative; root cause — malicious or buggy peer reports oversized ack_delay; debugging — ack_delay_correction_negative_total and delay-distribution dashboard; recovery — clamp to max_ack_delay transport parameter (I7).
  • Ambiguous RTT samples: manifestation — RTT estimate oscillates wildly; root cause — retransmitted packets' ACKs credited to the wrong send time (Karn's algorithm violation); debugging — cross-check against retransmit_ambiguity.bin (§13); recovery — reject sample outright (I3), never approximate.
  • Fixed-point rounding drift: manifestation — two replay runs diverge by 1 unit after many updates; root cause — integer-division truncation direction not pinned; debugging — differential replay test; recovery — single documented rounding rule, applied uniformly.

15.7 Performance Concerns

  • Floating-point avoidance on the hot update path (P1, determinism).
  • Timestamp precision: nanosecond-resolution monotonic clock from §12 avoids quantization bias in rttvar.
  • Histogram cardinality: bucket by connection-shard, not per-connection, to bound quic-telemetry memory.
  • Smoothing-formula branch count kept minimal — every branch is a potential replay-divergence source under P1.

15.8 Edge Cases

  • Zero-duration RTT sample (same-tick send/ack, degenerate but not invalid).
  • Negative corrected RTT before clamping (I7).
  • ACK-delay field at its transport-parameter maximum.
  • First-ever sample on a connection: no prior smoothed_rtt to smooth against, must bootstrap from kInitialRtt = 333 ms.
  • Clock-source switch mid-connection, forbidden by P4, must be detected as an invariant violation, not silently tolerated.
  • A sample arriving after the estimator has been reset by a packet-number-space discard.

15.9 Failure Analysis

  • Symptom: incorrect RTT estimation destabilizes PTO (§16, spurious probe storms).
  • Downstream effect: pacing rate mis-set (§18, under/over-pacing) and cwnd growth mistimed (§17, slow-start exit mistimed).
  • Detection: rtt_sample_rejected_total spike or rttvar variance-spike alert (§24).
  • Containment: bad estimator state is connection-scoped, never shared across connections.

15.10 Operational Notes

  • Metrics: rtt_smoothed_ms, rttvar_ms, rtt_min_ms, ack_delay_distribution, rtt_sample_rejected_total.
  • Tracing spans: rtt.sample, rtt.update.
  • Structured-log fields: latest_rtt_us, ack_delay_us.
  • Compatibility: RttEstimator is additive-extend only (§11); a new smoothing algorithm is a new trait implementation, not a breaking change to the trait.

16. Phase 4 — Loss Detection & PTO Engine

16.1 Objectives

Implement RFC 9002's normative loss-recovery core: packet-threshold and time-threshold loss detection, PTO scheduling and exponential backoff, persistent-congestion detection surfaced for §19 to act on.

16.2 Detailed Implementation Steps

Implement quic-loss-detector (lib.rs, pto.rs, threshold.rs). Implement packet-threshold loss (kPacketThreshold = 3, RFC 9002) and time-threshold loss (kTimeThreshold = 9/8 × max(latest_rtt, smoothed_rtt), RFC 9002) against the send history from §13 and the implied-loss candidates from §14. Implement the PTO timer: pto_base() from §15 plus exponential backoff (2^n × pto_base, capped) on repeated PTO expiry, coordinated through the timer wheel from §12 (I5, I8 — exactly one armed timer per packet-number space). Implement persistent-congestion detection (I9): a run of PTO-triggered probes spanning ≥ the persistent-congestion duration with no intervening ACK. Anchor: RFC 9002 (Iyengar & Swett, 2021) is the normative source for every constant in this phase; deviation from it is a defect, not a design choice.

16.3 Deliverable

A recovery engine that, given the current send history and RTT state, declares loss correctly against RFC 9002 vectors and schedules/backs off PTO deterministically.

16.4 Acceptance Criteria

100% pass rate on fixtures/loss/tail_loss_probe.bin and fixtures/loss/persistent_congestion.bin RFC vectors. PTO scheduling latency < 50 µs end to end (§4). Persistent congestion detected within one connection's worth of consecutive PTO failures matching the RFC 9002 persistent-congestion duration formula, zero false positives across 10k quic-sim runs.

16.5 Conformance Fixtures

  • fixtures/loss/tail_loss_probe.bin — end-of-burst loss requiring a PTO probe, not a threshold declaration.
  • fixtures/loss/persistent_congestion.bin — sustained-collapse vector triggering I9.
  • fixtures/loss/reorder_threshold.bin — reordering below kPacketThreshold, must not declare loss.
  • fixtures/loss/pto_backoff_overflow.json — exponential-backoff cap regression case.

16.6 Pitfalls

  • Timer coalescing: manifestation — PTO fires later than scheduled under scheduler load; root cause — timer-wheel tick coalescing batches nearby deadlines; debugging — compare scheduled vs. actual fire time via pto_fire_lag_ns; recovery — tighten wheel granularity for the loss-timer bucket specifically.
  • Spurious loss under aggressive thresholds: manifestation — unnecessary retransmissions inflate traffic; root cause — kPacketThreshold set too low for the §4 32-packet reordering assumption; debugging — spurious_loss_total correlated with reorder-heavy quic-sim traces; recovery — hold kPacketThreshold at the RFC-specified 3, do not tune down.
  • PTO storms during idle periods: manifestation — repeated PTO firing with nothing inflight; root cause — timer not disarmed when inflight drops to zero; debugging — pto_count spike with zero concurrent inflight_bytes; recovery — disarm loss timer when no ack-eliciting packet is outstanding (I8).

16.7 Performance Concerns

  • Loss-scan complexity bounded by slab occupancy, §4's 65,536 ceiling.
  • Timer churn: re-arming on every ACK is wasteful — only re-arm when the earliest-unacked deadline actually changes (I5).
  • Retransmission-queue contention under bursty loss: single-writer per connection (ADR-08) avoids cross-thread contention.
  • Backoff-exponent arithmetic must saturate, not overflow, at the cap (see fixtures/loss/pto_backoff_overflow.json).

16.8 Edge Cases

  • PTO firing during an idle period with nothing inflight (§16.6).
  • ACK arriving after loss has already been declared — must not double-count the reduction (ties to I2).
  • Reordered PTO-probe ACK arriving after a second probe already fired.
  • Persistent congestion spanning a packet-number-space discard boundary.
  • Simultaneous packet-threshold and time-threshold triggers on the same packet — declare once, not twice.
  • A PTO probe itself being lost, requiring correct exponential re-escalation rather than a reset.

16.9 Failure Analysis

  • Symptom: broken PTO logic causes throughput collapse when probes never escalate.
  • Alternate symptom: retransmission storms from over-eager thresholds, or persistent-congestion loops when I9 never clears.
  • Detection: declared_losses_total and spurious_loss_total divergence from expected ratios.
  • Forensics: starts from the replay log around the first anomalous pto_count increment.

16.10 Operational Notes

  • Metrics: pto_count, declared_losses_total, spurious_loss_total, persistent_congestion_total, pto_fire_lag_ns.
  • Tracing spans: loss.detect, loss.pto_fire, loss.persistent_congestion.
  • Structured-log fields: loss_reason (packet_threshold|time_threshold|pto), pto_backoff_exponent.
  • Migration: PTO backoff cap is a tunable transport parameter, changeable without a schema bump.

17. Phase 5 — Congestion Control Framework

17.1 Objectives

Introduce the pluggable CongestionController trait (§11, P11) and ship two conformant implementations — Reno and CUBIC — plus a delivery-rate/bandwidth-estimation module that anticipates a future BBR implementation without committing to it yet.

17.2 Detailed Implementation Steps

Implement quic-congestion (lib.rs, cubic.rs, reno.rs, bandwidth.rs). Implement the CongestionController trait's four hooks against the CongestionState machine from §8.4 (SlowStart → CongestionAvoidance → Recovery → PersistentCongestion). Implement Reno per Jacobson 1988's AIMD discipline: additive increase in CongestionAvoidance, multiplicative decrease on loss, slow-start exit at ssthresh informed by Chu et al. 2013's initial-window analysis. Implement CUBIC per RFC 8312 / Ha, Rhee, Xu 2008: the cubic window-growth function with fixed-point arithmetic (P1 — determinism over floating-point convenience), fast-convergence on repeated congestion events, and CUBIC's own slow-start-exit heuristic (Hybrid Slow Start is out of scope for v1, deferred). Implement the bandwidth estimator (delivery-rate sampling per Cardwell et al. 2016) as a passive observer feeding pacing_rate() even under Reno/CUBIC, laying groundwork for §21's BBR-readiness work (PhaseDeferred("§17") covers BBRv2 itself). Anchor: I6 (cwnd floor) and I9 (persistent-congestion reset) are enforced in this crate.

17.3 Deliverable

An operational congestion-control abstraction: either Reno or CUBIC selectable at connection start, both driving cwnd()/pacing_rate()/state() correctly under quic-sim fault injection.

17.4 Acceptance Criteria

Fairness validated: two CUBIC flows sharing a bottleneck in fixtures/congestion/fairness_competition.sim converge to within 10% of equal share over 60 simulated seconds. cwnd never observed negative across 1M synthetic ACK/loss events (I6). Recovery-state transitions are deterministic and replay-identical (fixtures/congestion/cubic_growth_trace.bin checksum match).

17.5 Conformance Fixtures

  • fixtures/congestion/cubic_growth_trace.bin — RFC 8312 growth-function conformance vector.
  • fixtures/congestion/reno_loss_trace.bin — AIMD multiplicative-decrease regression case.
  • fixtures/congestion/fairness_competition.sim — two-flow bottleneck-sharing simulation.
  • fixtures/congestion/idle_restart.bin — cwnd behavior after a send-idle gap exceeding one RTT.

17.6 Pitfalls

  • ACK compression inflating cwnd: manifestation — cwnd grows faster than the path can sustain; root cause — coalesced ACK bursts (§14.6) look like many independent growth events; debugging — correlate cwnd_bytes growth rate against inter-ACK-arrival histogram; recovery — cap per-ACK-batch cwnd growth to one RTT-worth, not per-ACK.
  • Recovery-state oscillation: manifestation — repeated Recovery↔CongestionAvoidance flapping destabilizes throughput; root cause — new loss detected within the same RTT as entering Recovery is treated as a fresh event; debugging — trace congestion_events_total timestamps against RTT boundaries; recovery — RFC 9002-style single-Recovery-per-RTT gating.
  • cwnd underflow near minimum: manifestation — send budget hits zero unexpectedly; root cause — multiplicative decrease applied without the I6 floor check; debugging — cwnd_floor_hits_total; recovery — clamp before, not after, applying the decrease.
  • Idle-restart overshoot: manifestation — a connection resuming after idle sends a burst exceeding path capacity; root cause — cwnd retained at pre-idle value despite stale RTT/pacing state; debugging — fixtures/congestion/idle_restart.bin replay; recovery — reset cwnd toward slow-start-equivalent on idle restart beyond one RTT.

17.7 Performance Concerns

  • Integer-arithmetic precision in CUBIC's cubic-root approximation must be deterministic across platforms (P1).
  • Pacing-rate recomputation cost on every cwnd change: batch recomputation per ACK batch, not per packet.
  • Trait dynamic-dispatch overhead on the hot ACK path, bounded by the §4 p99 ACK-processing budget.
  • Bandwidth-estimator sampling must not allocate on the ACK path — fixed-size ring buffer for delivery-rate samples.

17.8 Edge Cases

  • cwnd underflow at minimum_cwnd (I6).
  • Idle restart after a multi-RTT silence.
  • Repeated losses within a single Recovery epoch.
  • CUBIC's W_max reduction under fast convergence.
  • Algorithm swap mid-connection — not supported, must be rejected at config time, not attempted at runtime.
  • Persistent congestion immediately following a fresh slow-start (I9 re-triggering before cwnd has grown meaningfully).

17.9 Failure Analysis

  • Symptom: unfairness — one flow starves another sharing a bottleneck.
  • Alternate symptom: network collapse from runaway cwnd growth undetected, or bandwidth starvation from an overly conservative decrease that never recovers.
  • Detection: fairness-competition simulation regression, cwnd_bytes telemetry divergence from expected AIMD/cubic shape.
  • Containment: connection-scoped; a single misbehaving flow's cwnd bug does not corrupt shared node-level accounting (P3).

17.10 Operational Notes

  • Metrics: cwnd_bytes, slow_start_exits_total, congestion_events_total, cwnd_floor_hits_total, bandwidth_estimate_bps.
  • Tracing spans: congestion.on_ack, congestion.on_loss, congestion.state_transition.
  • Structured-log fields: cc_algorithm (reno|cubic), congestion_state.
  • Deployment: algorithm choice is a per-connection config, swappable fleet-wide via a config rollout without a binary redeploy.

18. Phase 6 — Pacing Engine

18.1 Objectives

Implement the token-bucket pacing scheduler (P12) that turns a congestion controller's pacing_rate() into bounded, burst-limited transmission timing.

18.2 Detailed Implementation Steps

Implement quic-pacer (lib.rs, pacer.rs, token_bucket.rs). Implement the TokenBucket (§11) refill/drain cycle against the monotonic clock from §12 (P4), sized from the active CongestionController's pacing_rate(). 18.3 Deliverable

A stable pacing subsystem: given a pacing_rate() and a send request, either grants immediate transmission, defers to a computed wake deadline, or reports starvation — all replay-deterministic.

  • fixtures/pacing/burst_amplification.trace — bottleneck-queue amplification regression case.
  • fixtures/pacing/idle_restart_pacing.bin — token-bucket behavior after an idle gap.

18.6 Pitfalls

  • Scheduler jitter causing pacing bursts: manifestation — packets sent in clumps despite a smooth target rate; root cause — timer-wheel wake delay accumulates unspent tokens; debugging — pacing_debt_ns histogram correlated with runtime_timer_drift_ns (§12); recovery — cap accumulated token carry-over, don't let debt compound indefinitely.
  • Token-refill drift: manifestation — pacing rate silently diverges from pacing_rate(); root cause — improper refill-interval rounding compounds over many refills; debugging — differential test refill logic against a reference float computation off the hot path; recovery — single canonical fixed-point refill formula (ties to §17.7's determinism concern).
  • Idle-restart pacing overshoot: manifestation — a burst on resume after silence; root cause — stale token balance retained across the idle gap; debugging — fixtures/pacing/idle_restart_pacing.bin; recovery — reset token balance to capacity, not accumulated debt, on idle restart.
  • Starvation misclassified as healthy pacing: manifestation — a connection appears "paced" but is actually stalled; root cause — starvation detector threshold set too loose; debugging — cross-check pacing_queue_depth growth against zero-token duration; recovery — tighten starvation threshold to one RTT (I10).

18.7 Performance Concerns

  • Timer-wake amplification: one wake per packet is too fine-grained at 250k connections/node — batch wakeups per shard.
  • Syscall-batching interaction (sendmmsg, ADR-06): release a batch's worth of tokens together when the rate allows.
  • Pacing granularity floor: §4's ≤ 1 ms pacing-clock granularity bounds achievable smoothness at high rates.
  • Token-bucket refill computation must avoid a full division on every send-path check — precompute the refill-per-tick constant.

18.8 Edge Cases

  • Idle restart after a multi-RTT gap (§18.6).
  • cwnd collapse mid-pacing-interval: tokens must not outlive the new, smaller cwnd.
  • Delayed wakeups under scheduler load.
  • Pacing rate recomputed to zero transiently during a congestion-state transition — must not deadlock (ties to I10).
  • Extremely high pacing rate exceeding what the batching syscall layer can sustain — backpressure to the caller, not silent drop.
  • Two congestion-state transitions arriving between consecutive pacer wakeups, requiring the pacer to use only the latest rate.

18.9 Failure Analysis

  • Symptom: microbursts causing bottleneck-queue drops.
  • Alternate symptom: switch-queue drops (correlated packet-loss bursts, not random loss — confuses §16's loss classification), or RTT spikes from self-inflicted queueing delay.
  • Detection: pacing_burst_bytes and pacing_queue_depth alert thresholds (§24).
  • Containment: pacing state is connection-scoped; a misbehaving pacer does not affect sibling connections' token budgets.

18.10 Operational Notes

  • Metrics: pacing_debt_ns, pacing_burst_bytes, pacing_queue_depth, pacing_starvation_total.
  • Tracing spans: pacer.refill, pacer.grant, pacer.defer.
  • Structured-log fields: tokens_available, pacing_rate_bps.
  • Rollback: pacing constants (burst multiple, starvation threshold) are hot-reloadable config, no redeploy required.

  • Broken middleboxes mangling ECN: manifestation — false congestion signaled on an otherwise healthy path; root cause — a middlebox remarks or strips ECN codepoints; debugging — compare self-reported sent-ECN codepoints against peer-reported received counts; recovery — validation-failure counter trips ECN disable for that path (I11), never for the fleet.
  • CE-mark double-counting: manifestation — one physical congestion event triggers two on_ecn_ce() calls; root cause — CE counter updated both on ACK-range decode and on a separate ECN-summary frame; debugging — cross-reference ecn_ce_total against ACK-batch count; recovery — attribute CE marks exactly once per ACK batch.
  • Persistent-congestion false positive on a genuinely idle connection: manifestation — I9 triggers with no real congestion; root cause — PTO-failure counting doesn't exclude idle-induced probe gaps; debugging — cross-check pto_count against concurrent inflight_bytes; recovery — only count PTO failures while data was actually inflight.

19.7 Performance Concerns

  • Counter synchronization across ECN and ACK processing: single-writer per connection avoids a lock (ADR-08).
  • Telemetry amplification from per-packet ECN tracking at 250k connections — aggregate to per-shard histograms, not per-connection time series (§24).
  • Validation-state-machine transitions must stay off the ACK-decode hot path — evaluate once per ACK batch, not per range.

19.8 Edge Cases

  • Partial ECN deployment: one direction ECN-capable, the other not.
  • CE-mark storms exceeding the counter's expected range.
  • Persistent congestion spanning a packet-number-space discard (§13.8).
  • ECN validation failure occurring mid-persistent-congestion-window — two independent degraded-path signals overlapping.
  • A peer that stops sending ECN feedback entirely mid-connection — must be distinguished from validation failure.
  • A path that flips between ECN-capable and ECN-broken repeatedly (flapping middlebox).

19.9 Failure Analysis

  • Symptom: incorrect ECN handling collapses throughput by treating every CE mark as a full loss event.
  • Alternate symptom: congestion signaling disabled entirely from over-eager ECN disable on transient noise.
  • Detection: ecn_validation_failures rate and ecn_ce_total correlated with actual loss events.
  • Containment: ECN state is per-path; disabling it for one path does not affect sibling connections.

19.10 Operational Notes

  • Metrics: ecn_ce_total, ecn_validation_failures, persistent_congestion_total (shared with §17), path_degradation_events_total.
  • Tracing spans: ecn.validate, ecn.ce_process, loss.persistent_congestion_confirm.
  • Structured-log fields: ecn_state (capable|disabled|unknown), persistent_congestion_duration_ms.
  • Deployment: ECN can be globally disabled via config for a fleet segment behind a known-broken middlebox without touching the loss-detection binary.

20. Phase 8 — Deterministic Simulator, Fault Injection & Replay Tooling

20.1 Objectives

Build the deterministic network simulator (quic-sim) driving every prior phase's real API under injected faults, and the replay pipeline (quic-replay) turning production telemetry into re-executable traces (P1, P6).

20.2 Detailed Implementation Steps

Implement quic-sim (lib.rs, network.rs, fault.rs): a deterministic event-queue network model supporting delay, loss, duplication, reordering, bandwidth shaping, and ECN marking, driven by a fixed seed (P1) and consuming the exact same Transport Integration API as production (§3.2). Implement quic-replay (lib.rs, log.rs, event.rs): the ReplayEvent (§11) append pipeline, sequence-continuity enforcement (I12), and a re-execution driver that feeds a recorded log back through the recovery core to reproduce a prior run bit-for-bit. Kleppmann's (2017) stream-processing determinism model motivates the append-only, gap-free design. Add queue modeling (bounded bottleneck-queue simulation, needed for realistic pacing/loss interaction fixtures) and simulation-clock-drift detection to catch any P4 violation introduced by later code.

20.3 Deliverable

A fully replayable transport simulator producing deterministic, reproducible congestion traces, and a replay tool that re-executes any production connection's recorded events with checksum-verified fidelity.

20.4 Acceptance Criteria

Deterministic outputs: 1,000 repeated runs of fixtures/sim/cellular_network.sim with the same seed produce byte-identical replay logs (I12, P1). Reproducible congestion traces across the reference fixtures below with zero divergence. Replay throughput exceeds 1,000,000 events/sec (§4).

20.5 Conformance Fixtures

  • fixtures/sim/cellular_network.sim — variable-RTT, bursty-loss mobile-network profile.
  • fixtures/sim/satellite_rtt.sim — high-RTT (600 ms ceiling, §4) GEO-satellite profile.
  • fixtures/sim/reorder_heavy.sim — reordering at the §4 32-packet boundary.
  • fixtures/sim/ack_blackhole.sim — total ACK loss for a bounded interval, tests PTO escalation.

20.6 Pitfalls

  • Non-deterministic scheduling in the simulator itself: manifestation — two runs from the same seed diverge; root cause — the simulator's own event-queue ordering uses a non-stable tie-break (e.g. hash-map iteration order); debugging — differential replay across repeated runs; recovery — deterministic tie-break by (timestamp, insertion sequence).
  • Simulation-clock drift from the production clock abstraction: manifestation — simulated PTO timing diverges from what §12's real-clock backend would produce; root cause — the fake-clock backend rounds differently than the real one; debugging — shared rounding-helper differential test (ties to §15.6); recovery — one clock-math implementation, two backends.
  • Replay divergence from a schema change: manifestation — an old replay log fails to re-execute after a code change; root cause — a ReplayEvent field changed meaning without a schema-major bump; debugging — replay-log version check at load time; recovery — reject mismatched-schema replay explicitly rather than misinterpreting it (§25).

20.7 Performance Concerns

  • Event-queue scaling: binary-heap-backed priority queue bounded by concurrent simulated connections.
  • Simulation-clock-drift checks add overhead proportional to event count — sample, don't check every event, outside a dedicated determinism-CI job.
  • Replay-log read throughput for large historical traces: streaming decode, not full-file load.
  • Fault-injection random-number generation must itself be deterministic (seeded), not merely the event ordering.

20.8 Edge Cases

  • 100% packet-loss intervals — must not deadlock the simulated connection, PTO must still escalate correctly.
  • ACK blackholes of bounded duration.
  • Simulator seed reuse across unrelated test cases — must be namespaced to avoid accidental correlation.
  • Replay of a log spanning a packet-number-space discard boundary.
  • Replay-log gap from a crashed production process mid-append — I12 must flag it, not silently skip.
  • A simulated connection outliving the configured simulation-clock horizon.

20.9 Failure Analysis

  • Symptom: simulator divergence invalidates regression testing — a "passing" simulation run may not reflect the real recovery engine's behavior.
  • Alternate symptom: replay debugging becomes misleading when a postmortem is built on a divergent replay.
  • Detection: determinism-CI job comparing repeated-seed runs.
  • Forensics: starts from the first diverging event sequence number (I12).

20.10 Operational Notes

  • Metrics: replay_gap_detected_total (shared with I12), sim_event_queue_depth, replay_throughput_events_per_sec.
  • Tracing spans: sim.inject_fault, replay.append, replay.reexecute.
  • Structured-log fields: sim_seed, replay_schema_version.
  • Deployment: quic-sim and quic-conformance (§21) run in CI on every PR; quic-replay ships to production for on-demand postmortem tooling.

21.1 Objectives

Ship the RFC 9002 conformance runner (quic-conformance), the operator CLI (quic-cli), and harden the system for production rollout: soak testing, fuzz-corpus maturity, and delivery-rate-based bandwidth-estimation groundwork ahead of a future BBR phase.

21.2 Detailed Implementation Steps

Implement quic-conformance (lib.rs, runner.rs): a vector runner executing every fixtures/** conformance case from Phases 0–8 against the assembled workspace, gating merges (P9). Implement quic-cli (main.rs): operator commands for replay diff, metrics snapshot, and connection inspect, backed by quic-replay and quic-telemetry. Anchor: Dean & Barroso's (2013) tail-at-scale reasoning justifies the soak-testing emphasis on p99/p999 behavior, not just mean throughput. Multipath QUIC scheduling is explicitly out of scope for this rollout and is deferred until single-path production hardening is complete (PhaseDeferred("§21")).

21.3 Deliverable

A CI-gating conformance suite covering every phase's fixtures, an operator CLI capable of diagnosing a live or replayed connection without reading source code, and a soak-tested build ready for staged production rollout.

21.4 Acceptance Criteria

100% of fixtures/** (≥ 40 named fixtures across Phases 0–8) pass under quic-conformance. quic-cli replay diff correctly highlights the first divergent event between two logs in fixtures/cli/replay_diff_case.bin. 72-hour soak run sustains the §4 availability budget (99.99% crash-free) with zero unbounded memory growth (P7).

21.5 Conformance Fixtures

  • fixtures/cli/replay_diff_case.bin — two near-identical replay logs with one injected divergence.
  • fixtures/conformance/full_suite_manifest.json — the aggregated fixture manifest quic-conformance executes.
  • fixtures/soak/72h_profile.sim — long-duration mixed-fault soak profile.
  • fixtures/bandwidth/delivery_rate_trace.bin — delivery-rate-sampling regression case for the BBR-readiness interface.

21.6 Pitfalls

  • Conformance suite drift from fixture rot: manifestation — a fixture no longer represents the RFC vector it was named for after an unrelated refactor; root cause — fixtures are edited ad hoc without re-validating against RFC 9002 text; debugging — periodic manual re-audit of fixtures/loss/ and fixtures/congestion/ against RFC 9002; recovery — fixture changes require a linked ADR-12-style justification.
  • CLI masking real state via stale cache: manifestation — quic-cli connection inspect shows outdated cwnd/RTT; root cause — CLI reads a cached metrics snapshot instead of live state; debugging — compare CLI output against direct quic-telemetry scrape; recovery — CLI always requests a fresh snapshot, never trusts a cache older than one telemetry interval.
  • Soak-test memory growth masked by GC-like behavior: not applicable in Rust (no GC), but slab-reclamation lag (§13.6) can look like a leak; debugging — packet_history_entries trend over the 72-hour window; recovery — verify reclamation sweep cadence matches connection churn rate.

21.7 Performance Concerns

  • Conformance-suite runtime must stay CI-fast: parallelize fixture execution across cores, not serialize 40+ fixtures.
  • CLI responsiveness against a live production connection: bounded-time snapshot read, never blocking the hot path.
  • Soak-test telemetry cardinality: aggregate, don't retain full per-connection history for 72 hours.
  • Fuzz-corpus growth must be pruned periodically or corpus-replay time in CI degrades unboundedly.

21.8 Edge Cases

  • A fixture that passes in isolation but fails when run after another fixture mutates shared simulator state — a test-isolation bug, not a product bug, must be caught by CI.
  • quic-cli invoked against a connection that closes mid-inspection.
  • Soak test spanning a machine clock's NTP correction — must show zero P4 violations.
  • Bandwidth-estimator producing a sample during a period with no ACKs — must report "no estimate," not zero.
  • A conformance vector added for one RFC 9002 clause that inadvertently also exercises an unrelated ECN code path.

21.9 Failure Analysis

  • Symptom: a weak conformance suite lets an RFC 9002 regression reach production undetected.
  • Alternate symptom: a broken CLI slows incident response during a live congestion incident.
  • Alternate symptom: a failed soak test surfaces slow leaks or rare-event accumulation (e.g. slab fragmentation, §12.6) that short-duration tests miss.
  • Detection: conformance-suite red build; soak-test dashboard trend lines.
  • Forensics: replay log from the soak run pinpoints the first anomalous event.

21.10 Operational Notes

  • Metrics: conformance_pass_rate, soak_uptime_seconds, bandwidth_estimate_confidence.
  • Tracing spans: conformance.run_vector, cli.inspect, cli.replay_diff.

24. Operational Readiness

Metrics Strategy

  • Mandatory fleet-wide metrics: cwnd_bytes, inflight_bytes, pto_count, pacing_jitter_ns, rtt_smoothed_ms, packet_loss_rate, retransmit_rate, scheduler_wake_lag_ns.
  • Per-phase metrics: every metric enumerated in each N.10 (§12–§21) is exported unconditionally, not sampled.
  • Label discipline: metrics are label-bounded (T9) — no raw peer-controlled strings as label values, ever.
  • Cardinality budget: per-shard aggregation, not per-connection time series, for any metric that would otherwise scale with the 250k-connection ceiling (§4).

Tracing Strategy

  • Every connection carries a connection UUID correlating packet-sequence spans, recovery-epoch spans, and pacing-event spans (ADR-10, OTLP export).
  • Span names follow the <crate>.<action> convention established in §12–§21 (e.g. ack_engine.decode, pacer.grant).
  • Sampling: hot-path spans (ACK decode, pacing grant) are sampled under load; state-transition spans (loss declaration, congestion-state change, ECN disable) are never sampled.
  • Trace context propagates through quic-cli's replay diff and connection inspect commands (§21) for incident response.

Alerting Philosophy

  • Alert on: replay divergence (FM-2), pacing-burst amplification (FM-3), persistent-congestion spikes (FM-7), ACK corruption (T1/T2), timer lag (FM-5).
  • Alerts key off the same metric names used in dashboards — no alert-only shadow metrics (P10).
  • Every alert names the invariant or failure-mode ID it corresponds to, so on-call can jump directly to §7 or §23.

25. Compatibility & Versioning

Wire Compatibility

RFC 9002-compliant behavior is non-negotiable (P9); ACK-frame semantics are RFC 9000-locked (§14) and never independently versioned. Congestion-algorithm identity (cc_algorithm, §17.10) is a connection-level negotiated/configured value, not part of the wire contract.

Storage / Replay-Log Compatibility

Replay logs are versioned major.minor.schema (ADR-19, ADR-05). ReplayEvent/EventKind/EventPayload (§11) changes are additive-only within a minor version; removing or repurposing a field requires a schema-major bump and an explicit migration note in CHANGELOG.md. A replay tool refusing a mismatched-schema log (§20.6) is correct behavior, not a bug.

API Compatibility

CongestionController and RttEstimator (§11) are additive-extend traits (P11) — new hooks ship with default no-op implementations so existing implementers keep compiling. Breaking trait changes require a major-version bump across all 12 crates simultaneously (workspace-versioned, ADR-15).

29. Scalability Analysis

Primary bottlenecks:

  • Packet-metadata memory (C1/C2, §32) at the 250k-connection ceiling.
  • Pacing-timer wakeups (§18.7) under fine-grained per-connection scheduling.
  • ACK-range scan cost (§14.7) under adversarial reordering.
  • Telemetry cardinality (T9) at fleet scale.
  • Replay-log IO bandwidth (C3/C4, §32).

Scaling ceilings:

  • Timer-wheel contention beyond the ADR-23 design point, extending C5's 750,000-slot baseline.
  • Socket-batching efficiency diminishing beyond the §4 32-worker/node assumption.
  • Cache-locality degradation once per-connection metadata (§4's ≤ 64 B/entry target) spills past L2.
  • Cross-NUMA-socket connection migration cost if shard rebalancing (FM-5's manual recovery) crosses socket boundaries.

Horizontal scaling: stateless transport workers, connection sharding (ADR-08), independent pacing domains per shard — adding a node adds capacity linearly until cross-shard telemetry aggregation (§24) becomes the bottleneck.

Vertical scaling: multicore packet processing, batched syscalls (ADR-06), memory-pool reuse (P7-aligned bounded slabs), NUMA-aware socket placement (§4's NUMA-awareness recommendation) — diminishing returns past the C6 FD-budget ceiling without a §4 revision.

30. Mental Models & First Principles

  • MM1 — ACK Clock. Compressed insight: transmission cadence is derived from ACK arrival, not from a local timer · predicts: bursty ACK arrival (compression) causes bursty sending even with a perfect pacer upstream · bug class without it: blaming the pacer (§18) for a burst actually caused by the network path compressing ACKs · applies in §14 and §18.
  • MM2 — Bandwidth-Delay Product. Compressed insight: the amount of data "in the pipe" at full utilization is rate × RTT · predicts: a token bucket sized for low-RTT paths starves high-RTT paths · bug class without it: under-provisioning pacing-token capacity for the §4 600 ms RTT ceiling · applies in §18 and §32.
  • MM3 — Retransmission Ambiguity. Compressed insight: an ACK for a retransmitted packet cannot tell you which transmission it acknowledges · predicts: naive RTT sampling on retransmissions systematically biases the estimate · bug class without it: RTT/PTO instability traced to "network jitter" that is actually a sampling bug · applies in §15 and §7.
  • MM4 — Fail-Closed Beats Best-Effort at Scale. Compressed insight: at 250k connections, a rare silent-corruption bug multiplies into an unattributable fleet-wide incident · predicts: fail-open designs accumulate corrupted state invisibly until a much larger failure surfaces · bug class without it: "the system recovered on its own" masking an accounting bug that will resurface under load · applies in §7 and §23.
  • MM5 — Congestion Signals Are Probabilistic, Not Certain. Compressed insight: loss, ECN CE marks, and delay are all noisy proxies for congestion, never direct measurements of it · predicts: treating any single signal as authoritative overreacts to noise · bug class without it: ECN promoted to authoritative (rejected in §11/P13) causing false congestion collapse · applies in §17 and §19.
  • MM6 — Determinism Is a Design Constraint, Not a Testing Nicety. Compressed insight: replayability must be designed into the data model (§11), not bolted on via logging · predicts: any wall-clock read or unordered iteration silently breaks replay months later · bug class without it: "flaky" simulation failures that are actually real nondeterminism bugs · applies in §12 and §20.
  • MM7 — Backpressure Must Be Structural. Compressed insight: a system that can be told "no" at every layer cannot collapse from one misbehaving input source · predicts: any layer that queues without a bound becomes the next incident's root cause · bug class without it: an unbounded retransmission queue absorbing a burst until it OOMs · applies in §6 and §29.
  • MM8 — Loss and Delay Are Different Failure Signals. Compressed insight: a packet-threshold loss (reordering) and a time-threshold loss (real congestion or a dropped packet) demand different responses even though both end in the same Lost state · predicts: collapsing the two into one code path loses the information needed to tune reordering tolerance independently of RTT-based timeout tolerance · bug class without it: a fix for spurious loss under reordering accidentally weakens genuine-congestion responsiveness · applies in §16.
  • MM9 — Telemetry Cardinality Is a Capacity Dimension. Compressed insight: an unbounded label (e.g. per-packet or per-connection granularity) turns a metrics system into the next bottleneck, independent of the transport logic being measured · predicts: a dashboard that looks fine in a 100-connection test environment can take down the telemetry pipeline at the §4 250k-connection ceiling · bug class without it: shipping a well-intentioned new metric that silently becomes T9 · applies in §24 and §29.
  • MM10 — A Deferred Feature Is a Design Decision, Not a TODO. Compressed insight: deferring BBR/multipath/hardware pacing (§35) with an explicit un-defer trigger forces the current design to be complete and correct without them, rather than half-built around a feature that never lands · predicts: a codebase with silent TODOs instead of registered deferrals accumulates dead partial implementations · bug class without it: a half-wired BBR code path that neither works nor is removed · applies in §35 and §9.

32. Back-of-Envelope Capacity Model

  • C1 — Fleet memory ceiling. 250,000 connections × 128 KB steady-state ceiling (§4) = 32,000,000 KB = 32 GB/node, fitting a 64 GB node at 50% headroom for OS, telemetry, and slab fragmentation.
  • C2 — Worst-case per-connection metadata. 65,536 inflight packets × 256 B/packet ceiling (§4) = 16,777,216 B ≈ 16 MB worst case — 128× the 128 KB steady-state budget, meaning typical inflight occupancy must stay ≤ 0.8% of the ceiling under normal operation.
  • C3 — Replay-log append rate. 1,000,000 events/sec (§4) × ~64 B/event (postcard-framed ReplayEvent, §11) = 64,000,000 B/sec = 64 MB/sec sustained; × 1.35 storage amplification (§4) = 86.4 MB/sec worst case.
  • C4 — Replay-log daily volume. 64 MB/sec (C3) × 86,400 sec/day = 5,529,600 MB/day ≈ 5.4 TB/day/node at sustained peak, driving the retention/rotation policy in §27.
  • C5 — Timer-wheel slot baseline. 250,000 connections × 3 packet-number spaces × 1 loss timer each (I8) = 750,000 concurrently addressable timer slots, the ADR-23 wheel's O(1)-insert design point.
  • C6 — FD budget exactness. 32 workers/node (§4) × 4 sockets/worker (§4) = 128 FDs/node = the §4 FD budget exactly, zero headroom — any additional per-worker socket forces a §4 budget revision.
  • C7 — Correlated PTO-storm spike. 250,000 connections × 6 worst-case consecutive PTO backoffs before persistent congestion (I9) = 1,500,000 timer re-arms in a worst-case correlated-failure window = 2× the C5 baseline the wheel must transiently absorb.
  • C8 — Pathological ACK-processing CPU bound. 250,000 connections × 1 ACK per §4's 1 ms RTT floor = 250,000,000 ACKs/sec fleet-wide × 5 µs/ACK p50 (§4) = 1,250 core-seconds/sec of work — real traffic is not synchronized at the RTT floor across all connections, so this bounds only the pathological worst case, not expected load.
  • C9 — Per-shard connection density. 250,000 connections ÷ 32 workers (§4) = 7,813 connections/worker, each needing its own timer-wheel slot (C5) and slab region — sizes the per-worker memory arena at 7,813 × 128 KB ceiling = 1,000,064 KB ≈ 977 MB/worker.
  • C10 — Availability budget in absolute time. 99.99% (§4) means ≤ 0.01% × 525,600 min/year = 52.56 minutes/year of unplanned recovery-subsystem downtime — roughly 13.14 minutes per quarter (52.56 ÷ 4) if evenly distributed, the number FM-1 through FM-12's mean-time-to-detect must collectively stay under.
  • C11 — Conformance-suite CI budget. ~40 fixtures (§21.4) × an assumed 2 s/fixture parallel-execution target = 80 fixture-seconds of work, divided across ≥ 8 parallel CI runners (§21.7) = 10 s wall-clock, keeping the conformance gate from becoming the release-velocity bottleneck.
  • C12 — Soak-test event volume. 72 hours (§21.4) × 3,600 sec/hour × up to 1,000,000 events/sec (§4) = 259,200,000,000 events theoretical ceiling per soaked node, motivating the aggregated (not per-event-retained) soak-telemetry policy in §21.7.

34. Alternative Architectures (Roads Not Taken)

Alt A — Kernel-Resident Congestion Control

+------------------+      +---------------------+
| Application      | ---> | tcp_congestion_ops   |
+------------------+      | (in-kernel module)   |
                           +---------------------+
                                    |
                                    v
                           +---------------------+
                           | Kernel TCP/IP stack |
                           +---------------------+

Wins in: environments where kernel-level scheduling and NIC integration already exist and userspace round-trips are the bottleneck (classic kernel TCP deployments). Real system: Linux kernel's tcp_congestion_ops framework (pluggable in-kernel CUBIC/BBR modules). Rejected because: userspace determinism and replay (P1, P6) cannot be retrofitted onto kernel scheduling, and portability across the BSD/macOS secondary targets (§1.5) breaks entirely.

Alt B — Hashmap-Indexed Send History

HashMap<PacketNumber, SentPacket>
  lookup: O(1) average, cache-hostile
  iteration: unordered, defeats descending ACK-range scan

Wins in: low connection counts (<1,000/node) where implementation simplicity and flexible eviction outweigh cache locality. Real system: early quic-go send-history implementations before locality-driven rewrites. Rejected because: at the §4 250k-connection ceiling, hashmap cache-miss amplification dominates ACK-processing latency (ADR-27's rationale), breaking the §4 p99 budget.

Alt C — BBR-First Congestion Control

CongestionController = BbrV1 { delivery_rate_filter, min_rtt_filter, pacing_gain_cycle }

Wins in: long-fat-network-dominated fleets (satellite CDN edge, transcontinental links) where CUBIC's loss-based signal is too slow to react. Real system: msquic (ships BBR by default). Rejected for v1 because: BBR's delivery-rate-sampling determinism needed for replay (P1) is unsolved absent the groundwork planned for §21; CUBIC's RFC 8312 formula is simpler to make bit-reproducible today, with BBR deferred (§35, PhaseDeferred("§17")).

Alt D — Single Global Connection Table with Lock Striping

Mutex<HashMap<ConnId, ConnectionState>>  (striped N-ways)
  every ACK/loss/pacing decision acquires a stripe lock

Wins in: moderate connection counts where a simpler mental model (one table, no actor mailboxes) is worth some contention. Real system: earlier lsquic engine-wide locking designs before per-connection isolation. Rejected because: cross-connection lock contention on the hot ACK path violates the single-writer, no-cross-connection-contention goal (ADR-08) at the §4 250k-connection scale.

36. Glossary

  • ACK Clock — transmission cadence derived from ACK arrival rather than a local timer (MM1).
  • PTO — probe timeout; the deadline after which an unacknowledged ack-eliciting packet triggers a probe.
  • cwnd — congestion window; the byte budget of data allowed inflight.
  • ECN — explicit congestion notification; IP-layer congestion signaling (RFC 3168).
  • Inflight — bytes sent but not yet acknowledged or declared lost.
  • Pacing — rate-controlled transmission spreading a cwnd's worth of sends across time.
  • RTT — round-trip time; send-to-ACK latency.
  • rttvar — RTT variance estimator, smoothed exponentially (§15).
  • Persistent congestion — sustained network collapse detected via consecutive PTO failures (I9).
  • Spurious loss — a packet incorrectly declared lost that was, in fact, delivered.
  • Recovery epoch — one congestion-recovery interval bounded by entry into and exit from the Recovery state.
  • Packet threshold — reordering-based loss heuristic (kPacketThreshold = 3, RFC 9002).
  • Time threshold — RTT-based loss heuristic (kTimeThreshold = 9/8, RFC 9002).
  • Tail loss — loss of the last packet(s) in a burst, typically requiring a PTO probe rather than threshold detection.
  • ACK compression — bursty ACK arrival caused by network-path buffering, distorting perceived cwnd headroom.
  • GSO — generic segmentation offload; kernel-assisted batching of outbound UDP datagrams.
  • GRO — generic receive offload; kernel-assisted coalescing of inbound UDP datagrams.
  • Replay log — the durable, sequence-continuous stream of ReplayEvents (§11) enabling deterministic re-execution.
  • Pacing debt — the delayed transmission budget accrued when tokens are unspent past their ideal release time.
  • Transport epoch — a monotonic per-connection timeline used to correlate telemetry across recovery-state transitions.
  • Slow start — the initial CongestionState in which cwnd grows exponentially until ssthresh.
  • Congestion avoidance — the steady-state CongestionState with additive (Reno) or cubic (CUBIC) cwnd growth.
  • Recovery (state) — the CongestionState entered on loss/CE detection, exited after one clean RTT.
  • min_rtt — the lowest RTT sample observed over the connection's lifetime, used for ACK-delay correction bounds.
  • smoothed_rtt — the exponentially smoothed RTT estimate (RFC 9002 §5 formula).
  • max_ack_delay — the transport-parameter-negotiated ceiling on peer-reported ACK delay.
  • Token bucket — the pacing primitive holding a capped balance of send-eligible bytes, refilled at pacing_rate().
  • Burst limiter — the cap on token-bucket capacity preventing large instantaneous sends.
  • Packet number space — one of {Initial, Handshake, Application}, each with independent packet-number and loss-timer state.
  • Send history — the per-connection record of sent, unacknowledged packets and their metadata.
  • Slab arena — a fixed-slot allocator used for SentPacket storage, chosen for cache locality (ADR-27).
  • DeliveryState — the exhaustive per-packet state enum {Sent, Acked, Lost, PtoPending} (I14).
  • AckRange — a decoded, validated [start, end] inclusive range of acknowledged packet numbers.
  • CongestionController — the pluggable trait implemented by Reno, CUBIC, and (deferred) BBR.
  • RttEstimator — the trait owning RTT sampling, smoothing, and PTO-base computation.
  • CE mark — a Congestion Experienced ECN codepoint observed on a received packet.
  • ECN validation — the state machine confirming a path's ECN marking is trustworthy before acting on it.
  • Path degradation — a sustained shift in loss/RTT/ECN behavior attributable to the network path rather than a transient blip.
  • Timer wheel — the hierarchical, bucketed-by-deadline structure scheduling PTO and pacing wakeups (ADR-23).
  • Replay determinism — the property that identical inputs and seed produce byte-identical replay-log output (P1).
  • Fixed seed — the deterministic random-number seed driving quic-sim fault injection.
  • Conformance vector — a named fixture encoding an RFC 9002 expected input/output pair.
  • Bandwidth-delay product (BDP) — the data volume "in flight" at full path utilization, rate × RTT (MM2).
  • ACK eliciting — a packet whose receipt obligates the peer to send an ACK within a bounded delay.
  • Idle restart — resumption of sending after a silence period exceeding one RTT, requiring cwnd/pacing re-derivation.
  • kInitialRtt — the RFC 9002 bootstrap RTT value (333 ms) used before any real sample exists.
  • kGranularity — the RFC 9002 timer-granularity constant (1 ms) added to the PTO computation.
  • ssthresh — slow-start threshold; the cwnd value at which growth switches from exponential to additive/cubic.
  • AIMD — additive-increase/multiplicative-decrease; Reno's core growth/backoff discipline (Jacobson 1988).
  • Fast convergence — CUBIC's mechanism for accelerating cwnd reduction when a flow's own W_max recently decreased.
  • Hybrid Slow Start — a slow-start-exit heuristic using delay increase as an early signal; out of scope for CUBIC v1 (§17).
  • Delivery rate — bytes delivered divided by the time interval over which they were delivered; BBR's core signal (Cardwell et al. 2016).
  • App-limited — a sending period where the application, not the network, is the throughput bottleneck; must be excluded from bandwidth samples.
  • W_max — CUBIC's remembered pre-reduction window size, anchoring the cubic growth curve's inflection point.
  • NUMA — non-uniform memory access; cross-socket memory latency that motivates §4's NUMA-aware socket-placement recommendation.
  • Shard — a partition of connections assigned to one worker thread for lock-free, single-writer processing (ADR-08).
  • OTLP — OpenTelemetry Protocol; the span-export format chosen in ADR-10.
  • SBOM — software bill of materials; the per-release dependency manifest required by §27.
