In one paragraph

When data crosses a network, some packets are lost, and the sender has to work out which ones, send them again, and slow down enough not to flood the path. This design builds that machinery for QUIC from scratch in Rust: tracking every sent packet, reading acknowledgements, estimating round-trip time, declaring loss, scheduling probes, capping data in flight and spacing sends in time (§1.1, ADR-01). It is a library embedded in a QUIC stack, not a whole stack (§1.3). CDN operators, networking teams and RPC-runtime SREs run it (§1.6). Its distinguishing choice is that every decision is replayable bit for bit from a log and a fixed seed (P1, P6, §31).

The problem, concretely

A sender has put six packets on the wire, numbered 100 to 105. The peer's acknowledgement says it received 105, 104 and 103, and also 101 and 100. Packet 102 is in neither range, and three higher-numbered packets have been acknowledged, so the blueprint calls it an implied loss (§8.5). Handling that one gap means reducing the bytes in flight, telling the congestion controller, and recalculating how fast to send (§8.5).

Each of those steps has a naive version that fails, and the blueprint names the failure:

  • Taking an RTT sample from an acknowledgement of a resent packet. The ACK cannot say which transmission it answers, so the estimate is biased and timeouts then look like "network jitter" (MM3, I3).
  • Sending a full window in one burst. The queue at the bottleneck overflows, which is why pacing exists at all (§2.2, P12).
  • Treating every loss the same. Reordering and genuine congestion need different responses, and tuning one then weakens the other (MM8).
  • Trusting one signal. Loss, ECN marks and delay are all noisy proxies for congestion (MM5, P13).

Underneath all four, time is uncertain: delayed ACKs, reordering, ACK compression and timer drift (§2.1, MM1). The design answers with explicit state machines (§8) and full determinism, so an incident can be reproduced from a replay log and a fixed seed (P1, MM6, §20).

How it works, end to end

Follow one packet through the boxes of §3's diagram, compacted here:

 Application layer            send_frame() / on_ack() / poll_budget()
   -> Transport Integration API (trust boundary: caller cannot touch cwnd or inflight directly)
   -> Packet Assembly           quic-packet-space: packet numbers, send-history slab, SentPacket
   -> Congestion + Recovery Core (single writer per connection)
        quic-ack-engine, quic-rtt, quic-loss-detector, quic-congestion, quic-pacer, ECN sub-state
   -> Send Budget Engine        cwnd | pacing tokens | inflight bytes
   -> Runtime Event Scheduler   timer wheel, wake queues
   -> UDP Socket Layer          sendmmsg / recvmmsg / GSO       -> network path
 Telemetry: Recovery Core -> quic-telemetry -> tracing spans -> quic-replay (durable log)
 Simulation (tests only): quic-sim drives the same API as production
  1. Asking to send. The application calls the Transport Integration API, the only crossing point into recovery. It must ask poll_tx_budget() before building any packet (§3.2, P2).
  2. Registering the packet. quic-packet-space gives it the next number in its space and stores an immutable SentPacket in a slab, the one owner of that record (§3.2, §11, P5, I1).
  3. Budget. The Send Budget Engine is the only place inflight bytes are counted. A send is allowed only up to the smaller of congestion-window headroom and pacing tokens (§3.2, P2, P3).
  4. Timers. The timer wheel wakes the system when a probe or pacing deadline passes (§3.2, ADR-23). quic-recovery-core supplies the shared types, invariant checks, and the monotonic clock and timer abstractions (§1.2, P4).
  5. The ACK comes back. quic-ack-engine decodes the ranges, checks they are well ordered, and extracts implied losses (§14, I4). quic-rtt turns the send and receive times into an RTT estimate (§15). quic-loss-detector declares loss and arms the single loss timer per space (§16, I8). quic-congestion adjusts the window (§17), and quic-pacer converts the window into a send rate (§18).
  6. Everything is logged. Each state change is emitted as a structured event, appended to the replay log before it counts as committed (P6, P10, §3.3). quic-sim replays the same API under injected faults, quic-conformance runs RFC 9002 vectors, and quic-cli lets an operator diff two logs (§20, §21, ADR-26).

The core is a single-writer concurrency boundary with no lock on the ACK, loss or pacing path, which makes replay deterministic (§3.2, §3.3, ADR-08).

The core ideas

Packet number spaces and ACK ranges (§8.1, §8.5)

QUIC keeps three separate numbering sequences: Initial, Handshake and Application. Each tracks its own largest_acked, its own slab region, its own loss timer and its own ACK-range state (§8.1). Numbers must strictly rise within a space (I1). An ACK frame is a list of inclusive ranges that must run strictly downward and never overlap (I4). A packet is in exactly one of four states, and only these transitions are allowed (I14, §13, §11):

Packet In an ACK range? Higher packets acked Result (§8.5)
100, 101 yes, [101-100] Acked
102 no 103, 104, 105 (three, matching kPacketThreshold = 3) implied loss
103, 104, 105 yes, [105-103] Acked

The blueprint words the rule two ways: §8.3 and §14.2 count three higher acked packets as enough, while §8.5 says 102 lies below largest_acked (105) "by more than" kPacketThreshold's gap.

Losing 102 subtracts bytes_sent(102) from inflight, sends a congestion event to the controller and triggers a pacing-rate recalculation (§8.5).

RTT and the probe timeout (§8.2)

Five variables: latest_rtt, smoothed_rtt, rttvar, min_rtt, max_ack_delay. For each valid sample the blueprint's seven steps are (§8.2):

  1. Reject the sample if the packet was ambiguously retransmitted (I3).
  2. Raw sample = ACK receive time minus send time.
  3. adjusted_rtt = max(latest_rtt - min(ack_delay, max_ack_delay), min_rtt).
  4. min_rtt = min(min_rtt, latest_rtt).
  5. rttvar = 3/4 * rttvar + 1/4 * |smoothed_rtt - adjusted_rtt|.
  6. smoothed_rtt = 7/8 * smoothed_rtt + 1/8 * adjusted_rtt.
  7. PTO = smoothed_rtt + max(4 * rttvar, kGranularity) + max_ack_delay, with kGranularity = 1 ms.

Step 6 means one new sample moves the smoothed estimate by an eighth of the gap. Step 3 stops a peer from inflating RTT by claiming a huge ACK delay (I7, T13). Before any sample exists the bootstrap value is kInitialRtt = 333 ms (§36). The corrected sample must never be negative before smoothing (I7), and the arithmetic is fixed-point integer so replay cannot differ by platform (§15, P1).

Declaring a packet lost, or probing (§8.3, MM8)

A packet leaves the Sent state in one of three ways (§8.3):

Trigger Rule Meaning (MM8, §36)
Packet threshold 3 higher-numbered packets acked (kPacketThreshold = 3) likely reordering
Time threshold older than 9/8 x max(latest_rtt, smoothed_rtt) likely real loss or congestion
Probe timeout nothing acked before the PTO fires: PtoPending tail loss, last packets of a burst

The first two end in Lost. A PtoPending packet becomes Acked if its probe is answered, otherwise it stays pending and the timer re-arms (§8.3). Repeated PTO expiry backs off as 2^n x pto_base, capped (§16.2). Exactly one loss timer is armed per space (I8), and the timer is disarmed when no ack-eliciting packet is outstanding, otherwise it keeps firing on an idle connection (§16.6, I8). kPacketThreshold stays at 3, because lowering it causes spurious retransmissions (§16.6).

Congestion states and the window (§8.4, §17)

The controller is a four-state machine, owned by whichever CongestionController is active (§11). It has hooks on_packet_sent, on_packet_acked, on_packet_lost, on_ecn_ce and reports cwnd(), pacing_rate() and state() (§11). The transitions (§8.4):

From Event To
SlowStart loss or ECN CE Recovery
SlowStart cwnd >= ssthresh CongestionAvoidance
CongestionAvoidance loss or CE Recovery
Recovery one RTT elapsed, no new loss CongestionAvoidance
Recovery persistent congestion (I9) PersistentCongestion
PersistentCongestion successful send at minimum cwnd SlowStart

Reno grows additively in CongestionAvoidance and cuts multiplicatively on loss, leaving slow start at ssthresh (AIMD, §17.2). CUBIC grows along a cubic curve anchored on W_max, the window size remembered from before the last reduction, with fast convergence on repeated congestion events (§17.2, §36). The exact constants are not given in the blueprint; it points at RFC 8312 (§5). Three guards matter: the window never drops below minimum_cwnd of 2 x MSS (I6), a new loss inside the same RTT as entering Recovery is not a fresh event (§17.6), and growth is capped per ACK batch so compressed ACKs do not inflate the window (§17.6, T10).

Persistent congestion: the hard reset (§8.6, I9, I15)

If probes keep firing and nothing is acknowledged for long enough, halving the window is not enough. The blueprint defines the duration (§8.6):

pc_duration = (smoothed_rtt + max(4 * rttvar, kGranularity) + max_ack_delay) x kPersistentCongestionThreshold

where the threshold is only "a small integer constant": no section gives its value (§8.6). A run of consecutive PTO-triggered probes spanning at least pc_duration with no ACK in that space triggers I9, which sets the window to minimum_cwnd, not half (I9, §19.4). It is evaluated at three boundaries that the fixtures must cover: one probe short does not trigger, exactly at pc_duration does, and a run that spans the Initial-to-Handshake space discard must not combine probes from two spaces (§8.6). I15 forbids declaring it while only the Initial space exists.

Pacing: spreading the window across time (§18, P12, MM1, MM2)

A window says how much may be in flight; pacing says when each packet leaves. The pacer is a token bucket with capacity_bytes, tokens_bytes, refill_rate_bps and last_refill (§11). It refills at the controller's pacing_rate() against the monotonic clock and is never bypassed (§18.2, P12, P4). Capacity is a small multiple of one packet's worth, and the acceptance bound is a burst of at most 2 x one packet's worth (§18.2, §18.4). Three rules keep it honest:

  1. Rate must stay above zero while cwnd is above zero, or sending deadlocks (I10).
  2. A connection with window headroom but zero tokens for more than one RTT is starved, not merely paced (§18.2).
  3. After an idle gap, rate is re-derived from current window and RTT rather than resuming stale tokens, and the token balance resets to capacity, not accumulated debt (P12, §18.6).

The bandwidth estimator feeds pacing_rate() but never overrides window-based eligibility while Reno or CUBIC is active (P14, §17.2). Capacity must also scale with the 600 ms RTT ceiling, since data in the pipe is rate x RTT (MM2, §4).

The trade-offs — where engineers disagree

Congestion algorithm v1: CUBIC (ADR-24)

Chosen: CUBIC (RFC 8312), because its formula is well specified and deterministic, while BBR's bandwidth-estimation determinism needs groundwork first (ADR-24, §21). Rejected: BBR, Reno-only. When the rejected choice is right: BBR wins on long-fat-network paths such as satellite and high-BDP links once delivery-rate-sample determinism is solved (ADR-24, §34 Alt C).

Packet-metadata storage: a slab arena (ADR-27)

Chosen: a fixed-slot slab over packet number, for cache-local sequential scans under the 65,536-entry-per-connection ceiling (ADR-27, §4). Rejected: HashMap<PacketNumber, SentPacket>. When the rejected choice is right: below about 1,000 connections per node, where flexible eviction and simpler code outweigh cache locality (ADR-27, §34 Alt B). The hashmap's iteration is also unordered, which defeats a descending ACK-range scan (§34 Alt B).

Concurrency: one actor per connection (ADR-08)

Chosen: an actor per connection over a shared executor, isolating connection state and avoiding cross-connection lock contention on the ACK path (ADR-08, P3). Rejected: a global lock-protected connection table. When the rejected choice is right: under about 100 connections, where actor-mailbox overhead exceeds the contention cost (ADR-08); §34 Alt D says "moderate connection counts".

Timer engine: a hierarchical timer wheel (ADR-23)

Chosen: a bucketed wheel with O(1) amortized insert and cancel at 250,000 connections and three timer slots each (ADR-23, C5). Rejected: a binary heap or sorted skip-list. When the rejected choice is right: a binary heap wins below about 1,000 concurrent timers, where wheel bucket overhead is not amortized (ADR-23).

Backpressure: a token-bucket pacer plus window gating (ADR-21)

Chosen: pacing in-process, which keeps congestion state replayable and swappable between algorithms (ADR-21, P2). Rejected: kernel qdisc-level shaping only. When the rejected choice is right: when the deployment owns the whole network fabric and wants kernel-enforced fairness (ADR-21).

Failure policy: fail closed (ADR-17, P8, MM4)

Chosen: any invariant breach terminates the connection, trading one connection's availability for correctness of the fleet (ADR-17, P8). Rejected: fail-open with a log-only warning. When the rejected choice is right: best-effort telemetry collectors where availability outranks correctness (ADR-17). The reason against it at this scale is that a silent corruption bug multiplies into an unattributable fleet-wide incident (MM4).

Roads not taken

Kernel-resident congestion control (§34 Alt A), as in Linux's tcp_congestion_ops, wins where kernel scheduling and NIC integration exist and userspace round trips are the bottleneck. It is rejected because replay cannot be retrofitted onto kernel scheduling and the BSD/macOS secondary targets would break (§34 Alt A, §1.5).

BBR first (§34 Alt C, §35) wins in satellite CDN edges and transcontinental links where a loss-based signal reacts too slowly. It is deferred until delivery-rate-sample determinism is proven in soak testing (§35). The naming is inconsistent: ADR-24 and §2.6 say BBR and Alt C sketches BbrV1, while §35 and §17.2 defer "BBRv2" (ADR-24, §2.6, §34 Alt C, §35, §17.2).

NIC pacing offload waits for a measured scaling ceiling in the software pacer. eBPF telemetry export waits for a replay schema unchanged across two major versions. Multipath scheduling waits for a 90-day single-path stability window at the availability budget (§35).

What must never be false

  • I1: packet numbers strictly rise per space. Insert-time assertion; pn_monotonicity_violation_total (§7).
  • I2: inflight bytes never go negative. Checked after every ACK or loss batch; accounting_violation_total (§7).
  • I3: RTT samples from ambiguous retransmissions are discarded. Marker check; rtt_sample_rejected_total (§7).
  • I4: ACK ranges are strictly descending and disjoint. Order assertion at decode; malformed_ack_total (§7).
  • I5: PTO deadlines move earlier only by explicit recalculation. Deadline-monotonicity assertion; pto_deadline_anomaly_total (§7).
  • I6: cwnd is never below 2 x MSS. Post-reduction floor check; cwnd_floor_hits_total (§7).
  • I7: the ACK-delay-corrected RTT sample is never negative. Bounds check before smoothing; ack_delay_correction_negative_total (§7).
  • I8: exactly one loss timer per space. Wheel-slot assertion; loss_timer_duplicate_total (§7).
  • I9: persistent congestion resets cwnd to the minimum, not half. State check; persistent_congestion_total (§7).
  • I10: pacing rate is above zero while cwnd is above zero. Rate-computation assertion; pacing_rate_zero_total (§7).
  • I11: ECN validation only disables ECN, never invents a CE mark. Transition guard; ecn_validation_failures (§7).
  • I12: replay-log sequence numbers are gap-free per connection. Continuity check; replay_gap_detected_total (§7).
  • I13: send-history occupancy stays under the inflight ceiling. Check on insert; slab_occupancy_ratio (§7).
  • I14: a packet is in exactly one of four states. Exhaustive transition table; delivery_state_conflict_total (§7).
  • I15: no persistent-congestion declaration while a space is Initial-only. Space-kind guard before I9; space-labelled persistent_congestion_total (§7).
  • I16: app-limited bandwidth samples never set a rate ceiling. is_app_limited check; bandwidth_estimate_confidence (§7).

Each has one assertion site in quic-sim, so a fixed-seed run that trips it reproduces from the replay log (§7). §12.1 and §12.2 scope the Phase 0 assertion kernel to I1–I14, while §7 lists sixteen invariants (§12.1, §7).

What breaks in production

(The §23 header names seven columns but each row has eight cells; the text follows the cells, §23.)

  • FM-1: packet-metadata corruption. An assertion for I1, I13 or I14 trips and the connection ends unexpectedly. The cause is a slab-index arithmetic bug or a concurrent mutation that breaks the single-writer assumption (ADR-08). It is detected by the named assertion, recovered by terminating (P8), and diagnosed from the replay log up to the failing assertion (§23).
  • FM-2: replay divergence. Two runs from one seed produce different checksums. Causes are a non-deterministic tie-break in quic-sim or a wall-clock leak (P4). The checksum mismatch detects it, the replay is invalidated from the divergence point, and the fix is manual bisection of the offending commit with differential replay across recent releases (§23).
  • FM-3: pacing collapse. Throughput falls despite window headroom, from token-refill drift (§18.6) or starvation misclassified as pacing. pacing_burst_bytes and pacing_starvation_total show it. Recovery is to reset the pacing epoch and recompute rate from window and smoothed RTT; an operator can force a pacer restart through quic-cli (§23).
  • FM-4: RTT instability. rttvar spikes and PTO oscillates, from ACK-delay abuse (§15.6) or ambiguous samples leaking past I3. Detected through rtt_sample_rejected_total and an rttvar alert. The automatic response is a conservative PTO fallback with wider backoff; an operator may disable the path (§23).
  • FM-5: timer starvation. PTO or loss timers fire late or not at all, from timer-wheel bucket contention at peak connection count. pto_fire_lag_ns exceeding budget detects it. Recovery is a scheduler reset for the shard, then manual rebalance (§23, T8).
  • FM-7: persistent-congestion loop. I9 re-triggers repeatedly without recovery, because idle-induced PTO failures are miscounted (§19.6). A rate anomaly on persistent_congestion_total detects it; the fix is excluding idle PTO failures from the count (§23).
  • FM-8: ECN false-disable cascade. ECN gets switched off fleet-wide when it need not be. The validation threshold is too sensitive, or a counter is shared across connections. Correlated ecn_validation_failures across unrelated connections is the tell; the fix is per-path disable scope (I11) and a higher threshold (§23).
  • FM-9: slab exhaustion. New sends are rejected and slab_occupancy_ratio nears 1.0, because a peer withholds ACKs (T5) or reclamation lags. The caller is backpressured (P7), and an operator can force-close the offending connections (§23).

Threats a reader should know (§22):

  • T1: crafted ACK ranges meant to maximise scan cost near the 32-packet reordering bound. Strict range-order validation before any mutation (I4) rejects the frame.
  • T3: forged CE marks meant to cause false congestion. A validation state machine cross-checks sent against reported ECN, and a failure disables ECN on the path (I11).
  • T5: a peer withholds ACKs so metadata grows without bound. A hard slab ceiling (I13) rejects new sends and pushes back on the caller (P7).
  • T10: ACK-splitting to over-credit growth. Growth is capped at one RTT-worth per batch (§17.6).
  • T13: a peer that always delays ACKs to the maximum to inflate PTO. The max_ack_delay clamp (I7) bounds the inflation.

How it compares

  • quiche chose Rust with userspace token pacing, CUBIC, Reno and BBR, and couples recovery to BoringSSL. That is fine for edge proxies that standardise on one vetted TLS stack (§31).
  • quic-go chose Go-idiomatic APIs and developer ergonomics over allocation-free hot paths, with GC-affected timing. That suits Go-native service meshes where team velocity beats micro-latency (§31).
  • msquic chose a C library with a Windows kernel-mode option and BBR shipped by default. It fits Windows or Azure workloads that want kernel-mode QUIC or default BBR (§31).
  • ngtcp2 chose a minimal, transport-only C library with bring-your-own TLS and caller-driven timers. That fits codebases that already own their TLS integration end to end (§31).
  • lsquic chose QUIC and HTTP/3 as one integrated C unit. That fits a monolithic web-server stack where the two layers are never deployed separately (§31).

None of the five ships built-in determinism or replay, which is the dimension this design adds (§31, P1, P6).

Questions to test yourself

  1. Why doesn't I3's ambiguous-retransmission rule (§7, §15) simply disable RTT sampling entirely during any retransmission episode, and how would that interact with §16's PTO backoff ever converging? Hint: MM3 in §30 and the backoff rule in §16.2.
  2. Why is ECN (§19) advisory rather than authoritative (P13, §11), and what would have to change in the CongestionController trait (§11) if it were promoted? Hint: MM5 in §30 and the hook list in §11.
  3. §13's slab-arena choice (ADR-27) trades hashmap flexibility for cache locality — under what connection-count regime does §34's Alt B make that trade wrong? Hint: the last column of ADR-27 in §9.
  4. Why is persistent congestion (§19, I9) defined to reset cwnd to minimum rather than to ssthresh, and how does that interact with §17's slow-start-exit heuristic on the very next RTT? Hint: §8.4's last transition and §19.4.
  5. I15 (§7) exempts the Initial packet-number space from persistent-congestion declaration — why doesn't the same exemption apply to the Handshake space, given §13's description of both as short-lived bootstrap spaces? Hint: §8.6's boundary conditions and §8.1.

If you only remember three things

Loss recovery is a set of small state machines (packet spaces, RTT, loss, congestion, pacing), and the window, the pacing rate and the inflight count each have exactly one owner (§11, P3, P5). The blueprint trusts no single signal: ambiguous RTT samples are dropped, ECN is advisory, and bandwidth estimates are only observational (I3, P13, P14, MM5). Everything is deterministic and logged, so a production incident can be replayed from a seed, and any broken invariant ends the connection rather than letting wrong state spread (P1, P6, P8).

Words used here

  • Packet number space: one of Initial, Handshake or Application, each with its own numbers and timers.
  • Implied loss: a packet that no range covers while higher ones are acked.
  • RTT: round-trip time, the gap between sending and the acknowledgement.
  • PTO: probe timeout, the deadline after which unacknowledged data triggers a probe.
  • cwnd: congestion window, the byte budget allowed in flight.
  • ECN CE mark: a flag a router sets on a packet to signal congestion before dropping anything.
  • Pacing: spreading a window's worth of sends over time instead of in one burst.
  • Slab arena: a fixed-slot store for per-packet records, chosen for cache locality.
  • Timer wheel: a bucketed-by-deadline structure for scheduling many timers cheaply.
  • Replay log: the gap-free, append-only record of every state change, used to re-run a connection.
