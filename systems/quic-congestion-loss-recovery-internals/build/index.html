⬜ Phase 0 — Repository, Runtime & Correctness Kernel §12

Objectives

Stand up the Cargo workspace, the monotonic-clock/timer-wheel runtime abstraction, the telemetry foundation, the packet-metadata slab allocator interface, and the invariant-assertion kernel (I1–I14) that every later phase plugs into. This phase introduces the constraint that no later phase may bypass (P4, P6): no wall-clock reads, no unlogged state transitions.

Deliverable

A compiling 12-crate workspace with: a metrics endpoint exposing at least runtime_timer_drift_ns; a replay-log writer (quic-replay stub) producing deterministic byte-identical output across two runs from the same seed; a timer wheel that can arm/cancel/fire 100k synthetic timers in a benchmark.

Acceptance

All 12 crates compile under cargo build --workspace. Two replay runs from fixtures/runtime/replay_clock_seed.bin produce byte-identical logs (checksum match). Timer-wheel benchmark sustains ≥ 100,000 arm/cancel operations/sec on a single core. Startup initialization completes in < 500 ms (§4).

Fixtures
  • fixtures/runtime/replay_clock_seed.bin — deterministic replay across two runs from a fixed seed.
  • fixtures/runtime/timer_rollover.json — timer-wheel deadline-overflow edge case.
  • fixtures/runtime/slab_fragmentation.bin — allocator fragmentation regression case.
  • fixtures/runtime/malformed_config.json — malformed workspace config, must fail closed at startup.
Pitfalls
  • Timer drift: manifestation — PTO deadlines fire late under load; root cause — timer-wheel tick granularity coarser than assumed; debugging — compare scheduler wake-delta histogram against runtime_timer_drift_ns; signal — drift > 1 ms sustained; recovery — reduce tick granularity or shard the wheel.
  • Allocator fragmentation: manifestation — cache-miss amplification on slab scans; root cause — variable-size metadata defeats slab-slot reuse; debugging — allocator_fragmentation_ratio trend; recovery — fixed-size slot compaction (ties to I13's occupancy bound).
  • Clock backend swap bugs: manifestation — simulator and production diverge; root cause — fake-clock and real-clock trait impls drift in rounding behavior; debugging — differential test both backends against the same fixture; recovery — single shared rounding helper.

⬜ Phase 1 — Packet Number Spaces & Send History §13

Objectives

Build the packet-tracking foundation: three independent packet-number spaces (Initial, Handshake, Application), the send-history slab, and the DeliveryState transition table (I14) that every later phase reads and mutates.

Deliverable

A packet-metadata engine supporting insertion, ACK-driven updates, loss marking, space discard, and replay serialization, exercised by a benchmark inserting 65,536 packets (§4's inflight ceiling) per connection.

Acceptance

No packet-number duplication across 10M synthetic insertions (I1). ACK-driven state updates are deterministic across replay (checksum match against fixtures/packet-space/overlapping_ack_ranges.json). Inflight-byte accounting nets to zero on connection close in ≥ 99.99% of quic-sim runs (I2). Slab occupancy never exceeds 65,536 entries/connection (I13).

Fixtures
  • fixtures/packet-space/overlapping_ack_ranges.json — malformed overlapping ranges, must reject (I4).
  • fixtures/packet-space/packet_number_wraparound.json — u64 packet-number boundary case.
  • fixtures/packet-space/retransmit_ambiguity.bin — replay case for ambiguous-retransmission marking (feeds I3 in §15).
  • fixtures/packet-space/handshake_discard.bin — regression case for early space discard while packets are still inflight.
Pitfalls
  • Duplicate ACK processing: manifestation — inflight underflow; root cause — idempotency not enforced on mark_packet_acked(); debugging — replay with accounting_violation_total breakpoint; recovery — dedupe by DeliveryState guard (I14).
  • Packet-metadata leaks: manifestation — memory growth over long-lived connections; root cause — slab entries not reclaimed after ACK+drain window; debugging — packet_history_entries trend over connection lifetime; recovery — bounded reclamation sweep tied to largest_acked watermark.
  • Space-discard races: manifestation — Handshake-space packets referenced after discard; root cause — discard not gated on zero-inflight for that space; debugging — assertion on post-discard access; recovery — defer discard until inflight drains.

⬜ Phase 2 — ACK Range Processing Engine §14

Objectives

Implement the ACK-frame decode and implied-loss extraction pipeline that turns wire-level ACK ranges into DeliveryState transitions, per the worked example in §8.5.

Deliverable

An ACK-processing engine that, given a wire-format ACK frame and the current send history, emits a deterministic set of {newly-acked, provisionally-lost, duplicate} packet numbers plus the inflight-byte delta.

Acceptance

Zero false-positive duplicate-ACK detections across 1M synthetic frames. Implied-loss extraction matches RFC 9002 vectors in fixtures/ack-engine/overlapping_ack_ranges.json bit-for-bit. ACK processing latency stays under the §4 budgets (p50 < 5 µs, p99 < 40 µs) on a warm 65,536-entry slab.

Fixtures
  • fixtures/ack-engine/malformed_ack_ranges.bin — non-descending ranges, must reject per I4.
  • fixtures/ack-engine/ack_flood_replay.bin — high-rate duplicate-ACK replay, tests idempotency.
  • fixtures/ack-engine/implied_loss_vector.json — RFC 9002-style implied-loss conformance vector.
  • fixtures/ack-engine/reordered_ranges.bin — reordered-arrival regression case.
Pitfalls
  • ACK compression: manifestation — a burst of coalesced ACKs looks like a sudden large cwnd-worthy event; root cause — network-path buffering delays ACK delivery, then releases many at once; debugging — inter-ACK-arrival histogram; recovery — feed ACK-compression detection into §17's cwnd-growth gating, not the ACK engine itself.
  • Off-by-one range boundaries: manifestation — one extra or missing packet marked acked; root cause — inclusive/exclusive range-boundary confusion; debugging — property test against exhaustive small ranges; recovery — single canonical inclusive-inclusive convention, enforced at decode.
  • ACK-of-never-sent packet number: manifestation — engine dereferences a nonexistent slab slot; root cause — missing existence check before state mutation; debugging — fuzz target ack_parser (fuzz/fuzz_targets/ack_parser.rs); recovery — reject frame, connection error (I4).

⬜ Phase 3 — RTT Estimation & ACK Delay Processing §15

Objectives

Implement the RFC 9002 §5 RTT model: sample validation, ACK-delay correction, min_rtt/smoothed_rtt/rttvar maintenance, feeding PTO computation in §16.

Deliverable

A fully operational RTT subsystem: given a validated ACK-eliciting packet's send time and the peer's ACK-delay field, produces an updated smoothed_rtt/rttvar/min_rtt triple and the current pto_base() duration.

Acceptance

RFC 9002 §5 formulas validated bit-for-bit against fixtures/rtt/delayed_ack_trace.bin. PTO base duration stays within 1 µs of the reference computation across 100k synthetic samples. Zero negative corrected-RTT values reach the smoothing step (I7). Replay of the same sample sequence twice yields identical smoothed_rtt (P1).

Fixtures
  • fixtures/rtt/delayed_ack_trace.bin — delayed-ACK replay validating ACK-delay correction.
  • fixtures/rtt/ack_delay_overflow.json — malformed oversized ack_delay field, must clamp (I7).
  • fixtures/rtt/rtt_reordering_trace.bin — RTT sampling under 32-packet reordering.
  • fixtures/rtt/zero_rtt_sample.bin — degenerate same-tick send/ack regression case.
Pitfalls
  • ACK-delay abuse: manifestation — perceived RTT inflates, PTO grows unnecessarily conservative; root cause — malicious or buggy peer reports oversized ack_delay; debugging — ack_delay_correction_negative_total and delay-distribution dashboard; recovery — clamp to max_ack_delay transport parameter (I7).
  • Ambiguous RTT samples: manifestation — RTT estimate oscillates wildly; root cause — retransmitted packets' ACKs credited to the wrong send time (Karn's algorithm violation); debugging — cross-check against retransmit_ambiguity.bin (§13); recovery — reject sample outright (I3), never approximate.
  • Fixed-point rounding drift: manifestation — two replay runs diverge by 1 unit after many updates; root cause — integer-division truncation direction not pinned; debugging — differential replay test; recovery — single documented rounding rule, applied uniformly.

⬜ Phase 4 — Loss Detection & PTO Engine §16

Objectives

Implement RFC 9002's normative loss-recovery core: packet-threshold and time-threshold loss detection, PTO scheduling and exponential backoff, persistent-congestion detection surfaced for §19 to act on.

Deliverable

A recovery engine that, given the current send history and RTT state, declares loss correctly against RFC 9002 vectors and schedules/backs off PTO deterministically.

Acceptance

100% pass rate on fixtures/loss/tail_loss_probe.bin and fixtures/loss/persistent_congestion.bin RFC vectors. PTO scheduling latency < 50 µs end to end (§4). Persistent congestion detected within one connection's worth of consecutive PTO failures matching the RFC 9002 persistent-congestion duration formula, zero false positives across 10k quic-sim runs.

Fixtures
  • fixtures/loss/tail_loss_probe.bin — end-of-burst loss requiring a PTO probe, not a threshold declaration.
  • fixtures/loss/persistent_congestion.bin — sustained-collapse vector triggering I9.
  • fixtures/loss/reorder_threshold.bin — reordering below kPacketThreshold, must not declare loss.
  • fixtures/loss/pto_backoff_overflow.json — exponential-backoff cap regression case.
Pitfalls
  • Timer coalescing: manifestation — PTO fires later than scheduled under scheduler load; root cause — timer-wheel tick coalescing batches nearby deadlines; debugging — compare scheduled vs. actual fire time via pto_fire_lag_ns; recovery — tighten wheel granularity for the loss-timer bucket specifically.
  • Spurious loss under aggressive thresholds: manifestation — unnecessary retransmissions inflate traffic; root cause — kPacketThreshold set too low for the §4 32-packet reordering assumption; debugging — spurious_loss_total correlated with reorder-heavy quic-sim traces; recovery — hold kPacketThreshold at the RFC-specified 3, do not tune down.
  • PTO storms during idle periods: manifestation — repeated PTO firing with nothing inflight; root cause — timer not disarmed when inflight drops to zero; debugging — pto_count spike with zero concurrent inflight_bytes; recovery — disarm loss timer when no ack-eliciting packet is outstanding (I8).

⬜ Phase 5 — Congestion Control Framework §17

Objectives

Introduce the pluggable CongestionController trait (§11, P11) and ship two conformant implementations — Reno and CUBIC — plus a delivery-rate/bandwidth-estimation module that anticipates a future BBR implementation without committing to it yet.

Deliverable

An operational congestion-control abstraction: either Reno or CUBIC selectable at connection start, both driving cwnd()/pacing_rate()/state() correctly under quic-sim fault injection.

Acceptance

Fairness validated: two CUBIC flows sharing a bottleneck in fixtures/congestion/fairness_competition.sim converge to within 10% of equal share over 60 simulated seconds. cwnd never observed negative across 1M synthetic ACK/loss events (I6). Recovery-state transitions are deterministic and replay-identical (fixtures/congestion/cubic_growth_trace.bin checksum match).

Fixtures
  • fixtures/congestion/cubic_growth_trace.bin — RFC 8312 growth-function conformance vector.
  • fixtures/congestion/reno_loss_trace.bin — AIMD multiplicative-decrease regression case.
  • fixtures/congestion/fairness_competition.sim — two-flow bottleneck-sharing simulation.
  • fixtures/congestion/idle_restart.bin — cwnd behavior after a send-idle gap exceeding one RTT.
Pitfalls
  • ACK compression inflating cwnd: manifestation — cwnd grows faster than the path can sustain; root cause — coalesced ACK bursts (§14.6) look like many independent growth events; debugging — correlate cwnd_bytes growth rate against inter-ACK-arrival histogram; recovery — cap per-ACK-batch cwnd growth to one RTT-worth, not per-ACK.
  • Recovery-state oscillation: manifestation — repeated Recovery↔CongestionAvoidance flapping destabilizes throughput; root cause — new loss detected within the same RTT as entering Recovery is treated as a fresh event; debugging — trace congestion_events_total timestamps against RTT boundaries; recovery — RFC 9002-style single-Recovery-per-RTT gating.
  • cwnd underflow near minimum: manifestation — send budget hits zero unexpectedly; root cause — multiplicative decrease applied without the I6 floor check; debugging — cwnd_floor_hits_total; recovery — clamp before, not after, applying the decrease.
  • Idle-restart overshoot: manifestation — a connection resuming after idle sends a burst exceeding path capacity; root cause — cwnd retained at pre-idle value despite stale RTT/pacing state; debugging — fixtures/congestion/idle_restart.bin replay; recovery — reset cwnd toward slow-start-equivalent on idle restart beyond one RTT.

⬜ Phase 6 — Pacing Engine §18

Objectives

Implement the token-bucket pacing scheduler (P12) that turns a congestion controller's pacing_rate() into bounded, burst-limited transmission timing.

Deliverable

A stable pacing subsystem: given a pacing_rate() and a send request, either grants immediate transmission, defers to a computed wake deadline, or reports starvation — all replay-deterministic.

Acceptance

Pacing bursts bounded to ≤ 2× one packet's worth of tokens (fixtures/pacing/pacing_burst.sim). Zero pacing-starvation events across 10k quic-sim runs with cwnd headroom present (I10). Throughput stable within 5% under RTT variance of ±50% (fixtures/pacing/pacing_jitter.bin).

Fixtures
  • fixtures/pacing/pacing_burst.sim — burst-limiter conformance under a sudden cwnd increase.
  • fixtures/pacing/pacing_jitter.bin — throughput stability under RTT variance.
  • fixtures/pacing/burst_amplification.trace — bottleneck-queue amplification regression case.
  • fixtures/pacing/idle_restart_pacing.bin — token-bucket behavior after an idle gap.
Pitfalls
  • Scheduler jitter causing pacing bursts: manifestation — packets sent in clumps despite a smooth target rate; root cause — timer-wheel wake delay accumulates unspent tokens; debugging — pacing_debt_ns histogram correlated with runtime_timer_drift_ns (§12); recovery — cap accumulated token carry-over, don't let debt compound indefinitely.
  • Token-refill drift: manifestation — pacing rate silently diverges from pacing_rate(); root cause — improper refill-interval rounding compounds over many refills; debugging — differential test refill logic against a reference float computation off the hot path; recovery — single canonical fixed-point refill formula (ties to §17.7's determinism concern).
  • Idle-restart pacing overshoot: manifestation — a burst on resume after silence; root cause — stale token balance retained across the idle gap; debugging — fixtures/pacing/idle_restart_pacing.bin; recovery — reset token balance to capacity, not accumulated debt, on idle restart.
  • Starvation misclassified as healthy pacing: manifestation — a connection appears "paced" but is actually stalled; root cause — starvation detector threshold set too loose; debugging — cross-check pacing_queue_depth growth against zero-token duration; recovery — tighten starvation threshold to one RTT (I10).

⬜ Phase 7 — ECN Validation & Persistent Congestion §19

Objectives

Implement ECN codepoint validation (RFC 3168) as an advisory signal (P13) into the congestion path, and finish persistent-congestion handling (I9) with path-degradation telemetry.

Deliverable

An ECN-aware recovery engine that processes CE marks correctly when ECN is viable, safely disables ECN when a middlebox is mangling it, and detects persistent congestion without false positives.

Acceptance

CE marks correctly attributed to the packet-number space and ACK batch that reported them in fixtures/ecn/ce_mark_storm.sim, zero mis-attribution across 100k events. False ECN (fixtures/ecn/ecn_false_positive.bin) disabled within 3 validation failures, connection continues without ECN (I11). Persistent congestion (I9) detected with zero false positives across 10k quic-sim runs and cwnd reset to minimum_cwnd exactly, not a partial reduction.

Fixtures
  • fixtures/ecn/ecn_false_positive.bin — middlebox ECN-mangling regression case, must disable safely.
  • fixtures/ecn/ce_mark_storm.sim — high-rate CE-mark burst, tests counter synchronization.
  • fixtures/ecn/partial_ecn_deployment.bin — mixed ECN-capable/incapable path segments.
  • fixtures/ecn/persistent_congestion_boundary.bin — I9 duration-formula boundary case.
Pitfalls
  • Broken middleboxes mangling ECN: manifestation — false congestion signaled on an otherwise healthy path; root cause — a middlebox remarks or strips ECN codepoints; debugging — compare self-reported sent-ECN codepoints against peer-reported received counts; recovery — validation-failure counter trips ECN disable for that path (I11), never for the fleet.
  • CE-mark double-counting: manifestation — one physical congestion event triggers two on_ecn_ce() calls; root cause — CE counter updated both on ACK-range decode and on a separate ECN-summary frame; debugging — cross-reference ecn_ce_total against ACK-batch count; recovery — attribute CE marks exactly once per ACK batch.
  • Persistent-congestion false positive on a genuinely idle connection: manifestation — I9 triggers with no real congestion; root cause — PTO-failure counting doesn't exclude idle-induced probe gaps; debugging — cross-check pto_count against concurrent inflight_bytes; recovery — only count PTO failures while data was actually inflight.

⬜ Phase 8 — Deterministic Simulator, Fault Injection & Replay Tooling §20

Objectives

Build the deterministic network simulator (quic-sim) driving every prior phase's real API under injected faults, and the replay pipeline (quic-replay) turning production telemetry into re-executable traces (P1, P6).

Deliverable

A fully replayable transport simulator producing deterministic, reproducible congestion traces, and a replay tool that re-executes any production connection's recorded events with checksum-verified fidelity.

Acceptance

Deterministic outputs: 1,000 repeated runs of fixtures/sim/cellular_network.sim with the same seed produce byte-identical replay logs (I12, P1). Reproducible congestion traces across the reference fixtures below with zero divergence. Replay throughput exceeds 1,000,000 events/sec (§4).

Fixtures
  • fixtures/sim/cellular_network.sim — variable-RTT, bursty-loss mobile-network profile.
  • fixtures/sim/satellite_rtt.sim — high-RTT (600 ms ceiling, §4) GEO-satellite profile.
  • fixtures/sim/reorder_heavy.sim — reordering at the §4 32-packet boundary.
  • fixtures/sim/ack_blackhole.sim — total ACK loss for a bounded interval, tests PTO escalation.
Pitfalls
  • Non-deterministic scheduling in the simulator itself: manifestation — two runs from the same seed diverge; root cause — the simulator's own event-queue ordering uses a non-stable tie-break (e.g. hash-map iteration order); debugging — differential replay across repeated runs; recovery — deterministic tie-break by (timestamp, insertion sequence).
  • Simulation-clock drift from the production clock abstraction: manifestation — simulated PTO timing diverges from what §12's real-clock backend would produce; root cause — the fake-clock backend rounds differently than the real one; debugging — shared rounding-helper differential test (ties to §15.6); recovery — one clock-math implementation, two backends.
  • Replay divergence from a schema change: manifestation — an old replay log fails to re-execute after a code change; root cause — a ReplayEvent field changed meaning without a schema-major bump; debugging — replay-log version check at load time; recovery — reject mismatched-schema replay explicitly rather than misinterpreting it (§25).

⬜ Phase 9 — Conformance Harness, Operator CLI & Production Hardening §21

Objectives

Ship the RFC 9002 conformance runner (quic-conformance), the operator CLI (quic-cli), and harden the system for production rollout: soak testing, fuzz-corpus maturity, and delivery-rate-based bandwidth-estimation groundwork ahead of a future BBR phase.

Deliverable

A CI-gating conformance suite covering every phase's fixtures, an operator CLI capable of diagnosing a live or replayed connection without reading source code, and a soak-tested build ready for staged production rollout.

Acceptance

100% of fixtures/** (≥ 40 named fixtures across Phases 0–8) pass under quic-conformance. quic-cli replay diff correctly highlights the first divergent event between two logs in fixtures/cli/replay_diff_case.bin. 72-hour soak run sustains the §4 availability budget (99.99% crash-free) with zero unbounded memory growth (P7).

Fixtures
  • fixtures/cli/replay_diff_case.bin — two near-identical replay logs with one injected divergence.
  • fixtures/conformance/full_suite_manifest.json — the aggregated fixture manifest quic-conformance executes.
  • fixtures/soak/72h_profile.sim — long-duration mixed-fault soak profile.
  • fixtures/bandwidth/delivery_rate_trace.bin — delivery-rate-sampling regression case for the BBR-readiness interface.
Pitfalls
  • Conformance suite drift from fixture rot: manifestation — a fixture no longer represents the RFC vector it was named for after an unrelated refactor; root cause — fixtures are edited ad hoc without re-validating against RFC 9002 text; debugging — periodic manual re-audit of fixtures/loss/ and fixtures/congestion/ against RFC 9002; recovery — fixture changes require a linked ADR-12-style justification.
  • CLI masking real state via stale cache: manifestation — quic-cli connection inspect shows outdated cwnd/RTT; root cause — CLI reads a cached metrics snapshot instead of live state; debugging — compare CLI output against direct quic-telemetry scrape; recovery — CLI always requests a fresh snapshot, never trusts a cache older than one telemetry interval.
  • Soak-test memory growth masked by GC-like behavior: not applicable in Rust (no GC), but slab-reclamation lag (§13.6) can look like a leak; debugging — packet_history_entries trend over the 72-hour window; recovery — verify reclamation sweep cadence matches connection churn rate.
