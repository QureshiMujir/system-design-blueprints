In one paragraph

A distributed cache keeps hot data in the memory of many machines so the database behind it sees only the misses. This design is a sharded in-memory key-value cluster in the memcached / Redis Cluster lineage (§1): the client hashes each key onto one of 16,384 slots and talks straight to the owning node (ADR-04); each slot has a primary and async-fed replicas (ADR-08); a separate Raft-backed coordinator is the sole authority on slot ownership (ADR-07, I1); slots move between nodes under live traffic (ADR-11); coherency policies and hot-key defences complete it (§1). Its defining property: the data path never calls the cluster path synchronously (§4). Platform teams run it in front of a primary datastore (§1).

The problem, concretely

The cache sits in front of a primary datastore (§1). One node holds a 64 GiB engine heap — at ≈ 1 KiB per entry plus 48 bytes of overhead, ≈ 60.2 million keys (§4, §34 C1) — so a larger working set must be spread across nodes, and the spreading rule matters: the first lesson is how consistent hashing behaves under node churn, keeping key movement small (§2, MM7). Now a node dies. If the survivors decide by gossip who owns its slots, a split vote during a partition can leave two nodes both believing they own a slot — split brain (§36 Alt 2, MM2). Now hot keys expire. The motivating workload is 50,000 hot keys hammered by 10,000 clients each, with a backing store that serves at most 5,000 misses per second (§21.1); in the blueprint's words, losing a cache shard is "a thundering-herd incident the entire user base notices within seconds" (§2). Then you must rebalance, and skipping the online protocol "reintroduces the maintenance-window outage this design exists to avoid" (P4, ADR-11). One more trap: one coherency-policy choice rewrites the durability contract (§2, MM5). Each trap has its own answer below: §13, §17, §18, §19, §20 with its WAL rule (I7), and §21.

How it works, end to end

The §3 diagram, lightly trimmed:

Follow one GET from an application:

  1. Client library (dcache-client). HotKeyDetector, a count-min sketch, tags the key Cold/Warm/Hot; a Hot read is answered from the client's ephemeral local_cache when possible (§21.2, ADR-14), and concurrent identical (key, op) requests collapse into one upstream call through SingleFlight::run (§21.2, ADR-15).
  2. Router (dcache-router::Router). SlotId::from_key computes CRC16(hash_tag(key) or key) mod 16384 (§11, I11); route() reads the local ArcSwap<SlotTable> snapshot — an O(1) index into SlotTable.primary (§13.2, §13.7) — and returns ToPrimary, or Importing if the slot is mid-migration (§13.2).
  3. Wire layer (dcache-wire-memcached / -resp3 / -grpc). Every node listens on Memcached binary :11211, RESP3 :6379 and gRPC :50051 at once over one key namespace; the magic byte or first frame token picks the protocol per connection (§3, P5). Each codec decodes to one shared Operation and encodes one Response (§11, §14.2).
  4. Dispatch (dcache-server). Recompute the slot, compare with table.primary[slot]: serve if owned, else answer Response::Moved, which the client follows after refreshing its table (§15.2, I6) — at most 5 redirects (§15.6).
  5. Coherency engine (dcache-coherency). A miss or a write goes through the namespace's policy, write-through by default (§3, §20, ADR-12).
  6. Per-node engine (dcache-engine). Storage and eviction are delegated to the LRU-LFU-Cache crate behind the Engine trait (§11, P6); one shared-nothing event loop per shard worker (ADR-03).

A SET takes the same path to the primary, which applies it locally, advances seq, appends a ReplicationRecord to a ring buffer, fans it out to the replicas, then acknowledges (§19.2); under write-through the ack also waits for the backing store (§20.2).

Everything below the trust boundary is out of band. Gossip (dcache-membership, rank 72) says only whether nodes are alive (I5); the Raft coordinator (dcache-coordinator, rank 39) is the sole writer of the SlotTable (I1), and every data node keeps a long-lived WatchTopology stream open, swapping in each new table atomically (§17.2, P3, I2). The rebalancer, dashboard and admin CLI are the only sanctioned callers of its ProposeEvent RPC (§3).

The core ideas

Slots and hash tags: where a key lives (§11, §13)

A key's slot is CRC16(hash_tag(key) or key) mod 16384 (§11, I11), bit-identical to Redis Cluster's keyHashSlot() (§13.3) using the CRC16/CCITT-FALSE polynomial 0x1021 — the wrong polynomial fails silently if you only test with your own client (§13.6). The hash tag is the first {...} substring, and it pins a key's slot so related keys can be co-located (§13.2, §38). {a}{b} hashes on a; an empty {} or an unterminated { means "no tag" (§13.2, §13.6, §13.8).

Ownership moves one slot at a time, 1/16,384 of a node's keys (§34 C8); the count is a compile-time constant and changing it means a new cluster (ADR-04, I13, P11). A slot is a unit of ownership, not of locality or locking (MM1). Jump, rendezvous and ketama sit behind one HashStrategy trait (ADR-05); jump hash is biased below 16 shards, so the slot table is the production default (§13.6). Consistent hashing minimises movement, not variance — weights and virtual nodes are still needed for balance (MM7).

The epoch and the one-writer rule (§11, §17)

The committed SlotTable is {epoch, primary[16384], replicas, migrating} (§11). Only the coordinator writes it, one Raft-committed ClusterEvent at a time — NodeJoined, NodeFailed, SlotMoved, Failover, EpochAdvanced (§11, §17.2, I1). The epoch is a logical clock for authority, not for time (MM8): a node applies a new table only if epoch_new > epoch_old (I2), so one that has seen Epoch(n+5) must never accept a write tagged Epoch(n) (§17.6). Gossip carries liveness metadata capped at 1 KiB per round, never slot ownership (§16.2, I5): gossip answers "is it alive", consensus "who owns it" (MM2).

Failover (§16.2, §17.2): a NodeFailed sustained past a 30 s grace period starts it; the coordinator promotes the lowest-lag replica, demotes the failed primary (it rejoins as a replica), updates the table and advances the epoch. Two timings sit side by side: failover starts only after that 30 s grace (§16.2), yet M7 budgets ≤ 30 s from primary kill to completed failover (§30). Coordinator re-election is budgeted at ≤ 5 s (M8).

Online migration: four phases, one owner at every instant (§8, §18)

Moving a slot from source to destination is a state machine that never skips a phase (I4). The transition table (§8):

Phase Source reads Dest reads Source writes Dest writes Next, when
Importing serves ASK source serves accepted, stored locally dest confirms import-ready
DoubleWrite serves serves replicated to dest replicated to source bulk copy completes
Catchup brief read-only serves blocked (drain) serves in-flight writes drained
Cutover MOVED dest serves, authoritative rejected serves coordinator commits SlotMoved

During DoubleWrite a daemon scans the source with scan_slot — which must be snapshot-isolated or it silently drops or duplicates keys (I10, §18.6) — and copies keys across, skipping any whose destination CAS is already higher (§18.2, I3). The two redirects are not interchangeable: ASK means "retry this one request over there, change nothing"; MOVED means "update your table" (I6, §38). In §8's worked trace, a GET to the destination during DoubleWrite is served if the key was already copied; otherwise the destination answers ASK source and the client retries once there with an ASKING prefix.

The bug zone is the start of the window: a write that reaches the source after the destination was added but before the source knows about the migration is lost, so the destination must know before double-writing starts (§18.6). Copy is throttled to 50 MiB/s per migration (§18.7); one slot of a full node is ≈ 3,672 keys ≈ 3.6 MiB ≈ 72 ms before the drain (§34 C8). A rollback mid-DoubleWrite returns the slot to Importing on the source and the destination evicts (§18.2).

Async replication, with lag as a queue depth (§8, §19)

A replication record is seq | epoch | op (Set|Delete|Migrate) | timestamp | HMAC (§8). Replicas apply in strict order — incoming.seq == applied_seq + 1 — and a record that is out of order or fails its HMAC is rejected, never applied speculatively (I8, §8). Each replica reports its applied seq; the primary computes lag = current_seq − applied_seq (§19.2). Lag is a queue depth, not a clock, so clock skew cannot fake freshness (MM4, §19.6). Yet the read threshold is a time — min_lag_ms (P8), min_freshness: Duration (§11) — and M6 and the dashboard state lag in milliseconds (§19.4). A lag-aware read filters replicas by lag, picks one by round-robin, weight or P2C, and falls back to the primary when none qualifies (§11, §19.2, §19.8). A replica too far behind the bounded ring buffer is forced into a snapshot rebase (§19.6). Acknowledging before replicas confirm means a primary crash can lose acknowledged writes — the documented trade-off, not a bug (ADR-08, FM-6, §19.6).

Coherency policies are durability contracts (§20)

The policy decides when the backing store hears about a write (§20.2):

Policy On write On read Client acknowledged when
Write-through (default) cache + synchronous backing-store write normal both succeeded (ADR-12)
Write-back cache now; backing store later, journaled in the WAL normal immediately (I7)
Write-around bypasses the cache entirely a later read populates lazily not stated
Refresh-ahead — a read near TTL triggers an async refresh; current value served —
Read-through — a miss is filled synchronously from the backing store, stored, returned —

Write-through is the only policy correct without a write-ahead log (WAL), which is why it is the default (ADR-12); write-back without a WAL "is not write-back — it is 'we lose your data on cache restart'", so the server refuses to start with wal: None (I7, §20.6). Policy is chosen per namespace in the coordinator's metadata, and cached data is not migrated when it changes (§20.2). A coherency policy is a durability contract wearing a performance costume (MM5).

Hot keys and stampedes: four layers (§21)

A hot key draws far more traffic than its shard can serve; a thundering herd is many clients recomputing the same value after one miss or expiry (§38). The stack (§2, §21.2):

  1. Detect with a client-side count-min sketch (ADR-14). It is approximate; false positives (cold keys flagged hot) are cheap, false negatives are not, which is how cms_width/cms_depth are tuned (§21.6).
  2. Coalesce with single-flight: concurrent same-(key, op) callers share one upstream future (ADR-15, §11). It only works inside one process — two co-located client processes still send two requests (§21.6, §37).
  3. Refresh early with XFetch: refresh when now − (Δcompute × β × ln U) ≥ expires_at, with U ~ Uniform(0,1), Δcompute the last recompute duration and β a per-namespace knob (§11, ADR-13). U is sampled once per read near expiry, so each read gets a random lead that scales with Δcompute × β, and refreshes spread across the TTL window instead of bunching at expiry (§11, §21.2). β is the most consequential knob: 1.0 is the paper's default, and cache workloads benefit from β in [0.5, 1.5] (§21.6). XFetch needs a finite TTL (§21.8).
  4. Fan out with shadow replicas: ephemeral, non-promotable, read-only copies the coordinator places from hot-key telemetry (§21.2). The fix for a hot key is fan-out, never a bigger node (MM6).

The trade-offs — where engineers disagree

Who owns the slot map: a separate Raft quorum (ADR-07)

Chosen: a Raft coordinator in its own 3-or-5-node quorum, consuming the Raft-Consensus crate; consensus stays off the hot path and a coordinator failure does not compound with a data-plane failure (ADR-07, P3). Rejected: Raft embedded in every data node; a single non-replicated coordinator. When the rejected choice is right: embedding Raft per node wins for a small (3–5 node) fixed cluster not worth a second quorum — etcd's own bet (ADR-07). §36 Alt 3 gives the same alternative a wider regime, 3–7 nodes (§36 Alt 3). One of the four decisions §9 calls load-bearing.

Slot count: 16,384, fixed for the cluster's life (ADR-04)

Chosen: 16,384 slots, the Redis Cluster convention — the right granularity for a 1,000-shard fleet (ADR-04, I13). Rejected: 1,024 slots; no slot indirection at all. When the rejected choice is right: fewer slots win for small fixed clusters (≤ 8 nodes) where gossip payload size matters more than migration granularity (ADR-04).

Replication: asynchronous, primary to N replicas (ADR-08)

Chosen: the primary acknowledges after local apply; cache workloads tolerate losing the last few acknowledged writes in exchange for steady-state latency (ADR-08, M6). Rejected: synchronous quorum replication. When the rejected choice is right: when cached values cannot be cheaply recomputed — idempotency tokens, distributed locks (ADR-08).

Resharding: a double-write window plus ASK/MOVED (ADR-11)

Chosen: the four-phase online protocol, mirroring Redis Cluster exactly and therefore wire-compatible with its client ecosystem (ADR-11). Rejected: stop-the-world migration; two-phase commit per key. When the rejected choice is right: stop-the-world wins for a cache that already tolerates maintenance windows — batch-only, no live traffic (ADR-11).

Default coherency policy: write-through (ADR-12)

Chosen: write-through, the only policy correct without a WAL, so a namespace nobody provisioned is still safe (ADR-12, I7). Rejected: write-back as the default. When the rejected choice is right: once a namespace has provisioned the WAL and is write-latency-sensitive (ADR-12).

Roads not taken (§36)

Proxy-routed topology — a stateless proxy tier hashes on the client's behalf (Twemproxy, mcrouter). Wins for many small, polyglot client fleets that should never see topology; rejected because it hides topology from the application (P1), adds a hop, and makes the proxy tier its own capacity and single-point-of-failure problem (§36 Alt 1).

Gossip-only topology — ownership derived from gossip-converged state, no Raft (Redis Cluster). Wins for small-to-medium fixed clusters (tens of nodes) where a second quorum is not worth operating; rejected because a split vote during a partition can leave two nodes both believing they own a slot, which I1 and I2 forbid (§36 Alt 2).

Embedded consensus per node — every data node is also a Raft voter (etcd, CockroachDB). Wins for 3–7 node clusters that want one binary; rejected because quorum latency degrades as the data plane grows, violating P3 beyond roughly 7 nodes against a 1,000-shard target (§36 Alt 3, §31).

Deferred features — multi-master, snapshot persistence, Lua, geo-replication, tiered storage and more wait on named triggers, e.g. a working set beyond affordable RAM (§37).

What must never be false

  • I1 — exactly one primary owns any slot at any epoch; checked on every ProposeEvent (slot_ownership_conflicts_total).
  • I2 — the topology epoch only goes up on each node; epoch_new > epoch_old asserted on apply (epoch_rollback_rejected_total).
  • I3 — a key's CAS value only goes up across replicas; the replica compares the incoming CAS before applying (cas_monotonicity_violation_total).
  • I4 — migration passes Importing → DoubleWrite → Catchup → Cutover without skipping; the coordinator checks an allowed-next-phase table (migration_phase_transition_total).
  • I5 — gossip informs liveness only, never ownership; structural, plus an integration test.
  • I6 — a client persists MOVED, never ASK; conformance cases, client_redirect_total{kind}.
  • I7 — write-back requires a WAL; startup refuses wal: None (coherency_startup_refused).
  • I8 — replication records apply in strict seq order per shard; the replica asserts incoming.seq == applied_seq + 1 (replication_out_of_order_total).
  • I9 — an ACL cache invalidates within one gossip interval; acl_cache_staleness_seconds alerts.
  • I10 — scan_slot is snapshot-isolated under concurrent writes; migration scenarios assert no duplicated or missing key (migration_scan_anomaly_total).
  • I11 — hash-tag extraction is total and deterministic; CRC16 parity fixtures, release-blocking.
  • I12 — the audit log's HMAC chain survives rotation; verified daily (audit_chain_break_alert).
  • I13 — the slot count is 16,384 for the cluster's lifetime; a compile-time constant.
  • I14 — gossip incarnation numbers only rise; refutation beats stale suspicion (rank-72 suite).

Each has an assert_i1 … assert_i14 in the seeded chaos simulator, so any failure replays byte-for-byte from its seed (§7).

What breaks in production

  • FM-1 — a primary crashes. Process kill, OOM or host failure; seen as gossip NodeFailed plus coordinator confirmation; failover to the lowest-lag replica (§17, M7).
  • FM-2 — a redirect storm. A client treats ASK as MOVED or the reverse (I6); client_redirect_total spikes; the server-side 5-hop breaker stops the loop and the client gets fixed (§15.6).
  • FM-3 — replication lag runs away. A slow replica, a saturated network or a long pause; replication_lag_ms crosses the M6 threshold; no auto-recovery — an operator forces a snapshot rebase (§19.6).
  • FM-5 — a migration stalls. Destination unresponsive or a partition mid-DoubleWrite; a stalled-progress metric fires; the daemon restarts from the last committed phase, or the operator rolls back (§18.9).
  • FM-6 — acknowledged writes are lost when a primary fails. The async loss window (ADR-08); detected by post-failover write-count reconciliation; no auto-recovery — the manual step is to verify that write-back+WAL was the intended configuration.
  • FM-9 — a hot key overloads a shard. The hot-key log crosses its threshold; shadow replicas are placed automatically (§21); the manual step is application-level key sharding.
  • FM-12 — slot-table split-brain. A coordinator or Raft bug allows a dual commit (I1); slot_ownership_conflicts_total; reject the event, halt writes to the slot, inspect the log.

Threats a reader should know (§24): T-1 malformed frames — bounded reads, length-checked allocation, fuzz targets, close the connection; T-3 a forged replication record — an HMAC under the cluster trust-bundle key, and a failure triggers a rebase; T-5 hot-key amplification — a per-API-key rate limit, single-flight and shadow replicas; T-6 out-of-memory via an oversized value — the 1 MiB per-namespace ceiling is enforced before allocation; T-11 a revoked principal kept alive by a stale ACL cache — bounded by I9, and a check that cannot resolve denies (P13). The four trust boundaries are the wire, the mTLS cluster interior, the CRC+HMAC replication stream and the admin surface (§24).

How it compares

  • Memcached with Twemproxy/mcrouter routes in a thin proxy or client hash ring with no server-side cluster awareness and no native replication (§33). It wins for "many independent tiny caches, no cluster ops overhead" (§33).
  • Redis Cluster is the closest relative — client-side hash slots, MOVED/ASK, online reshard — but trusts gossip for cluster metadata with no strong consensus layer (§33). It wins when skipping a second quorum beats a small split-brain-election risk (§33, §36 Alt 2).
  • Couchbase Server uses a server-provided vBucket map, a single elected orchestrator and first-class disk persistence; it wins when the system is really a document database that happens to cache (§33).
  • Aerospike pairs a Paxos-backed, strongly consistent cluster map with native SSD-tier storage; it wins for a real-time operational database with a strict SLA and a working set too large for RAM (§33).
  • This design pays for two clusters to get a linearizable ownership guarantee (I1, I2); it wins where a split-brain double-write is a compliance incident (§33). Its routing and redirection design generalizes to Distributed-KV-Store and Distributed-Lock-Service (§2).

If you only remember three things

The client is the router: a key's slot is a fixed function of the key, the slot table is a local snapshot, and the data path never waits on the cluster (P1, P3, §4). Liveness and ownership are different questions with different answers — gossip for the first, a separate Raft quorum for the second, and an epoch that only moves forward (MM2, MM8, I1, I2). Everything else is a contract with a price attached: ASK versus MOVED is the migration contract (I6), async replication is a bounded-loss contract (ADR-08, FM-6), and a coherency policy is a durability contract — write-back without a WAL is not allowed to start (I7, MM5).

Words used here

  • Slot — one of 16,384 fixed partitions of the key space; the unit of ownership (ADR-04, I13).
  • SlotTable — the committed map of slots to primaries, replicas and in-flight migrations (§11).
  • Epoch — the monotonic version number of the topology; a logical clock for authority (I2, MM8).
  • Coordinator — the Raft-backed process that owns topology, slot ownership and the epoch (§17).
  • Gossip — the SWIM/Lifeguard liveness protocol; never a source of ownership (§16, I5).
  • ASK — "this slot is migrating; retry this one request over there, keep your table" (I6).
  • MOVED — "this slot lives elsewhere; update your table and retry" (I6).
  • DoubleWrite — the migration phase in which source and destination both accept writes (§18).
  • Replication lag — the sequence-number gap between a primary and a replica (MM4).
  • WAL — the write-ahead log that write-back needs before it may start (I7).
  • Single-flight — concurrent identical requests share one upstream call (§21).
  • XFetch — probabilistic early expiration: refresh a little before TTL, at random (§11, ADR-13).
