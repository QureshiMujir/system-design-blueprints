Project Name: Distributed Cache

1. Goal & Scope

Definition. Distributed Cache (project 188) is a horizontally sharded, in-memory key-value cache cluster in the memcached / Redis-Cluster lineage: client-side consistent-hash routing onto a 16,384-slot table, primary/replica sharding with asynchronous replication, pluggable per-node eviction (LRU/LFU/TTL, delegated to the LRU-LFU-Cache crate, project rank 59), gossip-based membership (SWIM/Lifeguard, delegated to Gossip-Protocol, rank 72), a Raft-backed cluster coordinator (delegated to Raft-Consensus, rank 39) owning slot ownership and the topology epoch, an online (zero-downtime) slot-migration protocol mirroring Redis Cluster's ASK/MOVED redirection, five cache-coherency policies (write-through, write-back, write-around, refresh-ahead, read-through), and a hot-key / thundering-herd mitigation suite (client-side detection, request coalescing / single-flight, probabilistic early expiration).

Phase-0 deliverable — numbered modules:

  1. dcache-types — shared identifiers and wire-neutral domain types (§11).
  2. dcache-hash — consistent-hashing strategies (jump, rendezvous, ketama) + the 16,384-slot table (§13 Phase 1).
  3. dcache-wire-memcached — Memcached binary protocol codec (§14 Phase 2).
  4. dcache-wire-resp3 — Redis RESP3 codec (§14 Phase 2).
  5. dcache-wire-grpc — native gRPC service (§14 Phase 2).
  6. dcache-engine — adapter trait to the delegated per-node eviction engine (rank 59).
  7. dcache-coherency — write-through / write-back / write-around, refresh-ahead, read-through (§20 Phase 8).
  8. dcache-replication — primary→replica log shipping + lag tracking (§19 Phase 7).
  9. dcache-migration — the four-phase online slot-migration state machine (§18 Phase 6).
  10. dcache-membership — gossip integration (rank-72 consumer, §16 Phase 4).
  11. dcache-coordinator — Raft-backed topology authority (rank-39 consumer, §17 Phase 5).
  12. dcache-router — client-side slot-table router + redirect follower (§13 Phase 1).
  13. dcache-server — the cache-node binary (three concurrent listeners).
  14. dcache-client — client library (router + hot-key detector + single-flight, §21).
  15. dcache-stampede — single-flight + XFetch probabilistic early expiration (§21 Phase 9).
  16. dcache-rebalancer — deterministic slot-rebalancing planner (§22 Phase 10).
  17. dcache-admin — operator CLI (§22 Phase 10).

System boundaries.

  • Provides: sharded GET/SET/DELETE/CAS cache semantics over three wire protocols; online resharding with at most one client redirection per request; async replication with lag-aware reads; five coherency policies; hot-key + stampede mitigation; gossip membership; Raft-committed topology; per-namespace TLS/ACL.
  • Delegates: per-node eviction algorithm (rank 59), gossip transport / failure-detector internals (rank 72), Raft log / leader-election internals (rank 39), write-back durability substrate (WAL, rank 69).
  • Does NOT provide: a SQL surface, server-side scripting (Lua), geo-replication, multi-master / active-active writes, on-disk persistence beyond the write-back WAL, pub/sub, Redis Streams, sub-second-granularity per-key TTL, atomic cross-key transactions beyond a single hash tag.

Non-goals for Phase 0: the polished web dashboard frontend (a CLI dashboard ships instead, §22 Phase 10); the Clojure Jepsen chaos probe (scaffold only, §23 Phase 11); the 30-day continuous fuzzing campaign (target M10 defined, not executed inside Phase 0).

Deployment model. 3–200 data-plane nodes plus a 3-or-5-node coordinator quorum on separate hosts (ADR-07), deployed as containers — Docker Compose for development, Helm / Terraform / Ansible for production (§10) — one process per data node exposing Memcached binary, RESP3, and gRPC listeners concurrently (P5).

Target users / operators. Platform and infrastructure teams operating a cache fleet in front of a primary datastore; on-call engineers debugging cache-cluster incidents using the runbooks in §10 (docs/runbooks/) and the Operational Readiness surface (§26).

What later phases unlock. Multi-master replication, geo-replication, tiered storage, Lua scripting, and Redis Streams — every one gated PhaseDeferred("§37") and tracked in the Deferred Features Register (§37).

Recommended language: Rust 2021, MSRV 1.75. Rationale: the per-node engine (rank 59) and the write-back WAL (rank 69) are Rust crates consumed directly with zero FFI; the Tokio ecosystem (hyper, tonic, tower) covers gRPC + RESP3 + Memcached fan-out from one async runtime; the absence of stop-the-world GC pauses is required to hold the p99 < 2 ms target (§4, M3) under load. Rejected — Go: a better out-of-the-box gossip story (Memberlist) but forces either FFI or a rewrite of the rank-59/69/72 Rust crates, and GC pauses compete directly with the p99 target (ADR-01 documents the concrete regime where Go still wins). Rejected — C++: matches the latency floor but the dependency/memory-safety story for codecs parsing untrusted network bytes (§24, T-1) is materially weaker than Rust's borrow-checked parsers.

Prerequisites: async I/O at the level of a working Tokio service; the Memcached binary protocol's opcode table and ext_len/key_len/vbucket_id framing; the Redis RESP3 type system and HELLO handshake; consistent-hashing variants (jump hash, rendezvous/HRW, ketama); SWIM and Lifeguard gossip; Raft to the level of reading Ongaro & Ousterhout (2014) unaided; at least one of thundering-herd mitigation, request coalescing, or probabilistic early expiration.

Estimated timeline: Phase 0 — 1 week (repo skeleton + correctness kernel). Full 12-phase system (Phase 0 through Phase 11) — 5–6 months.

PhaseDeferred flags (all resolve at §37, the Deferred Features Register): multi-master / active-active replication, RDB/AOF-style snapshot persistence, Lua / SCRIPT EVAL, Redis Streams, geo-replication, tiered storage, per-value compression, encryption at rest, the 30-day continuous fuzzing campaign, the Jepsen Clojure probe, the polished web dashboard frontend, shared-memory cross-process single-flight, per-key sub-second TTL, atomic multi-key MULTI/EXEC within a hash tag, a Pub/Sub listener, and a bloom-filter-fronted negative cache — each PhaseDeferred("§37").

2. Why Build This

  • A cache is the boundary between a service that survives traffic and one that does not: losing a database replica is a dashboard event; losing a cache shard is a thundering-herd incident the entire user base notices within seconds.
  • Teaches consistent-hashing tradeoffs under node churn (Karger et al. 1997), the exact ASK/MOVED redirection contract during a live reshard, the gossip-vs-consensus division of labor (liveness vs. ownership, MM2), single-flight and probabilistic early expiration as the two standard stampede defenses, and how one coherency-policy choice rewrites the durability contract (MM5).
  • Architecturally distinguishes proxy-routed (Twemproxy, mcrouter) from client-routed (Redis Cluster) cache topologies, and shows why Couchbase's vBucket map and Aerospike's Paxos-backed coordinator solve the same ownership problem over different consistency substrates (§33).
  • Historically, Nishtala et al. (2013) is the canonical account of what breaks at Facebook's scale — lease-based stampede control, regional pools, the gutter pool for backing-store failure; this project builds the lease-adjacent primitive (single-flight, §21) at a fraction of that scope, and documents exactly where the fraction stops (HQ10).
  • Builds the engineering muscle of designing a state machine correct under concurrent access (slot migration, §18), a router that never blocks the hot path on a consensus round trip (§6 P3), and reasoning about async-replication durability quantitatively instead of by adjective (§34).
  • Cross-links: shares the per-node eviction engine with LRU-LFU-Cache (rank 59); shares gossip with Gossip-Protocol (rank 72); shares consensus with Raft-Consensus (rank 39); shares the durability substrate with Write-Ahead-Log (rank 69); the routing and redirection design generalizes to Distributed-KV-Store and Distributed-Lock-Service.
  • Calibration: deliberately scoped to the GET/SET/DELETE/CAS core plus the minimal CLUSTER surface — small enough to finish in months, large enough that every phase ships something that would page an on-call engineer in production.

What Mastery Looks Like — after finishing, the reader can:

  • Derive the exact key-movement bound under node churn for jump hash vs. ketama vs. rendezvous, and pick the right one for a given shard-weight distribution (§13 Phase 1).
  • Explain why the data path must never block on a Raft round trip, and name the exact mechanism (ArcSwap + WatchTopology stream) that keeps it that way (§17 Phase 5).
  • Walk through the four-phase slot-migration state machine and identify the exact window where a naive implementation loses a write (§18 Phase 6).
  • Quantify the difference between async and sync replication in terms of the acknowledged-write-loss window, and state which coherency policy requires which durability substrate (§20 Phase 8).
  • Design a hot-key mitigation stack — client cache → single-flight → XFetch → shadow replica — and justify each layer's placement (§21 Phase 9).
  • Read a real cache-stampede or hot-key incident postmortem and map it onto this blueprint's Threat Model (§24) and Failure Modes (§25) vocabulary.
  • Redesign the cluster with a proxy-routed topology (the Twemproxy/mcrouter shape) and state exactly what operational observability the application loses (§36).

Client library. Owns the hash ring and the redirect-follower state machine; the only place a MOVED permanently updates routing state (I6). Runs inside the caller's process — no separate hop.

Wire layer. Three concurrent listeners (Memcached binary : 11211, RESP3 : 6379, gRPC : 50051) sharing one key namespace; the magic byte / first frame token disambiguates the protocol per connection, never per node (P5).

Routing / slot table. A read-mostly SlotTable (§11) behind an ArcSwap; the data path reads a local snapshot and never calls the coordinator inline (P3). This is the concurrency boundary between the hot path and cluster control.

Coherency engine. Dispatches to one of five policies per namespace (§20); the boundary between "cache" and "cache in front of a backing store."

Per-node engine. Delegated to LRU-LFU-Cache (rank 59) behind the Engine trait (§11); this is the persistence-adjacent boundary — the engine owns in-memory storage, the WAL (rank 69) owns durability when write-back is enabled.

Replication. Async, primary → N replicas, lag-tracked per replica; the data-plane's own internal consistency boundary, distinct from cluster-layer consensus.

Migration. The four-phase (Importing → DoubleWrite → Catchup → Cutover) state machine that moves slot ownership online; touches both the data plane (double-write) and the cluster layer (the SlotMoved commit).

Cluster layer. Gossip (liveness, eventually consistent) and the Raft coordinator (ownership, linearizable) are structurally separate processes on separate hosts — this is the project's central trust and authority boundary (I5, ADR-07).

Operability layer. The rebalancer, dashboard, and admin CLI are the only sanctioned callers of the coordinator's ProposeEvent RPC (§11); this is the admin trust boundary (§24, admin surface).

Three properties recur throughout this document: the data path is one-way at steady state (client hashes → client routes → server serves → replicas tail); the cluster layer is strictly out-of-band of the data path; the wire layer is multi-protocol by construction, never a per-node configuration choice.

6. Design Principles

  1. P1 — The client is the router. Routing logic lives in the client library, not a proxy. Tradeoff: the client library carries more logic than a thin proxy client would. Operational implication: topology is observable to the application (metrics, tracing attach to the caller's own process). Violating it (routing in a proxy) breaks P1's whole premise — see §36 Alt 1's rejection.
  2. P2 — Cluster topology is consensus-backed. Slot ownership, replica assignment, and the epoch live in the Raft log (I1, I2). Tradeoff: a second quorum to operate. Violating it (deriving ownership from gossip) produces split-brain slot ownership (MM2, §36 Alt 2).
  3. P3 — The data path never blocks on the cluster path. The data path reads a local SlotTable snapshot; it never calls the coordinator inline. Tradeoff: topology updates are eventually — not immediately — visible to the data plane. Violating it collapses the p99 latency target (§4, M3) the instant a Raft round trip lands on the hot path.
  4. P4 — Migrations are online by construction. Exactly one node is authoritative for a slot at every instant; the migration window admits reads from both sides. Tradeoff: a more complex state machine (§18) than stop-the-world migration. Violating it (skip the double-write window) reintroduces the maintenance-window outage this design exists to avoid.
  5. P5 — The wire surface is multi-protocol, simultaneously. Every node listens on Memcached binary, RESP3, and gRPC concurrently over one key namespace. Tradeoff: three codecs to maintain instead of one. Violating it (protocol-specific node pools) fragments the fleet and reintroduces the operational cost this design avoids (ADR-09).
  6. P6 — The per-node engine is pluggable, not bespoke. Eviction is delegated to the Engine trait (rank 59). Tradeoff: an extra trait-object indirection on every engine call. Violating it (forking the cluster code per eviction policy) makes TinyLFU/ARC/ S3-FIFO experiments require a cluster-code rewrite.
  7. P7 — No silent fallbacks. MOVED is a client bug (stale hash table); ASK is a migration in flight and must not be retained as authoritative (I6). Tradeoff: clients must implement the redirect state machine correctly. Violating it produces redirect storms (FM-2, MM3).
  8. P8 — Replication is async and lag-aware. The primary acks after local apply; reads with a freshness requirement specify min_lag_ms. Tradeoff: acknowledged writes can be lost on primary failure (ADR-08, FM-6). Violating it (silently promoting a lagging replica) serves stale reads as if they were fresh.
  9. P9 — Hot keys are a client concern first, server concern second. Detection, ephemeral caching, and coalescing happen client-side; shadow replicas (§21) are the server-side escalation. Tradeoff: client library complexity. Violating it pushes all hot-key load onto a single shard primary with no absorption layer.
  10. P10 — Determinism is the default for the rebalancer. The rebalancer's plan is a pure function of (current topology, target topology, weights, seed). Tradeoff: less "clever" heuristic freedom. Violating it makes two operators running the same rebalance get different plans — unacceptable for change management.
  11. P11 — Slot count is a load-bearing constant, never parameterized at runtime. 16,384 is compiled in (ADR-04, I13). Tradeoff: changing it requires a new cluster, not an online operation. Violating it (making slot count configurable per cluster) breaks every slot-indexed structure's fixed-size assumptions (§34).
  12. P12 — Observability is a first-class deliverable, not an afterthought. Every phase ships metrics and traces before it ships a feature flag to disable them. Tradeoff: more upfront work per phase. Violating it means the first production incident is also the first time anyone looks at what telemetry exists.
  13. P13 — Fail closed on ambiguous authorization. An ACL check that cannot resolve (stale cache, unknown principal) denies rather than allows. Tradeoff: a transient ACL propagation delay can cause spurious denials. Violating it fails open, the worse security failure mode (§24).
  14. P14 — Backward compatibility is a wire-format contract, not a convention. Every wire/storage schema change is versioned and dual-read for one release (§27). Tradeoff: slower schema iteration. Violating it breaks a rolling upgrade mid-fleet.

Malformed-input example

A Memcached frame whose declared total body length (bytes 8–11) does not equal key_len + extras_len + value_len: the codec rejects the frame, closes the connection, and increments wire_malformed_frame_total (T-1) — it never attempts a best-effort parse.

Failure-path example

A replica receives a replication record whose HMAC fails verification: the record is rejected (I8, I3 remain intact because nothing is applied), the replica requests a rebase, and the primary streams a fresh engine snapshot from scan_slot (FM-4).

XFetch (probabilistic early expiration)

Trigger a refresh when: now − (Δcompute × β × ln(U)) ≥ expires_at, where U ~ Uniform(0,1), Δcompute = last recomputation duration, β = per-namespace tunable aggressiveness (ADR-13). This is a formula, not an algorithm transcription — the implementation samples U once per read-near-expiry and compares against the closed-form threshold above.

12.6 Pitfalls

  • Slot count is 16,384, never 16,000 or 65,536 — load-bearing (ADR-04, I13).
  • SlotId is u16; do not widen to u32 for arithmetic convenience — keep promotions explicit at use sites.
  • Coordinator and data plane must never share a Tokio runtime, even in stub form.
  • An unpinned workspace Cargo.toml drifts between contributor machines — pin exact versions from commit one.

12.7 Performance Concerns

  • No networking yet, but the stub crate boundaries chosen here fix every later phase's incremental-build time and binary-size profile (P6).

12.8 Edge Cases

  • Empty SlotTable (0 nodes) must fail construction with a clear error, never panic.
  • A fixture with a node weight of 0 must be rejected at load time.

12.9 Failure Analysis

  • A malformed fixture (invalid JSON) must fail the smoke test with a descriptive parse error, not a context-free panic — the project's first error-handling discipline test.

12.10 Operational Notes

  • make bootstrap is the only supported dev-environment path; document expected wall-clock time in README.md.
  • The six workflows in .github/workflows/ are the sanctioned CI surface; a seventh requires an ADR.

13. Phase 1 — Client-Side Hashing & Routing

13.1 Objectives

  • Land the hash ring and the client-side router; no server exists yet — route() maps a key + SlotTable to a NodeId (P1).
  • Lock the slot-calculation contract (CRC16(hash_tag(key) or key) mod 16384, I11) before any server code depends on it.

13.2 Detailed Implementation Steps

  • dcache-hash: implement JumpHash, Rendezvous, Ketama behind a shared HashStrategy trait (ADR-05; Karger et al. 1997 for the movement bound; Lamping & Veach 2014 for jump hash; Thaler & Ravishankar 1998 for rendezvous).
  • Hash-tag extraction: the first {...} substring is the tagged slice; empty {} is treated as no tag (I11).
  • Virtual-node / weight placement: a shard with weight w takes w× the slots of a weight-1 shard; ticket-proportional round-robin assignment (documented, computed on the coordinator in §17 Phase 5).
  • dcache-router::Router: holds ArcSwap<SlotTable> + a fallback HashStrategy; route() returns ToPrimary or Importing depending on table.migrating (P3, I2).
  • Default path: slot-table + jump hash for placement; rendezvous/ketama exposed for the rebalancer and migration planner, not the default GET/SET path.

13.3 Deliverable

  • dcache-hash compiles with unit tests asserting distribution uniformity (jump, rendezvous, ketama) over 1M random keys.
  • SlotId::from_key is bit-identical to Redis Cluster's keyHashSlot() on every key in the parity fixture.

13.4 Acceptance Criteria

  • Per-shard frequency within 5% of the uniform expectation across shard counts {3, 6, 12, 24, 96} (fixture hash/distribution_*.jsonl).
  • 100% parity with hash/redis_cluster_parity.jsonl (10,000 keys), zero mismatches (I11).
  • Router::route returns a deterministic NodeId for a fixed (key, table) pair across 1M repeated calls.

13.5 Conformance Fixtures

  • hash/redis_cluster_parity.jsonl — 10,000 (key, expected_slot) pairs; expects exact match.
  • hash/distribution_{3,6,12,24,96}.jsonl — 1M keys per shard count; expects ≤5% skew.
  • hash/hash_tag_edge_cases.jsonl — {a}{b}, {}, no-tag keys; expects tag-on-first-only.

13.6 Pitfalls

  • CRC16 has many polynomial variants; Redis Cluster uses CRC16/CCITT-FALSE (poly 0x1021, init 0x0000, no reflection, xor-out 0x0000) — the wrong polynomial fails the parity test silently if all tests use only this project's own client (§13.5).
  • A hash tag is only the first {...} segment — {a}{b} hashes on a.
  • Jump consistent hash is biased for shard counts < 16 — document the floor; recommend the slot table for production (ADR-05).

13.7 Performance Concerns

  • Ketama's O(log N) binary search on a sorted ring is the cost center for the rebalancer/migration-planner path, not the default GET/SET path (which is an O(1) array index into SlotTable.primary).
  • ArcSwap::load is the only hot-path allocation-free read; never introduce a lock here (P3).

13.8 Edge Cases

  • A key with an unterminated { (no closing }) — treated as no tag, not an error.
  • A shard-weight change mid-flight — the placement algorithm's output is deterministic per (topology, weights, seed) (P10) even under concurrent weight updates queued by the coordinator.

13.9 Failure Analysis

  • A parity-test regression (I11 violation) is a P0 routing-correctness bug: client and server disagreeing on slot ownership for a key produces silent data unavailability, not a crash — blocks release until fixed.

13.10 Operational Notes

  • Expose hash_distribution_skew as a gauge per shard so operators see imbalance before it becomes a hot-node incident.
  • The rendezvous/ketama code paths are dormant in Phase 0's default routing — document this explicitly so operators don't mistake dormancy for a bug.

14. Phase 2 — Shard Server & Multi-Protocol Wire

14.1 Objectives

  • Bring up a single shard server speaking Memcached binary (:11211), RESP3 (:6379), and gRPC (:50051) concurrently (P5), consuming the engine via the Engine trait (rank 59).
  • No cluster yet — the server serves every key it sees.

14.2 Detailed Implementation Steps

  • dcache-wire-memcached: implement the 24-byte header codec (§8) as a tokio_util::codec::Decoder/Encoder pair producing Operation (§11); opcode table per §8 (Memcached source tree, proto_bin.c).
  • dcache-wire-resp3: implement the type-prefix codec (§8), the HELLO handshake, and the Phase-2 command subset (RESP3 spec).
  • dcache-wire-grpc: tonic-generated DCache service (Get/Set/Cas/Delete/ Stats) (ADR-18).
  • dcache-engine: adapter wrapping the rank-59 crate behind the Engine trait (§11; The Art of Multiprocessor Programming Ch.9 for the linearizability bar the adapter must preserve).
  • Dispatcher: protocol-agnostic; every wire crate produces an Operation, consumes a Response (§11); per-shard event loop (ADR-03, Dragonfly's shard-thread shape).
  • Wire each listener into bins/dcache-server.rs on independent Tokio tasks joined at shutdown.

14.3 Deliverable

  • dcache-server listens on all three ports concurrently.
  • pymemcache and redis-py both operate against the same key space from the same server.

14.4 Acceptance Criteria

  • examples/pymemcache_demo.py: write + read-back round-trips a key (fixture-gated exit 0).
  • examples/redis_py_demo.py: write over RESP3, read back the same key (fixture-gated exit 0).
  • conformance buckets wire.memcached.frame and wire.resp3.frame: 100% of fixtures round-trip; 100% of malformed fixtures are rejected with the documented error code.

14.5 Conformance Fixtures

  • wire/memcached/*.bin — valid + malformed binary frames; expects round-trip or documented rejection.
  • wire/resp3/*.bin — valid + malformed RESP3 frames, including the HELLO 3 negotiation sequence.

14.6 Pitfalls

  • Every multi-byte Memcached field is big-endian — use u32::from_be_bytes, never a hand-rolled byte-swap (Reference Impl: Memcached).
  • RESP3 disables RESP2 as default after HELLO 3; track the negotiated version per-connection, never globally (Reference Impl: Redis).
  • gRPC's default 4 MiB max-message-size is below the 1 MiB value ceiling plus migration RPC overhead — configure 16 MiB headroom.
  • Engine::cas returns CasOutcome::Mismatch, not an error — conflating the two has caused at least one production incident in every deployed cache lineage (§8).

14.7 Performance Concerns

  • Per-shard event loop avoids cross-core lock contention (ADR-03) but forces cross-shard operations through explicit channels — never reach across shards directly.
  • Frame allocation on the wire codec's hot path is not pre-bounded by default; profile under steady state and pre-allocate hot-path buffers (§30).

14.8 Edge Cases

  • A connection that sends HELLO 3 mid-stream after already issuing RESP2 commands — reject, do not silently re-negotiate.
  • A gRPC request exceeding the configured max-message-size — reject with a documented status code, not a panic.

14.9 Failure Analysis

  • A malformed frame that passes length checks but fails semantic validation (e.g. opcode 0xFF) must close the connection cleanly — an unclosed connection on a bad frame is a slow FD leak (§4 FD budget).

14.10 Operational Notes

  • Expose wire_frames_total{protocol,opcode} and wire_malformed_frame_total{protocol} from day one (P12).
  • Each listener's bind address is independently configurable for environments that firewall protocols differently.

15. Phase 3 — Static Cluster Routing (MOVED)

15.1 Objectives

  • Bring up a static 3-node cluster with consistent-hash-derived ownership; membership and resharding are out of scope until §16/§18.

15.2 Detailed Implementation Steps

  • Load a SlotTable (§11) from a JSON config file at startup; every node and every client holds a copy (the coordinator becomes the source of truth in §17 Phase 5, but the wire format locks here, P14).
  • dispatch(): compute SlotId::from_key (I11), compare against table.primary[slot]; if owned locally, serve; else return Response::Moved (§11, Redis Cluster spec).
  • Client follows Moved, refreshes its slot table, retries (I6).

15.3 Deliverable

  • A 3-node make compose-up cluster routes correctly: a fixed key always lands on the same node.

15.4 Acceptance Criteria

  • A client hitting the wrong node receives Moved and successfully follows the redirect (fixture-gated, wire/resp3/moved_redirect.bin).
  • Slot distribution balanced to within 1 slot for equal weights (reuses §13.4's bound).
  • Zero requests silently dropped across 100,000 randomly routed requests in tests/integration/test_cluster_routing.rs.

15.5 Conformance Fixtures

  • wire/resp3/moved_redirect.bin / wire/memcached/moved_redirect.bin — a request to the wrong node; expects Moved with the correct target.
  • hash/redirect_loop_guard.jsonl — a client configured to retry past 5 redirects; expects a clear terminal error, not an infinite loop.

15.6 Pitfalls

  • The slot table is read-mostly — use ArcSwap, never a lock, on the hot path (P3).
  • A node returning Moved to itself is a configuration error — assert in debug, warn in release.
  • A stale client sees Moved storms after a topology change — cap retries at 5 redirects and surface a clear terminal error past that threshold (I6).
  • The hash-tag rule (§13) applies before slot calculation — test both tagged and untagged keys in the routing corpus.

15.7 Performance Concerns

  • Moved responses add one full round trip; a client with a stale table under a fast-changing topology pays this repeatedly — bound by the 5-redirect cap above.

15.8 Edge Cases

  • A SlotTable fixture where two nodes claim the same slot — must fail load-time validation (I1), never silently pick one.
  • A client with an entirely empty (uninitialized) slot table — must fall back to a seed node, not panic.

15.9 Failure Analysis

  • A routing bug that sends a Get to the wrong node without a Moved response is a silent correctness bug (returns NotFound for a key that exists elsewhere) — the conformance corpus's 100,000-request integration test exists specifically to catch this class.

15.10 Operational Notes

  • Log every Moved at DEBUG with the requested vs. actual slot for post-incident correlation; never log key/value contents (§24).
  • The static JSON slot-table file's path is a Phase-3-only configuration surface; it is superseded by the coordinator in §17 Phase 5 and removed from the operator-facing config surface at that point (P14).

16. Phase 4 — Gossip Membership

16.1 Objectives

  • Bring membership online via the delegated SWIM/Lifeguard crate (rank 72); this project integrates, it does not re-implement gossip (I5).

16.2 Detailed Implementation Steps

  • dcache-membership: consume rank-72's NodeSuspect/NodeFailed/NodeAlive events (Das, Gupta, Motivala 2002); apply Lifeguard's Self-Awareness, Refute, and Suspicion Multiplier tweaks via the rank-72 crate directly (Gupta et al. 2018, I14).
  • Gossip payload: NodeId, address tuple (mc_addr/resp3_addr/grpc_addr), weight, highest observed epoch, coarse health bucket, replication lag (if a replica) — capped at 1 KiB per round (§34, C6).
  • Gossip explicitly excludes slot ownership, replica assignment, and failover decisions (I5) — those are Raft-committed in §17.
  • Bootstrap: a new node gossips to a seed list (not required to be exhaustive); once converged, it fetches the slot table from the coordinator over Raft-replicated metadata.
  • Failure detection: the coordinator subscribes to rank-72's failure events; a NodeFailed sustained past a 30 s grace period triggers failover initiation (§17 Phase 5).

16.3 Deliverable

  • A 3-node cluster's nodes discover each other via gossip given only the first node's address; a 4th node joins by gossiping to any one of the existing three.

16.4 Acceptance Criteria

  • Killing a node produces a NodeFailed event in the coordinator's log within the configured grace period (default 30 s, ±5 s jitter tolerance).
  • Gossip convergence time for a 6-node cluster ≤ 2 s from a single seed contact (tests/integration/test_gossip.rs).
  • Gossip payload size per round ≤ 1 KiB regardless of cluster size (fanout-bounded, §34 C6).

16.5 Conformance Fixtures

  • coordinator/gossip_join.jsonl — a new node's join sequence; expects convergence within the acceptance bound.
  • coordinator/gossip_false_positive.jsonl — a slow-link scenario; expects Lifeguard's refute mechanism to suppress the false failure report.

16.6 Pitfalls

  • Gossip says "no probe has failed recently," never "this node is alive with certainty" — never use it as ownership source of truth (I5, MM2).
  • The NodeFailed grace period trades spurious failovers (too short) against slow real recovery (too long); 30 s is the documented starting point (§4, M7).
  • Gossip's piggybacked metadata grows with cluster size uncapped without the 1 KiB cap — the coordinator broadcasts the slot table out-of-band instead of relying on gossip for it (Reference Impl: HashiCorp memberlist).

16.7 Performance Concerns

  • SWIM's per-round fanout is O(log N); at N = 200 nodes, per-node per-round traffic stays near 8 KiB even though full-cluster state is ~200 KiB (§34, C6) — the fanout, not the cap alone, is what makes this scale.

16.8 Edge Cases

  • A node that flaps (alive→suspect→alive) rapidly — Lifeguard's Suspicion Multiplier must grow the timeout, not treat every flap identically (I14).
  • A partitioned minority that still gossips among itself — must not conclude it is the majority; ownership decisions stay with the coordinator's quorum (§17), never gossip consensus.

16.9 Failure Analysis

  • A gossip false-positive failure report during a network blip triggers an unnecessary failover if the grace period is set too short — FM-7 documents the detection and mitigation path.

16.10 Operational Notes

  • Dashboard surfaces per-node gossip incarnation number and last-seen timestamp (§22).
  • docs/runbooks/partition.md documents the operator playbook when gossip reports a partition that Raft has not yet resolved.

17. Phase 5 — Raft Coordinator & Topology

17.1 Objectives

  • Stand up the coordinator: a separate process (3-or-5-node Raft quorum, rank 39) owning the epoch, the committed SlotTable, membership reconciliation, replica assignments, and failover decisions (P2, ADR-07).

17.2 Detailed Implementation Steps

  • dcache-coordinator: wrap the rank-39 Raft crate; every committed log entry is a ClusterEvent (§11; Ongaro & Ousterhout 2014 for leader election + log replication + membership changes).
  • Expose the Coordinator gRPC service (§11): GetTopology, WatchTopology (streaming), ProposeEvent (rate-limited, authenticated — the rebalancer/admin CLI's only entry point), HealthReport.
  • Data-plane subscription: every cache node opens a long-lived WatchTopology stream at startup; on a new event, atomically swap ArcSwap<SlotTable> (P3, I2).
  • Failover sequence on confirmed primary failure: pick the lowest-lag replica, promote, demote the failed primary (rejoins as a replica on return), update the slot table, advance the epoch (§19 Phase 7 for lag tracking).
  • Snapshot the Raft log every 10,000 entries (rank-39 default) to bound log growth (§34, C7).

17.3 Deliverable

  • The coordinator binary is built and deployed via compose-up; a 3-node coordinator + a 3-node data plane elects a leader, commits an EpochAdvanced event on every topology change, and survives killing the coordinator leader.

17.4 Acceptance Criteria

  • Coordinator leader election completes within 5 s of a leader kill (M8).
  • Data-plane SlotTable snapshots converge to the coordinator's latest committed table within 2 s of a WatchTopology push (tests/integration/test_coordinator.rs).
  • Zero topology events accepted out of epoch order across 10,000 simulated events (I2).

17.5 Conformance Fixtures

  • coordinator/events/*.jsonl — event sequences; expects monotonic epoch advancement and correct failover selection (lowest-lag replica).
  • coordinator/leader_kill.jsonl — kills the Raft leader mid-stream; expects re-election within M8's bound and zero lost committed entries.

17.6 Pitfalls

  • The coordinator must never share hosts with the data plane in production — a correlated failure of both is far harder to recover from (§24, FM-8).
  • An un-snapshotted Raft log grows unbounded — the 10,000-entry snapshot interval is provided by rank 39, not reimplemented here.
  • The data plane and coordinator must agree on epoch monotonicity (I2): a node that has observed Epoch(n+5) must never accept a write tagged Epoch(n) afterward — assert this in the data path, not just document it.

17.7 Performance Concerns

  • A Raft round trip (single-digit ms) must never appear on the GET/SET hot path (P3, §4); the WatchTopology push model is what keeps it off.
  • Coordinator quorum size (3 vs 5) trades election latency against fault tolerance — 5 tolerates 2 failures at the cost of a larger quorum round trip during ProposeEvent.

17.8 Edge Cases

  • A ProposeEvent submitted during an in-progress leader election — must queue or reject cleanly, never silently drop.
  • Two ProposeEvent calls racing to claim the same slot's ownership change — Raft's single-writer log serializes them; the loser receives a clear conflict response, not a corrupted commit (I1).

17.9 Failure Analysis

  • Coordinator leader loss triggers a brief ProposeEvent unavailability window (≤ 5 s, M8) — the data plane continues serving reads/writes from its last-known SlotTable snapshot throughout (P3 in action).

17.10 Operational Notes

  • docs/runbooks/failover.md documents the manual failover path via the admin CLI when automatic failover is intentionally disabled for a maintenance window.
  • Coordinator dashboard panel: current leader, epoch, quorum health, time-since-last-commit.

18. Phase 6 — Online Slot Migration

18.1 Objectives

  • Implement the four-phase migration state machine (§8) guaranteeing exactly one authoritative node per slot at every instant, with at most one client redirection per request during the window (P4, ADR-11).

18.2 Detailed Implementation Steps

  • dcache-migration::Migration: { slot, source, destination, phase, started_epoch, last_seq_copied } (§11); step() advances per the state-transition table (§8, I4).
  • Importing: destination told to import; reads to destination for slot keys return Ask source; writes accepted and stored locally.
  • DoubleWrite: both nodes hold the slot; a Set/Delete on either side replicates to the other; the migration daemon scans the source (scan_slot, I10) and copies keys, skipping any whose destination CAS is already higher (I3).
  • Catchup: bulk copy complete; daemon drains in-flight writes; source enters a brief read-only window for the slot.
  • Cutover: coordinator commits SlotMoved (§11); source stops serving the slot, returns Moved destination to any straggler request; migration complete.
  • Ask never mutates the client's slot table; Moved always does (I6) — this is the exact mechanism that prevents redirect storms in either direction.
  • Migration progress (keys/bytes copied, ETA) is published to the coordinator; the admin CLI can pause/resume/roll back (rollback returns the slot to Importing on the source; destination evicts).

18.3 Deliverable

  • dcache-cli migrate <slot> --from <node> --to <node> initiates and completes a migration under continuous load with zero failed requests.

18.4 Acceptance Criteria

  • benchmarks/reshard/online_reshard.rs: YCSB-A through a 100-slot migration reports zero error responses; p99 stays within 1.5× baseline (M5).
  • Every migration scenario in migration/*.json produces the documented end-state (I4-verified).
  • A migration that is rolled back mid-DoubleWrite leaves the source as sole authoritative owner within one grace period, zero data loss on already-committed keys.

18.5 Conformance Fixtures

  • migration/happy_path.json — full Importing→Cutover; expects final ownership at destination, zero dropped writes.
  • migration/rollback_mid_doublewrite.json — expects source reverts to Importing, dest evicts, zero corruption.
  • migration/concurrent_cas_during_doublewrite.json — a CAS race on both sides; expects I3-consistent resolution.

18.6 Pitfalls

  • The double-write window is the bug zone: a write hitting the source after the destination is added but before the source knows about the migration is a lost write — the state machine must guarantee the destination knows before double-writing starts.
  • Conflating Ask and Moved client-side causes infinite redirect spam in one direction or the other (I6, §15.6).
  • scan_slot's stream must be snapshot-isolated under concurrent writes (I10) — a non-isolated scan silently drops or duplicates keys mid-migration.
  • A CAS success on the source during DoubleWrite must replicate as a CAS, not a blind Set, so a concurrent CAS on the destination still respects the new value's CAS (I3).

18.7 Performance Concerns

  • The rebalancer's blast radius: migrating too many slots concurrently saturates the network and degrades the entire cluster's latency — bound concurrent migrations and gate on lag/latency signals (§22 Phase 10).
  • Migration copy throughput is throttled (default 50 MiB/s per migration, §34 C8) to keep the DoubleWrite window's replication overhead off the hot-path latency budget.

18.8 Edge Cases

  • Source crashes mid-DoubleWrite before destination acknowledges — daemon resumes from the coordinator's last-committed phase on restart, never re-imports already-imported keys (a re-import is a correctness bug, not an efficiency concern).
  • A key deleted on the source during Catchup after being copied to the destination — the delete must replicate to the destination before cutover, or the destination serves a phantom key.

18.9 Failure Analysis

  • A migration that stalls in DoubleWrite (destination unresponsive) is FM-5 — detection via a stalled-progress metric, recovery via daemon restart from last committed phase or operator-initiated rollback.

18.10 Operational Notes

  • docs/runbooks/reshard.md documents the pre-flight checklist (network headroom, target node capacity) and the abort procedure.
  • Dashboard surfaces migration progress (keys copied, ETA) and the per-slot phase in real time.

19. Phase 7 — Primary-Replica Replication

19.1 Objectives

  • Bring up async primary→N-replica replication with per-replica lag tracking and lag-aware read routing (P8, ADR-08).

19.2 Detailed Implementation Steps

  • dcache-replication: primary applies locally, advances seq, appends a ReplicationRecord (§11) to an append-only ring buffer, fans out to replicas, then acks the client (Kleppmann Ch.5 for the leader-based replication failure-mode taxonomy this design accepts).
  • Replica catch-up on join: fetch an engine snapshot (scan_slot composed across owned slots, I10), then tail the replication log from the snapshot's seq (Petrov Ch.11–12 for the catch-up strategy).
  • Lag tracking: each replica reports its applied seq; primary computes lag = current_seq − applied_seq, publishes via gossip, surfaces on the dashboard.
  • ReadRoutingPolicy (§11): a read with min_freshness filters replicas (and the primary) by lag, picks one (round-robin/weighted/P2C); falls back to the primary if none qualify.
  • Failover (§17): the coordinator promotes the lowest-lag replica; surviving replicas re-tail the new primary.

19.3 Deliverable

  • A 3-shard cluster, 1 replica per shard, runs continuous load; killing a primary triggers failover within the grace period, losing at most the documented async-replication window of unacknowledged writes.

19.4 Acceptance Criteria

  • Replication lag p99 < 100 ms at 100 KQPS write load (M6).
  • Failover completes within 30 s (M7) with zero acknowledged writes lost (tests/integration/test_replication.rs).
  • Dashboard shows per-replica lag in milliseconds, refreshed every second.

19.5 Conformance Fixtures

  • replication/lag_convergence.jsonl — a replica joining under steady load; expects lag to converge monotonically to near-zero.
  • replication/failover_no_loss.jsonl — kills the primary mid-load; expects zero acknowledged-write loss within the documented SLA.

19.6 Pitfalls

  • Async replication can lose acknowledged writes on primary failure — this is the documented tradeoff (ADR-08, FM-6), not a bug; customers needing stronger guarantees use write-back+WAL or a future sync-replication mode (§37).
  • The replication ring buffer must survive a slow replica within its bounded size; a replica that falls too far behind is forced into a snapshot rebase, not an unbounded buffer grow.
  • Lag is measured against the primary's monotonic seq counter, never wall-clock — clock skew between nodes must never leak into the lag computation (MM4).

19.7 Performance Concerns

  • Snapshot transfer on replica join is bandwidth-bound; throttle it similarly to migration copy (§18.7) so it doesn't compete with steady-state replication traffic.
  • min_freshness filtering adds a small per-read replica-selection cost — bound it to O(R) in the replica count R, which is small (≤ 3, §4).

19.8 Edge Cases

  • All replicas exceed min_freshness simultaneously — the router falls back to the primary rather than serving a stale read silently.
  • A replica that never catches up (persistently high lag) — flagged distinctly from a transiently lagging one; the dashboard and alerting differentiate the two (§26).

19.9 Failure Analysis

  • FM-3 (replication lag runaway) and FM-6 (acknowledged write loss on primary failure) are the two failure classes this phase's acceptance criteria are built to catch before production.

19.10 Operational Notes

  • docs/runbooks/replica-lag.md documents the triage sequence when the lag dashboard panel crosses the M6 threshold.
  • Replication metrics (replication_lag_ms, replication_apply_total) are per-shard, per-replica labeled from day one (P12).

20. Phase 8 — Coherency Policies

20.1 Objectives

  • Implement all five coherency policies — write-through (default), write-back, write-around, refresh-ahead, read-through — configurable per namespace (ADR-12).

20.2 Detailed Implementation Steps

  • WriteThrough (§11): cache write + synchronous backing-store write; ack only after both succeed — the only policy correct without a WAL (I7, ADR-12).
  • WriteBack (§11): cache write acked immediately; backing-store write is asynchronous, durable via the WAL (rank 69) until flushed (flush_interval, max_dirty_bytes); startup refuses to bind without a configured WAL (I7).
  • Write-around: writes bypass the cache entirely; a subsequent read populates it lazily — best for write-heavy, rarely-re-read workloads.
  • Refresh-ahead: a read nearing TTL triggers an async backing-store refresh; the current value serves immediately, the next read sees the refreshed value.
  • Read-through: a miss is filled from the backing store synchronously, stored, then returned — the cache becomes the reader's only API surface.
  • Per-namespace policy selection lives in the coordinator's namespace metadata; changing it is a coordinator operation — existing cached data is not migrated on policy change.

20.3 Deliverable

  • All five policies exercised by examples/coherency_demo.rs against a running cluster.

20.4 Acceptance Criteria

  • conformance bucket coherency.policies: each policy's documented invariant holds across its recorded backing-store call sequence (fixture-gated, 100% pass).
  • Write-back with no WAL configured refuses to start (I7, exit code non-zero, clear error message).
  • Refresh-ahead reduces p99 read latency for a key within 10% of its TTL by ≥ 30% versus a cold read-through baseline (measured in coherency_demo).

20.5 Conformance Fixtures

  • coherency/write_through.jsonl, write_back.jsonl, write_around.jsonl, refresh_ahead.jsonl, read_through.jsonl — one fixture per policy; each records the expected backing-store call sequence.
  • coherency/write_back_no_wal.jsonl — expects a startup refusal, not a silent fallback.

20.6 Pitfalls

  • Write-back without a WAL is not write-back — it is "we lose your data on cache restart"; refuse to start rather than silently degrade (I7).
  • Refresh-ahead can amplify backing-store load under hot-key conditions; combine with single-flight (§21).
  • Read-through has the thundering-herd problem out of the box on a cold cache; combine with single-flight and XFetch (§21).

20.7 Performance Concerns

  • Write-through's synchronous backing-store round trip is the write-latency floor for that policy — document it explicitly in the namespace's SLA (§26).
  • Write-back's flush_interval/max_dirty_bytes tuning trades backing-store batch efficiency against the dirty-data exposure window on cache crash.

20.8 Edge Cases

  • A backing-store call that times out mid-write-through — the client must see a clear error, never a silent "stored" acknowledgment for data that didn't reach the backing store.
  • A namespace policy change while writes are in-flight under the old policy — in-flight operations complete under the policy active when they started (no policy tearing).

20.9 Failure Analysis

  • A crashed cache node under write-back loses any dirty data not yet flushed to the WAL — bounded by max_dirty_bytes/flush_interval; the WAL replay on restart is the recovery path (§25, FM table).

20.10 Operational Notes

  • Namespace coherency policy is visible on the dashboard and in dcache-cli cluster nodes --namespace <ns> output.
  • docs/runbooks/triage.md includes a coherency-policy-specific decision tree for "reads look stale" incidents.

21. Phase 9 — Hot-Key Mitigation & Stampede Protection

21.1 Objectives

  • Land the full mitigation stack against the motivating workload: 50,000 hot keys hammered by 10,000 clients each, with a backing store serving ≤ 5,000 misses/second (P9).

21.2 Detailed Implementation Steps

  • Client-side detection: a count-min sketch (HotKeyDetector, §11) tags keys Cold/ Warm/Hot; Hot reads consult the client's ephemeral local_cache first (ADR-14).
  • Request coalescing: SingleFlight::run (§11) collapses concurrent same-(key,op) requests into one upstream call (ADR-15; Nishtala et al. 2013 for the lease-based alternative this design defers, HQ10).
  • Probabilistic early expiration: XFetch's closed-form trigger (§11; Vattani, Chierichetti, Lowenstein 2015, ADR-13) spreads refresh load across a key's TTL window instead of bunching it at expiry.
  • Server-side shadow replicas: a key hot enough to overwhelm one shard's primary is replicated to ephemeral, non-promotable read-only shadow replicas; the coordinator places them based on hot-key telemetry.
  • Hot-key log: a 5-minute rolling log of top-256-by-rate, top-256-by-miss-rate, top-256-by-latency keys per node, exposed via HotKeyTop(N) gRPC and a flat file.

21.3 Deliverable

  • benchmarks/hot_key/50k_hotkeys.rs runs against a 6-node cluster with no per-node latency degradation beyond the documented bound.

21.4 Acceptance Criteria

  • 50,000 hot keys × 1,000 QPS each (50M QPS aggregate demand): aggregate p99 ≤ 2 ms, no node exceeds 1.2× baseline latency degradation (M4).
  • Single-flight coalescing factor ≥ 100:1 under the 50K-hot-key load (M11, §34 C9).
  • XFetch's observed refresh probability matches the analytical curve within 5% (stampede/xfetch.jsonl).

21.5 Conformance Fixtures

  • stampede/xfetch.jsonl — sampled (now, expires_at, beta) triples; expects observed vs. predicted probability within 5%.
  • coherency/single_flight_coalescing.jsonl — N concurrent identical requests; expects exactly 1 upstream call.

21.6 Pitfalls

  • Count-min sketch is approximate: false positives (cold keys flagged hot) are tolerable, false negatives (hot keys missed) are not — tune cms_width/cms_depth accordingly (ADR-14).
  • Single-flight inside one client process does not coalesce across processes — two co-located client processes still issue two upstream requests (HQ10, deferred at §37).
  • XFetch's beta is the most consequential parameter: 1.0 is the paper's default; cache workloads benefit from beta ∈ [0.5, 1.5] — surface the recommended value from observed hit rate and miss latency.

21.7 Performance Concerns

  • Shadow-replica placement decisions add coordinator load proportional to hot-key telemetry volume — rate-limit telemetry submission from the data plane.
  • The hot-key log's rolling window (5 minutes) is a memory/precision tradeoff against a longer window's better trend visibility.

21.8 Edge Cases

  • A key that oscillates between Hot and Warm across the sketch's decay period — the shadow-replica placement must not thrash allocate/deallocate on every oscillation.
  • A hot key with a TTL of 0 (no expiry) — XFetch has no trigger window; document that XFetch requires a finite TTL and single-flight/shadow-replicas remain the mitigation for non-expiring hot keys.

21.9 Failure Analysis

  • FM-9 (hot-key overload) is this phase's target failure class: detection via the hot-key log crossing a rate threshold, auto-recovery via shadow-replica placement, manual recovery via dcache-cli hotkey-top plus operator-directed sharding of the offending key (application-level, out of this project's scope).

21.10 Operational Notes

  • docs/runbooks/hot-key.md documents the triage sequence: check the hot-key log, confirm shadow-replica placement, escalate to application-level key sharding if mitigation is insufficient.
  • Expose hotkey_detected_total, single_flight_coalesced_total, and xfetch_triggered_total from day one (P12).

22. Phase 10 — Auth, TLS, ACL & Operability

22.1 Objectives

  • Land the security and operability surface: TLS, per-namespace ACL, audit log, slow-log, the CLI dashboard, and the admin CLI (P13).

22.2 Detailed Implementation Steps

  • TLS via rustls (ADR-10) on every listener; SNI honored; mTLS opt-in for cluster-internal gRPC (coordinator ↔ data plane, ADR-07's trust boundary).
  • ACL: (Principal, Permissions) pairs per namespace; principals are SPIFFE IDs (mTLS) or API keys (client auth); permissions Read/Write/Delete/Admin; checked once per connection after HELLO/AUTH, cached, and re-validated once per command against the namespace prefix — an unresolvable check denies (P13, I9).
  • Audit log: every admin op, ACL denial, failover, and migration appended as HMAC-chained JSON-Lines, rotated daily (I12).
  • Slow-log: operations exceeding a per-namespace threshold (default 1 ms) logged with operation, key, duration, slot (Redis SLOWLOG lineage).
  • CLI dashboard (dcache-dashboard, JSON API) surfaces the slot map, per-shard lag, the hot-key log, the slow-log, migration progress, and the rebalancer's plan/state.
  • Admin CLI (dcache-admin): cluster create/nodes/slots, migrate, failover, add-node, remove-node, rebalance --confirm (deterministic, P10), hotkey-top, slowlog.

22.3 Deliverable

  • Every admin CLI command runs successfully against a compose-up cluster; the dashboard backend serves JSON at :8080/api/...; TLS is on by default in docker-compose.yml.

22.4 Acceptance Criteria

  • ACL check adds ≤ 5 µs p99 per command with the connection-level cache warm (M12).
  • A revoked-namespace ACL denies within one gossip interval of the revocation (I9, fixture-gated).
  • The audit log's HMAC chain verifies across a simulated daily rotation (tests/integration/test_audit_chain.rs).

22.5 Conformance Fixtures

  • coordinator/acl_revocation.jsonl — a revoked principal; expects denial within I9's bound.
  • coordinator/audit_chain_rotation.jsonl — a rotation event; expects unbroken HMAC chain.

22.6 Pitfalls

  • mTLS misconfiguration is silent: a node unable to authenticate to the coordinator can run forever as a useless data plane — add a startup smoke test that verifies the handshake.
  • ACL denial latency is user-visible — cache the per-connection evaluation; never re-evaluate the full ACL per command (only the cheap namespace-prefix check, §22.2).
  • The audit log's HMAC chain breaks if a record is dropped — the rotation procedure must preserve chain continuity across files (I12).

22.7 Performance Concerns

  • The rebalancer's deterministic plan output (P10) must still respect a concurrent- migration cap to avoid saturating the network during a large rebalance (§18.7).
  • Dashboard JSON API polling frequency is capped to avoid becoming a load source on the coordinator's GetTopology path.

22.8 Edge Cases

  • A principal presenting a valid mTLS cert but no namespace grants — denies per P13, not a crash.
  • A slow-log threshold set to 0 — must not flood the log with every operation; document the practical floor.

22.9 Failure Analysis

  • FM-10 (ACL cache staleness / authz drift) is this phase's target failure class — detection via acl_cache_staleness_seconds (I9), recovery via forced cache refresh.

22.10 Operational Notes

24. Threat Model

Trust boundaries

  1. Wire boundary. Untrusted: any client. Authenticated: clients completing HELLO + AUTH (RESP3), the Memcached SASL extension, or a valid mTLS certificate (gRPC).
  2. Cluster-internal boundary. Data nodes and the coordinator mutually authenticate via mTLS; a node without a valid certificate cannot participate (ADR-07).
  3. Replication boundary. Records carry a CRC and an HMAC; a replica that cannot verify either rejects the record and rebases (I8).
  4. Admin boundary. The admin CLI authenticates with a separate principal; admin operations require Admin permission on the coordinator's namespace (§22).

  • Tracing (OpenTelemetry, ADR-19): a span per request, per redirection, per replication apply, per migration step; trace context propagated across the wire boundary via gRPC metadata and a RESP3 attribute.
  • Structured logging: JSON-Lines; keys truncated at DEBUG, values never logged (T-9); a startup-configured redaction list.
  • Dashboards: slot-map heatmap, per-shard primary/replica/lag, hot-key log, slow-log, migration progress, rebalancer plan/state (§22).
  • Alerting philosophy: page on invariant violations (I1–I14 telemetry columns, §7) and M-table breaches (§30); warn on FM-table symptom-metric thresholds before they become pages.
  • SLOs: 99.95% monthly availability (§4); p99 ≤ 2 ms at documented throughput (M3); failover RTO ≤ 30 s (M7).
  • Incident response: blameless postmortem template (templates/postmortem.md, SRE Ch.21); every P0/P1 incident links its triggering metric and the runbook followed.
  • Named runbooks (docs/runbooks/): triage.md, partition.md, failover.md, reshard.md, hot-key.md, replica-lag.md.
  • Backup/restore: the WAL (rank 69) under write-back is the only durable state; restore replays the WAL into a fresh engine instance.
  • Deployment topology: data plane and coordinator on separate host pools (ADR-07, FM-8); 3-or-5-node coordinator quorum; data plane scales independently.
  • Canary/rolling-upgrade/rollback: one data node at a time, drained via SIGTERM grace (§4), validated against the conformance suite before proceeding to the next node; rollback replays the previous binary against the same SlotTable (P14).
  • Migration strategy (schema, not slot): wire/storage schema changes are additive and dual-read for one release (§27) before a breaking change is permitted.

27. Compatibility & Versioning

  • Wire compatibility: Operation/Response (§11) variants are additive; a codec encountering an unknown variant emits a protocol error, never a silent drop (P14).
  • Storage compatibility: Value/ReplicationRecord schema changes are additive (new optional fields); removing a field is a major-version, coordinated-upgrade change.
  • Schema evolution: every schema change ships a migration note in CHANGELOG.md and a dual-read window of one release before the old form is retired.
  • API stability: the Coordinator gRPC service (§11) is versioned via the protobuf package path; a breaking change bumps the package version and runs alongside the old one during the rolling upgrade.
  • Deprecation policy: a deprecated field/RPC is marked in the .proto/type doc comment for at least one minor release before removal.
  • SemVer policy: dcache-* crates follow SemVer; a breaking Engine/Coherency/ WireProtocol trait change is a major bump across the whole workspace (they are interdependent).
  • Rolling-upgrade guarantees: a mixed-version cluster (N and N+1) must interoperate for the duration of a rolling upgrade — enforced by the dual-read window above and by CI running a mixed-version conformance pass before a release is cut.

31. Scalability Analysis

  • Constant regardless of scale: per-request routing cost (O(1) array index into SlotTable.primary, P3); per-connection ACL check after the cache warms (M12).
  • Grows with shard count (O(1,000) target): gossip per-round traffic is O(log N) fanout, not O(N) (§34, C6); Raft log growth is bounded by the snapshot interval (§34, C7), independent of data-plane size.
  • Grows with data volume: per-node RAM (§34, C1); migration copy time per slot (§34, C8).
  • Named bottlenecks, in order: (1) coordinator ProposeEvent throughput under a high-churn fleet (mitigated by rate-limiting non-urgent proposals); (2) gossip payload size at very large N without the fanout property (mitigated by SWIM's O(log N) design, §16); (3) migration network bandwidth during a large rebalance (mitigated by the concurrent-migration cap, §18.7); (4) single NIC bandwidth per node at extreme per-node QPS (§34, C4).
  • Horizontal scaling: add data nodes; the rebalancer redistributes slots online (§18). Coordinator quorum size (3 or 5) is independent of data-plane size and does not need to grow with it.
  • Vertical scaling: more RAM per node raises the per-node key ceiling (§34, C1) linearly; more cores raise per-node shard-worker count (ADR-03) up to the point NIC bandwidth becomes the ceiling (§34, C4).
  • Sharding/partitioning: the 16,384-slot table (ADR-04) is the partitioning granularity; it is deliberately over-provisioned relative to the ~1,000-shard target so migration granularity stays fine even at scale.
  • Coordination overhead: bounded by keeping the coordinator off the data path entirely (P3) — the data plane's steady-state coordination cost is one WatchTopology stream per node, not a per-request cost.
  • Practical ceiling and levers beyond it: ~1,000 shards / ~200 physical nodes before slot-table broadcast size and gossip convergence time become the dominant cost (§31, HQ18); the lever beyond that ceiling is geo-sharding into independent clusters (PhaseDeferred("§37"), a fundamentally different scaling axis, not a parameter tweak).

32. Mental Models & First Principles

  1. MM1 — A slot is a unit of ownership, not a unit of locality. Predicts: 16,384 slots does not imply 16,384 lock domains. Bug class without it: assuming a slot boundary is a thread/lock boundary. Applies: §17 Phase 5, §18 Phase 6.
  2. MM2 — Gossip answers "is it alive"; consensus answers "who owns it." Predicts: merging the two produces split-brain. Bug class without it: routing decisions made from eventually-consistent gossip state. Applies: §16 Phase 4, §17 Phase 5, I5.
  3. MM3 — A redirect is a client-side state machine, not a server-side courtesy. Predicts: Ask/Moved must be tracked per-request vs. per-table respectively. Bug class without it: redirect storms in either direction. Applies: §18 Phase 6, I6.
  4. MM4 — Replication lag is a queue depth, not a clock. Predicts: lag-aware routing must consult applied-seq deltas, never wall-clock timestamps. Bug class without it: false freshness under clock skew. Applies: §19 Phase 7.
  5. MM5 — A cache-coherency policy is a durability contract wearing a performance costume. Predicts: write-back's real cost is the WAL dependency, not the async flush itself. Bug class without it: enabling write-back without provisioning durability. Applies: §20 Phase 8, I7.
  6. MM6 — A hot key is a distributed load-balancing problem hiding inside a single key. Predicts: the fix is fan-out (shadow replicas), never a bigger single node. Applies: §21 Phase 9.
  7. MM7 — Consistent hashing minimizes movement, not variance. Predicts: virtual nodes/weights are still required for balance; jump hash alone under-serves heterogeneous fleets. Applies: §13 Phase 1, ADR-05.
  8. MM8 — An epoch is a logical clock for authority, not for time. Predicts: epoch comparisons, never wall-clock timestamps, gate topology acceptance. Applies: §17 Phase 5, I2.

Memcached (+ Twemproxy/mcrouter): routing lives in a thin proxy or client hash ring with zero server-side cluster awareness — wins in the "many independent tiny caches, no cluster ops overhead" niche, where operational simplicity outweighs any cluster feature.

Redis Cluster: decided gossip is sufficient for cluster metadata and skipped a strong consensus layer, betting operators tolerate brief inconsistency windows during failover — wins when not running a second quorum matters more than the small split-brain-election risk (§36 Alt 2).

Couchbase Server: the cluster manager is a single elected orchestrator with disk-backed persistence as a first-class citizen — wins when the system is really a document database that happens to cache, where tiered memory+disk economics matter.

Aerospike: a Paxos-backed, strongly-consistent cluster map with native SSD-tier storage — wins in the "real-time operational database with a strict SLA and a working set too large for RAM" niche (ad-tech bidding, fraud detection).

This Design: Raft-in-a-separate-quorum is worth the operational cost of running two clusters, trading Redis Cluster's gossip-only simplicity for a linearizable topology-ownership guarantee (I1, I2) — wins when slot-ownership correctness is worth more than one fewer moving part, e.g. regulated environments where a split-brain double-write is a compliance incident.

34. Back-of-Envelope Capacity Model

  • C1 — Per-node key capacity: RAM = N × (S + overhead). Overhead ≈ 48 B/entry (rank-59 default); avg entry ≈ 1 KiB. For the 64 GiB ceiling (§4): N ≈ 64×2³⁰ / (1024+48) ≈ 60.2M keys/node.
  • C2 — Cluster key capacity, RF=1: 6 nodes × 60.2M ≈ 361M keys (§4 deployment model baseline).
  • C3 — Cluster key capacity, RF=2: replica copies consume half the aggregate RAM, halving usable distinct keys to ≈ 180M (§4 replication-factor row).
  • C4 — Bandwidth at M2: 10M GET/s × 1 KiB avg value ≈ 9.5 GiB/s aggregate egress across 6 nodes ≈ 1.6 GiB/s/node — sized against a 25 GbE NIC (~3.1 GiB/s), leaving headroom for replication and gossip traffic.
  • C5 — FD budget check: 100,000 FDs/node (§4) vs. 65,536 max connections + ~30 replication/gossip/coordinator streams — comfortable headroom for TIME_WAIT churn.
  • C6 — Gossip payload growth: a 200-node cluster's full-state size ≈ 200 KiB (1 KiB/node cap, §16); SWIM's per-round fanout (log₂ 200 ≈ 8) keeps per-node per-round traffic ≈ 8 KiB, not 200 KiB — the fanout, not the cap alone, bounds this.
  • C7 — Coordinator Raft log growth: at a worst-case 1 topology event/s × 200 B/event, with a 10,000-entry snapshot interval (§17.6): a snapshot every ≈ 2.8 hours; log size between snapshots ≈ 2 MiB.
  • C8 — Migration bandwidth: moving 1/16,384 of a 60.2M-key node ≈ 3,672 keys at 1 KiB avg ≈ 3.6 MiB, at a throttled 50 MiB/s migration-copy budget (§18.7): ≈ 72 ms per slot copy before the catchup drain.
  • C9 — Hot-key single-flight collapse factor: 50,000 hot keys × 1,000 QPS/key = 50M QPS logical demand (§4 hot-key workload); at a ~200 µs local p50 round trip (§4), up to ~200 concurrent duplicate requests per key can coalesce into one upstream call within one in-flight window — consistent with the ≥ 100:1 target (M11).
  • C10 — Audit log volume: ≈ 10 admin ops/hour + 1,000 ACL denials/day worst case × ~300 B/record ≈ 300 KB/day/node — trivial against the 64 GiB memory ceiling, confirming daily rotation (§26) is sized correctly.

36. Alternative Architectures (Roads Not Taken)

Alt 1 — Proxy-Routed Topology

Show the original text diagram
client -> [stateless proxy tier] -> shard 1..N
              (consistent hash,
               no cluster awareness
               in the client)

Regime where it wins: many small, independent, polyglot client fleets that should never see cluster topology; the simplest possible client library. Real system: Twemproxy, mcrouter. Rejected because it hides topology from the application (violates P1), adds a network hop, and turns the proxy tier itself into a new capacity-planning and SPOF-class problem this design's client-routed model avoids entirely.

Alt 2 — Gossip-Only Topology (no separate consensus quorum)

Show the original text diagram
node1 <--gossip--> node2 <--gossip--> node3
   (slot ownership derived from
    gossip-converged state, no Raft)

Regime where it wins: small-to-medium fixed clusters (tens of nodes) where operating a second quorum is not worth it. Real system: Redis Cluster. Rejected because gossip is eventually consistent; a split vote during a network partition can produce two nodes both believing they own a slot — this design's I1/I2 require linearizable ownership, which gossip alone cannot provide (§33).

Alt 3 — Embedded Consensus Per Node

Show the original text diagram
[node1 = data + Raft peer] <-> [node2 = data + Raft peer] <-> [node3 = data + Raft peer]
        (every data node is also a consensus voter)

Regime where it wins: small fixed clusters (3–7 nodes) where a second quorum is pure overhead and the team wants one binary, one deployment unit. Real system: etcd, CockroachDB. Rejected because coupling every data node to consensus-quorum membership degrades quorum latency as the data plane scales — it violates P3 at scale beyond roughly 7 nodes, well below this project's 1,000-shard target (§31, HQ19).

38. Glossary

ACL — access-control list; here, per-namespace (Principal, Permissions) grants. ASK — a redirect meaning "this slot is migrating; retry this one request at the destination without updating your routing table" (I6). CAS (Compare-And-Swap) — a conditional write that succeeds only if the value's current version matches an expected version (I3). Coherency policy — the rule governing how the cache and a backing store stay consistent (write-through, write-back, write-around, refresh-ahead, read-through). Coordinator — the Raft-backed process owning topology, slot ownership, and the epoch (§17). Count-min sketch — a probabilistic frequency-counting structure used for hot-key detection (§21). Cutover — the terminal migration phase committing new slot ownership (§8). DoubleWrite — the migration phase where both source and destination accept writes for a slot (§18). Engine — the per-node eviction/storage trait, delegated to LRU-LFU-Cache (rank 59). Epoch — the monotonic topology version number (I2, MM8). Failover — promoting a replica to primary after a confirmed primary failure (§17). Gossip — the SWIM/Lifeguard-based liveness-propagation protocol (§16); never a source of ownership truth (I5). Hash tag — a {...} substring within a key that pins its slot for co-location. Hot key — a key receiving disproportionate request volume relative to its shard's capacity. HRW (rendezvous) hashing — a hash strategy selecting the shard with the highest weighted hash per key (Thaler & Ravishankar 1998). Importing — the first migration phase; the destination accepts writes but has no existing keys for the slot yet (§8). Incarnation number — a per-node gossip counter used to resolve suspicion vs. refutation (I14). Jump consistent hash — an O(log N), memory-free hash strategy (Lamping & Veach 2014). Ketama — a virtual-node consistent-hash ring, the standard memcached-client choice. Lifeguard — SWIM extensions (Self-Awareness, Refute, Suspicion Multiplier) reducing false-positive failure detection (Gupta et al. 2018). Migration — the online process of moving slot ownership between nodes (§18). Moved — a redirect meaning "this slot is owned elsewhere; update your routing table and retry" (I6). Namespace — a key-space partition used for ACL, coherency policy, and quota scoping. Primary — the node authoritative for a slot's writes. Quorum — the minimum voter count required for a Raft (or gossip failure-decision) commit. Raft — the leader-election-plus-log-replication consensus algorithm backing the coordinator (Ongaro & Ousterhout 2014). Rebalancer — the deterministic planner producing slot-migration plans (P10). Refresh-ahead — a coherency policy that asynchronously refreshes a value nearing TTL. Replica — a node holding an async-replicated copy of a shard's data. Replication lag — the sequence-number gap between a primary and a replica (MM4). RESP3 — the Redis serialization protocol, version 3 (§8). Rendezvous hashing — see HRW hashing. RTO — recovery time objective; the maximum tolerable outage duration (§4). Shadow replica — an ephemeral, non-promotable read-only replica created to absorb hot-key load (§21). Single-flight — request coalescing: concurrent identical requests share one upstream call (§21). Slab allocator — the fixed-size-class memory allocator used by the per-node engine. Slot — one of 16,384 fixed partitions of the key space (ADR-04, I13). SlotTable — the committed mapping of slots to primaries/replicas/migration state (§11). SPIFFE — a standard for cryptographically verifiable workload identity, used for mTLS principals. SWIM — Scalable Weakly-consistent Infection-style Membership; the gossip failure-detection protocol (Das, Gupta, Motivala 2002). Thundering herd — many concurrent requests recomputing/backfilling the same value simultaneously after a cache miss or expiry. Topology — the current cluster membership + slot-ownership state. Virtual node — a placement point on a consistent-hash ring, used to smooth shard-weight distribution. WAL (Write-Ahead Log) — the durability substrate (rank 69) required by write-back coherency (I7). Write-around — a coherency policy where writes bypass the cache entirely. Write-back — a coherency policy where the cache acks immediately and flushes to the backing store asynchronously via the WAL. Write-through — a coherency policy where the cache acks only after the backing store write succeeds (the default, ADR-12). XFetch — the probabilistic early-expiration algorithm (Vattani, Chierichetti, Lowenstein 2015). YCSB — the Yahoo! Cloud Serving Benchmark, used for macro-benchmarking (ADR-21).
