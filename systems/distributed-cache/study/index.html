Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why must the data path read the slot table from a local ArcSwap snapshot rather than calling the coordinator inline, and what latency number does this avoid paying on every request? (§4, §17 Phase 5, P3)
  2. Trace what happens to an in-flight write if the source node crashes mid-DoubleWrite before the destination acknowledges the migration; which invariant prevents data loss, and which one still allows a narrow loss window? (§18 Phase 6, I4, I8)
  3. Why does Ask never mutate the client's slot table while Moved always does, and what failure mode results from swapping the two behaviors? (§18 Phase 6, I6, MM3)
  4. Derive the node-level RAM ceiling for 60M keys at 1 KiB average size, and explain why replication factor changes the usable key count, not the raw RAM number. (§4, §34 C1–C3)
  5. Why is gossip explicitly forbidden from carrying slot ownership, and what specific split-brain scenario results if it did? (§16 Phase 4, I5, MM2)
  6. Compare Redis Cluster's gossip-only topology model to this design's separate Raft coordinator — under what operational regime does the simpler model actually win? (§17 Phase 5, §33)
  7. Explain why write-back coherency without a WAL is strictly worse than write-around, not just "less durable." (§20 Phase 8, I7, ADR-12)
  8. What is the mathematical mechanism by which XFetch spreads refresh load across a key's TTL window, and why is beta the most consequential tuning parameter? (§21 Phase 9, §11 XFetch)
  9. Why does the count-min-sketch hot-key detector tolerate false positives but not false negatives, and how does that asymmetry drive cms_width/cms_depth? (§21 Phase 9, ADR-14)
  10. A client-side single-flight only coalesces within one client process — trace the exact multi-client scenario where this fails to prevent a thundering herd, and name the two mitigations that still apply. (§21 Phase 9, §37, Nishtala et al. 2013)
  11. Why must the coordinator run on hosts separate from the data plane, and what specific failure-correlation risk does colocating them introduce? (§17 Phase 5, §24, FM-8)
  12. Using the FD budget and connection-count numbers in §4, show why 100,000 FDs/node is sufficient headroom rather than a tight fit. (§4, §34 C5)
  13. Why is the slot count locked at 16,384 rather than parameterized per cluster, and what would have to be rebuilt if it changed mid-life? (§9 ADR-04, I13, §31)
  14. Trace a GET request arriving at a node mid-Cutover for its slot — which of the four migration phases could plausibly still be observed by the client, and what response does each phase produce? (§18 Phase 6, §8)
  15. Why does the ACL check happen once per connection rather than once per command, and what correctness property (I9) would break if the per-connection cache were never invalidated? (§22 Phase 10, I9)
  16. Contrast this design's replication-lag-aware read routing with Dynamo's read-repair / quorum approach — which failure mode does each handle that the other does not? (§19 Phase 7, DeCandia et al. 2007, §33)
  17. Why is xxHash3 acceptable for slot assignment but not necessarily for a public-facing hash-flooding-resistant surface, and where in the Threat Model does this tradeoff surface? (§9 ADR-17, §24, T-6)
  18. Using the M2/M4 targets and the C4 bandwidth derivation, explain why a 25 GbE NIC is sized correctly for the target cluster but would not be for a 10× larger deployment — what breaks first? (§30, §34 C4, §31)
  19. Why does this design reject embedding Raft on every data node (the etcd/CockroachDB shape) even though it is a well-proven pattern — what does the separate-coordinator shape buy that's worth the second quorum? (§36, ADR-07)
  20. A postmortem states "the cache lost writes during a routine primary restart, even though replication looked healthy." Using the Failure Modes table and the async- replication ADR, explain the most likely root cause and which Phase-7 acceptance criterion should have caught it pre-production. (§25, FM-6, ADR-08, §19 Phase 7 N.4)

32. Mental Models & First Principles

  1. MM1 — A slot is a unit of ownership, not a unit of locality. Predicts: 16,384 slots does not imply 16,384 lock domains. Bug class without it: assuming a slot boundary is a thread/lock boundary. Applies: §17 Phase 5, §18 Phase 6.
  2. MM2 — Gossip answers "is it alive"; consensus answers "who owns it." Predicts: merging the two produces split-brain. Bug class without it: routing decisions made from eventually-consistent gossip state. Applies: §16 Phase 4, §17 Phase 5, I5.
  3. MM3 — A redirect is a client-side state machine, not a server-side courtesy. Predicts: Ask/Moved must be tracked per-request vs. per-table respectively. Bug class without it: redirect storms in either direction. Applies: §18 Phase 6, I6.
  4. MM4 — Replication lag is a queue depth, not a clock. Predicts: lag-aware routing must consult applied-seq deltas, never wall-clock timestamps. Bug class without it: false freshness under clock skew. Applies: §19 Phase 7.
  5. MM5 — A cache-coherency policy is a durability contract wearing a performance costume. Predicts: write-back's real cost is the WAL dependency, not the async flush itself. Bug class without it: enabling write-back without provisioning durability. Applies: §20 Phase 8, I7.
  6. MM6 — A hot key is a distributed load-balancing problem hiding inside a single key. Predicts: the fix is fan-out (shadow replicas), never a bigger single node. Applies: §21 Phase 9.
  7. MM7 — Consistent hashing minimizes movement, not variance. Predicts: virtual nodes/weights are still required for balance; jump hash alone under-serves heterogeneous fleets. Applies: §13 Phase 1, ADR-05.
  8. MM8 — An epoch is a logical clock for authority, not for time. Predicts: epoch comparisons, never wall-clock timestamps, gate topology acceptance. Applies: §17 Phase 5, I2.

5. Required Reading

Books

  • Kleppmann, Designing Data-Intensive Applications (O'Reilly, 2017) — Ch.5 (Replication), Ch.6 (Partitioning). Extract: leader-based replication failure modes, hash- vs. range-based partitioning tradeoffs. Applied in §19 Phase 7, §13 Phase 1.
  • Petrov, Database Internals (O'Reilly, 2019) — Ch.11–12 (Replication and Consistency), Ch.13 (Anti-Entropy). Extract: replica catch-up strategies, read-repair. Applied in §19 Phase 7.
  • Tanenbaum & Van Steen, Distributed Systems: Principles and Paradigms (3rd ed.) — Ch.6 (Coordination — Election Algorithms), Ch.7 (Consistency and Replication). Extract: election-algorithm tradeoffs, the consistency-model taxonomy. Applied in §17 Phase 5.
  • Beyer, Jones, Petoff, Murphy (eds.), Site Reliability Engineering (O'Reilly, 2016) — Ch.4 (SLOs), Ch.21 (Postmortem Culture). Extract: SLO definition discipline, blameless postmortem structure. Applied in §26 Operational Readiness.
  • Herlihy & Shavit, The Art of Multiprocessor Programming (rev. ed.) — Ch.9 (Linearizability), Ch.13 (Concurrent Hashing). Extract: linearizability as the correctness bar for the Engine trait; lock-free hash-table lessons. Applied in §14 Phase 2.
  • Blandy, Orendorff, Tindall, Programming Rust (2nd ed., O'Reilly, 2021) — Ch.5 (References), Ch.19 (Concurrency). Extract: Arc/Mutex/channel idioms used throughout the crate split. Applied in §12 Phase 0, §10 Repository Layout.
  • Gjengset, Rust for Rustaceans (No Starch Press, 2021) — Ch.8 (Async Programming), Ch.9 (Unsafe Code). Extract: dyn-safe async-trait patterns — Engine, WireProtocol, Coherency are all dyn-compatible async traits. Applied in §11 Core Schema & Types.

Papers

  • Karger, Lehman, Leighton, Levine, Lewin, Panigrahy, 1997, Consistent Hashing and Random Trees, STOC. Proves the O(1/n) key-movement bound under churn. Applied in §13 Phase 1, ADR-05.
  • Lamport, 1998, The Part-Time Parliament, ACM TOCS (Paxos). Quorum-consensus foundation, contrasted against Raft. Applied in §17 Phase 5.
  • Ongaro & Ousterhout, 2014, In Search of an Understandable Consensus Algorithm, USENIX ATC (Raft). Leader election, log replication, membership changes. Applied in §17 Phase 5 (rank-39 crate), I2.
  • Das, Gupta, Motivala, 2002, SWIM: Scalable Weakly-consistent Infection-style Process Group Membership Protocol, DSN. The indirect-probe failure detector. Applied in §16 Phase 4, I5.
  • Gupta, Dadgar et al., 2018, Lifeguard: Local Health Awareness for More Accurate Failure Detection (HashiCorp). Self-Awareness, Refute, Suspicion Multiplier. Applied in §16 Phase 4, I14.
  • Lamping & Veach, 2014, A Fast, Minimal Memory, Consistent Hash Algorithm, arXiv: 1406.2294 (Jump Hash). Applied in §13 Phase 1, ADR-05.
  • Thaler & Ravishankar, 1998, Using Name-Based Mappings to Increase Hit Rates, IEEE/ACM Transactions on Networking, vol. 6 (rendezvous / HRW hashing). Applied in §13 Phase 1, ADR-05.
  • Nishtala et al., 2013, Scaling Memcache at Facebook, NSDI. Lease-based coalescing, regional pools, the gutter pool. Applied in §21 Phase 9, ADR-15, HQ10.
  • Bronson et al., 2013, TAO: Facebook's Distributed Data Store for the Social Graph, USENIX ATC. Read-after-write semantics across replicas. Applied in §19 Phase 7.
  • Vattani, Chierichetti, Lowenstein, 2015, Optimal Probabilistic Cache Stampede Prevention, PVLDB (XFetch). Applied in §21 Phase 9, ADR-13.
  • Srinivasan et al., 2016, Aerospike: Architecture of a Real-Time Operational DBMS, PVLDB. Paxos-backed cluster coordination, contrasted against this design's Raft choice. Applied in §33 Comparative Architecture, §17 Phase 5.
  • DeCandia et al., 2007, Dynamo: Amazon's Highly Available Key-value Store, SOSP. Eventual consistency, gossip membership, hinted handoff, vector clocks under partition. Applied in §16 Phase 4 (MM2), §24 Threat Model.

Reference Implementations

  • Memcached (memcached.c, assoc.c, slabs.c, proto_bin.c). Lesson: binary protocol framing. Pitfall: do not hand-roll byte-swap logic — use the standard big-endian primitives. Applied in §14 Phase 2.
  • Redis (cluster.c, resp_parser.c). Lesson: MOVED/ASK semantics and the RESP3 type system. Pitfall: protocol negotiation is per-connection state, never global. Applied in §15 Phase 3, §18 Phase 6.
  • Twemproxy (twitter/twemproxy: nc_proxy.c, nc_server.c). Lesson: proxy-routed operational tradeoffs. Pitfall: a proxy hides topology from the application. Applied in §36 Alternative Architectures.
  • mcrouter (facebook/mcrouter: mcrouter/routes/). Lesson: the routing-policy DSL shape (AllSyncRoute, MissFailoverRoute, LatestRoute, WarmUpRoute). Pitfall: over-general routing DSLs become unauditable. Applied in §22 Phase 10, §36.
  • HashiCorp memberlist (hashicorp/memberlist). Lesson: the canonical Lifeguard implementation. Pitfall: gossip payload growth is uncapped without a piggyback cap. Applied in §16 Phase 4.
  • Dragonfly (dragonflydb/dragonfly). Lesson: the shard-thread, shared-nothing event loop shape. Pitfall: shared-nothing forces cross-shard operations through explicit message passing — do not reach across shards directly. Applied in §14 Phase 2, ADR-03.
  • KeyDB (Snapchat/KeyDB design notes). Lesson: the multi-master conflict-resolution design space. Pitfall: last-writer-wins loses concurrent writes silently without application-level awareness. Applied in §37 Deferred Features Register, ADR-23.

Glossary (§38) · 49 terms · site-wide glossary

ACL
access-control list; here, per-namespace (Principal, Permissions) grants.
ASK
a redirect meaning "this slot is migrating; retry this one request at the destination without updating your routing table" (I6).
CAS (Compare-And-Swap)
a conditional write that succeeds only if the value's current version matches an expected version (I3).
Coherency policy
the rule governing how the cache and a backing store stay consistent (write-through, write-back, write-around, refresh-ahead, read-through).
Coordinator
the Raft-backed process owning topology, slot ownership, and the epoch (§17).
Count-min sketch
a probabilistic frequency-counting structure used for hot-key detection (§21).
Cutover
the terminal migration phase committing new slot ownership (§8).
DoubleWrite
the migration phase where both source and destination accept writes for a slot (§18).
Engine
the per-node eviction/storage trait, delegated to LRU-LFU-Cache (rank 59).
Epoch
the monotonic topology version number (I2, MM8).
Failover
promoting a replica to primary after a confirmed primary failure (§17).
Gossip
the SWIM/Lifeguard-based liveness-propagation protocol (§16); never a source of ownership truth (I5).
Hash tag
a {...} substring within a key that pins its slot for co-location.
Hot key
a key receiving disproportionate request volume relative to its shard's capacity.
HRW (rendezvous) hashing
a hash strategy selecting the shard with the highest weighted hash per key (Thaler & Ravishankar 1998).
Importing
the first migration phase; the destination accepts writes but has no existing keys for the slot yet (§8).
Incarnation number
a per-node gossip counter used to resolve suspicion vs. refutation (I14).
Jump consistent hash
an O(log N), memory-free hash strategy (Lamping & Veach 2014).
Ketama
a virtual-node consistent-hash ring, the standard memcached-client choice.
Lifeguard
SWIM extensions (Self-Awareness, Refute, Suspicion Multiplier) reducing false-positive failure detection (Gupta et al. 2018).
Migration
the online process of moving slot ownership between nodes (§18).
Moved
a redirect meaning "this slot is owned elsewhere; update your routing table and retry" (I6).
Namespace
a key-space partition used for ACL, coherency policy, and quota scoping.
Primary
the node authoritative for a slot's writes.
Quorum
the minimum voter count required for a Raft (or gossip failure-decision) commit.
Raft
the leader-election-plus-log-replication consensus algorithm backing the coordinator (Ongaro & Ousterhout 2014).
Rebalancer
the deterministic planner producing slot-migration plans (P10).
Refresh-ahead
a coherency policy that asynchronously refreshes a value nearing TTL.
Replica
a node holding an async-replicated copy of a shard's data.
Replication lag
the sequence-number gap between a primary and a replica (MM4).
RESP3
the Redis serialization protocol, version 3 (§8).
Rendezvous hashing
see HRW hashing.
RTO
recovery time objective; the maximum tolerable outage duration (§4).
Shadow replica
an ephemeral, non-promotable read-only replica created to absorb hot-key load (§21).
Single-flight
request coalescing: concurrent identical requests share one upstream call (§21).
Slab allocator
the fixed-size-class memory allocator used by the per-node engine.
Slot
one of 16,384 fixed partitions of the key space (ADR-04, I13).
SlotTable
the committed mapping of slots to primaries/replicas/migration state (§11).
SPIFFE
a standard for cryptographically verifiable workload identity, used for mTLS principals.
SWIM
Scalable Weakly-consistent Infection-style Membership; the gossip failure-detection protocol (Das, Gupta, Motivala 2002).
Thundering herd
many concurrent requests recomputing/backfilling the same value simultaneously after a cache miss or expiry.
Topology
the current cluster membership + slot-ownership state.
Virtual node
a placement point on a consistent-hash ring, used to smooth shard-weight distribution.
WAL (Write-Ahead Log)
the durability substrate (rank 69) required by write-back coherency (I7).
Write-around
a coherency policy where writes bypass the cache entirely.
Write-back
a coherency policy where the cache acks immediately and flushes to the backing store asynchronously via the WAL.
Write-through
a coherency policy where the cache acks only after the backing store write succeeds (the default, ADR-12).
XFetch
the probabilistic early-expiration algorithm (Vattani, Chierichetti, Lowenstein 2015).
YCSB
the Yahoo! Cloud Serving Benchmark, used for macro-benchmarking (ADR-21). ---
