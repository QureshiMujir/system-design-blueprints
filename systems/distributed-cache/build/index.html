⬜ Phase 0 — Skeleton & Correctness Kernel §12

Objectives
  • Stand up the repository skeleton (§10) as a single commit; every crate compiles as an empty stub wired into the workspace manifest.
  • Land governance files and the six .github/workflows/ pipelines.
  • Lock ADR-01 through ADR-11 (§9, ADR-01 through ADR-11) before any wire code exists — P2/P3's high-blast-radius decisions come first.
  • Deliver the "Hello, slot map" smoke test: a 3-node SlotTable (§11) that satisfies I1 and a balanced-to-within-1 distribution.
Deliverable
  • make bootstrap && make build && make test exit 0 from a clean clone.
  • One passing test: the "Hello, slot map" smoke test.
  • ADR-01 through ADR-11 committed under docs/adr/.
Acceptance
  • make test reports exactly 1 passing, 0 failing, 0 ignored.
  • hash/3node-balanced.json round-trips through serde with zero field loss.
  • Primary-count balance: max(count) − min(count) ≤ 1 across the 3 nodes.
  • ci.yml is green within 10 minutes wall-clock on the initial commit.
Fixtures
  • hash/3node-balanced.json — 3-node equal-weight SlotTable; expects I1 holds, balance ≤ 1.
  • hash/malformed_slot_table.json — two primaries claim slot 42; expects the invariant-check assertion to fail loudly (proves the assertion catches the violation).
Pitfalls
  • Slot count is 16,384, never 16,000 or 65,536 — load-bearing (ADR-04, I13).
  • SlotId is u16; do not widen to u32 for arithmetic convenience — keep promotions explicit at use sites.
  • Coordinator and data plane must never share a Tokio runtime, even in stub form.
  • An unpinned workspace Cargo.toml drifts between contributor machines — pin exact versions from commit one.

⬜ Phase 1 — Client-Side Hashing & Routing §13

Objectives
  • Land the hash ring and the client-side router; no server exists yet — route() maps a key + SlotTable to a NodeId (P1).
  • Lock the slot-calculation contract (CRC16(hash_tag(key) or key) mod 16384, I11) before any server code depends on it.
Deliverable
  • dcache-hash compiles with unit tests asserting distribution uniformity (jump, rendezvous, ketama) over 1M random keys.
  • SlotId::from_key is bit-identical to Redis Cluster's keyHashSlot() on every key in the parity fixture.
Acceptance
  • Per-shard frequency within 5% of the uniform expectation across shard counts {3, 6, 12, 24, 96} (fixture hash/distribution_*.jsonl).
  • 100% parity with hash/redis_cluster_parity.jsonl (10,000 keys), zero mismatches (I11).
  • Router::route returns a deterministic NodeId for a fixed (key, table) pair across 1M repeated calls.
Fixtures
  • hash/redis_cluster_parity.jsonl — 10,000 (key, expected_slot) pairs; expects exact match.
  • hash/distribution_{3,6,12,24,96}.jsonl — 1M keys per shard count; expects ≤5% skew.
  • hash/hash_tag_edge_cases.jsonl — {a}{b}, {}, no-tag keys; expects tag-on-first-only.
Pitfalls
  • CRC16 has many polynomial variants; Redis Cluster uses CRC16/CCITT-FALSE (poly 0x1021, init 0x0000, no reflection, xor-out 0x0000) — the wrong polynomial fails the parity test silently if all tests use only this project's own client (§13.5).
  • A hash tag is only the first {...} segment — {a}{b} hashes on a.
  • Jump consistent hash is biased for shard counts < 16 — document the floor; recommend the slot table for production (ADR-05).

⬜ Phase 2 — Shard Server & Multi-Protocol Wire §14

Objectives
  • Bring up a single shard server speaking Memcached binary (:11211), RESP3 (:6379), and gRPC (:50051) concurrently (P5), consuming the engine via the Engine trait (rank 59).
  • No cluster yet — the server serves every key it sees.
Deliverable
  • dcache-server listens on all three ports concurrently.
  • pymemcache and redis-py both operate against the same key space from the same server.
Acceptance
  • examples/pymemcache_demo.py: write + read-back round-trips a key (fixture-gated exit 0).
  • examples/redis_py_demo.py: write over RESP3, read back the same key (fixture-gated exit 0).
  • conformance buckets wire.memcached.frame and wire.resp3.frame: 100% of fixtures round-trip; 100% of malformed fixtures are rejected with the documented error code.
Fixtures
  • wire/memcached/*.bin — valid + malformed binary frames; expects round-trip or documented rejection.
  • wire/resp3/*.bin — valid + malformed RESP3 frames, including the HELLO 3 negotiation sequence.
Pitfalls
  • Every multi-byte Memcached field is big-endian — use u32::from_be_bytes, never a hand-rolled byte-swap (Reference Impl: Memcached).
  • RESP3 disables RESP2 as default after HELLO 3; track the negotiated version per-connection, never globally (Reference Impl: Redis).
  • gRPC's default 4 MiB max-message-size is below the 1 MiB value ceiling plus migration RPC overhead — configure 16 MiB headroom.
  • Engine::cas returns CasOutcome::Mismatch, not an error — conflating the two has caused at least one production incident in every deployed cache lineage (§8).

⬜ Phase 3 — Static Cluster Routing (MOVED) §15

Objectives
  • Bring up a static 3-node cluster with consistent-hash-derived ownership; membership and resharding are out of scope until §16/§18.
Deliverable
  • A 3-node make compose-up cluster routes correctly: a fixed key always lands on the same node.
Acceptance
  • A client hitting the wrong node receives Moved and successfully follows the redirect (fixture-gated, wire/resp3/moved_redirect.bin).
  • Slot distribution balanced to within 1 slot for equal weights (reuses §13.4's bound).
  • Zero requests silently dropped across 100,000 randomly routed requests in tests/integration/test_cluster_routing.rs.
Fixtures
  • wire/resp3/moved_redirect.bin / wire/memcached/moved_redirect.bin — a request to the wrong node; expects Moved with the correct target.
  • hash/redirect_loop_guard.jsonl — a client configured to retry past 5 redirects; expects a clear terminal error, not an infinite loop.
Pitfalls
  • The slot table is read-mostly — use ArcSwap, never a lock, on the hot path (P3).
  • A node returning Moved to itself is a configuration error — assert in debug, warn in release.
  • A stale client sees Moved storms after a topology change — cap retries at 5 redirects and surface a clear terminal error past that threshold (I6).
  • The hash-tag rule (§13) applies before slot calculation — test both tagged and untagged keys in the routing corpus.

⬜ Phase 4 — Gossip Membership §16

Objectives
  • Bring membership online via the delegated SWIM/Lifeguard crate (rank 72); this project integrates, it does not re-implement gossip (I5).
Deliverable
  • A 3-node cluster's nodes discover each other via gossip given only the first node's address; a 4th node joins by gossiping to any one of the existing three.
Acceptance
  • Killing a node produces a NodeFailed event in the coordinator's log within the configured grace period (default 30 s, ±5 s jitter tolerance).
  • Gossip convergence time for a 6-node cluster ≤ 2 s from a single seed contact (tests/integration/test_gossip.rs).
  • Gossip payload size per round ≤ 1 KiB regardless of cluster size (fanout-bounded, §34 C6).
Fixtures
  • coordinator/gossip_join.jsonl — a new node's join sequence; expects convergence within the acceptance bound.
  • coordinator/gossip_false_positive.jsonl — a slow-link scenario; expects Lifeguard's refute mechanism to suppress the false failure report.
Pitfalls
  • Gossip says "no probe has failed recently," never "this node is alive with certainty" — never use it as ownership source of truth (I5, MM2).
  • The NodeFailed grace period trades spurious failovers (too short) against slow real recovery (too long); 30 s is the documented starting point (§4, M7).
  • Gossip's piggybacked metadata grows with cluster size uncapped without the 1 KiB cap — the coordinator broadcasts the slot table out-of-band instead of relying on gossip for it (Reference Impl: HashiCorp memberlist).

⬜ Phase 5 — Raft Coordinator & Topology §17

Objectives
  • Stand up the coordinator: a separate process (3-or-5-node Raft quorum, rank 39) owning the epoch, the committed SlotTable, membership reconciliation, replica assignments, and failover decisions (P2, ADR-07).
Deliverable
  • The coordinator binary is built and deployed via compose-up; a 3-node coordinator + a 3-node data plane elects a leader, commits an EpochAdvanced event on every topology change, and survives killing the coordinator leader.
Acceptance
  • Coordinator leader election completes within 5 s of a leader kill (M8).
  • Data-plane SlotTable snapshots converge to the coordinator's latest committed table within 2 s of a WatchTopology push (tests/integration/test_coordinator.rs).
  • Zero topology events accepted out of epoch order across 10,000 simulated events (I2).
Fixtures
  • coordinator/events/*.jsonl — event sequences; expects monotonic epoch advancement and correct failover selection (lowest-lag replica).
  • coordinator/leader_kill.jsonl — kills the Raft leader mid-stream; expects re-election within M8's bound and zero lost committed entries.
Pitfalls
  • The coordinator must never share hosts with the data plane in production — a correlated failure of both is far harder to recover from (§24, FM-8).
  • An un-snapshotted Raft log grows unbounded — the 10,000-entry snapshot interval is provided by rank 39, not reimplemented here.
  • The data plane and coordinator must agree on epoch monotonicity (I2): a node that has observed Epoch(n+5) must never accept a write tagged Epoch(n) afterward — assert this in the data path, not just document it.

⬜ Phase 6 — Online Slot Migration §18

Objectives
  • Implement the four-phase migration state machine (§8) guaranteeing exactly one authoritative node per slot at every instant, with at most one client redirection per request during the window (P4, ADR-11).
Deliverable
  • dcache-cli migrate <slot> --from <node> --to <node> initiates and completes a migration under continuous load with zero failed requests.
Acceptance
  • benchmarks/reshard/online_reshard.rs: YCSB-A through a 100-slot migration reports zero error responses; p99 stays within 1.5× baseline (M5).
  • Every migration scenario in migration/*.json produces the documented end-state (I4-verified).
  • A migration that is rolled back mid-DoubleWrite leaves the source as sole authoritative owner within one grace period, zero data loss on already-committed keys.
Fixtures
  • migration/happy_path.json — full Importing→Cutover; expects final ownership at destination, zero dropped writes.
  • migration/rollback_mid_doublewrite.json — expects source reverts to Importing, dest evicts, zero corruption.
  • migration/concurrent_cas_during_doublewrite.json — a CAS race on both sides; expects I3-consistent resolution.
Pitfalls
  • The double-write window is the bug zone: a write hitting the source after the destination is added but before the source knows about the migration is a lost write — the state machine must guarantee the destination knows before double-writing starts.
  • Conflating Ask and Moved client-side causes infinite redirect spam in one direction or the other (I6, §15.6).
  • scan_slot's stream must be snapshot-isolated under concurrent writes (I10) — a non-isolated scan silently drops or duplicates keys mid-migration.
  • A CAS success on the source during DoubleWrite must replicate as a CAS, not a blind Set, so a concurrent CAS on the destination still respects the new value's CAS (I3).

⬜ Phase 7 — Primary-Replica Replication §19

Objectives
  • Bring up async primary→N-replica replication with per-replica lag tracking and lag-aware read routing (P8, ADR-08).
Deliverable
  • A 3-shard cluster, 1 replica per shard, runs continuous load; killing a primary triggers failover within the grace period, losing at most the documented async-replication window of unacknowledged writes.
Acceptance
  • Replication lag p99 < 100 ms at 100 KQPS write load (M6).
  • Failover completes within 30 s (M7) with zero acknowledged writes lost (tests/integration/test_replication.rs).
  • Dashboard shows per-replica lag in milliseconds, refreshed every second.
Fixtures
  • replication/lag_convergence.jsonl — a replica joining under steady load; expects lag to converge monotonically to near-zero.
  • replication/failover_no_loss.jsonl — kills the primary mid-load; expects zero acknowledged-write loss within the documented SLA.
Pitfalls
  • Async replication can lose acknowledged writes on primary failure — this is the documented tradeoff (ADR-08, FM-6), not a bug; customers needing stronger guarantees use write-back+WAL or a future sync-replication mode (§37).
  • The replication ring buffer must survive a slow replica within its bounded size; a replica that falls too far behind is forced into a snapshot rebase, not an unbounded buffer grow.
  • Lag is measured against the primary's monotonic seq counter, never wall-clock — clock skew between nodes must never leak into the lag computation (MM4).

⬜ Phase 8 — Coherency Policies §20

Objectives
  • Implement all five coherency policies — write-through (default), write-back, write-around, refresh-ahead, read-through — configurable per namespace (ADR-12).
Deliverable
  • All five policies exercised by examples/coherency_demo.rs against a running cluster.
Acceptance
  • conformance bucket coherency.policies: each policy's documented invariant holds across its recorded backing-store call sequence (fixture-gated, 100% pass).
  • Write-back with no WAL configured refuses to start (I7, exit code non-zero, clear error message).
  • Refresh-ahead reduces p99 read latency for a key within 10% of its TTL by ≥ 30% versus a cold read-through baseline (measured in coherency_demo).
Fixtures
  • coherency/write_through.jsonl, write_back.jsonl, write_around.jsonl, refresh_ahead.jsonl, read_through.jsonl — one fixture per policy; each records the expected backing-store call sequence.
  • coherency/write_back_no_wal.jsonl — expects a startup refusal, not a silent fallback.
Pitfalls
  • Write-back without a WAL is not write-back — it is "we lose your data on cache restart"; refuse to start rather than silently degrade (I7).
  • Refresh-ahead can amplify backing-store load under hot-key conditions; combine with single-flight (§21).
  • Read-through has the thundering-herd problem out of the box on a cold cache; combine with single-flight and XFetch (§21).

⬜ Phase 9 — Hot-Key Mitigation & Stampede Protection §21

Objectives
  • Land the full mitigation stack against the motivating workload: 50,000 hot keys hammered by 10,000 clients each, with a backing store serving ≤ 5,000 misses/second (P9).
Deliverable
  • benchmarks/hot_key/50k_hotkeys.rs runs against a 6-node cluster with no per-node latency degradation beyond the documented bound.
Acceptance
  • 50,000 hot keys × 1,000 QPS each (50M QPS aggregate demand): aggregate p99 ≤ 2 ms, no node exceeds 1.2× baseline latency degradation (M4).
  • Single-flight coalescing factor ≥ 100:1 under the 50K-hot-key load (M11, §34 C9).
  • XFetch's observed refresh probability matches the analytical curve within 5% (stampede/xfetch.jsonl).
Fixtures
  • stampede/xfetch.jsonl — sampled (now, expires_at, beta) triples; expects observed vs. predicted probability within 5%.
  • coherency/single_flight_coalescing.jsonl — N concurrent identical requests; expects exactly 1 upstream call.
Pitfalls
  • Count-min sketch is approximate: false positives (cold keys flagged hot) are tolerable, false negatives (hot keys missed) are not — tune cms_width/cms_depth accordingly (ADR-14).
  • Single-flight inside one client process does not coalesce across processes — two co-located client processes still issue two upstream requests (HQ10, deferred at §37).
  • XFetch's beta is the most consequential parameter: 1.0 is the paper's default; cache workloads benefit from beta ∈ [0.5, 1.5] — surface the recommended value from observed hit rate and miss latency.

⬜ Phase 10 — Auth, TLS, ACL & Operability §22

Objectives
  • Land the security and operability surface: TLS, per-namespace ACL, audit log, slow-log, the CLI dashboard, and the admin CLI (P13).
Deliverable
  • Every admin CLI command runs successfully against a compose-up cluster; the dashboard backend serves JSON at :8080/api/...; TLS is on by default in docker-compose.yml.
Acceptance
  • ACL check adds ≤ 5 µs p99 per command with the connection-level cache warm (M12).
  • A revoked-namespace ACL denies within one gossip interval of the revocation (I9, fixture-gated).
  • The audit log's HMAC chain verifies across a simulated daily rotation (tests/integration/test_audit_chain.rs).
Fixtures
  • coordinator/acl_revocation.jsonl — a revoked principal; expects denial within I9's bound.
  • coordinator/audit_chain_rotation.jsonl — a rotation event; expects unbroken HMAC chain.
Pitfalls
  • mTLS misconfiguration is silent: a node unable to authenticate to the coordinator can run forever as a useless data plane — add a startup smoke test that verifies the handshake.
  • ACL denial latency is user-visible — cache the per-connection evaluation; never re-evaluate the full ACL per command (only the cheap namespace-prefix check, §22.2).
  • The audit log's HMAC chain breaks if a record is dropped — the rotation procedure must preserve chain continuity across files (I12).

⬜ Phase 11 — Benchmarks (YCSB) & Chaos Engineering §23

Objectives
  • Land the validation surface: YCSB macro-benchmarks and the Jepsen-style chaos harness, gating the M-table (§30) and proving the invariants (§7) under adversarial conditions.
Deliverable
  • make bench runs all four YCSB workloads, emitting results to benchmarks/results/<date>/<workload>.json; make chaos runs the seven scenarios with a per-scenario verdict.
Acceptance
  • 6-node cluster sustains ≥ 10M GET/s with p99 ≤ 2 ms (M2, M3).
  • All seven chaos scenarios report the documented expected outcome (e.g. kill-primary: failover ≤ 30 s, zero acknowledged writes lost).
  • 24-hour soak: zero unhandled exceptions, memory growth ≤ 5% (M9).
Fixtures
  • chaos/kill_primary.json, kill_replica.json, partition.json, slow_link.json, crash_coordinator.json, corrupt_replication_record.json, lose_slot_mid_migration.json — one fixture per scenario; each records the expected system-state trajectory.
Pitfalls
  • YCSB's default Zipfian skew makes the hottest 1% of keys carry 99% of traffic — tune the skew to the workload under study; do not assume the defaults represent production.
  • Chaos scenarios needing tc/iptables require root or Linux capabilities — document the requirement and provide a Compose-based scenario subset that runs without root.
  • A benchmark run from a cold cache produces optimistic numbers before the slab allocator warms up — always include and record a warm-up phase duration in the result schema.
