⬜ Phase 0 — Repository Bootstrap & Deterministic Runtime Kernel §12

Objectives
  • Establish repository topology (§10) and workspace tooling.
  • Implement the deterministic logical clock and event loop (P1, P7).
  • Define the Scheduler trait contract (§11) and a FIFO reference implementation.
  • Define replay-hash identifiers and correlation-ID scheme.
  • Stand up the correctness kernel that every later phase depends on.
Deliverable

A runnable deterministic runtime capable of executing no-op transactions end-to-end (Created → Running → Committed) with a FIFO scheduler and a byte-serialized replay trace.

Acceptance
  • Deterministic replay hash (I2) identical across 100 runs of fixtures/runtime/basic.json.
  • Zero ThreadSanitizer/loom race-condition failures in CI.
  • CI green on Linux and macOS runners (ADR-09).
  • Startup time < 2 s (M4, §4).
Fixtures
  • fixtures/runtime/basic.json — 10-transaction no-op workload.
  • fixtures/runtime/replay_seed.json — seed-sensitivity regression fixture.
  • fixtures/runtime/crash_bootstrap.json — crash-during-bootstrap fixture (feeds Phase 7, §19).
Pitfalls
  • Non-monotonic clock updates (violates I6).
  • Randomized iteration ordering hiding in a HashMap (violates P6).
  • Async task starvation under Tokio's default scheduler (mitigate via LocalSet, ADR-02).

⬜ Phase 1 — Write-Ahead Log & Persistence Simulation §13

Objectives
  • Implement append-only WAL semantics (P9) with checksummed segments.
  • Implement replay reconstruction from WAL alone (MM6).
  • Implement crash-truncation detection and quarantine (not silent skip, per FM-1).
Deliverable

A crash-recoverable, replayable WAL engine whose recovery reconstructs exactly the set of committed transactions, byte-identically, from the WAL alone.

Acceptance
  • Recovery reconstructs 100% of committed transactions across fixtures/wal/wal_partial_segment.bin.
  • Corruption-detection coverage > 99% (M14, §28) on injected-fault runs.
  • WAL append throughput ≥ 100 MB/s simulated (M6, §4).
Fixtures
  • fixtures/wal/wal_partial_segment.bin
  • fixtures/wal/wal_corrupt_crc.bin
  • fixtures/wal/wal_checkpoint_gap.bin
Pitfalls
  • Partial-record visibility during scan (torn writes).
  • Replay-ordering drift if segment rollover races checkpoint metadata.

⬜ Phase 2 — Lock Manager: Strict Two-Phase Locking & Deadlock Detection §14

Objectives
  • Implement strict 2PL with a shared/exclusive/update/intent compatibility matrix (§11 LockMode).
  • Implement wait-for-graph deadlock detection that never mutates scheduler state (I4).
  • Implement lock escalation and starvation metrics.
Deliverable

A concurrent (simulated) lock manager with full replay support: identical seed reproduces an identical wait-for graph and identical victim selections.

Acceptance
  • Deadlock detection completes within 50 ms on fixtures/lockmgr/deadlock_triangle.json (tighter than the p99 M3 target of 10ms is aspirational; 50ms is the fixture-level gate).
  • Zero orphaned locks after rollback (I3) across all lockmgr fixtures.
Fixtures
  • fixtures/lockmgr/deadlock_triangle.json
  • fixtures/lockmgr/starvation_queue.json
  • fixtures/lockmgr/escalation_threshold.json
Pitfalls
  • Queue-reordering bugs that break P6's deterministic wake order.
  • Lost wakeups on lock release (violates I3's "no orphaned wait queue entries").
  • Recursive/self-referential deadlock cycles (self-deadlock, §14.8).

⬜ Phase 3 — MVCC Engine: Version Chains & Snapshot Visibility §15

Objectives
  • Implement append-only version chains (§11 VersionNode) honoring I5 (acyclic).
  • Implement the visibility evaluator as a pure predicate (I9, P5).
  • Implement epoch-based vacuum honoring I10 (never reclaims a visible version).
Deliverable

A serializable-capable version-visibility runtime (SI by default per ADR-17) where identical snapshots always see an identical version set (I9).

Acceptance
  • Snapshot visibility deterministic (I9) across fixtures/mvcc/snapshot_visibility.json.
  • Vacuum preserves all active snapshots (I10) across fixtures/mvcc/vacuum_race.json.
  • Storage amplification < 4x (M9, §4) on the 1M-record baseline.
Fixtures
  • fixtures/mvcc/snapshot_visibility.json
  • fixtures/mvcc/write_skew.json (feeds Phase 6's anomaly matrix, §18)
  • fixtures/mvcc/vacuum_race.json
Pitfalls
  • Premature vacuum (violates I10).
  • Snapshot leakage (a snapshot outlives its transaction's TxnState::Committed transition).
  • Dangling version references after a chain-append race.

⬜ Phase 4 — Optimistic Concurrency Control (OCC) §16

Objectives
  • Implement the Kung & Robinson (1981) read/validate/write phase model.
  • Guarantee validation-phase atomicity (I11): no two conflicting write sets both commit.
  • Measure validation overhead against the M11 budget.
Deliverable

An OCC engine where, under fixtures/occ/validation_conflict.json, exactly one of two conflicting transactions commits and the other aborts deterministically by seed.

Acceptance
  • Zero double-commits (I11) across 10,000 simulated conflicting-pair runs.
  • Validation-phase overhead < 5% of transaction wall time at low contention (M11, §28).
Fixtures
  • fixtures/occ/validation_conflict.json
  • fixtures/occ/backoff_storm.json
  • fixtures/occ/read_set_growth.json
Pitfalls
  • Unbounded read-set growth under long-running read-heavy transactions.
  • Validation storms under high contention (near-100% abort rate, FM-7).
  • Missing commit-serial-number gap check (silently permits I11 violation).

⬜ Phase 5 — Serializable Snapshot Isolation (SSI) & Dangerous-Structure Detection §17

Objectives
  • Build the rw-conflict dependency graph (Adya 1999 G2-item generalization).
  • Implement dangerous-structure detection per Cahill, Röhm & Fekete (2008).
  • Guarantee I8: serialization-graph edges are immutable post-commit.
Deliverable

An SSI validator with rollback support that rejects every known dangerous-structure fixture while committing all non-anomalous concurrent histories.

Acceptance
  • 100% of fixtures/ssi/dangerous_structure.json cases rejected.
  • 100% of fixtures/ssi/phantom_cycle.json cases rejected.
  • Conflict-edge ingestion ≥ 100k edges/sec (M10, §28).
Fixtures
  • fixtures/ssi/dangerous_structure.json
  • fixtures/ssi/phantom_cycle.json
Pitfalls
  • Missing edge registration before a concurrent commit validates (root cause of FM-6).
  • Validation races between two pivot-adjacent transactions.

⬜ Phase 6 — Isolation-Level Matrix & Anomaly Conformance Suite §18

Objectives
  • Implement the full RU/RC/RR/SI/Serializable isolation-level matrix (§11 IsolationLevel).
  • Reproduce, on demand, every Berenson et al. (1995) P0–P3 phenomenon and every Adya (1999) G0–G2 anomaly.
  • Wire txsim-conformance to assert level-vs-anomaly admissibility per the matrix.
Deliverable

A conformance matrix: for every (isolation level, engine, anomaly fixture) triple, an admit/reject verdict matching the Berenson/Adya oracle.

Acceptance
  • 100% oracle match across fixtures/isolation/matrix.json (isolation-level × anomaly cross product, ≥20 cells).
  • Write-skew fixture: admitted under SI, rejected under Serializable (SSI engine) — exact match to Fekete et al. (2005).
Fixtures
  • fixtures/isolation/matrix.json
  • fixtures/isolation/write_skew_matrix.json
  • fixtures/isolation/read_only_anomaly.json
Pitfalls
  • Conflating "uses MVCC" with "is Serializable" (MM1) — the single most common blueprint-review error in this domain.
  • Missing the read-only-anomaly fixture (frequently omitted; Fekete et al. 2005's key contribution beyond plain write-skew).

⬜ Phase 7 — Deterministic Replay, Time-Travel Debugging & Failure Injection §19

Objectives
  • Build the replay executor consuming WAL + scheduler trace only (MM6).
  • Implement binary-search replay narrowing to localize divergence within 5 events (M12).
  • Implement deterministic crash coordinates (I14) via txsim-crash.
Deliverable

A replay debugger that, given two runs with a hash mismatch, localizes the first divergent event within 5 events using binary search.

Acceptance
  • Divergence localized within 5 events (M12) on fixtures/replay/replay_divergence.json.
  • Recovery for a 10 GB WAL completes within 30 s (M8, §4) on fixtures/replay/crash_mid_commit.json scaled fixtures.
Fixtures
  • fixtures/replay/replay_divergence.json
  • fixtures/replay/crash_mid_commit.json
Pitfalls
  • Hidden nondeterminism surviving from Phase 0 (e.g., a newly introduced HashSet iteration).
  • Replay drift introduced by a vacuum sweep (§15) not itself being deterministic.

⬜ Phase 8 — Replication Lag Simulation & Distributed Consistency Verification §20

Objectives
  • Implement a single-leader logical-replication apply queue with injectable lag.
  • Build a consistency verifier detecting replica divergence.
  • Generalize snapshot-visibility reasoning (MM8) to bounded-staleness replica reads.
Deliverable

A primary-replica simulator where injected lag produces a detectable, quantified divergence window, never an undetected silent divergence.

Acceptance
  • Replica divergence detectable within one apply-queue drain cycle on fixtures/replication/lagged_replica.json.
  • Apply-queue lag under injected fault is bounded and reported (M13, §28), never silently dropped.
Fixtures
  • fixtures/replication/lagged_replica.json
  • fixtures/replication/split_brain_replay.json
Pitfalls
  • Apply-order drift: a replica applying WAL records out of primary commit order (would violate the I7 generalization above).

⬜ Phase 9 — Observability, Conformance Harness & Release Hardening §21

Objectives
  • Finalize txsim-observability metrics/tracing/export surface (P8 closure).
  • Build the full txsim-conformance differential harness, including an elle-style black-box anomaly inferencer (Kingsbury & Alvaro 2020).
  • Harden the release pipeline (§27) for first tagged release.
Deliverable

A tagged v1.0 release: black-box (elle-style) and white-box (engine-internal) anomaly verdicts agree on 100% of the fixture corpus; full observability surface live; signed release artifacts.

Acceptance
  • Black-box/white-box verdict agreement = 100% across fixtures/isolation/matrix.json (reused from §18).
  • Dependency-audit gate green; SBOM generated for the release tag.
  • Corruption-detection coverage > 99% (M14) re-verified against the frozen v1 WAL schema.
Fixtures
  • reuses fixtures/isolation/matrix.json (§18.5) plus conformance/elle_history_corpus.json.
Pitfalls
  • Black-box/white-box disagreement masking a real engine bug behind "it's just a different detection method" rationalization.
