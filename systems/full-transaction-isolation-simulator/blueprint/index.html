Project Number: 211

Project Name: Full Transaction Isolation Simulator from Scratch

Status: specification — locked

1. Goal & Scope

Engineering definition: a deterministic, byte-replayable simulator that executes synthetic transactional workloads under four pluggable concurrency-control engines (strict-2PL, MVCC, OCC, SSI) and validates the resulting histories against the ANSI/Berenson phenomena taxonomy (§18) and the Adya (1999) generalized anomaly taxonomy, producing conflict/serialization graphs, replay artifacts, and anomaly verdicts identical across runs given an identical seed.

Phase-0 deliverable — module/crate list (see §10 for the full tree):

  1. txsim-core — shared types, error taxonomy, IDs
  2. txsim-runtime — deterministic clock + event loop + scheduler authority
  3. txsim-scheduler — interleaving policies (FIFO, randomized, adversarial, priority, starvation)
  4. txsim-lockmgr — strict-2PL lock manager, wait-for graph, deadlock detection
  5. txsim-mvcc — version chains, snapshot visibility, vacuum
  6. txsim-occ — optimistic concurrency control (read/validate/write phases)
  7. txsim-ssi — serializable snapshot isolation, dangerous-structure detection
  8. txsim-wal — write-ahead log segment format, checksums, replay scanning
  9. txsim-storage — storage version manager, persistence simulator
  10. txsim-replay — deterministic replay engine, divergence localization
  11. txsim-crash — crash/fault injection hooks, deterministic crash coordinates
  12. txsim-observability — metrics, tracing, timeline + conflict-graph export
  13. txsim-fixtures — conformance fixture loader/generator
  14. txsim-conformance — anomaly test harness (Berenson/Adya/elle-style checks)
  15. txsim-cli — CLI entrypoint (workload compiler + fixture loader + subcommands)

System boundaries:

  • Provides: deterministic execution of synthetic transaction workloads; 2PL/MVCC/OCC/SSI engines; isolation-level conformance verdicts (RU/RC/RR/SI/Serializable); serialization-graph construction and cycle/dangerous-structure detection; WAL + crash-recovery simulation; deterministic replay and divergence localization; single-leader replication-lag simulation.
  • Delegates: real disk I/O durability guarantees (simulated only, §4); real network transport (simulated apply queues only, §20); cryptographic signing of release artifacts (delegated to standard toolchain, §27).
  • Does NOT provide: a query optimizer, a full SQL parser, cost-based planning, a columnar execution engine, a production-grade storage engine, distributed consensus, or multi-tenant security boundaries (all PhaseDeferred("§35")).

Non-goals: production OLTP throughput; SQL compatibility; a general-purpose database product.

Deployment model: single-node deterministic runtime; multi-process simulation harness for comparative runs; CI-driven replay validation; local developer workstation execution; containerized benchmarking (ADR-10).

Target users: database engineers, distributed-systems engineers, concurrency-control researchers, storage-engine developers, performance engineers, advanced systems students.

Language: Rust 1.82+. Rationale: ownership model gives compile-time data-race detection for the lock-free structures in §11; mature async runtime (ADR-02); strong fuzzing/property-testing tooling (ADR-08); reproducible binary generation (§27). Rejected: Go (GC pauses interfere with p99 latency targets, §4), C++ (no compile-time aliasing guarantees for the shared lock table, §14).

Prerequisites: OS internals, database internals, concurrency-control theory, transaction processing theory, WAL semantics, lock-free programming, CPU cache behavior, memory models, failure-recovery semantics, testing methodology.

Timeline: Phase 0 MVP — 10 weeks; full ten-phase platform — 9–14 months; production-quality observability/replay tooling — 4 additional months (see §38 for per-phase durations).

Deferred features (full register at §35): distributed Raft-backed replication PhaseDeferred("§35"); WAN/geo latency injection PhaseDeferred("§35"); HTAP execution model PhaseDeferred("§35"); GPU-accelerated conflict-graph analysis PhaseDeferred("§35"); full SQL parser/optimizer PhaseDeferred("§35"); multi-tenant security boundaries PhaseDeferred("§35"); columnar execution engine PhaseDeferred("§35").

2. Why Build This

Transaction isolation is taught abstractly (isolation-level names) but fails in production at the implementation seam: visibility-timestamp off-by-ones, lost wakeups in wait queues, missing rw-edge registration in SSI validators, WAL torn-write handling. This project forces the implementation-level knowledge that Berenson et al. (1995) and Adya (1999) formalized but that most engineers only encounter as documentation prose.

Unique systems knowledge exercised: lock-manager construction with wait-for-graph deadlock detection (§14); MVCC visibility resolution and vacuum-safety (§15); OCC validation-phase atomicity (§16); SSI dangerous-structure detection (§17); deterministic replay with divergence-localization (§19); WAL sequencing and ARIES-style recovery (§13); single-leader replication-lag anomalies (§20).

Architectural/historical significance: this system is a hands-on synthesis of three research lineages — classical locking (Eswaran et al. 1976, Bernstein/Hadzilacos/Goodman 1987), MVCC/OCC (Kung & Robinson 1981, Cahill/Röhm/Fekete 2008), and deterministic execution (Lamport 1978, Thomson et al. 2012/Calvin). Cross-links: shares its lock-manager shape with PostgreSQL's lmgr (§31); shares its deterministic-simulation philosophy with FoundationDB's simulation testing (§31); shares its timestamp-oracle tradeoffs with TiDB/CockroachDB (§31).

Calibration value: completing this project permanently improves concurrency-debugging ability, replay-driven debugging capability, lock-contention analysis, and the ability to distinguish "uses MVCC" from "is Serializable" (MM1, §30).

What Mastery Looks Like

  • Can explain, from first principles, why Snapshot Isolation permits write-skew while excluding ANSI P1/P2 phenomena — tied to Phase 5 (§17) and Phase 6 (§18).
  • Can implement a wait-for-graph deadlock detector that never mutates scheduler state (I4) — tied to Phase 2 (§14).
  • Can design a WAL format whose replay is byte-identical across 100 runs — tied to Phase 1 (§13) and Phase 7 (§19).
  • Can construct and prune a serialization graph and correctly classify a dangerous structure per Cahill/Röhm/Fekete — tied to Phase 5 (§17).
  • Can localize a replay divergence to within 5 events using binary-search narrowing — tied to Phase 7 (§19).
  • Can reason about bounded-staleness replica reads as a generalization of MVCC snapshot visibility (MM8) — tied to Phase 8 (§20).
  • Can build a differential conformance harness that reproduces Berenson/Adya anomalies on demand — tied to Phase 6 (§18) and Phase 9 (§21).

Workload Compiler: parses declarative workload definitions into deterministic execution DAGs; preserves semantic ordering so identical input compiles to an identical event stream.

Fixture Loader: reads conformance fixtures (§26) and replays them as workloads without going through the compiler's random-seed path.

Deterministic Runtime: sole authority for logical-time advancement (P1, I2); no subsystem below it may read the host wall clock or iterate a non-deterministic collection.

Scheduler: chooses interleaving order per §3's Coordination Layer input; supports FIFO, randomized, adversarial, priority, and starvation-injection modes (ADR selection irrelevant here — policy, not tech choice).

WAL: append-only mutation lineage; the only source of truth for recovery (MM6); crossed by every committing transaction before it becomes visible.

Transaction Coordination Layer: dispatches each transaction's operations to exactly one active concurrency-control engine per run (2PL, MVCC, OCC, or SSI) — engines are mutually exclusive per run, not composed (ADR-16).

Storage Version Manager: holds the canonical on-disk-simulated record representation independent of which CC engine is active; this is the trust boundary between concurrency semantics and bytes.

Recovery + Replay Engine: reconstructs execution state purely from WAL + scheduler trace (MM6); crash injection (txsim-crash) fires only at deterministic logical-clock coordinates (I14).

Metrics + Tracing + Export: one-way sink; never feeds back into scheduling decisions (keeps the Deterministic Runtime boundary closed).

6. Design Principles

P1. Determinism Over Throughput — Rule: every scheduling decision is a pure function of (seed, event history); no host-clock or OS-thread-scheduling dependency. Tradeoff: forgoes hardware parallelism that would introduce nondeterministic interleavings. Operational implication: concurrency is simulated by one logical scheduler (§12), not racing OS threads. Violation breaks: replay hashes (I2) diverge, invalidating every conformance fixture (§26).

P2. Replayability First — Rule: every executed event is serialized to the WAL before it is considered to have happened. Tradeoff: extra serialization cost on the hot path. Operational implication: txsim-replay never needs a second data source. Violation breaks: crash-mid-commit scenarios (FM-8) become unreconstructable.

P3. Crash-Only Recovery — Rule: there is exactly one recovery path — WAL replay — used both for planned restart and crash. Tradeoff: no fast "clean shutdown" shortcut. Operational implication: shutdown flush (§4, <5s) is the only optimization surface. Violation breaks: divergent recovery code paths that are individually undertested (FM-1).

P4. Bounded Memory Ownership — Rule: every subsystem declares a hard memory ceiling (§4) and enforces it locally. Tradeoff: may reject work rather than degrade gracefully. Operational implication: T4/T6 mitigations are per-subsystem caps, not global throttling. Violation breaks: one hot key can OOM the whole simulator.

P5. Explicit Visibility Semantics — Rule: visibility is a pure predicate over (snapshot_vector, VersionNode.begin_visibility_ts, end_visibility_ts) — never implicit ordering. Tradeoff: extra fields on every version. Operational implication: visibility bugs are always traceable to one predicate (MM2). Violation breaks: phantom stale reads.

P6. No Hidden Synchronization — Rule: no subsystem may use an OS primitive (mutex, condvar) whose wake order is not itself deterministic under the runtime's control. Tradeoff: some lock-free structures are replaced by scheduler-mediated queues. Operational implication: all "concurrency" bugs are event-order bugs, reproducible from the trace. Violation breaks: I2.

P7. Stable Event Ordering — Rule: identical (seed, workload) always produces an identical total order of events. Tradeoff: total order is a global bottleneck (§29). Operational implication: the Deterministic Runtime is a single serialization point. Violation breaks: replay narrowing (§19) has nothing stable to binary-search over.

P8. Observability by Default — Rule: every state transition emits a metric or span; nothing is invisible by default. Tradeoff: telemetry overhead on every hot path. Operational implication: §24 dashboards are populated from day one of Phase 0. Violation breaks: failure analysis (N.9) sections across every phase have no data to work from.

P9. Immutable WAL Semantics — Rule: a WAL record, once appended and checksummed, is never rewritten in place. Tradeoff: corrections require a compensating record, not a patch. Operational implication: I1 (WAL monotonicity) is trivially checkable. Violation breaks: replay determinism (I2) — a mutable WAL cannot be byte-identically replayed.

P10. Version Compatibility Preservation — Rule: VersionNode and WalRecord schemas are additive-only within a major version (§25). Tradeoff: dead fields accumulate until a major bump. Operational implication: fixtures from an old minor version keep replaying. Violation breaks: §25 compatibility guarantees.

P11. Backpressure Everywhere — Rule: every bounded queue (replay buffer, apply queue, event queue) rejects or blocks rather than silently drops when full. Tradeoff: throughput ceilings are explicit and lower. Operational implication: T3/T4/FM-12 all resolve to "apply backpressure," never "drop and hope." Violation breaks: silent data loss that no fixture can catch.

P12. Scheduler Authority Centralization — Rule: only txsim-scheduler (via txsim-runtime) may decide which transaction runs next. Tradeoff: no subsystem may "self-schedule" for local efficiency. Operational implication: deadlock detection (I4) can safely be read-only. Violation breaks: two subsystems racing to advance logical time — I2 fails.

P13. State Machine Transparency — Rule: every transaction's TxnState (§8) transition is externally observable and total order is preserved in the trace. Tradeoff: extra event volume. Operational implication: replay divergence (FM-4) always has a state-transition trail to diff. Violation breaks: opaque internal states that forensics (§23) cannot reconstruct.

P14. Invariant-Driven Development — Rule: every phase's acceptance criteria (N.4) must cite at least one invariant (§7) it upholds. Tradeoff: slower phase sign-off (invariant audit gate). Operational implication: §7's table is the release checklist, not documentation-after-the-fact. Violation breaks: invariants rot silently until a fixture accidentally catches the regression.

P15. Failure Injection as a Core Feature — Rule: txsim-crash fault hooks are first-class, versioned, and fixture-covered — not a debug-only afterthought. Tradeoff: extra API surface (FaultDescriptor, §11) to maintain. Operational implication: every phase (N.9 Failure Analysis) has an executable fault, not just a prose scenario. Violation breaks: failure modes (§23) that are described but never actually reproducible.

8. Domain Model / Protocol / Data Model

Transaction lifecycle state machine:

State Meaning Valid Predecessors
Created allocated but not scheduled —
Running executing operations Created, Waiting
Waiting blocked on a dependency (lock, validation) Running
Committing WAL durability phase Running
Committed durable and visible Committing
Aborted rolled back Running, Waiting, Committing
Replaying recovery reconstruction Committed, Aborted (historical)

Wire event grammar (EBNF, informal):

event      ::= begin | read | write | acquire | release | commit | abort | checkpoint | crash | recover
begin      ::= "BeginTxn" txn_id
read       ::= "Read" txn_id key
write      ::= "Write" txn_id key value
acquire    ::= "AcquireLock" txn_id resource mode
release    ::= "ReleaseLock" txn_id resource
commit     ::= "CommitTxn" txn_id
abort      ::= "AbortTxn" txn_id
checkpoint ::= "Checkpoint" seq
crash      ::= "Crash" coordinate
recover    ::= "Recover" seq

Worked example — snapshot visibility under SI:

  • T1 begins at begin_ts = 100 (snapshot_vector frozen at 100).
  • T2 commits V2 (a new version of key k) at commit_ts = 110.
  • Per I9, T1's visibility predicate is V2.begin_visibility_ts(110) > T1.snapshot_vector(100) → V2 is not visible to T1 for the remainder of T1's lifetime.

State-transition / sequence table — deadlock cycle:

Step Actor Action Wait-For Edge Added
1 T1 AcquireLock(R2, X) blocked by T2 T1 → T2
2 T2 AcquireLock(R3, X) blocked by T3 T2 → T3
3 T3 AcquireLock(R1, X) blocked by T1 T3 → T1
4 Detector cycle T1→T2→T3→T1 found —
5 Detector victim selected (I4: read-only report) —
6 txsim-lockmgr rollback emitted for victim —

Malformed-input example: CommitTxn(T5) observed before any BeginTxn(T5). Expected behavior: reject the workload at compile time (Workload Compiler, §3), emit a validation event, persist the rejected-workload replay artifact for forensics (matches T1's mitigation).

Failure-path example: a WAL segment's trailing record fails its checksum (I1) mid-scan during recovery. 25. Compatibility & Versioning

Wire/storage/schema evolution: WalRecord and VersionNode (§11) are additive-only within a major version (P10); a new variant requires a major bump.

API stability: Scheduler trait (§11) is stable within a major version; new methods are added via a default-implemented extension trait, never by breaking the existing signature.

SemVer: crate versions (§10) follow SemVer; the workspace is released in lockstep (single workspace version tag) to keep cross-crate ADR-24 error-taxonomy compatibility simple.

Deprecation: a deprecated WalRecord variant is retained (readable) for 2 major releases before removal, matching the compatibility guarantee already present in the source workload's requirements.

Rolling-upgrade guarantees: replay-fixture compatibility is preserved for 2 major releases (a fixture recorded under v1.x replays correctly under v2.x); stable event-schema IDs across the same window; deterministic serialization ordering preserved (P9/P10).

Concrete versioning example: WalRecord::Write (§11) gains an optional compression_hint field in v1.1 — additive, so a v1.0 fixture still replays under v1.1 (P10). A hypothetical removal of the tombstone field from VersionNode would require a v2.0 bump, a 2-major-release deprecation window per the guarantee above, and a corresponding update to every N.5 fixture referencing VersionNode serialization (§15.5, §17.5).

26. Testing & Verification Strategy

Unit testing: every visibility-rule predicate (I9) has a dedicated unit test per IsolationLevel variant.

Property testing: lock compatibility matrix (§14) is property-tested for the invariant "no two granted locks in the same LockEntry are mutually incompatible" (I3-adjacent).

Differential testing: txsim-conformance (§21) runs the same fixture through white-box engine verdicts and the elle-style black-box inferencer (Kingsbury & Alvaro 2020) and asserts agreement.

Fuzzing (ADR-08): WAL parser (§13) and workload-compiler parser (§12) are both libFuzzer targets under fuzz/.

Chaos injection: txsim-crash fault hooks (§19) fire during replay runs in CI as a scheduled chaos job, not only in unit tests.

Deterministic soak testing: a 24-hour soak run replays the same seed corpus nightly and asserts zero replay-hash drift (I2) — regressions here block release (T9/FM-4).

Crash-recovery validation: every Phase-1/Phase-7 fixture (crash_mid_commit.json, wal_corrupt_crc.bin) is re-run against every tagged release candidate.

Conformance: the full Berenson/Adya matrix (§18) is a release gate, not an optional suite.

Perf-regression gating: every M# target in §28 is a Criterion-benchmarked CI gate (ADR-11); a regression beyond the target blocks merge.

Traceability: every invariant (§7) maps to at least one test class above; every phase's N.5 fixtures feed both unit and conformance suites.

Regression corpus growth: every forensics artifact produced by an FM-# incident (§23) that is not already covered by an existing fixture is converted into a new fixture before the incident is closed — this is the mechanism by which the conformance corpus (§18, §26) grows over time rather than staying frozen at launch.

Test-environment parity: the same txsim-conformance binary runs identically in local development, CI (§27), and the nightly soak job — no environment-specific test doubles are permitted, since a test double would itself be a source of the P6-forbidden hidden nondeterminism.

29. Scalability Analysis

What stays constant vs. grows: per-transaction metadata (TransactionDescriptor, §11) is O(1) per txn by the §4 128 KB cap; version-chain depth grows with hot-key write rate (O(writes/key)) until vacuum bounds it (I10); the serialization graph (§17) grows with concurrent rw-conflict count, O(active txns²) worst case but O(active txns) in the sparse target workload (§32).

Named bottlenecks, in order: (1) serialization-graph growth under high write-concurrency (T5); (2) lock-table contention on hot keys (§14.7); (3) replay-scan amplification on large WAL (M7/M8); (4) snapshot-retention pressure from long-lived readers (T6); (5) scheduler coordination overhead as the single serialization point (P7, P12).

Subsystem Growth driver Big-O (worst case) Bounded by
Serialization graph (§17) concurrent rw-conflicts O(active txns²) conflict pruning, ADR-21
Lock wait-for graph (§14) hot-key skew O(waiters per resource) escalation, T4 cap
Version chains (§15) per-key write frequency O(writes per key) vacuum epoch, I10
Replay buffer (§19) unflushed event volume O(events since flush) backpressure, I12
WAL append (§13) write rate O(1) amortized/record fixed-size checksummed frames

The table's rightmost column is the concrete lever already implemented in the corresponding phase; none of these bottlenecks require an un-deferred feature (§35) to bound at the §4 target scale — they only become un-boundable beyond that scale, which is exactly the trigger condition recorded in §35's Un-defer Trigger column.

Horizontal scaling: deferred to the distributed-simulation phases (PhaseDeferred("§35")) — today's Phase 8 (§20) models only single-leader replication lag, not sharding.

Vertical scaling: bounded by the §4 2 GB memory ceiling; the practical ceiling today is ~10,000 concurrent simulated transactions with a ~1024-deep version-chain target before vacuum pressure (I10) dominates.

Levers beyond the ceiling: (a) tighten vacuum epoch granularity (ADR-20) to trade CPU for lower retention; (b) switch the serialization-graph representation from adjacency-list to a sharded per-key index once conflict density crosses the ADR-21 breakeven point; (c) un-defer distributed sharding (§35) once a single node cannot hold the target record count.

Constant-cost subsystems: TransactionDescriptor allocation (§11) is O(1) per transaction regardless of workload shape; WAL append (§13) is O(1) amortized per record given fixed-size checksummed frames (ADR-04); the FIFO scheduler's enqueue/next pair (§11) is O(1) per call.

Growing-cost subsystems, ranked by growth rate: the serialization graph (§17) grows fastest under adversarial write-heavy contention; the lock wait-for graph (§14) grows with hot-key skew; version chains (§15) grow with per-key write frequency until bounded by vacuum (I10); the replay buffer (§19) grows with unflushed event volume until bounded by backpressure (I12).

Sharding readiness: the storage version manager (§3) already partitions by resource_id internally, which is the same partition key a future sharded deployment (§35) would use — this is a deliberate design choice to make the eventual un-defer a partitioning change, not a rewrite.

30. Mental Models & First Principles

MM1. Isolation is a phenomenon-avoidance contract, not a mechanism. Predicts: different mechanisms (2PL, MVCC, OCC) can satisfy the same isolation level. Bug class without it: conflating "uses MVCC" with "is Serializable" (SI ≠ Serializable, write-skew). Resolving: §8, §18.

MM2. Snapshot visibility is a pure timestamp-range predicate. Predicts: visibility bugs are always begin_visibility_ts/end_visibility_ts off-by-one errors. Bug class: phantom stale reads from a mis-set end_visibility_ts. Resolving: §11, §15.

MM3. A cycle in the serialization graph is necessary and sufficient for a non-serializable history (Papadimitriou 1979). Predicts: SSI only needs to detect potential cycles (dangerous structures), not full cycles, to be conservative. Bug class: under-detection that misses G2-item anomalies. Resolving: §17.

MM4. Determinism is a closure property of the whole causal history, not any single component. Predicts: one nondeterministic HashMap iteration anywhere breaks global replay. Bug class: "mostly deterministic" replay hashes that pass 99/100 runs. Resolving: §12, I2.

MM5. Deadlock is a liveness property, not a correctness property. Predicts: a system can be always-correct (no anomalies admitted) yet always-live-locked. Resolving: §14, §23.

MM6. WAL is the source of truth; in-memory state is a cache of it. Predicts: recovery equals WAL replay, nothing more. Bug class: recovery logic that reconstructs state from something other than the WAL. Resolving: §13, §19.

MM7. Optimistic concurrency shifts conflict detection from acquisition-time to commit-time. Predicts: OCC has zero blocking but unbounded abort-and-retry under contention. Resolving: §16, §29.

MM8. Replication lag is a bounded-staleness read anomaly, structurally identical to a stale MVCC snapshot. Predicts: the same visibility-horizon reasoning used for snapshots (§15) applies to replicas (§20). Resolving: §15, §20.

SQLite differs by sidestepping concurrent-writer conflict entirely: WAL-mode allows one writer at a time, so it never needs a lock manager (§14) or SSI validator (§17) in the sense this project builds them; it wins wherever an application accepts single-writer throughput in exchange for near-zero operational complexity.

PostgreSQL differs by defaulting to Read Committed for backward compatibility and implementing SSI as an opt-in predicate-lock layer (Ports & Grittner 2012) rather than the primary engine; it wins wherever broad SQL compatibility matters more than pluggable CC-engine comparison.

CockroachDB differs by making Serializable the only isolation level and using hybrid logical clocks for external consistency across geo-distributed replicas; it wins in multi-region deployments where clients cannot tolerate any of Berenson's phenomena.

FoundationDB differs by treating determinism as a testing property (its deterministic simulation harness), not an execution property of production traffic; it wins wherever production performance must not be constrained by the same total-order discipline used to test it.

Calvin differs most fundamentally by eliminating runtime concurrency control altogether — transactions are ordered before execution by a sequencer, so no lock manager or validation phase exists at all; it wins in high-contention partitioned workloads where lock/validation overhead would otherwise dominate, at the cost of needing read/write sets known in advance.

32. Back-of-Envelope Capacity Model

  1. Lock-table memory: 10,000 concurrent txns (§4) × avg 2 held locks × ~128 B/entry ≈ 2.5 MB — under 0.2% of the 2 GB ceiling (§4).
  2. Version-chain memory: 1M records (§4) × steady-state avg depth 8 (well under the 1024 target) × (8 B payload_ref + 24 B metadata) ≈ 1,000,000 × 8 × 32 B = 256 MB — 12.5% of the 2 GB ceiling, motivating vacuum aggressiveness (ADR-20, I10).
  3. WAL write rate: 250k versioned writes/minute (§4) = 4,167 writes/sec × avg 256 B/record ≈ 1.07 MB/s — far below the 100 MB/s simulated append throughput (M6); WAL append is not the bottleneck at baseline load.
  4. Replay-buffer fill time: 256 MB cap (§4) ÷ 1.07 MB/s (step 3) ≈ 239 s of writes bufferable before backpressure (I12/P11) engages under baseline load.
  5. Recovery time for the RTO fixture: 10 GB WAL (§4) ÷ 500 MB/s replay scan throughput (§4) = 20 s — inside the < 30 s RTO target (M8), leaving ~10 s of margin for checksum overhead.
  6. Deadlock-detection budget: p99 target < 10 ms (M3) over up to 10,000 txns — with the sparse adjacency-list graph (ADR-21) at realistic conflict density, edge count tracks active conflicts, not O(n²), keeping the traversal inside budget.
  7. Conflict-edge ingestion bandwidth: 100k edges/sec (§4) × 16 B/edge (two 8 B txn IDs) = 1.6 MB/s serialization-graph growth rate — informs the T5/§29 bottleneck ranking.
  8. Storage-amplification ceiling: 1M logical records × < 4x target (M9) ⇒ ≤ 4M physical version slots before vacuum must reclaim to stay under target.
  9. Startup budget per crate: < 2 s total (M4) ÷ 15 crates (§10) ⇒ ≈ 133 ms average per-crate init budget, assuming roughly even initialization cost.

34. Alternative Architectures (Roads Not Taken)

A. Deterministic pre-ordering (Calvin-style).

Sequencer -> [batch epoch: fixed txn order] -> Execution replicas (no locks, no validation)

Wins in: partitioned OLTP with heavy, predictable contention. Embodied by: Calvin (Thomson et al. 2012). Rejected because: requires knowing each transaction's read/write set in advance, which is incompatible with this simulator's interactive/ad hoc Workload Compiler (§3) — the whole point is comparing engines that don't know the future.

B. Actor-per-key serialization (no shared lock table).

Key k1 -> Actor(k1) mailbox   Key k2 -> Actor(k2) mailbox   ...
Multi-key txn -> fan-out messages to each owning actor, await all replies

Wins in: high-key-cardinality, low-cross-key-transaction workloads. Embodied by: actor-model grain-per-entity in-memory systems (e.g., Orleans-style architectures). Rejected because: multi-key transactions require cross-actor coordination that reintroduces a lock-manager- equivalent complexity (§14) without the wait-for-graph tooling already built for it.

C. Optimistic-only, single global validation pass (no locks, no MVCC snapshots).

All reads unguarded -> single serializing validation pass at commit -> accept/reject

Wins in: read-mostly, low-contention analytic-style workloads. Embodied by: the original Kung & Robinson (1981) OCC prototypes. Rejected because: it cannot cheaply reproduce lock-based anomalies (starvation, deadlock) that are core teaching goals of this project (§2).

D. CRDT / conflict-free convergence (no isolation levels at all).

Replica A --merge(commutative op)--> converged state <--merge(commutative op)-- Replica B

Wins in: offline-first collaborative applications. Embodied by: CRDT modules in systems like Riak/Redis. Rejected because: this project's scope (§1) is transaction isolation semantics — CRDTs sidestep isolation by construction rather than model or test it.

36. Glossary

  • 2PL: Two-Phase Locking — growing phase (acquire only) followed by shrinking phase (release only).
  • ADR: Architecture Decision Record.
  • Adya anomaly (G0–G2): generalized isolation anomalies per Adya (1999), defined over dependency graphs rather than lock behavior.
  • ARIES: Algorithm for Recovery and Isolation Exploiting Semantics (Mohan et al. 1992).
  • Backpressure: refusing/blocking new work when a bounded resource is full, rather than silently dropping it (P11).
  • Cascading abort: an abort that forces the abort of dependent transactions.
  • Compatibility matrix: table of which lock modes may be held concurrently on one resource.
  • Conflict graph / serialization graph: directed graph of transactions with an edge for each ww/wr/rw conflict; acyclicity implies conflict-serializability (Papadimitriou 1979).
  • Conformance fixture: a versioned input/expected-output pair used to gate correctness.
  • Correlation ID: an identifier threading a logical operation across spans/events.
  • Dangerous structure: the two-consecutive-rw-edge pattern SSI rejects (Cahill et al. 2008).
  • Deadlock: a cycle in the wait-for graph; a liveness failure, not a correctness failure (MM5).
  • Determinism: identical (seed, input history) always produces an identical execution trace.
  • Dirty read (P1): reading an uncommitted write.
  • Dirty write (P0): overwriting an uncommitted write.
  • Elle: black-box isolation-anomaly inference tool/technique (Kingsbury & Alvaro 2020).
  • Escalation: promoting a lock's granularity (e.g., row → table) under contention.
  • Fixture poisoning: tampering with a conformance fixture to corrupt its expected verdict.
  • G0 (write cycle): a cycle among only write-write dependencies (Adya 1999).
  • G1a/b/c: Adya's aborted-read, intermediate-read, and circular-information-flow anomalies.
  • G2 / G2-item: Adya's anti-dependency-cycle anomaly, generalizing write-skew.
  • HLC: Hybrid Logical Clock.
  • Isolation level: a named contract (RU/RC/RR/SI/Serializable) bounding which phenomena a system permits.
  • Lost update: two transactions read-modify-write the same key, and one overwrite is lost.
  • MVCC: Multi-Version Concurrency Control.
  • Non-repeatable read (P2): a value read twice by the same transaction differs.
  • OCC: Optimistic Concurrency Control (Kung & Robinson 1981).
  • P0–P3: Berenson et al. (1995) phenomena — dirty write, dirty read, non-repeatable read, phantom.
  • Phantom (P3): a repeated range query returns a different row set.
  • Predicate lock: a lock over a query predicate rather than a specific row (Eswaran et al. 1976).
  • Read-only anomaly: a read-only transaction observes a non-serializable state despite every individual writer being serializable (Fekete et al. 2005).
  • Read skew: a transaction's reads are individually valid but mutually inconsistent.
  • Replay divergence: two runs of the same (seed, input) produce different replay hashes.
  • RTO: Recovery Time Objective.
  • RU/RC/RR/SI: Read Uncommitted / Read Committed / Repeatable Read / Snapshot Isolation.
  • Serializability: equivalence to some serial (non-interleaved) execution order.
  • SIREAD lock: PostgreSQL's SSI read-tracking lock (Ports & Grittner 2012).
  • Snapshot horizon / visibility horizon: the maximum commit timestamp visible to a snapshot.
  • Split brain: two replicas independently diverge from a shared history.
  • SSI: Serializable Snapshot Isolation.
  • Starvation: indefinite delay of a transaction despite the system remaining live overall.
  • Tombstone: a marker for a deleted version, retained until vacuum-eligible.
  • Torn write: a partially-written record observable after a crash mid-write.
  • TSO: Timestamp Oracle (centralized timestamp allocator, e.g., TiDB/Percolator-derived).
  • Vacuum: reclamation of version-chain entries no longer visible to any active snapshot.
  • Victim (deadlock): the transaction chosen to abort to break a detected cycle.
  • Wait-for graph: directed graph of "transaction A waits for transaction B" edges.
  • WAL: Write-Ahead Log.
  • Write skew: two transactions each read a value the other writes, both commit under SI, violating an invariant that spans both rows.
  • Anti-dependency: a rw-conflict edge, i.e., transaction A reads a value that transaction B later overwrites; the raw material of Adya's G2/G2-item anomalies.
  • Checkpoint: a WAL marker recording the set of active transactions at a point in time, bounding replay's redo scan range.
  • Commit dependency: a transaction's commit is contingent on another transaction's prior commit outcome (used to reason about cascading aborts).
  • Conformance matrix: the isolation-level × anomaly × engine cross-product table (§18) used as the release-gating correctness oracle.
  • Degrees of consistency: Eswaran et al.'s (1976) predecessor terminology to modern isolation levels.
  • Logical clock: a monotonic counter used in place of wall-clock time to establish a happens-before order (Lamport 1978).
  • Timestamp oracle (TSO): a centralized service issuing globally ordered timestamps, as used in Percolator-derived designs (§31).

Canonical-home note: the list above is the single canonical home for every domain term used across §1–§35 and §37–§38; no other section defines a term without a forward or backward reference to this list.

  • Correlation ID scope: a correlation ID is scoped to one logical transaction's lifetime (§8), never reused across a retry — a retried transaction is issued a fresh txn_id and a fresh correlation ID, keeping forensics (§23) unambiguous per attempt.
  • Fixture corpus: the union of every fixtures/**/*.json and fixtures/**/*.bin file referenced across §12–§21's N.5 subsections plus §18's isolation matrix and §21's elle corpus.
  • AnomalyVerdict: the shared enum (§11) returned by both the white-box (§18) and black-box (§21) conformance oracles, making their outputs directly diffable.
  • MetricsSink: the one-way telemetry trait (§11) that P8 forbids from feeding back into any scheduling decision.
