In one paragraph

A load balancer sits in front of a group of servers and decides, for every incoming connection or request, which server should handle it. This design is one Rust binary that does that for raw TCP and UDP and for HTTP/1.1, HTTP/2, HTTP/3 and gRPC (§1). It adds ten selection algorithms, server discovery, active and passive health checks, TLS, routing, rate limiting, circuit breaking, telemetry, and an admin API that reloads configuration without dropping requests (§1, §3). Platform/SRE teams run it as one node, a failover pair or a consistent-hash fleet at their own edge or internal L7 tier (§1). Its defining property: "a tail-latency game on the data path and a correctness game on the control plane" (§4).

The problem, concretely

Put several copies of a server behind one address and the blueprint names the failures that recur across HAProxy, NGINX, Envoy and Pingora deployments: a flapping health check evicting healthy backends, TCP backpressure inverting under file-descriptor exhaustion, and a config reload silently dropping in-flight long-lived gRPC streams (§2). Three naive answers make these worse. Handing out servers in a fixed rotation (round-robin) ignores how slow each server currently is, so it "degrades badly the moment backends are heterogeneous in speed, even briefly" (MM1). Assigning a client by hash(key) % N looks fine in a demo and then reshuffles nearly every key the moment N changes, which shows up as cache stampedes or session loss (MM4). Mutating a shared configuration map in place during a reload "will eventually drop in-flight requests"; the blueprint's canonical example is a reload that dropped 12,000 gRPC streams (P2, MM3). The design answers each one: choose servers under uncertainty, move as few keys as possible when the set changes, and treat configuration as an immutable value.

How it works, end to end

The blueprint's architecture diagram separates an in-process control plane from a one-way data path (§3):

 Admin API (§22): reload · drain · stats · config
        │
 Control plane (in-process): ConfigSnapshot behind ArcSwap (I1, I2) · discoverers → BackendPool (§14)
                             · health checkers (§17) · two-phase reloader (§22)   — never blocks the data path (P4)
        │
 Listeners: TCP/UDP (§13) · HTTP/1.1 (§13) · HTTP/2 (§23) · HTTP/3 (§23)
        │                      └── L7 Router (§16) → RateLimit (§19) · Circuit (§20) · Auth/JWT (§16.2)
        ▼
 Algorithm library (§15): RR · WRR · LC · WLC · P2C · EWMA · Maglev · Ketama · Jump · LA
        ▼
 BackendPool (§14): ArcSwap<Vec<Arc<Backend>>> · health bits · connection pool · outlier ejector (§20)
        ▼
 Upstream sockets: TLS re-encrypt (§18) · PROXY protocol v2
        ▼
 Cross-cuts (§21): Prometheus · OpenTelemetry · structured access logs

Follow one HTTPS request. A listener in lb-proxy-l7 accepts it, with lb-tls terminating TLS and choosing the certificate by SNI (§10, §18). The L7 Router in lb-router turns the request plus the current ConfigSnapshot into a RouteAction; it is a pure function of (request, snapshot), so a route decision is reproducible from logs alone (§3, P7). Per-request gates then run before backend selection: rate limiting (lb-rate-limit), circuit breaking (lb-circuit) and JWT checks (lb-router::jwt) (§3, §10). The blueprint is not consistent about their order: §3 lists the gates as RateLimit, Circuit, Auth (JWT) and calls them "ordered per-request gates", while §19.2 and §16.6 say JWT validation must precede the rate-limit check so an invalid-token flood cannot bypass the per-consumer budget.

Next the algorithm library in lb-algo picks a backend from the pool's current snapshot, synchronously and without allocating (§11.4, I3), and the BackendPool in lb-backend hands over a pooled connection, plain or re-encrypted through lb-tls (§3, §18). Bytes stream in both directions; no body byte is buffered beyond one flow-control window (I5, P11). lb-observe emits metrics, traces and access logs without altering data-path control flow (§3). Raw TCP and UDP traffic in lb-proxy-l4 skips routing entirely (§3, P1).

The control plane feeds all of this but never blocks it (P4): lb-discovery watchers update the pool, lb-health checkers flip status bits, and lb-config plus lb-admin run the reload, which builds a complete new ConfigSnapshot and swaps one pointer. In-flight requests keep the old snapshot until they complete; new requests see the new one immediately (§3, ADR-07, I1, I2).

The core ideas

A request is a small state machine (§8.1)

Every request moves through named states: Accepted → Parsed → Routed → RateLimited → Picked → Connecting → Streaming → Completed (§8.1). Failed can be entered from any state, and Redirected, Direct, Denied (429) and NotFound are terminal states that write a synthetic response with no upstream contact (§8.1). Each transition names its guard: hop-by-hop headers are stripped between Parsed and Routed (I7), and Selector::pick returns either a backend or a PickError that leads to Failed(NoHealthy) (§8.1, I3, I4).

Health is an estimate, not a fact (§8.2, §17, MM2)

Each backend sits on a two-state axis: Healthy, or PassiveEjected once consecutive_5xx reaches a threshold; a passing active probe moves it back (§8.2, I4). The passive defaults are concrete: 5 consecutive 5xx within 30 s eject the backend for base_ejection_time_seconds · eject_count², with at most 50% of a cluster's backends ejected at once (§17.2). healthy is the AND of the active-check flag and "not passively ejected", written independently with no shared lock (§17.2). A separate Draining flag, set or cleared only by the admin API or a reload, removes a backend from new picks while its existing streams finish (§8.2, I9, P12). The blueprint calls healthy "a stale AND of two independently-lagging observers", so a backend can receive traffic for up to one probe interval after it died; that is bounded-latency detection, not a bug (MM2).

Pick the better of two random servers (§15.2, MM1)

Power of two choices (P2C) samples two backends without replacement and sends the request to the one with fewer active_requests (§15.2). The blueprint cites Mitzenmacher for the bound: max load O(log log N) versus round-robin's O(log N / log log N) (§15.2). The default variant, EWMA-P2C, compares a per-backend latency average instead, updated as ewma = alpha·sample + (1-alpha)·ewma, to dampen herd effects from transient latency spikes (§15.2, ADR-12). Picking must be synchronous and allocation-free (I3, P3); the targets are p50 under 10 µs and p99 under 50 µs at 100 backends, and p99 under 200 µs at 10,000 backends (§15.4, §31 M6, M7).

Minimal disruption when the set changes: Maglev (§8.7, MM4)

For sticky workloads the proxy uses consistent hashing, which accepts a small balance imperfection so that removing one backend moves close to 1/N of keys (MM4). Maglev builds a lookup table of prime size M: each backend has its own permutation of slots, and backends take turns claiming the next free slot in their permutation (§8.7). The blueprint's worked example with M=7, offset(B0)=3, skip(B0)=2 and offset(B1)=0, skip(B1)=3:

Step Backend Proposes Claims
1 B0 3 3
2 B1 0 0
3 B0 5 5
4 B1 3 (taken) → 6 6
5 B0 0 (taken) → 2 2
6 B1 2 (taken) → 5 (taken) → 1 1
7 B0 4 4

Final table [B1, B1, B0, B0, B0, B0, B1]; a lookup is table[hash(k) % 7], O(1). Removing B1 moves only the 3 slots it held (§8.7). The build costs O(M·N): with the default M = 65,537 and 100 backends that is 6,553,700 operations, about 6.5 ms at ~1 ns each, which is why I13 forbids rebuilding on the request path (§15.2, §35 item 7).

Configuration is a value, not state (§8.4, ADR-07, MM3)

A reload runs a small state machine: Building → Validating → Committing → DrainingOld → Retired, with RolledBack if any schema or referential check fails, leaving the previous snapshot live (§8.4, I2). Committing is one atomic ArcSwap::store, the read-copy-update pattern: readers never block, writers never wait for readers, and the old value survives exactly as long as its last reader (ADR-07, MM3). New listeners bind before old ones drain, so there is no listener gap (§22.2). The acceptance test is 100 back-to-back reloads with zero dropped requests (§22.4, §31 M5), and a new snapshot must serve its first request within 50 ms (§4).

Breakers rate-limit the truth, not the traffic (§8.3, §20, MM7)

A per-cluster circuit breaker opens when the fraction of ejected backends exceeds threshold_percent, waits open_duration_seconds, then enters HalfOpen and admits a bounded probe quota; all probes succeeding closes it, any failure reopens it (§8.3, §20.2). A per-backend breaker runs independently, tripping on consecutive_5xx ≥ breaker_threshold (§20.2). The quota is an atomic counter, and an excess probe is short-circuited to 503 (I12, §20.2). Skipping the quota and closing on any single success reintroduces the thundering herd the breaker exists to prevent, producing a recovery outage that looks identical to the original (MM7, FM-7).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust (Tokio, Hyper, Quinn, Rustls, Tonic), for zero-cost abstractions and no GC pause on the data path shared by every listener (§1, ADR-01). Rejected: Go (GC pauses surface in p99.9 above ~500K req/s, and a generic algorithm library over Go interfaces pays a virtual-dispatch tax) and C++ (no differentiator over Tokio for this scope in 2026) (§1). When the rejected choice is right: Go wins for a control-plane-only tool at under 10K req/s where iteration speed beats tail-latency headroom (ADR-01).

Hot reload: an atomic pointer swap, not a lock (ADR-07)

Chosen: arc_swap::ArcSwap<ConfigSnapshot>, lock-free and RCU-style, with no data-path blocking (ADR-07, I1, I2). Rejected: RwLock<Config>, actor-message reload (ADR-07). When the rejected choice is right: RwLock wins for a low-QPS admin-only config (under 100 req/s) where reload contention is immaterial (ADR-07).

Default consistent hash: Maglev (ADR-11)

Chosen: Maglev, the best disruption bound (1/N) among O(1)-lookup schemes (ADR-11). Rejected: Ketama, Rendezvous (ADR-11). When the rejected choice is right: Ketama wins when table-rebuild cost must be zero and looser disruption is acceptable at 100K+ rapidly-churning backends (ADR-11). ADR-01 and ADR-11 are load-bearing: overturning either moves the entire engine (§9).

Default load-aware algorithm: EWMA-P2C (ADR-12)

Chosen: EWMA-P2C, which dampens herd effects from transient latency spikes (ADR-12). Rejected: vanilla P2C (ADR-12). When the rejected choice is right: vanilla P2C wins for homogeneous, stateless backends with no observed latency skew (ADR-12).

Outlier detection: active and passive, both (ADR-13)

Chosen: active plus passive, because "active alone is too slow; passive alone is too noisy" (ADR-13, P5). Rejected: active-only, passive-only (ADR-13). When the rejected choice is right: passive-only wins in a metered-egress edge deployment where active probe traffic is cost-prohibitive (ADR-13).

Backpressure: bodies stream, nothing is buffered (ADR-24)

Chosen: streaming body plus a bounded channel, which bounds memory under slow-client and slow-upstream conditions (ADR-24, P11, I5). Rejected: full-body buffering (ADR-24). When the rejected choice is right: full-body buffering wins when the proxy must transform, not just forward, small (under 64 KiB), contractually bounded bodies (ADR-24). The mental model behind it: buffering "just this one stage" reintroduces unbounded memory growth exactly at that stage (MM5).

TLS library: Rustls (ADR-06)

Chosen: Rustls, memory-safe, ALPN-aware, integrating cleanly with Quinn (ADR-06, P8). Rejected: OpenSSL (ADR-06). When the rejected choice is right: OpenSSL wins when FIPS-140-validated modules or ENGINE-based hardware offload are mandatory (ADR-06).

Roads not taken (§37)

A kernel-bypass XDP/eBPF data path (Facebook Katran) wins at CDN-edge or DDoS-scrubbing scale and is rejected because it forfeits nearly all L7 capability and sets an operator skill floor far above the target audience; ADR-16 defers it explicitly, not permanently (§37 Alt1). The blueprint states its regime two ways: §37 Alt1 puts it "roughly beyond the ~8 Gbps / 1.5M pkt/s ceiling" of the user-space L4 path (§35 items 6 and 8), while ADR-16 and the §38 register put it at more than 5M pkt/s single-box.

Client-side balancing inside every client library (Ribbon-style, gRPC client-side LB) wins when one organisation controls both call sites, because it removes the proxy hop and its added latency entirely; it is rejected because every client must embed and keep current a copy of the logic, and cross-cutting policy (rate limits, TLS, audited admin control) can no longer be enforced at one choke point (§37 Alt2, P1, P10).

A separate xDS control-plane server (Envoy plus a management server, the Istio model) wins at large multi-team, multi-cluster scale where centralised policy authorship matters more than operational simplicity; it is rejected because this blueprint's target team does not need a separately operated control-plane server, at the cost of not scaling policy distribution to hundreds of proxy instances (§37 Alt3).

A hardware appliance (F5 BIG-IP class) wins where throughput must be extremely high and predictable and capex and vendor lock-in are acceptable; it is rejected because this project exists to teach and own the stack in software with weekly-or-faster iteration (§37 Alt4).

What must never be false

  • I1 — a published ConfigSnapshot is immutable; noticed by code review and loom checks, with an lb_config_generation gauge.
  • I2 — in-flight requests never see a partially built snapshot; noticed by the reload_atomicity.json soak fixture and lb_config_reload_total{outcome}.
  • I3 — Selector::pick never blocks the calling task; noticed by a loom model and a p99 < 50 µs perf assertion, with lb_pick_duration_seconds.
  • I4 — a backend is never selected while ejected or unhealthy; noticed by fixture flapping_backend.json and lb_outlier_ejections_total.
  • I5 — no body byte is buffered beyond one flow-control window; noticed by a 1 GiB upload memory-profiling fixture and the process RSS gauge.
  • I6 — a connection's peer address is captured before its task spawns; noticed by a unit test on access-log field presence and an access-log completeness metric.
  • I7 — hop-by-hop headers are stripped before every forward; noticed by the smuggling_*.json fixtures and lb_header_violations_total.
  • I8 — a discovery failure never empties a live pool; noticed by a discovery-source-kill soak test, with lb_discovery_stale_seconds rising.
  • I9 — a draining backend gets no new picks but finishes its streams; noticed by fixture drain_in_flight.json and lb_pool_size{status="draining"}.
  • I10 — every admin mutation writes exactly one audit record before returning success; noticed by an audit-log completeness test and lb_admin_audit_failures_total.
  • I11 — a TLS session ticket never outlives the master-key rotation window; noticed by fixture ticket_rotation.json and tls_full_handshakes_total.
  • I12 — a breaker's half-open probe quota is never exceeded concurrently; noticed by a concurrency stress test and lb_circuit_state.
  • I13 — Maglev/Ketama/Jump tables are rebuilt off the request path; noticed by the M7 perf assertion and lb_table_rebuild_seconds.
  • I14 — a rate limiter's retry_after never decreases across consecutive denies of one key; noticed by fixture burst_429.json and lb_rate_limit_denies_total.

What breaks in production

  • FM-1 — a 5xx storm from one backend. A backend process crash or dependency outage shows up as a per-backend lb_requests_total{status_class=5xx} spike; passive ejection removes the backend within 2 s, and an operator can drain it through the admin API (FM-1, §17.4, §22.2).
  • FM-2 — a reload drops requests. A reload replaced state instead of swapping a snapshot, violating I2; the reload soak fixture would have caught it pre-release, there is no automatic recovery because it is a correctness bug, and the fix is rolling the binary back (FM-2).
  • FM-3 — file descriptors run out. A connection leak or an under-provisioned budget shows up as accept() failures and EMFILE in logs; new connections are refused until a restart with a corrected RLIMIT_NOFILE or a leak fix, with an lsof snapshot for forensics (FM-3).
  • FM-4 — the discovery source is down. Consul, etcd or the Kubernetes API is unreachable; lb_discovery_stale_seconds rises while the last-good pool is retained indefinitely (FM-4, I8).
  • FM-5 — health checks cry wolf. An overloaded-but-alive backend is misclassified dead, visible as an Inconclusive rate spike against Unhealthy; by design Inconclusive neither clears nor advances, so the fix is tuning timeouts and thresholds (FM-5, §17.2).
  • FM-6 — a spike of full TLS handshakes. The session-ticket master key was rotated without staging; tls_full_handshakes_total spikes and self-resolves as tickets re-establish, and future rotations are staged via the admin API (FM-6, §18.9).
  • FM-7 — a thundering herd when a breaker recovers. The half-open quota was bypassed or set to 0; lb_circuit_state flaps Open↔HalfOpen; quota enforcement (I12) prevents it structurally, and a longer open_duration_seconds stops persistent flapping (FM-7).
  • FM-9 — split brain in the active-active fleet. A gossip partition lets two nodes serve the same key, visible on the gossip-membership dashboard; it reconciles on gossip recovery, but an operator must verify no non-idempotent writes happened in the window (FM-9, §24.8).

Threats a reader should know (§25): T1 volumetric and SYN-flood attacks, shed at the listener with SYN cookies and per-IP caps so upstreams are unaffected; T2 slowloris and slow-read attacks, closed by tight header, body and idle timeouts; T4 request smuggling through ambiguous Content-Length and Transfer-Encoding, rejected on first ambiguity (I7, §8.9); T5 HTTP/2 reset floods, capped by a per-connection RST rate limit plus a capped HPACK/QPACK table (§23); T12 a malicious config payload, defeated by validate-then-commit with rollback to the previous snapshot (§22.2, I2).

How it compares

  • HAProxy chose a decades-proven single-threaded event loop per process with optional multi-process fan-out and the richest ACL and stick-table configuration language; its reconfiguration (full process reload or a limited Runtime API) is less ergonomic than xDS or an ArcSwap swap (§34).
  • NGINX chose the web-server-plus-reverse-proxy combination with a multi-process worker model; it wins when the same binary must also serve static files and terminate TLS for a traditional web stack, at the cost of worker-level reloads rather than per-object atomic swaps (§34).
  • Envoy chose a fully dynamic xDS-driven control-plane/data-plane split for large multi-team, multi-cluster fleets; it wins at organisational scale and costs a separately operated control-plane server this blueprint's scope does not need (§34, §37 Alt3).
  • Cloudflare Pingora chose to be a library embedded in a team's own binary rather than a standalone proxy; it wins when a team wants Rust-level performance with full control over its own config and discovery, and costs every embedding team re-solving the integration this blueprint ships (§34).

Questions to test yourself

  1. Why does a config reload never drop an in-flight gRPC stream, and what specifically would break if ConfigSnapshot were a mutated Mutex<HashMap<...>> instead of an ArcSwap? — Hint: §22.2 and invariants I1/I2, plus ADR-07.
  2. A backend is receiving traffic despite having crashed 1.5 seconds ago. Is this a bug? Walk through exactly which invariant governs the answer. — Hint: I4, §17.2 and mental model MM2.
  3. Why does removing one backend from a Maglev table move only ~1/N of keys, and what would the disruption fraction be under naive hash(key) % N instead? — Hint: the worked table in §8.7 and §35 item 7.
  4. Derive, from the System Constraints table alone, why session-ticket resumption is mandatory at scale rather than a nice-to-have. — Hint: §4's two handshake rows and §35 item 9.
  5. Why does this design choose to buffer zero bytes of body in DRAM structurally, and what principle would you cite to a reviewer who suggested "just add a small buffer for simplicity"? — Hint: P11 and MM5.

If you only remember three things

Choosing a backend is a decision under uncertainty, so comparing two random candidates by load beats a fixed rotation that ignores transient slowness (MM1). Health is always a lagging estimate and configuration is always an immutable value, so detection has bounded delay and a reload swaps a pointer instead of editing state (MM2, MM3). When the set of servers changes, the goal is to move close to 1/N of keys rather than nearly all of them, which consistent hashing buys at the price of a small balance imperfection (MM4).

Words used here

  • Backend — one upstream server the proxy can send traffic to.
  • BackendPool — the single source of truth for which backends exist and how healthy they are.
  • ConfigSnapshot — one immutable, complete configuration; a reload makes a new one.
  • ArcSwap / RCU — swapping a pointer to a new value so readers never block and old readers finish on the old value.
  • Selector — the trait every selection algorithm implements; pick must be synchronous and allocation-free.
  • P2C — power of two choices: sample two backends, take the one with fewer active requests.
  • EWMA — a moving average that weights recent latency more, used by EWMA-P2C in place of the request count.
  • Consistent hashing / Maglev — mapping keys to backends so that removing one backend moves only about its share of keys.
  • Outlier ejection — passively removing a backend after a run of consecutive 5xx responses.
  • Circuit breaker — a per-cluster or per-backend switch that stops traffic after too many failures and probes before resuming.
  • Half-open — the breaker state that lets a bounded number of probe requests through.
  • Draining — a backend that takes no new picks but finishes its current streams.
  • Hop-by-hop header — an HTTP header meant for one connection only; it must be stripped before forwarding.
  • VRRP / VIP — the protocol and shared address that let a standby node take over a failed one.
  • PROXY protocol v2 — a small binary header that tells the upstream the real client address.
