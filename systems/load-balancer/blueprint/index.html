1. Goal & Scope

Build a single-binary reverse proxy / load balancer that terminates and forwards L4 (TCP, UDP) and L7 (HTTP/1.1, HTTP/2, HTTP/3, gRPC) traffic across a pluggable algorithm library, a dynamically-discovered backend pool, active + passive health checking, TLS termination with upstream re-encryption, host/path/header/method/JWT-claim routing with rewrite / redirect / canary / split / shadow, per-route rate limiting, circuit breaking with outlier ejection, Prometheus metrics + OpenTelemetry traces + structured access logs, and a mutation-only admin API for hot-reload, drain, and inspection — deployable as a single node, an active-passive VRRP pair, or an active-active consistent-hash fleet.

In-scope Phase-0 deliverable (numbered modules, §10 names them normatively):

  1. lb-core — id types (BackendId/ClusterId/RouteId/RequestId), error types, Clock abstraction.
  2. lb-config — ConfigSnapshot, schema, static validation (hard-coded snapshot in Phase 0).
  3. lb-backend — Backend, BackendStatus, BackendPool (ArcSwap-backed).
  4. lb-algo — Selector trait; RoundRobin only (the other nine algorithms land Phase 3).
  5. lb-proxy-l4 — raw TCP listener + copy_bidirectional proxy.
  6. lb-proxy-l7 — HTTP/1.1 listener (Hyper); lands fully in Phase 1.
  7. lb-observe — minimal Prometheus registry.
  8. lb-admin — /admin/health, graceful shutdown.
  9. lb-cli — the lb binary entry point.

System boundaries.

  • Provides: connection acceptance; backend selection; protocol framing (L4 raw bytes; L7 HTTP/1.1, HTTP/2, HTTP/3, gRPC pass-through); TLS termination + upstream re-encryption; routing; rate limiting; circuit breaking; health checking; discovery; observability; admin control.
  • Delegates: DNS resolution to the OS/library resolver (cf. the sibling DNS-Resolver project, rank 65, §5); JWT signature verification to the sibling Auth-System project (rank 49, §5); distributed cross-replica rate-limit state to an external store (deferred, §38); active-active membership/gossip to the sibling Gossip-Protocol project (rank 70, §5).
  • Does NOT provide: a WAF rule library (hook points only — PhaseDeferred("§38")); an XDP/eBPF kernel datapath (PhaseDeferred("§38")); body-content transformation (PhaseDeferred("§38")); a Wasm filter runtime (PhaseDeferred("§38")); post-quantum TLS (PhaseDeferred("§38")); protocol-aware proxying for SMTP/MySQL/Postgres/Redis.

Non-goals: a plugin marketplace; a bundled xDS-style control-plane server; a bundled dashboard UI beyond a Grafana JSON export.

Deployment model: single static binary (lb), YAML/JSON ConfigSnapshot on disk or pushed via the admin API, run as a systemd unit, a container, or a Kubernetes Deployment/DaemonSet fronted by a Service.

Target users/operators: platform/SRE teams operating their own edge or internal L7 tier; the on-call engineer diagnosing a 5xx storm or a latency regression.

What later phases unlock: HTTP/2 and HTTP/3 (Phase 11, §23) unlock modern client multiplexing; the active-active topology (Phase 12, §24) unlocks horizontal scale past one NIC; TLS (Phase 6, §18) unlocks public-internet exposure.

Recommended language: Rust (Tokio + Hyper + Quinn + Rustls + Tonic). Exact rationale: the algorithm library and backend pool are shared, must be zero-allocation on the hot path, and must be safely concurrent across L4 and L7 listeners simultaneously; Rust's ownership model delivers this without a GC pause budget, and by 2026 the async ecosystem (Hyper/Quinn/Rustls) is production-grade (ADR-01). Rejected — Go: simpler discovery/admin code, but GC pauses surface in p99.9 tail latency above ~500K req/s, and a shared generic algorithm library over Go interfaces pays a virtual-dispatch tax the Rust monomorphized trait does not. Rejected — C++: no differentiator over Tokio for this scope in 2026; a hand-rolled epoll reactor is a maintenance tax with no corresponding benefit once a mature async runtime exists.

Prerequisites: async Rust (Future, Pin, at least one hand-written Future); BSD sockets and TCP backpressure; the HTTP/1.1 vs HTTP/2 vs HTTP/3 head-of-line-blocking distinction; the TLS 1.2/1.3 handshake + ALPN; HTTP/2 framing + HPACK; HTTP/3/QUIC framing + QPACK; gRPC-over-HTTP/2 framing; SO_REUSEPORT, TCP_NODELAY, TCP_DEFER_ACCEPT, TCP_USER_TIMEOUT, IP_FREEBIND; enough queueing theory to justify P2C over round-robin (§33 MM1, §5 Mitzenmacher).

Estimated timeline: Phase 0 in 1 week; the full 13-phase plan in 4–7 months (one senior engineer, part-time reviewer).

Deferred features (all registered in §38, each anchored to a real heading): XDP/eBPF L4 fast path PhaseDeferred("§38"); WAF rule library PhaseDeferred("§38"); multi-cluster geo/latency steering PhaseDeferred("§38"); distributed cross-replica rate limiting PhaseDeferred("§38"); body-aware transformation PhaseDeferred("§38"); post-quantum TLS PhaseDeferred("§38"); Wasm filter runtime PhaseDeferred("§38").

2. Why Build This

  • Teaches the single most consequential hop in any production system: every request crosses it first, every response crosses it last.
  • The failure modes are canonical and recur across HAProxy, NGINX, Envoy, and Pingora deployments: a flapping health check evicting healthy backends; TCP backpressure inverting under FD exhaustion; a config reload silently dropping in-flight long-lived gRPC streams.
  • Architecturally, the ArcSwap/RCU-style hot-reload pattern (I1, I2, MM3 in §33) generalizes to any control-plane/data-plane split — the same shape reappears in every system that must mutate configuration without stopping the world.
  • Historically, the lineage runs from early NAT boxes through HAProxy's stick tables to Envoy's dynamic xDS control plane — the same lineage Kubernetes' kube-proxy and Istio grew through.
  • Engineering muscles built: tail-latency-first design, lock-free data structures under real concurrency, protocol-framing discipline, zero-copy body streaming, consistent-hashing math, chaos/soak-testing discipline.
  • Cross-links: shares its discovery abstraction with Service-Discovery (rank 42, §5); its rate limiter with Rate-Limiter (rank 39, §5); its JWT verification with Auth-System (rank 49, §5); its DNS resolution with DNS-Resolver (rank 65, §5); its active-active membership with Gossip-Protocol (rank 70, §5).
  • Calibration value: small enough to finish in months, large enough to expose nearly every distributed-systems failure mode that also appears in databases, queues, and service meshes — the highest information density per engineering-hour in the portfolio.

What Mastery Looks Like

  • Explains why P2C beats round-robin on tail latency from the Mitzenmacher result, not intuition (Phase 3, §15).
  • Hand-constructs a Maglev lookup table for small M/N and predicts which backend a given key lands on (Phase 3, §15; §35).
  • Diagnoses a "config reload dropped my gRPC stream" incident from the ArcSwap snapshot model alone (Phase 10, §22; §33 MM3).
  • Defends, with numbers, why the admin API is mTLS-only and why that is not paranoia (Phase 10, §22; §25 T7).
  • Redesigns this proxy as an eBPF/XDP datapath and states exactly which invariants (I3, I5) become the kernel's problem instead of the proxy's (§37).
  • Sizes a fleet from first principles — FD budget, RAM per backend, bandwidth — without measuring anything first (§35).
  • Reads HAProxy's backend.c, Envoy's router.cc, and Pingora's pingora-proxy crate and maps each to the equivalent module in this blueprint (§34).

Three properties recur throughout this document. First, the data path is one-way: request → listener → router → algorithm library → backend pool → upstream socket; the response mirrors it back. The control plane never blocks the data path (P4). Second, the L4 and L7 listeners share the algorithm library, the backend pool, and the admin/metrics/ discovery surface; only the listener-side framing diverges. Third, config is an immutable snapshot behind arc_swap::ArcSwap<ConfigSnapshot> (ADR-07); a reload allocates a new snapshot and swaps the pointer atomically (I1, I2) — in-flight requests keep the old snapshot until they complete; new requests see the new one immediately. There is no shared mutable state between control plane and data path.

Per-box description. Admin API — the sole mutation surface (P10); mTLS by default; writes an audit record before applying any change (I10). Control Plane — owns discovery watchers, health-check timers, and the two-phase reloader; runs on its own task set. Listeners — one per protocol; L4 (raw TCP/UDP) skips routing entirely (P1); L7 listeners share one Service boundary. L7 Router — a pure function of (request, snapshot) (P7); resolves host/path/header/method/JWT matchers to a RouteAction. RateLimit/Circuit/Auth — ordered per-request gates before backend selection. Algorithm Library — the Selector trait and its ten implementations (§15); reads the BackendPool snapshot, never mutates it. BackendPool — the single source of truth for backend health and connections; written by discovery, health checks, and the outlier ejector; read by every pick. Upstream sockets — plaintext or re-encrypted TLS; PROXY protocol v2 injection is opt-in per cluster. Cross-cuts — metrics, tracing, and access logs observe every box without altering data-path control flow.

6. Design Principles

  1. P1 — One Core, Two Listeners. The algorithm library, backend pool, discovery layer, health checker, metrics surface, admin API, and hot-reload contract are written once and used by every listener kind. Tradeoff: L4-specific latency shaving (e.g. splice(2)-style zero-copy) is harder to bolt on later. Operational implication: a pick_backend bug fix is a bug fix everywhere. Violated: duplicated code paths silently diverge and one gets fixed, the other doesn't.
  2. P2 — Hot-Reload Is In-Flight-Safe. A config reload never drops an in-flight request; long-lived gRPC streams against a removed backend continue until they close. Tradeoff: requires holding old Arc<ClusterConfig>/Arc<Backend> memory until the last reference drops. Operational implication: reload frequency is rate-limited (ADR-07, I2). Violated: the canonical "reload dropped 12,000 gRPC streams" incident (§33 MM3).
  3. P3 — Zero Per-Request Heap Allocation on the Hot Path. Backend selection and body framing use pre-allocated buffers and bytes::Bytes views. Tradeoff: more upfront design complexity (niche-optimized IDs, Arc-based sharing). Operational implication: allocator pressure is bench-asserted, not assumed. Violated: allocator contention shows up as p99 latency jitter under load (§31).
  4. P4 — The Control Plane Never Blocks the Data Path. Discovery push, health-check timers, metric scrapes, and admin calls run on separate tasks; the data path communicates via ArcSwap and lock-free channels only. Tradeoff: eventual, not immediate, consistency between control and data plane. Operational implication: a stuck discoverer cannot stall requests. Violated: a health-check HTTP call blocking on the request-handling thread pool stalls unrelated traffic.
  5. P5 — Health Is Observed, Never Assumed. Active checks (TCP/HTTP/gRPC/exec) provide baseline truth; passive outlier ejection provides fast-path eviction. Tradeoff: two subsystems must reconcile via one BackendStatus (I4). Operational implication: a backend can be evicted before the next scheduled active probe. Violated: traffic keeps flowing to a backend mid-5xx-storm until the next probe fires.
  6. P6 — One Algorithm at a Time per Cluster, No Silent Fallback. A cluster declares exactly one Selector; if it cannot pick, the proxy fails open and observes rather than silently falling back to round-robin. Tradeoff: an operator must explicitly choose a fallback policy. Operational implication: algorithm behavior is always predictable from config. Violated: a silent fallback masks a real bug in the configured algorithm.
  7. P7 — Routing Is a Pure Function of (Request, Snapshot). No hidden per-request mutable state; canary/split assignment is a stable hash of a request key. Tradeoff: statefulness (e.g. sticky sessions beyond hash-based) needs an explicit key, not implicit affinity. Operational implication: a route decision is reproducible from logs alone. Violated: non-deterministic routing makes incident reproduction impossible.
  8. P8 — TLS Terminates Here; Upstream Re-Encryption Is Default-On. Plaintext-to-upstream is opt-in per cluster, never the default. Tradeoff: extra CPU cost for the second handshake. Operational implication: upstream cert expiry becomes an operational surface (T9, §25). Violated: an accidentally-plaintext upstream hop leaks data on a compromised internal network.
  9. P9 — Metrics Are Typed, Not Stringly-Typed. Every metric is a typed handle declared at construction; label cardinality is bounded at the type level. Tradeoff: a new metric requires a code change, not a config change. Operational implication: no typo'd metric names in production. Violated: an unbounded label (e.g. raw upstream IP) blows Prometheus cardinality.
  10. P10 — The Admin API Is the Only Mutation Surface. No SIGHUP, no inotify-watched config file as a mutation trigger (though it exists as a discovery source), no out-of-band poke; every mutation is an audited admin call (I10). Tradeoff: an extra network hop for local config changes. Operational implication: every mutation has an auditable actor. Violated: an unaudited config change is undebuggable after the fact.
  11. P11 — Backpressure Propagates, Never Gets Absorbed. Both proxy directions stream; a slow reader on one side throttles the read from the other via bounded buffers, never via unbounded in-memory queuing. Tradeoff: a slow client can hold upstream resources longer. Operational implication: OOM from a large body is structurally impossible. Violated: a 1 GiB upload behind a slow upstream buffers entirely in DRAM and OOMs the proxy.
  12. P12 — Draining Is Not Unhealthy. A draining backend is healthy from the upstream's perspective but excluded from new picks; the health checker must not flag it. Tradeoff: two independent boolean flags (healthy, draining) instead of one enum simplifies concurrent writers at the cost of an extra invariant (I9) to maintain. Operational implication: draining backends still serve their existing long-lived streams. Violated: conflating the two states either kills in-flight streams early or keeps sending new traffic to a backend mid-decommission.
  13. P13 — Time Is Injected, Never Read Raw. All timers, TTLs, and EWMA updates go through the Clock trait (MonotonicClock in production, MockClock in tests). Tradeoff: an extra trait-object indirection on every timestamp read. Operational implication: deterministic replay and chaos testing become possible (§29). Violated: a flaky test that depends on wall-clock timing cannot be reproduced deterministically.
  14. P14 — Every Stochastic Algorithm Ships a Deterministic Conformance Fixture. P2C, EWMA-P2C, Maglev, Ketama, and Jump all have a seeded fixture asserting a chi-square-bounded pick distribution. Tradeoff: fixture maintenance cost on every algorithm change. Operational implication: a regression in pick fairness is caught in CI, not production. Violated: a bug in P2C's sampling-without-replacement only manifests under real load (§15.6).

These principles are enforced at the type level where possible, by code review where not.

Debugging methodology. Every invariant above has a corresponding assertion in a deterministic simulator (conformance/runner.rs, driven by MockClock, P13): the simulator replays a scripted sequence of accepts, discovery events, health-check outcomes, and reload calls, and asserts each I# after every step. A failed assertion names the violated I# directly in its panic message, so a CI failure points at the exact invariant, not a generic test name.

8.5 Wire layout: PROXY protocol v2 header (upstream injection, §12.2, §24.2)

Signature (12B): 0x0D 0x0A 0x0D 0x0A 0x00 0x0D 0x0A 0x51 0x55 0x49 0x54 0x0A

Malformed-input example: a length field that overruns the segment the proxy read from the socket is rejected at parse time (never trusted past the declared Length); the connection is reset and lb_header_violations_total{kind="proxy_v2_overrun"} increments (I7 sibling check).

8.6 gRPC-over-HTTP/2 frame layout (§23.2)

compressed-flag (1B) | message-length (4B, big-endian) | protobuf payload (message-length bytes)

The proxy treats the payload as opaque bytes (P1/P3: no per-request allocation to parse protobuf); only the HTTP/2 DATA frame boundaries and the grpc-status/grpc-message trailers are inspected.

8.7 Worked example: Maglev lookup table, M=7, N=2

Backends B0, B1. offset(Bi) = h1(Bi) % M, skip(Bi) = h2(Bi) % (M-1) + 1. Take offset(B0)=3, skip(B0)=2 → permutation [3,5,0,2,4,6,1]; offset(B1)=0, skip(B1)=3 → permutation [0,3,6,2,5,1,4]. Construction visits backends round-robin; each proposes the next unfilled slot in its own permutation, skipping slots already claimed:

Step Backend Proposes Slot claimed
1 B0 3 3
2 B1 0 0
3 B0 5 5
4 B1 3 (taken) → 6 6
5 B0 0 (taken) → 2 2
6 B1 2 (taken) → 5 (taken) → 1 1
7 B0 4 4

Final table (slot → backend): [B1, B1, B0, B0, B0, B0, B1]. Lookup for key k is table[hash(k) % 7] — O(1). Removing B1 rebuilds with N=1; only the 3 slots B1 held move, matching the 1/N disruption bound (§35) — this is the O(M·N) build cost quantified in §35 and the reason I13 forbids running it on the request path.

8.8 Failure-path example: upstream connection reset mid-stream

  1. Client sends GET /orders/42; proxy picks B7 via EWMA-P2C (§15.2).
  2. Upstream connection to B7 accepts, streams 4 KiB of the response, then sends TCP RST (backend process crashed).
  3. Proxy's copy_bidirectional/Hyper body stream observes the RST as an I/O error mid-frame.
  4. Proxy cannot retry transparently — headers and 4 KiB of body have already been flushed to the client (HTTP/1.1 has no mid-response rollback). The connection to the client is reset with lb_requests_total{status_class="5xx"} incremented and the incident logged with request_id, backend_id=B7.
  5. B7's consecutive_5xx (or, since this is a transport-level reset rather than a 5xx status, a distinct connection_reset counter) increments; five such events within 30 s trigger passive ejection (I4, §20.2).
  6. Active health check on B7 (§17) fails next probe; BackendStatus.healthy flips false independently, confirming the passive signal (§7 debugging methodology).

8.9 Malformed-input example: HTTP request smuggling (CL.TE)

A request carrying both Content-Length: 44 and Transfer-Encoding: chunked is ambiguous about framing. Per RFC 7230 section 3.3.3 and I7, Hyper's parser refuses to resolve the ambiguity in the proxy's favor; the proxy rejects the request outright (HTTP 400) rather than guessing, because guessing wrong is exactly the CL.TE smuggling vector documented in the conformance fixtures conformance/corpora/routing/smuggling_cl_te.json (§13.5, T4 in §25).

12. Phase 0 — Skeleton, Governance & TCP Kernel

12.1 Objectives

  • Stand up the repository skeleton (§10) as a single commit; every crate manifest compiles with an empty body.
  • Deliver a raw TCP L4 proxy: accept → dial upstream → bidirectional byte copy.
  • Raise the FD budget at boot (§4) and land the governance documents.
  • Constraints introduced: one hard-coded ConfigSnapshot (I1); no dynamic discovery yet (Phase 2, §14); no TLS yet (Phase 6, §18).

12.2 Detailed Implementation Steps

  • lb-core::id — BackendId/ClusterId/RouteId/RequestId newtypes over NonZeroU64 (§11.1); applies P3 (zero-allocation hot path) via niche-optimized Option<Id>.
  • lb-core::time — Clock trait + MonotonicClock + MockClock per P13/ADR-23; every later phase's timers depend on this abstraction.
  • lb-proxy-l4::tcp — accept loop dialing a configured upstream, spawning tokio::io::copy_bidirectional per connection (ADR-02).
  • Raise RLIMIT_NOFILE via prlimit at binary entry (Kerrisk, TLPI ch. 36, §5) to the §4 FD budget (1,048,576); never rely on operator ulimit.
  • Land governance files (§10): README, CONTRIBUTING, CODE_OF_CONDUCT, SECURITY, CHANGELOG, BLUEPRINT_LOG, LICENSE (ADR-08).
  • Land Makefile targets: bootstrap/build/test/lint/typecheck/compose-up/compose-down/ release-check/clean — each single-line output, non-zero exit on failure.
  • Land Dockerfile (cargo-chef caching + distroless runtime, ADR-21) and docker-compose.yml.
  • Land .github/workflows/{ci,conformance,fuzz,security,release}.yml (ADR-22, ADR-27, ADR-29).
  • Capture the peer SocketAddr from TcpListener::accept before task spawn, for the Phase-9 access log (I6).

12.3 Deliverable

  • make bootstrap && make build && make test all exit 0 on a clean checkout.
  • A running lb binary proxying nc 127.0.0.1:8080 to a nc -l 9000 upstream bidirectionally.
  • ADR files for ADR-01, ADR-02, ADR-08, ADR-09, ADR-10, ADR-18, ADR-21, ADR-22 landed under docs/adr/.

12.4 Acceptance Criteria

  • make test passes with ≥1 test asserting bidirectional byte-count equality on a loopback proxy (fixture tcp_smoke.json).
  • RLIMIT_NOFILE raised to exactly 1,048,576 on Linux, asserted via getrlimit(2) in test.
  • Cold-start time to first accept() < 250 ms (§4), measured by scripts/bootstrap.sh.
  • Zero clippy::all warnings at -D warnings.

12.5 Conformance Fixtures

  • conformance/corpora/reload/tcp_smoke.json — single-connection byte-echo, both directions.
  • conformance/corpora/reload/fd_limit.json — asserts post-boot RLIMIT_NOFILE value.
  • conformance/corpora/reload/cold_start.json — asserts time-to-first-accept < 250 ms.

12.6 Pitfalls

  • copy_bidirectional takes &mut to both halves; a naive select! around it fails to compile with a use-after-move — read the rustdoc contract rather than hand-rolling the loop.
  • Default Linux nofile is 1,024; the raise must happen in-process (§4, TLPI ch. 36).
  • TcpListener::accept's peer address is lost to the access log if not captured pre-spawn (I6).
  • cargo-chef layer caching silently goes stale if Cargo.lock isn't copied before the recipe step — verify Docker build cache hit rate in CI.

12.7 Performance Concerns

  • copy_bidirectional's default per-connection buffers (2 × 8 KiB) cost ~16 KiB/conn; at the §4 500,000-connection ceiling that is ~7.6 GiB — over the 2 GiB RSS budget. Phase 1's streaming model (ADR-24) resolves this for the steady state; Phase 0 accepts the gap because it never runs at that concurrency.
  • prlimit's syscall cost is paid once at boot — negligible.

12.8 Edge Cases

  • Upstream refuses connection: proxy closes the client side cleanly, never hangs.
  • Client closes before upstream dial completes: cancel the dial, do not leak the task.
  • TCP FIN vs RST: both must terminate the mirrored side (§8.1 half-close semantics).
  • RLIMIT_NOFILE raise fails under a restrictive container securityContext: log and continue at the container ceiling rather than crash-looping.

12.9 Failure Analysis

  • What breaks: an unbounded upstream dial hangs the client connection indefinitely.
  • Detection: lb_upstream_connect_seconds (stubbed here, wired Phase 9) shows unbounded tail.
  • Blast radius: one client connection per stuck dial — bounded by the per-connection task model, never process-wide.
  • Containment: a hard-coded 5 s dial timeout (config-driven from Phase 2 onward).
  • Recovery path: connection reset to the client with a logged reason.
  • Operator visibility: stderr log line (structured logging lands Phase 9, §21).

12.10 Operational Notes

  • Deployment: single static binary + systemd unit or container; no runtime deps beyond libc.
  • Rollback: previous binary version — Phase 0 has no persistent state, so rollback is a binary swap.
  • Migration: none (no schema yet).
  • Compatibility: N/A until Phase 2 introduces ConfigSnapshot versioning (§28).

13. Phase 1 — HTTP/1.1 Reverse Proxy Core

13.1 Objectives

  • Stand up the L7 path the remaining twelve phases extend: serve HTTP/1.1 against a static, single-cluster backend, with client- and upstream-side keepalive.
  • Emit one structured access-log line per request (full schema lands Phase 9; a minimal line ships here).
  • Constraints introduced: static (hard-coded) RouteConfig; no routing intelligence yet (Phase 4, §16); RR-only selection (Phase 3, §15 ships the rest).

13.2 Detailed Implementation Steps

  • lb-proxy-l7::h1 — drive connections via Hyper's server::conn::http1::Builder (ADR-03); Hyper owns framing, chunked encoding, Connection: keep-alive — the proxy never hand-parses HTTP/1.1 bytes (RFC 7230/7231, §5).
  • Upstream client via Hyper's client::conn::http1::handshake; the Connection future is tokio::spawned; SendRequest is checked out of lb-backend::connection::ConnectionPool (§11.2 Backend), keyed (BackendId, scheme), honoring max_idle_per_backend and keepalive_idle_timeout.
  • Body streaming both directions via Body::poll_frame; back-pressure propagates through bounded buffers (P11, ADR-24, I5) — never buffer a full body in DRAM.
  • Header normalization stage strips hop-by-hop headers (Connection, Keep-Alive, Proxy-Authorization, Proxy-Authenticate, TE, Trailers, Transfer-Encoding, Upgrade except for WebSocket) per RFC 7230 section 6.1 and I7; rejects CL.TE/TE.CL ambiguity outright (§8.9) rather than guessing.
  • Header rewriting: Host rewrite when routed; X-Forwarded-For append (never replace); X-Forwarded-Proto per listener; X-Request-Id set-if-absent (UUIDv7), preserved if present (RFC 7239, §5).
  • A minimal structured access-log line (ts, request_id, client_ip, method, path, status, duration_ms) written via a bounded mpsc channel to a writer task, never formatted inline on the request thread (§21 anticipates the full schema).

13.3 Deliverable

  • An HTTP/1.1 reverse proxy that round-robins (RoundRobin, §15) across two static backends from YAML.
  • A benchmarks/wrk2_bench.sh script driving load against the proxy on one core.

13.4 Acceptance Criteria

  • Sustains ≥ 100,000 req/s single-core with a 1 KiB response (§4, §31 M1).
  • p50 added latency < 100 µs, p99 < 1,000 µs at that load (§4).
  • Access-log line present for 100% of completed requests (fixture access_log_complete.json).
  • Hop-by-hop headers absent from every forwarded request (fixture hop_by_hop_stripped.json).

13.5 Conformance Fixtures

  • conformance/corpora/routing/smuggling_cl_te.json — CL.TE ambiguity rejected with HTTP 400.
  • conformance/corpora/routing/smuggling_te_cl.json — TE.CL ambiguity rejected with HTTP 400.
  • conformance/corpora/reload/access_log_complete.json — 10K requests, 10K log lines.
  • conformance/corpora/routing/hop_by_hop_stripped.json — asserts absence of all 7 hop-by-hop headers on the upstream-bound request.

13.6 Pitfalls

  • Hyper's Body may be !Send in some configurations; the tokio::spawn boundary requires Send — use the workspace BoxBody alias.
  • Host is HTTP/1.1-only; HTTP/2 uses :authority (§16.3) — the router must consult HttpRequestHead::authority(), never branch on protocol in routing code (P7).
  • Hop-by-hop stripping must special-case Upgrade for WebSocket — stripping it unconditionally breaks WebSocket proxying.
  • A PooledConnection that errors mid-request must be destroyed, never returned to the pool.

13.7 Performance Concerns

  • Per-request allocation is bounded to the header map and the BoxBody wrapper — no body copy (P3, ADR-24).
  • Connection-pool checkout is the dominant per-request cost at steady state; contention on the per-backend pool shard is bounded by ADR-31's sharding choice.
  • wrk2-measured tail latency must isolate GC-equivalent pauses — Rust has none, but allocator contention can still show up (§31).

13.8 Edge Cases

  • Upstream closes the pooled connection between checkout and use: the client-facing retry is transparent for idempotent methods, surfaced as 502 for non-idempotent ones.
  • A request with neither Content-Length nor Transfer-Encoding and a non-empty body: rejected (RFC 7230 section 3.3).
  • Upgrade requests (WebSocket) bypass the normal proxy body path entirely.
  • A backend that never responds within the configured timeout: 504, connection to backend reset.

13.9 Failure Analysis

  • What breaks: a pool-checkout race against a just-closed upstream connection.
  • Detection: lb_upstream_connect_seconds histogram tail, total_5xx counter.
  • Blast radius: one request per race; the pool's next checkout gets a fresh handshake.
  • Containment: checkout validates connection liveness with a zero-byte read probe before reuse.
  • Recovery path: transparent retry for idempotent methods only (GET/HEAD/OPTIONS).
  • Operator visibility: access-log line carries retry_count.

13.10 Operational Notes

  • Deployment: no change from Phase 0 topology.
  • Rollback: binary swap; the static RouteConfig has no migration path yet.
  • Metrics stub: lb_requests_total, lb_request_duration_seconds (full set Phase 9, §21).
  • Compatibility: the access-log line schema is versioned from this phase onward (§28).

14. Phase 2 — Backend Pool & Discovery

14.1 Objectives

  • Replace Phase 1's hard-coded backend list with a BackendPool fed by a Discoverer (§11.7).
  • Ship all five discoverers: static, DNS, file-watch, Consul, etcd, Kubernetes EndpointSlice.
  • Constraints introduced: discovery runs on the control-plane task set only (P4); the data path only ever reads BackendPool::snapshot().

14.2 Detailed Implementation Steps

  • lb-backend::pool — BackendPool::replace swaps the inner Vec atomically (§11.3, ADR-07); a removed-but-still-active backend is marked draining on the old Arc<Backend> so in-flight picks against the old snapshot also avoid it (I9, P12).
  • lb-discovery::static_ — reads (addr, weight, locality) tuples from the ConfigSnapshot; the conformance ground truth every dynamic discoverer is validated against.
  • lb-discovery::dns — resolves A/AAAA/optional SRV on a configurable interval; re-resolves on TTL expiry, honoring min_ttl/max_ttl overrides for lying upstreams; emits both address families when dual-stack (cites the sibling DNS-Resolver project, rank 65, §5).
  • lb-discovery::file — watches a JSON/YAML file via notify (inotify/kqueue), debounced 200 ms; schema-validates every read; a syntactically invalid file never replaces the live snapshot (I8).
  • lb-discovery::consul — long-polls /v1/health/service/<name>?passing=1&index=<N>; compares X-Consul-Index to detect real change (Consul returns 200 on a no-op timeout).
  • lb-discovery::etcd — watches the /services/<name>/ prefix via the etcd v3 watch API.
  • lb-discovery::k8s — watches EndpointSlice objects (not the deprecated Endpoints type) matching a label selector, honoring the excluded-from-external-load-balancers label (§5 Kubernetes EndpointSlice spec).
  • Every discoverer implements Discoverer::watch (§11.7); a source failure logs + increments lb_discovery_errors_total{cluster, kind} and never empties the pool (I8) — the last-good snapshot is retained and lb_discovery_stale_seconds rises.

14.3 Deliverable

  • All five discoverers implement Discoverer; BackendPool is fed exclusively through it.
  • A 10-minute Consul flap-soak: a backend flaps in/out every 5 s with zero dropped connections.

14.4 Acceptance Criteria

  • Flap-soak (flap_soak.json, 10 min, 5 s period) emits zero 5xx and zero dropped connections (§31 M2).
  • A killed discovery source (Consul agent stopped) leaves the pool unchanged for ≥ 60 s while lb_discovery_stale_seconds rises monotonically (fixture discovery_source_kill.json).
  • DNS TTL of 0 triggers re-resolution on every probe (fixture dns_ttl_zero.json).

14.5 Conformance Fixtures

  • conformance/corpora/reload/flap_soak.json — 10-minute Consul flap, zero drops.
  • conformance/corpora/reload/discovery_source_kill.json — source outage, last-good retained.
  • conformance/corpora/reload/dns_ttl_zero.json — TTL-0 re-resolution on every probe.
  • conformance/corpora/reload/k8s_endpointslice_aggregate.json — multi-slice aggregation for one service.

14.6 Pitfalls

  • DNS TTLs lie: some upstreams set 0 and expect honoring, others set 86,400 and expect an earlier refresh — min_ttl/max_ttl overrides exist for exactly this (§5 TCP/IP Illustrated informs the retransmission-adjacent reasoning, not directly DNS, but the "don't trust the wire" posture generalizes).
  • EndpointSlice supersedes Endpoints — implementing against the deprecated type is a Phase-2 dead end.
  • Consul's long-poll returns 200 even on a no-op timeout; compare X-Consul-Index, not the status code.
  • A discoverer that fails to connect must never empty the pool (I8) — last-good wins.

14.7 Performance Concerns

  • BackendPool::snapshot() is a single atomic load — O(1), no lock (I3-adjacent guarantee).
  • Discovery push frequency is bounded per source (e.g. Consul long-poll blocks up to 5 min server-side) to avoid needlessly rebuilding the Maglev/Ketama table (I13) on every push.

14.8 Edge Cases

  • A discoverer that emits an empty initial snapshot (new cluster, no backends yet): the pool starts empty and Selector::pick returns NoHealthy until the first non-empty push.
  • Two discoverers racing to update the same cluster (misconfiguration): the config validator (Phase 4 hardens this) should reject more than one Discoverer per ClusterId.
  • A Kubernetes API server outage: lb_discovery_stale_seconds for the k8s discoverer rises; pool holds last-good.

14.9 Failure Analysis

  • What breaks: a discovery source stays down long enough that the last-good pool becomes meaningfully wrong (backends decommissioned outside the proxy's knowledge).
  • Detection: lb_discovery_stale_seconds crosses an alerting threshold (§27).
  • Blast radius: requests routed to decommissioned backends — bounded by the health checker (Phase 5, §17) catching the resulting connection failures.
  • Containment: health checks are independent of discovery freshness (P5) and will eject.
  • Recovery path: discovery source recovery triggers a fresh push; pool updates atomically.
  • Operator visibility: docs/runbooks/upstream-flap.md.

14.10 Operational Notes

  • Deployment: each discoverer is a background task per cluster, started at reload time.
  • Metrics: lb_discovery_stale_seconds, lb_discovery_errors_total, lb_pool_size.
  • Rollback: reverting a cluster's discovery config takes effect on next reload (§22).
  • Compatibility: DiscoveryConfig is additive-only across versions (§28).

15. Phase 3 — Algorithm Library

15.1 Objectives

  • Implement all ten Selectors: RR, WRR, LC, WLC, P2C, EWMA-P2C, Maglev, Ketama, Jump, LatencyAware.
  • Every stochastic algorithm ships a deterministic conformance fixture (P14).
  • Constraints introduced: pick must stay allocation-free and synchronous (I3).

15.2 Detailed Implementation Steps

  • RoundRobin (round_robin.rs) — per-selector AtomicUsize counter mod the healthy-backend count; contended on multi-core, noted in §15.6.
  • WeightedRoundRobin (weighted.rs) — smooth WRR (the NGINX algorithm, §5 ref-impl): each backend's current_weight accumulates effective_weight per pick; the pick is the max current_weight, then subtract total_weight — avoids naive WRR's burst-then-pause pattern.
  • LeastConnections/WeightedLeastConnections (least_conn.rs) — pick min active_requests (LC) or min active_requests / weight in fixed-point (WLC); tie-break by oldest last_pick_micros to spread load onto freshly-added backends.
  • PowerOfTwoChoices (p2c.rs) — sample two backends without replacement, pick lower active_requests; implements the Mitzenmacher result (§5 P4/P5) that this bounds max load at O(log log N) vs round-robin's O(log N / log log N) — cited inline: applies §5 Mitzenmacher 2001/1996 and Dean & Barroso "Tail at Scale" (P3, I3).
  • EwmaP2C (ewma_p2c.rs) — per-backend ewma_latency_micros updated via a bounded compare-exchange loop (ewma = alpha·sample + (1-alpha)·ewma); sample two, pick lower EWMA; the Finagle variant (§5 ref-impl, ADR-12) that dampens transient herd effects.
  • Maglev (maglev.rs) — build the M-slot lookup table (default M = 65,537, a prime) per Eisenbud et al. 2016 §3 (§5 P1, §8.7 worked example); rebuild triggered only from the discovery/reload task (I13), never pick; lookup is table[hash(key) % M], O(1).
  • Ketama (ketama.rs) — classic ring: R virtual nodes per backend (default 160) on a 2^32-position ring; lookup walks clockwise to the first virtual node (§5 Karger).
  • JumpHash (jump.rs) — the Lamping & Veach two-line jump algorithm, O(log N) time, O(1) memory; removing a non-tail backend requires renumbering, so a removal is modeled as an ejection routed to a fallback RoundRobin over survivors.
  • LatencyAware (latency_aware.rs) — EWMA-P2C variant that excludes backends whose EWMA exceeds a configurable percentile (default p99) of the cluster from the random sample.
  • xxhash-rust (ADR-19) is the hash function backing Maglev/Ketama/Jump key hashing.

15.3 Deliverable

  • All ten algorithms implement Selector (§11.4); a common conformance harness runs every algorithm against a seeded backend list and asserts the expected pick distribution.

15.4 Acceptance Criteria

  • Each stochastic algorithm's pick distribution over 10,000 samples passes a chi-square goodness-of-fit test at p > 0.01 against its expected distribution (fixture per algorithm, §15.5).
  • pick p50 < 10 µs, p99 < 50 µs at 100 backends; p99 < 200 µs at 10,000 backends (§4, §31 M6/M7).
  • Maglev table construction for M=65,537, N=100 completes in < 10 ms off the request path (§35 derivation; I13).

15.5 Conformance Fixtures

  • conformance/corpora/algorithms/round_robin.json, weighted_rr.json, least_conn.json, weighted_least_conn.json, p2c.json, ewma_p2c.json, maglev.json, ketama.json, jump.json, latency_aware.json — one per algorithm: seed, backend list, expected distribution, chi-square tolerance.
  • conformance/corpora/algorithms/maglev_disruption.json — asserts 1/N disruption bound on backend removal (§8.7).

15.6 Pitfalls

  • Round-robin's atomic counter is contended on multi-core; a per-thread counter is the Phase-1 optimization if profiling shows contention (§31).
  • Maglev's O(M·N) construction re-runs on every backend-list change — for M=65,537, N=100 this is ~6.5 ms (§35); running it on the data path violates I13.
  • P2C's "sample two" must be without replacement — sampling with replacement biases toward picking the same backend twice on small clusters.
  • Jump hash's O(1)-memory property is bought at the cost of no true "remove" operation — modeling removal as ejection-to-fallback is a deliberate, documented compromise, not a bug.

15.7 Performance Concerns

  • Cache locality: the healthy-backend filter (Vec<&Arc<Backend>>) is rebuilt per pick for RR/WRR/LC/WLC/P2C — for large N this becomes the dominant cost; §35 quantifies the ceiling where a cached healthy-subset index becomes necessary.
  • EWMA's compare-exchange loop is bounded by contention on a single AtomicU64 per backend; under high fan-in this can retry, but never blocks (I3).
  • Maglev/Ketama/Jump lookups are O(1)/O(log N)/O(log N) respectively and dominate none of the p99 budget at design-ceiling backend counts (§4).

15.8 Edge Cases

  • All backends unhealthy: every algorithm returns PickError::NoHealthy (I4); no algorithm silently falls back to a different one (P6).
  • A single-backend cluster: P2C degenerates to always picking that backend — correct, not a bug.
  • A backend added mid-Maglev-table-lookup (concurrent reload): the lookup always completes against one consistent snapshot (I2) — never a torn table.
  • Weight of 0: WRR/WLC must exclude a zero-weight backend from selection entirely, not merely deprioritize it.

15.9 Failure Analysis

  • What breaks: a chi-square regression in a stochastic algorithm's fairness (e.g. a correlated RNG seed) only manifests under real production load, not in a quick manual test.
  • Detection: the seeded conformance fixture (P14) catches it deterministically in CI before merge.
  • Blast radius: one cluster's traffic skews toward a subset of backends — bounded by the outlier ejector (Phase 8, §20) eventually correcting for resulting overload.
  • Containment: algorithm changes are gated behind the fixture; a failing fixture blocks merge (§29).
  • Recovery path: revert to the previous algorithm version via config (fail-open, P6).
  • Operator visibility: lb_pick_duration_seconds and per-backend active_requests expose skew in the dashboard (§27).

15.10 Operational Notes

  • Deployment: algorithm choice is per-cluster config, hot-reloadable without restart (§22).
  • Metrics: lb_pick_duration_seconds{algorithm}, per-backend active_requests gauge.
  • Rollback: switching AlgorithmConfig back is a config reload, not a code change.
  • Compatibility: adding an eleventh algorithm is additive; removing one requires a deprecation window (§28).

16. Phase 4 — L7 Routing & Traffic Management

16.1 Objectives

  • Resolve a request to a RouteAction (§11.5): proxy, redirect, direct, or a canary/split variant.
  • Ship rewrite, redirect, canary, traffic-split, and shadow-mirroring.
  • Constraints introduced: routing must remain a pure function of (request, snapshot) (P7); no per-request mutable routing state.

16.2 Detailed Implementation Steps

  • lb-router::matcher — host (exact/suffix/regex), path (exact/prefix/regex), method, header, and query-parameter matchers; regex matchers use the regex crate (RE2-compatible, no catastrophic backtracking) — validated at config-load time, never regex_lite (applies P7, Fielding's statelessness argument §5).
  • lb-router::lib — a path trie for prefix matchers (O(path_segments) lookup); regex matchers fall back to a linear scan after a trie miss; specificity resolves ties (/api/v1/users beats /api/v1).
  • lb-router::rewrite — path rewrite (/old/* → /new/$1); header add/set/remove on request and response; X-Request-Id preserved if present, else generated (UUIDv7).
  • Redirect action: HTTP 301/302/307/308 with a templated Location; scheme upgrade (http→https) as a first-class action, never a string template.
  • lb-router::canary / split — canary is a percentage routed to an alternate cluster; split is a weighted assignment across N clusters via a hash of X-Request-Id/consumer id modulo a 10,000-bucket space (P7: same key ⇒ same cluster within a snapshot generation).
  • lb-router::shadow — mirrors the request to a shadow cluster; response discarded; a short shadow_timeout_ms bounds worst case so a slow shadow never slows the primary (I3-adjacent: the shadow task is spawned and forgotten, never awaited inline).
  • lb-router::jwt — validates the bearer token via the sibling Auth-System project (rank 49, §5); extracts a claim (sub/tenant_id/plan) for routing; a missing/invalid token either short-circuits 401 or falls through to the matcher's default cluster, per-route configurable.

16.3 Deliverable

  • Router::route resolves a request to a RouteAction in microseconds on a 1,000-route table.
  • Conformance fixtures cover every matcher type, every rewrite primitive, and all four routing actions.

16.4 Acceptance Criteria

  • Route resolution p99 < 50 µs on a 1,000-route table (fixture route_1000_p99.json).
  • Canary/split assignment is stable for a fixed X-Request-Id across 10,000 repeated lookups within one snapshot generation (fixture split_stability.json).
  • Shadow requests never add > 1 ms to the primary path's p99 regardless of shadow-cluster latency (fixture shadow_isolation.json).

16.5 Conformance Fixtures

  • conformance/corpora/routing/matchers_all.json — host/path/method/header/query, exact matches for every routing action.
  • conformance/corpora/routing/route_1000_p99.json — 1,000-route table, p99 latency assertion.
  • conformance/corpora/routing/split_stability.json — stable-hash assignment fixture.
  • conformance/corpora/routing/shadow_isolation.json — shadow-latency-isolation fixture.

16.6 Pitfalls

  • Regex matchers are a footgun for catastrophic backtracking; the config validator refuses any pattern flagged by a backtracking-risk heuristic, and the runtime never uses regex_lite.
  • Header values are byte strings, not UTF-8 strings; some clients send invalid UTF-8 — match on HeaderValue::as_bytes(), never a lossy string conversion.
  • The shadow path must never influence response timing — spawn and return immediately; only a completion metric fires.
  • JWT validation must precede rate-limiting so an unauthenticated burst is priced correctly (§19.6 cross-reference) — validating after limiting lets invalid-token floods bypass the per-consumer budget.

16.7 Performance Concerns

  • The path trie keeps prefix lookup at O(path_segments); regex fallback is linear and must be bounded (config validator caps regex route count per listener).
  • HttpRequestHead is parsed once and reused across routing, rate-limiting, and auth (P3) — re-parsing per stage would triple the allocation cost.
  • Canary/split hashing uses xxhash-rust (ADR-19) for speed; cryptographic hashing here would be pure overhead since the key space is not attacker-adversarial in the routing context.

16.8 Edge Cases

  • A request matching zero routes: RouterDecision::NotFound, synthetic 404, no upstream contact.
  • A request matching multiple routes at equal specificity: resolved by declaration order in the snapshot (deterministic, documented, not "first match wins by accident").
  • A canary percentage of 0% or 100%: degenerates cleanly to "never canary" / "always canary" — no special-cased code path.
  • A shadow cluster that is itself unhealthy: the mirrored request fails silently (metric-only), never surfaces to the client.

16.9 Failure Analysis

  • What breaks: a misconfigured regex route causes catastrophic backtracking under a crafted path, stalling the request-handling task.
  • Detection: the config validator's backtracking-risk heuristic (rejects at load time, not at request time) plus a per-route routing-latency histogram.
  • Blast radius: without the validator, one crafted request could stall one task; with the validator, the configuration is rejected before it ever serves traffic.
  • Containment: config validation is part of the two-phase reload (§22.2) — a bad route config never reaches the data path.
  • Recovery path: reload rolled back to the previous snapshot (I2).
  • Operator visibility: docs/runbooks/triage.md documents the regex-validator rejection message format.

16.10 Operational Notes

  • Deployment: routing config lives in the same ConfigSnapshot as clusters; both reload atomically together.
  • Metrics: lb_requests_total{route}, route-resolution latency histogram.
  • Rollback: a bad route table is caught by validation before it is ever live (§22.2).
  • Compatibility: RouteAction variants are additive-only across versions (§28).

17. Phase 5 — Health Checking

17.1 Objectives

  • Keep the backend list honest via four active check kinds (TCP/HTTP/gRPC/exec) plus passive outlier ejection.
  • Reconcile active and passive signals into one BackendStatus (I4, P5).
  • Constraints introduced: health checks run on a connection pool separate from the request pool (never steal request-serving capacity).

17.2 Detailed Implementation Steps

  • lb-health::tcp — TcpChecker: connect, success = connect, close immediately; default timeout 1 s (§4).
  • lb-health::http — HttpChecker: GET /healthz; status-code allowlist (200..=399 default, configurable); optional body match, optional header match.
  • lb-health::grpc — GrpcChecker: speaks gRPC Health v1 (grpc.health.v1.Health/Check); a SERVING response is healthy, any other status unhealthy.
  • lb-health::exec — ExecChecker: configurable subprocess, exit 0 = healthy; stdout captured to a bounded ring buffer for the runbook; per-check timeout kills the process.
  • lb-health::passive — OutlierEjector: triggered by request completions (not a Checker); a backend with consecutive_5xx ≥ threshold (default 5) within interval_seconds (default 30) is ejected for base_ejection_time_seconds · eject_count², capped by max_ejection_percent (default 50% of cluster backends) — the ejected backend continues to be actively probed; a passing probe clears the ejection (I4).
  • Reconciliation: BackendStatus.healthy is the AND of the active-check flag and "not passively ejected" — the two paths write independently, never sharing a lock (P5, applies I4).
  • All four Checker implementations satisfy the trait's normative contract (§11.6): probe returns within timeout(); longer probes are Inconclusive, not Unhealthy — an overloaded-but-alive backend is not the same failure as a dead one.

17.3 Deliverable

  • All five health-check kinds (four active + passive) wired into BackendStatus.
  • A flapping-backend conformance test: a backend flipping healthy/unhealthy every 5 s never receives traffic during its unhealthy window.

17.4 Acceptance Criteria

  • A backend returning 100% 5xx is passively ejected within 2 s (fixture outlier_2s.json, §31 M3).
  • Flap-soak (5 s period, active+passive both wired): zero traffic sent during any unhealthy window (fixture flapping_backend.json).
  • Inconclusive outcomes never advance the consecutive-pass counter (fixture inconclusive_no_advance.json).

17.5 Conformance Fixtures

  • conformance/corpora/reload/flapping_backend.json — 5 s flap period, zero traffic during unhealthy windows.
  • conformance/corpora/reload/outlier_2s.json — 100% 5xx backend ejected within 2 s.
  • conformance/corpora/reload/inconclusive_no_advance.json — timeout-driven Inconclusive does not clear or advance health state.
  • conformance/corpora/reload/max_ejection_cap.json — a 2-backend cluster never ejects more than max_ejection_percent.

17.6 Pitfalls

  • Health checks consume upstream connection slots — use a dedicated connection pool, never the request-serving pool, or health-check load starves real traffic.
  • A health-check response slower than the request timeout must not be reported Healthy — the upstream may be overloaded, not dead; Inconclusive exists for exactly this and does not advance the pass counter.
  • Passive ejection on a 2-backend cluster will eject one backend on the first 5xx storm without the max_ejection_percent cap (default 50%) — do not disable the cap "to be safe."

17.7 Performance Concerns

  • Active probes are scheduled per-backend on independent timers (P4: never on the request path); probe concurrency is bounded to avoid a probe storm against a large backend pool.
  • The passive ejector's consecutive_5xx counter is a single atomic increment on the request completion path — negligible cost (P3).

17.8 Edge Cases

  • A backend healthy by active check but ejected by passive outlier: BackendStatus.healthy correctly reports false (AND semantics) until the ejection clears.
  • Exec checker subprocess that never exits: killed at timeout(), reported Inconclusive (not Unhealthy — the check itself failed, not necessarily the backend).
  • A gRPC health check against a backend that doesn't implement Health v1: treated as Unhealthy (unimplemented status), not a crash.
  • All backends simultaneously ejected (max_ejection_percent reached at 100% concurrently failing): pick returns PickError::AllEjected, distinct from NoHealthy, for cleaner incident triage.

17.9 Failure Analysis

  • What breaks: an active health check itself becomes the bottleneck against an overloaded backend, worsening the overload it is trying to detect.
  • Detection: health-check latency histogram per checker kind; Inconclusive rate spike.
  • Blast radius: bounded to the checked backend's probe traffic — the dedicated connection pool (§17.6) prevents it from stealing request capacity.
  • Containment: exponential probe-interval backoff on repeated Inconclusive results.
  • Recovery path: once probes succeed again, the healthy-threshold counter must reach its configured value before the backend rejoins (not a single pass).
  • Operator visibility: docs/runbooks/upstream-flap.md.

17.10 Operational Notes

  • Deployment: health-checker tasks start per-cluster at reload time, alongside discovery.
  • Metrics: lb_health_check_total{cluster, backend, kind, outcome}.
  • Rollback: a checker config change (e.g. threshold tuning) takes effect on next reload.
  • Compatibility: HealthConfig is additive-only across versions (§28).

18. Phase 6 — TLS Termination & Upstream Re-Encryption

18.1 Objectives

  • Terminate TLS at the listener with SNI multiplexing; re-encrypt to upstream by default (P8).
  • Support cert hot-reload without dropping in-flight connections.
  • Constraints introduced: TLS 1.3 default, TLS 1.2 opt-in per listener for legacy clients.

18.2 Detailed Implementation Steps

  • lb-tls::server — Rustls server (ADR-06); ALPN advertises h2, http/1.1 (and h3 from Phase 11, §23); a ResolvesServerCert implementation reads the per-SNI cert map from the ConfigSnapshot (§5 Grigorik, HPBN ch. 4).
  • Session tickets: enabled, rotated hourly with a per-listener master key (I11) — a master-key rotation invalidates outstanding tickets without affecting in-flight connections (the cert is only consulted at handshake).
  • 0-RTT: disabled by default per route (RFC 8470, §5); enabling it per route is the operator's explicit replay-safety decision.
  • lb-tls::client — Rustls client for upstream re-encryption (P8); ServerName is the cluster's configured upstream name (typically DNS, not a bare IP); cert verification is mandatory; a per-cluster CA bundle pin is supported; mTLS to upstream presents a configured client cert+key.
  • lb-tls::reload — the ResolvesServerCert implementation holds an ArcSwap<HashMap<ServerName, CertifiedKey>>; a reload swaps the map; in-flight connections keep their already-negotiated cert (I11).

18.3 Deliverable

  • HTTPS proxy serving multiple SNI certificates to HTTP/1.1 and HTTP/2 clients, re-encrypting to upstream.
  • A conformance fixture verifying a wrong-SNI request receives a TLS unrecognized_name alert.

18.4 Acceptance Criteria

  • 10 distinct SNI certificates dispatch with 100% correct-cert selection (fixture sni_dispatch_10.json, §31 M4).
  • TLS handshake p99 < 5 ms with session resumption, < 25 ms full handshake (§4).
  • A cert hot-reload during 1,000 concurrent handshakes drops zero in-flight connections (fixture cert_reload_soak.json).

18.5 Conformance Fixtures

  • conformance/corpora/tls/sni_dispatch_10.json — 10-SNI, expected-cert-subject fixture.
  • conformance/corpora/tls/wrong_sni_alert.json — unconfigured SNI yields unrecognized_name.
  • conformance/corpora/tls/cert_reload_soak.json — 1,000-handshake concurrent reload, zero drops.
  • conformance/corpora/tls/ticket_rotation.json — I11 ticket-rotation-window assertion.

18.6 Pitfalls

  • TLS 1.3 0-RTT data is replayable; the proxy does not rate-limit it without an explicit anti-replay cache — default off, and non-idempotent methods must never enable it.
  • Session tickets outliving a master-key rotation force a full handshake fallback; tls_full_handshakes_total rising is the operator signal something is misconfigured (I11).
  • Upstream certs expiring mid-flight kill the next connection, not the in-flight one — upstream_cert_expiry_seconds must alert at 14 days remaining, not at expiry.

18.7 Performance Concerns

  • Full handshakes are CPU-bound (asymmetric crypto); the 25 ms p99 budget (§4) assumes AVX2 acceleration in Rustls's backing crypto provider.
  • Session-ticket resumption avoids the asymmetric-crypto cost entirely — the 5x latency difference (5 ms vs 25 ms, §35) is why resumption is not optional at scale.

18.8 Edge Cases

  • A connection with no SNI (legacy HTTP/1.0-over-TLS to a wildcard cert): served the configured default certificate, or a TLS alert if none is configured.
  • A cert that expires between reload construction and reload commit: the two-phase reload (§22.2) validates expiry at the validation phase, not just at load time.
  • mTLS upstream where the client cert itself has expired: connection fails at handshake, not silently falls back to plaintext.

18.9 Failure Analysis

  • What breaks: an operator rotates the master key without coordinating with a rolling fleet upgrade, causing a fleet-wide full-handshake spike.
  • Detection: tls_full_handshakes_total spike correlated across all replicas.
  • Blast radius: CPU load spike, not availability loss (fallback to full handshake still succeeds).
  • Containment: master-key rotation is itself staged via the admin API with an audit record (I10).
  • Recovery path: the spike self-resolves as tickets re-establish post-rotation.
  • Operator visibility: docs/runbooks/high-latency.md documents this exact signature.

18.10 Operational Notes

  • Deployment: certs are provisioned via the admin API or a file-watch discovery source feeding lb-tls::reload.
  • Metrics: lb_upstream_tls_handshake_seconds, tls_full_handshakes_total, upstream_cert_expiry_seconds.
  • Rollback: cert map swap is atomic and instantly revertible via another reload.
  • Compatibility: TLS 1.2 remains opt-in per listener indefinitely for legacy clients (§28).

19. Phase 7 — Rate Limiting

19.1 Objectives

  • Protect backends from runaway clients with per-route and per-consumer limits.
  • Constraints introduced: rate-limit decisions must be O(1) per call (I14) and never block the data path.

19.2 Detailed Implementation Steps

  • lb-rate-limit::token_bucket / leaky_bucket — embed the sibling Rate-Limiter project's canonical primitives (rank 39, §5) rather than re-implementing; token bucket suits bursty API limits (refill rate + burst capacity), leaky bucket suits smooth proxy-protection limits.
  • Per-route limits: the RouteConfig.rate_limit block declares (algorithm, rps, burst, key); key is the limiting dimension — consumer_id (from a JWT claim, §16.2), client_ip, route_id, or a header value.
  • Per-consumer limits: a consumer (typically the JWT subject) can be limited globally across all routes; the limit map is admin-API-reloadable at runtime (P10, I10).
  • 429 response: standard HTTP 429 with Retry-After and RateLimit-* headers; body configurable per route.
  • Ordering (applies P7, I14): JWT validation (§16.2) precedes the rate-limit check so an unauthenticated burst is still priced into someone's budget rather than bypassing limiting entirely.

19.3 Deliverable

  • Token-bucket and leaky-bucket rate limiters wired into the per-route and per-consumer paths.
  • A sustained-overload conformance test and a burst-tolerance conformance test.

19.4 Acceptance Criteria

  • 1,000 RPS sustained against a 100 RPS limit: ≥ 90% of requests receive 429 (fixture sustained_429.json).
  • A 200-request burst against a 100 RPS/200-burst limit returns 200 OK; the next 200-request burst within the same second returns 429 (fixture burst_429.json).
  • Retry-After is monotonic non-decreasing across consecutive denies for the same key (I14, fixture retry_after_monotonic.json).

19.5 Conformance Fixtures

  • conformance/corpora/routing/sustained_429.json — 1,000 RPS vs 100 RPS limit, ≥90% denied.
  • conformance/corpora/routing/burst_429.json — burst-tolerance fixture.
  • conformance/corpora/routing/retry_after_monotonic.json — I14 monotonicity assertion.

19.6 Pitfalls

  • Per-consumer-id limiting requires the consumer identified before the rate-limit check; JWT validation cost must itself be inside the rate-limit budget — a burst of 1,000 invalid JWTs against an unauthenticated route still costs CPU and must be bounded independently (§16.6 cross-reference).
  • A distributed (cross-replica) rate limiter needs shared state; Phase 0–10 ship per-instance limiting only — the cross-instance variant is PhaseDeferred("§38").

19.7 Performance Concerns

  • RateLimiter::check is O(1) per call by construction (I14) — a hash-map lookup plus a fixed-point arithmetic update, no allocation (P3).
  • Per-consumer global limits require a shared map keyed by consumer id; sized to the expected consumer cardinality, not per-request.

19.8 Edge Cases

  • A key that has never been seen before: initialized lazily with a full bucket/allowance, not a rejection.
  • Clock skew between the request's now_micros (P13) and the bucket's last-refill timestamp: bounded by the Clock abstraction's monotonicity guarantee — never wall-clock-derived.
  • A rate-limit config removed entirely on reload: existing buckets are dropped; the next request for that key starts fresh (documented behavior, not silently persisted forever).

19.9 Failure Analysis

  • What breaks: an unbounded per-consumer map grows without limit under a many-unique-consumer attack (each new JWT sub claim creates a new bucket).
  • Detection: lb_rate_limit_denies_total combined with a bucket-count gauge.
  • Blast radius: memory growth, not availability loss until the process nears its RSS ceiling (§4).
  • Containment: an LRU eviction policy on the per-consumer bucket map bounds worst-case memory.
  • Recovery path: evicted buckets simply reinitialize on next request — no correctness loss, only a burst-tolerance reset.
  • Operator visibility: bucket-count gauge alerted in docs/runbooks/triage.md.

19.10 Operational Notes

  • Deployment: rate-limit config lives in the same ConfigSnapshot; reloads atomically (§22).
  • Metrics: lb_rate_limit_denies_total{route, key_kind}.
  • Rollback: reverting a limit is a config reload; no persistent bucket state survives a process restart by design (in-memory only, Phase 0–10 scope).
  • Compatibility: RateLimitConfig is additive-only across versions (§28).

20. Phase 8 — Circuit Breaking & Outlier Ejection

20.1 Objectives

  • Prevent one bad backend, or a bad fraction of a cluster, from poisoning the whole cluster.
  • Ship per-cluster and independent per-backend breakers, plus bulkheading.
  • Constraints introduced: half-open probe quota must never be exceeded concurrently (I12).

20.2 Detailed Implementation Steps

  • lb-circuit::ejection — layers directly on the Phase-5 passive OutlierEjector (§17.2, P5, I4) rather than duplicating its bookkeeping.
  • lb-circuit::breaker — per-cluster breaker: Closed → Open when the ejected-backend fraction exceeds threshold_percent; Open → HalfOpen after open_duration_seconds; HalfOpen admits a bounded probe quota (I12) — all succeed ⇒ Closed, any fail ⇒ Open (§8.3 state table).
  • Per-backend breaker: independent of the cluster-level one; a backend with consecutive_5xx ≥ breaker_threshold is marked open; a probe quota over M seconds tests recovery.
  • Bulkheading: per-backend max_concurrent_requests; excess requests are queued (bounded size, default 2 × max_concurrent_requests) or short-circuited, per config.
  • The half-open probe quota is an atomic counter (I12); an excess probe attempt during HalfOpen is short-circuited to 503 rather than admitted, preventing the exact thundering-herd-on-recovery failure mode documented in §20.6.

20.3 Deliverable

  • Per-cluster and per-backend circuit breakers wired to the outlier ejector; bulkheading caps in place.
  • A conformance test: a 100%-5xx backend ejects within 2 s, the cluster breaker opens at threshold_percent, half-open probing recovers within recovery_seconds once the backend heals.

20.4 Acceptance Criteria

  • Cluster breaker opens within one health-check interval of crossing threshold_percent (fixture breaker_open.json, default interval per §17).
  • Half-open recovery completes within recovery_seconds (default 30 s) once the backend passes its probe quota (fixture breaker_recover.json).
  • Bulkhead queue never exceeds 2 × max_concurrent_requests entries (fixture bulkhead_cap.json).

20.5 Conformance Fixtures

  • conformance/corpora/reload/breaker_open.json — threshold-crossing opens the breaker.
  • conformance/corpora/reload/breaker_recover.json — half-open probe-quota recovery timing.
  • conformance/corpora/reload/bulkhead_cap.json — queue-size ceiling assertion.
  • conformance/corpora/reload/half_open_quota_exceeded.json — excess probes short-circuit to 503, never admitted (I12).

20.6 Pitfalls

  • Circuit breakers can stampede: when a breaker opens, a herd of clients sees 5xx; if they all retry the instant it half-opens, the healing backend is hit by a thundering herd — the half-open probe quota (I12) exists specifically to prevent this; do not skip it "to recover faster."
  • Bulkheading queues are a footgun: a 10,000-entry queue against a 100 ms latency budget produces 1,000 client-side timeouts before it drains — the default 2× sizing is deliberately conservative.

20.7 Performance Concerns

  • The half-open quota counter is a single atomic, checked before admission — negligible cost on the hot path (P3, I3).
  • Bulkhead queuing, when engaged, adds queueing latency; the default queue size is chosen to keep worst-case wait under the route's configured timeout, not to maximize throughput.

20.8 Edge Cases

  • A cluster with only 2 backends: threshold_percent interacts with max_ejection_percent (§17) — both defaults are tuned so a single bad backend does not trip the cluster breaker from ejection alone.
  • A backend that recovers mid-probe-quota (passes 3 of 5 probes, half-open window ends): the outcome is decided strictly by the configured quota, not by a majority-of-attempts heuristic — a partial pass count that doesn't meet the quota re-opens.
  • Concurrent per-backend and per-cluster breaker trips on the same backend: the pick path checks both; either one being open excludes the backend.

20.9 Failure Analysis

  • What breaks: a slow (not failing) backend trips 5xx-based ejection incorrectly if request timeouts are misclassified as 5xx rather than a distinct timeout class.
  • Detection: a spike in lb_outlier_ejections_total correlated with lb_request_duration_seconds p99, not with actual 5xx status codes.
  • Blast radius: one backend incorrectly ejected — bounded by max_ejection_percent.
  • Containment: timeouts are tracked as a distinct outcome from consecutive_5xx (§17.2) so slow-but-alive backends are not conflated with actually-erroring ones.
  • Recovery path: the misclassified backend clears on its next passing active probe.
  • Operator visibility: docs/runbooks/5xx-storm.md documents the distinction.

20.10 Operational Notes

  • Deployment: breaker thresholds are per-cluster config, hot-reloadable (§22).
  • Metrics: lb_circuit_state{cluster} (0=closed, 1=half-open, 2=open).
  • Rollback: a breaker config change is a reload; no persistent breaker state survives a process restart (in-memory, resets to Closed on restart — documented, not a bug).
  • Compatibility: CircuitConfig is additive-only across versions (§28).

Cardinality budget < 50,000 series at 1,000-backend/100-route scale (§4); the backend label is opt-in per cluster.
  • lb-observe::tracing — OpenTelemetry spans wrap every request: lb.request (root), lb.route, lb.pick, lb.upstream.connect, lb.upstream.tls, lb.upstream.send, lb.upstream.recv; attributes include route_id, cluster_id, backend_id, algorithm, status_code, request_id; trace context propagates upstream via traceparent; export uses the batching exporter, never inline (P4).
  • lb-observe::log — one JSON line per request: ts, request_id, client_ip, method, authority, path, status, bytes_in, bytes_out, duration_ms, cluster, backend, algorithm, tls_version, alpn, route_id; sampling 100% default, configurable to 1% per route; formatted lazily on a writer task via a bounded mpsc channel (P3, ADR-26).
  • lb-observe::error_budget — lb_error_budget_remaining{route,slo} evaluated against the route's configured SLO and the histogram data (§5 SRE book ch. 4).

21.3 Deliverable

  • A Grafana dashboard JSON (docs/api/ sibling asset, referenced from docs/runbooks/) rendering the four-golden-signals view (latency, traffic, errors, saturation).
  • A trace exported to a Jaeger-compatible OTLP sidecar shows the full request lifecycle including upstream connect and TLS handshake spans.

21.4 Acceptance Criteria

  • Metric cardinality stays < 50,000 series at 1,000-backend/100-route scale (fixture cardinality_budget.json).
  • Access-log line emitted for 100% of completed requests at 100,000 req/s sustained for 60 s, zero dropped log lines (fixture access_log_no_drop.json).
  • Trace export never adds > 100 µs to the request path even when the OTLP endpoint is artificially slowed to 500 ms (fixture trace_export_isolation.json).

21.5 Conformance Fixtures

  • conformance/corpora/reload/cardinality_budget.json — series-count ceiling assertion.
  • conformance/corpora/reload/access_log_no_drop.json — 100K req/s, zero dropped log lines.
  • conformance/corpora/reload/trace_export_isolation.json — slow-OTLP isolation fixture.

21.6 Pitfalls

  • Histogram bucket boundaries matter more than people expect: the default Prometheus buckets are wrong for sub-millisecond latency — the proxy ships its own bucket definitions (§5 SRE book).
  • Trace export blocks the request thread if the OTLP endpoint is slow and export is inline — use the batching exporter exclusively, never export from the request task.
  • The access log is on the hot path; format it lazily on the writer task and pass typed fields through the channel, never a pre-formatted string (P3, ADR-26).

21.7 Performance Concerns

  • Metric-handle lookups are O(1) via the typed registry (P9) — no string hashing per emission.
  • The bounded mpsc channel to the log-writer task applies backpressure by dropping (with a drop-counter metric) rather than blocking the request thread under sustained overload — a documented, deliberate lossy-under-extreme-load tradeoff.

21.8 Edge Cases

  • The OTLP endpoint is unreachable at startup: tracing degrades to no-op with a startup warning, never blocks proxy startup.
  • A metric label value containing characters Prometheus rejects: sanitized at the type boundary before emission, never passed through raw.
  • Log-writer channel saturation: log lines are dropped (never buffered unbounded, P11) and lb_access_log_dropped_total increments.

21.9 Failure Analysis

  • What breaks: an operator adds a high-cardinality label (e.g. raw client IP) to a metric outside the typed registry's guardrails, exploding series count.
  • Detection: cardinality_budget.json-style CI check plus Prometheus's own scrape_samples_scraped trending upward.
  • Blast radius: Prometheus server memory pressure, not proxy availability.
  • Containment: P9's type-level cardinality bound makes this a compile-time rejection, not a runtime surprise.
  • Recovery path: revert the offending metric definition; no data-path impact either way.
  • Operator visibility: docs/runbooks/triage.md.

21.10 Operational Notes

  • Deployment: metrics scraped from /admin/metrics (§22) or the main listener per config.
  • Metrics: (this phase is the metrics implementation — see §21.2 for the full list).
  • Rollback: dashboard/alert changes are independent of proxy version; the metric names are stable across versions (§28).
  • Compatibility: new metrics are additive; removing one requires a deprecation window (§28).

22. Phase 10 — Admin API & Hot Reload

22.1 Objectives

  • Make the proxy operable: reload, drain, inspect, all via one audited, mTLS-only API (P10).
  • Ship the two-phase reload protocol underpinning I1/I2.
  • Constraints introduced: every mutation writes an audit record before returning success (I10).

22.2 Detailed Implementation Steps

  • lb-admin::server — an axum-driven HTTP server, mTLS-only by default (P8-adjacent trust boundary); a bearer-token mode exists for development only and is refused in production by the config validator.
  • lb-admin::api — endpoints: POST /admin/config/reload (atomic snapshot swap from body or file), POST /admin/config/validate (dry-run, returns diff + validation result), GET /admin/config (current snapshot, secrets redacted), POST /admin/cluster/<id>/drain (mark every backend draining, P12), POST /admin/backend/<id>/drain (single backend), GET /admin/stats, GET /admin/health, GET /admin/metrics.
  • Reload semantics (§8.4 state machine): the new ConfigSnapshot is built in full before the ArcSwap::store (ADR-07, I1, I2); listeners absent from the new snapshot enter Draining — stop accepting, existing connections continue to idle-out; new listeners bind and start accepting before old ones drain, so there is no listener gap; clusters absent from the new snapshot enter Terminating — existing requests complete, the pool drops on last reference.
  • A reload that fails validation partway rolls back to the previous snapshot — the protocol is strictly two-phase: build-and-validate, then commit (I2).
  • lb-admin::audit — every admin call writes a structured audit entry (ts, actor, endpoint, request_body_hash, outcome) to a separate sink before the call is applied (I10); if the audit sink is unavailable, the admin call fails closed.
  • The drain endpoint is intentionally asymmetric with un-drain: un-draining only comes from a config reload, never a live admin call, preventing a fat-finger un-drain of a backend that should stay evicted.

22.3 Deliverable

  • The admin API serves its OpenAPI schema at docs/api/admin.openapi.yaml (ADR-15).
  • A reload soak test: 100 back-to-back reloads produce zero dropped requests.

22.4 Acceptance Criteria

  • 100-reload soak: zero dropped requests, zero 5xx storms, monotonically increasing generation (fixture reload_soak_100.json, §31 M5).
  • Time from /admin/config/reload acceptance to first request served on the new snapshot < 50 ms (§4, fixture reload_latency.json).
  • Every admin call — success or failure — produces exactly one audit record (fixture audit_completeness.json, I10).

22.5 Conformance Fixtures

  • conformance/corpora/reload/reload_soak_100.json — 100 reloads, zero drops, monotonic generation.
  • conformance/corpora/reload/reload_latency.json — < 50 ms time-to-first-new-request.
  • conformance/corpora/reload/audit_completeness.json — one audit record per admin call.
  • conformance/corpora/reload/rollback_on_invalid.json — a reload with an invalid cluster reference rolls back cleanly.

22.6 Pitfalls

  • A reload failing partway (e.g. a discoverer cannot connect for the new config) must roll back to the previous snapshot, not commit a half-built one — the two-phase protocol exists precisely for this (I2).
  • The audit log is the security boundary of the entire mutation surface; if it silently drops a record on sink failure, mutations become undebuggable — fail the call closed instead (I10).
  • Un-draining via a live admin call (rather than requiring a reload) is a fat-finger hazard — deliberately not exposed.

22.7 Performance Concerns

  • Reload cost is dominated by the Maglev/Ketama table rebuild for every affected cluster (§15, I13) — reloads are rate-limited (one per second default) to bound this cost under reload-storm misuse.
  • The admin API runs on its own listener/task set, entirely isolated from the data-path thread pool (P4) — an admin-API slowdown cannot degrade request latency.

22.8 Edge Cases

  • Two concurrent /admin/config/reload calls: the second's build phase races the first's commit; the config-generation counter and ArcSwap's atomicity ensure the later commit wins cleanly, never a torn state (I1).
  • A reload that only changes an unrelated cluster: listeners and clusters that didn't change keep their existing task state — no unnecessary connection churn.
  • /admin/config requested during an in-flight reload: returns the currently-live snapshot, never a partially-built one (I1).

22.9 Failure Analysis

  • What breaks: an operator scripts reloads faster than the rate limit, and reloads start queuing, silently increasing config-propagation latency.
  • Detection: lb_config_reload_total{outcome="rate_limited"} rising.
  • Blast radius: delayed config propagation, never dropped requests (I2 still holds).
  • Containment: the reload rate limit is itself audited and alertable (§27).
  • Recovery path: operator throttles their reload script; no proxy-side recovery action needed.
  • Operator visibility: docs/runbooks/triage.md.

22.10 Operational Notes

  • Deployment: the admin listener is bound to localhost or a management VLAN by default.
  • Metrics: lb_config_reload_total{outcome}, lb_config_generation, lb_admin_audit_failures_total.
  • Rollback: POST /admin/config/reload with the previous snapshot body is the rollback mechanism — no separate rollback API needed given I2's guarantees.
  • Compatibility: the OpenAPI schema is versioned; a breaking admin-API change requires a major version bump (§28).

23. Phase 11 — HTTP/2, HTTP/3 & gRPC

23.1 Objectives

  • Generalize the L7 path to multiplexed streams: HTTP/2 (Hyper), HTTP/3 (Quinn+h3), and gRPC pass-through over both.
  • Constraints introduced: HPACK/QPACK dynamic-table sizes are bounded to prevent header-bomb OOM (§25 T5).

23.2 Detailed Implementation Steps

  • lb-proxy-l7::h2 — Hyper's server::conn::http2::Builder / client::conn::http2::handshake (ADR-03, RFC 7540, §5); stream multiplexing over one TCP connection; connection- and stream-level flow control honored both directions; HPACK (RFC 7541) handled by Hyper, dynamic table capped at 4 KiB per side (mitigates T5).
  • ALPN dispatch: the TLS handshake (§18) negotiates h2 or http/1.1; the listener inspects the negotiated protocol and routes to the matching Hyper builder.
  • lb-proxy-l7::h3 — quinn::Endpoint::server for the QUIC listener (RFC 9000, §5 Langley et al. SIGCOMM 2017); ALPN advertises h3; the h3 crate layers HTTP/3 framing (RFC 9114) with QPACK (RFC 9204) as QUIC's analog of HPACK; 0-RTT is a per-route config choice (RFC 8470, same replay caveat as §18.2).
  • lb-proxy-l7::grpc — gRPC is HTTP/2 (or HTTP/3) with the framing convention compressed-flag(1B) | length(4B) | protobuf(length B) (§8.6); the proxy passes bytes through opaquely, never parsing protobuf (P3); grpc-status/grpc-message trailers are honored as HTTP/2 trailers — gRPC streaming (server/client/bidi) works because the proxy streams bodies end-to-end already (ADR-24).
  • H2-specific routing: :authority replaces Host; :path includes the query string, split on ? by the matcher (§16.2, applies P7).
  • H2-specific health checks: the HTTP checker (§17.2) speaks HTTP/2 when the upstream demands it; the gRPC checker is HTTP/2-native by definition.
  • UDP buffer tuning for QUIC: default Linux SO_RCVBUF (~200 KiB) is raised to 4 MiB at startup via setsockopt (§35 derives the sizing); recvmmsg/sendmmsg batch UDP I/O.
  • Connection migration: QUIC's NAT-rebind migration is honored; backend sticky-sessioning by connection_id preserves the pick assignment across migration.

23.3 Deliverable

  • End-to-end gRPC echo example via examples/grpc-p2c/.
  • HTTP/2 conformance against a subset of h2spec; HTTP/3 conformance against a subset of qns-interop.

23.4 Acceptance Criteria

  • HTTP/2 single-core throughput ≥ 80,000 req/s @ 1 KiB response (§4, §31 M8).
  • HTTP/3 conformance subset (qns-interop-derived) passes 100% (§31 M9).
  • gRPC conformance (unary + all three streaming modes) passes 100% (§31 M10).
  • HPACK/QPACK dynamic table capped at 4 KiB confirmed under a header-bomb fixture (T5, §25).

23.5 Conformance Fixtures

  • conformance/corpora/h2/h2spec_subset.json — HTTP/2 framing/flow-control conformance.
  • conformance/corpora/h3/qns_interop_subset.json — HTTP/3/QUIC conformance.
  • conformance/corpora/grpc/unary_streaming_bidi.json — full gRPC mode coverage.
  • conformance/corpora/h2/header_bomb.json — HPACK dynamic-table-size attack, capped at 4 KiB.

23.6 Pitfalls

  • HTTP/2 head-of-line blocking is a TCP-layer problem, not an HTTP-layer one — the fix is HTTP/3, not a proxy-side workaround.
  • gRPC errors return HTTP 200 with grpc-status != 0 in trailers — a status-class metric computed from HTTP status alone miscounts the error budget; the error-budget logic (§21.2) must special-case gRPC trailers.
  • HPACK/QPACK dynamic table size is per-connection; an uncapped table lets a misconfigured or malicious upstream/client OOM the proxy via header bombs — cap at 4 KiB on both sides.

23.7 Performance Concerns

  • QUIC congestion control is sensitive to the kernel UDP receive buffer; an undersized buffer presents as packet loss, masquerading as a tuning problem rather than a sizing one (§35 derives the 4 MiB choice).
  • HTTP/2 flow-control window mistuning (initial_stream_window_size) can stall a single stream while the connection has ample budget — the proxy clamps to a known-good default rather than trusting the upstream's advertised window blindly.

23.8 Edge Cases

  • A network path that blocks UDP (corporate firewall): HTTP/3 silently falls back to HTTP/2 via Alt-Svc; lb_alt_svc_fallback_total tracks this.
  • 0-RTT replay risk under an anycast-fronted deployment: a retransmitted 0-RTT request could be replayed by a different anycast node — 0-RTT is disabled for non-idempotent methods regardless of per-route config.
  • A gRPC bidi-streaming call held open indefinitely: subject to the same idle-timeout and drain semantics as any long-lived stream (P2, I9).

23.9 Failure Analysis

  • What breaks: a client behind a UDP-blocking firewall stalls waiting for a QUIC handshake that never completes, instead of falling back promptly.
  • Detection: lb_alt_svc_fallback_total combined with QUIC handshake-timeout metrics.
  • Blast radius: one client's connection attempt, bounded to the handshake timeout window.
  • Containment: Alt-Svc advertising lets a well-behaved client retry over HTTP/2 automatically; the timeout itself is bounded (§4-derived).
  • Recovery path: client-driven fallback; no proxy-side intervention needed.
  • Operator visibility: docs/runbooks/high-latency.md documents the Alt-Svc fallback signature.

23.10 Operational Notes

  • Deployment: the HTTP/3 listener requires an additional UDP port bound alongside the TCP listener for the same service.
  • Metrics: lb_alt_svc_fallback_total; H2/H3-specific latency histograms share the §21.2 metric names, disambiguated by the listener label.
  • Rollback: disabling HTTP/3 is a listener-config change; clients fall back to HTTP/2 via Alt-Svc absence.
  • Compatibility: HTTP/2 and HTTP/3 share the same RouteConfig/ClusterConfig — no protocol-specific routing config exists (§28).

24. Phase 12 — Multi-Node Topology

24.1 Objectives

  • Lift the proxy from a single binary to a fleet: single-node, active-passive (VRRP), and active-active (consistent-hash) topologies.
  • Constraints introduced: the proxy binary itself is topology-unaware; topology is composed externally or via lb-topology glue (P1: one core, reused across all three).

24.2 Detailed Implementation Steps

  • lb-topology::single — the default: one proxy instance, availability is the operator's problem (typically DNS round-robin over two independently-deployed instances).
  • lb-topology::active_passive — two nodes share a virtual IP via an out-of-process keepalived (VRRP) companion; the active node holds the VIP, the passive is hot standby; keepalived uses the proxy's /admin/health (§22.2) as its health trigger — the proxy itself has no VRRP-awareness (§5 UNIX Network Programming ch. 7, socket-option lineage informing the VIP rebind).
  • lb-topology::active_active — N nodes each serve a fraction of the keyspace; membership and liveness are managed via the sibling Gossip-Protocol project (rank 70, §5); a node failure triggers a Maglev rebuild on survivors (§15.2, I13) — approximately 1/N of keys move (§8.7); the connection pool on survivors warms previously-cold backends as the new keyspace fraction routes to them (§5 Kleppmann DDIA ch. 8–9 on the resulting eventual-consistency window).
  • Client-side or upstream-LB-side hashing must route to the same node the proxy fleet expects; a mismatch produces an extra forwarding hop and doubles latency — documented as a deployment contract, not a proxy-side auto-correction.

24.3 Deliverable

  • A topology=active_active config driving a 3-node cluster behind a Maglev-hashed front-door.
  • A failure-injection test: kill one of three nodes; the surviving two absorb traffic with no client-visible 5xx within the gossip convergence window.

24.4 Acceptance Criteria

  • Active-passive VRRP failover completes in < 3 s (§4, fixture vrrp_failover.json).
  • Active-active 1-of-3 node kill: zero client-visible 5xx after the gossip convergence window (< 5 s, §4, §31 M11, fixture node_kill_3.json).
  • Post-failure key redistribution disturbs ≤ 1/N of keys (fixture redistribution_bound.json, consistent with §8.7/§35).

24.5 Conformance Fixtures

  • conformance/corpora/reload/vrrp_failover.json — VIP failover timing.
  • conformance/corpora/reload/node_kill_3.json — 3-node active-active kill-one fixture.
  • conformance/corpora/reload/redistribution_bound.json — 1/N disruption bound assertion.

24.6 Pitfalls

  • Active-passive failover is a TCP-and-ARP problem, not just an IP problem — keepalived must emit a gratuitous ARP on VIP move, and the kernel neighbor cache must update, or clients keep sending to the dead node's MAC.
  • Active-active sharding requires the client (or upstream LB) to hash to the node the proxy expects — a mismatch silently doubles latency via an extra hop rather than failing loudly.
  • The gossip convergence window is non-zero; during it, both the old and new owner of a key may serve it — idempotent operations are safe, bare counter increments are not (documented application-level contract, not a proxy guarantee).

24.7 Performance Concerns

  • A Maglev rebuild on node loss costs the same O(M·N) as any other backend-list change (§15.2, §35) — bounded and off the request path (I13) regardless of topology.
  • Cross-node connection-pool warming after a rebalance adds a transient latency bump for requests landing on a previously-cold backend — bounded by the connection-pool's handshake cost (§13.2), not unbounded.

24.8 Edge Cases

  • All three active-active nodes losing gossip connectivity simultaneously (network partition): each node serves its last-known keyspace view — a documented split-brain window, not a crash; reconciliation happens on gossip recovery.
  • A VRRP failover racing an in-flight admin reload on the newly-active node: the reload protocol's I1/I2 guarantees hold per-node regardless of which node currently holds the VIP.
  • A node rejoining after a long partition with a stale ConfigSnapshot generation: the rejoining node must re-fetch the current config before serving, never serve on a known-stale generation (§28 versioning).

24.9 Failure Analysis

  • What breaks: a client library that caches DNS/VIP resolution longer than the failover time continues sending to the dead node past the 3 s RTO.
  • Detection: client-reported error rate outlives the proxy-side failover metric window.
  • Blast radius: bounded to clients with overly-long DNS/connection caching, not a proxy defect.
  • Containment: documented client-side guidance (short DNS TTLs, connection-level retry) in docs/runbooks/upstream-flap.md.
  • Recovery path: client-side reconnect on the next attempt.
  • Operator visibility: VIP-holder metric plus gossip-membership dashboard (§27).

24.10 Operational Notes

  • Deployment: active-passive requires keepalived as a companion process; active-active requires the Gossip-Protocol sidecar/library integration.
  • Metrics: gossip-membership size, VIP-holder identity, 1/N-disruption-observed gauge.
  • Rollback: reverting topology=active_active to single is a deployment-level change, not a hot-reload — it changes the fleet shape, not just config (§28).
  • Compatibility: the wire/config contract for topology is additive; the Gossip-Protocol dependency version is pinned in Cargo.lock (ADR-25).

27. Operational Readiness

  • Metrics/tracing/logging: the full set is §21's Prometheus registry, OpenTelemetry spans, and structured access log; scraped via /admin/metrics (§22.2).
  • Dashboards: a Grafana JSON (§21.3) renders the four golden signals (latency, traffic, errors, saturation) per listener/route/cluster.
  • Alerting philosophy: alert on symptom (SLO burn rate, §21.2 error budget), page on sustained burn, ticket on transient burn — never alert on a raw metric threshold alone (§5 SRE book ch. 4-6).
  • SLOs: per-route, expressed as lb_error_budget_remaining{route,slo}; default SLO is 99.9% success + p99 < 1,000 µs added latency (§4).
  • Incident response: four named runbooks — docs/runbooks/triage.md (first response), high-latency.md, 5xx-storm.md, upstream-flap.md — each maps a symptom to the relevant §26 failure class and §25 threat.
  • Backup/restore: the only persistent state is the ConfigSnapshot source (YAML/JSON on disk or in the admin API's last-applied config); backup is a file copy; restore is POST /admin/config/reload with the backed-up body.
  • Deployment topology: single node → active-passive VRRP → active-active consistent-hash fleet (§24), chosen independently of code version.
  • Canary/rolling upgrade: a canary node runs the new binary version behind the same VIP/ keyspace fraction; RouteConfig.canary (§16.2) can additionally canary at the traffic level independent of binary version.
  • Rollback: binary rollback is a version swap (no persistent schema to migrate below ConfigSnapshot, §28); config rollback is a /admin/config/reload with the prior body (I2).
  • Migration: ConfigSnapshot.generation is monotonic; a downgrade to an older binary that doesn't understand a newer generation's fields must reject it explicitly, never silently truncate (§28).
  • Privacy/redaction: default access-log/trace redaction hashes client IPs and drops JWT bodies; per-route override exists for compliance-cleared routes (docs/compliance/ — see §25 T13).

28. Compatibility & Versioning

  • Wire compatibility: the L4/L7 proxy speaks standard HTTP/1.1, HTTP/2, HTTP/3, gRPC, and raw TCP/UDP — no proprietary wire extensions; PROXY protocol v2 (§8.5) is the one proxy-specific wire addition, opt-in per cluster.
  • Storage/config schema evolution: ConfigSnapshot.generation is monotonic (§11.5); every config struct (ClusterConfig, RouteConfig, ListenerConfig, …) is additive-only across minor versions — new optional fields default to a documented safe value; removing a field requires a major version bump and a deprecation window (see the Deferred Features Register, §38, for the process).
  • API stability: the admin API's OpenAPI schema (docs/api/admin.openapi.yaml, ADR-15) is SemVer'd independently of the binary version; a breaking admin-API change is itself a major version bump.
  • Migration: downgrading to an older binary that does not understand a newer ConfigSnapshot.generation's fields must reject the config explicitly (fail closed) rather than silently truncating unknown fields.
  • Deprecation policy: a deprecated config field is accepted with a warning for one minor version cycle, then rejected; the same policy applies to admin-API endpoints and metric names.
  • SemVer policy: MAJOR.MINOR.PATCH (ADR-30); MAJOR = wire/config/API breaking change, MINOR = additive feature, PATCH = bug fix with no interface change.
  • Rolling-upgrade guarantees: in an active-active fleet (§24), nodes running N and N+1 (same MAJOR) must interoperate for the duration of a rolling upgrade — enforced by the additive-only schema rule above.

29. Testing & Verification Strategy

  • Unit tests: per-crate, covering pure logic (matchers, rewrite templates, bucket arithmetic) with no I/O.
  • Integration tests: cross-crate, e.g. BackendPool + a Discoverer + a Selector together, using MockClock (P13) for determinism.
  • Property-based tests: proptest (ADR-27) over router matcher combinations and rate-limiter arithmetic, asserting invariants (§7) hold for arbitrary generated inputs.
  • Differential tests: the smooth-WRR implementation is differentially tested against a reference Python model of the NGINX algorithm (§5 ref-impl) to confirm the same pick sequence for the same weight sequence.
  • Fuzzing: cargo-fuzz/libFuzzer targets request_parser.rs, header_matcher.rs, maglev_table.rs (§10); a 30-day continuous fuzz canary is M12 (§31).
  • Chaos/fault injection: the deterministic simulator (§7 debugging methodology) replays scripted discovery/health/reload event sequences and asserts every I#; a separate fault-injection harness kills real backend processes mid-test for the flap-soak fixtures (§14, §17).
  • Deterministic replay: every timer/TTL goes through Clock (P13), so a failing chaos run is exactly reproducible from its seed and event script.
  • Soak testing: the 100-reload soak (§22.4), the 10-minute discovery flap-soak (§14.4), and the 60-minute sustained-throughput runs (§31 M5/M6) are all soak-class tests gating release.
  • Conformance: the conformance/ suite (§10, one bucket per protocol/subsystem) is the fixture-level ground truth referenced by every phase's N.5.
  • Performance-regression gating: every M# target (§31) is asserted in CI on every release-candidate build; a regression below threshold blocks release (§30).
  • Tie-back to invariants: every I# (§7) has at least one conformance fixture or simulator assertion; every phase's N.5 fixtures are the concrete artifacts this strategy produces.

30. Build & Release Engineering

  • Reproducible builds: sccache + Nix-pinned toolchain (ADR-18); the same commit produces a byte-identical binary across maintainer machines and CI.
  • Artifact signing: release binaries and container images are signed (cosign-compatible) at release.yml (ADR-22, ADR-30).
  • SBOM: a software bill of materials is generated per release via cargo-cyclonedx, published alongside the signed artifact.
  • Release channels: stable (SemVer-tagged), nightly (main branch, unsigned, for internal testing only).
  • CI/CD topology: GitHub Actions (ADR-22): ci.yml (build+test+lint), conformance.yml (the §29 suite), fuzz.yml (scheduled), security.yml (cargo-audit+cargo-deny, ADR-29), release.yml (signed tag → artifact + SBOM).
  • Version stamping: the binary embeds its git SHA, build timestamp, and SemVer tag, exposed via GET /admin/health and the access-log startup banner.
  • Provenance/attestation: release.yml produces SLSA-style build provenance attached to the signed artifact.
  • Dependency auditing: cargo-audit (known-vulnerability DB) and cargo-deny (license + duplicate-version policy) gate every merge to main (ADR-29).

32. Scalability Analysis

  • Stays constant: Selector::pick latency at a fixed backend count (O(1) for RR/Maglev/ Ketama-lookup, O(log N) for Jump); per-request allocation count (P3); admin-API mutation latency (independent of data-plane load, P4).
  • Grows, with Big-O: memory with backend count (O(N), 4 KiB/backend, §4); Maglev table-rebuild cost with O(M·N) (§15.6, §35); route-resolution cost with route count (O(path_segments) amortized via the trie, O(routes) worst case for pure-regex tables, §16.7); metric cardinality with backend-label opt-in (O(clusters × backends) when enabled, §21.2).
  • Named bottlenecks, in order: (1) connection-pool checkout contention at high fan-in (§13.7); (2) Maglev table rebuild frequency under a flapping discovery source (§15.6, I13); (3) per-consumer rate-limit map growth under high-cardinality consumer identifiers (§19.9, FM8); (4) single-NIC bandwidth ceiling at the L4 throughput target (§35 derivation #6).
  • Horizontal scaling: the active-active topology (§24) is the horizontal lever — each node serves an independent keyspace fraction; adding a node redistributes 1/N of keys (§8.7).
  • Vertical scaling: more cores via SO_REUSEPORT-sharded listeners (§5 UNIX Network Programming ch. 7); the shared-nothing-per-core design (P1, P3) means near-linear scaling up to the point NUMA crossing appears (§4 single-socket assumption).
  • Sharding/partitioning: Maglev-consistent-hash sharding across active-active nodes; no cross-shard coordination is needed for a read (a request always lands on its owning node), only for membership changes (via Gossip-Protocol, rank 70).
  • Coordination overhead: bounded to the gossip convergence window (< 5 s, §4) on membership change; steady-state request handling has zero cross-node coordination.
  • Practical ceiling and the levers beyond it: the single-node ceiling is ~1M req/s L4 / ~100K req/s L7 per core × available cores, bounded ultimately by NIC bandwidth (§35 derivation #6, ~8 Gbps at the L4 target); beyond a single NIC's ceiling, the lever is horizontal (add active-active nodes, §24) or a kernel-bypass datapath (eBPF/XDP, PhaseDeferred("§38"), §37 Alt1) — a fundamentally different architecture, not a tuning knob.

33. Mental Models & First Principles

  • MM1 — A pick is a load-balancing decision under uncertainty, not a routing table lookup. Compressed insight: every Selector is answering "which backend is least likely to make this request slow," and P2C's win over round-robin is precisely that round-robin ignores the uncertainty entirely (§5 Mitzenmacher). Predicts: round-robin degrades badly the moment backends are heterogeneous in speed, even briefly. Bug class without it: "but round-robin is fair" reasoning that ignores transient backend slowness, leading to a P2C-vs-RR regression that only shows up under real skew, never in a synthetic uniform-latency test. Resolving: §15.

  • MM2 — Health is a lagging, reconciled signal, not ground truth. Compressed insight: BackendStatus.healthy is always a stale AND of two independently-lagging observers (active probe interval, passive ejection window) — it is an estimate, not a fact (P5). Predicts: a backend can receive traffic for up to one probe interval after it actually died. Bug class without it: "why did we send traffic to a dead backend" incidents where the engineer expects instant detection instead of bounded-latency detection. Resolving: §7 I4, §17.

  • MM3 — Config is data, not state; a reload is a new value, not a mutation. Compressed insight: ConfigSnapshot behind ArcSwap is RCU — readers never block, writers never wait for readers, and the old value survives exactly as long as its last reader (ADR-07). Predicts: any hot-reload design that instead mutates a shared map in place will eventually drop in-flight requests. Bug class without it: the canonical "reload dropped 12,000 gRPC streams" incident (§1, §2). Resolving: §7 I1/I2, §22.

  • MM4 — Consistent hashing trades perfect balance for minimal disruption. Compressed insight: Maglev/Ketama/Jump all accept a small balance imperfection in exchange for the property that removing one backend moves close to 1/N of keys, not close to all of them (§5 Karger, Eisenbud). Predicts: a naive hash(key) % N scheme will look fine in a demo and then reshuffle nearly every key the moment N changes. Bug class without it: cache stampedes or session loss on every backend-count change. Resolving: §8.7, §15.

  • MM5 — Backpressure is a property of the whole pipe, not a buffer setting. Compressed insight: streaming bodies end-to-end (P11) means a slow reader anywhere throttles the writer at every stage automatically, via the kernel's own TCP flow control — no explicit buffer-size tuning is the actual goal. Predicts: any design that buffers "just this one stage" reintroduces unbounded memory growth exactly at that stage. Bug class without it: a 1 GiB upload behind a slow upstream OOMs the proxy despite every individual buffer being "reasonably sized." Resolving: §6 P11, §13.

  • MM6 — Tail latency is a fan-out and variance problem, not an average problem. Compressed insight: p99 is dominated by rare, correlated slow events (a GC pause, a cold cache line, a contended lock) that averages hide entirely (§5 Dean & Barroso). Predicts: optimizing mean latency can leave p99 untouched or even worsen it (e.g. batching helps mean throughput but can hurt tail latency). Bug class without it: shipping a change that improves the dashboard's average-latency graph while an SLO burn alert fires on p99. Resolving: §31.

  • MM7 — A circuit breaker's half-open state is rate-limiting the truth, not the traffic. Compressed insight: half-open exists to answer "is this backend actually better now" with a bounded, safe sample size — not to gradually ramp traffic back up (I12). Predicts: skipping the probe quota and going straight to Closed on any single success reintroduces the thundering-herd failure the breaker was built to prevent. Bug class without it: a recovery-triggered outage that looks identical to the original outage. Resolving: §20.

  • MM8 — An admin API is a distributed system's only legible causality. Compressed insight: because every mutation is audited before being applied (I10), the admin API is the one place where "what changed, when, and who did it" is provably reconstructible — everything else (discovery pushes, health-check transitions) is inferred from telemetry, not recorded as intent. Predicts: an unaudited mutation path (SIGHUP, a config file poked outside the discovery watcher) will eventually be the thing nobody can explain during an incident. Resolving: §6 P10, §22.

HAProxy made the different call of a mature, battle-tested single-threaded-per-process event loop with an optional multi-process fan-out — it wins in shops that want the single most predictable, decades-proven L4/L7 balancer with the richest ACL/stick-table configuration language, at the cost of a less ergonomic dynamic-reconfiguration story than xDS or ArcSwap. NGINX made the different call of prioritizing the web-server-plus-reverse-proxy combo with a battle-hardened multi-process worker model — it wins whenever the same binary must also serve static files and terminate TLS for a traditional web stack, at the cost of a coarser hot-reload granularity (a worker reload, not a per-object atomic swap). Envoy made the different call of a fully dynamic, xDS-driven control-plane/data-plane split designed for large multi-team, multi-cluster fleets (the Istio/service-mesh use case) — it wins at organizational scale where centralized policy distribution matters more than a lean single binary, at the cost of running (and operating) a separate control-plane server most deployments of this blueprint's scope don't need. Cloudflare Pingora made the different call of being a library, not a standalone proxy — teams embed it into their own binary and own the control plane themselves — it wins when an organization needs Rust-level performance and safety but wants full control over its own config/discovery layer rather than adopting a prescriptive one, at the cost of every embedding team re-solving the discovery/observability integration this blueprint ships out of the box.

35. Back-of-Envelope Capacity Model

Every number below is derived from the §4 System Constraints table, formula shown.

  1. Total connection RAM at max concurrency. 500,000 conns × 4 KiB/idle-conn (§4) = 2,000,000 KiB ≈ 1.9 GiB — just under the 2 GiB RSS ceiling (§4), leaving ~100 MiB headroom for backend descriptors and route tables.
  2. FD budget check. 500,000 conns × 2 FDs/conn (client + upstream) = 1,000,000 FDs vs the 1,048,576 RLIMIT_NOFILE budget (§4) — leaves 48,576 FDs of headroom for listener sockets, health-check connections, and admin-API connections.
  3. Backend descriptor RAM at design ceiling. 10,000 backends × 4 KiB/backend (§4) = 40,000 KiB ≈ 39 MiB — negligible against the 1.9 GiB connection budget (#1).
  4. Route table RAM at design ceiling. 10,000 routes × 1 KiB/route (§4) = 10,000 KiB ≈ 9.8 MiB.
  5. L7 HTTP/1.1 bandwidth at target throughput. 100,000 req/s × 1 KiB response (§4) = 100,000 KiB/s ≈ 800 Mbps — comfortably under a 10 Gbps NIC (12.5× headroom).
  6. L4 TCP bandwidth at target throughput. 1,000,000 req/s × 1 KiB (§4) = 1,000,000 KiB/s ≈ 8 Gbps — saturates a 10 Gbps NIC almost entirely, which is exactly why the L4 path needs SO_REUSEPORT-sharded multi-core accept (§5 UNP ch. 7) rather than a single-core design.
  7. Maglev table-build cost at N=100 backends. M·N operations = 65,537 × 100 = 6,553,700; at ~1 ns/operation (a hash + a comparison) ≈ 6.5 ms (§15.6) — confirms the requirement (I13) that this never run on the request path.
  8. UDP receive-buffer sizing for the L4 UDP target. 1,500,000 pkt/s × 512 B avg (§4) ≈ 768 MB/s inbound; a 4 MiB SO_RCVBUF (§23.2) holds 4 MiB / 512 B ≈ 8,192 packets, i.e. 8,192 / 1,500,000 pkt/s ≈ 5.5 ms of absorption headroom against scheduling jitter — comfortably above a typical <1 ms scheduler tick, validating the 4 MiB choice.
  9. TLS handshake CPU budget under a reconnect storm. At 10,000 new conns/s, a full handshake (25 ms p99, §4) costs 10,000 × 25 ms = 250 CPU-seconds/s if fully serial — far beyond one core; with session resumption (5 ms p99, §4) the cost drops to 10,000 × 5 ms = 50 CPU-seconds/s, still requiring ~50 cores of parallel handshake capacity — this is why resumption (I11) is mandatory at scale, not merely an optimization.
  10. Availability improvement from active-passive failover. Single-node 99.9% (43.2 min/month, §4) vs a VRRP pair with < 3 s RTO (§4): a single failover event now costs 3 s / 2,592,000 s-per-month ≈ 0.00012% of a month — the practical availability ceiling moves to 99.99% (4.32 min/month, §4), bounded by node MTBF, not by RTO.
  11. Access-log storage rate at full sampling. 100,000 req/s × ~300 B/JSON-line × 1.2× amplification (§4) = 36,000,000 B/s = 36 MB/s ≈ 3.1 TB/day per node at 100% sampling — the reason per-route sampling down to 1% (§21.2) is a first-class config knob, not an afterthought.
  12. Cache-locality ceiling for the hot pick path. 10,000 backends × 4 KiB/backend (§4) = 39 MiB (#3) exceeds a typical 24 MiB shared L3 (§4) once other working-set data is counted — this validates keeping the filtered healthy-subset array (§15.7, typically hundreds of entries at realistic per-cluster backend counts) as the structure pick iterates, rather than scanning the full 10,000-entry backend array on every call.

37. Alternative Architectures (Roads Not Taken)

Alt1 — Kernel-bypass XDP/eBPF L4 datapath (embodied by Facebook Katran).

 NIC → XDP program (in-kernel) ──hit──► forward packet (consistent-hash, no context switch)
                │
              miss / control-plane event
                ▼
      user-space health-checker + control plane (updates XDP maps)

Wins in the regime where single-box packet rate must exceed what a user-space proxy can sustain — roughly beyond the ~8 Gbps / 1.5M pkt/s ceiling this blueprint's L4 path targets (§35 #6, #8) — i.e. CDN-edge or DDoS-scrubbing scale. Rejected here because it forfeits nearly all L7 capability (routing, TLS termination, rate limiting) in exchange for raw L4 throughput, and because the operator skill bar (kernel version, BTF, eBPF verifier constraints) is a much higher floor than this blueprint's target audience (§1). ADR-16 defers it explicitly, not permanently.

Alt2 — Client-side / library-embedded load balancing (embodied by Netflix Ribbon-style and modern gRPC client-side LB).

 Client library ──(has its own copy of the backend list + Selector)──► Backend
                     (no proxy hop at all)

Wins when the organization controls both call sites and can afford to push discovery, health-checking, and algorithm logic into every client — it eliminates the proxy hop's added latency (§4's <1,000 µs p99 becomes zero) entirely. Rejected here because it requires every client to embed and keep current a copy of the balancing logic (this blueprint's whole value proposition, P1, is one shared core), and because it cannot uniformly enforce cross-cutting policy (rate limiting, TLS termination, audited admin control) at a single choke point (§6 P10) — those become N independent implementations to keep consistent instead of one.

Alt3 — Centralized xDS control-plane / data-plane split (embodied by Envoy + a separate management server, the Istio model).

 xDS management server ──(CDS/EDS/RDS/LDS push)──► Envoy data-plane instance (× N)
        ▲                                                    │
        └────────────── policy authored once, fanned out ────┘

Wins at large multi-team, multi-cluster organizational scale where centralized policy authorship and audit (who can route what, where) matters more than operational simplicity — exactly Envoy's actual niche (§34). Rejected here because this blueprint's target deployment (§1: a platform/SRE team running its own edge or internal tier) does not need a separately-operated control-plane server; the in-process ArcSwap-fed control plane (§3, ADR-07) is deliberately simpler at the cost of not scaling policy distribution to hundreds of proxy instances the way full xDS does.

Alt4 — Hardware/appliance load balancer (embodied by F5 BIG-IP and similar ASIC-accelerated appliances).

 [ dedicated ASIC/FPGA appliance ] ── wire-speed L4/L7 switching, vendor firmware

Wins where throughput must be extremely high and predictable, the traffic pattern is stable enough to justify capex, and the organization can accept vendor lock-in and slow firmware-driven iteration in exchange for not operating a software fleet at all. Rejected here because this blueprint's entire purpose (§2) is to teach and own the algorithm/discovery/ observability stack in software, with weekly-or-faster iteration — the opposite of an appliance's vendor-controlled release cadence.

39. Glossary

  • ALPN (Application-Layer Protocol Negotiation) — TLS extension negotiating h2/ http/1.1/h3 during the handshake; drives listener protocol dispatch (§18.2).
  • ArcSwap — a lock-free atomically-swappable Arc pointer; the mechanism behind hot-reload (ADR-07, I1/I2).
  • Backend — one upstream server instance, identified by BackendId (§11.2).
  • BackendPool — the per-cluster, ArcSwap-backed collection of Backends (§11.3).
  • BackendStatus — the reconciled health/draining/ejection state of a Backend (§11.2, I4).
  • Bulkhead — a per-backend/per-cluster concurrency cap that isolates overload (§20.2).
  • Canary — routing a small traffic percentage to an alternate cluster (§16.2).
  • Circuit Breaker — a state machine (Closed/Open/HalfOpen) that short-circuits traffic to a failing cluster or backend (§20, §8.3).
  • ConfigSnapshot — the immutable, versioned config object behind ArcSwap (§11.5, I1).
  • Connection Pool — the per-backend keepalive connection cache (§13.2).
  • Consistent Hashing — a hash scheme minimizing key movement on membership change; Maglev/ Ketama/Jump are the three variants shipped (§15.2, §5 Karger).
  • Discoverer — a trait implementation that watches a backend source and pushes updated lists (§11.7, §14).
  • Draining — a backend/listener state excluded from new picks but still serving existing work (P12, I9).
  • EWMA (Exponentially-Weighted Moving Average) — the latency-smoothing statistic behind EWMA-P2C and LatencyAware (§15.2, ADR-12).
  • FD (File Descriptor) — the kernel handle for a socket; budgeted explicitly (§4).
  • Half-Open — the circuit-breaker probing state between Open and Closed (§8.3, I12).
  • Health Check, Active — a proxy-initiated probe (TCP/HTTP/gRPC/exec) (§17.2).
  • Health Check, Passive — outlier ejection derived from real request outcomes (§17.2, P5).
  • Hop-by-hop Header — a header meaningful only for one connection segment, stripped before forwarding (I7, RFC 7230 section 6.1).
  • HPACK — HTTP/2 header compression (RFC 7541, §23.2).
  • Jump Hash — the Lamping & Veach O(1)-memory consistent-hash algorithm (§15.2, §5).
  • Ketama — the classic virtual-node ring consistent-hash algorithm (§15.2, §5 Karger).
  • Maglev — Google's O(1)-lookup, 1/N-disruption consistent-hash table (§15.2, §5 Eisenbud).
  • mTLS (mutual TLS) — both client and server present certificates; used for the admin API and optionally upstream re-encryption (P8, P10).
  • Outlier Ejection — passive removal of a misbehaving backend from the pick set (§17.2, I4).
  • P2C (Power of Two Choices) — sampling two backends and picking the less-loaded one (§15.2, §5 Mitzenmacher).
  • PROXY protocol v2 — a wire header injecting original client address info on a re-proxied connection (§8.5).
  • QPACK — HTTP/3's header-compression scheme, QUIC's analog of HPACK (RFC 9204, §23.2).
  • QUIC — the UDP-based transport underlying HTTP/3 (RFC 9000, §23.2).
  • Rate Limiter, Leaky Bucket — a smooth-output-rate limiting algorithm (§19.2).
  • Rate Limiter, Token Bucket — a burst-tolerant limiting algorithm (§19.2).
  • RCU (Read-Copy-Update) — the general concurrency pattern ArcSwap implements: readers never block, a writer publishes a new value atomically (§33 MM3).
  • Reload Generation — the monotonic counter identifying a ConfigSnapshot version (§11.5, §28).
  • Route — a (matcher, action) pair resolving a request to a cluster or synthetic response (§11.5, §16).
  • Selector — the trait implementing a load-balancing algorithm (§11.4, §15).
  • Shadow Traffic — mirroring a request to a secondary cluster without affecting the primary response (§16.2).
  • SLO (Service-Level Objective) — the target success/latency rate a route is held to (§21.2, §27).
  • SNI (Server Name Indication) — the TLS ClientHello field selecting which certificate to serve (§18.2).
  • Split-brain — a window where two nodes both believe they own the same key, possible during a gossip partition (§24.8).
  • Sticky Session — request affinity to a specific backend, achieved here via consistent-hash keying rather than server-side session state (§15.2).
  • Traffic Split — weighted request distribution across N clusters via stable hashing (§16.2).
  • TTL (Time to Live) — the validity duration of a DNS record or similar cached value (§14.2).
  • Two-Phase Reload — build-and-validate, then commit; rolls back on validation failure (§22.2, I2).
  • VIP (Virtual IP) — a floating IP address shared by an active-passive pair (§24.2).
  • VRRP (Virtual Router Redundancy Protocol) — the protocol keepalived uses to manage VIP failover (§24.2).
  • WRR (Weighted Round Robin), Smooth — the NGINX-style weighted round-robin avoiding burst-then-pause (§15.2).
  • xDS — Envoy's family of dynamic-configuration discovery protocols (CDS/EDS/RDS/LDS), contrasted with this blueprint's ArcSwap-based model (§34).
