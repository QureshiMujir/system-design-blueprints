Decisions (§9) · 31 ADRs

ADR-01

Core language

Chosen

Rust

Rejected

Go, C++

When the rejected choice is right

Go wins for a control-plane-only tool at <10K req/s where iteration speed beats tail-latency headroom.

Why: Zero-cost abstractions + no GC pause on the shared data path (§1).

ADR-02

Async runtime

Chosen

Tokio

Rejected

async-std, smol

When the rejected choice is right

smol wins for a tiny embedded proxy with a strict binary-size budget and no H2/H3/gRPC needs.

Why: Only Tokio has production-grade Hyper/Quinn/Tonic/Rustls integration.

ADR-03

HTTP/1.1 + HTTP/2 library

Chosen

Hyper (as a library)

Rejected

hand-rolled parser

When the rejected choice is right

A hand-rolled parser wins only for a research prototype studying HTTP parsing itself.

Why: Canonical Rust HTTP implementation with production keepalive/backpressure.

ADR-04

HTTP/3 stack

Chosen

Quinn + h3 crate

Rejected

quiche (Cloudflare)

When the rejected choice is right

quiche wins when the org already standardizes on BoringSSL/C ABI across languages.

Why: Best-integrated with the Tokio/Rustls stack already chosen.

ADR-05

gRPC scaffolding (examples only)

Chosen

Tonic

Rejected

grpc-rs

When the rejected choice is right

grpc-rs wins when parity with an existing C++ libgrpc deployment is required.

ADR-06

TLS library

Chosen

Rustls

Rejected

OpenSSL

When the rejected choice is right

OpenSSL wins when FIPS-140-validated modules or ENGINE-based hardware offload are mandatory.

ADR-07

Hot-reload primitive

Chosen

arc_swap::ArcSwap<ConfigSnapshot>

Rejected

RwLock<Config>, actor-message reload

When the rejected choice is right

RwLock wins for a low-QPS admin-only config (<100 req/s) where reload contention is immaterial.

Why: Lock-free, RCU-style, no data-path blocking (I1, I2).

ADR-08

Licensing

Chosen

Apache-2.0 (data plane), ELv2 reserved (future hosted control plane)

Rejected

When the rejected choice is right

Pure Apache-2.0 wins with no hosted-SaaS ambition and a pure-community-adoption goal.

Why: Preserves an open-core path without restricting the proxy itself.

ADR-11

Chosen

Maglev

Rejected

When the rejected choice is right

Ketama wins when table-rebuild cost must be zero and looser disruption is acceptable at 100K+ rapidly-churning backends.

ADR-12

ADR-13

When the rejected choice is right

Passive-only wins in a metered-egress edge deployment where active probe traffic is cost-prohibitive.

Why: Active alone is too slow; passive alone is too noisy (P5).

37. Alternative Architectures (Roads Not Taken)

Alt1 — Kernel-bypass XDP/eBPF L4 datapath (embodied by Facebook Katran).

 NIC → XDP program (in-kernel) ──hit──► forward packet (consistent-hash, no context switch)
                │
              miss / control-plane event
                ▼
      user-space health-checker + control plane (updates XDP maps)

Wins in the regime where single-box packet rate must exceed what a user-space proxy can sustain — roughly beyond the ~8 Gbps / 1.5M pkt/s ceiling this blueprint's L4 path targets (§35 #6, #8) — i.e. CDN-edge or DDoS-scrubbing scale. Rejected here because it forfeits nearly all L7 capability (routing, TLS termination, rate limiting) in exchange for raw L4 throughput, and because the operator skill bar (kernel version, BTF, eBPF verifier constraints) is a much higher floor than this blueprint's target audience (§1). ADR-16 defers it explicitly, not permanently.

Alt2 — Client-side / library-embedded load balancing (embodied by Netflix Ribbon-style and modern gRPC client-side LB).

 Client library ──(has its own copy of the backend list + Selector)──► Backend
                     (no proxy hop at all)

Wins when the organization controls both call sites and can afford to push discovery, health-checking, and algorithm logic into every client — it eliminates the proxy hop's added latency (§4's <1,000 µs p99 becomes zero) entirely. Rejected here because it requires every client to embed and keep current a copy of the balancing logic (this blueprint's whole value proposition, P1, is one shared core), and because it cannot uniformly enforce cross-cutting policy (rate limiting, TLS termination, audited admin control) at a single choke point (§6 P10) — those become N independent implementations to keep consistent instead of one.

Alt3 — Centralized xDS control-plane / data-plane split (embodied by Envoy + a separate management server, the Istio model).

 xDS management server ──(CDS/EDS/RDS/LDS push)──► Envoy data-plane instance (× N)
        ▲                                                    │
        └────────────── policy authored once, fanned out ────┘

Wins at large multi-team, multi-cluster organizational scale where centralized policy authorship and audit (who can route what, where) matters more than operational simplicity — exactly Envoy's actual niche (§34). Rejected here because this blueprint's target deployment (§1: a platform/SRE team running its own edge or internal tier) does not need a separately-operated control-plane server; the in-process ArcSwap-fed control plane (§3, ADR-07) is deliberately simpler at the cost of not scaling policy distribution to hundreds of proxy instances the way full xDS does.

Alt4 — Hardware/appliance load balancer (embodied by F5 BIG-IP and similar ASIC-accelerated appliances).

 [ dedicated ASIC/FPGA appliance ] ── wire-speed L4/L7 switching, vendor firmware

Wins where throughput must be extremely high and predictable, the traffic pattern is stable enough to justify capex, and the organization can accept vendor lock-in and slow firmware-driven iteration in exchange for not operating a software fleet at all. Rejected here because this blueprint's entire purpose (§2) is to teach and own the algorithm/discovery/ observability stack in software, with weekly-or-faster iteration — the opposite of an appliance's vendor-controlled release cadence.
