⬜ Phase 0 — Skeleton, Governance & TCP Kernel §12

Objectives
  • Stand up the repository skeleton (§10) as a single commit; every crate manifest compiles with an empty body.
  • Deliver a raw TCP L4 proxy: accept → dial upstream → bidirectional byte copy.
  • Raise the FD budget at boot (§4) and land the governance documents.
  • Constraints introduced: one hard-coded ConfigSnapshot (I1); no dynamic discovery yet (Phase 2, §14); no TLS yet (Phase 6, §18).
Deliverable
  • make bootstrap && make build && make test all exit 0 on a clean checkout.
  • A running lb binary proxying nc 127.0.0.1:8080 to a nc -l 9000 upstream bidirectionally.
  • ADR files for ADR-01, ADR-02, ADR-08, ADR-09, ADR-10, ADR-18, ADR-21, ADR-22 landed under docs/adr/.
Acceptance
  • make test passes with ≥1 test asserting bidirectional byte-count equality on a loopback proxy (fixture tcp_smoke.json).
  • RLIMIT_NOFILE raised to exactly 1,048,576 on Linux, asserted via getrlimit(2) in test.
  • Cold-start time to first accept() < 250 ms (§4), measured by scripts/bootstrap.sh.
  • Zero clippy::all warnings at -D warnings.
Fixtures
  • conformance/corpora/reload/tcp_smoke.json — single-connection byte-echo, both directions.
  • conformance/corpora/reload/fd_limit.json — asserts post-boot RLIMIT_NOFILE value.
  • conformance/corpora/reload/cold_start.json — asserts time-to-first-accept < 250 ms.
Pitfalls
  • copy_bidirectional takes &mut to both halves; a naive select! around it fails to compile with a use-after-move — read the rustdoc contract rather than hand-rolling the loop.
  • Default Linux nofile is 1,024; the raise must happen in-process (§4, TLPI ch. 36).
  • TcpListener::accept's peer address is lost to the access log if not captured pre-spawn (I6).
  • cargo-chef layer caching silently goes stale if Cargo.lock isn't copied before the recipe step — verify Docker build cache hit rate in CI.

⬜ Phase 1 — HTTP/1.1 Reverse Proxy Core §13

Objectives
  • Stand up the L7 path the remaining twelve phases extend: serve HTTP/1.1 against a static, single-cluster backend, with client- and upstream-side keepalive.
  • Emit one structured access-log line per request (full schema lands Phase 9; a minimal line ships here).
  • Constraints introduced: static (hard-coded) RouteConfig; no routing intelligence yet (Phase 4, §16); RR-only selection (Phase 3, §15 ships the rest).
Deliverable
  • An HTTP/1.1 reverse proxy that round-robins (RoundRobin, §15) across two static backends from YAML.
  • A benchmarks/wrk2_bench.sh script driving load against the proxy on one core.
Acceptance
  • Sustains ≥ 100,000 req/s single-core with a 1 KiB response (§4, §31 M1).
  • p50 added latency < 100 µs, p99 < 1,000 µs at that load (§4).
  • Access-log line present for 100% of completed requests (fixture access_log_complete.json).
  • Hop-by-hop headers absent from every forwarded request (fixture hop_by_hop_stripped.json).
Fixtures
  • conformance/corpora/routing/smuggling_cl_te.json — CL.TE ambiguity rejected with HTTP 400.
  • conformance/corpora/routing/smuggling_te_cl.json — TE.CL ambiguity rejected with HTTP 400.
  • conformance/corpora/reload/access_log_complete.json — 10K requests, 10K log lines.
  • conformance/corpora/routing/hop_by_hop_stripped.json — asserts absence of all 7 hop-by-hop headers on the upstream-bound request.
Pitfalls
  • Hyper's Body may be !Send in some configurations; the tokio::spawn boundary requires Send — use the workspace BoxBody alias.
  • Host is HTTP/1.1-only; HTTP/2 uses :authority (§16.3) — the router must consult HttpRequestHead::authority(), never branch on protocol in routing code (P7).
  • Hop-by-hop stripping must special-case Upgrade for WebSocket — stripping it unconditionally breaks WebSocket proxying.
  • A PooledConnection that errors mid-request must be destroyed, never returned to the pool.

⬜ Phase 2 — Backend Pool & Discovery §14

Objectives
  • Replace Phase 1's hard-coded backend list with a BackendPool fed by a Discoverer (§11.7).
  • Ship all five discoverers: static, DNS, file-watch, Consul, etcd, Kubernetes EndpointSlice.
  • Constraints introduced: discovery runs on the control-plane task set only (P4); the data path only ever reads BackendPool::snapshot().
Deliverable
  • All five discoverers implement Discoverer; BackendPool is fed exclusively through it.
  • A 10-minute Consul flap-soak: a backend flaps in/out every 5 s with zero dropped connections.
Acceptance
  • Flap-soak (flap_soak.json, 10 min, 5 s period) emits zero 5xx and zero dropped connections (§31 M2).
  • A killed discovery source (Consul agent stopped) leaves the pool unchanged for ≥ 60 s while lb_discovery_stale_seconds rises monotonically (fixture discovery_source_kill.json).
  • DNS TTL of 0 triggers re-resolution on every probe (fixture dns_ttl_zero.json).
Fixtures
  • conformance/corpora/reload/flap_soak.json — 10-minute Consul flap, zero drops.
  • conformance/corpora/reload/discovery_source_kill.json — source outage, last-good retained.
  • conformance/corpora/reload/dns_ttl_zero.json — TTL-0 re-resolution on every probe.
  • conformance/corpora/reload/k8s_endpointslice_aggregate.json — multi-slice aggregation for one service.
Pitfalls
  • DNS TTLs lie: some upstreams set 0 and expect honoring, others set 86,400 and expect an earlier refresh — min_ttl/max_ttl overrides exist for exactly this (§5 TCP/IP Illustrated informs the retransmission-adjacent reasoning, not directly DNS, but the "don't trust the wire" posture generalizes).
  • EndpointSlice supersedes Endpoints — implementing against the deprecated type is a Phase-2 dead end.
  • Consul's long-poll returns 200 even on a no-op timeout; compare X-Consul-Index, not the status code.
  • A discoverer that fails to connect must never empty the pool (I8) — last-good wins.

⬜ Phase 3 — Algorithm Library §15

Objectives
  • Implement all ten Selectors: RR, WRR, LC, WLC, P2C, EWMA-P2C, Maglev, Ketama, Jump, LatencyAware.
  • Every stochastic algorithm ships a deterministic conformance fixture (P14).
  • Constraints introduced: pick must stay allocation-free and synchronous (I3).
Deliverable
  • All ten algorithms implement Selector (§11.4); a common conformance harness runs every algorithm against a seeded backend list and asserts the expected pick distribution.
Acceptance
  • Each stochastic algorithm's pick distribution over 10,000 samples passes a chi-square goodness-of-fit test at p > 0.01 against its expected distribution (fixture per algorithm, §15.5).
  • pick p50 < 10 µs, p99 < 50 µs at 100 backends; p99 < 200 µs at 10,000 backends (§4, §31 M6/M7).
  • Maglev table construction for M=65,537, N=100 completes in < 10 ms off the request path (§35 derivation; I13).
Fixtures
  • conformance/corpora/algorithms/round_robin.json, weighted_rr.json, least_conn.json, weighted_least_conn.json, p2c.json, ewma_p2c.json, maglev.json, ketama.json, jump.json, latency_aware.json — one per algorithm: seed, backend list, expected distribution, chi-square tolerance.
  • conformance/corpora/algorithms/maglev_disruption.json — asserts 1/N disruption bound on backend removal (§8.7).
Pitfalls
  • Round-robin's atomic counter is contended on multi-core; a per-thread counter is the Phase-1 optimization if profiling shows contention (§31).
  • Maglev's O(M·N) construction re-runs on every backend-list change — for M=65,537, N=100 this is ~6.5 ms (§35); running it on the data path violates I13.
  • P2C's "sample two" must be without replacement — sampling with replacement biases toward picking the same backend twice on small clusters.
  • Jump hash's O(1)-memory property is bought at the cost of no true "remove" operation — modeling removal as ejection-to-fallback is a deliberate, documented compromise, not a bug.

⬜ Phase 4 — L7 Routing & Traffic Management §16

Objectives
  • Resolve a request to a RouteAction (§11.5): proxy, redirect, direct, or a canary/split variant.
  • Ship rewrite, redirect, canary, traffic-split, and shadow-mirroring.
  • Constraints introduced: routing must remain a pure function of (request, snapshot) (P7); no per-request mutable routing state.
Deliverable
  • Router::route resolves a request to a RouteAction in microseconds on a 1,000-route table.
  • Conformance fixtures cover every matcher type, every rewrite primitive, and all four routing actions.
Acceptance
  • Route resolution p99 < 50 µs on a 1,000-route table (fixture route_1000_p99.json).
  • Canary/split assignment is stable for a fixed X-Request-Id across 10,000 repeated lookups within one snapshot generation (fixture split_stability.json).
  • Shadow requests never add > 1 ms to the primary path's p99 regardless of shadow-cluster latency (fixture shadow_isolation.json).
Fixtures
  • conformance/corpora/routing/matchers_all.json — host/path/method/header/query, exact matches for every routing action.
  • conformance/corpora/routing/route_1000_p99.json — 1,000-route table, p99 latency assertion.
  • conformance/corpora/routing/split_stability.json — stable-hash assignment fixture.
  • conformance/corpora/routing/shadow_isolation.json — shadow-latency-isolation fixture.
Pitfalls
  • Regex matchers are a footgun for catastrophic backtracking; the config validator refuses any pattern flagged by a backtracking-risk heuristic, and the runtime never uses regex_lite.
  • Header values are byte strings, not UTF-8 strings; some clients send invalid UTF-8 — match on HeaderValue::as_bytes(), never a lossy string conversion.
  • The shadow path must never influence response timing — spawn and return immediately; only a completion metric fires.
  • JWT validation must precede rate-limiting so an unauthenticated burst is priced correctly (§19.6 cross-reference) — validating after limiting lets invalid-token floods bypass the per-consumer budget.

⬜ Phase 5 — Health Checking §17

Objectives
  • Keep the backend list honest via four active check kinds (TCP/HTTP/gRPC/exec) plus passive outlier ejection.
  • Reconcile active and passive signals into one BackendStatus (I4, P5).
  • Constraints introduced: health checks run on a connection pool separate from the request pool (never steal request-serving capacity).
Deliverable
  • All five health-check kinds (four active + passive) wired into BackendStatus.
  • A flapping-backend conformance test: a backend flipping healthy/unhealthy every 5 s never receives traffic during its unhealthy window.
Acceptance
  • A backend returning 100% 5xx is passively ejected within 2 s (fixture outlier_2s.json, §31 M3).
  • Flap-soak (5 s period, active+passive both wired): zero traffic sent during any unhealthy window (fixture flapping_backend.json).
  • Inconclusive outcomes never advance the consecutive-pass counter (fixture inconclusive_no_advance.json).
Fixtures
  • conformance/corpora/reload/flapping_backend.json — 5 s flap period, zero traffic during unhealthy windows.
  • conformance/corpora/reload/outlier_2s.json — 100% 5xx backend ejected within 2 s.
  • conformance/corpora/reload/inconclusive_no_advance.json — timeout-driven Inconclusive does not clear or advance health state.
  • conformance/corpora/reload/max_ejection_cap.json — a 2-backend cluster never ejects more than max_ejection_percent.
Pitfalls
  • Health checks consume upstream connection slots — use a dedicated connection pool, never the request-serving pool, or health-check load starves real traffic.
  • A health-check response slower than the request timeout must not be reported Healthy — the upstream may be overloaded, not dead; Inconclusive exists for exactly this and does not advance the pass counter.
  • Passive ejection on a 2-backend cluster will eject one backend on the first 5xx storm without the max_ejection_percent cap (default 50%) — do not disable the cap "to be safe."

⬜ Phase 6 — TLS Termination & Upstream Re-Encryption §18

Objectives
  • Terminate TLS at the listener with SNI multiplexing; re-encrypt to upstream by default (P8).
  • Support cert hot-reload without dropping in-flight connections.
  • Constraints introduced: TLS 1.3 default, TLS 1.2 opt-in per listener for legacy clients.
Deliverable
  • HTTPS proxy serving multiple SNI certificates to HTTP/1.1 and HTTP/2 clients, re-encrypting to upstream.
  • A conformance fixture verifying a wrong-SNI request receives a TLS unrecognized_name alert.
Acceptance
  • 10 distinct SNI certificates dispatch with 100% correct-cert selection (fixture sni_dispatch_10.json, §31 M4).
  • TLS handshake p99 < 5 ms with session resumption, < 25 ms full handshake (§4).
  • A cert hot-reload during 1,000 concurrent handshakes drops zero in-flight connections (fixture cert_reload_soak.json).
Fixtures
  • conformance/corpora/tls/sni_dispatch_10.json — 10-SNI, expected-cert-subject fixture.
  • conformance/corpora/tls/wrong_sni_alert.json — unconfigured SNI yields unrecognized_name.
  • conformance/corpora/tls/cert_reload_soak.json — 1,000-handshake concurrent reload, zero drops.
  • conformance/corpora/tls/ticket_rotation.json — I11 ticket-rotation-window assertion.
Pitfalls
  • TLS 1.3 0-RTT data is replayable; the proxy does not rate-limit it without an explicit anti-replay cache — default off, and non-idempotent methods must never enable it.
  • Session tickets outliving a master-key rotation force a full handshake fallback; tls_full_handshakes_total rising is the operator signal something is misconfigured (I11).
  • Upstream certs expiring mid-flight kill the next connection, not the in-flight one — upstream_cert_expiry_seconds must alert at 14 days remaining, not at expiry.

⬜ Phase 7 — Rate Limiting §19

Objectives
  • Protect backends from runaway clients with per-route and per-consumer limits.
  • Constraints introduced: rate-limit decisions must be O(1) per call (I14) and never block the data path.
Deliverable
  • Token-bucket and leaky-bucket rate limiters wired into the per-route and per-consumer paths.
  • A sustained-overload conformance test and a burst-tolerance conformance test.
Acceptance
  • 1,000 RPS sustained against a 100 RPS limit: ≥ 90% of requests receive 429 (fixture sustained_429.json).
  • A 200-request burst against a 100 RPS/200-burst limit returns 200 OK; the next 200-request burst within the same second returns 429 (fixture burst_429.json).
  • Retry-After is monotonic non-decreasing across consecutive denies for the same key (I14, fixture retry_after_monotonic.json).
Fixtures
  • conformance/corpora/routing/sustained_429.json — 1,000 RPS vs 100 RPS limit, ≥90% denied.
  • conformance/corpora/routing/burst_429.json — burst-tolerance fixture.
  • conformance/corpora/routing/retry_after_monotonic.json — I14 monotonicity assertion.
Pitfalls
  • Per-consumer-id limiting requires the consumer identified before the rate-limit check; JWT validation cost must itself be inside the rate-limit budget — a burst of 1,000 invalid JWTs against an unauthenticated route still costs CPU and must be bounded independently (§16.6 cross-reference).
  • A distributed (cross-replica) rate limiter needs shared state; Phase 0–10 ship per-instance limiting only — the cross-instance variant is PhaseDeferred("§38").

⬜ Phase 8 — Circuit Breaking & Outlier Ejection §20

Objectives
  • Prevent one bad backend, or a bad fraction of a cluster, from poisoning the whole cluster.
  • Ship per-cluster and independent per-backend breakers, plus bulkheading.
  • Constraints introduced: half-open probe quota must never be exceeded concurrently (I12).
Deliverable
  • Per-cluster and per-backend circuit breakers wired to the outlier ejector; bulkheading caps in place.
  • A conformance test: a 100%-5xx backend ejects within 2 s, the cluster breaker opens at threshold_percent, half-open probing recovers within recovery_seconds once the backend heals.
Acceptance
  • Cluster breaker opens within one health-check interval of crossing threshold_percent (fixture breaker_open.json, default interval per §17).
  • Half-open recovery completes within recovery_seconds (default 30 s) once the backend passes its probe quota (fixture breaker_recover.json).
  • Bulkhead queue never exceeds 2 × max_concurrent_requests entries (fixture bulkhead_cap.json).
Fixtures
  • conformance/corpora/reload/breaker_open.json — threshold-crossing opens the breaker.
  • conformance/corpora/reload/breaker_recover.json — half-open probe-quota recovery timing.
  • conformance/corpora/reload/bulkhead_cap.json — queue-size ceiling assertion.
  • conformance/corpora/reload/half_open_quota_exceeded.json — excess probes short-circuit to 503, never admitted (I12).
Pitfalls
  • Circuit breakers can stampede: when a breaker opens, a herd of clients sees 5xx; if they all retry the instant it half-opens, the healing backend is hit by a thundering herd — the half-open probe quota (I12) exists specifically to prevent this; do not skip it "to recover faster."
  • Bulkheading queues are a footgun: a 10,000-entry queue against a 100 ms latency budget produces 1,000 client-side timeouts before it drains — the default 2× sizing is deliberately conservative.

⬜ Phase 9 — Observability §21

Objectives
  • Ship the full Prometheus metric set, OpenTelemetry tracing, structured access logging, and per-route error budgets — this is what separates a hobby proxy from a production one.
  • Constraints introduced: no observability call may block the request thread (P4, P9).
Deliverable
  • A Grafana dashboard JSON (docs/api/ sibling asset, referenced from docs/runbooks/) rendering the four-golden-signals view (latency, traffic, errors, saturation).
  • A trace exported to a Jaeger-compatible OTLP sidecar shows the full request lifecycle including upstream connect and TLS handshake spans.
Acceptance
  • Metric cardinality stays < 50,000 series at 1,000-backend/100-route scale (fixture cardinality_budget.json).
  • Access-log line emitted for 100% of completed requests at 100,000 req/s sustained for 60 s, zero dropped log lines (fixture access_log_no_drop.json).
  • Trace export never adds > 100 µs to the request path even when the OTLP endpoint is artificially slowed to 500 ms (fixture trace_export_isolation.json).
Fixtures
  • conformance/corpora/reload/cardinality_budget.json — series-count ceiling assertion.
  • conformance/corpora/reload/access_log_no_drop.json — 100K req/s, zero dropped log lines.
  • conformance/corpora/reload/trace_export_isolation.json — slow-OTLP isolation fixture.
Pitfalls
  • Histogram bucket boundaries matter more than people expect: the default Prometheus buckets are wrong for sub-millisecond latency — the proxy ships its own bucket definitions (§5 SRE book).
  • Trace export blocks the request thread if the OTLP endpoint is slow and export is inline — use the batching exporter exclusively, never export from the request task.
  • The access log is on the hot path; format it lazily on the writer task and pass typed fields through the channel, never a pre-formatted string (P3, ADR-26).

⬜ Phase 10 — Admin API & Hot Reload §22

Objectives
  • Make the proxy operable: reload, drain, inspect, all via one audited, mTLS-only API (P10).
  • Ship the two-phase reload protocol underpinning I1/I2.
  • Constraints introduced: every mutation writes an audit record before returning success (I10).
Deliverable
  • The admin API serves its OpenAPI schema at docs/api/admin.openapi.yaml (ADR-15).
  • A reload soak test: 100 back-to-back reloads produce zero dropped requests.
Acceptance
  • 100-reload soak: zero dropped requests, zero 5xx storms, monotonically increasing generation (fixture reload_soak_100.json, §31 M5).
  • Time from /admin/config/reload acceptance to first request served on the new snapshot < 50 ms (§4, fixture reload_latency.json).
  • Every admin call — success or failure — produces exactly one audit record (fixture audit_completeness.json, I10).
Fixtures
  • conformance/corpora/reload/reload_soak_100.json — 100 reloads, zero drops, monotonic generation.
  • conformance/corpora/reload/reload_latency.json — < 50 ms time-to-first-new-request.
  • conformance/corpora/reload/audit_completeness.json — one audit record per admin call.
  • conformance/corpora/reload/rollback_on_invalid.json — a reload with an invalid cluster reference rolls back cleanly.
Pitfalls
  • A reload failing partway (e.g. a discoverer cannot connect for the new config) must roll back to the previous snapshot, not commit a half-built one — the two-phase protocol exists precisely for this (I2).
  • The audit log is the security boundary of the entire mutation surface; if it silently drops a record on sink failure, mutations become undebuggable — fail the call closed instead (I10).
  • Un-draining via a live admin call (rather than requiring a reload) is a fat-finger hazard — deliberately not exposed.

⬜ Phase 11 — HTTP/2, HTTP/3 & gRPC §23

Objectives
  • Generalize the L7 path to multiplexed streams: HTTP/2 (Hyper), HTTP/3 (Quinn+h3), and gRPC pass-through over both.
  • Constraints introduced: HPACK/QPACK dynamic-table sizes are bounded to prevent header-bomb OOM (§25 T5).
Deliverable
  • End-to-end gRPC echo example via examples/grpc-p2c/.
  • HTTP/2 conformance against a subset of h2spec; HTTP/3 conformance against a subset of qns-interop.
Acceptance
  • HTTP/2 single-core throughput ≥ 80,000 req/s @ 1 KiB response (§4, §31 M8).
  • HTTP/3 conformance subset (qns-interop-derived) passes 100% (§31 M9).
  • gRPC conformance (unary + all three streaming modes) passes 100% (§31 M10).
  • HPACK/QPACK dynamic table capped at 4 KiB confirmed under a header-bomb fixture (T5, §25).
Fixtures
  • conformance/corpora/h2/h2spec_subset.json — HTTP/2 framing/flow-control conformance.
  • conformance/corpora/h3/qns_interop_subset.json — HTTP/3/QUIC conformance.
  • conformance/corpora/grpc/unary_streaming_bidi.json — full gRPC mode coverage.
  • conformance/corpora/h2/header_bomb.json — HPACK dynamic-table-size attack, capped at 4 KiB.
Pitfalls
  • HTTP/2 head-of-line blocking is a TCP-layer problem, not an HTTP-layer one — the fix is HTTP/3, not a proxy-side workaround.
  • gRPC errors return HTTP 200 with grpc-status != 0 in trailers — a status-class metric computed from HTTP status alone miscounts the error budget; the error-budget logic (§21.2) must special-case gRPC trailers.
  • HPACK/QPACK dynamic table size is per-connection; an uncapped table lets a misconfigured or malicious upstream/client OOM the proxy via header bombs — cap at 4 KiB on both sides.

⬜ Phase 12 — Multi-Node Topology §24

Objectives
  • Lift the proxy from a single binary to a fleet: single-node, active-passive (VRRP), and active-active (consistent-hash) topologies.
  • Constraints introduced: the proxy binary itself is topology-unaware; topology is composed externally or via lb-topology glue (P1: one core, reused across all three).
Deliverable
  • A topology=active_active config driving a 3-node cluster behind a Maglev-hashed front-door.
  • A failure-injection test: kill one of three nodes; the surviving two absorb traffic with no client-visible 5xx within the gossip convergence window.
Acceptance
  • Active-passive VRRP failover completes in < 3 s (§4, fixture vrrp_failover.json).
  • Active-active 1-of-3 node kill: zero client-visible 5xx after the gossip convergence window (< 5 s, §4, §31 M11, fixture node_kill_3.json).
  • Post-failure key redistribution disturbs ≤ 1/N of keys (fixture redistribution_bound.json, consistent with §8.7/§35).
Fixtures
  • conformance/corpora/reload/vrrp_failover.json — VIP failover timing.
  • conformance/corpora/reload/node_kill_3.json — 3-node active-active kill-one fixture.
  • conformance/corpora/reload/redistribution_bound.json — 1/N disruption bound assertion.
Pitfalls
  • Active-passive failover is a TCP-and-ARP problem, not just an IP problem — keepalived must emit a gratuitous ARP on VIP move, and the kernel neighbor cache must update, or clients keep sending to the dead node's MAC.
  • Active-active sharding requires the client (or upstream LB) to hash to the node the proxy expects — a mismatch silently doubles latency via an extra hop rather than failing loudly.
  • The gossip convergence window is non-zero; during it, both the old and new owner of a key may serve it — idempotent operations are safe, bare counter increments are not (documented application-level contract, not a proxy guarantee).
