Decisions (§9) · 26 ADRs

A01

Implementation language

Chosen

Rust 2021, MSRV 1.74

Rejected

C++ (mediasoup/Janus class), Go (Pion/LiveKit), Zig

When the rejected choice is right

C++ wins when the team already owns a mature C++ media codebase (libwebrtc) and the marginal safety win doesn't offset a full rewrite; Go wins for a control-plane-only service with no hot forwarding path, where GC pause tolerance is high and hiring velocity matters more than tail latency

Why: memory safety on adversarial RTMP/BMFF/RTP bytes; no GC tail in SFU hot path; Bytes zero-copy egress (§1.9)

A02

Async runtime

Chosen

tokio multi-thread, work-stealing

Rejected

async-std, glommio (thread-per-core), hand-rolled epoll

When the rejected choice is right

glommio (thread-per-core, io_uring) wins once egress exceeds tokio's syscall-batching ceiling on a single NUMA node and cross-core work-stealing overhead dominates — a future post-v1.0 lever (Scalability Analysis)

Why: mature ecosystem; sendmmsg/recvmmsg via socket2; per-room single-writer task isolates lock-free forward path

A03

Workspace / build

Chosen

Cargo workspace, 14 crates (§1.5)

Rejected

monolithic crate, Bazel

When the rejected choice is right

Bazel wins once flux must build alongside non-Rust services in one monorepo with cross-language remote caching; a monolithic crate wins for a single-engineer prototype where crate-boundary discipline isn't yet needed

Why: crate boundaries enforce layering (flux-core ⊥ daemon); independent test/fuzz targets; embeddable libraries (DP)

A04

Zero-copy buffers

Chosen

bytes::Bytes/BytesMut refcounted slices

Rejected

Vec<u8> + clone, Arc<[u8]>

When the rejected choice is right

Vec<u8> wins for low-fan-out batch/VOD tooling where clone cost is negligible and Bytes' refcount bookkeeping isn't worth its complexity

Why: fan-out forwards a refcounted slice to N consumers without copy; Gbps egress (§4)

A05

RTP/RTCP design

Chosen

Sans-IO codec (parse/serialize pure; IO at edges)

Rejected

When the rejected choice is right

an IO-coupled codec wins when adopting an existing battle-tested stack (libwebrtc) wholesale is cheaper than re-deriving its edge cases, and Sans-IO's testability premium isn't needed

Why: deterministic, table-testable, fuzzable without sockets; mirrors str0m/Pion interceptor split (R4/R10)

38. Alternative Architectures (Roads Not Taken)

Four fundamentally different architectures for the same problem space — not parameter tweaks.

(A) MCU (Multipoint Control Unit) — server-side composite + re-encode.

producers --> [ DECODE + COMPOSITE + RE-ENCODE ] --> one mixed stream --> every subscriber
                        (server-side pixel pipeline)

Regime where it wins: very low-power/low-bandwidth clients (feature phones, PSTN gateways) that can decode only one incoming stream and cannot handle simulcast negotiation. Real system: legacy hardware MCUs (Polycom/Cisco conference bridges) and early enterprise video-bridge products. Rejected because: CPU cost is O(participants × pixels) instead of O(packets) (violates DP3), doesn't scale past small rooms, and the encode hop adds latency that breaks the <500 ms glass-to-glass budget (§4).

(B) Full mesh — no server-side media component at all.

peer A <--> peer B
  ^  \      /  ^
  |   \    /   |
  v    \  /    v
peer D <--> peer C     (every peer sends to every other peer directly)

Regime where it wins: 2–3 participant calls, or a deployment with zero appetite for media-server operational burden. Real system: early WebRTC group calls in P2P mode (small Jitsi Meet rooms, early appear.in). Rejected because: N² uplink cost on each participant's home connection is precisely the problem selective forwarding was invented to solve (§2); one participant's poor uplink degrades everyone; it stops scaling past ~4 peers (§33).

(C) Per-consumer transcoding SFU — re-encode a personalized bitrate for every subscriber.

one high-quality source --> [ per-consumer TRANSCODE ] --> consumer 1 (custom bitrate)
                                                       --> consumer 2 (custom bitrate)
                                                       --> consumer N (custom bitrate)

Regime where it wins: a publisher that can't or won't send multiple simulcast layers (a legacy or bandwidth-constrained encoder) but a downstream population with precisely heterogeneous bandwidths that simulcast's discrete rungs approximate too coarsely. Real system: some cloud/webinar transcoding-bridge products. Rejected because: it violates DP3, multiplies CPU by O(consumers) instead of O(packets), and adds an encode-latency hop that defeats the SFU's core forwarding-latency advantage (§4); simulcast/SVC (§22) gets acceptable quality diversity at near-zero marginal CPU.

(D) Codec/transport co-designed pipeline — one adaptive loop spanning encode and network.

[ ENCODER <-- rate/loss feedback --> NETWORK STACK ]  (one integrated control loop, one team owns both ends)

Regime where it wins: a single-hop, single-vendor deployment where one team controls both the codec and the transport end-to-end and can co-adapt frame-level encode decisions to instantaneous network state. Real system: Salsify (Fouladi et al., NSDI 2018 research prototype). Rejected because: flux must interoperate with arbitrary third-party encoders (OBS, hardware encoders) over a standard ingest protocol (RTMP) and standard SFU/signaling surfaces — a codec/transport co-design requires owning both ends, which breaks DP1 (coded-frame agnosticism) and the project's interoperability goal (§2).
