Decisions (§9) · 34 ADRs

001

Language

Chosen

Python ≥3.11

Rejected

Rust core + Python bindings; Go; Julia

When the rejected choice is right

CPU-bound harness control plane with pure-Python plugins and no FFI latency; a Rust core wins when the control plane itself is compute-saturated rather than I/O-bound — e.g., a high-throughput streaming parser or a local-model batching kernel running millions of samples/s

Why: Dataset/model/judge/stats ecosystem is Python; researcher-authorable plugins; control plane is I/O-bound not CPU-bound → Rust speed unneeded; FFI seam rejected.

002

Numerics

Chosen

numpy + scipy.stats

Rejected

hand-rolled

When the rejected choice is right

Hand-rolled numerics win when the target is an embedded system or microcontroller where numpy is unavailable or when binary size is constrained below numpy's footprint

Why: Vectorized bootstrap/tests; correct, audited stat fns.

003

Packaging

Chosen

pyproject.toml (PEP 621) + uv/pip; src layout

Rejected

setup.py; poetry-only

When the rejected choice is right

poetry-only wins on small pure-Python libraries with no binary deps where its lock format is preferred by the team and uv speed is not a bottleneck

Why: Modern, reproducible; lockfile pinned.

004

Dependency policy

Chosen

pinned lock (uv.lock/requirements.lock) + pip-audit

Rejected

floating

When the rejected choice is right

Floating deps win in rapid prototyping notebooks where pinning creates friction and reproducibility is not yet a requirement — never in a published benchmark harness

Why: Reproducible builds + supply-chain gate.

005

Dataset format

Chosen

JSON Lines (jsonl) + optional HF datasets adapter

Rejected

CSV; pickle

When the rejected choice is right

CSV wins when the dataset is owned by a non-engineering team that edits it in spreadsheet tools and streaming/hashing are not required; pickle wins for numpy-array datasets where schema validation is handled externally

Why: Streamable, diffable, hashable; pickle is unsafe.

006

Canonical serialization

Chosen

RFC 8785 JSON canonicalization (manifests, cache keys)

Rejected

repr(); pickle; default json

When the rejected choice is right

repr-based or default json.dumps serialization wins for human-readable debug logs where byte-stability is irrelevant and canonical ordering adds friction

Why: Byte-stable hashing → stable cache keys + manifests (I6/I10).

007

Hash function

Chosen

SHA-256 (hashlib)

Rejected

md5; xxhash

When the rejected choice is right

xxhash wins when collision resistance is not required and throughput dominates — e.g., a hot-path in-process dedup cache for ephemeral objects that never enter a manifest

Why: Collision-resistant content addressing; xxhash for non-security perf paths only.

008

Run-cache store

Chosen

content-addressed dir (sharded) + sqlite index

Rejected

redis-only; flat dir

When the rejected choice is right

Redis-backed cache wins when multiple machines need a shared mutable completion cache with sub-millisecond cross-host lookup and a server is already provisioned in the infrastructure

Why: Durable, resumable, no server; sqlite index for fast lookup.

009

Result/provenance store

Chosen

append-only jsonl + sqlite metadata; immutable

Rejected

mutable db rows

When the rejected choice is right

A mutable database wins when results need updates — e.g., annotation pipelines that refine labels in place — where append-only provenance is sacrificed for mutability

Why: Provenance (I7); audit trail.

010

Concurrency model

Chosen

asyncio for API I/O + multiprocessing/process pool for CPU scoring & sandbox

Rejected

threads-only; pure async

When the rejected choice is right

Thread-per-request wins for simple synchronous metric backends where asyncio complexity is unwarranted and the concurrency level is low (< 20 workers)

Why: API calls are I/O-bound (async); scoring/sandbox are CPU/isolation-bound (processes).

011

Backpressure / rate-limit

Chosen

token-bucket per backend + bounded async queue

Rejected

unbounded gather

When the rejected choice is right

Unbounded gather wins in a batch-offline job that owns the backend and rate limiting is irrelevant — e.g., a local model run with no external API quota

Why: Honor provider rate caps (I5); no overspend bursts.

012

Model backend SDKs

Chosen

thin adapters over OpenAI/Anthropic/local + #330 runtime

Rejected

one hard-coded SDK

When the rejected choice is right

A single hard-coded SDK wins for a purpose-built internal tool that only ever calls one provider and plugin indirection adds maintenance overhead with no benefit

Why: Pluggable Model protocol; backends swappable.

013

Sandbox (pass@k)

Chosen

delegate to #50 sandbox (subprocess + seccomp/nsjail/container)

Rejected

bare exec()

When the rejected choice is right

Bare exec() wins for a fully trusted, sandboxed CI environment where the harness itself runs inside a container and adding a nested seccomp layer adds latency with no security gain

Why: Untrusted code isolation; resource caps; no network.

014

Tokenizer (budget + BLEU)

Chosen

pinned tiktoken/HF tokenizer @version; sacrebleu tokenizer for BLEU

Rejected

ad-hoc split

When the rejected choice is right

Ad-hoc tokenizer splitting wins for quick prototyping when budget enforcement is approximate and BLEU is not required to match a canonical published number

Why: BLEU/budget are tokenization-sensitive; pin version (I2).

015

Stats: bootstrap

Chosen

numpy seeded Generator resampling; BCa for skewed

Rejected

naive percentile only

When the rejected choice is right

Naive percentile bootstrap wins when the metric distribution is known symmetric and the sample size is large (n > 1000) where BCa's jackknife overhead saves no coverage accuracy

Why: Correct CIs; reproducible (I12).

016

Significance tests

Chosen

paired bootstrap + McNemar (binary) + t-test (continuous, with caveats)

Rejected

unpaired only

When the rejected choice is right

Unpaired tests win when comparing two models evaluated on independent, non-overlapping sample populations where pairing would require alignment that does not exist

Why: Paired tests for same-sample comparisons (Dror 2018).

017

Multiple comparisons

Chosen

Holm-Bonferroni (default) + Benjamini-Hochberg (FDR option)

Rejected

none

When the rejected choice is right

No correction wins when reporting is exploratory, a single primary metric is pre-registered, and there is no family of slices to inflate the false-positive rate

Why: Control family-wise/false-discovery across slices/metrics.

018

Logging

Chosen

structlog (structured JSON)

Rejected

stdlib print

When the rejected choice is right

stdlib print logging wins for single-script tools where structured JSON parsing adds friction and the log consumer is a human reading a terminal

Why: Machine-parsable; per-sample + per-run context.

019

Metrics/telemetry

Chosen

OpenTelemetry → Prometheus exporter

Rejected

bespoke

When the rejected choice is right

A bespoke metrics system wins when the deployment environment has no Prometheus infrastructure and the overhead of OTel exporter dependencies outweighs the benefit

Why: Standard counters/histograms (throughput, cost, cache-hit).

020

Tracing

Chosen

OpenTelemetry spans (run/sample/judge)

Rejected

none

When the rejected choice is right

No tracing wins for batch-offline jobs where latency attribution is irrelevant and the trace volume would overwhelm the backend

Why: Latency + budget attribution.

021

Testing

Chosen

pytest + hypothesis (property) + golden snapshots

Rejected

unit only

When the rejected choice is right

Unit-only testing wins for a small, stable library where property space is narrow and hypothesis overhead is not justified

Why: Property tests for metric purity/invariants; conformance goldens (cross-link #137).

022

Differential oracle

Chosen

reference metric libs (sacrebleu, rouge-score, scikit) offline

Rejected

none

When the rejected choice is right

No differential oracle wins when the metric is novel with no reference implementation and the only ground truth is a curated golden dataset

Why: Cross-validate our metric impls.

023

Fuzzing

Chosen

atheris (libFuzzer for Python) on parsers/cache-key/judge-parse

Rejected

none

When the rejected choice is right

No fuzzing wins for a small codebase with a narrow, fully-validated input grammar where the fuzz corpus would cover no new paths

Why: Malformed input → no crash/oscillation.

Determinism CI

Chosen

Rejected

none

No determinism CI gate wins when the system is intentionally nondeterministic (e.g., human-in-the-loop) and replay equivalence is not a design goal

A simpler shell-script CI wins for a solo project where GitHub Actions YAML complexity is unwarranted and merge gating is informal

Type checking

Rejected

When the rejected choice is right

Untyped code wins for throwaway scripts or research notebooks where mypy strict overhead blocks iteration speed

Why: Plugin contracts enforced statically.

Lint/format

Rejected

When the rejected choice is right

Separate flake8 + black wins when a team's existing toolchain pre-dates ruff and migration cost outweighs consolidation benefit

Containers

Chosen

Dockerfile (slim) + compose (cache vol + prometheus + sandbox)

Rejected

host-only

When the rejected choice is right

Host-only deployment wins when Docker is not available in the target environment (e.g., HPC cluster) and reproducibility is achieved via conda/spack environment files

029

Error model

Chosen

typed exception hierarchy; no bare except on data path

Rejected

When the rejected choice is right

Bare except on a best-effort background logger wins where crashing an observability side-channel would disrupt the main data path and silent failure is preferable

Why: Typed recovery; fail-closed budgets (I5).

Schema/cache-key versioning

Chosen

SemVer on evalh.types, TaskSpec, MetricSpec, cache-key schema

Implicit versioning wins for a private research repo where the team is small and all consumers are on the same commit — external consumers and cached completions are the forcing function for explicit SemVer

Why: Compatibility + cache-invalidation discipline (I6; see Compatibility & Versioning).

Alt-A: Static Benchmark Scoring with Exact/Fuzzy Match Only

┌─────────────────────────────────────────────────────────┐
│ Benchmark JSONL (fixed, public, pre-split)               │
└───────────────────────┬─────────────────────────────────┘
                        │ all test samples
┌───────────────────────▼─────────────────────────────────┐
│ Model Inference (batch all N samples)                    │
└───────────────────────┬─────────────────────────────────┘
                        │ N completions
┌───────────────────────▼─────────────────────────────────┐
│ Exact-match or fuzzy-match scorer                        │
│ (normalize → compare → accuracy)                        │
└───────────────────────┬─────────────────────────────────┘
                        │ accuracy (point estimate)
┌───────────────────────▼─────────────────────────────────┐
│ Report: "Accuracy = X%"                                  │
└─────────────────────────────────────────────────────────┘

Wins when: the benchmark is a well-curated closed set, models are cheap to query, the result is a leaderboard number for a paper appendix, and operational rigor (CIs, resume, cost) is not required. Embodied by: EleutherAI lm-evaluation-harness in its early form; any one-off eval script. Why rejected here: produces bare point estimates with no CI (violates Principle 1); no run-cache means re-runs re-spend full inference budget; no manifest means reviewers cannot reproduce the number; contamination is assumed away rather than checked.

Alt-B: LLM-as-Judge / Model-Graded Evaluation Only

┌─────────────────────────────────────────────────────────┐
│ Open-ended prompt dataset (no gold references needed)    │
└───────────────────────┬─────────────────────────────────┘
                        │ prompts
┌───────────────────────▼─────────────────────────────────┐
│ Candidate model → free-form responses                    │
└───────────────────────┬─────────────────────────────────┘
                        │ response pairs (A, B)
┌───────────────────────▼─────────────────────────────────┐
│ LLM Judge (e.g., GPT-4)                                  │
│ single-order: (question, A, B) → winner                  │
│ (no swap; no calibration)                                │
└───────────────────────┬─────────────────────────────────┘
                        │ win-rates (raw)
┌───────────────────────▼─────────────────────────────────┐
│ Report: "Model A wins 63% of pairs"                      │
└─────────────────────────────────────────────────────────┘

Wins when: tasks have no gold reference (open-ended instruction following, creative writing, long-form QA) where EM/F1/BLEU are meaningless and a capable judge model provides a meaningful signal. Embodied by: MT-Bench (Zheng et al. 2023). Why rejected here: this design buries the judge as one component inside a full harness (Phase 8) rather than replacing it; without a reference-metric layer, code tasks (pass@k), calibration (ECE), and n-gram metrics are not supported; and the naive single-order judge creates systematic position bias that this architecture has no mechanism to detect.

Alt-C: Human Preference Elo Arena

┌──────────────────────────────────────────────────────────┐
│ User sends a real query (no dataset; live traffic)        │
└────────────────────────┬─────────────────────────────────┘
                         │
┌────────────────────────▼─────────────────────────────────┐
│ Arena: route to Model A and Model B anonymously           │
│ (random assignment per query)                             │
└──────────┬─────────────────────────────┬─────────────────┘
           │ response A                   │ response B
┌──────────▼─────────────────────────────▼─────────────────┐
│ Human voter: "which is better?" → preference vote         │
└────────────────────────┬─────────────────────────────────┘
                         │ votes
┌────────────────────────▼─────────────────────────────────┐
│ Bradley-Terry Elo model → ranked leaderboard              │
└──────────────────────────────────────────────────────────┘

Wins when: the evaluation target is open-ended human-preferred helpfulness on real-user queries, benchmark gaming is a known risk, and the deployment context provides sufficient live traffic for Elo convergence. Embodied by: LMSYS Chatbot Arena. Why rejected here: requires live user traffic and a human annotation pipeline (an explicit non-goal in §1); cannot run in CI; provides no reproducibility guarantee — a number changes as more votes arrive; contamination and split discipline are undefined in this model; and it cannot evaluate closed-form tasks (code, math, classification) where there is a ground-truth answer.

Alt-D: Reference-Based NLG Metrics Only (BLEU/ROUGE/BERTScore)

┌─────────────────────────────────────────────────────────┐
│ Source + Reference translation/summary corpus            │
└───────────────────────┬─────────────────────────────────┘
                        │ (source, reference) pairs
┌───────────────────────▼─────────────────────────────────┐
│ Model → hypothesis (generated text)                      │
└───────────────────────┬─────────────────────────────────┘
                        │ (hypothesis, reference) pairs
┌───────────────────────▼─────────────────────────────────┐
│ Corpus-BLEU / ROUGE / BERTScore scorer                   │
│ (no judge, no sandbox, no CI)                            │
└───────────────────────┬─────────────────────────────────┘
                        │ corpus-level metric score
└─────────────────────────────────────────────────────────┘

Wins when: the task is machine translation or extractive summarization with high-quality reference translations, evaluation must be fully automated with zero inference cost beyond the candidate model, and the metric is being used for a development signal (not a final published comparison). Embodied by: WMT shared task leaderboards; early ROUGE-based summarization benchmarks. Why rejected here: BLEU/ROUGE have low sentence-level correlation with human judgment on instruction-following and QA tasks (a well-documented limitation since Callison-Burch et al. 2006); they are retained in this design as one metric option (Phase 6) but are not the evaluation backbone; and they cannot grade code correctness, calibration, or open-ended generation.
