331 — AI Evaluation Harness from Scratch

Project Number: 331

Project Name: AI Evaluation Harness from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build a framework for evaluating LLMs and agents reproducibly and at scale. Declarative tasks bind a dataset + prompt template + few-shot config + metric set + decoding params; a runner executes a model-under-test over the dataset; scorers compute metrics; statistics aggregate with confidence intervals; a regression engine compares against pinned baselines; a reporter emits a reproducible artifact. Equivalent in spirit to lm-eval-harness / HELM / OpenAI evals, rebuilt from first principles with determinism, provenance, and statistical rigor as load-bearing properties — not afterthoughts.

The novelty over a one-off eval script: a deterministic run-cache keyed by every output-affecting input (task-version ⊕ model-version ⊕ prompt ⊕ params) makes re-runs cheap, resumable, and exactly-once; a manifest (code hash ⊕ data hash ⊕ model version ⊕ config ⊕ RNG seeds ⊕ env) makes any headline number reproducible bit-for-bit; and every reported number carries a confidence interval — never a bare point estimate.

System boundaries (in scope):

  • Task & dataset registry: declarative TaskSpec (dataset ref + prompt template + few-shot + metric set + decoding params), content-addressed, versioned; dataset loaders with content-hash; train/dev/test split discipline; contamination/leakage detection.
  • Prompt / template management: versioned templates, deterministic few-shot exemplar selection (fixed seed), chat vs completion formatting, system/user/assistant roles, tokenization-budget enforcement.
  • Model-under-test abstraction: pluggable backends — local model, hosted API, the #330 streaming token-generation runtime; request batching; retry/timeout/rate-limit handling; deterministic generation controls (seed, temperature=0 path) where the backend supports them.
  • Runner / execution engine: parallel/async execution, sharding across workers, the deterministic run-cache (completion cache keyed by output-affecting inputs), idempotent exactly-once scoring, crash-resume from a durable journal.
  • Metrics: exact-match, token-F1 / span-F1, accuracy, BLEU/ROUGE/METEOR, pass@k via a code-exec sandbox (cross-link #50), perplexity / log-likelihood, calibration (ECE), pairwise win-rate; a metric plugin contract.
  • LLM-as-judge: rubric scoring, pairwise comparison, position-bias mitigation (swap & average), judge calibration vs human labels, self-consistency, judge-model versioning; judge bias/variance treated as first-class.
  • Statistics: bootstrap confidence intervals, paired significance tests (paired bootstrap / McNemar / t-test), variance decomposition, multiple-comparison correction, minimum-detectable-effect / sample-size guidance, stratified aggregation.
  • Regression detection & leaderboards: baseline pinning, A/B model compare with CIs, regression gates in CI, per-slice breakdowns, leaderboard store.
  • Reproducibility & provenance: run manifest, full result + transcript persistence, deterministic replay, audit trail.
  • Observability: throughput (samples/s), cost/tokens, cache hit-rate, judge-call budget, failure/timeout rates, score distributions, flakiness.

Explicit non-goals (deferred, gated PhaseDeferred("Deferred Features Register")):

  • Training / fine-tuning models — the harness only evaluates; training lives in #114/#329. PhaseDeferred("Deferred Features Register").
  • Serving the model-under-test in production — backends are eval-time clients, not a serving plane. PhaseDeferred("Deferred Features Register").
  • A general agent framework / tool-use orchestration beyond a single-turn + minimal multi-turn rollout adapter. PhaseDeferred("Deferred Features Register").
  • Distributed multi-node sharding beyond process-level workers on one host; cloud queue fan-out. PhaseDeferred("Deferred Features Register").
  • Human-annotation collection UI; we consume human labels for judge calibration but do not gather them. PhaseDeferred("Deferred Features Register").
  • GPU/accelerator kernels for local backends — local model inference is delegated to an external runtime (#330), not implemented here. PhaseDeferred("Deferred Features Register").

Deployment model: a Python package (evalh) plus a thin evalh CLI/driver. evalh run --task gsm8k --model openai:gpt-x --shots 5 loads a task, runs the model, scores, aggregates with CIs, writes a manifest + result store + report; evalh compare, evalh replay, evalh report operate over stored runs. Embeds as a library beneath CI gates and research notebooks.

Target users/operators/developers: ML/eval engineers wiring a model into a leaderboard; researchers who need a paper number to be reproducible by reviewers; infra engineers running nightly regression gates; anyone debugging why a benchmark number moved at 3 a.m. without re-spending the inference budget.

Phase 0 deliverable (numbered packages/modules):

  1. evalh.types — TaskSpec, Sample, Prediction, Score, RunManifest, content-hash helpers, error hierarchy.
  2. evalh.registry — declarative task/dataset/metric/template registration; resolution by (name, version).
  3. evalh.task — Task object: bind dataset + template + few-shot + metrics + decoding into an executable spec.
  4. evalh.dataset — dataset loaders (in-memory + JSONL) with content-hash; split tags (train/dev/test).
  5. evalh.model — Model protocol + a deterministic EchoModel / MockModel for tests (real backends in §Phase 4).
  6. evalh.runner — single-process runner: iterate samples → call model → store predictions (cache/parallelism in §Phase 5).
  7. evalh.metric — metric plugin contract + ExactMatch baseline; MetricResult.
  8. evalh.report — minimal text/JSON report renderer; evalh CLI: run a task end-to-end on MockModel, print scores.

What later phases unlock: dataset loaders + content-hash + split discipline (Phase 1); prompt/template + few-shot (Phase 2); model-under-test + deterministic controls + real backends (Phase 3); multi-turn rollout + answer parsing (Phase 4); runner + parallelism + run-cache + resume (Phase 5); core metrics EM/F1/BLEU/ROUGE (Phase 6); pass@k via sandbox (Phase 7); LLM-as-judge + bias mitigation + calibration (Phase 8); statistics — bootstrap CI + paired tests + power (Phase 9); regression detection + leaderboards + CI gates (Phase 10); reproducibility manifest + replay + provenance (Phase 11); observability + reporting (Phase 12); soak + conformance + contamination audit (Phase 13).

Timeline: Phase 0 = 6–14 weeks. Full plan = 6–9 months.

Recommended language: Python (≥3.11). Rationale: (a) the entire dataset/model/judge ecosystem (HF datasets, tokenizers, OpenAI/Anthropic SDKs, scikit/scipy/numpy for stats) is Python-native; (b) metric/judge/scorer plugins must be trivially authorable by researchers — duck-typed protocols + entry-points beat a compile cycle; (c) LLM-as-judge prompt iteration is an interactive, notebook-driven loop; (d) numerical libs (numpy/scipy) give correct, fast bootstrap/CI/significance math; (e) pytest + hypothesis cover property/conformance testing. The determinism-critical core (run-cache key derivation + journal) is small, pure, and content-hash based — it does not need a systems language. A Rust core for the deterministic runner/cache was considered and rejected in ADR-001 (FFI seam + plugin-authoring friction outweigh the marginal speed of a control plane that is I/O- and inference-bound, not CPU-bound). Locked in ADR-001.

Prerequisites: probability + statistics (bootstrap, hypothesis tests, multiple comparisons, power analysis); NLP metrics (n-gram overlap, tokenization); LLM decoding semantics (temperature, top-p, seeds, logprobs); content-addressed storage + hashing; idempotency / exactly-once design; sandboxing for code execution (cross-link #50); basic distributed work-sharding + backpressure; bias/variance reasoning for judge models. Conceptual ancestor: #137 Test Framework + Assertion Engine (Rust) — assertions, fixtures, deterministic test selection map directly onto metrics, conformance fixtures, and the run-cache here.

2. Why Build This

  • Unique systems knowledge: measurement as a system. Most engineers can write a one-off accuracy script; few can build an eval that is reproducible, resumable, statistically honest, and cheap to re-run. This project teaches why a bare benchmark number is nearly meaningless (no CI, no provenance, no contamination check) and how to make it trustworthy.
  • Historical / architectural significance: the field's shift from leaderboard point-numbers to rigorous, contamination-aware, CI-bounded evaluation (HELM 2022; lm-eval-harness; OpenAI/Anthropic internal evals). Reproducibility crises (train/test leakage, prompt-format sensitivity, judge bias) are the reason this discipline exists.
  • Engineering muscles: content-addressed caching; idempotent exactly-once execution under crashes; deterministic replay of a system whose backend is non-deterministic; statistical estimation (bootstrap, paired tests, power); adversarial reasoning about a model that grades models (judge bias/variance); plugin contracts; provenance/manifest design.
  • Production concepts exercised: regression gating in CI; budget enforcement (token/cost/judge-call ceilings); backpressure + rate-limit handling against hosted APIs; sandboxed untrusted-code execution; stratified aggregation; supply-chain-grade provenance.
  • Cross-links:
    • #137 Test Framework + Assertion Engine (Rust) — assertions/fixtures/deterministic selection are the conceptual ancestor of metrics/conformance/run-cache.
    • #50 Sandbox / Isolation — the code-execution sandbox that makes pass@k safe (§7).
    • #119 RL Environment + #120 RLHF — evaluation is the reward/eval signal; a stable eval is a prerequisite for stable RL.
    • #329 Vector Embedding Training Pipeline — a downstream consumer of this harness (embedding-retrieval eval tasks).
    • #330 Streaming Token Generation Runtime — a first-class backend for the model-under-test abstraction (§4).
  • Calibration value: after this you can audit any published benchmark, detect contamination and prompt-format artifacts, attach correct error bars, design a judge that is calibrated against humans, and build a regression gate that does not flap on noise.

What Mastery Looks Like — finishing this blueprint means you can:

  • Design a content-addressed run-cache with a formally correct key schema that provably prevents stale-completion bugs under any prompt-template change (Phase 5, Phase 2)
  • Derive a bootstrap confidence interval with seeded numpy resampling, choose BCa vs percentile for a given metric's skew, and justify the paired vs unpaired test decision for a given A/B comparison (Phase 9)
  • Instrument a pairwise LLM-as-judge with swap-and-average position-bias removal, measure residual bias, and calibrate judge agreement against human labels via Cohen's κ (Phase 8)
  • Audit any published benchmark number for contamination, prompt-format sensitivity, and missing CIs, and reproduce or refute it from a RunManifest alone (Phase 11, Phase 13)
  • Build a CI regression gate that holds a false-positive rate ≤ 1% under the null via paired significance testing and multiple-comparison correction (Phase 10, Phase 9)
  • Implement the unbiased pass@k estimator, integrate it with a seccomp-isolated code-execution sandbox, and account for variance across problems correctly (Phase 7)
  • Emit a canonical, byte-stable RunManifest that binds code⊕data⊕model⊕config⊕seed⊕env and reconstruct any aggregate without re-spending inference (Phase 11)

Per-box dense notes:

  • Caller / CLI — constructs an immutable EvalRequest; all seeds explicit. Trust boundary: request validated (task/model exist, budgets sane) before any inference spend.
  • Registry — resolves (name, version) to content-hashed specs; refuses unversioned or drifted specs. Source of truth for what a task is. Cross-link #137 (deterministic test selection ≈ deterministic task resolution).
  • Task binder — turns a spec into an executable Task; enforces split discipline (eval reads only the declared split) and runs the contamination check (train/test overlap, canary strings). Token-budget enforcement happens here against the model's context window.
  • Dataset — loaders compute a content-hash over the materialized split (post-filter, post-shuffle-with-seed) → the hash that enters the cache key and manifest. Maintains a leakage/contamination index.
  • Prompt — versioned templates; deterministic few-shot exemplar selection (fixed seed over the train/dev pool, never the eval split); chat vs completion formatting; role assembly.
  • Runner — the execution core. Computes the cache key per sample (output-affecting inputs only — Invariant I1/I6), checks the run-cache, calls the model on a miss, journals progress for crash-resume, guarantees exactly-once scoring. Concurrency + backpressure boundary against the model backend.
  • Run-cache — content-addressed completion store: key → Completion. Makes re-runs free and resumable; the key must include every output-affecting input or stale completions poison results (I6).
  • Model-under-test — pluggable backend protocol; local model, hosted API, or #330 streaming runtime. Owns retry/timeout/rate-limit + deterministic-generation controls (seed, temperature=0) where supported. Trust + non-determinism boundary: backend output may be non-deterministic; the cache + manifest pin a specific observed output.
  • Scoring — score(response, reference, metric@version) is a pure function (I2); no I/O, no clock, no RNG (except seeded bootstrap downstream). Deterministic given inputs.
  • LLM-as-judge — a model used as a metric; rubric or pairwise; position-bias mitigated by swap-and-average; calibrated against human labels; judge model is versioned and pinned. Bias/variance are first-class telemetry.
  • Statistics — converts per-sample scores into an aggregate with a confidence interval (bootstrap), paired significance vs a baseline, variance decomposition (sample vs judge vs decoding noise), multiple-comparison correction across slices, and power/MDE guidance. Never emits a bare point estimate (Design Principle 6).
  • Regression + leaderboard — pins baselines, compares A/B with overlapping/paired CIs, gates CI on a significant regression (not noise), breaks down per slice, persists a leaderboard.
  • Result store — append-only persistence of predictions, transcripts, per-sample scores, and the manifest; the substrate for replay and audit.
  • Provenance + report + observability — RunManifest binds code hash ⊕ data hash ⊕ model version ⊕ config ⊕ RNG seeds ⊕ env; the REPLAY harness reconstructs an identical aggregate from the manifest + stored completions (determinism gate, §Phase 11); reports render HTML/MD/JSON; metrics cover throughput, cost, cache-hit, judge budget, flakiness.

4. System Constraints

Dimension Target
Scoring determinism score(resp, ref, metric@v) bit-identical across runs/platforms (I2)
Aggregate reproducibility identical manifest ⇒ identical aggregate ± CI (seeded bootstrap), to last digit
Run-cache hit (warm) ≤ 1 ms p95 per sample (content-hash lookup + deserialize)
Run-cache miss → backend bounded by backend latency; runner adds ≤ 2 ms overhead/sample
Scoring throughput (EM/F1, cached completions) ≥ 50 K samples/s single-core; ≥ N×/N-cores
Parallelism configurable; default = min(cpu, backend_concurrency_limit); per-backend rate cap honored
Bootstrap CI compute 10 K resamples over 10 K samples ≤ 1 s; vectorized (numpy)
Memory ceiling stream samples; never hold full dataset of completions in RAM for > config window (default 100 K)
Judge-call budget hard ceiling per run (max_judge_calls); exceeding → fail-closed before overspend
Token/cost budget hard ceiling (max_tokens, max_cost_usd); enforced pre-call, abort on breach
Startup (CLI cold) ≤ 300 ms to first sample dispatched (registry load + task bind)
Crash-resume resume from journal in ≤ 5 s for a 100 K-sample run; zero re-spend on cached samples
Exactly-once scoring each (sample, metric) scored exactly once per run; no double-count under retry/resume (I3)
Idempotent re-run re-running identical request with warm cache spends $0 on inference
Split-leakage guarantee eval reads only declared split; few-shot drawn only from train/dev; 0 eval-set exemplars (I4)
Sandbox (pass@k) per-execution CPU ≤ 10 s, mem ≤ 512 MiB, no network, no fs writes outside tmp (cross-link #50)
Position-bias residual (judge)
CI gate flakiness regression gate false-positive rate ≤ 1% under null (no real regression) via paired test + correction
Availability single host; crash = resume from journal (no lost completed work)
Recovery time objective resume ≤ 5 s; lost-cache-entry → re-call that sample only
Determinism of report identical manifest ⇒ byte-identical canonical JSON report (timestamps in a separate envelope)

Scaling assumptions: single host, 4–64 cores; backend concurrency is the real throughput ceiling (hosted API rate limits, local-runtime batch size), not CPU. Horizontal multi-node sharding deferred (process-level workers + shared cache dir first). Vertical scaling: more workers up to the backend rate cap; scoring is embarrassingly parallel over cached completions.

6. Design Principles

  1. (P1) Every reported number carries a confidence interval. No bare point estimates ever leave the system — an aggregate is (value, ci_low, ci_high, method, n). Tradeoff: a bootstrap pass per metric. Operational: dashboards show error bars; gates test significance. Violation: a 0.3% "improvement" within noise gets shipped, then reverts — the canonical eval failure.
  2. (P2) Scoring is a pure function of (response, reference, metric-version). No I/O, clock, RNG, or global state inside a metric. Operational: metrics are unit-testable + cacheable + replayable. Violation: a metric that calls a tokenizer with a process-global seed produces different scores on different machines → unreproducible numbers.
  3. (P3) The cache key includes every output-affecting input. H(task@v ⊕ model@v ⊕ rendered-prompt ⊕ decode-params ⊕ harness-version). Tradeoff: over-keying loses some cache reuse. Operational: changing a prompt template must miss the cache. Violation: under-keying serves a stale completion for a changed prompt → silently wrong scores (the worst bug class — looks fine, is wrong).
  4. (P4) Same manifest ⇒ same aggregate. Code hash ⊕ data hash ⊕ model version ⊕ config ⊕ seeds ⊕ env fully determine the headline number (given stored completions). Operational: a reviewer reproduces a paper number from the manifest. Violation: "works on my machine" benchmarks; irreproducible research.
  5. (P5) No train/test leakage; few-shot never touches the eval split. Eval reads only its declared split; exemplars drawn only from train/dev with a fixed seed; contamination index checked. Violation: exemplar = eval question → inflated score that collapses on a clean set.
  6. (P6) Determinism of the control plane; non-determinism quarantined to the backend. The runner, cache, scorer, and stats are deterministic; only the model backend may be non-deterministic, and its output is pinned in the cache + manifest. Violation: re-running gives a different number with no recorded reason.
  7. (P7) Exactly-once scoring under crashes and retries. A sample is scored once per run regardless of retries/resume, via a journal + content-addressed completions. Violation: resume double-counts → inflated n, wrong CI width.
  8. (P8) Bounded, fail-closed budgets. Token, cost, and judge-call ceilings are enforced before spending; breach aborts cleanly with partial results persisted. Violation: a runaway judge loop spends the monthly API budget overnight.
  9. (P9) Judge bias and variance are first-class, not assumed away. Position bias mitigated (swap-&-avg), verbosity/self-preference flagged, judge calibrated vs human labels, judge model versioned. Violation: a position-biased judge "proves" the candidate that happened to go first is better.
  10. (P10) Provenance is append-only and total. Predictions, transcripts, scores, and manifests are written once, never mutated; the run is fully auditable. Violation: an edited result with no audit trail; silent score laundering.
  11. (P11) Datasets and prompts are content-addressed and versioned. A dataset's hash is over its materialized split; a prompt's hash over its rendered template. Violation: "the benchmark changed under us" with no version bump — irreproducible deltas.
  12. (P12) Stratified before aggregate; distributions before means. Report per-slice metrics and score distributions, not just a global mean. Violation: a global accuracy hides a catastrophic regression on a minority slice.
  13. (P13) Regression gates test significance, not point deltas. A gate fires only on a statistically significant paired regression after multiple-comparison correction. Tradeoff: needs adequate n/power. Violation: a noisy gate flaps and gets disabled — worse than no gate.
  14. (P14) Conservative under estimator error. Sketch/sample error bounds widen CIs; a marginal judge verdict (near 0.5) is reported as uncertain, not forced to a winner. Violation: over-claiming significance from a wide-CI difference.
  15. (P15) Replayability first. Any run can be reconstructed from its manifest + stored completions without re-spending inference; the replay harness asserts identical aggregates (determinism gate). Violation: you can never reproduce last quarter's leaderboard.

8.1 Task specification (declarative, the source of truth)

                 DatasetRef Split TemplateRef FewShot MetricSet DecodeParams [Slices] [Contamination]
               "}"

8.4 Cache-key derivation (the most safety-critical function)

cache_key(sample) = SHA256( canonical_json({
   harness_version, task_name, task_version,
   model_id, model_version, decode_params,        # temperature, top_p, max_tokens, seed, stop
   rendered_prompt_hash                            # H(template@v rendered with this sample + few-shot)
}))

Every field is output-affecting (I6). Excluded by design: wall-clock, run_id, worker_id, attempt number — these must NOT change the key (else cache never hits / resume re-spends). Adding a field is a major key-schema bump (ADR-030).

8.5 LLM-as-judge protocols

RubricJudge   : prompt = (rubric, question, response) → verdict ∈ {score 1..K | pass/fail}; calibrated vs human.
PairwiseJudge : prompt = (question, A, B) → winner ∈ {A,B,tie}.
                MUST evaluate BOTH (A,B) and (B,A); verdict = mean (swap-&-avg, I9).
SelfConsistency: sample judge T times (seeded), majority/mean → reduce judge variance.

Position-bias telemetry: pos_bias = win_rate(first) − win_rate(second) over swapped pairs; residual after swap-&-avg should be ≈ 0.

8.6 Statistics: estimators & tests (selection table)

Metric / question Estimator CI method Significance test (paired)
Accuracy / EM (binary per sample) mean bootstrap or Wilson paired bootstrap / McNemar
Token-F1 / BLEU / ROUGE (continuous) mean bootstrap (BCa) paired bootstrap
pass@k (code) unbiased pass@k estimator bootstrap over problems paired bootstrap over problems
Pairwise win-rate (judge) mean of swapped verdicts bootstrap over pairs paired bootstrap / sign test
Calibration (ECE) binned acc−conf
Multi-slice / multi-metric per-slice mean bootstrap per slice + multiple-comparison correction (Holm/BH)

Power/MDE: given baseline variance σ², target effect δ, α, β → required n (closed-form for proportions; bootstrap-empirical otherwise). Reported as guidance, not a gate.

8.7 Worked example — GSM8K, 5-shot, accuracy with CI

TaskSpec gsm8k@1: dataset gsm8k@1 split test; template gsm8k_cot@2; shots 5 from train seed 1234;
  metrics [exact_match@1]; decode {temperature 0, max_tokens 512}.
Run: bind → 1319 test samples; few-shot drawn from train (seed 1234), 0 overlap with test (I4 pass).
  cache_key per sample = H(harness ⊕ gsm8k@1 ⊕ model@v ⊕ decode{t=0,...} ⊕ rendered_prompt_hash).
  Runner: 1280 cache hits (warm), 39 misses → model.generate; exactly-once scoring (I3).
  Score: exact_match per sample (pure I2); n=1319, error_n=0.
  Stats: accuracy=0.612, bootstrap 95% CI [0.586, 0.638] (10K resamples, seed 7), per-slice by digit-count.
  Manifest: code_hash, dataset_hash, template_hash, model@v, seeds {few_shot:1234, bootstrap:7}, env.
  Report: "GSM8K 5-shot EM = 61.2% [58.6, 63.8], n=1319". Never "61.2%" alone (Principle 1).

8.8 Malformed / failure-path examples

  • TaskSpec with shots ... from test → bind rejected, PlanError::FewShotFromEvalSplit (I4).
  • Prompt exceeds model context window → TaskError::TokenBudgetExceeded at bind (truncate-or-fail per config).
  • Dataset hash ≠ manifest hash on replay → ProvenanceError::ContentHashMismatch (I10); refuse run.
  • Pairwise judge called with only (A,B) ordering → JudgeError::UnswappedComparison (I9).
  • Bootstrap invoked with global RNG → StatsError::UnseededRNG (I12).
  • pass@k with n < k samples → MetricError::InsufficientSamples (I15).
  • Resume finds a journal gap (missing seq) → RunnerError::JournalGap (I13); re-dispatch missing samples only.
  • Budget breach mid-run → BudgetError::Exceeded (I5); run Aborted, partial results persisted, resumable.

12. Phase 0 — Repo Skeleton, Core Types, Registry, Task Binder, MockModel, Single-Process Runner, EM Metric, Report, CLI

12.1 Objectives

Stand up the package; define evalh.types core records + content-hash helpers; a Registry resolving (name, version); a Task binder; a deterministic MockModel; a single-process Runner (no cache/parallelism yet); the ExactMatch metric (pure, I2); a minimal report; evalh run end-to-end on MockModel. This phase establishes the deterministic spine every later phase depends on.

12.2 Detailed Implementation Steps

  • evalh.types: Sample/Prompt/Completion/Prediction/Score/MetricResult/RunManifest as frozen dataclasses; error hierarchy (EvalhError + subclasses). evalh.version: harness_version, schema + cache-key SemVer constants.
  • evalh.hashing: canonical_json(obj) (RFC 8785 ordering, UTF-8, no insignificant whitespace) + sha256_hex(bytes); content_hash(obj) = sha256(canonical_json(obj)). This is the single hashing entry point (I6/I10). (RFC 8785; ADR-006)
  • evalh.registry: in-process registry; register_task/metric/template/dataset; resolve_* by (name, version); raise on unversioned or duplicate-version registration. (ADR-030; I6)
  • evalh.config: EvalRequest, DecodeParams, BudgetSpec; validate(request) — task/model resolvable, seeds present, budgets non-negative.
  • evalh.task: Task.bind(spec, registry) → resolve dataset+split, template, metrics; leakage check stub (full in §1/§2); produce an executable Task.
  • evalh.model.mock: MockModel (maps input→fixed output via a pure function or lookup; model_version fixed) + EchoModel. Deterministic — the substrate for testing the whole pipeline without inference spend.
  • evalh.runner (single-process): iterate samples → render prompt (stub template) → model.generate → Prediction → score with each metric → collect Score[]. Exactly-once is trivial here (no retries yet) but the scored-set membership check (I3) is wired from day one. (I3; I7)
  • evalh.metric.exact_match: normalized EM (strip, lowercase, optional punctuation strip — all parameterized & versioned). Pure (I2). (Rajpurkar et al. 2016; I2)
  • evalh.report.render: text + canonical JSON of MetricResult[].
  • evalh.cli: evalh run --task <ref> --model mock:<id> --shots 0 → bind, run, aggregate (trivial mean + degenerate CI for now), print.

12.3 Deliverable

evalh run --task toy_em@1 --model mock:echo executes single-process, scores ExactMatch, prints a report with n and a placeholder CI; pytest green; mypy --strict clean; ruff clean.

12.4 Acceptance Criteria

  • ExactMatch score on a 100-sample toy task matches a hand-computed golden exactly.
  • content_hash is byte-stable across two processes / two OSes (same input → same hex) — the cornerstone test (I10).
  • Registry rejects unversioned task registration + duplicate version with typed errors.
  • Re-running the identical request yields a byte-identical canonical-JSON report (modulo timestamp envelope) — first determinism check (I1 precursor).

12.5 Conformance Fixtures

  • conformance/tasks/toy_em@1/ (samples.jsonl + expected_scores.json + expected_report.json). conformance/metrics/exact_match_golden.json (input→Score pairs incl. normalization edge cases). conformance/cache_keys/ placeholder. Malformed: tasks/unversioned_task.json → registry error.

12.6 Pitfalls

  • Non-canonical JSON hashing → hashes differ across dict-ordering / float repr / platforms → cache misses + manifest mismatch everywhere. Root: using json.dumps defaults. Debug: hash same object twice with shuffled keys. Recover: route all hashing through canonical_json (RFC 8785), never raw json.
  • Mutable dataclasses → a sample mutated after hashing → hash no longer matches stored. Root: non-frozen records. Debug: hash-after-use mismatch. Recover: frozen=True everywhere; copy-on-derive.
  • EM normalization hidden in the metric, unversioned → silently changing strip/lowercase changes scores with no version bump. Root: normalization not part of metric_version. Debug: score drift with no code-diff trace. Recover: normalization params are part of the metric version (I2/ADR-030).
  • Float in cache-key/manifest serialized lossily → 0.1 round-trips differently. Root: float repr. Debug: key instability on decode params. Recover: canonicalize floats (shortest round-trip repr) or store as exact decimals/strings.

12.7 Performance Concerns

Hashing is the only hot op here; canonical_json over small records is cheap but called per sample → memoize template/decode-param hashes (constant per run); stream samples (generator) rather than materializing the whole dataset.

12.8 Edge Cases

Empty dataset (n=0 → MetricResult with n=0, undefined CI flagged); single sample (CI degenerate, flagged n_too_small); reference is a list (EM against any-of); unicode normalization in EM (NFC); all-correct / all-wrong (CI at boundary).

12.9 Failure Analysis

Unversioned/duplicate registration → typed registry error pre-run (blast radius: that run). Mock model returns wrong shape → RunnerError before scoring. No persistence yet → a crash loses the run (documented limit until §5 journal).

12.10 Operational Notes

structlog JSON logs with run_id; counters samples_scored, metric_errors. Report is the operator's first window; canonical JSON is the contract every later phase diffs against. No metrics endpoint yet (Phase 12).

13. Phase 1 — Dataset Loaders + Content-Hash + Split Discipline + Leakage/Contamination Check

13.1 Objectives

Make datasets first-class, content-addressed, and split-disciplined. Implement JSONL + HF-adapter loaders; compute a content-hash over the materialized split (post-filter, post-seeded-shuffle); enforce that eval reads only its declared split and that few-shot exemplars are drawn only from train/dev; implement the contamination/leakage index (I4) and canary check.

13.2 Detailed Implementation Steps

  • evalh.dataset.jsonl: stream Samples from JSONL; schema-validate (id/input/reference/split); stable ordering (by id) before hashing. (ADR-005; I10)
  • evalh.dataset.hf_adapter: optional adapter mapping HF datasets rows → Sample (pinned dataset revision recorded).
  • evalh.dataset.splits: enforce Split ∈ {train,dev,test}; a Dataset.load(split) returns only that split; the eval split is frozen (read-only).
  • content_hash(split): canonical-JSON of the sorted materialized split → SHA-256; recorded in the manifest (I10). Filtering/shuffle (if any) is seeded and part of the hash input. (RFC 8785; ADR-006; ADR-007)
  • evalh.dataset.contamination: build an index of eval-set normalized n-gram fingerprints + declared canary strings; expose check_overlap(train_pool, eval_set) (few-shot pool must not intersect eval IDs or share canaries) — the I4 gate, invoked by the task binder. (Sainz et al. 2023; I4)
  • evalh.task: wire the leakage check into bind; shots ... from test → PlanError::FewShotFromEvalSplit. (I4; ADR-029)

13.3 Deliverable

A real task (e.g., a small QA set) loads from JSONL with a stable content-hash; the binder draws few-shot only from train, runs the leakage check, and rejects a deliberately contaminated config. EXPLAIN-style report shows dataset_hash, split, few_shot_source.

13.4 Acceptance Criteria

  • content_hash stable across runs/processes; changes iff the materialized split bytes change (mutation test).
  • Leakage check flags a planted overlap (an eval question inserted into the few-shot pool) → bind rejected (I4).
  • Canary string present in eval data → contamination flagged.
  • Few-shot selection is deterministic (same seed → same exemplar IDs) and never includes a test-split ID.

13.5 Conformance Fixtures

  • conformance/tasks/qa_small@1/ (train.jsonl, dev.jsonl, test.jsonl + expected dataset_hash). conformance/contamination/leakage_positive/ (planted overlap), contamination/clean/ (no overlap), contamination/canary/ (planted canary). Malformed: dataset/bad_schema.jsonl (missing reference) → loader error.

13.6 Pitfalls

  • Shuffle without a seed before hashing → non-stable dataset_hash → cache + manifest churn. Root: unseeded shuffle. Debug: two loads → two hashes. Recover: seeded, deterministic ordering; hash the post-order bytes.
  • Few-shot drawn from the eval split (the canonical leakage bug) → inflated, irreproducible scores. Root: pool = full dataset. Debug: exemplar IDs ∩ eval IDs ≠ ∅. Recover: pool restricted to train/dev; I4 assert.
  • Near-duplicate contamination missed (paraphrased eval item in train) → leakage slips through exact-match index. Root: exact-string index only. Debug: high score that collapses on a held-out clean set. Recover: n-gram / fuzzy fingerprint index; document residual risk.
  • HF dataset revision unpinned → "the dataset changed under us". Root: floating dataset version. Debug: dataset_hash changed with no code change. Recover: pin HF revision; record it in the manifest.

13.7 Performance Concerns

Hashing streams the split once (no double materialization); contamination index built once per task (n-gram hashing O(tokens)); cache the index keyed by dataset_hash. Stream samples; never hold the whole corpus if it exceeds the window.

13.8 Edge Cases

Dataset with no train split (few-shot impossible → 0-shot only, or error if shots>0); duplicate sample IDs (reject); empty split; reference absent (generation-only task — metric must handle); canary substring vs whole-token match (define matching granularity).

13.9 Failure Analysis

Leakage detected → bind aborts (blast radius: that run; prevents a poisoned number). Bad-schema row → loader error pre-run. Dataset hash mismatch on replay (§11) → ProvenanceError::ContentHashMismatch.

13.10 Operational Notes

14. Phase 2 — Prompt / Template Management: Versioned Templates, Few-Shot, Chat/Completion Formatting, Token-Budget Enforcement

14.1 Objectives

Make the prompt — the single biggest source of irreproducible eval deltas — versioned, hashed, and budget-checked. Implement the versioned template engine (chat + completion formats), deterministic few-shot assembly, role construction (system/user/assistant), and tokenization-budget enforcement against the model's context window.

14.2 Detailed Implementation Steps

  • evalh.prompt.template: a PromptTemplate with a version and a render(sample, few_shot, style) → Prompt; the rendered string/messages are content-hashed (template_hash, feeds cache key I6). Templates are data (files in templates/), versioned; editing a template requires a version bump (lint check). (ADR-030; I6; I10)
  • Chat vs completion: PromptStyle ∈ {Chat, Completion}; chat → ChatMessages (role-tagged); completion → a single string. Same logical template renders both deterministically. (Zheng et al. 2023; I2)
  • evalh.prompt.fewshot: select_few_shot(pool, k, seed) — deterministic (seeded permutation over train/dev pool); stable exemplar IDs recorded in Prompt.few_shot_ids; never test (I4, re-asserted). (I4; ADR-034)
  • evalh.prompt.budget: count tokens with a pinned tokenizer (ADR-014) for the target model; if tokens(prompt) + max_tokens > context_window → PlanError::TokenBudgetExceeded (or truncate per config, with truncation recorded). (ADR-014; I6)
  • Render is pure + deterministic; template_hash is the cornerstone of cache correctness.

14.3 Deliverable

A versioned CoT template renders a GSM8K-style 5-shot prompt deterministically in both chat and completion form; template_hash stable; over-long prompts rejected/truncated with a recorded decision. Report shows template@version, template_hash, few_shot_ids.

14.4 Acceptance Criteria

  • Same (template@v, sample, few-shot seed) → byte-identical rendered prompt + identical template_hash across processes.
  • Editing the template body without a version bump → CI lint failure (template_unversioned_edit).
  • Token-budget enforcement: a prompt exceeding the window is detected pre-call (no wasted inference).
  • Chat and completion renders are both deterministic and self-consistent (same exemplars, same order).

14.5 Conformance Fixtures

  • templates/gsm8k_cot@2.txt + conformance/tasks/gsm8k_cot_render/ (sample + few-shot → golden rendered prompt, chat + completion). conformance/prompt/over_budget.json (→ TokenBudgetExceeded). Edge: prompt/empty_fewshot.json (0-shot).

14.6 Pitfalls

  • Template edited without version bump → cache serves completions for the old prompt → silently wrong scores. Root: no version discipline. Debug: scores moved with no model change; template_hash differs from manifest. Recover: version-bump lint + template_hash in cache key (I6).
  • Few-shot order non-deterministic → prompt varies run-to-run → cache misses + irreproducible numbers. Root: unseeded selection / set iteration. Debug: few_shot_ids differ across runs. Recover: seeded permutation; record IDs.
  • Tokenizer mismatch (budget counted with tokenizer A, model uses B) → off-by context, truncation surprises. Root: unpinned tokenizer. Debug: budget passes but API rejects length. Recover: pin the model's tokenizer @version (ADR-014).
  • Chat-role leakage (putting the answer in a system message; instruction in the wrong role) → format artifacts dominate the score. Root: sloppy role assembly. Debug: score swings with role layout. Recover: explicit, tested role construction; ablate format in conformance.

14.7 Performance Concerns

Render once per sample; memoize the few-shot block (constant within a run) and its hash; tokenization is O(prompt length) — batch-tokenize; cache template_hash (constant per template version).

14.8 Edge Cases

0-shot (empty exemplar block, still deterministic); k larger than the pool (error or cap, recorded); prompt exactly at the context boundary; multi-turn template (assistant turns interleaved); non-ASCII in template (NFC + tokenizer agreement).

14.9 Failure Analysis

Over-budget prompt → rejected/truncated pre-call (blast radius: that sample; no inference waste). Template hash mismatch on replay → ProvenanceError. Wrong role layout → caught by format-ablation conformance (artifact, not crash).

14.10 Operational Notes

Metrics: prompt_tokens_p99, budget_rejections, truncations. Report + manifest carry template@version + template_hash + few_shot_ids (full prompt reproducibility). Runbook note: "number moved, no model change → diff template_hash first".

  • evalh.model.openai_api / anthropic_api: map Prompt (chat/completion) + DecodeParams to the provider request; parse completions (+ logprobs if available); record tokens_in/out and finish_reason. Honor provider seed param where present. (ADR-012; I8)
  • evalh.model.local_runtime: adapter to the #330 streaming runtime (submit prompt + decode params, collect streamed tokens into a Completion); deterministic when run with temperature=0 + fixed seed + pinned weights/version.
  • evalh.model.decoding: normalize deterministic controls — temperature=0 ⇒ greedy; record seed; for backends without a seed, mark the completion nondeterministic=true (the manifest records this; replay then relies on the stored completion, not regeneration). (ADR-034; I6)
  • evalh.model.ratelimit: token-bucket per backend (RPM/TPM); bounded async queue; backpressure when the bucket is empty (I5). Retries with exponential backoff + jitter on 429/5xx/timeouts; timeout per request; max-retries → Completion with finish_reason="error" (counted in error_n, I11). (I5; ADR-011)
  • Batching: group prompts up to a backend batch limit; preserve sample↔completion mapping. (I3; ADR-010)

15.3 Deliverable

A task runs against a real API backend and against the #330 local runtime; rate limits respected (no 429 storms); transient failures retried; deterministic backends produce identical completions on re-run (temperature=0 + seed). Report shows model@version, tokens, cost, and per-backend determinism status.

15.4 Acceptance Criteria

  • Mock + #330 (temperature=0, fixed seed) → byte-identical completions across two runs (determinism where supported).
  • Rate-limit handling: a burst of N requests against an R-RPM cap never exceeds the cap (measured); no 429-induced data loss.
  • Retry path: injected transient 500s recovered without losing samples; permanent failures land in error_n (I11), not silently dropped.
  • Cost/token accounting matches a hand-computed expectation on a fixed fixture.

15.5 Conformance Fixtures

  • conformance/tasks/api_smoke/ (mock-API server transcript → expected completions). conformance/model/ratelimit_burst.json (N requests, R cap → no breach). conformance/model/retry_transient.json (injected 500s → recovered). conformance/model/determinism_temp0.json (two runs → identical).

15.6 Pitfalls

  • Assuming temperature=0 ⇒ determinism on a hosted API — many APIs are not bit-deterministic even at t=0 (batching/hardware nondeterminism). Root: false determinism assumption. Debug: two t=0 runs differ. Recover: pin the observed completion in the cache + manifest (Principle 6); mark backend nondeterministic; replay uses stored output, never regeneration.
  • Retry without idempotency key → double-charged / duplicate completions. Root: re-issuing a non-idempotent request. Debug: tokens_out double-counted. Recover: dedupe by cache_key; idempotent put (I3/I7).
  • Unbounded asyncio.gather → ignores rate limits → 429 storm + bans. Root: no concurrency cap. Debug: 429 spike, backend errors. Recover: bounded queue + token-bucket (I5).
  • Streaming reassembly bug (#330 backend) → truncated/concatenated completions. Root: mishandling stream end / partial chunks. Debug: completion length vs token count mismatch. Recover: explicit stream-finish handshake; verify finish_reason.
  • Rate-limit retry hides a real outage → run "completes" mostly as errors. Root: errors counted as samples. Debug: error_n high but n reported full. Recover: I11 — n = successfully scored only; surface error_n.

15.7 Performance Concerns

Throughput is backend-bound; saturate up to the rate cap, not the CPU. Batch requests to amortize HTTP overhead. Async I/O (no thread-per-request). Backoff with jitter to avoid synchronized retry storms. Keep the async queue depth ≈ a few × concurrency to stay saturated without unbounded memory.

15.8 Edge Cases

Backend with no seed param (mark nondeterministic); empty completion (finish_reason="stop" with 0 tokens); max_tokens hit (finish_reason="length"); content filter / refusal (recorded, not retried as transient); 429 with Retry-After header (honor it); partial batch failure (per-prompt error isolation).

15.9 Failure Analysis

Sustained backend outage → bounded retries → samples land in error_n; run can Abort (partial persisted) or continue with a documented error rate. Cost overrun → budget guard (I5) aborts before overspend. Streaming corruption → finish-reason validation catches it (blast radius: affected samples).

15.10 Operational Notes

Metrics: backend_latency_p50/p95/p99, rate_limit_waits, retries{code}, tokens_in/out, cost_usd, error_rate{backend}, nondeterministic_backend. Tracing span per model call. Runbook: docs/runbooks/budget-breach.md. Each backend's determinism status is recorded in the manifest (drives replay strategy in §11).

16. Phase 4 — Multi-Turn / Agent Rollout Adapter (minimal), Prediction Parsing, Answer Extraction

16.1 Objectives

Bridge from raw completions to scorable predictions, and support the minimal multi-turn rollout an agent task needs. Implement answer-extraction/parsers (the task-specific bridge from free-text to a typed answer), and a bounded multi-turn adapter (model ↔ environment turns) sufficient for tool-use/agent tasks — without building a full agent framework.

16.2 Detailed Implementation Steps

  • evalh.task parsing hook: a Parser per task (parse(completion) -> parsed) — regex/JSON/structured extraction of the final answer (e.g., "#### <number>" for GSM8K, last boxed expr, JSON field). Parsers are pure + versioned (part of the task version). (Rajpurkar et al. 2016; ADR-030)
  • Multi-turn adapter (evalh.runner extension): a bounded loop — model.generate → environment step (deterministic stub or pluggable) → next prompt, up to max_turns; the full transcript is persisted; the final state is scored. Determinism: the environment must be deterministic or its randomness seeded (else mark nondeterministic). (I5; ADR-013; I13)
  • Parse-failure handling: unparseable completion → parsed = None → metric treats as wrong (or task-specific); recorded as a parse_failure (distinct from a model error). (I11; ADR-029)
  • Transcript record: ordered turns (prompt, completion, env-observation) appended to the result store (I7) for audit/replay. (I7; I8)

16.3 Deliverable

A QA task extracts the final numeric/string answer from CoT output and scores it; a minimal 2–3 turn tool-use task runs a bounded rollout against a deterministic environment stub and scores the final outcome. Transcripts persisted.

16.4 Acceptance Criteria

  • Answer extraction matches a golden on a CoT fixture (incl. tricky cases: multiple numbers, negative, formatted).
  • Parse failures are counted separately and do not crash the run; score = wrong (or per-task policy).
  • Multi-turn rollout is deterministic given a seeded environment; transcript is complete and ordered.
  • max_turns enforced (no infinite loops); budget (I5) counts every turn's tokens.

16.5 Conformance Fixtures

  • conformance/tasks/gsm8k_parse/ (CoT completions → expected extracted answers, incl. malformed). conformance/tasks/tooluse_2turn/ (deterministic env → expected final score + transcript). Edge: parse/unparseable.json (→ parse_failure, not crash).

16.6 Pitfalls

  • Greedy regex extraction grabs the wrong number (e.g., a step's intermediate value, not the final answer). Root: under-specified parser. Debug: extracted ≠ expected on multi-number CoT. Recover: anchor on the answer marker ("####", "the answer is", boxed); version the parser.
  • Parse failure counted as a model error → wrong error_n/n bookkeeping. Root: conflating parse vs backend failure. Debug: error breakdown. Recover: distinct parse_failure category (I11).
  • Unbounded multi-turn loop → runaway cost. Root: no max_turns. Debug: cost/turn spike. Recover: hard turn cap + budget guard (I5).
  • Non-deterministic environment in a rollout → irreproducible agent score. Root: env uses wall-clock/RNG. Debug: replay divergence. Recover: seed the env; if external/nondeterministic, mark the run nondeterministic and rely on stored transcript (Principle 6).

16.7 Performance Concerns

Multi-turn serializes model calls (turn t depends on t−1) → less parallelism within a sample, but samples still parallelize across the dataset. Parsing is cheap (regex/JSON) but runs per sample → keep patterns compiled. Persist transcripts in batches to amortize I/O.

16.8 Edge Cases

Completion with no extractable answer (parse_failure); multiple valid answer forms (normalize); environment returns terminal early (short rollout); turn limit hit before resolution (scored as incomplete); tool call with malformed args (env error, recorded).

16.9 Failure Analysis

Parser bug → systematic score error: caught by parser conformance goldens + differential against a reference extraction. Runaway rollout → budget guard aborts. Env nondeterminism → replay gate flags divergence (§11). Blast radius: per-task.

16.10 Operational Notes

Metrics: parse_failures, turns_per_sample_p99, rollout_incomplete. Transcripts in the result store are the agent-task audit trail. Parser version is part of the task version (manifest). Multi-turn determinism status recorded.

17. Phase 5 — Runner Core: Async Execution, Sharding, Content-Addressed Run-Cache, Exactly-Once Journal, Resume

17.1 Objectives

Turn the single-process runner (Phase 0) into the production execution engine: async I/O dispatch to model backends, CPU scoring on a process pool, sharding across workers, a content-addressed run-cache (I6), an append-only journal for exactly-once + resumable runs (I3, I13). Constraint introduced: every spent inference call is cached and journaled before it is scored.

17.2 Detailed Implementation Steps

  • evalh.runner.executor — asyncio dispatch of Model.generate (ADR-010); bounded async queue (ADR-011) sized to backend rate cap; multiprocessing pool for pure scoring + sandbox (CPU/isolation-bound). (ADR-010; ADR-011)
  • evalh.runner.shard — deterministic sample→shard map shard(sample_id)=H(id)%N; shards are independent units; no cross-shard ordering dependence.
  • evalh.cache.key — derive cache_key per §8.4 (output-affecting inputs only, I6); evalh.cache.store — sharded content-addressed dir + sqlite index (ADR-008); get/put idempotent; warm-hit returns stored Completion without spending. (I6; ADR-006; ADR-030)
  • evalh.runner.journal — append-only (seq, sample_id, cache_key, state) log; monotone seq (I13); state ∈ {dispatched, completed, scored}; fsync on batch boundary. (I3; I13; I7)
  • evalh.runner.budget — running token/cost/judge-call counters checked before dispatch; breach → fail-closed, persist partial, Aborted (I5). (I5; ADR-011)
  • Resume path: on restart, replay journal → set of scored samples; re-dispatch only the gap (I13); never re-score a completed+scored sample (I3).

17.3 Deliverable

evalh run <taskspec> --model <backend> --workers N executes a full task with caching + journaling; killing and restarting mid-run resumes with zero double-scoring and zero re-spend on cached completions.

17.4 Acceptance Criteria

  • Warm re-run of a completed task: 100% cache hits, 0 model calls, identical aggregate.
  • Kill at 50% → resume → final n equals cold-run n (no double count); journal has no gaps.
  • Throughput ≥ 500 scored samples/s for a MockModel (scoring-bound) on 8 workers.
  • Budget ceiling honored: a run capped at K calls makes ≤ K calls then aborts cleanly.

17.5 Conformance Fixtures

  • conformance/replay/warm_rerun.json — cold then warm; assert hit-rate=1.0, equal aggregate.
  • conformance/tasks/resume_midrun.json — kill/resume; assert n + journal continuity.
  • conformance/cache_keys/key_coverage.json — mutate each output-affecting field → key changes; mutate run_id/worker_id → key stable (I6).
  • conformance/tasks/budget_abort.json — call ceiling → BudgetError::Exceeded, partial persisted.

17.6 Pitfalls

  • Cache key under-keying → stale completion served for a changed prompt (Principle 3); manifests as "scores didn't move when I changed the template". Detect via key-coverage test; debug by recomputing key field-by-field.
  • Resume double-count → inflated n, narrowed CI; root cause: scoring before journaling. Fix: journal completed before scored; idempotent score keyed by (sample,metric).
  • Async queue unbounded → memory blow-up under a slow backend; root cause: asyncio.gather over all samples. Fix: bounded queue + worker pool (ADR-011).
  • Process-pool nondeterminism → scores depend on worker count; root: shared mutable state. Fix: pure metrics (I2), no globals.

17.7 Performance Concerns

Cache lookup is the hot path → sqlite index on cache_key, sharded dirs to bound inode count. Batch journal fsync (amortize syscalls). Pickling overhead to process pool → send (response, reference, metric_id) not heavy objects. Backend RTT dominates wall-time → concurrency = rate-cap, not core count.

17.8 Edge Cases

Duplicate samples (same id) → scored once; backend returns truncated completion (finish_reason=length) → recorded, scored as-is; cache corruption (hash mismatch on read) → treat as miss, re-spend, log; clock change mid-run → no effect (logical seq only, I13); worker crash → its shard's un-journaled samples re-dispatched.

17.9 Failure Analysis

Cache store FS full → put fails → fail-closed, persist journal, Aborted resumable. Blast radius: one run. sqlite index corruption → rebuild from content-addressed dir (dir is source of truth). Journal loss → conservative: re-dispatch all unscored; cached completions prevent re-spend. Postmortem: journal + cache index reconstruct the exact execution.

17.10 Operational Notes

Metrics: cache_hit_rate, samples_scored_per_s, journal_seq, budget_spent/remaining, inflight_requests. Runbook cache-miss-storm.md (cold cache after key bump → expected; budget-protect). Cache GC (evalh.cache.gc) never evicts a live run's keys. Resume is the default restart behavior.

18. Phase 6 — Core Metrics: EM, Token-F1, Accuracy, BLEU, ROUGE, METEOR, Perplexity/Log-Likelihood, Calibration; Plugin Contract + Differential Oracle

18.1 Objectives

Implement the lexical/probabilistic metric suite as pure functions (I2) behind the Metric plugin contract, each validated against a reference library (differential oracle, ADR-022). Constraint: a metric never does I/O, never reads a clock/RNG, and is byte-stable across platforms.

18.2 Detailed Implementation Steps

  • evalh.metric protocol — score(response, reference, params) -> Score; version field; registered by (name, version) (I2, ADR-030). (I2; ADR-030)
  • exact_match (normalization: lowercase, strip punctuation/articles, whitespace-collapse — SQuAD-style); f1 (token-F1 / span-F1); accuracy (label match).
  • bleu (sacrebleu-compatible, pinned tokenizer, ADR-014); rouge (ROUGE-N/L, LCS); meteor (alignment + stem/synonym). (Papineni et al. 2002; Lin 2004; Banerjee & Lavie 2005; ADR-014)
  • perplexity / log-likelihood — requires logprobs from the backend; guard: metric errors if logprobs absent. (I2; ADR-030)
  • calibration — ECE (binned |acc − conf|); needs confidence/logprob.
  • Normalization registry — shared, versioned text normalizers (changing one bumps the dependent metric version). (ADR-030; I2; Rajpurkar et al. 2016)

18.3 Deliverable

evalh run scores any task with the full lexical suite; evalh metric verify runs each metric against its reference-library golden and reports max abs diff.

18.4 Acceptance Criteria

  • BLEU/ROUGE within 1e-6 of sacrebleu/rouge-score on the differential corpus (ADR-022).
  • All metrics pass a Hypothesis property test: score(x)==score(x) across processes/platforms (I2).
  • EM/F1 match SQuAD reference on its dev fixtures.
  • Metric throughput ≥ 50k scores/s (EM/F1) single-core.

18.5 Conformance Fixtures

  • conformance/metrics/{em,f1,bleu,rouge,meteor,ppl,ece}_golden.json — input→expected (vs reference lib).
  • conformance/metrics/normalization_cases.json — Unicode, articles, numbers, casing.
  • conformance/metrics/purity_property.json — determinism across runs.

18.6 Pitfalls

  • Tokenizer drift → BLEU/ROUGE numbers shift silently when a dep updates; root: unpinned tokenizer. Fix: pin version (ADR-014); version is part of metric version.
  • Normalization mismatch → our EM ≠ published EM; debug via per-step normalization trace against reference.
  • Locale-dependent casing (Turkish-i) → nondeterministic lowercase; fix: locale-independent normalization (I2).
  • NaN from empty references → divide-by-zero in F1; fix: defined edge semantics (empty ref → score 0/1 by spec).

18.7 Performance Concerns

Compile regex/normalizers once (module load). BLEU n-gram counting is the cost → vectorize with Counter; avoid per-call tokenizer construction. ROUGE-L LCS is O(mn) → cap reference length or use rolling DP. Run scoring in the process pool (ADR-010) to use all cores.

18.8 Edge Cases

Empty response (parse_failure upstream) → score 0 by spec; multi-reference (max over refs for EM/F1, corpus-BLEU semantics); extremely long generation (truncate per metric spec, record); non-ASCII/emoji (NFC-normalize, never crash); ties in multi-ref.

18.9 Failure Analysis

A metric bug is the most dangerous failure (silently wrong numbers, looks fine). Detection: differential oracle in CI (ADR-022) + property tests. Blast radius: every score using that metric@version. Recovery: bump metric version, re-score from cached completions (no re-spend). Postmortem: golden diff pinpoints the regression.

18.10 Operational Notes

Metrics: metric_eval_per_s, metric_nondeterminism (should be 0). Changing any normalizer/tokenizer is a metric-version bump (CHANGELOG + cache invalidation; see Compatibility & Versioning). docs/stats-guide.md cross-references which metric suits which task.

19. Phase 7 — Code-Execution Metrics: pass@k via #50 Sandbox, Unbiased Estimator

19.1 Objectives

Score code-generation tasks by executing candidate programs against unit tests inside the isolated #50 sandbox (ADR-013), and aggregate with the unbiased pass@k estimator (I15). Constraint: untrusted model-generated code never runs in-process; always sandboxed, resource-capped, no network.

19.2 Detailed Implementation Steps

  • evalh.sandbox.runner — delegates to #50: subprocess + seccomp/nsjail/container; CPU/mem/time caps; no network; per-candidate clean workdir. (ADR-013; I5)
  • evalh.metric.passk — sample n ≥ k completions per problem; execute each against the test suite; count c passes; pass@k = 1 − C(n−c, k)/C(n, k) (I15). (Chen et al. 2021; I15)
  • Test harness fixtures per problem (HumanEval/MBPP-style): prompt, canonical tests, entry point; timeout per test. (Chen et al. 2021; ADR-021)
  • Result recording: per-candidate pass/fail/error/timeout; stored append-only with stderr (truncated) for debugging. (I7; I3)

19.3 Deliverable

evalh run humaneval@1 --model <backend> --n 20 --k 1,10 produces pass@1 and pass@10 with CIs (Phase 9), executing all candidates in the sandbox.

19.4 Acceptance Criteria

  • pass@k matches the unbiased combinatorial formula on synthetic (n,c) fixtures exactly (I15).
  • Sandbox blocks network + filesystem escape + fork bombs (security fixtures pass).
  • n < k → MetricError::InsufficientSamples (I15), never a wrong number.
  • No sandbox leak: all subprocesses reaped; FD/temp dirs cleaned.

19.5 Conformance Fixtures

  • conformance/metrics/passk_formula.json — (n,c,k)→expected estimator value.
  • conformance/metrics/sandbox_security.json — malicious snippets (network, file write, infinite loop) → contained.
  • conformance/tasks/humaneval_mock.json — deterministic MockModel solutions → known pass@k.

19.6 Pitfalls

  • Flaky tests (timing/random in problem tests) → nondeterministic pass; fix: seed + generous timeout; flag flaky problems.
  • Resource exhaustion by a candidate → starves the run; fix: hard cpu/mem/wall caps per candidate (ADR-013).
  • Estimator misuse with n<k or n varying per problem → biased; fix: enforce n≥k, aggregate per-problem then over problems (I15).
  • Zombie processes → FD leak; fix: process-group kill + reap.

19.7 Performance Concerns

Sandbox spawn cost dominates → pool warm sandboxes; batch candidates per problem. Cap concurrency by CPU (execution is CPU-bound, not I/O). Truncate captured stdout/stderr to bound memory.

19.8 Edge Cases

Candidate that imports forbidden modules (blocked); test that reads stdin (closed); non-terminating program (wall-cap kill → fail); compile/syntax error (error, not pass); partial test pass (counts as fail unless task spec says otherwise).

19.9 Failure Analysis

Sandbox misconfiguration → either false security (escape) or false negatives (everything fails). Detection: security fixtures + a known-good solution must pass. Blast radius: all code tasks. Recovery: pin sandbox image/version (reproducible, ADR-034). Postmortem: per-candidate stderr + exit code.

19.10 Operational Notes

Metrics: sandbox_exec_per_s, sandbox_timeouts, sandbox_kills, passk_n_per_problem. Runbook: sandbox image rotation. Security: SECURITY.md documents the isolation contract; sandbox version pinned in the manifest (I8).

20. Phase 8 — LLM-as-Judge: Rubric + Pairwise + Swap-&-Avg + Self-Consistency + Calibration + Bias Telemetry

20.1 Objectives

Make model-graded evaluation trustworthy: rubric and pairwise judges with position-bias removal (swap-&-avg, I9), self-consistency, calibration against human labels, and first-class bias telemetry (Principle 9). Constraint: a pairwise verdict is invalid unless both orderings were evaluated.

20.2 Detailed Implementation Steps

  • evalh.judge.rubric — (rubric, question, response) → score∈1..K | pass/fail; judge model + version recorded as scorer_fp. (Zheng et al. 2023; I9)
  • evalh.judge.pairwise — evaluate (A,B) and (B,A); verdict = mean; enforce both-orderings present (I9). (Zheng et al. 2023; I9; ADR-016)
  • evalh.judge.consistency — sample judge T times (seeded, ADR-015); majority/mean to cut variance. (Wang et al. 2022; I12)
  • evalh.judge.bias — telemetry: pos_bias = win_rate(first) − win_rate(second); verbosity-bias (length vs win), self-preference (judge favors its own family).
  • evalh.judge.calibration — judge-vs-human agreement (Cohen's κ, accuracy) on a labeled calibration set; report before trusting a judge. (Zheng et al. 2023; ADR-022)
  • Judge is a Metric whose output feeds winrate (Phase 6) and stats (Phase 9).

20.3 Deliverable

evalh run mt-bench@1 --judge <model> produces swap-corrected pairwise win-rates with position-bias telemetry and a judge-calibration report.

20.4 Acceptance Criteria

  • Every pairwise call has both orderings (I9); unswapped_judge_call = 0.
  • Residual position bias after swap-&-avg ≈ 0 on the bias fixture.
  • Self-consistency reduces verdict variance vs single-sample on the fixture.
  • Calibration report emits κ + accuracy vs human labels; refuses to headline a judge below a configured κ floor.

20.5 Conformance Fixtures

  • conformance/judge/swap_avg.json — biased single-order vs swap-corrected.
  • conformance/judge/calibration_humanset.json — judge vs human labels → κ.
  • conformance/judge/self_consistency.json — variance reduction with T.
  • conformance/judge/position_bias.json — synthetic first-position-favoring judge → detected.

20.6 Pitfalls

  • Position bias → "A always wins because it's first"; fix: swap-&-avg (I9); telemetry residual ≈ 0.
  • Verbosity bias → judge rewards length; detect via length-vs-win correlation; report, optionally length-normalize.
  • Self-preference → judge favors its own model family; mitigate: cross-family judge, disclose scorer_fp.
  • Judge drift → silent provider model update changes verdicts; fix: pin judge version (I8); recalibrate on bump.

20.7 Performance Concerns

Judges double cost (two orderings × T samples). Cache judge calls by (judge@v, rendered-judge-prompt) (I6) — re-runs are free. Budget judge calls explicitly (I5). Batch pairwise comparisons.

20.8 Edge Cases

Judge returns unparseable verdict → parse-retry then JudgeError::Unparseable, sample excluded (counted in error_n, I11); tie verdicts; judge refuses (safety) → recorded as abstain; A==B identical responses (expect ~tie, a sanity check).

20.9 Failure Analysis

An uncalibrated/biased judge produces confident-but-wrong rankings — the most insidious eval failure. Detection: mandatory calibration + bias telemetry. Blast radius: every judge-scored leaderboard entry. Recovery: re-judge from cached completions with a calibrated judge. Postmortem: per-pair order audit + scorer_fp.

20.10 Operational Notes

Metrics: pos_bias, judge_kappa, judge_calls, judge_unparseable, verdict_variance. Runbook judge-bias.md. Judge model + version is in the manifest (I8); a judge change is a headline-affecting event (CHANGELOG).

21. Phase 9 — Statistics: Bootstrap CI (+BCa), Paired Significance, Multiple-Comparison Correction, Power/MDE, Variance Decomposition

21.1 Objectives

Guarantee Principle 1 (no bare point estimates) and Principle 13 (gates test significance): seeded bootstrap CIs, paired significance tests, multiple-comparison correction, power/MDE guidance, and variance decomposition. Constraint: every aggregate is (value, ci_low, ci_high, method, n) computed with a seeded RNG (I12).

21.2 Detailed Implementation Steps

  • evalh.stats.bootstrap — seeded numpy Generator resampling (ADR-015); percentile + BCa for skewed metrics; configurable resamples (default 10k). (Efron & Tibshirani 1993; I12)
  • evalh.stats.significance — paired bootstrap (same samples), McNemar (binary paired), paired t-test (continuous, with normality caveat) — ADR-016. (Dror et al. 2018; Koehn 2004; ADR-016)
  • evalh.stats.correction — Holm-Bonferroni (default), Benjamini-Hochberg FDR option (ADR-017) across slices/metrics. (Dror et al. 2018; ADR-017; I14)
  • evalh.stats.power — MDE / required-n (closed-form for proportions; bootstrap-empirical otherwise); reported as guidance, not a gate. (Card et al. EMNLP 2020; Wasserman 2004)
  • evalh.stats.variance — decompose variance into sample / judge / decode components.
  • aggregate(scores) -> MetricResult (§8.2) with per-slice breakdown (Principle 12).

21.3 Deliverable

Every reported metric carries a CI; evalh compare A B reports paired deltas with significance + correction; evalh power gives required-n for a target effect.

21.4 Acceptance Criteria

  • Bootstrap CI reproducible bit-for-bit given a fixed seed (I12); unseeded_bootstrap = 0.
  • CI coverage validated on synthetic data with known parameters (≈95% coverage at 95% CI).
  • Paired test recovers known significant/non-significant differences on fixtures.
  • Correction reduces false-positive rate across many slices on a null fixture.

21.5 Conformance Fixtures

  • conformance/stats/bootstrap_coverage.json — known dist → CI coverage ≈ nominal.
  • conformance/stats/paired_known.json — designed significant + null pairs.
  • conformance/stats/correction_null.json — many null slices → FWER/FDR controlled.
  • conformance/stats/seed_repro.json — same seed → identical CI.

21.6 Pitfalls

  • Unpaired test on paired data → loses power / wrong p; fix: paired bootstrap/McNemar (ADR-016).
  • No multiple-comparison correction → some slice "significant" by chance; fix: Holm/BH (I14, ADR-017).
  • Global RNG → irreproducible CIs; fix: explicit seeded Generator (I12).
  • Tiny-n over-claim → wide CI reported as a win; fix: power/MDE guidance + Principle 14 conservatism.

21.7 Performance Concerns

10k-resample bootstrap × many slices/metrics is the stats hot path → vectorize with numpy (resample index matrix); cache bootstrap distributions per metric; parallelize across metrics. BCa adds jackknife cost — use only for skewed metrics.

21.8 Edge Cases

n=0 or all-error (undefined aggregate → report n=0, no CI); constant scores (zero-variance CI = point); heavy-tailed metric (BCa); extreme class imbalance (Wilson for proportions); single-sample (no CI, flagged).

21.9 Failure Analysis

A statistics bug yields confidently-wrong CIs → false ship/revert decisions. Detection: coverage tests + differential vs scipy (ADR-016). Blast radius: every gate/leaderboard decision. Recovery: recompute from stored scores (no re-spend). Postmortem: seeded re-run reproduces the exact CI.

21.10 Operational Notes

Metrics: bootstrap_resamples, ci_width, significant_slices. docs/stats-guide.md is the operator reference (which test/CI/correction when). All headline numbers in reports render with error bars (Principle 1).

22. Phase 10 — Regression Detection, Baseline Pinning, A/B Compare, Leaderboards, CI Gates

22.1 Objectives

Operationalize comparison: pin baselines, run A/B model comparisons with CIs, render leaderboards, and fire CI regression gates only on statistically significant paired regressions after correction (I14, Principle 13). Constraint: a gate never fires on a point delta within noise.

22.2 Detailed Implementation Steps

  • evalh.regress — baseline pinning by (task@v, model@v, manifest); A/B compare reuses cached completions when present (I6). (I8; ADR-030; I1)
  • evalh.regress.gate — decision: regression iff paired delta significant (paired bootstrap) AND beyond a configured effect floor, post multiple-comparison correction (I14, ADR-017). (Dror et al. 2018; I14; ADR-017)
  • evalh.regress.leaderboard — append-only leaderboard store; render ranked table with CIs + per-slice (Principle 12). (I7; ADR-009; I1)
  • evalh.regress.slices — per-slice breakdown; flag slice-level regressions hidden by a flat global mean. (Card et al. EMNLP 2020; ADR-017)
  • CI integration (ADR-025): evalh ci-gate returns nonzero on a significant regression; emits a structured gate-decision artifact (p, corrected-α, effect).

22.3 Deliverable

evalh compare baseline candidate → A/B report with significance; evalh ci-gate → pass/fail used in GitHub Actions; evalh leaderboard → ranked board with error bars.

22.4 Acceptance Criteria

  • Gate does NOT fire on a null A/A comparison (no self-regression) across repeated runs.
  • Gate fires on an injected significant regression fixture.
  • Leaderboard ordering stable given identical inputs (deterministic, I1).
  • Per-slice regression surfaced even when global mean is flat.

22.5 Conformance Fixtures

  • conformance/regress/aa_null.json — A vs A → never fires.
  • conformance/regress/injected_regression.json → fires with correct p.
  • conformance/regress/slice_hidden.json — flat global, regressed slice → flagged.
  • conformance/regress/leaderboard_render.json — golden board.

22.6 Pitfalls

  • Flaky gate (no correction/power) → disabled by frustrated devs (worse than none); fix: significance + correction + adequate n (I14).
  • Baseline drift (provider model changed under a pinned name) → spurious regression; fix: pin model version/fingerprint in baseline manifest (I8).
  • Comparing across task versions → apples-to-oranges; fix: refuse compare on differing task@v.
  • Multiple-metric cherry-picking → fix: correct across the whole metric/slice family.

22.7 Performance Concerns

A/B reuses cached completions → compare is scoring/stats-bound, not inference-bound. Bootstrap over the paired sample is the cost (Phase 9). Leaderboard render is O(entries) — paginate.

22.8 Edge Cases

Unequal n between A and B (use paired subset on shared samples); missing baseline (first run → seed baseline, no gate); ties in leaderboard (stable tie-break by model id); a metric present in A but not B (excluded, noted).

22.9 Failure Analysis

A wrong gate decision either ships a regression (false pass) or blocks a good change (false fail). Detection: A/A null tests in CI + gate-decision audit (I14). Blast radius: the merge pipeline. Recovery: gate decisions are reproducible from stored scores; re-run the gate offline. Postmortem: gate-decision artifact (p, α, effect, n).

22.10 Operational Notes

Metrics: gate_decision, regressions_flagged, leaderboard_size. Gate config (effect floor, α, correction) is versioned. Runbook: "gate fired — reproduce offline, inspect slices, decide." Leaderboard is append-only provenance (I7).

23. Phase 11 — Reproducibility: RunManifest, Env Fingerprint, Deterministic Replay Harness (I1 gate), Append-Only Provenance

23.1 Objectives

Make any run reconstructable from its manifest + stored completions without re-spending inference (Principle 15), and enforce the determinism gate (I1): replay reproduces the identical aggregate. Constraint: a run cannot be Finalized without a complete manifest (I8).

23.4 Acceptance Criteria

  • Replay of any stored run reproduces the headline aggregate exactly (I1).
  • Finalize refuses a run missing any manifest field (I8).
  • Result store rejects writes after finalize (I7); mutation_after_finalize = 0.
  • A reviewer reproduces a published number from the manifest alone (given completions).

23.5 Conformance Fixtures

  • conformance/replay/manifest_roundtrip.json — run → replay → identical aggregate.
  • conformance/replay/incomplete_manifest.json → finalize refused.
  • conformance/replay/immutable_store.json → post-finalize write rejected.
  • conformance/replay/env_fingerprint.json — deterministic fingerprint.

23.6 Pitfalls

  • Hidden nondeterminism (a metric/judge touching global RNG) → replay diverges; fix: I2/I12 purity; replay gate catches it in CI.
  • Manifest omission (an output-affecting field not recorded) → irreproducible; fix: completeness check (I8) + key-coverage test (I6).
  • Mutable results → silent score laundering; fix: append-only store (I7).
  • Floating-point drift across platforms → tiny aggregate differences; fix: pinned numerics + tolerance spec, document determinism boundary.

23.7 Performance Concerns

Replay is inference-free (reads completions) → fast; cost is re-scoring + bootstrap (Phases 6/9). Manifest hashing is O(size) once per run. Store reads are sqlite-indexed.

23.8 Edge Cases

Replay after a metric-version bump (aggregate legitimately changes → flagged, not a failure, with version diff); missing completions for a sample (replay reports incompleteness); non-deterministic backend run replayed (uses pinned stored completions, I6); env mismatch (replay warns if fingerprint differs).

23.9 Failure Analysis

Replay mismatch is the canary for any reproducibility break. Detection: replay gate in CI (ADR-024, I1). Blast radius: trust in all numbers. Recovery: bisect inputs (manifest fields) to find the unrecorded/nondeterministic source. Postmortem: aggregate JSON diff + field bisection.

23.10 Operational Notes

Metrics: replay_mismatch (must be 0), incomplete_manifest, mutation_after_finalize. Runbook replay-divergence.md. The manifest is the unit of scientific reproducibility; it ships with every published result.

Scalability Analysis

Bottlenecks in order: (1) model/judge backend RTT + rate caps (inference cost) — mitigated by run-cache (warm runs are free) + bounded concurrency; (2) sandbox execution for code tasks (CPU) — pool + cap concurrency; (3) bootstrap × slices × metrics (CPU) — vectorize + parallelize; (4) result/cache store I/O — sharded CAS + sqlite, → Postgres + object store at scale (ADR-005/028). Horizontal scaling: shard samples across workers sharing the cache/result store (deterministic shard map); leaderboard/regress are read-mostly. Vertical scaling: process pool for scoring/sandbox/stats. Scaling ceilings: single sqlite index → migrate to Postgres beyond ~10⁶ cached completions / multi-writer; cache dir inode pressure → deeper sharding. Coordination overhead is low (shards independent, journal per-shard). Storage growth: completions + transcripts dominate → GC by age/size (never a live run), compression for transcripts. Metadata scaling: run index grows with runs → periodic archival of finalized runs (still replayable from CAS).

Mental Models & First Principles

  1. MM1 — Content-addressed storage decouples identity from location. Predicts: any object stored by its SHA-256 hash is immutable, deduplicated, and self-verifying on retrieval. Without it: you write a mutable cache indexed by a run-id or a timestamp and silently serve stale completions after a prompt change. Applied: §8.4 (cache_key derivation), §Phase 5 (run-cache store), §Phase 11 (result store, manifest).

  2. MM2 — A key must include all and only the output-affecting inputs. Predicts: over-keying loses cache reuse; under-keying serves wrong completions. Either failure is silent unless you have a key-coverage test. Without it: you omit decode_params from the key, temperature changes are invisible, and you report a "new" number that is actually the old run's cached output. Applied: §8.4, §Phase 5, §Phase 2 (template_hash feeds the key), ADR-030.

  3. MM3 — Paired comparison eliminates between-subject variance. Predicts: for two models evaluated on the same samples, the paired test (paired bootstrap, McNemar) has strictly higher power than an unpaired test at the same n. Without it: you use a two-sample t-test, miss a real regression because the inter-sample noise swamps the signal, and disable the gate as "too noisy." Applied: §8.6, §Phase 9, ADR-016, §Phase 10.

  4. MM4 — A pairwise judge's verdict is a random variable with position and verbosity bias as systematic components. Predicts: a single-order judge vote is E[verdict] + position_bias + verbosity_bias + noise; swap-and-average removes the first-order position component. Without it: whichever response appears first consistently "wins," and you ship a model simply because it happened to be candidate A. Applied: §8.5, §Phase 8 (swap-&-avg, I9), §Phase 8 (bias telemetry).

  5. MM5 — Exactly-once semantics requires journaling before side-effecting, not after. Predicts: if you journal after scoring, a crash between score and journal-write causes re-scoring on resume, inflating n and narrowing the CI. Without it: a killed run at 50% through produces a resume that double-counts hundreds of samples and reports a CI width that is too narrow. Applied: §Phase 5 (journal, I3, I13), §8.3 (run state machine).

  6. MM6 — Statistical power is a design constraint, not a post-hoc concern. Predicts: given baseline variance σ², target effect δ, α, and β, you can compute the required n before running; running with insufficient n produces a wide CI that neither gates a regression nor validates an improvement. Without it: you ship "improvements" that are within noise (Card et al. EMNLP 2020). Applied: §8.6, §Phase 9 (evalh.stats.power, MDE), §Phase 10 (gate design).

  7. MM7 — Provenance is a total order over inputs; a missing field is a reproducibility hole. Predicts: if any output-affecting input (model version, env, seed, decode params) is absent from the manifest, a reviewer cannot reproduce the number. Without it: "works on my machine" benchmarks — a number published without its manifest is not a scientific claim. Applied: §8.2 (RunManifest), §Phase 11 (I8, finalize completeness check), §Phase 0 (manifest spine).

  8. MM8 — An eval metric is only as trustworthy as its calibration against the ground truth it proxies. Predicts: BLEU correlates poorly with human judgment at the sentence level; an LLM judge's κ against human labels is the only honest measure of its reliability. Without it: you optimize a metric proxy and regress on the thing you actually care about. Applied: §8.5 (judge calibration), §Phase 8 (judge/calibration.py), §Phase 6 (differential oracle, ADR-022).

  9. MM9 — Contamination inflates scores monotonically with overlap; a clean-set held out is the only reliable detection. Predicts: n-gram overlap between train and eval data produces scores that collapse when re-evaluated on a genuinely unseen set. Without it: a leaderboard winner is the model most exposed to test questions during training, not the most capable one. Applied: §Phase 1 (contamination index, I4), §Phase 13 (contamination audit), §1 (non-goals: training data is not in scope).

  10. MM10 — Non-determinism must be quarantined at the boundary and pinned, not eliminated end-to-end. Predicts: a hosted API is never bit-deterministic even at temperature=0 (hardware batching, version drift); the correct design pins the observed completion in the cache and replays the stored output. Without it: your "deterministic" run gives a different number each time because the backend silently shifted, and you can never reproduce a published result. Applied: §Phase 3 (nondeterministic backend handling), §8.4 (cache key), §Phase 11 (replay, I1), Principle 6.

Back-of-Envelope Capacity Model

  1. Scoring throughput target (from §4: ≥ 50,000 samples/s single-core). EM/F1 on a single core at 50 k samples/s means ≤ 20 µs per score. Python function call + regex normalization + set intersection for token-F1 is empirically 2–10 µs on modern CPUs. Design consequence: keep metric functions allocation-free in the hot path; compile regex once at module load; avoid per-call tokenizer construction (ADR-014 — pin and reuse the tokenizer object).

  2. Bootstrap CI wall-time (from §4: 10 K resamples × 10 K samples ≤ 1 s). Required throughput = 10⁸ resample-index lookups/s. A vectorized numpy operation over a (10 K × 10 K) integer index matrix at 4 bytes/entry is 400 MB; modern numpy can execute this in ~0.3–0.7 s on a single core. Design consequence: pre-generate the resample index matrix once and apply via scores[indices] (ADR-015) — no Python loop over resamples; use np.mean(axis=1).

  3. Memory ceiling for completions window (from §4: default 100 K samples). A typical completion is ~200–2000 tokens. At 2 bytes/token average (UTF-8 compressed) and a generous 500 tokens average, one completion ≈ 1 KB. 100 K completions = ~100 MB in RAM. Design consequence: stream samples from the JSONL cache dir rather than loading the full result set; the 100 K window is the maximum inflight at any moment, sized to fit within a 256 MB process heap budget.

  4. Cache lookup budget (from §4: ≤ 1 ms p95). A sqlite SELECT by cache_key (indexed, VARCHAR primary key) on a local SSD is ~0.1–0.3 ms. Sharded dirs reduce inode pressure; shard count = sqrt(expected completions) → for 1 M completions, 1024 shards gives ~1000 entries/shard. Design consequence: index must exist on the cache_key column (ADR-008); shard the physical store to bound directory-scan cost.

  5. Parallelism ceiling: inference-bound runs (from §4: concurrency = min(cpu, backend_concurrency_limit)). A hosted API at 60 RPM (1 req/s) with p50 RTT of 2 s: optimal concurrency = 2 s × 1 req/s = 2 in-flight requests to saturate the rate limit. Adding more workers beyond this point queues, wastes memory, and risks a 429. Design consequence: the bounded async queue depth (ADR-011) must be set to rate_cap_per_sec × RTT_p95, not a fixed thread count.

  6. Judge-call cost multiplier (from §4: swap-&-avg requires 2× calls). If a pairwise eval of N response pairs is planned, the actual judge calls = 2 N × T (T = self-consistency samples). For T=1, N=1000 pairs, max_judge_calls from §4 must be set ≥ 2000. At GPT-4-class pricing (~$0.01/call), 2000 calls = $20. Design consequence: budget the judge_call ceiling at 2 × N × T + safety margin; set max_judge_calls in BudgetSpec before the run (I5).

  7. Crash-resume journal replay time (from §4: ≤ 5 s for 100 K-sample run). Journal file has 100 K lines at ~100 bytes/line = 10 MB. Sequential read at 500 MB/s = 20 ms. Building the "already scored" membership set from 100 K entries via a Python set = ~10 ms. Total well under 5 s. Design consequence: the journal must be a flat append-only log (no random-access index); the membership check uses a Python set of (sample_id, metric) tuples, not a sqlite query per sample.

  8. Contamination index build time (from §4 and Phase 1). An eval split of N=10 K samples at 200 tokens each: 4-grams per sample = 200 − 3 = 197, so total ≈ 10 K × 197 ≈ 2 M n-gram hashes. At ~50 ns each (hash + set insert) → 2 M × 50 ns ≈ 0.1 s per split; a 1 M-sample benchmark scales to ≈ 200 M hashes ≈ 10 s. Design consequence: a benchmark split is evaluated by many models repeatedly, so the index is cached keyed by dataset_hash and rebuilt only on a hash change — never recomputed per run (Phase 1).

  9. End-to-end harness overhead (from §4: ≤ 1% of wall-time on a real backend). For a 1000-sample run at 2 s RTT/call and 10 concurrency, wall-time ≈ 1000/10 × 2 s = 200 s. 1% budget = 2 s total for the control plane (registry load, task bind, cache lookup, journal, report). Registry load + bind: < 100 ms (§4: CLI cold ≤ 300 ms). Cache lookup: 100 K × 0.3 ms = 30 s for a 100 K run — reveals the 1 ms p95 constraint is load-bearing. Design consequence: cache lookup is the only harness component that can become the bottleneck at scale; the sqlite index and sharding are not optional.

  10. Reporter canonical-JSON stability. The RunManifest over a 1000-sample run with 10 metrics has ~100 KB of JSON. RFC 8785 canonicalization (sort keys, normalize floats) on 100 KB is < 5 ms (ADR-006). Design consequence: report rendering is never on the critical path; run the canonicalization in-process at report time, not during scoring.

Hard Questions (Self-Examination)

  1. If decode_params includes a seed field but the hosted API ignores it silently, the cache key will treat two runs as equivalent even though the completions may differ. How does the system distinguish a backend that respects seeds from one that does not, and how does the manifest record this distinction to prevent a reviewer from assuming bit-exact replay? (§8.4, §Phase 3, I6, I8, MM10)

  2. The cache key is derived from rendered_prompt_hash, which is itself a hash of the template content and the few-shot exemplars. If the few-shot pool changes between two runs (e.g., because the train split was re-filtered) but the template version does not change, will the cache correctly miss? Trace the hash dependency chain from the train split to the final cache key and identify every invariant that must hold. (§8.4, §Phase 1, §Phase 2, I4, I6, I10, ADR-030)

  3. Bootstrap CIs are valid when samples are i.i.d. In a stratified-aggregation scenario where you compute per-slice CIs and then report a weighted aggregate, the slice scores are correlated if a sample belongs to multiple slices. What is the correct resampling strategy, and how does the multiple-comparison correction interact with per-slice significance thresholds? (§8.6, §Phase 9, ADR-015, ADR-017, MM3)

  4. The pairwise judge evaluates (A, B) and (B, A). Swap-and-average removes first-order position bias. Does it remove verbosity bias? How would you design a conformance fixture that distinguishes a judge with pure position bias from one with pure verbosity bias, and what additional mitigation would each require? (§8.5, §Phase 8, I9, MM4)

  5. A MetricResult carries n = number of successfully scored samples and error_n = number of errors. The bootstrap CI is computed over the n scores. Under what conditions does a high error_n invalidate the CI's coverage guarantee, and what should the report say to the operator? (§8.2, §Phase 9, I11, §Phase 6, MM6)

  6. The replay harness asserts that manifest + stored completions → identical aggregate. If the scoring code (metric@version) is updated between the original run and the replay, the assertion should fail. How does the system differentiate a legitimate version-bump divergence from a hidden-nondeterminism divergence, and what does it report in each case? (§Phase 11, I1, I2, ADR-030, Compatibility & Versioning, MM7)

  7. The pass@k estimator is 1 − C(n−c, k)/C(n, k). When n is large and c is small (rare passes), the combinatorial terms underflow float64. How should evalh.metric.passk implement this numerically, and what is the conformance test that catches a naive implementation? (§Phase 7, I15, §8.6, ADR-015)

  8. A run has max_judge_calls = 2000 and requires 1000 pairwise comparisons × 1 self-consistency sample = 2000 calls. Exactly at the ceiling. The budget guard checks before dispatch. If the dispatcher pre-reserves the budget for a batch of calls and some calls fail and are retried, is the ceiling still honored? Trace the budget accounting through a retry. (§Phase 5, §Phase 8, I5, I3, ADR-011, ADR-029)

  9. Contamination detection uses n-gram overlap between the few-shot pool and the eval split. A test question appears in the training data paraphrased at the sentence level but not verbatim. The n-gram index misses it. What is the residual contamination risk after the current design, and how would you bound it quantitatively given a specific n-gram size? (§Phase 1, §Phase 13, I4, §1, MM9)

  10. The regression gate fires only on a significant paired regression after Holm-Bonferroni correction across the metric-slice family. Suppose a developer adds 50 new slices to a task to improve observability. Does this increase or decrease the gate's sensitivity to a real per-slice regression? How should the gate policy be adjusted, and which invariant governs the decision? (§Phase 10, §Phase 9, I14, ADR-017, MM3, MM6)

  11. The run-cache is content-addressed and never mutates a stored completion (I7). A metric bug is discovered post-run. The correct completions are already cached. Describe the full recovery procedure: which artifacts need to change, which remain valid, what version bumps are required, and which invariants are exercised. (§Phase 6, §Phase 11, I2, I7, ADR-030, Compatibility & Versioning, §Phase 0)

  12. Two runs of the same task on the same model produce n_A = 1319 and n_B = 1301 (18 samples errored in run B). The A/B comparison must be paired. How should the system construct the paired sample, and what should the report say about the 18 missing samples? Does the CI on the paired delta correctly reflect the uncertainty from those missing samples? (§8.6, §Phase 10, §Phase 9, I11, ADR-016, MM3)

  13. The evalh CLI cold-start target is ≤ 300 ms to first sample dispatched (§4). The registry loads from disk; the task binder runs a leakage check; the model backend initializes a connection pool. Profile each contributor to this budget and identify which phase adds the most risk of exceeding it as the registry grows. (§Phase 0, §Phase 1, §Phase 3, §4, MM2)

  14. An operator runs evalh replay <run_id> after migrating to a new Python version. The aggregate differs by 1e-8 from the stored value. Is this within the documented determinism boundary, a float-platform drift case, or a genuine nondeterminism bug? What is the diagnostic procedure, and which invariants determine when the difference is acceptable vs a blocker? (§Phase 11, I1, I2, Compatibility & Versioning, ADR-034, MM10)

  15. The judge's scorer_fp (judge model fingerprint) is recorded in the manifest. A provider silently updates their model under the same API name between two runs of the same task. How does the system detect this, and what is the recovery path for a leaderboard entry whose judge is now under a different distribution? (§Phase 8, §Phase 11, I8, ADR-012, §Phase 10, MM8)

  16. The bootstrap uses a seeded numpy.random.Generator. In a process pool (ADR-010), each worker receives a copy of the same seed at fork time. If two workers both bootstrap independently, their bootstrap distributions are identical (same seed). Is this a problem for the aggregate CI, and what is the correct seeding strategy in a parallel scoring context? (§Phase 9, §Phase 5, I12, ADR-010, ADR-015)

  17. A TaskSpec pins decode {temperature 0.0}. A researcher wants to estimate the variance of the model's output distribution (not just the greedy decoding) to inform power calculations. Explain the design change required to the TaskSpec, the impact on the cache-key schema, and the version bump required. (§8.1, §8.4, ADR-030, §Phase 9, §Phase 3, I6, MM2)

  18. The contamination index checks n-gram overlap at task-bind time. But the few-shot pool is drawn at run time (seeded, from train). If a different seed happens to select exemplars that do overlap with eval (even though the pool overall does not), the pre-run check would pass but a specific run would be contaminated. Is this possible given the current design, and which invariant closes the gap? (§Phase 1, §Phase 2, I4, §8.1, §Phase 5, MM9)

  19. The result store is append-only. An operator wants to annotate a run with a post-hoc human review of 10 randomly sampled predictions. Where in the architecture does this annotation live, how is it linked to the immutable run, and what does it mean for the manifest's completeness invariant? (§Phase 11, I7, I8, §Phase 4, §8.2, MM7)

  20. The Holm-Bonferroni correction applied to K tests controls the family-wise error rate (FWER). The Benjamini-Hochberg procedure controls the false-discovery rate (FDR). For a leaderboard with 20 slices and 5 metrics (100 tests), which correction is appropriate for a CI regression gate vs a research exploration report, and what is the practical consequence of choosing the wrong one? (§Phase 10, §Phase 9, ADR-017, I14, MM3, MM6)

  21. The journal uses a monotone sequence number (I13) to ensure resume completeness. If two workers write to the same journal file (e.g., after a shard reassignment on crash), the sequence may have gaps or collisions. What is the correct journal write protocol for multi-worker runs, and which invariant governs the acceptable journal topology? (§Phase 5, §Phase 13, I13, I3, ADR-010, MM5)

  22. A new metric is contributed as a plugin via the entry-point mechanism. It uses a global mutable normalization table that is loaded at import time. What is the specific invariant it violates, what property test would catch it, and what change to the plugin contract would prevent such plugins from being registered? (§Phase 6, I2, ADR-021, ADR-026, ADR-030, MM8)
