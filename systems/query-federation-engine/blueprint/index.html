1. Goal & Scope

Engineering Definition

A query federation engine is a distributed query-processing layer that accepts declarative queries (SQL, gRPC RPC) against a virtual unified schema, plans and optimizes execution across heterogeneous, autonomous data sources it does not own, pushes as much work as each source's capability model allows, and executes the remainder — joins, aggregation, re-shuffling — inside its own distributed runtime. It owns metadata, plans, and telemetry; it never owns the rows. Build target: a Rust workspace implementing the coordinator, planner/optimizer, distributed scheduler, Arrow-native execution engine, connector SDK, metadata catalog, and observability/replay subsystem described in §3, sized to the budgets in §4.

Phase 0 Deliverable — numbered crates/services

  1. coordinator — session and query lifecycle authority (§12).
  2. parser — SQL lexer/grammar/AST (§13).
  3. planner — logical plan construction, semantic validation (§13).
  4. optimizer — cost-based rewrite, join ordering, pushdown negotiation (§14).
  5. scheduler — fragment placement, worker registry, admission control (§15).
  6. execution-engine — Arrow operator runtime, exchange, hash join (§16).
  7. spill-engine — disk-backed overflow for memory-bounded operators (§17).
  8. connector-sdk — capability-negotiated source integration trait set (§18).
  9. connectors/postgres, connectors/mysql, connectors/parquet — first three source integrations (§18).
  10. metadata-catalog — schema/connector/statistics registry (§19).
  11. telemetry — tracing, metrics, structured logging (§20).
  12. replay-engine — deterministic execution WAL and replay CLI (§20).
  13. sql-gateway / grpc-api — client-facing protocol front ends (§21).
  14. authz — OIDC/RBAC enforcement (§21).
  15. conformance — fixture-driven cross-crate acceptance suite (all phases).
  16. benchmarks — TPC-H subset and connector latency harness (§28).

System Boundaries

Provides:

  • federated SQL/gRPC query surface over heterogeneous backends,
  • logical/physical planning, cost-based optimization, predicate/projection/aggregation/join/limit pushdown negotiation,
  • distributed fragment scheduling and Arrow-native execution with spill,
  • connector isolation, capability negotiation, retry-bounded source access,
  • metadata catalog, statistics cache, governance (RBAC, tenant isolation),
  • deterministic, replayable execution telemetry.

Delegates (does not reimplement):

  • durable primary storage — owned by Postgres, MySQL, ClickHouse, Elasticsearch, object storage, Kafka, Parquet/Iceberg tables,
  • transactional consistency inside each source,
  • source-side query execution beyond what pushdown negotiates.

Does NOT provide (Phase 0, see §35 for deferrals):

  • a distributed storage engine,
  • a distributed ACID transaction coordinator or federated writes,
  • OLTP serving latency guarantees,
  • a custom vectorized on-disk storage format,
  • GPU execution,
  • autonomous/adaptive re-planning at runtime,
  • speculative distributed execution,
  • full SQL:2016 standard coverage — a locked subset only (§5).

Non-Goals (Phase 0)

Distributed storage ownership, multi-region consensus replication, adaptive cost-model self-tuning, WASM-sandboxed connector execution, vectorized SIMD execution beyond Arrow compute kernels already provided by the ecosystem. Each is registered in §35 with a phase anchor and un-defer trigger.

Deployment Model

Kubernetes-native control plane; stateless coordinators behind a load balancer; elastic worker pools autoscaled on scheduler queue depth; dedicated PostgreSQL-backed metadata database; isolated per-connector-type runtime pools (process or thread-pool isolation, ADR-08); object storage-backed spill. Five supported modes: single-node developer, HA coordinator, distributed execution cluster, air-gapped enterprise, edge federated (bounded connector set, no spill tier).

Target Operators

Platform SRE and data-infrastructure operators run and scale the cluster; security/governance teams own RBAC policy and audit; connector authors, optimizer engineers, and runtime engineers extend it; BI tools, analysts, federated API consumers, and ML feature pipelines consume it.

What Later Phases Unlock

Phase 0 unlocks an inspectable, health-checked, but query-less skeleton. Phase 1 unlocks parsed, validated logical plans. Phase 2 unlocks cost-based physical plans. Phase 3 unlocks distributed placement. Phase 4 unlocks actual cross-source execution. Phase 5 unlocks bounded memory under skew. Phase 6 unlocks real backends. Phase 7 unlocks governed multi-tenant catalogs. Phase 8 unlocks forensic replay. Phase 9 unlocks the client-facing, authenticated, production surface.

Recommended Language

Rust, locked (ADR-01). Rationale: deterministic ownership eliminates a GC-pause class of tail-latency amplification (§5 "The Tail at Scale"); the borrow checker enforces the single-owner execution-state principle (P3) at compile time rather than by runtime discipline; the Tokio/Arrow/ DataFusion ecosystem (§5) gives a mature async runtime plus a columnar memory format without a from-scratch batch representation. Rejected: Go (GC pauses collide with p99 budgets in §4; weaker generic/trait guarantees for a plan-rewrite-heavy codebase); Java (JVM tuning overhead, GC pause tails, heavier operational footprint per worker); C++ (memory-safety risk in a codebase with untrusted connector plugins, ADR-08 concurrency model harder to enforce without the borrow checker); Python (no compile-time determinism guarantee, unsuitable as the execution runtime though acceptable for scripts/ tooling, ADR-01 column 6).

Prerequisites

Distributed systems fundamentals, relational algebra and cost-based optimization, storage internals, scheduler design, async runtimes (Tokio), concurrency control, Arrow memory format, RPC protocol design (gRPC/protobuf), observability systems (OpenTelemetry), benchmarking methodology.

Estimated Timeline

Phase 0 MVP: 10 weeks. Distributed execution (Phases 1–4): +3 months. Connectors and governance (Phases 5–7): +4 months. Observability/replay and production gateway (Phases 8–9): +6 months. Advanced optimization and HA federation hardening beyond Phase 9: +8 months. Full system: ~21 months to production stabilization from Phase 0 start.

2. Why Build This

Core Educational Value

Distributed query planning under uncertain source statistics; heterogeneous execution orchestration across trust and protocol boundaries; runtime scheduling with bounded queues; connector isolation and capability negotiation; cost estimation with adversarial skew; distributed observability across coordinator/worker/connector process boundaries; execution replayability from an append-only WAL; schema evolution management without breaking in-flight plans.

The implementation forces reasoning about: cross-system consistency without 2PC, partial failure of one connector while others succeed, pushdown semantics that vary per source, runtime memory pressure and deterministic spill, bounded execution under adversarial cardinality, asynchronous execution DAGs with backpressure, transport serialization cost (Arrow IPC vs Protobuf), and tail-latency amplification (fan-out to N sources bounds p99 by the slowest one, §5).

Historical Importance

Lineage: the Volcano iterator model (1994) → Apache Calcite's rule-based/cost-based optimizer framework → Presto/Trino's disaggregated storage-compute federation model → Dremio/Drill's self-describing schema pushdown → Spark SQL's Catalyst-style logical/physical split → BigQuery external tables and Snowflake external tables as federation-as-a-feature inside a warehouse. This project reconstructs the planner/scheduler/connector triad that all of the above share, at a scope one engineer can hold in their head.

Engineering Calibration Value

A completed implementation demonstrates systems architecture maturity (planner-optimizer-executor separation), production operations competency (§24), distributed runtime understanding (scheduler/exchange/spill), performance engineering discipline (§28), reliability engineering capability (§23), API governance awareness (§25), and storage interoperability expertise across six heterogeneous backend protocols.

What Mastery Looks Like

  • Can explain why predicate pushdown is unsound for a source without transactional snapshot isolation, tied to Phase 6 (§18) connector capability negotiation.
  • Can derive the memory budget for a hash join from cardinality estimates and know when to spill, tied to Phase 4/5 (§16, §17).
  • Can design a fragment placement algorithm that survives a worker crash without orphaning state, tied to Phase 3 (§15).
  • Can read a deterministic replay WAL and reconstruct why an optimizer chose a bad join order, tied to Phase 8 (§20).
  • Can articulate the difference between logical and physical plan invariants and why reordering column IDs breaks schema evolution, tied to Phase 2 and Phase 7 (§14, §19).
  • Can bound tail latency for a fan-out query across N sources and justify a per-source timeout, tied to Phase 6 and Performance Engineering (§18, §28).
  • Can enforce tenant isolation in a shared metadata catalog under concurrent schema mutation, tied to Phase 7 (§19).

Subsystem Responsibilities

sql-gateway/grpc-api (§21) — protocol translation, session multiplexing, admission control at the edge, rate limiting. Trust boundary: all external traffic terminates here; nothing downstream trusts client-supplied identity without an authz decision.

authz (§21) — OIDC token validation, RBAC policy evaluation, tenant binding. Failure mode: authentication bypass reaches the coordinator with an unauthenticated session context — P12 (fail closed) exists to prevent this.

coordinator (§12) — query lifecycle (QueryHandle, §11), session/tenant context, admission control, retry supervision, plan orchestration hand-off. Concurrency boundary: one coordinator instance owns a session's mutable state exclusively (P3); persistence boundary: execution metadata snapshots checkpoint to the metadata catalog before a query is acknowledged RUNNING.

parser+planner (§13) — SQL grammar (§5 SQL:2016 subset), AST, semantic validation against catalog, logical operator DAG.

optimizer (§14) — join reordering, cardinality estimation from the statistics service, pushdown capability negotiation against ConnectorCapability (§11), fragment parallelization hints.

scheduler (§15) — fragment placement onto workers, worker heartbeats, bounded admission queues, execution leases (I7), retry orchestration, cancellation propagation. Concurrency boundary: exactly one worker holds an active lease per fragment (I3).

execution-engine (§16) — Arrow RecordBatch operator pipeline (scan/filter/project/hash-join/ aggregate), exchange streams between fragments, memory tracking.

spill-engine (§17) — Arrow-IPC-encoded disk overflow for operators that would otherwise exceed their memory budget; checksum-validated restore (I5).

connector-sdk + connectors/* (§18) — per-source pushdown translation, protocol adaptation (wire protocol boundary — each connector process/thread pool is isolated per P4), retry policy, schema discovery.

metadata-catalog (§19) — schema registry, connector registry, capability metadata, statistics cache, governance policy metadata. Persistence boundary: PostgreSQL-backed (ADR-04), the only subsystem permitted to mutate durable schema/policy state.

telemetry + replay-engine (§20) — every box above emits traces/metrics/structured logs; replay-engine additionally taps coordinator/scheduler/execution-engine/connector-sdk event streams into an append-only WAL (I2) for deterministic reconstruction.

6. Design Principles

  • P1 — Deterministic Execution. Rule: every execution plan must be replayable byte-for-byte from its telemetry snapshot · Tradeoff: forbids nondeterministic operator ordering and wall-clock reads inside the hot path · Operational: replay-engine (§20) is the audit tool of record · Violated: production failures become non-debuggable, optimizer regressions can't be bisected.
  • P2 — Backpressure Everywhere. Rule: every queue (scheduler admission, exchange channel, connector request pool) is bounded · Tradeoff: bounded queues reject or block producers instead of buffering unboundedly · Operational: queue-depth metrics page before collapse (§15.10) · Violated: one slow connector or worker causes unbounded memory growth and coordinator OOM.
  • P3 — Explicit Single Ownership. Rule: every piece of execution state has exactly one lifecycle owner at any instant · Tradeoff: requires explicit hand-off protocols (leases, I7) instead of shared mutable state · Operational: enforced by Rust's ownership model at compile time · Violated: two workers can both believe they own a fragment — split-brain execution.
  • P4 — Connector Isolation. Rule: each connector type runs in an isolated runtime pool (process or dedicated thread pool) · Tradeoff: costs one context-switch/serialization hop per source call · Operational: a crashing connector cannot take down the coordinator or another connector · Violated: a buggy connector's panic or resource leak becomes a cluster-wide outage.
  • P5 — Observability First. Rule: every query stage emits a trace span, a metric, a structured log line, and a replay checkpoint · Tradeoff: telemetry overhead on the hot path (§16.7) · Operational: incident response starts from a trace, never from grep · Violated: an operator cannot answer "why is this query slow" without redeploying with debug logging.
  • P6 — Spill Before OOM. Rule: memory pressure triggers deterministic spill at the §4 threshold before the allocator is exhausted · Tradeoff: spill adds disk I/O and up to 1.5x storage amplification (§4) · Operational: spill-engine (§17) owns this contract exclusively · Violated: the process OOM-kills mid-query with no checkpoint to resume from.
  • P7 — Stable Wire Compatibility. Rule: all external APIs (gRPC, SQL wire protocol) are semver governed with N-1 coordinator compatibility · Tradeoff: slows breaking-change velocity · Operational: rolling upgrades depend on this (§25) · Violated: a minor upgrade breaks every connected BI tool simultaneously.
  • P8 — Crash-Only Workers. Rule: workers are disposable — no graceful-shutdown state that must be preserved outside a lease/checkpoint · Tradeoff: forces all recoverable state into the scheduler/catalog, never the worker process · Operational: autoscale-down is just SIGKILL · Violated: worker restarts silently lose in-flight results with no detectable failure.
  • P9 — Schema Evolution Safety. Rule: schema changes are validated for backward compatibility before commit — column IDs never reorder (I4) · Tradeoff: additive-only evolution is stricter than some source systems allow · Operational: metadata-catalog (§19) enforces at write time · Violated: an in-flight plan reads a column by position and silently reads the wrong data.
  • P10 — Bounded Retry Semantics. Rule: every retry path has a fixed budget (I12) and backoff · Tradeoff: a source that needs more than 3 attempts (§4) fails the query instead of hanging · Operational: retry-storm protection for the scheduler and every connector · Violated: a flaky source causes exponential fan-out of retries that saturates the scheduler queue.
  • P11 — Cost Model Transparency. Rule: every optimizer decision (join order, pushdown acceptance/rejection) emits an inspectable trace with the cost inputs used · Tradeoff: extra telemetry volume on every optimized query · Operational: EXPLAIN-equivalent debugging without re-running the query · Violated: a bad join order can only be diagnosed by trial and error.
  • P12 — Fail Closed on Governance. Rule: an RBAC or tenant-isolation decision that cannot be evaluated (catalog outage, ambiguous policy) denies the request · Tradeoff: catalog unavailability becomes a read-only or denied state instead of best-effort access · Operational: authz (§21) and metadata-catalog (§19) both enforce this · Violated: a policy-evaluation bug fails open and leaks cross-tenant data.
  • P13 — Idempotent Fragment Dispatch. Rule: dispatching the same fragment_id + lease token twice must be a no-op on the second delivery · Tradeoff: requires deduplication state per lease · Operational: makes scheduler retries safe under network duplication · Violated: a duplicate dispatch under an at-least-once RPC executes a fragment twice, double-counting aggregates.
  • P14 — Time Source Discipline. Rule: all duration/timeout logic uses a monotonic clock; wall clock is used only for display/audit timestamps · Tradeoff: requires threading a clock abstraction through every timeout path instead of calling the system clock directly · Operational: enables deterministic replay under P1 · Violated: an NTP correction mid-query causes a spurious timeout or a negative duration in telemetry.

Failure Path Example — Connector Timeout

  1. connector runtime emits a timeout event on its isolated pool (P4),
  2. scheduler marks the owning fragment DEGRADED, decrements retry budget (I12),
  3. if retry budget remains, scheduler reissues a new lease (I7) and reschedules,
  4. if exhausted, coordinator transitions the query FAILED (I8) with the connector diagnostic attached,
  5. replay-engine emits a checkpoint capturing the full retry sequence for forensics (§20).

Blast radius: one coordinator replica; Kubernetes readiness gating keeps it out of traffic. No query telemetry exists yet, so postmortems here are config- or environment-driven by construction.

  3. Implement parser combinators building the raw AST, anchored to Graefe 1994's operator-tree shape (§5) so the logical DAG (step 7) is a direct lowering.
  4. Add AST normalization (planner/src/ast.rs): canonicalize expressions, resolve * expansion against catalog column lists.
  5. Create the semantic analyzer (planner/src/semantic.rs): type-checks, resolves references, rejects ambiguity with a located diagnostic.
  6. Implement catalog resolution against metadata-catalog's schema registry (§19), read-only here.
  7. Create the logical operator DAG (planner/src/logical.rs): Scan/Filter/Project/Join/Aggregate/ Sort/Limit nodes, no physical properties yet (§14).
  8. Implement parser/src/diagnostics.rs: every rejection carries source span, expected-vs-found token, and the catalog resolution trace attempted.

  10. Add fuzz/fuzz_targets/parser_fuzz.rs (ADR-13): must survive 1M iterations, zero panics.

13.3 Deliverable

A parser/planner pair that, for any query in the §5 subset, produces either a validated logical DAG or a source-located diagnostic — never a panic, never a silently wrong plan.

  • Parser conformance suite (fixtures/parser/*.sql) passes ≥ 95%.
  • Malformed-query fixtures produce byte-identical diagnostics across 100 repeated runs (P1).
  • Zero parser panics across 1,000,000 cargo-fuzz iterations (ADR-13).

13.5 Conformance Fixtures

  • fixtures/parser/select-basic.sql — single-table projection, 3-node logical DAG.
  • fixtures/parser/join-nested.sql — three-way nested join, correct pre-reorder tree shape.
  • fixtures/parser/malformed-missing-from.sql — diagnostic citing the missing FROM clause.
  • fixtures/parser/malformed-invalid-group.sql — non-aggregated column with GROUP BY, semantic (not syntax) diagnostic.
  • fixtures/parser/replay-query-hash-stability.trace — hash stability across whitespace/case.

13.6 Pitfalls

  1. Ambiguous grammar around nested/correlated subqueries — manifestation: accept/reject flips on near-identical inputs; root cause: combinator rule-ordering sensitivity; recovery: explicit disambiguation rule plus regression fixture.
  2. AST ownership cycles normalizing self-referential constructs — manifestation: stack overflow; root cause: unbounded recursive traversal; recovery: bounded traversal depth with a diagnostic.
  3. Catalog lookup races during concurrent analysis of a mid-migration schema — manifestation: nondeterministic validation for the same query; recovery: pin the catalog snapshot version at query-start (I11).

13.7 Performance Concerns

  • Combinator parsing allocates a node per production — arena-pool small allocations (bumpalo).
  • Hash-map contention on the catalog resolution cache under concurrent parses — shard by schema ID.
  • Fold query hashing into the normalization pass rather than a second AST traversal.

13.8 Edge Cases

  • Deeply nested expressions (200-deep AND chains) — bounded recursion, never stack-overflow.
  • Unicode identifiers (including RTL scripts) in quoted identifiers, normalized to NFC.
  • Overflow literals (exceeding i64/u64 range) — reject with a diagnostic, never truncate silently.

13.9 Failure Analysis

Semantic failures emit source location, operator context, and the full catalog resolution trace — sufficient to reproduce without a live catalog. Blast radius is confined to the single query; no shared state mutates during parsing. Detection is synchronous; the caller receives the diagnostic in the same RPC. Grammar-ambiguity fixes always gain a regression fixture, never a one-off patch.

13.10 Operational Notes

Metrics: parser_latency_seconds, parser_fuzz_panics_total (pages if nonzero), query_class_distribution. Spans: plan.parse, plan.normalize, plan.semantic_validate, plan.catalog_resolve. Log fields: query_hash, diagnostic_code, catalog_snapshot_version. Deployment: runs inside the coordinator/planner call path, no new service.

14. Phase 2 — Cost-Based Optimizer & Statistics

14.1 Objectives

  • Implement cost-based physical planning: join reordering, cardinality estimation, pushdown negotiation against ConnectorCapability (I10).
  • Bound optimization time so a pathological join graph cannot blow the p95 latency budget (§4).
  • Produce cost-annotated, inspectable plans satisfying P11.

14.2 Detailed Implementation Steps

  1. Define statistics interfaces (optimizer/src/histogram.rs) consuming metadata-catalog's stats_cache.rs (§19): row counts, histograms, NDV estimates.
  2. Implement the rule registry (optimizer/src/rules.rs), anchored to Calcite's RelOptRule pattern (§5) but with an explicit iteration cap (step 8) since exhaustive matching diverges.
  3. Implement heuristic pre-optimization (predicate simplification, constant folding) applied unconditionally before cost-based rewrite.
  4. Implement pushdown negotiation (optimizer/src/pushdown.rs): check every candidate against the source's declared ConnectorCapability — the only place I10 decisions are made.
  5. Implement join reordering (optimizer/src/join_order.rs) via DP cost search bounded to ≤ 12 relations, greedy heuristic beyond that (Roy et al. 2000, §5).
  6. Create the histogram-based cardinality estimator, falling back to documented default selectivity (0.1 equality, 0.33 range) when statistics are missing.
  7. Add optimizer trace emission (P11): every accepted/rejected rule application with its cost delta.
  8. Implement an optimization timeout budget: hard-abort rule search at the §4 p95 budget, emit the best plan found.

14.3 Deliverable

A cost-based optimizer producing physical plans with per-node cost annotations and a full, replayable rule-application trace, deterministic for a fixed catalog snapshot and statistics version.

14.4 Acceptance Criteria

  • Optimizer output byte-identical across 100 runs against a pinned snapshot (P1).
  • fixtures/optimizer/tpch-q1.sql-class join reordering completes with optimization p95 < 200 ms.
  • fixtures/optimizer/pushdown-filter.sql: 100% of eligible predicates pushed where supports_predicate_pushdown: true, 0% where false (I10, zero tolerance).
  • Timeout budget triggers a fallback (never a hang) on pathological-join-30way.sql within timeout ± 50 ms.

14.5 Conformance Fixtures

  • fixtures/optimizer/tpch-q1.sql — canonical aggregation, golden-file plan-shape regression.
  • fixtures/optimizer/pushdown-filter.sql — mixed-capability two-source join.
  • fixtures/optimizer/distributed-join.sql — three-source join exercising exchange insertion.
  • fixtures/optimizer/pathological-join-30way.sql — stresses timeout and greedy fallback.
  • fixtures/optimizer/missing-statistics.sql — default-selectivity fallback, not a failure.

14.6 Pitfalls

  1. Cardinality explosion on skew where the default-selectivity fallback badly underestimates — root cause: missing statistics silently substituted a generic default; recovery: feed the actual-vs-estimated ratio back as a statistics-refresh trigger (deferred, §35).
  2. Unstable heuristics: logically-equivalent queries (a JOIN b vs b JOIN a) produce different plans — root cause: rule-order sensitivity; recovery: canonicalize the join graph before cost search.
  3. Recursive optimization loops where two rules each treat the other's output as an improvement — root cause: rules not confluent; recovery: enforce a strict cost-decrease invariant per rule application.

14.7 Performance Concerns

  • Combinatorial growth beyond 12 relations — bounded DP switches to greedy (step 5).
  • Metadata lookup amplification — batch all statistics fetches into one round-trip per query.
  • Rule registry scan overhead — index rules by the operator type they match, not a full-tree scan.

14.8 Edge Cases

  • Missing statistics on a newly registered table — default-selectivity fallback, never a hard failure.
  • Skewed distributions (one bucket holding > 50% of rows) — bucket-boundary-aware estimation.
  • Unsupported pushdown the optimizer assumed available — I10 rejects at negotiation, engine-side fallback inserted instead of failing.

14.9 Failure Analysis

Optimizer failures (timeout, invariant violation) fall back to the heuristic pre-optimization plan rather than failing the query — a suboptimal plan beats no plan. Detection: optimization-duration metric crossing the timeout threshold. Blast radius: single query, surfaced as degraded via a plan-quality warning header, not an error. The rejected-plan trace (P11) is retained even on the fallback path.

14.10 Operational Notes

Metrics: optimizer_latency_seconds, optimizer_timeout_fallbacks_total, pushdown_capability_violations_total (I10). Spans: plan.optimize, plan.join_reorder, plan.pushdown_negotiate. Log fields: plan_cost_estimate, statistics_snapshot_version. PhaseDeferred("§14"): adaptive cost-model self-tuning from runtime feedback is out of scope here — registered in §35.

  3. Add bounded admission queues (scheduler/src/queue.rs) enforcing I9's §4 cap via a bounded channel (ADR-21).
  4. Define placement (scheduler/src/placement.rs): capacity-weighted round-robin with locality hints from the optimizer's fragment-parallelization output.
  5. Add admission control ahead of placement: reject once I9's cap is reached, surfaced as backpressure (P2), never silently queued past the cap.
  6. Implement fragment retry tracking enforcing I12 — the counter only increments except on a fresh lease.
  7. Add execution leases (scheduler/src/lease.rs): time-bounded, unique per attempt, enforcing I7 and I3 together — expiry is the only path to reassignment.
  8. Implement cancellation propagation: a cancelled query's fragments are fenced within one heartbeat interval.
  9. Add queue and lease telemetry: depth, age, eviction counters feeding §15.10.

15.3 Deliverable

A distributed scheduler that places fragments onto a live worker pool, detects and recovers from worker failure within a bounded time, and guarantees via I3/I7 that no fragment ever executes on two workers simultaneously.

15.4 Acceptance Criteria

  • Worker failover (missed heartbeat to reassignment) < 10 s across 200 injected-crash trials.
  • Zero orphaned fragments across a 10,000-fragment chaos run (fixtures/scheduler/worker- restart.trace).
  • Queue depth never exceeds 100,000 (I9) across a 24-hour soak with sustained overload.
  • Retry budget (3, §4) exhausted correctly on retry-budget.trace — the 4th failure transitions FAILED.

15.5 Conformance Fixtures

  • fixtures/scheduler/worker-restart.trace — crash mid-execution, reassignment within SLO.
  • fixtures/scheduler/queue-overflow.trace — sustained submission past the I9 cap, rejection.
  • fixtures/scheduler/retry-budget.trace — repeated failure, exhaustion at exactly 3 (I12).
  • fixtures/scheduler/split-brain-injected.trace — two workers claim the same lease, I3 fencing.
  • fixtures/scheduler/duplicate-worker-id.trace — duplicate registration, deterministic rejection.

15.6 Pitfalls

  1. Split-brain worker state after a network partition — root cause: lease expiry checked by wall-clock without a fencing token; recovery: monotonically increasing fencing epoch on every dispatch, stale epochs rejected downstream.
  2. Queue starvation where cheap fragments crowd out large ones — root cause: FIFO admission with no fairness dimension; recovery: weighted fair queueing by query.
  3. Retry storms where fragments of a failing query retry in lockstep — root cause: no backoff jitter; recovery: exponential backoff with jitter (extends P10).

15.7 Performance Concerns

  • Lock contention in the registry/lease table under fragment churn — shard by worker/fragment ID hash (ADR-08).
  • Heartbeat amplification at scale — batch heartbeat processing per tick, not per-worker syscalls.
  • Locality-hint lookups must not add a per-fragment catalog round-trip — precompute once per query.

15.8 Edge Cases

  • Coordinator restart during active execution — leases survive since they live in scheduler state, checkpointed independently.
  • Duplicate worker IDs from a misconfigured autoscaler — deterministic rejection of the second.
  • Lease renewal racing lease expiry at the exact boundary — both read the same monotonic clock (P14) to avoid a false eviction.

15.9 Failure Analysis

Scheduler saturation (I9 cap) triggers admission rejection, a degraded-mode metric, and — if sustained — a full queue-state dump to the replay WAL. Blast radius of a worker crash is bounded by its leased fragments and the lease TTL. Blast radius of registry corruption is cluster-wide and requires the readonly-degraded posture (P12) until rebuilt from worker re-registration.

15.10 Operational Notes

Metrics: scheduler_queue_depth (I9), fragment_retries_total, worker_churn_total, lease_expirations_total (I7), fragment_ownership_conflicts_total (I3). Spans: schedule.place, schedule.heartbeat_tick, schedule.lease_renew. Log fields: fencing_epoch, worker_id, lease_id. Rollback: registry state is rebuildable from re-registration, no data migration needed.

  1. Exchange deadlocks from a cyclic backpressure dependency between two fragments — root cause: an exchange topology with a cycle the physical planner should have rejected; recovery: static cycle rejection upstream in §14, runtime assertion here.
  2. Batch ownership bugs where a RecordBatch buffer is read concurrently after an improperly reference-counted slice — recovery: never manually slice buffers, always use Arrow's buffer- sharing APIs.
  3. Spill corruption surfacing here as wrong row counts after a spill-restore cycle — root cause: checksum validation (I5) not wired into the join's restore path; recovery: treat a restored batch identically to a checksum-fresh one.

16.7 Performance Concerns

  • Hash join build-side layout: open-addressing (Robin Hood) over chained buckets for cache behavior at §32's table sizes.
  • Arrow buffers must stay aligned for SIMD compute kernels — never manually offset a buffer without re-checking alignment.
  • Exchange batch size (§4's 8 MB) balances per-batch fixed cost against last-batch tail latency.

16.8 Edge Cases

  • Partial spill writes interrupted by worker crash — validated by I5's checksum at restore, never assumed complete.
  • Connector backpressure propagating upstream through scan into the exchange — bounded channels (P2) propagate slowdown, never buffer around it.
  • Worker cancellation mid-join — teardown releases the memory tracker reservation and closes exchange channels without half-written batches downstream.

16.9 Failure Analysis

Worker crashes require fragment replay from the last checkpointed lease state (§15), spill file cleanup for any partial spill owned by the crashed worker (§17.9), and orphan-exchange detection — a downstream fragment blocked on a dead upstream times out rather than hanging. Blast radius: the crashed fragment and any fragment directly exchanging with it; unrelated fragments continue.

16.10 Operational Notes

17. Phase 5 — Spill Subsystem & Memory Governance

17.1 Objectives

  • Implement the disk-backed spill path (P6) triggered by §16's memory tracker at the §4 70%-heap threshold.
  • Guarantee checksum-validated restore (I5) so a spilled batch is never silently corrupted.
  • Bound storage amplification to the §4 target (< 1.5x) and recovery time to the §4 RTO (< 60 s).

17.2 Detailed Implementation Steps

  1. Implement spill-engine/src/spill_writer.rs: Arrow-IPC-encoded batch framing (ADR-05) written to a per-fragment spill file, anchored to the Arrow IPC RFC (§5).
  2. Implement spill-engine/src/checksum.rs: CRC32C framing per spilled batch, computed on write.
  3. Implement spill-engine/src/spill_reader.rs: checksum-validated restore path enforcing I5 — any mismatch rejects the batch rather than returning it.
  4. Wire the spill writer to the §16 memory tracker's pressure signal: crossing 70% heap (§4) arms spill for the next allocation, not the current one (avoids spilling mid-batch).
  5. Implement spill file lifecycle: created lazily, deleted on fragment completion or lease expiry (ties to I7 — an expired lease's orphaned spill file is garbage-collected).
  6. Add object-storage-backed spill tier for the distributed cluster mode (§1 deployment model), local-disk tier for single-node developer mode.
  7. Add spill telemetry: bytes written/read, restore latency, checksum failure counter.
  8. Add a spill-storage-amplification metric computed as spilled-bytes ÷ logical-batch-bytes, validated against the §4 1.5x budget in CI.

17.3 Deliverable

A spill subsystem that transparently overflows any memory-bounded operator (hash join, aggregation) to disk or object storage at the §4 threshold, and restores with checksum-validated integrity within the §4 RTO.

17.4 Acceptance Criteria

  • Spill-and-restore round trip on fixtures/spill/large-join-spill.dataset produces byte- identical results to the non-spilled reference computation.
  • Restore RTO < 60 s (§4) for a 4 GB spilled table across 20 trials.
  • Storage amplification < 1.5x (§4) measured across 10 mixed-cardinality fixtures.
  • A corrupted spill file (fixtures/spill/checksum-corrupt.dataset) is rejected 100% of the time, never silently restored (I5).

17.5 Conformance Fixtures

  • fixtures/spill/large-join-spill.dataset — forces spill mid-join, correctness baseline.
  • fixtures/spill/checksum-corrupt.dataset — bit-flipped spill file, expects I5 rejection.
  • fixtures/spill/orphaned-lease-cleanup.trace — expired lease with an orphaned spill file, expects garbage collection.
  • fixtures/spill/object-storage-spill.trace — distributed-mode spill tier round trip.
  • fixtures/spill/partial-write-crash.trace — crash mid-spill-write, expects a truncated-file detection, not a false-positive checksum pass.

17.6 Pitfalls

  1. Spilling mid-batch instead of at a batch boundary — manifestation: a batch is half-written when pressure crosses threshold; root cause: pressure check placed inside the batch loop instead of between batches; recovery: only check pressure at operator batch boundaries (17.2 step 4).
  2. Storage amplification exceeding budget under small-batch workloads — root cause: per-batch framing overhead dominates at small batch sizes; recovery: coalesce small batches before spilling, bounded by a max-coalesce-delay.
  3. Orphaned spill files accumulating after repeated worker crashes — root cause: cleanup tied to graceful shutdown, which crash-only workers (P8) never perform; recovery: garbage collection keyed to lease expiry, not process shutdown.

17.7 Performance Concerns

  • Spill write path competes with exchange writes for disk I/O bandwidth — separate I/O queues per purpose to avoid one starving the other.
  • CRC32C computation on the hot spill-write path — use a SIMD-accelerated implementation, not a naive byte-loop.
  • Restore path random-reads across a large spill file — sequential-write, sequential-read layout avoids seek amplification.

17.8 Edge Cases

  • Disk full during spill write — must fail the fragment cleanly (I5-adjacent: a truncated file must never checksum-validate by accident) rather than silently truncating.
  • Object-storage spill tier latency spike — bounded retry (P10) before failing the fragment, never an unbounded wait.
  • Concurrent spill and restore on the same fragment during a retry — the old spill file must be invalidated before a new attempt writes, preventing a stale restore.

17.9 Failure Analysis

A crashed worker's orphaned spill files are detected by the garbage collector on lease expiry (§15's I7) and removed; if object-storage-backed, this is a deferred-delete tagged for a retention sweep rather than a synchronous delete on the hot path. Detection: checksum failure counter and orphan-file-age metric. Blast radius: confined to the fragment that owned the spill file — a corrupted spill never propagates past the operator that reads it, because I5 rejects at the boundary.

17.10 Operational Notes

Metrics: spill_bytes_total, spill_restore_latency_seconds, spill_checksum_failures_total (I5), spill_storage_amplification_ratio (§4 budget). Spans: spill.write, spill.restore, spill.gc_sweep. Log fields: fragment_id, spill_file_path, amplification_ratio. Deployment: local-disk tier requires a dedicated ephemeral volume per worker pod; object-storage tier requires the spill bucket's IAM role bound to the worker service account.

  • fixtures/replay/scheduler-divergence.trace — injected nondeterminism, expects a flagged divergence offset.

  2. Missing event ordering where two events with the same logical timestamp race in the WAL — root cause: no tie-breaking sequence number; recovery: every ReplayRecord carries a monotonic per-fragment sequence number in addition to its timestamp.
  3. Replay WAL amplification where every batch-level event is recorded at full fidelity — root cause: no sampling/coalescing policy; recovery: coalesce high-frequency intra-batch events into periodic snapshots, keep full fidelity only at fragment-lifecycle granularity.

20.7 Performance Concerns

  • WAL write amplification: every fragment event triggers a write — batch WAL appends with a bounded flush interval, trading a small durability window for throughput.

  • Truncated WAL (crash mid-write) — the reader must detect and stop at the last complete record, never interpret a partial record as valid (extends I2).
  • Partial replay metadata (a checkpoint reference to a rotated-away WAL segment) — CLI reports a bounded-replay-window error rather than fabricating missing history.
  • Clock skew between workers producing out-of-order timestamps despite correct sequence numbers — ordering uses the sequence number, timestamp is informational only.

20.9 Failure Analysis

Replay failures emit divergence offsets (the first WAL record where recorded and re-executed state disagree) and checksum mismatches. Detection is on-demand (operator-triggered CLI run) rather than continuous, since replay is a forensic tool, not a live-path check. Blast radius: informational only — a replay failure never affects the original query's already-delivered results, it only limits postmortem confidence.

20.10 Operational Notes

Metrics: wal_sequence_gap_total (I2), replay_divergence_events_total, wal_write_latency_seconds. Spans: replay.wal_append, replay.cli_diff. Log fields: wal_segment_id, divergence_offset, sequence_number. Retention: WAL segments rotated by size and age, archived to object storage per a documented retention policy before local deletion.

  6. Add protocol version negotiation supporting N-1 coordinator compatibility (P7, §25).
  7. Add mTLS between gateway and coordinator, and between coordinator and worker pools (ADR-17), closing the trust-boundary gaps identified in §22.
  8. Wire canary-coordinator rollout support: a canary pool receives a configurable traffic percentage before full rollout.

21.3 Deliverable

A production-hardened client-facing surface: authenticated (OIDC), authorized (RBAC, fail-closed), rate-limited, protocol-versioned SQL and gRPC endpoints with N-1 rolling-upgrade compatibility.

21.4 Acceptance Criteria

  • 100% of unauthenticated requests rejected before reaching the coordinator, across fixtures/gateway/unauthenticated-request.trace.
  • RBAC-denied requests never receive partial results — fixtures/gateway/denied-partial- result.trace shows zero rows returned, not a truncated set.
  • Protocol version negotiation succeeds between an N and N-1 coordinator across fixtures/gateway/rolling-upgrade-compat.trace for 100% of the locked wire-protocol surface.
  • Canary rollout traffic split is accurate to within 2% of configured percentage across 10,000 synthetic requests.

21.5 Conformance Fixtures

  • fixtures/gateway/unauthenticated-request.trace — missing/invalid token, expects rejection.
  • fixtures/gateway/denied-partial-result.trace — RBAC deny mid-fan-out, expects zero rows.
  • fixtures/gateway/rolling-upgrade-compat.trace — N/N-1 protocol negotiation.
  • fixtures/gateway/rate-limit-burst.trace — burst above the configured rate, expects throttling not admission.
  • fixtures/gateway/malformed-grpc-frame.trace — malformed protobuf frame, expects a clean protocol error, never a panic.

21.6 Pitfalls

  1. Authentication bypass via a malformed-but-parseable token that skips signature validation — root cause: permissive JWT library defaults; recovery: explicit algorithm allowlist, reject alg: none.
  2. RBAC fail-open under a catalog outage if the policy-evaluation error path isn't audited — root cause: an exception path that defaults to allow; recovery: every policy-evaluation error path is unit-tested to assert deny (P12).
  3. Protocol version negotiation silently downgrading to a lossy compatibility mode — root cause: no explicit warning when N-1 compatibility drops a feature; recovery: surface a client-visible compatibility-mode header.

21.7 Performance Concerns

  • mTLS handshake overhead on connection establishment — connection pooling/reuse at the gateway amortizes this across many queries per client.
  • Gateway-level rate limiting must not become a serialization point — token-bucket implementation sharded per tenant, not a single global lock.
  • Protocol translation (SQL wire protocol / gRPC) must not re-serialize RecordBatch data twice — share the Arrow IPC framing used internally (§16) end to end where the client protocol allows.

21.8 Edge Cases

  • Token expiring mid-session (long-running streaming query) — session must re-validate on a configured interval, not just at connection start.
  • Canary pool receiving disproportionate traffic due to a load-balancer hashing quirk — traffic- split metric must be monitored, not assumed correct from configuration alone.
  • Malformed gRPC frames from a misbehaving or malicious client — must produce a protocol error, never a panic that could be a DoS vector (§22).

21.9 Failure Analysis

An authz outage (identity provider unreachable) fails closed cluster-wide (P12) — no new sessions authenticate, existing sessions run to completion under their already-validated token until expiry. Blast radius: total for new traffic, zero for in-flight authorized work. Detection: OIDC provider health check feeding a dedicated authz_provider_unreachable alert distinct from general catalog unavailability.

21.10 Operational Notes

Metrics: gateway_requests_rejected_total{reason}, authz_decision_latency_seconds, rate_limit_throttled_total, canary_traffic_split_ratio. Spans: gateway.authenticate, gateway.authorize, gateway.admit. PhaseDeferred("§21"): federated write transactions across sources are out of scope for Phase 9 — registered in §35.

24. Operational Readiness

Metrics strategy. Every subsystem exports the counters/histograms/gauges named in its own N.10 Operational Notes; the union is the on-call dashboard. Required cluster-level rollups: query latency percentiles, fragment latency percentiles, spill bytes, scheduler queue depth, worker utilization, connector latency per source, replay divergence count, availability against the §4 error budget.

Alerting philosophy. Page only on: sustained query failure rate above a rolling baseline, replay corruption (WAL checksum failure, FM-2/FM-7 adjacent), scheduler saturation (I9 cap sustained), metadata catalog unavailability (FM-3), authz provider outage (FM-9). Everything else is a dashboard signal, not a page — this bounds on-call fatigue and keeps pages meaningful (P5's observability-first principle is undermined by alert noise as much as by missing telemetry).

Deployment strategy. Rolling upgrades with N-1 coordinator compatibility (P7, §25); canary coordinators receiving a configurable traffic percentage before full rollout (§21.2); immutable, digest-pinned container images (ADR-16, ADR-19); version-gated protocol upgrades so a client never silently talks to an incompatible coordinator.

Runbook discipline. Every FM row in §23 has a corresponding docs/runbooks/ entry (§37); a new failure mode discovered in production gets a new FM row and a new runbook in the same change, never a runbook without a corresponding table row.

25. Compatibility & Versioning

Wire compatibility. Protobuf backward compatibility is required for every field ever shipped (P7) — field removal is forbidden, only deprecation; the gRPC service surface (federation.proto, §10) follows additive-only evolution.

Storage compatibility. The replay WAL (§20) evolves append-only — a new ReplayEventType variant is additive, an old variant is never removed while any retained WAL segment could contain it (§20.10 retention policy bounds how long that obligation lasts).

API stability. Semver enforced end-to-end: a breaking change to the SQL wire protocol or gRPC surface requires a major version bump and a documented migration path; minor versions are strictly additive.

Rolling upgrades. N-1 coordinator compatibility is mandatory (§21.2) — a coordinator running version N must correctly serve fragments dispatched by, and dispatch fragments to, a worker running version N-1, for the duration of a rolling upgrade window.

Schema compatibility. Catalog schema evolution is additive-only (I4, P9) — column IDs never reorder, and a compatibility validator runs in CI against every schema-migration fixture in fixtures/catalog/ before merge.

Connector capability compatibility. A connector declaring a new ConnectorCapability flag (§11) must default it false for any client that predates the flag's introduction, preserving I10's guarantee that pushdown never exceeds a declared capability.

26. Testing & Verification Strategy

Required layers. Unit testing (per-crate, fast feedback); integration testing (cross-crate, against real Postgres/MySQL/Parquet fixtures in connectors/); distributed chaos testing (worker crash, network partition, clock skew — driving §15/§16's fixtures); fuzzing (cargo-fuzz, ADR-13, gating §13's parser and any other untrusted-input boundary); deterministic replay validation (§20, asserting P1 end to end); performance regression testing (§28's benchmark harness, gating on the §4 targets table in §28); compatibility testing (§25's N-1 rolling-upgrade fixture suite).

Fault injection. The conformance simulator (§7, conformance/src/runner.rs) injects: worker crashes (exercising I3/I7), packet loss and reordering (exercising I14's reorder buffer), spill corruption (exercising I5), clock skew (exercising P14/I2), and connector throttling (exercising P10). Every injected fault maps to exactly one invariant assertion per §7's debugging methodology — never a combined "did anything go wrong" check.

Fixture governance. Every fixture referenced anywhere in §12–§21's N.5 subsections is checked into the conformance/ or per-crate fixtures/ tree; a fixture referenced in a blueprint section but absent from the tree is a CI-blocking lint failure, not a documentation gap.

27. Build & Release Engineering

Build guarantees. Reproducible builds (bit-identical container digest across two independent CI runs, ADR-19); SBOM generation on every release artifact; artifact signing (cosign or equivalent) gating deployment (T7's mitigation); dependency auditing via cargo-vet (ADR-03) on every dependency bump.

Release channels. Nightly (every merge to main, unsupported); beta (weekly cut, feature- complete but unproven under load); stable (monthly cut, the default operator target); LTS (quarterly cut, extended patch support for air-gapped/enterprise deployments per §1's deployment model).

CI/CD pipeline. Lint (cargo clippy -D warnings), unit tests, fuzz smoke tests (a bounded-time slice of the full fuzz corpus, ADR-13), integration cluster spin-up against real connector fixtures, benchmark regression gate (§28's targets table) — a release that regresses any M1–M12 target beyond its documented tolerance fails the pipeline, not just a warning.

Packaging. Per-crate cargo workspace members produce independently versioned container images (ADR-15); templates/k8s-*.yaml (§10) are the canonical deployment manifests, kept in lockstep with the coordinator/worker image tags they reference.

29. Scalability Analysis

Bottlenecks. Scheduler coordination (registry/lease contention, §15.7) is the first coordinator-side ceiling; metadata hotspotting (§19.7) on frequently-queried catalog objects is the second; connector throughput (§18.7, bounded by the slowest source per "The Tail at Scale") is the cross-cluster ceiling; exchange serialization (§16.7) is the per-query intra-cluster ceiling.

Scaling model. Stateless coordinators scale horizontally behind the gateway (§21) — adding a coordinator replica adds session capacity linearly up to the shared metadata-catalog's connection limit. Workers autoscale independently on scheduler_queue_depth and memory_tracker_pressure_ratio jointly (§16.10) — this is why those two metrics, not CPU alone, drive the horizontal pod autoscaler. The catalog is scaled vertically first (larger PostgreSQL instance, ADR-04) before sharding, since §4's 10M-object ceiling fits comfortably on a single well-resourced instance (§32 C10) — horizontal catalog sharding is deferred until that ceiling is approached in practice, not designed for speculatively.

Cross-cutting limit. The single hardest ceiling is aggregate connector throughput to a fixed set of source systems that the federation engine does not control — no amount of coordinator or worker scaling increases what PostgreSQL or MySQL can sustain upstream; §18's per-source connection pooling and §28's per-source latency metrics exist specifically to make that ceiling visible before it becomes an incident.

30. Mental Models & First Principles

  • MM1 — The Tail at Scale. Fan-out latency is bounded by the slowest participant, not the average · predicts p99 degrades disproportionately as source count grows · without it: no per-source timeout, one slow source hangs the whole query · applies in §18.
  • MM2 — Push What You Can Prove. Pushdown is only sound when declared capability matches source semantics exactly · predicts silent correctness bugs from assumed capabilities · without it: engineers push a filter a source can't actually apply correctly · applies in §14.
  • MM3 — Spill Is Steady-State, Not an Exception. Memory pressure under adversarial cardinality is expected, not rare · predicts under-invested spill/checksum code paths fail in production first · without it: spill is untested until an incident teaches the lesson · applies in §17.
  • MM4 — Leases With Fencing Beat Locks Under Partition. A time-bounded lease with a monotonic fencing epoch survives a network partition; a lock does not · predicts split-brain in any scheduler that skips the epoch · without it: two workers both believe they own a fragment · applies in §15.
  • MM5 — Determinism Must Be Structural, Not Disciplinary. Any wall-clock read anywhere eventually breaks replay · predicts intermittent, hard-to-reproduce divergence, never a clean failure · without it: "it worked in testing" nondeterminism bugs surface only in production · applies in §20.
  • MM6 — Schema IDs Are a One-Way Ratchet. Column IDs are a contract binding every in-flight and cached plan · predicts a "harmless" renumbering silently reads the wrong column · without it: schema evolution breaks consumers that never touched the migrating code path · applies in §19.
  • MM7 — Fail Closed Beats Fail Fast for Governance. An unevaluatable policy must deny, not error open · predicts a catalog outage during a security-sensitive window stays safe by default · without it: an exception handler silently becomes an authorization bypass · applies in §21.
  • MM8 — Cost Models Bound Regret, They Don't Predict Truth. Every cardinality estimate is wrong by some margin; the optimizer's job is a bounded-regret decision under a timeout · predicts any optimizer without a fallback path eventually hangs on an adversarial plan · without it: no plan B when statistics are absent or wrong · applies in §14.

32. Back-of-Envelope Capacity Model

  • C1 — Coordinator session capacity. 8 GB coordinator ceiling ÷ ~16 MB average QueryHandle + session state = 512 ≈ 500 concurrent queries, matching the §4 cap exactly.
  • C2 — Worker usable memory before spill. 32 GB worker ceiling × 70% spill threshold = 22.4 GB usable before the memory tracker (§16) arms the spill signal.
  • C3 — Hash-join build-side RAM. 40,000,000 build-side rows × 56 B/entry = 2.24 GB + 18% Robin-Hood open-addressing slack = 2.64 GB, inside the 22.4 GB usable ceiling from C2.
  • C4 — Scheduler fragment metadata footprint. 100,000 max queue depth × ~2 KB/fragment metadata = 200 MB, well under the 8 GB coordinator ceiling (§4).
  • C5 — Max fragments per query. 100,000 scheduler queue depth ÷ 10 assumed concurrent large queries = 10,000 fragments/query, matching the §4 cap exactly.
  • C6 — Aggregate scan throughput. 8 MB result-streaming chunk × 1,250 chunks/sec sustained across the worker pool = 10 GB/s, matching the §4 target throughput exactly.
  • C7 — Spill restore throughput floor. 4 GB spilled table × 1.5x storage amplification (§4) = 6 GB on-disk representation ÷ 60 s RTO (§4) = 100 MB/s minimum sequential-read throughput required of the spill tier.
  • C8 — File descriptor budget per fleet. 200,000 max FDs (§4) ÷ (4 FDs per connector connection + 2 per open spill file) = 33,333 concurrent connector connections plus spill files sustainable per fleet.
  • C9 — Monthly error budget. 99.95% availability target (§4) × 43,200 min/30-day month → (1 − 0.9995) × 43,200 = 21.6 ≈ 21 min/month, matching the §4 error budget exactly.
  • C10 — Catalog table size. 10,000,000 max catalog objects (§4) × ~200 B average row size = 2 GB catalog table size, comfortably inside single-instance PostgreSQL scale (ADR-04), the basis for §29's vertical-first catalog scaling decision.

34. Alternative Architectures (Roads Not Taken)

Alt A — Single-Node Vectorized Engine

        +-------------------------------+
        | single process                |
        |  parser -> planner -> exec    |
        |  vectorized morsel scheduler  |
        |  direct file/source access    |
        +-------------------------------+

Regime where it wins: a single analyst's laptop or a single-tenant BI workload that fits in one machine's memory — no distributed coordination overhead at all. Real system: DuckDB (§5). Why rejected here: §1's target operators include multi-tenant platform teams serving many concurrent BI/ML consumers against 32 GB+ working sets and 10 heterogeneous source systems simultaneously — a single process cannot isolate tenants (I6) or scale past one machine's memory ceiling.

Alt B — Storage-Owning MPP Warehouse

        +------------+   +------------+   +------------+
        | shard node |   | shard node |   | shard node |
        | owns data  |   | owns data  |   | owns data  |
        +-----+------+   +-----+------+   +-----+------+
              \_______________|________________/
                     distributed query layer

Regime where it wins: workloads where the large majority of queries hit engine-native storage and federation is the rare exception. Real system: ClickHouse (§5, §31). Why rejected here: §1's non-goals explicitly exclude owning primary data persistence — the entire point of this project is virtualizing over heterogeneous, pre-existing, autonomously-owned sources, not replacing them.

Alt C — View-Only Data Virtualization

   client -> [virtual view layer] -> pushdown-or-fail -> source A / source B / source C
                    (no distributed execution engine of its own)

Regime where it wins: environments where every query can be fully pushed down to a single capable source with no cross-source join or aggregation ever required. Real system: classic data- virtualization products in the Denodo/Dremio lineage when operated in pure pass-through mode. Why rejected here: §1 explicitly requires cross-source joins and distributed execution when pushdown is incomplete (§14's pushdown negotiation assumes an engine-side fallback exists, §16) — a view- only layer cannot answer a query spanning two sources with no shared execution engine.

Alt D — Serverless Function-per-Fragment

   scheduler -> invoke(fragment) -> ephemeral function (cold start, no persistent state)
                                 -> invoke(fragment) -> ephemeral function

Regime where it wins: highly bursty, infrequent query workloads where idle worker-pool cost dominates and cold-start latency is acceptable. Real system: AWS Athena's underlying serverless execution model. Why rejected here: §4's p50 startup budget (< 150 ms) and worker startup budget (< 15 s, itself already a compromise) are incompatible with per-fragment cold starts at the 10,000-fragment-per-query scale in §32 C5 — persistent worker pools amortize startup cost across fragments, which a per-invocation serverless model cannot.

36. Glossary

  • Fragment — an executable physical query unit dispatched to exactly one worker at a time (I3).
  • Pushdown — delegating filter/projection/aggregation/join/limit execution to a source (§8).
  • Spill — disk- or object-storage-backed overflow for a memory-bounded operator (§17).
  • Exchange — bounded inter-worker RecordBatch stream between execution fragments (§16).
  • Replay WAL — append-only deterministic execution log (§20, I2).
  • Coordinator — the query/session lifecycle authority (§12).
  • Connector — an isolated source-integration runtime (§18).
  • Operator DAG — the physical execution graph a fragment executes (§11).
  • Cardinality — an estimated or actual row count used by the optimizer (§14).
  • Admission Control — the throttling subsystem bounding concurrent query/fragment intake (§15, §21).
  • Stage — a grouped boundary of fragments sharing a logical pipeline step (§11).
