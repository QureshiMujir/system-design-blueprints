⬜ Phase 0 — Workspace Bootstrap & Correctness Kernel §12

Objectives
  • Establish the Cargo workspace and per-crate manifest structure from §10.
  • Stand up a runnable coordinator binary with health/readiness/metrics endpoints only — no query path yet.
  • Establish observability (structured logging, OpenTelemetry, Prometheus) that every later phase depends on (P5).
  • Establish the deterministic simulator harness (§7) that will assert I1–I14 as they come online.
Deliverable

A runnable coordinator exposing /healthz, /readyz (fails until telemetry connects), and /metrics, plus structured JSON logs carrying a trace-context field on every line — the correctness kernel (ID allocation, config, telemetry, panic handling) every later phase builds on.

Acceptance
  • Cold start to /readyz 200 in < 2 s (§4), p99 across 50 runs.
  • configs/valid-basic.toml loads clean; configs/invalid-port.toml rejects with a field-located diagnostic.
  • /metrics scrape returns ≥ 12 registered series (ADR-11).
  • CI green on main for 10 consecutive commits, zero flake; container digest reproducible across two independent CI runs (ADR-19).
Fixtures
  • fixtures/config/valid-basic.toml — minimal valid config, clean startup.
  • fixtures/config/invalid-port.toml — malformed port, field-located rejection.
  • fixtures/config/env-override-conflict.toml — env vs file disagreement, env wins (documented).
  • fixtures/traces/bootstrap-success.json — golden span tree for clean startup.
  • fixtures/replay/id-collision-injected.trace — forces two allocations to collide, exercises I1.
Pitfalls
  1. Async runtime starvation from a blocking filesystem read during config load — manifestation: readiness latency spikes; root cause: blocking syscall on the Tokio executor; debugging: tokio-console starvation view; recovery: spawn_blocking for all file I/O.
  2. Logging cardinality explosion from labeling metrics with a per-query identifier before query traffic exists — root cause: unbounded label cardinality; signal: TSDB memory growth; recovery: trace correlation instead of per-query labels (P5).
  3. Panic hook double-fires under a nested panic — manifestation: crash log missing/duplicated; root cause: hook not itself panic-safe; recovery: allocation-free, re-entrant-guarded hook.

⬜ Phase 1 — SQL Parser & Logical Planner §13

Objectives
  • Implement the locked SQL:2016 subset grammar (§5) as lexer + parser-combinator pipeline.
  • Produce a normalized AST and a semantically validated logical operator DAG against the catalog.
  • Establish deterministic query hashing for later cache-key and replay correlation.
  • Establish parser fuzzing (ADR-13) as a standing CI gate before optimizer logic exists.
Deliverable

A parser/planner pair that, for any query in the §5 subset, produces either a validated logical DAG or a source-located diagnostic — never a panic, never a silently wrong plan.

Acceptance
  • Parser conformance suite (fixtures/parser/*.sql) passes ≥ 95%.
  • Malformed-query fixtures produce byte-identical diagnostics across 100 repeated runs (P1).
  • Zero parser panics across 1,000,000 cargo-fuzz iterations (ADR-13).
  • Query hashing yields identical hashes for whitespace/case variants across 500 paired fixtures.
Fixtures
  • fixtures/parser/select-basic.sql — single-table projection, 3-node logical DAG.
  • fixtures/parser/join-nested.sql — three-way nested join, correct pre-reorder tree shape.
  • fixtures/parser/malformed-missing-from.sql — diagnostic citing the missing FROM clause.
  • fixtures/parser/malformed-invalid-group.sql — non-aggregated column with GROUP BY, semantic (not syntax) diagnostic.
  • fixtures/parser/replay-query-hash-stability.trace — hash stability across whitespace/case.
Pitfalls
  1. Ambiguous grammar around nested/correlated subqueries — manifestation: accept/reject flips on near-identical inputs; root cause: combinator rule-ordering sensitivity; recovery: explicit disambiguation rule plus regression fixture.
  2. AST ownership cycles normalizing self-referential constructs — manifestation: stack overflow; root cause: unbounded recursive traversal; recovery: bounded traversal depth with a diagnostic.
  3. Catalog lookup races during concurrent analysis of a mid-migration schema — manifestation: nondeterministic validation for the same query; recovery: pin the catalog snapshot version at query-start (I11).

⬜ Phase 2 — Cost-Based Optimizer & Statistics §14

Objectives
  • Implement cost-based physical planning: join reordering, cardinality estimation, pushdown negotiation against ConnectorCapability (I10).
  • Bound optimization time so a pathological join graph cannot blow the p95 latency budget (§4).
  • Produce cost-annotated, inspectable plans satisfying P11.
Deliverable

A cost-based optimizer producing physical plans with per-node cost annotations and a full, replayable rule-application trace, deterministic for a fixed catalog snapshot and statistics version.

Acceptance
  • Optimizer output byte-identical across 100 runs against a pinned snapshot (P1).
  • fixtures/optimizer/tpch-q1.sql-class join reordering completes with optimization p95 < 200 ms.
  • fixtures/optimizer/pushdown-filter.sql: 100% of eligible predicates pushed where supports_predicate_pushdown: true, 0% where false (I10, zero tolerance).
  • Timeout budget triggers a fallback (never a hang) on pathological-join-30way.sql within timeout ± 50 ms.
Fixtures
  • fixtures/optimizer/tpch-q1.sql — canonical aggregation, golden-file plan-shape regression.
  • fixtures/optimizer/pushdown-filter.sql — mixed-capability two-source join.
  • fixtures/optimizer/distributed-join.sql — three-source join exercising exchange insertion.
  • fixtures/optimizer/pathological-join-30way.sql — stresses timeout and greedy fallback.
  • fixtures/optimizer/missing-statistics.sql — default-selectivity fallback, not a failure.
Pitfalls
  1. Cardinality explosion on skew where the default-selectivity fallback badly underestimates — root cause: missing statistics silently substituted a generic default; recovery: feed the actual-vs-estimated ratio back as a statistics-refresh trigger (deferred, §35).
  2. Unstable heuristics: logically-equivalent queries (a JOIN b vs b JOIN a) produce different plans — root cause: rule-order sensitivity; recovery: canonicalize the join graph before cost search.
  3. Recursive optimization loops where two rules each treat the other's output as an improvement — root cause: rules not confluent; recovery: enforce a strict cost-decrease invariant per rule application.

⬜ Phase 3 — Distributed Scheduler & Fragment Placement §15

Objectives
  • Implement fragment placement across a dynamic worker pool with bounded admission (I9) and leased ownership (I7, I3).
  • Implement worker heartbeat and failure detection with a bounded failover time.
  • Implement retry orchestration within the fixed retry budget (I12, P10).
Deliverable

A distributed scheduler that places fragments onto a live worker pool, detects and recovers from worker failure within a bounded time, and guarantees via I3/I7 that no fragment ever executes on two workers simultaneously.

Acceptance
  • Worker failover (missed heartbeat to reassignment) < 10 s across 200 injected-crash trials.
  • Zero orphaned fragments across a 10,000-fragment chaos run (fixtures/scheduler/worker- restart.trace).
  • Queue depth never exceeds 100,000 (I9) across a 24-hour soak with sustained overload.
  • Retry budget (3, §4) exhausted correctly on retry-budget.trace — the 4th failure transitions FAILED.
Fixtures
  • fixtures/scheduler/worker-restart.trace — crash mid-execution, reassignment within SLO.
  • fixtures/scheduler/queue-overflow.trace — sustained submission past the I9 cap, rejection.
  • fixtures/scheduler/retry-budget.trace — repeated failure, exhaustion at exactly 3 (I12).
  • fixtures/scheduler/split-brain-injected.trace — two workers claim the same lease, I3 fencing.
  • fixtures/scheduler/duplicate-worker-id.trace — duplicate registration, deterministic rejection.
Pitfalls
  1. Split-brain worker state after a network partition — root cause: lease expiry checked by wall-clock without a fencing token; recovery: monotonically increasing fencing epoch on every dispatch, stale epochs rejected downstream.
  2. Queue starvation where cheap fragments crowd out large ones — root cause: FIFO admission with no fairness dimension; recovery: weighted fair queueing by query.
  3. Retry storms where fragments of a failing query retry in lockstep — root cause: no backoff jitter; recovery: exponential backoff with jitter (extends P10).

⬜ Phase 4 — Execution Engine & Operator Runtime §16

Objectives
  • Build the Arrow-native operator pipeline (scan/filter/project/hash-join/aggregate) implementing the Volcano iterator model (§5, Graefe 1994).
  • Implement inter-worker exchange streams carrying RecordBatch data across fragment boundaries placed in §15.
  • Implement the memory tracker arming the spill trigger (P6) at the §4 threshold; spill mechanics themselves are §17's.
Deliverable

A distributed execution runtime that executes a physical plan's operator DAG across worker fragments, streams RecordBatch results between fragments via bounded exchange channels, and never exceeds its configured memory budget without triggering the spill signal.

Acceptance
  • fixtures/execution/hash-join-large.dataset (10M+ rows, two-source) completes with zero row- count drift versus a single-node reference.
  • Memory tracker fires the spill signal within 100 ms of crossing the 70%-heap threshold across 50 injected-pressure trials.
  • Worker RSS stays under the 32 GB ceiling (§4) across a 1-hour sustained-load soak.
  • Exchange reordering (I14) resolves within the bounded window on exchange-reorder- injected.trace, or fails the fragment deterministically — never silently returns misordered data.
Fixtures
  • fixtures/execution/hash-join-large.dataset — 10M-row two-source join correctness baseline.
  • fixtures/execution/spill-recovery.trace — forces the spill signal mid-join.
  • fixtures/execution/aggregation-overflow.trace — high-cardinality GROUP BY over budget.
  • fixtures/execution/exchange-reorder-injected.trace — malformed delivery, I14's reorder buffer.
  • fixtures/execution/partial-batch-cancel.trace — cancellation mid-batch, no leaked buffers.
Pitfalls
  1. Exchange deadlocks from a cyclic backpressure dependency between two fragments — root cause: an exchange topology with a cycle the physical planner should have rejected; recovery: static cycle rejection upstream in §14, runtime assertion here.
  2. Batch ownership bugs where a RecordBatch buffer is read concurrently after an improperly reference-counted slice — recovery: never manually slice buffers, always use Arrow's buffer- sharing APIs.
  3. Spill corruption surfacing here as wrong row counts after a spill-restore cycle — root cause: checksum validation (I5) not wired into the join's restore path; recovery: treat a restored batch identically to a checksum-fresh one.

⬜ Phase 5 — Spill Subsystem & Memory Governance §17

Objectives
  • Implement the disk-backed spill path (P6) triggered by §16's memory tracker at the §4 70%-heap threshold.
  • Guarantee checksum-validated restore (I5) so a spilled batch is never silently corrupted.
  • Bound storage amplification to the §4 target (< 1.5x) and recovery time to the §4 RTO (< 60 s).
Deliverable

A spill subsystem that transparently overflows any memory-bounded operator (hash join, aggregation) to disk or object storage at the §4 threshold, and restores with checksum-validated integrity within the §4 RTO.

Acceptance
  • Spill-and-restore round trip on fixtures/spill/large-join-spill.dataset produces byte- identical results to the non-spilled reference computation.
  • Restore RTO < 60 s (§4) for a 4 GB spilled table across 20 trials.
  • Storage amplification < 1.5x (§4) measured across 10 mixed-cardinality fixtures.
  • A corrupted spill file (fixtures/spill/checksum-corrupt.dataset) is rejected 100% of the time, never silently restored (I5).
Fixtures
  • fixtures/spill/large-join-spill.dataset — forces spill mid-join, correctness baseline.
  • fixtures/spill/checksum-corrupt.dataset — bit-flipped spill file, expects I5 rejection.
  • fixtures/spill/orphaned-lease-cleanup.trace — expired lease with an orphaned spill file, expects garbage collection.
  • fixtures/spill/object-storage-spill.trace — distributed-mode spill tier round trip.
  • fixtures/spill/partial-write-crash.trace — crash mid-spill-write, expects a truncated-file detection, not a false-positive checksum pass.
Pitfalls
  1. Spilling mid-batch instead of at a batch boundary — manifestation: a batch is half-written when pressure crosses threshold; root cause: pressure check placed inside the batch loop instead of between batches; recovery: only check pressure at operator batch boundaries (17.2 step 4).
  2. Storage amplification exceeding budget under small-batch workloads — root cause: per-batch framing overhead dominates at small batch sizes; recovery: coalesce small batches before spilling, bounded by a max-coalesce-delay.
  3. Orphaned spill files accumulating after repeated worker crashes — root cause: cleanup tied to graceful shutdown, which crash-only workers (P8) never perform; recovery: garbage collection keyed to lease expiry, not process shutdown.

⬜ Phase 6 — Connector SDK & Source Integrations §18

Objectives
  • Implement the connector abstraction (lifecycle, capability declaration, retry policy) that every source integration implements.
  • Deliver the first three source integrations: PostgreSQL, MySQL, Parquet.
  • Enforce connector isolation (P4) so a single misbehaving source cannot destabilize the cluster.
Deliverable

Operational federated query support against three real backends, each declaring an accurate ConnectorCapability, each isolated from the others' failures (P4), each retry-bounded (I12).

Acceptance
  • fixtures/connectors/postgres-pushdown.sql validates 100% capability-correct pushdown (I10).
  • Schema discovery is deterministic — identical ConnectorCapability and schema across 50 repeated registrations against a fixed source version.
  • fixtures/connectors/mysql-timeout.trace: connector failure is isolated — the coordinator and other connectors remain healthy (P4), measured by zero cross-connector error correlation.
  • Parquet partition pruning eliminates 100% of non-matching partitions on fixtures/connectors/parquet-partition.dataset.
Fixtures
  • fixtures/connectors/postgres-pushdown.sql — predicate/projection/limit pushdown validation.
  • fixtures/connectors/parquet-partition.dataset — partition-pruning correctness.
  • fixtures/connectors/mysql-timeout.trace — connector RPC timeout, isolation validation.
  • fixtures/connectors/schema-drift-mid-query.trace — source schema changes mid-query.
  • fixtures/connectors/auth-token-expired.trace — expired credential mid-session.
Pitfalls
  1. Connector resource leaks (unreturned pool connections) under repeated retries — root cause: retry path not wrapped in an RAII guard; recovery: connection checkout tied to Drop.
  2. Translation mismatches where a pushed-down predicate changes semantics across dialects (e.g. NULL-handling in comparisons) — root cause: naive expression-string translation; recovery: dialect-aware translation table with explicit NULL-semantics tests per source.
  3. Pool exhaustion under a slow source holding connections past their useful lifetime — root cause: no connection-level timeout independent of the query-level retry budget; recovery: per-connection idle/max-lifetime timeouts.

⬜ Phase 7 — Metadata Catalog & Governance §19

Objectives
  • Implement the centralized metadata catalog: schema registry, connector registry, statistics cache, governance policy metadata.
  • Enforce tenant isolation (I6) and RBAC (P12) at the catalog layer.
  • Implement schema versioning that never reorders column IDs (I4, P9).
Deliverable

A queryable, versioned, tenant-isolated metadata catalog that the optimizer (§14), connectors (§18), and authz (§21) all read, and only the catalog itself writes.

Acceptance
  • Schema evolution validated: fixtures/catalog/schema-evolution-v2.json accepted (additive), a column-ID-reordering variant rejected 100% of the time (I4).
  • RBAC enforced: fixtures/catalog/denied-access.trace produces a deny decision in 100% of ambiguous-policy trials (P12 fail-closed).
  • Metadata cache coherent: a write is visible to a subsequent read within one cache-invalidation cycle (< 100 ms), verified across 200 write-then-read trials.
  • Catalog lookup p95 < 20 ms (§4) under a 10,000-object working set.
Fixtures
  • fixtures/catalog/schema-evolution-v2.json — additive schema change, accepted.
  • fixtures/catalog/schema-reorder-rejected.json — column-ID reorder, rejected (I4).
  • fixtures/catalog/denied-access.trace — ambiguous RBAC policy, expects deny (P12).
  • fixtures/catalog/tenant-cross-read-attempt.trace — cross-tenant read, expects I6 denial.
  • fixtures/catalog/concurrent-schema-write.trace — two concurrent migrations, expects I11's monotonicity to serialize them.
Pitfalls
  1. Stale cache propagation after a write during a partial network partition between cache and source of truth — root cause: invalidation message lost; recovery: bounded cache TTL as a backstop even when invalidation is expected to be immediate.
  2. Policy drift where an RBAC rule's intent diverges from its evaluated behavior after an unrelated schema change — root cause: policy rules referencing column names, not stable IDs; recovery: policies bind to column IDs (I4's stability guarantee extends here).
  3. Conflicting concurrent schema updates from two operators — root cause: no optimistic- concurrency check on catalog writes; recovery: version-check-and-set writes, second writer retries against the new version (I11).

⬜ Phase 8 — Observability & Deterministic Replay §20

Objectives
  • Implement the append-only replay WAL (I2) capturing every fragment lifecycle event.
  • Implement deterministic replay: reconstruct a query's exact execution sequence from the WAL alone (P1).
  • Implement replay divergence detection so a non-reproducible replay is caught, not silently accepted.
Deliverable

A replay-engine that reconstructs any completed query's exact fragment/event sequence from the append-only WAL, and a CLI that detects and localizes divergence between a recorded and a re-executed run.

Acceptance
  • Deterministic replay reproducible: fixtures/replay/replay-consistency.trace replays byte- identical across 50 trials (P1).
  • Replay divergence detectable: fixtures/replay/scheduler-divergence.trace (deliberately nondeterministic input) is flagged within one CLI invocation, with a divergence offset reported.
  • WAL write latency does not add more than 5% overhead to fragment dispatch latency, measured against §16's execution-latency baseline.
  • Checksum mismatches (I5-adjacent, applied to WAL records too) are detected on 100% of injected corruption fixtures.
Fixtures
  • fixtures/replay/replay-consistency.trace — clean run, expects byte-identical replay.
  • fixtures/replay/scheduler-divergence.trace — injected nondeterminism, expects a flagged divergence offset.
  • fixtures/replay/truncated-wal.trace — WAL cut mid-record, expects graceful truncation handling.
  • fixtures/replay/partial-replay-metadata.trace — incomplete checkpoint, expects a documented replay-from-last-good-offset fallback.
  • fixtures/replay/clock-skew-injected.trace — nonmonotonic timestamp injected, expects I2's ordering guard to reject the record.
Pitfalls
  1. Non-deterministic clocks breaking replay determinism — root cause: a code path reading wall clock instead of the monotonic clock (violates P14); recovery: lint rule banning direct SystemTime::now() outside the display-formatting layer.
  2. Missing event ordering where two events with the same logical timestamp race in the WAL — root cause: no tie-breaking sequence number; recovery: every ReplayRecord carries a monotonic per-fragment sequence number in addition to its timestamp.
  3. Replay WAL amplification where every batch-level event is recorded at full fidelity — root cause: no sampling/coalescing policy; recovery: coalesce high-frequency intra-batch events into periodic snapshots, keep full fidelity only at fragment-lifecycle granularity.

⬜ Phase 9 — SQL/gRPC Gateway, AuthZ & Production Hardening §21

Objectives
  • Implement the client-facing sql-gateway and grpc-api protocol front ends (§1 Phase 0 deliverable items 13–14).
  • Implement authz: OIDC token validation and RBAC policy enforcement at the edge (P12).
  • Harden the end-to-end path for production: semver-governed wire compatibility (P7), N-1 rolling upgrade support (§25).
Deliverable

A production-hardened client-facing surface: authenticated (OIDC), authorized (RBAC, fail-closed), rate-limited, protocol-versioned SQL and gRPC endpoints with N-1 rolling-upgrade compatibility.

Acceptance
  • 100% of unauthenticated requests rejected before reaching the coordinator, across fixtures/gateway/unauthenticated-request.trace.
  • RBAC-denied requests never receive partial results — fixtures/gateway/denied-partial- result.trace shows zero rows returned, not a truncated set.
  • Protocol version negotiation succeeds between an N and N-1 coordinator across fixtures/gateway/rolling-upgrade-compat.trace for 100% of the locked wire-protocol surface.
  • Canary rollout traffic split is accurate to within 2% of configured percentage across 10,000 synthetic requests.
Fixtures
  • fixtures/gateway/unauthenticated-request.trace — missing/invalid token, expects rejection.
  • fixtures/gateway/denied-partial-result.trace — RBAC deny mid-fan-out, expects zero rows.
  • fixtures/gateway/rolling-upgrade-compat.trace — N/N-1 protocol negotiation.
  • fixtures/gateway/rate-limit-burst.trace — burst above the configured rate, expects throttling not admission.
  • fixtures/gateway/malformed-grpc-frame.trace — malformed protobuf frame, expects a clean protocol error, never a panic.
Pitfalls
  1. Authentication bypass via a malformed-but-parseable token that skips signature validation — root cause: permissive JWT library defaults; recovery: explicit algorithm allowlist, reject alg: none.
  2. RBAC fail-open under a catalog outage if the policy-evaluation error path isn't audited — root cause: an exception path that defaults to allow; recovery: every policy-evaluation error path is unit-tested to assert deny (P12).
  3. Protocol version negotiation silently downgrading to a lossy compatibility mode — root cause: no explicit warning when N-1 compatibility drops a feature; recovery: surface a client-visible compatibility-mode header.
