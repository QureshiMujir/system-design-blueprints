ADR-01

Implementation language

Chosen

Rust, edition 2021, MSRV 1.78

Rejected

C/C++; Python; Java; Haskell; OCaml; Go

When the rejected choice is right

C would be chosen if the engine must embed inside an existing C-based verifier toolchain with strict ABI stability requirements (e.g., a legacy SPIN plugin). Python wins for rapid prototype phases where verification is a script that calls an external solver and correctness is asserted via Spot.

Why: Automata construction + graph emptiness + trace eval are pointer/graph-heavy + hot. Rust enums + exhaustive match model Formula/Nba/Ngba/Verdict as zero-cost tagged unions; bitset AP valuations + arena automaton states give cache-friendly perf with memory safety. C/C++ = memory-unsafe on-the-fly automaton graphs; Python/Java = nested DFS + product too hot for GC + boxing; Haskell/OCaml = strict mutable DFS-coloring + on-the-fly build fight laziness/GC.

ADR-02

Project decomposition

Chosen

7-crate Cargo workspace: tl-syntax, tl-formula, tl-trace, tl-automata, tl-eval, tl-monitor, tl-cli

Rejected

Single monolithic crate; 2 crates (lib+bin); 12+ micro-crates

When the rejected choice is right

A monolith wins when the team is a solo developer shipping quickly without needing tl-monitor as an independent embedded library. 12+ micro-crates win when the formula AST and the automata layer are independently versioned and distributed to separate teams consuming only one crate each.

Why: One concern per crate -> independent test surfaces + clean dep DAG (syntax->formula->trace->automata->eval->monitor->cli). Monolith = no enforced layering, slow incremental builds. Micro-crates = version churn + dep-graph noise with no benefit at this scale. DAG is acyclic by construction; cli is the only std member.

ADR-03

Crate-level no_std policy

Chosen

tl-formula, tl-trace, tl-automata, tl-eval, tl-monitor, tl-syntax are no_std + alloc; only tl-cli is std

Rejected

All crates std; whole workspace no_std (incl. cli)

When the rejected choice is right

All-std wins when the engine will never target embedded or no_std environments and the cost of maintaining no_std compatibility (no std::collections, manual alloc error handling) outweighs the embedding benefit.

Why: Core engine embeddable in RV/embedded monitors (tl-monitor on-device). alloc suffices for Vec/Box AST + automaton arenas. std-everywhere blocks embedding; no_std cli is pointless (needs files/argv/stdout for HOA/dot). I/O + filesystem live solely in tl-cli.

ADR-04

Formula AST representation

Chosen

Single unified Formula enum covering LTL + CTL + past-LTL + LTLf operators; Kind enum classifies well-formedness post-parse

Rejected

Separate LtlFormula/CtlFormula/PastFormula types; trait-object AST; untyped s-expression tree

When the rejected choice is right

Separate typed formulas win when the logics diverge significantly in future (e.g., adding MTL/TCTL with time-bounds that require a fundamentally different AST node type), making a unified enum unwieldy. Trait objects win when the logic set is open-ended and plugins must add operators at runtime without recompiling the core.

Why: Shared nnf(), closure(), simplify, pretty-printer over ONE type; CTL fuses path-quantifier+temporal-op into single variants (Ex,Au,…) so the state-vs-path distinction is enforced by Kind + well-formedness, not by separate types. Separate types = 3x duplicated traversals + lossy conversions. Trait objects = no exhaustive match, heap-indirection on hot eval paths.

ADR-05

NNF as algorithmic precondition

Chosen

nnf(&Formula)->Formula pushes negation onto atoms only; GPVW + CTL labeling + progression all assume NNF

Rejected

Carry arbitrary Not; on-the-fly negation handling in each algorithm

When the rejected choice is right

In-place negation wins when the formula is only evaluated once and the one-time NNF pass costs more than the occasional in-evaluator Not-dispatch (e.g., a single-shot web-service that runs progress exactly once per request with a small formula).

Why: Dualities (not X = X not; not(p U q)=(not p) R (not q); not F=G not; not G=F not; not(EX)=AX(not)) applied once. Fixed positive operator set shrinks GPVW node alphabet + labeling cases. Arbitrary Not = combinatorial special-cases in every evaluator + duplicated closure entries. NNF is idempotent + size-linear.

ADR-06

LTL->automaton algorithm

Chosen

GPVW on-the-fly tableau: ltl_to_ngba(&Formula)->Ngba

Rejected

LTL2BA (Gastin-Oddoux, very-weak alternating automata); Safra/Safraless determinization; tableau-free (Couvreur); direct Spot port

When the rejected choice is right

LTL2BA wins when minimizing automaton state count is critical (its VWAA route often yields smaller automata than GPVW on safety/liveness patterns). Safra determinization wins when the application requires a deterministic Büchi automaton (e.g., quantitative or probabilistic model checking where nondeterminism is disallowed).

Why: GPVW (Gerth-Peled-Vardi-Wolper 1995) builds nodes lazily from current/next obligation sets over the subformula closure -> matches the explicit-state philosophy + is the canonical teaching/reference construction. Builds only reachable nodes (on-the-fly). LTL2BA/Safra add alternating/determinization machinery out of scope; Safra needed only for determinization (not required for emptiness).

ADR-07

Buchi flavor + reduction

Chosen

Build generalized Buchi Ngba (one accept set per Until-eventuality) then degeneralize(&Ngba)->Nba (counter construction)

Rejected

Construct a deterministic-acceptance Buchi directly; transition-based generalized Buchi (TGBA) as the terminal form; keep Ngba and check generalized emptiness directly

When the rejected choice is right

TGBA terminal form wins when targeting Spot's twa_graph directly for interop, since Spot operates natively on TGBA and conversion to NBA bloats state count by the acceptance-set count factor. Generalized-emptiness-directly wins in a research context where the degeneralization state blowup is measured as unacceptably large.

Why: GPVW naturally yields generalized acceptance (one set per U); degeneralization on (state x counter 0..k) advancing through accept sets is textbook + lets the downstream product/emptiness assume a single accept set (Nba.accept: Vec<usize>). Direct Buchi = re-derive acceptance bookkeeping. TGBA terminal form would complicate product + nested DFS contract.

ADR-08

Emptiness / counterexample algorithm

Chosen

Nested DFS (Courcoubetis-Vardi-Wolper-Yannakakis): emptiness(&Nba)->Option<Lasso>

Rejected

SCC-based (Tarjan) emptiness; one-pass Couvreur SCC; CEGAR

When the rejected choice is right

SCC-based (Tarjan) emptiness wins in parallel model checkers where SCC decomposition can be distributed (nested DFS is inherently sequential due to its DFS-coloring invariant). Couvreur one-pass wins when the acceptance condition is generalized (TGBA) and you want to avoid degeneralization before the emptiness check.

Why: Nested DFS = memory-efficient (2-bit coloring/state), finds a reachable accepting cycle, and directly extracts a Lasso{stem,cycle} counterexample for check_ltl. Outer DFS finds accepting states; inner DFS seeks a path back -> the cycle. SCC/Tarjan returns components, not a ready lasso witness, and needs extra reconstruction. Nested DFS is the canonical RV/model-check emptiness check.

ADR-11

Automaton state storage

Chosen

Arena-allocated automaton states (index-addressed Vecs: edges: Vec<Vec<(Guard,usize)>>, accept), usize ids

Rejected

Box/Rc<Node> graph with pointer edges; HashMap<StateId,Node>

When the rejected choice is right

Pointer-based graphs win in incremental automaton construction scenarios where states must be inserted and deleted arbitrarily (e.g., an online symbolic fixpoint that adds states one at a time and prunes unreachable ones mid-construction). HashMap wins when state IDs are sparse and non-sequential (e.g., content-addressed nodes hashed by obligation set in a persistent tableau).

Why: Arena + usize indices = cache-friendly contiguous storage, trivial visited-bitsets for nested DFS, no per-node alloc, no reference-cycle leaks. Pointer graphs = scattered allocs + unsafe cycles + awkward coloring. HashMap = hashing overhead + non-contiguous iteration during DFS. Product reuses the same index scheme ((auto_state, kripke_state) pair -> id).

ADR-12

CTL evaluation algorithm

Chosen

Explicit-state iterative labeling (Clarke-Emerson-Sistla 1986): CtlChecker::sat(&Formula)->Vec<bool>; EX=preimage, E[pUq]=lfp, EG p=gfp via SCC quotient; derive EF/AG/AF/AX/A[U]

Rejected

Game-based (parity/model-checking games); tableau CTL; symbolic CTL

When the rejected choice is right

Game-based wins when the logic is extended to CTL* or µ-calculus (parity games subsume both), and the invested machinery pays off across the richer formula class. Symbolic/BDD CTL wins (project #281) once the Kripke structure exceeds the explicit-state wall (~10⁷ states).

Why: Labeling is the canonical explicit CTL procedure: per-state truth vectors, fixpoints over the Kripke graph, EG via SCCs of the sat(p) sub-Kripke. holds = every init state labeled. Game-based adds parity-game machinery with no payoff for CTL (no fairness/CTL* here). Symbolic CTL belongs to #281.

ADR-13

Chosen

Progression: eval_ltlf(&Formula,&Trace)->bool via progress() recurrences; weak/strong next at end-of-trace

Rejected

Translate every LTLf to a DFA first (Phase 11 only); brute-force suffix enumeration

When the rejected choice is right

DFA-first wins when the same LTLf formula is checked against thousands of traces (amortized DFA construction over many checks); DFA step is O(1) per event vs O(

Why: Progression is incremental, allocation-light, and shared with the runtime monitor (Monitor::progress). Recurrences: progress(X f,s)=f; progress(f U g,s)=progress(g,s) OR (progress(f,s) AND f U g); progress(G f,s)=progress(f,s) AND G f. DFA construction (LTLf->DFA) is reserved for Phase 11 bounded/repeated checks where amortization pays; per-trace it is overkill.

ADR-14

Runtime monitoring strategy

Chosen

Incremental formula progression (Monitor::step/progress) as the default; monitor-automaton synthesis optional

Rejected

Always pre-compile a monitor automaton (Bauer-Leucker-Schallhart 3-valued automaton); rewriting engine (Rosu-Havelund) as a separate subsystem

When the rejected choice is right

Pre-compiled monitor automaton wins for continuous high-rate streams (>10⁶ events/s) where per-event O(1) state transition is required and the one-time synthesis cost is amortized over millions of events — the monitor-automaton synthesis path in tl-monitor handles exactly this.

Why: Progression = zero precompute, derivative folds over the event stream, residual True/False = definitive verdict; ideal for ad-hoc/short streams + embedded no_std. Pre-compiled automaton wins only for long high-throughput streams over a fixed formula -> kept as an OPTIONAL synthesis path (tl-monitor). Rewriting (Rosu-Havelund) is effectively progression -> one mechanism, not two.

ADR-15

Monitor verdict domains

Chosen

Verdict{True,False} (2-valued definitive) + RvVerdict{True,False,PresumablyTrue,PresumablyFalse,Unknown} (LTL3 3-valued ∪ RV-LTL 4-valued)

Rejected

2-valued only; raw boolean; custom per-call enum

When the rejected choice is right

2-valued verdict wins in safety-critical embedded systems where the controller only needs "alarm" or "no alarm" and the richer Unknown/Presumably* states cannot be mapped to a control output — and the monitoring engineer guarantees monitorability of all deployed formulas at design time.

Why: LTL3 needs Unknown (no good/bad prefix yet); RV-LTL adds PresumablyTrue/PresumablyFalse via finite-semantics tie-break. One RvVerdict covers both (LTL3 = drop the Presumably-* into Unknown). 2-valued cannot express "verdict not yet decided" -> would force premature commitment + break monitorability.

ADR-17

LTLf decision via DFA (Phase 11)

Chosen

Progression-to-DFA / alternating-automaton construction -> minimized DFA for bounded + repeated finite-model checks

Rejected

BDD-symbolic LTLf; SAT-based bounded check; skip DFA entirely

When the rejected choice is right

SAT-based bounded checking wins when the LTLf formula has a very long horizon (many X nestings) that would cause DFA state explosion, but a bounded SAT encoding can express reachability within the horizon without building the full DFA.

Why: De Giacomo-Vardi LTLf->DFA gives a reusable deterministic decision procedure (minimize once, decide many traces) for bounded/finite model checks. Symbolic LTLf = #281 territory; SAT path = #277 dependency. Per-trace evaluation stays on progression (ADR-13); DFA is the amortized path only.

ADR-18

Product construction timing

Chosen

On-the-fly (lazy) product during nested DFS (Phase 12 optimization); eager product() as the baseline/reference

Rejected

Always eager full product; always lazy (no eager reference impl)

When the rejected choice is right

Eager full product wins when the same product is queried multiple times (e.g., checking a family of related LTL properties against one Kripke model) — build once, search many — amortizing the construction cost over multiple emptiness checks.

Why: Eager product(&Nba,&KripkeStructure)->Nba is the simple, testable baseline (differential oracle). Phase 12 adds lazy product so unreachable product states are never materialized -> bounded memory on large Kripke structures. Keeping BOTH lets the lazy path be validated against the eager one. Always-lazy loses the simple reference; always-eager OOMs on big models.

ADR-19

Automaton/formula output formats

Chosen

HOA (Hanoi Omega-Automata) + Graphviz dot, emitted by tl-cli to-buchi

Rejected

Custom binary format; Spot-only native dump; JSON

When the rejected choice is right

A custom binary format wins when automata must be serialized and loaded at high throughput (e.g., millions of small automata cached on disk) where HOA text parsing overhead is unacceptable. JSON wins when the consumer is a web frontend or a language without an HOA parser but with first-class JSON support.

Why: HOA = the lingua franca interchange consumed by Spot + autfilt -> enables direct differential testing of the produced Nba/Ngba; dot = human inspection/debugging. Custom/JSON formats need bespoke parsers on the oracle side. HOA round-trips through the ecosystem; dot is universal for visualization.

ADR-20

Error handling discipline

Chosen

Result<_, E> everywhere on fallible paths; ParseError/ParseErrorKind in tl-syntax; NO panic!/unwrap in library crates on user input

Rejected

panic! on malformed input; Option for parse errors (loses cause); Box<dyn Error> in libs

When the rejected choice is right

Box<dyn Error> wins in a CLI-only codebase where error types never need to be matched by library consumers — all errors bubble to main as display strings. Option wins for extremely simple internal helpers where the only possible error is "input was absent" and callers handle it by always checking is_none.

Why: Libraries return typed errors; only tl-cli may convert to process exit codes. unwrap/panic on user-supplied formulas/traces = DoS + uncatchable failure for embedders. Option drops the diagnostic (location/kind). panic permitted ONLY for internal invariant violations (documented, unreachable). Fuzzers (ADR-22) assert no panic on arbitrary bytes.

ADR-21

Differential correctness oracle

Chosen

Spot (ltl2tgba, autfilt) as the primary differential oracle for LTL automata + model-check verdicts (Phase 13)

Rejected

Hand-written expected-output golden files only; no external oracle; NuSMV-only

When the rejected choice is right

Golden files only wins in an air-gapped environment where Spot cannot be installed (e.g., a certified avionics build environment) — the golden set must then be curated to cover all known failure modes of GPVW and nested DFS. NuSMV-only wins if the primary concern is CTL correctness and LTL automata correctness is deferred.

Why: GRAVEST failure = a GPVW/degeneralize bug or buggy nested DFS silently FLIPS a verdict (no crash). Cross-check Nba acceptance + emptiness/model-check verdicts against Spot on standard LTL pattern formulas + random formulas. Goldens alone can't catch the formulas nobody thought to write. CTL labeling cross-checked vs known results (no direct Spot CTL).

Rejected

When the rejected choice is right

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1: Symbolic/BDD LTL Model Checking

Sketch. Instead of building an explicit-state Nba and synchronous product, represent the Kripke transition relation and the automaton acceptance sets as BDDs (Binary Decision Diagrams). The product becomes a BDD conjunction; emptiness becomes a fixpoint over symbolic state sets. This is project #281's core technique.

Where it wins over this engine. Systems with |S| ≥ 10⁸ reachable states — typical in hardware verification and concurrent software with many components. A symbolic representation can handle 10²⁰ states in moderate-size BDDs (depending on variable ordering) while this engine OOMs at ~10⁷. The BDD-based fixpoint for LTL (LTL → Büchi → symbolic product → EG/EF fixpoint) is NuSMV's core approach.

Why rejected here. (a) Correctness/pedagogical: the automata-theoretic path produces concrete counterexample lassos that replay on the Kripke structure; symbolic counterexamples require symbolic witness extraction (much harder). (b) Explicit separation: #281 is the symbolic engine; differential cross-checking between explicit (#283) and symbolic (#281) is a portfolio testing strategy. (c) BDD variable ordering is a separate, deep engineering problem that would dominate this project's scope.

The concrete thing that changes. Drop tl-automata's explicit product + emptiness. Replace with a BDD library (CUDD), a symbolic transition relation, and a symbolic EG/EU fixpoint. The check_ltl API surface stays identical from the caller's perspective.

Alt-2: One-Pass SCC-Based Emptiness (Couvreur) Instead of Nested DFS

Sketch. Couvreur's on-the-fly SCC algorithm (FM 1999) computes SCCs incrementally during a single DFS. It detects a non-empty accepting SCC without running a second (inner) DFS. Works directly on the generalized Büchi acceptance without degeneralization.

Where it wins. Generalized Büchi automata (Ngba) can be checked for emptiness without the degeneralize step, avoiding the (k+1) × nstates blowup. On formulas with many Until-subformulas (k large), this can yield a (k+1)× speedup in emptiness check time and memory. Couvreur also yields a direct witness in one pass.

Why rejected here. (a) Complexity: Couvreur's SCC management is more intricate than two-color nested DFS, making it harder to audit for the critical correctness property. (b) The degeneralize step is already designed and tested; keeping nested DFS as the single canonical emptiness check lets the codebase have exactly one correctness-critical graph algorithm. (c) Nested DFS is the standard RV/model-check teaching algorithm — the primary pedagogical goal.

The concrete thing that changes. Remove degeneralize (or make it optional). Rework emptiness to accept Ngba directly. Couvreur's Tarjan SCC + acceptance-set tracking replaces the two-color coloring. The Lasso extraction from SCC roots is more involved.

Alt-3: LTL2BA Very-Weak Alternating Automata (VWAA) Route

Sketch. LTL2BA (Gastin-Oddoux, CAV 2001) translates LTL to a very-weak alternating automaton (VWAA) — an automaton with universal (∧) branching — then converts to a generalized Büchi (GBA) through a subset construction, resulting in automata that are typically smaller than GPVW's output. The VWAA representation is more succinct (linear in |f|) before determinization.

Where it wins. State-minimality: on safety and liveness patterns from the Dwyer specification pattern suite, LTL2BA automata average 2–5× fewer states than GPVW automata. For deep verification where the automaton is queried millions of times (e.g., batchwise hardware model checking), smaller automata directly translate to faster emptiness checks.

Why rejected here. (a) Alternating automata require a separate codebase path (universal branching, powerset construction, different acceptance handling) adding significant complexity. (b) GPVW is the direct, auditable teaching construction — it maps 1:1 to the PSTV 1995 paper, making bug attribution straightforward. (c) The 2–5× size advantage disappears for random formulas and for the formula sizes (|f| ≤ 30) targeted by this engine.

The concrete thing that changes. ltl_to_ngba is replaced by a two-stage ltl_to_vwaa → vwaa_to_ngba pipeline. The Vwaa type needs universal branching (And(Vec<succ>) edges). The subset construction is an additional ~300 LOC. degeneralize and product remain unchanged downstream.
