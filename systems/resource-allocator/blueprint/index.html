201 — Resource Allocator (Mesos/YARN-like) from Scratch

Project Number: 201

Project Name: Resource Allocator (Mesos/YARN-like) from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a distributed cluster resource allocator and two-level workload scheduler — a control plane that pools the CPU, memory, disk, network-bandwidth and device capacity of a fleet of worker nodes, tracks it as a live multi-dimensional inventory, and hands slices of it to competing tenants under hierarchical fair-share (Dominant Resource Fairness) governance, placement constraints, quotas, gang (all-or-nothing) semantics and priority preemption, while surviving control-plane failover with no double-allocation. The design fuses the Mesos resource-offer model (a master offers revocable resource bundles to framework schedulers) with the YARN ResourceManager/NodeManager/ApplicationMaster split and Borg-style admission control and priority. It is an allocation and placement engine, not an application runtime: it provides scheduling, leasing, isolation orchestration, accounting and reconciliation, and delegates the workload's business logic to executors.

Phase-0 deliverable (numbered modules/crates):

  1. alloc-manager — control-plane binary: leader, scheduler host, API server.
  2. alloc-agent — per-node binary: resource probe, executor supervisor, heartbeat client.
  3. scheduler-core — offer generation, feasibility filtering, placement scoring, epochs.
  4. lease-engine — offer→accept→launch lifecycle, lease issuance, expiry, fencing, reclamation.
  5. queue-manager — hierarchical queue tree, DRF share computation, borrowing, preemption selection.
  6. quota-engine — tenant/queue guaranteed & max share, admission control, headroom.
  7. runtime-executor — cgroups v2 / namespace container shim, process supervision, signal/exit capture.
  8. metadata-store — Raft-replicated write-ahead log, snapshotting, deterministic state machine.
  9. rpc-protocol — protobuf schemas + tonic gRPC service stubs, wire versioning.
  10. resource-model — resource vector algebra, DRF math, capacity conservation primitives.
  11. observability — tracing/metrics/log initialisation, replay tooling, cluster event bus.
  12. alloc-cli — operator CLI (submit, drain, inspect queues/leases/nodes).
  13. sim-harness — deterministic discrete-event cluster simulator (one assertion per invariant).

System boundaries. Provides: resource inventory, two-level scheduling, DRF fairness, hierarchical quotas, leasing, gang scheduling, preemption, cgroups isolation orchestration, WAL-backed HA, operator APIs, observability. Delegates: container image build/registry (OCI runtime is invoked, not implemented), authentication provider (SPIFFE/mTLS identities consumed, not issued), persistent application data (workloads bring their own storage). Does NOT provide: a hypervisor, a distributed filesystem, an object store, a billing system, GPU device-plugin drivers, or a Kubernetes API-compatibility layer.

Non-goals: application scheduling policy beyond DRF+priority+constraints (per-framework meta-schedulers are PhaseDeferred("§35")); cross-region federation PhaseDeferred("§35"); ML-model-driven right-sizing PhaseDeferred("§35"); Windows/macOS agents (Linux-only Phase 0).

Deployment model. 3–7 replicated managers (one Raft leader) + 100–10,000 agents; single region, multi-AZ; bare-metal or VM workers; kernel ≥ 6.6 for cgroups v2. Managers are stateless above the Raft log; agents are semi-trusted and re-validated.

Target users/operators. Cluster operators (capacity planning, incident response, governance); platform engineers (queue policy, placement constraints, executor integration); application teams (workload submission, quota consumption, job monitoring).

What later phases unlock. Phase 4 unlocks placement; Phase 5 real allocation; Phase 6 real workload execution; Phase 7 multi-tenant fairness; Phase 9 HA + scale. Post-blueprint: federation, GPU topology, over-subscription with revocable classes, storage-aware placement.

Recommended language: Rust (1.82+, edition 2021). Rationale: (a) no GC → predictable scheduler tail latency (Go's stop-the-world pauses directly inflate M1's p99); (b) ownership types statically enforce single-owner allocation (I1) and eliminate the data races a global-lock C++ allocator invites; (c) tokio gives a mature work-stealing async runtime for 100k concurrent RPC streams; (d) prost/tonic give first-class protobuf/gRPC. Rejected: Go (GC tail-latency variance, weaker compile-time aliasing guarantees for the lease invariants — the exact tradeoff Nomad accepts for velocity); C++ (memory-safety burden across a 13-crate concurrent codebase; no borrow checker to enforce I1/I11); Java (JVM heap/GC footprint at 16 GB manager RSS, the pain YARN operators know well).

Prerequisites (systems knowledge): consensus (Raft), write-ahead logging and snapshotting, failure detectors, DRF and proportional-share scheduling theory, cgroups v2 / Linux namespaces, async runtimes and backpressure, hybrid logical clocks, lock-free/sharded concurrency, bin-packing and fragmentation.

Timeline. Phase 0: 3–4 weeks. Phases 1–9 to production: 14–18 months. Every deferred feature is registered in §35 with a resolving anchor.

2. Why Build This

  • Unique systems knowledge. Two-level scheduling (resource offers vs. request-based) is a fork in distributed-systems history: Mesos pushed policy to frameworks; YARN centralised it; Omega made it optimistic-concurrent. Building all three teaches why each exists and where each wins.
  • Multi-resource fairness. DRF is non-obvious: fairness across ≥2 resource types is not "equal shares of each" — it equalises each tenant's dominant share. Implementing it from the 2011 paper builds intuition no single-resource scheduler gives.
  • Failure-domain reasoning. Managers, agents and executors fail independently; the allocator must never double-allocate across a failover. This is the canonical fencing/epoch problem in miniature.
  • Architectural/historical significance. Mesos (2011), YARN (2013), Omega (2013), Borg (2015) and Kubernetes are the lineage of every modern cluster manager; this project is that lineage compressed into one codebase.
  • Engineering muscles. Event-sourced state machines; Raft integration; backpressure-aware control loops; cgroups isolation; deterministic replay debugging; capacity modelling; tail-latency engineering.
  • Named cross-links to sibling systems. Consensus engine (Raft here is a client of that knowledge); LSM storage engine (RocksDB WAL/compaction underpins §14); container runtime (§18 orchestrates an OCI runtime); distributed database (shares the WAL/snapshot/replay spine); service mesh (shares mTLS/SPIFFE identity, §18).
  • Calibration value. Finishing this demonstrates principal-level command of control-plane design: correctness under partition, fairness under contention, and operability under load.

  • API Gateway — stateless, horizontally scalable front door. Terminates mTLS, authenticates SPIFFE identities, rate-limits, validates, audits, routes to the current leader. Fails closed; never mutates cluster state directly.
  • Control Plane Manager — the scheduling brain. Hosts scheduler-core, queue-manager, quota-engine, placement scoring. Exactly one manager is Raft leader and runs the single-writer scheduling loop; followers stand by hot. All decisions become mutations proposed to Raft before they take external effect (I7).
  • State machine (RAM) — the deterministic, in-memory projection of the committed WAL: node inventory, leases, queues, quotas, workloads. It is a cache of the log (MM3); rebuilt by replay on restart.
  • metadata-store (Raft) — replicated WAL + periodic snapshots over RocksDB. Provides linearizable commit ordering (I3), quorum durability (I7) and monotonic epochs (I2).
  • Agent fleet — semi-trusted per-node daemons. Probe true capacity, stream heartbeats under bounded credit-flow, supervise executors, and locally reconcile against manager intent. Managers re-validate all agent-reported state.
  • runtime-executor — applies cgroups v2 limits + namespaces and invokes an OCI runtime to launch the workload process, capturing stdout/stderr and exit codes.
  • Data flows. submit → admission (quota-engine) → queue → DRF pick → offer → framework/auto-accept → lease (WAL-committed) → launch RPC → agent executor → running → exit/preempt → reclaim.
  • Trust boundary (double line). Everything above it (operator/apps, gateway) is untrusted input; agents below are semi-trusted and re-validated. Only the manager, gated by Raft, mutates authoritative state.
  • Concurrency boundary. The scheduling loop is single-writer per shard (P5); cross-shard work and agent I/O are message-passed, never shared-memory — this is where race-freedom is enforced.
  • Persistence boundary. Below it, nothing is authoritative until quorum-committed (I7); above it, RAM state is a rebuildable projection (MM3).
  • Protocol boundary. Manager↔agent is bounded, credit-flow gRPC (ADR-21); a slow or flooding agent cannot back-pressure into the scheduler core.
  • Queues/channels. The admission queue, per-agent heartbeat streams, and the event bus are all bounded (P2); overflow is rejection, never unbounded buffering.

6. Design Principles

  1. P1 — Determinism over convenience. Rule: the scheduler state machine is a pure function of the committed WAL; identical logs replay to identical state. Tradeoff: forbids wall-clock reads and RNG in the apply path (must feed them as log entries). Operational implication: any incident is reproducible by replay. Violation: non-reproducible failovers and un-debuggable fairness drift.
  2. P2 — Backpressure at every hop. Rule: every queue, channel and stream is bounded with credit-based flow control (ADR-21). Tradeoff: rejects/throttles under overload instead of buffering. Operational: load is shed at the edge, not amplified in the core. Violation: unbounded memory growth → OOM cascade (FM-9).
  3. P3 — The log is the database. Rule: durable truth lives only in the Raft WAL + snapshots; RAM state is a rebuildable cache (MM3). Tradeoff: every externally-visible mutation costs one quorum commit. Operational: RPO 0. Violation: state divergence between managers after failover.
  4. P4 — Fence, don't trust liveness. Rule: before reissuing a lease held by a possibly-dead node, fence the old holder by epoch (I11, MM4). Tradeoff: a slow-but-alive node loses its lease. Operational: no double-allocation. Violation: two executors believe they own the same resources (I1 breach).
  5. P5 — Single-writer per shard. Rule: each state shard is mutated by exactly one thread; cross-shard work is message-passed (ADR-08). Tradeoff: no shared-memory parallelism inside a shard. Operational: no data-race class of bugs; lock-free reads via epoch snapshots. Violation: torn reads of inventory, phantom capacity.
  6. P6 — Isolation before density. Rule: enforce cgroups limits before packing tighter (ADR-17). Tradeoff: lower utilisation than best-effort oversubscription. Operational: one tenant cannot starve another's CPU/mem. Violation: noisy-neighbour SLO breaches.
  7. P7 — Quota is admission, not eviction. Rule: reject at submit when a tenant is over max-share; do not admit-then-kill (quota-engine, §18 admission). Tradeoff: bursty tenants see rejections. Operational: predictable cluster headroom. Violation: churn from admit/kill loops (FM-12).
  8. P8 — Offers are revocable leases. Rule: an offer is a time-boxed, epoch-stamped claim, not ownership (MM1). Tradeoff: frameworks must accept promptly or lose the offer. Operational: no offer hoarding starves the cluster. Violation: stale offers double-book capacity (I6).
  9. P9 — Conserve capacity exactly. Rule: for every node and resource, allocated + reserved + available = total, always (I10). Tradeoff: every mutation must update the vector atomically. Operational: accounting reconciles to zero. Violation: phantom or leaked capacity.
  10. P10 — Fairness is progress, not snapshots. Rule: always allocate next to the tenant with the lowest dominant share (I8, DRF). Tradeoff: short-term inefficiency for long-term fairness. Operational: no tenant starves. Violation: dominant-resource monopolisation.
  11. P11 — Idempotent side effects. Rule: launch/kill/preempt RPCs carry (workload, attempt, epoch) and are safe to retry (I13). Tradeoff: agents keep a dedup window. Operational: at-least-once RPC is safe. Violation: duplicate task launches after retry.
  12. P12 — Observable by construction. Rule: every state transition emits a structured event with request_id/epoch/queue (§20). Tradeoff: telemetry volume. Operational: on-call can localise regressions in one dashboard. Violation: blind failovers.
  13. P13 — Explicit failure domains. Rule: manager, agent and executor crash independently and reconcile, never cascade. Tradeoff: more reconciliation code. Operational: blast radius bounded to one domain. Violation: one agent crash stalls the scheduler.
  14. P14 — Compatible by version, not by luck. Rule: wire and storage schemas evolve additively; fields are never reused (§25, ADR-05). Tradeoff: deprecated fields linger. Operational: rolling upgrades never break. Violation: mixed-version corruption.

Debugging methodology. The sim-harness (§12) is a deterministic discrete-event simulator that drives injected schedules (submissions, crashes, partitions, clock skew) and asserts I1–I17 after every applied event. Each invariant maps to exactly one assertion; a failing seed is a minimal reproducer. Property tests (§26) generate randomized event streams; a violation shrinks to the smallest failing WAL prefix, which replays identically under P1. Because the state machine is a pure function of the log (MM3), a production incident is reproduced by shipping its WAL segment to a developer laptop and replaying it under the same assertions — no live cluster needed. The invariants are ordered by blast radius: I1/I2/I7/I11 (double-allocation and split-brain) are Sev-1 assertions that abort the process on violation in test builds and page immediately in production; I4/I8 (fairness) degrade rather than corrupt and are Sev-2; I5/I10/I12/I13 are detection-and-recover. The one-assertion-per-invariant discipline means a green sim run is a machine-checked proof of correctness for the injected schedule, and the fuzzer (§26) searches the schedule space for a counterexample.

8. Domain Model / Protocol / Data Model

8.1 Resource model

Resources are a fixed-arity vector over typed dimensions: cpu_millicores, memory_bytes, disk_bytes, net_bps, gpu_units, ephemeral_ports. All allocation math is vector algebra with per-dimension conservation (I10).

ResourceVector { cpu_mc:u64, mem_b:u64, disk_b:u64, net_bps:u64, gpu:u32, ports:u16 }
NodeCapacity   { total:ResourceVector, allocated:ResourceVector,
                 reserved:ResourceVector, available:ResourceVector,   // available = total-allocated-reserved (I10)
                 overcommit:OvercommitRatio }
DominantShare  = max over dims( tenant_usage[dim] / cluster_total[dim] )   // DRF (I8)

8.2 Workload lifecycle (state machine)

From Event To Guard
SUBMITTED admit ok ADMITTED quota headroom (I4)
SUBMITTED admit deny REJECTED over max-share
ADMITTED enqueue QUEUED queue bounded (P2)
QUEUED DRF pick + feasible PLACED lowest dominant share (I8)
PLACED lease committed LAUNCHING quorum commit (I7)
LAUNCHING agent ack RUNNING RUNNING idempotent (I13)
RUNNING task exit 0 COMPLETED —
RUNNING task exit ≠0 / crash FAILED retry policy
RUNNING preempt PREEMPTED victim fenced (I14)
RUNNING node LOST LOST heartbeat timeout (I5)
any active kill TERMINATING→COMPLETED fence (I11)

Failure terminals: FAILED, LOST, PREEMPTED, REJECTED. Retries re-enter as a new attempt (I13 keys on it).

8.3 Offer protocol (sequence)

Manager -> Framework : RESOURCE_OFFER {offer_id, node_id, vector, epoch, ttl}
Framework -> Manager : ACCEPT_OFFER  {offer_id, workload_id, epoch}     # I6 checks epoch
Manager  (commit lease to WAL, I7) -> Agent : LAUNCH {lease_id, spec, attempt, epoch}
Agent -> Manager : STATUS RUNNING {lease_id, attempt}                    # I13 dedup
Agent -> Manager : STATUS EXITED  {lease_id, code}  -> reclaim (I10)

Un-accepted offers expire at ttl and their capacity returns to available (P8). Auto-mode: the built-in scheduler accepts on the framework's behalf.

8.4 Placement constraints

Affinity / anti-affinity (workload↔workload, workload↔node label), rack awareness, NUMA locality, resource labels, taints/tolerations. Constraints are feasibility filters (hard) or score modifiers (soft); Tetris-style alignment scoring breaks ties toward tight packing (§16).

8.5 Worked example

Cluster of 2 nodes, each <9 cpu, 18 GB>; cluster total <18, 36>. Tenant A tasks <1 cpu, 4 GB> (mem-dominant: 4/36=0.111 > 1/18=0.056). Tenant B tasks <3 cpu, 1 GB> (cpu-dominant: 3/18=0.167 > 1/36=0.028). DRF equalises dominant shares → A gets 3 tasks (<3,12>, dom 0.33), B gets 2 tasks (<6,2>, dom 0.33): the Ghodsi et al. NSDI-2011 canonical example.

Preemption walk-through. Queue Q-batch (guarantee 40% CPU) runs 8 low-priority tasks filling 60% CPU by borrowing idle capacity (I4). Queue Q-svc (guarantee 40%) submits a high-priority gang needing 30% CPU but the cluster is full. Sequence: (1) quota-engine confirms Q-svc is under guarantee and Q-batch is over its guarantee on borrowed capacity; (2) queue-manager selects victims from Q-batch by lowest priority then latest start, choosing the fewest tasks that free ≥ 30% CPU; (3) victims get SIGTERM→grace→SIGKILL (§18); (4) resources are NOT offered to Q-svc until each victim's exit is acked (I14) — premature_reuse_total must stay 0; (5) the freed capacity is committed as a lease for the Q-svc gang atomically (I9). If any victim fails to die within grace, the gang stays QUEUED rather than partially placed.

8.6 Malformed / failure paths

  • Malformed input: an offer ACCEPT whose vector exceeds the offer's vector → rejected by resource-model bounds check, offer_overclaim_total++, offer voided.
  • Failure path: LAUNCH committed (I7) but agent never acks RUNNING within launch-deadline → lease enters LAUNCHING timeout → fence (I11) → reclaim capacity (I10) → workload retried as new attempt (I13).

8.7 WAL record & wire layouts

Every durable mutation is a length-prefixed, checksummed WAL record; every RPC frame is protobuf over HTTP/2. Layouts (bytes, little-endian):

WAL record (metadata-store):
  +0   u32   total_len            # record length excluding this field
  +4   u64   log_index            # strictly increasing (I3)
  +12  u64   epoch                # cluster generation (I2)
  +20  u8    entry_type           # WalEntry discriminant (never renumbered, P14)
  +21  var   payload (protobuf)   # entry body
  +N   u256  blake3               # checksum over bytes [0..N) (I12)

Heartbeat frame (agent -> manager):
  node_id:16B  hlc:{wall_ms:u64, logical:u32}  seq:u64
  capacity_delta:ResourceVector  running_task_ids_delta:[LeaseId]
  suspicion_ack:u8               # echoes detector state for tuning (§13)

Snapshot header:
  magic:u32 "RASN"  sm_version:u32  at_log_index:u64  epoch:u64
  entry_count:u64   blake3:u256    writer_semver:[u8;16]   # §25 downgrade-safety

Records are self-describing and forward-compatible: an unknown entry_type in a mixed-version quorum is gated by feature-epoch (§25) so it is never written before every replica can apply it.

12. Phase 0 — Repository Skeleton, Correctness Kernel & Deterministic Simulator

12.1 Objectives

Stand up the 13-crate Cargo workspace, the deterministic build/CI spine, the protobuf schema baseline, and the correctness kernel: the resource-model vector algebra + DRF math and the sim-harness that will assert I1–I17 for every later phase. Constraint introduced: everything downstream must be replayable (P1).

12.2 Detailed Implementation Steps

  • Create the workspace (§10) with pinned rust-toolchain.toml and deny.toml (ADR-19, ADR-03).
  • Implement ResourceVector algebra (add/sub/fits/max-normalize) and DominantShare in resource-model, enforcing capacity conservation (I10, P9).
  • Define proto/allocator.proto baseline: ResourceVector, WorkloadDescriptor, offer/lease messages (ADR-05); wire build.rs prost/tonic codegen.
  • Implement sim-harness discrete-event core: virtual clock (feeds TimeTick WAL entries, P1), event queue, and one assertion hook per invariant (I1–I17).
  • Configure observability init: tracing JSON subscriber (ADR-10), Prometheus registry (ADR-12), OTLP exporter stub (ADR-11).
  • Define the WalEntry enum and StateMachine trait (§11) with a no-op reference state machine so the sim can drive apply-order assertions (I3) before Phase 2 exists.
  • Fixed-arity ResourceDim (6 dims) frozen in proto with reserved tags for future dims (P14) — the dimensionality is load-bearing for constant-time DRF (§29).
  • Establish the golden-hash harness: a canonical state serializer so any later phase can assert replay(WAL) == golden (P1).
  • CI (ci.yml): build, cargo test, clippy -D warnings, cargo-deny, coverage, SBOM. Reproducible-build check via Nix (ADR-19).

12.3 Deliverable

A workspace that builds reproducibly, a passing CI pipeline, generated protobuf bindings, and a sim-harness that can run a scripted event trace and evaluate all 14 invariant assertions on a toy 2-node cluster.

12.4 Acceptance Criteria

  • cargo test green; clippy zero warnings; cargo-deny zero advisories.
  • Two identical build invocations produce byte-identical manager+agent artifacts (SHA-256 match) — reproducibility gate (ADR-19).
  • resource-model property tests: 10,000 random vector ops preserve I10 (allocated+reserved+available=total) with zero violations.
  • DRF math reproduces the §8.5 Ghodsi example exactly (A:3 tasks, B:2 tasks).
  • sim-harness runs fixture sim_baseline.trace with all 17 invariant assertions passing.
  • Golden-hash serializer produces a stable hash for a fixed state across 100 runs (determinism, P1).

12.5 Conformance Fixtures

  • sim_baseline.trace | scripted 2-node admit→place→launch | all I-assertions pass.
  • drf_ghodsi.json | §8.5 canonical inputs | dominant shares equalise at 0.33.
  • malformed_proto.bin | truncated offer message | decode error, no panic.
  • vector_overflow.json | request exceeds u64 dim | checked-add rejects, AllocError::Infeasible.

12.6 Pitfalls

  • Non-reproducible builds — build-time timestamps leak into artifacts → SHA mismatch; fix: SOURCE_DATE_EPOCH, strip build ids; signal: reproducibility gate red.
  • DRF float drift — comparing dominant shares with == on f64 → non-deterministic picks; root cause: FP non-associativity; fix: compare with fixed epsilon or scaled integers; detection: replay mismatch.
  • Proto field renumber — reusing a field tag breaks P14; detection: schema-diff CI check.
  • Sim clock realism — using wall-clock inside the sim breaks determinism (P1); fix: only virtual clock.
  • Silent HashMap iteration order — non-deterministic map iteration leaks into serialized golden state; fix: BTreeMap/sorted iteration on any hashed collection in the apply path (P1).
  • cargo-deny false green — an advisory DB not refreshed passes stale; fix: pin + refresh the advisory DB in CI, fail on unknown licenses.

12.7 Performance Concerns

  • Build-graph fan-out across 13 crates: mitigate with a thin rpc-protocol codegen crate to avoid rebuild storms.
  • DRF max-normalize is O(dims) per candidate: fixed-arity dims (6) keep it constant-time (§29).
  • The sim must run ≥ 10⁶ events/s to make property tests (§26) practical: allocation-free event loop.
  • Reference state machine in flat arrays, not boxed graphs, for cache locality.

12.8 Edge Cases

  • Empty cluster: no nodes → all offers empty, scheduler idles cleanly.
  • Zero-resource workload: must still consume a queue slot and get a lease for accounting.
  • Missing generated bindings: codegen must fail the build, not silently skip.
  • Toolchain version skew across developers: the pin resolves it deterministically.
  • A resource dimension at u64::MAX: checked-add must saturate-or-reject, never wrap.
  • DRF input where a cluster-total dimension is zero: division guard → that dim contributes 0 share, not NaN.
  • Duplicate WAL entry replayed in the sim: apply must be idempotent per index (I3).

12.9 Failure Analysis

  • Blast radius: Phase 0 defects are compile-time or test-time — contained to CI, never production.
  • Poisoned CI cache (FM-2 analogue): yields stale codegen; detect via schema hash in artifact metadata; recover by cache purge + rebuild.
  • Non-deterministic test: a flaky sim seed hides a real invariant bug; fix by recording the seed and replaying (P1).
  • Postmortem artifact: CI logs + artifact SHA manifest + the failing sim seed.

12.10 Operational Notes

  • Metrics: build_info{version,git_sha,toolchain} gauge (ADR-12); sim event-rate and assertion-pass counters.
  • Release: sign artifacts + generate SBOM in release.yml (§27).
  • Deployment: none yet — the deliverable is inspectable by running sim-harness and reading the invariant report.

13. Phase 1 — RPC Transport, Membership & Failure Detection

13.1 Objectives

Build the gRPC control channel (mTLS), the agent membership registry, bounded heartbeat streaming with credit flow-control, and an accrual-style failure detector. Constraint: every stream is bounded (P2, ADR-21); agents are semi-trusted (re-validate).

13.2 Detailed Implementation Steps

  • Define AgentRegistration, Heartbeat, NodeStatus RPCs in rpc-protocol; tonic server in alloc-manager, client in alloc-agent (ADR-06).
  • mTLS bootstrap with SPIFFE SVIDs (ADR-18, RFC 8446); reject unknown identities (fail-closed, P1 of API gateway).
  • Heartbeat multiplexer: one bidi stream per agent, HTTP/2 flow-control as backpressure (ADR-21, RFC 9113); bounded per-manager ingest queue.
  • Failure detector implementing ◇P properties (Chandra-Toueg, applied): last-heartbeat age → SUSPECT at 10 s, LOST after grace; enforces I5.
  • Node fencing primitive: on LOST, bump node epoch (I2) so any late heartbeat is stale-rejected (I11 groundwork).
  • HLC (ADR-20) stamped on every heartbeat for skew-tolerant ordering.
  • Accrual failure detection (φ-accrual variant of Chandra-Toueg ◇P, applied): track heartbeat inter-arrival distribution per node and emit a suspicion level rather than a hard boolean, so a transiently slow link degrades gracefully instead of flapping (FM-1).
  • Connection admission: cap concurrent handshakes and per-source connection rate at the gateway (P2) so a reconnect storm (FM-9) cannot exhaust the accept queue.
  • Registration is a WAL entry (RegisterNode) once Phase 2 exists; in Phase 1 it lives in the in-RAM reference state so membership is already replayable (P1, MM3).

13.3 Deliverable

Agents register over mTLS and sustain heartbeats; the manager maintains a live membership table with SUSPECT/LOST transitions and epoch fencing, observable via CLI nodes list.

13.4 Acceptance Criteria

  • 10,000 simulated agents sustain 2 s heartbeats; heartbeat processing p99 ≤ 20 ms (M3), zero dropped-below-credit stalls.
  • Node marked SUSPECT within 10 s and LOST within grace (I5) in fixture hb_timeout.trace.
  • A LOST node's late heartbeat is rejected with StaleEpoch (I2/I11) in late_hb_replay.trace.
  • mTLS handshake rejects an unlisted SPIFFE ID in bad_spiffe.pem (100% rejection).
  • Under a 10k-agent reconnect storm, credit flow-control holds ingest below the bounded queue with zero OOM in hb_storm.trace (FM-9).

13.5 Conformance Fixtures

  • hb_timeout.trace | drop heartbeats for one node | SUSPECT@10s, LOST after grace.
  • late_hb_replay.trace | replay heartbeat after fence | StaleEpoch reject.
  • bad_spiffe.pem | unlisted identity | handshake refused.
  • hb_storm.trace | 10k agents reconnect at once | credit flow-control holds, no OOM.
  • dup_node_id.trace | two agents claim one NodeId | second rejected.
  • svid_expiry.trace | SVID expires mid-stream | re-auth required, stream dropped on failure.

13.6 Pitfalls

  • Heartbeat storm on reconnect (FM-9) — all agents reconnect after a manager restart → ingest overload; fix: jittered backoff + credit flow-control (ADR-21); signal: node_hb_age_seconds spike, ingest queue depth.
  • FD exhaustion — one connection per agent nears the 200k FD budget; fix: multiplex streams over HTTP/2, monitor manager_open_fds.
  • Split heartbeat/gossip clocks — using wall-clock for age with skewed nodes → false LOST; fix: HLC (ADR-20).
  • Duplicate NodeId — agent restart with a new identity but old id; detection: registration dedup by SPIFFE+id.
  • φ-accrual mis-tuning — too-tight threshold flaps healthy nodes (FM-1), too-loose delays LOST past M3 usefulness; fix: calibrate against net_partition.trace; signal: node_state transition rate.
  • Expired SVID mid-stream — a long-lived stream outlives its certificate; fix: require re-auth on SVID expiry, not just at connect (ADR-18).

13.7 Performance Concerns

  • Heartbeat ingest is the hottest path (5,000 hb/s, §32 #1): batch-decode and apply on the single-writer membership shard (P5).
  • Avoid per-heartbeat allocation: reuse decode buffers.
  • Syscall overhead amortised by HTTP/2 stream multiplexing (ADR-06).
  • Delta payloads after the first full report cut §32 #2 bandwidth (20 MB/s) by ~10× in steady state.

13.8 Edge Cases

  • Clock skew beyond the 250 ms envelope: HLC absorbs it; beyond the envelope, alert (FM-11).
  • Agent heartbeats but reports impossible capacity: re-validate and clamp (T1).
  • Half-open TCP: detected by stream keepalive, treated as disconnect.
  • Manager failover mid-stream: agent re-registers with the new leader.
  • Agent clock jumps backward: HLC logical component preserves order (ADR-20).
  • Node flaps SUSPECT↔RUNNING every few seconds: dampen with φ-accrual hysteresis.
  • Heartbeat larger than the frame limit: reject, force a full re-register.
  • Agent presents a valid SVID for a decommissioned node: reject, the node id is tombstoned.

13.9 Failure Analysis

  • Manager crash: agents detect via stream close and re-register with the new leader within the failover window (§21).
  • Blast radius: membership only — scheduling pauses but committed leases persist (P3).
  • Heartbeat storm on recovery (FM-9): detect via ingest queue depth; recover with credit flow-control + jitter (ADR-21).
  • Detection/Forensics: leader_changes_total; heartbeat trace + epoch log.

14. Phase 2 — Persistent Metadata Store (Raft WAL + Snapshots)

14.1 Objectives

Build the durable spine: a Raft-replicated write-ahead log over RocksDB, a deterministic state-machine host, periodic snapshots, and crash recovery by replay. Constraint: the log is the database (P3, MM3); nothing externally visible before quorum commit (I7).

14.2 Detailed Implementation Steps

  • Integrate a Raft library (leader election, log replication, membership change) per Ongaro & Ousterhout (Raft paper, applied; ADR-09); back the log and snapshots with RocksDB (ADR-04, ADR-24).
  • Implement StateMachine::apply in strict log-index order (I3, P1) and snapshot/restore keyed to one committed index (I12).
  • WAL append with grouped fsync to hit M4 (≤ 8 ms p99), per Database Internals (applied).
  • Snapshot cadence + compaction: snapshot every N entries; truncate log below the snapshot index; Blake3 checksum per snapshot (I12).
  • Epoch management: leadership change bumps Epoch monotonically (I2); reject stale-epoch proposals.
  • Recovery: on boot, load latest valid snapshot then replay tail WAL to reach serving state within M8 (≤ 30 s).
  • Read-path semantics: linearizable reads via a lease-read (leader confirms it still leads before serving) vs. stale local reads for telemetry; expose both, default to leader-confirmed for allocation decisions (I7).
  • Membership change (add/remove manager) via Raft joint-consensus (per the Raft paper, applied); never change quorum size in one step.
  • WAL segment format: length-prefixed protobuf records + per-record Blake3 (I12); segments rotate at a fixed size for bounded recovery scan.

14.3 Deliverable

A 3-node replicated metadata store: proposals commit at quorum, survive leader kill with no data loss (RPO 0), and recover from crash by snapshot+replay, verified by tools/wal-inspect and tools/replay.

14.4 Acceptance Criteria

  • WAL append+fsync p99 ≤ 8 ms (M4) under 5,000 entries/s.
  • Kill-the-leader test: zero committed entries lost across 100 induced failovers (RPO 0) in raft_kill_leader.trace.
  • Cold-start replay of a 1.5M-entry tail + 1.2 GB snapshot reaches serving in ≤ 30 s (M8).
  • Snapshot at index K restores to a state byte-identical to replaying [0..K] (I12) — snapshot_equiv.trace.
  • Injected single-bit WAL flip is detected by checksum, entry rejected, wal_corruption_total++ (FM-2).
  • Read-your-writes: a leader-confirmed read after a committed write reflects that write (I7) in ryw.trace; a stale local read is flagged, never served on the allocation path.

14.5 Conformance Fixtures

  • raft_kill_leader.trace | repeated leader kills | no committed loss, epoch monotonic.
  • snapshot_equiv.trace | snapshot vs. replay | identical state hash.
  • wal_corrupt_bit.bin | flipped checksum byte | detected + rejected.
  • replay_regression.trace | historical log | replays to golden state hash.
  • stale_epoch_propose.trace | old-leader proposal | StaleEpoch reject (I2).
  • ryw.trace | write then leader-confirmed read | read reflects the write (I7).

14.6 Pitfalls

  • Applying before commit (I7 breach) — emitting effects on append not commit → phantom leases on rollback; detection: lease_precommit_leak_total; fix: gate effects on commit index.
  • Torn snapshot (FM-6) — snapshotting a mutating state → inconsistent blob; fix: snapshot from an immutable log-index-consistent view (I12); the real-world analogue is etcd's historical snapshot-consistency bugs.
  • fsync amplification — per-entry fsync blows M4; fix: group commit; signal: wal_fsync_ms.
  • Unbounded log growth — no compaction → disk fill; fix: snapshot+truncate; detection: wal_bytes.
  • Read-your-writes violation — serving a stale local read after a committed write confuses the scheduler; fix: leader-confirmed reads on the allocation path (I7); detection: differential test vs. golden.
  • Snapshot install stalls apply — a large snapshot transfer to a lagging follower blocks its apply loop; fix: chunked, throttled snapshot streaming (CockroachDB lesson, §5).

14.7 Performance Concerns

  • WAL is write-amplified by Raft replication (×quorum) and RocksDB LSM compaction: dedicated NVMe for the WAL (M4).
  • Group-commit batching trades a few ms latency for throughput (§32 #7).
  • Snapshotting must stay ≤ 10% CPU (M5): stream to disk, never copy the whole heap.
  • Chunked snapshot install to lagging followers avoids blocking their apply loop.

14.8 Edge Cases

  • Quorum loss: minority can't commit → read-only (FM-10).
  • Log divergence on a partitioned old leader: Raft term/epoch resolves (I2).
  • Disk full mid-append: fail the proposal, don't corrupt the log.
  • Snapshot during compaction: serialise via single-writer (P5, I12).
  • Partial write on crash: checksum + last-good truncation recovers.
  • Follower behind a truncated log: trigger snapshot install, not log catch-up.
  • Two snapshots racing: single-writer serialises them (I12).
  • Clock jump during HLC stamping: logical component stays monotonic (ADR-20).

14.9 Failure Analysis

  • WAL corruption (FM-2): detected by Blake3 checksum (I12); recover by restoring the latest good snapshot + replaying the clean tail; blast radius one replica, others keep serving.
  • Quorum loss (FM-10): control plane goes read-only; agents keep running existing leases (P13); recover by restoring a majority.
  • Slow follower: apply lag grows; detect via wal_apply_index gap; recover by snapshot install.
  • Forensics: tools/wal-inspect record dump + tools/snapshot-diff between the last good and the corrupt state.

14.10 Operational Notes

  • Metrics: wal_apply_index, wal_fsync_ms, snapshot_log_index, raft_term, cp_epoch, wal_bytes.
  • Runbooks: runbooks/wal-repair.md, runbooks/quorum-loss.md.
  • Backup: periodic snapshot ship to object store (§24), tested monthly.
  • Compat: state-machine version stamped in the snapshot header (§8.7, §25) for downgrade-safety.

15. Phase 3 — Resource Inventory & Cluster State Reconciliation

15.1 Objectives

Turn validated agent reports into an authoritative, WAL-backed resource inventory; reconcile manager intent vs. agent reality; maintain capacity conservation (I10). Constraint: agents are semi-trusted — the manager's inventory is the truth, agents propose deltas.

15.2 Detailed Implementation Steps

  • Agent resource probe: read cgroups//proc/sysfs to compute true NodeCapacity.total; report on registration and on change.
  • Manager admits capacity updates as RegisterNode/capacity-delta WAL entries (I3), updating resource-model vectors with the conservation check (I10, P9).
  • Reconciliation loop: periodically diff manager-believed leases on a node vs. agent-reported running set; converge (crash-only, P1); orphaned running tasks with no lease → kill; leased-but-not-running → relaunch or reclaim.
  • Reserved capacity accounting for static reservations and headroom (Borg-style, applied §19).
  • Emit inventory snapshot into the state machine so it survives failover (P3).
  • Copy-on-write inventory snapshots: the single writer publishes an immutable Arc<InventoryView> per epoch that scheduler read-shards consume lock-free (P5) — the mechanism that lets §16 scoring scale across cores.
  • Dirty-node index: track only nodes whose capacity changed since last cycle so reconciliation is O(dirty), not O(nodes) (§29 bottleneck 4).
  • Capacity-shrink handling: when a rebooted node returns with less capacity than its outstanding leases, mark it over-allocated and reclaim lowest-priority leases until I10 holds again.

15.3 Deliverable

A live cluster inventory reflecting 10,000 nodes, reconciling agent reality to manager intent every cycle, with capacity that always sums correctly (I10), inspectable via CLI nodes describe.

15.4 Acceptance Criteria

  • Inventory for 10,000 nodes held in ≤ 80 MB manager RAM (§32 derivation) — measured via node_inventory_bytes.
  • Capacity conservation (I10) holds after 1,000,000 randomized alloc/release ops: capacity_imbalance_total == 0.
  • Reconciliation converges a divergent node (orphan task + phantom lease) within 2 cycles in reconcile_divergence.trace.
  • Agent over-reporting capacity is clamped to probe-verified bounds in capacity_overreport.trace (T1).
  • Reconciliation cycle for 10,000 nodes completes ≤ 2 s (M14) in reconcile_scale.trace.

15.5 Conformance Fixtures

  • reconcile_divergence.trace | orphan + phantom | converges ≤ 2 cycles.
  • capacity_overreport.trace | agent claims 2× CPU | clamped, capacity_clamp_total++.
  • capacity_conservation.trace | 1M ops | imbalance 0.
  • node_drain.trace | drain node | leases migrated, no new placement.
  • reconcile_scale.trace | 10k-node reconcile | cycle ≤ 2 s (M14).

15.6 Pitfalls

  • Trusting agent capacity (T1) — accepting reported total blindly → overcommit; fix: clamp to probe bounds; detection: capacity_clamp_total.
  • Reconciliation thrash (FM-12) — aggressive convergence kills/relaunches oscillate; fix: hysteresis + confirm across 2 cycles (I14 discipline); signal: reconcile_actions_total rate.
  • Phantom capacity after crash — lease released in RAM but not WAL → leak (I10 breach); fix: rebuild inventory from WAL leases on recovery (P3).
  • Reserved vs. available confusion — double-counting reservations; fix: strict I10 partition.
  • COW snapshot churn — republishing the whole inventory view every mutation thrashes allocation; fix: structural sharing (persistent map), republish per cycle not per mutation.
  • Stale dirty-index — a node change that misses the dirty set is never reconciled; fix: periodic full sweep as a backstop (lower frequency), reconciling the fast path.

15.7 Performance Concerns

  • Inventory updates are frequent: single-writer node shard (P5) + COW snapshots for lock-free scheduler reads.
  • Reconciliation diff is O(leases-per-node): batch per node, index dirty nodes (§15.2).
  • COW view uses structural sharing: publishing a new epoch view is O(changed nodes), not O(10k).
  • Old views drop once no read-shard references them (Arc refcount), bounding memory.

15.8 Edge Cases

  • Node capacity shrinks below current allocation (heterogeneous reboot): mark over-allocated, reclaim gracefully.
  • Node draining while tasks run: no new placement, migrate on exit.
  • NUMA topology change or disk hot-swap: re-probe, update inventory.
  • Agent reports zero capacity: treat as draining.
  • Node reports a dimension the cluster doesn't track: ignore unknown dims (forward-compat, P14).
  • Label churn: a node relabeled mid-cycle invalidates in-flight offers referencing the old label (I6).
  • Two agents briefly claim one physical host after a re-image: epoch fence resolves (I2).

15.9 Failure Analysis

  • Inventory divergence (FM-7 lease leak): detected by the reconciliation diff + capacity_imbalance_total; recover by rebuilding from WAL truth (P3).
  • Capacity over-report (T1): detected by probe-clamp diff; recover by quarantining the node.
  • Blast radius: one node's schedulability; the rest of the cluster is unaffected.
  • Forensics: reconciliation log + inventory snapshot diff (tools/snapshot-diff).

15.10 Operational Notes

  • Metrics: node_inventory_bytes, capacity_imbalance_total, capacity_clamp_total, reconcile_actions_total, node_available_ratio.
  • Runbook: runbooks/node-drain.md.
  • Trace: span reconcile.cycle{node}.
  • Migration: draining is the primitive for rolling upgrades and host maintenance (§25).

16. Phase 4 — Scheduler Core & Two-Level Offer Loop

16.1 Objectives

Implement the deterministic scheduler: offer generation, feasibility filtering (hard constraints), placement scoring (Tetris alignment + soft constraints), gang atomicity, and epoch-stamped offers. Constraint: decentralised two-level scheduling (MM5, ADR-23) that is still starvation-free.

16.2 Detailed Implementation Steps

  • Offer generation: for available capacity per node, emit ResourceOffer stamped with current Epoch and ttl (P8, I6); offers are revocable (MM1).
  • Feasibility filter: apply hard Constraints (affinity/anti-affinity/taints/labels/NUMA, §8.4) to shrink candidate nodes — modelled on Kubernetes framework/plugins filter stage (applied), Nomad feasible.go (applied).
  • Placement scoring: multi-resource alignment per Tetris (Grandl et al., applied) + soft-constraint weights → PlacementScore; pick best-fit to reduce fragmentation (MM6).
  • Gang scheduling: all-or-nothing commit for a GangId (I9); if any member infeasible, place none.
  • Deterministic tie-break (P1): stable ordering by (score, workload_id) — no wall-clock, no RNG in apply.
  • Scheduling epochs: each cycle runs at a fixed epoch; accepts validated against it (I6).
  • Delay scheduling (YARN/Mesos technique, applied): if the best-scoring node is unavailable, briefly wait for locality rather than immediately placing on a poor node — bounded so it never starves (P10).
  • Offer coalescing: batch a node's fragments into one offer so a framework sees a node's full free shape (avoids the Mesos "tiny offer" fragmentation pitfall).
  • Reservation-aware filtering: honor static reservations and headroom (§15) so scoring never proposes reserved capacity.
  • Two-level modes: auto (built-in scheduler accepts) vs. framework (external scheduler decides within an offer TTL, P8) — the Mesos vs. monolithic switch (ADR-23, MM5).

16.3 Deliverable

A runnable scheduler that, given inventory + queued workloads, produces feasible, well-packed, epoch-stamped offers and placements, gang-atomic, deterministic under replay, inspectable via scheduler explain <workload>.

16.4 Acceptance Criteria

  • Scheduler decision p99 (submit→placed) ≤ 250 ms (M1) at 500k queued workloads.
  • Placement recompute cycle ≤ 500 ms for 10k nodes (M7).
  • Deterministic replay: same WAL → identical placement sequence (P1) in sched_replay.trace (golden hash match).
  • Gang atomicity (I9): a 50-task gang with one infeasible member places 0 tasks in gang_partial.trace.
  • Anti-affinity honored: no two anti-affine tasks co-placed in antiaffinity.trace.
  • No over-offering (I15): sum of outstanding offers per node ≤ available in over_offer.trace: over_offer_total == 0.

16.5 Conformance Fixtures

  • sched_replay.trace | fixed inputs | golden placement hash.
  • gang_partial.trace | infeasible gang member | 0 placed (I9).
  • antiaffinity.trace | anti-affine pair | placed on distinct nodes.
  • fragmentation.trace | mixed shapes | packing ratio ≥ 0.85.
  • stale_offer.trace | accept after epoch bump | StaleEpoch reject (I6).
  • over_offer.trace | offers exceed node available | rejected (I15).

16.6 Pitfalls

  • Offer hoarding — a framework holds offers, starving others (the Mesos pitfall, §5); fix: offer ttl + rescind (P8); detection: offer_outstanding_seconds.
  • Non-deterministic tie-break — HashMap iteration order → replay divergence (P1 breach); fix: stable sort by id; detection: replay hash mismatch.
  • Scoring O(workloads×nodes) blowup — full cross-product per cycle; fix: feasibility pre-filter to candidate set, cap candidates (M7); signal: score_candidates.
  • Fragmentation blindness (MM6) — first-fit leaves unusable holes; fix: Tetris alignment scoring; detection: packing_ratio.
  • Delay-scheduling starvation — waiting for locality forever starves a task; fix: hard wait cap that falls back to any feasible node (P10).
  • Head-of-line blocking — one un-placeable huge gang blocks the queue behind it; fix: skip-and-retry with a backfill pass for smaller work (I9 kept intact).

16.7 Performance Concerns

  • The scoring loop is the CPU hot path (§32 #9: 5×10⁷ ops/cycle): fixed-arity, cache-friendly ResourceVector.
  • Pre-filter to ~100 candidates/workload; parallelise across scheduler shards on read-only inventory snapshots (P5).
  • Candidate pre-filtering uses inverted label/zone indexes so feasibility is a set intersection, not a full node scan (§29 bottleneck 1).
  • Score computation is branch-light and SIMD-amenable over the 6-dim vector; no per-candidate allocation.

16.8 Edge Cases

  • No feasible node: workload stays QUEUED, not FAILED.
  • All nodes equal score: deterministic tie-break by (score, workload_id) (P1).
  • Gang larger than the cluster: reject at admission.
  • Constraint referencing a nonexistent label: treated infeasible.
  • Epoch bump mid-cycle: offers from the old epoch rejected (I6).
  • Workload requesting zero of every resource: placed anywhere, still leased for accounting.
  • Soft constraint no node satisfies: score penalty, still placeable.
  • Candidate node goes LOST between filter and score: dropped, re-filter next cycle (I5).

16.9 Failure Analysis

  • Scheduler deadlock/livelock (FM-3): detected by a watchdog on cycle duration; recover by aborting the cycle and re-running at a fresh epoch.
  • Placement thrash (FM-12): oscillating placements; detect via placement_churn_total; recover with hysteresis + delay-scheduling caps.
  • Blast radius: scheduling throughput only — committed leases are untouched (P13); queued work waits, never corrupts.
  • Forensics: cycle profile + flamegraph + scheduler explain on stuck workloads.

16.10 Operational Notes

  • Metrics: scheduler_cycle_ms, placement_decision_ms, packing_ratio, offer_outstanding_seconds, queued_workloads, placement_churn_total, over_offer_total.
  • Runbook: runbooks/scheduler-stall.md.
  • Trace: sched.cycle→sched.filter→sched.score.
  • Operator tool: scheduler explain <workload> surfaces per-workload feasibility and score breakdown.

17. Phase 5 — Lease & Allocation Engine

17.1 Objectives

Turn accepted offers into durable leases and drive the full offer→accept→launch→exit lifecycle with expiry, fencing (I11), and orphan reclamation — the phase that guarantees no double-allocation (I1). Constraint: a lease is visible only after quorum commit (I7).

17.2 Detailed Implementation Steps

  • Offer acceptance: validate epoch (I6) and that the accepted vector ≤ offered vector (§8.6 overclaim check); on success propose CommitLease to WAL (I7, P3).
  • Lease issuance: AllocationLease immutable post-commit (I1); capacity moved allocated→ in resource-model (I10).
  • Lease expiry: HLC-based expires (ADR-20); a lease not launched by deadline is reclaimed (ReleaseLease).
  • Fencing (I11, P4, MM4): before reissuing a lease on a SUSPECT/LOST node, bump node epoch and require the old executor to be unreachable/killed; only then reissue.
  • Orphan reclamation: reconciliation (§15) frees leases whose workload is terminal or whose node is LOST.
  • Idempotent launch (I13): launch RPC carries (workload, attempt, epoch); agent dedups.
  • Two-phase commit-free launch: because the lease is quorum-committed before the launch RPC (I7), the launch is a retriable side effect, not a distributed transaction — at-least-once delivery + agent dedup (I13) gives exactly-once effect (P11).
  • Fence protocol: fencing bumps the node epoch in the WAL (I2), then the reclaim proposal records the fence; the old executor's next status RPC carries a stale epoch and is rejected, proving it can no longer act (MM4).
  • Lease TTL renewal: a running task's lease is periodically renewed (heartbeat-driven); a manager that stops renewing (partitioned) lets the lease lapse so a new leader can safely reclaim.

17.3 Deliverable

End-to-end allocation: submit → offer → accept → committed lease → launch → running → exit → reclaim, with fencing that provably prevents two live executors on one resource set, inspectable via leases list and tools/replay.

17.4 Acceptance Criteria

  • Allocation (offer→lease-committed) p95 ≤ 40 ms (M2).
  • No double-lease under 1,000 induced failovers (I1) in failover_no_double.trace: alloc_double_owned_total == 0.
  • A LAUNCHING lease with no RUNNING ack within deadline is reclaimed and retried in launch_timeout.trace.
  • Fencing precedes every reissue (I11): unfenced_reissue_total == 0 in fence_before_reissue.trace.
  • Offer overclaim (accept > offer) rejected (§8.6) in offer_overclaim.trace.
  • Exactly-once effect (I17): a committed lease produces exactly one launch under retried RPCs in dup_effect.trace: duplicate_effect_total == 0.

17.5 Conformance Fixtures

  • failover_no_double.trace | kill leader mid-launch | no double-owned resource (I1).
  • fence_before_reissue.trace | LOST node reissue | fence precedes reissue (I11).
  • launch_timeout.trace | no RUNNING ack | reclaim + retry (I13).
  • offer_overclaim.trace | accept > offer | rejected.
  • lease_expiry.trace | unlaunched lease | expires, capacity returns (I10).
  • dup_effect.trace | retried launch RPC | one effect only (I17).

17.6 Pitfalls

  • Emitting launch before commit (I7 breach) — network launch races the WAL commit → phantom lease on rollback; fix: launch only post-commit; detection: lease_precommit_leak_total.
  • Reissue without fence (I11 breach) — a slow-but-alive node still runs the old task → double-allocation (I1); fix: epoch fence first (MM4); the canonical distributed-lock fencing problem.
  • Lease leak (FM-7) — workload terminal but lease not released → capacity leak (I10); fix: reconciliation sweep; detection: leaked_leases.
  • Clock-skew expiry — wall-clock expiry fires early under skew; fix: HLC (ADR-20).
  • Batch-commit head-of-line latency — batching too aggressively blows M2 p95; fix: adaptive batch window (size or time, whichever first); signal: lease_commit_ms histogram.
  • Renewal thundering herd — all leases renew on the same tick; fix: jittered renewal deadlines spread across the TTL window.

17.7 Performance Concerns

  • Every lease is a quorum commit (§32 #7: 5,000 commits/s at peak): batch proposals to amortise WAL fsync (M4).
  • Lease table is 500k × ~256 B = 128 MB (§32 #4): compact arena on the single-writer shard (P5).
  • Lease lookup by (node, workload) must be O(1) for reclaim: secondary indexes.
  • Indexes are updated in the same apply step to preserve I10 atomically.

17.8 Edge Cases

  • Accept for an already-expired offer: rejected, offer voided (P8).
  • Double-accept of one offer: first wins (I6).
  • Node LOST between commit and launch: reclaim the lease (I5).
  • Attempt counter overflow: cap retries, then FAILED terminal.
  • Lease for a node whose capacity shrank: reconcile (§15).
  • Split-brain accept: an old-epoch leader's accept is rejected (I2).
  • Launch RPC succeeds on the agent but the ack is lost: dedup on retry (I13).
  • Workload cancelled after commit but before launch: reclaim before launch fires.

17.9 Failure Analysis

  • Lease leak / orphan (FM-7): detected by inventory reconciliation and leaked_leases; recover by reclaim sweep.
  • Double-allocation attempt (I1): structurally blocked by I7 + I11; if the assertion ever fires it is a Sev-1.
  • Blast radius: one node's resources; no cross-node cascade (P13).
  • Forensics: WAL segment + epoch log + tools/replay of the lease's full history.

17.10 Operational Notes

  • Metrics: lease_commit_ms, leases_active, leaked_leases, unfenced_reissue_total, alloc_double_owned_total, lease_expiry_total, duplicate_effect_total.
  • Runbook: runbooks/lease-reclaim.md.
  • Trace: lease.commit→lease.launch.
  • Debug tool: tools/replay reconstructs any lease's full history from the WAL (P1).

18. Phase 6 — Runtime Executor & cgroups Isolation

18.1 Objectives

Launch real workloads under cgroups v2 + namespace isolation via an OCI runtime shim, supervise them, enforce resource limits, and capture lifecycle. Constraint: isolation before density (P6, ADR-17); the executor is the trust boundary to untrusted workload code.

18.2 Detailed Implementation Steps

  • cgroups v2 setup: create a per-task cgroup, set cpu.max, memory.max, io.max, pids.max from the lease vector (ADR-17, cgroup-v2 spec applied); enforce I10 at the kernel.
  • Namespace isolation: PID/mount/network/UTS/IPC namespaces per task (Kerrisk, applied, §5).
  • OCI runtime shim: generate an OCI runtime config and invoke runc/crun (OCI Runtime Spec applied, ADR-17); do not implement the runtime.
  • Supervision: capture stdout/stderr (bounded ring buffer, P2), forward signals, collect exit codes; report status RPC (idempotent, I13).
  • Admission enforcement at the node: reject a launch that would exceed node available (I10) — belt-and-suspenders to the scheduler.
  • Preemption support: SIGTERM→grace→SIGKILL; do not free resources until exit confirmed (I14).
  • cgroup hierarchy: a per-agent root cgroup with per-task children so kernel accounting rolls up; the agent reads memory.current/cpu.stat to feed usage telemetry back (§15 reconciliation).
  • Image handling: pull via the OCI image spec into a local content-addressed store (ADR-16); the runtime shim mounts the rootfs — image build/registry is delegated (§1 boundaries).
  • Crash re-adoption: on agent restart, enumerate existing task cgroups and re-attach supervision rather than kill-and-relaunch (crash-only, P1) so a manager restart does not disturb running work.
  • Seccomp + non-root: apply a default-deny seccomp profile and drop capabilities before exec (T6, SECURITY.md).

18.3 Deliverable

Isolated workloads run under enforced cgroups limits, with captured logs/exit codes and clean preemption, verified by cgroup accounting matching the lease and by memory-limit OOM behavior.

18.4 Acceptance Criteria

  • A task exceeding memory.max is OOM-killed by the kernel, reported as FAILED, in mem_limit.trace — measured, not asserted.
  • CPU throttling: a task capped at 500 mc uses ≤ 0.5 cores ±5% under load in cpu_cap.trace.
  • Executor launch latency p95 ≤ 1 s (M9).
  • Preemption frees resources only after exit ack (I14): premature_reuse_total == 0 in preempt_safety.trace.
  • Relaunch of an already-running (workload,attempt) is a no-op (I13) in dup_launch.trace.
  • Agent restart re-adopts running task cgroups without killing them (crash-only, P1) in readopt.trace: zero unintended restarts.

18.5 Conformance Fixtures

  • mem_limit.trace | task exceeds memory.max | OOM-killed, FAILED.
  • cpu_cap.trace | CPU-bound task | throttled to cap ±5%.
  • preempt_safety.trace | preempt then reuse | reuse only post-exit (I14).
  • dup_launch.trace | duplicate launch | no-op (I13).
  • zombie_reap.trace | child exits, parent gone | reaped, no zombie.
  • readopt.trace | agent restart with running tasks | cgroups re-adopted, no restart.

18.6 Pitfalls

  • cgroup leak — cgroups not removed on exit → pids.max exhaustion cluster-wide; fix: teardown on reap; detection: orphan_cgroups.
  • Zombie executors (FM-8) — orphaned child processes; fix: subreaper + PID-namespace init; signal: zombie_procs.
  • Freeing before kill confirmed (I14 breach) — resources reused while victim still writes → corruption; fix: withhold until exit ack.
  • Signal race on preempt — SIGKILL before flush; fix: grace period; the canonical container-runtime shutdown race.
  • Re-adoption mismatch — after restart the agent finds a cgroup whose lease the manager already reclaimed; fix: reconcile against manager truth (§15) and kill the orphan.
  • Memory throttling vs. OOM — setting memory.high (throttle) vs. memory.max (kill) changes behavior; pick per QoS class, document it (P6).

18.7 Performance Concerns

  • cgroup creation is syscall-heavy: pool/pre-create where safe.
  • Log capture is bounded (ring buffer) to avoid disk fill (P2).
  • Namespace setup dominates M9 launch latency: measure with executor_launch_ms.
  • Image pull is the M9 long tail for cold images: a warm content-addressed cache holds p95; cold pulls reported separately.

18.8 Edge Cases

  • Task fork-bombs: pids.max caps it.
  • Memory spike faster than accounting: kernel OOM handles it.
  • Node reboot with running tasks: reconcile marks LOST (§15).
  • Image pull failure: FAILED with retry.
  • NUMA pinning conflict: fall back to unpinned with a warning.
  • SIGKILL-uncatchable task: grace timeout → force.
  • Task ignores SIGTERM: escalate to SIGKILL after grace.
  • Disk-full on log capture: drop-oldest in ring buffer, never block the task (P2).
  • cgroup controller disabled in the kernel: fail launch with a clear error, never run unisolated (P6).

18.9 Failure Analysis

  • Executor zombie (FM-8): detected by zombie_procs; recover by subreaper reap + cgroup teardown.
  • Executor escape (T6): contained by namespaces + seccomp; detect via audit log anomalies.
  • cgroup leak: detect via orphan_cgroups; recover by teardown on next reconcile.
  • Blast radius: one node; a compromised task cannot reach the control plane (trust boundary, §3).
  • Forensics: task stdout/stderr ring buffer + exit code + cgroup stats snapshot.

18.10 Operational Notes

  • Metrics: executor_launch_ms, orphan_cgroups, zombie_procs, task_oom_total, preempt_total, seccomp_violation_total.
  • Runbook: runbooks/executor-cleanup.md.
  • Security: default-deny seccomp + non-root, capabilities dropped (SECURITY.md, T6).
  • Trace/Upgrade: executor.launch→executor.exit; agent restart re-adopts running cgroups (crash-only, P1).

19. Phase 7 — Multi-Tenant Governance (Hierarchical Queues, DRF, Preemption)

19.1 Objectives

Implement hierarchical queues, DRF fair-share across the queue tree (I8), quota/borrowing, and priority preemption. Constraint: fairness is progress (P10); quota is admission not eviction (P7).

19.2 Detailed Implementation Steps

  • Queue tree: parent/child QueueDefinitions with guaranteed and max shares and weights (YARN CapacityScheduler/FairScheduler, applied §5).
  • DRF share computation (Ghodsi et al., applied; I8): compute each tenant's dominant share; always allocate next to the lowest (P10); recompute per cycle within M10.
  • Quota + borrowing: a queue under its guaranteed share may borrow idle capacity up to max; enforce I4; revoke borrowed capacity when the owner needs it.
  • Priority preemption (Borg, applied §5): higher-priority queued work preempts lower-priority running work when its queue is under guarantee; select victims by lowest priority then latest start; fence victims (I14).
  • Headroom: keep a configurable reserve to absorb bursts (Borg-style, applied).
  • Deterministic ordering (P1): DRF ties broken by (dominant_share, queue_id, workload_id).
  • Fairness-formulation choice: DRF (per-cycle greedy, I8) is chosen over min-cost-flow scheduling (Quincy, Isard et al. 2009, applied) — the flow formulation optimizes fairness-vs-locality globally but recomputes a whole-cluster optimization per round, blowing M10 at 500k workloads.
  • Hierarchical DRF: apply DRF recursively down the queue tree — split a parent's share among children by weight, then among leaf tenants (YARN FairScheduler nesting, applied).
  • Min-share preemption vs. fair-share preemption: preempt only enough to bring an under-guarantee queue to its guarantee (min-share), then optionally toward fair-share with a higher threshold — two tunable timeouts, as in YARN.
  • Preemption cost model: prefer victims that are cheap to kill (recently started, checkpointable) to minimise lost work; never break a gang partially (I9, I14).
  • Elastic quotas: a queue's max-share can exceed its guarantee, borrowing from idle siblings (I4), reclaimed on demand within 2 cycles (§19.4).

19.3 Deliverable

Fair-share scheduling across a queue hierarchy: no tenant starves, quotas hold, borrowing is reclaimed, and preemption respects priority and safety (I14), inspectable via queues tree and queues shares.

19.4 Acceptance Criteria

  • DRF equalises dominant shares within ±2% across 8 tenants in drf_fairness.trace (matches Ghodsi model, §8.5).
  • No tenant starves > 3 scheduling cycles under contention (P10) in no_starvation.trace.
  • Quota non-exceedance (I4): queue_over_quota_total == 0 across quota_borrow.trace.
  • Borrowed capacity reclaimed within 2 cycles when owner submits (borrow_reclaim.trace).
  • Preemption frees only after victim exit (I14): premature_reuse_total == 0 in preempt_priority.trace.
  • DRF queue evaluation cycle ≤ 1 s @ 500k workloads (M10).
  • Preemption decision latency p95 ≤ 200 ms (M13) in preempt_latency.trace.

19.5 Conformance Fixtures

  • drf_fairness.trace | 8 tenants, mixed shapes | dominant shares equal ±2%.
  • no_starvation.trace | heavy contention | no starvation > 3 cycles.
  • quota_borrow.trace | borrow idle capacity | I4 holds, reclaim works.
  • preempt_priority.trace | high-pri preempts low | victim fenced (I14).
  • hierarchy_reweight.trace | change weights | shares re-converge.
  • preempt_latency.trace | high-pri burst | preemption decision p95 ≤ 200 ms (M13).

19.6 Pitfalls

  • DRF starvation from stale shares — computing shares from RAM cache diverged from WAL; fix: recompute from committed state (P1); detection: queue_dominant_share divergence.
  • Preemption cascade (FM-12) — preempt→resubmit→preempt loop; fix: preemption cooldown + only when under guarantee; signal: preempt_total rate.
  • Borrow without reclaim (I4 breach) — borrowed capacity never returned starves owner; fix: reclaim trigger on owner submit; detection: borrowed_bytes per queue.
  • Priority inversion — low-pri holds a gang blocking high-pri; fix: gang-aware preemption; the classic scheduling inversion.
  • Recompute-from-cache drift — computing shares from a diverged RAM cache; fix: recompute from committed state (P1, MM3); detection: differential vs. golden.
  • Elastic-quota flap — borrow granted then reclaimed then re-granted every cycle; fix: reclaim hysteresis and a minimum hold time.

19.7 Performance Concerns

  • DRF recompute is O(tenants × dims): fixed dims (6) keep it linear in tenants.
  • Sorting 500k workloads by dominant share drives M10: use an incremental per-queue heap, not a per-cycle re-sort.
  • Queue math stays on the single-writer scheduler shard (P5).
  • Preemption victim selection is bounded to the under-served delta: O(preempted), not O(running).

19.8 Edge Cases

  • Empty queue: contributes zero share.
  • Queue with guaranteed > cluster capacity: over-subscribed config → warn.
  • Gang that can't be preempted atomically: skip that victim (I9).
  • Tenant with a single huge task: dominant share jumps discretely.
  • Reweight mid-cycle: apply next cycle (P1).
  • Circular queue parenting: rejected at config time.
  • Children guaranteed shares summing above 100%: normalize or reject.
  • Tenant submitting faster than it can be scheduled: bounded queue rejects (P2).
  • Preemption that would violate a gang's atomicity: skip that victim (I9, I14).

19.9 Failure Analysis

  • Queue starvation (FM-5): detected by the fairness monitor + queue_dominant_share outliers; recover by rebalancing / preemption.
  • Preemption thrash (FM-12): detected by preempt_total rate; recover with a preemption cooldown.
  • Borrow-without-reclaim (I4): detected by per-queue borrowed_bytes not returning; recover by forced reclaim.
  • Blast radius: tenant fairness, never correctness — no invariant on I1/I10 is at risk.
  • Forensics: per-cycle dominant-share log + preemption decision trace.

19.10 Operational Notes

  • Metrics: queue_dominant_share, queue_over_quota_total, borrowed_bytes, preempt_total, queue_depth, starvation_cycles.
  • Runbooks: runbooks/quota-breach.md, runbooks/fairness-regression.md.
  • Trace: drf.recompute→preempt.select.
  • Config: queue changes are WAL entries (P3) — auditable, replayable, rolling-upgrade safe.

  • Cardinality explosion — labeling metrics by workload_id → Prometheus OOM; fix: bounded label sets, exemplars for high-cardinality; detection: prometheus_tsdb_series.
  • Trace sampling hides tail — head-sampling drops the slow requests (the Tail-at-Scale lesson, §5); fix: tail-based sampling for latency outliers.

  • Blocking export on the hot path — a synchronous OTLP export stalls the scheduler; fix: async batched export off-loop, drop on backpressure (P2, ADR-21).
  • Metric-name drift across versions — renamed series break dashboards silently; fix: a metric-name registry checked in CI (part of metric_inventory.json).

20.7 Performance Concerns

  • Telemetry must not perturb the scheduler hot path: lock-free counters + per-shard aggregation (P5).
  • Export off the critical path: async batched OTLP, drop on backpressure (ADR-21).

  • Event bus is bounded to avoid backpressure into the scheduler (ADR-21).

20.8 Edge Cases

  • Trace context lost across a retry: regenerate a span link.
  • Clock skew in trace timestamps: HLC-normalize (ADR-20).
  • Replay of a WAL from an older schema: honor §25 compat.
  • Missing telemetry backend: degrade, don't crash (P13).
  • High-cardinality label attempted: reject at registration, keep exemplars instead.

20.9 Failure Analysis

  • Cardinality blow-up: detect via prometheus_tsdb_series; recover by dropping the offending label set.
  • Forensics: the WAL is the ultimate artifact — every incident is replayable by tools/replay.

21. Phase 9 — Failover, HA & Scale Hardening

21.1 Objectives

Deliver HA control plane: leader election, hot-standby failover, reconciliation on takeover, split-brain prevention (I2), and scale hardening to the §4 targets. Constraint: RTO ≤ 300 s (target ≤ 30 s), RPO 0; fencing over liveness (P4, MM4).

21.2 Detailed Implementation Steps

  • Leader election via Raft (ADR-09); on election, bump Epoch (I2, MM8) and reject all stale-epoch traffic.
  • Takeover reconciliation: new leader replays WAL to serving state (M8), then reconciles agent reality (§15) and fences any node whose leases predate a failover it can't confirm (I11).
  • Split-brain prevention: an old leader that lost quorum cannot commit (Raft) and its epoch is stale (I2) — its writes are rejected (MM8).
  • Scale hardening: shard the scheduler read path across cores on COW inventory snapshots (P5); batch WAL commits (M4); cap candidate scoring (M7).
  • Rolling upgrade: drain-based leadership handover within 60 s (§4); mixed-version compat (§25, P14).
  • Load-gen soak: sustained 5,000 tasks/s (M12) for 24 h.
  • Pre-vote (Raft extension, applied): a partitioned follower runs a pre-vote round before incrementing its term, preventing disruptive term inflation and needless leader churn when it rejoins (FM-4).
  • Warm standby: followers keep the state machine hot by applying the committed log continuously, so takeover replays only the un-applied tail (M8 lever, §32 #8).
  • Priority-aware degradation: under quorum loss (FM-10) the surviving read-only plane still serves inspection and lets running leases renew locally within their TTL, so workloads survive a control-plane outage (P13).
  • Shard rebalancing: when agents are repartitioned across manager shards, migrate ownership via WAL hand-off entries so no node is double-owned during the move (I1).

21.3 Deliverable

A 3–7 manager HA cluster that survives leader kill with RPO 0, recovers within RTO, prevents split-brain, and sustains the §4 scale targets under a 24 h soak, verified by chaos + soak fixtures.

21.4 Acceptance Criteria

  • Failover recovery (leader kill → serving) ≤ 300 s, target ≤ 30 s (M6) in chaos_failover.trace.
  • Zero data loss across failover (RPO 0, I7) — reuses raft_kill_leader.trace acceptance.
  • Split-brain: an old leader's post-partition write is rejected (I2/MM8) in split_brain.trace: epoch_regression_total == 0 committed.
  • Sustained ≥ 5,000 tasks/s for 24 h with p99 within M1 (M12) in soak_24h.trace.
  • No double-allocation across 1,000 chaos failovers (I1) — alloc_double_owned_total == 0.
  • Exactly-once effect preserved across failover (I17): no duplicate launches when a leader dies mid-dispatch in failover_dup_effect.trace.

21.5 Conformance Fixtures

  • chaos_failover.trace | random leader kills | RTO ≤ 300 s, no loss.
  • split_brain.trace | partition old leader | stale writes rejected (I2).
  • soak_24h.trace | 5k tasks/s, 24 h | p99 within M1, no leak.
  • net_partition.trace | minority partition | minority read-only (FM-10).
  • rolling_upgrade.trace | mixed versions | no compat break (P14).
  • failover_dup_effect.trace | leader dies mid-dispatch | one effect only (I17).

21.6 Pitfalls

  • Split-brain double-leader (FM-4) — network partition yields two leaders; prevented by Raft quorum + epoch (I2, MM8); detection: leader_changes_total, epoch_regression_total; the canonical distributed-consensus failure.
  • Slow failover from cold replay — replaying a huge WAL blows RTO (M6); fix: frequent snapshots (M5) shrink the replay tail.
  • Reissue before fence on takeover (I11 breach) — new leader reissues leases a slow old node still serves → double-allocation (I1); fix: fence-before-reissue (P4).
  • Clock-skew fencing (FM-11) — skew triggers false LOST → needless reissue; fix: HLC (ADR-20).
  • Disruptive rejoin — a partitioned old leader rejoins and forces an election; fix: pre-vote (§21.2); detection: leader_changes_total spike.
  • Standby cold on takeover — a follower that lagged apply replays a long tail, blowing M6; fix: warm standby + bounded apply lag alert.

21.7 Performance Concerns

  • Failover time is dominated by replay (M8): snapshot cadence (M5) is the lever (§32 #8).
  • At scale the scheduler read path is the bottleneck (§29): shard it across cores (P5).
  • WAL commit batching (M4) sets the placement-throughput ceiling (M12).
  • Watch NUMA effects on the writer shard: pin it, keep its working set node-local.

21.8 Edge Cases

  • Simultaneous leader + agent failure: reconcile both domains on takeover (P13).
  • Partition isolates the leader from agents but not from quorum: leader stays, agents re-register.
  • Flapping leader: dampen with election-timeout jitter + pre-vote (§21.2).
  • WAL tail longer than the snapshot interval: bounded by M5 cadence.
  • Upgrade that changes the state-machine version mid-failover: feature-epoch gating (§25).
  • Minority partition that heals: rejoining nodes catch up via snapshot install (§14).

21.9 Failure Analysis

  • Split-brain (FM-4): structurally prevented (I2 + Raft quorum); if epoch_regression_total ever increments it is a Sev-1.
  • Quorum loss (FM-10): control plane read-only; existing workloads keep running (P13); recover by restoring quorum.
  • Slow failover: detect via failover_seconds breaching M6; recover by shortening snapshot cadence (M5).
  • Blast radius: control-plane availability only, bounded by the 99.95% budget (§4, §32 #11).
  • Forensics: epoch log + Raft term history + tools/replay.

21.10 Operational Notes

  • Metrics: leader_changes_total, failover_seconds, epoch_regression_total, replay_seconds, tasks_placed_per_sec.
  • Runbooks: runbooks/failover.md, runbooks/rolling-upgrade.md, runbooks/split-brain.md.
  • Deployment: 5 managers across 3 AZs — quorum survives one AZ loss.
  • Canary: upgrade one follower first, soak, then the leader last via handover-drain (≤ 60 s, §4).

25. Compatibility & Versioning

  • Wire compatibility (ADR-05, P14): protobuf proto3, fields additive-only, tags never reused, unknown fields preserved. Minor versions are wire-compatible; breaking changes bump major.

  • Migration: additive schema changes apply live; a required transform is a WAL migration entry replayed deterministically (P1).
  • Deprecation policy: announce → emit deprecated_api_total → remove after ≥ 1 major.
  • Compatibility test gate: CI runs the previous major's client against the current server and the current client against the previous server; a break fails the build (P14).
  • SemVer policy: MAJOR = wire/storage break; MINOR = additive feature; PATCH = fix. Channels dev/staging/stable (ADR-22).
  • Rolling-upgrade guarantee: mixed-version managers interoperate within one major; leadership handover-drains within 60 s (§4); the rolling_upgrade.trace fixture (§21) gates this.
  • Concrete evolution examples: adding a gpu_topology field to WorkloadDescriptor is a new proto tag (MINOR); a new WalEntry variant is additive (older managers reject unknown variants only if they must apply them — hence variants are gated behind a feature-epoch); removing overcommit_ratio is a MAJOR requiring a two-release deprecation window.
  • Feature-epoch gating: a new WAL entry type is only proposed once every manager in the quorum advertises support (discovered via a capabilities handshake), so a mixed-version quorum never commits an entry a follower cannot apply — the etcd/Raft membership-safety discipline (§5).
  • Agent↔manager skew: an agent may be one minor version ahead or behind its manager; heartbeat and launch schemas carry a version field and negotiate the common subset. Downgrade-safety: a manager rollback must read WAL written by the newer version (backward-compat ≥ 2 majors), so snapshots embed the writing version.

26. Testing & Verification Strategy

  • Unit: per-crate logic — resource-model algebra, DRF math, constraint matching.
  • Integration: multi-crate flows — submit→place→lease→launch on a docker-compose cluster.
  • Property (ADR-13): randomized event streams asserting I1–I17 (e.g. capacity conservation I10, no double-lease I1); shrinks to a minimal failing WAL prefix (§7).
  • Differential: DRF and placement outputs compared against a reference model derived from the Ghodsi/Tetris papers (§5) — catches subtle fairness drift.
  • Fuzzing (ADR-14, fuzz/): targets on the RPC/proto parser, constraint parser, and lease reconciliation — malformed/malformed_proto.bin inputs must not panic.
  • Chaos: random leader/agent kills, partitions, clock skew (chaos_failover.trace, split_brain.trace, net_partition.trace).
  • Simulation testing: the sim-harness (§12) is the primary correctness vehicle — a deterministic FoundationDB-style simulator where every source of nondeterminism (clock, network, scheduling) is controlled and every invariant is asserted per event.
  • Deterministic replay (P1): every incident WAL replays to an identical state hash (replay_fidelity.trace); the backbone of debugging.
  • Soak: 24 h at 5,000 tasks/s (soak_24h.trace, M12) — catches leaks (FM-7) and drift.
  • Fault injection: disk-full, fsync-stall, dropped RPC, corrupted WAL bit (wal_corrupt_bit.bin).
  • Conformance (conformance/): the protocol fixtures across phases (§12–§21 N.5) run in CI.
  • Perf-regression gating: every M# target (§28) is a CI benchmark gate — a regression fails the build.

Every phase's N.5 fixtures feed this matrix; invariants (§7) are the property-test oracles.

  • Property test oracles (concrete): I1 — after any event sequence, the set of (node, resource-unit) → lease is a partial function (no unit maps to two leases); I10 — for every node, the four vectors sum exactly; I8 — the tenant chosen for the next allocation has the minimum dominant share; I3 — applying a shuffled log fails the index-monotonicity assert. Each oracle is a boolean over the post-state, cheap enough to check after every event.
  • Differential harness: a ~200-line executable reference model of DRF+placement (deliberately naive, un-optimized) runs beside the production scheduler on the same input; any divergence in the placement decision (not just the final state) is a bug in the fast path — this is how the incremental DRF heap (§19.7) is validated against the O(n log n) re-sort.
  • Chaos matrix: the cross-product of {leader kill, follower kill, network partition, disk-fsync stall, clock skew ±5 s, agent mass-reconnect} × {idle, 50% load, overload} run nightly; each cell asserts the relevant invariant and the relevant M# SLO.
  • Fuzzing corpus: seeded from real malformed inputs (malformed_proto.bin, wal_corrupt_bit.bin) and grown by coverage; a crash or invariant-assert is a CI-blocking failure. Targets are re-run on every dependency bump (ADR-03).
  • Coverage gate: line coverage ≥ 80% and branch coverage on the apply path ≥ 90% (the apply path is the correctness core, P1); a drop fails CI.

29. Scalability Analysis

  • Constant vs. grows. Per-node record size O(1); inventory RAM O(nodes) (§32: ~80 MB @ 10k). Lease table O(active leases) (§32: ~128 MB @ 500k). Heartbeat ingest O(nodes/interval) (§32: 5,000 hb/s). Scheduler scoring O(queued × candidate-nodes) — the super-linear term, capped by feasibility pre-filter (M7). DRF recompute O(tenants × dims), dims fixed (6).
  • Named bottlenecks, in order: (1) scheduler scoring loop (CPU, §16 hot path); (2) WAL commit throughput (M4 sets M12 ceiling); (3) heartbeat ingest (M3); (4) inventory single-writer shard contention; (5) fragmentation (MM6) — the real capacity ceiling, not raw utilization.
  • Horizontal scaling: shard the scheduler read path across cores on COW inventory snapshots (P5); partition agents across manager shards; the WAL is the serialization point (vertical: faster NVMe, group commit).
  • Vertical scaling: more cores for scoring; more RAM for inventory+leases; NVMe for WAL.
  • Sharding/partitioning: partition by node-set or queue subtree; cross-shard gangs need coordination (cost).
  • Coordination overhead: every lease is one quorum commit — the fundamental tax; batching amortises it.
  • Practical ceiling and levers. Single-cluster ceiling ≈ 10k nodes / 500k tasks bounded by WAL commit rate and scoring CPU. Beyond it: (a) shared-state optimistic scheduling (Omega, §34); (b) federation across cells (PhaseDeferred("§35")); (c) two-level delegation to per-framework schedulers (Mesos model already in place).
  • Why WAL commit is the hard serialization point. Every externally-visible allocation is one quorum commit (I7); this is inherently serial per Raft group and cannot be parallelized without sharding the log. At 5,000 commits/s (§32 #7) with an 8 ms fsync (M4), group-commit batching is the only lever within one group — it trades a few ms of latency (M2) for throughput. The escape hatch above the ceiling is multiple Raft groups (one per node-partition or queue-subtree), which reintroduces the cross-group gang-placement coordination cost (§29 sharding).
  • Scoring parallelism math. Scoring is embarrassingly parallel across workloads on a read-only COW inventory snapshot (P5, §15.2): N read-shards give near-linear speedup until they contend on the shared candidate index or memory bandwidth. §32 #9 (5×10⁷ ops/cycle) needs ~4 cores for M7; the design reserves headroom to 8 so a 2× load spike does not blow the budget.
  • Fragmentation as a growth term. Utilization can rise while schedulability falls (MM6): as the cluster fills, the free-shape distribution narrows and large/gang workloads fail placement first. The lever is packing quality (Tetris scoring, §16) and admission of workload shapes the cluster can still fit — a capacity dimension the raw §4 numbers do not capture.
  • Coordination overhead scaling. Heartbeat ingest (5,000 hb/s) and reconciliation are O(nodes) and grow linearly; they are cheap relative to scoring. The nonlinear risk is cross-shard coordination once the log is partitioned — kept O(gangs spanning shards), which the placement policy minimizes by preferring single-shard gangs.
  • Vertical vs. horizontal decision. Below the ceiling, prefer vertical (more cores/RAM/faster NVMe on managers) — it avoids the coordination tax. Cross the ceiling only when a single Raft group's commit rate (§32 #7) or scoring CPU (§32 #9) is exhausted; then partition into multiple groups and accept cross-group gang coordination.
  • Memory ceiling headroom. Core state is ~1.2 GB (§32 #5); the 16 GB manager ceiling (M11) leaves ~12× headroom for indexes, COW view retention, and telemetry — the growth term to watch is COW-view retention under slow read-shards, bounded by dropping old epochs promptly (§15.7).

30. Mental Models & First Principles

  1. MM1 — An offer is a revocable lease, not ownership. The scheduler never owns a node; it holds a time-boxed, epoch-stamped claim. Predicts: why offers must expire and why acceptance is racy. Bug without it: treating offers as durable → double-booking. Resolved in: §8 (offer protocol) and Phase 5 (§17).
  2. MM2 — DRF equalizes the dominant share, not each resource. Fairness across resource types means equalizing each tenant's max-normalized resource, not giving equal CPU and equal RAM. Predicts: the §8.5 3-vs-2 split. Bug without it: "fair" schedulers that starve mem-heavy tenants. Resolved in: §7 (I8) and Phase 7 (§19).
  3. MM3 — The WAL is the database; RAM is a cache. Durable truth is the log; in-memory state is a rebuildable projection. Predicts: why nothing is visible before commit (I7) and why recovery is replay. Bug without it: mutating RAM then losing it on crash → divergence. Resolved in: Phase 2 (§14) and §7 (I3/I7).
  4. MM4 — Fence, don't detect. You cannot reliably tell a dead node from a slow one; you can only fence a possibly-live holder by epoch. Predicts: why failover needs epochs before reissue. Bug without it: reissuing a lease a slow node still serves → double-allocation. Resolved in: §7 (I11) and Phase 9 (§21).
  5. MM5 — Two-level scheduling trades global optimality for decentralization. Offering resources to frameworks gives autonomy at the cost of a globally-optimal packing. Predicts: why Mesos scales frameworks but can fragment. Bug without it: expecting monolithic-optimal placement from an offer model. Resolved in: §3 and Phase 4 (§16).
  6. MM6 — Fragmentation is the real capacity ceiling. A cluster at 70% utilization can be unschedulable for large shapes because free capacity is scattered. Predicts: why packing scoring matters more than raw headroom. Bug without it: provisioning by average utilization and still failing placements. Resolved in: §29 and §32.
  7. MM7 — Backpressure is admission control at every hop. A bounded queue that rejects is a hop-local admission controller. Predicts: why every stream must be bounded to avoid OOM cascades. Bug without it: unbounded ingest → memory blow-up under load (FM-9). Resolved in: §6 (P2) and §24.
  8. MM8 — A monotonic epoch linearizes failover. One always-increasing number turns split-brain into a stale-write rejection. Predicts: why an old leader's writes are safely dropped. Bug without it: two leaders both commit → divergence. Resolved in: §7 (I2) and Phase 9 (§21).
  9. MM9 — Exactly-once is at-least-once plus idempotency. You cannot get exactly-once delivery over an unreliable network; you get exactly-once effect by making the receiver dedup a retried, at-least-once message. Predicts: why launch/kill RPCs carry an idempotency key. Bug without it: duplicate task launches after a lost ack. Resolved in: §6 (P11), §7 (I13/I17), Phase 5 (§17).
  10. MM10 — Admission is cheaper than eviction. Rejecting work you cannot fairly run costs nothing; admitting it then killing it wastes the work already done and churns the cluster. Predicts: why quota is enforced at submit, not by reaper. Bug without it: admit-then-kill loops (FM-12). Resolved in: §6 (P7), §7 (I4), Phase 7 (§19).

32. Back-of-Envelope Capacity Model

Each number is derived from the §4 System Constraints table.

  1. Heartbeat ingest rate = nodes ÷ interval = 10,000 ÷ 2 s = 5,000 hb/s. (Drives M3.)
  2. Heartbeat bandwidth = rate × payload. Payload ≈ 4 KB (resource vector + running-task ids). 5,000 × 4 KB = 20 MB/s ≈ 160 Mbps ingest per leader.
  3. Inventory RAM = nodes × per-node record. Record ≈ 8 KB (capacity vectors + labels + state). 10,000 × 8 KB = 80 MB (Phase 3 acceptance).
  4. Lease-table RAM = active leases × record. 500,000 × 256 B = 128 MB.
  5. Workload-state RAM = workloads × record. 500,000 × 2 KB = 1.0 GB. Sum (3)+(4)+(5) ≈ 1.2 GB core state ⇒ 16 GB manager ceiling (§4) leaves headroom for telemetry/indexes (M11).
  6. Snapshot size ≈ core state = 1.2 GB (from 5). At 500 MB/s NVMe (§4), write time = 1.2 GB ÷ 500 MB/s = 2.4 s ⇒ within the ≤ 5 s snapshot budget (M5).
  7. WAL write rate = peak placements × entry size. 5,000 tasks/s (M12) × 512 B = 2.5 MB/s; with Raft quorum ×3 replication = 7.5 MB/s cluster WAL traffic — trivial for NVMe, so M4 is fsync-latency-bound, not bandwidth-bound.
  8. Recovery time = snapshot load + tail replay. Tail = ingest × snapshot-interval. At 5,000 entries/s over a 60 s snapshot interval = 300,000 entries; replay at ~200k entries/s = 1.5 s; + snapshot load 2.4 s (6) = ~4 s ⇒ far under RTO 300 s and even the 30 s target (M6/M8).
  9. Scoring ops per cycle = queued × candidates-per-workload. With feasibility pre-filter to ~100 candidates: 500,000 × 100 = 5 × 10⁷ scoring ops/cycle. At ~50 M ops/s/core that is ~1 s/core ⇒ shard across ~4 cores to hit the ≤ 500 ms recompute (M7).
  10. FD budget = agent connections + client streams. 10,000 agents (HTTP/2 multiplexed, 1 conn each) + ~10,000 operator/client streams = ~20,000 FDs ⇒ well under the 200,000 budget (§4), leaving room for ephemeral connections.
  11. Availability budget = (1 − 0.9995) × 30 days = 21.9 min/month downtime. With ~4 s failovers (8), that permits ~300 unplanned failovers/month before the budget is spent — the error-budget lever for release gating (§24).
  12. Telemetry egress = placement rate × span size. 5,000 placements/s (M12) × ~1 KB/span = 5 MB/s trace data; at 10% head-sampling + full tail-sampling that is ~0.6 MB/s steady per manager — small vs. the 160 Mbps heartbeat ingest (2), so telemetry is not a bandwidth constraint but a cardinality one (§20 pitfall).

34. Alternative Architectures (Roads Not Taken)

A. Shared-state optimistic scheduling (Omega model).

[ Scheduler 1 ]-\                       /-> conflict?
[ Scheduler 2 ]--> shared cell state <--   retry on stale
[ Scheduler N ]-/    (versioned)         \-> commit if unchanged

Multiple schedulers read a shared, versioned cell state and optimistically commit placements, retrying on conflict. Wins at extreme scale/heterogeneity where a single scheduling loop is the bottleneck (the §32 #9 scoring wall). Embodied by Omega (Schwarzkopf et al. 2013, §5). Rejected here (ADR-23) because conflict-retry storms under high contention hurt tail latency (M1) and the added complexity isn't justified below the 10k-node ceiling; revisit if that ceiling is hit (§29).

B. Monolithic scheduler (Kubernetes/Borg model).

[ submit ] -> [ single scheduler: filter -> score -> bind ] -> [ etcd ]

One central scheduler makes every decision against a global view. Wins when global-optimal packing and simple reasoning matter more than framework autonomy, and one operator owns all workloads. Embodied by the Kubernetes scheduler and Borg (§5). Rejected here because it couples all frameworks to one scheduling policy and one throughput ceiling; the offer model (ADR-23) preserves per-framework autonomy — though we borrow its filter/score plugin structure (§16).

C. Gossip-based decentralized allocation (no central log).

[ agent ]<->[ agent ]<->[ agent ]   (peer gossip of capacity; local claims)

Agents gossip capacity and place work peer-to-peer with no central WAL. Wins for very large, loosely-consistent, best-effort clusters where eventual consistency and partition tolerance beat strict correctness. Embodied by Sparrow (Ousterhout et al. 2013, §5), which uses batch sampling of a few nodes per decision. Rejected here because it cannot provide the no-double-allocation invariant (I1) or RPO 0 (§4) — our defining property (§4) requires a linearizable log (P3).

D. Batch/gang-exclusive HPC scheduling (Slurm model).

[ job queue ] -> [ backfill scheduler ] -> whole-node/whole-core allocation
                          |                (exclusive, gang, wall-time limits)
                          +-> reservation + fair-share tree

Jobs request whole nodes/cores for a bounded wall-clock time; a backfill scheduler packs shorter jobs into reservation gaps. Wins for HPC/MPI workloads needing exclusive, tightly-coupled gangs and predictable wall-time (tightly-coupled scientific computing). Embodied by Slurm. Rejected here because whole-node exclusivity wastes capacity for the fine-grained, long-running, elastic services this allocator targets (ADR-27 chose millicore granularity); the gang and reservation primitives (§19, I9) are borrowed, the exclusivity model is not.

36. Glossary

  • Agent — per-node daemon that probes capacity, heartbeats, and supervises executors.
  • Admission control — accept/reject decision at submit based on quota headroom (I4, P7).
  • Allocation — capacity assigned to a workload, made durable as a lease (I1).
  • Anti-affinity — constraint forbidding co-placement of two workloads (§8.4).
  • Attempt — a numbered retry of a workload; key for idempotent launch (I13).
  • Available capacity — total − allocated − reserved, per node/resource (I10).
  • Backpressure — bounded queues + credit flow-control shedding load at each hop (P2, ADR-21).
  • Borrowing — a queue temporarily using idle capacity above its guarantee, reclaimable (I4).
  • Capacity conservation — allocated + reserved + available = total, always (I10, P9).
  • Control plane — the manager cluster making scheduling/allocation decisions.
  • DRF (Dominant Resource Fairness) — fairness equalizing each tenant's dominant (max-normalized) share (I8, MM2).
  • Dominant resource — the resource type a tenant uses the largest normalized fraction of.
  • Epoch — monotonically increasing cluster generation; fences stale writers (I2, MM8).
  • Executor — the process that launches and supervises a workload under isolation.
  • Failure detector — heartbeat-age logic classifying nodes SUSPECT/LOST (I5).
  • Fencing — invalidating a possibly-live holder by epoch before reissuing its lease (I11, P4, MM4).
  • Framework — an external scheduler that accepts offers (Mesos model, ADR-23).
  • Fragmentation — scattered free capacity that can't fit large shapes (MM6).
  • Gang scheduling — all-or-nothing placement of a set of tasks (I9).
  • Guaranteed share — the capacity a queue is entitled to before borrowing.
  • Headroom — reserved slack to absorb bursts (Borg-style).
  • Heartbeat — periodic agent liveness + capacity report (interval 2 s).
  • Hybrid Logical Clock (HLC) — skew-tolerant causal timestamp (ADR-20).
  • Lease — a durable, time-boxed, single-owner allocation record (I1, I7).
  • Manager — a control-plane replica; one is Raft leader.
  • Offer — a revocable, epoch-stamped resource proposal to a framework (P8, MM1).
  • Overcommit ratio — factor by which advertised capacity exceeds physical.
  • Preemption — reclaiming resources from lower-priority work for higher (§19, I14).
  • Placement scoring — ranking feasible nodes (Tetris alignment + soft constraints, §16).
  • Quorum — majority of managers required to commit (Raft).
  • Quota — per-tenant guaranteed/max share enforced at admission (I4).
  • Raft — the consensus protocol backing the WAL (ADR-09).
  • Reconciliation — converging agent reality to manager intent (§15).
  • Reserved capacity — capacity held out of scheduling (static reservations/headroom).
  • RPO / RTO — recovery point / time objectives (0 / ≤ 300 s, §4).
  • Snapshot — a consistent state image at one committed log index (I12).
  • Split-brain — two managers both believing they lead; prevented by I2 (MM8).
  • State machine — the deterministic RAM projection of the WAL (P1, MM3).
  • Two-level scheduling — resources offered to frameworks that decide (MM5, ADR-23).
  • WAL (write-ahead log) — the durable, ordered record of all mutations (P3, I3).
  • Workload — a submitted unit of work with a resource request and lifecycle (§8.2).
  • Accrual failure detector — a detector emitting a graded suspicion level (φ) rather than a boolean (§13).
  • Affinity — a constraint preferring or requiring co-placement (§8.4).
  • Backfill — placing smaller work into holes a blocked large workload leaves (§16).
  • Bin-packing — fitting multi-dimensional resource shapes onto nodes to reduce fragmentation (Tetris, §16).
  • Copy-on-write view — an immutable per-epoch inventory snapshot read lock-free by scheduler shards (§15, P5).
  • Credit flow-control — receiver-granted credits bounding in-flight data per stream (ADR-21).
  • Delay scheduling — briefly waiting for a preferred (local) node before placing elsewhere (§16).
  • Drain — stopping new placement on a node and migrating its work on exit (§15, §24).
  • Feature-epoch gating — proposing a new WAL entry type only once every quorum member supports it (§25).
  • Feasibility filter — the hard-constraint stage that shrinks candidate nodes (§16).
  • Group commit — batching WAL appends into one fsync to amortise latency (§14, M4).
  • Hierarchical queue — a tree of queues with per-node guaranteed/max shares (§19).
  • Idempotency key — the (workload, attempt, epoch) tuple making launches retry-safe (I13).
  • Joint consensus — Raft's two-phase membership change avoiding split quorums (§14).
  • Pre-vote — a Raft round preventing disruptive term inflation on rejoin (§21).
  • Revocable resource — capacity lent out that can be reclaimed (over-subscription, §35).
  • SPIFFE SVID — a short-lived cryptographic workload identity used for mTLS (ADR-18).
  • Suspicion level — the accrual detector's continuous liveness estimate (§13).
  • Taint / toleration — a node repellent and the workload marker that overrides it (§8.4).
