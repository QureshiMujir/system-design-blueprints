Decisions (§9) · 31 ADRs

1

Language

Chosen

Rust 2021

Rejected

Go, Java, C++, Erlang

When the rejected choice is right

Go when shipping speed + a large gossip/server team + an existing Go fleet (Consul/Eureka lineage) outweigh sub-3 s detection jitter; Erlang for a control-plane-only registry where its supervisor/gossip model and hot-code-reload dominate raw data-plane QPS

Why: networking+distributed; no GC jitter for SWIM timing; reuse #72/#197/#99/#71/#65/#59; Go is the lineage but jitters detection (§1.9)

2

Workspace

Chosen

Cargo, 12 crates

Rejected

monolith

When the rejected choice is right

a monolith for a single-author < 5 kLOC prototype where crate-boundary ceremony slows iteration more than it clarifies layering

Why: registry↛gossip↛federation layering

3

Consistency model

Chosen

AP (health/membership) + optional per-region CP catalog

Rejected

global CP; global AP-only

When the rejected choice is right

global CP when the registry doubles as the coordination store (locks/leader-election) and a registration outage is acceptable but split-brain is not (then it is #36/etcd, not this); global AP-only (Eureka) when even the catalog never needs linearizable writes and operational simplicity beats conflict-freedom

Why: the split (principle 7, §2.7)

4

Membership/failure detection

Chosen

SWIM (#197, Lifeguard refinements)

Rejected

all-to-all heartbeat; centralized

When the rejected choice is right

all-to-all heartbeat at tiny scale (≤ ~20 nodes) where O(N²) is trivial and gives faster, lower-variance detection; centralized failure detection when a CP coordinator already exists and is the source of truth (a K8s-style API server lease)

Why: O(1) load, bounded detection, scale (§4.3)

5

Dissemination

Chosen

gossip push-pull, fanout k (#72)

Rejected

broadcast; central pub-sub

When the rejected choice is right

broadcast/multicast on a small reliable LAN with hardware multicast where O(N) is cheap and convergence must be one hop; central pub-sub (Kafka/NATS) when a durable ordered log of changes is independently required and a broker is already operated

Why: O(log N), bounded bandwidth (I8)

6

Convergence backstop

Chosen

anti-entropy Merkle reconcile (#99/#71)

Rejected

gossip-only; full-state sync

When the rejected choice is right

gossip-only when state is tiny + churn-light and a rare permanent divergence is tolerable (or caught out-of-band); full-state sync when the state set is small enough that a Merkle tree's bookkeeping costs more than just shipping everything

Why: guaranteed convergence, diff-sized BW (I9)

7

Conflict resolution

Chosen

incarnation + logical_ts LWW register

Rejected

vector clocks per value; CRDT OR-set

When the rejected choice is right

vector clocks when third parties legitimately concurrently edit one key and the app must detect+merge concurrency (not own-state-only); CRDT OR-set when the value is a set with concurrent add/remove that must all survive (e.g. multi-writer tag sets), not a single-owner register

Why: own-state authority → LWW sufficient + O(1) (§8.12)

8

Liveness

Chosen

lease/TTL and SWIM (combined)

Rejected

lease-only; SWIM-only

When the rejected choice is right

lease-only when there is no peer-to-peer mesh (a pure client→registry model like classic Eureka) and slow crash detection (full TTL) is acceptable; SWIM-only when every instance is itself a mesh node and an external liveness assertion is redundant

Why: catch both clean exit and sudden death (principle 4)

9

Self-preservation

Chosen

Eureka-style renewal-rate threshold

Rejected

always-expire

When the rejected choice is right

always-expire when stale-but-listed instances are more dangerous than a temporary empty result (e.g. a security-sensitive endpoint where routing to a dead/compromised host must never happen), or when client-side health checks are absent

Why: avoid evicting fleet on a network blip (§8.3)

10

Federation

Chosen

sparse WAN gossip pool + selective replication

Rejected

full mesh; replicate-all

When the rejected choice is right

full mesh + replicate-all for a handful of regions with a fat private backbone and a small global catalog, where every region querying every service makes selective replication pure overhead (full global state everywhere is simplest)

Why: bounded WAN traffic, region independence (principle 6)

11

Region authority

Chosen

per-region authoritative + projections

Rejected

one global catalog

When the rejected choice is right

one global catalog when strong global read-your-writes across regions is a hard product requirement and you accept minority-region write unavailability (a globally-linearizable system like Spanner/etcd-stretch — not a discovery substrate)

Why: AP under WAN partition (I13)

12

Catalog consistency (opt)

Chosen

per-region Raft for catalog writes only

Rejected

health-in-Raft; no consistency

When the rejected choice is right

no consistency (catalog also gossiped, Eventual) when catalog edits are single-writer or conflict-free and operational simplicity (no Raft group to run) wins; health-in-Raft essentially never for discovery — only if "health" means a rare, authoritative admin override, not live heartbeats

Why: rare writes can be CP; health never (principle 7, I14)

13

DNS interface

Chosen

authoritative A/AAAA/SRV/TXT + DNS-SD

Rejected

HTTP-only

When the rejected choice is right

HTTP/gRPC-only in a greenfield fleet where every client embeds the SDK/agent and DNS's TTL coarseness + lack of rich filtering (tags/locality) is a liability rather than legacy reach

Why: legacy/zero-SDK clients (#65 wire reuse, server side)

14

API

Chosen

gRPC (HTTP/2) + REST gateway

Rejected

gRPC-only; REST-only

When the rejected choice is right

gRPC-only for an all-internal fleet with no browser/curl consumers (drop the gateway's maintenance cost); REST-only when clients are heterogeneous scripts/browsers and streaming watch is not needed (poll instead)

Why: modern + compatible; watch via long-poll/stream (I5)

15

Cache

Chosen

multi-tier TTL + negative + stale-if-error (#59)

Rejected

no cache; single tier

When the rejected choice is right

no cache when the authoritative store is in-process / sub-ms and read volume is low (caching adds coherence bugs for no latency win); single tier when there is no per-host agent (server-side-discovery-only) so the agent tier has nowhere to live

Why: latency + load-shed + AP (principle 10)

16

Anti-stampede

Chosen

single-flight / request coalescing

Rejected

none; lock-per-key

When the rejected choice is right

none when keys are uniformly cold (no hot key to stampede) or the source is cheap/elastic enough that a herd is harmless; lock-per-key when fetches must not share a result (per-caller auth context differs) so coalescing would leak

Why: bound source load on TTL expiry (I17)

17

Transport

Chosen

UDP (SWIM/gossip) + TCP (anti-entropy/API)

Rejected

TCP-only; QUIC

When the rejected choice is right

QUIC when gossip must traverse the public internet with NAT/mobility + built-in encryption (a P2P/edge deployment) and the per-packet crypto cost is acceptable; TCP-only on a network that drops/blocks UDP (some clouds/firewalls) where UDP's loss-tolerance is moot

Why: UDP small-lossy-ok for gossip; TCP for bulk

18

Gossip security

Chosen

shared key (HMAC) now; mTLS deferred

Rejected

none; full mTLS now

When the rejected choice is right

full mTLS now in a zero-trust / multi-tenant deployment where per-node identity + revocation is a launch requirement; none only inside a fully-trusted single-tenant private network where the HMAC handshake is pure overhead

Why: integrity now, identity later (§26.3)

19

Resolution structure

Chosen

RCU/arc-swap read-optimized catalog

Rejected

RwLock; Mutex

When the rejected choice is right

RwLock when writes are frequent relative to reads (the RCU copy-on-write churn would dominate) or the working set is too large to snapshot cheaply; Mutex for a tiny, write-heavy, low-QPS table where simplicity beats lock-free subtlety

Why: lock-free hot path, 50k+ QPS (principle 9)

20

Timer wheel

Chosen

hierarchical timing wheel for leases

Rejected

per-lease timer task

When the rejected choice is right

per-lease timer task when lease count is small (≤ ~10^3) and the runtime's native timer is simpler + precise enough — the wheel's slot-granularity tradeoff isn't worth it

Why: O(1) amortized at 10^6 leases (I3)

21

Locality model

Chosen

explicit labels + locality ladder

Rejected

geo-IP inference

When the rejected choice is right

geo-IP inference when clients are external end-users (not labeled fleet hosts) whose locality can't be declared — a CDN/edge-steering use where approximate geo beats no locality signal (this is #358's regime, not discovery's)

Why: deterministic, testable; geo-IP deferred (§26.5)

Error handling

Chosen

Result<_,SdError>; codes at ABI/API

Rejected

panic across FFI

When the rejected choice is right

panic/abort never across FFI; acceptable only in a pure-Rust internal tool with no FFI boundary where ?-propagation ceremony is avoidable and a crash is an acceptable failure mode

Why: FFI/API safety (I16)

unversioned for a throwaway prototype or a fleet that always deploys atomically (no mixed-version window ever) — then negotiation is dead weight

ABI

C ABI + client-SDK-friendly layer

none

When the rejected choice is right

no C ABI when every consumer is a Rust service (call the crate directly) or when discovery is exposed only over DNS/gRPC and in-process embedding is not a goal

Testing core

Chosen

Rejected

live-cluster-only

When the rejected choice is right

live-cluster-only when the system is not distributed (no eventual-consistency bug class to reproduce) or when DST's determinism discipline costs more than the bug class it catches — never true for an AP gossip system

Roads not taken (§38)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Strongly-consistent CP registry on Raft (etcd / Consul-servers model)

clients ──► [ Raft leader ] ──► replicated log ──► state machine (catalog+health)
                 │  (followers; minority refuses writes under partition)
                 ▼
            linearizable reads/writes; one global (or per-DC) consensus group
  • Regime where it wins: when the registry is also the coordination store (locks, leader election, strongly-consistent config) and stale/split answers are catastrophic while a brief write or read unavailability under partition is acceptable. Small-to-mid clusters in a single failure domain.
  • Real system: etcd (#36); Consul's server tier for its catalog/KV; ZooKeeper.
  • Why rejected here: discovery's value is availability — under partition a minority region must keep answering, or its entire fleet's routing dies (§2.7, MM2). A globally-CP registry makes discovery availability = consensus availability. We do reuse Raft, but only for the optional per-region catalog tier (P10), never for health, and never globally (I13/I14).

Pure hierarchical DNS delegation (no gossip, no mesh)

root zone ──delegates──► region zone ──delegates──► service zone
   client recursive resolver walks the delegation, caches by TTL at each level
   liveness = "remove the record"; convergence = TTL expiry
  • Regime where it wins: internet-scale naming where updates are infrequent, clients are arbitrary DNS resolvers, and second-to-minute TTL-bounded staleness is fine — the original planet-scale discovery system. Zero custom protocol; infinite client compatibility.
  • Real system: the DNS itself (Mockapetris); classic SRV-based discovery; cloud private DNS zones.
  • Why rejected here (as the core): DNS TTL convergence is coarse (you can't push a "instance just died" in < TTL), it has no rich filtering (health/tag/locality/weight beyond SRV), and no active failure detection (a dead instance lingers a full TTL with no SWIM). We keep DNS as an interface (P6) over a gossip+SWIM core that gives sub-second health propagation and filtered resolution — DNS as a facade, not the engine.

Centralized SQL/relational registry (single authoritative DB)

all nodes ──► [ primary SQL DB ] ◄── all reads/writes (catalog+health rows)
                 │  (optional read replicas, async)
              health = a "last_heartbeat" column updated per renew
  • Regime where it wins: a single datacenter, modest fleet, where a relational store the team already operates gives transactions, ad-hoc queries, and simple operations — and the DB's availability is "good enough." Strong consistency + arbitrary queries for free.
  • Real system: early/in-house service registries on PostgreSQL/MySQL; many homegrown "service table" designs.
  • Why rejected here: it does not survive the constraints — a heartbeat-per-instance write load (§36 C5: 20 k–200 k renews/s) hammers the DB; it is a single failure domain (no region independence, principle 6); cross-region means DB replication lag or a stretched cluster (CP availability problem); and it has no O(log N) dissemination or O(1) failure detection. It melts at internet scale.

Client-side gossip-only, no authoritative tier (full peer-to-peer)

every instance ◄──gossip──► every instance   (no servers; the mesh IS the registry)
   each app embeds the full membership+catalog; resolves from its own local view
   convergence = gossip + anti-entropy among ALL instances
  • Regime where it wins: a fully decentralized / edge / serverless-peer system with no operable server tier, where every participant is symmetric and willing to carry membership state — and the fleet is small-to-mid (gossip among instances, not nodes, scales with instance count). Maximum decentralization, no SPOF tier.
  • Real system: Serf used standalone; Cassandra/Dynamo's peer gossip (every node is symmetric); some P2P/edge discovery (cf. #360 overlay).
  • Why rejected here: gossiping among all instances makes membership O(instances) not O(nodes) — at 10^6 instances the SWIM/gossip load explodes (the §4.3 scale property is lost); there is no place for the catalog-CP tier, the DNS/agent caching tier, or selective WAN federation. We keep a thin server + agent topology so membership is node-scoped (10^6 instances ride on ~10²–10³ nodes' liveness, §36 C7) and the cache/DNS/federation tiers have a home.
