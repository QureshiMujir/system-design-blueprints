⬜ Phase 0 — Skeleton: data model, naming, single-region oracle §12

Objectives
  • Stand up the workspace + sd-core; define the vocabulary every crate speaks.
  • ServiceName/InstanceId/Instance/Service/Lease/Health/Version/Locality; canonical naming (I1); the LWW Version order (I11).
  • A single-region, single-store (no gossip) execution path as the oracle (principle 14).
Deliverable
  • Register/resolve against the single-store oracle; sddctl catalog-info prints services/instances; canonical names round-trip to DNS form.
Acceptance
  • ServiceName::parse accepts valid FQDNs, rejects malformed/too-long/upper-case (I1); to_dns round-trips.
  • Version::dominates is a total order (transitive, antisymmetric) — property-tested (I11).
  • Oracle register→resolve returns the registered instance; deregister removes it; renew resets expiry.
Fixtures
  • naming/name_valid.json, naming/name_invalid.json, naming/dns_roundtrip.json, registry/oracle_register_resolve.json, registry/version_order.json.
Pitfalls
  • DNS label rules (length ≤63/label, ≤253 total, allowed chars, case-insensitive) — get them exact or DNS breaks (P6).
  • InstanceId uniqueness vs (addr,port) reuse (a port can be reused by a new instance) — key by InstanceId (I2).
  • logical_ts source: must be monotonic per node (use a per-node Lamport counter, not wall-clock alone) for the LWW order to be sane.

⬜ Phase 1 — Single-region registry: catalog, leases, TTL expiry, change-stream §13

Objectives
  • The per-region source of truth: catalog store (register/deregister), the lease manager + TTL expiry (I3), and a change-stream (the substrate for gossip + blocking queries, I5).
Deliverable
  • A single region node holds a catalog; instances register, renew, expire on TTL; sddctl catalog-info shows live state + the change-stream version.
Acceptance
  • Register/deregister/renew correct; a non-renewed lease expires within [ttl, ttl+slack] (I3).
  • The timer wheel handles 10^5 leases with < 5 % CPU; expiry latency bounded.
  • The change-stream emits a monotonic version on every change (the blocking-query substrate, I5).
  • All operations match the P0 oracle (single node = oracle).
Fixtures
  • registry/lease_expiry.json, registry/renew_resets.json, registry/idempotent_register.json, registry/change_stream_versions.json, registry/timer_wheel_scale.json.
Pitfalls
  • Timer-wheel resolution vs TTL granularity → too coarse = late expiry, too fine = CPU; tune to ~100 ms slots.
  • Lease expiry uses a monotonic clock, never wall-clock (NTP steps would mis-expire) — clock-skew safety (I3).
  • The change-stream must not lose events under burst (registry storm) → bounded ring + a version-gap signal for consumers to anti-entropy-recover.
  • Self-preservation threshold mis-set → never expires (stale fleet) or never triggers (evicts on a blip) — tune carefully (§8.3).

⬜ Phase 2 — SWIM membership + health propagation §14

Objectives
  • Implement SWIM (#197): scalable failure detection (direct + indirect probes, suspicion, incarnation) over nodes; tie node liveness to instance health (the SWIM liveness signal, principle 4, I6).
Deliverable
  • N nodes form a membership group; killing a node is detected < 3×probe_interval and propagated; sddctl member-view shows Alive/Suspect/Dead.
Acceptance
  • A dead node detected < 3×probe_interval (I6); its instances → Critical.
  • A briefly-slow (GC-paused) node is not falsely killed (indirect probes + incarnation refute, principle 8).
  • SWIM per-node load is O(1) (one probe/period regardless of N) — verified at N=100.
Fixtures
  • membership/detect_dead_node.json, membership/indirect_probe.json, membership/refute_false_suspect.json, membership/swim_load_o1.json, membership/self_preservation.json.
Pitfalls
  • Probe timeout too tight → false positives (healthy instances flap out → real traffic loss, principle 8); too loose → slow detection.
  • Incarnation handling: a node must increment its own incarnation to refute; receivers must honor the higher incarnation (the subtle SWIM correctness point, I11).
  • Suspicion must converge (all nodes agree dead) before eviction — a split (some say dead, some alive) needs the confirmation round.
  • Self-preservation interacting with real mass-death (vs network) — it errs toward keeping instances; document the tradeoff (§8.3).

⬜ Phase 3 — Gossip dissemination engine §15

Objectives
  • Implement the epidemic engine (#72): disseminate registry/health/membership events via piggyback + push-pull, fanout k, dissemination limit — O(log N) propagation, bounded bandwidth (I8). This is the headline propagation path.
Deliverable
  • A registration on node A is visible on every region node within the §4 propagation bound via gossip; sddctl gossip-trace shows rounds/bytes; examples/register + examples/resolve on different nodes.
Acceptance
  • Register→discoverable cluster-wide p99 < 2 s intra-region (§4.1) — measured at N=100.
  • Gossip bandwidth bounded (I8): fanout ≤ k, events retired at the limit; bytes/node within §4.4.
  • The apply rule is monotonic: an older event never overwrites a newer one (I7); concurrent updates converge to the LWW winner (I11).
  • All nodes converge to the oracle's state (absent loss; loss is P4's job).
Fixtures
  • gossip/propagate_register.json, gossip/fanout_bounded.json, gossip/dissemination_limit.json, gossip/monotonic_apply.json, gossip/lww_conflict.json, gossip/storm_batching.json.
Pitfalls
  • Dissemination limit too low → incomplete propagation (some nodes miss it, rely on anti-entropy); too high → bandwidth blowup. Tune to ~log N (I8).
  • Push vs pull vs push-pull: pure push wastes bandwidth on already-known events; push-pull (digest first) is the default — get the digest exchange right.
  • The apply rule must be strictly monotonic (> not ≥) or equal-version events ping-pong forever.
  • HMAC over the right bytes; a forged event with a higher incarnation could poison state (defended by the shared key, ADR-18; full identity deferred §26.3).
  • Storm: without batching, mass register → broadcast storm → meltdown (§8.14) — batching is mandatory, not optional.

⬜ Phase 4 — Anti-entropy: Merkle reconciliation (the convergence guarantee) §16

Objectives
  • Implement anti-entropy (#99/#71): periodic Merkle-tree reconciliation so any gossip loss is repaired — guaranteed eventual convergence, diff-sized bandwidth (I9, principle 3).
Deliverable
  • Two nodes that diverged (inject gossip loss) reconcile to identical state within one anti-entropy interval; sddctl ae-stats shows diff keys/bytes/repairs.
Acceptance
  • After arbitrary gossip loss, all nodes converge within one anti-entropy interval (I9) — verified by injecting loss in DST (P13).
  • Reconciliation bandwidth ∝ diff size, not total state (§4.4) — matching digests transfer ~nothing.
  • Post-reconcile, cross-node state hashes are identical (convergence, I9/I11).
Fixtures
  • antientropy/merkle_digest.json, antientropy/reconcile_after_loss.json, antientropy/diff_sized_bandwidth.json, antientropy/converge_identical.json.
Pitfalls
  • Merkle tree key ordering must be deterministic (same keys → same tree on both nodes) or digests never match — canonical key sort (I9).
  • Reconciling huge diffs at once → bandwidth spike → flow control / incremental reconcile (the van Renesse lesson).
  • A version that's equal-but-different-value (shouldn't happen if the LWW order is correct) → indicates an I11 violation — assert it.
  • Anti-entropy too frequent → wasted bandwidth on matching digests; too rare → long worst-case convergence — tune (10–30 s).

⬜ Phase 5 — Resolution / query engine (filters, locality, blocking queries) §17

Objectives
  • The read path: resolve a name → healthy instances filtered by health/tag/locality/weight (I4/I12), with blocking queries (long-poll change notification, I5). The 50 k+ QPS hot path (principle 9).
Deliverable
  • resolve(name, filters) returns ordered healthy candidates; watch blocks until change; examples/resolve + examples/watch; matches the oracle.
Acceptance
  • Resolution returns only health-policy-allowed, tag-matching instances (I4), ordered by locality (I12) then weight.
  • Resolution authoritative-miss p99 < 20 ms in-region (§4); cache hit (P7) sub-ms.
  • Blocking query returns exactly on a result-set change or timeout — never spuriously, never hangs (I5).
  • Results match the oracle (same filters → same set).
Fixtures
  • resolve/health_filter.json, resolve/tag_filter.json, resolve/locality_order.json, resolve/weight_order.json, resolve/blocking_query.json, resolve/blocking_timeout.json, resolve/empty_result.json.
Pitfalls
  • Blocking query: a change between the client's last_seen_version and the server registering the wait → must re-check immediately (don't miss a change → a hang until timeout). The classic long-poll race (I5).
  • Locality ladder ties (two instances same locality rank) → stable order or random/weighted — define it (determinism for testing).
  • Filtering on stale health (the data is eventually consistent) → the result is correctly bounded-stale (I10), not wrong — flag it.
  • Empty result vs error: zero healthy instances is a valid (negatively-cacheable, I17) result, not an error.

⬜ Phase 6 — DNS + DNS-SD authoritative interface §18

Objectives
  • Expose discovery over DNS (the zero-SDK, legacy-compatible interface, #65 wire reuse, server side): authoritative A/AAAA/SRV/TXT + DNS-SD (PTR/SRV/TXT, RFC 6763), TTLs tied to the cache strategy (I16).
Deliverable
  • dig SRV _payments._tcp.prod.us-east.svc.discovery returns healthy instances; A/AAAA/TXT work; DNS-SD enumeration works; examples/dns_sd.
Acceptance
  • A/AAAA/SRV/TXT/PTR responses correct vs the resolution result (P5) — same healthy set.
  • DNS-SD PTR→SRV+TXT enumeration per RFC 6763.
  • TTLs reflect the freshness bound; NXDOMAIN/NODATA negatively-TTL'd (RFC 2308, I17).
  • Malformed DNS packets rejected without UB (I16) — fuzzed.
Fixtures
  • dns/a_record.json, dns/srv_record.json, dns/txt_record.json, dns/dns_sd_enumerate.json, dns/nxdomain_ttl.json, dns/truncation_tcp.json, dns/malformed_packet.json.
Pitfalls
  • DNS message compression (name pointers) on serialize/parse — a classic source of bugs and fuzz crashes (I16).
  • UDP 512-byte (or EDNS0-extended) limit → set TC (truncated) → client retries over TCP; handle both.
  • SRV weight/priority semantics (clients pick by priority then weighted-random) — we emit correct weights; the client load-balances (consistent with "we return candidates").
  • TTL too high → stale DNS answers cached downstream past the freshness bound (un-AP for DNS clients); tie TTL to health-TTL (I10).

⬜ Phase 7 — Multi-tier caching: TTL, negative caching, stale-if-error, anti-stampede §19

Objectives
  • The latency + load-shed layer (#59 reused): agent (tier 1) + regional (tier 2) caches; per-entry TTL (I10), negative caching (I17), stale-if-error (AP, principle 10), single-flight anti-stampede (ADR-16).
Deliverable
  • Resolution served from the agent cache at sub-ms; a source blip serves stale (not error); a TTL-expiry stampede is coalesced to one fetch; sddctl cache-stats shows hit ratio by tier.
Acceptance
  • Agent-cache-hit resolution p99 < 1 ms; regional-hit p99 < 5 ms (§4).
  • Stale-if-error: source down → stale flagged answer (I10), not a failure (principle 10).
  • Single-flight: N concurrent misses → 1 source fetch (verified); cache hit ratio ≥ 90 % under a realistic read mix.
  • Negative results cached + re-checked (I17); never cached past the bounded negative TTL.
Fixtures
  • cache/ttl_expiry.json, cache/negative_cache.json, cache/stale_if_error.json, cache/single_flight.json, cache/two_tier_hit.json, cache/invalidation.json.
Pitfalls
  • Cache key must include the filter (health policy/tags/locality) — two different queries for the same service must not collide (a subtle correctness bug → wrong results).
  • TTL longer than the freshness bound → stale answers past §4.2 (un-AP) — TTL must be ≤ health-TTL (I10).
  • Stale-if-error vs hard error: distinguish "source down" (serve stale) from "source says empty" (negatively cache) — conflating them serves stale forever or never serves stale.
  • Single-flight thundering herd: the first requester fetches, others wait — but a fetch error must fail/serve-stale all waiters, not hang them.
  • Negative-cache poisoning: a transient empty result cached too long → a real instance is invisible for the negative TTL — keep it short + freshen on register-gossip.

⬜ Phase 8 — Federation / WAN: region link, selective replication, locality-aware resolution §20

Objectives
  • The internet-scale layer (principle 6): link regions over the WAN via a sparse gossip pool (ADR-10); selective/locality-scoped replication; cross-region resolution (I12); region projection — each region stays independently authoritative (I13, the AP heart).
Deliverable
  • A service in region B is discoverable from region A (demand-driven projection); a WAN partition does not stop either region's local discovery; sddctl member-view --wan shows the WAN pool; examples/multi_region.
Acceptance
  • Cross-region register→discoverable p99 < 5 s (§4): intra-region + WAN-RTT + WAN-gossip round.
  • A WAN partition → both regions keep serving local discovery (I13); remote projections served stale-flagged (I10), never a hang.
  • WAN bandwidth bounded by the replicated set + churn (§4.4), not the full global catalog.
  • Locality ladder: local → same-locality → remote ordering correct (I12).
Fixtures
  • federation/cross_region_resolve.json, federation/demand_driven_repl.json, federation/wan_partition_serves_local.json, federation/projection_staleness.json, federation/wan_bandwidth_bounded.json, federation/locality_ladder.json.
Pitfalls
  • Replicate-all (every service to every region) → WAN-traffic blowup → demand-driven + policy scoping is mandatory (principle 6).
  • A WAN-pool node failure must not partition the region from the WAN → ≥2 WAN-pool nodes/region + SWIM over the WAN pool (bounded WAN failure detection).
  • Projection staleness must be flagged + aged (I10) — a silently-stale remote answer is the worst case (un-AP).
  • Cross-region clock skew on logical_ts → use per-region Lamport counters + incarnation; never compare wall-clocks across regions (the LWW order must survive WAN skew, I11).
  • A federation read on the local critical path → a WAN slowness stalls local resolution → federation must be strictly off the local-hit path (only on local-miss + allow_remote, I13).

⬜ Phase 9 — Partition behavior + staleness bounds + CAP enforcement (the AP heart) §21

Objectives
  • Make the AP choice operational (principle 1/2/6): define + enforce + report staleness bounds (§4.2, I10); partition behavior (serve-stale vs fail-closed, configurable, I13); self-preservation under mass heartbeat loss (§8.3). This is the section that makes the system correctly AP.
Deliverable
  • Under injected partitions (DST, P13), staleness stays within §4.2 bounds + is always flagged; serve-stale vs fail-closed behaves per policy; self-preservation prevents fleet eviction on a simulated mass heartbeat loss; sddctl partition-status.
Acceptance
  • Staleness ≤ §4.2 bound, always flagged with an age (I10/principle 2) — verified in DST under partition.
  • A region serves local discovery throughout a WAN partition (≥99.99 % local availability, §4, I13).
  • FailClosed returns an error past the max-stale threshold; ServeStale returns stale-flagged data — both per policy.
  • Self-preservation: a simulated 80 % heartbeat-loss does not evict the fleet (§8.3); recovers when heartbeats resume.
Fixtures
  • partition/staleness_bounded.json, partition/serve_stale.json, partition/fail_closed.json, partition/self_preservation.json, partition/flap_damping.json, partition/region_independence.json, partition/max_stale_failsafe.json.
Pitfalls
  • Unbounded staleness (a value that ages forever with no flag) → silent black-holing → the age + bound + fail-safe are mandatory (principle 2, I10).
  • Self-preservation triggering on real mass death (vs network) → keeps dead instances listed → it errs toward availability (clients health-check + retry); document the tradeoff (§8.3) — there is no perfect answer (it's the AP corner of CAP).
  • Flap damping too aggressive → slow to reflect a real flap-then-die; too lax → churn amplification — tune hysteresis (P12).
  • FailClosed semantics: a caller that opts in must handle the error (no stale fallback) — easy to misconfigure into an outage; default is ServeStale (AP).
  • Asymmetric partition (one-way reachability) → both sides may suspect each other → bounded by SWIM confirmation + self-preservation; never a permanent split-brain of liveness (the catalog tier, P10, handles split-brain of metadata via Raft).

⬜ Phase 10 — Catalog consistency: per-region linearizable writes (the split from health) §22

Objectives
  • Implement the optional per-region linearizable catalog tier (principle 7, I14, ADR-12): serialize catalog writes (service/instance registration metadata) through a per-region Raft group, while health/membership stays AP (gossip). The central design decision made concrete.
Deliverable
  • With CatalogMode::RegionRaft, concurrent conflicting catalog writes in a region are linearized (no two ports for one instance); health stays AP; sddctl catalog-info --consistency shows the Raft term + the mode; toggling to Eventual works.
Acceptance
  • Catalog writes are linearizable within a region under RegionRaft (I14) — verified by a linearizability check (concurrent writes → a single total order).
  • Health/membership is never routed through Raft (verified — a Raft outage does not stop health propagation or resolution, I14).
  • A catalog-Raft minority partition: catalog writes block on the minority side (CP for the catalog) but resolution + health continue (the split — discovery stays up even if registration is briefly unavailable).
  • Eventual mode matches the gossip-only behavior (no regression).
Fixtures
  • registry/catalog_linearizable.json, registry/health_not_in_raft.json, registry/catalog_raft_minority.json, registry/catalog_mode_toggle.json, registry/split_resolution_under_raft_outage.json.
Pitfalls
  • Routing health through Raft (the classic mistake) → health changes need consensus → unscalable + blocks resolution → health must never touch Raft (principle 7, the whole point of the split).
  • Linearizable write ≠ linearizable read — local reads may lag the leader by a term; document the read semantics (bounded staleness for catalog reads too) so callers don't assume read-your-writes across nodes.
  • A catalog-Raft outage blocking registration is acceptable (rare writes); blocking resolution is not → resolution reads the local snapshot, never the Raft leader (the split protects availability).
  • Raft group sizing: too large → slow writes; the catalog write rate is low (§4) so a small group (3–5) suffices; do not put 10^5 instances' health through it.

⬜ Phase 11 — C ABI + client-SDK layer §23

Objectives
  • Expose register/deregister/renew/resolve/watch over a stable C ABI (ADR-24) so client SDKs in any language can embed the agent; map SdError → frozen codes (§11.13); no panics across FFI (I16).
Deliverable
  • examples/register_from_c.c registers + resolves over the C ABI; a result array round-trips; a forced internal error surfaces as SDD_EINTERNAL, not a crash.
Acceptance
  • Every API operation reachable over the C ABI; codes match §11.13.
  • No panic crosses the FFI boundary (catch_unwind everywhere, I16) — fuzz the ABI with bad args.
  • Result-array ownership/lifetime correct (no leak, no use-after-free) — ASan-clean.
  • ABI version macro present; a mismatched header refuses (I15).
Fixtures
  • cabi/register_resolve_c.json, cabi/error_codes.json, cabi/panic_to_errno.json, cabi/result_array_lifetime.json, cabi/abi_version.json.
Pitfalls
  • Panic across FFI = UB → catch_unwind at every entry (I16); a single missed boundary is a latent crash.
  • Result-array ownership: who allocates/frees (caller vs callee)? Document + provide sdd_free_results; a mismatch leaks or double-frees.
  • Callback (watch) re-entrancy + thread-safety: the callback fires on a runtime thread; document that it must not block / re-enter the API (deadlock risk).
  • String encoding (UTF-8 service names) + NUL-termination across the boundary; validate (I16).
  • ABI stability: adding a field to a result struct is a breaking change → version it; freeze the layout (SemVer-major to change, I15).

⬜ Phase 12 — Performance hardening: 10^5–10^6 instances, gossip fan-out, endpoint sharding §24

Objectives
  • Reach internet scale (§4): 10^5–10^6 instances/region, 50 k+ resolution QPS/node, bounded gossip/anti-entropy at scale; EndpointSlice-style sharding for huge services; calibrate gossip/SWIM params per cluster.
Deliverable
  • A region simulated at 10^5–10^6 instances sustains 50 k+ resolution QPS/node with gossip < 5 % CPU + bounded bandwidth; a 10^4-instance service resolves via slices; bench reports scale curves.
Acceptance
  • 10^5 instances/region steady (design to 10^6) with §4 memory/CPU/bandwidth budgets met.
  • Resolution ≥ 50 k QPS/node (cache-backed); p99 latencies within §4 by tier.
  • Gossip CPU < 5 %/core + bandwidth ≤ a few MB/s at 10^5 instances (§4.4); SWIM detection still < 3×probe-interval at N=1000.
  • A huge service (10^4 instances) resolves/DNS-answers via bounded slices without materializing the full set.
Fixtures
  • bench/scale_100k_instances.json, bench/resolution_qps.json, bench/gossip_bandwidth_at_scale.json, bench/swim_detection_n1000.json, bench/endpoint_slice.json, bench/timer_wheel_1m_leases.json.
Pitfalls
  • A lock on the resolution path surfaces only under load (50 k QPS) → contention collapse; lock-free from the start (principle 9), verified under load not just unit tests.
  • Per-query allocation looks fine at low QPS, melts at 50 k → allocation profiling on the hot path (flamegraph).
  • Gossip params tuned for a small cluster (low fanout/limit) → incomplete propagation at scale; re-calibrate per cluster size (a calibration probe).
  • A huge service materialized per query → memory/latency blowup → EndpointSlice sharding is mandatory above a size threshold.
  • Timer-wheel cascade cost under simultaneous 10^6 expiry (a region-wide TTL alignment) → jitter TTLs / spread expiry to avoid a thundering expiry.

⬜ Phase 13 — Conformance, deterministic simulation, fault/partition injection, bench §25

Objectives
  • The correctness + performance harness (principle 14): the single-region oracle, a deterministic-simulation (DST) differential (virtual time + injected faults → reproducible convergence/staleness assertions), fault/partition injection, and the §4 benchmark suite. The net that catches eventual-consistency bugs.
Deliverable
  • make conformance runs all fixtures + DST scenarios green; make dst SEED=n reproduces any run; make bench reports §4 SLOs; fuzz targets run clean for the CI budget.
Acceptance
  • All phase fixtures pass; DST asserts convergence + staleness bounds under every injected fault class — reproducibly from a seed (principle 14).
  • The differential matches the oracle for every scenario (converged state identical).
  • Benchmarks meet §4 SLOs; a regression > a threshold fails CI.
  • Fuzz targets find no crashes in the CI budget (I16); a found crash becomes a regression fixture.
Fixtures
  • golden/* (convergence/state hashes per (scenario, seed)); partition/*, badinput/*; the full per-phase buckets; dst/scenarios/*.json (seeded fault scenarios).
Pitfalls
  • DST must be fully deterministic (one source of randomness = the seed; no wall-clock, no real I/O, no unseeded HashMap iteration order) or "reproducible" is a lie — the discipline is the hard part (eliminate every nondeterminism source).
  • The oracle must be obviously correct (simple single-store) — if the oracle is complex it can share a bug with the system → keep it trivial (principle 14).
  • A flaky DST test = a real nondeterminism bug (not "just rerun it") → hunt the unseeded source; never paper over flakiness.
  • Fault injection that's too weak (only clean partitions) misses real bugs → inject loss + reorder + skew + asymmetric partitions + storms (the messy reality).
