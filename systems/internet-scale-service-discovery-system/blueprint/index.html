359 — Internet-Scale Service Discovery System

Goal: Implement, from scratch in Rust, a planet-scale service registry + discovery system: how services find each other across regions and datacenters at internet scale — generalizing single-DC discovery (#40). Instances register (name/address/metadata/health), renew leases (TTL liveness), are discovered by clients (query name → healthy instances filtered by health/tag/locality), and deregister (graceful + lease-expiry). The hard part beyond #40: federated/hierarchical registries (per-region authoritative + cross-region federation), eventual consistency via gossip + anti-entropy (Merkle reconciliation), multi-tier TTL caching (client → regional → authoritative), health propagation across regions with bounded staleness, and the CAP choice — discovery is AP (available, partition-tolerant, eventually consistent), not CP, with explicit reasoning. Crates: sd-core / registry / membership / gossip / antientropy / federation / resolve / dns / cache / runtime / cabi / bench / conformance. Models the Consul (multi-DC WAN gossip) + Netflix Eureka + CoreDNS/Kubernetes-EndpointSlices + DNS-SD family — not a strongly-consistent KV / coordination store (#36 etcd; contrast CP), not single-DC (#40, which this generalizes), not a global traffic-steering brain (#358; discovery answers "where are healthy instances of X", not "which DC should this user hit"). Correctness is validated against a single-region reference oracle and a deterministic-simulation differential (DST: virtual time, injected partitions/loss/skew).

1. Goal

1.1 Engineering Definition

  • Build a from-scratch internet-scale service-discovery system: per-region authoritative registry (catalog of services/instances), lease-based liveness (TTL heartbeats), SWIM-style membership/health, a gossip dissemination layer, anti-entropy (Merkle-tree) reconciliation, a federation/WAN layer (region links, selective replication, locality-aware resolution), a resolution/query engine (filter by health/tag/locality), DNS + DNS-SD + HTTP/gRPC interfaces, and multi-tier TTL caching.
  • Consistency model: AP (eventually consistent) for liveness/health; per-region linearizable catalog writes optionally serialized through a region's small Raft group (the metadata path), with health kept eventually consistent (the split: strongly-consistent catalog vs eventually-consistent health, principle 7).
  • Concurrency model: shared-nothing nodes within a region (gossip-coupled); regions coupled only by the federation WAN link (loosely, selectively).

1.2 System Boundaries

  • In scope: service/instance/lease/health data model + naming hierarchy; registration/deregistration; TTL lease renewal + expiry; SWIM failure detection (direct + indirect probes, suspicion, incarnation numbers); gossip dissemination (push/pull/push-pull, fanout, anti-entropy fallback); Merkle-tree anti-entropy reconciliation; federation (region link, WAN gossip, selective/locality-scoped replication, cross-region resolution); resolution query engine (health/tag/locality/weight filtering, blocking/long-poll queries); DNS server (A/AAAA/SRV/TXT) + DNS-SD (PTR/SRV/TXT) + HTTP/gRPC API; multi-tier cache (client agent cache → regional cache → authoritative) with TTL + negative caching + stale-if-error; partition behavior (serve-stale vs fail, configurable); deterministic-simulation testing harness.
  • Out of scope (non-goals): strongly-consistent global KV / coordination / locks → #36 etcd (this is AP, contrast §2.7); single-DC discovery → #40 (this generalizes it); global user→DC traffic steering / GSLB policy brain → #358 (sibling — discovery feeds it, does not replace it); the generic gossip protocol → #72 (reused), SWIM → #197 (reused), anti-entropy/read-repair → #99 (reused), Merkle tree → #71 (reused), DNS resolver client → #65 (we are the authoritative server side; the recursive resolver is #65); distributed cache → #59 (we reuse its TTL/eviction patterns); a service mesh data plane / sidecar proxy / mTLS L7 routing → PhaseDeferred("§1.7"); config/KV management beyond service metadata → PhaseDeferred("§1.7"); per-request load balancing execution (we return weighted candidates; the client/LB picks) → out of scope.

1.3 Deployment Model

  • A Rust library + a per-node server daemon (sdd) and a co-located client agent (sdd-agent, the local caching resolver every app talks to). Topology: ≥3 server nodes per region (gossip cluster; optional Raft group for the catalog), agents on every host. A sddctl CLI for catalog inspection, membership, gossip/anti-entropy stats, and a single-region simulation mode. Regions are linked by configuring WAN peers; the WAN gossip pool is sparse (a few designated nodes per region, the Consul model).

1.4 Target Users

  • Platform/infra engineers running multi-region fleets who must understand how services discover each other across regions, why discovery is AP, and how staleness/partition behavior is bounded; learners internalizing gossip + SWIM + anti-entropy + federation + the CAP tradeoff in a real system.
  • Downstream portfolio: #358 Global Traffic Steering (consumes "healthy instances of X per region"), #326 Inference Router / generic L4-L7 LBs (consume the resolved endpoint set), #40 (the single-DC special case), service-mesh control planes.

1.9 Recommended Language & Rationale

  • Rust. (a) It is a networking + distributed-systems project — async I/O (gossip, DNS, HTTP/gRPC, WAN) + safe binary parsing (DNS wire, gossip frames) are exactly Rust's strengths; (b) ownership/Send/Sync make the per-node concurrency (gossip threads, SWIM probers, DNS server, watch/long-poll waiters, cache) auditable; (c) reuses #72 gossip, #197 SWIM, #99 anti-entropy/read-repair, #71 Merkle, #65 DNS wire, #59 cache — all Rust portfolio components; (d) no GC pauses to perturb gossip/SWIM timing (false-positive failure detection is timing-sensitive); (e) extern "C" ABI so client SDKs in any language can embed the agent; (f) consistency with the recent networking/distributed batch #355–#358.
  • Rejected: Go — this is the Consul/Eureka/etcd lineage language (and #40/#36 were Go); strong fit for gossip + servers, but GC tail-latency jitter perturbs SWIM detection windows and resolution p99, weaker zero-copy DNS parsing, and the portfolio's recent networking work is Rust. Go is the explicitly acknowledged alternative. Java (Eureka's language) — JIT warmup + GC pauses + heavyweight; C++ — manual memory across a large async surface is error-prone here; Erlang/Elixir — superb failure/gossip model and a real fit, but weaker DNS/HTTP ecosystem reuse and outside the portfolio's Rust line; Python — too slow for the data plane (DNS QPS, gossip).

2. Why Build This

2.1 Unique Knowledge Taught

  • Why discovery is AP, not CP (the CAP choice made concrete). A coordination store (#36/etcd) chooses CP: under partition it refuses writes to preserve linearizability. Discovery chooses AP: under partition each region keeps answering with possibly-stale data, because "a slightly stale list of healthy instances" is far better than "no answer" (which takes the whole fleet down). You build the system that makes the opposite tradeoff from etcd, and learn exactly when each is right (PACELC: else-latency favors local/cached answers too).
  • Gossip + anti-entropy convergence from first principles. How epidemic dissemination (push/pull/push-pull, fanout k, O(log N) rounds) spreads state, why it probabilistically converges, and why it needs anti-entropy (periodic Merkle reconciliation) as a backstop so a dropped gossip never leaves two nodes permanently divergent.
  • Lease-based liveness vs failure detection (two liveness signals, combined). TTL leases (the instance asserts "I'm alive" by renewing) and SWIM (peers detect "you stopped responding") — and why you want both: leases catch a clean process exit / a stuck-but-not-renewing instance; SWIM catches a node that died without deregistering and bounds detection time.
  • Bounded staleness across regions. How far behind can a region's view be? You derive and enforce a staleness bound (gossip round time + WAN RTT + anti-entropy interval) and expose it, so clients know how stale "healthy" might be.
  • The metadata/liveness consistency split. Why service catalog (names, ports, tags — changes rarely, wants consistency) can be on a different consistency tier than health (changes constantly, must be eventually consistent and cheap). Putting them on one tier (all-CP or all-AP) is the classic mistake; you build the split.

2.2 Why It Matters

  • Every large fleet runs one of these: Consul (multi-DC WAN gossip), Eureka (Netflix's AP registry), Kubernetes (etcd + EndpointSlices + CoreDNS) at scale, or DNS-SD. Service discovery is the substrate every microservice depends on for every request — if discovery is wrong or down, nothing can route. Understanding internet-scale discovery (across regions, partition-tolerant, eventually consistent) is understanding how planet-scale fleets stay reachable. The #40 single-DC version is the easy case; the cross-region, partition-tolerant, federated version is the real one.

2.3 Engineering Muscles

  • Epidemic/gossip protocol implementation + convergence reasoning; failure-detector design (SWIM: false-positive vs detection-time tuning); anti-entropy / Merkle reconciliation; eventual-consistency reasoning (causality, conflict resolution via incarnation numbers / LWW); federation / WAN-link design (selective replication, locality scoping); DNS authoritative-server + wire-format engineering; multi-tier cache design (TTL, negative caching, stampede); partition-behavior design (the AP choices); deterministic-simulation testing of a distributed system.

2.4 Production Concepts Exercised

  • AP vs CP (CAP/PACELC) made operational; gossip + anti-entropy; SWIM failure detection + incarnation numbers; lease/TTL liveness; bounded staleness; multi-tier caching + negative caching + stale-if-error; locality-aware resolution; graceful drain vs lease-expiry; registry storm / thundering-herd control; flap damping; clock-skew-tolerant leases; deterministic simulation testing.

  • You leave able to read Consul (serf/memberlist + WAN gossip), Eureka, CoreDNS, and DNS-SD and explain every design decision — why discovery is AP, how gossip+anti-entropy converge, why leases and SWIM coexist, how federation scopes replication, and how to reason about staleness under partition. And to debug "why can't service A find service B across regions" with a mental model of the whole path.

2.7 The CAP/PACELC choice — the defining constraint (vs #36/etcd)

  • A service registry has two readers' realities: (1) a stale-but-present answer is usually fine — an instance that died 2 s ago and is still in the list costs one failed request + a retry, recoverable; (2) no answer is catastrophic — if discovery refuses to answer under partition, every service that needs to route stops, fleet-wide.
  • Therefore discovery picks A over C under partition (the AP corner). Under a region partition, each side keeps serving its local view (possibly stale, bounded by §4); it does not block to agree, because blocking = outage.
  • PACELC: else (no partition) it also favors L over C — answer from the local cache/region at low latency rather than round-trip to a global authority. Discovery is PA/EL.
  • The cost of AP is transient incorrectness: a just-dead instance may be returned (mitigated by health checks at the client + short health TTL + SWIM), or a just-registered instance may not yet be visible (bounded by propagation time). These are bounded and recoverable; an outage is not.
  • Contrast #36/etcd (CP/PC): etcd refuses to make progress on the minority side of a partition to never serve stale/divergent data — correct for locks and leader election, wrong for "where is service X". Putting discovery on an etcd-style CP core (as naive Kubernetes-only setups effectively do via the API server) makes discovery availability equal to consensus availability — a known failure mode this design avoids by federating AP regional registries.
  • The one nuance (principle 7): the catalog (rarely-changing names/ports/tags) may be made per-region linearizable (a small Raft group) because its writes are rare and a brief unavailability of registration is tolerable; but health/liveness is always AP because it changes constantly and must never block resolution. This split is the system's central design decision and the sharpest contrast with treating discovery as "just a KV store."

2.8 What Mastery Looks Like

  • Make and defend the CAP/PACELC choice for a discovery substrate — articulate why discovery is PA/EL, quantify the cost of AP (bounded stale answer + a retry) vs CP (fleet-wide outage), and know the one place CP is right (the catalog tier). Built in Phase 9 (partition behavior / CAP enforcement) and Phase 10 (the catalog split).
  • Reason about epidemic convergence numerically — derive ≈ log_k N rounds, predict propagation time from fanout/interval, and know why anti-entropy is a necessary backstop, not an optimization. Built in Phase 3 (gossip) and Phase 4 (anti-entropy / Merkle).
  • Tune a failure detector against the false-positive/detection-time frontier — set probe/suspicion timeouts knowing a false positive costs real traffic and slow detection costs retries, and explain incarnation refutation + Lifeguard. Built in Phase 2 (SWIM membership).
  • Design diff-sized reconciliation — build a Merkle tree over (key→version) whose bandwidth scales with the diff, not the state, and know why deterministic key ordering is load-bearing. Built in Phase 4 (anti-entropy).
  • Engineer a lock-free read hot path at 50 k+ QPS — RCU/arc-swap snapshot reads, zero per-query allocation, pre-indexed candidate lookup, and prove it under load not unit tests. Built in Phase 5 (resolution) and Phase 12 (performance hardening).
  • Bound and report staleness — compute a freshness bound, flag every answer with an age, and enforce a fail-safe so stale never becomes silent black-holing. Built in Phase 7 (caching) and Phase 9 (staleness bounds).
  • Scope federation so a WAN partition never takes local discovery down — sparse WAN pools, demand-driven selective replication, region projections with origin+age, and the locality ladder. Built in Phase 8 (federation / WAN).
  • Validate an eventually-consistent system deterministically — drive the whole multi-region cluster in one process at virtual time with seeded fault injection, asserting convergence + staleness bounds against a trivially-correct single-region oracle. Built in Phase 0 (oracle) and Phase 13 (deterministic simulation).

3.2 Box Narratives

  • sdd-agent (client agent). The local caching resolver every app talks to (the Consul-agent / Eureka-client model). Caches resolutions (cache tier 1, §3.x), serves them at sub-ms latency, renews the app's own registrations/leases, and holds watch/long-poll subscriptions for change notifications. Shields the region servers from per-request load; serves stale-if-error when the region is unreachable (AP, principle 6). The single most load-bearing component for resolution latency.
  • resolve (query engine). Answers "give me healthy instances of service X" filtered by health (only Passing/Warning per policy), tag, locality (prefer same-AZ/region, the locality ladder), and weight. Supports blocking queries (long-poll: hold the request open until the result set changes or a timeout — the efficient watch primitive). Composes the registry's current state + health into an ordered candidate list. Does not load-balance (returns candidates; the caller picks).
  • registry (catalog + lease manager). The per-region source of truth: the catalog (services → instances → address/port/metadata/tags) and the lease manager (each instance has a TTL lease it must renew; expiry → mark unhealthy/remove). Emits a change-stream (the substrate for gossip events and blocking-query notifications). Optionally serializes catalog writes through a per-region Raft group (P10) while keeping health out of consensus (the split, principle 7).
  • membership (SWIM). The failure-detection layer (#197 reused): each node periodically probes a random peer (ping/ack); on no ack, indirect-probes via k other peers; persistent failure → suspect then dead, with incarnation numbers so a node can refute a false suspicion (alive with a higher incarnation). Provides cluster membership and a fast liveness signal for instances co-located with a dead node. Bounded detection time (§4).
  • gossip (dissemination). The epidemic engine (#72 reused): registry change events and membership/health updates are piggybacked on SWIM probes and on periodic push-pull rounds to random peers, with fanout k and a dissemination limit (each event gossiped O(log N) times then retired). Spreads state across the region in O(log N) rounds. Lossy by design — anti-entropy is the backstop.
  • antientropy (Merkle reconciliation). The convergence guarantee (#99/#71 reused): periodically, two nodes exchange a Merkle digest of their catalog/health state and reconcile only the differing subtrees (read-repair style). Catches anything gossip dropped, so no two nodes stay permanently divergent. The reason gossip can be lossy-but-correct.
  • dns (authoritative server). The legacy-compatible interface (#65 wire-format reused, server side): answers A/AAAA (instance IPs), SRV (host+port+weight+priority), TXT (metadata), and DNS-SD (PTR enumerate → SRV+TXT resolve, RFC 6763). Lets any DNS-speaking client discover services with zero SDK. TTLs on responses tie into the cache strategy.
  • cache (multi-tier TTL). The latency + load-shedding layer (#59 reused): tier 1 = agent cache (per host), tier 2 = regional cache (per server, shields the authoritative store + cross-region), authoritative = the registry. TTL per entry, negative caching (NXDOMAIN/empty), stale-if-error (serve expired data when the source is down — AP), and anti-stampede (single-flight / request coalescing so a popular key's TTL expiry doesn't storm the source).
  • federation (WAN). The internet-scale layer: links regions over the WAN. A sparse WAN gossip pool (a few designated nodes per region, not all-to-all, the Consul model) exchanges region-level summaries; selective/locality-scoped replication (a region replicates only the services another region actually queries, or per a policy) keeps WAN traffic bounded; cross-region resolution lets a client ask for service X in region B; region catalog projection presents remote services locally. Each region stays independently authoritative — a WAN partition does not stop local discovery (principle 6, the AP heart).
  • runtime. Node/region lifecycle: bootstrap (a node joins its region's gossip cluster via seed/join addresses, gets identity), the HTTP/gRPC API surface (register/deregister/renew/resolve/watch/catalog), config, and (P10) the optional per-region catalog Raft group.
  • bench / conformance. Propagation-time (register→discoverable), resolution-latency (cache hit/miss), and gossip-bandwidth/CPU harnesses (vs §4); the single-region oracle (one authoritative store, no gossip — the trusted result); a deterministic-simulation (DST) differential (virtual time + injected partitions/loss/skew/reorder — convergence + staleness assertions); fault/partition injection.

3.3 Boundaries

  • Trust boundary: the network — clients (register/resolve), gossip peers (intra-region), and WAN peers (other regions). Inputs are validated/length-checked; a peer can be slow, dead, byzantine-lite (send a stale/forged update — defended by incarnation numbers + monotonicity, not full BFT). The DNS/HTTP/gRPC surface is the public attack surface.
  • Consistency boundary: health/liveness is eventually consistent (gossip + anti-entropy, AP); catalog writes may be per-region linearizable (optional Raft, P10). Cross-region is always eventually consistent (federation never blocks local reads). This split is the central boundary (principle 7).
  • Concurrency boundary: per node — gossip/SWIM threads (timing-sensitive), the DNS server, the HTTP/gRPC server, watch/long-poll waiters, the cache, lease-expiry timers. No shared lock on the resolution hot path (principle 9).
  • Failure boundary: a region is the unit of independence — a region keeps serving under WAN partition; within a region, a node failure is handled by gossip+SWIM, not by stopping. The coordinator-free data plane (gossip) means no single point of failure for discovery (contrast a central registry).

3.4 Data-flow walk — one cross-region registration → discovery (the headline path)

  1. Instance i of service payments starts in region B; its sdd-agent calls register(payments, addr, port, tags, locality=B/az2, ttl=15s) → the local region-B registry writes the catalog record + a Lease{ttl=15s}, sets health Passing (I2/I3).
  2. The registry emits a change event → gossip piggybacks it on SWIM probes + push-pull rounds → within O(log N) gossip rounds every region-B node has the record (propagation bound, §4; I8).
  3. antientropy runs periodically; if any node missed the gossip event, the next Merkle reconciliation repairs it (I9) — convergence guaranteed, not just probable.
  4. The instance's agent renews the lease every ttl/3 ≈ 5s (renew); each renewal resets expiry (I3). SWIM independently probes the node hosting i; if that node dies, SWIM marks it dead → all its instances flagged unhealthy fast (I6), without waiting for lease expiry.
  5. A client in region A resolves payments with locality=A, allow_remote=true. Region A's resolve first returns region-A healthy instances; finding none (service only in B), it consults the federation projection of region B (replicated selectively, §3.x) → returns region-B instances ordered by locality (I12).
  6. The answer flows through the cache tiers (regional tier 2 → agent tier 1) with a TTL = min(record_ttl, health_ttl); subsequent resolutions hit the agent cache at sub-ms (I11). Negative results (no healthy instance) are negatively cached briefly.
  7. Instance i is later gracefully drained (deregister) → catalog record removed → gossiped → converges. Had it crashed instead, lease expiry (≤15s) + SWIM (≤§4 bound) would have removed it (I3/I6) — the two liveness signals.
  8. Throughout, a WAN partition between A and B would not stop either region serving its local view; region A would serve its last-known (stale, bounded by §4) projection of region B's payments, marked stale (I10, principle 6). Trace records propagation time, gossip rounds, anti-entropy repairs, resolution latency, staleness.

3.5 Per-node concurrency model (threads, timers, waiters)

  • SWIM prober thread(s): periodic probe/ack + indirect probe on a fixed cadence (timing-sensitive — jitter must not falsely suspect; principle 8, I6); piggybacks gossip.
  • Gossip thread(s): periodic push-pull to random peers; drains the dissemination queue; bounded fanout (I8).
  • Anti-entropy thread: lower-frequency Merkle exchange + reconcile (I9).
  • Lease-expiry timer wheel: a hierarchical timer wheel firing per-instance TTL expiry (O(1) amortized, scales to 10^6 leases; I3).
  • DNS server (UDP+TCP) + HTTP/gRPC server: async, serve from cache/registry; never block on gossip.
  • Watch/long-poll waiters: parked tasks woken by the registry change-stream (the blocking-query primitive; I5).
  • Federation/WAN thread: sparse WAN gossip + selective replication; isolated so WAN slowness never stalls local serving (principle 6).
  • Cache maintenance: TTL expiry, single-flight coalescing.
  • Synchronization: the catalog is read-mostly (resolution) + write-rare (register/health) → an RCU/arc-swap-style read-optimized structure (principle 9); no global lock on resolution. Cross-thread ordering only via the change-stream + explicit versions, never hidden locks on the hot path.

4.1 Worked propagation-time budget (gossip O(log N) convergence)

  • Gossip model: each round, every node forwards each un-retired event to k random peers; an event reaches all N nodes in ≈ log_k N rounds (epidemic spreading), with high probability after a few extra rounds.
  • Intra-region: N=100 nodes, fanout k=3, gossip interval 200 ms. log₃100 ≈ 4.2 rounds → ~5–6 rounds for high-probability full coverage → ~1.0–1.2 s < the 2 s p99 target. SWIM piggybacking shortens this (every probe also carries events).
  • Cross-region: add one WAN-gossip round (sparse pool exchanges region B's update with region A) + WAN RTT. WAN interval 1 s, WAN RTT 80 ms → region A learns B's update ~1 s + 80 ms after it converged in B → total ~2–3 s < the 5 s target.
  • Anti-entropy backstop: if an event is dropped by gossip (UDP loss), it is not lost forever — the next Merkle reconciliation (interval ≤ 30 s) repairs it. So the p99 propagation is the gossip path; the worst case (after loss) is bounded by the anti-entropy interval (I9). The §4 table states the gossip-path SLO; the anti-entropy interval is the convergence guarantee, not the common-case latency.
  • Implication: propagation time scales with log N (gossip) not N (broadcast) — this is why gossip is used and why the system reaches 10^6 instances; the constraint table targets are stated against the log N model, calibrated per cluster (P12), never assumed.

4.2 Worked staleness budget (what "healthy" can lag reality)

  • A resolution returns instances marked healthy. How stale can that be? Two failure-to-reality delays:
    • Just-died instance still listed: worst case = SWIM detection time (≤ 3 s) or lease TTL (≤ 15 s default) — whichever fires first; the client also health-checks, catching it at request time. So a dead instance is returned for ≤ ~3 s (SWIM) in the common case.
    • Just-registered instance not yet listed: worst case = propagation time (§4.1, < 2 s intra, < 5 s cross-region).
  • Under partition: add the partition duration up to the anti-entropy interval — but capped: the answer is flagged stale with an age, so the client knows (I10). Staleness is bounded (≤ anti-entropy-interval + WAN-RTT), never unbounded — the AP system promises bounded staleness, not zero staleness (principle 6).
  • Why this is acceptable (the §2.7 argument made numeric): a stale entry costs one failed request + retry to another candidate (the client's LB retries; resolution returned multiple candidates). The alternative — blocking for consistency under partition (CP) — costs a fleet-wide outage. Bounded staleness (seconds) ≪ outage (until partition heals). The numbers justify the AP choice.
  • Tuning knob: shorter health-TTL / probe-interval → fresher data but more gossip/probe load + more false positives; the operator trades freshness against load (§4.3). The bound is always enforced and reported, never silent.

4.3 Failure-detection budget (detection-time vs false-positive, SWIM)

  • SWIM detection time ≈ probe_interval + (k_indirect · probe_timeout) + suspicion_timeout. Smaller intervals/timeouts → faster detection but more false positives (a GC-paused or briefly-slow node wrongly suspected).
  • Example: probe_interval=1 s, probe_timeout=500 ms, indirect probes via k=3 peers, suspicion_timeout=2 s → detection ≈ 1 + 0.5 + … < 3 s (< the §4 "3 × probe-interval" bound) with a low false-positive rate (indirect probes filter transient slowness; incarnation numbers let a falsely-suspected node refute).
  • Cost asymmetry: a false positive marks healthy instances unhealthy → they drop out of resolution → real traffic loss until refuted (~suspicion_timeout). A slow detection leaves a dead instance listed → retries (recoverable). So the default leans slightly conservative (favor avoiding false positives), tunable per service criticality.
  • Scale-independence: SWIM's per-node load is O(1) (one random probe per interval regardless of N), and detection time is O(1) (not O(N)) — so detection does not slow as the region grows to 10^5–10^6 instances (membership is over nodes, not instances; instance health rides on node liveness + per-instance lease). This is why SWIM is chosen over all-to-all heartbeating (which is O(N²) and does not scale).

4.4 Worked gossip-bandwidth budget (why it stays bounded at scale)

  • Per-node gossip bandwidth ≈ fanout · event_rate · event_size · dissemination_limit. It depends on the event rate (registrations/health-changes per second), not on the total instance count — a steady fleet of 10^6 mostly-stable instances gossips almost nothing; churn drives cost.
  • Example: 10^5 instances, 1 % churn/s = 1 k events/s, event ≈ 200 B, fanout k=3, each event gossiped ~log N ≈ 12 times before retiring → 1000 · 200 · 3 · (12/rounds…) ≈ low single-digit MB/s/node — within the §4 budget.
  • Anti-entropy adds a periodic O(state-digest) Merkle exchange, but reconciliation transfers only the diff (I9), so steady-state anti-entropy bandwidth is near-zero (digests match); it spikes only after divergence (loss/partition heal).
  • Registry storm (mass restart: every instance re-registers at once) is the worst case — O(instances) events in a burst. Mitigations (P1/P12): dissemination batching (coalesce many events per gossip message), rate-limited re-registration (agents jitter their re-register), and the §4 50 k/s burst target. The storm is bounded and shed, not amplified (principle 5).
  • Implication: gossip cost is governed by churn, and the design keeps churn-driven traffic O(log N) per event and batched — so bandwidth stays bounded as instances grow, the property that makes internet scale feasible.

6. Design Principles

  1. Discovery is AP, not CP — choose availability under partition. Every region keeps answering with bounded-stale data rather than blocking to agree. Violation: a CP discovery core (etcd-only) → discovery availability = consensus availability → a partition takes the whole fleet's routing down (§2.7). Tradeoff: transient stale answers (bounded, recoverable) over outages.
  2. Bounded staleness, always reported — never unbounded, never silent. Stale answers carry an age/stale flag; the staleness bound (§4.2) is enforced (gossip + anti-entropy + TTL). Violation: unbounded or unlabeled staleness → clients trust dead data indefinitely → silent black-holing of traffic.
  3. Gossip for speed, anti-entropy for certainty. Gossip disseminates fast but lossily (O(log N)); periodic Merkle anti-entropy guarantees eventual convergence (catches drops). Violation: gossip-only → a dropped update leaves nodes permanently divergent; anti-entropy-only → propagation is minutes, not seconds.
  4. Two liveness signals: lease (instance asserts) + SWIM (peers detect) — combine them. Leases catch clean exits / stuck-but-present; SWIM catches sudden node death fast and bounds detection. Violation: leases-only → slow detection of crashed nodes (wait full TTL); SWIM-only → can't catch an instance that's up but unhealthy/not-renewing.
  5. Backpressure + bounding everywhere — survive the registry storm. Gossip fanout, dissemination limits, batching, rate-limited re-registration, bounded caches, single-flight. Violation: unbounded gossip on mass restart → broadcast storm → cluster meltdown; unbounded caches → OOM (§4.4).
  6. A region is independently authoritative; the WAN is best-effort. Local discovery never depends on a remote region or the WAN link being up. Federation replicates selectively and asynchronously. Violation: synchronous cross-region dependency → a WAN partition stops local discovery (the opposite of AP, principle 1).
  7. Split catalog (consistency-leaning) from health (eventual). Rarely-changing catalog metadata may be per-region linearizable (Raft); constantly-changing health is always eventual (gossip). Violation: all-CP → health changes need consensus → unscalable + blocks resolution; all-AP catalog → conflicting metadata (two ports for one instance) with no authority.
  8. Failure detection is bounded and false-positive-aware. Detection time < a fixed bound (§4.3); indirect probes + incarnation numbers minimize false positives. Violation: aggressive timeouts → healthy instances flap out of resolution (real traffic loss); lax timeouts → dead instances served for minutes.
  9. Resolution is read-mostly and lock-free on the hot path. The catalog is RCU/arc-swap-read-optimized; resolution never takes a global write lock. Violation: a lock on the resolution path → contention collapses QPS under load (the hot path is 50 k+ QPS/node).
  10. Cache aggressively with TTLs, negative caching, and stale-if-error. Multi-tier (agent → regional → authoritative) shields the source and serves AP under failure. Violation: no caching → every request hits the authoritative store → it melts; no stale-if-error → a source blip = a resolution outage (un-AP).
  11. Conflict resolution is deterministic (incarnation + LWW), not ad hoc. Concurrent updates to the same instance resolve by incarnation number then timestamp — total order, every node agrees. Violation: non-deterministic merge → nodes converge to different states (divergence that anti-entropy can't fix because they disagree on the winner).
  12. Stable wire compatibility across gossip, DNS, and the API. Gossip/WAN frames, DNS responses, and the gRPC schema are versioned; mixed-version nodes negotiate or refuse. Violation: silent protocol drift during a rolling upgrade → corruption / partition between versions.
  13. Observe every propagation, every convergence, every staleness. Emit propagation time, gossip rounds, anti-entropy repairs, resolution latency by tier, staleness age, false-positive rate. Violation: opaque convergence → "why isn't service X visible in region B?" is undebuggable.
  14. Correctness anchored to a single-region oracle + deterministic simulation. A single authoritative store (no gossip) is the reference; DST (virtual time + injected faults) verifies convergence/staleness deterministically. Violation: no oracle → eventual-consistency bugs (the worst kind) are unreproducible and undebuggable.

8. Domain Model — Naming, Records, Liveness, Gossip, Federation, Resolution

8.1 Naming hierarchy

  • A fully-qualified service name: service[.tag].namespace.region.<root> — e.g. payments.prod.us-east.svc.discovery. (DNS-compatible labels; I1). Components:
    • service — the logical service (payments).
    • namespace — tenancy/isolation boundary (prod, staging).
    • region — the authoritative region (us-east).
    • DNS-SD form: _payments._tcp.prod.us-east.svc.discovery. (RFC 6763 _service._proto prefix).
  • Resolution may omit region (→ "any/locality-preferred region", I12) or pin it (→ a specific region, cross-region allowed by policy).
  • Tags subset a service (payments with tag v2 → only v2 instances) — expressed as a query filter, not a separate name.

8.2 Core records (the catalog)

Record Fields (lightweight) Consistency tier

Instance InstanceId, service, addr, port, locality, tags, metadata, weight catalog (CP-able)

  • The split (principle 7): Service/Instance (the catalog — rare changes) may sit on a per-region linearizable tier; Lease/Health/NodeMember (constant changes) are always eventually consistent (gossip/SWIM). A resolution joins catalog + health at read time.

8.3 Liveness — leases + SWIM (the two signals)

Signal Who asserts/detects Catches Timescale
Lease (TTL renew) the instance renews clean exit, stuck-but-present (not renewing), graceful drain TTL (5–90 s, default 15 s)
SWIM probe peer nodes detect sudden node death, network-isolated node < 3×probe_interval (< 3 s)
  • Combined rule: an instance is Passing iff (lease not expired) and (its node is Alive in SWIM) and (its health check passes). Any failing → degrade (I4). SWIM is fast for node death; lease is the catch-all; the health check is application-level.
  • Eureka self-preservation (a key AP safeguard): if a node loses heartbeats from a large fraction of instances at once (renewal rate drops below a threshold), assume network, not mass death — stop expiring leases until the rate recovers (avoids evicting a healthy fleet during a network blip). A bounded, AP-preserving override of I3.

8.4 Gossip dissemination

  • Model: each registry/health/membership change becomes an event {key, value, incarnation, logical_ts}. Events are (a) piggybacked on SWIM probe/ack messages and (b) spread by periodic push-pull rounds to k random peers.
  • Push / pull / push-pull: push = send my new events; pull = ask a peer for its events; push-pull = exchange digests then deltas (the default — converges fastest, Demers 1987).
  • Dissemination limit (I8): each event is gossiped at most ~log N times (a counter per event), then retired — bounds bandwidth; anti-entropy (I9) catches anyone who missed it.
  • Apply rule (I7/I11): a received event for key is applied iff (incarnation, logical_ts) is strictly greater than the local value's → monotonic, conflict-free, deterministic winner.

8.5 Anti-entropy (Merkle reconciliation)

  • Purpose (I9): guarantee convergence despite gossip loss. Periodically, node A and node B exchange a Merkle tree over their (key → version) state; matching subtrees are skipped, differing subtrees recursed into; only the differing keys are exchanged (read-repair).
  • Tree (#71): leaves = hash(key, incarnation, logical_ts); internal = hash(children); root mismatch → walk down to the differing leaves. Bandwidth ∝ diff size, not state size (§4.4).
  • Frequency: lower than gossip (e.g. every 10–30 s); the convergence backstop, not the primary path.

8.6 Federation / WAN

  • WAN gossip pool: a sparse set (e.g. 3 designated nodes per region) join a cross-region gossip pool exchanging region-level summaries (the Consul model) — not every node talks WAN (bounds WAN traffic, principle 6/§4.4).
  • Selective replication: a region replicates a remote service's instances only if (a) a local client has queried it (demand-driven) or (b) a replication policy includes it. Avoids replicating the whole world to every region.
  • Region projection: remote services appear locally as a read-only projection tagged with their origin region + a freshness/staleness age (I10).
  • Cross-region resolution (I12): resolve locally first; if empty or policy says allow_remote, consult region projections, ordered by the locality ladder.
  • Independence (I13): the WAN path is off the local read critical path — a WAN partition degrades remote answers (served stale, flagged) but never blocks local discovery.

8.7 Resolution / query engine

  • Input: ResolveQuery{ name, tags, health_policy, locality, allow_remote, max_results, weight_mode }.
  • Steps: (1) canonicalize name (I1); (2) gather candidate instances (local catalog ⨝ health); (3) filter by health policy (I4) + tags; (4) order by locality ladder (I12) then weight; (5) if empty and allow_remote, repeat over region projections (I13); (6) cap to max_results; (7) cache the result with TTL (I10).
  • Blocking query (I5): the client sends a last_seen_version; the server holds the request until the result set's version exceeds it or the timeout fires → efficient change notification without polling.
  • The engine returns candidates; it does not pick one (no load balancing) — the client/LB chooses (with retries across candidates, the AP recovery for a stale entry).

8.8 Wire protocols (lightweight)

  • Gossip frame: [magic | version | type | from-node | seq | len | checksum | payload]; types: Probe, Ack, IndirectProbe, Push, Pull, PushPull, AeDigest, AeDelta, WanSummary, Bye. UDP for SWIM/gossip (small, lossy-ok), TCP for anti-entropy/large deltas.
  • DNS: standard RFC 1035 message; we author A/AAAA/SRV/TXT/PTR answers; TTL per record from the cache strategy.
  • API: gRPC (HTTP/2) Register/Deregister/Renew/Resolve/Watch/Catalog; proto versioned (I15).
  • Apply / merge: every state-bearing frame carries (incarnation, logical_ts) for the apply rule (I7/I11).

8.9 State machines

  • Instance: Registered(Passing) → {Warning | Critical} → {Passing (recover) | Deregistered (graceful) | Expired (lease) | Evicted (node dead)}.
  • Node (SWIM): Alive → Suspect → Dead; Suspect → Alive on refutation (higher incarnation, I11); Dead gossiped, then forgotten after a tombstone window.
  • Lease: Active → (renew → Active) | (no renew within ttl → Expired).
  • Region link (federation): Connected → {Degraded(stale) → Connected | Partitioned(serve-local-only) → Connected}.

8.12 Convergence / consistency model (eventual + conflict resolution)

  • Consistency class: the health/membership state is an eventually consistent, conflict-free replicated map keyed by InstanceId/node-id, values ordered by (incarnation, logical_ts) — a last-writer-wins register per key with a deterministic total order (I11). This is a CRDT-flavored design (an LWW-register map): merges are commutative, associative, idempotent → any gossip/anti-entropy order converges to the same state.
  • Why not vector clocks (#95) for the value? Vector clocks detect concurrent updates so the application can merge them; here the desired semantic for "instance health" is simply the most recent assertion wins (a node's own incarnation is authoritative for its own state), so an incarnation+timestamp LWW register is sufficient and far cheaper (O(1) vs O(N) metadata). Vector clocks inform the reasoning and would be needed if we allowed third-party edits to an instance's state (we do not — each node owns its own + its instances').
  • Incarnation numbers (the SWIM mechanism): a node's incarnation increments whenever it must refute a suspicion ("I'm alive, incarnation N+1") — this lets a falsely-suspected node override the Suspect gossip deterministically (I11/principle 8). Incarnations are the per-key version that makes LWW correct across the refute/suspect race.
  • Convergence guarantee (I9): gossip gives probabilistic fast convergence; anti-entropy gives deterministic eventual convergence (Merkle reconcile transfers any missing/older keys). Together: bounded-time convergence (§4.1) with a hard backstop. No two correct nodes stay divergent past one anti-entropy interval.
  • What is NOT guaranteed: linearizability of health (it's AP — a read may return data another node has already superseded, within the staleness bound, I10); monotonic-read consistency across different agents (each agent's cache may be at a different version — bounded, flagged). The catalog tier (P10) optionally adds per-region linearizability for catalog writes only.

8.13 Worked example — Consul-style multi-DC, demand-driven federation

  • Setup: regions us-east, us-west, eu. Service payments runs only in us-east (10 instances). A client in us-west resolves payments with allow_remote=true.
  • First resolution: us-west has no local payments, no projection yet → federation queries the us-east WAN pool → fetches the 10 instances → caches a projection locally (tagged origin us-east, age 0) → returns them ordered (all remote, same locality tier).
  • The projection now subscribes (demand-driven selective replication): us-east's WAN pool gossips payments health/membership changes to us-west's WAN pool → subsequent us-west resolutions are local-projection cache hits (sub-ms), kept fresh within the WAN propagation bound (§4.1).
  • An instance in us-east goes Critical → gossiped within us-east (< 2 s) → WAN-gossiped to us-west projection (< +WAN-RTT+round) → us-west resolutions stop returning it (< ~3–5 s total, I10 staleness bound).
  • WAN partition us-east ↔ us-west: us-west keeps serving its last-known payments projection, flagged stale with a growing age (I10/I13); when age exceeds a policy threshold the projection may be marked all-Critical (fail-safe) or kept (fail-stale) per config (P9). us-east is entirely unaffected (serves locally). Neither region's discovery goes down for a WAN issue (principle 1/6).
  • Contrast with a hypothetical CP design: a global linearizable catalog would have refused the us-west registration-or-read on the minority side of the partition → us-west's payments routing down until heal. The AP design degrades to stale, not down (§2.7).

8.14 Worked example — registry storm (mass restart) and how it's shed

  • Trigger: a 10^4-instance region's hosts all restart (a rolling deploy gone wide, or a power event) → every instance's agent re-registers within seconds → O(10^4) catalog writes + health events in a burst.
  • Naive failure: each event gossiped independently at fanout k → O(10^4 · k · log N) messages in seconds → gossip broadcast storm → CPU/NIC saturation → SWIM probes delayed → false failure detections → more churn → meltdown (the feedback loop).
  • Mitigations (principle 5, §4.4):
    • Dissemination batching: the gossip layer coalesces many pending events into one push-pull message (amortize per-message overhead) — O(10^4) events ride in O(10^4 / batch) messages.
    • Rate-limited / jittered re-registration: agents spread re-registration over a window (randomized backoff) so the burst is smeared, not instantaneous.
    • SWIM isolation: the failure detector runs on its own cadence (and self-preservation, §8.3, kicks in if the renewal rate craters — assume network, don't evict) → the storm does not cause cascading false deaths.
    • Anti-entropy convergence: even if many gossip events are dropped under load, the post-storm Merkle reconcile (I9) converges everyone — correctness is preserved even when the fast path is overwhelmed.
  • Outcome: the storm is bounded and shed (batched, rate-limited, self-preserving), convergence is guaranteed (anti-entropy), and detection stays stable (SWIM isolation + self-preservation). The §4 50 k/s burst target is the design point for this scenario.

13. Phase 1 — Single-region registry: catalog, leases, TTL expiry, change-stream

13.1 Objectives

  • The per-region source of truth: catalog store (register/deregister), the lease manager + TTL expiry (I3), and a change-stream (the substrate for gossip + blocking queries, I5).

13.2 Detailed Implementation Steps

  • registry::catalog — (ServiceName → {InstanceId → Versioned<Instance>}); register/deregister; read-optimized via arc-swap (principle 9, ADR-19).
  • registry::lease_mgr — per-instance Lease; renew resets expiry; expiry → health Critical then removal (I3).
  • registry::timer_wheel — hierarchical timing wheel for O(1)-amortized lease expiry at 10^6 leases (ADR-20).
  • registry::change_stream — a versioned broadcast of catalog/health changes (monotonic version); consumers: gossip (P3) + blocking queries (P5).
  • registry::store — the storage abstraction (in-memory now; pluggable persistence later).
  • Idempotent register (re-register bumps incarnation, LWW, I2/I11); self-preservation hook (renewal-rate threshold, §8.3) wired but inert until P2 membership exists.

13.3 Deliverable

  • A single region node holds a catalog; instances register, renew, expire on TTL; sddctl catalog-info shows live state + the change-stream version.

13.4 Acceptance Criteria

  • Register/deregister/renew correct; a non-renewed lease expires within [ttl, ttl+slack] (I3).
  • The timer wheel handles 10^5 leases with < 5 % CPU; expiry latency bounded.
  • The change-stream emits a monotonic version on every change (the blocking-query substrate, I5).
  • All operations match the P0 oracle (single node = oracle).

13.5 Conformance Fixtures

  • registry/lease_expiry.json, registry/renew_resets.json, registry/idempotent_register.json, registry/change_stream_versions.json, registry/timer_wheel_scale.json.

13.6 Pitfalls

  • Timer-wheel resolution vs TTL granularity → too coarse = late expiry, too fine = CPU; tune to ~100 ms slots.
  • Lease expiry uses a monotonic clock, never wall-clock (NTP steps would mis-expire) — clock-skew safety (I3).
  • The change-stream must not lose events under burst (registry storm) → bounded ring + a version-gap signal for consumers to anti-entropy-recover.
  • Self-preservation threshold mis-set → never expires (stale fleet) or never triggers (evicts on a blip) — tune carefully (§8.3).

13.7 Performance Concerns

  • Resolution is read-mostly: arc-swap snapshot reads, no lock (principle 9). Writes (register/health) take a short write path; batch under storm.
  • Timer wheel: O(1) insert/expire; avoid per-lease tasks (10^6 tasks would melt the scheduler).

13.8 Edge Cases

  • TTL = min/max bounds; renew exactly at expiry (race — monotonic-clock decides); deregister an already-expired instance (no-op); 10^6 simultaneous expiries (timer-wheel cascade).

13.9 Failure Analysis

  • Late/early expiry → wrong liveness → bound it with the monotonic clock + slack; the oracle + lease fixtures guard correctness.
  • Change-stream loss → consumers diverge → version-gap detection triggers anti-entropy (I9) as the backstop.

13.10 Operational Notes

  • PropagationTrace (origin), lease metrics (active, expiring, expired/s); document the TTL/renew-at-ttl/3 + self-preservation tuning.

14. Phase 2 — SWIM membership + health propagation

14.1 Objectives

  • Implement SWIM (#197): scalable failure detection (direct + indirect probes, suspicion, incarnation) over nodes; tie node liveness to instance health (the SWIM liveness signal, principle 4, I6).

14.2 Detailed Implementation Steps

  • membership::swim — the protocol cycle: each period probe a random member (ping/ack); piggyback gossip (P3).
  • membership::indirect — on a missed ack, ask k random members to indirect-probe (filters transient slowness).
  • membership::suspicion — Alive → Suspect → Dead with a suspicion timeout; Lifeguard refinements (adaptive timeout, local-health-aware) to cut false positives.
  • membership::member_table — the member map with incarnation; a node refutes a false Suspect by gossiping Alive with a higher incarnation (I11/principle 8).
  • Integration: a node going Dead → all its instances flagged Critical immediately (the fast liveness path, I6); the self-preservation check (§8.3) now active (renewal-rate aware).

14.3 Deliverable

  • N nodes form a membership group; killing a node is detected < 3×probe_interval and propagated; sddctl member-view shows Alive/Suspect/Dead.

14.4 Acceptance Criteria

  • A dead node detected < 3×probe_interval (I6); its instances → Critical.
  • A briefly-slow (GC-paused) node is not falsely killed (indirect probes + incarnation refute, principle 8).
  • SWIM per-node load is O(1) (one probe/period regardless of N) — verified at N=100.

14.5 Conformance Fixtures

  • membership/detect_dead_node.json, membership/indirect_probe.json, membership/refute_false_suspect.json, membership/swim_load_o1.json, membership/self_preservation.json.

14.6 Pitfalls

  • Probe timeout too tight → false positives (healthy instances flap out → real traffic loss, principle 8); too loose → slow detection.
  • Incarnation handling: a node must increment its own incarnation to refute; receivers must honor the higher incarnation (the subtle SWIM correctness point, I11).
  • Suspicion must converge (all nodes agree dead) before eviction — a split (some say dead, some alive) needs the confirmation round.
  • Self-preservation interacting with real mass-death (vs network) — it errs toward keeping instances; document the tradeoff (§8.3).

14.7 Performance Concerns

  • O(1) probe load + bounded gossip piggyback; detection time O(1), not O(N) — the scale property (§4.3).
  • Timing isolation: the SWIM thread must run on its own cadence, not blocked by the data plane (ADR-27) — jitter causes false positives.

14.8 Edge Cases

  • N=1 (no peers to probe — trivially alive); simultaneous multi-node failure; a partition (each side suspects the other — bounded by the confirmation + self-preservation); clock skew on suspicion timeouts (monotonic clock).

14.9 Failure Analysis

  • False positive = healthy instances dropped from resolution = real impact → indirect probes + incarnation + Lifeguard + conservative defaults; docs/runbooks/false-failure-detection.md.
  • A SWIM bug that fails to detect death → dead instances served → lease expiry (I3) is the second-signal backstop (principle 4).

14.10 Operational Notes

  • MembershipTrace (members, suspect, dead, detect_ms, false_positive, incarnation); document probe/suspicion tuning + the false-positive runbook.

15. Phase 3 — Gossip dissemination engine

15.1 Objectives

  • Implement the epidemic engine (#72): disseminate registry/health/membership events via piggyback + push-pull, fanout k, dissemination limit — O(log N) propagation, bounded bandwidth (I8). This is the headline propagation path.

15.2 Detailed Implementation Steps

  • gossip::event — GossipEvent{key,value,version,hops} from the change-stream (P1) + membership (P2).
  • gossip::disseminate — a queue of pending events; each gossiped to k random peers; hops++; retire at dissemination_limit ≈ log N (I8).
  • gossip::push_pull — periodic exchange: digest → deltas (the fastest-converging mode, §8.4).
  • gossip::piggyback — attach pending events to SWIM probe/ack (free propagation).
  • gossip::frame — the wire frame (§8.8), versioned + checksummed + HMAC (ADR-18, I15/I16).
  • gossip::apply — the monotonic apply rule: accept iff version.dominates local (I7); record Applied/StaleDropped/Conflict (I11).
  • Dissemination batching (coalesce many events per message) for the registry-storm path (§8.14, principle 5).

15.3 Deliverable

  • A registration on node A is visible on every region node within the §4 propagation bound via gossip; sddctl gossip-trace shows rounds/bytes; examples/register + examples/resolve on different nodes.

15.4 Acceptance Criteria

  • Register→discoverable cluster-wide p99 < 2 s intra-region (§4.1) — measured at N=100.
  • Gossip bandwidth bounded (I8): fanout ≤ k, events retired at the limit; bytes/node within §4.4.
  • The apply rule is monotonic: an older event never overwrites a newer one (I7); concurrent updates converge to the LWW winner (I11).
  • All nodes converge to the oracle's state (absent loss; loss is P4's job).

15.5 Conformance Fixtures

  • gossip/propagate_register.json, gossip/fanout_bounded.json, gossip/dissemination_limit.json, gossip/monotonic_apply.json, gossip/lww_conflict.json, gossip/storm_batching.json.

15.6 Pitfalls

  • Dissemination limit too low → incomplete propagation (some nodes miss it, rely on anti-entropy); too high → bandwidth blowup. Tune to ~log N (I8).
  • Push vs pull vs push-pull: pure push wastes bandwidth on already-known events; push-pull (digest first) is the default — get the digest exchange right.
  • The apply rule must be strictly monotonic (> not ≥) or equal-version events ping-pong forever.
  • HMAC over the right bytes; a forged event with a higher incarnation could poison state (defended by the shared key, ADR-18; full identity deferred §26.3).
  • Storm: without batching, mass register → broadcast storm → meltdown (§8.14) — batching is mandatory, not optional.

15.7 Performance Concerns

  • Gossip CPU < 5 % steady (§4); cost is churn-driven, not instance-count-driven (§4.4).
  • UDP for small gossip (lossy-ok, fast); avoid large messages over UDP (fragmentation) — anti-entropy bulk over TCP (P4).
  • Random peer selection must be uniform (biased selection → slow convergence in part of the cluster).

15.8 Edge Cases

  • N=1 (no peers); a single event vs a storm; an event for an unknown key (a new instance — accept); duplicate events (idempotent apply, I7); a node far behind (anti-entropy bulk-syncs it, P4).

15.9 Failure Analysis

  • A gossip bug that drops/duplicates → divergence → the apply rule (idempotent, monotonic) tolerates duplicates; anti-entropy (P4) catches drops (I9). Cross-node state-hash compare detects divergence.
  • A poison event (forged) → HMAC + monotonicity bound it; docs/failure-analysis/divergence.md.

15.10 Operational Notes

  • GossipTrace (events in/out, bytes, fanout, stale_dropped); PropagationTrace.gossip_rounds; document the gossip params + the storm runbook (docs/runbooks/registry-storm.md).

16. Phase 4 — Anti-entropy: Merkle reconciliation (the convergence guarantee)

16.1 Objectives

  • Implement anti-entropy (#99/#71): periodic Merkle-tree reconciliation so any gossip loss is repaired — guaranteed eventual convergence, diff-sized bandwidth (I9, principle 3).

16.2 Detailed Implementation Steps

  • antientropy::merkle — a Merkle tree over (key → version); leaves = hash(key, incarnation, logical_ts); internal = hash(children) (#71).
  • antientropy::digest — produce/compare digests; root match → in sync, root mismatch → recurse to differing leaves.
  • antientropy::reconcile — exchange differing keys' Versioned values; apply via the monotonic rule (I7); both sides converge (I9).
  • antientropy::flow_control — bound reconciliation bandwidth (van Renesse 2008); reconcile incrementally, not the whole tree at once.
  • Frequency: lower than gossip (10–30 s); over TCP (bulk). Triggered also by a change-stream version-gap signal (P1) for fast recovery.

16.3 Deliverable

  • Two nodes that diverged (inject gossip loss) reconcile to identical state within one anti-entropy interval; sddctl ae-stats shows diff keys/bytes/repairs.

16.4 Acceptance Criteria

  • After arbitrary gossip loss, all nodes converge within one anti-entropy interval (I9) — verified by injecting loss in DST (P13).
  • Reconciliation bandwidth ∝ diff size, not total state (§4.4) — matching digests transfer ~nothing.
  • Post-reconcile, cross-node state hashes are identical (convergence, I9/I11).

16.5 Conformance Fixtures

  • antientropy/merkle_digest.json, antientropy/reconcile_after_loss.json, antientropy/diff_sized_bandwidth.json, antientropy/converge_identical.json.

16.6 Pitfalls

  • Merkle tree key ordering must be deterministic (same keys → same tree on both nodes) or digests never match — canonical key sort (I9).
  • Reconciling huge diffs at once → bandwidth spike → flow control / incremental reconcile (the van Renesse lesson).
  • A version that's equal-but-different-value (shouldn't happen if the LWW order is correct) → indicates an I11 violation — assert it.
  • Anti-entropy too frequent → wasted bandwidth on matching digests; too rare → long worst-case convergence — tune (10–30 s).

16.7 Performance Concerns

  • Digest computation: incremental Merkle update on each change (don't rebuild the whole tree per round) — O(log N) update.
  • Steady-state anti-entropy is near-free (digests match); it spikes only post-divergence (loss/partition-heal) — by design (§4.4).

16.8 Edge Cases

  • Identical states (digest match, zero transfer); fully divergent (full-state transfer — bounded by flow control); a node joining (bulk-sync via anti-entropy, P12 bootstrap); concurrent reconcile with two peers.

16.9 Failure Analysis

  • A reconcile bug → permanent divergence (the worst eventual-consistency failure) → cross-node hash compare + DST loss-injection convergence tests are the net (I9); docs/failure-analysis/divergence.md.
  • Reconcile storm post-partition-heal → flow control bounds it; docs/runbooks/wan-partition.md.

16.10 Operational Notes

  • GossipTrace.ae_diff_keys/ae_bytes, ReconcileStats; document the Merkle scheme + interval tuning in docs/performance/gossip-convergence.md.

17. Phase 5 — Resolution / query engine (filters, locality, blocking queries)

17.1 Objectives

  • The read path: resolve a name → healthy instances filtered by health/tag/locality/weight (I4/I12), with blocking queries (long-poll change notification, I5). The 50 k+ QPS hot path (principle 9).

17.2 Detailed Implementation Steps

  • resolve::query — ResolveQuery parse/validate (I1/I16); canonicalize name.
  • resolve::filter — join catalog ⨝ health; filter by HealthPolicy (I4) + tags.
  • resolve::locality_ladder — order candidates by the locality ladder (same-zone → same-region → other-region) (I12).
  • resolve::order — within a locality tier, order/weight by weight_mode (the candidate ranking; no LB pick).
  • resolve::blocking_query — hold a request on the change-stream version (P1) until the result set's version exceeds last_seen_version or the timeout fires (I5); never spurious, never past-timeout.
  • Read from the arc-swap snapshot (lock-free, principle 9, ADR-19); stamp stale+stale_age from data freshness (I10).

17.3 Deliverable

  • resolve(name, filters) returns ordered healthy candidates; watch blocks until change; examples/resolve + examples/watch; matches the oracle.

17.4 Acceptance Criteria

  • Resolution returns only health-policy-allowed, tag-matching instances (I4), ordered by locality (I12) then weight.
  • Resolution authoritative-miss p99 < 20 ms in-region (§4); cache hit (P7) sub-ms.
  • Blocking query returns exactly on a result-set change or timeout — never spuriously, never hangs (I5).
  • Results match the oracle (same filters → same set).

17.5 Conformance Fixtures

  • resolve/health_filter.json, resolve/tag_filter.json, resolve/locality_order.json, resolve/weight_order.json, resolve/blocking_query.json, resolve/blocking_timeout.json, resolve/empty_result.json.

17.6 Pitfalls

  • Blocking query: a change between the client's last_seen_version and the server registering the wait → must re-check immediately (don't miss a change → a hang until timeout). The classic long-poll race (I5).
  • Locality ladder ties (two instances same locality rank) → stable order or random/weighted — define it (determinism for testing).
  • Filtering on stale health (the data is eventually consistent) → the result is correctly bounded-stale (I10), not wrong — flag it.
  • Empty result vs error: zero healthy instances is a valid (negatively-cacheable, I17) result, not an error.

17.7 Performance Concerns

  • The hot path: lock-free snapshot read (principle 9); pre-index by (ServiceName) for O(1) candidate lookup; avoid per-query allocation (reuse buffers).
  • Blocking queries: a parked-task model (not a polling loop) — O(waiters) memory, woken by the change-stream, not CPU-spinning.
  • Locality/weight ordering on a large candidate set (a 10^4-instance service) → cap + sample, or pre-shard (EndpointSlice-style, P12).

17.8 Edge Cases

  • A service with 10^4 instances (cap max_results, P12 sharding); zero healthy (negative, I17); all instances remote (locality ladder → remote tier, P8); a tag matching nothing (empty); last_seen_version in the future (clock/version skew → return current).

17.9 Failure Analysis

  • A filter/order bug → wrong candidates returned → bad routing → vs oracle + per-filter fixtures (I4/I12).
  • A blocking-query hang (missed wakeup) → clients stall → the re-check-on-register rule + the timeout floor bound it (I5); stress-test under churn.

17.10 Operational Notes

  • ResolveTrace (tier, latency, candidates, stale, stale_age, locality_rank); document the locality ladder + blocking-query semantics.

18.1 Objectives

18.2 Detailed Implementation Steps

  • dns::message — RFC 1035 message parse/serialize (header, question, RR sections); strict bounds (I16).
  • dns::rr / dns::srv / dns::txt — build A/AAAA (instance IPs), SRV (priority/weight/port/target, RFC 2782), TXT (metadata).

18.3 Deliverable

  • dig SRV _payments._tcp.prod.us-east.svc.discovery returns healthy instances; A/AAAA/TXT work; DNS-SD enumeration works; examples/dns_sd.

18.4 Acceptance Criteria

  • A/AAAA/SRV/TXT/PTR responses correct vs the resolution result (P5) — same healthy set.
  • DNS-SD PTR→SRV+TXT enumeration per RFC 6763.
  • TTLs reflect the freshness bound; NXDOMAIN/NODATA negatively-TTL'd (RFC 2308, I17).
  • Malformed DNS packets rejected without UB (I16) — fuzzed.

18.5 Conformance Fixtures

  • dns/a_record.json, dns/srv_record.json, dns/txt_record.json, dns/dns_sd_enumerate.json, dns/nxdomain_ttl.json, dns/truncation_tcp.json, dns/malformed_packet.json.

18.6 Pitfalls

  • DNS message compression (name pointers) on serialize/parse — a classic source of bugs and fuzz crashes (I16).
  • UDP 512-byte (or EDNS0-extended) limit → set TC (truncated) → client retries over TCP; handle both.
  • SRV weight/priority semantics (clients pick by priority then weighted-random) — we emit correct weights; the client load-balances (consistent with "we return candidates").
  • TTL too high → stale DNS answers cached downstream past the freshness bound (un-AP for DNS clients); tie TTL to health-TTL (I10).

18.7 Performance Concerns

  • DNS QPS: served from cache (P7); parse/serialize is the cost — zero-copy where possible; pre-build common RRsets.
  • UDP fast path; TCP only on truncation; EDNS0 to raise the UDP limit and cut TCP fallback.

18.8 Edge Cases

  • A service with > UDP-limit instances (truncate → TCP, or cap RRset); wildcard/missing names (NXDOMAIN); a query for a remote-region name (federation, P8); EDNS0 vs legacy clients; case-insensitive name match (I1).

18.9 Failure Analysis

  • A DNS parse bug = a remotely-triggerable crash (public attack surface) → strict bounds + fuzz (dns_parse, I16); docs/threat-model.md.
  • A wrong RR = mis-routing of legacy clients → vs resolution fixtures + dig integration tests.

18.10 Operational Notes

19. Phase 7 — Multi-tier caching: TTL, negative caching, stale-if-error, anti-stampede

19.1 Objectives

  • The latency + load-shed layer (#59 reused): agent (tier 1) + regional (tier 2) caches; per-entry TTL (I10), negative caching (I17), stale-if-error (AP, principle 10), single-flight anti-stampede (ADR-16).

19.2 Detailed Implementation Steps

  • cache::tier — two-tier topology: agent cache (per host, in sdd-agent) → regional cache (per server) → authoritative (registry/resolve). Cache keyed by (ServiceName, filter-hash).
  • cache::ttl — per-entry TTL = min(record_ttl, health_ttl); expiry → refetch; serve-while-revalidate (return stale, refresh in background) optionally.
  • cache::negative — negative entries (no healthy instance / NXDOMAIN) with a short bounded TTL (RFC 2308 for DNS); re-checked on TTL expiry (I17).
  • cache::stale_if_error — when the source (registry/remote region) is unreachable, serve the expired entry flagged stale+age (I10/principle 6) instead of failing — the AP behavior.
  • cache::single_flight — request coalescing: concurrent misses for the same key share one in-flight fetch (anti-stampede, ADR-16) — a popular key's TTL expiry does not storm the source.
  • Cache invalidation via the change-stream / gossip (push-based freshening for hot keys) + TTL (pull-based) — hybrid.

19.3 Deliverable

  • Resolution served from the agent cache at sub-ms; a source blip serves stale (not error); a TTL-expiry stampede is coalesced to one fetch; sddctl cache-stats shows hit ratio by tier.

19.4 Acceptance Criteria

  • Agent-cache-hit resolution p99 < 1 ms; regional-hit p99 < 5 ms (§4).
  • Stale-if-error: source down → stale flagged answer (I10), not a failure (principle 10).
  • Single-flight: N concurrent misses → 1 source fetch (verified); cache hit ratio ≥ 90 % under a realistic read mix.
  • Negative results cached + re-checked (I17); never cached past the bounded negative TTL.

19.5 Conformance Fixtures

  • cache/ttl_expiry.json, cache/negative_cache.json, cache/stale_if_error.json, cache/single_flight.json, cache/two_tier_hit.json, cache/invalidation.json.

19.6 Pitfalls

  • Cache key must include the filter (health policy/tags/locality) — two different queries for the same service must not collide (a subtle correctness bug → wrong results).
  • TTL longer than the freshness bound → stale answers past §4.2 (un-AP) — TTL must be ≤ health-TTL (I10).
  • Stale-if-error vs hard error: distinguish "source down" (serve stale) from "source says empty" (negatively cache) — conflating them serves stale forever or never serves stale.
  • Single-flight thundering herd: the first requester fetches, others wait — but a fetch error must fail/serve-stale all waiters, not hang them.
  • Negative-cache poisoning: a transient empty result cached too long → a real instance is invisible for the negative TTL — keep it short + freshen on register-gossip.

19.7 Performance Concerns

  • Agent cache is the 50 k+ QPS shield (principle 9); it must be lock-free read (sharded/arc-swap), O(1) lookup.
  • Memory: bounded caches (LRU/LFU eviction, #59); a 10^4-service fleet's hot set must fit; cap + evict cold entries.
  • Single-flight reduces source QPS by the fan-in factor (a hot key with 1000 concurrent misses → 1 fetch) — the key load-shed lever.

19.8 Edge Cases

  • TTL=0 (always-fetch, no cache); a key never accessed (evicted); source flaps (down/up) during stale-serve (refresh on recovery); negative entry then a register arrives (gossip invalidates the negative entry promptly); cache full (eviction under memory pressure).

19.9 Failure Analysis

  • A cache coherence bug (serving past TTL/freshness) → stale routing → the stale flag + age + TTL≤freshness bound it (I10); docs/runbooks/stale-resolution.md.
  • A stampede (no single-flight) → source meltdown on a popular TTL expiry → single-flight + jittered TTLs; docs/runbooks/cache-stampede.md.

19.10 Operational Notes

  • Cache hit-ratio by tier, stale-serve rate, single-flight coalesce rate, eviction rate; document the TTL strategy + stale-if-error policy + the stampede runbook.

20. Phase 8 — Federation / WAN: region link, selective replication, locality-aware resolution

20.1 Objectives

  • The internet-scale layer (principle 6): link regions over the WAN via a sparse gossip pool (ADR-10); selective/locality-scoped replication; cross-region resolution (I12); region projection — each region stays independently authoritative (I13, the AP heart).

20.2 Detailed Implementation Steps

  • federation::wan_pool — a sparse set of designated WAN nodes per region (e.g. 3) joins a cross-region pool (the Consul WAN-gossip model) — not all-to-all (bounds WAN traffic, §4.4).
  • federation::wan_gossip — region-level summary exchange over the WAN pool (lower cadence, TCP-backed); carries region catalog/health deltas for replicated services only.
  • federation::selective_repl — replicate a remote service into a region only on (a) demand (a local client queried it → subscribe, §8.13) or (b) a static replication policy. Demand-driven keeps the replicated set minimal.
  • federation::projection — remote services appear as a read-only Projection{origin, instances, age} (I10) tagged with origin region + freshness age.
  • federation::region_link — RegionLink{status: Connected|Degraded|Partitioned} (I13); a WAN partition → Partitioned → serve local-only + stale projection, never block (principle 6).
  • Cross-region resolution (P5 integration, I12): resolve local first; on local-empty + allow_remote, consult projections ordered by the locality ladder.

20.3 Deliverable

  • A service in region B is discoverable from region A (demand-driven projection); a WAN partition does not stop either region's local discovery; sddctl member-view --wan shows the WAN pool; examples/multi_region.

20.4 Acceptance Criteria

  • Cross-region register→discoverable p99 < 5 s (§4): intra-region + WAN-RTT + WAN-gossip round.
  • A WAN partition → both regions keep serving local discovery (I13); remote projections served stale-flagged (I10), never a hang.
  • WAN bandwidth bounded by the replicated set + churn (§4.4), not the full global catalog.
  • Locality ladder: local → same-locality → remote ordering correct (I12).

20.5 Conformance Fixtures

  • federation/cross_region_resolve.json, federation/demand_driven_repl.json, federation/wan_partition_serves_local.json, federation/projection_staleness.json, federation/wan_bandwidth_bounded.json, federation/locality_ladder.json.

20.6 Pitfalls

  • Replicate-all (every service to every region) → WAN-traffic blowup → demand-driven + policy scoping is mandatory (principle 6).
  • A WAN-pool node failure must not partition the region from the WAN → ≥2 WAN-pool nodes/region + SWIM over the WAN pool (bounded WAN failure detection).
  • Projection staleness must be flagged + aged (I10) — a silently-stale remote answer is the worst case (un-AP).
  • Cross-region clock skew on logical_ts → use per-region Lamport counters + incarnation; never compare wall-clocks across regions (the LWW order must survive WAN skew, I11).
  • A federation read on the local critical path → a WAN slowness stalls local resolution → federation must be strictly off the local-hit path (only on local-miss + allow_remote, I13).

20.7 Performance Concerns

  • WAN RTT (tens–hundreds of ms) dominates cross-region latency → cache projections aggressively (P7); demand-driven subscription keeps subsequent reads local.
  • Sparse WAN pool (O(regions·pool-size), not O(nodes)) keeps WAN connection count + gossip bounded — the scale property for many regions.
  • Selective replication: WAN bandwidth ∝ (replicated services · churn), independent of total catalog size.

20.8 Edge Cases

  • A region with no WAN peers (isolated — local-only, valid); a service replicated to a region then deregistered (projection invalidated via WAN gossip); a 3-region partition (each isolated — each serves local); asymmetric partition (A sees B, B doesn't see A — bounded by WAN SWIM); a brand-new region joining the WAN pool (bulk-syncs replicated set via WAN anti-entropy).

20.9 Failure Analysis

  • A federation bug that makes local discovery depend on the WAN → a WAN partition cascades to local outage (violates principle 6/I13) → the partition-injection DST test (P13) is the guard; docs/runbooks/wan-partition.md.
  • A projection that never refreshes (stuck subscription) → silently stale → the age flag + a max-age fail-safe (mark all-Critical past a threshold, P9) bound it.

20.10 Operational Notes

  • Per-region-link status, WAN-pool membership, projection ages, WAN bandwidth, cross-region propagation time; document the federation model + the WAN-partition runbook + the replication-policy config.

21. Phase 9 — Partition behavior + staleness bounds + CAP enforcement (the AP heart)

21.1 Objectives

  • Make the AP choice operational (principle 1/2/6): define + enforce + report staleness bounds (§4.2, I10); partition behavior (serve-stale vs fail-closed, configurable, I13); self-preservation under mass heartbeat loss (§8.3). This is the section that makes the system correctly AP.

21.2 Detailed Implementation Steps

  • Staleness computation: every cached/projected/resolved value carries an age; resolve stamps stale+stale_age when age > freshness_bound (I10); the bound is gossip-round + health-TTL (no partition) or anti-entropy-interval + WAN-RTT (partition) per §4.2.
  • Partition detection: a RegionLink → Partitioned (WAN SWIM) or an intra-region partition (SWIM split) flips serving into degraded mode.
  • StaleMode policy (ADR / I13): ServeStale (default — return stale-flagged data, AP) vs FailClosed (return error past a max-stale threshold, for callers that must not use stale data). Per-service configurable.
  • Self-preservation (§8.3): if the renewal rate drops below a threshold (mass heartbeat loss), stop expiring leases (assume network, not mass death) — an AP safeguard against evicting a healthy fleet during a blip (a bounded override of I3).
  • Flap damping: hysteresis on health transitions (don't gossip a Passing↔Critical flap; require N stable intervals) — reduces churn + false-positive amplification (P2/P12 tie-in).
  • Max-stale fail-safe: a projection/region older than a policy threshold may be marked all-Critical (fail-safe) so traffic stops routing to a region we've lost contact with (configurable per StaleMode).

21.3 Deliverable

  • Under injected partitions (DST, P13), staleness stays within §4.2 bounds + is always flagged; serve-stale vs fail-closed behaves per policy; self-preservation prevents fleet eviction on a simulated mass heartbeat loss; sddctl partition-status.

21.4 Acceptance Criteria

  • Staleness ≤ §4.2 bound, always flagged with an age (I10/principle 2) — verified in DST under partition.
  • A region serves local discovery throughout a WAN partition (≥99.99 % local availability, §4, I13).
  • FailClosed returns an error past the max-stale threshold; ServeStale returns stale-flagged data — both per policy.
  • Self-preservation: a simulated 80 % heartbeat-loss does not evict the fleet (§8.3); recovers when heartbeats resume.

21.5 Conformance Fixtures

  • partition/staleness_bounded.json, partition/serve_stale.json, partition/fail_closed.json, partition/self_preservation.json, partition/flap_damping.json, partition/region_independence.json, partition/max_stale_failsafe.json.

21.6 Pitfalls

  • Unbounded staleness (a value that ages forever with no flag) → silent black-holing → the age + bound + fail-safe are mandatory (principle 2, I10).
  • Self-preservation triggering on real mass death (vs network) → keeps dead instances listed → it errs toward availability (clients health-check + retry); document the tradeoff (§8.3) — there is no perfect answer (it's the AP corner of CAP).
  • Flap damping too aggressive → slow to reflect a real flap-then-die; too lax → churn amplification — tune hysteresis (P12).
  • FailClosed semantics: a caller that opts in must handle the error (no stale fallback) — easy to misconfigure into an outage; default is ServeStale (AP).
  • Asymmetric partition (one-way reachability) → both sides may suspect each other → bounded by SWIM confirmation + self-preservation; never a permanent split-brain of liveness (the catalog tier, P10, handles split-brain of metadata via Raft).

21.7 Performance Concerns

  • Staleness computation is O(1) per result (an age subtract); no hot-path cost.
  • Partition mode must not add latency to the local-hit path — degraded mode only changes remote answers + flags, not local serving.
  • Flap damping reduces gossip volume (fewer transitions) → a perf win under flappy conditions.

21.8 Edge Cases

  • Partition exactly at the staleness-bound boundary (age == bound → not yet stale); a partition that heals mid-resolution (anti-entropy reconciles, I9); a single-node region (no intra-region partition possible); FailClosed with zero non-stale data (returns error — the caller must handle); clock skew inflating computed age (monotonic clock for age, never wall-clock).

21.9 Failure Analysis

  • Mis-bounded staleness → clients route to long-dead instances silently → the bound + flag + DST partition tests are the net; the highest-stakes correctness property of an AP system (principle 2).
  • Self-preservation stuck on (never resumes expiry) → a permanently stale fleet → a recovery condition (renewal rate recovers → resume) + an alert if stuck > threshold; docs/failure-analysis/clock-skew.md + a self-preservation runbook.

21.10 Operational Notes

  • Partition status, staleness age distribution, self-preservation on/off + duration, flap-damp suppressions, fail-closed error rate; document the AP guarantees + the StaleMode/self-preservation tuning + the partition runbook. This section's telemetry is how an operator proves the AP bounds hold.

22. Phase 10 — Catalog consistency: per-region linearizable writes (the split from health)

22.1 Objectives

  • Implement the optional per-region linearizable catalog tier (principle 7, I14, ADR-12): serialize catalog writes (service/instance registration metadata) through a per-region Raft group, while health/membership stays AP (gossip). The central design decision made concrete.

22.2 Detailed Implementation Steps

  • registry::raft_catalog — a small per-region Raft group (3–5 nodes) ordering catalog writes (register/deregister/metadata changes) into a linearizable log (I14). (Raft itself reuses portfolio consensus; here it serializes only catalog ops.)
  • The split (principle 7): catalog writes → Raft log → applied to the read-optimized catalog (arc-swap); health/lease/membership updates → gossip/SWIM, never through Raft. A resolution joins the (linearizable) catalog + the (eventual) health at read time.
  • CatalogMode::{Eventual, RegionRaft} (ADR-12): Eventual = catalog also gossiped (Eureka-style, no consensus); RegionRaft = catalog writes Raft-serialized (Consul-style). Operator choice.
  • Read path: catalog reads are still served from the local arc-swap snapshot (linearizable-write does not mean linearizable-read here — reads are local, may be a Raft-term behind; bounded) — resolution stays lock-free + fast (principle 9). Health is always eventual.
  • Cross-region: the catalog is per-region authoritative (no global consensus, I13/principle 6); federation projects remote catalogs eventually. There is no global linearizable catalog (deferred §26.4) — that would re-introduce the CP availability problem (§2.7).

22.3 Deliverable

  • With CatalogMode::RegionRaft, concurrent conflicting catalog writes in a region are linearized (no two ports for one instance); health stays AP; sddctl catalog-info --consistency shows the Raft term + the mode; toggling to Eventual works.

22.4 Acceptance Criteria

  • Catalog writes are linearizable within a region under RegionRaft (I14) — verified by a linearizability check (concurrent writes → a single total order).
  • Health/membership is never routed through Raft (verified — a Raft outage does not stop health propagation or resolution, I14).
  • A catalog-Raft minority partition: catalog writes block on the minority side (CP for the catalog) but resolution + health continue (the split — discovery stays up even if registration is briefly unavailable).
  • Eventual mode matches the gossip-only behavior (no regression).

22.5 Conformance Fixtures

  • registry/catalog_linearizable.json, registry/health_not_in_raft.json, registry/catalog_raft_minority.json, registry/catalog_mode_toggle.json, registry/split_resolution_under_raft_outage.json.

22.6 Pitfalls

  • Routing health through Raft (the classic mistake) → health changes need consensus → unscalable + blocks resolution → health must never touch Raft (principle 7, the whole point of the split).
  • Linearizable write ≠ linearizable read — local reads may lag the leader by a term; document the read semantics (bounded staleness for catalog reads too) so callers don't assume read-your-writes across nodes.
  • A catalog-Raft outage blocking registration is acceptable (rare writes); blocking resolution is not → resolution reads the local snapshot, never the Raft leader (the split protects availability).
  • Raft group sizing: too large → slow writes; the catalog write rate is low (§4) so a small group (3–5) suffices; do not put 10^5 instances' health through it.

22.7 Performance Concerns

  • Catalog write latency = Raft commit (one round-trip + fsync) — acceptable for rare writes; health/resolution unaffected (not in Raft).
  • Resolution stays lock-free local-snapshot reads (principle 9) regardless of mode — the Raft tier only orders writes, never gates reads.
  • The Raft log applies to the arc-swap catalog → one publish per committed batch; batch writes under storm.

22.8 Edge Cases

  • Eventual↔RegionRaft toggle on a live cluster (drain in-flight, switch the write path); a Raft leader change mid-write (retry); a catalog write during a Raft minority partition (blocks/errs CatalogUnavailable — resolution unaffected); a single-node region (Raft trivial / Eventual); conflicting metadata writes (Raft linearizes; LWW within the eventual tier if Eventual).

22.9 Failure Analysis

  • Health-in-Raft regression (someone routes a health update through consensus) → resolution stalls on a Raft hiccup → a guard test (health updates must succeed during a Raft outage, I14) catches it; this is the most important correctness gate of the split.
  • A catalog/health join inconsistency (catalog says instance exists, health is gossiped-stale) → bounded by §4.2; the join is at read time, eventual health is expected — not a bug, a flagged staleness (I10).

22.10 Operational Notes

  • Catalog Raft term/leader/commit-latency, mode, catalog-write rate; document the split (docs/adr/catalog-health-split.md), the read semantics, and why health is never in Raft (the §2.7 / principle 7 rationale). This is the design's signature decision — document it loudly.

23.1 Objectives

23.3 Deliverable

23.4 Acceptance Criteria

  • Every API operation reachable over the C ABI; codes match §11.13.
  • No panic crosses the FFI boundary (catch_unwind everywhere, I16) — fuzz the ABI with bad args.
  • Result-array ownership/lifetime correct (no leak, no use-after-free) — ASan-clean.
  • ABI version macro present; a mismatched header refuses (I15).

23.5 Conformance Fixtures

  • cabi/register_resolve_c.json, cabi/error_codes.json, cabi/panic_to_errno.json, cabi/result_array_lifetime.json, cabi/abi_version.json.

23.6 Pitfalls

  • Panic across FFI = UB → catch_unwind at every entry (I16); a single missed boundary is a latent crash.
  • Result-array ownership: who allocates/frees (caller vs callee)? Document + provide sdd_free_results; a mismatch leaks or double-frees.
  • Callback (watch) re-entrancy + thread-safety: the callback fires on a runtime thread; document that it must not block / re-enter the API (deadlock risk).
  • String encoding (UTF-8 service names) + NUL-termination across the boundary; validate (I16).
  • ABI stability: adding a field to a result struct is a breaking change → version it; freeze the layout (SemVer-major to change, I15).

23.7 Performance Concerns

  • The SDK/agent embeds the cache → resolution is in-process sub-ms (no network on a cache hit) — the latency win of the agent model.
  • Avoid per-call allocation across FFI (reuse caller buffers where the ABI allows); the resolve hot path must not allocate per call.

23.8 Edge Cases

  • NULL pointers (validate → SDD_EINVAL, I16); a zero-length result (empty, not error); a watch callback that outlives the handle (cancellation must be safe); concurrent FFI calls on one handle (thread-safe or documented-single-threaded); a very large result array (cap / paginate).

23.9 Failure Analysis

  • An FFI memory bug = a crash in the embedding application (worst blast radius — it takes down the app, not just discovery) → ASan/Valgrind in CI + ABI fuzz + catch_unwind; the highest-stakes safety boundary (I16).
  • A wrong error code → SDK mishandles (e.g. retries a non-retryable) → the frozen code table + cabi/error_codes.json guard it.

23.10 Operational Notes

  • ABI version in the header + at runtime; document the embedding model (link the agent), ownership rules, and thread-safety in include/sdd.h + docs/. SDKs (Go/Python/Java) wrap this ABI.

24. Phase 12 — Performance hardening: 10^5–10^6 instances, gossip fan-out, endpoint sharding

24.1 Objectives

  • Reach internet scale (§4): 10^5–10^6 instances/region, 50 k+ resolution QPS/node, bounded gossip/anti-entropy at scale; EndpointSlice-style sharding for huge services; calibrate gossip/SWIM params per cluster.

24.2 Detailed Implementation Steps

  • Catalog scale: shard the catalog by service; per-service instance maps; an arc-swap snapshot per shard (lock-free reads, principle 9); 10^6 instances fit / shard across nodes.
  • EndpointSlice-style sharding (CoreDNS/K8s lesson): a service with 10^4 instances is split into bounded slices → resolution/DNS returns a slice (capped max_results) → avoids materializing/transferring the whole set per query.
  • Timer-wheel scale: the hierarchical wheel (ADR-20) handles 10^6 leases at O(1) amortized; verify the cascade cost under mass expiry.
  • Gossip scale: dissemination batching + the ~log N dissemination limit keep bandwidth churn-driven (§4.4); calibrate fanout k, intervals, dissemination limit per cluster size + churn (never hardcoded — a calibration probe like the cost model).
  • SWIM scale: O(1) probe load verified to N=1000 nodes; Lifeguard suspicion adaptation tuned for the cluster's jitter profile (false-positive minimization, §4.3).
  • Anti-entropy scale: incremental Merkle (O(log N) update/change), flow-controlled reconcile (bounded bandwidth, I9); near-free at steady state.
  • Resolution hot path: zero-allocation snapshot reads, pre-indexed candidate lookup, buffer reuse; profile + remove allocations on the 50 k-QPS path.

24.3 Deliverable

  • A region simulated at 10^5–10^6 instances sustains 50 k+ resolution QPS/node with gossip < 5 % CPU + bounded bandwidth; a 10^4-instance service resolves via slices; bench reports scale curves.

24.4 Acceptance Criteria

  • 10^5 instances/region steady (design to 10^6) with §4 memory/CPU/bandwidth budgets met.
  • Resolution ≥ 50 k QPS/node (cache-backed); p99 latencies within §4 by tier.
  • Gossip CPU < 5 %/core + bandwidth ≤ a few MB/s at 10^5 instances (§4.4); SWIM detection still < 3×probe-interval at N=1000.
  • A huge service (10^4 instances) resolves/DNS-answers via bounded slices without materializing the full set.

24.5 Conformance Fixtures

  • bench/scale_100k_instances.json, bench/resolution_qps.json, bench/gossip_bandwidth_at_scale.json, bench/swim_detection_n1000.json, bench/endpoint_slice.json, bench/timer_wheel_1m_leases.json.

24.6 Pitfalls

  • A lock on the resolution path surfaces only under load (50 k QPS) → contention collapse; lock-free from the start (principle 9), verified under load not just unit tests.
  • Per-query allocation looks fine at low QPS, melts at 50 k → allocation profiling on the hot path (flamegraph).
  • Gossip params tuned for a small cluster (low fanout/limit) → incomplete propagation at scale; re-calibrate per cluster size (a calibration probe).
  • A huge service materialized per query → memory/latency blowup → EndpointSlice sharding is mandatory above a size threshold.
  • Timer-wheel cascade cost under simultaneous 10^6 expiry (a region-wide TTL alignment) → jitter TTLs / spread expiry to avoid a thundering expiry.

24.7 Performance Concerns

  • Cache locality on the resolution path: pre-indexed, compact candidate layout; minimize pointer chasing on a hot read.
  • Gossip: batched UDP (amortize syscall + per-message overhead); avoid fragmentation (keep gossip frames < MTU; bulk over TCP).
  • Anti-entropy: incremental digest update (not full rebuild) — O(log N) per change, not O(N) per round.
  • NUMA / core pinning for the SWIM/gossip threads (timing isolation, ADR-27) on large nodes.

24.8 Edge Cases

  • A single service = the entire fleet (one giant slice set); 10^6 leases all expiring in one wheel tick; a cluster scaled from 3→1000 nodes (re-calibrate gossip live); a churn spike (registry storm at scale — §8.14 mitigations under load); a cold cache at 50 k QPS (single-flight prevents the source melt, P7).

24.9 Failure Analysis

  • A scale cliff (works at 10^4, melts at 10^5) → identify via scale-sweep benches before production; the bottleneck is usually a hidden lock or per-item allocation → flamegraph + lock-contention analysis.
  • Gossip bandwidth blowup at scale (mis-tuned limit/fanout) → the §4.4 budget gate + gossip-bandwidth-at-scale bench catch it; docs/performance/federation-bandwidth.md.

24.10 Operational Notes

  • Scale curves (QPS/latency/CPU/bandwidth vs instance count + node count) in docs/performance/; the gossip/SWIM calibration procedure; capacity-planning guidance (instances/node, nodes/region, WAN-pool sizing). Re-calibrate on cluster-size change.

25. Phase 13 — Conformance, deterministic simulation, fault/partition injection, bench

25.1 Objectives

  • The correctness + performance harness (principle 14): the single-region oracle, a deterministic-simulation (DST) differential (virtual time + injected faults → reproducible convergence/staleness assertions), fault/partition injection, and the §4 benchmark suite. The net that catches eventual-consistency bugs.

25.2 Detailed Implementation Steps

  • conformance::oracle — the single-region, single-store reference (P0); every scenario's expected end-state (principle 14).
  • conformance::dst — a deterministic simulation: a virtual clock + a seeded scheduler runs the whole multi-node/multi-region system in one process with injected partitions, message loss, reorder, delay, clock skew, and node death — and asserts convergence (all nodes reach the oracle state) + staleness bounds (§4.2) deterministically (reproducible from a seed). This is the signature testing technique for an AP distributed system (FoundationDB-style).
  • conformance::differential — run a scenario in DST vs the oracle; assert the converged state matches (modulo bounded in-flight staleness).
  • conformance::fault_inject — partition (WAN + intra-region), packet loss, reorder, delay, clock skew, node kill/restart, registry storm — all seeded + replayable.
  • conformance::fixtures — the per-phase fixture buckets (naming/registry/membership/gossip/antientropy/resolve/dns/cache/federation/partition/badinput).
  • bench — propagation-time, resolution-latency-by-tier, gossip-bandwidth, convergence-time, scale sweeps (§4); plot + regression-gate.
  • fuzz — DNS parse, gossip frame, name parse, query parse, Merkle decode (I16) — the boundary parsers.

25.3 Deliverable

  • make conformance runs all fixtures + DST scenarios green; make dst SEED=n reproduces any run; make bench reports §4 SLOs; fuzz targets run clean for the CI budget.

25.4 Acceptance Criteria

  • All phase fixtures pass; DST asserts convergence + staleness bounds under every injected fault class — reproducibly from a seed (principle 14).
  • The differential matches the oracle for every scenario (converged state identical).
  • Benchmarks meet §4 SLOs; a regression > a threshold fails CI.
  • Fuzz targets find no crashes in the CI budget (I16); a found crash becomes a regression fixture.

25.5 Conformance Fixtures

  • golden/* (convergence/state hashes per (scenario, seed)); partition/*, badinput/*; the full per-phase buckets; dst/scenarios/*.json (seeded fault scenarios).

25.6 Pitfalls

  • DST must be fully deterministic (one source of randomness = the seed; no wall-clock, no real I/O, no unseeded HashMap iteration order) or "reproducible" is a lie — the discipline is the hard part (eliminate every nondeterminism source).
  • The oracle must be obviously correct (simple single-store) — if the oracle is complex it can share a bug with the system → keep it trivial (principle 14).
  • A flaky DST test = a real nondeterminism bug (not "just rerun it") → hunt the unseeded source; never paper over flakiness.
  • Fault injection that's too weak (only clean partitions) misses real bugs → inject loss + reorder + skew + asymmetric partitions + storms (the messy reality).

25.7 Performance Concerns

  • DST runs the whole cluster in one process at virtual time → fast (no real network/sleep) → can run thousands of seeded scenarios in CI; this speed is why DST is feasible as a gate.
  • Benchmarks must run on representative topology (multi-node, multi-region) — single-process numbers mislead for a distributed system.

25.8 Edge Cases

  • A scenario that converges only after a partition heals (assert convergence post-heal, not during); a seed that triggers a rare interleaving (save it as a regression fixture); a fault sequence that the system should fail-closed on (assert the error, not convergence); maximum injected skew/loss (the boundary of the bounds).

25.9 Failure Analysis

  • The whole point: DST + the oracle catch eventual-consistency bugs (divergence, unbounded staleness, lost updates) that are unreproducible on a live cluster — without this harness, those bugs ship and manifest as "service X randomly invisible in region B" in production (the worst kind, principle 14).
  • A bug found only in production (not DST) → a gap in fault injection → add the fault class + a regression scenario; the harness must subsume every production-found failure.

25.10 Operational Notes

  • CI runs conformance + a DST seed sweep + bench regression on every PR; dst + fault + bench workflows; document the DST methodology + how to reproduce + how to add a scenario (docs/). DST is the project's correctness backbone — every distributed-consistency claim in §7 is a DST assertion.

29. Compatibility Guarantees

  • Wire compatibility (gossip/WAN): versioned, checksummed frames (I15); a node negotiates the protocol version on join and refuses an incompatible peer (no silent drift, principle 12). Frame layout is append-only within a major version.
  • DNS compatibility: strict RFC 1034/1035/2782/6763 conformance — any standard resolver works against the authoritative server unchanged; DNS-SD per RFC 6763; negative caching per RFC 2308. DNS is a frozen external contract.
  • API compatibility: the gRPC/proto schema is versioned (additive-only within major); REST gateway mirrors it. Resolve/Watch/Register signatures are stable; new fields are optional.
  • C ABI compatibility: the SDD_E* codes and result struct layouts are frozen within a major version (SemVer-major to change, I15); an ABI version macro guards mismatch. Adding a result field is a breaking change → new major.
  • Schema evolution: catalog metadata is a BTreeMap<String,String> (forward/backward compatible — unknown keys ignored); record types evolve additively.
  • Migration: a cluster upgrades via rolling node replacement under version negotiation; no flag-day. Crossing a wire-major requires a documented two-step (deploy version-N+1-capable readers, then writers).
  • Deprecation policy: a deprecated field/endpoint is supported ≥2 minor versions with a deprecation metric before removal at a major.
  • SemVer: crate SemVer; separate wire-protocol, DNS-interface, and gRPC-schema version numbers (they evolve independently of the crate version, ADR-30). Rolling-upgrade safety = same wire-major across the fleet.

30. Testing Strategy

  • Unit: every type/parser/algorithm — ServiceName::parse, Version::dominates (total-order property), timer-wheel, Merkle digest, DNS RR build, gossip apply rule, locality ordering.
  • Property-based (proptest): the LWW Version order is a total order (transitive/antisymmetric, I11 — the highest-leverage property); gossip apply is monotonic + idempotent + commutative (any order converges, §8.12); Merkle reconcile converges two arbitrary states; DNS parse↔serialize round-trips.
  • Differential: every scenario vs the single-region oracle (principle 14) — the converged distributed state == the oracle state (modulo bounded in-flight staleness).
  • Deterministic simulation (DST, the backbone): the whole multi-node/multi-region system in one process at virtual time, seeded, with injected partitions/loss/reorder/delay/skew/death/storm → asserts convergence (I9) + staleness bounds (§4.2, I10) + no lost update + region independence (I13) — reproducibly. Every §7 distributed invariant is a DST assertion.
  • Fuzzing: dns_parse, gossip_frame, name_parse, query_parse, merkle_decode (I16) — the boundary parsers; run for the CI budget + a longer nightly; a crash → a regression fixture.
  • Chaos / fault injection: seeded partition/loss/skew/kill/storm in DST (cheap, reproducible) + occasionally on a live docker cluster (realistic timing). Asymmetric partitions + reorder + skew (the messy reality), not just clean cuts.
  • Conformance: the per-phase fixture buckets (naming/registry/membership/gossip/antientropy/resolve/dns/cache/federation/partition/badinput); golden convergence/state hashes per (scenario, seed).
  • Soak: a long-running cluster under steady churn → watch for memory growth (leaks), divergence (anti-entropy gaps), and propagation drift.
  • Performance regression: bench SLO gates (§4) in CI — propagation, resolution-by-tier, gossip-bandwidth, convergence-time, scale; a regression > threshold fails the build.
  • Compatibility: mixed-wire-version cluster (negotiate/refuse, I15); dig against the DNS server (standard-resolver conformance); ABI tests (ASan-clean, frozen codes).
  • CI gate (the bar): make test (unit+property+differential) + make conformance (fixtures+DST seed sweep) + make bench (SLO regression) + fuzz-budget — all green; ASan on the FFI tests.

32. Performance Engineering

  • Benchmarking strategy: bench measures the §4 SLOs on representative topology (multi-node + multi-region, not single-process): propagation time (register→discoverable, intra/cross-region), resolution latency by tier, resolution QPS, gossip bandwidth + CPU, anti-entropy diff-bandwidth, convergence time under loss, scale sweeps (instances + nodes).
  • Profiling: perf + flamegraphs on the resolution hot path (target: zero allocation, lock-free, O(1) candidate lookup — principle 9); on the gossip/SWIM threads (target: < 5 % CPU, bounded bandwidth).
  • Flamegraph workflow: profile the 50 k-QPS resolution path + the gossip-storm path → identify allocations/locks/syscalls → eliminate; re-profile (the loop continues until SLOs hold under load).
  • Allocator analysis: per-query allocation is the resolution-path killer (melts at 50 k QPS) → buffer reuse, pre-indexed candidates, arena/pool for transient query state; track allocations/op.
  • Lock analysis: the resolution path must be lock-free (arc-swap/RCU snapshot reads, principle 9, ADR-19) — any lock surfaces as contention collapse under load; verify with a lock-contention profiler under the 50 k-QPS bench, not just unit tests.
  • Cache analysis: compact, pre-indexed candidate layout (minimize pointer chasing on a hot read); cache-line awareness for the member table + catalog snapshot.
  • Syscall analysis: batched UDP for gossip (amortize per-message syscall); zero-copy DNS serialize where possible; TCP_NODELAY off the bulk path, on for control.
  • Tail latency: GC-free (Rust) removes a major tail source; the remaining tails are lock waits (eliminated, principle 9), allocation spikes (pooled), and cross-region/WAN RTT (cached/demand-driven, P8). The agent-cache hit is the p99 < 1 ms guarantee.
  • Throughput targets: ≥50 k resolution QPS/node (cache-backed), ≥5 k registrations/s/region sustained (50 k burst), gossip ≤ a few MB/s/node at 10^5 instances (§4).
  • Memory profiling: bounded caches (LRU/LFU, #59) + the catalog (O(instances-in-region)) + membership (O(nodes)) — soak-test for leaks; the 10^6-instance target sets the per-node memory ceiling (shard above it).

33. Scalability Analysis

  • The scale property: gossip propagation is O(log N) rounds (not O(N) broadcast); SWIM load + detection are O(1) per node (not O(N²) all-to-all); anti-entropy bandwidth is O(diff) (not O(state)); gossip bandwidth is churn-driven (not instance-count-driven, §4.4). These together are why internet scale (10^5–10^6 instances) is feasible.
  • Bottlenecks + ceilings:
    • Resolution QPS — sharded lock-free caches scale near-linearly with nodes; ceiling = per-node cache size + CPU; mitigate by adding agents/regional caches (read scale-out).
    • Catalog memory — O(instances-in-region); ceiling ≈ 10^6 instances/region per node memory → shard the catalog across nodes + EndpointSlice huge services (P12).
    • Gossip bandwidth — churn-driven; ceiling = churn rate × fanout × event-size; mitigate by batching + dissemination limit (I8) + flap damping (P9).
    • SWIM membership — over nodes (not instances), so it scales with cluster node-count, not fleet size; instance health rides on node liveness + per-instance lease → membership stays small even at 10^6 instances.
    • Catalog-Raft write throughput — bounded (rare writes by design, §4); not a discovery-availability bottleneck (the split keeps reads/health out of it, principle 7).
  • Horizontal scaling: add server nodes (more gossip cluster + read capacity) + agents (read scale-out) within a region; add regions (federation scales by sparse WAN pools, O(regions·pool-size), not O(total-nodes)).
  • Vertical scaling: bigger nodes hold more catalog + serve more QPS; NUMA/core-pinning for gossip/SWIM timing isolation (ADR-27).
  • Sharding/partitioning: catalog by service; huge services by EndpointSlice (P12); regions are the natural geographic shard (each authoritative, principle 6).
  • Replication pressure: intra-region = full gossip replication (every node has the region's state) — bounded because it's per-region, not global; cross-region = selective replication (only queried/policied services, §8.13) — keeps WAN bounded.
  • Coordination overhead: near-zero on the data plane (gossip is coordination-free, principle 9); the only coordination is bootstrap + the optional catalog-Raft (rare writes). This is the AP scale advantage over a CP core (whose coordination is on every write, §2.7).
  • Network fanout: intra-region gossip fanout k (constant); WAN fanout = sparse pool (constant per region) — neither grows with fleet size.
  • Metadata scaling: the member table (O(nodes)) and the catalog (O(instances-in-region, shardable)) are the scaling metadata; both bounded/shardable; the design reaches 10^6 instances by keeping membership node-scoped + gossip churn-driven + anti-entropy diff-sized.

34. Mental Models & First Principles

The compressed insights an expert holds about internet-scale discovery. Each: the model, what it predicts, the bug class you write without it, and where this blueprint applies it.

  • MM1 — Discovery is a liveness oracle, not a truth oracle. It answers "where are instances that were healthy a bounded moment ago," never "where are instances that are healthy now" (impossible across a network). Predicts: every answer is inherently a recent past; correctness is bounded staleness, not zero staleness. Bug class without it: treating a returned instance as guaranteed-live → no client-side health check / retry → traffic black-holed at a just-died instance. Applied: §2.7, §4.2 (staleness budget), §21 (P9), I10.
  • MM2 — Availability is the product, consistency is a feature. If discovery can't answer, every dependent request fails — discovery down = fleet down. A stale answer costs one retry; no answer costs an outage. Predicts: under partition you serve stale, never block; the asymmetry forces the AP corner. Bug class without it: putting discovery on a CP core (etcd-only) → consensus unavailability = discovery unavailability → a minority-partition region's routing dies. Applied: §2.7 (the §36/etcd contrast), §6 principle 1, §21 (P9), I13.
  • MM3 — Gossip is probabilistic speed; anti-entropy is deterministic certainty. Epidemic dissemination converges fast (O(log N)) but lossily; periodic Merkle reconciliation guarantees no permanent divergence. They are complementary, not redundant. Predicts: gossip-only eventually diverges on packet loss; anti-entropy-only is minutes-slow. Bug class without it: shipping gossip-only → a dropped UDP frame leaves two nodes permanently disagreeing, undetected. Applied: §6 principle 3, §15 (P3), §16 (P4), I9.
  • MM4 — The version is the conflict-resolution algorithm. A total order (incarnation desc, logical_ts desc) makes merges commutative/associative/idempotent → any gossip/anti-entropy delivery order converges to the same state with zero coordination. Predicts: if the order isn't total, two nodes pick different winners and anti-entropy can't fix it (they disagree on truth). Bug class without it: ≥ instead of > in the apply rule → equal-version events ping-pong forever; a non-total order → permanent divergence. Applied: §8.12, §11.3 (Version::dominates), I7/I11, §12 (P0).
  • MM5 — Two liveness signals because each is blind to the other's failure. A lease catches a process that exited cleanly or is stuck-but-present (not renewing); SWIM catches a node that vanished suddenly and bounds detection time. Neither alone covers both. Predicts: lease-only → slow crash detection (full TTL); SWIM-only → an up-but-not-renewing instance looks alive. Bug class without it: relying on one signal → either dead instances served for a full TTL, or hung instances never detected. Applied: §6 principle 4, §8.3, §13 (lease, P1), §14 (SWIM, P2), I3/I6.
  • MM6 — Failure detection lives on a frontier, not at a point. Detection-time and false-positive-rate trade off continuously; you pick a point on the curve, you don't eliminate the tradeoff. A false positive evicts healthy instances (real traffic loss); slow detection serves dead ones (retries). Predicts: aggressive timeouts flap healthy nodes out under load/GC; lax timeouts serve corpses. Bug class without it: tuning for fast detection and discovering healthy instances vanish whenever a node GC-pauses. Applied: §4.3 (detection budget), §14 (P2), §6 principle 8, I6.
  • MM7 — Cost is driven by churn, not by size. Gossip bandwidth ∝ event-rate × fanout × event-size, independent of the total instance count; a million stable instances gossip almost nothing. Predicts: the registry storm (mass restart), not steady scale, is the bandwidth worst case. Bug class without it: sizing capacity off instance-count and being surprised when a deploy-wide restart broadcast-storms the cluster. Applied: §4.4 (gossip-bandwidth budget), §8.14 (storm), §6 principle 5, §33, I8.
  • MM8 — A region is the unit of independence; the WAN is best-effort glue. Local discovery must never sit on the WAN critical path; federation replicates selectively and asynchronously, and a WAN partition degrades only remote answers. Predicts: any synchronous cross-region read makes a WAN blip a local outage. Bug class without it: a "resolve anywhere" path that round-trips the WAN on every miss → WAN latency/partition cascades into local resolution. Applied: §6 principle 6, §20 (P8), §3.3 failure boundary, I13.
  • MM9 — Merkle reconciliation pays for the difference, not the whole. A hash tree over (key→version) lets two nodes skip matching subtrees and exchange only divergent keys — but only if both build the identical tree (deterministic key ordering). Predicts: steady-state anti-entropy is near-free (digests match); it spikes only after divergence. Bug class without it: non-deterministic key ordering → digests never match → every reconcile ships the full state → bandwidth blowup. Applied: §8.5, §16 (P4), §4.4, I9.
  • MM10 — Determinism is the only debugger for eventual consistency. Divergence/lost-update/unbounded-staleness bugs are unreproducible on a live cluster (timing-dependent); you must drive the whole system at virtual time from a seed, with injected faults, and assert against a trivially-correct oracle. Predicts: without a deterministic harness, these bugs ship and manifest as "service X randomly invisible in region B." Bug class without it: "just rerun it" on a flaky distributed test → papering over a real nondeterminism bug. Applied: §6 principle 14, §25 (P13, DST), §12 (oracle, P0).

36. Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from the System Constraints table (§4). Inputs from §4: N=100 nodes/region, fanout k=3, gossip interval 200 ms, instances 10^5 (design 10^6), record ≈ 200 B, lease TTL 15 s (renew at ttl/3 ≈ 5 s), probe interval 1 s, anti-entropy interval 30 s, WAN RTT 80 ms, hash 32 B.

  • C1 — Gossip rounds to full coverage. rounds ≈ log_k N = log₃ 100 = ln100/ln3 = 4.605/1.099 ≈ 4.2 → with a few extra for high-probability coverage, ≈ 5–6 rounds. Predicts intra-region propagation = 6 × 200 ms ≈ 1.2 s < the §4 2 s p99. (§4.1.)
  • C2 — Steady-state gossip event rate. At 10^5 instances and 1 % churn/s, event_rate = 10^5 × 0.01 = 1,000 events/s. Drives every bandwidth number below; independent of total instance count (MM7).
  • C3 — Per-node gossip bandwidth. Each event is gossiped to k=3 peers and disseminated ~log N ≈ 12 times before retiring: bytes/s ≈ event_rate × event_size × k × (dissemination_limit / spread) . Upper-bound it as 1,000 × 200 B × 3 × 12 ≈ 7.2 MB/s aggregate sent across its dissemination life, amortized per round ≈ low single-digit MB/s/node → within §4's "a few MB/s." Batching (coalescing events per message) cuts the per-message overhead further. (§4.4.)
  • C4 — Registry RAM (catalog). instances × record_size = 10^5 × 200 B = 20 MB per region replica; at the 10^6 design point = 200 MB → fits one node, shard beyond. Add health/lease overhead (~3× with versions/timestamps) → ≈ 60 MB at 10^5, ≈ 600 MB at 10^6 → the per-node memory ceiling that triggers catalog sharding (§4, P12).
  • C5 — Lease-renewal write QPS. Each instance renews every ttl/3 = 5 s: renew_QPS = instances / 5 s = 10^5 / 5 = 20,000 renews/s/region (200,000/s at 10^6). Predicts the steady write load the lease manager + timer wheel must absorb (distinct from the §4 5 k/s registration rate — renewals dominate). Timer-wheel O(1) expiry is why this is feasible (ADR-20).
  • C6 — Timer-wheel expiry load. With a 100 ms slot and 10^5 leases spread over a 15 s TTL: expiries/slot ≈ instances × (slot / ttl) = 10^5 × (0.1/15) ≈ 667 leases/slot checked per tick → trivial O(slot-occupancy) work; the cascade only bites if TTLs align (mitigate by jitter, §24.6). (I3.)
  • C7 — SWIM probe load (per node). SWIM probes one random member per interval regardless of N: probe_msgs/s/node = 1/probe_interval = 1/s direct + k_indirect only on a miss → O(1), independent of N and of instance count — ~1–4 msgs/s/node. This is why detection time stays < 3 s at N=1000 (§4.3). (MM6, I6.)
  • C8 — Detection time. detect ≈ probe_interval + k_indirect × probe_timeout + suspicion_timeout = 1 s + (3 × 0.5 s capped) + 2 s; the indirect probes run in parallel so ≈ 1 + 0.5 + … < 3 s → meets the §4 "< 3×probe-interval" bound. (§4.3, I6.)
  • C9 — Anti-entropy digest size. A Merkle tree over 10^5 keys with 32 B leaf hashes: leaf layer = 10^5 × 32 B = 3.2 MB; but a digest exchange sends only the root + the path to divergent leaves — for d differing keys ≈ d × tree_depth × 32 B, depth = log₂(10^5) ≈ 17. For d=100 divergent keys: ≈ 100 × 17 × 32 B ≈ 54 KB per reconcile — diff-sized, not 3.2 MB (MM9). Matching trees transfer just the 32 B root. (§4.4, I9.)
  • C10 — Cross-region propagation. intra_region (C1) + WAN_gossip_round + WAN_RTT = 1.2 s + 1 s + 0.08 s ≈ 2.3 s < the §4 5 s cross-region p99. (§4.1.)
  • C11 — Resolution QPS shielding. Target 50 k QPS/node from cache. At a 90 % agent-cache hit ratio, authoritative load = 50,000 × 0.10 = 5,000 QPS/node to the registry; single-flight collapses a hot key's M concurrent misses to 1 fetch → a 1,000-fan-in hot key cuts that key's source QPS by 1000×. Predicts the cache is the load-bearing latency + load-shed layer (§4, P7). (I11 caching, principle 10.)
  • C12 — WAN bandwidth (federation). WAN cost ∝ replicated services × their churn, not the global catalog. If region A subscribes to 1,000 remote instances at 1 % churn: = 1,000 × 0.01 × 200 B × pool_fanout(3) ≈ 6 KB/s per WAN-pool link — negligible vs replicating the whole 10^5-instance remote region. This is why demand-driven selective replication is the scale lever (§4.4, §8.13, P8).

38. Alternative Architectures (Roads Not Taken)

Fundamentally different architectures for the same problem — each with a sketch, the regime where it wins, the real system that embodies it, and why this blueprint rejected it.

38.1 Strongly-consistent CP registry on Raft (etcd / Consul-servers model)

clients ──► [ Raft leader ] ──► replicated log ──► state machine (catalog+health)
                 │  (followers; minority refuses writes under partition)
                 ▼
            linearizable reads/writes; one global (or per-DC) consensus group
  • Regime where it wins: when the registry is also the coordination store (locks, leader election, strongly-consistent config) and stale/split answers are catastrophic while a brief write or read unavailability under partition is acceptable. Small-to-mid clusters in a single failure domain.
  • Real system: etcd (#36); Consul's server tier for its catalog/KV; ZooKeeper.
  • Why rejected here: discovery's value is availability — under partition a minority region must keep answering, or its entire fleet's routing dies (§2.7, MM2). A globally-CP registry makes discovery availability = consensus availability. We do reuse Raft, but only for the optional per-region catalog tier (P10), never for health, and never globally (I13/I14).

38.2 Pure hierarchical DNS delegation (no gossip, no mesh)

root zone ──delegates──► region zone ──delegates──► service zone
   client recursive resolver walks the delegation, caches by TTL at each level
   liveness = "remove the record"; convergence = TTL expiry
  • Regime where it wins: internet-scale naming where updates are infrequent, clients are arbitrary DNS resolvers, and second-to-minute TTL-bounded staleness is fine — the original planet-scale discovery system. Zero custom protocol; infinite client compatibility.
  • Real system: the DNS itself (Mockapetris); classic SRV-based discovery; cloud private DNS zones.
  • Why rejected here (as the core): DNS TTL convergence is coarse (you can't push a "instance just died" in < TTL), it has no rich filtering (health/tag/locality/weight beyond SRV), and no active failure detection (a dead instance lingers a full TTL with no SWIM). We keep DNS as an interface (P6) over a gossip+SWIM core that gives sub-second health propagation and filtered resolution — DNS as a facade, not the engine.

38.3 Centralized SQL/relational registry (single authoritative DB)

all nodes ──► [ primary SQL DB ] ◄── all reads/writes (catalog+health rows)
                 │  (optional read replicas, async)
              health = a "last_heartbeat" column updated per renew
  • Regime where it wins: a single datacenter, modest fleet, where a relational store the team already operates gives transactions, ad-hoc queries, and simple operations — and the DB's availability is "good enough." Strong consistency + arbitrary queries for free.
  • Real system: early/in-house service registries on PostgreSQL/MySQL; many homegrown "service table" designs.
  • Why rejected here: it does not survive the constraints — a heartbeat-per-instance write load (§36 C5: 20 k–200 k renews/s) hammers the DB; it is a single failure domain (no region independence, principle 6); cross-region means DB replication lag or a stretched cluster (CP availability problem); and it has no O(log N) dissemination or O(1) failure detection. It melts at internet scale.

38.4 Client-side gossip-only, no authoritative tier (full peer-to-peer)

every instance ◄──gossip──► every instance   (no servers; the mesh IS the registry)
   each app embeds the full membership+catalog; resolves from its own local view
   convergence = gossip + anti-entropy among ALL instances
  • Regime where it wins: a fully decentralized / edge / serverless-peer system with no operable server tier, where every participant is symmetric and willing to carry membership state — and the fleet is small-to-mid (gossip among instances, not nodes, scales with instance count). Maximum decentralization, no SPOF tier.
  • Real system: Serf used standalone; Cassandra/Dynamo's peer gossip (every node is symmetric); some P2P/edge discovery (cf. #360 overlay).
  • Why rejected here: gossiping among all instances makes membership O(instances) not O(nodes) — at 10^6 instances the SWIM/gossip load explodes (the §4.3 scale property is lost); there is no place for the catalog-CP tier, the DNS/agent caching tier, or selective WAN federation. We keep a thin server + agent topology so membership is node-scoped (10^6 instances ride on ~10²–10³ nodes' liveness, §36 C7) and the cache/DNS/federation tiers have a home.

40. Glossary

  • Service discovery — the mechanism by which a client finds the network location(s) of a named service's healthy instances. The substrate every microservice request depends on.
  • Registry / catalog — the authoritative record of services → instances (address/port/metadata/tags). The "what exists" tier.
  • Instance — a single running copy of a service, identified by InstanceId, with an address/port/locality/tags/weight.
  • Lease (TTL) — a time-bounded liveness assertion an instance must renew; expiry → the instance is presumed gone. One of the two liveness signals.
  • Heartbeat / renew — the periodic call that resets a lease's expiry (renew-at-ttl/3 to tolerate skew + loss).
  • Health state — Passing | Warning | Critical; resolution filters by a health policy.
  • SWIM — Scalable Weakly-consistent Infection-style Process group Membership: a failure detector using direct + indirect probes, suspicion, and incarnation numbers; O(1) load, bounded detection. The second liveness signal.
  • Direct / indirect probe — SWIM pings a peer directly; on no ack, asks k other peers to probe it (filters transient slowness → fewer false positives).
  • Suspicion — SWIM's intermediate state (Alive → Suspect → Dead) giving a node time to refute before eviction.
  • Incarnation number — a per-node monotonic counter; a node refutes a false Suspect by re-asserting Alive with a higher incarnation. The per-key version that makes LWW correct across the refute race.
  • Gossip / epidemic protocol — randomized peer-to-peer dissemination; state spreads in O(log N) rounds at fanout k. Fast but lossy.
  • Push / pull / push-pull — gossip modes: push new events, pull a peer's events, or exchange digests-then-deltas (push-pull converges fastest).
  • Fanout (k) — the number of random peers an event is gossiped to per round.
  • Dissemination limit — the max times an event is gossiped before retiring (~log N); bounds bandwidth.
  • Piggybacking — attaching gossip events to SWIM probe/ack messages (free propagation).
  • Anti-entropy — periodic full-state reconciliation (here via Merkle trees) that repairs anything gossip dropped → guaranteed eventual convergence. Gossip's correctness backstop.
  • Merkle tree — a hash tree over (key → version); matching subtrees are skipped, so reconciliation transfers only the diff, not the whole state.
  • Read repair — repairing a stale replica during a read/reconcile (the anti-entropy mechanism).
  • Eventual consistency — replicas converge to the same state given no new updates + time; reads may transiently differ (bounded here).
  • AP (CAP) — under partition, choose Availability + Partition-tolerance over Consistency: keep answering with bounded-stale data. Discovery's choice.
  • CP (CAP) — choose Consistency + Partition-tolerance, refusing progress under partition (etcd/#36). The contrast; wrong for discovery availability.
  • PACELC — extends CAP: else (no partition) trade Latency vs Consistency. Discovery is PA/EL (favors availability under partition, latency otherwise).
  • Bounded staleness — a hard cap on how stale a returned answer can be (gossip-round + health-TTL, or anti-entropy-interval + WAN-RTT under partition), always flagged with an age.
  • LWW register — Last-Writer-Wins: concurrent updates to a key resolve by a total order (incarnation desc, logical_ts desc); commutative/idempotent → convergence.
  • Logical clock / Lamport timestamp — a per-node monotonic counter giving a causal-ish order without synchronized wall-clocks (used in the Version order).
  • Self-preservation — Eureka's safeguard: when too many heartbeats are lost at once, assume a network problem (not mass death) and stop expiring leases — avoids evicting a healthy fleet during a blip.
  • Federation — linking independently-authoritative regional registries over the WAN with selective replication. The internet-scale layer.
  • WAN gossip pool — a sparse set of designated nodes per region that gossip region-level summaries cross-region (bounds WAN traffic; the Consul model).
  • Selective / demand-driven replication — a region replicates a remote service only if a local client queried it (or per policy) — not the whole world to everywhere.
  • Region projection — a read-only, freshness-tagged local view of a remote region's service.
  • Locality ladder — the resolution ordering preference: same-zone → same-region → other-region.
  • Blocking query / long-poll — a resolution that holds the request open until the result set's version changes or a timeout fires (efficient change notification without polling).
  • DNS-SD — DNS-Based Service Discovery (RFC 6763): _service._proto PTR enumerate → SRV+TXT resolve.
  • SRV record — a DNS record giving a service's host+port+priority+weight (RFC 2782).
  • Negative caching — caching a "no result / NXDOMAIN" answer with a short bounded TTL (RFC 2308) to shed repeat misses.
  • Stale-if-error — serving expired (stale, flagged) cached data when the source is unreachable — an AP cache behavior.
  • Single-flight / request coalescing — collapsing concurrent misses for the same key into one source fetch (anti-stampede).
  • Registry storm — a burst of registrations (mass restart/deploy) that can broadcast-storm gossip if not batched + rate-limited.
  • Flap damping — hysteresis on health transitions to avoid gossiping a rapidly-flapping instance's every state change.
  • Timer wheel — a hierarchical timing-wheel data structure giving O(1)-amortized expiry for millions of leases.
  • EndpointSlice — sharding a huge service's instance set into bounded slices (the Kubernetes/CoreDNS technique) so resolution/DNS doesn't materialize the whole set.
  • Deterministic simulation (DST) — running the whole distributed system in one process at virtual time with seeded fault injection, so convergence/staleness are asserted reproducibly. The correctness backbone.
  • Single-region oracle — the trivially-correct single-store reference the distributed system is validated against.
  • Split (catalog/health) — the design decision to put rarely-changing catalog metadata on an optional consistency tier (per-region Raft) while keeping constantly-changing health eventually consistent (gossip). The system's signature decision.
  • Crash-only — a node can be killed at any time and rejoin cleanly (via gossip + anti-entropy) with no data loss.
