4.1 Worked propagation-time budget (gossip O(log N) convergence)

  • Gossip model: each round, every node forwards each un-retired event to k random peers; an event reaches all N nodes in ≈ log_k N rounds (epidemic spreading), with high probability after a few extra rounds.
  • Intra-region: N=100 nodes, fanout k=3, gossip interval 200 ms. log₃100 ≈ 4.2 rounds → ~5–6 rounds for high-probability full coverage → ~1.0–1.2 s < the 2 s p99 target. SWIM piggybacking shortens this (every probe also carries events).
  • Cross-region: add one WAN-gossip round (sparse pool exchanges region B's update with region A) + WAN RTT. WAN interval 1 s, WAN RTT 80 ms → region A learns B's update ~1 s + 80 ms after it converged in B → total ~2–3 s < the 5 s target.
  • Anti-entropy backstop: if an event is dropped by gossip (UDP loss), it is not lost forever — the next Merkle reconciliation (interval ≤ 30 s) repairs it. So the p99 propagation is the gossip path; the worst case (after loss) is bounded by the anti-entropy interval (I9). The §4 table states the gossip-path SLO; the anti-entropy interval is the convergence guarantee, not the common-case latency.
  • Implication: propagation time scales with log N (gossip) not N (broadcast) — this is why gossip is used and why the system reaches 10^6 instances; the constraint table targets are stated against the log N model, calibrated per cluster (P12), never assumed.

4.2 Worked staleness budget (what "healthy" can lag reality)

  • A resolution returns instances marked healthy. How stale can that be? Two failure-to-reality delays:
    • Just-died instance still listed: worst case = SWIM detection time (≤ 3 s) or lease TTL (≤ 15 s default) — whichever fires first; the client also health-checks, catching it at request time. So a dead instance is returned for ≤ ~3 s (SWIM) in the common case.
    • Just-registered instance not yet listed: worst case = propagation time (§4.1, < 2 s intra, < 5 s cross-region).
  • Under partition: add the partition duration up to the anti-entropy interval — but capped: the answer is flagged stale with an age, so the client knows (I10). Staleness is bounded (≤ anti-entropy-interval + WAN-RTT), never unbounded — the AP system promises bounded staleness, not zero staleness (principle 6).
  • Why this is acceptable (the §2.7 argument made numeric): a stale entry costs one failed request + retry to another candidate (the client's LB retries; resolution returned multiple candidates). The alternative — blocking for consistency under partition (CP) — costs a fleet-wide outage. Bounded staleness (seconds) ≪ outage (until partition heals). The numbers justify the AP choice.
  • Tuning knob: shorter health-TTL / probe-interval → fresher data but more gossip/probe load + more false positives; the operator trades freshness against load (§4.3). The bound is always enforced and reported, never silent.

4.3 Failure-detection budget (detection-time vs false-positive, SWIM)

  • SWIM detection time ≈ probe_interval + (k_indirect · probe_timeout) + suspicion_timeout. Smaller intervals/timeouts → faster detection but more false positives (a GC-paused or briefly-slow node wrongly suspected).
  • Example: probe_interval=1 s, probe_timeout=500 ms, indirect probes via k=3 peers, suspicion_timeout=2 s → detection ≈ 1 + 0.5 + … < 3 s (< the §4 "3 × probe-interval" bound) with a low false-positive rate (indirect probes filter transient slowness; incarnation numbers let a falsely-suspected node refute).
  • Cost asymmetry: a false positive marks healthy instances unhealthy → they drop out of resolution → real traffic loss until refuted (~suspicion_timeout). A slow detection leaves a dead instance listed → retries (recoverable). So the default leans slightly conservative (favor avoiding false positives), tunable per service criticality.
  • Scale-independence: SWIM's per-node load is O(1) (one random probe per interval regardless of N), and detection time is O(1) (not O(N)) — so detection does not slow as the region grows to 10^5–10^6 instances (membership is over nodes, not instances; instance health rides on node liveness + per-instance lease). This is why SWIM is chosen over all-to-all heartbeating (which is O(N²) and does not scale).

4.4 Worked gossip-bandwidth budget (why it stays bounded at scale)

  • Per-node gossip bandwidth ≈ fanout · event_rate · event_size · dissemination_limit. It depends on the event rate (registrations/health-changes per second), not on the total instance count — a steady fleet of 10^6 mostly-stable instances gossips almost nothing; churn drives cost.
  • Example: 10^5 instances, 1 % churn/s = 1 k events/s, event ≈ 200 B, fanout k=3, each event gossiped ~log N ≈ 12 times before retiring → 1000 · 200 · 3 · (12/rounds…) ≈ low single-digit MB/s/node — within the §4 budget.
  • Anti-entropy adds a periodic O(state-digest) Merkle exchange, but reconciliation transfers only the diff (I9), so steady-state anti-entropy bandwidth is near-zero (digests match); it spikes only after divergence (loss/partition heal).
  • Registry storm (mass restart: every instance re-registers at once) is the worst case — O(instances) events in a burst. Mitigations (P1/P12): dissemination batching (coalesce many events per gossip message), rate-limited re-registration (agents jitter their re-register), and the §4 50 k/s burst target. The storm is bounded and shed, not amplified (principle 5).
  • Implication: gossip cost is governed by churn, and the design keeps churn-driven traffic O(log N) per event and batched — so bandwidth stays bounded as instances grow, the property that makes internet scale feasible.

36. Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from the System Constraints table (§4). Inputs from §4: N=100 nodes/region, fanout k=3, gossip interval 200 ms, instances 10^5 (design 10^6), record ≈ 200 B, lease TTL 15 s (renew at ttl/3 ≈ 5 s), probe interval 1 s, anti-entropy interval 30 s, WAN RTT 80 ms, hash 32 B.

  • C1 — Gossip rounds to full coverage. rounds ≈ log_k N = log₃ 100 = ln100/ln3 = 4.605/1.099 ≈ 4.2 → with a few extra for high-probability coverage, ≈ 5–6 rounds. Predicts intra-region propagation = 6 × 200 ms ≈ 1.2 s < the §4 2 s p99. (§4.1.)
  • C2 — Steady-state gossip event rate. At 10^5 instances and 1 % churn/s, event_rate = 10^5 × 0.01 = 1,000 events/s. Drives every bandwidth number below; independent of total instance count (MM7).
  • C3 — Per-node gossip bandwidth. Each event is gossiped to k=3 peers and disseminated ~log N ≈ 12 times before retiring: bytes/s ≈ event_rate × event_size × k × (dissemination_limit / spread) . Upper-bound it as 1,000 × 200 B × 3 × 12 ≈ 7.2 MB/s aggregate sent across its dissemination life, amortized per round ≈ low single-digit MB/s/node → within §4's "a few MB/s." Batching (coalescing events per message) cuts the per-message overhead further. (§4.4.)
  • C4 — Registry RAM (catalog). instances × record_size = 10^5 × 200 B = 20 MB per region replica; at the 10^6 design point = 200 MB → fits one node, shard beyond. Add health/lease overhead (~3× with versions/timestamps) → ≈ 60 MB at 10^5, ≈ 600 MB at 10^6 → the per-node memory ceiling that triggers catalog sharding (§4, P12).
  • C5 — Lease-renewal write QPS. Each instance renews every ttl/3 = 5 s: renew_QPS = instances / 5 s = 10^5 / 5 = 20,000 renews/s/region (200,000/s at 10^6). Predicts the steady write load the lease manager + timer wheel must absorb (distinct from the §4 5 k/s registration rate — renewals dominate). Timer-wheel O(1) expiry is why this is feasible (ADR-20).
  • C6 — Timer-wheel expiry load. With a 100 ms slot and 10^5 leases spread over a 15 s TTL: expiries/slot ≈ instances × (slot / ttl) = 10^5 × (0.1/15) ≈ 667 leases/slot checked per tick → trivial O(slot-occupancy) work; the cascade only bites if TTLs align (mitigate by jitter, §24.6). (I3.)
  • C7 — SWIM probe load (per node). SWIM probes one random member per interval regardless of N: probe_msgs/s/node = 1/probe_interval = 1/s direct + k_indirect only on a miss → O(1), independent of N and of instance count — ~1–4 msgs/s/node. This is why detection time stays < 3 s at N=1000 (§4.3). (MM6, I6.)
  • C8 — Detection time. detect ≈ probe_interval + k_indirect × probe_timeout + suspicion_timeout = 1 s + (3 × 0.5 s capped) + 2 s; the indirect probes run in parallel so ≈ 1 + 0.5 + … < 3 s → meets the §4 "< 3×probe-interval" bound. (§4.3, I6.)
  • C9 — Anti-entropy digest size. A Merkle tree over 10^5 keys with 32 B leaf hashes: leaf layer = 10^5 × 32 B = 3.2 MB; but a digest exchange sends only the root + the path to divergent leaves — for d differing keys ≈ d × tree_depth × 32 B, depth = log₂(10^5) ≈ 17. For d=100 divergent keys: ≈ 100 × 17 × 32 B ≈ 54 KB per reconcile — diff-sized, not 3.2 MB (MM9). Matching trees transfer just the 32 B root. (§4.4, I9.)
  • C10 — Cross-region propagation. intra_region (C1) + WAN_gossip_round + WAN_RTT = 1.2 s + 1 s + 0.08 s ≈ 2.3 s < the §4 5 s cross-region p99. (§4.1.)
  • C11 — Resolution QPS shielding. Target 50 k QPS/node from cache. At a 90 % agent-cache hit ratio, authoritative load = 50,000 × 0.10 = 5,000 QPS/node to the registry; single-flight collapses a hot key's M concurrent misses to 1 fetch → a 1,000-fan-in hot key cuts that key's source QPS by 1000×. Predicts the cache is the load-bearing latency + load-shed layer (§4, P7). (I11 caching, principle 10.)
  • C12 — WAN bandwidth (federation). WAN cost ∝ replicated services × their churn, not the global catalog. If region A subscribes to 1,000 remote instances at 1 % churn: = 1,000 × 0.01 × 200 B × pool_fanout(3) ≈ 6 KB/s per WAN-pool link — negligible vs replicating the whole 10^5-instance remote region. This is why demand-driven selective replication is the scale lever (§4.4, §8.13, P8).
