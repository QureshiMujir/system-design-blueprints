31. Mental Models & First Principles

  1. MM1 — Visibility is a pure function, not a lookup. The compressed insight: a version is visible or not based only on (header, snapshot), never on "ask someone else." Predicts: any design that adds a lock or a remote call to the read path has broken the core promise. Bug class without it: read-path lock contention that silently regresses P1's throughput guarantee. Resolving: §13 (Phase 1), I1.
  2. MM2 — MVCC is fundamentally about naming versions, not locking data. Reed's 1978 thesis framed it as "version pumps" — a generational naming problem, not a mutual-exclusion problem. Predicts: the hard part is always the id/timestamp allocation scheme (xid, commit-ts), not the locking primitive. Bug class without it: engineers reach for locks to "fix" an MVCC bug that is actually a timestamp-ordering bug. Resolving: §2, §20 (Phase 8).
  3. MM3 — There are three distinct "time" axes and conflating any two is a bug class. Allocation-order (TransactionId), commit-order (CommitTs), and physical wall-clock (HLC's physical component) are different number lines. Predicts: any comparison between an xid and a commit-ts, or a physical-clock read substituting for an HLC read, is probably wrong. Bug class without it: horizon/snapshot confusion (§15.6), clock-skew bugs in SSI's dangerous-structure check (§17.6). Resolving: §15 (Phase 3), §20 (Phase 8).
  4. MM4 — Append-only and in-place-with-undo are different universes, not variations on a theme. The compressed insight: GC strategy, rollback mechanism, and crash-recovery semantics all follow from this one architectural choice (ADR-04/ADR-05). Predicts: code that "shares a little logic" between HeapStore and InMemStore beyond the VersionStore trait surface is a maintenance trap. Bug class without it: rollback bugs from assuming append-only's "no undo needed" property applies to the in-memory backend. Resolving: §18 (Phase 6), P10.
  5. MM5 — The xmin horizon is the one number that must never be wrong in the "too high" direction. Compressed insight: an incorrectly-low horizon merely delays GC (safe, wasteful); an incorrectly-high horizon reclaims a version a live reader can still see (unsafe, catastrophic). Predicts: every horizon-adjacent bug should be biased toward "GC does less," never "GC does more," when in doubt. Bug class without it: FM9 (premature reclamation). Resolving: §7 (I4, I10), §18 (Phase 6).
  6. MM6 — Snapshot Isolation is a specific, nameable gap away from serializability, not a vague approximation. The gap has a name (write-skew, A5B) and a fix (SSI's dangerous-structure detection) — it is not "mostly serializable." Predicts: any claim of "SERIALIZABLE" in a vendor's default configuration should be independently verified against the Berenson suite, not trusted. Bug class without it: business-invariant violations shipped to production under a false serializability assumption. Resolving: §15 (Phase 3), §17 (Phase 5).
  7. MM7 — A predicate lock that never blocks is still a lock — it has cardinality and memory cost. SIREAD locks (§17.2) do not block writers but are not free; they are O(reads) memory structures with their own scaling story. Predicts: an SSI deployment with extreme read volume needs its own capacity plan, independent of the write-path capacity plan. Bug class without it: unbounded memory growth mistaken for a leak rather than a scaling limit (§17.6, T10). Resolving: §17 (Phase 5), §30.
  8. MM8 — A timestamp source's failure mode is the actual architectural decision, not its happy-path latency. Centralized oracle fails by halting the cluster; HLC fails by bounded-but-nonzero skew; TrueTime fails by requiring infrastructure most deployments do not have. Predicts: choosing a timestamp source is choosing which failure mode you can live with, not which one is "fastest." Resolving: §20 (Phase 8), §32.

5. Required Reading

Books

  • Bernstein, P., Hadzilacos, V., Goodman, N. Concurrency Control and Recovery in Database Systems. Addison-Wesley, 1987. Chapters 1–3 (the model), 5 (two-phase locking), 8 (timestamp ordering & multiversion methods, esp. Section 8.5 "Multiversion Mixed Method"). Applied throughout Phase 1–3 (§13–§15); the theoretical base for I1–I5.
  • Weikum, G., Vossen, G. Transactional Information Systems. Morgan Kaufmann, 2002. The multiversion concurrency control chapter (serialization graph testing for MVSG). Applied in Phase 3 (§15) for the SI correctness argument.
  • Gray, J., Reuter, A. Transaction Processing: Concepts and Techniques. Morgan Kaufmann, 1993. Chapters on optimistic and multiversion concurrency control, and on commit protocols. Applied in Phase 2 (§14, commit/abort protocol) and the 2PC boundary (ADR-21).
  • Silberschatz, A., Korth, H., Sudarshan, S. Database System Concepts, 7th ed. The Concurrency Control chapter's multiversion-schemes section. Applied as the pedagogical cross-check for §8's domain model.
  • Hellerstein, J., Stonebraker, M. (eds.) Readings in Database Systems, 5th ed., 2015. Chapter 2 (transactions), the canonical curated paper list. Applied in §5's own paper selection and in Phase 5's SSI framing (§17).
  • Kleppmann, M. Designing Data-Intensive Applications. O'Reilly, 2017. Chapter 7 (transactions); the isolation-levels-visualized diagrams. Applied in Phase 3–4 (§15–§16) as the operator-facing explanation of RC/RR/SI.

Reference Implementations

  • PostgreSQL source tree — src/backend/access/heap/heapam_visibility.c, src/backend/storage/ipc/procarray.c, src/backend/access/heap/pruneheap.c, src/backend/utils/time/snapmgr.c, src/backend/storage/lmgr/predicate.c. Lesson: the HeapTupleSatisfies* family is the visibility contract this blueprint ports. Pitfall: do not copy Postgres's oldest-first chain direction (ADR-06 rejects it) or its CLOG-lookup-per-visibility-check design (ADR-11 rejects it for the eager-tombstone alternative). Applied in §11.5, Phase 1 (§13).
  • CockroachDB — pkg/kv/kvserver, the transaction-layer docs (cockroachlabs.com/docs/stable/architecture/transaction-layer.html). Lesson: HLC + priority-based deadlock-free retry. Pitfall: CockroachDB's uncertainty-interval retries are a distributed-specific mechanism not needed single-node; do not port the retry loop wholesale. Applied in Phase 8 (§20), ADR-07.
  • MySQL InnoDB — storage/innobase/read/read0read.cc (read_view_t), storage/innobase/trx/trx0purge.cc (purge thread). Lesson: InnoDB's undo-log-based in-place MVCC is the closest real analogue to this blueprint's InMemStore alternative backend. Pitfall: InnoDB's purge-lag-driven undo growth is the same horizon-pinning pathology as Postgres bloat — do not assume undo-based storage escapes it. Applied in Phase 6 (§18), Phase 9 (§21).
  • FoundationDB — fdbserver/storageserver.actor.cpp. Lesson: a multi-version key-value store with a hard 5-second MVCC window (deliberately bounded, unlike this blueprint's unbounded-until-GC window). Pitfall: FDB's bounded window trades flexibility for a hard operational ceiling — document why this project rejects a hard window. Applied in §35 (Alternative Architectures).
  • SQL Server Hekaton — documented in Diaconu 2013 (SIGMOD) and MS Docs "In-Memory OLTP Internals"; no public source, spec used instead of code. Lesson: lock-free hash index + optimistic MVCC tuned for main-memory. Pitfall: Hekaton's begin/end timestamp pair differs subtly from this blueprint's xmin/xmax + separate commit-ts scheme — do not conflate them. Applied in §11.3 note, Phase 6 (§18).

RFCs / Specifications

  • ISO/IEC 9075 (SQL) Part 2, transactions clause — the modern successor; applied as the vocabulary source for IsolationLevel (§11.4) naming.

Glossary (§37) · 44 terms · site-wide glossary

ABORTED_XMIN
the sentinel TransactionId value stamped into a version's xmin on abort; makes the version invisible to every snapshot immediately (§11.1).
ADR
Architecture Decision Record; this blueprint's locked decisions, §9.
Chain (version chain)
the linked sequence of physical versions for one logical row, connected via next pointers (§8).
Chain compaction
an opportunistic rewrite of a version chain dropping sub-horizon versions once it exceeds the 1,024-version cap (§18, §22).
cmin / cmax
command-id fields on TupleHeader resolving self-visibility within a multi-statement transaction (the Halloween-problem guard, §13.6).
CommitTs
the commit timestamp type; HLC-encoded or oracle-assigned, distinct from TransactionId (§11.1).
DurableToken
a typestate value only constructible after a WAL fsync completes; the sole path to TransactionState::Committed (§11.9, §19).
First-committer-wins (FCW)
the write-write conflict policy: the transaction that commits first wins; the later committer aborts (§9 ADR-14).
First-updater-wins (FUW)
the rejected alternative: conflict detected at write time, blocking the second writer (§9 ADR-14).
FROZEN
the sentinel TransactionId (u64::MAX) meaning "always visible" (§11.1).
GC horizon (xmin horizon)
the minimum xmin across all active transactions and replication slots; the GC reclamation boundary (§7 I4).
HLC (Hybrid Logical Clock)
a timestamp scheme combining a physical clock with a logical counter, bounding cross-node skew (Kulkarni 2014, §20).
HOT (Heap-Only Tuple)
a Postgres 8.3-derived optimization: an update that doesn't touch an indexed column chains in-page without a new index entry (§18).
Horizon pinner
a transaction whose snapshot's xmin equals the current GC horizon, blocking reclamation of everything newer (§21).
in_progress set
the set of transaction ids active at snapshot-construction time, carried in every Snapshot (§11.3).
Isolation level
RC / SI / SSI in this blueprint's vocabulary (§11.11, §16, §17).
MVCC
Multi-Version Concurrency Control (§1).
MV-TO
Multiversion Timestamp Ordering, the rejected alternative in §35 A3.
Non-repeatable read (P2)
a Berenson 1995 anomaly: a transaction re-reads a row and sees a different value (§15.4).
Oracle (timestamp)
the source of TransactionId/CommitTs allocation; centralized or HLC-based (§11.9).
Phantom (P3)
a Berenson 1995 anomaly: a range re-query returns different rows.
PhaseDeferred
the anchor mechanism marking a feature deferred beyond this blueprint's scope (§36).
Predicate lock (SIREAD)
an SSI tracking lock over a key/page/predicate scope that never blocks a writer (§11.10, §17.2).
Read-Committed (RC)
the isolation level taking a fresh snapshot per statement (§16).
Read skew (A5A)
a Berenson 1995 anomaly involving two related reads observing an inconsistent combination (§15.4).
Repeatable Read (RR)
Postgres's historical name for what this blueprint calls Snapshot Isolation (§16.6).
rw-antidependency
an edge in SSI's conflict graph: T1 read a version that T2 later wrote (§17.2, Cahill 2008).
Sealed
this blueprint's terminal quality gate: 30-day soak + fuzz canaries + external audit closed (§39, Appendix B).
SerializationFailure
the error returned to an aborted committer under first-committer-wins or SSI's dangerous-structure detection (§14.2, §17.2).
Serializable Snapshot Isolation (SSI)
Cahill 2008's algorithm layering serializability on top of SI via predicate locks and dangerous-structure detection (§17).
Snapshot
the (xmin_horizon, xmax_ceiling, in_progress, snapshot_ts) tuple defining a consistent read frontier (§11.3).
Snapshot Isolation (SI)
the default isolation level: one snapshot per transaction, first-committer-wins conflict detection, not serializable (§15).
TrueTime
Spanner's GPS/atomic-clock-backed interval clock; contrasted, not implemented, in this blueprint (§20.3).
TupleHeader
the 32-byte MVCC metadata header on every tuple version (§11.2).
TransactionId (xid)
the monotonic identifier allocated at BEGIN (§11.1).
VersionPtr
an opaque, backend-interpreted pointer to a tuple version (§11.2).
VersionStore
the trait abstracting HeapStore/InMemStore (§11.7).
Vacuum
the GC pass reclaiming dead versions and pruning HOT chains (§18).
Visibility
the pure predicate is_visible(header, snapshot) -> bool (§11.5, §7 I1).
Write skew (A5B)
the anomaly SI permits and SSI prevents: two transactions each read a shared invariant and each write a different row, jointly violating it (§15.6, §17).
Write-write conflict
two transactions attempting to supersede the same version; resolved by first-committer-wins (§9 ADR-14).
xmax
the tuple-header field naming the deleting/superseding transaction (§11.2).
xmin
the tuple-header field naming the inserting transaction (§11.2).
xmin_commit_ts
the commit timestamp of xmin, stamped once that transaction commits (§11.2).
