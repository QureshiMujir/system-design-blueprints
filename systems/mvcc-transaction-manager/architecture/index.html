External integration boundaries (owned elsewhere, contract owned here):
  ─► WAL (#88): commit record fsync BEFORE visibility flip (Phase 7, §19)
  ─► Lock Manager (#101): 2PL fallback for DDL paths (ADR-13)
  ─► Replication (#46): streaming snapshot preserves SI semantics (ADR-20)
  ─► 2PC (#73): prepared txns hold a permanent xmin (ADR-21)

One paragraph per box. API surface: the only public entry point; hides isolation-level dispatch (RC takes a fresh per-statement snapshot, SI/SSI take one at BEGIN). Statement Executor: stateless router; owns no data, only decides which snapshot a given read uses and forwards read/write-sets to SSI when active. Visibility Engine: the single hottest function in the system (M3, §29); consults only (TupleHeader, Snapshot), no shared mutable state — this is what makes readers never block writers (P1). Transaction Manager: owns the one-way state machine (I5, §7) and the write-write conflict check (first-committer-wins, ADR-14). Version Store: the persistence boundary; two implementations behind one trait — this is the concurrency/persistence boundary in the diagram. Timestamp Oracle: the trust boundary for time — a compromised or skewed clock here poisons every downstream snapshot (T3, §23). SSI Tracker: the predicate-lock/tracking boundary; never blocks a writer, only records for later conflict detection (I11). GC/Vacuum: the reclamation boundary and the sole caller of unsafe fn reclaim (§11.7) — every other subsystem treats storage as append-only. All later sections stay consistent with this diagram; module names here are the module names in §10 and §11, verbatim.

8. Domain Model / Protocol / Data Model

Tuple Version Layout

Every logical row is a chain of physical versions. Each version carries a 32-byte header:

Field Type Bytes Meaning
xmin TransactionId 8 inserter's transaction id
xmax TransactionId 8 deleter/superseder's transaction id, or INVALID
cmin u32 4 command id within xmin (self-visibility, Halloween-problem guard)
cmax u32 4 command id within xmax
xmin_commit_ts CommitTs 8 (packed) set once xmin commits; 0 while active
next VersionPtr 8 pointer to the next-older version

Total: 32 bytes header + payload. Postgres pays 24 bytes (32-bit xmin/xmax) plus an external page-slot next-pointer; this blueprint's 64-bit ids cost more per tuple in exchange for a 584,000-year wraparound horizon at 1 µs resolution (§4).

Version Chain Semantics

The chain head is the newest version (ADR-06, Neumann 2015 direction). A reader walks newest→oldest, testing is_visible at each step, and stops at the first visible version — O(1) for a reader on the current committed value. Chain state-transition table:

Event Chain effect
INSERT new version appended at head; xmin = txn.id, xmax = INVALID
UPDATE old head's xmax set to txn.id (CAS from INVALID); new version appended at head
DELETE head's xmax set to txn.id; no new version appended
commit xmin_commit_ts stamped on every version this txn inserted
abort xmin stamped ABORTED_XMIN on every inserted version; xmax cleared (CAS from txn.id → INVALID) on every superseded version
GC reclaim version physically freed once xmax's commit precedes xmin_horizon, or xmin == ABORTED_XMIN

Snapshot Visibility Predicate

A Snapshot is (xmin_horizon, xmax_ceiling, in_progress, snapshot_ts). sees_xid(x): x < xmin_horizon ⇒ true; x ≥ xmax_ceiling ⇒ false; else x ∉ in_progress. A version is visible iff sees_xid(xmin) and (xmax == INVALID or !sees_xid(xmax)).

Worked Example: Three Concurrent Transactions

T1 begins, writes k = v1. T2 begins before T1 commits (T1's xid ∈ T2's in_progress). T1 commits (commit_ts = 100). T3 begins after T1 commits. Result: T2.read(k) → None (T1's xmin still in T2's in_progress at snapshot time); T3.read(k) → Some(v1) (T1's xmin < T3.xmin_horizon). This is the readers_do_not_block_writers fixture (Phase 0, §12.5).

Malformed Input: Truncated Commit Record

A CommitRecord (§11.9) truncated mid-writes vector (e.g. WAL torn by a partial write(2) before crash) fails a length-prefix check in WalSink::append_commit's replay path; recovery (§19.3) treats the transaction as not committed — its writes are tombstoned as if aborted. Fixture: recovery.partial_wal (§19.5 bucket).

Failure-Path Example: Crash Between Commit Steps 4 and 5

If the process crashes after WAL fsync (step 4, §14.2) but before the in-memory state flips to Committed (step 5), the WAL is durable — recovery (§19.3) replays the commit record and reconstructs Committed{commit_ts} from the log. If the crash occurs before step 4, no commit record exists; recovery treats the transaction as Aborted (I6, I5). This is why I6's typestate (DurableToken) is load-bearing: it is structurally impossible to observe the in-between state after restart.

Design principles (§6)

  • MVCC is a contract: readers never block writers, writers never block readers, ever. is_visible is a pure function of (TupleHeader, Snapshot) (§11.5); any code path that adds shared-state consultation to the read path is a bug (I1). Applied: Phase 1 (§13).
  • Snapshot Isolation is the practical default and is NOT serializable. Write-skew (Berenson 1995 A5B) proves it. Applied: Phase 3 (§15), Phase 5 (§17).
  • SSI bridges the gap with bounded false positives, never zero. Cahill 2008's algorithm trades precision for tractability (ADR-18: ≤5% spurious aborts). Applied: Phase 5 (§17).
  • Version chains support O(1) visible-version lookup for hot tuples. Newest-first (Neumann 2015), not Postgres's oldest-first. Applied: Phase 1 (§13.1), ADR-06.
  • The timestamp source is load-bearing — choose deliberately. Centralized oracle (simplest, single point of contention) vs HLC (decentralized, bounded skew) vs TrueTime (external consistency, GPS/atomic-clock infrastructure, out of scope). Applied: Phase 8 (§20).
  • Garbage collection is mandatory or storage grows unbounded. The xmin horizon (I4) is computed continuously; a long-running transaction pinning it is a first-class, surfaced condition, not a silent failure. Applied: Phase 6 (§18), Phase 9 (§21).
  • Deletes are tombstones, not in-place removal. xmax = current_txn; the version remains physically present until GC. Applied: Phase 1 (§13), ADR-11.
  • Aborts must be visible to GC immediately. xmin = ABORTED_XMIN; no special-cased path. Applied: Phase 2 (§14.3), Phase 6 (§18.2).
  • Long-running readers are the bane of MVCC. Surfaced in metrics (M-series), subject to administrator-driven cancellation. Applied: Phase 9 (§21).
  • Append-only vs in-place storage is an irrevocable architectural choice per backend. HeapStore (append-only) and InMemStore (in-place-with-undo) are different code paths behind one VersionStore trait (§11.7); they do not share GC strategy. Applied: Phase 1 (§13), Phase 6 (§18), ADR-04/ADR-05.
  • Integration with replication must preserve snapshot semantics. Replication-slot xmins participate in the GC horizon (I13). Applied: §20.2's integration boundary, ADR-20.
  • Commit timestamp assignment is the heart of the protocol. commit_ts > xmin always; commit_ts persists before visibility flips (I6, the WAL durability requirement). Applied: Phase 2 (§14.2), Phase 7 (§19).
  • The transaction state machine is one-way. Active → Committing → Committed | Aborted; no reverse transition (I5). A bug that lets Committed become Aborted is Sev-0 (T-class incident, FM1). Applied: Phase 2 (§14).
  • Read-set tracking is opt-in per isolation level. RC needs none; RR/SI need the snapshot; SSI needs the full read-set as predicate locks — cost paid only when the level requires it. Applied: Phase 4 (§16), Phase 5 (§17).
  • Conformance is the contract. Berenson 1995, Adya 1999, Jepsen/Elle, and the TLA+ correspondence gate every phase's exit criteria; a regression is a merge block. Applied: §27 (Testing & Verification Strategy).
