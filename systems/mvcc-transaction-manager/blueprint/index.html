1. Goal & Scope

Build a production-grade Multi-Version Concurrency Control (MVCC) transaction manager in Rust: append-only tuple version chains with xmin/xmax/cmin/cmax visibility metadata (Postgres-style), a one-way transaction state machine (Active → Committing → Committed | Aborted), snapshot construction over an active-transaction registry, Snapshot Isolation (SI) as the default isolation level with first-committer-wins write-write conflict detection, Serializable Snapshot Isolation (SSI, Cahill 2008 / Ports-Grittner 2012) layered on top, a pluggable timestamp source (Hybrid Logical Clock default per Kulkarni 2014, centralized-oracle fallback), xmin-horizon-driven garbage collection with HOT chain pruning (Postgres 8.3 model), and integration seams with the WAL (#88), Lock Manager (#101), Replication (#46), and 2PC (#73) blueprints. The system is a library + CLI, not a full DBMS: no query planner, no B+-tree index, no SQL parser, no network protocol.

In-scope Phase-0 deliverable (modules, §10/§11 name these identically):

  1. mvcc-core — tuple layout, version chain, visibility predicate, snapshot type (no_std
    • alloc-optional).
  2. mvcc-txn — transaction id/commit-ts types, state machine, commit/abort protocol, active-transaction registry.
  3. mvcc-timestamp — TimestampOracle trait, CentralizedOracle.
  4. mvcc-storage — HeapStore (append-only page heap) implementing VersionStore.
  5. mvcc-cli — mvccctl: begin / read / write / commit / abort over the in-process engine.

System boundaries. Provides: version storage, visibility evaluation, transaction lifecycle, snapshot construction, SI and SSI isolation, GC/vacuum, HLC/oracle timestamping. Delegates: durable logging and crash-log format to WAL (#88); non-MVCC DDL locking to the Lock Manager (#101); cross-node log shipping to Replication (#46); distributed atomic commit to 2PC (#73). Does NOT provide: a query executor, an index structure beyond the primary key path, network transport, authentication, or a SQL dialect.

Non-goals: distributed two-phase commit implementation — PhaseDeferred("§36") (owned by #73, only the integration hook is specified here); multi-master conflict resolution (#46); formal machine-checked proof of the SSI safety theorem beyond TLA+ model checking — PhaseDeferred("§36"); a cost-based query optimizer / SQL parser — PhaseDeferred("§36").

Deployment model: embedded library linked into a host storage engine or standalone via mvccctl for conformance/demo use; single-node by default, HLC timestamping makes the transaction-manager crate safe to embed in a multi-node deployment once paired with #46. Target users/operators: database engine authors, on-call SREs running the resulting OLTP store, and engineers implementing MVCC for the first time. Later phases unlock: SSI (Phase 5, §17), a Hekaton-style in-memory backend (Phase 6, §18, via the same VersionStore trait), distributed timestamping (Phase 8, §20), and long-running-reader bloat mitigation (Phase 9, §21).

Recommended language: Rust 1.78+, edition 2021. Rationale: a TransactionId/CommitTs type confusion or a chain-head data race is a correctness bug with silent data loss; Rust's ownership model and Send/Sync bounds turn the version-chain CAS race and the xmin/xmax type confusion into compile-time errors. Rejected: C (Postgres's own language — rejected because the CVE history of heapam.c-adjacent code shows the exact memory-safety bugs Rust's borrow checker eliminates); C++ (rejected — no borrow checker, and RAII does not prevent the chain-CAS ABA problem without discipline this project cannot enforce by tooling); Go (rejected — GC pauses interact badly with the xmin-horizon computation's latency budget, and no unsafe-free lock-free CAS primitive exists in the standard library); Zig (rejected — no mature Loom-equivalent concurrency model checker exists in its ecosystem yet, and this project's correctness case rests on Loom + Miri).

Prerequisites: two-phase locking vs timestamp ordering vs optimistic concurrency control (Bernstein-Hadzilacos-Goodman 1987 ch. 5, 8); WAL/ARIES recovery (Mohan 1992) and how it interacts with visibility; conflict-serializability vs view-serializability. Familiarity with heap_tuple_satisfies_mvcc or InnoDB's read-view code helps but is not required — both are derived from first principles in §8.

Estimated timeline: Phase 0–2 (repo skeleton, version chain, visibility, transaction state machine) — 6 weeks. Full plan (Phases 0–10) — 24 weeks (~5.5 months). Every deferred feature named above resolves to a row in the Deferred Features Register (§36).

2. Why Build This

  • MVCC is the dominant OLTP concurrency scheme: PostgreSQL (6.5+, 1999), MySQL InnoDB, Oracle, SQL Server (RCSI + Hekaton), CockroachDB, Spanner, TiDB, YugabyteDB, FoundationDB, HyPer, Umbra, DuckDB, SingleStore, Snowflake all implement a flavor of it.
  • Delivers the cardinal OLTP property: readers never block writers, writers never block readers — strict 2PL cannot give you this without serializing analytical scans behind the write path.
  • Closes the "missing half" of the standard database course: B+-trees, hash joins, query optimization, and ARIES recovery are taught; MVCC gets a paragraph. Engineers who cannot name write-skew, who believe "snapshot isolation" implies serializable, who cannot explain why one idle connection blocks VACUUM cluster-wide, are common — and expensive in production.
  • Berenson 1995 (SIGMOD) catalogued the ANSI anomalies; Adya 1999 (MIT thesis) formalized the isolation levels via the Direct Serialization Graph. Both are required reading and rarely read; this project forces internalization of both.
  • Architecturally teaches: version-chain design (append-only vs in-place-with-undo, §6 P10), visibility as a pure function (§6 P1), timestamp-source tradeoffs — centralized oracle vs HLC (Kulkarni 2014) vs TrueTime (Spanner, Corbett 2012) — and xmin-horizon-driven garbage collection, the load-bearing operational fact behind every Postgres bloat incident.
  • Cross-links: sibling to the Lock Manager (#101, pessimistic concurrency contrast), WAL (#88, the durability-before-visibility boundary), Replication (#46, streaming-snapshot consistency), 2PC (#73, prepared-transaction xmin pinning).
  • Calibration value: after this project, a "SERIALIZABLE" claim in any vendor's docs is something you can personally verify against the Berenson/Adya vectors rather than take on faith.

What Mastery Looks Like (owner: after finishing this blueprint, the reader can):

  • Explain, from the tuple header outward, why a reader in this design never blocks a writer — tied to Phase 1 (§13) and Design Principle P1 (§6).
  • Diagnose a "VACUUM cannot advance" incident from first principles — tied to Phase 9 (§21) and the xmin-horizon invariant I4 (§7).
  • Distinguish Snapshot Isolation from serializability with a concrete write-skew example and know exactly which SSI machinery (SIREAD locks, rw-antidependency graph) closes the gap — tied to Phase 3 (§15) and Phase 5 (§17).
  • Choose a timestamp source for a new distributed OLTP engine and defend the choice against HLC, a centralized oracle, and TrueTime by name — tied to Phase 8 (§20) and ADR-07.
  • Read Postgres's heapam_visibility.c or InnoDB's read_view_t and map every field to this blueprint's TupleHeader/Snapshot types — tied to §11 and Required Reading (§5).
  • Debug a version-chain corruption or a GC/reader race using the invariant table (§7) and the Loom/TLA+ conformance harness (§27) rather than ad hoc reasoning.

One paragraph per box. API surface: the only public entry point; hides isolation-level dispatch (RC takes a fresh per-statement snapshot, SI/SSI take one at BEGIN). Statement Executor: stateless router; owns no data, only decides which snapshot a given read uses and forwards read/write-sets to SSI when active. Visibility Engine: the single hottest function in the system (M3, §29); consults only (TupleHeader, Snapshot), no shared mutable state — this is what makes readers never block writers (P1). Transaction Manager: owns the one-way state machine (I5, §7) and the write-write conflict check (first-committer-wins, ADR-14). Version Store: the persistence boundary; two implementations behind one trait — this is the concurrency/persistence boundary in the diagram. Timestamp Oracle: the trust boundary for time — a compromised or skewed clock here poisons every downstream snapshot (T3, §23). SSI Tracker: the predicate-lock/tracking boundary; never blocks a writer, only records for later conflict detection (I11). GC/Vacuum: the reclamation boundary and the sole caller of unsafe fn reclaim (§11.7) — every other subsystem treats storage as append-only. All later sections stay consistent with this diagram; module names here are the module names in §10 and §11, verbatim.

6. Design Principles

  1. MVCC is a contract: readers never block writers, writers never block readers, ever. is_visible is a pure function of (TupleHeader, Snapshot) (§11.5); any code path that adds shared-state consultation to the read path is a bug (I1). Applied: Phase 1 (§13).
  2. Snapshot Isolation is the practical default and is NOT serializable. Write-skew (Berenson 1995 A5B) proves it. Applied: Phase 3 (§15), Phase 5 (§17).
  3. SSI bridges the gap with bounded false positives, never zero. Cahill 2008's algorithm trades precision for tractability (ADR-18: ≤5% spurious aborts). Applied: Phase 5 (§17).
  4. Version chains support O(1) visible-version lookup for hot tuples. Newest-first (Neumann 2015), not Postgres's oldest-first. Applied: Phase 1 (§13.1), ADR-06.
  5. The timestamp source is load-bearing — choose deliberately. Centralized oracle (simplest, single point of contention) vs HLC (decentralized, bounded skew) vs TrueTime (external consistency, GPS/atomic-clock infrastructure, out of scope). Applied: Phase 8 (§20).
  6. Garbage collection is mandatory or storage grows unbounded. The xmin horizon (I4) is computed continuously; a long-running transaction pinning it is a first-class, surfaced condition, not a silent failure. Applied: Phase 6 (§18), Phase 9 (§21).
  7. Deletes are tombstones, not in-place removal. xmax = current_txn; the version remains physically present until GC. Applied: Phase 1 (§13), ADR-11.
  8. Aborts must be visible to GC immediately. xmin = ABORTED_XMIN; no special-cased path. Applied: Phase 2 (§14.3), Phase 6 (§18.2).
  9. Long-running readers are the bane of MVCC. Surfaced in metrics (M-series), subject to administrator-driven cancellation. Applied: Phase 9 (§21).
  10. Append-only vs in-place storage is an irrevocable architectural choice per backend. HeapStore (append-only) and InMemStore (in-place-with-undo) are different code paths behind one VersionStore trait (§11.7); they do not share GC strategy. Applied: Phase 1 (§13), Phase 6 (§18), ADR-04/ADR-05.
  11. Integration with replication must preserve snapshot semantics. Replication-slot xmins participate in the GC horizon (I13). Applied: §20.2's integration boundary, ADR-20.
  12. Commit timestamp assignment is the heart of the protocol. commit_ts > xmin always; commit_ts persists before visibility flips (I6, the WAL durability requirement). Applied: Phase 2 (§14.2), Phase 7 (§19).
  13. The transaction state machine is one-way. Active → Committing → Committed | Aborted; no reverse transition (I5). A bug that lets Committed become Aborted is Sev-0 (T-class incident, FM1). Applied: Phase 2 (§14).
  14. Read-set tracking is opt-in per isolation level. RC needs none; RR/SI need the snapshot; SSI needs the full read-set as predicate locks — cost paid only when the level requires it. Applied: Phase 4 (§16), Phase 5 (§17).
  15. Conformance is the contract. Berenson 1995, Adya 1999, Jepsen/Elle, and the TLA+ correspondence gate every phase's exit criteria; a regression is a merge block. Applied: §27 (Testing & Verification Strategy).

8. Domain Model / Protocol / Data Model

Tuple Version Layout

Every logical row is a chain of physical versions. Each version carries a 32-byte header:

Field Type Bytes Meaning
xmin TransactionId 8 inserter's transaction id
xmax TransactionId 8 deleter/superseder's transaction id, or INVALID
cmin u32 4 command id within xmin (self-visibility, Halloween-problem guard)
cmax u32 4 command id within xmax
xmin_commit_ts CommitTs 8 (packed) set once xmin commits; 0 while active
next VersionPtr 8 pointer to the next-older version

Total: 32 bytes header + payload. Postgres pays 24 bytes (32-bit xmin/xmax) plus an external page-slot next-pointer; this blueprint's 64-bit ids cost more per tuple in exchange for a 584,000-year wraparound horizon at 1 µs resolution (§4).

Version Chain Semantics

The chain head is the newest version (ADR-06, Neumann 2015 direction). A reader walks newest→oldest, testing is_visible at each step, and stops at the first visible version — O(1) for a reader on the current committed value. Chain state-transition table:

Event Chain effect
INSERT new version appended at head; xmin = txn.id, xmax = INVALID
UPDATE old head's xmax set to txn.id (CAS from INVALID); new version appended at head
DELETE head's xmax set to txn.id; no new version appended
commit xmin_commit_ts stamped on every version this txn inserted
abort xmin stamped ABORTED_XMIN on every inserted version; xmax cleared (CAS from txn.id → INVALID) on every superseded version
GC reclaim version physically freed once xmax's commit precedes xmin_horizon, or xmin == ABORTED_XMIN

Snapshot Visibility Predicate

A Snapshot is (xmin_horizon, xmax_ceiling, in_progress, snapshot_ts). sees_xid(x): x < xmin_horizon ⇒ true; x ≥ xmax_ceiling ⇒ false; else x ∉ in_progress. A version is visible iff sees_xid(xmin) and (xmax == INVALID or !sees_xid(xmax)).

Worked Example: Three Concurrent Transactions

T1 begins, writes k = v1. T2 begins before T1 commits (T1's xid ∈ T2's in_progress). T1 commits (commit_ts = 100). T3 begins after T1 commits. Result: T2.read(k) → None (T1's xmin still in T2's in_progress at snapshot time); T3.read(k) → Some(v1) (T1's xmin < T3.xmin_horizon). This is the readers_do_not_block_writers fixture (Phase 0, §12.5).

Malformed Input: Truncated Commit Record

A CommitRecord (§11.9) truncated mid-writes vector (e.g. WAL torn by a partial write(2) before crash) fails a length-prefix check in WalSink::append_commit's replay path; recovery (§19.3) treats the transaction as not committed — its writes are tombstoned as if aborted. Fixture: recovery.partial_wal (§19.5 bucket).

Failure-Path Example: Crash Between Commit Steps 4 and 5

If the process crashes after WAL fsync (step 4, §14.2) but before the in-memory state flips to Committed (step 5), the WAL is durable — recovery (§19.3) replays the commit record and reconstructs Committed{commit_ts} from the log. If the crash occurs before step 4, no commit record exists; recovery treats the transaction as Aborted (I6, I5). This is why I6's typestate (DurableToken) is load-bearing: it is structurally impossible to observe the in-between state after restart.

14. Phase 2 — Transaction State Machine & Commit/Abort Protocol (Weeks 4–6)

14.1 Objectives

Implement the one-way transaction state machine and the commit/abort protocols. Realizes P8, P12, P13; applies ADR-14, ADR-19 (partially — full WAL binding is Phase 7, §19); I2, I5, I6 (stubbed pending Phase 7's DurableToken), I9.

14.2 Detailed Implementation Steps

State-transition table (mvcc-txn::state):

From Event To Guard
— BEGIN Active allocate xid (I14 wraparound guard)
Active commit() Committing write-write check passes (ADR-14, step below)
Committing WAL fsync ok Committed{commit_ts} DurableToken obtained (I6, stub until §19)
Committing WAL fsync fail Aborted —
Active abort() Aborted —

Commit protocol (mvcc-txn::commit), steps in order: (1) write-write conflict check — for each WriteEntry, if the superseded version's xmax is committed and ≠ this txn, return SerializationFailure (ADR-14, first-committer-wins, I2, I9's CAS backing); (2) state = Committing; (3) commit_ts = oracle.assign_commit_ts() (I3); (4) append commit record, block on durability (stub in this phase, real in §19); (5) state = Committed{commit_ts}; (6) stamp xmin_commit_ts on every inserted version; (7) registry.retire.   • The abort tombstone step must be idempotent — a concurrent GC pass may have already reclaimed the version (null VersionPtr); the stamp becomes a no-op.

15. Phase 3 — Snapshot Isolation (Weeks 6–8)

15.1 Objectives

Implement snapshot construction and make Snapshot Isolation the functionally correct default isolation level. Realizes P2; applies ADR-09, ADR-14 (the full commit-time check against the true registry); I3, I4.

15.2 Detailed Implementation Steps

Registry::take_snapshot (§11.8): acquire a brief read-lock, copy the in_progress set, read next_xid as xmax_ceiling, compute xmin_horizon = min(in_progress) or xmax_ceiling, stamp snapshot_ts = oracle.now_for_snapshot() (§11.3). Lock held for O(|active txns|), typically microseconds — Phase 10 (§22.1) replaces this with an epoch-protected lock-free projection. First-committer-wins conflict window: a transaction in Committing is not yet a conflict for a concurrent committer; only a Committed superseder trips SerializationFailure (ADR-14; P2's "SI is not serializable" gap is exactly write-skew, deliberately left open here, closed by SSI in §17).

17. Phase 5 — Serializable Snapshot Isolation (SSI) (Weeks 9–12)

17.1 Objectives

Close the write-skew gap left open by SI (§15.6) using Cahill 2008's dangerous-structure detection. Realizes P3, P14; applies ADR-17, ADR-18; I11.

17.2 Detailed Implementation Steps

Every visible-tuple read under SSI installs a SiReadLock (§11.10) — a tracking lock, never a blocking one (I11, preserving P1). Every write checks existing SiReadLocks on the same key from other transactions and records an RwAntidep edge into the RwAntidepGraph. At commit, check_dangerous_at_commit (signature in §11, logic per Cahill 2008, Section 3): for the committing transaction, if it has an incoming rw-antidependency from T1 and an outgoing one to T2, and T2 has committed before (or T1 has not yet committed relative to) the committer, abort the committer — this is the "dangerous structure" (a T1→committer→T2 rw-antidependency chain). Lock promotion (ADR-17): when the per-key SiReadLock count exceeds a configurable threshold, promote Key scope to Page scope (Ports-Grittner 2012, Section 4).

17.3 Deliverable

The Berenson 1995 A5B write-skew anomaly is prevented under SSI (one of the two conflicting transactions aborts with SerializationFailure); Adya 1999's G2 phenomenon is prevented.

17.4 Acceptance Criteria

  • examples/write_skew_demo.rs run under SSI: one of the two doctor transactions aborts; the on-call invariant holds in 100% of 1,000 repeated trials.
  • Adya 1999 G2 (anti-dependency cycle) prevented: conformance/corpora/adya1999/g2.json, 0 undetected cycles across 10,000 generated cycle-shaped workloads.
  • SSI false-positive rate ≤ 5% on the TPC-C variant (ADR-18, M-target cross-referenced in §29) — measured, not asserted.
  • SSI throughput ≥ 60% of SI throughput on the same workload (M2, §29).

17.6 Pitfalls

  • SIREAD lock storage grows linearly with read volume — a 1M-read/sec workload sustains millions of locks; page-level promotion (§17.2) is the safety valve, not optional.
  • The rw-antidependency graph must drop an aborted transaction's edges, or leaked edges produce false negatives (missed anomaly) or false positives (spurious aborts).
  • The "T2 commits before T1" check is sensitive to clock skew under HLC (§20) — the HLC-aware comparator uses HLC timestamps, never physical wall-clock reads directly.
  • The dangerous-structure check is O(in-degree × out-degree) for the committer — a large read+write set dominates commit cost; Phase 10 (§22) mitigates via incremental maintenance, not by skipping the check.

17.7 Performance Concerns

SIREAD insertion amortized ≤ 100 ns (M9, §29); a fast lock table shards by (table, page) (ADR-26) — a single global mutex-protected structure fails the M2 throughput target.

17.8 Edge Cases

Three-way (or longer) dangerous structures; a transaction that both reads and writes the same key under SSI (self-antidependency, must be excluded from the graph); lock-promotion mid-transaction (a key-level lock already held, promoted to page-level while another reader holds a different key-level lock on the same page).

17.9 Failure Analysis

An undetected dangerous structure is a silent serializability violation — the worst class of bug in this system (comparable to FM3, §24). Detection: the Adya G2 conformance bucket and Jepsen/Elle (§27) are the safety net; containment is impossible after the fact (the data is already wrong) — this is why the conformance gate blocks merge, not a runtime mitigation.

18. Phase 6 — Garbage Collection / Vacuum / HOT (Weeks 12–15)

18.1 Objectives

Implement xmin-horizon computation, dead-version reclamation, and HOT chain pruning; land the InMemStore alternate backend. Realizes P6, P7, P10; applies ADR-05, ADR-10, ADR-16; I4, I8, I10.

18.2 Detailed Implementation Steps

compute_xmin_horizon (signature §11.8, logic per I4): scan active transactions' snapshot xmins plus replication-slot xmins (ADR-20, stubbed until #46 integration), take the minimum. vacuum_page (§11.7's reclaim, precondition I10): a version is reclaimable iff xmax is committed and xmax < xmin_horizon (equivalently, no live snapshot's snapshot_ts could still see it), or xmin == ABORTED_XMIN. hot_prune_chain: rotates a HOT chain (Postgres 8.3 model, Required Reading §5) so the index continues to target the first live version after dead prefix versions are marked. InMemStore (ADR-05, Larson 2011 Hekaton): lock-free hash index into an in-place-with-undo version store — a structurally different VersionStore impl from HeapStore, sharing only the trait surface (P10).

18.3 Deliverable

A 1M-row insert+update workload holds storage proportional to live rows, not historical rows; HOT prune collapses a 1,000-update chain back to depth 1 within one GC pass.

18.4 Acceptance Criteria

  • GC throughput ≥ 1,000,000 dead versions/sec/core (M6, §29), measured on bench/gc_throughput.rs.
  • Storage overhead vs single-version after vacuum ≤ 30% (M11, §29).
  • HOT prune reduces a 1,000-version chain to depth 1 in a single pass, verified on examples/hot_chain_demo.rs.
  • InMemStore passes the full visibility_matrix.rs suite (§13.5) unchanged (trait-level parity with HeapStore).

18.6 Pitfalls

  • The horizon must include replication-slot xmins (ADR-20, I13) or a standby falls behind the primary's GC and breaks streaming consistency (the #46 integration boundary).
  • reclaim is unsafe — the caller must prove xmax < xmin_horizon (I10) before calling; the GC subsystem is the only caller (§11.7).
  • HOT prune races with concurrent readers — Loom (loom.gc_reader_race) enumerates: reader on slot A while HOT-prune rotates A→B; the reader must see either the pre-prune A or the post-prune B atomically, never a half-rotated state.
  • Vacuum must not reclaim a version whose xmax-owning transaction is still Committing (writes not yet durable) — the horizon check implicitly covers this (I4 excludes in-flight committers), but an explicit assertion documents the invariant.

18.7 Performance Concerns

Horizon recomputation is O(|active txns|) per GC tick, run continuously and cheaply; vacuum's page rewrite is the dominant per-tick cost, batched and rate-limited to avoid competing with the OLTP write path for page-cache bandwidth.

18.8 Edge Cases

An empty registry (horizon = next_xid, everything reclaimable); a page with 100% dead tuples (full-page reclaim, no live version to preserve); a replication slot reporting a stale (very old) xmin due to a disconnected standby.

18.9 Failure Analysis

Premature reclamation (I10 violated) is a Sev-0: a live reader sees a torn/missing tuple. Detection: Loom model + the gc_reader_race conformance bucket. Containment: the unsafe boundary at reclaim is the only call site, code-reviewed on every change. Recovery: none possible after the fact for the affected reader — this is a correctness bug, not an operational incident, and blocks release (FM9, §24).

18.10 Operational Notes

Metrics: mvcc_gc_horizon_xid, mvcc_gc_reclaimed_total, mvcc_gc_slot_xmin_lag (I13). Runbook docs/runbook/bloat-incident.md is the long-form operational treatment of what this phase's metrics are for.

19. Phase 7 — WAL Integration Boundary (Weeks 15–16)

19.1 Objectives

Bind the commit protocol's durability step to a real WAL contract (blueprint #88); implement crash recovery. Realizes P12; applies ADR-19, ADR-24; I6.

19.2 Detailed Implementation Steps

CommitRecord/WriteEntryRecord (§11.9, ADR-24 fixed binary layout) are the on-disk unit. WalSink::append_commit returns a CommitHandle; CommitHandle::wait_durable(self) -> DurableToken blocks until group-fsync completes (default: 1 ms interval / 64 commits, tunable). DurableToken is the only constructor path to TransactionState::Committed (I6's typestate — the durability-before-visibility rule, Mohan 1992). Crash recovery sequence (§8's failure-path example, generalized): (1) read WAL forward from last checkpoint LSN; (2) for each commit record found, mark that xid Committed, replay its writes; (3) for each xid Active/Committing at crash time with no commit record, mark it Aborted, stamp ABORTED_XMIN; (4) recompute next_xid = max(seen xid) + 1; (5) recompute xmin_horizon from the last checkpoint's recorded in-flight set.

19.3 Deliverable

kill -9 the process at random intervals; on restart the database is consistent, no committed transaction is lost, no aborted transaction resurrects.

19.4 Acceptance Criteria

  • recovery.crash_replay: 1,000 random kill -9 cycles with random WAL truncation — every replay produces a consistent state (0 lost commits, 0 resurrected aborts).
  • Group commit sustains ≥ 100,000 commits/sec on a single core at fsync_interval = 1 ms (part of M4's basis, §29).
  • WAL replay rate ≥ 500 MB/sec (M10, §29), gating the RTO budget (§4).
  • Constructing Committed{..} without a DurableToken is a compile error (structural proof, not a test).

19.5 Conformance Fixtures

Fixture Purpose Expected Output
recovery.crash_replay (1,000 cycles) random kill -9 + WAL truncation consistent post-recovery state, every cycle
recovery.partial_wal WAL truncated mid-CommitRecord transaction treated as not-committed (§8)
conformance/corpora/group_commit_throughput.json sustained commit load ≥ 100K commits/sec

19.6 Pitfalls

  • Linux's durability barrier is fdatasync, not fsync, once the WAL file's size/inode is fixed at creation — using fsync per record is ~3× slower for no correctness benefit.
  • Group-commit batches must not coalesce across a WAL file rollover — the second half's fsync is independent of the first file's.
  • A "no commit record found" recovery verdict is final — the engine must never later discover a commit record and resurrect a transaction already marked Aborted; the WAL is the sole source of truth (I6).
  • Replication slots (ADR-20) hold the WAL from truncating past the slot's LSN — a permanently disconnected replica grows the WAL unboundedly (cross-referenced in FM7, §24).

19.7 Performance Concerns

Group commit's latency floor is max(fsync_interval, group_size_threshold_time); too small an interval starves throughput, too large inflates p99 commit latency (M4) — the default (1 ms / 64) is a measured, not asserted, balance point.

19.8 Edge Cases

A crash during the group-fsync itself (partial durability within the batch — the WAL's length-prefix framing, ADR-24, makes a torn record detectable and rejected); a checkpoint record itself truncated (falls back to the prior checkpoint, longer replay, still correct).

19.9 Failure Analysis

A reordering of steps 4/5 (commit flip before fsync, I6 violated) makes a torn read visible before it is durable — a Sev-0 silently-lost-update class bug (FM1, §24). The typestate proof makes this class of bug unrepresentable rather than merely tested-against.

19.10 Operational Notes

Metrics: mvcc_wal_fsync_latency_ns, mvcc_wal_group_commit_batch_size, mvcc_recovery_replay_bytes_per_sec. Deployment: WAL segment rollover and checkpoint cadence are #88's responsibility; this phase only emits the checkpoint's (next_xid, xmin_horizon, active_xids) payload (§19.2 step 5's inputs).

20. Phase 8 — Distributed Timestamps: HLC (Weeks 16–18)

20.1 Objectives

Replace the Phase-0 CentralizedOracle with the Hybrid Logical Clock as the production default; document the TrueTime contrast. Realizes P5; applies ADR-07, ADR-08; I3, I12.

20.2 Detailed Implementation Steps

HybridLogicalClock (§11.9, Kulkarni 2014): a single AtomicU64 packing 48-bit physical microseconds (high) + 16-bit logical counter (low). now(): CAS-loop — if the wall clock has advanced past the stored physical component, reset the logical counter to 0; else increment it, asserting it stays below 2¹⁶ (I14-adjacent overflow guard). update_from_remote (remote: CommitTs): CAS-loop folding in a peer's timestamp, guaranteeing every subsequent local now() exceeds remote (I12, Kulkarni 2014 Theorem 1). make_oracle(config) (§11.9-adjacent factory) selects CentralizedOracle or HybridLogicalClock per OracleKind — both satisfy TimestampOracle (ADR-07 default: HLC). TrueTime contrast (Spanner, Corbett 2012): TT.now() returns an interval [earliest, latest], backed by GPS + atomic clocks per datacenter; a commit chooses TT.now().latest and blocks ("commit wait", typically 1–7 ms) until TT.now().earliest exceeds it, yielding external consistency. This blueprint does not implement TrueTime — the GPS/atomic-clock infrastructure requirement is out of scope (§1 non-goals); docs/architecture/ hlc-vs-oracle-vs-truetime.md is the long-form comparison, referenced again in §32 (Comparative Architecture Table).

20.3 Deliverable

HLC passes the Kulkarni 2014 Section 4 ordering-invariant suite; a synthetic ±100 ms clock-skew injection between two simulated nodes preserves snapshot consistency.

20.4 Acceptance Criteria

  • HLC ordering invariant suite: 100% pass on conformance/corpora/hlc_ordering.json.
  • examples/hlc_skew_demo.rs: ±100 ms injected skew, 0 snapshot-consistency violations.
  • Berenson 1995 anomaly suite (§15.4) re-passes unchanged against the HLC backend (parity with the centralized-oracle backend).
  • HLC logical-counter overflow assertion fires deterministically on a frozen-clock fixture (not a production expectation — a correctness-boundary test).

20.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/hlc_ordering.json Kulkarni 2014 Section 4 invariants 100% pass
examples/hlc_skew_demo.rs ±100 ms cross-node skew snapshot consistency preserved
tests/hlc_overflow_frozen_clock.rs 65,536 consecutive now() calls, frozen clock overflow assertion fires

20.6 Pitfalls

  • The 16-bit logical counter overflows if the physical clock fails to advance for 65,536 consecutive now() calls — the panic is the defense; monitoring the counter's range is the operational complement.
  • update_from_remote must be called on every cross-node interaction (replication tick, RPC reply); a missed call is a correctness bug the skew demo is designed to catch.
  • Lamport's clock (1978) gives a total order but discards physical proximity; HLC keeps both — conflating the two in documentation or code comments is a recurring error (MM3, §31).

20.7 Performance Concerns

now()/update_from_remote are single-CAS operations on one AtomicU64 — contention under very high allocation rates is the only concern; sharding the clock across cores is a candidate future enhancement (Deferred Features Register, §36), pending real contention evidence.

20.8 Edge Cases

Two nodes with wall clocks skewed by exactly the max_skew boundary; a node whose clock runs backward (NTP step correction) — now()'s physical_now > prev_phys check falls back to the logical-counter-increment branch, never regressing.

20.9 Failure Analysis

A far-future timestamp from a compromised or misconfigured peer poisons the cluster's clock via update_from_remote — mitigated by rejecting updates where remote.physical_us() > local_physical_now + max_skew (T3, §23). Detection: the bounded-skew check itself; telemetry: mvcc_hlc_skew_rejected_total.

20.10 Operational Notes

Metrics: mvcc_hlc_logical_counter (I12), mvcc_hlc_skew_rejected_total, mvcc_timestamp_oracle_kind (label: centralized/hlc). docs/architecture/ hlc-vs-oracle-vs-truetime.md is the operator-facing reference when choosing an oracle at deployment time; switching oracle kind post-deployment requires a full restart (no live migration between CentralizedOracle and HybridLogicalClock).

21. Phase 9 — Long-Running Readers & Bloat Mitigation (Weeks 18–20)

21.1 Objectives

Turn the xmin-horizon-pinning pathology (P9) from a silent operational failure into a surfaced, actionable one. Applies P9; extends I4.

21.2 Detailed Implementation Steps

detect_horizon_pinners (signature per §18's horizon module, logic extension of I4): for every active transaction whose snapshot.xmin_horizon equals the current cluster-wide horizon, compute its age; emit warn at gc_warn_us (default 60 s), error-level alert at gc_alert_us (default 5 min). pre_empt_pinners: at gc_pre_empt_us (default 30 min), signal the transaction's cancellation token; the transaction observes cancellation at its next operation and self-aborts (P9, ADR-14-adjacent — pre-emption is a cancel, not a forced external abort of in-flight state).

21.3 Deliverable

A synthetic horizon-pinner workload triggers warn/alert/pre-empt at the configured ages; a 1-hour write-heavy workload with one 30-minute pinner shows bounded storage growth (pinner pre-empted at 30 min, horizon advances, bloat reclaimed within one GC tick).

21.4 Acceptance Criteria

  • Warn fires at 60 s ± 1 s, alert at 5 min ± 5 s, pre-empt at 30 min ± 10 s on the synthetic fixture (100 trials, 0 misses).
  • The 1-hour bloat fixture (§18.4's gc_bloat_bound extended) shows storage returning to within 5% of the no-pinner baseline within one GC tick after pre-emption.
  • 2PC-prepared and replication-slot pinners are correctly excluded from pre-emption (they are not cancelable — routed to the operator instead, per ADR-21/ADR-20).

21.5 Conformance Fixtures

Fixture Purpose Expected Output
conformance/corpora/horizon_pinner_thresholds.json synthetic pinner at each threshold age warn/alert/pre-empt fire on schedule
conformance/corpora/gc_bloat_bound_pinner.json 1-hr write-heavy + 30-min pinner bounded growth, reclaimed post-pre-empt
tests/pinner_2pc_excluded.rs prepared-txn pinner not pre-empted, routed to operator alert

21.6 Pitfalls

  • Pre-emption is dangerous for a legitimate long analytical scan — default thresholds are aggressive; production deployments must tune per-session (documented, not hardcoded).
  • A pinner held by a 2PC-prepared transaction (#73) is not pre-emptable — only the coordinator's resolution path can release it.
  • Replication-slot xmins are not pre-emptable either — the operator must drop the slot; the metric distinguishes pinner source (active txn vs slot) so the runbook routes correctly.

21.7 Performance Concerns

Horizon-pinner detection is folded into the existing O(|active txns|) GC tick (§18.7) — no additional scan pass; the cost is amortized into work already being done.

21.8 Edge Cases

Multiple simultaneous pinners at different ages (only the oldest defines the horizon, but all past their own threshold age are individually warned/alerted); a pinner that self-commits between the alert and pre-empt checks (race handled by re-checking horizon membership at pre-empt time, not caching the earlier check).

21.9 Failure Analysis

Failure to detect a pinner (bug in the age computation) reproduces the classic Postgres bloat incident silently — detection is purely the metric/alert pipeline (no other safety net), which is why this phase's fixtures are acceptance-gating, not advisory.

21.10 Operational Notes

Metrics: mvcc_gc_horizon_pinner_age_us{xid}, mvcc_gc_preempt_total. Runbook docs/runbook/idle-in-txn-storm.md is validated end-to-end against a Postgres-style bloat-incident postmortem template (templates/postmortem.md) this phase.

22. Phase 10 — Performance Hardening (Weeks 20–24)

22.1 Objectives

Close the M-series performance gaps left open by Phases 3–9: lock-free snapshot construction, hot-tuple read path, version-chain compaction. Applies P4; targets M1–M9 (§29).

22.2 Detailed Implementation Steps

Registry's epoch-protected RegistryProjection (§11.8): published atomically on every begin/commit/abort; take_snapshot becomes a single epoch-pinned pointer load, no lock (replaces §15.2's brief read-lock, closing the M5 gap). find_visible_hot (§11.6): inlines the chain-head-plus-first-header fetch into a single cache-line read; 99%-hot-path workloads never walk past the head (closing the M3 gap). Version-chain compaction: when a chain exceeds 1,024 (I8, ADR-16), an opportunistic pass drops sub-horizon versions and rewrites the chain in place, distinct from GC's periodic vacuum (§18).

22.3 Deliverable

The full M1–M9 benchmark suite (mvcc-bench) meets target on the reference host; Loom covers every unsafe block introduced by the epoch-based reclamation.

22.4 Acceptance Criteria

  • bench/single_writer.rs: read latency < 200 ns (M3).
  • bench/readers_dont_block.rs: 1 writer + 32 readers — writer throughput within 5% of the no-reader baseline (P1's throughput proof).
  • bench/snapshot_construct.rs: < 1 µs (M5).
  • bench/ssi_overhead.rs: SSI ≥ 60% of SI throughput (M2).
  • bench/gc_throughput.rs: ≥ 1,000,000 dead-versions/sec (M6).
  • Zero regressions on the full Berenson/Adya/Jepsen suite (§27) at these settings.

22.5 Conformance Fixtures

Fixture Purpose Expected Output

conformance/corpora/regression_gate.json full anomaly suite at hardened settings 0 new failures vs Phase 5–9 baseline

22.6 Pitfalls

  • Epoch-based reclamation requires every reader to pin() before dereferencing the projection — a thread that holds the pointer without pinning is a latent use-after-free.
  • The single-cache-line hot-path optimization assumes a hot slot directory; on a cold-tuple workload it degrades to two cache lines and yields no benefit — document the assumption, do not claim the M3 target unconditionally.
  • SSI's throughput floor depends on the SIREAD-lock data structure choice (§17.7) — a global mutex-protected map fails M2 regardless of other Phase-10 work.

22.7 Performance Concerns

This phase is the performance-concerns phase; its own N.7 is the meta-note: every target here is measured against the reference host defined in §29's benchmarking methodology, not asserted from theory.

22.8 Edge Cases

A reader that never calls pin() (bug, not a supported edge case — caught by Loom); an epoch-reclamation cycle racing a page-level HOT prune (§18) on the same page — ordered via the page's own LSN-gated compaction lock, distinct from the epoch mechanism.

22.9 Failure Analysis

A missed pin() causing a use-after-free is a memory-safety Sev-0 — Rust's type system cannot catch a logic-level "forgot to pin" bug the way it catches a data race, which is why Loom coverage on every unsafe block introduced here (§22.6) is an acceptance gate, not optional hardening.

22.10 Operational Notes

Metrics: mvcc_epoch_pin_duration_ns, mvcc_hot_path_hit_rate. This phase is the last before the system is considered "runnable/verifiable" at full target performance — Appendix B (§39) marks Phase 10 as the milestone where all M-series targets (§29) are simultaneously gated in CI (ADR-27).

23. Threat Model

Trust Boundaries

  1. Caller boundary — the library trusts the caller to use a TxnHandle exactly once after commit/abort (§12.8's double-commit guard is a courtesy check, not a security boundary).
  2. WAL boundary — the engine trusts #88 to durably persist commit records once wait_durable returns (I6).
  3. Lock Manager boundary — the engine trusts #101 for DDL-path locking; never circumvented (ADR-13).
  4. Replication boundary — the engine trusts replication slots to report accurate xmins (I13, ADR-20).
  5. Clock boundary — the HLC backend trusts the OS clock to advance within a bounded skew; unbounded skew triggers the overflow guard (§20.7), not silent corruption.

26. Compatibility & Versioning

  • Wire format: CommitRecord/WriteEntryRecord (§11.9, ADR-24) carry a schema_version field; a reader rejects a version it does not recognize rather than guessing.
  • Storage format: PageHeader/SlotEntry (§13.2) is versioned at the page-header flags field; a page-format bump requires an offline or online migration tool under tools/ and a new ADR.
  • Schema evolution: the TupleHeader (§11.2) is fixed at 32 bytes for the lifetime of this blueprint's v1; any field addition is a major-version, incompatible change (SemVer below).
  • API stability: TxnHandle's public surface (begin/read/write/commit/abort, §11.4/§11.11) is stable from Phase 2 (§14) onward; VersionStore/Visibility/ TimestampOracle/WalSink traits (§11.5–§11.9) are stable from their introducing phase.
  • Migration: a page-format migration runs as an offline mvccctl migrate pass or an online dual-write shadow period; both require a full conformance-suite re-run before cutover.
  • Deprecation policy: a deprecated API surface carries a #[deprecated] attribute for at least one minor version before removal; removal is a major-version bump.
  • SemVer policy: crate versions follow SemVer; a TupleHeader/CommitRecord/page-format change is major; a new VersionStore/TimestampOracle implementation is minor; a bug fix with no API change is patch.
  • Rolling-upgrade guarantees: a cluster (once paired with #46) may run mixed minor versions during a rolling upgrade as long as the wire schema_version is unchanged; mixed major versions are unsupported and block the upgrade at the coordinator level (#73).

30. Scalability Analysis

  • Constant regardless of scale: TupleHeader size (32 B), visibility-check cost (O(1) in shared state, I1), chain cap (1,024, ADR-16).
  • Grows with active-transaction count: snapshot construction — O(n) under the Phase 3 registry lock (§15.7), O(1) amortized under Phase 10's epoch projection (§22.1, M5).
  • Grows with write volume: version-chain length before HOT prune (O(updates since last prune)); GC/vacuum work (O(dead versions), bounded by M6's throughput).
  • Grows with read volume under SSI: SIREAD lock-table size (O(reads)), mitigated by page-level promotion (ADR-17) — the named bottleneck when SSI is enabled at scale.
  • Named bottlenecks, in order of first appearance as load increases: (1) registry lock contention on snapshot construction (Phase 3, resolved Phase 10); (2) SIREAD lock-table growth under SSI (Phase 5, mitigated by promotion, not eliminated); (3) single-AtomicU64 HLC contention at extreme allocation rates (deferred, §36 row 5); (4) xmin-horizon pinning by any single long-lived reader (Phase 9, §21) — this one is not a throughput bottleneck but an unboundedness hazard, the most operationally dangerous of the four.
  • Horizontal scaling: this blueprint is single-node; horizontal scale-out requires #46 (replication, read scaling) and #73 (2PC, write scaling across shards) — both integration boundaries, not implemented here.
  • Vertical scaling: near-linear read throughput with core count once Phase 10's lock-free snapshot lands (each reader touches no shared mutable state, I1); write throughput is bounded by the single commit-mutex serialization window (§14.7) and by WAL fsync bandwidth (M4/M10).
  • Sharding/partitioning: out of scope for this blueprint; a sharded deployment assigns disjoint key ranges to independent instances, coordinated by #73 for cross-shard transactions.
  • Coordination overhead: zero for single-node SI/SSI (no cross-node coordination); HLC's update_from_remote is the only cross-node coordination primitive this blueprint defines, and it is O(1) per message.
  • Practical ceiling: bounded by (a) single-core visibility-check throughput × core count (near-linear per the read-side argument above), and (b) WAL fsync bandwidth for the write path (M4/M10). The lever beyond (a) is more cores (P1 guarantees near-linear scaling); the lever beyond (b) is group-commit batching (§19.2) or faster durable media.

31. Mental Models & First Principles

  1. MM1 — Visibility is a pure function, not a lookup. The compressed insight: a version is visible or not based only on (header, snapshot), never on "ask someone else." Predicts: any design that adds a lock or a remote call to the read path has broken the core promise. Bug class without it: read-path lock contention that silently regresses P1's throughput guarantee. Resolving: §13 (Phase 1), I1.
  2. MM2 — MVCC is fundamentally about naming versions, not locking data. Reed's 1978 thesis framed it as "version pumps" — a generational naming problem, not a mutual-exclusion problem. Predicts: the hard part is always the id/timestamp allocation scheme (xid, commit-ts), not the locking primitive. Bug class without it: engineers reach for locks to "fix" an MVCC bug that is actually a timestamp-ordering bug. Resolving: §2, §20 (Phase 8).
  3. MM3 — There are three distinct "time" axes and conflating any two is a bug class. Allocation-order (TransactionId), commit-order (CommitTs), and physical wall-clock (HLC's physical component) are different number lines. Predicts: any comparison between an xid and a commit-ts, or a physical-clock read substituting for an HLC read, is probably wrong. Bug class without it: horizon/snapshot confusion (§15.6), clock-skew bugs in SSI's dangerous-structure check (§17.6). Resolving: §15 (Phase 3), §20 (Phase 8).
  4. MM4 — Append-only and in-place-with-undo are different universes, not variations on a theme. The compressed insight: GC strategy, rollback mechanism, and crash-recovery semantics all follow from this one architectural choice (ADR-04/ADR-05). Predicts: code that "shares a little logic" between HeapStore and InMemStore beyond the VersionStore trait surface is a maintenance trap. Bug class without it: rollback bugs from assuming append-only's "no undo needed" property applies to the in-memory backend. Resolving: §18 (Phase 6), P10.
  5. MM5 — The xmin horizon is the one number that must never be wrong in the "too high" direction. Compressed insight: an incorrectly-low horizon merely delays GC (safe, wasteful); an incorrectly-high horizon reclaims a version a live reader can still see (unsafe, catastrophic). Predicts: every horizon-adjacent bug should be biased toward "GC does less," never "GC does more," when in doubt. Bug class without it: FM9 (premature reclamation). Resolving: §7 (I4, I10), §18 (Phase 6).
  6. MM6 — Snapshot Isolation is a specific, nameable gap away from serializability, not a vague approximation. The gap has a name (write-skew, A5B) and a fix (SSI's dangerous-structure detection) — it is not "mostly serializable." Predicts: any claim of "SERIALIZABLE" in a vendor's default configuration should be independently verified against the Berenson suite, not trusted. Bug class without it: business-invariant violations shipped to production under a false serializability assumption. Resolving: §15 (Phase 3), §17 (Phase 5).
  7. MM7 — A predicate lock that never blocks is still a lock — it has cardinality and memory cost. SIREAD locks (§17.2) do not block writers but are not free; they are O(reads) memory structures with their own scaling story. Predicts: an SSI deployment with extreme read volume needs its own capacity plan, independent of the write-path capacity plan. Bug class without it: unbounded memory growth mistaken for a leak rather than a scaling limit (§17.6, T10). Resolving: §17 (Phase 5), §30.
  8. MM8 — A timestamp source's failure mode is the actual architectural decision, not its happy-path latency. Centralized oracle fails by halting the cluster; HLC fails by bounded-but-nonzero skew; TrueTime fails by requiring infrastructure most deployments do not have. Predicts: choosing a timestamp source is choosing which failure mode you can live with, not which one is "fastest." Resolving: §20 (Phase 8), §32.

PostgreSQL made the same append-only + xmin/xmax choice this design starts from, but kept oldest-first chains and CLOG-based abort lookup — its niche is "correctness with decades of production hardening," and it wins wherever operational maturity matters more than the marginal read-latency gain this design's newest-first chain buys.

Oracle rejected tuple-chain versioning entirely in favor of undo segments reconstructed on demand from a centralized SCN — it wins in workloads with very long-running reports against a mostly-static base table, where undo-segment reconstruction cost is amortized across few, long reads rather than paid per-tuple on every hot read.

MySQL InnoDB is the closest real analogue to this design's InMemStore-adjacent in-place approach, using undo logs instead of chained tuple versions — it wins where storage engines must support both MVCC reads and traditional row-locking DDL paths in one integrated structure, at the cost of purge-thread lag becoming its own bloat-equivalent pathology (§18.6's InnoDB parity).

CockroachDB made this design's exact timestamp-source choice (HLC) but layered it under an LSM storage engine and Raft replication, making every transaction serializable-by-default rather than offering SI as a cheaper opt-out — it wins in geo-distributed deployments where serializability-by-default is worth the throughput cost this design defers to opt-in SSI.

MyRocks (not tabled above for space, referenced here) layers MVCC semantics on RocksDB's LSM engine similarly to CockroachDB but single-node — it wins where write-amplification- optimized storage (LSM compaction) matters more than read-latency optimization, the inverse tradeoff from this design's page-heap-optimized-for-reads default (ADR-04).

35. Alternative Architectures (Roads Not Taken)

A1 — Strict Two-Phase Locking (Pessimistic Concurrency Control)

Reader ──acquire S-lock──▶ [Lock Table] ──block──▶ Writer waits
Writer ──acquire X-lock──▶ [Lock Table] ──block──▶ Reader waits
        (2PL: all locks held until commit/abort)

Regime where it wins: workloads with very high write-write contention on a small hot key set, where MVCC's optimistic first-committer-wins would abort most transactions anyway — 2PL's blocking cost is lower than repeated-abort-and-retry cost there. Real embodying system: the Lock Manager blueprint (#101) itself, and every pre-1980s relational database. Why rejected here: violates P1 (readers never block writers) outright — this is the single non-negotiable property this blueprint exists to deliver; 2PL cannot provide it by construction.

A2 — Deterministic Single-Threaded Execution (Calvin / VoltDB-style)

[Sequencer] ──assigns global order──▶ [Single-threaded executor per partition]
   no locks, no MVCC — determinism replaces concurrency control entirely

Regime where it wins: workloads whose transactions are short, known in advance (no interactive/ad hoc SQL), and partitionable — determinism eliminates concurrency-control overhead entirely. Real embodying system: VoltDB, Calvin (Thomson et al. 2012). Why rejected here: this blueprint targets general interactive OLTP with ad hoc read/write patterns and long-running analytical readers (§1) — Calvin's model requires transactions to declare their read/write sets upfront, which most real workloads (and this project's non-goal of a query planner, §1) cannot guarantee.

A3 — Timestamp-Ordering Multiversion Without Snapshots (Bernstein's MV-TO)

Read(k, ts) ──▶ pick the version with the largest xmin_commit_ts ≤ ts, no in_progress set
Write(k, ts) ──▶ reject if a read at ts' > ts has already occurred (TO rule)

Regime where it wins: a workload where every transaction's timestamp is known and fixed before execution begins (e.g., a batch pipeline replaying historical events in timestamp order) — MV-TO's simpler per-operation rule (no in_progress set to maintain) is cheaper there. Real embodying system: the classical MV-TO scheme itself (Bernstein & Goodman 1983, §5 Required Reading), rarely used standalone in production. Why rejected here: MV-TO's per-operation rejection rule produces far higher abort rates under interactive/unplanned transaction arrival than snapshot-based SI's commit-time check (ADR-14's rationale extends here) — the in_progress set (§11.3) is exactly the mechanism that avoids this.

A4 — Shadow-Paging / Copy-on-Write B-Tree (LMDB-style)

[Root Ptr] ──▶ [B-tree v1, immutable]
Writer builds [B-tree v2] copy-on-write, then atomically swaps [Root Ptr] → v2
   readers holding old [Root Ptr] see a fully consistent, frozen v1 forever

Regime where it wins: read-dominated workloads with infrequent, small writes and a strong preference for zero-lock reads with a trivially simple crash-recovery story (an atomic pointer swap) — no WAL, no visibility predicate needed at all. Real embodying system: LMDB, and Postgres's own historical CoW filesystem-level alternatives (ZFS snapshots). Why rejected here: copy-on-write at the page/tree level amplifies write cost proportional to tree depth per write (every write copies a root-to-leaf path), which fails this blueprint's M1 throughput target (100,000 txn/sec) at any realistic key cardinality — tuple-level versioning (this design's actual choice) amortizes far better under write-heavy OLTP.

37. Glossary

  • ABORTED_XMIN — the sentinel TransactionId value stamped into a version's xmin on abort; makes the version invisible to every snapshot immediately (§11.1).
  • ADR — Architecture Decision Record; this blueprint's locked decisions, §9.
  • Chain (version chain) — the linked sequence of physical versions for one logical row, connected via next pointers (§8).
  • Chain compaction — an opportunistic rewrite of a version chain dropping sub-horizon versions once it exceeds the 1,024-version cap (§18, §22).
  • cmin / cmax — command-id fields on TupleHeader resolving self-visibility within a multi-statement transaction (the Halloween-problem guard, §13.6).
  • CommitTs — the commit timestamp type; HLC-encoded or oracle-assigned, distinct from TransactionId (§11.1).
  • DurableToken — a typestate value only constructible after a WAL fsync completes; the sole path to TransactionState::Committed (§11.9, §19).
  • First-committer-wins (FCW) — the write-write conflict policy: the transaction that commits first wins; the later committer aborts (§9 ADR-14).
  • First-updater-wins (FUW) — the rejected alternative: conflict detected at write time, blocking the second writer (§9 ADR-14).
  • FROZEN — the sentinel TransactionId (u64::MAX) meaning "always visible" (§11.1).
  • GC horizon (xmin horizon) — the minimum xmin across all active transactions and replication slots; the GC reclamation boundary (§7 I4).
  • HLC (Hybrid Logical Clock) — a timestamp scheme combining a physical clock with a logical counter, bounding cross-node skew (Kulkarni 2014, §20).
  • HOT (Heap-Only Tuple) — a Postgres 8.3-derived optimization: an update that doesn't touch an indexed column chains in-page without a new index entry (§18).
  • Horizon pinner — a transaction whose snapshot's xmin equals the current GC horizon, blocking reclamation of everything newer (§21).
  • in_progress set — the set of transaction ids active at snapshot-construction time, carried in every Snapshot (§11.3).
  • Isolation level — RC / SI / SSI in this blueprint's vocabulary (§11.11, §16, §17).
  • MVCC — Multi-Version Concurrency Control (§1).
  • MV-TO — Multiversion Timestamp Ordering, the rejected alternative in §35 A3.
  • Non-repeatable read (P2) — a Berenson 1995 anomaly: a transaction re-reads a row and sees a different value (§15.4).
  • Oracle (timestamp) — the source of TransactionId/CommitTs allocation; centralized or HLC-based (§11.9).
  • Phantom (P3) — a Berenson 1995 anomaly: a range re-query returns different rows.
  • PhaseDeferred — the anchor mechanism marking a feature deferred beyond this blueprint's scope (§36).
  • Predicate lock (SIREAD) — an SSI tracking lock over a key/page/predicate scope that never blocks a writer (§11.10, §17.2).
  • Read-Committed (RC) — the isolation level taking a fresh snapshot per statement (§16).
  • Read skew (A5A) — a Berenson 1995 anomaly involving two related reads observing an inconsistent combination (§15.4).
  • Repeatable Read (RR) — Postgres's historical name for what this blueprint calls Snapshot Isolation (§16.6).
  • rw-antidependency — an edge in SSI's conflict graph: T1 read a version that T2 later wrote (§17.2, Cahill 2008).
  • Sealed — this blueprint's terminal quality gate: 30-day soak + fuzz canaries + external audit closed (§39, Appendix B).
  • SerializationFailure — the error returned to an aborted committer under first-committer-wins or SSI's dangerous-structure detection (§14.2, §17.2).
  • Serializable Snapshot Isolation (SSI) — Cahill 2008's algorithm layering serializability on top of SI via predicate locks and dangerous-structure detection (§17).
  • Snapshot — the (xmin_horizon, xmax_ceiling, in_progress, snapshot_ts) tuple defining a consistent read frontier (§11.3).
  • Snapshot Isolation (SI) — the default isolation level: one snapshot per transaction, first-committer-wins conflict detection, not serializable (§15).
  • TrueTime — Spanner's GPS/atomic-clock-backed interval clock; contrasted, not implemented, in this blueprint (§20.3).
  • TupleHeader — the 32-byte MVCC metadata header on every tuple version (§11.2).
  • TransactionId (xid) — the monotonic identifier allocated at BEGIN (§11.1).
  • VersionPtr — an opaque, backend-interpreted pointer to a tuple version (§11.2).
  • VersionStore — the trait abstracting HeapStore/InMemStore (§11.7).
  • Vacuum — the GC pass reclaiming dead versions and pruning HOT chains (§18).
  • Visibility — the pure predicate is_visible(header, snapshot) -> bool (§11.5, §7 I1).
  • Write skew (A5B) — the anomaly SI permits and SSI prevents: two transactions each read a shared invariant and each write a different row, jointly violating it (§15.6, §17).
  • Write-write conflict — two transactions attempting to supersede the same version; resolved by first-committer-wins (§9 ADR-14).
  • xmax — the tuple-header field naming the deleting/superseding transaction (§11.2).
  • xmin — the tuple-header field naming the inserting transaction (§11.2).
  • xmin_commit_ts — the commit timestamp of xmin, stamped once that transaction commits (§11.2).
