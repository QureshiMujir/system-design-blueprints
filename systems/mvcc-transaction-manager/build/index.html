⬜ Phase 0 — Skeleton, Governance & Hello-MVCC (Weeks 1–2) §12

Objectives

Stand up the repo skeleton (§10) and a placeholder single-thread-safe engine sufficient to demonstrate P1 (readers never block writers) end to end. No real visibility, chain, or GC logic yet — those are Phase 1+. Introduces the workspace crate boundaries that every later phase builds inside.

Deliverable

make bootstrap && make build && make test all exit 0; mvccctl begin/read/write/ commit/abort work over the placeholder engine.

Acceptance
  • make test passes with exactly 1 test, tests/hello_mvcc.rs::readers_do_not_block_writers.
  • Zero unsafe blocks in the skeleton (audited by cargo geiger); cargo miri test clean.
  • ADR-01, ADR-02, ADR-09, ADR-22 written under docs/adr/.
Fixtures
Fixture Purpose Expected Output
tests/hello_mvcc.rs::readers_do_not_block_writers T2 (begun pre-commit) sees no value, T3 (begun post-commit) sees v1 both assertions pass, deterministic
tests/hello_mvcc.rs::malformed_double_commit commit() called twice on the same handle second call returns Err, no panic
Pitfalls
  • Concurrency-test flakiness: use a deterministic single-threaded interleaving harness for this smoke test; real multi-threaded races are Phase 1+'s Loom tests, not this phase's.
  • The placeholder oracle's u64 xid counter wraps at 2⁶⁴ allocations; documented, not handled — real wraparound handling is Phase 6 (§18, ADR-16-adjacent).
  • cargo miri refuses to run past any unsafe block; the skeleton has none by design — re-audit at every phase boundary (a P1-derived project rule).

⬜ Phase 1 — Version Chain & Visibility Check (Weeks 2–4) §13

Objectives

Implement the real version chain (mvcc-core::chain), the Postgres-style page heap (mvcc-storage::heap, HeapStore), and the complete visibility predicate. Realizes P1, P4, P7, I1, I7, I8; applies ADR-04, ADR-06, ADR-15, ADR-16.

Deliverable

HeapStore end-to-end: insert, chain traversal, visibility all functional; tests/ visibility_matrix.rs enumerates the 6×5 xmin×xmax case cross-product.

Acceptance
  • is_visible_full passes all 30 hand-crafted cases in visibility_matrix.rs (fixture name below); zero mismatches.
  • Property test: 1,000,000 random (header, snapshot, my_xid) triples match a line-for-line Postgres-HeapTupleSatisfiesMVCC reference port, zero divergences.
  • Chain traversal p99 ≤ 1 µs over a 10-version chain (M8, §29).
Fixtures
Fixture Purpose Expected Output
conformance/corpora/visibility_matrix.json 30-case xmin×xmax cross-product all 30 verdicts match hand-derived truth table
conformance/corpora/chain_cycle_fuzz.json adversarial next-pointer construction AppendError::IndexCorrupt, never an infinite loop (I7)
fuzz_targets/visibility_random.rs 24h fuzz canary zero panics (M13-adjacent)
Pitfalls
  • xmin == my_xid && cmin >= my_cmd is the Halloween-problem guard (Stonebraker 1975); get it wrong and UPDATE t SET x = x + 1 non-terminates.
  • FROZEN must be u64::MAX, not 0 — a zero xmin means "never inserted."
  • ABORTED_XMIN eager-tombstone (ADR-11) trades read-path cost for abort-path cost; get the tradeoff backwards and every read pays a CLOG-equivalent lookup.
  • The next pointer must be set atomically with the chain-head CAS at insert (I7); Loom (loom.chain_head_cas) enumerates the interleavings.

⬜ Phase 2 — Transaction State Machine & Commit/Abort Protocol (Weeks 4–6) §14

Objectives

Implement the one-way transaction state machine and the commit/abort protocols. Realizes P8, P12, P13; applies ADR-14, ADR-19 (partially — full WAL binding is Phase 7, §19); I2, I5, I6 (stubbed pending Phase 7's DurableToken), I9.

Deliverable

Commit/abort round-trip on the Phase-0 smoke workload; Transaction's state machine passes a TLA+ mini-spec (tla/MvccSI.tla, partial — full spec completes in §15).

Acceptance
  • Property test: 1,000 random 100-op begin/read/write/commit/abort workloads match a serial-equivalent reference; zero divergences.
  • Loom test loom.commit_abort_race: two threads, one commits while the other aborts a different txn on an overlapping key — registry state consistent in every enumerated interleaving (target: 100% of Loom-enumerated schedules, typically 10³–10⁵ per test).
  • Zero observed Committed → Aborted transitions in 10⁶ simulator ticks (I5).
Fixtures
Fixture Purpose Expected Output
conformance/corpora/commit_abort_property.json 1,000 random workload replay matches serial reference, 0 divergences
loom.commit_abort_race concurrent commit/abort interleavings consistent registry state, all interleavings
tests/state_machine_illegal_transition.rs attempt Committed→Aborted via crafted call compile error (no such API exists)
Pitfalls
  • The abort tombstone step must be idempotent — a concurrent GC pass may have already reclaimed the version (null VersionPtr); the stamp becomes a no-op.
  • Clearing xmax on abort races with another transaction's own set_xmax attempt on the same tuple; CAS-loop, only clear if current xmax == txn.id (I9).
  • Reordering commit steps 4 and 5 (flip before fsync) is the visibility-before-durability violation (I6) — a Sev-0 (FM1, §24).
  • commit_ts > snapshot_ts(any active reader) is required for ordering; the centralized oracle gets this via monotonicity (I3); HLC (§20) needs an explicit max-of-physical/ counter step.

⬜ Phase 3 — Snapshot Isolation (Weeks 6–8) §15

Objectives

Implement snapshot construction and make Snapshot Isolation the functionally correct default isolation level. Realizes P2; applies ADR-09, ADR-14 (the full commit-time check against the true registry); I3, I4.

Deliverable

All isolation levels defined in the IsolationLevel enum (§11.11); SI functionally correct against the Berenson 1995 anomaly suite (P0–P3, A5A prevented; A5B intentionally observed, not prevented).

Acceptance
  • Berenson 1995 vectors: P0/P1/P2/P3/A5A prevented under SI — 100% pass on conformance/corpora/berenson1995/ (≥ 6 sub-cases per anomaly, 0 failures).
  • A5B (write-skew) occurs under SI — this is a documented Pass, not a failure (fixture anomaly.berenson1995_a5b, expected outcome "observed").
  • Property test: 10,000 random concurrent workloads are SI-consistent (checked via Elle, §27), 0 anomaly-checker violations outside the documented A5B case.
Fixtures
Fixture Purpose Expected Output
conformance/corpora/berenson1995/p0..a5a.json dirty-write/read, non-repeatable-read, phantom, read-skew all "prevented" under SI
conformance/corpora/berenson1995/a5b.json write-skew (two-doctors-on-call) "observed" under SI (documented limitation)
examples/write_skew_demo.rs runnable A5B reproducer both doctors go off-call, invariant violated
Pitfalls
  • "SI is serializable" is the most common misconception in the field (P2) — the conformance bucket records A5B's occurrence as a correct Pass, not a bug.
  • The write-write check (step 1) races the atomic-publication step (step 5, §14.2); the two are serialized through a single per-key commit-mutex.
  • snapshot_ts (a CommitTs) and xmin_horizon (a TransactionId) are different number lines — conflating them is a recurring bug class (MM3, §31).

⬜ Phase 4 — Read-Committed & Repeatable-Read (Weeks 8–9) §16

Objectives

Implement the two "cheap" isolation levels: per-statement snapshots (RC) and the transaction-level snapshot already built in Phase 3 exposed as RR. Realizes P14; applies ADR-09.

Deliverable

BEGIN ISOLATION LEVEL {ReadCommitted|SnapshotIsolation} dispatches correctly through mvccctl; the Postgres-isolation-tester corpus subset for RC/SI passes.

Acceptance
  • Berenson 1995 P2 (non-repeatable read): occurs under RC, prevented under SI/RR — both documented outcomes verified by conformance/corpora/postgres_isolation/.
  • conformance/corpora/postgres_isolation/ (RC + SI subsets) passes 100% (≥ 40 cases).
  • Mixing RC/RR reads in one transaction returns Err(MixedIsolationLevel) in 100% of the 20 fixture attempts.
Fixtures
Fixture Purpose Expected Output
conformance/corpora/postgres_isolation/rc_p2.json P2 under RC anomaly occurs (documented)
conformance/corpora/postgres_isolation/si_p2.json P2 under SI/RR anomaly prevented
tests/mixed_isolation_reject.rs RC read then RR read same txn Err(MixedIsolationLevel)
Pitfalls
  • RC reads are individually cheap but frequent; snapshot construction must not be O(n) in active-txn count at scale — Phase 4 accepts the Phase-3 lock (documented ceiling, resolved §22).
  • A transaction holding an earlier statement's RR/SI snapshot must not have the horizon advanced past it by a later statement in the same transaction — the registry tracks the minimum over all live snapshots, not just the latest.
  • Postgres's "REPEATABLE READ" name is a historical artifact predating Berenson 1995 — it is SI, not textbook RR; this blueprint's IsolationLevel::SnapshotIsolation is named accurately instead.

⬜ Phase 5 — Serializable Snapshot Isolation (SSI) (Weeks 9–12) §17

Objectives

Close the write-skew gap left open by SI (§15.6) using Cahill 2008's dangerous-structure detection. Realizes P3, P14; applies ADR-17, ADR-18; I11.

Deliverable

The Berenson 1995 A5B write-skew anomaly is prevented under SSI (one of the two conflicting transactions aborts with SerializationFailure); Adya 1999's G2 phenomenon is prevented.

Acceptance
  • examples/write_skew_demo.rs run under SSI: one of the two doctor transactions aborts; the on-call invariant holds in 100% of 1,000 repeated trials.
  • Adya 1999 G2 (anti-dependency cycle) prevented: conformance/corpora/adya1999/g2.json, 0 undetected cycles across 10,000 generated cycle-shaped workloads.
  • SSI false-positive rate ≤ 5% on the TPC-C variant (ADR-18, M-target cross-referenced in §29) — measured, not asserted.
  • SSI throughput ≥ 60% of SI throughput on the same workload (M2, §29).
Fixtures
Fixture Purpose Expected Output
conformance/corpora/adya1999/g2.json anti-dependency cycle detection 0 undetected cycles / 10,000
conformance/corpora/postgres_isolation/ssi_parity.json matches Postgres 9.6+ SSI behavior ≥ 95% verdict agreement
examples/ssi_aborts_write_skew.rs runnable SSI A5B fix one txn aborts, invariant holds
Pitfalls
  • SIREAD lock storage grows linearly with read volume — a 1M-read/sec workload sustains millions of locks; page-level promotion (§17.2) is the safety valve, not optional.
  • The rw-antidependency graph must drop an aborted transaction's edges, or leaked edges produce false negatives (missed anomaly) or false positives (spurious aborts).
  • The "T2 commits before T1" check is sensitive to clock skew under HLC (§20) — the HLC-aware comparator uses HLC timestamps, never physical wall-clock reads directly.
  • The dangerous-structure check is O(in-degree × out-degree) for the committer — a large read+write set dominates commit cost; Phase 10 (§22) mitigates via incremental maintenance, not by skipping the check.

⬜ Phase 6 — Garbage Collection / Vacuum / HOT (Weeks 12–15) §18

Objectives

Implement xmin-horizon computation, dead-version reclamation, and HOT chain pruning; land the InMemStore alternate backend. Realizes P6, P7, P10; applies ADR-05, ADR-10, ADR-16; I4, I8, I10.

Deliverable

A 1M-row insert+update workload holds storage proportional to live rows, not historical rows; HOT prune collapses a 1,000-update chain back to depth 1 within one GC pass.

Acceptance
  • GC throughput ≥ 1,000,000 dead versions/sec/core (M6, §29), measured on bench/gc_throughput.rs.
  • Storage overhead vs single-version after vacuum ≤ 30% (M11, §29).
  • HOT prune reduces a 1,000-version chain to depth 1 in a single pass, verified on examples/hot_chain_demo.rs.
  • InMemStore passes the full visibility_matrix.rs suite (§13.5) unchanged (trait-level parity with HeapStore).
Fixtures
Fixture Purpose Expected Output
conformance/corpora/gc_bloat_bound.json 1-hour write-heavy workload, no pinner storage growth proportional to live rows
examples/gc_horizon_demo.rs horizon computation across active + slot xmins horizon = true minimum
examples/hot_chain_demo.rs 1,000-update HOT chain pruned to depth 1
Pitfalls
  • The horizon must include replication-slot xmins (ADR-20, I13) or a standby falls behind the primary's GC and breaks streaming consistency (the #46 integration boundary).
  • reclaim is unsafe — the caller must prove xmax < xmin_horizon (I10) before calling; the GC subsystem is the only caller (§11.7).
  • HOT prune races with concurrent readers — Loom (loom.gc_reader_race) enumerates: reader on slot A while HOT-prune rotates A→B; the reader must see either the pre-prune A or the post-prune B atomically, never a half-rotated state.
  • Vacuum must not reclaim a version whose xmax-owning transaction is still Committing (writes not yet durable) — the horizon check implicitly covers this (I4 excludes in-flight committers), but an explicit assertion documents the invariant.

⬜ Phase 7 — WAL Integration Boundary (Weeks 15–16) §19

Objectives

Bind the commit protocol's durability step to a real WAL contract (blueprint #88); implement crash recovery. Realizes P12; applies ADR-19, ADR-24; I6.

Deliverable

kill -9 the process at random intervals; on restart the database is consistent, no committed transaction is lost, no aborted transaction resurrects.

Acceptance
  • recovery.crash_replay: 1,000 random kill -9 cycles with random WAL truncation — every replay produces a consistent state (0 lost commits, 0 resurrected aborts).
  • Group commit sustains ≥ 100,000 commits/sec on a single core at fsync_interval = 1 ms (part of M4's basis, §29).
  • WAL replay rate ≥ 500 MB/sec (M10, §29), gating the RTO budget (§4).
  • Constructing Committed{..} without a DurableToken is a compile error (structural proof, not a test).
Fixtures
Fixture Purpose Expected Output
recovery.crash_replay (1,000 cycles) random kill -9 + WAL truncation consistent post-recovery state, every cycle
recovery.partial_wal WAL truncated mid-CommitRecord transaction treated as not-committed (§8)
conformance/corpora/group_commit_throughput.json sustained commit load ≥ 100K commits/sec
Pitfalls
  • Linux's durability barrier is fdatasync, not fsync, once the WAL file's size/inode is fixed at creation — using fsync per record is ~3× slower for no correctness benefit.
  • Group-commit batches must not coalesce across a WAL file rollover — the second half's fsync is independent of the first file's.
  • A "no commit record found" recovery verdict is final — the engine must never later discover a commit record and resurrect a transaction already marked Aborted; the WAL is the sole source of truth (I6).
  • Replication slots (ADR-20) hold the WAL from truncating past the slot's LSN — a permanently disconnected replica grows the WAL unboundedly (cross-referenced in FM7, §24).

⬜ Phase 8 — Distributed Timestamps: HLC (Weeks 16–18) §20

Objectives

Replace the Phase-0 CentralizedOracle with the Hybrid Logical Clock as the production default; document the TrueTime contrast. Realizes P5; applies ADR-07, ADR-08; I3, I12.

Deliverable

HLC passes the Kulkarni 2014 Section 4 ordering-invariant suite; a synthetic ±100 ms clock-skew injection between two simulated nodes preserves snapshot consistency.

Acceptance
  • HLC ordering invariant suite: 100% pass on conformance/corpora/hlc_ordering.json.
  • examples/hlc_skew_demo.rs: ±100 ms injected skew, 0 snapshot-consistency violations.
  • Berenson 1995 anomaly suite (§15.4) re-passes unchanged against the HLC backend (parity with the centralized-oracle backend).
  • HLC logical-counter overflow assertion fires deterministically on a frozen-clock fixture (not a production expectation — a correctness-boundary test).
Fixtures
Fixture Purpose Expected Output
conformance/corpora/hlc_ordering.json Kulkarni 2014 Section 4 invariants 100% pass
examples/hlc_skew_demo.rs ±100 ms cross-node skew snapshot consistency preserved
tests/hlc_overflow_frozen_clock.rs 65,536 consecutive now() calls, frozen clock overflow assertion fires
Pitfalls
  • The 16-bit logical counter overflows if the physical clock fails to advance for 65,536 consecutive now() calls — the panic is the defense; monitoring the counter's range is the operational complement.
  • update_from_remote must be called on every cross-node interaction (replication tick, RPC reply); a missed call is a correctness bug the skew demo is designed to catch.
  • Lamport's clock (1978) gives a total order but discards physical proximity; HLC keeps both — conflating the two in documentation or code comments is a recurring error (MM3, §31).

⬜ Phase 9 — Long-Running Readers & Bloat Mitigation (Weeks 18–20) §21

Objectives

Turn the xmin-horizon-pinning pathology (P9) from a silent operational failure into a surfaced, actionable one. Applies P9; extends I4.

Deliverable

A synthetic horizon-pinner workload triggers warn/alert/pre-empt at the configured ages; a 1-hour write-heavy workload with one 30-minute pinner shows bounded storage growth (pinner pre-empted at 30 min, horizon advances, bloat reclaimed within one GC tick).

Acceptance
  • Warn fires at 60 s ± 1 s, alert at 5 min ± 5 s, pre-empt at 30 min ± 10 s on the synthetic fixture (100 trials, 0 misses).
  • The 1-hour bloat fixture (§18.4's gc_bloat_bound extended) shows storage returning to within 5% of the no-pinner baseline within one GC tick after pre-emption.
  • 2PC-prepared and replication-slot pinners are correctly excluded from pre-emption (they are not cancelable — routed to the operator instead, per ADR-21/ADR-20).
Fixtures
Fixture Purpose Expected Output
conformance/corpora/horizon_pinner_thresholds.json synthetic pinner at each threshold age warn/alert/pre-empt fire on schedule
conformance/corpora/gc_bloat_bound_pinner.json 1-hr write-heavy + 30-min pinner bounded growth, reclaimed post-pre-empt
tests/pinner_2pc_excluded.rs prepared-txn pinner not pre-empted, routed to operator alert
Pitfalls
  • Pre-emption is dangerous for a legitimate long analytical scan — default thresholds are aggressive; production deployments must tune per-session (documented, not hardcoded).
  • A pinner held by a 2PC-prepared transaction (#73) is not pre-emptable — only the coordinator's resolution path can release it.
  • Replication-slot xmins are not pre-emptable either — the operator must drop the slot; the metric distinguishes pinner source (active txn vs slot) so the runbook routes correctly.

⬜ Phase 10 — Performance Hardening (Weeks 20–24) §22

Objectives

Close the M-series performance gaps left open by Phases 3–9: lock-free snapshot construction, hot-tuple read path, version-chain compaction. Applies P4; targets M1–M9 (§29).

Deliverable

The full M1–M9 benchmark suite (mvcc-bench) meets target on the reference host; Loom covers every unsafe block introduced by the epoch-based reclamation.

Acceptance
  • bench/single_writer.rs: read latency < 200 ns (M3).
  • bench/readers_dont_block.rs: 1 writer + 32 readers — writer throughput within 5% of the no-reader baseline (P1's throughput proof).
  • bench/snapshot_construct.rs: < 1 µs (M5).
  • bench/ssi_overhead.rs: SSI ≥ 60% of SI throughput (M2).
  • bench/gc_throughput.rs: ≥ 1,000,000 dead-versions/sec (M6).
  • Zero regressions on the full Berenson/Adya/Jepsen suite (§27) at these settings.
Fixtures
Fixture Purpose Expected Output
benchmarks/results/host/perf.json full M1–M9 suite all targets met
loom.epoch_reclamation epoch-pin/unpin races no use-after-free, all interleavings
conformance/corpora/regression_gate.json full anomaly suite at hardened settings 0 new failures vs Phase 5–9 baseline
Pitfalls
  • Epoch-based reclamation requires every reader to pin() before dereferencing the projection — a thread that holds the pointer without pinning is a latent use-after-free.
  • The single-cache-line hot-path optimization assumes a hot slot directory; on a cold-tuple workload it degrades to two cache lines and yields no benefit — document the assumption, do not claim the M3 target unconditionally.
  • SSI's throughput floor depends on the SIREAD-lock data structure choice (§17.7) — a global mutex-protected map fails M2 regardless of other Phase-10 work.
