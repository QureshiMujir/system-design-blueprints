Decisions (§9) · 29 ADRs

ADR-01

Implementation language

Chosen

Rust 1.78+, edition 2021

Rejected

C, C++, Go, Zig

When the rejected choice is right

A team with zero Rust experience and a hard 3-month deadline on a throwaway prototype — C/Go ship faster short-term

Why: Borrow checker eliminates the memory-bug class behind Postgres CVE-2023-2454-family and MySQL CVE-2024-21164-family heap-corruption bugs

ADR-02

mvcc-core platform

Chosen

no_std + alloc-optional

Rejected

std-only

When the rejected choice is right

The crate will only ever run hosted with a full OS — std-only simplifies dependency management

Why: Embeds in a kernel-bypass storage engine; compiles to WASM for the simulator (§27)

ADR-03

Async model

Chosen

Synchronous core, tokio only at the API/IO boundary

Rejected

Fully async core

When the rejected choice is right

The host application is already 100% async end-to-end and the sync/async boundary crossing cost dominates

Why: Avoids "async colours" polluting the hot visibility path; keeps is_visible a plain fn (I1)

ADR-04

Default version storage

Chosen

Append-only page heap (HeapStore)

Rejected

In-place-with-undo only

When the rejected choice is right

A pure in-memory OLTP engine with no crash-durability requirement and extreme write throughput needs (Hekaton's niche)

Why: Simpler durability reasoning; dominant production model (Postgres)

ADR-05

Alternate backend

Chosen

In-place-with-undo (InMemStore, Hekaton-style)

Rejected

Skip the alt backend entirely

When the rejected choice is right

A team that only ever needs the durable backend — maintaining two VersionStore impls is unjustified overhead

Why: Wu 2017 shows this is the high-performance choice for main-memory OLTP

ADR-06

Chain direction

Chosen

Newest-first (Neumann 2015 / HyPer)

Rejected

Oldest-first (Postgres)

When the rejected choice is right

A workload dominated by historical/time-travel reads (AS OF queries) — oldest-first avoids a chain reversal on every historical scan

Why: O(1) hot-tuple reads; the dominant OLTP access pattern reads the latest value

ADR-07

Timestamp source (default)

Chosen

Hybrid Logical Clock (Kulkarni 2014)

Rejected

Centralized oracle only, TrueTime

When the rejected choice is right

Single-node deployment with no cross-node clock coordination need — centralized oracle is simpler and equally correct there

Why: Decentralized, bounded skew, no single point of contention; TrueTime needs GPS/atomic-clock infra we do not require

ADR-08

Timestamp width

Chosen

64-bit, 128-bit feature-gated

Rejected

32-bit (Postgres-style)

When the rejected choice is right

A memory-constrained embedded deployment where 8 bytes/tuple-header field is prohibitive — 32-bit + freeze machinery wins

Why: 64 bits at 1 µs resolution = 584,000-year horizon; 32-bit wraps in ~2^31 transactions, forcing freeze maintenance

ADR-09

Isolation levels exposed

Chosen

RC, RR/SI, SSI; default SI

Rejected

Expose Read-Uncommitted

When the rejected choice is right

An analytics-only workload that explicitly wants to read in-flight aggregates for approximate dashboards — RU would serve that niche

Why: RU offers no correctness benefit MVCC does not already give for free at RC's cost; Berenson A1 stays closed at the type level

ADR-10

GC scheme

Chosen

xmin-horizon-driven background vacuum + opportunistic HOT prune

Rejected

Reference counting per version

When the rejected choice is right

A workload with extremely low write volume and tight latency budget on delete — refcounting reclaims immediately at higher per-write cost

Why: Matches the Postgres post-8.3 model; amortizes reclamation cost

ADR-11

Abort representation

Chosen

ABORTED_XMIN sentinel stamped eagerly

Rejected

CLOG-style lazy status lookup (Postgres)

When the rejected choice is right

A workload with a very high abort rate (e.g., heavy optimistic-retry contention) — CLOG lookup amortizes better than a write-heavy abort stamp

Why: Moves cost from the read path (every visibility check) to the abort path (rare)

ADR-12

Rollback mechanism

Chosen

No undo log (append-only backend); per-version undo (InMemStore)

Rejected

Universal undo log

When the rejected choice is right

A single-backend design that must support both storage models with one code path — a universal undo log would simplify at a durability cost

Why: Append-only backend does not need undo — the version simply never becomes visible

ADR-13

DDL concurrency path

Chosen

2PL fallback via Lock Manager (#101)

Rejected

MVCC-native DDL (versioned schema)

When the rejected choice is right

A system requiring true online schema change with zero downtime — versioned-schema MVCC (as in F1/Spanner) wins there

Why: DDL is rare and its "every version has an old and new schema" semantics is a distinct, harder problem out of scope

ADR-14

Write-write conflict detection

Chosen

First-committer-wins, checked at commit

Rejected

First-updater-wins, checked at write time

When the rejected choice is right

A workload where aborting late (after doing all the work) is far more expensive than blocking early — FUW wins under high write-contention + cheap blocking

Why: FUW blocks writers behind not-yet-committed writers, violating P1

ADR-15

Version metadata placement

Chosen

Inline per-row header (32 B)

Rejected

Separate side-table (id → version metadata)

When the rejected choice is right

An extremely wide-row workload where 32 B/row is a rounding error but random side-table lookups would be free — side-table wins if it's smaller in total

Why: Matches Postgres; one cache-line fetch gets header + can co-locate short payloads

ADR-16

Version chain length cap

Chosen

1,024, triggers compaction at cap

Rejected

Unbounded chain length

When the rejected choice is right

A read-rarely, append-mostly workload with a single writer per key (no update contention) where compaction cost exceeds any realistic traversal cost — raise or disable the cap

Why: Bounds worst-case traversal latency (I8)

ADR-17

SSI predicate-lock granularity

Chosen

Tuple-level default, page-level under pressure

Rejected

Table-level only

When the rejected choice is right

A workload with enormous cardinality and low per-tuple contention where table-level locking's simplicity outweighs the false-positive cost

Why: Cahill 2008, Section 5.2 promotion path; tuple-level minimizes false positives

ADR-18

SSI false-positive policy

Chosen

Tolerate ≤ 5% spurious aborts

Rejected

Zero-false-positive (full precision) tracking

When the rejected choice is right

A workload where every spurious abort has extreme business cost (e.g., irreversible external side effects) — pay the precision cost

Why: Cahill 2008, Section 6.3 — full precision requires unbounded predicate-lock cardinality

ADR-19

WAL durability ordering

Chosen

Commit record fsync before visibility flip

Rejected

Visibility flip then async fsync

When the rejected choice is right

A pure read-through cache tier rebuilt from an upstream source of truth on every restart, where losing the last few seconds of "commits" on crash is an accepted, cheap-to-recover cost — there, leading visibility ahead of fsync buys lower commit latency with no durability promise to violate

Why: Mohan 1992's ARIES rule; async flip risks phantom-committed reads after a crash

ADR-20

Replication integration

Chosen

Replication-slot xmin folds into GC horizon (I13)

Rejected

Ignore slot xmin, let replicas resync from base backup on lag

When the rejected choice is right

A deployment with disposable, always-rebuildable replicas (e.g., ephemeral read replicas in a cache tier) — ignoring slot xmin avoids primary bloat from a lagging throwaway replica

Why: Standbys need to reconstruct a valid snapshot mid-stream

ADR-21

2PC integration

Chosen

Prepared transactions hold a permanent xmin until resolved

Rejected

Auto-abort prepared transactions after a timeout

When the rejected choice is right

A deployment that prioritizes availability over the (rare) distributed-transaction correctness edge case — auto-abort-on-timeout wins there, at the cost of occasional inconsistency

Why: Prepared-but-uncommitted state must survive coordinator failure (#73's contract)

Roads not taken (§35)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

A1 — Strict Two-Phase Locking (Pessimistic Concurrency Control)

Reader ──acquire S-lock──▶ [Lock Table] ──block──▶ Writer waits
Writer ──acquire X-lock──▶ [Lock Table] ──block──▶ Reader waits
        (2PL: all locks held until commit/abort)

Regime where it wins: workloads with very high write-write contention on a small hot key set, where MVCC's optimistic first-committer-wins would abort most transactions anyway — 2PL's blocking cost is lower than repeated-abort-and-retry cost there. Real embodying system: the Lock Manager blueprint (#101) itself, and every pre-1980s relational database. Why rejected here: violates P1 (readers never block writers) outright — this is the single non-negotiable property this blueprint exists to deliver; 2PL cannot provide it by construction.

A2 — Deterministic Single-Threaded Execution (Calvin / VoltDB-style)

[Sequencer] ──assigns global order──▶ [Single-threaded executor per partition]
   no locks, no MVCC — determinism replaces concurrency control entirely

Regime where it wins: workloads whose transactions are short, known in advance (no interactive/ad hoc SQL), and partitionable — determinism eliminates concurrency-control overhead entirely. Real embodying system: VoltDB, Calvin (Thomson et al. 2012). Why rejected here: this blueprint targets general interactive OLTP with ad hoc read/write patterns and long-running analytical readers (§1) — Calvin's model requires transactions to declare their read/write sets upfront, which most real workloads (and this project's non-goal of a query planner, §1) cannot guarantee.

A3 — Timestamp-Ordering Multiversion Without Snapshots (Bernstein's MV-TO)

Read(k, ts) ──▶ pick the version with the largest xmin_commit_ts ≤ ts, no in_progress set
Write(k, ts) ──▶ reject if a read at ts' > ts has already occurred (TO rule)

Regime where it wins: a workload where every transaction's timestamp is known and fixed before execution begins (e.g., a batch pipeline replaying historical events in timestamp order) — MV-TO's simpler per-operation rule (no in_progress set to maintain) is cheaper there. Real embodying system: the classical MV-TO scheme itself (Bernstein & Goodman 1983, §5 Required Reading), rarely used standalone in production. Why rejected here: MV-TO's per-operation rejection rule produces far higher abort rates under interactive/unplanned transaction arrival than snapshot-based SI's commit-time check (ADR-14's rationale extends here) — the in_progress set (§11.3) is exactly the mechanism that avoids this.

A4 — Shadow-Paging / Copy-on-Write B-Tree (LMDB-style)

[Root Ptr] ──▶ [B-tree v1, immutable]
Writer builds [B-tree v2] copy-on-write, then atomically swaps [Root Ptr] → v2
   readers holding old [Root Ptr] see a fully consistent, frozen v1 forever

Regime where it wins: read-dominated workloads with infrequent, small writes and a strong preference for zero-lock reads with a trivially simple crash-recovery story (an atomic pointer swap) — no WAL, no visibility predicate needed at all. Real embodying system: LMDB, and Postgres's own historical CoW filesystem-level alternatives (ZFS snapshots). Why rejected here: copy-on-write at the page/tree level amplifies write cost proportional to tree depth per write (every write copies a root-to-leaf path), which fails this blueprint's M1 throughput target (100,000 txn/sec) at any realistic key cardinality — tuple-level versioning (this design's actual choice) amortizes far better under write-heavy OLTP.
