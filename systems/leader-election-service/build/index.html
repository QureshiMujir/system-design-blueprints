⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the workspace (§10), the injectable-clock/network/disk primitives, the error taxonomy (§11), the protobuf schema skeleton, and the deterministic sim-harness carrying one assertion per invariant I1–I15 — before any protocol logic exists. Introduce constraints: no ambient time/randomness in replicated code (P2); reproducible builds (ADR-25).

Deliverable

A compiling workspace where cargo test runs the empty sim-harness green, CI is reproducible across two clean machines (byte-identical binary), and electiond --version prints a stamped build.

Acceptance
  • All 14 crates compile; clippy -D warnings clean; cargo deny check passes (0 advisories).
  • Two independent builds produce byte-identical electiond (sha256 match) — fixture repro-build.attest.
  • Sim-harness executes ≥ 10,000 random seeds/min with a fixed seed replaying identically (hash match).
  • Injected-fault matrix (partition, delay, drop, torn-write) each reproduce from a recorded seed.
Fixtures
Fixture Purpose Expected output
build/repro-build.attest reproducible build proof two sha256 equal
sim/replay-seed-0001.trace deterministic replay identical final-state hash
wire/proto-skeleton.bin proto3 round-trip decode==encode
malformed/oversize-entry.bin payload > C20 (1 MiB) rejected InvalidRequest
sim/torn-write.trace (regression) injected torn write replays wal_crc_error asserted
Pitfalls
  • Ambient Instant::now() sneaking into replicated code → nondeterministic replay (root cause: convenience; detect: clippy lint banning std::time::Instant::now; recover: route through injected clock; P2).
  • Non-deterministic HashMap iteration order in applied state → apply-hash divergence (use BTreeMap; I8).
  • Host-specific paths/timestamps leaking into the binary → build non-reproducible (SOURCE_DATE_EPOCH; ADR-25).

⬜ Phase 1 — Peer Transport Runtime §13

Objectives

Deliver authenticated, framed, back-pressured peer-to-peer transport so raft-engine (Phase 3) can exchange votes, heartbeats, and log entries. Constraints: bounded inflight (P4), TLS identity (P14), no unbounded buffering (P5). Not yet: consensus logic.

Deliverable

Two electiond processes exchange authenticated, length-prefixed protobuf messages over TLS with observable RTT and enforced backpressure; a slow peer never grows the sender's memory beyond the window.

Acceptance
  • Sustains ≥ 50,000 concurrent framed streams/node with memory ≤ 512 MiB (fixture transport/50k-streams.json).
  • p99 peer RTT < 20 ms on loopback+injected 2 ms (matches C2); histogram exported.
  • Backpressure: with a stalled consumer, sender memory stays ≤ window size (bounded, P4), verified by transport/slow-consumer.trace.
  • Malformed frame (bad length prefix, truncated) rejected without panic; frame_decode_error_total increments.
Fixtures
Fixture Purpose Expected output
transport/50k-streams.json concurrency/memory ceiling ≤ 512 MiB, no drops
transport/truncated-frame.bin (malformed) partial frame rejected, no panic
transport/oversize-frame.bin (malformed) > C20+header rejected
transport/slow-consumer.trace backpressure sender mem ≤ window
transport/replay-frames.trace (replay) duplicate frames idempotent decode
Pitfalls
  • Retry storms after a blip synchronize all peers (thundering herd) — jittered backoff; detect via peer_retry_total spike; root cause: un-jittered timers (P5).
  • Connection leaks on half-open sockets — TCP keepalive + idle reaper; detect via peer_conn_open monotonic climb.
  • Head-of-line blocking on a single TCP stream stalling heartbeats — dedicate a high-priority control stream separate from bulk log shipping.

⬜ Phase 2 — Write-Ahead Log Engine §14

Objectives

Provide crash-safe, append-only, ordered durable storage for LogEntry with group-commit fdatasync, CRC integrity (I15), and deterministic replay (I3). This is the durability substrate for Raft commit (P8, I10). Constraint: write amplification ≤ C19; fsync p99 < C5.

Deliverable

A WAL that survives kill -9 and simulated power loss with correct, ordered replay; group commit meets C5 at C3 throughput; replay reconstructs the exact committed prefix.

Acceptance
  • Power-loss simulation (fixture wal/powerloss-matrix.trace, 1,000 random kill points): 0 committed entries lost (RPO=0, C12/I10), 0 gaps (I3).
  • Group-commit fdatasync p99 < 3 ms on NVMe at 25,000 entries/s (C5/C3); wal_fsync_seconds p99 recorded.
  • Cold replay of 1,000,000 entries < 15 s (C8); wal_replay_seconds < 15.
  • Write amplification ≤ 1.5× (C19) measured over a 10 GiB workload.
  • Every torn/corrupt record is quarantined, never applied (I15); wal/corrupt-crc.bin → CorruptWal.
Fixtures
Fixture Purpose Expected output
wal/powerloss-matrix.trace 1000 kill points RPO=0, no gap
wal/corrupt-crc.bin (malformed) flipped byte CorruptWal, quarantine
wal/short-tail.bin (malformed) torn last record truncate tail, replay clean
wal/replay-1M.trace (regression) replay budget < 15 s
wal/disk-full.trace ENOSPC on append fail-closed, step down
Pitfalls
  • fsync-batching bug acks before the batch actually synced → silent data loss on crash (I10) — root cause: acking on enqueue not on sync-return; detect via power-loss fixture; the worst possible bug (P8).
  • Silent truncation misread as EOF → losing committed entries — distinguish torn tail (uncommitted, safe to drop) from a hole before commit index (corruption, fail-closed).
  • fdatasync not syncing the directory entry on file create → segment lost on crash — fsync the parent dir on rotation.

⬜ Phase 3 — Raft Replication & Leader Election Core §15

Objectives

Implement the heart: terms, RequestVote with randomized election timeouts (MM3), AppendEntries with the log-matching consistency check (I6), commit-index advancement over durable quorum (I10), and role transitions — yielding one stable leader per term (I4) across a 3-node cluster. Constraints: all Raft safety properties I4–I8.

Deliverable

A 3-node cluster that elects a stable leader, replicates entries to a durable quorum, tolerates a follower crash with no leadership change, and re-elects within C18 bounds on leader loss — all reproducible in the sim-harness.

Acceptance
  • Election Safety (I4): across 100,000 randomized sim seeds, leaders_per_term ≤ 1 always (fixture raft/dual-candidate.trace).
  • Leader Completeness (I7): every committed entry survives every re-election (fixture raft/completeness.trace, 0 completeness_violation_total).
  • Failover: leader kill → new leader serving within 2 s typical, < 3 election timeouts worst case (M13, raft/failover.trace).
  • Log matching (I6): partition-heal converges logs identically on all nodes (apply-hash match, I8).
  • Split-vote convergence within 3 election rounds under a symmetric 2-candidate race (fixture raft/split-vote.trace).
Fixtures
Fixture Purpose Expected output
raft/dual-candidate.trace simultaneous candidates ≤ 1 leader/term
raft/split-vote.trace (regression) symmetric race converge ≤ 3 rounds
raft/network-partition.trace minority/majority split majority elects, minority blocks
raft/stale-term.bin (malformed) old-term message rejected, term_regression_total guarded
raft/failover.trace leader crash new leader < 2 s
raft/completeness.trace commit survives re-election 0 violations
Pitfalls
  • Election storms from too-tight or un-randomized timeouts (Howard 2015) → perpetual re-election (MM3, FM-8) — randomize [150,300] ms; detect via leader_changes_total rate.
  • Committing an entry from a previous term by count alone (Raft paper, sec. 5.4.2 bug) → violates I7 — only commit current-term entries directly; detect in raft/completeness.trace.
  • Persisting voted_for after replying to a vote → double vote after crash (I4) — persist before reply (I14).
  • Truncating committed entries on a spurious conflict → data loss (I5) — never truncate at/below commit index.
  • A rejoining partitioned node bumping its term and disrupting a healthy leader → needless failover (FM-8) — pre-vote gate (§15.2) prevents it; detect via pre_vote_reject_total.
  • Answering a linearizable read from a leader that was silently deposed → stale read — read-index barrier confirms leadership before replying (§15.2, MM9).

⬜ Phase 4 — Failure Detection & Cluster Membership §16

Objectives

Add the phi-accrual failure detector (ADR-08, MM6) driving election triggers with damped false positives, and single-server membership changes (ADR-21) that preserve quorum intersection (I11, P13). Constraint: detection false-positive rate low enough to keep failover under M13 without flapping (FM-8/FM-13).

Deliverable

A cluster that detects a hung/dead peer within a tunable window without flapping under a 2 s GC pause, and that grows 3→5 and shrinks 5→3 online while continuously serving, never creating disjoint quorums.

Acceptance
  • Under an injected 2 s scheduler pause (FM-13), phi threshold 8 yields 0 spurious leader changes (fixture fd/gc-pause.trace).
  • Detection latency: a truly dead peer is suspected within ≤ 1.5 × election timeout (fixture fd/dead-peer.trace).
  • Membership: 3→5→3 reconfiguration completes with 0 unsafe_reconfig_total and continuous availability (fixture membership/grow-shrink.trace).
  • Learner catch-up completes before promotion; no committed entry is missing post-promotion (I7/I11).
Fixtures
Fixture Purpose Expected output
fd/gc-pause.trace 2 s STW pause 0 spurious failovers
fd/dead-peer.trace hard peer death suspected ≤ 1.5× timeout
fd/flapping-link.trace (regression) intermittent link damped, no storm
membership/grow-shrink.trace 3→5→3 online 0 unsafe_reconfig
membership/even-size.bin (malformed) reconfig to even size rejected/override-gated
Pitfalls
  • Fixed-timeout detector flapping under GC/scheduler pauses (FM-13) — phi-accrual's continuous suspicion is the fix (MM6); detect via false_positive_total.
  • Adding two voters "at once" via two quick single changes without waiting for commit → transient disjoint quorum (I11) — serialize: one change commits before the next is proposed (P13).
  • Promoting a learner before it has caught up → a leader missing committed entries (I7) — gate promotion on match-index ≥ commit.
  • Removing the current leader — trigger a step-down first, then remove.

⬜ Phase 5 — Lease Coordination & Fencing Engine §17

Objectives

Build the client-facing product: the lease FSM (§8), fence-token allocation from committed indices (I2, ADR-10), renewal/expiry with the safe-TTL floor (C15), session liveness, and duplicate-request suppression — so a client acquires renewable, fenced leadership over a group with no dual-owner window (I1, P9). Constraint: safe TTL derived, never wall-clock-trusted (P11, MM5).

Deliverable

Clients acquire a lease + fence token, renew it, and on leader failover the new leader issues a strictly higher fence token while the old owner's stale token is rejected downstream — demonstrated end-to-end with a fencing consumer.

Acceptance
  • Dual-owner safety (I1): across 100,000 partition/skew seeds, never two Active leases per group (fixture lease/dual-owner.trace, 0 dual_owner_violation_total).
  • Fence monotonicity (I2): fence tokens strictly increase across every failover (fixture lease/fence-monotonic.trace, 0 fence_regression_total).
  • Under 100 ms injected clock skew (C16) leases remain safe (no premature grant) with TTL ≥ 250 ms (C15), fixture lease/skew-safety.trace.
  • Acquire latency p50 < 5 ms, p99 < 75 ms at 25,000 ops/s (M1/M2/M4, C3/C4).
  • Zombie writer rejected: lease/zombie-fence.trace shows a stale-token mutation refused (StaleFenceToken).
Fixtures
Fixture Purpose Expected output
lease/dual-owner.trace partition + skew 0 dual owners
lease/fence-monotonic.trace failover chain strictly increasing tokens
lease/skew-safety.trace (regression) 100 ms skew no premature grant
lease/zombie-fence.trace stale writer StaleFenceToken reject
lease/dup-acquire.bin (replay) retried request-id idempotent, one grant
lease/negative-ttl.bin (malformed) ttl<1 or >600k InvalidRequest
Pitfalls
  • Trusting wall-clock TTL for safety → skew grants two leaders (MM5, P11) — use monotonic clock + 2·RTT+fsync+drift floor (C15). Real class: Kubernetes leaderelection flapping when RenewDeadline is set below round-trip+skew (FM-8, client-go lesson §5).
  • A lock without a fence token → zombie writer corrupts downstream (MM2, Kleppmann DDIA Ch 8) — fencing mandatory (P7, I2).
  • Renewing across a leader change without re-checking the fence → renewing a lease you no longer own — bind renewal to the exact fence (I2).
  • Stale cache read of lease state on a follower answering a read — route ownership reads through the leader or a read-index barrier.

⬜ Phase 6 — Snapshotting & Log Compaction §18

Objectives

Bound WAL growth and recovery time by capturing applied state to a chunked snapshot with a checksummed manifest, installing it atomically (I12), and truncating the log prefix — meeting C9 recovery and enabling learner catch-up (Phase 4). Constraint: snapshot + remaining log compose to the exact state (MM8), no off-by-one at the boundary.

Deliverable

A node that recovers a 1 GiB state from snapshot + tail within C9, and a lagging follower that catches up via InstallSnapshot when it has fallen behind the leader's compacted prefix.

Acceptance
  • Snapshot-based recovery of a 1 GiB snapshot < 60 s (C9/M7), fixture snapshot/recover-1gib.trace.
  • Atomic install (I12): an interrupted install (kill mid-transfer) leaves prior state intact, 0 partial applies (fixture snapshot/interrupted-install.trace).
  • Boundary correctness (MM8): snapshot@N + log(N+1..) equals full-replay state (apply-hash match, I8) across 10,000 seeds (snapshot/boundary.trace).
  • Corrupt snapshot rejected (checksum, I12): snapshot/corrupt.bin → SnapshotRejected, fallback to log replay.
Fixtures
Fixture Purpose Expected output
snapshot/recover-1gib.trace recovery budget < 60 s
snapshot/interrupted-install.trace kill mid-install prior state intact
snapshot/boundary.trace (regression) off-by-one apply-hash match
snapshot/corrupt.bin (malformed) bad checksum SnapshotRejected
snapshot/wal-mismatch.trace snapshot ahead of log reconcile via leader
Pitfalls
  • Snapshot/WAL index mismatch (truncate too much/little) → replay gap or double-apply (MM8, I3) — assert snapshot.last_index == truncation point; the boundary.trace fixture guards this.
  • Capturing state while the apply loop mutates it → torn snapshot — copy-on-write or apply-loop-consistent read.
  • Installing a snapshot older than the follower's applied state → regressing state — reject if manifest.last_index < last_applied.
  • Non-atomic rename (write-in-place) crash → half-installed snapshot (I12) — temp + fsync + rename + dir fsync.

⬜ Phase 7 — Watch Streams & Event Delivery §19

Objectives

Deliver ownership-change notifications to up to 200,000 concurrent subscribers (C6) with bounded per-watch memory (P4), backpressure that evicts slow consumers rather than OOMing (P5, FM-10), and cursor-based replay after reconnect. Constraint: fan-out delay p99 < C14 at C6 fan-out.

Deliverable

An electiond that fans an ownership change to 200,000 watchers within 500 ms while capping memory at C7, evicting only the consumers that cannot keep up, and correctly resuming reconnecting clients by cursor.

Acceptance
  • 200,000 concurrent watchers supported at ≤ 8 GiB/node (C6/C7/M10), fixture watch/200k-fanout.trace.
  • Fan-out delivery p99 < 500 ms at C6 (C14/M8), watch_fanout_seconds p99 recorded.
  • A slow consumer is evicted with bounded broker memory (P4), never causing OOM (fixture watch/slow-consumer.trace); other watchers unaffected.
  • Reconnect from a live cursor replays missed events exactly once; a compacted cursor returns "must resync" (fixture watch/cursor-resume.trace).
Fixtures
Fixture Purpose Expected output
watch/200k-fanout.trace scale + latency p99 < 500 ms, ≤ 8 GiB
watch/slow-consumer.trace (regression) backpressure evicted, bounded mem
watch/cursor-resume.trace reconnect replay exactly-once from cursor
watch/compacted-cursor.bin (malformed) cursor past snapshot "must resync"
watch/dropped-conn.trace mid-stream drop clean resume
Pitfalls
  • Unbounded per-watch buffers → OOM under fan-out (P4, FM-10) — this is the exact early-etcd bug (§5); bound + evict.
  • Head-of-line blocking: one slow watcher stalling a shared stream — isolate per-watch queues, evict independently.
  • Duplicate delivery on reconnect without a cursor — cursor + revision dedupe (exactly-once from the client's view).
  • Cursor pointing past a compaction boundary (Phase 6) — return resync, don't silently skip events.

⬜ Phase 8 — Security, Identity & Authorization §20

Objectives

Enforce that only mTLS-authenticated peers replicate (P14, T5) and only authorized identities acquire/renew (T13), with certificate rotation, per-group authorization, and audit logging. Constraint: an unauthenticated or unauthorized request is rejected before it reaches consensus (§3 trust boundary).

Deliverable

A cluster where a node without a valid cluster cert cannot join or vote (T13), an unauthorized client cannot acquire a group, and certificates rotate online without a leadership change.

Acceptance
  • Unauthorized acquire denied 100% (fixture sec/unauthorized-acquire.trace), authz_denied_total increments.
  • A peer with an expired/invalid cert cannot replicate or vote (T5/T13), fixture sec/rogue-node.trace.
  • Cert rotation completes with 0 leadership changes and 0 dropped quorum (fixture sec/cert-rotation.trace).
  • cert_expiry_seconds alerts fire ≥ 14 days before expiry (fixture sec/expiry-alert.trace).
Fixtures
Fixture Purpose Expected output
sec/unauthorized-acquire.trace ACL deny 100% denied
sec/rogue-node.trace (regression) bad cert peer join/vote refused
sec/cert-rotation.trace online rotation 0 failover
sec/expired-cert.bin (malformed) expired leaf handshake fail
sec/invalid-issuer.bin (malformed) wrong CA rejected
Pitfalls
  • Trust-store drift across nodes during rotation → a node rejects valid peers mid-rotation (T10) — overlap old+new CA; detect via tls_handshake_fail_total spike.
  • Authorizing at the follower instead of before proposal → a denied request still consumes log space — authorize in admission.rs first (P14).
  • Certificate expiry unmonitored → cluster-wide handshake failure (real class: expired-cert outages) — cert_expiry_seconds alert (FM class).
  • Treating identity as authorization — authn (who) and authz (may they) are separate checks.

⬜ Phase 9 — Conformance, Client SDKs & Operational Hardening §21

Objectives

Ship a client SDK with the k8s-leaderelection-compatible lease contract (§5), a full conformance suite tying every fixture to an invariant, chaos/soak testing, and the operational surface (runbooks, dashboards, canary) needed to run in production. Constraint: green conformance + a 72 h soak with 0 safety violations before GA.

Deliverable

A GA-candidate release: SDK + electionctl + conformance suite green, a 72 h soak report with 0 safety violations, and operator runbooks/dashboards for every failure mode (FM-1..FM-13).

Acceptance
  • 100% of conformance fixtures pass in CI; each maps to ≥ 1 invariant (fixture manifest conformance/manifest.json).
  • 72 h soak at 25,000 ops/s (C3) with injected failover every 5 min: 0 dual_owner_violation_total, 0 fence_regression_total, 0 lost commits (C12) — report soak/72h-report.json.
  • Chaos matrix (partition/skew/disk-full/pause/loss) each recover within RTO < 60 s (C11/M11), fixture chaos/matrix.trace.
  • SDK interop: a controller using k8s-style lease semantics fails over correctly with no double-activation (fixture sdk/failover-interop.trace).
