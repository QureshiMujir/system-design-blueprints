198 — Leader Election Service from Scratch

Project Number: 198

Project Name: Leader Election Service from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a self-contained distributed leader election service — daemon electiond plus CLI electionctl — that grants at most one leader per named election group, backed by a from-scratch Raft replicated log, time-bounded leases, and monotonic fencing tokens, so that stateless controllers and stateful failover systems can coordinate exclusive ownership across a 3–7 node cluster with linearizable safety under partition and sub-second failover. The service is a CP coordinator (§30 MM3, P1): it sacrifices availability of the minority partition to preserve single-leader safety, exactly as etcd, ZooKeeper, and Chubby do.

Phase-0 deliverable (numbered modules / crates):

  1. election-core — ownership FSM, lease manager, fencing-token allocator, session registry.
  2. raft-engine — terms, RequestVote, AppendEntries, randomized election timeouts, commit index, membership.
  3. wal — append-only segmented log, CRC framing, group-commit fdatasync, crash-replay scanner.
  4. snapshot — chunked snapshot capture/install, manifest, log truncation.
  5. transport — TLS peer links, length-prefixed protobuf codec, connection pools, bounded flow control.
  6. failure-detector — phi-accrual suspicion estimator + heartbeat sampler.
  7. api — protobuf/gRPC service surface (client + peer wire schemas).
  8. telemetry — Prometheus metrics registry, OpenTelemetry spans, structured JSON logs.
  9. server — electiond daemon wiring all crates.
  10. cli — electionctl operator tool.
  11. sim-harness — deterministic discrete-event simulator (one assertion per invariant, §7).
  12. conformance — protocol/replay/regression fixture runner.

System boundaries. Provides: single-leader election per group, lease grant/renew/release, fencing tokens, ownership watch streams, durable replicated metadata, membership change. Delegates: NTP/clock discipline to the OS; certificate issuance to an external CA/SPIFFE; block-storage durability to the local filesystem; DNS/service discovery to the platform. Does NOT provide: a general KV store, transactions over arbitrary keys, a message queue, a scheduler, cross-region consensus (Phase-deferred), or Byzantine fault tolerance.

Non-goals. Arbitrary multi-key transactions; AP-mode eventual leadership; secondary indexing; a query language; acting as primary system-of-record for application data beyond election metadata.

Deployment model. Odd-sized cluster (3/5/7) on dedicated hosts or Kubernetes StatefulSet, anti-affinity across failure domains, dedicated NVMe volume per node, single region for Phase 0. Linux x86_64 primary target.

Target users / operators. Distributed-scheduler authors, database-failover engineers (Patroni-class), HA control-plane teams, and SREs who today reach for etcd/ZooKeeper leaderelection and need to understand or self-host the mechanism.

What later phases unlock. Failure detection tuning (Phase 4, §16), lease coordination (Phase 5, §17), snapshot-bounded recovery (Phase 6, §18), massive watch fan-out (Phase 7, §19), mTLS identity (Phase 8, §20), and client-SDK/k8s compatibility + chaos hardening (Phase 9, §21).

Recommended language: Rust. Rationale: (a) memory safety without GC removes the STW-pause class that causes false failure-detector positives (§30 MM6, FM-13); (b) ownership/Send+Sync types make the concurrency boundaries of §3 checkable at compile time; (c) tokio gives a mature async runtime for 200k concurrent watch streams (C6); (d) deterministic control over allocation supports the replay simulator (P2). Rejected languages: Go — GC pauses jeopardize tight lease/heartbeat budgets (C15, C18) and the runtime hides scheduling from the deterministic simulator; C++ — no borrow checker, higher memory-safety incident rate for a safety-critical coordinator; Java — JVM warm-up and GC conflict with C8/C11 recovery budgets (ZooKeeper pays this tax).

Prerequisites. Consensus theory (Raft/Paxos), unreliable failure detectors, the FLP/CAP results, WAL and crash-recovery mechanics, TCP/TLS internals, async runtimes, and structured observability.

Deferred features (all registered in §35): WAN/geo replication PhaseDeferred("§34"); witness/arbiter nodes PhaseDeferred("§29"); hierarchical elections PhaseDeferred("§29"); multi-tenant quota isolation PhaseDeferred("§24"); pluggable storage engine PhaseDeferred("§9"); Kubernetes CRD operator PhaseDeferred("§21"); Byzantine fault tolerance PhaseDeferred("§22"); hardware-clock (TrueTime-style) external consistency PhaseDeferred("§9").

Timeline. Phase 0: 3–4 weeks. Phases 1–9 core: ~5 months. Operational hardening + soak: +2 months. Deferred WAN work: +4–6 months (out of scope here).

2. Why Build This

  • Unique systems knowledge. Leader election is the atom beneath every HA control plane; building it exposes the exact seam where safety (at most one leader) and liveness (eventually a leader) trade against each other — the FLP boundary made concrete.
  • Consensus internals. You implement Raft's five safety properties (I4–I8) rather than importing them, so the meaning of term, commit, and quorum overlap stops being folklore.
  • The fencing lesson. You learn viscerally why a distributed lock without a fencing token is unsafe (§30 MM2, Kleppmann DDIA Ch 8) — the single most common production data-corruption bug in lock services.
  • Time discipline. You learn to treat the clock as a liveness device only (P11, MM5): leases are safe under bounded drift, unsafe the moment wall-clock is load-bearing.
  • Failure detection as probability. Phi-accrual (Hayashibara 2004) teaches suspicion as a continuous signal, not a boolean timeout — the fix for GC-pause flapping (FM-13).
  • Architectural significance. etcd, ZooKeeper, Chubby, Consul, and Kubernetes leaderelection are all specializations of what you build here; after this, their docs read as configuration of a machine you understand.
  • Engineering muscles. WAL crash-safety, deterministic replay simulation, quorum reasoning, bounded-queue backpressure, mTLS peer identity, tail-latency budgeting.
  • Cross-links (by name). Sibling systems in this portfolio: a WAL storage engine (§14 reuses its fsync discipline), a gossip membership service (SWIM, contrasted in ADR-08), a distributed KV store (etcd-class, the natural consumer), and a service mesh control plane (a canonical client).
  • Calibration value. After this you can bound why an election takes as long as it does, why a lease TTL must exceed 2·RTT + fsync + drift, and why an even-sized cluster is a latent split-brain (MM4).

What Mastery Looks Like

  • Quorum reasoning — you can prove at most one leader per term from majority intersection alone (Phase 3, §15; I4/I11).
  • Fencing fluency — you can place a monotonic epoch check at every mutation boundary and explain the corruption it prevents (Phase 5, §17; MM2).
  • Time-safety instinct — you never let wall-clock decide safety, only liveness, and can size a lease TTL from first principles (Phase 5, §17; §32).
  • Failure-detector tuning — you can trade phi threshold against false-positive election storms (Phase 4, §16; FM-8/FM-13).
  • Crash-recovery command — you can reason about torn writes, replay ordering, and snapshot/log composition off-by-ones (Phase 2/6, §14/§18; I15/I12).
  • Backpressure design — you can bound every queue and shed load before OOM at 200k watchers (Phase 7, §19; P4/P5).
  • Operational readiness — you can drive a failover runbook and read the telemetry that proves single-leader safety held (Phase 9, §21; §24).

  • api — authenticated admission, protobuf validation, per-request authz, transport-independent routing to the core; enforces the ingress backpressure invariant (P5, I-bounded) before any request reaches consensus.
  • election-core — the ownership state machine: lease lifecycle (Pending→Active→Expiring→Revoked/Expired), fencing-token allocation from the committed (term,index) (I2), session liveness, and the watch broker that fans ownership changes to subscribers.
  • raft-engine — replicated log and election: term tracking, RequestVote with randomized timeouts (MM3), AppendEntries heartbeats, commit-index advancement, single-server membership change (ADR-21); consumes suspicion from the failure detector.
  • failure-detector — phi-accrual estimator over heartbeat inter-arrival times; emits a continuous suspicion level, not a boolean, damping false positives from scheduler pauses (MM6, FM-13).
  • wal — append-only segmented log with per-entry CRC32C, group-commit fdatasync, torn-write detection, and ordered crash replay (I3/I15).
  • snapshot — captures applied state to a chunked artifact with a checksummed manifest, installs atomically (I12), and truncates the WAL prefix.
  • transport — TLS-authenticated peer links, length-prefixed protobuf frames, bounded inflight windows, retry/backoff, and peer-health signals feeding the detector.
  • telemetry — one metrics registry, span exporter, and JSON logger; every state transition in every box emits a signal (P6).

End-to-end acquire data flow (one trace across the boundaries above). (1) client → api: ACQUIRE(group,session,ttl) over mTLS; admission validates + authorizes, admits into the bounded ingress queue or sheds (P5). (2) api → election-core: routed to the leader (or NotLeader redirect). (3) election-core → raft-engine: proposes a replicated command. (4) raft-engine → wal + peers: appends locally, ships AppendEntries; each of a quorum fdatasyncs (I10, P8). (5) raft-engine commit-index advances; the apply loop applies in index order (I3). (6) election-core grants the lease, allocates fence_token = commit_index (I2), and hands the result back. (7) election-core → watch broker: emits ownership-changed to subscribers (§19). (8) api → client: {fence_token, expiry}. Every hop emits a span under one trace id; the whole acquire is one flame.

6. Design Principles

  • P1 — Safety over liveness (CP by construction). Rule: never acknowledge an ownership decision that a future leader could contradict; block rather than risk two leaders. Tradeoff: minority partitions lose availability (Gilbert–Lynch CAP). Operational implication: alerts distinguish "no quorum" (expected under partition) from "corruption" (never expected). Violating it: split-brain double-writes.
  • P2 — Determinism & replayability. Rule: every replicated decision is a pure function of (committed log, snapshot); all nondeterminism (time, randomness, IO order) is injected. Tradeoff: no ambient Instant::now() in the apply loop. Implication: the sim-harness can replay any incident bit-for-bit. Violating it: unreproducible consensus bugs.
  • P3 — Crash-only design. Rule: the only shutdown path is "process dies"; there is no clean-shutdown fast path that recovery does not also cover. Tradeoff: every write is crash-tested. Implication: kill -9 is a supported operation. Violating it: recovery paths that only run in tests rot.
  • P4 — Bounded everything. Rule: every buffer, queue, watch set, and inflight window has a compile-time or config ceiling (C6, C13, C20). Tradeoff: reject rather than absorb. Implication: memory is provably capped at C7. Violating it: OOM under fan-out (etcd's early watch bug).
  • P5 — Backpressure at every boundary. Rule: a full bounded queue sheds load with BackpressureExceeded, never blocks the apply loop or grows unboundedly. Tradeoff: clients must retry. Implication: latency degrades gracefully, not catastrophically. Violating it: head-of-line stall cascades into false failure detection.
  • P6 — Observability-first. Rule: every FSM transition, vote, commit, lease event, and rejection emits a metric/span/log with the causal (group, term, fence_token). Tradeoff: telemetry cost budgeted (M9). Implication: on-call can prove safety from dashboards. Violating it: unexplainable failovers.
  • P7 — Fencing is mandatory. Rule: every state mutation carries a fence token; a stale token is rejected regardless of who sent it (I2). Tradeoff: downstream consumers must check tokens. Implication: a zombie ex-leader cannot corrupt state. Violating it: the classic lock-service data-corruption bug (MM2).
  • P8 — Durability before acknowledgment. Rule: a client success returns only after the entry is fdatasync'd on a quorum (I10). Tradeoff: latency floored by C5 + RTT. Implication: RPO = 0 (C12). Violating it: acknowledged leadership lost on failover.
  • P9 — Fail closed under uncertainty. Rule: a leader that cannot confirm quorum contact within its lease steps down and revokes locally before the lease can be re-granted (I13, P11). Tradeoff: brief unavailability on network blips. Implication: no two nodes believe themselves leader simultaneously. Violating it: dual-leader window.
  • P10 — Monotonic epochs for ownership. Rule: ownership transfer strictly increases the fence token; tokens never repeat or regress (I2). Tradeoff: token is 64-bit, effectively inexhaustible. Implication: total order on leadership. Violating it: ABA on ownership.
  • P11 — Clock is a liveness device, never a safety device. Rule: wall-clock never decides whether something is safe, only when to attempt liveness (elect, expire). Safety uses term/index order (MM5). Tradeoff: lease TTL must absorb drift (C15/C16). Violating it: skew grants two leaders.
  • P12 — Wire & storage forward-compatibility. Rule: protobuf fields are add-only; WAL/snapshot records are versioned and self-describing (ADR-04). Tradeoff: no field reuse ever. Implication: N-1 rolling upgrades (§25). Violating it: a mixed-version cluster corrupts state.
  • P13 — Quorum intersection on every reconfiguration. Rule: change membership one voter at a time so old and new majorities always intersect (ADR-21, I11). Tradeoff: multi-node changes are serialized. Implication: no reconfiguration can create disjoint quorums. Violating it: two independent majorities → two leaders (MM4).
  • P14 — Explicit trust boundaries. Rule: only mTLS-authenticated peers replicate; only authorized identities acquire (T5/T10). Tradeoff: PKI operational burden. Implication: a rogue host cannot join or vote (T13). Violating it: forged-vote split-brain.
  • P15 — Minimize coordination. Rule: the common path (renew an already-held lease) touches only the leader and a quorum append; no cross-group locks. Tradeoff: cross-group atomicity unsupported (non-goal). Implication: groups scale independently (§29). Violating it: a global lock bottleneck.

Debugging methodology. The sim-harness (§12, Phase 0) is a deterministic discrete-event simulator with an injected clock, network, and disk. The method:

  1. Each invariant I1–I15 has exactly one runtime assertion compiled in debug/sim builds; the assertion names the invariant it guards.
  2. The harness drives random schedules from a seed: partitions, delays, drops, reorders, crashes, clock skew, torn writes — the full fault space (§26).
  3. On any assertion failure it captures (seed, step) and the full event list.
  4. The trace-minimizer (§12.2) delta-debugs the event list to the smallest sequence that still fails.
  5. The minimized trace replays bit-for-bit (P2) on any machine, so a consensus bug is reproduced deterministically before a fix and used as a regression fixture (N.5) after.

The trace is the primary forensic artifact for every consensus bug; production incidents are reproduced by feeding the captured schedule back into the same simulator.

Worked example (acquire, happy path). Client → leader ACQUIRE(group=A, session=S, ttl=5000); leader appends entry at (term=7,index=42), replicates to a quorum, each fdatasyncs (I10); commit index advances to 42; apply loop grants Lease{owner=S, fence_token=42, expiry=now_mono+5000ms} and emits ownership-changed to watchers; leader returns {fence_token:42, expiry}. The client stamps every downstream mutation with 42.

Failure-path example (fenced zombie). Leader L1 (fence 42) is partitioned; its lease expires; a quorum in the majority elects L2 (term 8), grants ACQUIRE at index 57 → fence 57. L1 reconnects still believing it holds the lock and issues a mutation stamped 42 to a downstream store; the store rejects it because 42 < 57 (I2, P7). No corruption. Telemetry: fence_regression_total{group=A} increments on the store side.

Read consistency model. Three read levels: (a) linearizable — routed through the leader with a read-index barrier (§15.2), sees all committed state; (b) serializable — served by any node from its applied state, may lag; (c) bounded-stale — a follower read tagged with its commit_index so the client can reject reads older than a bound. Ownership/leadership queries default to linearizable (safety), watch bootstraps to serializable (throughput).

Idempotency & dedup. Every mutating request carries (session_id, request_id); the leader keeps a bounded per-session dedup cache keyed by request_id, so a client retry after an ambiguous timeout (network drop between commit and ack) returns the original result rather than re-acquiring. The cache is itself part of the replicated state (survives failover), bounded per session (P4).

Revision semantics. Each group carries a monotonic revision bumped on every committed change; watch cursors and bounded-stale reads use it. revision is per-group (not global) so groups scale independently (P15); it is distinct from the cluster-wide commit_index (which sources fence tokens, ADR-10).

Worked example (renewal across leader change). Owner S holds fence=42 on group A with expiry=T+5s. At T+3s leader L1 fails; L2 wins term 8. S's SDK retries RENEW(group=A, fence=42) at L2; L2 checks the committed ElectionRecord for A, sees owner S still valid (not yet expired per the committed expiry, evaluated on L2's monotonic clock offset from the record, P11), and commits a renew extending expiry — keeping the same fence 42 because ownership did not change hands (I2 is monotone, not strictly-increasing-per-renew). Had S's lease expired first, L2 would have granted a fresh acquire to a competitor with fence ≥ 57.

Malformed / adversarial inputs (all rejected, telemetry emitted). Negative or > 600 s TTL; fence-token rollback (I2); RENEW with a fence not matching the active lease; duplicate request-id (idempotency dedupe); AppendEntries with prev_log_term mismatch (I6 → AppendEntriesResp.success=false with conflict hints); log entry payload > C20 (1 MiB); protobuf with unknown required semantics or nesting depth > 32 (T7).

12.6 Pitfalls

12.7 Performance Concerns

  • Sim-harness event-queue allocation churn dominates seed throughput — use an arena/slab; target ≥ 10k seeds/min.

  • Tracing span creation on the hot path — use static field sets and sampling so span overhead stays off the acquire latency budget (M1).
  • The metrics registry lookup must be O(1) (pre-registered handles), never a per-emit hashmap lookup.

12.8 Edge Cases

  • Missing entropy source at boot (seed the sim RNG explicitly; never thread_rng in replicated paths).
  • Clock rollback from the injected clock (monotonic only; a decrease is a test bug, asserted).
  • Zero-length and max-length (C20) payloads at the codec boundary.

12.9 Failure Analysis

  • A dropped assertion (invariant hook removed or feature-gated out of the sim build) silently weakens the harness — CI verifies all I1–I15 hooks compile into the sim build.

  • Implement codec.rs: length-prefixed protobuf frames (FrameKind, §11), max frame = C20 + header; reject oversize (ADR-04, P12).
  • Implement pool.rs: per-peer connection pool with a BoundedWindow inflight cap and credit-based flow control (P5, ADR-23); overflow → BackpressureExceeded.
  • Implement retry.rs: exponential backoff with jitter (avoid retry storms, cf. C18) and per-peer circuit state feeding failure-detector (Phase 4).
  • Separate a high-priority control stream (votes/heartbeats) from a bulk stream (log/snapshot shipping) so bulk transfer never delays a heartbeat (§13.6 HOL blocking).
  • Implement buffer pooling on the codec hot path so a frame encode/decode does zero heap allocation at steady state (§13.7).
  • Emit peer RTT histograms and inflight gauges (P6) — feeds C2 verification.

13.3 Deliverable

Two electiond processes exchange authenticated, length-prefixed protobuf messages over TLS with observable RTT and enforced backpressure; a slow peer never grows the sender's memory beyond the window.

13.4 Acceptance Criteria

  • Sustains ≥ 50,000 concurrent framed streams/node with memory ≤ 512 MiB (fixture transport/50k-streams.json).
  • p99 peer RTT < 20 ms on loopback+injected 2 ms (matches C2); histogram exported.
  • Backpressure: with a stalled consumer, sender memory stays ≤ window size (bounded, P4), verified by transport/slow-consumer.trace.
  • Malformed frame (bad length prefix, truncated) rejected without panic; frame_decode_error_total increments.

13.6 Pitfalls

  • Retry storms after a blip synchronize all peers (thundering herd) — jittered backoff; detect via peer_retry_total spike; root cause: un-jittered timers (P5).
  • Connection leaks on half-open sockets — TCP keepalive + idle reaper; detect via peer_conn_open monotonic climb.
  • Head-of-line blocking on a single TCP stream stalling heartbeats — dedicate a high-priority control stream separate from bulk log shipping.

13.7 Performance Concerns

  • Syscall amplification from small frames — coalesce with vectored writes; batch heartbeats.
  • Allocator churn per frame — reuse buffers via a pool; target zero per-frame heap alloc on the hot path.
  • TLS record overhead on tiny heartbeats — 100 ms interval (C18) keeps this negligible (see §32).

13.8 Edge Cases

  • Half-open socket (peer NIC dead, no RST) — detected by keepalive + failure-detector, not by transport alone.
  • Frame split across TCP segments — codec must buffer until length satisfied (bounded by C20).
  • TLS renegotiation mid-stream (disabled in 1.3) — reject legacy renegotiation attempts.
  • Length-prefix claiming a huge frame before body arrives — reject at the prefix if it exceeds C20, before allocating (T7).
  • Peer address change (NAT rebind) mid-connection — treat as a new link; re-authenticate (P14).
  • Simultaneous connect from both peers — deterministic tie-break by lower node_id keeps one link, closes the other.

13.9 Failure Analysis

Transport failure must not collapse consensus: a dead peer link degrades to "suspected" (Phase 4), never to a crash. Blast radius: one peer edge. Detection: peer_up{node} gauge = 0. Recovery: reconnect + backoff. Operator visibility: peer-connectivity panel. Postmortem: correlate peer_retry_total with detector suspicion.

  • A single congested link raising RTT (not down) inflates peer_rtt_seconds and may nudge the detector; the control/bulk stream split (§13.2) keeps heartbeats flowing so a bulk-transfer stall does not look like a dead peer.
  • Backpressure on one peer must never block the apply loop — the sender drops to the bounded window and sheds, isolating the slow edge (P5).

13.10 Operational Notes

  • Metrics: peer_rtt_seconds histogram, peer_up{node}, peer_inflight, frame_decode_error_total, peer_retry_total.
  • Runbook runbooks/peer-connectivity.md: diagnose a flapping or half-open peer link.
  • Alert on peer_up{node}=0 sustained and on frame_decode_error_total (possible version mismatch or attack, T7).
  • Rolling upgrade: transport wire is versioned (P12); N-1 FrameKind values are accepted.

14. Phase 2 — Write-Ahead Log Engine

14.1 Objectives

Provide crash-safe, append-only, ordered durable storage for LogEntry with group-commit fdatasync, CRC integrity (I15), and deterministic replay (I3). This is the durability substrate for Raft commit (P8, I10). Constraint: write amplification ≤ C19; fsync p99 < C5.

14.2 Detailed Implementation Steps

  • Implement wal/segment.rs: fixed-size segment rotation with a monotone base_index; sealed segments are immutable (I5).
  • Implement record.rs: RecordHeader{len,crc32c,kind} framing; CRC32C covers term|index|payload (I15); torn-write detection at replay.
  • Implement sync.rs: group-commit — batch pending appends, one fdatasync per batch (ADR-07); expose batch-size/latency knobs (C5).
  • Implement replay.rs: on boot, scan segments in index order, verify CRC, stop at the first torn/short record and truncate the tail (crash-only, P3); reconstruct RaftState.commit_index lower bound.
  • fsync the parent directory on segment creation/rotation so a crash cannot lose the newly-linked segment file (POSIX gotcha, §14.6).
  • Preallocate segments (fallocate) to avoid metadata fsync per append and to detect ENOSPC eagerly (FM-6).
  • Maintain an in-memory index (index → (segment, offset)) rebuilt on replay for O(1) entry lookup during replication catch-up.
  • Wire durability so Raft (Phase 3) advances commit only after a quorum has fdatasync'd (I10, P8).
  • Emit wal_fsync_seconds, wal_replay_seconds, wal_crc_error_total, wal_amplification_ratio, wal_group_commit_batch.

14.3 Deliverable

A WAL that survives kill -9 and simulated power loss with correct, ordered replay; group commit meets C5 at C3 throughput; replay reconstructs the exact committed prefix.

14.4 Acceptance Criteria

  • Power-loss simulation (fixture wal/powerloss-matrix.trace, 1,000 random kill points): 0 committed entries lost (RPO=0, C12/I10), 0 gaps (I3).
  • Group-commit fdatasync p99 < 3 ms on NVMe at 25,000 entries/s (C5/C3); wal_fsync_seconds p99 recorded.
  • Cold replay of 1,000,000 entries < 15 s (C8); wal_replay_seconds < 15.
  • Write amplification ≤ 1.5× (C19) measured over a 10 GiB workload.
  • Every torn/corrupt record is quarantined, never applied (I15); wal/corrupt-crc.bin → CorruptWal.

14.5 Conformance Fixtures

Fixture Purpose Expected output

wal/corrupt-crc.bin (malformed) flipped byte CorruptWal, quarantine
wal/short-tail.bin (malformed) torn last record truncate tail, replay clean
wal/replay-1M.trace (regression) replay budget < 15 s
wal/disk-full.trace ENOSPC on append fail-closed, step down

14.6 Pitfalls

  • fsync-batching bug acks before the batch actually synced → silent data loss on crash (I10) — root cause: acking on enqueue not on sync-return; detect via power-loss fixture; the worst possible bug (P8).
  • Silent truncation misread as EOF → losing committed entries — distinguish torn tail (uncommitted, safe to drop) from a hole before commit index (corruption, fail-closed).
  • fdatasync not syncing the directory entry on file create → segment lost on crash — fsync the parent dir on rotation.

14.7 Performance Concerns

  • Page-cache pressure from large segments — advise posix_fadvise(DONTNEED) on sealed segments.
  • Write amplification from over-small batches — tune group_commit_bytes to keep C19 ≤ 1.5×.
  • fsync serialization as the throughput ceiling — group commit amortizes; see §32 batch-size derivation.

14.8 Edge Cases

  • Disk full (ENOSPC) mid-append — fail closed, step down leadership (P9), do not partially write.
  • Delayed/reordered flush on some filesystems — rely only on fdatasync return, never write-order.
  • Segment boundary exactly at a commit — replay must stitch across segments without a gap (I3).
  • A zero-length or truncated final segment after crash — treated as an empty tail, not corruption.
  • Clock change during a slow fsync — durability uses the fsync return, not elapsed wall-clock (P11).
  • Reopening a WAL written by a newer version — read via versioned RecordHeader.kind (P12) or refuse with a clear error.

14.9 Failure Analysis

WAL corruption is fail-closed (I15, P9): the node quarantines the segment, marks itself non-voting, and refetches from the leader/snapshot (Phase 6). Blast radius: one node. Detection: wal_crc_error_total > 0. Recovery: snapshot install + replay from leader. Forensics: the quarantined segment + CRC report. Long-term: scrub background verification.

14.10 Operational Notes

  • Metrics: wal_fsync_seconds, wal_replay_seconds, wal_amplification_ratio, wal_group_commit_batch, wal_crc_error_total.
  • Runbook runbooks/wal-corruption.md: quarantine a bad segment and recover the node from leader/snapshot.
  • Alert on wal_fsync_seconds p99 breaching C5 (disk degradation → FM-6) and on any wal_crc_error_total (T3/FM-2).
  • Tool tools/wal-inspect dumps segment records and CRCs for forensics.
  • Rolling upgrade: WAL RecordHeader.kind/version is forward-compatible (P12); a newer node reads N-1 records.

15. Phase 3 — Raft Replication & Leader Election Core

15.1 Objectives

Implement the heart: terms, RequestVote with randomized election timeouts (MM3), AppendEntries with the log-matching consistency check (I6), commit-index advancement over durable quorum (I10), and role transitions — yielding one stable leader per term (I4) across a 3-node cluster. Constraints: all Raft safety properties I4–I8.

15.2 Detailed Implementation Steps

  • Implement raft-engine/term.rs: durable current_term/voted_for persisted before any vote reply (I14); one vote per term (I4).
  • Implement election.rs: follower→candidate on election timeout randomized in [150,300] ms (C18) to break split votes (MM3, Howard 2015 tuning); candidate requests votes with the up-to-date-log restriction guaranteeing I7.
  • Implement append.rs: leader heartbeats every 100 ms (C18); AppendEntries prev-log consistency check (I6); follower truncates conflicting suffix (never committed entries, I5).
  • Implement commit.rs: leader advances commit index to the highest index replicated+fdatasync'd on a quorum (I10, P8), then the apply loop applies in order (I3, I8).
  • Implement pre-vote (Raft paper, sec. 9.6): a candidate first probes whether it could win before incrementing its term, so a partitioned node rejoining does not force a term bump and a disruptive election (FM-8).
  • Implement leadership-transfer (TimeoutNow): a leader stepping down for maintenance hands off to a caught-up follower without a timeout-driven gap (§24 rolling upgrade).
  • Implement the read-index / lease-read barrier so linearizable reads do not require a log append: the leader confirms it is still leader via a heartbeat round before answering (MM9).
  • Drive everything through the injected clock/network (P2) so every scenario replays; wire failure-detector suspicion (Phase 4) as an election trigger hint.
  • Emit raft_term, leader_changes_total, election_duration_seconds, commit_index, apply_gap_total, pre_vote_reject_total.

15.3 Deliverable

A 3-node cluster that elects a stable leader, replicates entries to a durable quorum, tolerates a follower crash with no leadership change, and re-elects within C18 bounds on leader loss — all reproducible in the sim-harness.

15.4 Acceptance Criteria

  • Election Safety (I4): across 100,000 randomized sim seeds, leaders_per_term ≤ 1 always (fixture raft/dual-candidate.trace).
  • Leader Completeness (I7): every committed entry survives every re-election (fixture raft/completeness.trace, 0 completeness_violation_total).
  • Failover: leader kill → new leader serving within 2 s typical, < 3 election timeouts worst case (M13, raft/failover.trace).
  • Log matching (I6): partition-heal converges logs identically on all nodes (apply-hash match, I8).
  • Split-vote convergence within 3 election rounds under a symmetric 2-candidate race (fixture raft/split-vote.trace).

15.5 Conformance Fixtures

Fixture Purpose Expected output
raft/dual-candidate.trace simultaneous candidates ≤ 1 leader/term
raft/split-vote.trace (regression) symmetric race converge ≤ 3 rounds
raft/network-partition.trace minority/majority split majority elects, minority blocks
raft/stale-term.bin (malformed) old-term message rejected, term_regression_total guarded
raft/failover.trace leader crash new leader < 2 s
raft/completeness.trace commit survives re-election 0 violations

15.6 Pitfalls

  • Election storms from too-tight or un-randomized timeouts (Howard 2015) → perpetual re-election (MM3, FM-8) — randomize [150,300] ms; detect via leader_changes_total rate.
  • Committing an entry from a previous term by count alone (Raft paper, sec. 5.4.2 bug) → violates I7 — only commit current-term entries directly; detect in raft/completeness.trace.
  • Persisting voted_for after replying to a vote → double vote after crash (I4) — persist before reply (I14).
  • Truncating committed entries on a spurious conflict → data loss (I5) — never truncate at/below commit index.
  • A rejoining partitioned node bumping its term and disrupting a healthy leader → needless failover (FM-8) — pre-vote gate (§15.2) prevents it; detect via pre_vote_reject_total.
  • Answering a linearizable read from a leader that was silently deposed → stale read — read-index barrier confirms leadership before replying (§15.2, MM9).

15.7 Performance Concerns

  • Heartbeat amplification: leader→(n-1) every 100 ms; at n=7, 60 msgs/s (§32) — negligible CPU (M9 < 5%).
  • Lock contention on the single apply loop — keep it lock-free/single-writer; offload IO to the WAL group-committer.
  • Batch AppendEntries to amortize RTT and fsync (P8) — pipeline inflight up to the bounded window (P4).

15.8 Edge Cases

  • Leader crash after append but before commit — new leader may or may not have the entry; client sees NotLeader/timeout and retries idempotently.
  • Two nodes both time out simultaneously — randomized timeout + one-vote-per-term breaks it (I4).
  • Delayed/duplicated AppendEntries from a stale leader — rejected by term (I14) and prev-log check (I6).
  • Message from a future term — step down, adopt term, do not vote against a more up-to-date log.
  • A single node partitioned and repeatedly timing out — pre-vote (§15.2) keeps its term from climbing and disrupting the cluster on rejoin.
  • All entries in a term uncommitted when the leader dies — the next leader may overwrite that suffix; only committed entries are protected (I5/I7).
  • Candidate receiving a valid AppendEntries from a current-term leader — it reverts to follower immediately (one leader per term, I4).

15.9 Failure Analysis

A partition leaves the minority unable to elect (P1: it blocks, does not split). Blast radius: minority partition loses availability, not safety. Detection: QuorumUnavailable + raft_term climbing only on the majority side. Recovery: heal → minority catches up via log/snapshot. Forensics: the seed-replayable trace (§7). Postmortem: verify leaders_per_term ≤ 1 held throughout.

  • A minority that keeps campaigning wastes CPU but cannot win — pre-vote (§15.2) suppresses most of it; pre_vote_reject_total quantifies it.
  • A leader that is CPU-saturated (not dead) stops heartbeating and is failed over — the old leader must observe the new term on rejoin and step down (I14).
  • Log divergence after an unclean partition heal is resolved by the log-matching truncation (I6), never by manual edit.

15.10 Operational Notes

  • Metrics: raft_term, leader_changes_total, election_duration_seconds, commit_index, apply_gap_total, pre_vote_reject_total.
  • Tracing: one span per election and per replication round, tagged with term and leader id.
  • Runbook runbooks/failover.md: how to read a failover trace and confirm leaders_per_term ≤ 1 held.
  • Alert on leader_changes_total rate > threshold (flapping, FM-8) and on apply_gap_total > 0 (page — safety-adjacent).
  • Rolling upgrade: term/vote/append wire is versioned and stable (P12); a mixed-version cluster elects identically.
  • electionctl leader <group> and electionctl transfer-leadership expose/drive leadership for maintenance (§21.2).

16. Phase 4 — Failure Detection & Cluster Membership

16.1 Objectives

Add the phi-accrual failure detector (ADR-08, MM6) driving election triggers with damped false positives, and single-server membership changes (ADR-21) that preserve quorum intersection (I11, P13). Constraint: detection false-positive rate low enough to keep failover under M13 without flapping (FM-8/FM-13).

16.2 Detailed Implementation Steps

  • Implement failure-detector/phi.rs: a sliding window of heartbeat inter-arrival times → a phi suspicion value (Hayashibara 2004, MM6); expose phi_threshold (default 8) tuning false-positive vs detection latency (C18).
  • Feed transport peer-health (Phase 1) and heartbeat arrivals into the estimator; a phi crossing the threshold is a hint to election.rs (Phase 3), never an authoritative "dead" (P1 keeps safety in quorum, not the detector).
  • Implement membership.rs: ADD_NODE/REMOVE_NODE as replicated log entries applied one at a time (ADR-21); a new voter joins as non-voting learner first (catch-up), then is promoted (I11).
  • Guard: reject any reconfiguration that would break majority overlap or make the cluster even-sized without operator override (MM4, I11).
  • Distinguish detector suspicion (soft, triggers a pre-vote probe, §15.2) from lease liveness (hard, drives step-down, I13): the detector never directly revokes leadership — quorum does (P1).
  • Feed suspicion into an adaptive election-timeout hint so a node that already suspects the leader starts its campaign slightly sooner, shortening failover without lowering the floor (M13).
  • Emit phi_suspicion{peer}, false_positive_total (detector said dead, peer alive), membership_change_total, learner_lag.

16.3 Deliverable

A cluster that detects a hung/dead peer within a tunable window without flapping under a 2 s GC pause, and that grows 3→5 and shrinks 5→3 online while continuously serving, never creating disjoint quorums.

16.4 Acceptance Criteria

  • Under an injected 2 s scheduler pause (FM-13), phi threshold 8 yields 0 spurious leader changes (fixture fd/gc-pause.trace).
  • Detection latency: a truly dead peer is suspected within ≤ 1.5 × election timeout (fixture fd/dead-peer.trace).
  • Membership: 3→5→3 reconfiguration completes with 0 unsafe_reconfig_total and continuous availability (fixture membership/grow-shrink.trace).
  • Learner catch-up completes before promotion; no committed entry is missing post-promotion (I7/I11).

16.5 Conformance Fixtures

fd/dead-peer.trace hard peer death suspected ≤ 1.5× timeout
fd/flapping-link.trace (regression) intermittent link damped, no storm

16.6 Pitfalls

  • Fixed-timeout detector flapping under GC/scheduler pauses (FM-13) — phi-accrual's continuous suspicion is the fix (MM6); detect via false_positive_total.
  • Adding two voters "at once" via two quick single changes without waiting for commit → transient disjoint quorum (I11) — serialize: one change commits before the next is proposed (P13).
  • Promoting a learner before it has caught up → a leader missing committed entries (I7) — gate promotion on match-index ≥ commit.
  • Removing the current leader — trigger a step-down first, then remove.

16.7 Performance Concerns

  • Phi computation per heartbeat per peer — O(window) with a ring buffer; at n=7 negligible (M9).
  • Learner catch-up floods the leader — throttle snapshot/log shipping via the bounded window (P4).
  • Detector window memory bounded (P4) — fixed ring buffer per peer.

16.8 Edge Cases

  • Asymmetric partition (A sees B, B not A) — detector + one-directional heartbeats; quorum still decides (P1).
  • Clock jump on a peer skewing inter-arrival — phi uses local monotonic arrival times (P11), not peer wall-clock.
  • Reconfiguration during an election — membership entries commit like any other; the current config at each index governs.
  • Removing a node that is itself the current leader — issue a leadership transfer first (§15.2), then remove.
  • A learner that never catches up (too slow) — bounded catch-up deadline; abort promotion and alert rather than block reconfiguration.
  • Cluster shrinking below 3 voters — refuse (loses fault tolerance) unless an explicit single-node override is set for disaster recovery.

16.9 Failure Analysis

A too-sensitive detector causes election storms (FM-8): repeated failover, latency spikes, but never two leaders (I4). Detection: leader_changes_total rate + false_positive_total. Blast radius: cluster-wide latency, not safety. Recovery: raise phi threshold (runbook). Forensics: phi timeline per peer. Long-term: adaptive threshold.

  • Conversely, a threshold set too high delays legitimate failover toward the C11 RTO — tuning trades false-positive rate against detection latency (§16.6), and both extremes are alertable.
  • A partial/asymmetric partition can leave the detector suspicious in one direction only; quorum, not the detector, still decides leadership (P1), so safety is unaffected either way.

16.10 Operational Notes

  • Metrics: phi_suspicion{peer}, false_positive_total, membership_change_total, learner_lag.
  • Runbooks: runbooks/membership.md (grow/shrink safely), runbooks/detector-tuning.md (adjust phi threshold under flapping).
  • Alert on sustained high phi (network degradation) and on any reconfiguration rejection (I11 guard tripped).
  • electionctl member add/remove drives single-server changes with the quorum-overlap guard enforced server-side.
  • Rolling upgrade: membership entries are versioned (P12); mixed versions apply an identical config at each index (MM10).

17. Phase 5 — Lease Coordination & Fencing Engine

17.1 Objectives

Build the client-facing product: the lease FSM (§8), fence-token allocation from committed indices (I2, ADR-10), renewal/expiry with the safe-TTL floor (C15), session liveness, and duplicate-request suppression — so a client acquires renewable, fenced leadership over a group with no dual-owner window (I1, P9). Constraint: safe TTL derived, never wall-clock-trusted (P11, MM5).

17.2 Detailed Implementation Steps

  • Implement election-core/lease.rs: the state machine Pending→Active→Expiring→Revoked/Expired (§8), driven only by committed commands (P2) and the injected monotonic clock (P11).
  • Implement fence.rs: on grant, fence_token = commit_index of the ACQUIRE entry — monotonic by construction (I2, MM2); embed in every mutation the leader authorizes (P7).
  • Implement session.rs: session registry with monotonic renewal; a missed renewal past TTL expires the lease and emits ownership-changed (§19).
  • Enforce the leader lease/step-down rule: a leader that loses quorum contact for longer than its granted lease locally revokes before a new leader can grant (I13, P9) — safe TTL ≥ 2·RTT + fdatasync + drift + margin (§32).
  • Idempotency: dedupe by (session, request_id) so retried ACQUIRE/RENEW do not double-issue.
  • Compute lease expiry as committed_expiry, evaluated against each node's local monotonic clock via the offset captured when the entry applied — never re-read wall-clock (P11); a follower promoted to leader inherits the committed expiry exactly (no extension, I9).
  • Implement observe/ObserveElection: a client can passively watch a group's ownership without contending, backed by the watch broker (§19).
  • Support voluntary release + graceful handoff: RELEASE commits, ownership-changed fires, and the next waiter (if any) is granted with a strictly higher fence (P10).
  • Emit lease_active{group}, lease_renew_total, lease_expired_total, fence_token{group}, fence_regression_total.

17.3 Deliverable

Clients acquire a lease + fence token, renew it, and on leader failover the new leader issues a strictly higher fence token while the old owner's stale token is rejected downstream — demonstrated end-to-end with a fencing consumer.

17.4 Acceptance Criteria

  • Dual-owner safety (I1): across 100,000 partition/skew seeds, never two Active leases per group (fixture lease/dual-owner.trace, 0 dual_owner_violation_total).
  • Fence monotonicity (I2): fence tokens strictly increase across every failover (fixture lease/fence-monotonic.trace, 0 fence_regression_total).
  • Under 100 ms injected clock skew (C16) leases remain safe (no premature grant) with TTL ≥ 250 ms (C15), fixture lease/skew-safety.trace.
  • Acquire latency p50 < 5 ms, p99 < 75 ms at 25,000 ops/s (M1/M2/M4, C3/C4).
  • Zombie writer rejected: lease/zombie-fence.trace shows a stale-token mutation refused (StaleFenceToken).

17.5 Conformance Fixtures

Fixture Purpose Expected output
lease/dual-owner.trace partition + skew 0 dual owners
lease/fence-monotonic.trace failover chain strictly increasing tokens
lease/skew-safety.trace (regression) 100 ms skew no premature grant
lease/zombie-fence.trace stale writer StaleFenceToken reject
lease/dup-acquire.bin (replay) retried request-id idempotent, one grant
lease/negative-ttl.bin (malformed) ttl<1 or >600k InvalidRequest

17.6 Pitfalls

  • Trusting wall-clock TTL for safety → skew grants two leaders (MM5, P11) — use monotonic clock + 2·RTT+fsync+drift floor (C15). Real class: Kubernetes leaderelection flapping when RenewDeadline is set below round-trip+skew (FM-8, client-go lesson §5).
  • A lock without a fence token → zombie writer corrupts downstream (MM2, Kleppmann DDIA Ch 8) — fencing mandatory (P7, I2).
  • Renewing across a leader change without re-checking the fence → renewing a lease you no longer own — bind renewal to the exact fence (I2).
  • Stale cache read of lease state on a follower answering a read — route ownership reads through the leader or a read-index barrier.

17.7 Performance Concerns

  • Expiry scanning all leases each tick is O(groups) — use a min-heap keyed by expiry; wake only for the next expiry.
  • Fence allocation is O(1) (commit index) — no contention (ADR-10).
  • Renewal amortization: a renew is a normal Raft append; batch with other commands to hold M4 (§15.7).

17.8 Edge Cases

  • Client reconnect race: old and new connection both renew — dedupe by (session,request_id); fence disambiguates.
  • Lease expiring exactly at a leader failover — new leader recomputes expiry from the committed record + its monotonic clock (P11); never extends beyond the committed expiry.
  • Renewal arriving after expiry but before revoke apply — treated as a fresh acquire attempt (new fence).
  • Clock skew beyond C16 budget — detector + safety margin; if drift exceeds budget, fail closed (P9).
  • Two clients racing to acquire a free group — Raft serializes the two ACQUIRE entries; the first committed wins, the second sees owner != self and fails.
  • A client whose session expired mid-operation — its next request is rejected LeaseExpired; it must re-acquire (new fence).
  • Very short TTL near the C15 floor under load — renew scheduling must leave margin; SDK warns if TTL < 2× expected RTT (§21.6).

17.9 Failure Analysis

A leader partitioned with an outstanding lease is the split-brain risk (FM-4). Containment: I13 step-down before the lease can be re-granted (P9); fence tokens make any late write harmless (I2). Detection: dual_owner_violation_total (must be 0), fence_regression_total on consumers. Recovery: automatic on heal. Forensics: fence-token timeline. Postmortem: confirm the old token < new token everywhere (Chubby sequencer lesson, §5).

  • The dangerous window is bounded by the lease safe-TTL (C15); a client operation longer than one TTL must renew mid-flight or re-check its fence before committing downstream.
  • If a downstream store does not enforce fencing, the guarantee degrades to at-most-one-acknowledged owner, not at-most-one-acting owner — the SDK documents this loudly (P7).
  • Mass lease expiry after a long quorum outage causes a reconnection stampede — clients use jittered re-acquire (FM-15).

17.10 Operational Notes

  • Metrics: lease_active, lease_renew_total, lease_expired_total, fence_token, dual_owner_violation_total, fence_regression_total.
  • Runbook runbooks/lease-debug.md: reconstruct a group's fence-token timeline and confirm strict ordering across failovers.
  • Client SDK contract (Phase 9) mirrors k8s LeaseDuration/RenewDeadline semantics (§5) with safe defaults (≥ C15).
  • Alert on any dual_owner_violation_total > 0 or fence_regression_total > 0 — page immediately (safety breach, §24 P0 playbook).

18. Phase 6 — Snapshotting & Log Compaction

18.1 Objectives

Bound WAL growth and recovery time by capturing applied state to a chunked snapshot with a checksummed manifest, installing it atomically (I12), and truncating the log prefix — meeting C9 recovery and enabling learner catch-up (Phase 4). Constraint: snapshot + remaining log compose to the exact state (MM8), no off-by-one at the boundary.

18.2 Detailed Implementation Steps

  • Implement snapshot/capture.rs: serialize the applied ElectionRecord map + MembershipConfig at a chosen last_index/last_term (Ongaro thesis Ch 5), without blocking the apply loop (copy-on-write snapshot of state).
  • Implement manifest.rs: SnapshotManifest{snapshot_id,last_index,last_term,chunk_count,sha256} (§11); verify sha256 on install (I12).
  • Implement install.rs: leader ships InstallSnapshot chunks to a lagging follower (Phase 1 transport); follower writes to a temp file, verifies checksum, then atomically renames + truncates its log prefix (I12, crash-only P3).
  • Trigger policy: snapshot when the log exceeds a size/entry threshold (e.g. 100k entries, §32 #11), not on a fixed timer, so churn — not wall-clock — drives compaction.
  • Compress chunks with zstd and rate-limit transfer via the bounded window so InstallSnapshot never starves heartbeats (C18).
  • Include the MembershipConfig and dedup cache in the snapshot so a recovered node has complete replicated state, not just ElectionRecords.
  • Truncation: never truncate above the follower's applied index; compose snapshot(last_index) + log(last_index+1..) exactly (MM8, I3).
  • Emit snapshot_last_index, snapshot_install_seconds, snapshot_install_abort_total, snapshot_age_seconds.

18.3 Deliverable

A node that recovers a 1 GiB state from snapshot + tail within C9, and a lagging follower that catches up via InstallSnapshot when it has fallen behind the leader's compacted prefix.

18.4 Acceptance Criteria

  • Snapshot-based recovery of a 1 GiB snapshot < 60 s (C9/M7), fixture snapshot/recover-1gib.trace.
  • Atomic install (I12): an interrupted install (kill mid-transfer) leaves prior state intact, 0 partial applies (fixture snapshot/interrupted-install.trace).
  • Boundary correctness (MM8): snapshot@N + log(N+1..) equals full-replay state (apply-hash match, I8) across 10,000 seeds (snapshot/boundary.trace).
  • Corrupt snapshot rejected (checksum, I12): snapshot/corrupt.bin → SnapshotRejected, fallback to log replay.

Fixture Purpose Expected output

snapshot/boundary.trace (regression) off-by-one apply-hash match
snapshot/corrupt.bin (malformed) bad checksum SnapshotRejected
snapshot/wal-mismatch.trace snapshot ahead of log reconcile via leader

18.6 Pitfalls

  • Snapshot/WAL index mismatch (truncate too much/little) → replay gap or double-apply (MM8, I3) — assert snapshot.last_index == truncation point; the boundary.trace fixture guards this.
  • Capturing state while the apply loop mutates it → torn snapshot — copy-on-write or apply-loop-consistent read.
  • Installing a snapshot older than the follower's applied state → regressing state — reject if manifest.last_index < last_applied.
  • Non-atomic rename (write-in-place) crash → half-installed snapshot (I12) — temp + fsync + rename + dir fsync.

18.7 Performance Concerns

  • IO spike during capture/install — chunk + rate-limit via the bounded window (P4); avoid starving heartbeats (C18).
  • zstd compression of snapshots trades CPU for transfer size — tune to hold C9.
  • Copy-on-write memory doubling for large state — bound by C7; page-in incrementally.

18.8 Edge Cases

  • Follower receiving a snapshot while also receiving AppendEntries past it — apply snapshot first, then the log tail.
  • Partial snapshot transfer then leader change — new leader restarts InstallSnapshot; idempotent by snapshot_id.
  • Snapshot exactly at a membership-change index — the config in the snapshot governs subsequent entries (I11).
  • A snapshot arriving that is older than the receiver's state — rejected (manifest.last_index < last_applied), no regression (§18.6).
  • Disk full during snapshot capture — abort capture, keep the log; retry when space frees (FM-6).
  • Concurrent capture and a large burst of writes — copy-on-write snapshot isolates the reader from ongoing applies.

18.9 Failure Analysis

A snapshot corruption or install abort leaves the follower behind but safe (I12, P9). Blast radius: one follower's availability. Detection: snapshot_install_abort_total > 0, growing learner_lag. Recovery: retry install or fall back to log replay. Forensics: manifest + checksum report. Long-term: periodic snapshot verification scrub.

  • If compaction stalls (snapshot never taken), the log grows unbounded toward the C8 replay budget — the snapshot_age_seconds alert catches this before recovery time blows out.
  • A snapshot taken at a bad boundary is caught by the boundary.trace regression fixture before it can ship (§18.4).

18.10 Operational Notes

  • Metrics: snapshot_last_index, snapshot_install_seconds, snapshot_age_seconds, snapshot_install_abort_total.
  • Runbook runbooks/snapshot-recovery.md: force a snapshot, verify checksum, and drive a lagging node's catch-up.
  • Tool tools/wal-inspect cross-checks the snapshot boundary against the log (guards MM8 off-by-one).
  • Alert on snapshot_age_seconds exceeding the retention target (compaction stalled → log growth → C8 risk).
  • Compatibility: snapshot format is versioned (P12); N-1 install supported for rolling upgrade.
  • electionctl snapshot triggers an on-demand snapshot for backup/export (§24 backup/restore).

19. Phase 7 — Watch Streams & Event Delivery

19.1 Objectives

Deliver ownership-change notifications to up to 200,000 concurrent subscribers (C6) with bounded per-watch memory (P4), backpressure that evicts slow consumers rather than OOMing (P5, FM-10), and cursor-based replay after reconnect. Constraint: fan-out delay p99 < C14 at C6 fan-out.

19.2 Detailed Implementation Steps

  • Implement election-core/watch.rs: a WatchBroker fanning ownership-changed/lease_expiring events keyed by group; each subscriber holds a WatchCursor{group,from_revision} (§11).
  • Bounded per-watch queue (P4); on overflow, the broker drops the slow consumer with a compacted/overrun signal (ZooKeeper herd-effect lesson §5), never blocks the apply loop (P5).
  • Reconnect: a client resumes from its last revision; if the revision was compacted past (snapshot, Phase 6), the broker returns a "must resync" so the client refetches current state.
  • Multiplex many watches over few gRPC/HTTP-2 streams (ADR-05) to stay within the FD budget (C13).
  • Share one serialized WatchEvent buffer (Bytes) across all subscribers of a group so fan-out is one allocation, not N (§32 #6, §19.7).
  • Coalesce rapid ownership churn for far-behind cursors: deliver the latest committed state rather than every intermediate revision (§19.8).
  • Support filtered watches (single group vs prefix) so a client subscribes only to the groups it coordinates, bounding its event rate.
  • Emit watch_active, watch_lag_events{group}, watch_evicted_total, watch_fanout_seconds, watch_coalesced_total.

19.3 Deliverable

An electiond that fans an ownership change to 200,000 watchers within 500 ms while capping memory at C7, evicting only the consumers that cannot keep up, and correctly resuming reconnecting clients by cursor.

19.4 Acceptance Criteria

  • 200,000 concurrent watchers supported at ≤ 8 GiB/node (C6/C7/M10), fixture watch/200k-fanout.trace.
  • Fan-out delivery p99 < 500 ms at C6 (C14/M8), watch_fanout_seconds p99 recorded.
  • A slow consumer is evicted with bounded broker memory (P4), never causing OOM (fixture watch/slow-consumer.trace); other watchers unaffected.
  • Reconnect from a live cursor replays missed events exactly once; a compacted cursor returns "must resync" (fixture watch/cursor-resume.trace).

19.5 Conformance Fixtures

Fixture Purpose Expected output
watch/200k-fanout.trace scale + latency p99 < 500 ms, ≤ 8 GiB
watch/slow-consumer.trace (regression) backpressure evicted, bounded mem
watch/cursor-resume.trace reconnect replay exactly-once from cursor
watch/compacted-cursor.bin (malformed) cursor past snapshot "must resync"
watch/dropped-conn.trace mid-stream drop clean resume

19.6 Pitfalls

  • Unbounded per-watch buffers → OOM under fan-out (P4, FM-10) — this is the exact early-etcd bug (§5); bound + evict.
  • Head-of-line blocking: one slow watcher stalling a shared stream — isolate per-watch queues, evict independently.
  • Duplicate delivery on reconnect without a cursor — cursor + revision dedupe (exactly-once from the client's view).
  • Cursor pointing past a compaction boundary (Phase 6) — return resync, don't silently skip events.

19.7 Performance Concerns

  • Fan-out amplification: one change × 200k watchers — batch by group, share the serialized event buffer across subscribers (zero-copy Bytes).
  • Allocation per event per watcher — reference-counted shared payload; per-watch state is just a cursor + bounded queue (§32 memory derivation).
  • Wakeup storms (thundering herd) on a popular group — coalesce wakeups.

19.8 Edge Cases

  • Watcher subscribing during an in-flight ownership change — deliver from the committed revision, no gap.
  • Client acking slower than events arrive — backpressure evicts (FM-10), telemetry flags it.
  • Group with rapid ownership churn — coalesce to the latest state for far-behind cursors.
  • A watch established against a follower that then loses quorum — the stream reports the disconnect; the client re-establishes against the new leader.
  • Duplicate subscription for the same group from one client — deduplicated to a single broker entry.
  • Revision wrap concerns — revision is u64; at realistic churn it never wraps within the system's lifetime (§32).

19.9 Failure Analysis

Watch subsystem overload degrades to evictions (FM-10), never to apply-loop stall or OOM (P4/P5). Blast radius: slow clients only. Detection: watch_evicted_total rate, watch_lag_events. Recovery: clients reconnect + resync. Forensics: per-watch lag histogram. Long-term: adaptive per-tenant watch quotas (deferred §24).

  • Because per-watch queues are isolated, one slow consumer never blocks another — the failure is contained to the offending client, which is the whole point of the eviction policy.
  • A thundering-herd reconnect after a mass eviction is smoothed by client-side jittered backoff (FM-15) and the per-node watch ceiling (§19.10).

19.10 Operational Notes

  • Metrics: watch_active, watch_lag_events, watch_evicted_total, watch_fanout_seconds, watch_coalesced_total.
  • Runbook runbooks/watch-overload.md: identify and drain a hot group's watcher set.
  • Alert on high eviction rate (clients falling behind) and on watch_fanout_seconds p99 breaching C14.
  • Compatibility: watch is a streaming gRPC, versioned (P12); older clients receive the N-1 event schema.
  • Capacity guard: a per-node watch_active ceiling (C6) rejects new watches with BackpressureExceeded rather than degrading all subscribers.

20. Phase 8 — Security, Identity & Authorization

20.1 Objectives

Enforce that only mTLS-authenticated peers replicate (P14, T5) and only authorized identities acquire/renew (T13), with certificate rotation, per-group authorization, and audit logging. Constraint: an unauthenticated or unauthorized request is rejected before it reaches consensus (§3 trust boundary).

20.2 Detailed Implementation Steps

  • Complete mutual TLS on transport/peer.rs (ADR-14, RFC 8446): both peers present + validate X.509 chains (RFC 5280); pin the cluster CA (P14).
  • Implement client-plane authn in api/admission.rs: mTLS or token identity → SessionId; reject unknown identities (T10).
  • Implement authorization: per-ElectionGroup ACLs (who may acquire) evaluated before proposing (P14); deny → audit log + authz_denied_total.
  • Certificate rotation: hot-reload leaf/CA without dropping quorum; overlap old+new CA during rotation (T10).
  • Audit: every acquire/release/reconfig logged with identity, fence_token, and outcome (P6, structured JSON, ADR-13).
  • Bind peer identity to node_id: a cert's SAN must match the configured node id, so a valid cert for node X cannot impersonate node Y (T13).
  • Bind client identity to SessionId: derive it from the client cert/token, not a client-supplied field, so a client cannot spoof another's session (T8).
  • Rate-limit per identity at the gateway (token bucket, ADR-23) so one client cannot exhaust ingress for others (T1, T11).
  • Emit tls_handshake_fail_total, authz_denied_total, cert_expiry_seconds, ingress_shed_total.

20.3 Deliverable

A cluster where a node without a valid cluster cert cannot join or vote (T13), an unauthorized client cannot acquire a group, and certificates rotate online without a leadership change.

20.4 Acceptance Criteria

  • Unauthorized acquire denied 100% (fixture sec/unauthorized-acquire.trace), authz_denied_total increments.
  • A peer with an expired/invalid cert cannot replicate or vote (T5/T13), fixture sec/rogue-node.trace.
  • Cert rotation completes with 0 leadership changes and 0 dropped quorum (fixture sec/cert-rotation.trace).
  • cert_expiry_seconds alerts fire ≥ 14 days before expiry (fixture sec/expiry-alert.trace).

20.5 Conformance Fixtures

Fixture Purpose Expected output

sec/rogue-node.trace (regression) bad cert peer join/vote refused
sec/cert-rotation.trace online rotation 0 failover

20.6 Pitfalls

  • Trust-store drift across nodes during rotation → a node rejects valid peers mid-rotation (T10) — overlap old+new CA; detect via tls_handshake_fail_total spike.
  • Authorizing at the follower instead of before proposal → a denied request still consumes log space — authorize in admission.rs first (P14).
  • Certificate expiry unmonitored → cluster-wide handshake failure (real class: expired-cert outages) — cert_expiry_seconds alert (FM class).
  • Treating identity as authorization — authn (who) and authz (may they) are separate checks.

20.7 Performance Concerns

  • TLS handshake cost on reconnect — session resumption (1.3 PSK); keep peer links long-lived.
  • Per-request authz lookup — cache ACLs in memory, invalidate on committed ACL change; O(1) hot path.
  • Audit-log volume — structured, sampled for reads, full for mutations (P6).

20.8 Edge Cases

  • Partial cert rotation (some nodes rotated) — old+new CA overlap window covers it (T10).
  • Clock skew affecting cert notBefore/notAfter — allow a bounded skew window (C16) on validation.
  • Revoked cert mid-session — CRL/OCSP check on handshake; long sessions re-validated periodically.
  • A valid cert whose SAN does not match its claimed node_id — rejected as impersonation (T13).
  • ACL change committed while a request is in flight — the config at the request's commit index governs (deterministic).
  • Token/cert with skewed local validation clock — validated with the C16 skew allowance, not strict wall-clock.

20.9 Failure Analysis

An expired or misconfigured CA can cause cluster-wide handshake failure (availability, not safety — P1). Blast radius: whole cluster loses peering. Detection: tls_handshake_fail_total cluster-wide + cert_expiry_seconds < 0. Recovery: emergency cert reissue via runbooks/cert-rotation.md. Forensics: audit log + handshake failure reasons. Long-term: automated cert issuance (SPIFFE, deferred).

20.10 Operational Notes

  • Metrics: tls_handshake_fail_total, authz_denied_total, cert_expiry_seconds, ingress_shed_total.
  • Runbook runbooks/cert-rotation.md: overlap old+new CA and rotate leaves without a leadership change.
  • Audit sink to a tamper-evident (append-only, hash-chained) store for every mutation.
  • Alert on cert_expiry_seconds < 14 d, on authz_denied_total anomalies, and on tls_handshake_fail_total cluster-wide (T5/T10).
  • Compatibility: TLS 1.3 only, no downgrade (P14); ACL schema versioned (P12).

    • Each metric maps to a constraint C# or invariant I#; a metric with no owner is deleted.
  • Tracing (OTel, ADR-12). Spans per acquire, election, replication round, snapshot install; propagate (group, term, fence_token) so a failover is one trace.
  • Structured logging (JSON, ADR-13). Every FSM transition + rejection with causal fields (P6).
  • Dashboards. (1) Safety board: dual_owner_violation_total and fence_regression_total must read 0 — page on any nonzero. (2) Leadership board: term, leader, change rate (FM-8). (3) Durability board: fsync/replay/amplification (C5/C8/C19). (4) Watch board: active/evicted/lag (C6/C14). (5) Security board: handshake fails, cert expiry (T5/T10).
  • Alerting philosophy. Page on safety signals (dual owner, fence regression, apply-hash mismatch) and quorum loss; ticket on degradations (flapping, watch evictions, high phi). Distinguish "no quorum" (expected under partition, P1) from "corruption" (never).
  • SLOs. Availability 99.95% with majority up (C10); acquire p99 < 75 ms (C4); RTO < 60 s (C11); RPO 0 (C12).
  • Incident response. On-call opens the failover trace, confirms leaders_per_term ≤ 1, checks fence monotonicity, follows the matching FM runbook.
  • Runbooks (named). failover.md, quorum-loss.md, wal-corruption.md, snapshot-recovery.md, membership.md, detector-tuning.md, cert-rotation.md, lease-debug.md, watch-overload.md, peer-connectivity.md.
  • Incident-response playbook (safety breach). (1) Page fires on dual_owner_violation_total > 0 or fence_regression_total > 0. (2) Freeze: electionctl puts the affected group into read-only (reject new acquires) to stop further divergence. (3) Capture: dump the seed-replayable trace (§7), fence-token timeline, and per-node raft_term/commit_index. (4) Identify the highest committed fence token — it is authoritative (I2); all lower-token actors are stale. (5) Reconcile downstream: instruct fenced consumers to reject sub-token writes. (6) Root-cause via replay; file into docs/failure-analysis/. A safety breach is always a bug (the honest-quorum model makes it impossible), so it is P0.
  • Incident-response playbook (quorum loss). (1) QuorumUnavailable cluster-wide. (2) Confirm this is expected (majority of nodes/DC down) vs a config error (even-size, FM-12). (3) Do not force a single node to "win" — that is manual split-brain; follow runbooks/quorum-loss.md. (4) Restore enough nodes to form a majority; the cluster self-heals (P1). (5) Only as a last resort use the documented unsafe-recovery tool (reduces the config), accepting possible data loss, with explicit sign-off.
  • Backup/restore. Periodic snapshot export to object storage; restore = install snapshot on a fresh quorum, verify checksum (I12). Backups are tested by a scheduled restore-and-verify job (a backup never verified is not a backup).
  • Deployment topology. Odd-size (3/5/7), anti-affinity across failure domains, dedicated NVMe per node, learners in remote zones (read scaling).
  • Canary / rolling upgrade / rollback / migration. One node at a time, N-1 compat gate (P12, §25); canary a single follower first; rollback = redeploy N-1 binary (wire/storage compatible); migrations are additive schema changes.

25. Compatibility & Versioning

  • Wire compatibility. Protobuf proto3, add-only fields, never reuse a field number (P12, ADR-04); every message carries no removed required semantics. N-1 wire supported so a mixed-version cluster replicates safely during upgrade.
  • Storage compatibility. WAL RecordHeader.kind/version and snapshot manifest version are self-describing; a newer node reads N-1 records/snapshots; a downgrade to N-1 is supported for one minor version (rollback).
  • Schema evolution. ElectionRecord/MembershipConfig evolve by adding optional fields; unknown fields are preserved and re-serialized (P12).
  • API stability. The client gRPC surface (acquire/renew/release/watch) is SemVer-stable within a major version; error codes (ElectionError) are stable (P12).
  • Migration. Additive only in a minor; any breaking storage change ships a one-shot migration tool gated behind a version bump and a snapshot checkpoint.
  • Deprecation policy. A field/RPC is marked deprecated for ≥ 2 minor versions with telemetry (deprecated_field_use_total) before removal in the next major.
  • SemVer policy. MAJOR = wire/storage break; MINOR = additive; PATCH = fixes. Rolling upgrade guaranteed across one MAJOR boundary only via the migration tool; freely within a MAJOR.
  • Rolling-upgrade guarantee. With N-1 compat, upgrade one node at a time keeping quorum; the cluster never runs more than two adjacent versions.
  • Worked upgrade sequence (v1.3 → v1.4, additive). (1) Canary one follower to v1.4; it speaks v1.3 wire, reads v1.3 WAL/snapshots, and emits any new metrics inert. (2) Observe for one soak window: no frame_decode_error_total, no apply_hash_mismatch_total. (3) Upgrade remaining followers one at a time, each rejoining as a learner if it fell behind. (4) Transfer leadership (TimeoutNow, §15.2) to an upgraded node, then upgrade the old leader last — no election gap. (5) Only after all nodes are v1.4 and a version-gate flag is flipped may v1.4 write new optional fields, so a rollback to v1.3 mid-upgrade stays readable (P12).
  • Downgrade. Supported to the immediately prior minor only, and only before the version-gate flag enables new-field writes; past that point, a snapshot checkpoint + one-shot migration is required.

26. Testing & Verification Strategy

  • Unit. Per-crate logic: CRC framing (I15), phi math (MM6), fence monotonicity (I2), codec bounds (T7).
  • Integration. Multi-node clusters (docker-compose) exercising acquire/renew/failover end-to-end.
  • Property-based. proptest over the lease FSM (§8) and log-matching (I6): random command sequences preserve I1/I2/I3.
  • Differential. Compare raft-engine behavior against tikv/raft-rs on identical injected schedules (§5) — divergence is a bug.
  • Fuzzing (cargo-fuzz, ADR-19). Targets: wire_decode (T7), wal_replay (I15), lease_fsm (I1). Nightly smoke in CI, extended corpus offline.
  • Deterministic replay simulation (§7, §12). The primary safety net: 100,000s of seeds, one assertion per invariant I1–I15; every failure minimizes to a replayable seed.
  • Chaos. scripts/chaos.sh: partition, skew (C16), disk-full, pause (FM-13), packet loss against a live cluster (Phase 9).
  • Soak. 72 h at C3 with periodic failover; 0 safety violations gate GA (§21.4).
  • Fault injection. Injected fsync latency/faults (Phase 2), network delay/drop (Phase 1), torn writes (I15).
  • Conformance. conformance/runner.rs runs every phase's N.5 fixtures, each mapped to an invariant (conformance/manifest.json).
  • Performance-regression gating. Criterion benches (ADR-20) gate CI on M1–M13 thresholds (§28); a regression fails the build.

Coverage matrix (invariant → verification technique). I1 (dual-owner) → sim replay + soak; I2 (fence monotonic) → property test + differential; I3/I8 (apply order/hash) → sim + differential vs raft-rs; I4/I7 (election safety/completeness) → sim over 100k seeds; I6 (log matching) → property test; I10 (durability) → power-loss fault injection; I12 (snapshot atomic) → kill-mid-install chaos; I15 (WAL CRC) → fuzz + fault injection. No invariant is left to unit tests alone; each has an adversarial technique.

Test pyramid budget. Unit ~70% of test count (fast, per-PR), integration ~20% (docker-compose, per-PR), sim ~continuous (100k seeds/PR gate, millions nightly), fuzz + chaos + soak nightly/pre-release. CI wall-clock budget: PR gate < 10 min (unit+integration+10k sim seeds); nightly unbounded.

Determinism as a test oracle. Because replicated code is a pure function of (log, snapshot) (P2), the oracle for most tests is "two runs of the same seed produce the same final-state hash"; a mismatch localizes to an un-injected nondeterminism source (§12.6). This is stronger than assertion-only testing: it catches bugs no assertion anticipated.

Every fixture in §12–§21 (N.5) is registered here and mapped to the invariant it guards; a fixture that asserts no invariant is rejected in review (§21.6).

Bottleneck order (measured): (1) WAL fsync (M3, mitigated by group commit), (2) watch fan-out CPU/memory (M8/M10), (3) quorum RTT on acquire latency (C2→M1/M2), (4) serialization on the hot path. Tail-latency budget for M2: RTT (2×C2) + fsync (C5) + queueing < 75 ms.

Allocation analysis. The hot path (acquire→append→replicate→commit→apply) is engineered for zero steady-state heap allocation: frame buffers pooled (§13.2), log entries use Bytes reference-counted slices, the applied state map is pre-sized. Allocation shows up only on group creation and snapshot, off the latency-critical path. dhat/bytehound profiles run in bench.yml.

Lock analysis. The apply loop is single-writer (no lock on state mutation, I3/I8); the only shared locks are the peer-pool map and the metrics registry, both sharded to avoid contention. A contended lock on the apply path is a design bug, caught by lock-contention profiling.

Syscall analysis. Steady-state syscalls per second are dominated by fdatasync (batched, §32 #5) and sendmsg/recvmsg (vectored, batched heartbeats). eBPF syscount gates a regression if per-op syscall count rises. io_uring (the glommio path noted in ADR-02, optional) can cut submission overhead on high-throughput nodes.

Tail-latency method. Report p50/p95/p99/p99.9 histograms, never averages (Gregg §2); the p99.9 acquire tail is dominated by an fsync coinciding with a group-commit boundary and by GC-free scheduling jitter (why Rust, ADR-01). Coordinated-omission is avoided by open-loop load generation in the cluster harness (ADR-20).

29. Scalability Analysis

  • Constant vs grows. Per-acquire cost is O(quorum) messages = O(n) with cluster size n (small, 3–7, C1); it does not grow with the number of groups. Watch fan-out is O(watchers) per change (C6). WAL is O(entries) sequential. Snapshot is O(state size).
  • Named bottlenecks, in order. (1) Single-leader write path: all proposals serialize through one leader's apply loop and its fsync (M3) — the fundamental Raft ceiling. (2) Watch fan-out memory/CPU at C6 (M8/M10). (3) Quorum RTT flooring acquire latency (C2). (4) Log/snapshot IO on recovery (C8/C9).
  • Horizontal scaling. Partition election groups across independent Raft clusters (shards) — groups are independent (P15), so throughput scales linearly with shard count; a routing layer maps group_id → shard. PhaseDeferred("§29") for the automatic sharding/rebalancer.
  • Vertical scaling. NUMA-pin the apply loop and WAL threads (C17); larger group-commit batches for higher fsync throughput (C19 tradeoff); more cores for watch fan-out.
  • Sharding/partitioning. By group_id hash into K Raft clusters; no cross-shard transactions (non-goal). Rebalancing moves whole groups via snapshot handoff.
  • Coordination overhead. Within a shard, single-leader serialization; across shards, zero coordination (independent). This is why the design refuses cross-group atomic operations (P15).
  • Read scaling. Linearizable reads still funnel through the leader (read-index, §15.2); serializable/bounded-stale reads scale out to followers and learners, so read-heavy workloads add learner replicas rather than shards.
  • Watch scaling. Fan-out is the dominant per-node cost at high subscriber counts; shard watchers across nodes by routing a group's watchers to that group's leader/replicas, and cap per-tenant watches (deferred §24).
  • What stays constant. Per-op message count O(n) with small n (C1); fence-token allocation O(1); apply O(1) per entry — none grow with total group count, which is the property that makes sharding linear.
  • Practical ceiling & levers. One Raft group tops out at fsync-bound ~25,000 acquire/s (M4); the lever past it is sharding (linear) and, for geo, WAN multi-leader — PhaseDeferred("§34") (EPaxos-class, ADR-03). Witness/arbiter nodes reduce quorum cost in 2-DC deployments — PhaseDeferred("§29"). Hierarchical elections (region leaders electing a global leader) — PhaseDeferred("§29").

30. Mental Models & First Principles

  • MM1 — Leadership is a lease, not a crown. Insight: a leader holds time-bounded, renewable authority, never permanent ownership. Predicts: every leader must renew and every consumer must tolerate a leader vanishing. Bug without it: a zombie ex-leader keeps writing after a partition. Resolved in §17 (Phase 5), P7.
  • MM2 — A fencing token turns an unsafe lock into a safe one. Insight: attach a monotonically increasing epoch to leadership and check it at every downstream mutation (Kleppmann DDIA Ch 8, Chubby sequencers §5). Predicts: without it, a delayed request from an old leader corrupts state. Bug without it: dual-writer corruption. Resolved in §17, I2.
  • MM3 — FLP means you buy liveness with timeouts and randomness. Insight: with async + one crash, no protocol is both safe and live (FLP 1985); Raft keeps safety always and adds randomized timeouts for probabilistic liveness. Predicts: deterministic timeouts → perpetual split votes. Bug without it: livelocked elections. Resolved in §15 (Phase 3), P1.
  • MM4 — Quorum intersection is the whole safety argument. Insight: any two majorities of the same configuration share a node, so two leaders in one term is impossible (I4); the danger is two configurations with disjoint majorities. Predicts: even-size clusters and unsafe reconfig cause split-brain. Bug without it: two independent quorums elect two leaders. Resolved in §16 (Phase 4), I11.
  • MM5 — The clock is a liveness device, never a safety device. Insight: wall-clock decides when to try to elect/expire, never whether something is committed; safety uses term/index order (Lamport 1978). Predicts: skew must only delay, never violate. Bug without it: wall-clock lease TTL grants two leaders under skew. Resolved in §17, P11.
  • MM6 — Failure detection is a probability, not a boolean. Insight: phi-accrual outputs a continuous suspicion level over inter-arrival statistics (Hayashibara 2004), so a GC pause raises suspicion gradually instead of flipping "dead". Predicts: fixed timeouts flap under pauses. Bug without it: election storms on a hiccup. Resolved in §16 (Phase 4), FM-13.
  • MM7 — Commit means durable on a majority, not written locally. Insight: an entry is committed only once a quorum has fdatasync'd it (I10); local write is not commit. Predicts: acking early loses data on failover. Bug without it: acknowledged leadership disappears (RPO break). Resolved in §15/§14, P8.
  • MM8 — Snapshot and log must compose exactly once. Insight: state = snapshot(@N) + log(N+1..); the boundary must be exact (Ongaro thesis Ch 5). Predicts: an off-by-one at the boundary drops or double-applies an entry. Bug without it: replay gap after compaction. Resolved in §18 (Phase 6), I12.
  • MM9 — Even reads need consensus. Insight: a leader that was silently deposed will happily serve stale reads; a linearizable read must confirm current leadership (read-index barrier) or go through the log. Predicts: "just read locally" leaks stale ownership. Bug without it: a client acts on a leadership view that a new leader already superseded. Resolved in §15.2 (Phase 3), I4.
  • MM10 — Membership is just another log entry. Insight: reconfiguration is committed through the same log as data, so the config in effect at index i is well-defined and replays deterministically; the only special rule is quorum-overlap on transition (I11). Predicts: treating membership as out-of-band state creates disjoint-quorum races. Bug without it: two configs active at once → split-brain (MM4). Resolved in §16 (Phase 4), ADR-21.

32. Back-of-Envelope Capacity Model

Each number is derived from §4 (C#) with the formula shown; nothing asserted.

  1. Safe lease TTL floor (→ C15). TTL ≥ 2·RTT + fdatasync + drift + margin. From C2 (RTT p99 20 ms), C5 (fdatasync 3 ms), C16 (drift 100 ms): 2·20 + 3 + 100 = 143 ms; add ~40% margin ⇒ ≥ 250 ms = C15. This is why a client RenewDeadline below this flaps (FM-8, §17).
  2. Leader→follower heartbeat rate. (n-1) · (1000/interval). From C1 (n=7) and C18 (100 ms): 6 · 10 = 60 msgs/s; at ~256 B ⇒ 60·256 = 15.4 KB/s — negligible (justifies M9 < 5%).
  3. Replication bandwidth at peak. throughput · entry_size · (n-1). From C3 (25,000/s), 256 B entry, n=7: 25,000 · 256 · 6 = 38.4 MB/s outbound on the leader — fits a 10 GbE NIC with headroom.
  4. WAL write rate & amplification. throughput · entry_size · amplification. From C3, 256 B, C19 (1.5×): 25,000 · 256 · 1.5 = 9.6 MB/s fsync-backed — trivial for NVMe (justifies M3).
  5. Group-commit batch size needed. throughput · fdatasync_p99. From C3 and C5 (3 ms): 25,000 · 0.003 = 75 entries/fsync minimum batch to keep fsync off the critical path (justifies ADR-07 group commit).
  6. Watch memory at fan-out (→ C7/M10). watchers · per_watch_bytes. From C6 (200,000) and per-watch ≈ 4 KB (cursor 16 B + bounded queue 32×64 B + gRPC/task overhead ~2 KB): 200,000 · 4 KB = 800 MB — under C7 (8 GiB) with room for state/log.
  7. FD usage at fan-out (→ C13). watchers/streams_per_conn + peers + listeners. From C6, ~100 multiplexed streams/conn (ADR-05), C1: 200,000/100 + 6 + few ≈ 2,010 FDs — far under C13 (65,536).
  8. Cold replay time (→ C8/M6). entries / apply_rate. Apply is in-memory map insert ≈ 1M/s; 1,000,000 / 1,000,000 ≈ 1 s CPU + IO read of ~256 MB at NVMe 2 GB/s ≈ 0.13 s ⇒ well under C8 (15 s), leaving margin for CRC verification.
  9. Snapshot recovery (→ C9/M7). snapshot_bytes / (net_or_disk_rate). 1 GiB over 10 GbE ≈ 1 GiB / 1.25 GB/s ≈ 0.9 s transfer + deserialize ≈ few s ⇒ under C9 (60 s) with wide margin.
  10. Failover time (→ C11/M5). detection + election + first_commit. From C18: detection ≈ 1 election timeout (~225 ms avg), election ≈ 1–2 timeouts (150–600 ms), first commit ≈ RTT+fsync (~23 ms) ⇒ typically < 1 s, worst case ≤ 3 timeouts (M13) — inside C11 (60 s) and M5 (2 s).
  11. In-RAM Raft log before snapshot. retained_entries · entry_size. Keeping 100,000 recent entries: 100,000 · 256 B = 25.6 MB — trivial vs C7; triggers a snapshot to cap it.
  12. Max independent groups per node (memory-bound). (C7 − overhead) / per_group_state. With ~1 GiB reserved for watches/log and per-group ElectionRecord ≈ 128 B: ~6 GiB / 128 B ≈ 50M groups theoretical; practically bounded by watch/session memory (#6), so groups scale by sharding (§29), not per-node stuffing.

34. Alternative Architectures (Roads Not Taken)

A. ZooKeeper-style ephemeral-sequential znode election.

clients -> [ ZooKeeper ensemble (Zab) ] : create ephemeral-sequential /elect/n_
leader = client owning the lowest sequence number; each watches its predecessor

Regime where it wins: when a flexible hierarchical namespace and mature client recipes are worth more than a purpose-built election API, and clients already speak ZK. Embodied by ZooKeeper (Hunt 2010, §5). Rejected because it pushes election logic into every client (herd effects, subtle session-expiry semantics, no built-in fencing API), whereas we want a single server-side lease + fence contract (§17, P7) with server-owned safety.

B. Multi-leader / leaderless WAN consensus (EPaxos-class).

region A leader ---\
region B leader ----> conflict-graph ordering (no single stable leader)
region C leader ---/

Regime where it wins: geo-distributed writes where a single leader's cross-region RTT is intolerable and commands rarely conflict. Embodied by EPaxos (rejected in ADR-03) and Zab-with-observers variants. Rejected for Phase 0 because it multiplies the reasoning surface (dependency graphs, cross-region quorums) against a single-region target (C2); kept as PhaseDeferred("§34") for WAN.

C. External lock on a shared KV (etcd/Redis lease as a library).

app -> [ etcd/Redis ] : PUT key with lease TTL; renew; whoever holds key = leader

Regime where it wins: when you already run etcd/Redis and want zero new infrastructure — the Kubernetes leaderelection model (§5). Embodied by etcd lease / Redis SETNX+TTL. Rejected as the primary design because it inherits the backing store's fencing story (or lack of it, in naive Redis) and its failure model, and because building the mechanism from scratch is the entire pedagogical point (§2); we instead offer an etcd-compatible client contract (§21) on top of our own safe core.

D. Classical Bully / Ring election over direct links.

Bully: highest-id live node wins; on suspicion, higher ids "bully" lower ones
Ring:  token/election message circulates the logical ring; max id elected

Regime where it wins: small, fully-connected, crash-stop clusters with a trusted synchronous-ish network and no durability requirement (classic textbook setting, van Steen §5). Embodied by the Bully and Ring algorithms. Rejected because they assume reliable failure detection and provide no replicated log, no durability, and no fencing — unsafe under the partitions and asynchrony we target (P1, MM3); we keep them only as the §5 baseline for understanding.

36. Glossary

  • Acquire — client request to become owner of an election group; commits an ACQUIRE entry and, on success, returns a lease + fence token.
  • AppendEntries — Raft RPC carrying log entries + heartbeat from leader to followers; also the consistency check (I6).
  • Apply loop — the single-writer thread that applies committed entries to the state machine in index order (I3, I8).
  • Availability (CP sense) — ability to serve within a partition; sacrificed on the minority side to preserve safety (P1).
  • Backpressure — bounded-queue load-shedding that returns BackpressureExceeded rather than growing memory (P5, ADR-23).
  • Bully algorithm — classical election where the highest-id live node wins (§34 D).
  • Commit index — highest log index durably replicated on a quorum (I10); source of fence tokens (ADR-10).
  • Conformance fixture — a named test input + expected output mapped to an invariant (§26).
  • CP — Consistent + Partition-tolerant (CAP); this service's classification (§4, P1).
  • Election group — an independent coordination domain with its own ownership FSM (group_id).
  • Election timeout — randomized interval (150–300 ms, C18) after which a follower becomes a candidate (MM3).
  • Ephemeral-sequential znode — ZooKeeper election recipe primitive (§34 A).
  • Fail closed — on uncertainty, revoke/refuse rather than risk unsafe action (P9).
  • Fence token — monotonic u64 ownership epoch from the commit index; checked at every mutation (I2, P7, MM2).
  • fdatasync — POSIX call flushing file data (not metadata) to stable storage; the durability primitive (ADR-07).
  • FLP impossibility — no async consensus is both safe and live with one crash (MM3, §5).
  • Follower / Candidate / Leader — Raft roles (RaftRole).
  • Group commit — batching many appends into one fdatasync to amortize cost (§14, §32 #5).
  • Heartbeat — periodic leader→follower AppendEntries (100 ms, C18) proving liveness.
  • Learner — non-voting node catching up before promotion to voter (§16, I11).
  • Lease — time-bounded ownership grant (owner, fence_token, expiry) (§8).
  • Linearizable — reads/writes appear to take effect atomically in real-time order.
  • Log matching — Raft property: equal (index,term) ⇒ identical entries and prefixes (I6).
  • Membership change — single-server add/remove preserving quorum overlap (ADR-21, I11).
  • Monotonic clock — CLOCK_MONOTONIC; used for lease timing, never for safety (P11, ADR-22).
  • mTLS — mutual TLS; both peers authenticate (P14, ADR-14).
  • Phi-accrual — failure detector emitting a continuous suspicion value (ADR-08, MM6).
  • Quorum — majority ⌊n/2⌋+1 of voters (C1); any two intersect (MM4).
  • Quorum intersection — the property that two majorities share a node, ensuring single leadership (I4, I11).
  • RequestVote — Raft RPC by a candidate seeking votes, subject to the up-to-date-log restriction (I7).
  • Revision — monotonic per-group version used by watch cursors (§8, §19).
  • Ring algorithm — classical election over a logical ring (§34 D).
  • RPO — recovery point objective; 0 committed entries lost here (C12, I10).
  • RTO — recovery time objective; < 60 s worst case (C11, M11).
  • Session — client liveness context that renews leases and expires on missed heartbeats (§8).
  • Snapshot — checksummed capture of applied state enabling compaction + fast recovery (§18, I12).
  • Split-brain — two nodes believing they are leader simultaneously; prevented by quorum + fencing (FM-4, MM4).
  • Term — Raft logical clock / election epoch; never decreases (I14, MM5).
  • Torn write — a partially written record detected by CRC and truncated on replay (I15, §14).
  • WAL — write-ahead log; append-only durable record of entries (§14).
  • Watch cursor — per-subscriber stream position for resumable delivery (§19, WatchCursor).
  • Zab — ZooKeeper Atomic Broadcast; the primary-order protocol contrasted in §31/§34.
  • Zombie leader — an ex-leader still acting after losing leadership; neutralized by fencing (MM1, MM2).
  • Pre-vote — a Raft round where a candidate checks it could win before bumping its term, preventing disruptive elections by rejoining nodes (§15.2).
  • Read-index — a barrier that lets a leader answer a linearizable read after confirming it still leads, without appending a log entry (§15.2, MM9).
  • Leadership transfer — a leader handing off to a caught-up follower via TimeoutNow, avoiding a timeout-driven election gap (§24).
  • Learner lag — how far behind a non-voting node's match-index is from the leader's commit index (§16).
  • Joint consensus — the alternative multi-server reconfiguration protocol rejected in ADR-21 in favor of single-server change.
  • Load shedding — rejecting excess work with BackpressureExceeded rather than queueing unboundedly (P5, ADR-23).
  • Suspicion (phi) — the continuous failure-detector output; higher phi = higher probability the peer is down (MM6).
  • Sequencer — Chubby's name for a fencing token handed to clients and validated by downstream services (§5, MM2).
  • Dedup cache — the replicated per-session (request_id → result) map giving exactly-once semantics across retries (§8).
  • Bounded-stale read — a follower read tagged with its commit index so a client can reject reads older than a bound (§8).
