Decisions (§9) · 25 ADRs

ADR-01

Implementation language

Chosen

Rust workspace, no Go split

Rejected

Go gateway/Rust storage split; JVM (Cassandra-style)

When the rejected choice is right

a team with deep Go strength and no Rust hires, prioritizing hiring velocity over p99 tail latency — MinIO shipped Go successfully at scale

Why: one supervision tree, one memory model, no GC-pause tail latency

ADR-02

Auth surface

Chosen

Sigv4 strict, no Sigv2/anonymous-by-default

Rejected

Sigv2 fallback; always-anonymous

When the rejected choice is right

a closed intranet with no external threat model and legacy Sigv2-only clients that cannot be upgraded

Why: Sigv2 is deprecated, doubles fuzz surface

ADR-03

Blob addressing

Chosen

Content-addressed (xxh3 key, SHA-256 verify)

Rejected

(bucket,key,version)-addressed blob layer

When the rejected choice is right

a workload with near-zero duplicate bytes (e.g. client-side-encrypted blobs), where the manifest-pointer indirection buys nothing

Why: free dedup, clean integrity story

ADR-04

Default durability

Chosen

3-way replication

Rejected

EC(6,3) default

When the rejected choice is right

capacity-bound cold-archive workloads from day one — EC saves 1.5× capacity immediately when reads are rare

Why: simpler repair/degraded-read story for early phases

ADR-05

EC scheme

Chosen

Reed-Solomon (6,3) via rank-108

Rejected

Locally Repairable Codes (LRC)

When the rejected choice is right

high-node-churn clusters where repair bandwidth dominates cost (Rashmi et al. 2014) — LRC cuts repair I/O ~2× at ~1.33× space overhead vs. RS(6,3)'s 1.5×

Why: simpler encoder, ships first

ADR-06

Versioning default

Chosen

opt-in per bucket

Rejected

always-on versioning

When the rejected choice is right

a compliance-first deployment where every bucket must default to WORM-capable — flip the cluster-wide template default, not per-bucket

Why: matches the S3 contract

ADR-07

Lifecycle cadence

Chosen

daily batch worker

Rejected

synchronous per-write evaluation

When the rejected choice is right

a low-object-count bucket (<10K objects) needing near-real-time expiry (e.g. ephemeral CI artifacts) — a documented per-bucket faster cadence override

Why: per-write eval is bandwidth-prohibitive at scale

ADR-08

Multipart finalize

Chosen

metadata manifest transition

Rejected

concatenate parts into one physical blob

When the rejected choice is right

a legacy tool requiring one contiguous on-disk file (e.g. direct mmap) — accepts the IO-doubling cost of physical concatenation

Why: avoids doubling IO at finalize

ADR-09

Metadata HA

Chosen

Raft (rank 39)

Rejected

Quorum-Journal (HDFS-style); CRUSH-style decentralized (no consensus)

When the rejected choice is right

a shop already standardized on ZooKeeper/QJM — reuse avoids running a second consensus service

Why: simpler, self-contained, strictly linearizable

ADR-10

Metadata persistence

Chosen

WAL (rank 71)

Rejected

bespoke from-scratch log

When the rejected choice is right

a hard license/export-control conflict forcing an in-house WAL — otherwise reuse dominates

Why: reuse a vetted, already-conformance-tested crate

ADR-11

Transport security

Chosen

mTLS internal (rank 50), TLS external, from Phase 0

Rejected

plaintext internal wires

When the rejected choice is right

an air-gapped single-rack test lab with no untrusted tenants, for a throwaway benchmark run

Why: internal plaintext is a frequent CVE source

ADR-12

Cross-region replication

Chosen

asynchronous

Rejected

synchronous cross-region write

When the rejected choice is right

two datacenters on the same metro dark-fiber ring (<2 ms RTT) where sync buys zero-RPO DR affordably

Why: sync pushes p99 PUT over 100 ms on real WAN links

ADR-13

Object-lock exposure

Chosen

versioning must be Enabled and visible via the versions API

Rejected

implicit/hidden versioning under object-lock

When the rejected choice is right

a single-tenant deployment wanting WORM without teaching every client the versions API — trades auditability for client simplicity

Why: explicit exposure lets operators audit retained versions directly

ADR-14

HTTP runtime

Chosen

tokio + axum

Rejected

async-std; warp; thread-per-connection sync server

When the rejected choice is right

a small internal tool at <100 req/s, where a synchronous server is simpler to debug with standard blocking-IO tools

Why: streaming-body PUT needs async backpressure; axum/tower maturity

ADR-15

Internal RPC

Chosen

tonic + protobuf

Rejected

When the rejected choice is right

a two-node prototype where protobuf codegen overhead exceeds the win before the schema stabilizes

Why: schema evolution, codegen, streaming support

ADR-16

Hash roles

Chosen

xxh3 (addressing) + SHA-256 (integrity)

Rejected

SHA-256-only for both roles

When the rejected choice is right

a FIPS-validated-crypto-everywhere compliance regime, where a non-cryptographic hash anywhere fails an audit

Why: xxh3 is ~10× faster on the hot per-byte path

ADR-21

Addressing style

Chosen

path-style default, virtual-host behind a flag

Rejected

virtual-host-style only

ADR-22

Response formats

Chosen

XML (S3 surface), JSON (admin)

Rejected

JSON for both

When the rejected choice is right

an internal-only deployment with zero third-party S3 SDK clients — but then it is no longer S3-compatible

Why: S3 clients hard-expect XML; admin is our own surface

ADR-23

Blob on-disk layout

Chosen

flat directory of fragment files (Phase 0), packed later

Rejected

packed needle files (Haystack-style) from day one

When the rejected choice is right

a workload known in advance to be dominated by objects <32 KiB — pack from day one, avoid a costly later migration

Why: flat is trivially debuggable; pack once inode pressure is measured

ADR-24

Multipart limits

Chosen

5 MiB–5 GiB/part, 10,000 parts — exactly the S3 contract

Rejected

a looser/custom limit set

When the rejected choice is right

an internal-only deployment with a purpose-built client and no AWS SDK usage — forfeits SDK compatibility but is technically viable

Why: clients and SDKs hardcode S3's limits

ADR-25

Consistency model

Chosen

strong intra-region (same leader term), eventual cross-region

Rejected

fully eventual everywhere (Dynamo-style); fully strong everywhere (sync cross-region)

When the rejected choice is right

fully-eventual wins for globally-distributed, write-heavy, conflict-tolerant workloads (Dynamo's cart use case); fully-strong wins for a single-region deployment with no cross-region requirement at all

Why: matches the durability/latency budget in §4

36. Alternative Architectures (Roads Not Taken)

A1 — Fully leaderless, Dynamo-style (sloppy quorums, vector-clock reconciliation, no Raft metadata leader).

        client --> consistent-hash ring --> N replica nodes (N/W/R quorum)
                         no single leader; conflicts resolved by
                         vector clocks / last-writer-wins at read time

Regime where it wins: globally-distributed, write-availability-over-consistency workloads (Dynamo's original shopping-cart use case). Real system: Amazon Dynamo / Riak. Rejected because: object-lock (I8) and versioning correctness (I5) need a linearizable metadata decision point; a leaderless AP design pushes that correctness burden into application-level reconciliation this project does not want to own.

A2 — Unified filesystem+object substrate (Tectonic-style).

        one chunk-server fleet serves both:
        POSIX filesystem namespace  <-->  object-store namespace
                    (shared storage, shared placement)

Regime where it wins: a single organization running both a cluster filesystem and an object store, wanting one storage fleet instead of two. Real system: Facebook Tectonic. Rejected because: this project explicitly delegates filesystem concerns to rank 86 and wants a narrower, independently shippable Phase-0 surface (§1 non-goals).

A3 — CRUSH-style decentralized placement (no central placement table).

        client/gateway --> CRUSH(cluster_map, object_id) --> placement
                     (computed, not looked up; no metadata-service hop)

Regime where it wins: extreme cluster sizes (10,000+ nodes) where a centralized placement authority becomes a bottleneck or single point of contention. Real system: Ceph/RADOS. Rejected because: the metadata service is already the strongly-consistent authority for every other decision (I13); adding CRUSH would create two sources of placement truth. Documented as an optional pluggable placement function (ADR-09), not the default.

A4 — Client/gateway-side erasure coding with no separate blob-node RPC tier (Backblaze-Vaults-style).

        gateway computes 20-shard (17+3) EC directly, writes each shard
        straight to a fixed storage-pod mapping — no metadata-index
        transaction per write, no blob-node abstraction layer

Regime where it wins: extreme-cold, extremely price-sensitive archival storage, where operational simplicity (a fixed pod mapping, no Raft cluster) outweighs feature flexibility. Real system: Backblaze Vaults (Backblaze Engineering, publicly documented architecture, 2015). Rejected because: this system needs a strongly consistent metadata index regardless, for versioning, lifecycle, and object-lock (I5, I8) — so the "no metadata service" simplification Vaults relies on does not actually apply once those features are in scope.
