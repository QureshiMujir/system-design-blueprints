In one paragraph

An object store keeps large, unchanging blobs — data-lake files, backups, CI build artifacts — and hands each one back by name. This design is an S3-compatible one: every object is addressed by a (bucket, key, versionId) triple, reached over a Sigv4-signed HTTPS REST surface, stored either as three full copies or as Reed-Solomon erasure-coded shards, and indexed by a Raft-replicated, LSM-structured metadata service, with 99.999999999% annual durability as the engineering target (§1). Its defining property is that no write is acknowledged before it is durable — it trades write latency for never lying about durability (§4, I1). It is one Rust workspace (ADR-01), run by platform teams as an internal store for data-lake, backup and CI-artifact workloads (§1).

The problem, concretely

The data warehouse (rank 60) reads Parquet from an object store, the streaming engine (rank 65) checkpoints to one, the training pipeline (rank 80) reads TFRecords from one; if the store is opaque, every downstream incident becomes a support ticket (§2). The blueprint names what goes wrong in a simpler store. Count replicas and stop there, and RF=3 looks "safe" without rack diversity, when durability is a probability built from disk failure rate (2% a year in §34 item 5), repair time and copy count (MM2). Skip the checksum on reads, and bitrot returns wrong bytes with a success code (P6). Overwrite in place, and write leases become necessary (P2). Let each front-end pick disks, and placement drifts between servers during a rolling upgrade (P14). Design only the happy path of an upload — anything above the 5 GiB single-part maximum arrives in parts (§4) — and a crash mid-upload has no recoverable state (MM7). And clients hard-expect S3's XML (ADR-22), while Sigv4 normalization is "the surface every implementation gets wrong at least once" (§2). Hence: computed durability, uploads as state machines, one placement authority, a fixed wire contract (MM2, MM7, P14, MM8).

How it works, end to end

       +-------v-------+ +-------v-------+     +-------v--------+
       |   metadata    | |   blob nodes   |     |  admin / ops   |
       | (Raft + WAL)  | | (storage pool) |     | rebalance / GC |
       | bucket/obj/   | | fragments/     |     | scrub / fsck   |
       | ver/mpu index | | shards on disk |     | lifecycle work |

Follow the blueprint's own worked PUT, then GET (§8.5), through §3's boxes:

  1. The client signs PUT /demo/hello.txt with body "hi" and sends it over HTTPS (§8.5).
  2. Gateway (obj-gateway-s3, with obj-sigv4): verifies the signature (§17) and, in one streaming pass over the body, computes three hashes — md5 for the ETag, xxh3 for the storage name (the FragmentId), sha256 for integrity (§8.5, §12.7). The gateway holds nothing the user could lose (P4).
  3. Metadata service (obj-index, Raft + WAL): the gateway calls put_object_begin and gets back a ticket (ticket_id: 42) (§8.5). The metadata service — never the gateway — chooses the placement: three replica nodes for an RF=3 bucket (I13, P7).
  4. Blob nodes (obj-blob): the gateway calls put_fragment(frag, bytes, plan); once 2 of the 3 replicas acknowledge, the write may be committed (§8.5, §14.2).
  5. Back to the metadata service: put_object_commit(ticket, manifest) appends PutObjectCommit to the write-ahead log (obj-wal), fsyncs it, then applies it (I3); the bucket is unversioned, so the result is VersionId::NONE (§8.5).
  6. The gateway returns 200 OK with ETag: "<md5_hex>" (§8.5) — only now, after the bytes are durable (I1).
  7. A later GET /demo/hello.txt resolves the head version, streams the fragment from any replica and verifies SHA-256 before returning the two bytes (§8.5, I4).

The third column — admin / ops (obj-admin, obj-scrub, obj-gc, obj-lifecycle, obj-replication, driven by the obs CLI in obj-cli) — runs rebalance, GC, scrub, fsck and lifecycle work behind an mTLS admin REST surface (§3, §10.1, §23.2). Internal RPCs are protobuf over tonic (ADR-15), with mTLS on internal wires from Phase 0 (ADR-11).

The core ideas

Content addressing: an object is a list of pointers (§8.3, §11.4, ADR-03, MM1)

A fragment is stored under a 128-bit xxh3 fingerprint of its own bytes (content addressing) and carries a SHA-256 for verification (§11.4, ADR-16). An object version is a manifest: an ordered list of entries {part_number, fragment, bytes, md5, sha256, placement} (§11.4). The blob layer never learns about buckets, keys or versions (§3). Three things fall out. CopyObject just reuses the source FragmentIds in a new manifest — O(1) whatever the object size (§13.2) — so 1,000 copies of one 10 MB object leave exactly one fragment in the blob layer (§13.4). Mutation becomes allocation: a PUT to an existing key makes a new version, never an overwrite (P2). And GC must count references, because deleting a fragment still named by any live manifest is data loss (I10). On disk each fragment is one file plus .meta and .crc sidecars, one CRC32C per 64 KiB block (§8.3, ADR-23), moving through Writing → Committed → {Quarantined | GcPending → Deleted}; Quarantined is entered only on a checksum mismatch (§8.3, I4).

Replication or erasure coding: the per-bucket durability knob (§11.5, §14.2, §15.2, P7)

Durability is a bucket policy: Replication{rf} (default 3, ADR-04), Erasure{k, m} (default (6,3), ADR-05) or Tiered{hot, cold} (§11.5). Under RF=3 the metadata service picks 3 distinct nodes, the PUT commits once 2 of 3 acknowledge, and a GET degrades to any one surviving replica (§14.2). Under erasure coding the fragment is split into k=6 data shards plus m=3 parity shards placed on 9 distinct, rack-diverse nodes (§15.3); the PUT commits at a k+1-of-k+m quorum, a GET reconstructs from any 6, losing up to 3 of 9 shards is tolerated and losing more makes the object unavailable (§15.2, §15.3, FM-6, FM-7). The blueprint is not consistent on how strict rack diversity is: I6 says "rack-diverse where possible", while §15.2 says placement refuses with InsufficientReplicas when it cannot diversify, and §15.4 requires that refusal in 100% of 200 rack-constrained trials.

RF=3 EC(6,3)
Commit quorum 2 of 3 (§14.2) k+1 of k+m (§15.2)
Minimum survivors for a read 1 (§14.2) 6 (§15.3)
Storage amplification 3.0× (§4) 1.5× (§4)
Internal write bandwidth at 800 MB/s of PUTs 2,400 MB/s (§34 item 1) 1,200 MB/s (§34 item 2)

The surprise is repair: EC cuts the storage bill, but repairing one shard costs k× the shard size, so an EC cluster needs more provisioned repair bandwidth than a replicated one at the same failure rate (§15.7, MM5) — which is why §31 names Locally Repairable Codes (rejected in ADR-05) as the lever once repair bandwidth, not storage cost, binds. To keep tail latency down when one shard is slow, an EC read is hedged: it issues k+1 reads from the start and uses the first k, spending one shard's bandwidth per GET — a per-bucket knob that capacity-sensitive workloads can switch off (P13, §15.6).

The metadata service: log, then apply (§8.4, §14.2, I3, I13)

Every change to the index — bucket creation, object insert, version allocation, multipart transition, placement — is one MetadataWalOp written to a log that is fsync'd before the change is applied (write-ahead log, WAL) (§3, §14.2, I3). The index itself is an LSM-tree: a sorted in-memory table (MemTable) guarded by the WAL, flushed on checkpoint into immutable sorted files (SSTables), merged by a background compactor; a read checks the MemTable, then segments newest-first, and a prefix listing merge-iterates across every level (§8.4). CheckpointPolicy{max_wal_bytes, max_wal_age, max_uncheckpointed_ops} bounds how much log must be replayed after a crash — §4's target is ≤ 90 s for a 100M-object replay (§14.2). The service is replicated with Raft (ADR-09), and it is the only place that decides where bytes go (I13, P14).

The blueprint's crash trace (§8.7): a gateway dies after the blob write is acked but before the commit is logged. (1) The ticket stays Allocating in the WAL. (2) The recovery sweep finds no PutObjectCommit after the GC threshold and issues PutObjectAbort, queuing the fragment for GC (I10) — or a client retry with the same idempotency key re-attempts the commit. (3) No GET sees a partial object: the manifest installs in a single WAL entry.

Multipart upload is a state machine, and "complete" is one transition (§16.2, I7, ADR-08)

Objects above 5 GiB — and in practice most above 100 MB — arrive as parts of 5 MiB–5 GiB, at most 10,000 of them, the last part exempt from the minimum (§4, §16.1, ADR-24). An upload moves through InProgress → {Completing → Completed | Aborting → Aborted} | Expired (§16.2); the intermediate Completing and Aborting states exist precisely so that a crash there is recoverable (MM7, FM-5). CompleteMultipartUpload copies no bytes: it validates that every listed part exists and its MD5 matches the client's claim, checks that part numbers are strictly ascending with gaps allowed (I7), installs a manifest with one entry per part and flips the state to Completed — all in one WAL entry (§16.2, ADR-08). Parts uploaded out of order (5, 3, 7) complete with a correctly ordered manifest (§16.4); a wrong MD5 is 400 InvalidPart, a non-last part under 5 MiB is 400 EntityTooSmall, and Complete racing Abort is 409 Conflict because the state check is atomic with the transition (§16.6). The result's ETag is hex(md5(concat(part_md5s)))-N (§16.2).

Versions, delete markers and who sees what (§8.1, §18.2, I2, I5, I14)

For each (bucket, key) the index keeps a version ladder, Vec<(VersionId, Object)> in descending order; the head is the current object (§8.1). VersionId is 128 bits and strictly increasing per key (I2, §11.1). On a versioned bucket a DELETE without a versionId removes nothing: it pushes a delete marker — itself a version — onto the ladder, so the key reads as logically deleted; a DELETE with a versionId hard-removes that version, subject to object-lock (§18.2, §21.2).

Request on a versioned bucket Effect on the ladder
PUT to an existing key a new version on top; the old one is retained (P2, §18.3)
DELETE without versionId a delete marker becomes the head; the key reads as deleted (§18.2)
DELETE of the delete marker the next-older version is revealed (§18.6)
DELETE with a versionId that version is hard-removed, unless object-lock refuses (§18.2, §21.2)
DELETE on a suspended bucket a delete marker with a legacy null version (§18.2)

Versioning can be suspended (no new versions) but never returned to Unversioned, and a suspended bucket keeps its ladder (P9, I5, §18.6). Object-lock requires versioning Enabled (§21.2, ADR-13). Consistency is a per-read-path property, not a system-wide slogan (MM3): a read served by the same metadata-leader term as the write it follows sees that write (I14), while a read from a cross-region replica right after a source PUT may legitimately 404 — documented eventual consistency, not a bug (§20.6, ADR-25).

Sigv4: the only front door, verified in constant time (§17.2, I12, ADR-02)

Every request is signed with AWS Signature Version 4 (Sigv4); there is no Sigv2 fallback and no anonymous-by-default (ADR-02, P5). The verifier rebuilds the canonical request — sorted, percent-encoded query parameters; lowercase, whitespace-collapsed, sorted headers; a payload hash that is hex(sha256(body)), UNSIGNED-PAYLOAD or the streaming sentinel — derives the signing key, computes the expected signature and compares with constant_time_eq::eq, because a timing leak on that comparison is a known CVE pattern (§17.2, I12). Streaming aws-chunked bodies are verified chunk by chunk as they arrive, never after the whole body has landed (§17.2). Signed timestamps are accepted within a 15-minute skew window, matching AWS: tighter breaks real clients, looser widens the replay window (§17.6, T2).

The trade-offs — where engineers disagree

Blob addressing: by content, not by name (ADR-03)

Chosen: content-addressed fragments — xxh3 as the storage key, SHA-256 to verify — giving free deduplication and a clean integrity story. Rejected: a blob layer addressed by (bucket, key, version). When the rejected choice is right: a workload with near-zero duplicate bytes, such as client-side-encrypted blobs, where the manifest-pointer indirection buys nothing.

Default durability: three copies, not erasure coding (ADR-04)

Chosen: 3-way replication by default, because its repair and degraded-read story is simpler for the early phases. Rejected: EC(6,3) as the default. When the rejected choice is right: capacity-bound cold-archive workloads from day one — EC saves 1.5× capacity immediately when reads are rare (and halves internal write bandwidth, §34 item 2).

Multipart finalize: a manifest edit, not a rewrite (ADR-08)

Chosen: Complete is a metadata manifest transition, which avoids doubling I/O at finalize. Rejected: concatenating the parts into one physical blob. When the rejected choice is right: a legacy tool that requires one contiguous on-disk file (direct mmap, say) and accepts the I/O-doubling cost.

Metadata high availability: Raft (ADR-09)

Chosen: Raft (rank 39) — simpler, self-contained, strictly linearizable. Rejected: an HDFS-style Quorum Journal; CRUSH-style decentralized placement with no consensus at all. When the rejected choice is right: a shop already standardized on ZooKeeper/QJM, where reuse avoids running a second consensus service. CRUSH stays documented as an optional pluggable placement function, not the default (§36 A3).

Cross-region replication: asynchronous (ADR-12)

Chosen: asynchronous replication through a persisted queue, because a synchronous cross-region write pushes PUT p99 past 100 ms on real WAN links — §4 assumes 40–120 ms cross-region RTT, and §34 item 7 caps a 1 Gbps link at 125 MB/s. Rejected: synchronous cross-region write. When the rejected choice is right: two datacenters on one metro dark-fiber ring (< 2 ms RTT), where synchronous replication buys zero-RPO DR affordably.

Consistency: strong at home, eventual abroad (ADR-25)

Chosen: strong within a region (same leader term), eventual across regions — the shape that fits §4's durability and latency budget. Rejected: fully eventual everywhere (Dynamo-style); fully strong everywhere (synchronous cross-region). When the rejected choice is right: fully eventual wins for globally distributed, write-heavy, conflict-tolerant workloads such as Dynamo's shopping cart; fully strong wins for a single-region deployment with no cross-region requirement at all.

Roads not taken (§36)

A1 — leaderless, Dynamo-style (hash ring, sloppy quorums, vector clocks): wins for globally distributed, write-availability-first workloads (Dynamo, Riak); rejected because object-lock (I8) and versioning (I5) need a linearizable decision point.

A2 — one filesystem-plus-object substrate (Tectonic): wins for an organization wanting one storage fleet instead of two; rejected because filesystem concerns go to rank 86 and Phase 0 wants a narrow surface (§1).

A3 — CRUSH computed placement: wins at 10,000+ nodes, where a central placement authority becomes the bottleneck (Ceph); rejected because the metadata service is already the strongly consistent authority (I13).

A4 — gateway-side EC to a fixed pod mapping (Backblaze Vaults): wins for extreme-cold, price-sensitive archives; rejected because versioning, lifecycle and object-lock need a strongly consistent index anyway (I5, I8).

Deferred, each with an un-defer trigger: V1 listing, pre-signed POST, a single-AZ low-latency class, IAM identity policies, SQL-over-objects and a Swift shim (§37).

What must never be false

  • I1 — every acknowledged PUT is durably placed (RF quorum or EC k+1 quorum) before the gateway returns 200. The chaos bucket kills a gateway after a hypothetical ack; put_ack_before_durable_total must stay 0; a violation is a sev-1 bug.
  • I2 — VersionId strictly increases per (bucket, key). A WAL-replay assertion; version_monotonic_violation_total; the write is rejected and on-call is paged.
  • I3 — WAL entries are fsync'd before the operation is applied. A replay checksum mismatch; wal_fsync_latency_seconds; recovery replays from the last verified snapshot.
  • I4 — SHA-256 is verified before bytes reach a client. A checksum mismatch on read; fragment_checksum_mismatch_total; reconstruct from replica or parity, quarantine the copy.
  • I5 — a bucket with versioning Enabled never becomes Unversioned. The policy-transition validator; versioning_downgrade_attempt_total; the transition is rejected.
  • I6 — EC placement always picks k+m distinct nodes, "rack-diverse where possible" (§15.2 instead refuses when it cannot diversify). The placement diversity check; placement_diversity_violation_total; re-place via repair.
  • I7 — part numbers are 1..=10,000 and a completed part list is strictly ascending. The part-list validator; mpu_complete_reject_total; 400 InvalidPart, client retries.
  • I8 — Compliance-mode retention is never shortened or bypassed by any caller. The delete-attempt-on-locked-object check; compliance_delete_denied_total; refusal is recovery.
  • I9 — replication never loops: an object tagged x-amz-replication-trace is never re-replicated. The trace-header check; replication_loop_detected_total; drop the attempt.
  • I10 — GC never deletes a fragment referenced by a live manifest. A reference-count check before delete; gc_referenced_fragment_delete_blocked_total; skip and log it for fsck.
  • I11 — lifecycle application is idempotent per bucket cursor. The cursor-position consistency check; lifecycle_cursor_position; resume from the persisted cursor.
  • I12 — Sigv4 signature comparison is constant-time. Code review plus fuzzing; sigv4_verify_failure_total; structural, no runtime recovery.
  • I13 — only the metadata service decides placement; the gateway never chooses nodes. An RPC trace audit; gateway_placement_bypass_total must stay 0; reject and page.
  • I14 — a read in the same metadata-leader term as its write sees that write; cross-region replica reads are eventual. The read-after-write trial; stale_read_total stays 0 in-region.

obj-conformance::chaos keeps all fourteen honest: a deterministic simulator that injects crashes, partitions and disk-full at every phase boundary, one invariant per fault (§7).

What breaks in production

  • FM-3 — the metadata leader is lost. RPCs return RetryLater; the cause is a leader crash or partition; detected by the Raft heartbeat timeout; re-election is automatic with RTO ≤ 10 s (§4), manual fencing only if the leader flaps.
  • FM-4 — the WAL is corrupt. Replay fails its checksum after disk corruption or an incomplete fsync (an I3 violation); there is deliberately no auto-recovery — replay halts, fail-closed — and the operator restores from the last verified snapshot plus peer replay.
  • FM-5 — a multipart upload is stuck in Completing after a crash between validate and commit; WAL replay finds no terminal entry and the sweep re-applies mpu_complete idempotently.
  • FM-6 — up to 3 of 9 EC shards are lost. Degraded reads and the hedge path engage; scrub or heartbeat spots the missing shard; the repair worker reconstructs it within 5 min (M9).
  • FM-7 — more than 3 of 9 are lost. GETs return 503 after correlated rack/AZ failure, seen as a placement-diversity plus read-failure spike; no auto-recovery until ≥ 6 of 9 return — the manual path is a cross-region replica, if configured (§20).
  • FM-8 — the replication link is partitioned. replication_queue_depth grows without bound during a WAN outage; the queue is persistent and auto-drains on restore — 100 queued writes within 10 minutes.
  • FM-11 — orphan fragments accumulate. Disk usage grows without a matching object count, from GC lag or crashed uploads; fsck reports the orphan count; the reaper deletes them after a 24-hour quarantine (§23.2), or the operator forces fsck --repair.
  • FM-12 — the rebalancer would create a single-replica window. A move would briefly under-replicate a fragment; the placement-validation-before-move check refuses the move outright (rebalance_move_refused_total); a spike in refusals means a rebalancer bug.

Threats (§24): T1 Sigv4 forgery via a canonicalization bug — a fuzzed canonical-request parser and constant-time compare (I12); T5 silent bitrot — periodic scrub plus one CRC32C per 64 KiB block, reconstructing from replica or parity; T7 mass deletion by operator error, an over-broad lifecycle rule or a compromised admin credential — dry-run and a mass-delete guard threshold, restoring from the version ladder if versioned; T10 a root-account delete on a Compliance object — refused at the metadata layer regardless of privilege (P10, I8), and the refusal is the correct behaviour.

How it compares

  • Amazon S3 is the wire-protocol target; internals undisclosed, strong read-after-write cluster-wide since December 2020. It makes durability and AZ placement automatic and invisible, where this design asks for per-bucket configuration — right for a managed multi-tenant cloud where operator configuration is itself a liability (§33).
  • MinIO embeds metadata in xl.meta sidecar files next to the data, with no separate metadata service. That wins for zero-dependency single-binary deployment, at the cost of no cluster-wide strongly consistent listing without a full-bucket scan in some setups (§33).
  • Ceph RADOS/RGW places with CRUSH — a computed function, no lookup table, no metadata-service bottleneck. That wins at 10,000+ OSDs, at the cost of a harder-to-debug "where is this object" story (§33, §36 A3).
  • OpenStack Swift is eventually consistent everywhere, with the longest production record (since 2010) of any open-source object store. That wins for pure availability-first workloads — semantics this design rejected for versioning and compliance (§33, ADR-25).
  • Azure Storage is the closest cousin: append-only Stream Layer, strongly consistent Partition Layer, stateless front end — nearly this blob/metadata/gateway split. It also serves tables and queues over one stream layer, a generality scoped out here (§33, §1).

If you only remember three things

An object is a manifest of content-addressed fragments, so copying is free, mutation is a new version, and garbage collection must count references. Nothing is acknowledged until it is durable, and only the Raft-led metadata service decides where bytes go — the gateway is a disposable proxy. Durability is arithmetic (failure rate, repair time, rack diversity, copy count) and consistency belongs to each read path: strong in a region, eventual across them.

Words used here

  • Fragment — a content-addressed unit of stored bytes (§8.3, §11.4).
  • Manifest — the ordered list of fragment/shard references composing an object version (§11.4).
  • Shard — one data or parity fragment of an erasure-coded object (§8.3, §15.2).
  • Quorum — the minimum number of replica/shard acknowledgments required to commit a write (§14.2, §15.2).
  • Hedged read — issuing k+1 reads and using the first k, trading bandwidth for tail latency (P13).
  • WAL (write-ahead log) — the durability primitive metadata mutations are logged to before being applied (§14.2, I3).
  • LSM-tree — Log-Structured Merge-Tree, the metadata index's on-disk structure (§8.4).
  • Version ladder — the ordered list of versions for a (bucket, key) pair (§18.2).
  • Orphan fragment — a fragment on disk referenced by no live manifest (§23.2, FM-11).
