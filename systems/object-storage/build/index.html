⬜ Phase 0 — Repo Skeleton & Correctness Kernel §12

Objectives

Stand up the repository (§10); implement obj-core types (§11.1–11.5) compile-only with exhaustive unit tests; a single-node gateway; a single-replica flat-file blob store; a PUT/GET/HEAD/DELETE smoke test. No WAL (§14), no Sigv4 (§17), no replication (§14) — those are explicitly out of scope here and are the next phase's job.

Deliverable

make compose-up brings up 1 gateway + 3 blob nodes; aws s3 cp ./hello.txt s3://demo/hello.txt followed by aws s3 cp s3://demo/hello.txt - round-trips the bytes.

Acceptance

make test passes with tests/integration/hello_bucket.rs green; ETag equals the MD5 of the body (§11.2); conformance.report.json shows 100% pass across core_types, bucket_ops, object_io; cold start ≤ 2 s (§4); BucketName::parse rejects all 8 named adversarial fixtures below with zero false-accepts.

Fixtures
Fixture Purpose Expected Output
bucket_name_leading_hyphen.json reject edge hyphen 400 InvalidBucketName
bucket_name_64_chars.json reject over-length 400 InvalidBucketName
bucket_name_uppercase.json reject invalid char 400 InvalidBucketName
hello_bucket_roundtrip.json PUT/GET/HEAD/DELETE happy path 200/200/200/204
object_key_1024_boundary.json exact max-length key 200 OK
object_key_1025.json over-length key 400 KeyTooLong
Pitfalls
  • Docker-compose networking: a blob node must register its externally-reachable address, not 127.0.0.1 — a bug here creates a cluster that creates objects but cannot read them back.
  • Resist shipping replication early: Phase 0's conformance suite expects exactly one fragment per object on exactly one blob node.
  • Protobuf field numbers are a wire-compatibility commitment (ADR-15) — a Phase-1 rev requires a documented wire-version bump.
  • Do not implement Sigv4 here; anonymous access is fine for the smoke test (ADR-02 arrives in full at §17).

⬜ Phase 1 — Bucket & Object CRUD Wire Surface §13

Objectives

Full CRUD wire surface: CreateBucket/HeadBucket/DeleteBucket/ListBuckets; PutObject/GetObject/HeadObject/DeleteObject/ListObjectsV2/CopyObject; single byte-range reads; still anonymous (Sigv4 is §17).

Deliverable

A gateway accepting every PUT/GET/HEAD/DELETE/LIST/COPY a typical S3 user issues for a single-part object, driven end-to-end by awscli.

Acceptance

A 10,000-object listing+pagination+delete-a-third+relist test asserts the surviving set is exactly correct; a 1,000× copy of one 10 MB object leaves exactly 1 fragment in the blob layer (dedup proof, quantifying P6); single-part PUT bodies > 5 GiB are rejected 413 RequestEntityTooLarge in 100% of trials.

Fixtures
Fixture Purpose Expected Output
listing_pagination_10k.json stable cursor across 10K keys exact key set across pages
copy_dedup_1000x.json content-addressed copy 1 fragment in blob layer
oversized_put_5gib_plus.json single-part size ceiling 413 RequestEntityTooLarge
head_get_header_parity.json HEAD == GET headers byte-identical header set
list_maxkeys_zero.json S3 corner case IsTruncated:false, KeyCount:0
Pitfalls
  • The listing cursor must be gateway-independent (encode bucket + last key only).
  • HEAD must return byte-identical headers to GET (Content-Length, ETag, x-amz-version-id, every x-amz-meta-*) — a divergence here is a recurring bug-report class in production S3-compatible stores.
  • V1 listing is deliberately unsupported (ADR-20); do not half-implement it.

⬜ Phase 2 — Durable Replicated Storage Backend §14

Objectives

Add metadata durability (WAL + checkpoint, rank 71) and blob-layer 3-way replication (ADR-04); the Phase-0/1 in-RAM index and single-replica blob store did not survive a restart or a node loss — this phase makes both durable.

Deliverable

A metadata service that survives kill -9 and reconstructs every bucket and object; a blob layer that tolerates 1-of-3 replica loss transparently on both read and write paths.

Acceptance

10K buckets + 100K objects survive a metadata-service restart bit-identical; WAL append throughput ≥ 80,000 ops/s on NVMe (M8); a test that kills 1 of 3 replicas mid-read still returns 200 OK with correct bytes in 100% of 500 trials; recovery sweep GCs every Allocating ticket older than the GC threshold (FM-5).

Fixtures
Fixture Purpose Expected Output
metadata_restart_100k.json full-index crash/replay bit-identical index
replica_loss_mid_read.json 1-of-3 replica killed mid-GET correct bytes, no client error
wal_append_throughput.bench durability write path ≥ 80,000 ops/s
crash_between_begin_commit.json ticket left Allocating GC-reaped after threshold
Pitfalls
  • The WAL must be fsync'd before the operation is acknowledged (I3) — async writeback is a correctness bug, not a performance choice.
  • The checkpoint must be atomic with respect to the WAL; Phase-2 takes the simpler quiesced-snapshot approach over copy-on-write (documented tradeoff, higher snapshot latency for lower implementation risk).
  • Replay must be idempotent: counters (version_id, ticket_id, mpu_id) are recorded in the log entry, never reallocated at replay time, or replay diverges from the original run.

⬜ Phase 3 — Reed-Solomon Erasure-Coded Backend §15

Objectives

Add Durability::Erasure{k:6,m:3} as an opt-in per-bucket durability mode (ADR-04, ADR-05) via rank 108's Reed-Solomon crate. PhaseDeferred("§15"): an S3-Express-One-Zone-style single-AZ low-latency class is out of scope here (registered §37).

Deliverable

A bucket configurable as Erasure{k:6,m:3}; a PUT path placing 9 distinct, rack-diverse shards; a GET path reconstructing from any 6.

Acceptance

Killing 3 of 9 blob nodes mid-read still reconstructs correctly, p99 ≤ 400 ms hedged (M6); the repair worker restores a lost shard within 5 minutes on a 10 GbE LAN (M9); placement refuses to under-diversify (I6) in 100% of 200 rack-constrained trials.

Fixtures
Fixture Purpose Expected Output
ec_loss_3_of_9.json tolerate m=3 shard loss reconstruction succeeds
ec_repair_5min.bench repair SLA ≤ 5 min, 1 TiB, 10 GbE
ec_placement_rack_violation.json insufficient rack diversity InsufficientReplicas
ec_hedge_latency.bench hedged read tail latency p99 ≤ 400 ms
Pitfalls
  • The k+1-of-k+m commit quorum is an operator-facing knob: too low risks too few shards on disk at commit time; too high makes routine maintenance flap PUTs.
  • Hedged reads waste one shard's worth of bandwidth per GET; disable per-bucket for capacity-sensitive workloads (P13).
  • EC and replication cannot coexist for the same fragment; a tier transition (§19) composes a new manifest rather than mutating in place (ADR-08 corollary).

⬜ Phase 4 — Multipart Upload §16

Objectives

The full multipart state machine: initiate, upload-part, complete, abort, list-parts, list-uploads — the operation every >5 GiB object and most >100 MB objects use.

Deliverable

A 100-part, 5 MiB-each multipart upload completes with the correct multipart-style ETag.

Acceptance

Uploading parts out of order (5, 3, 7) and completing succeeds with correct manifest ordering in 100% of 50 trials (I7 permits gaps, requires ascending); aborting a 99-part upload reaps all fragments within 5 minutes; a chaos test killing the gateway between UploadPart and Complete recovers via WAL replay and remains resumable.

Fixtures
Fixture Purpose Expected Output
mpu_out_of_order_5_3_7.json ascending-with-gaps validation manifest correctly ordered
mpu_abort_99_parts.json GC reap SLA 0 orphan fragments after 5 min
mpu_complete_mismatched_md5.json client-claimed MD5 wrong 400 InvalidPart
mpu_complete_after_abort.json state-machine race 409 Conflict
Pitfalls
  • A part-list MD5 mismatch is 400 InvalidPart; never silently accept it — clients depend on the validation.
  • The last part is the only one exempt from the 5 MiB minimum, validated only at Complete (not at UploadPart, since the last part isn't known until then); a non-last part under 5 MiB is 400 EntityTooSmall.
  • Complete racing Abort (or vice versa) is a known MinIO-class bug; the state check must be atomic with the transition, returning 409 Conflict.

⬜ Phase 5 — Sigv4 Authentication §17

Objectives

Every request Sigv4-signed and verified: canonical-request normalization, streaming chunked bodies, presigned URLs, access-key administration. PhaseDeferred("§17"): pre-signed POST (browser form-upload) is out of scope here (registered §37).

Deliverable

A verifier passing the AWS-published Sigv4 test-vector corpus; a streaming-body verifier; presigned URL generate/verify; an access-key admin surface.

Acceptance

100% pass on the aws-c-auth/tests/sigv4/ published test-vector corpus (named external fixture); the canonical-request fuzz target runs ≥ 1 CPU-hour with zero panics; verify throughput ≥ 50,000 verifications/s/core (M7).

Fixtures
Fixture Purpose Expected Output
aws_c_auth_sigv4_vectors/* published AWS test suite 100% pass
sigv4_multi_space_header.json header normalization signature verifies
sigv4_replay_outside_skew.json clock-skew rejection 403 SignatureDoesNotMatch
sigv4_streaming_chunk_bad_sig.json per-chunk streaming verify reject at the bad chunk
Pitfalls
  • Canonical-URI double-encoding is S3's documented quirk — get it backwards and every path containing % breaks.
  • Repeated query parameters must preserve original order within the same key.
  • The clock-skew tolerance (default 15 minutes, matching AWS) trades security against operability — too tight breaks legitimate clients, too loose widens the replay window (T2).

⬜ Phase 6 — Versioning, Delete Markers & Read-Consistency Model §18

Objectives

Bucket versioning (opt-in, P9), delete-marker semantics, list-versions, and the formal read-consistency contract (I14, ADR-25): strong intra-region, eventual cross-region.

Deliverable

A versioned bucket recording every PUT as a new version; a version-aware GET; a ?versions listing returning every (key, versionId) pair with IsLatest.

Acceptance

A 5-version put/list/delete-head/relist cycle correctly reveals each prior version in order; 10,000 sequential same-session read-after-write trials show 0 stale reads (I14); versioning-suspended-then-attempted-disable is rejected in 100% of trials (I5).

Fixtures
Fixture Purpose Expected Output
version_ladder_5_deep.json multi-version put/delete/list correct head at each step
raw_same_session_10k.json read-after-write, intra-region 0 stale reads
versioning_disable_attempt.json illegal downgrade rejected (I5)
delete_marker_of_delete_marker.json marker-on-marker reveals next-older version
Pitfalls
  • A delete-marker is itself a version; deleting one reveals the next-older version, it is not a true delete.
  • Versioning-suspended is not versioning-disabled — the ladder is retained permanently (P9).
  • The ?versions listing cursor is (key, versionId), not just key — get this wrong and pagination breaks across pages.

⬜ Phase 7 — Lifecycle Policies & Tiering §19

Objectives

The lifecycle rule evaluator: expiration, hot↔cold transition, AbortIncompleteMultipart, running once per bucket per day (ADR-07).

Deliverable

A lifecycle worker completing a full daily sweep per bucket; expire, transition, and abort-incomplete-multipart all functioning end-to-end.

Acceptance

1,000 objects with a 7-day expire rule are 100% expired within one worker cycle (24h ± 5 min jitter budget); a 30-day transition rule moves matching objects to the cold/EC tier with zero observed 404s during a continuous-GET-during-transition fixture; AbortIncompleteMultipart{days:1} aborts an MPU left open 2 days on the next run.

Fixtures
Fixture Purpose Expected Output
lifecycle_expire_7day_1k.json expiry cadence 100% expired within 1 cycle
lifecycle_transition_30day.json hot→cold, zero downtime 0 404s during transition
lifecycle_abort_incomplete_mpu.json MPU leak guard aborted on next run
lifecycle_crash_mid_sweep.json worker crash-resume resumes from cursor, no dup actions
Pitfalls
  • An unthrottled worker firing many deletes in one second floods the Raft log and starves user requests — rate-limit.
  • The worker must resume from its persisted cursor after a crash, never reprocess or skip (I11).
  • A failed transition (cold-tier disk full, network partition) is retried next cycle via a per-object retry cursor, never silently abandoned.

⬜ Phase 8 — Cross-Region Replication §20

Objectives

Asynchronous cross-region replication (ADR-12) mirroring writes to a destination bucket, without blocking the source write path.

Deliverable

A replication worker mirroring every PUT to a destination bucket within the target latency; a ?replication-status per-object endpoint.

Acceptance

Steady-state replication lag ≤ 60 s on a 1 Gbps inter-region link (M12); a 5-minute link-break with 100 queued writes fully drains within 10 minutes of link restoration; delete_marker:false verified to leave the destination's prior version untouched in 100% of trials.

Fixtures
Fixture Purpose Expected Output
crr_steady_state_lag.bench replication latency ≤ 60 s
crr_link_break_100_writes.json queue durability + drain 100% drained ≤ 10 min
crr_delete_marker_false.json delete replication opt-out destination unchanged
crr_loop_guard.json bidirectional misconfig no infinite replication
Pitfalls
  • Bidirectional replication misconfiguration is a known footgun (T8) — the trace-header guard (I9) is the structural defense, not operator discipline alone.
  • The queue must persist across worker restarts; an in-memory-only queue silently drops in-flight replication state.
  • A destination read immediately after a source PUT may legitimately 404 — this is documented eventual consistency (I14, ADR-25), not a bug.

⬜ Phase 9 — Object-Lock & Bucket Policies §21

Objectives

WORM object-lock (Governance/Compliance), legal hold, and bucket-policy evaluation. PhaseDeferred("§21"): IAM-style identity policies attached to access keys are out of scope here (registered §37).

Deliverable

A bucket configurable with ObjectLockConfig{default_mode:Compliance, default_days:365}; a bucket policy allowing anonymous GET on a public/ prefix and denying everything else.

Acceptance

A delete attempt on a Compliance-locked object returns 403 in 100% of 1,000 trials, before and after simulating a root-credential caller; the policy evaluator returns a stable decision across 10,000 varied principal/action/resource/condition combinations (named fixture policy_eval_10k.json).

Fixtures
Fixture Purpose Expected Output
compliance_delete_1000_trials.json WORM refusal 100% 403

legal_hold_expired_retention.json hold outlives retention still refused until hold cleared

Pitfalls
  • Compliance mode is permanent — there is no bucket-level escape hatch; the only recovery is a new bucket (T10).
  • Bucket policy and IAM policy interact in AWS; Phase 9 ships bucket policy only — identity policies are deferred (§37).
  • The condition-language subset implemented is documented; rare conditions (DateGreaterThan, etc. beyond the common set) are explicitly out of scope.

⬜ Phase 10 — Conditional Headers, Multi-Range & Conformance Polish §22

Objectives

If-Match/If-None-Match/If-Modified-Since/If-Unmodified-Since (RFC 7232), multi-range GET (RFC 7233), and a full run of the AWS-published s3-tests suite.

Deliverable

The full conditional-header matrix implemented and conformance-tested; multi-range GET returning correctly-framed multipart/byteranges.

Acceptance

The If-None-Match:* create-if-not-exists idiom under 50 concurrent racing writers admits exactly 1 winner in 100% of 200 trials; the AWS-published s3-tests external suite passes ≥ 95%.

Fixtures
Fixture Purpose Expected Output
if_none_match_star_race_50.json atomic create-if-not-exists exactly 1 winner/trial
multi_range_3_parts.json multipart/byteranges framing correctly framed 206
if_match_stale_etag.json conditional PUT 412 PreconditionFailed
s3_tests_external_suite.json AWS s3-tests conformance ≥ 95% pass
Pitfalls
  • If-None-Match:* requires the check-and-commit to be one atomic metadata RPC; a gateway-side check-then-write is a race that lets two concurrent writers both "win."
  • The multipart/byteranges boundary and per-part headers are finicky — copy exactly from RFC 7233's examples rather than improvising.

⬜ Phase 11 — Gateway Scale-Out, Admin REST, Scrubbing & Operator Tooling §23

Objectives

Horizontal gateway scale-out behind a load balancer; the mTLS admin REST surface; fsck; the scrubber; the rebalancer; the decommissioner; the orphan-fragment reaper — the phase that makes the cluster operable (P12).

Deliverable

A 3-gateway load-balanced tier; obs fsck / obs admin CLIs; scrub, rebalance, and decommission running against a 100-node test cluster.

Acceptance

fsck completes a 10M-object cluster scan ≤ 30 minutes (M11); the scrubber completes a full 1 PB sweep ≤ 7 days; the rebalancer converges a 100-node cluster from 30% to 5% utilization variance ≤ 4 hours (M10); the decommissioner drains a 10 TB node ≤ 1 hour.

Fixtures
Fixture Purpose Expected Output
fsck_10m_objects.bench full-cluster scan SLA ≤ 30 min
scrub_1pb_sweep.bench full scrub cycle ≤ 7 days
rebalance_convergence_100node.bench variance convergence 30%→5% ≤ 4h
decommission_10tb_node.bench node drain SLA ≤ 1 hour
rebalance_single_replica_refusal.json move-safety check move refused, not attempted
Pitfalls
  • Unthrottled scrubbing floods the network for days on a 1 PB cluster — the bandwidth budget must be operator-tunable.
  • The orphan-reaper quarantine window must exceed the longest plausible multipart upload (24h default; document the tradeoff for 7-day-upload workloads).
  • The rebalancer must never move the last surviving copy of a fragment — validate placement before every move, refusing any move that would create a single-replica window.
