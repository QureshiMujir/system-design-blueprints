107 — Object Storage (S3-like)

Project Number: 107

Project Name: Object Storage (S3-like)

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

A cluster-scale, S3-API-compatible object storage system in the Amazon S3 / Ceph RADOS Gateway / MinIO / OpenStack Swift lineage: an immutable, versioned blob store addressed by a (bucket, key, versionId) triple, exposed over a Sigv4-authenticated HTTPS REST surface, backed by a pluggable durability layer (three-way replication or Reed-Solomon erasure coding) and a Raft-replicated, LSM-structured metadata index, engineered for 99.999999999% (11-nines) annual durability with a per-read-path consistency contract (strong intra-region, eventual cross-region).

Phase-0 deliverable (numbered list of crates/services that must exist and interoperate):

  1. obj-core — load-bearing types (§11).
  2. obj-proto — protobuf wire schemas for the internal RPCs.
  3. obj-index — metadata service stub (in-RAM index, no WAL yet).
  4. obj-blob — blob node stub (single-replica flat-file fragment store).
  5. obj-gateway-s3 — single-node S3 REST gateway (PUT/GET/HEAD/DELETE only).
  6. obj-cli — the obs operator/user CLI (ls, cat).
  7. obj-conformance — the conformance runner with three buckets: core_types, bucket_ops, object_io.

System boundaries:

  • Provides: bucket/object CRUD, multipart upload, versioning, lifecycle and tiering, cross-region replication, object-lock (WORM), Sigv4 authentication, replicated and erasure-coded durability, background repair/scrub, an admin REST surface.
  • Delegates: Reed-Solomon encode/decode (rank 108), the write-ahead log (rank 71), Raft consensus (rank 39), the TLS handshake (rank 50); the shared chunk-server abstraction (rank 86) only where an operator co-locates a POSIX filesystem workload on the same disk pool — not required for the core system.
  • Does NOT provide: a POSIX filesystem interface; a SQL query layer over objects (Athena-style); a client-side-encryption SDK (documented as a client concern); a hierarchical namespace (keys are flat, opaque strings — §6 P1); an IAM identity-policy engine beyond per-bucket policy.

Non-goals: sub-millisecond latency (this is a bulk-object store, not a KV cache); a native BitTorrent/IPFS swarm surface; ListObjects v1 support (PhaseDeferred("§13") — V2 only, ADR-20).

Deployment model: containerized services (gateway, metadata node, blob node, lifecycle worker, replication worker) orchestrated by Kubernetes/Helm or docker-compose for development; the gateway tier is stateless and horizontally scaled behind a load balancer (§23).

Target users/operators: platform teams running an internal S3-compatible store for data-lake, backup, and CI-artifact workloads; SREs who debug placement, durability, and replication incidents from the runbooks referenced in the Repository Layout (§10).

What later phases unlock: multipart (§16) unlocks objects above 5 GiB; Sigv4 (§17) unlocks multi-tenant auth; versioning (§18) unlocks compliance workloads; lifecycle (§19) unlocks cost-tiering; replication (§20) unlocks disaster recovery; object-lock (§21) unlocks WORM/regulatory retention; §23 unlocks horizontal scale and self-healing operations.

Recommended language: Rust (edition 2021). Rationale: the data path (hashing, encoding, wire framing) is CPU- and memory-safety-sensitive; tokio + axum give async I/O without a GC-pause tax on tail latency; one language across gateway/metadata/blob/worker tiers gives one supervision tree and one dependency-audit surface (ADR-01). Rejected languages: Go (MinIO's choice) — simpler concurrency model, but GC pauses surface in P99 latency under memory pressure, and Reed-Solomon's hot loop is slower without SIMD intrinsics as ergonomic as Rust's; Java/JVM (Cassandra's choice) — rejected for GC-pause tail latency in the data path; a Go-gateway / Rust-storage split (ADR-01) — rejected: two runtimes, two dependency-audit surfaces, cross-language debugging cost.

Prerequisites: rank 108 (Erasure Coding) for the EC backend; rank 71 (Write-Ahead Log) for metadata persistence; rank 39 (Raft Consensus) for metadata HA; rank 50 (TLS/SSL Handshake) for transport security; comfort with tokio, HTTP/1.1 semantics, Sigv4 canonical-request normalization, and GF(2^8) field arithmetic.

Estimated timeline: Phase 0 in 2–3 weeks; the full 12-phase system in 10–13 months for a 2–4 engineer team.

Deferred features (each anchored with PhaseDeferred(...) to a real heading below, registered in §37):

  • ListObjects v1 pagination — PhaseDeferred("§13").
  • Pre-signed POST (browser form-upload) — PhaseDeferred("§17").
  • S3 Express One Zone-style single-AZ low-latency storage class — PhaseDeferred("§15").
  • IAM-style identity policies attached to access keys — PhaseDeferred("§21").
  • SQL-over-objects query engine (Athena-style, rank 92 integration) — PhaseDeferred("§1").
  • OpenStack Swift wire-compatibility shim — PhaseDeferred("§1").

2. Why Build This

  • The substrate everything else leans on. The data warehouse (rank 60) reads Parquet from an object store; the streaming engine (rank 65) checkpoints to one; the training pipeline (rank 80) reads TFRecords from one. An opaque store turns every downstream incident into a support ticket; a self-built one turns it into a placement audit and a fix.
  • Historically foundational. Dynamo (DeCandia et al., 2007, SOSP) is the design ancestor of every horizontally-scaled key-value store behind an object service — sloppy quorums, vector clocks, consistent hashing. Haystack (Beaver et al., 2010, OSDI) taught the industry the cost of a directory-per-object layout and the win of packing many small objects into one large file. f4 (Muralidhar et al., 2014, OSDI) generalized Haystack's idea into erasure-coded warm storage. Tectonic (Pan et al., 2021, FAST) folded a cluster filesystem and a warm-object service into one substrate a decade later.
  • Engineering muscles built. Content-addressed storage design; quorum and erasure-coded durability math; Sigv4 canonical-request normalization (the surface every implementation gets wrong at least once); background-repair systems design; multi-tenant authorization.
  • Cross-links. Shares the WAL with rank 71, Raft with rank 39, TLS with rank 50, erasure coding with rank 108, and the chunk-server abstraction with rank 86 (Distributed File System) — building this cements how those primitives compose into one production system.
  • Calibration value. An engineer who ships this owns the same toolbox the engineers at S3, MinIO, Ceph, and Backblaze had when they shipped their stores — with the source open to the builder.

What Mastery Looks Like

  • Can derive the durability of a replicated vs. erasure-coded pool from first principles (AFR, MTTR, replica/shard count) and defend the (6,3) EC default — Phase 3 (§15).
  • Can trace a Sigv4 canonical-request bug to the exact normalization step that produced it — Phase 5 (§17).
  • Can explain why multipart-complete is a metadata transition, not a blob rewrite, and what breaks if it isn't — Phase 4 (§16).
  • Can state precisely which reads are strongly consistent and which are eventual across a Raft-replicated metadata index and an asynchronously-replicated cross-region copy — Phase 6 (§18) and Phase 8 (§20).
  • Can design a lifecycle-rule evaluator that is idempotent under crash-restart — Phase 7 (§19).
  • Can operate a live cluster: run fsck, interpret a scrub report, drain a node without an availability dip — Phase 11 (§23).
  • Can articulate why WORM/compliance-mode retention must be enforced at the metadata layer, never the client — Phase 9 (§21).

Five properties, referenced throughout:

  1. The gateway is stateless (P4). Every byte a user PUTs is durably in the storage pool before the gateway acknowledges (I1). A gateway can be killed and replaced at any moment without data loss — the property that lets the gateway tier scale horizontally (§23).
  2. The metadata service is the sole authoritative writer of the index (P14, I13). Bucket creation, object insertion, version-id allocation, MPU state transitions, and placement decisions all go through the Raft-replicated state machine (§14).
  3. Objects are immutable (P2). A PUT to an existing key produces a new version, never an in-place mutation; there is no "overwrite" RPC, only "produce a new version" and "delete an old version" — removing the need for write leases on the data path.
  4. The data path is content-addressed (P6). Each fragment is stored under an xxh3 fingerprint; a SHA-256 verifies integrity at read time (I4). The blob layer does not know about buckets, keys, or versions.
  5. Failures are first-class (P11). Gateway death, blob-node death, rack/zone loss, metadata-leader loss, replication-link loss, partial multipart, partial lifecycle transition — each has a phase, a conformance fixture, and a runbook (§24, §25).

6. Design Principles

P1 — Buckets are flat; the object key is opaque. A key like 2024/05/12/log.json.gz looks hierarchical to a user; to the system it is one UTF-8 byte string. Tradeoff: no native directory rename. Operational implication: prefix-scan is the only "directory" surface. Violate it and hierarchy leaks into the metadata index, coupling it to rank 86.

P2 — Objects are immutable; mutation is a new version. A PUT to an existing key produces a fresh VersionId. Tradeoff: storage cost of retained old versions. Operational implication: GC (not overwrite) reclaims space. Violate it and write leases become necessary, destroying the fire-and-forget data path.

P3 — Metadata is small; data is large. Metadata is sized for object count, the blob layer for bytes; each scales independently. Tradeoff: an extra RPC hop for every data operation. Operational implication: metadata and blob capacity are planned separately. Violate it and one hot path starves the other under load.

P4 — The gateway is stateless. Every gateway holds nothing the user can lose. Tradeoff: every operation costs an RPC to metadata/blob. Operational implication: a gateway death is a connection reset, not an incident. Violate it and horizontal scale-out (§23) becomes unsafe.

P5 — Sigv4 is the only authentication surface. Tradeoff: legacy Sigv2 clients must migrate. Operational implication: one fuzz target, one conformance suite (§17). Violate it and the auth surface doubles along with its attack surface (T1).

P6 — Content is addressable; the network is never trusted. Every fragment carries an xxh3 storage key and a SHA-256 integrity check (I4, I6). Tradeoff: an extra hash pass per byte. Operational implication: corruption becomes an alarm, not a silent 200. Violate it and bitrot returns wrong bytes with a success code.

P7 — Durability is a per-bucket policy. Replication{rf} | Erasure{k,m} | Tiered{hot,cold}. Tradeoff: operational complexity of mixed-durability clusters. Operational implication: capacity planning is per-bucket, not cluster-wide. Violate it and a cost-sensitive bucket pays replication's 3× overhead unnecessarily.

P8 — Lifecycle is declarative and idempotent. Rules are (filter, action) pairs evaluated once per day per bucket (I11). Tradeoff: up to 24h latency on rule application. Operational implication: a crashed worker resumes from a cursor, never reprocesses. Violate it and a lifecycle sweep either floods the metadata log or double-applies actions.

P9 — Versioning is opt-in, never silently reversible. Once enabled, a bucket can be suspended (no new versions) but never returned to Unversioned (old versions persist). Tradeoff: permanent version-ladder storage cost. Operational implication: capacity planning must assume monotonic growth once versioning is on. Violate it and a "disable" path silently destroys the audit trail compliance depends on.

P10 — Object-lock is a hard barrier. A locked object refuses DELETE at the metadata layer regardless of caller privilege (I8). Tradeoff: no operator escape hatch in Compliance mode. Operational implication: the only recovery from a misconfigured Compliance bucket is a new bucket. Violate it and the compliance guarantee is fiction.

P11 — Failures are first-class. Every failure mode in §25 has a phase, a fixture, and a runbook. Tradeoff: engineering time spent on paths that "usually" don't happen. Operational implication: on-call has a runbook for every alarm in §24/§25. Violate it and incidents become improvisation.

P12 — Operations are the product. fsck, rebalance, decommission, scrub, and the lifecycle simulator are not afterthoughts (§23). Tradeoff: as much engineering time on tooling as on the gateway. Operational implication: a cluster is operable from day one of Phase 11. Violate it and the system is a toy that cannot be run in production.

P13 — Read-path hedging trades bandwidth for tail latency. An EC GET issues k+1 reads and uses the first k (§15.5). Tradeoff: wasted bandwidth on the unused read. Operational implication: hedging is a per-bucket, disableable knob for capacity-sensitive workloads. Violate it (disable indiscriminately) and P99 latency regresses under partial degradation.

P14 — Placement decisions live only in the metadata service. The gateway never picks storage nodes (I13); it asks. Tradeoff: an extra RPC before every PUT begins. Operational implication: a placement bug has one fix location, not N gateway copies. Violate it and placement logic drifts between gateway instances during a rolling upgrade.

8. Domain Model

8.1 Bucket / Key / Version Model

BucketName — 3–63 chars, lowercase, hyphenated, S3 lexical rules (§11.1). ObjectKey — opaque UTF-8, ≤ 1024 bytes (§11.1). VersionId — 128-bit, cluster-monotonic per (bucket, key) (I2). An object's identity is the triple; the version ladder for a key is Vec<(VersionId, Object)> ordered descending, the head being the "current" object (§18.1).

8.2 REST Wire Grammar

Request-line grammar (ABNF-style, RFC 5234 conventions):

request-target = "/" bucket [ "/" key ] [ "?" query ]
query          = param *( "&" param )
param          = key-name [ "=" value ]
range-value    = "bytes=" ( byte-range-spec / suffix-range-spec )
byte-range-spec   = first-byte-pos "-" [ last-byte-pos ]
suffix-range-spec = "-" suffix-length

Every documented S3 verb (PUT, GET, HEAD, DELETE, POST for multipart/batch) maps 1:1 to a MetadataService/BlobService RPC pair (§11.9–11.10); the gateway performs no business logic beyond translation, validation, and streaming (P4).

8.3 Storage Backend Record Layout

A blob node stores one file per fragment (Phase 0–2, ADR-23) or one file per EC shard (Phase 3+):

${BLOB_DATA_DIR}/<fragment_id_hex>            # replicated fragment (Phase 0-2)
${BLOB_DATA_DIR}/<fragment_id_hex>.shard-<i>  # EC data/parity shard, i in 0..k+m
${BLOB_DATA_DIR}/<fragment_id_hex>.meta       # size, hash, durability mode
${BLOB_DATA_DIR}/<fragment_id_hex>.crc        # one CRC32C per 64 KiB block

State per fragment (as tracked by obj-blob::fragment_store): Writing → Committed → {Quarantined | GcPending → Deleted}. Quarantined is entered only on checksum mismatch (I4); a quarantined fragment is excluded from placement and read paths until repaired.

8.4 Metadata Index (LSM-Tree)

The metadata index is an LSM-tree (O'Neil et al., 1996), chosen over a plain in-RAM BTreeMap once object counts exceed comfortable RAM residency: a MemTable (sorted skip-list, the live write target), a WAL (I3) guarding the MemTable, immutable SSTable segments flushed on checkpoint, and a background compactor merging segments (§14.3). Reads check the MemTable, then segments newest-first; range scans (prefix listing, §13.4) merge-iterate across all levels. This directly extends Petrov's B-Tree treatment (Database Internals) with the log-structured write path Kleppmann motivates in DDIA Ch.3.

8.5 Worked Example — PUT then GET

  1. Client PUTs /demo/hello.txt, body "hi" (2 bytes), Sigv4-signed.
  2. Gateway computes md5, xxh3 (⇒ FragmentId), sha256 in one streaming pass.
  3. Gateway calls MetadataService::put_object_begin → PutObjectTicket{ticket_id: 42}.
  4. Gateway calls BlobService::put_fragment(frag, bytes, plan); plan names 3 replica nodes (RF=3, P7) chosen by the metadata service (I13).
  5. Once the RF quorum (2 of 3) acks, gateway calls put_object_commit(ticket, manifest) → VersionId::NONE (unversioned bucket).
  6. Metadata service logs PutObjectCommit to the WAL (I3), applies it, returns.
  7. Gateway returns 200 OK, ETag: "<md5_hex>".
  8. A later GET /demo/hello.txt resolves the head version, streams the fragment from any replica, verifies SHA-256 (I4), returns the 2 bytes.

8.7 Failure-Path Example

A gateway crashes between step 4 and step 5 of §8.5 (blob write acked, commit not yet logged). Recovery: the ticket remains Allocating in the WAL; the recovery sweep (§14.4, FM-5) either finds no matching PutObjectCommit after the GC threshold and issues PutObjectAbort (fragment queued for GC, I10), or — if the client retries the same idempotency key — re-attempts the commit. No partial object is ever visible to a GET because the object index installs the manifest atomically (single WAL entry).

14. Phase 2 — Durable Replicated Storage Backend

14.1 Objectives

Add metadata durability (WAL + checkpoint, rank 71) and blob-layer 3-way replication (ADR-04); the Phase-0/1 in-RAM index and single-replica blob store did not survive a restart or a node loss — this phase makes both durable.

14.2 Detailed Implementation Steps

obj-wal delegates to rank 71's WriteAheadLog. Every metadata mutation is a MetadataWalOp variant, logged then applied ("log, then apply" — I3). The metadata index becomes the LSM-tree of §8.4: MemTable + WAL + periodic SSTable checkpoint + background compactor (O'Neil et al. 1996). CheckpointPolicy{max_wal_bytes, max_wal_age, max_uncheckpointed_ops} bounds replay time (§4's 90 s cold-start target). On the blob side, plan_replicated_placement (I13) selects 3 distinct nodes (P3, P7, ADR-04); a PUT commits once a 2-of-3 quorum acks (Dynamo's quorum concept, DeCandia et al. 2007); a GET degrades transparently to any 1 surviving replica.

14.3 Deliverable

A metadata service that survives kill -9 and reconstructs every bucket and object; a blob layer that tolerates 1-of-3 replica loss transparently on both read and write paths.

14.4 Acceptance Criteria

10K buckets + 100K objects survive a metadata-service restart bit-identical; WAL append throughput ≥ 80,000 ops/s on NVMe (M8); a test that kills 1 of 3 replicas mid-read still returns 200 OK with correct bytes in 100% of 500 trials; recovery sweep GCs every Allocating ticket older than the GC threshold (FM-5).

Fixture Purpose Expected Output

14.6 Pitfalls

  • The WAL must be fsync'd before the operation is acknowledged (I3) — async writeback is a correctness bug, not a performance choice.
  • The checkpoint must be atomic with respect to the WAL; Phase-2 takes the simpler quiesced-snapshot approach over copy-on-write (documented tradeoff, higher snapshot latency for lower implementation risk).
  • Replay must be idempotent: counters (version_id, ticket_id, mpu_id) are recorded in the log entry, never reallocated at replay time, or replay diverges from the original run.

15. Phase 3 — Reed-Solomon Erasure-Coded Backend

15.1 Objectives

Add Durability::Erasure{k:6,m:3} as an opt-in per-bucket durability mode (ADR-04, ADR-05) via rank 108's Reed-Solomon crate. PhaseDeferred("§15"): an S3-Express-One-Zone-style single-AZ low-latency class is out of scope here (registered §37).

15.2 Detailed Implementation Steps

obj-ec delegates to rank 108 (ReedSolomon::encode/decode, Reed & Solomon 1960, Plank 2007 Jerasure). plan_ec_placement(topology, bucket, fragment, k, m) returns k+m rack-diverse distinct nodes (I6); a request for more shards than the cluster can diversify refuses with InsufficientReplicas. The PUT path encodes once the fragment (or MPU part) is complete in memory, writes k+m shards in parallel, commits at a k+1-of-k+m quorum — the durability/availability knob (P7). The GET path reads k shards; if any fails, fetches the next parity shard; hedges by issuing k+1 reads from the start and using the first k (P13). Repair (triggered by scrub, §23, or heartbeat) reconstructs a lost shard from any surviving k via ReedSolomon::decode, throttled to a configurable fraction of cluster bandwidth (default 10%, Rashmi et al. 2014's repair-bandwidth analysis).

15.3 Deliverable

A bucket configurable as Erasure{k:6,m:3}; a PUT path placing 9 distinct, rack-diverse shards; a GET path reconstructing from any 6.

15.4 Acceptance Criteria

Killing 3 of 9 blob nodes mid-read still reconstructs correctly, p99 ≤ 400 ms hedged (M6); the repair worker restores a lost shard within 5 minutes on a 10 GbE LAN (M9); placement refuses to under-diversify (I6) in 100% of 200 rack-constrained trials.

15.5 Conformance Fixtures

Fixture Purpose Expected Output

15.6 Pitfalls

  • The k+1-of-k+m commit quorum is an operator-facing knob: too low risks too few shards on disk at commit time; too high makes routine maintenance flap PUTs.
  • Hedged reads waste one shard's worth of bandwidth per GET; disable per-bucket for capacity-sensitive workloads (P13).
  • EC and replication cannot coexist for the same fragment; a tier transition (§19) composes a new manifest rather than mutating in place (ADR-08 corollary).

15.7 Performance Concerns

Repair bandwidth cost is k× the shard size per shard repaired (Rashmi et al. 2014) — an EC cluster needs more provisioned repair bandwidth than a replicated one at the same per-node failure rate (§33 MM5).

15.8 Edge Cases

Fewer than k shards reachable (503); a rack-diversity violation at placement time; a second shard loss during an active repair of the first.

15.9 Failure Analysis

See FM-6 (≤3-of-9 shard loss, degraded) and FM-7 (>3-of-9, unavailable) in §25.

15.10 Operational Notes

Emit ec_repair_duration_seconds and placement_diversity_violation_total (T12); alert on sustained repair-queue depth as a leading indicator of correlated failure.

16. Phase 4 — Multipart Upload

16.1 Objectives

The full multipart state machine: initiate, upload-part, complete, abort, list-parts, list-uploads — the operation every >5 GiB object and most >100 MB objects use.

16.2 Detailed Implementation Steps

MpuState transitions InProgress → {Completing→Completed | Aborting→Aborted} | Expired (§11.7). CompleteMultipartUpload is one atomic metadata transition (ADR-08): validate every referenced part exists and its MD5 matches the client's claim, validate ascending part-number order with gaps permitted (I7), install a new ObjectManifest with one ManifestEntry per part, transition to Completed — one WAL entry (Bernstein, Hadzilacos, Goodman 1987, Ch.8 on atomic recovery). AbortMultipartUpload transitions to Aborting; the GC worker (§11.10, I10) reaps part fragments in the background. The multipart ETag is hex(md5(concat(part_md5s)))-N (§11.2).

16.3 Deliverable

A 100-part, 5 MiB-each multipart upload completes with the correct multipart-style ETag.

16.4 Acceptance Criteria

Uploading parts out of order (5, 3, 7) and completing succeeds with correct manifest ordering in 100% of 50 trials (I7 permits gaps, requires ascending); aborting a 99-part upload reaps all fragments within 5 minutes; a chaos test killing the gateway between UploadPart and Complete recovers via WAL replay and remains resumable.

Fixture Purpose Expected Output

16.6 Pitfalls

  • A part-list MD5 mismatch is 400 InvalidPart; never silently accept it — clients depend on the validation.
  • The last part is the only one exempt from the 5 MiB minimum, validated only at Complete (not at UploadPart, since the last part isn't known until then); a non-last part under 5 MiB is 400 EntityTooSmall.

17. Phase 5 — Sigv4 Authentication

17.1 Objectives

Every request Sigv4-signed and verified: canonical-request normalization, streaming chunked bodies, presigned URLs, access-key administration. PhaseDeferred("§17"): pre-signed POST (browser form-upload) is out of scope here (registered §37).

17.2 Detailed Implementation Steps

canonical_request(method, uri, query, headers, signed_headers, payload_hash) normalizes per the AWS Sigv4 spec and RFC 5234's ABNF conventions: sorted, percent-encoded query params; lowercase, whitespace-collapsed, sorted headers; payload_hash as hex(sha256(body)), UNSIGNED-PAYLOAD, or the streaming sentinel. Sigv4Verifier::verify derives the signing key, computes the expected signature, and compares with constant_time_eq::eq (I12, ADR-16) — a timing leak here is a CVE pattern. Streaming aws-chunked bodies are verified per-chunk as they stream, never deferred to whole-body-after-the-fact (a replay-vulnerability pattern). Presigned URLs sign a canonical request with X-Amz-Signature omitted; access keys are administered via the mTLS admin surface (§23.3) bootstrapped by a root key from an environment variable.

17.3 Deliverable

A verifier passing the AWS-published Sigv4 test-vector corpus; a streaming-body verifier; presigned URL generate/verify; an access-key admin surface.

17.4 Acceptance Criteria

100% pass on the aws-c-auth/tests/sigv4/ published test-vector corpus (named external fixture); the canonical-request fuzz target runs ≥ 1 CPU-hour with zero panics; verify throughput ≥ 50,000 verifications/s/core (M7).

Fixture Purpose Expected Output

  • Canonical-URI double-encoding is S3's documented quirk — get it backwards and every path containing % breaks.

18. Phase 6 — Versioning, Delete Markers & Read-Consistency Model

18.1 Objectives

Bucket versioning (opt-in, P9), delete-marker semantics, list-versions, and the formal read-consistency contract (I14, ADR-25): strong intra-region, eventual cross-region.

18.2 Detailed Implementation Steps

VersionIndex (§8.1) holds a (bucket,key) → VersionLadder map, versions: Vec<(VersionId, Object)> descending. A DELETE on a versioned bucket without versionId inserts a delete-marker version (itself a version, I2); a DELETE with versionId hard-removes that version (subject to object-lock, §21). A versioning-suspended bucket inserts delete-markers with a legacy null version. Read-after-write: any read served by the same metadata leader term as the write it follows returns that write (I14, Lamport 1979's sequential-consistency grounding); a cross-region replica read (§20) is documented eventual, matching Kleppmann DDIA Ch.9's consistency taxonomy and ADR-25.

18.3 Deliverable

A versioned bucket recording every PUT as a new version; a version-aware GET; a ?versions listing returning every (key, versionId) pair with IsLatest.

18.4 Acceptance Criteria

A 5-version put/list/delete-head/relist cycle correctly reveals each prior version in order; 10,000 sequential same-session read-after-write trials show 0 stale reads (I14); versioning-suspended-then-attempted-disable is rejected in 100% of trials (I5).

18.5 Conformance Fixtures

18.6 Pitfalls

  • A delete-marker is itself a version; deleting one reveals the next-older version, it is not a true delete.

18.7 Performance Concerns

18.8 Edge Cases

1,000+ versions of the same key; a delete-marker as head while an older version carries a legal hold; a versioned GET for a versionId that never existed (404 NoSuchVersion).

18.9 Failure Analysis

18.10 Operational Notes

19. Phase 7 — Lifecycle Policies & Tiering

19.1 Objectives

20. Phase 8 — Cross-Region Replication

20.1 Objectives

Asynchronous cross-region replication (ADR-12) mirroring writes to a destination bucket, without blocking the source write path.

20.2 Detailed Implementation Steps

Every put_object_commit on a replication-configured bucket enqueues a ReplicationQueue entry (persisted, survives worker restart). A replication loop is prevented by refusing to re-replicate any object arriving with an x-amz-replication-trace header (I9). Deletes replicate only if delete_marker:true is set on the rule (the documented default is false, a compliance-safety choice).

20.3 Deliverable

A replication worker mirroring every PUT to a destination bucket within the target latency; a ?replication-status per-object endpoint.

20.4 Acceptance Criteria

Steady-state replication lag ≤ 60 s on a 1 Gbps inter-region link (M12); a 5-minute link-break with 100 queued writes fully drains within 10 minutes of link restoration; delete_marker:false verified to leave the destination's prior version untouched in 100% of trials.

  • The multipart/byteranges boundary and per-part headers are finicky — copy exactly from RFC 7233's examples rather than improvising.

22.7 Performance Concerns

Conditional checks are evaluated before any data-path work begins, so a failed precondition costs one metadata RPC, never a wasted blob read.

22.8 Edge Cases

If-Match with a list of multiple ETags; overlapping multi-ranges (0-9,5-14); an If-Range header naming a now-stale ETag (falls back to a full 200 response, not 206).

22.9 Failure Analysis

A race between the conditional check and the manifest install must be closed by making both one atomic metadata RPC — a two-RPC implementation reintroduces the exact race the conditional header exists to prevent.

22.10 Operational Notes

precondition_failed_total and an s3_tests_pass_rate dashboard track conformance drift release over release.

23. Phase 11 — Gateway Scale-Out, Admin REST, Scrubbing & Operator Tooling

23.1 Objectives

Horizontal gateway scale-out behind a load balancer; the mTLS admin REST surface; fsck; the scrubber; the rebalancer; the decommissioner; the orphan-fragment reaper — the phase that makes the cluster operable (P12).

23.2 Detailed Implementation Steps

Gateways are stateless (P4) and deployed N-wide behind a health-checking, weighted round-robin load balancer. The admin REST surface runs on a separate port with mTLS (rank 50, ADR-11) — no Sigv4 here, this is operator territory. obs fsck cross-references the metadata index against every blob node's inventory, reporting missing fragments, orphans, checksum mismatches, and MPU/replication leak candidates (OpenStack Swift's auditor precedent). The scrubber walks the blob layer once per scrub_interval (default 7 days), verifying every fragment/shard checksum (I4, I6) and triggering repair on mismatch (Swift's replicator precedent). The rebalancer moves fragments to even utilization, refusing any move that would create a single-replica window (I10 corollary). The decommissioner drains a node to Decommissioned via the same rebalance machinery. The orphan reaper deletes unreferenced fragments after a 24h quarantine (accommodating in-flight multipart completions).

23.3 Deliverable

A 3-gateway load-balanced tier; obs fsck / obs admin CLIs; scrub, rebalance, and decommission running against a 100-node test cluster.

23.4 Acceptance Criteria

fsck completes a 10M-object cluster scan ≤ 30 minutes (M11); the scrubber completes a full 1 PB sweep ≤ 7 days; the rebalancer converges a 100-node cluster from 30% to 5% utilization variance ≤ 4 hours (M10); the decommissioner drains a 10 TB node ≤ 1 hour.

23.6 Pitfalls

  • Unthrottled scrubbing floods the network for days on a 1 PB cluster — the bandwidth budget must be operator-tunable.
  • The orphan-reaper quarantine window must exceed the longest plausible multipart upload (24h default; document the tradeoff for 7-day-upload workloads).

23.7 Performance Concerns

fsck cost is O(objects + fragments); scrub cost is O(bytes / bandwidth_budget) — both scale predictably and must be capacity-planned alongside user traffic.

23.8 Edge Cases

A node flapping (up/down) during an active rebalance; concurrent fsck and scrub contending for the same disk bandwidth budget; decommissioning the last healthy node in a rack that would otherwise leave a bucket under-diversified (I6).

27. Compatibility & Versioning

  • Wire compatibility: obj-proto field numbers are a commitment (ADR-15, §12.6) — a breaking change requires a new proto message version, never a field-number reuse.
  • Storage compatibility: the on-disk fragment/shard layout (§8.3) is versioned via the .meta sidecar's format field; a blob-node upgrade must read both the old and new layout during a migration window.
  • Schema evolution: the metadata LSM-tree's SSTable format (§8.4) carries a version byte; the compactor rewrites old-format segments opportunistically during normal compaction, never requiring a stop-the-world migration.
  • API stability: the documented S3 subset (docs/api/s3-subset.md) is the stability contract with clients; the admin REST surface (JSON, ADR-22) versions via /admin/v1/.
  • Deprecation policy: a deprecated field or endpoint is marked in CHANGELOG.md, supported for at least 2 minor releases, then removed with an explicit migration note.
  • SemVer policy: the workspace crates follow SemVer; a wire- or storage-format break is a major version bump cluster-wide, gated by the release-engineering process (§28).
  • Rolling-upgrade guarantees: any two adjacent minor versions of every service interoperate on the wire and on disk; this is gated by the conformance suite's version-skew fixtures.

31. Scalability Analysis

Stays constant: gateway request-handling cost per object (O(1) RPC fan-out, P4); per-object metadata footprint (~300 bytes, §33 row 3).

Grows: metadata index size (O(objects), sharded beyond ~200M objects/shard per §4); blob capacity (O(bytes × amplification), §4); repair bandwidth demand (O(node-failure rate × shard size), §15.7); replication queue depth under sustained link degradation (§20.7).

Named bottlenecks, in order: (1) metadata Raft-group write throughput — the single strongly-consistent write path (I13), bounded by fsync latency (M4, M8); (2) EC repair bandwidth under correlated failure (§15.7, MM5); (3) cross-region replication link capacity (§33 row 7); (4) lifecycle-worker Raft-log pressure under naive un-throttled deletion (§19.6).

Horizontal scaling: gateway tier scales linearly to the connection/FD limits in §4 (P4 makes this safe); blob-node tier scales linearly to ≥ 500 nodes (§4); metadata scales by sharding the index once a single Raft group's write throughput or RAM footprint is saturated (Petrov's partitioned-log pattern).

Vertical scaling: metadata-node RAM is the first vertical lever (MemTable + hot SSTable cache, §8.4); blob-node NVMe IOPS is the second (fragment/shard write path).

Sharding/partitioning: metadata shards by a consistent hash of BucketName once a single Raft group saturates; each shard is an independent Raft group with its own WAL/LSM-tree, coordinated only for cross-shard operations (none exist in the current domain model — bucket-scoped operations stay single-shard by design, P1/P3).

Coordination overhead: bounded to intra-shard Raft consensus (rank 39) and, cross-region, the asynchronous replication queue (§20) — there is no synchronous cross-shard or cross-region coordination path in the system (ADR-25).

Practical ceiling and levers beyond it: the practical ceiling for a single Raft-group metadata shard is ~200M objects (§4); the lever beyond it is index sharding (above); the practical ceiling for EC repair bandwidth is the provisioned inter-rack fabric bandwidth (§15.7); the lever beyond it is LRC (ADR-05's rejected-alternative regime) once repair bandwidth, not storage cost, is the binding constraint.

32. Mental Models & First Principles

MM1 — A manifest is a level of indirection that turns mutation into allocation. Predicts CopyObject is free (§13.2) and GC must be reference-counted (I10). Bug class without it: an engineer "optimizing" by writing bytes in place, breaking P2. Applies in §8.5, §16.

MM2 — Durability is a probability, not a boolean. Predicts you must compute AFR×MTTR math (§33), not just count replicas. Bug class without it: assuming RF=3 alone is "safe" without rack diversity (I6). Applies in §4, §33.

MM3 — Consistency is a per-read-path property, not a whole-system property. Predicts intra-region and cross-region reads can carry different guarantees simultaneously (I14). Bug class without it: a single doc comment claiming "the system is eventually consistent" that is wrong for half the read paths. Applies in §18, §20.

MM4 — The gateway is a stateless proxy; the metadata service is the truth. Predicts gateway crashes are free, metadata crashes are expensive (§3, P4, P14). Bug class without it: caching placement decisions in the gateway (I13 violation). Applies in §3, §14.

MM5 — Erasure coding trades repair bandwidth for storage cost. Predicts an EC cluster needs more provisioned repair bandwidth than a replicated cluster at the same node-failure rate (Rashmi et al. 2014). Bug class without it: sizing an EC cluster's network the same as a replicated one. Applies in §15, §33.

MM6 — A background worker that isn't idempotent is a data-loss bug waiting for a restart. Predicts every worker (lifecycle, GC, scrub, replication) needs a persisted cursor (I11). Bug class without it: a worker that reprocesses or skips work on crash-restart. Applies in §19, §25.

MM7 — Every state machine needs an explicit, recoverable state for every crash point. Predicts MpuState::Completing/Aborting exist precisely because a crash there is otherwise unrecoverable (§16.2). Bug class without it: designing only the happy-path states. Applies in §16, §25.

MM8 — The wire protocol is a contract with people you will never meet. Predicts you cannot silently change Sigv4 canonicalization or XML response shapes once clients exist (ADR-22, §27). Bug class without it: "cleaning up" the API surface post-launch and breaking every existing SDK integration. Applies in §17, §27.

Ceph RADOS/RGW uses CRUSH, a decentralized, computed placement function with no lookup table and no metadata-service bottleneck. This wins at extreme scale (10,000+ OSDs) where a centralized placement authority would itself become the bottleneck, at the cost of a harder-to-reason-about placement story when debugging a specific object's location.

OpenStack Swift commits to eventual consistency everywhere, with no strong metadata layer at all, backed by the longest production track record (since 2010) of any open-source object store. This wins for pure availability-over-consistency workloads, at the cost of the eventual-consistency semantics this system explicitly rejected (ADR-25) for versioning and compliance correctness.

Azure Storage (Calder et al. 2011) is the closest published architecture to this system's: a Stream Layer (append-only) plus a strongly-consistent Partition Layer plus a stateless Front-End — nearly the same three-tier split as this design's blob/metadata/ gateway. It wins by additionally exposing blobs, tables, and queues over one Stream Layer, a generality this project deliberately scopes out (§1 non-goals: object-only).

34. Back-of-Envelope Capacity Model

  1. RF=3 internal write bandwidth = PUT throughput × RF = 800 MB/s × 3 = 2,400 MB/s internal replication bandwidth per gateway (chained from §4's M1).
  2. EC(6,3) internal write bandwidth = PUT throughput × (k+m)/k = 800 MB/s × 1.5 = 1,200 MB/s — half the internal bandwidth of RF=3 for the same external throughput (chained from §4, explains ADR-04's cost tradeoff).
  3. Metadata RAM footprint = object_count × bytes_per_entry = 100,000,000 × 300 B ≈ 30 GB for a 100M-object metadata index (chains to §4's "sharded beyond ~200M objects" scaling assumption).
  4. FD ceiling per blob node = min(open_fragments, ulimit) — at 500,000 hot fragments against a 65,536 FD budget (§4), the design must pool/close idle fragment file handles once hot-fragment count exceeds 65,536.
  5. RF=3 durability ≈ 1 − (AFR × MTTR/8760h)^3, scaled by the combinatorial exposure of needing all 3 replicas to fail within the repair window. At AFR = 2% (published Backblaze disk-failure rates) and MTTR = 5 min (§4's RTO), the single-region annual loss probability per object is ≈ (0.02 × 5/525,600)^3 ≈ 6.9×10⁻¹⁵ — well past 11 nines, validating §4's durability target given rack diversity (I6).
  6. EC(6,3) durability requires 4 simultaneous shard failures (m+1) among 9 to lose data — combinatorially C(9,4) exposure vs. RF=3's C(3,3)=1 — meaning EC's per-object fragility is more sensitive to correlated (same-rack) failure than RF=3 at equal node count, which is exactly why placement enforces rack diversity (I6, ADR-05).
  7. Cross-region replication bandwidth ceiling = link_capacity / 8 = 1 Gbps / 8 = 125 MB/s sustainable replicated-write rate — far below §4's 800 MB/s local PUT throughput, which is why replication is asynchronous (ADR-12): synchronous CRR would throttle every local write to the WAN link's ceiling.
  8. Listing page size ceiling = max_keys × avg_XML_entry_bytes = 1,000 × 150 B ≈ 150 KB per ListObjectsV2 response page (chains to §4's max-concurrency planning for gateway response buffers).
  9. Multipart theoretical vs. actual ceiling = 10,000 parts × 5 GiB/part = 50,000 GiB theoretical, clipped to §4's 5 TiB object-size max — proving the object-size constraint, not the part-count/part-size constraint, is the binding limit (ADR-24).
  10. Scrub full-sweep bandwidth utilization = cluster_bytes / (scrub_window × aggregate_scrub_bandwidth) = 1 PB / (604,800 s × 10 GB/s) ≈ 16.5% of the 7-day budget at a 10 GB/s cluster-aggregate scrub rate — validating headroom for the 10% per-node throttle default (§23.6) even at petabyte scale.

Regime where it wins: globally-distributed, write-availability-over-consistency workloads (Dynamo's original shopping-cart use case). Real system: Amazon Dynamo / Riak. Rejected because: object-lock (I8) and versioning correctness (I5) need a linearizable metadata decision point; a leaderless AP design pushes that correctness burden into application-level reconciliation this project does not want to own.

A2 — Unified filesystem+object substrate (Tectonic-style).

        one chunk-server fleet serves both:
        POSIX filesystem namespace  <-->  object-store namespace
                    (shared storage, shared placement)

Regime where it wins: a single organization running both a cluster filesystem and an object store, wanting one storage fleet instead of two. Real system: Facebook Tectonic. Rejected because: this project explicitly delegates filesystem concerns to rank 86 and wants a narrower, independently shippable Phase-0 surface (§1 non-goals).

A3 — CRUSH-style decentralized placement (no central placement table).

        client/gateway --> CRUSH(cluster_map, object_id) --> placement
                     (computed, not looked up; no metadata-service hop)

Regime where it wins: extreme cluster sizes (10,000+ nodes) where a centralized placement authority becomes a bottleneck or single point of contention. Real system: Ceph/RADOS. Rejected because: the metadata service is already the strongly-consistent authority for every other decision (I13); adding CRUSH would create two sources of placement truth. Documented as an optional pluggable placement function (ADR-09), not the default.

A4 — Client/gateway-side erasure coding with no separate blob-node RPC tier (Backblaze-Vaults-style).

        gateway computes 20-shard (17+3) EC directly, writes each shard
        straight to a fixed storage-pod mapping — no metadata-index
        transaction per write, no blob-node abstraction layer

Regime where it wins: extreme-cold, extremely price-sensitive archival storage, where operational simplicity (a fixed pod mapping, no Raft cluster) outweighs feature flexibility. Real system: Backblaze Vaults (Backblaze Engineering, publicly documented architecture, 2015). Rejected because: this system needs a strongly consistent metadata index regardless, for versioning, lifecycle, and object-lock (I5, I8) — so the "no metadata service" simplification Vaults relies on does not actually apply once those features are in scope.

38. Glossary

Access key — the AccessKeyId/Secret pair used to Sigv4-sign requests (§11.8). ADR — Architecture Decision Record; this document's ADR table is §9. AFR — Annualized Failure Rate, a disk-reliability statistic used in §34's durability math. Bucket — the top-level namespace container for objects (§8.1). Bucket policy — a JSON-like statement list controlling principal/action/resource access (§11.9, §21). Canonical request — the normalized Sigv4 request form that is signed (§17.2). Checkpoint — a periodic snapshot of the metadata index that bounds WAL replay time (§14.3). Compaction — the LSM-tree background process merging SSTable segments (§8.4). Compliance mode — the irreversible object-lock retention mode (§21.2, I8). Conditional header — If-Match/If-None-Match/etc., RFC 7232 semantics (§22.1). Conformance suite — the obj-conformance fixture-driven test runner (§10.2, §28). Content addressing — storing a fragment under a hash of its bytes (§8.3, ADR-03). Continuation token — the opaque cursor for paginated listings (§13.2). Degraded read — a GET served despite a missing replica/shard (§14.2, §15.5). Delete marker — a version representing a logical delete on a versioned bucket (§18.2). Durability — the per-bucket policy selecting replication, erasure coding, or tiering (§11.5, §6 P7). Erasure coding (EC) — Reed-Solomon-based durability splitting data into k data + m parity shards (§15). ETag — an opaque content-identity token, MD5-derived for single/multipart objects (§11.2). Fragment — a content-addressed unit of stored bytes (§8.3, §11.4). Fsck — the operator tool cross-referencing metadata against blob-node inventory (§23.2). Gateway — the stateless S3 REST front-end (§3, §6 P4). Hedge (hedged read) — issuing k+1 reads and using the first k, trading bandwidth for tail latency (§6 P13). Legal hold — an independent hold preventing deletion regardless of retention (§21.2). Lifecycle rule — a declarative (filter, action) pair evaluated daily (§11.9, §19). LSM-tree — Log-Structured Merge-Tree, the metadata index's on-disk structure (§8.4). Manifest — the ordered list of fragment/shard references composing an object version (§11.4). Metadata service — the Raft-replicated authoritative index and placement decision maker (§3, §11.10). Multipart upload (MPU) — the chunked-upload protocol for large objects (§16). Object — one version of a (bucket, key) pair's data and headers (§11.6). Object-lock — WORM retention enforced at the metadata layer (§21). Orphan fragment — a fragment on disk referenced by no live manifest (§23.2, FM-11). Placement plan — the concrete set of storage nodes holding an object's fragments/shards (§11.5). Presigned URL — a Sigv4-signed URL granting temporary scoped access (§17.2). Quorum — the minimum number of replica/shard acknowledgments required to commit a write (§14.2, §15.2). RAID-adjacent term — rack diversity — placement spreading replicas/shards across failure domains (I6). Rebalancer — the worker evening fragment distribution across blob nodes (§23.2). Replication (cross-region) — asynchronous mirroring of writes to a remote bucket (§20). RF (replication factor) — the count of full copies stored under Durability::Replication (§11.5). Scrubber — the background worker verifying fragment/shard checksums on a cadence (§23.2). Shard — one data or parity fragment of an erasure-coded object (§8.3, §15.2). Sigv4 — AWS Signature Version 4, the request-signing scheme (§17). SSTable — an immutable, sorted, on-disk segment of the LSM-tree (§8.4). Streaming chunked body — an aws-chunked request body verified per-chunk (§17.2). Tiering — moving an object between hot and cold durability/cost classes (§11.9, §19.3). Version ladder — the ordered list of versions for a (bucket, key) pair (§18.2). VersionId — the monotonic 128-bit identifier distinguishing object versions (§11.1, I2). WAL (Write-Ahead Log) — the durability primitive metadata mutations are logged to before being applied (§14.2, I3). WORM — Write-Once-Read-Many, the property object-lock enforces (§21).
