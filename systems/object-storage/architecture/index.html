3. Architectural Overview

                       S3 clients (awscli, boto3, s5cmd, mc, ...)
                                     |
                                     | HTTPS, Sigv4
                                     v
        +----------------------------+----------------------------+
        |                          gateway                        |
        | axum HTTP | Sigv4 verifier | policy eval | range parser |
        | router    | conditional    | multipart    | OTel spans  |
        +------+-----------------+---------------------+---------+
               |                 |                     |
         metadata RPCs     blob put/get RPCs       admin REST (mTLS)
               |                 |                     |
       +-------v-------+ +-------v-------+     +-------v--------+
       |   metadata    | |   blob nodes   |     |  admin / ops   |
       | (Raft + WAL)  | | (storage pool) |     | rebalance / GC |
       | bucket/obj/   | | fragments/     |     | scrub / fsck   |
       | ver/mpu index | | shards on disk |     | lifecycle work |
       | LSM engine    | | CRC32C, EC k+m |     +-------+--------+
       +-------+-------+ +----------------+             |
               |          replication + cross-region     |
               +------------------------------------------+

Five properties, referenced throughout:

  1. The gateway is stateless (P4). Every byte a user PUTs is durably in the storage pool before the gateway acknowledges (I1). A gateway can be killed and replaced at any moment without data loss — the property that lets the gateway tier scale horizontally (§23).
  2. The metadata service is the sole authoritative writer of the index (P14, I13). Bucket creation, object insertion, version-id allocation, MPU state transitions, and placement decisions all go through the Raft-replicated state machine (§14).
  3. Objects are immutable (P2). A PUT to an existing key produces a new version, never an in-place mutation; there is no "overwrite" RPC, only "produce a new version" and "delete an old version" — removing the need for write leases on the data path.
  4. The data path is content-addressed (P6). Each fragment is stored under an xxh3 fingerprint; a SHA-256 verifies integrity at read time (I4). The blob layer does not know about buckets, keys, or versions.
  5. Failures are first-class (P11). Gateway death, blob-node death, rack/zone loss, metadata-leader loss, replication-link loss, partial multipart, partial lifecycle transition — each has a phase, a conformance fixture, and a runbook (§24, §25).

8. Domain Model

8.1 Bucket / Key / Version Model

BucketName — 3–63 chars, lowercase, hyphenated, S3 lexical rules (§11.1). ObjectKey — opaque UTF-8, ≤ 1024 bytes (§11.1). VersionId — 128-bit, cluster-monotonic per (bucket, key) (I2). An object's identity is the triple; the version ladder for a key is Vec<(VersionId, Object)> ordered descending, the head being the "current" object (§18.1).

8.2 REST Wire Grammar

Request-line grammar (ABNF-style, RFC 5234 conventions):

request-target = "/" bucket [ "/" key ] [ "?" query ]
query          = param *( "&" param )
param          = key-name [ "=" value ]
range-value    = "bytes=" ( byte-range-spec / suffix-range-spec )
byte-range-spec   = first-byte-pos "-" [ last-byte-pos ]
suffix-range-spec = "-" suffix-length

Every documented S3 verb (PUT, GET, HEAD, DELETE, POST for multipart/batch) maps 1:1 to a MetadataService/BlobService RPC pair (§11.9–11.10); the gateway performs no business logic beyond translation, validation, and streaming (P4).

8.3 Storage Backend Record Layout

A blob node stores one file per fragment (Phase 0–2, ADR-23) or one file per EC shard (Phase 3+):

${BLOB_DATA_DIR}/<fragment_id_hex>            # replicated fragment (Phase 0-2)
${BLOB_DATA_DIR}/<fragment_id_hex>.shard-<i>  # EC data/parity shard, i in 0..k+m
${BLOB_DATA_DIR}/<fragment_id_hex>.meta       # size, hash, durability mode
${BLOB_DATA_DIR}/<fragment_id_hex>.crc        # one CRC32C per 64 KiB block

State per fragment (as tracked by obj-blob::fragment_store): Writing → Committed → {Quarantined | GcPending → Deleted}. Quarantined is entered only on checksum mismatch (I4); a quarantined fragment is excluded from placement and read paths until repaired.

8.4 Metadata Index (LSM-Tree)

The metadata index is an LSM-tree (O'Neil et al., 1996), chosen over a plain in-RAM BTreeMap once object counts exceed comfortable RAM residency: a MemTable (sorted skip-list, the live write target), a WAL (I3) guarding the MemTable, immutable SSTable segments flushed on checkpoint, and a background compactor merging segments (§14.3). Reads check the MemTable, then segments newest-first; range scans (prefix listing, §13.4) merge-iterate across all levels. This directly extends Petrov's B-Tree treatment (Database Internals) with the log-structured write path Kleppmann motivates in DDIA Ch.3.

8.5 Worked Example — PUT then GET

  1. Client PUTs /demo/hello.txt, body "hi" (2 bytes), Sigv4-signed.
  2. Gateway computes md5, xxh3 (⇒ FragmentId), sha256 in one streaming pass.
  3. Gateway calls MetadataService::put_object_begin → PutObjectTicket{ticket_id: 42}.
  4. Gateway calls BlobService::put_fragment(frag, bytes, plan); plan names 3 replica nodes (RF=3, P7) chosen by the metadata service (I13).
  5. Once the RF quorum (2 of 3) acks, gateway calls put_object_commit(ticket, manifest) → VersionId::NONE (unversioned bucket).
  6. Metadata service logs PutObjectCommit to the WAL (I3), applies it, returns.
  7. Gateway returns 200 OK, ETag: "<md5_hex>".
  8. A later GET /demo/hello.txt resolves the head version, streams the fragment from any replica, verifies SHA-256 (I4), returns the 2 bytes.

8.6 Malformed-Input Examples

Input Expected Handling
Bucket name "-bad-" (leading/trailing hyphen) 400 InvalidBucketName at parse (§11.1)
Key of 1025 bytes 400 KeyTooLong
Range: bytes=500-100 (start > end) 416 InvalidRange
Authorization header with a mismatched x-amz-date 403 SignatureDoesNotMatch (I12)
Content-MD5 header not matching the body 400 BadDigest
partNumber=10001 on UploadPart 400 InvalidPartNumber (I7)

8.7 Failure-Path Example

A gateway crashes between step 4 and step 5 of §8.5 (blob write acked, commit not yet logged). Recovery: the ticket remains Allocating in the WAL; the recovery sweep (§14.4, FM-5) either finds no matching PutObjectCommit after the GC threshold and issues PutObjectAbort (fragment queued for GC, I10), or — if the client retries the same idempotency key — re-attempts the commit. No partial object is ever visible to a GET because the object index installs the manifest atomically (single WAL entry).
