Decisions (§9) · 28 ADRs

ADR-01

Language

Chosen

Rust 2021, MSRV 1.78

Rejected

C, Go, Python

When the rejected choice is right

C wins when you must interop with a C ABI, have no Rust toolchain, or need platform-intrinsic code that Rust std::arch cannot yet express (e.g., embedded DSP targets). Go wins for a quick throwaway script where GC pauses don't matter. Python wins for a 100-line research prototype to verify algorithmic correctness before implementing in a systems language.

Why: Untrusted-input decoder demands memory safety + no GC; slice bounds + checked indexing + enums model bitstreams cleanly; C = unsafe decoder on adversarial input; Go = GC + weaker bit-level layout; Python = too slow

ADR-02

Workspace layout

Chosen

6 comp-* crates in Cargo workspace

Rejected

single crate; 2 crates

When the rejected choice is right

A single crate wins when the project is a library-only deliverable, the total codebase is < 1 000 lines, and you want to minimise Cargo.toml boilerplate. Two-crate split wins when there is one no_std library and one std CLI with no further decomposition needed.

Why: Isolation: comp-core/lz/entropy/format/dict are no_std+alloc, comp-cli is std; enables embedded targets; clear dependency DAG; each crate has its own fuzz harness

ADR-03

no_std + alloc for core crates

Chosen

comp-core, comp-lz, comp-entropy, comp-format, comp-dict

Rejected

std throughout

When the rejected choice is right

std throughout wins when the codec is only ever used on Linux/macOS servers, you want std::io::Read/Write ergonomics natively, and you have zero embedded/WASM requirements. The extra no_std discipline is dead weight in that scenario.

Why: Decoder runs on bare-metal / WASM targets; alloc-bounded (no unbounded Vec growth without size guard); comp-cli alone uses std

ADR-04

Bit I/O convention

Chosen

LSB-first BitWriter / BitReader (comp-core)

Rejected

MSB-first (deflate style)

When the rejected choice is right

MSB-first wins when you are building a DEFLATE-compatible codec (RFC 1951 mandates MSB-first Huffman bit ordering), or integrating with hardware AES-GCM or HDLC streams that are MSB-first by protocol.

Why: FSE/tANS naturally reads LSB-first; aligns with zstd/FiniteStateEntropy reference; MSB-first would require bit-reversal on FSE integration

ADR-05

Sequence representation

Chosen

Sequence { literal_length, match_length, offset } grouped struct

Rejected

flat token stream (LITERAL / MATCH alternating)

When the rejected choice is right

Flat token stream wins when implementing DEFLATE or LZ4, where the wire format interleaves literal and match tokens and a grouped struct would require an extra transformation pass before bitstream emission.

Why: Matches zstd's internal model; LL/ML/OF decompose directly to 3 FSE streams; no extra tagging bits; repeat-offset codes encoded in the offset field (1..=3)

ADR-06

Match finder I (default)

Chosen

HashChainFinder (hash_log bits head + prev chain)

Rejected

suffix automaton, suffix array

When the rejected choice is right

Suffix arrays win for offline compression where the entire input is available before encoding and you need the provably-optimal longest match without a search_depth cap (e.g., archival xz --extreme). Suffix automata win for streaming dictionary problems (substring matching, not LZ77 compression).

Why: O(search_depth) per position; tunable depth per level; simple append-only structure; good ratio/speed tradeoff at Fast/Default levels

ADR-07

Match finder II (Optimal)

Chosen

BtFinder (binary-tree, greater/less child arrays)

Rejected

HC4 lazy + more depth; suffix automaton

When the rejected choice is right

HC4 with more depth wins when you want near-optimal ratio at lower memory cost than BtFinder (no greater/less arrays, only the hash-chain prev array) and you can tolerate the O(search_depth × position) cost rather than the BtFinder's logarithmic tree walk.

Why: BtFinder finds all matches at all lengths in one pass → required by OptimalParser for exact price minimization; suffix automaton: higher memory, complex build

ADR-08

Parse strategy

Chosen

Greedy / Lazy / Optimal selectable via Strategy enum

Rejected

always-greedy; always-optimal

When the rejected choice is right

Always-greedy wins for real-time low-latency pipelines (live video, telemetry) where any added latency from lookahead is unacceptable. Always-optimal wins for archival-only tools where encode time is irrelevant and ratio is the single objective.

Why: Greedy = max speed; Lazy = +1 lookahead, ~1–2% ratio gain over greedy for low cost; Optimal = best ratio, ~3–5× slower encode; user selects via CompressionLevel

ADR-09

Repeat offsets

Chosen

RepeatOffsets { recent: [u32; 3] }, LRU per zstd rules

Rejected

no repeat offsets

When the rejected choice is right

Omitting repeat offsets wins when targeting DEFLATE or LZ4 format compatibility (neither has a repeat-offset mechanism), when the input is random binary data with no recurring offset patterns, or when decoder simplicity is the overriding constraint.

Why: Repeat offsets recover ~0.5–2% ratio on structured data (source code, JSON) with near-zero cost; 3-slot LRU is the minimal implementation matching the format model

ADR-10

Huffman implementation

Chosen

Canonical length-limited via package-merge, max_len=11

Rejected

Shannon-Fano; plain Huffman without length limit; max_len=15

When the rejected choice is right

max_len=15 wins when you need slightly better compression on alphabets with very skewed distributions and you can afford a 16 KiB decode table (L2 resident). Plain Huffman without length limit wins for a pure-software toy implementation where table size is not a concern. Shannon-Fano wins for a teaching demonstration of greedy code assignment.

Why: max_len=11 → decode table = 2^11 = 2048 entries, fits L1; package-merge = provably optimal length-limited assignment; max_len=15 doubles table, diminishing returns

ADR-11

Literals multi-stream layout

Chosen

4-stream jump table (default for ≥1 KiB literals) + 1-stream fallback

Rejected

single stream always

When the rejected choice is right

Single-stream always wins on an in-order embedded processor (e.g., Cortex-M0) where OOO execution is absent and the overhead of tracking four BitReader positions exceeds any parallelism benefit. Also wins for extremely small literal sections where 4-way split is sub-optimal.

Why: 4 independent streams enable 4-way instruction-level parallelism on modern CPUs; jump table adds 6 bytes overhead; decoder falls back to 1-stream for small blocks

ADR-12

FSE table_log default

Chosen

LL=6, ML=6, OF=5 (following zstd defaults); range [5, 9]

Rejected

fixed table_log=8; adaptive per-block

When the rejected choice is right

fixed table_log=8 wins when your distribution is nearly uniform (random binary data) and you need the full 256-state resolution to avoid the rounding penalty of 64-state tables. Adaptive per-block wins in experimental contexts where input statistics change dramatically across blocks.

Why: Matches reference tables (Predefined mode); 2^6=64 and 2^5=32 state entries fit in cache lines; larger logs improve ratio <0.1% at 2× memory cost

ADR-13

FSE normalization rule

Chosen

"less than 1 probability" → count = 1 (-1 marker in i16); normalize_counts ensures sum = 2^table_log

Rejected

floor-rounding only; discard zero-count symbols

When the rejected choice is right

Floor-rounding with zero-symbol discard wins when you pre-filter the alphabet before building the table and you can guarantee that all symbols with positive probability have sufficient frequency to survive floor rounding (e.g., alphabet size ≤ 8 on a large corpus).

Why: -1 marker preserves rare symbols (omitting them breaks decode); Duda/FiniteStateEntropy canonical rule; avoids degenerate tables

ADR-14

Third entropy backend

Chosen

RangeEncoder / RangeDecoder (arithmetic coder) included

Rejected

omit arithmetic coder entirely

When the rejected choice is right

Omitting the arithmetic coder wins for a pure-production codebase where code size and maintenance burden are the primary concerns and there is no pedagogic or research agenda. The range coder adds ~600 lines for a backend that is never selected by the default frame format.

Why: Teaching + comparison backend; validates entropy lower-bound; future: context-adaptive model atop range coder; not used in primary frame format (FSE+Huffman)

ADR-15

Frame format magic

Chosen

Own magic 0xFD2F_B528 (distinct from zstd's 0xFD2F_B52B)

Rejected

clone zstd's magic for instant interop

When the rejected choice is right

Cloning zstd's magic wins when the explicit goal is to produce frames decodable by the stock zstd CLI and library — i.e., if this project were a drop-in zstd replacement with byte-exact format compatibility. In that case, the magic must match and the full normative format (RFC 8878) must be implemented exactly.

Why: We are zstd-STYLE, not zstd-compatible at Phase-0; own magic prevents decoders from silently accepting our frames as valid zstd; stretch goal: add zstd-decode probe in Phase 13

ADR-16

Content checksum

Chosen

xxhash64 (lower 32 bits stored)

Rejected

CRC32; Adler-32; full 64-bit xxhash

When the rejected choice is right

CRC32 wins when hardware acceleration is present (Intel CRC32 instruction, ARMv8 crc32 ISA extension) and you need an industry-standard checksum that integrates with external tools (ZIP, iSCSI, Ethernet). Full 64-bit xxhash wins when you need stronger collision resistance for content-addressed storage (e.g., dedup pipelines).

Why: xxhash64 = fast (>10 GB/s), low collision rate, no table needed; lower 32 bits sufficient for corruption detection; CRC32 = slower for same protection; Adler-32 = weaker

ADR-17

Dictionary format

Chosen

Dictionary { id: u32, entropy: EntropyTables, content: Box<[u8]> } with own magic

Rejected

raw content only (no entropy pre-training)

When the rejected choice is right

Raw-content-only wins when the target file set is homogeneous in content but heterogeneous in symbol distribution across samples (e.g., mixed text/binary archives), so a shared entropy table would hurt rather than help. Also wins for simpler dict implementations where entropy pre-training is not worth the added format complexity.

Why: Pre-built entropy tables avoid cold FSE/Huffman on small inputs; id → frame dict_id → decoder validation; content primes MatchFinder history

ADR-18

Dictionary trainer

Chosen

COVER-lite (suffix sampling + frequency scoring)

Rejected

random segment sampling; full COVER (expensive)

When the rejected choice is right

Random segment sampling wins when the total corpus is small (< 1 000 samples × 1 KB each), training latency is more important than 2–4% ratio, and you can afford the ratio gap. Full COVER wins for offline, high-value dictionary builds (e.g., a CDN serving millions of similar JSON API responses) where training time is hours but the resulting dictionary is used billions of times.

Why: COVER-lite: O(n log n) build, good coverage on typical inputs; full COVER: O(n²) impractical for large corpora; random sampling: 2–4% worse ratio on code/text

ADR-19

Streaming window management

Chosen

Ring-buffer window, carry history across blocks within a frame; flush = emit block, reset only between frames

Rejected

flush = full reset; no streaming (whole-file only)

When the rejected choice is right

Flush-full-reset wins when each block is independently decodable (parallel decode, random access, per-block error recovery) and cross-block ratio gain is acceptable to sacrifice. No-streaming wins for a pure archival batch tool where the entire file is available in memory.

Why: Streaming required for real-world pipe usage; cross-block back-references (window spanning blocks) are critical for ratio on large inputs; frame-boundary reset is safe

ADR-20

Default block size

Chosen

128 KiB

Rejected

64 KiB; 256 KiB; adaptive

When the rejected choice is right

64 KiB wins for very low-latency streaming (e.g., live transcription, real-time telemetry) where a 128 KiB buffer flush creates unacceptable tail latency. 256 KiB wins for batch archival when throughput is more important than latency. Adaptive wins for mixed workloads where block size self-tunes to input entropy.

Why: 128 KiB: empirically balances ratio (larger = more match candidates) vs latency (smaller = faster flush); matches zstd default; adaptive adds complexity with <1% ratio gain

ADR-21

Decoder output + window caps

Chosen

Output cap = min(content_size_field, DECODER_OUTPUT_MAX); window cap = DECODER_WINDOW_MAX = 128 MiB default

Rejected

no cap; trust content_size field

When the rejected choice is right

No-cap (trust content_size) wins when the decompressor runs in a trusted environment (same-process, same-machine, no adversarial input), the operator controls both encoder and decoder, and the cost of the cap check is measurable on very high-throughput pipelines (≥5 GB/s).

Why: Untrusted input: a malicious frame with content_size = 2^63 would pre-allocate ≫ RAM; caps enforced before allocation; configurable upper bound for CLI override

ADR-22

SIMD match acceleration

Chosen

Deferred to Phase 11 (opt-in via feature flag)

Rejected

Phase 0 SIMD; always-on SIMD

When the rejected choice is right

Phase-0 SIMD wins when the project targets a specific known platform (e.g., server-only x86-64) and throughput is a hard requirement from day one. Always-on SIMD wins for a hardware-specific embedded codec (e.g., a dedicated NEON-accelerated codec for an ARMv8 SoC) where portability is not required.

Why: Correctness first; SIMD complicates no_std + cross-target builds; Phase 11 wraps in #[cfg(target_feature)] with scalar fallback

ADR-23

Multithreaded compression

Chosen

Deferred opt-in phase (Phase 11); frame-level parallelism only

Rejected

always parallel; block-level parallel default

When the rejected choice is right

Always-parallel wins for a standalone CLI tool (like pigz or zstdmt) where the user always has > 1 core available and encode throughput is the primary UX metric. Block-level parallel default wins when compressing many independent large files (archival) and cross-block references are not needed.

Why: Sequential decode is simpler + correct; parallel encode splits into independent frames; block-parallel requires shared state (window synchronization) — deferred

ADR-24

Fuzz testing

Chosen

cargo-fuzz harnesses: fuzz_compress_decompress (identity) + fuzz_decode_never_panics

Rejected

property tests only; manual corpus

When the rejected choice is right

Property-tests-only wins for a codec used exclusively in an internal trusted environment where the decoder never processes untrusted bytes and fuzz infrastructure maintenance cost exceeds perceived value. Manual corpus wins in resource-constrained projects with no CI budget for fuzz runs.

Why: Decoder is the security surface; libFuzzer coverage-guided fuzzing finds truncated/corrupt-frame bugs that hand-written tests miss; both harnesses run in CI

ADR-25

Differential oracle

Chosen

zlib CLI + zstd CLI as external comparison (ratio + throughput benchmarks in Phase 13)

Rejected

no external oracle

When the rejected choice is right

No-oracle wins when the codec targets a niche domain (hardware-specific, domain-specific corpus) where zlib/zstd ratios are not meaningful comparisons, and internal round-trip correctness is the only required gate.

Why: Validates our ratio is competitive; catches regressions; zstd decode probe (STRETCH) validates frame-level interop

ADR-26

Benchmark framework

Chosen

criterion crate + real corpora (Calgary, Canterbury, Silesia, enwik8 slice)

Rejected

std::time microbench; synthetic random data

When the rejected choice is right

std::time microbench wins for quick iteration during algorithm development where statistical rigor adds overhead. Synthetic random data wins when specifically measuring incompressible-input overhead (Raw block election, entropy detection path) rather than compression ratio.

Why: criterion = statistical rigor, wall-clock + throughput; real corpora = representative compression ratios; random data = incompressible, not useful for ratio regression

ADR-27

Dependency policy

Chosen

Zero compression deps in comp-core/lz/entropy/format/dict; comp-cli may use clap, memmap2

Rejected

pull in flate2, zstd crate

When the rejected choice is right

Pulling in flate2/zstd wins when the goal is a convenience wrapper or a higher-level archive tool (e.g., tar + compression) rather than a from-scratch codec implementation. Appropriate for tools, not for a learning/portfolio project.

Why: Pulls would invalidate "from-scratch" claim + conflate our codec with theirs; also prevents circular dependency in fuzz differential

ADR-28

License

Chosen

MIT OR Apache-2.0 (SPDX)

Rejected

GPL; MIT-only; proprietary

When the rejected choice is right

GPL wins when you explicitly want copyleft reciprocity — preventing proprietary forks while requiring derivative works to publish source. MIT-only wins for maximum simplicity when patent grant is not a concern. Proprietary wins for commercial products where the codec is a competitive advantage.

Why: Dual MIT/Apache-2.0 = standard Rust ecosystem convention; Apache-2.0 provides patent grant; GPL would restrict embedding in non-GPL projects

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1: Context-Adaptive Range Coder (LZMA-style)

Input bytes
    │
    ▼ LZMA BtFinder (4-byte hash)
Match candidates
    │
    ▼ Adaptive probability models (per bit, per context)
      literal contexts: 256×3 models
      match/rep bit:    32+ models
    │
    ▼ Range coder (arithmetic) with per-model updates
    │
    ▼ .lzma / .xz frame

Regime where it wins: archival compression where encode time is unconstrained, ratio is the sole metric, and input is text or structured binary. LZMA achieves 10–20% better ratio than FSE-based codecs because adaptive context models track local statistics that a static per-block histogram misses.

Real system: LZMA2 (7-zip, Igor Pavlov, 2001), XZ Utils (Lasse Collin, 2009), used in Linux kernel tarballs, Debian packages, and .xz format.

Why rejected: encode throughput of ~5–15 MB/s is incompatible with the ≥300 MB/s Fast-level target. Per-bit probability updates add O(n × context_count) state transitions on the encode path. The range coder is included as RangeEncoder for teaching, but the full LZMA context model (256-tree literal models, length/distance models) is out of scope.

Alt-2: Purely Byte-Oriented Huffman + LZ77 (DEFLATE-style)

Input bytes
    │
    ▼ Hash-chain match finder (single pass)
Literal + match tokens (combined stream)
    │
    ▼ Combined literal/length Huffman tree (288 symbols)
       + separate distance Huffman tree (32 symbols)
    │
    ▼ DEFLATE block (RFC 1951)

Regime where it wins: format ubiquity. When the compressed output must be decodable by any device on Earth (PNG, ZIP, HTTP, TLS), DEFLATE is the only option. The combined literal/length tree simplifies the format at the cost of coupling two different symbol distributions. Decoder complexity is lower (one tree format, no FSE state machine).

Real system: zlib (Gailly/Adler, 1995), DEFLATE (Deutsch, RFC 1951), used in every browser, OS, and network stack.

Why rejected: FSE achieves ~5–10% better ratio than Huffman on the LL/ML/OF streams at equal or higher decode throughput (decode table lookup is O(1) for both). Separating literal coding (Huffman) from sequence-symbol coding (FSE) is strictly more flexible. DEFLATE's combined tree is a legacy artifact of wanting one wire format for both.

Alt-3: Block-Independent Compression (LZ4-style)

Input bytes
    │
    ▼ Hash table (1 entry per 4-byte hash, no chain)
Match candidates (max 1 per position)
    │
    ▼ Token stream: literal_length | match_length | offset
       encoded as fixed-width fields (no entropy coding)
    │
    ▼ LZ4 block format

Regime where it wins: ultra-low-latency and hardware simplicity. LZ4's decoder is a simple copy loop with no entropy decoding state machine, achieving 2–5 GB/s decode throughput on commodity hardware. This wins for in-memory caching tiers (Redis RDB compression, RocksDB kLZ4Compression), real-time log pipelines, and any setting where decode latency dominates over ratio.

Real system: LZ4 (Yann Collet, 2011), used by Redis, Kafka, RocksDB, Hadoop, and many in-memory stores.

Why rejected: LZ4 achieves only ~2:1 compression ratio on text (vs. 3:1+ for this design at Default). Omitting entropy coding forfeits the entire entropy-coding gain. For the portfolio goal of building a complete entropy-aware codec from first principles, skipping FSE would omit the most technically interesting component.

Alt-4: Asymmetric Shared-Format (Brotli-style)

Input bytes
    │
    ▼ Hash + context model match finder
Literals + matches
    │
    ▼ Context map (64 context clusters × per-cluster Huffman trees)
    │
    ▼ 11 MB static web dictionary lookup
    │
    ▼ Brotli frame (RFC 7932)

Regime where it wins: web content delivery. The 11 MB static dictionary recognizes common HTML/CSS/JS tokens without training, and the context map routes different byte contexts through different Huffman tables (e.g., ASCII lower vs upper half, after < vs after >). This achieves the best ratio on homogeneous web assets at the cost of an 11 MB bundled dictionary and higher decode complexity.

Real system: Brotli (Alakuijärvi/Kliuchnikov, Google, 2013–present), mandatory in HTTP/2 Accept-Encoding: br, used by all major CDNs.

Why rejected: The 11 MB static dictionary is domain-specific to web content and provides zero benefit for binary, scientific, or log data. The context-map entropy model requires 64× more Huffman tables per block, making the decoder ~3× slower than zstd/FSE for non-web workloads. The comp-dict COVER-lite trainer provides an equivalent trained-dictionary capability for domain-specific data without the static-dictionary lock-in.
