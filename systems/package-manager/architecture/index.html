CLI (pm-cli). Argument parsing, subcommand dispatch, config load, exits with structured errors. Trust boundary: the process's own entry point, trusts nothing from the environment beyond user-supplied CLI flags and config files. Concurrency boundary: single-threaded dispatcher, hands off to worker pools (ADR-13) inside later stages. Persistence boundary: none itself; reads $PM_HOME-rooted config.

Manifest parser (pm-manifest). TOML to Manifest, schema validation, workspace-glob expansion. Trust boundary: the manifest is developer-authored, semi-trusted (validated, not adversarial by default, though a malicious manifest in a supply-chain context is still defended per T1/T2). Concurrency boundary: pure, synchronous parse, no shared state. Persistence boundary: reads pkg.toml from disk, writes nothing.

SemVer engine (pm-semver). Grammar (§8.1), comparator, range satisfaction. Trust boundary: parses both developer-authored manifest strings and registry-supplied index strings — the latter is untrusted input (MM7) and must never panic. Concurrency boundary: pure value-type comparisons, Send + Sync by construction (§11.1). Persistence boundary: none.

Resolver core (pm-resolver). PubGrub incompatibility derivation and partial-solution search; the only component allowed to backtrack. Trust boundary: consumes IndexEntry records from the registry client as untrusted input (MM7), never mutates them. Concurrency boundary: deliberately single-threaded (ADR-13) to preserve I3. Persistence boundary: none — ephemeral to one resolve call.

Registry client (pm-registry). Sparse-index fetch with conditional GETs, mirror failover queue, feeds IndexEntry records to the resolver on demand (resolver and registry are mutually recursive: resolution is online, not a single upfront index load). Trust boundary: the network/protocol boundary of the entire system (T3, T4, T6) — every byte crossing it is adversarial until hash-verified (P3). Concurrency boundary: bounded-concurrency fetch pool (§4 FD budget). Persistence boundary: $PM_HOME/index-cache/ on disk.

Lockfile writer (pm-lockfile). Serializes the resolver's chosen assignment set deterministically; verifies a lockfile re-resolves to itself (I1). Trust boundary: the lockfile is the system's own output, trusted once written, but re-verified against a fresh resolve rather than trusted blindly across sessions. Concurrency boundary: single-writer per invocation, atomic-rename write path. Persistence boundary: pkg.lock at the project root.

Signature verifier (pm-sign). Checks Sigstore signatures and in-toto provenance before any artifact reaches the store. Trust boundary: the supply-chain trust gate (P7, I6) — sits directly between the untrusted network boundary and the store's trusted-once-verified boundary. Concurrency boundary: synchronous per-artifact gate, cacheable by content hash (§21.7). Persistence boundary: an append-only verification-log audit trail.

Content-addressed store (pm-store). BLAKE3-keyed blob storage, GC mark-and-sweep rooted at lockfiles-in-use. Trust boundary: the last line of defense before bytes are considered "ours" (P2, P3) — nothing enters without passing the signature-verifier boundary first. Concurrency boundary: lock-free reads, a bounded root-set-snapshot critical section for GC (§17.6). Persistence boundary: $PM_HOME/store/{objects,refs}/.

Build orchestrator (pm-build). Topologically schedules BuildUnits, runs build scripts inside a namespace/seccomp jail, captures outputs back into the store. Trust boundary: the execution trust boundary (P6, T5) — every build script runs as untrusted code regardless of the artifact's signature status (MM5). Concurrency boundary: bounded thread pool (ADR-13, §4's CPU-count ceiling), one sandbox namespace per unit. Persistence boundary: writes back into pm-store on success only.

Telemetry. Structured tracing spans across every stage, sampled counters feeding the Performance Engineering targets (§30). Trust boundary: outbound-only, redacted per P13 (names/versions/hashes/timings, never source bytes or secrets) so it is safe to route through third-party observability vendors. Concurrency boundary: async, non-blocking relative to every other stage's critical path. Persistence boundary: none within this system; consumed by an external observability pipeline.

8. Domain Model

8.1 SemVer Grammar (EBNF) and Precedence

version      ::= major "." minor "." patch [ "-" pre-release ] [ "+" build ]
major        ::= digits
minor        ::= digits
patch        ::= digits
digits       ::= "0" | pos-digit { digit }
pre-release  ::= pre-id { "." pre-id }
pre-id       ::= alphanum-id | digits
build        ::= build-id { "." build-id }
alphanum-id  ::= { digit | letter | "-" }  (must contain a non-digit)
version-req  ::= comparator { "," comparator } | "^" version | "~" version | "*"
comparator   ::= ( "=" | ">" | ">=" | "<" | "<=" ) version

Precedence table (highest to lowest, per SemVer 2.0.0 §11): major, then minor, then patch, numerically; a pre-release version has lower precedence than its associated normal version; pre-release identifiers compare left-to-right, numeric identifiers compare numerically, alphanumeric identifiers compare ASCII lexically, numeric identifiers always have lower precedence than alphanumeric; build metadata is ignored for precedence. 1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-beta < 1.0.0-rc.1 < 1.0.0.

Field Type Required Notes

workspace.members array of glob no present only in a workspace root manifest

8.3 Dependency Graph Model

The dependency graph is a directed graph over PackageId where an edge (A, B, req) means A declares a dependency on B satisfying VersionReq req. The graph is not known in full until resolution completes — before resolution it is a manifest graph (one node per direct dependency, unresolved); after resolution it is a lock graph (one node per resolved (PackageId, Version) pair, edges fully concrete). PubGrub never materializes the full manifest graph up front; it fetches IndexEntry records for a package lazily, only when that package is a candidate under consideration (§8.4).

8.4 PubGrub Incompatibility / Derivation Model

Concept Representation Meaning
Term (PackageId, VersionSet, positive: bool) "P is in range R" (positive) or "P is not in range R" (negative)
Incompatibility Vec<Term> + Cause a set of terms that cannot all be true simultaneously
Cause enum: Dependency, NoVersions, Conflict(derived from two incompatibilities), Root why the incompatibility exists — feeds P4's explanations
Assignment Term + decision_level + optional Cause one fact learned during search: a decision or a derivation
PartialSolution ordered list of Assignment the current in-progress candidate solution
decision_level integer increments on each decision (guess); derivations inherit the current level

Worked conflict-resolution trace (three packages: root requires a ^1.0.0; a 1.0.0 requires b ^2.0.0; a later fact reveals b's only published version is 1.5.0):

Step Assignment / Incompatibility Decision Level Cause
1 {root is 1.0.0} 0 Root
2 Incompatibility {not root@1.0.0, a in ^1.0.0} — Dependency (root→a)
3 Derive {a in ^1.0.0} 0 unit propagation on step 2
4 Decision: a = 1.0.0 1 decision (pick highest satisfying version)
5 Incompatibility {not a@1.0.0, b in ^2.0.0} — Dependency (a→b)
6 Derive {b in ^2.0.0} 1 unit propagation on step 5
7 Incompatibility {not b in ^2.0.0} (no matching version published; only 1.5.0 exists) — NoVersions
8 Conflict: steps 6 and 7 contradict — Conflict
9 Learn new incompatibility {not a@1.0.0} (backjump target = level 0) — derived Conflict, generalizes the root cause
10 Backjump to level 0, retry a at next candidate version (or fail with explanation "a 1.0.0 requires b ^2.0.0 but no version of b satisfies ^2.0.0; b's only published version is 1.5.0") 0 —

8.5 Resolver State Machine

State Entry Condition Action Exit Transition
Init resolve invoked seed root incompatibility → UnitPropagate
UnitPropagate pending derivations exist apply unit propagation across PartialSolution conflict found → ConflictResolve; no conflict, no pending → DecisionMaking; solution complete → Solved
DecisionMaking no pending derivations, unassigned package exists pick next undecided package + candidate version (fetch IndexEntry lazily from pm-registry if not cached) → UnitPropagate
ConflictResolve conflicting incompatibility found derive new incompatibility, compute backjump level backjump level ≥ 0 → UnitPropagate at that level; backjump level < 0 → Failed
Solved PartialSolution assigns exactly one version per required package emit lock graph terminal
Failed root incompatibility derived emit conflict explanation chain (P4) terminal

8.7 Sparse-Index Wire Format

Each package's index entry is a newline-delimited JSON (NDJSON) document at {index-base}/{name-path} (name-path sharded per Cargo convention: 1-char, 2-char, 3-char, or {first-2}/{next-2} for ≥4-char names), one JSON line per published version: {name, vers, deps: [{name, req, features, optional}], cksum, yanked, features}.

ETag/conditional-request sequence (RFC 7232):

Step Client Server Result
1 GET /a/aa/aaron (no If-None-Match, cold) 200 OK, body, ETag: "e1" full body transferred, cache stores e1
2 GET /a/aa/aaron, If-None-Match: "e1" index unchanged → 304 Not Modified, no body zero bytes transferred, cache entry revalidated
3 Upstream publishes a new version (server state changes) —
4 GET /a/aa/aaron, If-None-Match: "e1" 200 OK, new body, ETag: "e2" I8 fires: cache invalidated, new e2 stored

8.8 Content-Addressed Store Record Layout

Field Type Notes
CacheKey Blake3Hash (32 bytes) hash of canonicalized artifact bytes
object path objects/{hash[0:2]}/{hash[2:4]}/{hash} sharded to bound directory fanout
refcount metadata separate refs/{hash} file, list of referencing lockfile IDs supports mark-and-sweep GC (§17)
write mode write-to-temp then atomic rename enforces I2/I4

8.9 Worked Example

Manifest: app 0.1.0 depends on net ^2.0; net 2.3.0 (latest matching) depends on tls ^1.4; tls's latest matching version is 1.4.2. Resolver decisions: app@0.1.0 (root) → net@2.3.0 → tls@1.4.2. Lock graph: three [[package]] entries; app.dependencies = ["net 2.3.0"]; net.dependencies = ["tls 1.4.2"]. Re-running resolve against the same index snapshot reproduces this exact lock graph (I1, I3).

8.10 Malformed-Input Examples

  • Manifest with version = "1.0" (missing patch component): rejected at pm-manifest parse time, error names the missing patch field and cites §8.1 grammar.
  • Index entry with req = "^^1.0" (double caret): rejected at pm-semver parse time before it reaches the resolver; treated as a corrupt-index signal (T3 detection path).
  • Lockfile with package.checksum absent: rejected at pm-lockfile load time; refuses to build rather than silently trusting an unverified artifact (I6).
  • Sparse-index NDJSON line with an unterminated JSON object (truncated mid-fetch): rejected at the line level (§16.2's malformed-line handling); sibling lines in the same file remain usable, per the isolation discipline in §16.5.
  • Vendor bundle tarball with a truncated header (corrupt transfer): rejected as a distinct "corrupt bundle container" error at pkg vendor import before any per-object hash check is attempted (§22.8).

8.11 Failure-Path Example

app requires net ^3.0; the index has no published net version ≥ 3.0.0 (highest is 2.9.1). Resolver state machine reaches ConflictResolve with cause NoVersions, backjump level < 0, transitions to Failed. Emitted explanation: "app 0.1.0 depends on net ^3.0.0, but the latest available net is 2.9.1; no version of net satisfies ^3.0.0" — the full derivation chain from §8.4's trace-table format, not a bare error code.

8.12 Consistency & Concurrency Semantics

Cross-cutting summary of how each subsystem's consistency model composes into one system-level guarantee (MM6):

Subsystem Consistency Model Concurrency Discipline Governing Invariant
Resolver (§14) Deterministic, single-writer (one resolve call, one thread) No concurrency inside one resolve; multiple resolves may run in separate processes without shared state I3
Lockfile (§15) Snapshot-consistent (a lockfile is a point-in-time proof certificate, MM2) Read-mostly; writes are atomic-rename, never in-place mutation I1, I4-style discipline
Registry cache (§16) Eventually consistent across mirrors, strongly consistent per-request via conditional GET Bounded-concurrency fetch pool (§4 FD budget); no shared mutable cache state across requests beyond the on-disk ETag map I8, I12
CAS (§17) Append-only, content-addressed (identity implies immutability, P2) Lock-free reads; a snapshot-then-sweep GC critical section (§17.6) is the only serialization point I4, I5
Install/materialization (§18) Atomic-visibility (a package directory is all-or-nothing visible) Lock-free across distinct packages; same-package races are harmless under I4 I2
Build DAG (§19) Causal (a build never observes an un-materialized dependency) Bounded thread pool (ADR-13), one sandbox namespace per BuildUnit I2 (extended), I10
Signing/audit (§21) Fail-closed (unverified is never treated as verified) Synchronous gate per artifact, cached by content hash once verified I6

The composed guarantee: no subsystem's own consistency model is sufficient in isolation — I1's lockfile bijection depends on I3's resolver determinism, which depends on I7's total order, which depends on P12's discipline being honored at every serialization boundary (§13.9, §15.6, §19.2). A single layer's consistency bug propagates as an apparent bug in whichever layer is easiest to observe, not necessarily the layer where it originates (MM6's core insight, applied concretely here).

8.13 Worked Example — Feature Unification

Workspace with two members: svc-a depends on net ^2.0 with features = ["tls"]; svc-b depends on net ^2.0 with features = ["http2"]. Both are gated as optional features on net's own dep:compress optional dependency, activated only if either tls or http2 is enabled (§20.2's feature-graph edge model).

Step Event Feature Graph State Cause
1 Combined manifest graph loaded (§20.2) net requested by svc-a (feature tls) and svc-b (feature http2) Workspace load
2 Resolver decides net@2.3.0 (single decision, P11) One (PackageId, Version) entry pending unification Decision (§14.2)
3 Feature-graph edge: tls → dep:compress inactive alone compress not yet activated Graph traversal
4 Feature-graph edge: http2 → dep:compress activates it compress activated (either edge suffices) Graph traversal
5 Union: net@2.3.0's active feature set = {tls, http2, compress} I9 uniqueness check: exactly one net@2.3.0 entry Unification (P11)
6 Lock graph emitted: one net entry, features = ["tls", "http2", "compress"], visible to both svc-a and svc-b Terminal Solved

This is MM4's coupling made concrete: compress's activation depended on either dependent's feature choice, and once activated it is visible to both — including svc-a, which never asked for http2's companion feature (P11's documented tradeoff, §20.9).
