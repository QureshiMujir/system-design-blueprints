In one paragraph

A package manager decides which exact versions of a project's libraries to use, fetches them without trusting the network, and builds them. This design is a Rust command-line tool, pkg, split into a set of library crates (§1.1, §1.2). A developer or a CI runner starts it for one job and it exits; there is no daemon and no server component (§1.5). It pairs a version solver that explains its failures (ADR-02, P4) with a lockfile that makes builds reproducible (P5, I1), a store addressed by content hash (P2), and gates that distrust both the registry and the build scripts (P3, P6, P7). Its performance targets are set on a 500-package project (§4).

The problem, concretely

Your project lists dependencies as ranges, such as net ^2.0. A range is a compatibility promise, not a specific file, so a new upstream patch release can flow into a build without anyone editing the manifest (P9). Take the blueprint's small example: app 0.1.0 needs net ^2.0, the latest matching net is 2.3.0, and it needs tls ^1.4, whose latest match is 1.4.2 (§8.9). Any two runs given the same manifest and index snapshot must reach that same answer (I3); the blueprint treats "worked on my machine" as evidence of a hidden nondeterminism bug (§7). So resolution is a pure function of the manifest and an index snapshot (P1), and the lockfile, not the manifest, is the unit of reproducibility (P5).

Next, the naive error message. If app asks for net ^3.0 and the highest published net is 2.9.1, a bare "resolution failed" sends the user to a bug tracker. The blueprint instead requires the full chain: "app 0.1.0 depends on net ^3.0.0, but the latest available net is 2.9.1; no version of net satisfies ^3.0.0" (§8.11, P4).

Then trust. The blueprint names three incidents, left-pad (2016), event-stream (2018) and ua-parser-js (2021), as the reason it treats the registry as an adversarial input channel rather than a database (§2, MM7). A compromised mirror can serve garbage and a maintainer account can be taken over (P3, T11). Even a correctly signed package can ship a malicious build script (MM5).

Finally, scale. Choosing versions is NP-complete in the worst case (§31, §2), and an index that must be downloaded whole makes every client pay for the entire ecosystem (MM10).

How it works, end to end

Follow one build through the boxes of §3's diagram, shown here in compressed form.

 pm-cli ─▶ pm-manifest ─▶ pm-semver ─▶ pm-resolver
   ─▶ pm-registry (sparse, ETag cache, mirror queue)   carries IndexEntry
   ─▶ pm-lockfile (writer / verifier)                  carries Lockfile
   ─▶ pm-sign (Sigstore / in-toto verifier)            carries verified artifact ref
   ─▶ pm-store (BLAKE3 CAS, GC queue)                  carries StoreHandle
   ─▶ pm-build (DAG scheduler, sandbox jail)           carries build events
   ─▶ Telemetry (tracing)
  1. pm-cli parses arguments, loads config rooted at $PM_HOME, and dispatches. It is a single-threaded dispatcher that trusts nothing from the environment beyond flags and config files (§3, §1.5).
  2. pm-manifest turns pkg.toml into a Manifest, validates it and expands workspace globs; it is pure, and manifest size is capped at 1 MiB (§3, §8.2, §4). pm-semver parses and compares versions and ranges, including untrusted registry strings, and must never panic on them (§3, MM7).
  3. pm-resolver runs the PubGrub search. It is the only component allowed to backtrack, and it consumes IndexEntry records without mutating them (§3). §3, §11.3 and §14.2 call it deliberately single-threaded to preserve I3 and credit ADR-13 for that. The ADR-13 row itself puts CPU work on a bounded thread pool and names the resolver as the CPU-bound side (ADR-13).
  4. pm-registry fetches those records on demand with conditional GETs and a mirror failover queue. Resolver and registry are mutually recursive: resolution is online, not a single upfront index load (§3, §8.3). Every byte crossing this boundary is adversarial until hash-verified (§3, P3).
  5. pm-lockfile serializes the chosen assignment set deterministically, writes it by atomic rename, and can verify that a fresh resolve reproduces it (§3, I1).
  6. pm-sign checks Sigstore signatures and in-toto provenance between fetch and store-write, never after (§3, P7, I6). It also cross-references the OSV audit feed (I13).
  7. pm-store keeps BLAKE3-addressed objects under $PM_HOME/store/{objects,refs}/, with lock-free reads and garbage collection rooted at pinned lockfiles (§3, §8.8, P8).
  8. pm-install links store objects into a build tree without copying bytes. Its directories become visible by atomic rename, all or nothing (§1.1, §8.12, I2). It is a crate in §1.2 and a row in §8.12, but §3's diagram and per-component text have no box for it.
  9. pm-build schedules BuildUnits as a DAG, runs each build script inside a namespace and seccomp jail, and writes outputs back to the store on success only (§3, ADR-12).
  10. Telemetry (tracing) is outbound-only and redacted: names, versions, hashes and timings, never source bytes (§3, P13).

Three more crates sit outside the diagram. pm-workspace loads multi-package workspaces and merges feature requests (§1.2, §20). pm-mirror holds mirror configuration and the offline vendoring bundle (§1.2, §22). pm-conformance is the shared fixture and fuzz harness (§1.2, §23). §1.2 lists 13 crates, while §12.1, §12.7 and §39 say twelve. The registry itself is a black-box HTTP contract; no server is built (§1.3).

The core ideas

Version solving as a search that learns (§8.4, §8.5)

Plain version: guess a version, work out what that forces, and when two forced facts contradict, write down the reason as a new rule so the same dead end is never entered again. This is PubGrub, a descendant of the SAT-solver technique CDCL (ADR-02, ADR-03). Its vocabulary (§8.4): a Term is "package P is in range R" or "is not in range R". An Incompatibility is a set of terms that cannot all be true, tagged with a Cause (Dependency, NoVersions, Conflict, Root). The PartialSolution is the ordered list of assignments so far, and a decision_level goes up by one on each guess while derived facts inherit the current level.

The blueprint's trace: root requires a ^1.0.0, a 1.0.0 requires b ^2.0.0, and the only published b is 1.5.0 (§8.4).

Step What happens Level
4 Decision: pick a = 1.0.0, the highest satisfying version 1
6 Derive {b in ^2.0.0} from a's dependency (unit propagation) 1
7 Incompatibility NoVersions: nothing published satisfies ^2.0.0 n/a
8 Steps 6 and 7 contradict: conflict n/a
9 Learn {not a@1.0.0}; backjump target is level 0 n/a
10 Retry a at its next candidate, or fail with the readable explanation 0

The state machine (§8.5) has six states: Init, UnitPropagate, DecisionMaking, ConflictResolve, Solved, Failed. ConflictResolve computes a backjump level. A level below zero means the root itself is incompatible, so the machine goes to Failed and prints the derivation chain (§8.5, P4). Ordering rests on SemVer precedence: numeric parts compare numerically, a pre-release sorts below its release, and build metadata is ignored, so 1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-beta < 1.0.0-rc.1 < 1.0.0 (§8.1, I7).

The lockfile is a proof certificate, not a cache (§8.6, MM2)

The lockfile records the exact result so builds never drift (P5). One [[package]] entry per resolved (name, version), with source, a BLAKE3 checksum, and dependencies as "name version" strings sorted lexically for determinism (§8.6). The file also carries metadata.index-snapshot, an opaque token from the registry that lets a later run re-resolve against the same index state (§8.6). I1 says a lockfile re-resolves to itself given the same manifest and snapshot, and pkg lock verify checks it by doing a fresh resolve and comparing (I1).

For the §8.9 example the lock graph has three entries: app with ["net 2.3.0"], net with ["tls 1.4.2"], and tls. Re-running against the same snapshot must reproduce it exactly (§8.9, I1, I3). MM2 draws the consequence: a lockfile that cannot be re-derived is untrustworthy, however it was produced (MM2). MM6 adds the practical warning that nondeterminism usually enters at layer boundaries, such as serialization or an unordered HashMap, not inside the resolver (MM6, P12).

A sparse index and the conditional GET (§8.7, MM10)

Instead of one giant index file, each package has its own file at a sharded path: 1-char, 2-char and 3-char names get their own prefixes, and longer names use {first-2}/{next-2} (§8.7). Each file is newline-delimited JSON, one line per published version, with name, vers, deps, cksum, yanked and features (§8.7). A client fetches only the packages the resolver actually visits (MM10, §8.3). Freshness uses a conditional GET (RFC 7232), shown in the blueprint's own sequence:

Step Client sends Server answers Effect
1 GET /a/aa/aaron (cold) 200, body, ETag: "e1" full body, cache stores e1
2 same, If-None-Match: "e1" 304 Not Modified, no body zero bytes moved
3 upstream publishes a version (server state changes) n/a
4 same, If-None-Match: "e1" 200, new body, ETag: "e2" I8 fires: old entry dropped

I8 forbids ever using a stale cached response after a non-304 (§8.7, I8). A req = "^^1.0" in an index line is rejected at parse time and treated as a corrupt-index signal (§8.10, T3).

A content-addressed store and a garbage collector that cannot race (§8.8, MM3, MM8)

Name the object by the hash of its bytes (content addressing) and an object can never change, only become unreferenced (P2, MM3). Objects live at objects/{hash[0:2]}/{hash[2:4]}/{hash} and a separate refs/{hash} file lists the lockfiles that reference each (§8.8). Writes go to a temp file and are renamed into place (§8.8, I4). So cache invalidation turns into reachability, solved by mark-and-sweep: mark everything reachable from a root set, delete the rest (MM3, ADR-08). The root set is every lockfile the operator pinned with pkg cache pin, plus the lockfile in the working tree (P8).

MM8 locates the real difficulty: the sweep is simple, and the hard part is taking the root-set snapshot atomically relative to concurrent pin, unpin and install (MM8, I5). A race shows up as FM-5, not as a wrongly deleted object in isolation (MM8, FM-5). The blueprint's Phase 5 fixture: a store of 1000 objects with 400 referenced by a pinned lockfile must lose exactly 600 (§17.4).

Feature unification: a second constraint problem riding on the first (§8.13, MM4)

A feature is an optional switch on a package. When two dependents ask for different feature sets of the same package version, the resolver merges them and builds that package once (P11, ADR-11). The blueprint's example (§8.13): svc-a wants net ^2.0 with tls, svc-b wants net ^2.0 with http2, and net's optional compress dependency is set up to switch on if either feature is on.

  1. The resolver decides one net@2.3.0 (P11).
  2. The table's step 3 says the tls edge alone leaves compress inactive, which the setup's "either feature" rule contradicts; both stand as written (§8.13).
  3. http2 activates compress; either edge suffices.
  4. The union is {tls, http2, compress}, and I9 checks that exactly one net@2.3.0 entry exists.

The price is that svc-a now sees compress, which it never asked for (§8.13, P11, FM-9). MM4's point is that features can imply new dependency edges, which constrain versions, which change features, so resolving versions fully and filtering optional dependencies afterwards gives wrong answers on connected graphs (MM4).

Two gates in series: verify who published, then jail what runs (P6, P7, MM5)

Signature checking happens between fetch and store-write, never after, so an unsigned or invalid package never touches the store (P7, I6). But a signature proves who published an artifact, not what its build script does. The event-stream incident was a validly signed malicious version (MM5). So every build script runs in a Linux namespace and seccomp-bpf jail (a kernel filter that kills a process making disallowed system calls) with no network and a read-only source tree by default (P6, ADR-12, ADR-26). A build script cannot write outside its output directory (I10). The jail covers time too: SOURCE_DATE_EPOCH is pinned from the lockfile and wall-clock now() is not read inside a sandboxed build (ADR-31). The Phase 7 fixtures kill a script that tries ptrace or an unauthorized mount (§19.4).

The trade-offs — where engineers disagree

Resolver: PubGrub (ADR-02)

Chosen: PubGrub, for sub-second resolves at 500-package scale with explainable failures (§4, P4). Rejected: a full SAT encoding, greedy or backtracking-only search, ASP (Spack-style). When the rejected choice is right: full SAT, when the index is small (under 50 packages) and exhaustiveness matters more than speed. §36 widens this: libsolv-style full encoding wins for distro-scale indexes where an optimal install set matters.

Registry protocol: a sparse HTTP index (ADR-06)

Chosen: per-package files with ETags, which the ADR row says scales index size independently of client bandwidth; MM10 adds that client cost then tracks the project's own dependency graph, not the registry's catalogue (§16, MM10). Rejected: a full git-cloned index, or a per-request API endpoint. When the rejected choice is right: a git-cloned index, for fully offline air-gapped mirrors with no HTTP server available.

Cache cleanup: mark-and-sweep from pinned lockfiles (ADR-08)

Chosen: mark-and-sweep rooted at pinned lockfiles, because refcounting alone cannot handle cross-lockfile sharing cycles cleanly and LRU risks evicting a pinned dependency. Rejected: naive LRU eviction, pure refcounting. When the rejected choice is right: LRU, for an ephemeral CI cache with no pinning concept and guaranteed full teardown between runs. The cost of the chosen path is that forgetting to unpin old lockfiles wastes disk (P8, FM-4).

Features: Cargo-style unification (ADR-11)

Chosen: merge feature requests into one build per package version (P11), avoiding duplicate builds. Rejected: per-package isolated builds with no unification. When the rejected choice is right: per-package isolation, when two dependents' feature sets are mutually incompatible, for example no_std against std. The unification leak is the accepted price (FM-9).

Build isolation: namespaces plus seccomp (ADR-12)

Chosen: Linux namespaces and seccomp-bpf, which have lower overhead than a full container per build unit (§4); the target is at most 5 ms of setup per unit (§30, M13). Rejected: a Docker/OCI container per build, or no sandbox. When the rejected choice is right: full containers, when the host also needs filesystem-level rollback or snapshotting per build. Cargo and uv choose the "no sandbox" side by default (§33).

Language: Rust (ADR-01)

Chosen: Rust, for memory safety and algebraic data types that fit Incompatibility and Term (§11). Rejected: Go, C++, Zig per the ADR row; §1.8 instead lists Go, C++ and Python, and both lists stand as written. When the rejected choice is right: Go, for a team with zero Rust experience and a two-week deadline.

Roads not taken (§36, §37)

Full SAT/SMT over the whole index (§36): wins for a small, bounded index, such as distro package managers, where a provably optimal install set (for example minimum total size) matters; libsolv works this way. It is rejected because encoding the entire index up front does not fit a lazily discovered registry (§16).

A Nix-style store with no version resolution (§36): wins for whole-system reproducible deployment where every input is pinned exactly and "which version satisfies this range" is never a runtime question. It is rejected here because the project's goal is to teach resolution (§1.1).

Flat or hoisted node_modules (§36): wins where dependency trees are huge and disk space is the dominant concern. It is rejected because it brings the phantom-dependency bug class (§33), which the CAS-linked model avoids while still deduplicating (§18).

Server-side resolution returning a lockfile (§36): wins for very large enterprise monorepos that want organization-wide policy enforced in one place. It is rejected because it adds a server (against §1.5) and makes the resolution service part of the threat model.

Deferred, not rejected (§37): cross-ecosystem manifest translation, hardware-backed key custody, Windows/macOS build sandboxing and a distributed shared CAS, each with an un-defer trigger such as a compliance rule or a measured build-farm cost (§37).

What must never be false

  • I1: a lockfile re-resolves to itself for the same manifest and snapshot. Noticed by pkg lock verify; lockfile.reresolve.mismatch.
  • I2: no partially materialized package is visible to a build. Noticed by a marker-file check before the build; install.partial.detected.
  • I3: resolution is deterministic for (manifest, snapshot). Noticed by a differential re-run in CI; resolve.nondeterminism.detected.
  • I4: the store is append-only and content-addressed. Noticed by a hash recheck at write time; store.write.hash_mismatch.
  • I5: GC never removes an object reachable from a pinned lockfile. Noticed by the root-set snapshot before the sweep; gc.roots.count.
  • I6: every artifact in the store passed signature verification. Noticed via an append-only verification log; sign.verify.failure.
  • I7: versions and ranges obey a total, transitive order. Noticed by a property test; semver.compare.calls.
  • I8: the registry client never reuses a stale response after a non-304. Noticed by a cache generation counter; registry.cache.invalidations.
  • I9: unification yields exactly one build per (package, version). Noticed by a uniqueness check after resolution; resolve.duplicate_version.detected.
  • I10: a build script cannot write outside its output directory. Noticed by the seccomp denial log and an escape test; sandbox.escape_attempt.
  • I11: the lockfile is forward-readable by exactly one prior major version. Noticed by the schema-version field; lockfile.version.unsupported.
  • I12: a mirror never serves an artifact whose hash differs from the primary index's digest. Noticed by hash comparison at fetch; mirror.hash_mismatch.
  • I13: an audit finding is never silently dropped or downgraded. Noticed by diffing finding counts between runs; audit.finding_count.
  • I14: cached signature verdicts are invalidated when the trust root rotates. Noticed by a trust-root generation counter; sign.trust_root_rotated.

What breaks in production

  • FM-1: the resolver never terminates. Root cause: a backjump-level bug that makes no forward progress (§14.9). Detection: an iteration-count counter over a sanity threshold, in test builds only. Production has no automatic abort, to avoid silent truncation (§25). Recovery: kill the process, capture the manifest and index snapshot as a replay fixture, and bisect.
  • FM-2: the lockfile fails to re-resolve to itself. Root cause: nondeterministic collection ordering upstream, or real index drift between resolve and verify (§25, MM6). Detection: pkg lock verify (I1). Recovery: re-resolve fresh, diff against the prior file, and investigate whichever field changed; the forensic tool is a byte-diff of two serializations.
  • FM-5: GC deletes an object mid-install. Root cause: a non-atomic root-set snapshot racing a concurrent install (§17.6, MM8). Detection: StoreError::GcRaceDetected. Recovery: the install retries from the registry or a mirror; if the retry fails too, it points at a deeper pinning bug.
  • FM-7: signature verification is silently bypassed. Root cause: some path, such as vendor import (§21, §22), forgets to call the gate. Detection: a cross-phase conformance regression test, and a trace showing a store-write with no preceding sign.verify.success span. Recovery: patch the missing call and add a fixture (I6).
  • FM-8: "temporarily unavailable" is treated as "package does not exist". Root cause: conflated error variants (§16.6). Symptom: a wrong NoVersions error during a network outage. Recovery in the design: retry via mirror failover before surfacing any terminal error (P10).
  • FM-10: audit reports clean despite a real CVE. Root cause: a stale OSV feed (T9). Detection: the audit.feed_stale counter past its window (§4: 24 h). Recovery: the feed refreshes on a schedule, and pkg audit --refresh-feed forces it. T9's rule is to refuse to report "clean" when the feed itself is stale.

Threats worth knowing (§24):

  • T3 index MITM: an on-path attacker alters an index response. The answer is TLS (rustls, ADR-14) plus hash verification of every artifact (P3, I4).
  • T4 rollback or freeze: a stale index snapshot hides a security fix. The answer is the ETag check (I8) plus a monotonic snapshot counter; a snapshot token moving backward is the tell.
  • T5 a malicious build script. The answer is the sandbox with no network by default (ADR-12, ADR-26). It mirrors the event-stream and ua-parser-js attack shape.
  • T8 signature stripping: the attacker removes the signature hoping the client skips the check. The answer is the mandatory gate before store-write (I6), with no silent fall-back to unsigned.

How it compares

  • Cargo uses PubGrub, a flat registry cache and one Cargo.lock per workspace, and runs build.rs unsandboxed (§33). That is fine where build scripts are mostly trusted; this design diverges on sandboxing because of the event-stream class of attack (§33, ADR-12).
  • Dart pub is PubGrub's origin, with one pubspec.lock per package (§33). Its ecosystem has fewer native build scripts, so sandboxing is less urgent there (§33).
  • npm with arborist uses a hoisting-driven backtracker over a flat or hoisted node_modules (§33). It trades determinism for disk space and gets phantom dependencies, which is fine where disk pressure dominates; the CAS-linked layout avoids them (§33, §18).
  • Nix does no solving: every input is hash-pinned in a global content-addressed store, with full sandboxed builds (§33). It fits whole-system reproducibility, where a range is never a runtime question (§33, §36).
  • Spack uses an ASP-based concretizer with no OS-level sandbox by default (§33). It is right once feature and variant combinatorics outgrow Cargo-style unification (§33, P11).
  • uv uses PubGrub with a content-addressed cache hardlinked into virtual environments and speculative prefetch, but no sandbox for Python source builds (§33). It is the closest living proof that this architecture is buildable in Rust (§33).

Questions to test yourself

  1. Why does I1's re-resolve bijection require the lockfile to store an index_snapshot token (§8.6) rather than just a timestamp? — Hint: §8.6's metadata.index-snapshot row and the verify step in §15.2.
  2. Why is GC's root-set snapshot (§17.6) required to be atomic relative to pkg cache pin, and not merely "eventually consistent"? — Hint: MM8 and FM-5.
  3. Why does P6's sandbox default (network-disabled) not by itself close T5, per MM5 — what is the residual risk MM5 identifies? — Hint: MM5's event-stream account and T5 in §24.
  4. Why does the mirror-failover design (§16.2, ADR-24) hash-verify every response regardless of source, rather than trusting a designated "primary" mirror unconditionally? — Hint: I12, T3, and P3.
  5. What is the difference between "the registry is unavailable" and "the package does not exist," and why does §16.6/FM-8 treat conflating them as a real production incident class, not a cosmetic bug? — Hint: FM-8 in §25 and P10.

If you only remember three things

A lockfile is a proof that a valid answer exists, so the whole system is built so that the same manifest and index snapshot always give the same result at every layer (MM2, MM6, P12). Content addressing turns cache invalidation into garbage collection, and the hard part of that collection is taking a consistent snapshot of what is still in use (MM3, MM8). A registry is untrusted input and a signed package is not a safe package, so bytes are hash-checked before they enter the store and every build script runs in a jail (MM5, MM7, P3, P7).

Words used here

  • Resolver: the component that chooses one version per needed package so all requirements hold.
  • PubGrub: the version-solving algorithm used here, which learns from conflicts and explains failures.
  • Incompatibility: a set of package-version statements that cannot all be true together.
  • Lockfile: the exact resolved versions with checksums, written so a re-resolve reproduces it.
  • Index snapshot: an opaque token naming one point-in-time state of the registry index.
  • Sparse index: a registry layout with one small file per package instead of one huge file.
