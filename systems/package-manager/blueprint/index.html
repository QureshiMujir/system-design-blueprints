Project Number: 135

Project Name: Package Manager

1. Goal & Scope

1.1 Precise Engineering Scope

Build, from scratch in Rust, a production-grade package manager for a single-language ecosystem: SemVer 2.0.0 parsing and comparison, a TOML manifest format, a PubGrub-style CDCL (conflict-driven clause learning) version-resolution engine with incompatibility learning and human-readable conflict explanations, a deterministic cross-platform lockfile, a sparse HTTP registry-index protocol with ETag/conditional-GET caching and mirror failover, a BLAKE3 content-addressed store (CAS) with reference-counted garbage collection and cross-package deduplication, an install/materialization pipeline that links CAS objects into a build tree without copying bytes, a parallel build orchestrator with a sandboxed build-script execution model, workspace and Cargo-style feature-unification support, and a supply-chain security layer covering package signing (Sigstore-compatible keyless signing), provenance attestation (in-toto-style), and audit/CVE integration. The system is the resolver-plus-registry-plus-cache core that every language package manager (Cargo, npm, pip, Nix, Spack) converges on, stripped to one ecosystem so the full surface fits in twelve phases.

1.2 Phase-0 Deliverable

Phase 0 (§12) establishes the Cargo workspace skeleton, CI, and fuzzing harness that every later phase fills in. The Phase-0 deliverable is exactly this crate list, each crate present as a compiling stub with its public signatures declared (bodies arrive in later phases):

  1. pm-semver — SemVer 2.0.0 parser, comparator, range/requirement grammar (Phase 1, §13).
  2. pm-manifest — package manifest (pkg.toml) schema, parser, validation (Phase 1, §13).
  3. pm-resolver — PubGrub incompatibility/derivation engine, partial-solution state machine (Phase 2, §14).
  4. pm-lockfile — deterministic lockfile serializer/deserializer, lock-resolve bijection checker (Phase 3, §15).
  5. pm-registry — sparse-index HTTP client, ETag cache, mirror failover (Phase 4, §16).
  6. pm-store — BLAKE3 content-addressed store, GC, dedupe (Phase 5, §17).
  7. pm-install — materialization: CAS objects to build-tree links (Phase 6, §18).
  8. pm-build — build-unit DAG scheduler, sandboxed build-script execution (Phase 7, §19).
  9. pm-workspace — multi-package workspace loader, feature unification, optional deps (Phase 8, §20).
  10. pm-sign — Sigstore-compatible signing/verification, in-toto provenance, audit/CVE feed (Phase 9, §21).
  11. pm-mirror — mirror registry configuration, offline vendoring bundle format (Phase 10, §22).
  12. pm-cli — pkg binary: subcommand dispatch, config loading, telemetry init (present from Phase 0 as a stub with pkg --version, filled incrementally every phase).
  13. pm-conformance — fixture-driven conformance-test harness and fuzz targets shared across all crates (Phase 0 and Phase 11, §23).

1.3 System Boundaries

  • Provides: manifest parsing, version resolution, lockfile generation, registry protocol client, content-addressed cache, build orchestration for a single target triple at a time, workspace/feature resolution, signature verification, CVE-feed audit, mirror/offline support.
  • Delegates: a hosted registry server (the registry is consumed as an HTTP contract, never implemented server-side); cross-compilation toolchain management; a package publish web UI.
  • Does NOT provide: binary patching/diffing for delta updates; a plugin/extension marketplace; distributed build caching across machines (single-host CAS only).

1.4 Non-Goals

  • No full SAT/SMT solve over the entire index (§36 contrasts this).
  • No support for ecosystems other than the one manifest format this system defines — PhaseDeferred("§22") covers only mirroring of this format, not translating package.json or requirements.txt.
  • No distributed or multi-tenant build cache. No GUI.
  • No package-signing key custody service (keys are BYO or ephemeral Sigstore identities).
  • No automatic vulnerability patching — audit surfaces CVEs, it does not silently upgrade.

1.5 Deployment Model

Single static binary (pkg), invoked from a developer workstation or a CI runner. No daemon process; each invocation is a cold start that reads a project directory, talks to zero or more registries over HTTPS, and reads/writes a local CAS rooted at $PM_HOME (default ~/.pm). CI runners share the CAS across cache-restore boundaries via a tarball of $PM_HOME/store. No server-side component ships from this project — the sparse registry is treated as a black-box HTTP contract (§16) that the team may point at crates.io-style infrastructure or a self-hosted index.

1.6 Users & Operators

  • Primary: an application developer running pkg add, pkg build, pkg test locally.
  • Secondary: a CI/CD pipeline maintainer who needs deterministic, cacheable builds and readable resolver failures.
  • Tertiary: a security/platform team operator running pkg audit, configuring mirror allow-lists, and rotating signing trust roots.
  • Out of scope: registry index operators — but the sparse-protocol contract (§16) is written so a small team can stand up a compliant index in an afternoon.

1.7 What Later Phases Unlock

  • Phase 2 (§14) unlocks resolving real multi-package dependency graphs with human-readable conflict explanations instead of "resolution failed."
  • Phase 4 (§16) unlocks talking to a real remote registry instead of an in-memory fixture.
  • Phase 5 (§17) unlocks disk-bounded operation via GC instead of unbounded cache growth.
  • Phase 7 (§19) unlocks untrusted build scripts running under a namespace/seccomp sandbox instead of arbitrary host access.
  • Phase 9 (§21) unlocks refusing to install a package whose signature or provenance fails verification — this is the phase that closes the event-stream-class attack (§24, T5).

1.8 Language & Rationale

Rust. Rationale: memory safety without a GC (predictable latency for a resolver that must run in CI); a mature cargo ecosystem to dogfood against; first-class BLAKE3 and Sigstore Rust crates; strong sum-type support (enum with data) maps directly onto Incompatibility/Term/Assignment variants central to PubGrub; serde gives deterministic, auditable (de)serialization for the lockfile and index formats.

  • Rejected: Go — lacks algebraic data types, making the resolver's incompatibility representation stringly-typed and error-prone; weaker sandboxing primitives for the build-script jail (§19).
  • Rejected: C++ — manual memory management raises the CAS's use-after-free risk surface for zero justified performance gain over Rust in this domain.
  • Rejected: Python — too slow for a 500-package resolve within the p95 target in §4; no static typing for the incompatibility algebra.

1.9 Prerequisites

  • SemVer 2.0.0 spec fluency.
  • SAT/CDCL fundamentals (unit propagation, conflict clauses, backjumping).
  • TOML syntax; basic cryptographic hashing (BLAKE3/SHA-256) and digital signatures (Ed25519).
  • HTTP conditional requests (RFC 7232).
  • Linux namespaces and seccomp-bpf at a conceptual level.
  • Content-addressed storage concepts (Git objects or Nix store as a mental model).
  • Rust ownership and async/threads basics.

1.10 Timeline

  • Phase-0 drop (workspace skeleton, CI, fuzz harness, stub crates): 1 week.
  • Phases 1–3 (SemVer, manifest, PubGrub resolver, lockfile): 4 weeks — this is the intellectual core and gets the most time.
  • Phases 4–6 (registry protocol, CAS + GC, install/materialization): 4 weeks.

  • Phases 10–11 (mirrors/offline, conformance/perf hardening): 2 weeks.

1.11 Deferrals

  • PhaseDeferred("§22") — full cross-ecosystem manifest translation (npm/pip import) stays out of scope permanently; only same-format offline vendoring is built.
  • PhaseDeferred("§21") — hardware-backed key custody (HSM/YubiKey signing) deferred past Phase 9; software Ed25519 keys and Sigstore keyless identities ship first.
  • PhaseDeferred("§19") — Windows/macOS build sandboxing (no Linux namespaces available) deferred; Phase 7 ships Linux-only sandboxing with an explicit unsandboxed fallback flag on other platforms.

2. Why Build This

Version resolution, content addressing, supply-chain trust, sandboxed execution, deterministic serialization, HTTP caching protocol design, conflict-driven learning algorithms, garbage collection under concurrent access, cross-platform reproducibility, workspace/feature-graph unification, cryptographic provenance, incident-driven threat modeling.

A package manager is the rare project where "toy version" and "production version" differ only in scale, not in kind: the same PubGrub algorithm that resolves three packages resolves ten thousand; the same CAS GC that reclaims ten objects reclaims ten million. Building it end to end means confronting NP-completeness (§31) as an engineering constraint, not a classroom exercise; means treating the registry as an adversarial input channel after left-pad (2016), event-stream (2018), and ua-parser-js (2021) made "the registry can be actively malicious" a lived production fact, not a hypothetical.

Cross-links to sibling systems. The resolver core is a direct sibling of the SAT/SMT Solver blueprint (CDCL/DPLL lineage, §14, §5) — building both teaches the same conflict-driven-learning discipline from two angles. The content-addressed store is a direct sibling of a Git Object Store or Nix-style Build System blueprint (§17, §36) — hash-addressed, append-only, GC-by-reachability is one idea reused across all three. The sandboxed build orchestrator shares its namespace/seccomp discipline with a Container Runtime blueprint (§19, ADR-12) — both isolate untrusted execution behind the same kernel primitives. The signing/provenance layer shares its trust model with a Certificate Authority PKI Infrastructure blueprint (§21, ADR-28's cross-reference) — both reason about root-of-trust rotation and revocation.

What Mastery Looks Like

  • Explaining why Cargo abandoned a naive backtracking resolver for PubGrub, and reproducing the incompatibility-learning trace by hand (Phase 2, §14).
  • Proving a lockfile re-resolves to itself bit-for-bit across two OSes (Phase 3, §15; I1).
  • Running GC under concurrent installs without racing a live install into deletion (Phase 5, §17; I2).
  • Explaining the exact HTTP sequence that turns a warm sparse-index cache into zero-byte-transferred requests (Phase 4, §16; RFC 7232).
  • Sandbox-escaping a deliberately malicious build script and watching the seccomp filter kill it (Phase 7, §19).
  • Verifying a Sigstore signature and rejecting a stripped one (Phase 9, §21; T8).
  • Explaining precisely why full SAT-over-the-whole-index does not scale past a few hundred packages while PubGrub does (§36, §31).
  • Tracing a single nondeterminism bug report to its actual originating layer using §8.12's consistency-semantics table, rather than assuming the resolver is at fault by default.

CLI (pm-cli). Argument parsing, subcommand dispatch, config load, exits with structured errors. Trust boundary: the process's own entry point, trusts nothing from the environment beyond user-supplied CLI flags and config files. Concurrency boundary: single-threaded dispatcher, hands off to worker pools (ADR-13) inside later stages. Persistence boundary: none itself; reads $PM_HOME-rooted config.

Manifest parser (pm-manifest). TOML to Manifest, schema validation, workspace-glob expansion. Trust boundary: the manifest is developer-authored, semi-trusted (validated, not adversarial by default, though a malicious manifest in a supply-chain context is still defended per T1/T2). Concurrency boundary: pure, synchronous parse, no shared state. Persistence boundary: reads pkg.toml from disk, writes nothing.

SemVer engine (pm-semver). Grammar (§8.1), comparator, range satisfaction. Trust boundary: parses both developer-authored manifest strings and registry-supplied index strings — the latter is untrusted input (MM7) and must never panic. Concurrency boundary: pure value-type comparisons, Send + Sync by construction (§11.1). Persistence boundary: none.

Resolver core (pm-resolver). PubGrub incompatibility derivation and partial-solution search; the only component allowed to backtrack. Trust boundary: consumes IndexEntry records from the registry client as untrusted input (MM7), never mutates them. Concurrency boundary: deliberately single-threaded (ADR-13) to preserve I3. Persistence boundary: none — ephemeral to one resolve call.

Registry client (pm-registry). Sparse-index fetch with conditional GETs, mirror failover queue, feeds IndexEntry records to the resolver on demand (resolver and registry are mutually recursive: resolution is online, not a single upfront index load). Trust boundary: the network/protocol boundary of the entire system (T3, T4, T6) — every byte crossing it is adversarial until hash-verified (P3). Concurrency boundary: bounded-concurrency fetch pool (§4 FD budget). Persistence boundary: $PM_HOME/index-cache/ on disk.

Lockfile writer (pm-lockfile). Serializes the resolver's chosen assignment set deterministically; verifies a lockfile re-resolves to itself (I1). Trust boundary: the lockfile is the system's own output, trusted once written, but re-verified against a fresh resolve rather than trusted blindly across sessions. Concurrency boundary: single-writer per invocation, atomic-rename write path. Persistence boundary: pkg.lock at the project root.

Signature verifier (pm-sign). Checks Sigstore signatures and in-toto provenance before any artifact reaches the store. Trust boundary: the supply-chain trust gate (P7, I6) — sits directly between the untrusted network boundary and the store's trusted-once-verified boundary. Concurrency boundary: synchronous per-artifact gate, cacheable by content hash (§21.7). Persistence boundary: an append-only verification-log audit trail.

Content-addressed store (pm-store). BLAKE3-keyed blob storage, GC mark-and-sweep rooted at lockfiles-in-use. Trust boundary: the last line of defense before bytes are considered "ours" (P2, P3) — nothing enters without passing the signature-verifier boundary first. Concurrency boundary: lock-free reads, a bounded root-set-snapshot critical section for GC (§17.6). Persistence boundary: $PM_HOME/store/{objects,refs}/.

Build orchestrator (pm-build). Topologically schedules BuildUnits, runs build scripts inside a namespace/seccomp jail, captures outputs back into the store. Trust boundary: the execution trust boundary (P6, T5) — every build script runs as untrusted code regardless of the artifact's signature status (MM5). Concurrency boundary: bounded thread pool (ADR-13, §4's CPU-count ceiling), one sandbox namespace per unit. Persistence boundary: writes back into pm-store on success only.

Telemetry. Structured tracing spans across every stage, sampled counters feeding the Performance Engineering targets (§30). Trust boundary: outbound-only, redacted per P13 (names/versions/hashes/timings, never source bytes or secrets) so it is safe to route through third-party observability vendors. Concurrency boundary: async, non-blocking relative to every other stage's critical path. Persistence boundary: none within this system; consumed by an external observability pipeline.

6. Design Principles

P1 — Resolution is a pure function of (manifest, index snapshot). Rule: given identical inputs, the resolver always produces the identical output set. Tradeoff: forbids "latest wins ties" nondeterminism that some ecosystems rely on for convenience. Operational implication: CI can cache resolver output keyed only on manifest+index-snapshot hash. Violating it breaks I3 and makes lockfiles non-reproducible.

P2 — The store is append-only and content-addressed. Rule: no object's bytes are ever mutated in place; identity is hash(bytes). Tradeoff: costs one hash computation per write. Operational implication: GC can safely delete unreferenced objects without a write-lock on the whole store. Violating it breaks I2 (concurrent-install safety).

P3 — Never trust the network by default. Rule: every fetched byte is hash-verified against the index-declared digest before it is linked into a build tree. Tradeoff: adds one hash pass per artifact. Operational implication: a compromised mirror can serve garbage but never poison the store. Violating it opens T3 (index MITM) and T6 (cache poisoning).

P4 — Conflict explanations are a first-class output, not a debugging afterthought. Rule: every resolution failure carries the full incompatibility derivation chain, not just "no solution." Tradeoff: the resolver must retain derivation provenance in memory during search. Operational implication: users self-diagnose without filing a ticket. Violating it makes the resolver a black box (Weizenbaum's design goal for PubGrub).

P5 — The lockfile is the unit of reproducibility, not the manifest. Rule: builds read the lockfile; the manifest only feeds a fresh resolve. Tradeoff: requires an explicit "update" step to move version pins forward. Operational implication: pkg build never silently drifts versions. Violating it breaks I1.

P6 — Build scripts are untrusted code until proven otherwise. Rule: every build script executes inside a namespace/seccomp jail with no network and a read-only source tree by default. Tradeoff: legitimate build scripts that need network access (rare, e.g. codegen download) must declare it explicitly and get extra scrutiny. Operational implication: a malicious build script cannot exfiltrate secrets or persist on the host. Violating it is exactly the event-stream (2018) and ua-parser-js (2021) attack class (T5).

P7 — Signatures are verified before bytes are trusted, never after. Rule: verification happens between fetch and store-write, not between store-write and link. Tradeoff: adds latency to every fresh fetch (not to CAS-cached hits, which were already verified at write time). Operational implication: an unsigned or invalid package never touches the store. Violating it opens T8 (signature stripping).

P8 — GC never deletes anything reachable from a locked manifest. Rule: the GC root set is the union of every lockfile the operator has told the store about (pkg cache pin), plus anything referenced by a lockfile in the current working tree. Tradeoff: forgetting to unpin old lockfiles wastes disk. Operational implication: pkg build never fails because GC raced it. Violating it breaks I2.

P9 — Version ranges are intentions, not identities. Rule: ^1.2.3 describes a compatibility promise (SemVer precedence, §8.1), never a specific artifact. Tradeoff: resolution must search a range, not look up one entry. Operational implication: a patch release from upstream can flow into a build without a manifest edit. Violating it collapses the resolver into a glorified pkg get <exact-version>.

P10 — Every wire request degrades gracefully to a cached answer. Rule: registry client failures (timeout, 5xx, mirror down) fall back to the last-known-good ETag-cached response before failing the resolve. Tradeoff: a stale cache can mask an upstream yank momentarily. Operational implication: flaky networks do not turn into flaky builds. Violating it makes CI reliability a function of registry uptime.

P11 — Feature unification is per-resolution, not per-package. Rule: if two dependents request different feature sets of the same package version, the resolver unions them into one build of that package (Cargo's model). Tradeoff: a feature enabled by one dependent leaks into every other dependent's view of that package. Operational implication: unsafe or heavy features must be additive-safe by convention (documented, not enforced). Violating it either causes duplicate builds of the same version (binary bloat) or silent behavior divergence.

P12 — Determinism beats performance when they conflict. Rule: any optimization (parallel index prefetch, speculative resolution, incompatibility caching) must not change the output for a fixed (manifest, index snapshot) pair. Tradeoff: some fast paths (e.g., "trust the last successful resolve without re-checking") are forbidden. Operational implication: perf work in §30/§23 never regresses I1/I3. Violating it turns a resolver bug into a Heisenbug that only reproduces under load.

P13 — Telemetry never carries package contents. Rule: tracing spans record names, versions, hashes, timings — never source bytes or environment variable values from a build script. Tradeoff: some debugging requires re-running locally instead of reading a trace. Operational implication: telemetry pipelines are safe to route through third-party observability vendors. Violating it turns the telemetry pipeline into a supply-chain exfiltration channel.

P14 — Backpressure is applied at the edge, never inside the resolver. Rule: bounded concurrency (ADR-29) gates fetch and build workers at the system's I/O boundaries; the resolver's own search loop is never throttled or rate-limited internally. Tradeoff: a pathological resolve can still consume unbounded wall-clock time (mitigated only by the resolve-time budget in §31, not by backpressure). Operational implication: a slow network degrades fetch throughput gracefully (§4's FD budget) without ever making resolution itself nondeterministic or timing-dependent. Violating it would couple I3's determinism guarantee to transient system load, which P12 forbids.

P15 — Every deprecation ships with a warning window before removal. Rule: no manifest field, wire-format field, or CLI subcommand disappears in the same release it is first flagged deprecated (§27). Tradeoff: deprecated surface area must be maintained (and tested) for at least one additional minor release. Operational implication: operators upgrading pkg are never surprised by a silently vanished feature. Violating it turns every minor upgrade into a potential breaking change, undermining §27's entire compatibility contract.

8. Domain Model

8.1 SemVer Grammar (EBNF) and Precedence

version      ::= major "." minor "." patch [ "-" pre-release ] [ "+" build ]
major        ::= digits
minor        ::= digits
patch        ::= digits
digits       ::= "0" | pos-digit { digit }
pre-release  ::= pre-id { "." pre-id }
pre-id       ::= alphanum-id | digits
build        ::= build-id { "." build-id }
alphanum-id  ::= { digit | letter | "-" }  (must contain a non-digit)
version-req  ::= comparator { "," comparator } | "^" version | "~" version | "*"
comparator   ::= ( "=" | ">" | ">=" | "<" | "<=" ) version

Precedence table (highest to lowest, per SemVer 2.0.0 §11): major, then minor, then patch, numerically; a pre-release version has lower precedence than its associated normal version; pre-release identifiers compare left-to-right, numeric identifiers compare numerically, alphanumeric identifiers compare ASCII lexically, numeric identifiers always have lower precedence than alphanumeric; build metadata is ignored for precedence. 1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-beta < 1.0.0-rc.1 < 1.0.0.

8.3 Dependency Graph Model

The dependency graph is a directed graph over PackageId where an edge (A, B, req) means A declares a dependency on B satisfying VersionReq req. The graph is not known in full until resolution completes — before resolution it is a manifest graph (one node per direct dependency, unresolved); after resolution it is a lock graph (one node per resolved (PackageId, Version) pair, edges fully concrete). PubGrub never materializes the full manifest graph up front; it fetches IndexEntry records for a package lazily, only when that package is a candidate under consideration (§8.4).

8.4 PubGrub Incompatibility / Derivation Model

Concept Representation Meaning
Term (PackageId, VersionSet, positive: bool) "P is in range R" (positive) or "P is not in range R" (negative)
Incompatibility Vec<Term> + Cause a set of terms that cannot all be true simultaneously
Cause enum: Dependency, NoVersions, Conflict(derived from two incompatibilities), Root why the incompatibility exists — feeds P4's explanations
Assignment Term + decision_level + optional Cause one fact learned during search: a decision or a derivation
PartialSolution ordered list of Assignment the current in-progress candidate solution
decision_level integer increments on each decision (guess); derivations inherit the current level

Worked conflict-resolution trace (three packages: root requires a ^1.0.0; a 1.0.0 requires b ^2.0.0; a later fact reveals b's only published version is 1.5.0):

Step Assignment / Incompatibility Decision Level Cause
1 {root is 1.0.0} 0 Root
2 Incompatibility {not root@1.0.0, a in ^1.0.0} — Dependency (root→a)
3 Derive {a in ^1.0.0} 0 unit propagation on step 2
4 Decision: a = 1.0.0 1 decision (pick highest satisfying version)
5 Incompatibility {not a@1.0.0, b in ^2.0.0} — Dependency (a→b)
6 Derive {b in ^2.0.0} 1 unit propagation on step 5
7 Incompatibility {not b in ^2.0.0} (no matching version published; only 1.5.0 exists) — NoVersions
8 Conflict: steps 6 and 7 contradict — Conflict
9 Learn new incompatibility {not a@1.0.0} (backjump target = level 0) — derived Conflict, generalizes the root cause
10 Backjump to level 0, retry a at next candidate version (or fail with explanation "a 1.0.0 requires b ^2.0.0 but no version of b satisfies ^2.0.0; b's only published version is 1.5.0") 0 —

8.7 Sparse-Index Wire Format

Each package's index entry is a newline-delimited JSON (NDJSON) document at {index-base}/{name-path} (name-path sharded per Cargo convention: 1-char, 2-char, 3-char, or {first-2}/{next-2} for ≥4-char names), one JSON line per published version: {name, vers, deps: [{name, req, features, optional}], cksum, yanked, features}.

ETag/conditional-request sequence (RFC 7232):

Step Client Server Result
1 GET /a/aa/aaron (no If-None-Match, cold) 200 OK, body, ETag: "e1" full body transferred, cache stores e1
2 GET /a/aa/aaron, If-None-Match: "e1" index unchanged → 304 Not Modified, no body zero bytes transferred, cache entry revalidated
3 Upstream publishes a new version (server state changes) —
4 GET /a/aa/aaron, If-None-Match: "e1" 200 OK, new body, ETag: "e2" I8 fires: cache invalidated, new e2 stored

8.9 Worked Example

Manifest: app 0.1.0 depends on net ^2.0; net 2.3.0 (latest matching) depends on tls ^1.4; tls's latest matching version is 1.4.2. Resolver decisions: app@0.1.0 (root) → net@2.3.0 → tls@1.4.2. Lock graph: three [[package]] entries; app.dependencies = ["net 2.3.0"]; net.dependencies = ["tls 1.4.2"]. Re-running resolve against the same index snapshot reproduces this exact lock graph (I1, I3).

8.10 Malformed-Input Examples

  • Manifest with version = "1.0" (missing patch component): rejected at pm-manifest parse time, error names the missing patch field and cites §8.1 grammar.
  • Index entry with req = "^^1.0" (double caret): rejected at pm-semver parse time before it reaches the resolver; treated as a corrupt-index signal (T3 detection path).
  • Lockfile with package.checksum absent: rejected at pm-lockfile load time; refuses to build rather than silently trusting an unverified artifact (I6).
  • Sparse-index NDJSON line with an unterminated JSON object (truncated mid-fetch): rejected at the line level (§16.2's malformed-line handling); sibling lines in the same file remain usable, per the isolation discipline in §16.5.
  • Vendor bundle tarball with a truncated header (corrupt transfer): rejected as a distinct "corrupt bundle container" error at pkg vendor import before any per-object hash check is attempted (§22.8).

8.11 Failure-Path Example

app requires net ^3.0; the index has no published net version ≥ 3.0.0 (highest is 2.9.1). Resolver state machine reaches ConflictResolve with cause NoVersions, backjump level < 0, transitions to Failed. Emitted explanation: "app 0.1.0 depends on net ^3.0.0, but the latest available net is 2.9.1; no version of net satisfies ^3.0.0" — the full derivation chain from §8.4's trace-table format, not a bare error code.

8.12 Consistency & Concurrency Semantics

Cross-cutting summary of how each subsystem's consistency model composes into one system-level guarantee (MM6):

Subsystem Consistency Model Concurrency Discipline Governing Invariant
Resolver (§14) Deterministic, single-writer (one resolve call, one thread) No concurrency inside one resolve; multiple resolves may run in separate processes without shared state I3
Lockfile (§15) Snapshot-consistent (a lockfile is a point-in-time proof certificate, MM2) Read-mostly; writes are atomic-rename, never in-place mutation I1, I4-style discipline
Registry cache (§16) Eventually consistent across mirrors, strongly consistent per-request via conditional GET Bounded-concurrency fetch pool (§4 FD budget); no shared mutable cache state across requests beyond the on-disk ETag map I8, I12
CAS (§17) Append-only, content-addressed (identity implies immutability, P2) Lock-free reads; a snapshot-then-sweep GC critical section (§17.6) is the only serialization point I4, I5
Install/materialization (§18) Atomic-visibility (a package directory is all-or-nothing visible) Lock-free across distinct packages; same-package races are harmless under I4 I2
Build DAG (§19) Causal (a build never observes an un-materialized dependency) Bounded thread pool (ADR-13), one sandbox namespace per BuildUnit I2 (extended), I10
Signing/audit (§21) Fail-closed (unverified is never treated as verified) Synchronous gate per artifact, cached by content hash once verified I6

The composed guarantee: no subsystem's own consistency model is sufficient in isolation — I1's lockfile bijection depends on I3's resolver determinism, which depends on I7's total order, which depends on P12's discipline being honored at every serialization boundary (§13.9, §15.6, §19.2). A single layer's consistency bug propagates as an apparent bug in whichever layer is easiest to observe, not necessarily the layer where it originates (MM6's core insight, applied concretely here).

8.13 Worked Example — Feature Unification

Workspace with two members: svc-a depends on net ^2.0 with features = ["tls"]; svc-b depends on net ^2.0 with features = ["http2"]. Both are gated as optional features on net's own dep:compress optional dependency, activated only if either tls or http2 is enabled (§20.2's feature-graph edge model).

Step Event Feature Graph State Cause
1 Combined manifest graph loaded (§20.2) net requested by svc-a (feature tls) and svc-b (feature http2) Workspace load
2 Resolver decides net@2.3.0 (single decision, P11) One (PackageId, Version) entry pending unification Decision (§14.2)
3 Feature-graph edge: tls → dep:compress inactive alone compress not yet activated Graph traversal
4 Feature-graph edge: http2 → dep:compress activates it compress activated (either edge suffices) Graph traversal
5 Union: net@2.3.0's active feature set = {tls, http2, compress} I9 uniqueness check: exactly one net@2.3.0 entry Unification (P11)
6 Lock graph emitted: one net entry, features = ["tls", "http2", "compress"], visible to both svc-a and svc-b Terminal Solved

This is MM4's coupling made concrete: compress's activation depended on either dependent's feature choice, and once activated it is visible to both — including svc-a, which never asked for http2's companion feature (P11's documented tradeoff, §20.9).

13.2 Detailed Implementation Steps

  • Modules/files touched: pm-semver/src/{parse,cmp,req}.rs; pm-manifest/src/{schema,validate}.rs.
  • Algorithm named: hand-written recursive-descent parser over §8.1's EBNF (P4-aligned: a parser-generator would obscure the field-named error messages ADR-15 requires; each grammar production maps to one parse function, named identically to its EBNF rule).
  • Data structures: Version, VersionReq, Comparator, ComparatorOp (§11.1) constructed once at parse time, never mutated after (P1/P12 — an immutable value is trivially safe to share and compare without synchronization).

  • Observability hooks: a semver.compare.calls counter (I7's telemetry row, §7) wired even though a comparator bug is a compile-time-tested code defect, not a runtime signal — the counter exists so a later phase's perf profiling (§30) can attribute resolver hot-path time correctly.

Zero panics across a 10,000-case fuzz corpus seed (ADR-18) of adversarially malformed version strings.

13.6 Pitfalls

  • Comparing pre-release identifiers as raw strings instead of per-dot-segment — manifestation: 1.0.0-2 sorts after 1.0.0-10 under naive string compare; root cause: SemVer 2.0.0 requires numeric segments compare numerically, not lexically; debug method: unit-test the exact spec ordering example segment-by-segment; signal: a property test finds a non-transitive triple; recovery: segment on . first, classify each identifier numeric-vs-alphanumeric before comparing.
  • Treating build metadata (+build) as significant for equality — manifestation: I7's total order silently breaks; root cause: SemVer explicitly excludes build metadata from precedence; debug method: property test two versions differing only in +build; signal: they compare unequal when they must be precedence-equal; recovery: strip +build before any comparison, keep it only for Display.
  • Accepting a leading v prefix (v1.2.3) without an explicit opt-in — manifestation: silently divergent behavior from the SemVer 2.0.0 spec; root cause: many ecosystems tolerate this informally, but the spec does not define it; debug method: grep manifest fixtures for a v-prefixed version string; signal: a fixture parses when the spec says it should not; recovery: reject by default (this blueprint does not opt in), document the deviation if a future policy layer chooses to allow it.
  • Silently accepting a numeric identifier with a leading zero (1.0.0-01) — manifestation: two logically distinct pre-release strings compare as string-equal when only one is spec-legal; root cause: missing the explicit leading-zero-numeric-identifier rejection rule; debug method: fuzz corpus (§13.4) surfaces it as a diverging-behavior case; signal: "01" and "1" are treated as the same identifier; recovery: reject at parse time, named error citing §8.1.

13.7 Performance Concerns

The comparator runs on every candidate version during resolution (§14) — an accidental O(n²) comparison (e.g., re-parsing strings on every compare instead of comparing parsed Version structs) silently blows the §4 p95 resolve-latency budget at 500-package scale; parse once, compare parsed structs. VersionReq::matches is called once per candidate per decision (§14.2's decision-making step) — keep it allocation-free (no intermediate String formatting) to avoid a hidden allocator-pressure tax at 500-package scale (M1/M2).

13.8 Edge Cases

  • Version 0.0.0 (valid per grammar, lowest possible precedence).
  • Pre-release with a numeric-looking-but-leading-zero identifier (1.0.0-01 — SemVer 2.0.0 explicitly disallows leading zeros in numeric identifiers; must reject, not silently accept as string "01").
  • A manifest with an empty dependencies table (valid, zero-dependency package).
  • A version string at the exact u64 boundary for major/minor/patch (grammar permits arbitrarily large digit sequences; must not silently truncate or panic on overflow — reject with a named "out of range" error instead).

13.9 Failure Analysis

Symptom: two builds of the identical manifest on different OSes produce different resolved orderings during later resolution. Root cause: HashMap iteration order used somewhere upstream of the comparator instead of BTreeMap (violates P12/ADR-21 discipline even though this phase is semver-only). Debug method: diff the exact sequence of comparator calls between the two runs via a captured trace; signal is a reordering with identical comparator results but different call order feeding a non-deterministic first-match heuristic downstream. Containment: the bug is caught here, in Phase 1's own property tests, rather than surfacing three phases later as an unexplained I3 violation (MM6).

13.10 Operational Notes

pkg semver check "<version>" and pkg semver satisfies "<req>" "<version>" ship as debug-only CLI subcommands from this phase, giving operators a way to sanity-check a version string against the grammar without invoking a full resolve.

14. Phase 2 — PubGrub Resolver Core

14.1 Objectives

Implement pm-resolver's core: the Term/Incompatibility/Assignment/PartialSolution model (§11.3), unit propagation, decision-making, and conflict-driven incompatibility learning per the state machine in §8.5, against an in-memory fixture registry (the real pm-registry HTTP client arrives in Phase 4; this phase uses a hardcoded IndexEntry map).

14.2 Detailed Implementation Steps

  • Modules/files touched: pm-resolver/src/{term,incompatibility,partial_solution,propagate,decide,conflict,explain}.rs.
  • Algorithm named — unit propagation: Moskewicz et al.'s watched-literal pattern (DAC 2001, Chaff, §5) adapted to Terms instead of SAT literals — track, per Incompatibility, the terms not yet falsified, and only re-examine an incompatibility when one of its watched terms changes (I3-safe: a pure function of PartialSolution state).
  • Algorithm named — decision-making: P9-driven heuristic — when no propagation is pending, pick the package with the fewest viable candidate versions remaining (reduces expected backtracking depth) and decide its highest satisfying version, fetching its IndexEntry lazily (§8.3) only at this point.
  • Algorithm named — conflict resolution: GRASP/DPLL lineage (Marques-Silva & Sakallah 1999; Davis–Putnam–Logemann–Loveland 1962, §5) — walk backward through the derivation chain, resolve pairs of conflicting incompatibilities per Weizenbaum's PubGrub algorithm, compute a backjump decision level as a pure function of PartialSolution (never randomized, per I3/P12).
  • Data structures: Term, Incompatibility, Assignment, PartialSolution (§11.3) — Cause::Conflict recursion depth bounded by decision-level count, preventing unbounded memory growth (I5-adjacent memory discipline).
  • Sync primitives: none — the resolver is deliberately single-threaded (ADR-13 reserves parallelism for network/build, not search, to preserve I3's determinism).
  • Persistence: none — Incompatibility/Assignment are ephemeral to one resolve call; only the final lock graph (Phase 3) persists.
  • Observability hooks: resolve.propagation.no_progress counter (FM-1's detection point, §25); a decision-level trace log emitted at DEBUG level for pkg resolve --explain (§14.10).
  • Test harness: the explanation renderer (P4) — given a Cause::Conflict chain, render it top-down as the §8.4 trace-table format, verified byte-for-byte against the diamond-conflict fixture.

14.3 Deliverable

pm-resolver::resolve(manifest, fixture_index) -> Result<Lockfile, ResolveError> correctly resolves the worked example (§8.9) and the worked conflict (§8.4) against the in-memory fixture, matching the exact trace-table sequence.

14.4 Acceptance Criteria

Resolves a 500-package synthetic fixture graph (conformance/fixtures/phase2/synthetic-500/) within 450 ms p95 wall-clock, single-threaded, per §4's SC-row (M2). Peak resolver memory stays under 128 MiB on the same fixture (§4, M4). Conflict-explanation output for conformance/fixtures/phase2/diamond-conflict/ matches the expected derivation chain byte-for-byte. Zero nondeterminism across 100 repeated resolves of the same fixture (I3, replay-nondeterminism-regression).

14.5 Conformance Fixtures

  • conformance/fixtures/phase2/synthetic-500/ — a generated 500-package graph with realistic fan-out (avg out-degree 3, per ADR-21's sparsity assumption); expected: a valid lock graph within the §4 latency budget.
  • conformance/fixtures/phase2/diamond-conflict/ — the §8.4 worked trace as a fixture; expected: exact incompatibility-derivation sequence.
  • conformance/fixtures/phase2/no-solution/ — the §8.11 failure-path example; expected: ResolveError::NoVersions with the exact explanation string.
  • conformance/fixtures/phase2/replay-nondeterminism-regression/ — a captured historical case where two runs diverged (replay fixture per §12.2's convention); expected: identical output on every replay.
  • conformance/fixtures/phase2/legitimate-diamond-no-conflict/ — the §14.8 legitimate-diamond edge case; expected: resolves without a spurious conflict.

14.6 Pitfalls

  • Growing the incompatibility set unboundedly without simplification — manifestation: wall-clock degrades on large graphs; root cause: Dart pub's own implementation notes (§5) flag unbounded incompatibility growth as a real performance cliff; debug method: track incompatibility-set size over decision count; signal: superlinear growth with no periodic drop; recovery: periodically drop subsumed incompatibilities.
  • Randomizing decision order for "better average case" — manifestation: two runs of the same fixture diverge; root cause: directly violates I3/P12; debug method: replay the same fixture twice, diff outputs; signal: any byte-level divergence; recovery: any heuristic must be a pure, deterministic function of graph shape, never a random tie-break.
  • Conflating "no version satisfies the range" (NoVersions, an index fact) with "the range itself is malformed" (a pm-semver-layer parse error) — manifestation: misleading explanation text; root cause: sharing one error variant for two distinct fault classes; debug method: inspect ResolveError variant at the failure site; signal: a NoVersions explanation naming a range that never should have parsed; recovery: keep them as distinct variants (§11.5).
  • Off-by-one in backjump level computation — manifestation: resolver re-explores the same dead branch infinitely, or discards a still-valid decision; root cause: incorrect backjump-target arithmetic; debug method: verify against the SANER 2020 survey's (Abate et al., §5) description of correct backjumping; signal: decision-level sequence oscillates without shrinking the search space; recovery: fix the backjump-target formula, add a regression fixture.
  • Fetching every package's IndexEntry eagerly instead of lazily — manifestation: request count blows past the §4 sparse-index budget even in the fixture-backed phase; root cause: prefetching the whole manifest graph up front instead of per §8.3's online-fetch model; debug method: count fixture-index lookups per resolve; signal: lookup count exceeds the graph's actual package count; recovery: fetch only when a package becomes a decision candidate.

14.7 Performance Concerns

Unit propagation dominates wall-clock time on graphs with deep transitive chains; the watched-literal-style optimization (§14.2) is not optional past ~200 packages — without it, propagation degrades toward the naive O(incompatibilities × terms) per-step cost and blows the p95 target in §4/M2. Lazy IndexEntry fetching (only fetch metadata for a package once it becomes a decision candidate) bounds the request count in §4's sparse-index-requests row (M7), but in Phase 2's fixture-backed form this is simulated, not yet measured against real network latency (that measurement is Phase 4's job, §16). Memory: Assignment history must not retain fully materialized IndexEntry copies beyond what PartialSolution needs live, or M4's 128 MiB ceiling is at risk on the 500-package fixture.

14.8 Edge Cases

  • A package that depends on itself transitively through two different version ranges that both resolve to the same version (not a cycle bug, a legitimate diamond — must not be flagged as a conflict).
  • A root manifest with zero dependencies (resolves trivially to a one-entry lock graph).
  • A dependency range that matches infinitely many published versions (e.g., *) — decision-making must still pick exactly one (highest) without enumerating all candidates eagerly.
  • Two incompatibilities that are logical duplicates derived via different derivation paths — must be recognized as subsuming one another (§14.6) rather than both retained, or memory grows without bound on pathological graphs.

14.9 Failure Analysis

Symptom: resolver hangs (never reaches Solved or Failed) on a specific fixture. Root cause: a backjump loop where the same decision level is repeatedly re-derived without the incompatibility set actually shrinking the search space (a learning-soundness bug, FM-1). Debug method: log the decision-level sequence and incompatibility-count-over-time; a flat or oscillating incompatibility count with no forward progress is the signal (resolve.propagation.no_progress telemetry counter, §30). Blast radius: a single pathological manifest can hang one pkg resolve invocation; it does not corrupt any persisted state (resolution is side-effect-free until Solved). Recovery: add an iteration cap in tests only (never in production, where it would silently truncate valid searches) purely to catch the regression before it escapes to production.

14.10 Operational Notes

pkg resolve --explain surfaces the full trace-table-formatted derivation chain on failure, matching §8.4's format exactly, so operators never see a bare "resolution failed." The decision-level trace log (§14.2) is gated behind RUST_LOG=pm_resolver=debug to avoid P13's telemetry-redaction concerns leaking into default-verbosity production logs.

  • Data structures: Lockfile, LockedPackage (§11.4), serialized to TOML with lexically sorted [[package]] entries and lexically sorted dependencies arrays within each entry (P12 — determinism is a serialization-layer property, not just a resolver-layer one).
  • Algorithm named — verify: pkg lock verify loads an existing lockfile, re-runs pm-resolver::resolve (§14) against the same manifest and the index_snapshot token recorded in the lockfile (§8.6), and byte-compares the freshly serialized output against the on-disk file — I1's direct enforcement point.
  • Algorithm named — schema check: I11's forward-read rule — a lockfile whose version field is more than one major step behind the current pm-lockfile schema version is rejected with a named upgrade prompt, never silently migrated.
  • Sync primitives: none — lockfile I/O is single-threaded per invocation; the write path reuses I4-style atomic rename (temp-write-then-rename) to avoid a torn-write hazard.
  • Persistence: the lockfile itself, at <project>/pkg.lock, is the persisted artifact (P5 — the lockfile, not the manifest, is the unit of reproducibility).
  • Observability hooks: lockfile.reresolve.mismatch counter (I1's telemetry row, §7), fired every time verify detects drift, feeding a dashboard trend line distinguishing "occasional intentional update" from "chronic drift."
  • Test harness: a triple-run determinism fixture — serialize the same resolve three independent times, assert byte-identical output every time.

15.3 Deliverable

pm-lockfile round-trips the worked example (§8.9) losslessly and pkg lock verify passes on a freshly generated lockfile and fails loudly (not silently) on a hand-edited, now-inconsistent one.

15.4 Acceptance Criteria

Lockfile serialization is byte-identical across three independent runs on the same fixture (conformance/fixtures/phase3/determinism-triple-run/). pkg lock verify detects a hand-edited version bump within one field-level diff line. Schema-version mismatch (version = 999) rejected with a named upgrade-required error, not a parse crash. pkg lock verify on a 500-package lockfile completes within the §4/M2 p95 resolve budget (450 ms), since it internally re-runs the full resolver.

15.5 Conformance Fixtures

  • conformance/fixtures/phase3/worked-example-roundtrip/ — the §8.9 worked example; expected: identical Lockfile struct after serialize-then-deserialize.
  • conformance/fixtures/phase3/hand-edited-drift/ — a valid lockfile with one checksum field manually altered; expected: pkg lock verify fails naming that exact package entry.
  • conformance/fixtures/phase3/cross-platform-determinism/ — the same manifest resolved on two recorded platform fixtures (simulated path-separator and line-ending differences); expected: identical lockfile bytes.
  • conformance/fixtures/phase3/schema-version-too-new/ — version = 999; expected: named upgrade-required error.
  • conformance/fixtures/phase3/zero-package-lockfile/ — a manifest with no dependencies (§15.8); expected: a valid, verifiable, one-line lockfile.

15.6 Pitfalls

  • Using a HashMap anywhere in the serialization path — manifestation: nondeterministic byte output across runs; root cause: reintroducing the nondeterminism Phase 1's BTreeMap discipline was supposed to close off; debug method: audit every collection type touched by the lockfile writer; signal: determinism-triple-run fixture fails intermittently; recovery: replace with BTreeMap/sorted Vec.
  • Silently "fixing up" a hand-edited lockfile instead of failing — manifestation: a tampered checksum goes undetected; root cause: P5's contract is that the lockfile is authoritative, and auto-repair masks a real drift (an attacker-edited checksum is T6/T8 territory); debug method: attempt the hand-edited-drift fixture and confirm a hard failure, not a silent rewrite; signal: pkg lock verify exits 0 on a deliberately corrupted fixture; recovery: never auto-repair, always fail loudly naming the exact field.
  • Ignoring line-ending and path-separator differences (\r\n vs \n, \ vs /) — manifestation: cross-platform byte mismatch even when every logical field matches; root cause: OS-level newline/path conventions leaking into the serializer; debug method: run cross-platform-determinism on both simulated platform fixtures; signal: byte-diff isolates to whitespace/separator characters only; recovery: normalize both at the serializer boundary, never at the OS boundary.
  • Caching a prior resolve's result and skipping the full re-resolve inside verify "for speed" — manifestation: verify reports clean on a lockfile that would not actually re-resolve to itself; root cause: conflating "fast" with "correct" under time pressure; debug method: deliberately corrupt an index-snapshot-dependent field and confirm verify still catches it; signal: a known-bad fixture passes; recovery: verify must always perform the full resolve, per I1's exact definition.

15.7 Performance Concerns

pkg lock verify re-runs the full resolver (§14) — on a 500-package lockfile this must still land within the §4 p95 resolve budget (M2), since pkg build may invoke verify on every CI run; a verify that silently skips the full re-resolve "for speed" would violate I1's very definition. Serialization itself (sorting + TOML encoding) must stay sub-millisecond relative to the resolve it wraps, or verify's wall-clock budget is dominated by the wrong stage.

15.8 Edge Cases

  • A lockfile with zero packages (a manifest with no dependencies, still a valid, verifiable lockfile).
  • Two packages with the same name from two different SourceIds (registry vs vendored) — the lock record layout's source field must disambiguate them, and pkg lock verify must not conflate them as duplicates.
  • A lockfile written by a pm-lockfile version one minor step ahead of the reading binary (an additive-only field per §27) — must parse successfully, ignoring the unknown field, not fail closed.

15.9 Failure Analysis

Symptom: pkg lock verify fails in CI but passes locally. Root cause candidates: an unpinned index_snapshot token that the local registry mock returns differently than the real registry (Phase 4 concern surfacing early); or an OS-specific line-ending regression from §15.6. Debug method: diff the exact TOML bytes between local and CI output, byte-for-byte, before assuming a logic bug; the byte diff usually localizes to one of the two known hazard classes immediately. Operator visibility: pkg lock verify --ci's exit code (§15.10) distinguishes the failure class at the CI-log level without requiring a human to read the byte diff first.

15.10 Operational Notes

pkg lock verify --ci runs in non-interactive mode returning a machine-readable exit code (0 = reproducible, 1 = drift detected, 2 = schema too new) for direct use in ci.yml.

16. Phase 4 — Sparse Registry Protocol

16.1 Objectives

Implement pm-registry: a real HTTP client for the sparse-index wire format (§8.7), ETag/conditional-GET caching (RFC 7232), and replace Phase 2's in-memory fixture with live IndexEntry fetches feeding the resolver from Phase 2 unchanged (the resolver's interface to the registry, Fetcher, was already trait-abstracted in §11.5).

16.2 Detailed Implementation Steps

  • Modules/files touched: pm-registry/src/{sharding,conditional_get,cache,mirror_queue}.rs; tools/index-fixture-server/ (test double).
  • Algorithm named — sharding: the name-path scheme from §8.7 (1/2/3-char direct, {first-2}/{next-2} for ≥4-char names, Cargo sparse-protocol precedent, §5).
  • Algorithm named — conditional GET: cache every ETag response header keyed by request path; on a subsequent request send If-None-Match; treat 304 as "reuse cached body" and 200 as "replace cached body and ETag" — I8's enforcement point.
  • Data structures: an on-disk index cache under $PM_HOME/index-cache/ mirroring the name-path shard layout; an in-memory Fetcher trait object (§11.5) shared between pm-registry and pm-mirror (Phase 10).
  • Algorithm named — lazy batching: since PubGrub (§14) requests IndexEntry metadata lazily as it becomes a decision candidate, issue index requests as needed rather than prefetching the whole graph — bounding request count per §4/M7.
  • Algorithm named — mirror failover: ADR-24's ordered registry-base-URL list; on primary timeout or 5xx, retry the next mirror, hash-verifying every response against the index-declared checksum regardless of source (I12, P3).
  • Sync primitives: a bounded semaphore gating concurrent in-flight HTTP requests (§4's FD budget, M-row alignment); the resolver's single-threaded decision loop (§14.2) issues requests but does not block on more than the semaphore's width concurrently.
  • Persistence: $PM_HOME/index-cache/ on disk, keyed by sharded path; survives across pkg invocations (distinguishing warm from cold resolve).
  • Observability hooks: registry.cache.invalidations (I8), a per-mirror request/failure counter feeding the failover-queue's health view.
  • Test harness: tools/index-fixture-server/ serves the four-step ETag sequence (§8.7) and simulated mirror-down/hash-mismatch scenarios deterministically for CI.

16.3 Deliverable

pm-registry fetches and caches real IndexEntry records over HTTPS, feeding pm-resolver from Phase 2 with zero changes to the resolver's own code, and demonstrates a warm-cache resolve producing ≥95% 304 responses per §4.

16.4 Acceptance Criteria

Cold resolve of the 500-package fixture (now over HTTP against a local fixture server, tools/index-fixture-server/) issues ≤ 500 index requests (§4, M7). Warm resolve (second run, same fixture) achieves ≥ 95% 304 responses with zero body bytes transferred on those (§4/M8, §8.7 step 2). Mirror failover fixture (conformance/fixtures/phase4/primary-down/) succeeds against the secondary mirror within 2 retry attempts.

16.5 Conformance Fixtures

  • conformance/fixtures/phase4/etag-sequence/ — replays the exact four-step sequence from §8.7's table; expected: cache state matches each step.
  • conformance/fixtures/phase4/primary-down/ — fixture server configured to 503 on the primary; expected: successful failover to mirror 2 within the retry budget.
  • conformance/fixtures/phase4/hash-mismatch-mirror/ — a mirror serving a body that does not match the index-declared checksum; expected: FetchError::HashMismatch, mirror dropped, next mirror tried (I12).
  • conformance/fixtures/phase4/malformed-ndjson-line/ — one corrupt line in an otherwise valid index file; expected: that single version entry rejected, sibling entries still usable.
  • conformance/fixtures/phase4/redirect-outside-allowlist/ — a mirror 3xx-redirecting to a host outside the configured allow-list; expected: redirect not followed, named rejection (T3 mitigation, §16.8).

16.6 Pitfalls

  • Caching a 200 response's ETag but forgetting to invalidate any resolver-side memoization keyed on the old body — manifestation: I8 violated even though the on-disk cache is correct; root cause: a second in-memory cache layer unaware of the on-disk invalidation event; debug method: trace a full 200-after-304 sequence end to end; signal: resolver behavior reflects a stale body after a confirmed cache update; recovery: invalidate every memoized layer at the same generation-counter tick (§11.4).
  • Treating index unavailability (network down, all mirrors exhausted) as equivalent to "package does not exist" — manifestation: a false "no such package" during a network outage; root cause: sharing one error path for two distinct fault classes; debug method: simulate an outage fixture and inspect the surfaced ResolveError/FetchError variant; signal: NoVersions returned when the true cause is IndexUnavailable; recovery: keep them distinct (§11.5) — the left-pad (2016) unpublish incident is the cautionary tale for conflating "temporarily unavailable" with "does not exist" at the registry layer (FM-8).
  • Not verifying the mirror response hash before caching it — manifestation: a permanently poisoned cache entry; root cause: trusting mirror content without independent verification; debug method: hash-mismatch-mirror fixture; signal: an unverified mirror body reaches pm-store; recovery: I12/P3's hash-then-write discipline, no exceptions for "trusted" mirrors.
  • Following a redirect past the configured mirror allow-list — manifestation: an on-path attacker's redirect silently substitutes an untrusted origin; root cause: default HTTP-client redirect-following behavior with no allow-list check; debug method: redirect-outside-allowlist fixture; signal: a request reaches a host never configured as primary or mirror; recovery: disable automatic redirect-following, resolve redirects only against the configured allow-list (T3).

16.7 Performance Concerns

RTT dominates cold-resolve wall clock at the assumed 60 ms p50 / 250 ms p95 baseline (§4): with up to 500 sequential single-package requests and no batching, cold resolve could reach into seconds; bounded concurrent fetching (§4's FD budget) is required to hit the p95 target (M1/M2), prefetching a small window of "likely next decision candidates" ahead of the resolver's actual demand (a uv-inspired speculative-prefetch pattern, §5) without violating I3 (prefetch must never change the decision order, only its I/O timing). Warm-path throughput (M8) depends on 304 header parsing staying allocation-light — a header-only response should not trigger the same body-buffer allocation path as a 200.

16.8 Edge Cases

  • A package whose index file exists but contains zero non-yanked versions (all published versions yanked) — must surface as NoVersions, not as a parse error.
  • An index server returning 200 with an identical body to the cached one (no ETag support on that mirror) — must still function correctly, just without the bandwidth savings of I8.
  • A redirect (3xx) from a mirror to an unexpected host — must not be followed silently past the configured mirror allow-list (T3 mitigation).
  • A response with a valid ETag but a body that fails NDJSON parsing entirely (not just one malformed line, but a structurally invalid file) — must be rejected as a distinct "corrupt index" signal, not silently cached as an empty version list.

16.9 Failure Analysis

Symptom: intermittent NoVersions errors for a package known to exist. Root cause candidates: a load-balanced registry origin serving an eventually-consistent, momentarily-stale index shard; or a genuine yank event racing the resolve. Debug method: capture the exact response headers (ETag, Date) alongside the body in a replay fixture; compare against a second immediate request — a self-resolving second request confirms eventual consistency, not a client bug. Operator visibility: pkg registry ping <name> (§16.10) is the first diagnostic step before escalating as a registry-operator incident.

16.10 Operational Notes

pkg registry ping <name> issues a single conditional GET and reports cache-hit/miss plus RTT, giving operators a fast way to distinguish "my network is slow" from "my resolver is slow" before filing a performance bug against Phase 2's resolver.

17. Phase 5 — CAS Cache + GC

17.1 Objectives

Implement pm-store: the BLAKE3 content-addressed record layout (§8.8), write-once atomic-rename discipline (I4), and mark-and-sweep garbage collection rooted at pinned lockfiles (I5, P8).

17.2 Detailed Implementation Steps

  • Modules/files touched: pm-store/src/{write,refcount,gc,verify}.rs.
  • Algorithm named — write path: hash incoming bytes with BLAKE3 (ADR-07), write to a temp file, atomically rename into objects/{hash[0:2]}/{hash[2:4]}/{hash} (§8.8) — hash-then-write, never write-then-hash, is what makes I4 hold even under a crash mid-write (a partial temp file is simply never renamed into place, so it is invisible).
  • Data structures: refcount metadata as a refs/{hash} file listing every lockfile ID (a hash of the lockfile's own canonical bytes) that references the object.
  • Interfaces added: pkg cache pin <lockfile> / pkg cache unpin <lockfile> managing the GC root set (P8).
  • Algorithm named — mark-and-sweep GC: mark phase walks every pinned lockfile's [[package]] checksums into a live set (a root-set snapshot taken atomically before sweep begins, per I5's enforcement note); sweep phase deletes any objects/ entry not in the live set.
  • Algorithm named — watermark trigger: GC runs automatically when store size exceeds 20 GiB or free disk drops below 5% (§4), otherwise only on explicit pkg cache gc.
  • Sync primitives: a store-level advisory lock held only during the root-set snapshot (bounding GC's critical section, §17.7), not during the full sweep — sweep proceeds against an immutable snapshot, so concurrent reads never block on it.
  • Persistence: objects/ (content), refs/ (refcount metadata) — both under $PM_HOME/store/, both append-only per P2/I4.
  • Observability hooks: gc.roots.count, gc.swept.bytes (I5, §7); store.write.hash_mismatch (I4).
  • Test harness: a simulated-crash fixture that kills the write process after temp-file write but before rename, asserting zero corrupt objects visible on restart.

17.3 Deliverable

pm-store write/read round-trips content-addressed blobs with I4's crash-safety property, and pkg cache gc reclaims exactly the unreferenced objects, verified against a fixture with a mix of pinned and unpinned lockfiles.

17.4 Acceptance Criteria

A simulated crash mid-write (kill process after temp-file write, before rename) leaves zero corrupt objects visible on restart (conformance/fixtures/phase5/crash-mid-write/). GC on a fixture store with 1000 objects, 400 referenced by a pinned lockfile, deletes exactly 600 (§4's storage-amplification row bounds the remainder). GC never runs concurrently with an active install per I5/I2 — verified via a fixture that starts a GC and an install in the same process and asserts no GcRaceDetected under correct sequencing, but does assert it under a deliberately broken sequencing fixture. GC sweep of a 20 GiB store completes within the §4/M9 RTO bound (≤ 5 s) via batched unlinking.

17.5 Conformance Fixtures

  • conformance/fixtures/phase5/crash-mid-write/ — simulated kill signal between temp-write and rename; expected: no partial object visible.
  • conformance/fixtures/phase5/gc-mixed-pinned/ — 1000 objects, 400 pinned; expected: exactly 600 deleted, live set matches expected list.
  • conformance/fixtures/phase5/gc-race-detection/ — a deliberately mis-sequenced concurrent GC + install; expected: StoreError::GcRaceDetected raised, not silent corruption.
  • conformance/fixtures/phase5/watermark-trigger/ — store size fixture exceeding 20 GiB threshold; expected: automatic GC invoked without an explicit pkg cache gc call.
  • conformance/fixtures/phase5/stale-ref-orphan/ — a refs/{hash} file naming a lockfile ID no longer present anywhere on disk; expected: treated as unreferenced at sweep time, object deleted without error.

17.6 Pitfalls

  • Computing the hash after the file is already visible at its final path (write-then-hash) — manifestation: a crash between write and hash-verify leaves a corrupt-but-visible object; root cause: reversing the required hash-then-write order; debug method: fault-inject a crash immediately after write, before hashing; signal: a corrupt object survives restart; recovery: always hash before the atomic rename (I4).
  • Taking the GC root-set snapshot non-atomically — manifestation: an object pinned mid-sweep gets deleted; root cause: reading the pinned-lockfile list, then separately walking each one, with a pkg cache pin racing in between; debug method: gc-race-detection fixture; signal: a pin call during sweep does not prevent deletion; recovery: snapshot the full root set in one pass before any deletion begins (I5's enforcement note).
  • Refcounting without handling "same object referenced by two lockfiles, one unpinned mid-sweep" — manifestation: an object still needed by a pinned lockfile is deleted; root cause: trusting stale refcounts instead of recomputing liveness from the current pinned set; debug method: gc-mixed-pinned with an unpin racing the sweep; signal: refcount says "referenced" but the actual pinned set has moved on; recovery: recompute liveness from the current pinned set at sweep time, never from stale refcounts alone.
  • Unbounded sweep-phase unlink batching — manifestation: GC saturates the FD budget (§4) alongside a concurrent install's own FD usage; root cause: issuing all unlinks in one unthrottled burst; debug method: monitor FD count during a large-store GC run; signal: FD count spikes near the 1024 ceiling; recovery: throttle/batch sweep unlinks (§17.7).

17.7 Performance Concerns

GC over a large store (approaching the 20 GiB high watermark, §4) must not block installs indefinitely; the mark phase's root-set snapshot bounds GC's critical section, but the sweep phase (actual unlink calls) should be throttled/batched to avoid saturating the FD budget (§4) alongside any concurrent install's own FD usage. M9's 5 s RTO target for a 20 GiB sweep requires roughly 4 GiB/s-equivalent metadata throughput if naively serial — achieved instead via batched, parallel unlink across the sharded objects/{hash[0:2]}/{hash[2:4]}/ directory structure (§8.8), which naturally partitions work across up to 65,536 shard buckets.

17.8 Edge Cases

  • An object referenced by two different packages with different names but identical content (deduplication case, P2/ADR-07) — refcount metadata must list both referencing lockfile IDs, and GC must not delete it while either reference is pinned.
  • A store directory that has never had any object written (first run) — GC must no-op cleanly, not error on a missing objects/ directory.
  • A refs/{hash} file that references a lockfile ID no longer present anywhere on disk (a stale unpin that was never recorded) — treat as unreferenced at sweep time, not as an error.
  • A concurrent pkg cache pin and pkg cache unpin on the same lockfile ID racing each other, both outside any active sweep — last-writer-wins is acceptable here (unlike mid-sweep, §17.6) since no deletion decision is in flight.

17.9 Failure Analysis

Symptom: disk usage grows unbounded despite pkg cache gc running on schedule. Root cause candidates: an operator never calling pkg cache unpin on old lockfiles (P8's documented tradeoff materializing exactly as predicted in §1); or a bug in root-set computation treating every historical lockfile as still pinned. Debug method: pkg cache gc --dry-run --explain lists the computed root set and its source (which pinned lockfile each retained object traces to) — an unexpectedly large root set immediately reveals whether the issue is operator hygiene or a computation bug. Blast radius: unbounded growth is a capacity problem, never a correctness one (I5 guarantees nothing needed is ever deleted) — the failure mode is purely operational.

17.10 Operational Notes

pkg cache verify walks every object, recomputes its BLAKE3 hash, and flags any mismatch (bit rot or tampering, T6-adjacent) as a runbook-documented (docs/runbooks/) recovery procedure: re-fetch the mismatched object from its original registry source.

18. Phase 6 — Install / Materialization

18.1 Objectives

Implement pm-install: turning a resolved lockfile plus store-resident objects into a materialized build tree via linking (not copying), enforcing I2's atomic-visibility guarantee.

18.2 Detailed Implementation Steps

  • Modules/files touched: pm-install/src/{materialize,marker,fallback}.rs.
  • Algorithm named — materialization: for each LockedPackage (§8.6), resolve its StoreHandle (§11.5) from pm-store, and hardlink (same-filesystem) or reflink (copy-on-write filesystem, when available) the object into a per-package staging directory under target/deps/{name}-{version}/.
  • Algorithm named — atomic visibility (I2): build the staging directory fully under a temp name, then atomically rename it into its final visible path — a build process reading target/deps/ never observes a half-populated package directory.
  • Data structures: a per-package marker file recording the content hash actually linked, distinguishing a real idempotent hit from a stale directory.
  • Algorithm named — materialization plan cache: skip re-linking a package whose staging directory already exists with the correct content hash recorded in its marker file (idempotent re-install, avoiding redundant I/O on repeat pkg build invocations).
  • Algorithm named — fallback-to-copy: when hardlink/reflink is unavailable (cross-filesystem $PM_HOME), copy bytes instead, with a telemetry counter distinguishing link-mode from copy-mode installs.
  • Sync primitives: no explicit lock — atomicity comes from the filesystem's own rename semantics (I2), so concurrent installs of different packages proceed lock-free; two installs of the same package race harmlessly (last rename wins, content is identical by I4).
  • Persistence: target/deps/{name}-{version}/ plus its marker file; ephemeral to one build tree, regenerable from the store at any time.
  • Observability hooks: link-mode vs copy-mode counters (feeding §4/M6's warm-install-throughput target, which assumes link mode); install.partial.detected (I2).
  • Test harness: a 1000-trial concurrent-visibility fixture — a reader thread polls target/deps/ continuously while an installer thread runs, asserting zero partial-directory observations.

18.3 Deliverable

pkg install (invoked implicitly by pkg build) materializes a full lockfile's packages into a build tree using links, never exposing a partial directory to a concurrently running build.

18.4 Acceptance Criteria

Warm install (all objects already in store, link mode, same filesystem) achieves ≥ 800 MB/s materialization throughput on the 500-package fixture (§4/M6). A build process polling target/deps/ during a concurrent install never observes a directory missing its completion marker (conformance/fixtures/phase6/concurrent-visibility/). Idempotent re-install (second pkg install with no lockfile change) completes in under 50 ms (M12, marker-cache hit path).

18.5 Conformance Fixtures

  • conformance/fixtures/phase6/concurrent-visibility/ — a build reader polling during install; expected: zero partial-directory observations across 1000 trials.
  • conformance/fixtures/phase6/cross-filesystem-fallback/ — $PM_HOME on a different filesystem than the build tree; expected: copy-mode fallback used, correctness preserved, throughput target relaxed accordingly.
  • conformance/fixtures/phase6/idempotent-reinstall/ — a second install with an unchanged lockfile; expected: marker-cache hit, no re-linking I/O.
  • conformance/fixtures/phase6/missing-store-object/ — a lockfile referencing a checksum not present in the store; expected: named StoreError::NotFound, triggers a re-fetch through pm-registry/pm-mirror, not a silent failure.
  • conformance/fixtures/phase6/stale-target-deps-dir/ — a target/deps/ containing a pre-lockfile-change directory for an old version; expected: removed or ignored, never mixed into the new build's view (§18.8).

18.6 Pitfalls

  • Renaming the staging directory before all its files are fully written — manifestation: a build reads a half-populated directory; root cause: I2 requires the entire package directory complete before rename, not just the top-level entry; debug method: concurrent-visibility fixture with narrowed timing windows; signal: a partial-directory observation in any of the 1000 trials; recovery: complete every file write before the single top-level rename.
  • Assuming hardlinks are always available — manifestation: silent hardlink failures on a cross-filesystem $PM_HOME (common on CI runners with a separate cache volume); root cause: no filesystem-boundary check before attempting hardlink; debug method: cross-filesystem-fallback fixture; signal: hardlink syscall fails with EXDEV; recovery: detect the cross-device error explicitly and fall back to copy-mode rather than erroring.
  • Forgetting to invalidate the marker-cache when the store object itself changes underneath an unchanged lockfile — manifestation: a desynced marker silently serves stale content; root cause: should be impossible under I4's append-only guarantee, but a corrupted store (§17.10) could otherwise desync silently; debug method: corrupt a store object out-of-band and re-run install; signal: marker reports a hit despite content mismatch; recovery: marker must include the content hash, not just an "installed" boolean.
  • Racing two installs of the same package under copy-mode (no atomic rename benefit from a single filesystem op) — manifestation: a torn copy visible mid-write; root cause: copy-mode's fallback path must reimplement the same temp-then-rename discipline as link-mode, not just "copy directly to the final path"; debug method: concurrent-visibility fixture run specifically in copy-mode; signal: partial file observed only in the copy-mode configuration; recovery: apply the identical stage-then-rename pattern regardless of link vs copy mode.

18.7 Performance Concerns

Hardlink/reflink-based materialization is the entire reason the §4/M6 warm-install throughput target (≥ 800 MB/s) is achievable at all — a copy-based fallback path realistically caps out around typical disk-bandwidth numbers (hundreds of MB/s), so the fallback path's performance floor must be documented separately and not conflated with the link-mode target in dashboards (§30). Marker-file lookups on the idempotent-reinstall path (M12) must be a single stat-equivalent call per package, not a full re-hash, or the 50 ms ceiling is unreachable at 500-package scale.

18.8 Edge Cases

  • Two packages in the same lockfile that are byte-identical (same content hash, different names — a legitimate dedupe case per P2) — materialization must link both directory entries to the same store object without either write racing the other.
  • A build tree that already has a stale (pre-lockfile-change) target/deps/{name}-{old-version}/ directory from a prior build — must be removed or ignored, never silently mixed into the new build's view.
  • A partially-populated target/deps/ from a process that was killed mid-materialization in a previous run (no clean shutdown) — must be detected via the missing completion marker and re-materialized from scratch, not treated as already-installed.

18.9 Failure Analysis

Symptom: a build occasionally fails with "file not found" for a dependency that the lockfile clearly lists. Root cause candidates: a build process starting before install's atomic rename completes (a scheduling bug upstream in pm-build, Phase 7's responsibility to sequence correctly); or a GC race (§17) deleting a store object between materialization's read and its own linking, despite I5's pinning — which would indicate a pinning bug, not an install bug. Debug method: telemetry span correlation between install.complete and build.start timestamps per package; a build start strictly before its install-complete timestamp is the signal. Containment: the atomic-rename discipline (I2) bounds the blast radius to "build waits or fails cleanly," never "build reads corrupt/partial data."

18.10 Operational Notes

pkg install --link-mode (debug flag) forces copy-mode even when hardlinks are available, letting operators reproduce and diagnose cross-filesystem-class bugs (§18.6) on a same-filesystem development machine.

19. Phase 7 — Build Orchestration

19.1 Objectives

Implement pm-build: the BuildUnit DAG scheduler (§11.5) and the Linux namespace + seccomp-bpf sandbox (ADR-12) that untrusted build scripts execute inside, per P6's "untrusted until proven otherwise" principle.

19.2 Detailed Implementation Steps

  • Modules/files touched: pm-build/src/{scheduler,sandbox,seccomp_policy,env,capture}.rs.
  • Algorithm named — DAG scheduling: topologically order BuildUnits (§11.5) from the lock graph (§8.6), scheduling a package's build only after every dependency's materialization (§18, not merely its build) has completed; bound parallelism to §4's concurrency target (1× logical CPU count for build).
  • Algorithm named — sandbox construction (ADR-12): a new mount namespace exposing only the package's declared source tree (read-only) and its declared output directory (read-write); a new network namespace with no interfaces by default (P6, ADR-26) unless the manifest explicitly declares a network-access need; a seccomp-bpf filter denying syscalls outside a documented allow-list (file I/O within the two mounted paths, process spawn for the build tool itself, no raw socket/ptrace/mount syscalls).
  • Data structures: BuildUnit (§11.5), consumed (moved) once scheduled, never mutated concurrently (I2 extends to in-flight BuildUnits).
  • Algorithm named — deterministic environment: fixed TZ=UTC, fixed LC_ALL=C, SOURCE_DATE_EPOCH pinned to the lockfile's recorded timestamp — reproducibility extends past resolution (I1/I3) into the build itself (MM6).
  • Algorithm named — output capture: on build-script success, hash and write the declared output directory's contents into pm-store (Phase 5) as new content-addressed objects.
  • Sync primitives: OS threads / bounded thread pool (ADR-13) for the scheduler's parallel BuildUnit dispatch; each sandboxed child process is isolated by namespace, requiring no in-process locking between concurrent builds.
  • Persistence: build outputs land in pm-store (Phase 5) identically to fetched artifacts — no build-specific persistence format.
  • Observability hooks: sandbox.escape_attempt (I10, T5); a per-build span recording wall-clock, exit code, and denied-syscall count.
  • Test harness: fixture build scripts that deliberately attempt ptrace, unauthorized mount, and outbound network access, asserting the sandbox denies each within one scheduling tick.

19.3 Deliverable

pkg build schedules and executes a full dependency DAG's build scripts inside the sandbox, producing content-addressed build outputs, and demonstrably kills a build script that attempts a sandbox-escaping syscall.

19.4 Acceptance Criteria

A malicious fixture build script attempting ptrace or an unauthorized mount syscall is killed by the seccomp filter within one scheduling tick, logged as sandbox.escape_attempt (I10, §7). A malicious fixture build script attempting outbound network access with no declared network permission fails to connect (namespace has no route). Two consecutive builds of the same lockfile on the same host produce byte-identical output-directory hashes (build-level reproducibility, conformance/fixtures/phase7/deterministic-rebuild/). Sandbox setup overhead per BuildUnit stays ≤ 5 ms (§30/M13).

19.5 Conformance Fixtures

  • conformance/fixtures/phase7/sandbox-escape-ptrace/ — a build script attempting ptrace on the host process; expected: seccomp kill, sandbox.escape_attempt telemetry fired (mirrors the ua-parser-js 2021 and event-stream 2018 attack pattern of a malicious install/build step reaching for host access).
  • conformance/fixtures/phase7/network-exfil-attempt/ — a build script attempting an outbound HTTP request with no declared network permission; expected: connection failure, no data reaches any host endpoint.
  • conformance/fixtures/phase7/deterministic-rebuild/ — the same lockfile built twice; expected: identical output-directory hash.
  • conformance/fixtures/phase7/dag-ordering/ — a five-package diamond dependency DAG; expected: build order respects every edge, no package builds before its dependencies are materialized.
  • conformance/fixtures/phase7/declared-network-access/ — a build script declaring network need in its manifest, attempting an outbound request; expected: connection succeeds, logged distinctly (network.access.granted) from the default-denied case.

19.6 Pitfalls

  • Granting the build sandbox write access to the source tree "just in case a build script needs to touch a generated file" — manifestation: reopens exactly the persistence vector T5 exists to close; root cause: convenience overriding the least-privilege default; debug method: audit sandbox mount flags for any read-write source mount; signal: a mount-namespace inspection shows the source tree as writable; recovery: outputs belong only in the declared output directory, never the source tree.
  • Forgetting SOURCE_DATE_EPOCH and other timestamp-sensitive environment pinning — manifestation: build-level reproducibility silently breaks even when every input hash matches; root cause: many build tools embed current wall-clock time into output artifacts; debug method: deterministic-rebuild fixture; signal: two builds of the same lockfile produce different output hashes; recovery: pin TZ, LC_ALL, SOURCE_DATE_EPOCH for every sandboxed process.
  • Scheduling a build before its dependency's materialization (§18) completes, only checking that the dependency's build completed — manifestation: a race between Phase 6's atomic rename and Phase 7's scheduler start; root cause: watching the wrong completion signal; debug method: dag-ordering fixture with narrowed timing; signal: a build starts reading a dependency directory before its install-complete marker exists; recovery: the scheduler must wait on the install-complete signal (§18), not the build-complete signal, for each edge.
  • Reusing a namespace template across packages with different declared network needs — manifestation: a package that should be network-denied inherits a network-enabled namespace from a batching optimization (§19.7); root cause: over-aggressive namespace-setup batching; debug method: network-exfil-attempt run immediately after a declared-network-access build in the same batch; signal: the denied-by-default build unexpectedly succeeds at a connection; recovery: namespace batching may share setup cost but never share the network-namespace grant itself.

19.7 Performance Concerns

Sandbox setup (namespace creation, seccomp filter install) has fixed per-build-unit overhead; at the §4 concurrency target (1× CPU count), this overhead must stay small relative to actual build-script execution time or it dominates wall clock on a graph of many small packages — batch namespace setup costs where the OS allows (e.g., reusing a namespace template) without weakening isolation between distinct packages' builds (M13's ≤ 5 ms target). Output-capture hashing (BLAKE3, ADR-07) runs once per build unit on success and should overlap with the next unit's scheduling rather than serializing the pipeline.

19.8 Edge Cases

  • A package with no build script at all (pure data/manifest-only package) — skips sandboxing entirely, materializes its source as its "build output" directly.
  • A build script that legitimately needs network access (e.g., downloading a codegen tool) — must declare it in the manifest, and the sandbox grants network only to that specific BuildUnit, logged distinctly from the default-denied case.
  • A build DAG with a cycle (should be impossible given I1/I3's acyclic lock-graph guarantee, but must be defensively detected) — scheduler aborts with a named internal-invariant-violation error rather than deadlocking.
  • A build script that forks a long-lived background process before exiting — the sandbox's namespace teardown must reap or kill it, or a "successful" build leaks a process past the sandbox's intended lifetime.

19.9 Failure Analysis

Symptom: a build hangs indefinitely with no scheduler progress. Root cause candidates: a cyclic dependency that escaped resolver-time detection (an I3-adjacent resolver bug, not a Phase 7 bug); or a build script blocked on a syscall the seccomp filter silently stalls rather than denies outright (a filter-configuration bug — deny should return EPERM promptly, not block). Debug method: dump the scheduler's current DAG state (which units are pending/running/done) — a DAG with a cycle is the first thing to rule out; if acyclic, strace-equivalent (constrained to the sandboxed process's own logs) for the specific blocked syscall. Blast radius: a hung build occupies one worker slot in the bounded thread pool (ADR-13); it does not corrupt store or lockfile state (output capture only happens on success).

19.10 Operational Notes

pkg build --sandbox-report prints every syscall the seccomp filter denied during a build run, even for successful builds, giving operators visibility into what a build script attempted versus what it needed — an operational precursor to tightening the allow-list further per-package if desired.

20. Phase 8 — Workspaces + Features/Optional Deps

20.1 Objectives

Implement pm-workspace: multi-package workspace loading (§8.2's workspace.members glob), feature-flag unification across dependents (P11, ADR-11), and optional-dependency activation gating.

20.2 Detailed Implementation Steps

  • Modules/files touched: pm-workspace/src/{load,feature_graph,unify,optional_gate}.rs.
  • Algorithm named — workspace loading: expand workspace.members globs (ADR-27) against the root manifest's directory, load each member's Manifest, and produce a single combined manifest graph feeding one resolver invocation (a workspace resolves as one unit — one lockfile, not one per member, per P5).
  • Algorithm named — feature unification (P11, Cargo's model, §5): when two dependents request different feature subsets of the same (PackageId, Version), union the requested feature sets into one build of that package; verify uniqueness per I9 (post-resolution check that no (PackageId, Version) pair appears twice with divergent feature sets).
  • Algorithm named — optional-dependency activation: an optional dependency (DepSpec.optional = true, §11.2) only enters the resolved graph if some enabled feature (transitively) requires it — implemented as an edge in the feature graph from a feature name to dep:<name> (Cargo's dep: syntax precedent), keeping optional-dep activation and feature activation as one unified graph problem, not two separate passes (Gamblin et al.'s Spack lesson on variant/feature graphs, §5).
  • Data structures: a feature graph (adjacency-list, ADR-21 discipline) layered over the dependency graph (§8.3), computed incrementally during the resolver's normal decision-making (§20.7), not as a separate post-pass.
  • Sync primitives: none — feature unification runs within the same single-threaded resolver invocation as version resolution (ADR-13).
  • Persistence: none new — the unified feature set is recorded implicitly via which dep:<name> edges are active in the final lock graph (§8.6).
  • Observability hooks: resolve.duplicate_version.detected (I9, §7).
  • Test harness: a three-member workspace fixture with overlapping dependencies and divergent feature requests on a shared dependency, verifying exactly one unified lock entry.

20.3 Deliverable

A workspace with three member packages, overlapping dependency requirements, and divergent feature requests on a shared dependency resolves to one lockfile with correctly unified features and correctly gated optional dependencies.

20.4 Acceptance Criteria

conformance/fixtures/phase8/three-member-workspace/ resolves with exactly one entry for the shared dependency, its feature set equal to the union of all three members' requests. An optional dependency with no feature path enabling it does not appear in the resolved lock graph at all (verified absent, not merely unused). I9's uniqueness check fires (test-only negative fixture) when a deliberately broken unification path produces two divergent-feature entries for the same version.

20.5 Conformance Fixtures

  • conformance/fixtures/phase8/three-member-workspace/ — three members, shared dependency, divergent feature requests; expected: one unified entry.
  • conformance/fixtures/phase8/optional-dep-gated-off/ — an optional dependency behind an unenabled feature; expected: absent from lock graph.
  • conformance/fixtures/phase8/optional-dep-gated-on/ — same dependency, feature enabled by one workspace member; expected: present, and visible (per P11's documented tradeoff) to every member's build.
  • conformance/fixtures/phase8/malformed-workspace-glob/ — a workspace.members glob matching zero directories; expected: named error, not a silently empty workspace.
  • conformance/fixtures/phase8/local-path-member-dependency/ — a workspace member depending on another member by path (§20.8); expected: resolves without any registry round-trip.

20.6 Pitfalls

  • Resolving each workspace member independently (one resolve per member, one lockfile per member) — manifestation: duplicate builds of the same version reappear; root cause: breaking P5/P11's single-unit model; debug method: inspect the lock graph for two entries of the same (PackageId, Version); signal: I9 fires; recovery: one resolver invocation over the combined manifest graph, always.
  • Treating optional-dependency gating as a post-resolution filter rather than a graph edge — manifestation: a wrong lock graph despite looking plausible; root cause: a naive "resolve everything, then drop unused optional deps" approach can pull in transitive dependencies of an optional dep that then contribute spurious version constraints to the resolve itself; debug method: compare the lock graph produced by early-gating vs. late-filtering on the same fixture; signal: the two differ; recovery: gate optional deps in from the start as feature-graph edges (§20.2).
  • Forgetting that a feature enabled by one workspace member is visible to every member sharing that dependency version — manifestation: a member relying on a feature being disabled silently breaks; root cause: P11's explicit, documented tradeoff, not a bug; debug method: pkg workspace explain-features (§20.10); signal: a test only fails in full-workspace builds (FM-9); recovery: document the tradeoff, do not "fix" it by adding per-member isolation (ADR-11 already rejected that).
  • Expanding workspace.members globs lazily/on-demand instead of eagerly at load time — manifestation: a member added mid-resolve is missed or double-counted; root cause: glob expansion timing inconsistent with the "resolve as one unit" model; debug method: malformed-workspace-glob combined with a glob that matches a directory created after load started; signal: nondeterministic member-set membership across runs; recovery: expand globs once, eagerly, before any resolver invocation begins.

20.7 Performance Concerns

Feature unification adds a second fixed-point computation pass on top of PubGrub's version resolution (§14) — for large workspaces this must not become its own O(n²) hazard; represent the feature graph with the same sparse adjacency-list discipline as the dependency graph (ADR-21) and compute unification incrementally as features are discovered during the resolver's normal decision-making, not as a separate full pass after resolution completes.

20.8 Edge Cases

  • A workspace member depending on another workspace member by path (not by registry version) — must resolve without a registry round-trip at all (a SourceKind::Local PackageId, §11.1).
  • Two workspace members requesting mutually exclusive features of the same dependency (e.g., one wants no_std, one wants std) — per P11's tradeoff this either unifies incorrectly or must be surfaced as an explicit resolution conflict (§14's explanation renderer); this blueprint's design principle (P11) accepts unification and documents the hazard rather than silently building both.
  • A workspace member with zero declared dependencies but non-empty features (a features-only crate) — must still participate in the combined manifest graph's feature-unification pass, even though it contributes no version constraints.

20.9 Failure Analysis

Symptom: a workspace member's tests fail only when built as part of the full workspace, never when built standalone. Root cause: P11's feature-leakage tradeoff — another member enabled a feature on the shared dependency that changes its behavior. Debug method: pkg workspace explain-features <dep> (§20.10) lists every member requesting each feature and the resulting unified set — the leaking feature and its requester are immediately visible, distinguishing "expected P11 tradeoff" from "a genuine unification bug." Blast radius: confined to members sharing the specific unified dependency; unrelated workspace members are unaffected.

20.10 Operational Notes

pkg workspace explain-features <dep> prints, per dependency, which workspace members requested which features and the final unified set — the direct operational mitigation for the P11 tradeoff documented in §20.9.

21. Phase 9 — Signing, Provenance, Audit

21.1 Objectives

Implement pm-sign: Sigstore-compatible keyless signature verification (ADR-09) gating every artifact write into pm-store (I6), in-toto-style provenance attestation (ADR-10), and CVE/audit-feed integration (ADR-25).

21.2 Detailed Implementation Steps

  • Modules/files touched: pm-sign/src/{verify,attest,audit_feed}.rs.
  • Algorithm named — signature verification (TUF, Samuel et al. CCS 2010, §5): a root-of-trust key set (rotatable, per TUF's role-key hierarchy) verifies a package's Sigstore certificate chain (Fulcio-issued, tied to an OIDC identity) and its Rekor transparency-log inclusion proof before the artifact reaches Phase 5's write path — I6's exact gate, inserted between Phase 4's fetch and Phase 5's store-write.
  • Algorithm named — provenance attestation (in-toto, Torres-Arias et al. USENIX Security 2019, §5): each build step (Phase 7) emits a signed attestation naming its inputs (by content hash), its command, and its outputs (by content hash), chained so a consumer can verify the full farm-to-table path from source fetch to final build artifact.
  • Algorithm named — CVE/audit integration (ADR-25): ingest an OSV-format vulnerability feed, cross-reference every locked package's (name, version) against known advisories, and surface matches via pkg audit.
  • Data structures: a verified-artifact cache entry keyed by content hash (§21.7), distinct from pm-store's own object metadata.
  • Sync primitives: none — verification is a synchronous gate per artifact fetch (P7: verification happens between fetch and store-write, never after).
  • Persistence: an append-only verification-log audit trail (I6's telemetry row, §7), independent of the store itself so a verification decision remains auditable even after GC reclaims the underlying object.
  • Observability hooks: sign.verify.failure (I6, T8); audit.feed_stale (T9, FM-10).
  • Test harness: fixture artifacts with a stripped signature, a mismatched Rekor inclusion proof, and a static OSV feed containing one known-CVE version.

21.3 Deliverable

pkg install refuses an artifact with an invalid or missing signature; pkg build emits a verifiable in-toto attestation chain per build; pkg audit reports every OSV-matched CVE for the current lockfile with severity and affected version range.

21.4 Acceptance Criteria

A fixture artifact with a stripped signature is rejected before it reaches pm-store (conformance/fixtures/phase9/stripped-signature/), closing T8. A fixture artifact with a valid signature but a Rekor inclusion proof that does not match is rejected (conformance/fixtures/phase9/rekor-mismatch/). pkg audit against a fixture lockfile containing a known-CVE version (from a static OSV fixture feed) reports it with correct severity and remediation version range.

21.5 Conformance Fixtures

  • conformance/fixtures/phase9/stripped-signature/ — an artifact with its Sigstore signature removed; expected: rejected before store-write, mirroring the trust-stripping step of a supply-chain compromise (T8).
  • conformance/fixtures/phase9/rekor-mismatch/ — valid signature, mismatched transparency-log proof; expected: rejected.
  • conformance/fixtures/phase9/attestation-chain-verify/ — a full build's in-toto attestation chain; expected: verifies end to end from source fetch to output artifact.
  • conformance/fixtures/phase9/osv-known-cve/ — a lockfile entry matching a static OSV fixture advisory; expected: pkg audit reports it with the fixture's exact severity field.
  • conformance/fixtures/phase9/legacy-unsigned-transition-mode/ — a pre-signing-era artifact under transition-mode policy (§21.8); expected: accepted with a loud, logged warning, never silently.

21.6 Pitfalls

  • Verifying the signature but not the transparency-log inclusion proof — manifestation: a technically-valid-looking signature with no public accountability; root cause: a compromised or coerced Fulcio-adjacent step could otherwise mint one; debug method: rekor-mismatch fixture; signal: a signature verifies but the inclusion proof does not; recovery: Sigstore's entire trust model (§5) depends on the Rekor log, not the signature alone — always check both.
  • Treating "no signature present" and "invalid signature" as the same rejection path with the same message — manifestation: an operator cannot distinguish policy state from an active attack; root cause: sharing one error path for two distinct fault classes; debug method: inspect the exact FetchError/audit-log variant on rejection; signal: both cases produce identical log text; recovery: keep them as distinct entries — "this ecosystem doesn't sign yet" (policy) vs. "this specific artifact's signature is broken" (active-attack signal).
  • Running the CVE audit as a one-time check at install time only, never re-checked — manifestation: a CVE disclosed after install goes unreported indefinitely; root cause: treating audit as an install-time gate rather than a standing, re-runnable check; debug method: osv-known-cve re-run against an already-installed lockfile with no fresh install; signal: pkg audit requires a fresh install to see the advisory; recovery: pkg audit must be re-runnable against an already-installed lockfile at any time.
  • Accepting a legacy unsigned artifact silently under transition-mode policy — manifestation: an operator has no visibility into how many unsigned artifacts remain in their dependency tree; root cause: "accept but don't warn" implementation of the transition-mode policy (§21.8); debug method: legacy-unsigned-transition-mode fixture; signal: no log entry despite an unsigned artifact passing; recovery: transition mode must log loudly on every unsigned acceptance, never silently.

21.7 Performance Concerns

Signature and inclusion-proof verification adds cryptographic-operation latency per artifact fetch — cache verified-artifact status alongside the content hash in pm-store's metadata (§8.8) so a warm-cache install (§18) never re-verifies an artifact whose bytes, and therefore whose already-verified signature, have not changed (I4's append-only guarantee makes this safe: the hash uniquely identifies bytes that were verified exactly once).

21.8 Edge Cases

  • A package published before the registry required signing (a legacy unsigned artifact) — policy-configurable: reject outright (strict mode) or accept with a loud warning (transition mode), never accept silently.
  • An OSV advisory covering a version range that includes the locked version but the advisory itself is later retracted — pkg audit must re-fetch the feed rather than caching a stale advisory indefinitely.
  • A build's in-toto attestation chain with a gap (a build step that ran before Phase 9 shipped, with no attestation) — must be reported as "unattested," not silently treated as verified.
  • A Rekor inclusion proof that is valid but references a certificate that has since been revoked — verification must check revocation status independently of inclusion-proof validity, or a revoked-but-once-logged identity remains trusted indefinitely.

21.9 Failure Analysis

Symptom: pkg install starts rejecting previously-working packages after a routine registry-mirror change. Root cause candidates: the new mirror serving artifacts signed under a different (also valid, but newly-added) Sigstore identity not yet in the local trust configuration; or an actual T3/T6-class compromise. Debug method: pkg sign verify --explain <artifact> reports the exact certificate chain and identity presented versus the configured trust policy — a legitimate new-identity rollout shows a recognizable, expected identity; a compromise shows an unexpected one, escalated per the runbook in docs/runbooks/. Blast radius: verification failures are fail-closed by design (I6) — worst case is a false-positive rejection blocking a legitimate install, never a false-negative acceptance of a compromised artifact.

21.10 Operational Notes

pkg audit --fix-suggest (report-only, never auto-applies per the Non-Goals in §1.4) prints the minimal version bump satisfying both the existing VersionReq and the OSV-clear range, leaving the actual manifest edit to the operator.

22.1 Objectives

Implement pm-mirror: mirror registry configuration beyond the failover queue from Phase 4, and the offline/vendoring bundle format (§8's ADR-23) enabling fully air-gapped builds.

22.2 Detailed Implementation Steps

  • Modules/files touched: pm-mirror/src/{config,export,import,offline}.rs.
  • Data structures: an ordered list of registry base URLs with per-mirror trust scoping (a mirror marked read-only-cache vs authoritative, affecting whether pkg audit's OSV feed is also fetched from it).
  • Algorithm named — pkg vendor export: given a lockfile, bundle every referenced pm-store object plus the lockfile plus the exact index_snapshot token (§8.6) into a single tarball (ADR-23) — small, since it contains only what is actually locked, not a full index mirror.
  • Algorithm named — pkg vendor import: given a vendor bundle, populate a target host's pm-store directly (bypassing pm-registry/pm-mirror entirely) and verify every imported object's hash before making it visible (I4/I6 apply identically to vendor-imported objects — vendoring is not a trust bypass).
  • Algorithm named — offline mode: pkg build --offline resolves and builds using only already-vendored/cached store objects and the local index cache (§16.2), failing loudly (not silently falling back to network) if a required object or index entry is missing.
  • Sync primitives: none beyond pm-store's own write-path discipline (I4) — import is a sequence of ordinary hash-verified store writes.
  • Persistence: the vendor bundle tarball itself, an offline-transportable artifact independent of any live registry connection.
  • Observability hooks: vendor.import.hash_mismatch (I12/T10); a network-call counter asserting zero calls during an offline build.
  • Test harness: an export-on-host-A, import-on-host-B roundtrip fixture verifying byte-identical materialized build trees.

22.3 Deliverable

A lockfile generated on a networked host exports to a vendor bundle that a fully air-gapped host imports and builds from, byte-identically to the networked host's own build.

22.4 Acceptance Criteria

pkg vendor export produces a bundle whose imported result on a second host reproduces the exact same materialized build tree (§18) as the original host, verified by content-hash comparison. pkg build --offline on a host missing one required object fails with a named "missing vendored object" error rather than attempting any network call. Vendor import verifies every object's hash before making it store-visible — a deliberately corrupted bundle fixture is rejected object-by-object, not accepted wholesale.

22.5 Conformance Fixtures

  • conformance/fixtures/phase10/export-import-roundtrip/ — export on host A, import on host B; expected: identical materialized build tree hash.
  • conformance/fixtures/phase10/offline-missing-object/ — offline build missing one vendored object; expected: named failure, zero network calls attempted (verified via a network-call-counter assertion).
  • conformance/fixtures/phase10/corrupted-bundle-partial-reject/ — a vendor bundle with one tampered object among many valid ones; expected: only the tampered object rejected, siblings imported successfully.
  • conformance/fixtures/phase10/mirror-trust-scoping/ — a read-only-cache mirror vs an authoritative mirror; expected: OSV feed fetched only from the authoritative one.
  • conformance/fixtures/phase10/dedupe-across-bundles/ — two vendor bundles sharing a common object; expected: import dedupes against the existing store, no double-write (§22.8).

22.6 Pitfalls

  • Treating vendor import as an implicitly trusted path because "it's local, not network" — manifestation: a malicious bundle bypasses signature verification; root cause: conflating transport medium with trust level; debug method: attempt import of a bundle with a stripped signature; signal: import succeeds despite invalid signature; recovery: I6's gate must still apply — a vendor bundle is just another artifact source, not a trust bypass, or it becomes a trivially exploitable supply-chain shortcut (drop a malicious bundle on a USB stick).
  • pkg build --offline silently falling back to network on a cache miss — manifestation: an air-gap guarantee is silently violated; root cause: treating a cache miss as "degrade to network" instead of "fail loudly"; debug method: offline-missing-object fixture with network access available but expected to go unused; signal: a network call is observed; recovery: fail loudly, matching P10's "degrade to cache" principle inverted (here, the absence of network is the intended state, not a degraded fallback).
  • Exporting a vendor bundle without the index_snapshot token — manifestation: I1's re-resolve verification breaks on the import side; root cause: omitting §8.6's token from the export; debug method: attempt pkg lock verify on an imported lockfile lacking the token; signal: verify cannot reproduce the original resolve; recovery: always include the token in the export bundle.
  • Re-importing an already-present object without dedupe-checking — manifestation: wasted disk and I/O on repeated imports of overlapping bundles; root cause: import path always writes rather than checking existence first; debug method: dedupe-across-bundles fixture; signal: object write count exceeds unique-object count; recovery: check store presence by hash before writing (P2 applies identically here).

22.7 Performance Concerns

Vendor bundle size is bounded by ADR-23's design (only locked objects, not a full index) — chained to the §34 capacity model's store-bytes estimate; a bundle export/import operation is dominated by object-copy I/O, not by any resolution or verification computation, so its throughput target inherits directly from §4's warm-install figure.

22.8 Edge Cases

  • A vendor bundle exported from a lockfile that itself later fails pkg lock verify on the original host (drifted since export) — import should still succeed (the bundle is a snapshot in time) but pkg lock verify on the imported host should independently re-check against the bundled index_snapshot, catching drift on either side.
  • Two vendor bundles for two different lockfiles that share some objects (common dependency) — import should dedupe against the existing store, not double-write (P2 applies identically here).
  • A vendor bundle transferred over a lossy medium (partial write to a USB drive) — import must detect a truncated tarball before attempting any object-level verification, surfacing a distinct "corrupt bundle container" error rather than a confusing per-object failure cascade.

22.9 Failure Analysis

Symptom: an air-gapped build succeeds on one host and fails on a nominally identical second host. Root cause candidates: the two hosts' vendor bundles were exported from lockfiles at different points in time (a process hygiene issue, not a system bug); or a partial/corrupted bundle transfer (network or storage-media corruption in transit to the air-gapped environment). Debug method: pkg vendor verify <bundle> independently before import — hash-checks every object in the bundle file itself, isolating "the bundle is bad" from "the import process is bad."

22.10 Operational Notes

pkg vendor verify <bundle> (§22.9) is the documented pre-flight step in docs/runbooks/ before any air-gapped transfer, avoiding a failed import discovered only after physically carrying media across an air gap.

A single green CI run executing every conformance fixture from every phase, a converged fuzz corpus with zero outstanding crashes, and a recorded performance report showing every §4/§30 target met on the 500-package fixture.

23.4 Acceptance Criteria

100% of conformance/fixtures/phase*/ fixtures pass in one consolidated CI job. Fuzz corpus runs 4 hours per target with zero new crashes on the final run (fuzz.yml scheduled job). Recorded p95 resolve latency on the 500-package fixture ≤ 450 ms (§4); recorded warm-install throughput ≥ 800 MB/s (§4); recorded GC sweep on a 20 GiB store completes within the RTO bound (§4, ≤ 5 s for index/lockfile-corruption recovery specifically, GC sweep itself tracked separately in docs/performance/).

23.5 Conformance Fixtures

conformance/fixtures/phase11/full-suite-manifest/ — a manifest listing every fixture directory from every phase, expected: the consolidated runner discovers and executes all of them with none skipped. conformance/fixtures/phase11/stress-5000-packages/ — the larger stress fixture, expected: completes (does not need to meet the 500-package p95 exactly, but must not exceed the practical bound discussed in §31) and reports actual numbers. conformance/fixtures/phase11/cross-phase-regression-t5/ — a Phase 10 vendoring path combined with a Phase 9-class malicious build script, expected: still killed by the seccomp sandbox (T5 stays closed across the vendoring boundary).

23.6 Pitfalls

Running each phase's fixtures only within that phase's own CI job, never consolidated — regressions where a later phase's change breaks an earlier phase's invariant (e.g., Phase 10's vendor import accidentally bypassing Phase 9's signature gate, §22.6) go undetected until a human notices; the consolidated suite in this phase exists specifically to close that gap. Declaring performance targets met based on a single run — p95/p99 latency claims (§4) require enough samples (a documented minimum sample count in docs/performance/) to be statistically meaningful, not a single lucky run. Treating fuzz-corpus convergence as "ran once with no crash" rather than a sustained multi-hour run — many parser bugs (especially in pm-manifest's TOML edge cases and pm-registry's NDJSON parsing) only surface after the fuzzer has explored deep into the input-mutation space.

23.7 Performance Concerns

The 5000-package stress fixture is explicitly not held to the same p95 target as the 500-package fixture (§4 is scoped to 500) — its purpose is to confirm the resolver degrades gracefully (roughly the expected super-linear-but-bounded curve per §31's NP-completeness discussion) rather than catastrophically, and to catch any accidental quadratic-or-worse regression before it reaches production scale.

23.8 Edge Cases

A fixture that passed in isolation but fails only when run as part of the full consolidated suite (shared global state leaking between fixture runs, e.g. a shared $PM_HOME not properly isolated per test) — the consolidated runner must sandbox each fixture's $PM_HOME/temp directories independently, or cross-fixture contamination produces flaky, hard-to-reproduce CI failures exactly analogous to the nondeterminism bugs this whole blueprint works to eliminate elsewhere (I3).

23.9 Failure Analysis

Symptom: the consolidated suite is flaky (different fixtures fail on different runs, no clear pattern). Root cause candidates: fixture-isolation leakage (§23.8); or genuine nondeterminism escaping earlier phases' own conformance gates because a phase's fixture set was incomplete. Debug method: run the consolidated suite with fixture execution order randomized across CI runs (not fixed) — if failures correlate with specific orderings, it is an isolation bug; if failures are order-independent but still intermittent, escalate as a genuine nondeterminism regression against the specific phase's I1/I3-class invariant.

23.10 Operational Notes

docs/performance/ accumulates one dated report per Phase-11 run, forming a historical trend line operators can consult before and after any resolver/store optimization change lands, directly supporting the Performance Engineering methodology in §30.

26. Operational Readiness

Metrics. Every counter named across §7 (invariants), §24 (threats), and §25 (failure modes) is exported via tracing's metrics layer (ADR-19) under the <crate>.<event> namespace fixed in Phase 0 (§12.10) — resolve.propagation.no_progress, gc.roots.count, sandbox.escape_attempt, sign.verify.failure, audit.feed_stale, and the rest are first-class dashboard series, not log-grep afterthoughts.

Tracing. Every top-level pkg subcommand opens one root span; each phase's crate opens a child span (resolve, fetch, install, build, sign) so a single slow invocation is attributable to a specific stage without cross-referencing separate log streams — P13 bounds span content to names/versions/hashes/timings, never source bytes or environment values.

Structured logging. JSON-formatted, one event per line, correlated by a per-invocation trace ID; pkg build --sandbox-report (§19.10) and pkg cache gc --dry-run --explain (§17.9) are the two "verbose explain" modes that operators reach for first.

Dashboards. Three: (1) resolver health (p50/p95/p99 latency vs M1–M3, incompatibility-set growth trend); (2) store health (size vs the §4 watermarks, GC sweep duration vs M9); (3) supply-chain health (sign.verify.failure rate, audit.feed_stale duration, sandbox.escape_attempt count).

Alerting philosophy. Page immediately on anything that indicates active compromise or unrecoverable hang: a resolver hang (FM-1), a sandbox-escape alert (FM-6/T5), a signature-verification-gate bypass (FM-7). Next-business-day ticket for hygiene-class signals: a stale-audit-feed alert (T9/FM-10), a GC root-set creeping upward (FM-4). Never page on a single flaky sample — alert thresholds require sustained breach across the minimum sample count documented in §23.6.

SLOs. Resolve p95 ≤ 450 ms (M2) measured over a rolling 24 h window; warm-install throughput ≥ 800 MB/s (M6) measured per CI runner class (bare-metal vs virtualized FD/IO characteristics differ enough to warrant separate SLO tracks).

Incident response. docs/runbooks/ holds one procedure per FM-class (§25) plus: GC watermark tuning, mirror rotation/failover drill, signature trust-root rotation, air-gapped vendor-transfer pre-flight (§22.10), sandbox allow-list tightening procedure. Every incident closes with a postmortem appended to docs/failure-analysis/, cross-referenced to the FM-class it matched (or a new FM-class if none matched, triggering a blueprint amendment per §1.1).

Backup/restore. The lockfile and manifest are the only state that must survive a host loss (P5) — the CAS store is fully regenerable from the registry/mirror plus the lockfile's checksums (I4/I6), so "backup" for $PM_HOME/store is optional performance insurance, never a correctness requirement; $PM_HOME/index-cache/ is pure cache, never backed up.

Deployment topology. A single static binary per host (§1.5); CI runners share $PM_HOME/store via a tarball restore step keyed on a cache-hit heuristic (last lockfile hash), not a live network-shared filesystem (avoiding the distributed-CAS scope explicitly deferred in §1.11/PhaseDeferred("§17")).

Canary/rolling-upgrade/rollback. A new pkg release is canaried against the Phase-11 consolidated suite (§23.2) on the release CI matrix before tagging; rollback is "install the prior pinned binary version" (SemVer-versioned per §27) — no server-side state to migrate back, since the registry contract is external and the lockfile format's one-major-version forward-read (I11) already bounds the blast radius of a bad release.

27. Compatibility & Versioning

Binary versioning. The pkg binary itself is SemVer-versioned (I7's grammar applied reflexively) — a major bump signals a breaking CLI-surface or lockfile-schema change; minor bumps are additive-only (new subcommands, new optional manifest fields); patch bumps are behavior-preserving fixes only.

Lockfile schema (wire/storage). I11's forward-read rule: exactly one prior major version's forward-read, enforced at load time — a pkg binary refuses to silently migrate a lockfile more than one major step behind, prompting an explicit pkg lock migrate. A minor lockfile-schema bump adds an optional field that older readers ignore; a major bump may restructure [[package]] layout and requires the explicit migration path.

Sparse-index wire format. Additive-only across minor versions (§8.7) — new optional NDJSON fields are ignored by older clients. A breaking wire-format change requires a new index base path, never an in-place incompatible change, protecting every client pinned to an old pkg version from silent breakage (this is the same "never mutate in place, only append a new addressable location" discipline P2 applies to the CAS, generalized to the wire protocol).

Manifest schema. Additions are backward-compatible by construction (new optional fields default to absent); removals are never permitted, only deprecation with a multi-release warning window (a removed field first becomes a no-op-with-warning for at least one minor release before disappearing from the schema entirely).

API stability. Every public crate signature (§11) is a stability contract from the moment its owning phase ships (§12.2's Phase-0 discipline extended forward) — a signature change after a phase's Phase-11 (§23) exit requires a documented docs/adr/ entry, not a silent edit.

Rolling-upgrade guarantees. A CI fleet running a mix of pkg binary versions (a rolling deploy in progress) must never produce two different lock graphs for the identical manifest+index-snapshot pair across versions within the same minor line (I1/I3 hold per-version, and the additive-only wire/schema rules bound cross-version drift to the documented deprecation window above).

Deprecation policy. Every deprecation ships with: the release it was flagged in, the release it will be removed in (minimum one minor version of warning), and the pkg diagnostic text an operator sees — tracked in CHANGELOG.md and cross-checked against BLUEPRINT_LOG.md per §29.

28. Testing & Verification Strategy

Property-based testing (proptest, ADR-17). Every algebraic invariant gets a property, not just an example: I7's total order (reflexive, antisymmetric, transitive over sampled Version pairs, §13.4); I1's re-resolve bijection (any generated manifest+index-snapshot pair re-resolves to byte-identical output, §15.4); I9's feature-unification uniqueness (no generated workspace fixture produces two divergent-feature entries for the same version, §20.4).

Fixture-driven conformance testing (§23). Every phase's N.5 fixtures feed the single consolidated runner (pm-conformance, §23.2) — malformed-input, replay, and regression cases are first-class, not an afterthought bolted onto the happy-path fixtures.

Fuzz testing (ADR-18). Every untrusted-input parser (pm-semver, pm-manifest, pm-lockfile, pm-registry's NDJSON path) runs under cargo-fuzz on a scheduled cadence (§23.2, 4 h/target); any new crash is minimized and checked in as a permanent regression fixture, never silently fixed without a fixture.

Differential testing. The worked examples in §8.9–§8.11 (a successful resolve, a conflict, a failure path) serve as golden-output regression tests — any change to the resolver, serializer, or explanation renderer that alters their output is a deliberate, reviewed decision, never an accidental drift.

Chaos / fault injection. Simulated crash-mid-write (§17.5's crash-mid-write fixture), simulated GC-vs-install races (§17.5's gc-race-detection), and simulated mirror failure (§16.5's primary-down) are fault-injection tests exercising the recovery paths in §25, not just the happy path.

Deterministic replay. Every bug fix lands with a regression fixture under conformance/fixtures/*/replay/ or conformance/replay/, per the debugging methodology closing §7 — a captured (manifest, index snapshot, observed output) triple is the minimum bar for accepting any fix.

Soak testing. The Phase-11 fuzz-corpus convergence run (§23.4, 4 h/target) and the 5000-package stress fixture (§23.7) are this system's soak-test surface — sustained load surfaces the memory-growth and incompatibility-set-growth classes of bug (§14.6) that a single short test run cannot.

Performance-regression gating. Every §30 M# target is checked in CI against the last Phase-11 recorded baseline in docs/performance/; a regression beyond a documented tolerance band fails the build, never merges silently.

CI gates on the full consolidated suite (§23.2) before any merge to the release branch.

29. Build & Release Engineering

Reproducible builds. release.yml triggers on a version tag, cross-compiles pm-cli for the supported target triples, and runs the full §23 consolidated suite against each target's binary (not just the build host's) — a release build must itself satisfy the same SOURCE_DATE_EPOCH/TZ/LC_ALL pinning discipline (§19.2) the system enforces on every package it builds (MM6's "determinism is a system property" applies reflexively to the release pipeline).

Artifact signing. Release binaries are signed via the same Sigstore keyless path pm-sign implements for packages (ADR-09) — the project dogfoods its own trust model rather than maintaining a separate, unaudited release-signing process.

SBOM. Every release ships a Software Bill of Materials enumerating every crate dependency (including transitive ones) by name, version, and license, generated from the release build's own lockfile (P5 applied to the tool's own supply chain).

Release channels. stable (SemVer-tagged, the default), and a rolling nightly channel built from main for early adopters — nightly never receives the same reproducibility guarantee as stable (its SOURCE_DATE_EPOCH floats with each build), a deliberate, documented tradeoff distinct from any package-level determinism guarantee.

CI/CD topology. ci.yml gates every PR; conformance.yml gates the consolidated suite (§23.2); fuzz.yml runs on a schedule, not per-PR (4 h/target is too slow for PR latency); release.yml is tag-triggered only, never automatic on every main merge.

Version stamping. Every release binary embeds its own SemVer version, build SOURCE_DATE_EPOCH, and the Git commit hash it was built from, surfaced via pkg --version — the same version string that appears in every telemetry span's metadata (P13-compliant: names/versions only, never secrets).

Provenance/attestation. A generated in-toto provenance attestation (ADR-10) accompanies the release build itself, chaining the release binary back to the exact source commit and CI job that produced it — the release pipeline is subject to the identical farm-to-table guarantee (§21.2) it enforces on third-party packages.

Dependency auditing. pkg audit (§21) runs against the tool's own Cargo.lock in CI on every release-candidate build, closing the reflexive gap where a package manager could ship with an unaudited vulnerable dependency of its own.

CHANGELOG.md is generated from conventional-commit-style PR titles, cross-checked against BLUEPRINT_LOG.md for any decision that shipped without a corresponding ADR update.

30. Performance Engineering

Methodology. Every target below is measured on the 500-package synthetic fixture (§14.4) under docs/performance/-tracked repeated runs (minimum sample count documented per §23.6), never a single-run claim. Regressions are gated in CI via a threshold check against the last Phase-11 recorded baseline.

Profiling. perf/flamegraph-based CPU profiling on the resolver's hot path (§14.7's unit-propagation cost) and heaptrack-equivalent allocation profiling on the 500-package fixture, run once per Phase-11 cycle and whenever M2/M4 regress beyond tolerance.

Allocation analysis. The resolver's Term/Incompatibility/Assignment types (§11.3) are audited for unnecessary heap churn per decision — an allocation inside the watched-literal inner loop (§14.2) is treated as a regression candidate even if it does not yet breach M2, since it signals a latent scaling problem.

Lock contention. The build orchestrator's bounded thread pool (ADR-13) is profiled for scheduler-queue contention at the §4 concurrency ceiling (1× CPU count) — contention here manifests as workers idling while BuildUnits remain schedulable, a distinct signal from genuine CPU saturation.

Cache/syscall analysis. The registry client's conditional-GET path (§16) is profiled for syscall count per request (target: no more than one connect + one read per warm 304); the CAS write path (§17.2) is profiled for fsync/rename syscall pairing to confirm no redundant fsyncs beyond what I4's crash-safety guarantee requires.

Tail-latency analysis. p99 (M3) is tracked separately from p50/p95 specifically because PubGrub's backtracking depth is graph-shape-dependent (§31) — a single pathological fixture can dominate the p99 tail without moving the p50/p95 median at all; the 5000-package stress fixture (§23.7) exists partly to surface this tail behavior before production does.

31. Scalability Analysis

What stays constant. Version/VersionReq comparison cost (O(1)-ish, bounded by identifier count, §13.7); the CAS write/read path per object (O(1) amortized, hash-addressed, §17); the sparse-index sharding fanout (bounded to at most 65,536 directory buckets regardless of package count, §8.7).

What grows, and the Big-O. Index-cache bytes: O(packages × avg versions) — linear (§34, step 11's extrapolation confirms this empirically). Resolver wall-clock: worst-case exponential in decision-graph depth (NP-complete, below), but empirically closer to O(packages × avg incompatibility-set size) on realistic sparse graphs (ADR-21's assumption) once conflict-driven learning (§14) prunes dead branches. Store bytes: O(artifacts × avg size ÷ dedupe ratio) — linear, per §34 step 4. GC sweep cost: O(store objects) for the mark phase, O(reclaimed objects) for the sweep phase — both linear, batched to bound wall-clock (§17.7).

Named bottlenecks, in order. (1) Resolver backtracking depth on adversarial/densely-interconnected graphs (worst-case exponential, below) — the dominant bottleneck once graphs exceed the low thousands. (2) Registry RTT on a cold cache (§16.7) — dominant only on first-ever resolve of a given dependency set, eliminated by I8's 304 warm path thereafter. (3) GC sweep I/O at the 20 GiB+ watermark (§17.7) — bounded by batching, not eliminated. (4) Build-sandbox setup overhead (§19.7) on graphs with many small packages — bounded to ≤ 5 ms/unit (M13), amortized across build-script execution time.

Complexity theory. Version solving is NP-complete in the general case (dependency graph satisfiability reduces from 3-SAT — the formal basis cited by Abate et al., SANER 2020, §5, and the reason Tucker et al.'s OPIUM, §5, frames package installability as an optimization problem in the first place). The practical bound this blueprint targets is not "solve every instance fast" but "solve realistic ecosystem-shaped instances fast, and degrade predictably, never catastrophically, on adversarial or pathological ones." PubGrub's conflict-driven learning (§14) keeps typical real-world graphs (sparse, mostly-tree-shaped with occasional diamonds, per ADR-21's assumption) tractable well past the 500-package target (§4) into the low thousands (§23.7's 5000-package stress fixture) before backtracking depth becomes the dominant cost.

Horizontal/vertical scaling. The resolver itself is deliberately not horizontally scaled (ADR-13 keeps it single-threaded for I3's determinism) — its scaling lever is vertical (single-core clock speed) or algorithmic (better heuristics, §14.2), never "add more resolver workers." The registry client and build orchestrator do scale horizontally within one host (bounded concurrency, §4's FD/CPU budgets) but never across hosts (§1.11's PhaseDeferred("§17") explicitly excludes a distributed CAS).

Sharding/partitioning. The CAS's objects/{hash[0:2]}/{hash[2:4]}/ sharding (§8.8) partitions filesystem metadata load across up to 65,536 buckets — the only sharding this system performs; there is no multi-node partitioning by design (single-host CAS, §1.11).

Coordination overhead. Zero cross-host coordination exists in this design (no distributed consensus, no shared mutable registry state client-side) — the only coordination is intra-host: the GC root-set snapshot (§17.6) and the build DAG scheduler's dependency-completion signals (§19.2), both bounded, short-lived critical sections.

Practical ceiling and levers beyond it. Pathological, densely-interconnected, deliberately adversarial graphs remain NP-hard in the worst case regardless of algorithm — the practical mitigation is a resolve-time budget (a configurable wall-clock ceiling past which pkg resolve fails loudly with a partial-progress explanation rather than hanging indefinitely, distinct from FM-1's bug-driven hang) rather than a claim of universal tractability. Beyond the single-host CAS ceiling, the only lever this blueprint's scope permits is the deferred distributed-CAS feature (PhaseDeferred("§17"), §37) — explicitly out of scope until a build-farm-scale cost problem justifies it.

32. Mental Models & First Principles

MM1 — PubGrub is CDCL where the clause database is derived lazily from the index. Insight: a SAT solver's clause database is fixed upfront; PubGrub's incompatibility set grows on demand as IndexEntry fetches reveal new dependency edges (§14.2). Prediction: resolve time is dominated by index-fetch latency for cold caches (§16.7), by pure search cost for warm ones. Bug class without it: engineers "optimize" the solver loop while the real bottleneck is network RTT, or vice versa. Resolves §14, §16.

MM2 — A lockfile is a proof certificate, not a cache. Insight: I1's re-resolve bijection means the lockfile proves a satisfying assignment exists, rather than merely remembering one (§15.2). Prediction: any lockfile that cannot be independently re-derived is untrustworthy regardless of how it was produced. Bug class without it: treating a hand-edited lockfile as valid because "it looks right," reopening exactly the drift class T6/FM-2 exist to catch. Resolves §15, I1.

MM3 — Content addressing turns cache invalidation into garbage collection. Insight: because identity is hash(bytes) (§8.8, P2), there is no "update this cache entry" operation, only "this object may become unreferenced" (§17). Prediction: the entire cache-coherence problem collapses into a liveness/reachability problem, solvable with standard mark-and-sweep. Bug class without it: name-addressed caches (e.g., name@version as the key) require explicit invalidation logic that inevitably misses an edge case. Resolves §17, I4/I5.

MM4 — Feature unification is a second, coupled constraint-satisfaction problem riding on the first. Insight: version resolution (§14) and feature-graph resolution (§20) are not independent passes — an activated feature can imply a new dependency edge, which can constrain version choice, which can activate a different feature (§20.6). Prediction: any implementation that resolves versions fully before touching features will produce a wrong answer on sufficiently interconnected graphs. Bug class without it: "resolved fine, but a required optional dependency is missing" bugs (§20.6). Resolves §20, P11.

MM5 — The build sandbox is the trust boundary, not the signature check. Insight: signature verification (§21) proves who published an artifact; it says nothing about what that artifact's build script does once trusted — a legitimately-signed package can still ship a malicious build script (the event-stream 2018 incident was a legitimate maintainer transferring ownership to an attacker, who then published a validly-signed-under-the-new-key malicious version). Prediction: signing alone cannot close T5; sandboxing (§19) is the independent, layered control. Bug class without it: conflating "signed" with "safe," under-investing in sandbox hardening because signing feels like it already solved supply-chain trust. Resolves §19, §21, T5/T8.

MM6 — Determinism is a system property, not a resolver property. Insight: I1/I3 are stated about the resolver, but P12 requires every layer — serialization (§15.6), the build environment (§19.2's SOURCE_DATE_EPOCH), even collection-type choices (§13.9) — to independently preserve it, or the system-level guarantee is false despite the resolver being individually correct. Prediction: reproducibility bugs cluster at layer boundaries (serialization, environment capture), not inside the resolver's own logic, once the resolver itself is well-tested. Bug class without it: chasing a "nondeterministic resolver" bug report that is actually a nondeterministic HashMap iteration three layers away. Resolves §13, §15, §19, P12.

MM7 — A registry is an adversarial input channel, not a database. Insight: every byte from pm-registry/pm-mirror (§16) must be treated with the same skepticism as untrusted user input, because it is untrusted input — the registry operator, a mirror, or an on-path attacker can all shape it (T1–T4, T6). Prediction: any code path that trusts index metadata without independent hash verification (P3) is a latent vulnerability regardless of how unlikely compromise seems today. Bug class without it: the left-pad/event-stream/ua-parser-js incidents, all downstream of some layer trusting the registry more than the threat model warranted. Resolves §16, §24, P3.

MM8 — GC correctness is a snapshot-consistency problem, not a deletion-algorithm problem. Insight: mark-and-sweep itself (§17.2) is simple; the hard part is taking the root-set snapshot atomically relative to concurrent pin/unpin/install operations (§17.6, I5). Prediction: GC bugs manifest as races (FM-5), not as wrong-object-deleted-in-isolation bugs. Bug class without it: engineers harden the sweep algorithm when the actual bug is in root-set computation timing. Resolves §17, I5, FM-5.

MM9 — Explanations are a compiler-error-message problem, not a logging problem. Insight: P4's conflict explanations (§8.4, §14.2) require the same discipline as a good compiler's type-error messages — naming the specific conflicting requirement chain, not just "resolution failed" (a generic exception message is the resolver equivalent of error: expected expression). Prediction: resolver UX quality is measurable by whether a user can fix a conflict from the message alone, without reading resolver source. Bug class without it: users file "resolver is broken" tickets that are actually correct rejections of a genuinely unsatisfiable manifest. Resolves §14, P4.

MM10 — A sparse index turns "download the world" into "download only what search touches." Insight: a monolithic index (one file listing every package) forces every client to fetch data proportional to the entire ecosystem's size; a sparse, per-package index (§8.7, ADR-06) makes fetch cost proportional only to the subgraph the resolver actually visits (§8.3's online-fetch model). Prediction: as an ecosystem's total package count grows without bound, a sparse-index client's cold-resolve cost stays bounded by the dependency graph's own size, never by the registry's total catalog size. Bug class without it: an index design that scales client-side cost with total-ecosystem size rather than with the requesting project's own dependency count — a design that works in a demo and falls over as the registry matures. Resolves §16, ADR-06, §34 step 1.

Cargo (§5 reference implementation) is this blueprint's closest sibling: PubGrub resolution, a flat registry cache, and — notably — unsandboxed build.rs execution by default, which this blueprint deliberately diverges from (ADR-12, P6) precisely because of the event-stream/ua-parser-js incident class. Nix eliminates version resolution altogether by pushing version selection into the Nix expression language itself and hash-pinning every input — the tradeoff explored fully in §36's alternative-architectures discussion. Spack's ASP-based concretizer is the right model once feature/variant combinatorics exceed what unification (§20, P11) can cleanly express, relevant background for why this blueprint bounds its own feature model to Cargo-style unification rather than Spack-style full constraint solving (ADR-02's rationale column). uv (§5 reference implementation) is the closest living proof that this blueprint's whole architecture is buildable in Rust at production quality — a sparse-index-first, PubGrub-based resolver with aggressive speculative prefetch (§16.7's uv-inspired pattern) — but it inherits Python's unsandboxed sdist-build convention rather than adopting this blueprint's namespace/seccomp jail (ADR-12), the one dimension where this blueprint deliberately goes further than its most modern sibling.

34. Back-of-Envelope Capacity Model

  1. Index cache size. 500 packages × avg 8 published versions/package × avg 600 bytes/NDJSON line (§8.7) = 500 × 8 × 600 = 2,400,000 bytes ≈ 2.3 MiB local index cache for the 500-package fixture (§4).
  2. Cold resolve wall-clock, no prefetch. 500 unique package requests × 60 ms p50 RTT (§4) ÷ 8 concurrent connections (§4 aggregate-throughput assumption) = (500 × 60) ÷ 8 = 3,750 ms naive-sequential-equivalent; with the lazy-fetch + bounded-concurrency design (§16.2) this is the ceiling, and M1's 120 ms p50 target requires warm-cache (§8.7 step 2, 304 responses) to dominate in practice.
  3. Warm resolve wall-clock. ≥ 95% of 500 requests return 304 with ~200-byte header-only response (M8) — 500 × 0.95 × 200 bytes ÷ (150 MB/s aggregate, §4) ≈ negligible transfer time; wall-clock collapses to pure CPU-bound resolver search cost, consistent with M1's 120 ms p50.
  4. Store bytes for the 500-package fixture. 500 packages × avg 45 KiB compressed artifact size × (1 − 0.12 dedupe ratio, a conservative estimate for a realistic ecosystem with shared transitive deps) = 500 × 45,000 × 0.88 ≈ 19.8 MiB store footprint before amplification.
  5. Storage amplification overhead. 19.8 MiB × 1.15× (M10 ceiling) ≈ 22.8 MiB worst-case store footprint on disk including refcount metadata (§8.8).
  6. Cold install network time. 19.8 MiB store payload ÷ 40 MB/s per-connection floor (M5) ≈ 0.5 s per connection; ÷ 150 MB/s aggregate (8 conns, §4) ≈ 0.13 s aggregate cold-fetch time for the whole fixture's artifacts.
  7. Warm install (link-mode) time. 19.8 MiB ÷ 800 MB/s (M6) ≈ 25 ms materialization time — three orders of magnitude faster than a copy-based install would achieve on typical disk bandwidth (§18.7).
  8. GC sweep cost at high watermark. 20 GiB store ÷ assume 500 MB/s sustained unlink+metadata-update throughput on a typical SSD ≈ 40 s naive full-sweep; bounded instead by M9's 5 s RTO target via incremental/batched sweep (§17.7) rather than a single blocking pass.
  9. Vendor bundle size, 500-package lockfile. Store bytes (step 5, ≈22.8 MiB) + lockfile (≈500 entries × ~150 bytes/entry ≈ 75 KiB, §8.6) + index snapshot token (negligible) ≈ 22.9 MiB total bundle (§22.2, ADR-23's "small, locked-only" design confirmed quantitatively).
  10. Fuzz corpus convergence budget. 4 target crates (§23.2) × 4-hour sustained run (§23.4) = 16 CPU-hours per full Phase-11 fuzz pass, run on a scheduled (not per-PR) cadence per fuzz.yml.
  11. 5000-package stress fixture, index cache size (linear extrapolation). 10× the 500-package figure (step 1) ≈ 23 MiB — confirms index-cache size scales linearly with package count, unlike resolve latency, which is expected to scale worse than linearly per §31's NP-completeness discussion.
  12. FD budget headroom. 1024 concurrent-FD budget (§4) ÷ 8 concurrent fetch connections (§4) ÷ ~2 FDs per in-flight build unit (source read + output write, §19.2) ≈ headroom for ~60 concurrent build units before the FD budget itself becomes the binding constraint ahead of the CPU-count-based concurrency target (§4).

36. Alternative Architectures (Roads Not Taken)

Full SAT/SMT solve over the whole index (libsolv/OPIUM-style).

┌────────────┐    ┌──────────────┐    ┌────────────┐
│ Full Index │───▶│ CNF Encoder  │───▶│ SAT/SMT    │
│ (all pkgs, │    │ (every pkg,  │    │ Solver     │
│ all vers)  │    │ every version│    │ (exhaustive│
└────────────┘    │ = a variable)│    │  search)   │
                   └──────────────┘    └─────┬──────┘
                                              │
                                       ┌──────▼──────┐
                                       │ Optimal Lock│
                                       └─────────────┘

Winning regime: package-manager ecosystems with a small, bounded index (OS distro package managers with tens of thousands of packages total, not millions of version permutations) where finding a provably optimal (not just satisfying) install set matters, e.g. minimizing total installed size. Real embodying system: libsolv (used by zypper/dnf's backend), and Tucker et al.'s OPIUM (ICSE 2007, §5). Why rejected here: encoding the entire index upfront as CNF does not scale to a sparse-index-fetched, lazily-discovered registry model (§16) — PubGrub's lazy incompatibility derivation (§14) achieves "good enough, explainable, fast" without ever materializing a full CNF encoding of an index with potentially unbounded package×version cardinality.

Nix-style purely functional store with no version resolution.

┌───────────────┐     ┌──────────────────┐     ┌────────────────┐
│ Derivation    │────▶│ Hash Every Input │────▶│ Content-Addr   │
│ Expression    │     │ (no ranges, no   │     │ Store          │
│ (exact inputs)│     │  resolution)     │     │ /nix/store/    │
└───────────────┘     └──────────────────┘     │ {hash}-{name}  │
                                                 └────────────────┘

Winning regime: whole-system reproducible deployment where every input (including the compiler and libc) must be pinned exactly, and "which version satisfies this range" is never a runtime question. Real embodying system: Nix (Dolstra, 2006 PhD thesis, §5). Why rejected here: this blueprint's explicit goal (§1.1) is to teach version resolution — PubGrub, incompatibility learning, conflict explanations (§14) — which a purely functional, pre-pinned-input model has no need for by design; adopting it would eliminate the resolver entirely, the opposite of this project's pedagogical goal.

Flat/hoisted node_modules vs. a symlinked CAS.

  • Flat/Hoisted: Symlinked CAS (this blueprint):
  • node_modules/ target/deps/
    • lodash/ (hoisted to top) ├── lodash-4.17.21 ──▶ CAS object
    • pkg-a/ ├── pkg-a-1.0.0 ──▶ CAS object
      • node_modules/ └── pkg-b-2.0.0 ──▶ CAS object
        • lodash/ (shadowed) (CAS: content-addressed,
    • pkg-b/ deduped by hash, §17)

Winning regime: ecosystems with very large dependency trees and disk-space pressure as the dominant concern, where hoisting's phantom-dependency risk (§33) is an accepted tradeoff for disk savings without a CAS. Real embodying system: npm/yarn classic hoisting. Why rejected here: this blueprint's CAS-linked model (§18, P2) gets deduplication and determinism simultaneously (I2/I4), without hoisting's implicit-access phantom-dependency bug class — the CAS approach strictly dominates hoisting once link/reflink materialization (§18.2) is available, per §33's comparative note.

Server-side resolution returning a precomputed lockfile.

┌────────┐   manifest    ┌───────────────┐   lockfile   ┌────────┐
│ Client │──────────────▶│ Resolution    │─────────────▶│ Client │
│  (CLI) │               │ Service (SaaS)│               │ builds │
└────────┘               └───────┬───────┘               └────────┘
                                  │ (full index, full
                                  │  resolver state,
                                  │  server-side only)

Winning regime: extremely large enterprise monorepos where centralizing resolution enables organization-wide policy enforcement (e.g., "never resolve to a package below security tier X") without distributing that policy logic to every client. Why rejected here: violates §1.5's deployment model (no server-side component in scope) and P1's "pure function of local inputs" simplicity — it also introduces a new trust dependency (the resolution service itself becomes part of the threat model, T3-adjacent) that this blueprint's client-only design avoids entirely.
