Decisions (§9) · 25 ADRs

ADR-01

Implementation language

Chosen

Rust

Rejected

OCaml, Haskell, Python

When the rejected choice is right

teaching HM by reading OCaml's own typing/ in OCaml itself, if the goal were literate self-hosting rather than an independent build

Why: ownership-friendly enums, no GC obscuring union-find lifetimes, mature fuzzing ecosystem

ADR-02

Inference algorithm

Chosen

Constraint-based HM(X) (generate-then-solve)

Rejected

Algorithm W (recursive, eager substitution); Algorithm J (in-place mutable unification)

When the rejected choice is right

a single-pass teaching build of the STLC-only core (Phase 3), where eager Algorithm W is simpler to trace by hand

Why: separates constraint generation from solving, required once extensions (rows, classes) need their own solver passes (Pottier & Rémy 2005)

ADR-03

Unification representation

Chosen

Union-find over mutable TyVar cells

Rejected

Persistent substitution map (immutable HashMap<TyVar, Type>)

When the rejected choice is right

a REPL history feature needing full substitution snapshots per step, where an immutable map's structural sharing is worth the extra cost

Why: near-linear amortized cost via path compression; avoids explicit map-composition on every bind

ADR-04

Occurs-check strategy

Chosen

Eager, on every bind

Rejected

Deferred periodic sweep

When the rejected choice is right

a batch-mode bulk-import of an already-verified corpus (Phase 11 conformance replay), where the source is known well-typed and the check is redundant work

Why: correctness-first; the eager check is O(size of τ), and skipping it risks constructing unrepresentable infinite types before detection

ADR-05

Generalization strategy

Chosen

Let-generalization with the value restriction

Rejected

Unrestricted generalization (unsound with refs); relaxed value restriction (generalize covariant results of value-restricted expressions)

When the rejected choice is right

a pure, ref-free subset of the language (e.g. a config-DSL frontend) where unrestricted generalization is provably safe and strictly more expressive

Why: Wright 1995's restriction is the minimal fix that keeps ML-style mutation sound

ADR-06

Type-variable representation

Chosen

Levels/ranks (à la OCaml, Rémy 1989)

Rejected

Global free-variable scan of the whole environment per generalization

When the rejected choice is right

a toy REPL evaluating single, small top-level expressions (Phase 0–4), where the scan's simplicity aids debugging before Phase 6 lands

Why: O(1)-amortized generalization instead of O(|Γ|) per let — essential once modules exceed a few hundred bindings

ADR-07

Constraint-solver design

Chosen

Incremental online solving (solve constraints as generated)

Rejected

Fully offline solving (collect all constraints, solve once at the end)

When the rejected choice is right

the qualified-types extension's predicate resolution (Phase 10), where deferring predicate constraints until generalization is required by design

Why: matches Algorithm W's original online character and gives earlier error locality

ADR-08

Error-message strategy

Chosen

Report at the unification failure site with full constraint provenance

Rejected

Report only "no type" at the top-level expression

When the rejected choice is right

a minimal REPL smoke-test mode where only pass/fail matters (Phase 0 CI gate)

Why: precise, actionable diagnostics require the originating sub-expression's span, not just failure

ADR-09

Row polymorphism extension

Chosen

Row variables with a "lacks" constraint (Rémy-style)

Rejected

Nominal record types with fixed fields

When the rejected choice is right

a language with declared, nominal record types (contrast a Pascal-family frontend), where field sets are always statically fixed

Why: keeps records first-class and polymorphic without declaring every shape ahead of time

ADR-10

Type-class extension

Chosen

Qualified types with deferred predicate resolution (Wadler & Blott 1989)

Rejected

Ad-hoc overload resolution at the call site with no principal-type story

When the rejected choice is right

a language with a fixed, closed set of numeric-literal overloads only, where call-site dispatch is simpler and provably terminates

Why: preserves a documented principal-qualified-type guarantee (§8.10) rather than an unprincipled dispatch heuristic

ADR-11

Recursive types

Chosen

let rec via a fixpoint type variable solved before generalization

Rejected

Explicit μ-type annotations required from the user

When the rejected choice is right

an explicitly iso-recursive data-type extension where the user is defining a type, not just a recursive function, and annotation is the point

Why: keeps the zero-annotation guarantee (P1) for recursive functions, the common case

ADR-12

AST / IR representation

Chosen

Rejected

When the rejected choice is right

a one-shot scripting tool inferring a single 20-node expression, where boxed trees are simpler to write and the arena's setup cost isn't repaid

Why: cheap Copy node handles, cache-friendly traversal, stable IDs for diagnostics/trace

ADR-13

When the rejected choice is right

Why: automatable, regression-proof, runs in CI on every change

Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Bidirectional Type Checking

  annotated-or-inferred
   mode: Check(expected_ty) | Synth
        |
        v
  +----------------+     Check mode: push expected type
  |  bidirectional  | <---  down through the term
  |  type checker   |
  +----------------+     Synth mode: pull a type up
        |                 from a sub-term (e.g. a
        v                 variable's declared type)
   inferred/checked type

Winning regime: richer type systems (dependent types, higher-rank polymorphism, GADTs) where full HM-style reconstruction is undecidable or requires exponential search — bidirectional propagation trades some annotation burden for decidable, predictable checking. Real embodying system: Agda and Idris 2 (bidirectional elaboration — dependent types have no decidable full-inference algorithm analogous to Damas–Milner); GHC's -XRankNTypes checking path, which switches to Check mode at every annotated higher-rank binder. Why rejected here: this project's entire point is the zero-annotation reconstruction guarantee (P1) — adopting bidirectional checking would answer a different question than the one this blueprint exists to answer, even though it is the more scalable design for richer type systems in general.

Constraint-Based HM(X) / OutsideIn(X) as the Sole Architecture

  AST --generate--> [ constraints ]  --collect-all-->  solver
                                                          |
                                            simplify, defer, or reject
                                                          |
                                                          v
                                              scheme (with residual predicates)

Winning regime: type systems with multiple, mutually-interacting extensions (type classes, GADTs, type families simultaneously) where generation and solving must be fully decoupled to stay tractable. Real embodying system: GHC's OutsideIn(X) (§33). Why partially adopted, not fully: this project does adopt the constraint-based generate-then-solve shape for its extensions (ADR-02, ADR-07) but keeps the core Var/App/Abs/Let path close to classic Algorithm W's directness (§8.3) for pedagogical clarity and to keep the §8.3 worked example legible by hand — a full OutsideIn(X)-style architecture for the entire engine, including the four core rules, was rejected as disproportionate machinery for a system with only two small extensions.

Local Type Inference / No Let-Generalization

  Var --lookup(monotype only)--> App --unify--> Abs --unify--> (no generalize step)

Winning regime: simple scripting-language type inference where full let-polymorphism is not needed and a monomorphic-per-binding model is acceptable — local/contextual inference within a function body, generalization handled separately or not at all. Real embodying system: TypeScript's local and contextual inference (no let-generalization — generics are declared, never reconstructed at a let); Go's := short-variable-declaration inference, monomorphic per binding by construction. Why rejected here: this is precisely the "monomorphic inference would reject" case worked through in §8.9 — dropping let-generalization would make the engine unable to type let id = λx. x in (id 3, id true), which is the textbook demonstration of HM's core value proposition; a project about HM inference without let-polymorphism is a different, lesser project.

Full Annotation, No Inference (System F)

  Λα. λ(x:α). x  : ∀α. α -> α        -- every quantifier and every
                                        parameter type written by hand

Winning regime: systems requiring impredicative or higher-rank polymorphism, where full type inference is undecidable (Wells 1994) and the honest engineering answer is "the programmer writes the types." Real embodying system: GHC Core (System FC) — the fully type-annotated intermediate language every Haskell program is elaborated into, where -dcore-lint type-checks with zero inference; likewise GHC's -XRankNTypes surface extension requires explicit forall annotations at exactly the points inference can't reach. Why rejected here: zero-annotation reconstruction (P1) is the explicit product; a System-F-style fully annotated core is the polar opposite design point, useful as a contrast (cited throughout §1, §36) but not a candidate implementation for this project.
