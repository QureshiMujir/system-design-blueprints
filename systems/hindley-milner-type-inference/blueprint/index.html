238 — Hindley–Milner Type Inference

Project Number: 238

Project Name: Hindley–Milner Type Inference

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from scratch in Rust, a Hindley–Milner (HM) type inference engine: full type reconstruction for a polymorphic lambda calculus with let-polymorphism, requiring zero type annotations from the programmer. The engine parses source to an AST, generates equality constraints over a fresh set of type variables, solves them with Robinson unification (occurs-checked, union-find-backed), generalizes let-bound expressions into type schemes, instantiates schemes at use sites, and reports either a principal type or a deterministic type error. The product is the inference core plus a thin library/REPL shell — not a compiler, not a runtime, not a backend.

Phase-0 deliverable (crate list):

  1. hm-ast — expression grammar, literals, let/let rec, lambda, application, AST node IDs.
  2. hm-parser — recursive-descent/Pratt parser from source text to hm-ast.
  3. hm-types — Type, TypeScheme, TyCon, row/qualified-type extension types.
  4. hm-unify — union-find substitution store, Robinson unification, occurs check.
  5. hm-infer — constraint generator, Algorithm W driver, generalize/instantiate.
  6. hm-diagnostics — InferError taxonomy, principal-type-aware error rendering.
  7. hm-driver — REPL/session orchestration, pretty-printer for inferred types.
  8. hm-conformance — well-typed/ill-typed corpus runner, differential-oracle harness.
  9. hm-cli — command-line entry point invoking the driver.
  10. hm-trace — inference-trace instrumentation (constraint emission, unify steps).

Boundaries: the engine infers principal types for terms of the source language defined below and hands a fully-elaborated, type-annotated AST to whatever downstream compiler wants it. It does not generate code, does not run programs, does not manage memory layout, and does not define an evaluator — those are a sibling Compiler blueprint's job (PhaseDeferred("§1 Goal & Scope (Boundaries)")).

Non-goals, stated precisely against the two nearest sibling projects: this is not Type-Checker (project 42) — 42 checks a program against annotations the programmer already wrote (a bidirectional or syntax-directed checker with no reconstruction obligation); this project performs full reconstruction with no annotations required, which is a strictly harder and different problem (Damas & Milner 1982). This is not Dependent-Type-Checker (project 239) — 239 has a dependent type system where type checking is in general undecidable and requires normalization of terms inside types; this project's type system (HM) has decidable, complete inference (Damas & Milner 1982) precisely because it restricts polymorphism to prenex, rank-1 quantification at let. Also non-goals: no full type-class resolution beyond the documented HM(X) extension (superclasses, functional dependencies, overlapping instances are out of scope — PhaseDeferred("§22 Phase 10 — Type Classes / Qualified Types (HM(X))")); no higher-rank or impredicative polymorphism (PhaseDeferred("§36 Alternative Architectures")); this is not a compiler backend and emits no machine code or IR beyond a typed AST.

Source language: a polymorphic lambda calculus — variables, integer/boolean/string literals, lambda abstraction, application, let (non-recursive, generalizing) and let rec (recursive, generalizing after fixpoint typing), plus three documented extensions layered in phases 9–10: row-polymorphic records, qualified types (type-class-style constraints), and iso-recursive types for let rec data.

Deployment model: (1) a Rust library (hm-infer + hm-types + hm-unify) embeddable by any host compiler or tool; (2) a REPL (hm-cli over hm-driver) that reads an expression, infers and prints its principal type (e.g. id : forall a. a -> a), and optionally dumps the inference trace. No server, no daemon, no network surface.

Users/operators: PL researchers validating HM extensions; compiler engineers embedding inference into a language frontend; the project author, self-studying Algorithm W, unification, and let-generalization by building the load-bearing algorithm from the papers upward. What later phases unlock: Phase 6 (levels/ranks) unlocks inference at realistic module sizes without the naive free-variable scan; Phase 7 (principal-type verification) unlocks a trustworthy differential oracle; Phases 9–10 (rows, qualified types) unlock language features most real MLs and Haskell ship; Phase 11's differential corpus unlocks confidence claims against OCaml and GHC's inference on shared fixtures.

Language: Rust. Rationale — sum-type-friendly enum modeling for Type/Constraint/ InferError variants that must be matched exhaustively; no garbage collector, so union-find and substitution arenas have deterministic, inspectable lifetimes; a mature property-testing and fuzzing ecosystem (proptest, cargo-fuzz) needed for the soundness/completeness properties in §28; a real precedent — rustc's own type inference (compiler/rustc_hir_typeck/) and OCaml's typing/ are both written in languages with the same ownership-and-enums shape this project needs. Rejected alternatives: OCaml (the canonical HM host language, but self-hosting the algorithm in the language whose own compiler already implements it would obscure the learning target and complicate differential comparison against typing/typecore.ml); Haskell (GHC's own inference is the comparison target in §33 — implementing the student engine in Haskell risks accidentally leaning on GHC's runtime laziness/typeclass machinery instead of building unification by hand); Python (no static typing discipline for modeling Type/Constraint ASTs, and reference-counted GC obscures the union-find ownership story this project is meant to teach).

Prerequisites: untyped and simply-typed lambda calculus; substitution and alpha- equivalence; the notion of a type scheme vs. a monotype; first-order unification (Robinson 1965); the shape of a soundness/completeness theorem for a type system.

Timeline: Phase 0 (skeleton, AST, parser, CI) 1–2 weeks; Phases 1–4 (mono types, unification, Algorithm W, let-polymorphism) 4–6 weeks — this is the load-bearing core; Phases 5–7 (value restriction, levels/ranks, principal-type verification) 3–4 weeks; Phases 8–10 (recursive types, rows, qualified types) 5–7 weeks; Phase 11 (conformance + differential + perf) 2–3 weeks. Total: roughly 4–5 months to a fully-extended, perf- hardened engine; roughly 6 weeks to a correct core (Phases 0–4) sufficient to infer let id = \x. x in (id id) and reject \x. x x.

Deferrals: PhaseDeferred("§22 Phase 10 — Type Classes / Qualified Types (HM(X))") for full resolution beyond single-parameter classes; PhaseDeferred("§36 Alternative Architectures") for higher-rank/impredicative polymorphism and for a module/functor system; PhaseDeferred("§1 Goal & Scope (Boundaries)") for codegen and runtime, which belong to a sibling Compiler blueprint; dependent types are never in scope for this project (see Dependent-239).

2. Why Build This

Keywords: principal types; Algorithm W; Robinson unification; occurs check; union-find; let-generalization; instantiation; the value restriction; prenex polymorphism; type schemes; substitution calculus; soundness and completeness; row polymorphism; qualified types; HM(X); the Damas–Milner theorem; DEXPTIME-completeness vs. practical linearity; differential testing against a production compiler's type checker.

This project is the direct, from-the-papers construction of the algorithm that made statically-typed functional programming practical: Milner's 1978 insight that a type system could infer polymorphism without programmer annotation, formalized and proved complete by Damas & Milner in 1982. Building it forces confrontation with unification as an engine (not a library call), with why generalization has to happen exactly at let, and with why "just generalize everything" is unsound once mutable references exist (Wright 1995). It is a small, precisely bounded system whose correctness is a mathematical theorem, not a vibe — which makes it an unusually good target for property-based and differential testing.

What Mastery Looks Like

  • Deriving the Algorithm W trace for let id = \x. x in (id id) by hand and matching the engine's constraint log, node for node (Phase 3, Phase 4).
  • Explaining why the occurs check is not optional — producing the infinite-type example \x. x x and showing the unifier rejects it deterministically (Phase 2).
  • Explaining, with a concrete ref-based counterexample, why unrestricted generalization is unsound and what the value restriction changes (Phase 5).
  • Implementing OCaml-style levels/ranks and measuring the generalization-cost win over the naive free-type-variable environment scan (Phase 6).
  • Proving (empirically, via the corpus in Phase 7) that every type the engine returns is principal — every other valid typing is an instance of it.
  • Extending HM soundly with row-polymorphic records without breaking principal types (Phase 9), and contrasting that with a qualified-type extension for type classes (Phase 10) — understanding HM(X) as a design space, not a single algorithm.
  • Running a differential oracle against OCaml's and GHC's inference on a shared corpus and explaining every discrepancy (Phase 11).

Parser → AST: hm-parser turns source text into the hm-ast node graph (§8.3); it performs no typing work and defers all semantic questions to inference. The AST is immutable once built and every node carries a stable NodeId for diagnostics.

Constraint Generator: hm-infer's Algorithm-W (or the constraint-based HM(X)) driver walks the AST, allocates fresh type variables, threads the TypeEnv (§8.1), and emits Constraint values (Equality/Instance) rather than solving eagerly when the constraint-based formulation is chosen (ADR-02). This is the single place where the typing rules of §8.2 are executed as code-shaped steps.

Type Environment: TypeEnv maps term variables to TypeSchemes; it is persistent (structural sharing) so that entering/leaving a let-scope is O(1) to snapshot and restore, which matters once levels/ranks (Phase 6) depend on cheap scope entry/exit.

Unifier (union-find): hm-unify holds the canonical substitution as a union-find forest over TyVar representatives (Robinson 1965, with the union-find acceleration standard in modern implementations — see OCaml's Ctype). Every Equality constraint is solved here; the occurs check runs on every variable-to-type binding.

Generalizer/Instantiator: converts a monotype into a TypeScheme by quantifying over type variables free in the type but not free in the environment (generalization), and the reverse — replacing a scheme's bound variables with fresh ones at each use (instantiation). Phase 6 replaces the naive environment free-variable scan with levels/ranks (Rémy 1989-style, as used in OCaml).

Substitution Engine: the idempotent, composed mapping from TyVar to Type that the unifier builds incrementally; hm-types/hm-unify jointly guarantee it is always applied to canonical form before being read (I9, §7).

Type-Scheme Store: hm-types owns interned Type/TypeScheme values so identical types compare and hash in O(1); this is what makes principal-type-equivalence checks (Phase 7) and differential comparison (Phase 11) tractable.

Extension Modules (rows, classes): row polymorphism (Phase 9) and qualified types (Phase 10) are implemented as HM(X)-shaped extensions — extra constraint forms plus an extra solving step — layered on the same unifier and generalizer rather than forking them, per Pottier & Rémy 2005's constraint-based view.

REPL/Pretty-Printer: hm-driver/hm-cli read one expression, run the whole pipeline, and print the principal type or a diagnostic (hm-diagnostics), optionally alongside an inference trace (hm-trace) for pedagogical/debugging use.

4. System Constraints

Constraint Target
AST size handled (single expression) up to 200,000 nodes
Max let-nesting depth 10,000 (stack-safe via explicit worklist beyond depth 512)
Cold single-expression inference latency (≤500 nodes) < 5 ms p50, < 20 ms p99
Inference latency, realistic module (~5,000 nodes) < 150 ms p95
Unification cost per constraint (amortized, union-find) O(α(n)) — near-constant (inverse-Ackermann)
Worst-case theoretical complexity DEXPTIME-complete (Mairson 1990, on nested-let blowup); practical corpora run near-linear
Type-variable count ceiling (single session) 2,000,000 live variables before forced GC of dead substitution entries
Union-find operations budget 10,000,000 find/union ops/sec sustained (single core)
Memory ceiling (5,000-node module) < 64 MB resident
Principal-type guarantee 100% — every accepted term's returned type is principal (Damas–Milner)
Error-reporting latency after unification failure < 1 ms to render a diagnostic from the failed constraint
RTO (REPL session crash) < 1 s to cold-restart a fresh session; no persistent state to recover (Phase 0–7 have no cross-session persistence)

6. Design Principles

P1. Inference reconstructs the principal (most general) type with zero annotations — that guarantee is the entire product; any heuristic returning a less-general type is a bug (Damas & Milner 1982).

P2. Unification is the engine — inference is generating equality constraints between types and solving them with Robinson's algorithm plus the occurs check; everything else is bookkeeping (Robinson 1965).

P3. Let-generalization is where polymorphism enters; the value restriction is the scar tissue that keeps it sound in the presence of mutation (Wright 1995).

P4. A substitution is a value, not an effect — it is built once per unification step and composed explicitly; nothing outside hm-unify mutates types in place.

P5. The occurs check is never skippable for correctness; where it is skipped for performance (deferred to a periodic sweep), the deferral must be provably safe on the subset of terms it covers.

P6. Generalization only quantifies variables that are free in the candidate type and not free in the ambient environment — never "all variables in the type."

P7. Every constraint carries enough provenance (source NodeId, originating rule) to render a diagnostic without re-walking the AST.

P8. The constraint-based formulation (HM(X)) is preferred over hand-rolled Algorithm W recursion wherever an extension (rows, classes) needs its own solving pass, because it separates "what must be true" from "how we prove it" (Pottier & Rémy 2005).

P9. Type identity is structural and interned — two types are the same value if and only if they are the same interned node, never compared field-by-field at the call site.

P10. Levels/ranks, not a free-variable scan of the whole environment, are the mechanism for cheap generalization once Phase 6 lands; Phase 3–5 may use the naive scan deliberately, as a correctness baseline to differential-test the optimization against.

P11. Diagnostics must be deterministic and reproducible byte-for-byte given the same source — nondeterministic error ordering is a correctness bug in an inference engine, not a cosmetic one.

P12. Every extension (rows, qualified types, recursive types) must preserve the principal-types guarantee for the un-extended core — an extension that silently degrades core inference is rejected regardless of the feature it buys.

P13. No unbounded recursion on attacker/fuzzer-controlled AST shape — every recursive traversal (unification, generalization, occurs check) has an explicit depth budget or is rewritten iteratively before it ships.

P14. A worked example beats a hand-wave — every non-trivial rule (unification, generalization, the value restriction) in §8 ships with a fully worked derivation, not just the equation.

Debugging methodology: every invariant violation is first reproduced as a minimal fixture (shrunk via proptest's shrinker where property-derived, or hand-minimized from a corpus regression), then replayed through hm-trace to find the exact constraint or unification step where the invariant broke, then fixed at that step — never patched by special-casing the symptom at a higher layer (P4, P9).

8. Domain Model

8.1 Type Grammar

Type variables   α, β, γ  ∈ TyVar
Type constructors k       ∈ TyCon        (Int, Bool, String, ->, list, ...)
Monotypes        τ ::= α | k τ1 ... τn | τ1 -> τ2
Type schemes      σ ::= τ | ∀α. σ

A monotype τ has no quantifiers. A type scheme σ = ∀ᾱ. τ is a monotype τ with a (possibly empty) prefix of universally quantified variables ᾱ; HM restricts quantification to prenex position at let — no quantifier may appear nested inside an arrow (that restriction is exactly what makes inference decidable — contrast System F, §36). The type environment Γ maps term variables to schemes: Γ : Var ⇀ σ.

8.2 Typing Rules

 Var:     x : σ ∈ Γ        σ' = instantiate(σ)
        ------------------------------------------
                    Γ ⊢ x : σ'

 App:      Γ ⊢ e1 : τ1 -> τ2       Γ ⊢ e2 : τ1
        ------------------------------------------
                    Γ ⊢ e1 e2 : τ2

 Abs:            Γ, x : τ1 ⊢ e : τ2
        ------------------------------------------
                Γ ⊢ (λx. e) : τ1 -> τ2

 Let:    Γ ⊢ e1 : τ1     σ = generalize(Γ, τ1)     Γ, x : σ ⊢ e2 : τ2
        ------------------------------------------------------------
                        Γ ⊢ (let x = e1 in e2) : τ2

Var is where instantiation happens (fresh copies of the bound variables in σ); Let is where generalization happens (quantify the free variables of τ1 not free in Γ) — these two rules are the entire polymorphism story; App/Abs are the ordinary simply-typed rules, unchanged from Curry-style STLC.

8.3 Algorithm W — Worked Example

Term: let id = λx. x in (id id).

Step 1  Infer λx. x under Γ0 = {}:
          fresh α1;  Γ0,x:α1 ⊢ x : α1   (Var, no scheme, trivial instantiate)
          Abs gives  Γ0 ⊢ (λx. x) : α1 -> α1
Step 2  Generalize at let:  free(α1 -> α1) \ free(Γ0) = {α1}
          σ_id = ∀α1. α1 -> α1
          Γ1 = Γ0, id : σ_id
Step 3  Infer (id id) under Γ1:
          instantiate σ_id for the operator id:  fresh α2, gives α2 -> α2
          instantiate σ_id for the operand id:   fresh α3, gives α3 -> α3
          App needs: (α2 -> α2) ~ ((α3 -> α3) -> β)   [β fresh, result type]
Step 4  Unify (α2 -> α2) with ((α3 -> α3) -> β):
          α2 ~ (α3 -> α3)          [domain]
          α2 ~ β                  [codomain, after substituting α2]
          => substitution S = { α2 ↦ (α3 -> α3), β ↦ (α3 -> α3) }
Step 5  Result type of (id id):  β  under S  =  α3 -> α3
Final:  let id = λx. x in (id id)  :  ∀α3. α3 -> α3

Every use of id gets its own fresh instantiation (α2, α3) — this is exactly why id can be applied to itself: the two occurrences are not required to unify with each other, only each with its own use site.

8.4 Unification (Robinson) — Named Steps

Unification is specified as a dispatch table over the canonical operands τ1', τ2' — the union-find representatives of τ1, τ2 (§8.6). Rules are total and mutually exclusive; the first matching row is the applicable one. Rule IDs U0–U5 and B1–B3 are the terminology used by hm-unify error paths, telemetry labels, and Phase 2 (§14).

# Canonical LHS τ1' Canonical RHS τ2' Action Error
U0 any any precondition: both operands replaced by their union-find representatives before any other rule is consulted —
U1 TyVar α TyVar α, same representative no-op — already the same class —
U2 TyVar α any (not covered by U1) delegate to bind table with (α, τ2') inherited from B2
U3 any non-var TyVar β delegate to bind table with (β, τ1') inherited from B2
U4 k(a1..an) k(b1..bn), same constructor k, same arity n decompose into n child constraints ai ~ bi, enqueued left-to-right on the worklist first child failure propagates unchanged
U5 k(a1..an) j(b1..bm), k ≠ j or n ≠ m none — terminal Clash(τ1', τ2')
# Condition on bind(α, τ) Action Error
B1 τ is the representative α itself no-op — the constraint is already satisfied —
B2 occurs(α, τ) holds (α reachable inside τ) none — terminal Occurs(α, τ)
B3 neither B1 nor B2 matches union-find union; α's class representative becomes τ; level of α propagated into τ's vars (§18) —

Worked unify: unify(α -> Int, Bool -> β) → U4 decomposes the Arrow constructor → unify(α, Bool) takes U2→B3 and binds α ↦ Bool; unify(Int, β) takes U3→B3 and binds β ↦ Int. Result substitution {α ↦ Bool, β ↦ Int}.

Worked occurs-check failure: unify(α, α -> Int) → U2 delegates bind(α, α -> Int) → B2 matches: occurs(α, α -> Int) is true (α appears inside its own proposed binding) → terminal failure Occurs(α, α -> Int). This is precisely the constraint Algorithm W would generate for λx. x x (self-application): x : α is applied to itself, requiring α ~ (α -> β), an infinite type — correctly rejected.

8.5 Generalization and Instantiation

generalize(Γ, τ) = ∀ᾱ. τ    where ᾱ = free(τ) \ free(Γ)

instantiate(∀ᾱ. τ) = τ[ᾱ ↦ β̄]     β̄ fresh, |β̄| = |ᾱ|

free(Γ) is the union of free variables of every scheme in Γ's range (a scheme's own bound variables ᾱ do not count as free inside it). Both operations are total and O(1) in the conceptual equations above; §8.6 and Phase 6 concern the cost of computing free(Γ) in practice.

8.6 Union-Find Representation of the Substitution

The substitution S is not stored as a literal map from every variable to its type; it is a union-find forest over TyVar nodes. find(α) follows parent pointers with path compression to the canonical representative; if the representative is itself bound to a non-variable type τ, that binding is the variable's current type under S. union(α, τ) (via bind, §8.4) sets α's representative to a fresh node holding τ. Composition of two unifications is implicit — later bind calls simply extend the same forest; no separate "compose substitutions" step is needed (contrast a naive substitution-map implementation, which must explicitly compose two maps — ADR-03).

8.7 The Principal-Types Theorem

Stated (Damas & Milner 1982, Theorem 3): if a closed term e is typable under Γ, then Algorithm W computes a type scheme σ such that every type scheme σ' derivable for e under Γ is a generic instance of σ. Corollary: type inference for this language is complete — if any typing exists, W finds the most general one — and sound — every type W returns is a valid typing. This is I1/I5.

8.8 The Value Restriction — Worked Unsound Example

Without the value restriction, given a mutable reference primitive ref : α -> Ref α:

let r = ref (λx. x) in
  (set r (λn:Int. n + 1);      -- unifies α with Int -> Int
   (!r) true)                  -- unsoundly typed true : Int -> Int !!

If r's type were unsoundly generalized to ∀α. Ref (α -> α) at the let, each use of r would instantiate fresh, allowing the set to fix the contents at Int -> Int while a later read is typed as if still polymorphic, applying true where an Int is expected — a type error at runtime that the checker should have caught. The value restriction (Wright 1995) fixes this: r's binding, ref (λx. x), is not syntactically a value (it is a function application), so it is not generalized; r gets a monomorphic type Ref (α -> α) at the ambient rank, and the set call's unification of α with Int -> Int correctly forces every subsequent use — the unsound program above no longer type-checks (I4).

8.9 Let-Polymorphism Example Monomorphic Inference Would Reject

let id = λx. x in
  (id 3, id true)

A monomorphic (non-generalizing) inference would unify id's single type variable with both Int (from id 3) and Bool (from id true) — a clash. HM's Let rule generalizes id : ∀α. α -> α before the body is checked, so each application instantiates its own fresh α; the tuple types as (Int, Bool). This is the entire point of let-polymorphism (P3, P8.5).

8.10 Extensions as HM(X) Contrasts

Extension Constraint form added Solved by Preserves principal types?
Row polymorphism (Phase 9) row equality/row-lacks constraints over RowVar row-unification pass alongside hm-unify yes, for the row-closed core (Rémy 1989)
Qualified types / classes (Phase 10) predicate constraints π (e.g. Eq α) accumulated in ∀ᾱ. π ⇒ τ deferred resolution + dictionary-passing elaboration (Wadler & Blott 1989) yes, with the caveat that a scheme now carries a predicate context — "principal" means "most general qualified type"
Recursive types (Phase 8) let rec fixpoint constraint before generalization ordinary unification, generalization deferred until the fixpoint type is solved yes, provided the value restriction still gates the bound function value

8.11 Malformed / Hard Examples

  • Occurs-check failure / infinite type: λx. x x → unify(α, α -> β) fails (§8.4).
  • Unification clash: (λx:Int. x) true conceptually forces unify(Int, Bool) → fails with Clash(Int, Bool).
  • Monomorphism-restriction case: let f = λx. x in (f f, f 1) — legal under HM's ordinary let-generalization (no value-restriction issue, since λx. x is a value); contrast with §8.8, where the bound expression is not a value.
  • Value-restriction trap: §8.8's ref (λx. x) example.
  • Exponential-blowup nested-let case: let x1 = λy.(y,y) in let x2 = λy.(x1 y, x1 y) in ... let xn = λy.(x_{n-1} y, x_{n-1} y) in xn — each level doubles the printed type size, giving O(2^n) type-term size in the worst case (Mairson 1990) — see §31, §34.

8.12 Failure-Path Example

Input: let bad = λx. (x x) in bad. Constraint generation produces α ~ (α -> β) for the body x x under x : α. Unification fails at bind(α, α -> β) with Occurs(α, α -> β); hm-diagnostics renders InferError::Occurs { var: α, ty: α -> β, span: <x x> }, and the REPL prints a deterministic message naming the offending sub-expression, not merely "type error."

  • Recursive-descent stack depth on deeply nested applications (f x1 x2 ... x1000) — bounded per I13-style depth budgets (see §7's spirit, formalized fully in Phase 2).

  • Deeply right-nested let ... in let ... in ... chains (10,000 deep, per §4).
  • Mixed line-ending styles in source files.

12.9 Failure Analysis

  14. Document the occurs-check-skip-is-never-safe rule (P5) inline as a code comment anchor for future extension authors (rows, classes).

A correct, occurs-checked, union-find-backed unifier passing all worked examples from §8.4 and satisfying I2/I6/I9/I10 under property testing.

14.4 Acceptance Criteria

  • unify(α -> Int, Bool -> β) yields exactly {α ↦ Bool, β ↦ Int} (fixture match).
  • unify(α, α -> Int) yields InferError::Occurs deterministically (fixture match).
  • Union-find throughput ≥ 10,000,000 ops/sec on the reference benchmark machine (§4).
  • Zero fuzz-found panics after a 1-hour local cargo-fuzz run (full campaign deferred to Phase 11's scheduled fuzzing, §28).

14.5 Conformance Fixtures

  • conformance/well-typed/unify-basic.fixture (the §8.4 worked unify)
  • conformance/ill-typed/unify-occurs.fixture (the §8.4 occurs-check failure)
  • conformance/ill-typed/unify-clash.fixture (Int vs Bool)
  • conformance/well-typed/unify-recursive-arrow.fixture (nested arrow unification)

14.6 Pitfalls

  • Forgetting path compression, degrading union-find to O(n) per find and silently missing the §4 throughput target.
  • Running the occurs check after the tentative bind rather than before, requiring an unwind step and risking a half-mutated forest on failure.
  • An occurs check without a depth budget on adversarial deeply-nested types, risking a stack overflow rather than a clean InferError (violates I10, P13).
  • Comparing TyVars by raw equality instead of through find(), silently treating two unified variables as distinct.

14.7 Performance Concerns

  • Path-compression amortized cost is O(α(n)) but a pathological adversarial union pattern (long chains before any find) can transiently spike latency — mitigated by union-by-rank (not just path compression alone).
  • Occurs-check cost is O(size of the candidate type); nested-let-heavy programs (§8.11) can make individual binds expensive even though total work stays bounded.

14.8 Edge Cases

  • Unifying a type with itself (no-op, must not spuriously "occur-check fail").
  • Unifying two already-equal representatives (post path-compression short-circuit).
  • A constraint stream with zero constraints (trivial success).
  • Deeply nested Arrow chains (10,000-deep curried function types).

14.9 Failure Analysis

Symptoms of a broken unifier: non-termination (I10 violation, caught by the step budget), a forest that becomes cyclic (I2 violation, caught by the corruption assertion), or non-canonical reads (I9 violation, caught by the fixed-point property test) — each has a dedicated automated detector, not just manual inspection.

14.10 Operational Notes

Metrics: unify_ops_total, occurs_check_rejections_total, union_find_path_compressions_total, unify_step_budget_exceeded_total. These are the direct inputs to §26's inference-trace dashboards and §30's performance targets M3–M5.

16. Phase 4 — Let-Polymorphism: Generalization and Instantiation

16.1 Objectives

  • Implement generalize/instantiate (§8.5, §11) and wire them into the Let typing rule (§8.2), completing the core HM algorithm (P1, P3, P6).

16.2 Detailed Implementation Steps

  1. Implement free_vars(TypeEnv) using Phase 1's naive scan (ADR-06 notes this is intentionally the pre-Phase-6 baseline).
  2. Implement generalize(env, ty): compute free(ty) \ free(env), build a TypeScheme (I3, §8.5).
  3. Implement instantiate(scheme): allocate fresh TyVars disjoint from every live variable (I11), substitute for the scheme's bound variables (§8.5).

  8. Add property test: I3 (generalized variables ∩ free(env) = ∅) across a generated corpus of nested lets.
  9. Add property test: I11 (instantiation freshness disjointness).
  10. Extend hm-trace with Generalize/Instantiate events carrying the before/after scheme (groundwork for the pedagogical trace viewer, tools/).
  11. Add let rec-shaped parsing already accepted by Phase 0's grammar but reject it cleanly in this phase with a clear "not yet supported until Phase 8" diagnostic, avoiding silent wrong answers.
  12. Add 20 let-polymorphism example programs (nested lets, polymorphic identity/compose, shadowing).
  13. Benchmark generalization cost with the naive scan against the §4 targets, recording a baseline number that Phase 6 is measured against (§34).
  14. Differential-check the worked example's final type against OCaml's ocaml REPL manually as a one-time sanity fixture (the systematic differential harness is Phase 11).

16.3 Deliverable

A complete Damas–Milner Algorithm W implementation: Var/App/Abs/Let all wired, correctly generalizing and instantiating, matching the §8.3 worked example exactly.

16.4 Acceptance Criteria

  • let id = λx. x in (id id) infers ∀a. a -> a (canonical print), matching §8.3's derivation step-for-step in the trace fixture.
  • let id = λx. x in (id 3, id true) infers (Int, Bool) (via a pair primitive introduced for this fixture only).
  • The monomorphic-only ablation build rejects the same program with a clash — proving the generalization step is load-bearing, not cosmetic.
  • I3 and I11 property tests pass across ≥ 10,000 generated nested-let programs.

16.5 Conformance Fixtures

  • conformance/well-typed/let-poly-id-self-app.fixture (§8.3's worked example)
  • conformance/well-typed/let-poly-int-bool.fixture (§8.9's example)
  • conformance/regression/let-poly-monomorphic-ablation.fixture
  • conformance/well-typed/let-poly-nested-shadowing.fixture

16.6 Pitfalls

  • Generalizing under the post-binding environment (after x is already added to Γ) instead of the pre-binding one, which can spuriously capture x's own type variable and violate I3.
  • Sharing a single "fresh variable" counter incorrectly across independent instantiations, accidentally unifying two logically distinct uses (violates I11).
  • Forgetting to instantiate at every Var occurrence — caching an instantiated type and reusing it across two different use sites reintroduces the exact bug let-polymorphism exists to prevent.

16.7 Performance Concerns

  • The naive free_vars(TypeEnv) scan is O(|Γ|) per let, which on deep or wide environments dominates inference time — intentionally not yet fixed (ADR-06); the benchmark recorded here (step 13) is the "before" number for Phase 6's "after."

16.8 Edge Cases

  • A let whose bound expression has no free type variables to generalize (monomorphic result, degenerate but valid scheme σ = τ with an empty quantifier list).

  • A polymorphic function instantiated zero times in the body (dead code, but must still type-check the binding itself).

16.9 Failure Analysis

18. Phase 6 — Efficient Generalization with Levels/Ranks

18.1 Objectives

  • Replace Phase 4's naive free_vars(TypeEnv) scan with the levels/ranks technique (Rémy 1989, as used in OCaml's Ctype) for O(1)-amortized generalization (ADR-06, P10).
  • Preserve exact type-equivalence with the naive implementation (differential-checked against Phase 4's baseline).

18.2 Detailed Implementation Steps

  1. Add a Level field to every TyVar at allocation time, set to the current TypeEnv's level (§11's Level/Rank).
  2. Increment the level on entering a let's right-hand-side inference, decrement on exit (bracketing the binding's own scope).
  3. On bind(var, ty) in the unifier, propagate the minimum level down into ty's free variables (the standard OCaml "level lowering" step) — this keeps levels a sound proxy for "could this variable be free in an outer scope."
  4. Reimplement generalize: quantify exactly the variables whose level is deeper than the ambient (ADR-06) let's level, in O(1) amortized by scanning only the candidate type's own free variables, not the whole environment.
  5. Remove the Phase-4 naive scan from the hot path; retain it behind a feature flag as a differential oracle for this phase only (self-testing infrastructure, not shipped default behavior).
  6. Add a differential property test: for every fixture in conformance/well-typed/, assert generalize_levels(...) == generalize_naive(...) (same resulting scheme, up to alpha-equivalence).
  7. Benchmark generalization cost before/after on a synthetic 5,000-binding module, confirming the ADR-06 O(1)-amortized claim empirically (feeds §34).
  8. Extend hm-trace events with the level at allocation/generalization time, useful for debugging level-lowering bugs.
  9. Add property test: no TyVar is ever generalized at a level shallower than its own allocation level (an invariant specific to the levels scheme, additive to I3).
  10. Add a targeted fuzz corpus of adversarial nested-let programs (§8.11) to stress the level-lowering propagation step specifically.
  11. Document the level-lowering step's interaction with bind explicitly in code comments, citing Rémy 1989, since this is the single most bug-prone step reported across reference implementations (OCaml's own history includes level bugs).
  12. Re-run every Phase-0–5 conformance fixture under the new levels-based generalizer and confirm zero regressions.

18.3 Deliverable

A levels/ranks-based generalizer, differentially verified equivalent to the naive Phase-4 implementation on the full conformance corpus, with a measured performance win.

18.4 Acceptance Criteria

  • Zero differences between levels-based and naive generalization across 100% of the conformance/well-typed/ corpus (differential property test).
  • Generalization cost on the 5,000-binding synthetic module drops from the Phase-4 baseline (recorded in §16.10) to O(1)-amortized per let, verified by a benchmark showing sub-linear scaling as binding count grows (10x bindings, < 2x generalize time).
  • Zero regressions across all Phase 0–5 conformance fixtures.

18.5 Conformance Fixtures

  • conformance/regression/levels-vs-naive-differential.fixture (full corpus replay)
  • benchmarks/levels-generalization-5000-bindings.bench
  • conformance/ill-typed/levels-nested-let-blowup.fixture (§8.11's exponential case, used here to confirm levels don't change correctness on the pathological case, only Phase 11 addresses its performance)

18.6 Pitfalls

  • Forgetting the level-lowering propagation step (§18.2 step 3), which is the classic OCaml levels bug class — causes unsound over-generalization (a variable that should be pinned to an outer scope gets generalized anyway), a direct I3/I4-adjacent regression that is easy to miss because most simple test programs don't exercise it.
  • Off-by-one level bracketing (incrementing after, not before, entering the RHS), silently shifting every subsequent generalization decision by one scope.
  • Trusting the levels implementation without the differential oracle against the naive scan — levels bugs are exactly the kind of error that "looks right" on hand-checked small examples while being wrong on deep nesting.

18.7 Performance Concerns

  • Level-lowering itself must not become an O(|type|) traversal repeated on every bind in a way that erases the asymptotic win — it should piggyback on the occurs-check traversal already happening in bind (Phase 2), not add a second full pass.
  • Level metadata adds a u32 per TyVar — negligible on the §4 memory ceiling but worth confirming via the benchmark suite.

18.8 Edge Cases

  • A type variable whose level is lowered multiple times across nested binds — must converge to the minimum, not the most recent.
  • Top-level (level-0) bindings — the boundary condition where "deeper than ambient" degenerates to "any level > 0."

18.9 Failure Analysis

A levels-related soundness bug typically surfaces as a fixture that passed under Phase 4's naive scan silently changing its inferred type (usually becoming more polymorphic than it should) under levels — the differential property test (§18.2 step 6) is specifically designed to catch this class before it reaches Phase 7's principal-type verification.

18.10 Operational Notes

Metrics: generalize_level_scan_size (should stay near-constant regardless of TypeEnv size, in contrast to Phase 4's generalize_scan_env_size), plus a dashboard panel plotting both series against binding count to visually confirm the O(1) vs O(n) contrast for the differential capacity model in §34.

19.7 Performance Concerns

  • verify_principal's "perturbed re-run" strategy multiplies CI inference cost by the number of perturbations tried per fixture — budgeted and capped (documented cap: 8 perturbations per fixture) to keep the CI gate's wall-clock bounded.
  • Diagnostic rendering must not re-run any inference; it operates purely on the already -captured InferError and trace data (P7).

19.8 Edge Cases

  • A fixture with no valid alternative typing to compare against (an already-maximally- general monotype, e.g. Int) — verify_principal trivially passes but must not silently skip the check (explicit "vacuously verified" telemetry tag).
  • Two fixtures producing diagnostics for the same underlying bug in different syntactic forms — ordering must still be deterministic per-session, not globally deduplicated in a way that hides one.

19.9 Failure Analysis

A verify_principal failure is treated with the same severity as a differential-oracle mismatch (I5's telemetry class, §26) — it means the engine's own generalization or unification logic produced a non-principal type, which is a direct violation of the project's core guarantee (P1), not a cosmetic bug.

19.10 Operational Notes

Metrics: principal_type_verify_total, principal_type_verify_fail_total (I1's telemetry, now actually populated by a real subsystem), diagnostic_render_latency_ms. This phase's CI gate becomes the permanent regression backbone referenced by every subsequent phase's §N.4/§N.5.

20. Phase 8 — Recursive Types and let rec

20.1 Objectives

  • Implement let rec (§11's AstExpr::LetRec), removing Phase 4's placeholder rejection (§16.2 step 11), per ADR-11's fixpoint-then-generalize strategy.
  • Preserve I4 (value restriction) for recursively-bound functions.

20.2 Detailed Implementation Steps

  1. Implement the LetRec typing rule: allocate a fresh TyVar α for the recursive binder before inferring its own body, add x : α (monomorphic, unquantified) to Γ, infer e1 under that extended Γ, unify the inferred type of e1 with α (the fixpoint constraint), then generalize the now-solved α (ADR-11).
  2. Confirm the value restriction still applies at the generalization step: if e1 is not syntactically a value (a lambda, in the common recursive-function case, always is — but a recursively-defined non-function value is not), monomorphize per I4.
  3. Extend hm-diagnostics with a specific InferError rendering for a fixpoint unification failure (a genuinely non-terminating/ill-typed recursive definition, e.g. let rec x = x + 1 in x-shaped non-function recursion without a base case type mismatch).
  4. Add the canonical worked example: let rec fact = λn. if iszero n then 1 else n * fact (n - 1) in fact inferring Int -> Int (using if/iszero/arithmetic primitives introduced as fixed-signature built-ins for this fixture set only).
  5. Add a polymorphic-recursion negative fixture: a function recursively calling itself at a different instantiation than its own binder's monomorphic type — confirm it is correctly rejected (HM's let rec is not polymorphic-recursion-capable; that is a documented, deliberate non-goal here, distinct from Dependent-239's much richer inference).
  6. Add mutual recursion support: let rec f = ... and g = ... in ..., threading both binders' fixpoint TyVars into the shared environment before either body is inferred.
  7. Add property test: every accepted let rec fixture's generalized type is verified principal via Phase 7's verify_principal (cross-phase reuse, not a new checker).
  8. Extend hm-trace with a FixpointUnify event distinct from ordinary Equality constraints, for trace-viewer clarity.
  9. Benchmark let rec-heavy programs (a synthetic mutual-recursion cluster of 50 functions) against the §4 latency targets.
  10. Add 12 example programs: single recursion, mutual recursion, the polymorphic- recursion rejection case, and a value-restriction-in-let rec edge case.

20.3 Deliverable

Working let rec/mutual recursion, correctly fixpoint-typed, generalized, and value- restriction-aware, verified principal via the Phase 7 checker.

20.4 Acceptance Criteria

  • fact's worked example infers exactly Int -> Int and passes verify_principal.
  • The polymorphic-recursion negative fixture is deterministically rejected with a Clash naming the conflicting instantiation.
  • Mutual recursion (2-cycle and 5-cycle fixtures) type-checks correctly and deterministically.
  • 100% of the 12 example programs match expected accept/reject outcomes.

20.5 Conformance Fixtures

  • conformance/well-typed/letrec-factorial.fixture
  • conformance/ill-typed/letrec-polymorphic-recursion.fixture
  • conformance/well-typed/letrec-mutual-5-cycle.fixture
  • conformance/well-typed/letrec-value-restriction.fixture

20.6 Pitfalls

  • Generalizing the recursive binder's type before the fixpoint unification with the body completes, which can generalize variables the body's recursive call will later need to constrain — a direct soundness bug distinct from, but similar in flavor to, the ordinary value-restriction hole (I4).
  • Mutual recursion implemented as two sequential let recs instead of one shared extended environment, silently breaking cases where f and g call each other.
  • Treating let rec as automatically eligible for polymorphic recursion (assuming every self-call is fine at any instantiation) — HM's let rec is deliberately monomorphic-within-its-own-body; only the outside use sites see the generalized scheme.

20.7 Performance Concerns

  • Mutual-recursion clusters require holding N fixpoint TyVars live simultaneously before any unification resolves them — memory-bounded by cluster size, tracked against the §4 type-variable-count ceiling for large clusters.
  • The fixpoint unification step can cascade through a large function body's constraint set; benchmarked explicitly rather than assumed cheap.

20.8 Edge Cases

  • let rec x = x in x — a trivial, technically well-typed (but useless) self-loop at type ∀a. a only if never used at conflicting instantiations; otherwise a clash.
  • A let rec whose body never actually recurses (a non-recursive function written with rec unnecessarily) — must type identically to the non-rec form.
  • Deep mutual-recursion clusters (100+ functions) — a stress fixture for the fixpoint environment extension step.

20.9 Failure Analysis

A let rec unsoundness typically manifests as a program that should be rejected for polymorphic recursion instead type-checking with an over-general scheme — the debugging methodology directs first checking whether the fixpoint unification (§20.2 step 1) ran to completion before generalization, per the pitfall in 20.6.

20.10 Operational Notes

Metrics: letrec_fixpoint_unify_total, letrec_mutual_cluster_size (histogram). Cross- referenced against Phase 7's principal_type_verify_fail_total to catch any regression introduced by recursive-binder generalization.

21. Phase 9 — Row Polymorphism (Records)

21.1 Objectives

  • Extend the type system with row-polymorphic records (§8.10, §11's Row/RowVar), per Rémy 1989's row-variable-with-lacks-constraint design (ADR-09).
  • Preserve I8: core-language terms' inferred types are unaffected by the extension being enabled.

21.2 Detailed Implementation Steps

  1. Extend hm-ast with record literal ({ field = expr, ... }) and field-projection (expr.field) syntax.
  2. Extend hm-types::Row (§11) with fields: BTreeMap<Symbol, TypeId> and an optional tail: RowVar for open (extensible) rows.
  3. Implement RowLacks constraint generation for projection: projecting .field from an open row requires only that the row contains field, not that it matches exactly (the source of row polymorphism — a function projecting .x works on any record that has an x field, regardless of what else it has).
  4. Implement row unification: two closed rows unify iff same field set with pairwise- unifying types; an open row unifies with any row containing at least its known fields, unifying the tail with the remainder (Rémy-style row unification, cited directly).
  5. Implement hm-diagnostics::RowMismatch for a missing/incompatible field, with provenance naming both the projection site and the record's construction site.
  6. Add the canonical worked example: λr. r.x infers ∀a b. { x : a | b } -> a (row-polymorphic — usable on any record with at least an x field) — printed via an extended pretty-printer supporting row syntax.
  7. Wire row generalization/instantiation through the same generalize/instantiate machinery from Phase 4/6 (extended to also quantify/freshen RowVars), rather than a parallel implementation — directly operationalizing P8's "separate what must be true from how we solve it."
  8. Add the I8 conservativity property test: run the full Phase 0–8 core corpus with the row extension compiled in but unused, assert byte-identical inferred types to a row-extension-disabled build.
  9. Add 15 example programs: field projection, record construction, row-polymorphic function composition, and a row-mismatch negative fixture.
  10. Add property test: row unification is symmetric and produces the same canonical row regardless of argument order.
  11. Benchmark row-heavy programs (records with 50+ fields) against the §4 memory/ latency targets.
  12. Document the row-vs-nominal-record ADR-09 tradeoff inline where the row grammar is defined, for future extension authors.

21.3 Deliverable

Row-polymorphic records: literals, projection, row unification, and generalization, integrated into the existing Algorithm-W/unification pipeline without regressing the core language (I8).

21.4 Acceptance Criteria

  • λr. r.x infers exactly ∀a b. { x : a | b } -> a (fixture match, canonical print).
  • I8 conservativity property test: 100% identical core-corpus types with the extension compiled in vs. out.
  • The row-mismatch negative fixture ({ y = 1 }.x) is deterministically rejected with RowMismatch.
  • 100% of the 15 example programs match expected outcomes.

21.5 Conformance Fixtures

  • conformance/well-typed/rows-field-projection.fixture
  • conformance/well-typed/rows-composition.fixture
  • conformance/ill-typed/rows-missing-field.fixture
  • conformance/regression/rows-core-conservativity.fixture (I8's dedicated gate)

21.6 Pitfalls

  • Implementing rows as closed (fixed-field) types by default, accidentally losing polymorphism and forcing every record-consuming function to be monomorphic in its field set — defeats the entire point of ADR-09's choice.
  • Forgetting to thread RowVar freshness through instantiate (Phase 4/6's machinery extended in step 7), silently capturing row variables across unrelated use sites — the row-polymorphism analogue of I11.
  • A row-unification implementation that mutates one side's field map in place instead of producing a new canonical row, breaking P9's interning/immutability discipline.

21.7 Performance Concerns

  • Row unification with large field sets (BTreeMap comparison) is O(fields) per unification step — acceptable per §4's constraints but must be benchmarked, not assumed, once field counts exceed the common case (~10 fields).
  • Row-polymorphic function composition can accumulate long row-variable chains through the union-find forest, interacting with the occurs check's traversal cost (Phase 2).

21.8 Edge Cases

  • An empty record {} — the degenerate closed row with no fields.
  • A record literal used both as a fully closed argument and, elsewhere, row- polymorphically — must not force premature closure of the row variable.
  • Two structurally different but field-set-identical records — must unify as the same row type regardless of field-declaration order (BTreeMap ordering handles this).

21.9 Failure Analysis

A row-extension bug that violates I8 (core corpus regression) is treated with the same severity as any other principal-type failure (§19's gate) — the extension is conservative by construction requirement (P12), so any core regression blocks merge regardless of how the row feature itself behaves.

21.10 Operational Notes

Metrics: row_unify_total, row_lacks_constraints_total, row_field_count (histogram, feeding the §30 performance-targets table for row-heavy workloads).

22. Phase 10 — Type Classes / Qualified Types (HM(X))

22.1 Objectives

  • Extend the type system with qualified types ∀ᾱ. π ⇒ τ (§11's Qualified/ Predicate) for single-parameter type classes, per Wadler & Blott 1989 and Odersky, Sulzmann & Wehr 1999's HM(X) framing (ADR-10).
  • Preserve I8-style conservativity for the class-free core, and define what "principal" means once qualifiers are present (§8.10's caveat, resolved here).

22.2 Detailed Implementation Steps

  1. Extend hm-ast/parser with a minimal class-declaration and instance-declaration surface (e.g. class Eq a where eq : a -> a -> Bool; instance Eq Int where ...) sufficient to drive inference — instance elaboration/dictionary construction is out of scope beyond what's needed to validate typing (full evidence/dictionary- passing codegen is a compiler concern, per §1's boundary).
  2. Extend Constraint with Predicate(ClassId, TypeId, NodeId) (§11), generated whenever a class method is used at a not-yet-resolved type.
  3. Implement deferred predicate resolution (ADR-07/ADR-10): predicates accumulate during constraint generation and are resolved (checked against known instances or left as part of the generalized scheme) at the enclosing let's generalization step, per Wadler & Blott 1989's dictionary-passing account (adapted here to a typing-only, non-codegen form).
  4. Implement generalize for qualified types: quantify ᾱ as before (§8.5), and carry forward any predicates over ᾱ that could not be resolved to a known instance, producing ∀ᾱ. π ⇒ τ rather than a bare ∀ᾱ. τ.
  5. Implement instantiate for qualified schemes: freshen ᾱ and re-emit the predicates over the fresh variables as new Predicate constraints at the use site.
  6. Implement hm-diagnostics::UnresolvedPredicate for a predicate that can never be resolved (no matching instance exists for a fully-monomorphic type) — this is the qualified-type analogue of Clash.
  7. Extend verify_principal (Phase 7) to compare qualified schemes: σ' is a generic instance of σ = ∀ᾱ. π ⇒ τ only if it instantiates ᾱ and discharges/preserves π correctly — documenting precisely how §8.7's theorem statement is generalized to HM(X) (with the explicit caveat that full principal-qualified-types results are more delicate than plain HM and are validated empirically here, not proved from scratch).
  8. Add the canonical worked example: λx. λy. eq x y under a single Eq class infers ∀a. Eq a ⇒ a -> a -> Bool.
  9. Add I8-style conservativity property test: class-free core corpus produces byte-identical types whether the extension is compiled in or out.
  10. Explicitly scope out and document as non-goals (P8, §1): superclasses, functional dependencies, overlapping instances, multi-parameter type classes — all four flagged PhaseDeferred("§22 Phase 10 — Type Classes / Qualified Types (HM(X))") in §37 under the consolidated "Full type-class resolution" register row.
  11. Add 12 example programs: single-class usage, unresolved-predicate rejection, qualified-scheme generalization/instantiation round-trip, and a conservativity fixture.
  12. Benchmark predicate-resolution cost against §4's latency targets on a moderate-sized class hierarchy (5 classes, 10 instances).

22.3 Deliverable

Single-parameter qualified types integrated into generalization/instantiation and verify_principal, with documented, deliberate non-goals for richer class-system features.

22.4 Acceptance Criteria

  • The eq-based worked example infers exactly ∀a. Eq a ⇒ a -> a -> Bool.
  • The unresolved-predicate negative fixture (e.g. calling eq on a type with no Eq instance) is deterministically rejected with UnresolvedPredicate.
  • I8-style conservativity: 100% identical core-corpus types with/without the class extension compiled in.
  • 100% of the 12 example programs match expected outcomes.

22.5 Conformance Fixtures

  • conformance/well-typed/classes-eq-qualified-scheme.fixture
  • conformance/ill-typed/classes-unresolved-predicate.fixture
  • conformance/regression/classes-core-conservativity.fixture
  • conformance/well-typed/classes-instantiate-fresh-predicate.fixture

22.6 Pitfalls

  • Resolving predicates eagerly at first use instead of deferring to the enclosing generalization point, which breaks legitimately polymorphic class-constrained functions (resolving too early forces a concrete instance where none should be chosen yet).
  • Treating "no instance found" and "ambiguous, multiple instances match" identically — these are different failure modes (UnresolvedPredicate vs. a documented-but-out-of- scope overlap case) and conflating them produces misleading diagnostics.
  • Silently dropping predicates during generalization instead of carrying them into the scheme, which produces an unsoundly unqualified (too general) type — a direct analogue of the I3 violation risk, specific to this extension.

22.7 Performance Concerns

  • Predicate accumulation across a deeply nested expression can grow large before resolution at the enclosing let; bounded by the same node-count constraints as §4 but explicitly benchmarked here since it's a new growth dimension.
  • Instance lookup (matching a predicate's type against known instances) must not become a linear scan of every instance in large hierarchies — indexed by ClassId at minimum.

22.8 Edge Cases

  • A predicate over a variable that is never generalized (because the enclosing binding fails the value restriction, Phase 5) — must still be checked, not silently discarded, at the ambient monomorphic level.
  • Two predicates over the same class and same variable arising from different call sites — must be deduplicated before being carried into the scheme.
  • A class method used entirely within a single monomorphic context with a concrete, resolvable instance — the predicate should fully resolve and not appear in the final scheme at all.

22.9 Failure Analysis

An unsound qualified-type bug (a scheme missing a predicate it should carry) typically manifests as verify_principal accepting an alternative typing that is not a valid qualified instance of the engine's output — Phase 7's extended checker (§22.2 step 7) is the first line of detection, escalated with the same severity as a plain-HM principal-type failure.

22.10 Operational Notes

Metrics: predicate_constraints_generated_total, predicate_resolved_total, predicate_unresolved_total, instance_lookup_latency_ms.

23. Phase 11 — Conformance Corpus, Differential Check, and Performance Hardening

23.1 Objectives

  • Assemble the complete well-typed/ill-typed conformance corpus accumulated across Phases 0–10 into a single CI-gated suite (ADR-13, §28).
  • Build the differential-testing harness comparing this engine's accept/reject decisions and principal types against OCaml's and GHC's inference on shared fixtures (I5's authoritative check).
  • Perform the performance-hardening pass against every §4/§30 target.

23.2 Detailed Implementation Steps

  1. Consolidate all conformance/well-typed/ and conformance/ill-typed/ fixtures from Phases 0–10 into hm-conformance's single runner, tagged by originating phase.
  2. Implement the differential-oracle harness (hm-conformance::differential): for each shared fixture, shell out to ocaml/ocamlfind ocamltop (or a small OCaml driver script) and to ghc/runghc (or ghci), capture accept/reject and, where accepted, the printed principal type; normalize printed types (canonical variable naming) before comparison.
  3. Curate the shared-fixture subset: core HM programs expressible identically in this language, OCaml, and Haskell (necessarily excludes this project's row/qualified-type extensions, which have no exact OCaml/GHC syntactic equivalent — documented explicitly as a differential-scope limitation).
  4. Wire the differential harness as a CI job (conformance.yml, §10) gated on every PR, with differential_mismatch_total == 0 as a hard merge gate (I5).
  5. Implement the fuzz campaign: parser fuzzing (structural coverage) plus a random well-typed-term generator that builds terms from known-good types (so every generated term is expected-accepting) to fuzz for false rejections — the "inference reflexivity" property, tied to I5 and the §28 property-testing gate.
  6. Run a scheduled (nightly) extended fuzz campaign (fuzz.yml) and triage any crash or property violation within 24 hours per the runbook (§26).
  7. Performance-harden: replace any remaining recursive AST/traversal code flagged in earlier phases' Performance Concerns sections with iterative, explicitly-budgeted versions where profiling shows it matters (P13).
  8. Run the full §30 performance-targets table (M1–M14) against the reference machine and record actual vs. target for each; file follow-up work for any miss.
  9. Implement perf-regression gating in CI: benchmark deltas beyond a documented threshold (10%) block merge (§28, §29).
  10. Run the exponential-blowup nested-let fixture (§8.11, §18.5) at increasing depth and confirm the measured growth curve matches the DEXPTIME-worst-case/near-linear- practical characterization in §4/§31, recording the crossover point.
  11. Produce the final docs/performance/ report summarizing §34's capacity model against measured numbers.
  12. Freeze the conformance corpus size and composition as the permanent regression baseline for any future phase.

23.3 Deliverable

A complete, CI-gated conformance corpus; a working OCaml/GHC differential-testing harness with zero open mismatches; a performance-hardened engine meeting or explicitly documenting exceptions to every §30 target.

23.4 Acceptance Criteria

  • differential_mismatch_total == 0 across the full shared-fixture set (numeric gate, currently sized at ≥ 150 shared fixtures spanning Phases 0–8's core language).
  • Zero fuzz-found panics or property violations across a 24-hour nightly campaign before this phase is marked complete.
  • ≥ 90% of §30's M1–M14 targets met exactly; any miss has a filed, documented follow-up with root cause.
  • The nested-let blowup fixture's measured growth curve is recorded and matches the documented theoretical characterization within an order of magnitude at n=20.

23.5 Conformance Fixtures

  • conformance/differential/* (the full shared-fixture set)
  • benchmarks/full-suite-perf-report.bench
  • conformance/regression/nested-let-blowup-growth-curve.fixture
  • fuzz/corpus/parser/ and fuzz/corpus/unify/ (accumulated nightly-campaign corpus)

23.6 Pitfalls

  • A differential harness that silently swallows OCaml/GHC subprocess failures (missing toolchain, timeout) as "match" instead of "inconclusive" — must fail loudly and distinctly from a genuine mismatch.
  • Normalizing printed types too aggressively when comparing across engines (e.g. treating any two polymorphic types as "equivalent enough"), which would mask real discrepancies and defeat the purpose of I5's check.
  • Chasing every last percentage point of the §30 targets at the cost of the P4/P9 invariants (e.g. introducing in-place type mutation for speed) — performance hardening must never regress a system invariant from §7.

23.7 Performance Concerns

  • The differential harness's subprocess-shelling cost (spawning ocaml/ghc per fixture) is itself a CI-time cost, not a product-latency concern — batched/cached across CI runs where the shared-fixture set is unchanged.
  • Fuzzing campaigns are resource-intensive; scheduled nightly rather than per-PR to keep the PR feedback loop within the CI wall-clock budget from Phase 0.

23.8 Edge Cases

  • A shared fixture that OCaml and GHC themselves disagree on (rare, but possible for edge-of-spec behavior) — documented as a known engine-choice divergence, not treated as this project's bug, with the disagreement itself recorded in docs/failure-analysis/.
  • A performance target met on the reference machine but missed on CI's shared runners — tracked separately, with the reference-machine number as the authoritative §30 figure.

23.9 Failure Analysis

Any differential_mismatch_total > 0 is escalated per §26's page-immediately correctness-event class — this phase's entire purpose is making that counter the project's ultimate soundness/completeness oracle, so a mismatch here is never triaged as "low priority."

23.10 Operational Notes

Metrics: differential_mismatch_total, differential_inconclusive_total, fuzz_campaign_crashes_total, perf_regression_blocked_total. This phase's dashboards (§26) become the steady-state operational picture for the finished engine.

27. Compatibility & Versioning

Source-language version: the grammar in §8.1 plus its Phase 8–10 extensions is the v1 source language; any grammar-breaking change (new reserved word, changed precedence) is a major version bump.

Inference-algorithm stability: the externally observable behavior — which programs are accepted, and what principal type each infers to — is the stability contract, not the internal algorithm (Algorithm W vs. the constraint-based formulation, ADR-02, are free to change internally as long as I1/I5 and the differential suite hold).

Extension-set versioning: rows (Phase 9) and qualified types (Phase 10) are each independently versioned feature flags; enabling a newer extension version must not change core-language typing (I8) and is itself differential-tested against its own prior version's fixture set before promotion.

Error-format stability: InferError's variant set is additive-only within a major version (new variants may be added; existing ones are never removed or repurposed) per ADR-08's provenance guarantee; diagnostic text may improve within a minor version but snapshot tests are versioned alongside the release so consumers can diff.

API stability: hm-infer/hm-types/hm-unify's public signatures (§11) follow SemVer; TyVar/RowVar/NodeId remain explicitly session-local and out of the compatibility contract (ADR-14) — no consumer may persist them across versions.

Migration: a major-version bump ships a migration note in CHANGELOG.md describing any grammar or InferError taxonomy change; there is no automated migration tool since there is no persisted cross-version state to migrate (§26).

SemVer: major = breaking grammar, breaking InferError taxonomy, or a change to which programs are accepted/rejected; minor = additive extensions, new diagnostics, new primitives; patch = performance improvements, diagnostic text refinements, and bug fixes that only make previously-nonconformant behavior conformant (i.e. patch releases only ever move toward I1/I5, never away).

28. Testing & Verification Strategy

Unit testing: every crate from §10 has unit coverage for its own signatures — hm-types interning identity, hm-unify::bind/unify dispatch, hm-infer::generalize/ instantiate, hm-diagnostics rendering per InferError variant.

Integration testing: full parser-to-diagnostic pipeline runs over the accumulated conformance corpus (§23), gating every PR.

Property testing — the defining properties, each tied to a specific I# and a phase's §N.5 fixtures:

  • Every inferred type is principal (I1) — checked by verifying all other valid typings (generated via perturbed solving order, §19.2 step 2) are generic instances of the engine's output; tied to Phase 7 fixtures (§19.5).
  • A well-typed program is always accepted and an ill-typed one always rejected (I5) — checked by the Phase 11 differential oracle against OCaml/GHC; tied to §23.5 fixtures.
  • Unification produces a most-general unifier — checked by confirming any other unifier for the same pair factors through the engine's result (a substitution-composition property); tied to Phase 2 fixtures (§14.5).
  • Inference is deterministic (I7, I11) — checked by replay-diff across repeated runs of the same input; tied to Phase 1/2/4 fixtures (§13.5, §14.5, §16.5).
  • The occurs check always terminates (I10) — checked by a step-budget property test over a fuzz-generated type corpus; tied to Phase 2 fixtures (§14.5).

Conformance corpus: the well-typed/ill-typed corpus (§23) is a named CI gate (conformance.yml) — every accumulated fixture from Phases 0–10 runs on every PR.

Differential testing: OCaml and GHC inference on the shared corpus (§23.2 steps 2–4) — same accept/reject decision and equivalent (up to alpha-renaming and, for qualified types, predicate-context) principal types; differential_mismatch_total == 0 is a hard merge gate (I5).

Fuzzing: the parser (structural/UTF-8 robustness, T5/FM-5) and a random well-typed-term generator that constructs terms from known types, then checks the engine reflects the same type back (inference reflexivity) — both scheduled nightly (fuzz.yml) with 24-hour crash triage SLO (§26).

Chaos: intentional corruption of the union-find forest / interned type arena in a test-only harness to confirm the corruption-detection assertions (§14.2 step 13) actually fire rather than silently propagating.

Deterministic replay: every conformance/differential fixture's hm-trace output is archived and re-diffed on the next run of the same engine version, catching any silent nondeterminism regression (I7) before it reaches the differential oracle.

Soak: a long-running REPL session soak test (10,000 sequential top-level expressions) checking for unbounded memory growth in the type arena/union-find forest (§4's memory ceiling) absent any incremental/caching layer (ADR-14 means no cache to leak, but the arena itself must be bounded or explicitly reset per session).

Fault injection: simulated OCaml/GHC subprocess failure in the differential harness (§23.6) verified to surface as "inconclusive," never silently as "match."

Perf-regression gating: benchmark deltas beyond 10% block merge (§23.2 step 9), tied to the §30 M1–M14 targets.

30. Performance Engineering

Methodology: union-find operations are near-linear amortized (inverse-Ackermann per op, Robinson 1965 plus standard union-find analysis); the levels/ranks trick (Phase 6, Rémy 1989) makes generalization O(1)-amortized per let instead of the naive O(|Γ|) free-variable scan; substitution reads are O(size of type) via canonicalization (I9), paid once per read, not accumulated across reads because the union-find forest itself is the composed substitution (§8.6); the exponential worst case (Mairson 1990, §8.11/§31) is real but empirically rare — the Phase 11 growth-curve benchmark (§23.2 step 10) exists specifically to characterize where the crossover from "practical" to "pathological" actually falls on this implementation, rather than relying on the asymptotic bound alone; tail behavior on deep terms is dominated by occurs-check traversal depth and AST-walk recursion depth, both budgeted (P13) to convert a potential unbounded-latency tail into a bounded, diagnosable rejection.

31. Scalability Analysis

What stays constant regardless of program size: the shape of the typing rules (§8.2) and the unification algorithm (§8.4) — these are the same four rules and the same U0–U5 dispatch whether the input is 10 nodes or 200,000. What grows: type-variable count (roughly linear in AST node count, absent generalization-driven sharing), union- find forest size (linear in type-variable count, but operations on it are near- constant amortized via inverse-Ackermann), and — in the worst theoretical case — printed type size itself, which the nested-let construction (§8.11) can double per level, giving O(2^n) for n nested lets (Mairson 1990's DEXPTIME-completeness result for HM type inference in the worst case). In practice, real programs do not construct adversarial doubling chains, and Phase 11's growth-curve benchmark (§23.2 step 10, M12) exists to make "in practice" a measured claim rather than an assertion.

Named bottlenecks: (1) the naive pre-Phase-6 generalization scan, eliminated by levels/ranks; (2) occurs-check traversal depth on deeply nested types, bounded by P13's depth budgets; (3) row/predicate constraint accumulation in Phases 9–10, which grows with feature usage rather than raw program size and is budgeted separately (§30 M10/ M11); (4) the differential oracle's subprocess-shelling cost, a CI-time bottleneck only, never a product-runtime one.

Practical program-size ceiling and the levers beyond it: the engine is validated up to the §4 ceilings (200,000 AST nodes, 2,000,000 live type variables); beyond that, the documented lever is incrementality — explicitly out of scope for this project (ADR-14) and deferred to a sibling IDE/build-system integration project that would reuse hm-infer's core but add a Salsa-style query layer on top, re-inferring only changed sub-trees rather than the whole program.

32. Mental Models & First Principles

MM1. Type inference is constraint solving — you walk the AST emitting equalities between types and hand them to unification, and the "algorithm" is just the order you do that in (Wand 1987). Algorithm W, Algorithm J, and the constraint-based HM(X) formulation (ADR-02) are three different orders, not three different theories.

MM2. let is where polymorphism is born: generalize at let, instantiate at use, and the entire expressive power of HM lives in that one rule (Damas & Milner 1982, §8.2's Let). Every other rule (Var/App/Abs) is ordinary simply-typed lambda calculus.

MM3. The value restriction is not elegant — it is a patch. It exists because unrestricted generalization plus mutable references is unsound, and every ML dialect carries the scar (Wright 1995, §8.8). Understanding why it's a patch (rather than memorizing the syntactic-value rule) is what lets you predict its edge cases.

MM4. Unification is search with no backtracking: Robinson's algorithm never guesses — every step is forced by the structure of the two types being compared (§8.4). If a step ever requires choosing between two possible bindings, that is a sign the type system has moved beyond plain HM (e.g. into overloading, Phase 10).

MM5. A principal type is a proof object, not just an answer — the Damas–Milner theorem (§8.7) says the inferred type dominates every other valid typing, which is why verify_principal (Phase 7) can be built as an automated checker at all: principality is a checkable relation (generic-instance), not a vibe.

MM6. Levels/ranks are a scoping trick disguised as a performance trick — they encode "which lexical scope could this variable have come from" as a cheap integer comparison, replacing an expensive free-variable-set computation with an O(1) check (Rémy 1989, Phase 6). The performance win and the scoping-correctness question are the same question asked two ways.

MM7. Extensions to HM are additions to the constraint language, not replacements for the solver — row polymorphism and qualified types both work by adding a new constraint form (RowLacks, Predicate) solved by a new pass layered next to, not instead of, the core unifier (Pottier & Rémy 2005's HM(X) view, §8.10). This is why P8/P12 insist on conservativity: an extension that has to rewrite the core solver has stopped being "HM plus X" and become something else.

MM8. DEXPTIME-completeness and "HM inference is fast in practice" are both true and not in tension — the worst case requires an adversarial construction (§8.11) that no one writes by accident; the near-linear behavior on realistic code is why the industry adopted HM at all, and the gap between the two is exactly what §31/§34 quantify rather than assert.

MM9. A differential oracle is more convincing than a hand proof for an implementation (as opposed to the algorithm itself) — Damas & Milner's proof is about the algorithm; whether this specific Rust code correctly implements that algorithm is an empirical question, best answered by comparing against two independent production implementations (OCaml, GHC) on a shared corpus (Phase 11, I5).

Standard ML's SML/NJ is the historical-lineage contrast: the value restriction itself (Wright 1995, Phase 5) was adopted first in the SML world in response to the same unsoundness this project's §8.8 fixture demonstrates, making SML/NJ the direct ancestor of Phase 5's design rather than a mere comparison point.

34. Back-of-Envelope Capacity Model

Unification cost for a 5,000-node module: assume ~1 constraint per AST node (conservative for App/Abs/Let) → 5,000 constraints; union-find cost per constraint is O(α(n)) ≈ 4 effective operations at this scale (inverse-Ackermann is ≤4 for any n representable in physical memory) → ≈ 20,000 effective union-find steps → at the M3 target of 10,000,000 ops/sec, that's 2 microseconds of raw unification work, confirming that unification itself is not the dominant cost at this scale (parsing and constraint generation dominate instead — consistent with M2's 150ms budget being mostly non-unification overhead plus safety margin).

Generalization cost with levels vs. naive: naive scan is O(|Γ|) per let; for a module with an average environment depth of 50 bindings and 500 let-expressions, naive cost is 50 × 500 = 25,000 scan-steps; levels cost is O(1)-amortized per let (scanning only the bound expression's own free variables, typically ≤5) → 500 × 5 = 2,500 steps — a 10x reduction at this modest scale, growing to a 100x+ reduction as environment depth grows independently of per-binding type complexity (exactly the scaling gap benchmarked in §18.2 step 7 and M6).

Exponential-blowup nested-let worked example: the construction let x1 = λy.(y,y) in let x2 = λy.(x1 y, x1 y) in ... let xn = ... doubles the printed type size at each level — size(x_k) ≈ 2 · size(x_{k-1}), so size(x_n) = O(2^n). At n=20, that is 2^20 ≈ 1,048,576 — a printed type over a million nodes from a program of only 20 lets. This is why M12 targets recording the observed crossover point rather than the asymptotic bound alone: real programs essentially never construct this shape, but a fuzzer or adversarial input could, so the engine must convert the failure into a bounded, diagnosable rejection (P13) well before physical memory exhaustion, not rely on "it's rare" as a safety argument.

Type-variable count for a program of N AST nodes: each Var/Abs/App node allocates at most 1–2 fresh type variables (per §8.3's step pattern); for N=200,000 (the §4 ceiling), that's an upper bound of ≈ 400,000 live variables before any are resolved away by unification — well under the 2,000,000 (M9) ceiling, leaving headroom for generalization-driven variable retention (quantified variables in long-lived schemes are not reclaimed until the scheme itself goes out of scope).

Substitution memory: each union-find node is a TyVar (4 bytes) + parent pointer (4 bytes) + rank (1 byte) + optional bound TypeId (4 bytes) ≈ 13 bytes/variable (padded to 16); at the 400,000-variable estimate above, that's ≈ 6.4 MB for the substitution forest alone — a small fraction of the 64 MB (M8) memory ceiling, with the remainder budgeted to the AST arena, interned Type/TypeScheme store, and row/ predicate constraint bookkeeping.

Inference latency for a realistic module (5,000 nodes): parsing at the M13 target (>20 MB/s) processes a typical 5,000-node/≈150KB source file in <10ms; constraint generation is a single linear AST walk, budgeted at ≈1μs/node → 5ms; unification, per the first calculation above, is negligible (~microseconds); generalization with levels (second calculation) is similarly negligible; the remaining budget to the 150ms (M2) target is intentional safety margin for diagnostics, tracing overhead, and the row/predicate extension passes when enabled.

Winning regime: type systems with multiple, mutually-interacting extensions (type classes, GADTs, type families simultaneously) where generation and solving must be fully decoupled to stay tractable. Real embodying system: GHC's OutsideIn(X) (§33). Why partially adopted, not fully: this project does adopt the constraint-based generate-then-solve shape for its extensions (ADR-02, ADR-07) but keeps the core Var/App/Abs/Let path close to classic Algorithm W's directness (§8.3) for pedagogical clarity and to keep the §8.3 worked example legible by hand — a full OutsideIn(X)-style architecture for the entire engine, including the four core rules, was rejected as disproportionate machinery for a system with only two small extensions.

Local Type Inference / No Let-Generalization

  Var --lookup(monotype only)--> App --unify--> Abs --unify--> (no generalize step)

Winning regime: simple scripting-language type inference where full let-polymorphism is not needed and a monomorphic-per-binding model is acceptable — local/contextual inference within a function body, generalization handled separately or not at all. Real embodying system: TypeScript's local and contextual inference (no let-generalization — generics are declared, never reconstructed at a let); Go's := short-variable-declaration inference, monomorphic per binding by construction. Why rejected here: this is precisely the "monomorphic inference would reject" case worked through in §8.9 — dropping let-generalization would make the engine unable to type let id = λx. x in (id 3, id true), which is the textbook demonstration of HM's core value proposition; a project about HM inference without let-polymorphism is a different, lesser project.

Full Annotation, No Inference (System F)

  Λα. λ(x:α). x  : ∀α. α -> α        -- every quantifier and every
                                        parameter type written by hand

Winning regime: systems requiring impredicative or higher-rank polymorphism, where full type inference is undecidable (Wells 1994) and the honest engineering answer is "the programmer writes the types." Real embodying system: GHC Core (System FC) — the fully type-annotated intermediate language every Haskell program is elaborated into, where -dcore-lint type-checks with zero inference; likewise GHC's -XRankNTypes surface extension requires explicit forall annotations at exactly the points inference can't reach. Why rejected here: zero-annotation reconstruction (P1) is the explicit product; a System-F-style fully annotated core is the polar opposite design point, useful as a contrast (cited throughout §1, §36) but not a candidate implementation for this project.

38. Glossary

Type inference: reconstructing a program's types without requiring the programmer to write them. Type reconstruction: synonym used interchangeably in the HM literature. Hindley–Milner (HM): the type system and inference algorithm from Hindley 1969 and Milner 1978, formalized by Damas & Milner 1982. Algorithm W: the classical eager, recursive inference algorithm from Damas & Milner 1982. Algorithm J: an imperative variant of W using in-place mutable unification (Milner's original formulation). Monotype (τ): a type with no universal quantifiers. Polytype / type scheme (σ): a type of the form ∀ᾱ. τ. Principal type: the most general type derivable for a term; every other valid type is an instance of it (§8.7). Generalization: converting a monotype into a type scheme by quantifying variables free in it but not in the environment (§8.5). Instantiation: replacing a scheme's bound variables with fresh ones at a use site (§8.5). Let-polymorphism: the specific mechanism by which let-bound expressions are generalized before their body is checked (§8.2, §8.9). Unification: the process of solving equality constraints between types by finding a substitution that makes them syntactically equal (Robinson 1965). Most general unifier (mgu): a unifier that every other valid unifier for the same pair factors through. Occurs check: the check preventing a type variable from being bound to a type containing itself, which would produce an infinite type (§8.4, I2). Substitution: a mapping from type variables to types, applied to eliminate variables as they are solved. Union-find: the data structure used to represent and efficiently query the current substitution (§8.6). Type variable: a placeholder standing for an as-yet-unknown monotype. Free type variable: a type variable not bound by any enclosing quantifier. Type environment (Γ): the mapping from term variables to their type schemes. Value restriction: the rule restricting generalization to syntactic values, required for soundness with mutable references (Wright 1995, §8.8). Row polymorphism: polymorphism over the field set of a record type, using row variables (Rémy 1989, §21). Qualified type: a type scheme carrying predicates, ∀ᾱ. π ⇒ τ, used to express type-class constraints (Wadler & Blott 1989, §22). Type class: a named predicate on types associated with a set of required operations. Constraint: a formal statement (equality, instance, predicate) that must hold for a term to type-check. Bidirectional typing: an alternative discipline propagating expected types down (checking mode) and inferred types up (synthesis mode), used where full HM-style inference is undecidable (§36). HM(X): the constraint-based generalization of HM parameterized by a constraint domain X (Pottier & Rémy 2005). Levels / ranks: an integer tag on each type variable recording its allocation scope depth, used to make generalization O(1)-amortized (Rémy 1989, §18). Monomorphism restriction: a related but distinct restriction (from Haskell) limiting generalization of syntactically simple bindings for a different reason than the value restriction; noted here for terminology precision, not implemented as a separate mechanism in this project. Soundness: every type the checker assigns is a valid typing under the formal type system. Completeness: every term that has a valid typing is assigned one by the checker. Prenex polymorphism: quantifiers appear only at the outermost position of a type scheme, never nested inside an arrow — the restriction that makes HM inference decidable. Type constructor (TyCon): a named, fixed-arity former of types, e.g. Int, List. Arrow type: the function-type constructor τ1 -> τ2. Canonicalization: resolving a type to its fully path-compressed, up-to-date form under the current substitution (I9). Interning: storing structurally-equal values once and comparing by identity thereafter (P9). Differential testing: comparing this engine's behavior against independent reference implementations (OCaml, GHC) on shared input (§23, §28). Conformance corpus: the accumulated set of well-typed and ill-typed fixtures used as a regression and verification baseline (§23). Principal-types theorem: the Damas–Milner 1982 result establishing that Algorithm W computes principal types (§8.7). Fixpoint typing: the technique used for let rec, unifying a recursive binder's own type variable with its inferred body type before generalizing (§20, ADR- 11). Mutual recursion: multiple let rec-bound functions defined simultaneously, sharing a single extended type environment during inference (§20.2 step 6). Dictionary passing: the standard elaboration technique for type classes, passing method implementations as an explicit runtime value (Wadler & Blott 1989); referenced for typing purposes only, since codegen/elaboration output is a compiler-backend concern (§1 Boundaries). Predicate: a class constraint on a type, Eq α, accumulated during inference and either resolved or carried into a scheme (§22). Evidence: the runtime witness for a resolved predicate (a dictionary), mentioned for completeness but not implemented (§1 Boundaries, §22.2 step 1). Alpha-equivalence: equivalence of two type schemes up to renaming of bound variables, used when comparing printed types across engines (§23.2 step 2). Path compression: the union-find optimization flattening parent chains during find, giving near-constant amortized cost (§8.6, §14). Arena allocation: bump-allocating AST/type nodes from a contiguous region for cache locality and stable handles (ADR-12). DEXPTIME-completeness: the worst-case complexity class of HM type inference (Mairson 1990), contrasted throughout with the near-linear practical behavior (§4, §31, §34).
