75 — Profiler and Distributed Tracer

Project Number: 75

Project Name: Profiler and Distributed Tracer

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a native, low-overhead, whole-fleet profiling-and-tracing runtime for compiled Linux processes (x86_64, aarch64): sample on-CPU stacks via SIGPROF/timer_create and perf_event_open(2) at up to 999 Hz with < 1% application overhead at 99 Hz (§4, M1); walk stacks through frame-pointer, DWARF CFI (.eh_frame/.debug_frame), and kernel-side ORC unwinders behind one Unwinder trait; symbolize via .symtab/.dynsym/.debug_info/ .debug_line with inline-frame expansion and Itanium/Rust-v0 demangling; record spans through an in-process SDK wire-compatible with the OpenTelemetry data model and the W3C Trace Context propagation format; attach zero-source-change via eBPF uprobes/USDT/tracepoints; export to pprof, folded-stack, Speedscope, Chrome Trace, and OTLP; and run a continuous-profiling agent and ingestion/query server across a fleet.

Phase-0 deliverable — numbered modules/crates (full names/paths in §10, §11):

  1. prof-core — process model, /proc/<pid>/maps parser, ELF module table, build-id index.
  2. prof-sample — SIGPROF/timer_create sampler, perf_event_open sampler, per-thread ring.
  3. prof-unwind — frame-pointer walker, DWARF CFI walker, Unwinder trait.
  4. prof-symbol — addr2line resolver, ELF symtab fallback, inline expansion, demangling.
  5. prof-aggregate — StackTable, per-stack counters, folded-stack and flamegraph writers.
  6. prof-pprof — google/pprof/profile.proto builder and gzip writer.
  7. prof-trace-sdk — Tracer/Span/Context, W3C traceparent propagator, batcher.
  8. prof-otlp — OTLP/HTTP exporter (OTLP/gRPC gated behind a feature flag).
  9. prof-cli — the prof operator binary (record, report, flamegraph, trace).

System boundaries.

  • Provides: in-process sampling (signal + hardware-counter), stack unwinding, symbolization, span recording, OTLP export, pprof/flamegraph rendering, a single-tenant continuous-profiling agent and query server.
  • Delegates: long-term trace/metric storage and cross-signal correlation UI to an external APM (this runtime is the producer, not the warehouse); kernel BPF verification to the kernel; DWARF parsing to gimli-rs; protobuf codegen to prost-build.
  • Does NOT provide (non-goals): a JVMTI/managed-runtime agent, a Python setprofile hook, a Ruby tracer, machine-learned auto-instrumentation, cross-vendor APM request stitching, macOS/ Windows support in Phase 0, RISC-V support in Phase 0.

Deployment model: a per-host/per-container sidecar or linked-in library (prof-agent) supervised by systemd or the container runtime; a fleet-wide prof-server ingestion/query tier reachable over OTLP/HTTP and a pprof-compatible query API (§21).

Target users/operators: the on-call engineer debugging a production latency regression; the platform team running the fleet-wide continuous-profiling tier; application developers binding prof-trace-sdk::Tracer directly, or transitively via the tracing ecosystem.

What later phases unlock: Phase 3 (eBPF, §15) unlocks system-wide and off-CPU sampling without code changes; Phase 7 (§19) unlocks distributed trace correlation across services; Phase 9 (§21) unlocks fleet-wide continuous profiling and historical query.

Recommended language + rationale: Rust 1.78+ for every crate in §1's list — memory safety without a GC pause on the sampling hot path, a mature DWARF/ELF/protobuf crate ecosystem (gimli, addr2line, object, prost), and zero-cost async for the exporter tier (ADR-01, §9). Three small C shims are accepted, not rejected: signal_handler.c (the async-signal- safe stub, §14), the libbpf CO-RE glue, and an optional LD_PRELOAD allocator shim (§20) — Rust's AS-safety lints reject constructs the signal path legitimately needs, and a small, fully-audited C surface is safer than fighting the borrow checker inside a signal handler. Rejected: Go (GC pauses violate the < 1% overhead budget, M1); C++ (no memory-safety backstop for a network-facing decoder, §22); Python (interpreter overhead precludes in-process use; retained only for examples/notebooks/, analysis-side).

Prerequisites: async-signal-safety discipline (which libc calls are AS-safe); SIGPROF, perf_event_open(2), ptrace(2), ioctl(2); DWARF 5 Call Frame Information; ELF program headers and /proc/<pid>/maps; Itanium C++ and Rust-v0 mangling; the OpenTelemetry data model (Tracer/Span/SpanContext/Resource/baggage); the Linux BPF execution model (helpers, maps, verifier); enough tokio/tracing to wire the SDK into an async program.

Estimated timeline: Phase 0 in 1 week; the full ten-phase plan (§12–§21) in 13–14 weeks (4–6 months including hardening, fuzzing, and the 24-hour soak, §26).

Deferred features (full table: §35):

  • PhaseDeferred("§14") — Windows sampling backend (ETW).
  • PhaseDeferred("§16") — macOS sampling backend (Mach task_for_pid) and Intel PT decoding.
  • PhaseDeferred("§17") — mixed-mode managed-runtime symbolization (JVM/V8/.NET beyond a flat /tmp/perf-<pid>.map reader) and native .gopclntab Go symbol tables.
  • PhaseDeferred("§17") — WebAssembly JIT support (Wasmtime/Wasmer/V8-Wasm).
  • PhaseDeferred("§15") — kprobe/uretprobe attach points beyond tracepoints.
  • PhaseDeferred("§21") — multi-tenant auth, mTLS ingestion, a ClickHouse-backed time-series store, and a profile-diff web UI.

2. Why Build This

  • Teaches the whole observability stack top to bottom — kernel sampling primitive → AS-safe signal path → lock-free ring → DWARF unwinding → symbol resolution → wire-format encoding → span propagation — with no layer left as a black box.
  • Why it matters architecturally: every production incident eventually needs either a profile or a trace; the teams that own their tooling can debug the tool itself, not just file a ticket against it. The 2010 Google Dapper paper (§5) exists because Google needed exactly this and nothing off-the-shelf existed yet.
  • Historically: this project retraces the lineage gprof → perf → pprof/gperftools → Dapper/OpenTracing → OpenTelemetry → continuous profiling (Pyroscope/Parca) — each step adding a dimension (sampling, symbolization, causality, fleet-wide continuity) this blueprint builds in order (§12–§21).
  • Engineering muscles built: async-signal-safety discipline; lock-free single-producer/ single-consumer data structures; binary-format parsing (ELF, DWARF, protobuf) with a hostile- input mindset; eBPF verifier-constrained kernel programming; wire-protocol compatibility engineering (bytewise OTLP/pprof round-trips, not "close enough").
  • Cross-links to sibling systems: the Tracer trait (§11.6) is the dependency the Agentic-Framework (Ranking 26) and the Multi-Agent-Coordinator (Ranking 49) bind against for their span-per-tool-call and span-per-agent-step instrumentation; the OTLP exporter (§19) is the wire those systems' operator dashboards consume; the continuous-profiling agent (§21) is what an operator runs across those systems' fleets to find the one worker whose tail latency is dominated by an allocator stall.
  • Calibration value: the < 1% overhead budget (M1) and the bytewise pprof/OTLP round-trip requirements (I11, I12) are unforgiving — there is no partial credit for "mostly compatible."

What Mastery Looks Like:

  • Can explain, from first principles, why a SIGPROF handler must never call malloc — and can name the exact deadlock (§14.6, Pitfall).
  • Can read a .eh_frame CIE/FDE pair and hand-evaluate the CFI program for one instruction (§16.2).
  • Can explain why symbol resolution is offline-by-default in a fleet profiler and what memory budget that decision buys back (§17, P3, M10).
  • Can construct a pprof Profile message by hand and explain why string_table[0] must be the empty string (§18.4, Pitfall).
  • Can trace a traceparent header through parse → Context → child Span → OTLP export and name every field that survives the round-trip (§19.4, I8).
  • Can defend, with a concrete regime, why an eBPF sidecar collector is sometimes wrong and an in-process SDK is right (§34, Alternative Architectures).
  • Can compute, from §4's numbers alone, the symbol-table memory budget for a 200-service fleet (§32, Capacity Model).

Box paragraphs.

  • Process Model owns every cross-cut identity: the module table, the build-id index. Every other box queries it; none re-parses /proc/<pid>/maps independently (P4, I4).
  • Sample Acquisition is the only trust/concurrency boundary that runs inside a signal handler or a BPF verifier sandbox; it is lock-free and allocation-free on the producer side (P1, I1).
  • Unwinder and Symbolizer are pure, off-signal, and swappable behind one trait each (P5, P9); the aggregator never branches on which implementation ran (P5).
  • Sample Aggregator and Span Recorder are the two independent data-path halves that converge only at the operator surfaces and the continuous-profiling agent — they never call into each other (§3 diagram; a violation would be a P11 defect).
  • Continuous-Profiling Agent owns time: batching, compression, backpressure, upload retries (P8). Producers never block on it.
  • Operator Surfaces are the only human- or dashboard-facing boundary; every one of them is read-only against the ingestion server's query API except prof attach, which mutates kernel state (loads a BPF program) and is gated by CAP_PERFMON (I13, §22 T4).

Persistence boundary: the ingestion server's object store (§21.5). Protocol boundaries: OTLP/ HTTP+gRPC (§19), the pprof query API (§21.4), the W3C traceparent header (§8.2). Concurrency boundaries: the per-thread ring (§14.1, SPSC), the worker→exporter MPSC channel (§19.3).

6. Design Principles

  1. P1 — Async-signal-safety is a hard floor on the producer side. The SIGPROF handler calls only AS-safe libc functions, holds no lock the application might hold, and allocates nothing. Violating it deadlocks the sampled thread the instant a signal lands mid-malloc. Enforced by §26.6's fault-injection harness.
  2. P2 — One overhead budget, audited every phase. ≤ 1% at 99 Hz (M1) is a merge-blocking gate, not an aspiration; the eBPF path is audited identically to the user-mode path.
  3. P3 — Symbolization is offline by default. Agents ship (build-id, ip) tuples; resolution happens in the analysis tier. Violating it inflates agent RSS past M10 (§17.6).
  4. P4 — Build-ids are the only durable module identity. Filenames/inodes/base addresses churn across deploys and containers; the GNU build-id does not. Every sample carries one.
  5. P5 — One unwinder API, three implementations. FP, DWARF, kernel ORC behind one Unwinder trait (§11.10); the aggregator never branches on which ran. Violating it couples the aggregator to backend internals and breaks P5 at every call site touching it.
  6. P6 — Determinism is the default. A fixed (seed, frequency, duration) tuple reproduces bit-identical pprof output on one binary/backend; cross-backend determinism is a narrower, separately-scoped guarantee (§25).
  7. P7 — No silent fallbacks. An unwalkable frame emits [unknown] and increments a counter (I7); it never substitutes a wrong frame or crashes. Violating it produces plausible-looking but silently wrong profiles — the worst failure mode a profiler can have.
  8. P8 — The exporter owns time, not the producers. Producers run flat-out; batching, compression, and backpressure live only in the exporter/agent tier (§19.3, §21.2).
  9. P9 — Strings are owned by the symbolizer. No other module demangles or normalizes a symbol string; downstream code sees only an interned SymbolId (§11.4).
  10. P10 — One arena per profile window, plus an interner arena. Sample/stack data lives in the window arena, freed at window end; symbol/build-id/module strings live in the interner arena, freed at shutdown. No per-sample malloc/free in steady state (M9, M10).
  11. P11 — The Tracer trait is the SDK's only public surface. Application code depends on Tracer/Span/Context (§11.6), never on tonic/prost/OTLP internals directly.
  12. P12 — OpenTelemetry compatibility is bytewise, not semantic. Exported traces validate against the OTLP protobuf schema and round-trip through the upstream opentelemetry-collector unmodified (§26.4, otlp.roundtrip).
  13. P13 — Sampling backends present one Sample shape. User-mode and eBPF backends both emit Sample (§11.3); the aggregator, symbolizer, and exporter are backend-agnostic.
  14. P14 — Fail closed on ambiguity, fail open on load. A malformed build-id or truncated frame fails closed (marks unknown, per P7); a saturated ring fails open (drops and counts, per I1) — the runtime never blocks the target application to preserve a sample.

8. Domain Model / Protocol / Data Model

8.1 The Sample record — internal producer→consumer protocol

Fixed-size, Copy, no heap pointers (P1, P10):

Sample {
  timestamp_ns : u64            // CLOCK_MONOTONIC or CLOCK_THREAD_CPUTIME_ID
  tid          : i32
  cpu          : u32
  kind         : SampleKind     // OnCpu | OffCpu | Allocation | Free | LockWait | LockAcquire
  stack_len    : u8             // 0..=127
  stack        : [u64; 127]     // raw instruction pointers, leaf-first
  value        : u64            // cycles | bytes | nanoseconds | 1
}

8.2 W3C Trace Context — traceparent grammar (EBNF)

traceparent   = version "-" trace-id "-" parent-id "-" trace-flags
version       = 2HEXDIG                      ; "00" only, others reserved
trace-id      = 32HEXDIG                     ; not all-zero
parent-id     = 16HEXDIG                     ; not all-zero
trace-flags   = 2HEXDIG                      ; bit 0 = sampled
tracestate    = list-member *( "," list-member )
list-member   = key "=" value

Malformed-input examples: version = "01" with extra fields → per spec, forward-compatible parse (ignore trailing fields); trace-id all-zero → reject, start a new root trace (I8); missing dashes → PropagationError::Format, treated as no incoming context (new root trace, never a crash).

8.3 DWARF CFI evaluation — state table (unwind one frame)

State Input Action Next State
FindFde rip binary-search per-module FDE index (§16.3) by rip range EvalCie on hit, Fail(NoFde) on miss
EvalCie CIE initial instructions seed UnwindTable with CIE defaults EvalFde
EvalFde FDE instructions up to rip apply DW_CFA_* opcodes, building the row for rip Recover
Recover UnwindTable row + current Registers compute parent cfa, ip, sp, bp per row rules Emit
Emit parent Registers push regs.ip to out; set regs = parent FindFde (next frame) or Done (ip == 0 or sp non-increasing, I7)
Fail(NoFde) — emit [unknown], increment prof_unwind_failures_total{cause=no_fde} (I7) Done

Malformed-input example: a .eh_frame truncated mid-FDE → EvalFde runs out of bytes → Fail(Truncated) → partial stack returned with [unknown] at the truncation point (fixture conformance/corpora/unwind/dwarf-truncated.bin, §16.9).

8.7 Worked example — one sample, end to end

SIGPROF fires at t=1000ns on tid=42 mid-compute_pi → handler pushes Sample{timestamp_ns:1000, tid:42, kind:OnCpu, stack_len:1, stack:[0x401234]} (I2) → worker drains ring → walk_fp (§16.2, frame pointers present) returns [0x401234, 0x401100, 0x400f00] → Symbolizer::resolve maps each IP to Frame{function:"compute_pi", file:"pi.rs", line:42} (§17.1) → StackTable::intern returns StackId(7) (§18.1) → Aggregator increments counts[StackId(7)] += 1 → at window close, ProfileBuilder::add_sample(StackId(7), 1) then finish() emits gzip pprof bytes (§18.4) validated by I10/I11.

8.8 Failure-path example

Same pipeline, but the module for 0x401234 has no build-id (Module::Anonymous, JIT page, §13.2) and /tmp/perf-<pid>.map is absent → Symbolizer::resolve returns Frame{function: "[unknown]", ...} (P7, I7) → the sample still counts in the aggregate (not dropped) → the pprof's Function.name string-table entry is "[unknown]", distinguishable in the flamegraph from a resolved frame, never conflated with a legitimately-named function.

12.6 Pitfalls

  • SIGPROF is per-thread via timer_create+SIGEV_THREAD_ID, per-process via setitimer(ITIMER_PROF) — Phase 0 uses the former; the latter would multiplex onto one timer and break the per-thread ring model (I1).

  • Small thread stacks without sigaltstack risk overflow when the handler runs on the main stack; document and ship a helper.
  • Rust's AS-safety lints reject most of std; the handler stays in csrc/signal_handler.c by design (ADR-01), never ported to Rust.

12.7 Performance Concerns

timer_create/timer_settime are syscalls per armed timer — one per sampled thread; batching timer creation at thread-registration time (not per-sample) keeps this off the hot path. clock_gettime+syscall(SYS_gettid) inside the handler are both AS-safe but not free; the handler's total instruction count is measured against M1 from day one (§12.3 baseline fixture).

12.8 Edge Cases

A sample with stack_len == 0 (handler fired before ring registration) is logged and skipped, not a crash. A thread that exits mid-sample leaves an orphaned ring; the registry reclaims it on next refresh_modules pass. Concurrent thread creation during sampler start is handled by registering new threads lazily on first signal delivery.

12.9 Failure Analysis

Ring registration failure (OOM on the 4 MiB/thread ring, §4) surfaces as SamplerError:: RingAlloc; the sampler refuses to start rather than sample without a ring (P14, fail closed). Blast radius: one thread's samples are lost, not the process's; detection via prof_samples_dropped_total; forensic artifact: the SamplerError log line with tid.

12.10 Operational Notes

Metrics: prof_samples_total, prof_samples_dropped_total (§24.2) exist from Phase 0. Deployment: none yet (local binary only). Rollback: N/A. Compatibility: the Sample layout (§11.3) is frozen from this phase forward — any change is a breaking ABI change across crates.

13. Phase 1 — Process Model and Module Table

13.1 Objectives

Attach to a target pid, parse its memory map, identify every loaded ELF object, extract its GNU build-id, and expose Process::module_for_address (§11.1) — the lookup every later phase queries (P4, I4; theory: Levine, Linkers and Loaders, §5).

13.2 Detailed Implementation Steps

  • prof_core::process::parse_maps_line tokenizes each /proc/<pid>/maps line (start-end perms offset dev inode pathname), classifies the VMA (executable, writable, anonymous, vDSO, stack, heap), and emits a ModuleCandidate per executable VMA (applies I4).
  • prof_core::module::read_elf opens each candidate via object-rs, reads program headers, locates .note.gnu.build-id, extracts the 20-byte SHA-1 (ADR-09). .text range comes from the PT_LOAD segment with PF_X.
  • Anonymous executable VMAs (JIT pages) have no build-id/file; tagged Module::Anonymous, resolved later via /tmp/perf-<pid>.map if present (§17; PhaseDeferred("§17") for full managed-runtime symbolization).
  • Process::build_id_index: HashMap<BuildId, ModuleId> built during attach() (§11.1).
  • On dlopen in the target, the eBPF mmap-watch program (§15) notifies the worker; refresh_modules() re-parses /proc/<pid>/maps incrementally (applies P4).

13.3 Deliverable

Process::attach(pid) returns a fully populated Process for a live target; a test asserts libc.so.6 appears in the module table with a non-zero build-id.

13.4 Acceptance Criteria

  • Process::module_for_address(rip) returns the correct Module for the calling thread's current IP, verified against /proc/self/maps ground truth, 100% of 1,000 sampled addresses.
  • A dlopen test on a synthetic .so shows up in refresh_modules() output within one call.
  • Fixture process/maps-edge-cases.txt (§13.5) classifies every line correctly.

13.5 Conformance Fixtures

Fixture Purpose Expected Output
process/maps-edge-cases.txt anonymous/vDSO/vsyscall/[stack]/[heap]/multi-segment ELF every line classifies correctly
process/build-id-mismatch.bin ELF with malformed .note.gnu.build-id loads with build_id: None + BuildIdMalformed warning

13.6 Pitfalls

  • /proc/<pid>/maps lines can omit pathname for anonymous regions; parser handles the truncated form (fixture above).
  • The dev field is MAJOR:MINOR for file-backed VMAs, 0:0 for anonymous; do not parse it strictly as always-present.
  • Go binaries carry .note.go.buildid in addition to (usually) the GNU note; ADR-09 locks GNU build-id as canonical — Go binaries resolve via the GNU note when present (nearly always, since Go links libc).
  • Kernel /proc format drift across LTS releases (5.10 vs 6.6) — tested against both (§26.7).

13.7 Performance Concerns

/proc/<pid>/maps re-parses are O(VMA count); a busy process can have thousands of VMAs. refresh_modules() is incremental where the eBPF mmap watcher is available (§15), avoiding a full re-parse per dlopen. The build-id index lookup is O(1) amortized (HashMap).

13.8 Edge Cases

A build-id present but truncated (fewer than 20 bytes) → BuildIdMalformed, module loads with build_id: None (fail closed, P14). A statically-linked binary with no dynamic segment still parses correctly (single Module entry). A container-namespaced target's /proc/<pid>/maps paths may reference paths invisible to the agent's mount namespace; the reader falls back to Module::Anonymous when the file cannot be opened, never crashes.

13.9 Failure Analysis

Process::attach failing (target exited between discovery and attach) surfaces as ProcError::NoSuchProcess; the caller (agent supervisor, §21.3) treats this as expected churn, not a fault. Detection: attach return value; forensic artifact: the pid and timestamp in the supervisor log; recovery: retry on next scheduling pass, no operator action needed.

13.10 Operational Notes

No new metrics beyond §12; prof_symbolize_lookups_total{outcome=miss} (§7 I4) is populated starting here when a sample's build-id has no matching module. Compatibility: Module's field set (§11.1) is consumed identically by §17 (symbolizer) and §21 (server) — a field rename here is a cross-cutting breaking change.

14. Phase 2 — User-Mode Sample Acquisition

14.1 Objectives

Acquire samples portably, without eBPF: the per-thread SPSC ring (P1, I1), the SIGPROF handler (I2), and the perf_event_open(2) hardware-counter path — the two backends behind the one Sampler trait (§11.9, P13; theory: Desnoyers & Dagenais, LTTng ring design, §5).

14.2 Detailed Implementation Steps

  • ring.rs: fixed-capacity SPSC ring, one page per registered thread, pointer in a pthread_key_t. Push is wait-free: compare head - tail against capacity, write slot, release-store head; full → return "dropped", increment dropped_samples atomic (I1).
  • sigprof.rs: arm_thread_timer uses timer_create(CLOCK_THREAD_CPUTIME_ID, SIGEV_THREAD_ID) so the timer charges only on-CPU time — off-CPU sampling is a separate, eBPF-only mechanism (§15). Signature: pub fn arm_thread_timer(tid: pid_t, hz: u32) -> Result<TimerId, SamplerError>.
  • perf.rs: open_cpu_cycles opens a perf_event_open fd with PERF_TYPE_HARDWARE/ PERF_COUNT_HW_CPU_CYCLES, PERF_SAMPLE_CALLCHAIN, frequency mode; the kernel mmaps a ring the worker drains as PERF_RECORD_SAMPLE events (applies P13; no glibc wrapper exists, so the syscall is invoked directly per the man page, §5).
  • Kernel-walked PERF_SAMPLE_CALLCHAIN frames are split at the PERF_CONTEXT_USER sentinel to separate kernel and user IPs before handing to the unwinder (§16).

14.3 Deliverable

SigprofSampler records 99 Hz samples from examples/cpu-bound with < 1% overhead (M1); PerfSampler opens PERF_COUNT_HW_CPU_CYCLES, mmaps the ring, drains into Vec<Sample>.

14.4 Acceptance Criteria

  • Overhead measured against §12.5's baseline: < 1% at 99 Hz (M1), < 5% at 999 Hz (M2).
  • Drop-rate test at a synthetic 100 kHz rate: drop counter > 0, runtime keeps running (I1).
  • PerfSampler sample count within ±5% of frequency_hz × duration_s (fixture below).

14.5 Conformance Fixtures

Fixture Purpose Expected Output
sample/sigprof-99hz.json 99 Hz, 10 s on cpu-bound < 1% overhead, 0 drops
sample/perf-cycles.json PERF_COUNT_HW_CPU_CYCLES, same target sample count within ±5% of 99×10

14.6 Pitfalls

  • perf_event_open has no glibc wrapper — invoke via syscall(2) directly; the header (perf_event.h) may lag the running kernel, so a vendored copy pinned to the target kernel ships in ebpf/vmlinux.h's sibling headers.
  • perf_event_attr's set_freq/set_disabled bitfield setters have been inverted in some libc crate versions — test against the actual kernel ABI, never trust crate docs alone.
  • The mmap'd perf_event_open ring must be a power-of-two ≥ page size; default 64 KiB/fd.
  • A SIGPROF delivered inside pthread_mutex_lock deadlocks if the handler allocates — exactly what P1/I2 forbid; this is the fault the §26.6 injection harness specifically targets.

14.7 Performance Concerns

The ring push is the entire producer-side cost budget (M1); everything else (unwinding, symbolizing) is off the signal path by construction (P1, P10). perf_event_open's kernel-side PERF_SAMPLE_CALLCHAIN walk is "free" (kernel does it) but returns mixed kernel/user frames that cost a linear scan to split at PERF_CONTEXT_USER.

14.8 Edge Cases

Ring saturation under a synthetic 100 kHz load (§14.4) drops samples but never corrupts ring state (I1). A thread that never calls into the runtime (no ring registered) receiving a signal is a no-op return, not a crash (§12.8). perf_event_open returning EACCES (missing CAP_PERFMON) is a clean SamplerError, not a panic (P14, I13).

14.9 Failure Analysis

A dropped-sample burst (ring saturated) is detected via prof_samples_dropped_total crossing a threshold (§24.2 alert); blast radius is confined to that thread's profile fidelity, not process stability; recovery is either raising ring capacity or lowering frequency_hz (§24.3 runbook).

14.10 Operational Notes

New metrics: prof_samples_total{kind,backend}, prof_samples_dropped_total{kind,backend} (§24.2). No deployment change (still local). Compatibility: the Sampler trait (§11.9) is the frozen contract §15's eBPF backend must also satisfy (P13).

15. Phase 3 — eBPF Sampling Backend

15.1 Objectives

Lift the two limits of §14's user-mode path: sample threads in other processes without code injection, and capture off-CPU stacks. Land the CPU-profile BPF program, the off-CPU sched_switch program, and uprobe/USDT attach (P13, I13; theory: Gregg & Goldshtein, BPF Performance Tools, §5; ADR-05).

15.2 Detailed Implementation Steps

  • ebpf/src/cpu.bpf.c: SEC("perf_event") program attached to a PERF_TYPE_SOFTWARE/ PERF_COUNT_SW_CPU_CLOCK fd; per sample, filters by pid/cgroup, calls bpf_get_stackid() (kernel side, ORC — ADR-19) and bpf_get_stack(BPF_F_USER_STACK) (user side), pushes a sample_event to a BPF_MAP_TYPE_RINGBUF.
  • ebpf/src/offcpu.bpf.c: attaches tp/sched/sched_switch; on switch-out records (prev_pid, ts) in a BPF_MAP_TYPE_HASH; on switch-in for a tracked pid, computes the delta and emits an OffCpuSample (kind OffCpu, value = blocked nanoseconds, §11.3).
  • libbpf-rs glue (ebpf_sampler.rs) opens/loads/attaches via a CO-RE skeleton generated at build time from vmlinux.h (ADR-05); every kernel-struct read uses BPF_CORE_READ exclusively (no hard-coded offsets — portability across 5.10 LTS/6.6, §26.7).
  • ebpf/src/uprobe.bpf.c/usdt.bpf.c: attach to a named symbol (Program::attach_uprobe) or to a .note.stapsdt-declared static probe (attach_usdt) for zero-source-change instrumentation (I13 gates capability).

15.3 Deliverable

EbpfCpuSampler collects on-CPU samples from examples/cpu-bound with kernel-side stack-ids resolved; OffCpuSampler records blocking events from examples/lock-contended; a uprobe smoke test fires on every call into examples/usdt-probed.

15.4 Acceptance Criteria

  • Distinct kernel-side stack-id count ≤ 16 for the tight-loop target (bounded program shape).
  • Off-CPU 90th-percentile blocked_for_ns within ±10% of the recorded fixture value.
  • Every BPF program in this phase passes the verifier on both kernel 5.10 LTS and 6.6 (§26.7).

15.5 Conformance Fixtures

Fixture Purpose Expected Output
ebpf/cpu-stackids.json distinct stack-id + sample count, cpu-bound stack-ids ≤ 16, count within ±5%
ebpf/offcpu-blocked.json blocked-time distribution, lock-contended p90 within ±10%

15.6 Pitfalls

  • The verifier rejects unbounded loops, unaligned reads, and out-of-order helper calls; every program here is checked against both supported kernels in CI (§26.7).
  • bpf_get_stack() truncates at MAX_STACK_DEPTH; deeper stacks are marked truncated (I6), never silently shortened without a flag.
  • ringbuf needs kernel 5.8+; older kernels fall back to BPF_MAP_TYPE_PERF_EVENT_ARRAY (ADR-05 documents the fallback path).
  • perf_event_open for system-wide sampling needs CAP_PERFMON (or CAP_SYS_ADMIN pre-5.8); the agent's systemd unit grants exactly this, nothing broader (I13).

15.7 Performance Concerns

BPF ring-buffer reservation/submit is two helper calls per sample — cheap, but the verifier's bound on loop iterations means stack-walking depth is capped in-kernel identically to MAX_STACK_DEPTH (§4). CO-RE relocation adds a one-time load-time cost, not a per-sample one.

15.8 Edge Cases

A dlopen during active sampling changes the module table mid-window; the mmap-watch program (§13.2) notifies the worker to refresh_modules(). A BPF program load rejected by the verifier surfaces as a load-time error, never a partial/corrupt attach (P14). FUTEX_WAIT_BITSET and FUTEX_LOCK_PI variants are out of scope for the futex tracer introduced in §20 — documented as a known gap, not silently mishandled.

15.9 Failure Analysis

Verifier rejection is unrecoverable at runtime (a kernel/toolchain mismatch); the supervisor (§21.3) does not retry it — it surfaces once and the agent exits with a clean, actionable error (FM naming in §23). Missing CAP_PERFMON is detected at load time and reported identically.

15.10 Operational Notes

New metrics: prof_unwind_walks_total{path=orc} populated via the kernel-side stack-id path. Deployment: the agent's systemd unit documents required capabilities explicitly (CAP_PERFMON, CAP_BPF). PhaseDeferred("§15") covers kprobe/uretprobe attach beyond tracepoints (§35).

16. Phase 4 — Stack Unwinder

16.1 Objectives

Turn a sampled IP into a stack of IPs via three dispatch-by-module implementations behind one Unwinder trait (§11.10, P5, I5; theory: DWARF v5 section 6.4, Levine ch. 8; ADR-03).

16.2 Detailed Implementation Steps

  • fp.rs: frame-pointer walker — read [saved-rbp][return-addr] at rbp, validate saved_bp > bp (stack grows down) and ret_addr != 0, repeat until MAX_STACK_DEPTH or a sentinel (applies I6, M5 target: ≥ 5M stacks/s).
  • dwarf.rs: DWARF CFI walker via gimli-rs (ADR-03) — per rip, binary-search the per-module FDE index (built once per module, keyed by rip range), evaluate the FDE's DW_CFA_* program against the CIE's initial state (the §8.3 state table), recover parent registers, repeat (applies I7, M4 target: ≥ 200K stacks/s).
  • orc.rs: kernel-side only — bpf_get_stackid() (§15) already performs the ORC walk; no user-space ORC synthesis (ADR-19, P5 dispatch boundary).
  • jit.rs: reads /tmp/perf-<pid>.map (<addr> <size> <symbol> lines, the perf convention) to attribute IPs in anonymous JIT pages; unwinding through JIT'd frames falls back to frame pointers if the JIT opts in (PhaseDeferred("§16") for deeper managed-runtime unwinding).
  • LBR (Last Branch Record) capture via PERF_SAMPLE_BRANCH_STACK is an auxiliary path merged at aggregation time, not a primary unwinder (PhaseDeferred("§16"), Intel-only, SkyLake+).

16.3 Deliverable

FpUnwinder walks examples/cpu-bound's stack to depth ≥ 5 with zero [unknown] frames; DwarfUnwinder walks the same source compiled with -fomit-frame-pointer to matching depth; dispatch across a stack crossing an FP module into a DWARF-only module unwinds correctly through both (I5).

16.4 Acceptance Criteria

  • unwind.fp and unwind.dwarf conformance buckets: unwound stack matches recorded (function, line) tuples exactly, 7-function synthetic call chain (§16.5).
  • DWARF throughput ≥ 200K stacks/s (M4); FP throughput ≥ 5M stacks/s (M5), both on reference hardware (§4).
  • A truncated .eh_frame fixture returns a partial stack with [unknown] at the truncation point, never a wrong frame (I7).

16.5 Conformance Fixtures

Fixture Purpose Expected Output
unwind/fp-canonical.bin 7-function chain, frame pointers exact (function,line) match
unwind/dwarf-canonical.bin same source, -fomit-frame-pointer exact (function,line) match
unwind/dwarf-truncated.bin artificially truncated .eh_frame partial stack + [unknown] at cut
unwind/jit-perf-map.txt synthetic JIT scenario every JIT-range IP resolves via the map

16.6 Pitfalls

  • .eh_frame (runtime, C++ exception personality) and .debug_frame (debugger-only) interpret CFI rules slightly differently; gimli abstracts the difference — do not hand-roll either.
  • DW_CFA_GNU_args_size is a widely-used non-standard opcode; gimli handles it, custom walkers commonly miss it.
  • FP walking can read into freed stack pages after a longjmp; always go through StackMemory (§11.10), which bounds reads to the thread's mapped stack range — never raw pointer deref.
  • aarch64 uses link-register (lr) + frame-record (fp) conventions distinct from x86_64's rbp/return-address pair; both are fixtured (§16.5, ADR-02).

16.7 Performance Concerns

The DWARF hot path is dominated by FDE search (M4); the per-module FDE index (sorted by rip range, built once at module-load time) turns this into a binary search rather than a linear scan. FP walking is memory-latency-bound (pointer chasing) but has no lookup cost at all.

16.8 Edge Cases

__libc_start_main/_start have no useful unwind info; the walker stops at rip == 0 or a recognized process-entry symbol rather than reading garbage. A stack whose FP chain loops (corrupted rbp) is caught by the saved_bp > bp sanity check (§16.2) and terminates instead of hanging. A signal-interrupted stack mid-prologue (before the frame pointer is established) returns a one-frame stack, not a crash.

16.9 Failure Analysis

An unwalkable frame increments prof_unwind_failures_total{cause} and emits [unknown] (I7, P7) rather than aborting the sample; blast radius is confined to depth-of-attribution for that one stack, never process stability. A systemic rise in unwind.failures across many samples is the signal for the on-call runbook (§24.3) to check for a binary/DWARF-info mismatch.

16.10 Operational Notes

Metrics: prof_unwind_walks_total{path} (path ∈ {fp,dwarf,orc}), prof_unwind_failures_total {cause}, prof_unwind_truncated_total (§24.2). No deployment change. PhaseDeferred("§16") covers macOS/Windows unwinding and Intel PT decoding (§35).

17. Phase 5 — Symbolizer

17.1 Objectives

Resolve an IP to (function, file, line), expanding inline frames, across three lookup paths behind one Symbolizer trait (§11.11, P9, ADR-04; theory: Levine ch. 8, §5).

17.2 Detailed Implementation Steps

  • addr2line.rs: addr2line-rs walks the DWARF compilation unit covering the IP, then .debug_line's line program, caching the per-module DWARF context LRU-keyed on BuildId (P4, applies M6 target: ≥ 100K symbols/s cached).
  • elf_symtab.rs: stripped-binary fallback via .symtab/.dynsym (object-rs); returns (function, "", 0) — no line info available on this path.
  • inline.rs: DW_TAG_inlined_subroutine DIEs expand via Context::find_frames, drained fully (a partially-consumed iterator silently truncates, §17.6); the deepest frame has is_inlined == false, callers above it true (I5 dispatch invariant analogue for symbols).
  • demangle.rs: Itanium (cpp_demangle, symbols prefixed _Z) or Rust v0 (rustc_demangle, prefixed _R); undetected prefixes pass through undemangled rather than erroring.
  • cache.rs: build-id-keyed LRU (I14 — never evicts a build-id in active use in the current window; pins active ids, evicts oldest unpinned).
  • Offline mode (P3, ADR-08): the agent ships (build-id, offset) only; this phase's resolver runs in the analysis tier or in prof report/prof flamegraph (dev workflows).

17.3 Deliverable

Symbolizer::resolve returns Vec<Frame> for an IP in cpu-bound with function/file/ line populated and inline frames expanded; throughput ≥ 100K resolutions/s cached (M6).

17.4 Acceptance Criteria

  • Three-level #[inline] fixture (§17.5) returns exactly three Frames, two marked is_inlined: true.
  • A stripped-binary fixture returns the function name via .symtab with line == 0.
  • C++ and Rust demangling fixtures assert exact-string match; a Go-binary fixture asserts a non-empty result via .symtab fallback (Go's .gopclntab is PhaseDeferred("§17")).

17.5 Conformance Fixtures

Fixture Purpose Expected Output

symbol/stripped.bin binary with no .debug_info .symtab fallback, line==0

17.6 Pitfalls

  • Context::find_frames's iterator silently truncates if not drained to completion — always exhaust it.
  • .debug_line can map one address to multiple (file,line) entries (macros, headers); resolve by highest column when present, else the last entry.
  • Build-id mismatch (sample from v1.2.3, resolved against v1.2.4 on disk) gives plausible-but- wrong results silently — the #1 symbolizer failure mode; the build-id-keyed cache (I14) fails closed on an unknown id rather than guessing.
  • glibc alone ships 100K+ symbols; size the interner pool accordingly (§32 capacity model); M10's 100 MiB RSS budget assumes offline symbolization (P3), not an in-agent symbol table.

17.7 Performance Concerns

Cached resolution is O(1) amortized (LRU hit); a cold module's first resolution pays the full .debug_info parse cost (hundreds of µs to ms depending on module size) — amortized across the window, not per-sample, because the cache is keyed by module, not by IP.

17.8 Edge Cases

A symbol table update mid-window (binary hot-reloaded, rare but possible in dev workflows) invalidates the cache entry for that build-id; the cache detects via a changed build-id, never serves stale symbols for a different binary. A mangled name with an unrecognized prefix passes through as-is rather than erroring (fail-open on cosmetic demangling, fail-closed on identity).

17.9 Failure Analysis

A .debug_info parse failure (corrupted DWARF) surfaces as SymbolError::MalformedDwarf, handled per P7 (falls back to .symtab, then to [unknown]); never propagates as a panic. The fuzz target dwarf_unwind_fuzz.rs (§10, §26.6) exercises this path continuously.

17.10 Operational Notes

Metrics: prof_symbolize_lookups_total{outcome∈{hit,miss,error}}, prof_symbol_cache_bytes (§24.2). PhaseDeferred("§17") covers managed-runtime (JVM/V8/.NET) symbolization beyond the flat perf-map reader, .gopclntab, and WebAssembly JIT support (§35).

18. Phase 6 — Aggregation, pprof, and Flamegraphs

18.1 Objectives

Collapse millions of samples into a compact StackTable (§11.5), encode to pprof (I10, I11), and render folded-stack and flamegraph SVG output (theory: Gregg, "The Flame Graph," CACM 2016, §5; ADR-06, ADR-14).

18.2 Detailed Implementation Steps

  • stack_table.rs: StackTable::intern walks frames bottom-up, deduplicating shared prefixes into a parent-pointer tree (P10 window arena); unfold walks parent pointers to the root (applies §8.1's Sample→StackId mapping).
  • counter.rs: HashMap<StackId, u64> per profile type (cycles for on-CPU, nanoseconds for off-CPU, bytes for heap); merge across windows is associative/commutative.
  • flamegraph.rs: folded-stack writer (func1;func2;func3 count, one line/stack, Gregg's format) feeds the SVG renderer — Gregg's standard layout: vertical strips per stack, shared prefixes merge, width ∝ count, X-axis alphabetically sorted for diff legibility (§18.5). diff.rs: two-profile differential — red/blue rectangles by delta sign and magnitude.
  • prof-pprof/builder.rs: ProfileBuilder::finish (§11.8) emits the google/pprof/profile.proto message (§8.5) — string_table[0] == "" (I10) from construction; period in nanoseconds for cpu type (period_type=("cpu","nanoseconds")), bytes for alloc-space; gzip-compressed (ADR-14). Inline-frame expansion goes in Location.lines, never as separate Location records (§18.6 pitfall).

18.3 Deliverable

Aggregator accumulates 1M samples into ≤ 10K distinct stacks for cpu-bound; ProfileBuilder::finish emits gzip pprof go tool pprof -raw accepts cleanly; the flamegraph renderer emits an SVG geometry-identical to Gregg's reference flamegraph.pl output.

18.4 Acceptance Criteria

  • pprof output is bytewise-identical to the recorded fixture, modulo timestamps (I11, compare. pprof_clean bucket, §26.4).
  • Flamegraph SVG geometry bytewise-matches the fixture (CSS may differ, §18.5 fixture).
  • Off-CPU and differential renders reuse the same DOM layout (verified by fixture, §18.5).

18.5 Conformance Fixtures

Fixture Purpose Expected Output
pprof/cpu-bound.pprof.gz 10 s @ 99 Hz, cpu-bound bytewise match modulo timestamps
pprof/heap-alloc.pprof.gz 10 s, alloc-heavy alloc-objects total within ±1%
flamegraph/cpu-bound.svg SVG for the above bytewise geometry match
flamegraph/diff-baseline-vs-new.svg differential render bytewise match

18.6 Pitfalls

  • string_table[0] must be "" (I10) — omitting it makes go tool pprof reject the profile.
  • period is in the units of period_type (nanoseconds for cpu) — confusing it with a raw frequency value corrupts every downstream total.
  • Location.address must be module-relative (IP minus mapping start), not absolute — absolute IPs make the profile symbolizable only against the exact mapping it was recorded against, defeating offline symbolization (P3).
  • Inline expansion belongs in Location.lines, not as extra Location records — the latter doubles location count and breaks UI grouping in every downstream pprof viewer.
  • Folded-stack separators are semicolons; a function name containing one (rare Rust-v0 closure case) must be escaped.

18.7 Performance Concerns

StackTable::intern's dedup is the entire compression story — without it, 1M samples produce 1M stack records instead of ≤ 10K; the hash-table lookup is O(1) amortized per frame. The flamegraph renderer's alphabetical X-sort is O(n log n) over distinct stacks, done once per render, not per sample.

18.8 Edge Cases

A profile with zero samples (target ran but nothing was sampled, e.g. sub-Hz duration) still emits a structurally valid, empty-sample-array pprof — never a malformed/truncated one. A stack exactly at MAX_STACK_DEPTH (127) is stored whole, not off-by-one truncated.

18.9 Failure Analysis

A ProfileBuilder::finish failure (encode error) is a BuildError, surfaced to the caller (agent or CLI) rather than emitting a truncated/corrupt file — the caller decides whether to retry the window or skip it (§21.3 supervisor logic).

18.10 Operational Notes

Metrics: prof_aggregator_stacks (gauge), prof_pprof_bytes_emitted_total (counter) (§24.2). Compatibility: pprof and folded-stack are both frozen wire/text formats from this phase forward (I10, I11) — any change to ProfileBuilder's field mapping is a breaking export-format change.

19. Phase 7 — Tracer SDK and OTLP Exporter

19.1 Objectives

Land the in-process Tracer/Span/Context (§11.6, P11), the W3C traceparent propagator (I8), the batcher (P8), and the OTLP/HTTP+gRPC exporter (I12, ADR-07, ADR-15; theory: Sigelman et al., "Dapper," 2010; Fonseca et al., "X-Trace," NSDI 2007, §5).

19.2 Detailed Implementation Steps

  • tracer.rs: GlobalTracer::start reads the current Context (thread-local or async-task- local), derives trace_id (inherited from parent or freshly random if root), allocates a random span_id, and constructs a SpanInner (§11.6). Hot-path budget: ≤ 1 µs (M7).
  • batcher.rs: per-thread bounded queue (1,024 spans default); one worker drains all queues, batches into groups of 512 or every 5 s, whichever first (P8). Span::finish pushes to the thread-local queue and returns — no allocation if not full; on full, drop + increment a counter (mirrors the §14.1 ring discipline).
  • propagator.rs: parse_traceparent/emit implement the §8.2 EBNF exactly; malformed input starts a fresh root trace rather than erroring the caller (I8, P14).
  • prof-otlp/http_exporter.rs: serializes ExportTraceServiceRequest (§8.6), gzips, POSTs to <endpoint>/v1/traces; HTTP 4xx logged+dropped (retry would not help); 5xx retried with exponential backoff, max 5 attempts (ADR-15 default transport).
  • prof-otlp/grpc_exporter.rs: feature-gated (feature = "grpc"), targets TraceService.Export over HTTP/2 (ADR-15, ADR-20) — preferred at sustained throughput ≥ M8.
  • tracing integration: a Layer impl translates tracing::Span create/close into prof_trace_sdk::Span create/finish (ADR-13, P11) — zero source changes for existing tracing! call sites in sibling projects (Ranking 26, 49).

19.3 Deliverable

Tracer::start→finish hot path measured ≤ 1 µs p99 (M7); OtlpHttpExporter exports a 512-span batch to a local OTel collector, ingested without warnings; a tracing-instrumented binary produces spans that arrive at the collector unmodified.

19.4 Acceptance Criteria

  • benchmarks/span_emit_latency.rs: p99 ≤ 1 µs (M7).
  • Round-trip test: span exported → ingested by upstream opentelemetry-collector → re-exported → deserialized — bytewise-equivalent except collector-added resource attributes (I12).
  • traceparent parse→emit round-trip matches byte-for-byte (I8, fixture below).

19.6 Pitfalls

  • OTLP requires raw bytes for trace_id/span_id on the protobuf wire — JSON uses hex; sending hex on protobuf is silently accepted by the upstream collector but breaks downstream indexing by trace (§8.6).
  • A finished span dropped by a full batcher queue must never propagate as an application error — only the drop counter signals it.
  • tracing::Field::Debug values become meaningless "Foo { .. }" strings if not flattened into structured KeyValues before crossing into OTel.
  • Resource attributes (service.name, service.version, host.name) must be identical across every span in one batch — some collectors accept per-span drift, many reject it.
  • Instant::now() has no epoch; OTLP time_unix_nano must derive from SystemTime::now(), captured at span start alongside Instant (ADR-25).

19.7 Performance Concerns

The hot path (M7) is dominated by Arc allocation for SpanInner and the thread-local queue push; batching, compression, and network I/O all live off this path (P8). gRPC's HTTP/2 multiplexing amortizes connection overhead better than HTTP/1.1 at high sustained throughput (M8), the reason ADR-15 keeps gRPC available behind a flag.

19.8 Edge Cases

A span started with no parent context becomes a new trace root (I8). A Span dropped without calling finish() (a panic! mid-scope) still records via Drop, capturing an Error status — tracing never silently loses a span to an unwind. Clock skew between the emitting host and the collector is tolerated up to the §21.9 threshold; beyond it, the ingestion server flags it.

19.9 Failure Analysis

An OTLP 5xx after 5 retries surfaces as prof_otlp_spans_dropped_total{cause=export_failed}; blast radius is the lost batch only — the application was never blocked (P8, I12 preserved for every batch that does get through). Detection is the drop-rate alert (§24.3); recovery is collector-side (restart the collector) or network-side, never application-side.

19.10 Operational Notes

Metrics: prof_otlp_spans_exported_total{outcome}, prof_otlp_spans_dropped_total{cause} (§24.2). The Multi-Agent-Coordinator (Ranking 49) attaches one span per agent step against this Tracer; the Agentic-Framework (Ranking 26) defines the agent.<verb>.<noun> attribute schema this SDK's KeyValue constructors mirror.

20. Phase 8 — Heap and Lock-Contention Profilers

20.1 Objectives

Two specialized profilers reusing the §14–§18 sampling/unwinding/symbolizing/aggregation stack: an LD_PRELOAD heap-allocation sampler with leak detection, and an eBPF futex-based lock-contention tracer (ADR-17, ADR-05).

20.2 Detailed Implementation Steps

  • prof-heap/csrc/shim.c: intercepts malloc/free/realloc/calloc/posix_memalign and the C++ operator new/delete family via dlsym(RTLD_NEXT, ...); samples with Poisson discipline, configurable mean inter-arrival in bytes (default 512 KiB) (applies §11.3 SampleKind::Allocation/Free).
  • jemalloc.rs: alternative path for jemalloc-linked targets — reads prof.dump via mallctl("prof.dump", ...), parses into the same Sample shape (ADR-17 trade-off).
  • leak.rs: allocations unfreed by window end are reported LSan-compatible: <n_bytes> bytes in <n_allocations> allocations from <stack>.
  • prof-lock/futex.bpf.c: attaches sys_enter_futex/sys_exit_futex; a FUTEX_WAIT exceeding a threshold (default 100 µs) records Sample{kind: LockWait, value: blocked_ns}.
  • mutex_shim.rs: ProfMutex<T> drop-in for std::sync::Mutex<T> recording lock-acquire/ release with #[track_caller] site attribution — opt-in, complementary to the zero-source- change eBPF futex tracer.

20.3 Deliverable

prof-heap records a 95th-percentile allocation-sample distribution for examples/alloc-heavy and emits pprof with period_type=("alloc-objects","count")/("alloc-space","bytes"); prof-lock records the lock-wait distribution for examples/lock-contended matching the recorded fixture within ±10% at p90.

20.4 Acceptance Criteria

  • Alloc-objects total in the emitted pprof within ±1% of the recorded fixture.
  • Leak report for a deliberately-leaking binary matches the LSan-compatible fixture format.
  • Futex-wait p90 within ±10% of the recorded distribution; ProfMutex::lock records the Location::caller() site on every contended acquire.

20.5 Conformance Fixtures

Fixture Purpose Expected Output

heap/leak-report.txt deliberately-leaking binary matches LSan-compatible format
lock/contended-distribution.json futex-wait distribution p90 within ±10%

20.6 Pitfalls

  • LD_PRELOAD does not intercept statically-linked allocators — documented (ADR-17); static targets use the jemalloc-native path.
  • dlsym(RTLD_NEXT, "malloc") itself allocates on first call — a naive shim re-enters and deadlocks; fixed with a thread-local in_malloc_shim guard suppressing recursive recording.
  • Some libc functions (getaddrinfo) call malloc from signal-adjacent contexts; the recording path must be as AS-safe as §14's SIGPROF discipline or it deadlocks identically.
  • FUTEX_WAIT_BITSET and FUTEX_LOCK_PI variants are not handled by the Phase-0 futex tracer — a documented known gap, not a silent miss (§20.8).

20.7 Performance Concerns

Poisson sampling (mean 512 KiB inter-arrival) keeps per-allocation overhead near zero in steady state — most malloc calls take the fast "not sampled" branch. The futex tracer's 100 µs threshold filters out uncontended fast-path futex calls entirely (no BPF ringbuf write for sub-threshold waits).

20.8 Edge Cases

An allocation exactly at the sampling boundary is sampled or not per the Poisson draw — no special-cased off-by-one. A mutex acquired and released within the same nanosecond bucket (uncontended) never enters the wait-recording path at all — the shim distinguishes uncontended (fast) from contended (slow, timed) acquisition. FUTEX_WAIT_BITSET/FUTEX_LOCK_PI calls are counted separately as "unhandled variant," never conflated with FUTEX_WAIT.

20.9 Failure Analysis

A shim re-entrancy bug (missing guard) would deadlock the target process — caught in Phase 8's own fault-injection test (recursive malloc under the shim, §26.6) before it can reach production; detection in production would be via the target hanging with no forward metric progress, forensics via gdb on the frozen thread's stack.

20.10 Operational Notes

No new metrics beyond prof_samples_total{kind=Allocation|Free|LockWait} (reuses §14/§24.2 naming). PhaseDeferred register does not apply here — both profilers ship complete in Phase 0 scope; the futex variant gap is a documented limitation, not a deferral.

21. Phase 9 — Continuous-Profiling Agent, CLI, and Server

21.1 Objectives

Ship the operator surfaces: the prof CLI, the supervised continuous-profiling agent, and the ingestion/query server — the fleet-wide companion to every earlier phase (theory: Kaldor et al., "Canopy," SOSP 2017, §5; ADR-10, ADR-16, ADR-24).

21.2 Detailed Implementation Steps

  • prof-cli/main.rs: subcommands record [-F freq] [-d duration] -- <cmd>, report <profile>, flamegraph <profile>, diff <baseline> <new>, trace --otel-endpoint <url> -- <cmd>, attach --pid <pid> --uprobe <symbol@binary>, serve --listen <addr> — semantics mirror perf record (§21.1's record forks the target, attaches the sampler, writes pprof to out, default prof.pprof.gz).
  • prof-agent/supervisor.rs: Agent::run loops: collect a window_seconds-long sample window (default 10 s), build a pprof (§18), upload via the exporter; upload failure logs and retries next window rather than blocking (P8). The supervisor restarts a failed sampler; on max_pending_windows backlog, the oldest window is dropped (drop counter incremented, mirrors I1's discipline at the agent tier).
  • prof-server/http.rs (axum, ADR-16): POST /ingest/v1/profiles indexes by (service, instance, build-id, timestamp), writes to the object_store-backed tier (ADR-24: file:// dev default, s3:///gs:// production); GET /query/v1/profiles?service=...&from=...&to=... &type=cpu; GET /query/v1/render/flamegraph?profile_id=....
  • Authentication: Authorization: Bearer <key> on every prof-server endpoint; multi-tenant auth and mTLS are PhaseDeferred("§21") (ELv2 control-plane surface, ADR-10).
  • Window boundaries carry (start_ts, end_ts) in nanoseconds precisely, because the analysis tier joins windows across instances; cross-instance clock skew tolerated to 1 s (§4), beyond which the server records and flags the skew.

21.3 Deliverable

prof record -F 99 -d 10 -- ./examples/cpu-bound produces a valid pprof; the agent runs 60 s against the same target, uploads 6 windows, and GET /query/v1/profiles?service=cpu-bound returns 6 entries; make compose-up brings agent + server + Grafana up together.

  • CLI record/flamegraph outputs match §18's fixtures exactly.
  • Agent 60 s run uploads exactly 6 windows (±0, deterministic window boundary); server query returns exactly 6 matching entries.

21.6 Pitfalls

  • The supervisor must not retry an unrecoverable error (verifier rejection, missing CAP_PERFMON, missing kernel headers) — these report once and the agent exits (P14).
  • The 10 s window is a trade-off (finer timelines vs. upload load); ADR-level default, tunable per deployment.

  • Object-store credential misconfiguration surfaces at first upload attempt, not silently — runbook/symbol-store-down.md (§24.3) covers the operator response.

21.7 Performance Concerns

Agent steady-state CPU (M9, ≤ 0.5% of one core) and RSS (M10, ≤ 100 MiB) are gated by P3 (offline symbolization) — the agent never materializes symbol tables. gRPC vs HTTP transport choice (ADR-15) applies identically to the profile-upload path when gRPC ingestion is enabled.

21.8 Edge Cases

A target that exits mid-window yields a partial (but structurally valid) profile, uploaded as- is rather than discarded. Two agents uploading windows with overlapping (start_ts, end_ts) for the same (service, instance) is treated as instance restart/redeploy, not corruption — the server's query API returns both, timestamp-ordered. A build-id absent from the store at query time returns the profile un-symbolized (offline-mode contract, P3) rather than erroring.

21.9 Failure Analysis

Ingestion server crash/restart is stateless (all state in the object store, ADR-24); RTO ≤ 60 s (§4). Agent supervisor exhausting sampler restarts (3 consecutive failures) exits cleanly with a diagnostic log rather than looping silently — the failure class is named in §23 FM3.

25. Compatibility & Versioning

  • Wire compatibility: pprof and OTLP are frozen external formats (I10–I12); this runtime never emits a variant the upstream pprof/opentelemetry-collector tooling rejects.
  • Storage schema evolution: the ingestion server's object-store layout ((service, instance, build-id, timestamp), §21.2) is additive-only within a major version — new optional fields, never a repurposed key.
  • API stability: the prof-server HTTP API (§21.2, OpenAPI at docs/api/openapi.yaml) is SemVer'd independently of the CLI; a breaking API change requires a major-version bump and a documented migration path.
  • SDK stability: the Tracer/Span/Context/SpanExporter traits (§11.6–§11.7, P11) are the longest-lived public surface — a breaking change here breaks every sibling project (Ranking 26, 49) that binds against it; changes require a deprecation window (§25's SemVer policy: one minor version deprecated before removal).
  • Rolling-upgrade guarantee: agents and servers on adjacent minor versions interoperate; a major-version agent upgrade requires the server to be upgraded first (server is backward-compatible with N-1 agent major versions for one release cycle).
  • Deprecation policy: deprecated fields/endpoints are marked in CHANGELOG.md, emit a Deprecated response header (HTTP) or doc-comment (SDK), and are removed no sooner than the next major version.

29. Scalability Analysis

Constant regardless of fleet size: per-thread ring capacity (4 MiB), MAX_STACK_DEPTH (127), per-sample record size (§11.3) — all fixed at compile time, not fleet-size-dependent.

Grows with fleet size (Big-O): symbol-table memory across the analysis tier — O(distinct build-ids × avg symbols/module) (§32); ingestion-server storage — O(instances × windows/day × window size); query-API latency — O(matching windows) per query, mitigated by the (service, instance, build-id, timestamp) index (§21.2).

Named bottlenecks, in order: (1) symbol-resolution throughput at the analysis tier under a query-time burst (M6 sets the per-core ceiling); (2) ingestion-server object-store write throughput under a synchronized fleet-wide upload burst (all agents on the same window boundary); (3) the per-thread ring's fixed capacity under an unexpectedly bursty sampling target (I1 fails open by design — this is a fidelity bottleneck, not an availability one).

Horizontal scaling: prof-server instances are stateless (object store is the shared state, ADR-24) — scale by adding instances behind a load balancer; no coordination overhead between them beyond the shared store's own consistency model.

Vertical scaling / sharding: the object store itself shards by (service, instance) prefix naturally (S3/GCS key-space partitioning); no application-level sharding logic needed at Phase-0 scale.

Practical ceiling and levers beyond it: at fleet sizes beyond ~10K instances, upload burst synchronization (bottleneck 2) becomes dominant; the lever is jittering each agent's window start by a random offset (0–10 s) to desynchronize uploads — a Phase-1 agent-config surface, not yet in Phase-0 scope (not deferred via PhaseDeferred since it is a tuning knob, not a feature).

30. Mental Models & First Principles

  1. MM1 — A profiler is a sampling statistician, not a debugger. Insight: every sampled profile carries Poisson measurement error; it predicts that a rare-but-expensive function can be statistically invisible at low Hz. Bug class without it: treating "absent from the profile" as "not costly." Applied in §4 (Hz choice) and §28.1 (methodology).
  2. MM2 — The signal handler runs inside another program's undefined-behavior boundary. AS-safety is the literal edge of defined behavior, not a style guideline. Predicts: any libc call outside signal-safety(7) is a latent deadlock. Bug class: silent hangs under signal delivery. Applied in §12 (P1) and §14 (I2).
  3. MM3 — Build-id is identity; path is address. Like a stable node id vs. a mutable network address. Predicts symbol mismatches across redeploys/containers when identity is path-keyed. Bug class: silently-wrong symbolication that looks plausible. Applied in §13 and §17.
  4. MM4 — A stack is a reconstructed proof of causality, not raw data. The CPU destroys the call chain on every ret; unwinding is inference from what survives (frame pointers, DWARF metadata), not observation. Predicts unwinding is fundamentally lossy when metadata is missing. Bug class: trusting a partial/garbage stack as ground truth instead of marking it [unknown]. Applied in §16 and §8.
  5. MM5 — A span is a distributed causal token, not a log line. Dapper/X-Trace's insight: causality must travel with the request, not be reconstructed after the fact from timestamps. Predicts cross-service causality is unrecoverable without explicit propagation. Bug class: broken or truncated traces at service boundaries. Applied in §19 and §8.
  6. MM6 — The exporter owns time; the producer owns none. Separating "produce" from "decide when to flush/batch/retry" is what keeps a hot path bounded. Predicts any producer that also does I/O will blow its own latency budget. Bug class: a hot-path p99 regression traced to an inline batching decision. Applied in §6 (P8) and §19.
  7. MM7 — Don't let the profiler measure itself with the wrong ruler. Overhead must be measured as the target's wall-clock delta with/without the agent attached — never via perf stat on the agent process, which measures the wrong subject entirely. Predicts a team can convince itself of a false low-overhead number. Bug class: publishing an unverified M1/M2 claim. Applied in §28 and §12.
  8. MM8 — Offline symbolization trades agent memory for query-time latency. Shipping (build-id, offset) defers cost to the analysis tier, valid because query volume is much less than ingest volume. Predicts a naive "resolve on the agent" design blows the RSS budget at fleet scale even though it looks fine on a single dev box. Bug class: agent OOM in production. Applied in §17 and §32.

  • Linux perf wins for single-host, single-invocation, ad hoc investigation with zero setup cost — it has no fleet-wide continuity story at all, which is precisely the gap continuous profiling (§21) exists to fill; this runtime's compare.perf conformance bucket (§26) uses perf as the ground-truth reference for unwind quality, not as an architecture competitor.
  • Pyroscope/Parca are this runtime's closest architectural siblings — continuous, low- overhead, pprof-compatible, fleet-wide — differing mainly in implementation language and in this runtime's tighter coupling to a single in-process SDK for trace correlation (§19) rather than treating tracing as a separate product.

32. Back-of-Envelope Capacity Model

Assumed reference fleet (order-of-magnitude, stated explicitly, not asserted as fact): 200 services x 10 instances = 2,000 instances; 16 sampled threads/instance; 50 req/s/instance; 5 spans/request.

  1. On-CPU producer write rate/instance = frequency_hz (99, §4) x sampled_threads (16) = 1,584 samples/s, then x Sample size (1,024 B, §4/§11) = 1.62 MB/s produced into rings (transient, freed at drain — not network traffic).
  2. Ring memory ceiling, system-wide = max concurrent sampled threads (4,096, §4) x ring capacity (4 MiB, §4) = 16 GiB theoretical worst case — a safety bound, never a working-set target (P10's arena discipline keeps steady state far below it).
  3. Span/OTLP ingest bandwidth, per instance = req/s (50) x spans/req (5) x ~300 B/span (serialized OTLP) = 75,000 B/s = 75 KB/s/instance; fleet aggregate = x 2,000 = 150 MB/s.
  4. Profile-window upload bandwidth, per instance = upload budget (<=256 KiB, §4) / window (10 s, §4) = 25.6 KiB/s/instance; fleet aggregate = x 2,000 = ~51.2 MB/s.
  5. Symbol-table memory, worst case (all modules loaded) = distinct build-ids (~200, one per service) x symbol cardinality limit (500,000, §4) x avg interned-symbol size (~40 B) = ~4 GB — the number P3/I14's offline-symbolization-plus-LRU-eviction design avoids paying per agent (M10's 100 MiB budget would be violated ~40x over without it).
  6. DWARF-only unwind cost, per instance (worst case, no frame pointers) = 1,584 samples/s (item 1) / M4 (200,000 stacks/s, §4/§28) = ~0.79% of one core — comparable to the entire M9 budget (<=0.5% of one core), which is why ADR-18 prefers frame pointers (M5: 5,000,000 stacks/s) whenever the target opts in.
  7. Aggregate fleet agent CPU tax = M9 (<=0.5% of one core) x 2,000 instances <= 10 cores continuous-profiling overhead across the whole fleet.
  8. Ingestion hot-tier storage, 30-day retention = instances (2,000) x windows/day (86,400 s / 10 s window = 8,640) x avg compressed window size (~100 KiB, within the <=256 KiB budget, §4) x retention (30 days, §4) ~ 51.8 TB — motivates the S3/GCS object-store choice (ADR-24) over local disk.
  9. Max sampling frequency for a stricter overhead ceiling = using M1's calibration point (99 Hz -> 1% overhead, near-linear in this regime): max_hz ~ 99 x (target_overhead_pct / 1%) — e.g. a 0.3% target yields ~30 Hz, the lever an operator pulls per §24's overhead-regression runbook.

34. Alternative Architectures (Roads Not Taken)

Alt-A — Compiler/binary instrumentation instead of sampling

 source --> [instrumented counters/calls] --> binary --> exact call graph + counts

Regime where it wins: exhaustive, exact call-count coverage (e.g. fuzzing-coverage instrumentation) where wall-clock overhead is acceptable and precision matters more than production safety. Real embodying system: gprof/Intel Pin-style binary instrumentation. Rejected here because instrumentation overhead scales with call frequency, not wall-clock time — a hot inlined function called billions of times would dominate overhead in a way no Hz-based budget (M1/M2, §4) can bound, violating P2.

Alt-B — Tail-based sampling instead of head-based sampling

 all spans --> [buffer full trace] --> sample decision after trace completes (keep slow/error)

Regime where it wins: guaranteeing capture of every slow/error trace even at a low overall sampling rate — valuable when interesting traces are rare. Real embodying system: OpenTelemetry Collector's tail_sampling processor / Honeycomb Refinery. Rejected here because tail sampling requires buffering entire traces at the collector before deciding, which is memory-bound and conflicts with the stateless, per-window agent design (M10, §21) this runtime commits to.

Alt-C — eBPF-only sidecar collector instead of an in-process SDK

 target (unmodified) <-- uprobes/socket-tracing -- [sidecar: eBPF + protocol parsers] --> export

Regime where it wins: closed-source targets or mixed-language fleets with no shared SDK to link against. Real embodying system: Pixie / Cilium Hubble. Rejected as the primary mechanism here because pure eBPF/socket-level tracing cannot see application-level semantics (span names, business attributes) without protocol-specific parsers — it loses the causal richness Dapper- style tracing needs (§31); this runtime instead uses eBPF as a complement (§15's uprobe/USDT attach) alongside, not instead of, the in-process SDK (§19).

Alt-D — Fully decentralized pull-based profiling instead of a fleet server

 operator --> GET /debug/pprof (per instance, on demand) -- no fleet-wide store

Regime where it wins: small fleets, interactive single-instance debugging with zero infrastructure. Real embodying system: Go's built-in net/http/pprof. Rejected as the fleet-wide default here because it has no durable retention (§25), no cross-instance window correlation (§21), and does not scale to the query patterns of §29 — though prof-cli's report/flamegraph subcommands (§21) still support this exact on-demand, no-server workflow for local development.

36. Glossary

  • AS-safety (async-signal-safety): the property that a function may be safely called from within a signal handler; the hard floor on the §14 producer path (P1, I2).
  • SIGPROF: the POSIX signal used to deliver profiling timer interrupts to a thread.
  • perf_event_open(2): the Linux syscall opening a kernel performance-counter/sampling fd.
  • SPSC ring: single-producer, single-consumer lock-free ring buffer; the §14 producer's data structure.
  • Build-id: a GNU-convention 20-byte identifier (.note.gnu.build-id) uniquely identifying a compiled binary, stable across redeploys (I4, ADR-09).
  • ELF: Executable and Linkable Format, the Linux binary/object-file container format.
  • DWARF: the standard debugging information format; source of line tables and unwind info.
  • CFI (Call Frame Information): DWARF's per-instruction description of how to recover the previous stack frame.
  • .eh_frame / .debug_frame: the two DWARF CFI section flavors — runtime (exception unwinding) and debugger-only, respectively.
  • FDE / CIE: Frame Description Entry / Common Information Entry — the two DWARF CFI record types evaluated during unwinding (§8.3).
  • ORC (Oops Rewind Capability): the Linux kernel's internal unwind format, used kernel-side by bpf_get_stackid() (ADR-19).
  • Frame pointer: the rbp(x86_64)/fp(aarch64) register convention enabling fast stack walking when the binary opts in (-fno-omit-frame-pointer).
  • Symbolization: resolving an instruction pointer to (function, file, line).
  • Demangling: reversing a compiler's name-mangling scheme (Itanium C++, Rust v0) to a human-readable symbol.
  • Inline-frame expansion: reporting the full call chain for an address inside an inlined function, not just the outer function.
  • StackTable: the parent-pointer-tree structure deduplicating shared stack prefixes (§11.5).
  • SymbolId / StackId: interned 32-bit handles standing in for a resolved string or a full stack, respectively (P9).
  • pprof: Google's protobuf-based profile interchange format (google/pprof/profile.proto).
  • Folded stack: Brendan Gregg's func1;func2;func3 count text encoding, the flamegraph renderer's input format.
  • Flamegraph: Gregg's SVG visualization where stack width encodes sample count.
  • Speedscope / Chrome Trace: ancillary operator-facing profile visualization formats.
  • OTLP (OpenTelemetry Protocol): the wire protocol for exporting traces/metrics/logs to a collector, over HTTP or gRPC.
  • Span: a single named, timed operation with attributes, events, and a status, the unit of distributed tracing.
  • Trace: the causally-linked tree of spans sharing one TraceId.
  • traceparent / tracestate: the W3C Trace Context HTTP headers propagating trace identity across service boundaries (§8.2).
  • Causal ordering: the guarantee that a child span's start time is never before its parent's (I9).
  • Head-based sampling: deciding whether to sample a trace at its start, before its outcome is known (contrast: tail-based, §34 Alt-B).
  • Poisson sampling: a sampling discipline where events are selected with independent, memoryless probability — the heap profiler's allocation-sampling model (§20).
  • Off-CPU profiling: measuring time a thread spends blocked (I/O, futex, sleep) rather than executing.
  • Lock contention: time threads spend waiting to acquire a lock rather than holding it.
  • Futex: the Linux fast userspace mutex primitive; FUTEX_WAIT/FUTEX_WAKE are the syscall operations the §20 lock-contention tracer hooks.
  • LD_PRELOAD: the dynamic-linker environment variable causing a shared library to be loaded before others, enabling function interposition (the §20 heap shim's mechanism).
  • jemalloc: an allocator with built-in sampling-profiler support, an alternative heap- profiling path to the LD_PRELOAD shim (ADR-17).
  • LSan (LeakSanitizer): an LLVM sanitizer whose leak-report text format the §20 leak detector's output is compatible with.
  • eBPF: the Linux kernel's verified, sandboxed in-kernel bytecode execution facility.
  • BPF verifier: the kernel component statically proving an eBPF program's safety before load.
  • CO-RE (Compile Once — Run Everywhere): the eBPF technique for kernel-struct-layout portability across kernel versions via BPF_CORE_READ relocations.
  • Tracepoint: a static, kernel-defined instrumentation point (e.g. sched_switch) eBPF programs can attach to.
  • Uprobe / USDT: dynamic (uprobe) and static (USDT, via .note.stapsdt) user-space instrumentation points eBPF programs attach to for zero-source-change tracing.
  • ringbuf: the BPF_MAP_TYPE_RINGBUF kernel-to-userspace event-delivery map type (kernel 5.8+).
  • Capability (CAP_PERFMON/CAP_BPF): Linux fine-grained privileges gating perf_event_open/BPF-program loading (I13).
  • Continuous profiling: always-on, low-overhead, fleet-wide sampling with durable retention and historical query (§21, contrast with perf's ad hoc single-host model, §31).
  • Ingestion server: the fleet-wide component (prof-server) accepting uploaded profiles and exposing the query API.
  • Object store: the pluggable durable storage backend (file:///s3:///gs://) behind the ingestion server (ADR-24).
  • Profile window: a bounded (default 10 s) sampling interval the continuous-profiling agent uploads as one unit.
  • RTO (Recovery Time Objective): the maximum acceptable time to restore service after a failure (§4, §23 FM7).
  • LRU (Least Recently Used): the symbol-cache eviction policy, pinned against active build-ids (I14).
  • Arena allocator: a bump-pointer allocation strategy freeing an entire region at once (P10's per-window and interner arenas).
  • Symbol table: the in-memory mapping from SymbolId to resolved string (§11.4).
  • Mangled name: a compiler-encoded symbol name requiring demangling to be human-readable.
  • Last Branch Record (LBR): an Intel CPU feature recording the last N taken branches, usable for partial stack reconstruction without unwinding.
  • ptrace(2): the Linux syscall for process inspection/control; notably not used by this runtime's primary sampling path (ADR-03 rejects a ptrace-dependent unwinder).
  • vDSO: the kernel-mapped virtual dynamic shared object present in every process's address space, a special case in the §13 /proc/<pid>/maps classifier.
