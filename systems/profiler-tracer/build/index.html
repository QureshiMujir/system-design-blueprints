⬜ Phase 0 — Skeleton, Governance, and the Sampling Smoke Test §12

Objectives

Stand up the repository (§10) at the production-scaffold bar; land governance files; ship a "Hello, sample" smoke test that proves the SIGPROF + per-thread-ring path (P1, I1, I2) end to end with no unwinding yet — (timestamp_ns, tid, ip) only.

Deliverable

make bootstrap && make build && make test all exit 0; the smoke test forks examples/cpu-bound, samples at 99 Hz for 1 s, and prints a non-zero sample count.

Acceptance
  • make test passes with ≥ 1 test exercising the smoke sample; sample count within ±5% of 99.
  • ADR-01, ADR-02, ADR-10, ADR-13, ADR-21 written to docs/adr/.
  • Fixture conformance/corpora/overhead/cpu-bound-baseline.json recorded (unsampled wall-clock).
Fixtures
Fixture Purpose Expected Output
overhead/cpu-bound-baseline.json unsampled wall-clock of examples/cpu-bound denominator for M1 (§28)
overhead/cpu-bound-99hz.json same target, 99 Hz sampling on ratio < 1% vs baseline
Pitfalls
  • SIGPROF is per-thread via timer_create+SIGEV_THREAD_ID, per-process via setitimer(ITIMER_PROF) — Phase 0 uses the former; the latter would multiplex onto one timer and break the per-thread ring model (I1).
  • IP location in ucontext_t is architecture-specific (REG_RIP on x86_64, uc_mcontext.pc on aarch64); signal_handler.c ifdefs per arch (ADR-02).
  • Small thread stacks without sigaltstack risk overflow when the handler runs on the main stack; document and ship a helper.
  • Rust's AS-safety lints reject most of std; the handler stays in csrc/signal_handler.c by design (ADR-01), never ported to Rust.

⬜ Phase 1 — Process Model and Module Table §13

Objectives

Attach to a target pid, parse its memory map, identify every loaded ELF object, extract its GNU build-id, and expose Process::module_for_address (§11.1) — the lookup every later phase queries (P4, I4; theory: Levine, Linkers and Loaders, §5).

Deliverable

Process::attach(pid) returns a fully populated Process for a live target; a test asserts libc.so.6 appears in the module table with a non-zero build-id.

Acceptance
  • Process::module_for_address(rip) returns the correct Module for the calling thread's current IP, verified against /proc/self/maps ground truth, 100% of 1,000 sampled addresses.
  • A dlopen test on a synthetic .so shows up in refresh_modules() output within one call.
  • Fixture process/maps-edge-cases.txt (§13.5) classifies every line correctly.
Fixtures
Fixture Purpose Expected Output
process/maps-edge-cases.txt anonymous/vDSO/vsyscall/[stack]/[heap]/multi-segment ELF every line classifies correctly
process/build-id-mismatch.bin ELF with malformed .note.gnu.build-id loads with build_id: None + BuildIdMalformed warning
Pitfalls
  • /proc/<pid>/maps lines can omit pathname for anonymous regions; parser handles the truncated form (fixture above).
  • The dev field is MAJOR:MINOR for file-backed VMAs, 0:0 for anonymous; do not parse it strictly as always-present.
  • Go binaries carry .note.go.buildid in addition to (usually) the GNU note; ADR-09 locks GNU build-id as canonical — Go binaries resolve via the GNU note when present (nearly always, since Go links libc).
  • Kernel /proc format drift across LTS releases (5.10 vs 6.6) — tested against both (§26.7).

⬜ Phase 2 — User-Mode Sample Acquisition §14

Objectives

Acquire samples portably, without eBPF: the per-thread SPSC ring (P1, I1), the SIGPROF handler (I2), and the perf_event_open(2) hardware-counter path — the two backends behind the one Sampler trait (§11.9, P13; theory: Desnoyers & Dagenais, LTTng ring design, §5).

Deliverable

SigprofSampler records 99 Hz samples from examples/cpu-bound with < 1% overhead (M1); PerfSampler opens PERF_COUNT_HW_CPU_CYCLES, mmaps the ring, drains into Vec<Sample>.

Acceptance
  • Overhead measured against §12.5's baseline: < 1% at 99 Hz (M1), < 5% at 999 Hz (M2).
  • Drop-rate test at a synthetic 100 kHz rate: drop counter > 0, runtime keeps running (I1).
  • PerfSampler sample count within ±5% of frequency_hz × duration_s (fixture below).
Fixtures
Fixture Purpose Expected Output
sample/sigprof-99hz.json 99 Hz, 10 s on cpu-bound < 1% overhead, 0 drops
sample/perf-cycles.json PERF_COUNT_HW_CPU_CYCLES, same target sample count within ±5% of 99×10
Pitfalls
  • perf_event_open has no glibc wrapper — invoke via syscall(2) directly; the header (perf_event.h) may lag the running kernel, so a vendored copy pinned to the target kernel ships in ebpf/vmlinux.h's sibling headers.
  • perf_event_attr's set_freq/set_disabled bitfield setters have been inverted in some libc crate versions — test against the actual kernel ABI, never trust crate docs alone.
  • The mmap'd perf_event_open ring must be a power-of-two ≥ page size; default 64 KiB/fd.
  • A SIGPROF delivered inside pthread_mutex_lock deadlocks if the handler allocates — exactly what P1/I2 forbid; this is the fault the §26.6 injection harness specifically targets.

⬜ Phase 3 — eBPF Sampling Backend §15

Objectives

Lift the two limits of §14's user-mode path: sample threads in other processes without code injection, and capture off-CPU stacks. Land the CPU-profile BPF program, the off-CPU sched_switch program, and uprobe/USDT attach (P13, I13; theory: Gregg & Goldshtein, BPF Performance Tools, §5; ADR-05).

Deliverable

EbpfCpuSampler collects on-CPU samples from examples/cpu-bound with kernel-side stack-ids resolved; OffCpuSampler records blocking events from examples/lock-contended; a uprobe smoke test fires on every call into examples/usdt-probed.

Acceptance
  • Distinct kernel-side stack-id count ≤ 16 for the tight-loop target (bounded program shape).
  • Off-CPU 90th-percentile blocked_for_ns within ±10% of the recorded fixture value.
  • Every BPF program in this phase passes the verifier on both kernel 5.10 LTS and 6.6 (§26.7).
Fixtures
Fixture Purpose Expected Output
ebpf/cpu-stackids.json distinct stack-id + sample count, cpu-bound stack-ids ≤ 16, count within ±5%
ebpf/offcpu-blocked.json blocked-time distribution, lock-contended p90 within ±10%
ebpf/usdt-probe.json probe-fire count, deterministic loop exact match
Pitfalls
  • The verifier rejects unbounded loops, unaligned reads, and out-of-order helper calls; every program here is checked against both supported kernels in CI (§26.7).
  • bpf_get_stack() truncates at MAX_STACK_DEPTH; deeper stacks are marked truncated (I6), never silently shortened without a flag.
  • ringbuf needs kernel 5.8+; older kernels fall back to BPF_MAP_TYPE_PERF_EVENT_ARRAY (ADR-05 documents the fallback path).
  • perf_event_open for system-wide sampling needs CAP_PERFMON (or CAP_SYS_ADMIN pre-5.8); the agent's systemd unit grants exactly this, nothing broader (I13).

⬜ Phase 4 — Stack Unwinder §16

Objectives

Turn a sampled IP into a stack of IPs via three dispatch-by-module implementations behind one Unwinder trait (§11.10, P5, I5; theory: DWARF v5 section 6.4, Levine ch. 8; ADR-03).

Deliverable

FpUnwinder walks examples/cpu-bound's stack to depth ≥ 5 with zero [unknown] frames; DwarfUnwinder walks the same source compiled with -fomit-frame-pointer to matching depth; dispatch across a stack crossing an FP module into a DWARF-only module unwinds correctly through both (I5).

Acceptance
  • unwind.fp and unwind.dwarf conformance buckets: unwound stack matches recorded (function, line) tuples exactly, 7-function synthetic call chain (§16.5).
  • DWARF throughput ≥ 200K stacks/s (M4); FP throughput ≥ 5M stacks/s (M5), both on reference hardware (§4).
  • A truncated .eh_frame fixture returns a partial stack with [unknown] at the truncation point, never a wrong frame (I7).
Fixtures
Fixture Purpose Expected Output
unwind/fp-canonical.bin 7-function chain, frame pointers exact (function,line) match
unwind/dwarf-canonical.bin same source, -fomit-frame-pointer exact (function,line) match
unwind/dwarf-truncated.bin artificially truncated .eh_frame partial stack + [unknown] at cut
unwind/jit-perf-map.txt synthetic JIT scenario every JIT-range IP resolves via the map
Pitfalls
  • .eh_frame (runtime, C++ exception personality) and .debug_frame (debugger-only) interpret CFI rules slightly differently; gimli abstracts the difference — do not hand-roll either.
  • DW_CFA_GNU_args_size is a widely-used non-standard opcode; gimli handles it, custom walkers commonly miss it.
  • FP walking can read into freed stack pages after a longjmp; always go through StackMemory (§11.10), which bounds reads to the thread's mapped stack range — never raw pointer deref.
  • aarch64 uses link-register (lr) + frame-record (fp) conventions distinct from x86_64's rbp/return-address pair; both are fixtured (§16.5, ADR-02).

⬜ Phase 5 — Symbolizer §17

Objectives

Resolve an IP to (function, file, line), expanding inline frames, across three lookup paths behind one Symbolizer trait (§11.11, P9, ADR-04; theory: Levine ch. 8, §5).

Deliverable

Symbolizer::resolve returns Vec<Frame> for an IP in cpu-bound with function/file/ line populated and inline frames expanded; throughput ≥ 100K resolutions/s cached (M6).

Acceptance
  • Three-level #[inline] fixture (§17.5) returns exactly three Frames, two marked is_inlined: true.
  • A stripped-binary fixture returns the function name via .symtab with line == 0.
  • C++ and Rust demangling fixtures assert exact-string match; a Go-binary fixture asserts a non-empty result via .symtab fallback (Go's .gopclntab is PhaseDeferred("§17")).
Fixtures
Fixture Purpose Expected Output
symbol/inlined-3-deep.bin 3-level Rust #[inline] chain all 3 frames returned
symbol/stripped.bin binary with no .debug_info .symtab fallback, line==0
symbol/cpp-templated.bin C++ templated functions exact Itanium-demangled strings
symbol/rust-v0.bin Rust v0-mangled symbols exact rustc_demangle strings
Pitfalls
  • Context::find_frames's iterator silently truncates if not drained to completion — always exhaust it.
  • .debug_line can map one address to multiple (file,line) entries (macros, headers); resolve by highest column when present, else the last entry.
  • Build-id mismatch (sample from v1.2.3, resolved against v1.2.4 on disk) gives plausible-but- wrong results silently — the #1 symbolizer failure mode; the build-id-keyed cache (I14) fails closed on an unknown id rather than guessing.
  • glibc alone ships 100K+ symbols; size the interner pool accordingly (§32 capacity model); M10's 100 MiB RSS budget assumes offline symbolization (P3), not an in-agent symbol table.

⬜ Phase 6 — Aggregation, pprof, and Flamegraphs §18

Objectives

Collapse millions of samples into a compact StackTable (§11.5), encode to pprof (I10, I11), and render folded-stack and flamegraph SVG output (theory: Gregg, "The Flame Graph," CACM 2016, §5; ADR-06, ADR-14).

Deliverable

Aggregator accumulates 1M samples into ≤ 10K distinct stacks for cpu-bound; ProfileBuilder::finish emits gzip pprof go tool pprof -raw accepts cleanly; the flamegraph renderer emits an SVG geometry-identical to Gregg's reference flamegraph.pl output.

Acceptance
  • pprof output is bytewise-identical to the recorded fixture, modulo timestamps (I11, compare. pprof_clean bucket, §26.4).
  • Flamegraph SVG geometry bytewise-matches the fixture (CSS may differ, §18.5 fixture).
  • Off-CPU and differential renders reuse the same DOM layout (verified by fixture, §18.5).
Fixtures
Fixture Purpose Expected Output
pprof/cpu-bound.pprof.gz 10 s @ 99 Hz, cpu-bound bytewise match modulo timestamps
pprof/heap-alloc.pprof.gz 10 s, alloc-heavy alloc-objects total within ±1%
flamegraph/cpu-bound.svg SVG for the above bytewise geometry match
flamegraph/diff-baseline-vs-new.svg differential render bytewise match
Pitfalls
  • string_table[0] must be "" (I10) — omitting it makes go tool pprof reject the profile.
  • period is in the units of period_type (nanoseconds for cpu) — confusing it with a raw frequency value corrupts every downstream total.
  • Location.address must be module-relative (IP minus mapping start), not absolute — absolute IPs make the profile symbolizable only against the exact mapping it was recorded against, defeating offline symbolization (P3).
  • Inline expansion belongs in Location.lines, not as extra Location records — the latter doubles location count and breaks UI grouping in every downstream pprof viewer.
  • Folded-stack separators are semicolons; a function name containing one (rare Rust-v0 closure case) must be escaped.

⬜ Phase 7 — Tracer SDK and OTLP Exporter §19

Objectives

Land the in-process Tracer/Span/Context (§11.6, P11), the W3C traceparent propagator (I8), the batcher (P8), and the OTLP/HTTP+gRPC exporter (I12, ADR-07, ADR-15; theory: Sigelman et al., "Dapper," 2010; Fonseca et al., "X-Trace," NSDI 2007, §5).

Deliverable

Tracer::start→finish hot path measured ≤ 1 µs p99 (M7); OtlpHttpExporter exports a 512-span batch to a local OTel collector, ingested without warnings; a tracing-instrumented binary produces spans that arrive at the collector unmodified.

Acceptance
  • benchmarks/span_emit_latency.rs: p99 ≤ 1 µs (M7).
  • Round-trip test: span exported → ingested by upstream opentelemetry-collector → re-exported → deserialized — bytewise-equivalent except collector-added resource attributes (I12).
  • traceparent parse→emit round-trip matches byte-for-byte (I8, fixture below).
Fixtures
Fixture Purpose Expected Output
otlp/single-span.otlp.bin one finished span bytewise-equal OTLP body
otlp/parent-child.otlp.bin parent/child pair span-id linkage preserved
otlp/with-events.otlp.bin span with 3 events event-time ordering preserved
otlp/traceparent-roundtrip.json recorded header SDK parse/re-emit matches
Pitfalls
  • OTLP requires raw bytes for trace_id/span_id on the protobuf wire — JSON uses hex; sending hex on protobuf is silently accepted by the upstream collector but breaks downstream indexing by trace (§8.6).
  • A finished span dropped by a full batcher queue must never propagate as an application error — only the drop counter signals it.
  • tracing::Field::Debug values become meaningless "Foo { .. }" strings if not flattened into structured KeyValues before crossing into OTel.
  • Resource attributes (service.name, service.version, host.name) must be identical across every span in one batch — some collectors accept per-span drift, many reject it.
  • Instant::now() has no epoch; OTLP time_unix_nano must derive from SystemTime::now(), captured at span start alongside Instant (ADR-25).

⬜ Phase 8 — Heap and Lock-Contention Profilers §20

Objectives

Two specialized profilers reusing the §14–§18 sampling/unwinding/symbolizing/aggregation stack: an LD_PRELOAD heap-allocation sampler with leak detection, and an eBPF futex-based lock-contention tracer (ADR-17, ADR-05).

Deliverable

prof-heap records a 95th-percentile allocation-sample distribution for examples/alloc-heavy and emits pprof with period_type=("alloc-objects","count")/("alloc-space","bytes"); prof-lock records the lock-wait distribution for examples/lock-contended matching the recorded fixture within ±10% at p90.

Acceptance
  • Alloc-objects total in the emitted pprof within ±1% of the recorded fixture.
  • Leak report for a deliberately-leaking binary matches the LSan-compatible fixture format.
  • Futex-wait p90 within ±10% of the recorded distribution; ProfMutex::lock records the Location::caller() site on every contended acquire.
Fixtures
Fixture Purpose Expected Output
heap/alloc-heavy.pprof.gz recorded heap profile alloc-objects total within ±1%
heap/leak-report.txt deliberately-leaking binary matches LSan-compatible format
lock/contended-distribution.json futex-wait distribution p90 within ±10%
Pitfalls
  • LD_PRELOAD does not intercept statically-linked allocators — documented (ADR-17); static targets use the jemalloc-native path.
  • dlsym(RTLD_NEXT, "malloc") itself allocates on first call — a naive shim re-enters and deadlocks; fixed with a thread-local in_malloc_shim guard suppressing recursive recording.
  • Some libc functions (getaddrinfo) call malloc from signal-adjacent contexts; the recording path must be as AS-safe as §14's SIGPROF discipline or it deadlocks identically.
  • FUTEX_WAIT_BITSET and FUTEX_LOCK_PI variants are not handled by the Phase-0 futex tracer — a documented known gap, not a silent miss (§20.8).

⬜ Phase 9 — Continuous-Profiling Agent, CLI, and Server §21

Objectives

Ship the operator surfaces: the prof CLI, the supervised continuous-profiling agent, and the ingestion/query server — the fleet-wide companion to every earlier phase (theory: Kaldor et al., "Canopy," SOSP 2017, §5; ADR-10, ADR-16, ADR-24).

Deliverable

prof record -F 99 -d 10 -- ./examples/cpu-bound produces a valid pprof; the agent runs 60 s against the same target, uploads 6 windows, and GET /query/v1/profiles?service=cpu-bound returns 6 entries; make compose-up brings agent + server + Grafana up together.

Acceptance
  • CLI record/flamegraph outputs match §18's fixtures exactly.
  • Agent 60 s run uploads exactly 6 windows (±0, deterministic window boundary); server query returns exactly 6 matching entries.
  • prof attach --uprobe denied without CAP_PERFMON/CAP_BPF returns a clean, actionable error, never a silent failure (I13).
Fixtures
Fixture Purpose Expected Output
cli/record-99hz-10s.txt prof record sample/drop/upload-size within ±5% of recorded
server/query-profiles.json GET /query/v1/profiles response OpenAPI schema match
Pitfalls
  • The supervisor must not retry an unrecoverable error (verifier rejection, missing CAP_PERFMON, missing kernel headers) — these report once and the agent exits (P14).
  • The 10 s window is a trade-off (finer timelines vs. upload load); ADR-level default, tunable per deployment.
  • The upload path must never block the sampler; it sits behind a bounded MPSC channel, oldest window dropped on full (mirrors §19.2's batcher discipline).
  • Object-store credential misconfiguration surfaces at first upload attempt, not silently — runbook/symbol-store-down.md (§24.3) covers the operator response.
