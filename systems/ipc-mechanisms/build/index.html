⬜ Phase 0 — Repo Skeleton & Correctness Kernel §12

Objectives

Stand up the Cargo workspace (§10), the three ipc-core traits, WaitQueue, IpcError, and ipc-verifier's deterministic-simulator skeleton — the correctness kernel every later phase builds on. No IPC primitive is implemented yet; this phase only builds the contract all five will implement.

Deliverable

cargo build --workspace succeeds; ipc-verifier runs an empty trace and reports "0/14 invariants wired" without panicking; CI green on both matrix legs.

Acceptance

cargo test --workspace passes with ≥ 20 trait-dispatch unit tests; cold workspace build completes in < 90 s (§4 startup budget applies to the dev loop, not just runtime); CI matrix shows 2/2 legs green; fixture core/trait_dispatch.fixture passes.

Fixtures
Fixture Purpose Expected Output
core/trait_dispatch.fixture confirms &self-only trait methods compile under concurrent access compiles + passes under loom model-checking
core/waitqueue_wake_one.fixture confirms default wake discipline is wake-one exactly 1 waiter observes wake per push
core/error_enum_nonexhaustive.fixture confirms downstream crates can match IpcError without exhaustiveness breakage compiles after a variant is added
Pitfalls
  • A trait method taking &mut self makes shared access impossible across the FD-table boundary; all three traits use &self with interior mutability from the start (P6).
  • Wiring wake_all as the default "to get tests passing faster" bakes in thundering herd (T8) that is expensive to unwind once call sites depend on it.
  • An IpcError declared #[non_exhaustive] too late forces a breaking change across every downstream crate; declare it non-exhaustive in Phase 0.

⬜ Phase 1 — Anonymous Pipes §13

Objectives

Implement ipc-pipe::Pipe: the page-list ring buffer (ADR-23), PIPE_BUF atomicity (I3), and the SIGPIPE/EPIPE delivery ordering (I2) — the load-bearing correctness property of the entire pipe primitive.

Deliverable

ipc-pipe::Pipe with read, write, poll, close; passes conformance/buckets/pipe/.

Acceptance

pipe/atomicity.fixture passes for writes up to 4,096 B under 8-thread contention; pipe/sigpipe.fixture passes 10,000 iterations with zero ordering violations (I2); write throughput ≥ 2 GB/s per core on 64 KiB writes (M1); F_SETPIPE_SZ-equivalent resize succeeds up to 1 MiB and rejects above it with EINVAL.

Fixtures
Fixture Purpose Expected Output
pipe/atomicity.fixture I3 under contention no interleaved bytes at ≤ PIPE_BUF
pipe/sigpipe.fixture I2 ordering EPIPE + SIGPIPE on every last-reader-close write
pipe/nonblock.fixture O_NONBLOCK on full/empty EAGAIN, never blocks
pipe/malformed_resize.fixture resize beyond 1 MiB EINVAL, buffer unchanged
Pitfalls
  • The reader-zero check happening before the count decrement (instead of after) produces a duplicate-wake under high churn — order is decrement → check → wake (I2).
  • O_NONBLOCK on a full buffer must return EAGAIN immediately, not after entering the wait queue and timing out — a common off-by-one in the blocking/non-blocking branch.
  • Writes larger than PIPE_BUF interleaving is correct per POSIX, not a bug — do not "fix" it by holding the mutex for the whole large write (defeats P6/P8's fairness goal).

⬜ Phase 2 — Named Pipes (FIFOs) §14

Objectives

Layer a filesystem-namespace name atop Pipe (§8.1) to produce Fifo, matching POSIX mkfifo(3) semantics, without duplicating the ring-buffer logic (P2).

Deliverable

ipc-pipe::Fifo + mkfifo/open syscall plumbing; passes conformance/buckets/fifo/.

Acceptance

fifo/open_block.fixture passes: reader-open blocks until writer-open within 50 ms of the writer arriving; fifo/nonblock_enxio.fixture passes: write-open with no reader and O_NONBLOCK returns ENXIO in 100% of 1,000 iterations; unlink-while-open leaves the underlying Pipe object alive (matches I4's sibling contract for shm).

Fixtures
Fixture Purpose Expected Output
fifo/open_block.fixture reader-blocks-until-writer unblocks within 50 ms of writer-open
fifo/nonblock_enxio.fixture write-open, no reader, nonblock ENXIO
fifo/unlink_while_open.fixture inode removed while fd open pipe object survives until last close
Pitfalls
  • Treating FIFO open-blocking as a special case of Pipe's read/write blocking (rather than a separate open-time rendezvous) misses the "two opens must rendezvous" semantics distinct from I3/I2's already-open blocking.
  • Deleting the FIFO's inode while open must not destroy the underlying Pipe; the pipe object persists via the open file description, an FD table interaction (§8.1) — this is the same lesson as I4's shm-unlink-while-mapped case, applied to filesystem-node pipes.

⬜ Phase 3 — Shared Memory & Futex Synchronization §15

Objectives

Implement ipc-shm::ShmRegion (§8.2, I4) and the futex-based synchronization layer atop raw shared bytes, addressing the memory-model/race issues that make shared memory the most dangerous of the five primitives.

Deliverable

ipc-shm + shm_open/shm_unlink/futex_wait/futex_wake syscalls; passes conformance/buckets/shm/.

Acceptance

shm/attach_latency.fixture: 64 MiB region attach p50 < 5 µs (M5); shm/unlink_while_ mapped.fixture passes (I4); shm/race_detector.fixture passes under a ThreadSanitizer- equivalent race detector with zero unsynchronized concurrent writes across 10,000 randomized sequences.

Fixtures
Fixture Purpose Expected Output
shm/attach_latency.fixture M5 p50 < 5 µs, p99 < 50 µs
shm/unlink_while_mapped.fixture I4 unlink succeeds, mapped pages remain readable
shm/race_detector.fixture T1 0 unsynchronized concurrent writes detected
shm/futex_wait_wake.fixture futex correctness wait returns only on matching wake or value change
Pitfalls
  • Assuming MAP_SHARED writes are ordered across attachments without an explicit futex/ fence is the single most common shared-memory bug (T1, MM2) — the region shares bytes, not synchronization.
  • shm_unlink while mapped does not free pages; confirmed POSIX-specified behavior (Kerrisk Ch. 54), not a bug to "fix."
  • A futex word placed across a cache-line boundary shared with unrelated data causes false sharing under high contention — align it to its own cache line.

⬜ Phase 4 — Message Queues §16

Objectives

Implement ipc-mq::Mqueue (§8.3): bounded, priority-ordered delivery (I5), with atomic oversize rejection (I13).

Deliverable

ipc-mq + mq_open/mq_unlink/mq_send/mq_receive/mq_notify; passes conformance/buckets/mqueue/.

Acceptance

mqueue/priority_order.fixture: 1,000,000 random-priority sends, 100% dequeue order matches the heap invariant (I5); mqueue/oversize.fixture: 100% of oversized sends rejected with EMSGSIZE and zero partial enqueues (I13); enqueue/dequeue p50 < 500 ns (M2).

Fixtures
Fixture Purpose Expected Output
mqueue/priority_order.fixture I5, FM-9 1M sends, 0 order violations
mqueue/oversize.fixture I13 EMSGSIZE, 0 partial writes
mqueue/notify_reregister.fixture duplicate mq_notify EBUSY on second registration
Pitfalls
  • A binary-heap sibling-swap bug during sift-up that swaps twice can leave the heap property locally valid but globally violated — manifests as occasional wrong-order delivery (FM-9); caught only by the 1M-random-send fixture, not small hand-written cases.
  • mq_notify re-registration before the first notice fires must return EBUSY, not silently replace the registration (§16.2, Stevens Vol. 2 Ch. 5).

⬜ Phase 5 — Unix Domain Sockets §17

Objectives

Implement ipc-unix-sock::UnixSocket (§8.4) for all three kinds — stream, dgram, seqpacket — as the "do-it-all" primitive, ahead of fd-passing (Phase 6, which extends this crate).

Deliverable

ipc-unix-sock::{Stream, Dgram, Seqpacket} + bind/listen/accept/connect; passes conformance/buckets/unix-sock/.

Acceptance

Stream throughput ≥ 5 GB/s per core (M7); dgram throughput ≥ 3 GB/s (M8); unix-sock/ truncation.fixture passes: an oversized dgram is truncated with the flag set, never silently dropped (P8); SO_RCVBUF-equivalent cap enforced per-process (T11 mitigation).

Fixtures
Fixture Purpose Expected Output
unix-sock/stream_throughput.fixture M7 ≥ 5 GB/s sustained
unix-sock/dgram_truncation.fixture oversized dgram truncated + flag set
unix-sock/peer_crash_epipe.fixture peer crash mid-write EPIPE + SIGPIPE on next write
unix-sock/bind_addrinuse.fixture stale socket file EADDRINUSE
Pitfalls
  • SO_RCVBUF without a per-process cap allows one socket to claim unbounded memory — cap it (T11, ADR-21).
  • A socket closed while the peer is mid-write must surface EPIPE + SIGPIPE on the peer's next write, matching Phase 1's I2 ordering discipline applied to sockets.
  • A stale socket file left by a previous bind causes EADDRINUSE on rebind — this is caller responsibility per POSIX, not a bug to auto-remediate (silently unlinking a stale socket file is itself a race with a live process still using it).

⬜ Phase 6 — FD Passing & Credentials §18

Objectives

Extend ipc-unix-sock with SCM_RIGHTS fd-passing (I6) and SCM_CREDENTIALS credential-passing (T10 mitigation) — the most security-sensitive code path in the project.

Deliverable

ipc-unix-sock extended with SCM_RIGHTS/SCM_CREDENTIALS; passes conformance/buckets/ fd-passing/ and conformance/buckets/credentials/.

Acceptance

FD pass p50 < 2 µs (M4); fd-passing/rollback.fixture: 100% refcount balance after induced sendmsg failure across 10,000 iterations (I6); credentials/spoof_rejected. fixture: 100% of user-supplied ucred-equivalent values rejected (T10).

Fixtures
Fixture Purpose Expected Output
fd-passing/sendfd_recvfd.fixture canonical pass pattern receiver gets a valid fresh FD to the same file
fd-passing/rollback.fixture I6 rollback 0 refcount imbalance after induced failure
fd-passing/cycle_rejected.fixture Phase-0 cycle rejection second half of a 2-socket cycle send fails
credentials/spoof_rejected.fixture T10 user-supplied creds ignored, kernel values used
Pitfalls
  • A sendmsg that bumps refcounts for N FDs then fails to queue (e.g., simulated ENOMEM) must decrement all N — missing this leaks file references (T3, FM-3), the historical Linux bug class this phase is built to avoid.
  • A message queued but never received (receiver crashes, or socket closes first) must be walked on socket destruction to decrement every FD reference — skipping this is the unix_destruct_scm leak class (FM-7).
  • Accepting user-supplied credential fields instead of kernel-populated ones is a direct privilege-escalation vulnerability (T10) — always populate from process state at send time, never from the message buffer.

⬜ Phase 7 — Semaphores, Mutexes, Condition Variables §19

Objectives

Implement ipc-sync::{Semaphore, Mutex, CondVar} (§8.5) as the process-shared synchronization primitives that shared memory (Phase 3) and application-level protocols build on, unifying the futex-based blocking discipline (ADR-08) across all three.

Deliverable

ipc-sync crate with Semaphore, Mutex, CondVar; passes conformance/buckets/sync/.

Acceptance

sync/sem_no_underflow.fixture: 0 negative-count observations across 100,000 randomized wait/post sequences (I11); sync/mutex_ownership.fixture: 100% of non-owner unlock attempts return EPERM (I12); sync/condvar_no_lost_wakeup.fixture: 0 lost wakeups across 10,000 signal-before-wait races.

Fixtures
Fixture Purpose Expected Output
sync/sem_no_underflow.fixture I11 count never negative, 100k iterations
sync/mutex_ownership.fixture I12 EPERM on non-owner unlock, 100%
sync/condvar_no_lost_wakeup.fixture lost-wakeup race 0 lost wakeups, 10k races
Pitfalls
  • Comparing a boolean "signaled" flag instead of a monotonic generation counter in CondVar reintroduces the lost-wakeup bug the generation counter exists to prevent.
  • Allowing unlock from any thread (skipping the owner check) silently permits double-unlock and use-after-unlock bugs that manifest only under contention (I12).
  • A semaphore post that doesn't wake exactly one waiter (P10) when multiple are blocked reintroduces the thundering-herd class this project otherwise avoids (T8, I9).

⬜ Phase 8 — Capability-Based Naming & Permission Model §20

Objectives

Build ipc-cap: a single capability object (CapToken/CapSet) that gates access to all five primitives uniformly (ADR-17, ADR-26), replacing per-primitive POSIX DAC-bit checks as the project's own access-control layer above the raw syscalls (P5, I7).

Deliverable

ipc-cap + dispatch wrapper wired into every primitive's syscall entry; passes conformance/buckets/capabilities/.

Acceptance

capabilities/check_before_alloc.fixture: 100% of syscall entry points show the capability check preceding any allocation, verified by ipc-verifier's instrumented trace replay (I7); capability check overhead ≤ 50 ns/op (M11); capabilities/deny_by_default. fixture: an ambiguous/missing token denies 100% of the time (P11).

Fixtures
Fixture Purpose Expected Output
capabilities/check_before_alloc.fixture I7 check precedes mutation, 100% of entry points
capabilities/deny_by_default.fixture P11 ambiguous state → deny
capabilities/bypass_audit_log.fixture any bypass logged 100% of bypasses produce an audit entry
Pitfalls
  • A capability check added after the resource is already allocated leaks the resource to an unauthorized caller before the check fires — check-then-allocate order is non-negotiable (I7).
  • A "temporary" DAC-bit fallback path added for POSIX differential-testing purposes (ADR-26's rejected-choice-wins regime) must still route through the audit log if it bypasses the capability check, or T2's detection story silently breaks.

⬜ Phase 9 — Readiness: Blocking/Non-blocking, poll/select/epoll §21

Objectives

Implement ipc-notify::Notifier (§11): the single readiness surface all five primitives plug into via Pollable (P4), covering both blocking and non-blocking modes and both level-triggered and edge-triggered notification (I8).

Deliverable

ipc-notify + epoll_create/epoll_ctl/epoll_wait-equivalent syscalls; passes conformance/buckets/notify/.

Acceptance

epoll_wait-equivalent wake p50 < 200 ns (M3), p99 < 5 µs (M9); notify/edge_trigger. fixture: exactly one wakeup per ready-transition across 10,000 synthetic transitions (I8); notify/exclusive_wake.fixture: exactly one of N registered waiters wakes per event (I9).

Fixtures
Fixture Purpose Expected Output
notify/edge_trigger.fixture I8 1 wakeup per transition, 10k trials
notify/level_trigger.fixture level semantics wakeup on every wait call while ready
notify/exclusive_wake.fixture I9/P10 exactly 1 of N waiters wakes
notify/drain_to_eagain.fixture edge-trigger drain discipline next transition observed only after EAGAIN
Pitfalls
  • A handle that transitions ready→not-ready→ready before the user calls wait produces only one wakeup under edge-triggered mode (I8) — this is correct per POSIX/epoll(7), not a missed-event bug; the user must drain to EAGAIN before the next ready fires observably (MM3, §32).
  • Registering many waiters on one handle without exclusive/wake-one semantics reproduces the thundering herd this project is built to avoid (T8) — default to wake-one (I9).
  • A missed wakeup (the opposite failure) is a hang, not a crash — the discipline of "wake on every state change, even one that looks redundant" is the safety net against it.

⬜ Phase 10 — Backpressure & Flow Control §22

Objectives

Implement ipc-flow::FlowController (§11): explicit high/low watermark signaling (I10) so every bounded channel in the project surfaces pressure to its producer instead of silently dropping or growing unbounded (P8, P9).

Deliverable

ipc-flow::FlowController wired into Pipe, Mqueue, and UnixSocket; passes conformance/buckets/flow/.

Acceptance

flow/watermark_no_overflow.fixture: 0 buffer-bytes observations exceeding high across 100,000 randomized producer/consumer rate combinations (I10); backpressure-signal-to- producer-resume latency < 100 ms after consumer resumes draining (M12); flow/hysteresis. fixture: no oscillation (rapid signal/clear toggling) at the high/low boundary.

Fixtures
Fixture Purpose Expected Output
flow/watermark_no_overflow.fixture I10 0 overflow observations, 100k trials
flow/hysteresis.fixture no boundary oscillation ≤ 1 signal/clear pair per drain cycle
flow/producer_resume_latency.fixture M12 resume signal < 100 ms after drain
Pitfalls
  • Setting high == low (no hysteresis gap) causes the controller to oscillate the backpressure signal on every single byte crossing the boundary — always leave a gap (e.g., high = 75%, low = 50% of capacity).
  • Applying backpressure by silently dropping instead of signaling violates P8 outright and produces invisible data loss indistinguishable from a network partition to the operator.
  • Sharing one FlowController across two logically independent channels reintroduces a cross-channel deadlock risk (FM-11) — one controller per bounded channel, always.

⬜ Phase 11 — Conformance, Differential Testing & Fuzz Hardening §23

Objectives

Assemble the full conformance/buckets/ suite (§10) into one CI-gated run, stand up the differential harness against Linux (P14), and launch the 30-day fuzz canary (M10) — the release-readiness gate for the whole project.

Deliverable

conformance/buckets/differential-linux/ green in CI; ipc-fuzz 30-day canary running with a live dashboard; a signed release is blocked from shipping while the canary reports an open finding.

Acceptance

Differential corpus (≥ 500 traced sequences) runs in CI in < 10 minutes with 100% match or an ADR-documented divergence for every mismatch; 30-day fuzz canary: 0 panics, 0 leaked FDs (M10); fuzz throughput ≥ 50,000 execs/s sustained (feeding the §34 capacity-model row 10 derivation).

Fixtures
Fixture Purpose Expected Output
differential-linux/corpus_replay.fixture P14 100% match or ADR-documented divergence
fuzz/multi_primitive_race.fixture cross-primitive bug class 0 panics across 24h local run
fuzz/canary_dashboard.fixture 30-day canary health live panic/leak counters at 0
Pitfalls
  • Treating every Linux divergence as a bug to match exactly, rather than distinguishing "POSIX-mandated behavior we must match" from "Linux-specific quirk we may intentionally diverge from," produces an unmaintainable pile of undocumented special cases — every divergence gets an ADR (P14).
  • Gating every PR on the full 30-day canary (rather than treating it as a release gate) stalls the entire team on an inherently slow signal — the canary informs releases, not commits.
