Project Number: 149

Project Name: IPC Mechanisms

Owner: Mujir Qureshi

1. Goal & Scope

Definition. Build a POSIX-conformant, capability-gated suite of inter-process communication (IPC) primitives — anonymous pipes, named pipes (FIFOs), shared-memory segments with futex/semaphore synchronization, priority message queues, and Unix-domain sockets with fd-passing — plus the readiness (poll/select/epoll-equivalent) and backpressure layers that make them usable at production throughput, in Rust, verified differentially against Linux.

Phase-0 deliverable (numbered modules):

  1. ipc-core — Pollable/Readable/Writable traits, WaitQueue, PollMask, IpcError.
  2. ipc-pipe — anonymous pipe (Pipe) skeleton with page-list buffer.
  3. ipc-syscall — syscall shim boundary (the ABI the rest of the workspace calls through).
  4. ipc-verifier — deterministic simulator asserting System Invariants (§7) from day one.
  5. conformance/buckets/pipe/ — first conformance bucket, exercised by CI.

System boundaries.

  • Provides: in-process-tree and same-host IPC; capability-checked access; readiness notification; explicit backpressure.
  • Delegates: virtual-memory mapping mechanics to the host kernel's mmap (this project does not reimplement a VM subsystem); network transport (this is same-host only).
  • Does NOT provide: cross-host transport, RDMA, encryption at rest for shared memory (PhaseDeferred("§15")), a general-purpose serialization framework (ADR-05 fixes the wire format), Windows/macOS support (PhaseDeferred("§1")).

Non-goals: replacing a message broker (Kafka-class); providing durable/replicated queues; implementing a distributed transaction protocol.

Deployment model: a linked library (Rust crates) consumed by same-host processes; no daemon is required except where a broker pattern is explicitly chosen (ADR-26 keeps per-primitive kernel objects, not a broker, as the default).

Target users/operators: systems engineers building container runtimes, shells, databases, and sandboxed multi-process applications; on-call engineers debugging stuck pipelines.

What later phases unlock: Phase 3 (shared memory) unlocks zero-copy bulk transfer; Phase 8 (capabilities) unlocks a uniform security model across all five primitives; Phase 10 (backpressure) unlocks safe unbounded-producer workloads.

Language: Rust — memory safety for kernel-adjacent buffer manipulation (no use-after-free on WaitQueue nodes), a real unsafe-fenced FFI boundary to the raw syscalls, and a type system that makes the five primitives' divergent ownership rules (ADR-02) checkable at compile time. Rejected: C (no memory-safety net for the FD-refcount and page-list bookkeeping that is the majority of this project's bug surface); Go (GC pauses violate the p99 latency budget in §4); C++ (feasible, but the crates.io fuzzing/property-testing ecosystem, ADR-13, is materially stronger in Rust).

Prerequisites: process/thread scheduling, virtual memory basics, POSIX signal semantics, syscall ABI conventions, basic queueing theory.

Estimated timeline: Phase 0 — 2 weeks. Full system (Phases 0–11) — 7 months.

Deferred features (see §37 for the full register): PhaseDeferred("§36") an io_uring-style async submission ring; PhaseDeferred("§17") abstract-namespace sockets and a netlink-style socket family; PhaseDeferred("§18") a full cyclic garbage collector for SCM_RIGHTS graphs; PhaseDeferred("§15") encrypted/MAC-protected shared memory; PhaseDeferred("§31") a cross-host RDMA-backed bridge; PhaseDeferred("§1") Windows/macOS portability shims; PhaseDeferred("§19") a priority-inheriting futex upgrade for ipc-sync mutexes.

2. Why Build This

IPC is the systems-programming topic where the textbook description ("one process writes, a pipe carries bytes, another process reads") and the production reality (twenty years of accreted edge cases: SIGPIPE ordering, PIPE_BUF atomicity, SCM_RIGHTS refcount transfer, epoll thundering herd, vmsplice page-stealing) diverge the most sharply of any OS subsystem. Building this teaches: kernel object lifetime management across process boundaries; the exact difference between a capability and a name; the memory-model implications of shared memory without a language-level Send/Sync boundary; and the queueing-theory reasoning behind backpressure.

Architecturally/historically: every OS studied here made a different tradeoff — Linux kept five separate syscall families (pipe/SysV/POSIX/socket/futex); Mach unified around message-passing ports; seL4 chose synchronous rendezvous for a formally verified minimal TCB; Android's Binder chose a single-copy broker-free driver; D-Bus chose a broker-mediated bus atop AF_UNIX. Studying all five in one project is the fastest way to internalize the full IPC design space (§33).

Engineering muscles built: reasoning about concurrent state without a garbage collector; capability-based security design (§20); readiness-driven event loops (§21); flow control under backpressure (§22); differential testing against a reference kernel (§28).

Cross-links to sibling systems: the page-list buffer design mirrors project #148's (virtual memory subsystem) buddy-allocator magazine reuse (§30); the capability model here is the same shape as a capability-based filesystem ACL project; the differential-testing harness (§28) is the same methodology as a network-protocol conformance suite.

Calibration value: IPC bugs are silent-until-they-aren't — a missed wakeup or a leaked FD looks fine in a demo and pages someone at 3 a.m. six months later. This project calibrates the reader's sense for "looks done" vs. "is done."

What Mastery Looks Like

  • Can explain, from memory, why Linux's pipe buffer is a page-list and not a single contiguous allocation, and reproduce the argument in §13.
  • Can trace the exact ordering of "reader count → zero" → wakeup → SIGPIPE delivery and name the bug class each wrong ordering produces (§13, §25 FM-2).
  • Can design a capability token that gates all five primitives uniformly, and defend it against a per-primitive DAC-bit design (§20, ADR-17, ADR-26).
  • Can compute, from the System Constraints table alone, the memory ceiling of an unbounded producer and explain why backpressure is a protocol decision, not an implementation detail (§22, §34).
  • Can name the exact refcount-transfer sequence SCM_RIGHTS performs and the two ways it leaks (§18, §25 FM-3, FM-7).
  • Can distinguish edge-triggered from level-triggered readiness and predict the missed- wakeup bug class edge-triggered introduces (§21, §32 MM3).
  • Can redesign the system as synchronous rendezvous (seL4-style) or broker-mediated (D-Bus-style) and state exactly which of this project's invariants each alternative breaks or trivializes (§36).

Userspace processes — producers, consumers, and peers; may run at different privilege levels (§20 capability boundary is the trust boundary here). ipc-cap — every syscall entry passes through a capability check before any object is touched or allocated (I7); this is the security boundary. IPC objects — the five primitives, each a distinct kernel-side struct with its own state machine (§8); all implement the three ipc-core traits, which is the concurrency-boundary contract (interior-mutability, &self methods). ipc-flow — every object with an unbounded producer risk reports a watermark; this is the persistence/memory boundary — nothing here is bounded by default without it (P9). ipc-notify — the single readiness surface all five plug into; this is the protocol/queue boundary between "data moved" and "someone was told." The one defining property: every operation that can block or allocate unboundedly must be capability-checked (I7) and watermark-guarded (I10) before it touches kernel state — this single property is what makes the five primitives composable under load instead of independently correct but jointly capable of exhausting memory or file descriptors.

6. Design Principles

  • P1 — POSIX-compatible semantics. Every primitive's observable behavior is specified by reference to POSIX.1-2017 first. Tradeoff: rules out faster non-conformant shortcuts. Operational implication: the differential harness (§28) is the ground truth. Violate it and callers' POSIX-conformant assumptions (e.g., PIPE_BUF atomicity) silently break.
  • P2 — One implementation per primitive. No shared code path hides divergent semantics across pipe/mq/shm/socket. Tradeoff: more code, more maintenance surface. Operational implication: each primitive's bug is isolated to its own crate. Violate it and a "generic channel" abstraction leaks the wrong semantics into the wrong primitive.
  • P3 — Zero-copy where the kernel allows. splice/vmsplice are first-class, not bolted on. Tradeoff: page-ownership transfer complexity (T4). Operational implication: throughput targets (M6) are unreachable without it. Violate it and the 10 GB/s target (§4) is unreachable on the copy path alone (2 GB/s ceiling, M1).
  • P4 — Unified readiness model. One epoll-style surface (ipc-notify) for all five primitives via Pollable. Tradeoff: an extra trait-dispatch indirection. Operational implication: one wakeup discipline to reason about, not five. Violate it and every primitive reinvents its own (probably inconsistent) blocking model.
  • P5 — Capabilities gate every operation. No IPC object is touched without a capability check (§20). Tradeoff: ~50 ns/op overhead (M11). Operational implication: security audits check one chokepoint, not five. Violate it and privilege escalation (T2) becomes reachable through whichever primitive's check was skipped.
  • P6 — No global state in the fast path. Per-object and per-CPU data only; no global mutex. Tradeoff: more per-object bookkeeping. Operational implication: throughput scales with cores (§31). Violate it and a single global lock becomes the ceiling at low core counts.
  • P7 — Determinism in panic/failure paths. Cleanup order is fixed and tested, not best-effort. Tradeoff: extra explicit teardown code. Operational implication: crash recovery (§25) has a known shape. Violate it and forensic postmortems (§25 Forensics column) become guesswork.
  • P8 — Explicit backpressure over silent drops. A full buffer surfaces as EAGAIN/ block, never a silently dropped message. Tradeoff: producers must handle backpressure explicitly. Operational implication: no invisible data loss. Violate it and a "fast" channel becomes a lossy one under load with no operator signal (T11).
  • P9 — Bounded resources everywhere. No unbounded queue, buffer, or FD table entry. Tradeoff: callers must size buffers up front (§4). Operational implication: memory ceilings are computable (§34). Violate it and a slow consumer becomes an OOM vector.
  • P10 — Wake-one over wake-all. Default wakeup discipline wakes exactly one waiter. Tradeoff: an extra "who's next" bookkeeping structure. Operational implication: no thundering herd under multi-waiter fan-out (T8). Violate it and CPU burns on redundant wakeups at scale.
  • P11 — Fail closed on capability/permission checks. Any ambiguous or missing capability state denies, never allows. Tradeoff: occasional false-negative denial needing an explicit grant. Operational implication: the default posture is safe. Violate it and a missing-capability bug silently allows instead of silently (and safely) denying.
  • P12 — Observability is first-class. Every invariant (§7) emits telemetry on violation, not just on crash. Tradeoff: instrumentation overhead in hot paths (bounded by M-series targets). Operational implication: production incidents are diagnosable from metrics alone (§26). Violate it and on-call has only strace and hope.
  • P13 — Every technique is theory-anchored. No IPC mechanism is implemented without citing the paper, book, or reference kernel it is drawn from (§5). Tradeoff: slower initial design (research before code). Operational implication: design reviews can challenge a decision against its source. Violate it and the design degrades into folklore no one can defend.
  • P14 — Differential testing is the ground truth. Where POSIX is ambiguous, Linux's observed behavior (via the differential harness, §28) resolves the ambiguity. Tradeoff: couples correctness to one reference kernel's quirks. Operational implication: divergence requires an explicit ADR, not a silent shortcut. Violate it and "conformant" becomes a matter of opinion instead of a passing test.

Debugging methodology. ipc-verifier runs a deterministic simulator that replays a recorded syscall trace against all fourteen invariants, one assertion per invariant, firing on the first violation with the exact trace offset — the same technique TigerBeetle and FoundationDB use for deterministic-simulation testing, applied here to IPC sequences instead of storage transactions.

8.2 Shared-memory segment

ShmRegion { id, size, pfn, attached_count, creator, futex_word: AtomicU32 }
States: CREATED → MAPPED(n≥1) ⇄ MAPPED(n-1) → UNLINKED(name gone, pages live while n>0) → FREED(n=0)

The futex_word is the synchronization primitive layered atop the raw shared bytes — the segment itself provides no ordering guarantee (MM2, §32); every mutation protocol built on a ShmRegion must define its own memory-ordering discipline (acquire/release pairs around the futex, per Linux futex(2)).

8.5 Semaphore / mutex / condvar

Mutex     { owner: AtomicOption<Tid>, waiters }   // I12
CondVar   { generation: AtomicU32, waiters }

Worked example (pipe + epoll producer/consumer): producer writes 4 KiB records to a pipe; consumer registers the pipe's read end with ipc-notify in level-triggered mode. Each write ≤ PIPE_BUF is atomic (I3); the consumer's epoll_wait-equivalent returns immediately whenever bytes are resident; consumer reads until EAGAIN, then re-waits.

Malformed-input example: mq_send with a 2 MiB payload against a queue configured with mq_msgsize = 1 MiB is rejected atomically with EMSGSIZE before any heap mutation (I13) — conformance fixture mqueue/oversize.fixture.

Failure-path example: a socket's peer crashes mid-write holding two SCM_RIGHTS FD references in-flight; on socket-close cleanup, ipc-unix-sock walks the queued-message list and decrements every FD reference (I6) before the socket object is freed — this is the unix_destruct_scm-equivalent path (§5 Linux reference implementation).

12. Phase 0 — Repo Skeleton & Correctness Kernel

12.1 Objectives

Stand up the Cargo workspace (§10), the three ipc-core traits, WaitQueue, IpcError, and ipc-verifier's deterministic-simulator skeleton — the correctness kernel every later phase builds on. No IPC primitive is implemented yet; this phase only builds the contract all five will implement.

12.2 Detailed Implementation Steps

Create the workspace Cargo.toml per §10's crate list. In ipc-core, define Pollable, Readable, Writable (P4 — one readiness contract for all primitives) with &self methods only (P6 — no &mut self, since objects are shared across threads/processes). Implement WaitQueue as a mutex-guarded VecDeque<WaiterRef> with wake_one/wake_all methods, defaulting call sites to wake_one (P10, I9). Define the IpcError enum (ADR-05 non-exhaustive so later phases add variants without a breaking change). Stand up ipc-verifier with an empty invariant-assertion registry keyed by I# (I1–I14 stubs, each a no-op assertion until its owning phase fills it in). Wire CI (ADR-14) with the Linux x86_64/aarch64 matrix.

12.3 Deliverable

cargo build --workspace succeeds; ipc-verifier runs an empty trace and reports "0/14 invariants wired" without panicking; CI green on both matrix legs.

12.4 Acceptance Criteria

cargo test --workspace passes with ≥ 20 trait-dispatch unit tests; cold workspace build completes in < 90 s (§4 startup budget applies to the dev loop, not just runtime); CI matrix shows 2/2 legs green; fixture core/trait_dispatch.fixture passes.

12.5 Conformance Fixtures

Fixture Purpose Expected Output
core/trait_dispatch.fixture confirms &self-only trait methods compile under concurrent access compiles + passes under loom model-checking
core/waitqueue_wake_one.fixture confirms default wake discipline is wake-one exactly 1 waiter observes wake per push
core/error_enum_nonexhaustive.fixture confirms downstream crates can match IpcError without exhaustiveness breakage compiles after a variant is added

12.6 Pitfalls

  • A trait method taking &mut self makes shared access impossible across the FD-table boundary; all three traits use &self with interior mutability from the start (P6).
  • Wiring wake_all as the default "to get tests passing faster" bakes in thundering herd (T8) that is expensive to unwind once call sites depend on it.
  • An IpcError declared #[non_exhaustive] too late forces a breaking change across every downstream crate; declare it non-exhaustive in Phase 0.

12.7 Performance Concerns

WaitQueue push/pop must not allocate on the hot path once warmed (pre-sized VecDeque); trait-object dispatch (dyn Pollable) is avoided in favor of monomorphized generics where the call site is known at compile time, to keep §4's sub-microsecond latency budgets reachable in later phases.

12.8 Edge Cases

Empty WaitQueue wake is a no-op, not a panic; concurrent add_waiter/remove_waiter during an in-flight wake must not double-wake or drop the waiter (verified under loom in Phase 0's fixtures, ahead of any real primitive existing).

12.9 Failure Analysis

A cargo build failure at this phase blocks all later phases — the blast radius is the entire project, which is why CI gates on this phase first. Detection: CI red. Recovery: fix and re-push; there is no partial-success state for a broken workspace root.

12.10 Operational Notes

No runtime deployment yet. Observability hooks: ipc-verifier's assertion registry is the foundation for every later phase's telemetry (P12) — its counter names (I1_violation … I14_violation) are fixed here and never renamed, since §26 dashboards key on them.

13. Phase 1 — Anonymous Pipes

13.1 Objectives

Implement ipc-pipe::Pipe: the page-list ring buffer (ADR-23), PIPE_BUF atomicity (I3), and the SIGPIPE/EPIPE delivery ordering (I2) — the load-bearing correctness property of the entire pipe primitive.

13.2 Detailed Implementation Steps

Implement PageList as a doubly-linked chain of PipeBuffer { page, offset, len } (§8.1, ADR-23 — rejects a single contiguous ring for fragmentation reasons, per Bovet & Cesati Ch. 19). Default capacity 16 pages / 64 KiB (§4); F_SETPIPE_SZ-equivalent resize up to 1 MiB. Writes ≤ PIPE_BUF (4,096 B) hold the buffer mutex for the entire write (I3); larger writes release the mutex between page-worths to let waiters proceed (P6). Implement the reader-count-drop → zero-check → wake → SIGPIPE sequence as a single critical section (I2) — this is the exact bug class documented in Stevens & Rago Ch. 15 and reproduced in the original project retrospective (§25 FM-2). Wire Pipe into Pollable/ Readable/Writable from ipc-core (P4).

13.3 Deliverable

ipc-pipe::Pipe with read, write, poll, close; passes conformance/buckets/pipe/.

13.4 Acceptance Criteria

pipe/atomicity.fixture passes for writes up to 4,096 B under 8-thread contention; pipe/sigpipe.fixture passes 10,000 iterations with zero ordering violations (I2); write throughput ≥ 2 GB/s per core on 64 KiB writes (M1); F_SETPIPE_SZ-equivalent resize succeeds up to 1 MiB and rejects above it with EINVAL.

13.5 Conformance Fixtures

Fixture Purpose Expected Output
pipe/atomicity.fixture I3 under contention no interleaved bytes at ≤ PIPE_BUF
pipe/sigpipe.fixture I2 ordering EPIPE + SIGPIPE on every last-reader-close write
pipe/nonblock.fixture O_NONBLOCK on full/empty EAGAIN, never blocks
pipe/malformed_resize.fixture resize beyond 1 MiB EINVAL, buffer unchanged

13.6 Pitfalls

  • The reader-zero check happening before the count decrement (instead of after) produces a duplicate-wake under high churn — order is decrement → check → wake (I2).
  • O_NONBLOCK on a full buffer must return EAGAIN immediately, not after entering the wait queue and timing out — a common off-by-one in the blocking/non-blocking branch.
  • Writes larger than PIPE_BUF interleaving is correct per POSIX, not a bug — do not "fix" it by holding the mutex for the whole large write (defeats P6/P8's fairness goal).

13.7 Performance Concerns

Mutex held only for the buffer manipulation, not the full copy_from_user-equivalent region, except where the source page might be concurrently unmapped; page allocation uses a per-CPU magazine (P6; cross-links to project #148's buddy allocator, §2). Splice/ vmsplice (P3) bypass the copy path entirely for the zero-copy target (M6, ADR-23).

13.8 Edge Cases

Zero-length write returns 0 without blocking; a pipe with 0 readers and 0 writers is collected; a write exactly equal to the remaining buffer capacity must not spuriously report EAGAIN; concurrent close() on both ends races the refcount path (I1) and must not double-free the PageList.

13.9 Failure Analysis

A reversed I2 ordering is a silent correctness bug (FM-2): writers hang instead of receiving EPIPE. Detection: pipe/sigpipe.fixture in CI; production detection via sigpipe_order_violation_total (I2 telemetry). Blast radius: any pipeline relying on SIGPIPE-driven shutdown (every POSIX shell) hangs instead of terminating. Recovery: fix the ordering, re-run the fixture 10,000× before re-release.

13.10 Operational Notes

Metrics: pipe_bytes_written_total, pipe_bytes_read_total, pipe_refcount_negative_total (I1), sigpipe_order_violation_total (I2), pipe_atomicity_violation_total (I3). Runbook: "SIGPIPE storm" (§26). No migration concerns — Pipe has no persisted state across restarts.

14. Phase 2 — Named Pipes (FIFOs)

14.1 Objectives

Layer a filesystem-namespace name atop Pipe (§8.1) to produce Fifo, matching POSIX mkfifo(3) semantics, without duplicating the ring-buffer logic (P2).

14.2 Detailed Implementation Steps

Fifo wraps a Pipe plus an inode_path: PathBuf. mkfifo-equivalent creates a filesystem node of type S_IFIFO; open-for-read blocks until a writer opens (unless O_NONBLOCK, which returns immediately per POSIX); open-for-write with no reader and O_NONBLOCK returns ENXIO (Kerrisk Ch. 44, applied here). Reuses Pipe's I1–I3 invariants unchanged (P2 — no second implementation of atomicity or SIGPIPE ordering).

14.3 Deliverable

ipc-pipe::Fifo + mkfifo/open syscall plumbing; passes conformance/buckets/fifo/.

14.4 Acceptance Criteria

fifo/open_block.fixture passes: reader-open blocks until writer-open within 50 ms of the writer arriving; fifo/nonblock_enxio.fixture passes: write-open with no reader and O_NONBLOCK returns ENXIO in 100% of 1,000 iterations; unlink-while-open leaves the underlying Pipe object alive (matches I4's sibling contract for shm).

14.5 Conformance Fixtures

Fixture Purpose Expected Output
fifo/open_block.fixture reader-blocks-until-writer unblocks within 50 ms of writer-open
fifo/nonblock_enxio.fixture write-open, no reader, nonblock ENXIO
fifo/unlink_while_open.fixture inode removed while fd open pipe object survives until last close

14.6 Pitfalls

  • Treating FIFO open-blocking as a special case of Pipe's read/write blocking (rather than a separate open-time rendezvous) misses the "two opens must rendezvous" semantics distinct from I3/I2's already-open blocking.
  • Deleting the FIFO's inode while open must not destroy the underlying Pipe; the pipe object persists via the open file description, an FD table interaction (§8.1) — this is the same lesson as I4's shm-unlink-while-mapped case, applied to filesystem-node pipes.

14.7 Performance Concerns

Identical to Phase 1's Pipe once open — no additional per-byte cost from the filesystem name; the only overhead is the one-time open-rendezvous.

14.8 Edge Cases

Two writers racing to open the same FIFO for write; a reader opening in O_NONBLOCK mode before any writer exists returns immediately with an empty-but-open handle rather than blocking or erroring.

14.9 Failure Analysis

A FIFO whose inode is deleted mid-use and whose pipe object is incorrectly torn down produces EBADF for an in-flight reader — detection via fifo/unlink_while_open.fixture; recovery is a code fix, not an operational workaround, since this is a correctness bug not an environmental failure.

14.10 Operational Notes

Metrics inherited from Pipe (§13.10) plus fifo_open_rendezvous_latency_seconds. No new runbook needed — the SIGPIPE-storm runbook (§26) applies unchanged.

15. Phase 3 — Shared Memory & Futex Synchronization

15.1 Objectives

Implement ipc-shm::ShmRegion (§8.2, I4) and the futex-based synchronization layer atop raw shared bytes, addressing the memory-model/race issues that make shared memory the most dangerous of the five primitives.

15.2 Detailed Implementation Steps

shm_open-equivalent creates a named tmpfs-backed file (ADR-04); ftruncate-equivalent sizes it (≤ 1 GiB, §4); mmap-equivalent maps MAP_SHARED into the process's VMA tree (delegated to the host kernel per §1's system boundary — this project does not reimplement mmap). The region's lifetime is independent of the mapping's (I4): shm_unlink removes the name only; pages persist until the last attached_count drop. Layer a futex_word: AtomicU32 per region as the synchronization primitive (ADR-08; Linux futex(2)) — raw shared bytes provide no ordering guarantee without it (MM2, §32); every read/write protocol atop a region must define explicit acquire/release fences around the futex, documented per-protocol in docs/adr/.

15.3 Deliverable

ipc-shm + shm_open/shm_unlink/futex_wait/futex_wake syscalls; passes conformance/buckets/shm/.

15.4 Acceptance Criteria

shm/attach_latency.fixture: 64 MiB region attach p50 < 5 µs (M5); shm/unlink_while_ mapped.fixture passes (I4); shm/race_detector.fixture passes under a ThreadSanitizer- equivalent race detector with zero unsynchronized concurrent writes across 10,000 randomized sequences.

15.5 Conformance Fixtures

Fixture Purpose Expected Output
shm/attach_latency.fixture M5 p50 < 5 µs, p99 < 50 µs
shm/unlink_while_mapped.fixture I4 unlink succeeds, mapped pages remain readable
shm/race_detector.fixture T1 0 unsynchronized concurrent writes detected
shm/futex_wait_wake.fixture futex correctness wait returns only on matching wake or value change

15.6 Pitfalls

  • Assuming MAP_SHARED writes are ordered across attachments without an explicit futex/ fence is the single most common shared-memory bug (T1, MM2) — the region shares bytes, not synchronization.
  • shm_unlink while mapped does not free pages; confirmed POSIX-specified behavior (Kerrisk Ch. 54), not a bug to "fix."
  • A futex word placed across a cache-line boundary shared with unrelated data causes false sharing under high contention — align it to its own cache line.

15.7 Performance Concerns

Attach cost dominated by page-table setup, not data copy (memory-speed read/write once mapped); cross-NUMA attach incurs ≥ 2.5× local latency (§4) — pin producer/consumer to the same NUMA node where the capacity model (§34) assumes single-node.

15.8 Edge Cases

Two processes racing shm_open with O_CREAT | O_EXCL on the same name — exactly one succeeds (T5 mitigation); a region resized (ftruncate) after another process has already mapped it at the old size — the design ceiling (1 GiB) bounds worst-case waste but growth requires re-map, documented as a caller responsibility.

15.9 Failure Analysis

A missing futex/fence around a shared write manifests as an intermittent, load-dependent data corruption (T1) — the hardest class in this project to reproduce. Detection: the race-detector fixture in CI (deterministic under ipc-verifier's simulator) plus production race_detected_total telemetry (T1). Recovery: no auto-recovery; fail the conformance bucket and block release until the missing fence is added.

15.10 Operational Notes

Metrics: shm_attach_latency_seconds, shm_dangling_name_total (I4), race_detected_ total (T1). Runbook: none dedicated (race bugs are code fixes); the shm-cleanup tool (tools/, FM-4) reclaims orphaned tmpfs entries operationally.

16. Phase 4 — Message Queues

16.1 Objectives

Implement ipc-mq::Mqueue (§8.3): bounded, priority-ordered delivery (I5), with atomic oversize rejection (I13).

16.2 Detailed Implementation Steps

Mqueue holds a BinaryHeap<MqMsg> (ADR-24 — chosen over N parallel FIFOs for arbitrary priority-count generality). mq_send checks data.len() ≤ max_msg_size before any heap mutation (I13); on pass, inserts and wakes exactly one reader (P10, I9). mq_ receive pops the max-priority element and wakes one blocked writer if the queue was full. mq_notify-equivalent registers a one-shot empty→non-empty transition notice, ordered against concurrent mq_send via the same mutex that guards the heap (avoiding the register/fire race documented in Stevens Vol. 2 Ch. 5).

16.3 Deliverable

ipc-mq + mq_open/mq_unlink/mq_send/mq_receive/mq_notify; passes conformance/buckets/mqueue/.

16.4 Acceptance Criteria

mqueue/priority_order.fixture: 1,000,000 random-priority sends, 100% dequeue order matches the heap invariant (I5); mqueue/oversize.fixture: 100% of oversized sends rejected with EMSGSIZE and zero partial enqueues (I13); enqueue/dequeue p50 < 500 ns (M2).

  • A binary-heap sibling-swap bug during sift-up that swaps twice can leave the heap property locally valid but globally violated — manifests as occasional wrong-order delivery (FM-9); caught only by the 1M-random-send fixture, not small hand-written cases.
  • mq_notify re-registration before the first notice fires must return EBUSY, not silently replace the registration (§16.2, Stevens Vol. 2 Ch. 5).

16.7 Performance Concerns

Heap operations are O(log n) on max_msgs (design ceiling 65,536, §4) — at that ceiling, log₂(65536) = 16 comparisons per operation, still within the 500 ns budget (M2) on modern hardware; a compile-time-bounded low-priority-count deployment should instead choose ADR-24's rejected alternative (N FIFOs) for O(1).

16.8 Edge Cases

Two sends at the identical priority must dequeue FIFO-ordered (I5's "FIFO within equal priority" clause); a queue at exactly max_msgs rejects further sends with EAGAIN/blocks per the caller's blocking mode, never silently drops (P8).

16.9 Failure Analysis

Priority inversion (FM-9): a high-priority message waits behind low-priority ones due to a comparator bug. Detection: mqueue/priority_order.fixture; blast radius is any consumer relying on priority-ordered delivery for correctness (e.g., a control-plane message queued at high priority behind a data-plane flood). Recovery: fix comparator, re-run the 1M-fixture before re-release.

16.10 Operational Notes

Metrics: mq_depth_gauge, mq_priority_violation_total (I5), mq_oversize_rejected_ total (I13), mq_low_prio_age_seconds (T7 starvation signal). Runbook: none dedicated; depth-gauge trending toward max_msgs is the backpressure signal feeding §22.

17. Phase 5 — Unix Domain Sockets

17.1 Objectives

Implement ipc-unix-sock::UnixSocket (§8.4) for all three kinds — stream, dgram, seqpacket — as the "do-it-all" primitive, ahead of fd-passing (Phase 6, which extends this crate).

17.2 Detailed Implementation Steps

socketpair-equivalent returns a connected Arc<UnixSocket> pair sharing peer pointers; bidirectional I/O writes into the peer's recv_buf (a PageList, reusing ADR-23's design, P2 notwithstanding since this is intentional buffer-layout reuse, not logic reuse). Filesystem-named sockets (bind/listen/accept/connect) create an S_IFSOCK inode with an accept queue of pending connections, mirroring the FIFO discipline (§14.2). SOCK_DGRAM messages are atomic, queued as (message, source) pairs; oversized dgrams are truncated with a truncation flag surfaced to the caller (McKusick et al. Ch. 11). SOCK_SEQPACKET is connection-oriented, atomic, and ordered.

17.3 Deliverable

ipc-unix-sock::{Stream, Dgram, Seqpacket} + bind/listen/accept/connect; passes conformance/buckets/unix-sock/.

17.4 Acceptance Criteria

Stream throughput ≥ 5 GB/s per core (M7); dgram throughput ≥ 3 GB/s (M8); unix-sock/ truncation.fixture passes: an oversized dgram is truncated with the flag set, never silently dropped (P8); SO_RCVBUF-equivalent cap enforced per-process (T11 mitigation).

  • SO_RCVBUF without a per-process cap allows one socket to claim unbounded memory — cap it (T11, ADR-21).

17.8 Edge Cases

A connect to a non-existent path returns ENOENT; a dgram sent to an unbound socket is dropped at the kernel boundary (not this project's queue — outside our accept-queue model); simultaneous close() on both peers of a connected pair must not double-free the shared recv_buf.

17.9 Failure Analysis

A peer-crash mid-write that fails to surface EPIPE on the surviving side hangs the writer indefinitely — same blast radius as FM-2 (pipe SIGPIPE storm) but on the socket path; detection via unix-sock/peer_crash_epipe.fixture and production epipe_total.

18. Phase 6 — FD Passing & Credentials

18.1 Objectives

Extend ipc-unix-sock with SCM_RIGHTS fd-passing (I6) and SCM_CREDENTIALS credential-passing (T10 mitigation) — the most security-sensitive code path in the project.

18.2 Detailed Implementation Steps

A sendmsg-equivalent carrying SCM_RIGHTS looks up each sender-side FD's open-file entry, bumps its refcount, and attaches the reference to the queued message — before the message is queued (I6). On recvmsg-equivalent, the kernel allocates a fresh receiver-side FD pointing at the same open-file entry. A sendmsg that fails after bumping N refcounts must roll back all N (I6's rollback clause) — the "sendmsg cleanup" block, per the Linux reference implementation (§5). A socket destroyed with queued-but-unreceived SCM_RIGHTS messages walks the queue and decrements every reference (the unix_destruct_scm-equivalent path, §8.4 failure-path example). SO_PASSCRED-equivalent auto-attaches a kernel-sourced SocketCreds (pid/uid/gid) to every sendmsg on an enabled socket; user-supplied credential values are rejected outright (T10) — the kernel is the only writer of this field. Phase-0-scope cycle handling: reject a send that would create a two-socket SCM_RIGHTS reference cycle at send time (a full mark-and-sweep collector for the general cyclic case is PhaseDeferred("§18"), per §37).

18.3 Deliverable

ipc-unix-sock extended with SCM_RIGHTS/SCM_CREDENTIALS; passes conformance/buckets/ fd-passing/ and conformance/buckets/credentials/.

18.4 Acceptance Criteria

FD pass p50 < 2 µs (M4); fd-passing/rollback.fixture: 100% refcount balance after induced sendmsg failure across 10,000 iterations (I6); credentials/spoof_rejected. fixture: 100% of user-supplied ucred-equivalent values rejected (T10).

18.5 Conformance Fixtures

Fixture Purpose Expected Output
fd-passing/sendfd_recvfd.fixture canonical pass pattern receiver gets a valid fresh FD to the same file
fd-passing/rollback.fixture I6 rollback 0 refcount imbalance after induced failure
fd-passing/cycle_rejected.fixture Phase-0 cycle rejection second half of a 2-socket cycle send fails
credentials/spoof_rejected.fixture T10 user-supplied creds ignored, kernel values used

18.6 Pitfalls

  • A sendmsg that bumps refcounts for N FDs then fails to queue (e.g., simulated ENOMEM) must decrement all N — missing this leaks file references (T3, FM-3), the historical Linux bug class this phase is built to avoid.
  • A message queued but never received (receiver crashes, or socket closes first) must be walked on socket destruction to decrement every FD reference — skipping this is the unix_destruct_scm leak class (FM-7).
  • Accepting user-supplied credential fields instead of kernel-populated ones is a direct privilege-escalation vulnerability (T10) — always populate from process state at send time, never from the message buffer.

18.7 Performance Concerns

Refcount bump/decrement is an atomic increment, not a lock acquisition, keeping the M4 budget reachable; the cycle-rejection check (§18.2) adds one hash-lookup per send and must stay off the steady-state (acyclic) fast path's critical section.

18.8 Edge Cases

Sending 0 FDs with a non-empty SCM_RIGHTS cmsg (malformed, zero-length rights array); sending more FDs than the platform's SCM_MAX_FD-equivalent limit (rejected, not truncated); receiver closing the socket between recvmsg header parse and FD table allocation (must not leak the in-flight reference).

18.9 Failure Analysis

A refcount leak from a missed rollback (T3) is a slow kernel-object leak, invisible until /proc-equivalent FD accounting trends upward over days — detection via fd_refcount_ imbalance_total (I6) and the FD-exhaustion runbook (§26). A credential-spoofing bug (T10) is a silent privilege escalation with no crash signature at all — this is why credentials/spoof_rejected.fixture runs on every CI pass, not just periodically.

18.10 Operational Notes

Metrics: fd_refcount_imbalance_total (I6), fd_pass_latency_seconds (M4), cred_ spoof_attempt_total (T10), scm_rights_cycle_rejected_total (T9). Runbook: "FD leak in SCM_RIGHTS path" (§26).

19. Phase 7 — Semaphores, Mutexes, Condition Variables

19.1 Objectives

Implement ipc-sync::{Semaphore, Mutex, CondVar} (§8.5) as the process-shared synchronization primitives that shared memory (Phase 3) and application-level protocols build on, unifying the futex-based blocking discipline (ADR-08) across all three.

19.2 Detailed Implementation Steps

Semaphore::wait decrements count only if it would remain ≥ 0 (I11); otherwise blocks on the futex word backing count. Mutex::lock/unlock track owner: AtomicOption<Tid>; unlock by a non-owner returns EPERM without mutating state (I12) — the ownership check Robert Love's Linux Kernel Development Ch. 10 documents as the standard mutex contract. CondVar::wait atomically releases the paired mutex and blocks on a generation counter (preventing the classic lost-wakeup: a signal between "check condition" and "block" is not missed because the generation counter, not a boolean, is what's compared). All three use the futex-based blocking primitive from Phase 3 (ADR-08) rather than a spin loop, keeping CPU idle while blocked (P6).

19.3 Deliverable

ipc-sync crate with Semaphore, Mutex, CondVar; passes conformance/buckets/sync/.

19.4 Acceptance Criteria

sync/sem_no_underflow.fixture: 0 negative-count observations across 100,000 randomized wait/post sequences (I11); sync/mutex_ownership.fixture: 100% of non-owner unlock attempts return EPERM (I12); sync/condvar_no_lost_wakeup.fixture: 0 lost wakeups across 10,000 signal-before-wait races.

19.5 Conformance Fixtures

Fixture Purpose Expected Output
sync/sem_no_underflow.fixture I11 count never negative, 100k iterations
sync/mutex_ownership.fixture I12 EPERM on non-owner unlock, 100%
sync/condvar_no_lost_wakeup.fixture lost-wakeup race 0 lost wakeups, 10k races

19.6 Pitfalls

  • Comparing a boolean "signaled" flag instead of a monotonic generation counter in CondVar reintroduces the lost-wakeup bug the generation counter exists to prevent.
  • Allowing unlock from any thread (skipping the owner check) silently permits double-unlock and use-after-unlock bugs that manifest only under contention (I12).
  • A semaphore post that doesn't wake exactly one waiter (P10) when multiple are blocked reintroduces the thundering-herd class this project otherwise avoids (T8, I9).

19.7 Performance Concerns

Uncontended Mutex::lock/unlock must stay in userspace (an atomic compare-and-swap on the futex word) with zero syscalls — the syscall (futex_wait) is only reached on actual contention, per the ADR-08 rationale; this is the same fast/slow-path split Linux's own futex-based pthread_mutex_t uses.

19.8 Edge Cases

A Mutex whose owning thread exits without unlocking (no PI/robust variant in this phase — PhaseDeferred("§19") covers the priority-inheriting upgrade); a CondVar::wait racing a generation bump that happens between the atomic release-mutex-and-block steps must still observe the bump (no missed generation transition).

19.9 Failure Analysis

A lost wakeup (FM-12-adjacent) manifests as a consumer hanging despite the producer having already signaled — detection via the liveness watchdog pattern shared with FM-6 (epoll missed wakeup); recovery requires a code fix to the generation-counter comparison, not an operational workaround.

19.10 Operational Notes

Metrics: sem_underflow_total (I11), mutex_unlock_by_nonowner_total (I12), condvar_ lost_wakeup_total. No persisted state; no migration concerns.

20. Phase 8 — Capability-Based Naming & Permission Model

20.1 Objectives

Build ipc-cap: a single capability object (CapToken/CapSet) that gates access to all five primitives uniformly (ADR-17, ADR-26), replacing per-primitive POSIX DAC-bit checks as the project's own access-control layer above the raw syscalls (P5, I7).

20.2 Detailed Implementation Steps

Every IPC syscall entry point (pipe open, shm attach, mq open, socket connect, sem/mutex open) passes through ipc-cap's dispatch wrapper first (I7); the wrapper checks the calling process's CapSet for a matching CapToken{kind, target, rights} before any allocation occurs (P11 — fail closed on ambiguity). This follows the capability-vs-ACL distinction from Miller, Yee & Shapiro's "Capability Myths Demolished": a capability is an unforgeable, transferable reference bundling authority with designation — not a name checked against a separate permission table. Watson et al.'s Capsicum (USENIX Security 2010) is the closest real precedent: capability-mode restricts a process to operating only through FDs it already holds; ipc-cap generalizes that model to all five IPC object kinds, not just FDs. Every capability bypass (e.g., a legacy DAC-bit fallback path) is logged (T2 mitigation, P7).

20.3 Deliverable

ipc-cap + dispatch wrapper wired into every primitive's syscall entry; passes conformance/buckets/capabilities/.

20.4 Acceptance Criteria

capabilities/check_before_alloc.fixture: 100% of syscall entry points show the capability check preceding any allocation, verified by ipc-verifier's instrumented trace replay (I7); capability check overhead ≤ 50 ns/op (M11); capabilities/deny_by_default. fixture: an ambiguous/missing token denies 100% of the time (P11).

20.5 Conformance Fixtures

Fixture Purpose Expected Output
capabilities/check_before_alloc.fixture I7 check precedes mutation, 100% of entry points
capabilities/deny_by_default.fixture P11 ambiguous state → deny
capabilities/bypass_audit_log.fixture any bypass logged 100% of bypasses produce an audit entry

20.6 Pitfalls

  • A capability check added after the resource is already allocated leaks the resource to an unauthorized caller before the check fires — check-then-allocate order is non-negotiable (I7).
  • A "temporary" DAC-bit fallback path added for POSIX differential-testing purposes (ADR-26's rejected-choice-wins regime) must still route through the audit log if it bypasses the capability check, or T2's detection story silently breaks.

20.7 Performance Concerns

The 50 ns/op budget (M11) is a bitmap/hash-set lookup, not a linear scan — CapSet uses a hash set keyed by (kind, target) so the check stays O(1) regardless of how many tokens a process holds.

20.8 Edge Cases

A process holding a capability for ShmAccess on region A must not be able to use it against region B (target-scoped, not kind-scoped, matching); a revoked capability must take effect on the next syscall, not retroactively invalidate an already-open handle (documented semantics, not a bug).

20.9 Failure Analysis

A missing capability check (T2) is a privilege-escalation bug with no crash signature — detection is exclusively via the CI-gating verifier assertion (I7) and the cap_check_ missing_total telemetry; there is no runtime auto-recovery for a code path that never checks in the first place, only a CI merge-block.

20.10 Operational Notes

Metrics: cap_check_missing_total (I7, CI-only in practice), cap_check_latency_seconds (M11), cap_bypass_total (audit). Runbook: any bypass-log entry triggers a security review, not an automated remediation (P7's determinism ends at "log it," recovery is human).

21. Phase 9 — Readiness: Blocking/Non-blocking, poll/select/epoll

21.1 Objectives

Implement ipc-notify::Notifier (§11): the single readiness surface all five primitives plug into via Pollable (P4), covering both blocking and non-blocking modes and both level-triggered and edge-triggered notification (I8).

21.2 Detailed Implementation Steps

Notifier maintains a HashMap<FdHandle, Interest> (registered interests) and a ready: VecDeque<ReadyEvent> (the ready list, O(1) insert/remove, doubly-linked per the Linux reference implementation's design, §5). epoll_wait-equivalent drains the ready list immediately if non-empty; only blocks (on WaitQueue) if empty. Level-triggered mode fires whenever the handle is ready; edge-triggered mode fires exactly once per not-ready→ready transition (I8) — the caller must drain to EAGAIN before the next transition is observable, per Kerrisk Ch. 63's epoll(7) documentation of EPOLLET. Multiple Notifiers waiting on the same handle wake at most one by default (P10, I9) — an "exclusive" mode mirroring Linux's EPOLLEXCLUSIVE.

21.3 Deliverable

ipc-notify + epoll_create/epoll_ctl/epoll_wait-equivalent syscalls; passes conformance/buckets/notify/.

21.4 Acceptance Criteria

epoll_wait-equivalent wake p50 < 200 ns (M3), p99 < 5 µs (M9); notify/edge_trigger. fixture: exactly one wakeup per ready-transition across 10,000 synthetic transitions (I8); notify/exclusive_wake.fixture: exactly one of N registered waiters wakes per event (I9).

21.5 Conformance Fixtures

Fixture Purpose Expected Output
notify/edge_trigger.fixture I8 1 wakeup per transition, 10k trials
notify/level_trigger.fixture level semantics wakeup on every wait call while ready
notify/exclusive_wake.fixture I9/P10 exactly 1 of N waiters wakes
notify/drain_to_eagain.fixture edge-trigger drain discipline next transition observed only after EAGAIN

21.6 Pitfalls

  • A handle that transitions ready→not-ready→ready before the user calls wait produces only one wakeup under edge-triggered mode (I8) — this is correct per POSIX/epoll(7), not a missed-event bug; the user must drain to EAGAIN before the next ready fires observably (MM3, §32).
  • Registering many waiters on one handle without exclusive/wake-one semantics reproduces the thundering herd this project is built to avoid (T8) — default to wake-one (I9).
  • A missed wakeup (the opposite failure) is a hang, not a crash — the discipline of "wake on every state change, even one that looks redundant" is the safety net against it.

21.7 Performance Concerns

The ready list is doubly-linked and per-Notifier-instance (not global, P6), giving O(1) insert/remove and keeping epoll_wait-equivalent's non-blocking path a simple list drain, which is what keeps M3/M9 reachable.

21.8 Edge Cases

Registering interest in a handle that is already ready must return that readiness on the very next wait call, not require a fresh transition; de-registering a handle mid-wait must not leave a dangling ReadyEvent in the queue; a Notifier with zero registered interests blocks indefinitely on wait (correct — matches epoll_wait with an empty set).

21.9 Failure Analysis

A missed wakeup (FM-6) hangs the consumer indefinitely with no crash signature — detection via a liveness watchdog (no progress for N seconds) rather than a direct assertion, since the bug is an absence of an event, not a wrong one; recovery is a consumer restart operationally, and a code fix to the drain discipline permanently.

22. Phase 10 — Backpressure & Flow Control

22.1 Objectives

Implement ipc-flow::FlowController (§11): explicit high/low watermark signaling (I10) so every bounded channel in the project surfaces pressure to its producer instead of silently dropping or growing unbounded (P8, P9).

22.2 Detailed Implementation Steps

FlowController tracks bytes_buffered: AtomicUsize against a Watermark{high, low}. Enqueue past high rejects (or blocks, per caller mode) before the buffer actually grows past the ceiling (I10) — the signal precedes the overflow, not follows it. Once buffered bytes fall back to low, the controller clears the backpressure signal and the producer resumes (hysteresis between high and low avoids oscillation at the boundary — a standard queueing-theory technique, Tanenbaum & Bos §2). Every bounded primitive (Pipe's capacity, Mqueue's max_msgs, a socket's SO_RCVBUF-equivalent cap) is wrapped with a FlowController instance rather than reimplementing watermark logic per-primitive (P2's "no shared code path" is about primitive semantics, not this cross-cutting flow-control utility, which is intentionally shared).

22.3 Deliverable

ipc-flow::FlowController wired into Pipe, Mqueue, and UnixSocket; passes conformance/buckets/flow/.

22.4 Acceptance Criteria

flow/watermark_no_overflow.fixture: 0 buffer-bytes observations exceeding high across 100,000 randomized producer/consumer rate combinations (I10); backpressure-signal-to- producer-resume latency < 100 ms after consumer resumes draining (M12); flow/hysteresis. fixture: no oscillation (rapid signal/clear toggling) at the high/low boundary.

22.5 Conformance Fixtures

Fixture Purpose Expected Output
flow/watermark_no_overflow.fixture I10 0 overflow observations, 100k trials
flow/hysteresis.fixture no boundary oscillation ≤ 1 signal/clear pair per drain cycle
flow/producer_resume_latency.fixture M12 resume signal < 100 ms after drain

22.6 Pitfalls

  • Setting high == low (no hysteresis gap) causes the controller to oscillate the backpressure signal on every single byte crossing the boundary — always leave a gap (e.g., high = 75%, low = 50% of capacity).
  • Applying backpressure by silently dropping instead of signaling violates P8 outright and produces invisible data loss indistinguishable from a network partition to the operator.
  • Sharing one FlowController across two logically independent channels reintroduces a cross-channel deadlock risk (FM-11) — one controller per bounded channel, always.

22.7 Performance Concerns

The watermark check is a single atomic load compared against two constants — this must stay off any lock, since it runs on every enqueue across all three wrapped primitives; the 100 ms resume-latency budget (M12) is dominated by the consumer's drain rate, not the controller's own overhead (sub-microsecond).

22.8 Edge Cases

A consumer that stops draining entirely (not just slow) must still let the producer observe the backpressure signal indefinitely, not time out into silent dropping; two producers on the same channel racing to enqueue near the high watermark must not both "win" past the ceiling (the atomic compare-and-add is the arbiter).

22.9 Failure Analysis

A backpressure deadlock (FM-11) — two channels' watermarks form a circular producer/ consumer dependency — is detected by ipc-verifier's deadlock-detection timeout (the same simulator that checks I1–I14, extended with a wait-for-graph check); recovery is operator-driven (break the cycle by restarting one side), since automatic deadlock resolution would require killing a live, otherwise-healthy process.

22.10 Operational Notes

Metrics: backpressure_reject_total (I10), flow_buffer_bytes_gauge, flow_resume_ latency_seconds (M12). Runbook: none dedicated; the depth-gauge trend from §16.10 (mq) and this phase's buffer-bytes gauge are the primary dashboards operators watch under load (§26).

26. Operational Readiness

Metrics (Prometheus-style, ADR-11): every counter named in §7's invariant table and §24's threat table is exported; histograms for the M-series latencies (§30). Tracing (ADR-10): one span per IPC op, tagged with the primitive kind and object ID. Structured logging (ADR-09): JSON, one line per capability-bypass or invariant-violation event. Dashboards: the fuzz-canary dashboard (§23.10) is the release-readiness board; per-primitive depth/buffer gauges (§16.10, §22.10) are the load board. Alerting philosophy: alert on sustained trend (e.g., wakeup_fanout_total > 1 for 5 minutes), not single-sample spikes — most of these counters have legitimate transient nonzero values. SLOs: p99 latency within the M-series targets (§4, §30) for 99.9% of 5-minute windows. Incident response: the runbooks below are the first response; escalate to the owning crate's maintainer if the runbook's remediation doesn't resolve within 30 minutes.

Named runbooks:

  • SIGPIPE storm (§13.10, §17.10) — diagnose via strace -p <pid>; check reader liveness via lsof -p <reader_pid>; remediate by trapping SIGPIPE app-side.
  • FD leak in SCM_RIGHTS path (§18.10) — diagnose via lsof -p <pid> | head -100, classify by FD kind (pipe:[N] vs socket:[N]); remediate by patching the missing close() or the missing rollback (T3).
  • epoll wakeup storm (§21.10) — diagnose via perf top showing wake-path functions at the top; remediate by switching the offending FD's consumer to drain-to-EAGAIN discipline or exclusive registration.

Backup/restore: none of the five primitives persist data across a host restart by design (P9's boundedness implies ephemerality) — the only durable artifact is a named shm/mq/socket-path entry, which is recreated by the owning application on restart, not backed up by this project.

Deployment topology: a linked library within each participating process; no shared daemon except where a broker pattern is explicitly adopted by the consumer (outside this project's default, ADR-26).

Canary/rolling-upgrade/rollback/migration: see §27 for the compatibility contract this topology depends on.

27. Compatibility & Versioning

Wire compatibility: the length-prefixed raw-bytes format (ADR-05) has no schema to evolve — payload interpretation is entirely the caller's responsibility; this project guarantees only the framing (length prefix width, byte order) is stable within a major version. Storage compatibility: N/A — no persisted state (§26). API stability: ipc-core traits (Pollable/Readable/Writable) are the frozen public contract post-1.0; IpcError's #[non_exhaustive] declaration (§12.2) allows new variants without a major bump. Migration: a capability-model change (§20) that alters CapToken's fields requires a major version bump, since it is the security boundary. Deprecation policy: a deprecated API path stays functional for one full major version with a compile-time warning before removal. SemVer policy (ADR-18): breaking changes to any ipc-core trait, IpcError variant removal (not addition), or CapToken field changes are major; new primitives or new optional fields are minor; bug fixes are patch. Rolling-upgrade guarantees: since there is no persisted cross-process wire state beyond a single message's framing, two processes at adjacent minor versions interoperate as long as neither uses a primitive kind absent from the other's version.

28. Testing & Verification Strategy

Unit: per-crate, trait-dispatch and single-object-state tests (§12.5 onward). Integration: cross-crate (e.g., a pipe registered with ipc-notify, gated by ipc-cap). Property-based (ADR-12, proptest): randomized operation sequences per primitive, checked against the invariant table (§7). Differential (P14, §23): byte- for-byte comparison against Linux. Fuzzing (ADR-13, §23): coverage-guided, multi-primitive sequences. Chaos: induced sendmsg failures (§18.4's rollback fixture), induced consumer stalls (§22's backpressure fixtures). Deterministic replay: ipc-verifier's simulator (§7) — the same trace always reproduces the same invariant verdict, the mechanism that makes fuzz-found races debuggable (§23.8). Soak: the 30-day fuzz canary (§23, M10). Fault injection: peer-crash-mid-write (§17.9, §18.4), reader-never-drains (§13.8). Conformance: the full conformance/buckets/ tree (§10), one bucket per primitive plus cross-cutting (notify/, capabilities/, flow/). Performance-regression gating: every M-series target (§30) is a CI gate — a PR that regresses a target by more than 10% fails CI, tied to the same benchmark harness (ipc-bench) that produced the target. Every invariant (§7) has at least one fixture (§13.5–§22.5) that exercises it; every fixture traces back to a named invariant, ADR, or threat-model row.

31. Scalability Analysis

Constant regardless of load: per-object memory overhead (§4's header/metadata rows); capability-check cost (M11, O(1) hash lookup, §20.7). Grows with load: wait-queue depth (O(waiters)); mq heap depth (O(log n) per op, ADR-24); FD-table size (O(concurrent objects), bounded by §4's budget). Named bottlenecks, in order: (1) wait-queue lock contention under many-waiters-per-object beyond ~64 cores (P6 mitigates but does not eliminate this — the ceiling in §4's scaling assumption); (2) mq heap O(log n) at the 65,536-message ceiling (§16.7); (3) cross-NUMA shm access at ≥ 2.5× local latency (§15.7). Horizontal scaling: not applicable within a single host — this project's scope is same-host IPC (§1 non-goals); horizontal scale is achieved by sharding IPC objects across independent host-local process groups, not by this layer. Vertical scaling: near- linear to 64 cores per the §4 assumption; beyond that, wait-queue lock contention is the practical ceiling. Sharding/partitioning: per-object (each Mqueue/ShmRegion is independently lockable, P6) — no cross-object coordination is required by design. Coordination overhead: limited to the capability-check chokepoint (§20, O(1) per op) and the differential/fuzz harness (§23, off the runtime path entirely). The practical ceiling: ~64 cores / 10,000 objects per process before wait-queue contention dominates (§4); levers beyond it: partition IPC objects across multiple processes (avoiding one process's FD-table/wait-queue contention entirely), or adopt the deferred RDMA-backed cross-host bridge (PhaseDeferred("§31"), §37) once same-host capacity is genuinely exhausted.

32. Mental Models & First Principles

  • MM1 — A pipe is a bounded ring of pages, not an infinite stream. Predicts: writes beyond PIPE_BUF may interleave; a full buffer blocks or EAGAINs, it never silently grows. Bug class without it: assuming unbounded, always-atomic writes. Applies in §13.
  • MM2 — Shared memory shares bytes, not synchronization. Predicts: any concurrent write without an explicit futex/fence is a race, regardless of how "obviously fine" the access pattern looks. Bug class without it: torn reads, reordered writes, the entire T1 threat class. Applies in §15.
  • MM3 — Edge-triggered readiness is a stricter contract requiring full drain. Predicts: a consumer that doesn't drain to EAGAIN before the next wait misses events it thinks it should have gotten. Bug class without it: FM-6's missed-wakeup hang. Applies in §21.
  • MM4 — A file descriptor is a capability, not merely a name. Predicts: possessing the FD is the authority; passing it (§18) transfers that authority, which is why SCM_RIGHTS needs kernel-mediated refcounting instead of a userspace lookup table. Bug class without it: treating fd-passing as "just sending a number," which breaks the security model (T2, ADR-25). Applies in §18, §20.
  • MM5 — Backpressure is a protocol decision, not an implementation accident. Predicts: every unbounded producer eventually needs an explicit signal, or memory growth is inevitable. Bug class without it: T11's silent OOM vector. Applies in §22.
  • MM6 — Message-queue priority is a scheduling policy, not a delivery guarantee. Predicts: without an aging mechanism, low-priority messages can starve indefinitely under sustained high-priority load (this is correct-per-spec, not a bug). Bug class without it: assuming eventual delivery is guaranteed at every priority. Applies in §16, T7.
  • MM7 — A semaphore's count is state; a condition variable's wake is an event. Predicts: conflating the two (comparing a boolean instead of a counter) reintroduces the lost-wakeup race a generation counter exists to prevent. Bug class without it: FM-12- adjacent livelocks and hangs. Applies in §19.
  • MM8 — Every IPC channel has both a trust boundary and a crash boundary, and they are not the same line. Predicts: a peer can be fully trusted and still crash mid-operation (§17.9's EPIPE handling), or fully untrusted but never crash (§20's capability checks) — designing for only one of the two boundaries misses real failure modes. Applies in §17, §20, §24.

D-Bus: chose a broker-mediated bus, trading a single point of contention for centralized routing/policy and easy N-to-M fan-out without every pair of peers needing a direct connection — the model this project's Alternative Architectures §36 evaluates and rejects for the default case.

seL4: chose zero-buffering synchronous rendezvous IPC, formally verified end-to-end (Klein et al. 2009) — wins decisively where the TCB must be minimal and provably correct, at the cost of generalizing poorly to the buffered/async delivery this project's throughput targets (M6, M7) require (§36).

  4. FD budget/host = FDs_per_process × processes_per_host = 65,536 × 64 = 4,194,304 FDs/host (chained from §4's working-set-FD row).
  5. epoll wakeup budget/core = 1 / t_wake = 1 / 200 ns = 5M wakeups/s/core (chained from §4's M3 row).
  6. Socket buffer memory ceiling/process = buf_size × N_sockets = 208 KiB × 65,536 = 13.3 GiB worst case — the number that makes backpressure (ADR-21, §22) mandatory rather than optional (chained from §4's FD-budget row applied to sockets).
  7. Splice-vs-copy throughput ratio = bandwidth_splice / bandwidth_copy = 10 GB/s / 2 GB/s = 5× (chained from §4's M6/M1 rows).
  8. Capability-check overhead at max throughput = check_cost × ops_per_sec = 50 ns × 2,000,000/s = 100 ms/s = 10% of one core's budget at the mq throughput ceiling (chained from §4's M11 row and capacity-model row 2).

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Synchronous rendezvous (seL4-style, zero buffering).

Sender ──(register-passed message, blocks)──▶ Receiver
         no kernel buffer; call returns only
         after receiver has consumed

Regime where it wins: a formally-verified minimal-TCB microkernel where every byte of buffering is attack surface (Klein et al. 2009). Real system: seL4. Rejected here because this project's throughput targets (M6: ≥10 GB/s, M7: ≥5 GB/s, §4) require buffered, asynchronous delivery that a zero-copy-buffer rendezvous model cannot provide without the caller building its own buffering layer on top — at which point the "no buffering" benefit is illusory.

Alternative 2 — Unified shared-memory ring buffer for all five primitives (io_uring- style).

┌───────────── single SQ/CQ ring, shared-memory-mapped ─────────────┐
│ submission entries (any op: pipe-write, mq-send, shm-attach, …)    │
│ completion entries                                                 │
└─────────────────────────────────────────────────────────────────────┘

Regime where it wins: extremely high syscall-rate workloads where per-op syscall overhead itself (not the IPC semantics) is the bottleneck. Real system: Linux io_uring. Rejected here (for the default design) because it collapses five semantically distinct primitives (P2) into one generic submission format, which would either leak type-specific behavior back into a "generic" ring entry or force every primitive into a least-common-denominator shape — exactly the leaky-abstraction failure ADR-02 rejects. Retained as PhaseDeferred("§36") for a future opt-in fast path once the five primitives' semantics are locked.

Alternative 3 — Broker-mediated IPC (D-Bus/Binder-style central relay).

Peer A ──▶ Broker/Driver ──▶ Peer B
Peer C ──▶ Broker/Driver ──▶ Peer B
   (broker owns naming, policy, and routing)

Regime where it wins: N-to-M fan-out where every pair of peers establishing a direct connection would be O(N²) — a broker makes it O(N). Real systems: D-Bus (userspace broker), Android Binder (kernel-driver broker). Rejected as the default transport here because it introduces a single point of contention (§33's D-Bus paragraph) and an extra copy (broker relay) that this project's peer-to-peer socket model avoids for the common one-to-one and small-fan-out case; a broker remains a valid consumer-built pattern atop this project's Unix-domain sockets (§17), just not baked into the core.

Alternative 4 — Capability-passing microkernel naming (seL4 endpoints + untyped memory) instead of POSIX namespace-based naming.

CSpace (capability address space) ─▶ Endpoint capability ─▶ IPC object
   (no global names; every reference is an unforgeable capability)

Regime where it wins: a system with no filesystem namespace at all (a bare microkernel with no VFS) where POSIX-style named rendezvous (shm_open, mkfifo) has no natural home. Real system: seL4's capability-addressed IPC endpoints. Rejected as the sole naming mechanism here because this project targets POSIX-hosted processes that already have a filesystem namespace and expect shm_open/mkfifo-style rendezvous (P1); instead, §20's CapToken layers capability semantics atop POSIX names rather than replacing them — the pragmatic middle ground between the two rejected extremes (pure DAC bits vs. pure capability-only naming).

38. Glossary

  • ADR — Architecture Decision Record; a locked, rationale-carrying design decision (§9).
  • Ancillary data (cmsg) — control message attached to sendmsg/recvmsg, carrier of SCM_RIGHTS/SCM_CREDENTIALS.
  • Backpressure — an explicit signal to a producer that a bounded resource is near capacity (§22).
  • Binder — Android's kernel-driver-mediated single-copy IPC transport (§33).
  • Capability — an unforgeable, transferable reference bundling authority with designation (§20, MM4).
  • CapToken / CapSet — this project's unified capability object and per-process capability collection (§11).
  • CLOCK_MONOTONIC — a non-jumping clock source used for internal deadlines (ADR-20).
  • cmsg — see Ancillary data.
  • Condition variable (CondVar) — a wait/signal primitive paired with a mutex, generation-counter-based here to avoid lost wakeups (§19).
  • D-Bus — a broker-mediated message bus atop AF_UNIX (§33).
  • Deferred Features Register — the table (§37) anchoring every PhaseDeferred(...).
  • Differential testing — comparing this project's behavior byte-for-byte against a reference kernel (Linux) on a curated trace (§23, P14).
  • Edge-triggered — a readiness notification mode that fires only on a not-ready→ready state transition (§21, I8).
  • EPIPE — the error returned by a write to a pipe/socket with no remaining readers.
  • EAGAIN — the non-blocking-would-block return code.
  • FD (file descriptor) — a per-process integer indexing into the open-file table.
  • FD table — the per-process map from FD to open-file entry.
  • FIFO — a named pipe, rendezvoused via a filesystem path (§14).
  • FlowController — this project's backpressure enforcement object (§11, §22).
  • Futex — Linux's fast userspace mutex primitive; the kernel-assisted blocking mechanism underlying ipc-sync and ipc-shm (ADR-08).
  • Hysteresis (watermark) — the deliberate gap between a high and low watermark that prevents signal oscillation (§22.6).
  • Level-triggered — a readiness notification mode that fires whenever a handle remains ready (§21).
  • Mach port — a capability-typed message-passing IPC object in the Mach microkernel (§33).
  • mq / mqueue — POSIX message queue (§16).
  • Mqueue — this project's message-queue type (§11).
  • NUMA — non-uniform memory access; cross-node shared-memory latency penalty (§4).
