36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Synchronous rendezvous (seL4-style, zero buffering).

Sender ──(register-passed message, blocks)──▶ Receiver
         no kernel buffer; call returns only
         after receiver has consumed

Regime where it wins: a formally-verified minimal-TCB microkernel where every byte of buffering is attack surface (Klein et al. 2009). Real system: seL4. Rejected here because this project's throughput targets (M6: ≥10 GB/s, M7: ≥5 GB/s, §4) require buffered, asynchronous delivery that a zero-copy-buffer rendezvous model cannot provide without the caller building its own buffering layer on top — at which point the "no buffering" benefit is illusory.

Alternative 2 — Unified shared-memory ring buffer for all five primitives (io_uring- style).

┌───────────── single SQ/CQ ring, shared-memory-mapped ─────────────┐
│ submission entries (any op: pipe-write, mq-send, shm-attach, …)    │
│ completion entries                                                 │
└─────────────────────────────────────────────────────────────────────┘

Regime where it wins: extremely high syscall-rate workloads where per-op syscall overhead itself (not the IPC semantics) is the bottleneck. Real system: Linux io_uring. Rejected here (for the default design) because it collapses five semantically distinct primitives (P2) into one generic submission format, which would either leak type-specific behavior back into a "generic" ring entry or force every primitive into a least-common-denominator shape — exactly the leaky-abstraction failure ADR-02 rejects. Retained as PhaseDeferred("§36") for a future opt-in fast path once the five primitives' semantics are locked.

Alternative 3 — Broker-mediated IPC (D-Bus/Binder-style central relay).

Peer A ──▶ Broker/Driver ──▶ Peer B
Peer C ──▶ Broker/Driver ──▶ Peer B
   (broker owns naming, policy, and routing)

Regime where it wins: N-to-M fan-out where every pair of peers establishing a direct connection would be O(N²) — a broker makes it O(N). Real systems: D-Bus (userspace broker), Android Binder (kernel-driver broker). Rejected as the default transport here because it introduces a single point of contention (§33's D-Bus paragraph) and an extra copy (broker relay) that this project's peer-to-peer socket model avoids for the common one-to-one and small-fan-out case; a broker remains a valid consumer-built pattern atop this project's Unix-domain sockets (§17), just not baked into the core.

Alternative 4 — Capability-passing microkernel naming (seL4 endpoints + untyped memory) instead of POSIX namespace-based naming.

CSpace (capability address space) ─▶ Endpoint capability ─▶ IPC object
   (no global names; every reference is an unforgeable capability)

Regime where it wins: a system with no filesystem namespace at all (a bare microkernel with no VFS) where POSIX-style named rendezvous (shm_open, mkfifo) has no natural home. Real system: seL4's capability-addressed IPC endpoints. Rejected as the sole naming mechanism here because this project targets POSIX-hosted processes that already have a filesystem namespace and expect shm_open/mkfifo-style rendezvous (P1); instead, §20's CapToken layers capability semantics atop POSIX names rather than replacing them — the pragmatic middle ground between the two rejected extremes (pure DAC bits vs. pure capability-only naming).
