Decisions (§9) · 25 ADRs

A01

Implementation language

Chosen

Rust (stable 1.78+)

Rejected

Go (SpiceDB, OpenFGA), C++

When the rejected choice is right

Go wins when ship-velocity and hiring a large authz team dominate, and p99 Check tail is allowed to absorb GC pauses (SpiceDB/OpenFGA chose Go and dominate adoption precisely because the ecosystem and contributor pool are larger). C++ wins when embedding inside an existing C++ data plane (e.g. a C++ proxy) where a second runtime is unacceptable.

Why: Zero-GC; recursive graph traversal without GC pause; newtypes for type-safe tuples; Tonic gRPC; safety in MVCC read paths

A02

Async runtime

Chosen

tokio (multi-thread)

Rejected

async-std, smol, rayon

When the rejected choice is right

rayon wins for the Leopard full-rebuild (§20.2), a CPU-bound parallel transitive-closure over a static snapshot — a data-parallel job, not async I/O; a rebuild tool could legitimately use rayon while the server uses tokio.

Why: Tonic requires tokio; largest ecosystem; structured concurrency via JoinSet; no GC

A03

gRPC framework

Chosen

tonic 0.11+

Rejected

grpc-rs (gRPC C-core), grpcio

When the rejected choice is right

grpc-rs (C-core) wins when you must match Google's reference gRPC behavior bug-for-bug (e.g. exotic HTTP/2 flow-control or xDS load-balancing features) that the pure-Rust stack has not yet implemented.

Why: Pure Rust; zero-copy streaming; tower middleware; proc-macro codegen from .proto

A04

Protobuf codegen

Chosen

prost + tonic-build

Rejected

protobuf-codec, serde

When the rejected choice is right

runtime-reflection codegen wins for an admin/debug tool that must introspect arbitrary, dynamically-loaded .proto schemas it was not compiled against (a generic tuple inspector).

Why: Compile-time codegen; no runtime reflection; efficient encoding

A05

HTTP/JSON gateway

Chosen

grpc-gateway (sidecar) or axum proxy

Rejected

envoy grpc-json-transcode

When the rejected choice is right

Envoy transcoding wins when an Envoy mesh is already the org's edge — reusing its battle-tested transcoder and rate-limit filters beats shipping a bespoke axum proxy.

Why: Optional; axum proxy preferred to avoid additional sidecar binary

A06

Storage engine (prod)

Chosen

RocksDB via rust-rocksdb

Rejected

PostgreSQL, TiKV, sled

When the rejected choice is right

PostgreSQL wins for a small/medium deployment that already runs Postgres, needs ad-hoc SQL audit over tuples, and values operational familiarity over peak write throughput (SpiceDB's default datastore is Postgres for exactly this reason). TiKV wins when horizontal, auto-sharded, Raft-replicated storage is needed out-of-the-box rather than built (Phase 11).

Why: LSM suits append-heavy workloads; column family per concern; compaction filter for tombstone GC; proven at scale

A07

Storage engine (test/dev)

Chosen

In-memory BTreeMap + Arc<RwLock<_>>

Rejected

SQLite, sled

When the rejected choice is right

SQLite wins when dev/test must survive process restarts (a long-lived local sandbox) and you want SQL inspection of fixture state without standing up RocksDB.

Why: Zero external deps; deterministic for property tests; fast startup

A08

Distributed cache

Chosen

Redis 7+ via redis-rs

Rejected

Memcached, in-process only

When the rejected choice is right

In-process-only wins for a single-node or embedded deployment where cross-node sharing is irrelevant and a network hop to Redis is pure added latency (Ory Keto-style small deployments). Memcached wins when only a simple LRU blob cache is needed with no atomic-op/pubsub requirement.

Why: Atomic operations for lock-table; pub/sub for cache invalidation; TTL support

A09

Timestamp oracle impl

Chosen

HLC (hybrid logical clock) in-process

Rejected

TrueTime (GPS), NTP-only, Spanner-as-service

When the rejected choice is right

TrueTime wins when you run on GCP/Spanner-class infrastructure with GPS+atomic-clock time masters — true bounded global time gives tighter commit-wait than HLC's pessimistic 7 ms window. NTP-only wins when single-region deployment makes a logical counter unnecessary.

Why: No GPS hardware required; bounded uncertainty (≤ 7 ms); implementable from scratch per portfolio requirement

A10

Oracle HA

Rejected

When the rejected choice is right

Why: Single-crate Rust; leader election + log replication; simpler than multi-Paxos

Alternative Architectures (Roads Not Taken)

Fundamentally different ways to build authorization for the same goal — not parameter tweaks. Each: ASCII sketch, the regime where it wins, the real system embodying it, why this blueprint rejected it.

A1 — Embedded/library authorization (policy + data co-located in each service). No central authority; every service links an authz library and owns its own relation data or policy bundle.

  ┌── service A ──┐   ┌── service B ──┐   ┌── service C ──┐
  │ app + authz   │   │ app + authz   │   │ app + authz   │
  │ lib + local   │   │ lib + local   │   │ lib + local   │
  │ policy/data   │   │ policy/data   │   │ policy/data   │
  └───────────────┘   └───────────────┘   └───────────────┘
      (no shared store; each evaluates against its own copy)
  • Wins: low-latency, no-network-hop authorization for services that own their own data and need no cross-service consistency — eval is a local function call with zero RTT.
  • Real system: OPA/Rego (Open Policy Agent) deployed as a sidecar/library, evaluating policy against data supplied per request; Casbin embedded in-process.
  • Rejected because: the entire premise here is a centralized, decoupled authority with cross-service consistency and a single audit point (§1, §2). A library model cannot answer "which objects across the whole system can this user see?" or guarantee new-enemy-safe revocation across services (design principle 2) — each copy is an independent source of truth (MM4), the opposite of this design.

A2 — Pure RBAC / role table (no relation graph, no rewrites). Authorization is a join over (user→role) and (role→permission) tables; no transitive group traversal, no userset rewrites.

   users ──┐                       ┌── permissions
           ▼                       ▼
        user_roles ──▶ roles ──▶ role_perms
           (flat joins; no recursion, no parent inheritance)
  • Wins: simple, well-understood, fast (two indexed joins) for flat organizations where permissions map cleanly to a bounded set of roles and there is no "folder inherits from parent folder" structure.
  • Real system: classical NIST RBAC (Sandhu et al., P11; Ferraiolo & Kuhn, P13) as implemented in countless application roles/permissions tables and in database GRANT systems.
  • Rejected because: RBAC is the union-of-_this-only special case of this engine (§8.3, MM1) — it cannot natively express transitive group-via-parent inheritance or computed/tuple-to-userset rewrites without bolting on custom recursion, which is exactly the recursion this design makes a first-class, bounded primitive (Phase 4 §16.2). Building the general engine subsumes RBAC at modest extra cost.

A3 — ABAC / policy-as-attributes (decision = f(subject attrs, resource attrs, context)). No stored relationships; each decision is a boolean function over attributes evaluated at request time.

   request ─▶ ┌─────────────────────────────┐
   {subj,     │  policy engine: evaluate     │ ─▶ allow / deny
    res,      │  rules over attributes        │
    action,   │  (time, IP, dept, clearance)  │
    env}      └─────────────────────────────┘
              (no relation store; attributes arrive with the request)
  • Wins: policies that genuinely depend on attributes and context — time-of-day, IP range, data-classification level, dynamic risk score — that no relation graph can encode.
  • Real system: NIST ABAC (SP 800-162, RFC6/P12); XACML; AWS IAM policy conditions; OPA/Rego when used for attribute logic.
  • Rejected because: this service is deliberately not an attribute engine (§1 non-goals) — its strength is relationship reachability (MM1), and mixing attribute arithmetic into rewrite rules would yield a half-ABAC engine satisfying neither model (MM1's bug class). ABAC and ReBAC are complementary system classes; this blueprint stays purely on the relation side and defers attribute predicates entirely.
