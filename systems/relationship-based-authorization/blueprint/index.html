410 — Relationship-Based Authorization Service (Zanzibar-style) from Scratch

Project Number: 410 Project Name: Relationship-Based Authorization Service (Zanzibar-style) from Scratch Owner: Mujir Qureshi Document: FINAL_BLUEPRINT.md Status: specification — locked

1. Goal

Build a production-grade, centralized relationship-based authorization (ReBAC) service — peer class to Google Zanzibar, SpiceDB (Authzed), OpenFGA (CNCF), and Ory Keto. The service answers "can user U perform relation R on object O?" at high throughput with strong consistency semantics, decoupled from application authentication.

Core capability surface:

  • Relation tuples — ⟨object#relation@user⟩ atoms; user = user-id OR userset object#relation (group references); namespace-qualified.
  • Namespace config — per-type relation definitions with userset-rewrite rules: _this, computed_userset, tuple_to_userset (TTU), union/intersection/exclusion; rewrite AST stored and evaluated at check time.
  • Check API — boolean point query Can(user, relation, object) at a specified consistency level (zookie or latest); recursive graph traversal over rewrite rules + tuples; depth-bounded; cycle-detected.
  • Expand API — enumerate userset tree for (relation, object) up to depth limit; used for debugging and ACL computation.
  • Read/Write API — CRUD for relation tuples; transactional multi-tuple writes; conditional writes (preconditions); changelog append.
  • Watch API — streaming changelog from a given zookie; gap-free total order; consumers rebuild or invalidate caches.
  • ListObjects / ListUsers — reverse expansion: "which objects can user U access via R?" / "which users can access object O via R?"; fanout-bounded.
  • Zookies / consistency tokens — snapshot timestamps encoding "this token was read at zookie Z; check must be at least as fresh"; prevents new-enemy problem.
  • Timestamp oracle — from-scratch monotonic oracle service providing globally ordered snapshot IDs (Spanner/TrueTime analog without GPS); used for MVCC tuple store versioning.
  • MVCC tuple store — (namespace, object_id, relation, user) primary key; versioned by snapshot timestamp; soft-delete via tombstone; compaction policy.
  • Leopard index — flattened transitive group membership materialized index; incremental maintenance from changelog; bounds deep-nesting fanout during Check.
  • Distributed cache — per-Check subproblem memoization; stampede prevention (lock-table + request coalescing); zookie-aware invalidation; hedged reads.

System boundaries:

  • In scope: tuple storage, namespace config management, Check/Expand/Read/Write/Watch/ListObjects/ListUsers RPCs, consistency token protocol, MVCC store, Leopard index, distributed cache, gRPC + HTTP/JSON gateway.
  • Out of scope: authentication (project #49), token issuance/OAuth (project #406), application-level role UI, LDAP/SCIM provisioning, policy languages beyond relation rewrites (OPA/Rego), multi-region consensus.

Non-goals:

  • NOT an ABAC/PBAC engine — only relationship graph.
  • NOT a token issuer — JWTs, OIDC, SAML belong to #406.
  • NOT a directory service — user/group provisioning is caller responsibility.
  • NOT a UI or admin console.
  • NOT a managed cloud offering — designed as self-hosted, operator-run.

Deployment model: single binary (authzd) exposing gRPC port 50051 + HTTP/JSON gateway port 8080; backed by pluggable storage (embedded RocksDB dev mode; PostgreSQL + Redis prod mode); horizontally scalable stateless Check nodes; stateful MVCC store cluster with replication; oracle as sidecar or co-located.

Target users: platform/infra engineers embedding centralized authz into microservice meshes; security engineers needing auditable, decoupled permission decisions; operators running multi-tenant SaaS.

Phase 0 deliverable — numbered crates/modules:

  1. crates/proto/ — generated gRPC stubs + Protobuf types.
  2. crates/model/ — tuple, namespace, rewrite AST, zookie types.
  3. crates/store/ — MVCC tuple store trait + in-memory impl.
  4. crates/oracle/ — timestamp oracle trait + local impl.
  5. crates/server/ — gRPC service skeleton.
  6. crates/cli/ — authzctl management CLI.

What later phases unlock: P3+ unlocks namespace rewrite evaluation; P4 unlocks recursive Check; P5 unlocks Expand; P6 unlocks Write + changelog; P7 unlocks Watch streaming; P8 unlocks zookie consistency protocol; P9 unlocks Leopard index; P10 unlocks ListObjects/ListUsers; P11 unlocks distributed cache + hotspot mitigation; P12 unlocks sharding/replication + conformance.

Deferred: multi-region consensus PhaseDeferred("Deferred Features Register"); CLDR display names PhaseDeferred("Deferred Features Register"); schema migration tooling PhaseDeferred("Deferred Features Register").

Estimated timeline: Phase 0 = 6–8 weeks; P0–P8 = 4–5 months; full P0–P12 = 7–9 months (one principal engineer, full-time).

2. Why Build This

Unique systems knowledge taught:

  • Relationship graph modeling — authorization as a directed graph; reachability queries as the core primitive; RBAC/ABAC are special cases of a relation graph.
  • New-enemy problem — why naive caching breaks multi-tenant authz; how zookies encode "must be at-least-as-fresh as when I wrote this tuple" without global locking.
  • Userset rewrites — composing union/intersection/exclusion of computed and transitively-resolved usersets; rewrite AST as a mini-language; termination guarantees.
  • Leopard index — flattened transitive group membership; incremental maintenance from WAL; bounds fanout from O(depth) to O(1) amortized.
  • MVCC in authorization store — snapshot reads for deterministic Check; tombstone semantics; compaction without breaking Watch consumers.
  • Timestamp oracle design — globally ordered, monotonically increasing, gapless snapshot IDs without GPS; hybrid logical clocks (HLC) vs TrueTime; bounding clock uncertainty.
  • Distributed cache correctness — consistency under concurrent writes; request coalescing to prevent thundering herd; zookie-aware TTL.
  • Fanout DoS — deeply nested group membership as a DoS vector; depth caps, cycle detection, fanout budgets as mitigations.

Historical/architectural significance:

  • Google Zanzibar (2019) — the paper that crystallized ReBAC at scale; serves trillions of ACL checks/day for Google Drive, Calendar, YouTube; introduced zookies.
  • SpiceDB / OpenFGA — dominant open-source Zanzibar implementations; production pitfalls this codebase avoids by reading their issues.
  • RBAC → ReBAC evolution — classical RBAC cannot represent transitive group-via-parent inheritance without custom code; ReBAC encodes it natively.

Engineering muscles developed: recursive graph traversal with correctness invariants; MVCC store design; cache invalidation under consistency constraints; gRPC streaming; property-based + differential testing against reference oracles; adversarial tuple fuzzing.

Cross-links:

  • #49 Authentication — upstream; this service trusts user IDs from caller, never validates tokens.
  • #406 Token Issuance — upstream; bearer token → user ID extraction is caller responsibility.
  • #394 NTP/PTP — oracle depends on wall-clock monotonicity; clock sync quality bounds HLC uncertainty.
  • Distributed KV / consensus projects — MVCC store replication can reuse Raft engine; Leopard index as a CRDT.
  • Observability stack — distributed tracing spans across Check subproblems; latency histograms per relation type.

Calibration value: authorization is systematically underengineered until a multi-tenant incident exposes the new-enemy vulnerability; building a correct Zanzibar-style service recalibrates engineering judgment on consistency, caching, and security-critical correctness.

What Mastery Looks Like

  • Model authorization as a reachability problem — after Phase 4 (§16) you can express RBAC, group-via-parent inheritance, and ownership-implies-edit as one rewrite AST (_this/computed_userset/tuple_to_userset/union/intersection/exclusion), and explain why RBAC is the union-only special case (P11, §8.3, design principle 4).
  • Make a security decision deterministic and replayable — after Phase 3 (§15) you can pin a Check to a SnapshotId, key a cache on it, and reproduce any production allow/deny bit-for-bit from (user, relation, object, snapshot) alone (design principle 1, I1, MM1).
  • Defeat the new-enemy problem with a consistency token, not a global lock — after Phase 7 (§19) you can issue a zookie on Write, resolve it to a snapshot on Check, and prove a revoked grant can never be served stale, without paying a coordination round-trip on every read (design principle 2, I2, §8.8 Example C, MM3, Zanzibar P1).
  • Build a timestamp oracle without atomic clocks — after Phase 7 (§19) you can implement an HLC with a bounded uncertainty window and wait_until_safe, deriving external consistency from commit-wait the way Spanner does from TrueTime, and bound the worst-case wait (ADR-A09, I9, §8.4, P2/P4, MM6).
  • Bound a recursive security evaluator against adversarial input — after Phase 4 (§16) you can cap depth and fanout, detect cycles with a visited set, and prove termination regardless of tuple data or namespace config (design principle 3, I5, Threat Model T7, MM7).
  • Trade write amplification for read latency with a materialized index — after Phase 8 (§20) you can build and incrementally maintain the Leopard flat-membership index from a changelog, quantify its 3× storage cost, and know exactly when its eventual-consistency lag forces a fallback to live traversal (design principle 10, I7, MM8, Zanzibar P1).
  • Make a distributed cache correct under revocation — after Phase 10 (§22) you can key on snapshot, invalidate from a Watch stream, coalesce a stampede, and prove the cache never serves an allow that a fresh read would deny (design principle 2, I8, MM4).

Client Layer: gRPC clients (application backends, sidecar proxies); HTTP/JSON gateway for languages without native gRPC; authzctl CLI for operator tuple management, namespace config deployment, and diagnostic queries. All external-facing; TLS-terminated here.

API Gateway / Router: intercepts every inbound request; validates caller identity (mTLS or bearer token as metadata); parses and validates zookies; enforces per-tenant rate limits via token-bucket; logs structured request metadata; routes to appropriate service handler.

Check Service: entry point for boolean authorization queries; resolves consistency level (zookie → snapshot ID); dispatches to Rewrite Evaluator; collects sub-decisions from cache or store; returns {allowed: bool, debug_trace: optional}.

Expand Service: builds and returns the full userset tree for (relation, object); depth-bounded; each node labeled with resolution rule; used for ACL debugging, pre-computation, and admin audit.

Read/Write Service: transactional tuple CRUD; precondition-conditional writes (optimistic concurrency); appends to changelog with oracle-assigned snapshot ID; enforces tuple uniqueness; emits Write metrics.

Watch Service: streaming RPC; accepts start zookie cursor; tails changelog from that point forward; delivers gap-free ordered tuples; applies backpressure via flow control; used by Leopard index maintainer and external cache invalidators.

ListObjects / Reverse Expander: answers "which objects can user U access via relation R?" by running reverse BFS from user through the relation graph; fanout-capped; leverages Leopard index for group membership traversal.

Rewrite Evaluator: interprets namespace rewrite ASTs at Check time; recursive descent; handles _this (direct tuple lookup), computed_userset (recurse with different relation), tuple_to_userset (TTU: fetch subject from tuple, then recurse on new relation); union short-circuits on first true; intersection requires all true; exclusion = A and not B; depth counter + visited set prevent infinite recursion.

Subproblem Cache: memoizes (user, relation, object, snapshot_id) → bool across Check subproblems within a single request and across requests; lock-table prevents stampede; coalesces concurrent identical requests; zookie-aware TTL never serves stale results violating freshness.

MVCC Tuple Store: core persistence layer; primary key (namespace, object_id, relation, user); each row carries created_at: SnapshotId and deleted_at: Option<SnapshotId>; supports snapshot reads; sharded by (namespace, hash(object_id)); changelog column family provides ordered mutation log; compaction filter GCs tombstones past retention window.

Leopard Index: materialized flat set of (group_userset → user_id) transitive memberships; built and maintained incrementally from changelog; allows Check to short-circuit deep group nesting with O(1) set membership test; trade-off: write amplification vs read latency.

Namespace Config Store: persists rewrite ASTs per namespace, versioned; Check loads config at snapshot read time; validated on write (no undefined relation references, bounded rewrite depth).

Timestamp Oracle: provides globally monotonically increasing SnapshotId values; implemented as HLC with bounded uncertainty window; exposes now() → SnapshotId and wait_until_safe(snap) → () (waits for clock to advance past snap's uncertainty window); active-passive failover.

Watch / Changelog Fan-out: broadcasts changelog mutations to all subscribers; total ordering guaranteed by oracle-assigned snapshot IDs; each subscriber holds a cursor (last-seen zookie); backpressure applied per subscriber; lagging subscribers receive SLOW_CONSUMER signal.

6. Design Principles

1. Snapshot Determinism — Every Check request executes against an immutable snapshot identified by SnapshotId. Given identical (user, relation, object, snapshot_id), the result must always be the same. Violating this makes debugging impossible and zookies meaningless. Enforced by: passing SnapshotId through every tuple fetch and cache key; never reading "latest" implicitly.

2. Zookie-Enforced Freshness — A zookie encodes the minimum snapshot at which a response is valid. Serving a Check result from a snapshot older than the caller's zookie is a correctness violation (new-enemy). Enforced by: cache keys include snapshot_id; TTL-based cache entries are only valid if their snapshot ≥ requested zookie; read path always resolves zookie to snapshot before any cache lookup.

3. Bounded Recursion — The rewrite evaluator and graph traversal must terminate in finite time regardless of namespace config complexity or tuple data. Enforced by: hard depth cap (25 levels) and fanout cap (1,000 usersets/level); visited-set cycle detection; each cap returns a typed error (DEPTH_EXCEEDED, FANOUT_EXCEEDED, CYCLE_DETECTED).

4. Type-Safe Tuple Model — Every tuple component (namespace, object_id, relation, user) is a distinct newtype; no string-to-string conflation at API boundaries. Violating this caused most SpiceDB early bugs. Enforced by: Rust newtype wrappers; no String in tuple APIs, only Namespace, ObjectId, Relation, UserId, UserSet.

5. Append-Only Changelog — Mutations are never updated in place; every write appends a new versioned record to the changelog column family. Enables: Watch consumers to replay; Leopard index to maintain; audit log to be complete. Compaction only removes records past the retention window, never rewrites.

6. Explicit Consistency Contracts — Every API call declares its consistency requirement: MINIMIZE_LATENCY (may use stale cache), AT_LEAST_AS_FRESH(zookie), or FULLY_CONSISTENT (latest oracle snapshot). No implicit "just give me the latest" without paying the oracle round-trip cost.

7. Fail-Closed Authorization — On any error (store timeout, oracle unavailability, depth exceeded, fanout exceeded), Check returns DENIED or a structured error, never ALLOWED. Callers may choose to retry; the service never permits by default on uncertainty.

8. Observable by Default — Every significant operation emits a span (OpenTelemetry trace), a structured log line, and increments a metric counter/histogram. Latency, cache hit/miss, depth reached, fanout encountered — all observable without code changes. Violating this makes production incidents undebuggable.

9. Storage Abstraction — All persistence operations go through the TupleStore trait and Oracle trait. No code outside crates/store/ calls RocksDB directly. Enables: in-memory impl for tests; PostgreSQL impl for prod; future pluggable backends. Prevents: RocksDB-specific leakage into business logic.

10. Incremental Leopard Maintenance — The Leopard index is never rebuilt from scratch during normal operation; it is maintained incrementally from the changelog. A full rebuild is a recovery procedure only. Incremental maintenance must be idempotent (re-applying the same changelog entry twice must be a no-op).

11. Backpressure Everywhere — Every async channel, gRPC stream, and cache fill path has explicit backpressure. No unbounded queues. Watch consumers that cannot keep up receive SLOW_CONSUMER and are disconnected; the server sheds load rather than OOM. Enforced by: bounded tokio::sync::mpsc channels; gRPC recv_data flow control.

12. Namespace Config Versioning — Namespace configs are immutable once written; each write produces a new version. Check reads config at the same snapshot as tuple reads. This ensures that a config change does not retroactively change Check results for in-flight requests or cached zookies.

13. No Silent Truncation — Tuple keys exceeding the 2,048-byte limit, namespace configs exceeding 256 KB, and batches exceeding limits return errors immediately. No silent truncation, no partial writes, no accepting data that cannot be stored faithfully.

14. Test Oracle First — Every invariant must have a corresponding property-based test or differential test against a reference oracle before the implementation is considered complete. "It works in my manual test" is not acceptance.

8. Domain Model / Protocol

8.1 EBNF — Relation Tuple

tuple           ::= object "#" relation "@" user_ref
object          ::= namespace ":" object_id
namespace       ::= ident ("/" ident)*
object_id       ::= PRINTABLE_ASCII+ (max 512 bytes)
relation        ::= ident
user_ref        ::= user_id | userset
user_id         ::= ident (":" ident)*     (* e.g., user:alice *)
userset         ::= object "#" relation    (* e.g., group:eng#member *)
ident           ::= [a-zA-Z_][a-zA-Z0-9_-]* (max 64 bytes)

Examples:

  • document:readme#viewer@user:alice — alice is viewer of readme.
  • document:readme#viewer@group:eng#member — eng group members are viewers of readme.
  • folder:home#owner@user:bob — bob owns folder home.

Malformed (rejected with INVALID_TUPLE):

  • document:#viewer@user:alice — empty object_id.
  • doc:readme#@user:alice — empty relation.
  • doc:readme#viewer@group:eng# — empty userset relation.
  • Namespace not registered in config store.

8.2 EBNF — Namespace Config

namespace_config ::= "namespace" namespace "{" relation_def* "}"
relation_def     ::= "relation" relation "{" rewrite_expr "}"
rewrite_expr     ::= "_this"
                   | "computed_userset" "(" relation ")"
                   | "tuple_to_userset" "(" "tupleset_rel" ":" relation "," "computed_rel" ":" relation ")"
                   | "union" "{" rewrite_expr (";" rewrite_expr)+ "}"
                   | "intersection" "{" rewrite_expr (";" rewrite_expr)+ "}"
                   | "exclusion" "{" rewrite_expr ";" rewrite_expr "}"

Example — Google Drive–like document namespace:

namespace document {
  relation owner   { _this }
  relation editor  { union { _this; computed_userset(owner) } }
  relation viewer  { union { _this; computed_userset(editor);
                             tuple_to_userset(tupleset_rel: parent, computed_rel: viewer) } }
  relation parent  { _this }
}

8.3 Rewrite AST Nodes

Node Fields Semantics
This — Direct tuple lookup: (namespace, object_id, relation, user) in store
ComputedUserset relation: Relation Recurse: same object, different relation
TupleToUserset tupleset_rel, computed_rel: Relation Fetch tuples for (obj, tupleset_rel, *), then check (fetched_subj, computed_rel, user)
Union children: Vec<RewriteExpr> OR; short-circuit on first true
Intersection children: Vec<RewriteExpr> AND; fail-fast on first false
Exclusion base, subtract: RewriteExpr base AND NOT subtract

8.4 SnapshotId / Zookie

SnapshotId  ::= u64   (* HLC timestamp: 48-bit wall-clock ms + 16-bit logical counter *)
Zookie      ::= base64url(SnapshotId || hmac_sha256(key, SnapshotId)[..8])
  • Zookie is an opaque token handed to clients after Write; encodes the SnapshotId at which the write committed.
  • Callers pass the zookie in Check/Read; the server resolves it to a SnapshotId, then reads at snapshot >= resolved.
  • HMAC prefix prevents forgery; key is per-deployment secret.
  • Zookie 0 = "latest" (no freshness constraint).

8.5 Consistency Levels

Level Behavior Latency Use Case
MINIMIZE_LATENCY Use cache; may serve stale (no zookie check) ≤ 2 ms p50 Non-sensitive reads; analytics
AT_LEAST_AS_FRESH(z) Check snapshot ≥ zookie's SnapshotId + cache lookup overhead Post-write reads; standard authz
FULLY_CONSISTENT Read at current oracle now() + oracle RTT ≤ 10 ms Admin operations; audit

8.6 State Transitions — Tuple Lifecycle

                ┌──────────────────┐
     Write      │                  │   Delete
────────────────▶  ACTIVE           ├─────────────────▶  TOMBSTONED
                │  created_at=S1   │                    deleted_at=S2
                │  deleted_at=NULL │
                └──────────────────┘
                        │
                        │  compaction (after retention window)
                        ▼
                   COMPACTED (record physically removed)
  • Snapshot reads at S return ACTIVE tuples where created_at ≤ S AND (deleted_at IS NULL OR deleted_at > S).
  • TOMBSTONED tuples remain readable by historical snapshots until compaction.

8.8 Worked Examples

Example A — Direct viewer check (depth 1):

  • Tuple: document:readme#viewer@user:alice
  • Check: Can(user:alice, viewer, document:readme) at any snapshot ≥ write zookie.
  • Eval: viewer rewrite = union{_this; computed_userset(editor); TTU(parent→viewer)}.
  • _this: lookup (document, readme, viewer, user:alice) → found → true → short-circuit.

Example B — Transitive group membership (depth 3):

  • Tuples: group:eng#member@user:alice, project:backend#editor@group:eng#member.
  • Check: Can(user:alice, editor, project:backend).
  • Eval: editor rewrite = union{_this; computed_userset(owner)}.
  • _this: lookup (project, backend, editor, user:alice) → miss.
  • computed_userset(owner): recurse with owner → miss.
  • No user:alice but group:eng#member is an editor → TTU traversal → fetch (project, backend, editor, *) → group:eng#member → recurse: Can(user:alice, member, group:eng) → _this: found → true.

Example C — New-enemy scenario (rejected):

  • T=0: user:mallory removed from document:sensitive#viewer.
  • T=1: alice receives zookie Z1 from a Write that removed mallory.
  • T=2: alice sends Check(user:mallory, viewer, document:sensitive, AT_LEAST_AS_FRESH(Z1)).
  • Server resolves Z1 → SnapshotId S1; reads at snapshot ≥ S1; tombstone at S1 is visible → false.
  • Without zookies: cached result from T=-1 (before deletion) could return true → new-enemy violation.

Example D — Malformed tuple (rejected):

  • document:readme#viewer@group:eng# → empty userset relation → rejected at parse time with INVALID_TUPLE.

11. Core Schema and Core Types

11.1 Tuple Types

// Ownership: Clone+Send+Sync; immutable after construction
// Serialization: Protobuf (prost); storage key: BE-encoded bytes
// Compatibility: field order stable; no removal without major version bump

struct Namespace(Arc<str>);      // max 256 bytes; interned
struct ObjectId(Arc<str>);       // max 512 bytes
struct Relation(Arc<str>);       // max 64 bytes; interned
struct UserId(Arc<str>);         // max 512 bytes
struct UserSet { object: ObjectRef, relation: Relation }
enum UserRef { Id(UserId), Set(UserSet) }
struct ObjectRef { namespace: Namespace, id: ObjectId }
struct RelationTuple {
    object: ObjectRef,
    relation: Relation,
    user: UserRef,
}

11.2 Snapshot / Zookie Types

// SnapshotId: HLC timestamp; monotonically increasing; u64
// Zookie: opaque token; HMAC-protected; base64url encoded
// Mutation: never mutated after construction
// Concurrency: Copy; safe to share across threads

#[derive(Copy, Clone, Ord, PartialOrd, Eq, PartialEq)]
struct SnapshotId(u64);   // high 48 bits = wall-clock ms; low 16 bits = logical

struct Zookie(String);    // base64url(SnapshotId || HMAC[..8])

impl Zookie {
    fn encode(snap: SnapshotId, key: &[u8; 32]) -> Self;
    fn decode(&self, key: &[u8; 32]) -> Result<SnapshotId, AuthzError>;
}

11.3 Namespace Config Types

// Ownership: Arc<NamespaceConfig> shared across Check workers; immutable
// Versioning: each Write produces new VersionedConfig; old versions retained for snapshot reads
// Serialization: Protobuf; stored in namespace_config CF keyed by (namespace, version)

struct NamespaceConfig {
    namespace: Namespace,
    version: u64,
    relations: HashMap<Relation, RewriteExpr>,
    created_at: SnapshotId,
}

enum RewriteExpr {
    This,
    ComputedUserset { relation: Relation },
    TupleToUserset { tupleset_rel: Relation, computed_rel: Relation },
    Union(Vec<RewriteExpr>),
    Intersection(Vec<RewriteExpr>),
    Exclusion { base: Box<RewriteExpr>, subtract: Box<RewriteExpr> },
}

11.4 TupleStore Trait

// Trait: object-safe; async; pluggable impl (memory/rocksdb/postgres)
// Snapshot reads: all reads take snapshot_id; no implicit "latest"
// Error: all ops return Result<_, StoreError>; StoreError is non-exhaustive enum

#[async_trait]
trait TupleStore: Send + Sync {
    async fn get_tuples(
        &self, namespace: &Namespace, object: &ObjectId,
        relation: &Relation, snapshot: SnapshotId
    ) -> Result<Vec<RelationTuple>, StoreError>;

    async fn write_tuples(
        &self, writes: Vec<TupleWrite>,
        preconditions: Vec<Precondition>,
    ) -> Result<SnapshotId, StoreError>;

    async fn delete_tuples(
        &self, deletes: Vec<TupleDelete>,
        preconditions: Vec<Precondition>,
    ) -> Result<SnapshotId, StoreError>;

    async fn read_changelog(
        &self, from: SnapshotId, limit: u32
    ) -> Result<Vec<ChangelogEntry>, StoreError>;

    async fn get_namespace_config(
        &self, namespace: &Namespace, at: SnapshotId
    ) -> Result<NamespaceConfig, StoreError>;

    async fn write_namespace_config(
        &self, config: NamespaceConfig
    ) -> Result<SnapshotId, StoreError>;
}

11.5 Oracle Trait

#[async_trait]
trait Oracle: Send + Sync {
    async fn now(&self) -> SnapshotId;
    async fn wait_until_safe(&self, snap: SnapshotId) -> Result<(), OracleError>;

    // ensures reads at snap are externally consistent
}

13. Phase 1 — In-Memory MVCC Tuple Store + Local Oracle

13.1 Objectives

  • Implement TupleStore trait with in-memory MVCC backend.
  • Implement Oracle trait with single-process HLC.
  • Wire store + oracle into server; unblock integration tests.
  • No RocksDB, no distributed components.

13.2 Detailed Implementation Steps

  • crates/store/src/memory.rs: MemoryTupleStore backed by Arc<RwLock<BTreeMap<TupleKey, Vec<VersionedTuple>>>>.

    • TupleKey: (Namespace, ObjectId, Relation, UserId_or_UserSet) — sort key; derive Ord.
    • VersionedTuple: { created_at: SnapshotId, deleted_at: Option<SnapshotId>, tuple: RelationTuple }.
    • get_tuples: iterate BTreeMap range [key_start, key_end); filter by created_at ≤ snap AND (deleted_at IS NULL OR deleted_at > snap).
    • write_tuples: acquire write lock; validate preconditions; append new VersionedTuple with created_at = oracle.now(); append ChangelogEntry to an Arc<Mutex<Vec<ChangelogEntry>>> changelog.
    • delete_tuples: acquire write lock; find matching active tuple at snapshot; set deleted_at = oracle.now(); append tombstone ChangelogEntry.
    • read_changelog: slice Vec<ChangelogEntry> from from snapshot index onward.
    • get_namespace_config: BTreeMap<(Namespace, SnapshotId), NamespaceConfig>; return latest config with created_at ≤ snap.
    • write_namespace_config: insert with created_at = oracle.now().

  • crates/oracle/src/local.rs: LocalOracle wrapping Arc<AtomicU64> for HLC counter.

    • now(): fetch current SystemTime as ms; combine with logical counter (increment on collision); return SnapshotId.
    • wait_until_safe(): for local oracle, uncertainty window = 0; return immediately.
    • Monotonicity: if SystemTime::now() regresses (NTP correction), advance counter instead; never return smaller ID.

  • crates/server/src/check.rs: stub CheckService::check() → reads namespace config at snapshot, calls TupleStore::get_tuples, returns true if any matching tuple found (no rewrite eval yet).

  • Integration tests in crates/store/tests/: write tuple → read at same snapshot → found; delete → read at post-delete snapshot → not found; read at pre-delete snapshot → found.

Anchors: MVCC visibility filter created_at ≤ S AND (deleted_at IS NULL OR deleted_at > S) enforces I10 and §8.6 (B6, P6); TupleStore/Oracle behind traits per design principle 9 (B7), ADR-A07 (in-memory dev store); HLC monotonicity (never return a smaller ID) enforces I9 (P3); append-only changelog realizes design principle 5; snapshot determinism per design principle 1 / I1 / MM1. MVCC patterns from CockroachDB (R4).

13.3 Deliverable

  • MemoryTupleStore passes MVCC isolation tests.
  • LocalOracle produces strictly monotonic IDs.
  • authzd starts; a curl against gRPC health check endpoint returns SERVING.
  • authzctl tuple write doc:readme#viewer@user:alice executes without panic (returns unimplemented for now or writes to memory).

13.4 Acceptance Criteria

  • 100% of crates/store/tests/ pass: snapshot isolation, write/delete/read, changelog ordering.
  • Oracle: 1M now() calls; assert monotonically increasing; no panics.
  • MemoryTupleStore::get_tuples at snapshot S: returns only tuples with created_at ≤ S AND (deleted_at IS NULL OR deleted_at > S).
  • Write tuple at S1, delete at S2, read at S1: returns tuple; read at S2: empty.
  • Write 10k tuples: memory usage ≤ 200 MB.

13.5 Conformance Fixtures

  • conformance/store/write_read.json — write 5 tuples; read at write snapshot; expect all 5.
  • conformance/store/snapshot_isolation.json — write at S1; read at S0; expect empty.
  • conformance/store/delete.json — write at S1; delete at S2; read at S1: present; read at S2: absent.
  • conformance/store/changelog_order.json — 20 writes; read changelog; assert IDs monotonically increasing.

13.6 Pitfalls

  • Snapshot ID wraparound: u64 wall-clock ms + 16-bit logical; if logical counter overflows (> 65535 ops in the same ms), the HLC must advance wall-clock component; detect in LocalOracle::now() by checking counter overflow.
  • RwLock write starvation: under high concurrent reads, write lock may starve; use parking_lot::RwLock with fair mode; or tokio::sync::RwLock for async contexts.
  • Changelog unbounded growth: in-memory changelog grows forever; for test purposes, cap at 1M entries; prod uses RocksDB changelog CF with compaction.
  • Precondition TOCTOU: check preconditions under the same write lock that performs the write; never check before acquiring lock.

13.7 Performance Concerns

  • BTreeMap range scan: O(log N + K) per get_tuples; acceptable for test store; not for production (use RocksDB).
  • Arc<RwLock<_>> contention: all writes serialize; single bottleneck; acceptable for test; prod uses sharded RocksDB.
  • Vec<VersionedTuple> per key: linear scan for MVCC filter; bounded by write+delete pairs per tuple key (typically 1–2).

13.8 Edge Cases

  • Concurrent writes to the same key: both succeed (new versions appended); read sees both unless one was deleted.
  • write_tuples with empty batch: return current oracle now() as snapshot; no-op; idempotent.
  • Changelog read from snapshot > latest: return empty vec.

13.9 Failure Analysis

  • LocalOracle panics on SystemTime::now() failure: replace with UNIX_EPOCH + monotonic fallback; never panic on clock read.
  • MemoryTupleStore OOM under infinite writes: caught by test max_tuples limit; StoreError::Capacity returned.

13.10 Operational Notes

  • No persistence: MemoryTupleStore state lost on process restart; dev/test only.
  • Metrics added: tuples_written_total, tuples_deleted_total, snapshot_ids_generated_total counters via prometheus-client; registered in server startup.
  • Tracing: tracing::info_span!("store.write_tuples") wraps write path.

    • Call eval(expr, user, object, ctx).

19.1 Objectives

19.2 Detailed Implementation Steps

  • crates/oracle/src/hlc.rs: HybridLogicalClock:

    • State: wall_ms: u64 (last seen wall-clock ms), logical: u16.
    • tick(event_ts: Option<u64>) → SnapshotId: update per HLC paper algorithm; if event_ts > wall_ms, advance; else increment logical; if logical overflows, advance wall_ms; return packed SnapshotId.
    • unpack(snap: SnapshotId) → (wall_ms: u64, logical: u16).

  • crates/oracle/src/raft_oracle/mod.rs: RaftOracle:

    • Wraps openraft state machine; node ID from config; peer addresses.
    • Leader-only: only leader responds to now() and wait_until_safe().
    • Non-leader nodes: forward now() to leader; add ≤ 1 ms latency.
    • now(): leader calls hlc.tick(None); appends log entry OracleEntry::SnapshotId(snap) to Raft log; returns snap after majority commit.
    • wait_until_safe(snap): wait until HLC has advanced to snap.wall_ms + uncertainty_window; implemented as tokio::time::sleep_until(target).

    • AT_LEAST_AS_FRESH(zookie): decode zookie → SnapshotId; call oracle.wait_until_safe(snap) if snap > oracle.now(); then read at snap.
    • FULLY_CONSISTENT: call oracle.now() → current snap; read at current snap; wait_until_safe(snap) before returning.
    • MINIMIZE_LATENCY: no oracle call; read at cached snapshot.

Anchors: HLC tick + bounded uncertainty window implement the oracle per ADR-A09 (P3 Lamport happened-before; P4 HLC; B9 Spanner) and guarantee monotonicity I9; wait_until_safe (commit-wait) supplies external consistency the way TrueTime does (P2, P10); the zookie→snapshot resolve before any read closes the new-enemy gap per design principle 2 / I2 (§8.8 Example C, P1, MM3); Raft leader election + log replication per ADR-A10 (P8; Paxos P9 as rejected-alt); consistency-level dispatch realizes design principle 6 (§8.5).     • Subscribes to Watch stream from last Leopard checkpoint SnapshotId.
    • On ChangelogEntry { operation: Write, tuple: group:X#member@user:Y }:
      • Add user:Y to LeopardIndex[group:X#member].
      • Propagate: for every userset U where group:X#member ∈ LeopardIndex[U], also add user:Y to LeopardIndex[U].
    • On ChangelogEntry { operation: Delete, tuple: group:X#member@user:Y }:
      • Remove user:Y from LeopardIndex[group:X#member].
      • Propagate removal: walk upward through group containment; re-verify if user still reachable via other paths before removing from parent sets.
      • Deletion propagation is more expensive than addition; batch deletions and re-derive from scratch for affected subtrees if batch size > threshold (100).
    • Flush checkpoint to RocksDB every 1,000 entries or 10 seconds.
    • Recovery: if changelog cursor is before available history → trigger LeopardMaintainer::full_rebuild().

  • crates/leopard/src/rebuild.rs: full_rebuild(store, oracle) → LeopardIndex:

    • Scan all tuples of the form *#member@* at current oracle snapshot.
    • Build transitive closure via BFS.
    • Replace running index atomically (swap Arc<LeopardIndex>).

  • crates/evaluator/src/eval.rs: integrate Leopard at _this and TTU steps:

    • Before recursing into a UserRef::Set(userset), call leopard.is_member(userset, user_id).
    • If true: short-circuit return true without further store lookups.
    • If false: continue with normal recursive evaluation (Leopard false-negative case: index is eventually consistent, not strongly consistent; fall through to store).

  • Guard: if leopard.checkpoint() < ctx.snapshot - MAX_LEOPARD_LAG, skip Leopard and use store directly; avoids serving stale index under lag.

Anchors: the flat transitive-membership index is P1's Leopard (B4 set/skip-list structures, B5 BFS closure); changelog-driven incremental maintenance realizes design principle 10 (idempotent apply) and I7 (eventual consistency with the store, verified by differential test); the MAX_LEOPARD_LAG fallback to live traversal upholds design principle 2 / I2 under index lag (MM8); membership-cap fallback bounds memory per §4 (Leopard ≤ 3× store); short-circuiting deep group chains is the design-principle-3 fanout mitigation realized as O(1) lookup.

  • Full rebuild from 10M membership tuples completes in ≤ 60 s.

  • Differential test: for 1,000 random (userset, user) pairs, Leopard answer = store recursive traversal answer.
  • After 100 group membership adds + 50 deletes: Leopard index = freshly-rebuilt index (incremental = rebuild).
  • Check depth-10 chain with Leopard: ≤ 10 ms p99 (criterion benchmark).
  • Full rebuild: 10M memberships → ≤ 60 s; memory ≤ 2 GB.
  • Leopard lag > MAX_LEOPARD_LAG: Check falls back to store traversal gracefully.

  • conformance/leopard/membership.json — 20 userset membership cases; expected is_member results.
  • conformance/leopard/incremental.json — sequence of adds/deletes; expected index state after each.
  • conformance/leopard/rebuild.json — full dataset; expected index after rebuild.

20.6 Pitfalls

  • Deletion propagation under shared group membership: user alice in both group:eng#member and group:admin#member; if group:eng#member is nested in group:all#member, deleting alice from group:eng must not remove her from group:all if group:admin also contributes her. Re-verify full reachability before removal.
  • Eventually-consistent Leopard in strongly-consistent Check: Check at AT_LEAST_AS_FRESH(Z) may use Leopard that hasn't processed up to Z yet; the MAX_LEOPARD_LAG guard handles this — skip Leopard if too stale.
  • Index memory explosion: a single group with 1M members stored as HashSet<UserId> uses significant memory; cap per-userset at MAX_MEMBERS_PER_USERSET = 500,000; beyond that, fall back to store traversal for that userset.
  • Transitive closure on deletion not idempotent: applying same delete twice must not incorrectly remove members still reachable via other paths; use reference-counting or full re-derive.

20.7 Performance Concerns

  • HashMap<UserSet, HashSet<UserId>>: heap pressure; use AHashMap + AHashSet for SIMD-accelerated hashing.
  • Incremental propagation on add: O(ancestors × batch_size); fast for shallow group hierarchies.
  • Propagation on delete: O(subtree_size); batch and re-derive for large deletions.
  • RocksDB Leopard persistence: write entire userset bucket on any change; consider delta encoding for large sets.

20.8 Edge Cases

  • Empty group (no members): valid; is_member returns false for all users; no error.

  • Group with no namespace config: Leopard tracks membership regardless of namespace config; membership semantics are config-independent.

20.9 Failure Analysis

21. Phase 9 — ListObjects / ListUsers + Reverse Expansion

21.1 Objectives

  • Implement ListObjects: "which objects of type T can user U access via relation R?"
  • Implement ListUsers: "which users can access object O via relation R?"
  • Fanout-bounded; Leopard-assisted for group membership reverse lookup.
  • Pagination via zookie-based cursors.

21.2 Detailed Implementation Steps

  • crates/proto/proto/authz/v1/list.proto: define:

    • ListObjectsRequest { user, relation, namespace, consistency, page_size, page_token }.
    • ListObjectsResponse { objects: Vec<ObjectRef>, next_page_token, zookie }.
    • ListUsersRequest { object, relation, user_filter, page_size, page_token }.
    • ListUsersResponse { users: Vec<UserRef>, next_page_token, zookie }.

  • crates/server/src/list.rs + crates/evaluator/src/reverse_expander.rs:

    • ListObjects algorithm: reverse BFS.

      1. Start from user_id.
      2. Find all tuples where user = user:alice across all objects in namespace.
      3. For each such (object, relation, user:alice) tuple: this is a direct hit.
      4. Expand indirectly: find all usersets U where alice ∈ LeopardIndex[U] (Leopard membership → set of candidate usersets).
      5. For each userset U, find tuples (object, relation, userset=U) → candidate objects.
      6. For each candidate object, run Check(alice, relation, object, AT_LEAST_AS_FRESH(snap)) to confirm (eliminates false positives from Leopard lag or intersection/exclusion rules).
      7. Paginate by object_id cursor.
      8. Apply fanout cap: if intermediate set > MAX_LIST_OBJECTS_FANOUT = 10,000, return partial results with FANOUT_TRUNCATED indicator.

    • ListUsers algorithm: forward BFS from object.

      1. Fetch all tuples (object, relation, *) → direct users and usersets.
      2. For each userset, expand via Leopard index to get flat member set.
      3. Paginate by user_id cursor.
      4. Confirm each candidate with Check (when user_filter.type = CONFIRMED; omit for UNCONFIRMED fast mode).

Anchors: reverse BFS from the user is the inverse of the §16 forward eval (B5 graph reachability, P1 reverse expansion); the Leopard inverted index UserId → Set<UserSet> reuses Phase 8's structure (I7) for candidate generation; the mandatory Check-confirm step makes the result exactly the set Check would allow — never an over-approximation from intersection/exclusion — upholding design principle 1 / I1 and design principle 7 (no false-allow), and the over-approx→confirm pattern is why Leopard lag (I2) cannot leak access; fanout cap (FANOUT_TRUNCATED) per design principle 3 / I5.

  • crates/cli/src/list.rs: authzctl list-objects --user alice --relation viewer --namespace document.

21.3 Deliverable

  • authzctl list-objects returns paginated list of objects user can access.
  • authzctl list-users returns paginated list of users who can access object.

22. Phase 10 — Distributed Cache + Hotspot Mitigation

22.1 Objectives

  • Redis-backed distributed subproblem cache for cross-node Check sharing.
  • Lock-table prevents stampede on cache miss.
  • Request coalescer deduplicates concurrent identical subproblems.
  • Hotspot detection + mitigation (objects/usersets with extreme fanout).

22.2 Detailed Implementation Steps

  • crates/cache/src/redis.rs: RedisCacheBackend:

    • Key: base64(hash(user || relation || object || snapshot_id)) (32-byte BLAKE3 hash).
    • Value: 1-byte (0x00 = denied, 0x01 = allowed) + 8-byte snapshot_id.
    • TTL: min(snapshot_freshness_window, 60 s).
    • get(key): GETEX key EX ttl — atomic get + refresh TTL.
    • set(key, value, ttl): SET key value EX ttl NX — only set if not exists (first writer wins).
    • Invalidation: on Watch event for (object, relation), call DEL on all cache keys for that object+relation prefix — use Redis keyspace pattern <namespace>:<object_id>:<relation>:*; requires SCAN + DEL; accept eventual invalidation (within Watch lag ≤ 500 ms).

  • crates/cache/src/lock_table.rs: LockTable:

    • HashMap<CacheKey, Arc<tokio::sync::Mutex<()>>> guarded by DashMap.
    • lock(key) → LockGuard: acquire mutex; prevents concurrent computation of same subproblem.
    • On cache miss: acquire lock → check cache again (double-checked locking) → if still miss, compute → store result → release lock.

  • crates/cache/src/coalescer.rs: RequestCoalescer:

    • DashMap<CacheKey, tokio::sync::broadcast::Sender<bool>>.
    • First waiter for a key creates broadcast channel; computes subproblem; sends result to all waiters.
    • Subsequent waiters for same key subscribe to channel; receive result without re-computing.

  • Hotspot detection: crates/server/src/check.rs: track per-(namespace, object_id) access count in a DashMap<ObjectRef, AtomicU64>; sliding 1-minute window via decaying counter. If object exceeds HOTSPOT_THRESHOLD = 10,000 req/min, apply:

    • Jitter: add 0–5 ms random delay before cache miss store fetch (reduces thundering herd).
    • Staggered cache refresh: instead of TTL expiry causing simultaneous misses, use probabilistic early expiry (random() < (now - set_time) / ttl).
    • Alert: emit hotspot_detected_total metric with object label.

Anchors: snapshot-keyed entries + Watch-driven invalidation enforce design principle 2 / I2 / I8 (never serve an allow a fresh read would deny, MM4); the L1+L2 (in-process → Redis) design and atomic SET NX lock-table per ADR-A08 (Redis); lock-table + coalescer realize design principle 11 (stampede prevention, request coalescing); Redis-unavailable degrades to L1-only while preserving correctness (design principle 7); BLAKE3 key derivation defends the cache-poisoning threat (§Threat Model); hedged reads target the tail-latency budget (§4, §Performance Engineering).

22.3 Deliverable

  • authzd cluster (3 nodes) shares cache state via Redis.
  • Stampede test: 1,000 concurrent Check requests for same cold subproblem → exactly 1 store fetch.
  • Hotspot object: 10,000 req/min → hotspot detected in metrics; jitter applied.

22.4 Acceptance Criteria

  • Cache hit rate: ≥ 95% after warm-up (1,000 unique subproblems, 10,000 requests).
  • Stampede prevention: 1,000 concurrent requests for same key → ≤ 5 store fetches (coalescer allows small burst).
  • Redis unavailable: system falls back to in-process cache only; Check still correct (higher latency); cache_redis_unavailable_total metric.
  • Cache invalidation: write tuple; Watch delivers event; cache entry invalidated within 1 s; subsequent Check fetches from store.
  • Zookie freshness: cache entry for snapshot S must not be served for request requiring snapshot S' > S.

22.5 Conformance Fixtures

  • conformance/cache/stampede.json — 1,000 concurrent requests for cold key; assert 1 store fetch.
  • conformance/cache/invalidation.json — write tuple; check cached; delete tuple; check invalidated.
  • conformance/cache/zookie_freshness.json — cache hit at snapshot S; request at snapshot S+1; must not serve cached result.

22.6 Pitfalls

  • Double-checked locking in Rust async: tokio::sync::Mutex must be held across await point; do not use std::sync::Mutex here (deadlock under async); use tokio::sync::Mutex.
  • Redis key space explosion: one cache entry per (user, relation, object, snapshot_id) 4-tuple; snapshot rotates frequently; entries accumulate; rely on TTL expiry and Redis maxmemory-policy allkeys-lru.
  • Invalidation by prefix SCAN: SCAN is O(keyspace); under large keyspace, invalidation is slow; consider structured Redis hash slots or a separate invalidation channel (pub/sub).
  • Coalescer memory leak: if broadcast sender is never consumed (all receivers dropped), entry stays in DashMap; add cleanup on broadcast completion.

22.7 Performance Concerns

  • Redis round-trip: ~200–500 μs; adds to cache-hit path; accept this cost for cross-node sharing; in-process cache checked first (L1), Redis second (L2).
  • BLAKE3 key hash: ~50 ns; negligible.
  • Lock table contention: DashMap uses sharded locks; N=64 shards; hot objects land on same shard; monitor DashMap contention via parking_lot metrics.

22.8 Edge Cases

  • Redis SET NX race: two nodes compute same result simultaneously; both attempt SET NX; one wins; other discards; both correct.
  • Redis eviction (maxmemory): evicted cache entries are cache misses, not correctness violations; tolerate.

22.9 Failure Analysis

  • Redis cluster partition: nodes fall back to in-process cache; cache hit rate drops; latency increases; Check still correct; alert on cache_redis_error_total.

22.10 Operational Notes

  • Redis config: maxmemory 4GB, maxmemory-policy allkeys-lru, bind 127.0.0.1 (or mTLS tunnel); save "" (no persistence for cache).
  • Metrics: cache_hit_total, cache_miss_total, cache_stampede_coalesced_total, hotspot_detected_total.
  • Runbook: docs/runbooks/runbook-check-latency-regression.md — section: cache miss rate spike.

23. Phase 11 — Sharding, Replication, and Production Hardening

23.1 Objectives

  • Partition MVCC tuple store across N shards by hash(namespace, object_id).
  • Replicate each shard via Raft (using openraft).
  • Rate limiting, circuit breaker, graceful degradation.
  • Production-grade TLS, mTLS service mesh, cert rotation.
  • All SLOs met under production load profile.

23.2 Detailed Implementation Steps

  • Shard routing: crates/server/src/router.rs: ShardRouter:

    • shard_for(namespace, object_id) → ShardId: ShardId = hash(namespace || object_id) % NUM_SHARDS.
    • Consistent hashing ring (rendezvous hashing preferred over modular for low resharding on scale-out).
    • Shard map: HashMap<ShardId, Vec<NodeAddr>> (primary + replicas); refreshed from config store.
    • For writes: route to primary only.
    • For reads: route to primary (FULLY_CONSISTENT) or any replica (MINIMIZE_LATENCY).

  • Shard Raft groups: each shard runs an independent openraft group; leader = write primary; followers = read replicas.

    • authzd node participates in multiple Raft groups (one per shard it hosts); shard count / node count = shards per node.
    • Raft log = tuple WAL; state machine = RocksDB shard.

  • Rate limiting: crates/server/src/interceptors/rate_limit.rs:

    • Token bucket per tenant per RPC type: Check / Write / ListObjects.
    • Configured via rate_limits.toml; hot-reloaded on SIGHUP.
    • On exceed: gRPC RESOURCE_EXHAUSTED with Retry-After header.

  • Circuit breaker: crates/server/src/circuit_breaker.rs:

    • Per-shard circuit breaker (half-open / open / closed).
    • Open after 5 consecutive failures within 10 s.
    • Half-open probe every 30 s.
    • Metrics: circuit_breaker_open_total, circuit_breaker_half_open_total.

  • TLS: crates/server/src/config.rs:

    • TlsConfig { cert_path, key_path, ca_path }.
    • rustls acceptor; SIGHUP reloads certs without dropping connections.
    • mTLS option: require_client_cert: bool; validate client cert against CA.

Anchors: per-shard Raft groups replicate the MVCC store per ADR-A10 (P8 Raft; R4/R5 sharded-store patterns) to meet RTO ≤ 30 s / RPO 0 (§4); rendezvous hashing minimizes resharding movement; rate limiter + circuit breaker realize design principle 11 (load shedding) and back the gRPC-flood/DoS threat (§Threat Model); rustls TLS/mTLS with SIGHUP reload per ADR-A17 (RFC8) defends the mTLS-bypass threat; graceful drain honors the §4 30 s shutdown budget; cross-shard writes are explicitly non-atomic (documented), upholding design principle 13 (no silent partial success).

  • Graceful shutdown: on SIGTERM → stop accepting new requests → drain in-flight RPCs (30 s deadline) → flush WAL → close RocksDB → exit 0.

23.3 Deliverable

  • 3-shard, 3-replica cluster running in docker-compose.yml.
  • 50,000 Check req/s sustained; p99 ≤ 30 ms.
  • Shard leader failure: auto-reelection; zero Check failures after 30 s.
  • Cert rotation: SIGHUP reloads certs; no dropped connections.

23.4 Acceptance Criteria

  • Load test: benchmarks/load/check_load.rs → 50,000 req/s; p99 ≤ 30 ms; error rate ≤ 0.01%.
  • Shard failure: kill shard-0 leader; 30 s later → all Checks to shard-0 objects succeed.
  • Rate limit: exceed configured limit → RESOURCE_EXHAUSTED within 10 ms.
  • Circuit breaker opens after 5 failures; closes after probe success.
  • mTLS: client without cert → UNAUTHENTICATED.

23.5 Conformance Fixtures

  • conformance/cluster/shard_routing.json — 100 objects; assert correct shard assignment.
  • conformance/cluster/failover.json — shard leader killed; requests succeed after re-election.

23.6 Pitfalls

  • Shard routing consistency: after resharding (adding nodes), some objects route to new shards; in-flight requests may hit wrong shard; add routing version to request metadata; stale routing → SHARD_MOVED error with redirect hint.
  • Raft log compaction and snapshot: each shard Raft log grows; must snapshot state machine (RocksDB checkpoint) and truncate log periodically; implement openraft::RaftStorage::apply_snapshot.
  • Multi-shard writes: a WriteTuples batch spanning multiple shards is not atomic across shards; document this; only per-shard atomicity is guaranteed; cross-shard 2PC not in scope.

Mental Models & First Principles

The compressed intuitions an expert holds about a Zanzibar-style authorization system. Each: the insight, what it predicts, the bug class you write without it, and where this blueprint applies it. Every cited § resolves.

  • MM1 — Authorization is a reachability query over a relation graph; everything else is an evaluation strategy. "Can U do R on O?" = "is there a path from U to (O,R) through tuples and rewrite rules?" cwnd-style growth laws have no analog here — the only question is graph reachability under a rewrite-defined edge expansion. Predicts: any policy expressible as graph reachability (RBAC, group inheritance, ownership-implies-edit) fits; anything requiring attribute arithmetic (time-of-day, IP range) does not. Bug without it: bolting attribute predicates into rewrite rules, producing a half-ABAC engine that satisfies neither model. Applied: §8.3 (rewrite AST), Phase 3 §15.2, Phase 9 §21.2 (reverse reachability), Comparative Architecture Table.
  • MM2 — A consistency token (zookie) converts a global-ordering problem into a per-request freshness floor. Instead of locking the world to agree "what is true now," each writer hands the reader a snapshot stamp meaning "be at least this fresh." The reader, not the system, carries the freshness requirement. Predicts: you get safe revocation without a coordination round-trip on every read — the cost moves to the (rare) reads that actually need freshness. Bug without it: either a global lock (kills throughput) or stale caches that re-admit a revoked user (new-enemy). Applied: design principle 2, §8.4, §8.8 Example C, Phase 7 §19.2, I2.
  • MM3 — The new-enemy problem is a causality violation, not a staleness nuisance. If Alice revokes Mallory and then shares a doc, a check that sees the share but not the revocation has reordered two causally-linked writes. Snapshot freshness keyed by the zookie restores the happened-before order. Predicts: bounding staleness alone (a TTL) is insufficient; you must bound it relative to a specific prior write. Bug without it: "our cache is only 5 s stale, that's fine" — 5 s is forever for a revocation. Applied: §2 (new-enemy), design principle 2, §8.8 Example C, I2, Threat Model T3.
  • MM4 — A cache in a correctness-critical path is not an optimization; it is a second source of truth that must agree with the first. A latency cache that can disagree with the store is a security bug generator. The snapshot key + Watch invalidation make the cache a function of (store, snapshot), never an independent opinion. Predicts: any cache entry not keyed by snapshot will eventually serve a result the store would not. Bug without it: caching (user,relation,object)→bool without the snapshot, serving a post-revocation allow. Applied: design principle 2, Phase 10 §22.2, I8, Failure Modes & Recovery FM4.
  • MM5 — Termination must be a structural guarantee, not an emergent property of the data. A recursive evaluator over operator-supplied namespace configs and attacker-supplied tuples will loop or explode unless depth and fanout are hard-capped independent of input. Cycle detection is an optimization on top; the caps are the guarantee. Predicts: even a maliciously cyclic config terminates because the depth cap fires regardless of whether cycle detection works. Bug without it: relying on visited-set cycle detection alone, then hanging on a path the set doesn't cover (TTU-initiated sub-checks). Applied: design principle 3, §4 (depth 25 / fanout 1000), Phase 4 §16.2, I5, Threat Model T7.
  • MM6 — External consistency is bought with waiting, and the wait is the clock's uncertainty. Without GPS/atomic clocks, an HLC cannot know it is "past" a timestamp until it has waited out the worst-case skew. wait_until_safe is that wait; the uncertainty window is its price. Predicts: tighter clocks (TrueTime) → shorter commit-wait → lower FULLY_CONSISTENT latency; the 7 ms window is a direct latency tax on the freshest reads. Bug without it: returning a snapshot before it is safe, admitting a write that should have been ordered after the read. Applied: §4 (uncertainty window 7 ms), Phase 7 §19.2, I9, §8.5 (FULLY_CONSISTENT).
  • MM7 — A materialized index trades write amplification for read latency, and its lag is a correctness boundary, not just a freshness one. Leopard makes deep group checks O(1) by precomputing transitive closure, paid for in write fan-out and storage. But because it is eventually consistent, a check that trusts it blindly can serve a stale membership. Predicts: the index helps reads exactly in proportion to group nesting depth, and its lag must gate its use on freshness-sensitive checks. Bug without it: serving an AT_LEAST_AS_FRESH(Z) check from a Leopard that hasn't processed up to Z. Applied: design principle 10, Phase 8 §20.2 (MAX_LEOPARD_LAG guard), I7, §Scalability Analysis.
  • MM8 — Reverse expansion is an over-approximation that must be narrowed by forward confirmation. "Which objects can Alice see?" via reverse BFS yields candidates; intersection/exclusion rules and index lag mean some candidates are false positives. Only a forward Check per candidate is ground truth. Predicts: ListObjects without a confirm step leaks objects under any rewrite using exclusion, or under Leopard lag. Bug without it: returning the raw reverse-BFS set as the answer. Applied: Phase 9 §21.2, design principle 7, I1, §8.3 (Exclusion).
  • MM9 — Type confusion in the tuple model is a silent authorization bug, not a crash. Conflating object_id with user_id, or a namespace with a relation, doesn't panic — it grants or denies the wrong thing. Distinct newtypes make the conflation a compile error. Predicts: a stringly-typed tuple API will eventually mismatch a field and mis-authorize; the bug surfaces as a security incident, not a stack trace. Bug without it: passing (user, object) where (object, user) was meant and checking the wrong direction. Applied: design principle 4, §11.1, Phase 0 §12.2, §2.
  • MM10 — Fail-closed is a property of every error path, not a top-level catch. Authorization must deny on any uncertainty — store timeout, oracle unavailable, depth exceeded, decode failure. A single error path that returns Ok(true) or defaults to allow is a breach. Predicts: every new error variant added to AuthzError must be audited for its Check return; the safe default is structural. Bug without it: a newly added timeout path that propagates a default-true. Applied: design principle 7, §11.7 (AuthzError), I12, Phase 12 §24.2 (fault injection).

  • Google Zanzibar (Pang et al., USENIX ATC 2019) is the system this design reimplements; its one defining decision was to make a consistency token (the zookie) a first-class part of the API, so that correctness under caching becomes the caller's explicit choice rather than the system's global guarantee. It wins at Google scale — trillions of checks/day across Drive/Calendar/YouTube — because that scale makes per-read global coordination impossible, so pushing freshness to a token is the only viable path. It is not open-source; this blueprint and the systems below are the reproductions.
  • SpiceDB (authzed) made the decision to ship a schema DSL (caveats, a typed object/relation language) on top of the raw tuple model, trading some of Zanzibar's minimalism for developer ergonomics and a compile-time-checked permission schema. It wins for teams that want a typed, reviewable permission model in source control with strong tooling — its niche is the "Zanzibar you can actually adopt." Its datastore default is Postgres (this blueprint defaults to RocksDB, ADR-A06), and it dispatches recursively with caching rather than exposing a public Leopard index (R1).
  • OpenFGA (Okta/Auth0, CNCF) made the decision to standardize an authorization-model language and a consistency-preference knob, and to be a CNCF-governed open standard rather than a single vendor's engine. It wins where vendor-neutral governance and a documented model spec (RFC5) matter, and where an organization wants to adopt FGA-as-a-spec across services; this blueprint's parser treats OpenFGA model syntax as a comparison/compat baseline (§8.2, R2) and can be differential-tested against it (ADR-A20).
  • AWS IAM made the decision to bind policies to identities and resources as JSON documents evaluated by a managed service, rather than modeling a relation graph — there is no notion of "userset rewrite," only policy statements with conditions. It wins overwhelmingly inside AWS, where every resource already has an ARN and the control plane is the same vendor; its niche is "authorization for the cloud you're already in." It cannot express arbitrary application-domain relationships (a document's parent folder's viewers) the way ReBAC does, which is exactly the gap ReBAC fills (§2).
  • OPA / Rego (Open Policy Agent) made the most different decision: authorization as policy-as-code evaluated against caller-supplied JSON, with no stored relation graph at all — the engine is stateless and the data arrives with the query. It wins for heterogeneous policy that mixes attributes, request context, and arbitrary logic (admission control, API gateways), where a fixed relation model is too rigid. It is the ABAC/PBAC counterpoint to this design (RFC6): it cannot answer "which objects can this user see?" without the caller materializing the data, because it owns no store and runs no graph traversal — the precise reason this service exists as a separate system class.

Back-of-Envelope Capacity Model

Numbers an expert computes from §4 (System Constraints) before designing. Each is derived step-by-step; the §4 input is named. (Units: 1 KB = 10³ B for storage rounding; ms/μs as stated.)

  • C1 — Tuple-store footprint per billion tuples. Input: §4 "Storage per 1B tuples ≤ 200 GB (compressed)" and §4 "Max tuple key size 2,048 B". A raw tuple key+version is ≤ 2,048 B key + 16 B (created_at + deleted_at, 2×u64) ≈ 2 KB worst case → 1e9 × 2 KB = 2 TB uncompressed; the §4 200 GB ceiling implies an assumed compression + typical-key ratio of ~10× (2 TB ÷ 200 GB = 10). This sets the RocksDB compression expectation and matches the §4 "write amp ≤ 10×" budget being the other 10× to watch.
  • C2 — Leopard index size at the worst case. Input: §4 "Leopard index overhead ≤ 3× tuple store size" and C1. 3 × 200 GB = 600 GB per 1B tuples fully-transitive — exactly the §Scalability "~600 GB for 1B tuples" figure. This is why §Scalability distributes Leopard by userset hash: a single node's §4 4 GB heap cannot hold it, so Leopard is disk-backed (RocksDB CF) with the hot set in memory.
  • C3 — Per-Check tuple-fetch bandwidth at target throughput. Input: §4 "Check throughput ≥ 50,000 req/s per node" and "Max Check recursion depth 25". Worst-case a cold Check issues up to depth × (1 fetch/level) store reads; at a typical depth 3 with ~1 fetch/level and ~1 KB per fetched tuple row: 50,000 req/s × 3 fetches × 1 KB = 150 MB/s of store read traffic per node before caching. The §4 "≥ 95% cache hit" target (Phase 10) cuts this to ~7.5 MB/s of actual store I/O — the quantitative reason the cache is not optional at 50k req/s.
  • C4 — Subproblem cache capacity in entries. Input: §4 "Subproblem cache size 256 MB per node". A cache entry ≈ 32 B BLAKE3 key + 1 B bool + 8 B snapshot + ~40 B map overhead ≈ 80 B. 256 MB ÷ 80 B ≈ 3.2 M entries resident per node. At 50k req/s that is 3.2e6 ÷ 50,000 = 64 s of unique-subproblem working set before eviction — consistent with the §15.9 / Phase 3 60 s config-cache TTL and the design-principle-2 freshness window.
  • C5 — Write WAL bandwidth and the fsync bound. Input: §4 "Write throughput ≥ 5,000 tuples/s per node" and "gRPC max message size 4 MB". 5,000 tuples/s × ~2 KB/tuple (key+changelog entry) = 10 MB/s sustained WAL write — trivial for an SSD's sequential bandwidth, confirming §Scalability's diagnosis that writes are bound by fsync latency (per-commit durability), not bandwidth. Batching (one fsync per WriteBatch) is therefore the lever, as §17.7 states.
  • C6 — Oracle commit-wait tax on the freshest reads. Input: §4 "Oracle uncertainty window ≤ 7 ms" and "Check p99 ≤ 30 ms". A FULLY_CONSISTENT Check pays up to the full 7 ms wait_until_safe (MM6) plus a Raft commit (~2 ms, §19.7) = ~9 ms, which is 9 ÷ 30 = 30% of the p99 budget. This is why §8.5 reserves FULLY_CONSISTENT for admin/audit and defaults standard authz to AT_LEAST_AS_FRESH (no oracle round-trip on a cache hit).
  • C7 — Watch fan-out and the consumer ceiling. Input: §4 "Watch lag p99 ≤ 500 ms", §Scalability "~1,000 concurrent consumers", and §18.2 "channel capacity 256". Each consumer holds a 256-entry bounded channel; at ~1 KB per WatchEvent, 1,000 consumers buffer 1,000 × 256 × 1 KB = 256 MB worst case — a meaningful slice of the §4 4 GB heap, which is exactly why §Scalability caps consumers at ~1,000 and routes beyond that through a Kafka-style fan-out proxy.
  • C8 — Fanout-DoS amplification bounded by the caps. Input: §4 "Max fanout per level 1,000" and "Max depth 25". An uncapped recursive Check on a maliciously wide+deep graph is O(fanout^depth) = 1000^25 — astronomically unbounded. The per-request fanout cap (total, not per-level, §16.6) plus depth cap convert this to a hard linear bound ≤ 1,000 subjects total before FANOUT_EXCEEDED (MM5). This is the single most important DoS arithmetic in the system (Threat Model T7).
  • C9 — Leopard ROI: when the index pays for itself. Input: §4 "Check p99.9 ≤ 100 ms (adversarial deep nesting)" and §20 "depth-10 chain p99 drops to ≤ 10 ms". A depth-10 group chain without Leopard costs ~10 store round-trips × ~2 ms = ~20 ms+ per check; Leopard's O(1) is_member collapses that to one lookup (~sub-ms) + confirm. The index earns its 3× storage cost (C2) precisely when group nesting depth × check rate is high — breakeven ≈ (store_rtt × avg_depth × check_rate) > (write_amp_cost), which §20 frames as the depth/fanout tradeoff.
  • C10 — Snapshot retention vs changelog/Watch window. Input: §4 "MVCC snapshot retention 72 h" and "Changelog retention 7 days". Retention must satisfy snapshot_retention ≤ changelog_retention so a Watch/Leopard consumer that resumes from an old zookie can still replay — 72 h < 7 days ✓ with ~5.6 days of headroom. A consumer offline longer than 7 days hits SNAPSHOT_TOO_OLD (§18.8) and must full-resync; this inequality is the operational contract behind that error.
  • C11 — Connection budget per node. Input: §Scalability "~10k concurrent connections per node (fd limit)" and §4 "Check throughput ≥ 50,000 req/s". At 10k connections sharing 50k req/s, each connection averages 50,000 ÷ 10,000 = 5 req/s — but gRPC/HTTP-2 multiplexes many streams per connection (RFC4), so the fd limit, not the stream count, is the binding constraint. This is why §Scalability scales connections horizontally (more Check nodes) rather than vertically.

Alternative Architectures (Roads Not Taken)

Fundamentally different ways to build authorization for the same goal — not parameter tweaks. Each: ASCII sketch, the regime where it wins, the real system embodying it, why this blueprint rejected it.

A1 — Embedded/library authorization (policy + data co-located in each service). No central authority; every service links an authz library and owns its own relation data or policy bundle.

  ┌── service A ──┐   ┌── service B ──┐   ┌── service C ──┐
  │ app + authz   │   │ app + authz   │   │ app + authz   │
  │ lib + local   │   │ lib + local   │   │ lib + local   │
  │ policy/data   │   │ policy/data   │   │ policy/data   │
  └───────────────┘   └───────────────┘   └───────────────┘
      (no shared store; each evaluates against its own copy)
  • Wins: low-latency, no-network-hop authorization for services that own their own data and need no cross-service consistency — eval is a local function call with zero RTT.
  • Real system: OPA/Rego (Open Policy Agent) deployed as a sidecar/library, evaluating policy against data supplied per request; Casbin embedded in-process.
  • Rejected because: the entire premise here is a centralized, decoupled authority with cross-service consistency and a single audit point (§1, §2). A library model cannot answer "which objects across the whole system can this user see?" or guarantee new-enemy-safe revocation across services (design principle 2) — each copy is an independent source of truth (MM4), the opposite of this design.

A2 — Pure RBAC / role table (no relation graph, no rewrites). Authorization is a join over (user→role) and (role→permission) tables; no transitive group traversal, no userset rewrites.

   users ──┐                       ┌── permissions
           ▼                       ▼
        user_roles ──▶ roles ──▶ role_perms
           (flat joins; no recursion, no parent inheritance)
  • Wins: simple, well-understood, fast (two indexed joins) for flat organizations where permissions map cleanly to a bounded set of roles and there is no "folder inherits from parent folder" structure.
  • Real system: classical NIST RBAC (Sandhu et al., P11; Ferraiolo & Kuhn, P13) as implemented in countless application roles/permissions tables and in database GRANT systems.
  • Rejected because: RBAC is the union-of-_this-only special case of this engine (§8.3, MM1) — it cannot natively express transitive group-via-parent inheritance or computed/tuple-to-userset rewrites without bolting on custom recursion, which is exactly the recursion this design makes a first-class, bounded primitive (Phase 4 §16.2). Building the general engine subsumes RBAC at modest extra cost.

A3 — ABAC / policy-as-attributes (decision = f(subject attrs, resource attrs, context)). No stored relationships; each decision is a boolean function over attributes evaluated at request time.

   request ─▶ ┌─────────────────────────────┐
   {subj,     │  policy engine: evaluate     │ ─▶ allow / deny
    res,      │  rules over attributes        │
    action,   │  (time, IP, dept, clearance)  │
    env}      └─────────────────────────────┘
              (no relation store; attributes arrive with the request)
  • Wins: policies that genuinely depend on attributes and context — time-of-day, IP range, data-classification level, dynamic risk score — that no relation graph can encode.
  • Real system: NIST ABAC (SP 800-162, RFC6/P12); XACML; AWS IAM policy conditions; OPA/Rego when used for attribute logic.
  • Rejected because: this service is deliberately not an attribute engine (§1 non-goals) — its strength is relationship reachability (MM1), and mixing attribute arithmetic into rewrite rules would yield a half-ABAC engine satisfying neither model (MM1's bug class). ABAC and ReBAC are complementary system classes; this blueprint stays purely on the relation side and defers attribute predicates entirely.
