Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why is a TTL-bounded cache insufficient to prevent the new-enemy problem, and what does the zookie add that a 1-second TTL does not? (design principle 2 + §8.8 Example C + MM3 + I2)
  2. Trace a single AT_LEAST_AS_FRESH(Z) Check from zookie decode to allow/deny, naming every point where a stale or unsafe value would be rejected. (§8.4 + §8.5 + Phase 7 §19.2 + I2)
  3. The depth cap (25) and the fanout cap (1,000) both bound termination. Show why removing either one alone still leaves a DoS, using the amplification arithmetic. (§4 + §Back-of-Envelope C8 + MM5 + Threat Model T7)
  4. Why does the fanout counter have to be per-request total rather than per-level, and what is the exact blow-up if it is per-level? (Phase 4 §16.6 + §Back-of-Envelope C8 + design principle 3)
  5. Leopard is eventually consistent but Check claims snapshot determinism. Reconcile these: how can a check that consults Leopard still be deterministic at a fixed snapshot? (design principle 1 + design principle 10 + Phase 8 §20.2 + I1 + I7 + MM7)
  6. A ListObjects result includes an object the caller cannot actually access. Name every layer that could have produced the false positive and the single mechanism that eliminates all of them. (Phase 9 §21.2 + §8.3 + MM8 + I1)
  7. Why does FULLY_CONSISTENT consume ~30% of the p99 latency budget, and what two costs compose that number? (§Back-of-Envelope C6 + §8.5 + Phase 7 §19.7 + MM6)
  8. Explain why the in-memory dev store and the RocksDB prod store can share one TupleStore trait but must implement the MVCC visibility filter identically, and what breaks if they drift. (§11.4 + design principle 9 + I10 + Phase 1 §13.2 + Phase 6 §18.2)
  9. The HMAC on a zookie prevents forgery, but what attack remains possible if an attacker captures a valid old zookie, and which design property neutralizes it? (§8.4 + Threat Model T3/T9 + I2)
  10. Why must namespace config be read at the same snapshot as the tuples in a Check, and construct the incorrect result that arises if config is read at now() instead? (design principle 12 + Phase 3 §15.6 + I6 + §8.6)
  11. Derive the store-read bandwidth a single node sees at 50k req/s before and after the cache, and explain why the cache is a correctness and capacity requirement. (§Back-of-Envelope C3 + §4 + Phase 10 §22.2 + MM4)
  12. Why is the changelog the single source for both Watch and Leopard, and what ordering invariant must hold for both consumers to be correct? (design principle 5 + Phase 6 §18.2 + Phase 8 §20.2 + I3 + I11)
  13. Compare how this design and OPA/Rego would each answer "which documents can Alice view?" and explain why one can and one structurally cannot. (Comparative Architecture Table + Phase 9 §21.2 + MM1)
  14. A new AuthzError variant is added for a storage backpressure condition. What must be audited about its Check return path, and which principle makes the safe default structural? (§11.7 + design principle 7 + I12 + MM10)
  15. Why does the snapshot-retention window have to be shorter than the changelog-retention window, and what operator-visible error enforces the boundary when a consumer violates it? (§Back-of-Envelope C10 + §4 + Phase 6 §18.8)
  16. Explain why hot-swapping is not a concern here the way it is in a pluggable algorithm host, but namespace-config versioning is the analogous problem — and how I6 plays the role hot-swap state-migration would. (design principle 12 + I6 + §8.6 + Phase 2 §14.6)
  17. The Leopard index has a MAX_LEOPARD_LAG guard. Derive when skipping the index (falling back to live traversal) is cheaper overall than the latency it was added to save. (Phase 8 §20.2 + §Back-of-Envelope C9 + MM7)
  18. Why can two simultaneous writes in the same wall-clock millisecond both receive unique, ordered SnapshotIds, and what field of the HLC guarantees it? (§8.4 + Phase 7 §19.2/§19.8 + I9 + P4)
  19. Walk the exact failure sequence when the oracle leader dies mid-Check, naming which consistency levels block, which proceed, and the recovery path. (Phase 7 §19.6/§19.9 + Failure Modes & Recovery FM1 + design principle 7)
  20. Why is _this defined to match a userset by exact equality rather than expanding it, and what double-counting or infinite-loop bug arises if _this expands group members inline? (§8.3 + Phase 4 §16.2 + MM5)
  21. Construct the storage and bandwidth budget for 1B tuples end-to-end (store + Leopard + WAL), and identify which of the three is the binding constraint on a single node. (§Back-of-Envelope C1/C2/C5 + §4 + §Scalability Analysis)
  22. Explain why a cross-shard WriteTuples batch is deliberately non-atomic, what guarantee is offered, and which principle forbids silently pretending it succeeded. (Phase 11 §23.6 + design principle 13 + Compatibility & Versioning)
  23. Why does the differential harness compare against SpiceDB by default but allow OpenFGA as an alternative oracle, and what does each validate that the other does not? (§9 ADR-A20 + Comparative Architecture Table + Phase 12 §24.2)
  24. A confused-deputy attack and a tuple-injection attack both end in privilege escalation. Distinguish their vectors and the different mechanism that stops each. (Threat Model T1/T2 + design principle 4 + MM9)
  25. Given the 7 ms uncertainty window and a path where clocks skew by 12 ms, what does wait_until_safe do, what does the HLC's logical counter absorb, and where does the system refuse rather than serve a wrong answer? (§4 + Phase 7 §19.6/§19.8 + I9 + MM6)

Mental Models & First Principles

The compressed intuitions an expert holds about a Zanzibar-style authorization system. Each: the insight, what it predicts, the bug class you write without it, and where this blueprint applies it. Every cited § resolves.

  • MM1 — Authorization is a reachability query over a relation graph; everything else is an evaluation strategy. "Can U do R on O?" = "is there a path from U to (O,R) through tuples and rewrite rules?" cwnd-style growth laws have no analog here — the only question is graph reachability under a rewrite-defined edge expansion. Predicts: any policy expressible as graph reachability (RBAC, group inheritance, ownership-implies-edit) fits; anything requiring attribute arithmetic (time-of-day, IP range) does not. Bug without it: bolting attribute predicates into rewrite rules, producing a half-ABAC engine that satisfies neither model. Applied: §8.3 (rewrite AST), Phase 3 §15.2, Phase 9 §21.2 (reverse reachability), Comparative Architecture Table.
  • MM2 — A consistency token (zookie) converts a global-ordering problem into a per-request freshness floor. Instead of locking the world to agree "what is true now," each writer hands the reader a snapshot stamp meaning "be at least this fresh." The reader, not the system, carries the freshness requirement. Predicts: you get safe revocation without a coordination round-trip on every read — the cost moves to the (rare) reads that actually need freshness. Bug without it: either a global lock (kills throughput) or stale caches that re-admit a revoked user (new-enemy). Applied: design principle 2, §8.4, §8.8 Example C, Phase 7 §19.2, I2.
  • MM3 — The new-enemy problem is a causality violation, not a staleness nuisance. If Alice revokes Mallory and then shares a doc, a check that sees the share but not the revocation has reordered two causally-linked writes. Snapshot freshness keyed by the zookie restores the happened-before order. Predicts: bounding staleness alone (a TTL) is insufficient; you must bound it relative to a specific prior write. Bug without it: "our cache is only 5 s stale, that's fine" — 5 s is forever for a revocation. Applied: §2 (new-enemy), design principle 2, §8.8 Example C, I2, Threat Model T3.
  • MM4 — A cache in a correctness-critical path is not an optimization; it is a second source of truth that must agree with the first. A latency cache that can disagree with the store is a security bug generator. The snapshot key + Watch invalidation make the cache a function of (store, snapshot), never an independent opinion. Predicts: any cache entry not keyed by snapshot will eventually serve a result the store would not. Bug without it: caching (user,relation,object)→bool without the snapshot, serving a post-revocation allow. Applied: design principle 2, Phase 10 §22.2, I8, Failure Modes & Recovery FM4.
  • MM5 — Termination must be a structural guarantee, not an emergent property of the data. A recursive evaluator over operator-supplied namespace configs and attacker-supplied tuples will loop or explode unless depth and fanout are hard-capped independent of input. Cycle detection is an optimization on top; the caps are the guarantee. Predicts: even a maliciously cyclic config terminates because the depth cap fires regardless of whether cycle detection works. Bug without it: relying on visited-set cycle detection alone, then hanging on a path the set doesn't cover (TTU-initiated sub-checks). Applied: design principle 3, §4 (depth 25 / fanout 1000), Phase 4 §16.2, I5, Threat Model T7.
  • MM6 — External consistency is bought with waiting, and the wait is the clock's uncertainty. Without GPS/atomic clocks, an HLC cannot know it is "past" a timestamp until it has waited out the worst-case skew. wait_until_safe is that wait; the uncertainty window is its price. Predicts: tighter clocks (TrueTime) → shorter commit-wait → lower FULLY_CONSISTENT latency; the 7 ms window is a direct latency tax on the freshest reads. Bug without it: returning a snapshot before it is safe, admitting a write that should have been ordered after the read. Applied: §4 (uncertainty window 7 ms), Phase 7 §19.2, I9, §8.5 (FULLY_CONSISTENT).
  • MM7 — A materialized index trades write amplification for read latency, and its lag is a correctness boundary, not just a freshness one. Leopard makes deep group checks O(1) by precomputing transitive closure, paid for in write fan-out and storage. But because it is eventually consistent, a check that trusts it blindly can serve a stale membership. Predicts: the index helps reads exactly in proportion to group nesting depth, and its lag must gate its use on freshness-sensitive checks. Bug without it: serving an AT_LEAST_AS_FRESH(Z) check from a Leopard that hasn't processed up to Z. Applied: design principle 10, Phase 8 §20.2 (MAX_LEOPARD_LAG guard), I7, §Scalability Analysis.
  • MM8 — Reverse expansion is an over-approximation that must be narrowed by forward confirmation. "Which objects can Alice see?" via reverse BFS yields candidates; intersection/exclusion rules and index lag mean some candidates are false positives. Only a forward Check per candidate is ground truth. Predicts: ListObjects without a confirm step leaks objects under any rewrite using exclusion, or under Leopard lag. Bug without it: returning the raw reverse-BFS set as the answer. Applied: Phase 9 §21.2, design principle 7, I1, §8.3 (Exclusion).
  • MM9 — Type confusion in the tuple model is a silent authorization bug, not a crash. Conflating object_id with user_id, or a namespace with a relation, doesn't panic — it grants or denies the wrong thing. Distinct newtypes make the conflation a compile error. Predicts: a stringly-typed tuple API will eventually mismatch a field and mis-authorize; the bug surfaces as a security incident, not a stack trace. Bug without it: passing (user, object) where (object, user) was meant and checking the wrong direction. Applied: design principle 4, §11.1, Phase 0 §12.2, §2.
  • MM10 — Fail-closed is a property of every error path, not a top-level catch. Authorization must deny on any uncertainty — store timeout, oracle unavailable, depth exceeded, decode failure. A single error path that returns Ok(true) or defaults to allow is a breach. Predicts: every new error variant added to AuthzError must be audited for its Check return; the safe default is structural. Bug without it: a newly added timeout path that propagates a default-true. Applied: design principle 7, §11.7 (AuthzError), I12, Phase 12 §24.2 (fault injection).

Glossary · 42 terms · site-wide glossary

Relation tuple
Atomic permission record: ⟨object#relation@user⟩; the fundamental data unit of the system
Namespace
Type name for objects (e.g., document, folder); scopes relation definitions
Relation
Named edge type in the authorization graph (e.g., viewer, editor, owner)
Userset
A set of users identified by object#relation (e.g., group:eng#member); used as subject in tuples
UserRef
Union type: either a concrete UserId or a UserSet
Zookie
Opaque consistency token encoding a SnapshotId; HMAC-protected; prevents new-enemy
SnapshotId
Monotonically increasing u64 HLC timestamp; identifies a point-in-time view of the store
New-enemy problem
Consistency anomaly: after revoking access, a cached result still allows access because it predates the revocation
Rewrite rule
Expression defining how a relation's membership is computed: _this, computed_userset, tuple_to_userset, union, intersection, exclusion
_this
Rewrite leaf: membership = direct tuples in the store for (object, relation)
computed_userset
Rewrite: membership = membership of another relation on the same object
TTU (tuple_to_userset)
Rewrite: follow a tupleset relation to find a subject, then check computed_rel on that subject
Rewrite AST
Tree representation of a relation's membership computation rules
Check
Boolean API: "can user U perform relation R on object O?"
Expand
Tree API: returns the full userset membership tree for (relation, object)
Watch
Streaming API: delivers changelog events since a given zookie
ListObjects
Reverse expansion API: "which objects of type T can user U access via R?"
Leopard index
Materialized flat transitive group membership index; bounds deep-nesting fanout
MVCC
Multi-Version Concurrency Control: each row versioned by SnapshotId; enables snapshot-isolated reads
Changelog
Append-only ordered log of all tuple mutations; keyed by SnapshotId; source for Watch and Leopard
Timestamp oracle
Service providing globally ordered, monotonically increasing SnapshotIds; HLC-based
HLC (Hybrid Logical Clock)
Clock combining wall-clock time with a logical counter to ensure monotonicity across events
Uncertainty window
Maximum HLC clock skew (7 ms); wait_until_safe blocks for this duration to ensure external consistency
External consistency
Property: if a write commits before another write starts (in real time), the second write has a higher SnapshotId
Snapshot read
Read at a fixed SnapshotId; returns only tuples with created_at ≤ snap AND (deleted_at IS NULL OR deleted_at > snap)
Tombstone
Soft-deleted tuple record; deleted_at set; visible to historical snapshots; removed by compaction
Compaction filter
RocksDB callback invoked during compaction; removes tombstones past retention window
Fanout
Number of userset subjects fetched in one TTU or union step; bounded by MAX_FANOUT = 1,000
Depth cap
Maximum recursion depth for Check traversal; MAX_DEPTH = 25
Subproblem cache
Memoization of (user, relation, object, snapshot_id) → bool; L1 in-process + L2 Redis
Stampede prevention
Lock-table ensuring only one concurrent computation per cache key; prevents thundering herd
Request coalescer
Deduplicates concurrent identical requests; all waiters receive the result of one computation
Hotspot
Object or userset with extremely high access rate (> 10k req/min); requires special mitigation
ConsistencyLevel
Enum: MINIMIZE_LATENCY, AT_LEAST_AS_FRESH(zookie), FULLY_CONSISTENT
Precondition
Write condition: MUST_EXIST or MUST_NOT_EXIST on a tuple; atomic with the write
Circuit breaker
Per-shard failure detector; OPEN state rejects requests immediately after repeated failures
ShardId
hash(namespace, object_id) % NUM_SHARDS; determines which Raft group stores the tuple
Shard router
Maps (namespace, object_id) to a shard and its healthy replicas
SLSA provenance
Supply-chain attestation linking a binary artifact to its source code and build process
SBOM
Software Bill of Materials; lists all transitive dependencies and their licenses
Fail-closed
On error, Check returns DENIED (or error), never ALLOWED; safety property
Differential testing
Running identical queries against two implementations and comparing results
