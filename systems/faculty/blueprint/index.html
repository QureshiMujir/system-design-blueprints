1. Goal & Scope

Faculty is a cognition-runtime platform: a browser extension and web application that loads a versioned, signed, manifest-defined behavioral package (a "Faculty") into a live session, wraps an arbitrary browser task with that Faculty's retrieval-grounded, rule-constrained LLM output, and persists a per-(user, Faculty) memory that compounds across sessions. A Faculty is not a chat persona; it is a data artifact — Manifest + corpus + behavioral rules + evaluation suite — interpreted by a stateless Cognitive Pattern Engine, never executed as code. The platform additionally operates a two-sided marketplace: third-party authors submit Faculties that must pass a mandatory evaluation gate before listing, and a royalty ledger allocates 70% of net rental revenue to the author, settled monthly via Stripe Connect.

In-scope Phase 0 deliverable (numbered modules; names match Repository Layout §10 and Core Schema §11):

  1. packages/manifest — Manifest schema, Zod validators, TypeScript types (§11.1).
  2. packages/engine (skeleton) — Manifest loader + Ed25519 signature verifier only; no retrieval or LLM calls yet.
  3. packages/shared — cross-cutting types (FacultyId, UserId, error taxonomy).
  4. conformance/fixtures — malformed, tampered, and valid Manifest fixtures (§12.5).
  5. scripts/sign-manifest.ts — CLI signing tool (local signature issuance only, no server).
  6. CI pipeline (.github/workflows/ci.yml) running schema and signature conformance on every pull request.

System boundaries:

  • Provides: manifest-driven prompt assembly, corpus retrieval, behavioral-rule enforcement, per-user-Faculty memory, session accounting, marketplace listing and discovery, royalty allocation, multi-Faculty stacking, multi-wearer Rooms, enterprise tenant isolation.
  • Delegates: LLM inference (Anthropic / OpenAI / self-hosted), payment rails and KYC (Stripe Connect), embeddings (OpenAI text-embedding-3-large, swappable per Manifest), identity federation (WorkOS SAML/OIDC), compliance evidence collection (Vanta).
  • Does NOT provide: a general-purpose chatbot builder, proprietary foundation-model training, a persona role-play surface, native mobile clients (PhaseDeferred("§1")), voice-first interaction (PhaseDeferred("§1")).

Non-goals: competing with GPT-Store-style persona builders; entertainment/roleplay Faculties; training or fine-tuning base models; becoming a general workflow-automation product.

Deployment model: multi-tenant SaaS ("Faculty Cloud") for Phases 0–11; single-tenant / BYO-cloud (Helm chart + Terraform module) added in Phase 12 for enterprise. Extension distributed via Chrome Web Store (unlisted → public); web app on Vercel edge; backend on Fly.io (Phases 0–8), migrating region-by-region to AWS ECS Fargate (Phase 12, SOC 2 posture).

Target users/operators: wearers (founders, consultants, designers, writers, engineers); Faculty authors (individual and corporate); platform operators (on-call engineering, Trust & Safety, finance/payouts).

What later phases unlock: Phase 6 unlocks marketplace listing — nothing lists without clearing evaluation. Phase 10 unlocks cognitive ensembles (stacking). Phase 11 unlocks multi-human shared Faculty sessions. Phase 12 unlocks single-tenant enterprise deployment and the Custom Corporate Faculty pipeline.

Recommended language: TypeScript 5.x, strict mode, end-to-end (web, extension, backend, CLI, eval-suite orchestration). Rationale: one language across a solo-plus-AI-assisted team eliminates context-switch cost; structural types make Manifest-schema drift a compile error rather than a runtime surprise (ties to I3, I10, ADR-01). Rejected: Go — superior raw throughput, but forces a second type system at the Manifest/engine boundary, the one boundary that must never silently drift; Python — best ML-tooling ergonomics, retained narrowly inside packages/eval-suite for meta-judge tooling per ADR-01, never in the request path.

Prerequisites (systems knowledge required): retrieval-augmented generation architecture (Lewis et al. 2020, §5); vector-index tuning — HNSW (§5); Postgres row-level security and partitioning; Ed25519 signing and content-addressed hashing; OAuth2/OIDC/SAML federation; two-sided marketplace economics (Rochet & Tirole 2003, §5); Chrome Manifest V3 extension architecture; WebSocket-based real-time systems.

Estimated timeline: Phase 0 — 2 weeks. Full system (Phase 0 through Phase 12) — approximately 14 months.

Deferred features (full register at §38): native mobile apps PhaseDeferred("§1"); voice-first interaction PhaseDeferred("§1"); cross-browser (Firefox/Safari) extension support PhaseDeferred("§17"); passive/ambient (non-gesture) capture PhaseDeferred("§17"); dedicated external vector database extraction PhaseDeferred("§15"); Llama-3-70B on-prem inference path PhaseDeferred("§24"); SOC 2 Type II PhaseDeferred("§24"); cross-Room persistent team memory PhaseDeferred("§23").

2. Why Build This

Faculty sits at the intersection of three systems disciplines rarely exercised together in one project: retrieval-augmented generation under a hard trust boundary (an author's corpus and rules are untrusted input, never code — P1, I3); compounding per-tenant state at the database layer (memory partitioned by (user_id, faculty_id), the same primitive underlying multi-tenant SaaS isolation — I2, I8); and two-sided marketplace mechanics backed by a real money ledger (royalty allocation that must reconcile to the cent — I5, ADR-21). Few systems force an engineer to reason about signature verification, vector-index recall/latency tradeoffs, and payout-ledger idempotency in the same codebase.

Historically this is the shape of a plugin marketplace with a runtime sandbox (VS Code extensions, Figma plugins, the Chrome Web Store itself) crossed with RAG-as-a-product (the shape Notion AI, GitHub Copilot Workspace, and Glean occupy) crossed with creator-economy royalty rails (Patreon, Substack, the App Store's 70/30 split — deliberately mirrored here, ADR-21). Building it teaches: how to keep an untrusted third-party artifact from becoming a code-execution vector while still letting it drive real behavior (P1, P7); how to keep a memory store from leaking across tenants under concurrent load (I2, I8); how to make a revenue-split ledger auditable rather than "trust the dashboard" (I5, P10); how to degrade gracefully across LLM providers without breaking a signed contract (P13, ADR-07).

Cross-links to sibling systems in this portfolio: the Manifest signing/verification pipeline shares its threat model with any plugin-marketplace project (signed-artifact loaders); the Memory Layer's partition-key discipline is the same pattern as any multi-tenant database project; the Reconciler (§22) is a small-scale instance of any system that merges N independent model outputs into one coherent answer (the same shape as reconciling divergent replicas, minus the CAP-theorem stakes).

Calibration value: this is a medium-large system (13 phases, ≈14 months) whose hardest problems are not raw performance but trust-boundary discipline and financial-ledger correctness — a useful counterweight to portfolio projects obsessed purely with latency and throughput.

What Mastery Looks Like — after building this, the reader can:

  • Design a signed-artifact loading pipeline where a third party's declarative data drives runtime behavior with zero code-execution surface (§13 Phase 1, §14 Phase 2).
  • Tune a retrieval pipeline's chunking, embedding, and ANN-index parameters against a measured recall/latency budget rather than intuition (§15 Phase 3).
  • Partition a multi-tenant datastore so a partition-boundary violation is structurally impossible, not merely policy-forbidden (§15 Phase 3, §23 Phase 11).
  • Build a royalty/revenue-split ledger that reconciles deterministically against an external payment processor (§20 Phase 8).
  • Design a marketplace submission pipeline where automated evaluation, not human judgment, is the primary gate to listing (§18 Phase 6, §19 Phase 7).
  • Reconcile N independent model outputs into one coherent, disagreement-preserving summary under a latency budget (§22 Phase 10).
  • Extend a consumer SaaS into a single-tenant / BYO-cloud enterprise deployment without forking the codebase (§24 Phase 12).

  • Wearer's Browser — untrusted execution context; the extension and web app run wearer-controlled code, so no server-side trust decision may depend on client honesty (I13, P3).
  • Extension — captures a task selection only on an explicit gesture, tracks per-tab/per-domain scope, renders the streamed response (§17).
  • Faculty Web App — the canonical wearing surface for users without the extension installed; same Pattern Engine contract (§16).
  • Session Gateway — the sole TLS termination point (I13); validates session JWTs, enforces per-user rate limits, scrubs PII before any logging.
  • Cognitive Pattern Engine — the only component that assembles prompts; composes signed-Manifest rules, retrieved corpus chunks, retrieved memory chunks, and sanitized task text (§14).
  • Memory Layer — vector + structured store, partitioned at the database layer by tenant key, never by application-layer filtering alone (I2, I8, §15).
  • Room Real-Time Channel — WebSocket fan-out for multi-wearer Faculty Rooms, with a private per-participant side-channel (§23).
  • Faculty Store / Royalty Ledger / Stripe — marketplace listing, search, ratings, and the revenue-split ledger that must reconcile to Stripe Billing (§21, §20).
  • Author Tools API — the only path by which a third-party artifact enters the system; validates schema, runs the evaluation suite, signs, and queues borderline submissions for Trust & Safety review (§19).
  • LLM Providers — delegated inference, provider-abstracted for failover (ADR-07).
  • Object Storage / Postgres — durable storage for signed Manifests, corpus chunks, memory rows, session/Room state, and the royalty ledger.
  • Concurrency boundary — the Cognitive Pattern Engine is stateless per request; all cross-request state (memory, sessions) lives exclusively in Postgres, never in engine-worker process memory, which is what makes horizontal scale-out (§32) a capacity decision rather than a redesign.

6. Design Principles

  1. P1 — Manifest-as-Data, Never-as-Code. Author-submitted rules and prompts are compiled and interpreted as declarative data by the Pattern Engine; never executed as arbitrary code. Tradeoff: less expressive than a scripting sandbox. Operational implication: eliminates an entire class of RCE/exfiltration risk. Violating it: a sandbox escape becomes wearer-task-content exfiltration (T1).
  2. P2 — Task Content Never Leaves the Vault. Raw wearer task text is never persisted beyond ephemeral session scope without explicit opt-in. Tradeoff: limits cross-session raw-text recall (mitigated by summarization, §15). Violating it: a privacy breach indistinguishable from a data-broker leak.
  3. P3 — Explicit Gesture Before Capture. No ambient DOM scraping; every capture requires a discrete user action. Tradeoff: one extra interaction step. Violating it: Chrome Web Store rejection (ADR-09) and a prompt-injection surface from arbitrary page content.
  4. P4 — Signed Manifests Only. Every Manifest is Ed25519-signed by the platform key before the Engine will load it. Tradeoff: every publish requires a signing round-trip. Violating it: I1/I14 fail, tampering becomes undetectable.
  5. P5 — Partition at the Database, Not the Application. Cross-tenant isolation is enforced by DB-level partition keys, never solely by application-layer filters. Tradeoff: every query must carry its partition key explicitly. Violating it: I2/I8 fail — a single missed WHERE clause leaks memory across tenants.
  6. P6 — Evaluation Gates Before Marketplace, Not After. A Faculty cannot list publicly until it clears its evaluation floor. Tradeoff: slows author time-to-list. Violating it: the marketplace fills with low-fidelity Faculties (R-08-class risk).
  7. P7 — Behavioral Rules Compile to Guards, Not Prompts Alone. Rules produce pre-flight prompt augmentation and post-flight validators, with exactly one automatic retry on violation (I7, Madaan et al. 2023). Tradeoff: doubles worst-case latency on a violation. Violating it: silent behavioral drift the wearer cannot detect.
  8. P8 — Idempotent, Replayable Session Accounting. Every wearing-second increment and royalty-allocation event is idempotent and replayable from an append-only session-event log. Tradeoff: extra storage for the event log. Violating it: reconciliation double-counts or under-counts revenue (I5).
  9. P9 — Backward-Compatible Schema Evolution. Manifest/Memory/Session schemas are semver; the runtime supports the current and previous major version simultaneously for ≥ 6 months. Tradeoff: dual-path read code during the overlap window. Violating it: a schema bump breaks every in-flight wearer session (§28).
  10. P10 — Royalty Arithmetic Lives in One Service. Allocation logic is centralized in the Royalty Ledger service; no other service computes revenue splits. Tradeoff: every consumer of "how much does an author earn" makes a network call. Violating it: the author dashboard and the actual Stripe transfer drift apart (I5).
  11. P11 — Memory Is Portable, Not a Moat. Export and delete are first-class, documented, and complete within a bounded SLA (24 h propagation). Tradeoff: no data-lock-in retention lever. Violating it: the compounding-value story becomes coercive rather than earned (Principle 7 of the original product charter).
  12. P12 — Every External Claim Is Framed as Inspiration, Not Fact. Output attributing views to a named human is transformed at the post-processing layer into "inspired-by" framing, non-overridable by author rules. Tradeoff: a small, constant post-processing cost on every response. Violating it: defamation exposure (I12, R-04-class risk).
  13. P13 — Degrade Gracefully Across LLM Providers. The orchestrator's provider abstraction allows hot failover without a user-visible Manifest change. Tradeoff: must certify behavior against ≥ 2 providers per Faculty. Violating it: a single provider's rate-limit or pricing change halts the product (ADR-07).
  14. P14 — Human Review Is a Backstop, Not the Primary Gate. Automated evaluation and corpus fingerprint scanning are the primary marketplace gate; the human review queue handles only flagged borderline cases within an SLA. Tradeoff: some false negatives reach a human late. Violating it: the review queue becomes an unscalable bottleneck at marketplace scale (§21).

8. Domain Model

8.1 Faculty Manifest — Canonical Envelope

The Manifest is the JSON realization of the type in §11.1, stored at manifests/{faculty_id}/{version}.json in object storage, Ed25519-signed by the platform key (ADR-05). Required fields are normative; unknown top-level fields are rejected — no silent forward compatibility on the envelope itself (ADR-19), so a materially new capability always forces a conscious major-version bump.

8.3 Memory Model

Per-(user_id, faculty_id) (or (room_id, faculty_id), §23) rows of kind interaction | summary | anchor | preference (full type at §11.2). Interactions are retained verbatim only with opt-in; otherwise summarized within 24 hours (P2). Anchors are explicit, user-editable "remember this" facts. Retrieval scores memory chunks by salience × recency × cosine (§15).

8.4 Session and Room Model

A Session (§11.3) accumulates wearingSeconds — the raw input to the HW/WAU north-star metric — and carries facultyIds: FacultyId[], where length > 1 marks a stacked session (§22). A Room (§23, §11.4) is a Session variant scoped to (room_id, faculty_id) with a separate real-time transcript.

8.5 Worked Example — Wearing Munger Around a Fundraising Paragraph

  1. Wearer highlights a paragraph in Google Docs, hits Ctrl-J (P3). Extension sends {selection, domain: "docs.google.com"} to the Session Gateway over TLS (I13).
  2. Engine loads manifests/munger-multidisciplinary/1.4.0.json, verifies its Ed25519 signature (I1) and content hash (I14).
  3. Retrieval fetches top-5 corpus chunks (corpus_chunk_id: mnc-0042, mnc-0117, …) via pgvector cosine search (§15) plus top-3 memory chunks tagged with this wearer's prior "fundraising" anchor.
  4. Prompt Assembler composes: behaviour.systemPrompt + structured rules (must_invert, must_cite) + the 5 corpus chunks + the 3 memory chunks + the sanitized selection.
  5. LLM Orchestrator streams from Claude Sonnet (Manifest's llm.preferred); Behavioural Rule Enforcer checks the response for a citation anchor and an inversion — both present, no retry needed (I7).
  6. Post-processing filter confirms the response is framed as "the Munger-inspired pattern suggests…", never "Munger says…" (I12).
  7. Response streams to the side panel; wearer clicks "remember this about me" — a new anchor memory row is written, partitioned to (user_id="u_9a1", faculty_id="munger-multidisciplinary") (I2).
  8. Session's wearingSeconds accumulator increments; on session end, revenue for this wearing-second range is queued for royalty allocation (§20).

8.6 Malformed-Input Example

Submission payload includes an undeclared top-level field "authorNotes": "draft v2" and omits provenance.rightsBasis. The Manifest schema validator (Zod, §11.1) rejects the submission with MANIFEST_UNKNOWN_FIELD: authorNotes and MANIFEST_MISSING_REQUIRED: provenance.rightsBasis, both surfaced verbatim in the Author Tools CLI (faculty validate) before any network call — the submission never reaches evaluation (I3, ADR-19).

8.7 Failure-Path Example

An attacker rewrites the corpus pointer inside a previously-signed Manifest stored in object storage (bypassing the signing service). On next cold load, the Engine recomputes the content hash, finds it does not match the embedded signed hash, and refuses to load (I1, I14). The wearer sees "Faculty temporarily unavailable" with an incident id; manifest_hash_mismatch_total increments; if the same Faculty id triggers twice within 10 minutes, on-call is paged and the Faculty is auto-unlisted pending investigation (§25, §26 FM-2).

8.8 Continuity Note

The Munger Multidisciplinary, Feynman First-Principles, and Jobs Product-Critique Faculties referenced throughout this document are the three founder-curated Faculties shipped in §12 Phase 0; their corpora are public-domain or original analyses only, per the provenance policy at T5 (§25) and the rightsBasis field (§11.1).

12. Phase 0 — Repository Skeleton & Manifest Correctness Kernel

12.1 Objectives

Stand up the pnpm + Turborepo monorepo (ADR-14); implement the Manifest schema and Zod validators (packages/manifest, §11.1); implement the Ed25519 signing CLI and loader/verifier (ADR-05); establish the CI gate. No retrieval, no LLM calls, no server — this phase is the correctness kernel only.

12.2 Detailed Implementation Steps

  • packages/manifest: a Zod schema mirroring §11.1, every nested object declared .strict() so unknown fields are rejected at every level, not just the envelope (ADR-19, I3).
  • scripts/sign-manifest.ts: loads an Ed25519 keypair from env (RFC 8032, ADR-05), computes a canonical (key-sorted) JSON hash, signs it, and embeds {hash, signature, keyId} in the envelope (I14).
  • packages/engine (skeleton): loadFacultyManifest(path) re-derives the hash, verifies it against the embedded value, then verifies the signature before returning a typed object — reject-closed on any mismatch (I1, P4).
  • CI (ci.yml) runs pnpm typecheck && pnpm test; conformance.yml runs the invariant-sim subset covering I1/I3/I14 only — the full simulator arrives in §14.
  • This phase is also where canonical names (FacultyId, Manifest, Engine, Wearer, Author) are fixed and used identically in every later phase (§5.5-style terminology lock).
  • A JSON-canonicalization helper (key-sorted, whitespace-normalized) is shared between sign-manifest.ts and loadFacultyManifest so signing and verification can never drift on serialization order (P4).

12.3 Deliverable

A CLI (pnpm faculty sign <path>) that signs a draft Manifest JSON file, and a loader that verifies and rejects tampered or unsigned files — runnable entirely offline against the fixtures below.

12.4 Acceptance Criteria

pnpm test green with ≥ 90% line coverage on packages/manifest; loadFacultyManifest rejects manifest-tampered-hash.json and manifest-unsigned.json with MANIFEST_SIGNATURE_INVALID; accepts manifest-valid-v1.json; CI pipeline completes in < 4 minutes.

12.5 Conformance Fixtures

Fixture Purpose Expected Output
manifest-valid-v1.json well-formed, signed Munger v0.1 draft loads, returns typed object
manifest-tampered-hash.json valid signature over a different hash MANIFEST_HASH_MISMATCH (I14)
manifest-unsigned.json no signature field MANIFEST_SIGNATURE_INVALID (I1)
manifest-unknown-field.json includes stray authorNotes MANIFEST_UNKNOWN_FIELD (ADR-19)
manifest-missing-required.json omits provenance.rightsBasis MANIFEST_MISSING_REQUIRED

12.6 Pitfalls

  1. Non-deterministic JSON key ordering before hashing silently breaks every signature — fixed with canonical key-sorted serialization, caught by a fixture that re-serializes and re-hashes.
  2. A nested schema that forgets .strict() reopens the closed-schema guarantee (ADR-19) for just that subtree.
  3. Treating "valid JSON" as "valid Manifest" — schema validation must gate before any business logic touches the object.
  4. A signing key committed to source control by accident — CI runs a secret-scan step from Phase 0 onward.

12.7 Performance Concerns

Signature verification is O(1) per load (≈2–3 ms Ed25519 verify); JSON parse cost dominates for large manifests. The < 5 ms p99 signature budget (§4) leaves comfortable headroom even at 100 KB manifest size.

12.8 Edge Cases

  • Empty corpus.sources array.
  • A version string that is not valid semver.
  • Duplicate id across two draft manifests.
  • A manifest at the JSON size ceiling.
  • Concurrent sign invocations on the same file (documented last-write-wins CLI limitation, not yet a service concern).

12.9 Failure Analysis

  • A corrupted signing key produces a hard CLI failure with a non-zero exit code — never a silently-accepted unsigned manifest.
  • Blast radius is limited to local development since nothing is deployed yet.
  • Recovery is regenerating the keypair and re-signing the fixture set.

12.10 Operational Notes

  • No production deployment in this phase; CI green is the only health signal.
  • The public verification key is checked into packages/engine from day one so every later phase inherits the same trust root (the key later becomes pluggable under BYOK, §24).
  • The secret-scan CI step (§12.6) is the one operational control that already matters pre-deployment — a leaked key here would compromise every Faculty signed with it in every later phase.

13. Phase 1 — Manifest Signing & Loader Service

13.1 Objectives

Promote signing/verification from a local CLI (§12) into a hosted service backed by object storage (Cloudflare R2, ADR-04); support key rotation; re-issue the three founder-curated Faculties (Munger Multidisciplinary, Feynman First-Principles, Jobs Product-Critique) as hosted, signed v1.0.0 Manifests.

13.2 Detailed Implementation Steps

  • apps/api (tRPC, ADR-02) exposes manifest.load(facultyId, version?).
  • An R2 storage adapter (packages/manifest/src/storage.ts, ADR-04) fetches signed envelopes from manifests/{id}/{version}.json.
  • A signing_keys table (keyId, activatedAt, retiredAt) supports rotation; the loader checks the envelope's keyId against the active-or-retired key set — retired-but-not-revoked keys still verify (I1, I14, P4).
  • An in-memory LRU cache (5-minute TTL) sits in front of the loader to hit the cold-load budget only on a genuine miss (§4).
  • Corpus for the three founder Faculties is uploaded to R2 under corpus/{id}/{chunkId}.json.
  • scripts/rotate-signing-key.ts automates the rotation drill: mint a new key, mark the prior key retiredAt, re-sign no existing Manifests (retired keys remain verify-only), and confirm all 3 hosted Faculties still load.

13.3 Deliverable

engine.loadFaculty("munger-multidisciplinary") over the network returns a verified Manifest from R2; a rotated signing key can retire without breaking Manifests signed under the prior key.

13.4 Acceptance Criteria

Cold load < 400 ms p95 (§4) over 200 requests, measured against benchmarks/latency/manifest-cold-load.md; cached load < 5 ms p99; the key-rotation drill (scripts/rotate-signing-key.ts) completes with zero manifest-load failures across all 3 hosted Faculties; 100% of the §12.5 fixture set still passes against the hosted loader.

13.5 Conformance Fixtures

Fixture Purpose Expected Output
manifest-rotated-key-valid.json signed under a retired-but-not-revoked key loads, keyId: legacy telemetry tag
manifest-revoked-key.json signed under a fully revoked key MANIFEST_SIGNATURE_INVALID
manifest-cache-stale.json replay past the 5-minute TTL re-fetch from storage, not stale cache serve

13.6 Pitfalls

  1. A manifest cached before a key revocation can stay "valid" until TTL expiry — mitigated by an explicit cache-bust on revocation, not TTL alone.
  2. R2's eventual-consistency window on first write is mitigated by read-after-write from the signing service's own region.
  3. Forgetting to propagate keyId silently breaks the backward-compatibility contract (P9).
  4. A key-rotation drill run only against the primary region misses replica-lag exposure in a secondary region — the drill fixture (§13.5) is run against every configured region.
  5. Running the key-rotation drill (§13.2) only against a GitHub-hosted CI runner's IAM assumption path (ADR-27) can mask a region-specific credential misconfiguration that only manifests against production IAM roles — the drill's staging run assumes the same IAM role as production, never a CI-only service account with broader implicit trust.

13.7 Performance Concerns

LRU cache hit rate target ≥ 95% in steady state (Faculties change rarely). R2 egress is free (ADR-04), but request-count billing means the cache also controls cost, not only latency.

13.8 Edge Cases

  • Two versions of the same Faculty requested concurrently by different wearers — both must resolve to the correct version, no cross-version bleed.
  • A corrupt object-storage read (partial body) must fail closed, never partially parse.
  • Clock skew between the signing service and the loader on rotation timestamps.
  • A retired key revoked mid-request — the in-flight verification completes against the key state captured at request start, never a torn read.
  • A GitHub Actions runner restarting mid-rotation-drill (ADR-27) must not leave signing_keys.retiredAt partially committed — the rotation script wraps the key-state transition in a single transaction, never a multi-step unguarded sequence.

13.9 Failure Analysis

  • Object storage outage: the loader falls back to the LRU cache for already-cached Faculties and fails closed (503) for uncached ones — never stale-serve-forever.
  • Blast radius is read-only.
  • Recovery is R2 region failover, monitored via manifest_load_error_rate.
  • A rotation-drill failure surfaces only as a non-zero CI exit code, never a silently retried job — scripts/rotate-signing-key.ts mirrors the Phase 0 signing CLI's fail-closed discipline (§12.9).

13.10 Operational Notes

  • Dashboard panel "Manifest Load Health" tracks p50/p95/p99, cache hit rate, and signature-fail rate.
  • Runbook: docs/runbooks/manifest-load-degraded.md.
  • Key rotation is a documented quarterly operator procedure, never ad hoc.

14. Phase 2 — Cognitive Pattern Engine

14.1 Objectives

Implement the full request path: retrieval over corpus and memory, prompt assembly, behavioral-rule enforcement with a single retry, and LLM orchestration with provider failover (ADR-07). This is the phase where P1 (Manifest-as-data) becomes load-bearing: rules compile to a runtime guard, never an executed script.

14.2 Detailed Implementation Steps

  • packages/engine/src/retrieval.ts — top-k cosine query over corpus_chunks via pgvector (default k=5, HNSW index per ADR-06, Malkov & Yashunin 2018); embeddings precomputed at publish time with text-embedding-3-large (ADR-17).
  • packages/pattern-rules/src/compiler.ts compiles BehaviouralRule[] into a pre-flight prompt-augmentation reference and a post-flight validator set (P7; Madaan et al. 2023 self-refine pattern) — never an eval'd string (P1).
  • packages/engine/src/assembler.ts composes systemPrompt + rules + corpus chunks + memory chunks + sanitized input in one fixed, documented order (Lewis et al. 2020 RAG shape, ADR-08).
  • packages/engine/src/orchestrator.ts wraps the Anthropic and OpenAI SDKs behind one interface; on a provider error it retries once against the configured fallback within the same request (ADR-07, P13).
  • The post-processing framing filter (packages/pattern-rules/src/framing.ts) rewrites first-person impersonation phrasing before the response leaves the Engine (I12, P12) — non-overridable by Manifest content.
  • A per-stage cost ledger entry (retrieval tokens, assembly tokens, generation tokens) is written on every call, the concrete mechanism behind the LangChain-lesson cost-tracking practice cited in §14.7.

14.3 Deliverable

An end-to-end call engine.wear({facultyId, userId, input}) returning a streamed, rule-conformant, "inspired-by"-framed response citing at least one corpus chunk, exercised against the Munger fixture Faculty.

14.4 Acceptance Criteria

Round-trip latency < 1.2 s p95 / < 2.5 s p99 (§4) over 200 calls (benchmarks/latency/wearing-latency.md); the smoke fixture wear-munger-deal-review.json must never contain the string "As Charlie Munger" across 100 replayed samples (I12); behavioral-rule violation retry rate < 8% on the Phase-0 content evaluation corpus; retrieval precision@5 ≥ 0.8 on the 30-item Munger pattern-fidelity benchmark (ties to §18).

14.5 Conformance Fixtures

Fixture Purpose Expected Output
wear-munger-deal-review.json happy path an inversion + a corpus citation
wear-rule-violation-retry.json crafted input triggering one violation exactly one retry, then compliant response (I7)
wear-provider-failover.json primary provider forced to error GPT-4o fallback response within budget (ADR-07)
wear-impersonation-attempt.json "pretend to be Munger" refusal framed per RefusalPolicy

14.6 Pitfalls

  1. Retrieval returning semantically-similar but citation-poor chunks — mitigated by chunking-strategy tuning (ADR-22).
  2. The single-retry rule (I7) silently doubling p99 latency under adversarial input — dashboarded explicitly, never averaged away.
  3. Provider failover changing output style enough to drop the evaluation score — both providers must independently clear minScore (§18).
  4. Prompt injection via the corpus itself if an author's source text is adversarial — corpus chunks are escaped/quoted, never concatenated as instructions (mirrors P3's untrusted-page-content principle).
  5. A behavioral-rule validator that only checks the final token buffer misses a violation that appears mid-stream and self-corrects — the validator runs against the complete assembled response, not a partial stream snapshot.
  6. A provider failover (ADR-07) landing mid-retry-cycle (I7) could double the effective retry budget if the retry counter were scoped per-provider-call rather than per-request — the counter is request-scoped, decremented once regardless of how many provider calls occur underneath it (§36 Q6).

14.7 Performance Concerns

Retrieval is cache-unfriendly per call (memory chunks vary per user); token cost is logged per stage — retrieval, assembly, generation — per the LangChain reference-implementation lesson (§5); streaming backpressure is bounded internally, never an unbounded queue, if the side panel can't keep up with ≥ 30 tokens/s (§4).

14.8 Edge Cases

  • Empty corpus (zero chunks retrieved) — the Engine still assembles a valid prompt from system rules alone, never errors.
  • Memory retrieval returning stale pre-migration rows (P9 lazy-migration path).
  • Both providers failing simultaneously surfaces a user-visible "Faculty temporarily unavailable," never a silent hang.
  • An assembled prompt exceeding contextWindowMin is a hard validation error, never a silent truncation.
  • A Manifest requesting a cognitive primitive absent from its own behaviour.rules set (declared but unenforced) is rejected at load time, not silently accepted.
  • A request whose provider failover and its single rule-violation retry (I7) both fire in the same call must still complete within budget — the retry counter and the failover retry are independent, never compounded into an unbounded retry chain.

14.9 Failure Analysis

  • A stuck retry loop would be an I7 breach — the invariant simulator (§7) specifically fuzzes malformed rule sets to confirm the cap holds.
  • Blast radius of a rule-enforcer bug is a single session (no cross-session state).
  • The forensic artifact is the full assembled-prompt log (sanitized, no raw task text per P2), retained 72 hours for debugging only.
  • The forensic artifact set also includes the provider-selection decision (which provider served the response), so a quality regression can be attributed to a specific provider rather than assumed uniform across the router (ADR-07).

14.10 Operational Notes

  • Metrics: pattern_engine_latency_ms{stage}, rule_violation_retry_total, provider_failover_total.
  • Tracing spans per stage (retrieval/assembly/generation/framing) via OpenTelemetry (ADR-16).
  • Rollback path is a Manifest version pin (P9) if a new Faculty version regresses its evaluation score.

15. Phase 3 — Memory Layer

15.1 Objectives

Implement the partitioned Memory Layer (§11.2): anchors, summaries, preferences, interactions; export/delete flows (P11); retrieval scoring by salience × recency × cosine.

15.2 Detailed Implementation Steps

  • Postgres schema memory_entries with a composite partition key (user_id, faculty_id) enforced by row-level security (I2; Kleppmann 2017 ch. 6 partitioning).
  • A Claude Haiku summarizer job runs after every session with ≥ 3 turns, writing a summary row with a computed salience score.
  • The Anchors UI writes a flags.userPinned=true row directly from a wearer gesture.
  • packages/memory/src/retrieve.ts scores candidates by salience × recency_decay × cosine_similarity and returns top-m (default m=3).
  • The export endpoint GET /me/memory/{facultyId} streams all rows as JSON.
  • The delete endpoint marks rows redacted=true immediately and physically purges within 24 h (P11).
  • A background compaction job merges low-salience interaction rows older than 30 days into their session's summary row, keeping the per-Faculty row count (§4, item 1) growing sub-linearly with raw interaction count.

15.3 Deliverable

Wearing Munger on Monday with "I'm fundraising," then again Friday with no preamble, surfaces the fundraising context organically — verified by the memory-continuity fixture.

15.4 Acceptance Criteria

Memory retrieval < 80 ms p95 (§4) over 200 queries at 50k rows/Faculty; export completes < 2 s for a 10k-row account; delete propagates to the vector index within the 24 h SLA (memory-delete-propagation.json); zero cross-partition reads across 10,000 fuzzed query attempts (conformance/invariant-sim, I2/I8).

15.5 Conformance Fixtures

Fixture Purpose Expected Output
memory-continuity.json two-session replay Friday response references Monday's anchor
memory-cross-tenant-probe.json crafted cross-tenant read attempt PARTITION_VIOLATION (I2)
memory-delete-propagation.json delete then poll at T+24h zero remaining rows
memory-schema-migration.json v1-schema row read under v2 runtime lazy migration succeeds (P9)

15.6 Pitfalls

  1. Recency decay tuned wrong makes an old-but-pinned anchor disappear — salience must dominate for userPinned=true rows regardless of age.
  2. A summarizer that runs on every single-turn session floods memory with low-value rows — gated at ≥ 3 turns.
  3. An RLS policy silently dropped by a migration that recreates the table — CI asserts RLS presence, not just functional behavior.
  4. A retrieval query that forgets to filter redacted=false can surface a row mid-deletion — the query builder applies this filter unconditionally, never per-callsite.
  5. A compaction job (§15.2) merging interaction rows into a summary row without re-checking redacted status can resurrect content a wearer already deleted — compaction runs strictly after the 24h delete-propagation window, never concurrently with an in-flight delete (P11, I2).

15.7 Performance Concerns

HNSW index build cost scales with row count per Faculty (ADR-06); the 2M-row-per-Faculty ceiling (§4) is the ADR-03 migration trigger, monitored via the memory_rows_per_faculty gauge. The summarizer job queue (BullMQ) is bounded and priority-ordered so interactive retrieval never queues behind background summarization.

15.8 Edge Cases

  • A wearer deletes memory mid-session — in-flight retrieval must not silently use rows already marked for deletion.
  • Two devices writing anchors for the same (user_id, faculty_id) concurrently — last-write-wins with a logged conflict, never silent data loss.
  • A Faculty version bump changing embeddingModel — old rows keep their original dimensionality and are re-embedded lazily, never dimension-mismatched at query time.
  • A wearer's export request racing an in-progress delete — export reflects a consistent snapshot taken at request time, never a partially-deleted view.
  • A compaction job racing an export request could produce an export reflecting a partially-compacted state — export takes its consistent snapshot before compaction begins, the same discipline already applied to export-vs-delete races (above).

15.9 Failure Analysis

  • A partition-key bug is the single worst-case failure in this system (I2/I8).
  • Detection is the fuzzed invariant simulator plus a quarterly external red-team pass (Gilman & Barth 2017, §5).
  • Blast radius if it slipped to production would be cross-user memory leakage, requiring mandatory wearer notification.
  • Recovery is immediate query-path lockdown plus a forensic row-level audit of the affected partitions.
  • A compaction bug that merges rows across the wrong partition boundary is treated with the same severity as a direct partition-key bug (I2/I8), since compaction operates on the same physical rows the RLS policy protects.

15.10 Operational Notes

  • Metrics: memory_retrieval_latency_ms, memory_rows_per_faculty, rls_denial_total (I2).
  • Runbook: docs/runbooks/memory-partition-incident.md.
  • Export/delete SLAs are surfaced on a public trust page (§27).

eval-latency-cost-budget.json reference-hardware run meets §4 budgets

18.6 Pitfalls

  1. A miscalibrated meta-LLM judge silently rubber-stamps a weak Faculty — mitigated by the 10% human spot-check and periodic judge-vs-human agreement audits (Zheng et al. 2023).
  2. Authors can game a public fixed prompt bank — the marketplace-facing subset is smaller than the full server-side suite, with held-out prompts never disclosed.
  3. An evaluation score can drift across minor Manifest bumps if a re-run is not triggered on every publish.
  4. A judge model itself upgraded mid-quarter (provider-side) can silently shift every Faculty's score baseline — the judge model identity is pinned per suite version (EvaluationResult.judgeModel, §11.4) and only rotated with an explicit suite-version bump.

18.7 Performance Concerns

The full suite is LLM-call-heavy (≈150 calls per Faculty); batched, rate-limited parallel execution keeps CI runtime bounded. Judge-model cost is tracked per run and rolled into the platform's own unit economics (ties to R-11-class risk, §26).

18.8 Edge Cases

  • A Faculty declaring zero cognitive primitives is rejected at the schema level before evaluation even runs (ADR-19).
  • A domain benchmark below the 50-item floor blocks submission.
  • A judge-model outage mid-run fails the suite closed and re-queues, never partially scores.
  • Resubmitting an unchanged Manifest reuses the cached result unless the content hash changed (I14-adjacent).
  • A Faculty passing pattern-fidelity but failing anti-impersonation is blocked overall — no partial-pass listing state exists (I4 is all-or-nothing per Faculty version).
  • A duplicate-corpus fingerprint flag (ADR-31, T15) raised during an in-progress evaluation run pauses evaluation the same way a takedown report does (§21.8), never letting evaluation complete and list a Faculty already flagged for review.

18.9 Failure Analysis

A false-positive pass (a genuinely weak Faculty clears evaluation) surfaces downstream via refund-rate and re-wear-rate signals (R-08-class risk, §26). Blast radius is reputational and financial — royalty paid on a low-quality listing. Recovery is a re-evaluation trigger plus retroactive listing suspension if the gap is confirmed.

18.10 Operational Notes

Metrics: eval_suite_runtime_seconds, eval_score_by_faculty, judge_human_agreement_rate. Runbook: docs/runbooks/eval-suite-degraded.md. The suite's own version (EvaluationSuiteRef) is tracked so a stricter suite upgrade never silently re-scores every existing Faculty without notice.

20. Phase 8 — Royalty Ledger & Stripe Connect Payouts

20.1 Objectives

Implement the Royalty Ledger service (P10) computing the 70/30 author/platform split; onboard authors via Stripe Connect; run the first automated monthly payout.

20.2 Detailed Implementation Steps

  • packages/payouts implements Stripe Connect Express onboarding (KYC, W-9/W-8BEN collection).
  • A nightly aggregation job writes RoyaltyLedgerEntry (§11.4) rows summing wearing-second-weighted revenue per Faculty per period.
  • The reconciliation job (I5) diffs the ledger's period total against the corresponding Stripe Billing statement, halting the payout run if the delta exceeds $0.01/Faculty.
  • The payout run creates Stripe Transfers to each author's connected account on the 5th of the following month, rolling over balances under the $25 minimum threshold.
  • The author dashboard (apps/studio) surfaces earnings, anonymized wearer counts (P2, §21), and a refund/chargeback view.
  • Every RoyaltyLedgerEntry is append-only and references its predecessor by id for the same (facultyId, periodStart), so a correction is a new row with an audit trail, never an in-place update (P8, P10).

20.3 Deliverable

A full monthly cycle — wearer pays → revenue allocated per Faculty → 70/30 split computed → Stripe Transfer executed → 1099-NEC accrual recorded — run end-to-end against the 3 founder Faculties (author-of-record is the platform corp entity until third-party authors onboard, §19).

20.4 Acceptance Criteria

Reconciliation delta ≤ $0.01 per Faculty per period (I5) across 3 consecutive monthly runs; payout run completes within a 4-hour window on the 5th; zero double-paid or double-skipped Faculties across a chaos-injected mid-run restart; chargeback netting reduces the correct author's next-cycle payout by exactly the chargeback amount.

20.5 Conformance Fixtures

Fixture Purpose Expected Output

royalty-reconciliation-mismatch.json deliberately-skewed ledger payout run halts, finance paged
royalty-payout-restart.json mid-run process kill idempotent resume (P8)
royalty-chargeback-netting.json a chargeback event correct next-cycle deduction

20.6 Pitfalls

  1. Floating-point money arithmetic anywhere in the pipeline — mitigated by integer-cents columns throughout (§11.4).
  2. A non-idempotent payout run double-pays an author on a mid-run crash — every Transfer is keyed by a deterministic idempotency key {facultyId}-{periodStart} (P8).
  3. Stacked-session royalty attribution (ADR-21) computed inconsistently between the dashboard estimate and the ledger's final figure — both must call the same allocation function, never two implementations.
  4. A timezone-naive period boundary (e.g., "the 1st of the month" in local time) causing a wearing-second to be attributed to the wrong period at a UTC-offset edge — all period boundaries are UTC, never local time (I10-style discipline).
  5. Choosing a Redis-backed idempotency key (rejected in ADR-25) would have introduced a second source of truth for a money-critical guarantee — the Postgres unique constraint on (facultyId, periodStart) keeps idempotency and the ledger's durability in the same transactional boundary.

20.7 Performance Concerns

The nightly aggregation job scales linearly with wearing-second event volume; at marketplace scale it is sharded by Faculty-id range to stay within its overnight batch window. Stripe API rate limits bound payout-run parallelism (batched Transfer creation, exponential backoff on 429s).

20.8 Edge Cases

  • An author whose Stripe Connect account is de-activated mid-period — balance held, no Transfer attempted until re-activated.
  • A Faculty deprecated mid-period — royalty continues accruing through the 90-day access window (I9).
  • A refund issued after payout already ran — netted against the next cycle, never clawed back beyond the chargeback amount.
  • An author in a jurisdiction with unsupported Stripe Connect payouts — flagged at onboarding, before any revenue accrues; multi-currency support is PhaseDeferred("§20").
  • Two Faculties owned by the same author reconciling in the same period — each RoyaltyLedgerEntry row is independent; a delta on one never blocks the other's payout unless the halt-the-whole-run policy (§20.9) is triggered.
  • A payout run retried after a partial failure reuses the exact same idempotency key derived per ADR-25, never minting a fresh one per retry attempt, or the unique-constraint guarantee stops preventing double-pay.

20.9 Failure Analysis

A reconciliation mismatch halts the entire payout run, not just the affected Faculty — conservative by design, since a systemic bug is more likely than an isolated one at this stage. Blast radius of a halted run is a delayed payout (communicated to authors), never a wrong one. The forensic artifact is the full aggregation-job input snapshot for the affected period. A bug generating a non-deterministic idempotency key would silently reopen the double-pay risk ADR-25 was chosen to close — the key-derivation function is a pure function of (facultyId, periodStart) alone, covered by a dedicated unit test asserting determinism across repeated calls.

20.10 Operational Notes

Metrics: royalty_reconciliation_delta_cents, payout_run_duration_seconds, payout_halted_total. Runbook: docs/runbooks/royalty-reconciliation-halt.md. A finance on-call rotation begins in this phase — the first non-engineering operational responsibility in the system.

The forensic artifact is the full takedown-queue timeline with every state transition timestamped.

22. Phase 10 — Stacking & the Reconciler (Cognitive Ensembles)

22.1 Objectives

Implement multi-Faculty stacking (N ≤ 4, I11): parallel behavioral-rule execution plus a Reconciler that surfaces agreement and disagreement rather than flattening it; pro-rata royalty attribution for stacked sessions (ADR-21).

22.2 Detailed Implementation Steps

  • packages/reconciler constructs and validates StackManifest (§11.4) against I11.
  • The Cognitive Pattern Engine (§14) runs each stacked Faculty's prompt-assembly and rule-enforcement pipeline in parallel, each fully isolated with no shared mutable state.
  • A platform-controlled Reconciler prompt — never author-controlled, mirroring P1's data-not-code boundary — synthesizes the N independent responses into agreements, disagreements, and unresolved tensions, never silently picking one Faculty's view.
  • Memory writes are tagged with the stack composition so a future single-Faculty session can optionally retrieve cross-Faculty stack memory via an opt-in UI toggle.
  • Royalty for a stacked session apportions revenue pro-rata by each Faculty's active wearing-time within the stack (ADR-21), computed by the same allocation function used in §20 (P10).
  • Each stacked Faculty's rule-enforcement runs against its own isolated context object (no shared references), the same discipline the invariant simulator (§7) already fuzzes for partition boundaries, extended here to in-memory compute isolation.

22.3 Deliverable

Wearing Munger and Feynman together on a deal review yields a Reconciler summary naming where they agree, where they diverge, and what remains unresolved — not a single blended voice.

22.4 Acceptance Criteria

2-Faculty stack latency < 1.6 s p95, 4-Faculty stack latency < 2.4 s p95 (§4); the 50-item stacked-session evaluation benchmark shows disagreements surfaced, not flattened, in ≥ 90% of cases with a genuine ground-truth disagreement; royalty pro-rata allocation reconciles to the cent against a synthetic 3-Faculty session; stacking adoption instrumented against a ≥ 30% of paid sessions operational target.

22.6 Pitfalls

  1. A Reconciler that defaults to averaging or picking the "loudest" Faculty's answer defeats the feature's purpose — the §22.4 benchmark exists specifically to catch this regression.
  2. Parallel rule-execution sharing an accidental mutable cache key across stacked Faculties breaks isolation — the same discipline as I2/I8 applied to compute, not just storage.
  3. Royalty pro-rata can drift from the dashboard's live estimate unless per-Faculty-within-stack wearing time is tracked at the same granularity as the ledger's final computation (P10).
  4. A Reconciler prompt tuned against 2-Faculty stacks that degrades in quality at N=4 — the evaluation benchmark (§22.4) is run at every stack size the product allows, never validated at N=2 alone.
  5. A Reconciler pass silently inheriting the per-author submission rate limit (ADR-23) would incorrectly throttle a wearer's stacked session — ADR-23's token bucket scopes to author-submission traffic only, never to wearing-time request paths, enforced by routing rate-limit checks through separate middleware for the two traffic classes.

22.7 Performance Concerns

An N=4 fan-out multiplies LLM-call cost and provider rate-limit pressure fourfold for that session — tracked distinctly from single-Faculty session cost. The Reconciler pass itself is one additional LLM call, budgeted separately within the 1.6s/2.4s figures above.

22.8 Edge Cases

  • A wearer attempting a 5th Faculty on an existing 4-stack is blocked at the UI and the constructor (I11).
  • One Faculty erroring while others succeed — the Reconciler synthesizes from the N-1 successful responses with an explicit note on the failure, never blocking the whole stack.
  • Two Faculties sharing overlapping corpus content must be attributed to both, not double-counted as trivial "agreement."
  • A stack where all N Faculties agree completely still states the agreement explicitly, never silently collapsing into a single-voice-looking response.
  • The same Faculty added twice to one stack request is rejected at the constructor — StackManifest.facultyIds must be a set of distinct ids.
  • A stacked session where one Faculty's provider failover (ADR-07) fires mid-Reconciler-pass must not let the Reconciler wait on a response from a Faculty that ultimately never returns — the Reconciler's per-Faculty timeout is bounded independently of any single provider's retry/failover budget.

22.9 Failure Analysis

A Reconciler that silently flattens disagreement is a content-quality failure invisible to standard error monitoring — detection is exclusively the stacked-session evaluation benchmark (§22.4), re-run on every Reconciler-prompt change. Blast radius is product-trust erosion, not a technical outage. Recovery is a Reconciler-prompt rollback plus a re-run of the benchmark before re-deploying.

22.10 Operational Notes

Metrics: stack_size_distribution, reconciler_latency_ms, stack_disagreement_surfaced_rate. Runbook: docs/runbooks/reconciler-quality-regression.md. Stacking adoption is reported alongside HW/WAU in the monthly KPI review.

23. Phase 11 — Faculty Rooms (Multi-Wearer Shared Sessions)

23.1 Objectives

Implement multi-human shared Faculty sessions: real-time WebSocket transcript, a room-level memory partition, E2EE transcript storage at rest, and a per-participant private side-channel.

23.2 Detailed Implementation Steps

  • Room (§11.3) extends Session with roomId, ownerId, participantIds (≤ 200, §4), transcriptCipherRef.
  • A WebSocket fan-out server (ADR-11) broadcasts the shared transcript to all connected participants while routing each participant's private prompts through an isolated side-channel.
  • Room-level memory writes to a separate partition (room_id, faculty_id) (I8) — never merged with a participant's personal memory unless explicitly opted in via the §22 cross-stack-memory toggle, itself default-off.
  • Transcripts are end-to-end encrypted at rest; ciphertext is stored server-side and decrypted only in-session, under a room-owner-controlled invite model.
  • A replay UX lets a late-joining participant scrub through prior turns via the same ciphertext-backed transcript.
  • Presence tracking (join/leave/heartbeat events) is deduplicated server-side by (roomId, userId), the mechanism behind the edge case in §23.8 where a flaky connection reconnects repeatedly without inflating the participant count.

23.3 Deliverable

A 5-person Room wearing Feynman around a shared strategy memo, with a late joiner able to replay the prior 20 minutes and the room accumulating its own memory distinct from any participant's personal memory.

23.4 Acceptance Criteria

WebSocket fan-out supports ≤ 200 concurrent participants / ≤ 5,000 FDs per Room server (§4), verified by a load-test fixture; the red-team fixture shows zero cross-partition reads across 5,000 fuzzed attempts (I8); transcript ciphertext verified at rest via a cloud storage audit (zero plaintext objects written outside the active WebSocket session); replay scrub latency < 300 ms per turn fetched.

23.5 Conformance Fixtures

Fixture Purpose Expected Output

room-memory-isolation-probe.json fuzzed cross-partition attempts zero cross-partition reads (I8)

23.6 Pitfalls

  1. A WebSocket server holding open connections past a participant's actual departure leaks FDs toward the §4 ceiling — mitigated by an explicit heartbeat-timeout disconnect, not TCP-level detection alone.
  2. Room-level memory accidentally joined against personal memory in a shared query path is the single highest-severity regression possible here, guarded by I8's dedicated fixture.
  3. E2EE key material must be re-derived from the room invite on a device reload, never cached insecurely client-side.
  4. A Room server crash losing in-memory presence state without a corresponding transcript gap — presence is reconstructed from the ciphertext-backed event log on restart, never assumed clean from a fresh in-memory slate.

23.7 Performance Concerns

Fan-out breadth means a single Faculty response is broadcast once, never computed once per participant — the Reconciler pattern from §22 does not apply here since a Room wears exactly one Faculty at a time (§8.4). Replay scrub is paginated, never loading the full transcript client-side at once.

23.8 Edge Cases

  • A participant joining and leaving repeatedly within one session requires deduplicated presence tracking, never double-counted wearing-seconds.
  • The room owner leaving does not auto-transfer ownership — the room continues read-only until the owner returns or explicitly transfers, an explicit design choice.
  • A network partition splitting participants across two WebSocket instances is prevented in steady state by sticky routing on roomId, with a documented reconnect-and-resync flow on failover, never silent data loss.
  • Simultaneous late-joiner replay requests during peak activity are served from a read replica, isolated from the live fan-out path.
  • A participant attempting to invite past the 200-participant ceiling (§4) is blocked at the invite step with an explicit capacity message, never a silent no-op.

23.9 Failure Analysis

A Room memory-partition breach would be the single most severe failure in the entire system (I8, multi-human data exposure) — the quarterly external red-team pass (§15.9) explicitly includes Room fixtures. Blast radius is potentially multiple organizations' shared strategy content, requiring mandatory disclosure. Recovery is immediate Room-service lockdown plus forensic partition audit, the same severity tier as the §15 memory-partition incident.

23.10 Operational Notes

Runbook: docs/runbooks/room-partition-incident.md (shares its escalation tier with memory-partition-incident.md, §15.10). A BYO-cloud tenant's CI/CD pipeline pulling container images without verifying the build-provenance attestation (T14, I18, §30) reopens the supply-chain risk the SaaS deployment path already closes — the Helm chart's default values enforce attestation verification, and disabling it requires an explicit, audited override.

24.7 Performance Concerns

Single-tenant BYO-cloud deployments do not share the multi-tenant Postgres instance, so per-tenant vector-index tuning (ADR-06) is re-validated per tenant size rather than assumed from the multi-tenant baseline. Helm chart resource requests/limits are tenant-configurable, not hardcoded from SaaS defaults.

24.8 Edge Cases

  • An expert leaving the corporation mid-intake leaves the pattern co-authoring session incomplete — the Faculty remains in draft, never auto-promoted.
  • A departed employee's right-to-be-forgotten request against a Custom Corporate Faculty purges their personal wearing history while the Faculty's corporation-co-owned aggregate pattern is not deleted (the same personal-vs-aggregate distinction §11.2 draws).
  • An air-gapped installer environment with no outbound network access routes LLM calls to a customer-provided private endpoint (ADR-17's BYO-LLM escape hatch, PhaseDeferred("§24") for the Llama-3-70B path specifically).
  • A BYO-cloud tenant's Helm upgrade applied out of order relative to a Terraform infrastructure change — the deploy pipeline enforces infra-then-app ordering, never a free-standing Helm upgrade against unverified infrastructure state.
  • A Custom Corporate Faculty's corporate_owned provenance (I16) combined with a BYO-cloud tenant's own tenant-scoped query layer (§24.2) must both independently exclude it from any Store-adjacent query — the two exclusion mechanisms are tested together, never assumed to compose correctly from separate unit tests alone.

24.9 Failure Analysis

A tenant-isolation breach in the BYO-cloud path is the single worst-case failure across the entire system — it combines §15's memory-partition severity with enterprise-contract and compliance exposure. Detection extends the same red-team and fuzzed-partition-probe discipline to tenant_id. Recovery requires immediate tenant-boundary lockdown, mandatory customer disclosure, and a SOC 2 control-gap filing.

28. Compatibility & Versioning

  • Wire compatibility. tRPC contracts are versioned alongside the API; a breaking change is a new router namespace, never an in-place field removal.
  • Storage compatibility. every persisted record carries __schemaVersion (I10); the runtime supports the current and previous major schema version simultaneously for ≥ 6 months (P9).
  • Legacy rows migrate lazily on next read, never via a blocking batch migration.
  • Manifest schema evolution. closed schema, reject-unknown-fields (ADR-19); a behavior-changing field requires a major version bump and a public changelog entry.
  • Patch versions auto-update for existing wearers; minor and major versions require explicit wearer opt-in (§8.2).
  • API stability. the public OSS surface (Manifest schema, Pattern Engine reference, Author CLI) follows SemVer with a documented deprecation window of 2 minor versions before removal.
  • Migration tooling. packages/memory ships a lazy-migration adapter per major version; packages/manifest ships a faculty migrate CLI command for authors upgrading a Manifest across a major bump.
  • Rolling-upgrade guarantee. an engine-worker fleet may run mixed versions (current + previous minor) during a rolling deploy without breaking an in-flight session, because Session/Room state is versioned independently of the deployed code version (§11.3).

29. Testing & Verification Strategy

  • Unit (Vitest). ≥ 80% line coverage on engine, manifest, memory, pattern-rules, payouts.
  • Integration. tRPC route-level tests run against a real, containerized Postgres + pgvector, never a mock DB, so partition-key behavior (I2, I8) is exercised for real.
  • Property-based. the Manifest schema validator is fuzz-tested with structure-aware inputs (fuzz/manifest-fuzz) to catch schema-bypass edge cases beyond the hand-written fixtures.
  • Differential. every Faculty's evaluation score is compared across its current and previous Manifest version on every publish, flagging an unexplained regression before it reaches wearers (§18.6).
  • Fuzzing. the invariant simulator (§7) fuzzes signature tampering, partition-boundary probes, and stack-size overflow on every PR.
  • A dedicated tenant-isolation fuzz target (§24) extends the same harness to tenant_id.
  • Chaos. mid-run process kills injected into the royalty payout job (royalty-payout-restart.json, §20.5) and the Manifest signing service, verifying idempotent resume (P8).
  • Deterministic replay. every conformance fixture (§12.5 onward) is a deterministic input/expected-output pair, replayable byte-for-byte in CI — no fixture depends on wall-clock time or a live network call.
  • Soak. a 1-hour extension idle soak (§17.4) and a 72-hour Room fan-out soak at 150 participants precede every Phase 11+ release.
  • Fault injection. provider failover (ADR-07) is tested by forcing the primary provider to 5xx in staging before every release touching the orchestrator.
  • Conformance gating. the full evaluation suite (§18) and invariant simulator (§7) must be green before any release proceeds past the conformance.yml CI gate — the single non-negotiable merge gate in the system.
  • Performance-regression gating. every §31 M-table target is checked in CI on every release touching a relevant subsystem; two consecutive misses halts new feature work on that subsystem (§4's budget-exceeded rule).
  • Rate-limit testing. the token-bucket limiter (ADR-23) is fixture-tested against a burst-then-idle-then-burst replay pattern, confirming refill behavior matches the documented ceiling (M13) rather than an approximated one.
  • Idempotency-key determinism. a dedicated unit test asserts the payout idempotency-key derivation (ADR-25) is a pure function of (facultyId, periodStart), run on every change to packages/payouts.

30. Build & Release Engineering

  • Reproducible builds. pnpm lockfile pinned; Turborepo remote cache keyed by content hash, not timestamp, so a given commit always produces byte-identical build artifacts.
  • Artifact signing. the extension's Chrome Web Store package is signed by Google's store pipeline; internal container images are signed via cosign and verified at Fargate/Fly deploy time.
  • SBOM. generated per release via syft against every published container image and the extension bundle, archived alongside the ADR record for that release.
  • Release channels. main is always green and shippable, trunk-based with a max feature-branch lifetime of 5 days; weekly minor releases (Friday mornings UTC); patch releases on any green merge carrying a patch Changeset; major releases announced 30 days ahead with a migration guide (§28).
  • CI/CD topology. GitHub Actions runs lint/typecheck/unit on every PR, the full conformance.yml gate before merge to main, and release.yml (Changesets version + publish + signing) on merge.
  • Version stamping. every deployed artifact embeds its git SHA and Changeset-derived semver in a /health endpoint response and in OpenTelemetry resource attributes.
  • Provenance/attestation. container images carry SLSA-style build provenance attestations generated in CI, verifiable against the GitHub Actions run that produced them.
  • Dependency auditing. pnpm audit plus Dependabot on every PR; a critical CVE in a production dependency blocks merge until patched or explicitly waived with a written justification recorded in the PR.
  • Attestation verification. every deploy step (Fly.io, Fargate, and BYO-cloud Helm installs alike) verifies the SLSA-style provenance attestation (T14, I18) before accepting a new container image, closing the loop between CI-time attestation generation above and its runtime enforcement.

32. Scalability Analysis

  • What stays constant. Manifest load latency — O(1) signature verify, independent of corpus size; the Behavioural Rule Enforcer's single-retry bound (I7) — constant regardless of load; the royalty ledger's per-Faculty reconciliation cost — O(1) per Faculty per period.
  • What grows, and its Big-O. Memory rows grow O(wearers × sessions) per Faculty, bounding retrieval at O(log n) under HNSW (Malkov & Yashunin 2018) until the pgvector ceiling (§4, ADR-03).
  • Room fan-out cost grows O(participants) per broadcast message.
  • Search index size grows O(listings), with query cost held near-constant by the faceted-index structure until re-benchmarking is required (§21.6).
  • Named bottlenecks, in order. (1) pgvector query latency past ~2M vectors/Faculty — the first wall, mitigated by ADR-03's dedicated-vector-store migration path.
  • (2) LLM provider rate limits under stacked-session fan-out (§22.7) — mitigated by multi-provider routing (ADR-07).
  • (3) the nightly royalty-aggregation batch window — mitigated by Faculty-id-range sharding (§20.7).
  • (4) WebSocket FD budget per Room server (§4) — mitigated by horizontal Room-server scale-out with sticky roomId routing.
  • Horizontal vs. vertical scaling. the Cognitive Pattern Engine scales horizontally — stateless workers behind a load balancer.
  • Postgres scales vertically first (larger instance), then horizontally via read replicas for retrieval-heavy paths once write load allows.
  • Sharding/partitioning. the Memory Layer's (user_id, faculty_id) partition key is also the natural future shard key if a single Postgres instance becomes the ceiling.
  • The royalty ledger shards by Faculty-id range for batch processing today, and could shard by tenant for BYO-cloud isolation (§24) without a schema change.
  • Coordination overhead. the Reconciler (§22) is the one place where N independent computations must synchronize before responding — bounded at N ≤ 4 (I11) specifically to keep this coordination cost small and predictable.
  • Practical ceiling. roughly 2M vectors/Faculty and ~150 concurrent sessions/engine-worker (§4).
  • Levers beyond the ceiling. (a) the ADR-03 dedicated vector store; (b) horizontal engine-worker scale-out — already stateless, so this is a capacity, not a redesign, decision; (c) Postgres read-replica fan-out for retrieval-only traffic.
  • The rate-limiter's Postgres-backed state (ADR-28) adds negligible load at current author counts (§35 item 12) but is the first subsystem re-evaluated for a Redis migration (the ADR-28-rejected alternative) if author count grows an order of magnitude past the 250-author reference point.

33. Mental Models & First Principles

  1. MM1 — A Manifest is a contract, not a prompt. Treat it as an interface boundary with a compatibility guarantee, like a public API, never a casual prompt template. Predicts: schema changes need versioning discipline. Bug class without it: silent behavioral drift disguised as a "prompt tweak" that breaks wearer trust. Applies at §11.1, ADR-19.
  2. MM2 — Retrieval is lossy compression of the corpus, not search. Top-k retrieval always discards relevant context; recall@k is a first-class tunable, not an afterthought. Predicts: chunking strategy materially changes fidelity. Bug class without it: authors blame "the LLM" for what is actually a retrieval-recall problem. Applies at §14.2, ADR-08, ADR-22.
  3. MM3 — A partition key is a promise enforced by the database, not the application. Any isolation guarantee resting on every code path remembering to filter will eventually fail; push it to the schema/RLS layer. Bug class without it: one forgotten WHERE clause becomes a cross-tenant leak. Applies at §15.2, I2, I8.
  4. MM4 — Behavioral rules are guards around a black box, not control over it. You cannot make an LLM obey a rule by asking nicely in the prompt alone; a post-hoc validator with a bounded retry is required. Predicts: naive prompt-only rule systems degrade under adversarial input. Bug class without it: silent rule violations invisible in casual testing. Applies at §14.2, P7, I7.
  5. MM5 — Royalty is a distributed-ledger problem wearing a subscription business's clothes. Revenue-split allocation needs the rigor of a financial ledger (idempotency, reconciliation, append-only), not a dashboard computation. Bug class without it: double-pays and silent drift between the UI and actual money moved. Applies at §20, I5, P10, P8.
  6. MM6 — A Faculty Room is a convergence problem even without a CRDT. Multiple private side-channels plus one shared transcript is the same shape as shared-document convergence; sticky routing sidesteps needing an actual CRDT at this scale. Predicts: naive "broadcast to everyone" designs break under mid-session failover. Bug class without it: split-brain transcripts. Applies at §23.2, §23.8, ADR-11.
  7. MM7 — Evaluation is the load-bearing wall, not a QA afterthought. In a system whose core claim ("this Faculty thinks differently") is unfalsifiable by casual inspection, the evaluation suite is the only thing standing between the marketplace and pure marketing claims. Bug class without it: a marketplace that quietly degrades into a directory of unverified prompts. Applies at §18, P6, I4.
  8. MM8 — Every provider abstraction is a bet that behavior transfers, and it never fully does. A Faculty certified against Claude may behave differently on GPT-4o; provider-agnosticism is a spectrum, not a boolean. Predicts: silent quality regressions after a failover event. Bug class without it: assuming ADR-07's failover is quality-neutral. Applies at §14.6, ADR-07.
  9. MM9 — A rate limiter is a promise about the future, not just a counter of the past. A token bucket's refill rate encodes an assumption about sustainable throughput; tuning it wrong either starves legitimate bursts or fails to prevent abuse. Predicts: a limiter needs empirical calibration against real submission patterns, not a guessed constant. Bug class without it: an untuned limiter that either blocks power authors or lets a denial-of-wallet attack (T11/T13) through. Applies at §19.2, ADR-23, T11, T13.

35. Back-of-Envelope Capacity Model

  1. Vector storage at the ADR-03 migration ceiling: 2,000,000 rows × 3,072 dims × 4 bytes/float32 = 24.6 GB raw vector data per Faculty — the concrete byte figure behind the §4 "2M vectors/Faculty" ceiling.
  2. Memory rows per wearer at the Memory Lift mark: 5 rows/session (1 summary + up to 4 anchors/interactions) × 50 sessions (§18.4 benchmark) = 250 rows/wearer/Faculty.
  3. Platform-wide memory rows at a 5,000-WAU scale point (§16-equivalent KPI): 250 rows × 5,000 WAU × 1.5 avg Faculties/wearer ≈ 1.875M rows — well under the 24.6 GB/2M-row per-Faculty ceiling (item 1) when spread across even a modest 10-Faculty catalogue.
  4. Streaming bandwidth per session: 30 tokens/s (M6) × ≈4 bytes/token (UTF-8 English average) = 120 bytes/s per streaming session; × 150 concurrent sessions/worker (§4 ceiling) = 18 KB/s outbound per engine worker — confirms bandwidth is never the bottleneck (§32 places pgvector latency first, not network).
  5. Corpus text footprint: 512 tokens/chunk ≈ 2 KB text × 15 chunks/document × 30 documents/Faculty (§18.4 fixture scale) ≈ 900 KB raw text per corpus — negligible against the 24.6 GB vector-storage ceiling (item 1), confirming vectors, not source text, dominate storage.
  6. Room-server capacity: 5,000 FDs per server (§4 M8) ÷ 200 participants/Room = ≈25 concurrent full Rooms per server instance — the number behind §32's "horizontal Room-server scale-out" lever.
  7. Royalty reconciliation tolerance as a fraction of revenue: $0.01 (§4 M9) ÷ $19/month bundle price = 0.05% of the smallest meaningful per-wearer transaction — two orders of magnitude tighter than the smallest real transaction, which is why I5 halts the whole run rather than tolerating drift.
  8. Evaluation-suite marginal cost: ≈150 LLM calls/Faculty (§18.7) × ≈$0.01/call blended judge+generation cost ≈ $1.50 per full evaluation run; at a 250-publish/month marketplace cadence ≈ $375/month platform-wide — small against marketplace GMV, confirming the evaluation gate (P6) is not the economic bottleneck.
  9. Stacked-session cost multiplier: N=4 stack (§22.7) ≈ 4× single-Faculty LLM cost + 1 Reconciler pass ≈ 5× baseline per-session cost — the number that justifies pro-rata, not equal-split, royalty attribution (ADR-21): a stacked session must earn proportionally more revenue or the unit economics invert.
  10. Trust & Safety staffing implication: at a conservative 1 report per 50 listings/month and a 250-Faculty catalogue (§21-equivalent KPI target) ≈ 5 Sev-2 reports/month — comfortably within a single part-time reviewer's capacity, the number behind the Trust & Safety hiring trigger.
  11. Author submission rate-limit ceiling in practice: 10 publishes/author/day (M13, ADR-23) × 250 active authors (item 10's catalogue scale) = 2,500 max daily submissions — far above the ~8/day actually observed (250 publishes/month ÷ 30, item 8), confirming ADR-23's token-bucket ceiling is a safety margin, not a routine constraint.
  12. Rate-limiter state footprint: one token-bucket row per author (≈64 bytes: author id + token count + last-refill timestamp) × 250 authors ≈ 16 KB total — negligible against every other subsystem in this model, confirming ADR-28 chose Postgres for correctness and simplicity, not to solve a memory problem.

37. Alternative Architectures (Roads Not Taken)

Alternative 1 — Client-Side Pattern Engine (No Trusted Server Boundary)

  • [Browser: Extension/Web App]
    • Manifest downloaded + interpreted locally
    • Retrieval + prompt assembly run client-side
    • LLM provider called directly from the client
  • (no Session Gateway, no server trust boundary)

Regime where it wins: an offline-first, privacy-maximalist product with no marketplace or royalty requirement — nothing to enforce server-side because there is no revenue to protect. Real system: the shape of a fully local-first RAG note-taking assistant. Why rejected: I12 (anti-impersonation framing), I4 (evaluation gating), and I5 (the royalty ledger) all require a server-side enforcement point the wearer cannot bypass; a client-side engine cannot protect an author's royalty entitlement or the platform's legal framing guarantee.

Alternative 2 — Federated / Peer-to-Peer Faculty Distribution

[Author] → signs package → [Content-addressed DHT]
                                    │
                          [Wearer fetches directly]
                                    │
                     [Smart-contract royalty settlement]
                        (no central Faculty Store)

Regime where it wins: a context where centralized-platform risk (deplatforming, takedown-as-censorship) is the primary threat model — e.g., a jurisdiction-resistant publishing tool. Real system: the architecture decentralized social protocols (Farcaster/Lens-style) use for content distribution and payment. Why rejected: the takedown SLA (T5, §25) and the evaluation gate (P6) require a central enforcement point precisely because impersonation, IP, and quality risk are real and time-sensitive — a P2P system cannot delist a defamatory Faculty within 24 hours by design.

Alternative 3 — Fine-Tuned Per-Faculty Models (No Runtime RAG)

[Manifest] → points to a model-weights artifact, not a corpus
[Engine]   → loads weights per session instead of retrieving chunks
[Author]   → ships a fine-tune/LoRA checkpoint, not a document corpus

Regime where it wins: when a pattern's fidelity genuinely benefits from weight-level adaptation beyond prompting-plus-retrieval, and the inference cost of serving many fine-tuned checkpoints is acceptable — e.g., a small, fixed catalogue of very high-value enterprise Faculties. Real system: the shape of OpenAI's fine-tuning API or a LoRA-serving platform (Predibase). Why rejected: it breaks marketplace economics (fine-tuning cost per Faculty far exceeds a RAG corpus update, ADR-08) and breaks fast iteration (an author cannot A/B a behavioral-rule change without a full retrain) — though it remains a future enterprise-tier option for very-high-value Custom Corporate Faculties (§38).

39. Glossary

  • Anchor — an explicit "remember this about me for this Faculty" memory row, surfaced in UI and user-editable (§11.2).
  • Author — the creator of a Faculty, identity-verified via Stripe Connect KYC (§20), entitled to royalty under ADR-21.
  • Author Tools — the CLI (@faculty/cli) and Web Studio (apps/studio) through which an author drafts, validates, evaluates, and publishes a Faculty (§19).
  • Behavioral Rule — a structured constraint (e.g., must_invert, must_cite) compiled into a pre-flight/post-flight runtime guard, never executed as code (§11.1, P1, P7).
  • BYO-Cloud — a single-tenant, customer-hosted deployment topology (Helm + Terraform) sharing the SaaS codebase behind a config flag (ADR-18, §24).
  • Cognitive Pattern Engine ("the Engine") — the trusted-boundary runtime turning a Manifest into live behavior: retrieval, prompt assembly, rule enforcement, LLM orchestration (§14).
  • Cognitive Primitive — a declared atomic operation (e.g., inversion, first-principles decomposition) a Faculty performs and the evaluation suite tests for (§11.1, §18).
  • Corpus — the retrieval source material for a Faculty: signed, chunked, embedded documents (§11.1, ADR-22).
  • Corpus Fingerprint — a content hash (or SimHash/MinHash under ADR-31) used both for IP-infringement scanning (§19, T2) and duplicate-across-account rate-limit-evasion detection (T15).
  • Custom Corporate Faculty — a Faculty trained on an internal expert's archive, corporate_owned provenance, deployed only inside one tenant, never publicly listed (§24).
  • Denial-of-Wallet — an attack pattern (T11) where pathological or abusive usage inflates LLM-call cost rather than compromising data; mitigated by per-Faculty cost ledgers and rate limits (§19, ADR-23).
  • Ed25519 — the elliptic-curve signature scheme (RFC 8032) used to sign every Manifest (ADR-05, I1, I14).
  • Evaluation Suite — the mandatory automated test pack (packages/eval-suite) gating marketplace listing (§18, P6, I4).
  • Faculty — a versioned, Manifest-defined bundle of cognitive pattern, corpus, behavioral rules, evaluation suite, and memory scope (§11.1).
  • Faculty Room — a multi-human shared session wearing one Faculty around a shared task, with a separate memory partition (§23).
  • Faculty Store — the public marketplace surface for browsing, searching, and renting Faculties (§21).
  • Fingerprint Scan — the IP-infringement and duplicate-corpus detection step run at submission time (§19, T2, T15).
  • HNSW (Hierarchical Navigable Small World) — the approximate-nearest-neighbor graph index type used by pgvector for retrieval (ADR-06, Malkov & Yashunin 2018).
  • HW/WAU — Hours Wearing per Weekly Active User; the north-star metric, accumulated via Session.wearingSeconds (§11.3, §16).
  • Idle Network Invariant — informal name for I15: the guarantee that the extension emits zero network traffic while no Faculty is active (§17.4).
  • Invariant (I#) — a system-wide correctness guarantee enforced structurally, not by convention (§7).
  • Manifest — the signed, versioned JSON envelope defining a Faculty (§11.1).
  • Memory Entry — a single row of per-(user, Faculty) or per-(room, Faculty) compounding context: interaction, summary, anchor, or preference (§11.2).
  • Memory Layer — the partitioned vector-plus-structured store implementing compounding context (§15).
  • Memory Lift — the measured relevance improvement in retrieval once a Faculty's memory crosses a usage threshold (§18.4 target: ≥ 25% by interaction 50).
  • Partition Key — the (user_id, faculty_id), (room_id, faculty_id), or (tenant_id, user_id, faculty_id) tuple enforced at the database layer to guarantee isolation (I2, I8, §24).
  • Pattern Engine — shorthand for Cognitive Pattern Engine.
  • Provenance — the declared rights basis (public_domain, estate_licensed, original_work, corporate_owned) of a Faculty's corpus (§11.1).
  • Provenance Attestation — a SLSA-style, CI-generated cryptographic record proving a build artifact came from a specific, verifiable CI run (§30, T14, I18) — distinct from Manifest Provenance (rights basis) despite the shared term.
  • Query-Builder Exclusion — the pattern behind I16: a structural, base-query-level filter (e.g., excluding corporate_owned Faculties) rather than a per-callsite WHERE clause (§24.2).
  • RAG (Retrieval-Augmented Generation) — the retrieve-then-generate architecture underlying the Engine's corpus and memory retrieval (§14, Lewis et al. 2020, ADR-08).
  • Rate Limit (Token Bucket) — the per-author submission throttle (ADR-23) that refills continuously rather than resetting on a fixed window boundary, gating publish frequency (§19, I17).
  • Reconciler — the platform-controlled prompt that synthesizes agreements and disagreements across a Stack's independent Faculty responses (§22).
  • Retrieval — the top-k similarity search over corpus and memory embeddings that grounds a Faculty's response (§14.2).
  • Rights Basis — see Provenance.
  • Royalty Ledger — the append-only, reconciled record of revenue allocation to authors (§11.4, §20, I5).
  • Session — a scoped wearing instance accumulating wearingSeconds and an append-only event log (§11.3).
  • Signing Key — the Ed25519 keypair (with rotation lineage) used to sign Manifests; pluggable to an HSM/KMS for BYO-cloud tenants (§13, §24.2).
  • SLSA — Supply-chain Levels for Software Artifacts; the build-provenance attestation framework applied to container images and the extension bundle (§30, T14, I18).
  • Stack — a composition of N ≤ 4 Faculties worn simultaneously, reconciled by the Reconciler (§11.4, §22, I11).
  • Takedown SLA — the response-time commitment for a Trust & Safety report: 24h for Sev-1, 7 days for Sev-2 (§21, §25).
  • Tenant — an isolated customer boundary in the BYO-cloud deployment topology, scoped by tenant_id (§24).
  • Token Bucket — see Rate Limit (Token Bucket).
  • Trust & Safety (T&S) — the human-review backstop for borderline evaluation, impersonation, and takedown cases (P14, §21).
  • Vault Scope — the per-record privacy marker (user_only, user_and_platform_audit, user_and_faculty_aggregate) governing what an author may ever see (§11.2).
  • Wearer — a user actively wearing a Faculty around a task.
  • Wearing — active use of a Faculty around a browser task, the unit HW/WAU measures.
  • Wearing Surface — the web app's rich-text task editor plus Faculty side panel (§16).
