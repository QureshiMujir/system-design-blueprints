Decisions (§9) · 31 ADRs

ADR-01

Primary language

Chosen

TypeScript 5.x strict, end-to-end

Rejected

Go; Python throughout

When the rejected choice is right

Go wins for a pure-throughput microservice with no Manifest boundary; Python wins inside eval-suite for ML-judge tooling (retained narrowly)

Why: one language for a solo+AI team; types catch Manifest drift at compile time (§1, I3)

ADR-02

API layer

Chosen

tRPC internal

Rejected

REST; GraphQL

When the rejected choice is right

REST wins once non-TS third parties need a stable, language-agnostic public API — the Manifest/corpus-fetch surface is published as OpenAPI at the OSS boundary

Why: end-to-end type inference eliminates contract drift between backend and Next.js

ADR-03

Primary vector store

Chosen

pgvector inside Postgres 16

Rejected

Pinecone; Weaviate; Milvus

When the rejected choice is right

a dedicated vector DB wins past ~50M vectors or when sub-10ms p99 ANN recall at high QPS is required (PhaseDeferred("§15"))

Why: one database to operate at < 2M vectors/Faculty; transactional consistency with memory rows (§4)

ADR-04

Object storage

Chosen

Cloudflare R2 (Phase 0–8), AWS S3 (Phase 12+)

Rejected

S3-only from day one; GCS

When the rejected choice is right

S3 wins once SOC 2 posture and AWS-native KMS/BYOK integration outweigh egress cost (§24)

Why: R2's zero egress fee matters while manifest/corpus downloads are frequent pre-revenue

ADR-05

Manifest signing algorithm

Chosen

Ed25519 (RFC 8032)

Rejected

RSA-2048; ECDSA-P256

When the rejected choice is right

RSA/ECDSA win when interoperating with an enterprise HSM/KMS exposing only those primitives (§24 BYOK path)

Why: smaller signatures, faster verify, deterministic signing avoids nonce-reuse bugs (I1, I14)

ADR-06

Vector index type

Chosen

HNSW (pgvector)

Rejected

IVFFlat; brute-force scan

When the rejected choice is right

IVFFlat wins when insert throughput dominates over query latency and a periodic re-train window is acceptable (bulk re-embedding jobs)

Why: best recall/latency at < 2M vectors/Faculty with no training step (Malkov & Yashunin 2018)

ADR-07

LLM provider strategy

Chosen

multi-provider router, Claude primary

Rejected

Claude-only lock-in

When the rejected choice is right

Claude-only wins for a Faculty whose evaluation score depends on provider-specific behavior; llm.preferred can pin and skip fallback

Why: rate-limit/pricing risk requires failover (P13)

ADR-08

Retrieval architecture

Chosen

RAG (retrieve-then-generate), top-k

Rejected

full-corpus-in-context

When the rejected choice is right

full-context wins for a small (< 20-doc) corpus where retrieval-recall risk outweighs token cost

Why: corpora exceed context budgets at scale; bounds latency and cost (Lewis et al. 2020)

ADR-19

Manifest schema-evolution policy

Chosen

Rejected

When the rejected choice is right

an open field wins only for genuinely additive, non-behavioral metadata added as an explicitly optional field inside a minor bump

Why: a behavior-changing field can never be silently ignored (I3, I10)

ADR-20

Chosen

server-side post-processing filter

Rejected

When the rejected choice is right

client-side wins only for cosmetic UX rendering (e.g., highlighting a counter-question) carrying no legal weight

ADR-21

Chosen

Rejected

When the rejected choice is right

ADR-25

Payout idempotency-key store

Chosen

Postgres unique constraint on (facultyId, periodStart)

Rejected

Redis-backed dedup set with TTL

When the rejected choice is right

Redis wins when the idempotency window is much shorter than a billing period and eviction is desirable — not the case for monthly payouts

Why: ties idempotency to the same durable store as the ledger itself, avoiding a second source of truth for a money-critical guarantee (I5, P8)

ADR-26

Rate-limit enforcement point

Chosen

Session/API Gateway layer, before the Author Tools handler

Rejected

inside each individual tRPC procedure

When the rejected choice is right

per-procedure limits win for a route with a materially different abuse profile than submission (none identified yet in this system)

Why: one enforcement point for every submission-shaped call, mirrors P5's "partition at the database, not the application" discipline applied to rate limiting

Chosen

SimHash / MinHash over corpus shingles

Rejected

When the rejected choice is right

Roads not taken (§37)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alternative 1 — Client-Side Pattern Engine (No Trusted Server Boundary)

  • [Browser: Extension/Web App]
    • Manifest downloaded + interpreted locally
    • Retrieval + prompt assembly run client-side
    • LLM provider called directly from the client
  • (no Session Gateway, no server trust boundary)

Regime where it wins: an offline-first, privacy-maximalist product with no marketplace or royalty requirement — nothing to enforce server-side because there is no revenue to protect. Real system: the shape of a fully local-first RAG note-taking assistant. Why rejected: I12 (anti-impersonation framing), I4 (evaluation gating), and I5 (the royalty ledger) all require a server-side enforcement point the wearer cannot bypass; a client-side engine cannot protect an author's royalty entitlement or the platform's legal framing guarantee.

Alternative 2 — Federated / Peer-to-Peer Faculty Distribution

[Author] → signs package → [Content-addressed DHT]
                                    │
                          [Wearer fetches directly]
                                    │
                     [Smart-contract royalty settlement]
                        (no central Faculty Store)

Regime where it wins: a context where centralized-platform risk (deplatforming, takedown-as-censorship) is the primary threat model — e.g., a jurisdiction-resistant publishing tool. Real system: the architecture decentralized social protocols (Farcaster/Lens-style) use for content distribution and payment. Why rejected: the takedown SLA (T5, §25) and the evaluation gate (P6) require a central enforcement point precisely because impersonation, IP, and quality risk are real and time-sensitive — a P2P system cannot delist a defamatory Faculty within 24 hours by design.

Alternative 3 — Fine-Tuned Per-Faculty Models (No Runtime RAG)

[Manifest] → points to a model-weights artifact, not a corpus
[Engine]   → loads weights per session instead of retrieving chunks
[Author]   → ships a fine-tune/LoRA checkpoint, not a document corpus

Regime where it wins: when a pattern's fidelity genuinely benefits from weight-level adaptation beyond prompting-plus-retrieval, and the inference cost of serving many fine-tuned checkpoints is acceptable — e.g., a small, fixed catalogue of very high-value enterprise Faculties. Real system: the shape of OpenAI's fine-tuning API or a LoRA-serving platform (Predibase). Why rejected: it breaks marketplace economics (fine-tuning cost per Faculty far exceeds a RAG corpus update, ADR-08) and breaks fast iteration (an author cannot A/B a behavioral-rule change without a full retrain) — though it remains a future enterprise-tier option for very-high-value Custom Corporate Faculties (§38).
