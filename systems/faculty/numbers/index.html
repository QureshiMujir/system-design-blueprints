35. Back-of-Envelope Capacity Model

  1. Vector storage at the ADR-03 migration ceiling: 2,000,000 rows × 3,072 dims × 4 bytes/float32 = 24.6 GB raw vector data per Faculty — the concrete byte figure behind the §4 "2M vectors/Faculty" ceiling.
  2. Memory rows per wearer at the Memory Lift mark: 5 rows/session (1 summary + up to 4 anchors/interactions) × 50 sessions (§18.4 benchmark) = 250 rows/wearer/Faculty.
  3. Platform-wide memory rows at a 5,000-WAU scale point (§16-equivalent KPI): 250 rows × 5,000 WAU × 1.5 avg Faculties/wearer ≈ 1.875M rows — well under the 24.6 GB/2M-row per-Faculty ceiling (item 1) when spread across even a modest 10-Faculty catalogue.
  4. Streaming bandwidth per session: 30 tokens/s (M6) × ≈4 bytes/token (UTF-8 English average) = 120 bytes/s per streaming session; × 150 concurrent sessions/worker (§4 ceiling) = 18 KB/s outbound per engine worker — confirms bandwidth is never the bottleneck (§32 places pgvector latency first, not network).
  5. Corpus text footprint: 512 tokens/chunk ≈ 2 KB text × 15 chunks/document × 30 documents/Faculty (§18.4 fixture scale) ≈ 900 KB raw text per corpus — negligible against the 24.6 GB vector-storage ceiling (item 1), confirming vectors, not source text, dominate storage.
  6. Room-server capacity: 5,000 FDs per server (§4 M8) ÷ 200 participants/Room = ≈25 concurrent full Rooms per server instance — the number behind §32's "horizontal Room-server scale-out" lever.
  7. Royalty reconciliation tolerance as a fraction of revenue: $0.01 (§4 M9) ÷ $19/month bundle price = 0.05% of the smallest meaningful per-wearer transaction — two orders of magnitude tighter than the smallest real transaction, which is why I5 halts the whole run rather than tolerating drift.
  8. Evaluation-suite marginal cost: ≈150 LLM calls/Faculty (§18.7) × ≈$0.01/call blended judge+generation cost ≈ $1.50 per full evaluation run; at a 250-publish/month marketplace cadence ≈ $375/month platform-wide — small against marketplace GMV, confirming the evaluation gate (P6) is not the economic bottleneck.
  9. Stacked-session cost multiplier: N=4 stack (§22.7) ≈ 4× single-Faculty LLM cost + 1 Reconciler pass ≈ 5× baseline per-session cost — the number that justifies pro-rata, not equal-split, royalty attribution (ADR-21): a stacked session must earn proportionally more revenue or the unit economics invert.
  10. Trust & Safety staffing implication: at a conservative 1 report per 50 listings/month and a 250-Faculty catalogue (§21-equivalent KPI target) ≈ 5 Sev-2 reports/month — comfortably within a single part-time reviewer's capacity, the number behind the Trust & Safety hiring trigger.
  11. Author submission rate-limit ceiling in practice: 10 publishes/author/day (M13, ADR-23) × 250 active authors (item 10's catalogue scale) = 2,500 max daily submissions — far above the ~8/day actually observed (250 publishes/month ÷ 30, item 8), confirming ADR-23's token-bucket ceiling is a safety margin, not a routine constraint.
  12. Rate-limiter state footprint: one token-bucket row per author (≈64 bytes: author id + token count + last-refill timestamp) × 250 authors ≈ 16 KB total — negligible against every other subsystem in this model, confirming ADR-28 chose Postgres for correctness and simplicity, not to solve a memory problem.
