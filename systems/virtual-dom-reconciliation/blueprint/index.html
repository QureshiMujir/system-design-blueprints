Project Name: Virtual DOM + Reconciliation

Status: specification — locked

1. Goal & Scope

Build a production-grade UI reconciliation runtime, nimbus, in the React/Preact/Inferno tradition: a typed virtual-DOM (VNode) representation, an O(n log n) keyed-children diff heuristic, a fiber-style interruptible work loop with priority lanes and time-slicing, a positional hooks/state model, a render/commit phase split with a host-adapter trait, a synthetic event-delegation system, SSR streaming + hydration with mismatch recovery, and concurrent-mode primitives (transitions, deferred values, tearing-safe external-store reads). The system is a library, not an application: it is embedded into a host document via createRoot/hydrateRoot and driven by component re-renders, not by an external event loop it owns.

Phase-0 deliverable (numbered):

  1. nimbus-reconciler — fiber tree, beginWork, keyed diff (sync only, no scheduler).
  2. nimbus (public package) — createRoot, Root.render, minimal component contract.
  3. nimbus-jsx-runtime — jsx/jsxs/Fragment triple, no jsxDEV.
  4. nimbus-host-test — pure-data host adapter for deterministic conformance testing.
  5. conformance/ harness — one passing fixture: render <h1>hi</h1>.

System boundaries.

  • Provides: VNode diffing, fiber scheduling, hooks, synthetic events, SSR + hydration, suspense/error-boundary containment, DevTools wire protocol, ESLint hooks-rules plugin.
  • Delegates: actual layout/paint (to the host document's layout engine — project rank 124, the HTML/CSS Layout Engine, is the paired system this runtime targets); routing; global state management beyond useSyncExternalStore; CSS-in-JS (only an insertion-order hook, useInsertionEffect, is provided as a seam).
  • Does NOT provide: a bundler, a compiler-level auto-memoization pass (see Deferred Features Register, §37), a native-platform renderer (§37), Server Components (§37).

Non-goals: exact tree-edit-distance (Zhang-Shasha optimality) diffing — the O(n log n) LIS-keyed heuristic is the locked choice (ADR-09, §9); a global reactive-signal graph (SolidJS's model, see Alternative Architectures, §36) — the runtime is coarse-grained, re-render-based by design (P1, §6).

Deployment model: an npm-published, dual ESM/CJS library, tree-shakeable, embedded into a host application's bundle; no server process of its own beyond the optional renderToReadableStream/renderToPipeableStream entry points invoked by the embedding application's own HTTP server.

Target users/operators: application engineers building interactive UIs who need a runtime smaller and more legible than React, with an explicit, auditable concurrent-rendering contract; the "operator" of a running instance is the embedding application's own on-call engineer, not a nimbus-specific operations team — Operational Readiness (§26) is written for that audience.

What later phases unlock: Phase 4 (Hooks, §16) unlocks stateful components; Phase 5 (Scheduler, §17) unlocks non-blocking large-tree updates; Phase 8 (SSR, §20) unlocks server rendering; Phase 9 (Concurrent Mode, §21) unlocks transitions/deferred values; Phase 10 (DevTools, §22) unlocks production debugging.

Language + rationale. TypeScript 5.4+ for the runtime (npm-published, browser- and Node-embedded); rejected: plain JavaScript (no compile-time discriminated-union checking on VNode, no structural typing for the HostAdapter trait — both are load-bearing for correctness, P1/P4 §6); Rust (wrong runtime target — the reconciler must run inside the same JS heap as the embedding application to share object identity for refs/closures; FFI marshalling cost on every fiber would dominate); ReScript/OCaml-to-JS (excellent ADT support but a niche toolchain the target audience does not already run, raising the adoption floor for zero correctness gain over TS's discriminated unions). Rust is retained only for nimbus-host-test's determinism harness and the deferred native backend (§37), where FFI cost is amortized once per host operation, not once per fiber.

Prerequisites: tree traversal algorithms, JS event-loop and microtask/macrotask semantics, closures and referential equality, the DOM event model (capture/bubble), amortized-analysis reasoning (for the LIS-keyed diff), basic queueing-theory intuition (for priority-lane starvation, §31).

Estimated timeline: Phase 0 — 1 week. Full system (Phases 0–11) — 24 weeks (~6 months).

Deferred features (full register at §37): native platform host backend PhaseDeferred("§11"); Server Components PhaseDeferred("§20"); compiler-driven automatic memoization PhaseDeferred("§16"); form actions / useActionState PhaseDeferred("§20"); WASM-compiled core PhaseDeferred("§11"); resource-preload hooks PhaseDeferred("§20").

2. Why Build This

Unique systems knowledge. A VDOM reconciler is the smallest system that forces mastery of five hard problems at once: (1) computing a minimal edit script from two trees without paying tree-edit-distance's cubic cost (§8, ADR-09 §9); (2) making a call stack pausable — Fiber's central trick (§14, MM1 §32); (3) giving imperative-looking code (useState) a positional, order-dependent contract that must survive arbitrary composition (§16, MM3 §32); (4) making "the user never sees a half-finished render" a scheduling invariant, not a hope (I9 §7, §21); (5) reconciling a server-rendered string against a client tree with zero shared memory (§20).

Why it matters architecturally. Every declarative UI framework shipped since 2013 (React, Vue, Angular's Ivy, Elm, Svelte's compiled variant, SolidJS) answers these five questions differently, and the answer chosen determines the framework's entire performance envelope and debugging experience. Historically, this is also the clearest teaching example of "coarse-grained re-render + cheap diff" (React/Preact/Inferno) versus "fine-grained reactive graph, no diff" (SolidJS, Svelte) — a genuine fork in programming-model history, not a performance footnote (Comparative Architecture Table, §33).

Engineering muscles built. Amortized-cost algorithm selection under a hard latency budget (§8, §34); designing a positional (not keyed) API contract and defending it with tooling instead of runtime checks (§16); building a cooperative scheduler with true preemption semantics inside a single-threaded host (§17); reasoning about consistency without locks (useSyncExternalStore's synchronous-read contract, §21, MM7 §32).

Cross-links to sibling systems. Shares the host-adapter boundary with project rank 124 (HTML/CSS Layout Engine) — nimbus computes what to mutate, 124 computes where things land. The scheduler's cooperative-yield design is the same shape as a green-thread runtime or an async executor (compare any project in this portfolio implementing a task scheduler); the SSR streaming protocol is a specialized single-producer streaming protocol (compare any project implementing a streaming RPC framework).

Calibration value. Finishing this project is the calibration point for "can you design an API contract that is unenforceable by the type system alone and must be defended by static analysis (the hooks linter) instead" — a recurring shape in systems work (e.g. unsafe Rust contracts, wire-format versioning contracts).

What Mastery Looks Like

  • Explain why the render phase must be pure and the commit phase must not be, and name the exact bug class each half of that split prevents (Phase 2 §14, Phase 3 §15).
  • Derive the keyed-children diff's O(n log n) bound from the LIS subproblem and state exactly when it degrades to O(n²) (Phase 2 §14, §8).
  • Explain why hooks are positional instead of keyed, and reproduce the exact failure a conditional hook call produces (Phase 4 §16).
  • Explain why a bitmask of lanes, not a priority integer, is required for interruptible concurrent rendering (Phase 5 §17).
  • Explain the tearing failure mode precisely enough to write the useSyncExternalStore fuzz fixture that catches it (Phase 9 §21).
  • Explain why hydration recovers locally instead of bailing out globally, and what SSR investment a bail-out design would destroy (Phase 8 §20).
  • Trace a single click event from native dispatch through synthetic delegation to a component's handler, across a portal boundary (Phase 6 §18).

Public API. The only surface an embedding application imports; every function is a thin entry into the reconciler. VNode Model + JSX Runtime. The vocabulary: a frozen, discriminated-union tree produced fresh on every render call; never mutated in place. Reconciler. The render-phase engine; pure and restartable (P1 §6); diffs the previous committed fiber tree against the new VNode tree using the LIS-keyed heuristic (§8). Hooks. A per-fiber, call-order-indexed slot list threaded through beginWork invocations of function components; the positional contract (P3 §6, MM3 §32). Scheduler. Owns the lane bitmask, the 5ms time-slice budget, and the yield-to-host mechanism; the sole concurrency boundary in the diagram — everything left of it may pause. Suspense/Error Boundary. Structured control flow for async-wait and failure, expressed as thrown values, not callbacks (P7/P8 §6). Commit Phase. The only place side effects happen; synchronous and indivisible (P2 §6) — the persistence boundary where host mutations become observable. Host Adapter. The protocol boundary: the reconciler never imports the DOM directly (P4 §6); the DOM backend and the deterministic test renderer are two implementations of one trait. Event System. Delegates at the root; portal-aware, independent of native DOM bubble order (P6 §6). SSR + Hydration. Produces and consumes the wire format that lets a server-rendered string become an interactive client tree without a full re-render. Concurrent Mode. The layer that makes "no visible half-finished render" (I9 §7) hold even when rendering is interruptible. Dev Tools. Entirely compiled out of production bundles (T11 §24, ADR-19 §9).

6. Design Principles

  1. P1 — The render phase is pure and restartable. Components return new VNode trees; they never mutate the host. Violating it: a beginWork call that touches the DOM breaks time-slicing (§17) and concurrent mode (§21) simultaneously, since a paused/discarded render would leave stray mutations. Tradeoff: forces every side effect through the commit phase's stricter contract (P2). Operational implication: a "component touches document directly" bug report is always a P1 violation; the runbook (§26) starts there.
  2. P2 — The commit phase is synchronous and indivisible. Once entered, it runs to completion; no reentrancy, no yielding. Tradeoff: a slow commit (e.g., a huge commitMutation batch) blocks the main thread with no escape hatch — this is the one place time-slicing does not apply, by design (I2 §7). Violating it (yielding mid-commit) would let the host observe a torn tree, breaking I9.
  3. P3 — Hooks are positional. A function component's hook list is determined by call order on each render. Tradeoff: unenforceable by the type system; defended by the dev-only Strict Mode check (§21.5) and the eslint-plugin (§22.3), not by the runtime. Violating it silently corrupts unrelated state slots (MM3 §32).
  4. P4 — The reconciler does not know about the DOM. A HostAdapter trait (§11) abstracts every host operation. Tradeoff: an extra vtable-style indirection per host operation (small constant overhead); the payoff is the DOM backend, the test renderer, and the deferred native backend (§37) sharing one reconciler. Violating it (importing document in the reconciler) breaks the test renderer's determinism (I4 §7).
  5. P5 — Children diff is keyed; key order is honoured. Unkeyed: match by position. Keyed: match by key via the LIS-based middle-reorder pass (§14.4). Tradeoff: O(n log n), not optimal (ADR-09 §9); an unstable key (T3 §24) silently defeats memoization.
  6. P6 — Synthetic events delegate at the root. A single native listener per event type at the root container; dispatch walks the fiber tree in React-tree order, not DOM-tree order. Tradeoff: one delegated listener regardless of tree size (derivation 10, §34) at the cost of a per-dispatch fiber-chain walk; violating it breaks portal event propagation (T10 §24).
  7. P7 — Suspense throws. A component that needs to wait throws a Promise; the reconciler walks up to the nearest <Suspense> boundary. Tradeoff: composes with any data-fetching library with zero API surface, at the cost of an unusual (exception-as- control-flow) mental model (MM5 §32).
  8. P8 — Error boundaries catch. A boundary defining getDerivedStateFromError / componentDidCatch (or the functional equivalents) catches descendant render/commit errors. Tradeoff: errors above the topmost boundary kill the root (I8 §7); violating this containment contract (e.g., a try/catch inside render swallowing an error silently) is FM-7 (§25).
  9. P9 — Concurrent rendering preserves invariants. The render phase writes to an off-tree work-in-progress fiber tree; the host only observes the result after commit. Tradeoff: doubles peak fiber memory during an in-flight concurrent render (derivation 8, §34); violating it (partial commit) breaks I9.
  10. P10 — Strict Mode is dev-only. Double-invocation of render and effect-mount, hook-order verification. Tradeoff: doubles dev-mode render cost; stripped entirely from production (ADR-19 §9, T11 §24).
  11. P11 — The JSX runtime is the jsx/jsxs/Fragment triple. Compatible with the Babel/TypeScript 5+ automatic JSX transform. Tradeoff: couples us to that transform's calling convention; violating it (inventing a bespoke transform) breaks tooling interop across the whole ecosystem.
  12. P12 — Refs are imperative and committed. useRef returns a mutable { current } cell; the commit phase assigns/detaches it. Tradeoff: refs are not reactive — reading .current in render is a documented anti-pattern, not a type error.
  13. P13 — Hydration recovers from mismatches, never bails out wholesale. A mismatch triggers a local client re-render of the affected subtree only. Tradeoff: a silent recovery risk (mitigated by the onRecoverableError channel, ADR-23 §9); violating it (global bail-out) destroys the entire SSR investment (§20).
  14. P14 — No global mutable state. The runtime is per-root; the scheduler is a single shared instance across roots but coordinates via message-passing, not shared mutable state. Tradeoff: cross-root synchronization has message-passing latency instead of a direct write; violating it makes multi-root embedding (e.g., micro-frontends) unreliable.
  15. P15 — A root is Send-like (single-owner-thread) but not Sync. One root is driven by one thread (typically the DOM main thread). Tradeoff: no cross-thread direct access to a root's fiber tree; the deferred native/worker backend (§37) must define its own cross-thread contract explicitly, not inherit one implicitly.

8. Domain Model

VNode Schema (the AST the reconciler consumes)

VNode
 ├─ $$typeof: brand              # Symbol.for("nimbus.element") — distinguishes from plain objects
 ├─ type: string | Component | ClassComponent | Sentinel
 │        Sentinel ∈ {Fragment, Portal, Suspense, ErrorBoundary, Profiler,
 │                     StrictMode, Memo, ForwardRef, Lazy}
 ├─ key: string | number | null   # extracted from props before freeze (P5, I5)
 ├─ ref: RefObject | RefCallback | null
 └─ props: frozen record          # children live at props.children

A VNode tree is produced fresh, bottom-up, on every render call (P1 §6); it is never diffed against itself — it is always diffed against the previous fiber tree, not a previous VNode tree (the fiber tree is the memory of "what happened last time").

Reconciliation Algorithm (named, not coded)

Reconciliation is a two-phase walk over a (currentFiber, nextVNode) pair, producing a workInProgressFiber:

  1. Type-match test. If currentFiber.type === nextVNode.type (and, for keyed nodes, currentFiber.key === nextVNode.key), the fiber is reused (update path); otherwise the old subtree is scheduled for deletion and a new fiber is mounted (mount path).
  2. Children reconciliation. Dispatches to the unkeyed or keyed algorithm (below) depending on whether any child VNode carries a key.
  3. Flag bubbling. Each fiber accumulates flags (Placement, Update, Deletion, RefAttach, RefDetach, LayoutEffect, PassiveEffect); completeWork bubbles these into the parent's subtreeFlags so the commit phase can skip clean subtrees in O(1) per skipped subtree (§30).

Keyed Children Matching — the Five-Pass Algorithm

The children diff is the single most-studied component of every modern VDOM reconciler (Inferno's version, per Required Reading §5, is the reference for this five-pass shape):

Pass Name Action Stops when
1 Prefix scan Walk previous/new children in parallel from index 0; mark matching-key fibers "no move" First key mismatch
2 Suffix scan Walk from the end in parallel; mark matching-key fibers "no move" First key mismatch
3 Removal scan If new-children middle is empty, mark every previous-children middle fiber "delete" N/A — single pass
4 Insertion scan If previous-children middle is empty, mark every new-children middle vnode "insert" N/A — single pass
5 Middle reorder Build key→previous-index map; compute LIS over the new-middle's previous-index array; LIS members "no move", the rest "move or insert" N/A — single pass

Complexity: passes 1–4 are O(n); pass 5's LIS computation is O(n log n) (patience- sorting formulation). Total: O(n log n), matching ADR-09 (§9) and Levenshtein's edit-distance lineage (§5 Papers). Degenerate case: an adversarial input where every key appears in the middle in fully-reversed order still costs O(n log n) — the LIS of a reversed sequence has length 1, which is cheap to compute, not the worst case; the actual worst case for wall-clock cost is a middle with no shared keys at all (all delete + all insert, O(n) but with n DOM operations, §30).

Worked Example — Keyed Reorder

Previous children (keys): [A, B, C, D, E]. New children (keys): [A, C, B, D, F].

  1. Prefix scan: A matches at index 0 → "no move". Stop (index 1: B vs C mismatch).
  2. Suffix scan: D (previous index 3, new index 3) matches from the end → "no move". Stop (previous C vs new B mismatch going backward).
  3. Middles: previous [B, C] (indices 1–2), new [C, B, F] (indices 1–3, F is new).
  4. Key→previous-index map over previous middle: {B: 1, C: 2}.
  5. New middle's previous-index array: [C→2, B→1, F→-1] = [2, 1, -1]. LIS of [2, 1, -1] (ignoring -1 sentinels, which are always insertions): longest increasing run is length 1 (either [2] or [1]) — so one of B/C moves, the other one is the anchor F is a fresh mount (Placement, no previous fiber).

Result: A and D untouched; C retained as anchor, B moved after it, F mounted. Fixture: conformance/corpora/diff/keyed/reorder-with-insert.json.

Malformed-Input Example — Duplicate Keys

Input: previous [{key:"x"}, {key:"x"}] (a duplicate-key list — a common authoring bug, T3 §24). The key→previous-index map construction (pass 5) overwrites the first x entry with the second's index — first-match-wins is not the contract; last-write-wins during map construction is, so the second previous fiber is the one matched, silently discarding the first's identity. Dev-mode detects and warns (Encountered two children with the same key); production does not check (documented tradeoff, T3 §24). Fixture: conformance/corpora/diff/keyed/duplicate-key-warns.json.

Failure-Path Example — Suspense Throw During Reconciliation

A FunctionComponent fiber's render throws a Promise (not an Error) during beginWork. The reconciler's begin-work dispatch (§14.2) catches the thrown value, checks typeof thrown.then === "function", and — finding a thenable — walks the return chain looking for the nearest fiber tagged SuspenseComponent. That boundary's state transitions Mounted → Suspended (§19.6); its fallback VNode is reconciled and committed instead of the throwing subtree; a .then callback is attached to the promise that, on resolution, re-schedules the suspended subtree at its original lane. If no SuspenseComponent ancestor exists, the thrown promise propagates as an uncaught error to the root (I8 §7). Fixture: conformance/corpora/suspense/no-boundary-propagates-to-root.json.

13.6 Pitfalls

  • Extracting key/ref after freezing props leaks them as ordinary props to consumers — a Phase-1 defect that surfaces only much later, in Phase 2's key-based matching (§14.4), as an inexplicable "key changes every render" bug.
  • defaultProps on legacy class components (§11 ClassComponent) must be applied at element-creation time (inside jsx()), not at render time, or SSR (§20) and CSR compute different effective props for the same element.

13.7 Performance Concerns

jsx()/jsxs() are called once per element per render — at 100k elements this is the single hottest allocation site in the whole runtime (derivation 1, §34). Object-shape consistency (same key order, same hidden class in V8) is the concrete lever; a props object built via spread in inconsistent key order defeats V8's inline-cache optimization.

13.8 Edge Cases

  • jsx(type, props, key) where key is 0 (falsy but valid) must not be coerced to null.
  • A Symbol passed as type that is not one of the nine registered sentinels must throw InvalidElementType, not silently pass through to beginWork in Phase 2.
  • Non-serializable props values (functions, class instances) must round-trip identically in-memory; VNodes are never (de)serialized (§11 compat note), only host output is.

13.9 Failure Analysis

An InvalidElementType at the JSX boundary is always a build-time-catchable class of bug once TSC strict mode is clean (§13.4); a runtime occurrence means a value crossed an any boundary (e.g. a dynamically computed type from untyped JSON). Detection: the thrown error carries the offending type's typeof and a component-stack trace precursor to DevTools (full stack trace lands in Phase 10, §22). Containment: caught at the nearest Phase-7 error boundary once that phase lands; until then, propagates to the root (I8 §7).

13.10 Operational Notes

jsxDEV's source/self fields are the seed of the component-stack traces Phase 10's DevTools protocol (§22) will consume; keep their shape stable from this phase forward — changing it later is a breaking change to every dev-mode error message format.

14. Phase 2 — Reconciler Core: Fiber Tree & Keyed Diff

14.1 Objectives

Implement the fiber tree (§11 Fiber), the beginWork/completeWork render-phase walk, and the five-pass keyed-children diff (§8), all executing synchronously — the scheduler (§17) and its interruption semantics are explicitly out of scope until Phase 5; this phase proves the diff algorithm and fiber bookkeeping in isolation, matching P1 (§6: render phase pure) without yet exercising P9's pause/resume machinery.

14.2 Detailed Implementation Steps

Implement beginWork(current, workInProgress, renderLanes) dispatching on Fiber.tag (HostRoot, HostComponent, FunctionComponent, ClassComponent, Fragment, Portal — Suspense/ ErrorBoundary dispatch stubs land here but their state machines are Phase 7's, §19). Implement completeWork, bubbling flags into subtreeFlags bottom-up (I2 precursor, enabling Phase 3's commit-phase skip-clean-subtrees optimization, §30). Implement the children-diff dispatcher: unkeyed path (position-matched, ADR-09 §9 fallback) versus keyed path (the five-pass algorithm of §8, anchored to Levenshtein's edit-distance lineage, §5 Papers, and Inferno's reference implementation, §5 Reference Implementations). Implement the type-match test (§8) as the entry gate to both paths. Every Placement/Update/Deletion flag recorded here is read, not applied, until Phase 3's commit.

14.3 Deliverable

A <App/> fixture with a keyed 5-item list passes a full mount → keyed-reorder → re-mount cycle against nimbus-host-test, matching the §8 worked example (A,B,C,D,E → A,C,B,D,F) fiber-for-fiber (not just DOM-output-for-DOM-output).

14.4 Acceptance Criteria

  • diff/keyed and diff/unkeyed corpora (§10) pass at ≥ 99% (matches the Phase-11 conformance-bucket commitment, §23.1).
  • A 1,000-element list full shuffle produces a fiber-level move-list whose size is within 5% of the theoretical LIS-optimal move count (property test, ADR-09 §9).
  • Reconciliation of the 1,000-element shuffle completes in ≤ 5 ms synchronous compute time (M2 §30 precursor — scheduler-mediated timing lands in Phase 5).

14.6 Pitfalls

  • Copying React's full dual-buffer alternate machinery uncritically (Reference Implementations, §5) before re-deriving why it is needed at this scale over-engineers Phase 2; derive the need from I14 (§7) first.
  • The LIS middle-reorder pass (§8) is easy to get "almost right" — an off-by-one in the previous-index sentinel (-1 for unmatched) silently corrupts insert detection; the duplicate-key-warns fixture (§14.5) is the regression canary.
  • The fiber's return back-edge must never be walked by a naive recursive serializer (e.g. JSON.stringify in a debug log) — it is cyclic by construction.

14.7 Performance Concerns

The children-diff dispatcher's unkeyed/keyed branch decision is taken once per parent per render; misclassifying a mixed keyed/unkeyed sibling list (P5 §6 — undefined per spec, but must not crash) is the concrete edge to test. LIS computation via patience sorting (§8) must use binary search over the "pile tops" array, not a linear scan, to hold the O(n log n) bound (ADR-09 §9) — a linear-scan implementation silently degrades to O(n²) at scale and the bench_update_keyed.ts regression gate (M2 §30) is the only thing that catches it.

14.8 Edge Cases

  • A children array containing both keyed and unkeyed siblings (P5 §6 documents this as "each keyed item matched by key, contiguous unkeyed runs matched by position within the run" — an explicit, tested contract, not undefined behavior).
  • Reordering to an empty list and back (full unmount then full remount) must not leak fiber references (memory edge, cross-checked against M9 §30 in Phase 11).
  • A key that collides with a different previous fiber's key across a type change (same key, different type) is a fresh mount, not a reuse — type-match gates before key-match (§8 Reconciliation Algorithm, step 1).

14.9 Failure Analysis

A children-diff defect's blast radius is bounded to the parent fiber's subtree (the diff is local per §8's algorithm); detection is the conformance corpus's per-fixture pass/fail, not a global invariant violation. Recovery: since Phase 2 has no commit phase yet, "recovery" here means the next render recomputes from the (correct) previous fiber tree — there is no persisted corrupt state to unwind.

14.10 Operational Notes

Every fiber allocated in this phase carries the flags/subtreeFlags fields Phase 3's commit will consume; keep the FiberFlags bit layout stable from here forward (documented in docs/architecture/fiber.md) — it is the terminology-lock anchor (per the blueprint standard's naming-consistency rule) for the whole commit-phase design.

15. Phase 3 — Commit Phase & Host Adapter

15.1 Objectives

Implement the synchronous, indivisible commit phase (P2 §6, I2 §7) and the production HostAdapter DOM backend (P4 §6), turning Phase 2's fiber-level diff output into real mutations against a real document. This is the phase where the trust boundary between "the reconciler decided what changed" and "the host actually changed" is drawn concretely.

15.2 Detailed Implementation Steps

Implement the three-sub-pass commit ordering from §8's table (commitBeforeMutation → commitMutation → commitLayout, plus the deferred passive pass), each a forward depth-first walk filtered by flags (per-pass flag membership documented in §8). Implement nimbus-host-dom as the second HostAdapter implementation (P4, ADR-04 §9): attribute vs. property dispatch via a checked-in table (attribute.ts/property.ts, cross-browser quirks documented per Reference Implementations' snabbdom module-hook pattern, §5). Implement subtree-flag-skip in commitMutation: a fiber whose subtreeFlags carries none of Placement|Update|Deletion is skipped in O(1) (§30 elaborates the batching rationale). Wire refs (P12 §6): attach in commitLayout, detach during the Deletion walk of commitMutation.

15.3 Deliverable

The Phase-2 keyed-reorder fixture (§14.5) now produces observable DOM mutations in a JSDOM-backed Playwright page matching the fiber-level move list exactly — the first point in the build where "what the reconciler decided" and "what the user's screen shows" are verified to be the same thing.

15.4 Acceptance Criteria

  • render-trees and diff/* corpora (§10) pass against the DOM backend at ≥ 99%, matching their Phase-2 fiber-level pass rate exactly (cross-checking §14.4's numbers).
  • Commit-phase wall-clock for a 1,000-node full mount: ≤ 5 ms p95 (M1 §30).
  • Zero DOM mutations observed outside the commitMutation sub-pass window (asserted via a MutationObserver harness in the conformance runner) — the concrete test of I1/I2 (§7).

Fixture Purpose Expected Output

15.6 Pitfalls

  • Copying React's dual-buffering uncritically (flagged already in §14.6) resurfaces here as "which buffer does commitMutation read attributes from" — get the old/new props source wrong and commitUpdate diffs against stale data.
  • commitLayout's ref-attach must run after the host node exists in the tree, not before — a ref attached before commitMutation's insert sees a detached node.
  • Batching contiguous placements into a single DocumentFragment insert (§30) is a real perf win but silently breaks if the batching logic spans a Deletion-flagged sibling incorrectly, producing a visually-correct but ordering-wrong DOM (only caught by a full-tree structural diff, not an "is it visible" check).

15.7 Performance Concerns

The attribute-vs-property dispatch table (§15.2) is on the hot path of every commitUpdate call; a linear scan over "which category does this prop belong to" at 1,000 nodes × average 5 props/node = 5,000 lookups per commit — this table must be a Map/frozen-object lookup, not a switch re-derived per call (concrete instance of the general allocation/ lookup-cost concern, §30).

15.8 Edge Cases

  • SVG/MathML namespace handling: createElement must dispatch to the correct namespaced DOM API (createElementNS) — a bare createElement("svg") in an HTML document produces a non-functional node.
  • A commitMutation pass that throws partway through (e.g. a host-adapter bug) leaves the DOM in a partially-mutated state with no rollback — documented as FM-2 (§25), since P2's indivisibility is a design contract, not a transactional guarantee against adapter bugs.
  • Removing a node that has already been removed by a prior (buggy) direct DOM manipulation outside the runtime — the host adapter's removeChild must not throw on a NotFoundError-class failure; it logs and continues (documented boundary, not a runtime invariant).

15.9 Failure Analysis

A partial-commit crash (FM-2, §25) has a blast radius bounded to the subtree being mutated in that sub-pass, but its symptom (a visually broken tree) is global until the next successful commit. Detection: the MutationObserver harness (§15.4) plus a production-mode commitMutation try/catch that reports via a to-be-defined error channel (formalized fully once Phase 7's error-boundary machinery lands, §19) and marks the root for forced re-render. This is also where I11's re-render cap (§7) starts mattering: a commit-triggered crash-and-retry loop without the cap could hang the tab.

15.10 Operational Notes

Every commit emits a commit.durationMs sample (I2's telemetry, §7) tagged with sub-pass breakdown (beforeMutation/mutation/layout); this is the first real performance-observability surface in the build and the direct precursor to Phase 10's Profiler API (§22.2).

16. Phase 4 — Hooks & State Model

16.1 Objectives

Implement the full hooks dispatcher (useState, useReducer, useEffect, useLayoutEffect, useMemo, useCallback, useRef, useContext, useId, useInsertionEffect, useImperativeHandle, useDebugValue) against the positional per-fiber slot list (P3 §6, §11 Hook) established in Phase 2's fiber bookkeeping. useSyncExternalStore, useTransition, useDeferredValue are stubbed here and completed in Phase 5/9 (§17, §21) once lanes exist.

16.2 Detailed Implementation Steps

Implement the mount/update dispatcher swap (§5 Papers — Abramov/Alpert Hooks RFC): on mount, each hook call allocates a new Hook node appended to the fiber's memoizedState linked list; on update, the same call order walks the existing list, asserting positional identity (I3 §7). Implement useState as useReducer((s,a)=>a) per the canonical contract; implement the update queue as an append-only linked list replayed from last-committed state on each render (determinism requirement, I3 adjacent). Implement useEffect/useLayoutEffect's dependency-array shallow comparison via Object.is element-wise (P1/P2 §6 — effects fire only in commit, never during beginWork). Implement useContext as a return-chain walk to the nearest Provider fiber (P4-adjacent: context lookup stays inside the reconciler, no host involvement).

16.3 Deliverable

A counter component using useState + useEffect (mount-logs, cleanup-logs) passes a mount → three updates → unmount cycle against the DOM backend, with effect fire/cleanup order matching the two-pass model of §8's commit-ordering table exactly.

16.4 Acceptance Criteria

  • hooks/state, hooks/effect, hooks/memo, hooks/reducer corpora (§10) pass at ≥ 99% (Phase-11 commitment, §23.1).
  • A component calling 12 hooks in a stable order across 50 re-renders shows zero I3 violations (hook-order checksum, §7).
  • useMemo cache-hit rate on an unchanged-deps re-render: 100% (no factory re-invocation), verified by a call-count spy fixture.

16.6 Pitfalls

  • Out-of-order hook calls between renders are undefined in production (P3 §6); only Strict Mode (Phase 9, §21) catches them at dev-time — this phase must not add a production runtime check, or it silently reintroduces the "named hooks" cost the design explicitly rejected (ADR-04 §9).
  • useEffect's deps array uses Object.is, not deep equality — a fresh [a, b] literal on every render is not stably equal to the previous [a, b] as an array reference, but the hook compares element-wise, so this is correct; the pitfall is a naive implementation that compares the array reference itself instead of its elements.
  • useMemo must be documented as a perf hint, not a correctness guarantee (the runtime may discard cached values under memory pressure per the React-canonical contract, §5) — a consumer relying on it for identity stability (e.g. object identity gating a child's React.memo) has a latent bug this phase must flag in the docs, not silently "fix."

16.7 Performance Concerns

The hook linked-list walk on update is O(hooks-per-fiber), typically small (≤ 20); the concrete perf risk is a component that calls hooks in a loop producing thousands of slots — undocumented in React itself and equally undocumented (by design, P3) here: the runbook (§26) covers the diagnostic (a Hook list length outlier visible in DevTools, Phase 10). useMemo/useCallback recomputation cost is bounded by the factory function's own cost, outside this phase's control.

16.8 Edge Cases

  • A setState called during render (not inside an effect) — a reentrancy case caught by I11's consecutive-re-render cap (§7) once it exceeds 25 (T6 §24).
  • useEffect's cleanup running on every dependency change, not only on unmount — a common authoring confusion (an effect meant to "run once" needs an explicit empty deps array, not an omitted one, which instead runs after every render).
  • useContext reading a context with no ancestor Provider returns the context's default value — must not throw.

16.9 Failure Analysis

A hook-order violation (I3, §7) corrupts the wrong slot's state silently in production — there is no crash, only a state value that appears to belong to a different hook call. This is the single hardest-to-diagnose failure class in the whole runtime (FM-3, §25); detection in production is only possible via user-visible symptom reports, since there is no runtime check (P3 §6) — this is precisely why the ESLint plugin (Phase 10, §22) is mandatory tooling, not optional.

16.10 Operational Notes

Hook allocation count per fiber is exposed to DevTools (Phase 10, §22) as hooks.perFiberCount; this phase establishes the data shape DevTools will render as the "Hooks" panel per component, so the Hook.kind tag values (§11) are a terminology-lock surface — renaming a kind later breaks the DevTools protocol's backward compatibility (ADR-19 §9, Compatibility & Versioning §27).

17. Phase 5 — Fiber Scheduler: Lanes, Priority, Time-Slicing

17.1 Objectives

Implement the Scheduler (§11), the 31-bit Lanes bitmask (ADR-08 §9), and cooperative time-slicing via MessageChannel-based yielding, turning Phase 2's synchronous reconciler into an interruptible one. This is the phase that makes P9 (§6: concurrent rendering preserves invariants) buildable — Phase 9 (§21) only exercises the guarantee this phase establishes.

17.2 Detailed Implementation Steps

Implement the lane constants: SyncLane, InputContinuousLane, DefaultLane, TransitionLane ×16, RetryLane ×4, SelectiveHydrationLane, IdleLane, OffscreenLane (§8 lane-semantics table). Implement per-root active-lanes and pending-lanes masks; scheduleWork(root, lane, work) OR's the lane into pending and, if no tick is in flight, posts a MessageChannel message (Andrew Clark's Fiber-architecture write-up, §5 Papers, is the direct reference for why MessageChannel over setTimeout/requestIdleCallback/ requestAnimationFrame — each alternative either clamps to 4ms minimum, means "idle" not "soon," or is paint-aligned when post-paint is wanted). Implement shouldYield(): current time minus slice-start exceeds sliceMs (default 5, §4 System Constraints). Implement interruption: a higher-priority lane arriving mid-render discards the in-progress work-in-progress tree (P9 §6) and restarts at the new lane — no partial commit is ever produced (I9 §7 depends on this).

17.3 Deliverable

A benchmark harness (bench_concurrent.ts) demonstrating a 30ms-if-unsliced render completing across 6 × 5ms slices, interleaved with a simulated input handler that fires every frame with zero dropped input events.

17.4 Acceptance Criteria

  • Slice budget adherence: p99 ≤ 6 ms per slice (M10 §30), default sliceMs = 5.
  • A synthetic 10,000-item filter-as-you-type benchmark sustains 60fps (16.6 ms/frame, M5 §30) with zero dropped keystrokes across a 5-second run.
  • Lane-priority correctness: a SyncLane update issued mid-TransitionLane render interrupts and completes before the transition resumes, in 100% of 1,000 fuzz trials (ADR-08 §9).

17.5 Conformance Fixtures

Fixture Purpose Expected Output
concurrent/transitions/interrupt-by-sync.json priority preemption sync lane commits first
concurrent/transitions/discard-on-interrupt.json no partial commit (I9) 0 host mutations from discarded WIP tree
concurrent/deferred/slice-budget-respected.json time-slicing every slice ≤ sliceMs + 1ms tolerance

17.6 Pitfalls

  • flushSync(fn) runs fn and commits synchronously — overusing it defeats concurrent rendering's entire point; reserve it for input-handler synchronization needs (e.g. focus management before a state change), a documented anti-pattern otherwise (§17.9's list extends into Phase 9, §21.7).
  • A transition that completes successfully commits atomically at the end; there is no partial commit — an implementation that tries to "stream" a transition's commit incrementally violates I9 directly.
  • The 5ms slice budget is empirical (short enough to avoid input latency, long enough to amortize dispatch overhead, §5 Books — Grigorik's latency-budget reasoning); hard-coding it instead of exposing setSliceMs blocks embedders who need to tune it for a slower/faster host.

17.7 Performance Concerns

MessageChannel.postMessage's round-trip cost (post → macrotask queue → handler) is the scheduler's fixed per-yield overhead; a work loop that yields too eagerly (small sub-slice-budget fiber batches) pays this cost more than necessary — the concrete tuning lever is batching several small fibers' beginWork calls between shouldYield() checks rather than checking after every single fiber.

17.8 Edge Cases

  • Two TransitionLanes racing (16 available, ADR-08 §9): each keeps its own work-in-progress state; a starvation edge exists if 16 concurrent transitions are open simultaneously and a 17th is requested — documented as a scalability ceiling (§31), not a crash.
  • shouldYield() called with a clock that has been paused (e.g. a suspended browser tab) — the scheduler must use a monotonic clock source (performance.now()), not Date.now(), to avoid negative slice durations after tab resume.
  • A synchronous flushSync nested inside another flushSync — must not deadlock; the inner call reuses the outer's already-synchronous context (idempotent nesting).

17.9 Failure Analysis

Scheduler starvation (FM-8, §25) — a low-priority IdleLane update that never runs because higher-priority lanes keep preempting it — has no automatic recovery by design (idle priority means exactly "runs only when nothing else needs to"); detection is a DevTools Profiler (Phase 10, §22) view showing a lane's pending age exceeding a runbook threshold (docs/runbooks/slow-render.md).

17.10 Operational Notes

Every scheduler tick emits scheduler.sliceDurationMs, scheduler.activeLanesMask, and scheduler.interruptCount telemetry; these three counters are the primary signal Phase 10's Profiler consumes to render a lane-timeline view, and the primary signal an on-call engineer uses to diagnose a "the page feels janky" report (§26).

18. Phase 6 — Synthetic Event System

18.1 Objectives

Implement root-delegated synthetic event dispatch (P6 §6, ADR-05 §9): one native listener per tracked event type at the root container, event plugins translating native events to typed SyntheticEvents (§11), and portal-aware capture/target/bubble propagation that follows the fiber tree, not the DOM tree.

18.2 Detailed Implementation Steps

Implement the delegation registry (I6 §7: exactly one listener per event type per root). Implement the plugin contract (extractEvents, tagName, eventTypes) and the five plugins: pointer (mouse/touch/pointer unification per the W3C Pointer Events spec, §5 RFCs), keyboard, focus (synthesizing bubbling for natively-non-bubbling focus/blur), form (change/input cross-browser normalization), composition (IME state machine). Implement propagation: walk from the target fiber up to the root collecting fibers whose props carry the matching handler prop name; dispatch capture-phase root-to-target, then target, then bubble-phase target-to-root — critically, walking the fiber return chain (§11), not parentNode, which is what makes portal-aware dispatch possible (a click inside a createPortal target whose fiber-tree parent is elsewhere bubbles through that fiber parent, not through the DOM ancestor, T10 §24 documents the trust-boundary implication).

18.3 Deliverable

A conformance fixture demonstrating a click dispatched inside a portal's DOM subtree invokes the portal's fiber-tree ancestor's onClick handler, not any handler attached along the portal's actual DOM ancestor chain — the concrete, checkable proof of P6.

18.4 Acceptance Criteria

  • events/pointer, events/keyboard, events/form corpora (§10) pass at ≥ 99%; events/composition, events/focus at ≥ 95% (Phase-11 commitment, §23.1).
  • Event dispatch through a 100-fiber bubble path: ≤ 0.1 ms (M4 §30).

18.6 Pitfalls

  • Reusing native DOM bubble order instead of the fiber-tree order is the single most common reimplementation mistake (P6 §6); it is invisible until a portal is involved, since without portals the two orders coincide.
  • Passive listeners (touchstart/touchmove/wheel per the WHATWG spec, §5 RFCs) cannot call preventDefault — the synthetic event object must surface this constraint (a no-op preventDefault with a dev-mode warning), not silently swallow the call.
  • The change event on <input type="checkbox"> fires on every keystroke in some browsers' native implementations; the form plugin must normalize to fire only on actual value commit, or downstream useState updates thrash (Phase 4, §16) on every keypress.

18.7 Performance Concerns

The per-fiber event-handler lookup table is cached and invalidated once per commit (§30); a naive implementation that re-walks props on every dispatch instead of reading the cached table turns every click into an O(depth × props-scan) operation instead of O(depth). Contiguous handler collection during the bubble-order walk should short-circuit once stopPropagation() is called, avoiding wasted fiber-chain walks past the stop point.

18.8 Edge Cases

  • An event handler that throws mid-dispatch: dispatch must continue to remaining listeners in the chain (the canonical contract) while routing the thrown error to the nearest error boundary (Phase 7, §19) — a handler throw must not silently swallow sibling handlers' invocations.
  • setPointerCapture's host-side capture semantics are not interposed by the runtime; the synthetic event surface documents this as an explicit boundary, not a bug.
  • Wheel deltaMode differs between touch and mouse devices; the pointer plugin normalizes it — an un-normalized deltaMode produces scroll amounts off by 2–3 orders of magnitude on some devices.

18.9 Failure Analysis

A dispatch-order defect (native bubble order leaking through instead of fiber order) has a blast radius limited to portal-using subtrees but is a silent failure — no error is thrown, a handler simply never fires or fires in the wrong sequence. Detection: only the click-bubbles-through-portal fixture (§18.5) or a user bug report; there is no runtime assertion for this, since "wrong order" and "right order" both produce syntactically valid dispatch calls. This is documented in the runbook (§26) as the first thing to check when a portal-adjacent event handler "sometimes doesn't fire."

18.10 Operational Notes

Event-dispatch telemetry (events.dispatchDurationMs, tagged by event type) feeds the same Profiler surface as commit timing (§15.10); a spike in events.dispatchDurationMs for a specific event type is the operational signal for "someone attached an expensive handler at a shallow fiber that fires on every bubble pass," a documented pitfall class distinct from the render-side performance concerns of earlier phases.

19. Phase 7 — Suspense, Error Boundaries & Lazy

19.1 Objectives

Implement the Suspense state machine (Mounted/Suspended/Recovering, §8), the thrown-promise protocol (P7 §6, ADR-06 §9), the error-boundary state machine (Mounted/ Erroring/Recovered), and lazy() — the structured-control-flow layer for async-wait and failure that Phase 2's begin-work dispatch stubbed out (§14.2).

19.2 Detailed Implementation Steps

Implement the throw-catch protocol in beginWork: a caught value with a .then method is a suspension (walk return chain to nearest SuspenseComponent fiber, per §8's Failure-Path Example); a caught value without .then is an error (walk return chain to nearest fiber implementing getDerivedStateFromError/componentDidCatch, P8 §6). Implement the Suspense boundary's fallback-delay commit (I7 §7: 500ms default in transitions, 0ms outside — Sebastian Markbåge's concurrent-mode design notes, §5 Papers, motivate the delay as avoiding "flash of fallback" on fast-resolving suspensions). Implement lazy(() => import(...)) as a component wrapper that suspends until its dynamic import resolves. Implement error-boundary recovery: getDerivedStateFromError computes new state, componentDidCatch/onCaughtError reports, boundary re-renders with derived state; an error above the topmost boundary propagates to the root (I8 §7) and unmounts it.

19.3 Deliverable

Three fixtures passing together: a <Suspense fallback={<Spinner/>}> wrapping a lazy() component renders the spinner then the resolved component; an error boundary catches a thrown error from a deep descendant and renders its fallback; an uncaught error at the root triggers onUncaughtError and full unmount.

19.4 Acceptance Criteria

  • Suspense fallback commit delay: exactly 500 ms in a transition context, 0 ms outside one, verified against a fake-timer harness (I7 §7).
  • Error-boundary containment: 100% of thrown errors below a defined boundary are caught at that boundary, never propagating further (I8 §7, T6/T4 §24).
  • suspense and error-boundary corpora (§10) pass at ≥ 99% (Phase-11 commitment, §23.1).

19.6 Pitfalls

  • A suspended boundary must not commit its fallback synchronously inside a transition — the 500 ms delay (I7 §7) is the gate; committing immediately produces the "flash of fallback" UX defect the delay exists to prevent.
  • Error boundaries do not catch errors thrown in effects (useEffect/useLayoutEffect callbacks run after commit, outside the render/commit throw-catch window, §16) — such errors propagate to the root directly; a common author misconception this phase's docs must call out explicitly.
  • A lazy() component whose dynamic import fails surfaces the load error to the nearest error boundary, not the Suspense boundary's fallback — conflating the two silently hides load failures behind a permanent spinner (a T5-class symptom, §24).

19.7 Performance Concerns

The return-chain walk to find the nearest Suspense/error boundary is O(depth); at the System Constraints' documented tree-depth ceilings (§4) this is bounded but non-trivial for very deep trees — the walk is cached per-fiber-subtree only within a single render pass, not across renders, since boundary ancestry can change between renders (a component can be re-parented via conditional rendering).

19.8 Edge Cases

  • Nested Suspense boundaries: an outer boundary's fallback VNode can itself suspend, in which case the next-outer boundary (or root) handles it — no nesting-depth limit is enforced by design.
  • A boundary that suspends every render (a promise that immediately re-throws on retry) is documented as an authoring bug (T5 §24), not a runtime-detected condition — the runbook covers the diagnostic pattern.
  • An error boundary's getDerivedStateFromError itself throwing — escalates to the next enclosing boundary per §19.5's nested-boundary-failure-escalates fixture; if none exists, the root unmounts (I8 §7).

19.9 Failure Analysis

A stuck Suspense boundary (a promise that never resolves) has a blast radius limited to its own subtree — siblings and ancestors render normally (FM-6, §25). Detection: the Profiler (Phase 10, §22) surfaces a boundary's "suspended duration" metric; there is no automatic timeout by design (an indefinite loading state is sometimes intentional), documented as an explicit non-goal alongside the fallback-delay's fixed 500 ms (which governs commit timing, not resolution timing).

19.10 Operational Notes

Every suspend/resolve/error transition emits suspense.stateTransition and errorBoundary.stateTransition telemetry tagged with the boundary's component name (sourced from Phase 1's jsxDEV component-stack data, §13.10); these feed both the runbook diagnostics (docs/runbooks/) and the DevTools tree view (Phase 10, §22).

20. Phase 8 — SSR Streaming & Hydration

20.1 Objectives

Implement renderToString (synchronous, non-streaming), renderToReadableStream / renderToPipeableStream (streaming, suspense-aware, out-of-order flush, ADR-07 §9), and hydrateRoot's mismatch-recovering hydration matcher (P13 §6) — the layer that lets a server-rendered string become an interactive client tree with zero shared memory between server and client processes.

20.2 Detailed Implementation Steps

Implement renderToString: a synchronous string-producing walk that throws on any suspended boundary encountered (no streaming support, documented scope limit). Implement renderToReadableStream: the shell (everything above the first pending Suspense boundary) flushes immediately; a suspended boundary emits a placeholder marker and the boundary's resolved HTML streams out-of-order later, swapped into place via a small inline runtime script (Kleppmann's stream-processing framing, §5 Books, is the direct analogy — partial, out-of-order result delivery under a single logical stream). Implement the hydration matcher (§8's four-step walk: type match, attribute scan, event attach, child recurse); implement mismatch recovery (§8's Malformed-Input-adjacent failure path): mark the mismatched subtree, discard its SSR'd DOM, re-render from empty into that position, report via onRecoverableError (ADR-23 §9, P13 §6) — never a global bail-out. Implement XSS escaping (T7 §24): every string child is HTML-entity-escaped by default; dangerouslySetInnerHTML-equivalent is an explicit, separately-named, audited escape hatch.

20.3 Deliverable

A streaming-news fixture: a page with 5 posts behind independent Suspense boundaries streams the shell immediately, then each post's HTML arrives and swaps in out-of-order as its data resolves, and the client hydrates each boundary as its HTML arrives (streaming hydration) without waiting for the whole page.

20.4 Acceptance Criteria

  • Hydration of a 1,000-host-node tree: ≤ 10 ms (M3 §30).
  • A hydration mismatch on a data-now-style dynamic attribute is silently recovered (subtree re-rendered) with zero thrown exceptions and exactly one onRecoverableError call (I13 §7 adjacent).
  • The SSR-emitted XSS-escape fixture (ssr/xss-escape) passes at 100% — no injected <script> content survives renderToString output unescaped (T7 §24).

Fixture Purpose Expected Output

20.6 Pitfalls

  • useId values must be deterministic and identical between SSR and CSR given the same tree shape (fiber-path-derived, §16.7's useId section) — a non-deterministic ID scheme (e.g. Math.random()-seeded) makes every hydration a guaranteed mismatch.
  • A streaming render that errors after the shell has already flushed cannot "un-flush" — the error must be reported as a partial response (FM-11 §25); the runbook documents operator-facing recovery (serve a full error page on the next request, not a retroactive fix to the one in flight).
  • <input value="..."> in SSR output is the initial value only; on hydration the controlled-value contract takes over — treating the SSR value as authoritative post- hydration is a documented seam, not a bug to "fix" by re-reading the DOM.

20.7 Performance Concerns

Streaming hydration's per-boundary cost is amortized over network arrival time (§30): a 100-boundary page hydrates in 100 separate, time-sliced passes (Phase 5's scheduler, §17), so total hydration cost tracks the visible viewport's complexity, not the whole page's — the concrete lever is selective hydration (§20.8) promoting only the boundary the user actually interacts with.

20.8 Edge Cases

  • Selective hydration: a click on an unhydrated subtree promotes that subtree's hydration to InputContinuousLane (§17.1); the original click's native event cannot be replayed cleanly, so the runtime records its normalized data, calls preventDefault on the original, and dispatches a synthetic replay after hydration completes.
  • SVG/MathML serialization in renderToString must honor default-namespace rules — a naive string template omits xmlns attributes silently, producing invalid markup that renders differently across browsers.
  • A component whose SSR output and CSR output structurally diverge by an entire subtree (not just an attribute) triggers the largest-blast-radius mismatch recovery case; documented as expected-but-expensive, not a crash.

20.9 Failure Analysis

A shell-already-flushed streaming error (FM-11, §25) cannot be corrected within the same response; detection is the onError SSR-option callback (§11 SSROptions) firing after onShellReady; containment is operator-level (the embedding application's HTTP server decides whether to append an error boundary's fallback HTML or truncate the stream) — this is the one failure class this runtime documents but explicitly cannot auto-recover, since HTTP response headers/status are typically already committed by the time the shell flushed.

20.10 Operational Notes

onRecoverableError and onUncaughtError (§11 HydrateOptions) are the two channels an operator wires to their error-tracking system; a spike in recoverable-error rate for a specific component is the leading indicator of an SSR/CSR environment divergence (e.g. a locale or feature-flag mismatch between server and client), documented in docs/runbooks/hydration-mismatch.md.

21. Phase 9 — Concurrent Mode & Tearing Safety

21.1 Objectives

Complete useSyncExternalStore, useTransition, useDeferredValue (stubbed in Phase 4, §16), implement <Offscreen>, and implement dev-only Strict Mode (double-invocation, hook-order verification, effect-symmetry checks) — the layer that makes I9/I10 (§7) hold under real, adversarial concurrent usage, not just Phase 5's synthetic slicing benchmark.

21.2 Detailed Implementation Steps

Implement useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot): read getSnapshot() synchronously and inline within the render call (I10 §7 — MM7 §32); if the snapshot value observed at the end of the render differs from the value read at the start, the render bails and retries at the same lane rather than committing a torn result (Markbåge's concurrent-mode notes, §5 Papers, and Meijer-style reactive-consistency framing motivate synchronous-read-over-locking, since a lock is meaningless in a single-threaded JS host — the tearing problem is a snapshot problem, MM7 §32). Implement useTransition: startTransition(fn) marks updates inside fn at TransitionLane; isPending reflects in-flight status; an interrupting higher-priority update discards the transition's WIP tree (P9 §6). Implement useDeferredValue: renders the current value at the current lane and a deferred copy at a lower lane (IdleLane or an available TransitionLane) — necessarily rendering the subtree twice (documented cost, §21.7). Implement <Offscreen>: keeps a subtree mounted-but-unrendered (host-level display:none + state-preservation hook on the DOM backend). Implement Strict Mode: double-invoke function components and effect-mount callbacks in dev, verify hook-order checksums (I3 §7) across the two invocations, verify effect cleanup fires symmetrically on the synthetic remount.

21.3 Deliverable

The tearing conformance corpus (concurrent/tearing) passes at 100% against a property-tested Redux-style reference store under concurrent transition load — the strongest correctness claim in the entire runtime.

21.4 Acceptance Criteria

  • Tearing incidence: 0 events / 10,000 fuzz iterations (M11 §30, I10 §7) — this is a hard gate, not a target; any nonzero count blocks release (ADR-21 §9).
  • An <Offscreen> subtree retains component state (verified via a counter component) across 10 mount/hide/show cycles with zero state resets.
  • A Strict-Mode double-invocation run over the full examples/dashboard sample app produces zero false-positive impurity warnings.

21.6 Pitfalls

  • Tearing bugs are subtle by nature — property-testing against a Redux-style reference store (not a hand-picked example) is the only reliable way to surface them; a hand-written "looks fine" test suite is documented as insufficient (this is why ADR-21's fuzzing choice, §9, is load-bearing specifically for this phase).
  • useDeferredValue is not free: the runtime renders the subtree twice per meaningful input change (current value + deferred value) — using it for a cheap subtree is a documented anti-pattern that wastes the mechanism's benefit.
  • Offscreen requires the host adapter to support hide/show semantics explicitly; assuming display:none alone preserves component state without an explicit state-preservation hook in the DOM backend (§15) is a common reimplementation mistake — CSS visibility alone says nothing about the fiber tree's lifecycle.

21.7 Performance Concerns

useDeferredValue's double-render cost (§21.6) compounds with tree size — reserved only for expensive subtrees per the documented guidance; flushSync overuse (flagged already in §17.6) resurfaces here as a concurrent-mode-defeating anti-pattern specifically because it forces every subsequent transition to wait behind a synchronous commit. Strict Mode's double-invocation doubles dev-mode render cost across the board — acceptable only because it is fully stripped from production (P10 §6, T11 §24).

21.8 Edge Cases

  • 16 concurrent TransitionLanes in flight simultaneously with a 17th requested — the scalability ceiling documented in §17.8 and elaborated in §31; the 17th transition queues behind the oldest completing one.
  • A useSyncExternalStore subscription that fires synchronously during its own getSnapshot() call (a reentrant store) — the runtime must not deadlock; documented as the store implementation's responsibility, not the hook's.
  • Strict Mode's double-invocation interacting with a component that has genuine (not accidental) side effects in render — the double-invoke deliberately surfaces this as a bug (P1 §6 violation) rather than working around it.

21.9 Failure Analysis

A tearing event (FM-5, §25) — two parts of the tree observing different values of the same external store within one committed render — has an unbounded blast radius (any consumer of the torn store) and is, by construction, supposed to be impossible after this phase (I10 §7); detection is exclusively the fuzz corpus (§21.5) since production has no runtime tearing-detector (that would itself require locking, the exact mechanism rejected by design, MM7 §32). A tearing report in production is treated as a Sev-1 regression against M11 (§30), not a routine bug.

21.10 Operational Notes

concurrent.tornRenderCount and store.tornReadCount (I9/I10 telemetry, §7) are wired to CI as hard release gates (§29), not just dashboards — a nonzero value on the perf.yml workflow fails the build. This is the one telemetry pair in the whole runtime with a zero-tolerance policy.

30. Performance Engineering

Methodology. nimbus-bench (ADR-17 §9) runs each benchmark against per-host checked-in baselines; a regression beyond a tolerance band fails perf.yml (§29). Allocation analysis. §30's fiber/hook/VNode allocation breakdown (below) is the profiling methodology's primary lens — heap snapshots are diffed per commit, not just per test run. Lock analysis. N/A in the traditional sense (single-threaded JS host); the analogous concern is lane contention (§17.8), profiled via scheduler.activeLanesMask history. Cache analysis. V8 hidden-class consistency for VNode/Fiber shapes (§13.7) is profiled via --trace-maps in dev builds. Syscall analysis. N/A for the DOM backend; relevant only to the deferred native backend (§37). Tail-latency analysis. p95/p99 tracked separately for every M-target below, since a p50-only view hides the exact slice-budget-overrun class of bug (§17.9).

Render-Phase Allocations

The fiber tree is the largest allocation: ~30 fields per fiber, ~200 B each (§4, §34 derivation 1); reused via the current/alternate pair (§11) so steady state allocates one alternate per dirty fiber, not one per render. The hook list is second-largest: one slot per hook call, allocated on mount, reused on update (§16.2). The VNode tree is third-largest and fully transient — one VNode per jsx() call (§13.7), discarded once consumed by beginWork.

Commit-Phase Efficiency

commitMutation walks the subtreeFlags bitmap to skip clean subtrees in O(1) per skipped subtree (§15.2). Contiguous placements batch into a single DocumentFragment insert; contiguous deletions batch into one removal pass — the concrete mechanism behind M1/M2's 5 ms targets below.

Event Dispatch

The per-fiber handler lookup table is cached and invalidated once per commit (§18.7); a 100-fiber bubble dispatch walks the chain once, collecting handlers, dispatching in a single pass — the mechanism behind M4.

Hydration

Streaming hydration's per-boundary cost is amortized over network arrival (§20.7); total hydration cost tracks visible-viewport complexity, not whole-page complexity, via selective hydration (§20.8).

Memory Profile

A 100k-element tree consumes ≈50 MB of fibers + hooks (§34 derivation 1); bench_memory.ts runs the canonical 10k-item TodoMVC-style scenario producing a heap-snapshot diff per commit, the input to M8/M9 below.

Tracing

performance.mark markers at every phase boundary (render start/end, commit sub-pass boundaries, effect-fire) feed the DevTools Profiler's flamegraph (§22.2) directly — no separate tracing format is maintained.

31. Scalability Analysis

Constant regardless of scale. Native listener count (I6 §7 — 20 tracked event types ⇒ 20 listeners at any tree size, derivation 10 §34); scheduler slice budget (5 ms, fixed regardless of tree size — larger trees take more slices, not longer slices). Grows linearly, O(n). Fiber/hook/VNode memory with node count (§34 derivation 1); initial mount cost with node count (M1 scales linearly past the 1,000-node benchmark point). Grows O(n log n). Keyed-children diff cost with children-list length (§8, ADR-09 §9) — the deliberate trade against Zhang-Shasha's O(n³) optimal bound (§5 Papers).

Named bottlenecks, in order:

  1. Commit-phase DOM mutation batching (§30) — the first ceiling hit at scale; a tree with a very high mutation rate (not just size) saturates commitMutation's batching before the diff itself becomes the bottleneck.
  2. The LIS-keyed diff's O(n log n) pass (§8) — the second ceiling, reached on very long keyed sibling lists (tens of thousands of items in one list, distinct from tree depth).
  3. Concurrent transition-lane exhaustion (§17.8, §21.8) — 16 simultaneous transitions is a hard ceiling; the 17th queues.
  4. Hydration's per-boundary time-slicing (§20.7) — bounded by network arrival rate for streaming SSR, not by the runtime's own compute.

Horizontal/vertical scaling. The runtime itself does not scale horizontally (it is a per-root, per-tab library, P14/P15 §6); "scaling" here means scaling tree size and update rate within one root. Vertical scaling (a faster CPU) directly improves M1–M5 linearly; it does not change the O(n log n) asymptotic shape of the keyed diff.

Sharding/partitioning. Multiple independent roots (P14 §6) are the closest analogue to partitioning — a micro-frontend architecture with several createRoot instances shares only the scheduler singleton (message-passing coordinated, P14), not fiber-tree state.

Coordination overhead. Cross-root scheduler coordination costs one message-pass per cross-root priority decision (§11 Scheduler); negligible compared to any single root's own render cost at realistic root counts (single digits to low tens per page).

Practical ceiling and levers beyond it. The practical ceiling is a single root's tree size beyond which even time-sliced rendering cannot keep the first paint interactive (roughly the 1,000,000-fiber constraint of §4, driven by heap, not algorithm). The lever beyond it is virtualization at the application level (windowing — only rendering the visible viewport's subtree, as examples/data-table demonstrates, §20.3) — a technique the runtime enables but does not itself implement, since it is an application-level, not a reconciler-level, concern.

React made the opposite bundle-size trade deliberately: the concurrent-mode machinery and the full feature surface (Server Components, full Suspense data-fetching integration) cost 5× our bundle target because React optimizes for framework-scale ecosystem compatibility, a niche where our smaller, focused runtime does not compete.

We reject this model as our primary architecture (Alternative Architectures §36 elaborates why) because the coarse-grained re-render model is the one this project exists to teach (§2), but the contrast is the clearest available lens on why React-family frameworks made the choices they did.

34. Back-of-Envelope Capacity Model

Every number below is derived from the §4 System Constraints table, formula shown.

  1. Resident memory, 100k-node tree (chains to M8, §30). Fibers: 100,000 × 200 B = 20 MB. Alternates (worst-case fully-dirty steady state): +20 MB. Hook slots (avg 3 hooks/component × ≈40 B/slot × 100,000 components): +12 MB. Total ≈ 52 MB, matching the ≤ 50 MB target (M8) within rounding — the derivation that justifies the target, not an independently asserted number.
  2. Keyed full-shuffle diff cost, 1,000 items (chains to M2). LIS computation: 1,000 × log₂(1,000) ≈ 10,000 unit ops × ≈0.3 ns/op ≈ 3 µs pure compute. Per-node property diff: 1,000 × ≈2 µs ≈ 2 ms. DOM mutation batching: ≈1–2 ms. Total ≈ 3–4 ms, under the 5 ms p95 target (M2) with headroom for GC pauses.
  3. Event dispatch cost, 100-fiber bubble (chains to M4). 100 fibers × ≈1 µs/fiber (handler-map lookup + presence check) = 100 µs = 0.1 ms, exactly the M4 target — this is the target derived directly from the mechanism, not rounded to a nice number.
  4. Time-slicing throughput. Frame budget 16.6 ms − paint/input reserve ≈ 3 ms ≈ 13.6 ms available; at a 5 ms slice, ≈ 2–3 slices/frame achievable before paint must occur — a 30 ms unsliced render becomes 6 × 5ms slices ≈ 2–3 frames of wall-clock work interleaved with input handling, matching the M10/M5 pairing (§30).
  5. Bundle parse cost. 8 KB gzip ≈ 24 KB raw (≈3× typical JS gzip ratio) → V8 parse+ compile ≈ 1 ms per 10 KB on a mid-tier mobile CPU ≈ 2.4 ms parse time — small relative to M1's 5 ms render budget, confirming bundle size is not the dominant startup cost.
  6. Hydration cost, 1,000 host nodes (chains to M3). 1,000 nodes × ≈10 µs/node (type + attribute match, §8 hydration-matcher walk) = 10 ms, exactly the M3 target.
  7. Concurrent transition memory overhead. 16 max transition lanes (ADR-08 §9) × an assumed 500-fiber average transition payload × 200 B/fiber = 1.6 MB worst-case additional peak memory from fully-saturated concurrent transitions — small relative to the 52 MB baseline (derivation 1), confirming lanes are cheap relative to tree size.
  8. Startup-time extrapolation. p95 startup for 1,000 nodes is 10 ms (Phase 3 measured, §15.4); linearly extrapolated to 10,000 nodes ≈ 100 ms raw, but bounded to remain interactive by scheduler slicing (derivation 4) into ≈ 20 slices of 5 ms interleaved with paint — the concrete reason time-slicing exists at all past the 1,000-node scale.
  9. Delegation savings at scale. Without root delegation (rejecting ADR-05, §9), a 100,000-node tree with an average of 2 event handlers/node would require 200,000 native listeners; with delegation, 20 tracked event types ⇒ 20 total listeners — a 10,000× reduction at this scale, the concrete number behind P6's justification (§6).
  10. Suspense fallback-delay budget. At the default 500 ms delay (I7 §7) inside a transition, and a target 60fps (16.6 ms/frame, M5), the delay spans ≈ 30 frames — long enough that a resolving-within-one-frame data dependency never flashes a fallback at all, the concrete justification for 500 ms over a smaller value.

                                   direct DOM write (no diff step)

Regime where it wins: highly dynamic, small-surface-area UIs (a live trading ticker, a collaborative cursor overlay) where even an O(n log n) diff is measurable overhead relative to a compiler-derived direct write. Real system: SolidJS. Rejected because: this project's teaching goal (§2) is specifically the coarse-grained re-render + diff model and its scheduler; adopting signals would mean building a different system entirely, not a variant of this one (also elaborated in §33's SolidJS row).

2. Non-interruptible stack reconciler (pre-Fiber).

render(root) ──recursive call stack──▶ children ──▶ grandchildren ──▶ …
              (no pause point; unwinds only on completion)

Regime where it wins: fully static or server-only rendering where no interruption is ever needed (a build-time SSG pass, or renderToString's own internal walk, §20.2, which is implemented this way deliberately since it never needs to yield). Real system: React ≤15 (and Elm's runtime, which has no time-slicing concept at all). Rejected as the primary architecture because it cannot support Phase 5's time-slicing (§17) or Phase 9's concurrent mode (§21) — a large tree update would block the main thread for the tree's full render duration with no escape hatch (ADR-03 §9).

3. Shadow-DOM-first templating (no synthetic event system).

Tagged template ──▶ compiled template diffing (directives) ──▶ native Shadow DOM
                                                    │
                                          native event listeners per node

Regime where it wins: web-components-first design systems where encapsulation via native Shadow DOM boundaries is the primary goal, not cross-target host abstraction. Real system: Lit. Rejected because: nimbus needs the HostAdapter trait's cross-target abstraction (P4 §6, the DOM/test-renderer/deferred-native split) and portal-aware synthetic event propagation (§18) that a native-Shadow-DOM-first design does not need and does not provide.

4. Compile-time reactivity (no runtime reconciler at all).

Component source ──compiler pass──▶ surgical, per-binding DOM update instructions
                                     (reconciler eliminated at compile time)

Regime where it wins: bundle-size-critical, structurally-static component trees where the compiler can fully determine update sites ahead of time. Real system: Svelte (compiled mode). Rejected because: nimbus must support dynamic, runtime-composed JSX trees (arbitrary third-party components composed at runtime, conditional rendering shapes unknown at compile time) — the compile-time-elimination trade only holds when the component graph is knowable statically, which contradicts the "any composition of any components" scope this project targets (§1).

38. Glossary

  • Alternate. The work-in-progress copy of a fiber, paired with the current fiber via the alternate pointer (§11).
  • Beginwork. The render-phase function that produces a fiber's children from its VNode (§14.2).
  • Commit phase. The synchronous, side-effect-bearing phase following a successful render (§8, §15).
  • Completework. The render-phase function that bubbles subtree flags bottom-up once a fiber's children are done (§14.2).
  • Concurrent rendering. Rendering that can be interrupted and resumed without committing a partial result (§21).
  • Deferred value. A lower-priority copy of a value rendered via useDeferredValue (§16.9, §21.2).
  • Delegation. Root-level, single-listener-per-event-type native event registration (§18.2).
  • Effect. A side effect scheduled by useEffect or useLayoutEffect, fired in the commit phase (§16.3).
  • Error boundary. A component catching descendant render/commit errors via getDerivedStateFromError/componentDidCatch (§19.2).
  • Fiber. A typed work-unit; one per VNode per render pass (§11).
  • Fiber tag. The enum discriminating a fiber's kind (HostRoot, HostComponent, FunctionComponent, etc., §14.2).
  • Flags. A per-fiber bitmask recording pending commit-phase work (Placement, Update, Deletion, etc., §8).
  • Fragment. A VNode wrapper emitting no host node (§13.2).
  • Hook. A per-fiber, positional slot backing a hooks-API call (§11, §16).
  • Hydration. Client-side attachment of event listeners to SSR'd HTML without re-rendering matched nodes (§20.2).
  • Lane. A single bit in the 31-bit priority mask; multiple lanes may be active simultaneously (§11, §17.1).
  • LIS (Longest Increasing Subsequence). The subproblem solved during the keyed-diff's middle-reorder pass to identify fibers that need not move (§8).
  • Mismatch recovery. The local, subtree-scoped re-render triggered when SSR and CSR output diverge during hydration (§20.2, P13 §6).
  • Offscreen. A boundary keeping a subtree mounted but unrendered (§21.2).
  • Passive effect. A useEffect-scheduled effect fired asynchronously after paint (§8 commit-ordering table).
  • Portal. A VNode rendering into a DOM node other than its parent's host, while retaining fiber-tree event-propagation ancestry (§18.2).
  • Reconciler. The algorithm diffing the previous fiber tree against a new VNode tree (§8, §14).
  • Render phase. The pure, restartable phase producing a work-in-progress fiber tree (§8, §14).
  • Root. The top of a fiber tree, constructed by createRoot/hydrateRoot (§11).
  • Scheduler. The priority-lane scheduler driving the cooperative work loop (§11, §17).
  • Selective hydration. Promoting an unhydrated subtree's hydration priority in response to a user interaction (§20.8).
  • Sentinel. A registered symbol type (Fragment, Portal, Suspense, etc.) distinguishing non-component/non-intrinsic VNode kinds (§13.2).
  • Slice (time-slice). A bounded quantum of render-phase work between yield checks, default 5 ms (§17.2).
  • Strict Mode. The dev-only double-invocation and hook-order verification mode (§21.2).
  • Suspense. A boundary rendering a fallback while a descendant's thrown promise is pending (§19.2).
  • Synthetic event. A normalized, non-pooled event object dispatched in fiber-tree order (§11, §18.2).
  • Tearing. Two parts of a tree observing different values of the same external store within one committed render (§21.1, MM7 §32).
  • Transition. A state update explicitly marked non-urgent via startTransition (§16.9, §17.4, §21.2).
  • VNode. A virtual-DOM node; the immutable, frozen input to the reconciler (§11, §13.2).
  • Work-in-progress (WIP) tree. The off-tree fiber tree being constructed during an in-flight render, discarded if interrupted (§8 Fiber Work-Loop State Machine).
  • Workloop. The scheduler-driven loop calling beginWork/completeWork across fibers, checking shouldYield() between them (§17.2).
