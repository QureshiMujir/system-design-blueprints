Decisions (§9) · 24 ADRs

ADR-01

Source language

Chosen

TypeScript 5.4+

Rejected

Plain JS; ReScript/OCaml-to-JS

When the rejected choice is right

Plain JS wins for a throwaway prototype with no type-safety budget

Why: Discriminated-union checking on VNode/Fiber.tag is load-bearing (P4 §6)

ADR-02

Test/native-host language

Chosen

Rust

Rejected

TypeScript throughout

When the rejected choice is right

TS wins if no native-embedding target ever materializes (§37)

Why: FFI/determinism boundary for conformance oracle and deferred native backend

ADR-03

Reconciliation architecture

Chosen

Fiber (pausable work-unit tree)

Rejected

Stack reconciler (React ≤15 style)

When the rejected choice is right

Stack reconciler wins for a fully static, non-interactive render (e.g. a build-time SSG pass with no interruption need)

Why: Time-slicing (§17) requires pause/resume; stack reconciler cannot

ADR-04

Hooks model

Chosen

Positional per-fiber slots

Rejected

Named/keyed hooks

When the rejected choice is right

Named hooks win in a language with first-class effect handlers (e.g. OCaml 5 effects) where naming is unambiguous

Why: Positional composes without name collisions across custom hooks

ADR-05

Event dispatch

Chosen

Root-delegated synthetic events

Rejected

Native per-node listeners

When the rejected choice is right

Native listeners win for a handful of static, non-portal DOM nodes with no delegation benefit (e.g. a single top-level <canvas> widget)

Why: O(1) listener count (I6 §7); portal-aware bubble order

ADR-06

Suspense mechanism

Chosen

Thrown promise

Rejected

Callback/props-based loading state

When the rejected choice is right

Callback-based loading wins when the host language has no exception-as-control-flow idiom (e.g. Go-style explicit error returns)

Why: Composes with any async data source with zero API surface

ADR-07

SSR streaming

Chosen

renderToReadableStream, suspense-aware out-of-order flush

Rejected

Synchronous renderToString only

When the rejected choice is right

Synchronous-only wins for pages with no async boundaries at all, where streaming adds protocol overhead for no benefit

Why: Time-to-first-byte independent of slowest data dependency

ADR-08

Concurrent priority model

Chosen

Bitmask of lanes

Rejected

Single priority integer/queue

When the rejected choice is right

A single priority integer wins in a scheduler with ≤3 fixed priority classes and no need for independent concurrent transitions

Why: Expresses "A > B and both < input" without total ordering collapse

ADR-09

Keyed children diff

Chosen

LIS-based O(n log n) heuristic

Rejected

Zhang-Shasha optimal tree-edit-distance O(n³)

When the rejected choice is right

Optimal tree-edit-distance wins for small, deeply-nested trees where minimal-move-count matters more than diff speed (e.g. a diagram-editor's undo-tree)

Why: Optimality not worth cubic cost at UI-scale trees (§5 Papers)

ADR-10

Effect commit passes

Chosen

Two-pass (layout sync, passive async)

Rejected

Single synchronous effect pass

When the rejected choice is right

Single-pass wins in a non-interactive/off-screen render target where paint timing is irrelevant (e.g. server-only string rendering)

Why: useLayoutEffect needs pre-paint DOM reads; useEffect must not block paint

ADR-11

Strict Mode

Chosen

Dev-only double-invocation

Rejected

Always-on double-invocation

When the rejected choice is right

Always-on wins in a CI-only "impurity fuzz" build variant used purely for pre-release auditing

Why: Doubles render+effect cost; unacceptable in production

ADR-12

Cross-root external state

Chosen

useSyncExternalStore

Rejected

Ad-hoc subscription hooks per library

When the rejected choice is right

Ad-hoc subscriptions win for a single-root app with no concurrent-mode usage at all

Why: Tearing prevention requires one synchronous-read contract, not N incompatible ones

ADR-13

License

Chosen

Apache-2.0

Rejected

MIT

When the rejected choice is right

MIT wins for a tiny, no-patent-risk utility library with adoption friction from Apache's extra clauses

Why: Apache's explicit patent grant matches the React ecosystem's norm

ADR-14

Package format

Chosen

Dual ESM + CJS, sub-path exports

Rejected

ESM-only

When the rejected choice is right

ESM-only wins once the ecosystem's CJS long tail is provably gone (a future ADR would flip this)

ADR-15

Build tool

Chosen

esbuild (prod) + tsup (dev)

Rejected

Rollup-only; Webpack

Rollup wins when highly custom plugin-chain transforms are required that esbuild's plugin API can't express

Test tooling

Jest wins in a codebase already standardized on Jest with no Vite migration planned

Benchmark harness

Chosen

criterion-style with per-host checked-in baselines

When the rejected choice is right

Ad-hoc timing wins for a one-time exploratory perf spike with no CI-gating need

ADR-18

Lint enforcement

Chosen

nimbus-eslint-plugin (rules-of-hooks, exhaustive-deps)

Rejected

No linter; runtime dev-warnings only

When the rejected choice is right

Runtime-only warnings win for a single-developer prototype where CI lint gating is not yet set up

Why: Positional hooks are unenforceable by the type system (P3 §6); static analysis is the only pre-merge gate

ADR-19

DevTools protocol

Chosen

React DevTools v4-compatible wire protocol

Rejected

Bespoke DevTools extension

When the rejected choice is right

A bespoke extension wins once the wire protocol's version drift (T11 §24) becomes the bigger cost

Why: Riding the existing extension's UX is far cheaper than building a new one

ADR-20

Source authoring

Chosen

Plain TS in the runtime; JSX only in consumer code

Rejected

JSX inside the runtime itself

When the rejected choice is right

JSX-in-runtime wins if the runtime's own build pipeline can be proven fully independent of that transform (rare, so rejected here)

Why: Avoids a cyclic bootstrap dependency between the runtime and its own JSX transform

ADR-21

Fuzzing

Chosen

@fast-check/jest property-based fuzzing with custom corpora

Rejected

Hand-written edge-case tests only

When the rejected choice is right

Hand-written tests win for a fixed, fully-enumerable input space (not the case here — trees are unbounded)

Why: Pathological tree-diff/hook-sequence inputs are found by property search, not by hand

ADR-22

Test-renderer host mocking

Chosen

No global window mocks; explicit HostAdapter implementation

Rejected

jsdom-based implicit globals

When the rejected choice is right

jsdom mocking wins for testing DOM-backend-specific quirks (attribute vs. property tables) that the abstract host can't express

Why: The test renderer's contract must be the same trait every real backend implements (P4 §6)

ADR-23

Hydration mismatch reporting

Chosen

Structured onRecoverableError channel

Rejected

Silent recovery, no reporting

When the rejected choice is right

Silent-only wins only in a throwaway demo with no observability need, where the reporting channel's own overhead is unjustified

Why: Silent recovery hides real bugs from developers (P13 §6)

ADR-24

Test-only helpers

Chosen

act() lives in a separate testing package, not the runtime

Rejected

act() shipped in the core runtime

When the rejected choice is right

Bundling act() in-core wins for a single-package "batteries included" distribution model, at a bundle-size cost we reject

Why: Runtime should not carry test-only code paths into production bundles (M6/M7 §30)

36. Alternative Architectures (Roads Not Taken)

1. Fine-grained reactive signals (no VDOM diff).

Component fn ──creates──▶ Signal(s) ──tracked-by──▶ Compiled effect graph
                                            │
                                   direct DOM write (no diff step)

Regime where it wins: highly dynamic, small-surface-area UIs (a live trading ticker, a collaborative cursor overlay) where even an O(n log n) diff is measurable overhead relative to a compiler-derived direct write. Real system: SolidJS. Rejected because: this project's teaching goal (§2) is specifically the coarse-grained re-render + diff model and its scheduler; adopting signals would mean building a different system entirely, not a variant of this one (also elaborated in §33's SolidJS row).

2. Non-interruptible stack reconciler (pre-Fiber).

render(root) ──recursive call stack──▶ children ──▶ grandchildren ──▶ …
              (no pause point; unwinds only on completion)

Regime where it wins: fully static or server-only rendering where no interruption is ever needed (a build-time SSG pass, or renderToString's own internal walk, §20.2, which is implemented this way deliberately since it never needs to yield). Real system: React ≤15 (and Elm's runtime, which has no time-slicing concept at all). Rejected as the primary architecture because it cannot support Phase 5's time-slicing (§17) or Phase 9's concurrent mode (§21) — a large tree update would block the main thread for the tree's full render duration with no escape hatch (ADR-03 §9).

3. Shadow-DOM-first templating (no synthetic event system).

Tagged template ──▶ compiled template diffing (directives) ──▶ native Shadow DOM
                                                    │
                                          native event listeners per node

Regime where it wins: web-components-first design systems where encapsulation via native Shadow DOM boundaries is the primary goal, not cross-target host abstraction. Real system: Lit. Rejected because: nimbus needs the HostAdapter trait's cross-target abstraction (P4 §6, the DOM/test-renderer/deferred-native split) and portal-aware synthetic event propagation (§18) that a native-Shadow-DOM-first design does not need and does not provide.

4. Compile-time reactivity (no runtime reconciler at all).

Component source ──compiler pass──▶ surgical, per-binding DOM update instructions
                                     (reconciler eliminated at compile time)

Regime where it wins: bundle-size-critical, structurally-static component trees where the compiler can fully determine update sites ahead of time. Real system: Svelte (compiled mode). Rejected because: nimbus must support dynamic, runtime-composed JSX trees (arbitrary third-party components composed at runtime, conditional rendering shapes unknown at compile time) — the compile-time-elimination trade only holds when the component graph is knowable statically, which contradicts the "any composition of any components" scope this project targets (§1).
