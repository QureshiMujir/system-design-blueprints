Public API. The only surface an embedding application imports; every function is a thin entry into the reconciler. VNode Model + JSX Runtime. The vocabulary: a frozen, discriminated-union tree produced fresh on every render call; never mutated in place. Reconciler. The render-phase engine; pure and restartable (P1 §6); diffs the previous committed fiber tree against the new VNode tree using the LIS-keyed heuristic (§8). Hooks. A per-fiber, call-order-indexed slot list threaded through beginWork invocations of function components; the positional contract (P3 §6, MM3 §32). Scheduler. Owns the lane bitmask, the 5ms time-slice budget, and the yield-to-host mechanism; the sole concurrency boundary in the diagram — everything left of it may pause. Suspense/Error Boundary. Structured control flow for async-wait and failure, expressed as thrown values, not callbacks (P7/P8 §6). Commit Phase. The only place side effects happen; synchronous and indivisible (P2 §6) — the persistence boundary where host mutations become observable. Host Adapter. The protocol boundary: the reconciler never imports the DOM directly (P4 §6); the DOM backend and the deterministic test renderer are two implementations of one trait. Event System. Delegates at the root; portal-aware, independent of native DOM bubble order (P6 §6). SSR + Hydration. Produces and consumes the wire format that lets a server-rendered string become an interactive client tree without a full re-render. Concurrent Mode. The layer that makes "no visible half-finished render" (I9 §7) hold even when rendering is interruptible. Dev Tools. Entirely compiled out of production bundles (T11 §24, ADR-19 §9).

8. Domain Model

VNode Schema (the AST the reconciler consumes)

VNode
 ├─ $$typeof: brand              # Symbol.for("nimbus.element") — distinguishes from plain objects
 ├─ type: string | Component | ClassComponent | Sentinel
 │        Sentinel ∈ {Fragment, Portal, Suspense, ErrorBoundary, Profiler,
 │                     StrictMode, Memo, ForwardRef, Lazy}
 ├─ key: string | number | null   # extracted from props before freeze (P5, I5)
 ├─ ref: RefObject | RefCallback | null
 └─ props: frozen record          # children live at props.children

A VNode tree is produced fresh, bottom-up, on every render call (P1 §6); it is never diffed against itself — it is always diffed against the previous fiber tree, not a previous VNode tree (the fiber tree is the memory of "what happened last time").

Reconciliation Algorithm (named, not coded)

Reconciliation is a two-phase walk over a (currentFiber, nextVNode) pair, producing a workInProgressFiber:

  1. Type-match test. If currentFiber.type === nextVNode.type (and, for keyed nodes, currentFiber.key === nextVNode.key), the fiber is reused (update path); otherwise the old subtree is scheduled for deletion and a new fiber is mounted (mount path).
  2. Children reconciliation. Dispatches to the unkeyed or keyed algorithm (below) depending on whether any child VNode carries a key.
  3. Flag bubbling. Each fiber accumulates flags (Placement, Update, Deletion, RefAttach, RefDetach, LayoutEffect, PassiveEffect); completeWork bubbles these into the parent's subtreeFlags so the commit phase can skip clean subtrees in O(1) per skipped subtree (§30).

Keyed Children Matching — the Five-Pass Algorithm

The children diff is the single most-studied component of every modern VDOM reconciler (Inferno's version, per Required Reading §5, is the reference for this five-pass shape):

Pass Name Action Stops when
1 Prefix scan Walk previous/new children in parallel from index 0; mark matching-key fibers "no move" First key mismatch
2 Suffix scan Walk from the end in parallel; mark matching-key fibers "no move" First key mismatch
3 Removal scan If new-children middle is empty, mark every previous-children middle fiber "delete" N/A — single pass
4 Insertion scan If previous-children middle is empty, mark every new-children middle vnode "insert" N/A — single pass
5 Middle reorder Build key→previous-index map; compute LIS over the new-middle's previous-index array; LIS members "no move", the rest "move or insert" N/A — single pass

Complexity: passes 1–4 are O(n); pass 5's LIS computation is O(n log n) (patience- sorting formulation). Total: O(n log n), matching ADR-09 (§9) and Levenshtein's edit-distance lineage (§5 Papers). Degenerate case: an adversarial input where every key appears in the middle in fully-reversed order still costs O(n log n) — the LIS of a reversed sequence has length 1, which is cheap to compute, not the worst case; the actual worst case for wall-clock cost is a middle with no shared keys at all (all delete + all insert, O(n) but with n DOM operations, §30).

Worked Example — Keyed Reorder

Previous children (keys): [A, B, C, D, E]. New children (keys): [A, C, B, D, F].

  1. Prefix scan: A matches at index 0 → "no move". Stop (index 1: B vs C mismatch).
  2. Suffix scan: D (previous index 3, new index 3) matches from the end → "no move". Stop (previous C vs new B mismatch going backward).
  3. Middles: previous [B, C] (indices 1–2), new [C, B, F] (indices 1–3, F is new).
  4. Key→previous-index map over previous middle: {B: 1, C: 2}.
  5. New middle's previous-index array: [C→2, B→1, F→-1] = [2, 1, -1]. LIS of [2, 1, -1] (ignoring -1 sentinels, which are always insertions): longest increasing run is length 1 (either [2] or [1]) — so one of B/C moves, the other one is the anchor F is a fresh mount (Placement, no previous fiber).

Result: A and D untouched; C retained as anchor, B moved after it, F mounted. Fixture: conformance/corpora/diff/keyed/reorder-with-insert.json.

Malformed-Input Example — Duplicate Keys

Input: previous [{key:"x"}, {key:"x"}] (a duplicate-key list — a common authoring bug, T3 §24). The key→previous-index map construction (pass 5) overwrites the first x entry with the second's index — first-match-wins is not the contract; last-write-wins during map construction is, so the second previous fiber is the one matched, silently discarding the first's identity. Dev-mode detects and warns (Encountered two children with the same key); production does not check (documented tradeoff, T3 §24). Fixture: conformance/corpora/diff/keyed/duplicate-key-warns.json.

Failure-Path Example — Suspense Throw During Reconciliation

A FunctionComponent fiber's render throws a Promise (not an Error) during beginWork. The reconciler's begin-work dispatch (§14.2) catches the thrown value, checks typeof thrown.then === "function", and — finding a thenable — walks the return chain looking for the nearest fiber tagged SuspenseComponent. That boundary's state transitions Mounted → Suspended (§19.6); its fallback VNode is reconciled and committed instead of the throwing subtree; a .then callback is attached to the promise that, on resolution, re-schedules the suspended subtree at its original lane. If no SuspenseComponent ancestor exists, the thrown promise propagates as an uncaught error to the root (I8 §7). Fixture: conformance/corpora/suspense/no-boundary-propagates-to-root.json.

Pass Visits fibers with flag Host DOM state during pass Fires
commitBeforeMutation Snapshot Pre-commit (old) getSnapshotBeforeUpdate

This ordering is the concrete mechanism behind P2, I2, I7 (§6, §7) and is elaborated with its rationale in §15.1–§15.2 (Phase 3).

Design principles (§6)

  • P1 — The render phase is pure and restartable. Components return new VNode trees; they never mutate the host. Violating it: a beginWork call that touches the DOM breaks time-slicing (§17) and concurrent mode (§21) simultaneously, since a paused/discarded render would leave stray mutations. Tradeoff: forces every side effect through the commit phase's stricter contract (P2). Operational implication: a "component touches document directly" bug report is always a P1 violation; the runbook (§26) starts there.
  • P2 — The commit phase is synchronous and indivisible. Once entered, it runs to completion; no reentrancy, no yielding. Tradeoff: a slow commit (e.g., a huge commitMutation batch) blocks the main thread with no escape hatch — this is the one place time-slicing does not apply, by design (I2 §7). Violating it (yielding mid-commit) would let the host observe a torn tree, breaking I9.
  • P3 — Hooks are positional. A function component's hook list is determined by call order on each render. Tradeoff: unenforceable by the type system; defended by the dev-only Strict Mode check (§21.5) and the eslint-plugin (§22.3), not by the runtime. Violating it silently corrupts unrelated state slots (MM3 §32).
  • P4 — The reconciler does not know about the DOM. A HostAdapter trait (§11) abstracts every host operation. Tradeoff: an extra vtable-style indirection per host operation (small constant overhead); the payoff is the DOM backend, the test renderer, and the deferred native backend (§37) sharing one reconciler. Violating it (importing document in the reconciler) breaks the test renderer's determinism (I4 §7).
  • P5 — Children diff is keyed; key order is honoured. Unkeyed: match by position. Keyed: match by key via the LIS-based middle-reorder pass (§14.4). Tradeoff: O(n log n), not optimal (ADR-09 §9); an unstable key (T3 §24) silently defeats memoization.
  • P6 — Synthetic events delegate at the root. A single native listener per event type at the root container; dispatch walks the fiber tree in React-tree order, not DOM-tree order. Tradeoff: one delegated listener regardless of tree size (derivation 10, §34) at the cost of a per-dispatch fiber-chain walk; violating it breaks portal event propagation (T10 §24).
  • P7 — Suspense throws. A component that needs to wait throws a Promise; the reconciler walks up to the nearest <Suspense> boundary. Tradeoff: composes with any data-fetching library with zero API surface, at the cost of an unusual (exception-as- control-flow) mental model (MM5 §32).
  • P8 — Error boundaries catch. A boundary defining getDerivedStateFromError / componentDidCatch (or the functional equivalents) catches descendant render/commit errors. Tradeoff: errors above the topmost boundary kill the root (I8 §7); violating this containment contract (e.g., a try/catch inside render swallowing an error silently) is FM-7 (§25).
  • P9 — Concurrent rendering preserves invariants. The render phase writes to an off-tree work-in-progress fiber tree; the host only observes the result after commit. Tradeoff: doubles peak fiber memory during an in-flight concurrent render (derivation 8, §34); violating it (partial commit) breaks I9.
  • P10 — Strict Mode is dev-only. Double-invocation of render and effect-mount, hook-order verification. Tradeoff: doubles dev-mode render cost; stripped entirely from production (ADR-19 §9, T11 §24).
  • P11 — The JSX runtime is the jsx/jsxs/Fragment triple. Compatible with the Babel/TypeScript 5+ automatic JSX transform. Tradeoff: couples us to that transform's calling convention; violating it (inventing a bespoke transform) breaks tooling interop across the whole ecosystem.
  • P12 — Refs are imperative and committed. useRef returns a mutable { current } cell; the commit phase assigns/detaches it. Tradeoff: refs are not reactive — reading .current in render is a documented anti-pattern, not a type error.
  • P13 — Hydration recovers from mismatches, never bails out wholesale. A mismatch triggers a local client re-render of the affected subtree only. Tradeoff: a silent recovery risk (mitigated by the onRecoverableError channel, ADR-23 §9); violating it (global bail-out) destroys the entire SSR investment (§20).
  • P14 — No global mutable state. The runtime is per-root; the scheduler is a single shared instance across roots but coordinates via message-passing, not shared mutable state. Tradeoff: cross-root synchronization has message-passing latency instead of a direct write; violating it makes multi-root embedding (e.g., micro-frontends) unreliable.
  • P15 — A root is Send-like (single-owner-thread) but not Sync. One root is driven by one thread (typically the DOM main thread). Tradeoff: no cross-thread direct access to a root's fiber tree; the deferred native/worker backend (§37) must define its own cross-thread contract explicitly, not inherit one implicitly.
