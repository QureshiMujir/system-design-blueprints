Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why must the render phase be pure while the commit phase is synchronous and indivisible — what specific bug does conflating them produce, and which invariant formalizes the split? (§6 P1/P2, §7 I1/I2)
  2. Derive the keyed-children diff's O(n log n) bound from first principles, and state the exact adversarial input shape that maximizes real-world wall-clock cost without changing the asymptotic class. (§8, §14.4, §14.7)
  3. Why are hooks positional instead of keyed, and what does the rejected "named hooks" alternative buy you in a language with first-class effect handlers? (§6 P3, §9 ADR-04)
  4. Trace exactly what happens, mechanism by mechanism, when a SyncLane update arrives mid-render of a TransitionLane — name every state transition involved. (§17.2, §21.2, §8 Fiber Work-Loop State Machine)
  5. Why does useSyncExternalStore read synchronously instead of acquiring a lock, given that the host is single-threaded — what would a lock actually protect against here? (§21.2, MM7 §32)
  6. What specific SSR investment does a hydration-mismatch bail-out design destroy that a local-recovery design preserves, and quantify the blast-radius difference? (§6 P13, §20.2, §9 ADR-07)
  7. Why does the runtime reject callback-based Suspense in favor of thrown promises, and what composability property does the rejected design lack? (§6 P7, §9 ADR-06, §19.2)
  8. Using the §4 constraints and the §34 derivations, compute the memory overhead of 16 fully-saturated concurrent transitions and explain why it is small relative to baseline tree memory. (§34 derivation 7, §4, §17.1)
  9. Why is root-delegated event dispatch necessary for portal-aware propagation, and what exact ordering difference exists between fiber-tree bubble order and native DOM bubble order? (§6 P6, §18.2, §8 Architectural Overview trust boundary)
  10. What makes tearing structurally impossible to detect in production, and why is that an acceptable tradeoff given the fuzz-based detection strategy chosen instead? (§21.9, §25 FM-5, §30 M11)
  11. Why does useDeferredValue necessarily render its subtree twice, and under what circumstances does that cost exceed its benefit? (§16.9, §21.6, §21.7)
  12. Compare the rejected pre-Fiber stack reconciler (§36 Alternative #2) to the chosen Fiber design: what exact scheduling capability does the rejected design lack, and name a real system that still ships it successfully today. (§9 ADR-03, §36)
  13. Why does the ADR table's "When the Rejected Choice Wins" column matter architecturally — pick any two ADRs and explain the regime in which nimbus's own locked choice would be wrong. (§9, any two rows)
  14. Explain the exact mechanism by which the Deferred Features Register's Server Components entry interacts with the streaming SSR protocol already built in Phase 8 — what would have to change, and what stays the same? (§20, §37)
  15. Why is the consecutive-re-render cap set at a fixed integer (25) rather than a time budget, and what failure mode would a time-budget-based cap introduce instead? (§7 I11, §24 T6, §25 FM-1)
  16. Using the Comparative Architecture Table and the Capacity Model, explain quantitatively why SolidJS's fine-grained model wins for a live trading ticker but loses for this project's stated teaching goal. (§33, §34, §2)
  17. Why must the DevTools hook be fully stripped from production builds rather than merely disabled at runtime, and what threat does a runtime-only disable fail to close? (§22.2, §24 T11, §30 M6/M7)
  18. Trace the full lifecycle of a ref from useRef call through commit-phase attach to unmount-time detach, citing every phase and invariant involved. (§16.5, §15.2, §6 P12)
  19. Why does the runtime's scalability ceiling (1,000,000 fibers) come from heap exhaustion rather than an algorithmic wall, and what is the first algorithmic bottleneck encountered before that heap ceiling is ever reached? (§31, §4)
  20. Explain why the five-pass keyed-diff algorithm's prefix/suffix scans exist at all, given that the middle-reorder LIS pass alone could theoretically handle the full list — what performance property would be lost without them? (§8, §14.6, §5 Reference Implementations — Inferno)

32. Mental Models & First Principles

# Insight Predicts Bug Class Without It Applies In
MM1 A fiber is a work-unit, not a data structure that outlives its render Why holding a stale fiber reference across renders is meaningless Use-after-free-style logic bugs from caching a fiber pointer across commits §14, §19
MM2 Render is pure math over the previous tree; commit is the only side-effecting instruction Why setState during render throws/loops instead of "just working" DOM mutation escaping the commit phase, corrupting I1/I2 §12 (P1), §15
MM3 Hooks are an array indexed by call order, not a dictionary keyed by name Why conditional/looped hook calls corrupt unrelated state silently FM-3 — the hardest-to-diagnose failure class in the runtime §16
MM4 A lane is a priority, not a queue entry Why interruption discards in-progress work instead of pausing a queued item Attempting to "resume" a preempted transition instead of restarting it, violating P9 §17, §21
MM5 Suspense is control flow expressed as an exception, not a loading-state prop Why suspense composes with arbitrary async data sources with zero API surface Reimplementing Suspense as a callback API and losing composability §19
MM6 Hydration is a diff against zero shared memory, not a zero-cost operation Why mismatches cost a local re-render, never a crash Treating hydration as "just attach listeners" and missing the matcher's cost model §20
MM7 Tearing is a snapshot problem, not a locking problem Why useSyncExternalStore reads synchronously instead of locking (locks are meaningless in a single-threaded host) Attempting to "fix" tearing with a mutex-shaped API that solves nothing §21
MM8 Keys are identity, not position Why array-index keys silently break on reorder while content-derived keys don't T3-class silent state-corruption bugs (§24) §14

Each model is the compressed form of a design decision an expert holds without re-deriving it from scratch every time; a reader who cannot restate all eight in their own words has not yet finished internalizing this blueprint, regardless of how much code they've written against it.

5. Required Reading

Books

  • Chris Okasaki, Purely Functional Data Structures (1998), ch. 2–3 (persistence, amortization) — the structural-sharing model behind never mutating a committed VNode tree in place. Applied in §8 (Domain Model), §11 (Core Schema — VNode immutability).
  • Pavel Panchekha & Chris Harrelson, Web Browser Engineering (browser.engineering, 2023), ch. 12 (Scheduling) and ch. 16 (Reusing Previous Computations) — the event-loop and incremental-layout reasoning that motivates cooperative, yield-based scheduling. Applied in §17 (Phase 5, Scheduler) and §20 (Phase 8, SSR/Hydration).
  • Martin Kleppmann, Designing Data-Intensive Applications (2017), ch. 11 (Stream Processing) — out-of-order, partial-result delivery under a streaming protocol. Applied in §20 (Phase 8, SSR streaming) and §21 (Phase 9, tearing/consistency).
  • Ilya Grigorik, High Performance Browser Networking (2013), ch. 1 (Primer on Latency and Bandwidth) and ch. 10 (Rendering) — the latency-budget reasoning behind the 16.6 ms frame constraint. Applied in §4 (System Constraints) and §23 (Phase 11, Performance Hardening).
  • Michael T. Nygard, Release It! (2nd ed., 2018), ch. 5 (Stability Patterns) — circuit-breaker/bulkhead containment reasoning, the direct ancestor of error-boundary blast-radius containment. Applied in §19 (Phase 7, Error Boundaries) and §25 (Failure Modes & Recovery).
  • Benjamin C. Pierce, Types and Programming Languages (2002), ch. 11 (Simple Extensions — variants) — the discriminated-union typing discipline behind VNode's tagged-union design. Applied in §11 (Core Schema & Types) and §6 (P4, Design Principles).

Papers

  • K. Zhang, D. Shasha, "Simple Fast Algorithms for the Editing Distance between Trees and Related Problems," SIAM J. Computing 18(6), 1989 — the optimal O(n³)-class tree-edit distance; the gold standard our O(n log n) heuristic deliberately does not chase. Applied in §8 (Domain Model) and ADR-09 (§9).
  • V. Levenshtein, "Binary Codes Capable of Correcting Deletions, Insertions, and Reversals," Soviet Physics Doklady 10(8), 1966 — the edit-distance/LIS reasoning underlying the keyed-children matching pass. Applied in §14 (Phase 2, Reconciler Core).
  • Andrew Clark, "React Fiber Architecture," GitHub gist (acdlite/react-fiber-architecture), 2017 — the canonical write-up of the pausable-work-loop design. Applied in §14 (Phase 2) and §17 (Phase 5, Scheduler).
  • Sebastian Markbåge, React Core Team concurrent-rendering design notes and talks (JSConf Iceland 2018; React Conf 2019, 2021) — the concurrent-mode rationale, the "the user must never see a torn intermediate render" invariant. Applied in §21 (Phase 9, Concurrent Mode).
  • D. Abramov, S. Alpert, React Core Team, "Hooks RFC," reactjs/rfcs #0068, 2018 — the positional-hooks contract and the rules-of-hooks rationale. Applied in §16 (Phase 4, Hooks).
  • React Core Team, "Suspense for Data Fetching" RFC and Streaming Server Rendering with Suspense documentation, reactjs/rfcs and react.dev, 2018–2022 — the thrown-promise convention and the out-of-order streaming-flush protocol. Applied in §19 (Phase 7, Suspense) and §20 (Phase 8, SSR Streaming).
  • U. A. Acar, G. E. Blelloch, R. Harper, "Adaptive Functional Programming," ACM TOPLAS 28(6), 2006 — self-adjusting computation; the fine-grained-reactivity alternative to coarse re-render + diff. Applied in §33 (Comparative Architecture Table) and §36 (Alternative Architectures).
  • Evan Czaplicki, "Blazing Fast HTML, Round Two," elm-lang.org blog, 2013 — Elm virtual-dom's practical diffing design, an early production VDOM implementation predating React's public Fiber work. Applied in §14 (Phase 2, Reconciler Core) and §9 (ADR-09).

Reference Implementations

  • facebook/react — packages/react-reconciler/src/{ReactFiberBeginWork, ReactFiberCompleteWork, ReactFiberCommitWork, ReactFiberWorkLoop, ReactFiberHooks, ReactFiberLane}.js, packages/scheduler/. The reference for the fiber/lane/hooks design; read for architecture, never copied line-for-line. Applied in §14, §16, and §17. Pitfall not to copy: React's dual-buffering (current/workInProgress fiber pairs) is necessary at React's scale; a smaller runtime can over-engineer by copying it uncritically without re-deriving the need (§15.6).
  • preactjs/preact — src/diff/{index,children}.js, src/component.js. The smallest legible production VDOM reconciler; the reference for "what falls out when the concurrent-mode machinery is removed." Applied in §14, §33. Pitfall: Preact's synchronous, non-fiber diff cannot be naively adopted once time-slicing (§17) is a requirement.
  • infernojs/inferno — the keyed-children diff implementation (prefix/suffix/LIS middle-reorder). The fastest legible reference for §14's five-pass keyed algorithm. Applied in §14.4 (§14). Pitfall: Inferno's diff assumes a fully synchronous commit; adapting it to an interruptible render phase requires re-deriving where the LIS pass may safely pause (§14.6 Pitfalls).
  • vuejs/core — packages/runtime-core/src/renderer.ts. A dual-invariant reference: Vue's compiler-assisted "block tree" patch flags versus our uncompiled JSX runtime. Applied in §33 (Comparative Architecture Table).
  • snabbdom/snabbdom — the modular-hooks VDOM design (init, create, update, remove, destroy module hooks over a minimal core). The reference for keeping the core diff small and pushing DOM-specific concerns (attributes, style, events) into separate modules — directly informs the HostAdapter trait boundary (§11). Applied in §9 (ADR-04, ADR-15) and §15 (Phase 3, Host Adapter).

RFCs / Specifications

  • WHATWG HTML Living Standard, the "Web application APIs" event-loop chapter, and the DOM Standard's event-dispatch algorithm (capture/target/bubble). Applied in §18 (Phase 6, Synthetic Events).
  • W3C Pointer Events specification (Level 2/3) — the unified mouse/touch/pen event model. Applied in §18.4 (Pointer plugin).
  • WHATWG Streams Standard — the ReadableStream contract consumed by renderToReadableStream. Applied in §20 (Phase 8, SSR Streaming).
  • ECMAScript Language Specification (current edition) — WeakRef/Symbol semantics used for the $$typeof VNode brand and any weak caches. Applied in §11 (Core Schema).

The literature changes faster than this document; a post-2026 paper or RFC that supersedes one of these for our purposes is captured by a new ADR (§9), never by silently replacing a citation.

Glossary (§38) · 36 terms · site-wide glossary

Alternate
The work-in-progress copy of a fiber, paired with the current fiber via the alternate pointer (§11).
Beginwork
The render-phase function that produces a fiber's children from its VNode (§14.2).
Commit phase
The synchronous, side-effect-bearing phase following a successful render (§8, §15).
Completework
The render-phase function that bubbles subtree flags bottom-up once a fiber's children are done (§14.2).
Concurrent rendering
Rendering that can be interrupted and resumed without committing a partial result (§21).
Deferred value
A lower-priority copy of a value rendered via useDeferredValue (§16.9, §21.2).
Delegation
Root-level, single-listener-per-event-type native event registration (§18.2).
Effect
A side effect scheduled by useEffect or useLayoutEffect, fired in the commit phase (§16.3).
Error boundary
A component catching descendant render/commit errors via getDerivedStateFromError/componentDidCatch (§19.2).
Fiber
A typed work-unit; one per VNode per render pass (§11).
Fiber tag
The enum discriminating a fiber's kind (HostRoot, HostComponent, FunctionComponent, etc., §14.2).
Flags
A per-fiber bitmask recording pending commit-phase work (Placement, Update, Deletion, etc., §8).
Fragment
A VNode wrapper emitting no host node (§13.2).
Hook
A per-fiber, positional slot backing a hooks-API call (§11, §16).
Hydration
Client-side attachment of event listeners to SSR'd HTML without re-rendering matched nodes (§20.2).
Lane
A single bit in the 31-bit priority mask; multiple lanes may be active simultaneously (§11, §17.1).
LIS (Longest Increasing Subsequence)
The subproblem solved during the keyed-diff's middle-reorder pass to identify fibers that need not move (§8).
Mismatch recovery
The local, subtree-scoped re-render triggered when SSR and CSR output diverge during hydration (§20.2, P13 §6).
Offscreen
A boundary keeping a subtree mounted but unrendered (§21.2).
Passive effect
A useEffect-scheduled effect fired asynchronously after paint (§8 commit-ordering table).
Portal
A VNode rendering into a DOM node other than its parent's host, while retaining fiber-tree event-propagation ancestry (§18.2).
Reconciler
The algorithm diffing the previous fiber tree against a new VNode tree (§8, §14).
Render phase
The pure, restartable phase producing a work-in-progress fiber tree (§8, §14).
Root
The top of a fiber tree, constructed by createRoot/hydrateRoot (§11).
Scheduler
The priority-lane scheduler driving the cooperative work loop (§11, §17).
Selective hydration
Promoting an unhydrated subtree's hydration priority in response to a user interaction (§20.8).
Sentinel
A registered symbol type (Fragment, Portal, Suspense, etc.) distinguishing non-component/non-intrinsic VNode kinds (§13.2).
Slice (time-slice)
A bounded quantum of render-phase work between yield checks, default 5 ms (§17.2).
Strict Mode
The dev-only double-invocation and hook-order verification mode (§21.2).
Suspense
A boundary rendering a fallback while a descendant's thrown promise is pending (§19.2).
Synthetic event
A normalized, non-pooled event object dispatched in fiber-tree order (§11, §18.2).
Tearing
Two parts of a tree observing different values of the same external store within one committed render (§21.1, MM7 §32).
Transition
A state update explicitly marked non-urgent via startTransition (§16.9, §17.4, §21.2).
VNode
A virtual-DOM node; the immutable, frozen input to the reconciler (§11, §13.2).
Work-in-progress (WIP) tree
The off-tree fiber tree being constructed during an in-flight render, discarded if interrupted (§8 Fiber Work-Loop State Machine).
Workloop
The scheduler-driven loop calling beginWork/completeWork across fibers, checking shouldYield() between them (§17.2).
