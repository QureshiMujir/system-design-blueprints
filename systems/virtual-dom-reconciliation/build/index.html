⬜ Phase 0 — Repo Skeleton & Correctness Kernel §12

Objectives

Stand up the §10 repository layout, governance files, CI workflows, and the smallest possible correctness kernel: a createRoot that can mount one intrinsic element via the nimbus-host-test adapter. No diffing, no hooks, no scheduler — this phase exists to prove the workspace, the trait boundary (P4 §6), and the conformance harness wiring all work before any reconciliation logic is written.

Deliverable

A cloned repo where pnpm install && pnpm build && pnpm test && pnpm conformance all exit zero, and pnpm conformance emits conformance.report.json with one Pass entry (render-trees/hello) and every other corpus directory marked Deferred.

Acceptance
  • pnpm test passes with exactly 1 test asserting the host-test event log for createRoot(host).render(<h1>hi</h1>) equals [{op:"createElement",type:"h1"}, {op:"createTextNode",text:"hi"}, {op:"insertBefore",...}].
  • pnpm conformance reports passRate: 100% on a corpus of exactly 1 fixture.
  • CI (ci.yml) green on a clean clone in ≤ 3 minutes.
  • ADR-01, ADR-02, ADR-13 (§9) committed to docs/adr/ verbatim.
Fixtures
Fixture Purpose Expected Output
render-trees/hello.json smoke-test mount path 3-entry host-test event log (create h1, create text, insert)
render-trees/unsupported-nested.json documents Phase-0 scope limit throws UnsupportedInPhase0 for any element with element children
Pitfalls
  • Building the reconciler before the workspace skeleton is the strongest temptation on this phase; resist it — a skeleton retrofitted after Phase 2 always has import-boundary violations (I4 §7) that are expensive to unwind.
  • pnpm's strict-peer-dependency mode flags peer mismatches across the 10-package workspace immediately; pin an .npmrc peer policy in this phase, not later.
  • A Root.render that "cheats" by importing document directly to pass the smoke test invalidates I4 for every later phase; the host-test adapter must be the only path.

⬜ Phase 1 — VNode Model & JSX Runtime §13

Objectives

Implement the full VNode discriminated union (§11) and the jsx/jsxs/Fragment/ jsxDEV runtime (P11 §6), establishing the vocabulary every later phase consumes. No reconciliation logic changes in this phase — Phase 0's single-element mount path is extended to accept the full VNode shape, still without diffing.

Deliverable

A type-only round-trip test: <div className="x"><span/></div> (compiled via the automatic JSX transform) produces a VNode whose deep equality matches a hand-authored object literal built directly from the VNode schema (§11).

Acceptance
  • TSC strict-mode clean across the whole workspace: 0 errors.
  • Round-trip fixture parser-jsx/div-span-roundtrip.json passes at 100%.
  • jsx() allocation cost: ≤ 200 ns per call (measured via bench_initial_render.ts's warmup phase, M1 precursor, §30).
Fixtures
Fixture Purpose Expected Output
parser-jsx/div-span-roundtrip.json jsx() vs hand-built VNode equality deep-equal pass
parser-jsx/key-ref-extraction.json key/ref pulled out of props props has no key/ref field
parser-jsx/fragment-sentinel.json <>...</> produces Fragment sentinel type type === Fragment
parser-jsx/malformed-missing-type.json malformed input: type undefined throws InvalidElementType
Pitfalls
  • Extracting key/ref after freezing props leaks them as ordinary props to consumers — a Phase-1 defect that surfaces only much later, in Phase 2's key-based matching (§14.4), as an inexplicable "key changes every render" bug.
  • defaultProps on legacy class components (§11 ClassComponent) must be applied at element-creation time (inside jsx()), not at render time, or SSR (§20) and CSR compute different effective props for the same element.
  • Treating jsxDEV's extra parameters as load-bearing in production builds bloats the bundle (M6 §30); they must be fully tree-shaken out of nimbus/jsx-runtime.

⬜ Phase 2 — Reconciler Core: Fiber Tree & Keyed Diff §14

Objectives

Implement the fiber tree (§11 Fiber), the beginWork/completeWork render-phase walk, and the five-pass keyed-children diff (§8), all executing synchronously — the scheduler (§17) and its interruption semantics are explicitly out of scope until Phase 5; this phase proves the diff algorithm and fiber bookkeeping in isolation, matching P1 (§6: render phase pure) without yet exercising P9's pause/resume machinery.

Deliverable

A <App/> fixture with a keyed 5-item list passes a full mount → keyed-reorder → re-mount cycle against nimbus-host-test, matching the §8 worked example (A,B,C,D,E → A,C,B,D,F) fiber-for-fiber (not just DOM-output-for-DOM-output).

Acceptance
  • diff/keyed and diff/unkeyed corpora (§10) pass at ≥ 99% (matches the Phase-11 conformance-bucket commitment, §23.1).
  • A 1,000-element list full shuffle produces a fiber-level move-list whose size is within 5% of the theoretical LIS-optimal move count (property test, ADR-09 §9).
  • Reconciliation of the 1,000-element shuffle completes in ≤ 5 ms synchronous compute time (M2 §30 precursor — scheduler-mediated timing lands in Phase 5).
Fixtures
Fixture Purpose Expected Output
diff/keyed/reorder-with-insert.json §8 worked example matches hand-derived move list
diff/keyed/duplicate-key-warns.json §8 malformed-input example dev warning + last-write-wins match (T3 §24)
diff/unkeyed/type-change-remounts.json type mismatch forces unmount+mount old fiber deleted, new fiber mounted
diff/fragment/nested-fragments.json Fragment children flatten correctly host tree has no Fragment-sentinel nodes
Pitfalls
  • Copying React's full dual-buffer alternate machinery uncritically (Reference Implementations, §5) before re-deriving why it is needed at this scale over-engineers Phase 2; derive the need from I14 (§7) first.
  • The LIS middle-reorder pass (§8) is easy to get "almost right" — an off-by-one in the previous-index sentinel (-1 for unmatched) silently corrupts insert detection; the duplicate-key-warns fixture (§14.5) is the regression canary.
  • The fiber's return back-edge must never be walked by a naive recursive serializer (e.g. JSON.stringify in a debug log) — it is cyclic by construction.

⬜ Phase 3 — Commit Phase & Host Adapter §15

Objectives

Implement the synchronous, indivisible commit phase (P2 §6, I2 §7) and the production HostAdapter DOM backend (P4 §6), turning Phase 2's fiber-level diff output into real mutations against a real document. This is the phase where the trust boundary between "the reconciler decided what changed" and "the host actually changed" is drawn concretely.

Deliverable

The Phase-2 keyed-reorder fixture (§14.5) now produces observable DOM mutations in a JSDOM-backed Playwright page matching the fiber-level move list exactly — the first point in the build where "what the reconciler decided" and "what the user's screen shows" are verified to be the same thing.

Acceptance
  • render-trees and diff/* corpora (§10) pass against the DOM backend at ≥ 99%, matching their Phase-2 fiber-level pass rate exactly (cross-checking §14.4's numbers).
  • Commit-phase wall-clock for a 1,000-node full mount: ≤ 5 ms p95 (M1 §30).
  • Zero DOM mutations observed outside the commitMutation sub-pass window (asserted via a MutationObserver harness in the conformance runner) — the concrete test of I1/I2 (§7).
Fixtures
Fixture Purpose Expected Output
render-trees/mutation-window-bounded.json I1/I2 enforcement 0 mutations outside commitMutation
diff/keyed/reorder-dom-matches-fiber.json fiber move-list ⇔ real DOM Playwright DOM snapshot equals fiber-derived expectation
render-trees/ref-attach-after-mount.json P12 — ref timing ref.current non-null only after commitLayout
render-trees/ref-detach-on-delete.json ref cleanup on unmount ref.current === null post-commit
Pitfalls
  • Copying React's dual-buffering uncritically (flagged already in §14.6) resurfaces here as "which buffer does commitMutation read attributes from" — get the old/new props source wrong and commitUpdate diffs against stale data.
  • commitLayout's ref-attach must run after the host node exists in the tree, not before — a ref attached before commitMutation's insert sees a detached node.
  • Batching contiguous placements into a single DocumentFragment insert (§30) is a real perf win but silently breaks if the batching logic spans a Deletion-flagged sibling incorrectly, producing a visually-correct but ordering-wrong DOM (only caught by a full-tree structural diff, not an "is it visible" check).

⬜ Phase 4 — Hooks & State Model §16

Objectives

Implement the full hooks dispatcher (useState, useReducer, useEffect, useLayoutEffect, useMemo, useCallback, useRef, useContext, useId, useInsertionEffect, useImperativeHandle, useDebugValue) against the positional per-fiber slot list (P3 §6, §11 Hook) established in Phase 2's fiber bookkeeping. useSyncExternalStore, useTransition, useDeferredValue are stubbed here and completed in Phase 5/9 (§17, §21) once lanes exist.

Deliverable

A counter component using useState + useEffect (mount-logs, cleanup-logs) passes a mount → three updates → unmount cycle against the DOM backend, with effect fire/cleanup order matching the two-pass model of §8's commit-ordering table exactly.

Acceptance
  • hooks/state, hooks/effect, hooks/memo, hooks/reducer corpora (§10) pass at ≥ 99% (Phase-11 commitment, §23.1).
  • A component calling 12 hooks in a stable order across 50 re-renders shows zero I3 violations (hook-order checksum, §7).
  • useMemo cache-hit rate on an unchanged-deps re-render: 100% (no factory re-invocation), verified by a call-count spy fixture.
Fixtures
Fixture Purpose Expected Output
hooks/state/lazy-initializer-once.json lazy useState(() => …) fires once init spy call count = 1 across 10 renders
hooks/effect/cleanup-before-next-effect.json cleanup ordering cleanup(prev) called before effect(next)
hooks/memo/deps-array-object-is.json Object.is semantics, not deep-equal new-array-same-values still recomputes
hooks/state/conditional-hook-throws-dev.json I3 violation detection dev-mode throws Hooks order changed
Pitfalls
  • Out-of-order hook calls between renders are undefined in production (P3 §6); only Strict Mode (Phase 9, §21) catches them at dev-time — this phase must not add a production runtime check, or it silently reintroduces the "named hooks" cost the design explicitly rejected (ADR-04 §9).
  • useEffect's deps array uses Object.is, not deep equality — a fresh [a, b] literal on every render is not stably equal to the previous [a, b] as an array reference, but the hook compares element-wise, so this is correct; the pitfall is a naive implementation that compares the array reference itself instead of its elements.
  • useMemo must be documented as a perf hint, not a correctness guarantee (the runtime may discard cached values under memory pressure per the React-canonical contract, §5) — a consumer relying on it for identity stability (e.g. object identity gating a child's React.memo) has a latent bug this phase must flag in the docs, not silently "fix."

⬜ Phase 5 — Fiber Scheduler: Lanes, Priority, Time-Slicing §17

Objectives

Implement the Scheduler (§11), the 31-bit Lanes bitmask (ADR-08 §9), and cooperative time-slicing via MessageChannel-based yielding, turning Phase 2's synchronous reconciler into an interruptible one. This is the phase that makes P9 (§6: concurrent rendering preserves invariants) buildable — Phase 9 (§21) only exercises the guarantee this phase establishes.

Deliverable

A benchmark harness (bench_concurrent.ts) demonstrating a 30ms-if-unsliced render completing across 6 × 5ms slices, interleaved with a simulated input handler that fires every frame with zero dropped input events.

Acceptance
  • Slice budget adherence: p99 ≤ 6 ms per slice (M10 §30), default sliceMs = 5.
  • A synthetic 10,000-item filter-as-you-type benchmark sustains 60fps (16.6 ms/frame, M5 §30) with zero dropped keystrokes across a 5-second run.
  • Lane-priority correctness: a SyncLane update issued mid-TransitionLane render interrupts and completes before the transition resumes, in 100% of 1,000 fuzz trials (ADR-08 §9).
Fixtures
Fixture Purpose Expected Output
concurrent/transitions/interrupt-by-sync.json priority preemption sync lane commits first
concurrent/transitions/discard-on-interrupt.json no partial commit (I9) 0 host mutations from discarded WIP tree
concurrent/deferred/slice-budget-respected.json time-slicing every slice ≤ sliceMs + 1ms tolerance
Pitfalls
  • flushSync(fn) runs fn and commits synchronously — overusing it defeats concurrent rendering's entire point; reserve it for input-handler synchronization needs (e.g. focus management before a state change), a documented anti-pattern otherwise (§17.9's list extends into Phase 9, §21.7).
  • A transition that completes successfully commits atomically at the end; there is no partial commit — an implementation that tries to "stream" a transition's commit incrementally violates I9 directly.
  • The 5ms slice budget is empirical (short enough to avoid input latency, long enough to amortize dispatch overhead, §5 Books — Grigorik's latency-budget reasoning); hard-coding it instead of exposing setSliceMs blocks embedders who need to tune it for a slower/faster host.

⬜ Phase 6 — Synthetic Event System §18

Objectives

Implement root-delegated synthetic event dispatch (P6 §6, ADR-05 §9): one native listener per tracked event type at the root container, event plugins translating native events to typed SyntheticEvents (§11), and portal-aware capture/target/bubble propagation that follows the fiber tree, not the DOM tree.

Deliverable

A conformance fixture demonstrating a click dispatched inside a portal's DOM subtree invokes the portal's fiber-tree ancestor's onClick handler, not any handler attached along the portal's actual DOM ancestor chain — the concrete, checkable proof of P6.

Acceptance
  • events/pointer, events/keyboard, events/form corpora (§10) pass at ≥ 99%; events/composition, events/focus at ≥ 95% (Phase-11 commitment, §23.1).
  • Event dispatch through a 100-fiber bubble path: ≤ 0.1 ms (M4 §30).
  • Exactly one native listener installed per tracked event type per root, verified by a listener-count assertion fixture (I6 §7) — 20 tracked event types ⇒ 20 total native listeners regardless of tree size (derivation 10, §34).
Fixtures
Fixture Purpose Expected Output
events/pointer/click-bubbles-through-portal.json P6 portal-aware bubbling fiber-ancestor handler invoked
events/focus/synthesized-bubble.json native focus/blur don't bubble synthetic bubble reaches ancestor handler
events/composition/ime-sequence.json composition state machine compositionstart→update→end order preserved
events/pointer/listener-count-invariant.json I6 enforcement exactly 20 native listeners at root
Pitfalls
  • Reusing native DOM bubble order instead of the fiber-tree order is the single most common reimplementation mistake (P6 §6); it is invisible until a portal is involved, since without portals the two orders coincide.
  • Passive listeners (touchstart/touchmove/wheel per the WHATWG spec, §5 RFCs) cannot call preventDefault — the synthetic event object must surface this constraint (a no-op preventDefault with a dev-mode warning), not silently swallow the call.
  • The change event on <input type="checkbox"> fires on every keystroke in some browsers' native implementations; the form plugin must normalize to fire only on actual value commit, or downstream useState updates thrash (Phase 4, §16) on every keypress.

⬜ Phase 7 — Suspense, Error Boundaries & Lazy §19

Objectives

Implement the Suspense state machine (Mounted/Suspended/Recovering, §8), the thrown-promise protocol (P7 §6, ADR-06 §9), the error-boundary state machine (Mounted/ Erroring/Recovered), and lazy() — the structured-control-flow layer for async-wait and failure that Phase 2's begin-work dispatch stubbed out (§14.2).

Deliverable

Three fixtures passing together: a <Suspense fallback={<Spinner/>}> wrapping a lazy() component renders the spinner then the resolved component; an error boundary catches a thrown error from a deep descendant and renders its fallback; an uncaught error at the root triggers onUncaughtError and full unmount.

Acceptance
  • Suspense fallback commit delay: exactly 500 ms in a transition context, 0 ms outside one, verified against a fake-timer harness (I7 §7).
  • Error-boundary containment: 100% of thrown errors below a defined boundary are caught at that boundary, never propagating further (I8 §7, T6/T4 §24).
  • suspense and error-boundary corpora (§10) pass at ≥ 99% (Phase-11 commitment, §23.1).
Fixtures
Fixture Purpose Expected Output
suspense/lazy-then-resolved.json full suspend→resolve cycle spinner, then real component, in order
suspense/no-boundary-propagates-to-root.json §8 failure-path example root unmounts, onUncaughtError fires
error-boundary/deep-child-caught.json boundary containment fallback rendered, siblings outside boundary unaffected
error-boundary/nested-boundary-failure-escalates.json boundary-that-throws-while-erroring escalates to next-outer boundary
Pitfalls
  • A suspended boundary must not commit its fallback synchronously inside a transition — the 500 ms delay (I7 §7) is the gate; committing immediately produces the "flash of fallback" UX defect the delay exists to prevent.
  • Error boundaries do not catch errors thrown in effects (useEffect/useLayoutEffect callbacks run after commit, outside the render/commit throw-catch window, §16) — such errors propagate to the root directly; a common author misconception this phase's docs must call out explicitly.
  • A lazy() component whose dynamic import fails surfaces the load error to the nearest error boundary, not the Suspense boundary's fallback — conflating the two silently hides load failures behind a permanent spinner (a T5-class symptom, §24).

⬜ Phase 8 — SSR Streaming & Hydration §20

Objectives

Implement renderToString (synchronous, non-streaming), renderToReadableStream / renderToPipeableStream (streaming, suspense-aware, out-of-order flush, ADR-07 §9), and hydrateRoot's mismatch-recovering hydration matcher (P13 §6) — the layer that lets a server-rendered string become an interactive client tree with zero shared memory between server and client processes.

Deliverable

A streaming-news fixture: a page with 5 posts behind independent Suspense boundaries streams the shell immediately, then each post's HTML arrives and swaps in out-of-order as its data resolves, and the client hydrates each boundary as its HTML arrives (streaming hydration) without waiting for the whole page.

Acceptance
  • Hydration of a 1,000-host-node tree: ≤ 10 ms (M3 §30).
  • A hydration mismatch on a data-now-style dynamic attribute is silently recovered (subtree re-rendered) with zero thrown exceptions and exactly one onRecoverableError call (I13 §7 adjacent).
  • The SSR-emitted XSS-escape fixture (ssr/xss-escape) passes at 100% — no injected <script> content survives renderToString output unescaped (T7 §24).
Fixtures
Fixture Purpose Expected Output
ssr/streaming/shell-then-out-of-order.json streaming flush order shell first, boundaries resolve out-of-order
ssr/hydration/type-match-walk.json hydration matcher core listeners attached, no attribute rewrite (I13)
ssr/mismatch-recovery/local-subtree-replace.json P13 local recovery only mismatched subtree re-rendered
ssr/xss-escape/script-tag-in-string-child.json T7 mitigation <script> rendered as escaped text, not executed
Pitfalls
  • useId values must be deterministic and identical between SSR and CSR given the same tree shape (fiber-path-derived, §16.7's useId section) — a non-deterministic ID scheme (e.g. Math.random()-seeded) makes every hydration a guaranteed mismatch.
  • A streaming render that errors after the shell has already flushed cannot "un-flush" — the error must be reported as a partial response (FM-11 §25); the runbook documents operator-facing recovery (serve a full error page on the next request, not a retroactive fix to the one in flight).
  • <input value="..."> in SSR output is the initial value only; on hydration the controlled-value contract takes over — treating the SSR value as authoritative post- hydration is a documented seam, not a bug to "fix" by re-reading the DOM.

⬜ Phase 9 — Concurrent Mode & Tearing Safety §21

Objectives

Complete useSyncExternalStore, useTransition, useDeferredValue (stubbed in Phase 4, §16), implement <Offscreen>, and implement dev-only Strict Mode (double-invocation, hook-order verification, effect-symmetry checks) — the layer that makes I9/I10 (§7) hold under real, adversarial concurrent usage, not just Phase 5's synthetic slicing benchmark.

Deliverable

The tearing conformance corpus (concurrent/tearing) passes at 100% against a property-tested Redux-style reference store under concurrent transition load — the strongest correctness claim in the entire runtime.

Acceptance
  • Tearing incidence: 0 events / 10,000 fuzz iterations (M11 §30, I10 §7) — this is a hard gate, not a target; any nonzero count blocks release (ADR-21 §9).
  • An <Offscreen> subtree retains component state (verified via a counter component) across 10 mount/hide/show cycles with zero state resets.
  • A Strict-Mode double-invocation run over the full examples/dashboard sample app produces zero false-positive impurity warnings.
Fixtures
Fixture Purpose Expected Output
concurrent/tearing/store-mutate-during-render.json I10 core property test render bails and retries, no torn read observed
concurrent/transitions/offscreen-state-preserved.json Offscreen state retention counter value unchanged across hide/show
strict-mode/double-invoke-no-false-positive.json Strict Mode calibration 0 spurious impurity warnings on dashboard example
concurrent/deferred/double-render-cost-bounded.json useDeferredValue cost exactly 2 renders per input change, no more
Pitfalls
  • Tearing bugs are subtle by nature — property-testing against a Redux-style reference store (not a hand-picked example) is the only reliable way to surface them; a hand-written "looks fine" test suite is documented as insufficient (this is why ADR-21's fuzzing choice, §9, is load-bearing specifically for this phase).
  • useDeferredValue is not free: the runtime renders the subtree twice per meaningful input change (current value + deferred value) — using it for a cheap subtree is a documented anti-pattern that wastes the mechanism's benefit.
  • Offscreen requires the host adapter to support hide/show semantics explicitly; assuming display:none alone preserves component state without an explicit state-preservation hook in the DOM backend (§15) is a common reimplementation mistake — CSS visibility alone says nothing about the fiber tree's lifecycle.

⬜ Phase 10 — DevTools, Profiler & Lint §22

Objectives

Implement the React DevTools v4-compatible wire protocol (ADR-19 §9) so the existing DevTools browser extension renders this runtime's fiber tree; implement the <Profiler> API consuming the commit/scheduler telemetry established in Phases 3 and 5 (§15.10, §17.10); ship nimbus-eslint-plugin (rules-of-hooks, exhaustive-deps) as the mandatory static-analysis defense for Phase 4's unenforceable positional-hooks contract (P3 §6).

Deliverable

The React DevTools browser extension, installed unmodified, renders this runtime's component tree, hook values, and per-commit timings against the examples/dashboard sample app; the ESLint plugin, run against a checked-in corpus of canonical hooks violations, flags every one.

Acceptance
  • DevTools extension displays the full fiber tree for examples/dashboard with zero missing or mislabeled components (manual + Playwright-screenshot-diff verification).
  • exhaustive-deps catches 100% of a checked-in 20-fixture violation corpus with zero false positives on the corpus's 10 correctly-written companion fixtures.
  • Production bundle contains zero bytes of DevTools-hook code (verified by scripts/check-bundle-size.ts, contributing to the M6/M7 ≤ 8KB/12KB gate, §30).
Fixtures
Fixture Purpose Expected Output
strict-mode/devtools-tree-matches-fiber.json wire-protocol fidelity DevTools tree structurally equals internal fiber tree
N/A (ESLint corpus) eslint/fixtures/violations/*.tsx 20/20 flagged, 10/10 companions clean
N/A (bundle check) scripts/check-bundle-size.ts output devtools symbol count = 0 in prod bundle
Pitfalls
  • The DevTools wire-protocol version is brittle — pinning to v4 and documenting the drift explicitly (rather than silently tracking upstream's latest) is the locked choice (ADR-19 §9); an un-pinned implementation breaks silently whenever the extension updates.
  • exhaustive-deps has well-known false positives (e.g. a setter function from useState that is referentially stable but flagged anyway) — the suppression syntax must be documented, or teams disable the rule entirely, losing the only static defense for P3.
  • Leaving any DevTools-hook code path reachable in a production bundle (even dead-code that fails to tree-shake due to a side-effecting import) breaks the M6/M7 bundle-size gate and re-opens T11 (§24)'s attack surface.

Pitfalls
