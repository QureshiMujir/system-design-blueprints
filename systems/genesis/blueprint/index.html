Project Name: Genesis

Status: specification — locked

1. Goal & Scope

Genesis is a program-evolution platform: a genetic-programming engine that mutates a typed genome intermediate representation (IR) of candidate programs, evaluates each candidate against a declarative fitness specification (the .gns DSL), executes every candidate inside a hardened sandbox boundary, and selects across generations toward one or more fitness objectives. A genome is a typed abstract syntax tree compiled to WebAssembly and executed under fuel/memory metering; fitness is not a hand-coded scalar function but a declared DSL program, compiled once per run and re-evaluated per candidate. Genesis targets research and applied program-synthesis workloads: automatic bug repair search (Weimer et al. ICSE 2009; Le Goues et al. ICSE 2012), architecture/algorithm search (Real et al. AAAI 2019; Real et al. ICML 2020), and open-ended function discovery (Romera-Paredes et al. Nature 2024).

Phase-0 deliverable (numbered modules):

  1. genesis-genome — typed genome IR, grammar, parser/serializer, type-checker.
  2. genesis-store — content-addressed genome store (RocksDB-backed).
  3. genesis-mutate — mutation-operator catalogue.
  4. genesis-crossover — subtree crossover with type preservation.
  5. genesis-fitness — .gns DSL parser + compiler to an evaluation plan.
  6. genesis-sandbox — Wasmtime-backed sandbox pool, OCI/gVisor fallback.
  7. genesis-scheduler — job scheduling, backpressure, distributed dispatch.
  8. genesis-population — population + MAP-Elites archive + lineage DAG.
  9. genesis-select — selection/replacement engine.
  10. genesis-telemetry — metrics, tracing, structured logging.
  11. genesis-checkpoint — checkpoint/resume, operator autotuning.
  12. genesis-cli — operator command-line tool.
  13. genesis-api — control-plane gRPC/HTTP API.
  14. genesis-worker — distributed worker node binary.
  15. genesis-conformance — conformance/fixture test harness.

System boundaries:

Provides: genome IR + type system; mutation/crossover operator catalogue; fitness DSL compiler and runtime; hardened per-candidate sandboxing; generational and steady-state selection; MAP-Elites/novelty archive; distributed evaluation scheduling; checkpoint/resume; lineage-based reproducibility; parsimony/bloat control.

Delegates: container/VM kernel isolation internals to gVisor and the OCI runtime; WebAssembly bytecode semantics and validation to the Wasmtime runtime and the WebAssembly Core Specification; supply-chain artifact signing to cosign/sigstore tooling (ADR-19); persistent key-value storage engine internals to RocksDB.

Does NOT provide: a general-purpose ML training framework; a hyperparameter-tuning service unrelated to program evolution; a production compiler backend for evolved programs (evolved genomes are research artifacts, not shipped binaries — PhaseDeferred("§37")); a general container orchestration platform (Kubernetes is an optional deployment substrate, not a Genesis subsystem); a static analysis / formal verification engine for evolved code.

Non-goals: real-time/interactive evolution (sub-100ms generation turnaround); evolving genomes that call arbitrary host FFI; supporting non-deterministic fitness oracles as a first-class case (only as an explicitly flagged, non-reproducible run mode).

Deployment model: primary — a Kubernetes-orchestrated fleet of stateless genesis-worker nodes plus one (or a raft-replicated set of) genesis-api control-plane instances, backed by a RocksDB genome/archive store on durable volumes; secondary — single-node research mode, all crates in one process, in-memory-backed store with periodic snapshot to disk.

Users/operators: program-synthesis researchers; automated-repair engineers; architecture-search practitioners; SRE teams operating the evaluation fleet.

What later phases unlock: distributed evaluation at fleet scale (§19); quality-diversity search beyond scalar fitness (§20); long-run bloat resistance (§21); crash-safe resumable multi-week runs with self-tuning operator rates (§22); externally auditable conformance and tail-latency guarantees (§23).

Language: Rust — memory safety without GC-pause jitter in a system whose fuel/wall-clock budgets (§4) must stay deterministic; a memory-corruption bug in the engine (not the sandboxed genome) would be a sandbox-adjacent security defect, not merely a crash. Rejected: Python (interpreter throughput too low for the target evaluations/second, and the GIL serializes exactly the multi-core fan-out the scheduler needs); Go (stop-the-world/concurrent GC pauses corrupt fuel-metered wall-clock budgets exactly when many sandboxes are cycling); C++ (manual memory management risk in the same process that arbitrates sandbox trust boundaries is an unacceptable attack-surface multiplier — Provos 2003's lineage of "the arbiter must be smaller and safer than what it arbitrates" applies to the engine itself, not only the sandbox).

Prerequisites: systems knowledge of process/VM sandboxing (seccomp-bpf, namespaces, the OCI runtime spec), WebAssembly execution semantics (linear memory, fuel metering), evolutionary algorithm theory (Holland 1975; Goldberg 1989), genetic programming operator theory (Koza 1992; Langdon & Poli 2002), and distributed job scheduling with backpressure.

Estimated timeline: Phase 0 — 3 weeks. Full system (Phases 0–11) — approximately 14 months at one senior engineer plus one distributed-systems engineer, or 7 months at 2x staffing with the phase arc unchanged.

Deferred features: LLM-proposed genome seeding, à la FunSearch (Romera-Paredes et al. Nature 2024) — PhaseDeferred("§36"); GPU-accelerated batched sandbox execution — PhaseDeferred("§31"); coevolutionary (predator/prey) fitness — PhaseDeferred("§37"); evolved-genome native-code shipping/export pipeline — PhaseDeferred("§37").

2. Why Build This

  • genetic-programming theory in practice: representation, operators, selection pressure, bloat (Koza 1992; Langdon & Poli 2002)
  • adversarial-execution engineering: sandboxing untrusted-adjacent, self-modifying-by-construction code at scale
  • declarative-DSL-as-oracle design: compiling a fitness specification instead of hand-coding fitness functions
  • distributed-systems calibration: backpressure, idempotent job dispatch, fleet-wide scheduling under partial failure
  • quality-diversity search: MAP-Elites (Mouret & Clune 2015) and novelty search (Lehman & Stanley 2011) as alternatives to scalar-fitness ranking
  • reproducibility engineering: seed+lineage-deterministic replay of a stochastic search process
  • historical throughline: Koza's tree GP → DEAP's scriptable toolbox (Fortin et al. JMLR 2012) → GenProg's real-world patch search (Weimer et al. 2009; Le Goues et al. 2012) → AmoebaNet/AutoML-Zero's architecture search (Real et al. 2019, 2020) → FunSearch's LLM-seeded function discovery (Romera-Paredes et al. 2024)
  • cross-links: shares sandboxing lineage with Malware-Sandbox-Dynamic-Analysis and Sandboxed-Browser-Security-Model; shares distributed-scheduler lineage with Distributed-Job-Queue and Parallel-Compute-Scheduler; shares typed-IR lineage with AST-Optimizer and Bytecode-Verifier

What Mastery Looks Like

  • can explain why fitness must be total (never NaN/undefined) and design the penalty scheme that guarantees it (Phase 2, §14)
  • can defend WebAssembly + fuel metering over native-code JIT for untrusted candidate execution, including where the rejected choice wins (Phase 1, §13; ADR-02/ADR-03)
  • can design a type-preserving crossover operator and prove it cannot emit an ill-typed genome (Phase 5, §17)
  • can reproduce any archived genome bit-for-bit from seed + lineage alone, and explain why float reduction order breaks this without care (Phase 6, §18)
  • can compare scalar-fitness ranking against a MAP-Elites archive and state the regime where each wins (Phase 8, §20; §33)
  • can design backpressure into a distributed evaluation scheduler such that a slow fitness oracle degrades throughput, never memory (Phase 7, §19)
  • can diagnose bloat and premature convergence from telemetry alone, without re-running the search (Phase 9, §21; §25)

Genome Store — content-addressed (BLAKE3) persistence for every genome ever created, mutated, or archived, backed by RocksDB (ADR-05); dedupes structurally identical genomes and is the join point for lineage queries (I11). Mutation Engine — applies the operator catalogue (§8) to a parent genome, always producing a syntactically valid, then type-checked, candidate (P5, I7) before it can enter a job. Fitness Compiler — parses a .gns fitness spec once per run into an immutable evaluation plan (I13) that the sandbox executes against each candidate's compiled WASM module. Sandbox Pool — the trust boundary: every candidate genome is compiled to a WASM module and instantiated under Wasmtime fuel/memory metering (ADR-02/ADR-03), OCI+gVisor as the fallback path for legacy-target or native-code evaluation. Scheduler — turns a generation's candidate list into backpressured, idempotently-keyed evaluation jobs dispatched across the worker fleet (P6, ADR-21). Population/Archive Store — holds the current generation, the MAP-Elites behavior-space grid (§20), and the lineage DAG (I11) that makes every genome reproducible (I3). Selection Engine — implements the selection/replacement state machine (§8) that turns evaluated fitness into the next generation's parent set. Telemetry — every box above emits named metrics/traces/logs (§26) before, not after, functional behavior is declared correct (P11).

6. Design Principles

P1. Determinism Under Fixed Seed — Rule: given an identical seed, run config, and .gns spec, every generation's population, fitness, and archive state must be bit-identical across runs and across worker-fleet topologies. Tradeoff: forces float-reduction-order discipline (fixed accumulation order, no floating nondeterministic parallel reduce) and forbids wall-clock-derived randomness anywhere in the hot path. Operational implication: every RNG stream derives from seed ⊕ lineage_counter (ADR-07), never OS entropy, except in an explicitly flagged non-reproducible mode. Violating it breaks: reproducibility (I3), checkpoint/resume correctness (§22), and forensic replay (§25).

P2. Sandboxing Is Non-Negotiable — Rule: no candidate genome executes anywhere — including fitness-DSL authoring/testing — outside the sandbox boundary (§13). Tradeoff: adds spawn latency (§4) to every evaluation, including trusted-author test runs. Operational implication: even a "trusted-author" fitness-DSL test harness runs candidates through the same Wasmtime/OCI path as production evaluation. Violating it breaks: I2, and converts every mutation into a potential host-compromise vector.

P3. Fitness Is Total — Rule: every candidate produces a finite, comparable fitness value or vector; crashes, timeouts, and DSL errors map to a defined penalty (§14), never NaN/undefined/absent. Tradeoff: requires a penalty schedule design upfront, not an afterthought. Operational implication: selection (§16) never special-cases missing fitness. Violating it breaks: I4, and silently corrupts tournament selection with incomparable candidates.

P4. Content-Addressed Genomes — Rule: every genome is BLAKE3-hashed at creation; structurally identical genomes deduplicate to one store entry (I11). Tradeoff: hashing cost on every mutation/crossover output. Operational implication: lineage is a hash-DAG, not a generation-indexed list. Violating it breaks: I3, I11, and archive storage bloats with duplicate genomes (§34).

P5. Type Preservation Across Operators — Rule: mutation and crossover never produce an ill-typed genome; every operator output is type-checked before it can enter a job (I7). Tradeoff: constrains operator design to type-aware subtree selection (§8), slower than untyped random-subtree swap. Operational implication: an operator that cannot find a type-compatible target degrades to a no-op mutation, never emits an ill-typed genome. Violating it breaks: I5, I7, and the sandbox's WASM codegen step (§13), which assumes well-typed input.

P6. Backpressure Over Unbounded Queues — Rule: the scheduler (§19) applies credit-based backpressure and load-shedding rather than growing an unbounded job queue when workers lag. Tradeoff: a slow fitness oracle throttles generation cadence instead of exhausting scheduler memory. Operational implication: bounded MPSC channels everywhere on the hot path (ADR-21). Violating it breaks: control-plane memory bounds and I8 (resource ceilings).

P7. Archive Over Single-Best — Rule: a MAP-Elites behavior-space archive (§20) coexists with scalar-fitness ranking; the "best ever" genome is never the sole survivor criterion. Tradeoff: archive storage (§4) and behavior-descriptor design overhead. Operational implication: premature convergence is diagnosable from archive-cell occupancy trends (§25), not just fitness variance. Violating it breaks: I9 and the system's resistance to premature convergence (§21, §25).

P8. Continuous Parsimony Pressure — Rule: bloat control (§21) via a size-adjusted fitness term is active from generation 0, not bolted on after bloat is observed. Tradeoff: slightly slower early-generation raw-fitness gains (parsimony discounts raw fitness). Operational implication: the parsimony coefficient is a run-config parameter, autotuned in Phase 10 (§22). Violating it breaks: Langdon & Poli's bloat-growth prediction (§21) goes unmitigated, and evaluation cost/candidate grows unbounded (§30).

P9. Reproducibility From Seed + Lineage — Rule: any archived genome is fully reconstructible by replaying seed plus the lineage DAG's operator log — no hidden state. Tradeoff: the operator log must be durably persisted at every generation (§18). Operational implication: checkpoint/resume (§22) replays operator history, not just a state snapshot. Violating it breaks: I3, forensic debugging, and long-run crash recovery (§25).

P10. Ephemeral, Stateless Sandboxes — Rule: no sandbox instance retains state across evaluations; the pool recycles cold Wasmtime Store instances per candidate (§13). Tradeoff: no cross-candidate JIT-warm-cache reuse beyond the shared Engine/compiled-module cache. Operational implication: a compromised or wedged sandbox is discarded, never "cleaned and reused" for correctness. Violating it breaks: I2 (state leakage between candidates is itself an escape class) and P1 (accumulated hidden state breaks determinism).

P11. Telemetry Is First-Class — Rule: every subsystem emits its named metrics/traces (§26) before, not after, functional correctness is declared done in a phase. Tradeoff: instrumentation overhead budgeted into every phase's N.7. Operational implication: a debugging methodology (§7) exists only because every invariant has a paired telemetry signal. Violating it breaks: the ability to diagnose Failure Mode classes (§25) without re-running a multi-hour search.

P12. Versioned, Immutable Per-Run Operator Config — Rule: mutation rates, selection pressure, and parsimony coefficients are fixed for a run unless changed at an explicit checkpoint boundary (§22), and every change is logged. Tradeoff: autotuning (§22) can only adjust operator rates between checkpoints, not mid-generation. Operational implication: a run's behavior is fully explained by (seed, run config, config-change log). Violating it breaks: P1/I1 and makes A/B comparison of operator strategies unreliable.

P13. Fail-Closed Fitness-Oracle Errors — Rule: any error while executing a .gns-compiled evaluation plan (runtime sandbox trap, resource-limit trap, DSL assertion failure) maps to the worst-defined penalty fitness, never propagates as a crash of the run. Tradeoff: a systemic fitness-DSL bug silently produces uniformly bad fitness rather than halting loudly — mitigated by dedicated oracle-error telemetry (§26). Operational implication: an oracle-error-rate spike is a paged alert, not a crash log. Violating it breaks: P3/I4 and availability of the generational loop (§16).

P14. Idempotent Distributed Dispatch — Rule: every evaluation job carries an idempotency key (genome hash + generation + attempt); a worker or scheduler restart never double-applies a job's fitness result to the population. Tradeoff: requires a dedup ledger on the scheduler (§19) sized to in-flight generation width. Operational implication: at-least-once delivery semantics are safe by construction. Violating it breaks: I14 and silently double-counts fitness under retries.

8. Domain Model

Genome IR grammar (EBNF):

genome      ::= expr ;
expr        ::= literal | var-ref | call | if-expr | let-expr ;
literal     ::= int-lit | float-lit | bool-lit ;
var-ref     ::= identifier ;
call        ::= "(" identifier expr* ")" ;
if-expr     ::= "(" "if" expr expr expr ")" ;
let-expr    ::= "(" "let" "(" binding+ ")" expr ")" ;
binding     ::= "(" identifier expr ")" ;
identifier  ::= letter (letter | digit | "-")* ;
int-lit     ::= digit+ ;
float-lit   ::= digit+ "." digit+ ;
bool-lit    ::= "true" | "false" ;

Typed AST node table:

Node Arity Type Signature Notes
IntLit 0 () -> Int terminal
FloatLit 0 () -> Float terminal
BoolLit 0 () -> Bool terminal
VarRef 0 () -> τ (bound type) terminal, resolved against enclosing Let/param scope
Call N (τ1..τN) -> τ_ret resolved against the primitive-function signature table (§11)
If 3 (Bool, τ, τ) -> τ both branches must unify to the same τ
Let 2 (bindings, body) binds N (id, τ) pairs then body: τ_body scoped; shadowing forbidden

Mutation-operator catalogue:

Operator Arity (parents) Type-Preservation Locality Expected Fitness Δ
Point Mutation 1 strict (same-τ replacement only) local (single node) small, ±ε
Subtree Mutation 1 strict (type-compatible subtree swap) non-local (depth-bounded) moderate, variance-heavy
Hoist Mutation 1 strict (promotes a well-typed subtree to root iff root τ matches) non-local often negative (usually shrinks toward a weaker partial solution)
Shrink Mutation 1 strict (replaces subtree with a minimal same-τ terminal) non-local negative on average, positive on size-adjusted fitness (§21)
Permutation 1 strict (reorders type-commutative Call arguments only) local negligible, ±ε
Size-Fair Mutation (Langdon & Poli 2002) 1 strict non-local, size-matched replacement low-variance, controls bloat

Crossover semantics: subtree crossover (Koza 1992) selects one crossover point per parent such that the two subtrees share type τ; if no type-compatible pair exists within the configured depth-search budget, crossover degrades to cloning parent A — it never emits an ill-typed genome (P5). Depth-limited to the run config's max_depth (§11 RunConfig).

Fitness DSL (.gns) grammar (EBNF):

spec        ::= objective+ constraint* ;
objective   ::= "objective" identifier weight case+ ;
weight      ::= "weight" float-lit ;
case        ::= "case" identifier input expected tolerance? ;
input       ::= "input" "(" value* ")" ;
expected    ::= "expect" value ;
tolerance   ::= "tolerance" float-lit ;
constraint  ::= "constraint" identifier "max-fuel" int-lit
              | "constraint" identifier "max-memory" int-lit ;
value       ::= int-lit | float-lit | bool-lit ;

Evaluation semantics: each objective compiles to a weighted sum over its case list; each case invokes the candidate's compiled WASM export with input, compares the sandbox's returned value to expected within tolerance (default 0 for exact match; a nonzero tolerance is required for Float objectives, per the float-reduction-order pitfall in §21 N.6), and contributes weight × pass_fraction; constraint rows are hard ceilings enforced by the sandbox (I8), not scored — a breach maps to the worst-penalty constant (I4) regardless of objective score.

Worked .gns example:

objective fib_correct
  weight 1.0
  case fib_0 input(0) expect 0
  case fib_1 input(1) expect 1
  case fib_10 input(10) expect 55
constraint bounded max-fuel 200000
constraint bounded max-memory 4194304

Selection/replacement state machine:

State Trigger Action Next State
INIT run start seed initial population from RNG stream (I1) EVALUATING
EVALUATING population admitted (I6) dispatch eval jobs via scheduler (§19) AWAIT_RESULTS
AWAIT_RESULTS all jobs settled or backpressure timeout collect fitness (P3) SELECTING
SELECTING fitness collected tournament / age-based selection (Real et al. 2019) picks parents BREEDING
BREEDING parents chosen apply mutation (§15) / crossover (§17) per configured rates (P12) TYPE_CHECK
TYPE_CHECK offspring produced reject ill-typed (I7), fallback-operator retry REPLACING
REPLACING offspring type-checked replace population per replacement policy (generational or steady-state) ARCHIVING
ARCHIVING population replaced update MAP-Elites archive (I9) + lineage DAG (I11) ADVANCING
ADVANCING archive updated checkpoint if boundary reached (§22), increment generation counter (I12) EVALUATING or TERMINATED
TERMINATED termination criterion met (generation ceiling, fitness target, operator-requested stop) final checkpoint, emit summary telemetry —

Sandbox execution contract: input = (compiled WASM module bytes, compiled fitness plan, resource ceilings from .gns constraint rows intersected with run-config defaults §4, a deterministic RNG substream for any stochastic primitive); output = SandboxResult { per-case pass/fail + values, fuel consumed, peak memory, wall-clock, exit taxonomy ∈ {Ok, Trap, FuelExhausted, MemoryExceeded, WallClockTimeout, HostError} }; the sandbox never returns partial host state beyond this result record (P10).

Worked end-to-end generation: SELECTING's parent list feeds BREEDING, which applies the configured operator-rate table; TYPE_CHECK discards roughly 2–5% of offspring in steady state (I7 telemetry); REPLACING merges surviving offspring into the next generation per the replacement policy (§16); ARCHIVING writes MAP-Elites cells whose behavior descriptor improved (I9) and appends lineage edges (I11); ADVANCING increments the generation counter (I12) and returns to EVALUATING.

Malformed-genome example: (call-undefined-fn 1 2) — call-undefined-fn is absent from the primitive-function signature table (§11); the type-checker rejects at ingest (I5), incrementing genesis_typecheck_reject_total with reason UnknownIdentifier.

Malformed-.gns example: an objective block whose case input arity does not match the candidate export signature is rejected at fitness-compile time (I13's well-formedness pass), never at evaluation time — a bad spec fails once per run, not once per candidate.

Failure-path example: a candidate whose WASM module traps mid-evaluation (integer overflow, out-of-bounds access) yields SandboxResult.exit = Trap; the fitness compiler's penalty mapping (I4) assigns the worst-defined fitness for every remaining unexecuted case, and TYPE_CHECK/REPLACING proceed unaffected — one crashing candidate never halts the generation (P13).

    hash: Blake3Hash,             // owner: genesis-store; immutable once written
    root: NodeId,                 // index into node arena
    arena: Vec<Node>,              // owner: genome; mutation: copy-on-write per operator
    node_types: Vec<Type>,         // parallel to arena; set by type-checker
    size: u32,                     // node count, used by parsimony (§21)
    depth: u16,
}
// concurrency: immutable after construction, shared via Arc across threads
// persistence: Cap'n Proto (ADR-04) in genesis-store; keyed by hash (P4)
// serialization: Cap'n Proto wire form; compatibility: additive-only schema evolution (§27)

enum Node {
    IntLit(i64),
    FloatLit(f64),
    BoolLit(bool),
    VarRef { name: Interned },
    Call { func: Interned, args: Vec<NodeId> },
    If { cond: NodeId, then_branch: NodeId, else_branch: NodeId },
    Let { bindings: Vec<(Interned, NodeId)>, body: NodeId },
}
// ownership: owned by GenomeRecord.arena; mutation: never mutated in place (P5)

// ownership: owned by GenomeRecord.node_types; persistence: derived, not stored (recomputed on load)

12. Phase 0 — Skeleton, Genome IR, CI

12.1 Objectives

Stand up the Cargo workspace, the genesis-genome crate's IR + grammar + type-checker, and CI (ADR-16). No sandbox, no fitness DSL yet — mutation/evaluation are stubbed.

12.2 Detailed Implementation Steps

Create the workspace Cargo.toml with crate members per §10; implement Node enum + GenomeRecord (§11) in genesis-genome/src/ast.rs; implement a recursive-descent parser for the EBNF grammar (§8) in grammar.rs; implement the type-checker (I5) in typecheck.rs enforcing the typed AST node table (§8); implement BLAKE3 hashing (P4) in hash.rs; wire genesis-store's RocksDB backend (ADR-05) for content-addressed writes; stand up GitHub Actions ci.yml (ADR-16) running cargo test, cargo clippy, cargo fmt --check.

12.3 Deliverable

genesis-cli parse <file>.gnm parses, type-checks, hashes, and stores a genome; genesis-cli show <hash> retrieves and pretty-prints it.

12.4 Acceptance Criteria

100% of the EBNF grammar (§8) accepted by the parser with zero panics across a 5,000-case proptest corpus; type-checker rejects 100% of the malformed-genome fixture set (§12.5); round-trip parse→hash→store→fetch→pretty-print is byte-identical for 1,000 random genomes; CI green on 3 consecutive PRs.

12.5 Conformance Fixtures

fixtures/genome_basic.gnm — canonical well-typed genome; expected: parses + type-checks. fixtures/genome_malformed_unknown_fn.gnm — undefined identifier; expected: TypeCheckReject{UnknownIdentifier}. fixtures/genome_malformed_shadow.gnm — illegal Let shadowing; expected: reject. fixtures/genome_roundtrip_regression.gnm — pins a previously-buggy hash-stability regression.

12.6 Pitfalls

Hash instability from non-canonical arena ordering — manifests as duplicate store entries for structurally identical genomes; root cause: arena index order not normalized before hashing; debug via lineage_inspector's hash-collision scan; signal: store size grows unexpectedly while genesis_lineage_cycle_detected_total stays zero; recovery: canonicalize the arena via post-order re-index before hashing.

Type-checker accepting shadowed Let bindings — manifests as ambiguous VarRef resolution later; root cause: missing shadow-check in typecheck.rs; debug via targeted proptest; signal: genesis_typecheck_reject_total undercounts known-bad fixtures; recovery: add an explicit shadow-detection pass.

Parser accepting trailing garbage after a valid genome — manifests as silently truncated evaluation later; root cause: missing EOF assertion; debug via fuzz corpus; recovery: require full-input consumption.

12.7 Performance Concerns

Arena-based Vec<Node> storage keeps genome traversal cache-local versus pointer-chasing a tree (Langdon & Poli 2002's size-fair operators assume O(1) node access); BLAKE3 hashing cost is O(genome size), batched at store-write time rather than per mutation attempt.

12.8 Edge Cases

Empty genome (zero-node arena) — rejected at parse time (grammar requires ≥1 expr). Deeply nested Let (>256 levels) — rejected via max_depth (§11 RunConfig) before type-check, bounding stack depth. Duplicate binding names within one Let — rejected (shadowing forbidden, §8). Non-UTF8 identifier bytes — rejected at lex time.

12.9 Failure Analysis

A corrupt RocksDB write (partial flush) is detected via CRC mismatch on next read (I10-adjacent); blast radius limited to the single genome hash; recovery: refetch from an upstream lineage ancestor or re-parse from the retained original .gnm source.

12.10 Operational Notes

genesis_genome_parse_duration_seconds histogram; genesis_typecheck_reject_total counter by reason; structured JSON logs (ADR-13) tagged with genome hash on every reject; no rollback/migration concerns yet (single crate, no live wire protocol).

13.1 Objectives

Build the genesis-sandbox crate's Wasmtime-backed execution path (ADR-02, ADR-03) and the minimal evaluation harness that invokes a compiled WASM module and returns a SandboxResult (§11), using fixed built-in test cases in place of §14's fitness DSL.

fixtures/sandbox_ok.gnm — well-behaved genome; expected: ExitTaxonomy::Ok. fixtures/sandbox_infinite_loop.gnm — fuel exhaustion; expected: FuelExhausted within timeout. fixtures/sandbox_oob_memory.gnm — out-of-bounds linear-memory access; expected: Trap. fixtures/sandbox_escape_replay.gnm — regression pin for a prior escape-adjacent bug.

13.6 Pitfalls

Sandbox escape via shared Engine state — manifests as one candidate influencing another's execution; root cause: mutable state leaked through a shared compiled-module cache; debug via cross-candidate determinism diff; signal: genesis_sandbox_escape_attempts_total; recovery: audit Engine config for interior mutability, isolate per pool shard.

Non-determinism from float reduction order inside numeric ops — manifests as replay divergence (I1) on floating-point-heavy genomes; root cause: unspecified summation order in a Call chain; debug via the sim harness replay-diff; recovery: mandate a canonical left-to-right reduction order in codegen.

13.7 Performance Concerns

A warm module-compile cache keyed by genome-shape hash cuts p95 spawn latency from 4 ms toward 2 ms after warmup (§4); pool checkout uses a lock-free MPMC queue to avoid contention at 4,096 concurrent sandboxes (§4).

13.8 Edge Cases

A genome allocating linear memory right at the 64 MiB ceiling must trap deterministically, never silently truncate. Concurrent pool exhaustion (all sandboxes checked out) blocks the caller under backpressure (P6), never spawns unbounded new instances. A sandbox hanging past 2× the wall-clock ceiling with fuel metering disabled (OCI fallback) is SIGKILLed via the cgroup freezer.

13.9 Failure Analysis

A wedged OCI/gVisor sandbox (SIGKILL ignored) is detected via a liveness heartbeat with a hard external timeout; blast radius: one worker slot, isolated by cgroup; recovery: force-destroy the container's cgroup and network namespace, mark the candidate HostError, continue the generation.

15.1 Objectives

15.2 Detailed Implementation Steps

15.3 Deliverable

genesis-cli mutate <hash> --operator subtree --seed N applies one operator and prints the offspring's hash and whether it passed type-check.

15.4 Acceptance Criteria

100% of 100,000 fuzz-generated operator applications produce either a well-typed offspring or a documented no-op fallback — zero ill-typed genomes ever reach the store (I7); operator-reject rate stays within the 2–5% steady-state band (§8) on the reference fibonacci_repair corpus; each operator's expected-fitness-Δ sign (§8 table) matches the observed distribution within one standard deviation across 10,000 trials.

15.5 Conformance Fixtures

fixtures/mutate_point_basic.gnm — canonical point-mutation case; expected: same-τ replacement. fixtures/mutate_subtree_no_target.gnm — no type-compatible target exists; expected: no-op fallback, not an ill-typed genome. fixtures/mutate_hoist_regression.gnm — pins a prior hoist-mutation type-check bypass bug. fixtures/mutate_size_fair_bloat_control.gnm — verifies size-matched replacement doesn't grow genome size.

15.6 Pitfalls

Subtree mutation silently degrading to always-no-op — manifestation: population diversity collapses; root cause: find_typed_subtree's depth-search budget too small for the type lattice's branching factor; debug via operator-reject-rate telemetry; signal: genesis_operator_reject_total far above the 2–5% band; recovery: widen the search budget or add more terminal types.

Hoist mutation bypassing the type-checker via a cached stale type annotation — manifestation: an ill-typed genome reaches the store; root cause: node_types not recomputed after hoist's root-swap; debug via a store-write assertion; recovery: force a full re-typecheck post-hoist, never trust cached types across a structural edit.

Permutation treating non-commutative Call arguments as swappable — manifestation: a subtle semantic change disguised as permutation; root cause: missing commutativity metadata on the primitive-function signature table (§11); debug via differential testing pre/post permutation; recovery: annotate commutative primitives explicitly, default to non-commutative.

15.7 Performance Concerns

find_typed_subtree is O(genome size) per attempt; bounding attempts (a configurable retry budget) keeps worst-case mutation cost from dominating the generation-cadence budget (§4); size-fair mutation's size-matching adds a second O(genome size) scan, budgeted into the 30–120 s generation cadence (§4).

15.8 Edge Cases

Mutating a single-node (terminal-only) genome — only point mutation is applicable, others fall back to no-op. A genome at max_depth — subtree/hoist must not produce a deeper-than-ceiling result. Concurrent mutation of genomes sharing store-deduplicated subtrees (P4) — copy-on-write ensures no cross-genome mutation.

15.9 Failure Analysis

An operator-reject-rate regression (sustained above 5%) signals either a type-lattice gap or a search-budget regression; detection via a dashboard trend on genesis_operator_reject_total; recovery: roll back the most recent operator-rate config change (P12 change log) at the next checkpoint boundary.

15.10 Operational Notes

16. Phase 4 — Selection & the Generational Loop

16.1 Objectives

Implement genesis-select: tournament selection, Real et al. (2019) AAAI age-based (regularized-evolution) replacement, and the SELECTING → REPLACING → ARCHIVING → ADVANCING arc of the state machine (§8), driving Phases 0–3's genome/sandbox/fitness/mutation crates into a working generational loop.

16.2 Detailed Implementation Steps

Implement tournament.rs: k-way tournament sampling over PopulationRecord.fitness (§11), tie-break by lower size (P8 pre-echo, full parsimony term lands §21); implement regularized.rs: age-based oldest-out replacement per Real et al. (2019), tracking per-genome insertion generation; implement admission control at population-store write (I6) rejecting any batch that would exceed population_size (§11 RunConfig), truncating lowest-fitness overflow; implement the generation-counter increment (I12) as a single-writer atomic in ADVANCING; wire selection pressure as a run-config knob (tournament size k, or age-window for regularized) per Goldberg (1989)'s premature-convergence tuning guidance; implement the replacement-policy dispatch (Generational vs SteadyStateAge, §11) behind one ReplacementPolicy trait so §20's archive-aware variant (Phase 8) can plug in without changing the state machine.

16.3 Deliverable

genesis-cli run --generations N --policy tournament|regularized drives N full generations end-to-end (select → breed via §15/§17 stubs → type-check → replace → archive-stub → advance) against a fixed population and prints per-generation best/mean/worst fitness plus population size.

16.4 Acceptance Criteria

Population size never exceeds population_size across 1,000 generations on a 500-genome reference population (I6, zero violations); tournament selection with k=4 reproduces Goldberg (1989)'s expected selection-intensity curve within 5% across a 10,000-trial statistical fixture; regularized evolution's age distribution matches Real et al. (2019)'s oldest-out property exactly (100% of replaced genomes are the oldest surviving cohort member) on fixtures/regularized_age_order.gnm; generation counter (I12) is strictly monotonic across 10 simulated worker-restart-mid-generation trials.

16.5 Conformance Fixtures

fixtures/select_tournament_k4.gnm — reference population with known fitness distribution; expected: selection-intensity curve within 5% of theory. fixtures/select_regularized_age_order.gnm — pins oldest-out replacement order; expected: exact age-rank match. fixtures/select_population_overflow.gnm — offspring batch exceeding ceiling; expected: truncate-lowest-fitness, I6 holds. fixtures/select_replay_regression.gnm — pins a prior counter-regression bug (I12) under simulated restart.

16.6 Pitfalls

Premature convergence from tournament size set too high — manifestation: fitness variance collapses by generation 20–30 on problems needing exploration; root cause: k too close to population size, selection pressure crowds out diversity (Goldberg 1989); debug via per-generation fitness-variance telemetry; signal: genesis_population_fitness_variance trending to near-zero far earlier than the reference corpus's expected knee; recovery: lower k or switch to regularized evolution's implicit diversity preservation.

Age-tracking drift under checkpoint/resume — manifestation: regularized evolution replaces the wrong cohort after a resume (§22); root cause: age counter reset instead of restored from checkpoint; debug via lineage-DAG cross-check of insertion generation vs stored age; signal: genesis_archive_regression_total-adjacent anomaly in oldest-out order; recovery: persist age as an explicit checkpoint field, never derive from wall-clock.

Off-by-one in population admission control — manifestation: population briefly exceeds ceiling by exactly one offspring batch; root cause: admission check runs before, not after, the full REPLACING batch is materialized; debug via I6 size assertion firing sporadically; recovery: gate admission on the post-batch size, not per-offspring.

Selection collapsing under a stale fitness cache — manifestation: tournament repeatedly picks an already-replaced genome; root cause: PopulationRecord.fitness read from a pre-REPLACING snapshot; debug via generation-boundary read/write ordering trace; recovery: SELECTING must read only the ARCHIVING-committed prior generation.

16.7 Performance Concerns

Tournament selection is O(k) per pick, O(population_size × k) per generation — negligible next to sandbox spawn cost (§4); regularized evolution's oldest-out lookup uses a min-heap on insertion generation for O(log n) eviction rather than a full linear scan; admission control's truncate-lowest-fitness path uses a partial sort (select_nth_unstable) to stay O(n) rather than O(n log n) at 200,000-genome population ceiling (§4).

16.8 Edge Cases

A population where all fitness values are tied — tournament selection falls back to uniform random pick among ties, never panics. Regularized evolution with population size 1 — replacement is a no-op every generation (nothing older exists). An admission batch that is itself larger than population_size — truncated in one pass, never causes a multi-generation size violation. Restarting mid-ADVANCING with a torn generation-counter write — I12's single-writer discipline plus checkpoint CRC (I10) ensures the counter resumes from the last durably committed value, never regresses.

16.9 Failure Analysis

A fitness-variance collapse detected mid-run (P8/§25 FM-3-adjacent) is diagnosed from genesis_population_fitness_variance telemetry alone, without re-running; blast radius: search quality for the remainder of the run, not correctness; recovery: operator lowers tournament k or switches replacement policy at the next checkpoint boundary (§22), no data loss since lineage (I3) permits replay from any earlier generation.

16.10 Operational Notes

genesis_population_fitness_variance gauge per generation; genesis_population_size gauge (I6); genesis_generation_counter monotonic counter (I12); docs/runbooks/premature-convergence.md; selection-policy changes are versioned (P12) and logged in the run's config-change log, consistent with Phase 3's operator-rate table discipline.

17. Phase 5 — Crossover & Type Preservation

17.1 Objectives

Implement genesis-crossover's subtree crossover (Koza 1992) with hard type preservation (P5, I7), completing the BREEDING stage of the state machine (§8) alongside Phase 3's mutation operators.

17.2 Detailed Implementation Steps

Implement subtree_crossover.rs: select one crossover point per parent such that both subtrees share type τ, per §8's crossover semantics; implement the type-compatible point search using the same find_typed_subtree utility Phase 3 built for mutation (shared budget-bounded search, avoiding duplicate O(genome size) scans); implement the depth-search budget as a RunConfig-scoped parameter (§11), consistent with max_depth; implement the clone-parent-A fallback (§8) for when no type-compatible pair exists within budget — crossover must never emit an ill-typed genome (P5); wire the offspring pair through the same TYPE_CHECK gate (I7) mutation offspring pass through, sharing the fallback-operator retry path (§15); extend the primitive-function signature table (§11) with commutativity metadata needed to avoid Phase 3's permutation pitfall (§15.6) resurfacing inside crossover point selection.

17.3 Deliverable

genesis-cli crossover <hashA> <hashB> --seed N produces one or two offspring, prints their hashes, whether each passed type-check, and whether the operation degraded to clone-fallback.

17.4 Acceptance Criteria

100% of 100,000 fuzz-generated crossover pairs produce either a well-typed offspring or a documented clone-fallback — zero ill-typed genomes reach the store (I7), matching Phase 3's bar; clone-fallback rate stays below 8% on the reference fibonacci_repair corpus at max_depth 12 (a rate above this signals a type-lattice gap per §17.6); crossover offspring depth never exceeds max_depth in 50,000 trials; a differential test against Koza (1992)'s canonical subtree-crossover semantics on 20 hand-checked genome pairs matches exactly.

17.5 Conformance Fixtures

fixtures/crossover_basic_pair.gnm — two well-typed parents with a known compatible pair; expected: both offspring well-typed, non-fallback. fixtures/crossover_no_compatible_point.gnm — parents with no shared-τ subtree within budget; expected: clone-fallback of parent A, never ill-typed. fixtures/crossover_depth_ceiling.gnm — a pair whose naive swap would exceed max_depth; expected: rejected candidate point, search continues or falls back. fixtures/crossover_regression_type_bypass.gnm — pins a prior type-checker-bypass bug found via fuzzing.

17.6 Pitfalls

Crossover point search degrading to always-fallback — manifestation: population-wide loss of recombination diversity, visible as a genesis_operator_reject_total-adjacent crossover-fallback-rate spike; root cause: depth-search budget too small relative to type-lattice branching factor, identical class of bug to §15.6's subtree-mutation collapse; debug via fallback-rate telemetry; recovery: widen the budget or add a cheaper coarse pre-filter by top-level type before the full search.

Non-local swap silently violating max_depth — manifestation: an offspring genome exceeds the depth ceiling and is rejected downstream at sandbox codegen instead of at crossover time; root cause: depth check computed pre-swap, not post-swap; debug via a depth-recompute assertion immediately after subtree substitution; recovery: recompute depth post-swap before returning the candidate, reject-and-retry if exceeded.

Commutative-argument mismatch corrupting semantic equivalence assumptions — manifestation: crossover treats two non-commutative Call argument positions as interchangeable during point matching; root cause: missing or stale commutativity metadata reused incorrectly from Phase 3; debug via differential pre/post-crossover execution trace; recovery: default every primitive to non-commutative unless explicitly annotated (same fail-safe default as §15.6).

Shared-subtree aliasing across parents from store deduplication (P4) causing a copy-on-write miss — manifestation: mutating one offspring's subtree corrupts the other parent's stored genome; root cause: crossover output arena not fully copied before substitution; debug via a post-crossover hash-stability check on both original parents; recovery: enforce copy-on-write at the arena level for every crossover output, never share arena slices across genome hashes.

17.7 Performance Concerns

Crossover reuses Phase 3's find_typed_subtree, keeping the per-attempt cost O(genome size) with the same bounded-retry budget; the shared coarse type-lattice pre-filter (§17.6 recovery) trims average search cost below Phase 3's mutation-only baseline since crossover has two candidate trees to filter jointly rather than one; crossover cost is budgeted into the 30–120 s generation cadence (§4) alongside mutation and selection.

17.8 Edge Cases

Crossing a genome with itself (hashA == hashB) — permitted, produces a valid self-recombination offspring, not rejected as degenerate. Two parents whose only shared type is the root type — crossover degrades to a root-level swap, equivalent to whole-genome exchange. A parent at max_depth crossed with a shallow parent — the shallow parent's subtree may be inserted into the deep parent only if the resulting depth stays within ceiling, else fallback. Crossing genomes from different .gns-target export signatures (mismatched primitive-function tables) — rejected at ingest, never attempted (I5-adjacent).

17.9 Failure Analysis

A sustained clone-fallback-rate regression above the 8% acceptance threshold (§17.4) signals either a type-lattice coverage gap or an overly aggressive max_depth shrink in run config; detection via the same dashboard trend pattern as §15.9's operator-reject regression; recovery: roll back the most recent max_depth/budget config change (P12 log) at the next checkpoint boundary, identical remediation path to Phase 3.

17.10 Operational Notes

genesis_crossover_duration_seconds; genesis_crossover_fallback_total by reason (NoCompatiblePoint, DepthCeiling); docs/runbooks/crossover-fallback-spike.md; crossover budget/config changes versioned under the same P12 config-change log as mutation operator rates.

18. Phase 6 — Archive, Lineage & Reproducibility

18.1 Objectives

Complete genesis-store's lineage DAG (I11), wire the full ARCHIVING-stage reproducibility contract (P9, I3), and build the seed+lineage replay harness that Phase 0–5's crates have been referencing since §7's debugging methodology.

18.2 Detailed Implementation Steps

Implement lineage.rs's append-only edge log: every mutation/crossover output writes a (parent_hash[, parent_hash_b], operator, rng_substream_id, child_hash) edge before the child enters the population (P9); implement insert-time cycle detection (I11) rejecting any edge that would close a cycle in the hash-DAG; implement the replay engine: given (seed, RunConfig, .gns spec, lineage edge log), deterministically reconstruct every generation's population and fitness by re-deriving each RNG substream from seed ⊕ lineage_counter (P1, ADR-07) and re-applying the recorded operator sequence; implement the replay-diff harness (§7, referenced by I1's Enforced-At column) comparing two independently produced runs node-by-node; wire durable append-only WAL persistence for the edge log (ADR-23) ahead of periodic RocksDB compaction snapshots.

18.3 Deliverable

genesis-cli replay --seed N --lineage-log <path> --spec <file>.gns --to-generation G reconstructs generation G's population bit-for-bit and diffs it against a recorded reference run, printing PASS/FAIL per genome hash.

18.4 Acceptance Criteria

100% bit-identical replay across 200 independent (seed, config) reference runs up to generation 500 (I1, I3); zero lineage cycles across a 500,000-edge stress-inserted DAG (I11); replay-diff harness detects an intentionally injected float-reduction-order bug in fixtures/lineage_nondeterminism_injected.gnm within one generation of divergence; lineage edge-log WAL recovers to the last fsynced edge after a simulated mid-write crash in 100/100 trials (ADR-23, I10-adjacent).

18.5 Conformance Fixtures

fixtures/lineage_replay_basic.gnm — 50-generation reference run; expected: bit-identical replay. fixtures/lineage_cycle_attempt.gnm — a malformed edge insert that would close a cycle; expected: reject, genesis_lineage_cycle_detected_total increments. fixtures/lineage_nondeterminism_injected.gnm — deliberately reordered float accumulation; expected: replay-diff flags divergence at the exact generation it occurs. fixtures/lineage_wal_crash_recovery.gnm — simulated torn WAL write; expected: recovers to last complete edge, no partial-edge corruption.

18.6 Pitfalls

Non-determinism from parallel float reduction order — manifestation: replay diverges only under multi-worker fan-in, never in single-node reference runs; root cause: a fitness-aggregation or archive-merge step summing floats in worker-arrival order instead of a canonical (e.g. genome-hash-sorted) order; debug via the replay-diff harness run once single-node, once fleet-distributed, comparing divergence generation; signal: genesis_replay_divergence_total nonzero only in fleet mode; recovery: mandate a canonical sort key before every cross-worker float reduction (extends P1's discipline from single-node to fleet-wide).

Lineage DAG unboundedness — manifestation: the WAL and RocksDB store grow without bound across a multi-week run; root cause: no retention/compaction policy on old lineage edges whose genomes have long since left the population and archive; debug via store-size-vs-generation trend; signal: disk usage exceeding the §34 capacity-model projection; recovery: compact edges older than a configurable retention horizon into a summary checkpoint (§22), retaining only archive-cell ancestry chains, not every discarded genome's full history.

Stale-worker result poisoning the lineage log — manifestation: an edge is recorded for a child genome whose evaluation result actually came from a since-retried, superseded worker attempt; root cause: lineage write not gated on the same idempotency key (I14) the scheduler (§19) uses for job dispatch; debug via cross-referencing lineage edges against the dedup ledger; signal: a lineage edge whose (genome hash, generation, attempt) key is not the ledger's accepted attempt; recovery: gate every lineage write on the scheduler's idempotency decision, never write ahead of it.

Cycle check false-negative under concurrent inserts — manifestation: two concurrent edge inserts each individually acyclic together close a cycle; root cause: cycle check read a stale DAG snapshot under concurrent writers; debug via a targeted concurrent-insert stress fixture; recovery: serialize cycle-check-and-insert as one atomic RocksDB transaction, never check-then-insert as two steps.

18.7 Performance Concerns

Lineage edge writes are O(1) append plus an O(depth) ancestor-chain cycle check bounded by max_depth-derived generation depth, not full-DAG traversal; the append-only WAL (ADR-23) amortizes fsync cost via group-commit batching across a generation's edge writes rather than fsyncing per edge, keeping edge-write throughput ahead of the 200,000-genome/generation ceiling (§4); replay reconstruction cost is O(generations × population_size), acceptable for the offline forensic/debug path but never on the hot generational loop.

18.8 Edge Cases

Replaying a run whose .gns spec changed mid-run (an operator error, not a supported path) — rejected at replay time, spec_hash (§11) mismatch detected before any reconstruction attempt. A lineage edge for a genome that was later evicted from the archive and population — retained in the log regardless (P9: reproducibility is unconditional, not archive-scoped). Replay requested past the last durably logged generation — returns the last complete generation plus a partial-progress marker, never fabricates unlogged state. A cycle-check on an empty DAG (first genome ever inserted) — trivially passes, no ancestor to check.

18.9 Failure Analysis

A nonzero genesis_lineage_cycle_detected_total in production (not a fixture) indicates either a scheduler idempotency-key collision or a genuine bug in insert-time serialization; blast radius: the single rejected edge, quarantined per I11's recovery; forensics: lineage_inspector (§10) walks the attempted edge's parent chain to identify the collision point; recovery: reject-and-alert, never auto-merge a cycle.

18.10 Operational Notes

genesis_lineage_cycle_detected_total; genesis_lineage_replay_fail_total; genesis_lineage_wal_fsync_duration_seconds; docs/runbooks/lineage-replay-divergence.md; lineage store schema changes follow the additive-only compatibility rule (§27) shared with GenomeRecord.

fixtures/scheduler_duplicate_dispatch.gnm — simulated retry of an already-completed job; expected: rejected by dedup ledger, genesis_duplicate_job_total increments, no double fitness-apply. fixtures/scheduler_credit_exhaustion.gnm — fleet credit fully consumed; expected: new dispatch blocks, queue depth stays bounded, no unbounded growth. fixtures/scheduler_worker_restart_midjob.gnm — worker dies mid-evaluation; expected: job re-dispatched exactly once under the same idempotency key. fixtures/scheduler_stale_worker_poison.gnm — a stale worker's delayed result arrives after its job was already reassigned; expected: stale result dropped, not applied (ties to §18.6's stale-worker pitfall).

19.6 Pitfalls

Stale-worker result poisoning the population — manifestation: a slow worker's delayed result overwrites a newer, already-applied fitness for the same genome; root cause: result application not re-checked against the dedup ledger's current accepted attempt at apply time, only at dispatch time; debug via correlating result-arrival timestamps against reassignment events; signal: genesis_duplicate_job_total stays zero while population fitness shows an inexplicable regression; recovery: re-validate the idempotency key at result-apply time, not only at dispatch time — the fix generalizes §18.6's lineage-side mitigation to the scheduler's own state.

Credit accounting drift under partial heartbeat loss — manifestation: a worker's advertised credit silently diverges from its true available capacity; root cause: credit renewal message loss not distinguished from an intentional zero-credit signal; debug via per-worker credit-vs-in-flight-job-count cross-check; signal: a worker perpetually shown with negative effective credit; recovery: treat missed heartbeat as credit-zero (fail closed) rather than credit-unknown (fail open).

Backpressure deadlock from a fully circular credit wait — manifestation: the scheduler stalls dispatching to a fleet with nonzero aggregate credit; root cause: a single-queue-per-worker design head-of-line-blocked behind one slow job while credit sits idle elsewhere; debug via per-worker queue-depth-vs-credit dashboard; recovery: work-stealing across worker queues within the same credit budget, never a strict per-worker FIFO that can starve.

Idempotency key collision across generations — manifestation: two distinct evaluation attempts share a dedup key and one is incorrectly dropped; root cause: key composed of only (genome hash, attempt), omitting generation, and P4's content-addressing means the same genome can legitimately recur across generations; debug via ledger-key collision audit; recovery: the key must always be the full (genome hash, generation, attempt) triple per I14's definition, never a subset.

19.7 Performance Concerns

Credit-based flow control adds one round-trip of latency per credit-renewal cycle, amortized by batching multiple job dispatches per credit grant rather than one-credit-per-job; the dedup ledger is sized to in-flight generation width (§4's population ceiling), kept in-memory with periodic WAL flush rather than synchronous durable write per entry, since a ledger-loss-on-crash worst case is a bounded re-verification pass, not silent corruption; gRPC streaming (ADR-08/ADR-09) avoids per-job connection setup overhead that would otherwise dominate at 4,096 concurrent sandboxes (§4).

19.8 Edge Cases

A worker advertising more credit than its configured sandbox-pool concurrency — clamped to the pool's true ceiling, never trusted verbatim. All workers simultaneously stalled — the scheduler holds the generation in AWAIT_RESULTS (§8) until a configurable backpressure timeout, then proceeds with partial results per P3's total-fitness guarantee (missing results map to the worst penalty, same path as a HostError). A single job whose genome hash collides with an in-flight job from a prior generation (P4 dedup) — the dedup ledger's generation field disambiguates, both proceed independently. Network partition splitting the fleet — each partition's workers time out on heartbeat and are marked unhealthy; no split-brain fitness application since results require the scheduler's dedup ledger, which lives with the control plane, not the workers.

19.9 Failure Analysis

A sustained duplicate-job-rate-zero-but-fitness-regression pattern (§19.6) is diagnosed by cross-referencing genesis_duplicate_job_total (flat) against a population fitness dip uncorrelated with selection pressure changes; blast radius: one generation's population quality, recoverable via replay from lineage (I3) once the poisoning root cause is patched; recovery: patch result-apply-time key re-validation, replay affected generations.

19.10 Operational Notes

genesis_duplicate_job_total; genesis_worker_credit_gauge per worker; genesis_scheduler_queue_depth; docs/runbooks/scheduler-backpressure-stall.md, docs/runbooks/stale-worker-poisoning.md; rolling worker-fleet upgrades follow the wire-protocol compatibility rules of §27 (ADR-09's Protobuf schema evolution).

20. Phase 8 — Novelty Search & Quality-Diversity Archive

20.1 Objectives

Implement genesis-population's MAP-Elites behavior-space archive (Mouret & Clune 2015) and novelty search as an alternative/complementary selection pressure (Lehman & Stanley 2011), completing P7's "archive over single-best" principle and I9's archive-monotonicity invariant.

20.2 Detailed Implementation Steps

Implement map_elites.rs: a fixed-resolution behavior-space grid (default 10,000 cells, §4) where each ArchiveCell (§11) holds the highest-fitness (or most-novel) occupant per behavior-descriptor coordinate; implement the behavior-descriptor extraction function as a run-config-pluggable mapping from SandboxResult (§11) case outputs to a low-dimensional descriptor vector, distinct from scalar fitness; implement the archive compare-and-swap write path (I9): a cell is overwritten only if the candidate's fitness (or novelty score) strictly exceeds the current occupant's, enforced atomically to prevent the concurrent-insert race class seen in §18.6; implement novelty scoring (Lehman & Stanley 2011): k-nearest-neighbor distance in behavior-descriptor space against a bounded novelty archive, computed once per candidate per generation; wire an archive-aware ReplacementPolicy variant (§16's pluggable trait) so a run can select for novelty, fitness, or a weighted blend.

20.3 Deliverable

genesis-cli archive-status prints per-cell occupancy, coverage percentage, and mean cell fitness; genesis-cli run --selection novelty|map-elites|blend drives the generational loop under the chosen quality-diversity pressure; archive_viewer (§10) renders the grid.

20.4 Acceptance Criteria

Zero archive regressions (a cell overwritten by a strictly worse occupant) across 1,000,000 simulated concurrent-write trials (I9); archive coverage on the reference sorting_synthesis corpus reaches at least 40% of the 10,000-cell grid within 200 generations under novelty-driven search, versus under 15% under scalar-fitness-only search on the same corpus (reproducing Lehman & Stanley 2011's coverage-advantage finding); k-nearest-neighbor novelty scoring completes within the per-generation cadence budget (§4) at k=15, population 10,000; archive disk footprint matches the §4 projection (≈40 MiB per generation snapshot at default grid size) within 10%.

20.5 Conformance Fixtures

fixtures/archive_cas_race.gnm — two candidates racing for the same cell; expected: strictly-better-wins, no regression (I9). fixtures/archive_coverage_novelty.gnm — reference corpus run under novelty search; expected: ≥40% coverage by generation 200. fixtures/archive_coverage_scalar_baseline.gnm — same corpus under scalar-fitness-only; expected: <15% coverage, establishing the comparison baseline. fixtures/archive_descriptor_malformed.gnm — a behavior descriptor outside the configured grid bounds; expected: clamped to the nearest valid cell, never a silent out-of-bounds write.

20.6 Pitfalls

Archive unboundedness from an unbounded novelty-comparison set — manifestation: novelty scoring cost grows without bound across a multi-week run as the comparison archive accumulates every historically novel genome; root cause: no cap on the novelty archive's retained-genome count; debug via per-generation novelty-scoring-duration trend; signal: genesis_novelty_score_duration_seconds growing generation-over-generation; recovery: bound the novelty archive to a fixed-size reservoir sample (age- or novelty-weighted eviction), never let it grow with run length.

Premature convergence masked by archive occupancy alone — manifestation: archive coverage looks healthy while scalar-fitness progress has actually stalled; root cause: reading coverage in isolation without also tracking mean-cell-fitness trend; debug via joint coverage + mean-fitness dashboard (extends §16.6's diagnosis pattern to the archive path); recovery: pair every coverage metric with a fitness-trend metric, treat coverage alone as necessary but not sufficient evidence of healthy search.

Behavior-descriptor degeneracy collapsing diversity into few cells — manifestation: most candidates map to a small cluster of cells despite genome-level diversity; root cause: descriptor dimensions chosen too coarse or correlated with each other, not spanning the true behavior space; debug via descriptor-value distribution histogram across a random-genome sample; recovery: redesign descriptor extraction (operator-config change, versioned per P12), never silently widen grid resolution as a substitute for a better descriptor.

Archive compare-and-swap race under distributed writers — manifestation: two workers' results for the same behavior cell interleave incorrectly across the scheduler (§19); root cause: CAS implemented as read-then-write across a network round-trip instead of an atomic RocksDB transaction; debug via a targeted concurrent-write stress fixture, same failure class as §18.6's cycle-check race; recovery: the archive write must be one atomic transaction server-side, never a client-observed read followed by a separate write.

20.7 Performance Concerns

MAP-Elites grid lookup is O(1) (direct descriptor-to-cell-index mapping); k-nearest-neighbor novelty scoring is the dominant added cost at O(archive size × k) per candidate — bounded by the reservoir cap (§20.6) to keep pace with the 30–120 s generation cadence (§4); archive snapshot writes (ADR-24) batch all cell updates for a generation into one RocksDB write-batch rather than per-cell transactions, avoiding write-amplification at 10,000 cells/generation.

20.8 Edge Cases

A candidate whose behavior descriptor lands exactly on a grid boundary — resolved by a fixed, documented rounding convention (round-half-to-even), never platform-dependent float rounding. An empty archive at generation 0 — every candidate's first write always succeeds (I9 vacuously holds, nothing to be "strictly better" than). A run configured with grid resolution larger than the population ceiling — permitted; most cells simply stay unoccupied, coverage percentage reported accordingly. Novelty search with k larger than the current archive size — degrades to full-archive distance computation, never errors.

20.9 Failure Analysis

A behavior-descriptor degeneracy incident (§20.6) is detected from a coverage plateau despite continued fitness gains; blast radius: search-quality only, no correctness violation; recovery: operator redesigns the descriptor extraction function at the next checkpoint boundary (§22) and the run resumes with the new descriptor, prior archive cells retained but new writes use the updated mapping — a documented, versioned discontinuity, not silently blended.

20.10 Operational Notes

genesis_archive_coverage_ratio gauge; genesis_archive_regression_total (I9); genesis_novelty_score_duration_seconds; docs/runbooks/archive-coverage-plateau.md; descriptor-function changes are versioned (P12) and recorded in the config-change log alongside operator rates and selection-policy changes.

21. Phase 9 — Bloat Control & Parsimony Pressure

21.1 Objectives

Implement continuous parsimony pressure (P8) as a size-adjusted fitness term active from generation 0, and reconcile it with Phase 3's size-fair mutation (§15) to give Langdon & Poli (2002)'s bloat theory an operational, measurable mitigation.

21.2 Detailed Implementation Steps

Implement a size-adjustment term in the fitness-compiler's scoring path (§14): adjusted_fitness = raw_fitness − parsimony_coefficient × size, applied post-penalty-mapping (I4) so a crashed candidate's total-fitness guarantee is unaffected; implement parsimony-coefficient bounds and validation in RunConfig (§11) — a coefficient of 0 recovers Phase 2's original unadjusted behavior, verifying backward compatibility; implement bloat-trend telemetry: mean/median genome size per generation, tracked independently of fitness; wire size-fair mutation's (§15) size-matched replacement rate as a second, orthogonal bloat lever alongside the fitness-term coefficient; implement an automatic bloat-alert threshold (mean size growth rate exceeding a configurable multiple of the reference corpus's expected growth curve, per Langdon & Poli 2002) feeding §26 telemetry.

21.3 Deliverable

genesis-cli run --parsimony-coefficient C runs the generational loop with the size-adjusted fitness term active; genesis-cli bloat-report prints mean/median/max genome size per generation and flags any run exceeding the bloat-alert threshold.

21.4 Acceptance Criteria

With parsimony_coefficient at the reference-tuned default, mean genome size growth across 500 generations on the sorting_synthesis corpus stays within 1.5× its generation-0 mean size (versus unbounded growth exceeding 8× observed with coefficient 0, reproducing Langdon & Poli 2002's bloat prediction); adjusted-fitness ranking never reorders two candidates whose raw fitness differs by more than 10× the parsimony term's maximum possible contribution (guards against parsimony dominating raw fitness); zero cases of a Trap/HostError penalty (I4) being altered by the size-adjustment term across 10,000 fuzzed candidates (penalty floor stays a size-independent constant).

21.5 Conformance Fixtures

fixtures/parsimony_bloat_baseline.gns — 500-generation run with coefficient 0; expected: size growth exceeds 8× baseline, establishing the unmitigated-bloat reference. fixtures/parsimony_bloat_controlled.gns — same run with tuned coefficient; expected: size growth stays within 1.5×. fixtures/parsimony_penalty_floor_unaffected.gns — a Trap-exit candidate under size adjustment; expected: penalty constant identical regardless of candidate size. fixtures/parsimony_ranking_stability.gns — pins a case where a large fitness gap must not be reordered by the size term.

21.6 Pitfalls

Code bloat despite an active parsimony term — manifestation: mean size still grows steadily, just slower than uncontrolled; root cause: coefficient tuned too low relative to the fitness landscape's raw-score scale, or size-fair mutation rate too low to counter crossover-driven size drift (§17); debug via the bloat-report trend against the §21.4 reference curve; signal: genesis_genome_mean_size trending above the 1.5× threshold; recovery: autotune the coefficient (§22) rather than hand-tune per run.

Parsimony term dominating and collapsing search into trivial small genomes — manifestation: population converges to minimal-size, low-raw-fitness genomes; root cause: coefficient set too high relative to the raw-fitness scale, size term overwhelms objective signal; debug via adjusted-vs-raw fitness divergence trend; signal: mean genome size dropping toward the terminal-only floor while raw fitness stagnates; recovery: lower the coefficient, verify against the §21.4 ranking-stability bound.

Fitness-function gaming via size-invariant shortcuts — manifestation: a candidate exploits a .gns case weighting to score well with degenerate near-constant logic, appearing not to be bloat but actually a fitness-oracle gap; manifestation overlaps with §14.6's fitness-gaming pitfall; root cause: parsimony pressure treated as a substitute for held-out case coverage, which it is not; debug via held-out case injection (§14.6's remedy) alongside bloat metrics; recovery: address via .gns spec design, not the parsimony coefficient — the two failure classes must not be conflated operationally.

Size-fair mutation rate and parsimony coefficient fighting each other — manifestation: bloat-control levers produce oscillating mean-size trends generation-to-generation instead of monotonic control; root cause: both levers tuned independently without joint calibration; debug via cross-correlating size-fair mutation rate changes against mean-size derivative; recovery: treat the two levers as one joint bloat-control config unit, autotuned together (§22), never adjusted independently mid-run.

21.7 Performance Concerns

The size-adjustment term is an O(1) arithmetic addition per candidate post-scoring, negligible against sandbox evaluation cost (§4); bloat-trend telemetry aggregation (mean/median/max size) is computed once per generation over the population, O(population_size), well within the generation-cadence budget; unmitigated bloat's real performance cost is indirect — larger genomes increase per-candidate sandbox compile time (§13.7) and WASM module size, which is why parsimony pressure is a first-class performance concern, not merely a search-quality one.

21.8 Edge Cases

A genome at the minimum size (a single terminal) — the parsimony term contributes its minimum (near-zero) penalty, never a negative adjusted fitness beyond the raw floor. A .gns spec with an extremely narrow fitness range — the parsimony coefficient must be scaled relative to the observed fitness range (§21.6), not a fixed absolute constant, to avoid unintentionally dominating. Coefficient set to a negative value (rewarding larger genomes) — rejected at RunConfig validation, not a supported mode. Two genomes of identical size and identical raw fitness — tie-broken by generation order (oldest wins), consistent with §16's regularized-evolution tie-break convention.

21.9 Failure Analysis

A bloat-alert threshold breach mid-run is diagnosed via the joint bloat-report/fitness-trend dashboard without re-running the search (P11); blast radius: evaluation cost and generation cadence degrade (§30), not correctness; recovery: operator applies an autotuned coefficient adjustment (§22) at the next checkpoint boundary, run resumes without replay since prior generations remain valid and reproducible (I3).

21.10 Operational Notes

genesis_genome_mean_size / genesis_genome_max_size gauges per generation; genesis_bloat_alert_total; docs/runbooks/bloat-growth-alert.md; parsimony-coefficient and size-fair-rate changes are versioned jointly (P12) as one bloat-control config unit.

22. Phase 10 — Checkpoint/Resume & Operator Autotuning

22.1 Objectives

Implement genesis-checkpoint: crash-consistent snapshot/resume (I10) satisfying the 30 s control-plane RTO (§4), and operator-rate/parsimony-coefficient autotuning per Poli, Langdon & McPhee (2008)'s practical tuning heuristics.

22.2 Detailed Implementation Steps

Implement snapshot.rs: an atomic-rename-plus-fsync write path producing a versioned Protobuf snapshot (ADR-24) embedding RunConfig (§11) verbatim, the current generation's population (genome hashes only, P4), archive state (§20), and a pointer to the last durably logged lineage edge (§18); implement CRC validation on load (I10) rejecting a torn snapshot and falling back to the previous generation's checkpoint; implement autotune.rs: a bounded-adjustment controller that nudges operator rates, tournament k / age-window, and the joint bloat-control unit (§21) only at checkpoint boundaries (P12), using the same telemetry signals §16/§20/§21 already emit (fitness variance, archive coverage, mean genome size trend) as its control inputs; implement resume: reload the snapshot, replay lineage edges since the snapshot pointer (§18) to reach exact pre-crash state, and resume the state machine (§8) at ADVANCING.

22.3 Deliverable

genesis-cli checkpoint --now forces an out-of-band snapshot; genesis-cli resume --from <snapshot> restores full run state and continues the generational loop; genesis-cli autotune-report prints the autotuning controller's decision log since run start.

22.4 Acceptance Criteria

Control-plane recovery from a killed process completes within the 30 s RTO (§4) in 100/100 trials on the reference 200,000-genome-population checkpoint; CRC validation rejects 100% of 500 deliberately corrupted snapshot fixtures, falling back to the prior generation's checkpoint every time (I10); autotuning converges tournament k and parsimony coefficient to within 10% of the hand-tuned reference values (§16.4, §21.4) within 50 autotuning-eligible checkpoints on the reference corpus; resumed runs replay bit-identically to an uninterrupted reference run through generation 500 (I1, I3 — extends §18.4's replay bar across a crash/resume boundary).

22.5 Conformance Fixtures

fixtures/checkpoint_crash_mid_write.gnm — simulated kill during snapshot write; expected: torn snapshot detected via CRC, fallback to prior checkpoint. fixtures/checkpoint_resume_bitidentical.gnm — resume-then-replay compared against an uninterrupted reference run; expected: bit-identical through generation 500. fixtures/autotune_convergence_reference.gnm — 50-checkpoint autotuning run; expected: converges within 10% of hand-tuned reference. fixtures/checkpoint_rto_budget.gnm — timed recovery on the reference population size; expected: under 30 s.

22.6 Pitfalls

Autotuning oscillation from overlapping control loops — manifestation: operator rates and the bloat-control unit (§21) each independently autotuned end up fighting, producing oscillating rather than converging telemetry trends; root cause: separate controllers acting on correlated signals (fitness variance and mean-size trend both react to selection-pressure changes) without joint awareness; debug via cross-correlating consecutive autotuning decisions against the telemetry deltas that triggered them; recovery: autotune as one joint controller with a single bounded-step-size policy across all levers, never as independent per-lever controllers (extends §21.6's joint-tuning lesson to the full autotuning surface).

Checkpoint RTO regression from an unbounded lineage-replay-since-snapshot window — manifestation: resume time grows with time-since-last-checkpoint instead of staying bounded; root cause: checkpoint cadence configured too sparse relative to generation cadence, forcing a long lineage replay (§18) on every resume; debug via resume-time-vs-checkpoint-interval trend; signal: RTO budget (§4) breached only after long inter-checkpoint gaps; recovery: bound checkpoint interval as a function of the RTO budget divided by observed per-generation lineage-replay cost, not a fixed generation count.

Snapshot embedding stale RunConfig after a live config change — manifestation: a resumed run silently reverts an operator-rate change an operator made between checkpoints; root cause: config-change log (P12) applied in-memory but not flushed into the next snapshot atomically with the config-change log entry; debug via diffing snapshot RunConfig against the config-change log's latest entry timestamp; recovery: snapshot writer must read the config-change log's current head atomically with population state, same atomicity discipline as the lineage-edge/result-apply ordering fix in §19.6.

Autotuning drifting parameters outside validated bounds — manifestation: the parsimony coefficient (§21) or tournament k (§16) autotunes past the range those phases' acceptance criteria were validated against; root cause: autotuning step bounds not clamped to the same validated ranges §16.4/§21.4 establish; debug via an out-of-validated-range alert on every autotuning decision; recovery: clamp autotuning to the validated envelope, require explicit operator override to exceed it.

22.7 Performance Concerns

Snapshot write cost scales with population size (genome hashes only, not full genomes, per P4) plus archive cell count (§20) — the §34 capacity model's checkpoint-size estimate bounds this; CRC validation on load is O(snapshot size), negligible against the RTO budget (§4); autotuning decision computation runs once per checkpoint boundary, not per generation, keeping its overhead orders of magnitude below the generation-cadence budget.

22.8 Edge Cases

Resuming from a snapshot whose .gns spec_hash no longer matches an available compiled EvaluationPlan — rejected at resume time, requires the operator to supply the original spec (I13-adjacent, spec content-addressed like genomes). Forcing a checkpoint mid-generation (between EVALUATING and SELECTING) — the snapshot captures the partially-evaluated state explicitly, resume re-enters AWAIT_RESULTS rather than re-dispatching completed jobs. Autotuning with fewer than the minimum eligible checkpoints observed — the controller holds parameters at their configured defaults rather than acting on insufficient signal. A resume request targeting a snapshot older than the lineage retention horizon (§18.6) — rejected, since full replay-since-snapshot is no longer possible; operator must resume from a more recent checkpoint.

22.9 Failure Analysis

A resume that fails CRC validation on every available checkpoint (cascading corruption) is a page-worthy incident; forensics: lineage_inspector (§10) walks back to the last known-good lineage edge independent of any snapshot; recovery: rebuild population state from the lineage DAG (I3) directly, bypassing snapshots entirely — the slow but always-available fallback path P9 exists to guarantee.

22.10 Operational Notes

genesis_checkpoint_write_duration_seconds; genesis_checkpoint_corrupt_total (I10); genesis_autotune_adjustment_total by parameter; docs/runbooks/checkpoint-corruption-cascade.md, docs/runbooks/autotune-oscillation.md; checkpoint format version bumps follow §27's SemVer/migration-tooling rules.

23. Phase 11 — Conformance Suite & Performance Hardening

23.1 Objectives

Complete genesis-conformance: the deterministic sim harness (§7's debugging methodology) asserting all fourteen invariants (I1–I14) per generation, the golden-fixture runner aggregating every phase's §N.5 fixtures, and CI-gated performance-regression enforcement against the §4/§30 targets.

23.2 Detailed Implementation Steps

Implement sim.rs: a mocked-sandbox, mocked-clock generational-loop simulator that runs the full state machine (§8) at high speed, asserting one check per invariant (I1–I14) every generation and capturing a minimal reproducing (seed, generation, genome-hash) tuple on any failure; implement golden.rs: a runner that executes every fixtures/* file referenced across §12–§22's N.5 subsections and asserts the documented expected outcome, wired into conformance.yml (§10 CI workflows); implement the property-test suite (ADR-14/proptest) verifying type preservation (P5) holds across randomly generated mutation/crossover sequences and fitness totality (P3) holds across randomly generated .gns specs and candidate genomes; implement perf-gate.yml's CI job comparing benchmark output (benchmarks/, §10) against the §30 M-table targets, failing the build on regression beyond a configured tolerance band; implement fuzzing corpus integration (ADR-15/cargo-fuzz) for the genome-IR and .gns parsers (§10 fuzz/), seeded from conformance/fixtures/.

23.3 Deliverable

genesis-cli conformance run executes the full golden-fixture + sim-harness + property-test suite and prints a pass/fail matrix keyed by invariant ID and fixture name; make perf-gate runs the benchmark suite against the §30 targets locally, matching CI.

23.4 Acceptance Criteria

100% of every N.5 fixture across §12–§22 passes under golden.rs (zero silently-skipped fixtures — a CI check asserts fixture-file-to-assertion coverage); the sim harness runs 10,000 simulated generations with zero I1–I14 assertion failures on the reference corpus; property tests execute at least 1,000,000 total cases across type-preservation and fitness-totality properties per CI run with zero counterexamples; perf-gate.yml catches a deliberately introduced 20% eval/s regression in fixtures/perf_regression_injected/ within one CI run.

23.5 Conformance Fixtures

fixtures/conformance_full_matrix.gnm — meta-fixture asserting every §12–§22 fixture file is registered and exercised; expected: 100% coverage, zero orphaned fixtures. fixtures/sim_invariant_sweep.gnm — 10,000-generation sim-harness run; expected: zero I1–I14 failures. fixtures/perf_regression_injected/ — a deliberately slowed sandbox-spawn path; expected: perf-gate.yml fails the build. fixtures/property_type_preservation_seed_corpus/ — seed corpus for the type-preservation property test; expected: zero counterexamples across 1,000,000 generated cases.

23.6 Pitfalls

Fixture coverage rot — manifestation: a new fixture is added to a phase's §N.5 list in the blueprint but never actually wired into golden.rs; root cause: no automated cross-check between documented fixtures and registered test cases; debug via the conformance_full_matrix meta-fixture (§23.5); signal: a fixture file present on disk but absent from the coverage report; recovery: CI fails the build on any fixture-registration gap, not just on fixture failure.

Property-test shrinking masking the true minimal counterexample — manifestation: a proptest failure reports an overly complex genome instead of proptest's shrunk minimal case; root cause: a custom Arbitrary impl for GenomeRecord that doesn't implement shrinking correctly for tree-shaped IR; debug via manually re-shrinking a reported failure; recovery: implement tree-aware shrinking (subtree removal before leaf mutation) rather than relying on proptest's default derive.

Sim harness diverging from the real generational loop's behavior — manifestation: sim passes but production exhibits an invariant violation the simulator never caught; root cause: the mocked sandbox/clock omits a real-world code path (e.g. actual Wasmtime fuel-exhaustion timing jitter); debug via comparing sim-harness assertions against production telemetry for the same invariant; recovery: periodically replay a real captured production trace through sim to detect simulator/reality drift, don't trust the simulator as the sole conformance gate indefinitely.

Perf-gate false positives from noisy CI runners — manifestation: perf-gate.yml flags a regression that isn't real, blocking unrelated PRs; root cause: shared/noisy CI hardware (ADR-16 hosted runners) without statistical tolerance banding; debug via historical benchmark variance analysis (docs/performance/); recovery: require N repeated benchmark runs with a median-based comparison and a documented tolerance band before failing the gate, never a single noisy sample.

23.7 Performance Concerns

The sim harness must run orders of magnitude faster than real sandbox-backed evaluation (mocked sandbox returns synthetic SandboxResults) to make 10,000-generation sweeps CI-tractable; property-test case counts are budgeted against CI wall-clock limits, favoring many cheap generated cases over few expensive ones; fuzzing runs on a scheduled cadence (fuzz.yml, §10) rather than per-PR to avoid blocking the fast-CI-feedback loop while still accumulating corpus coverage over time.

23.8 Edge Cases

A fixture referenced in a phase's §N.5 text but whose file was renamed without updating the blueprint — caught by the conformance_full_matrix cross-check, treated as a documentation bug, not a silent gap. A property test whose generator can produce a genome exceeding max_depth — the generator itself must respect run-config bounds, or the test asserts rejection rather than treating it as a counterexample. A perf-gate benchmark run on a differently-provisioned CI runner tier — the tolerance band (§23.6) is relative to that runner tier's own historical baseline, never an absolute cross-tier number. Zero fixtures registered for a hypothetical future phase — the coverage check fails loudly rather than vacuously passing.

23.9 Failure Analysis

A conformance-suite regression (any of golden/sim/property/perf-gate) blocks merge by CI design (ADR-16 workflow gating); forensics: the failing fixture or minimal counterexample tuple is attached to the CI run artifact, enabling direct reproduction via genesis-cli conformance run --only <fixture> without re-running the full suite.

23.10 Operational Notes

genesis_conformance_pass_rate per suite (golden/sim/property/perf-gate); docs/runbooks/conformance-regression.md; conformance suite versioning tracks the blueprint's own phase numbering — a new phase's fixtures are added to the suite in the same PR that adds the phase's implementation, never retroactively.

27. Compatibility & Versioning

Genome IR versioning: GenomeRecord's Cap'n Proto schema (ADR-04) evolves additive-only — new Node variants may be appended, never renumbered or removed; a genome parsed under an older schema version round-trips unchanged under a newer reader (schema evolution ergonomics, ADR-04's rationale).

Fitness-DSL grammar evolution: .gns grammar (§8) changes are versioned via a spec_version field in FitnessSpec (§11); a new grammar version may add objective/constraint forms but must not silently reinterpret an existing construct's semantics — an incompatible change requires a new major spec_version and an explicit migration note in CHANGELOG.md.

Archive format migration: ArchiveCell/behavior-descriptor schema changes (ADR-24, Protobuf) follow the same additive-only discipline as the genome schema; a behavior-descriptor dimensionality change is treated as a breaking migration requiring an explicit archive-rebuild pass (re-scoring existing occupants under the new descriptor), never an in-place reinterpretation of old cell coordinates.

Operator-catalogue versioning: the mutation/crossover operator catalogue (§8) is versioned alongside RunConfig.operator_rates (P12); adding a new operator is additive and backward-compatible (older runs simply never reference it); removing or redefining an operator's semantics requires a major version bump and is disallowed mid-run (P12's immutable-per-run-config guarantee).

API stability: genesis.proto (ADR-08/ADR-09) follows Protobuf's field-numbering discipline — fields are never renumbered or reused; new RPCs are additive; a breaking RPC signature change requires a new service version served alongside the old one during the rolling-upgrade window (§26 canary/rollback).

Migration tooling: genesis-cli migrate --from-version V --to-version V+1 runs schema-specific migration passes (genome schema, archive schema, checkpoint format) registered per version pair; every migration is dry-run-capable and idempotent.

Cross-crate version skew: because genesis-worker and genesis-api may run mixed versions during a rolling upgrade (§26), the migration tool's version-pair registry must cover every adjacent version pair a fleet could legitimately observe mid-rollout, not just the latest-to-latest jump.

Deprecation: a deprecated grammar construct, operator, or RPC is marked #[deprecated]/flagged in .gns compiler warnings for at least one minor version before removal, consistent with SemVer (ADR-19/ADR-22's release discipline).

SemVer: major bumps for breaking IR/DSL/API changes; minor for additive schema/grammar/operator additions; patch for bug fixes with no schema impact; every release is cosign-signed (ADR-19) and tagged accordingly.

Version-skew testing: the conformance suite (§23, §28) runs a dedicated mixed-version fixture set — an N-1 worker against an N control plane, and vice versa — on every release candidate, verifying the rolling-upgrade guarantee below actually holds before it is relied upon in production.

Rolling-upgrade guarantees: a genesis-worker fleet may run mixed versions across a bounded upgrade window (§26 canary) as long as both versions share the same major genesis.proto/genome-schema version; the scheduler's idempotency ledger (I14) is version-agnostic by design, so mixed-version dispatch never double-applies results.

28. Testing & Verification Strategy

Unit tests: per-crate coverage of parser/type-checker (genesis-genome, I5), mutation/crossover operators (I7), fitness-compiler penalty mapping (I4), archive CAS (I9) — each crate's unit suite ties directly to its owning invariant.

Scheduler unit tests: dedup-ledger insertion/eviction (I14), credit accounting under simulated heartbeat loss (§19.6), and work-stealing dispatch fairness (§19.6's head-of-line-blocking fix) are unit-tested in isolation from the full fleet-integration path, keeping the fast-feedback CI loop (§23.7) fast.

Integration tests: end-to-end generational-loop runs across genesis-genome → genesis-mutate/crossover → genesis-fitness → genesis-sandbox → genesis-select → genesis-population, exercised via genesis-cli run against the reference corpora (fibonacci_repair, sorting_synthesis, §10).

Property tests (ADR-14/proptest): type preservation — every mutation/crossover output is well-typed or a documented no-op/clone-fallback (P5, I7, tied to §15.5/§17.5 fixtures); crossover produces well-typed offspring specifically (§17.4); fitness is total — every (genome, .gns spec) pair yields a finite fitness (P3, I4, tied to §14.5/§21.5 fixtures).

Differential testing: crossover semantics checked against Koza (1992)'s canonical subtree-crossover definition (§17.4); regularized-evolution replacement order checked against Real et al. (2019)'s oldest-out property (§16.4).

Tooling correctness: lineage_inspector and archive_viewer (§10, §39) are themselves covered by integration tests against a known-good lineage/archive fixture, since T14's insider-tooling threat assumes these tools are trustworthy read paths — an untested tool would undermine that assumption silently.

Fuzzing (ADR-15/cargo-fuzz): genome IR parser and .gns DSL parser (§10 fuzz/), seeded from conformance/fixtures/, run on a scheduled cadence (fuzz.yml, §23.7) accumulating corpus coverage.

Fuzz-to-fixture promotion: any crash or panic found by fuzz.yml is triaged and, once fixed, promoted into conformance/fixtures/ as a permanent named regression fixture — the fuzz corpus and the golden-fixture suite are not independent, the former continuously feeds the latter.

Chaos testing: simulated worker kill-mid-job (I14, §19.4), simulated mid-write checkpoint crash (I10, §22.4), simulated network partition (FM-2, §25) — all exercised as first-class conformance fixtures, not ad hoc manual drills.

Regression testing: every fixed bug across §12–§23's Pitfalls (N.6) subsections gets a permanent regression fixture (the *_regression.* naming convention used throughout §12.5–§23.5) so a reintroduced bug fails CI immediately rather than resurfacing in production telemetry months later.

Deterministic replay from seed and lineage: the replay-diff harness (§18) is the canonical verification mechanism for I1/I3 — every reference run has a pinned replay fixture asserting bit-identical reconstruction.

Soak testing: a 10,000-generation sim-harness sweep (§23.4) stands in for a multi-week wall-clock soak, asserting I1–I14 continuously; a lower-frequency real-sandbox soak (weekly, non-blocking CI) validates the mocked-vs-real drift concern raised in §23.6.

Fault injection: deliberately corrupted checkpoints (§22.5), deliberately reordered float accumulation (§18.5), deliberately poisoned stale-worker results (§19.5) — each a named fixture, not a one-off manual test.

Conformance: the full golden-fixture matrix (§23.2) aggregates every phase's §N.5 fixtures with the coverage cross-check (§23.6) preventing fixture-registration rot.

Performance-regression gating: perf-gate.yml (§23.2, §30) blocks merge on a statistically-tolerance-banded regression against the §30 M-table targets, using a median-of-5-runs sampling policy over the three benchmarks/ criterion suites (§39) to keep hosted-runner noise (§23.6) from producing false-positive gate failures.

29. Build & Release Engineering

Reproducible builds: pinned rust-toolchain.toml (§10) plus a fully vendored dependency tree (ADR-18) ensures a given commit hash produces a bit-identical binary across build hosts; Docker multi-stage distroless build (ADR-17) minimizes both attack surface and non-determinism from base-image drift.

Artifact signing: every tagged release is cosign-signed (ADR-19, sigstore) before publication; genesis-worker and genesis-api container images carry a verifiable signature checked at deployment time.

SBOM: a software bill of materials is generated per release from the vendored dependency tree (ADR-18), published alongside the signed artifact for downstream audit.

SBOM diffing: release.yml diffs each release's SBOM against the prior release's, flagging any new transitive dependency for an explicit cargo-vet review even if the direct dependency itself did not change (T6's supply-chain mitigation extended to transitive drift).

Release channels: stable (SemVer-tagged, cosign-signed, §27), nightly (tracks HEAD, unsigned, research-cluster only per ADR-19's rejected-alternative note), canary (§26's fleet-upgrade canary batch, a stable-candidate pre-release).

CI/CD topology: GitHub Actions (ADR-16) runs ci.yml (build+test+lint) on every PR, conformance.yml (§23) on every PR, fuzz.yml on a schedule, perf-gate.yml (§30) on every PR against main, release.yml (cosign-signed build) on tag push.

Version stamping: every binary embeds its SemVer tag, commit hash, and build timestamp, surfaced via genesis-cli version and included in every telemetry stream's resource attributes (§26).

Provenance/attestation: release.yml produces SLSA-style build provenance attesting the exact CI job, commit, and dependency set that produced each signed artifact.

Rollback provenance: a rolled-back release retains its original provenance attestation rather than being re-attested under the rollback event, so the audit trail always shows what actually ran at every point in time, not a revised history.

Dependency auditing: cargo-vet (ADR-18) gates any new or updated dependency behind a manual security review recorded in docs/adr/ before it can land, consistent with the supply-chain mitigation for T6.

Release cadence: stable releases follow the phase-arc milestones (§40 Appendix B) — a release is cut once a phase's conformance suite (§23) clears its full fixture matrix, never on a fixed calendar cadence independent of phase completion.

31. Scalability Analysis

What stays constant as population/generations grow: per-candidate sandbox spawn cost (O(1) amortized, warm module cache, §13.7); per-candidate fitness-scoring cost (fixed EvaluationPlan, I13, O(cases) not O(population)); type-checker cost per genome (O(genome size), independent of population size).

What grows, with Big-O: scheduler queue/credit bookkeeping O(population_size) per generation; lineage DAG size O(population_size × generations) before retention compaction (§18.6); archive store O(grid cells), bounded and generation-independent once at steady occupancy (§20); dedup ledger O(in-flight generation width) (I14); checkpoint size O(population_size + archive cells) per snapshot (§22, quantified in §34).

Named bottlenecks, in order: (1) sandbox spawn rate — the dominant per-candidate fixed cost (§4 M3–M6), gates raw eval throughput before anything else; (2) evaluation wall clock — heavy .gns suites (M2) multiply spawn cost by case count, dominating generation cadence (M9) once suites exceed a few dozen cases; (3) archive I/O — RocksDB write-batch cost at 10,000+ cells/generation (§20.7) becomes visible only after (1) and (2) are no longer the constraint, typically at fleet scale beyond ~32 workers.

Horizontal scaling: adding genesis-worker nodes linearly increases aggregate eval/s up to the point where scheduler dispatch overhead (§19.7) or archive-write contention (§20.7) becomes the binding constraint — the practical ceiling is FD-bound before CPU-bound at 4,096 concurrent sandboxes per the default fleet (§4).

Vertical scaling: more sandboxes/node raises per-node throughput until FD budget (65,536 ulimit, §4) or host CPU core count binds; OCI/gVisor fallback candidates scale far worse per-core than Wasmtime candidates (ADR-03), so a fleet with a high native-target fraction hits its vertical ceiling much earlier.

Population sharding / island models: beyond a single control plane's 200,000-genome ceiling (M8), the natural next lever is an island model — independent sub-populations each with their own scheduler/archive shard, periodically exchanging migrants via a lineage-tagged crossover-import path; this is a documented extension point, not built in Phases 0–11 (no PhaseDeferred marker — it is future scope beyond this blueprint's stated arc, distinct from the tracked deferrals in §37).

Coordination overhead: credit-renewal round-trips (§19.7) and archive CAS contention (§20.7) both grow sub-linearly with worker count under the current design (bounded MPSC + atomic RocksDB transactions), but cross-shard migrant exchange in an island model would introduce a new coordination axis outside this design's current scope.

Practical scaling checklist, in the order an operator should apply levers as a run approaches its ceiling: (1) verify sandbox spawn rate is still the binding bottleneck via the §26 fleet-health dashboard before adding workers; (2) add genesis-worker nodes up to the FD-bound ceiling (§34); (3) only past that ceiling, consider .gns suite trimming (fewer, better-chosen cases) before considering the deferred GPU-batched execution path (§37).

Practical ceiling and levers beyond it: the default fleet's 4,096-concurrent-sandbox ceiling is FD-bound (§4); raising it requires either more worker nodes (horizontal, bound by scheduler dispatch overhead) or GPU-accelerated batched sandbox execution — PhaseDeferred("§31") — which would trade the current one-fuel-metered-instance-per-candidate model for batched SIMD/GPU evaluation of structurally similar genomes, a fundamentally different execution model deferred out of this blueprint's scope.

32. Mental Models & First Principles

MM1. Evolution optimizes the measured proxy, never the intent — every fitness function is a specification bug waiting to be exploited. Predicts: a candidate will eventually find the cheapest path to a high score that isn't the intended behavior. Bug class without it: shipping a .gns spec with a narrow case set and being surprised by a gaming candidate (§14.6). Resolved by: §14 (penalty design), §28 (held-out case discipline).

MM2. A sandbox is only as trustworthy as its smallest unaudited surface — the arbiter must be smaller and safer than what it arbitrates (Provos 2003). Predicts: the escape that eventually happens comes from an overlooked import or syscall, not the audited main path. Bug class without it: adding a convenience host-function "just for debugging" that becomes T7/T8. Resolved by: §13 (sandbox contract), §24 (threat model).

MM3. Reproducibility is a property of the write path, not an afterthought bolted onto the read path — determinism must be designed into every RNG derivation and reduction order from day one. Predicts: retrofitting determinism onto an already-parallel reduction is far more expensive than building it in. Bug class without it: chasing an unreproducible replay divergence months into a run (§18.6 FM-9). Resolved by: §6 (P1), §18 (lineage/replay).

MM4. Type preservation is a search-space design decision, not a safety check bolted onto operators — it determines which mutations are even reachable. Predicts: an operator that "falls back to no-op too often" signals a type-lattice gap, not a bug in the fallback logic itself. Bug class without it: chasing phantom operator bugs when the real issue is insufficient terminal-type coverage (§15.6, §17.6). Resolved by: §8 (domain model), §15/§17.

MM5. An archive beats a single "best-ever" record because premature convergence is a property of the whole population's diversity, not any one genome's score. Predicts: fitness-only elitism will eventually plateau on deceptive landscapes long before a quality-diversity archive does. Bug class without it: diagnosing a stalled search purely from a flat best-fitness line, missing a healthy-archive/dead-fitness split. Resolved by: §20 (archive), §25 (FM-8).

MM6. Bloat is not a bug, it is the null hypothesis — genetic programming grows code size by default absent an active counter-pressure (Langdon & Poli 2002). Predicts: any run without parsimony pressure from generation 0 will bloat, regardless of problem domain. Bug class without it: adding parsimony only after observing bloat, having already paid the compile-time cost of oversized genomes. Resolved by: §21 (P8).

MM7. Backpressure converts overload into latency; unbounded queues convert overload into a crash later and worse. Predicts: a slow fitness oracle should show up as a slower generation cadence, never as scheduler OOM. Bug class without it: an unbounded channel that "worked fine" until one worker got slow enough to expose it (§19.6, P6). Resolved by: §19 (scheduler), §6 (P6).

MM8. A distributed system's correctness under retries is a property of idempotency keys, not of how rarely retries happen. Predicts: the retry path is exercised far less in testing than in production, so its correctness must be proven structurally (I14), not empirically. Bug class without it: double-counted fitness under a rare worker-restart race that testing never triggered. Resolved by: §19 (P14), §25 (FM-12).

MM9. Telemetry designed after the fact answers yesterday's incident, not tomorrow's — every invariant needs a paired signal before the code that could violate it ships (P11). Predicts: an incident without a corresponding counter/gauge will require a re-run to diagnose, burning hours a dashboard would have saved. Bug class without it: discovering mid-incident that the exact signal needed doesn't exist. Resolved by: §26 (operational readiness), §7 (debugging methodology).

MM10. A checkpoint is a cache of derivable state, not a second source of truth — lineage (I3) is the ground truth, snapshots are an optimization. Predicts: a cascading checkpoint-corruption incident is recoverable exactly because the lineage DAG independently reconstructs everything, just slower. Bug class without it: treating checkpoint loss as unrecoverable data loss instead of a performance regression in recovery. Resolved by: §22 (P9), §25 (FM-4).

Net synthesis: Genesis is closest in spirit to a fusion of DEAP's operator composability, AutoML-Zero's regularized-evolution replacement, and MAP-Elites' archive model, layered under a reproducibility and sandboxing discipline none of GenProg, DEAP, or FunSearch treat as a first-class architectural concern.

34. Back-of-Envelope Capacity Model

Run wall clock: population × generations × eval-seconds ÷ workers. At population 10,000, generations 500, eval time 1/800 s/eval (M1) fanned over 64 workers: (10,000 × 500 × 0.00125 s) ÷ 64 ≈ 97.7 s of pure eval time — but the heavy-fitness case (M2, 5 eval/s) dominates in practice: (10,000 × 500 × 0.2 s) ÷ 64 ≈ 15,625 s ≈ 4.3 hours, consistent with the 30 s–120 s per-generation cadence (§4/M9) × 500 generations ≈ 4.2–16.7 hours.

Host RAM: sandbox RSS × concurrency. At 64 MiB per WASM sandbox (§4 default ceiling) × 64 concurrent sandboxes/node ≈ 4 GiB/node just for candidate linear memory, plus Wasmtime engine/module-cache overhead (~500 MiB/node estimated) ≈ 4.5 GiB/node for the sandbox pool alone.

Archive disk: genome bytes × archive entries × generations retained. At ~4 KiB/cell (§4) × 10,000 cells ≈ 40 MiB per generation snapshot (§4's own figure); retaining 500 generations of full snapshots naively would be 500 × 40 MiB = 20 GiB, which is why ADR-23's WAL-plus-periodic-compaction model retains only the latest snapshot plus the append-only edge log, not 500 full snapshots.

Lineage store: ≈120 bytes/edge (§4) × 200,000 genomes/generation × 500 generations ≈ 120 × 10^8 bytes ≈ 12 GB, matching §4's own lineage-graph-growth figure exactly — confirming the retention-horizon compaction (§18.6, §37) is necessary well before a multi-week 500-generation run at full population completes.

Sandbox spawn throughput vs evaluations/second required: at population 10,000 and a 60 s target generation cadence, required throughput = 10,000 ÷ 60 ≈ 167 eval/s aggregate; at M1's 800 eval/s per warm-cache worker, that requires ⌈167 ÷ 800⌉ = 1 worker in the trivial-fitness case, but at M2's 5 eval/s (heavy fitness) it requires ⌈167 ÷ 5⌉ = 34 workers to hit the same cadence — the heavy-fitness case, not the trivial case, sizes the fleet.

Scheduler message rate: one dispatch + one result message per evaluation; at 34 workers × 5 eval/s (M2 fleet-sized case) ≈ 170 evals/s ⇒ 340 scheduler messages/s, well within gRPC/Protobuf (ADR-08/ADR-09) throughput headroom, confirming the scheduler is not the bottleneck at this scale (§31's bottleneck ordering).

Checkpoint size and write time: population_size genome hashes (32 bytes BLAKE3 each) + archive (§4's 40 MiB/generation figure) ⇒ 10,000 × 32 bytes ≈ 320 KB for population membership, dominated by the ≈40 MiB archive snapshot; at a conservative 200 MB/s durable-volume write throughput, a 40 MiB checkpoint write completes in ≈0.2 s, well inside the 30 s RTO budget (M11) even accounting for fsync overhead and CRC computation.

Dedup ledger memory footprint: (genome hash 32 bytes + generation 8 bytes + attempt 1 byte + status flag 1 byte) ≈ 42 bytes/entry × in-flight generation width (population 10,000) ≈ 420 KB resident, negligible against the ≈4.5 GiB/node sandbox-pool RAM figure above.

Fleet-wide FD budget check: 4,096 concurrent sandboxes (§4 M10) × ≈16 FDs/sandbox (§4) = 65,536 FDs, exactly the per-worker ulimit (§4) at the default 64-workers-×-64-sandboxes topology — confirming the FD ceiling is reached, not exceeded, at the documented default fleet size, leaving zero headroom without raising the ulimit or reducing per-sandbox FD usage.

WASM module-compile cache size: at an estimated 50 KB compiled-module size per distinct genome shape and a working set of ~2,000 distinct shapes per generation (population 10,000 with substantial structural reuse from crossover/mutation locality), the warm cache footprint is ≈100 MB/node — well within a typical worker node's available RAM alongside the 4.5 GiB sandbox-pool figure.

Novelty-scoring cost at reservoir cap: k=15 nearest-neighbor lookups against a 5,000-entry reservoir-capped novelty archive (§20.6), each a behavior-descriptor distance computation of O(descriptor dimensionality) ≈ 10 dimensions ⇒ 15 × 5,000 × 10 ≈ 750,000 floating-point distance-term operations per candidate; at 10,000 candidates/generation this is ≈7.5 × 10^9 operations/generation, parallelized across the same worker fleet doing sandbox evaluation, budgeted well inside the 30 s–120 s generation cadence (M9) on modern multi-core hardware.

Lineage WAL group-commit batch size: at 200 bytes/edge-record on the wire (§18's ≈120 bytes/edge store figure plus framing overhead) × 10,000 offspring/generation ≈ 2 MB per generation's batched WAL write; at a conservative 200 MB/s durable-volume throughput (same figure used for the checkpoint estimate above) this fsyncs in ≈10 ms, negligible against the 30 s–120 s generation cadence (M9).

36. Alternative Architectures (Roads Not Taken)

(a) LLM-proposal search, à la FunSearch, instead of syntactic mutation.

  seed program(s)
       |
       v
  +-----------+      propose      +------------+
  |    LLM    | ----------------> | candidate  |
  | (frozen)  |                   |  program   |
  +-----------+                   +-----+------+
       ^                                |
       | prompt = best-scoring          v
       | prior candidates        +------------+
       +------------------------ | evaluator  |
                                  | (sandbox)  |
                                  +------------+

Winning regime: open-ended mathematical/algorithmic discovery where the space of "reasonable next edits" is not well captured by tree-shaped syntactic mutation — an LLM's prior over plausible code is a stronger proposal distribution than random typed-subtree search. Real embodying system: FunSearch (Romera-Paredes et al. 2024). Why rejected here: Genesis targets P1's bit-for-bit determinism and P4's content-addressed reproducibility; an LLM proposal distribution is neither deterministic nor practically reproducible run-to-run without pinning a specific model checkpoint indefinitely — tracked as a deferral (PhaseDeferred, §37), not a rejection of the idea's value.

(b) Gradient-based / differentiable program synthesis.

  program template (differentiable relaxation)
              |
              v
   +--------------------+
   | continuous params  | <--- gradient step
   +----------+---------+
              |
              v
   +--------------------+
   |  loss(program(x))  |
   +--------------------+

Winning regime: domains where the target program has a natural differentiable relaxation (e.g. neural-network-shaped search spaces, soft program sketches) and gradient signal is far cheaper per step than a full sandboxed evaluation. Real embodying system: differentiable program synthesis lines of work stemming from neural module networks and program-relaxation research. Why rejected here: Genesis's typed AST IR (§8) and .gns fitness DSL (§14) are discrete by construction — control flow (If), variable binding (Let), and typed primitive calls do not have a natural differentiable relaxation without abandoning the closure-typed representation P5 depends on.

(c) SMT-guided enumerative synthesis.

  spec (from .gns, expressed as constraints)
              |
              v
   +--------------------+      UNSAT / model
   |   SMT solver        | <--------------------+
   +----------+----------+                      |
              | candidate program                |
              v                                  |
   +--------------------+   counterexample  -----+
   |  verify vs spec     | ------------------------
   +--------------------+

Winning regime: small, tightly bounded program spaces with a precise logical specification, where exhaustive-but-guided search (CEGIS-style counterexample loops) can prove optimality or unsatisfiability, not just find a good-enough candidate. Real embodying system: Sketch, Rosette, and CEGIS-family enumerative synthesizers. Why rejected here: the .gns DSL's case-based fitness (§8) is deliberately example-driven and tolerant of approximate/partial matches (weighted objectives, tolerance), not a decidable logical spec — encoding Genesis's fitness landscape into an SMT-checkable constraint set would discard exactly the soft, weighted-objective expressiveness §14 is designed to provide, and would not scale to the 200,000-genome/generation population Genesis targets (§4).

(d) A MAP-Elites quality-diversity archive replacing scalar fitness ranking entirely.

  population --------> behavior descriptor --------> archive grid
                                                       (no scalar
                                                        ranking at
                                                        all — only
                                                        per-cell
                                                        elitism)

Winning regime: research questions where behavioral diversity is the primary object of study and scalar fitness is actively misleading (deceptive landscapes), making a pure quality-diversity search preferable to any hybrid. Real embodying system: pure MAP-Elites deployments and QDpy-based research pipelines with no scalar-ranking fallback. Why rejected here as the sole mechanism (though adopted as a coexisting mechanism in §20): Genesis's target workloads (automated repair, architecture search) have a genuine external objective (patch correctness, model accuracy) that operators need ranked, not just illuminated — P7 (§6) explicitly keeps scalar-fitness ranking alongside the archive rather than replacing it, because a pure quality-diversity mode would leave operators unable to answer "which genome should I ship" without an additional ad hoc ranking step layered back on top.

38. Glossary

  • Genome — a typed AST (§8) representing one candidate program; content-addressed by BLAKE3 hash (P4).
  • IR node — one Node enum variant (§11: IntLit, Call, If, Let, etc.).
  • Arity — the fixed number of child expressions a node type accepts (§8 typed AST node table).
  • Mutation operator — a MutationOperator (§11) trait impl producing one offspring from one parent (§15).
  • Crossover — subtree exchange between two parents producing one or two offspring (§17, Koza 1992).
  • Type preservation — the guarantee (P5, I7) that every operator output is well-typed or a documented fallback, never ill-typed.
  • Locality — how far from the mutation/crossover point a genome's behavior is expected to change (§8 operator catalogue).
  • Fitness DSL — the .gns declarative specification language compiled to an EvaluationPlan (§14).
  • Fitness landscape — the mapping from genome to fitness across the search space, referenced when discussing deceptiveness/premature convergence.
  • Selection pressure — the degree to which higher-fitness genomes are favored for reproduction (§16, Goldberg 1989).
  • Tournament selection — sampling k genomes and picking the best as a parent (§16).
  • Elitism — never letting the best-known solution be lost across generations (contrasted with archive-based approaches, P7).
  • Bloat — genome size growth unconnected to fitness gain (Langdon & Poli 2002, §21).
  • Parsimony pressure — a size-adjusted fitness term counteracting bloat (P8, §21).
  • Novelty search — selection driven by behavioral distinctiveness rather than objective fitness (Lehman & Stanley 2011, §20).
  • Behavioral descriptor — the low-dimensional feature vector extracted from a candidate's execution, used to place it in the MAP-Elites grid (§20).
  • MAP-Elites cell — one grid coordinate in the behavior-space archive, holding its best-known occupant (§11, §20).
  • Island model — a population-sharding scheme running independent sub-populations with periodic migrant exchange (§31, not built in Phases 0–11).
  • Lineage — the hash-DAG of parent→child mutation/crossover edges (I11, §18).
  • Seed determinism — the guarantee that a fixed seed plus config reproduces a bit-identical run (P1, I1).
  • Sandbox — the WASM/OCI execution boundary every candidate runs inside (P2, §13).
  • Fuel metering — Wasmtime's deterministic, preemptible CPU-accounting mechanism (ADR-02, §13).
  • Exit taxonomy — the closed set of sandbox outcomes (Ok, Trap, FuelExhausted, etc., §11).
  • Penalty mapping — the total-fitness function assigning a finite score to every crash/timeout/error (P3, I4, §14).
  • Purity check — the static-analysis pass rejecting a .gns spec that could reference host-observable state (I13, §14).
  • Content addressing — identifying a genome or spec by the hash of its structure, not an arbitrary ID (P4).
  • Idempotency key — the (genome hash, generation, attempt) triple preventing duplicate job application (I14, §19).
  • Backpressure — throttling dispatch under load instead of growing an unbounded queue (P6, §19).
  • Credit — a worker's advertised concurrent-evaluation capacity in the scheduler's flow-control scheme (§19).
  • Dedup ledger — the scheduler's idempotency-key tracking store (§19).
  • Checkpoint — a durable, crash-consistent snapshot of run state enabling resume (I10, §22).
  • Autotuning — bounded, checkpoint-boundary-gated adjustment of operator/selection/parsimony parameters (§22).
  • Replay — deterministic reconstruction of a run from seed plus lineage (§18).
  • Conformance suite — the golden-fixture, sim-harness, and property-test aggregate verifying every phase's fixtures (§23).
  • Golden fixture — a named, version-controlled input/expected-output pair used for regression testing (§23).
  • Property test — a test asserting an invariant holds across randomly generated inputs, not one example (ADR-14, §28).
  • Differential test — a test comparing Genesis's behavior against a canonical external definition (e.g. Koza 1992's crossover semantics, §17).
  • Fuzzing — automated adversarial input generation targeting parser/grammar robustness (ADR-15, §28).
  • Regularized evolution — age-based, oldest-out steady-state replacement (Real et al. 2019, §16).
  • Steady-state replacement — a replacement policy that replaces individuals continuously rather than whole-generation-at-once (§8, §11 ReplacementPolicy).
  • Generational replacement — a replacement policy that replaces the entire population each generation (§8, §11).
  • Archive coverage — the fraction of MAP-Elites grid cells currently occupied (§20).
  • Coverage plateau — a stall in archive coverage growth despite continued generations, a premature-convergence-adjacent signal (§20.9).
  • Stale-worker poisoning — a delayed evaluation result being incorrectly applied after its job was reassigned (§19.6).
  • Sandbox escape — a candidate genome executing code outside its intended sandbox boundary (T1, I2).
  • Held-out case — a .gns test case withheld from a candidate's visible scoring to detect fitness gaming (§14.6).
  • Fitness gaming — a candidate exploiting a narrow fitness specification rather than solving the intended problem (MM1, §14.6).
  • Type-checker gate — the ingest-time check rejecting any ill-typed genome before it can enter a job (I5, §12).
  • Depth-search budget — the bounded retry count for finding a type-compatible mutation/crossover target (§15, §17).
  • Size-fair mutation — a bloat-control operator that replaces a subtree with a size-matched substitute (Langdon & Poli 2002, §15).
  • WAL — write-ahead log; the lineage edge log's durability mechanism ahead of periodic compaction (ADR-23, §18).
  • Behavioral diversity — the spread of a population across the behavior-descriptor space, the object of study for novelty search and MAP-Elites alike (§20).
  • Closure property — the strongly-typed-GP requirement (Banzhaf et al. 1998) that every operator output remain within the well-typed language of the IR (§8, P5).
  • Regularized evolution age-window — the sliding cohort of oldest surviving individuals eligible for steady-state replacement (§16, Real et al. 2019).
  • Reservoir sampling — the bounded-size, age/novelty-weighted eviction scheme keeping the novelty-comparison archive from growing unbounded across a multi-week run (§20.6).
