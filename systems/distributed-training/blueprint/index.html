115 — Distributed Training

Project Number: 115

Project Name: Distributed Training

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a distributed training framework, in the DeepSpeed / Megatron-LM / PyTorch-FSDP lineage, that composes four orthogonal forms of parallelism — data parallel (DP) gradient all-reduce, tensor parallel (TP) intra-layer matmul sharding, pipeline parallel (PP) inter-layer micro-batch scheduling, and ZeRO optimizer/gradient/parameter sharding — over PyTorch and NCCL, such that any composition is a configuration change (a ParallelStrategy tuple) rather than a rewrite, and every composition is verified bit-exact against a single-GPU baseline under deterministic mode.

Phase-0 deliverable (numbered modules/packages, §10 Repository Layout is normative for names):

  1. dt.core — ProcessGroup, Topology, Mesh, ShardSpec/PartitionedTensor types (§11).
  2. dt.comm — the NCCL/Gloo collective wrapper plus an in-tree single-process shim for tests.
  3. dt.dp — the data-parallel gradient-all-reduce engine.
  4. dt.trainer — the public Trainer/ParallelStrategy API, delegating the per-rank inner loop to the sibling single-host training-loop project (rank 114).
  5. dt.cli — dt launch / dt verify, the two-GPU smoke-test launcher and bit-exact checker.
  6. correctness/ — the bit-exact correctness harness and its Phase-0 fixture corpus.

System boundaries. Provides: collective-communication wrapping with backpressure/retry/ trace; DP/TP/PP/ZeRO engines and their composition; a topology-aware planner; elastic rendezvous and sharded checkpointing; a profiler (timeline, memory, bandwidth, hang detection). Delegates: the per-rank forward/backward/optimizer-step/LR-schedule/gradient- clip/mixed-precision-cast loop to rank 114's single-host trainer (ADR-12, §9); the physical NCCL ring/tree algorithm selection to NCCL itself (ADR-14, §9); cluster scheduling (Slurm/ Kubernetes) to the operator's scheduler. Does NOT provide: a model zoo, a data pipeline/ ETL system, an experiment-tracking UI, an automatic cost-model parallelism planner (deferred, §39), on-wire encryption of collective traffic (deferred, §39; trusted-fabric assumption, ADR-11).

Non-goals. Single-GPU training (rank 114's job); inference serving; a from-scratch autograd engine (rank 99's job); a from-scratch tensor library (rank 95's job); CPU-only training at scale (Gloo fallback exists for correctness testing only, not for production throughput).

Deployment model. A dt-launched Python process per GPU, coordinated by torch. distributed's process-group abstraction; single-host via torch.multiprocessing.spawn (ADR-13, §9), multi-host via Slurm srun or Kubernetes+torchx (§25, Phase 13). No daemon, no parameter server, no long-lived control-plane process — the framework's lifetime is the training job's lifetime.

Target users/operators. ML systems engineers building or debugging a pre-training, fine-tuning, or RLHF loop at 2–1024 GPU scale (the sibling projects at ranks 120, 125, 130 depend on this substrate); cluster operators who run and page on the correctness/chaos/ performance CI gates (§30, §31).

What later phases unlock. Phase 0 (§12) unlocks nothing beyond itself except the bit-exact gate every later phase must pass. Phase 1 (§13) unlocks fabric-saturating DP. Phases 2–3 (§14–§15) unlock models too wide for one GPU. Phases 4–6 (§16–§18) unlock models too large in optimizer/gradient/parameter footprint for one GPU. Phase 7 (§19) unlocks models too deep for one GPU group. Phase 8 (§20) unlocks composing all of the above. Phases 9–13 (§21–§25) unlock activation-memory reduction, production-grade collective hardening, elastic fault tolerance, measured performance parity with reference stacks, and multi-node scale.

Recommended language: Python 3.11, rationale. PyTorch is the reference dependency for every target model in the portfolio; its autograd integration (hooks, torch.autograd. Function, CUDA-stream semantics) is the entire mechanism this framework hangs off of — adopting a different tensor runtime means re-deriving that integration from nothing. Optional CUDA C++ kernels sit behind a pybind11 boundary (ADR-19, §9) for the small hot-path fused ops; control plane stays pure Python.

Rejected languages. Rust (+ a Rust tensor runtime such as Burn) — rejected because no target model in this portfolio has a Rust-native definition, and re-implementing PyTorch's autograd/CUDA-stream semantics from scratch is a multi-year undertaking orthogonal to this project's goal (ADR-01, §9). JAX + XLA — rejected on ecosystem reach: JAX's pjit/GSPMD compiler-driven sharding is architecturally cleaner for this problem (see §38, Alternative Architectures) but the portfolio's models are PyTorch-defined, and adopting JAX means losing the existing model zoo and the rank-114 single-host trainer's direct reuse (ADR-01, ADR-12). C++ alone — rejected because Python's role here is orchestration and autograd-hook registration, not the hot loop; a pure-C++ control plane would need to re-implement Python's nn.Module introspection that shardformer (§11) depends on.

Prerequisites. The single-host Training Loop project (rank 114, forward/backward/step abstractions); Autograd-from-Scratch (rank 99, what a gradient is along a parallelism cut); the Tensor Library project (rank 95, stride semantics under sharding); an MPI/NCCL primer (rank 105, collective semantics). Comfort with PyTorch hooks, torch.distributed, CUDA streams, and NCCL group lifetime is assumed before Phase 0.

Estimated timeline. Phase 0: 1–2 weeks. Full plan (Phases 0–13): 9–12 months at one phase per 1–2 weeks steady-state, per Appendix B (§42).

Deferred features (full Register at §39): CPU/NVMe offload (ZeRO-Infinity) PhaseDeferred("§9"); an Alpa-style automatic parallelism planner PhaseDeferred("§9"); asynchronous PipeDream-style weight-stashing pipelines PhaseDeferred("§38"); on-wire mTLS for collectives PhaseDeferred("§9"); GSPMD/compiler-driven sharding propagation PhaseDeferred("§38").

2. Why Build This

A distributed training framework is the substrate every large-model project in this portfolio quietly depends on — the pre-training run (rank 120), the RLHF loop (rank 125), the fine-tuning service (rank 130). An opaque substrate (a vendored fork, a closed-source wrapper) turns every later debugging session into "the loss diverged after rank 4 dropped, file a ticket"; a substrate you have built turns it into a collective trace, a per-rank gradient histogram, and a fix.

  • Unique systems knowledge. Distributed training is the rare systems problem where correctness is numerical, not behavioral: a wrong summation order does not crash, it produces a loss curve that gently diverges by 0.5% after 10K steps. Building the correctness harness alongside the runtime is the only way to develop the instinct that catches this before it ships.
  • Why it matters architecturally. Rajbhandari et al.'s ZeRO progression (shard optimizer state → gradients → parameters) and Shoeybi et al.'s Megatron column/row-parallel split are the two ideas the entire field's production stacks (DeepSpeed, Megatron-LM, FSDP) are built from; implementing both from the papers, not from a wrapper, is what makes the tradeoffs legible.
  • Engineering muscles built. Reasoning about bandwidth-vs-latency in collective placement; debugging silent numerical drift across ranks; designing a schedule (1F1B) that is a correctness object, not just a performance one; building fault tolerance for a job that will lose a rank at 1000-GPU scale.
  • Cross-links to sibling systems. The MPI/NCCL Primer (rank 105) supplies the collective vocabulary this project builds on; the Tensor Library (rank 95) supplies the stride semantics ShardSpec (§11) depends on; the pre-training/RLHF/fine-tuning projects (ranks 120/125/130) are this framework's downstream consumers via the ParallelStrategy API (§11).
  • Calibration value. By Phase 8 (§20) you hold the same toolbox NVIDIA, Meta, and Microsoft's engineers held when they shipped Megatron-LM, FSDP, and DeepSpeed respectively — with the source open on your screen, so you know exactly which line runs when rank 7 stalls.

What Mastery Looks Like (after completing the full blueprint, a reader can):

  • Derive, not just state, why ZeRO's reduce-scatter+all-gather is wire-equivalent to an all-reduce and where the memory saving actually comes from — cemented in Phases 4–6 (§16–§18).
  • Pair Megatron's f/g autograd-boundary operators correctly for column- and row-parallel linears and explain what breaks if they are swapped — cemented in Phase 2 (§14).
  • Design and defend a 1F1B pipeline schedule against GPipe on bubble fraction, and know the regime where GPipe still wins — cemented in Phase 7 (§19).
  • Build a bit-exact correctness gate as a first-class design constraint, not a bolted-on test suite — cemented in Phase 0 (§12).
  • Compose DP, TP, PP, and ZeRO into a working 3D-parallel mesh and reason about placement against real NVLink/IB topology — cemented in Phase 8 (§20).
  • Diagnose and recover from a NCCL hang, a killed rank, or an IB partition using the framework's own instrumentation — cemented in Phases 10–11 (§22–§23).
  • Read Megatron-LM, DeepSpeed, and FSDP source and correctly attribute which design choice came from which paper — cemented across §5 Required Reading and §35 Comparative Architecture Table.

User training script / dt.Trainer. The single entry point; the user supplies a normal nn.Module, an optimizer, a data loader, and a ParallelStrategy (§11); nothing else changes (P10, §6).

Parallel planner. Turns a (dp_size, tp_size, pp_size, zero_stage) tuple into a concrete Mesh (§11); validates dp_size * tp_size * pp_size == world_size.

Model rewriter (shardformer). Walks the module tree once and substitutes nn.Linear / nn.Embedding for their TP-sharded equivalents and PP split points; the user's forward is unchanged (§11, §14).

Topology mapper. Consults a Topology (§11) — host, NUMA node, GPU index, link bandwidth/kind per rank pair — to place TP groups on NVLink and DP/PP groups across IB (P2, §6).

Parallel mesh. The immutable (dp_rank, tp_rank, pp_rank) -> world_rank map every engine below consults (§11 Mesh).

DP / TP / PP / ZeRO engines. Four composable ParallelEngine implementations (§11) wired together per §20 (Phase 8); each owns exactly its subsystem's collective pattern.

Activation checkpoint. An orthogonal, engine-agnostic wrapper (§21, Phase 9) that trades compute for activation memory at block or sub-block granularity.

Collective comm layer. The single cross-rank primitive (P13, §6): every all_reduce, all_gather, reduce_scatter, send/recv, broadcast goes through the typed CollectiveOp wrapper (§11, §22) — never an out-of-band RPC.

Intra-/inter-node fabric. NCCL rides NVLink within a node and IB/TCP between nodes; the framework never overrides NCCL's ring/tree algorithm selection except the timeout (ADR-14, §9).

The one defining property: correctness here is numerical equivalence to a single-GPU baseline (I1, §7), not merely absence-of-crash — every constraint above exists to keep that equivalence checkable at scale.

6. Design Principles

  1. Numerics-Preserving Collectives. Every collective, given a fixed seed and a fixed (dp,tp,pp,zero_stage) configuration, must produce a bit-identical loss curve to a reference. Tradeoff: forbids assuming floating-point associativity; reductions use a documented, fixed order. Operational implication: CI runs a deterministic mode at ~20% throughput cost (§4). Violated: silent numerical drift ships to production (FM-2, §27).
  2. Topology-Aware Placement. The (dp,tp,pp) mesh is mapped to physical devices respecting NUMA, NVLink, and IB. Tradeoff: the planner must consult a Topology object before issuing groups, adding planning complexity. Operational implication: the planner emits a topology report operators audit (I5, §7). Violated: TP across hosts is a 5–10x slowdown (M3, §32).
  3. Micro-Batch Is the Unit of Forward/Backward. The trainer's inner loop iterates micro-batches; the optimizer steps once per accumulated batch. Tradeoff: every parallelism form (grad accumulation, PP, checkpointing) must be expressible as a micro-batch policy. Violated: PP and grad-accumulation cannot compose (I3, §7).
  4. ZeRO-3 Prefetch Is Correctness-First. A ZeRO-3 forward all-gathers a module's parameters before use and re-shards after; the correctness bar is "same activations as non-prefetched," the performance bar is "hides ≥ 80% of all-gather latency" (M7, §32). Violated: a wrong prefetch either leaks memory or stalls the pipeline.
  5. Every Op Is Classified Comm or Compute. A run trace records, per op, whether it issued a collective. Operational implication: the profiler (§24) can separate the two on parallel timelines. Violated: misclassification is itself a profiler or planner bug.
  6. Gradient-Accumulation Correctness. Accumulating N micro-batches then stepping must equal a single batch of size N * micro_batch_size (mod loss-reduction convention). Tradeoff: the collective must fire post-accumulation via a post-backward hook, not per-micro-batch (I3, §7; ADR-09, §9). Violated: effective batch size silently changes.
  7. Failure Is First-Class. NCCL timeout, rank crash, IB flap, node loss — each has a typed exception, a retry policy, a documented recovery path (§26, §27). Violated: the cluster is falsely assumed reliable and the elastic surface (§23) never engages.
  8. Deterministic Seed Propagation. Every rank seeds from root_seed plus its (dp,tp,pp) coordinates (I6, §7). Operational implication: the same root seed + strategy reproduces the same loss curve on any cluster. Violated: Phase-0's bit-exact gate cannot pass.
  9. No Silent Device Migration. A tensor's device is part of its identity; the framework never moves a tensor between devices without an explicit collective or .to() (I13, §7). Violated: cross-device corruption fails loudly instead of silently, by design.
  10. The User's nn.Module Is Preserved. TP substitutes nn.Linear via shardformer; PP chunks the module list; ZeRO hooks each parameter — the user's forward is unchanged. Tradeoff: shardformer's heuristics must handle the common case and allow model-specific overrides. Violated: every model needs a bespoke rewrite (defeats P10 itself).
  11. Operations Are the Product. A profiler, a memory-usage breakdown, a collective tracer, a hang detector are first-class deliverables (§28), not afterthoughts. Violated: operators cannot diagnose a stalled 1,024-GPU job (FM-1, §27).
  12. Rank-114's Inner Loop Is Reused Unchanged. Forward, backward, optimizer step, LR schedule, gradient clipping, mixed precision, logging are delegated to rank 114 (ADR-12, §9); this framework wraps, never reimplements. Violated: two divergent single-host training loops must be kept in numerical lock-step forever.
  13. The Collective Is the Only Cross-Rank Primitive. Every cross-rank state change is a named collective against a typed ProcessGroup — no RPC, no Redis, no shared filesystem side-channel. Violated: a side-channel bypasses backpressure/retry/trace and is invisible to the profiler and the Threat Model (§26).
  14. Communication-Volume Equivalence Across ZeRO Stages. Reduce-scatter + all-gather costs the same wire volume as an all-reduce; ZeRO's memory savings come from shard residency, not reduced traffic (MM5, §34). Violated: an engineer expects ZeRO-3 to also cut network load and mis-diagnoses a bandwidth-bound run.

8. Domain Model

Data Parallel & AllReduce

State per rank: a full model replica, a full optimizer replica, a locally-computed gradient. Step sequence: forward -> backward -> [accumulate] -> all_reduce(sum) -> divide(dp_size) -> optimizer.step -> zero_grad. The all-reduce is bucketed (§13): parameters are binned into fixed-size buffers in registration order; a bucket all-reduces once full.

Field Type Semantics
bucket.capacity_bytes int fixed buffer size, default 25 MiB (ADR default)
bucket.params ordered list registration-order parameters binned into this bucket
bucket.ready int count of parameters whose gradient has been deposited
bucket.cursor int write offset into the flat buffer

Worked example. Two ranks, one parameter of 100 elements. Rank 0 computes local gradient g0, rank 1 computes g1. Bucketed all-reduce with a fixed-tree reduction computes g0+g1 identically on both ranks (order: rank 0 then rank 1, always), divides by dp_size=2, and both ranks now hold (g0+g1)/2 bit-identically — matching a single-GPU run over the concatenated batch of both ranks' samples (I1, §7).

Malformed input. A bucket add() call for a parameter whose numel() exceeds the remaining bucket capacity must return a rejection (not silently overflow the buffer); the engine then opens a new bucket. A parameter added twice to the same bucket (a registration bug) violates I4-adjacent shard completeness and must raise, not silently double-count.

Failure path. A NCCL all-reduce that exceeds timeout_ms raises CollectiveTimeout (I11, §7); the DP engine does not retry silently — the exception propagates to the elastic layer (§23) which decides reform vs. abort.

Tensor & Pipeline Parallel

TP state: a ShardSpec per sharded parameter (ShardKind ∈ REPLICATE | SHARD_DIM_0 | SHARD_DIM_1 | SHARD_FLAT), plus the f/g autograd-boundary operator pair (identity-forward/ all-reduce-backward and all-reduce-forward/identity-backward respectively) that make a column-parallel-then-row-parallel pair numerically equal to the unsharded computation (Shoeybi et al. 2019, sec. 3.2; ADR-06, §9).

PP state: a PipelineStage (module slice, is_first/is_last, input_shape/output_shape, prev_rank/next_rank) plus a ScheduleStep sequence (FORWARD | BACKWARD | SEND_ACTIVATION | RECV_ACTIVATION | SEND_GRADIENT | RECV_GRADIENT | OPTIMIZER_STEP) built by build_1f1b_schedule (§19).

Step kind Cross-rank? Fires when
FORWARD no this stage's input activation is available
BACKWARD no this stage's output gradient is available
SEND_ACTIVATION yes (P2P) after FORWARD completes and a next stage exists
RECV_ACTIVATION yes (P2P) before FORWARD when a previous stage exists
SEND_GRADIENT yes (P2P) after BACKWARD completes and a previous stage exists
RECV_GRADIENT yes (P2P) before BACKWARD when a next stage exists
OPTIMIZER_STEP no once per accumulated batch, all micro-batches drained

Worked example. pp_size=4, num_micro_batches=8. Stage 0's schedule: 4 forwards (warm-up, filling the pipeline) then steady-state 1F1B (one forward, one backward per cycle) then 4 backwards (cool-down). Bubble fraction = (P-1)/(M+P-1) = 3/11 ≈ 27% (Huang et al. 2019; Harlap et al. 2018).

Malformed input. A schedule where stage 2's SEND_ACTIVATION(mb=3) has no matching RECV_ACTIVATION(mb=3) on stage 3 violates I9 (§7) and must be rejected by the static validator at schedule-build time, not discovered at runtime as a deadlock.

Failure path. A RECV_ACTIVATION that never arrives (peer crashed) blocks indefinitely; the hang detector (§22) surfaces this within the soft-timeout floor (§4) as a stuck-rank report naming the stage and micro-batch id.

ZeRO Sharding Progression

Stage Shards Communication pattern Memory factor (per rank, N=dp_size)
ZeRO-1 optimizer state only all-reduce grad, local step, all-gather updated params optimizer state /N; params & grads full
ZeRO-2 + gradients reduce-scatter grad, local step, all-gather updated params optimizer state & grad /N; params full
ZeRO-3 + parameters per-module all-gather-before-use, reduce-scatter grad, release after use optimizer, grad, params all /N

The reduce-scatter + all-gather pair is wire-equivalent to an all-reduce (MM5, §34); ZeRO's memory win is shard residency between collectives, not reduced traffic (P14, §6).

Worked example. ZeRO-3, dp_size=8, a module with 800 elements → each rank's persistent shard is 100 elements. On forward_pre_hook, all-gather reconstructs the full 800-element tensor on every rank (I4, §7); the module computes; on forward_hook, the full tensor is released and only the 100-element shard survives.

Malformed input. An all-gather refcount release() called without a matching prior all_gather() (I8, §7) — e.g. from a mis-tracked shared-parameter tie (tied embeddings) — must raise rather than let the refcount go negative and corrupt the freed buffer.

Failure path. A reduce-scatter whose output shard size does not evenly divide the parameter-shard boundary (I7, §7) — e.g. a bucket sized without alignment to dp_size — is rejected at bucket-construction time with a named BucketAlignmentError, not at collective issue time.

Collective Operations (Ring / Tree)

Ring all-reduce: each rank forwards a chunk to its ring-neighbor over N-1 steps (reduce- scatter phase) then N-1 steps (all-gather phase); total data moved per rank ≈ 2*(N-1)/N * size — bandwidth-optimal (Patarasuk & Yuan 2009). Tree all-reduce: O(log N) steps, lower latency at small message sizes or large N, at the cost of some links carrying more volume than the ring's uniform distribution. NCCL selects per-topology by default; the framework only overrides the timeout (ADR-14, §9).

Comm/Compute Overlap

A bucket's all-reduce is issued on a dedicated CUDA stream (priority=-1) that the current compute stream does not block on; the next bucket's autograd computation proceeds concurrently with the previous bucket's collective, because autograd walks the graph in reverse (later-defined layers' gradients are ready first). The optimizer step must stream.synchronize() (or, in production, record_stream) before reading the reduced gradient (§13.6 Pitfalls).

    REDUCE_SCATTER = "reduce_scatter"; BROADCAST = "broadcast"
    SEND = "send"; RECV = "recv"; BARRIER = "barrier"

@dataclass
class CollectiveOp:
    kind: CollectiveKind
    group: ProcessGroup
    tensors: list[torch.Tensor]
    op_id: int                        # monotonic per group
    timeout_ms: int = 30_000
    bucket_id: int | None = None

async def issue(op: CollectiveOp) -> None: ...   # backpressure + retry + trace, §22

Conformance (ties to I2/I11 §7): determinism — fixed input + fixed group + fixed order ⇒ bit-identical output; liveness — completes within timeout_ms or raises CollectiveTimeout; atomicity — succeeds on all participants or none.

12. Phase 0 — Repo Skeleton & Bit-Exact Correctness Kernel

12.1 Objectives

Stand up the full repo skeleton (§10); implement dt.core types (§11) as compile-time definitions; land a two-GPU DP smoke test that reproduces a single-GPU baseline bit-exactly (I1, §7). Constraints introduced: deterministic mode only (ADR-10, §9); DP-only scope (ADR-02, §9).

12.2 Detailed Implementation Steps

Land dt/core/{process_group,topology,mesh,shard_spec,pipeline_stage,schedule_step, collective_op,seed,error}.py as signature-only definitions (§11). Implement dt.comm.nccl as a thin wrapper around torch.distributed.all_reduce/all_gather/barrier with a fixed-tree reduction order (P1, §6) and a 30 s timeout (I11, §7). Implement dt.comm.shim, an in-tree single-process collective implementation for tests without multiple processes. Implement dt.dp.engine.DataParallelEngine: one post-backward hook per parameter (no bucketing yet — ADR-02 keeps Phase 0 minimal), one all-reduce per parameter in deterministic registration order, divide by dp_size (P6, §6). Implement dt.trainer.Trainer: init the process group, construct Mesh, wrap the model with DataParallelEngine, delegate the per-micro-batch inner loop to rank 114's train_step (ADR-12, §9). Implement dt.cli.launch (torch.multiprocessing.spawn, ADR-13 §9) and dt.cli.verify (byte-identity check between two safetensors dumps, ADR-15 §9).

12.3 Deliverable

make bootstrap && make build && make test && make verify-bit-exact all succeed; a two-GPU DP run on a 2-layer MLP over a 1,000-sample synthetic dataset for 100 steps produces a parameter dict byte-identical to the single-GPU baseline.

12.4 Acceptance Criteria

make test passes 3 tests (test_smoke_single_gpu, test_smoke_dp2, test_bit_exact_dp2); the two loss logs match to the last bit at all 100 steps (I1, §7); ADRs 01, 02, 03, 09, 10, 11, 12, 13, 15, 16, 22 (§9) are written; process-group init completes in ≤ 60 s (§4).

12.5 Conformance Fixtures

correctness/corpora/dp/baseline.safetensors (single-GPU reference param dict); correctness/corpora/dp/baseline.loss.json (per-step loss log); correctness/corpora/dp/dp2_bitexact.safetensors (two-GPU candidate); malformed fixture correctness/corpora/dp/malformed_strategy.json (dp_size*tp_size*pp_size != world_size, expect a rejected ParallelStrategy).

12.6 Pitfalls

NCCL is not bit-deterministic by default — ring construction depends on topology detected at init; NCCL_ALGO=Tree plus a fixed topology file is required (ADR-10, §9). torch. use_deterministic_algorithms(True) is necessary but not sufficient — some kernels (certain cross_entropy shapes) fall back to non-deterministic paths and must error loudly. bf16 has consistent numerics across GPU generations, fp16 does not — Phase 0 ships bf16 only (ADR-16, §9). The data sampler must be deterministic and DP-aware (DistributedSampler with a fixed seed, not RandomSampler, which gives both ranks the same samples). Do not ship gradient bucketing in Phase 0 — bucketing without determinism breaks bit-exactness (deferred to §13).

12.7 Performance Concerns

Deterministic mode costs ~20% throughput (§4); acceptable for CI, not production (ADR-10). One all-reduce per parameter is launch-overhead-bound (~10 µs/collective, §4) — intentionally unoptimized until §13.

12.8 Edge Cases

A ParallelStrategy where dp_size*tp_size*pp_size != world_size must be rejected at construction, not at first collective. A model with zero trainable parameters must not deadlock Trainer.fit. A single-GPU run (dp_size=1) must skip all collectives entirely, never issue degenerate one-rank all-reduces.

12.9 Failure Analysis

A NCCL init failure (mismatched CUDA/driver versions across ranks) fails process-group construction with a named ProcessGroupInitError, not a generic timeout; blast radius is the whole job (no partial start); containment is a pre-flight dt.cli.detect-fabric version check (§25); recovery is fixing the environment and relaunching. A bit-exact mismatch halts the build and requires per-rank gradient-histogram bisection (I1, §7).

12.10 Operational Notes

make verify-bit-exact is the CI gate every later phase's correctness bucket extends (§30). BUILD_PLAN.md tracks Phase-0 Status: complete; every not-yet-built Phase-1+ surface is flagged PhaseDeferred("§9") where applicable, resolved in the Deferred Features Register (§39). No rollback/migration concerns yet — this is the first shippable state.

13. Phase 1 — Gradient Bucketing & Comm-Compute Overlap

13.1 Objectives

Replace per-parameter all-reduce with fixed-size gradient bucketing (default 25 MiB) and overlap the collective with ongoing backward compute (P1, P6, §6), while preserving I1 (§7) bit-exactness.

13.2 Detailed Implementation Steps

dt.dp.buckets.GradientBucket — a fixed-capacity contiguous buffer, an ordered parameter list, an offset table, deposit-on-ready tracking. dt.dp.overlap.OverlapEngine — a dedicated CUDA comm stream (priority=-1); the post-backward hook deposits into the owning bucket and issues the bucket's all-reduce once full, using the fixed-tree order from Phase 0 (P1, §6; ADR-10, §9). Bin-packing order is fixed to nn.Module.parameters() registration order so the bucket layout — and therefore the reduction order — stays deterministic (I1, I6, §7). The optimizer step synchronizes the comm stream before reading reduced gradients.

13.3 Deliverable

A DP engine achieving ≥ 80% of NCCL peak bandwidth (M2, §32) on a two-GPU NVLink link, verified in dt.profile.timeline (§24); the Phase-0 bit-exact bucket re-passes with bucketing enabled.

13.4 Acceptance Criteria

The bucketed two-GPU run produces a loss curve byte-identical to the bucketless two-GPU run and to the single-GPU baseline (I1, §7); a benchmark at micro-batch sizes 1/4/16/64 on a 100M-param transformer shows bucketing delivering 1.5–2x at small micro-batch, ≥ 1.1x at large (M2, §32).

13.5 Conformance Fixtures

correctness/corpora/dp/bucketed_bitexact.safetensors; benchmarks/dp_step_time.py results at MB = 1/4/16/64 with/without bucketing; malformed fixture: a bucket capacity_bytes smaller than the largest single parameter, expect a graceful single-parameter bucket, not a crash.

13.6 Pitfalls

The post-backward hook's firing order is deterministic only given a stable forward graph — a model with early-exit/dynamic depth breaks bit-exactness (a known limitation, ties to MM8, §34). The comm stream's gradient buffer must not be read by the optimizer before the collective completes — stream.synchronize() is the Phase-1 fix, record_stream/CUDA events are the Phase-10 production fix (§22). A too-small bucket under-utilizes the fabric; a too-large bucket delays the first collective until late in backward — 25 MiB is the PyTorch DDP-derived default (§5 Reference Implementations).

13.7 Performance Concerns

Launch-overhead amortization is the entire point of bucketing (§4: ~10 µs/collective floor); bucket-fill latency vs. all-reduce-issue latency is the tuning knob revisited in §24 Phase 12.

13.8 Edge Cases

A parameter larger than the bucket capacity gets its own dedicated bucket. A model with a single parameter degenerates to Phase-0 behavior. Grad-accumulation windows (§16 onward) must not issue the bucket all-reduce until the full window completes (I3, §7; ADR-09, §9).

13.9 Failure Analysis

A bucket all-reduce that times out (I11, §7) surfaces CollectiveTimeout naming the bucket id and its parameter list, not a bare NCCL error string — the diagnostic the hang detector (§22) later automates.

13.10 Operational Notes

dt.profile.timeline (§24) is the first-stop view for "bucketing isn't helping" — a glance shows whether rows are compute-bound (green) or comm-bound (red). Bucket size is operator-tunable via ParallelStrategy-adjacent config, not hardcoded.

14. Phase 2 — Tensor Parallelism: Column/Row-Parallel Linears

14.1 Objectives

Shard each weight matrix in a transformer block along one dimension (Megatron column-/ row-parallel split, ADR-06 §9) so a matmul that does not fit one GPU's compute/memory runs across tp_size ranks with correct autograd-boundary collectives.

14.2 Detailed Implementation Steps

dt.tp.column_parallel.ColumnParallelLinear shards the output dimension; forward is a local matmul (no collective); backward's input-gradient is all-reduced across tp_group via the _IdentityFwd_AllReduceBwd autograd-boundary operator (Megatron's "f" operator, Shoeybi et al. 2019, sec. 3.2). dt.tp.row_parallel.RowParallelLinear shards the input dimension; forward's partial sums are all-reduced via _AllReduceFwd_IdentityBwd (the "g" operator); backward is local. dt.tp.shardformer walks the module tree and substitutes nn.Linear/nn.Embedding per a documented wide-dimension heuristic (P10, §6), with per-architecture override registration. dt.tp.cross_entropy implements vocab-parallel cross-entropy: local log-softmax after a global-max all-reduce (ReduceOp.MAX), local loss contribution, sum all-reduce.

14.3 Deliverable

ColumnParallelLinear/RowParallelLinear on two TP ranks produce a forward output bit-identical to a single-rank nn.Linear of the same total dimensions; shardformer converts a Phase-0 MLP into a TP-2 version training to the same final loss as the single-rank baseline.

14.4 Acceptance Criteria

An 8-rank TP test of a transformer block (hidden=512, heads=8) matches single-rank forward output within 1e-5 (fp32) / 1e-2 (bf16) at every layer (M3, §32); TP=2/4/8 throughput on a 1.3B-param transformer scales sub-linearly (all-reduce overhead), documented against M3.

14.5 Conformance Fixtures

correctness/corpora/tp/tp2_forward_match.safetensors; correctness/corpora/tp/tp8_block_tolerance.json; malformed fixture: out_features % tp_size != 0, expect a rejected ColumnParallelLinear construction, not silent truncation.

14.6 Pitfalls

The f/g operator pairing is non-obvious and silently wrong if swapped — _AllReduceFwd_IdentityBwd's backward is correct only if every rank's input was already replicated by a preceding _IdentityFwd_AllReduceBwd boundary (§8 Domain Model). RowParallelLinear's bias must be added after the all-reduce, not before, or it is summed tp_size times — the single most common Megatron-pattern bug. The vocab-parallel cross-entropy's global-max subtraction must use ReduceOp.MAX on every rank; a per-rank max is silently wrong.

14.7 Performance Concerns

Two all-reduces per transformer block (attention output + MLP output) is the Megatron-minimal communication pattern (ADR-06, §9); TP must stay within a single NVLink-connected node (P2, §6; I5, §7) or throughput drops 5–10x.

14.8 Edge Cases

hidden_dim not divisible by tp_size must raise at shardformer time. A model with tied input/output embeddings requires the embedding's TP shard to be shared, not duplicated (interacts with I8, §7, revisited in §18).

14.9 Failure Analysis

A swapped f/g operator pair does not crash — it silently corrupts the backward pass, manifesting as loss divergence caught only by the bit-exact bucket (§30) or the numerical bucket, never by an exception.

14.10 Operational Notes

docs/architecture/tp.md documents the f/g operator diagram; the shardformer's per-architecture override registry is the extension point for models the default heuristic misclassifies.

15. Phase 3 — Sequence Parallelism & Attention Sharding

15.1 Objectives

Shard the non-linear (LayerNorm/Dropout) activation's sequence dimension between TP collectives (Korthikanti 2022; ADR-07 §9) to remove the tp_size-fold activation-memory replication Phase 2 leaves in place.

15.2 Detailed Implementation Steps

Replace the block-boundary all_reduce with reduce_scatter (after a row-parallel op, via _ReduceScatterFwd_AllGatherBwd) and the identity-forward with all_gather (before a column-parallel op, via _AllGatherFwd_ReduceScatterBwd) — same wire volume as Phase 2 (P14, §6; MM5, §34), per Korthikanti et al. 2022 and ADR-07 (§9), lower activation memory. Attention sharding: QKV column-parallel along the head dimension (heads_per_rank = num_heads / tp_size); attention math is rank-local per head; output row-parallel, summed via all-reduce. FlashAttention (Dao 2022) substitutes at construction time inside the attention wrapper — TP collectives are unchanged either way.

15.3 Deliverable

A sequence-parallel transformer block whose activation memory is 1/tp_size of the Phase-2 version (M4, §32), same forward output to bit-exactness in fp32 / 1e-2 in bf16.

15.4 Acceptance Criteria

A 4-rank TP test of an 8-layer transformer matches single-rank loss within numerical tolerance for 100 steps; a benchmark on a 6.7B-param transformer at sequence length 4096 confirms the 1/tp_size memory reduction (M4, §32); swapping in FlashAttention leaves the loss curve unchanged within tolerance.

15.5 Conformance Fixtures

correctness/corpora/tp/seq_parallel_activation_mem.json; correctness/corpora/tp/flash_attn_swap_test.json; malformed fixture: sequence length not divisible by tp_size, expect a rejected configuration (documented constraint, not silent padding).

15.6 Pitfalls

reduce_scatter's scatter dimension must divide evenly by tp_size — most production sequence lengths (1024/2048/4096) satisfy this for common TP sizes (≤ 8). Dropout is the trickiest non-linear layer to shard — a naive per-rank mask breaks the "replicated activation" assumption sequence parallelism relies on; use a seed-recorded DroppedTensor or a rank-0-broadcast mask (Megatron's tensor-parallel-region dropout). all_gather/ reduce_scatter along a non-dim-0 axis needs an explicit transpose-gather-transpose, or throughput drops 10x.

15.7 Performance Concerns

Communication volume is unchanged from Phase 2 (P14, §6) — the win is purely memory; verify via dt.profile.memory (§24) that peak activation memory actually drops 1/tp_size.

15.8 Edge Cases

Irregular sequence lengths (non-divisible by tp_size) must be rejected, not silently padded, to avoid a silent shape/loss mismatch. Tied Q/K/V weights (rare architectures) require the shardformer override registry (§14) to avoid double-sharding.

15.9 Failure Analysis

A mis-ordered transpose in the non-dim-0 gather produces a shape-correct but numerically-wrong activation — caught only by the bit-exact/numerical buckets (§30), never by a shape assertion; document this explicitly in docs/numerics/.

15.10 Operational Notes

docs/architecture/tp.md's sequence-parallel subsection documents the reduce-scatter/ all-gather placement; ADR-07 (§9) records the on-by-default decision and its opt-out.

16. Phase 4 — ZeRO-1: Optimizer-State Sharding

16.1 Objectives

Shard optimizer state across the DP group (Rajbhandari et al. 2020, sec. 4–5) cutting per-rank optimizer memory from 12 bytes/param (Adam fp32 master+m+v) to 12/dp_size.

16.2 Detailed Implementation Steps

dt.zero.z1_optimizer.Zero1Optimizer flattens the parameter list into one contiguous buffer, partitions it into dp_size equal shards, and constructs the wrapped optimizer over only the local shard's view(). Step: gradient is already all-reduced (Phase 1's DP engine, unchanged); the optimizer updates only its shard; an all-gather reconstructs the full parameter buffer for the next forward (P6, §6; I4, §7). Mixed-precision compatibility: the fp32 master shard is stepped, then cast to bf16, then all-gathered (I14, §7; ADR-16, §9).

16.3 Deliverable

Zero1Optimizer uses 1/dp_size of the optimizer-state memory of an equivalent DP-only run (M5, §32), with an identical loss curve to bit-exactness under deterministic mode.

16.4 Acceptance Criteria

Parameter values at every step are identical between a DP-only run and a ZeRO-1 run (I1, §7); a benchmark on a 6.7B-param model with DP=8 shows step time within 5% of DP-only and memory within 1/8 (M5, §32).

16.5 Conformance Fixtures

correctness/corpora/zero/z1_vs_dp_bitexact.safetensors; benchmarks/results/z1_memory_profile.json; malformed fixture: a flat-buffer shard size not aligned to the fused optimizer's 16-byte requirement, expect automatic padding, not a crash.

16.6 Pitfalls

The flat-buffer view() is fragile — user code that reassigns param.data breaks the shared view; the framework asserts this invariant every step. The end-of-step all-gather is a synchronization point that blocks the next forward — Phase 4 accepts this; §17 hides it. Shard size must be padded to the optimizer's alignment requirement (e.g. fused Adam's 16 bytes); padding is excluded from gradient accumulation but included in the all-gather.

16.7 Performance Concerns

The all-gather-per-step cost is the dominant new overhead vs. Phase 1 (quantified in M5, §32); comm-compute overlap for this all-gather is deferred to §17's reduce-scatter redesign.

16.8 Edge Cases

A world size that does not evenly divide the flattened parameter count requires the last shard to be smaller — the framework pads rather than dropping elements (I4, §7 shard completeness). An optimizer with per-parameter-group hyperparameters (e.g. differing weight decay) must preserve group membership across the flatten/partition step.

16.9 Failure Analysis

A param.data reassignment bug silently desynchronizes the flat buffer and the optimizer's view of it — caught by an assertion at every step() boundary, not a passive invariant check, because the corruption is otherwise undetectable until the loss diverges.

16.10 Operational Notes

docs/architecture/zero.md documents the flatten/partition scheme; dt.profile.memory (§24) is the tool operators use to confirm the 1/dp_size reduction actually materialized.

17. Phase 5 — ZeRO-2: Gradient Sharding

17.1 Objectives

Replace ZeRO-1's post-all-reduce full-copy gradient with a reduce-scatter (Rajbhandari et al. 2020), so only the locally-needed gradient shard is ever materialized, halving gradient-memory peak vs. ZeRO-1.

17.2 Detailed Implementation Steps

dt.zero.z2_optimizer.Zero2Optimizer (a Zero1Optimizer subclass) replaces the Phase-1 bucketed all-reduce with a bucketed reduce_scatter_tensor, dividing by dp_size as before (P6, §6). Bucket boundaries must align with parameter-shard boundaries (I7, §7) so a reduce-scattered chunk never straddles two parameters' shards. Gradient accumulation across grad_accum_steps micro-batches happens locally (no collective) for the first N-1 steps; the reduce-scatter fires once on the Nth (ADR-09, §9; I3, §7).

17.3 Deliverable

Zero2Optimizer reduces gradient peak memory to 1/dp_size of DP-only (M6, §32), with an identical loss curve to bit-exactness vs. ZeRO-1.

17.4 Acceptance Criteria

Parameter values are bit-identical between ZeRO-1 and ZeRO-2 runs at every step (I1, §7); peak GPU memory on a 13B-param model at DP=8 shows the expected gradient_dtype_bytes * num_params * (1 - 1/dp_size) saving (M6, §32).

17.5 Conformance Fixtures

correctness/corpora/zero/z2_vs_z1_bitexact.safetensors; benchmarks/results/z2_memory_profile.json; malformed fixture: a bucket whose size is not a multiple of the parameter-shard size, expect a BucketAlignmentError at construction (I7, §7), not runtime corruption.

17.6 Pitfalls

reduce_scatter's output ordering must align with the parameter-shard ordering — NCCL gives chunk r to rank r contiguously, matching the shard layout only if both use the same flat ordering; a misalignment silently produces gradients-for-the-wrong-shard, manifesting as slow loss divergence, not a crash. The post-backward hook still fires per-parameter; the bucket must be fully populated before the reduce-scatter issues.

17.7 Performance Concerns

Total wire volume is unchanged from an all-reduce (reduce-scatter + all-gather = all-reduce, P14 §6, MM5 §34) — the memory win is not a bandwidth win; verify via dt.profile.comm_trace (§24) that no bandwidth regression occurred.

17.8 Edge Cases

grad_accum_steps=1 degenerates to firing the reduce-scatter every step (no accumulation-window interaction to test separately). A model whose largest single parameter exceeds one bucket capacity needs a dedicated oversized bucket, same as Phase 1.

17.9 Failure Analysis

A reduce-scatter/shard misalignment is the highest-blast-radius bug in this phase — it corrupts every subsequent step's optimizer update without raising, detected only by the bit-exact bucket (§30) or a slowly-diverging numerical bucket; the fix is re-verifying I7 at every bucket construction, not just at startup.

17.10 Operational Notes

docs/architecture/zero.md's ZeRO-2 subsection documents the bucket/shard alignment contract; engine.is_accumulation_step(i) (trainer-to-engine signal) is the operator-visible hook for debugging accumulation-boundary issues.

18. Phase 6 — ZeRO-3: Parameter Sharding

18.1 Objectives

Shard parameters themselves (Rajbhandari et al. 2020, sec. 4) so each rank holds 1/dp_size of every tensor at rest; all-gather on demand before each module's forward/backward, release after (P4, §6).

18.2 Detailed Implementation Steps

dt.zero.z3_parameter.Zero3Parameter — a persistent local shard plus a refcounted all_gather()/release() pair (I8, §7) that materializes/frees the full tensor. dt.zero.prefetch.PrefetchPolicy — trace-driven by default (ADR-05, §9): record first-pass module access order, prefetch trace[i+1] while trace[i] computes; fixed-depth lookahead is the documented alternative for static graphs. forward_pre_hook/forward_hook (and their backward equivalents) trigger all-gather/release transparently — the user's forward is unchanged (P10, §6). Gradients reduce-scatter per-module (the ZeRO-2 pattern from §17, applied at module granularity, "one module" replacing the bucket boundary).

18.3 Deliverable

Zero3Parameter runs a 6.7B-param model on 8 GPUs at ~1/8 the parameter memory of a DP-only run; the prefetch policy hides ≥ 80% of all-gather latency (M7, §32).

18.4 Acceptance Criteria

The ZeRO-3 loss curve matches a DP run to bit-exactness under the same root seed (I1, §7); step time on a 13B-param model at DP=8 is within 1.2x of a Megatron ZeRO-3 reference (§32).

18.5 Conformance Fixtures

correctness/corpora/zero/z3_vs_dp_bitexact.safetensors; correctness/corpora/zero/prefetch_overlap_fraction.json; malformed fixture: a release() call with no matching prior all_gather(), expect a raised RefcountError (I8, §7), never a silent negative refcount.

18.6 Pitfalls

Shared-parameter ties (tied embeddings) must not be all-gathered twice without an intervening release — refcounting handles this only if every access path goes through the hook, not a direct parameter reference. The prefetch trace assumes a stable model graph — MoE top-k routing violates this; document the constraint and the fixed-depth opt-out. The all-gather's full tensor must live on the comm stream and be record_stream'd on the compute stream before use, or the gather blocks the next module's compute — a well-known PyTorch CUDA-stream correctness trap.

18.7 Performance Concerns

Gradient reduce-scatter at module granularity is finer than Phase 1's bucket boundary — the two approaches compete; ZeRO-3 wins for this phase, with "one module" as the effective bucket size.

18.8 Edge Cases

A module with zero parameters must not trigger a degenerate zero-size all-gather. Nested modules sharing a Zero3Parameter (weight tying across non-adjacent layers) require the framework's refcount to span both hook sites correctly.

18.9 Failure Analysis

A hook that fires on the wrong module (a registration-order bug) either double-gathers (I8 violation, caught) or never gathers (a None-parameter crash at forward time, loud) — the loud failure is preferred and enforced by never allowing a bare-reference fallback path.

18.10 Operational Notes

docs/architecture/zero.md's ZeRO-3 subsection documents the hook-based instrumentation and the prefetch-policy decision tree; dt.profile.timeline (§24) is where the ≥ 80% hidden-latency target (M7, §32) is measured.

19. Phase 7 — Pipeline Parallelism: 1F1B Schedule

19.1 Objectives

Split the model along depth into pp_size stages (GPipe's micro-batch insight, Huang et al. 2019) and schedule forward/backward with 1F1B (Harlap et al. 2018; ADR-04, §9) to keep the bubble at (P-1)/(M+P-1).

19.2 Detailed Implementation Steps

dt.pp.stage.PipelineSplit slices the module by nn.Sequential child boundaries or user-annotated pipeline_split_after("layer.10") points, producing one PipelineStage (§11) per pp_rank. dt.pp.schedule_1f1b.build_1f1b_schedule(pp_size, num_mb, my_pp_rank) constructs the warm-up (stage 0 issues pp_size forwards before its first backward, decreasing per stage), steady-state (alternating forward/backward), and cool-down phases as a ScheduleStep sequence (§11; ADR-04, §9). dt.pp.activation_send/gradient_send implement point-to-point send/recv on the pp_group for activations forward and gradients backward. Weight-staleness (PipeDream's original problem) is avoided, not solved: the optimizer steps once per accumulated batch, so every forward/backward within one accumulation window uses the same weights — the synchronous-1F1B variant; asynchronous weight-stashing is deferred (§39; Narayanan et al. 2021).

19.3 Deliverable

A 4-stage pipeline-parallel transformer that trains end-to-end and matches a single-rank baseline to bit-exactness (I1, §7); the schedule produces the documented (P-1)/(M+P-1) bubble, verified by a timeline trace.

19.4 Acceptance Criteria

A regression test asserts the exact issued-op order for pp_size=4, num_mb=16; 1F1B vs. GPipe throughput on a 4-stage pipeline is ≥ 1.8x at M=2P, converging as M grows (M8, §32).

19.5 Conformance Fixtures

correctness/corpora/pp/4stage_bitexact.safetensors; correctness/corpora/pp/schedule_order_regression.json; malformed fixture: a schedule with an unmatched send/recv pair, expect rejection by the static validator (I9, §7) at build time.

19.6 Pitfalls

The first and last stages are asymmetric — stage 0 owns the data loader and feeds the first micro-batch; the last stage owns the loss and produces the first backward gradient; document the asymmetry explicitly, it is not a bug. A schedule bug that issues an out-of-order recv deadlocks the whole pipeline; the schedule validator traverses the graph and asserts every send has a matching recv (I9, §7) before any rank launches. NCCL send/recv between two specific ranks within a larger group needs batch_isend_irecv, not a dedicated subgroup per pair, to avoid leaking NCCL group lifetimes.

19.7 Performance Concerns

Activation send/recv buffers should be pinned for CPU-staged transfers; GPU-to-GPU intra-node uses NCCL P2P, inter-node uses IB Verbs — the framework relies on NCCL defaults here (ADR-14, §9) rather than hand-tuning transport.

19.8 Edge Cases

num_micro_batches < pp_size never fully fills the pipeline — document the resulting larger bubble rather than silently degrading. A model whose layer count does not evenly divide pp_size requires an explicit pipeline_split_after override, not an automatic (and possibly imbalanced) split.

19.9 Failure Analysis

An unmatched send/recv is caught statically (I9, §7) before launch, converting what would otherwise be an indefinite runtime deadlock (FM-8, §27) into a build-time rejection — the single highest-leverage check in this phase.

19.10 Operational Notes

docs/architecture/pp.md documents the warm-up/steady-state/cool-down schedule diagram; the schedule validator's output is logged so an operator can audit a custom split before launch.

20. Phase 8 — 3D Parallelism Composition

20.1 Objectives

Compose DP, TP, PP, and ZeRO into one (dp_size, tp_size, pp_size, zero_stage) mesh (§11 Mesh) so a single ParallelStrategy change reconfigures the run without a rewrite (§1).

20.2 Detailed Implementation Steps

dt.planner.mesh_planner.build_mesh constructs four ProcessGroups per rank — dp_group, tp_group, pp_group, world_group (§11) — via a topology-aware assignment placing TP-peers on NVLink and DP/PP-peers across IB where the topology permits (P2, §6; I5, §7). The Trainer wrap order is fixed and load-bearing: TP rewrites the model first (shardformer, §14), PP splits the TP-rewritten model into stages second (§19), ZeRO wraps the local stage's parameters last (§16–§18) — reversing this order produces a TP-sharded parameter ZeRO cannot shard further. Seed propagation (§11 dt.core.seed; P8, §6) derives per-source seeds: root_seed XOR hash(dp,tp,pp) for cross-rank-distinct randomness (data loading), root_seed XOR hash(tp,pp) for rank-replicated randomness within DP (weight init, TP-region dropout).

20.3 Deliverable

A 3D-parallel trainer running (D=2,T=4,P=2) on 16 GPUs training a 6.7B-param transformer end-to-end.

20.4 Acceptance Criteria

(D=2,T=1,P=1), (D=1,T=2,P=1), and (D=1,T=1,P=2) runs on the same model and seed match each other's loss curve to bit-exactness (I1, I6, §7); tokens/sec on a 13B model across multiple (D,T,P) configurations is documented per-cluster (M9, §32).

20.5 Conformance Fixtures

correctness/corpora/3d/dtp_equivalence.safetensors; correctness/corpora/3d/16gpu_6b7_e2e.json; malformed fixture: dp_size*tp_size*pp_size != world_size, expect rejection at build_mesh (echoing §12's Phase-0 check, now for the full 3D case).

20.6 Pitfalls

Getting the TP→PP→ZeRO wrap order backwards is the single most consequential Phase-8 bug — the framework asserts the order and fails loudly rather than silently mis-wrapping. num_micro_batches must be derived from grad_accum_steps when PP is active (num_micro_batches = grad_accum_steps), not set independently, or the pipeline never fills (§19). Mixed precision under ZeRO under PP is the hardest combination — cast points are bf16 forward, bf16 backward, fp32 optimizer step, bf16 all-gather of updated parameters (I14, §7); getting a cast point wrong diverges the loss, caught by the bit-exact bucket.

20.7 Performance Concerns

The default world_rank = dp*(T*P) + tp*P + pp assignment is a heuristic that places TP/ PP-peers on adjacent ranks (typically same node) and DP-peers apart (typically cross-node); a cost-model-driven placement (Alpa, ADR-23 §9) is deferred (§39).

20.8 Edge Cases

A (D,T,P) combination where T exceeds the single-node GPU count violates I5 (§7) and must be refused at mesh-build time, not discovered as a slow run. Elastic reform (§23) must rebuild the Mesh from scratch, never patch an existing one in place.

20.9 Failure Analysis

A wrap-order violation is detected by an assertion at Trainer.__init__ (checking that ZeRO's wrapped module has no un-sharded TP-tagged parameters), converting a silent correctness bug into a loud construction-time failure.

20.10 Operational Notes

docs/architecture/3d.md documents the mesh-construction diagram and the wrap-order contract; operators overriding the default placement supply a custom Mesh directly, bypassing mesh_planner.

21. Phase 9 — Activation Checkpointing

21.1 Objectives

Trade compute for activation memory (Chen et al. 2016; Korthikanti et al. 2022) via per-block recompute-on-backward, with selective recomputation of only the cheap-to-recompute, memory-heavy activations (ADR-08, §9).

21.2 Detailed Implementation Steps

dt.checkpoint.recompute.CheckpointedBlock wraps a transformer block's forward in a non-reentrant checkpoint boundary per ADR-08 (§9) (use_reentrant=False is mandatory — the reentrant variant does not compose with ZeRO-3's autograd hooks, §18); the forward discards intermediate activations, backward re-runs forward to reconstruct them. dt.checkpoint. selective.SelectiveCheckpoint drops only the attention softmax/dropout output and the MLP GELU output (Korthikanti et al. 2022), implemented inside the attention/MLP kernels rather than at the block boundary. Interaction with PP (§19): each stage's forward saves only the stage-output activation sent to the next stage; inter-block activations within a stage are checkpointed. RNG state must be preserved at the checkpoint boundary (preserve_rng_state=True, PyTorch default) so the recompute pass consumes identical random numbers (dropout) as the original forward.

21.3 Deliverable

An auto-checkpoint mode wrapping every transformer block, reducing activation memory by num_layers * activation_per_layer per stage; selective recompute integrated with the TP attention wrapper (§15).

21.4 Acceptance Criteria

Loss curve with checkpointing matches the curve without, to bit-exactness (recompute is deterministic, I1 §7); full checkpointing costs ~30% wall-clock, selective costs ≤ 10% (M10, §32).

21.5 Conformance Fixtures

correctness/corpora/checkpoint/full_vs_none_bitexact.safetensors; correctness/corpora/checkpoint/selective_throughput.json; malformed fixture: a checkpoint region nested inside another checkpoint region without an intervening non-checkpointed boundary, expect a documented-and-rejected configuration.

21.6 Pitfalls

use_reentrant=False is mandatory, not optional — the reentrant variant silently breaks ZeRO-3's parameter-gather hooks (§18) because those hooks rely on module.forward() being called exactly twice (original + recompute) in a specific, hookable way. RNG-state mismatch between the original forward and its recompute (if preserve_rng_state is disabled) silently changes which dropout mask applies, corrupting the gradient without any exception.

21.7 Performance Concerns

Full checkpointing's ~30% wall-clock cost (M10, §32) is why selective recomputation (ADR-08, §9) is the default for production; dt.profile.timeline (§24) is how an operator confirms the actual measured penalty on their model.

21.8 Edge Cases

A checkpointed region whose forward has side effects (e.g. an in-place buffer update outside the checkpoint's tracked state) is unsound — an explicit non-goal; users must avoid side-effecting forwards inside checkpoint boundaries.

21.9 Failure Analysis

A use_reentrant=True misconfiguration under ZeRO-3 manifests as a ZeRO-3 hook firing zero or one time instead of twice, producing a None-parameter crash at recompute time — loud, but easy to misattribute to ZeRO-3 rather than the checkpoint flag; the runbook (docs/runbook/) documents this specific failure signature.

21.10 Operational Notes

The auto-checkpoint mode is a ParallelStrategy.activation_checkpoint field (§11) — "none" | "block" | "selective" — a configuration change, not a code change, consistent with §1's goal.

22. Phase 10 — NCCL Collective Hardening

22.1 Objectives

Wrap every remaining direct torch.distributed call in the typed CollectiveOp (§11) and add production-grade backpressure, retry, timeout, and tracing (P7, P11, §6).

22.2 Detailed Implementation Steps

dt.comm.nccl.issue(op) (§11) issues the collective asynchronously, awaits with a bounded timeout, and on NCCLTimeout retries up to twice with a freshly re-initialized NCCL communicator before raising CollectiveTimeout (I11, §7; ADR-14, §9). dt.comm.backpressure. Backpressure bounds in-flight collectives per group to 32 (§4) via a semaphore, preventing host-side memory bloat from queued collectives each holding a tensor reference. dt.profile.hang_detector.HangDetector tracks per-rank last-progress timestamps and flags ranks silent beyond a 60 s soft timeout (§4). Every wrapped collective emits a trace record — (rank, op_id, kind, group_name, shape, dtype, started_at, finished_at, attempts) — to a per-rank JSONL file, integrated with NVTX (ADR-18, §9) for nsys visibility.

22.3 Deliverable

Every NCCL call in the framework routes through CollectiveOp; a hang detector reports a stuck rank within 60 s of progress stopping (M11, §32); a Chrome-trace renderer shows every rank's collectives over time.

22.4 Acceptance Criteria

A chaos test injects a NCCL timeout on rank 3 mid-step and the trainer surfaces CollectiveTimeout naming the rank, group, collective kind, and step within the 60 s soft-timeout floor (§4; M11, §32).

22.5 Conformance Fixtures

correctness/corpora/chaos/forced_timeout_rank3.json; correctness/corpora/chaos/hang_detector_report.json; malformed fixture: a trace JSONL file corrupted mid-write, expect the renderer to skip the malformed record, not crash the whole trace merge.

22.6 Pitfalls

NCCL's own NCCL_BLOCKING_WAIT/NCCL_ASYNC_ERROR_HANDLING env-var timeout path is undocumented in its interaction with torch.distributed — the framework uses Python-side wait_with_timeout and explicitly aborts the communicator on timeout instead. Retrying a "stuck on a peer" timeout just times out again — the policy is exactly two retries with a fresh NCCL group, then surface to the elastic layer (§23), never an unbounded retry loop.

22.7 Performance Concerns

Trace JSONL files grow large on long runs — rotate every 1M records; operators can disable tracing entirely for maximum-throughput production runs (a documented tradeoff against §28 observability).

22.8 Edge Cases

A timeout that fires during the warm-up phase of a PP schedule (§19) must be attributable to a specific (stage, mb_id), not just a bare group name. A backpressure semaphore that is never released (a bug in the release path) must be caught by a queue-depth telemetry alarm, not discovered only as a full stall.

22.9 Failure Analysis

FM-1 (NCCL collective hang, §27) is this phase's primary target — the hang detector's soft-timeout report is the first operator-visible artifact; blast radius is the whole job until the elastic layer (§23) decides reform vs. abort.

22.10 Operational Notes

The collective trace and hang-detector report are cross-referenced in docs/runbook/nccl-timeout.md and docs/runbook/hang.md (§10); collective_timeout_count and the in-flight-collective gauge (§4 backpressure ceiling) are the two Prometheus metrics operators dashboard first (§28).

23. Phase 11 — Elastic Training & Fault Tolerance

23.1 Objectives

Turn a NCCL timeout or a rank crash from a fatal event into a re-shape-and-resume cycle (P7, §6) using torch.distributed.elastic (ADR-17, §9).

23.2 Detailed Implementation Steps

dt.elastic.rendezvous.ElasticRendezvous wraps c10d rendezvous: join() blocks until min_workers have joined; reform_on_failure() is invoked on heartbeat loss and returns a new world size (I15, §7 quorum monotonicity). dt.elastic.checkpoint saves/loads sharded safetensors per rank plus a manifest (ADR-15, §9); re-sharding on load reconstructs each new rank's shard from the union of overlapping source shards via a minimized all-to-all (I12, §7). Restart sequence: rendezvous detects failure → survivors stop and call reform_on_failure → new Mesh is constructed (§20) → most recent checkpoint loads under the new mesh → training resumes from the checkpoint's step. A configurable policy governs proceeding with fewer workers (default: proceed if ≥ 50% of workers remain) vs. waiting for replacement.

23.3 Deliverable

An elastic trainer surviving a kill -9 on one rank of eight and resuming from the most recent checkpoint within 60 s; a sharded-checkpoint format saving/loading in O(model_size/dp_size) per rank.

23.4 Acceptance Criteria

A re-shard test saves under (D=8,T=1,P=1) and loads under (D=4,T=2,P=1) with bit-identical loaded parameters (I12, §7); a chaos test kills a random rank every 100 steps for 1,000 steps and completes with the same loss curve as a non-chaos run modulo lost steps; reform-and-resume completes within 120 s (M12, §32; §4).

23.5 Conformance Fixtures

correctness/corpora/elastic/killrank_resume.json; correctness/corpora/elastic/reshard_8to4x2.safetensors; malformed fixture: a checkpoint manifest whose recorded step number is ahead of the current run (a rollback/replay attempt), expect a refused load (T9, §26).

23.6 Pitfalls

Rendezvous failure-detection must be strictly more conservative than the NCCL timeout, or the world re-forms while NCCL is still trying to recover — the documented ordering is NCCL timeout 30 s < hang detector 60 s < rendezvous detection 120 s (§4; MM7, §34). Checkpoint frequency is a cost/benefit call — every-step is I/O-unaffordable, every-1000-steps loses up to 1,000 steps; the default of every 100 steps is operator-tunable. Optimizer-internal state that does not shard like the parameters (some LR-scheduler internals) must be saved per-rank but read-from-rank-0 — the manifest distinguishes these explicitly.

23.7 Performance Concerns

Re-sharding's all-to-all is minimized per-tensor rather than a naive full gather-then-scatter, bounding the one-time reshape cost at load (not steady-state) time.

23.8 Edge Cases

A rendezvous reform that would drop below min_workers must block, not proceed under-quorum (I15, §7). A checkpoint saved mid-write (crashed process) must be detected via manifest checksum (FM-6, §27) and the loader must fall back to the previous generation automatically.

23.9 Failure Analysis

FM-3 (rank crash) and FM-7 (re-shard mismatch) are this phase's primary targets (§27); the post-load bit-exact assertion (I12, §7) is the last line of defense against a subtly wrong re-shard shipping silently.

23.10 Operational Notes

docs/runbook/oom.md and the elastic-specific sections of docs/architecture/elastic.md document the restart sequence; dt.elastic.checkpoint's manifest is the audit trail an operator reads after any elastic event.

24. Phase 12 — Performance Profiling & Tokens-per-Second Target

24.1 Objectives

Reach ≥ 45% MFU on a 13B-dense transformer at (D=8,T=8,P=1,zero=1) on one DGX H100 node (§4; M13, §32) via systematic profiling rather than ad hoc tuning.

24.2 Detailed Implementation Steps

dt.profile.timeline renders a per-rank, NVTX-annotated view separating compute kernels from collectives (P5, §6), with cross-rank arrows for send/recv pairs. dt.profile.memory renders a per-rank, per-tensor memory timeline broken down by parameter/optimizer-state/gradient/ activation/framework-overhead category, identifying peak-memory timing (typically PP's deepest-layer backward or ZeRO-3's largest all-gather). dt.profile.comm_trace measures achieved-vs-peak NCCL bandwidth per collective, flagging any below 50% of peak as an optimization candidate. Five tuning targets in priority order: gradient-bucket size (§13); ZeRO-3 prefetch depth (§18); TP-topology confinement to NVLink (§14; I5, §7); PP micro-batch count (~4 * pp_size sweet spot, §19); activation-checkpoint policy (§21).

24.3 Deliverable

A timeline view rendering a 1 s slice of a 16-rank run with every op visible; a memory view breaking down peak memory by category for any rank; a bandwidth view flagging sub-50%-of-peak collectives; a documented optimization playbook (docs/runbook/optimization.md).

24.4 Acceptance Criteria

A benchmark suite measures tokens/sec on a 13B transformer across (D,T,P,zero,checkpoint) configurations, published to benchmarks/results/; the best configuration reaches ≥ 45% MFU (M13, §32) on one DGX H100 node.

24.5 Conformance Fixtures

benchmarks/results/13b_mfu_sweep.json; correctness/corpora/perf/leaderboard_regression. json; malformed fixture: a bandwidth measurement on a sub-MB collective (launch-overhead- bound, not bandwidth-bound), expect the tool to annotate and exclude it from the percentage-of-peak average, not report a misleadingly low number.

24.6 Pitfalls

A timeline at full resolution is unreadable — default to a 1 s single-rank view with zoom/ filter. torch.cuda.memory_allocated() excludes PyTorch's page-cache-style reserved memory that torch.cuda.memory_reserved() includes — report both, always. Bandwidth measurement is dominated by the small-message regime; exclude sub-MB collectives from the percentage-of-peak average or the number is meaningless.

24.7 Performance Concerns

This phase is the performance-concerns phase — see §24.2's five-target priority list, each cross-referenced to the phase that introduced the underlying mechanism.

24.8 Edge Cases

A model with highly imbalanced per-layer compute (e.g. an MoE layer) produces a timeline with visible per-rank skew that is expected, not a bug — document the distinction from a straggler (FM-4, §27).

24.9 Failure Analysis

A below-target MFU with no obvious single bottleneck in any of the three views (timeline/ memory/bandwidth) is itself a signal — cross-check against the M-table (§32) row-by-row rather than guessing.

24.10 Operational Notes

benchmarks/results/ is the append-only leaderboard CI compares against for perf-regression gating (§31); the optimization playbook is the on-call's second stop after the triage runbook.

25. Phase 13 — Multi-Node InfiniBand & Production Cluster

25.1 Objectives

Extend from single-host (Phases 0–12) to multi-node IB clusters, validating the scaling-efficiency targets in §4 at 2–1,024 GPUs.

25.2 Detailed Implementation Steps

dt launch --multi-node wraps Slurm's srun or Kubernetes via torchx, exposing MASTER_ADDR/MASTER_PORT/WORLD_SIZE/RANK/LOCAL_RANK to dt.core.init's process-group construction. dt.cli.detect-fabric auto-detects NCCL-over-IB tuning (NCCL_IB_HCA, NCCL_IB_GID_INDEX, NCCL_IB_TC, socket-thread counts) per common cluster profile (DGX A100/H100, generic IB) and validates the IB partition key (P_Key) at startup (T8, §26). The topology detector synthesizes a Topology (§11) from nvidia-smi topo -m (intra-node) and ibstat (IB devices), identifying NVLink-connected TP-natural groups and IB-connected DP-natural groups (P2, §6; I5, §7).

25.3 Deliverable

A 16-host × 8-GPU integration test running a 70B-param model at (D=16,T=8,P=1,zero=1) for 100 steps; a documented multi-node operator runbook covering Slurm, Kubernetes, and Slurm+Pyxis.

25.4 Acceptance Criteria

A throughput benchmark across (2,4,8,16,32) nodes validates scaling efficiency within the §4 targets (≥ 80% at 128 GPUs, ≥ 65% at 1,024 GPUs — M14, §32); a multi-node fault-injection test (elastic + IB bounce) confirms survival of an IB partition.

25.5 Conformance Fixtures

benchmarks/results/multinode_scaling.json; correctness/corpora/elastic/ ib_partition_survival.json; malformed fixture: a misconfigured IB P_Key on one host, expect dt.cli.detect-fabric to flag it at pre-flight, not let the job hang on first cross-host collective.

25.6 Pitfalls

IB performance is sensitive to P_Key and service class (NCCL_IB_TC) — a misconfigured P_Key produces a "works on one node, hangs on two" failure that is excruciating to diagnose without the pre-flight check. MASTER_ADDR/MASTER_PORT TCP rendezvous is a single point of failure for initialization; the framework retries with backoff but ultimately raises rather than hanging silently. NCCL's tree-vs-ring choice depends on IB topology — a full fat-tree favors tree, a torus or partial fat-tree can be 2x slower with tree than ring; the auto-tune calibration phase runs both and picks the faster (ADR-14, §9).

25.7 Performance Concerns

This phase is where the §4 scaling-efficiency targets are actually validated end-to-end, not merely asserted; M14 (§32) is measured, not assumed.

25.8 Edge Cases

A cluster with a mixed NVLink generation across nodes (heterogeneous hardware) must be reflected accurately in the detected Topology or the planner mis-places TP groups. A node dropped from the rendezvous mid-run must be handled by the elastic layer (§23), not by this phase's launcher directly.

25.9 Failure Analysis

FM-5 (IB link flap/partition, §27) is this phase's primary target; the fabric health scan from dt.cli.detect-fabric is the forensic artifact an operator pulls first.

25.10 Operational Notes

The multi-node runbook (docs/runbook/) is cluster-profile-specific (DGX A100, DGX H100, generic IB); docs/compliance/export-controls.md (§10) is cross-referenced for any cross-border multi-node deployment.

28. Operational Readiness

Metrics. Prometheus counters/gauges: step_time_seconds, collective_timeout_count, grad_norm, loss_scale, gpu_mem_allocated_bytes, tokens_per_second, mfu_ratio (§32 M-table).

Tracing. OpenTelemetry spans per collective plus NVTX ranges (ADR-20, §9); trace context propagates rank-to-rank via span links across PP send/recv (§19).

Structured logging. JSONL per-rank logs {rank, step, event, latency_ms}, shipped to a central store.

Dashboards. Three canonical boards: Throughput (tokens/s, MFU), Health (hang-detector status, timeout counts, straggler skew), Memory (peak-by-category from §24's memory view).

Alerting philosophy. Page on hang-detector soft-timeout breach (FM-1, §27) and on bit-exact-bucket CI failure; ticket (non-page) on straggler skew > 20% (FM-4, §27).

SLOs. 99% of training steps complete within 2x median step time; elastic reform completes within 120 s (I15, §7) for 99% of single-rank failures (§4).

Incident response. Named runbooks docs/runbook/{triage,nccl-timeout,oom,hang, divergence}.md (§10); on-call follows triage.md first, then branches by symptom.

Backup/restore. Sharded safetensors checkpoints (ADR-15, §9) every 100 steps (§4); manifest-driven restore validated by I12 (§7).

Deployment topology. Single-node Docker Compose for dev (4-GPU sim); Slurm srun or Kubernetes+torchx for production multi-node (§25).

Canary/rolling-upgrade. A new framework version is canaried on a 2-GPU bit-exact run before fleet-wide rollout; rollback is a version pin in requirements.txt/pyproject.toml.

Migration. Checkpoint-manifest format_version is stamped; a migration script re-writes old manifests forward (§29).

29. Compatibility & Versioning

Wire. torch.distributed NCCL/Gloo wire format is PyTorch-version-pinned (ADR-01, §9); mixing minor PyTorch versions across ranks is unsupported and detected at process-group init (version handshake).

Storage. The checkpoint manifest carries format_version; dt.elastic.checkpoint refuses to load a manifest whose major version differs without an explicit --allow-migration flag.

Schema evolution. ParallelStrategy fields (§11) are additive-only with defaults; removing a field is a MAJOR-version break.

API stability. Trainer, ParallelStrategy, ProcessGroup, CollectiveOp (§11) are the stable public surface under SemVer; internal dt.zero/dt.pp module internals are not.

Migration. A dt.cli migration subcommand re-shards/re-versions a checkpoint from version N to N+1.

Deprecation policy. A deprecated field/flag warns for one MINOR version, errors for one more, then is removed — a 2-MINOR-version window.

SemVer. MAJOR.MINOR.PATCH; MAJOR breaks checkpoint or public-API compatibility; MINOR adds parallelism features (e.g. a new ZeRO stage flag) additively; PATCH is bugfix-only and never changes the bit-exact reduction order (I1, §7) inside a MAJOR.MINOR.

Rolling-upgrade. Mid-run version upgrade is unsupported; upgrades happen at checkpoint boundaries between runs only.

30. Testing & Verification Strategy

Unit. Per-module tests for dt.core, dt.comm, and each engine (dt.dp, dt.tp, dt.pp, dt.zero) using the dt.comm.shim single-process backend.

Integration. Multi-process torch.multiprocessing.spawn-based tests per phase's correctness bucket (below), exercising real NCCL/Gloo.

Property-based. Shard-partition properties (I4, §7: the union of shards reconstructs exactly the full tensor) checked across randomly generated tensor shapes and world sizes.

Differential. Every parallel strategy diffed bit-exact against the single-GPU baseline (I1, §7) — the bit-exact bucket in correctness/corpora/dp/.

Fuzzing. Malformed ParallelStrategy combinations (non-divisible dp*tp*pp != world_size, tp_size not dividing hidden_dim) fed to the planner; must raise a typed error, never silently misconfigure.

Chaos. correctness/corpora/chaos/ — forced NCCL timeout, kill -9 on a rank, simulated IB bounce, rendezvous membership change (FM-1, FM-3, FM-5, FM-7, §27).

Deterministic replay. dt.testing.replay re-runs a recorded schedule + seed and asserts an identical loss curve — the core bit-exact mechanism (I1, I6, §7).

Soak. A 1,000-step chaos test that kills a random rank every 100 steps and asserts the final loss curve matches a non-chaos run modulo lost steps (FM-3, §27).

Fault injection. dt.testing.chaos programmatically injects NCCL timeouts, OOM, and rank kills at declared steps.

Conformance. correctness/report_schema.json defines the report contract every bucket must emit.

Performance-regression gating. benchmarks/ runs weekly; a regression beyond the M-table (§32) thresholds fails the release gate (§31).

Every phase's N.5 Conformance Fixtures (§12–§25) instantiates this strategy against that phase's specific invariant.

33. Scalability Analysis

Constant per rank as world size N grows, with ZeRO-3 + TP + PP fully engaged: O(model_size / (tp_size × zero_shard)) memory per rank; O(1) collective count per training step per bucket (bucket count is model-size-dependent, not N-dependent).

Grows with N: coordination overhead — rendezvous membership O(N), all-reduce ring latency term O(N) hops (tree: O(log N)), checkpoint manifest size O(N).

Named bottlenecks, smallest-N to largest: (1) NVLink intra-node bandwidth saturates first for TP at T > 8 (no more NVLink-connected GPUs per node); (2) IB inter-node bandwidth for DP all-reduce at very large DP; (3) rendezvous/coordination overhead above ~512 workers; (4) pipeline bubble at low micro-batch counts.

Horizontal scaling. Adding DP replicas is near-linear to the IB bandwidth ceiling (§36 M-derivation); adding PP stages helps memory, hurts bubble (§19).

Vertical scaling. More HBM per GPU raises the ZeRO-3 shard count needed before a model fits — not a lever this framework controls, but it changes the optimal (D,T,P).

Sharding/partitioning. ZeRO progressively shards optimizer → gradient → parameter (§16–§18); TP shards within a layer (§14); PP shards across depth (§19) — three orthogonal axes composed in §20.

Coordination overhead. Rendezvous heartbeat and manifest-write cost grows O(N); above ~512 workers this becomes measurable (> 1% of step time) — the Phase-13 (§25) multi-node tuning target.

Practical ceiling. The design's practical ceiling is ~1,024 GPUs / 70B dense params at ≥ 65% scaling efficiency (§4, M14 §32); beyond that, 3D-mesh tuning and Alpa-style auto-planning (§38) become necessary.

Levers beyond the ceiling. Automatic cost-model planning (deferred, §39), asynchronous pipelines with weight-stashing (deferred, §39), CPU/NVMe offload to trade bandwidth for reach (deferred, §39).

34. Mental Models & First Principles

  • MM1 — A collective is a distributed state machine, not an RPC. Predicts that a timed-out all-reduce leaves ranks in unknown, not synchronized, state. Bug class without it: assuming a timed-out collective "mostly happened" and proceeding. Applies in §11 CollectiveOp, §22 Phase 10.
  • MM2 — Sharding trades memory for a de-refresh dance. Predicts that once parameters are really sharded (ZeRO-3), prefetch becomes necessary, not optional. Bug class without it: a naive ZeRO-3 forward that stalls on every module's all-gather. Applies in §18 Phase 6.
  • MM3 — Bit-exactness is a compiler-level discipline, not a testing afterthought. Predicts every reduction order must be fixed at design time, not patched in later. Bug class without it: a correctness suite bolted on after the fact that can never actually pass. Applies in §12 Phase 0, I1 (§7).
  • MM4 — The pipeline bubble is a scheduling problem, not a hardware problem. Predicts 1F1B vs. GPipe is about instruction ordering, not about faster links. Bug class without it: throwing more bandwidth at a bubble that instruction reordering would have fixed for free. Applies in §19 Phase 7.
  • MM5 — Communication volume is conserved across ZeRO stages; only shard residency changes. Predicts ZeRO-2/3's memory wins cost no extra bandwidth. Bug class without it: an engineer expects ZeRO-3 to also cut network load and mis-diagnoses a bandwidth-bound run. Applies in §17 Phase 5, §18 Phase 6, P14 (§6).
  • MM6 — Topology is a graph the planner must consult, never assume. Predicts TP placed across hosts silently tanks throughput. Bug class without it: a working correctness test that is mysteriously 5–10x slow in production. Applies in §6 P2, §20 Phase 8.
  • MM7 — Failure detection has three independent clocks that must be strictly ordered. Predicts a race between NCCL timeout, hang detector, and rendezvous failure-detection if misordered. Bug class without it: the rendezvous tears down the world while NCCL is still trying to recover. Applies in §23 Phase 11.
  • MM8 — Determinism is a global property, not a per-op property. Predicts one non-deterministic kernel anywhere breaks the entire bit-exact chain. Bug class without it: chasing a "flaky" test that is actually a single mis-flagged CUDA kernel. Applies in §12.6 Pitfalls, §13.6 Pitfalls.

Megatron-LM made tensor parallelism (not ZeRO) its foundational primitive, because its niche — dense transformer pre-training on tightly coupled NVLink/IB clusters — rewards the intra-layer sharding this framework's §14–§15 directly reuses.

DeepSpeed made the ZeRO progression (optimizer → gradient → parameter) its foundational primitive, winning in the memory-constrained regime where fitting the largest possible model matters more than peak throughput — the reasoning this framework's §16–§18 is built from.

PyTorch FSDP collapsed the ZeRO-3 idea into a single flatten-then-shard, per-module-wrap API, winning in the "I just want DP-scale memory savings without hand-building TP/PP" regime — a niche this framework deliberately does not occupy (§1 non-goals), because the portfolio's larger models need TP/PP too.

Horovod made ring-all-reduce ergonomics (a simple Python API with tensor fusion) its contribution, winning in the "I have a model that already fits one GPU's memory and just need more of them" regime — exactly Phase 0–1's (§12–§13) scope, before this framework grows further.

36. Back-of-Envelope Capacity Model

All numbers chain from §4 System Constraints.

  1. Per-GPU optimizer memory, DP-only Adam, 13B params. mem = params × 12 bytes (fp32 master + m + v) = 13e9 × 12 = 156 GB — exceeds the 80 GB/GPU ceiling (§4) without sharding.
  2. ZeRO-1 per-rank optimizer memory at DP=8. mem / N = 156 GB / 8 ≈ 19.5 GB (M5, §32).
  3. ZeRO-3 per-rank total memory at DP=8. (16 bytes/param × params) / N where 16 bytes = bf16 param (2) + bf16 grad (2) + fp32 master+m+v (12): (16 × 13e9) / 8 ≈ 26 GB — fits comfortably under the 80 GB ceiling.
  4. NVLink all-reduce time for a 13B bf16 gradient bucket (26 GB), DP=8. Ring cost t = 2*(N-1)/N * size / BW = 2*(7/8) * 26 GB / 900 GB/s ≈ 51 ms (upper bound, ignoring bucketing overlap; §13).
  5. IB cross-node all-reduce, DP=16 across 2 nodes. Same tensor, aggregate ~400 GB/s/node: t ≈ 2 × 26 GB / 400 GB/s ≈ 130 ms.
  6. Pipeline bubble fraction, P=8, M=32 (1F1B). (P-1)/(M+P-1) = 7/39 ≈ 18% (Huang et al. 2019; Harlap et al. 2018; §19).
  7. Activation memory per layer, seq=4096, hidden=4096, batch=1, bf16, no sequence parallel. seq × hidden × 2 bytes ≈ 4096 × 4096 × 2 ≈ 33.6 MB per major activation tensor per layer; with sequence parallelism /tp_size=8: ≈ 4.2 MB (§15).
  8. Rendezvous FD budget sanity check. 1,024 ranks × ~4 sockets (NCCL/Gloo/rendezvous heartbeat/metrics) ≈ 4,096 FDs cluster-wide — well under typical per-host ulimits, not a bottleneck (§33).
  9. Checkpoint save time per rank. shard_size / io_bw = 26 GB / 5 GB/s ≈ 5.2 s per rank (§4), parallel across ranks ⇒ wall-clock ≈ 5–8 s including manifest write.
  10. Tokens/sec target derivation, 13B @ 45% MFU, 1 DGX H100 node. Peak cluster FLOPs = 8 × 989 TFLOPs/s = 7.9e15 FLOPs/s; effective at 45% MFU = 3.56e15 FLOPs/s; FLOPs/ token ≈ 6 × params = 6 × 13e9 = 7.8e10; tokens/sec = 3.56e15 / 7.8e10 ≈ 45,600 (M13, §32).

38. Alternative Architectures (Roads Not Taken)

1. Parameter-server architecture (DistBelief / Downpour SGD lineage).

 worker1 --push grad-->  [ parameter server ]  --pull params--> worker1
 worker2 --push grad-->  [   apply, avg     ]  --pull params--> worker2
 worker3 --push grad-->  [   broadcast      ]  --pull params--> worker3

Regime where it wins: extreme worker-count asynchrony tolerance, heterogeneous or unreliable workers (federated-like settings). Real system: the original TensorFlow parameter-server / DistBelief. Rejected because asynchronous PS updates break bit-exactness (P1, §6; I1, §7) and staleness is un-auditable at the scale this framework targets.

2. Fully automatic cost-model-driven parallelism (Alpa-style).

 model graph -> [ cost model + ILP/DP solver ] -> per-op (D,T,P) assignment -> compiled plan

Regime where it wins: heterogeneous architectures (MoE, mixed-depth) where manual strategy search is infeasible. Real system: Alpa (Zheng et al. 2022). Rejected (ADR-23, §9) because manual ParallelStrategy suffices through 3D parallelism and an auto-planner is a distinct, large research investment.

3. Fully asynchronous pipeline with weight-stashing (original PipeDream).

 stage i:  F(mb1,w0) F(mb2,w0) B(mb1,w0) F(mb3,w1) B(mb2,w0) ...  [stashed weight versions]

Regime where it wins: workloads where draining the pipeline per accumulated batch is too slow and staleness is tolerable. Real system: PipeDream (Harlap et al. 2018). Rejected because weight-version staleness is incompatible with bit-exact single-GPU equivalence (I1, §7).

4. Single flat compiler-driven mesh (GSPMD / JAX pjit).

 eager nn.Module  vs.  [ compiled graph + sharding annotations -> XLA partitioner -> SPMD ]

Regime where it wins: a compiler-first stack where the compiler, not hand-written engines, derives all communication from sharding annotations. Real system: GSPMD / JAX pjit. Rejected because the chosen substrate is eager PyTorch, not an XLA-compiled graph (ADR-01, §9), making compiler-driven sharding propagation unavailable without changing the runtime entirely.

40. Glossary

  • AllReduce — collective that combines values across ranks and returns the result to all.
  • AllGather — collective that gathers distinct per-rank values into a full copy on every rank.
  • ReduceScatter — collective that reduces across ranks and scatters distinct shards to each rank.
  • Ring All-Reduce — bandwidth-optimal all-reduce over a ring topology, 2(N-1)/N data moved per rank.
  • Tree All-Reduce — all-reduce over a tree topology; lower latency at small message sizes or large N.
  • Data Parallelism (DP) — replicate the model, shard the data, synchronize gradients.
  • Tensor Parallelism (TP) — shard a weight matrix's dimension across ranks within one layer.
  • Pipeline Parallelism (PP) — shard model depth across ranks, pass activations/gradients between stages.
  • ZeRO — Zero Redundancy Optimizer; progressive sharding of optimizer state (stage 1), gradients (stage 2), parameters (stage 3).
  • Micro-batch — the smallest unit of forward/backward the trainer schedules.
  • Gradient Accumulation — summing gradients over multiple micro-batches before an optimizer step.
  • 1F1B — one-forward-one-backward pipeline schedule (PipeDream), minimizing bubble vs. GPipe.
  • Bubble (pipeline) — the idle-time fraction while the pipeline fills/drains.
  • Weight Stashing — keeping historical weight versions so a pipelined backward uses the same weights its forward used.
  • Column-Parallel Linear — a Linear layer sharded along its output dimension.
  • Row-Parallel Linear — a Linear layer sharded along its input dimension.
  • Sequence Parallelism — sharding the sequence dimension of activations between TP collectives.
  • Activation Checkpointing — discarding activations during forward and recomputing them during backward to save memory.
  • Selective Recomputation — checkpointing only the cheap-to-recompute, memory-heavy activations.
  • Mixed Precision Training — computing forward/backward in reduced precision (fp16/bf16) with an fp32 master copy.
  • Loss Scaling — scaling the loss to keep fp16 gradients within representable range.
  • Process Group — a named, typed handle to a subset of world ranks that participate in collectives together.
  • Mesh — the mapping of (dp_rank, tp_rank, pp_rank) coordinates to world ranks.
  • Topology — the physical description of hosts, GPUs, NUMA nodes, and link bandwidths.
  • Shard — a partition of a tensor or state assigned to one rank.
  • Reduce-Scatter/All-Gather Duality — the wire-level equivalence between an all-reduce and a reduce-scatter followed by an all-gather.
  • Prefetch (ZeRO-3) — issuing the next module's parameter all-gather during the current module's compute.
  • Comm-Compute Overlap — issuing a collective on a separate CUDA stream so it runs concurrently with unrelated compute.
  • Bucket (gradient) — a fixed-size buffer that batches multiple parameters' gradients into one collective.
  • Backpressure — bounding the number of in-flight collectives to prevent host memory bloat.
  • Elastic Training — dynamically changing world size on worker failure/join without restarting from scratch.
  • Rendezvous — the coordination protocol by which workers agree on membership and world size.
  • Re-sharding — reconstructing sharded state under a different mesh shape than it was saved under.
  • MFU (Model FLOPs Utilization) — achieved FLOPs/s divided by peak hardware FLOPs/s.
  • Bit-Exactness — the property that two runs produce byte-identical outputs given identical inputs and configuration.
  • NVLink — NVIDIA's high-bandwidth intra-node GPU interconnect.
  • InfiniBand (IB) — a high-bandwidth, low-latency inter-node network fabric common in GPU clusters.
  • NCCL — NVIDIA Collective Communications Library, the GPU collective backend.
  • Gloo — a CPU-capable collective communications backend used as a fallback.
  • Hang Detector — a subsystem that flags ranks making no step progress within a soft timeout.
  • Straggler — a rank that is anomalously slow, delaying every collective it participates in.
  • Shardformer — the module-tree pass that rewrites nn.Linear/nn.Embedding into their tensor-parallel equivalents.
  • Vocab-Parallel Cross-Entropy — a cross-entropy computation that avoids materializing the full vocabulary-sized logit tensor on every rank.
  • Deterministic Mode — a PyTorch execution mode that forces deterministic kernel selection at a throughput cost.
