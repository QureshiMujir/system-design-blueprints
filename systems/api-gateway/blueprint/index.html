165 — API Gateway

Project Number: 165

Project Name: API Gateway

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a from-scratch Layer-7 API gateway in Rust: a clustered edge/ingress process that terminates client TLS (RFC 8446), parses HTTP/1.1 (RFC 9112) and HTTP/2 (RFC 9113) — HTTP/3 (RFC 9114 / QUIC RFC 9000) deferred — matches each request against a routing table keyed on host, path, header, and method, drives the request through an ordered filter/middleware chain (authentication, authorization, rate limiting, request/response transformation, CORS), selects a healthy upstream endpoint from a load-balanced connection pool, forwards with bounded retries under a shared budget, applies deadlines and circuit breaking, optionally serves or stores a response per RFC 9111 caching semantics, and emits metrics/traces/access logs for every request — all driven by a configuration plane that hot-reloads without dropping in-flight connections. The system's load-bearing concern is the API contract surface: the routing table, the auth/quota/transform pipeline, and the config plane are the product. Raw byte-forwarding throughput is necessary but secondary — contrast with the sibling Reverse-Proxy blueprint (project 82), whose load-bearing concern is raw proxy throughput and protocol/WAF breadth (five protocol surfaces, edge Wasm/Lua programs, cache, TLS/ACME) without an API-contract model layered on top.

Phase-0 deliverable (crates, one per bullet):

  1. gwy-core — shared types, config schema, error taxonomy, deadline primitive.
  2. gwy-proto-h1 — HTTP/1.1 wire codec: strict parser, chunked transfer-encoding, trailers.
  3. gwy-proto-h2 — HTTP/2 codec: HPACK (RFC 7541), stream multiplexing, flow control.
  4. gwy-router — host/path/header/method route table and matcher.
  5. gwy-filters — filter-chain framework plus built-in authn/authz/rate-limit/transform/CORS.
  6. gwy-upstream — cluster manager, connection pool, load balancer, health/outlier detection.
  7. gwy-resilience — retries, retry budgets, timeouts, circuit breaker.
  8. gwy-cache — response cache keyed and validated per RFC 9111.
  9. gwy-config — config snapshot, schema validation, hot-reload watch/push.
  10. gwy-observe — metrics, tracing, structured access log.
  11. gwy-admin — isolated admin/stats HTTP endpoint.
  12. gwy-bin — the gwyd binary; wires the above into a thread-per-core runtime.

System boundaries:

  • Provides — TLS termination and ALPN negotiation; H1/H2 downstream and upstream codecs; host/path/header/method routing with precedence; a compiled filter chain (authn via JWT/JWKS, authz, rate limiting, transformation, CORS); upstream pooling, load balancing, active/passive health checking, outlier ejection; budgeted retries, timeouts, circuit breaking; RFC-9111 response caching; a hot-reloadable, versioned, validated config plane; cardinality-bounded observability; an isolated admin/stats surface.
  • Delegates — TLS cryptographic primitives to rustls/ring; DNS resolution to a standalone resolver crate; certificate issuance/rotation to an external ACME client or CA (see Deferred Features Register); persistent credential storage to a secrets manager (the sibling Secret-Vault blueprint); backend business logic entirely to upstream services.
  • Does NOT provide — a developer portal, a billing system, GraphQL federation, a full OpenAPI-schema-aware request validator (only per-route structural limits), multi-region active-active config replication (v1; see Deferred Features Register), a WASM plugin runtime (v1; compiled-in Rust filters only).

Non-goals (explicit):

  • Not a service mesh sidecar. No per-pod sidecar injection, no workload-identity mTLS mesh, no east-west service-to-service transparency. That is the sibling Service-Mesh blueprint (project 164); this gateway is a single north-south ingress hop, not a ubiquitous per-hop proxy.
  • Not an L4 load balancer. Every stage inspects or mutates the HTTP request/response; blind byte/connection forwarding with no application-layer awareness is a strictly smaller system.
  • Distinct from Reverse-Proxy (project 82). Reverse-Proxy's bar is protocol/throughput breadth (five protocol surfaces including WebSocket/SSE, a WAF rule engine, sandboxed edge programs, ACME). This gateway's bar is the API contract surface: a routing table with method/header precedence semantics, a consumer-facing auth/quota/transform pipeline, and a config plane whose correctness (atomic swap, validation, rollback) is treated as a first-class distributed-systems problem, not a config-file convenience.

Deployment model: edge fleet (internet-facing, TLS-terminating, N nodes behind an L4 VIP/anycast, DMZ network segment) and per-cluster ingress (inside a Kubernetes cluster or VPC as the north-south ingress data plane fronting many backend services). Both share the same binary; deployment mode only changes the config plane's config source and the trust boundary of the "client".

Users/operators: platform/infra teams operate the fleet and own the config plane; API-producer teams register routes and clusters; the platform team owns global auth/quota policy defaults, route owners can layer route-scoped overrides.

What later phases unlock: HTTP/2 (§17) unlocks gRPC-shaped traffic and multiplexed upstream connections; §18 unlocks safe traffic shifting during partial outages; §20/§21 unlock multi-tenant API productization (metered, quota-enforced, authenticated APIs); §22 unlocks config changes without a restart and origin-load reduction via caching.

Language: Rust — memory safety without GC pauses on the request-parsing hot path (the historical CVE class this eliminates, see §24 T1/T5 and the 2017 Cloudbleed incident), fearless concurrency for thread-per-core sharding (ADR-05), zero-cost trait-object composition for the filter chain, and a production-proven async ecosystem (tokio, hyper-adjacent crates, rustls) with real precedent (Cloudflare Pingora, Linkerd2-proxy — §33). Rejected: Go — GC pauses interact badly with the p99.9 tail budget under high connection counts (§4); C++ — memory-safety surface on a security-critical parsing path is a defensible risk to eliminate (same argument as the sibling Service-Mesh blueprint, project 164); Lua/OpenResty (Kong's model) — coroutine scheduling and GC produce latency tails that are hard to reason about at scale (§33).

Prerequisites: HTTP/1.1 and HTTP/2 wire semantics (RFC 9110/9112/9113); TLS 1.3 handshake mechanics (RFC 8446); async I/O event-loop models; token-bucket and sliding-window-counter math; basic queueing theory (M/M/1-adjacent reasoning for pool sizing, §34).

Timeline: Phase 0 in 3 weeks (one senior engineer); full system (through Phase 11) in approximately 11 months at one-engineer pace, with Phases 4–9 partially parallelizable across two engineers once the Phase 3 filter-chain contract is frozen.

Deferrals (anchors are real headings elsewhere in this document; see the Deferred Features Register for the full table):

  • PhaseDeferred("§17 Phase 5 — HTTP/2 Downstream and Upstream") — HTTP/3 (QUIC, RFC 9000/9114, QPACK RFC 9204) downstream support.
  • PhaseDeferred("§15 Phase 3 — Filter-Chain Framework") — WASM-sandboxed third-party filters.
  • PhaseDeferred("§16 Phase 4 — TLS Termination + ALPN") — mutual TLS to upstream clusters.
  • PhaseDeferred("§22 Phase 10 — Response Caching + Hot-Reloadable Config Plane") — multi-region active-active config replication.
  • PhaseDeferred("§21 Phase 9 — Rate Limiting (Local Then Global)") — count-min-sketch-based heavy-hitter detection (Cormode & Muthukrishnan 2005) for adaptive per-key quota tightening.

2. Why Build This

  • API-contract-first design distinct from raw proxying: routing + auth + quota + transform composition mirrors real platform-engineering work (the Kong/Apigee/AWS API Gateway lineage).
  • The filter/middleware chain is the single most reusable abstraction across gateways, service meshes, and serverless edge platforms — get its contract right once, reuse the reasoning everywhere.
  • Token-bucket and sliding-window-counter math (§21) — foundational to every multi-tenant quota system, not just this one.
  • Circuit breaker / bulkhead / timeout vocabulary (Nygard, Release It!) — the industry-standard resilience language, exercised concretely in §19.
  • Connection pooling, load balancing, and outlier ejection (§18) are the same machinery inside every service mesh and reverse proxy — compare depth-of-focus against Reverse-Proxy (82).
  • Hot-reloadable config plane with atomic snapshot swap (§22) — a recurring distributed-systems pattern (control-plane push, xDS-adjacent, see §33 vs. Envoy).
  • JWT/JWKS-based stateless auth verification at the edge (§20) — the dominant pattern for API security today (RFC 7519, RFC 7517-adjacent JWKS, RFC 6749/RFC 7235 context).
  • RFC 9111 cache semantics (Vary, validators, stale-while-revalidate) — subtle correctness rules most engineers get wrong the first time; §8 works them out explicitly.

Box paragraphs:

Listener/Acceptor — one bound socket per port per worker via SO_REUSEPORT; accepts onto a bounded per-worker queue (SEDA admission control, Welsh 2001); trust boundary: untrusted network input begins here.

TLS Terminator — rustls session per connection; negotiates ALPN (h2, http/1.1); concurrency boundary: one terminator instance per accepted connection, no shared mutable state across connections except the session-ticket/PSK cache.

Protocol Codec (H1/H2/[H3]) — parses wire bytes into RequestContext-ready frames; protocol boundary: strict RFC 9112/9113 parsing rejects ambiguous framing (smuggling defense, I5/T1).

Request Context Builder — allocates the per-request Deadline, canonicalizes headers, attaches trace context; persistence boundary: nothing persisted here, pure in-memory construction.

Router/Matcher — resolves (RouteMatch, captures) from the active ConfigSnapshot; read-only against the snapshot Arc, never mutates it (I4).

Filter Chain — ordered, priority-driven Filter trait objects; concurrency boundary: filters may hold cross-request shared state (rate-limit counters) behind atomics/sharded locks, never blocking the async executor synchronously.

AuthN/Z filter — verifies JWT signatures against a JWKS cache (§20); trust boundary: this is where an unauthenticated request becomes an identified principal or is rejected.

Rate Limiter — token-bucket (local) / sliding-window-counter (global, §21); queue boundary: admission control, never queues past its own decision latency budget.

Transformer — header/body rewrite per route config; zero-copy where the transform is a no-op, copies across the trust boundary when content is mutated.

CORS filter — preflight (OPTIONS) short-circuit and response-header injection per route policy; explicit filter, never a blanket bypass (§24 T7 note on OPTIONS-bypass pitfalls).

Response Cache — RFC 9111 freshness/validation; persistence boundary: per-worker in-memory LRU, no cross-node consistency by default (ADR-20).

Retry+Timeout+CircuitBreaker layer — resilience machinery (§19); concurrency boundary: retry budget is a shared atomic counter per cluster, not per-request state.

Cluster Manager (LB + Pool + Health/Outlier) — owns upstream Endpoint state machines (§18); persistence boundary: health state is process-local, rebuilt on restart from a fresh probe cycle.

Config Plane — validated, versioned ConfigSnapshot behind an ArcSwap; the sole writer of routing/filter/cluster state; hot-reload triggers an atomic pointer swap (I4, P2).

Admin/Stats endpoint — isolated listener (I13), never reachable from the public data-plane bind; serves /healthz, /metrics, /config/dump.

Telemetry — metrics/tracing/access-log emission is async and off the hot path (P9, Welsh 2001 backpressure principle); cardinality-bounded labels (§24 T6).

6. Design Principles

P1. Fail-open/fail-closed contract is explicit per mechanism. Every added mechanism (auth, rate limit, cache, retry) declares its failure stance in config, not by accident. Tradeoff: fail-open trades security/correctness for availability; fail-closed trades availability for correctness. Operationally: the stance must be visible in /config/dump. Violating it: an unconfigured stance defaults ambiguously and an outage in a dependency (e.g., JWKS fetch) silently becomes either an auth bypass or a total outage — both are incidents, but an undeclared one is undebuggable.

P2. Config changes are atomic and versioned. A reload either fully applies or fully rolls back — never partially. Tradeoff: atomic swap costs one extra Arc allocation per reload versus in-place mutation, negligible next to reload frequency. Operationally: ConfigVersion is monotonic (I12). Violating it: a request can observe routes from version N and filters from version N+1, an inconsistent hybrid no one configured (I4).

P3. Deadlines propagate, never re-originate. A request's Deadline is set once at ingress and consumed, never extended, by every downstream wait. Tradeoff: a slow filter cannot "buy more time" for a request already close to its budget. Operationally: every blocking call (JWKS fetch, cache lookup, upstream RPC) takes a deadline-aware future. Violating it: a single slow dependency can hold a request indefinitely, defeating the whole timeout budget (I1).

P4. Retries consume a shared budget, never an unlimited allowance. A retry storm is how a gateway turns a partial outage into a total one (Nygard). Tradeoff: a strict budget occasionally denies a retry that would have succeeded. Operationally: budget is tracked per cluster as a token bucket refilled by successful primary requests. Violating it: retries amplify load on an already-degraded upstream until it fails completely (§34 amplification derivation, I6).

P5. Hop-by-hop headers are stripped; client-supplied trusted-header names are never forwarded unvalidated. Tradeoff: a strict strip list must be maintained and can lag a new hop-by-hop header. Operationally: Connection, Transfer-Encoding (post-parse), Keep-Alive, TE, Trailer, Upgrade are stripped by the codec, not a filter. Violating it: a client can inject Connection: Authorization to strip auth downstream of the check that ran on it (§24 T1, I5).

P6. Buffers are bounded; no request drives unbounded allocation. Tradeoff: a bound rejects a legitimately large body unless the route explicitly raises the cap. Operationally: default 1 MB per §4; per-route override to 100 MB max. Violating it: a single large-body request can exhaust node memory (I2, SEDA backpressure principle, Welsh 2001).

P7. Thread-per-core sharding avoids cross-core synchronization on the hot path. Tradeoff: per-core state (route-table cache line, connection-pool shard) can be momentarily inconsistent across cores versus a single shared structure. Operationally: SO_REUSEPORT plus per-core Tokio runtimes (ADR-05). Violating it: a shared mutex/atomic on the hot path becomes a cache-line-bouncing bottleneck under multi-core load (§30, §31).

P8. Compiled filters over dynamic scripting, for v1. Tradeoff: no filter can be added without a rebuild until WASM lands (Deferred Features Register). Operationally: predictable latency, no GC/coroutine jitter (contrast Kong/Lua, §33). Violating it (i.e., adding an interpreted scripting layer prematurely) reintroduces the tail-latency unpredictability this build exists to avoid.

P9. Observability is cardinality-bounded by construction. Tradeoff: per-consumer metrics are hash-bucketed, losing exact per-consumer dashboards in the metrics pipeline (available in access logs instead). Operationally: label set is fixed at build time (route_id, cluster_id, status_class). Violating it: an unbounded label (raw consumer ID, raw path) can take down the metrics pipeline itself (§24 T6).

P10. Retries are idempotency-aware. Tradeoff: a route must declare its methods/semantics as retry-safe; unsafe methods (e.g., non-idempotent POST without an explicit opt-in) are never auto-retried. Operationally: RetryPolicy.retry_on is scoped per route. Violating it: retrying a non-idempotent write can double-apply a side effect at the origin.

P11. Health-state transitions require hysteresis, not a single failure. Tradeoff: ejection is slower to trigger (multiple consecutive failures required) at the cost of slightly longer exposure to a genuinely failing endpoint. Operationally: the state machine (§8, I11) requires N consecutive failures to eject and M consecutive successes to fully recover. Violating it: a single transient blip ejects a healthy endpoint, and flapping ejection can eject an entire cluster at once (§25 FM-7).

P12. Zero-copy where safe; copy across trust boundaries. Tradeoff: a transform filter that mutates content must copy, costing CPU, to avoid aliasing a buffer a different trust domain still holds a view into. Operationally: Bytes/BytesMut slicing is zero-copy for read-only passes; mutation forces an owned copy. Violating it: an aliased buffer shared across the client/upstream boundary can leak one request's memory into another's response (§24 T5, the historical Cloudbleed class of bug).

P13. Config is validated before it is applied, with automatic rollback on construction failure. Tradeoff: validation adds latency to the reload path (bounded by §4's 500 ms target). Operationally: schema + referential checks (route → cluster existence) run before the snapshot is swapped; a filter-chain construction error rolls back to the prior version automatically. Violating it: a config that parses but is semantically wrong (a route pointing at a deleted cluster) is only caught in production traffic (§25 FM-9).

P14. The admin surface is isolated from the data-plane trust boundary. Tradeoff: operators must reach a separate listener/network segment for admin operations, adding deployment friction. Operationally: admin binds to a private interface only, never the public data-plane port (I13). Violating it: an admin endpoint reachable from the internet is a full config-read/ config-write compromise (§24 T11, the historical Kong 2019 admin-exposure incidents).

Failure edges: Healthy→Degraded on N=3 consecutive request failures (passive) or 1 active-probe failure; Degraded→Ejected on M=2 further failures; Ejected→Probing after a backoff (eject_duration, exponential up to a cap); Probing→Healthy requires K=2 consecutive probe successes; any probe failure in Probing returns to Ejected with a doubled backoff.

8.6 Rate-limiter equations

Token bucket refill: tokens(t) = min(capacity, tokens(t₀) + refill_rate × (t − t₀)); admit iff tokens(t) ≥ cost, then tokens ← tokens − cost.

Sliding-window-counter estimate: estimate = count_curr + count_prev × (1 − (t mod W) / W), where W is the window size; admit iff estimate < limit. Error bound: the estimate's worst-case overshoot versus a true sliding log is bounded by count_prev / W × Δt_boundary, which → 0 as the window boundary is approached from the previous side and is maximal (up to count_prev) at the instant the window rolls over — i.e., worst-case overshoot approaches the prior window's full count only in the pathological case of a single-instant traffic spike exactly at the boundary.

8.7 Cache key derivation and freshness (RFC 9111)

CacheKey = hash(method, scheme, host, path, sorted(query), sorted(Vary-listed request header values)). Freshness: is_fresh = (now − response_date) < freshness_lifetime, where freshness_lifetime derives from Cache-Control: max-age, else Expires, else a heuristic (RFC 9111 section 4.2.2) capped by gateway policy. Validation: on stale hit, issue a conditional request with If-None-Match/If-Modified-Since; a 304 refreshes the stored entry's metadata without re-fetching the body.

8.8 Config document schema and reload protocol (sketch)

GatewayConfig ::= version, listeners[], clusters[], routes[], filters[]
Listener      ::= id, bind_addr, tls?, protocols[]
Cluster       ::= id, endpoints[], lb_algorithm, health_check, circuit_breaker
Route         ::= id, host_match, path_match, method_match, header_match[],

FilterBinding ::= filter_name, scope(global|route), config(json)

Reload protocol: (1) fetch/receive candidate document; (2) schema validation; (3) referential validation (route→cluster, filter→known name); (4) construct new ConfigSnapshot off the hot path; (5) atomic ArcSwap publish; (6) old snapshot dropped once its last request completes (refcounted). Failure at (2)/(3)/(4) aborts before (5) — the running snapshot is untouched (P13).

8.9 Worked example — full request

POST /v1/payments HTTP/2 with a valid JWT, under quota, routed to cluster payments-v1. Router resolves exact-host + exact-path route (rank 1/3, §8.2). AuthN filter verifies signature against a cached JWKS key (I10), attaches principal.sub. Rate limiter's token bucket for (consumer, route) has capacity; admits. Transform filter injects X-Request-Id. Cache filter skips (POST is non-cacheable per RFC 9111 section 3). LB picks an endpoint via power-of-two-choices (§18); pool checks out a pooled H2 stream. Upstream responds 201; response passes through header filter (strips hop-by-hop), access log emitted async.

8.10 Malformed-request examples

  • Header smuggling: both Content-Length: 10 and Transfer-Encoding: chunked present → the codec rejects with 400 (RFC 9112 section 6.3 disallows this combination) rather than guessing which framing wins (§24 T1).
  • Conflicting Content-Length values: two Content-Length headers with different values → 400, connection closed (not kept alive — protocol state is unrecoverable).
  • Oversized headers: cumulative header block exceeds the configured cap (default 16 KB) → 431 Request Header Fields Too Large, connection kept alive if the parser reached a clean frame boundary, else closed.

8.11 Failure-path example

Upstream cluster payments-v1 drops to 40% healthy endpoints (outlier ejection, §8.5). Retry budget for the cluster is at 15% of its 20% cap (§4) — a request whose first attempt hits an ejected-in-flight endpoint (race: ejected after pool checkout) retries once, budget debited to 16%. Circuit breaker for the cluster remains Closed (error rate 12%, below the 50% Open threshold, §19). Requests continue to succeed at reduced capacity; no cascading failure.

12. Phase 0 — Skeleton + Listener + HTTP/1.1 Codec + CI

12.1 Objectives

Stand up gwy-core, gwy-proto-h1, gwy-bin: a working accept loop that parses HTTP/1.1 requests and returns a static response, with CI green. Establish the buffer/deadline primitives every later phase depends on.

12.2 Detailed Implementation Steps

  • gwy-core: Deadline (monotonic, ADR-33), HeaderMap (canonical-lowercase, capped per I2), GatewayError taxonomy, ConfigVersion stub (real versioning lands in §22 Phase 10).
  • Listener: one bound socket per worker via SO_REUSEPORT (ADR-05, P7); bounded per-worker accept queue implementing SEDA-style admission control (Welsh 2001, P6).
  • gwy-proto-h1: strict parser rejecting Content-Length+Transfer-Encoding conflicts per RFC 9112 section 6.3 (I5, §24 T1); chunked transfer-encoding support; header-block size cap (I2).
  • gwy-bin: main.rs wires a tokio multi-threaded runtime configured thread-per-core (ADR-04/ADR-05); loads a static gateway.yaml (no hot reload until §22 Phase 10).
  • CI: ci.yml build+test matrix (ADR-30); cargo-deny dependency policy gate (ADR-03).

12.3 Deliverable

curl http://localhost:8080/ returns a static 200; gwyd --config examples/minimal.yaml starts, binds, and logs its bind address and worker count.

12.4 Acceptance Criteria

  • conformance/h1/cl_te_conflict.txt (CL+TE both present) → 400, zero exceptions across ≥10 smuggling-shaped fixtures in conformance/h1_smuggling/.
  • Single-core static-response throughput ≥ 80,000 req/s (§4 row 1), measured by benchmarks/phase0_static.toml (wrk2, coordinated-omission-corrected).
  • CI green on stable+beta Rust, x86_64+aarch64 (ADR-30).

12.5 Conformance Fixtures

  • conformance/h1/valid_get.txt — well-formed GET → expect 200.
  • conformance/h1/cl_te_conflict.txt — CL+TE both present → expect 400 (malformed).
  • conformance/h1/chunked_valid.txt — valid chunked body → expect 200, reassembled body correct.
  • conformance/h1/oversized_headers.txt — header block > 16 KB → expect 431 (malformed).
  • conformance/h1/replay_prod_sample_001.txt — captured production-shaped traffic → regression.

12.6 Pitfalls

  • Header case mismatch: manifestation — a filter added later silently misses a header; root cause — no canonicalization at the codec boundary; debug — diff raw vs. canonical header names in a trace; signal — filter-miss with no corresponding 4xx; recovery — canonicalize once at parse time, never downstream (I5-adjacent discipline).
  • Accept-loop backpressure absent: manifestation — accept latency spikes under connection bursts; root cause — unbounded accept with no queue cap; debug — gwy_accept_queue_depth; signal — queue depth climbing unbounded; recovery — bounded queue + 503 admission control (P6, ADR-34).
  • Chunked-encoding size desync: manifestation — the next request on a reused connection is misframed; root cause — a parser bug miscounting chunk sizes; debug — differential replay against a reference parser (§28); signal — divergent framing on identical bytes; recovery — close the connection, never guess (I3).

12.7 Performance Concerns

Zero-copy header parsing via Bytes slices into the read buffer (ADR-10/ADR-11) — no per-header String allocation. Pooled read/write buffers per worker (ADR-10), not per-connection heap buffers, bounding allocator pressure under burst accept.

12.8 Edge Cases

Empty request line; request line exceeding the configured max URI length; an HTTP/0.9-shaped request (reject); pipelined requests on one connection (must process strictly in order); a client closing mid-header-parse; a request with a header value containing a bare CR or LF (reject per RFC 9112 section 5.5, smuggling-adjacent).

12.9 Failure Analysis

A miscounted chunk size desynchronizes framing for the request that follows on the same kept- alive connection — the classic connection-reuse-poisons-next-request bug class. Detection: the differential corpus (§28) replays identical bytes against a reference parser and flags any divergence. Containment: connection-scoped, never process-wide (I3). Recovery: close and log; the malformed-request fixtures in 12.5 pin this behavior as a regression gate.

12.10 Operational Notes

Metrics: gwy_requests_total, gwy_parse_errors_total{reason}, gwy_accept_queue_depth. Startup log (structured) includes bind address, worker count, and build version (ADR-32). No hot reload yet — a config change requires a restart until §22 Phase 10 lands ArcSwap-based reload.

13. Phase 1 — Router + Route Matching

13.1 Objectives

Replace the Phase 0 static response with real routing: host + path + method + header matching, with the precedence rules of §8.2, sublinear in route count.

13.2 Detailed Implementation Steps

  • gwy-router: RouteTable built as host HashMap → method HashMap → path prefix trie + compiled regex-set DFA (ADR-12) — the structure that makes matching O(request size), not O(route count) (§31 Scalability Analysis).
  • Precedence engine (precedence.rs) implementing the rank table of §8.2 (exact host > wildcard host > exact path > prefix path > regex path > header specificity > method specificity > created_at tie-break).
  • Header matchers: exact and regex, evaluated linearly only against the small candidate set that survives host/method/path narrowing.
  • RouteMatch construction: captures regex groups into a SmallVec (bounded, I2-adjacent — no unbounded capture growth).
  • Wildcard host matching: single-label only (*.example.com matches api.example.com, not example.com or a.b.example.com) — documented in §8.2 and mirrored in fixtures.

13.3 Deliverable

100-route fixture set loads; requests route correctly by host/path/method/header combination, verified against the worked trace in §8.2.

13.4 Acceptance Criteria

  • Route-match latency ≤ 1 µs average at 10,000 loaded routes (benchmarks/phase1_match.toml, criterion), consistent with the sublinear claim in ADR-12/§31.
  • Property test route_precedence_totality (§28): for any two overlapping routes in a 1,000-route generated fixture set, the precedence engine picks exactly one winner, never zero, never a tie left unresolved — 100,000 generated cases, zero failures.
  • Wildcard-host fixture set (conformance/router/wildcard_host.yaml, 12 cases) passes exactly as specified in §8.2.

13.5 Conformance Fixtures

  • conformance/router/precedence_worked_example.yaml — encodes the §8.2 worked trace, asserts route (b) wins.
  • conformance/router/wildcard_host.yaml — 12 cases distinguishing *.example.com from example.com and multi-label hosts.
  • conformance/router/regex_priority_tiebreak.yaml — two regex routes, asserts higher regex_priority wins.
  • conformance/router/replay_100k_routes.yaml — regression: 100,000-route table load + 10,000 sampled lookups, asserts identical results across two builds.

13.6 Pitfalls

  • Regex routes bypassing the prefix index: manifestation — adding one regex route degrades matching for all routes to linear scan; root cause — matcher topology decided too late; debug — benchmark regression on phase1_match.toml; signal — match latency jumps from ~1 µs to ~100 µs; recovery — regex routes go into a separate compiled DFA set (ADR-12), never mixed into the trie.
  • Path normalization mismatch (the CVE-2021-39156-class Istio bug): manifestation — matcher and upstream disagree on /foo/../bar vs. /bar; root cause — normalization applied inconsistently between match-time and forward-time path; debug — differential fixture with dot-segments; signal — authz bypass via path confusion; recovery — normalize once, forward the normalized form, never let match-time and forward-time paths diverge.
  • Catch-all route ambiguity: manifestation — a route with no match criteria silently swallows all traffic; root cause — admin API allowed an empty-criteria route; debug — route audit tool (tools/route-table-linter); recovery — reject empty-criteria routes at config validation (P13) unless explicitly flagged as a fallback.

13.7 Performance Concerns

Host/method lookup is O(1) (HashMap); path lookup is O(path segments) via the trie, independent of total route count (ADR-12, §31). Header evaluation is linear only over the already-narrowed candidate set (typically ≤5 routes), bounding worst-case cost by request shape, not table size.

13.8 Edge Cases

A path containing percent-encoded slashes (%2F) — matched against the encoded form by default, decoded only when explicitly opted in per route (documented divergence risk, §13.6). A header matcher against a header absent from the request (never matches, not an error). Two routes tied on every precedence rank — resolved deterministically by created_at (§8.2), never by insertion order (which is not guaranteed stable across a config reload).

13.9 Failure Analysis

A regex-priority misconfiguration (two overlapping regex routes with equal priority) resolves deterministically via created_at, but an operator who didn't expect ties will see "wrong" route selection that is actually well-defined — detection: the admin /config/dump surface shows the resolved precedence explicitly per route; recovery: no code recovery needed, this is a documentation/tooling problem solved by tools/route-table-linter flagging tied precedence.

13.10 Operational Notes

Metrics: gwy_route_match_total{route_id}, gwy_route_no_match_total. tools/route-table-linter runs in CI against every committed route fixture to flag catch-all routes and unresolved precedence ties before they reach production.

14. Phase 2 — Upstream Connection Pool + Forwarding

14.1 Objectives

Forward a matched request to a real upstream over a pooled connection; no load balancing or health checking yet (those are §18 Phase 6) — one endpoint per cluster, round-robin-of-one.

14.2 Detailed Implementation Steps

  • gwy-upstream::pool: per-worker ConnectionPool (P7 sharding — no cross-core pool sharing), backed by a lock-free SegQueue of idle PooledConn (ADR-10-consistent, no per-checkout allocation).
  • Checkout/release protocol: a connection is returned to the pool only in a known-clean protocol state (I3) — tagged clean: bool, checked at release(); a mid-body-read connection is closed, not recycled.
  • Forwarding path: RequestContext → upstream HTTP/1.1 request via gwy-proto-h1's writer half; response parsed back through the same codec.
  • DNS resolution: cached per cluster with a bounded TTL, refreshed off the hot path.
  • ClusterConfig stub in ConfigSnapshot (full hot-reload semantics land in §22 Phase 10).

14.3 Deliverable

A request matched to a route forwards to a single configured upstream and the client receives the byte-faithful upstream response, over a reused pooled connection on the second request.

14.4 Acceptance Criteria

  • Connection reuse rate ≥ 95% for a sustained keep-alive client benchmark (benchmarks/phase2_pool_reuse.toml).
  • Pool checkout latency p99 ≤ 5 µs (§4-consistent budget line item, §30 breakdown).
  • conformance/pool/half_read_body_poisoning.yaml: a connection released after a half-read response body is never returned clean (I3) — 0 poisoned reuses across 10,000 generated cases.

14.5 Conformance Fixtures

  • conformance/pool/reuse_basic.yaml — two sequential requests reuse one connection.
  • conformance/pool/half_read_body_poisoning.yaml — malformed-forward case: response body only partially read before the next checkout; asserts the connection is discarded, not reused.
  • conformance/pool/upstream_reset_mid_body.yaml — upstream RSTs mid-response; asserts client sees a clean 502, not a truncated body presented as complete.
  • conformance/pool/replay_keepalive_burst.yaml — regression: 10,000-request keep-alive burst, asserts stable reuse rate across builds.

14.6 Pitfalls

  • Connection reuse after a half-read body poisons the next request: manifestation — the next request on a "reused" connection receives bytes from the previous response; root cause — releasing a connection to the pool before the body was fully consumed or explicitly drained; debug — conformance/pool/half_read_body_poisoning.yaml reproduces deterministically; signal — gwy_pool_conn_discarded_total{reason="dirty"} should be nonzero instead of corrupted responses; recovery — I3's clean-state tag is the structural fix: never skip the check.
  • DNS TTL staleness: manifestation — traffic keeps flowing to a decommissioned IP; root cause — cached resolution outlives the record's actual TTL; debug — compare cached vs. authoritative TTL; recovery — bound the cache TTL from below by a configured floor, never trust an unbounded record TTL.
  • Pool exhaustion cascading: manifestation — one slow cluster's pool fills, but the node's total connection count also approaches the FD budget (§4); root cause — no per-cluster pool cap; debug — gwy_pool_checkout_wait_total{cluster}; recovery — per-cluster max_size (§4 row "upstream pool size"), never a single global pool.

14.7 Performance Concerns

Checkout/release avoids allocation via the pre-sized SegQueue (ADR-10). Forwarding copies the request line/headers into a fresh write buffer only when a transform mutated them (P12); the common no-transform case is a zero-copy passthrough write.

14.8 Edge Cases

Upstream closes the connection immediately after accept (before any bytes) — treated as a connect failure, not a protocol error. Upstream sends a response before the request is fully written (pipelining-adjacent edge, rare but must not deadlock the writer). A checkout race where the pool reports an idle connection that the upstream simultaneously closed (TCP RST arrives concurrently) — detected by a zero-byte read on first use, connection discarded and a fresh one opened transparently to the caller.

14.9 Failure Analysis

Upstream resets mid-body: the client must never see a response that looks complete but isn't — detection is a length/framing check at the codec boundary (an H1 response with a Content-Length that doesn't match bytes actually received before EOF is an error, not a success). Blast radius: connection-scoped. Recovery: 502 to the client, connection discarded (never reused, I3).

14.10 Operational Notes

Metrics: gwy_pool_checkout_total{cluster}, gwy_pool_conn_discarded_total{reason}, gwy_pool_idle_count{cluster}. No load balancing or health awareness yet — a downed single upstream simply fails every request until §18 Phase 6 adds multi-endpoint clusters.

15. Phase 3 — Filter-Chain Framework

15.1 Objectives

Introduce the Filter trait and lifecycle harness (§8.3): ordered execution, short-circuiting, and the phase model (Rewrite → Access → Transform → HeaderFilter → BodyFilter). No real authn/ratelimit logic yet (those are §20/§21) — two trivial filters prove the harness.

15.2 Detailed Implementation Steps

  • gwy-filters::chain: registry HashMap<Box<str>, Arc<dyn Filter>>; execution harness runs filters in (phase, priority desc, name asc) order (§8.3 contract table) — deterministic tie- break mirrors the router's created_at discipline (§13.2).
  • FilterVerdict::Suspend support from day one: the harness must await a suspended future before proceeding, because async filters (external authz calls, §20) arrive in a later phase and retrofitting async support is far costlier than designing for it now (P8-adjacent foresight).
  • Panic boundary: catch_unwind around each filter invocation — a panicking filter converts to a 500 and the worker continues (I14). This is implemented here because every later filter phase depends on this containment existing first.
  • Two reference filters: correlation-id (injects X-Request-Id if absent, Rewrite phase, priority 9000) and request-size-limiter (rejects bodies over a configured cap, Access phase, priority 950) — both exercise the full harness without needing real auth/quota state.
  • plugin_state: a TypeMap-keyed scratch space on RequestContext for cross-phase filter communication within one request (e.g., the authn filter in §20 will set principal for the authz/ratelimit filters to read).

15.3 Deliverable

A request flows through both reference filters in the documented priority order; a deliberately panicking test filter converts to 500 without crashing the worker (I14 verified).

15.4 Acceptance Criteria

  • conformance/filters/order_determinism.yaml: 20 filters at mixed priorities, including ties, produce byte-identical execution order across 1,000 runs (deterministic tie-break, §8.3).
  • conformance/filters/panic_containment.yaml: an injected panic in one filter yields a 500 for that request while a concurrent request on the same worker completes normally — verified by a two-request harness test, 0 worker crashes across 10,000 injected panics.
  • Filter-chain overhead ≤ 2 µs per filter at the Continue fast path (§4/§30 budget line item), measured by benchmarks/phase3_chain_overhead.toml.

15.5 Conformance Fixtures

  • conformance/filters/order_determinism.yaml — mixed-priority ordering with explicit ties.
  • conformance/filters/panic_containment.yaml — malformed-filter-behavior case (I14).
  • conformance/filters/short_circuit_reject.yaml — a filter returning Reject stops downstream filters but log()-equivalent telemetry still fires (§8.3).
  • conformance/filters/replay_mixed_chain.yaml — regression: a 12-filter chain replayed against a captured request corpus, asserting identical verdicts across builds.

15.6 Pitfalls

  • Async retrofitted too late: manifestation — adding Suspend after sync-only filters ship requires a breaking trait change; root cause — treating "most filters are sync" as "all filters are sync"; debug — none needed if designed correctly now; recovery — Suspend exists from this phase (Kong reference-implementation lesson, §5 Reference Implementations #6, applied here).
  • Priority-space drift: manifestation — over time, filter priorities become effectively random and operators can't predict ordering; root cause — no documented priority-range convention; debug — tools/route-table-linter-adjacent filter-priority auditor; recovery — reserve documented ranges per phase (9000+ rewrite, 900-999 access, 800-899 transform) and enforce in code review.
  • Cross-request state leaking into plugin_state: manifestation — a filter accidentally stores cluster-wide state (e.g., a rate-limit counter) in the per-request TypeMap instead of its own module-owned state; root cause — plugin_state looks convenient for anything; debug — a state-lifetime lint in code review; recovery — plugin_state is documented as single-request-lifetime only; anything living longer is the filter's own concern (§8.3).

15.7 Performance Concerns

The harness must not allocate per filter invocation on the Continue fast path — the registry is a pre-built Vec<Arc<dyn Filter>> sorted once at snapshot-construction time (§22), not re-sorted per request. catch_unwind has a small fixed cost (~tens of ns) paid on every filter call — acceptable given the alternative (a worker crash) per I14.

15.8 Edge Cases

A filter chain of zero filters (route has no bindings) — must still run the built-in phases (router match, forward) without special-casing an empty chain. A filter that returns Suspend and then the suspended future itself panics — must still hit the same catch_unwind boundary. Two filters at the exact same priority and the exact same name (a config error) — rejected at validation time (P13), never silently deduplicated.

15.9 Failure Analysis

A filter panic's blast radius is the single request, never the worker (I14) — the containment mechanism is structural (catch_unwind), not best-effort. Detection is immediate (gwy_filter_panic_total{filter} increments synchronously with the 500). Forensics: the backtrace is captured and logged at panic time, correlated to the request's trace ID for postmortem review (§25).

15.10 Operational Notes

Metrics: gwy_filter_duration_us{filter,phase}, gwy_filter_panic_total{filter}, gwy_filter_short_circuit_total{filter}. This phase's harness is the foundation every later filter (authn §20, rate limiter §21, transform, CORS) plugs into without changing the harness itself — the contract is frozen here.

16. Phase 4 — TLS Termination + ALPN

16.1 Objectives

Terminate TLS 1.3 (RFC 8446) at the listener, negotiate ALPN (h2 vs. http/1.1), and wire the TlsContext primitive introduced in §11 into the accept path.

16.2 Detailed Implementation Steps

  • Integrate rustls (ADR-06) as the TLS terminator; certificate chain loaded per Listener at startup, hot-rotation deferred to §22's config-plane mechanism.
  • ALPN negotiation selects h2 when both sides support it, else falls back to http/1.1 (Grigorik, High Performance Browser Networking ch. 4, applied here per §5).
  • Session resumption via TLS 1.3 PSK tickets — the ticket cache is per-listener, bounded, and is the only mutable state a TlsContext holds after handshake (§11 annotation honored).
  • SNI extraction for multi-cert listeners (one listener, many certs, selected by SNI) — the extraction point that a future SNI-routing extension (Reverse-Proxy's TCP-pass-through model, project 82) could hook, though this build always terminates (no pass-through mode, per the non-goals in §1).
  • Reject legacy TLS versions (<1.2) and weak cipher suites at the rustls config layer — structural, not filter-based (defense-in-depth ahead of any application-layer check).

16.3 Deliverable

gwyd serves HTTPS with a self-signed cert from examples/; curl -v shows ALPN negotiated to h2 against an H2-capable client and http/1.1 against a plain HTTP/1.1 client.

16.4 Acceptance Criteria

  • Full-handshake throughput ≥ 4,000 handshakes/s/core (ECDSA P-256), resumed-handshake throughput ≥ 40,000 handshakes/s/core (§4 rows), measured by benchmarks/phase4_tls.toml.
  • conformance/tls/legacy_version_rejected.yaml: TLS 1.0/1.1 ClientHello → handshake failure, 0 successful legacy handshakes across 50 generated cases.
  • conformance/tls/alpn_negotiation.yaml: 4 client-capability combinations (h2-only, h1-only, both, neither) each resolve to the documented outcome.

16.5 Conformance Fixtures

  • conformance/tls/alpn_negotiation.yaml — the 4-combination ALPN matrix above.
  • conformance/tls/legacy_version_rejected.yaml — malformed/downgrade-shaped ClientHellos.
  • conformance/tls/session_resumption.yaml — a second handshake from the same client reuses a PSK ticket; asserts the resumed-path CPU cost is measurably lower (§4).
  • conformance/tls/replay_handshake_corpus.yaml — regression: captured ClientHello corpus replayed across builds, asserting stable accept/reject decisions.

16.6 Pitfalls

  • TLS downgrade / certificate confusion: manifestation — a client is silently downgraded to a weaker version or a wrong SNI-selected cert is served; root cause — permissive rustls config or SNI-to-cert mapping ambiguity; debug — conformance/tls/legacy_version_rejected.yaml and an SNI-mismatch fixture; signal — gwy_tls_handshake_failed_total{reason} spikes on a legitimate client population; recovery — structural version/cipher floor at the rustls config layer, never a filter-level check (§24 T2).
  • Session-ticket cache unbounded growth: manifestation — memory grows with unique client count; root cause — no TTL/size cap on the PSK ticket cache; debug — cache size metric vs. configured cap; recovery — bounded LRU ticket cache, evict oldest on pressure.
  • ALPN mismatch silently falling back: manifestation — an H2-only backend integration test fails intermittently; root cause — a client that claims H2 support but negotiation falls back to H1 without the caller noticing; debug — log negotiated protocol per connection; recovery — expose negotiated protocol in the access log and admin dump for diagnosis.

16.7 Performance Concerns

ECDSA P-256 handshakes cost roughly 5–10× less CPU than RSA-2048 (§13.4-class reasoning, applied here); default to ECDSA certs, support RSA only for backward compatibility. Session resumption (TLS 1.3 PSK) cuts handshake CPU by ~90% for repeat clients — enabling it is the single highest- leverage TLS performance decision in this phase (Grigorik ch. 4).

16.8 Edge Cases

A ClientHello with no SNI (must select a default cert, never fail hard unless configured to require SNI). A ClientHello requesting an ALPN protocol list containing only unsupported values (negotiation fails cleanly, connection closed pre-handshake-completion). A resumption attempt with an expired or forged ticket (falls back to a full handshake, never accepted blindly).

16.9 Failure Analysis

A certificate rotation that ships a chain missing an intermediate breaks every new handshake at once (not gradually) — detection: handshake-failure-rate alert (§26) fires immediately; containment: per-listener, other listeners on other certs unaffected; recovery: rollback via the config plane's atomic snapshot mechanism (§22) applies here even though certs are loaded at listener-startup in this phase — the general "validate before apply" discipline (P13) is the long-term fix landed in §22.

16.10 Operational Notes

Metrics: gwy_tls_handshake_total{result,resumed}, gwy_tls_handshake_duration_us, gwy_tls_cert_expiry_seconds{listener} (feeds the cert-expiry runbook in docs/runbooks/cert-expiry.md, §26). ALPN outcome is logged per connection for negotiation diagnosis.

17. Phase 5 — HTTP/2 Downstream and Upstream

17.1 Objectives

Add HTTP/2 (RFC 9113) on both the client-facing (downstream) and upstream-facing legs: stream multiplexing, HPACK header compression (RFC 7541), and flow control, per the state table in §8.4.

17.2 Detailed Implementation Steps

  • gwy-proto-h2 wraps the h2 crate (ADR-08) rather than hand-rolling a stream state machine — the Cloudflare Pingora reference-implementation lesson (§5, applied here): lean on a mature H2 codec, don't reinvent it.
  • Stream lifecycle implements the Idle→Open→Half-Closed→Closed states of §8.4; flow-control window accounting is debited per DATA frame at both the stream and connection level.
  • Reset-storm guard: cap RST_STREAM frames per connection per window; exceeding it closes the connection — the direct mitigation for CVE-2023-44487 (Rapid Reset), cited in §5 Reference Implementations and §24 T8.
  • Upstream H2: one pooled connection per upstream endpoint suffices for many concurrent logical requests via multiplexing — PooledConn (§11) gains a stream-multiplexed variant; ConnectionPool (§14) now tracks per-connection stream-concurrency headroom, not just idle/busy.
  • HPACK dynamic table: sized per RFC 7541 defaults, bounded to prevent a malicious peer from forcing unbounded table growth (I2-adjacent: header compression state is a buffer too).
  • WebSocket-shaped upgrade requests (RFC 6455) arriving over H1 are detected and handed to a bidirectional-copy path that bypasses body-buffering filters — documented here as an edge case the filter-chain contract (§15) must respect (a filter cannot assume every request has a buffered body).

17.3 Deliverable

An H2 client multiplexes 100 concurrent streams over one TCP connection to the gateway; the gateway forwards to an H2 upstream over one pooled multiplexed connection; both directions verified byte-correct against h2spec-style fixtures.

17.4 Acceptance Criteria

  • conformance/h2/rapid_reset_guard.yaml: a client opening/resetting 10,000 streams/sec on one connection is disconnected once the configured reset budget is exceeded (default: 100 resets/ 10 s) — 0 unbounded-cost accepts across the fixture set.
  • Stream concurrency ≥ 100 simultaneous streams per connection sustained at flow-control-window- bounded throughput (benchmarks/phase5_h2_mux.toml).
  • h2spec-style conformance suite (conformance/h2/h2spec_subset.yaml) passes 100% of the frame-format and flow-control sections relevant to this build's feature set.

17.5 Conformance Fixtures

  • conformance/h2/rapid_reset_guard.yaml — the CVE-2023-44487 mitigation fixture.
  • conformance/h2/flow_control_deadlock.yaml — malformed case: a peer advertises a zero window and never updates it; asserts the gateway times out the stream (I1) rather than blocking forever.
  • conformance/h2/hpack_table_bound.yaml — a peer attempting to force unbounded HPACK dynamic- table growth is rejected.
  • conformance/h2/replay_mux_burst.yaml — regression: 100-stream multiplexed burst replayed across builds for identical per-stream outcomes.

17.6 Pitfalls

  • HTTP/2 flow-control deadlock: manifestation — a stream hangs indefinitely; root cause — a peer advertises a zero-size window and the gateway waits unboundedly for a WINDOW_UPDATE; debug — conformance/h2/flow_control_deadlock.yaml reproduces it; signal — stream duration metric with no terminal frame; recovery — every stream wait is Deadline-bounded (I1) — flow-control waits are not exempt from the deadline contract.
  • Reset-storm cost amplification: manifestation — CPU spikes from stream setup/teardown churn; root cause — no cap on client-initiated resets; debug — gwy_h2_stream_reset_total rate; recovery — the reset-budget guard from 17.2, closing the connection past threshold.
  • HPACK dynamic-table poisoning across streams: manifestation — one stream's header compression state affects another's decode; root cause — the dynamic table is connection- scoped by spec, but an implementation bug could leak entries across an unrelated boundary; debug — differential test against the h2 crate's own conformance suite; recovery — trust the reference h2 crate's HPACK implementation (ADR-08) rather than a hand-rolled one.

17.7 Performance Concerns

Multiplexing collapses many logical upstream requests onto one TCP connection, cutting FD usage from hundreds to tens per upstream target (§30, §34 FD derivation). Flow-control window sizing trades memory (larger windows buffer more in-flight data) against throughput (smaller windows cap achievable per-stream rate under high RTT) — tuned per §4's RTT assumptions.

17.8 Edge Cases

A stream that sends HEADERS with no END_STREAM and never sends DATA or trailers (must still respect the request Deadline, I1). A client that opens the maximum-allowed concurrent streams and immediately half-closes all of them (must not be treated as an attack by itself — only sustained reset velocity triggers the guard). A WebSocket upgrade request routed to a route whose filter chain includes a body-buffering filter (the filter must decline to buffer an upgrade's body, per the 17.2 note).

17.9 Failure Analysis

A flow-control deadlock's blast radius is one stream, not the connection — other streams on the same multiplexed connection continue unaffected (this is the entire point of H2 multiplexing, and a regression here — one stuck stream blocking the connection — is a P0 bug, tested by flow_control_deadlock.yaml). Detection: per-stream deadline-exceeded metric. Recovery: the stuck stream is reset (RST_STREAM) at its deadline, the connection continues serving the rest.

17.10 Operational Notes

Metrics: gwy_h2_streams_active{connection}, gwy_h2_stream_reset_total{initiator}, gwy_h2_flow_control_stalls_total. HTTP/3 remains PhaseDeferred("§17 Phase 5 — HTTP/2 Downstream and Upstream") per §1 and the Deferred Features Register — this phase's codec boundary is where it would eventually plug in.

18. Phase 6 — Load Balancing + Health Checks + Outlier Ejection

18.1 Objectives

Extend clusters from one endpoint to many: pick an endpoint via a real load-balancing algorithm, detect failure via active and passive health checks, and eject/recover per the state machine in §8.5.

18.2 Detailed Implementation Steps

  • gwy-upstream::lb: implement LoadBalancer (§11) with power-of-two-choices weighted by active-request count (ADR-16; Mitzenmacher 2001, applied here per §5) — pick two endpoints at random, route to the one with fewer in-flight requests.
  • gwy-upstream::health: active health checker task per cluster issuing periodic HTTP probes (default interval 5 s, §4) independent of live traffic.
  • gwy-upstream::outlier: passive detector counting consecutive failures from real traffic, feeding the same EndpointHealth state machine as the active checker (§8.5) — the two are independent triggers into one shared state machine, not two competing sources of truth.
  • State machine implementation exactly matches §8.5: Healthy→Degraded at N=3 consecutive failures (passive) or 1 active-probe failure; Degraded→Ejected at M=2 further failures; Ejected→Probing after an exponentially growing backoff; Probing→Healthy at K=2 consecutive probe successes; any Probing failure returns to Ejected with doubled backoff (P11 hysteresis discipline).
  • Weight-aware selection: an endpoint's configured weight scales its selection probability within the power-of-two-choices comparison, not just a post-hoc traffic percentage.

18.3 Deliverable

A 5-endpoint cluster with one endpoint killed mid-benchmark shows traffic shift away from the dead endpoint within the configured detection window, with zero requests routed to an Ejected endpoint.

18.4 Acceptance Criteria

  • Detection-to-ejection latency ≤ 3 active-probe intervals (≤ 15 s at the default 5 s interval, §4) in conformance/upstream/kill_one_endpoint.yaml.
  • conformance/upstream/health_state_machine.yaml: a deterministic-simulator run (§7 methodology) exercises all documented state edges in §8.5 and asserts zero illegal transitions across 100,000 simulated events (I11).
  • Load distribution across 4 healthy endpoints of equal weight is within 5% of uniform under a 10,000-request benchmark (benchmarks/phase6_lb_distribution.toml), consistent with the P2C balance guarantee (Mitzenmacher 2001).

18.5 Conformance Fixtures

  • conformance/upstream/kill_one_endpoint.yaml — the primary failover fixture.
  • conformance/upstream/health_state_machine.yaml — the full state-machine simulator run.
  • conformance/upstream/flapping_endpoint.yaml — an endpoint that alternates healthy/unhealthy faster than the hysteresis window; asserts it does not thrash between states (P11).
  • conformance/upstream/replay_p2c_distribution.yaml — regression: fixed random seed, asserts identical endpoint-selection sequence across builds.

18.6 Pitfalls

  • Outlier ejection removing every endpoint at once: manifestation — a correlated failure (e.g., a shared dependency all endpoints call) ejects the entire cluster simultaneously, turning a partial degradation into a total outage; root cause — no floor on how many endpoints can be ejected concurrently; debug — gwy_endpoint_health_state gauge across the whole cluster; signal — ejected count approaching cluster size; recovery — a configurable "panic threshold" (e.g., never eject past 50% of a cluster) that freezes further ejection and fails open to the remaining endpoints, however degraded (§25 FM-7).
  • Health-check-induced load: manifestation — active probes themselves become a meaningful fraction of backend load at very high endpoint counts; root cause — active-only design without considering probe cost at scale; debug — probe request-rate metric vs. real traffic rate; recovery — passive-only fallback mode for very large/lightweight endpoint fleets (ADR-17 rejected-alternative regime).
  • Weight-zero endpoints still selected: manifestation — a "disabled" endpoint (weight 0) keeps receiving traffic; root cause — the LB's random pre-selection step doesn't exclude zero-weight endpoints before the P2C comparison; debug — selection-distribution fixture; recovery — zero-weight endpoints are excluded from the candidate set entirely, not merely deprioritized.

18.7 Performance Concerns

Power-of-two-choices requires only two random picks and one comparison per selection — O(1), no sorted structure to maintain (contrast consistent hashing's ring maintenance cost, ADR-16 rejected alternative). Health-state reads on the selection hot path are lock-free atomics (P7); only the health-checker task itself writes state transitions.

18.8 Edge Cases

All endpoints in a cluster simultaneously Ejected (§18.6's panic-threshold fallback engages). An endpoint added to a cluster mid-reload starts Healthy optimistically but is subject to the same hysteresis on its first real failure (no grace-period exemption beyond normal detection timing). A probe response that is well-formed HTTP but the wrong status code (e.g., a maintenance-mode 503 from the endpoint itself) counts as a probe failure, not a parse error.

18.9 Failure Analysis

A correlated multi-endpoint failure (§18.6) has a blast radius bounded by the panic threshold — detection is immediate (ejected-count gauge crossing the configured fraction), containment holds remaining capacity in service rather than ejecting to zero, and recovery is automatic once probes succeed again (no manual intervention required for a transient correlated blip, though the docs/runbooks/upstream-brownout.md runbook (§26) covers the sustained case).

18.10 Operational Notes

Metrics: gwy_endpoint_health_state{cluster,endpoint}, gwy_lb_selection_total{cluster,endpoint}, gwy_active_probe_duration_us. The upstream-brownout runbook (§26, docs/runbooks/) is the on-call procedure when ejected-endpoint-count crosses the panic threshold.

19. Phase 7 — Timeouts, Retries with Budgets, Circuit Breaking

19.1 Objectives

Add the resilience layer (Nygard, Release It!, applied throughout this phase per §5): per-try timeouts, budgeted retries (P4/I6), and a per-endpoint circuit breaker (I7).

19.2 Detailed Implementation Steps

  • gwy-resilience::retry: RetryPolicy (§11) scoped per route; retry_on is idempotency-aware (P10) — non-idempotent methods are never auto-retried without an explicit per-route opt-in.
  • gwy-resilience::budget: RetryBudget (§11) as a per-cluster atomic token bucket, refilled by successful primary requests and debited by every retry attempt (I6) — the direct structural defense against the retry-storm amplification derived in §34.
  • gwy-resilience::breaker: per-endpoint CircuitState machine (§11): Closed under normal operation; trips to Open when the error rate over a rolling window exceeds a configured threshold (default 50%); after a cooldown, transitions to HalfOpen and admits a bounded probe count; success returns to Closed, failure returns to Open with backoff (I7 — no other transitions are legal).
  • Deadline interaction: a retry's per-try timeout is always bounded by the request's remaining Deadline (P3) — a retry is never granted a fresh, unrelated timeout budget.
  • Tail-latency reasoning (Dean & Barroso 2013, applied here per §5): a bounded number of hedged retries reduces p99.9 tail at the cost of the amplification tradeoff quantified in §34 — document the tradeoff explicitly in the route-level retry config schema, not just in code comments.

19.3 Deliverable

A cluster with a 50% synthetic failure rate: requests succeed via retry within budget; once the budget is exhausted, requests fail fast without further retry attempts; the breaker trips to Open once the endpoint-level error rate crosses threshold and requests fail immediately (no wasted upstream round-trip) until HalfOpen probing succeeds.

19.4 Acceptance Criteria

  • conformance/resilience/retry_budget_never_exceeded.yaml: a property test asserting retry attempts across 100,000 simulated requests never exceed the configured budget fraction (I6) — 0 violations.
  • conformance/resilience/breaker_state_machine.yaml: deterministic-simulator run exercising every CircuitState edge in I7, 0 illegal transitions across 100,000 events.
  • Deadline monotonicity property test (§28): a retried request's total elapsed time never exceeds its original Deadline, across 50,000 generated retry scenarios (I1, P3).

19.5 Conformance Fixtures

  • conformance/resilience/retry_budget_never_exceeded.yaml — the budget-bound property fixture.
  • conformance/resilience/breaker_state_machine.yaml — the full breaker state-machine simulator.
  • conformance/resilience/deadline_exhausted_mid_retry.yaml — malformed/edge case: a retry would be attempted but the deadline expires first; asserts no retry is attempted past the deadline (I1 takes precedence over I6's budget allowance).
  • conformance/resilience/replay_partial_outage.yaml — regression: a captured 40%-failure-rate traffic replay, asserting stable amplification-factor bounds across builds.

19.6 Pitfalls

  • Retry storms amplifying a partial outage: manifestation — a struggling upstream receives more load from retries than its original failure would have caused, tipping it into total failure; root cause — retries without a shared budget; debug — the amplification derivation in §34 quantifies exactly this; signal — upstream request rate rising as upstream success rate falls; recovery — I6's budget is the structural fix, not a tunable afterthought.
  • Non-idempotent retry double-application: manifestation — a payment is charged twice; root cause — a POST retried without an idempotency-key mechanism; debug — origin-side duplicate- charge report; recovery — P10's idempotency-aware retry_on scoping, defaulting to "safe methods only" unless a route explicitly opts a mutating method in with an idempotency-key contract.
  • Circuit breaker trips on a transient blip, not a real outage: manifestation — a two-request error burst opens the breaker for the whole cooldown window, wasting healthy capacity; root cause — a rolling-window error-rate threshold too sensitive at low request volume; debug — breaker trip rate vs. actual endpoint health (cross-reference §8.5's ejection state); recovery — require a minimum request-volume floor in the rolling window before the breaker is eligible to trip at all.

19.7 Performance Concerns

Retry-budget and breaker-state checks are both lock-free atomic reads on the hot path (P7, consistent with §18.7's health-read discipline). A HalfOpen probe cap (typically 1–3 concurrent probes) bounds the cost of testing recovery without re-flooding a still-fragile endpoint.

19.8 Edge Cases

A request whose deadline expires during the retry-budget check itself (I1 wins — no retry is attempted, regardless of remaining budget). A cluster where every endpoint's breaker is simultaneously Open (the request fails fast with 503/CircuitOpen, no upstream attempt at all — distinct from the outlier-ejection panic-threshold case in §18.6, though both protect against the same class of cascading failure from different layers). A retry attempt that would target the same endpoint as the failed first attempt (P2C re-selection should generally avoid this when other healthy endpoints exist, though it is not forbidden when only one endpoint remains).

19.9 Failure Analysis

A misconfigured retry budget (set too generously) reproduces the retry-storm failure mode this phase exists to prevent — detection: the amplification-factor metric (§26) crossing a configured alert threshold; containment: the budget itself is the containment, just misconfigured; recovery: the retry-storm-containment runbook (§26, docs/runbooks/) walks tightening the budget live via the config plane (§22) without a restart.

19.10 Operational Notes

Metrics: gwy_retry_attempts_total{cluster,outcome}, gwy_retry_budget_remaining{cluster}, gwy_breaker_state{cluster,endpoint} (gauge, matches I7's enumerated states), gwy_breaker_trip_total{cluster,endpoint}. The retry-storm-containment runbook is the primary on-call procedure this phase's telemetry feeds.

20. Phase 8 — Authn/Authz Filter + JWKS Caching

20.1 Objectives

Real identity: verify JWT (RFC 7519) bearer tokens against JWKS-published public keys, cache keys with a bounded staleness window (I10), and add a scope/claim-based authorization filter.

20.2 Detailed Implementation Steps

  • gwy-filters::authn: extract the bearer token (RFC 7235 Authorization header framing); parse header/claims; verify signature for RS256/ES256 (RSA/ECDSA) against a cached JWKS key — never accept alg: none (structural rejection, not a config option — §24 T6/CVE-class defense).
  • JWKS cache: keyed by kid, refreshed on a background task before TTL expiry (I10); a cache miss on an unknown kid triggers an out-of-band fetch bounded by its own short Deadline (P3) — never blocks the request past the request's own deadline budget.
  • Claim validation: exp, nbf, and configurably aud/iss, with a bounded clock-skew tolerance (default ±30 s) — this is where OAuth 2.0 (RFC 6749) bearer-token context applies: the gateway is a resource-server-shaped consumer of tokens it did not issue.
  • gwy-filters::authz: scope/claim-based per-route allow/deny — reads principal from plugin_state (§15) set by the authn filter; runs strictly after authn in the Access phase priority ordering (P10-adjacent ordering discipline: authz without a prior authn is a config error rejected at validation, P13).
  • CORS filter: explicit OPTIONS-preflight handling scoped to routes with CORS policy configured — never a blanket unauthenticated OPTIONS bypass in the core harness (§24 T7 pitfall this structurally avoids).

20.3 Deliverable

A request with a valid RS256 JWT signed by a key published in the test JWKS endpoint (tools/jwks-mock-server) is authenticated and authorized per route scope; an invalid signature, an expired token, and an alg: none token are each rejected with the documented status.

20.4 Acceptance Criteria

  • conformance/authn/alg_none_rejected.yaml: 100% rejection rate across a fixture set of alg: none-shaped tokens, 0 exceptions.
  • JWKS cache hit ratio ≥ 99% under a steady kid population in benchmarks/phase8_jwks_cache.toml (bounded refresh cost per I10).
  • conformance/authz/scope_enforcement.yaml: 20 (route, scope-set) combinations each produce the documented 200/403 outcome.

20.5 Conformance Fixtures

  • conformance/authn/alg_none_rejected.yaml — the alg: none bypass-attempt fixture set.
  • conformance/authn/expired_token.yaml — exp in the past, beyond clock-skew tolerance → 401.
  • conformance/authn/jwks_kid_miss.yaml — an unknown kid triggers a bounded out-of-band fetch, asserts the fetch respects the request's remaining Deadline (I1/P3).
  • conformance/authz/scope_enforcement.yaml — the scope-matrix fixture above.
  • conformance/authz/replay_mixed_principals.yaml — regression: a corpus of mixed valid/invalid tokens replayed across builds for stable authn/authz outcomes.

20.6 Pitfalls

  • JWT signature bypass via alg confusion: manifestation — an attacker resigns a token with alg: none or substitutes an HMAC signature verified against a public RSA key value; root cause — a permissive JWT library default; debug — conformance/authn/alg_none_rejected.yaml and an HMAC-confusion fixture; signal — an authenticated request with no corresponding valid signature check in the verification library's audit log; recovery — pin the accepted algorithm set per route explicitly, never trust the token's self-declared alg alone (§24 T6, the historical CVE class this defends against).
  • JWKS cache staleness widening the key-rotation window: manifestation — a revoked key is still accepted well past its intended rotation; root cause — I10's refresh task falling behind under load or a fetch failure loop; debug — gwy_jwks_refresh_age_seconds vs. configured max- age; recovery — alert when refresh age exceeds a grace threshold, and cap how long a stale key may still be served (a hard ceiling past which authn fails closed).
  • Authz running before authn completes: manifestation — a request reaches the authz filter with no principal set, either erroring confusingly or (worse) defaulting to an allow; root cause — a priority misconfiguration; debug — the priority-space audit from §15.6, extended to flag "authz without a preceding authn at higher priority"; recovery — config validation (P13) rejects a route with an authz binding but no authn binding at a higher Access-phase priority.

20.7 Performance Concerns

RSA-2048 signature verification is CPU-heavy (~1,000 verifications/s/core); ES256 (ECDSA) is substantially cheaper — document this in route-level auth-method guidance so operators choose ES256 where possible. JWKS cache lookups are O(1) (HashMap by kid), off the network entirely in the steady state (I10).

20.8 Edge Cases

A JWT with a valid signature but missing required claims (aud mismatch) — rejected, distinct error code from a bad signature for diagnosability. A JWKS endpoint that returns a well-formed but empty key set (no keys usable) — all tokens fail closed, not silently accepted. Clock skew beyond the tolerance window in either direction (nbf in the near future, exp just past) — both rejected per the same tolerance band, not asymmetric handling.

20.9 Failure Analysis

A JWKS endpoint outage during a key-rotation window is the dangerous case: the cache serves the last-known-good key set (I10's bounded grace period) rather than failing every request — blast radius is limited to tokens signed with a genuinely new key introduced during the outage, which fail until the cache recovers; detection is the refresh-age gauge; recovery is automatic once the JWKS endpoint returns, no manual intervention required within the grace window.

20.10 Operational Notes

Metrics: gwy_authn_result_total{outcome}, gwy_jwks_refresh_age_seconds, gwy_authz_decision_total{route,outcome}. tools/jwks-mock-server is the local-dev/CI fixture server; production JWKS endpoints are configured per auth-provider in the route/filter binding.

21. Phase 9 — Rate Limiting (Local Then Global)

21.1 Objectives

Enforce per-consumer/per-route quotas: local token-bucket admission first, then an opt-in global (cross-node) sliding-window-counter mode for accuracy-sensitive quotas (ADR-14/ADR-15).

21.2 Detailed Implementation Steps

  • gwy-filters::ratelimit, local mode: TokenBucket (§11) keyed by (consumer, route) in a per-worker sharded map (P7); admit/reject per the equation in §8.6; atomics only on the hot path, no lock (Herlihy & Shavit, applied here per §5).
  • Response headers on every decision: RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset; on rejection, additionally Retry-After (RFC 6585 429, applied here).
  • Global mode: a shared external store (e.g., a Redis-shaped backend) implementing the sliding- window-counter equation from §8.6 via an atomic check-and-increment round trip; opt-in per route because it adds a network hop to the default path (ADR-15).
  • Fail-open/fail-closed for the global store's unavailability is an explicit per-route config (P1) — never a hardcoded default.
  • Cost-aware limiting: a request may declare a cost > 1 (heavier endpoints debit more from the same bucket) — the bucket's capacity/refill math is unchanged, only the debited amount varies.
  • Deferred: count-min-sketch-based heavy-hitter detection (Cormode & Muthukrishnan 2005, §5) for adaptively tightening quotas on emergent abusive keys without per-key state — PhaseDeferred("§21 Phase 9 — Rate Limiting (Local Then Global)"), registered in the Deferred Features Register.

21.3 Deliverable

A consumer configured at 100 req/min is admitted up to the burst capacity, then receives 429 with Retry-After until the window recovers; switching the same route to global mode enforces the same limit accurately across a 3-node test fleet (no per-node drift).

21.4 Acceptance Criteria

  • conformance/ratelimit/admitted_never_exceeds_bound.yaml: property test, admitted count over N=100,000 trials never exceeds capacity + refill for the elapsed window (I8), 0 violations.
  • Local-mode decision latency ≤ 0.5 µs (§4/§30 budget line item), global-mode decision latency ≤ 2 ms including the network round trip (benchmarks/phase9_ratelimit.toml).
  • Cross-node drift under global mode ≤ 1% of configured limit across a 3-node fleet benchmark, versus documented ~2× drift for local-only mode at the same fleet size (§31-class reasoning).

21.5 Conformance Fixtures

  • conformance/ratelimit/admitted_never_exceeds_bound.yaml — the I8 property fixture.
  • conformance/ratelimit/burst_then_recover.yaml — burst to capacity, 429 until window recovery, then admits again — timing asserted against the token-bucket equation (§8.6).
  • conformance/ratelimit/global_store_unavailable.yaml — malformed/failure case: the global store is unreachable; asserts the configured fail-open/fail-closed stance is honored exactly (P1).
  • conformance/ratelimit/replay_multi_tenant.yaml — regression: a multi-consumer traffic replay, asserting stable per-consumer admission decisions across builds.

21.6 Pitfalls

  • Rate-limiter bypass via header spoofing: manifestation — a client claims a different consumer identity to reset its own quota; root cause — the rate-limit key derives from a client-controlled header rather than the authenticated principal; debug — a fixture asserting the key never derives from unauthenticated input; recovery — key by principal.sub (post-authn, §20) or a trusted proxy-injected identity, never a raw client header (§24 T7).
  • Cache stampede on a hot key: manifestation — many concurrent requests for the same extremely popular consumer/route key all miss simultaneously and hammer the global store; root cause — no request coalescing on a cold key; debug — global-store request-rate spike correlated to one key; recovery — a short-lived lease/single-flight pattern per key (Nishtala et al. 2013, applied here per §5) so only one request populates a cold counter while others wait briefly.
  • Local-node drift misunderstood as a bug: manifestation — operators report "the rate limit doesn't actually limit" because a consumer gets N× the configured rate across an N-node fleet; root cause — local-only counting is fleet-size-relative by design (ADR-15); recovery — this is documented behavior, not a defect; the fix is switching that route to global mode, not patching local mode.

21.7 Performance Concerns

Local-mode admission is a single atomic CAS loop (§8.6 equation), no allocation, no lock — the cheapest filter in the chain by design. Global mode's network round trip is the dominant cost; route-level opt-in (ADR-15) keeps it off the default hot-path budget in §4.

21.8 Edge Cases

A consumer with no configured plan (falls back to a documented default limit, never unlimited by omission). A rate-limit key collision across two distinct consumers (must not happen if keys derive from a unique principal.sub; a fixture asserts key uniqueness given distinct principals). A request whose cost exceeds the bucket's entire capacity (rejected immediately, never partially admitted — cost-aware limiting is all-or-nothing per request).

21.9 Failure Analysis

Global-store unavailability's blast radius depends entirely on the configured fail-open/fail- closed stance (P1) — fail-open risks over-admission during the outage window (bounded, since local per-node limits can act as a coarse backstop if configured); fail-closed risks blocking legitimate traffic. Detection: global-store health metric. Recovery: automatic once the store returns; no manual quota reset needed since counters are external, not gateway-local state.

21.10 Operational Notes

Metrics: gwy_ratelimit_admitted_total{route}, gwy_ratelimit_rejected_total{route}, gwy_ratelimit_global_store_latency_us, gwy_ratelimit_global_store_unavailable_total. Response headers (RateLimit-*) give consumers direct visibility into their own quota state, reducing "why am I getting 429s" support load (§21.6-class operational reasoning).

22. Phase 10 — Response Caching + Hot-Reloadable Config Plane

22.1 Objectives

Add RFC 9111-conformant response caching and replace the Phase 0 static-config load with the real hot-reloadable config plane: validated, versioned, atomically swapped (P2/P13, I4/I12).

22.2 Detailed Implementation Steps

  • gwy-cache: CacheKey derivation and freshness/validation exactly per §8.7's equations; per-worker segmented-LRU store (ADR-20/ADR-21); conditional-request revalidation on stale hits (If-None-Match/If-Modified-Since).
  • Cache-stampede mitigation: a single-flight lease per cold CacheKey so concurrent misses for the same key don't all forward to origin simultaneously (Nishtala et al. 2013, applied here — same technique introduced conceptually in §21.6, now implemented for the response cache).
  • gwy-config::schema+validate: schema validation (structural) then referential validation (route→cluster existence, filter-name existence) — both must pass before a candidate ConfigSnapshot is even constructed (P13).
  • gwy-config::watch: file-watch and/or control-plane push both feed the same validate-then-swap pipeline (ADR-22) — a versioned full snapshot is the unit of transport, not incremental field diffs, keeping the reload protocol simple at this fleet scale (contrast Envoy's incremental xDS, §5 Reference Implementations #1).
  • Atomic publish: ArcSwap<ConfigSnapshot> swap (I4); the old snapshot is dropped only once its last in-flight request completes (refcounted Arc), guaranteeing zero dropped connections across a reload (§4's reload-time target).
  • On a validation failure, the candidate snapshot is discarded and the running snapshot is untouched — logged as a rejected-apply event, never silently ignored (P13, I12).

22.3 Deliverable

A GET route with Cache-Control: max-age=60 serves from cache on the second identical request within the freshness window; editing gateway.yaml and sending SIGHUP (or a control-plane push) applies a new route within the §4 reload-time target with zero connection drops.

22.4 Acceptance Criteria

  • Cache hit-ratio ≥ 70% on a cacheable-GET-heavy synthetic workload (§4), measured by benchmarks/phase10_cache_hit_ratio.toml.
  • Config reload of a 50,000-route table completes in ≤ 500 ms with 0 dropped connections (conformance/config/reload_zero_drop.yaml, §4).
  • conformance/config/reject_bad_referential.yaml: a route referencing a nonexistent cluster is rejected at validation, the prior snapshot remains active, 0 requests affected.

22.5 Conformance Fixtures

  • conformance/cache/freshness_and_validation.yaml — the RFC 9111 decision-tree worked cases from §8.7, including a Vary-header scenario.
  • conformance/cache/stampede_single_flight.yaml — 1,000 concurrent requests for one cold key; asserts exactly one origin fetch.
  • conformance/config/reload_zero_drop.yaml — the atomic-swap zero-drop fixture (I4).
  • conformance/config/reject_bad_referential.yaml — malformed config: dangling cluster reference, rejected pre-apply (P13).
  • conformance/config/replay_version_monotonicity.yaml — regression: a sequence of config versions applied out of order; asserts only monotonically increasing versions are ever applied (I12).

22.6 Pitfalls

  • Cache stampede on a hot key: manifestation — a popular cached response expiring causes a burst of simultaneous origin fetches; root cause — no request coalescing on cache-miss; debug — origin request-rate spike synchronized to a TTL boundary; recovery — the single-flight lease from 22.2 (Nishtala et al. 2013).
  • Config reload that validates but is semantically wrong: manifestation — a route change passes schema and referential validation but points traffic at the wrong cluster (a typo'd but existing cluster ID); root cause — validation checks structure and referential integrity, not intent; debug — a config diff review step and canary-apply-to-one-node-first operational practice (§26); recovery — this class of error is caught by process (staged rollout, §27), not by the validator alone — document the limit of automated validation explicitly.
  • Caching authenticated responses without a consumer-scoped key: manifestation — consumer A's cached response is served to consumer B; root cause — the cache key omits the principal for a route where the response varies per caller; debug — a fixture with two distinct principals hitting the same URL; recovery — routes serving per-principal content must include the principal in CacheKey derivation or disable caching entirely (documented per-route opt-in, never a default-on assumption for authenticated routes).

22.7 Performance Concerns

Cache lookups are per-worker, lock-free reads against the segmented-LRU (ADR-20/21) — no cross- worker cache coherence traffic, at the cost of lower effective cache size per unique entry versus a shared cache (documented tradeoff, ADR-20). Config-snapshot construction happens off the hot path entirely; the only hot-path cost of a reload is the one-time ArcSwap pointer read cost per subsequent request (negligible, same cost as reading any other atomic pointer).

22.8 Edge Cases

A response with Vary: * (never cacheable, per RFC 9111 — the cache must recognize this explicitly, not attempt a best-effort match). A config reload arriving while a prior reload's old snapshot is still being drained (multiple snapshot generations alive simultaneously, each refcounted independently — must not leak or double-free). A cache entry whose validators (ETag) are present but the origin's revalidation response omits them (falls back to full re-fetch, not a partial-trust update).

22.9 Failure Analysis

A stampede's blast radius is bounded to the origin cluster's capacity for the fetch burst duration — the single-flight lease caps concurrent origin fetches per key to 1, regardless of how many gateway-side requests are waiting on it; detection is the origin-request-rate metric; recovery is automatic once the lease-holder's fetch completes and populates the cache for all waiters.

22.10 Operational Notes

Metrics: gwy_cache_hit_total{route}, gwy_cache_miss_total{route}, gwy_cache_stampede_ coalesced_total, gwy_config_version, gwy_config_apply_total{result}, gwy_config_reload_duration_ms. The bad-config-rollback runbook (§26, docs/runbooks/) documents the manual-rollback procedure for the semantically-wrong-but-valid config class from 22.6.

23. Phase 11 — Conformance Suite + Perf Hardening

23.1 Objectives

Consolidate every phase's fixtures into one runnable conformance suite, close remaining protocol-conformance gaps, and drive the system to the §4/§30 performance targets under sustained load.

23.2 Detailed Implementation Steps

  • conformance/ becomes a single CI-runnable suite aggregating every fixture named in §12.5 through §22.5, plus new h2spec-style and differential-vs-NGINX/Envoy corpus runs (§28).
  • Perf-regression gate: benchmarks/ runs against every §4-quantified target on each release candidate; a regression beyond a configured tolerance (e.g., 10% on p99 added latency) fails CI (ADR-30).
  • Fault injection harness (conformance/fault_injection/): upstream reset mid-body, slow reader, TLS renegotiation attempt — exercising the failure paths of §14/§16/§17/§19 under adversarial timing.
  • Soak test: 72-hour sustained-load run at the §4 mixed-workload throughput target, asserting no memory growth beyond the §4 ceiling (a leak detector, not just a functional check).
  • Coordinated-omission-corrected load generation (Dean & Barroso 2013-adjacent tail-latency discipline, applied here per §5) for every latency benchmark, so a slow period doesn't under-count the requests it delayed.

23.3 Deliverable

A single make conformance target runs the full aggregated fixture suite plus the differential corpus and reports pass/fail per fixture; a single make perf target runs the full benchmark suite and reports pass/fail per §4/§30 target with the gate's tolerance applied.

23.4 Acceptance Criteria

  • 100% pass rate across the aggregated conformance suite (all fixtures from §12.5–§22.5 plus this phase's additions), 0 skipped fixtures.
  • 72-hour soak: memory growth ≤ 5% of the §4 ceiling over the run, 0 crashes, 0 panics escaping the I14 containment boundary.
  • Differential corpus (conformance/differential/): ≥ 95% byte-identical response agreement with NGINX and Envoy on a shared 10,000-request corpus for the routing/forwarding behaviors common to all three (documented, expected divergence points listed explicitly, e.g. gateway- specific headers).

23.5 Conformance Fixtures

  • conformance/all/aggregate_manifest.yaml — the full fixture manifest aggregating every named fixture from Phases 0–10.
  • conformance/fault_injection/upstream_reset_mid_body.yaml, slow_reader.yaml, tls_renegotiation.yaml — the three named fault-injection cases from 23.2.
  • conformance/differential/nginx_envoy_corpus.yaml — the 10,000-request differential corpus.
  • conformance/soak/72h_leak_detector.yaml — the soak-test harness configuration and its memory- growth assertion.

23.6 Pitfalls

  • Metric-label cardinality explosion taking down the metrics pipeline: manifestation — the metrics backend itself falls over or drops data under load; root cause — a label (accidentally reintroduced raw route_path or consumer_id) breaks the cardinality budget from P9/§24 T6; debug — a cardinality-budget CI check scanning every metric emission site for disallowed label sources; recovery — the check is added in this phase as a permanent CI gate, not a one-time audit.
  • Perf gate false negatives from coordinated omission: manifestation — a benchmark reports "passing" latency numbers during a period the load generator itself was stalled, hiding a real regression; root cause — a naive closed-loop load generator; debug — compare against a known- regressed build with coordinated-omission correction on vs. off; recovery — every benchmark in benchmarks/ uses the corrected methodology from 23.2, enforced by a lint on new benchmark files.
  • Differential-corpus false failures from legitimately different behavior: manifestation — the NGINX/Envoy differential run reports failures for cases where this gateway's documented behavior intentionally differs (e.g., stricter smuggling rejection); root cause — the corpus doesn't yet distinguish "bug" from "documented divergence"; recovery — the differential fixture's manifest explicitly whitelists documented divergences with a citation back to the ADR or invariant that mandates the difference (e.g., ADR-07's strict-parsing rationale).

23.7 Performance Concerns

This phase is where the §30 profiling methodology (allocation, lock contention, cache locality, syscall/copy overhead, tail-latency analysis) is actually run against the assembled system for the first time end-to-end — earlier phases benchmark in isolation; this phase validates the composed system meets the §4 targets as a whole, not just per-component.

23.8 Edge Cases

A fault-injection case that overlaps two failure paths simultaneously (e.g., a slow reader on a connection whose cluster is also mid-outlier-ejection) — the suite must assert both mechanisms' invariants hold concurrently (I1/I3 alongside I11), not just in isolation. A soak-test run that crosses a config-reload boundary mid-run (validates §22's zero-drop guarantee under sustained load, not just a synthetic single reload).

23.9 Failure Analysis

A conformance-suite regression's blast radius is contained to CI — this phase's entire purpose is ensuring failures are caught before release, not in production; a failure here blocks the release pipeline (ADR-30's perf-regression gate) rather than reaching the fleet. Forensics for a soak-test failure include the leak detector's allocation-site sampling, correlated against the specific fixture or traffic pattern active when growth began.

23.10 Operational Notes

Metrics: this phase does not add new production metrics; it validates that every metric named in Phases 0–10 (§12.10 through §22.10) is actually emitted and cardinality-bounded under the aggregated suite. make conformance and make perf are the two release-gating entrypoints referenced by .github/workflows/release.yml (ADR-32).

Metrics (cardinality budget: fixed label set per P9 — route_id, cluster_id, status_class, filter, phase, result; consumer identity is hashed to a bounded bucket count, never emitted raw). Tracing — one span per filter-chain phase (Rewrite/Access/Transform/HeaderFilter/BodyFilter, §8.3) plus one span for the upstream forward, all children of one root span per request; trace-context propagation follows the W3C-style header passthrough locked in ADR-26.

Structured access-log fields — AccessLogRecord (§11): timestamp, route_id, cluster_id, status, gateway-added latency, upstream latency, hashed consumer bucket, trace ID. Emitted async, off the hot path (P9, Welsh 2001).

Alerting philosophy — alert on invariant-adjacent signals (I1 deadline-exceeded rate, I6 retry-budget-exhaustion rate, I11 ejected-endpoint-count crossing the panic threshold, I12 config-version skew across the fleet), not on raw error counts alone — an invariant-scoped alert tells the on-call which mechanism is under strain.

SLOs — availability: 99.95% monthly for the gateway tier itself (§4); added latency: p99 ≤ 150 µs gateway-only (§4). Both exclude upstream-caused unavailability/latency, tracked as a separate SLO the gateway's health-check/outlier telemetry directly informs.

Incident response — the four named runbooks under docs/runbooks/ are the primary on-call artifacts:

  • bad-config-rollback.md — rollback procedure for FM-9-class semantically-wrong-but-valid config, referenced in §22.6.
  • upstream-brownout.md — procedure for FM-7-class correlated endpoint degradation, referenced in §18.9/§18.10.
  • retry-storm-containment.md — procedure for FM-8-class retry amplification, referenced in §19.9/§19.10.
  • cert-expiry.md — procedure for TLS certificate rotation/expiry, referenced in §16.10.

Backup/restore — the config plane's source of truth (file repository or control-plane store) is backed up externally to the gateway fleet itself; a gateway node holds no durable state beyond its in-memory snapshot, so "restore" for a node is simply a fresh start plus a config-plane re-sync — the node itself is disposable by design.

Deployment topology — N nodes behind an L4 VIP/anycast (edge fleet) or as a Kubernetes ingress DaemonSet/Deployment (per-cluster ingress), both sharing one binary and one config-plane contract (§1).

Canary / rolling-upgrade / rollback / migration — a new binary version is deployed to a small node subset first (canary), validated against the differential-corpus and perf-gate criteria (§23) live, then rolled fleet-wide; rollback is redeploying the prior signed artifact (§29); connection draining on shutdown holds SIGTERM handling until in-flight requests complete or a grace-period deadline elapses, guaranteeing the same zero-drop property the config-reload path provides (I4-adjacent discipline applied to process lifecycle, not just config swap).

27. Compatibility & Versioning

Config schema versioning — every GatewayConfig document declares a schema version; the config plane validates against the schema version it claims before any referential check (P13); a document declaring an unknown/future schema version is rejected, never best-effort-parsed.

Validation-before-apply — structural, non-negotiable (§22.2/P13): no config document is ever partially applied; validation failure leaves the running snapshot untouched (I4).

Route semantics stability — the precedence rules of §8.2 are a stability contract: a future version may add new match dimensions but must never silently reorder existing precedence ranks without a major-version bump (SemVer, below).

Filter ABI / extension compatibility — v1 filters are compiled-in Rust trait objects (ADR-13); the Filter trait (§11) is the ABI boundary for this build's lifetime; a breaking change to the trait signature is a major-version event. WASM filter ABI versioning is deferred along with the runtime itself (Deferred Features Register).

Protocol negotiation and downgrade behavior — ALPN negotiation (§16.2) always prefers the highest mutually supported protocol; a client claiming a protocol it cannot actually speak fails the handshake cleanly rather than silently downgrading further than negotiated.

Admin surface API stability — the admin/stats endpoints (§11 gwy-admin) follow the same SemVer discipline as the rest of the system; a breaking admin API change is a major version.

Migration & deprecation — a deprecated config field or route-match dimension is accepted with a validation-time warning for one minor-version cycle before removal in the next major version; the deprecation is logged and surfaced in /config/dump.

SemVer — MAJOR: breaking change to config schema, Filter trait ABI, or route precedence semantics. MINOR: new optional config fields, new filters, new metrics. PATCH: bug fixes with no observable behavior change to a correctly-configured deployment.

Rolling-upgrade guarantees — zero dropped connections across a version upgrade, guaranteed by the same connection-draining discipline as §26's canary/rollback procedure; a node being upgraded stops accepting new connections, drains in-flight ones against their existing deadlines (I1), and only then restarts on the new binary.

28. Testing & Verification Strategy

Unit — per-crate (§10) unit tests for parsers, matchers, state machines in isolation.

Integration — gwy-bin-level tests wiring multiple crates (e.g., router + filter chain + upstream forwarding) against the fixtures named in each phase's N.5.

Property tests —

  • route_precedence_totality (§13.4): every overlapping-route pair resolves to exactly one winner, ties I4-consistent deterministic — 100,000 generated cases (§13.4).
  • retry_budget_never_exceeded (§19.4): retry attempts never exceed the configured budget fraction across 100,000 simulated requests, tied to I6.
  • deadline_monotonicity (§19.4): a retried request's total elapsed time never exceeds its original Deadline across 50,000 generated scenarios, tied to I1/P3.
  • ratelimit_admitted_never_exceeds_bound (§21.4): tied to I8.

Differential testing — against NGINX and Envoy on a shared 10,000-request corpus (conformance/differential/nginx_envoy_corpus.yaml, §23.4/§23.5), with documented, ADR-cited expected divergences (e.g., ADR-07's strict-smuggling-rejection behavior that NGINX/Envoy may handle more permissively).

Fuzzing — cargo-fuzz/libFuzzer (ADR-29) on three primary targets: the H1 parser (fuzz/h1_parser), the H2 frame decoder (fuzz/h2_frames), and the config parser (fuzz/config_parser) — these are the surfaces named explicitly as fuzz targets because they parse untrusted/semi-trusted input (T1, T9).

Chaos — fault injection into a running conformance/staging cluster: kill endpoints mid-benchmark (§18.4's kill_one_endpoint.yaml), inject network partition to the global rate-limit store (§21.5's global_store_unavailable.yaml).

Deterministic replay — the seeded-PRNG simulator (§7 methodology) replays byte-for-byte any invariant violation found in fuzzing or chaos runs, making every discovered bug reproducible.

Soak — 72-hour sustained-load run (§23.2/§23.4), memory-growth-bounded leak detection.

Fault injection — upstream reset mid-body (§14.5/§23.5), TLS renegotiation attempt (§23.5), slow reader (§23.5) — each tied to the invariant it threatens (I3, T2, I1 respectively).

Conformance — h2spec-style suite (§17.4) for HTTP/2 frame-format/flow-control correctness.

Performance-regression gating — every §4/§30-quantified target is checked in CI on each release candidate (ADR-30); a regression beyond the configured tolerance fails the build, enforced by the make perf entrypoint (§23.10).

29. Build & Release Engineering

Reproducible builds — pinned rust-toolchain.toml, cargo vendor-captured dependency sources, deterministic build flags (ADR-32); two builds from the same commit produce byte-identical artifacts, verified in CI.

Artifact signing — release binaries and container images are signed (e.g., via cosign-style detached signatures); signature verification is a precondition for deployment tooling to accept an artifact.

SBOM — a software bill of materials generated per release (scripts/gen-sbom.sh) enumerating every dependency and its version/license, feeding both the dependency-audit gate (T10) and the legal/ third-party license manifest (§10).

Release channels — stable (fleet-wide default), canary (small-subset early rollout, §26), nightly (CI-built, not deployment-eligible without manual promotion).

CI/CD topology — .github/workflows/ci.yml (build+test matrix, ADR-30), fuzz.yml (scheduled corpus runs, ADR-29), release.yml (signed artifact + SBOM publish, gated by make conformance and make perf, §23.10).

Version stamping — every binary embeds its build commit hash, build timestamp, and semantic version (§27), surfaced via the admin /healthz endpoint and the startup log.

Provenance / attestation — release artifacts carry build-provenance attestations (build system identity, source commit, dependency lockfile hash) verifiable independently of the signing key, defending against a compromised-but-not-detected build pipeline.

Dependency auditing — cargo-deny (ADR-03) runs on every CI build; a scheduled deeper audit (vulnerability database cross-reference) runs weekly against the current lockfile, feeding T10's mitigation.

31. Scalability Analysis

Constant vs. grows — route-match cost is O(request size), constant with respect to route count (ADR-12, the trie+regex-DFA structure is precisely what achieves this — a flat linear scan would be O(route count) and is explicitly rejected for that reason). Per-connection memory is constant per connection (§4); total memory grows linearly with concurrent connection count plus a fixed cache/config-snapshot overhead. Filter-chain overhead grows linearly with the number of filters bound to a route (each filter call is O(1) marginal cost, P7-consistent).

Named bottlenecks, in order — (1) TLS full-handshake CPU cost at very high new-connection rates (mitigated by session resumption, §16.7); (2) global rate-limit store round trip when a route opts into global mode (ADR-15's explicit tradeoff); (3) JWKS/JWT signature verification CPU cost under RSA (mitigated by preferring ES256, §20.7); (4) upstream connection-pool exhaustion per cluster under a slow-upstream scenario (mitigated by per-cluster caps and the circuit breaker, §19); (5) cross-core coordination cost for any global (fleet-wide) state — chiefly the global rate-limit store itself, since thread-per-core (P7) deliberately avoids cross-core coordination for everything else.

Horizontal scaling — add nodes behind the L4 VIP/anycast (§26); each node is independent (disposable, per §26's backup/restore reasoning) and requires no peer coordination for routing, forwarding, local rate limiting, or caching — only the global rate-limit mode and the control-plane config source introduce cross-node dependencies.

Vertical scaling — add cores per node; thread-per-core sharding (P7/ADR-05) scales near-linearly with core count for everything except global-rate-limit-mode routes (which share one external-store round-trip budget regardless of local core count) and the config-plane connection (one control-plane stream per node, not per core).

Thread-per-core sharding consequences for global rate limiting — because P7 shards connection pools, cache, and local rate-limit counters per core with no cross-core coordination, a global rate limit cannot be enforced purely locally: it requires the explicit opt-in network hop to a shared store (ADR-15) precisely because the sharding model that makes everything else fast structurally cannot see across cores, let alone across nodes, without that hop.

Coordination overhead — bounded to exactly two cross-node dependencies by design: the control-plane config stream (§22, amortized, not per-request) and the optional global rate-limit store (§21, per-request only for routes that opt in). No other subsystem requires cross-node coordination — this is the direct consequence of P7 and the deliberately node-local defaults in ADR-15/ADR-20.

Practical ceiling and levers beyond it — the practical per-node ceiling is the §4 concurrent- connection/memory ceiling (500,000 connections, ≤8 GB); beyond that, the lever is horizontal scaling (add nodes), not vertical (a single node's FD/memory ceiling is a hard OS-level limit before any CPU limit is reached at realistic core counts). Beyond a few hundred nodes, the global rate-limit store itself becomes the next bottleneck (its own read/write throughput ceiling), at which point sharding the store by consumer-ID range (a deferred extension, not in this build's scope) is the next lever.

32. Mental Models & First Principles

MM1. A gateway is a queueing system wearing a routing table. Every feature added is another place a request can wait. Predicts: any new filter/stage that lacks a deadline-aware wait silently becomes an unbounded queue under load. Bug class without it: latency tails from a "quick" feature that quietly blocks past the request's actual budget. Resolving: §19 (deadlines), §3 (Architectural Overview).

MM2. Every retry is a decision to spend someone else's capacity. A retry is never free; it is a claim on the upstream's remaining headroom. Predicts: retries must be budgeted, not unlimited. Bug class without it: retry storms turning a partial outage total. Resolving: §19 Phase 7, §34.

MM3. Config is a value, not a mutation target. Treat a running snapshot like an immutable data structure and "reload" like structural sharing (an atomic pointer swap), not like editing a live record. Predicts: partial-apply bugs disappear once you swap pointers instead of fields. Bug class without it: half-applied config visible to in-flight requests. Resolving: §22 Phase 10, I4.

MM4. Health is a state machine with hysteresis, not a boolean. A single failed probe is evidence, not a verdict. Predicts: single-sample health checks flap under normal jitter. Bug class without it: ejection storms that eject a whole cluster from one correlated blip. Resolving: §18 Phase 6, I11.

MM5. A filter chain is function composition with a short-circuit escape hatch. Ordering and short-circuit semantics are the entire contract a filter author needs; nothing else about a filter's internals matters to the chain. Predicts: ordering bugs manifest as "sometimes" failures that are actually fully deterministic once priority is understood. Bug class without it: assuming filter behavior depends on something other than phase+priority+short-circuit. Resolving: §15 Phase 3, §8.3.

MM6. Cache freshness is a promise about time, not a fact about content. A byte-identical cached response can still be wrong to serve if it is stale. Predicts: correctness bugs get mistaken for performance bugs (serving fast, serving wrong). Bug class without it: treating Cache-Control as advisory rather than load-bearing. Resolving: §8.7, §22 Phase 10.

MM7. Rate limiting is admission control running against a clock, not a ledger of who's naughty. The data structure is a small, fast counter, not a growing per-request record. Predicts: scaling the wrong thing (a database write per request) for what is fundamentally a streaming decision. Bug class without it: a rate limiter that itself becomes the bottleneck it was meant to protect against. Resolving: §21 Phase 9, §8.6.

MM8. Thread-per-core buys speed by giving up a free global view. Anything that genuinely needs to see across cores or nodes (a global rate limit, a fleet-wide config version) needs an explicit, visible hop — it is never accidentally free. Predicts: bugs where local state is mistaken for global state. Bug class without it: "the rate limit doesn't actually limit" reports from operators who don't realize local mode is fleet-size-relative by design. Resolving: §31 Scalability Analysis, ADR-15.

Envoy made a fundamentally different call by building for a universal data plane driven by a rich, incremental xDS control-plane protocol from day one — the right call for a heterogeneous mesh with many independent config producers (service teams, mesh control plane, gateway configs all converging on one data plane), at the cost of xDS's own protocol complexity. This design rejects that in favor of a simpler full-snapshot push (ADR-22) because a single-product API gateway's config sources are far fewer.

NGINX made concurrency and reload the same lever: one process per core, and a config reload forks entirely new worker processes rather than mutating in-process state. This wins for deployments that value process-level isolation between config generations (an old worker finishes its in-flight requests on the old config, guaranteed by OS process boundaries, not software discipline) — at the cost of a heavier reload than an atomic pointer swap.

HAProxy made rate-limiting/session-affinity ("stick-tables") a first-class, highly tunable built-in rather than a filter plugin — the right call for its operator base, who often need sophisticated per-key counters without writing code, at the cost of the stick-table config language's own operational opacity (a pitfall this design deliberately documents against in §21.6/§5 Reference Implementations #3).

Cloudflare Pingora made the call to not build a plugin/extensibility story at all in its open-sourced core, instead exposing a small set of Rust trait hooks that the operator's own binary implements directly — the right call when the operator (Cloudflare itself) is also the only extension author, at the cost of no third-party filter ecosystem. This design's compiled-in filter model (ADR-13) is closer to Pingora's approach than to Envoy's plugin registry, for the same reason: v1 has one extension author (the platform team), not many.

34. Back-of-Envelope Capacity Model

1. Memory ceiling from concurrent connections. memory = connections × per_conn_bytes + cache_bytes + snapshot_bytes. From §4: 500,000 connections × 8 KB/conn amortized = 4,000,000 KB ≈ 3.81 GB. Plus 2 GB cache (ADR-20) plus ~200 MB config-snapshot overhead (derivation #8 below) ≈ 6.0 GB total, within the §4 ≤8 GB ceiling with ~25% headroom.

2. FD budget. fds = connections × 2 + pool_reserve. 500,000 × 2 = 1,000,000, plus a pool reserve of 128 conns/cluster/worker × ~20 clusters × 8 workers ≈ 20,480 → ≈1,020,480 FDs, consistent with the §4 row (1,048,576, the common ulimit power-of-two ceiling).

3. Requests/second from per-request CPU cost. rps_per_core = 1,000,000 µs ÷ µs_per_request. Using the §30 mixed-workload breakdown (~29.5 µs/request): 1,000,000 ÷ 29.5 ≈ 33,898 req/s theoretical per core. The §4 target of 25,000 req/s/core reserves ~26% headroom below theoretical peak for scheduling jitter and non-steady-state traffic shape — a deliberately conservative gate, not the ceiling itself.

4. TLS handshake capacity. handshakes_per_sec = 1,000,000 µs ÷ µs_per_handshake. Full ECDSA handshake ≈ 250 µs/core → 1,000,000 ÷ 250 = 4,000/s/core (§4 row). Resumed (TLS 1.3 PSK) ≈ 25 µs/core → 1,000,000 ÷ 25 = 40,000/s/core — a 10× reduction, matching the §16.7 claim exactly.

5. Cache memory and hit ratio needed for an origin-load target. Node throughput 180,000 req/s (§4); origin capacity assumed 50,000 req/s sustainable. Required hit ratio: 1 − (origin_capacity ÷ node_throughput) = 1 − (50,000 ÷ 180,000) ≈ 72.2%, consistent with the §4/§30 target of ≥70% (a small margin below the strict-necessity number, since real workloads are not uniformly cacheable).

6. Upstream pool sizing via Little's Law. concurrency = arrival_rate × service_time. For a cluster receiving 10,000 req/s with average service time (upstream RTT + processing) of 3 ms (0.003 s): concurrency = 10,000 × 0.003 = 30 concurrent connections needed. The default pool size of 128/cluster/worker (§4) gives ≈4.3× headroom for burst absorption above the steady-state requirement.

7. Retry-budget amplification under a naive fixed-retry policy. A policy retrying up to 3 times on failure, against a cluster with a 50% per-attempt failure rate, has expected attempts per request = Σ_{k=0}^{3} p^k = 1 + 0.5 + 0.25 + 0.125 = 1.875 — i.e., a naive 3-retry policy generates 87.5% more load on an already-half-failing upstream, directly worsening the failure rate that triggered the retries in the first place. This is the precise mechanism P4/I6's RetryBudget exists to cap.

8. Route-table memory. route_bytes = route_count × bytes_per_route. At ~2 KB/route (compiled trie/regex entry + captures + filter-binding pointers), 100,000 routes ≈ 200 MB, the config-snapshot overhead used in derivation #1.

9. Config-reload time from route count. At ~5 µs/route validation cost, 50,000 routes ≈ 250 ms validation + snapshot-construction overhead ≈ 500 ms total, matching the §4/M9 target exactly.

36. Alternative Architectures (Roads Not Taken)

A1 — Sidecar service-mesh data plane with a central control plane.

 ┌────────┐      ┌────────┐      ┌────────┐
 │Service A│◀────▶│Sidecar A│      │Sidecar B│◀────▶│Service B│
 └────────┘      └───┬────┘      └───┬────┘
                     │ mTLS east-west  │
                     └────────┬─────────┘
                              ▼
                    ┌───────────────────┐
                    │ Central Control    │
                    │ Plane (xDS)         │
                    └───────────────────┘

Winning regime: many services, ubiquitous east-west traffic, uniform per-hop policy needed everywhere. Real embodying system: Istio/Envoy sidecar mesh. Rejected here because this build is a single north-south ingress hop by definition (§1 non-goals) — injecting a sidecar per backend service is a different product (the sibling Service-Mesh blueprint, project 164), not a variant of this one.

A2 — eBPF/kernel-bypass L4-plus-minimal-L7 design.

 client ──▶ [ XDP/eBPF L4 classify+LB ] ──▶ [ minimal L7 header peek ] ──▶ backend
              (kernel space, no userspace hop for most packets)

Winning regime: extreme packet-rate L4/L4.5 load balancing where per-request API-contract logic (auth, quota, transform) is unnecessary or handled elsewhere. Real embodying system: Cilium's eBPF-based load balancing, Katran (Meta). Rejected here because this build's load-bearing concern is precisely the API-contract surface (§1) — auth, quota, transform, config plane — which requires full userspace HTTP semantics per request, defeating the purpose of a kernel-bypass design.

A3 — Serverless/edge-function gateway, filters as per-request WASM.

 client ──▶ [ edge PoP ] ──▶ [ WASM filter invoked per request, cold-start or warm pool ] ──▶ origin

Winning regime: many independent third-party filter authors, deployment velocity valued over raw per-request latency, geographically distributed edge PoPs. Real embodying system: Cloudflare Workers, Fastly Compute. Rejected for v1 because compiled-in filters (ADR-13) give lower and more predictable per-request latency without WASM sandbox/ABI overhead — the exact tradeoff captured in ADR-13's "when WASM wins" column; this remains the deferred extension point (§15, Deferred Features Register), not a rejection of the idea outright.

A4 — Library-embedded gateway compiled into each service.

 ┌─────────────────────────────┐
 │ Service process               │
 │  ┌────────────────────────┐  │
 │  │ gwy-* crates, linked in  │  │
 │  └────────────────────────┘  │
 └─────────────────────────────┘
        (no separate network hop)

Winning regime: latency-critical internal RPC where even one extra network hop is unacceptable, and every caller is trusted/known at compile time. Real embodying system: tower-based in-process middleware stacks (the same crate family Linkerd2-proxy is built from, §5/§33) used as a library rather than a standalone proxy. Rejected here because a shared, independently deployable gateway is precisely what lets API-producer teams change routing/auth/quota policy without redeploying every backend service (§1's deployment-model rationale) — the entire point of a gateway, not a library, is that policy changes are a config-plane event (§22), not a service redeploy.

38. Glossary

  • Access phase — the filter-chain phase where authn/authz/rate-limit filters run (§8.3).
  • ALPN — Application-Layer Protocol Negotiation, the TLS extension selecting h2 vs. http/1.1 at handshake time (§16).
  • AtomicSwap / ArcSwap — lock-free atomic pointer swap used to publish a new ConfigSnapshot (P2, I4).
  • Backpressure — explicit admission control (bounded queues, 503s) instead of unbounded queueing under overload (P6, ADR-34).
  • Budgeted retry — a retry attempt gated by a shared RetryBudget token bucket, never unlimited (P4, I6).
  • Bulkhead — isolating one dependency's failure from affecting others (Nygard), realized here via per-cluster connection pools and breakers.
  • Cache key — the hash of method/scheme/host/path/query/Vary-listed headers identifying a cacheable response (§8.7).
  • Cardinality budget — the fixed set of allowed metric label values, bounding metrics- pipeline memory (P9, §24 T6).
  • Circuit breaker — the Closed/Open/HalfOpen state machine that fails fast once a dependency is provably unhealthy (I7, §19).
  • Claim (JWT) — a field inside a JWT payload (exp, nbf, aud, iss) validated at authn time (§20).
  • Coordinated omission — a load-generator measurement artifact that under-counts requests delayed during a stall; corrected in this build's benchmarks (§23, §30).
  • Deadline — the monotonic-clock expiry every downstream wait is bounded by (P3, I1).
  • Config snapshot — the immutable, versioned bundle of routes/clusters/filters swapped atomically on reload (§11, §22).
  • Config version — the monotonically increasing identifier preventing a stale reload from overwriting newer state (I12).
  • Connection draining — holding a shutting-down process open until in-flight requests complete or a grace deadline elapses (§26).
  • Filter — a unit of behavior in the request/response lifecycle implementing the Filter trait (§8.3, §11).
  • Filter chain — the ordered, priority-driven sequence of filters a request passes through (§3, §15).
  • Flow-control window — the HTTP/2 mechanism bounding how much unacknowledged data may be in flight per stream/connection (§8.4, RFC 9113).
  • Hop-by-hop header — a header meaningful only for one transport hop (Connection, Transfer-Encoding), stripped before forwarding (P5, I5).
  • Hot reload — applying a new configuration without a process restart or dropped connections (§22).
  • HPACK — the HTTP/2 header-compression scheme (RFC 7541) with a bounded dynamic table (§17).
  • Idempotency-aware retry — a retry policy scoped to methods/semantics safe to repeat (P10).
  • JWKS — JSON Web Key Set, the published key material a JWT signature is verified against (§20).
  • Listener — a port-binding accepting connections, one per protocol/TLS configuration (§11).
  • Load balancer — the component selecting an upstream Endpoint per request (§11, §18).
  • Outlier ejection — removing a misbehaving endpoint from load-balancing consideration based on passive failure detection (§8.5, §18).
  • P2C (power-of-two-choices) — the load-balancing algorithm picking the less-loaded of two randomly sampled endpoints (Mitzenmacher 2001, ADR-16).
  • Panic boundary — the catch_unwind containment point preventing a filter panic from crashing a worker (I14).
  • Pooled connection — an upstream connection held for reuse, released only in a known-clean protocol state (I3, §11).
  • Principal — the identified caller attached to a request after successful authentication (§20).
  • Rate limit — admission control bounding request rate per key (consumer/route), local or global (§21).
  • Reset-storm guard — the HTTP/2 mitigation capping client-initiated stream resets per window (§17, CVE-2023-44487).
  • Retry budget — the shared token bucket capping total retry volume per cluster (I6, §34).
  • Route — a configured rule matching requests by host/path/method/header to a cluster action (§8.2, §11).
  • Route precedence — the deterministic ranking resolving overlapping route matches (§8.2).
  • RTO — Recovery Time Objective, the target time to restore service after a failure (§4).
  • Segmented LRU — a cache-eviction policy with protected/probationary segments resisting scan-induced eviction of hot entries (ADR-21).
  • SEDA — Staged Event-Driven Architecture (Welsh 2001), the backpressure/admission-control model applied at the accept queue (§12).
  • Short-circuit — a filter verdict (Reject/Respond) that stops the remaining chain from running (§8.3).
  • Sliding-window counter — a rate-limiting algorithm blending current/previous fixed windows to bound edge-doubling error (§8.6).
  • SLO — Service Level Objective, a quantified target (e.g., availability, latency) the system is operated against (§26).
  • Snapshot swap — see Config snapshot; the atomic publish mechanism (I4).
  • Stampede (cache) — many concurrent requests for one cold cache key all missing simultaneously and hammering the origin (§22, Nishtala et al. 2013).
  • Thread-per-core — a concurrency model assigning one OS thread (and its state) per CPU core, avoiding cross-core synchronization on the hot path (P7, ADR-05).
  • Token bucket — a rate-limiting/retry-budget primitive with a capacity and refill rate (§8.6, §11).
  • Trust boundary — a point where data crosses from one security domain to another (e.g., client to gateway, gateway to upstream) (§3).
  • Vary — the HTTP response header declaring which request headers affect cache-key derivation (§8.7, RFC 9111).
  • xDS — Envoy's family of discovery-service protocols for incremental config streaming, referenced as a rejected-alternative comparison point (§33, ADR-22).
  • Zero-copy — processing data via views/slices into existing buffers rather than copying, used where the data does not cross a trust boundary unmodified (P12, ADR-11).
