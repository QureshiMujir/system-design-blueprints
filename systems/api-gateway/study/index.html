Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does atomic config swap (I4, §22) matter more for correctness than for performance, and what specific bug does a per-field mutation reload introduce that a full swap structurally cannot? (§22, §7)
  2. Derive the retry-amplification factor for this build's default retry policy against a cluster at 50% failure, and explain why the RetryBudget (I6) caps it rather than the per-route RetryPolicy alone. (§19, §34)
  3. Why is the route matcher's cost independent of route count, and what specific config change (adding one regex route the wrong way) would silently regress that guarantee? (§13, ADR-12, §31)
  4. Walk the health/outlier state machine (§8.5, I11) and explain why a correlated failure across many endpoints requires a different mitigation (the panic threshold, §18.6) than the per-endpoint hysteresis alone provides.
  5. Why does thread-per-core sharding (P7, ADR-05) make global rate limiting structurally harder than local rate limiting, and what is the minimum architectural change required to support it? (§21, §31, ADR-15)
  6. Explain the difference between the token-bucket and sliding-window-counter error bounds (§8.6) and identify a traffic shape where each would visibly misbehave relative to the other, tying the answer back to the local-vs-global mode split of §21.
  7. Why must a Deadline be set once at ingress and never re-originated (P3), and what specific failure mode does a filter that "grants more time" to a slow dependency reintroduce? (§19, §12)
  8. Trace the exact sequence of trust-boundary crossings a single request makes from accept to response and identify which crossing is the only one where a raw client-supplied byte range is ever forwarded without transformation. (§3, §8.1)
  9. Why does this design forward-declare the Filter::on_request async-suspend variant (§15) in Phase 3, before any filter actually needs it? What would retrofitting it cost later? (§15.6, §20)
  10. Explain why JWKS caching (I10, §20) trades security (a wider key-rotation window) for availability (no per-request network hop), and identify the configuration lever that shrinks that tradeoff without eliminating the cache entirely. (§20, §24)
  11. Why is cache-key derivation (§8.7) required to include every Vary-listed header, and what specific incident class (§24 T4) results from omitting one?
  12. Compare this design's config-transport choice (versioned full-snapshot push, ADR-22) against Envoy's incremental xDS (§33) and identify the fleet size at which the rejected choice becomes the right one. (§33, §22)
  13. Why does the circuit breaker (I7, §19) require a minimum request-volume floor before it is eligible to trip, and what failure mode does omitting that floor produce at low traffic volumes? (§19.6, §7)
  14. Using the capacity model (§34, derivation #1), compute the new memory ceiling if the default connection count target were doubled to 1,000,000 with all other §4 assumptions held constant, and state which other §4 row would need to move to stay under an 8 GB ceiling.
  15. Why does this design strip hop-by-hop headers at the codec layer (P5, I5) rather than as a filter, and what ordering bug would result if it were implemented as a filter running after authn instead? (§12, §24 T1)
  16. Explain why the cache-stampede mitigation (single-flight lease, §22.2) and the rate-limiter's hot-key concern (§21.6) are the same underlying problem appearing in two subsystems, and why each needed its own instance of the fix rather than a shared one.
  17. Why does this design reject WASM filters for v1 (ADR-13) despite the clear operational benefit of no-rebuild deployment, and under what condition (§36) does that rejection reverse? (§15, §36)
  18. Derive the requests/second theoretical ceiling from the §30 per-request CPU breakdown and explain the gap between that number and the §4 target — is the gap headroom, measurement error, or a missing cost line? (§30, §34 derivation #3)

32. Mental Models & First Principles

MM1. A gateway is a queueing system wearing a routing table. Every feature added is another place a request can wait. Predicts: any new filter/stage that lacks a deadline-aware wait silently becomes an unbounded queue under load. Bug class without it: latency tails from a "quick" feature that quietly blocks past the request's actual budget. Resolving: §19 (deadlines), §3 (Architectural Overview).

MM2. Every retry is a decision to spend someone else's capacity. A retry is never free; it is a claim on the upstream's remaining headroom. Predicts: retries must be budgeted, not unlimited. Bug class without it: retry storms turning a partial outage total. Resolving: §19 Phase 7, §34.

MM3. Config is a value, not a mutation target. Treat a running snapshot like an immutable data structure and "reload" like structural sharing (an atomic pointer swap), not like editing a live record. Predicts: partial-apply bugs disappear once you swap pointers instead of fields. Bug class without it: half-applied config visible to in-flight requests. Resolving: §22 Phase 10, I4.

MM4. Health is a state machine with hysteresis, not a boolean. A single failed probe is evidence, not a verdict. Predicts: single-sample health checks flap under normal jitter. Bug class without it: ejection storms that eject a whole cluster from one correlated blip. Resolving: §18 Phase 6, I11.

MM5. A filter chain is function composition with a short-circuit escape hatch. Ordering and short-circuit semantics are the entire contract a filter author needs; nothing else about a filter's internals matters to the chain. Predicts: ordering bugs manifest as "sometimes" failures that are actually fully deterministic once priority is understood. Bug class without it: assuming filter behavior depends on something other than phase+priority+short-circuit. Resolving: §15 Phase 3, §8.3.

MM6. Cache freshness is a promise about time, not a fact about content. A byte-identical cached response can still be wrong to serve if it is stale. Predicts: correctness bugs get mistaken for performance bugs (serving fast, serving wrong). Bug class without it: treating Cache-Control as advisory rather than load-bearing. Resolving: §8.7, §22 Phase 10.

MM7. Rate limiting is admission control running against a clock, not a ledger of who's naughty. The data structure is a small, fast counter, not a growing per-request record. Predicts: scaling the wrong thing (a database write per request) for what is fundamentally a streaming decision. Bug class without it: a rate limiter that itself becomes the bottleneck it was meant to protect against. Resolving: §21 Phase 9, §8.6.

MM8. Thread-per-core buys speed by giving up a free global view. Anything that genuinely needs to see across cores or nodes (a global rate limit, a fleet-wide config version) needs an explicit, visible hop — it is never accidentally free. Predicts: bugs where local state is mistaken for global state. Bug class without it: "the rate limit doesn't actually limit" reports from operators who don't realize local mode is fleet-size-relative by design. Resolving: §31 Scalability Analysis, ADR-15.

Required reading (§5)

Books

  • Stevens, Fenner & Rudoff — UNIX Network Programming, Vol. 1 (3rd ed.) — ch. 6 (I/O multiplexing: select/poll), ch. 16 (nonblocking I/O), ch. 30 (client/server design alternatives). Extract: the accept-loop and multiplexed-I/O reasoning underneath every async runtime. Applied in §12 Phase 0.
  • Grigorik — High Performance Browser Networking — ch. 4 (TLS), ch. 12 (HTTP/2). Extract: handshake cost accounting and stream-multiplexing/flow-control mental model. Applied in §16 Phase 4 and §17 Phase 5.
  • **Nygard — Release It!, 2nd ed.** — ch. 5 (Stability Patterns: Circuit Breaker, Bulkhead, Timeouts), ch. 13 (Handling Versions). Extract: the resilience-pattern vocabulary and the "the system doesn't fail because of you" operational discipline. Applied in §19 Phase 7 and Design Principles P1/P4.
  • Kleppmann — Designing Data-Intensive Applications — ch. 3 (storage/caching internals), ch. 9 (consistency and consensus, for config-snapshot versioning reasoning). Extract: cache-eviction tradeoffs and the "atomic swap over in-place mutation" pattern generalized. Applied in §22 Phase 10 and §8 Domain Model.
  • Beyer, Jones, Petoff & Murphy (eds.) — Site Reliability Engineering (O'Reilly, 2016) — ch. 4 (SLOs), ch. 12 (Effective Troubleshooting), ch. 21 (Handling Overload). Extract: SLO definition discipline and overload-shedding philosophy. Applied in §26 Operational Readiness.
  • Herlihy & Shavit — The Art of Multiprocessor Programming (rev. ed.) — ch. 5 (lock-free data structures), ch. 13 (concurrent hash maps). Extract: atomic-CAS reasoning for lock-free counters. Applied in §21 Phase 9 and ADR-05.

Papers

  • Cormode & Muthukrishnan, 2005, An Improved Data Stream Summary: The Count-Min Sketch and its Applications, J. Algorithms — sub-linear-memory frequency estimation. Relevance: heavy-hitter detection for adaptive quota tightening. Applied in §21 Phase 9 (deferred extension) and the Deferred Features Register.
  • Mitzenmacher, 2001, The Power of Two Choices in Randomized Load Balancing, IEEE TPDS — near-optimal load distribution with O(1) per-decision state. Applied in §18 Phase 6 and ADR-16.
  • Dean & Barroso, 2013, The Tail at Scale, CACM 56(2) — causes of and mitigations for tail latency (hedged/backup requests, bounded retries). Applied in §19 Phase 7 and §30 Performance Engineering.
  • Nishtala et al., 2013, Scaling Memcache at Facebook, NSDI — cache-stampede mitigation via leases, and cache consistency at fleet scale. Applied in §22 Phase 10, N.6 Pitfalls (cache stampede).
  • Welsh, Culler & Brewer, 2001, SEDA: An Architecture for Well-Conditioned, Scalable Internet Services, SOSP — staged event-driven architecture and explicit backpressure. Applied in §12 Phase 0 (bounded accept queue) and Design Principle P6.
  • Karger et al., 1997, Consistent Hashing and Random Trees, STOC — consistent hashing for distributed load distribution. Applied in ADR-16 (rejected alternative) and §36 Alternative Architectures.
  • Fan, Cao, Almeida & Broder, 2000, Summary Cache: A Scalable Wide-Area Web Cache Sharing Protocol, IEEE/ACM ToN — compact existence summaries for distributed cache coordination. Applied in §22 Phase 10 (cache-key negative-lookup reasoning).
  • DeCandia et al., 2007, Dynamo: Amazon's Highly Available Key-value Store, SOSP — sloppy quorum, hinted handoff, eventual convergence under partition. Relevance: the fail-safe "serve last-known-good config" posture during a control-plane outage. Applied in §27 Compatibility & Versioning and I12.

Reference Implementations

  • Envoy — source/common/router/ (route matching, retry policy), source/common/upstream/ (cluster manager, load balancer, health checking, outlier detection). Lesson: strong separation of route config from cluster config, xDS-driven dynamic updates. Pitfall: do not copy the full xDS protocol's incremental-diff complexity at this scale — a versioned full snapshot suffices (ADR-19). Applied in §22 Phase 10.
  • NGINX — src/http/ngx_http_request.c (request state machine), src/http/ngx_http_upstream.c. Lesson: event-driven, one-process-per-core worker model. Pitfall: config reload forks new worker processes — heavyweight versus in-process atomic swap. Applied in §12 Phase 0 and ADR-05.
  • HAProxy — general architecture: single-threaded-per-core event loop, ring-buffer logging. Lesson: disciplined buffer reuse avoids hot-path allocation. Pitfall: stick-table rate limiting is powerful but operationally opaque without explicit documentation. Applied in §21 Phase 9 and ADR-14.
  • Cloudflare Pingora — async Rust proxy framework (public engineering writeups + source). Lesson: per-request phase state machine mirroring a filter chain; leans on rustls/h2 rather than reinventing codecs. Pitfall: do not reinvent TLS/H2 codecs in-house. Applied in ADR-02/ADR-07/ADR-08.
  • Linkerd2-proxy — Rust, tower-based service stack, multiple single-threaded Tokio runtimes (thread-per-core). Lesson: tower::Service composition mirrors the Filter trait contract; small binary footprint. Applied in ADR-05 and §15 Phase 3.
  • Kong — Lua/OpenResty plugin model atop NGINX. Lesson: plugin priority + phase-based lifecycle is a proven operational model for authn/ratelimit/transform ordering. Pitfall: OpenResty's Lua GC/coroutine scheduling produces unpredictable tail latency under load — compiled Rust filters avoid this class of jitter. Applied in §15 Phase 3 and ADR-13.

Glossary (§38) · 49 terms · site-wide glossary

Access phase
the filter-chain phase where authn/authz/rate-limit filters run (§8.3).
ALPN
Application-Layer Protocol Negotiation, the TLS extension selecting h2 vs. http/1.1 at handshake time (§16).
AtomicSwap / ArcSwap
lock-free atomic pointer swap used to publish a new ConfigSnapshot (P2, I4).
Backpressure
explicit admission control (bounded queues, 503s) instead of unbounded queueing under overload (P6, ADR-34).
Budgeted retry
a retry attempt gated by a shared RetryBudget token bucket, never unlimited (P4, I6).
Bulkhead
isolating one dependency's failure from affecting others (Nygard), realized here via per-cluster connection pools and breakers.
Cache key
the hash of method/scheme/host/path/query/Vary-listed headers identifying a cacheable response (§8.7).
Cardinality budget
the fixed set of allowed metric label values, bounding metrics- pipeline memory (P9, §24 T6).
Circuit breaker
the Closed/Open/HalfOpen state machine that fails fast once a dependency is provably unhealthy (I7, §19).
Claim (JWT)
a field inside a JWT payload (exp, nbf, aud, iss) validated at authn time (§20).
Coordinated omission
a load-generator measurement artifact that under-counts requests delayed during a stall; corrected in this build's benchmarks (§23, §30).
Deadline
the monotonic-clock expiry every downstream wait is bounded by (P3, I1).
Config snapshot
the immutable, versioned bundle of routes/clusters/filters swapped atomically on reload (§11, §22).
Config version
the monotonically increasing identifier preventing a stale reload from overwriting newer state (I12).
Connection draining
holding a shutting-down process open until in-flight requests complete or a grace deadline elapses (§26).
Filter
a unit of behavior in the request/response lifecycle implementing the Filter trait (§8.3, §11).
Filter chain
the ordered, priority-driven sequence of filters a request passes through (§3, §15).
Flow-control window
the HTTP/2 mechanism bounding how much unacknowledged data may be in flight per stream/connection (§8.4, RFC 9113).
Hop-by-hop header
a header meaningful only for one transport hop (Connection, Transfer-Encoding), stripped before forwarding (P5, I5).
Hot reload
applying a new configuration without a process restart or dropped connections (§22).
HPACK
the HTTP/2 header-compression scheme (RFC 7541) with a bounded dynamic table (§17).
Idempotency-aware retry
a retry policy scoped to methods/semantics safe to repeat (P10).
JWKS
JSON Web Key Set, the published key material a JWT signature is verified against (§20).
Listener
a port-binding accepting connections, one per protocol/TLS configuration (§11).
Load balancer
the component selecting an upstream Endpoint per request (§11, §18).
Outlier ejection
removing a misbehaving endpoint from load-balancing consideration based on passive failure detection (§8.5, §18).
P2C (power-of-two-choices)
the load-balancing algorithm picking the less-loaded of two randomly sampled endpoints (Mitzenmacher 2001, ADR-16).
Panic boundary
the catch_unwind containment point preventing a filter panic from crashing a worker (I14).
Pooled connection
an upstream connection held for reuse, released only in a known-clean protocol state (I3, §11).
Principal
the identified caller attached to a request after successful authentication (§20).
Rate limit
admission control bounding request rate per key (consumer/route), local or global (§21).
Reset-storm guard
the HTTP/2 mitigation capping client-initiated stream resets per window (§17, CVE-2023-44487).
Retry budget
the shared token bucket capping total retry volume per cluster (I6, §34).
Route
a configured rule matching requests by host/path/method/header to a cluster action (§8.2, §11).
Route precedence
the deterministic ranking resolving overlapping route matches (§8.2).
RTO
Recovery Time Objective, the target time to restore service after a failure (§4).
Segmented LRU
a cache-eviction policy with protected/probationary segments resisting scan-induced eviction of hot entries (ADR-21).
SEDA
Staged Event-Driven Architecture (Welsh 2001), the backpressure/admission-control model applied at the accept queue (§12).
Short-circuit
a filter verdict (Reject/Respond) that stops the remaining chain from running (§8.3).
Sliding-window counter
a rate-limiting algorithm blending current/previous fixed windows to bound edge-doubling error (§8.6).
SLO
Service Level Objective, a quantified target (e.g., availability, latency) the system is operated against (§26).
Snapshot swap
see Config snapshot; the atomic publish mechanism (I4).
Stampede (cache)
many concurrent requests for one cold cache key all missing simultaneously and hammering the origin (§22, Nishtala et al. 2013).
Thread-per-core
a concurrency model assigning one OS thread (and its state) per CPU core, avoiding cross-core synchronization on the hot path (P7, ADR-05).
Token bucket
a rate-limiting/retry-budget primitive with a capacity and refill rate (§8.6, §11).
Trust boundary
a point where data crosses from one security domain to another (e.g., client to gateway, gateway to upstream) (§3).
Vary
the HTTP response header declaring which request headers affect cache-key derivation (§8.7, RFC 9111).
xDS
Envoy's family of discovery-service protocols for incremental config streaming, referenced as a rejected-alternative comparison point (§33, ADR-22).
Zero-copy
processing data via views/slices into existing buffers rather than copying, used where the data does not cross a trust boundary unmodified (P12, ADR-11).
