34. Back-of-Envelope Capacity Model

1. Memory ceiling from concurrent connections. memory = connections × per_conn_bytes + cache_bytes + snapshot_bytes. From §4: 500,000 connections × 8 KB/conn amortized = 4,000,000 KB ≈ 3.81 GB. Plus 2 GB cache (ADR-20) plus ~200 MB config-snapshot overhead (derivation #8 below) ≈ 6.0 GB total, within the §4 ≤8 GB ceiling with ~25% headroom.

2. FD budget. fds = connections × 2 + pool_reserve. 500,000 × 2 = 1,000,000, plus a pool reserve of 128 conns/cluster/worker × ~20 clusters × 8 workers ≈ 20,480 → ≈1,020,480 FDs, consistent with the §4 row (1,048,576, the common ulimit power-of-two ceiling).

3. Requests/second from per-request CPU cost. rps_per_core = 1,000,000 µs ÷ µs_per_request. Using the §30 mixed-workload breakdown (~29.5 µs/request): 1,000,000 ÷ 29.5 ≈ 33,898 req/s theoretical per core. The §4 target of 25,000 req/s/core reserves ~26% headroom below theoretical peak for scheduling jitter and non-steady-state traffic shape — a deliberately conservative gate, not the ceiling itself.

4. TLS handshake capacity. handshakes_per_sec = 1,000,000 µs ÷ µs_per_handshake. Full ECDSA handshake ≈ 250 µs/core → 1,000,000 ÷ 250 = 4,000/s/core (§4 row). Resumed (TLS 1.3 PSK) ≈ 25 µs/core → 1,000,000 ÷ 25 = 40,000/s/core — a 10× reduction, matching the §16.7 claim exactly.

5. Cache memory and hit ratio needed for an origin-load target. Node throughput 180,000 req/s (§4); origin capacity assumed 50,000 req/s sustainable. Required hit ratio: 1 − (origin_capacity ÷ node_throughput) = 1 − (50,000 ÷ 180,000) ≈ 72.2%, consistent with the §4/§30 target of ≥70% (a small margin below the strict-necessity number, since real workloads are not uniformly cacheable).

6. Upstream pool sizing via Little's Law. concurrency = arrival_rate × service_time. For a cluster receiving 10,000 req/s with average service time (upstream RTT + processing) of 3 ms (0.003 s): concurrency = 10,000 × 0.003 = 30 concurrent connections needed. The default pool size of 128/cluster/worker (§4) gives ≈4.3× headroom for burst absorption above the steady-state requirement.

7. Retry-budget amplification under a naive fixed-retry policy. A policy retrying up to 3 times on failure, against a cluster with a 50% per-attempt failure rate, has expected attempts per request = Σ_{k=0}^{3} p^k = 1 + 0.5 + 0.25 + 0.125 = 1.875 — i.e., a naive 3-retry policy generates 87.5% more load on an already-half-failing upstream, directly worsening the failure rate that triggered the retries in the first place. This is the precise mechanism P4/I6's RetryBudget exists to cap.

8. Route-table memory. route_bytes = route_count × bytes_per_route. At ~2 KB/route (compiled trie/regex entry + captures + filter-binding pointers), 100,000 routes ≈ 200 MB, the config-snapshot overhead used in derivation #1.

9. Config-reload time from route count. At ~5 µs/route validation cost, 50,000 routes ≈ 250 ms validation + snapshot-construction overhead ≈ 500 ms total, matching the §4/M9 target exactly.
