⬜ Phase 0 — Skeleton + Listener + HTTP/1.1 Codec + CI §12

Objectives

Stand up gwy-core, gwy-proto-h1, gwy-bin: a working accept loop that parses HTTP/1.1 requests and returns a static response, with CI green. Establish the buffer/deadline primitives every later phase depends on.

Deliverable

curl http://localhost:8080/ returns a static 200; gwyd --config examples/minimal.yaml starts, binds, and logs its bind address and worker count.

Acceptance
  • conformance/h1/cl_te_conflict.txt (CL+TE both present) → 400, zero exceptions across ≥10 smuggling-shaped fixtures in conformance/h1_smuggling/.
  • Single-core static-response throughput ≥ 80,000 req/s (§4 row 1), measured by benchmarks/phase0_static.toml (wrk2, coordinated-omission-corrected).
  • CI green on stable+beta Rust, x86_64+aarch64 (ADR-30).
Fixtures
  • conformance/h1/valid_get.txt — well-formed GET → expect 200.
  • conformance/h1/cl_te_conflict.txt — CL+TE both present → expect 400 (malformed).
  • conformance/h1/chunked_valid.txt — valid chunked body → expect 200, reassembled body correct.
  • conformance/h1/oversized_headers.txt — header block > 16 KB → expect 431 (malformed).
  • conformance/h1/replay_prod_sample_001.txt — captured production-shaped traffic → regression.
Pitfalls
  • Header case mismatch: manifestation — a filter added later silently misses a header; root cause — no canonicalization at the codec boundary; debug — diff raw vs. canonical header names in a trace; signal — filter-miss with no corresponding 4xx; recovery — canonicalize once at parse time, never downstream (I5-adjacent discipline).
  • Accept-loop backpressure absent: manifestation — accept latency spikes under connection bursts; root cause — unbounded accept with no queue cap; debug — gwy_accept_queue_depth; signal — queue depth climbing unbounded; recovery — bounded queue + 503 admission control (P6, ADR-34).
  • Chunked-encoding size desync: manifestation — the next request on a reused connection is misframed; root cause — a parser bug miscounting chunk sizes; debug — differential replay against a reference parser (§28); signal — divergent framing on identical bytes; recovery — close the connection, never guess (I3).

⬜ Phase 1 — Router + Route Matching §13

Objectives

Replace the Phase 0 static response with real routing: host + path + method + header matching, with the precedence rules of §8.2, sublinear in route count.

Deliverable

100-route fixture set loads; requests route correctly by host/path/method/header combination, verified against the worked trace in §8.2.

Acceptance
  • Route-match latency ≤ 1 µs average at 10,000 loaded routes (benchmarks/phase1_match.toml, criterion), consistent with the sublinear claim in ADR-12/§31.
  • Property test route_precedence_totality (§28): for any two overlapping routes in a 1,000-route generated fixture set, the precedence engine picks exactly one winner, never zero, never a tie left unresolved — 100,000 generated cases, zero failures.
  • Wildcard-host fixture set (conformance/router/wildcard_host.yaml, 12 cases) passes exactly as specified in §8.2.
Fixtures
  • conformance/router/precedence_worked_example.yaml — encodes the §8.2 worked trace, asserts route (b) wins.
  • conformance/router/wildcard_host.yaml — 12 cases distinguishing *.example.com from example.com and multi-label hosts.
  • conformance/router/regex_priority_tiebreak.yaml — two regex routes, asserts higher regex_priority wins.
  • conformance/router/replay_100k_routes.yaml — regression: 100,000-route table load + 10,000 sampled lookups, asserts identical results across two builds.
Pitfalls
  • Regex routes bypassing the prefix index: manifestation — adding one regex route degrades matching for all routes to linear scan; root cause — matcher topology decided too late; debug — benchmark regression on phase1_match.toml; signal — match latency jumps from ~1 µs to ~100 µs; recovery — regex routes go into a separate compiled DFA set (ADR-12), never mixed into the trie.
  • Path normalization mismatch (the CVE-2021-39156-class Istio bug): manifestation — matcher and upstream disagree on /foo/../bar vs. /bar; root cause — normalization applied inconsistently between match-time and forward-time path; debug — differential fixture with dot-segments; signal — authz bypass via path confusion; recovery — normalize once, forward the normalized form, never let match-time and forward-time paths diverge.
  • Catch-all route ambiguity: manifestation — a route with no match criteria silently swallows all traffic; root cause — admin API allowed an empty-criteria route; debug — route audit tool (tools/route-table-linter); recovery — reject empty-criteria routes at config validation (P13) unless explicitly flagged as a fallback.

⬜ Phase 2 — Upstream Connection Pool + Forwarding §14

Objectives

Forward a matched request to a real upstream over a pooled connection; no load balancing or health checking yet (those are §18 Phase 6) — one endpoint per cluster, round-robin-of-one.

Deliverable

A request matched to a route forwards to a single configured upstream and the client receives the byte-faithful upstream response, over a reused pooled connection on the second request.

Acceptance
  • Connection reuse rate ≥ 95% for a sustained keep-alive client benchmark (benchmarks/phase2_pool_reuse.toml).
  • Pool checkout latency p99 ≤ 5 µs (§4-consistent budget line item, §30 breakdown).
  • conformance/pool/half_read_body_poisoning.yaml: a connection released after a half-read response body is never returned clean (I3) — 0 poisoned reuses across 10,000 generated cases.
Fixtures
  • conformance/pool/reuse_basic.yaml — two sequential requests reuse one connection.
  • conformance/pool/half_read_body_poisoning.yaml — malformed-forward case: response body only partially read before the next checkout; asserts the connection is discarded, not reused.
  • conformance/pool/upstream_reset_mid_body.yaml — upstream RSTs mid-response; asserts client sees a clean 502, not a truncated body presented as complete.
  • conformance/pool/replay_keepalive_burst.yaml — regression: 10,000-request keep-alive burst, asserts stable reuse rate across builds.
Pitfalls
  • Connection reuse after a half-read body poisons the next request: manifestation — the next request on a "reused" connection receives bytes from the previous response; root cause — releasing a connection to the pool before the body was fully consumed or explicitly drained; debug — conformance/pool/half_read_body_poisoning.yaml reproduces deterministically; signal — gwy_pool_conn_discarded_total{reason="dirty"} should be nonzero instead of corrupted responses; recovery — I3's clean-state tag is the structural fix: never skip the check.
  • DNS TTL staleness: manifestation — traffic keeps flowing to a decommissioned IP; root cause — cached resolution outlives the record's actual TTL; debug — compare cached vs. authoritative TTL; recovery — bound the cache TTL from below by a configured floor, never trust an unbounded record TTL.
  • Pool exhaustion cascading: manifestation — one slow cluster's pool fills, but the node's total connection count also approaches the FD budget (§4); root cause — no per-cluster pool cap; debug — gwy_pool_checkout_wait_total{cluster}; recovery — per-cluster max_size (§4 row "upstream pool size"), never a single global pool.

⬜ Phase 3 — Filter-Chain Framework §15

Objectives

Introduce the Filter trait and lifecycle harness (§8.3): ordered execution, short-circuiting, and the phase model (Rewrite → Access → Transform → HeaderFilter → BodyFilter). No real authn/ratelimit logic yet (those are §20/§21) — two trivial filters prove the harness.

Deliverable

A request flows through both reference filters in the documented priority order; a deliberately panicking test filter converts to 500 without crashing the worker (I14 verified).

Acceptance
  • conformance/filters/order_determinism.yaml: 20 filters at mixed priorities, including ties, produce byte-identical execution order across 1,000 runs (deterministic tie-break, §8.3).
  • conformance/filters/panic_containment.yaml: an injected panic in one filter yields a 500 for that request while a concurrent request on the same worker completes normally — verified by a two-request harness test, 0 worker crashes across 10,000 injected panics.
  • Filter-chain overhead ≤ 2 µs per filter at the Continue fast path (§4/§30 budget line item), measured by benchmarks/phase3_chain_overhead.toml.
Fixtures
  • conformance/filters/order_determinism.yaml — mixed-priority ordering with explicit ties.
  • conformance/filters/panic_containment.yaml — malformed-filter-behavior case (I14).
  • conformance/filters/short_circuit_reject.yaml — a filter returning Reject stops downstream filters but log()-equivalent telemetry still fires (§8.3).
  • conformance/filters/replay_mixed_chain.yaml — regression: a 12-filter chain replayed against a captured request corpus, asserting identical verdicts across builds.
Pitfalls
  • Async retrofitted too late: manifestation — adding Suspend after sync-only filters ship requires a breaking trait change; root cause — treating "most filters are sync" as "all filters are sync"; debug — none needed if designed correctly now; recovery — Suspend exists from this phase (Kong reference-implementation lesson, §5 Reference Implementations #6, applied here).
  • Priority-space drift: manifestation — over time, filter priorities become effectively random and operators can't predict ordering; root cause — no documented priority-range convention; debug — tools/route-table-linter-adjacent filter-priority auditor; recovery — reserve documented ranges per phase (9000+ rewrite, 900-999 access, 800-899 transform) and enforce in code review.
  • Cross-request state leaking into plugin_state: manifestation — a filter accidentally stores cluster-wide state (e.g., a rate-limit counter) in the per-request TypeMap instead of its own module-owned state; root cause — plugin_state looks convenient for anything; debug — a state-lifetime lint in code review; recovery — plugin_state is documented as single-request-lifetime only; anything living longer is the filter's own concern (§8.3).

⬜ Phase 4 — TLS Termination + ALPN §16

Objectives

Terminate TLS 1.3 (RFC 8446) at the listener, negotiate ALPN (h2 vs. http/1.1), and wire the TlsContext primitive introduced in §11 into the accept path.

Deliverable

gwyd serves HTTPS with a self-signed cert from examples/; curl -v shows ALPN negotiated to h2 against an H2-capable client and http/1.1 against a plain HTTP/1.1 client.

Acceptance
  • Full-handshake throughput ≥ 4,000 handshakes/s/core (ECDSA P-256), resumed-handshake throughput ≥ 40,000 handshakes/s/core (§4 rows), measured by benchmarks/phase4_tls.toml.
  • conformance/tls/legacy_version_rejected.yaml: TLS 1.0/1.1 ClientHello → handshake failure, 0 successful legacy handshakes across 50 generated cases.
  • conformance/tls/alpn_negotiation.yaml: 4 client-capability combinations (h2-only, h1-only, both, neither) each resolve to the documented outcome.
Fixtures
  • conformance/tls/alpn_negotiation.yaml — the 4-combination ALPN matrix above.
  • conformance/tls/legacy_version_rejected.yaml — malformed/downgrade-shaped ClientHellos.
  • conformance/tls/session_resumption.yaml — a second handshake from the same client reuses a PSK ticket; asserts the resumed-path CPU cost is measurably lower (§4).
  • conformance/tls/replay_handshake_corpus.yaml — regression: captured ClientHello corpus replayed across builds, asserting stable accept/reject decisions.
Pitfalls
  • TLS downgrade / certificate confusion: manifestation — a client is silently downgraded to a weaker version or a wrong SNI-selected cert is served; root cause — permissive rustls config or SNI-to-cert mapping ambiguity; debug — conformance/tls/legacy_version_rejected.yaml and an SNI-mismatch fixture; signal — gwy_tls_handshake_failed_total{reason} spikes on a legitimate client population; recovery — structural version/cipher floor at the rustls config layer, never a filter-level check (§24 T2).
  • Session-ticket cache unbounded growth: manifestation — memory grows with unique client count; root cause — no TTL/size cap on the PSK ticket cache; debug — cache size metric vs. configured cap; recovery — bounded LRU ticket cache, evict oldest on pressure.
  • ALPN mismatch silently falling back: manifestation — an H2-only backend integration test fails intermittently; root cause — a client that claims H2 support but negotiation falls back to H1 without the caller noticing; debug — log negotiated protocol per connection; recovery — expose negotiated protocol in the access log and admin dump for diagnosis.

⬜ Phase 5 — HTTP/2 Downstream and Upstream §17

Objectives

Add HTTP/2 (RFC 9113) on both the client-facing (downstream) and upstream-facing legs: stream multiplexing, HPACK header compression (RFC 7541), and flow control, per the state table in §8.4.

Deliverable

An H2 client multiplexes 100 concurrent streams over one TCP connection to the gateway; the gateway forwards to an H2 upstream over one pooled multiplexed connection; both directions verified byte-correct against h2spec-style fixtures.

Acceptance
  • conformance/h2/rapid_reset_guard.yaml: a client opening/resetting 10,000 streams/sec on one connection is disconnected once the configured reset budget is exceeded (default: 100 resets/ 10 s) — 0 unbounded-cost accepts across the fixture set.
  • Stream concurrency ≥ 100 simultaneous streams per connection sustained at flow-control-window- bounded throughput (benchmarks/phase5_h2_mux.toml).
  • h2spec-style conformance suite (conformance/h2/h2spec_subset.yaml) passes 100% of the frame-format and flow-control sections relevant to this build's feature set.
Fixtures
  • conformance/h2/rapid_reset_guard.yaml — the CVE-2023-44487 mitigation fixture.
  • conformance/h2/flow_control_deadlock.yaml — malformed case: a peer advertises a zero window and never updates it; asserts the gateway times out the stream (I1) rather than blocking forever.
  • conformance/h2/hpack_table_bound.yaml — a peer attempting to force unbounded HPACK dynamic- table growth is rejected.
  • conformance/h2/replay_mux_burst.yaml — regression: 100-stream multiplexed burst replayed across builds for identical per-stream outcomes.
Pitfalls
  • HTTP/2 flow-control deadlock: manifestation — a stream hangs indefinitely; root cause — a peer advertises a zero-size window and the gateway waits unboundedly for a WINDOW_UPDATE; debug — conformance/h2/flow_control_deadlock.yaml reproduces it; signal — stream duration metric with no terminal frame; recovery — every stream wait is Deadline-bounded (I1) — flow-control waits are not exempt from the deadline contract.
  • Reset-storm cost amplification: manifestation — CPU spikes from stream setup/teardown churn; root cause — no cap on client-initiated resets; debug — gwy_h2_stream_reset_total rate; recovery — the reset-budget guard from 17.2, closing the connection past threshold.
  • HPACK dynamic-table poisoning across streams: manifestation — one stream's header compression state affects another's decode; root cause — the dynamic table is connection- scoped by spec, but an implementation bug could leak entries across an unrelated boundary; debug — differential test against the h2 crate's own conformance suite; recovery — trust the reference h2 crate's HPACK implementation (ADR-08) rather than a hand-rolled one.

⬜ Phase 6 — Load Balancing + Health Checks + Outlier Ejection §18

Objectives

Extend clusters from one endpoint to many: pick an endpoint via a real load-balancing algorithm, detect failure via active and passive health checks, and eject/recover per the state machine in §8.5.

Deliverable

A 5-endpoint cluster with one endpoint killed mid-benchmark shows traffic shift away from the dead endpoint within the configured detection window, with zero requests routed to an Ejected endpoint.

Acceptance
  • Detection-to-ejection latency ≤ 3 active-probe intervals (≤ 15 s at the default 5 s interval, §4) in conformance/upstream/kill_one_endpoint.yaml.
  • conformance/upstream/health_state_machine.yaml: a deterministic-simulator run (§7 methodology) exercises all documented state edges in §8.5 and asserts zero illegal transitions across 100,000 simulated events (I11).
  • Load distribution across 4 healthy endpoints of equal weight is within 5% of uniform under a 10,000-request benchmark (benchmarks/phase6_lb_distribution.toml), consistent with the P2C balance guarantee (Mitzenmacher 2001).
Fixtures
  • conformance/upstream/kill_one_endpoint.yaml — the primary failover fixture.
  • conformance/upstream/health_state_machine.yaml — the full state-machine simulator run.
  • conformance/upstream/flapping_endpoint.yaml — an endpoint that alternates healthy/unhealthy faster than the hysteresis window; asserts it does not thrash between states (P11).
  • conformance/upstream/replay_p2c_distribution.yaml — regression: fixed random seed, asserts identical endpoint-selection sequence across builds.
Pitfalls
  • Outlier ejection removing every endpoint at once: manifestation — a correlated failure (e.g., a shared dependency all endpoints call) ejects the entire cluster simultaneously, turning a partial degradation into a total outage; root cause — no floor on how many endpoints can be ejected concurrently; debug — gwy_endpoint_health_state gauge across the whole cluster; signal — ejected count approaching cluster size; recovery — a configurable "panic threshold" (e.g., never eject past 50% of a cluster) that freezes further ejection and fails open to the remaining endpoints, however degraded (§25 FM-7).
  • Health-check-induced load: manifestation — active probes themselves become a meaningful fraction of backend load at very high endpoint counts; root cause — active-only design without considering probe cost at scale; debug — probe request-rate metric vs. real traffic rate; recovery — passive-only fallback mode for very large/lightweight endpoint fleets (ADR-17 rejected-alternative regime).
  • Weight-zero endpoints still selected: manifestation — a "disabled" endpoint (weight 0) keeps receiving traffic; root cause — the LB's random pre-selection step doesn't exclude zero-weight endpoints before the P2C comparison; debug — selection-distribution fixture; recovery — zero-weight endpoints are excluded from the candidate set entirely, not merely deprioritized.

⬜ Phase 7 — Timeouts, Retries with Budgets, Circuit Breaking §19

Objectives

Add the resilience layer (Nygard, Release It!, applied throughout this phase per §5): per-try timeouts, budgeted retries (P4/I6), and a per-endpoint circuit breaker (I7).

Deliverable

A cluster with a 50% synthetic failure rate: requests succeed via retry within budget; once the budget is exhausted, requests fail fast without further retry attempts; the breaker trips to Open once the endpoint-level error rate crosses threshold and requests fail immediately (no wasted upstream round-trip) until HalfOpen probing succeeds.

Acceptance
  • conformance/resilience/retry_budget_never_exceeded.yaml: a property test asserting retry attempts across 100,000 simulated requests never exceed the configured budget fraction (I6) — 0 violations.
  • conformance/resilience/breaker_state_machine.yaml: deterministic-simulator run exercising every CircuitState edge in I7, 0 illegal transitions across 100,000 events.
  • Deadline monotonicity property test (§28): a retried request's total elapsed time never exceeds its original Deadline, across 50,000 generated retry scenarios (I1, P3).
Fixtures
  • conformance/resilience/retry_budget_never_exceeded.yaml — the budget-bound property fixture.
  • conformance/resilience/breaker_state_machine.yaml — the full breaker state-machine simulator.
  • conformance/resilience/deadline_exhausted_mid_retry.yaml — malformed/edge case: a retry would be attempted but the deadline expires first; asserts no retry is attempted past the deadline (I1 takes precedence over I6's budget allowance).
  • conformance/resilience/replay_partial_outage.yaml — regression: a captured 40%-failure-rate traffic replay, asserting stable amplification-factor bounds across builds.
Pitfalls
  • Retry storms amplifying a partial outage: manifestation — a struggling upstream receives more load from retries than its original failure would have caused, tipping it into total failure; root cause — retries without a shared budget; debug — the amplification derivation in §34 quantifies exactly this; signal — upstream request rate rising as upstream success rate falls; recovery — I6's budget is the structural fix, not a tunable afterthought.
  • Non-idempotent retry double-application: manifestation — a payment is charged twice; root cause — a POST retried without an idempotency-key mechanism; debug — origin-side duplicate- charge report; recovery — P10's idempotency-aware retry_on scoping, defaulting to "safe methods only" unless a route explicitly opts a mutating method in with an idempotency-key contract.
  • Circuit breaker trips on a transient blip, not a real outage: manifestation — a two-request error burst opens the breaker for the whole cooldown window, wasting healthy capacity; root cause — a rolling-window error-rate threshold too sensitive at low request volume; debug — breaker trip rate vs. actual endpoint health (cross-reference §8.5's ejection state); recovery — require a minimum request-volume floor in the rolling window before the breaker is eligible to trip at all.

⬜ Phase 8 — Authn/Authz Filter + JWKS Caching §20

Objectives

Real identity: verify JWT (RFC 7519) bearer tokens against JWKS-published public keys, cache keys with a bounded staleness window (I10), and add a scope/claim-based authorization filter.

Deliverable

A request with a valid RS256 JWT signed by a key published in the test JWKS endpoint (tools/jwks-mock-server) is authenticated and authorized per route scope; an invalid signature, an expired token, and an alg: none token are each rejected with the documented status.

Acceptance
  • conformance/authn/alg_none_rejected.yaml: 100% rejection rate across a fixture set of alg: none-shaped tokens, 0 exceptions.
  • JWKS cache hit ratio ≥ 99% under a steady kid population in benchmarks/phase8_jwks_cache.toml (bounded refresh cost per I10).
  • conformance/authz/scope_enforcement.yaml: 20 (route, scope-set) combinations each produce the documented 200/403 outcome.
Fixtures
  • conformance/authn/alg_none_rejected.yaml — the alg: none bypass-attempt fixture set.
  • conformance/authn/expired_token.yaml — exp in the past, beyond clock-skew tolerance → 401.
  • conformance/authn/jwks_kid_miss.yaml — an unknown kid triggers a bounded out-of-band fetch, asserts the fetch respects the request's remaining Deadline (I1/P3).
  • conformance/authz/scope_enforcement.yaml — the scope-matrix fixture above.
  • conformance/authz/replay_mixed_principals.yaml — regression: a corpus of mixed valid/invalid tokens replayed across builds for stable authn/authz outcomes.
Pitfalls
  • JWT signature bypass via alg confusion: manifestation — an attacker resigns a token with alg: none or substitutes an HMAC signature verified against a public RSA key value; root cause — a permissive JWT library default; debug — conformance/authn/alg_none_rejected.yaml and an HMAC-confusion fixture; signal — an authenticated request with no corresponding valid signature check in the verification library's audit log; recovery — pin the accepted algorithm set per route explicitly, never trust the token's self-declared alg alone (§24 T6, the historical CVE class this defends against).
  • JWKS cache staleness widening the key-rotation window: manifestation — a revoked key is still accepted well past its intended rotation; root cause — I10's refresh task falling behind under load or a fetch failure loop; debug — gwy_jwks_refresh_age_seconds vs. configured max- age; recovery — alert when refresh age exceeds a grace threshold, and cap how long a stale key may still be served (a hard ceiling past which authn fails closed).
  • Authz running before authn completes: manifestation — a request reaches the authz filter with no principal set, either erroring confusingly or (worse) defaulting to an allow; root cause — a priority misconfiguration; debug — the priority-space audit from §15.6, extended to flag "authz without a preceding authn at higher priority"; recovery — config validation (P13) rejects a route with an authz binding but no authn binding at a higher Access-phase priority.

⬜ Phase 9 — Rate Limiting (Local Then Global) §21

Objectives

Enforce per-consumer/per-route quotas: local token-bucket admission first, then an opt-in global (cross-node) sliding-window-counter mode for accuracy-sensitive quotas (ADR-14/ADR-15).

Deliverable

A consumer configured at 100 req/min is admitted up to the burst capacity, then receives 429 with Retry-After until the window recovers; switching the same route to global mode enforces the same limit accurately across a 3-node test fleet (no per-node drift).

Acceptance
  • conformance/ratelimit/admitted_never_exceeds_bound.yaml: property test, admitted count over N=100,000 trials never exceeds capacity + refill for the elapsed window (I8), 0 violations.
  • Local-mode decision latency ≤ 0.5 µs (§4/§30 budget line item), global-mode decision latency ≤ 2 ms including the network round trip (benchmarks/phase9_ratelimit.toml).
  • Cross-node drift under global mode ≤ 1% of configured limit across a 3-node fleet benchmark, versus documented ~2× drift for local-only mode at the same fleet size (§31-class reasoning).
Fixtures
  • conformance/ratelimit/admitted_never_exceeds_bound.yaml — the I8 property fixture.
  • conformance/ratelimit/burst_then_recover.yaml — burst to capacity, 429 until window recovery, then admits again — timing asserted against the token-bucket equation (§8.6).
  • conformance/ratelimit/global_store_unavailable.yaml — malformed/failure case: the global store is unreachable; asserts the configured fail-open/fail-closed stance is honored exactly (P1).
  • conformance/ratelimit/replay_multi_tenant.yaml — regression: a multi-consumer traffic replay, asserting stable per-consumer admission decisions across builds.
Pitfalls
  • Rate-limiter bypass via header spoofing: manifestation — a client claims a different consumer identity to reset its own quota; root cause — the rate-limit key derives from a client-controlled header rather than the authenticated principal; debug — a fixture asserting the key never derives from unauthenticated input; recovery — key by principal.sub (post-authn, §20) or a trusted proxy-injected identity, never a raw client header (§24 T7).
  • Cache stampede on a hot key: manifestation — many concurrent requests for the same extremely popular consumer/route key all miss simultaneously and hammer the global store; root cause — no request coalescing on a cold key; debug — global-store request-rate spike correlated to one key; recovery — a short-lived lease/single-flight pattern per key (Nishtala et al. 2013, applied here per §5) so only one request populates a cold counter while others wait briefly.
  • Local-node drift misunderstood as a bug: manifestation — operators report "the rate limit doesn't actually limit" because a consumer gets N× the configured rate across an N-node fleet; root cause — local-only counting is fleet-size-relative by design (ADR-15); recovery — this is documented behavior, not a defect; the fix is switching that route to global mode, not patching local mode.

⬜ Phase 10 — Response Caching + Hot-Reloadable Config Plane §22

Objectives

Add RFC 9111-conformant response caching and replace the Phase 0 static-config load with the real hot-reloadable config plane: validated, versioned, atomically swapped (P2/P13, I4/I12).

Deliverable

A GET route with Cache-Control: max-age=60 serves from cache on the second identical request within the freshness window; editing gateway.yaml and sending SIGHUP (or a control-plane push) applies a new route within the §4 reload-time target with zero connection drops.

Acceptance
  • Cache hit-ratio ≥ 70% on a cacheable-GET-heavy synthetic workload (§4), measured by benchmarks/phase10_cache_hit_ratio.toml.
  • Config reload of a 50,000-route table completes in ≤ 500 ms with 0 dropped connections (conformance/config/reload_zero_drop.yaml, §4).
  • conformance/config/reject_bad_referential.yaml: a route referencing a nonexistent cluster is rejected at validation, the prior snapshot remains active, 0 requests affected.
Fixtures
  • conformance/cache/freshness_and_validation.yaml — the RFC 9111 decision-tree worked cases from §8.7, including a Vary-header scenario.
  • conformance/cache/stampede_single_flight.yaml — 1,000 concurrent requests for one cold key; asserts exactly one origin fetch.
  • conformance/config/reload_zero_drop.yaml — the atomic-swap zero-drop fixture (I4).
  • conformance/config/reject_bad_referential.yaml — malformed config: dangling cluster reference, rejected pre-apply (P13).
  • conformance/config/replay_version_monotonicity.yaml — regression: a sequence of config versions applied out of order; asserts only monotonically increasing versions are ever applied (I12).
Pitfalls
  • Cache stampede on a hot key: manifestation — a popular cached response expiring causes a burst of simultaneous origin fetches; root cause — no request coalescing on cache-miss; debug — origin request-rate spike synchronized to a TTL boundary; recovery — the single-flight lease from 22.2 (Nishtala et al. 2013).
  • Config reload that validates but is semantically wrong: manifestation — a route change passes schema and referential validation but points traffic at the wrong cluster (a typo'd but existing cluster ID); root cause — validation checks structure and referential integrity, not intent; debug — a config diff review step and canary-apply-to-one-node-first operational practice (§26); recovery — this class of error is caught by process (staged rollout, §27), not by the validator alone — document the limit of automated validation explicitly.
  • Caching authenticated responses without a consumer-scoped key: manifestation — consumer A's cached response is served to consumer B; root cause — the cache key omits the principal for a route where the response varies per caller; debug — a fixture with two distinct principals hitting the same URL; recovery — routes serving per-principal content must include the principal in CacheKey derivation or disable caching entirely (documented per-route opt-in, never a default-on assumption for authenticated routes).

⬜ Phase 11 — Conformance Suite + Perf Hardening §23

Objectives

Consolidate every phase's fixtures into one runnable conformance suite, close remaining protocol-conformance gaps, and drive the system to the §4/§30 performance targets under sustained load.

Deliverable

A single make conformance target runs the full aggregated fixture suite plus the differential corpus and reports pass/fail per fixture; a single make perf target runs the full benchmark suite and reports pass/fail per §4/§30 target with the gate's tolerance applied.

Acceptance
  • 100% pass rate across the aggregated conformance suite (all fixtures from §12.5–§22.5 plus this phase's additions), 0 skipped fixtures.
  • 72-hour soak: memory growth ≤ 5% of the §4 ceiling over the run, 0 crashes, 0 panics escaping the I14 containment boundary.
  • Differential corpus (conformance/differential/): ≥ 95% byte-identical response agreement with NGINX and Envoy on a shared 10,000-request corpus for the routing/forwarding behaviors common to all three (documented, expected divergence points listed explicitly, e.g. gateway- specific headers).
Fixtures
  • conformance/all/aggregate_manifest.yaml — the full fixture manifest aggregating every named fixture from Phases 0–10.
  • conformance/fault_injection/upstream_reset_mid_body.yaml, slow_reader.yaml, tls_renegotiation.yaml — the three named fault-injection cases from 23.2.
  • conformance/differential/nginx_envoy_corpus.yaml — the 10,000-request differential corpus.
  • conformance/soak/72h_leak_detector.yaml — the soak-test harness configuration and its memory- growth assertion.
Pitfalls
  • Metric-label cardinality explosion taking down the metrics pipeline: manifestation — the metrics backend itself falls over or drops data under load; root cause — a label (accidentally reintroduced raw route_path or consumer_id) breaks the cardinality budget from P9/§24 T6; debug — a cardinality-budget CI check scanning every metric emission site for disallowed label sources; recovery — the check is added in this phase as a permanent CI gate, not a one-time audit.
  • Perf gate false negatives from coordinated omission: manifestation — a benchmark reports "passing" latency numbers during a period the load generator itself was stalled, hiding a real regression; root cause — a naive closed-loop load generator; debug — compare against a known- regressed build with coordinated-omission correction on vs. off; recovery — every benchmark in benchmarks/ uses the corrected methodology from 23.2, enforced by a lint on new benchmark files.
  • Differential-corpus false failures from legitimately different behavior: manifestation — the NGINX/Envoy differential run reports failures for cases where this gateway's documented behavior intentionally differs (e.g., stricter smuggling rejection); root cause — the corpus doesn't yet distinguish "bug" from "documented divergence"; recovery — the differential fixture's manifest explicitly whitelists documented divergences with a citation back to the ADR or invariant that mandates the difference (e.g., ADR-07's strict-parsing rationale).
