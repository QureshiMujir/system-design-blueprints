In one paragraph

Diff Merge (diffmerge) is a Rust library, a command-line tool (dm) and a C interface. It finds the smallest list of edits between two byte sequences, writes and applies patches in unified-diff format, and merges two divergent edits of a common ancestor (§1). Its bar is byte-for-byte agreement with git diff --no-color on a committed test corpus (§1, §22). It is a stateless library with no daemon and no network service, used by version-control tooling authors, code-review platforms and config-drift tools (§1, §4).

The problem, concretely

You want to diff two versions of a file and hand the result to git apply. A textbook diff gets you most of the way, and the blueprint says the remaining gap is "entirely in tie-breaking, streaming, and byte-exact conformance" (§2). Each of those bites separately.

Tie-breaking: many edit scripts can have the same cost, so "the diff" is not unique and choosing among them is a design decision (MM1). If your output must match git byte for byte, every tie has to be broken the way git breaks it (§15.6, I3). Size: the non-streaming path may hold up to 3 × (old + new) bytes, so a 1 GB pair needs 6 GB of RAM (§4, §33 item 1). Hostile input: two files with no line in common push Myers' edit distance to its maximum, D = n + m (§14.8), and the capacity model, using an O(D²) cost, estimates about 60 seconds for a 10 MB pair at the default cap (§33 item 5). Formatting: counting the \ No newline at end of file line in a hunk header shifts every later hunk header by one (I9, §17.6).

Merging adds its own trap. Take a base ["a","b","c"], one branch that changes b to x, and another that appends d. The edits do not overlap, so a correct merge gives ["a","x","c","d"] with zero conflicts (§8.4). Line-based merge can still be wrong while looking clean, a case the blueprint accepts and documents rather than hides (§8.6, §18.2 step 8). The structure of the blueprint answers these pressures: one shared description of an edit, strict budgets with typed errors, and a conformance suite against git (P2, P14, P12).

How it works, end to end

Follow a pair of files down the boxes of §3's diagram:

  1. Entry point. The dm CLI (diffmerge-cli) and the C ABI (diffmerge-ffi) are the only user-facing surfaces. Both are thin: each subcommand and each exported symbol maps 1:1 to a library call (§3, P9, §21). Every dm_* C symbol is wrapped so a Rust panic cannot unwind into C (I10, §21.2 step 5).
  2. Public surface. diffmerge-core is the only entry point; nothing below is reachable except through diff, tree::diff or json::diff (§3).
  3. Tokeniser. Input bytes are cut into Tokens (a slice plus a hash) at byte, line, word or character granularity (§11.1, §13). Each token is hashed once with xxh3_64 (§13.2 step 2). Equal hashes are not trusted: Token::eq falls back to comparing bytes (I4, §14.6).
  4. Edit-graph algorithm. One of five algorithms searches for the cheapest sequence of deletes and inserts and returns an EditScript stamped with its AlgorithmId (§3, §11.2, §14.2 step 3). Whatever the algorithm, the script is checked by EditScript::validate() before anything uses it (I1). Having a single shared shape is what lets a new algorithm be added without touching the patch code (P2).
  5. Patch. diffmerge-patch groups the script into hunks and renders them as unified-diff text; it also parses text back into a typed Patch and applies it exactly or fuzzily (§3, §17.2). Text is only a rendering of the typed Patch (P5).
  6. Three-way merge. diffmerge-merge diffs base against ours and base against theirs, then walks the two diffs together and emits a list of Resolved or Conflict blocks (§18.2 steps 1-2, §11.4). §3's diagram draws a Patch arrow into this box and P5 says the merge engine consumes Patch, while §18.2 step 1 says merge consumes EditScripts from myers_linear directly. The blueprint does not reconcile the two.
  7. Tree diff. diffmerge-tree first compares two file trees by path, then promotes matching delete+add pairs to renames or copies as a separate pass (§19.2, §11.5, P10).
  8. Structured side path. JSON, XML and YAML get a structural diff that shares only the boundary shape of the IR, never a text diff of pretty-printed output (§3, P11).
  9. Conformance. Every arrow ends at the suite that compares output to git diff, git merge-file and git merge-ort (§3, §22).

The core ideas

Diffing is a shortest-path search on a grid (§8.1, §14)

Lay the old sequence along one axis and the new one along the other. A node (i,j) means "consumed old[0..i] and new[0..j]". Moving right deletes an old item, moving down inserts a new one, and moving diagonally is free but only where old[i] == new[j]. The cheapest path from (0,0) to (n,m) is a minimum edit script, and D is the number of non-diagonal steps (§8.1).

Myers' O(ND) algorithm (§14.2): for each edit count d and each diagonal k, keep the furthest x reached after d edits and slide along free diagonal runs; backtracking the recorded trace yields the script (§14.2 steps 1 and 3). The blueprint gives the boundary cases: identical inputs have D = 0, and fully disjoint inputs have D = n + m (§14.8). Keeping the whole trace costs O((N+M)D) memory per §14.7, while §2 says the naive form needs O(D²) space and §14's opening calls it quadratic-space; the blueprint does not reconcile these. The linear-space middle snake runs a forward and a reverse search until they meet on one diagonal, then recurses on both halves, so time stays O((N+M)D) while space drops to O(N+M) (§14.2 steps 4-5, §14.7). Wu's O(NP) uses D = N - M + 2P, where P is the deletion count, and is only run when |n-m| ≤ 0.05 × max(n,m) (§14.2 step 6, ADR-22). Hunt-McIlroy LCS is kept, capped at 4096 tokens per side, as an independent checker, not a production path (§14.2 step 7). A property test over 1000 random pairs of up to 256 items checks that all four scripts apply to the same result (§14.2 step 8).

Anchors: patience and histogram diff (§15, §16)

Raw Myers can match unrelated lines. Patience diff first finds lines that appear exactly once in both files (the anchors), picks the largest set that keeps the same order in both files with patience sort (a longest increasing subsequence), and recurses into the gaps between anchors (§15.2 steps 1-4). "Unique" must hold in both files: a line unique in old but duplicated in new is not an anchor (§15.5, §15.6). With no anchors, as with 1000 blank lines, the region falls through to myers_linear (§15.4 criterion 4, §15.2 step 6). Histogram diff relaxes uniqueness: it picks the common token with the smallest combined count and splits there, but skips any token whose count exceeds max_chain (default 64, libxdiff's value) (§16.2 steps 2-3). That cap is the lever between O(N log N) and O(N²), and a test with max_chain=4 must give a different but valid output (§16.2 step 3, §16.4 criterion 4). The reason all this works is uniqueness, not proximity (MM2).

Hunks and the unified-diff header (§8.2, §17)

A hunk is a run of changes plus context lines, with a header @@ -old-start[,old-len] +new-start[,new-len] @@. Lengths are omitted when they equal 1, and a start is 0 when that side is empty (§8.2). The default context is 3 lines. Two changes join into one hunk when fewer than 2×context unchanged lines separate them; a gap of 2×context or more splits them (§17.2 steps 1-2). The line \ No newline at end of file is not counted in either length (I9, §8.2). Parsing counts the lines it consumes against the header: a header @@ -5,3 +5,4 @@ followed by only 2 old-side lines raises ParseError::HunkLengthMismatch{expected:3, actual:2} (§8.5, I6). Applying walks a cursor forward through the file once, so cost is O(file_size + hunk_count) (§17.2 step 6). If the exact context is gone, apply_fuzzy searches a ±50-line window for the best context match (§17.2 step 7). A rename with edits is applied rename first, edit second (§17.6).

Three-way merge: two diffs and a walker (§8.3, §8.4, §18)

A merge is two diffs reconciled, not a new algorithm (MM3). The weave walk classifies each region of the base:

Base region Ours Theirs Emitted block (§8.3)
unchanged none none Resolved(base)
changed edit none Resolved(ours)
changed none edit Resolved(theirs)
changed edit A same edit A Resolved(A) (a false conflict, clean)
changed edit A different edit B Conflict{ours:A, base, theirs:B}

Run on the §8.4 example (base a b c, ours changes b to x, theirs appends d), the regions come out as a, x, c, d with zero conflicts. The result is a list of blocks that exactly partitions the base range (I12), and conflict-marker text is only one renderer of that list (P6, MM6): <<<<<<<, |||||||, =======, >>>>>>> in that order (I13, §18.2 step 6). When history has several merge bases (a criss-cross history), recursive merge first merges the bases into one virtual ancestor, with recursion capped at 256 levels (§18.2 step 3, I14). Ort integrates rename detection into the merge itself instead of running it first (§18.2 step 5). Four identities must hold: merge(base,base,base) and merge(base,x,base) and merge(base,base,x) and merge(base,x,x) all resolve cleanly (§18.4 criterion 2).

Renames are a similarity search after the diff (§19, MM7)

A file-level diff cannot see a rename: a moved file looks like one delete plus one add (§19.2 step 1). So rename detection is a second pass (P10). Each file is cut into overlapping 3-line windows (shingles, §33 item 6), each shingle gets a 64-bit Rabin fingerprint, and two files score by Jaccard similarity, the size of the shared fingerprint set over the size of the combined set (§19.2 step 2, §37). Pairs scoring at least min_similarity (default 50) are sorted by score, and the best unused pair is promoted to a Rename greedily, up to max_pairs (default 1000) (§19.2 steps 4-5, I7). Copies work the same way but allow any file in either tree as the source, and are opt-in and cost more (§19.1, §19.2 step 6). The score is symmetric on purpose, even though "is a copy of" is not (P13).

The cost cap: a typed error instead of a hang (§6 P14, I8, §33 item 5)

Myers has a caller-visible cost_cap, default old_len + new_len (§4). Reaching it returns MyersError::CostBudgetExceeded, never a silently coarser result (I8, P4). The capacity model argues the default alone is not enough for latency (§33 item 5). A 10 MB pair of about 125,000 lines per side with nothing in common has D ≈ 250,000, and the model's worst case of D² ≈ 6.25×10¹⁰ operations at about 10⁹ operations per second is about 60 s. Capping D at 50,000 bounds it to 2.5×10⁹ operations, about 2.5 s, so latency-sensitive callers should lower the cap explicitly. Rename detection has the matching cap in max_pairs (§4, P14). The cap turns a denial-of-service input into an error the caller can handle (T3, MM8). The blueprint gives two formulas for Myers' worst-case time: §33 item 5 uses O(D²), which is where the 60 s and 2.5 s figures come from, while §14.2 step 5 and §30 give O((N+M)·D). It does not reconcile them, and this page does not pick one.

The trade-offs — where engineers disagree

Default algorithm: Myers (ADR-02)

Chosen: Myers O(ND), because it is the universal correctness reference the other algorithms are compared against; --algo exposes the rest (§9). Rejected: patience or histogram as the default. When the rejected choice is right: patience for human-reviewed source diffs in a code-review UI, histogram for log -p-style scans of large histories (§9).

Streaming from day one (ADR-04, P7)

Chosen: streaming mode is first-class in Phase 0, so memory is O(window_size), default 8 MiB, and a 1 GB file does not need a 1 GB allocation (§9, §4, I11). Rejected: slurp-only (read everything into memory). When the rejected choice is right: when every input is guaranteed to be under 10 MB, for example config-file diffing (§9). The price is a second code path with its own benchmarks (P7).

Conflicts as data, not text (ADR-05, P6)

Chosen: a structured Vec<Block>, so editors and review tools read conflicts without parsing marker text (§9, MM6). Rejected: conflict markers only. When the rejected choice is right: a minimal CLI-only tool with no editor or GUI integration ever planned (§9).

Similarity score: Rabin fingerprints over shingles (ADR-06, P13)

Chosen: a 64-bit Rabin fingerprint over shingles, for robustness on whitespace-only changes at similar cost (§9). Rejected: git's line-count heuristic. When the rejected choice is right: when matching git diff -M -C byte for byte outranks whitespace robustness (§9). The blueprint pulls two ways: P13 says the symmetric score lets rename conformance target byte-identity with git, and §19.4 criterion 1 requires byte-identical promotions, yet ADR-06's last column says git's heuristic is the choice for byte-matching. The text does not resolve this.

Primary structured-patch format: RFC 6902 (ADR-07)

Chosen: JSON Patch (RFC 6902), because it keeps array operations and test-then-apply semantics that Merge Patch (RFC 7396) loses (§9, §20.2 step 4). Rejected: RFC 7396 alone. When the rejected choice is right: a config system that only ever needs "apply overrides" (§9).

Owning the algorithms (ADR-10)

Chosen: no third-party diff crate; the project owns its algorithms and treats similar and imara-diff as benchmark targets (§9, §2). Rejected: depending on similar or imara-diff. When the rejected choice is right: a team that needs a diff feature fast and does not need algorithm ownership (§9). A citation quirk: P12 and §2 cite ADR-10 for the conformance-first strategy, but ADR-10's row in §9 is the no-dependency decision; the blueprint leaves both.

A second algorithm for near-identical inputs (ADR-22)

Chosen: Wu O(NP), selected only when a length-ratio check says the inputs are close, because it is faster when the deletion count P is small (§9, §14.2 step 6). Rejected: Myers only. When the rejected choice is right: when input pairs are never near-identical, for example diffing unrelated files, so the specialisation is dead weight (§9).

Roads not taken (§35, §36)

Block-copy diff (§35 A1): slide a rolling hash over the old file and emit COPY and ADD instructions, as xdelta3, bsdiff and VCDIFF do. It wins on near-duplicate large binary blobs where there are no line boundaries. It is rejected as the primary design because line-oriented byte-exactness with git needs edit-graph semantics; it stays as the deferred VCDIFF surface (ADR-08, §36).

CRDT or operational-transform merge (§35 A2): transform concurrent operations into a converged state, as Automerge, Yjs and the Wave OT engine do. It wins for real-time editing with many concurrent writers. It is rejected because live collaborative editing is an explicit non-goal and the project reconciles two finished edits against a common ancestor (§1, §35).

Suffix-array longest common substring (§35 A3): it wins on repeated-substring-heavy corpora such as log deduplication or genomic data, where D is large relative to n. It is rejected as the default because ordinary source diffs have D much smaller than n, which is where Myers' output-sensitive O(ND) is faster (§35).

AST-diff first (§35 A4): parse with tree-sitter and match subtrees by structural hash, as Difftastic does. It wins when a reformatted function should read as "nothing changed". It is rejected as the primary design because it needs a grammar per language and because the conformance goal is defined over text; it stays as the deferred semantic-diff surface (ADR-09, §36).

The deferred register (§36) holds six items, each with an un-defer trigger: the tree-sitter engine, VCDIFF, the Python frontend, the LSP shim, streaming three-way merge (base files over 1 GiB) and secure_apply.

What must never be false

  • I1: EditScript ops are sorted, contiguous and cover both inputs exactly once. Noticed by EditScript::validate() on every algorithm output; dm_edit_script_invalid_total (§7).
  • I2: apply(old, patch) is a pure function of its inputs. A round-trip property test notices it; dm_apply_nondeterminism_total should stay 0 (§7).
  • I3: two runs of diff on the same input give byte-identical scripts. The conformance suite re-run notices it; no runtime metric, only a CI property (§7).
  • I4: Token::eq never reports equal for different bytes. A property test with adversarial hash collisions; dm_hash_collision_total (§7).
  • I5: hunk ranges are 1-based, non-overlapping and ascending. The unified.parse conformance bucket; dm_hunk_order_violation_total (§7).
  • I6: a patch's hunks never overlap and are ordered by start. The apply.exact bucket; a violation becomes ParseError::OverlappingHunks; dm_patch_malformed_total (§7).
  • I7: a rename is promoted only at or above min_similarity. The tree.rename.git_M bucket; dm_rename_below_threshold_total (§7).
  • I8: a Myers cost-cap breach returns CostBudgetExceeded, never a coarser result. The --max-cost CLI flag test; dm_cost_budget_exceeded_total (§7).
  • I9: the no-newline sentinel never counts toward hunk lengths. The unified.emit.git byte-identity bucket; dm_hunk_header_mismatch_total (§7).
  • I10: no panic unwinds across the C boundary. Fuzz targets under ASan; dm_ffi_panic_total, and the caller sees DM_ERR_INTERNAL (§7).
  • I11: streaming-diff memory stays O(window_size). benchmarks/streaming_1gb.rs; the gauge dm_streaming_window_bytes (§7).
  • I12: merge blocks partition the base range exactly once. The merge.weave.git_merge_file bucket; dm_merge_block_gap_total (§7).
  • I13: conflict markers always appear in the order <<<<<<<, |||||||, =======, >>>>>>>. Golden-fixture comparison; dm_marker_order_violation_total (§7).
  • I14: virtual-ancestor recursion is capped, default 256. The three_way fuzz target; the histogram dm_merge_recursion_depth; the error is MergeError::RecursionDepthExceeded (§7).

Each invariant is property-tested on 1000+ random inputs per CI run, naming the ID on failure (§7).

What breaks in production

  • FM1: a diff never returns. An adversarial pair with no common token and no cost cap set. Seen as a wall-clock alert and an outlier in dm_diff_duration_seconds. The default cap catches most cases; the caller sets an explicit cost_cap and retries (§24, I8).
  • FM2: the output is wrong but nothing crashed. A tie-breaker diverges from the spec, or a hash collision is mishandled. The conformance suite reports Fail. There is no automatic recovery; the algorithm is fixed and conformance re-run (§24).
  • FM3: a patch that "should" apply does not. The file changed since the patch was made, so ApplyError::ContextMismatch is raised. apply_fuzzy is retried automatically unless --strict is set; otherwise the caller widens the window or regenerates the patch (§24).
  • FM4: an unexpected number of conflicts. Criss-cross history, CRLF drift or a whitespace policy mismatch. Seen as a spike in dm_merge_conflicts_total. There is no automatic fix; runbook/conflict-storm.md is the triage path (§24).
  • FM5: an obvious rename is missed. Similarity fell below min_similarity, or the max_pairs cap was hit. A logged cap warning or a tree.rename.git_M divergence shows it; the operator lowers the threshold or raises the cap explicitly (§24).
  • FM7: a structured patch corrupts a JSON document. A move or copy whose from is a prefix of its path was not rejected. The json.patch.rfc6902 bucket fails. Recovery is to restore the document from backup and fix the check (§24, §20.2 step 7).
  • FM8: the conformance suite shows a stale pass. The report file was not regenerated after a code change. CI shows the report unchanged despite a source diff; CI regenerates it every run and never caches it across commits (§24).
  • FM9: streaming memory climbs. A bug in the windowed cursor breaks I11. The gauge dm_streaming_window_bytes trends upward; the change is rolled back and a regression fixture added (§24, I11).

Threats a reader should know (§23): T1 malformed unified diffs fed to the parser, answered by bounded reads and typed ParseErrors plus a fuzz target; T3 adversarial inputs that blow up Myers or rename detection, answered by cost_cap and max_pairs; T5 crafted input that collides under xxh3_64 and slows throughput about 10×, answered by a randomised hash_seed at startup, with correctness still protected by I4; T6 a user-controlled JSON Pointer reaching unintended keys, where the library default has no path whitelist and the embedder must validate paths; T7 a panic crossing the FFI boundary, answered by catch_unwind on every dm_* symbol (I10).

How it compares

  • GNU diffutils made line-oriented Myers the default for diff and patch, with no rename or structured support. It wins where POSIX-conformant scripting depends on exact diff -u behaviour (§32).
  • git makes Myers the default, with patience and histogram opt-in and histogram the default for log -p; it does line-count rename similarity and runs rename detection inside merge-ort. It is the reference implementation, which is why this design's conformance strategy agrees with it byte for byte (§32, §22).
  • Google diff-match-patch chose character-level bisection as its main granularity and has no merge tool. That suits latency-sensitive, small-input, interactive editing, which this project does not target (§32, §1).
  • Mercurial chose greedy longest-match in bdiff.c over Myers. It trades provable minimal edit distance for simplicity and speed, which fits "good enough, fast", a trade this design rejects for byte-exact VCS conformance (§32, §4).

If you only remember three things

An edit script is a path through a grid, not "the" diff, so tie-breaking is a design decision and byte-exact agreement with git is what the whole system is tested against (MM1, I3, §4). Every algorithm and every emitter meets at one shared EditScript shape, and every expensive step has a cap that returns a typed error instead of hanging or quietly degrading (P2, P4, P14, I8). A merge is just two diffs plus a walker, with conflicts kept as data and rename detection as a separate pass after the diff (MM3, MM6, MM7).

Words used here

  • Edit script: the algorithm-neutral list of keep, delete, insert and replace operations that turns old into new (EditScript, §11.2).
  • Edit graph: the grid of (i,j) states whose shortest path is a minimum edit script (§8.1).
  • Token: a hashed slice of the input, the smallest unit the algorithms compare (§11.1).
  • Tokeniser: the part that cuts bytes into tokens at byte, line, word or character level (§11.1).
  • Myers algorithm: the O(ND) search for the shortest edit path; D is the edit count (§14).
  • Middle snake: the diagonal where a forward and a reverse search meet, enabling linear-space recursion (§37).
  • Anchor: a line chosen as a fixed match point before recursing into the gaps (§15, §16).
  • Hunk: a contiguous run of changes plus context inside a patch (§11.3).
  • Unified diff: the ---, +++, @@ text patch format (§8.2).
