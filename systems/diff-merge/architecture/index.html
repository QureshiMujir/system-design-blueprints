Per-box notes:

  • CLI/FFI (top): the only two user-facing surfaces; both are thin — every subcommand and every exported symbol maps 1:1 to a library call (P9, §6).
  • diffmerge-core public surface: the sole entry point; nothing downstream of it is reachable except through diff, tree::diff, or json::diff.
  • Tokenisers: orthogonal to algorithms — a Myers diff over byte tokens is the same Myers diff as over line tokens, modulo the equality test (P1, §6).
  • Structured (JSON/XML/YAML): shares the EditScript/patch IR only at the boundary; internally a structural diff, never a text diff over pretty-printed output (P11, §6).
  • Edit-graph algorithms: five algorithms, one EditScript output shape (P2, §6); this is the pluggability seam referenced throughout the document.
  • Patch: the unified-diff renderer/parser/applier; consumes EditScript, never touches tokenisation directly.
  • Three-way merge: built on top of the diff core — two diffs (base→ours, base→theirs) reconciled across hunks (§2).
  • Tree diff / rename+copy: a post-process over a naive per-file tree diff, never a preprocess (P10, §6).
  • Conformance suite: the contract with git (P12, §6); every arrow above ends here at test time.

8. Domain Model / Protocol / Data Model

8.1 The edit graph (grammar of the problem)

For sequences A[0..n], B[0..m]: node (i,j) = "consumed A[0..i], B[0..j]." Horizontal edge = delete from A; vertical edge = insert from B; diagonal edge = match (free, requires A[i]==B[j]). The shortest (0,0)→(n,m) path is the minimum edit script; D = path length minus diagonal steps. Every algorithm in §14–§16 is a different search strategy over this same graph (patience and histogram restrict the graph to anchor-adjacent regions before recursing).

8.2 Unified-diff grammar (EBNF)

patch        = { raw-header-line } file-header { hunk } ;
file-header  = "--- " path newline "+++ " path newline ;
hunk         = hunk-header { hunk-line } ;
hunk-header  = "@@ -" old-start ["," old-len] " +" new-start ["," new-len] " @@" [" " context] newline ;
hunk-line    = ( " " | "-" | "+" ) text newline
             | "\ No newline at end of file" newline ;
raw-header-line = git-index | git-rename | git-copy | new-file | deleted-file | binary-marker ;

old-len/new-len are omitted when they equal 1. old-start/new-start are 0 when the corresponding side is empty. The \ No newline... line is excluded from both length counts (I9, §7).

8.3 Three-way merge state table (weave walk)

Base region Ours diff Theirs diff Emitted Block
unchanged none none Resolved(base_bytes)
changed edit none Resolved(ours_bytes)
changed none edit Resolved(theirs_bytes)
changed edit A edit A (same bytes) Resolved(A) — false conflict, clean
changed edit A edit B (A≠B) Conflict{ours:A, base, theirs:B}

8.4 Worked example

Base: ["a","b","c"]. Ours: ["a","x","c"] (b→x). Theirs: ["a","b","c","d"] (append d). Weave walk: region ["a"] unchanged→Resolved; region ["b"] changed-by-ours-only→Resolved("x"); region ["c"] unchanged→Resolved; region [] (append point) changed-by-theirs-only→Resolved("d"). Merge output: ["a","x","c","d"], zero conflicts — the classic non-overlapping-edit case (§18.5).

8.5 Malformed-input example

Input hunk header @@ -5,3 +5,4 @@ followed by only 2 context/removed lines instead of 3: parse_unified counts consumed old-side lines against old_len from the header; a mismatch at hunk end raises ParseError::HunkLengthMismatch{expected:3, actual:2} rather than silently truncating (I6, §7). Conformance fixture: corpora/apply/exact/malformed-hunk-length/.

8.6 Failure-path example (Khanna–Kunal–Pierce counterexample)

Base: a single line "x". Ours: reorders a surrounding block so "x" shifts up one line without content change. Theirs: independently inserts a line directly above "x"'s original position. Classic diff3 walk sees both diffs as non-overlapping (different line ranges) and emits a clean merge — but the result misplaces the inserted line relative to the reordered block, an intent violation invisible to a line-oriented three-way merge (Khanna, Kunal, Pierce 2007, §5). This blueprint accepts the wrong-but-clean output (documented, not silently absorbed) and records the fixture in docs/three-way-merge.md; ADR-05 (§9) is where the conflict-shape decision that makes divergence visible rather than silent is recorded.

Design principles (§6)

  • Bytes are the substrate. Every algorithm operates on &[u8], encoding-agnostic at the core; UTF-8 awareness is a tokeniser property, not an engine property. Tradeoff: byte-level generality costs a hash computation per token. Operational implication: the same engine handles binary VCDIFF (deferred, §17.2) and UTF-8 source with no code fork. Violate it and binary-safety silently breaks the day someone adds a "smart" encoding check inside the algorithm.
  • One IR, many algorithms, many emitters. EditScript is the sole contract between any diff algorithm and any patch emitter (I1, §7). Tradeoff: the IR must be conservative enough to represent five algorithms' outputs uniformly. Operational implication: adding histogram next to Myers never touches the patch path. Violate it and every new algorithm requires a matching emitter change — an O(algorithms × emitters) maintenance surface instead of O(algorithms + emitters).
  • Determinism is the default. Two runs over the same (old, new, opts) produce byte-identical output regardless of OS, CPU, or thread count (I3, §7). Tradeoff: tie-breaking rules must be specified and tested, not left to hash-map iteration order. Operational implication: conformance tests are reproducible across CI runners. Violate it and the conformance suite becomes flaky, masking real regressions (MM4, §31).
  • No silent fallbacks between algorithms. Patience descending to Myers on an unmatched region is the algorithm, not a fallback; a Myers cost-cap breach returns an error, never a silent coarser tokenisation (I8, §7). Tradeoff: callers must handle CostBudgetExceeded explicitly. Operational implication: a slow diff surfaces as a typed error the caller can retry with different opts, not as a silently wrong result. Violate it and a denial-of-service input (§23 T3) becomes a silent correctness bug instead of a visible one.
  • Patches are typed, not stringly typed. Patch is Vec<Hunk>; unified-diff text is a render of Patch, never the internal representation (§11). Tradeoff: an extra parse/emit round-trip for every text interaction. Operational implication: the merge and apply engines consume Patch, so a text-format quirk fix never touches merge logic. Violate it and text-format parsing bugs leak into merge correctness.
  • Conflicts are first-class values. MergeResult is Vec<Block>, each Resolved or Conflict{ours,base,theirs} (I12, §7); the marker-text rendering is one renderer among many. Tradeoff: an extra type layer versus emitting markers directly. Operational implication: a review-tool embedder consumes structured conflicts, never re-parses marker text (MM6, §31). Violate it and every consumer needs its own marker parser — an inherently lossy round-trip.
  • Streaming over slurping where the algorithm allows. A 1 GB line diff must not require a 1 GB allocation; the line iterator is lazy; the streaming Myers variant holds only the diagonal arrays it needs. Tradeoff: streaming mode is a second code path with its own benchmark suite. Operational implication: memory stays O(window_size) regardless of input size (§4, §33). Violate it and the toolkit cannot diff anything larger than available RAM.
  • Performance is a property of the algorithm, not the implementation. A correct Myers in Rust is competitive with a correct Myers in C; the benchmark suite locks algorithm-level baselines before micro-optimisation. Tradeoff: early phases spend time on criterion benchmarks before the CLI exists. Operational implication: perf regressions are caught at the algorithm level, not masked by implementation noise. Violate it and engineering effort chases the wrong bottleneck.
  • The CLI is a thin wrapper over the library. Every dm subcommand maps 1:1 to a library call; the CLI implements zero algorithm logic. Tradeoff: some CLI ergonomics (progress bars, colour) must live at the boundary, not inside the library. Operational implication: the library's test suite is the CLI's test suite by construction. Violate it and library and CLI behaviour drift apart (MM-class bug: "works in the CLI but not via the library API").
  • Rename and copy detection are post-processes, not preprocesses. A tree diff first computes file-level deltas assuming names match; a similarity-index pass then promotes delete+add pairs to renames/copies (MM7, §31). Tradeoff: two passes over the tree diff instead of one. Operational implication: rename detection can be toggled cheaply at the CLI (--find-renames) without touching the diff core. Violate it and rename logic entangles with the per-file diff, breaking principle 2.
  • Structured diffs are not text diff with extra steps. A JSON patch is a structural operation over a document tree, not a unified diff over pretty-printed text; JSON/XML/YAML share the EditScript-adjacent IR concept but not the algorithm. Tradeoff: three separate structural-diff implementations instead of one text-diff reuse. Operational implication: whitespace/key-ordering changes never appear as spurious structured-patch operations. Violate it and every reformat looks like a content change.
  • The conformance suite is the contract with git. Wherever the toolkit emits a unified diff, three-way merge, rename detection, or patience/histogram output, conformance asserts byte-identity (or documented divergence) against the corresponding git invocation (ADR-10, §9; §22). Tradeoff: the corpus must be built and maintained before algorithms are "done." Operational implication: divergence is a tracked, named artifact (divergences.md), never silently absorbed. Violate it and the toolkit drifts from the ecosystem's de-facto reference with no visibility.
  • The similarity index is symmetric by design, matching git. SimilarityIndex::jaccard is a symmetric score even though "is this a copy of" is intuitively asymmetric (ADR-06, §9). Tradeoff: a one-way Tversky-style score would better match intuition but would diverge from git's rename output. Operational implication: rename/copy conformance (§19.5) can target byte-identity with git. Violate it and rename promotions silently disagree with git diff -M -C with no clear root cause.
  • A cost cap is a correctness feature. Every algorithm with unbounded worst-case cost (Myers, rename detection's pairwise comparison) exposes a caller-visible cap that fails loudly rather than degrading silently (I8, §7; T3, §23). Tradeoff: pathological-but-legitimate inputs occasionally need the caller to raise the cap explicitly. Operational implication: algorithmic-complexity attacks (§23) become typed errors, not hangs. Violate it and a single adversarial input can stall the whole pipeline with no operator signal.
