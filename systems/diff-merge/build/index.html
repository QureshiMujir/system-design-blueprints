⬜ Phase 0 — Skeleton, Governance & Tokeniser Contracts §12

Objectives
  • Land the full repository layout (§10) from a single commit.
  • Land Token, EditOp, EditScript, Patch, Hunk, HunkLine (§11) as compiling signatures.
  • Prove the round-trip contract apply(old, parse(emit(diff(old,new)))) == new with a trivial algorithm.
  • Wire CI (ci.yml) to fail on cargo clippy -D warnings and cargo test.
Deliverable

make bootstrap && make build && make test && make lint all exit 0 on a clean clone; dm binary compiles (subcommands stubbed).

Acceptance
  1. make test passes 3 named fixtures: empty/, one-line/, five-line/ (round-trip equality).
  2. make lint passes cargo clippy --all-targets --all-features -- -D warnings with zero warnings.
  3. EditScript::validate() rejects a hand-constructed script violating I1 in a unit test.
  4. conformance/runner runs and emits conformance.report.json with every bucket Deferred except the round-trip bucket, which is Pass.
Fixtures
Fixture Purpose Expected Output
corpora/diff/git-default/empty/{old,new}.txt round-trip on empty input apply(parse(emit(diff)))==new, both empty
corpora/diff/git-default/one-line/{old,new}.txt single-line change round-trip equality
corpora/diff/git-default/five-line/{old,new}.txt multi-line change round-trip equality
Pitfalls
  • The \ No newline at end of file sentinel (I9, §7) is a silent killer if bolted on later — account for it from HunkLine::NoNewlineAtEof on day one.
  • CRLF vs LF is a separate axis from "line" — the Phase-0 line tokeniser (landed fully in §13) must not normalise; document the policy now so §13 doesn't silently change behaviour.
  • Patch must stay externally immutable (&Patch) even though emission internally folds Delete+Insert — getting the mutability boundary wrong here creates aliasing bugs discovered only in §17.

⬜ Phase 1 — Tokenisers §13

Objectives
  • Implement LineTokeniser, ByteTokeniser, WordTokeniser, CharTokeniser against the Tokeniser trait (§11.1).
  • Match git diff --word-diff's tokenisation rule byte-for-byte for WordTokeniser.
  • Register Granularity::Token (tree-sitter) as an explicit deferred variant, not a silent omission.
Deliverable

Tokeniser trait + four implementations, each passing its named conformance fixtures; a criterion benchmark (diffmerge-bench/benches/myers.rs, extended in §14) that includes tokeniser cost in its measurement.

Acceptance
  1. tokeniser.line / .byte / .word / .char conformance buckets all Pass (§13.5 table).
  2. Property test: decode_lines(tokenise_lines(x)) == x for every byte string x < 64 KiB, 10,000 random cases.
  3. LineTokeniser throughput ≥ 1 GB/s on the linux-kernel-snapshot corpus (M1, §29).
  4. WordTokeniser output matches git diff --word-diff byte-for-byte on a 50-fixture corpus.
Fixtures
Fixture Purpose Expected Output
corpora/tokeniser/line/*.in line splitting Vec<line> serialised as JSON, byte-identical
corpora/tokeniser/byte/*.in 1:1 byte mapping one token per input byte
corpora/tokeniser/word/*.in word splitting matches git diff --word-diff
corpora/tokeniser/char/*.in UTF-8 boundaries includes an invalid-UTF-8 fixture and a Latin+CJK+emoji-ZWJ mixed-script fixture
Pitfalls
  • The \r\n problem: git diff treats \r as part of the line by default; we match that and document the deviation from core.whitespace=trailing-cr.
  • The empty-input case: tokenising b"" must return vec![], not a single empty token — a common off-by-one in naive implementations.
  • The byte tokeniser interacts badly with patience (§15): every byte is a candidate anchor, degenerate. Document and recommend the line tokeniser for patience.
  • Hash collisions on highly repetitive input (a million identical lines) are not a correctness issue (I4, §7 tie-breaks on bytes) but can quadratically degrade performance if the hash table's buckets fill — mitigated by ahash (step 7, §13.2).

⬜ Phase 2 — Myers O(ND) and the Linear-Space Middle-Snake §14

Objectives
  • Implement the forward furthest-reaching-path search over the edit graph (§8.1) per Myers 1986 §2, §4.
  • Implement the linear-space refinement via bidirectional middle-snake recursion.
  • Implement Wu O(NP) (Wu et al. 1990) and Hunt-McIlroy LCS (Hunt & McIlroy 1976) as cross-verifiers.
  • Enforce the cost-cap escape valve (I8, §7; P4, §6) on every entry point.
Deliverable

myers_forward, myers_linear, wu_onp, hunt_mcilroy all present, cross-verified, and selectable via AlgorithmId; a criterion report for Myers on the reference corpus.

Acceptance
  1. Cross-algorithm property test passes 1000/1000 cases (§14.2 step 8).
  2. Myers throughput ≥ 1 GB/s on unchanged regions, ≥ 100 MB/s on 10%-changed workload (M1/M2, §29), measured on linux-kernel-snapshot.
  3. myers_forward returns MyersError::CostBudgetExceeded (not a panic, not a wrong result) on an adversarial 10 MB no-common-token pair with cost_cap = 50,000 (derived in §33).
  4. wu_onp and myers_linear produce equivalent (apply-equal) scripts on 500 near-identical-file fixtures (|n-m|<5%).
Fixtures
Fixture Purpose Expected Output
algo.myers.roundtrip (1000 random pairs) correctness apply(old, emit(myers(old,new)))==new
algo.wu_onp.equivalent cross-check Wu and Myers scripts apply-equal
corpora/diff/adversarial/no-common-tokens/ cost-cap enforcement CostBudgetExceeded, no hang
corpora/diff/git-default/* (100 fixtures) git conformance byte-identical to git diff --no-color (used again in §17)
Pitfalls
  • Off-by-one in the V-array indexing convention (V[k+offset], never raw negative k) — test explicitly at D=0,1,2.
  • Middle-snake recursion can stack-overflow on adversarial input (a million identical lines); cap recursion depth (4096) and convert to an explicit work queue past that.
  • Forward/reverse passes use opposite-parity k — get this wrong and the middle snake never converges (silent infinite loop, caught only by the cost cap).
  • Token::eq falls back to byte equality on hash collision (I4, §7); comparing raw u64 hashes directly silently produces wrong diffs on collisions.
  • wu_onp requires n≥m (delete from the longer side); reversed inputs must be swapped at entry and the script reflected at exit.

⬜ Phase 3 — Patience Diff §15

Objectives
  • Implement unique-common-line anchor detection and LIS-based anchor selection (patience-sort, Cohen 2007).
  • Recurse on unmatched regions, descending to Myers (§14) when no anchors exist.
  • Match git diff --patience byte-for-byte on a 100-fixture corpus, or document divergence.
Deliverable

patience() producing conformant EditScripts; a criterion benchmark on chromium-source-pair; the --algo patience CLI path functional (stub CLI from §12, wired here).

Acceptance
  1. algo.patience.git ≥ 95/100 fixtures byte-identical to git diff --patience (documented divergence for the rest, per fixture, in divergences.md).
  2. Property test: apply(old, patience(old,new)) == new for every corpus pair (I2, §7).
  3. Patience wall-clock ≤ 2× Myers on chromium-source-pair (M6, §29).
  4. A degenerate all-identical-lines input (1000 blank lines) falls through entirely to Myers with zero anchors found, verified by a unit test asserting anchors.is_empty().
Fixtures
Fixture Purpose Expected Output
corpora/diff/git-patience/* (100 fixtures) git byte-identity matches git diff --patience --no-color or documented divergence
corpora/diff/patience/degenerate-identical/ fallback path falls through to Myers, zero anchors
corpora/diff/patience/duplicate-anchors/ uniqueness condition a line unique in old but duplicated in new is NOT an anchor
Pitfalls
  • "Unique" means unique in both files — a line unique in old but duplicated in new is not an anchor; a common bug is checking only one side.
  • The recursive descent can produce a different (but equally valid) result from Myers on the same sub-region — this is correct, not a bug; the conformance corpus tolerates it as long as the script is valid (I1, §7).
  • Empty regions on one side must emit Delete/Insert directly, never recurse into an empty slice — recursing wastes a call and can mis-order offsets.
  • Multiple optimal LIS solutions exist for degenerate anchor sets — git's tie-breaker (lexicographically smallest (old_idx,new_idx)) must be matched exactly (I3, §7) or conformance silently fails on tie-heavy fixtures.

⬜ Phase 4 — Histogram Diff §16

Objectives
  • Implement histogram-based anchor selection (least combined token count) per libxdiff's xhistogram.c (§5 reference impl).
  • Match git diff --histogram byte-for-byte on a 100-fixture corpus, replicating libxdiff's max_chain early-exit exactly.
  • Compare Myers/patience/histogram throughput on one shared benchmark corpus.
Deliverable

histogram() producing conformant EditScripts selectable via --algo histogram; comparative benchmark report across all three text algorithms.

Acceptance
  1. algo.histogram.git ≥ 95/100 fixtures byte-identical to git diff --histogram (documented divergence for the rest).
  2. Histogram wall-clock ≤ 1.5× Myers on chromium-source-pair (M7, §29).
  3. Property test: apply(old, histogram(old,new)) == new for every corpus pair (I2, §7).
  4. max_chain override test: setting max_chain=4 produces a documented-different (not wrong) output on a high-duplication fixture, proving the cap is load-bearing.
Fixtures
Fixture Purpose Expected Output
corpora/diff/git-histogram/* (100 fixtures) git byte-identity matches git diff --histogram --no-color or documented divergence
corpora/diff/histogram/no-common-token/ fallback path falls through to Myers
corpora/diff/histogram/max-chain-boundary/ cap behaviour a token at exactly max_chain count is included; max_chain+1 is excluded
Pitfalls
  • max_chain is the O(N²)-vs-O(N log N) lever (libxdiff default 64) — document the chosen value in code comments; test overriding it.
  • Histogram's anchor selection differs from patience's, so the two can produce different edit scripts on the same input — conformance must compare against git's histogram output specifically, never against patience's output.
  • The "chain too long" early-exit must fire during the histogram build (step 6, §16.2), not as a post-filter — get the timing wrong and byte-identity with git silently fails on high-duplication fixtures.
  • Empty or single-line inputs should short-circuit before calling best_histogram_split at all — calling it anyway is correct but wastes a call.

⬜ Phase 5 — Unified-Diff Emitter, Parser, and Patch Applier §17

Objectives
  • Implement hunk grouping with configurable context (default 3 lines, --unified=N).
  • Implement emit_unified/parse_unified covering git's extended raw header (renames, copies, mode changes, binary marker).
  • Implement apply_exact and apply_fuzzy (±50-line window, context-match scoring).
Deliverable

emit_unified, parse_unified, apply_exact, apply_fuzzy in source; dm diff and dm apply functional on the CLI (thin wrapper, P9 §6).

Acceptance
  1. unified.emit.git ≥ 99/100 fixtures byte-identical to git diff --no-color (M14, §29).
  2. apply.exact passes 100% of its named fixtures (§17.5); apply.fuzzy matches patch -F3 output on 50 fixtures.
  3. Round-trip property test: apply(old, parse(emit(diff(old,new)))) == new for every corpus pair.
  4. A hunk-length mismatch (§8.5) raises ParseError::HunkLengthMismatch with the expected/actual counts in the error, verified by a named unit test.
Fixtures
Fixture Purpose Expected Output
corpora/diff/git-default/* (100 fixtures) emitter byte-identity matches git diff --no-color
corpora/apply/exact/* exact apply produces expected output byte-for-byte
corpora/apply/exact/malformed-hunk-length/ malformed input (§8.5) ParseError::HunkLengthMismatch{expected,actual}
corpora/apply/fuzzy/* (50 fixtures) fuzzy apply matches patch -F3 output
corpora/apply/no-newline-eof/ I9 regression header arithmetic excludes the sentinel line
Pitfalls
  • The \ No newline at end of file sentinel is line-number-significant (I9, §7): omitted from OLD_LEN/NEW_LEN; getting this wrong shifts every subsequent hunk header by one.
  • Context lines start with a single space, not a tab; a file that legitimately starts with a single space creates an ambiguous parse resolved only by header arithmetic — mirror git exactly.
  • Renames with trailing edits: the extended header announces the rename; the hunks describe edits inside the renamed file. apply_exact must rename first, edit second, or the target path is wrong.
  • git emits Binary files a/foo and b/foo differ by default; --binary emits a binary delta (VCDIFF territory, deferred PhaseDeferred §17.2) — Phase 5 handles only the textual sentinel.

⬜ Phase 6 — Three-Way Merge §18

Objectives
  • Implement weave merge: two diffs (base→ours, base→theirs) reconciled per the state table (§8.3).
  • Implement recursive merge: virtual-ancestor computation for criss-cross histories, depth-capped (I14, §7).
  • Implement ort-style merge: rename detection integrated into the merge phase rather than as a preprocess.
  • Implement conflict-marker rendering matching git's merge.conflictStyle=diff3 output.
Deliverable

three_way_weave, three_way_recursive, three_way_ort in source; dm merge BASE OURS THEIRS --style {weave,recursive,ort} functional on the CLI.

Acceptance
  1. merge.weave.git_merge_file ≥ 195/200 fixtures byte-identical to git merge-file --diff3 (M15, §29).
  2. Conformance identities (I2 §7-style, per §11.4's Merge contract): merge(base,base,base)→Resolved(base); merge(base,x,base)→Resolved(x); merge(base,base,x)→Resolved(x); merge(base,x,x)→Resolved(x) — all four hold on 50 generated fixtures each.
  3. Recursive merge on a synthetic criss-cross fixture with 3 merge bases produces a result matching git merge-recursive's output or a documented divergence.
  4. Recursion depth cap fires (MergeError::RecursionDepthExceeded) on a synthetic 300-deep criss-cross fixture, never silently truncating.
Fixtures
Fixture Purpose Expected Output
corpora/merge/git-merge-file/* (200 fixtures) weave byte-identity matches git merge-file --diff3 or documented divergence
corpora/merge/git-merge-recursive/* criss-cross matches git merge-recursive or documented divergence
corpora/merge/git-ort/* ort semantics matches git merge-ort or documented divergence
corpora/merge/khanna-kunal-pierce/ known-wrong-but-clean case (§8.6) accepted divergence, recorded in docs/three-way-merge.md
corpora/merge/criss-cross-deep/ recursion cap RecursionDepthExceeded at depth 257
Pitfalls
  • The Khanna-Kunal-Pierce counterexample (§5, §8.6) produces a clean merge that violates intent — accept and document, never silently "fix" without a documented tradeoff.
  • Criss-cross detection requires the commit graph as input; the library does not walk git history — the CLI's dm merge uses git2 when run inside a repository (§1 delegation boundary).
  • Recursive merge can recurse arbitrarily deep on pathological histories — the depth cap (default 256, I14 §7) must return an error, never silently degrade to a single-base merge.
  • The ||||||| block must render before ======= and after <<<<<<< — several first-attempt implementations get this ordering wrong (I13, §7).
  • The merge-base algorithm itself is out of scope (§1); accepting merge bases as caller-supplied input is a boundary, not a shortcut.

⬜ Phase 7 — Tree Diff and Rename/Copy Detection §19

Objectives
  • Implement the naive tree diff (path-set difference + per-file Modify).
  • Implement similarity-index-based rename detection as a post-process (P10, §6).
  • Implement copy detection (opt-in, higher cost than rename detection).
Deliverable

tree_diff_naive, detect_renames, detect_copies in source; dm tree-diff OLD_DIR NEW_DIR --find-renames --find-copies functional; output round-trips through git apply --binary.

Acceptance
  1. tree.rename.git_M and tree.copy.git_C both Pass on the 50-fixture corpus (byte-identical rename/copy promotions to git diff -M -C).
  2. Rename-detection benchmark on a 10,000-file tree completes in < 5 s wall-clock (M9, §29).
  3. A pair count exceeding max_pairs emits an explicit warning (not a silent truncation) — verified by a unit test asserting the warning is logged.
  4. TreeOp::ModeChange is detected and distinct from TreeOp::Modify on a chmod-only fixture.
Fixtures
Fixture Purpose Expected Output
corpora/tree/rename/* (50 fixtures) rename promotion matches git diff -M50
corpora/tree/copy/* copy promotion matches git diff -C
corpora/tree/mode-change/ mode-only change TreeOp::ModeChange, no Modify
corpora/tree/rename-with-edits/ rename + content change TreeOp::Rename{patch: Some(_)}, rename-then-edit order
corpora/tree/pair-cap-exceeded/ max_pairs cap warning logged, pairs beyond cap dropped, never force-promoted
Pitfalls
  • The default threshold (-M50) matches a half-rewritten file; a lower threshold (e.g. -M30) catches more renames but produces false positives — document the tradeoff, never silently change the default.
  • Copy detection's quadratic cost (every Add against every file in both trees) is not optional to bound — cap the pair count and warn when the cap is hit (I7, §7).
  • Mode changes are invisible to the naive tree diff (step 1, §19.2) — a separate detection pass is required, not an afterthought.
  • The Jaccard score is symmetric; a one-way (Tversky-style) score would better match "is this a copy of" intuition but would diverge from git — documented in ADR-06 (§9), matched intentionally.
  • Rename-then-edit ordering: applying the content patch before the rename targets the wrong (old) path.

⬜ Phase 8 — Structured Patches: JSON, XML, YAML §20

Objectives
  • Implement RFC 6902 JSON Patch diff/apply.
  • Implement RFC 7396 JSON Merge Patch diff/apply.
  • Implement heuristic structural diff for XML and YAML, documenting information loss (YAML comments).
Deliverable

JsonPatch::{diff,apply}, JsonMergePatch::{diff,apply}, XmlDiff::diff, YamlDiff::diff in source; dm json-diff and dm json-merge-diff CLI subcommands.

Acceptance
  1. json.patch.rfc6902 and json.merge.rfc7396 both Pass against the RFC example vectors plus the jsonpatch.com test suite (≥ 100 combined cases).
  2. xml.diff and yaml.diff.structural Pass (structural-equivalence assertion, not byte-identity — XML/YAML lack a normative single-diff reference) on 30 fixtures each.
  3. A move with from a prefix of path returns a typed error on 100% of a 10-fixture self-move corpus, never corrupting the document.
  4. JSON Pointer escape round-trip (~0/~1) passes on a path containing both a literal ~ and a literal / in a key name.
Fixtures
Fixture Purpose Expected Output
corpora/json-patch/* (RFC 6902 + jsonpatch.com) apply correctness apply(target,patch)==expected
corpora/json-merge/* (RFC 7396 + 50 hand-rolled) merge-patch correctness null-removal, nested-null, array-replacement fixtures
corpora/xml/* (30 fixtures) structural diff expected XmlOp sequence
corpora/yaml/* (30 fixtures) structural diff, comments stripped documented limitation, structural equivalence only
corpora/json-patch/self-move-rejected/ move into itself typed error, not corruption
Pitfalls
  • JSON Pointer escape order: decode ~1→/ before ~0→~, or a key containing both is misparsed (RFC 6901 §5).
  • test's value comparison must be structural/deep, not stringly — 42 and 42.0 may or may not compare equal depending on the JSON number model; document the chosen behaviour (equal) explicitly.
  • Array index boundaries: remove at index 5 of a 5-element array is an error; add at index - (the special "end" token) appends — both covered by the corpus (§20.5).
  • move/copy self-containment (from a prefix of path) must be rejected, not silently applied (§20.4 criterion 3).
  • XML's element-matching is heuristic — the same document pair can have multiple equally valid diffs; the conformance corpus accepts any structurally valid output since XML lacks a normative reference diff.
  • YAML's anchor/alias system means the same data has multiple valid encodings — serde_yaml's canonicalisation is the documented, non-negotiable choice (not an omission).

⬜ Phase 9 — CLI and C ABI §21

Objectives
  • Ship dm diff/apply/merge/json-diff/tree-diff with a 1:1 mapping to library calls.
  • Ship a panic-safe C ABI via cbindgen-generated header.
  • Register the Python frontend and LSP shim as explicit deferred surfaces, not silent gaps.
Deliverable

dm CLI with all five subcommands documented; diffmerge.h generated and stable; make examples-c builds and runs a linked C client.

Acceptance
  1. Every dm subcommand's behaviour matches its underlying library call byte-for-byte on the same fixture (CLI/library parity test, 20 fixtures across all five subcommands).
  2. make examples-c builds and runs with exit code 0 on the reference platform (§4).
  3. Zero panics escape the FFI boundary across the full fuzz/fuzz_targets/* corpus run for 60 s each (make fuzz-quick) — verified by catch_unwind coverage, not by absence of crashes alone.
  4. CLI exit codes follow diff(1): 0/1/2 for no-diff/diff-found/error, verified against 10 named fixtures.
Fixtures
Fixture Purpose Expected Output
examples/diff-two-files.rs (+ CLI equivalent) CLI/library parity identical output both paths
examples/three-way-merge.rs CLI/library parity identical output both paths
corpora/ffi/panic-injection/ FFI panic safety DM_ERR_INTERNAL, process survives
corpora/cli/exit-codes/* (10 fixtures) exit-code convention 0/1/2 matching diff(1)
Pitfalls
  • clap's derive style is verbose but the maintenance cost of hand-rolled argument parsing is higher — accept the verbosity (ADR-12, §9).
  • FFI panic safety: every entry point must wrap in catch_unwind; missing even one is a silent UB risk discovered only under fuzzing (T7, §23).
  • Memory ownership across FFI: returning Rust-allocated memory expecting free(3) on the C side is a use-after-free/double-free hazard — dm_buffer_free is the only correct release path.
  • cbindgen's output is sensitive to feature flags; an unlocked feature set can leak internal-only types into the public header.

Pitfalls
  • A Deferred bucket silently miscounted as Pass would mask incomplete coverage — the schema (step 1, §22.2) requires cases_deferred to be explicit and non-zero for a genuinely deferred bucket.

  • A regression in any bucket (Pass→Fail) must block merge in CI — a soft-fail (warning-only) config silently erodes the conformance guarantee (P12, §6).
