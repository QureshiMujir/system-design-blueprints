31. Mental Models & First Principles

  • MM1 — An edit script is a path through an edit graph, not "the" diff between two strings. Predicts: two edit scripts of equal cost can differ in shape; tie-breaking is a real design decision, not an implementation detail. Bug class without it: assuming diff output is unique and building tooling that breaks the moment a tie-breaker changes. Applies at §14.
  • MM2 — Uniqueness (not proximity) is what makes a diff human-readable. Patience and histogram both hinge on this; "proximity-based" heuristics (e.g., preferring nearby matches) do not explain why either algorithm outperforms Myers on code review. Bug class without it: trying to improve diff readability by tuning context-line counts instead of anchor selection. Applies at §15, §16.
  • MM3 — A three-way merge is two diffs reconciled, not a new algorithm. The entire weave/recursive/ort family is diff (§14) plus a walker plus a conflict policy. Bug class without it: reimplementing merge logic from scratch instead of composing two diff() calls with a reconciliation pass. Applies at §18.
  • MM4 — Determinism is a property you test for, not one you get for free. Hash-table iteration order, thread scheduling, and tie-breaking all threaten it silently. Bug class without it: a flaky conformance suite that "sometimes" byte-matches, wasting debugging time on phantom regressions. Applies at §7, §27.
  • MM5 — The tokeniser is a silent correctness boundary. Most "algorithm bugs" reported against a diff tool are actually tokeniser drift (CRLF handling, empty-input edge cases). Bug class without it: chasing a Myers/patience bug for hours that is actually a one-line tokeniser fix. Applies at §13, §9.
  • MM6 — A conflict is data, not text. Treating MergeResult as structured means every consumer (marker renderer, editor UI, review tool) is a projection of one source of truth, never a re-parse of another projection. Bug class without it: parsing your own rendered conflict markers back into structured form — an inherently lossy round-trip. Applies at §11, §18.
  • MM7 — Rename detection is a similarity search over a bipartite graph, not a special case of diff. Deletes and adds form the two sides of the graph; similarity score is the edge weight; the promotion is a greedy matching. Bug class without it: trying to detect renames inside the per-file diff instead of as a tree-level post-process, entangling two orthogonal concerns. Applies at §19, §6 (P10).
  • MM8 — A cost cap is a correctness feature, not a performance knob. It converts "the algorithm might run forever/OOM" into "the caller gets a typed error and decides." Bug class without it: silently downgrading tokenisation or truncating input on a slow case instead of surfacing the budget breach — invisible correctness erosion under load. Applies at §6 (P4), §23.

5. Required Reading

Books

  • Gusfield, D. 1997. Algorithms on Strings, Trees, and Sequences. Cambridge University Press. Ch. 11 (dynamic-programming LCS, Hunt–Szymanski speedup). Extract: the DP recurrence that Myers' edit graph generalises. Applied in §14.
  • Crochemore, M. & Rytter, W. 2003. Jewels of Stringology. World Scientific. Ch. 6 (edit distance, LCS, approximate matching). Extract: the formal relationship between edit distance and LCS length. Applied in §14, §15.
  • Cormen, T., Leiserson, C., Rivest, R., Stein, C. Introduction to Algorithms, 3rd ed. MIT Press. Ch. 15 (Dynamic Programming), §15.4 LCS. Extract: the canonical O(nm) DP baseline every faster algorithm in §14 improves on. Applied in §14.
  • Apostolico, A. & Galil, Z. (eds.). 1997. Pattern Matching Algorithms. Oxford University Press. The edit-distance / approximate string matching chapters. Extract: the taxonomy of output-sensitive vs input-sensitive algorithms that motivates Wu O(NP) alongside Myers. Applied in §14.
  • Chacon, S. & Straub, B. Pro Git, 2nd ed. Apress (free at git-scm.com/book). Ch. 7 (Git Tools: advanced merging, rerere), Ch. 10 (Git internals: plumbing, blobs, trees). Extract: the tree/blob/commit model rename detection and tree diff (§19) operate over. Applied in §18, §19.
  • Loeliger, J. & McCullough, M. 2012. Version Control with Git, 2nd ed. O'Reilly. Ch. 7 (branching/merging strategies), Ch. 19 (git internals). Extract: how merge-recursive and merge-ort differ operationally. Applied in §18.

Papers

  • Myers, E. W. 1986. An O(ND) Difference Algorithm and Its Variations. Algorithmica 1(1):251–266. The foundational paper for line-by-line diff: the edit graph, the furthest-reaching-D-path insight, the linear-space middle-snake refinement. Applied in §14.
  • Hunt, J. W. & McIlroy, M. D. 1976. An Algorithm for Differential File Comparison. Bell Labs Computing Science Technical Report #41. The original diff(1) algorithm; the LCS-based formulation Myers later improved on; the weave-merge algorithm. Applied in §14, §18.
  • Wu, S., Manber, U., Myers, G., Miller, W. 1990. An O(NP) Sequence Comparison Algorithm. Information Processing Letters 35(6):317–323. Faster than Myers when P (deletion count) is small. Applied in §14.
  • Tichy, W. F. 1984. The String-to-String Correction Problem with Block Moves. ACM Transactions on Computer Systems 2(4):309–321. The edit-script formulation with block moves; explains why block moves are not part of the unified-diff format. Applied in §17, §35.
  • Hirschberg, D. S. 1975. A Linear Space Algorithm for Computing Maximal Common Subsequences. Communications of the ACM 18(6):341–343. The linear-space divide-and-conquer trick generalised by Myers' middle snake. Applied in §14.
  • Heckel, P. 1978. A Technique for Isolating Differences Between Files. Communications of the ACM 21(4):264–268. An alternative diff formulation using unique-line matching, a direct ancestor of patience diff's anchor selection. Applied in §15.
  • Aho, A. V., Hirschberg, D. S., Ullman, J. D. 1976. Bounds on the Complexity of the Longest Common Subsequence Problem. Journal of the ACM 23(1):1–12. Lower bounds on LCS computation; explains why no sub-quadratic general algorithm exists without extra structure. Applied in §14, §33.
  • Khanna, S., Kunal, K., Pierce, B. C. 2007. A Formal Investigation of Diff3. FSTTCS 2007. Proves diff3 correct under specific assumptions and exhibits counterexamples where it silently produces a clean-but-wrong merge. Applied in §18, §8.
  • Mens, T. 2002. A State-of-the-Art Survey on Software Merging. IEEE Transactions on Software Engineering 28(5):449–462. Survey of merge strategies (textual, structural, semantic); situates weave/recursive/ort in the broader taxonomy. Applied in §18, §32.

Reference Implementations

  • libxdiff (vendored in git's tree, xdiff/): xprepare.c (line tokenisation, hash table), xdiffi.c (Myers core), xhistogram.c (histogram diff), xmerge.c (three-way merge), xemit.c (unified-diff emit). Lesson: the tokeniser is older and faster than most blog-post descriptions; the max_chain early-exit is load-bearing for byte-identity. Pitfall not to copy: its C-style manual memory management does not translate to idiomatic Rust ownership. Applied in §13, §14, §16, §17.
  • git source tree: merge-recursive.c (recursive virtual ancestor), merge-ort.c (2.34+ replacement), diffcore-rename.c (rename detection), diffcore-break.c, diffcore-pickaxe.c. Lesson: merge-ort integrates rename detection into the merge phase rather than running it as a preprocess. Pitfall not to copy: git's merge-base graph walk is out of this project's scope (§1) — treat merge bases as caller-supplied input. Applied in §18, §19.
  • Mercurial source tree: mercurial/mdiff.py, mercurial/bdiff.c. Lesson: bdiff.c implements a greedy longest-match diff distinct from Myers, useful as a third independent cross-check for conformance divergence triage. Pitfall not to copy: its Python/C split is an artifact of Mercurial's history, not a design to emulate. Applied in §22, §32.
  • Difftastic (https://github.com/Wilfred/difftastic, Wilfred Hughes): src/diff/changes.rs, src/parse/syntax.rs. Lesson: AST-node hashing that ignores whitespace/comments is what makes structural diff readable. Pitfall not to copy: a grammar-per-language dependency is a large maintenance surface, deliberately deferred (§13.2). Applied in §13, §35.
  • similar crate (Armin Ronacher, https://github.com/mitsuhiko/similar): src/algorithms/myers.rs. Lesson: the cleanest existing Rust translation of Myers; used as a benchmark target, never a dependency (ADR-10, §9). Applied in §14, §22.
  • imara-diff crate (Pascal Kuthe, https://github.com/pascalkuthe/imara-diff): a fast Rust histogram-diff implementation. Lesson: arena-allocated token tables outperform per-token heap allocation at scale. Applied in §16.

RFCs / Specifications

  • RFC 3284 (2002). The VCDIFF Generic Differencing and Compression Data Format. Applied (deferred) in §17.2.
  • RFC 6901 (2013). JavaScript Object Notation (JSON) Pointer. Applied in §20, §8.
  • RFC 6902 (2013). JavaScript Object Notation (JSON) Patch. Applied in §20.
  • RFC 7396 (2014). JSON Merge Patch. Applied in §20.
  • POSIX.1-2017 / IEEE Std 1003.1, diff and patch utility specifications. Applied in §17.

Glossary (§37) · 47 terms · site-wide glossary

AlgorithmId
the tag (Myers/Patience/Histogram/WuOnp/HuntMcIlroy) stamped onto every EditScript recording which algorithm produced it (§11.2).
Anchor
a line (or token) selected as a fixed match point during patience or histogram recursion (§15, §16).
Apply (exact)
applying a Patch to old by verifying context/removed lines match exactly at the declared offset (§17).
Apply (fuzzy)
applying a Patch by searching a bounded window for the best-scoring context match when exact offsets fail (§17).
Back-of-envelope capacity model
the derived, formula-shown numeric estimates a system's expected scale (§33).
Byte-identity
the conformance bar: output matches a reference tool's output byte-for-byte (§22).
Conflict
a Block variant recording ours/base/theirs bytes where a three-way merge could not reconcile automatically (§11.4).
Conflict marker
the <<<<<<</|||||||/=======/>>>>>>> textual rendering of a Conflict (§18.4).
Conformance corpus
the set of committed (input, expected-output) fixtures a bucket is tested against (§22).
Content-defined chunking
a rolling-hash technique selecting chunk boundaries by a bit-pattern match, used in binary similarity indexing (§19.2, §35 A1).
Cost cap (cost_cap)
the caller-configurable ceiling on Myers' edit distance D before returning an error (§4, I8).
Criss-cross history
a commit graph with more than one lowest common ancestor between two branches (§18).
Determinism
the property that identical inputs always produce byte-identical output (I3, §7).
Diff3 / weave merge
the classic three-way merge algorithm from Hunt & McIlroy 1976, walking two diffs in lockstep over a common base (§18.1).
EditOp
one operation (Equal/Delete/Insert/Replace) in an EditScript (§11.2).
EditScript
the algorithm-agnostic IR describing how to transform old into new (§11.2).
Edit graph
the DAG of (i,j) states whose shortest path is the minimum edit script (§8.1).
Fuzzy apply
see Apply (fuzzy).
Granularity
the tokenisation level (Byte/Line/Word/Char/Token) an EditScript was computed at (§11.1).
Histogram diff
libxdiff's anchor-selection diff using least-repeated-token anchors (§16).
Hunk
a contiguous, context-bounded run of changes within a Patch (§11.3).
Hunt-McIlroy LCS
the 1976 DP-based longest-common-subsequence diff algorithm (§14.2 step 7).
Jaccard similarity
|A∩B|/|A∪B| over two shingle-fingerprint sets, the rename/copy similarity score (§19.2).
JSON Merge Patch
RFC 7396's recursive-merge structured-patch format (§20).
JSON Patch
RFC 6902's operation-list structured-patch format (§20).
JSON Pointer
RFC 6901's /a/b/c-style path addressing scheme into a JSON document (§8, §20).
LIS (longest increasing subsequence)
the patience-sort result selecting which anchors form the matched skeleton (§15.2).
Middle snake
the diagonal segment where a forward and reverse Myers search meet, the pivot of the linear-space refinement (§14.2 step 4).
Myers algorithm
the O(ND) edit-graph search from Myers 1986 (§14).
Ort (merge-ort)
git's 2.34+ merge strategy integrating rename detection into the merge phase (§18.2 step 5).
Patience diff
Bram Cohen's uniqueness-anchor diff algorithm (§15).
Rabin fingerprint
a rolling polynomial hash used to compute shingle fingerprints for similarity indexing (§19.2).
Recursive merge (merge-recursive)
git's virtual-ancestor three-way merge for criss-cross histories (§18.2 step 3).
RenameOpts
the configuration struct (min_similarity, max_pairs, detect_copies) governing rename/copy promotion (§11.5).
Shingle
a fixed-size (default 3-line) window over a file's lines, the unit fingerprinted for similarity (§19.2).
SimilarityIndex
the fingerprint set used to compute a Jaccard similarity score between two files (§11.5).
Streaming diff
a diff mode bounding memory to O(window_size) regardless of input size (§4, I11).
Three-way fallback (--3way)
git's apply-fallback that synthesizes a base and runs a three-way merge when a patch's context has drifted too far for fuzzy apply (§17.2 step 8).
Token
a non-owning, hashed slice into an input buffer, the atomic unit any diff algorithm compares (§11.1).
Tokeniser
the trait/implementation splitting raw bytes into Tokens at a chosen Granularity (§11.1, §13).
Tree diff
a file-tree-level (not single-file) diff producing Vec<TreeOp> (§11.6, §19).
TreeOp
one tree-level edit operation (Add/Delete/Modify/Rename/Copy/ModeChange) (§11.6).
Unified diff
the --- /+++ /@@ @@ text format this toolkit emits and parses (§8.2).
VCDIFF
RFC 3284's binary delta-encoding format, this toolkit's deferred binary-diff surface (§17.2).
Virtual ancestor
the synthesized common base computed by recursively merging multiple criss-cross merge bases (§18.2 step 3).
Wu O(NP)
Wu, Manber, Myers & Miller's 1990 diff algorithm, faster than Myers when the deletion count P is small (§14.2 step 6).
xxh3_64
the non-cryptographic hash function used for token equality checks (§13.2 step 2).
