1. Goal & Scope

Diff Merge (diffmerge) is a text diff and three-way merge engine: it computes minimal edit scripts between byte sequences at multiple granularities (byte, line, word, character), emits and parses unified-diff patches byte-identical to git diff --no-color on a conformance corpus, applies those patches exactly and fuzzily, and performs three-way content merges (weave, recursive, ort-style) with criss-cross resolution, rename/copy detection, and structured patches over JSON/XML/YAML. Binary delta (VCDIFF) and AST-aware semantic diff are explicit deferred stretch surfaces, not Phase-0 scope.

Phase-0 deliverable (numbered modules):

  1. diffmerge-core — tokenisers + edit-graph algorithms (Myers, Wu O(NP), Hunt-McIlroy LCS) producing the shared EditScript IR.
  2. diffmerge-patch — unified-diff emit/parse/apply (exact + fuzzy).
  3. diffmerge-merge — three-way weave merge with conflict-marker rendering.
  4. diffmerge-cli (dm) — thin CLI wrapper exposing 1–3 as subcommands.
  5. conformance/runner — Rust binary asserting byte-identity against git on the fixture corpus.

System boundaries:

  • Provides: diff computation, patch emit/parse/apply, three-way merge, rename/copy detection (§19), structured patches (§20), a C ABI (§21).
  • Delegates: merge-base computation — the caller supplies base/ours/theirs; the library does not walk a commit graph (the CLI optionally uses git2 for that).
  • Does NOT provide: a version-control system, a hosted code-review service, an operational-transformation engine for live collaborative editing, a general-purpose compression library.

Non-goals: real-time collaborative editing; a git-compatible object store; a GUI merge tool (the conflict-marker text and the structured MergeResult are the surfaces an embedder builds a GUI on top of, not a GUI itself).

Deployment model: a statically linked CLI binary plus a Rust library crate plus a C header; no daemon, no network service, no persistent state beyond the files the caller passes in.

Target users/operators: version-control tooling authors, code-review platform engineers, patch-shipping build systems, structured-config-diff tooling authors (JSON/YAML config-drift detection).

What later phases unlock: §18 (three-way merge) unlocks conflict resolution for VCS-adjacent tools; §19 (tree diff) unlocks whole-repository diffing; §20 (structured patches) unlocks config-management diffing; §21 (CLI/FFI) unlocks embedding in non-Rust hosts; §22 (conformance/fuzzing/ops) unlocks a Sealed release; deferred VCDIFF (§17.2) unlocks binary-file version control; deferred semantic AST diff (§13.2) unlocks syntax-aware code review.

Recommended language: Rust, edition 2021, MSRV 1.75. Rationale: memory safety without a GC pause on the streaming path (P7, §6); an unsafe-auditable ecosystem for the FFI boundary (ADR-11, §9); zero-cost abstractions keep the Myers inner loop competitive with git's C implementation (ADR-01, §9). Rejected languages: C++ (canonical implementations exist in C/C++, but manual memory management raises the audit cost of the FFI boundary without a compensating benefit); Go (GC pauses conflict with the streaming-diff target M4, §29; no zero-cost FFI story); OCaml (no mature cbindgen-equivalent C-header generator, weaker SIMD-friendly hashing ecosystem).

Prerequisites: dynamic programming on a 2D grid (edit distance); the unified-diff text format as git diff emits it; enough git internals to distinguish a tree, a blob, and a commit; big-O analysis of graph search.

Estimated timeline: Phase 0 — 1 week. Full system (§12–§22, including deferred stretch surfaces) — 14–16 weeks (~3.5–4 months).

Deferred features (registered in full at §36):

  • PhaseDeferred("§13.2") — tree-sitter-based token-aware tokenisation and AST-diff engine.
  • PhaseDeferred("§17.2") — VCDIFF (RFC 3284) binary delta encoding/decoding.
  • PhaseDeferred("§17.2") — secure_apply sandboxed, root-restricted patch application.
  • PhaseDeferred("§21.2") — PyO3-based Python frontend.
  • PhaseDeferred("§21.3") — Language Server Protocol code-action shim.
  • PhaseDeferred("§30") — streaming (bounded-memory) three-way merge for gigabyte-scale base files.

2. Why Build This

Diff and merge sit under every version-control system, code-review tool, patch shipper, and config-management pipeline. The literature is decades old and stable (Hunt & McIlroy 1976; Myers 1986; Tichy 1984); the canonical implementations are open (libxdiff in git's tree; Mercurial's bdiff.c); the gap between a textbook diff and a production one is entirely in tie-breaking, streaming, and byte-exact conformance. Building this system means owning the edit-graph search, the anchor-selection heuristics that make patience/histogram human-readable, and the three-way reconciliation a VCS's merge command depends on.

Architecturally this project teaches three transferable disciplines. First, IR design — one EditScript shape serving five algorithms and three emitters, the same discipline that makes a compiler's IR reusable across front-ends and back-ends (§11, §14–§16). Second, conformance-first engineering — asserting byte-identity against a 40-year-old reference implementation rather than trusting a fresh implementation's own tests (§9 ADR-10, §22, §27). Third, the recursive-descent "reduce to a smaller instance" pattern that recurs three times in this one domain: patience's recursion into unmatched regions (§15), histogram's recursion into split regions (§16), and merge-recursive's recursion into merge-base pairs (§18).

Sibling systems this calibrates against: an LSM-tree's compaction logic (merging sorted runs is structurally the same reconciliation shape as three-way merge, §18, §32); a CRDT's conflict resolution (solves the same "two divergent histories" problem with different consistency guarantees, §35 A2); a compiler's incremental-recompilation dependency diff (tree diff + rename detection, §19, is exactly what an incremental build system needs to know "what actually changed").

What Mastery Looks Like (competencies gained, tied to phases):

  • Implement Myers' O(ND) algorithm and its linear-space middle-snake refinement from the 1986 paper alone, and explain why the naive form needs O(D²) space (§14).
  • Explain why patience's uniqueness anchors and histogram's least-common-count anchors produce more human-readable diffs than raw Myers, and when each degrades to Myers (§15, §16).
  • Debug a unified-diff hunk-header off-by-one by reasoning about the \ No newline at end of file sentinel's exclusion from OLD_LEN/NEW_LEN (§17).
  • Explain why merge-recursive needs a virtual ancestor on criss-cross histories, and reconstruct the recursive-merge-of-bases algorithm from first principles (§18).
  • Implement a Jaccard-similarity rename detector and reason about its O(deletes × adds) cost and the cap that bounds it (§19).
  • Distinguish JSON Patch (RFC 6902) from JSON Merge Patch (RFC 7396) and state exactly which information each format loses (§20).
  • Wrap a Rust library in a panic-safe C ABI and reason about ownership across the FFI boundary (§21).
  • Design and run a conformance harness that turns "looks right" into "byte-identical against a reference implementation on N fixtures" (§22).

Per-box notes:

  • CLI/FFI (top): the only two user-facing surfaces; both are thin — every subcommand and every exported symbol maps 1:1 to a library call (P9, §6).
  • diffmerge-core public surface: the sole entry point; nothing downstream of it is reachable except through diff, tree::diff, or json::diff.
  • Tokenisers: orthogonal to algorithms — a Myers diff over byte tokens is the same Myers diff as over line tokens, modulo the equality test (P1, §6).
  • Structured (JSON/XML/YAML): shares the EditScript/patch IR only at the boundary; internally a structural diff, never a text diff over pretty-printed output (P11, §6).
  • Edit-graph algorithms: five algorithms, one EditScript output shape (P2, §6); this is the pluggability seam referenced throughout the document.
  • Patch: the unified-diff renderer/parser/applier; consumes EditScript, never touches tokenisation directly.
  • Three-way merge: built on top of the diff core — two diffs (base→ours, base→theirs) reconciled across hunks (§2).
  • Tree diff / rename+copy: a post-process over a naive per-file tree diff, never a preprocess (P10, §6).
  • Conformance suite: the contract with git (P12, §6); every arrow above ends here at test time.

6. Design Principles

  1. Bytes are the substrate. Every algorithm operates on &[u8], encoding-agnostic at the core; UTF-8 awareness is a tokeniser property, not an engine property. Tradeoff: byte-level generality costs a hash computation per token. Operational implication: the same engine handles binary VCDIFF (deferred, §17.2) and UTF-8 source with no code fork. Violate it and binary-safety silently breaks the day someone adds a "smart" encoding check inside the algorithm.
  2. One IR, many algorithms, many emitters. EditScript is the sole contract between any diff algorithm and any patch emitter (I1, §7). Tradeoff: the IR must be conservative enough to represent five algorithms' outputs uniformly. Operational implication: adding histogram next to Myers never touches the patch path. Violate it and every new algorithm requires a matching emitter change — an O(algorithms × emitters) maintenance surface instead of O(algorithms + emitters).
  3. Determinism is the default. Two runs over the same (old, new, opts) produce byte-identical output regardless of OS, CPU, or thread count (I3, §7). Tradeoff: tie-breaking rules must be specified and tested, not left to hash-map iteration order. Operational implication: conformance tests are reproducible across CI runners. Violate it and the conformance suite becomes flaky, masking real regressions (MM4, §31).
  4. No silent fallbacks between algorithms. Patience descending to Myers on an unmatched region is the algorithm, not a fallback; a Myers cost-cap breach returns an error, never a silent coarser tokenisation (I8, §7). Tradeoff: callers must handle CostBudgetExceeded explicitly. Operational implication: a slow diff surfaces as a typed error the caller can retry with different opts, not as a silently wrong result. Violate it and a denial-of-service input (§23 T3) becomes a silent correctness bug instead of a visible one.
  5. Patches are typed, not stringly typed. Patch is Vec<Hunk>; unified-diff text is a render of Patch, never the internal representation (§11). Tradeoff: an extra parse/emit round-trip for every text interaction. Operational implication: the merge and apply engines consume Patch, so a text-format quirk fix never touches merge logic. Violate it and text-format parsing bugs leak into merge correctness.
  6. Conflicts are first-class values. MergeResult is Vec<Block>, each Resolved or Conflict{ours,base,theirs} (I12, §7); the marker-text rendering is one renderer among many. Tradeoff: an extra type layer versus emitting markers directly. Operational implication: a review-tool embedder consumes structured conflicts, never re-parses marker text (MM6, §31). Violate it and every consumer needs its own marker parser — an inherently lossy round-trip.
  7. Streaming over slurping where the algorithm allows. A 1 GB line diff must not require a 1 GB allocation; the line iterator is lazy; the streaming Myers variant holds only the diagonal arrays it needs. Tradeoff: streaming mode is a second code path with its own benchmark suite. Operational implication: memory stays O(window_size) regardless of input size (§4, §33). Violate it and the toolkit cannot diff anything larger than available RAM.
  8. Performance is a property of the algorithm, not the implementation. A correct Myers in Rust is competitive with a correct Myers in C; the benchmark suite locks algorithm-level baselines before micro-optimisation. Tradeoff: early phases spend time on criterion benchmarks before the CLI exists. Operational implication: perf regressions are caught at the algorithm level, not masked by implementation noise. Violate it and engineering effort chases the wrong bottleneck.
  9. The CLI is a thin wrapper over the library. Every dm subcommand maps 1:1 to a library call; the CLI implements zero algorithm logic. Tradeoff: some CLI ergonomics (progress bars, colour) must live at the boundary, not inside the library. Operational implication: the library's test suite is the CLI's test suite by construction. Violate it and library and CLI behaviour drift apart (MM-class bug: "works in the CLI but not via the library API").
  10. Rename and copy detection are post-processes, not preprocesses. A tree diff first computes file-level deltas assuming names match; a similarity-index pass then promotes delete+add pairs to renames/copies (MM7, §31). Tradeoff: two passes over the tree diff instead of one. Operational implication: rename detection can be toggled cheaply at the CLI (--find-renames) without touching the diff core. Violate it and rename logic entangles with the per-file diff, breaking principle 2.
  11. Structured diffs are not text diff with extra steps. A JSON patch is a structural operation over a document tree, not a unified diff over pretty-printed text; JSON/XML/YAML share the EditScript-adjacent IR concept but not the algorithm. Tradeoff: three separate structural-diff implementations instead of one text-diff reuse. Operational implication: whitespace/key-ordering changes never appear as spurious structured-patch operations. Violate it and every reformat looks like a content change.
  12. The conformance suite is the contract with git. Wherever the toolkit emits a unified diff, three-way merge, rename detection, or patience/histogram output, conformance asserts byte-identity (or documented divergence) against the corresponding git invocation (ADR-10, §9; §22). Tradeoff: the corpus must be built and maintained before algorithms are "done." Operational implication: divergence is a tracked, named artifact (divergences.md), never silently absorbed. Violate it and the toolkit drifts from the ecosystem's de-facto reference with no visibility.
  13. The similarity index is symmetric by design, matching git. SimilarityIndex::jaccard is a symmetric score even though "is this a copy of" is intuitively asymmetric (ADR-06, §9). Tradeoff: a one-way Tversky-style score would better match intuition but would diverge from git's rename output. Operational implication: rename/copy conformance (§19.5) can target byte-identity with git. Violate it and rename promotions silently disagree with git diff -M -C with no clear root cause.
  14. A cost cap is a correctness feature. Every algorithm with unbounded worst-case cost (Myers, rename detection's pairwise comparison) exposes a caller-visible cap that fails loudly rather than degrading silently (I8, §7; T3, §23). Tradeoff: pathological-but-legitimate inputs occasionally need the caller to raise the cap explicitly. Operational implication: algorithmic-complexity attacks (§23) become typed errors, not hangs. Violate it and a single adversarial input can stall the whole pipeline with no operator signal.

8. Domain Model / Protocol / Data Model

8.1 The edit graph (grammar of the problem)

For sequences A[0..n], B[0..m]: node (i,j) = "consumed A[0..i], B[0..j]." Horizontal edge = delete from A; vertical edge = insert from B; diagonal edge = match (free, requires A[i]==B[j]). The shortest (0,0)→(n,m) path is the minimum edit script; D = path length minus diagonal steps. Every algorithm in §14–§16 is a different search strategy over this same graph (patience and histogram restrict the graph to anchor-adjacent regions before recursing).

8.2 Unified-diff grammar (EBNF)

patch        = { raw-header-line } file-header { hunk } ;
file-header  = "--- " path newline "+++ " path newline ;
hunk         = hunk-header { hunk-line } ;
hunk-header  = "@@ -" old-start ["," old-len] " +" new-start ["," new-len] " @@" [" " context] newline ;
hunk-line    = ( " " | "-" | "+" ) text newline
             | "\ No newline at end of file" newline ;
raw-header-line = git-index | git-rename | git-copy | new-file | deleted-file | binary-marker ;

old-len/new-len are omitted when they equal 1. old-start/new-start are 0 when the corresponding side is empty. The \ No newline... line is excluded from both length counts (I9, §7).

8.3 Three-way merge state table (weave walk)

Base region Ours diff Theirs diff Emitted Block
unchanged none none Resolved(base_bytes)
changed edit none Resolved(ours_bytes)
changed none edit Resolved(theirs_bytes)
changed edit A edit A (same bytes) Resolved(A) — false conflict, clean
changed edit A edit B (A≠B) Conflict{ours:A, base, theirs:B}

8.4 Worked example

Base: ["a","b","c"]. Ours: ["a","x","c"] (b→x). Theirs: ["a","b","c","d"] (append d). Weave walk: region ["a"] unchanged→Resolved; region ["b"] changed-by-ours-only→Resolved("x"); region ["c"] unchanged→Resolved; region [] (append point) changed-by-theirs-only→Resolved("d"). Merge output: ["a","x","c","d"], zero conflicts — the classic non-overlapping-edit case (§18.5).

8.5 Malformed-input example

Input hunk header @@ -5,3 +5,4 @@ followed by only 2 context/removed lines instead of 3: parse_unified counts consumed old-side lines against old_len from the header; a mismatch at hunk end raises ParseError::HunkLengthMismatch{expected:3, actual:2} rather than silently truncating (I6, §7). Conformance fixture: corpora/apply/exact/malformed-hunk-length/.

8.6 Failure-path example (Khanna–Kunal–Pierce counterexample)

Base: a single line "x". Ours: reorders a surrounding block so "x" shifts up one line without content change. Theirs: independently inserts a line directly above "x"'s original position. Classic diff3 walk sees both diffs as non-overlapping (different line ranges) and emits a clean merge — but the result misplaces the inserted line relative to the reordered block, an intent violation invisible to a line-oriented three-way merge (Khanna, Kunal, Pierce 2007, §5). This blueprint accepts the wrong-but-clean output (documented, not silently absorbed) and records the fixture in docs/three-way-merge.md; ADR-05 (§9) is where the conflict-shape decision that makes divergence visible rather than silent is recorded.

11.2 EditOp and EditScript (edit_script.rs)

pub enum EditOp {
    Equal   { old_range: Range<usize>, new_range: Range<usize> },
    Delete  { old_range: Range<usize>, new_pos: usize },
    Insert  { new_range: Range<usize>, old_pos: usize },
    Replace { old_range: Range<usize>, new_range: Range<usize> },

    pub ops: Vec<EditOp>, pub old_len: usize, pub new_len: usize,

Ownership: EditScript owns its Vec<EditOp>; ranges are indices, not borrows, so the script outlives the tokenised input. Serialization: not serialized across the C ABI directly — the FFI layer exposes it as an opaque DmEditScript* handle (§21.2). Compatibility: I1 (§7) is the invariant every producer must satisfy before handoff.

11.8 Normative Traits: Diff, Apply, Merge, StructuredDiff

pub trait Diff {
    type TokenT<'a>: PartialEq + Eq + Copy where Self: 'a;
    type Error: std::error::Error;
    fn diff<'a>(&self, old: &'a [Self::TokenT<'a>], new: &'a [Self::TokenT<'a>])
        -> Result<EditScript, Self::Error>;
}
pub trait Apply {
    type Error: std::error::Error;
    fn apply(&self, old: &[u8], patch: &Patch) -> Result<Vec<u8>, Self::Error>;
}
pub trait Merge {
    type Error: std::error::Error;
    fn three_way(&self, base: &[u8], ours: &[u8], theirs: &[u8], opts: MergeOpts)
        -> Result<MergeResult, Self::Error>;
}
pub trait StructuredDiff<T> {
    type Patch;
    type Error: std::error::Error;
    fn diff(&self, old: &T, new: &T) -> Result<Self::Patch, Self::Error>;
    fn apply(&self, old: &T, patch: &Self::Patch) -> Result<T, Self::Error>;
}

Ownership: trait implementors own no state beyond their own config (opts); every method borrows its inputs. Mutation: none — every method is a pure function of its arguments. Concurrency: every conformant implementor is Send + Sync (required for §21's CLI/FFI callers to share one implementor across threads). Persistence: none. Serialization: not applicable to the traits themselves — only their associated concrete types (EditScript, Patch, MergeResult, §11.2–§11.4) cross a boundary. Compatibility: a Diff implementation is conformant iff EditScript::validate() holds (I1, §7) and apply(old, emit(diff(old,new)))==new (I2, §7) for every corpus pair (§22); a Merge implementation is additionally conformant iff the four identities in §18.4 criterion 2 hold. These four traits are the contract §22's conformance suite tests against, independent of which concrete algorithm (Myers/patience/histogram, weave/recursive/ort) implements them.

13. Phase 1 — Tokenisers

Lands the four byte-oriented tokenisers (Line, Byte, Word, Char) and their conformance corpus. The tokeniser is the easiest place for a diff toolkit to silently drift from git and the hardest place to debug once it has (MM5, §31).

13.1 Objectives

  • Implement LineTokeniser, ByteTokeniser, WordTokeniser, CharTokeniser against the Tokeniser trait (§11.1).
  • Match git diff --word-diff's tokenisation rule byte-for-byte for WordTokeniser.
  • Register Granularity::Token (tree-sitter) as an explicit deferred variant, not a silent omission.

13.2 Detailed Implementation Steps

  1. LineTokeniser: split on \n, retain the trailing \n in the token; the last token has no trailing newline iff the input doesn't end in \n — propagate that fact into HunkLine::NoNewlineAtEof (I9, §7).
  2. Hash each token with xxh3_64 at tokenisation time (P1, §6) — hashing once here is the single largest performance win in the diff core (M1, §29).
  3. ByteTokeniser: one token per byte; used by the deferred VCDIFF path (PhaseDeferred §17.2) and the byte-level merge fallback (§18).
  4. WordTokeniser: split on [A-Za-z0-9_]+|[^A-Za-z0-9_\s], matching git diff --word-diff's default (ADR-03, §9).
  5. CharTokeniser: split on UTF-8 code-point boundaries; ill-formed UTF-8 falls back to one-byte-per-token in the offending region (documented deviation, not a panic).
  6. Register Granularity::Token as the PhaseDeferred("§13.2") call site for tree-sitter-based tokenisation (ADR-09, §9; Difftastic reference impl, §5).
  7. Use ahash (not std::collections::HashMap's default SipHash) for any internal hash-table use in the tokeniser to avoid quadratic degradation on repetitive input (§13.6 pitfall).
  8. Build the tokeniser conformance corpus (§13.5) and wire it into conformance/runner.

13.3 Deliverable

Tokeniser trait + four implementations, each passing its named conformance fixtures; a criterion benchmark (diffmerge-bench/benches/myers.rs, extended in §14) that includes tokeniser cost in its measurement.

13.4 Acceptance Criteria

  1. tokeniser.line / .byte / .word / .char conformance buckets all Pass (§13.5 table).
  2. Property test: decode_lines(tokenise_lines(x)) == x for every byte string x < 64 KiB, 10,000 random cases.
  3. LineTokeniser throughput ≥ 1 GB/s on the linux-kernel-snapshot corpus (M1, §29).
  4. WordTokeniser output matches git diff --word-diff byte-for-byte on a 50-fixture corpus.

13.5 Conformance Fixtures

Fixture Purpose Expected Output

13.6 Pitfalls

  • The \r\n problem: git diff treats \r as part of the line by default; we match that and document the deviation from core.whitespace=trailing-cr.
  • The empty-input case: tokenising b"" must return vec![], not a single empty token — a common off-by-one in naive implementations.
  • The byte tokeniser interacts badly with patience (§15): every byte is a candidate anchor, degenerate. Document and recommend the line tokeniser for patience.
  • Hash collisions on highly repetitive input (a million identical lines) are not a correctness issue (I4, §7 tie-breaks on bytes) but can quadratically degrade performance if the hash table's buckets fill — mitigated by ahash (step 7, §13.2).

13.7 Performance Concerns

  • xxh3_64 throughput (~10 GB/s single core) must stay ≤ 10% of the M1 (§29) per-token budget, leaving headroom for the edit-graph search itself (derived in §33).
  • WordTokeniser's regex-like scan must avoid backtracking; implement as a hand-rolled character-class scanner, not a general regex engine, to keep the cost linear.

13.8 Edge Cases

  • A file that is a single unterminated line (no \n anywhere).
  • A file that is all newlines (every line empty).
  • Mixed-script Unicode (Latin + CJK + emoji ZWJ sequence) for CharTokeniser.
  • A 4 GiB input at the ByteTokeniser's addressing ceiling (§4).

13.9 Failure Analysis

  • A tokeniser that silently misclassifies CRLF as two tokens instead of one corrupts every downstream diff on that file — detection is the tokeniser.line conformance bucket; blast radius is every consumer of LineTokeniser; containment is the conformance gate blocking merge (ADR-10 spirit, P12 §6).
  • A hash-seed collision attack (T5, §23) degrades throughput but never correctness (I4, §7); telemetry: dm_hash_collision_total.

13.10 Operational Notes

  • hash_seed defaults to a process-startup random value (mitigating T5, §23); the CLI exposes no flag to disable this by default.
  • Tokeniser cost is included in the tracing span for diff() (ADR-17, §9) as a named child span tokenise, visible in the OTLP trace for slow-diff triage (runbook/slow-diff.md, §25).

14. Phase 2 — Myers O(ND) and the Linear-Space Middle-Snake

Lands Myers' algorithm in two forms — quadratic-space O(ND) and linear-space O((N+M)D) via the bidirectional middle snake (Myers 1986, §5) — plus Wu's O(NP) variant and Hunt-McIlroy LCS as a third independent verifier.

14.1 Objectives

  • Implement the forward furthest-reaching-path search over the edit graph (§8.1) per Myers 1986 §2, §4.
  • Implement the linear-space refinement via bidirectional middle-snake recursion.
  • Implement Wu O(NP) (Wu et al. 1990) and Hunt-McIlroy LCS (Hunt & McIlroy 1976) as cross-verifiers.
  • Enforce the cost-cap escape valve (I8, §7; P4, §6) on every entry point.

14.2 Detailed Implementation Steps

  1. Build the forward V-array search: V[k+offset] tracks the furthest-reaching x on diagonal k after d edits, sliding along diagonals while A[x]==B[y] (Myers 1986 §2 — the edit-graph diagonal insight, anchored here as the direct application of P2 §6's "one IR" principle, since the trace this search produces feeds EditScript construction).
  2. At each d, check the caller's cost_cap (default old_len+new_len, I8 §7); breach returns MyersError::CostBudgetExceeded rather than continuing (P4 §6, ADR-01 §9 is the language decision that makes this bounds-check cheap).
  3. Backtrack the trace (O(D)) to produce Vec<EditOp>; this is where AlgorithmId::Myers and the input Granularity are stamped onto the resulting EditScript (§11.2).
  4. Implement the bidirectional middle-snake: run forward and reverse Myers passes in lockstep (reverse pass has opposite-parity k from the forward pass — Myers 1986 §4b) until they meet on a common diagonal; that meeting point is on the optimal path (Hirschberg 1975's linear-space divide-and-conquer trick, generalised).
  5. Recurse the middle-snake search on the two halves either side of the meeting snake; recursion depth is O(log D); total work stays O((N+M)D); space drops to O(N+M).
  6. Implement wu_onp: exploit D = N-M+2P (P=deletion count); gate its selection behind a length-ratio heuristic (|n-m| ≤ 0.05×max(n,m), ADR-22 §9) so it only runs where it wins.
  7. Implement hunt_mcilroy: the 1976 DP-based LCS, capped at 4096 tokens per side — a teaching/verification reference, not a production path (Hunt & McIlroy 1976; CLRS Ch.15 §15.4, §5).
  8. Cross-algorithm property test: 1000 random (a,b) pairs up to length 256; assert all four algorithms produce EditScripts that apply to the same result (I2, §7).
  9. Wire a make bench-myers criterion target against linux-kernel-snapshot (ADR-14, §9).

14.3 Deliverable

myers_forward, myers_linear, wu_onp, hunt_mcilroy all present, cross-verified, and selectable via AlgorithmId; a criterion report for Myers on the reference corpus.

14.4 Acceptance Criteria

  1. Cross-algorithm property test passes 1000/1000 cases (§14.2 step 8).
  2. Myers throughput ≥ 1 GB/s on unchanged regions, ≥ 100 MB/s on 10%-changed workload (M1/M2, §29), measured on linux-kernel-snapshot.
  3. myers_forward returns MyersError::CostBudgetExceeded (not a panic, not a wrong result) on an adversarial 10 MB no-common-token pair with cost_cap = 50,000 (derived in §33).
  4. wu_onp and myers_linear produce equivalent (apply-equal) scripts on 500 near-identical-file fixtures (|n-m|<5%).

14.5 Conformance Fixtures

Fixture Purpose Expected Output

algo.wu_onp.equivalent cross-check Wu and Myers scripts apply-equal

14.6 Pitfalls

  • Off-by-one in the V-array indexing convention (V[k+offset], never raw negative k) — test explicitly at D=0,1,2.
  • Middle-snake recursion can stack-overflow on adversarial input (a million identical lines); cap recursion depth (4096) and convert to an explicit work queue past that.
  • Forward/reverse passes use opposite-parity k — get this wrong and the middle snake never converges (silent infinite loop, caught only by the cost cap).
  • Token::eq falls back to byte equality on hash collision (I4, §7); comparing raw u64 hashes directly silently produces wrong diffs on collisions.
  • wu_onp requires n≥m (delete from the longer side); reversed inputs must be swapped at entry and the script reflected at exit.

14.7 Performance Concerns

  • The trace-storage array is the O((N+M)D) memory cost the linear-space variant eliminates — profile allocation count, not just wall-clock, to confirm the switch actually reduces peak RSS on the 1 GB corpus (M5, §29).
  • Cache locality: the V-array should be a flat Vec<i64>, never a HashMap, to keep the inner loop's memory access pattern sequential.
  • The cost-cap check (step 2, §14.2) executes once per d, not once per k — an accidental per-k check would add O(D) redundant branches.

14.8 Edge Cases

  • Identical old/new (D=0, trivial).
  • Completely disjoint old/new (D=n+m, worst case — this is where the cost cap matters most, §33).
  • Single-token inputs on either side.
  • Adversarial repeated-token input designed to maximise middle-snake recursion depth.

14.9 Failure Analysis

  • A CostBudgetExceeded breach on a legitimate large file is a caller-visible error, not a hang — detection is immediate (typed Result); blast radius is one diff() call; recovery is caller-initiated retry with a raised cap or a switch to streaming mode (§4).
  • A middle-snake parity bug manifests as non-termination — detection via the recursion-depth cap (§14.6) converting an infinite loop into a bounded, diagnosable failure.

14.10 Operational Notes

  • tracing span diff.myers records d_final (edit distance) and cost_cap_hit: bool as span fields, feeding dm_diff_duration_seconds{algorithm="myers"} (§25).
  • make bench-myers results are committed under benchmarks/results/<host>/ and diffed in CI to catch performance regressions (perf-regression gating, §27).

15. Phase 3 — Patience Diff

Bram Cohen's patience diff produces the most human-readable output on most code changes (Cohen 2007) and is the default in several code-review tools. The algorithm fits on a napkin; the engineering is in the recursive descent on unmatched regions.

15.1 Objectives

  • Implement unique-common-line anchor detection and LIS-based anchor selection (patience-sort, Cohen 2007).
  • Recurse on unmatched regions, descending to Myers (§14) when no anchors exist.
  • Match git diff --patience byte-for-byte on a 100-fixture corpus, or document divergence.

15.2 Detailed Implementation Steps

  1. Find every line appearing exactly once in old AND exactly once in new — the unique anchors (Cohen 2007; Heckel 1978's unique-line matching is the direct ancestor of this step, §5).
  2. Run patience-sort over the anchors in old-index order, maintaining piles keyed by smallest top-of-pile new-index; place each anchor on the leftmost pile whose top exceeds its new index, else start a new pile — O(K log K) for K anchors.
  3. Recover the LIS by following back-pointers from the last pile's top; tie-break lexicographically smallest (old_idx,new_idx), matching git's convention (I3, §7 determinism).
  4. The LIS partitions [old_off,old_len)×[new_off,new_len) into matched-anchor points and unmatched regions between them.
  5. For each unmatched region: recurse (step 1) if it's non-empty on both sides; if the region is empty on one side, emit Delete/Insert directly without recursing (avoids a degenerate recursive call).
  6. If no anchors are found in a region, descend to myers_linear (§14, P2 §6 — the same EditScript IR, no special-casing downstream) over that region and translate offsets.
  7. Anchored-context behaviour (Cohen's "prefer anchors with matching context") falls out of step 2 for free: an anchor's context lines, if also unique, become adjacent LIS entries, extending the matched run — no separate implementation needed.
  8. Build and wire the algo.patience.git conformance bucket against git diff --patience --no-color on 100 fixtures drawn from real-world commit pairs.

15.3 Deliverable

patience() producing conformant EditScripts; a criterion benchmark on chromium-source-pair; the --algo patience CLI path functional (stub CLI from §12, wired here).

15.4 Acceptance Criteria

  1. algo.patience.git ≥ 95/100 fixtures byte-identical to git diff --patience (documented divergence for the rest, per fixture, in divergences.md).
  2. Property test: apply(old, patience(old,new)) == new for every corpus pair (I2, §7).
  3. Patience wall-clock ≤ 2× Myers on chromium-source-pair (M6, §29).
  4. A degenerate all-identical-lines input (1000 blank lines) falls through entirely to Myers with zero anchors found, verified by a unit test asserting anchors.is_empty().

15.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/diff/git-patience/* (100 fixtures) git byte-identity matches git diff --patience --no-color or documented divergence
corpora/diff/patience/degenerate-identical/ fallback path falls through to Myers, zero anchors
corpora/diff/patience/duplicate-anchors/ uniqueness condition a line unique in old but duplicated in new is NOT an anchor

15.6 Pitfalls

  • "Unique" means unique in both files — a line unique in old but duplicated in new is not an anchor; a common bug is checking only one side.
  • The recursive descent can produce a different (but equally valid) result from Myers on the same sub-region — this is correct, not a bug; the conformance corpus tolerates it as long as the script is valid (I1, §7).
  • Empty regions on one side must emit Delete/Insert directly, never recurse into an empty slice — recursing wastes a call and can mis-order offsets.
  • Multiple optimal LIS solutions exist for degenerate anchor sets — git's tie-breaker (lexicographically smallest (old_idx,new_idx)) must be matched exactly (I3, §7) or conformance silently fails on tie-heavy fixtures.

15.7 Performance Concerns

  • Patience-sort is O(K log K) in the anchor count K, not in old_len/new_len directly — profile with a high-duplication corpus to confirm K stays small relative to file size.
  • The recursive descent's per-call overhead (allocating a new Vec<EditOp> slice per region) should use a shared arena or pre-sized Vec to avoid O(regions) small allocations dominating wall-clock on deeply fragmented diffs.

15.8 Edge Cases

  • Zero unique anchors anywhere (full fallback to Myers, §15.4 acceptance criterion 4).
  • A single unique anchor at the very start or end of the file (boundary recursion).
  • Anchors that appear in reversed relative order between old and new (excluded from the LIS by construction).
  • A file where every line is unique (patience should perform close to optimally, minimal recursion).

15.9 Failure Analysis

  • A tie-breaker mismatch against git manifests as a conformance Fail, not a crash — detection is immediate at CI (algo.patience.git bucket); containment is per-fixture (divergences.md); recovery is a targeted tie-breaker fix, re-run conformance.
  • Unbounded recursion depth on a pathological anchor pattern is bounded by the same depth cap introduced in §14.6, reused here (shared discipline, not reimplemented).

15.10 Operational Notes

  • tracing span diff.patience records anchor_count and recursion_depth_max as fields, useful for runbook/slow-diff.md triage (§25) distinguishing "few anchors, mostly Myers fallback" from "deep recursive fragmentation."
  • The CLI's --algo patience flag is documented in dm diff --help (clap derive, ADR-12 §9), generated automatically — no separate doc to maintain.

16. Phase 4 — Histogram Diff

libxdiff's improvement on patience: anchors are the least-repeated tokens rather than strictly unique ones, making it faster on small windows and more robust to minor duplication.

16.1 Objectives

  • Implement histogram-based anchor selection (least combined token count) per libxdiff's xhistogram.c (§5 reference impl).
  • Match git diff --histogram byte-for-byte on a 100-fixture corpus, replicating libxdiff's max_chain early-exit exactly.
  • Compare Myers/patience/histogram throughput on one shared benchmark corpus.

16.2 Detailed Implementation Steps

  1. Build a token-count histogram over old and new in a single pass per side.
  2. For each token appearing in both sides, compute its combined count; find the token with the smallest combined count (the "best" split point) — this is libxdiff's anchor heuristic (xhistogram.c, §5), the direct generalisation of patience's strict-uniqueness rule in §15.2 step 1.
  3. Skip any token whose combined count exceeds max_chain (default 64, libxdiff's value) — this is the O(N log N)-vs-O(N²) lever (P8 §6: performance is an algorithm property).
  4. The chosen split token's positions in old/new partition the region; recurse on the two sub-regions (steps 1–3), mirroring the patience recursion pattern in §15.2 step 5.
  5. If no common token survives the max_chain filter, fall through to myers_linear (§14) over the region — same fallback discipline as patience (P4, §6: no silent fallback, this is the documented algorithm behaviour, not a degradation).
  6. Replicate libxdiff's "chain too long" early-exit during histogram construction (not after) — required for byte-identity with git (a subtle timing detail documented in the reference impl, §5).
  7. Build and wire algo.histogram.git against git diff --histogram --no-color on 100 chromium-class fixtures.
  8. Add a criterion benchmark comparing Myers/patience/histogram on one shared corpus (chromium-source-pair).

16.3 Deliverable

histogram() producing conformant EditScripts selectable via --algo histogram; comparative benchmark report across all three text algorithms.

16.4 Acceptance Criteria

  1. algo.histogram.git ≥ 95/100 fixtures byte-identical to git diff --histogram (documented divergence for the rest).
  2. Histogram wall-clock ≤ 1.5× Myers on chromium-source-pair (M7, §29).
  3. Property test: apply(old, histogram(old,new)) == new for every corpus pair (I2, §7).
  4. max_chain override test: setting max_chain=4 produces a documented-different (not wrong) output on a high-duplication fixture, proving the cap is load-bearing.

16.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/diff/git-histogram/* (100 fixtures) git byte-identity matches git diff --histogram --no-color or documented divergence
corpora/diff/histogram/no-common-token/ fallback path falls through to Myers
corpora/diff/histogram/max-chain-boundary/ cap behaviour a token at exactly max_chain count is included; max_chain+1 is excluded

16.6 Pitfalls

  • max_chain is the O(N²)-vs-O(N log N) lever (libxdiff default 64) — document the chosen value in code comments; test overriding it.
  • Histogram's anchor selection differs from patience's, so the two can produce different edit scripts on the same input — conformance must compare against git's histogram output specifically, never against patience's output.
  • The "chain too long" early-exit must fire during the histogram build (step 6, §16.2), not as a post-filter — get the timing wrong and byte-identity with git silently fails on high-duplication fixtures.
  • Empty or single-line inputs should short-circuit before calling best_histogram_split at all — calling it anyway is correct but wastes a call.

16.7 Performance Concerns

  • Histogram construction is one pass, O(n+m); the max_chain cap bounds the per-token lookup cost, keeping the overall algorithm O((n+m) log(n+m)) rather than O((n+m)²) (derived in §33).
  • Compare allocation counts against Myers on the same corpus — histogram's recursive splitting should not allocate more Vecs per region than patience's equivalent recursion (§15.7).

16.8 Edge Cases

  • A token with combined count exactly at the max_chain boundary (§16.5 fixture).
  • No common token anywhere (full Myers fallback).
  • A single dominant repeated token (e.g., blank lines) surrounding a few unique anchors — histogram should still find the unique anchors as the best split.

16.9 Failure Analysis

  • A max_chain mismatch against libxdiff's exact behaviour manifests as a conformance Fail on high-duplication fixtures specifically — detection isolates to the git-histogram bucket; recovery is fixing the early-exit timing (§16.6), re-run conformance.
  • Wrong split-token selection (e.g., picking the first common token instead of the least-repeated) produces a valid but non-conformant script — I1 (§7) still holds, only byte-identity with git fails, distinguishing an IR bug from a heuristic-tuning bug.

16.10 Operational Notes

  • tracing span diff.histogram records max_chain_hits (count of tokens skipped by the cap) — a high value on a specific corpus signals the default cap may need per-corpus tuning, surfaced in runbook/slow-diff.md (§25).
  • Benchmark comparison report (Myers/patience/histogram) is committed to benchmarks/results/<host>/histogram-comparison.json for cross-phase regression tracking.

17. Phase 5 — Unified-Diff Emitter, Parser, and Patch Applier

Converts an EditScript into a unified-diff Patch, parses it back, and applies it exactly or fuzzily. Conformance target: byte-identical to git diff --no-color and interoperable with git apply.

17.1 Objectives

  • Implement hunk grouping with configurable context (default 3 lines, --unified=N).
  • Implement emit_unified/parse_unified covering git's extended raw header (renames, copies, mode changes, binary marker).
  • Implement apply_exact and apply_fuzzy (±50-line window, context-match scoring).

17.2 Detailed Implementation Steps

  1. Group EditScript ops into Hunks: two hunks merge when fewer than 2×context unchanged lines separate them (default context=3, §8.2 grammar) — this is a linear scan over EditOps, tracking a HunkBuilder accumulator (anchored to I5 §7: hunks stay ascending, non-overlapping).
  2. Trim trailing context to exactly context lines when closing a hunk out; a region of ≥ 2×context unchanged lines splits into two hunks rather than one over-wide hunk (matches git's grouping exactly, required for unified.emit.git byte-identity, §17.4).
  3. Implement emit_unified: git extended header (diff --git, index, optional similarity index/rename from/rename to) then file header then hunks (§8.2 grammar; ADR-01 §9 language choice is what keeps this emitter allocation-cheap via Vec<u8> byte-building rather than String formatting).

Function-context detection (@@ ... @@ <context>): scan backward from the hunk's first line for the first non-blank, non-whitespace-leading line, bounded by a configurable distance — replicate git's heuristic exactly for byte-identity (Tichy 1984's block-move discussion, §5, is why this heuristic exists: unified diff intentionally has no block-move primitive, so function-context is the only "where am I" signal it carries).
  5. Implement parse_unified: read raw-header lines, file header, then hunks while @@ prefix seen; reject a hunk whose line-consumption count disagrees with its header's declared length (I6, §7; §8.5 malformed-input example).
  6. Implement apply_exact: locate each hunk's declared start, verify context+removed lines match exactly, splice in context+added lines, advance a monotonic cursor — the incremental-cursor design keeps total cost O(file_size + hunk_count), not O(file_size × hunk_count) (mitigates T2, §23).
  7. Implement apply_fuzzy: on context mismatch, search a ±50-line window (configurable) for the best-scoring context match (count of exact context-line matches); apply at the matched offset if above a threshold — the patch -F3 / git apply --reject behaviour.

  1. unified.emit.git ≥ 99/100 fixtures byte-identical to git diff --no-color (M14, §29).

  3. Round-trip property test: apply(old, parse(emit(diff(old,new)))) == new for every corpus pair.

17.6 Pitfalls

  • The \ No newline at end of file sentinel is line-number-significant (I9, §7): omitted from OLD_LEN/NEW_LEN; getting this wrong shifts every subsequent hunk header by one.
  • Context lines start with a single space, not a tab; a file that legitimately starts with a single space creates an ambiguous parse resolved only by header arithmetic — mirror git exactly.
  • Renames with trailing edits: the extended header announces the rename; the hunks describe edits inside the renamed file. apply_exact must rename first, edit second, or the target path is wrong.
  • git emits Binary files a/foo and b/foo differ by default; --binary emits a binary delta (VCDIFF territory, deferred PhaseDeferred §17.2) — Phase 5 handles only the textual sentinel.

17.7 Performance Concerns

  • apply_exact's monotonic cursor keeps total cost O(file_size + hunk_count) — verify with a benchmark on a patch with 10⁶ tiny hunks (T2, §23) to confirm no quadratic blowup.
  • emit_unified's output buffer should be size-estimated up front (Vec::with_capacity) from the EditScript's op count to avoid repeated reallocation on large diffs.
  • apply_fuzzy's ±50-line window search is O(window × context_len) per hunk — bound the window explicitly; an unbounded search on a corrupted patch is a DoS vector (T2, §23).

17.8 Edge Cases

  • A patch whose old-side is fully empty (new-file creation).
  • A patch whose new-side is fully empty (file deletion).
  • A hunk at the very start (old_start=0) or very end of the file.
  • Trailing whitespace on +/- lines (significant to the patch, often invisible in editors) — must be preserved on both emit and parse.
  • A rename with zero content change (patch: None in TreeOp::Rename, §11.6) versus a rename with edits.

17.9 Failure Analysis

  • A malformed patch (adversarial or corrupted) must never panic the parser — detection is the fuzz target unified_parse.rs (§22); blast radius is contained to one parse_unified call returning Err; recovery is caller-visible, typed.
  • A hunk-count DoS attempt (10⁶ tiny hunks, T2 §23) is contained by the O(file_size+hunk_count) cursor design (§17.7); telemetry: dm_apply_failures_total{reason="hunk_count_exceeded"} if a configured hunk-count ceiling is added.

17.10 Operational Notes

  • tracing spans patch.emit, patch.parse, patch.apply_exact, patch.apply_fuzzy each record byte counts and hunk counts for runbook/slow-diff.md triage (§25).
  • CLI exit codes follow diff(1) convention: 0 = no differences, 1 = differences found, 2 = error — several downstream test scripts depend on this (§26 compatibility note).

18. Phase 6 — Three-Way Merge

Combines two divergent edits of a common ancestor. Lands weave (diff3, Hunt & McIlroy 1976), recursive (virtual ancestor for criss-cross), and ort-style (git 2.34+) strategies, plus conflict-marker rendering.

18.1 Objectives

  • Implement weave merge: two diffs (base→ours, base→theirs) reconciled per the state table (§8.3).
  • Implement recursive merge: virtual-ancestor computation for criss-cross histories, depth-capped (I14, §7).
  • Implement ort-style merge: rename detection integrated into the merge phase rather than as a preprocess.
  • Implement conflict-marker rendering matching git's merge.conflictStyle=diff3 output.

18.2 Detailed Implementation Steps

  1. Tokenise base/ours/theirs by line; compute d_ours = myers_linear(base,ours), d_theirs = myers_linear(base,theirs) (§14, P2 §6 — merge is built entirely on the diff core's EditScript IR, never a bespoke reconciliation format).
  2. Walk both diffs in lockstep over the base range (WeaveWalker); classify each region per the state table (§8.3) and emit Block::Resolved or Block::Conflict (I12, §7).
  3. For criss-cross histories (multiple merge bases supplied), recursively merge the bases pairwise into a single virtual ancestor before running step 1–2 against it (Hunt & McIlroy 1976 §III weave algorithm, generalised per git's merge-recursive.c, §5) — cap recursion depth at 256 (I14, §7; DoS mitigation T3 §23).
  4. On a conflicting recursive-base merge, take the conflict side's bytes as the virtual ancestor's content for that region (render_clean_or_take_left), matching git's documented behaviour — recorded in ADR-05 (§9).
  5. Implement ort: same recursive-virtual-ancestor core as step 3, but integrate rename detection (§19) into the merge phase rather than running detect_renames as a preprocess — the git 2.34+ semantics (Mens 2002 survey situates this in the broader merge-strategy taxonomy, §5).
  6. Render conflict markers: <<<<<<< ours / ||||||| base / ======= / >>>>>>> theirs, in that exact order (I13, §7); the ||||||| block is emitted only under --style diff3 (default here), omitted under --style merge.
  7. Implement automatic resolution for mechanically safe cases: adjacent non-overlapping edits both apply; identical changes at the same position collapse to one copy; whitespace-only conflicts are configurable (merge.whitespace=ignore-all-space) but not auto-resolved by default.
  8. Accept the Khanna-Kunal-Pierce diff3 counterexample (§8.6) as documented, non-silent divergence — recorded in docs/three-way-merge.md, not "fixed" (Khanna, Kunal, Pierce 2007, §5).
  9. Build and wire merge.weave.git_merge_file (200 fixtures: 100 from git's own test suite t/t6402-merge-rename.sh/t/t6404-recursive-merge.sh, 50 real-world triples, 50 synthetic criss-cross).

18.3 Deliverable

three_way_weave, three_way_recursive, three_way_ort in source; dm merge BASE OURS THEIRS --style {weave,recursive,ort} functional on the CLI.

18.4 Acceptance Criteria

  1. merge.weave.git_merge_file ≥ 195/200 fixtures byte-identical to git merge-file --diff3 (M15, §29).
  2. Conformance identities (I2 §7-style, per §11.4's Merge contract): merge(base,base,base)→Resolved(base); merge(base,x,base)→Resolved(x); merge(base,base,x)→Resolved(x); merge(base,x,x)→Resolved(x) — all four hold on 50 generated fixtures each.
  3. Recursive merge on a synthetic criss-cross fixture with 3 merge bases produces a result matching git merge-recursive's output or a documented divergence.
  4. Recursion depth cap fires (MergeError::RecursionDepthExceeded) on a synthetic 300-deep criss-cross fixture, never silently truncating.

Fixture Purpose Expected Output
corpora/merge/git-merge-file/* (200 fixtures) weave byte-identity matches git merge-file --diff3 or documented divergence
corpora/merge/git-merge-recursive/* criss-cross matches git merge-recursive or documented divergence
corpora/merge/git-ort/* ort semantics matches git merge-ort or documented divergence
corpora/merge/khanna-kunal-pierce/ known-wrong-but-clean case (§8.6) accepted divergence, recorded in docs/three-way-merge.md

18.6 Pitfalls

  • The Khanna-Kunal-Pierce counterexample (§5, §8.6) produces a clean merge that violates intent — accept and document, never silently "fix" without a documented tradeoff.
  • Criss-cross detection requires the commit graph as input; the library does not walk git history — the CLI's dm merge uses git2 when run inside a repository (§1 delegation boundary).
  • Recursive merge can recurse arbitrarily deep on pathological histories — the depth cap (default 256, I14 §7) must return an error, never silently degrade to a single-base merge.
  • The ||||||| block must render before ======= and after <<<<<<< — several first-attempt implementations get this ordering wrong (I13, §7).
  • The merge-base algorithm itself is out of scope (§1); accepting merge bases as caller-supplied input is a boundary, not a shortcut.

18.7 Performance Concerns

  • Weave merge cost is dominated by the two Myers diffs (§14) — M8 (§29) budgets 250 ms for a 10 MB triple, derived from M3's 100 ms-per-10MB-diff target times two diffs plus reconciliation overhead (§33).
  • The recursive virtual-ancestor computation on N merge bases costs O(N) sequential pairwise merges — document this as linear in base count, not exponential, and verify with a benchmark on N=5 synthetic bases.

18.8 Edge Cases

  • Zero merge bases (root-commit merge) — virtual ancestor is empty.
  • A single merge base (the common case) — no recursion needed.
  • Identical ours/theirs (auto-resolves cleanly, §18.4 criterion 2).
  • A conflict region at the very start or end of the base file (boundary walker behaviour).
  • Whitespace-only divergence between ours and theirs (configurable, not auto-resolved by default, §18.2 step 7).

18.9 Failure Analysis

  • An unbounded criss-cross recursion is contained by the depth cap (I14, §7); detection via dm_merge_recursion_depth histogram; recovery is caller-side base-list flattening.
  • A conflict-marker ordering bug (I13 violation) is caught by golden-fixture comparison before it ships — blast radius if it escaped would be every downstream consumer parsing marker text, which is exactly why P6 (§6) keeps MergeResult structured as the source of truth instead.

18.10 Operational Notes

  • tracing span merge.three_way records conflict_count, strategy, and recursion_depth — feeds dm_merge_conflicts_total (§25) and runbook/conflict-storm.md triage.
  • The --style {weave,recursive,ort} CLI flag and the library's MergeStrategy enum (§11.4) are the same three values everywhere — no separate CLI-only naming.

19. Phase 7 — Tree Diff and Rename/Copy Detection

Lifts the per-file diff to tree level: given two file trees, produce a minimal Vec<TreeOp> description including renames and copies, matching git diff -M -C.

19.1 Objectives

  • Implement the naive tree diff (path-set difference + per-file Modify).
  • Implement similarity-index-based rename detection as a post-process (P10, §6).
  • Implement copy detection (opt-in, higher cost than rename detection).

19.2 Detailed Implementation Steps

  1. Compute old_paths/new_paths as sorted path sets; paths only in old → TreeOp::Delete; only in new → TreeOp::Add; in both with differing content → TreeOp::Modify via a per-file diff (§14) — this naive pass detects zero renames by construction (every rename appears as a Delete+Add pair), matching P10 (§6)'s separation of concerns.
  2. Build a SimilarityIndex per file: Jaccard score over 64-bit Rabin fingerprints of shingle_size-line shingles (default 3 lines/shingle, ADR-06 §9) — computed once per file, not per comparison pair, keeping the cost O(file_size) per index (§33 capacity derivation).
  3. For binary content (no line boundary), use a rolling hash over a 64-byte window; keep only window hashes matching a configurable bit pattern (hash & 0xFF == 0, ≈1/256 of windows) — the standard content-defined-chunking trick, robust against insertion-induced fingerprint shifts.
  4. Enumerate every (Delete, Add) pair; compute SimilarityIndex::jaccard; keep pairs scoring ≥ min_similarity (default 50, matching git diff -M50, ADR-06 §9); cap the candidate set at max_pairs (default 1000, I7 §7).
  5. Sort candidate pairs by descending similarity; greedily promote the highest-scoring unconsumed pair to TreeOp::Rename, marking both sides consumed, until pairs are exhausted or max_pairs is hit.
  6. Copy detection (opt-in, RenameOpts::detect_copies): enumerate (Add, *) pairs where the source can be any file in either tree (not just deleted ones) — higher cost, matching git's -C flag; promote to TreeOp::Copy when the source is unchanged in its own location.
  7. Detect mode changes (chmod +x) as a separate pass producing TreeOp::ModeChange, since the naive diff (step 1) does not capture mode-only changes.
  8. A rename with content edits requires both the rename promotion and the file-level Patch — an applier must rename first, edit second (order matters, documented in §17.6 pitfall list, reused here).
  9. Build and wire tree.rename.git_M and tree.copy.git_C conformance buckets (50 fixtures) against git diff -M -C.

19.3 Deliverable

tree_diff_naive, detect_renames, detect_copies in source; dm tree-diff OLD_DIR NEW_DIR --find-renames --find-copies functional; output round-trips through git apply --binary.

19.4 Acceptance Criteria

  1. tree.rename.git_M and tree.copy.git_C both Pass on the 50-fixture corpus (byte-identical rename/copy promotions to git diff -M -C).
  2. Rename-detection benchmark on a 10,000-file tree completes in < 5 s wall-clock (M9, §29).
  3. A pair count exceeding max_pairs emits an explicit warning (not a silent truncation) — verified by a unit test asserting the warning is logged.
  4. TreeOp::ModeChange is detected and distinct from TreeOp::Modify on a chmod-only fixture.

19.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/tree/rename/* (50 fixtures) rename promotion matches git diff -M50
corpora/tree/copy/* copy promotion matches git diff -C
corpora/tree/mode-change/ mode-only change TreeOp::ModeChange, no Modify
corpora/tree/rename-with-edits/ rename + content change TreeOp::Rename{patch: Some(_)}, rename-then-edit order
corpora/tree/pair-cap-exceeded/ max_pairs cap warning logged, pairs beyond cap dropped, never force-promoted

19.6 Pitfalls

  • The default threshold (-M50) matches a half-rewritten file; a lower threshold (e.g. -M30) catches more renames but produces false positives — document the tradeoff, never silently change the default.
  • Copy detection's quadratic cost (every Add against every file in both trees) is not optional to bound — cap the pair count and warn when the cap is hit (I7, §7).
  • Mode changes are invisible to the naive tree diff (step 1, §19.2) — a separate detection pass is required, not an afterthought.
  • The Jaccard score is symmetric; a one-way (Tversky-style) score would better match "is this a copy of" intuition but would diverge from git — documented in ADR-06 (§9), matched intentionally.
  • Rename-then-edit ordering: applying the content patch before the rename targets the wrong (old) path.

19.7 Performance Concerns

  • SimilarityIndex construction is O(file_size) per file, done once; the O(deletes×adds) pairwise comparison is O(1) per pair via sorted-vector Jaccard — recomputing the index per comparison would make the whole pass O(deletes×adds×file_size), the single most common performance bug in naive rename-detector implementations (§33 derivation).
  • Copy detection's larger candidate set (every file, not just deletions) should reuse the same SimilarityIndex cache built in step 2 — never rebuild per copy-candidate check.

19.8 Edge Cases

  • A file renamed with zero content change (patch: None).
  • A file renamed AND edited in the same commit (patch: Some(_), ordering matters, §19.6).
  • Two files below min_similarity but structurally similar (correctly NOT promoted — a common false-expectation bug report).
  • A tree with 10,000+ files hitting the max_pairs cap (§19.5 fixture).
  • A binary file rename (content-defined-chunking path, step 3, §19.2).

19.9 Failure Analysis

  • A max_pairs cap breach silently dropping real renames without a warning would be an invisible correctness gap — mitigated by the explicit-warning requirement (§19.4 criterion 3); detection via unit test; telemetry: a structured log entry naming the dropped pair count.
  • A similarity-index cache miss (rebuilding per-comparison instead of per-file) degrades performance catastrophically on large trees but never produces a wrong result — a performance bug, not a correctness bug, distinguishable by profiling (§19.7).

19.10 Operational Notes

  • tracing span tree.diff records file_count, rename_candidates, pairs_capped: bool for runbook/slow-diff.md (§25) triage on large-tree diffs.
  • dm tree-diff --find-renames --find-copies is the CLI surface; the library's RenameOpts defaults match git's (-M50, cap 1000) so CLI and library behaviour never drift (P9, §6).

20. Phase 8 — Structured Patches: JSON, XML, YAML

Structural patches, not text diffs over pretty-printed output (P11, §6). JSON gets RFC 6902 (operations) and RFC 7396 (merge patch); XML and YAML get heuristic structural diffs.

20.1 Objectives

  • Implement RFC 6902 JSON Patch diff/apply.
  • Implement RFC 7396 JSON Merge Patch diff/apply.
  • Implement heuristic structural diff for XML and YAML, documenting information loss (YAML comments).

20.2 Detailed Implementation Steps

  1. Implement JsonPatch::diff: a structural tree comparison over serde_json::Value, emitting add/remove/replace for value differences at each JSON Pointer (RFC 6901, §5) path — move/copy detected via the same similarity-index technique as file rename detection (§19.2 step 2, reused conceptually: relocated subtrees are "renamed" JSON values).
  2. Implement JsonPatch::apply: walk the document per JSON Pointer, applying each op in sequence; test ops perform structural (deep) equality, not string equality (RFC 6902 §5, applied here per §5's traceability requirement).
  3. Handle JSON Pointer escaping correctly: ~ encodes as ~0, / as ~1, decoded in that order (~1 before ~0 is a common bug — RFC 6901 §5 is explicit; get the order backwards and the path resolves to the wrong key).
  4. Implement JsonMergePatch::diff/apply: a recursive merge where null means "remove this key" (RFC 7396); document that Merge Patch cannot express array-element operations or test, unlike 6902 (§5 traceability, §33 capacity note on information loss).
  5. Implement XmlDiff: match elements by tag name + attribute set + text-content similarity (same SimilarityIndex machinery as §19.2), diff children recursively; emit XmlOp::{Insert,Delete,AttributeChange,TextChange}.
  6. Implement YamlDiff: parse via serde_yaml (ADR-13, §9) into a JSON-equivalent tree, diff structurally; document that comments/anchors/aliases are NOT preserved — a Phase-8+ limitation, not silently absorbed (PhaseDeferred NOT used here since it's a documented permanent limitation of the chosen parser, not a future phase's job — recorded instead in docs/compat/yaml-limitations.md, §26).
  7. Reject move/copy operations where from is a prefix of path (moving a value into itself) — JsonPatch::apply must detect and return an error, not silently corrupt the document.
  8. Build and wire json.patch.rfc6902, json.merge.rfc7396, xml.diff, yaml.diff.structural conformance buckets.

20.3 Deliverable

JsonPatch::{diff,apply}, JsonMergePatch::{diff,apply}, XmlDiff::diff, YamlDiff::diff in source; dm json-diff and dm json-merge-diff CLI subcommands.

20.4 Acceptance Criteria

  1. json.patch.rfc6902 and json.merge.rfc7396 both Pass against the RFC example vectors plus the jsonpatch.com test suite (≥ 100 combined cases).
  2. xml.diff and yaml.diff.structural Pass (structural-equivalence assertion, not byte-identity — XML/YAML lack a normative single-diff reference) on 30 fixtures each.
  3. A move with from a prefix of path returns a typed error on 100% of a 10-fixture self-move corpus, never corrupting the document.
  4. JSON Pointer escape round-trip (~0/~1) passes on a path containing both a literal ~ and a literal / in a key name.

20.6 Pitfalls

  • JSON Pointer escape order: decode ~1→/ before ~0→~, or a key containing both is misparsed (RFC 6901 §5).
  • test's value comparison must be structural/deep, not stringly — 42 and 42.0 may or may not compare equal depending on the JSON number model; document the chosen behaviour (equal) explicitly.
  • Array index boundaries: remove at index 5 of a 5-element array is an error; add at index - (the special "end" token) appends — both covered by the corpus (§20.5).
  • move/copy self-containment (from a prefix of path) must be rejected, not silently applied (§20.4 criterion 3).
  • XML's element-matching is heuristic — the same document pair can have multiple equally valid diffs; the conformance corpus accepts any structurally valid output since XML lacks a normative reference diff.
  • YAML's anchor/alias system means the same data has multiple valid encodings — serde_yaml's canonicalisation is the documented, non-negotiable choice (not an omission).

20.7 Performance Concerns

  • JsonPatch::diff's move/copy detection reuses the shingle/similarity-index machinery (§19.2) — the same O(file_size)-index / O(1)-comparison discipline applies; recomputing per-comparison is the same anti-pattern flagged in §19.7.
  • Target: JSON Patch over a 50 MB document completes in < 500 ms wall-clock (M10, §29).

20.8 Edge Cases

  • null at the document root for JSON Merge Patch (removes everything, or is itself the new document — RFC 7396 is explicit; follow it exactly).
  • null nested inside an object (removes just that key) versus null as an array element (RFC 7396 does not define array semantics — array values are replaced wholesale).
  • A JSON key containing both ~ and / literally.
  • An XML document with attribute-only changes (no text/structural change).
  • A YAML document using an anchor/alias pair that both sides preserve identically (should diff as unchanged, not as two independent changes).

  • A self-move/self-copy that silently corrupted the document instead of erroring would be a data-loss bug with no operator signal — mitigated by the explicit rejection (§20.6); detection via corpora/json-patch/self-move-rejected/.

20.10 Operational Notes

  • tracing span structured.json_diff / structured.yaml_diff / structured.xml_diff record document size and op count.
  • The CLI's --rfc 6902|7396 flag selects the JSON format explicitly; there is no auto-detection, keeping behaviour deterministic (I3, §7) and the CLI a thin wrapper (P9, §6).

Ships the two user-facing surfaces: the dm CLI and the C ABI for non-Rust embedders. Both are thin wrappers (P9, §6); neither implements algorithm logic.

21.1 Objectives

  • Ship dm diff/apply/merge/json-diff/tree-diff with a 1:1 mapping to library calls.
  • Ship a panic-safe C ABI via cbindgen-generated header.
  • Register the Python frontend and LSP shim as explicit deferred surfaces, not silent gaps.

21.2 Detailed Implementation Steps

  1. Implement dm subcommands with clap derive macros (ADR-12, §9): diff [--algo myers|patience|histogram] [--unified=N] [--word-diff], apply [--strict|--3way], merge [--style weave|recursive|ort], json-diff [--rfc 6902|7396], tree-diff [--find-renames] [--find-copies] — every flag maps directly to a library option (P9, §6).

  7. Generate diffmerge.h via cbindgen (ADR-19, §9) at build time from a locked feature-flag set (cbindgen.toml) so downstream feature flags never leak into the public header.

dm CLI with all five subcommands documented; diffmerge.h generated and stable; make examples-c builds and runs a linked C client.

  1. Every dm subcommand's behaviour matches its underlying library call byte-for-byte on the same fixture (CLI/library parity test, 20 fixtures across all five subcommands).
  2. make examples-c builds and runs with exit code 0 on the reference platform (§4).
  3. Zero panics escape the FFI boundary across the full fuzz/fuzz_targets/* corpus run for 60 s each (make fuzz-quick) — verified by catch_unwind coverage, not by absence of crashes alone.
  4. CLI exit codes follow diff(1): 0/1/2 for no-diff/diff-found/error, verified against 10 named fixtures.

21.6 Pitfalls

  • clap's derive style is verbose but the maintenance cost of hand-rolled argument parsing is higher — accept the verbosity (ADR-12, §9).
  • FFI panic safety: every entry point must wrap in catch_unwind; missing even one is a silent UB risk discovered only under fuzzing (T7, §23).
  • Memory ownership across FFI: returning Rust-allocated memory expecting free(3) on the C side is a use-after-free/double-free hazard — dm_buffer_free is the only correct release path.
  • cbindgen's output is sensitive to feature flags; an unlocked feature set can leak internal-only types into the public header.

21.7 Performance Concerns

  • CLI startup (parsing args, initialising tracing) must stay ≤ 15 ms (§4) — profile clap's derive-macro-generated parser against a hand-rolled baseline if this budget is ever at risk.
  • FFI call overhead (the catch_unwind wrapper) is O(1) per call — verify it doesn't measurably regress the M1/M2 (§29) throughput targets when invoked via the C ABI instead of the Rust API.

21.8 Edge Cases

  • A CLI invocation with no arguments (should print usage, exit 2).
  • An FFI caller passing a null pointer where a valid buffer is required (DM_ERR_INVALID_INPUT, not UB).
  • A panic triggered mid-algorithm (e.g., an injected unreachable!() in a test build) — must convert to DM_ERR_INTERNAL, not crash the host process.
  • --3way apply fallback invoked without a base blob available (returns a typed error, since base-synthesis needs a git index entry — a caller responsibility, §1 delegation boundary).

21.9 Failure Analysis

  • An escaped panic across FFI is the single worst failure mode this phase defends against — detection is exhaustive catch_unwind coverage plus fuzzing (§22); containment is DM_ERR_INTERNAL plus the host process surviving; recovery is caller-side retry or fallback.
  • A CLI/library behavioural drift (P9 violation) is caught by the parity test (§21.4 criterion 1) before it reaches users.

  • tracing in the CLI installs an OTLP exporter when DM_OTLP_ENDPOINT is set; otherwise logs to stderr at INFO (ADR-17, §9).
  • dm_* symbol versioning: the C ABI is additive-only across MINOR versions (§26); a removed or renamed symbol is a MAJOR bump.

  2. A bucket depending on a Phase-11+ surface emits outcome:"Deferred" with a blueprint_ref field naming the relevant §; overall outcome is Pass iff every non-Deferred bucket is Pass (P12, §6).
  3. Implement fuzz_targets/unified_parse.rs: arbitrary bytes → parse_unified; assert no panic, no unbounded allocation, no ASan violation (mitigates T1, §23).
  4. Implement fuzz_targets/apply.rs: (old, patch) pairs where patch comes from unified_parse of arbitrary bytes; assert apply returns either a valid Vec<u8> or a typed ApplyError.
  5. Implement fuzz_targets/myers_random.rs: arbitrary (old,new) byte strings; assert apply(old, myers(old,new)) == new (I2, §7) whenever myers doesn't hit the cost cap.
  6. Implement fuzz_targets/three_way.rs: arbitrary (base,ours,theirs); assert the MergeResult is well-formed (I12, §7) and every block's bytes round-trip.
  7. Land Prometheus metrics: dm_diff_duration_seconds{algorithm}, dm_diff_input_bytes_total{algorithm}, dm_apply_failures_total{reason}, dm_merge_conflicts_total, dm_fuzz_iterations_total.
  8. Land runbooks: runbook/triage.md (check conformance outcome, fuzz-canary iteration count, benchmark regression report first), runbook/slow-diff.md (check cost cap, algorithm choice, granularity, hash-collision rate), runbook/conflict-storm.md (check criss-cross, CRLF drift, whitespace policy).
  9. Close out PhaseDeferred("§13.2") (tree-sitter AST diff) and PhaseDeferred("§17.2") (VCDIFF) as registered, anchored entries in the Deferred Features Register (§36) — the stub crates diffmerge-semantic/diffmerge-binary (§10) return NotImplemented, not a silent panic or missing symbol.
  10. Run the 30-day fuzz canary continuously on a dedicated CI runner; gate M13 (§29, "Sealed") on zero unexpected crashes across that window.

  1. conformance.report.json's top-level outcome is "Pass" (every non-Deferred bucket Pass, per §22.2 step 2).
  2. make fuzz-quick runs all four targets for 60 s each with exit code 0, zero crashes.

22.6 Pitfalls

  • A Deferred bucket silently miscounted as Pass would mask incomplete coverage — the schema (step 1, §22.2) requires cases_deferred to be explicit and non-zero for a genuinely deferred bucket.
  • Patch parsers are fuzz-target gold: bugs found in the first hour of fuzzing a mature format are common — land the fuzz harness here, but the parser itself was already built in §17, so this phase's job is coverage, not first-time correctness.
  • A regression in any bucket (Pass→Fail) must block merge in CI — a soft-fail (warning-only) config silently erodes the conformance guarantee (P12, §6).

22.7 Performance Concerns

  • The conformance suite's own wall-clock (M11, §29) is a first-class target — a slow suite gets skipped or run less often, defeating its purpose.
  • Fuzz throughput (iterations/second) should be tracked as a metric (dm_fuzz_iterations_total) — a silent throughput regression (e.g., from an accidentally added allocation in a hot fuzz path) reduces coverage without an obvious signal.

22.8 Edge Cases

  • A conformance bucket whose corpus directory is empty (misconfiguration) — must fail loudly (cases_run:0 on a bucket expected to have fixtures is itself flagged), not silently report Pass.
  • A fuzz target that finds zero crashes in 60 s but would find one at 61 s — the 30-day canary (M13, §29) is what actually gates Sealed, not the quick pass.
  • A blueprint_ref pointing at a § that has since been renumbered — caught by the same cross-reference discipline as the rest of this document (§36 anchors, resolved once, never drift).

22.9 Failure Analysis

  • A conformance regression escaping to a release (CI gate bypassed or misconfigured) is the worst-case failure this phase exists to prevent — detection is the committed conformance.report.json diff in code review; containment is the CI merge-block; forensic artifact is the historical report sequence in benchmarks/results/ and conformance/.
  • A fuzz-found crash in unified_parse blocks the 30-day canary clock (resets to zero) — detection is immediate (CI fuzz job failure); recovery is a targeted parser fix plus a new named regression fixture added to §17.5.

22.10 Operational Notes

  • .github/workflows/conformance.yml runs on every push, uploads conformance.report.json as a build artifact.
  • The 30-day fuzz canary's dashboard is the Grafana sidecar in docker-compose.yml (§10), scraping dm_fuzz_iterations_total and crash-count metrics continuously.
  • Sealed (the release-readiness milestone, §28) requires: conformance Pass, M1–M11 met (§29), M13's 30-day canary clean — all three, not any one alone.

25. Operational Readiness

Metrics (Prometheus, §22.2 step 7): dm_diff_duration_seconds{algorithm} (histogram), dm_diff_input_bytes_total{algorithm} (counter), dm_apply_failures_total{reason} (counter), dm_merge_conflicts_total (counter), dm_fuzz_iterations_total (counter), dm_cost_budget_exceeded_total (counter), dm_hash_collision_total (counter), dm_streaming_window_bytes (gauge), dm_ffi_panic_total (counter), dm_merge_recursion_depth (histogram).

Tracing: every public entry point (diff, apply, merge, tree_diff, structured diff) is wrapped in a tracing span (ADR-17, §9); child spans record algorithm-specific fields (d_final, anchor_count, max_chain_hits, conflict_count, recursion_depth). The CLI installs an OTLP exporter when DM_OTLP_ENDPOINT is set; otherwise logs to stderr at INFO.

Structured logging: every error path logs a structured event (algorithm, input sizes, error kind) at WARN or ERROR; success paths log at DEBUG only (no default log spam on the hot path).

Dashboards: a Grafana sidecar (via docker-compose.yml, §10) visualises the fuzz canary's iteration rate and crash count, the benchmark suite's regression trend, and the conformance suite's pass rate over time.

Alerting philosophy: alert on conformance regression (Pass→Fail) and fuzz-canary crash (both are correctness signals, page immediately); alert on perf-target miss (M1–M11, §29) at ticket severity, not page severity, since it's a regression, not an outage (this is a stateless library/CLI with no uptime SLO, §4).

Named runbooks: runbook/triage.md (on-call first 10 minutes), runbook/slow-diff.md, runbook/conflict-storm.md (§22.2 step 8).

Backup/restore: not applicable — the toolkit holds no persistent state; "restore" means re-running a diff/merge/apply from the caller's own inputs.

Deployment topology: a single static binary (CLI) or a linked library (Rust crate / C ABI); no service topology, no orchestration.

Canary/rolling-upgrade/rollback: release channel is versioned crates.io + GitHub release binaries (§28); a "rollback" is pinning the previous version via Cargo.lock/binary re-download — there is no live upgrade because there is no running service.

26. Compatibility & Versioning

Wire compatibility: the unified-diff text format (§8.2) is the wire format; emitter/parser changes that alter byte-for-byte output for existing inputs are MAJOR-version changes.

Storage compatibility: not applicable — no on-disk state owned by the library.

Schema evolution: RawHeaderLine and MergeStrategy (§11) are #[non_exhaustive]; adding a variant is MINOR; removing or renaming one is MAJOR. JsonOp is exhaustive by design (RFC 6902's operation set is closed) — adding a variant here is MAJOR, documented in docs/compat/json-patch.md (§11.7).

API stability: the public traits (Diff, Apply, Merge, StructuredDiff, §11.8) follow SemVer (ADR-18-adjacent policy); a signature change to any of them is MAJOR.

C ABI stability: every dm_* symbol is additive-only across MINOR versions (§21.10); a removed/renamed/reordered-field symbol is MAJOR. cbindgen's generated header is versioned alongside the crate.

Migration: no data migration exists (stateless tool); a "migration" is a caller updating call sites for a MAJOR-version API change, documented per-version in CHANGELOG.md.

Deprecation policy: a deprecated API surface carries #[deprecated(since, note)] for at least one MINOR release before removal in the next MAJOR.

SemVer policy: standard SemVer (MAJOR.MINOR.PATCH); PATCH is bugfix-only (including a conformance-divergence fix that doesn't change any documented API); MINOR adds surface (a new algorithm, a new TreeOp variant behind #[non_exhaustive]); MAJOR breaks wire/API/ABI compatibility per the rules above.

Rolling-upgrade guarantees: not applicable (no running service); a mixed-version scenario only arises when a CLI binary and an FFI-linked library disagree — the C ABI's additive-only-within-MINOR rule (above) is what keeps that scenario safe.

27. Testing & Verification Strategy

Unit tests: per-module, covering each EditOp/Patch/MergeResult construction path and every named pitfall in §12–§22's N.6 subsections.

Integration tests: examples/*.rs (§10) double as integration tests — each exercises a full diff→patch→apply or base/ours/theirs→merge round-trip through the public API.

Property tests (proptest+quickcheck, ADR-15 §9): one assertion per invariant (§7's debugging methodology) — 1000+ generated cases per CI run, covering I1–I14.

Differential tests: the conformance suite (§22) is a differential test — every bucket compares this toolkit's output against git/RFC reference behaviour.

Fuzzing (cargo-fuzz, ADR-16 §9): four targets (§22.2 steps 3–6); the 30-day canary gates Sealed (M13, §29).

Chaos / fault injection: the FFI panic-injection fixture (§21.5) and the adversarial cost-cap/no-common-token fixtures (§14.5, §4) are the toolkit's fault-injection surface — there is no distributed runtime to inject network/process faults into (§1 scope).

Deterministic replay: every conformance fixture is a committed, replayable (input, expected) pair; a Fail is reproducible by re-running conformance/runner on the exact fixture, no flaky non-determinism (I3, §7 is what makes this guarantee hold).

Soak testing: M12 (§29) — a 24-hour soak with zero unhandled exceptions and zero memory growth, run before Sealed.

Conformance testing: §22 in full; tied back to System Invariants (§7) and each phase's N.5 fixtures throughout §12–§22.

Performance-regression gating: every criterion benchmark (§14.10, §15.10, §16.10) is committed under benchmarks/results/<host>/; CI diffs the latest run against the committed baseline and fails on a regression beyond a documented tolerance (§29).

29. Performance Engineering

Benchmarking methodology: criterion (ADR-14, §9) for all micro/macro benchmarks; every algorithm's baseline is locked in §14–§16 before any micro-optimisation is attempted (P8, §6). Reference hardware: a contemporary x86_64 12-core/32 GB RAM/NVMe laptop; ARM/Apple-Silicon numbers tracked separately in benchmarks/results/<host>/.

Profiling methodology: allocation counting (via a custom #[global_allocator] wrapper in debug benchmark builds) precedes wall-clock profiling — an allocation-count regression is often the leading indicator of a latency regression before it's visible in the histogram.

Allocation analysis: the V-array (§14), the anchor list (§15), and the histogram table (§16) are the three hot allocation sites; each is benchmarked for allocation count per diff, not just wall-clock.

Lock/contention analysis: the library holds no locks — Send + Sync types with no shared mutable state (§11) mean there is no lock-contention surface to profile; concurrency is entirely caller-managed (P9-adjacent boundary, §4).

Cache analysis: the V-array and token-hash tables are flat Vecs, never HashMap, specifically for sequential cache access (§14.7); this is verified by a cache-miss-rate benchmark on the reference hardware, not asserted.

Syscall analysis: the CLI's file I/O is the only syscall surface; streaming mode's read pattern is benchmarked for syscall count per MB to confirm it isn't issuing more read() calls than the window size requires.

Tail-latency analysis: p99 (not just p50) is a first-class target (§4); the cost-cap escape valve (I8, §7) is what keeps a single adversarial input from blowing out the p99 tail — verified with an adversarial-input-mixed-into-normal-traffic benchmark.

30. Scalability Analysis

What stays constant: per-diff memory in streaming mode (O(window_size), I11 §7) regardless of input length; FFI call overhead (O(1) per call, §21.7); the number of algorithms in the pluggable IR (P2, §6) — adding one never changes the cost of the others.

What grows, and its Big-O: Myers worst case O((N+M)·D) time, O(N+M) space (linear-space variant, §14); rename detection O(deletes×adds) pairwise comparisons, bounded by max_pairs (I7, §7); tree diff O(files) for the naive pass, O(files²) unbounded for rename/copy without the cap; conformance suite wall-clock O(total fixture count), tracked against M11 (§29).

Named bottlenecks, in order: (1) the edit-graph search itself (Myers/Wu/Hunt-McIlroy) dominates single-diff cost; (2) rename/copy detection's pairwise similarity comparison dominates tree-diff cost at scale; (3) the conformance suite's total wall-clock dominates CI turnaround as the fixture corpus grows; (4) FFI marshalling overhead is negligible by comparison (§21.7) and never the bottleneck in practice.

Horizontal scaling: "horizontal scale" for this toolkit means running N independent invocations across N files/processes — there is no shared state to coordinate (§4), so this is embarrassingly parallel by construction, not a distributed-systems problem.

Vertical scaling: more cores help only if the caller parallelises across independent diffs; no single diff() call is internally multi-threaded (a deliberate simplicity choice — SIMD/multi-threading within one Myers call is a documented future lever, not a Phase-0 requirement).

Sharding/partitioning: a tree diff over a very large repository can be partitioned by top-level directory and merged (Vec<TreeOp> concatenation is associative for disjoint path sets) — this is a caller-side pattern, not a library feature.

Coordination overhead: zero at the library level (no locks, §29); at the CLI level, none (single process, single invocation).

Practical ceiling: a single diff() call is bounded by the cost cap (I8, §7) and available memory (streaming mode notwithstanding, still O(window_size) per call, not zero); the practical ceiling for one process is "however many files fit in the FD budget" (§4) run sequentially, or in parallel up to the OS's process/thread limits.

Levers beyond the ceiling: partition the workload across processes/machines (caller-side, embarrassingly parallel, above); raise cost_cap and max_pairs explicitly for legitimately large inputs (never silently); the deferred streaming three-way merge (PhaseDeferred §30, registered §36) is the lever for gigabyte-scale merge bases specifically.

31. Mental Models & First Principles

  • MM1 — An edit script is a path through an edit graph, not "the" diff between two strings. Predicts: two edit scripts of equal cost can differ in shape; tie-breaking is a real design decision, not an implementation detail. Bug class without it: assuming diff output is unique and building tooling that breaks the moment a tie-breaker changes. Applies at §14.
  • MM2 — Uniqueness (not proximity) is what makes a diff human-readable. Patience and histogram both hinge on this; "proximity-based" heuristics (e.g., preferring nearby matches) do not explain why either algorithm outperforms Myers on code review. Bug class without it: trying to improve diff readability by tuning context-line counts instead of anchor selection. Applies at §15, §16.
  • MM3 — A three-way merge is two diffs reconciled, not a new algorithm. The entire weave/recursive/ort family is diff (§14) plus a walker plus a conflict policy. Bug class without it: reimplementing merge logic from scratch instead of composing two diff() calls with a reconciliation pass. Applies at §18.
  • MM4 — Determinism is a property you test for, not one you get for free. Hash-table iteration order, thread scheduling, and tie-breaking all threaten it silently. Bug class without it: a flaky conformance suite that "sometimes" byte-matches, wasting debugging time on phantom regressions. Applies at §7, §27.
  • MM5 — The tokeniser is a silent correctness boundary. Most "algorithm bugs" reported against a diff tool are actually tokeniser drift (CRLF handling, empty-input edge cases). Bug class without it: chasing a Myers/patience bug for hours that is actually a one-line tokeniser fix. Applies at §13, §9.
  • MM6 — A conflict is data, not text. Treating MergeResult as structured means every consumer (marker renderer, editor UI, review tool) is a projection of one source of truth, never a re-parse of another projection. Bug class without it: parsing your own rendered conflict markers back into structured form — an inherently lossy round-trip. Applies at §11, §18.
  • MM7 — Rename detection is a similarity search over a bipartite graph, not a special case of diff. Deletes and adds form the two sides of the graph; similarity score is the edge weight; the promotion is a greedy matching. Bug class without it: trying to detect renames inside the per-file diff instead of as a tree-level post-process, entangling two orthogonal concerns. Applies at §19, §6 (P10).
  • MM8 — A cost cap is a correctness feature, not a performance knob. It converts "the algorithm might run forever/OOM" into "the caller gets a typed error and decides." Bug class without it: silently downgrading tokenisation or truncating input on a slow case instead of surfacing the budget breach — invisible correctness erosion under load. Applies at §6 (P4), §23.

It wins as the reference implementation itself — this project's entire conformance strategy (§22) is built around agreeing with it.
  • Google diff-match-patch made character-level bisection its primary granularity, optimised for real-time interactive diffing (e.g., live-typing diff in a text field) rather than batch VCS-style diffing; it wins in latency-sensitive, small-input, interactive-editing contexts this project does not target (§1 non-goals).
  • Mercurial made bdiff.c's greedy longest-match its default rather than Myers, prioritising implementation simplicity and speed over Myers' provable edit-distance optimality; it wins where "a good enough diff, fast" beats "the provably minimal diff," a tradeoff this project rejects for its VCS-conformance goal (§4's one defining property: byte-exact).

33. Back-of-Envelope Capacity Model

  1. Non-streaming memory for a 1 GB pair: §4's "memory per diff ≤ 3×(old_len+new_len)" ⇒ 3×(1 GB+1 GB) = 6 GB resident — this is exactly why streaming mode (ADR-04, §9) is mandatory above 100 MiB, not merely nice-to-have.
  2. Streaming memory, any input size: window_size default 8 MiB (§4) × a double-buffering constant (~3×) ⇒ ≈24 MiB resident, flat, independent of file size (I11, §7) — the entire point of P7 (§6).
  3. Wall-clock for a 100 MB, 10%-changed diff: 100 MB ÷ M2's 100 MB/s (§29) = 1 s compute-bound, comfortably inside M4's 2 s streaming-mode budget (§29), leaving ~1 s of margin for streaming overhead.
  4. Hashing's share of the per-token budget: xxh3_64 at ~10 GB/s (§13.2) against M1's 1 GB/s diff-throughput target (§29) ⇒ hashing consumes ≤ 10% of the per-byte budget, leaving ≥ 90% for the edit-graph search itself — this is why M1 is achievable at all with a per-token hash.
  5. Cost-cap sizing for a 10 MB adversarial pair: assume avg line length 80 bytes ⇒ ~125,000 lines/side; a no-common-token pair gives D ≈ 250,000 (=n+m, the default cap, §4); worst-case Myers cost is O(D²) ≈ 6.25×10¹⁰ operations — at ~10⁹ ops/s this is ~60 s, far past the p99 target (M3, §29). Derivation: capping D at 50,000 instead bounds worst-case cost to O(50,000²) = 2.5×10⁹ ops ≈ 2.5 s, motivating a tuned cap well below the naive n+m default for latency-sensitive callers (§4's default is a correctness ceiling, not a performance-tuned one — callers needing the p99 target on adversarial input should lower it explicitly).
  6. Rename-detection worst-case comparison count: max_pairs=1000 (§4) caps the promoted-pair search, but the candidate enumeration itself is O(deletes×adds) before the cap filters it; for a 10,000-file tree with 5% churn (500 deletes, 500 adds) that's 250,000 Jaccard comparisons, each O(shingle-count) ≈ O(file_size/3) — for average 1000-line files (~998 shingles), ≈2.5×10⁸ shingle-set operations, which is why M9's 5 s budget (§29) requires the O(1)-per-comparison sorted-vector Jaccard (§19.7), not a naive O(shingles²) intersection.
  7. FD budget for a 10,000-file tree diff: §4's "3 + 2/file" formula would need 20,003 FDs for full concurrency — over most default ulimit -n (1024) — so batching at, say, 256 concurrent file pairs requires ⌈10,000/256⌉ ≈ 40 batches, each bounded by the FD budget.
  8. Conformance suite wall-clock budget: ~500 total fixtures across §13–§20's buckets (100+50+100+100+50+200+50+~130) at M11's < 5 min (§29) target ⇒ ≤ 600 ms/fixture average, consistent with M3's 100 ms Myers-diff budget plus git-subprocess invocation overhead per fixture (the dominant cost is spawning git, not this toolkit's own algorithm).

35. Alternative Architectures (Roads Not Taken)

A1 — Content-defined-chunking / rolling-hash block-copy diff (bsdiff/xdelta3-style) instead of edit-graph search.

Show the original text diagram
old: [ window ][ window ][ window ][ window ]
          │ rolling hash, pick boundary on bit-pattern match
new: [ COPY src@k,len ][ ADD bytes ][ COPY src@k',len' ]

Regime where it wins: near-duplicate large binary blobs (compiled artifacts, media files) where line/token boundaries don't exist. Real system: xdelta3, bsdiff/bspatch, VCDIFF (RFC 3284). Rejected as the primary architecture because byte-exact line-oriented text conformance with git (§4's one defining property) requires edit-graph semantics, not block-copy semantics — kept as the deferred VCDIFF surface (PhaseDeferred §17.2) for the binary-specific case it actually wins at.

A2 — CRDT/Operational-Transformation live-merge instead of offline three-way diff3 merge.

Show the original text diagram
site A: op_a ─┐
              ├─► transform(op_a, op_b) ─► converged state
site B: op_b ─┘        (OT) or CRDT merge function

Regime where it wins: real-time collaborative editing with many concurrent writers (Google-Docs-style). Real system: Automerge/Yjs (CRDTs), the original Google Wave OT engine. Rejected because this project targets asynchronous, VCS-style batch merge (§1 non-goals explicitly excludes live collaborative editing) — CRDT convergence guarantees solve a stronger, differently-shaped problem than diff3's "reconcile two finished edits against a common ancestor," at a complexity cost this toolkit's scope doesn't need.

A3 — Suffix-array/generalized-suffix-tree LCS instead of the Myers edit-graph.

Show the original text diagram
old+new → generalized suffix array → LCP array → longest common substrings
                                            │
                                    repeated-substring-heavy inputs
                                    win here; sparse-change inputs don't

Regime where it wins: repeated-substring-heavy corpora (log deduplication, genomic sequences) where O(n log n) suffix construction beats Myers' O(ND) when D is large relative to n. Real system: bioinformatics diff/alignment tools (e.g. MUMmer-family suffix-array alignment), the Hunt-Szymanski algorithm referenced in Gusfield 1997 (§5). Rejected as the default because typical source-code diffs have D ≪ n (few changed lines), making Myers' output-sensitive O(ND) faster in the overwhelmingly common case (§4's throughput targets are tuned for that regime).

A4 — AST-diff-first architecture (Difftastic-style) instead of text-diff-first.

Show the original text diagram
old.rs ──►[tree-sitter parse]──► AST_old ──┐
                                            ├──► match subtrees by structural hash ──► AstOp*
new.rs ──►[tree-sitter parse]──► AST_new ──┘

Regime where it wins: syntax-rich programming-language diffs where line-based diff misrepresents refactors (a reformatted function reads as "everything changed" line-wise but "nothing changed" structurally). Real system: Difftastic (Wilfred Hughes, §5). Rejected as the primary architecture because it requires a grammar per language (a large, ongoing maintenance surface) and because the byte-exact git-conformance goal (§4, §22) is defined over text, not ASTs — kept as the deferred semantic-diff surface (PhaseDeferred §13.2) for the code-review niche it actually wins at.

37. Glossary

  • AlgorithmId — the tag (Myers/Patience/Histogram/WuOnp/HuntMcIlroy) stamped onto every EditScript recording which algorithm produced it (§11.2).
  • Anchor — a line (or token) selected as a fixed match point during patience or histogram recursion (§15, §16).
  • Apply (exact) — applying a Patch to old by verifying context/removed lines match exactly at the declared offset (§17).
  • Apply (fuzzy) — applying a Patch by searching a bounded window for the best-scoring context match when exact offsets fail (§17).
  • Back-of-envelope capacity model — the derived, formula-shown numeric estimates a system's expected scale (§33).
  • Byte-identity — the conformance bar: output matches a reference tool's output byte-for-byte (§22).
  • Conflict — a Block variant recording ours/base/theirs bytes where a three-way merge could not reconcile automatically (§11.4).
  • Conflict marker — the <<<<<<</|||||||/=======/>>>>>>> textual rendering of a Conflict (§18.4).
  • Conformance corpus — the set of committed (input, expected-output) fixtures a bucket is tested against (§22).
  • Content-defined chunking — a rolling-hash technique selecting chunk boundaries by a bit-pattern match, used in binary similarity indexing (§19.2, §35 A1).
  • Cost cap (cost_cap) — the caller-configurable ceiling on Myers' edit distance D before returning an error (§4, I8).
  • Criss-cross history — a commit graph with more than one lowest common ancestor between two branches (§18).
  • Determinism — the property that identical inputs always produce byte-identical output (I3, §7).
  • Diff3 / weave merge — the classic three-way merge algorithm from Hunt & McIlroy 1976, walking two diffs in lockstep over a common base (§18.1).
  • EditOp — one operation (Equal/Delete/Insert/Replace) in an EditScript (§11.2).
  • EditScript — the algorithm-agnostic IR describing how to transform old into new (§11.2).
  • Edit graph — the DAG of (i,j) states whose shortest path is the minimum edit script (§8.1).
  • Fuzzy apply — see Apply (fuzzy).
  • Granularity — the tokenisation level (Byte/Line/Word/Char/Token) an EditScript was computed at (§11.1).
  • Histogram diff — libxdiff's anchor-selection diff using least-repeated-token anchors (§16).
  • Hunk — a contiguous, context-bounded run of changes within a Patch (§11.3).
  • Hunt-McIlroy LCS — the 1976 DP-based longest-common-subsequence diff algorithm (§14.2 step 7).
  • Jaccard similarity — |A∩B|/|A∪B| over two shingle-fingerprint sets, the rename/copy similarity score (§19.2).
  • JSON Merge Patch — RFC 7396's recursive-merge structured-patch format (§20).
  • JSON Patch — RFC 6902's operation-list structured-patch format (§20).
  • JSON Pointer — RFC 6901's /a/b/c-style path addressing scheme into a JSON document (§8, §20).
  • LIS (longest increasing subsequence) — the patience-sort result selecting which anchors form the matched skeleton (§15.2).
  • Middle snake — the diagonal segment where a forward and reverse Myers search meet, the pivot of the linear-space refinement (§14.2 step 4).
  • Myers algorithm — the O(ND) edit-graph search from Myers 1986 (§14).
  • Ort (merge-ort) — git's 2.34+ merge strategy integrating rename detection into the merge phase (§18.2 step 5).
  • Patience diff — Bram Cohen's uniqueness-anchor diff algorithm (§15).
  • Rabin fingerprint — a rolling polynomial hash used to compute shingle fingerprints for similarity indexing (§19.2).
  • Recursive merge (merge-recursive) — git's virtual-ancestor three-way merge for criss-cross histories (§18.2 step 3).
  • RenameOpts — the configuration struct (min_similarity, max_pairs, detect_copies) governing rename/copy promotion (§11.5).
  • Shingle — a fixed-size (default 3-line) window over a file's lines, the unit fingerprinted for similarity (§19.2).
  • SimilarityIndex — the fingerprint set used to compute a Jaccard similarity score between two files (§11.5).
  • Streaming diff — a diff mode bounding memory to O(window_size) regardless of input size (§4, I11).
  • Three-way fallback (--3way) — git's apply-fallback that synthesizes a base and runs a three-way merge when a patch's context has drifted too far for fuzzy apply (§17.2 step 8).
  • Token — a non-owning, hashed slice into an input buffer, the atomic unit any diff algorithm compares (§11.1).
  • Tokeniser — the trait/implementation splitting raw bytes into Tokens at a chosen Granularity (§11.1, §13).
  • Tree diff — a file-tree-level (not single-file) diff producing Vec<TreeOp> (§11.6, §19).
  • TreeOp — one tree-level edit operation (Add/Delete/Modify/Rename/Copy/ModeChange) (§11.6).
  • Unified diff — the --- /+++ /@@ @@ text format this toolkit emits and parses (§8.2).
  • VCDIFF — RFC 3284's binary delta-encoding format, this toolkit's deferred binary-diff surface (§17.2).
  • Virtual ancestor — the synthesized common base computed by recursively merging multiple criss-cross merge bases (§18.2 step 3).
  • Wu O(NP) — Wu, Manber, Myers & Miller's 1990 diff algorithm, faster than Myers when the deletion count P is small (§14.2 step 6).
  • xxh3_64 — the non-cryptographic hash function used for token equality checks (§13.2 step 2).
