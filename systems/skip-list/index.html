In one paragraph

A skip list is a sorted collection built from several sorted linked lists stacked on top of each other, so a search can leap over most entries instead of walking past them one by one (§8.1). This design builds, in Rust, four versions behind one OrderedMap interface: a random-height list, a fixed-rule list with worst-case guarantees, one that can answer "what position is this key?", and a lock-free one that many threads can change at once (§1.1). It ships as six crates, one of which builds the sklist command-line tool (§1.5). It is a library that other programs embed, with no network or disk use (§1.3, §4.1). Its target users are systems, concurrency and storage engineers (§1.4).

The problem, concretely

You need a map that keeps keys sorted: look up, insert, delete, scan a range (§1.1). LevelDB and RocksDB use a skip list as the in-memory write buffer, Redis sorted sets use one for rank queries, and Java ships a lock-free one (§2.2). Three naive answers fail.

The first is a single sorted linked list. With every node at height 1, the structure collapses into exactly that list and search costs O(n) (P1, §8.9). A skip list gives each node a random "tower" of extra pointers, so search is O(log n) in expectation with no rotations (P1, §2.2). Balanced trees need rotations, which are notoriously hard to make lock-free (Alternative Architectures, ALT-1).

The second is trusting the randomness. An attacker who can predict the random number generator can craft keys that push towers into a bad shape and send search toward O(n) (T1, T2, MM1). The blueprint's answer is a second variant with no randomness at all (ADR-10).

The third is locking. A global lock makes writes a bottleneck, and a lock per node contradicts the lock-free goal (ADR-12, ADR-09). Without locks, a thread may hold a pointer to a node another thread just unlinked, so freeing it at once is a use-after-free, and reusing its address is the ABA bug (P8, MM8, §8.8). P8 calls freeing on unlink "the most common lock-free bug".

How it works, end to end

Follow one insert(k, v), then one concurrent remove(k), through §3.1's boxes, each a crate (§1.5):

 Application (sklist CLI / library user)
        |  get / insert / remove / range / rank / select
 skl-core : OrderedMap trait + LevelGenerator + Rng + Comparator
        |                    |                          |
 skl-list (sequential)   skl-variants               skl-concurrent (lock-free)
  Node, head sentinel     DetSkipList (1-2-3)         ConcurrentSkipList, MarkedPtr
  search via update[]     IndexableSkipList (spans)   find() snips marked nodes, Ebr
        +------------------+---------------------------+
 skl-bench : height distribution, O(log n) check, concurrent scaling, loom
  1. skl-core holds only shared vocabulary: the OrderedMap trait, LevelGenerator (the coin flips that pick a tower height), Rng (a fast random number generator, under 5 ns per call), Comparator and SklError (§3.3, ADR-04, ADR-07). It has no data structure and no unsafe (§3.3).
  2. skl-list is the plain sequential list. insert runs the search, which records in update[i] the last node before the key at each level. It then asks LevelGenerator for a height, allocates a Node, splices it in across its tower, raises level if the tower is taller than any so far, and adds 1 to len (§3.4, §8.3).
  3. skl-variants holds DetSkipList, shaped by a rule instead of luck (§8.6), and IndexableSkipList, whose pointers also count the level-0 nodes they skip (§3.3, §8.7).
  4. skl-concurrent holds ConcurrentSkipList, whose pointers are MarkedPtrs: an atomic pointer whose low bit means "deleted" (§8.8). Its find() records preds and succs for every level and cuts out any marked node it passes (§3.3).
  5. A concurrent remove(k) runs find(), marks the victim's pointers top-down, then calls find() again, whose clean-up unlinks it at every level, as any passing traversal would (§8.8, §22). The node is retired to Ebr, the epoch-based reclaimer, which frees it only when no thread can still read it: straight after the marks in §3.5, only after the unlink in §23 and T4 (§3.5, §23, T4).
  6. skl-bench checks heights, the O(log n) claim, concurrent scaling and runs the loom model checker. skl-cli is the sklist tool (insert, get, del, range, rank, select, load, stats, bench, viz) (§3.3).

The sequential variants are !Send + !Sync; only ConcurrentSkipList is Send + Sync (§3.2, §4.1). Nothing is stored on disk, so a crash loses the data, by design (§3.2).

The core ideas

Towers and the coin flip (P1, ADR-05, §8.5)

Every key is in the bottom list, level 0, in sorted order. Each key also gets a tower: it joins level 1 with probability p, then level 2 with probability p again, and so on, like flipping a coin until it comes up tails (P1, §3.3, §8.5). The coin-flip rule is a geometric distribution, and a cap called max_level stops any tower growing past a fixed height (I12, P11).

Quantity Formula p=1/2 p=1/4
Expected tower height 1/(1−p) 2 4/3
Expected total forward pointers n/(1−p) 2n 4n/3
max_level ⌈log_{1/p}(n)⌉ ⌈log₂ n⌉ ⌈log₄ n⌉

Source: §8.5 and capacity rows C1, C2, C6. Level 0 alone is the truth: len counts level-0 nodes and upper levels are only an index (P4). A node's height is fixed at birth and never changes (MM3).

The default is p = 1/2 and max_level = 32 (§4.2, ADR-05, ADR-06). The blueprint gives at least four different search costs at p = 1/4: about (4/3)·log₄(n) + 4/3 in §8.5's table, about 2 log₄ n in §4.2, about 1.5·log₄(n) in Performance Engineering, and 4·log₄(n) + 4/3 from §8.5's own general formula (1/p)·log_{1/p}(n) + 1/(1−p). The chance of a tower reaching level i is p^(i−1) in §8.5 and in Phase 1's distribution fixture, but p^i in Phase 1's objectives and the glossary (§8.5, §13, Glossary). None is resolved here.

Search and the update[] array (§8.2, §8.3, MM2)

Start at the head sentinel on the top level. Move right while the next key is smaller than the target. When you cannot, drop one level and repeat, and stop after level 0 (§8.2, glossary term "drop-down search"). Searching for 45 in the blueprint's 7-key list (10 to 70, p = 1/2, four levels):

Level Next key Decision
3 50 (not < 45) drop
2 30 (< 45), then 50 advance to 30, then drop
1 40 (< 45), then 50 advance to 40, then drop
0 50 drop; 45 is absent (§8.2)

Insert and delete use the same walk and record the last node visited per level in update[]; for 45 that is HEAD, 30, 40, 40 from the top down (§8.2). The blueprint calls the array "the whole algorithm" (MM2). Inserting 35 with height 2 is two pointer swaps per level, 30.forward[i] = 35 and 35.forward[i] = 40 (§8.3). Deleting 30 repoints each predecessor to 30's successor, then shrinks level while the top level is empty (§8.4, I4).

The level-shrink loop is written two ways, with different level numbering: level > 0 && head.forward[level] in I4, level > 1 && head.forward[level-1] in §8.4 and FM-3. An emptied list may reach level 0 in §8.9, but Phase 4's remove_last_key expects level 1 (I4, §8.4, FM-3, §8.9, §16).

The 1-2-3 deterministic list: balance by rule, not luck (§8.6, I5, ADR-10)

Replace the coin flips with one rule: between two neighbouring nodes at level i+1 there must be exactly 1, 2 or 3 nodes at level i. This is the gap invariant (I5). It is the same thing as a B-tree with 2 to 4 children per node, drawn sideways (§8.6, MM4):

B-tree 1-2-3 skip list (§8.6)
Split when a node reaches 5 children Raise a node one level when a gap reaches 4
Merge when a node drops to 1 child Lower a node when a gap reaches 0

A raise or lower can ripple upward, like a B-tree split (§8.6). A gap of 0 would let search skip a key range, and a gap of 4 or more degrades the worst case to O(√n) (I5). Worked example: four level-1 nodes sit between two level-2 nodes, so the gap is 4. Raising the second one splits it into gaps of 1 and 2 (§8.6). Worst case is O(log n) with no randomness (§8.6, MM4).

The blueprint gives two different worst-case height bounds. §5.4 says ceil(log_{4/3} n), about 2.4 log₂ n. Scalability Analysis and Phase 7's acceptance test say ⌈log₂ n⌉ + 1, which is 15 at n = 10,000 (§5.4, §19, Scalability Analysis).

Spans: rank and select with no second structure (§8.7, I6, I7, MM5)

Give each forward pointer a span, the number of level-0 nodes it jumps over, destination included (§8.7). Rank is the number of keys before a key, and select is the key at a given position. Rank sums spans along the search path, and select spends a count down the same path, both O(log n) (§3.3, §8.7). In the blueprint's list, level 2 is HEAD -(3)-> 30 -(3)-> 60 and level 0 holds 10, 20, 30, 40, 50, 60 (§8.7).

§8.7 prints two worked traces on this list, and neither matches its own definitions, so they are quoted here as printed, not as correct answers:

Trace in §8.7 What it prints Why it does not fit
rank(key=50) adds span 3 to reach 30 on level 2, then drops through levels 1 and 0 as if 30's next level-0 key were 50; prints rank = 3 rank counts keys before 50, and level 0 has four (10, 20, 30, 40); 30's level-0 successor is 40
select(i=4) starts with remaining = 4, spends 3 to reach 30, then 1 to reach 40; prints 40 its own label, §20 and the glossary call select 0-indexed, and position 4 counted from 0 is 50; 40 is the 4th key counted from 1

The blueprint does not resolve them (§8.7, §20, Glossary). The span definition is also split. §3.3 and §8.7 count the destination node, but I6 and FM-5 count only the nodes "strictly between" the two ends (§3.3, §8.7, I6, FM-5).

On insert, spans of pointers that jump over the new node go up by 1, and the new node's own spans come from subtraction using the update[] positions. Delete reverses it. Nothing is recounted (§8.7, P14). Two identities must always hold: level-0 spans sum to len (I6), and rank(select(i)) == i (I7).

Mark, then snip: a lock-free delete (§8.8, P6, MM6, MM7)

Lock-free means a stalled thread can never block the others (§4.1). To delete without a lock, split the delete in two. First logical deletion: set the low bit on the victim's pointers so every reader treats the node as gone (MM6). Then physical unlink: any traversal that meets a marked node swings the predecessor's pointer past it with a compare-and-swap (CAS: change a value only if it still holds what you last saw). This clean-up by whoever passes is helping (§8.8, MM7). Marking must come first, or a concurrent insert could splice a node after one being removed and lose it (P6).

Insert follows the mirror order. find() fills preds and succs, the new node's pointers are set with plain stores before anyone can see it, and one CAS on preds[0].next[0] publishes it. That is the insert's linearization point, the instant the operation takes effect (§8.8, ADR-13). Upper levels are linked bottom-up afterwards, and a stall there costs only index quality, never correctness (§8.8).

The delete's linearization point is stated two ways. §3.5, §8.8, §11.5, §22, ADR-13, MM6 and hard question 18 put it on the level-0 mark, and ADR-13 rejects the level-top CAS. §3.2 ("first mark on top-level pointer"), P7 ("top-level mark CAS"), the glossary ("first mark on the node"), T3 and Compatibility Guarantees ("top-down mark") point at the top (§3.2, P7, T3, ADR-13, Glossary). I8 says remove "marks level 0 first" and insert CASes level 0 "last", the reverse of §8.8 (I8, §8.8).

The ABA bug is a pointer going A, B, A between a read and a CAS, so the CAS wrongly succeeds after B was freed and its address reused. The design blocks it three ways: marked nodes are cut out rather than reused, Ebr forbids address reuse while a thread may hold the pointer, and find() checks the mark before a CAS (§8.8, T5).

Epoch-based reclamation: when is it safe to free? (§5.4, §23, P8, I10, MM8)

Each thread pins itself to the current epoch (a global counter) while it touches the list, and unpins afterwards. A node removed from the list is retired: put on a per-thread list for the current epoch, not freed (§5.4). The global epoch can advance only when every thread is either unpinned or already on the current epoch. Then the retire list from two epochs back is freed, since no thread can still hold a reference into it (§5.4, P8, I10). Epochs cycle 0, 1, 2 (§5.4).

The price: one thread pinned and stuck stops all reclamation, so retired nodes pile up (MM8, T7, ADR-14). Orderings: Acquire for traversal loads, AcqRel for a successful CAS, SeqCst for the epoch pin and advance check (§5.4, ADR-15, I11). Two places disagree: Compatibility Guarantees puts SeqCst on the level-0 insert CAS (§5.4 and §11.5 say AcqRel), and Phase 11 pins with Acquire/Release and advances with an AcqRel CAS, not SeqCst (Compatibility Guarantees, §5.4, §11.5, §23).

The trade-offs — where engineers disagree

Lock-free instead of locks (ADR-12)

Chosen: a lock-free ConcurrentSkipList with marked pointers, CAS and helping, because it scales to high core counts, cannot deadlock and shows linearizability techniques (§9). Rejected: per-segment locks (lock striping) and one global RwLock around the whole list (§9). When the rejected choice is right: striping wins at low-to-moderate core counts and low write contention, where simpler, easier-to-verify code matters more than the last 2x of scaling. A global RwLock wins for read-mostly workloads on few cores that need a snapshot-consistent iterator, which lock-free cannot offer (§9).

Epoch-based reclamation instead of hazard pointers (ADR-14)

Chosen: Ebr, because its common path is cheap: a pin is one atomic load plus a store (§9). Rejected: hazard pointers, reference counting with Arc, and a deferred free with a quiescent fence (§9). Hazard pointers cost extra stores on every pointer load, and Arc costs an atomic count on every dereference (§9). When the rejected choice is right: hazard pointers win when bounded memory and predictable reclamation delay are required, since Ebr can stall reclamation indefinitely if one thread fails to quiesce. Arc wins for low-contention structures where simplicity beats throughput (§9).

A 1-2-3 skip list for worst-case guarantees (ADR-10)

Chosen: DetSkipList, a skip list with the gap rule, because it shows worst-case O(log n) without introducing a separate tree structure (§9). Rejected: a treap (still randomized), AVL or red-black rebalancing, and a skip list with explicit rebalance triggers (§9). When the rejected choice is right: a red-black tree wins when the worst-case structure must also be the production one, with the tightest constant and lowest space because there are no towers, and the codebase wants an in-place pointer tree. The Linux kernel rbtree is the blueprint's example (§9).

p = 1/2 instead of p = 1/4 (ADR-05)

Chosen: p = 1/2, which gives the lowest constant on expected search comparisons and the simplest coin flip, one random bit. The API exposes p_inv, so callers can override it (§9). Rejected: p = 1/4, and p = 1/e, the theoretical optimum, which is irrational (§9). When the rejected choice is right: p = 1/4 wins for memory-bound, cache-sensitive workloads, about 1.33n pointers against 2n, trading a higher search constant that fewer cache misses hide. Redis t_zset uses 1/4 (§9).

Roads not taken (Alternative Architectures, Deferred Features Register)

Red-black or AVL tree (ALT-1) wins for hard worst-case latency with the smallest constant and memory (Linux rbtree, C++ std::map). It lost because rotations are hard to make lock-free, and DetSkipList covers the worst-case niche (ALT-1, ADR-10). B-tree (ALT-2) wins when cache-line or disk-page misses dominate, since high fan-out keeps the tree short (BTreeMap, database indexes). It lost because splits and merges under concurrency need locks or complex lock-free protocols (ALT-2, §2.4).

Lock-free binary search tree (ALT-3) wins as a pointer-lean lock-free tree for read-mostly sets. It lost because its operation-record protocol is harder to model-check than find plus helping and it has no clean order-statistics story (ALT-3, §20, §22). Learned index (ALT-4) wins on near-O(1) lookup for static, read-mostly data. It lost because inserts and deletes invalidate the model (ALT-4, MM1).

Three features are deferred (Deferred Features Register). A NUMA-aware allocator waits for benchmarks showing more than 15 % throughput loss from cross-socket pointer chasing above 8 cores. RCU or seqlock snapshot scans (and a SeqLockSnapshot) wait for a consumer that needs a transactionally consistent range aggregate or backup (§24, ADR-25).

What must never be false

  • I1: level 0 holds every key in strictly ascending order. Noticed by assert_sorted() and by stats comparing len with the counted level-0 nodes. Not recoverable: panic and drop it.
  • I2 and I3: a node at level i appears at every level below i, and each level is a sorted subsequence of the one below. Noticed by walking every node (I2) and assert_levels_consistent() (I3).
  • I4: list.level equals the tallest tower present. Noticed by asserting the top head pointer is non-null after each remove, and by viz showing stale empty rows.
  • I5: in DetSkipList every gap is 1, 2 or 3. Noticed by assert_gap_invariant(); a spike in the fix-up depth histogram in stats signals a degenerate input pattern.
  • I6 and I7: in IndexableSkipList each span equals the level-0 nodes it skips, level-0 spans sum to len, and rank(select(i)) == i. Noticed by assert_spans() and a 10,000-case property test.
  • I8: a key is present in the concurrent list exactly when its level-0 pointer is set and unmarked. Noticed by the loom harness.
  • I9: every marked node is eventually unlinked. Noticed by an 8-thread, 50 %-delete stress test that walks every level afterwards, and by counting CAS-helps per operation.
  • I10 and I11: no node is freed while a pinned thread could read it, and no atomic uses a weaker ordering than required. Noticed by loom with an allocator that poisons freed memory, and by Miri.
  • I12: no tower exceeds max_level, and the head always carries max_level slots. Noticed by a debug assert in insert and the level_histogram gauge; a non-zero top bucket means the cap is hit.

What breaks in production

FM-1: wrong order or a lost key. iter() yields keys out of order, or get misses a key that was inserted. The cause is a splice bug where update[i] is wrong at some level. It is caught by a differential test against BTreeMap, assert_sorted() and the viz dump. There is no automatic recovery, because the structure is corrupt (FM-1).

FM-4: search degrades toward O(n). Latency grows with n and the level histogram looks flat, from a fixed or biased seed or a misconfigured p or max_level. The benchmark fails when mean height differs from 1/(1−p) by more than 20 %. Recovery is to switch to DetSkipList (FM-4, T1).

FM-6: concurrent lost update or torn read. insert returns but another thread's get misses the key, or two inserts of the same key both see no prior value. The causes are stale preds/succs, an ordering weaker than required, or helping that unlinks a live node. Detection is loom. There is no automatic recovery; every CAS is reviewed against the proof (FM-6, I8, I11).

FM-7: use-after-free or double free. A crash or sanitizer report on a CNode field, or a corrupted value. The cause is an epoch mistake: a thread reads a retired node before the epoch advances, or a Guard is dropped too early. It is detected by Miri, AddressSanitizer and loom with injected epoch pauses; the blueprint says a crash is preferable to silent corruption (FM-7, I10).

FM-8: livelock or a CAS storm. Throughput collapses and cas_retry_rate spikes under contention on a narrow key range; the runbook alert is 100 retries per operation. The find() loop backs off and restarts from the head after K retries (FM-8, T6).

FM-10: arena exhaustion. With the optional arena allocator, memory climbs under insert-and-delete churn although len() is flat, because the arena never frees individual nodes and a lagging Ebr pins slabs. Detection: the ebr_retired_nodes gauge and a live-to-allocated ratio below 0.5. Recovery is a restart or a rebuild into a fresh arena; use the arena only for bounded lifetimes (FM-10, ADR-08).

Threats worth knowing (Threat Model):

  • T1, an adversary with a leaked seed builds tall, lopsided towers. DetSkipList is the hard answer, the max_level cap bounds height, and a maximum height above 3 times the expected height alerts (T1).
  • T2, a predictable random generator. LevelGenerator::new() must seed from the OS, never from a fixed or clock-derived seed; explicit seeding is for tests (T2, P3).
  • T7, memory exhaustion. The list does not cap its size, so callers apply a quota, and a stuck pinned thread builds a retired-node backlog with an alert metric (T7).
  • T9, a caller treating a weakly consistent iterator as a snapshot (T9, MM10).

Where the blueprint's numbers disagree, both are given:

  • Retired-node backlog. §4.1, M13 and C10 bound it at threads × batch (512 at 8 threads), while Phase 11's acceptance test allows up to 3 × (threads × threshold) (§4.1, §23).
  • Insert versus BTreeMap. M3 allows at most 2x, Phase 13's acceptance test allows 2.5x, and Appendix B says within 2x (Performance Engineering, §25, Appendix B).
  • Wait-free or not. §2.3 and §3.3 say helping makes delete wait-free for the deleter, but §4.1 says lock-free, not wait-free (§2.3, §3.3, §4.1).
  • Bench regression gate. The M-table fails a build on a regression above 10 %, and Phase 13 gates at 1.10× the baseline, while Testing Strategy and the bench workflow fail on 5 % (Performance Engineering, §25, Testing Strategy, Build and Release Engineering).

How it compares

  • Redis t_zset chose p = 1/4, one thread, and a hash map beside the skip list for O(1) member-to-score lookup, with per-pointer spans like IndexableSkipList. That fits a memory-frugal sorted set that scales by running more processes (Comparative Table).
  • LevelDB / RocksDB memtable chose a skip list as a write buffer only: inserts, deletes as tombstones, one writer with concurrent readers, the whole structure dropped at flush. That fits an LSM tree, where the memtable lives briefly and per-node frees would be wasted (Comparative Table, §2.4).
  • java.util.concurrent.ConcurrentSkipListMap chose the same level-0 CAS linearization point but leaves reclamation to the JVM garbage collector, which is fine wherever a collector is already paid for. This design forgoes it to teach reclamation (Comparative Table, ADR-01).
  • crossbeam-skiplist chose the maintained crossbeam-epoch crate over a hand-rolled one, the better choice for production Rust today. Here it is the differential oracle (Comparative Table, ADR-18, ADR-22).

Questions to test yourself

If you only remember three things

A skip list buys balance with random tower heights and a cap, and when luck is not acceptable the 1-2-3 variant buys the same O(log n) with a rule instead (P1, I5, ADR-10). A lock-free delete is two steps, mark and then snip, with any traversal allowed to finish the job (P6, MM6, MM7). Freeing memory in a lock-free structure is the hardest part, so nothing is freed until every thread has moved past the epoch in which it was retired (P8, I10, MM8).

Words used here

  • Skip list: stacked sorted linked lists in which level 0 holds every node and higher levels hold random subsets (Glossary, §8.1).
  • update[]: the per-level predecessors a search records, used to splice or unlink (Glossary, MM2).
  • Gap invariant: the rule that 1 to 3 nodes sit between neighbours one level up (I5, §8.6).
  • Span: how many level-0 nodes one pointer jumps over; it makes rank and select cheap (Glossary, I6).
  • CAS (compare-and-swap): an atomic update that succeeds only if the value is unchanged (Glossary).
  • Marked pointer: a pointer whose low bit means "logically deleted" (Glossary, §8.8).
  • Linearization point: the single atomic step at which an operation takes effect (Glossary, ADR-13).
  • Epoch-based reclamation (EBR): free a retired node once every thread has passed its epoch (Glossary, I10).
  • loom: a Rust model checker that explores thread interleavings exhaustively (Glossary, ADR-17).
