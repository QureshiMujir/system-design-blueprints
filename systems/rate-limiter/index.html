In one paragraph

A rate limiter decides, for every incoming unit of work (an HTTP request, a login attempt), whether the caller is still inside its allowance. This design is a Rust library plus an optional operator CLI. It targets 900 ns at p99 when the state lives in-process, and 5 ms at p99 when many servers share one allowance through Redis (§4). Its defining idea: a limiter shared across N servers is never perfectly exact. Every topology trades a quantified amount of over-admission for latency and coordination cost, and the design derives each such number (§4 "the one defining property"). The embedding service runs it; the backend is chosen per quota, not per code fork (§1, §3 Backend).

The problem, concretely

Your API allows each customer 1,000 requests per second. The naive fix is a counter in each server's memory. It fails as soon as you run more than one server: each of 8 servers enforces its own 1,000 per second, so one customer spread across all eight can get up to 8 × 1,000 through. The limit is multiplied by the number of servers, and the error has no ceiling as servers are added (§32, §35.1). Put the counter in one shared Redis and every server agrees. But now every request pays a network round trip (§4: 0.6 ms median instead of 80 ns). And when Redis is unreachable you must decide in advance whether to let everyone through or block everyone (§6 P4, §24 FM-1). Add a flood aimed at one key and the shared store itself becomes the target (P13, §23 T1). The blueprint's whole structure answers those three pressures: accuracy across servers, latency, and what happens when the shared piece is down.

How it works, end to end

Follow one request through the boxes of §3's diagram:

 Client → Middleware (KeyExtractor → Key{tenant, scope, value}; hierarchy IP→user→route→tenant→global)
        → Hot-Key Pre-Filter (local Count-Min Sketch; rejects before the coordination hop)
        → Limiter (exactly one of six algorithms per quota)
        → Backend (where per-key state lives: in-process shards | Redis + atomic Lua | cluster | gossip)
        → Circuit Breaker + FailureMode (fail-open or fail-closed — never a silent default)
        → Decision { Permit{remaining, reset} | Reject{retry_after, reset} }
        → Protocol layer (RateLimit-* headers; on reject HTTP 429 + Retry-After)
  1. Middleware (ratelimiter-tower / -axum / -hyper / -actix) turns the request into a Key with three parts (tenant, scope, value) and walks the layers in order IP → user → route → tenant → global. The first layer to reject stops the request before any layer's counter is touched twice (§3, P6).
  2. Hot-key pre-filter (ratelimiter-backend/src/sketch.rs) keeps a small fixed-size table of estimated request rates (Count-Min Sketch) per shard. If a key's estimated rate already exceeds a coarse ceiling, it is rejected locally, before the network hop to the shared store is spent (§3, §21, MM5).
  3. Limiter (ratelimiter-core) dispatches to one of six algorithms (token bucket, leaky bucket, fixed window, sliding log, sliding counter, GCRA), chosen per quota, never blended (P1).
  4. Backend holds the per-key state. In-process it is a sharded concurrent map (DashMap, ADR-04); centralized it is Redis running one atomic Lua script per algorithm (ratelimiter-redis); distributed it is a sharded cluster or local counters reconciled by gossip (§3, §14, §15, §19, §20).
  5. Circuit breaker (ratelimiter-redis/src/client.rs, §10) wraps every backend call. After repeated failures it opens, and the configured FailureMode decides the answer without touching the backend (§3, §8.12).
  6. Protocol layer renders the decision as IETF RateLimit-* headers, and on rejection as HTTP 429 plus Retry-After in seconds, rounded up (§8.9). §3 labels this box ratelimiter-protocol; the §10 tree places it in ratelimiter-core/src/headers.rs.

A monotonic clock (ClockSource, §8.8) feeds every box. Wall-clock time is used only once, at startup, to align fixed windows, and never on the hot path (P2).

The core ideas

Token bucket: a budget that refills (§8.1)

State per key: {tokens, last_refill}. On each request, add elapsed × rate/period tokens, cap at burst, then spend cost if enough remain; otherwise reject with retry_after = ceil((cost − tokens) / (rate/period)). With rate 10/s and burst 5, starting full: five requests at t=0 all pass (tokens 5→0), a sixth is rejected with retry_after = 1 ÷ 10/s = 100 ms, and an empty bucket is full again after 5 ÷ 10/s = 0.5 s. Memory: 16 bytes per key (§8.6 table).

Leaky bucket: the same budget seen from the output side (§8.2)

State: {level, last_drip}. The level drains at rate/period; a request is admitted if level + cost ≤ burst, then raises the level. It smooths the output rate regardless of how bursty the input is. That makes it the dual of the token bucket, which bounds bursts but smooths nothing.

Fixed window: cheap, with a cliff at the boundary (§8.3)

State: {count, window_start}; window_id = now / period by integer division. Reset the count when the window id changes. The known weakness: a client can send up to 2 × limit inside a real one-period span that straddles a boundary. That is the price of O(1) state and no per-request scan.

Sliding log and sliding counter: exact vs. approximate (§8.4, §8.5)

A sliding log stores every admitted timestamp inside the last period. It is exact but grows with traffic, so the design caps it (max_events, invariant I5). A sliding counter keeps only {current, previous, window_start} and estimates the in-window count as current + previous × (1 − f), where f is the fraction of the current window elapsed. It costs 24 bytes (§8.6 table). §8.5 cites Cloudflare's figures for its error: at most 6% in the worst case (a spike exactly at a boundary) and at most 1% under steady traffic. That 6% is the ε the accuracy invariant I1 allows it (§4).

GCRA: the token bucket compressed into one timestamp (§8.6, §8.10, MM2)

State: a single tat (theoretical arrival time) per key, 8 bytes. With increment = period/rate and tolerance dvt = (burst − 1) × increment: new_tat = max(now, tat) + increment; allow_at = new_tat − dvt; admit if allow_at ≤ now and store new_tat, else reject with retry_after = allow_at − now. The blueprint's worked trace (rate 10/s, burst 5, so increment 100 ms, dvt 400 ms):

t (ms) tat before new_tat allow_at decision
0 0 100 −300 Permit (burst)
10 100 200 −200 Permit
20 200 300 −100 Permit
30 300 400 0 Permit
40 400 500 100 Reject, retry after 60 ms
100 400 500 100 Permit

The table admits four requests in the first 30 ms and refuses the fifth (t=40) until t=100 ms. §8.10's own summary sentence says "five" are admitted, but its table, which is the §8.6 formula's output, shows four. Tested against new_tat, that formula gives a back-to-back burst of burst − 1 (recorded in blueprints/ERRATA.md). GCRA keeps 8 bytes where the token bucket keeps 16 (§8.6 table), and MM2 calls the two encodings equivalent views of the same state; the one-integer-per-key footprint is why GCRA is the default (ADR-10).

The over-admission bound: how wrong can N servers be? (§8.7, I2, MM4)

With a central store and an atomic script, decisions are exact at the store. Over-admission appears only when a server cannot reach it and is configured fail-open, bounded by burst × (nodes partitioned). With local counters reconciled asynchronously, each of N nodes can admit at its local rate r for the replication lag L before learning what the others did, so over_admission ≤ N × r × L. Worked example: 8 nodes × 1,000 req/s × 0.05 s = 400 excess admissions in the worst window, 0.4× one node's per-second budget, converging to 0 as L → 0 (the centralized mode).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust 1.75+ stable, for a GC-free hot path and the native async ecosystem (§1). Rejected: Go, C++, Java/JVM. When the rejected choice is right: Go, for a team with zero Rust depth shipping a low-QPS internal tool where the 250 µs p99 budget is irrelevant. (§1 cites that 250 µs budget to §4, but §4 has no such row; §4's in-process p99 is 900 ns.)

Default algorithm: GCRA (ADR-10)

Chosen: GCRA, for its one-integer-per-key footprint (§8.6). Rejected: token bucket as the default. When the rejected choice is right: when the operator's mental model is literally "N per second, burst M" and the code-review complexity of GCRA outweighs the memory saving.

Where shared state lives: Redis 7 + Lua (ADR-05)

Chosen: Redis 7 with one atomic Lua script per algorithm, for atomic scripting (I8) and operational ubiquity. Rejected: Memcached, a custom UDP protocol, a gRPC service. When the rejected choice is right: a custom gRPC service, when sub-100 µs cross-node latency is mandatory and Redis's protocol overhead is unacceptable.

What to do when the backend is down: no default (ADR-11, P4, MM7)

Chosen: no default. The operator must pick FailOpen or FailClosed at construction, and the type has no Default impl (§11, I6). Rejected: a hard-coded fail-open or fail-closed. When the rejected choice is right: a hard-coded fail-open, for an internal, low-stakes dev-environment limiter where operator friction must be minimized. The deeper point (MM7): fail-open protects availability and fail-closed protects containment. Which is "safer" depends on the API's threat model, so one blanket policy across a whole fleet is itself a design smell.

Hot-key detection: a sketch, not exact counts (ADR-21)

Chosen: a local Count-Min Sketch, for sub-linear memory at high key cardinality (32 KiB per shard regardless of how many keys exist, §33 item 9). Rejected: exact per-key counting, or no detection. When the rejected choice is right: exact counting, when the key space is small and bounded (< 10k keys) and false-positive collisions are unacceptable.

Header protocol: the IETF draft (ADR-08)

Chosen: draft-ietf-httpapi-ratelimit-headers, forward-compatible and standards-track. Rejected: GitHub-style and Twitter-style legacy headers. When the rejected choice is right: GitHub-style, when every consumer already hard-codes GitHub's exact header names. The design still ships the legacy shapes as opt-in adapters (P5).

Roads not taken (§35)

Pure client-side estimation (§35.1): each node counts alone, with no coordination. It wins for extremely latency-sensitive, loss-tolerant work such as best-effort telemetry sampling, where even gossip's 50 ms convergence window is too much; nginx limit_req works this way. It is rejected because the over-admission bound becomes unbounded the moment there is more than one node.

Kernel-level enforcement with eBPF/XDP (§35.2): admission happens before a packet reaches userspace. It wins when the protecting process may itself be starved of CPU during an attack (Cloudflare's and Meta's published XDP layers). It is rejected because it cannot see the key's tenant/route semantics and sits below this project's HTTP-level scope; it is parked in the deferred register as a research track (§36).

A single global sequencer (§35.3): one process orders every decision. It wins for a low-QPS workload where exactness matters more than the single point of failure (a single-writer Redis is effectively this at modest scale). It is rejected as the general answer because it hard-codes "exact but unscalable" instead of exposing the consistency dial (MM3).

What must never be false

  • I1: the admitted rate over any window of at least one period never exceeds rate × (1 + ε), with ε = 0 for token/leaky bucket, GCRA and sliding log, and ≤ 6% for sliding counter. Noticed by the conformance property test (§18); telemetry ratelimit_admitted_rate_error.
  • I2: total over-admission across N nodes is at most N × burst_per_node in the worst window. Checked by the cluster fixture cluster/over_admission (§19); ratelimit_over_admission_total.
  • I3: the clock read at decision time never goes backwards within one process. A debug assertion in now_ns; telemetry ratelimit_clock_regression_total (§21.2 and FM-2 spell it ratelimiter_clock_regression_total).
  • I4: every Reject carries a non-negative retry_after; the type makes a negative one unrepresentable.
  • I5: per-key memory never exceeds the §4 ceiling regardless of traffic shape. The sliding-log event cap enforces it; fixture algorithms/sliding_log/memory_cap and ratelimiter_key_memory_bytes detect it.
  • I6: a backend error never silently defaults. FailureMode is a required constructor argument, so the compiler enforces it; ratelimiter_failure_mode_invocations_total counts uses.
  • I7: every decision emits exactly one telemetry event (ratelimiter_decisions_total; fixture metrics/no_double_count).
  • I8: a Lua script's decision is atomic with respect to concurrent callers on the same key (fixture redis/atomicity_under_concurrency; ratelimiter_redis_script_errors_total).
  • I9: one tenant's key namespace never collides with another's. Key::wire separates the three parts with NUL bytes (ADR-24); fixture composition/per_tenant and the ratelimiter_cross_tenant_denied_total counter watch it.
  • I10: gossip-propagated counters converge within the §4 window (≤ 50 ms across 16 shards) once traffic stabilises (fixture gossip/convergence; ratelimiter_gossip_convergence_ms).
  • I11: an open circuit breaker always half-opens and probes on a bounded schedule (fixture redis/circuit_breaker; ratelimiter_circuit_state).
  • I12: a request of cost C consumes exactly C units (property test; ratelimiter_cost_applied_total).
  • I13: a malformed or replayed request never advances a key's state twice for the same idempotency scope (fixture algorithms/*/replay; ratelimiter_replay_rejected_total).
  • I14: every invariant above is exercised by at least one fixture or property test; a CI gate blocks the release otherwise (conformance_invariant_coverage).

What breaks in production

  • FM-1: everything is rejected. FailClosed engaged during a backend outage. You see a 429 spike across all keys. The breaker half-opens on its schedule (RTO ≤ 5 s, §4), and an operator can force a reset via the CLI.
  • FM-2: fixed-window ids go wrong. A wall-clock step during epoch alignment makes window ids jump in the logs. Keeping wall-clock off the hot path (P2) prevents it structurally; recovery is re-deriving the epoch alignment offset and restarting.
  • FM-3: the Redis breaker keeps opening. A network partition or Redis overload shows up as sustained ratelimiter_redis_script_errors_total. The half-open probe retries every RTO interval while the operator investigates and scales Redis.
  • FM-4: sliding-log memory climbs. The I5 cap was set too high for the traffic shape; ratelimiter_key_memory_bytes trends up. Eviction at the cap holds the line until max_events is lowered and redeployed.
  • FM-5: more over-admission than the formula predicts. More nodes were partitioned than assumed, or lag L was underestimated. ratelimiter_over_admission_total exceeds the formula's prediction. The bound is a ceiling, not a self-correcting mechanism: re-derive it with the real N and L, and consider the centralized fallback.
  • FM-7: the pre-filter rejects a legitimate spike. The sketch ceiling was set too close to the real quota. It is visible as a gap between sketch rejects and real algorithm rejects; raise the ceiling (§21.9).
  • FM-10: a lost update under concurrent Redis calls. A code path used WATCH/MULTI/EXEC instead of EVALSHA. The I8 fixture fails in CI, and it must never reach production; revert to the atomic script and re-audit every Redis call site.
  • FM-11: a replayed request double-consumes quota. A middleware layer is missing the idempotency-scope check. The tell is that ratelimiter_replay_rejected_total stays at zero when it should not; add the check at the missing layer.

Threats a reader should know (§23): T1 a flood aimed at one hot key, answered locally by the sketch pre-filter (P13); T2 memory exhaustion by minting unlimited distinct keys, answered by the per-key cap (I5); T6 a forged IP or tenant header used as the key, answered by trusting only headers set after authentication middleware; T7 fail-open chosen by omission, made impossible by I6; T10 credentials leaking through the operator CLI's inspect output, answered by Key::redacted() as the default form.

How it compares

  • Redis + redis-cell chose GCRA as a single Redis command (CL.THROTTLE), Redis-resident only, with no built-in hierarchy and no headers. That is fine when "one Redis, one command, no client-side algorithm logic" is the whole requirement and centralized-only is acceptable (§32).
  • Envoy ratelimit chose descriptor-based hierarchical composition over a per-request gRPC call to a central service backed by Redis, with token bucket and custom headers. That fits many heterogeneous proxies sharing one rate-limiting service, where a language-agnostic RPC boundary matters more than in-process latency (§32).
  • Kong rate-limiting chose pluggable local/cluster/Redis policies inside an existing proxy platform, with X-RateLimit-* headers. That fits teams already running Kong, where reusing its plugin lifecycle beats adding a new library (§32).
  • nginx limit_req chose a per-worker leaky bucket with no cross-instance coordination and status codes only. That fits a single nginx instance needing absolute minimum latency, at the cost of the per-instance multiplier beyond one node (§32, §35.1).

  2. Derive the over-admission bound for N=16, r=2000/s, L=20ms, and state which topology change would drive it to zero. — Hint: §8.7's formula; §33 item 7 shows the arithmetic pattern.

If you only remember three things

A rate limit is a budget, not a switch: every algorithm is a different way of answering "how much is left" (MM1). GCRA is the token bucket compressed into one timestamp per key, which is why it is the default (MM2, ADR-10). Across many servers exactness costs coordination, so the design is a dial from "exact, one round trip" to "local, eventually consistent, with a computable over-admission ceiling" (MM3, MM4), and it refuses to guess what to do when the shared store is down (P4).

Words used here

  • Admission control: deciding whether a unit of work may proceed against a quota.
  • Burst: the most a key may consume instantly before the steady rate applies.
  • Quota: the policy (algorithm, burst, rate, period), immutable per limiter.
  • Key: the identity being limited: tenant, scope, value.
  • Backend: the narrow trait that says where per-key state lives.
  • Circuit breaker: the state machine that stops calling a failing backend and probes it later.
  • Fail-open / fail-closed: admit, or reject, when the backend returns an error.
  • Count-Min Sketch: a fixed-memory approximate frequency counter, used to spot hot keys.
  • GCRA: Generic Cell Rate Algorithm; one theoretical-arrival-time per key.
  • Over-admission: traffic admitted beyond the nominal quota; bounded but nonzero when enforcement is distributed.
  • Monotonic clock: a clock that never moves backward within one process, immune to NTP steps.
  • Retry-After: the HTTP header telling a rejected client when to retry, in seconds.
  • AIMD: additive increase, multiplicative decrease; the Phase-10 adaptive controller's rule.
