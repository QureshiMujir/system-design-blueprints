Project Number: 39

1. Goal & Scope

Goal, in engineering terms. Build a distributed rate limiter: a library plus a thin control surface that admits or rejects discrete units of work against a quota, shared correctly across N stateless service replicas, under real clock skew, with a bounded and quantified over-admission error, sub-millisecond added latency in the common path, and a documented, quantified degradation behavior when the coordination substrate is unavailable.

Phase-0 deliverable — numbered list of crates:

  1. ratelimiter-core — the six algorithm state machines (token bucket, leaky bucket, fixed-window counter, sliding-window log, sliding-window counter, GCRA), plus Key, Quota, Decision, ClockSource.
  2. ratelimiter-backend — the Backend trait and the in-process sharded implementation.
  3. ratelimiter-redis — the centralized-store backend: Redis 7 with one atomic Lua script per algorithm.
  4. ratelimiter-protocol — RFC 6585 429 responses, Retry-After, and the IETF RateLimit-* header convention.
  5. ratelimiter-tower, ratelimiter-axum, ratelimiter-hyper, ratelimiter-actix — middleware integrations and hierarchical-quota composition.
  6. ratelimiter-cli — the operator surface: inspect / clear / set-quota / policy export.
  7. conformance/ and ratelimiter-bench — the accuracy-under-concurrency and throughput harnesses that gate every phase.

System boundaries.

  • Provides: per-key, per-tenant, and hierarchical admission control; a documented over-admission bound under N enforcement nodes (§8.7); the standard 429 + Retry-After + RateLimit-* protocol (§8.9); fail-open/fail-closed degradation (§22); hot-key and DDoS shedding (§21).
  • Delegates: transport/TLS termination to the embedding service or proxy; storage durability to Redis or the cluster substrate; caller authentication to upstream middleware; consistent-hash shard ownership to the Distributed-Cache substrate (rank 59) it composes with in Phase 7, not reimplemented here.
  • Does NOT provide: bot/CAPTCHA-shaped abuse classification, request-body inspection, or usage-based billing (the cost parameter is exposed for a billing consumer, not implemented here).

Non-goals. Exactly-once global admission — proven impossible under partition, §8.7; a bespoke consensus protocol (Raft/Paxos are delegated, never reimplemented); a GUI dashboard beyond the Grafana JSON shipped in §25.

Deployment model. An embedded library for the in-process and local-approximate paths (no sidecar required); a coordination client (Redis, or the cluster/gossip substrate) for the centralized, sharded, and eventually-consistent paths. ratelimiter-cli ships as an optional operator binary, never a requirement to run the library.

Target users/operators. Backend engineers protecting their own API surface (per-user, per-tenant quotas) and edge/proxy engineers shaping traffic at ingress (per-IP, global, hierarchical composition).

What later phases unlock. Phase 7 unlocks strict-and-fast sharded correctness under partition-tolerant topologies. Phase 8 unlocks eventual-consistency at a fraction of the coordination cost. Phase 9 unlocks resilience against adversarial and hot-key traffic. Phase 10 unlocks adaptive quotas and the full operator surface.

Recommended language + rationale. Rust 1.75+, stable toolchain. (a) The hot path carries a p99 budget of 250 µs (§4) — a stop-the-world GC forecloses this; (b) the async ecosystem (Tokio, Tower, Hyper, Axum) is where the middleware crates must live natively; (c) #[repr(C)]-friendly structs give a predictable, auditable per-key memory footprint (§4). Rejected languages: Go — GC pauses have historically shown up in the Envoy ratelimit service's own tuning issues under load, risking the p99 budget; C++ — no ownership model for the concurrent per-key map without hand-rolled RCU, raising the defect rate of the hottest code in the system; Java/JVM — GC pauses and cold-start cost are incompatible with a sidecar-style deployment that must be warm within milliseconds of a pod start.

Prerequisites. Monotonic vs. wall clocks and why the difference matters under NTP stepping; the CAP-theorem consequence for admission control under partition; RFC 6585 and RFC 7231; the token-bucket/leaky-bucket/GCRA equivalence; concurrent hash-map sharding and false sharing.

Estimated timeline. Phase 0 (repo skeleton + correctness kernel): 2 weeks. Full system, Phase 0 through Phase 10: 12 weeks at the workspace bar.

Deferred features flagged here (registered in full in §36 Deferred Features Register): the full closed-loop AIMD autotuner beyond the fixed-step controller built in Phase 10, PhaseDeferred("§22"); the hosted multi-tenant control plane, PhaseDeferred("§25"); the WASM/edge compile target, PhaseDeferred("§26").

2. Why Build This

  • Rate limiting is reached for, unread, more than almost any other piece of platform code — the failure mode is silent: GCRA chosen because a blog post recommended it when the operator wanted plain per-second quotas; sliding-window-log run past the memory ceiling of its Redis instance until eviction turns the limit into a coin toss; fixed-window's boundary effect flooding the next bucket at every minute mark. Building all six algorithms from scratch forces confrontation with each one's actual contract instead of its reputation.
  • Teaches the skeleton every coordination-under-partition problem shares: a local, fast, approximate answer vs. a centralized, slow, exact one — the same tension as leader-based vs. gossip-based membership (Gossip-Protocol, rank 72), and strict vs. eventual consistency in a distributed cache (Distributed-Cache, rank 59).
  • Architecturally, this is one of the smallest systems in which the CAP tradeoff is fully observable end-to-end within a single afternoon of load-testing: token count is the data, admission is the read-modify-write, node count is the partition axis.
  • Historically, GCRA descends from ATM network cell admission control, not HTTP — grasping why a 1996 telecom traffic-shaping equation now guards web APIs is a lesson in how a clean equation outlives its original substrate.
  • Builds the muscle of reasoning about an explicit accuracy/cost tradeoff with a number attached (the over-admission bound, §8.7) instead of a hand-waved "eventually consistent."
  • Concrete cross-links: Distributed-Cache (rank 59) supplies the consistent-hash shard map Phase 7 composes with; Gossip-Protocol (rank 72) supplies the epidemic broadcast Phase 8 composes with; Reverse-Proxy and API-Gateway are downstream consumers of the middleware crates built in Phase 5.
  • Calibration value: a reader who ships this can, for any future rate-limiting requirement, immediately judge which of the six algorithms fits the traffic shape and which topology the latency/consistency budget actually permits.

What Mastery Looks Like:

  • Derive the GCRA emission interval and delay-variation-tolerance from a (rate, burst, period) triple without consulting a reference — Phase 1 (§13).
  • State the exact formula bounding sliding-window-counter's error against sliding-window-log at O(1) memory — Phase 1 (§13), §8.5.
  • Write the atomicity argument for why WATCH/MULTI/EXEC is wrong on a hot key and a single EVALSHA is right — Phase 3 (§15).
  • Compute the over-admission bound for N enforcement nodes under a centralized store with replication lag L, and state when it goes to zero — Phase 7 (§19), §8.7.
  • Justify a fail-open vs. fail-closed default from a stated threat model rather than a personal preference — Phase 10 (§22), §23 Threat Model.
  • Design a hot-key/DDoS mitigation that filters locally before the coordination substrate ever sees the traffic, without the filter itself becoming the bottleneck — Phase 9 (§21).
  • Run an accuracy-under-concurrency test and correctly separate "wrong by design" (approximate counters within their documented ε) from "wrong by bug" — Phase 6 (§18).

 Telemetry (Prometheus counters + OTel spans) attaches to every decision.

Middleware. Extracts the caller's Key and composes the hierarchy (I5, §7); the first layer to reject short-circuits the request before any layer's counter is touched twice.

Hot-Key Pre-Filter. A local Count-Min Sketch (Cormode-Muthukrishnan 2005, §5) flags keys whose estimated rate already exceeds a coarse ceiling, rejecting locally before a network round-trip to the coordination substrate is spent — this is the structural DDoS defense (§23, T1).

Limiter. Dispatches to exactly one of the six algorithms per P1; the algorithm owns its state-transition semantics (§8) and never mixes with another algorithm's state shape.

Backend. The three topologies of §1's non-goals discussion: in-process (fastest, single node), Redis-centralized (strict, network-bound), cluster/gossip (partition-tolerant, approximate). Selection is a Quota-level configuration, not a code fork (P7).

Circuit Breaker + FailureMode Dispatch. Wraps every backend call; on repeated backend failure it opens and the configured FailureMode (never a silent default, P4) decides the Decision returned to the middleware.

Protocol Layer. Renders the Decision into wire form: the IETF RateLimit-* headers on every response, RFC 6585's 429 plus RFC 7231's Retry-After on reject (§8.9).

6. Design Principles

  1. P1 — Algorithms are first-class. The six algorithms are six independent modules dispatched by Algorithm (§11); a caller choosing GCRA gets exactly GCRA. Tradeoff: no silent algorithm blending. Operational implication: the operator picks per Quota, not per flag combination. Violating it: a "smart" dispatcher that blends algorithms breaks the accuracy guarantees of §4 because no single ε applies.
  2. P2 — Monotonic clocks only. Every decision reads ClockSource::now_ns (§8.8), never wall-clock. Tradeoff: bucket-id math (fixed-window) must convert monotonic time to a period index explicitly. Violating it: a wall-clock step during an NTP correction can double-admit or freeze a key (§24 FM-2).
  3. P3 — Decisions are checked, not negotiated. The hot path is Limiter::check(key, cost) -> Decision; there is no retry-politely surface. Violating it invites hidden retry storms that themselves violate I1.
  4. P4 — Fail-open vs. fail-closed is explicit, never defaulted. FailureMode is a required constructor argument (I6). Violating it silently picks a security posture the operator never chose (§23 T7).
  5. P5 — Headers are normative. The IETF draft's RateLimit-* headers are the default emission; legacy variants are opt-in adapters (§8.9). Violating it breaks every IETF-draft-aware client library.
  6. P6 — Hierarchical quotas compose, first-reject-wins. IP → user → route → tenant → global layers compose; the first layer to reject short-circuits (§17). Violating it lets one tenant's burst starve another's budget.
  7. P7 — The Backend abstraction is narrow. Exactly three operations: decide, state, clear (§11). Violating it (adding a fourth op) forces every backend, including future ones, to implement operations most will never need.
  8. P8 — Every distributed mutation is atomic. Redis decisions are one EVALSHA; no WATCH/MULTI/EXEC (I8). Violating it introduces a lost-update race under concurrent callers on the same key.
  9. P9 — Multi-tenancy lives in the key, never in global state. Key.tenant is part of the wire form (§11, I9). Violating it risks cross-tenant quota leakage (§23 T4).
  10. P10 — Observability is not opt-in. Every decision emits one Prometheus counter and one OTel span event (I7). Violating it makes a production incident undebuggable.
  11. P11 — Cost is a first-class parameter, default 1. A caller weighting requests by byte count or compute cost passes a cost (I12). Violating it hardcodes cost=1 as a silent assumption the next caller trips over.
  12. P12 — No sleeps on the hot path. Reject returns immediately with retry_after; the caller decides whether to sleep (§8.9). Violating it turns the limiter into an unbounded-latency surface under load.
  13. P13 — Hot keys are detected locally before they reach the coordination substrate. The Count-Min Sketch pre-filter (§21) rejects obvious abuse before a network hop is spent. Violating it lets a single hot key become the coordination substrate's DDoS vector (§23 T1).
  14. P14 — Every number in this specification is derived, not asserted. Every entry in §4 and §33 shows its arithmetic. Violating it (asserting "handles millions of RPS" without deriving it) is exactly the failure mode the god-level bar exists to prevent.

8. Domain Model / Protocol / Data Model

Every algorithm below shares the same contract: check(key, cost, now_ns) -> Decision. The state each keeps, and the equation each uses, differ. This section is the normative reference every phase's N.2 anchors back to.

8.1 Token Bucket

State: { tokens: f64, last_refill_ns: u64 }.

Equation: on check(cost) at now_ns: elapsed = now_ns - last_refill_ns; tokens = min(burst, tokens + elapsed × (rate / period)); if tokens ≥ cost, admit and tokens -= cost; else reject with retry_after = ceil((cost - tokens) / (rate/period)).

Field Meaning Bound
tokens current burst budget 0 ≤ tokens ≤ burst
last_refill_ns last decision's monotonic timestamp strictly non-decreasing (I3)

Contract: "burst once, then refill at rate." Paper: Turner 1986 (§5).

8.2 Leaky Bucket

State: { level: f64, last_drip_ns: u64 }.

Equation: on check(cost): elapsed = now_ns - last_drip_ns; level = max(0, level - elapsed × (rate/period)); if level + cost ≤ burst, admit and level += cost; else reject with retry_after = ceil((level + cost - burst) / (rate/period)).

Contract: smooths the output rate regardless of input burstiness — the dual of token bucket, which smooths nothing but bounds burst admission. Ref-impl: nginx ngx_http_limit_req_module (§5).

8.3 Fixed-Window Counter

State: { count: u64, window_start_ns: u64 }, keyed by window_id = now_ns / period_ns.

Equation: if now_ns / period_ns != window_start_ns / period_ns, reset count = 0, window_start_ns = now_ns; if count + cost ≤ limit, admit and count += cost; else reject with retry_after = window_start_ns + period_ns - now_ns.

Boundary effect: a client may issue up to 2 × limit requests inside any real 1-period span that straddles a window boundary — the defining weakness this algorithm trades for O(1) state and no per-request scan.

8.4 Sliding-Window Log

State: { events: Vec<u64> } (timestamps within [now_ns - period_ns, now_ns]), capped at a configurable max_events (I5).

Equation: evict every e ∈ events with e < now_ns - period_ns; if events.len() + cost ≤ limit, admit and push cost copies of now_ns (batched as a count, not cost separate pushes); else reject with retry_after = time until the oldest in-window event expires.

Exact accuracy, unbounded memory growth under sustained traffic — bounded here by I5's explicit cap, which trades exactness for the same memory ceiling as sliding-window-counter once the cap binds.

8.5 Sliding-Window Counter

State: { current: u64, previous: u64, window_start_ns: u64 }.

Equation: let f = (now_ns - window_start_ns) / period_ns (fraction elapsed in the current window); estimated_count = current + previous × (1 - f); if estimated_count + cost ≤ limit, admit and current += cost; on window roll-over, previous = current; current = 0; window_start_ns += period_ns.

Cloudflare's approximation (§5): O(1) memory, error ≤ 6% worst-case at a traffic spike exactly at the boundary, ≤ 1% under steady-state traffic — the number in §4 is this algorithm's documented ε for I1.

8.6 GCRA (Generic Cell Rate Algorithm)

State: { tat_ns: u64 } — the Theoretical Arrival Time, one integer per key.

Equation: increment_ns = period_ns / rate (scaled by cost); dvt_ns = (burst - 1) × increment_ns (delay-variation tolerance); new_tat = max(now_ns, tat_ns) + increment_ns; allow_at = new_tat - dvt_ns; if allow_at ≤ now_ns, admit and tat_ns = new_tat; else reject with retry_after = allow_at - now_ns.

GCRA is token-bucket-with-leaky-bucket-mean-rate re-expressed as a single timestamp (ATM Forum 1996, §5) — its one-integer-per-key footprint is why it is the Phase-0 default (ADR-10).

8.7 Distributed Counter & Over-Admission Bound

Two enforcement topologies, per P7:

Centralized (Redis + atomic Lua, Phase 3). Every node calls the same store; the atomic script (I8) makes the decision exact at the store. Over-admission arises only from network partition: if a node cannot reach the store, FailureMode::FailOpen admits unconditionally until the circuit breaker (§24 FM-3) opens. Bound: over_admission ≤ burst × (nodes partitioned) — zero when every node reaches the store.

Sharded / gossip (local-approximate, Phase 7/8). Each node keeps a local counter and reconciles asynchronously (Demers et al. 1987, §5). Over-admission bound, derived: with N enforcement nodes, replication lag L (seconds), and local rate r per node, over_admission ≤ N × r × L — the excess every node can admit before it learns of the others' consumption. This is I2's formal statement; §33 instantiates it with concrete numbers.

Worked example. N=8 nodes, r=1000 req/s local cap each, L=50 ms (Phase 8's convergence window, §4): over_admission ≤ 8 × 1000 × 0.05 = 400 excess admissions in the worst window — 0.4× a single node's per-second budget, converging to 0 as L → 0 (Phase 3's centralized mode).

8.8 Clock Model

ClockSource (§11) wraps tokio::time::Instant — monotonic, immune to NTP step corrections (P2, I3). Wall-clock (SystemTime) is used only to compute the fixed-window window_id initial epoch alignment (e.g. "align to the top of the UTC minute") and is converted to a monotonic offset once at startup, never read again on the hot path. Clock skew between nodes (relevant only to the distributed topologies, §8.7) is bounded by NTP's own guarantee (Mills 1991, §5); Phase 9 (§21) treats skew beyond that guarantee as an operational alert, not a correctness bug, because every per-node decision is local-clock-relative by construction (I3).

8.9 Protocol: 429 + Retry-After + RateLimit Headers

On Permit: emit RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset (delta seconds, IETF draft, §5), RateLimit-Policy. On Reject: HTTP 429 (RFC 6585) plus Retry-After (RFC 7231, seconds, ceiling-rounded) plus the same RateLimit-* set with Remaining=0. Legacy emitters (GitHub, Twitter header shapes) are opt-in adapters (P5); the draft form is the unconditional default.

8.11 Malformed-Input Handling

  • cost = 0: well-defined, always Permit (a zero-cost probe), never advances state (I12 — zero units consumed).
  • cost > burst (token bucket) or cost > limit (fixed window): always Reject, no matter the current state — the request can never be satisfied by this quota; retry_after is reported as the algorithm's own period as an upper bound, not computed as unreachable.
  • Key.value empty or Key.tenant empty: Error::InvalidKey, rejected at the middleware boundary before reaching any algorithm (never silently coerced to a wildcard key, I9).
  • Negative or overflowed Quota.rate/burst: rejected at Quota construction (Error::InvalidQuota), never at decision time — fail fast at configuration load.

8.12 Failure-Path Example

Redis backend, circuit breaker closed, FailureMode::FailClosed. Redis connection drops mid-decision. The adapter surfaces Error::Backend; the circuit breaker's failure count crosses threshold (§24 FM-3) and it opens; every subsequent check for the next half_open_after seconds (§4 RTO ≤ 5s) short-circuits to Decision::Reject per the configured FailureMode without attempting Redis; telemetry emits ratelimiter_circuit_state=open (I11); after the interval, one probe request is allowed through — success closes the breaker, failure resets the timer.

pub trait Limiter: Send + Sync {

}

// decision.rs — the contract handed to every caller

    Permit { remaining: u32, reset: Duration },              // I4-adjacent: reset always >= 0
    Reject { retry_after: RetryAfter, reset: Duration },      // I4: retry_after always >= 0
}
pub struct RetryAfter(pub Duration);                          // newtype, Copy-free (Duration is Copy)
impl RetryAfter {
    pub fn as_seconds_ceiled(&self) -> u64;                    // used by §8.9 Retry-After header
}
// Serialization: Decision is never persisted; it is computed fresh per request (P3).

impl Key {

13. Phase 1 — Single-Node Algorithm Primitives

13.1 Objectives

Implement all six algorithms (§8.1–§8.6) as independent modules in ratelimiter-core, each satisfying Limiter directly over an in-memory HashMap<Key, AlgorithmState> guarded by a single mutex (the multi-key sharding is Phase 2's concern, not this phase's).

13.2 Detailed Implementation Steps

Implement token_bucket.rs per §8.1's equation (P1, Turner 1986 — §5); leaky_bucket.rs per §8.2 (nginx ref-impl, §5); fixed_window.rs per §8.3, computing window_id = now_ns / period_ns via integer division only (never float, to avoid drift); sliding_log.rs per §8.4 with the max_events cap enforcing I5; sliding_counter.rs per §8.5 (Cloudflare ref-impl, §5), the interpolation weight (1-f) computed once per decision; gcra.rs per §8.6 (ATM Forum 1996, §5), increment_ns and dvt_ns precomputed at construction from Quota, never recomputed per request. Every module reads time exclusively through ClockSource (P2, I3).

13.3 Deliverable

Six algorithm structs, each implementing Limiter, each with the SimClock wired for deterministic tests, committed with the docs/algorithms.md long-form write-up matching §8 verbatim.

13.4 Acceptance Criteria

Property tests (proptest, ADR-16) prove: long-run admitted rate within the §4 ε for each algorithm over 100,000 simulated requests at 10 traffic shapes; burst is honored exactly (GCRA's worked example, §8.10, reproduced as a fixture); zero-cost requests always admit without state change (I12); cargo bench on GCRA's check reports p99 ≤ 900 ns per §4.

13.5 Conformance Fixtures

fixtures/positive/gcra_worked_example.json — the exact §8.10 trace, byte-for-byte. Six fixtures/positive/<algorithm>_long_run_rate.json files, one per algorithm. Six fixtures/negative/<algorithm>_malformed.json files exercising §8.11's cases.

13.6 Pitfalls

  • Refilling token bucket with if delta > 0 { tokens += 1 } instead of the closed-form min(burst, tokens + elapsed × rate/period) (§8.1) — wrong on long idle gaps.
  • Comparing f64 token counts for exact equality in tests instead of an ε-tolerant assertion — the algorithms are float-based by design (§8.1, §8.2).
  • Reaching for SystemTime "because it feels like wall clock" (P2) — a step during an NTP correction breaks fixed-window's boundary math and can freeze GCRA's tat_ns comparison.

13.7 Performance Concerns

GCRA's single u64 per key gives the best cache-line density (§4: 8 B/key) — a DashMap shard holding 8,000 keys fits in under one 64 KiB L1 data cache per Herlihy & Shavit's false sharing discussion (§5); sliding-log's Vec<u64> is the outlier and must never be allowed to grow unbounded (I5) or it becomes the allocator's hottest path under sustained traffic.

13.8 Edge Cases

Clock read returning the exact same now_ns as last_refill_ns/tat_ns twice in a row (two decisions in the same nanosecond) — token bucket must treat elapsed=0 as a valid no-refill case, not a division-by-zero; GCRA must treat now_ns == tat_ns as the boundary allow_at == now_ns case (permit), matching §8.10's row at t=30ms.

13.9 Failure Analysis

A property-test failure surfaces the exact (quota, sequence) that violated I1; blast radius is confined to the one algorithm module (P1 guarantees no cross-algorithm state); recovery is bisecting the failing sequence to the minimal reproducing case (proptest's built-in shrinking) and adding it as a permanent regression fixture under §13.5.

13.10 Operational Notes

Each algorithm module exposes its AlgorithmState via Limiter::state for operator inspection (P10); no metrics are wired yet (Phase 2 introduces the Backend-level instrumentation point) — Phase 1's telemetry surface is limited to tracing::trace! spans around check for local debugging.

14. Phase 2 — Backend Abstraction & In-Process Store

14.1 Objectives

Extract the Backend trait (§11, P7) so an algorithm's per-key state can live behind a pluggable store; ship the production in-process implementation (sharded, concurrent) and the conformance-negative stub.

14.2 Detailed Implementation Steps

crates/ratelimiter-backend/src/lib.rs defines Backend with exactly decide/state/ clear (P7 — never a fourth operation). inmem.rs shards a dashmap::DashMap<Key, AlgorithmState> at num_cpus × 4 shards (Herlihy & Shavit ch. 9, §5), each shard's critical section holding only that shard's lock — no global lock is ever taken. stub.rs returns Error::CapabilityNotSupported from every method and false from capability, forming the conformance baseline every real backend is compared against (§18). Wire Limiter implementations from Phase 1 to delegate their state lookup through Backend::decide instead of an internal HashMap, so the same algorithm module runs unmodified over any backend.

14.3 Deliverable

Backend trait, InMemBackend, StubBackend; every Phase-1 algorithm now runs over InMemBackend unmodified; a benchmark showing InMemBackend throughput.

14.4 Acceptance Criteria

cargo bench --bench inmem_throughput reports ≥ 1,000,000 decisions/s/core (§4, M1); StubBackend fails all 6 algorithms' positive conformance buckets and passes all negative ones (100% of capability() calls return false); shard count is verified equal to num_cpus::get() × 4 at runtime via a unit test.

14.5 Conformance Fixtures

fixtures/positive/inmem_all_algorithms.json — one fixture per algorithm run against InMemBackend. fixtures/negative/stub_rejects_everything.json — asserts every StubBackend call returns Error::CapabilityNotSupported.

14.6 Pitfalls

  • Taking a single global Mutex "to keep it simple" — this defeats the entire purpose of sharding and reintroduces the exact contention Herlihy & Shavit's ch. 9 (§5) warns against.
  • Forgetting that DashMap's shard count must be a power of two for its internal hashing — num_cpus × 4 is not guaranteed to be; round up explicitly.
  • Letting the stub silently succeed on clear() — it must fail every method uniformly, or the conformance suite's negative bucket for clear gives a false pass.

14.7 Performance Concerns

Shard-local locks still serialize concurrent writers to the same key — a single hot key still contends on one shard regardless of total shard count (this is exactly what Phase 9's hot-key pre-filter, P13, exists to relieve upstream); false sharing across adjacent shards' cache lines is mitigated by DashMap's internal padding, verified by a criterion benchmark comparing single-key vs. multi-key throughput.

14.8 Edge Cases

A clear() on a key that was never written must be a no-op success, not an error (idempotent by contract); concurrent decide() and clear() on the same key must never leave the shard in a state where a subsequent decide() observes a torn write (verified by a loom test in Phase 11, flagged here as the property Phase 2 must not violate).

14.9 Failure Analysis

InMemBackend cannot itself "fail" (no I/O) — the only failure surface is resource exhaustion (OOM from unbounded key growth); detection is ratelimiter_key_memory_bytes (I5) crossing an alert threshold; recovery is an operator-triggered clear() sweep via the CLI's policy export/inspection surface (§22) or a TTL-based eviction added as a follow-up (registered if pursued, §36).

14.10 Operational Notes

Backend selection is a Quota-adjacent configuration value, never a compile-time feature flag (P7) — an operator can run InMemBackend in dev and swap to RedisBackend in prod without recompiling. Metrics: ratelimiter_backend_decide_latency_seconds histogram, labeled by backend kind, established here as the pattern every later backend (Phase 3, 7, 8) reuses.

15. Phase 3 — Centralized Enforcement (Redis + Atomic Lua)

15.1 Objectives

Ship the strict, network-bound distributed backend: one atomic Lua script per algorithm against Redis 7, giving exact cross-node correctness at the cost of a round trip (§8.7's centralized topology, ADR-05).

15.2 Detailed Implementation Steps

crates/ratelimiter-redis/src/client.rs wraps redis-rs on the Tokio runtime with a pooled connection set (§4 FD budget: 1 connection per 200 concurrent tasks). Six Lua scripts under lua/ (ADR-20), each embedded via include_str! and SCRIPT LOAD-ed at connect time, cache the returned SHA; every decision is exactly one EVALSHA sha 1 key cost rate burst period_ms now_ms (P8, I8 — never WATCH/MULTI/EXEC, brandur/redis-cell ref-impl, §5). The caller's own now_ns (from ClockSource, P2) is passed as an argument — Redis's own TIME command is never read, keeping semantics identical to InMemBackend. Every write sets PEXPIRE key (period_ms × 2) (§4 storage amplification bound) to prevent unbounded idle-key growth. On a NOSCRIPT response the client falls back to EVAL once and reloads the script.

15.3 Deliverable

RedisBackend implementing Backend; six Lua scripts passing every algorithm's Phase-1 conformance fixtures replayed against a live Redis 7 instance (docker-compose.yml, §10).

15.4 Acceptance Criteria

cargo bench --bench redis_throughput reports ≥ 50,000 decisions/s/connection (§4, M2); p99 added latency ≤ 5 ms local-Redis (§4); a fixture asserting PEXPIRE is set on every key write (no idle-key leak) passes; redis/atomicity_under_concurrency (I8) shows zero lost updates across 64 concurrent callers hammering one key for 10,000 iterations.

15.5 Conformance Fixtures

fixtures/positive/redis_<algorithm>_matches_inmem.json — differential fixture: same input sequence must produce identical decisions on RedisBackend and InMemBackend. fixtures/negative/redis_noscript_recovery.json — forces a script flush mid-run, asserts recovery via reload.

15.6 Pitfalls

  • Reading Redis TIME instead of the caller's monotonic now_ns — breaks parity with InMemBackend and reintroduces wall-clock exposure P2 forbids.
  • Forgetting PEXPIRE — idle keys accumulate without bound, silently growing Redis memory until eviction turns the limiter into a coin toss (the exact failure §2 opens with).
  • Using WATCH/MULTI/EXEC "because it's more idiomatic redis-rs" — race-prone under load (P8); the Kong ref-impl's policies/init.lua (§5) is the pattern to follow instead.

15.7 Performance Concerns

Every decision costs one network round trip (§4 RTT assumption: ≤ 1 ms same-AZ) — this is the structural latency floor of the centralized topology (§8.7); connection pooling (§4 FD budget) avoids per-request TCP handshake cost; the Lua script itself executes in sub-microsecond Redis-internal time, so the round trip dominates entirely.

15.8 Edge Cases

Redis cluster mode with hash-slot migration mid-decision — the client must retry once on a MOVED/ASK redirect (standard redis-rs cluster support), never surfacing a spurious Error::Backend for a transient slot migration. A cost larger than u32::MAX / rate must be rejected as Error::InvalidQuota before it reaches Lua, avoiding integer overflow inside the script.

15.9 Failure Analysis

Connection loss mid-script-call surfaces Error::Backend; the circuit breaker (§22, §24 FM-3) counts the failure; on NOSCRIPT (e.g. after a SCRIPT FLUSH by an operator) the client reloads once before counting it as a real failure, per §15.2 — this distinguishes a transient cache-flush from an actual outage (§8.12's worked failure path).

15.10 Operational Notes

ratelimiter_redis_script_errors_total and ratelimiter_redis_connection_pool_in_use are the two dashboards operators watch first (§25); a runbook (docs/runbooks/redis-outage.md) documents the exact circuit-breaker timeline (§4 RTO ≤ 5 s) an on-call engineer should expect during a Redis incident.

16. Phase 4 — Wire Protocol (429, Retry-After, RateLimit Headers)

16.1 Objectives

Render every Decision into the standard wire form: RFC 6585's 429, RFC 7231's Retry-After, and the IETF draft's RateLimit-* headers (§8.9, P5).

16.2 Detailed Implementation Steps

headers.rs implements HeaderEmitter (§11) producing RateLimit-Policy, RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset (delta seconds, per the IETF draft, §5) on every response — both Permit and Reject. On Reject, additionally set HTTP status 429 (RFC 6585, §5) and Retry-After (RFC 7231, §5) via RetryAfter::as_seconds_ceiled (§11). A LegacyHeaders enum (GitHub, Twitter) provides opt-in adapters emitting the older epoch-seconds Reset convention (P5 — the draft form is the unconditional default, never overridden implicitly).

16.3 Deliverable

HeaderEmitter implementations for the draft and both legacy variants; a snapshot-test suite capturing byte-exact header output against fixtures transcribed from the IETF draft's own examples.

16.4 Acceptance Criteria

100% of snapshot fixtures match byte-for-byte; a fixture asserts Retry-After is present on every 429 response (never omitted, per RFC 7231); a fixture asserts RateLimit-Reset is expressed as delta seconds (not epoch) in the default emitter and as epoch seconds in the GitHub legacy adapter.

16.5 Conformance Fixtures

fixtures/positive/headers_ietf_draft.json — draft-transcribed examples. fixtures/positive/headers_legacy_github.json, headers_legacy_twitter.json. fixtures/negative/headers_429_missing_retry_after.json — must fail if triggered (this fixture exists to prove the emitter cannot regress into omitting it).

16.6 Pitfalls

  • Emitting Reset as Unix-epoch seconds in the default emitter — the IETF draft moved to delta seconds; this is the single most common header-compliance bug (§2).
  • Omitting Retry-After on 429 because "the RateLimit-Reset header already implies it" — RFC 7231 requires it explicitly; clients that only read Retry-After (many do) get nothing.
  • Hardcoding a single header set application-wide instead of making the emitter a swappable HeaderEmitter (P5) — this blocks a future consumer needing the GitHub legacy form.

16.7 Performance Concerns

Header construction is string formatting on the response path — negligible relative to the decision cost itself (§4), but a format!-per-header allocation pattern under high QPS is measurable; the emitter pre-allocates the HeaderMap capacity to avoid repeated reallocation.

16.8 Edge Cases

remaining computed as a negative value due to a race between concurrent decisions (transient under-counting at very high concurrency, algorithm-dependent) is clamped to 0 before emission, never serialized as a negative integer that would violate the wire format's u32 contract.

16.9 Failure Analysis

A malformed header value (e.g. a Duration that would serialize to a non-finite number) is a programming defect, not a runtime condition — caught by the snapshot-test suite (§16.5) before release, never surfaced to a live caller; there is no runtime recovery path because this class of bug cannot occur given RetryAfter's type (I4).

16.10 Operational Notes

docs/runbooks/header-compliance-drift.md documents the procedure for validating against a newer IETF draft revision when one is published — re-run the snapshot suite against the new draft's own published examples before flipping the default (Compatibility & Versioning, §26).

17. Phase 5 — Middleware & Hierarchical Quotas

17.1 Objectives

Ship the four middleware crates (Tower, Hyper, Axum, Actix) and hierarchical quota composition (IP → user → route → tenant → global, P6, Stripe's four-limiter taxonomy, §5).

17.2 Detailed Implementation Steps

ratelimiter-tower implements Layer+Service (§11) taking a Limiter and a KeyExtractor<R>; on call, extract the key, invoke Limiter::check, and on Reject short-circuit to a 429 built by the Phase-4 HeaderEmitter without invoking the inner service (P6 — first-reject-wins). ratelimiter-hyper, -axum, -actix are thin adapters over the same Layer (Envoy's descriptor-composition pattern, §5, informs the hierarchical extractor design, though its batching pitfall — §5's noted lesson — is explicitly not copied: each layer's Redis call is independent, never pipelined across unrelated keys). Built-in KeyExtractors: by IP, by authenticated user, by route, by tenant header, and a composite extractor that stacks multiple RateLimitLayers, each with its own Quota (P6); on Permit, every stacked layer's counter increments — only the first Reject stops the chain.

17.3 Deliverable

Four working middleware crates; examples/tower_layered demonstrates a 3-layer composition (per-IP → per-tenant → global) against InMemBackend.

17.4 Acceptance Criteria

composition/hierarchical conformance bucket (§18) passes: a request that would be admitted by layer 1 but rejected by layer 2 is rejected overall, and layer 1's counter still incremented (P6's contract, not a rollback); integration tests for all four frameworks pass; middleware/tower/reject_path fixture confirms the inner service is never invoked on reject.

17.5 Conformance Fixtures

fixtures/positive/composition_hierarchical_permit.json, fixtures/negative/composition_hierarchical_reject_layer2.json — asserts layer 1's state still advanced. fixtures/positive/middleware_tower_permit_path.json, fixtures/positive/middleware_axum_integration.json.

17.6 Pitfalls

  • Rolling back layer 1's increment when layer 2 rejects — this is explicitly not the contract (P6): each layer's budget is independent and consumed on attempt, matching every real hierarchical quota system's semantics (Stripe's taxonomy, §5).
  • Copying Envoy's cross-key Redis pipeline batching (§5's noted pitfall) — a slow key then stalls an unrelated batch; each layer issues its own independent backend call.
  • Building the 429 response without attaching Phase-4's headers — the middleware always routes through HeaderEmitter, never a bespoke response builder.

17.7 Performance Concerns

N stacked layers cost up to N backend round trips in the worst case (all layers using a network-bound backend) — an operator composing 5 Redis-backed layers pays 5× the §4 latency budget; the docs recommend at most 2 network-bound layers plus unlimited in-process layers (P7 — in-process layers are nearly free per §4's M1 throughput).

17.8 Edge Cases

A KeyExtractor that cannot extract a key (e.g. no IP available behind a misconfigured proxy) returns Error::InvalidKey (§8.11), and the middleware's FailureModeDispatcher (§11) decides the outcome — never silently skipping the layer, which would create an unbounded bypass.

17.9 Failure Analysis

A panic inside a KeyExtractor (e.g. an indexing bug) is caught at the Service::call boundary via catch_unwind equivalent guidance in the docs (Tower's own service contract requires it), converted to Error::Backend, and dispatched per FailureMode — never propagated as an unhandled panic that would take down the whole worker task.

17.10 Operational Notes

Each layer emits its own ratelimiter_decisions_total{layer="..."} label (P10); operators composing hierarchical quotas get per-layer dashboards for free, letting them see exactly which layer in the stack is rejecting traffic during an incident.

18. Phase 6 — Conformance & Accuracy-Under-Concurrency

18.1 Objectives

Build the conformance runner that gates every phase above and below this one; add the concurrency-accuracy harness that distinguishes "wrong by design" (documented ε) from "wrong by bug" (§2's calibration goal made mechanical).

18.2 Detailed Implementation Steps

conformance/runner/src/main.rs accepts --backend <name> --bucket <glob>, drives every fixture in fixtures/{positive,negative}/ against the named backend via conformance/adapters/, and emits conformance.report.json with a Pass|Fail|Deferred verdict per bucket (I14's harness). The concurrency-accuracy suite spawns C ∈ {1,8,64,256} concurrent callers against one key for D seconds and asserts the admitted count is within the algorithm's documented ε (§4, I1) of rate × D — this is the mechanical test of the debugging methodology described in §7. Buckets cover every algorithm × every backend, every header emitter, every failure-mode path, and the hierarchical composition fixtures from §17.5.

18.3 Deliverable

conformance/REPORT.md generated from a full run, showing Pass for every Phase 0–6 bucket and Deferred (with an anchor) for the cluster/gossip/adaptive buckets not yet built.

18.4 Acceptance Criteria

100% of Phase 0–6 buckets report Pass; the concurrency-accuracy suite at C=256 reports admitted-count error ≤ the §4 ε for every algorithm (0% for TB/LB/FW/GCRA/SWL up to the I5 cap, ≤6% for SWC); CI fails the build on any non-Pass, non-Deferred verdict (§27).

18.5 Conformance Fixtures

fixtures/positive/concurrency_accuracy_c256.json — the C=256 scenario per algorithm. fixtures/negative/concurrency_lost_update.json — a regression fixture asserting I8 (no lost update) holds even at C=256 against RedisBackend.

18.6 Pitfalls

  • Treating a concurrency-accuracy result within documented ε as a bug and "fixing" it by switching sliding-window-counter's interpolation — this destroys its O(1) memory property for no correctness gain (§8.5's ε is by design, not a defect).
  • Running the accuracy suite only at C=1 — low concurrency never exercises the lost-update race I8 exists to prevent; C must sweep up to the documented budget (§4: 100,000 concurrent in-flight per shard).
  • Letting a Deferred bucket silently rot without a resolving anchor — every Deferred verdict must name the phase that will close it (§18.2), checked by the register (§36).

18.7 Performance Concerns

The conformance runner itself must not become slower than the CI budget it gates (§12.4: ≤ 4 minutes) — the concurrency-accuracy suite's C=256 sweep is bounded to a fixed wall-clock duration D (documented per bucket) rather than a fixed request count, keeping CI time predictable regardless of backend latency.

18.8 Edge Cases

A backend that is itself flaky under the CI runner's resource constraints (e.g. Redis container cold-start) must not produce a false Fail — the runner retries container readiness up to a bounded timeout before executing any bucket, separating infrastructure flakiness from a genuine conformance failure.

18.9 Failure Analysis

A Fail verdict blocks the release pipeline (§28); the report names the exact bucket, the backend, and the fixture that failed, giving an on-call engineer the minimal repro without re-running the full suite; a flaky (intermittent) Fail is itself a defect — the harness tracks a bucket's pass rate over the last 20 CI runs and flags any bucket below 100%.

18.10 Operational Notes

conformance.report.json is archived as a build artifact on every CI run (§28); the REPORT.md rendering is what a reviewer reads in a PR to confirm no regression before merge — this is the testing strategy's (§27) primary gate, referenced there directly.

19. Phase 7 — Sharded Cluster Mode & Over-Admission Bound

19.1 Objectives

Ship strict-and-fast distributed enforcement: shard keys across N nodes via consistent hashing (Karger et al. 1997, §5) atop the Distributed-Cache substrate (rank 59, ADR-06), trading Phase 3's per-request network hop for a hop only on cache miss / rebalance.

19.2 Detailed Implementation Steps

crates/ratelimiter-cluster/src/lib.rs resolves each Key::wire() (§11) to a shard owner via the rank-59 consistent-hash ring; the owning node holds the authoritative AlgorithmState in its own InMemBackend shard (Phase 2) and answers decide calls routed to it. On shard-owner unavailability, the client consults the next replica per rank-59's replication factor before invoking FailureModeDispatcher (P4). The over-admission bound (§8.7, I2) is derived here concretely: over_admission ≤ burst × (nodes partitioned), verified by the cluster/over_admission fixture that partitions a configurable subset of nodes and asserts the bound holds.

19.3 Deliverable

ClusterBackend implementing Backend; a benchmark against a 16-shard rank-59-backed cluster; the cluster/over_admission conformance fixture passing at N=8 and N=16.

19.4 Acceptance Criteria

p99 decision latency ≤ 10 ms across 16 shards (§4, M3); the over-admission fixture asserts measured over-admission ≤ burst × partitioned_node_count at 3 injected-partition scenarios (1, 3, 8 of 16 nodes); shard rebalance (simulated node join/leave) completes reassignment within rank-59's own documented SLA with zero decisions lost (not merely delayed).

19.5 Conformance Fixtures

fixtures/positive/cluster_shard_ownership.json — asserts a key always routes to the same shard absent rebalance. fixtures/negative/cluster_over_admission_bound.json — the partition-injection scenario from §19.2.

19.6 Pitfalls

  • Re-implementing consistent hashing instead of composing with the already-audited rank-59 substrate (ADR-06) — doubles the surface area for a subtle ring-imbalance bug.
  • Treating "replica unavailable" the same as "shard permanently lost" — the former retries the next replica (I2's bound assumes this); only exhausting all replicas invokes FailureModeDispatcher.
  • Forgetting that rebalance is a live event, not a maintenance window — in-flight decisions during a rebalance must not be silently dropped; they retry against the new owner.

19.7 Performance Concerns

Steady-state latency approaches Phase 2's in-process numbers (§4 M1) because the local node usually is the shard owner for its own hottest keys under consistent hashing's locality properties; the 10 ms p99 (§4) is dominated by the tail case of a cross-node hop plus rank-59's own lookup cost, not the common case.

19.8 Edge Cases

Two nodes simultaneously believing they own the same shard during a rebalance race (a split-brain window) — resolved by rank-59's own fencing token, which this project trusts rather than re-verifies (delegation boundary, §1); a fixture asserts that under this race, over-admission still respects the I2 bound rather than growing unbounded.

19.9 Failure Analysis

A partitioned node continues admitting locally per its FailureMode (§8.7's centralized worked example generalizes here); detection is ratelimiter_over_admission_total (I2) rising; recovery is automatic on partition heal (rank-59's gossip-based membership, composing with Phase 8) or manual shard-map refresh via the CLI (§22).

19.10 Operational Notes

docs/runbooks/cluster-partition.md documents the expected over-admission ceiling during a named partition scenario so an on-call engineer can distinguish "bounded, expected drift" from "something is actually broken" — cross-referencing the exact formula in §8.7.

20. Phase 8 — Local Approximate Counters & Async Reconciliation

20.1 Objectives

Ship the eventually-consistent topology: each node keeps a local counter, gossip (Demers et al. 1987, §5) propagates deltas atop the Gossip-Protocol substrate (rank 72, ADR-07), trading exactness for near-zero per-decision coordination cost.

20.2 Detailed Implementation Steps

crates/ratelimiter-gossip/src/lib.rs keeps each shard's authoritative counter locally (reusing Phase 2's InMemBackend shape) and periodically gossips deltas to peers via the rank-72 epidemic broadcast; each node's view of a global key's total consumption is the local count plus the last-received peer deltas. The reconciliation loop runs on a fixed interval (§4: convergence window ≤ 50 ms across 16 shards, I10) and is itself a candidate for Phase 8's PhaseDeferred distributed-sketch backend (§36) once per-key cardinality exceeds the memory ceiling (§4 I5) — deferred, not built here.

20.3 Deliverable

GossipBackend implementing Backend; the gossip/convergence conformance fixture (I10) measuring actual convergence time across a simulated 16-node cluster under steady traffic.

20.4 Acceptance Criteria

Measured convergence ≤ 50 ms p99 across 16 shards under steady-state traffic (§4, M4); the over-admission bound from §8.7's derived formula (N × r × L) is verified empirically within 10% of the analytical prediction at 3 traffic rates; a forced full-state resync (I11 in reverse — a request to docs/runbooks) completes within the rank-72 substrate's own documented bound.

20.5 Conformance Fixtures

fixtures/positive/gossip_convergence_16nodes.json. fixtures/negative/gossip_partition_ excess_admission.json — asserts the excess stays within the derived bound during an injected partition, not merely "eventually corrects."

20.6 Pitfalls

  • Assuming gossip convergence is "fast enough" without measuring it against the derived formula (§8.7) — the bound must be checked empirically per traffic rate, not assumed.
  • Re-implementing SWIM-style failure detection instead of composing with rank-72 (ADR-07) — duplicates a hard-to-audit distributed algorithm for no benefit.
  • Using gossip mode for a workload that needs strict correctness (e.g. a hard financial quota) — this topology is explicitly for burst-shaping-tolerant workloads only (§8.7); the docs must state this boundary clearly to prevent misuse.

20.7 Performance Concerns

Gossip fan-out cost grows with cluster size, not with request rate — the per-decision cost is O(1) local-counter increment (§4 near-in-process throughput); the reconciliation background cost is bounded by rank-72's own fan-out parameter, tuned separately from the rate-limiter's own request-path performance budget.

20.8 Edge Cases

A node that rejoins after an extended partition holds a stale local counter — the reconciliation loop must treat a rejoining node's counter as suspect and prefer peer consensus (rank-72's own anti-entropy) over the stale local value for the first reconciliation cycle after rejoin, avoiding a burst of stale-state over-admission.

20.9 Failure Analysis

Convergence exceeding the §4 bound is detected by ratelimiter_gossip_convergence_ms (I10) and alerts; blast radius is confined to the over-admission bound already derived in §8.7 — gossip mode's failure is "more over-admission than expected," never "under-admission" or "crash," because every node always answers from its own local, always-available counter.

20.10 Operational Notes

ratelimiter_gossip_convergence_ms and ratelimiter_over_admission_total are the two dashboards; a runbook documents the tuning knob (rank-72's gossip interval) an operator adjusts when observed convergence drifts above the derived bound for a sustained period.

21. Phase 9 — Clock Skew, Hot-Key Detection & DDoS Handling

21.1 Objectives

Harden the system against two distinct threats: node-to-node clock skew beyond NTP's guarantee (§8.8), and adversarial hot-key/DDoS traffic that would otherwise reach the coordination substrate directly (P13, T1).

21.2 Detailed Implementation Steps

Implement the Count-Min Sketch pre-filter (crates/ratelimiter-backend/src/sketch.rs, Cormode-Muthukrishnan 2005, §5, ADR-21) sitting in front of every Backend: it maintains a fixed-memory approximate frequency table and rejects locally, before any network hop, any key whose estimated rate already exceeds a coarse pre-filter ceiling set well above the key's actual Quota (avoiding false-positive rejection of legitimate bursty-but-compliant traffic). For clock skew: each node logs ratelimiter_clock_regression_total (I3) and ratelimiter_ntp_offset_ms (Mills 1991, §5); because every algorithm's correctness is local-clock-relative by construction (§8.8), cross-node skew degrades only the distributed topologies' convergence/over-admission numbers (§8.7, §20), never a single node's own admission correctness — this is stated explicitly as the property clock skew cannot break.

21.3 Deliverable

The sketch pre-filter wired into the middleware chain ahead of every backend; a load test demonstrating sustained hot-key traffic (10× a single key's quota) is absorbed locally without the coordination substrate's request rate rising proportionally.

21.4 Acceptance Criteria

Under a synthetic 10× hot-key attack, backend-bound request rate for that key stays within 1.5× its configured Quota.rate (the sketch's false-positive margin, §4); sketch memory footprint stays within a fixed ceiling (documented per shard, independent of key cardinality — the whole point of the sketch, §5); a clock-skew injection of 200 ms (beyond NTP's typical guarantee) shows zero change in single-node admission accuracy (I1 still holds) and a measurable, bounded rise in cluster over-admission consistent with §8.7's formula.

21.5 Conformance Fixtures

fixtures/positive/hotkey_sketch_absorbs_attack.json. fixtures/negative/ clock_skew_200ms_single_node_unaffected.json — the explicit proof that I1 is clock-skew-immune at the single-node level.

21.6 Pitfalls

  • Setting the sketch's pre-filter ceiling equal to the real Quota.rate — this causes false positives on legitimate burst traffic; the ceiling must sit comfortably above it (tuned per §4's accuracy budget), with the real quota still enforced downstream by the algorithm.
  • Conflating "hot key" with "abusive key" — a legitimately popular key (e.g. a viral resource) needs the same local absorption without being treated as an attacker; the sketch only shapes the coordination-substrate load, it never itself decides admission.
  • Assuming NTP guarantees bound skew inside a single availability zone without verifying it — cross-AZ deployments can see larger skew than the same-AZ assumption baked into §4's numbers; operators deploying cross-AZ must re-derive the bound.

21.7 Performance Concerns

The sketch itself must be cheaper than the traffic it protects against — a Count-Min Sketch lookup is O(depth) hash computations (typically 4), fixed cost regardless of key cardinality, keeping it well under the in-process decision budget (§4, M1) even under attack-scale traffic.

21.8 Edge Cases

A legitimate traffic spike (e.g. a flash sale) that resembles an attack in shape but is within the real quota must still be admitted by the real algorithm even if the sketch's coarse pre-filter briefly flags it — the pre-filter only sheds load toward the coordination substrate, it is never the final admission authority (P13's exact scope).

21.9 Failure Analysis

A sketch false-positive under-admits a legitimate hot key during a spike; detection is a gap between ratelimiter_sketch_rejected_total and the real algorithm's own reject count; recovery is retuning the pre-filter ceiling (an operator-adjustable parameter, never a recompile) once the false-positive rate is confirmed via the dashboard (§25).

21.10 Operational Notes

ratelimiter_sketch_rejected_total, ratelimiter_ntp_offset_ms, and ratelimiter_clock_regression_total are the three new dashboards this phase introduces; docs/runbooks/ddos-response.md documents the operator procedure for temporarily lowering the pre-filter ceiling during a confirmed attack.

22. Phase 10 — Graceful Degradation, Adaptive Control & Operator Surfaces

22.1 Objectives

Ship the explicit FailureMode dispatch end-to-end (P4), the fixed-step AIMD adaptive quota controller (ADR-23, the full autotuner deferred per §36), and the operator CLI + Grafana surfaces that close out the Phase-0–10 arc.

22.2 Detailed Implementation Steps

FailureModeDispatcher (§11) is wired at every backend boundary (Phase 2, 3, 7, 8); its two variants — FailOpen (admit on backend error) and FailClosed (reject on backend error) — are never defaulted (I6, P4, SRE ch. 21 "Handling Overload," §5). The AIMD controller wraps an existing Limiter (P1 — it is itself a Limiter implementation, never a special case) and observes a configured signal (error-rate or p99-latency budget burn); on success it additively increases the effective quota, on failure it multiplicatively decreases it, converging within 5 RTT to ±5% of the new target (§4, M9) — Nygard's circuit-breaker pattern (ch. 5, §5) is the model for its own internal state machine. ratelimiter-cli (Clap-based) exposes inspect <key>, clear <key>, set-quota <scope> <quota>, list-quotas, policy export/import; Grafana JSON under ops/grafana/ visualizes every metric introduced across Phases 2–9.

22.3 Deliverable

FailOpen/FailClosed fully wired; AimdLimiter wrapping any inner Limiter; ratelimiter-cli binary; ops/grafana/dashboard.json with panels for every metric named in §25.

22.4 Acceptance Criteria

A fixture forcing backend failure under FailOpen shows 100% admission during the outage window; the same fixture under FailClosed shows 100% rejection; the AIMD controller converges to within ±5% of a stepped target quota within 5 RTT in a simulated signal-burn scenario (§4, M9); ratelimiter-cli inspect <key> returns the exact AlgorithmState (§11) matching what the backend holds, verified against InMemBackend and RedisBackend.

22.5 Conformance Fixtures

fixtures/positive/failure_mode_open.json, fixtures/positive/failure_mode_closed.json, fixtures/negative/failure_mode_construction_without_choice.json — asserts construction without an explicit FailureMode is rejected (compile-time where possible, per I6). fixtures/positive/aimd_convergence_5rtt.json.

22.6 Pitfalls

  • Defaulting FailureMode to FailOpen "for convenience" — this silently picks a security posture the operator never reviewed (P4, §23 T7); the type system forbids a Default impl precisely to prevent this.
  • Tuning the AIMD controller's decrease factor too aggressively — an overly multiplicative decrease under a transient signal blip causes unnecessary throughput collapse; the default factor is calibrated against the AIMD literature's stability proofs, not guessed.
  • Shipping the CLI without redacting keys in its own output — inspect must use Key::redacted() (§11) at INFO-equivalent verbosity, full value only behind an explicit --unsafe-show-key flag.

22.7 Performance Concerns

The AIMD controller adds one extra Limiter indirection per decision — measured overhead must stay within the in-process p99 budget (§4) even with the controller wrapping a Redis-backed inner limiter, since the controller's own bookkeeping is in-process regardless of the wrapped backend.

22.8 Edge Cases

An operator calling set-quota on a key mid-decision (a race between the CLI and a live check) must never leave the key's AlgorithmState in a torn state — the backend's atomic update contract (I8 for Redis, shard lock for in-process) already covers this; the CLI issues the update through the same Backend::decide-adjacent path, never a raw storage write.

22.9 Failure Analysis

An AIMD controller that oscillates (repeated increase/decrease without settling) is detected by a dashboard alert on quota-change frequency exceeding a threshold; recovery is an operator override via set-quota to pin the quota manually, disabling the controller for that key until the signal source is fixed.

22.10 Operational Notes

Every quota change (manual via CLI or automatic via AIMD) emits a tracing span event and a ratelimiter_quota_change_total counter (P10) — this is the audit trail an incident postmortem (§24) reconstructs from, and it is the last piece needed before Phase-0's conformance suite (§18) can report full Pass across every non-deferred bucket.

Tracing (OTel via tracing-opentelemetry, ADR-15): one span per Limiter::check, correlated by Key::redacted() (never the raw key, T10). Structured logging: TRACE includes full AlgorithmState; INFO redacts per Key::redacted() (P10).

Dashboards (ops/grafana/dashboard.json): decisions/s by algorithm and backend; reject ratio; p50/p95/p99 decision latency; top-N keys by reject count (hot-key surface, §21); per-tenant budget consumption (hierarchical quota surface, §17); circuit-breaker state timeline (§24 FM-3); gossip convergence time (§20); over-admission total (§8.7).

Alerting philosophy: alert on a bound being approached, not merely a threshold cross — e.g. ratelimiter_over_admission_total alerts at 80% of the derived §8.7 ceiling, giving an operator lead time before the bound is actually exceeded.

SLOs: 99.99% decision availability given a configured FailureMode (§4); p99 added latency within the topology-specific §4 ceiling; conformance suite (§18) green on every release.

Incident response: the on-call runbook set (docs/runbooks/) covers redis-outage.md (§15.10), cluster-partition.md (§19.10), ddos-response.md (§21.10) — each names the exact dashboard panel and the exact CLI command (§22) to run first.

Backup/restore: RedisBackend state is a cache of derived quota consumption, never a system of record — restore is "start from zero counters," documented explicitly so an operator never attempts a point-in-time Redis restore for rate-limit state.

Deployment topology: the library embeds in the service process (no sidecar); the optional ratelimiter-cli and Grafana/Prometheus stack deploy alongside as an operator convenience, never a runtime dependency of the decision path.

Canary/rolling-upgrade/rollback: a canary node runs the new Quota/algorithm configuration against a shadow traffic split before a full rollout; rollback is a configuration revert (no schema migration required for the in-process or Redis-hash-based state, §26).

PhaseDeferred("§25") — the hosted multi-tenant control plane (self-serve quota UI) is not built in Phase 0–10; the Grafana/CLI surface above is the shipped operator interface.

26. Compatibility & Versioning

Wire compatibility: the IETF draft header form (§8.9) is versioned by the draft's own revision; a draft revision bump is a minor version bump of ratelimiter-protocol, gated by re-running the snapshot suite (§16.10) against the new revision's published examples before flipping the default.

Storage compatibility: the Redis hash schema (tokens/last_refill_ms etc., per algorithm, §15) is versioned implicitly by the Lua script's SHA; a script change that alters the stored field shape ships alongside a migration note in CHANGELOG.md and is treated as a breaking change requiring a coordinated deploy (old and new scripts must never both write incompatible shapes to the same key concurrently).

API stability: Limiter, Backend, KeyExtractor (§11) are the stable public surface; AlgorithmState's non_exhaustive attribute allows a new algorithm variant without a major version bump; adding a Backend method is a breaking change by design (P7 keeps the surface narrow specifically to minimize this risk).

Migration: a Quota change (algorithm or parameter) does not require a storage migration — each algorithm's AlgorithmState is independent per key, and a key's state simply resets to the new algorithm's default on first decision under the new Quota (documented explicitly as "quota changes are not state-preserving across algorithm changes").

Deprecation policy: a deprecated legacy header emitter (§16) carries a #[deprecated] Rust attribute with a removal-version note, never silently removed within a major version.

SemVer policy: the workspace crates version in lockstep (a single workspace version); a breaking change to any stable trait (§11) bumps the major version across all crates simultaneously to avoid partial-upgrade incompatibility.

Rolling-upgrade guarantees: old and new binary versions may run concurrently against the same Redis instance only if the Lua script SHA is unchanged; a script-changing release requires either a maintenance window or a versioned-key-prefix migration strategy documented per release in CHANGELOG.md.

PhaseDeferred("§26") — the WASM/edge compile target (a distinct compatibility surface) is not built in Phase 0–10.

27. Testing & Verification Strategy

Unit tests: per-module, colocated with src/, covering each algorithm's equation (§8) and each type's invariant (§11).

Integration tests: per middleware crate (§17.4), per backend against a live Redis (§15.4).

Property tests (proptest, ADR-16): the long-run-rate and burst-honoring properties (§13.4) across all six algorithms; Key::wire round-trip (§12.4).

Differential tests: RedisBackend vs. InMemBackend given the same input sequence must produce identical decisions (§15.5) — this is the primary tool that catches a backend-specific implementation bug rather than an algorithm bug.

Fuzzing (cargo-fuzz, Phase 11 in the original hardening plan, folded into this strategy): each algorithm's check against arbitrary (quota, sequence) inputs; the header emitter against arbitrary Decision values — 30-day continuous run with zero unexpected panics as the gate (M-target, §29).

Chaos / fault injection: partition injection (§19.6), Redis connection drop mid-script (§15.9), clock-skew injection (§21.4) — each a first-class conformance fixture, not an ad-hoc manual test.

Deterministic replay: the SimClock-driven simulator (§7's debugging methodology, ratelimiter-bench/src/sim.rs) replays a scripted sequence and asserts every invariant (I1– I14) by ID after every step — this is the single tool a session runs first when triaging any reported bug.

Soak testing: a 24-hour sustained-load run at the §4 throughput targets, watching for memory growth (I5 violation) or latency drift (tail-latency regression, §29).

Conformance gating (§18): every phase's fixtures must report Pass before the next phase's PR merges; this is the mechanical enforcement of "phases must build on each other" (§7 of the standard).

Performance-regression gating: every M# target in §29 is checked in CI against the previous release's recorded benchmark; a regression beyond a documented tolerance fails the build (§28).

Every invariant (I1–I14, §7), every threat (T1–T12, §23), and every failure class (FM-1– FM-12, §24) maps to at least one fixture named above or in the phase-level §N.5 sections.

Reproducible builds: rust-toolchain.toml pins the exact compiler version (§12.2); Cargo.lock is committed and never gitignored; the Dockerfile's builder stage pins its base image by digest, not tag.

29. Performance Engineering

Methodology: the USE method (Utilization, Saturation, Errors — Gregg ch. 2, §5) applied per subsystem (CPU: shard lock contention; memory: per-key footprint I5; network: Redis RTT §4); tail-latency analysis follows Gregg ch. 10's percentile methodology, always reporting p50/p95/p99, never a bare average.

Allocation analysis: Key::wire() and header construction (§16.7) are the two hot-path allocation sites profiled first; GCRA's check (§8.6) is allocation-free in the steady state (no Vec growth), the benchmark that proves this is cargo bench --bench gcra_allocfree.

Lock contention analysis: shard-local lock hold time measured via criterion's iter_custom, comparing single-key (worst case, one shard, all contention) vs. multi-key (best case, spread across shards) traffic shapes (§14.7).

Cache analysis: GCRA's 8-byte-per-key state (§8.6 table) is chosen partly for cache-line density under the §4 shard-count assumption; a perf stat cache-miss comparison across algorithms is recorded in benchmarks/results/cache-analysis.md.

Syscall analysis: the Redis backend's connection-pool sizing (§4 FD budget) is verified via strace -c under load to confirm no unexpected per-request connect()/accept() calls.

30. Scalability Analysis

What stays constant: per-key memory footprint (O(1) per key, §4) regardless of total key count, up to the process memory ceiling; decision latency in the in-process and centralized topologies (O(1) per decision, no scan).

What grows, and its Big-O: total memory grows O(number of distinct keys) — the named bottleneck at high key cardinality, mitigated by the deferred Count-Min-Sketch backend (§36) once cardinality exceeds the per-process ceiling; Redis backend throughput is bounded by Redis's own single-threaded command-processing rate (a named ceiling, not this project's to remove — sharding Redis itself, or moving to the cluster topology of Phase 7, is the lever beyond it).

Named bottlenecks in order: (1) a single hot key's shard lock (relieved by the Phase-9 sketch pre-filter, P13); (2) Redis single-connection round-trip latency (relieved by connection pooling, then by the cluster topology); (3) cross-node coordination cost under the sharded/gossip topologies (bounded, not eliminated, by §8.7's derived formula); (4) per-process key-cardinality memory ceiling (relieved by the deferred sketch backend, §36).

Horizontal scaling: the in-process backend scales horizontally for free (each replica is independent, at the cost of the per-instance-multiplier problem P6/§17 solves via coordination); the centralized and sharded backends scale by adding Redis/cluster capacity, not application replicas.

Vertical scaling: shard count (num_cpus × 4, §14) scales automatically with core count on a single node; no manual retuning required below the false-sharing threshold Herlihy & Shavit's ch. 9 (§5) describes.

Sharding/partitioning: the cluster topology's consistent-hash ring (Karger et al. 1997, §5, ADR-06) is the partitioning scheme; rebalance cost on membership change is O(1/N) of keys moved per Karger's own guarantee, not O(N).

Coordination overhead: the practical ceiling is the point at which cross-node coordination latency (§4) exceeds the added-latency budget for the calling service's own SLO — beyond that ceiling, the lever is either the gossip topology's relaxed consistency (§20) or the local-approximate sketch backend (deferred, §36).

The practical ceiling and the levers beyond it: centralized-Redis mode ceilings around Redis's own single-instance throughput (tens of thousands of ops/s); the lever is Phase 7's sharded cluster; sharded-cluster mode ceilings around cross-node coordination latency at very high shard counts; the lever is Phase 8's gossip mode; gossip mode's ceiling is key-cardinality memory, whose lever is the deferred sketch backend (§36).

31. Mental Models & First Principles

  • MM1 — A rate limit is a budget, not a switch. The compressed insight: every algorithm is answering "how much budget remains," never a boolean "allowed/blocked" computed from scratch. Predicts: any design that can't answer "how much is left" (only "yes/no") cannot emit RateLimit-Remaining (§8.9) or support hierarchical composition (P6). Bug class without it: engineers reach for a boolean flag per key and then cannot explain partial admission or headers. Applied in §11 (Decision::Permit{remaining}) and §17.
  • MM2 — GCRA is token bucket wearing one number. The insight: a tat timestamp encodes exactly the same state as (tokens, last_refill) — they are mathematically equivalent views (§8.6). Predicts: any bug found in token bucket has a GCRA analogue expressible in timestamp arithmetic, and vice versa. Bug class without it: treating GCRA as a mysterious black box instead of a compressed encoding, leading to blind copy-paste from a reference implementation without understanding the tolerance term. Applied in §13, §8.10.
  • MM3 — Consistency is a dial, not a switch. The insight: centralized-Redis (§15), sharded-cluster (§19), and gossip (§20) are the same problem at three points on a dial between "coordination cost" and "admission accuracy," not three unrelated features. Predicts: a workload's actual latency/accuracy requirement determines the correct point on the dial; there is no universally-best topology. Bug class without it: picking gossip mode for a financial hard-quota workload because it "scales better," ignoring that its accuracy contract explicitly does not support that use case (§20.6). Applied in §8.7, §30.
  • MM4 — Every distributed counter has an over-admission bound; the question is whether it's zero. The insight: only a fully-synchronous, always-reachable centralized store drives the bound in §8.7's formula to zero — every other topology carries a nonzero, computable ceiling. Predicts: "is this limiter exact" is never the right question; "what is its over-admission ceiling at my N and L" is. Bug class without it: an operator promises exact enforcement on a topology that structurally cannot provide it. Applied in §8.7, §33.
  • MM5 — A hot key is a local problem before it is a distributed one. The insight: the cheapest place to shed hot-key load is the process that first sees it, not the shared coordination substrate three hops away (P13). Predicts: any DDoS mitigation strategy that starts at the coordination layer is already too late and too expensive. Bug class without it: scaling Redis to survive an attack instead of filtering upstream. Applied in §21.
  • MM6 — Monotonic time and wall time answer different questions. The insight: "how much time elapsed" (monotonic) and "what time is it" (wall clock) are never interchangeable (§8.8, P2). Predicts: any algorithm that reads wall time on its hot path will misbehave exactly once, at the worst possible moment (an NTP step). Bug class without it: the SystemTime pitfall repeated across nearly every phase's §N.6. Applied in §8.8, §21.
  • MM7 — Fail-open and fail-closed are both correct — for different threat models. The insight: there is no universally safer default; the right choice depends entirely on whether availability or containment is the higher-value asset for this particular API (SRE ch. 21, §5). Predicts: a blanket "always fail open" or "always fail closed" policy across an entire fleet is itself a design smell. Bug class without it: an operator applies one team's threat model to another team's API. Applied in §22, §23 T7.

33. Back-of-Envelope Capacity Model

Every number below is derived from §4, formula shown, never asserted.

  1. In-process single-core throughput ceiling: M1 target 1,000,000 decisions/s × 900 ns p99 (M5) ⇒ at steady state, 1 / 900ns ≈ 1.11M/s — consistent with M1's target, confirming the target is achievable at the stated per-decision cost.
  2. Per-shard key capacity within an 8 KiB L1 slice: 8 KiB / 8 bytes-per-key (GCRA, §8.6 table) = 1,024 keys per L1-resident shard segment before spilling to L2.
  3. Total in-process memory at 10M distinct keys (GCRA): 10,000,000 × 8 bytes = 80 MB — comfortably within a typical service pod's memory budget, confirming GCRA's cache advantage claim in §4/§8.6.
  4. Total in-process memory at 10M distinct keys (sliding-log, worst case): 10,000,000 × 16 KiB (M8 ceiling) = 160 GB — clearly infeasible at this cardinality, which is exactly why §8.4 states sliding-log's memory growth as its named weakness and why the deferred sketch backend (§36) exists for high-cardinality workloads.
  5. Redis round-trip bandwidth at M2's throughput: 50,000 decisions/s × (~120 bytes request + ~80 bytes response, EVALSHA argument + reply) ≈ 10 MB/s per connection — trivial relative to typical same-AZ network capacity, confirming M6's 5 ms p99 latency target is coordination-bound, not bandwidth-bound.
  6. Fan-out bandwidth for hierarchical composition (5 layers, Redis-backed): 5 × 10 MB/s (from #5) = 50 MB/s per connection pool at M2's throughput — this is why §17.7 recommends at most 2 network-bound layers.
  7. Cluster over-admission at N=8, r=1000/s/node, L=50ms (§8.7 worked example): 8 × 1000 × 0.05 = 400 excess admissions in the worst window — 0.4× one node's per-second budget, reproduced from §8.7 and chained here as the model's headline number.
  8. FD budget at M2's connection pooling ratio: 1 connection per 200 concurrent tasks (§4) × 50,000 decisions/s target ÷ (1,000/50ms round trips per connection per second at M6's 5ms latency) ≈ 12–13 pooled connections sustain the full M2 throughput target.
  9. Sketch pre-filter memory at fixed depth=4, width=2048 counters (§21): 4 × 2048 × 4 bytes (u32 counter) = 32 KiB per shard — independent of key cardinality, the exact property Cormode-Muthukrishnan's sub-linear guarantee (§5) predicts.
  10. Gossip convergence bandwidth at 16 nodes, 50ms window (§4, M4): if each node gossips its delta to log2(16) = 4 peers per cycle, and a cycle must complete within 50ms, each node's outbound rate is 4 messages / 50ms = 80 messages/s — a negligible fraction of the same-AZ bandwidth already budgeted in #5.

35. Alternative Architectures (Roads Not Taken)

35.1 Pure Client-Side Estimation (No Coordination At All)

 Node A [local counter]     Node B [local counter]     Node C [local counter]
    (no communication between nodes whatsoever)

Regime where it wins: extremely latency-sensitive, loss-tolerant workloads (e.g. best-effort telemetry sampling) where even gossip's 50ms convergence window (§20) is an unaffordable coordination tax. Real system: nginx limit_req (§32) — no cross-instance coordination by design. Rejected here because the over-admission bound (§8.7) becomes unbounded (grows with N with no L-driven ceiling at all) the moment more than one node exists — unacceptable for the API-protection and DDoS-mitigation goals in §1.

35.2 Kernel-Level Enforcement (eBPF)

  NIC → XDP/eBPF program (per-packet token-bucket check) → kernel drop or userspace

Regime where it wins: enforcement must survive even when the userspace process protecting itself is itself under CPU-starvation attack — eBPF admission happens before a packet ever reaches the application's scheduler. Real system: Cloudflare's and Meta's published XDP-based DDoS mitigation layers. Rejected here because it operates below the HTTP-semantic layer this project targets (no access to Key's tenant/route semantics, §11) and because the no-code, Rust-userspace scope of §1 explicitly delegates kernel-level enforcement as a research deliverable, not a Phase 0–10 goal (PhaseDeferred("§35"), registered §36).

35.3 Centralized Sequencer (Single Global Arbiter)

  All nodes ──requests──> [ single sequencer process ] ──decisions──> All nodes

Regime where it wins: a workload small enough that one process can sequence every decision globally with zero over-admission and no approximation at all — e.g. a low-QPS internal-tooling quota where exactness matters more than the single point of failure it introduces. Real system: a single-writer Redis instance is effectively this (§15) at modest scale, before its own throughput ceiling (§30) is reached. Rejected as the general answer here because it reintroduces exactly the coordination-cost-vs-accuracy tradeoff this project's dial (MM3) exists to make explicit and tunable, rather than hardcoding "exact but unscalable" as the only option.

37. Glossary

  • Admission control. The decision of whether a unit of work may proceed against a quota.
  • AIMD. Additive-Increase/Multiplicative-Decrease — the convergence discipline behind the Phase-10 adaptive controller (§22).
  • AlgorithmState. The per-key operator-visible state of whichever algorithm is active (§11).
  • Atomicity (Redis). The guarantee that an EVALSHA call's read-modify-write completes as one indivisible operation (I8, P8).
  • Backend. The narrow trait (decide/state/clear) abstracting where per-key state lives (§11, P7).
  • Burst. The maximum units a key may consume instantaneously before the steady-state rate applies (§8.1).
  • Circuit breaker. The state machine that stops calling a failing backend and periodically probes it (§22, §24 FM-3, Nygard §5).
  • Clock skew. The difference between two nodes' clocks, bounded by NTP's guarantee under normal operation (§8.8, §21).
  • Cluster mode. The sharded, consistent-hash-routed distributed enforcement topology (§19).
  • Conformance fixture. A named input/expected-output pair exercised by the conformance runner (§18).
  • Consistent hashing. The key-to-shard mapping scheme minimizing remap cost on membership change (Karger et al. 1997, §5).
  • Cost. The number of units a single request consumes against a quota, default 1 (P11).
  • Count-Min Sketch. A sub-linear-memory approximate frequency-counting structure used for hot-key detection (§21, Cormode-Muthukrishnan 2005).
  • Decision. The output of Limiter::check — Permit or Reject (§11).
  • Delay-Variation Tolerance (DVT). GCRA's burst-equivalent parameter (§8.6).
  • Distributed counter. A per-key count maintained across multiple enforcement nodes (§8.7).
  • Emission interval. GCRA's per-request time increment, period/rate (§8.6).
  • Fail-closed. The FailureMode that rejects on backend error (§22, P4).
  • Fail-open. The FailureMode that admits on backend error (§22, P4).
  • Fixed-window counter. The algorithm counting requests within a period keyed by integer division of time (§8.3).
  • GCRA. Generic Cell Rate Algorithm — token bucket expressed as a single timestamp (§8.6).
  • Gossip mode. The eventually-consistent, epidemic-broadcast distributed enforcement topology (§20).
  • Hierarchical quota. A composition of multiple quota layers (IP, user, route, tenant, global) evaluated first-reject-wins (§17, P6).
  • Hot key. A single key receiving disproportionately high traffic relative to its peers (§21).
  • In-process backend. The sharded, single-node, network-free Backend implementation (§14).
  • Invariant. A property the system guarantees to hold, numbered I1–I14 (§7).
  • Key. The typed, tenant-scoped identity of a rate-limited counter (§11).
  • Leaky bucket. The algorithm smoothing output rate via a draining queue (§8.2).
  • Monotonic clock. A clock guaranteed never to move backward within one process (§8.8, P2).
  • Over-admission. Admitted traffic in excess of the nominal quota, bounded but nonzero under the distributed topologies (§8.7, I2).
  • Quota. The policy triple (algorithm, burst, rate, period) (§11).
  • Reconciliation. The periodic process by which gossip-propagated counters converge (§20).
  • Retry-After. The RFC 7231 header advising a client when to retry after a 429 (§8.9).
  • RateLimit-*. The IETF-draft header family communicating limit/remaining/reset (§8.9).
  • Sharding. Partitioning keys across multiple nodes or lock domains (§14, §19).
  • Sliding-window counter. The O(1)-memory approximation interpolating between two fixed windows (§8.5, Cloudflare).
  • Sliding-window log. The exact, unbounded-memory-until-capped algorithm tracking individual event timestamps (§8.4).
  • Tenant. A namespace boundary within Key, preventing cross-tenant quota interference (§11, P9, I9).
  • Theoretical Arrival Time (TAT). GCRA's single-timestamp state variable (§8.6).
  • Token bucket. The algorithm admitting bursts up to a capacity, refilling at a steady rate (§8.1, Turner 1986).
