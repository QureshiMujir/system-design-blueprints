31. Mental Models & First Principles

  • MM1 — A rate limit is a budget, not a switch. The compressed insight: every algorithm is answering "how much budget remains," never a boolean "allowed/blocked" computed from scratch. Predicts: any design that can't answer "how much is left" (only "yes/no") cannot emit RateLimit-Remaining (§8.9) or support hierarchical composition (P6). Bug class without it: engineers reach for a boolean flag per key and then cannot explain partial admission or headers. Applied in §11 (Decision::Permit{remaining}) and §17.
  • MM2 — GCRA is token bucket wearing one number. The insight: a tat timestamp encodes exactly the same state as (tokens, last_refill) — they are mathematically equivalent views (§8.6). Predicts: any bug found in token bucket has a GCRA analogue expressible in timestamp arithmetic, and vice versa. Bug class without it: treating GCRA as a mysterious black box instead of a compressed encoding, leading to blind copy-paste from a reference implementation without understanding the tolerance term. Applied in §13, §8.10.
  • MM3 — Consistency is a dial, not a switch. The insight: centralized-Redis (§15), sharded-cluster (§19), and gossip (§20) are the same problem at three points on a dial between "coordination cost" and "admission accuracy," not three unrelated features. Predicts: a workload's actual latency/accuracy requirement determines the correct point on the dial; there is no universally-best topology. Bug class without it: picking gossip mode for a financial hard-quota workload because it "scales better," ignoring that its accuracy contract explicitly does not support that use case (§20.6). Applied in §8.7, §30.
  • MM4 — Every distributed counter has an over-admission bound; the question is whether it's zero. The insight: only a fully-synchronous, always-reachable centralized store drives the bound in §8.7's formula to zero — every other topology carries a nonzero, computable ceiling. Predicts: "is this limiter exact" is never the right question; "what is its over-admission ceiling at my N and L" is. Bug class without it: an operator promises exact enforcement on a topology that structurally cannot provide it. Applied in §8.7, §33.
  • MM5 — A hot key is a local problem before it is a distributed one. The insight: the cheapest place to shed hot-key load is the process that first sees it, not the shared coordination substrate three hops away (P13). Predicts: any DDoS mitigation strategy that starts at the coordination layer is already too late and too expensive. Bug class without it: scaling Redis to survive an attack instead of filtering upstream. Applied in §21.
  • MM6 — Monotonic time and wall time answer different questions. The insight: "how much time elapsed" (monotonic) and "what time is it" (wall clock) are never interchangeable (§8.8, P2). Predicts: any algorithm that reads wall time on its hot path will misbehave exactly once, at the worst possible moment (an NTP step). Bug class without it: the SystemTime pitfall repeated across nearly every phase's §N.6. Applied in §8.8, §21.
  • MM7 — Fail-open and fail-closed are both correct — for different threat models. The insight: there is no universally safer default; the right choice depends entirely on whether availability or containment is the higher-value asset for this particular API (SRE ch. 21, §5). Predicts: a blanket "always fail open" or "always fail closed" policy across an entire fleet is itself a design smell. Bug class without it: an operator applies one team's threat model to another team's API. Applied in §22, §23 T7.

Reference Implementations

  • brandur/redis-cell — src/algorithms/gcra.rs. Lesson: GCRA as a single Redis command (CL.THROTTLE) with no round-trip amplification. Pitfall: it hardcodes one tolerance rounding mode; this project's Lua script exposes it as a parameter. Applied in §15 (Phase 3).
  • envoyproxy/ratelimit (Go) — src/service/ratelimit.go, src/redis/. Lesson: descriptor-based hierarchical key composition. Pitfall: its Redis pipeline batches across unrelated keys, letting one slow key stall an unrelated batch. Applied in §17 (Phase 5).
  • Kong/kong — kong/plugins/rate-limiting/policies/init.lua. Lesson: pluggable policy backends (local/cluster/redis) behind one interface. Applied in §14 (Phase 2), ADR-06.
  • nginx ngx_http_limit_req_module (C). Lesson: leaky-bucket at connection-accept with a bounded burst queue (nodelay/delay). Applied in §13 (Phase 1), §8.2.
  • Stripe Engineering, "Scaling your API with Rate Limiters" reference architecture (published design). Lesson: the four-limiter taxonomy (request rate, concurrent requests, fleet usage, worker utilization). Applied in §6, §17 (Phase 5).
  • Cloudflare, sliding-window-counter approximation per "How we built rate limiting capable of scaling to millions of domains" and "Counting things, a lot of different things" (published design). Applied in §13 (Phase 1), §8.5.

Glossary (§37) · 40 terms · site-wide glossary

Admission control
The decision of whether a unit of work may proceed against a quota.
AIMD
Additive-Increase/Multiplicative-Decrease — the convergence discipline behind the Phase-10 adaptive controller (§22).
AlgorithmState
The per-key operator-visible state of whichever algorithm is active (§11).
Atomicity (Redis)
The guarantee that an EVALSHA call's read-modify-write completes as one indivisible operation (I8, P8).
Backend
The narrow trait (decide/state/clear) abstracting where per-key state lives (§11, P7).
Burst
The maximum units a key may consume instantaneously before the steady-state rate applies (§8.1).
Circuit breaker
The state machine that stops calling a failing backend and periodically probes it (§22, §24 FM-3, Nygard §5).
Clock skew
The difference between two nodes' clocks, bounded by NTP's guarantee under normal operation (§8.8, §21).
Cluster mode
The sharded, consistent-hash-routed distributed enforcement topology (§19).
Conformance fixture
A named input/expected-output pair exercised by the conformance runner (§18).
Consistent hashing
The key-to-shard mapping scheme minimizing remap cost on membership change (Karger et al. 1997, §5).
Cost
The number of units a single request consumes against a quota, default 1 (P11).
Count-Min Sketch
A sub-linear-memory approximate frequency-counting structure used for hot-key detection (§21, Cormode-Muthukrishnan 2005).
Decision
The output of Limiter::check — Permit or Reject (§11).
Delay-Variation Tolerance (DVT)
GCRA's burst-equivalent parameter (§8.6).
Distributed counter
A per-key count maintained across multiple enforcement nodes (§8.7).
Emission interval
GCRA's per-request time increment, period/rate (§8.6).
Fail-closed
The FailureMode that rejects on backend error (§22, P4).
Fail-open
The FailureMode that admits on backend error (§22, P4).
Fixed-window counter
The algorithm counting requests within a period keyed by integer division of time (§8.3).
GCRA
Generic Cell Rate Algorithm — token bucket expressed as a single timestamp (§8.6).
Gossip mode
The eventually-consistent, epidemic-broadcast distributed enforcement topology (§20).
Hierarchical quota
A composition of multiple quota layers (IP, user, route, tenant, global) evaluated first-reject-wins (§17, P6).
Hot key
A single key receiving disproportionately high traffic relative to its peers (§21).
In-process backend
The sharded, single-node, network-free Backend implementation (§14).
Invariant
A property the system guarantees to hold, numbered I1–I14 (§7).
Key
The typed, tenant-scoped identity of a rate-limited counter (§11).
Leaky bucket
The algorithm smoothing output rate via a draining queue (§8.2).
Monotonic clock
A clock guaranteed never to move backward within one process (§8.8, P2).
Over-admission
Admitted traffic in excess of the nominal quota, bounded but nonzero under the distributed topologies (§8.7, I2).
Quota
The policy triple (algorithm, burst, rate, period) (§11).
Reconciliation
The periodic process by which gossip-propagated counters converge (§20).
Retry-After
The RFC 7231 header advising a client when to retry after a 429 (§8.9).
RateLimit-*
The IETF-draft header family communicating limit/remaining/reset (§8.9).
Sharding
Partitioning keys across multiple nodes or lock domains (§14, §19).
Sliding-window counter
The O(1)-memory approximation interpolating between two fixed windows (§8.5, Cloudflare).
Sliding-window log
The exact, unbounded-memory-until-capped algorithm tracking individual event timestamps (§8.4).
Tenant
A namespace boundary within Key, preventing cross-tenant quota interference (§11, P9, I9).
Theoretical Arrival Time (TAT)
GCRA's single-timestamp state variable (§8.6).
Token bucket
The algorithm admitting bursts up to a capacity, refilling at a steady rate (§8.1, Turner 1986).
