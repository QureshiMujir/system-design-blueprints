Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. — If parse_script returns Ok(Program) but jsfront scopes shows a Binding with tdz=false for a const declaration, which invariant is violated, and which two passes are candidates for the bug? → I14 (hoist/TDZ) in §7 is violated; I12 (resolve) is the cross-check. Candidates: collect_bindings (P8/§20) setting wrong BindingKind or missing tdz=true, OR the ScopeKind/Binding decision per the schema in §11.4 (block vs function scope). Resolution requires tracing collect_bindings for Const in js-semantics/src/collect.rs. Sources: §7 (I14/I12), §20 (P8), §11.4 (Binding schema).
  2. — A module cycle a↔b links successfully (status Linked) but jsfront eval prints the wrong value for b's export. The live binding is correctly wired. What is the most likely cause, and which section defines the fix? → Evaluation order in cyclic modules (§22/P10, InnerModuleEvaluation): post-order DFS must evaluate a before b if b depends on a's export. If b's initializer reads a.x before a has evaluated, it sees TDZ. Fix: verify topological order respects SCC; cross-reference §8.6 (worked example B) for the evaluation sequence.
  3. — Why does jsfront parse emit an ArrowFunctionExpression for async (x) => x but a CallExpression for async\n(x) when the only difference is a newline? → Restricted production (I8/§18): async + [no LineTerminator here] before ( is required for async-arrow disambiguation. With a LT, async is parsed as an identifier, (x) as a call's argument list. This is the CoverCallExpressionAndAsyncArrowHead disambiguation (§16/P4). Sources: §6.3 (ASI) + §4.6 (async-arrow pitfall).
  4. — The link function runs successfully on a diamond graph A→{B,C}→D but is called three times for module D. Which invariant is violated and what is the root cause? → I18 (idempotent link). Root cause: ModuleStatus guard not consulted before recursing — link is re-entering D without checking status ≥ Linking. Fix: add status guard at entry to InnerModuleLinking. See §22/P10, §8.7 (link sequence).
  5. — A conformance test reports a/b/c parses as a regex literal followed by c instead of a division chain. What is the minimal 2-section diagnosis path? → §13 (P1, LexGoal returned by lexer at / after a) and §18 (P6, goal set by parser before requesting the / token). The parser must have set RegExp goal when it should have set Div after the identifier a. Check: goal is Div after all operand tokens per §14/P2 leading table.
  6. — Why must EarlyError be collected into a Vec rather than returned as Err immediately, and which two design principles enforce this? → P12 (LSP needs full diagnostics), §6.2 (parsing never panics implies Result-only API, not fail-fast). A fail-fast approach would provide only the first error; LSP (proj 139) requires all errors in a file. Also I25 (error list complete + source-ordered) mandates collection. Sources: §6 (Design Principles 6.2, 6.12), §7 (I25), §24 (P12).
  7. — resolve_export(m, "x") returns Ambiguous even though only one module exports x. What sequence of star re-exports produces this, and which abstract operation detects it? → Diamond re-export: m does export * from "a" and export * from "b", and both a and b export x (possibly from a shared dependency). ResolveExport (§22, resolve.rs) accumulates all resolved bindings into ResolveSet; size > 1 → Ambiguous. Fix: deduplicate same (module, binding) pairs (same ultimate source is not ambiguous). Sources: §22/P10 + §8.8 (early-error catalog).
  8. — An embedder calls parse_module and analyze successfully, then calls link and gets LinkError::NotFound. The module file exists on disk. What is the most likely missing step? → The embedder did not implement ModuleLoader::resolve correctly — probably returned a stub or used a loader that doesn't read from disk. js-cli's file loader is the only concrete std impl; embedders must supply their own. Sources: §22 (P10, ModuleLoader), §3.2 (component responsibilities), §11.5 (ModuleLoader trait).
  9. — Why can two var x declarations in the same scope not generate a DuplicateLexical early error, but two let x declarations do? → var allows redeclaration: CreateGlobalVarBinding/CreateMutableBinding for var is idempotent (I13 says no duplicate lexical binding). let enters LexicallyDeclaredNames; the invariant requires disjointness from other lexical names in the same scope. Mechanism: collect_bindings in js-semantics merges Var bindings, flags Let/Const duplicates as EarlyError. Sources: §8 (I13), §20 (P8, collect_bindings), §8.8 (early-error catalog).
  10. — Why does 259 define Completion as an enum rather than using Rust's Result<Value, Error>, and what does Break(Option<Atom>) enable that Err(BreakSignal) cannot? → Result<V,E> is binary (ok vs error); JS control flow has 5 completion types — Break/Continue carry an optional target label for labeled loops. Err(BreakSignal) would require the VM to re-examine the label on every unwinding frame. Completion::Break(Some(Atom)) carries the label inline, allowing the ExecutionContext stack to unwind to exactly the right labeled scope without re-matching. Sources: §23 (P11, Completion), §11.5 (Completion enum), §7 (I19).
  11. — If parse_script takes 200 ms for a 4 MB file (only 20 MB/s), what are the three most likely bottlenecks in order of probability? → (1) AST allocation churn: CowStr::Owned allocated for identifiers that should borrow — check escape rate in lexer, ensure ASCII idents use Borrowed. (2) Expr enum >48 B causing cache thrashing — run size_of::<Expr>() assert, check if recent variant additions broke boxing. (3) Unicode ID_Continue table lookup on ASCII — ensure byte-class LUT path fires before wide-char table. Sources: §25 (P13, profiling), the Performance Engineering section (Allocation Strategy, PE.2), §13 (P1, lexer perf).
  12. — A property test discovers that parse(print(parse(src))) produces a different AST from parse(src). What are the two most likely codegen bugs? → (1) Parenthesization: printer drops parens required for precedence (e.g., (a,b) sequence expression as function argument) — fix: consult bp table during print. (2) ASI hazard: printer emits return\n value without a ;, and re-parse inserts ASI turning it into return; value — fix: always emit ; or keep operand on same line. Sources: §24 (P12, roundtrip), §18 (P6, ASI), §12.6 (pitfalls).
  13. — Why must SourceTextModuleRecord.code (the Program) and ScopeTree be kept separately rather than embedding scope into the AST nodes? → The AST is immutable and Send+Sync post-parse; embedding mutable scope data would require Mutex/RefCell per node, destroying cache locality and concurrency. The ScopeTree is built in a separate pass, is itself immutable post-analysis, and can be independently cached (invalidated by source change) or shared across multiple Realms without re-parsing. Sources: §3.2 (component responsibilities), §11.5 (type semantics), §20/P8 (separate pass rationale — design principle 6.8).
  14. — An engine (project 126) reports that const c = 1; c = 2 does not throw TypeError at runtime. Is this a 259 bug or a 126 bug, and which invariant defines the responsibility boundary? → 259's responsibility: ScopeTree.Binding{ name:"c", kind:Const, mutable:false } must be set correctly (I14). EnvironmentRecord.create_immutable_binding must mark the slot immutable; set_mutable_binding on an immutable+strict slot must return Completion::Throw(TypeError) (I15). If those are correct, the bug is in 126's Evaluator not consulting the immutability flag. Diagnosis: dump jsfront scopes to confirm mutable:false, then test the set_mutable_binding abstract op directly. Sources: §7 (I14/I15), §21/P9 (EnvRecord ops, acceptance criterion 5), §11.5 (EnvironmentRecord contract).
  15. — The Test262 EarlyError bucket has 3 unexpected failures after adding generator support (P4). All three involve yield in default-parameter expressions. Which interaction between three passes causes this? → (1) js-parser (P4/§16): allow_yield in ParseCtx must be false for default parameter expressions even inside generators — parameters parse before the body context. (2) js-semantics (P8/§20): collect_bindings for a generator function sets allow_yield=true for the body but must not propagate that into default-param initializer scope. (3) Early-error check (P7/§19): yield as an expression in strict-mode default param is forbidden. The bug is likely ParseCtx leaking allow_yield=true into param initializer parse. Sources: §16 (P4, §4.6 pitfalls), §19 (P7, strict/early), §20 (P8). ---

Mental Models & First Principles

MM1 — The lexer-parser are one coupled state machine, not a pipeline.

  • Insight: JS tokenization is context-sensitive; the lexer cannot decide / = Div vs RegExp without knowing the parser's syntactic position. LexGoal is the channel from parser to lexer on every request.
  • What it predicts: any attempt to separate lexer and parser into independent stages produces mis-tokenized /regex/ patterns — the canonical JS implementation bug.
  • Bug class without it: a/b/g parsed as a / b / g (division chain) instead of a / (/b/g).
  • Applies at: §13 (P1, LexGoal design), §18 (P6, goal protocol), §8.1 (token model).

MM2 — Cover grammars are deferred disambiguation, not ambiguity.

  • Insight: (a, b) is grammatically a parenthesized expression OR arrow parameters depending on whether => follows. The spec defines a cover production that encompasses both; the parser reads it once and reinterprets on the deciding token.
  • What it predicts: any backtracking scheme re-lexes tokens and is O(n²) on long arrow heads.
  • Bug class without it: (a={f()}, b) => triggers a full re-parse of the args, causing quadratic blowup or span drift.
  • Applies at: §17 (P5, cover refinement), §16 (P4, arrow head).

MM3 — Hoisting creates two bindings for every let/const: the temporal dead zone and the initialized slot.

  • Insight: let x = 1 hoists x to block scope top (making shadowing predictable) but places it in TDZ — uninitialized — until the declaration point. The binding exists statically; the value does not.
  • What it predicts: x; let x is not "undeclared" — it is "declared but uninitialized" → ReferenceError at runtime, not TypeError.
  • Bug class without it: treating let as not hoisted → wrong use-before-decl diagnostics; implementing TDZ with a runtime sentinel rather than a static slot flag misses static analysis opportunities.
  • Applies at: §20 (P8, ScopeTree TDZ), §21 (P9, env slot uninitialized).

MM4 — Module live bindings are aliased slots, not copied values.

  • Insight: import { x } from "m" does not snapshot x; it creates an alias into m's Module env slot. Assigning to x in m is visible through the import.
  • What it predicts: CreateImportBinding must store (EnvId, slot_index) — a reference — not Value.
  • Bug class without it: copy-on-import semantics break all mutable shared state across modules; tests pass with constant exports but fail with mutated ones.
  • Applies at: §22 (P10, live binding wiring), §8.6 (worked example B).

MM5 — Completion is a tagged union that models ALL non-local control flow.

  • Insight: every JS statement produces a Completion: Normal, Throw, Return, Break(label), Continue(label). The evaluation bridge must propagate these faithfully — finally overrides with its own completion; label mismatch on Break/Continue stops at the wrong boundary.
  • What it predicts: any integer return-code scheme fails to distinguish return from break from throw, making finally semantics impossible.
  • Bug class without it: try { return x } finally { return y } returns x instead of y (finally overrides).
  • Applies at: §23 (P11, Completion propagation), §21 (P9, ExecutionContext stack).

MM6 — The parse→link→evaluate 3-phase ordering is cycle-safe because ModuleStatus is a monotone FSM.

  • Insight: a cyclic import graph a↔b would deadlock a 1-phase eager evaluator. The spec's DFS with Linking/Evaluating in-progress markers allows visiting a cycle without re-entering it: the second visit sees ≥Linking and skips.
  • What it predicts: without status guards, InnerModuleLinking on a cycle recurses infinitely.
  • Bug class without it: stack overflow on import a from "./a.js" self-import; or incorrect partial-link for diamond graphs.
  • Applies at: §22 (P10, link DFS), §8.7 (link sequence diagram).

MM7 — The Pratt binding-power model replaces recursive grammar nesting with a single iterative loop.

  • Insight: traditional recursive descent requires one function per precedence level (O(levels) stack frames per token). Pratt assigns left_bp/right_bp to each operator; a single loop handles all expression parsing with one frame.
  • What it predicts: deep expression chains a+b+c+... (10k ops) use O(1) stack instead of O(k).
  • Bug class without it: recursive expression parsers overflow on adversarial input; also, right-associativity (**) requires special-casing each level.
  • Applies at: §14 (P2, Pratt implementation), §5.2 (Pratt 1973).

MM8 — no_std + alloc is a correctness guarantee, not a portability feature.

  • Insight: no_std prevents any std::net/std::fs from entering core crates at compile time. The linker-level check is stronger than any code review. It is the enforcement mechanism for the isolation contract (C-10, C-12).
  • What it predicts: a no_std build failure catches accidental I/O imports that would break embedded deployments or introduce SSRF vectors.
  • Bug class without it: a transitive dep could add filesystem access to js-runtime, allowing a host engine to be surprised by implicit file reads.
  • Applies at: §12 (P0, no_std CI gate), §4 (C-12), §10 (all core crates).

MM9 — ESTree shape is the integration test, not just a format.

  • Insight: jsfront parse JSON must byte-diff-equal Acorn's output (modulo normalized fields) on any valid input. This is not just a compatibility goal — it is the only scalable way to prove grammar correctness across thousands of edge cases without hand-writing golden files for each.
  • What it predicts: any grammar divergence from Acorn on a valid input is either a bug in our parser or a deliberate spec-driven deviation (documented in the allowlist).
  • Bug class without it: parser ships with silent ASI errors, wrong precedence, or missing optional chain handling that only surface in production.
  • Applies at: §25 (P13, differential), §5.3 (Acorn reference).

MM10 — ScopeTree is the only correct interface between the parser and the runtime; the AST is not.

  • Insight: the AST knows where identifiers appear; ScopeTree knows what they resolve to and how they're hoisted. GlobalDeclarationInstantiation and InitializeEnvironment read ScopeTree, not the AST.
  • What it predicts: passing raw AST Ident nodes to the runtime requires the runtime to redo scope analysis — duplicating work and creating drift.
  • Bug class without it: the runtime re-implements hoisting logic and diverges from the semantics pass, producing different TDZ behavior in different contexts.
  • Applies at: §20 (P8, ScopeTree design), §21 (P9, GDI reads ScopeTree), §22 (P10, InitializeEnvironment).

Glossary · 34 terms · site-wide glossary

ADR
Architecture Decision Record. Numbered entry in §9 capturing a design choice, locked alternative, rationale, and when the rejected choice wins.
ASI
Automatic Semicolon Insertion. Three ECMA-262 §12.10 rules that implicitly insert ; at line boundaries and before }. Governed by I7/I8 and implemented in P6/§18.
AST
Abstract Syntax Tree. Typed enum tree rooted at Program. Nodes are ESTree-compatible, store Span, and are immutable post-parse. See §11.2.
Atom
Interned identifier-name newtype defined in js-ast/src/ident.rs. Equality is u32-id comparison; used for identifiers, keywords, and string-literal names. See ADR-19.
Binding
A named entity in a Scope: Binding{ name: Atom, kind: BindingKind, tdz: bool, mutable: bool, decl_span: Span }. Resolved by resolve_references up the parent chain. See §11.4.
BindingKind
Enum distinguishing Var, Let, Const, Function, Class, Param, Import, CatchParam. Governs hoisting and TDZ behaviour. See §11.4.
Completion
Enum: Normal(Value), Throw(Value), Return(Value), Break(Option<Atom>), Continue(Option<Atom>). The universal return type of all eval_* functions (I19). See §11.5.
Cover Grammar
A production in ECMA-262 that encompasses two possible syntactic interpretations, resolved by a subsequent token. Key examples: CoverParenthesizedExpressionAndArrowParameterList, CoverCallExpressionAndAsyncArrowHead.
CowStr
Copy-on-write string: Borrowed(&'src str) for escape-free identifiers/strings; Owned(String) for escape sequences. Minimizes allocation in the hot path. See ADR-19.
EarlyError
A static validity constraint from ECMA-262 §8/§16 that must be reported before evaluation. Collected into Parser.errors: Vec<SyntaxError> / analyze's Vec<EarlyError> rather than returned immediately (I25).
EnvironmentRecord
Runtime scope record, enum with 5 variants: Declarative(DeclEnv), Object(ObjEnv), Function(FnEnv), Global(GlobalEnv), Module(ModuleEnv). Holds value slots. See §11.5, §21/P9.
ESTree
Community-standard JSON schema for JavaScript ASTs, used by Acorn, Babel, and others. The differential oracle for 259's parser output.
Evaluator
Trait defined in js-runtime: fn evaluate(&mut self, node: &Stmt, ctx: &mut ExecutionContext) -> Completion. The contractual boundary between 259 and engine 126. See ADR-14, §11.5.
ExecutionContext
Runtime frame: ExecutionContext{ env: EnvId, realm: RealmId, function: Option<FnHandle> }. Lives on the execution-context stack. See §11.5, §21/P9.
EBNF
Extended Backus-Naur Form. Used in §8.2 to express JS grammar fragments normatively.
GDI
GlobalDeclarationInstantiation. Reads ScopeTree to allocate global var/function bindings before executing a script. See §21/P9.
Invariant
A property that must hold across all phases. 25 invariants (I1–I25) listed in §7. Violations are bugs, not design choices.
LexGoal
Enum { Div, RegExp, TemplateTail } passed from parser to lexer before each /-ambiguous scan. See ADR-9, MM1.
Live Binding
An import binding that aliases an export slot in the exporting module's env; not a snapshot. Value changes in the exporter are visible to all importers (I17). See §22/P10.
ModuleRecord
enum ModuleRecord { SourceText(SourceTextModuleRecord) }. SourceTextModuleRecord stores realm, code: Program, requested_modules, import_entries, local_export_entries, status: ModuleStatus, environment: Option<EnvId>. See §11.5.
ModuleStatus
FSM: Unlinked → Linking → Linked → Evaluating → Evaluated. Monotone; used as cycle guard in DFS (I18, MM6). See §22/P10.
ParseCtx
Context struct threaded through recursive parse calls: ParseCtx{ strict, in_function, in_loop, allow_await, allow_yield } (plus allow_in gate). See §11.3.
Pratt Parser
Top-down operator precedence parser. Assigns left_bp/right_bp to each operator token; a single loop handles all expression precedence. See ADR-8, MM7, P2/§14.
Program
Root AST node: Program{ body: Vec<ModuleItem>, source_type: SourceType, span: Span } where SourceType ∈ {Script, Module}. See §11.2.
Realm
Isolated execution context carrying global_env, a global-object hook, and a host-supplied intrinsics hook (no built-in library; ADR-14, Design Principle 14). See ADR-13, §21/P9.
ResolveSet
Set of (ModuleRecord, ExportName) pairs used to detect circular export * re-exports during resolve_export. Grows with the depth of re-export chains.
SCC
Strongly Connected Component. Tarjan's algorithm applied to the module graph during link to detect and short-circuit cycles without infinite recursion. See §22/P10, MM6.
Scope
Entry in ScopeTree: Scope{ kind: ScopeKind, parent: Option<ScopeId>, bindings: Vec<Binding>, strict: bool }. See §11.4.
ScopeKind
Enum: Global, Module, Function, Block, Catch, With, ClassStaticBlock. Governs which declarations hoist out. See §11.4.
ScopeTree
Arena of Scope nodes, indexed by ScopeId. Output of js-semantics. Consumed by js-runtime for env instantiation and by the CLI for jsfront scopes. See §11.4.
Span
Span{ lo: u32, hi: u32 } byte offsets into the source. Present on every AST node (I3). Never stores line/column — computed on demand. See ADR-6.
TDZ
Temporal Dead Zone. The period between a let/const binding's hoisted existence and its initialization. Accessing in TDZ → ReferenceError (I15). See MM3.
Test262
Official ECMAScript conformance test suite (~50k tests). 259 targets ≥14k cases by P13 with <2% unexpected failure (§25/P13). Sharded in CI.
Token
enum Token<'s> with variants (Ident, Keyword, Punctuator, NumericLiteral, StringLiteral, TemplatePart, RegExpLiteral, Eof, …). Produced by Lexer, consumed by Parser; positions tracked via byte pos → Span. See §11.1, §8.1. ---
