259 — JavaScript Parser + Runtime Integration

Goal: Build, from scratch in Rust, an ECMAScript front-end + runtime-integration layer — a goal-directed lexer, a recursive-descent + Pratt parser producing an ESTree-compatible immutable AST, full static semantics (scope, hoisting, TDZ, strict mode, early errors), and the runtime linkage layer (Realm, Environment Records, Script/Module Records, module resolution + linking with live bindings, and an Evaluator bridge). It is the parse-and-link front-end that an execution engine (project #126) plugs into — not the optimizing VM itself. Differential-test the AST against Acorn/SWC and validate against a Test262 subset.

1. Goal

Build a from-scratch, ECMAScript-2023 front-end + runtime-integration layer in Rust: a Unicode-correct lexer, a recursive-descent + Pratt parser emitting an immutable ESTree AST with byte Spans, full static semantics (scope/binding/hoisting/TDZ/strict/early-errors), and the runtime linkage — ScriptRecord/ModuleRecord, Realm, EnvironmentRecord, module resolution/linking with live bindings + cyclic modules, and a normative Evaluator bridge. 259 produces what 126 executes.

2.2 Unique Knowledge (not found in CRUD work)

Goal-directed lexing parser sets LexGoal per position / ambiguous; context-free lexer mis-tokenizes a/b/g vs /re/g

2.3 Engineering Muscles

  • Recursive descent + Pratt precedence — operator-precedence parsing
  • Cover grammar refine-in-place — ambiguity without backtracking
  • Goal-directed lexer↔parser feedback — coupled state machine
  • ScopeTree arena + BindingKind — name resolution, TDZ as data
  • ESTree immutability + byte Span — stable IR, differential-testable
  • 3-phase module linking — dependency graph, SCC/cycle handling
  • Evaluator trait + Completion — execution CONTRACT across crate boundary
  • no_std + alloc on untrusted input — memory safety on hot path

6. Design Principles

# Principle Rule → why → violation
6.1 ECMA-262 is the oracle Spec algorithm/grammar wins over intuition; cite the section number or SDO by name. Violation: "fixing" ASI to match a blog instead of §12.10.
6.2 Parsing never panics Malformed input → ParseError, never panic!/unwrap; fuzzed in P13. Violation: indexing src[pos] past EOF.
6.3 Goal-directed lexing Parser drives LexGoal{Div,RegExp,TemplateTail}; lexer never guesses /. Violation: lexing /regex/ as Div after return (P1,P6).
6.4 Cover then refine, never double-parse Parse cover once, reinterpret on =>; no re-tokenize. Violation: re-running parse_expr after => → O(n²) (P5).
6.5 ESTree-compatible AST Node shapes/field names mirror ESTree; differential-testable vs Acorn/SWC. Violation: renaming Member fields → diff false-positives.
6.6 Immutable AST, byte Spans Program frozen after parse; positions = Span{lo,hi:u32} byte offsets. Violation: mutating nodes in semantics → aliasing bugs.
6.7 Strict by spec, lenient nowhere Strict-mode early errors enforced exactly; modules always strict. Violation: allowing octal 0755 under strict → conformance fail (P7).
6.8 Static semantics are a separate pass js-semantics::analyze runs over finished AST; js-parser only collects syntactic early errors. Violation: resolving bindings during parse → can't reorder, breaks incremental (P8,P12).
6.9 Hoisting/TDZ modeled explicitly var/Function hoist to fn/script scope; let/const/class hoist to block head with Binding.tdz=true. Violation: treating let as un-hoisted.
6.10 Live bindings for modules Imports are live views of the exporter's env slot; ResolveExport detects ambiguous + circular. Violation: snapshotting import value at link (P10).
6.11 Bounded recursion Depth capped ~1000; deep nesting → graceful ParseError, not stack overflow. Violation: unbounded parse_expr recursion.
6.12 Errors carry Spans Every ParseError/EarlyError/LinkError carries byte Span. Violation: "unexpected token" with no location.
6.13 Evaluator is an interface js-runtime defines Evaluator trait + Completion; 126 supplies the VM. Violation: hardcoding eval logic in js-runtime.
6.14 Host supplies the world Intrinsics, global_object, module sources via hooks; no built-in library. Violation: baking Array.prototype into Realm.
6.15 Incremental-friendly Arena-allocated ScopeTree, span-keyed nodes, side-effect-free passes. Violation: global mutable parser state (P12).

8.2 Grammar (EBNF, ES2023 — abridged, load-bearing productions)

Script        ::= StatementList?
Module        ::= ModuleItemList?
ModuleItem    ::= ImportDeclaration | ExportDeclaration | StatementListItem

Statement     ::= Block | VariableStatement | EmptyStatement | ExpressionStatement
                | IfStatement | BreakableStatement | ReturnStatement | ThrowStatement
                | TryStatement | LabelledStatement | WithStatement | DebuggerStatement
IterationStatement ::= "do" Statement "while" "(" Expression ")" ";"
                | "while" "(" Expression ")" Statement
                | "for" "(" ForHeader ")" Statement
ForHeader     ::= Expression? ";" Expression? ";" Expression?
                | (("var"|LexicalKw) ForBinding | LeftHandSide) ("in"|"of") Expression
LexicalDeclaration ::= ("let"|"const") BindingList ";"
Expression    ::= AssignmentExpression ("," AssignmentExpression)*
AssignmentExpression ::= ConditionalExpression | ArrowFunction | YieldExpression
                | LeftHandSide AssignmentOperator AssignmentExpression
ShortCircuitExpression ::= LogicalORExpression | CoalesceExpression
CoalesceExpression ::= CoalesceExpr "??" BitwiseORExpression  (* ?? NOT mixable w/ &&,|| *)
UnaryExpression ::= ("delete"|"void"|"typeof"|"+"|"-"|"~"|"!"|"await") UnaryExpression

Mental Models & First Principles

MM1 — The lexer-parser are one coupled state machine, not a pipeline.

  • Insight: JS tokenization is context-sensitive; the lexer cannot decide / = Div vs RegExp without knowing the parser's syntactic position. LexGoal is the channel from parser to lexer on every request.
  • What it predicts: any attempt to separate lexer and parser into independent stages produces mis-tokenized /regex/ patterns — the canonical JS implementation bug.
  • Bug class without it: a/b/g parsed as a / b / g (division chain) instead of a / (/b/g).
  • Applies at: §13 (P1, LexGoal design), §18 (P6, goal protocol), §8.1 (token model).

MM2 — Cover grammars are deferred disambiguation, not ambiguity.

  • Insight: (a, b) is grammatically a parenthesized expression OR arrow parameters depending on whether => follows. The spec defines a cover production that encompasses both; the parser reads it once and reinterprets on the deciding token.
  • What it predicts: any backtracking scheme re-lexes tokens and is O(n²) on long arrow heads.
  • Bug class without it: (a={f()}, b) => triggers a full re-parse of the args, causing quadratic blowup or span drift.
  • Applies at: §17 (P5, cover refinement), §16 (P4, arrow head).

MM3 — Hoisting creates two bindings for every let/const: the temporal dead zone and the initialized slot.

  • Insight: let x = 1 hoists x to block scope top (making shadowing predictable) but places it in TDZ — uninitialized — until the declaration point. The binding exists statically; the value does not.
  • What it predicts: x; let x is not "undeclared" — it is "declared but uninitialized" → ReferenceError at runtime, not TypeError.
  • Bug class without it: treating let as not hoisted → wrong use-before-decl diagnostics; implementing TDZ with a runtime sentinel rather than a static slot flag misses static analysis opportunities.
  • Applies at: §20 (P8, ScopeTree TDZ), §21 (P9, env slot uninitialized).

MM4 — Module live bindings are aliased slots, not copied values.

  • Insight: import { x } from "m" does not snapshot x; it creates an alias into m's Module env slot. Assigning to x in m is visible through the import.
  • What it predicts: CreateImportBinding must store (EnvId, slot_index) — a reference — not Value.
  • Bug class without it: copy-on-import semantics break all mutable shared state across modules; tests pass with constant exports but fail with mutated ones.
  • Applies at: §22 (P10, live binding wiring), §8.6 (worked example B).

MM5 — Completion is a tagged union that models ALL non-local control flow.

  • Insight: every JS statement produces a Completion: Normal, Throw, Return, Break(label), Continue(label). The evaluation bridge must propagate these faithfully — finally overrides with its own completion; label mismatch on Break/Continue stops at the wrong boundary.
  • What it predicts: any integer return-code scheme fails to distinguish return from break from throw, making finally semantics impossible.
  • Bug class without it: try { return x } finally { return y } returns x instead of y (finally overrides).
  • Applies at: §23 (P11, Completion propagation), §21 (P9, ExecutionContext stack).

MM6 — The parse→link→evaluate 3-phase ordering is cycle-safe because ModuleStatus is a monotone FSM.

  • Insight: a cyclic import graph a↔b would deadlock a 1-phase eager evaluator. The spec's DFS with Linking/Evaluating in-progress markers allows visiting a cycle without re-entering it: the second visit sees ≥Linking and skips.
  • What it predicts: without status guards, InnerModuleLinking on a cycle recurses infinitely.
  • Bug class without it: stack overflow on import a from "./a.js" self-import; or incorrect partial-link for diamond graphs.
  • Applies at: §22 (P10, link DFS), §8.7 (link sequence diagram).

MM7 — The Pratt binding-power model replaces recursive grammar nesting with a single iterative loop.

  • Insight: traditional recursive descent requires one function per precedence level (O(levels) stack frames per token). Pratt assigns left_bp/right_bp to each operator; a single loop handles all expression parsing with one frame.
  • What it predicts: deep expression chains a+b+c+... (10k ops) use O(1) stack instead of O(k).
  • Bug class without it: recursive expression parsers overflow on adversarial input; also, right-associativity (**) requires special-casing each level.
  • Applies at: §14 (P2, Pratt implementation), §5.2 (Pratt 1973).

MM8 — no_std + alloc is a correctness guarantee, not a portability feature.

  • Insight: no_std prevents any std::net/std::fs from entering core crates at compile time. The linker-level check is stronger than any code review. It is the enforcement mechanism for the isolation contract (C-10, C-12).
  • What it predicts: a no_std build failure catches accidental I/O imports that would break embedded deployments or introduce SSRF vectors.
  • Bug class without it: a transitive dep could add filesystem access to js-runtime, allowing a host engine to be surprised by implicit file reads.
  • Applies at: §12 (P0, no_std CI gate), §4 (C-12), §10 (all core crates).

MM9 — ESTree shape is the integration test, not just a format.

  • Insight: jsfront parse JSON must byte-diff-equal Acorn's output (modulo normalized fields) on any valid input. This is not just a compatibility goal — it is the only scalable way to prove grammar correctness across thousands of edge cases without hand-writing golden files for each.
  • What it predicts: any grammar divergence from Acorn on a valid input is either a bug in our parser or a deliberate spec-driven deviation (documented in the allowlist).
  • Bug class without it: parser ships with silent ASI errors, wrong precedence, or missing optional chain handling that only surface in production.
  • Applies at: §25 (P13, differential), §5.3 (Acorn reference).

MM10 — ScopeTree is the only correct interface between the parser and the runtime; the AST is not.

  • Insight: the AST knows where identifiers appear; ScopeTree knows what they resolve to and how they're hoisted. GlobalDeclarationInstantiation and InitializeEnvironment read ScopeTree, not the AST.
  • What it predicts: passing raw AST Ident nodes to the runtime requires the runtime to redo scope analysis — duplicating work and creating drift.
  • Bug class without it: the runtime re-implements hoisting logic and diverges from the semantics pass, producing different TDZ behavior in different contexts.
  • Applies at: §20 (P8, ScopeTree design), §21 (P9, GDI reads ScopeTree), §22 (P10, InitializeEnvironment).

Back-of-Envelope Capacity Model

Derived from System Constraints (§4). All formulas shown.

N1 — Lexer throughput ceiling:

  • Source: C-03 (>20 MB/s parse), C-08 (lexer total), benchmark target ≥250 MB/s lex.
  • Formula: lex_ns_per_byte = 1 / (250 MB/s) = 4 ns/byte. At 3.5 GHz, 4 ns × 3.5 cycles/ns = ~14 cycles/byte budget.
  • Implication: hot path (ASCII ident scan + trivia skip) must fit in ≤14 cycles/byte; no String allocation, no Unicode table lookup on ASCII.

N2 — AST memory per source file:

  • Source: C-01 (≤48 B/node), C-04 (~6-12× source bytes), C-13 (Span=8B).
  • Formula: typical JS has 1 AST node per ~5-8 source bytes → 1 MB source → ~150k nodes → 150k × 48 B = 7.2 MB AST. Plus ScopeTree: ~1 Binding per 3 nodes → 50k × ~40 B = 2 MB. Total: ~9.2 MB for 1 MB source = 9.2× multiplier (within C-04 6-12× band).

N3 — Parser stack depth budget:

  • Source: C-06 (hard cap 1024 nesting), typical JS call stack ~8 MB.
  • Formula: typical Pratt frame ~200 B → 1024 × 200 B = 205 KB stack. Well within 8 MB. Deep arrow nesting (((((f)=>g)=>h)=>...)=>x) 1000-deep: 200 KB used → safe.

N4 — Module graph link time:

  • Source: OR.2 SLO (≤10 ms / 100-module graph), SA.2 O(V+E).
  • Formula: link_ns_per_module = 10 ms / 100 = 100 µs/module. 100 µs includes: parse_module_record (entry extraction), InitializeEnvironment (env alloc + binding wiring), resolve_export (per-import lookup). At 40 MB/s analyze throughput, a 2 KB avg module takes 2000 B / 40 MB/s = 50 µs → remaining 50 µs for env ops. Feasible with FxHashMap O(1) lookups.

N5 — Fuzzing corpus coverage target:

  • Source: P13/§25 (≥10M iters fuzz, 30 min nightly).
  • Formula: 30 min × 60 s/min × 1000 executions/s (libFuzzer typical) = 1.8M execs. At 10M target: need ~5.6× speedup from structured corpus (Arbitrary AST rather than raw bytes). Structured corpus achieves ~10× speedup → feasible within 30 min budget.

N6 — Span address space:

  • Source: C-13 (lo/hi = u32, source ≤ 4 GiB).
  • Formula: u32 max = 4,294,967,295 bytes = 4 GiB source file limit. Actual JS files: largest known bundled JS ~30 MB. 4 GiB is 4000 / 30 = 133× headroom → u32 is correct and never a bottleneck for real-world inputs.

N7 — Atom interner memory:

  • Source: C-04, ADR-19 (Atom for names).
  • Formula: average JS file has ~2000 unique identifiers × avg 8 chars = 16 KB strings + FxHashMap overhead ~40 B/entry = 2000 × 40 B = 80 KB interner per file. Across a 100-module graph: 100 × 80 KB = 8 MB — well within typical process limits.

N8 — Test262 CI time:

  • Source: §25 (≥14k cases, <180s sharded ×8).
  • Formula: 14k cases / 8 shards = 1750 cases/shard. At 180s budget: 180s / 1750 = 103 ms/case. Each case = file read + parse_script/parse_module + analyze + optional link. At 40 MB/s analyze: a 1 KB case = 1000B / 40 MB/s = 25 µs. Total overhead per case ~1 ms (process start, YAML parse). Actual: ~5 ms/case → 5 ms × 1750 = 8.75 s/shard — well within 180s.

Hard Questions (Self-Examination)

HQ1 — If parse_script returns Ok(Program) but jsfront scopes shows a Binding with tdz=false for a const declaration, which invariant is violated, and which two passes are candidates for the bug? → I14 (hoist/TDZ) in §7 is violated; I12 (resolve) is the cross-check. Candidates: collect_bindings (P8/§20) setting wrong BindingKind or missing tdz=true, OR the ScopeKind/Binding decision per the schema in §11.4 (block vs function scope). Resolution requires tracing collect_bindings for Const in js-semantics/src/collect.rs. Sources: §7 (I14/I12), §20 (P8), §11.4 (Binding schema).

HQ2 — A module cycle a↔b links successfully (status Linked) but jsfront eval prints the wrong value for b's export. The live binding is correctly wired. What is the most likely cause, and which section defines the fix? → Evaluation order in cyclic modules (§22/P10, InnerModuleEvaluation): post-order DFS must evaluate a before b if b depends on a's export. If b's initializer reads a.x before a has evaluated, it sees TDZ. Fix: verify topological order respects SCC; cross-reference §8.6 (worked example B) for the evaluation sequence.

HQ3 — Why does jsfront parse emit an ArrowFunctionExpression for async (x) => x but a CallExpression for async\n(x) when the only difference is a newline? → Restricted production (I8/§18): async + [no LineTerminator here] before ( is required for async-arrow disambiguation. With a LT, async is parsed as an identifier, (x) as a call's argument list. This is the CoverCallExpressionAndAsyncArrowHead disambiguation (§16/P4). Sources: §6.3 (ASI) + §4.6 (async-arrow pitfall).

HQ4 — The link function runs successfully on a diamond graph A→{B,C}→D but is called three times for module D. Which invariant is violated and what is the root cause? → I18 (idempotent link). Root cause: ModuleStatus guard not consulted before recursing — link is re-entering D without checking status ≥ Linking. Fix: add status guard at entry to InnerModuleLinking. See §22/P10, §8.7 (link sequence).

HQ5 — A conformance test reports a/b/c parses as a regex literal followed by c instead of a division chain. What is the minimal 2-section diagnosis path? → §13 (P1, LexGoal returned by lexer at / after a) and §18 (P6, goal set by parser before requesting the / token). The parser must have set RegExp goal when it should have set Div after the identifier a. Check: goal is Div after all operand tokens per §14/P2 leading table.

HQ6 — Why must EarlyError be collected into a Vec rather than returned as Err immediately, and which two design principles enforce this? → P12 (LSP needs full diagnostics), §6.2 (parsing never panics implies Result-only API, not fail-fast). A fail-fast approach would provide only the first error; LSP (proj 139) requires all errors in a file. Also I25 (error list complete + source-ordered) mandates collection. Sources: §6 (Design Principles 6.2, 6.12), §7 (I25), §24 (P12).

HQ7 — resolve_export(m, "x") returns Ambiguous even though only one module exports x. What sequence of star re-exports produces this, and which abstract operation detects it? → Diamond re-export: m does export * from "a" and export * from "b", and both a and b export x (possibly from a shared dependency). ResolveExport (§22, resolve.rs) accumulates all resolved bindings into ResolveSet; size > 1 → Ambiguous. Fix: deduplicate same (module, binding) pairs (same ultimate source is not ambiguous). Sources: §22/P10 + §8.8 (early-error catalog).

HQ8 — An embedder calls parse_module and analyze successfully, then calls link and gets LinkError::NotFound. The module file exists on disk. What is the most likely missing step? → The embedder did not implement ModuleLoader::resolve correctly — probably returned a stub or used a loader that doesn't read from disk. js-cli's file loader is the only concrete std impl; embedders must supply their own. Sources: §22 (P10, ModuleLoader), §3.2 (component responsibilities), §11.5 (ModuleLoader trait).

HQ9 — Why can two var x declarations in the same scope not generate a DuplicateLexical early error, but two let x declarations do? → var allows redeclaration: CreateGlobalVarBinding/CreateMutableBinding for var is idempotent (I13 says no duplicate lexical binding). let enters LexicallyDeclaredNames; the invariant requires disjointness from other lexical names in the same scope. Mechanism: collect_bindings in js-semantics merges Var bindings, flags Let/Const duplicates as EarlyError. Sources: §8 (I13), §20 (P8, collect_bindings), §8.8 (early-error catalog).

HQ10 — Why does 259 define Completion as an enum rather than using Rust's Result<Value, Error>, and what does Break(Option<Atom>) enable that Err(BreakSignal) cannot? → Result<V,E> is binary (ok vs error); JS control flow has 5 completion types — Break/Continue carry an optional target label for labeled loops. Err(BreakSignal) would require the VM to re-examine the label on every unwinding frame. Completion::Break(Some(Atom)) carries the label inline, allowing the ExecutionContext stack to unwind to exactly the right labeled scope without re-matching. Sources: §23 (P11, Completion), §11.5 (Completion enum), §7 (I19).

HQ11 — If parse_script takes 200 ms for a 4 MB file (only 20 MB/s), what are the three most likely bottlenecks in order of probability? → (1) AST allocation churn: CowStr::Owned allocated for identifiers that should borrow — check escape rate in lexer, ensure ASCII idents use Borrowed. (2) Expr enum >48 B causing cache thrashing — run size_of::<Expr>() assert, check if recent variant additions broke boxing. (3) Unicode ID_Continue table lookup on ASCII — ensure byte-class LUT path fires before wide-char table. Sources: §25 (P13, profiling), the Performance Engineering section (Allocation Strategy, PE.2), §13 (P1, lexer perf).

HQ12 — A property test discovers that parse(print(parse(src))) produces a different AST from parse(src). What are the two most likely codegen bugs? → (1) Parenthesization: printer drops parens required for precedence (e.g., (a,b) sequence expression as function argument) — fix: consult bp table during print. (2) ASI hazard: printer emits return\n value without a ;, and re-parse inserts ASI turning it into return; value — fix: always emit ; or keep operand on same line. Sources: §24 (P12, roundtrip), §18 (P6, ASI), §12.6 (pitfalls).

HQ13 — Why must SourceTextModuleRecord.code (the Program) and ScopeTree be kept separately rather than embedding scope into the AST nodes? → The AST is immutable and Send+Sync post-parse; embedding mutable scope data would require Mutex/RefCell per node, destroying cache locality and concurrency. The ScopeTree is built in a separate pass, is itself immutable post-analysis, and can be independently cached (invalidated by source change) or shared across multiple Realms without re-parsing. Sources: §3.2 (component responsibilities), §11.5 (type semantics), §20/P8 (separate pass rationale — design principle 6.8).

HQ14 — An engine (project 126) reports that const c = 1; c = 2 does not throw TypeError at runtime. Is this a 259 bug or a 126 bug, and which invariant defines the responsibility boundary? → 259's responsibility: ScopeTree.Binding{ name:"c", kind:Const, mutable:false } must be set correctly (I14). EnvironmentRecord.create_immutable_binding must mark the slot immutable; set_mutable_binding on an immutable+strict slot must return Completion::Throw(TypeError) (I15). If those are correct, the bug is in 126's Evaluator not consulting the immutability flag. Diagnosis: dump jsfront scopes to confirm mutable:false, then test the set_mutable_binding abstract op directly. Sources: §7 (I14/I15), §21/P9 (EnvRecord ops, acceptance criterion 5), §11.5 (EnvironmentRecord contract).

HQ15 — The Test262 EarlyError bucket has 3 unexpected failures after adding generator support (P4). All three involve yield in default-parameter expressions. Which interaction between three passes causes this? → (1) js-parser (P4/§16): allow_yield in ParseCtx must be false for default parameter expressions even inside generators — parameters parse before the body context. (2) js-semantics (P8/§20): collect_bindings for a generator function sets allow_yield=true for the body but must not propagate that into default-param initializer scope. (3) Early-error check (P7/§19): yield as an expression in strict-mode default param is forbidden. The bug is likely ParseCtx leaking allow_yield=true into param initializer parse. Sources: §16 (P4, §4.6 pitfalls), §19 (P7, strict/early), §20 (P8).

Alternative Architectures (Roads Not Taken)

Alt-1: Parser Combinator Kit (project 63 generic approach)

source bytes
    │
    ▼
Parser<Rule> ── combinator chain ──▶ CST/AST
    │
    (backtracking on mismatch)

Regime where it wins: grammars that are truly context-free with no goal-symbol feedback, where maintainability > throughput and the grammar is small and stable. Good for embedded DSLs (project 41).

Real system embodying it: nom (Rust), pest (Rust PEG), menhir (OCaml LR). ECMAScript parsers like tree-sitter-javascript use a generated parser from a formal grammar.

Why 259 rejected it: ECMA-262 requires goal-directed lexing (LexGoal is parser-owned state), cover-grammar reinterpretation that requires imperative single-pass logic, and ASI restricted-production checks that depend on whether a line terminator precedes the current token. These make the grammar impossible to express as a pure combinator. Backtracking combinators also create O(n²) worst-case on cover-grammar patterns. See ADR-8.

Alt-2: Shared-Nothing Parse Tree (token-soup / offset-only IR)

source bytes
    │
    ▼
token array [Token{kind, lo, hi}...]
    │
    ▼
parse table → (kind, children: [idx...]) flat Vec

Regime where it wins: incremental reparsing where subtree invalidation must be O(1) and memory is extremely constrained (e.g., an LSP server holding 1000 open files in a 1 GB process). Tree-Sitter's concrete syntax tree is the canonical example.

Real system embodying it: Tree-Sitter (C/Rust), rust-analyzer's rowan library.

Why 259 rejected it: ESTree compatibility requires typed nodes with named fields (not generic (kind, children) tuples). Differential testing against Acorn requires structural equality, not offset equality. An offset-only tree makes ScopeTree construction require re-traversal of the token array, not the typed AST — duplicating complexity. ADR-5 chose typed enum AST explicitly.

Alt-3: Full Interpreter in-crate (no Evaluator trait boundary)

parse_script ──▶ Program ──▶ js-runtime::eval(Program) ──▶ Value
                (no Evaluator trait; VM baked in)

Regime where it wins: single-consumer deployments where there is exactly one target engine and the performance cost of trait dispatch is measurable and unacceptable. Boa's original architecture before the front-end/engine split.

Real system embodying it: Boa (early versions), QuickJS (C, single coherent binary), Duktape.

Why 259 rejected it: the entire architecture is built around the 259/126 seam — 259 produces, 126 executes. Baking the VM into js-runtime would couple every front-end change to engine internals, block 126 from using a JIT, and prevent other consumers (bundler, linter, type checker) from depending on front-end crates without pulling in a VM. See ADR-14, Design Principle 13 (Evaluator is an interface).

Alt-4: Tree-Sitter-Backed Incremental Parse

source bytes
    │
    ▼
tree-sitter-javascript (external C library)
    │ concrete syntax tree (CST)
    ▼
259 adapter: CST → ESTree Program
    │
    ▼
js-semantics, js-runtime as normal

Regime where it wins: when incremental re-parse performance is the primary requirement (LSP with large files, live syntax highlighting), and correctness of the ES spec grammar is enforced by the adapter layer rather than the parser itself.

Real system embodying it: rust-analyzer (uses rowan + a custom Tree-Sitter grammar), Helix editor, VS Code via tree-sitter grammars.

Why 259 rejected it: the adapter from Tree-Sitter's CST to ESTree is non-trivial for cover grammars and ASI; the CST includes trivia and raw tokens that must be reinterpreted. More critically, Tree-Sitter's grammar cannot express goal-directed lexing natively — the JavaScript grammar for Tree-Sitter uses heuristics for regex/div disambiguation that produce incorrect token streams for some inputs. The differential testing against Acorn would expose these divergences. 259 owns the full pipeline to guarantee spec fidelity. Incremental re-parse is addressed by P12 hooks (§24) instead.

Glossary

ADR — Architecture Decision Record. Numbered entry in §9 capturing a design choice, locked alternative, rationale, and when the rejected choice wins.

ASI — Automatic Semicolon Insertion. Three ECMA-262 §12.10 rules that implicitly insert ; at line boundaries and before }. Governed by I7/I8 and implemented in P6/§18.

AST — Abstract Syntax Tree. Typed enum tree rooted at Program. Nodes are ESTree-compatible, store Span, and are immutable post-parse. See §11.2.

Atom — Interned identifier-name newtype defined in js-ast/src/ident.rs. Equality is u32-id comparison; used for identifiers, keywords, and string-literal names. See ADR-19.

Binding — A named entity in a Scope: Binding{ name: Atom, kind: BindingKind, tdz: bool, mutable: bool, decl_span: Span }. Resolved by resolve_references up the parent chain. See §11.4.

BindingKind — Enum distinguishing Var, Let, Const, Function, Class, Param, Import, CatchParam. Governs hoisting and TDZ behaviour. See §11.4.

Completion — Enum: Normal(Value), Throw(Value), Return(Value), Break(Option<Atom>), Continue(Option<Atom>). The universal return type of all eval_* functions (I19). See §11.5.

Cover Grammar — A production in ECMA-262 that encompasses two possible syntactic interpretations, resolved by a subsequent token. Key examples: CoverParenthesizedExpressionAndArrowParameterList, CoverCallExpressionAndAsyncArrowHead.

CowStr — Copy-on-write string: Borrowed(&'src str) for escape-free identifiers/strings; Owned(String) for escape sequences. Minimizes allocation in the hot path. See ADR-19.

EarlyError — A static validity constraint from ECMA-262 §8/§16 that must be reported before evaluation. Collected into Parser.errors: Vec<SyntaxError> / analyze's Vec<EarlyError> rather than returned immediately (I25).

EnvironmentRecord — Runtime scope record, enum with 5 variants: Declarative(DeclEnv), Object(ObjEnv), Function(FnEnv), Global(GlobalEnv), Module(ModuleEnv). Holds value slots. See §11.5, §21/P9.

ESTree — Community-standard JSON schema for JavaScript ASTs, used by Acorn, Babel, and others. The differential oracle for 259's parser output.

Evaluator — Trait defined in js-runtime: fn evaluate(&mut self, node: &Stmt, ctx: &mut ExecutionContext) -> Completion. The contractual boundary between 259 and engine 126. See ADR-14, §11.5.

ExecutionContext — Runtime frame: ExecutionContext{ env: EnvId, realm: RealmId, function: Option<FnHandle> }. Lives on the execution-context stack. See §11.5, §21/P9.

EBNF — Extended Backus-Naur Form. Used in §8.2 to express JS grammar fragments normatively.

GDI — GlobalDeclarationInstantiation. Reads ScopeTree to allocate global var/function bindings before executing a script. See §21/P9.

Invariant — A property that must hold across all phases. 25 invariants (I1–I25) listed in §7. Violations are bugs, not design choices.

LexGoal — Enum { Div, RegExp, TemplateTail } passed from parser to lexer before each /-ambiguous scan. See ADR-9, MM1.

Live Binding — An import binding that aliases an export slot in the exporting module's env; not a snapshot. Value changes in the exporter are visible to all importers (I17). See §22/P10.

ModuleRecord — enum ModuleRecord { SourceText(SourceTextModuleRecord) }. SourceTextModuleRecord stores realm, code: Program, requested_modules, import_entries, local_export_entries, status: ModuleStatus, environment: Option<EnvId>. See §11.5.

ModuleStatus — FSM: Unlinked → Linking → Linked → Evaluating → Evaluated. Monotone; used as cycle guard in DFS (I18, MM6). See §22/P10.

ParseCtx — Context struct threaded through recursive parse calls: ParseCtx{ strict, in_function, in_loop, allow_await, allow_yield } (plus allow_in gate). See §11.3.

Pratt Parser — Top-down operator precedence parser. Assigns left_bp/right_bp to each operator token; a single loop handles all expression precedence. See ADR-8, MM7, P2/§14.

Program — Root AST node: Program{ body: Vec<ModuleItem>, source_type: SourceType, span: Span } where SourceType ∈ {Script, Module}. See §11.2.

Realm — Isolated execution context carrying global_env, a global-object hook, and a host-supplied intrinsics hook (no built-in library; ADR-14, Design Principle 14). See ADR-13, §21/P9.

ResolveSet — Set of (ModuleRecord, ExportName) pairs used to detect circular export * re-exports during resolve_export. Grows with the depth of re-export chains.

SCC — Strongly Connected Component. Tarjan's algorithm applied to the module graph during link to detect and short-circuit cycles without infinite recursion. See §22/P10, MM6.

Scope — Entry in ScopeTree: Scope{ kind: ScopeKind, parent: Option<ScopeId>, bindings: Vec<Binding>, strict: bool }. See §11.4.

ScopeKind — Enum: Global, Module, Function, Block, Catch, With, ClassStaticBlock. Governs which declarations hoist out. See §11.4.

ScopeTree — Arena of Scope nodes, indexed by ScopeId. Output of js-semantics. Consumed by js-runtime for env instantiation and by the CLI for jsfront scopes. See §11.4.

Span — Span{ lo: u32, hi: u32 } byte offsets into the source. Present on every AST node (I3). Never stores line/column — computed on demand. See ADR-6.

TDZ — Temporal Dead Zone. The period between a let/const binding's hoisted existence and its initialization. Accessing in TDZ → ReferenceError (I15). See MM3.

Test262 — Official ECMAScript conformance test suite (~50k tests). 259 targets ≥14k cases by P13 with <2% unexpected failure (§25/P13). Sharded in CI.

Token — enum Token<'s> with variants (Ident, Keyword, Punctuator, NumericLiteral, StringLiteral, TemplatePart, RegExpLiteral, Eof, …). Produced by Lexer, consumed by Parser; positions tracked via byte pos → Span. See §11.1, §8.1.
