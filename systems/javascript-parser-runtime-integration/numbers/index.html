Back-of-Envelope Capacity Model

Derived from System Constraints (§4). All formulas shown.

N1 — Lexer throughput ceiling:

  • Source: C-03 (>20 MB/s parse), C-08 (lexer total), benchmark target ≥250 MB/s lex.
  • Formula: lex_ns_per_byte = 1 / (250 MB/s) = 4 ns/byte. At 3.5 GHz, 4 ns × 3.5 cycles/ns = ~14 cycles/byte budget.
  • Implication: hot path (ASCII ident scan + trivia skip) must fit in ≤14 cycles/byte; no String allocation, no Unicode table lookup on ASCII.

N2 — AST memory per source file:

  • Source: C-01 (≤48 B/node), C-04 (~6-12× source bytes), C-13 (Span=8B).
  • Formula: typical JS has 1 AST node per ~5-8 source bytes → 1 MB source → ~150k nodes → 150k × 48 B = 7.2 MB AST. Plus ScopeTree: ~1 Binding per 3 nodes → 50k × ~40 B = 2 MB. Total: ~9.2 MB for 1 MB source = 9.2× multiplier (within C-04 6-12× band).

N3 — Parser stack depth budget:

  • Source: C-06 (hard cap 1024 nesting), typical JS call stack ~8 MB.
  • Formula: typical Pratt frame ~200 B → 1024 × 200 B = 205 KB stack. Well within 8 MB. Deep arrow nesting (((((f)=>g)=>h)=>...)=>x) 1000-deep: 200 KB used → safe.

N4 — Module graph link time:

  • Source: OR.2 SLO (≤10 ms / 100-module graph), SA.2 O(V+E).
  • Formula: link_ns_per_module = 10 ms / 100 = 100 µs/module. 100 µs includes: parse_module_record (entry extraction), InitializeEnvironment (env alloc + binding wiring), resolve_export (per-import lookup). At 40 MB/s analyze throughput, a 2 KB avg module takes 2000 B / 40 MB/s = 50 µs → remaining 50 µs for env ops. Feasible with FxHashMap O(1) lookups.

N5 — Fuzzing corpus coverage target:

  • Source: P13/§25 (≥10M iters fuzz, 30 min nightly).
  • Formula: 30 min × 60 s/min × 1000 executions/s (libFuzzer typical) = 1.8M execs. At 10M target: need ~5.6× speedup from structured corpus (Arbitrary AST rather than raw bytes). Structured corpus achieves ~10× speedup → feasible within 30 min budget.

N6 — Span address space:

  • Source: C-13 (lo/hi = u32, source ≤ 4 GiB).
  • Formula: u32 max = 4,294,967,295 bytes = 4 GiB source file limit. Actual JS files: largest known bundled JS ~30 MB. 4 GiB is 4000 / 30 = 133× headroom → u32 is correct and never a bottleneck for real-world inputs.

N7 — Atom interner memory:

  • Source: C-04, ADR-19 (Atom for names).
  • Formula: average JS file has ~2000 unique identifiers × avg 8 chars = 16 KB strings + FxHashMap overhead ~40 B/entry = 2000 × 40 B = 80 KB interner per file. Across a 100-module graph: 100 × 80 KB = 8 MB — well within typical process limits.

N8 — Test262 CI time:

  • Source: §25 (≥14k cases, <180s sharded ×8).
  • Formula: 14k cases / 8 shards = 1750 cases/shard. At 180s budget: 180s / 1750 = 103 ms/case. Each case = file read + parse_script/parse_module + analyze + optional link. At 40 MB/s analyze: a 1 KB case = 1000B / 40 MB/s = 25 µs. Total overhead per case ~1 ms (process start, YAML parse). Actual: ~5 ms/case → 5 ms × 1750 = 8.75 s/shard — well within 180s.
