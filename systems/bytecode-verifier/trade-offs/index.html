36. Alternative Architectures (Roads Not Taken)

A1 — The classic iterative data-flow verifier without stack maps (retained here, not rejected). This project implements this design as Phase 6, so it is not a road not taken in the usual sense — it is documented here as the baseline every alternative below is measured against. Sound, general, no producer cooperation required, and the most expensive strategy by section 34's numbers. Real embodying system: the original pre-Java-6 JVM verifier.

  [entry] --T--> [block] --join(LUB)--> [block] --T--> ... --> [fixpoint]
     ^                                     |
     +---------- re-queue on change -------+

Winning regime: legacy class files (pre-version-50) with no stack-map data available at all — the only regime where this project's Phase 10 alternative is structurally unavailable.

A2 — Proof-carrying code (Necula). The producer ships a full machine-checkable proof of type/memory safety; the verifier's job shrinks to proof-checking, a strictly cheaper and more general operation than either inference or stack-map checking, since the proof can certify properties beyond the fixed type lattice this project's Phase 4 defines.

  producer: [compile] -> [generate proof] -> [module + proof]
  consumer: [module + proof] -> [proof checker] -> accept/reject
                                  (no type lattice, no fixpoint at all)

Winning regime: a closed producer/consumer pair willing to build and maintain a proof generator and a matching proof-checking logic — a substantially larger investment than a type-lattice verifier, justified only when the properties needed exceed what a fixed lattice can express. Real embodying system: Necula's original proof-carrying-code work and its descendants in certified-compiler research. Rejected here: this project's target ISA (JVM-CF) has an existing, well-specified, fixed type-lattice verification story (JVMS 4.10) that a bespoke proof system would duplicate at much higher implementation cost for no soundness gain within this project's scope.

A3 — A single-pass validator via structured control flow (WebAssembly's approach). Constrain the instruction set itself to structured blocks (no arbitrary goto), making a single forward pass sufficient without any producer-supplied certificate.

  block(A){ block(B){ ...instrs... } br_if -> B } -> single forward pass, no joins to solve

Winning regime: a bytecode format still being designed, where structured control flow can be mandated from the start — exactly WebAssembly's position (Haas et al. 2017). Real embodying system: the WebAssembly Core Specification's validator. Rejected here: the JVM-CF target already has an existing, unstructured goto-based instruction set (JVMS chapter 6) that predates this project by decades; retrofitting structured-control-flow constraints is a different project (a new ISA), not a verifier for the specified target.

A4 — A formally-verified verifier (Leroy/CompCert-style machine-checked proof). Prove the verifier's soundness as a machine-checked theorem (e.g. in Coq) rather than establishing confidence via testing and fuzzing.

  Coq: def verify (m: Module) : bool := ...
       theorem verify_sound : forall m, verify m = true -> type_safe (execute m)
       (extracted to OCaml/Rust-callable code, proof checked once at build time)

Winning regime: a verifier deployed in a context where testing-based confidence is insufficient by policy (e.g. a formally-certified toolchain requirement) and the engineering investment in a proof assistant is available. Real embodying system: Leroy's own formalization work (2003) and CompCert-adjacent verified-compiler projects. Rejected here (deferred, PhaseDeferred("section 36 Alternative Architectures")): the engineering cost of a machine-checked proof exceeds this project's v1 budget; the soundness-fuzzing campaign (Phase 11) is the pragmatic substitute, providing strong empirical — not formal — confidence, with the formal route left open as a stated future direction rather than a rejected one.
