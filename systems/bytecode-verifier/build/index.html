⬜ Phase 0 — Skeleton, Structural Parser, CI and Conformance Corpus §12

Objectives

Stand up a compilable Rust workspace with the crate boundaries of section 1's Phase-0 list; implement the structural class-file parser (verifier-parser) that decodes raw module bytes into an immutable ClassFile/Method/Instruction structure without trusting any embedded length; wire CI; seed the conformance corpus directory structure that every later phase adds fixtures to.

Deliverable

A compilable workspace exposing verifier-parser::parse(bytes: &[u8]) -> Result<ClassFile, VerifyError> that decodes structurally well-formed class files and rejects malformed ones with a located VerifyError, plus a green CI pipeline and a seeded, documented conformance directory.

Acceptance
  • Zero panics and zero out-of-bounds reads across a 10,000-input coverage-guided fuzz run of fuzz/parser/decode_class_file (I7).
  • 100% of conformance/adversarial/parser-*.bin fixtures rejected with a located VerifyError, never a panic.
  • conformance/valid/minimal-method.bin parses to a ClassFile with exactly 1 method.
  • CI green on all four target platforms of section 4.
  • Parser throughput ≥ 400 MB/s on benchmarks/throughput/parser_sequential (section 4).
Fixtures
  • conformance/valid/minimal-method.bin — smallest legal one-method class file; expect accept-at-this-phase (structural only).
  • conformance/ill-typed/truncated-header.bin — header cut mid-field; expect VerifyError at header decode.
  • conformance/ill-typed/oversized-code-length.bin — code_length > 64 KiB; expect VerifyError before code-array allocation.
  • conformance/adversarial/recursive-length-bomb.bin — a length field crafted to request a huge allocation; expect rejection before allocation (P7).
Pitfalls
  1. Trusting a section's declared length before validating it fits within the remaining buffer — manifests as an out-of-bounds slice panic; root cause: skipping the bounds check ADR-12 mandates; debug via the parser fuzz corpus; recovery: add the missing check and a regression fixture.
  2. Allocating a Vec sized directly from an attacker-controlled count field — manifests as OOM under fuzzing; root cause: violating P7; signal: verify_oob_read_attempts_total stays flat while process RSS spikes; recovery: cap the allocation and reject past the cap.
  3. Nondeterministic constant-pool iteration order from using a hash-based container instead of the section's declared array order — manifests as flaky differential-test mismatches; root cause: violating P12; recovery: use index-ordered Vec storage only.
  4. Treating an unrecognized opcode as a silent no-op instead of a structural reject — manifests as later phases mistyping an unknown instruction's stack effect; root cause: incomplete opcode-table coverage; recovery: make the opcode decode exhaustive via Rust's enum match-exhaustiveness (section 1 Rust rationale).

⬜ Phase 1 — The Constant Pool and Type Resolution §13

Objectives

Implement verifier-cpool: resolve every constant-pool index referenced by an instruction or by the class file's own metadata into a concrete, tag-checked entry, and derive the VerificationType a reference constant denotes, per I8 and P3.

Deliverable

verifier-cpool::resolve fully wired such that every downstream phase resolves constant-pool operands exclusively through it; a descriptor sub-module converting JVMS 4.3 descriptor strings into VerificationType vectors.

Acceptance
  • Every fixture in conformance/valid/cpool-*.bin resolves every referenced index with no VerifyError.
  • Every fixture in conformance/ill-typed/cpool-*.bin is rejected with ConstantPoolIndexOutOfRange or a tag-mismatch VerifyError at the correct offset.
  • Resolution-chain depth is bounded at 8 (Methodref → Class/NameAndType → Utf8) and a fixture exceeding it is rejected, not stack-overflowed.
  • Zero panics across a 10,000-input fuzz run of resolve_cpool.
Fixtures
  • conformance/valid/cpool-methodref-chain.bin — a well-formed Methodref resolving through Class/NameAndType/Utf8; expect accept.
  • conformance/ill-typed/cpool-index-out-of-range.bin — an invokestatic referencing index 70000 in a 500-entry pool; expect ConstantPoolIndexOutOfRange (I8, section 8.11 #4).
  • conformance/ill-typed/cpool-tag-mismatch.bin — an instruction expecting a Class tag resolving to a Utf8 entry; expect a tag-mismatch VerifyError.
  • conformance/adversarial/cpool-resolution-cycle.bin — a crafted NameAndType/Methodref cycle; expect bounded-depth rejection, not a hang.
Pitfalls
  1. Off-by-one in JVMS's 1-indexed, 0-reserved constant-pool numbering — manifests as every resolution being shifted by one entry; debug via a fixture with a single distinguishable entry at index 1.
  2. Trusting Long/Double entries' JVMS-mandated "double-width slot" convention (they consume two constant-pool indices) — manifests as misaligned resolution for every entry after one; root cause: skipping the double-slot skip in the entry-count loop.
  3. Unbounded resolution-chain recursion on a crafted cyclic reference — manifests as a stack overflow; root cause: no depth bound (P7); recovery: cap depth at 8 and reject beyond it.
  4. Accepting malformed modified-UTF-8 in a Utf8 entry and passing it to a string comparison — manifests as a later phase silently mismatching class names; root cause: skipping 4.4.7 validation eagerly.

⬜ Phase 2 — The Instruction Table and Per-Instruction Stack Effects §14

Objectives

Implement verifier-isa: an exhaustive table of the JVM-CF opcode set with each instruction's stack effect (pops/pushes) and typing precondition expressed as an inference rule (section 8.2), consumed by Phase 5's transfer functions.

Deliverable

verifier-isa::stack_effect(op: &Opcode) -> StackEffect and verifier-isa::precondition(op: &Opcode, descriptor_ctx: Option<&Descriptor>) -> Precondition, fully covering the JVM-CF core opcode subset with no todo!()/panic fallback arm.

Acceptance
  • 100% of the JVM-CF core opcode subset has a table entry (measured by an exhaustiveness test, not manual audit).
  • conformance/valid/isa-*.bin fixtures (one per opcode category) verify their stack-depth delta matches the JVMS reference value exactly.
  • conformance/ill-typed/isa-wrong-operand-type.bin fixtures (one per category) are rejected with a precondition-mismatch VerifyError at the correct offset.
Fixtures
  • conformance/valid/isa-arithmetic-iadd.bin — two Int pushes then iadd; expect accept, net stack delta -1.
  • conformance/valid/isa-invoke-virtual.bin — a well-typed invokevirtual matching its resolved descriptor; expect accept.
  • conformance/ill-typed/isa-iadd-on-object.bin — iadd applied to two Object operands; expect precondition-mismatch VerifyError.
  • conformance/ill-typed/isa-invoke-arity-mismatch.bin — invokevirtual with one fewer argument on the stack than the descriptor requires; expect stack-underflow VerifyError.
Pitfalls
  1. Miscounting long/double's two-slot stack/local width — manifests as every subsequent instruction's stack-height accounting drifting by one; root cause: treating all types as uniformly one slot.
  2. Forgetting that invokeinterface and invokespecial have receiver-popping rules distinct from invokestatic — manifests as accepting a static call missing a receiver check it never needed, or rejecting a correct instance call.
  3. Encoding checkcast/instanceof as no-ops on the stack type when they actually narrow the static type post-instruction — manifests as downstream code being verified against the pre-cast type, silently weakening precision (not unsound here, but a completeness loss against P1's stance).

⬜ Phase 3 — The Control-Flow-Graph Builder §15

Objectives

Implement verifier-cfg: split a method's decoded instruction stream into basic blocks at every branch target, fallthrough boundary, and exception-handler boundary, and build the successor/predecessor edge set the fixpoint driver (Phase 6) walks, enforcing control-flow integrity (I3, P10).

Deliverable

verifier-cfg::build(method: &Method) -> Result<Cfg, VerifyError> producing a deterministically ordered Cfg with reachability marks, ready for Phase 4/6 consumption.

Acceptance
  • Every conformance/valid/cfg-*.bin fixture builds a Cfg whose block/edge count matches a hand-computed expected value exactly.
  • Every conformance/ill-typed/cfg-invalid-branch-target.bin fixture rejects with BranchTargetOutOfRange at the branch instruction's offset, never at a later phase.
  • CFG construction is deterministic: hashing the built Cfg twice from identical bytes yields an identical hash across 1,000 repeated runs.
  • A method engineered to produce 70,000 basic blocks rejects at the block-count ceiling (section 4), not via unbounded memory growth.
Fixtures
  • conformance/valid/cfg-diamond.bin — an if/else diamond rejoining before return; expect a 4-block CFG (entry, two branches, join) with exact edge count 4.
  • conformance/valid/cfg-exception-loop.bin — a loop wrapped in a try/catch; expect correct ExceptionHandler edges from every covered instruction to the handler block.
  • conformance/ill-typed/cfg-invalid-branch-target.bin — a goto into the middle of an invokevirtual instruction (section 8.11 #1); expect BranchTargetOutOfRange.
  • conformance/adversarial/cfg-block-explosion.bin — a method engineered to maximize block count relative to code size (e.g. every instruction a distinct branch target); expect either a correctly-built large-but-bounded CFG or a clean ceiling reject, never a hang.
Pitfalls
  1. Splitting blocks only at branch sources and forgetting fallthrough-after-terminator splits — manifests as a block containing unreachable trailing instructions after a return/athrow merged into the next block incorrectly.
  2. Building exception-handler edges from handler_pc alone without covering every instruction in [start_pc, end_pc) — manifests as a handler that only "protects" the first instruction in its range instead of the whole range.
  3. Hash-map-based edge storage producing nondeterministic iteration order — manifests as flaky replay hashes (violates P12); recovery: switch to Vec-based, offset-sorted storage.
  4. Failing to validate tableswitch/lookupswitch target counts against the instruction's own encoded table size before dereferencing — manifests as an out-of-bounds read on a crafted switch table (ties to I7).

⬜ Phase 4 — The Type Lattice and Least-Upper-Bound §16

Objectives

Implement verifier-types: the finite verification-type lattice of section 8.1 with a computable, exact least-upper-bound (LUB) operation, satisfying P2 and I9's finite-height termination requirement.

Deliverable

verifier-types::{join, is_assignable} fully specified over every VerificationType pair, with the lattice-height bound documented as a named constant consumed by Phase 6's iteration ceiling.

Acceptance
  • Property tests confirm commutativity, associativity, and idempotence of join over 10,000 randomly generated VerificationType pairs/triples with zero counterexamples.
  • conformance/valid/types-join-*.bin fixtures (one per join-table row of section 8.1) produce the exact documented join result.
  • The documented lattice-height bound matches the constant used by Phase 6's iteration ceiling (cross-checked by a compile-time assertion).
Fixtures
  • conformance/valid/types-join-int-int.bin — join(Int, Int) == Int.
  • conformance/valid/types-join-object-null.bin — join(Object(A), Null) == Object(A).
  • conformance/ill-typed/types-join-uninit-distinct-offsets.bin — two distinct new sites joining at a branch; expect join == Top, then a downstream precondition mismatch when that Top is used as a receiver (I10).
Pitfalls
  1. Implementing class-hierarchy join via a naive walk-to-common-ancestor without a depth bound on a crafted deep or cyclic hierarchy — manifests as a hang; recovery: bound the walk and fall back to Object/Top beyond it (P7).
  2. Treating Uninitialized(offset) joins as always Top regardless of offset equality — manifests as an unnecessary false reject on straight-line code re-verifying the same new site from two merged paths (a completeness bug, not soundness, but still a section 4 zero-false-reject violation).
  3. Implementing join asymmetrically (checking a against b but not the reverse case) — manifests as a property-test failure on commutativity; root cause: an incomplete match arm ordering assumption.

⬜ Phase 5 — Abstract-Interpretation Transfer Functions §17

Objectives

Implement verifier-absint: TransferFunction::apply for every opcode, applying section 8.2's stack-effect/precondition table to a concrete AbstractState, producing the symbolically-executed successor state or a VerifyError (Cousot & Cousot 1977's abstract interpretation, instantiated over the type domain).

Deliverable

verifier-absint::TransferFunction fully implemented over the JVM-CF core opcode subset, composable with Phase 6's fixpoint driver as T(instruction, state) -> Result<AbstractState, VerifyError>.

Acceptance
  • Every conformance/valid/absint-*.bin fixture's straight-line (single-block, no merge) method type-checks end to end with the exact final stack/locals state matching a hand-computed expected value.
  • Every conformance/ill-typed/absint-*.bin fixture is rejected with the precondition mismatch located at the exact failing instruction offset.
  • Stack-height bookkeeping matches max_stack exactly on conformance/valid/absint-max- stack-boundary.bin (a method using exactly its declared max_stack, no more, no less).
Fixtures
  • conformance/valid/absint-straight-line.bin — a linear sequence of loads, an add, and a store; expect the exact final locals/stack state.
  • conformance/valid/absint-max-stack-boundary.bin — a method whose peak stack depth exactly equals its declared max_stack; expect accept.
  • conformance/ill-typed/absint-exceeds-max-stack.bin — one push beyond the declared max_stack; expect a stack-depth-ceiling VerifyError (section 4, section 8.11 #7).
  • conformance/ill-typed/absint-read-unassigned-local.bin — reading locals[3] before any store to it; expect a definite-assignment VerifyError (I2).
Pitfalls
  1. Checking max_stack only at method-declaration time and never re-checking the live state.stack.len() after each push — manifests as accepting a method whose actual peak depth silently exceeds its declared ceiling (a real runtime stack-safety violation, I1).
  2. Treating a Long/Double local slot pair as two independent single-slot locals for definite-assignment purposes — manifests as accepting a read of the second physical slot of a Long as if it were an independently assignable Int slot.
  3. Returning a generic "type error" VerifyError without the instruction offset — breaks P6/P12's replayable-diagnostics requirement; recovery: always thread the offset through.

⬜ Phase 6 — The Worklist Fixpoint Over Straight-Line and Branching Code §18

Objectives

Implement verifier-fixpoint: Kildall's worklist algorithm (section 8.5) driving TransferFunction::apply and TypeLattice::join across the full CFG to a fixpoint, with a provable, bounded iteration count (I5, I9).

Deliverable

verifier-fixpoint::run(cfg: &Cfg) -> Result<FixpointResult, VerifyError> implementing the full worklist algorithm with a proven-bounded iteration count and deterministic block-visit order.

Acceptance
  • conformance/valid/fixpoint-diamond-converge.bin converges in exactly 2 iterations (matching section 8.5's worked example) and is accepted.
  • conformance/ill-typed/fixpoint-diamond-mismatch.bin is rejected with MergeMismatch at the join block's offset (matching section 8.5's second worked example).
  • 100 repeated runs on the same fixture produce an identical iteration count and identical block-visit order (determinism, P12).
  • A synthetic adversarial CFG engineered to maximize iterations still terminates within the documented iteration ceiling (I5) — never exceeds it, never hangs.
Fixtures
  • conformance/valid/fixpoint-diamond-converge.bin — section 8.5's converging worked example, literally encoded.
  • conformance/ill-typed/fixpoint-diamond-mismatch.bin — section 8.5's rejecting worked example, literally encoded.
  • conformance/valid/fixpoint-loop-widening.bin — a while-style back edge where the loop-carried local's type stabilizes after one extra iteration; expect accept with iteration count one more than the loop-free equivalent.
  • conformance/adversarial/fixpoint-max-iteration-probe.bin — a CFG shape (deep chain of merges) engineered to approach the iteration ceiling; expect either a correct, bounded accept or a clean FixpointDidNotConverge reject, never a hang (ties to section 34's worst-case derivation).
Pitfalls
  1. Using a HashSet/HashMap-backed worklist for "already queued" deduplication — manifests as nondeterministic block-visit order across runs (violates P12); recovery: use an ordered set (e.g. a Vec-backed dedup or a BTreeSet keyed by BlockId).
  2. Re-pushing a successor even when its joined state is unchanged — manifests as excessive re-iteration and a false-positive "approaching iteration ceiling" signal; root cause: comparing by reference/pointer instead of by value equality.
  3. Forgetting to include ExceptionHandler edges in the propagate step — manifests as a handler block's entry state never reflecting the protected region's actual types, a silent I11-adjacent unsoundness risk caught only by exception-specific fixtures (Phase 9).
  4. Seeding non-entry blocks with Top instead of Bottom — manifests as the very first join already widening to Top regardless of the real incoming state, masking real type information (a severe completeness bug, and potentially unsound if it hides a real mismatch that should have been caught rather than widened away).

⬜ Phase 7 — Merges at Control-Flow Joins §19

Objectives

Harden and exhaustively test the join/merge behavior at every kind of control-flow confluence point — multi-predecessor blocks, loop back-edges, and exception-handler entries — establishing I4 as a property that holds across the full CFG shape space, not just the Phase 6 worked examples.

Deliverable

A verified-by-fixture guarantee that every join kind in the CFG taxonomy uses the identical TypeLattice::join code path with no kind-specific special case, plus the stack-height- equality pre-check as a distinct, offset-located VerifyError.

Acceptance
  • One conformance/valid/join-*.bin and one conformance/ill-typed/join-*.bin fixture per join kind enumerated in 19.2 step 1 (minimum 4 pairs), all producing the exact documented VerifyError variant or accept.
  • A property test over 5,000 randomly generated 3-to-6-predecessor join scenarios confirms merge-order invariance with zero counterexamples.
  • conformance/ill-typed/join-stack-height-mismatch.bin is rejected with a distinct VerifyError variant from a same-height-but-type-mismatched join fixture (proving the two checks are not conflated).
Fixtures
  • conformance/valid/join-branch-branch.bin — two if branches converging with identical types; expect accept.
  • conformance/valid/join-backedge-widen.bin — a loop back-edge where the loop-carried local's type only stabilizes after the back-edge's second join; expect accept after the documented extra iteration.
  • conformance/ill-typed/join-stack-height-mismatch.bin — one predecessor leaves 2 stack slots live into the join, the other leaves 3; expect a stack-height VerifyError distinct from a type-mismatch VerifyError.
  • conformance/ill-typed/join-exception-handler-partial-init.bin — an object initialized on the non-exceptional path only, then used after a handler join; expect an I10 VerifyError at the post-join use site.
Pitfalls
  1. Special-casing back-edge joins with a "trust the loop invariant" shortcut instead of running the same join code path — manifests as an unsound accept of a loop whose carried type actually changes across iterations in a way the shortcut missed.
  2. Comparing stack height only after already attempting a per-slot type join on mismatched-length stacks — manifests as an index-out-of-bounds panic instead of a clean VerifyError; recovery: check height equality strictly before any per-slot access.
  3. Merging init_marks with a bitwise OR (marked-if-any-path-marks-it) instead of AND (marked-only-if-every-path-marks-it) — manifests as accepting use of an object initialized on only one of several converging paths, a direct I10 violation.

⬜ Phase 8 — Object-Initialization Tracking (Uninitialized Types) §20

Objectives

Implement verifier-init: full tracking of Uninitialized(offset) and UninitializedThis per section 8.7 and Freund & Mitchell 1999, closing the object-initialization-bypass class that motivated the paper (I10).

Deliverable

verifier-init fully wired into Phase 5's transfer functions for new/invokespecial <init>, and into Phase 6's constructor-entry seeding, closing every Uninitialized-related gap in section 8.11.

Acceptance
  • conformance/valid/init-new-dup-invokespecial.bin (the canonical idiom) accepts, and the post-<init> state shows both the originally-popped and the dup'd stack copies as Object(C).
  • conformance/valid/init-constructor-chain-superclass.bin (a constructor calling super()) accepts.
  • conformance/ill-typed/init-use-before-init.bin (field access on an Uninitialized value) rejects with an I10 VerifyError at the exact offending offset.
  • conformance/ill-typed/init-constructor-return-without-super.bin (a constructor returning on a path that never calls super()) rejects at the return offset.
  • conformance/ill-typed/init-distinct-new-sites-join.bin (two different new sites' results joining before a shared invokespecial <init>) rejects, since join of two distinct offsets is Top (Phase 4), and Top never matches the exact-identity precondition of step 3.
Fixtures
  • conformance/valid/init-new-dup-invokespecial.bin — the canonical construct idiom.
  • conformance/valid/init-constructor-chain-superclass.bin — super() call in every path.
  • conformance/ill-typed/init-use-before-init.bin — field read before <init>.
  • conformance/ill-typed/init-constructor-return-without-super.bin — missing super() on one path.
  • conformance/ill-typed/init-distinct-new-sites-join.bin — cross-site join before init.
Pitfalls
  1. Transitioning only the popped stack value on successful <init> and forgetting aliased copies elsewhere in locals/stack — manifests as a dup'd reference remaining Uninitialized forever, causing every subsequent use of that alias to falsely reject (a completeness bug that is extremely common in first implementations).
  2. Allowing Uninitialized values to be stored into and read back from a local without losing their special status — must be preserved exactly (they are not laundered by a store/load round-trip); the opposite bug (losing the status) is the actual I10 violation to guard against.
  3. Checking the join-then-init-check order incorrectly: if the merge (Phase 7) happens after an init check instead of before, a value that should have been forced to Top by a cross-site join might incorrectly still be checked against its pre-join identity.
  4. Forgetting that UninitializedThis composes with Phase 7's join exactly like Uninitialized(offset) — a constructor with an if/else where only one branch calls super() must still reject at any post-join use, not just at the literal return.

⬜ Phase 9 — Exception-Table and Subroutine Validation §21

Objectives

Implement the remainder of verifier-exc: full exception-handler-table validation (I11) and full JSR/RET subroutine call-graph analysis (I12), the two historically hardest structural verification problems (section 8.9).

Deliverable

verifier-exc fully implementing both exception-handler validation and JSR/RET subroutine analysis, wired into Phase 6's fixpoint via ExceptionHandler and Subroutine edges.

Acceptance
  • Every conformance/valid/exc-*.bin and conformance/valid/jsr-*.bin fixture accepts with the documented handler/subroutine entry states.
  • Every conformance/ill-typed/exc-*.bin and conformance/ill-typed/jsr-*.bin fixture rejects with ExceptionTableInvalid/SubroutineAmbiguous at the correct offset.
  • conformance/valid/jsr-two-call-sites-distinct-state.bin accepts and its per-call-site re-analysis produces two distinct handler-body verification passes (asserted via an internal iteration-count check, not just accept/reject).
  • A crafted mutually-recursive subroutine nesting fixture rejects cleanly at the depth ceiling, never hangs (bounded by the section 4 timing budget).
Fixtures
  • conformance/valid/exc-nested-try-catch.bin — nested try blocks with distinct handlers; expect correct per-handler entry states.
  • conformance/ill-typed/exc-handler-pc-mid-instruction.bin — handler_pc targeting a non-boundary offset; expect ExceptionTableInvalid.
  • conformance/valid/jsr-two-call-sites-distinct-state.bin — section 8.9's worked scenario.
  • conformance/ill-typed/jsr-ret-wrong-subroutine.bin — a ret using a ReturnAddress from a different subroutine's call site; expect SubroutineAmbiguous (I12).
  • conformance/adversarial/jsr-deep-recursive-nesting.bin — nesting depth engineered to exceed the ceiling; expect a clean bounded reject.
Pitfalls
  1. Analyzing a subroutine only once regardless of call-site count — manifests as either a false reject (if one call site's state is stricter and gets applied to all) or, dangerously, a false accept (if the analysis picks the looser call site's state and applies it to a call site that actually needed the stricter one) — this is precisely the historical JSR/RET unsoundness class (section 8.9), so this pitfall is the single most important one in this phase.
  2. Failing to bound per-call-site re-analysis nesting depth — manifests as exponential blowup on nested subroutines called from multiple sites at each level (a real T3 algorithmic-complexity attack vector, tied directly to this phase).
  3. Conflating two different subroutines' ReturnAddress types because both happen to be stored in the same local-variable slot number at different points — manifests as accepting a ret that returns to the wrong caller; recovery: tag ReturnAddress by call- site offset, never by slot number alone.
  4. Treating an exception handler's catch_type resolution failure (Phase 1) as a warning instead of a hard reject — manifests as accepting a handler that can never correctly type its caught value.

⬜ Phase 10 — Stack-Map-Frame Checking (the Lightweight Strategy) §22

Objectives

Implement verifier-stackmap: the JVMS 4.10.2 lightweight verification strategy — decode a producer-supplied StackMapTable attribute and check it against the computed abstract state in a single linear pass, as the fast alternative to Phase 6's iterative fixpoint (P8, ADR-03, section 8.6).

Deliverable

verifier-stackmap::check(method: &Method, table: &StackMapTable) -> Result<(), VerifyError> implementing the full JVMS 4.10.2 strategy as a selectable alternative to Phase 6's verifier-fixpoint::run, both satisfying the identical soundness contract (P8).

Acceptance
  • Every conformance/valid/stackmap-*.bin fixture (one per frame-encoding variant) checks successfully in a single pass with zero fixpoint iterations recorded.
  • Every conformance/ill-typed/stackmap-mismatch-*.bin fixture rejects with StackMapMismatch at the exact declared-frame offset that disagrees with the computed state.
  • conformance/ill-typed/stackmap-missing-frame-at-merge.bin (a merge point with no declared frame) rejects structurally before any type check runs.
  • Differential benchmark shows Phase 10's per-instruction cost is a constant factor independent of CFG merge count, versus Phase 6's cost scaling with iteration count (section 34).
  • Every fixture accepted by Phase 6's fixpoint strategy on a re-encoded (stack-map-equipped) version of the same method is also accepted by Phase 10's checker, and vice versa for rejects (P8's cross-strategy soundness-contract equivalence, tested differentially).
Fixtures
  • conformance/valid/stackmap-full-frame.bin — a full_frame-encoded merge point; expect single-pass accept.
  • conformance/valid/stackmap-chop-append.bin — a sequence exercising chop_frame/ append_frame delta encodings; expect correct frame materialization.
  • conformance/ill-typed/stackmap-mismatch-locals.bin — a declared frame whose locals disagree with the computed state; expect StackMapMismatch.
  • conformance/ill-typed/stackmap-missing-frame-at-merge.bin — a 2-predecessor block with no declared frame; expect a structural reject.
Pitfalls
  1. Computing the "current state" for the single-pass check by re-running a fixpoint anyway (defeating the entire linear-time point of this strategy) — manifests as no performance improvement over Phase 6 despite the differential benchmark existing precisely to catch this regression.
  2. Trusting the declared frame's locals length without validating it against max_locals before materializing a Vec of that length — a direct P7 violation on attacker-controlled frame data.
  3. Applying delta-encoded frames (chop_frame/append_frame) relative to the wrong "previous frame" when frames are not strictly offset-ordered — manifests as every subsequent frame after the first ordering violation being silently mis-materialized rather than rejected.
  4. Forgetting that a full_frame frame's declared state, not the previous frame's state, fully replaces the running "current frame" for subsequent delta computations.

⬜ Phase 11 — Soundness Fuzzing Campaign, Conformance Completion and Performance Hardening §23

Objectives

Run the defining test of this entire project (section 28): generate bytecode modules, verify them, execute every accepted module in an instrumented VM, and assert zero type-safety or memory-safety violations ever occur. Complete the conformance corpus to full coverage of every prior phase's rejection classes, and harden performance to the section 4/30 targets.

Deliverable

Acceptance
  • Zero accepted-but-unsafe modules across a sustained campaign of ≥ 10,000,000 generated modules per release cycle (the soundness acceptance criterion — not "robust", a hard count).
  • Every VerifyError variant (section 11) has ≥ 1 dedicated conformance fixture; every invariant I1–I13 has ≥ 1 dedicated fixture; measured by an automated coverage-cross- reference script, not manual audit.
  • Differential-testing verdict parity with the HotSpot verifier and Wasm reference validator on 100% of the shared-applicable corpus subset.
  • Verification throughput ≥ 400 MB/s and p99 latency < 5 ms on the section 4 benchmark suite, measured on the release-candidate build.
Fixtures
  • conformance/adversarial/fuzz-seed-corpus/ — the full mutation/grammar seed set feeding the campaign, checked into the repository for reproducibility (P12).
  • conformance/valid/coverage-cross-reference.bin — a synthetic index fixture (not an actual module) used by the coverage script to assert every VerifyError/I# has a real fixture; failing this fixture's check fails the build.
  • conformance/regressions/ — every soundness-fuzz-found issue from this phase's campaign, minimized and checked in permanently as a regression fixture.
Pitfalls
  1. Running the soundness campaign against a debug build with assertions that mask real unsoundness behind an early panic! instead of a VerifyError — manifests as the campaign reporting a "crash" instead of the actual soundness violation it should be classified as; recovery: fuzz the release build's logic paths, panics included, and triage every panic as a potential soundness bug until proven otherwise.
  2. Under-diversifying the module generator so it only ever produces JSR/RET-free, exception-free straight-line code — manifests as high iteration counts with zero meaningful coverage of Phases 8/9's hardest cases; recovery: weight the generator toward the historically hardest opcode categories explicitly.
  3. Treating a differential-testing divergence from the HotSpot verifier as automatically "our bug" — sometimes the reference itself has documented, cited quirks (e.g. known HotSpot leniencies); recovery: resolve every divergence with a citation to the relevant JVMS clause, not a silent match-the-reference patch.
  4. Locking the performance-regression gate's tolerance too tightly immediately after a large allocation-hotspot fix, causing routine noise to trip the gate — recovery: set the tolerance from a rolling baseline over several runs, not a single measurement.
